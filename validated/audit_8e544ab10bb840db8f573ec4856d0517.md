### Title
Permanent stopEpoch freeze via poisoned APR0 withdraw bucket when APR later becomes nonzero - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` hard-reverts with `NotAllowed()` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged KYC-passed lender can open a withdraw request while `unscaledApr == 0`, permanently populating `apr0TotalPrincipal`. If the APR is ever set nonzero (a normal, honest manager/CDO operation via `setApr`/`setAprsWithBuffer` or a scheduled APR change), every subsequent `stopEpoch`/`stopEpochWithDuration` reverts before `apr0TotalPrincipal` can be cleared, permanently freezing the epoch state machine and all funds in the vault. This mirrors the external bug class: a stored accounting invariant (`apr0TotalPrincipal` valid only while APR is 0) becomes unreachable once a mutable parameter (the APR) moves, and the resulting revert blocks all claims, just like `assert(reward >= currentStore.reward)` blocked unstaking.

### Finding Description
In `IdleCreditVault.requestWithdraw`, when `unscaledApr == 0` and the pool is not closed, the request is routed to `_requestWithdrawApr0`, which increments both the per-user `apr0Users[_user].principal` and the global `apr0TotalPrincipal` (IdleCreditVault.sol:285-286, 567-577). At epoch stop, `prepareStopEpochWithApr0` is invoked by the CDO and enforces:

```solidity
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

(IdleCreditVault.sol:505-508). The only paths that reduce `apr0TotalPrincipal` are:
- `prepareStopEpochWithApr0` itself setting it to 0 at the end (IdleCreditVault.sol:540) — unreachable because the function reverts earlier;
- `_clearWithdrawClaimForEpoch` during default finalization (IdleCreditVault.sol:822-830) — only reachable on the borrower-default path.

Crucially, `_settleApr0` (IdleCreditVault.sol:545-565) does **not** decrement `apr0TotalPrincipal`, so no user action can drain the bucket. Meanwhile `requestWithdraw` only routes to `_requestWithdrawApr0` when `unscaledApr == 0`, and there is no symmetric mechanism that clears or migrates the bucket when the APR rises. Once `apr0TotalPrincipal > 0` and `unscaledApr > 0` coexist, `prepareStopEpochWithApr0` — called inside `stopEpoch`/`stopEpochWithDuration` before the try/catch around `getFundsFromBorrower` (the call resolves `_expInterest` prior to `previewLossAdjustedWithdrawFunds` in `IdleCDOEpochVariant.stopEpochWithDuration`) — reverts unconditionally. Because `epochNumber` can never increment, `_settleApr0` can never settle requests either (`_reqEpoch >= epochNumber` early-returns forever), and the pool is bricked.

Attack sequence:
1. Epoch running, `unscaledApr == 0` (APR0 mode is a supported pool mode per the mapping rules).
2. Attacker (any KYC-passed lender holding tranche tokens) calls `IdleCDOEpochVariant.requestWithdraw(amount, tranche)` with a dust amount. `requestWithdraw` → `IdleCreditVault.requestWithdraw` → `_requestWithdrawApr0` → `apr0TotalPrincipal += _amount`.
3. Manager/CDO honestly sets APR > 0 via `setApr`/`setAprsWithBuffer` (IdleCreditVault.sol:217-235) or the next `stopEpoch` carries `_newApr > 0` — note even the same `stopEpoch` that would set a new APR reverts first, because `prepareStopEpochWithApr0` reads the *current* `unscaledApr`... The freeze requires `unscaledApr` to already be nonzero while the bucket is non-empty, which occurs when the manager raises the APR mid-epoch before stopping.
4. All subsequent `stopEpoch`/`stopEpochWithDuration` calls revert with `NotAllowed`. `epochNumber` is frozen, so no withdraw request ever matures (`epochNumber <= lastWithdrawRequest` forever, IdleCreditVault.sol:326) and no APR0 request ever settles. User funds are permanently locked absent a borrower default path or an implementation upgrade.

### Impact Explanation
Permanent freezing of all user funds: tranche holders cannot complete withdraw claims (epoch never advances), APR0 requesters can never settle (`_reqEpoch >= epochNumber` holds forever), and depositors cannot exit through the normal epoch lifecycle. The attacker achieves this with an arbitrarily small withdraw request — a dust-sized griefing attack with no capital at risk (the requested amount remains claimable in principle, though it too is frozen). The broken invariant is liveness of the epoch state machine: a stored aggregate (`apr0TotalPrincipal`) is bound to a mutable parameter (`unscaledApr`) by a revert that has no escape path, exactly the bug-class pattern of a monotonicity assumption invalidated by a parameter change blocking claims.

### Likelihood Explanation
Requires a specific but plausible operational sequence: a pool operating at `unscaledApr == 0` (APR0 mode is an explicitly supported flow with dedicated accounting), at least one lender submitting any withdraw request during that window (normal user behavior, no malicious timing needed — the attacker's request is itself trivially cheap), and the APR later being raised by the manager before `stopEpoch` clears the bucket — a routine honest action (rate adjustment mid-epoch, or `setApr` called by the CDO). No malicious privileged role is needed; privileged actors behave honestly throughout. The only uncertainty is how frequently production pools run at APR0 and then re-rate, but the code provides no guard, warning, or escape for this combination, so any occurrence permanently bricks the vault.

### Recommendation
Do not revert on `unscaledApr != 0` while `apr0TotalPrincipal != 0`. Options: (a) settle the APR0 bucket at the last recorded rate (e.g., zero net interest) and clear `apr0TotalPrincipal` regardless of the current APR, treating the invariant violation as a degenerate settlement rather than a bricking condition; (b) decrement `apr0TotalPrincipal` inside `_settleApr0`/`_requestWithdrawApr0` settlement paths so user claims drain the bucket; (c) prevent requests from entering the APR0 bucket unless the APR0 regime is guaranteed to persist through the next `stopEpoch` (e.g., snapshot the APR at request time and settle at that snapshot). Any of these removes the permanent-revert edge, analogous to the external report's fix of removing the stale internal accounting rather than asserting on it.

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testApr0BucketBrickedByAprIncrease() external {
    // setup: pool running with unscaledApr == 0 (APR0 epoch), attacker holds tranche tokens
    _deposit(attacker, amount); // KYC-passed lender deposits into AA tranche
    // epoch is running, unscaledApr == 0

    // 1. attacker requests a dust withdraw while APR is 0
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // dust amount
    assertGt(IdleCreditVault(strategy).apr0TotalPrincipal(), 0);

    // 2. manager honestly raises the APR mid-epoch
    vm.prank(manager);
    IdleCreditVault(strategy).setAprsWithBuffer(newApr, epochDuration, bufferPeriod);

    // 3. every stopEpoch now reverts permanently
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpochWithDuration(newApr, interest, duration, 0);

    // 4. no user action can unbrick: _settleApr0 never runs because epochNumber
    //    can only advance through a successful stopEpoch; apr0TotalPrincipal
    //    is only cleared inside prepareStopEpochWithApr0 itself.
    //    -> attacker claim and all other funded claims are frozen indefinitely.
}
```

Expected result: `stopEpoch`/`stopEpochWithDuration` reverts on every call, `epochNumber` never increments, `claimWithdrawRequest` reverts for the attacker and any other pending requester (`epochNumber <= lastWithdrawRequest`), and `apr0TotalPrincipal` remains nonzero forever — permanent freezing of vault funds achieved by an unprivileged lender with a dust-sized request.
