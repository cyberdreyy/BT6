### Title
Missing zero-address check on `DefaultDistributor.claim(_to)` permanently burns a defaulted-tranche holder's recovery payout - (File: contracts/DefaultDistributor.sol)

### Summary
`DefaultDistributor.claim` pulls the caller's entire `trancheToken` balance into the distributor and sends the proportional underlying recovery to an arbitrary `_to` address supplied by the caller, with no `address(0)` validation. A lender redeeming defaulted tranche tokens who passes `address(0)` (fat-finger, buggy integration, or a contract wallet misconfiguration) has their tranche tokens escrowed while the recovery funds are sent to the zero address and lost forever, with no way to recall the claim. This is the same bug class as the external report (irreversible fund loss via an unchecked receiver on a withdrawal/claim path).

### Finding Description
In `DefaultDistributor.sol`, `claim` is the post-default recovery-claim path mapped from the external report's `requestWithdraw` receiver bug:

```solidity
function claim(address _to) external {
  require(isActive, '!ACTIVE');
  IERC20 tranche = IERC20(trancheToken);
  uint256 trancheBal = tranche.balanceOf(msg.sender);
  tranche.safeTransferFrom(msg.sender, address(this), trancheBal);
  IERC20(token).safeTransfer(_to, trancheBal * rate / ONE_TRANCHE);
}
``` [1](#0-0) 

Two properties make the missing check loss-bearing rather than a harmless revert:

1. `safeTransferFrom` moves the *entire* `tranche.balanceOf(msg.sender)` into the distributor before the payout, so the caller's claim is consumed regardless of where funds land.
2. Standard ERC-20 `transfer` does not revert on `address(0)` for common underlyings (USDC, DAI, etc. — `IdleCreditVault` deployments use these), so `IERC20(token).safeTransfer(address(0), amount)` succeeds and the underlying is burned/locked permanently.

The broken invariant is "one receipt, one payout": the holder surrenders their claim (tranche tokens are locked in the distributor and counted in the fixed `rate` denominator set in `setIsActive`) yet receives nothing, and the stranded underlying is not recoverable by the user — only the owner could sweep it via `transferToken`, at which point the user has no claim left to redeem. The epoch pool context is *defaulted/finalized*: the distributor is deployed after default, funded with all recovered `token`, activated via `setIsActive(true)` which fixes `rate` against the frozen `trancheToken.totalSupply()`.

No existing guard stops this: there is no `_to != address(0)` check anywhere in `claim`, `isActive` only gates timing, and the transfer succeeding means no revert.

### Impact Explanation
Permanent, unrecoverable loss of the caller's entire defaulted-tranche recovery entitlement. The magnitude is `tranche.balanceOf(msg.sender) * rate / ONE_TRANCHE` underlying tokens — i.e., 100% of that holder's recovery. The escrowed tranche tokens remain in the distributor (or were the pool's claim), so the loss cannot be undone by re-claiming. Quantified: a holder with `X` tranche tokens loses exactly `X * rate / 1e18` underlying.

### Likelihood Explanation
Likelihood is low-to-medium: it requires user error (passing `address(0)`) rather than an active attacker, and claims occur once per defaulted tranche holder. However, defaulted-epoch recovery claims are precisely the scenario where users interact via scripts/UIs on a one-shot basis with no redo — identical severity profile to the referenced Sherlock finding (Medium). Any unprivileged tranche holder can trigger it on themselves; the invariant break (consumed claim, zero payout, funds stuck at `address(0)`) is deterministic.

### Recommendation
Add a zero-address check in `claim` before consuming the tranche tokens:

```solidity
function claim(address _to) external {
  require(isActive, '!ACTIVE');
  require(_to != address(0), '!TO');
  ...
}
```

Optionally emit the recipient in an event for off-chain verification.

### Proof of Concept
Foundry-style PoC (assuming `DefaultDistributor` is deployed with underlying `token`, `trancheToken`, funded, and `setIsActive(true)` called by owner):

```solidity
function testClaimToZeroAddressLosesFunds() public {
  uint256 holderTranches = 100e18;
  deal(trancheToken, holder, holderTranches);
  // distributor funded with 50e18 underlying, rate = 0.5e18
  vm.prank(holder);
  IERC20(trancheToken).approve(address(distributor), holderTranches);
  vm.prank(holder);
  distributor.claim(address(0));
  assertEq(IERC20(trancheToken).balanceOf(holder), 0);      // claim consumed
  assertEq(IERC20(token).balanceOf(holder), 0);             // nothing received
  assertEq(IERC20(token).balanceOf(address(0)), 50e18);     // payout burned at 0x0
}
```

The holder's recovery is permanently lost with all state transitions completing normally.
