### Title
Kiosk owner can strip the `Lock` dynamic field via `uid_mut_as_owner` + `df::remove`, bypassing `TransferPolicy` enforcement — (`crates/sui-framework/packages/sui-framework/sources/kiosk/kiosk.move`)

### Summary

`uid_mut_as_owner` returns `&mut self.id` — the raw `UID` of the `Kiosk`. Because `Lock` is a `public struct` with `copy, drop, store`, any external module can construct `Lock { id: item_id }` and call `df::remove<Lock, bool>` on that `&mut UID`. Once the `Lock` DF is gone, `is_locked()` returns `false` and `take()` succeeds, extracting the item without ever producing a `TransferRequest`.

### Finding Description

The `lock()` function is the mechanism by which NFT creators enforce `TransferPolicy` rules (royalties, allow-lists, etc.). It stores a `Lock { id }` dynamic field on the kiosk's `UID`. The entire enforcement chain depends on that DF being present.

`uid_mut_as_owner` is intended for attaching *custom* extension data to the kiosk UID. However, because it returns `&mut self.id` — the same UID that holds `Lock`, `Listing`, and `Item` DFs — and because `Lock` is a fully public, freely constructible struct, a kiosk owner can use the returned reference to surgically remove the `Lock` DF with a standard `df::remove` call from their own published module.

Attack steps (all in a single PTB or custom module):

1. Lock an item: `kiosk::lock<T>(kiosk, cap, policy, item)` — `Lock { id: item_id }` DF is added.
2. Get mutable UID: `let uid_mut = kiosk::uid_mut_as_owner(kiosk, cap)`.
3. Strip the lock: `df::remove<kiosk::Lock, bool>(uid_mut, kiosk::Lock { id: item_id })`.
4. Extract item: `let item = kiosk::take<T>(kiosk, cap, item_id)` — `is_locked()` now returns `false`, assertion passes.
5. Transfer item freely — no `TransferRequest` is ever created, so no `TransferPolicy` rule (royalty, allow-list, etc.) is evaluated.

### Impact Explanation

This breaks the core guarantee of the kiosk system: that locked items can only leave via a `purchase` or `purchase_with_cap` call that produces a `TransferRequest` satisfying the creator's `TransferPolicy`. A kiosk owner can extract any locked item and transfer it peer-to-peer, completely bypassing royalty rules and any other policy constraints. This constitutes harmful smart-contract behavior that undermines the economic guarantees the protocol is designed to provide.

### Likelihood Explanation

The path requires only the kiosk owner's own `KioskOwnerCap` and a published module — no privileged access, no leaked keys, no malicious validators. Any kiosk owner motivated to avoid royalties can execute this.

### Recommendation

Do not return `&mut self.id` directly from `uid_mut_as_owner`. Instead, introduce a wrapper UID type (or a scoped accessor) that only allows adding/removing keys that are *not* in the reserved set (`Lock`, `Listing`, `Item`). Alternatively, make `Lock` a non-public or `#[internal]` struct so it cannot be constructed outside the `sui::kiosk` package, preventing external modules from using it as a `df::remove` key.
