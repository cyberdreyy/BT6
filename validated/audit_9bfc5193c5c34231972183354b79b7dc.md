### Title
Stale/duplicated signer weight in `BlockStatus` tally lets rejected weight and accepted weight double-count the same signer, wedging valid-block acceptance - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`BlockStatus` in the miner-side `StackerDBListener` keeps two independent running totals, `total_weight_approved` and `total_weight_rejected`, each incremented from signer messages instead of being derived from a single canonical per-signer "current vote" table. A signer that first rejects and later re-evaluates and accepts the same proposal (a normal, well-documented transition, `LocallyRejected --> LocallyAccepted: re-evaluated` per `docs/signer-flows.md:144`) has its weight added to `total_weight_rejected` and never removed, while its later acceptance is also added to `total_weight_approved`. The two ledgers are exactly the `deposits`-vs-`balance` pattern from the external report: a side-counter that can diverge from the real, current state (here, "who currently accepts/rejects this block") because nothing keeps them reconciled.

### Finding Description
On `Accepted`, the code guards the weight increment with `!block.gathered_signatures.contains_key(&slot_id)` [1](#0-0) , which is only true the first time *that same signer's `Accepted` message* is seen — it is never checked against `block.responded_signers`, the set that the `Rejected` branch uses as its single source of truth for "have we already counted this signer" [2](#0-1) .

Sequence:
1. Signer S sends `Rejected` for block B. `block.responded_signers.insert(slot_id)` succeeds, `total_weight_rejected += weight(S)` [2](#0-1) .
2. S re-evaluates (a normal, non-malicious path per the signer state machine) and sends `Accepted` for the same B. `gathered_signatures` doesn't yet contain slot_id, so the guard passes and `total_weight_approved += weight(S)` [1](#0-0) .
3. `total_weight_rejected` is never decremented for S; weight(S) now counts in both totals simultaneously, breaking the invariant that `total_weight_approved + total_weight_rejected <= total_weight` for mutually exclusive votes.

`SignerCoordinator::wait_for_block_acceptance` reads exactly these two counters to decide the miner's fate for the block: if `total_weight_rejected + weight_threshold > total_weight` it returns `Err(SignersRejected)` before ever inspecting `total_weight_approved` [3](#0-2) ; only in the `else if` branch does it check `total_weight_approved >= self.weight_threshold` to accept [4](#0-3) . Because the rejection tally is a monotonically-increasing, never-reconciled side ledger (it is only ever reset wholesale via `reset_rejections` on a full timeout [5](#0-4) , not per-signer when that signer's vote changes), stale rejection weight from signers who have since legitimately signed can push `total_weight_rejected` over the blocking-minority threshold even though the *current* signer set truly supports the block with enough weight.

### Impact Explanation
This wedges the miner into treating an actually-approvable block as globally rejected (`NakamotoNodeError::SignersRejected`), causing the block to be abandoned/re-attempted even though a supermajority of signers, by their *current* vote, would sign it. This is a liveness wedge on the coordinator's block-acceptance decision, driven purely by stale/duplicated accounting rather than any real signer misbehavior or majority action — matching the "High: a signer wedged into never signing valid blocks / acting on a stale ... threshold" impact class, since the tally the coordinator trusts is provably inconsistent with the true, current set of signer votes.

### Likelihood Explanation
Reachable by any single signer re-evaluating its vote from reject to accept for the same proposal — an explicitly supported, documented state transition (`should_reevaluate_block`, `LocallyRejected --> LocallyAccepted`), not an edge case requiring a majority or malicious behavior. Any transient rejection (e.g., a temporarily-stale local view that later clears) followed by a legitimate signature reproduces the double count.

### Recommendation
Track a single authoritative per-signer vote (e.g., a `HashMap<slot_id, Verdict>` where `Verdict` is `Accepted(weight)` or `Rejected(weight)`), and derive `total_weight_approved`/`total_weight_rejected` by summing over that map rather than maintaining two independently-incremented counters. When a signer's verdict changes, update the map entry and recompute both totals (or adjust both counters together) so the invariant `approved + rejected <= total_weight` always holds, mirroring the report's fix of removing the redundant `deposits` ledger and relying solely on the canonical balance.

### Proof of Concept
1. Signer set has signer S with weight `w`, and total weight/threshold such that `total_weight_rejected` from other genuine rejecters is already `total_weight - weight_threshold - w + 1` (i.e., one more rejecting-weight unit away from the blocking-minority threshold).
2. S sends `BlockResponse::Rejected` for block B → `total_weight_rejected += w`, now exactly at the blocking-minority threshold... but S then re-evaluates.
3. S sends `BlockResponse::Accepted` for the same B (valid signature) → because `gathered_signatures` doesn't contain S's slot yet, `total_weight_approved += w` also happens; `total_weight_rejected` still includes `w` from step 2.
4. `SignerCoordinator::wait_for_block_acceptance` observes `total_weight_rejected.saturating_add(weight_threshold) > total_weight` and returns `SignersRejected`, even though S — and hence the currently-consenting weight — actually supports the block and `total_weight_approved` may itself have already reached `weight_threshold`.
