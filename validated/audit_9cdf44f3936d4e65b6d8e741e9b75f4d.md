### Title
Stale confirmations from deleted multisig keys count toward the confirmation threshold, allowing request execution below the live-member quorum - (File: `multisig/src/lib.rs`)

### Summary
The multisig contract's `confirm` function checks `confirmations.len() + 1 >= self.num_confirmations` [1](#0-0)  where `confirmations` is a `HashSet<PublicKey>` of every key that has ever called `confirm` on that request. When a key is removed via the `DeleteKey` action, the contract only purges requests that were *originally created* by that key, filtered by `r.signer_pk == pk`; it never scans the `confirmations` map to strip that key out of confirmation sets on requests it merely confirmed (but did not create) [2](#0-1) . As a result, a confirmation recorded from a key that is later deleted remains counted toward `num_confirmations` for any other still-pending request, letting that request execute once enough of the *remaining live* keys confirm — even though fewer than `num_confirmations` currently-valid keys actually agreed.

### Finding Description
The intended custody binding for this contract is: `confirmations counted for a request == count of distinct currently-authorized keys that confirmed it`. The threshold check in `confirm` treats the `confirmations` HashSet as this live count:

```rust
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    ...
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    ...
``` [3](#0-2) 

`assert_valid_request` only validates that the caller is the current account (i.e. an active access key executed the tx) and that the request/confirmations map entries exist — it never re-validates the *previously stored* confirmers still hold live keys [4](#0-3) .

The cleanup for `DeleteKey` only removes requests whose *creator* (`signer_pk`) matches the deleted key, and clears that key's own `num_requests_pk` counter:

```rust
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [2](#0-1) 

It never iterates `self.confirmations` to remove the deleted key's `PublicKey` from the confirmation sets of requests it *confirmed but did not create*. That confirmation record survives the key deletion and stays in state, exactly like `totalWeight` in the Voter.sol report keeps stale voting power after the underlying source of that weight is gone — a stored aggregate diverges from the live set of authorized parties it's supposed to represent.

### Impact Explanation
This directly breaks the equality `confirmations recorded == live authorized signers who agreed`. Concretely, in a k-of-n multisig (e.g. 3-of-4 keys A, B, C, D):

1. A confirms a pending `Transfer` request R (created by B). `confirmations(R) = {A}`.
2. Separately, keys B, C, D confirm and execute a `DeleteKey{A}` request. Because R was created by B (not A), R is not purged; `confirmations(R)` still contains A's now-dead public key.
3. Now only two live keys (say B and C) need to call `confirm(R)` to reach `confirmations.len()+1 == 3 >= num_confirmations`, even though A's key no longer exists on the account and can never re-confirm anything.
4. R (a `Transfer` of NEAR, or an `AddKey`/`FunctionCall`, etc.) executes with effectively 2 live-member agreement instead of the required 3, i.e. below the configured threshold.

This matches the Critical impact category "a multisig request executed below threshold," resulting in unauthorized movement of NEAR held by the multisig account.

### Likelihood Explanation
Any legitimate operational sequence — key rotation/removal (`DeleteKey`) happening after other requests have already gathered partial confirmations from the key being removed — triggers this without any attacker-controlled deployment or malicious key needed; it only requires ordinary multisig lifecycle usage (add request → partially confirm → remove a signer → complete confirmation with fewer live signers). No privileged bypass or social engineering is required beyond normal use of the documented `DeleteKey` action and `confirm` flow, so the likelihood of the divergence occurring in practice is high once a key is ever rotated while requests are outstanding.

### Recommendation
When executing `DeleteKey`, iterate over all entries in `self.confirmations` (not just requests created by that key) and remove the deleted `PublicKey` from every confirmation set. Alternatively, when calling `confirm`, filter the stored confirmations set to strip out any keys no longer present as valid access keys on the account before comparing against `num_confirmations` (or maintain a canonical "active keys" tracking structure separate from ad-hoc `signer_pk` recording) so that the threshold check reflects only currently live signers.

### Proof of Concept
```
1. Deploy MultiSigContract::new(3) with 4 keys: A, B, C, D.
2. As B: add_request(Transfer{amount}) -> request_id = R  (signer_pk = B)
3. As A: confirm(R)                     -> confirmations(R) = {A}
4. As B: add_request_and_confirm(DeleteKey{A})  -> creates+confirms request R2 (signer_pk = B)
5. As C: confirm(R2)
6. As D: confirm(R2)                    -> 3/4 reached, executes DeleteKey{A}.
   -> execute_request filters requests where signer_pk == A; R (signer_pk = B) is untouched.
   -> confirmations(R) still == {A}, even though A's access key is now deleted.
7. As B: confirm(R)                     -> confirmations.len()+1 == 2, still < 3, insert B.
8. As C: confirm(R)                     -> confirmations.len()+1 == 3 >= num_confirmations(3)
   -> R executes (Transfer of funds) with only {A(dead), B, C} recorded,
      i.e. only 2 currently-live keys (B, C) actually approved.
```
This demonstrates a `Transfer` request executing while only 2 of the 4 live keys agreed, below the configured 3-of-4 threshold, because the third counted "confirmation" belongs to a key that no longer exists on the account.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
