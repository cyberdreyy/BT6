### Title
Fee Payment Bypass — Trie squash/extend_child node decodes during `TrieUpdate::finalize()` are never charged `touching_trie_node` gas - ([File: core/store/src/trie/ops/squash.rs])

### Summary
`squash_node`/`extend_child` (`core/store/src/trie/ops/squash.rs:29-175`) and `generic_delete` (`core/store/src/trie/ops/insert_delete.rs:305-449`) are only invoked from `TrieUpdate::finalize()` (`core/store/src/trie/update.rs:242-261`), which is called once per chunk from `validate_apply_state_update` (`runtime/runtime/src/lib.rs:2820`), strictly after every receipt's execution outcome (and its `ExecutionMetadata`/gas profile) has already been computed. Because `finalize()` calls `trie.update(..., AccessOptions::DEFAULT)`, none of the node decodes performed by `ensure_updated`/`get_node_ref`/`take_node` inside `squash_node`/`extend_child` go through the `StorageAccessTracker`/`GasCounter` that charges `touching_trie_node`, so an attacker can make deletion cascade through an arbitrarily deep trie path essentially for free.

### Finding Description
During contract execution, `RuntimeExt::storage_remove` (`runtime/runtime/src/ext.rs:233-272`) only performs a *read* (`trie_update.get_ref(...)`) to fetch the evicted value and then calls `self.trie_update.remove(storage_key)` (`core/store/src/trie/update.rs:169-182`), which merely inserts the key into the in-memory `prospective` map — no trie mutation happens. `touching_trie_node` is charged exactly once per node touched by this read, via `commit_counts_since` (`runtime/runtime/src/ext.rs:159,174,244,259` and `AccountingState::commit_counts_since`, `runtime/runtime/src/ext.rs:699-717`), which forwards deltas into the `GasCounter`'s `pay_per(ExtCosts::touching_trie_node, count)` (`runtime/near-vm-runner/src/logic/gas_counter.rs:400-402`).

The actual trie restructuring (`generic_delete` → post-order `squash_node` loop, `core/store/src/trie/ops/insert_delete.rs:429-446`) only happens later, once per whole chunk, inside `TrieUpdate::finalize()` (`core/store/src/trie/update.rs:242-261`), called from `validate_apply_state_update` (`runtime/runtime/src/lib.rs:2804-2820`) — i.e., after `process_receipts` has already completed and every receipt's `ExecutionOutcome`/`ExecutionMetadata::V4(profile)` (containing the `touching_trie_node` charge) has already been built and stored in `processing_state.outcomes`. `finalize()` calls `trie.update(changes, AccessOptions::DEFAULT)` (`update.rs:246-258`), which for the no-memtrie path goes to `update_with_trie_storage` (`core/store/src/trie/mod.rs:1677-1705`) and executes `generic_delete`/`squash_node`/`extend_child` with `AccessOptions::DEFAULT` — an options value carrying no `StorageAccessTracker`/gas counter reference at all. Inside `squash_node`'s Branch-with-one-child path (`squash.rs:78-89`) and `extend_child` (`squash.rs:110-175`), each ancestor on the deletion path is dereferenced via `ensure_updated`/`take_node`/`get_node_ref`, potentially decoding a previously-unread sibling/child node — none of these decodes reach `GasCounter::pay_per(ExtCosts::touching_trie_node, ...)`.

Since the outcome/profile object is fixed before `finalize()` even runs, it is structurally impossible for the `touching_trie_node` fee recorded in the receipt's `ExecutionMetadata` to reflect any node decode performed by `squash_node`/`extend_child`. An attacker who builds a deep near-prefix key chain (depth `D`, e.g. via `D` `storage_write` calls establishing nested Extension/Branch nodes) and then issues a single `storage_remove` on the leaf triggers up to `D` cascaded `squash_node`/`extend_child` calls during `finalize()`, each of which may decode a node that was never read (and thus never charged) during execution.

### Impact Explanation
This is a **fee payment bypass / gas mis-metering** issue: the gas charged to the sender for a receipt (specifically its `touching_trie_node` component) does not reflect the actual number of trie nodes decoded to process it, because squash-time decodes in `squash.rs`/`insert_delete.rs` are performed under `AccessOptions::DEFAULT` with no attached access tracker. As `D` (trie depth built via near-prefix keys) grows, `fee_charged / nodes_actually_decoded → 0`, i.e., unpriced computational/I-O work performed by chunk producers on behalf of a single cheap receipt. This falls under "Fee payment bypass" as scoped, since a receipt's gas cost is deliberately intended to price trie-node touches (`touching_trie_node`, see `docs/GenesisConfig/ExtCostsConfig.md:251-255` and `runtime/runtime-params-estimator/src/cost.rs:622-631`), and this scoped path defeats that pricing for the squash-time portion of node access.

### Likelihood Explanation
The attacker only needs an ordinary funded account and a deployed contract capable of issuing `storage_write`/`storage_remove` host calls (or a plain transaction using account/access-key storage, if reachable without a contract). Building a deep trie of near-prefix keys and deleting the leaf key is fully under attacker control (key content, deletion order, single receipt). No validator/chunk-producer privilege or protocol misconfiguration is required — this is reachable purely through normal RPC-submitted transactions. It is repeatable across chunks/receipts, bounded only by `max_length_storage_key`/receipt gas limit rather than by any `touching_trie_node`-linear parameter, as the audit states.

### Recommendation
Thread a `StorageAccessTracker` (or an equivalent counting mechanism) through `TrieUpdate::finalize()` → `Trie::update` → `update_with_trie_storage`/`update_with_memtrie` → `generic_insert`/`generic_delete`/`squash_node`/`extend_child`, and charge (or at minimum measure and bound) `touching_trie_node`-equivalent gas for every node decode performed while squashing, attributing the cost back to the receipt(s) responsible for the deletion. Alternatively, since `finalize()` intentionally aggregates changes across the whole chunk (making precise per-receipt attribution hard), enforce a conservative worst-case charge at deletion time (during `RuntimeExt::storage_remove`) sized to the maximum possible ancestor-squash chain length for the key being removed, so gas is charged proactively rather than retroactively.

### Proof of Concept
Integration/test-loop plan (model on `integration-tests/src/tests/features/chunk_nodes_cache.rs::compare_node_counts`):
1. Deploy a test contract exposing storage write/remove host calls.
2. In one chunk, issue `D` `storage_write` calls with keys `key[0..1]`, `key[0..2]`, ..., `key[0..D]` (near-prefix keys) to build a deep Extension/Branch chain, each in its own or the same receipt, then in a subsequent receipt issue a single `storage_remove(key[0..D])`.
3. From the delete receipt's `ExecutionOutcome`, read `ExecutionMetadata::V4(profile)` and extract `profile.get_ext_cost(ExtCosts::touching_trie_node)`, convert to node count by dividing by `ext_costs.gas_cost(ExtCosts::touching_trie_node)` (as done in `compare_node_counts`, `integration-tests/src/tests/features/chunk_nodes_cache.rs:134-139`).
4. Independently instrument (or add a debug counter to) `squash_node`/`extend_child`/`ensure_updated` invoked from `TrieUpdate::finalize()` for that chunk, counting `GenericUpdatedTrieNode` decodes.
5. Assert `profile_touching_trie_node_count < actual_squash_decode_count`, and that the gap grows linearly with `D` — demonstrating the profiled/charged fee undercounts the true node-decode work by a factor approaching `D`.

This is straightforward to construct because `finalize()` (`core/store/src/trie/update.rs:242`) runs strictly after outcome/profile construction (`runtime/runtime/src/lib.rs:1122` vs `:2820`), so the assertion is expected to hold deterministically for any `D` where the delete causes at least one cascaded squash beyond the directly-read path.
