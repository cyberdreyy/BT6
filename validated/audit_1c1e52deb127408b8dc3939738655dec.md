## Finding [1](#0-0) 

### Title
Stale confirmations from removed multisig members are counted toward the confirmation threshold, allowing request execution below the live-member quorum - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` counts entries in the `confirmations` set for a request against `num_confirmations` without verifying that each confirming party is still a current multisig member. `delete_member` (and, in the legacy `multisig` contract, `DeleteKey`) only purges requests *authored* by the removed member/key; it never scrubs that member's confirmation entries from *other* pending requests they had merely confirmed. A member removed from the multisig can therefore still count toward executing an unrelated, previously-confirmed request.

### Finding Description
`add_request`/`confirm` store confirmations as a `HashSet<String>` keyed by `MultisigMember::to_string()` in `confirmations: LookupMap<RequestId, HashSet<String>>` [2](#0-1) . Confirmation counting and execution trigger simply compares the size of this cached set to `self.num_confirmations`, with no re-validation against the live `members` set: [3](#0-2) 

When a member is removed via `MultiSigRequestAction::DeleteMember`, `delete_member` clears only requests where `r.member == member` (i.e., requests *created* by that member) and the member's `num_requests_pk` counter, but does not walk `self.confirmations` to remove that member's vote from other, still-pending requests: [4](#0-3) 

The identical gap exists in the legacy `multisig` contract: `DeleteKey` inside `execute_request` filters `self.requests` by `r.signer_pk == pk` only, not `self.confirmations`, and `confirm()` likewise never re-checks that a previously stored public key still belongs to an active multisig key [5](#0-4) [6](#0-5) .

This breaks the intended equality "confirmations counted == confirmations from currently live/authorized members". The binding that should hold is:
`len(confirmations(request)) counted toward num_confirmations` must equal `len(confirmations(request) ∩ current_members)`.
After a member removal, this invariant no longer holds for any request that member confirmed before being removed but that is still outstanding.

### Impact Explanation
This allows a multisig request to be executed with fewer live-member confirmations than the configured `num_confirmations` threshold — e.g., in a 2-of-3 setup where member B confirms a pending `Transfer` request, is later removed via `DeleteMember`, and then only one remaining live member (C) confirms — the stale confirmation from B plus C's confirmation reaches the count of 2 and the transfer (or `FunctionCall`, `AddKey`, etc.) executes, even though only one currently authorized member actually approved it. This matches "a multisig request executed below threshold," listed as a Critical-severity impact category, since it allows NEAR transfers, key additions, or other privileged actions to be pushed through with insufficient live authorization.

### Likelihood Explanation
Requires an unprivileged position relative to protection: any account that was previously a valid confirming member (now removed, e.g. due to a key rotation, compromise response, or governance change) retains latent influence over already-pending requests. Because member removal is a normal operational event in a multisig lifecycle, and pending, unconfirmed requests can remain active until `active_requests_limit`/`REQUEST_COOLDOWN`, the scenario (a request confirmed by a soon-to-be-removed member remains pending when other confirmations arrive) is realistic without requiring social engineering or a compromised key — a former member's leftover, previously-legitimate confirmation is enough.

### Recommendation
When executing `DeleteMember` (or `DeleteKey` in `multisig`), iterate all entries in `confirmations` and remove the removed member's vote from every request, not just requests they authored. Alternatively, validate at `confirm()`/execution time that every counted confirmation corresponds to an account/key still present in `self.members`, filtering stale confirmations before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. A calls `add_request_and_confirm` to create request `R` (a `Transfer`), confirmations(R) = `{A}`.
3. B calls `confirm(R)` → confirmations(R) = `{A, B}` (count 2, but note in this exact case it would already execute with 2 real members — instead use a 4-member example to keep it stale after removal):
   - Use members `[A, B, C, D]`, `num_confirmations = 3`.
   - A creates and confirms `R` (`Transfer` to attacker-controlled or arbitrary receiver): confirmations(R) = `{A}`.
   - B confirms `R`: confirmations(R) = `{A, B}` (count 2, below threshold 3, so `R` stays pending).
4. Separately, members execute a `DeleteMember { member: B }` request (via the normal 3-of-4 quorum using A, C, D) — B is removed from `self.members`, but `delete_member` does not touch `confirmations(R)`, so `confirmations(R)` still equals `{A, B}`.
5. C confirms `R`: `confirmations.len() as u32 + 1 = 3 >= num_confirmations(3)` → `execute_request(R)` runs the `Transfer`.
6. Result: `R` executed with confirmations effectively from A and C only (2 live members) plus a stale vote from removed member B, even though the contract was configured to require 3 live-member confirmations — the request executed below the intended threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
