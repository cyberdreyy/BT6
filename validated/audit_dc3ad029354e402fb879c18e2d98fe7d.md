## Analysis

The reported bug class is an **accounting/invariant mismatch**: two values that are supposed to move together (or be scoped identically) are calculated inconsistently, breaking an isolation guarantee the code claims to provide. The closest reachable analog in this codebase is in the CRE Gateway's HTTP capability response cache, where the documented "workflow isolation" invariant is violated by the actual cache-key computation.

### Title
Response cache key omits `WorkflowID`, breaking documented workflow isolation and enabling cross-workflow response cache confusion - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The gateway's HTTP Action response cache is documented as being "scoped by workflow ID to prevent cross-workflow data leakage," but the actual cache key (`OutboundHTTPRequest.Hash()`) does not include `WorkflowID` at all — only method, URL, headers, body, and `WorkflowOwner`. This is directly analogous to the reported bug class: one field (`WorkflowID`, the intended isolation unit) is expected to gate a stateful resource, while the actual implementation increments/keys off a different, coarser field (`WorkflowOwner`), causing the invariant to silently not hold.

### Finding Description
The cache struct comment and the module README both assert workflow-level isolation: [1](#0-0) [2](#0-1) 

However, the cache is keyed purely by `req.Hash()`, and the test suite explicitly documents that `Hash()` ignores `WorkflowID` while only `WorkflowOwner` differentiates entries: [3](#0-2) [4](#0-3) 

The cache is used from `Fetch`/`Set`, both keyed on `req.Hash()`: [5](#0-4) [6](#0-5) 

And this cache is invoked directly for outbound HTTP action requests originating from workflow-owned capability nodes, where `req` (including `WorkflowOwner`/`WorkflowID`) is unmarshaled straight from the node's message: [7](#0-6) 

Because the key omits `WorkflowID`, two distinct workflows belonging to the same owner that issue an HTTP action with identical method/URL/headers/body (a very plausible collision — e.g. a shared external API endpoint, health check, or templated action) will hit the exact same cache entry. A response fetched (and possibly containing owner-scoped but workflow-specific downstream data, e.g. via templated bodies causing different upstream responses depending on caller-supplied headers not included in the hash such as time-based/nonce headers) for Workflow A can be served to Workflow B, violating the "Workflow Isolation" property the code and docs claim to enforce.

### Impact Explanation
This breaks the documented workflow-level data isolation boundary within the same owner: workflow B receives cached content it never triggered, sourced from workflow A's request. Depending on what the outbound HTTP action returns (e.g., per-workflow secrets/tokens fetched from an external system, workflow-specific configuration, or user-supplied data echoed by the target endpoint), this is a cross-workflow response confusion vulnerability. Since caching is opt-in per request (`CacheSettings.Store`/`MaxAgeMs`), and the DON is expected to route data per-workflow, an attacker/workflow author within the same organization/owner boundary could deliberately craft a request that collides on the hash to read stale/foreign workflow data.

### Likelihood Explanation
Reaching this path only requires being a workflow owner able to configure an HTTP Action capability with caching enabled (`CacheSettings.Store=true`/`MaxAgeMs>0`) — a normal, unprivileged CRE workflow author capability, not a malicious node/operator scenario. Because `Hash()` intentionally strips `WorkflowID` (confirmed by the test comments), any two workflows under the same owner using semantically identical HTTP requests will collide by design, not merely by hash accident — making this a deterministic, not probabilistic, invariant violation.

### Recommendation
Include `WorkflowID` (or a workflow-execution scoping identifier consistent with the documented guarantee) in the cache key computed by `OutboundHTTPRequest.Hash()`, or explicitly update the documentation/comments to reflect that isolation is only owner-scoped (not workflow-scoped) and review whether owner-level scoping is sufficient for the caching feature's security requirements.

### Proof of Concept
1. Workflow `W1` (owner `Org`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings: {Store: true, MaxAgeMs: 600000}, WorkflowID: "W1", WorkflowOwner: "Org"}`. The gateway fetches and caches the response under `req.Hash()`.
2. Workflow `W2` (same owner `Org`, different `WorkflowID`) issues an identical request except `WorkflowID: "W2"`.
3. Per `response_cache_test.go` `TestRequestHash` ("having different workflowID results in same Hash"), `req.Hash()` for both requests is identical.
4. `W2`'s `Fetch` call hits the cache entry populated by `W1`'s request and returns `W1`'s cached response without making any new HTTP call — demonstrated by `response_cache_test.go` lines 139-149, and reachable via `makeOutgoingRequest`/`Fetch` in `http_handler.go` lines 433-435.

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```

```go
// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```
