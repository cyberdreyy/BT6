### Title
RPC jsonParsed token account/mint decoding trusts unvalidated mint owner, causing misreported token decimals and UI amounts - (File: rpc/src/parsed_token_accounts.rs)

### Summary
`get_parsed_token_account` and `get_parsed_token_accounts` in `rpc/src/parsed_token_accounts.rs` extract a "mint" pubkey directly from the first 32 bytes of a token account's raw data via `get_token_account_mint`, then fetch whatever account exists at that address and unconditionally interpret its raw bytes as an SPL `Mint` via `get_additional_mint_data`/`StateWithExtensions::<Mint>::unpack`, without ever verifying that the fetched "mint" account is actually owned by a recognized SPL token program.

### Finding Description
`get_token_account_mint` only checks that the token *account's own* data layout is a valid SPL token account (`Account::valid_account_data`), then blindly returns bytes `[0..32]` as the mint pubkey [2](#0-1) . Because a user fully controls the contents of their own SPL token account (as long as it is a validly-sized/typed token account owned by the token program), they control this "mint" field to point at *any* pubkey on-chain — a stake account, vote account, another program's data account, etc.

`get_parsed_token_account` (used for `simulateTransaction`/preflight jsonParsed encoding with account overwrites) then resolves that pubkey via `account_resolver::get_account_from_overwrites_or_bank` and immediately calls `get_additional_mint_data(bank, mint_account.data())` on whatever account is found — with no check that `mint_account.owner()` is `spl_token_interface::id()` or `spl_token_2022_interface::id()` [3](#0-2) . `get_additional_mint_data` just runs `StateWithExtensions::<Mint>::unpack(data)` on that arbitrary account's bytes and, if it happens to parse (i.e., the data is long enough and passes the Mint/extension layout checks), extracts `decimals`, `interest_bearing_config`, and `scaled_ui_amount_config` straight from that unrelated account's memory layout [4](#0-3) .

`get_parsed_token_accounts` (used by `getProgramAccounts`/`getTokenAccountsByOwner` with jsonParsed encoding) has the same gap: `get_mint_owner_and_additional_data` fetches the account by the untrusted mint pubkey and calls `get_additional_mint_data` on its raw data without validating the account's owner before unpacking [5](#0-4) . The owner is only returned/used elsewhere, but is never used to gate whether the byte-unpack should be trusted at this call site — only the separate `get_token_program_id_and_mint` (called for the explicit `mint` filter argument, not for the account's embedded mint field) performs an `is_known_spl_token_id` check [6](#0-5) .

This is a direct analog of the reported bug class: the wallet's business logic trusted an externally-supplied "token" descriptor without validating it against the expected schema/authority, allowing a spoofed token to be injected and displayed as legitimate. Here, the RPC's JSON-parsing logic trusts a self-referential "mint" pointer embedded in attacker-controlled account data and treats whatever data lives at that address as authoritative token metadata (decimals / scaling / interest-bearing config), without validating that the referenced account is actually owned by a recognized token program — exactly the "lack of business logic validation" pattern from the report, but manifesting as account-data misinterpretation in a JSON-RPC handler rather than a wallet UI bug.

By contrast, the equivalent SVM-side balance-collection code (`SvmTokenInfo::unpack_token_account`) does perform this validation (`if *mint_account.owner() != program_id { return None; }`) [1](#0-0) , showing the check is a recognized necessary safeguard that is missing from the RPC JSON-parsed account-decoder path.

### Impact Explanation
An unprivileged client can craft/own an SPL token account whose embedded "mint" field points at any existing account (e.g., a large stake/vote/program account) and then query it via `getAccountInfo`/`getProgramAccounts`/`getTokenAccountsByOwner` with `encoding: jsonParsed`, or via `simulateTransaction` account overwrites. If the target account's raw bytes happen to satisfy the `Mint`/extension unpack layout, the RPC response will report attacker-influenced `decimals`, `interestBearingConfig`, or `scaledUiAmountConfig` values sourced from a completely unrelated, non-token account. This causes `token_amount_to_ui_amount_v3` to compute and return an incorrect `uiAmount`/`uiAmountString` for the token balance in the JSON-RPC response — i.e., wrong account/token data returned by a single, low-rate, unprivileged query, which downstream consumers (wallets, dApps) may display or act on as if it were validated. This matches the "wrong-slot/fork/account data returned" / decoder-misreporting acceptance criteria.

### Likelihood Explanation
Reachable with a single unprivileged `getAccountInfo`/`getProgramAccounts`/`getTokenAccountsByOwner` (jsonParsed) or `simulateTransaction` call against an account the caller already owns/controls, requiring no special privileges — only the ability to construct a token account whose mint field points at a chosen pubkey with a data layout that happens to parse as `Mint`. Finding a naturally-occurring account whose bytes coincidentally unpack cleanly as a plausible `Mint` may require some search/crafting effort, but it does not require any elevated permissions, and self-consistent conditions (e.g., a system-owned account with zero-filled data, or another token mint the attacker also created) make the misreporting trivially reproducible.

### Recommendation
In `rpc/src/parsed_token_accounts.rs`, before calling `get_additional_mint_data` on a resolved "mint" account (in both `get_parsed_token_account` and `get_mint_owner_and_additional_data`/`get_parsed_token_accounts`), verify that the fetched account's owner is a known SPL token program id (`spl_generic_token::is_known_spl_token_id`) — mirroring the check already present in `svm/src/transaction_balances.rs::unpack_token_account`. If the owner check fails, treat the token account as having no resolvable additional mint data (fall back to `None`/default) rather than unconditionally unpacking arbitrary account bytes as `Mint`.

### Proof of Concept
1. Create an SPL token account (owned by `spl_token_interface::id()`, correct size/state) whose first 32 bytes (the `mint` field) are set to the pubkey of an arbitrary existing account not owned by any token program (e.g., a large stake or vote account, or a zero-lamport system account with enough data).
2. Call `getAccountInfo` (or `getTokenAccountsByOwner`/`getProgramAccounts`) on that token account with `{"encoding": "jsonParsed"}`.
3. Observe that `get_token_account_mint` extracts the crafted mint pubkey [2](#0-1) , `get_mint_owner_and_additional_data`/`get_additional_mint_data` fetch and attempt to unpack the unrelated target account's data as a `Mint` without any owner check [7](#0-6) , and if unpack succeeds, the returned `tokenAmount.decimals`/`uiAmount` reflect bytes from the unrelated account rather than a genuine token mint's decimals.

    mint: &Pubkey,

    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),

        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

    bank: &Bank,
    token_account_filter: TokenAccountsFilter,
