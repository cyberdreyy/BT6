### Title
Unfunded pre-default-epoch instant withdraw receipts are paid at par, bypassing the recovery haircut - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is an out-of-bounds read: `validate_protocol` reads bytes past the intended buffer boundary. The vault analog is a read past the intended *epoch* boundary in `claimInstantWithdrawRequest`: after default finalization it clears only receipts stored under `defaultRecoveryEpoch`, then pays the full remaining `instantWithdrawsRequests[_user]` aggregate at par via `_transferFundedClaim`. Unfunded instant receipts recorded under an earlier epoch are never included in the recovery basis nor haircut, yet are read and paid as if they were funded.

### Finding Description
`instantWithdrawsRequests[_user]` is an aggregate counter, while per-epoch data lives in `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` (`IdleCreditVault.sol` L103–L111). At default finalization, `defaultPendingClaimBasis` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — i.e., current-epoch instant claims (`IdleCreditVault.sol` L644–L649). Likewise, `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (`IdleCreditVault.sol` L842–L856).

If `pendingInstantWithdraws` is non-zero at finalization and part of that unfunded remainder belongs to a user whose request epoch is *earlier* than `defaultRecoveryEpoch`:

- that user's claim basis is excluded from `defaultPendingClaimBasis` (wrong index), so it is not haircut by `defaultRecoveryPrice`;
- `_claimDefaultedInstantWithdrawRequest` reads index `defaultEpoch` for that user, finds 0, returns;
- `claimInstantWithdrawRequest` then burns and pays the full `instantWithdrawsRequests[_user]` at par through `_transferFundedClaim` (`IdleCreditVault.sol` L387–L392), which only guards `defaultRecoveryReserve` (`IdleCreditVault.sol` L897–L906).

Additionally, `_defaultPrefundedInstantReserve` computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` (`IdleCreditVault.sol` L716–L723). When the unfunded remainder is attributed to an older epoch, this under-counts the prefunded reserve, deflating `recoveryPrice` for every legitimate recovery claimant while the old-epoch requester still exits at par. This is the same class as the external bug: the code reads the aggregate/`epochNumber`-indexed slot instead of the bounds-correct per-epoch entry.

### Impact Explanation
An unprivileged lender holding an unfunded instant-withdraw receipt from an epoch prior to the defaulted epoch withdraws 100% of its claim while every other defaulted receipt and active tranche holder is haircut by `defaultRecoveryPrice`. The payout comes from strategy-held underlyings that were never reserved for that receipt, directly diluting (or, via the deflated `recoveryPrice`, draining) the recovery of other claimants — direct theft of recovery funds, quantifiable as `oldEpochInstantBasis * (1 - defaultRecoveryPrice)` plus the reserve-miscount distortion.

### Likelihood Explanation
Requires an instant-withdraw request that remains unfunded (`pendingInstantWithdraws` non-zero) across an `epochNumber` boundary and a subsequent borrower default finalized via `finalizeDefaultRecovery`. Instant requests are unprivileged, and partial funding of the instant bucket is an explicitly handled state (hence `pendingInstantWithdraws` and `_defaultPrefundedInstantReserve`). No privileged attacker is needed; the honest owner/manager sequence (partial instant funding → default → `finalizeDefaultRecovery` → `claimInstantWithdrawRequest`) triggers it.

### Recommendation
Track per-epoch funding state for instant receipts the same way normal receipts use `lossRecoveryPriceByEpoch`/`withdrawsRequestsByEpoch`: in `claimInstantWithdrawRequest`, iterate or flag all epochs in `instantWithdrawsRequestsByEpoch` that were pending at finalization, add them to `defaultPendingClaimBasis`, and pay them through `_transferDefaultRecovery` at `defaultRecoveryPrice`. Only instant receipts actually funded (transferred into the strategy) should be payable at par via `_transferFundedClaim`. Fix `_defaultPrefundedInstantReserve` to subtract per-epoch unfunded amounts rather than assuming all of `pendingInstantWithdraws` belongs to `epochNumber`.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Epoch N: user A requests instant withdraw; CDO only partially funds it,
// leaving pendingInstantWithdraws == A_amount (epoch N attribution).
vm.prank(userA);
cdoEpoch.requestInstantWithdraw(aAmount);

// Epoch rolls over (manager startEpoch/stopEpoch) so epochNumber becomes N+1
// while A's receipt is still unfunded.
// Borrower then defaults; manager finalizes recovery.
cdoEpoch.stopEpoch(0, 0);            // defaulted
cdoEpoch.finalizeDefault(recovered, manager); // -> finalizeDefaultRecovery

// A's instant basis was never added to defaultPendingClaimBasis
// (only instantWithdrawClaimsByEpoch[N+1] is read).
// A claims at par:
uint256 balPre = underlying.balanceOf(userA);
vm.prank(userA);
cdoEpoch.claimInstantWithdrawRequest();
assertEq(underlying.balanceOf(userA) - balPre, aAmount); // full payout, no haircut

// Meanwhile recovery claimants for epoch N+1 receive defaultRecoveryPrice < 1e18,
// and defaultRecoveryReserve was under-counted by _defaultPrefundedInstantReserve.
```

Caveat: I could not fully confirm within the search budget the exact `IdleCDOEpochVariant` gating that lets `pendingInstantWithdraws` persist across `startEpoch`/`stopEpoch` (149 instant-related references exist in that file). If the CDO strictly forces full funding of the instant bucket before epoch rollover, this path is unreachable and the finding reduces to the reserve-miscount edge; verifying that gating is the one step needed to finalize the PoC.
