### Title
Any authenticated External Initiator (Run-role) credential can trigger and read results for **any** job by integer ID via `POST /v2/jobs/:ID/runs` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the integer-ID job-run path on `auth.GetAuthenticatedUser(c)` returning true, with a comment stating "only users are allowed to run jobs using int IDs - EIs not allowed." However, the middleware chain for this route (`AuthenticateExternalInitiator`) injects a synthetic `*sessions.User{Role: UserRoleRun}` into the same context key that `GetAuthenticatedUser` reads, so any valid EI credential satisfies the `isUser` check and can invoke `RunJobV2` for any job ID — not just a job bound to that initiator.

### Finding Description
The route is registered with a combined authenticator chain that tries EI auth first: [1](#0-0) 

In `auth.AuthenticateExternalInitiator`, upon successful EI credential verification, the code deliberately writes a fabricated `User` object with `UserRoleRun` into `SessionUserKey` "because EI endpoints inherently assume the role of 'run'": [2](#0-1) 

`auth.RequiresRunRole` then simply checks that a `User` object exists in context with role ≥ run — it has no way to distinguish a real logged-in user from this synthetic EI stand-in: [3](#0-2) 

Inside `PipelineRunsController.Create`, the intended safeguard is: only "real users" (`isUser == true`) may trigger jobs by integer ID, EIs must not be able to: [4](#0-3) 

Because `AuthenticateExternalInitiator` already set `SessionUserKey`, `auth.GetAuthenticatedUser(c)` returns `(user, true)` for an EI-authenticated request too, so the `isUser` branch is entered and `prc.App.RunJobV2(ctx, jobID, nil)` is invoked for **any** job ID supplied in the URL — there is no check anywhere in this call path that ties the specific authenticated `ExternalInitiator` (obtainable via `auth.GetAuthenticatedExternalInitiator(c)`) to the target job. `RunJobV2` itself performs no ownership/binding check either — it just loads the job by ID and executes its pipeline: [5](#0-4) 

The result is then returned via `FindRun`/`NewPipelineRunResource` to the caller regardless of which job or which credentials were used: [6](#0-5) 

Note: the webhook job type with the old `ExternalInitiatorSpec` binding mechanism referenced in the question has actually been fully removed from this codebase version (`job.Webhook`/`ErrJobTypeRemoved`, and UUID-based run requests are explicitly rejected at line 104-107 of the controller). So the literal "EI-A bound job vs EI-B bound job" ownership model no longer exists in code — but the underlying authorization bypass is broader and still real: **any** valid EI credential (or any Run-role token/session) can be used to run **any** job in the node by integer ID and read back its full pipeline run output, since the code path performs no per-job/per-caller authorization check at all beyond "is *a* run-role principal authenticated."

### Impact Explanation
An attacker holding only Run-role credentials (e.g., a legitimately provisioned External Initiator's access key/secret, or a restricted user API token with Run role) can trigger execution of arbitrary jobs on the node — including OCR, VRF, Flux Monitor, Direct Request jobs unrelated to their own integration — and read the resulting `PipelineRun`, which can include task outputs and bridge responses embedded in the run tree. This is unauthorized job execution and cross-tenant/cross-scope data exposure, matching the "unauthorized job run" and "cross-user response confusion" bounty impact classes. It does not directly move funds but can trigger unwanted on-chain side effects for jobs that submit transactions, and leaks internal computation results to an unauthorized principal.

### Likelihood Explanation
Preconditions are minimal: possession of any valid External-Initiator credential pair (`EI-Access-Key`/`EI-Secret` headers) or a Run-role user/API token is sufficient — no admin/edit privileges are needed, and the target job ID need not belong to the caller. The exploit is a single unauthenticated-looking HTTP POST with valid EI headers to `/v2/jobs/{anyJobID}/runs`, fully repeatable for any integer job ID on the node.

### Recommendation
In `auth.AuthenticateExternalInitiator`, do not overwrite `SessionUserKey` with a synthetic `User`; instead, keep EI identity solely in `SessionExternalInitiatorKey` and have `RequiresRunRole`/`PipelineRunsController.Create` check `auth.GetAuthenticatedExternalInitiator` explicitly and reject (401/403) when only an EI principal (no real user) is present for the int-ID run path, restoring the intended "EIs not allowed to trigger jobs by int ID" invariant. If EI-triggered runs must be supported at all going forward, reintroduce an explicit binding check between the authenticated `ExternalInitiator.Name` and the target job's initiator configuration before calling `RunJobV2`.

### Proof of Concept
Go handler-level integration test plan (extends existing `core/web/pipeline_runs_controller_test.go` patterns):
1. Start a `cltest.NewApplicationWithConfig` app.
2. Create two External Initiators, `eiA` and `eiB`, via `cltest.CreateExternalInitiatorViaWeb`.
3. Create Job A (e.g., a simple OCR or cron pipeline spec unrelated to any EI) via `app.AddJobV2`.
4. Build an unauthenticated HTTP client with only `eiB`'s `ExternalInitiatorAccessKeyHeader`/`ExternalInitiatorSecretHeader` headers (`cltest.UnauthenticatedPost`).
5. `POST /v2/jobs/{JobA.ID}/runs` using `eiB`'s credentials.
6. Assert: current buggy behavior returns `200 OK` with a `pipelineRun` JSON:API resource containing `JobA`'s run results (`respondWithPipelineRun`/`FindRun`), proving `eiB` triggered and read a job it has no relationship to.
7. Expected fixed behavior: response should be `401 Unauthorized` (or `403`), and `cltest.AssertCountStays(t, app.GetDB(), "pipeline_runs", 0)` should hold — no run created and no data returned.

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
