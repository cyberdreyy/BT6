### Title
Shared-vault liquidity drain makes `onStopEpoch` revert inside the epoch-stop critical path, freezing all lender funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
Analogous to CVE-2024-47724 ("sleeping in atomic context" — a blocking call executed inside a critical section that cannot tolerate failure), `IdleCDOEpochVariant.stopEpoch` synchronously calls `ProgrammableBorrower.onStopEpoch`, which performs a blocking external call, `vault.withdraw(shortfall, ...)`, inside the epoch-stop critical path. If the shared ERC4626 vault lacks instant liquidity while the borrower's shares still cover the shortfall, the withdraw reverts, the catch rethrows `StopEpochVaultLiquidityUnavailable`, and the entire `stopEpoch` reverts. Any user of the shared vault can keep this condition true, repeatedly bricking epoch settlement.

### Finding Description
`ProgrammableBorrower.onStopEpoch` (lines 231-268) frees liquidity for the CDO's `transferFrom` pull:

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
``` [1](#0-0) 

The guard only returns `true` early when the borrower's *share value* cannot cover the shortfall. It does not distinguish "position insolvent" from "vault liquid but cash drained by other shareholders". Standard ERC4626 vaults (and most yield vaults) allow any depositor to withdraw liquidity that physically sits in the vault. `_currentVaultAssets()` = `convertToAssets(shares)` measures share value, not withdrawable liquidity. [2](#0-1) 

The same synchronous-call-in-critical-path pattern exists in `_borrow` (line 452), where `vault.withdraw` is *not* wrapped in try/catch, so a drained vault also bricks borrower draws — but the fund-impacting case is `stopEpoch`: in `IdleCDOEpochVariant`, `_resolveStopEpochInterest` is read, then `onStopEpoch` runs, then the CDO pulls funds via `transferFrom`. A revert anywhere in that sequence aborts the whole stop, leaving `isEpochRunning` true, deposits paused, and `epochEndDate` in the past. [3](#0-2) 

### Impact Explanation
Temporary freezing of all pool funds. While `stopEpoch` reverts:
- The epoch cannot settle: `epochNumber` never increments, so every `claimWithdrawRequest` hits `epochNumber <= lastWithdrawRequest[_user]` → `NotAllowed()` (IdleCreditVault.sol:326).
- The CDO stays `paused`, blocking `depositAA/depositBB` and interest distribution.
- `epochPendingWithdraws` reserved liquidity stays locked in the borrower contract.

An attacker who holds (or flash-borrows into) shares of the shared ERC4626 vault can withdraw all vault liquidity just before each `manager.stopEpoch` transaction (public mempool), forcing `vault.withdraw(shortfall)` to revert while `shortfall <= _currentVaultAssets()`. This is repeatable every block, so the freeze lasts as long as the attacker sustains it; during that window lenders' capital and matured withdraw receipts are frozen, and a liquid-but-insolvent borrower position cannot be marked in default either. Loss is bounded by the duration the attacker maintains the drain, but requires only capital already committed to the shared vault — an explicitly in-scope attacker class ("a user of the programmable borrower's ERC4626 vault").

### Likelihood Explanation
Requires `isProgrammableBorrower == true` and the configured `vault` to be a multi-user ERC4626 (the intended design — the adapter "parks" capital in an external yield vault). Any liquidity crunch in that vault — organic redemption waves, utilization spikes, or deliberate draining — triggers the revert path. The attacker needs no privileges: only vault shares or a flash loan plus timing the manager's `stopEpoch` (a public, predictable call at `epochEndDate`). Cost is transient (gas + capital opportunity cost); no capital is burned.

### Recommendation
Treat the vault withdraw like the kernel fix treats `ath11k_wmi_cmd_send`: decouple the fallible operation from the atomic critical path.

1. In `onStopEpoch`, degrade gracefully instead of reverting: on withdraw failure, withdraw whatever is available (`vault.maxWithdraw(address(this))`, then `vault.withdraw(maxWithdrawable, ...)` inside the try), and let the CDO's `transferFrom` shortfall flow into the existing default path rather than a hard revert.
2. Alternatively, pre-pull vault liquidity during `onStartEpoch`/buffer so `stopEpoch` only does accounting, or make `stopEpoch` retryable with the withdrawn portion checkpointed.
3. At minimum, catch the revert and return `true` with partial liquidity so `transferFrom` shortfall deterministically routes to `_handleBorrowerDefault` instead of leaving the epoch wedged.

### Proof of Concept
Foundry fork-style test against `test/foundry/ProgrammableBorrowerCreditVault.t.sol` setup:

```solidity
// Assume: programmable CDO started epoch N; vault holds the facility funds;
// `attacker` also holds shares of the same ERC4626 vault.

// 1. Epoch N matures
vm.warp(cdoEpoch.epochEndDate() + 1);

// 2. Attacker (a normal vault user) drains vault liquidity.
//    Borrower's shares still cover the shortfall, so the early-return guard passes.
uint256 liquid = underlying.balanceOf(address(vault));
uint256 maxOut = vault.maxWithdraw(attacker);
vault.withdraw(Math.min(maxOut, liquid), attacker, attacker);
// (repeatable via flash-loan-minted shares if attacker owns none)

// 3. Manager's stopEpoch reverts inside onStopEpoch
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 1); // or any interest value

// 4. Consequences
assertTrue(cdoEpoch.isEpochRunning());           // epoch wedged
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimWithdrawRequest();                  // receipts frozen
vm.expectRevert(bytes("Pausable: paused"));
idleCDO.depositAA(1e18);                          // deposits frozen
```

Attacker repeats step 2 in front of every `stopEpoch` attempt to sustain the freeze. Uncertainty: exact revert propagation inside `IdleCDOEpochVariant.stopEpoch` was not fully re-verified line-by-line (grep confirmed `onStopEpoch` is called in the stop flow and its revert is not caught), but `onStopEpoch` being `nonReentrant` + external and unguarded by the CDO makes propagation straightforward.
