## Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing a request to execute with fewer live approvals than `num_confirmations` requires - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
The bug class in the external report is "a stale/reused identifier that should represent something no longer valid is instead trusted as still-valid, letting an unauthorized party corrupt the accounting that other users rely on." The direct analog here is in the NEAR multisig contracts: when a member (or key) is removed via `DeleteMember`/`DeleteKey`, the contract only purges *requests originated by* that member, but never purges *confirmations already cast by* that member on requests originated by other members. `confirm()` simply counts `confirmations.len()` without checking that every entry still belongs to a current member, so a stale confirmation from a removed member is silently counted toward the `num_confirmations` threshold - breaking the equality "confirmations counted == confirmations from live members."

### Finding Description
`confirm()` in both contracts decides whether to execute a request purely from the size of the stored confirmation set: [1](#0-0) 

`delete_member()` only cleans up requests whose *creator* (`r.member`) is the member being removed; it does not scan the `confirmations` map to strip that member's votes from requests created by *other* members: [2](#0-1) 

The same pattern exists in the key-based v1 contract, where `DeleteKey` only removes requests whose `signer_pk` matches the deleted key, leaving that key's confirmations on other requests intact: [3](#0-2) 

`assert_valid_request()` (used by `confirm()`) only checks that the *caller* is a current member and that the request/confirmations map entries exist - it never re-validates the members who are already recorded inside the `confirmations` set: [4](#0-3) 

Because of this, the invariant "every entry in `confirmations[request_id]` corresponds to a live member" is not maintained after a `DeleteMember`/`DeleteKey` execution, and `confirm()`'s threshold check (`confirmations.len() as u32 + 1 >= self.num_confirmations`) can be satisfied by counting a phantom, non-member vote.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." Concretely:

1. Member/key B confirms a pending request `R` (e.g., a `Transfer` or `AddKey` action) created by member A. `confirmations[R] = {B}`.
2. Independently, B is removed from the multisig (e.g., due to suspected key compromise) via a `DeleteMember`/`DeleteKey` request that reaches quorum.
3. `delete_member`/the `DeleteKey` branch removes only requests *created by* B; `R` (created by A) is untouched, and B's confirmation entry inside `confirmations[R]` is never purged.
4. Any single remaining live member (say C) calls `confirm(R)`. `confirmations.len()` is now 2 (`{B, C}`), which meets `num_confirmations = 2`, so `R` executes - even though only one live member (C) actually approved it after B's revocation.

This lets a request (fund transfer, key/member addition, contract deployment, etc.) execute with fewer genuinely-authorized approvals than the configured threshold, i.e. `confirmations counted != confirmations from live members`, which can move NEAR out of the account or grant access below the intended security threshold.

### Likelihood Explanation
The scenario requires no special privilege beyond normal multisig operation: a member confirms a legitimate-looking request, is later removed (a routine or security-driven action), and the earlier confirmation is never cleaned up. Any subsequent live member simply calling `confirm()` on the still-pending request triggers the flaw - no exploit of cryptography or contract bugs elsewhere is needed, only patience for a member-removal event to occur while a request is outstanding, which is a realistic and expected operational pattern (e.g., removing a member suspected of key compromise while requests they touched are still pending).

### Recommendation
When removing a member/key (`delete_member` in `multisig2/src/lib.rs`, and the `DeleteKey` branch in `multisig/src/lib.rs`), iterate over all pending requests and strip the removed member's/key's entry from every `confirmations` set, not just the requests they created. Alternatively, change `confirm()` to recompute the count by filtering `confirmations` against the current `members` set (or current valid keys) before comparing against `num_confirmations`, rather than trusting the raw stored `len()`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. As A: `add_request(Transfer{...})` → `request_id = R` (creator = A).
3. As B: `confirm(R)` → `confirmations[R] = {B}` (1 of 2, not yet executed).
4. As A and C: create and confirm a `DeleteMember{member: B}` request that reaches the 2-confirmation threshold; it executes, calling `delete_member`, which removes only requests created by B (not `R`) and does not touch `confirmations[R]`.
5. As C: `confirm(R)` → `confirmations.len() + 1 = 2 >= num_confirmations (2)`, so `R` executes via `execute_request`, even though B is no longer a member and only C's confirmation is legitimately live. [5](#0-4) [6](#0-5)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
