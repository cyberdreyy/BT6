### Title
Unchecked multiplication in fee burn calculation can overflow/wrap - (File: `runtime/src/bank/fee_distribution.rs`)

### Summary
`Bank::calculate_reward_and_burn_fee_details` computes the burned portion of collected transaction fees using raw (non-saturating, non-checked) integer multiplication and division, in contrast to every other arithmetic operation in the fee/compute-budget pipeline, which consistently uses `saturating_add`/`saturating_mul`/`saturating_sub` or `checked_*` variants.

### Finding Description [1](#0-0) 

```rust
pub fn calculate_reward_and_burn_fee_details(
    &self,
    fee_details: &CollectorFeeDetails,
) -> FeeDistribution {
    let burn = fee_details.transaction_fee * self.burn_percent() / 100;
    let deposit = fee_details
        .priority_fee
        .saturating_add(fee_details.transaction_fee.saturating_sub(burn));
    FeeDistribution { deposit, burn }
}
```

This is the analog of the reported `gasUsedDelta`/`baseFeeDelta` bug class: an arithmetic step that computes a derived accounting value (`burn`) using plain `*`/`/` operators with no overflow protection, immediately adjacent to code (`deposit`) that *does* use safe `saturating_*` arithmetic. Every other fee-related computation in the codebase deliberately avoids raw arithmetic for exactly this reason:
- `fee/src/lib.rs` `calculate_signature_fee` uses `saturating_add`/`saturating_mul`. [2](#0-1) 
- `compute-budget/src/compute_budget_limits.rs::get_prioritization_fee` uses `saturating_mul`/`saturating_add`/`checked_div` with a fallback to `u64::MAX`. [3](#0-2) 
- `cost-model/src/transaction_cost.rs::sum` uses `saturating_add` throughout. [4](#0-3) 

`fee_details.transaction_fee` in `calculate_reward_and_burn_fee_details` represents the total collected transaction fee for the slot/block (`self.collector_fee_details`), accumulated from all transactions processed by the leader, and is used both in the per-block distribution path [5](#0-4)  and in the per-transaction priority/reward estimation path used by forwarding/scheduling code. [6](#0-5) [7](#0-6) 

Because `burn_percent()` is a compile-time constant of 50 [8](#0-7) , the multiplication `transaction_fee * 50` overflows `u64` once `transaction_fee` exceeds `u64::MAX / 50` (~3.69 × 10¹⁷ lamports). In a debug build this triggers a panic (denial of service / validator crash on a bank-processing path executed every slot); in a release build it silently wraps, producing an incorrect `burn` value that is then subtracted from `transaction_fee` via `saturating_sub` to compute `deposit`, corrupting the fee accounting and the subsequent `capitalization.fetch_sub(total_burn, ...)` supply-accounting step. [9](#0-8) 

### Impact Explanation
If triggered, this could either crash the validator's bank-processing path (in debug/overflow-checked builds) on a per-slot code path, or silently corrupt the burn/deposit split and the tracked `capitalization` (total supply accounting) in release builds — both are consensus-relevant, since `capitalization` and reward/burn bookkeeping must be deterministic and correct across all validators.

### Likelihood Explanation
Low. Reaching `transaction_fee > u64::MAX / 50` requires the *accumulated* transaction fee across all transactions in a single slot to approach ~3.69 × 10¹⁷ lamports, which is a substantial fraction of total SOL supply. Per-transaction fee contributions are themselves computed with saturating arithmetic and are far smaller in practice, and accumulation of `collector_fee_details` across transactions in a block also appears to use saturating arithmetic elsewhere in `bank.rs` (not fully confirmed from indexed excerpts). A single unprivileged transaction sender cannot single-handedly push the block total anywhere near this threshold without paying an economically infeasible amount of real fees, so while this is a genuine deviation from the codebase's otherwise-consistent safe-math convention, it is not a practically exploitable overflow under current fee/compute-budget limits.

### Recommendation
Replace the raw arithmetic with checked/saturating equivalents for defense-in-depth and consistency with the rest of the fee pipeline, e.g.:
```rust
let burn = fee_details
    .transaction_fee
    .saturating_mul(self.burn_percent())
    .saturating_div(100);
```
or use `checked_mul`/`checked_div` and treat failure as a critical invariant violation, matching the pattern used in `compute_budget_limits.rs` and `fee/src/lib.rs`.

### Proof of Concept
Not practically constructible from a single unprivileged transaction under current network fee/compute-budget limits; the overflow condition requires accumulated per-slot `transaction_fee` near `u64::MAX / 50`, which is unreachable via realistic fee payments. The finding is a code-hygiene / defense-in-depth gap rather than a demonstrated exploit path.
