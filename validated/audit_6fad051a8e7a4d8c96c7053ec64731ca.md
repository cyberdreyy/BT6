### Title
`AnchorUpdater::next_game` permanently stalls anchor-state advancement after a `setImplementation` cadence change, with no recovery even on restart - (File: `crates/proof/challenge/src/anchor.rs`)

### Summary
The analogy to the TwapOracle report holds: just as a stuck Chainlink aggregator makes `consult` revert forever with no governance path to fix it, a dispute-game-factory `setImplementation` call whose new implementation changes the `(BLOCK_INTERVAL, INTERMEDIATE_BLOCK_INTERVAL)` cadence can make `AnchorUpdater::next_game` permanently fail to find the successor game, freezing the anchor state forever — and, per the code's own comment, "a restart no longer clears" it.

### Finding Description
`AnchorUpdater::next_game` resolves the interval pair used to build the UUID lookup key for the *next* anchor-successor game via `resolve_intervals`, which reads the dispute-game factory's **current** `gameImpls(game_type)` implementation address and asks it for `intervalsForStartingBlock` [1](#0-0) . This differs from how an *existing* game's own interval pair is read: for a proxy that already exists, the pair should be read through the game's own CWIA proxy so it reflects the pair the game was created with, since CWIA clones bake in the implementation at creation time and are unaffected by later `setImplementation` calls [2](#0-1) .

The bug: for the *next, not-yet-existing* anchor-successor game, `next_game` has no proxy to read from, so it must use the factory's current implementation. If governance calls `setImplementation` to swap in a new implementation whose cadence differs from the one the successor game was actually created with (e.g. it was created before the swap, or under a different cadence boundary), the UUID key built from the wrong `(block_interval, intermediate_block_interval)` pair will never match the on-chain game, and `factory_client.games(...)` returns `Address::ZERO` forever: "next anchor game not found" [3](#0-2) . The code's own comment explicitly documents this as a known, unresolved limitation: [4](#0-3) 

Because `poll()` caches `cached_next_game` keyed only on the current anchor snapshot and re-runs `next_game` (which always re-derives the same mismatched key) whenever the cache misses, there is no code path that ever recovers — not through retries, not through a process restart — until governance performs another out-of-band fix (external anchor advancement), exactly analogous to the TwapOracle's missing "update the aggregator" governance hook.

### Impact Explanation
When this stall occurs, `AnchorUpdater::poll` (crates/proof/challenge/src/anchor.rs) will never call `try_update`, meaning the `AnchorStateRegistry`'s anchor root/game is never advanced on-chain. This is used to gate what parent games proposers/challengers can build on and what output roots are considered valid starting points for proof verification. A stuck anchor freezes progress of the dispute-game/verification pipeline for that game type — new proposals cannot cheaply anchor off the latest finalized state, degrading the security and liveness guarantees of the fault-proof system (analogous to "permanent freezing" / "node halt" of a critical on-chain bookkeeping mechanism), until a manual, out-of-band intervention (not present in this codebase) forces anchor advancement.

### Likelihood Explanation
This requires a `setImplementation` call on the `DisputeGameFactory` — a governance/privileged action — combined with a successor game already having been created under the pre-swap cadence/pair. The report itself calls this a "Known limitation" acknowledged in code comments, so the code owners are aware the condition is reachable during a normal governance-driven implementation upgrade (not a malicious actor), similar to how the original TwapOracle finding was judged Medium despite requiring an unlikely external precondition (a stuck Chainlink aggregator). Given upgrades are a normal, expected operational event for this system (Denim-style cadence changes are explicitly designed for), the likelihood of hitting this window during a real upgrade is non-negligible.

### Recommendation
Do not rely solely on the factory's *current* implementation to resolve the successor game's interval pair. When the keyed UUID lookup misses, fall back to scanning the factory from the anchor's game index forward (as the code comment itself suggests) to find the actual successor regardless of which pair it was created under, rather than assuming a permanent "not found" result. Alternatively, expose enough on-chain state (e.g., let `intervalsForStartingBlock` be queryable in a way that reflects the pair at game-creation time for future games too) so `resolve_intervals` cannot silently diverge from the pair actually used to create a pending successor game.

### Proof of Concept
1. Dispute-game factory has an anchor game G0 at some L2 block; a successor game G1 already exists on-chain, created under cadence pair `(BI_old, IBI_old)`.
2. Governance calls `setImplementation` for the game type, switching the active implementation to one that reports `(BI_new, IBI_new)` via `intervalsForStartingBlock` for the same starting block (e.g., a Denim-style cadence change whose boundary/parameters shifted).
3. `AnchorUpdater::poll` → `next_game` calls `resolve_intervals`, which reads the **new** implementation's pair (`crates/proof/contracts/src/aggregate_verifier.rs:35-49`), builds a `game_lookup_key` with `(BI_new, IBI_new)`, and calls `factory_client.games(...)`. Because G1 was created under `(BI_old, IBI_old)`, its UUID differs, so `games()` returns `Address::ZERO` (`crates/proof/challenge/src/anchor.rs:192-201`).
4. Every subsequent poll re-derives the same mismatched key and gets the same `Address::ZERO` result; nothing in `poll`/`next_game`/the cache logic changes this outcome, and a process restart re-runs the exact same deterministic computation, so the anchor never advances — matching the code's own comment that "a restart no longer clears" the stall (`crates/proof/challenge/src/anchor.rs:116-126`). The existing test `poll_finds_next_game_built_with_fast_intervals` (`crates/proof/challenge/src/anchor.rs:572-641`) explicitly demonstrates the "stale" cadence case failing to find the game, confirming the mechanism.

pub async fn resolve_intervals(

    verifier_client: &dyn AggregateVerifierClient,

    starting_block: u64,

        )));
    }

    verifier_client.read_intervals_for_starting_block(impl_address, starting_block).await
}
