### Title
Re-proposal of an already globally-accepted block silently resets its `BlockInfo` to `Unprocessed`, defeating the same-height signature-conflict guard - ([File: stacks-signer/src/v0/signer.rs])

### Summary
When a signer's `BlockInfo` for a given block hash is already `GloballyAccepted` but this signer never itself validated/signed it (`valid == None`, `signed_self == None`, `signed_group == None`), a re-delivered `BlockProposal` for that same hash causes `should_reevaluate_block` to return `true`, and `handle_block_proposal` then overwrites the stored record with a brand-new `Unprocessed` `BlockInfo`. This is directly analogous to the reported `UpliftOnlyExample.afterUpdate` bug: a value that is supposed to be pinned once a terminal/committed state is reached (`upliftFeeBps` on transfer / `GloballyAccepted` + `signed_group` here) is instead retroactively overwritten by a later message, silently undoing the commitment the field was meant to preserve.

### Finding Description
`BlockInfo::from(BlockProposal)` always resets `valid`, `approved_time`, `signed_self`, `signed_group`, `reject_reason` and `state` to their empty defaults: [1](#0-0) 

`handle_block_proposal` constructs exactly this fresh `BlockInfo` and persists it over any existing record whenever `should_reevaluate_block` returns `true`, as its own comment acknowledges ("Creating a new proposal will overwrite any prior proposal info on the block if it exists, e.g. validity, signed_timestamps, etc."): [2](#0-1) 

`should_reevaluate_block` is supposed to gate this so that a settled decision is never disturbed. It explicitly refuses to re-evaluate only when `globally_approved_and_responded()` is true, i.e. when the block is `GloballyAccepted` **and** (`signed_self.is_some()` or `valid == Some(false)`): [3](#0-2) 
(also see `globally_approved_and_responded`): [4](#0-3) 

But a block can reach `GloballyAccepted` in this signer's local DB **without** this signer ever validating it: the network-confirmed "new block" handler unconditionally promotes any non-terminal, tracked block to `GloballyAccepted` the moment the node's chain tip reaches it, regardless of whether `valid`/`signed_self` were ever set: [5](#0-4) 

For such a block, `globally_approved_and_responded()` is `false` (signed_self is `None`, valid is `None`, not `Some(false)`), so the "already answered, ignore" guard does not fire. The subsequent PreCommitted-specific branch is also skipped (state is `GloballyAccepted`, not `PreCommitted`). `determine_response` then returns `None` because `valid` is `None` (the `?` short-circuits): [6](#0-5) 

With `determine_response` returning `None` and no pending validation outstanding, `should_reevaluate_block` falls through to its final `true`: [7](#0-6) 

`handle_block_proposal` then overwrites the `GloballyAccepted` record with a fresh `Unprocessed` `BlockInfo` via `insert_block`, which persists the object wholesale rather than routing it through `BlockInfo::move_to`/`check_state` (the mechanism the design doc says exists precisely to keep global states terminal against each other): [8](#0-7) 

### Impact Explanation
This breaks the "one-per-height" / signature-conflict equality the signer relies on elsewhere. Multiple DB queries that gate whether the signer may sign a *different, conflicting* block at the same height depend on `state`/`signed_self`/`signed_group` staying intact for any block this signer has committed to as canonical, e.g. `get_signed_conflicts`, `has_signed_block_in_tenure`, `get_last_signed_block`: [9](#0-8) [10](#0-9) 

Once the record is wiped back to `Unprocessed`, this signer's local view no longer reflects that the block at this height/tenure was already globally accepted. If a sibling block at the same height later reaches the pre-commit threshold (`handle_block_pre_commit`, section 5 of the flow), the conflict check `get_signed_conflicts` will not find the wiped record, and the signer can go on to sign the conflicting sibling: [11](#0-10) [12](#0-11) 

This is exactly the "signer signing a conflicting block" impact class: a single actor (the miner or any peer re-relaying the original `BlockProposal` message) can, without needing a majority of signers or any key material, cause a signer to lose its own record of the already-accepted block at a height and later add a signature to a conflicting sibling — undermining the guard that is supposed to prevent exactly that.

### Likelihood Explanation
The trigger requires two ordinary, miner-controlled conditions with no majority or privileged access needed:
1. This signer receives confirmation that a block is on-chain (`stacks_block_arrival`/new-block event) for a proposal it has tracked but never got to locally validate (e.g., validation was still queued/in-flight, or it never got a validation slot before the network settled the block) — a routine race under load or after a brief validation delay.
2. The same `BlockProposal` (or a resend of it, which miners routinely do on timeout) is later redelivered to this signer.

Both are ordinary, frequently occurring signer-network conditions (proposal resends and validation races) rather than adversarial edge cases, making this readily reachable in practice.

### Recommendation
`should_reevaluate_block` must treat a block whose `state == BlockState::GloballyAccepted` as terminal for re-proposal purposes even when `valid`/`signed_self` were never locally set — i.e., extend the early "ignore" check so that reaching `GloballyAccepted` (or, more generally, `has_reached_consensus()`) alone, regardless of `signed_self`/`valid`, suppresses re-evaluation and blocks the destructive overwrite in `handle_block_proposal`. Alternately, `insert_block` (or a wrapper used from `handle_block_proposal`) should refuse to replace a stored `BlockInfo` whose `state` is a terminal (global) state with a fresh `Unprocessed` one, mirroring the `check_state` terminality rule that already exists for `move_to`.

### Proof of Concept
1. Signer S receives `BlockProposal` for block B (height H, tenure T) and stores it as `Unprocessed`, then submits it for node validation (slot busy or response delayed).
2. Before S's own validation returns, S observes (via `SignerEvent::NewBurnBlock`/block-arrival handling) that the network's chain tip has already advanced to B; `handle_event_match`'s new-block-event branch looks up B by hash, finds it not yet `GloballyAccepted`, and calls `mark_globally_accepted()` — setting `state = GloballyAccepted` while `valid`, `signed_self` remain `None` (see `stacks-signer/src/v0/signer.rs:710-726`).
3. The miner (per its normal resend loop, e.g. after a timeout elsewhere in the network) re-broadcasts the same `BlockProposal` for B. S's `handle_block_proposal` looks up the stored `BlockInfo`, calls `should_reevaluate_block`: `globally_approved_and_responded()` is `false` (no `signed_self`, `valid != Some(false)`); the `PreCommitted` branch is skipped; `determine_response` returns `None` (`valid` is `None`); no pending validation remains ⇒ function returns `true`.
4. `handle_block_proposal` builds `BlockInfo::from(block_proposal.clone())` — `state = Unprocessed`, `signed_group = None`, `approved_time = None` — and persists it via `insert_block`, clobbering the `GloballyAccepted` record.
5. Later, a sibling block B' at height H in another tenure reaches the pre-commit threshold. `get_signed_conflicts(H, hash_of_B')` no longer sees B (its `state`/`signed_group` were erased in step 4), so S signs B', producing a signature over a block that conflicts with the block S's own node already treats as canonical at height H.
