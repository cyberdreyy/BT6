## No vulnerability found for this question.

**Analysis:**

The premise of the question — that signer message-dispatch logic does not gate `MockSignature`/`MockProposal` acceptance on the current epoch — is factually incorrect based on the code.

1. **`MockProposal` handling (from miner messages)** is explicitly gated by a *live* query to the node's current epoch, not by any field embedded in the replayed message itself:
```rust
SignerMessage::MockProposal(mock_proposal) => {
    let epoch = match stacks_client.get_node_epoch() { ... };
    if epoch == StacksEpochId::Epoch25 && self.reward_cycle == current_reward_cycle {
        self.mock_sign(mock_proposal.clone());
    }
}
``` [1](#0-0) 

Because `get_node_epoch()` queries the stacks-node's actual current epoch at processing time, a replayed Epoch-2.5-era `MockProposal` will simply fail this check once the node has transitioned into Nakamoto — the epoch check is not derived from stale message content, so there is no "stale artifact processed as if still epoch-relevant" condition.

2. **`MockSignature` messages received from other signers** (via the `SignerEvent::SignerMessages` loop) are not even matched — they fall through to the `_ => {}` catch-all and are completely ignored, regardless of epoch:
```rust
match message {
    SignerMessage::BlockResponse(block_response) => { ... }
    SignerMessage::StateMachineUpdate(update) => { ... }
    SignerMessage::BlockPreCommit(signer_signature_hash) => { ... }
    _ => {}
}
``` [2](#0-1) 

3. Even in the epoch where mock-signing is active, `mock_sign()` only sends a `MockSignature` gossip message and mutates no persistent signer state (`signer_db`, `local_state_machine`, block validation results, etc.) that gates real `BlockResponse` emission:
```rust
fn mock_sign(&mut self, mock_proposal: MockProposal) {
    let mock_signature = MockSignature::new(mock_proposal, &self.private_key);
    let message = SignerMessage::MockSignature(mock_signature);
    if let Err(e) = self.stackerdb.send_message_with_retry::<SignerMessage>(message) { ... }
}
``` [3](#0-2) 

4. Real block-proposal handling (`handle_block_proposal`, `determine_response`, `handle_block_validate_response`) is a completely separate code path from mock-signing and reads only `block_info.valid`/`signer_db` state populated by actual node validation responses, with no dependency on any mock-signing field. [4](#0-3) 

5. The stacks-node's own `StackerDBListener` (used by miners in Nakamoto to aggregate signer responses) also explicitly ignores mock messages: `SignerMessageV0::MockSignature(_) | MockProposal(_) | MockBlock(_) => { debug!("Received mock message. Ignoring."); }`. [5](#0-4) 

Since the epoch gate is evaluated live against the node's actual current epoch (not the message's embedded/implied epoch), and since mock-signing state is fully disjoint from the real `BlockResponse`/block-validation state machine, there is no reachable wedge, no stale-epoch replay effect, and no path from a replayed `MockSignature`/`MockProposal` into gating real block-signing behavior.
