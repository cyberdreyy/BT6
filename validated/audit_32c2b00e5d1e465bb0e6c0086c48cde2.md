### Title
Role confusion via unconditional local `users` table pre-check in `FindUser` overriding LDAP-derived role for colliding emails - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.FindUser` unconditionally queries the local `users` table by email as its very first step and returns that row's role immediately on any match, before ever consulting the LDAP directory group membership. Because `CreateSession` calls `FindUser` right after a successful LDAP `Bind` (using the attacker-supplied identity) without any indication to `FindUser` that authentication was performed via the LDAP path, an attacker who successfully completes a real LDAP Bind under an email that happens to collide with a row in the local `users` admin table is granted that local row's role instead of the role derived from their actual LDAP group memberships.

### Finding Description
In `CreateSession` [1](#0-0) , the code performs an LDAP `Bind` with attacker-supplied credentials, and regardless of whether `err` from `Bind` was set, immediately calls `l.FindUser(ctx, escapedEmail)`. If `Bind` succeeds, `returnErr` is `nil` at that point, so a subsequent successful `FindUser` result is used as-is to create the session with the returned `Role`.

Inside `FindUser`, the very first action is: [2](#0-1) 
This queries `SELECT * FROM users WHERE lower(email) = lower($1)` and, on any match, returns that row's `Role` immediately — with no check that the caller actually authenticated through the local password path (`localLoginFallback`, which validates a hashed password) rather than through the LDAP Bind. The genuinely correct fallback to the local table already exists later, gated on "no LDAP directory entries found": [3](#0-2) 
But because the unconditional check at lines 118-123 runs first and short-circuits with a `return`, the LDAP group search (lines 144-201) is never reached at all when there is any local-table match — the actual LDAP-derived role (`groupSearchResultsToUserRole`) is never computed or compared.

Exploit flow: an attacker holding any valid LDAP account/credentials (e.g. a "view"-only directory user) whose configured login attribute (email/uid) happens to match a row in the node's local `users` table (e.g. a shared/generic corporate email reused as the local CLI admin's email) completes a legitimate `Bind` with their own valid password. `FindUser` is then invoked with that email, matches the local `users` row before ever checking LDAP groups, and returns the local row's `Role` (potentially `UserRoleAdmin`). The resulting `ldap_sessions` entry is created with this elevated role, entirely bypassing the intended LDAP group-to-role mapping enforced by `GroupSearchResultsToUserRole`.

### Impact Explanation
This is a privilege escalation / authorization bypass: a user who only possesses "view" or "run"-level LDAP credentials can be granted `UserRoleAdmin` (or any role in the local `users` table) simply because their authenticated email string collides with a row in that table, with no requirement to know the local admin's password. This maps to Chainlink's "Broken Access Control / Privilege Escalation" bounty class, since it can grant node-admin capabilities (job management, key access via admin UI, bridge creation, etc.) to an identity that was never granted the admin role by an LDAP group.

### Likelihood Explanation
Requires a specific precondition: an email/uid collision between an LDAP-authenticatable directory account and a row in the local `users` table. This is not guaranteed in all deployments, but it is a realistic misconfiguration risk explicitly acknowledged by the code's own dual-purpose design (local CLI admin table coexisting with LDAP), e.g., shared/generic admin mailbox addresses reused across a directory, or organizations where the local CLI admin's bootstrap email matches a real LDAP user's email. Once the precondition holds, exploitation requires only a normal successful LDAP login with the attacker's own valid credentials — no local admin password, no elevated privileges, and it is fully repeatable.

### Recommendation
Remove the unconditional local-table pre-check at lines 118-129 of `core/sessions/ldapauth/ldap.go`, and rely solely on the existing, correctly-gated fallback at lines 173-188 (queried only when the LDAP directory search for the authenticated user returns zero group-membership entries). Additionally, `CreateSession` should track and pass down whether the current authentication path was LDAP Bind vs. local password fallback, and `FindUser`'s local-admin-role branch should only be reachable through the local password-verified path (`localLoginFallback`), never as a first-class override for an LDAP-Bind-authenticated identity.

### Proof of Concept
Go unit test in `core/sessions/ldapauth/ldap_test.go`:
1. Construct `ldapAuthenticator` with a `sqlmock`-backed `ds` where `SELECT * FROM users WHERE lower(email) = lower($1)` returns one row with `email = "shared@corp.com"`, `role = admin`.
2. Configure a mock `LDAPClient`/`LDAPConn` such that a group search for `shared@corp.com` would return entries mapping to `sessions.UserRoleView` only (i.e., the user is genuinely only in the "Read" LDAP group).
3. Call `l.FindUser(ctx, "shared@corp.com")` directly.
4. Assert: returned `sessions.User.Role == sessions.UserRoleAdmin` (the local table row's role) even though the LDAP mock's group data — if it had been consulted — would resolve to `UserRoleView`. This demonstrates the local-table short-circuit bypasses the LDAP group-derived role entirely.
5. Additionally assert (via mock call-count/expectation) that the LDAP `conn.Search` for group membership was never invoked, proving `FindUser` never validated the actual authentication path before returning the local admin role.

func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}

	// Bind was successful meaning user and credentials are present in LDAP directory
	// Reuse FindUser functionality to fetch user roles used to create ldap_session entry
	// with cached user email and role
	foundUser, err := l.FindUser(ctx, escapedEmail)
	if err != nil {
		l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
		returnErr = errors.New("log in successful, but no assigned groups to assume role")
	}
