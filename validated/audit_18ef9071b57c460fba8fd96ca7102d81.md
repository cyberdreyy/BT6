I have confirmed the vulnerability. The `assert_owner` check in `lockup/src/internal.rs` gates all owner-privileged operations (transfer, staking pool selection, etc.) purely on `self.owner_account_id`, and `LockupContract::new` is a public, callable-by-anyone `#[init]` method missing the `assert!(!env::state_exists())` guard present in every sibling contract in this repo.

### Title
Missing re-initialization guard on `LockupContract::new` allows any account to reset `owner_account_id` and hijack a deployed lockup - (File: `lockup/src/lib.rs`)

### Summary
`LockupContract::new` in [1](#0-0)  is an `#[init]` method that lacks the `assert!(!env::state_exists(), ...)` guard that every other contract in this repository enforces on its `new`. Because `#[init]` in this near-sdk version does not automatically prevent re-invocation, and because calling a deployed contract's public method requires no permission on the receiver account (only a signer transaction), any unprivileged account can call `new` again on an already-deployed lockup contract and fully overwrite its state — including `owner_account_id`, `lockup_information`, `vesting_information`, `staking_information`, and `foundation_account_id`.

### Finding Description
Every other init function in this repo explicitly reverts re-initialization:
- `staking-pool/src/lib.rs:179` — `assert!(!env::state_exists(), "Already initialized");` [2](#0-1) 
- `whitelist/src/lib.rs:34` [3](#0-2) 
- `voting/src/lib.rs:36` [4](#0-3) 
- `staking-pool-factory/src/lib.rs:106` [5](#0-4) 
- `lockup-factory/src/lib.rs:80` [6](#0-5) 

`LockupContract::new`, however, contains no equivalent check: [1](#0-0) . It only validates account-ID format and vesting/foundation consistency, then unconditionally overwrites `Self { owner_account_id, lockup_information, vesting_information, staking_information: None, staking_pool_whitelist_account_id, foundation_account_id }`.

This mirrors the reported "Reserves can be re-added" bug class: a state that should only be set once, guarded by an "already added/initialized" check, is instead silently overwritten, resetting critical accounting fields (here, `lockup_information.lockup_amount` reset to whatever the current `env::account_balance()` is, and `staking_information` reset to `None`, and `owner_account_id` reassigned).

Because `lockup-factory/src/lib.rs` deploys the lockup contract and calls `new` via a `FunctionCall` action with a fixed, deterministic account ID (`sha256(owner_account_id)` prefix + factory account) [7](#0-6) , the deployed lockup account has no special access-key protection preventing arbitrary accounts from later calling its public `new` method again — calling a contract's method only requires the caller to sign a transaction with the target as receiver; no permission on the receiver is checked by NEAR for `FunctionCall` actions to a public method.

All owner-gated operations (`select_staking_pool`, `unselect_staking_pool`, transfers, termination, etc. in `lockup/src/owner.rs`) rely exclusively on `assert_owner`, which compares `env::predecessor_account_id()` to `self.owner_account_id`: [8](#0-7) . An attacker who successfully re-calls `new` sets `owner_account_id` to their own account, thereby seizing owner control of the lockup contract and its locked NEAR balance.

### Impact Explanation
This breaks the custody binding of "account trusted as owner versus the code and arguments that trust was granted for": the original beneficiary designated at deployment can be silently replaced by an attacker-controlled account, who then gains the ability to invoke every owner-only method (staking pool selection/unstaking/withdrawal, and — once transfers are enabled per the lockup schedule — transferring the NEAR balance out). This is a Critical impact: NEAR moved by (or ownership transferred to) a party not entitled to it, and a wrongly-parameterized deployment.

### Likelihood Explanation
No privileged role, redeploy, or key compromise is required — any account can submit a `FunctionCall` transaction targeting the deployed lockup account's `new` method with attacker-chosen arguments, since NEAR does not restrict who can call a public contract method by receiver-account permission. The attack is a single transaction and does not depend on any race condition beyond the lockup contract already having been deployed (which is the normal, expected state for any lockup created via `lockup-factory`).

### Recommendation
Add `assert!(!env::state_exists(), "The contract is already initialized");` at the top of `LockupContract::new` in [9](#0-8) , consistent with every other contract in this repository.

### Proof of Concept
1. `lockup-factory` deploys and initializes a lockup contract at `lockup_account_id = sha256(owner)[..20] || factory_account`, with `owner_account_id = victim`, funded with NEAR, per `lockup-factory/src/lib.rs:119-157`.
2. Attacker submits a transaction with `receiver_id = lockup_account_id`, `method = "new"`, and arguments setting `owner_account_id = attacker`, `vesting_schedule = None`, `foundation_account_id = None`, and a `TransfersInformation::TransfersEnabled` value.
3. `LockupContract::new` executes without checking `env::state_exists()`, overwriting the contract state: `owner_account_id` becomes `attacker`, `staking_information` is reset to `None` (losing track of any funds already delegated to a staking pool), and `lockup_information.lockup_amount` is reset to the current `env::account_balance()`.
4. Attacker now calls owner-only methods (e.g. transfer once transfers are enabled) as the new `owner_account_id`, gaining control over the victim's locked NEAR.
