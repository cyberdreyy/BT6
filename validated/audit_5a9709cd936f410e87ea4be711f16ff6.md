### Title
Rejection-tracking table keyed only by signer address (not by block) can silently collide/overwrite rejection records across conflicting blocks - (File: stacks-signer/src/signerdb.rs)

### Summary
`block_rejection_signer_addrs` is defined with `PRIMARY KEY (signer_addr)` only, omitting `signer_signature_hash` from the key [1](#0-0) , unlike its sibling tables which key on the block hash (`blocks` PK is `(reward_cycle, signer_signature_hash)` [2](#0-1) , `block_signatures` PK is `signature` which is unique per message+key [3](#0-2) ). This means the table's "capacity" — one row per signer address — is smaller than what the domain actually needs: one row per (signer, block), because the same signer address can legitimately reject multiple different sibling/competing blocks at the same or different heights (this is exactly the "one-per-height equality" scenario called out in the prompt's rules).

### Finding Description
This table is read via `get_block_rejection_signer_addrs`-style queries and fed into `compute_reject_code_signing_weight`, which tallies per-block rejection weight from a list of `(StacksAddress, RejectReasonPrefix)` pairs [4](#0-3) . Because the primary key is `signer_addr` alone, a single signer address can only ever have one live row in the whole table across all blocks/tenures. When a signer rejects block A (e.g., a tenure-start block) and later rejects a different, conflicting block B proposed by the same one-slot miner at the same height (a scenario the codebase explicitly treats as reachable — see the sibling-conflict tests around `get_signed_conflicts`/`check_block_against_signer_db_state` [5](#0-4) ), the row keyed by that signer's address for block A collides with the attempt to record the rejection for block B.

### Impact Explanation
If this collision resolves via overwrite, block A's previously-recorded rejection is silently erased from `block_rejection_signer_addrs`, so a subsequent `compute_reject_code_signing_weight` computation for block A under-counts rejection weight — the local signer's view of "who rejected A" no longer matches reality. Since this weight feeds decisions about whether a block has reached the blocking/disagreement threshold and whether a locally-rejected block should be reconsidered, corrupting it can cause a signer to disagree with the true rejection tally for a given block, which falls into the "rejection recounted" / miscounted-response impact category (High).

### Likelihood Explanation
The triggering scenario (a single miner re-proposing a competing block at the same height, causing distinct signer_signature_hash values that share the same set of signer addresses) is reachable by a one-slot miner alone, matching the in-scope threat model. However, I could not confirm from the code I retrieved whether the actual `INSERT` executed against this table (in the `add_block_rejection_signer_addr`-equivalent function) is a plain `INSERT` (which SQLite would reject with a `UNIQUE`/primary-key constraint error, surfacing as a `DBError` rather than silent corruption) or an `INSERT OR REPLACE`/`INSERT OR IGNORE` (which would silently overwrite or drop the second block's row). This distinction is the deciding factor between "silent state corruption" (a real analog of the Buffer bug) and "a recoverable DB error with no corruption." I was unable to locate and read that specific insert function's SQL body before the tool budget was exhausted, so this finding should be treated as a plausible but not fully confirmed root cause.

### Recommendation
Add `signer_signature_hash` to the primary key of `block_rejection_signer_addrs` (i.e., `PRIMARY KEY (signer_signature_hash, signer_addr)`), matching the pattern used by the `blocks` table, so that rejections are tracked per (block, signer) pair rather than per signer alone. Independently, verify the insert statement's conflict-resolution clause (`OR REPLACE`/`OR IGNORE`/none) to confirm whether the current behavior is silent overwrite, silent drop, or a surfaced DB error, and add a regression test asserting that two different `signer_signature_hash` values for the same signer address are both retained.

    /// Compute the rejection weight for the given reject code, given a list of signatures
    fn compute_reject_code_signing_weight<'a>(
        &self,
        addrs: impl Iterator<Item = &'a (StacksAddress, RejectReasonPrefix)>,
        reject_code: RejectReasonPrefix,
    ) -> u32 {
        addrs.filter(|(_, code)| *code == reject_code).fold(
            0u32,
            |signing_weight, (stacker_address, _)| {
                let stacker_weight = self.signer_weights.get(stacker_address).unwrap_or(&0);
                signing_weight.saturating_add(*stacker_weight)
            },
        )
    }
