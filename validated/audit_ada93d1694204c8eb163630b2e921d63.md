### Title
Multisig request can execute below the live-member confirmation threshold because `DeleteKey`/`DeleteMember` only purges requests *submitted by* the removed member, not stale confirmations that member gave on requests submitted by *other* members - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
When a multisig member/key is removed via `MultiSigRequestAction::DeleteMember` (`multisig2`) or `MultiSigRequestAction::DeleteKey` (`multisig`), the cleanup logic only deletes pending requests that the removed member itself *originated*. It never scans other pending requests' `confirmations` sets to strip out a confirmation the now-removed member had previously cast. Because `confirm()` counts raw entries in that `HashSet<String>` against the fixed `num_confirmations` threshold, a stale confirmation from a removed member still counts toward execution, letting a request execute with fewer *live* member approvals than `num_confirmations` requires.

### Finding Description
`delete_member` in `multisig2/src/lib.rs` only removes requests where `r.member == member` (requests originated by the removed member): [1](#0-0) 

It does not touch `self.confirmations` entries for requests originated by *other* members that the removed member had confirmed. The analogous `DeleteKey` handler in `multisig/src/lib.rs` has the same gap: [2](#0-1) 

`confirm()` then compares the raw size of the stored `confirmations` set (which can still include the removed member's stale entry) against `num_confirmations`, with no re-validation that every entry in the set corresponds to a currently-live member: [3](#0-2) 

This breaks the intended custody binding: `confirmations counted == confirmations from members who are members at execution time`. Concretely:

1. Multisig has members `A, B, C, D`, `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R` (e.g., a `Transfer`). `R.member == A`.
3. `B` calls `confirm(R)`; `confirmations(R) = {B}` (len 1 < 3, so it's just stored).
4. Separately, `A, C, D` submit and confirm a `DeleteMember{member: B}` request. This executes `delete_member`, which removes `B` from `self.members` and only purges requests where `r.member == B` — `R` was submitted by `A`, so it is untouched, and `confirmations(R)` still contains `B`.
5. `C` calls `confirm(R)`: `confirmations(R).len() == 1` (`{B}`), `+1 = 2 < 3`, so `C` is added: `confirmations(R) = {B, C}`.
6. `D` calls `confirm(R)`: `confirmations(R).len() == 2` (`{B, C}`), `+1 = 3 >= num_confirmations(3)` → `execute_request` fires.

The request executes with confirmations from `B, C, D`, but `B` is no longer a member — only `C` and `D` are live confirmers, i.e. 2 live confirmations against a nominal 3-of-4 threshold. `assert_valid_request`/`current_member` checks only gate who can *call* `confirm`, not whether *previously stored* confirmations still belong to live members: [4](#0-3) 

### Impact Explanation
This lets a multisig request (including fund transfers, key additions, or contract deployment via `execute_request`) execute with fewer live-member confirmations than the configured `num_confirmations`, effectively lowering the security threshold of the multisig without governance approval for that specific request. This matches the in-scope Critical impact "a multisig request executed below threshold," since NEAR (or other privileged actions like `AddKey`/`DeployContract`) can be moved/authorized by a coalition smaller than the intended quorum.

### Likelihood Explanation
Exploitation requires: (a) a pending request with at least one confirmation from a member, and (b) a subsequent, otherwise-legitimate `DeleteMember`/`DeleteKey` request that removes that confirming member. Both actions are ordinary multisig operations — member turnover after partial confirmations is a realistic operational sequence, not an attacker-crafted deployment or admin-only bypass, and no special privilege beyond normal multisig membership is needed to trigger it (the members driving the deletion need not collude maliciously — the outcome is an unintended byproduct of ordinary usage). Because it depends on interleaving legitimate operations, likelihood is moderate rather than trivial-on-demand, but the code has no defense against it at all.

### Recommendation
When removing a member (`delete_member`/`DeleteKey`), iterate over **all** pending requests' `confirmations` sets (not just those the removed member originated) and strip the removed member's entry from each. Alternatively, re-validate at `confirm()` time (or at execution time, before calling `execute_request`) that every entry in the stored confirmation set still corresponds to a current member of `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
Using `multisig2/src/lib.rs` test harness with `members() = [A(account), B(account), C(key), D(key)]` and `num_confirmations = 3`:
1. As `A`, call `add_request(transfer_request)` → `request_id = R`.
2. As `B`, call `confirm(R)` → stored `confirmations(R) = {B}`.
3. As `A`/`C`/`D` (coordinated 3-of-4), submit+confirm `DeleteMember{member: B}` self-request → executes, removing `B` from `members`, but `confirmations(R)` still equals `{B}` because `delete_member`'s cleanup only filters `self.requests` by `r.member == member` (see `multisig2/src/lib.rs:362-371`), which does not match `R` (owned by `A`).
4. As `C`, call `confirm(R)` → `confirmations(R) = {B, C}` (len 2 < 3, stored).
5. As `D`, call `confirm(R)` → `confirmations(R).len()+1 == 3 >= num_confirmations`, so `execute_request(transfer_request)` runs and the transfer executes with only `C` and `D` as live confirmers plus the stale entry from removed member `B`.

This can be reproduced by extending the existing `add_key_delete_key_storage_cleared`-style tests in `multisig2/src/lib.rs` (lines 655-719) to add a third-party (`A`-originated) request confirmed by `B` before `B` is deleted, then completing confirmations with `C` and `D` and asserting the request executes.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
