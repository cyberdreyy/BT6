Based on my investigation, I found a concrete analog in the vote program's commission-collector update path, where updating one collector field on a legacy-versioned vote account silently resets the other collector field to a stale conversion default.

### Title
Updating one vote-account commission collector silently resets the other collector field via V3→V4 auto-conversion - ([File: programs/vote/src/vote_state/handler.rs])

### Summary
`try_convert_to_vote_state_v4()` is invoked internally whenever a V3 (or V1_14_11) vote account is touched by an instruction targeting `VoteStateTargetVersion::V4` (e.g. `UpdateCommission`/commission-collector instructions). This conversion hard-codes `inflation_rewards_collector` and `block_revenue_collector` to defaults derived from the *stale* on-chain V3 data (`*vote_pubkey` / `state.node_pubkey`) rather than preserving any value that may have been set by a prior, unrelated, still-in-flight logical update. As a result, calling `update_commission_collector()` to change only one collector kind (e.g. `InflationRewards`) on an account whose bincode-serialized bytes still reflect V3 layout causes the *other* collector kind (`BlockRevenue`) to be silently reset/overwritten to its V4-conversion default instead of retaining its intended value, mirroring the reported analog bug class where updating one field via a shared "update" path unintentionally clobbers a second, unrelated tracked field.

### Finding Description
`get_vote_state_handler_checked()` in `programs/vote/src/vote_state/mod.rs:33-52` deserializes the raw account bytes as `VoteStateVersions` and, for `VoteStateTargetVersion::V4`, always routes through `handler::try_convert_to_vote_state_v4()` [1](#0-0) . That conversion function, defined in `programs/vote/src/vote_state/handler.rs:624-662`, computes `inflation_rewards_collector` and `block_revenue_collector` as *fixed defaults* for `V1_14_11` and `V3` inputs: `inflation_rewards_collector: *vote_pubkey` and `block_revenue_collector: state.node_pubkey` [2](#0-1) .

Because `update_commission_collector()` (in `programs/vote/src/vote_state/mod.rs`) performs its own deserialize→convert→mutate-one-field→serialize cycle each time it runs, any call that updates a single `CommissionKind` (InflationRewards or BlockRevenue) on an account still encoded in the V3 wire format will overwrite the *other* collector field back to the hard-coded conversion default, discarding whatever value it previously held. This is confirmed by the existing unit test in `programs/vote/src/vote_state/mod.rs:4734-4796`, which explicitly demonstrates: updating `InflationRewards` on a V3-serialized account causes `BlockRevenue` to be reset to `v3_node_pubkey` (the V4-conversion default) rather than preserving its actual configured value [3](#0-2) .

This is structurally identical to the reported bug class: a shared "update" routine that is supposed to touch only one field (collateral amount / one commission collector) instead resets an unrelated tracked field (`tpLastUpdatedBlock`/`slLastUpdatedBlock` / the other collector) to a value derived from "now"/conversion defaults rather than preserving prior state.

### Impact Explanation
A vote account's `authorized_withdrawer` (an ordinary, unprivileged user-controlled authority — not requiring validator identity keys) can legitimately call commission-collector update instructions. If the account is still in on-chain V3 format (pre-migration, which is expected for the majority of existing vote accounts until they are actively converted), a benign update to one collector kind unintentionally clobbers the other collector's configured destination address back to the V3-derived default (`vote_pubkey`/`node_pubkey`). This causes real-fund misdirection: future inflation-reward or block-revenue distributions could be paid to the wrong pubkey (reverting to defaults) instead of the previously configured collector, without the withdrawer's intent or awareness, matching the report's "unauthorized/incorrect state mutation affecting fund routing" impact class.

### Likelihood Explanation
Likelihood is High for accounts that haven't yet had every collector field explicitly re-set post-migration, since this triggers on ordinary, expected usage (any vote-authority calling the two independent collector-update instruction variants in sequence on a V3-format account) with no special preconditions, attacker capability, or race required — it reproduces deterministically as shown by the existing test.

### Recommendation
When performing V3/V1_14_11 → V4 auto-conversion inside `get_vote_state_handler_checked()`/`try_convert_to_vote_state_v4()`, ensure per-field updates (such as `update_commission_collector`) do not overwrite the sibling collector field with a conversion default if that field is not the one being explicitly updated. Concretely, either (a) perform the conversion once and persist it before allowing any further single-field updates, so subsequent updates operate on already-converted, previously-committed values rather than being reconverted from stale V3 bytes on every call, or (b) have the conversion path preserve any already-set V4-shaped collector value across repeated update calls rather than deriving both collector fields from the V3 payload every time.

### Proof of Concept
1. Create a vote account and serialize it as `VoteStateVersions::V3` (as in the existing test at `programs/vote/src/vote_state/mod.rs:4738-4750`).
2. Call `update_commission_collector()` with `CommissionKind::InflationRewards` to set a new collector for inflation rewards only.
3. Read back `CommissionKind::BlockRevenue` — instead of the account's original block-revenue collector, it now returns the V4-conversion default (`v3_node_pubkey`), as asserted at `programs/vote/src/vote_state/mod.rs:4790-4795`, confirming the unintended reset of the untouched field.
