Confirmed analog found: a signer-weight double-counting bug in `StackerDBListener::run` on the miner/node side, structurally identical to the `totalExcludedSupply` drift — an aggregate counter (`total_weight_approved` / `total_weight_rejected`) is incrementally maintained across multiple update paths, and one of those paths fails to keep the invariant "each signer contributes to at most one side" consistent.

### Title
Signer vote-flip lets a single signer's weight be counted in both `total_weight_approved` and `total_weight_rejected`, letting a minority force premature/incorrect block (re)push or block decisions - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tracks, per proposed block, two independently-accumulated weight counters — `total_weight_approved` and `total_weight_rejected` — plus a single `responded_signers: HashSet<u32>` meant to record "this slot has already responded." The accept path guards its increment with a *different* set (`gathered_signatures`) than the reject path uses (`responded_signers`), so a signer that rejects a block and later (upon re-evaluation) accepts the same block gets counted in both totals. [1](#0-0) 

### Finding Description
On an accepted `BlockResponse`, the weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, and `gathered_signatures`/`responded_signers` are both then populated: [2](#0-1) 

On a rejected `BlockResponse`, the weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., this is the first time this slot_id has ever been recorded in `responded_signers`): [3](#0-2) 

Because a signer's local decision on a specific block *can* change (the signer-side state machine explicitly allows `LocallyAccepted <-> LocallyRejected` transitions on re-evaluation, per `docs/signer-flows.md`'s `BlockState` diagram, and `handle_block_validate_ok`/`handle_block_validate_reject` in `stacks-signer/src/v0/signer.rs` re-emit fresh `BlockResponse`s), the following sequence is reachable with only one signer and no majority:

1. Signer S sends `BlockResponse::Rejected` for block B. The node's reject handler sees `responded_signers.insert(slot_id) == true`, so it adds S's weight to `total_weight_rejected` and marks slot_id as responded.
2. S later re-evaluates B (e.g. it initially failed a check that is later resolved, or fault injection re-triggers signing) and sends `BlockResponse::Accepted` for the same block B.
3. The accept handler only checks `gathered_signatures.contains_key(&slot_id)` (a *different* map, never touched by the reject path), which is empty for S, so the accept path unconditionally adds S's weight *again*, this time to `total_weight_approved` — without ever removing it from `total_weight_rejected`.

The result: S's weight is now double-booked, present in both `total_weight_approved` and `total_weight_rejected` simultaneously. This breaks the intended equality that `total_weight_approved` and `total_weight_rejected` are built from disjoint sets of signer weight (bounded together by `self.total_weight`). This is structurally the same class of bug as the external report: an aggregate/cached counter is updated incrementally along several independent code paths that use *different* dedup keys/guards, so the counter drifts from the true underlying set it is supposed to represent.

### Impact Explanation
Both `total_weight_approved >= self.weight_threshold` (line 467) and `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` (line 567-570) are used to wake up the miner thread via `cvar.notify_all()`, driving the block-broadcast/give-up decision. With this drift:
- A minority signer set can inflate `total_weight_approved` past `weight_threshold` faster than legitimately possible (their weight is "double spent" across accept/reject), potentially causing the miner to push the block as approved before a genuine quorum exists.
- Alternatively it can inflate `total_weight_rejected` in the same way, wedging the miner into giving up on a block that in fact has (or could reach) sufficient legitimate approval weight.
- Since `total_weight_approved + total_weight_rejected` can now exceed `self.total_weight` for a single block, the intended safety property "an outcome requires a real majority of the *actual* signer set" is broken with only one signer's cooperation, not a majority.

This is a High-severity liveness/consensus-support wedge on the node side: it can cause the miner to broadcast a block on an inflated/incorrect tally, or to abandon a block prematurely, purely from one signer flipping its vote — no majority of signers or extra keys are required.

### Likelihood Explanation
Vote flips (Rejected -> Accepted) are an explicit, supported part of the signer state machine (`should_reevaluate_block`, `LocallyRejected -> LocallyAccepted : re-evaluated` in the documented `BlockState` diagram, and `handle_block_validate_ok`/`handle_block_validate_reject` both freely re-emit `BlockResponse`s for a signer_signature_hash already tracked). Any legitimate re-evaluation, replay, retried validation, or fault-injected resend that flips a single signer's vote on the same block hash triggers this drift — it does not require malicious behavior, just the ordinary re-evaluation flow already exercised by the codebase's own reject/pre-commit re-check logic (`check_block_against_signer_db_state`, `mark_locally_rejected`/`mark_pre_committed` calls in `stacks-signer/src/v0/signer.rs`).

### Recommendation
Use a single, shared "already counted" bookkeeping structure (e.g., record the *side* previously counted per slot_id, not two separate maps), and when a signer's response flips sides, subtract its weight from the previous total before adding it to the new one — analogous to the recommended fix for `totalExcludedSupply` ("update on every state change," not from independently-guarded, side-specific fast paths). Concretely, replace the `gathered_signatures.contains_key` guard in the accept branch and the `responded_signers.insert` guard in the reject branch with one map from `slot_id -> Side` that both branches consult and update atomically, decrementing the stale side's `total_weight_*` when a flip is detected.

### Proof of Concept
1. Set up a `StackerDBListener` tracking a block B with reward set containing signer S (weight w) among others, `weight_threshold` set normally.
2. Have S send `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for B: verify `blocks[B].total_weight_rejected == w` and `responded_signers == {S.slot_id}`.
3. Have S send `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same B (simulating a re-evaluation flip, as `stacks-signer/src/v0/signer.rs` naturally supports).
4. Observe `blocks[B].total_weight_approved == w` while `blocks[B].total_weight_rejected` remains `w` (not decremented) — i.e., `total_weight_approved + total_weight_rejected > self.total_weight` is achievable with fewer distinct signers than would normally be required, demonstrating the counted-weight invariant is broken.
