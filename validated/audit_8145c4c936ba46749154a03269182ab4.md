### Title
Dust instant-withdraw request freezes all funded instant claims via global `pendingInstantWithdraws` gate — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`requestWithdraw` routes to `IdleCreditVault.requestInstantWithdraw` whenever the new epoch's APR dropped by more than `instantWithdrawAprDelta` (`lastEpochApr > currentApr + instantWithdrawAprDelta`, `IdleCDOEpochVariant.sol:761-768`). Each request increments the *global* `pendingInstantWithdraws` counter in the strategy (`IdleCreditVault.sol:374`). Instant claims are only enabled again once `getInstantWithdrawFunds` pulls the **entire** pending amount from the borrower, which requires `isEpochRunning` and `block.timestamp >= instantWithdrawDeadline` (`IdleCDOEpochVariant.sol:560-573`). Until that funding completes, `claimInstantWithdrawRequest` reverts for every user — including users whose receipts were already funded — because the check is on the aggregate pending balance, not per-user funding (revert confirmed by `test/foundry/IdleCreditVault.t.sol:4882-4884`).

### Finding Description
An unprivileged, KYC-passing lender can grief the instant-withdraw lane with a dust request:

1. During a buffer period where instant withdraws are enabled (APR decreased ≥ `instantWithdrawAprDelta`), honest user A requests an instant withdraw.
2. Epoch starts; `instantWithdrawDelay` passes; manager calls `getInstantWithdrawFunds`, which transfers the pending amount from the borrower to the strategy and sets `allowInstantWithdraw = true` (`IdleCDOEpochVariant.sol:566-570`). `pendingInstantWithdraws` becomes 0 and A's receipt is now fully backed by tokens sitting in the vault.
3. At the next buffer, before A claims, the attacker calls `requestWithdraw(1 wei tranche, AATranche)` (or any dust amount that routes to the instant path). This mints a 1-wei receipt and sets `pendingInstantWithdraws += 1` (`IdleCreditVault.sol:356-374`).
4. Every `claimInstantWithdrawRequest` now reverts with `NotAllowed`, because the claim path gates on the global pending counter rather than on whether the caller's own receipt is funded. The vault already holds A's full payout but cannot release it.
5. The freeze persists until the next `instantWithdrawDeadline` passes inside a running epoch *and* the manager calls `getInstantWithdrawFunds` again to collect the 1 wei. The attacker can repeat the dust request every epoch that instant withdraws stay enabled, re-arming the block each time at a cost of ~1 wei of underlying per epoch.

The broken invariant is receipt isolation: a funded receipt ("one receipt one payout") becomes hostage to the funding state of *other* users' receipts, so a new dust receipt poisons the claim path for already-settled claims. Note `claimInstantWithdrawRequest` burns the caller's full receipt and pays it in one shot (`IdleCreditVault.sol:380-392`), so there is no per-user funded/pending split to fall back to.

### Impact Explanation
Temporary freezing of user funds. All holders of funded instant-withdraw receipts are blocked from claiming underlying already held by `IdleCreditVault` for at least one `instantWithdrawDelay` window (nominally ~3 days per the contract docs) plus the manager action latency, repeatable indefinitely while instant withdraws are enabled. Quantified loss: the full `instantWithdrawsRequests` balance of every funded user (can be the entire tranche NAV queued for instant exit) is locked for the delay duration each round, at negligible attacker cost.

### Likelihood Explanation
Requires an epoch where `lastEpochApr > currentApr + instantWithdrawAprDelta`, i.e., instant mode is active — attacker cannot force this, so likelihood is conditional on APR reductions (a normal market event). The attack needs only a standard KYC-passing lender wallet and dust capital; no privileged role, default, or oracle manipulation is involved. Manager action eventually unblocks each round, making the impact temporary rather than permanent.

### Recommendation
Track funded vs. unfunded instant receipts separately (per-user funded balance or a `fundedInstantWithdraws` counter), and let `claimInstantWithdrawRequest` pay out the caller's funded portion even while `pendingInstantWithdraws > 0`. Alternatively, refuse to route a request into the instant bucket unless it can be funded immediately, or require a minimum non-dust request size and let claims proceed against `min(receipt, fundedBalance)`.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testDustInstantRequestBlocksFundedClaims() external {
    uint256 amountWei = 10000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amountWei);
    idleCDO.depositBB(amountWei);
    address victim = makeAddr('victim');
    _depositWithUser(victim, amountWei, true);

    // epoch 0 -> buffer with lower APR so instant withdrawals are enabled
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // instant request

    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds(); // victim receipt fully funded, pendingInstantWithdraws == 0

    // next buffer, attacker (any KYC wallet) files a dust instant request
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1 * ONE_SCALE, true);
    _stopEpochAndCheckPrices(1, initialProvidedApr / 4, _expectedFundsEndEpoch());
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // dust instant receipt

    _startEpochAndCheckPrices(2);
    // victim's claim reverts even though strategy holds their full payout
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(victim);
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Uncertainty noted: the exact revert line inside `claimInstantWithdrawRequest` was not fully read in this pass, but the gating on global `pendingInstantWithdraws`/`allowInstantWithdraw` is confirmed by `IdleCDOEpochVariant.sol:560-573`, `IdleCreditVault.sol:374-392`, and the existing revert test at `IdleCreditVault.t.sol:4882-4884`.
