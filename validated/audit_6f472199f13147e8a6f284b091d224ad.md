### Title
Missing role check on `/v2/debug/pprof/*` allows any authenticated view-role user to obtain full process heap/CPU profile dumps - ([File: core/web/router.go])

### Summary
`metricRoutes` is mounted inside `authv2` (which only requires successful authentication via `auth.Authenticate`, not a minimum role) with no `auth.RequiresEditRole` or `auth.RequiresAdminRole` wrapper, unlike virtually every other sensitive endpoint in the same group. Any authenticated user — including the lowest-privileged `view`-role user — can therefore call `GET /v2/debug/pprof/heap`, `/profile`, `/goroutine`, etc., and retrieve a full process memory/heap dump.

### Finding Description
`v2Routes` builds the `authv2` group with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` [1](#0-0) , which only verifies that a request is authenticated as *some* user — it performs no role check. All sensitive handlers in this group are additionally wrapped individually with `auth.RequiresEditRole` or `auth.RequiresAdminRole` (e.g. key export/import, job mutation, chain/user management) [2](#0-1) . However, `metricRoutes(authv2)` is called with no such wrapper: [3](#0-2) .

Inside `metricRoutes`, the pprof handlers are registered directly on the group with no role gate: [4](#0-3) .

`auth.Authenticate` only checks that authentication succeeded (session or API token) and sets the `SessionUserKey` context value, without inspecting `user.Role` at all [5](#0-4) . The role-gating logic (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`) exists precisely to reject `view`-role users, but it is never invoked for the pprof routes [6](#0-5) .

Consequently, a `view`-role user (or an API token scoped to view) that successfully authenticates via `AuthenticateBySession` or `AuthenticateByToken` can call `GET /v2/debug/pprof/heap` and receive a 200 response with the raw pprof heap-dump payload, since `c.Next()` is called after auth succeeds and no subsequent role check exists on the route chain.

### Impact Explanation
A heap dump (`/debug/pprof/heap`) or full process profile (`/debug/pprof/profile`, `/goroutine`, `/allocs`) can expose in-memory secrets: decrypted private keys, session tokens, database credentials, or API secrets that transiently reside in Go heap memory during node operation. This corresponds to a credential/key-disclosure impact class — a low-privileged `view` role user (the least trusted authenticated principal, intended only for read-only dashboard access) can escalate to obtaining data far beyond their intended read scope, effectively bypassing the role model that every other route in the file enforces.

### Likelihood Explanation
The only precondition is possessing a valid `view`-role session cookie or `view`-role API token — the lowest privilege tier explicitly supported by the system (`clsessions.UserRoleView`). No admin/edit privileges, no host access, and no additional exploitation steps are required; a single unauthenticated-in-role, but authenticated-in-session, `GET` request suffices, and it is fully repeatable at will (rate-limited only by the generic authenticated rate limiter).

### Recommendation
Wrap the pprof routes with a minimum role requirement consistent with the sensitivity of the exposed data, e.g., require `auth.RequiresAdminRole` (or at minimum `auth.RequiresEditRole`) for all handlers registered in `metricRoutes`, mirroring the pattern already used for `/keys/*` and `/users` routes in `v2Routes`.

### Proof of Concept
1. In a `core/web` handler-level integration test (using the existing test harness in `core/web/router_test.go` or similar, which spins up `NewRouter` with a fake `chainlink.Application`/`AuthenticationProvider`):
   - Seed a user/session with `clsessions.UserRoleView`.
   - Authenticate via `POST /sessions` (or set the session cookie directly) to obtain a valid session for that view-role user.
   - Issue `GET /v2/debug/pprof/heap` with that session cookie.
   - Assert response status is `200 OK` and `Content-Type` matches pprof binary output (`application/octet-stream` or similar), demonstrating no 401/403 is returned.
2. Repeat for `GET /v2/debug/pprof/profile?seconds=1` to confirm CPU profile capture is also reachable.
3. As a regression check, add the same test for `run` and `edit` roles, and after applying the fix (wrapping with `auth.RequiresAdminRole`), assert `403 Forbidden` for `view`/`run`/`edit` roles and `200` only for `admin`.

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
