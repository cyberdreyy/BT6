### Title
Full raw JSON-RPC request (including `req.Auth` credential and `req.Params` secret payload) is logged in cleartext at Debug level before authorization - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
`HandleJSONRPCUserMessage` unconditionally logs the entire incoming request object via `h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)` at line 412, before any authorization or redaction takes place. Unlike the authorization-failure path at line 441, which deliberately reduces the credential to a boolean (`"hasAuth", req.Auth != ""`), this earlier log serializes the full `jsonrpc.Request[json.RawMessage]` struct—including the raw `req.Auth` credential and the raw `req.Params` payload (containing secret create/update/list request bodies)—into node logs.

### Finding Description
`HandleJSONRPCUserMessage` (`core/services/gateway/handlers/vault/handler.go:403`) is the entry point for every gateway user message routed to the Vault handler, reachable by any unauthenticated/unprivileged gateway client that can submit a signed JSON-RPC request (`vaultcommon` methods such as `SecretsCreate`, `SecretsUpdate`, `SecretsDelete`, `SecretsList`). Before the request reaches `h.requestProcessor.ProcessRequest` (the authorization/signature-verification step at line 436), the handler executes: [1](#0-0) 
This statement serializes `req` in its entirety via the structured logger's default encoding, which includes the `Auth` field (the raw credential/signature the requester supplies to prove ownership of a vault identity, referenced later at line 441: `req.Auth != ""`) and `Params` (the raw JSON body of the request, which for `SecretsCreate`/`SecretsUpdate` carries the request-level encrypted secret payload). This happens for every request regardless of whether the request later fails authorization, meaning an attacker only needs to send any well-formed request (with a non-empty `ID`) to have their raw `Auth` token persisted into node logs.

By contrast, the authorization-failure log path at line 441 deliberately avoids emitting the raw token (`"hasAuth", req.Auth != ""`), showing that the developers recognized `req.Auth` as sensitive—but this protection was not applied consistently to the earlier, always-executed debug statement.

### Impact Explanation
If `req.Auth` is a bearer-style credential/signature that authenticates the request as coming from a specific vault owner (used by `vaultcap.Authorizer`/`GatewayVaultRequestProcessor` to derive `AuthorizedOwner()`), then persisting it in cleartext in node logs creates a credential-disclosure path: any log consumer with less privilege than "can act as any vault owner" (e.g., log-aggregation viewers, support staff with read-only log access) can extract another user's raw `Auth` value from the logs and potentially replay it to impersonate that owner's vault write requests (secrets create/update/delete). This falls under the credential/token disclosure and request-impersonation impact classes.

### Likelihood Explanation
The log statement executes unconditionally on every request that has a valid, non-empty `ID` (line 404-410 checks), with no privilege requirement — an unauthenticated/unprivileged gateway client can trigger it on every call, including calls that later fail authorization. The only precondition for exploitation of the disclosed data is that the attacker (or another party) subsequently gains read access to the node's logs at Debug level, which is a lower bar than gaining vault-owner authorization directly. Repeatability is trivial since every request is logged this way.

### Recommendation
Redact or omit the `Auth` field and any sensitive fields inside `Params` before logging the initial "handling vault request" debug message, mirroring the pattern already used at line 441 (log only booleans/lengths, e.g., `"hasAuth", req.Auth != ""`), or implement a custom `MarshalLogObject`/redacting wrapper type for `jsonrpc.Request` that strips `Auth` and secret-bearing `Params` fields before they reach the logger.

### Proof of Concept
1. Construct a `logger.Logger` backed by an in-memory/observed core (e.g., zap's `observer.New`) and inject it as `h.lggr`.
2. Call `h.HandleJSONRPCUserMessage(ctx, req, callback)` with a `req` that has `ID` set and `Auth` set to a known sentinel string (e.g., `"SECRET-AUTH-TOKEN-1234"`), and `Method` set to `vaulttypes.MethodSecretsCreate` with `Params` containing a sentinel string.
3. Inspect the captured log entries for the "handling vault request" message and assert that the sentinel `Auth` value and/or `Params` bytes appear in the serialized `"request"` field.
4. Expected (buggy) result: the sentinel auth token string is present in the log output, confirming credential/secret disclosure. After applying the recommended fix, assert the sentinel string no longer appears in any emitted log field.
