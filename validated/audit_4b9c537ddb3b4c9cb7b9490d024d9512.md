This confirms the mechanism: the withdrawal address used to pay the builder's committed payment is taken directly and solely from `withdrawal.fee_recipient` in `get_builder_withdrawals`, which in turn comes verbatim from `bid.fee_recipient` recorded in `process_execution_payload_bid` (`specs/gloas/beacon-chain.md:2124-2137`), with no state-transition-level check tying it to the actual proposer's registered address.

### Title
Builder payment `fee_recipient` is unenforced in state transition, allowing a builder to misdirect or destroy its own committed payment to the proposer - (File: specs/gloas/beacon-chain.md)

### Summary
`process_execution_payload_bid` accepts and permanently records `bid.fee_recipient` — the execution address that is supposed to receive the builder's payment — without ever validating it against the proposer's actual preference. The only place this consistency is checked is a soft, gossip-layer `IGNORE` condition in `specs/gloas/p2p-interface.md`, which is neither a consensus rule nor mandatory (bids may be relayed off-protocol). The unchecked `fee_recipient` flows unmodified all the way to the final `Withdrawal.address` that pays out real Gwei.

### Finding Description
In `process_execution_payload_bid` (`specs/gloas/beacon-chain.md:2084-2141`), when a bid carries `amount > 0` a `BuilderPendingPayment` is recorded that stores `bid.fee_recipient` verbatim: [1](#0-0) 
No assertion anywhere in this function checks `bid.fee_recipient` against the proposer's registered `ProposerPreferences.fee_recipient`, nor against any non-zero constraint. The function only validates builder activity/balance, bid slot/hash/randao linkage, and blob count.

This pending payment is eventually settled (via `settle_builder_payment`/`apply_parent_execution_payload`) into a `BuilderPendingWithdrawal` that again just copies `fee_recipient`: [2](#0-1) 

Finally, `get_builder_withdrawals` turns this into an actual `Withdrawal` whose `address` is exactly `withdrawal.fee_recipient`, and `apply_withdrawals`/balance accounting pays out that amount to that address without any further validation: [3](#0-2) 

The *only* place the specs assert that `bid.fee_recipient` matches the proposer's intended recipient is a gossip-layer soft check: [4](#0-3) 
This is explicitly an `[IGNORE]` (non-authoritative, drop-from-relay-only) condition, not a `[REJECT]`, so it has no bearing on block or state validity — a block containing a bid with an arbitrary `fee_recipient` (including the zero-valued `ExecutionAddress()`) still passes `process_execution_payload_bid` and is accepted by every spec-following node identically. Additionally, the validator guide explicitly allows proposers to accept bids "by other off-protocol means" (`specs/gloas/validator.md:201-203`), bypassing gossip validation entirely.

This breaks the equality that the builder's committed `bid.value` Gwei is paid to the intended, protocol-recognized recipient (the proposer who accepted the bid expecting payment at their own preferred address). Instead, the builder unilaterally and unaccountably steers where its own committed payment lands, at the consensus/state-transition level, with zero enforcement.

### Impact Explanation
If a builder submits (directly, off gossip) a bid with `fee_recipient` set to the zero `ExecutionAddress()` or to any address other than the proposer's registered one, and the proposer accepts and includes it in a valid block, the resulting `Withdrawal` still executes for the committed `bid.value` — but the Gwei is paid to an address the proposer never authorized to receive it. If that address is the zero address, the Gwei is effectively destroyed (no one can spend from it); if it is any other address, the payment is misdirected away from its intended, protocol-committed recipient. In either case this is a fund-loss/fund-misdirection event for the proposer who is not the attacker and did not consent to that particular payout address, satisfying the "Gwei paid to a non-owner"/"destroyed" impact category — all spec-following nodes will accept this state deterministically identically, since nothing in `process_execution_payload_bid` or the withdrawal derivation enforces the linkage.

### Likelihood Explanation
Any active builder can trigger this merely by constructing a bid with an arbitrary `fee_recipient` and getting it accepted into a block — no special privilege, no coalition, and no client bug is required; it only requires the builder to deviate from the (unenforced) MUST-follow instructions in `specs/gloas/builder.md:134-139`. The check that would prevent it exists only as an optional gossip-relay heuristic, and is bypassed entirely for bids obtained off-protocol, which the validator spec explicitly permits.

### Recommendation
Add a mandatory state-transition-level check in `process_execution_payload_bid` requiring `bid.fee_recipient` to equal the fee recipient the proposer registered (via a committed/verified `ProposerPreferences` reference, e.g. bound into the block or state) whenever `bid.value > 0`, and/or disallow the zero `ExecutionAddress()` as a valid `fee_recipient` for non-zero-value bids, so that block validity itself — not merely gossip forwarding — enforces that the builder's payment goes to the intended recipient.

### Proof of Concept
1. Builder constructs `bid` with `builder_index = B` (an active, funded builder), `value = V > 0`, and `fee_recipient = ExecutionAddress()` (all zero bytes) instead of the proposer's registered address from `SignedProposerPreferences`.
2. Builder signs the bid and sends it directly to the proposer off-protocol (permitted per `specs/gloas/validator.md:201-203`), bypassing the gossip `IGNORE` check in `specs/gloas/p2p-interface.md:977-979`.
3. Proposer includes `signed_execution_payload_bid` in its block. `process_execution_payload_bid` accepts it: all asserted conditions (`is_active_builder`, `can_builder_cover_bid`, signature, slot/hash/randao checks) pass; `bid.fee_recipient` is never checked (`specs/gloas/beacon-chain.md:2084-2141`).
4. Once the parent payload settles (`apply_parent_execution_payload`/`settle_builder_payment`), a `BuilderPendingWithdrawal(fee_recipient=ExecutionAddress(), amount=V, builder_index=B)` is queued (`specs/gloas/beacon-chain.md:1729-1770`).
5. On a later slot's withdrawal sweep, `get_builder_withdrawals` emits `Withdrawal(address=ExecutionAddress(), amount=V, ...)` (`specs/gloas/beacon-chain.md:1815-1833`), and `apply_withdrawals` decreases the builder's balance by `V` while the execution layer credits the zero address — destroying `V` Gwei that the proposer expected to receive, with no consensus rule having been violated.
