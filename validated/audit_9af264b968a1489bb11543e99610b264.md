### Title
Loss haircut stored under post-increment epoch key makes loss-adjusted receipts payable at par — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
When `stopEpochWithDuration` realizes a loss on pending withdraw receipts, `IdleCreditVault.collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]`. However, `epochNumber` is bumped inside `deposit()` while the epoch is still flagged running (the "deposit done on stopEpoch" path, line 607–610), so by the time `collectWithdrawFunds` runs the counter already points at the *next* epoch. Receipts themselves were recorded under the pre-increment epoch via `withdrawsRequestsByEpoch[_user][N]` and `lastWithdrawRequest[_user] = N`. The claim path `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — i.e. key `N` — finds `0`, treats the receipt as fully funded, and `_claimFundedWithdrawRequest` pays the un-haircut `claimBasis` at par even though only the reduced amount was transferred in. This is the direct analog of CVE-2017-5439: a stale key/reference (old epoch index) is used to look up a haircut that was actually stored under a different (freed/advanced) epoch, so the loss adjustment is silently skipped.

### Finding Description
Relevant code, all in `contracts/strategies/idle/IdleCreditVault.sol`:

1. `requestWithdraw` tags the receipt with the *current* epoch (line 260–293): `currentEpoch = epochNumber` (e.g. `N`), `withdrawsRequestsByEpoch[_user][N] += _amount`, `lastWithdrawRequest[_user] = N`.

2. `deposit()` increments `epochNumber` whenever `isEpochRunning()` is true (lines 607–610) — this is the stopEpoch-time deposit, so the counter becomes `N+1` during `stopEpochWithDuration` while the loss-funding calls are still executing.

3. `collectWithdrawFunds(_amount)` then writes `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` (line 421) — i.e. under key `N+1`, not `N`.

4. `_claimLossAdjustedWithdrawRequest(_user)` (lines 789–800) reads `lossEpoch = lastWithdrawRequest[_user]` (= `N`) and `lossRecoveryPriceByEpoch[N]`, which is `0`, so it returns `0` without clearing anything.

5. `claimWithdrawRequest` then falls into `_claimFundedWithdrawRequest` (lines 319–350), which passes the epoch-wait check (`epochNumber (N+1) > lastWithdrawRequest (N)`), burns the receipt tokens, and transfers the *full* `withdrawsRequests[_user]` basis via `_transferFundedClaim`.

Only `pendingToFund = pendingBasis - pendingLoss` was ever pulled from the CDO (line 428), while `pendingWithdraws` was reset to `0` (line 420). The claimant is therefore paid `claimBasis` instead of `claimBasis * lossRecoveryPrice / 1e18`, and the difference is drawn from underlying held for other receipts, the APR0 pool, or recovery reserve.

A secondary corruption: any user whose `lastWithdrawRequest` legitimately equals `N+1` (a request made during the next buffer/epoch) reads `lossRecoveryPriceByEpoch[N+1] != 0` and is haircut by a loss that occurred *before* their request — an unfair haircut plus a matching `pendingWithdraws`/`withdrawsRequests` desync in `_clearWithdrawClaimForEpoch`.

Broken invariant: loss waterfall / one-receipt-one-payout. The haircut recorded under `N+1` is never matched to the receipts recorded under `N`.

### Impact Explanation
Direct theft / insolvency: the first loss-epoch claimant to call `claimWithdrawRequest` (or the queue's `claimWithdrawRequest` on behalf of users) receives `claimBasis - fundedAmount` more underlying than funded. Example: pendingBasis = 1,000,000 USDC-equivalent, realized loss splits so `pendingToFund = 700,000`. The vault holds 700,000 backing those receipts but pays out the full 1,000,000 across claimants until the balance is exhausted; later claimants (including instant-withdraw users whose `instantWithdrawsRequests` were funded, and the default-recovery reserve via `_transferFundedClaim`'s reserve-exclusion logic) are permanently undercollateralized. Loss scales with `pendingLoss = lossAmount * pendingBasis / totalBasis`, i.e. up to nearly the entire funded amount in a near-total loss.

### Likelihood Explanation
Triggering requires only: (a) an unprivileged lender calls `requestWithdraw` during a running epoch (normal user action), and (b) the honest manager later calls `stopEpochWithDuration` with `_lossAmount > 0` — a designed recovery path for partial borrower shortfalls, not an attacker precondition. No malicious privileged role is needed; the mismatch is deterministic given the keying asymmetry. The only caveat is the exact ordering inside `IdleCDOEpochVariant.stopEpochWithDuration`: the exploit holds iff `collectWithdrawFunds` executes after the epoch-number-bumping `deposit()` (or any path where `epochNumber` has advanced before the loss price is recorded). If the CDO calls `collectWithdrawFunds` strictly before the deposit bump, the keys align and this specific instance is invalid — this ordering should be verified first in the PoC, but the `deposit()`-increments-on-stopEpoch comment (line 608) and the "claims available at epoch N+1" test convention indicate the bump precedes funding collection.

### Recommendation
Key the loss price by the epoch in which the receipts were requested, not the current counter. Concretely:
- In `collectWithdrawFunds`, store the haircut under `epochNumber - 1` (or pass the request epoch explicitly from the CDO), matching the `lastWithdrawRequest`/`withdrawsRequestsByEpoch` convention; or
- Maintain an explicit `pendingReceiptsEpoch` variable set when `pendingWithdraws` transitions from 0 and cleared after claims, and index `lossRecoveryPriceByEpoch` with it.
- Alternatively, store the pending-loss ratio on a dedicated `pendingLossPrice` scalar consumed by the next claim cycle instead of an epoch-indexed map.
- Add an invariant test: after `stopEpochWithDuration` with `_lossAmount > 0`, `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` must be non-zero for every user with an unsettled receipt, and total claimed must equal `pendingToFund`.

### Proof of Concept
Foundry fork test (extend `test/foundry/IdleCreditVault.t.sol` harness conventions). Verify the stopEpoch ordering first by asserting `strategy.epochNumber()` inside `collectWithdrawFunds` via a spy or by reading `lossRecoveryPriceByEpoch` after the stop.

```solidity
function testLossHaircutKeyedToWrongEpoch() public {
    // epoch N running: borrower funded, users deposited
    _depositWithUser(alice, 1_000_000e6);
    vm.prank(manager); cdoEpoch.startEpoch();

    // Alice requests full withdraw during epoch N
    uint256 aliceTranches = tranche.balanceOf(alice);
    _requestWithdrawWithUser(alice, aliceTranches);
    uint256 reqEpoch = strategy.epochNumber();
    assertEq(strategy.lastWithdrawRequest(alice), reqEpoch);

    // Manager stops epoch realizing a partial loss (e.g. 30% on pending basis)
    // stopEpochWithDuration -> borrower repays short -> deposit() bumps epochNumber
    // -> collectWithdrawFunds stores lossRecoveryPriceByEpoch[reqEpoch + 1]
    _stopCurrentEpochWithLoss(lossAmount); // helper: stopEpochWithDuration(_interest, _lossAmount)

    // Haircut was stored under the NEXT epoch, not the request epoch
    assertEq(strategy.lossRecoveryPriceByEpoch(reqEpoch), 0);
    assertGt(strategy.lossRecoveryPriceByEpoch(reqEpoch + 1), 0);

    // Funded amount < claim basis
    uint256 funded = underlying.balanceOf(address(strategy));
    uint256 basis  = strategy.withdrawsRequests(alice); // full un-haircut basis
    assertLt(funded, basis);

    // Alice claims: _claimLossAdjustedWithdrawRequest returns 0 (price[N]==0),
    // _claimFundedWithdrawRequest pays at par -> drains funds belonging to others
    uint256 balPre = underlying.balanceOf(alice);
    vm.prank(alice); cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(alice) - balPre;

    // Overpayment equals basis * (1 - lossRecoveryPrice)
    assertGt(paid, funded);            // paid more than what was funded for the epoch
    // or: assertEq(paid, basis) with strategy balance driven toward insolvency
}
```

Expected result: `paid == basis` (par) while only `funded < basis` was collected, i.e. the strategy pays out more than funded and other claims/reserves are impaired. If `lossRecoveryPriceByEpoch(reqEpoch)` is non-zero instead (ordering assumption fails), the finding is invalid and only the symmetric `N+1` mis-haircut edge case would remain for analysis.
