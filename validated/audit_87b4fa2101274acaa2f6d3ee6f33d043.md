### Title
Lender removed from the Keyring whitelist can no longer request a withdrawal, permanently locking already-deposited tranche funds - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
`requestWithdraw`, `claimInstantWithdrawRequest` (indirectly via request-time gating), `depositDuringEpoch`, `_deposit`, and the epoch queue's `requestWithdraw` all enforce `isWalletAllowed(msg.sender)`, i.e. an active Keyring credential or admin whitelist entry. The whitelist check is applied uniformly to deposits and withdrawals. There is no escape path for a user whose credential is revoked after depositing: they cannot create a withdraw request, cannot queue a withdraw in `IdleCDOEpochQueue.requestWithdraw`, and cannot deposit-during-epoch to reposition. The only withdrawal-adjacent function not gated by Keyring is `claimWithdrawRequest`, but it only pays out requests created before revocation. This mirrors the external finding — a delisting/decredentialing event freezes exits, not just entries.

### Finding Description
`isWalletAllowed` (`contracts/IdleCDOEpochVariant.sol:984-987`) returns `IKeyring(keyring).checkCredential(keyringPolicyId, _user)`, which in `KeyringIdleWhitelist.checkCredential` (`contracts/KeyringIdleWhitelist.sol:78-80`) is `whitelist[entity] || Keyring(keyring).checkCredential(...)`. Both terms are revocable: the admin can call `setWhitelistStatus(entity, false)` (`contracts/KeyringIdleWhitelist.sol:102-112`) and the underlying Keyring policy credential can expire or be revoked externally.

`requestWithdraw` reverts with `NotAllowed` when the wallet is not allowed — confirmed by `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw` (`test/foundry/IdleCreditVaultWriteOffEscrow.t.sol:288-291`), where a non-keyring holder of legitimately acquired tranche tokens cannot even submit a withdraw request after epoch stop. `IdleCDOEpochQueue.requestWithdraw` applies `_checkAllowed(msg.sender)` the same way (`contracts/IdleCDOEpochQueue.sol:131-143`). During `isEpochRunning`, requests are closed anyway (`allowAAWithdrawRequest/allowBBWithdrawRequest = false`, set in `startEpoch` at lines 249-250), so the only exit window is the buffer period — and that window is gated by the revocable credential.

No compensating mechanism exists: `restoreOperations` re-enables flags but not the caller's credential; `claimWithdrawRequest`/`claimInstantWithdrawRequest` (`contracts/IdleCDOEpochVariant.sol:967-979`) delegate to `IdleCreditVault`, which tracks receipts by `msg.sender` but cannot help a user who was never able to create a request. Tranche tokens are transferable, but a revoked user cannot burn them for underlyings through any code path.

### Impact Explanation
A lender who deposited while KYC'd and later loses their credential (policy expiry, off-chain compliance event, or admin `setWhitelistStatus(false)` — all honest privileged actions) has 100% of their deposited principal and accrued interest frozen. The freeze is temporary only if the credential is restored; a permanent revocation means permanent freezing. Because requests can only be made during buffer periods, and the vault enforces the credential at request time (not at claim time), the user's funds remain locked inside NAV indefinitely, exposed to future borrower defaults they cannot exit from. Loss magnitude: the user's entire tranche position (`_trancheSupply` share of `lastNAVAA`/`lastNAVBB`).

### Likelihood Explanation
Medium. Credential revocation is a normal operational event for KYC providers (document expiry, sanctions re-screening, policy changes), not an exotic edge case. Every epoch-based vault using `setKeyringParams` exposes this. The countervailing factor is that a removed user could in principle re-credential or rely on admin re-whitelisting, making the freeze potentially temporary rather than permanent — consistent with a Medium rating, same as the source finding.

### Recommendation
Do not gate exit paths on `isWalletAllowed`. Specifically:
- Remove the wallet check from `requestWithdraw` (both in `IdleCDOEpochVariant` and `IdleCDOEpochQueue.requestWithdraw`) and from `claimInstantWithdrawRequest`/`claimWithdrawRequest`, keeping it only on deposit paths (`_deposit`, `depositDuringEpoch`, `requestDeposit`).
- Alternatively, split the flag into deposit-KYC and withdraw-KYC (the deprecated `keyringAllowWithdraw` slot at `contracts/IdleCDOEpochVariant.sol:56` suggests this separation was once intended), or introduce a `depositPaused`-style per-user/per-tranche flag that blocks entries without blocking exits.

### Proof of Concept
Foundry fork PoC (structure, mirroring `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw`):

```solidity
// Setup: vault with keyring set via setKeyringParams(keyring, policyId)
// 1. Mock checkCredential -> true for LP; LP deposits AA, epoch starts and stops normally
idleCDO.depositAA(10000e18);           // LP is credentialed
_startEpochAndCheckPrices(0);
_stopCurrentEpoch();                    // borrower repays, buffer period begins

// 2. Honest admin action: LP's credential is revoked
vm.mockCall(
    keyring,
    abi.encodeWithSelector(IKeyring.checkCredential.selector),
    abi.encode(false)
);
// (or: KeyringIdleWhitelist(admin).setWhitelistStatus(LP, false))

// 3. LP cannot exit despite holding tranche tokens
vm.prank(LP);
vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
cdoEpoch.requestWithdraw(amount, address(AAtranche));

// 4. Queue path equally blocked
vm.prank(LP);
vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
queue.requestWithdraw(amount);

// 5. No claim exists to fall back on -> funds remain in NAV indefinitely
vm.prank(LP);
cdoEpoch.claimWithdrawRequest();       // pays nothing; no prior request
assertGt(tranche.balanceOf(LP), 0);    // LP still holds frozen tranche tokens
```

Note: I did not read the top of `requestWithdraw` in `IdleCDOEpochVariant.sol` (lines ~700-760) directly, so the exact revert site is inferred from the `NotAllowed` revert in the existing test at `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol:288-291`; whether the wallet check sits in `requestWithdraw` itself or a shared helper should be confirmed. This also presumes the issue is not previously acknowledged in the audit scope.
