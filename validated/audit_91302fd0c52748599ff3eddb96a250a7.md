## Analysis

The proposed exploit path does not hold up against the actual code because `switch_operator` in `staking_contract.move` synchronizes commission distribution to the old operator **atomically and synchronously**, within the same transaction, before the operator is swapped — there is no window in which an unprivileged `distribute` call can misattribute commission.

**Key mechanics:**

1. `vesting::update_operator` calls `staking_contract::switch_operator` directly (same transaction, same admin call) — it does not defer synchronization to some later, separately-callable step. [1](#0-0) 

2. Inside `switch_operator`, before the operator key is changed in the `staking_contracts` map, the code forces `distribute_internal` (paying out any already-unlocked stake) and `request_commission_internal` (unlocking accrued commission) for the **old operator**, and only then calls `stake::set_operator_with_cap` and re-inserts the `StakingContract` struct under the new operator's key. [2](#0-1) 

3. `request_commission_internal` records the commission owed to the old operator as an explicit, fixed-address entry in the `distribution_pool` via `add_distribution(operator, staking_contract, operator, commission_amount)` — the recipient address is baked into the pool's shares, not re-derived from "whoever is currently the operator" at distribution time.
