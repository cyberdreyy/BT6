### Title
Signer weight double-counted in both approval and rejection tallies after a reject→accept flip - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::handle_block_response` (the miner-side aggregator that the `SigningCoordinator` polls) tracks per-block `total_weight_approved` and `total_weight_rejected` in `BlockStatus`. The guard that prevents double counting a signer's weight is asymmetric: the `Rejected` branch skips the increment if `responded_signers` already contains the slot (i.e. the signer already voted either way), but the `Accepted` branch only checks `gathered_signatures.contains_key(&slot_id)` — it never checks whether that same slot already contributed to `total_weight_rejected`. A signer that rejects, then legitimately reconsiders and accepts (a flow the codebase explicitly supports per `stacks-signer/CHANGELOG.md`: "a signer will reconsider a block proposal it previously rejected"), ends up with its weight permanently present in **both** `total_weight_rejected` and `total_weight_approved`.

### Finding Description [1](#0-0) 
On acceptance, weight is added solely gated by `gathered_signatures.contains_key(&slot_id)`:
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [2](#0-1) 
On rejection, weight is added gated by `responded_signers.insert(slot_id)` returning true (i.e., first response ever, from either branch):
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
```
This makes the two directions asymmetric:
- Accept → Reject: `responded_signers` already contains the slot from the Accept branch, so the later Reject is *not* counted into `total_weight_rejected`. Correct (no double count).
- Reject → Accept: `responded_signers` already contains the slot from the Reject branch, but the Accept branch never consults `responded_signers` — it only checks `gathered_signatures`, which is empty at that point — so the weight is added to `total_weight_approved` while the earlier addition to `total_weight_rejected` is never reversed.

The `BlockStatus` invariant the coordinator relies on — that each signer's weight is attributed to exactly one of the approve/reject pools — is broken. `stacks-signer/CHANGELOG.md` explicitly documents this as a fixed class of bug ("Do not count both a block acceptance and a block rejection for the same signer/block"), indicating the accept-path guard in this file was never updated to match that invariant. [3](#0-2) 

### Impact Explanation
`SignerCoordinator::wait_for_signatures` (or equivalent polling loop) checks rejection first, then approval: [4](#0-3) 
Because the rejection check runs before the approval check and consumes the stale, never-decremented `total_weight_rejected`, a block that has genuinely accumulated enough real signatures to cross `weight_threshold` can still be declared `SignersRejected` on the strength of weight that the same signers have since retracted by accepting — a stale rejection tally masks a valid acceptance. This wedges block production: the miner discards/retries a block that actually has sufficient signer backing, based on an accounting artifact rather than the live vote state. This is a liveness impact (miner unable to finalize a validly-signed block), consistent with the "wedged into never processing a valid signed outcome" class called out in scope.

### Likelihood Explanation
This requires no majority and no key compromise — it is triggered purely by the ordinary, supported reconsideration flow (`stacks-signer` reject-then-accept behavior documented in the CHANGELOG) from a single signer sending its two ordinary `BlockResponse` messages over StackerDB in the natural reject→accept order. No malicious signer coordination or gossip forgery is needed; a single honest signer that initially rejects for a recoverable reason and later reconsiders triggers it deterministically.

### Recommendation
Make the `Accepted` branch's weight-accounting guard consistent with the `Rejected` branch: when a signer's slot flips from rejected to accepted (or vice versa), decrement the previously-counted pool before incrementing the new one, rather than gating purely on `gathered_signatures`/`responded_signers` presence independently. E.g., track which pool (approved/rejected) each slot last contributed to and adjust both `total_weight_approved` and `total_weight_rejected` on transition, ensuring the invariant `sum of any single signer's weight is attributed to at most one pool at a time` holds.

### Proof of Concept
1. Signer S (weight w) sends `BlockResponse::Rejected` for block B → `responded_signers.insert(slot_S)` succeeds → `total_weight_rejected += w`.
2. Signer S reconsiders (a supported flow) and sends `BlockResponse::Accepted` for block B → `gathered_signatures.contains_key(slot_S)` is false → `total_weight_approved += w`; `responded_signers.insert(slot_S)` is a no-op (already present) but this doesn't gate the accept path.
3. Now `BlockStatus` for B carries S's weight `w` in both `total_weight_approved` and `total_weight_rejected` simultaneously, even though S has exactly one live vote (accept).
4. In `SigningCoordinator`'s polling loop, if `total_weight_rejected.saturating_add(weight_threshold) > total_weight` evaluates true due to this stale double-counted weight, the loop returns `Err(SignersRejected)` even though the current, live vote tally (recomputed from `responded_signers` alone) would show the block has enough approving weight — reproducing the wedge described above.
