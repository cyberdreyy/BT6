### Title
Missing recipient-validation in `staking_contract::set_beneficiary_for_operator` lets an operator permanently trap a staker's own principal and rewards - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::distribute_internal` pays out **all** pending shareholders of a `StakingContract`'s single shared `distribution_pool` (both the staker's withdrawal and the operator's commission) in one loop, using `aptos_account::deposit_coins`, which aborts if the recipient does not accept direct coin transfers. Unlike `vesting::set_beneficiary`, which explicitly guards against this with `assert_account_is_registered_for_apt`, `staking_contract::set_beneficiary_for_operator` performs no such check. An operator can therefore point their beneficiary at an address that rejects direct transfers, causing every future call to `distribute()` (and every internal call from `unlock_stake`, `switch_operator`, `update_commision`, `request_commission`) to abort, permanently freezing the staker's own withdrawable stake alongside the operator's commission.

### Finding Description
`distribute_internal` withdraws the pool's inactive/pending_inactive stake and pays every shareholder currently registered in `staking_contract.distribution_pool` in a single `while` loop: [1](#0-0) 

Both the staker (added via `add_distribution` in `unlock_stake`) and the operator/beneficiary (added via `request_commission_internal`) share this same pool: [2](#0-1) [3](#0-2) 

`aptos_account::deposit_coins` only auto-registers `AptosCoin` for the recipient when it creates a brand-new account; for an existing account that is not yet registered for the coin, it aborts unless `can_receive_direct_coin_transfers` is true: [4](#0-3) 

`set_beneficiary_for_operator` sets `new_beneficiary` with **no validation** that the address can actually receive a direct APT transfer: [5](#0-4) 

This is in sharp contrast to `vesting::set_beneficiary`, whose own docstring explains exactly why this check is required — to prevent `distribute()` from failing and blocking *all other accounts* from receiving APT: [6](#0-5) 

Because `staking_contract.move`'s equivalent function lacks this guard, an operator (who has no privilege over the staker's funds) can create an account they control, disable direct coin transfers on it (or otherwise leave it unregistered for `AptosCoin`), and set it as their beneficiary. From that point on, `distribute_internal` — invoked by the public `distribute()` entry function as well as internally from `unlock_stake`, `switch_operator`, `request_commission`, and `update_commision` — will always abort as soon as it tries to pay the poisoned beneficiary, because the loop processes all shareholders (including the staker) in the same transaction. There is no way to skip only the bad recipient; the entire distribution reverts every time.

### Impact Explanation
This traps the **staker's own principal and reward withdrawals**, not just the operator's commission, because both recipients share the same `distribution_pool` and are paid in the same atomic loop. Since `distribute()` is the only path to actually move funds out of `pending_inactive`/`inactive` stake into a recipient's account, and it becomes permanently un-callable once the malicious beneficiary is in place, the staker's funds are non-recoverably locked (barring the operator voluntarily switching the beneficiary back — an assumption the report should not rely on, especially if the operator's private key is later lost or the operator acts maliciously). This satisfies the "Permanent lock or non-recoverable loss of claim rights in stake … commission, beneficiary … flows" impact category and is a high severity finding: an operator, using only its own unprivileged operator role, can strand another party's (the staker's) assets indefinitely.

### Likelihood Explanation
Likelihood is high: exploitation requires no special access beyond the operator role that already exists in any staking_contract relationship, `features::operator_beneficiary_change_enabled()` must simply be on (a normal production flag), and the mechanics (creating an account and opting out of direct coin transfers, or using an account without an `AptosCoin` `CoinStore`) are standard, low-cost operations available to any account.

### Recommendation
Add the same safeguard used in `vesting::set_beneficiary` to `staking_contract::set_beneficiary_for_operator` (and its `delegation_pool` counterpart, if it has an equivalent push-based payout path): require `aptos_account::assert_account_is_registered_for_apt(new_beneficiary)` (or equivalent "can receive direct coin transfer" check) before accepting the new beneficiary. Additionally, consider hardening `distribute_internal` itself so that a failure to pay one shareholder does not block payment to the rest (e.g., process shareholders individually with isolated error handling, or fall back to a pull-based claim model per recipient) so that no single poisoned recipient can freeze the entire distribution for all parties.

### Proof of Concept
1. Staker `S` creates a `staking_contract` with operator `O` (`staking_contract::create_staking_contract`).
2. `O` (or an account `O` controls) creates a fresh account `B` via `account::create_account` (not through `aptos_account::create_account`, so `AptosCoin` is not auto-registered) and, as `B`, calls the account module's opt-out function to disable arbitrary direct coin transfers (so `can_receive_direct_coin_transfers(B) == false`).
3. `O` calls `staking_contract::set_beneficiary_for_operator(O, B)` — this succeeds with no validation.
4. Time passes; `S` calls `staking_contract::unlock_stake(S, O, amount)`, which internally calls `distribute_internal` (adding pending distributions for both `S` and `O`→`B`), then `request_commission_internal` (adds `O`'s commission, redirected to `B`).
5. Once the stake pool's lockup expires and the coins become inactive, anyone calls `staking_contract::distribute(S, O)`.
6. `distribute_internal`'s loop reaches the `B` entry, calls `aptos_account::deposit_coins(B, …)`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` because `B` is not registered for `AptosCoin` and rejects arbitrary transfers.
7. The entire transaction reverts — `S`'s own pending withdrawal (already computed and staged in the same `distribution_pool`) is never paid, and every subsequent call to `distribute()` (or any function that internally calls `distribute_internal`) fails identically, permanently freezing `S`'s funds unless `O` chooses to fix the beneficiary.

Note: I was not able to fully inspect the exact signature/location of the "opt-out of direct coin transfers" entry function (`set_allow_direct_coin_transfers` in `aptos_account.move`) due to index truncation of that file section; a Devin session with full file access should confirm the exact call path and confirm no additional registration side-effect neutralizes this scenario, and should also check whether `delegation_pool.move` has an analogous push-based payout loop that shares this weakness.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

        // Request to unlock the commission from the stake pool.
        // This won't become fully unlocked until the stake pool's lockup expires.
        stake::unlock_with_cap(commission_amount, &staking_contract.owner_cap);

        let pool_address = staking_contract.pool_address;
        emit(
            RequestCommission {
                operator,
                pool_address,
                accumulated_rewards,
                commission_amount
            }
        );

        commission_amount
    }

    /// Staker can call this to request withdrawal of part or all of their staking_contract.
    /// This also triggers paying commission to the operator for accounting simplicity.
    public entry fun unlock_stake(
        staker: &signer, operator: address, amount: u64
    ) acquires Store, BeneficiaryForOperator {
        // Short-circuit if amount is 0.
        if (amount == 0) return;

        let staker_address = signer::address_of(staker);
        assert_staking_contract_exists(staker_address, operator);

        let store = borrow_global_mut<Store>(staker_address);
        let staking_contract = store.staking_contracts.borrow_mut(&operator);

        // Force distribution of any already inactive stake.
        distribute_internal(
            staker_address,
            operator,
            staking_contract,
        );

        // For simplicity, we request commission to be paid out first. This avoids having to ensure to staker doesn't
        // withdraw into the commission portion.
        let commission_paid =
            request_commission_internal(
                operator,
                staking_contract,
            );

        // If there's less active stake remaining than the amount requested (potentially due to commission),
        // only withdraw up to the active amount.
        let (active, _, _, _) = stake::get_stake(staking_contract.pool_address);
        if (active < amount) {
            amount = active;
        };
        staking_contract.principal -= amount;

        // Record a distribution for the staker.
        add_distribution(
            operator,
            staking_contract,
            staker_address,
            amount,
        );

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
