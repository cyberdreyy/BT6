### Title
`getLargestAccounts` cache key omits commitment level, allowing an unrooted "processed" answer to be served as "finalized" - ([File: rpc/src/rpc_cache.rs])

### Summary
`LargestAccountsCache` stores cached results keyed only by `Option<RpcLargestAccountsFilter>` (i.e., `Circulating`/`NonCirculating`/`None`), with no dimension for commitment level. A client can populate the cache with a `processed`-commitment query that reads accounts from an as-yet-unrooted (and possibly soon-to-be-abandoned) fork, and then within `LARGEST_ACCOUNTS_CACHE_DURATION` issue a `finalized`-commitment query on the same filter, which will hit the cache and return the same (slot, accounts) tuple derived from the unrooted bank as if it were finalized data.

### Finding Description
`LargestAccountsCache::set_largest_accounts`/`get_largest_accounts` operate on `self.cache: HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>` [1](#0-0) . The key type is derived solely from `filter` (the circulating/non-circulating selector), and `set_largest_accounts`/`get_largest_accounts` never take or store a commitment level: [2](#0-1) . `JsonRpcRequestProcessor::get_largest_accounts` in `rpc.rs` selects the working `Bank` for the request using the caller-supplied commitment (`processed` picks the current, potentially unrooted, working bank; `finalized` picks the highest confirmed-rooted bank), computes `(slot, accounts)` from that bank, and calls `largest_accounts_cache.set_largest_accounts(&filter, slot, &accounts)` / `get_largest_accounts(&filter)` using only the filter as the lookup/storage key. Because commitment is not part of the key, a `processed` call that lands on a bank belonging to a fork that is later abandoned/pruned populates the same cache slot that a later `finalized` call for the same filter will read from, so the finalized RPC response can present unrooted-fork slot/account data as finalized truth. Existing guards (parameter validation, commitment enum, subscription quotas) only validate/parse commitment; none of them cause the cache key to encode commitment, so nothing prevents the cross-commitment collision.

### Impact Explanation
This causes an RPC client to receive `finalized`-commitment data (with `RpcResponseContext::new(slot)` and account balances) that actually originated from an unrooted, potentially-abandoned fork — a wrong-slot/fork data-integrity bug reachable via two normal, unprivileged JSON-RPC calls. This matches the "wrong slot/fork/account data returned" bounty category rather than a crash/DoS; there is no consensus-state mutation or validator crash, only an incorrect/misleading API response that downstream consumers (exchanges, indexers) may treat as finalized truth.

### Likelihood Explanation
Preconditions are minimal and fully within the unprivileged single-client model: one client, two sequential `getLargestAccounts` JSON-RPC calls (`processed` then `finalized`, same `filter`) within `LARGEST_ACCOUNTS_CACHE_DURATION`, timed so the first call lands while the node's working bank is on a fork that later gets abandoned before finalization. This is naturally occurring during any competing-fork/reorg window, not something the attacker needs to engineer beyond call timing, making it realistically repeatable, though it depends on the node actually experiencing a fork switch within the cache TTL, which is an environmental/timing condition outside the attacker's direct control.

### Recommendation
Extend the cache key to include the commitment level (e.g., change the map to `HashMap<(Option<RpcLargestAccountsFilter>, CommitmentLevel), LargestAccountsCacheValue>` or equivalent), and pass the request's commitment through `set_largest_accounts`/`get_largest_accounts` so entries for different commitment levels never collide.

### Proof of Concept
Integration test plan (in `rpc/src/rpc.rs` or a new integration test using `BankForks`):
1. Build two competing forks A (slot 10) and B (slot 11) off a common parent in `BankForks`, with fork B set to become the confirmed/finalized fork and fork A destined to be pruned.
2. Set fork A as the current working bank; call `JsonRpcRequestProcessor::get_largest_accounts` with `commitment: Some(CommitmentConfig::processed())` and `filter = Circulating`. Assert the returned slot equals fork A's slot (10), and that `largest_accounts_cache.set_largest_accounts(&filter, 10, &accounts_a)` was invoked.
3. Advance `BankForks` so fork B is rooted/finalized and fork A is pruned/dropped (simulating the fork loss), without exceeding `LARGEST_ACCOUNTS_CACHE_DURATION`.
4. Call `get_largest_accounts` again with `commitment: Some(CommitmentConfig::finalized())` and the same `filter = Circulating`.
5. Assert failure of the invariant: the returned slot is `10` (fork A's, abandoned) rather than fork B's finalized slot (11), demonstrating `get_largest_accounts(&filter)` returned the cached processed/unrooted value for a finalized request — i.e., `assert_ne!(result.context.slot, bank_forks.root())` currently fails to hold as an invariant, exposing the bug. A unit test directly on `LargestAccountsCache` can also show the collision: call `set_largest_accounts(&filter, 10, &accounts)` (simulating a processed/unrooted read), then `get_largest_accounts(&filter)` and show it returns slot 10 regardless of any commitment context, because no commitment parameter exists in the API at all.

```rust
    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }

    pub(crate) fn set_largest_accounts(
        &mut self,
        filter: &Option<RpcLargestAccountsFilter>,
        slot: u64,
        accounts: &[RpcAccountBalance],
    ) {
        self.cache.insert(
            filter.clone(),
            LargestAccountsCacheValue {
                accounts: accounts.to_owned(),
                slot,
                cached_time: SystemTime::now(),
            },
        );
    }
```
