### Title
Stale-`block_info` clobber in `process_pending_responses_for_block` lets a nested pre-commit reentry overwrite a same-pass sign/reject decision - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`process_pending_responses_for_block` replays parked early votes (pre-commits, rejections, signatures) for a block whose proposal just arrived. It holds a single `block_info: &mut BlockInfo` snapshot taken *before* the loop and passes it, by reference, into `store_and_process_block_rejection`/`store_and_process_block_signature` for the rejection/signature phases, but the pre-commit phase instead calls `self.handle_block_pre_commit(...)`, which independently re-loads its *own* copy of `BlockInfo` from the DB, mutates it (up to `mark_locally_accepted`/signing), and writes it back — all without touching or refreshing the caller's `block_info`. This is structurally the same "state-mutating call in the middle of a loop, callee touches shared state the loop's live variable doesn't see" pattern that the reported `createBasket` re-entrancy bug describes for token callback hooks.

### Finding Description
`handle_block_proposal` builds a fresh `BlockInfo` (`Unprocessed`, `valid: None`), stores it with `insert_block`, then calls: [1](#0-0) 

into `process_pending_responses_for_block`, which loops three times over drained pending responses: [2](#0-1) 

The pre-commit loop calls `handle_block_pre_commit`, which does its own independent DB round-trip: `self.block_lookup_by_reward_cycle(block_hash)` loads its own local `block_info`, and if the pre-commit threshold is already met (a single weight-1 pre-committer can meet it, as shown in the test at `stacks-signer/src/v0/tests.rs:695-703`), it can transition the block all the way through the chainstate re-check and reach a terminal decision (sign, or reject) inside `handle_block_pre_commit`/`should_reevaluate_block`'s sign path, writing that new state back via `insert_block`: [3](#0-2) [4](#0-3) 

Meanwhile, `process_pending_responses_for_block`'s own `block_info` variable was captured once, at loop entry, and never refreshed from the DB between the pre-commit sub-loop and the subsequent rejection/signature sub-loops. Those later sub-loops pass this *stale* `&mut BlockInfo` straight into `store_and_process_block_rejection`/`store_and_process_block_signature`, which mutate it further (e.g. `mark_locally_rejected` or `mark_locally_accepted`) and unconditionally `insert_block` it back: [5](#0-4) 

Because `insert_block` is a raw DB write of the passed `BlockInfo` object with no optimistic-concurrency/state check against what is currently persisted, a write derived from the stale in-loop copy can overwrite whatever terminal state the nested pre-commit call in the *same* pass already committed. `BlockInfo::move_to`/`check_state` guard illegal *local* transitions on the in-memory struct being written, but they cannot see that a *different* struct instance already moved the persisted row further along — the stale struct still thinks the block is `Unprocessed`, so its own transition (e.g. `mark_locally_rejected`) is "legal" from its own point of view and simply clobbers the DB row.

### Impact Explanation
This can regress a decision the signer already committed to in the same event: if the pre-commit sub-loop causes this signer to sign (`mark_locally_accepted`, `signed_self` set, signature already broadcast via `send_block_response`) or to reject-and-broadcast, and a later sub-loop in the same call subsequently writes the stale `Unprocessed`-derived `BlockInfo` back to the DB, the persisted `signed_self`/`state`/`reject_reason` can be lost or reverted even though the network-visible message (signature or rejection) was already sent. That breaks the local bookkeeping invariant the rest of the state machine relies on (`block_info.signed_self.is_some()` gates in `handle_block_pre_commit`, conflict checks in section 5 of the flow map, and duplicate-processing guards in `handle_block_validate_response`/`handle_block_validate_ok`), because the DB row no longer matches what was actually broadcast. That can, in turn, let this signer be tricked into re-evaluating and signing a second, conflicting block at the same height later (since `signed_self`/`state` no longer show the prior commitment), which is exactly the "signer signing a conflicting/equivocating block" class this scan is meant to catch. It is a self-inflicted local-state corruption bug, not requiring a majority of signers or another signer's key — only crafted pending votes (or naturally arriving ones) ahead of a delayed proposal.

### Likelihood Explanation
Triggering this requires no colluding majority: an attacker (or just network jitter/asynchrony) only needs to get this signer's peers' pre-commit for a new block to arrive and be parked as "pending" (unknown block) before the proposal itself, alongside a rejection or acceptance vote from another peer for the *same* block hash that also arrives early and gets parked. This is the normal "early votes" scenario the code explicitly supports (`drain_pending_block_responses`), so the ordering that exposes the stale-write race is well within reach of a single miner/relay controlling message timing — no majority weight is needed to *create* the window, only to reach the pre-commit threshold that makes `handle_block_pre_commit` produce a terminal decision inside the loop (which the code already assumes can happen "in a single event" per the existing test at `stacks-signer/src/v0/tests.rs:695-703`). Whether the DB-level clobber actually reverts an already-broadcast decision depends on exact interleaving of pending-vote types and thresholds, which I was not able to fully trace end-to-end within the available context (in particular I could not confirm from the excerpts available whether `store_and_process_block_rejection`'s and `store_and_process_block_signature`'s write of a *stale* `block_info` is unconditionally accepted by `insert_block` versus rejected by some invariant I have not located).

### Recommendation
In `process_pending_responses_for_block`, re-fetch `block_info` from `self.signer_db` (or otherwise refresh the caller's local copy) between each sub-loop — and ideally before each individual replayed response — so that the rejection/signature replay always operates on the block's current persisted state rather than the pre-loop snapshot. Alternatively, make `handle_block_pre_commit`, `store_and_process_block_rejection`, and `store_and_process_block_signature` all load-and-mutate the *same* shared `&mut BlockInfo` rather than each independently round-tripping through the DB, and have `insert_block` (or a wrapper) enforce that a write cannot regress a `state`/`signed_self` that is already more advanced than the one being written.

### Proof of Concept
1. Two peer signers pre-commit and one peer rejects a not-yet-seen block `B` at reward cycle `R`; all three responses are stored as pending (`add_pending_block_pre_commit_response` / `add_pending_block_rejection_response`) via the early-vote paths reachable from `handle_block_pre_commit`'s "unknown block" branch and `handle_block_response`'s rejection path.
2. The proposal for `B` finally arrives. `handle_block_proposal` builds `block_info` (`Unprocessed`), inserts it, drains the pending responses, and calls `process_pending_responses_for_block(..., &mut block_info, pending_responses)` (`stacks-signer/src/v0/signer.rs:1716-1725`).
3. In the pre-commit sub-loop, `handle_block_pre_commit` is invoked for the two parked pre-committers; with weight already at/above threshold (mirroring the single-weight-signer scenario asserted in `stacks-signer/src/v0/tests.rs:695-703`), this signer's own `handle_block_pre_commit` call reaches the threshold, passes `check_block_against_signer_db_state`, and signs — calling `mark_locally_accepted`, `insert_block`, and broadcasting the signature (`send_block_response`) — all using its *own* freshly loaded `BlockInfo`, independent of the caller's `block_info` (`stacks-signer/src/v0/signer.rs:1250-1366`).
4. Back in `process_pending_responses_for_block`, the rejection sub-loop now runs with the caller's original, stale `block_info` (still `Unprocessed`/`valid: None`) and calls `store_and_process_block_rejection`, which can mark it `LocallyRejected` and `insert_block` it, overwriting the just-signed row in the DB.
5. Observe (would require running the signer test harness) that `signer_db.block_lookup(&B.hash())` after step 4 no longer reflects `LocallyAccepted`/`signed_self`, even though a signature for `B` was already broadcast in step 3 — a persisted-state/broadcast-state divergence that downstream conflict/duplicate-signing guards rely on being consistent.

    /// Process pending responses for a block proposal that we may have received late.
    fn process_pending_responses_for_block(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &mut BlockInfo,
        pending_responses: PendingBlockResponses,
    ) {
        let signer_signature_hash = block_info.block.header.signer_signature_hash();
        for stacker_address in pending_responses.pre_commits {
            debug!("{self}: Processing pending pre-commit.";
                "stacker_address" => %stacker_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
            );
            self.handle_block_pre_commit(
                stacks_client,
                sortition_state,
                &stacker_address,
                &signer_signature_hash,
            );
        }
        for (stacker_address, reject_reason) in pending_responses.rejections {
            debug!("{self}: Processing pending rejection.";
                "stacker_address" => %stacker_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
                "reject_reason" => ?reject_reason,
            );
            self.store_and_process_block_rejection(
                sortition_state,
                block_info,
                &stacker_address,
                reject_reason,
            );
        }
        let block_id = block_info.block.block_id();
        for (stackers_address, signature) in pending_responses.signatures {
            debug!("{self}: Processing pending signature.";
                "stacker_address" => %stackers_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_id,
            );
            self.store_and_process_block_signature(
                stacks_client,
                sortition_state,
                block_info,
                &stackers_address,
                &signature,
            );
        }
    }

    /// Store the block acceptance signature and check if we have reached a consensus decision on the block because of it. If we have, update the block state accordingly and broadcast the block if accepted.
    fn store_and_process_block_signature(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &mut BlockInfo,
        signer_address: &StacksAddress,
        signature: &MessageSignature,
    ) {
        let block_hash = &block_info.signer_signature_hash();
        // signature is valid! store it.
        // if this returns false, it means the signature already exists in the DB, so just return.
        if !self
            .signer_db
            .add_block_signature(block_hash, signer_address, signature)
            .unwrap_or_else(|_| panic!("{self}: Failed to save block signature"))
        {
            return;
        }

        // If this isn't our own signature and we haven't seen a pre-commit from this signer yet, try treating it as a pre-commit in case the caller is running an outdated version
        if signer_address != &self.stacks_address && !self.signer_db.has_committed(block_hash, signer_address).inspect_err(|e| warn!("Failed to check if pre-commit message already considered for {signer_address:?} for {block_hash}: {e}")).unwrap_or(false) {
            self.handle_block_pre_commit(stacks_client, sortition_state, signer_address, block_hash);
            return;
        }

        if block_info.signed_group.is_some() {
            // We have already processed this block to the accepted state. Adding more signatures will not change anything so nothing to check.
            return;
        }
        // do we have enough signatures to broadcast?
        // i.e. is the threshold reached?
        let signatures = self
            .signer_db
            .get_block_signatures(block_hash)
            .unwrap_or_else(|_| panic!("{self}: Failed to load block signatures"));

        // put signatures in order by signer address (i.e. reward cycle order)
        let addrs_to_sigs: HashMap<_, _> = signatures
            .into_iter()
            .filter_map(|sig| {
                let Ok(public_key) = Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s(
                    block_hash.bits(),
                    &sig,
                ) else {
                    return None;
                };
                let addr = StacksAddress::p2pkh(self.mainnet, &public_key);
                Some((addr, sig))
            })
            .collect();

        let signature_weight = self.signer_weights.get(signer_address).unwrap_or(&0);
        let total_signature_weight = self.compute_signature_signing_weight(addrs_to_sigs.keys());
        let total_weight = self.compute_signature_total_weight();

        let min_weight = NakamotoBlockHeader::compute_voting_weight_threshold(total_weight)
            .unwrap_or_else(|_| {
                panic!("{self}: Failed to compute threshold weight for {total_weight}")
            });

        if min_weight > total_signature_weight {
            info!("{self}: Received block acceptance, but have not yet reached the acceptance threshold.";
                "signer_signature_hash" => %block_hash,
                "signature_weight" => signature_weight,
                "consensus_hash" => %block_info.block.header.consensus_hash,
                "block_height" => block_info.block.header.chain_length,
                "total_weight_approved" => total_signature_weight,
                "total_weight" => total_weight,
                "percent_approved" => (total_signature_weight as f64 / total_weight as f64 * 100.0),
            );
            return;
        }
        info!("{self}: have reached the block acceptance threshold";
            "signer_signature_hash" => %block_hash,
            "signature_weight" => signature_weight,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "total_weight_approved" => total_signature_weight,
            "total_weight" => total_weight,
            "percent_approved" => (total_signature_weight as f64 / total_weight as f64 * 100.0),
        );

        // have enough signatures to broadcast!
        // move block to LOCALLY accepted state.
        // It is only considered globally accepted IFF we receive a new block event confirming it OR see the chain tip of the node advance to it.
        if let Err(e) = block_info.mark_locally_accepted(true) {
            if !block_info.has_reached_consensus() {
                warn!("{self}: Failed to mark block as locally accepted: {e:?}");
            }
        }
        let _ = self.signer_db.insert_block(block_info).map_err(|e| {
            warn!("Failed to set group threshold signature timestamp for {block_hash}: {e:?}");
            panic!("{self} Failed to write block to signerdb: {e}");
        });
