## Analysis

Searching the signer's reorg-permission logic (`SortitionData::check_parent_tenure_choice`) turned up a timing calculation that mirrors the Lido bug exactly: a real, meaningful timestamp is silently replaced by a hardcoded `0` when it is missing, which then trivially satisfies a "was this too fast?" comparison and flips the result in the *permissive* direction. [1](#0-0) 

### Title
Missing `approved_time` defaulted to `0` causes the signer to wrongly permit a reorg of an already-established, globally-accepted tenure - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_parent_tenure_choice` decides whether a miner's tenure is allowed to reorg a previous tenure that already produced blocks. The permit hinges on how much time elapsed between the reorged tenure's first block being approved and the next sortition (`first_proposal_burn_block_timing`). When the signer's local record for that block has no `approved_time`, the code hardcodes the elapsed time to `0` instead of computing (or safely refusing to compute) the real value, which always satisfies "poorly timed" and unconditionally grants the reorg permit — exactly analogous to `LidoEthBaseInterestAllocator`'s `getLidoData` being seeded with `0` instead of `block.timestamp`, which deflated the elapsed-time denominator and let clearly-invalid low-APR offers pass a "was this properly rated" check.

### Finding Description
`BlockInfo::approved_time` is only stamped when the signer itself pre-commits or locally accepts a block: [2](#0-1) . It is explicitly documented elsewhere in this codebase that a block which reaches global acceptance purely through observation of the network's aggregate signature (i.e. this signer never personally pre-committed/locally-accepted it) can have `approved_time == None` even though `signed_group` is set and the block is fully, canonically settled: [3](#0-2) . `has_approved_block_in_tenure`'s SQL predicate (`signed_self IS NOT NULL OR signed_group IS NOT NULL OR approved_time IS NOT NULL`) confirms this three-way OR is the general pattern used across the file for "do we have local knowledge of this block": [4](#0-3) .

In `check_parent_tenure_choice`, once a reorged tenure's local block record is found, the code computes:

```rust
let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
    sortition_state_received_time.saturating_sub(approved_at)
} else {
    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
    0
};
if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
    // ... "poorly timed", ALLOW the reorg
}
``` [5](#0-4) 

`Duration::from_secs(0)` is always `<` the configured `first_proposal_burn_block_timing` (default 60s, never 0), so whenever `approved_time` is `None`, the branch that grants the reorg permit is taken unconditionally, regardless of how long the reorged tenure was actually alive and canonical. This is the same root-cause pattern as the Lido bug: a real elapsed-time input that should reflect "time since the event" is replaced by `0`, and that `0` silently biases a subsequent inequality check toward the permissive branch instead of causing an error or a safe default.

This directly breaks the "approved-parent vs canonical" invariant this function exists to protect: the whole point of the timing check is to distinguish a tenure that was established long enough to be defended (deny reorg) from one that had no fair chance (allow reorg). Coercing the unknown case to `0` always classifies it as "no fair chance," even for tenures that were fully, globally signed (which itself requires real wall-clock time for 70% of signers to aggregate signatures) and thus were unambiguously established.

### Impact Explanation
When this branch is hit, the signer treats a genuinely-established, globally-accepted tenure as if it had zero seconds to defend itself, and marks it superseded (`record_superseded_tenure`) purely on the strength of a missing local timestamp, then later signs over the replacing miner's block. This is a "canonical vs approved-parent" equality violation as scoped in the rules: a signer can be led into signing off on / permitting a reorg of a canonical established tenure that should have been denied. A miner that structures its proposal chain such that a given signer's local `approved_time` is unset for the target tenure (e.g., that signer observed global acceptance via the network rather than personally approving the block — a state reachable purely from normal signer/miner message flow, not requiring a majority of signers or key compromise) can exploit this bias to have that individual signer wrongly grant a reorg permit it should have refused.

### Likelihood Explanation
The precondition — a `BlockInfo` with `signed_group` set but `approved_time` unset — is a state the signer database is designed to produce (per the `get_tenure_last_block_info` doc comment) whenever a signer learns of global acceptance without itself having pre-committed/locally-accepted the block, e.g., timing/ordering of network messages, a restart between seeing the proposal and seeing the group signature, or a signer that never received the original proposal but did observe the resulting global acceptance. This is a plausible occurrence in normal one-signer-plus-gossip conditions, not requiring majority collusion.

### Recommendation
Do not substitute `0` for a missing `approved_time`. Either:
- fall back to a value that is safe in the "deny" direction (e.g., treat missing `approved_time` as "sufficient time has passed" so the reorg is denied by default when timing information is unavailable), or
- derive the real elapsed time from another reliable timestamp (e.g., `proposed_time`, or the tenure's globally-accepted timestamp) instead of hardcoding zero.

### Proof of Concept
1. Signer A never locally pre-commits/accepts Tenure T's first block (e.g., message ordering/restart), but later learns via the network that T's first block reached global acceptance (`signed_group` set, `approved_time` still `None`) — confirmed possible per `get_tenure_last_block_info`'s doc comment [3](#0-2) .
2. A new miner proposes a block whose parent tenure reorgs T (bypassing the prior sortition). `check_parent_tenure_choice` finds exactly one globally-accepted block in T and fetches Signer A's local record via `get_first_approved_block_in_tenure`.
3. Because `local_block_info.approved_time` is `None`, `proposal_to_sortition` is hardcoded to `0` at `stacks-signer/src/chainstate/mod.rs:251-258`.
4. `Duration::from_secs(0) < first_proposal_burn_block_timing` is always true, so the code path at `stacks-signer/src/chainstate/mod.rs:259-274` unconditionally logs "the block was poorly timed, allowing the reorg" and marks T superseded, regardless of T's real, possibly long-established, canonical status.

    pub fn mark_pre_committed(&mut self) -> Result<(), String> {
        self.valid = Some(true);
        self.approved_time.get_or_insert(get_epoch_time_secs());
        self.move_to(BlockState::PreCommitted)
    }

    /// Mark this block as valid and the appropriate timestamps if they aren't already set, and attempt to mark it as locally accepted.
    pub fn mark_locally_accepted(&mut self, group_signed: bool) -> Result<(), String> {
        if group_signed {
            self.signed_group.get_or_insert(get_epoch_time_secs());
        } else {
            self.valid = Some(true);
            self.approved_time.get_or_insert(get_epoch_time_secs());
            self.signed_self.get_or_insert(get_epoch_time_secs());
        }
        self.move_to(BlockState::LocallyAccepted)
    }
