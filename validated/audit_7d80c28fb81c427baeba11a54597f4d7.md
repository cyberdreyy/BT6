### Title
Multisig `confirm()` Counts Stale Confirmations From Revoked Keys/Members, Allowing Request Execution Below The Configured Threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` tallies confirmations purely from the `confirmations` `HashSet` stored against a `request_id`, without re-validating that every entry in that set still corresponds to a currently-authorized key/member. When a key (v1) or member (v2) is removed via `DeleteKey`/`DeleteMember`, the cleanup logic only purges requests and confirmations for **requests originally submitted by that key/member** — it does not purge confirmations that key/member previously cast on **other members' pending requests**. Those stale confirmations continue to count toward `num_confirmations`, letting a request execute with fewer live, currently-authorized approvers than the configured threshold.

### Finding Description
In `multisig/src/lib.rs`, `execute_request`'s `DeleteKey` branch:
```
MultiSigRequestAction::DeleteKey { public_key } => {
    ...
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)   // only requests ADDED by pk
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [1](#0-0) 

This filters on `r.signer_pk == pk`, i.e. only requests that the removed key itself *created*. If that key had instead cast a `confirm()` on a request created by a different signer, that stale entry remains inside the `confirmations` `HashSet` tied to that other `request_id`, because nothing else in the contract scans `self.confirmations` for stale public keys on deletion.

`confirm()` then trusts the raw cardinality of that set against the required threshold:
```
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert!(!confirmations.contains(&env::signer_account_pk()), ...);
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else { ... }
}
``` [2](#0-1) 

`assert_valid_request` never checks that entries in `confirmations` (nor the newly signing key) are still live access keys on the account — it only checks predecessor == current account and that the request/confirmations maps contain the id:
```
fn assert_valid_request(&mut self, request_id: RequestId) {
    assert_eq!(env::current_account_id(), env::predecessor_account_id(), ...);
    assert!(self.requests.get(&request_id).is_some(), ...);
    assert!(self.confirmations.get(&request_id).is_some(), ...);
}
``` [3](#0-2) 

The contract's own README acknowledges the underlying root cause — it has no way to query the blockchain for the account's live access-key set — but frames it only as a "lockup" gotcha, missing the inverse (and more severe) consequence: stale confirmations can also **help** a request cross the threshold rather than block it. [4](#0-3) 

The identical pattern exists in `multisig2`, whose `MultiSigRequestAction::DeleteMember` handler and `confirm()` mirror the v1 logic — cleanup on deletion is scoped to requests submitted by the removed member, not to that member's confirmations recorded on other members' requests. [5](#0-4) [6](#0-5) 

**Binding broken:** `confirmations recorded for request_id == live, currently-authorized members at time of execution`. The contract instead executes with `confirmations recorded ⊇ live members`, i.e. it can be satisfied by fewer than `num_confirmations` members who are actually still trusted.

### Impact Explanation
This is a threshold-bypass on a governance/custody primitive that directly guards a NEAR account's funds and full-access keys. A `Transfer` (or `AddKey`/`FunctionCall`) request can be pushed through and executed with fewer live approvals than the deployer configured (`num_confirmations`), because a confirmation cast by a key/member that has since been revoked is never purged from other pending requests. This maps to "a multisig request executed below threshold," moving NEAR (or granting a full-access key) without the intended quorum — a direct custody-binding violation with concrete NEAR loss potential.

### Likelihood Explanation
Requires: (1) a request created by member B, (2) confirmed early by member/key A while A was still valid, (3) A's key/member entry later removed via a legitimate `DeleteKey`/`DeleteMember` request (e.g. routine key rotation or offboarding), and (4) the original request from B remaining pending in `self.requests` at that time. Given multisig setups commonly used for treasury/ops accounts with periodic key rotation, and no automatic expiry or re-validation of stale confirmations (`REQUEST_COOLDOWN` only guards deletion timing, not confirmation validity), this is a realistic operational sequence rather than a contrived edge case.

### Recommendation
On any `DeleteKey`/`DeleteMember` execution, scan `self.confirmations` for **all** requests (not only those the removed key/member itself submitted) and strip the removed key/member's entry from each `HashSet`. Alternatively, re-validate at `confirm()`/execution time that every public key in the stored confirmation set is still a member/live key before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig` with 3 members (A, B, C) and `num_confirmations = 2`.
2. B calls `add_request` to create a `Transfer` request `X` (1 confirmation needed to reach threshold).
3. A calls `confirm(X)` → `confirmations[X] = {A}` (1 of 2, not yet executed).
4. Organization rotates out A: submits and confirms a `DeleteKey{public_key: A}` request (this request is unrelated to `X`; A did not create `X`, so the `DeleteKey` cleanup loop in `execute_request` does not touch `confirmations[X]`, per the `r.signer_pk == pk` filter at `multisig/src/lib.rs:198-216`).
5. A's key is now removed from the account (`promise.delete_key(pk)` executes), yet `confirmations[X]` still equals `{A}`.
6. C, believing 2 live approvals are required, calls `confirm(X)`. `confirmations.len() + 1 = 2 >= num_confirmations(2)` → the stale entry from removed A plus C's live confirmation triggers `execute_request(X)`, transferring funds — despite only **one** currently-valid member (C) having actually approved it at execution time.

        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
