### Title
`ProvisionerV2._solveRequestsVault` reverts entirely on async deposits for tokens that revert on zero-value approvals - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`_solveRequestsVault` calls `token.forceApprove(MULTI_DEPOSITOR_VAULT, type(uint256).max)` before processing deposit requests and `token.forceApprove(MULTI_DEPOSITOR_VAULT, 0)` afterward to reset the allowance [1](#0-0) . `SafeERC20.forceApprove` still ultimately performs a direct, non-tolerant `approve(spender, 0)` call if the initial optimistic call to set that value fails, so for a token that reverts on a zero-value approval, the reset call at the end of `_solveRequestsVault` will revert and unwind the whole solve transaction [2](#0-1) . This mirrors the reported analog from `VaultE4626.commit`, which suffers the identical root cause (`forceApprove(..., 0)` on a token that reverts on zero-value approvals).

### Finding Description
`_solveRequestsVault(IERC20 token, RequestV2[] calldata requests)` is the internal routine that solves async deposit/redeem requests registered via `requestDeposit`/`requestRedeem` (any ordinary user can call `requestDeposit` through the `anyoneButVault` modifier) [3](#0-2) . When at least one deposit request exists in the batch, the function grants the vault an unlimited allowance via `forceApprove(MULTI_DEPOSITOR_VAULT, type(uint256).max)`, then, after the loop finishes, resets the allowance with `token.forceApprove(MULTI_DEPOSITOR_VAULT, 0)` [4](#0-3) .

`SafeERC20.forceApprove` first attempts an optimistic `approve(spender, value)` call via `_callOptionalReturnBool`, which suppresses reverts and returns `false` on failure. If that optimistic call fails, `forceApprove` falls back to explicitly calling `approve(spender, 0)` and then `approve(spender, value)` again — both through `_callOptionalReturn`, which does **not** suppress reverts and will bubble up any revert reason [2](#0-1) [5](#0-4) . For a token that unconditionally reverts on a zero-value `approve` call (e.g. BNB, per the weird-erc20 "Revert on Zero Value Approvals" list cited in the analog report), the very first optimistic `approve(spender, 0)` call fails, and the subsequent explicit `approve(spender, 0)` in the fallback branch also reverts — this time without being caught — causing the whole `forceApprove(..., 0)` call, and therefore `_solveRequestsVault`, to revert.

Because this reset happens unconditionally at the end of the function whenever `depositsExist` was true, **any** solve call that includes at least one deposit request for such a token will always revert, permanently blocking the solving of async deposits (and any redeems bundled in the same batch) for that token.

### Impact Explanation
If any registered deposit token reverts on zero-value approvals, async deposit requests for that token registered through `requestDeposit` can never be solved via `solveRequestsVault`/`_solveRequestsVault`, since the mandatory allowance-reset step at the end of the function always reverts. Users' deposited tokens remain locked in the `ProvisionerV2` contract (already pulled in via `safeTransferFrom` at request time) with no way to complete the deposit, and their minted vault units are never issued. This is a freezing-of-funds scenario for any user who deposits such a token, matching the "Vaults won't work with tokens that revert on a 0 value approval" pattern from the referenced report, only now located in the `ProvisionerV2` async solve path rather than `VaultE4626.commit`.

### Likelihood Explanation
The trigger requires only that a project operator lists a token with the "revert on zero-value approval" trait (e.g., BNB) as a supported deposit token in `tokensDetails`, and that at least one ordinary user calls `requestDeposit` for that token. Both conditions are ordinary, expected usage flows — no privileged/guardian/solver misbehavior is needed beyond the solver simply calling the normal `solveRequestsVault` entry point, which then unconditionally reverts. This is exactly analogous in mechanism and severity to the referenced M-14 report, which the Sherlock/Ammplify team acknowledged but chose not to fix, since it depends entirely on which specific weird-ERC20 tokens the deploying protocol chooses to onboard.

### Recommendation
Avoid resetting the allowance to exactly `0` for tokens with this trait — e.g., only reduce the allowance to the amount actually consumed by the vault (mirroring the deposited amount) rather than always resetting to `0`, or track/allow a persistent non-zero "leftover" approval instead of forcing it back to zero after each solve.

### Proof of Concept
1. Deploy a mock ERC20 whose `approve` function reverts when `value == 0` (mirroring BNB's behavior).
2. Register this mock token in `ProvisionerV2.tokensDetails` with `asyncDepositEnabled = true`.
3. As an ordinary user, call `requestDeposit(mockToken, tokensIn, minUnitsOut, ...)`; tokens are pulled into the provisioner and the deposit hash is recorded.
4. As the solver, call `solveRequestsVault(mockToken, [request])`, which internally invokes `_solveRequestsVault`.
5. Assert the transaction reverts at `token.forceApprove(MULTI_DEPOSITOR_VAULT, 0)` (line 936), confirming the deposit can never be solved and the user's tokens remain stuck in the `ProvisionerV2` contract.

    function forceApprove(IERC20 token, address spender, uint256 value) internal {
        bytes memory approvalCall = abi.encodeWithSelector(token.approve.selector, spender, value);

        if (!_callOptionalReturnBool(token, approvalCall)) {
            _callOptionalReturn(token, abi.encodeWithSelector(token.approve.selector, spender, 0));
            _callOptionalReturn(token, approvalCall);
        }
    }

    function _callOptionalReturn(IERC20 token, bytes memory data) private {
        // We need to perform a low level call here, to bypass Solidity's return data size checking mechanism, since
        // we're implementing it ourselves. We use {Address-functionCall} to perform this call, which verifies that
        // the target address contains contract code and also asserts for success in the low-level call.

        bytes memory returndata = address(token).functionCall(data, "SafeERC20: low-level call failed");
        require(returndata.length == 0 || abi.decode(returndata, (bool)), "SafeERC20: ERC20 operation did not succeed");
    }

    /**
     * @dev Imitates a Solidity high-level call (i.e. a regular function call to a contract), relaxing the requirement
     * on the return value: the return value is optional (but if data is returned, it must not be false).
     * @param token The token targeted by the call.
     * @param data The call data (encoded using abi.encode or one of its variants).
     *
     * This is a variant of {_callOptionalReturn} that silents catches all reverts and returns a bool instead.
     */
    function _callOptionalReturnBool(IERC20 token, bytes memory data) private returns (bool) {
        // We need to perform a low level call here, to bypass Solidity's return data size checking mechanism, since
        // we're implementing it ourselves. We cannot use {Address-functionCall} here since this should return false
        // and not revert is the subcall reverts.

        (bool success, bytes memory returndata) = address(token).call(data);
        return
            success && (returndata.length == 0 || abi.decode(returndata, (bool))) && Address.isContract(address(token));
    }
