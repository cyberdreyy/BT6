<title>Duplicate builder pubkey causes deposit top-up to be misrouted to a stale, exited builder slot - (File: specs/gloas/beacon-chain.md)</title>

### Summary
`process_builder_deposit_request` in `specs/gloas/beacon-chain.md` locates the target builder by scanning `state.builders` for a matching `pubkey` and taking the **first** index found. The spec's own note acknowledges that builder indices are reusable and that "a newly registered builder's public key may have previously appeared in the builder set" [1](#0-0) . This mirrors the `InsuranceFund#syncDeps()` pattern: a dependency (here, "which builder slot owns this pubkey") can change out from under an in-flight, unprivileged action (a deposit top-up), causing Gwei to be credited to the wrong, stale entry.

### Finding Description
`process_builder_deposit_request` resolves the target builder purely by pubkey lookup: [2](#0-1) 

`builder_pubkeys.index(request.pubkey)` returns the index of the **first** occurrence of that pubkey in `state.builders`. Because exited builder slots are only overwritten lazily — `get_index_for_new_builder` returns the first index whose `withdrawable_epoch <= current_epoch and balance == 0`, and re-registration reuses that slot via `set_or_append_list` [3](#0-2)  — it is possible for a builder that has fully exited and been swept (its stale entry retains `pubkey`, `withdrawable_epoch != FAR_FUTURE_EPOCH`, `balance == 0`) to be re-registered as a *new* builder at a **different**, later index if an intervening builder occupies the freed slot first. The old stale entry (at the earlier index, still carrying the original `pubkey` and the **old** `execution_address`) is left in the registry until physically overwritten.

Once this duplicate-pubkey state exists, any subsequent top-up deposit for that pubkey resolves to the **first** (stale, exited) index rather than the new active registration. The code's own top-up branch even resurrects it:

```
if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
    epoch = get_current_epoch(state)
    builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY
builder.balance += request.amount
``` [4](#0-3) 

This silently "reactivates" the stale index's `withdrawable_epoch` and credits it with the deposit, while the deposit note explicitly documents this exact hazard: "Any deposit sent to an exited builder will be withdrawn to the builder's execution address," which is the **old** `execution_address` from before the exit, not the address the builder intended when re-registering with new withdrawal credentials [5](#0-4) .

This is structurally identical to `InsuranceFund#syncDeps()`: a governance-free, purely sequence-dependent state change (registry slot reassignment) races with a normal user action (a deposit/top-up), and the outcome (destination address for funds) silently changes between when the actor formed intent and when the deposit is actually applied — no malicious peer, coalition, or client bug is required, only ordinary chain progression (exit → sweep → re-registration → top-up).

### Impact Explanation
Gwei deposited via a builder-deposit top-up can end up credited to, and eventually withdrawn to, an **execution address that is not the one the depositor intended**, because the withdrawal path (`process_withdrawals`/builder sweep) pays out using `state.builders[builder_index].execution_address` at that stale index rather than the actively-used registration [6](#0-5) . This is a Gwei-paid-to-a-non-owner class impact: funds committed by a builder can be redirected to an execution address the builder no longer controls or intended for that deposit.

### Likelihood Explanation
This requires no coalition or malicious peer — only the sequence: builder fully exits and is swept (balance 0, `withdrawable_epoch` in the past) → a different builder deposit fills the freed slot before the original pubkey's holder re-registers → the original pubkey re-registers into a new slot at a later index with new withdrawal credentials → the holder (or anyone, since deposit requests only need the pubkey) sends a top-up. Registry churn combined with normal builder lifecycle events (exit/re-entry) makes this reachable through purely spec-permitted sequences; the spec authors explicitly called out that duplicate pubkeys across slots is an expected occurrence, indicating the code path is real and known but not defended in `process_builder_deposit_request`.

### Recommendation
Instead of matching on the first pubkey occurrence, either enforce a global invariant that a pubkey can only be *active* (non-exited) in a single index at a time and reject/redirect registrations that would create such a duplicate, or have `process_builder_deposit_request` search for the *active* (non-exited) entry for that pubkey specifically rather than `builder_pubkeys.index(...)`'s first match, e.g., prefer an entry with `withdrawable_epoch == FAR_FUTURE_EPOCH` when one exists, falling back to the deposit-creates-new-entry path otherwise.

### Proof of Concept
1. Builder B registers with pubkey `P` and `execution_address = A1` at index `i` via `process_builder_deposit_request` (new-registration branch) [7](#0-6) .
2. B fully exits (`process_builder_exit_request` → `initiate_builder_exit`), and the withdrawal sweep pays out the balance to `A1`, leaving `state.builders[i]` with `balance == 0` and `withdrawable_epoch` set to a past epoch.
3. Some other builder deposit occupies index `i` is avoided (or another builder fills a lower free index first), so when B re-registers with pubkey `P` and a **new** `execution_address = A2`, `get_index_for_new_builder` returns a different index `j > i` because index `i`'s reuse eligibility check happened to be raced by another registration, or B intentionally waits and another actor's deposit fills `i` with a distinct builder first (spec explicitly allows lazy slot reuse ordering) [8](#0-7) .
4. Now `state.builders` contains two entries with `pubkey = P`: stale entry at `i` (`execution_address = A1`, exited) and active entry at `j` (`execution_address = A2`).
5. Anyone submits a top-up `BuilderDepositRequest` with `pubkey = P`. `process_builder_deposit_request` computes `builder_pubkeys.index(P) == i` (first match), and the deposit is credited to the stale, exited slot `i`, reactivating its `withdrawable_epoch` and crediting funds that will ultimately sweep out to `A1`, not the builder's currently intended `A2` [9](#0-8) .

def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))

def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:
    # Ignore deposits with unexpected withdrawal credential prefixes
    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
        return

    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        if is_valid_builder_deposit_signature(request):
            add_builder_to_registry(
                state,
                request.pubkey,
                PAYLOAD_BUILDER_VERSION,
                ExecutionAddress(request.withdrawal_credentials[12:]),
                request.amount,
                state.slot,
            )
    else:
        builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
        builder = state.builders[builder_index]

        # If exited and swept, reset the withdrawable epoch
        if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
            epoch = get_current_epoch(state)
            builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY

        # Increase balance by deposit amount
        builder.balance += request.amount
