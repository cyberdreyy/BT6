Confirmed: `_cancel` in `EscrowSrc.sol` refunds the maker's tokens back to the maker themselves, and `cancel()`/`publicCancel()` are gated only by `TimelocksLib.Stage.SrcCancellation`/`SrcPublicCancellation` timestamps with no cross-check against `SrcWithdrawal`/`SrcPublicWithdrawal`.

### Title
Missing validation of timelock stage ordering allows a malicious maker to reclaim source escrow funds while also keeping the destination payout - (File: contracts/BaseEscrowFactory.sol, contracts/libraries/TimelocksLib.sol)

### Summary
`TimelocksLib` stores seven independent `uint32` offsets (`SrcWithdrawal`, `SrcPublicWithdrawal`, `SrcCancellation`, `SrcPublicCancellation`, `DstWithdrawal`, `DstPublicWithdrawal`, `DstCancellation`) packed into a single `Timelocks` value [1](#0-0) . These offsets are supplied by the order maker as part of the order's `extraData`/extension and are decoded verbatim in `_postInteraction`, only having `setDeployedAt` applied — no ordering is enforced between the stages [2](#0-1) .

### Finding Description
The escrow's `withdraw`/`publicWithdraw`/`cancel`/`publicCancel` functions on `EscrowSrc.sol` simply gate on `onlyAfter`/`onlyBefore` against the raw stage values with no invariant that `SrcWithdrawal < SrcPublicWithdrawal < SrcCancellation < SrcPublicCancellation` [3](#0-2) [4](#0-3) . This is analogous to the reported `UpDown.startGame` bug, where `endTime`/`stopPredictAt` ordering was never checked: here `SrcWithdrawal`/`SrcCancellation` ordering is never checked either.

A malicious maker can craft an order whose embedded `extraDataArgs.timelocks` set `SrcCancellation` (and even `SrcPublicCancellation`) to occur immediately after deployment/finality — i.e., before or at the same time as `SrcWithdrawal`. Because `cancel()` is `onlyCaller(taker)` and `_cancel` refunds the maker's original tokens back to the maker [5](#0-4) [6](#0-5) , and `publicCancel()` (reachable by any access-token holder, i.e., effectively public once `SrcPublicCancellation` is reached) also refunds to the maker [7](#0-6) , once the withdrawal window is closed the taker/resolver loses the ability to withdraw the maker's src-chain tokens and only cancellation remains available — sending those tokens back to the very maker who set up the malicious timelocks.

Meanwhile the maker still reveals the secret to withdraw their own funds from the resolver-funded `EscrowDst` (guarded independently by `DstWithdrawal`/`DstCancellation`, which are unrelated fields and unaffected by the src side manipulation) [8](#0-7) . Because `createDstEscrow` only checks `DstCancellation <= srcCancellationTimestamp` [9](#0-8)  — a completely different, unrelated guard — nothing prevents the src-side `SrcWithdrawal`/`SrcCancellation` stages from being ordered adversarially. The net effect: the maker collects the destination tokens from `EscrowDst` (funded by the resolver) and also reclaims their own source tokens via cancellation, at the resolver's expense.

### Impact Explanation
This is a temporary/permanent freezing and effectively theft of the resolver's expected consideration during the live swap lifecycle: the resolver funds the destination escrow expecting to redeem the maker's source tokens via `withdraw`/`publicWithdraw`, but a maker-controlled malformed timelock ordering can close that window before it is usable and route the source funds back to the maker via `cancel`/`publicCancel`. This matches the bounty's High-severity criteria ("theft or permanent loss of unclaimed fee-like value, or temporary freezing of funds during the live swap lifecycle").

### Likelihood Explanation
The `extraDataArgs.timelocks` field is fully attacker-controlled by the order maker at order-creation time and is used unchanged (aside from `setDeployedAt`) in the deployed escrow's stage checks [10](#0-9) . No on-chain validation anywhere in `BaseEscrowFactory.sol`, `TimelocksLib.sol`, `EscrowSrc.sol`, or `EscrowDst.sol` enforces monotonic ordering between `SrcWithdrawal < SrcPublicWithdrawal < SrcCancellation < SrcPublicCancellation` (nor the analogous `Dst` ordering). Exploitation requires only that a resolver fill such a maliciously-parameterized order without independently validating timelock ordering off-chain — plausible in an automated resolver/relayer pipeline that trusts on-chain enforcement to catch malformed orders, similar to how the original `UpDown.startGame` bug relied on the admin to manually order `endTime`/`stopPredictAt` correctly.

### Recommendation
Add an explicit ordering check (analogous to the recommended `require(stopPredictAt < endTime)` fix) in `_postInteraction` and `createDstEscrow`, e.g.:
```solidity
require(
    timelocks.get(Stage.SrcWithdrawal) < timelocks.get(Stage.SrcPublicWithdrawal) &&
    timelocks.get(Stage.SrcPublicWithdrawal) < timelocks.get(Stage.SrcCancellation) &&
    timelocks.get(Stage.SrcCancellation) < timelocks.get(Stage.SrcPublicCancellation),
    "InvalidTimelockOrder"
);
```
and similarly for the `Dst` stages, so a malformed/malicious timelock ordering is rejected before an escrow is ever funded.

### Proof of Concept
1. A malicious maker constructs an order with `extraDataArgs.timelocks` such that `SrcWithdrawal = 1000`, but `SrcCancellation = 10` (i.e., `SrcCancellation` occurs before `SrcWithdrawal`), and normal-looking `Dst*` values.
2. A resolver fills the order via the Limit Order Protocol; `_postInteraction` deploys `EscrowSrc` with these timelocks unmodified aside from `setDeployedAt` [11](#0-10) .
3. The resolver also calls `createDstEscrow`, funding the destination side for the maker [12](#0-11) .
4. Time passes finality; at `t = 10` the src escrow enters the `SrcCancellation` window while still before `SrcWithdrawal` (t=1000) is reached, so the resolver's `withdraw`/`publicWithdraw` calls (`onlyAfter(SrcWithdrawal)`) revert with `InvalidTime`, while the maker (as `immutables.taker` is actually the resolver — but crucially `cancel()`/`publicCancel()` refund to `immutables.maker`) can wait for `SrcPublicCancellation` and invoke `publicCancel()` (any access-token holder, including a colluding party) to route the source tokens back to the maker.
5. Independently, the maker reveals the secret on `EscrowDst` to withdraw the resolver-funded destination tokens (governed by unrelated `Dst*` timelocks) [8](#0-7) .
6. Net result: the maker receives both the destination tokens and their original source tokens back, while the resolver is left with neither — a full loss of the resolver's provided liquidity.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
