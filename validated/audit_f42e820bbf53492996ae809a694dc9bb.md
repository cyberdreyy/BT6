### Title
Optimistic internal stake-share accounting is never rolled back when the validator `Stake` action fails, letting delegators redeem shares against NEAR that was never actually staked/locked - (File: `staking-pool/src/internal.rs`)

### Summary
`internal_stake` in `staking-pool/src/internal.rs` credits `account.stake_shares`, `total_stake_shares`, and `total_staked_balance` synchronously, before the actual `Stake` action promise (fired asynchronously via `internal_restake`) is known to succeed. If that `Stake` action fails (e.g. the requested `total_staked_balance` is below the protocol's minimum validator stake threshold, or the public key becomes invalid), the only recovery path, `on_stake_action`, does not revert the optimistic share/balance bookkeeping — it just re-issues `stake(0)` to release the lock. This is the same class of bug as the reported `AlgebraEternalFarming` issue: an internal ledger (recorded shares / farming position) is updated as if an external, possibly-reverting call succeeded, and the failure-handling path does not resynchronize the internal state with the real external state (validator's actual locked balance).

### Finding Description
`staking-pool/src/lib.rs::stake`/`deposit_and_stake`/`stake_all` call `internal_stake(amount)` [1](#0-0) , which synchronously does:
```
account.stake_shares += num_shares;
...
self.total_staked_balance += stake_amount;
self.total_stake_shares += num_shares;
``` [2](#0-1) 

Right after, `internal_restake()` is called, which fires an actual native `Stake` action against `total_staked_balance` as an asynchronous `Promise`, with `on_stake_action` attached as a callback: [3](#0-2) 

The callback comment itself acknowledges the risk:
> "In case the stake amount is less than the minimum staking threshold, the staking action fails, and the stake amount is not changed. This might lead to inconsistent state and the follow withdraw calls might fail. To mitigate this, the contract will issue a new unstaking action in case of the failure of the first staking action." [4](#0-3) 

And indeed, `on_stake_action` only checks success and, on failure, re-stakes `0` to release the lock — it never decrements `total_staked_balance`, `total_stake_shares`, or any account's `stake_shares` that were already credited by `internal_stake`: [5](#0-4) 

The binding that should hold is:
`total_staked_balance` (and the sum of all `account.stake_shares` priced at the share ratio) == the NEAR actually locked at the validator (`env::account_locked_balance()`).

Before the failed `Stake` call: `total_staked_balance = X`, `account_locked_balance() = X` (assuming prior consistency).
After `internal_stake` credits the new deposit and the subsequent `Stake` action promise fails: `total_staked_balance = X + Δ`, but `account_locked_balance()` never increased (the runtime rejected the stake), so `account_locked_balance() = X`. The equality is broken: internal claims (`total_staked_balance`/shares) now exceed the tokens actually locked with the validator by `Δ`.

Because `unstake`/`withdraw` are driven purely from `total_staked_balance`/`stake_shares`/`unstaked` (no cross-check against `account_locked_balance()`), a delegator whose stake action failed can still `unstake` their phantom shares (converted back to `unstaked` balance) and then `withdraw`, pulling real NEAR out of the pool's liquid balance that was never actually staked with the validator - i.e., redeeming a claim that was never backed. Multiple such desyncs (e.g., via repeated deposit/stake attempts crafted to fall below the minimum stake threshold, or racing key rotation via `update_staking_key`) can drain the pool's liquid balance disproportionately relative to actual stake, at the expense of other delegators whose withdrawals will subsequently fail or be underfunded.

### Impact Explanation
This is a High-severity accounting-divergence issue matching the rules' "High" bucket: an accounting value (`total_staked_balance`/`stake_shares`) diverges from reality (`account_locked_balance()`), and other parties (co-delegators, the pool owner) settle on the incorrect internal ledger when computing withdrawable/staked balances. In the worst case it degrades to insolvency of the pool's liquid balance versus recorded stake-share claims, which is Critical-adjacent ("claims exceeding assets held").

### Likelihood Explanation
Triggering a failed native `Stake` action requires hitting NEAR's minimum validator stake threshold or an invalid staking key — conditions that are plausible near the threshold boundary (e.g., a delegator staking a very small amount when the pool's total is already near the minimum, or a staking-key rotation via `update_staking_key` racing with a `stake` call). This does not require the foundation, owner, or any privileged party — any account calling `stake`/`deposit_and_stake` when the resulting total lands below the minimum stake threshold can trigger the desync unprivileged. No malicious validator or RPC interception is needed; only the intrinsic behavior of NEAR's staking runtime.

### Recommendation
In `on_stake_action` (`staking-pool/src/lib.rs`), on stake-action failure, roll back the optimistic accounting performed in `internal_stake` for the corresponding call (or, more robustly, resynchronize `total_staked_balance`/`total_stake_shares` and the specific account's `stake_shares` against `env::account_locked_balance()` after the callback resolves), rather than only reissuing a `stake(0)`. Since `on_stake_action` currently has no context about which account/amount triggered the failed restake (it's a general "restake" callback shared across all actions), consider tracking pending stake deltas and reverting them precisely when the corresponding `Stake` promise fails.

### Proof of Concept
1. Pool has `total_staked_balance = X` NEAR already locked and validating, close to (but above) the network's minimum validator stake amount is not required — instead, exploit the boundary case: get `total_staked_balance` to be just at/below the minimum stake threshold so a subsequent `Stake` promise for `total_staked_balance` fails (e.g., after a large `unstake_all` by other delegators reduces `total_staked_balance` near/below the threshold, or by initial small-pool bootstrapping).
2. Attacker calls `deposit_and_stake(amount)` (or `deposit` then `stake(amount)`), which:
   - `internal_deposit` credits `account.unstaked`.
   - `internal_stake(amount)` synchronously credits `account.stake_shares += num_shares`, `total_staked_balance += stake_amount`, `total_stake_shares += num_shares` [2](#0-1) .
   - `internal_restake()` fires `Promise::new(...).stake(total_staked_balance, ...)`, which the NEAR runtime rejects (below minimum threshold), triggering `on_stake_action` with `PromiseResult::Failed`.
3. `on_stake_action` sees failure and merely issues `stake(0)` to fully release the lock; it does not undo the share/balance credit from step 2 [5](#0-4) .
4. Attacker now calls `unstake(amount)` and, after the unbonding period, `withdraw`, receiving NEAR out of the pool's liquid balance corresponding to shares that were never actually staked with the validator — extracting value with no corresponding lock ever having existed, at the expense of the pool's remaining delegators' withdrawable balance.

Note: I was unable to fully verify the exact minimum-stake-threshold condition enforced by the underlying NEAR runtime/`near-sdk` version pinned in this repo (this is outside the indexed contract code), so the precise numeric trigger for step 1/2 could not be confirmed from the repository alone; the accounting-desync logic itself, however, is fully verifiable in `staking-pool/src/internal.rs` and `staking-pool/src/lib.rs` as cited above.

    pub fn on_stake_action(&mut self) {
        assert_eq!(
            env::current_account_id(),
            env::predecessor_account_id(),
            "Can be called only as a callback"
        );

        assert_eq!(
            env::promise_results_count(),
            1,
            "Contract expected a result on the callback"
        );
        let stake_action_succeeded = match env::promise_result(0) {
            PromiseResult::Successful(_) => true,
            _ => false,
        };

        // If the stake action failed and the current locked amount is positive, then the contract
        // has to unstake.
        if !stake_action_succeeded && env::account_locked_balance() > 0 {
            Promise::new(env::current_account_id()).stake(0, self.stake_public_key.clone());
        }
    }

    pub(crate) fn internal_restake(&mut self) {
        if self.paused {
            return;
        }
        // Stakes with the staking public key. If the public key is invalid the entire function
        // call will be rolled back.
        Promise::new(env::current_account_id())
            .stake(self.total_staked_balance, self.stake_public_key.clone())
            .then(ext_self::on_stake_action(
                &env::current_account_id(),
                NO_DEPOSIT,
                ON_STAKE_ACTION_GAS,
            ));
    }
