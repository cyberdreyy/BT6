## Analog Found: Unchecked mint-account owner leads to wrong token-balance data returned to RPC callers

### Title
Unvalidated mint address allows spoofed decimals in `getTokenAccountBalance`/token RPC responses - (File: `rpc/src/parsed_token_accounts.rs`)

### Summary
The external report flags `VestingSplitter.sol` accepting an arbitrary "vesting contract" address with no check that it is actually a legitimate vesting contract, letting the caller redirect the contract into treating attacker data as trusted data. The same class of bug — accepting a pubkey and treating whatever it points to as trusted, "known-type" data without checking its owning program — exists in agave's SPL-token RPC decoding path: `get_mint_owner_and_additional_data` fetches the account referenced by a token account's `mint` field and unconditionally unpacks it as an SPL `Mint`, without first checking that the account's owner is actually `spl_token`/`spl_token_2022`.

### Finding Description
`get_mint_owner_and_additional_data` in `rpc/src/parsed_token_accounts.rs` loads the account at the caller/attacker-influenced `mint` pubkey and immediately unpacks it as a `Mint` via `get_additional_mint_data`, without verifying `mint_account.owner()`: [1](#0-0) [2](#0-1) 

By contrast, the closely related `get_token_supply` handler explicitly validates that the account owner is a known SPL token program before unpacking as a `Mint`: [3](#0-2) 

`get_token_account_balance` calls the unchecked helper directly: [4](#0-3) 

The `mint` field inside an SPL token account is arbitrary user-supplied data at account-creation time — the token program does not enforce at the consensus level that it points to an actual initialized `Mint` account owned by the token program. An attacker can therefore create a normal (owner-checked) SPL token account whose `mint` field points to any other account they control (e.g., an account owned by an arbitrary program, or even a `Mint`-shaped account under the token program that was never truly initialized as the "real" mint for that token), as long as the bytes at that address happen to satisfy `StateWithExtensions::<Mint>::unpack`. `get_mint_owner_and_additional_data` will happily accept those bytes as authoritative decimals/interest-bearing/scaled-UI-amount configuration.

The same unchecked helper is also reached from `get_parsed_token_accounts` (used by `getTokenAccountsByOwner`/`getProgramAccounts` with `jsonParsed` encoding) and `get_token_largest_accounts`: [5](#0-4) 

### Impact Explanation
This is reachable purely via a single unprivileged JSON-RPC call (`getTokenAccountBalance`, `getTokenAccountsByOwner` with `jsonParsed`, or `getTokenLargestAccounts`) against accounts an attacker fully controls (their own token account referencing an arbitrary "mint"-shaped account). The validator will return incorrect `decimals`/`uiAmount`/`uiAmountString` for that token, i.e., wrong account-derived data returned from a read-only query — matching the "wrong-slot/fork/account data returned" acceptance criterion. This can mislead any client (wallets, explorers, bots) that trusts the RPC-reported UI amount for that specific attacker-crafted account/mint pair.

### Likelihood Explanation
High: the attacker needs only to create two ordinary accounts (a token account and a mint-shaped account) and query a single RPC method once — no special privileges, no interaction with consensus, and no more than one call.

### Recommendation
In `get_mint_owner_and_additional_data` (and anywhere else a `mint` pubkey extracted from token-account data is dereferenced), validate `mint_account.owner()` against `is_known_spl_token_id` (as already done in `get_token_supply`) before treating the account's bytes as an authoritative `Mint`, and return `Error::invalid_params` otherwise.

### Proof of Concept
1. Create account `A` with arbitrary bytes that satisfy `StateWithExtensions::<Mint>::unpack` (e.g., set `decimals = 0`), owned by any program (does not need to be the token program).
2. Create a normal SPL token account `B` owned by `spl_token`/`spl_token_2022`, with its `mint` field set to `A`'s pubkey and `amount` set to a large integer.
3. Call `getTokenAccountBalance` (or `getTokenAccountsByOwner` with `encoding: jsonParsed`) for account `B`.
4. Observe the RPC response uses `A`'s attacker-chosen `decimals` (e.g., 0) to compute `uiAmount`, producing a misleading/incorrect balance for account `B` despite `A` never being validated as a real mint owned by the token program. [1](#0-0)

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}
