### Title
Builder payment quorum gate can be bypassed after a 2+ epoch settlement delay, causing a builder to be paid without meeting the PTC weight quorum - (File: `specs/gloas/beacon-chain.md`)

### Summary
`apply_parent_execution_payload` settles a builder's pending payment differently depending on how many epochs have elapsed since the parent block's slot. When settlement happens within the current or previous epoch, the quorum-gated path `settle_builder_payment` is used, honoring the invariant that a builder is only paid if PTC/attester weight reaches `get_builder_payment_quorum_threshold`. When settlement is delayed by 2+ epochs, the code instead unconditionally appends a withdrawal for `parent_bid.value`, bypassing the quorum check entirely — even though the same payment entry was already evaluated (and possibly discarded for failing quorum) by the ordinary epoch-boundary path `process_builder_pending_payments`.

### Finding Description
`process_builder_pending_payments` runs every epoch transition (via `process_epoch`, itself invoked by `process_slots` regardless of whether any block is produced), and enforces the payment gate: [1](#0-0) 

A pending payment recorded at slot `N` (in `builder_pending_payments[SLOTS_PER_EPOCH + N % SLOTS_PER_EPOCH]`) is rotated into the "previous epoch" half of the array at the next epoch boundary, then quorum-checked and evicted (converted into a withdrawal only `if payment.weight >= quorum`, otherwise silently dropped) at the epoch boundary after that — i.e., exactly two epoch transitions after slot `N`, independent of whether any subsequent block has referenced block `N` as its parent.

Separately, `apply_parent_execution_payload` (called once, when a later block finally processes block `N` as its parent) computes: [2](#0-1) 

If `parent_epoch` (the epoch of block `N`) is neither the current nor the previous epoch — i.e., 2+ epochs have already passed — the code takes the `elif parent_bid.value > 0` branch and appends a `BuilderPendingWithdrawal` built directly from `parent_bid`, with **no reference to, or check of, `payment.weight` / quorum at all**.

Because `process_epoch` (and thus the quorum-checking rotation/eviction in `process_builder_pending_payments`) always runs when the state slot crosses an epoch boundary — even through long stretches with no blocks — the quorum verdict for slot `N`'s payment is already resolved (paid if `weight >= quorum`, discarded otherwise) strictly before the eventual block that references `N` as parent is processed. The `elif` branch in `apply_parent_execution_payload` then re-derives a payment for the *same* commitment straight from `parent_bid`, without consulting that verdict.

`settle_builder_payment` itself shows the correct, quorum-independent-but-controlled pattern used elsewhere for the two "recent" cases: [3](#0-2) 

but the "old parent" branch does not call it, nor consult `state.builder_pending_payments` at all, and instead reconstructs the withdrawal purely from `state.latest_execution_payload_bid` (line 1733, `parent_bid = state.latest_execution_payload_bid`), which still holds `value` regardless of what happened to the corresponding payment entry.

This is structurally analogous to the reported `ConvexStakingWrapper._calcRewardIntegral` bug: a value that should be derived once from a single, consistently-updated piece of state (`reward.remaining` / here, `builder_pending_payments[i].weight` and its quorum verdict) is instead re-derived from a second, independently-updated source (`balanceOf` / here, `latest_execution_payload_bid.value`) that is not kept in sync with the first, so the same economic event can be paid out through two different code paths under different timing conditions.

### Impact Explanation
This breaks the "builder payment... escaped" invariant described as High severity in the analog-bug taxonomy: a builder is paid the full committed `parent_bid.value` even though the PTC/attester weight quorum required by `process_builder_pending_payments` was never met for that same payment entry (which, in the delayed-settlement scenario, will have `weight == 0` since no blocks/attestations could be processed while block `N` remained un-built-upon). The quorum mechanism exists specifically to withhold builder payment unless enough attesters vouch that the payload was timely; the `elif` fallback silently defeats this protection whenever settlement of a parent is delayed by 2+ epochs, converting an unconfirmed payment into a paid one. In the case where weight *did* reach quorum via attestations processed on blocks not directly citing `N` as parent, this can also produce a double payment (one via `process_builder_pending_payments`, one via the `elif` branch), since both paths construct a withdrawal from the same underlying commitment without any shared "already paid" marker.

### Likelihood Explanation
Triggering the bypass only requires that a proposer eventually build a block whose immediate parent is 2+ epochs old — i.e., that block `N` was not referenced as an immediate parent for two full epoch boundaries. This is the exact scenario the code's own comments and test (`test_builder_payment_after_missed_epochs`) describe as a deliberately handled case, so it is a realistic condition (extended periods without blocks/finality), not a contrived edge case. It does not require BLS/EL bugs; it is purely a consequence of the spec's own state-transition ordering (`process_epoch` running independently of `process_parent_execution_payload`). It is somewhat rate-limited by the fact that a validator cannot unilaterally force 2+ epochs of missed slots, but no coalition or protocol violation is needed for the condition to occur — a normal network degradation (temporary loss of majority participation) suffices, and any observer builder with a pending value bid on the stalled head benefits automatically once the chain resumes.

### Recommendation
Make the "old parent" branch of `apply_parent_execution_payload` consistent with `settle_builder_payment`/`process_builder_pending_payments`: either (a) never let a payment entry be evicted from `builder_pending_payments` without appending its (possibly-empty) withdrawal decision at the same logical point consulted by `apply_parent_execution_payload`, e.g., by tracking whether payment_index for slot `N` has already been resolved, or (b) require the `elif` branch to reconstruct and check weight/quorum from the archived payment record (if retained) rather than unconditionally trusting `parent_bid.value`. In general, a single authoritative code path should decide whether a given builder commitment is paid, and it should be impossible for both `process_builder_pending_payments` and `apply_parent_execution_payload` to independently produce a withdrawal (or a discard vs. a payment) for the same commitment.

### Proof of Concept
1. A builder submits a bid with `value = V > 0` for block at slot `N`; the bid is committed via `process_execution_payload_bid`, recording `state.builder_pending_payments[SLOTS_PER_EPOCH + N % SLOTS_PER_EPOCH] = BuilderPendingPayment(weight=0, withdrawal=BuilderPendingWithdrawal(fee_recipient, V, builder_index))`.
2. No further blocks are produced for 2+ full epochs (chain stall / low participation) — block `N` remains `state.latest_block_header`.
3. As slots advance through the epoch boundaries (via `process_slots`/`process_epoch`), `process_builder_pending_payments` runs at each boundary. Because no attestations were ever processed for slot `N` (no blocks existed to include them), `weight` stays `0`. At the second boundary after `N`, the entry is evicted with `weight (0) < quorum`, so **no** withdrawal is appended, and `state.builder_pending_payments[...] = BuilderPendingPayment.empty()`.
4. Eventually a proposer builds the next block, whose parent is still block `N` (2+ epochs old). `process_parent_execution_payload` → `apply_parent_execution_payload` computes `parent_epoch = compute_epoch_at_slot(N)`, which is neither `get_current_epoch(state)` nor `get_previous_epoch(state)`. Since `parent_bid.value == V > 0`, the `elif` branch fires and unconditionally appends `BuilderPendingWithdrawal(fee_recipient=parent_bid.fee_recipient, amount=V, builder_index=parent_bid.builder_index)` to `state.builder_pending_withdrawals`.
5. Result: the builder receives `V` even though the PTC quorum check for that exact commitment already failed and discarded the payment in step 3 — `Gwei` is paid to the builder ("escaped") without the required quorum-based authorization, violating the payment-gate invariant that governs every other settlement path in the spec. def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
