### Title
Post-default withdraw receipts drain `defaultRecoveryReserve` without being added to its basis, permanently freezing defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
After `finalizeDefaultRecovery`, `IdleCreditVault.requestWithdraw` lets a user open a new withdraw receipt (`postDefaultRequests`) that is backed by freshly deposited underlying held by the strategy. However, that fresh underlying is never added to `defaultRecoveryReserve`, while the claim path `_claimPostDefaultWithdrawRequest` pays the receipt 1:1 *out of* `defaultRecoveryReserve` via `_transferDefaultRecovery`. Each post-default claim therefore consumes reserve earmarked for defaulted-epoch receipts, until `_transferDefaultRecovery` underflows and all remaining defaulted claims revert permanently. Analogous to the CVE-2022-1283 missing-check class: the code dereferences a shared reserve bucket that was never topped up for the new claim basis.

### Finding Description
`finalizeDefaultRecovery` sizes the reserve exactly for the default basis: `defaultRecoveryReserve = reserveAmount` where `reserveAmount` covers `totalBasis * recoveryPrice` (active LPs + pending receipts) [1](#0-0) . There is no headroom for any other claim.

In the post-default branch of `requestWithdraw`, the strategy burns CDO strategy tokens and mints the same amount to the user, storing `postDefaultRequests[_user] = _amount` [2](#0-1) . The underlying backing this receipt was already transferred to the strategy during the user's post-default deposit (CDO `depositAA`/`depositBB` → `IdleCreditVault.deposit`), but `defaultRecoveryReserve` is not incremented — the comment even states the design goal "without increasing borrower-facing pendingWithdraws", and no reserve top-up occurs either [3](#0-2) .

On claim, `claimWithdrawRequest` processes `postDefaultRequests` first through `_claimPostDefaultWithdrawRequest`, which calls `_transferDefaultRecovery(_user, amount)` [4](#0-3) . `_transferDefaultRecovery` unconditionally decrements `defaultRecoveryReserve -= _amount` and transfers underlying [5](#0-4) . Because post-default claims are serviced by the same reserve that defaulted-epoch receipts depend on (`_claimDefaultedWithdrawRequest` → `_transferDefaultRecovery` at `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` [6](#0-5) ), every post-default claim of size `X` reduces the reserve available to defaulted claimants by `X` while the backing tokens for `X` came from the new deposit. Once cumulative post-default claims exhaust the arithmetic headroom, the next defaulted claim reverts on the unchecked subtraction — permanently, since the receipt state is only cleared inside the reverting call.

Broken invariant: one receipt one payout / isolation of the recovery reserve. No existing guard stops this: `requestWithdraw` post-default checks only `_hasWithdrawRequest`, `instantWithdrawsRequests` and `postDefaultRequests` of the *same* user [7](#0-6) , and nothing validates that the reserve can still cover all outstanding defaulted claims.

### Impact Explanation
Any unprivileged KYC-passing lender can deposit after default finalization and immediately request+claim a withdraw. Their payout is debited from `defaultRecoveryReserve`, so defaulted-epoch withdraw receipt holders (and `claimInstantWithdrawRequest` defaulted receipts via `_claimDefaultedInstantWithdrawRequest` [8](#0-7) ) find their claims reverting on `defaultRecoveryReserve -= _amount` underflow. The corresponding underlying remains stranded in the strategy (recoverable only via owner `transferToken`), i.e. permanent freezing of user recovery funds up to the total size of post-default claims, bounded by the reserve. A large post-default deposit can freeze effectively the entire recovery reserve.

### Likelihood Explanation
Requires only a finalized borrower default (a normal protocol state with dedicated UX explicitly kept alive post-default, per the "Preserve request/claim UX after default" comment) plus one ordinary post-default deposit+withdraw by any allowed lender — no privileged cooperation, no timing race beyond acting before victims claim. The closer the actual recovery is to the exact computed basis (the common case; over-recovery only adds slack), the smaller the post-default deposit needed to strand claims.

### Recommendation
Keep post-default receipts out of the recovery reserve: either (a) track post-default claims against their own backing — increment `defaultRecoveryReserve` (or a separate counter) by the deposited backing when `postDefaultRequests[_user]` is created, or pay them through `_transferFundedClaim` semantics that exempt the reserve — or (b) maintain a segregated `postDefaultReserve` funded by the post-default deposit flow, so `_claimPostDefaultWithdrawRequest` never decrements `defaultRecoveryReserve`. Option (a) minimally: in the `defaultRecoveryFinalized` branch of `requestWithdraw`, add `defaultRecoveryReserve += _amount` (the new deposit's underlying already sits in the vault), preserving the "one receipt one payout" invariant for defaulted claimants.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `_checkDefault`):

```solidity
function testPostDefaultClaimFreezesDefaultedReceipt() external {
    address victim = makeAddr('defaulted-receipt-user');
    address attacker = makeAddr('post-default-user');
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 recoveryRatio = 7e17;

    // Victim opens a normal withdraw request in epoch 0
    _depositWithUser(victim, amount, true);
    vm.prank(victim);
    uint256 victimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(0);
    uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest() - cdoEpoch.pendingWithdrawFees();
    uint256 recovered = (activeBasis + victimBasis) * recoveryRatio / ONE_TRANCHE;
    _stopEpochAndCheckPrices(0, initialProvidedApr, 0);
    _checkDefault();

    // Owner finalizes default with partial recovery; reserve == recovered
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    uint256 reservePre = creditVault.defaultRecoveryReserve();
    assertEq(reservePre, recovered);

    // Attacker deposits post-default and immediately requests + claims withdraw.
    // Claim is paid 1:1 out of defaultRecoveryReserve.
    _depositWithUser(attacker, reservePre, true); // sized to drain the reserve
    vm.startPrank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    cdoEpoch.claimWithdrawRequest();
    vm.stopPrank();
    assertLt(creditVault.defaultRecoveryReserve(), reservePre, 'reserve drained by post-default claim');

    // Victim's defaulted receipt can no longer be paid: reserve underflow reverts forever.
    vm.prank(victim);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertions: `postDefaultRequests[attacker]` is never added to `defaultRecoveryReserve`; the attacker's claim succeeds via `_transferDefaultRecovery`; the victim's `_claimDefaultedWithdrawRequest` then reverts on `defaultRecoveryReserve -= _amount`, leaving `victimBasis * defaultRecoveryPrice / 1e18` permanently unclaimable while the equivalent underlying sits stranded in the strategy.

  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);

    if (_amount == 0) return;
