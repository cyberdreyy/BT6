Analysis shows `delete_member` in `multisig2/src/lib.rs` deletes outstanding requests originated by the removed member and purges the member's confirmation set correctly, but it does **not** scrub that member's public key/account entry out of the `confirmations` `HashSet<String>` of *other* requests that the member had already confirmed but did not originate. [1](#0-0) 

However, this alone does not create a crossed authorization boundary: `confirm()` only checks `confirmations.len() as u32 + 1 >= self.num_confirmations`, i.e., it counts raw entries in the `HashSet`, not validated live members. [2](#0-1) 

So if member A confirms request X (not proposer), then is deleted via `DeleteMember`, request X's confirmation set (containing A's already-recorded confirmation) is left untouched since the removal loop only targets requests where `r.member == member` (i.e., requests A itself proposed), not requests A merely confirmed. A stale confirmation from a removed member would still count toward the threshold `num_confirmations`, potentially letting the remaining members execute the request with fewer *live* confirmations than intended — a direct match for the "confirmations counted versus live members" custody binding named in scope.

### Title
Stale confirmations from removed multisig members still count toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` removes a departing member's *own proposed* requests and their `num_requests_pk` counter, but never strips that member's recorded confirmation entries from *other* pending requests that member had already confirmed. `confirm()` subsequently authorizes execution purely by counting entries in the `confirmations` `HashSet`, without re-validating that each entry corresponds to a still-active member. This breaks the equality "confirmations counted == live members who confirmed."

### Finding Description
`delete_member` filters `self.requests` for entries whose `r.member == member` (the proposer) and removes those, plus clears `num_requests_pk` for the removed member: [3](#0-2) 

It does not iterate `self.confirmations` to strip the removed member's string key/account id from confirmation sets of requests proposed by *other* members. `confirm()` treats the size of that set as the source of truth for the threshold check: [2](#0-1) 

Consequently, once member M is removed (e.g. because they are believed compromised or offboarded), any request M had confirmed before removal keeps M's confirmation "alive" in state. If the remaining active members later add enough confirmations to reach `num_confirmations` counting M's stale entry, the request executes with fewer genuinely live-member confirmations than the K-of-N policy is supposed to require.

### Impact Explanation
This falls under the Critical impact category ("a multisig request executed below threshold"): the multisig authorization guarantee (K live members must approve) can be violated, allowing a `Transfer`, `FunctionCall`, `AddKey`, or other privileged `MultiSigRequestAction` to execute with fewer than K currently-trusted approvals, potentially moving NEAR or granting access under a weakened threshold.

### Likelihood Explanation
Requires a `DeleteMember` action to be executed (itself requires K confirmations, so it needs cooperation of the *current* members, not an unprivileged attacker acting alone) while a request confirmed by the removed member is still pending. This is a plausible operational sequence (revoking a compromised/departing signer) rather than a purely theoretical scenario, but it is not exploitable by an outside attacker without some multisig member cooperation, and the PoC has not been executed end-to-end against the deployed contract to confirm no other guard exists.

### Recommendation
In `delete_member`, iterate over all entries in `self.confirmations` (not just requests proposed by the removed member) and remove the departing member's key from every confirmation set, re-checking whether any request that consequently drops below the confirmation floor should be flagged/cleared. Alternatively, have `confirm()` re-validate, at check time, that every entry in the confirmation set still belongs to `self.members` before comparing the count to `num_confirmations`.

### Proof of Concept
Conceptual sequence (not executed against a live/sandbox deployment in this session):
1. Deploy `MultiSigContract::new` with members `[A, B, C]`, `num_confirmations = 2`.
2. A calls `add_request` proposing a `Transfer`. B calls `confirm(request_id)` — now `confirmations = {B}`, request stays pending (needs 2).
3. Members execute a separate `DeleteMember { member: B }` request (via A+C confirming), which calls `delete_member`; since the pending transfer request's `r.member == A` (not B), it is *not* purged, and B's confirmation entry inside its `confirmations` set is *not* stripped.
4. C now calls `confirm(request_id)` on the original transfer request. `confirmations.len() + 1 = 2 >= num_confirmations (2)` — the request executes, counting B's stale confirmation even though B is no longer a member. [4](#0-3) [2](#0-1)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
