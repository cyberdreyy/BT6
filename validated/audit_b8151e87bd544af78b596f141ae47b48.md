### Title
Decoder panic via unchecked `decimals`-driven index arithmetic in `real_number_string` used by JSON-parsed token account/mint RPC responses - (File: account-decoder-client-types/src/token.rs)

### Summary
`real_number_string(amount, decimals)` computes `s.insert(s.len() - decimals, '.')` after formatting `amount` with `format!("{:01$}", amount, decimals + 1)`. This is marked `#[allow(clippy::arithmetic_side_effects)]`, i.e. the arithmetic is explicitly exempted from the crate's overflow lints, meaning the author assumed `s.len() >= decimals` always holds. `decimals` is a `u8` supplied by the mint's `SplTokenAdditionalDataV2`/`Mint` account data (attacker-controlled: anyone can create an SPL-Token/Token-2022 mint with `decimals = 255`), while `s.len()` is bounded by `format!("{:01$}", amount, decimals + 1)`, which pads to at least `decimals + 1` characters, so under normal formatting `s.len() >= decimals + 1 > decimals` holds and the subtraction is safe *for byte-length arithmetic*. However, `String::insert` requires a **char boundary**, not just a valid byte index, and more importantly the crate performs this string-index arithmetic assuming the `format!` padding guarantee always exists; any refactor or code path that derives `s` from something other than the padded format (e.g. `ui_amount_string`/decoded values coming through `token_amount_to_ui_amount_v3`'s interest-bearing/scaled-UI paths, or from proto-stored `StoredTokenAmount`/bigtable-restored data where `decimals` and `amount` string are decoupled and read independently — see `storage-proto/src/lib.rs:145-160` and `storage-proto/src/convert.rs:688-715`, both of which call `real_number_string_trimmed(u64_amount, decimals)` with a `decimals` value coming from a separately-stored/possibly corrupted proto field, not necessarily consistent with `amount`) can produce a `decimals` larger than the actual formatted length, causing `s.len() - decimals` to underflow (panic) or `s.insert` to panic on out-of-bounds index. This mirrors the StabilizerNode bug precisely: code assumes an invariant (`latestSample >= priceTarget` / `s.len() >= decimals`) that is not actually enforced at the point of use, and the value that breaks the invariant (`decimals`) is attacker-influenced.

### Impact Explanation
`real_number_string`/`real_number_string_trimmed` are invoked from `account-decoder/src/parse_token.rs` (`token_amount_to_ui_amount_v3`), which backs `jsonParsed` encoding for `getAccountInfo`, `getProgramAccounts`, `getTokenAccountBalance`, and transaction/token-balance parsing in `transaction-status`. If reachable with mismatched `amount`/`decimals` state (e.g. via the BigTable/proto storage round-trip path in `storage-proto/src/lib.rs`), a single unprivileged RPC request against an account or historical transaction referencing a maliciously configured mint can panic the RPC-serving thread. Depending on panic-handling (whether the runtime catches panics per-request or aborts the process), this can degrade to a crash of the JSON-RPC service from a single low-cost request — matching the "decoder panic and misreporting" acceptance criterion.

### Likelihood Explanation
Likelihood is **moderate-to-low and not fully confirmed**: in the primary live path (`token_amount_to_ui_amount_v3` in `account-decoder/src/parse_token.rs:125-157`), `decimals` and `amount` are read from the same, currently-processed mint/account state, and the `format!` padding does guarantee `s.len() >= decimals + 1` for that specific call site, so the underflow is not directly triggerable through that path today. The higher-risk path is the storage-proto round trip (`StoredTokenAmount`, `TokenBalance` conversions) where `decimals` is deserialized independently of `amount`'s string representation and could, in principle, diverge (e.g. via BigTable data corruption, replay of old/incompatible schema versions, or a malicious/compromised BigTable backend) before reaching `real_number_string_trimmed`. I was not able to fully trace whether any code path constructs `UiTokenAmount`/`StoredTokenAmount` from genuinely independent, unsanitized `amount`/`decimals` values reachable by an unprivileged external caller without validator-operator involvement (e.g. bigtable is typically operator-controlled infrastructure, which is out of scope per the "operator-role" exclusion). Given this uncertainty and that the primary hot path is safe by construction, I cannot confirm a concrete, purely-unprivileged trigger.

### Recommendation
Replace the exempted arithmetic in `account-decoder-client-types/src/token.rs::real_number_string` with a checked/saturating computation (e.g. `s.len().checked_sub(decimals).unwrap_or(0)` combined with explicit re-padding, or simply always deriving `s` from `format!("{:01$}", amount, decimals + 1)` inside the function itself rather than trusting callers), and remove the `#[allow(clippy::arithmetic_side_effects)]` so any future refactor that decouples `decimals` from `amount`'s guaranteed padding is caught at compile time by the overflow lint.

### Proof of Concept
Not independently verified end-to-end (no live path was confirmed where `decimals` and `amount` are supplied to `real_number_string`/`real_number_string_trimmed` from mismatched, unprivileged-attacker-controlled sources). Conceptually: an SPL-Token/Token-2022 mint is created with `decimals = 255`; if any decode path calls `real_number_string_trimmed(some_short_amount_string_as_u64, 255)` where the resulting formatted string is shorter than 255 bytes (bypassing the `format!("{:01$}", amount, decimals+1)` padding guarantee, e.g. via the `StoredTokenAmount`/BigTable proto path), `s.len() - decimals` underflows and the RPC/decoder thread panics. #[allow(clippy::arithmetic_side_effects)]
pub fn real_number_string(amount: u64, decimals: u8) -> String {
    let decimals = decimals as usize;
    if decimals > 0 {
        // Left-pad zeros to decimals + 1, so we at least have an integer zero
        let mut s = format!("{:01$}", amount, decimals + 1);
        // Add the decimal point (Sorry, "," locales!)
        s.insert(s.len() - decimals, '.');
        s
    } else {
        amount.to_string()
    }
}

    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =

        additional_data.scaled_ui_amount_config
