After thorough investigation of the repository, I found a direct analog to the CsFeeOracle front-running initialization vulnerability in the Sui Native Bridge's EVM-side contracts.

---

### Title
Unprotected `initializeConfig` in `BridgeCommittee` Allows Any EOA to Front-Run and Set a Malicious Config — (`bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig()` is an `external` function with no access control. Any EOA can call it before the legitimate deployer and permanently wire a malicious `IBridgeConfig` contract into the bridge's committee, breaking all token-transfer validation and potentially causing a permanent fund lock.

---

### Finding Description

`BridgeCommittee` is deployed as a UUPS proxy. Its main `initialize` function is protected by OpenZeppelin's `initializer` modifier and is called atomically during proxy deployment. However, `initializeConfig` — which wires the critical `IBridgeConfig` contract — is a **separate, unprotected external function** called in a subsequent transaction:

```solidity
// bridge/evm/contracts/BridgeCommittee.sol  lines 63-66
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

The only guard is a one-time check (`config == address(0)`). There is no `onlyOwner`, no committee-signature requirement, and no deployer check. The deployment sequence in tests and production is:

1. Deploy `BridgeCommittee` proxy + call `initialize` (atomic, safe).
2. Deploy `BridgeConfig` proxy + call `initialize` (separate tx).
3. Call `committee.initializeConfig(_config)` ← **front-runnable window**.

An attacker monitoring the mempool can submit a higher-gas transaction calling `initializeConfig(maliciousConfig)` before step 3 lands.

Once set, `config` is **permanent** — there is no `updateConfig` or committee-signed setter to overwrite it.

---

### Impact Explanation

Every critical bridge path reads `committee.config()`:

- `SuiBridge.transferBridgedTokensWithSignatures` uses `committee.config().chainID()` and `committee.config().tokenAddressOf(tokenID)` to validate the target chain and resolve the ERC-20 address for vault transfers.
- The `onlySupportedChain` modifier calls `committee.config().isChainSupported(targetChainID)`.
- `BridgeLimiter.initialize` calls `committee.config().isChainSupported(chainIDs[i])`.

A malicious config can:

| Malicious return value | Effect |
|---|---|
| `isChainSupported` → always `false` | All `transferBridgedTokensWithSignatures` calls revert via `onlySupportedChain` → permanent DoS / fund lock |
| `chainID()` → wrong value | Chain-ID equality check in `transferBridgedTokensWithSignatures` always fails |
| `tokenAddressOf` → `address(0)` | Vault transfer reverts; bridge is bricked |
| `tokenAddressOf` → attacker ERC-20 | Vault attempts to transfer attacker-controlled token; legitimate tokens remain locked |

The result is a **permanent fund lock**: bridged assets held in `BridgeVault` become unreachable because every unlock path through `SuiBridge` reverts. Recovery requires a committee-signed UUPS upgrade of `BridgeCommittee` itself, which takes time and coordination.

This matches the allowed impact: **permanent fund lock** (High/Medium) and potentially **bridge governance bypass enabling illegitimate unlock** (Critical) depending on the malicious config's design.

---

### Likelihood Explanation

- The attacker is an ordinary EOA — no validator, bridge authority, or admin role required.
- The front-running window exists between proxy deployment and the `initializeConfig` call, which are separate transactions observable in the public mempool.
- The attacker must pre-deploy a contract implementing `IBridgeConfig` with malicious return values — a trivial one-time cost.
- On Ethereum mainnet, MEV bots routinely monitor for exactly this pattern.

---

### Recommendation

Add an access control check to `initializeConfig`. The simplest fix is to restrict it to the deployer or to require committee signatures, consistent with how other governance operations are protected:

```solidity
// Option A: restrict to the account that called initialize
address private _deployer;

function initialize(...) external initializer {
    _deployer = msg.sender;
    ...
}

function initializeConfig(address _config) external {
    require(msg.sender == _deployer, "BridgeCommittee: Unauthorized");
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}

// Option B: call initializeConfig atomically inside initialize
function initialize(address[] memory committee, uint16[] memory stake, uint16 minStakeRequired, address _config)
    external initializer
{
    ...
    config = IBridgeConfig(_config);
}
```

Alternatively, call `initializeConfig` inside `initialize` so both operations are atomic and the front-running window is eliminated entirely.

---

### Proof of Concept

1. Attacker deploys `MaliciousConfig` implementing `IBridgeConfig` where `isChainSupported` always returns `false`.
2. Legitimate deployer submits the `BridgeCommittee` proxy deployment + `initialize` transaction (atomic, succeeds).
3. Legitimate deployer submits `committee.initializeConfig(legitimateConfig)`.
4. Attacker front-runs step 3 with `committee.initializeConfig(maliciousConfig)` at higher gas.
5. `initializeConfig` succeeds for the attacker (config was `address(0)`).
6. Legitimate deployer's transaction reverts: `"BridgeCommittee: Config already initialized"`.
7. All subsequent calls to `SuiBridge.transferBridgedTokensWithSignatures` revert at the `onlySupportedChain` modifier because `maliciousConfig.isChainSupported(...)` returns `false`.
8. Tokens locked in `BridgeVault` are permanently inaccessible through the normal unlock path.
