### Title
Missing empty-password check before `conn.Bind` in `ldapAuthenticator.CreateSession` enables LDAP unauthenticated-bind account takeover - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.CreateSession` forwards `sr.Password` directly to `conn.Bind(searchBaseDN, sr.Password)` with no check that the password is non-empty. Since a simple LDAP bind with a valid DN and a zero-length password is defined by the LDAP protocol as an "unauthenticated bind" that many directory servers accept as successful (per RFC 4513 §5.1.2, unless the server explicitly disables it), an attacker who only knows a victim's email can submit an empty password and have `conn.Bind` return `nil`, causing the node to issue a valid `ldap_sessions` entry for that victim.

### Finding Description
The reachable path is: unauthenticated `POST /sessions` → `SessionsController.Create` in `core/web/sessions_controller.go:29-68`, which binds the JSON body directly into `clsessions.SessionRequest{Email, Password}` with no validation of `Password` (only `c.ShouldBindJSON` type-checking) [1](#0-0)  → `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` [2](#0-1) , which for LDAP-backed nodes resolves to `ldapAuthenticator.CreateSession`.

Inside `CreateSession`, the email is escaped and used to build `searchBaseDN`, and then the raw `sr.Password` (with no non-empty check) is passed straight to `conn.Bind`: [3](#0-2) 

If `conn.Bind` returns `nil` (success), the code proceeds to call `FindUser` for the victim's email to fetch roles, and on success writes a new row into `ldap_sessions` for that user's email/role and returns a valid session ID: [4](#0-3) 

`SessionRequest` itself has no validation logic (`Password` is a bare `string` field with a JSON tag, no `binding:"required"` or length check): [5](#0-4) 

The root cause is that this code path fully relies on the semantics of the upstream LDAP server to reject empty-password binds; the go-ldap client library's `Bind` call performs no client-side rejection of empty passwords, and chainlink adds none either. This differs from the `localLoginFallback` path, which uses `utils.CheckPasswordHash` for local users and is not vulnerable to this issue, but that fallback is only reached if the LDAP bind fails first [6](#0-5) .

### Impact Explanation
If the configured upstream LDAP/AD server permits unauthenticated ("anonymous"/empty-password) simple binds for a valid DN — a behavior explicitly allowed by the LDAP standard and a documented default in some deployments — an attacker who knows only a victim's email can obtain a fully valid, role-bearing `ldap_sessions` session cookie for that victim without ever supplying real credentials. This maps to the Chainlink bounty class of full unauthenticated account takeover / authentication bypass, since the resulting session inherits the victim's actual role from `FindUser`, potentially including admin/edit privileges.

### Likelihood Explanation
- Precondition: node is configured to use the LDAP authentication provider (`LDAPAuth`), and the upstream directory server does not explicitly reject unauthenticated binds (a config choice on the *directory server*, not chainlink, but a widely-seen default/legacy posture, especially for AD and older OpenLDAP deployments).
- Attacker precondition: no credentials at all beyond a known valid victim email — the lowest possible privilege bar, satisfying the "unauthenticated attacker" threat model.
- The request is a single, deterministic `POST /sessions {email, password: ""}` call, fully repeatable and requiring no timing or race conditions.
- The chainlink-side code is the layer that could and should have defended against this well-documented LDAP client footgun (OWASP's LDAP Injection Prevention Cheat Sheet explicitly recommends applications reject empty passwords before binding, rather than relying on server behavior), so this is a genuine application-level gap, not merely a server misconfiguration issue.

### Recommendation
In `ldapAuthenticator.CreateSession` (and `TestPassword`), explicitly reject empty/blank `sr.Password` (and empty `email`) before calling `conn.Bind`, e.g.:
```go
if sr.Password == "" {
    return "", errors.New("unable to log in with LDAP server. Check credentials")
}
```
Apply the same check in `TestPassword` (`core/sessions/ldapauth/ldap.go:504-530`), which has the identical pattern. This removes reliance on upstream server semantics and enforces the "empty/anonymous bind must never authenticate a named user" invariant at the application layer regardless of directory server configuration.

### Proof of Concept
Go unit test using the existing mockery-generated `mocks.LDAPConn`/`mocks.LDAPClient` (as used in `core/sessions/ldapauth/ldap_test.go`):
1. Set up `ldapAuthProvider` via `setupAuthenticationProvider(t, mockLdapClient)` as in `TestORM_CreateSession_UpstreamBind`.
2. Configure `mockLdapConnProvider.On("Bind", mock.Anything, "").Return(nil)` to simulate an RFC-compliant unauthenticated-bind-success-on-empty-password server.
3. Call `ldapAuthProvider.CreateSession(ctx, sessions.SessionRequest{Email: victimUser.Email, Password: ""})`.
4. Assert (post-fix) that the call returns an error *before* `Bind` is invoked (verify with `mockLdapConnProvider.AssertNotCalled(t, "Bind", mock.Anything, mock.Anything)`), and that no row is inserted into `ldap_sessions` for `victimUser.Email`.
5. Currently (pre-fix), the test would show `err == nil` and a valid session ID returned, confirming the vulnerability.
