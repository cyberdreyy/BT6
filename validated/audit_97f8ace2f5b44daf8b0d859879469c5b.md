### Title
Dust APR=0 withdraw receipt permanently bricks `stopEpoch` once APR is raised — (`File: contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The external bug is a crash reachable only through a specific unhandled input case ("book 10"). The analog in `IdleCreditVault.prepareStopEpochWithApr0` is a hard `revert NotAllowed()` that fires whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. An unprivileged user can place a dust-sized APR0 withdraw request (via `requestWithdraw` while `unscaledApr == 0`), which sets `apr0TotalPrincipal > 0`. If APR later becomes non-zero before that bucket is cleared, every subsequent `stopEpoch` call reverts, permanently freezing all LP funds.

### Finding Description
`requestWithdraw` routes requests into the APR0 bucket when `unscaledApr == 0`, incrementing `apr0TotalPrincipal` (`IdleCreditVault.sol:285-286`, `_requestWithdrawApr0` at `567-577`). During `stopEpoch`, `prepareStopEpochWithApr0` reverts unconditionally if the APR0 bucket is non-empty but `unscaledApr != 0` (`IdleCreditVault.sol:505-508`), and this call sits inside `_stopEpoch` before the epoch can close (`IdleCDOEpochVariant.sol:362`).

Because `apr0TotalPrincipal` is only cleared inside `prepareStopEpochWithApr0` (`IdleCreditVault.sol:540`), the revert is self-perpetuating: no stopEpoch can ever succeed again, so `isEpochRunning` stays true, `epochEndDate` passes, and deposits/withdrawals are locked indefinitely — a one-case crash that becomes a permanent freeze.

### Impact Explanation
Broken invariant: liveness of the epoch state machine. All underlying held by borrower and strategy is unrecoverable through normal flow; pending withdraw receipts can never be funded, matching "permanent freezing of funds". Loss magnitude equals the full pool TVL. Attacker cost is a dust-sized deposit plus one `requestWithdraw` call.

### Likelihood Explanation
Requires two conditions: (a) an APR0 request outstanding, which any KYC-passing lender can create at dust size while APR is 0, and (b) `unscaledApr` becoming non-zero while `apr0TotalPrincipal != 0`. The happy path clears the bucket inside the same `stopEpoch` that sets `_newApr`, so the trigger needs an APR transition that bypasses `prepareStopEpochWithApr0` — e.g., an honest owner/manager calling a direct APR setter (or orchestrator-driven APR update) mid-epoch, or an upgrade-path state where the APR0 bucket is non-zero at a non-zero APR. Medium likelihood, mirroring the medium severity of the source CVE.

### Recommendation
Instead of reverting when `unscaledApr != 0`, settle the APR0 bucket at zero interest: delete/zero `apr0TotalPrincipal` and mark the open requests claimable at principal only (move `_apr0User.principal` into `settledPrincipal` semantics), or explicitly convert APR0 receipts into `withdrawsRequests`/`withdrawsRequestsByEpoch` for `epochNumber` so users claim through `_claimFundedWithdrawRequest`. An invariant test should assert `stopEpoch` succeeds for any `(unscaledApr, apr0TotalPrincipal)` combination.

### Proof of Concept
Foundry fork sketch:

```solidity
// pool running at APR 0 (unscaledApr == 0)
uint256 dust = 1;
// attacker: deposit minimum AA, request withdraw -> fills apr0 bucket
deal(address(underlying), attacker, dust * ONE_SCALE);
vm.startPrank(attacker);
underlying.approve(address(cdoEpoch), dust * ONE_SCALE);
cdoEpoch.depositAA(dust * ONE_SCALE);
cdoEpoch.requestWithdraw(dust * ONE_SCALE, address(AAtranche));
vm.stopPrank();
assertGt(strategy.apr0TotalPrincipal(), 0);

// honest owner/manager raises APR outside stopEpoch (setter/orchestrator path)
// -> strategy.unscaledApr() != 0 while apr0TotalPrincipal != 0

vm.warp(cdoEpoch.epochEndDate() + 1);
vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);   // always reverts -> epoch can never close
```

Caveat: I could not fully enumerate every path that mutates `unscaledApr` outside `stopEpoch` (e.g., a direct `setApr`/orchestrator setter); if no such path exists, the revert branch may be unreachable in current configuration and the finding should be downgraded to a defensive-invariant gap rather than an exploitable freeze.
