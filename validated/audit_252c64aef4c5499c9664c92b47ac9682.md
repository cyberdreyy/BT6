### Title
Flashblocks "pending" RPC state (`eth_call`, `eth_estimateGas`, `eth_getBalance`, `eth_simulateV1`) can serve a state view that lags the canonical tip without surfacing that staleness to the caller - ([File: crates/execution/flashblocks/src/rpc/eth.rs])

### Summary
The external report describes a Chainlink TWAP oracle that, during periods of volatility, reports a price that lags the true value, letting an attacker exploit the gap between the reported (stale) price and the real price before the average "catches up." The reachable analog in this Base node stack is the flashblocks "pending" state served over the public `eth_*` RPC surface: account balances, `eth_call`/`eth_estimateGas` simulation results, and pending-block contents are computed against a `PendingBlocks` snapshot that is deliberately allowed to lag the canonical tip by a bounded-but-nonzero window, and that staleness bound is enforced only at snapshot-management time, not at the moment an RPC caller actually reads the value.

### Finding Description
`FlashblocksState`/`StateProcessor` merge the flashblock stream and canonical block notifications on one queue and publish a `PendingBlocks` snapshot that is allowed to sit up to `max_pending_blocks_depth + 1` blocks (default depth 3, so up to 4 blocks) behind the real canonical tip: [1](#0-0) 

This bound is checked when canonical notifications arrive and when the processor dequeues an update, but not when a consumer actually reads the published snapshot: [2](#0-1) 

The public RPC surface directly consumes this snapshot for `eth_call` (and analogously `eth_estimateGas`, `eth_getBalance`, `eth_getTransactionCount`, `eth_simulateV1`) when the `pending` tag is requested, applying the snapshot's `state_overrides` on top of `pending_blocks.get_canonical_block_number()` with no freshness check or staleness indicator returned to the caller: [3](#0-2) 

`get_pending_blocks()` simply loads whatever snapshot is currently published: [4](#0-3) 

The repository's own documentation and regression tests (referencing a real "2026-08-20 mainnet incident where canonical and flashblock updates piled up in the shared unbounded queue") confirm the queue can lag under load, and that the freshness guarantee is a bound, not an instantaneous truth, and that a caller wanting a tighter guarantee "must compare its view of the tip against `canonical_block_number` and `parent_hash` itself" — something the RPC response for `eth_call`/`eth_estimateGas` (a raw byte/gas result) cannot convey: [5](#0-4) [6](#0-5) 

Structurally this mirrors the reported bug class: a time-lagged data source (TWAP price / here, pending chain state) is consumed by downstream logic (liquidation/pricing decisions / here, `eth_call`-based simulation used by exchanges, bridges, or automated agents to decide whether to accept a transaction or release funds) without the consumer being told how stale the input is, and the lag window widens precisely during the conditions (high load/backlog) an attacker would want to exploit.

### Impact Explanation
Any anonymous RPC client — exchanges, bridges, MEV searchers, or automated agents — that uses `eth_call`/`eth_estimateGas`/`eth_getBalance` against the `pending` tag to decide whether to accept, forward, or settle a transaction can be given a view of account balances/state that is stale by design (bounded but nonzero, and unboundedly stale for the read-vs-check race window) without any signal that this occurred. During load spikes (queue backlog), the staleness window widens exactly when volatility/contention is highest, letting an attacker present a transaction that simulates successfully against stale "pending" balances/state but is inconsistent with true canonical state, mirroring the report's scenario of exploiting a lagging price/state feed for profit before it "catches up." This is a data-integrity/economic-risk issue for anyone building financial logic atop this RPC surface, not a node-halt or consensus bug.

### Likelihood Explanation
The staleness window is not a rare edge case — it is the explicitly documented, bounded design tradeoff (`max_pending_blocks_depth`, default 3, plus the anchor offset), and the repository's own tests/README reference a real production incident where the backlog grew unbounded. Any RPC caller relying on `pending`-tagged simulations for correctness during periods of elevated flashblock/canonical throughput will hit this without any special privilege — a single unauthenticated RPC request suffices.

### Recommendation
Short term: have `eth_call`/`eth_estimateGas`/`eth_getBalance`/`eth_simulateV1` return (or make queryable) the `canonical_block_number` and `parent_hash` the pending snapshot was anchored to, so callers can detect staleness themselves rather than being told to do so only via documentation; consider rejecting or flagging `pending` reads when the snapshot is not within a tighter, explicitly-communicated freshness bound. Long term: bound the update queue (acknowledged as separate work in the README) and evaluate freshness at the read boundary, not only at publish/notification time, closing the race window between "judged fresh" and "consumed."

### Proof of Concept
1. Drive the node into a queue-lag state as reproduced by the existing test harness (`advance_tip_without_processing`), simulating sustained flashblock/canonical backlog: [5](#0-4) 
2. While the backlog exists but before `pending_drop_stale` clears the snapshot, issue `eth_call`/`eth_estimateGas` with `block: "pending"` against a target contract/account whose real canonical balance/state has since diverged from the published `PendingBlocks` overlay.
3. Observe that the RPC layer computes the result purely from `pending_blocks.get_state_overrides()`/`get_canonical_block_number()` with no indication of the anchor's actual age relative to the true tip: [7](#0-6) 
4. A downstream consumer trusting this "success" result (e.g., approving a withdrawal or trade) acts on stale state, analogous to Eve exploiting a lagging TWAP in the original report.
