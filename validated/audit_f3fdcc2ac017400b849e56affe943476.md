# Vulnerability Found

### Title
Unbounded/blocking shareholder loop in `vesting::distribute` allows a single shareholder to permanently DoS reward and vesting distribution for the entire pool - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`vesting::distribute` iterates over every shareholder of a vesting contract in a single atomic loop and calls `aptos_account::deposit_coins` for each one [1](#0-0) . `deposit_coins` aborts if the recipient is not yet registered for the coin type and has opted out of direct coin transfers [2](#0-1) . Because Move has no try/catch, one aborting recipient reverts the whole transaction, which blocks the loop for every other shareholder — exactly the "one bad actor breaks an unbounded shared loop" pattern described in the external NFT report, applied here to vesting/reward distribution instead of NFT removal.

### Finding Description
`create_vesting_contract` fixes the list of `shareholders` for a vesting pool at creation time and this list cannot be modified or pruned afterward [3](#0-2) . `distribute` (callable permissionlessly by anyone, via `distribute` or `distribute_many`) later withdraws all unlocked stake and iterates `grant_pool.shareholders()`, sending each shareholder's share directly via `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` will `assert!(can_receive_direct_coin_transfers(to), ...)` and abort if the recipient address is not already registered for the coin type and has set `allow_arbitrary_coin_transfers = false` via `set_allow_direct_coin_transfers` [2](#0-1) [4](#0-3) .

Any account that is designated a shareholder (or its beneficiary via `update_beneficiary`) never has to actively register for `AptosCoin` before the first `distribute()` call — vesting `buy_ins` are recorded in the pool's internal `pool_u64` structure at creation, not as an actual coin transfer to the shareholder's wallet. Therefore a shareholder can, at any time before the first distribution, simply call `aptos_account::set_allow_direct_coin_transfers(signer, false)` on their own account. From that point on, every call to `distribute(contract_address)` will abort inside the shared loop as soon as it reaches that shareholder's turn, because there is no exception handling to skip the failing recipient and continue with the rest.

Since `distribute()` is also invoked as the first step of `terminate_vesting_contract` [5](#0-4)  and is a prerequisite before `admin_withdraw` can meaningfully release funds, this single self-inflicted abort blocks not only ordinary reward/vest distributions for all co-shareholders, but also contract termination and admin recovery of the underlying stake pool.

### Impact Explanation
This directly falls under the required "Stake And Lockup Gate" impact category — "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows." A single unprivileged shareholder in a shared vesting contract (e.g., an employee/team-grant vesting pool with many co-shareholders) can permanently strand all future stake rewards and vested-token distributions for every other, honest, shareholder of that same vesting contract, and also block `terminate_vesting_contract`/`admin_withdraw`. No compromise of the admin, operator, or other shareholders is required — the attacker only needs to control (or be) one shareholder or beneficiary entry already present in the pool.

### Likelihood Explanation
High likelihood in any vesting contract that has more than one shareholder — a very common configuration (team/investor vesting pools). Setting `allow_arbitrary_coin_transfers = false` via `set_allow_direct_coin_transfers` is a normal, permissionless, single-transaction operation available to any account, and does not require the account to hold privileged roles in the vesting contract. It can be executed pre-emptively before ever being registered for `AptosCoin`, guaranteeing the abort condition triggers on the very first distribution attempt.

### Recommendation
- Do not perform a single atomic multi-recipient `deposit_coins` loop inside `distribute`. Instead, accrue each shareholder's due amount as an individually claimable/pull-based balance (e.g., a per-shareholder "withdrawable" record), letting each shareholder or beneficiary withdraw independently.
- Alternatively, wrap each per-shareholder deposit attempt so that a failure for one recipient (e.g., not registered / transfers disabled) does not abort the whole batch — e.g., detect `can_receive_direct_coin_transfers`/registration status ahead of time and, if the recipient cannot currently receive funds, hold their share in an escrow entry redeemable later instead of aborting the entire `distribute()` call.
- Consider disallowing (or specially handling) shareholders that have `allow_arbitrary_coin_transfers == false` and are not yet registered, since this state can be set unilaterally by any account before any distribution has occurred.

### Proof of Concept
1. Admin calls `create_vesting_contract` with shareholders `[A (attacker), B (honest)]`.
2. Before any `distribute()` has ever run, attacker `A` calls `aptos_account::set_allow_direct_coin_transfers(A_signer, false)` — a permissionless, unprivileged self-call.
3. Time passes; rewards accrue and/or a vesting period completes (`vest`/`unlock_rewards` succeed since they never call `deposit_coins`).
4. Anyone calls `distribute(contract_address)`. Inside the `for_each_ref` loop, when it reaches shareholder `A`, `aptos_account::deposit_coins` executes `is_account_registered<AptosCoin>(A) == false` and `can_receive_direct_coin_transfers(A) == false`, aborting with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The abort propagates and reverts the entire `distribute()` transaction — shareholder `B`'s legitimate share is never paid, and every subsequent `distribute()`/`distribute_many()`/`terminate_vesting_contract()` call on this contract fails identically, permanently.

**Uncertainty note:** I was not able to fully trace `coin::deposit`/`coin::is_account_registered` internals for `AptosCoin` under the fungible-asset migration in this pass (the file was not indexed in the results I retrieved), so there is some residual uncertainty about whether an edge case in the FA-migrated coin path could special-case `AptosCoin` to bypass the `can_receive_direct_coin_transfers` check for this specific coin type. The `aptos_account::deposit_coins` generic function itself, as shown, does perform this check for any `CoinType` including `AptosCoin`, and `vesting::distribute` calls this generic function rather than the FA-specific `fungible_transfer_only` path used by `aptos_account::transfer`.

    /// Terminate the vesting contract and send all funds back to the withdrawal address.
    public entry fun terminate_vesting_contract(admin: &signer, contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        // Distribute all withdrawable coins, which should have been from previous rewards withdrawal or vest.
        distribute(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        verify_admin(admin, vesting_contract);
        let (active_stake, _, pending_active_stake, _) = stake::get_stake(vesting_contract.staking.pool_address);
        assert!(pending_active_stake == 0, error::invalid_state(EPENDING_STAKE_FOUND));

        // Unlock all remaining active stake.
        vesting_contract.state = VESTING_POOL_TERMINATED;
        vesting_contract.remaining_grant = 0;
        unlock_stake(vesting_contract, active_stake);

        emit(
            Terminate {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
            },
        );
    }

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }

    #[view]
    /// Return true if `account` can receive direct transfers of coins that they have not explicitly registered to
    /// receive.
    ///
    /// By default, this returns true if an account has not explicitly set whether the can receive direct transfers.
    public fun can_receive_direct_coin_transfers(
        account: address
    ): bool acquires DirectTransferConfig {
        !exists<DirectTransferConfig>(account)
            || borrow_global<DirectTransferConfig>(account).allow_arbitrary_coin_transfers
    }
