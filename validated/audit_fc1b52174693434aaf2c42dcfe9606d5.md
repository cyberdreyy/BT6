The reported issue is specific to a Uniswap-V2-style dual-token AMM concentrator (`Factory.sol#estimateDepositAmounts()`), where a boolean `aToken` swap flag causes `ADesired`/`BDesired` argument order to become inconsistent with `_quote()`'s expected `(AmountA, ReserveA, ReserveB)` ordering. I searched Aera's actual production contracts — `ProvisionerV2.sol` (deposit/mint/requestDeposit/requestRedeem/solveRequestsDirect/cancelRequest/refundRequest), `PriceAndFeeCalculatorV2.sol` (unit/token conversion, oracle quote binding), and the Balancer-based `AeraVaultV1.sol` — and found no functional analog. Aera's deposit/redeem flows are single-token-in/single-unit-out conversions via oracle pricing [1](#0-0) , not dual-token AMM liquidity quoting with a token-order swap boolean. The only token-ordering logic in the codebase is in third-party Balancer dependencies (`_sortTokens`, `ensureArrayIsSorted`) which enforce sorted-order token registration rather than runtime desired-amount swapping [2](#0-1) [3](#0-2) , and these are out-of-scope vendored dependencies, not Aera's own production logic. function _insertSorted(IERC20[] memory tokens, IERC20 token) pure returns (IERC20[] memory sorted) {
    sorted = new IERC20[](tokens.length + 1);

    if (tokens.length == 0) {
        sorted[0] = token;
        return sorted;
    }

    uint256 i;
    for (i = tokens.length; i > 0 && tokens[i - 1] > token; i--) sorted[i] = tokens[i - 1];
    for (uint256 j = 0; j < i; j++) sorted[j] = tokens[j];
    sorted[i] = token;
}
