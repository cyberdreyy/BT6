### Title
Post-default instant withdraw receipts are charged against the finalized default recovery reserve, draining or freezing other claimants' recovery - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug (CVE-2018-18065) is a NULL-pointer dereference reachable by an authenticated remote packet: a state lookup is performed on an object that was never populated for the new input, crashing the process. The analog in `IdleCreditVault` is a state lookup that conflates epochs: after `finalizeDefaultRecovery`, `requestWithdraw` has an explicit post-default path, but `requestInstantWithdraw` keeps recording receipts into `instantWithdrawsRequestsByEpoch[_user][epochNumber]` — and `epochNumber` never advances past `defaultRecoveryEpoch`. `_claimDefaultedInstantWithdrawRequest` then reads that same slot and pays the *new* post-default receipt out of `defaultRecoveryReserve` at the finalized haircut, i.e. it dereferences the defaulted-epoch bucket for a receipt that was never part of the finalized basis.

### Finding Description
- `requestWithdraw` branches on `defaultRecoveryFinalized` and routes new requests into `postDefaultRequests` (IdleCreditVault.sol:247-257).
- `requestInstantWithdraw` has no such branch; it executes `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` with `currentEpoch = epochNumber` (lines 367-374). Since `epochNumber` is frozen after default, `currentEpoch == defaultRecoveryEpoch`.
- `claimInstantWithdrawRequest` (lines 380-393), when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, calls `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844) and pays `claimBasis * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve` via `_transferDefaultRecovery` (lines 847-855, 912-917).
- The reserve was sized at finalization as `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` against `totalBasis` fixed at that moment (lines 685-692). A post-default instant receipt adds basis without adding reserve, so the attacker claims recovery-share value funded by other defaulted-epoch claimants. If enough attackers do this, `defaultRecoveryReserve -= _amount` underflows / the balance check fails, and legitimate `_claimDefaultedWithdrawRequest` / `_claimPostDefaultWithdrawRequest` calls revert — a permanent freeze of unclaimed recovery, mirroring the crash-after-crafted-input shape of the CVE.

### Impact Explanation
Direct theft plus permanent freezing of unclaimed yield: each post-default instant receipt withdraws `amount * defaultRecoveryPrice / 1e18` from a reserve it never contributed to; once the reserve is exhausted or underflows, every remaining defaulted-epoch claimant's `claimWithdrawRequest`/`claimInstantWithdrawRequest` reverts permanently. Loss is bounded by `postDefaultInstantSum * defaultRecoveryPrice`, up to the whole reserve.

### Likelihood Explanation
Requires (a) instant withdrawals enabled (not the prefunded variant, which disables them via `_isInstantWithdrawEnabled`), (b) a borrower default finalized with `pendingInstantWithdraws != 0` so `defaultInstantWithdrawsFinalized` is true, and (c) the CDO still routing `requestInstantWithdraw` after default (the strategy itself imposes no `defaulted`/`defaultRecoveryFinalized` guard on this entry point, unlike `requestWithdraw`). Any tranche-token holder can then trigger it with a single request+claim sequence. Caveat: whether `IdleCDOEpochVariant`/`IdleCDO` gates instant withdraw requests while `defaulted` could not be fully confirmed within the investigation; if a CDO-level check blocks post-default instant requests, the finding reduces to the accounting asymmetry in the strategy.

### Recommendation
In `requestInstantWithdraw`, mirror `requestWithdraw`: if `defaultRecoveryFinalized`, revert `NotAllowed()` (or route to `postDefaultRequests`-style accounting). Additionally, in `_claimDefaultedInstantWithdrawRequest`, bound `claimBasis` to the receipt basis that existed at finalization (e.g. snapshot per-epoch claims into a dedicated `defaultedInstantBasisByUser` at `finalizeDefaultRecovery`) so later writes to `instantWithdrawsRequestsByEpoch[defaultRecoveryEpoch]` cannot be claimed against the reserve.
