Both `staking_contract.move` and `delegation_pool.move` contain a beneficiary-switch analog of the Frax fee-change bug: the beneficiary lookup for already-accrued (but not yet distributed/synced) commission happens **at distribution/synchronization time**, not at accrual time, and the beneficiary-switch functions explicitly skip forcing that settlement first.

### Title
`set_beneficiary_for_operator` lets an operator redirect already-accrued, undistributed commission from the current beneficiary to a new one - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move` and `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary
In `staking_contract.move`, `set_operator`/commission-changing paths (`update_commision`, `switch_operator`) all force a settlement via `distribute_internal`/`request_commission_internal` before mutating state [1](#0-0) , but `set_beneficiary_for_operator` does not [2](#0-1) . The doc comment even admits the flaw: "Any existing unpaid commission rewards will be paid to the new beneficiary. To ensure payment to the current beneficiary, one should first call `distribute`..." [3](#0-2) . The actual recipient lookup for pending distributions happens lazily inside `distribute_internal`, at the time funds are finally paid out, not when they were earned: `if (recipient == operator) { recipient = beneficiary_for_operator(operator); }` [4](#0-3) .

The same pattern exists in `delegation_pool.move`: `set_beneficiary_for_operator` mutates `BeneficiaryForOperator` without calling `synchronize_delegation_pool` first [5](#0-4) , while `set_operator` and `update_commission_percentage` both explicitly call `synchronize_delegation_pool` first to "ensure the old operator is paid its uncommitted commission rewards" [6](#0-5) . Inside `synchronize_delegation_pool`, commission for potentially many epochs of undetected rewards is bought-in for `beneficiary_for_operator(stake::get_operator(pool_address))`, evaluated at call time [7](#0-6) .

### Finding Description
Both modules accrue operator commission continuously (as stake pool rewards compound), but only *crystallize* payment to a concrete address (`beneficiary_for_operator(operator)`) at a later, separate step — `distribute_internal` in `staking_contract.move`, or `synchronize_delegation_pool` in `delegation_pool.move`. Neither `set_beneficiary_for_operator` function forces that settlement step first. This is functionally identical to the external report's root cause: a rate/target-affecting parameter (`feeToProtocolRate` there, `beneficiary_for_operator` here) is changed without first accruing/settling value under the old parameter, so a later settlement retroactively applies the *new* parameter over a period where the *old* parameter should have applied.

Concretely for `delegation_pool`: commission can accumulate silently across many epochs without anyone calling `synchronize_delegation_pool` (it's only triggered incidentally by other delegator/owner actions). If the operator calls `set_beneficiary_for_operator(new_beneficiary)` at any point before the next synchronization, all commission earned while the *old* beneficiary was configured is instead paid to the *new* beneficiary once synchronization eventually runs, because `buy_in_active_shares`/`buy_in_pending_inactive_shares` resolve the beneficiary at sync time only [7](#0-6) . The same holds for `staking_contract`'s `distribute_internal`, which resolves the beneficiary at payout time for the entire `distribution_pool`, including distributions added long before the beneficiary switch [8](#0-7) .

### Impact Explanation
This corrupts payout accounting by crediting the wrong account: commission earned/owed to the previously-designated beneficiary is diverted to whatever address the operator sets afterward, before any pending distribution/sync occurs. This falls squarely under "Operator commission, beneficiary payout... corruption that credits the wrong account" in the impact scope. A beneficiary relying on the documented multi-step protection (must proactively call `distribute`/`synchronize_delegation_pool`) has no on-chain guarantee of receiving commission already earned on their behalf, and typical delegators/stakers/beneficiaries would not know to race the operator's beneficiary switch.

### Likelihood Explanation
Likelihood is high in the sense that no special privilege is needed beyond the operator role that already exists to call `set_beneficiary_for_operator` — no unusual precondition, race window, or attacker capability is required beyond normal operator behavior, and the vulnerable window (time since last distribution/sync) can be long since neither function is called automatically each epoch. The code comments themselves acknowledge this exact race exists, mirroring the disputed-but-confirmed severity discussion in the original Frax report.

### Recommendation
Mirror the pattern already used by `set_operator`/`update_commission_percentage` in both modules: force settlement of pending commission before mutating the beneficiary.
- In `staking_contract.move::set_beneficiary_for_operator`, iterate the staker's `staking_contracts` (or require callers pass staker/operator pairs) and call `distribute_internal` for any existing contracts under the operator before changing `BeneficiaryForOperator`.
- In `delegation_pool.move::set_beneficiary_for_operator`, call `synchronize_delegation_pool(pool_address)` (for the operator's pool) before mutating `BeneficiaryForOperator`, exactly as `set_operator` and `update_commission_percentage` already do.

### Proof of Concept
1. Operator `O` runs a delegation pool with beneficiary `B1` set via `set_beneficiary_for_operator(O, B1)`.
2. Multiple epochs pass without anyone calling `synchronize_delegation_pool` — commission accrues implicitly in the stake pool's rewards but is not yet bought into shares for any beneficiary.
3. `O` calls `set_beneficiary_for_operator(O, B2)`, changing `BeneficiaryForOperator` with no forced sync [9](#0-8) .
4. Any subsequent user action (e.g., a delegator calling `add_stake`/`unlock`) triggers `synchronize_delegation_pool`, which computes commission accrued over the *entire* window (including the period `B1` was beneficiary) and buys it into shares for `beneficiary_for_operator(O)`, which now resolves to `B2` [7](#0-6) .
5. `B1` never receives the commission earned while it was the designated beneficiary; `B2` receives the full amount instead.

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
