### Title
Missing Authorization on `base_setMeteringInformation`/`base_setMeteringEnabled`/`base_clearMeteringInformation` RPC Methods Allows Unprivileged Forgery of Builder Metering Data - ([File: crates/builder/metering/src/ext.rs])

### Summary
The Base builder node registers three JSON-RPC methods — `base_setMeteringInformation`, `base_setMeteringEnabled`, and `base_clearMeteringInformation` — under the public `base` RPC namespace with **no caller authentication, origin check, or role/permission gate**. These methods are intended to be called only by the trusted internal `ingress-rpc` component to forward simulation results into the builder's shared metering store, but any RPC client that can reach the builder's RPC port and invoke `base_*` methods can call them directly, exactly mirroring the Mattermost bug class of a privileged operation missing its required permission check.

### Finding Description
`MeteringStoreExt` implements the `BaseApiExt` RPC trait under the `base` namespace with three unauthenticated handlers that mutate the builder's shared `MeteringProvider` state directly, with no verification of the caller's identity or trust level: [1](#0-0) [2](#0-1) 

The extension is wired into the builder's RPC module set unconditionally via `add_or_replace_configured`, with no distinct admin/internal RPC gating comparable to the `admin_*` namespace used for `AdminTxPoolApi` (which is registered with `merge_if_module_configured(RethRpcModule::Admin, ...)`): [3](#0-2) 

Compare this to the txpool RPC extension, which explicitly gates its privileged `admin_dropSenderTransactions`/`admin_dropTransaction` methods behind the `RethRpcModule::Admin` configuration check: [4](#0-3) 

No equivalent gate exists for `MeteringStoreExtension`, which is installed on the builder binary alongside the transaction-submission and metering APIs that are reachable from public-facing infrastructure: [5](#0-4) 

The intended trust boundary is documented in the builder CLI args: the shared store is meant to be updated only by the `ingress-rpc` pipeline after it independently simulates a bundle and computes real timing/gas data: [6](#0-5) 

and the actual internal caller is `ingress-rpc`'s `BuilderConnector`, which forwards genuine simulation results to `base_setMeteringInformation` on the builder RPC: [7](#0-6) 

Because the handler performs no check that the caller is the trusted `ingress-rpc` component (no shared secret, mTLS check, or RPC-module gate distinguishing it from public `base_meterBundle`/`base_meterBlockByHash` methods that are explicitly proxied to public traffic per `etc/docker/proxyd/proxyd.toml`), any client with network access to the builder's RPC endpoint can directly call `base_setMeteringInformation` to inject an arbitrary, attacker-chosen `MeterBundleResponse` for any `tx_hash`, or call `base_clearMeteringInformation` / `base_setMeteringEnabled(false)` to wipe or disable the metering store entirely.

### Impact Explanation
The metering store backs block-building decisions: the ingress pipeline relies on the measured `total_execution_time_us` to reject bundles that would exceed the per-block time budget: [8](#0-7) 

An unprivileged caller that can forge entries via `base_setMeteringInformation` can make an expensive transaction appear cheap (or vice-versa), corrupting the builder's resource-metering/time-budget enforcement for block construction, or disable/clear metering outright, degrading the builder's ability to bound block-building resource consumption — a form of unauthorized operation against the block-building and resource-metering subsystem explicitly in scope for this analog.

### Likelihood Explanation
Exploitability depends entirely on network reachability of the builder's RPC port. If the builder's `base` namespace RPC listener is reachable by any transaction sender or third party (e.g., via a shared listener with `eth_sendRawTransaction`/`base_meterBundle`, both of which are proxied to the builder in `etc/docker/proxyd/proxyd.toml`), exploitation requires only a single unauthenticated JSON-RPC call — no signature, deposit, or special privilege needed. I could not fully verify from the indexed files whether production deployments isolate this RPC port from public listeners (docker-compose network topology was not fully explored), so likelihood is conditional on that network exposure, which should be confirmed before treating this as certainly externally reachable.

### Recommendation
Gate `base_setMeteringInformation`, `base_setMeteringEnabled`, and `base_clearMeteringInformation` behind the same kind of RPC-module/permission check used for `admin_*` methods (e.g. `merge_if_module_configured` against a dedicated internal-only module), or require mutual authentication (shared secret/mTLS) between `ingress-rpc` and the builder for this specific namespace, and ensure it is never exposed on the same listener as public `eth_*`/`base_meterBundle` traffic.

### Proof of Concept
Against a builder RPC endpoint that exposes the `base` namespace, any client can call, without authentication:
```
curl -X POST <builder-rpc> -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"base_clearMeteringInformation","params":[]}'
```
or forge metering data for an arbitrary transaction hash:
```
curl -X POST <builder-rpc> -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"base_setMeteringInformation","params":["0x<tx_hash>", {"results":[],"total_execution_time_us":0, ...}]}'
```
Both calls succeed with `Ok(())` from `MeteringStoreExt` with no caller-identity check, as shown in [2](#0-1) .
