The core question is whether an attacker can supply a `lending_market` account for a different Kamino market than the one the reserve (`integration_acc_1`) actually belongs to, while still passing the `integration_acc_2` (obligation) checks in `KaminoInitObligation`.

Looking at the account constraints, this is not exploitable:

**Why the binding holds:**
1. `integration_acc_2` (obligation) is constrained with `seeds = [&[0u8], &[0u8], liquidity_vault_authority.key(), lending_market.key(), system_program::ID, system_program::ID]` with `seeds::program = KAMINO_PROGRAM_ID` [1](#0-0) . Anchor's `seeds` constraint recomputes the PDA from the supplied `lending_market` and verifies it equals the actual `integration_acc_2` account key and bump — it is not a "hint," it's a hard equality check.
2. Separately, `bank` enforces `has_one = integration_acc_2 @ MarginfiError::InvalidKaminoObligation` [2](#0-1) , which pins `integration_acc_2` to the exact address recorded in the bank at creation time.
3. For the attacker's swapped `lending_market` to pass both checks simultaneously, they would need a *different* market pubkey that, when hashed with the fixed `tag=0, id=0, liquidity_vault_authority, system_program, system_program` seeds, produces the exact same PDA (address + bump) as the one already stored in the bank. This is a PDA preimage/collision requirement against `find_program_address`'s SHA-256-based derivation — not something an attacker can engineer; it isn't a "coincidence" that can be arranged, it's cryptographically infeasible.
4. The same seed-derivation logic is mirrored in `derive_kamino_obligation`/`derive_kamino_base_obligation` [3](#0-2) , confirming `lending_market` is a first-class seed input, not an independent/unchecked value — changing it changes the derived obligation address deterministically.
5. Additionally `cpi_refresh_reserve`, `cpi_init_obligation`, `cpi_refresh_obligation`, and `cpi_kamino_deposit` all pass the same `lending_market` account into the Kamino CPI alongside `integration_acc_1` (the reserve) [4](#0-3) ; Kamino's own program (not visible/modifiable here, but its behavior is assumed via mocks) would additionally validate that a reserve belongs to the given lending market during refresh/deposit operations, providing a second layer of defense at the CPI callee.

Since the `seeds` constraint on `integration_acc_2` cryptographically binds `lending_market` to the specific address already recorded on the bank, supplying a mismatched market cannot simultaneously satisfy `has_one = integration_acc_2` and the `seeds` derivation — the instruction would fail with a constraint seeds violation before ever reaching the CPI calls.

### No Vulnerability found for this question.
