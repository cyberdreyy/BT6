### Title
Unfunded instant-withdraw receipts drain underlying funded for prior normal claims - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug stores a pointer at trace time and dereferences fields later at print time, after the referenced object can be freed — i.e., a claim resolved against mutable state that no longer matches what was recorded. The in-scope analog is `IdleCreditVault.claimInstantWithdrawRequest`: an instant-withdraw receipt is recorded (strategy tokens minted 1:1, `pendingInstantWithdraws` incremented), but the claim is resolved later by blindly burning the receipt and paying out `instantWithdrawsRequests[_user]` in full, without checking that `collectInstantWithdrawFunds` ever pulled the corresponding underlying into the strategy and without decrementing `pendingInstantWithdraws`.

### Finding Description
In `requestInstantWithdraw` (`IdleCreditVault.sol:356-375`), the strategy burns CDO strategy tokens, mints a receipt token to the user, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws`. Funding for that receipt happens separately via `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`), which only the IdleCDO can call and which is the only place `pendingInstantWithdraws` is decremented.

`claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`) does not verify funding at all:

```
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`_transferFundedClaim` (`IdleCreditVault.sol:897-906`) only guards `defaultRecoveryReserve` — it pays out any other underlying held by the strategy, including underlying that `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`) pulled in to back funded *normal* withdraw receipts of other users. Unlike `claimWithdrawRequest`, there is no epoch gating (`epochNumber <= lastWithdrawRequest` check at `IdleCreditVault.sol:326` is absent), so the instant receipt can be claimed in the same transaction it is created.

Compare with the normal flow: `requestWithdraw` + claim paths have per-epoch records (`withdrawsRequestsByEpoch`, `lossRecoveryPriceByEpoch`) and explicit guards preventing a stale-pointer equivalent — `requestWithdraw` reverts if a loss-adjusted receipt is unclaimed (`IdleCreditVault.sol:263-271`). The instant path has none of these protections: the receipt is a pure claim on whatever underlying happens to sit in the strategy at claim time.

### Impact Explanation
Direct theft of other users' funded withdrawals. After `stopEpoch` calls `collectWithdrawFunds`, the strategy holds underlying reserved for funded normal withdraw receipts. An unprivileged tranche holder who can trigger an instant withdraw (APR drop greater than `instantWithdrawAprDelta` between epochs, `IdleCDOEpochVariant.sol:761-768`) can request an instant withdraw and immediately claim it, extracting up to `instantWithdrawsRequests` underlying that economically belongs to prior claimants. The loss is bounded by the funded underlying resident in the strategy minus `defaultRecoveryReserve`. When the real claimants later call `claimWithdrawRequest`, the strategy is insolvent on those receipts, or `_transferFundedClaim` reverts — permanent freezing of their payout.

### Likelihood Explanation
Requires: (a) a non-programmable deployment with instant withdraws enabled (`!disableInstantWithdraw && !isProgrammableBorrower`, `IdleCDOEpochVariant.sol:839-841`), (b) underlying present in the strategy (post-`collectWithdrawFunds` funding window, or partially prefunded instant claims), and (c) an APR decrease exceeding `instantWithdrawAprDelta`, which occurs naturally whenever the honest manager lowers APR at `stopEpoch`. The attacker is a KYC-passed tranche holder, in scope. The bypass is a missing sequencing check, not a privileged action.

### Recommendation
In `claimInstantWithdrawRequest`, only pay out from underlying actually collected for instant claims — e.g., track a `fundedInstantWithdraws` balance incremented in `collectInstantWithdrawFunds` and revert/limit the claim to that amount, mirroring the `epochNumber > lastWithdrawRequest` gating used by `_claimFundedWithdrawRequest`, and decrement `pendingInstantWithdraws` consistently on claim.

### Proof of Concept
Foundry fork scenario:

```solidity
// setup: user1 has a pending normal withdraw receipt; epoch stops and
// collectWithdrawFunds pulls X underlying into the strategy
vm.prank(manager);
cdoEpoch.stopEpoch(expectedApr, expectedInterest); // strategy now holds funded underlying

// attacker is an AA holder; manager set a lower APR for next epoch such that
// lastEpochApr > unscaledApr + instantWithdrawAprDelta
uint256 steal = underlying.balanceOf(address(strategy));
uint256 attackerTranches = AAtranche.balanceOf(attacker);
uint256 amount = steal; // size the request to available underlying

vm.startPrank(attacker);
// request: burns CDO tokens, mints receipt, pendingInstantWithdraws += amt
cdoEpoch.requestWithdraw(amount, address(AAtranche)); // instant path taken
// claim in the SAME tx/epoch: no funding or epoch check
cdoEpoch.claimInstantWithdrawRequest();
vm.stopPrank();

assertEq(underlying.balanceOf(attacker), steal);        // stole user1's funded claim
// user1's claim now reverts or underpays
vm.expectRevert();
vm.prank(user1);
cdoEpoch.claimWithdrawRequest();
```

Caveat: the claim path may route through `getInstantWithdrawFunds` on the CDO side first — I was unable to complete verification of `IdleCDOEpochVariant.sol`'s instant-funding flow within the available iterations. If the CDO atomically collects instant funds inside `requestWithdraw`, the unfunded-claim window narrows but `pendingInstantWithdraws` still not being decremented on claim leaves the funded-vs-recorded bookkeeping inconsistent.
