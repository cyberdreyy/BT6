Based on the investigation, I found a structurally similar bug class in the Agave stake-delegation accounting path, though I was unable to fully confirm one detail (how `use_fixed_point_stake_math` is threaded from the bank's feature snapshot into `upsert_stake_delegation` calls on every stake-account-modifying transaction) before running out of tool calls. I present the finding with that caveat noted explicitly.

### Title
Feature-gated effective-stake math produces inconsistent recomputation of previously-accumulated delegated stake, causing a `.expect()` panic in `Stakes::sub_delegated_stake` / `VoteAccounts::sub_stake` - (File: runtime/src/stakes.rs)

### Summary
`Stakes::upsert_stake_delegation` recomputes both the *new* and the *old* effective stake of a delegation using `delegation_effective_stake`, then diffs them against the cached `delegated_stakes` accumulator via `sub_delegated_stake`/`vote_accounts.sub_stake`, both of which use `checked_sub(...).expect(...)` (panic-on-underflow) rather than saturating arithmetic. [1](#0-0) [2](#0-1) [3](#0-2) 

This mirrors the JPEG'd `H-06` root cause: an accrual/accounting subtraction (`currentBalance - previousBalance`, resp. `delegated_stakes - old_stake`) that assumes the "old" value can be perfectly reconstructed at subtraction time, and reverts/panics hard the moment that assumption is violated by a change to how the underlying value is computed.

### Finding Description
`delegation_effective_stake` dispatches to either the legacy (`Delegation::stake`) or fixed-point (`Delegation::stake_v2`) warmup/cooldown formula based on the boolean `use_fixed_point_stake_math`, which is derived from the feature-set snapshot (`upgrade_bpf_stake_program_to_v5_1`) at call time rather than being pinned to the epoch during which a delegation's contribution was originally accumulated. [4](#0-3) 

`upsert_stake_delegation` is invoked whenever a stake account is modified in a transaction (delegate, deactivate, split, merge, withdraw, redelegate), and it recomputes `old_stake` for the *previously stored* delegation using whatever `use_fixed_point_stake_math` value is passed in for the current call: [5](#0-4) 

If the feature that toggles `use_fixed_point_stake_math` activates at a slot boundary that falls strictly inside an epoch (feature activation slots are not epoch-aligned), then:
- Transactions before the activation slot insert/update a delegation and add its effective stake to `delegated_stakes`/`VoteAccounts` computed with the legacy formula.
- Any subsequent stake-modifying transaction touching the same account (by any unprivileged wallet controlling that stake account) after activation recomputes `old_stake` for that same delegation using the fixed-point formula.
- Because the legacy and fixed-point warmup/cooldown formulas are not guaranteed to produce bit-identical results for identical delegation/epoch/history inputs (that is the entire reason two code paths exist), `old_stake` (new formula) can diverge from what is actually present in the `delegated_stakes` accumulator (added under the old formula).
- `sub_delegated_stake` and `vote_accounts.sub_stake` both use `checked_sub(...).expect(...)`, so if the recomputed `old_stake` exceeds the accumulated value, the subtraction panics instead of saturating. [6](#0-5) [3](#0-2) 

This is the same failure shape as the referenced report: a value that is expected to only be read back consistently (`vault.balanceOfJPEG()` / `delegated_stakes` entry) can be silently recomputed differently after a state-affecting change (`setController` / feature-flag flip), and the difference is not tolerated by the subtraction, converting a normal, expected user operation (withdraw / stake modification) into a hard failure.

### Impact Explanation
Because `sub_delegated_stake`/`sub_stake` panic rather than return an error, the panic occurs inside bank/stakes-cache update logic executed by every validator processing the same transaction deterministically. This is not an isolated single-node crash — every validator that replays the block containing the triggering transaction hits the identical panic, which fits the "transaction-triggered cluster halt" impact category. Unlike a simple stuck-withdraw (as in the original finding, which was a fund-availability bug), a validator process panic during bank commit is more severe: it can crash/halt the runtime thread processing that transaction across the whole cluster.

### Likelihood Explanation
Likelihood is constrained by the fact that the divergence window only exists around a `use_fixed_point_stake_math`-gating feature activation (a one-time, network-wide event at a fixed slot), so it is not perpetually exploitable by an attacker at will — it requires timing a normal stake-modifying transaction against a delegation whose stake was accumulated pre-activation, submitted after activation, and requires the legacy vs. fixed-point formulas to actually disagree for that delegation/epoch/history combination (rounding-sensitive, not guaranteed for every delegation). I was not able to fully verify from the available code whether `use_fixed_point_stake_math` is captured once per bank/epoch versus recomputed fresh from the live feature snapshot on every `upsert_stake_delegation` call site in `bank.rs`, which is the detail that determines whether this divergence window can actually be hit mid-epoch. This uncertainty should be resolved by inspecting the exact call sites in `runtime/src/bank.rs` that pass `use_fixed_point_stake_math` into `stakes.upsert_stake_delegation`/`stakes.remove_stake_delegation`, which I was unable to fully trace before running out of tool iterations.

### Recommendation
- Replace panicking `checked_sub(...).expect(...)` in `Stakes::sub_delegated_stake`, `VoteAccounts::sub_stake`, and `VoteAccounts::do_sub_node_stake` with saturating subtraction, logging a warning/metric on the previously-panicking condition instead of aborting. [2](#0-1) [7](#0-6) 
- Ensure `use_fixed_point_stake_math` (and any other feature-gated parameter feeding `delegation_effective_stake`) is pinned per-epoch (captured once at epoch boundary in `Stakes::activate_epoch`) rather than resolved dynamically per-transaction inside the same epoch, so that the value added and later subtracted for the same delegation is always computed with the same formula.
- Audit other call sites recomputing "old" derived values from feature-gated formulas for the same non-monotonic-diff pattern.

### Proof of Concept
1. Prior to slot `S` (activation slot for the fixed-point stake math feature, located mid-epoch `E`), submit a `DelegateStake`/`Split` transaction for stake account `A`, causing `upsert_stake_delegation` to add `old_effective_stake_legacy(A)` to `delegated_stakes[voter]` and `VoteAccounts` stake for `voter`.
2. Once the feature activates at slot `S` (still within epoch `E`), submit any ordinary stake instruction transaction against `A` (e.g., `Deactivate`, `Split`, `Merge`), which is fully reachable by the account's own authorized signer with no special privilege.
3. This causes `upsert_stake_delegation` to be called again in epoch `E`, but now with `use_fixed_point_stake_math = true`, recomputing `old_stake = delegation_effective_stake(old_delegation, E, history, ..., true)` — using `stake_v2` instead of the legacy `stake` formula used during step 1.
4. If `stake_v2(...)` for `A`'s delegation/epoch/history combination yields a value greater than what was actually recorded in `delegated_stakes[voter]` (rounding divergence between the two warmup/cooldown formulas), `sub_delegated_stake` panics at: [6](#0-5) 
5. Every validator processing this transaction in the same slot hits the identical deterministic panic, since the same feature-activation state and delegation history are used by all nodes replaying the block.

    fn upsert_stake_delegation(
        &mut self,
        stake_pubkey: Pubkey,
        stake_account: StakeAccount,
        new_rate_activation_epoch: Option<Epoch>,
        use_fixed_point_stake_math: bool,
    ) {
        debug_assert_ne!(stake_account.lamports(), 0u64);
        let delegation = stake_account.delegation();
        let voter_pubkey = delegation.voter_pubkey;
        let stake = delegation_effective_stake(
            delegation,
            self.epoch,
            &self.stake_history,
            new_rate_activation_epoch,
            use_fixed_point_stake_math,
        );
        match self.stake_delegations.insert(stake_pubkey, stake_account) {
            None => {
                self.add_delegated_stake(voter_pubkey, stake);
                self.vote_accounts.add_stake(&voter_pubkey, stake);
            }
            Some(old_stake_account) => {
                let old_delegation = old_stake_account.delegation();
                let old_voter_pubkey = old_delegation.voter_pubkey;
                let old_stake = delegation_effective_stake(
                    old_delegation,
                    self.epoch,
                    &self.stake_history,
                    new_rate_activation_epoch,
                    use_fixed_point_stake_math,
                );
                if voter_pubkey != old_voter_pubkey || stake != old_stake {
                    self.sub_delegated_stake(&old_voter_pubkey, old_stake);
                    self.add_delegated_stake(voter_pubkey, stake);
                    self.vote_accounts.sub_stake(&old_voter_pubkey, old_stake);
                    self.vote_accounts.add_stake(&voter_pubkey, stake);
                }
            }
        }
    }

    pub fn sub_stake(&mut self, pubkey: &Pubkey, delta: u64) {
        let vote_accounts = Arc::make_mut(&mut self.vote_accounts);
        if let Some((stake, vote_account)) = vote_accounts.get_mut(pubkey) {
            *stake = stake
                .checked_sub(delta)
                .expect("subtraction value exceeds account's stake");
            let vote_account = vote_account.clone();
            self.sub_node_stake(delta, &vote_account);
        }
    }

    fn add_node_stake(&mut self, stake: u64, vote_account: &VoteAccount) {
        let Some(staked_nodes) = self.staked_nodes.get_mut() else {
            return;
        };

        VoteAccounts::do_add_node_stake(staked_nodes, stake, *vote_account.node_pubkey());
    }

    fn do_add_node_stake(
        staked_nodes: &mut Arc<HashMap<Pubkey, u64>>,
        stake: u64,
        node_pubkey: Pubkey,
    ) {
        if stake == 0u64 {
            return;
        }

        Arc::make_mut(staked_nodes)
            .entry(node_pubkey)
            .and_modify(|s| *s += stake)
            .or_insert(stake);
    }

    fn sub_node_stake(&mut self, stake: u64, vote_account: &VoteAccount) {
        let Some(staked_nodes) = self.staked_nodes.get_mut() else {
            return;
        };

        VoteAccounts::do_sub_node_stake(staked_nodes, stake, vote_account.node_pubkey());
    }

    fn do_sub_node_stake(
        staked_nodes: &mut Arc<HashMap<Pubkey, u64>>,
        stake: u64,
        node_pubkey: &Pubkey,
    ) {
        if stake == 0u64 {
            return;
        }

        let staked_nodes = Arc::make_mut(staked_nodes);
        let current_stake = staked_nodes
            .get_mut(node_pubkey)
            .expect("this should not happen");
        match (*current_stake).cmp(&stake) {
            Ordering::Less => panic!("subtraction value exceeds node's stake"),
            Ordering::Equal => {
                staked_nodes.remove(node_pubkey);
            }
            Ordering::Greater => *current_stake -= stake,
        }
    }

pub(crate) fn delegation_effective_stake<T: StakeHistoryGetEntry>(
