### Title
Unsigned/unauthorized initialization of System Program nonce accounts allows authority hijacking - (File: `programs/system/src/system_instruction.rs`)

### Summary
The `SystemInstruction::InitializeNonceAccount` handler transitions a nonce account from `State::Uninitialized` to `State::Initialized`, permanently setting the `nonce_authority` from unchecked instruction data, without ever requiring the target nonce account (or any other account) to be a transaction signer. Every other nonce-account instruction (`AdvanceNonceAccount`, `WithdrawNonceAccount`, `AuthorizeNonceAccount`) enforces a signer check against either the account key or its stored authority, but `initialize_nonce_account` does not.

### Finding Description
`initialize_nonce_account` only checks that the account is writable and in `State::Uninitialized`, then unconditionally writes the caller-supplied `nonce_authority` into the account state: [1](#0-0) 

The dispatcher in `system_processor.rs` calls this function with no `is_instruction_account_signer` check on account index 0 (the nonce account), unlike other System Program handlers such as `allocate`/`assign`, which explicitly require `address.is_signer(signers)`: [2](#0-1) [3](#0-2) 

For comparison, `withdraw_nonce_account` explicitly requires `check_signer(from.get_key())` even in the `State::Uninitialized` branch, and `advance_nonce_account` requires the stored authority to be a signer: [4](#0-3) [5](#0-4) 

This is the direct analog of the reported Solidity bug: an "initialize" entry point that transitions an account from an uninitialized state and assigns an authority/owner, reachable without any authorization check equivalent to the missing `onlyProxy` modifier.

### Impact Explanation
If a nonce account is created (e.g., via `SystemInstruction::CreateAccount`, funded to the rent-exempt minimum and assigned to the System Program) in a transaction separate from its `InitializeNonceAccount` call — rather than atomically bundled as the CLI helper `create_nonce_account`/`create_nonce_account_with_seed` normally does — any unrelated party can observe the funded, still-`Uninitialized` account on-chain and submit their own `InitializeNonceAccount` instruction naming themselves as `nonce_authority`, without providing any signature tied to that account. Once initialized under the attacker's authority, the attacker can subsequently call `WithdrawNonceAccount` to drain the rent-exempt lamports funded by the legitimate creator, or otherwise control the nonce account (`AdvanceNonceAccount`, re-authorization), constituting concrete unsigned/unauthorized fund control.

### Likelihood Explanation
Exploitation requires only an ordinary, unprivileged transaction and a target account that is funded/allocated by the System Program but not yet initialized as a nonce in the same atomic transaction — a state that can arise whenever nonce-account creation and initialization are not submitted together (e.g., non-atomic client flows, partially-confirmed multi-step setups, or a race between a legitimate initializer and a chain observer). The window depends on client/application behavior rather than protocol enforcement, since nothing in `initialize_nonce_account`/`process_instruction` prevents it.

### Recommendation
Require that `InitializeNonceAccount` include and check a signer for the nonce account (or otherwise bind initialization to the same authority that funded/created the account), mirroring the signer checks already present in `withdraw_nonce_account`'s `State::Uninitialized` branch, so that only the legitimate creator can transition the account out of `State::Uninitialized`.

### Proof of Concept
1. Submit `SystemInstruction::CreateAccount` (or `Allocate`+`Assign`) to create/fund an account owned by `system_program`, sized for `nonce::state::State`, in one transaction — legitimate creator's transaction does not yet include `InitializeNonceAccount`.
2. Before the creator's follow-up `InitializeNonceAccount` transaction lands, an attacker submits a transaction with `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` naming the same nonce account at index 0 (no signature required for that account per `system_processor.rs:448-466`).
3. `initialize_nonce_account` succeeds because the account is `State::Uninitialized` and writable; the account's `nonce_authority` becomes `attacker_pubkey`.
4. Attacker submits `SystemInstruction::WithdrawNonceAccount` signed only by themselves as the stored authority, draining the rent-exempt lamports funded by the original creator.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
