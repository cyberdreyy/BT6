Confirmed: the `Accepted` branch never checks or clears `responded_signers`/`total_weight_rejected` for a signer who previously rejected the same block, and there's no `else` branch decrementing `total_weight_rejected` when a signature arrives from a signer already counted as a rejector.### Title
Stale rejection weight is never cleared when a signer later accepts the same block, corrupting the miner's accept/reject tally - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The report describes an asymmetric refund/accounting bug: one code path (ETH) correctly reverses excess state, while the parallel path (ERC20) silently fails to. The analogous flaw here is in the miner-side `StackerDBListener` message handler that maintains `BlockStatus.total_weight_approved` / `total_weight_rejected`: the `Rejected` branch is guarded against double counting via `responded_signers`, but the `Accepted` branch never "refunds"/clears a signer's prior contribution to `total_weight_rejected` when that same signer subsequently accepts (signs) the block.

### Finding Description
`handle_signer_message` processes `BlockResponse::Rejected` by only tallying weight the first time a signer responds:
`if block.responded_signers.insert(slot_id) { block.total_weight_rejected = ...add signer_entry.weight... }` [1](#0-0) 

For `BlockResponse::Accepted`, the guard instead checks only `gathered_signatures`, not `responded_signers`, and unconditionally adds the signer's weight to `total_weight_approved` with no corresponding subtraction from `total_weight_rejected`:
`if !block.gathered_signatures.contains_key(&slot_id) { block.total_weight_approved = ...add signer_entry.weight... }` followed by `block.gathered_signatures.insert(slot_id, signature); block.responded_signers.insert(slot_id);` [2](#0-1) 

The signer-side state machine explicitly supports a signer re-evaluating a previously rejected proposal and moving to acceptance (`LocallyRejected --> LocallyAccepted: re-evaluated`), and this is exactly mirrored/allowed in the signer's own local `SignerDb` (`reject_then_accept` clears the stored rejection when a signature for the same address/block arrives) [3](#0-2) . But the *miner-side* aggregate tally in `stackerdb_listener.rs` has no equivalent "refund" step: if signer S first rejects (tallied into `total_weight_rejected`) and then legitimately re-evaluates and accepts/signs the same block, its weight is added a second time into `total_weight_approved` while its earlier contribution to `total_weight_rejected` is never removed. `reset_rejections` only clears `total_weight_rejected` on a timeout retry, and explicitly preserves approvals for the opposite reason ("Block approvals cannot be cleared because an old approval could always be used") [4](#0-3) , but there is no symmetric mechanism to remove stale rejection weight when a signer's later, valid acceptance supersedes their own earlier rejection.

This breaks the invariant that `total_weight_approved + total_weight_rejected` should reflect at most one vote per signer's true current weight/intent — a single signer's weight can now be counted simultaneously on both sides of the tally.

### Impact Explanation
`signer_coordinator.rs::get_block_status` uses `total_weight_rejected` to decide when the block should be treated as globally rejected: `if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight { ... return Err(NakamotoNodeError::SignersRejected ...) }` [5](#0-4) . Because a signer who switched from reject to accept still contributes phantom weight to `total_weight_rejected`, the coordinator can conclude the rejection threshold has been crossed (and abandon/exclude the block, or evict transactions via the `failed_txids` logic) even though the real, current set of live rejecting signers is smaller and the true accept threshold may in fact be reachable. This is a liveness wedge on block production for that tenure/proposal: valid blocks can be spuriously treated as rejected due to accounting drift that never self-corrects (short of a full rejection-timeout, which resets rejections but not this root double-count once it recurs on the next round of vote changes).

### Likelihood Explanation
Triggering this requires only one signer that first rejects a proposal and then legitimately reconsiders and signs the same proposal — behavior the signer-side design explicitly permits and expects (`should_reevaluate_block`/`LocallyRejected --> LocallyAccepted`). No majority collusion, no cryptographic break, and no malicious behavior is needed; it can occur from ordinary gossip re-delivery/timing during normal operation whenever a signer's local re-evaluation flips its vote after the miner has already recorded the rejection.

### Recommendation
In the `Accepted` branch of `handle_signer_message`, before adding weight to `total_weight_approved`, check whether the slot previously contributed to `total_weight_rejected` (e.g., track per-signer vote kind, not just `responded_signers`/`gathered_signatures` presence) and subtract that signer's weight from `total_weight_rejected` if so, mirroring the refund/cleanup already done for the signer-local `SignerDb` (`reject_then_accept`). Ensure `total_weight_approved + total_weight_rejected` never double-counts a single signer's weight across both tallies.

### Proof of Concept
1. Miner proposes block B; `insert_block` initializes `BlockStatus{total_weight_approved:0,total_weight_rejected:0,...}` [6](#0-5) .
2. Signer S (weight w) sends `Rejected` for B; coordinator records `responded_signers.insert(S)` → true, `total_weight_rejected += w`.
3. S re-evaluates B (e.g., after a competing proposal it favored becomes stale) and legitimately signs/accepts B, sending `Accepted`.
4. Coordinator's `Accepted` handler checks only `gathered_signatures.contains_key(S)` (false, first signature) → adds `w` to `total_weight_approved`, but never subtracts `w` from `total_weight_rejected`.
5. Now `total_weight_rejected` still includes S's `w` even though S currently approves. If other signers' independent rejections bring `total_weight_rejected + weight_threshold > total_weight`, `get_block_status` returns `SignersRejected` for a block that, counting only current/live votes, would not actually meet the rejection threshold — wedging that block/tenure attempt purely due to stale accounting.

Note: I was not able to directly execute this scenario in a live/test harness (no filesystem/test execution access in this mode); the trace above is derived purely from static code reading of the referenced functions.
