### Title
A single queued deposit permanently reverts `stopEpochWithDuration` and freezes the prefunded credit vault - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The prefunded `IdleCDOEpochVariantPrefunded` variant routes every epoch stop through `_afterStopEpochWithDuration`, which calls `IdleCDOEpochQueue.prefundedDepositsToProcess()`. That view reverts with `NotAllowed` whenever `epochPendingDeposits[epoch] != 0`, i.e. whenever any raw queued deposit is still sitting in the queue. An unprivileged KYC-passing lender can create exactly that state for ~1 wei via `requestDeposit`, after which both `stopEpoch` (blocked by `_beforeStopEpoch` when `epochQueue` is set) and `stopEpochWithDuration` revert, freezing all LP funds until governance intervenes.

### Finding Description
- `IdleCDOEpochQueue.requestDeposit` (`contracts/IdleCDOEpochQueue.sol:103-127`) lets any wallet that passes `_checkAllowed` (epoch running + Keyring KYC) add `amount` to `epochPendingDeposits[nextEpoch]`. For the AA queue on a prefunded variant it only blocks deposits *after* prefunding happened (`epochPrefundedDeposits[nextEpoch] != 0`) or after the configured `prefundedDepositWindow` cutoff.
- `IdleCDOEpochQueue.prefundedDepositsToProcess` (`contracts/IdleCDOEpochQueue.sol:277-282`) returns `epochPrefundedDeposits[_epoch]` but first executes `_checkNotAllowed(epochPendingDeposits[_epoch] != 0)`, deliberately reverting if raw queue deposits remain.
- `IdleCDOEpochVariantPrefunded._afterStopEpochWithDuration` (`contracts/IdleCDOEpochVariantPrefunded.sol:72-89`) calls `prefundedDepositsToProcess()` unconditionally when `epochQueue != 0`, so the whole `stopEpochWithDuration` transaction reverts (line 529 of `IdleCDOEpochVariant.sol`).
- `IdleCDOEpochVariantPrefunded._beforeStopEpoch` (`contracts/IdleCDOEpochVariantPrefunded.sol:39-48`) reverts on the direct `stopEpoch` selector whenever a queue is configured, so there is no alternate stop path.
- The only ways to clear the poisoned state are the attacker calling `deleteRequest` (they won't) or the owner calling `setEpochQueue(0)` (or clearing the queue), which is a privileged recovery, not something the attacker role needs.

Attack sequence (prefunded mode, epoch running):
1. Manager has not prefunded this epoch (`epochPrefundedDeposits[nextEpoch] == 0`), or `prefundedDepositWindow == 0` so deposits are always open.
2. Attacker (KYC'd lender) calls `queue.requestDeposit(1)` → `epochPendingDeposits[nextEpoch] = 1`.
3. If `prefundedDepositWindow != 0`, attacker times the deposit just before the cutoff; once `block.timestamp + window >= epochEndDate`, `processDepositsToBorrower` reverts (line 164) and `requestDeposit` reverts (line 114-117), so the dust can no longer be moved or added to — only the attacker can delete it. With `window == 0`, `processDepositsToBorrower` reverts unconditionally (line 164 `_prefundedWindow == 0`), so the dust is stuck immediately.
4. After `epochEndDate`, every `stopEpoch`/`stopEpochWithDuration` call reverts via `prefundedDepositsToProcess`. The epoch cannot end; the vault stays paused (`isEpochRunning = true` keeps `_beforeUnpause` reverting at `IdleCDOEpochVariant.sol:635-637`), blocking all deposits, withdraw requests, and claims.

### Impact Explanation
Temporary freezing of all pool funds. While the revert persists: no `requestWithdraw`, no `claimWithdrawRequest`, no new deposits, and borrowers/LPs cannot exit — the entire TVL is locked past `epochEndDate`. Recovery requires the owner/manager to rotate `epochQueue` to zero and re-stop, or wait for the attacker to delete the dust request. Cost to the attacker is 1 wei of underlying plus gas; the freeze duration equals the governance reaction time, unbounded in the worst case.

### Likelihood Explanation
Requires only a KYC-passing wallet (explicitly an allowed attacker). The precondition is that the target epoch has no prefunded deposits yet, which holds whenever `prefundedDepositWindow == 0` (the storage default) or before the first `processDepositsToBorrower` call in an epoch. An honest manager can mitigate by prefunding queued deposits before the cutoff, but cannot remove the attacker's dust retroactively once the cutoff passes. The guard itself is intended (the comment says raw pending deposits "must not reach" stop), but it converts a user-creatable state into a halt of the only stop path — the same class as CVE-2017-11683's reachable assertion.

### Recommendation
Do not revert the stop path on leftover queue deposits. Options: (a) have `prefundedDepositsToProcess`/`processPrefundedDeposits` also settle or refund `epochPendingDeposits[_epoch]` (e.g. mint at the same epoch price or return underlyings to requesters) instead of reverting; (b) make `processDepositsToBorrower` callable up to `epochEndDate` regardless of the deposit-subscription cutoff, or permissionlessly sweepable, so dust can always be cleared; (c) allow `deleteRequest` by owner/manager for unprefunded pending deposits. At minimum, keep a non-queue emergency stop path that skips `_afterStopEpochWithDuration` when only raw pending deposits remain.

### Proof of Concept
Foundry fork sketch (setup mirrors `test/foundry/IdleCDOEpochVariantPrefunded.t.sol`):

```solidity
// Prefunded vault deployed with epochQueue set on IdleCDOEpochVariantPrefunded.
// Epoch N is running; attacker is a KYC-passed wallet. No prefunding done this epoch.

// 1) Attacker queues 1 wei while epoch N runs and the subscription window is open
vm.startPrank(attacker);
underlying.approve(address(queue), 1);
queue.requestDeposit(1);               // epochPendingDeposits[N+1] = 1
vm.stopPrank();

// 2) Let the cutoff pass (or window == 0): processDepositsToBorrower can no longer clear it
vm.warp(cdoEpoch.epochEndDate() - queue.prefundedDepositWindow() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
queue.processDepositsToBorrower();     // cutoff reached: dust is locked in the queue

// 3) Epoch ends; every stop path reverts
vm.warp(cdoEpoch.epochEndDate() + 1);
deal(address(underlying), borrower, fundsToRepay);
vm.prank(borrower);
underlying.approve(address(cdoEpoch), fundsToRepay);

vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpochWithDuration(newApr, 0, duration, 0);   // prefundedDepositsToProcess reverts

vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(newApr, 0);                          // blocked by _beforeStopEpoch

// Vault is stuck: isEpochRunning stays true, _beforeUnpause keeps reverting,
// no withdraw requests or claims can be processed until owner rotates epochQueue.
assertTrue(cdoEpoch.isEpochRunning());

// 4) Recovery requires privileged intervention
vm.prank(owner);
cdoEpoch.setEpochQueue(address(0));
vm.prank(manager);
cdoEpoch.stopEpoch(newApr, 0);         // succeeds only after queue is detached
```

Uncertainty note: I could not fully confirm whether `prefundedDepositWindow == 0` is a realistic production configuration (it is the storage default), but the attack also works with a nonzero window by depositing just before the cutoff, and the revert path in `prefundedDepositsToProcess` is unconditional once raw pending deposits exist.
