### Title
Missing role check on `/debug/vars` allows view-role authenticated users to read process runtime variables - (`core/web/router.go`)

### Summary
`debugRoutes` mounts `GET /debug/vars` behind only `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)`, with no `RequiresEditRole`/`RequiresAdminRole`/`RequiresRunRole` wrapper. Any authenticated user, including one with the lowest privilege `UserRoleView`, can call `expvar.Handler()` and read all registered expvar metrics/runtime data.

### Finding Description
`debugRoutes` is defined as:
```go
func debugRoutes(app chainlink.Application, r *gin.RouterGroup) {
	group := r.Group("/debug", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	group.GET("/vars", expvar.Handler())
}
``` [1](#0-0) 

`auth.AuthenticateBySession` only verifies the session cookie is valid and sets the authenticated `clsessions.User` in context; it performs no role comparison at all [2](#0-1) . The role-check functions `RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole` exist and are used pervasively elsewhere in `router.go` (e.g. `authv2.GET("/users", auth.RequiresAdminRole(uc.Index))`) [3](#0-2) , but `debugRoutes` never applies any of them to `/debug/vars`.

Since `expvar.Handler()` is directly registered as the terminal handler for `/debug/vars` with only session authentication in the middleware chain, any user who successfully logs in — including a user provisioned with `clsessions.UserRoleView` — reaches the handler and gets a 200 response containing the full expvar registry (command-line args, memstats, and any custom-registered vars via `expvar.Publish`).

### Impact Explanation
A view-role user (lowest privilege tier, intended only for read-only dashboards) can retrieve internal process runtime state exposed through Go's `expvar` package — memory statistics, GC stats, and any custom metrics the node registers — that is meant to be restricted to privileged debugging use. This is an authorization bypass: the route's access control does not match the intended privilege tier for a debug/diagnostic endpoint, falling under "unauthorized information disclosure due to broken access control" in Chainlink's bounty impact classes. The impact is limited to whatever data is registered in the process's `expvar` map (no direct key/secret exposure is present in the `expvar.Handler()` default output) — no keys, credentials, or the ability to move funds are directly divulged here.

### Likelihood Explanation
Trivial precondition: any account with a valid session cookie, even the lowest `UserRoleView` role, can trigger this. No token forgery, no state manipulation, and no timing dependency — a plain `GET /debug/vars` with a valid session cookie suffices, deterministically reproducible every time.

### Recommendation
Wrap the `/debug/vars` route with an appropriate role-check middleware (e.g. `auth.RequiresAdminRole` or at minimum `auth.RequiresEditRole`), matching the access level intended for debug/diagnostics endpoints, consistent with how `metricRoutes` under `authv2` is comment-labeled "Debug routes accessible via authentication" but still nested under `v2Routes`' broader authenticated group [4](#0-3) .

### Proof of Concept
Go handler-level integration test plan:
1. Build a test `gin.Engine` using `NewRouter` with a fake `chainlink.Application`/`AuthenticationProvider` whose `AuthorizedUserWithSession` returns a `clsessions.User{Role: clsessions.UserRoleView}`.
2. Perform `POST /sessions` (or directly set the session cookie via `sessions.Default`) to establish a valid session for the view-role user.
3. Issue `GET /debug/vars` with that session cookie attached.
4. Assert HTTP status is `200 OK` (not `401`/`403`).
5. Assert the response body is valid JSON matching expvar's output shape (contains keys like `cmdline`, `memstats`) to confirm the handler executed and returned full runtime data to a view-role principal.
6. Compare against a control test on `POST /jobs` (wrapped by `auth.RequiresEditRole`) with the same view-role session, expecting `401 Unauthorized`, to demonstrate the inconsistency in authorization enforcement across routes.

// AuthenticateBySession authenticates the request by the session cookie.

// Implements authMethod
func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}
