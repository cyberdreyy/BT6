### Title
Pre-Auth Rate-Limit Bypass Enables Unlimited Brute-Force Guessing of WebSocket-Proxy API Keys - ([File: crates/infra/websocket-proxy/src/server.rs])

### Summary
The `websocket-proxy` service's authenticated WebSocket routes validate the client-supplied `api_key` path segment **before** any rate limiting is applied. An unauthenticated, anonymous network client can send unlimited HTTP requests to `/ws/{api_key}` with different guessed keys; each invalid-key attempt returns `401 Unauthorized` and costs the attacker nothing, since the per-IP/global rate limiter (`state.rate_limiter.try_acquire`) is only invoked deep inside `websocket_handler`, which is reached only *after* `get_application_for_key` succeeds.

### Finding Description
`authenticated_websocket_handler` and `authenticated_filter_websocket_handler` look up the caller-supplied key with `state.auth.get_application_for_key(&api_key)` and, on failure, immediately return a `401` response — without ever calling into the rate limiter: [1](#0-0) 

The rate limiter (`state.rate_limiter.try_acquire(client_addr)`) is only invoked inside `websocket_handler`, which is called from the `map_or_else` success branch, i.e., only *after* a valid API key has already been matched: [2](#0-1) 

The `Authentication` type does a plain `HashMap` lookup with no throttling, delay, or lockout logic of its own: [3](#0-2) 

This is structurally identical to the reported bug class (CWE-307/CWE-521): a pre-auth endpoint rejects invalid credentials/tokens without any throttling, so weak or short API keys can be brute-forced at network speed. The existing `InMemoryRateLimit` (per-IP/global connection-count limiter in `crates/infra/websocket-proxy/src/rate_limit.rs`) only limits concurrent *open* WebSocket connections — it does not limit the rate of failed-auth HTTP requests, and is bypassed entirely on the `401` path.

### Impact Explanation
If deployed with authentication enabled (`authentication.is_some()` in `Server::listen`), this endpoint is meant to gate access to a metered/paid or trusted WS event feed (flashblocks broadcast, filtered log/tx streams) via per-application API keys. Because failed attempts are unthrottled, an external attacker can brute-force weak/guessable API keys and obtain unauthorized access to the feed — an unauthorized-operation impact (theft of a paid/gated service, exposure of subscription data limited to paying customers, or exhaustion of an app's own connection quota once a key is found and reused by an attacker to open many connections attributed to the victim app). This is a Medium-severity authorization-bypass-via-brute-force issue, matching the analog report's severity.

### Likelihood Explanation
The `/ws/{api_key}` route is directly reachable by any anonymous network client (no L1/L2 transaction or special privilege required), and each failed guess is a cheap, stateless HTTP request; nothing in the code path throttles repeated 401 responses. Likelihood is High for any deployment using shorter or lower-entropy API keys; it's inherent to the current code regardless of key strength since there's no defense-in-depth throttle on invalid attempts.

### Recommendation
Apply the per-IP rate limiter (or a dedicated stricter auth-failure limiter) to the authentication check itself, before or regardless of key-validity, e.g. call `state.rate_limiter.try_acquire(client_addr)` (or a separate lower-quota "auth attempt" limiter) at the top of `authenticated_websocket_handler` / `authenticated_filter_websocket_handler`, and increment/consume it on every 401. Consider also using constant-time comparison for the key lookup and enforcing minimum API key entropy/length at generation time.

### Proof of Concept
1. Deploy `websocket-proxy` with `Authentication::new(...)` configured (auth enabled).
2. From an external client, repeatedly send WebSocket upgrade requests to `GET /ws/<guess>` for a large space of guessed API keys (e.g., short alphanumeric strings), observing `401 Unauthorized` with no increasing latency or rejection based on request rate.
3. Because `state.rate_limiter.try_acquire` is never reached on the invalid-key path [4](#0-3) , the attacker can issue guesses as fast as the network/CPU allows until a valid key is found, at which point `websocket_handler` is invoked and a connection under the victim application's identity is established [5](#0-4) .

async fn authenticated_websocket_handler(
    State(state): State<ServerState>,
    ws: WebSocketUpgrade,
    ConnectInfo(addr): ConnectInfo<SocketAddr>,
    headers: HeaderMap,
    Path(api_key): Path<String>,
) -> impl IntoResponse {
    let application = state.auth.get_application_for_key(&api_key).cloned();

    application.map_or_else(
        || {
            Metrics::unauthorized_requests().increment(1);

            Response::builder()
                .status(StatusCode::UNAUTHORIZED)
                .body(Body::from(json!({"message": "Invalid API key"}).to_string()))
                .unwrap()
        },
        |app| {
            Metrics::connections_by_app(app).increment(1);
            websocket_handler(state, ws, addr, headers, FilterType::None)
        },
    )
}

fn websocket_handler(
    state: ServerState,
    ws: WebSocketUpgrade,
    addr: SocketAddr,
    headers: HeaderMap,
    filter: FilterType,
) -> Response {
    let connect_addr = addr.ip();
    let client_addr = state.trusted_proxy_config.client_ip(connect_addr, &headers);

    let ticket = match state.rate_limiter.try_acquire(client_addr) {
        Ok(ticket) => ticket,
        Err(RateLimitError::Limit { reason, limit_type }) => {
            match limit_type {
                RateLimitType::PerIp => {
                    info!(
                        message = "per-IP rate limit exceeded",
                        client_ip = client_addr.to_string(),
                        reason = reason
                    );
                    Metrics::per_ip_rate_limited_requests().increment(1);
                }
                RateLimitType::Global => {
                    Metrics::global_rate_limited_requests().increment(1);
                }
            }

            return Response::builder()
                .status(StatusCode::TOO_MANY_REQUESTS)
                .body(Body::from(json!({"message": reason}).to_string()))
                .unwrap();
        }
    };
