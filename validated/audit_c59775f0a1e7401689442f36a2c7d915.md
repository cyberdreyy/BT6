### Title
Pending withdraw receipts escape the BB-first loss waterfall — BB holders can dodge epoch losses by requesting withdraw before `stopEpochWithDuration` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is "exit early at a fixed penalty to dodge a larger impending penalty." The idle-tranches analog lives in the loss-splitting path of `stopEpochWithDuration`. When a loss is realized at epoch stop, `previewLossAdjustedWithdrawFunds` assigns pending withdraw receipts only a **pro-rata** share of the loss (`pendingLoss = _lossAmount * pendingBasis / totalBasis`), while the residual `activeLoss` is applied to active positions through the ordinary **BB-first** tranche waterfall via `burnStrategyTokens` + `_forceUpdateAccounting` [1](#0-0) [2](#0-1) . A BB (junior/first-loss) tranche holder who expects a loss at the next epoch stop can therefore call `requestWithdraw` during the open-request window to convert a junior claim — which would absorb the loss up to 100% — into a tranche-agnostic pending receipt that only absorbs a diluted pro-rata share. The escaped loss is pushed onto the remaining BB holders and, once BB NAV is exhausted, onto AA (senior) holders who were supposed to be protected.

### Finding Description
- `requestWithdraw` in `IdleCreditVault` burns the CDO's strategy tokens and mints the user a receipt; pending receipts have no tranche identity and join the aggregate `pendingWithdraws` bucket [3](#0-2) .
- At stop, `_stopEpoch` calls `previewLossAdjustedWithdrawFunds(_lossAmount)`, which splits the loss pro rata between `pendingBasis` and `activeBasis` — no BB-first ordering is applied to the pending bucket [4](#0-3) [5](#0-4) .
- The remaining `activeLoss` is then realized by `burnStrategyTokens` + `_forceUpdateAccounting`, i.e. the ordinary waterfall where BB absorbs losses before AA [2](#0-1) .
- Result: identical claim size, different loss treatment depending solely on whether the user requested withdraw before the stop. For a loss `L ≤ BB NAV`, an active BB holder bears `L`; the same position as a pending receipt bears only `L * userShare / (activeBasis + pendingBasis)`.
- The existing guard at `requestWithdraw` (revert if a previous loss-adjusted receipt at `lossRecoveryPriceByEpoch` is unclaimed) only blocks *repeat* requests, not the first escape [6](#0-5) .

### Impact Explanation
Direct value extraction at other LPs' expense. Quantified example: pool with 90 AA + 10 BB, attacker holds 5 BB. Manager stops the epoch with `_lossAmount = 5`. If the attacker stays active, BB takes the full 5 (attacker loses 2.5). If the attacker pre-requests a withdraw of their 5 BB, `pendingBasis = 5`, `totalBasis ≈ 100`, so the receipt loses only `5 * 5/100 = 0.25`; the remaining 4.75 loss hits the active side, which now has only 5 BB NAV — wiping out the other BB holder almost entirely and/or leaking into AA. Every epoch with an announced/foreseeable loss (the loss amount is a manager-supplied parameter, visible in mempool or inferable from borrower distress) is exploitable by whichever junior holder requests first — a gas-race to the exit, mirroring the QA-penalty dodge.

### Likelihood Explanation
Requires only: (a) `allowBBWithdrawRequest` open during a buffer/running window, (b) knowledge that a loss will be applied at the next `stopEpochWithDuration` — which is realistic because losses correspond to observable borrower shortfalls/write-offs, and the stop call itself is a public transaction that can be front-run. The attacker is an ordinary KYC'd BB lender; no privileged collusion needed. Manager/owner remain honest — the attacker merely sequences `requestWithdraw` before their `stopEpochWithDuration` call.

### Recommendation
Preserve tranche identity for pending receipts (e.g., `pendingWithdrawsAA`/`pendingWithdrawsBB`) and apply the pending-side loss BB-first, or equivalently apply the waterfall *before* moving requests into the pending bucket — i.e., haircut pending receipts by the same tranche-specific loss factor their original position would have suffered. Alternatively, gate new withdraw requests once a loss realization is scheduled, analogous to enforcing the unstake cooldown in the original report.

```solidity
function testBBHolderDodgesLossViaWithdrawRequest() external {
  // honest LPs: 90 AA (attacker has none), 10 BB split 5 attacker / 5 victim
  _depositWithUser(aaUser, 90 * ONE_SCALE, true);   // AA
  _depositWithUser(bbAttacker, 5 * ONE_SCALE, false);
  _depositWithUser(bbVictim,   5 * ONE_SCALE, false);

  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, apr, _expectedFundsEndEpoch()); // buffer opens requests

  // attacker converts junior claim to pending receipt BEFORE loss stop
  uint256 attackerTranche = IERC20Detailed(address(BBtranche)).balanceOf(bbAttacker);
  vm.prank(bbAttacker);
  cdoEpoch.requestWithdraw(attackerTranche, address(BBtranche));

  // manager stops next epoch with realized loss of 5
  _startEpochAndCheckPrices(1);
  vm.prank(manager);
  cdoEpoch.stopEpochWithDuration(newApr, 0, epochDuration, 5 * ONE_SCALE);

  // attacker claim loses only ~pro-rata share (~0.25) instead of 2.5 BB-first
  // assert attackerClaim > attackerBasis - proRataShare + epsilon
  // assert BB tranche price / victim claim absorbed ~4.75 loss
}
```

Uncertain items I could not fully verify within the search budget: the exact gating of `allowBBWithdrawRequest` during the buffer window (it is re-enabled post-stop at lines 478-483 and unset on default), and whether pending receipts also pick up next-epoch interest that partially offsets the haircut. Neither changes the core asymmetry: pending receipts are never exposed to BB-first ordering, and that ordering is the only thing protecting AA holders.

```text
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
  }
```
