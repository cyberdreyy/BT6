### Title
Unbounded `Cleanup.Run` invoked with `context.Background()` allows attacker-controlled repo content to hang cleanup indefinitely - ([File: functions/concrete/run/runner.go])

### Summary
`(*Runner).cleanup` deliberately detaches cleanup from the job's cancellable/timeout context by calling `r.config.Cleanup.Run(context.Background(), r.env)`. Since `stages.Cleanup.Run` shells out to `git` (via `cleanBuildDirectory`) using attacker-influenced repository state (`.gitmodules`, submodule URLs, git hooks, `.git/config`), a pipeline author can craft repo content that makes those `git` subprocesses block forever, and because the context is `context.Background()`, nothing ever cancels them. [1](#0-0) 

### Finding Description
`Run` derives `jobCtx` with the configured job timeout and always calls `defer r.cleanup()`, but `cleanup()` explicitly swaps in a fresh `context.Background()` rather than reusing `jobCtx` (even in its already-expired/canceled form) or deriving a bounded cleanup-specific context: [2](#0-1) [3](#0-2) 

`stages.Cleanup.Run` (when `EnableJobCleanup` is set) calls `cleanBuildDirectory`, which for `git_strategy: fetch` runs `git clean`, `git reset --hard`, and, when submodules are configured, `git submodule foreach ... git reset --hard` recursively over every submodule: [4](#0-3) 

All of these `git(ctx, e, nil, ...)` invocations receive the passed-in `ctx`, which by the time it reaches this code is the unbounded `context.Background()` from `cleanup()`. A pipeline author fully controls the repository fetched by the job (its own project), including `.gitmodules` entries, submodule remote URLs, and git config/hooks committed into the repo during `get_sources`. Known git behaviors that can cause `git` subprocesses to block indefinitely include:
- A submodule URL pointing at a host that accepts a TCP connection but never responds/completes the git protocol handshake (a slow-loris style endpoint), causing `git submodule foreach ... git reset --hard` (or the underlying fetch triggered as part of submodule initialization/foreach) to hang without a network timeout.
- A malicious `credential.helper` or other git config value that spawns an interactive/blocking helper process expecting stdin input that is never supplied.

Because `context.Background()` has no deadline and is never canceled, none of the timeout/cancellation machinery that protects every other stage (`withTimeout`, `ScriptTimeout`, `AfterScriptTimeout`, job `Timeout`) applies to cleanup. The `Cleanup` stage runs *after* the job's own timeout/cancellation has already fired, so the very deadline that was supposed to bound total job execution time no longer bounds this final stage.

### Impact Explanation
A malicious pipeline author can cause the `cleanup()` call (and its underlying `git` subprocess) to hang forever, leaking a goroutine and a subprocess for the lifetime of the Runner process. Since `Run` blocks on `defer r.cleanup()` before returning, the corresponding job-execution goroutine/worker slot is also never released. Repeated malicious jobs (each parked in the concurrent job pool) can exhaust the Runner's configured concurrency slots or process/goroutine/file-descriptor limits, denying service to other jobs scheduled on that Runner. This is a resource-exhaustion / availability impact scoped to the Runner host, not a sandbox escape or cross-job data leak.

### Likelihood Explanation
Preconditions are modest: `enable_job_cleanup` must be true (this is the default/typical `GIT_STRATEGY`-driven cleanup behavior configured by the Runner operator) and `git_strategy: fetch` with submodules, or a hook/credential-helper based mechanism. A pipeline author only needs push access to a project the Runner will build — a routine, unprivileged capability. The attack is repeatable on every job run and does not require any GitLab-admin or Runner-admin compromise.

### Recommendation
Derive the cleanup context from a bounded, non-background context instead of `context.Background()`, e.g. `context.WithTimeout(context.Background(), cleanupTimeout)`, so `Cleanup.Run`'s `git` invocations always terminate. Additionally, propagate this context (with a cancel timeout) into every `git(ctx, ...)` call inside `stages/cleanup.go`, and consider setting `GIT_TERMINAL_PROMPT=0` / disabling credential helpers for cleanup-time git invocations to remove interactive-hang vectors.

### Proof of Concept
Go integration test outline:
1. Create a temp working dir with a git repo containing a `.gitmodules` file referencing a submodule URL pointing to a TCP listener that accepts connections but never writes/closes (simulating a hung remote).
2. Configure `stages.Cleanup{GitStrategy: "fetch", SubmoduleStrategy: "normal", EnableJobCleanup: true}`.
3. Call `cleanup.Run(context.Background(), env)` (mirroring `(*Runner).cleanup`) in a goroutine, and assert via `select` with a short test-level timeout (e.g., 5s) that the call has NOT returned — proving it hangs unbounded.
4. Repeat by calling `cleanup.Run` with a `context.WithTimeout(..., 5*time.Second)` derived context and assert it *does* return within the timeout, demonstrating the fix's expected behavior contrast.

func (r *Runner) Run(ctx context.Context) error {
	jobCtx, jobCancel := r.withTimeout(ctx, r.config.Timeout)
	defer jobCancel()
	defer r.cleanup()

	// Before user scripts, Cancel() cancels the entire job.
	r.setCancel(jobCancel)

	if err := r.setupGitlabEnv(); err != nil {
		return fmt.Errorf("setting up GITLAB_ENV: %w", err)
	}

	if err := r.config.GetSources.SetupJobGitConfig(jobCtx, r.env); err != nil {
		return fmt.Errorf("setting up job git config: %w", err)
	}

	if err := r.prepare(jobCtx); err != nil {
		return err
	}

	scriptErr := r.executeSteps(jobCtx)
	cacheErr, artifactErr := r.finalize(jobCtx)

	return pickPriorityError(scriptErr, cacheErr, artifactErr)
}

func (r *Runner) cleanup() {
	if err := r.config.Cleanup.Run(context.Background(), r.env); err != nil {
		r.logWarningf("Cleanup failed: %v", err)
	}

	if r.env.GitLabEnvFile != "" {
		os.Remove(r.env.GitLabEnvFile)
	}

	r.config.GetSources.TeardownJobGitConfig(r.env)
}

func (s Cleanup) cleanBuildDirectory(ctx context.Context, e *env.Env) {
	projectDir := e.WorkingDir

	switch s.GitStrategy {
	case gitStrategyClone, gitStrategyEmpty:
		_ = os.RemoveAll(projectDir)

	case gitStrategyFetch:
		if len(s.GitCleanFlags) > 0 {
			_ = git(ctx, e, nil, append([]string{"clean"}, s.GitCleanFlags...)...)
		}

		_ = git(ctx, e, nil, "reset", "--hard")

		if s.hasSubmodules() {
			foreachArgs := []string{"submodule", "foreach"}
			if s.SubmoduleStrategy == submoduleStrategyRecursive {
				foreachArgs = append(foreachArgs, "--recursive")
			}
			foreachArgs = slices.Clip(foreachArgs)

			if len(s.GitCleanFlags) > 0 {
				cleanArgs := append([]string{"git", "clean"}, s.GitCleanFlags...)
				_ = git(ctx, e, nil, append(foreachArgs, cleanArgs...)...)
			}

			_ = git(ctx, e, nil, append(foreachArgs, "git", "reset", "--hard")...)
		}

	case gitStrategyNone:
		e.Noticef("Skipping build directory cleanup step")
	}
