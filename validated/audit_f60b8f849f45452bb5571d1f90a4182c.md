### Title
Multisig executes requests using confirmations from already-removed members - (File: multisig2/src/lib.rs)

### Summary
`delete_member` only purges the pending *requests originated by* the removed member, but never scrubs that member's *confirmations* recorded on other still-pending requests. Because `confirm()` only compares the raw confirmation-set size to `num_confirmations`, a stale confirmation cast by a member before their removal still counts toward the threshold, letting a request execute with fewer than `num_confirmations` currently-authorized (live) members having approved it.

### Finding Description
`confirm()` decides whether to execute a request purely by counting entries in the `confirmations: HashSet<String>` for that `request_id`: [1](#0-0) 

The set is only cleaned up in two places: `remove_request` (after successful execution) and `delete_member`. `delete_member` removes only the requests that were *created by* (`r.member == member`) the member being deleted; it does not scan `self.confirmations` for entries where the removed member had *confirmed* (but not created) some other still-open request: [2](#0-1) 

Since confirmations are stored simply as `member.to_string()` inside a `HashSet<String>`, with no link back to whether that member is still in `self.members`, a confirmation made by a member who is later removed remains valid forever for any request they didn't personally author. The `current_member()` check is only enforced at the moment `confirm()` is called - it is never re-validated for confirmations that are already stored.

**Binding broken:** `confirmations counted` (raw historical set of strings) vs. `live members` (`self.members`, the actual K-of-N trust set) - a confirmation is no longer tied to membership once cast.

### Impact Explanation
This directly breaks the multisig's core authorization guarantee: "a request only executes once `num_confirmations` distinct *current* members approve it." An attacker (or even benign operational sequence) can cause a `Transfer`, `AddKey`, `FunctionCall`, or `AddMember` action to execute with fewer than `num_confirmations` live approvals, because a removed member's stale confirmation is silently counted. This is exactly the Critical-tier impact category "a multisig request executed below threshold" - it can lead to unauthorized transfer of NEAR, addition of a rogue full-access key, or arbitrary function calls signed off by an insufficient, partially-stale quorum.

### Likelihood Explanation
This requires no attacker-controlled deployment parameters and no privileged foundation/owner action beyond the multisig's own normal `DeleteMember` operation, which is a documented, expected lifecycle event (e.g., offboarding a member). Any multisig that rotates membership while requests are pending (a realistic, even routine, operational scenario) is exposed. No special timing tricks or races are needed beyond ordinary multi-step multisig usage.

### Recommendation
When executing `DeleteMember`, iterate over all entries in `self.confirmations` (not only `self.requests` filtered by request originator) and remove the deleted member's string from every confirmation set, or alternatively, when checking `confirm()`'s reached-threshold condition, intersect stored confirmations with `self.members` (current live set) before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig configured with `members = {A, B, C}`, `num_confirmations = 2`.
2. `A.add_request(R1)` (e.g., `Transfer` to attacker-controlled account) → `confirmations[R1] = {}`.
3. `B.confirm(R1)` → `confirmations[R1] = {B}` (1 < 2, not yet executed).
4. Separately, `C.add_request_and_confirm(R2 = DeleteMember{B})`, then `A.confirm(R2)` → reaches 2 confirmations, `R2` executes: `B` is removed from `self.members` and `B`'s access key deleted via `delete_member` (multisig2/src/lib.rs:356-379). Note `R1` was created by `A`, not `B`, so it is untouched by the request-purge loop, and `confirmations[R1]` still contains `"B"`.
5. `A.confirm(R1)` → `confirmations[R1].len() + 1 = 2 >= num_confirmations(2)` → `R1` executes (multisig2/src/lib.rs:304-309), transferring funds, even though only one currently-live member (`A`) actually approved it after `B`'s removal. [3](#0-2) [4](#0-3) 

**Uncertainty note:** I was unable to inspect the analogous `delete_key`/removal path in the older `multisig/src/lib.rs` contract before the tool budget ran out, so I cannot confirm whether the same gap exists there; the finding above is fully verified against `multisig2/src/lib.rs`.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
