### Title
Underflow panic in `RewardCycleInfo::is_in_next_prepare_phase` can wedge a signer's next-cycle configuration - ([File: stacks-signer/src/runloop.rs])

### Summary
`RewardCycleInfo::is_in_next_prepare_phase` computes `burnchain_block_height - self.first_burnchain_block_height` using a raw, unchecked subtraction, unlike its sibling methods `is_in_reward_cycle` and `get_reward_cycle` on the same struct, which both explicitly use `saturating_sub` for the identical computation.

### Finding Description
`RewardCycleInfo` in `stacks-signer/src/runloop.rs` caches `first_burnchain_block_height` at initialization/refresh time [1](#0-0) . Two of its three height-normalizing helpers guard the subtraction with `saturating_sub` to avoid underflow:

```
pub const fn is_in_reward_cycle(&self, burnchain_block_height: u64) -> bool {
    let blocks_mined = burnchain_block_height.saturating_sub(self.first_burnchain_block_height);
    ...
pub const fn get_reward_cycle(&self, burnchain_block_height: u64) -> u64 {
    let blocks_mined = burnchain_block_height.saturating_sub(self.first_burnchain_block_height);
``` [2](#0-1) 

But `is_in_next_prepare_phase` uses a bare `-`:
```
pub fn is_in_next_prepare_phase(&self, burnchain_block_height: u64) -> bool {
    let effective_height = burnchain_block_height - self.first_burnchain_block_height;
``` [3](#0-2) 

This is directly analogous to the WatchPug `newRatio = a - b` underflow: a subtraction that is safe (saturating/clamped) everywhere else in the same struct except in this one code path, where a value derived from an externally-observed chain height (`current_burn_block_height`, itself `max(node peer-info height, event height)`) can, in principle, be smaller than the signer's cached `first_burnchain_block_height` — e.g., across a bitcoin reorg/rollback that the connected node reports, or a state refresh race where `refresh_runloop` recomputes `RewardCycleInfo` with a `first_burnchain_block_height` that is momentarily inconsistent with the burn height being evaluated [4](#0-3) . In a Rust build with debug-assertions/overflow-checks enabled (the default for debug builds, and commonly enabled by fuzzers/tests), this subtraction panics; in a release build without overflow checks it silently wraps to a huge `u64`, producing a bogus `reward_index` that will never satisfy `reward_index >= (reward_cycle_length - prepare_phase_block_length)`, so `is_in_next_prepare_phase` always incorrectly reports `false`.

The consequence maps directly onto `refresh_runloop`: `is_in_next_prepare_phase` gates whether the signer proactively configures itself for the *next* reward cycle before it starts:
```
if is_in_next_prepare_phase
    && !Self::is_configured_for_cycle(&self.stacks_signers, next_reward_cycle)
{
    self.refresh_signer_config(next_reward_cycle);
}
``` [5](#0-4) 
A panic here crashes the signer's runloop thread entirely (denial of liveness for that signer), and a silent wrap causes the signer to never register/configure itself for the upcoming reward cycle in time, meaning it enters the new cycle unregistered and cannot sign valid blocks for it until manually restarted or until a subsequent refresh recovers.

### Impact Explanation
This falls under the High-impact category: "a signer wedged into never signing valid blocks... or acting on a stale reward set/threshold." A panic in the runloop thread stops the signer process from evaluating any further burn events, and a silent underflow-wrap causes the signer to skip registering for the next reward cycle's signer set, both of which are liveness failures for an individual signer that require no cooperation from a majority of signers, node auth token, or another signer's key — only a state where the observed/cached burn height briefly regresses below the cached `first_burnchain_block_height`.

### Likelihood Explanation
The precondition (burnchain height reported as less than the cached `first_burnchain_block_height`) is narrow — it requires a burnchain reorg/rollback or a race in `refresh_runloop`'s recomputation of `RewardCycleInfo` between when `first_burnchain_block_height` is captured and when a stale/lower height is fed into `is_in_next_prepare_phase`. This is plausible but not trivially reproducible from the code alone; the exact triggering scenario (e.g., a bitcoind reorg reducing the reported header height, or an out-of-order event delivery) is not directly proven in this repo slice, and I could not fully trace every caller of `RewardCycleInfo` construction/refresh to confirm a concrete adversarial trigger path within the scope of this review.

### Recommendation
Change `is_in_next_prepare_phase` to use `saturating_sub` (or `checked_sub` with an explicit `false`/error fallback) exactly as `is_in_reward_cycle` and `get_reward_cycle` already do, to make the subtraction consistent and panic/wrap-proof:
```rust
pub fn is_in_next_prepare_phase(&self, burnchain_block_height: u64) -> bool {
    let effective_height = burnchain_block_height.saturating_sub(self.first_burnchain_block_height);
    ...
}
```

### Proof of Concept
No concrete external trigger was verified within the scope of the reviewed files; the finding is based on static code inspection showing the inconsistency between `is_in_next_prepare_phase`'s unchecked subtraction and its sibling methods' `saturating_sub` guards [6](#0-5) , plus the call site in `refresh_runloop` where `current_burn_block_height` is derived from live node/event data that is not proven to always be `>= first_burnchain_block_height` at call time [4](#0-3) .

impl RewardCycleInfo {
    /// Check if the provided burnchain block height is part of the reward cycle
    pub const fn is_in_reward_cycle(&self, burnchain_block_height: u64) -> bool {
        let blocks_mined = burnchain_block_height.saturating_sub(self.first_burnchain_block_height);
        let reward_cycle = blocks_mined / self.reward_cycle_length;
        self.reward_cycle == reward_cycle
    }

    /// Get the reward cycle for a specific burnchain block height
    pub const fn get_reward_cycle(&self, burnchain_block_height: u64) -> u64 {
        let blocks_mined = burnchain_block_height.saturating_sub(self.first_burnchain_block_height);
        blocks_mined / self.reward_cycle_length
    }

    /// Check if the provided burnchain block height is in the prepare phase of the next cycle
    pub fn is_in_next_prepare_phase(&self, burnchain_block_height: u64) -> bool {
        let effective_height = burnchain_block_height - self.first_burnchain_block_height;
        let reward_index = effective_height % self.reward_cycle_length;

        reward_index >= (self.reward_cycle_length - self.prepare_phase_block_length)
            && self.get_reward_cycle(burnchain_block_height) == self.reward_cycle
    }
