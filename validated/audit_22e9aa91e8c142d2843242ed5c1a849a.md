### Title
Stale confirmations from removed multisig members are still counted toward execution threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
The Symmio report's root cause is that a privileged action was authorized using stale, unrevalidated state (residual open positions) instead of re-checking the caller's *current* authorization status at the time of the privileged call. The same class of bug is present in this repository's multisig contracts: `confirm()` executes a request purely by counting entries in the `confirmations` set, without re-validating that every account/key whose confirmation is counted is still a live member at execution time. `delete_member`/`DeleteKey` purges only the confirmations tied to requests where the removed member was the **creator** (`r.member == member` / `r.signer_pk == pk`), not confirmations they cast on other members' still-pending requests.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` at [1](#0-0)  executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations`, purely based on the size of the stored `HashSet<String>` of past confirmations — it never re-checks that each entry in that set still corresponds to a member returned by `self.members.contains(...)`.

`delete_member()` at [2](#0-1)  only clears confirmations for requests where the removed member is the request **creator** (`r.member == member`). It does not scan the `confirmations` sets of *other* pending requests to strip out a signature previously cast by the now-removed member.

Concretely: member M confirms a pending `Transfer` request created by another member (so M's confirmation string is stored in that request's `confirmations` set, but M is not the `member` field of the `MultiSigRequestWithSigner`, so `delete_member` will not touch it). M is later removed from the multisig (e.g., because they were compromised or acting maliciously) via a separate `DeleteMember` request. The original `Transfer` request still counts M's earlier confirmation. When enough of the remaining live members later confirm, `confirmations.len() + 1 >= num_confirmations` can be satisfied using M's stale confirmation as one of the "votes," even though M is no longer an authorized signer. The binding that should hold — `confirmations counted == confirmations from currently live members` — is broken; a state entry recorded before removal is treated as equivalent to an authorization from a still-trusted party.

The identical pattern exists in the legacy `multisig/src/lib.rs`: `confirm()` at [3](#0-2)  and `DeleteKey` handling at [4](#0-3) , which likewise only purges confirmations for requests *created* by the deleted key, not confirmations that key cast on other pending requests.

### Impact Explanation
This allows a `MultiSigRequestAction::Transfer` (or `FunctionCall`, `AddKey`, `DeployContract`, etc.) to be executed with fewer than `num_confirmations` **currently valid** signers, because one "vote" is a leftover confirmation from a member/key that has since been revoked. This falls under Critical impact: a multisig request executed below the true, live threshold, enabling unauthorized movement of NEAR funds held by the multisig account.

### Likelihood Explanation
This requires no privileged access from the attacker beyond having been a legitimate member at some point and having confirmed a request before being removed — a realistic scenario when a member is removed specifically because they are compromised or acting maliciously (the very case where their earlier confirmation should be least trusted). Any k-of-n multisig where members are periodically rotated is exposed by default; there is no explicit guard preventing it.

### Recommendation
When executing a request in `confirm()`, revalidate that every entry in the request's `confirmations` set still satisfies `self.members.contains(...)` before counting it toward `num_confirmations` (or discard the confirmation set entirely as invalid the moment the member set changes, requiring fresh confirmations). Alternatively, in `delete_member`/`DeleteKey`, iterate over **all** pending requests' confirmation sets (not just requests they authored) and strip out the removed member's confirmation from each.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]` and `num_confirmations = 2`.
2. `C` creates a `Transfer` request (`add_request`); `B` calls `confirm(request_id)` — one confirmation recorded, request not yet executed (`1 < 2`).
3. `A` and `C` submit and confirm a separate `DeleteMember { member: B }` request (2-of-3), executing `delete_member` per [2](#0-1) . Because `B` did not create the `Transfer` request, its confirmation set is untouched; `B` is removed from `self.members` and its access key deleted.
4. `A` calls `confirm(request_id)` on the original `Transfer` request. `confirmations.len() as u32 + 1 = 2 >= num_confirmations (2)`, so `execute_request` runs the `Transfer`, even though `B` (whose vote is one of the two counted) is no longer a member — the transfer executes with only one genuinely live confirming member (`A`), not two.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
