### Title
Confirmations from Deleted Multisig Members Remain Counted Toward the K-of-N Threshold on Other Pending Requests - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` in `multisig2/src/lib.rs` only purges confirmation state for requests that the removed member *originated* (was the `signer`/`member` of), not for requests the removed member had already *confirmed* as a co-signer. As a result, a stale confirmation from an account that is no longer a live member of the multisig continues to count toward `num_confirmations` on any other pending request, allowing that request to execute with fewer genuinely-live approving members than the configured threshold requires.

### Finding Description
`confirm()` counts entries in the per-request `confirmations: HashSet<String>` against `self.num_confirmations` and executes the request once the count is reached: [1](#0-0) 

`delete_member()` removes the member from the live `members` set and deletes access keys, but when cleaning up stale confirmation state it only scans `self.requests` for entries where the request's *originating signer* (`r.member`) equals the member being deleted — it does not scan or purge the `confirmations` set of every other outstanding request that this member may have already confirmed as a co-signer: [2](#0-1) 

Concretely:
1. Member `X` (one of `N` live members, `K` confirmations required) confirms request `R1` (e.g. a `Transfer` action) via `confirm(R1)`. Since `K > 1`, `R1` stays pending with `X`'s confirmation stored under `confirmations[R1]`.
2. Later, the multisig legitimately executes a `DeleteMember { member: X }` request, removing `X` from `members` and revoking their key. `delete_member` only cleans up requests *signed* by `X` (i.e., ones `X` created), leaving `confirmations[R1]` untouched — `X`'s stale confirmation for `R1` is still present.
3. The remaining live members continue confirming `R1`. When the confirmation count (which still includes `X`'s stale entry) reaches `K`, `confirm()` executes `R1` via `execute_request`, even though only `K-1` (or fewer) *currently live* members actually approved it.

This breaks the intended custody/authorization binding of the multisig: `confirmations.len() >= num_confirmations` is checked, but this is supposed to be equivalent to "at least `num_confirmations` *live* members approved." Because a removed member's vote persists, `live_confirmations < num_confirmations` while the check still passes, letting a request execute below the actual approval threshold.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." A `Transfer`, `FunctionCall`, `AddKey`/`AddMember`/`DeleteMember` or `DeployContract` action can be pushed through with effectively fewer live approvers than the multisig's configured `K`, undermining the fundamental security guarantee of the K-of-N scheme (funds move, or control of the account is transferred, without the required number of currently-authorized approvers).

### Likelihood Explanation
The precondition (a member confirms a request, is later removed, and other pending confirmations accumulate to threshold using the stale vote) is a normal operational sequence for any multisig that rotates members — it does not require an external unprivileged attacker to break in, but it is a genuine contract defect reachable through ordinary, documented usage (`confirm`, `add_request`, `DeleteMember`) with no special privileges beyond being an existing member, and no reliance on foundation/owner misbehavior or a redeploy. Any team that rotates keys/members while requests are in flight is exposed.

### Recommendation
In `delete_member`, in addition to purging requests originated by the removed member, iterate over `self.confirmations` for all pending requests and remove the deleted member's confirmation entry (`member.to_string()`) from each set. Optionally, after removing a stale confirmation, re-validate that the request no longer meets the threshold (no action needed since removal only decreases the count, but ensure no other member's `confirm()` inadvertently double-counts). This ensures `confirmations.len()` for any pending request always reflects confirmations from currently-live members only.

### Proof of Concept
```
// num_confirmations = 3, members = {A, B, X}
add_request(R1)                // by A
confirm(R1)  as A               // confirmations[R1] = {A}
confirm(R1)  as X               // confirmations[R1] = {A, X}  -- 2 of 3, not yet executed

// Separately, members vote to remove X
add_request(R2: DeleteMember{X})
confirm(R2) x3 (A, B, X)        // executes, X removed from `members`
                                 // delete_member only cleans requests signed by X; confirmations[R1] untouched, still {A, X}

// Now only B is a live member besides A; X is gone but its vote on R1 persists
confirm(R1) as B                // confirmations[R1] = {A, X, B} -> len()=3 >= num_confirmations(3)
                                 // R1 executes with only A and B being live members (2 live approvals, not 3)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
