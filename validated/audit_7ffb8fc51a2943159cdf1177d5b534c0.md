### Title
Unsanitized cache key escapes cache root via `AlternateArchiveFile` when `FF_HASH_CACHE_KEYS` is enabled - ([File: shells/abstract.go], [File: commands/helpers/cache_archiver.go])

### Summary
The specific claim that `resolvedKey`/`humanKey` from `builder.cacheKey` (functions/concrete/builder/builder.go) leaks an unsanitized traversal string into the *primary* cache archive path or remote object key is **not exploitable**, because the primary key is either sanitized by `cachekey.Sanitize` or SHA-256 hashed before being used in any path. However, a closely related and real path-traversal bug exists in the **alternate** ("compat") cache key/path used to bridge `FF_HASH_CACHE_KEYS` transitions in `shells/abstract.go`'s `newCacheConfig`/`cacheAlternateKey`, which is consumed unsafely by `CacheArchiverCommand.tryRenameAlternateFile` in `commands/helpers/cache_archiver.go`.

### Finding Description
In `functions/concrete/builder/builder.go` `cacheKey()` (lines 570-603) and its twin in `shells/abstract.go` `newCacheConfig()` (lines 133-208), when `FF_HASH_CACHE_KEYS` is on, `humanKey` is intentionally left **unsanitized** (`humanKey = rawKey`), but the value actually used to build the local archive path (`hashedKey`/`resolvedKey`) is `sha256.Sum256(humanKey)` — a fixed-length hex digest that cannot contain `/../`. This is explicitly documented in the code comment at [1](#0-0) , confirming the primary key path is deliberately hardened against exactly the traversal attack the question describes.

The real gap is in the **alternate key**, computed by [2](#0-1)  `cacheAlternateKey`: when hashing is enabled, the alternate key returned is the **raw, unsanitized `humanKey`** (used to support downgrade/upgrade compatibility between hashed and unhashed cache naming schemes). This raw key is fed directly into `getArchivePath`, which builds a filesystem path with `path.Join(build.CacheDir, key, "cache.zip")` at [3](#0-2) . `path.Join`/`Clean` does not confine the result to `CacheDir`; a `key` such as `../../../etc/some-project-cache` will resolve outside `CacheDir` (up to filesystem root for absolute `CacheDir`).

This `AlternateArchiveFile` value is passed as `--alternate-file` to the `cache-archiver` helper and consumed in `commands/helpers/cache_archiver.go` `tryRenameAlternateFile()` (lines 253-284): it calls `os.Stat(c.AlternateFile)` and, if that path exists, `os.Rename(c.AlternateFile, c.File)` — moving whatever file exists at the attacker-influenced path into the job's own cache location, which is subsequently uploaded to the remote cache store under the attacker's own key.

Exploit flow:
1. Attacker sets `FF_HASH_CACHE_KEYS=true` is a runner-wide setting, not job-controlled, so this requires that flag to already be enabled on the runner (a precondition, not attacker-controlled) — this significantly limits real-world reachability.
2. With that flag on, attacker sets `cache:key: "../../<guessable-other-project-path>"` in `.gitlab-ci.yml`.
3. `cacheAlternateKey` returns this raw string unsanitized; `getArchivePath` builds `AlternateArchiveFile` outside the runner's cache root.
4. If a file happens to exist at that resolved path (e.g., another project's `cache.zip` on a shared local/NFS `CacheDir` with `Shared: true`), `tryRenameAlternateFile` renames it into the attacker's own cache file, which then gets uploaded/re-hashed under the attacker's key and becomes readable by the attacker in subsequent job runs.

### Impact Explanation
If exploitable, this allows a job on a shared runner (local/shared cache backend) to exfiltrate or move another project's local cache archive into its own cache namespace — a concrete cross-project cache read primitive, consistent with the "no escaping cache namespace" invariant. Impact is confined to the local-cache/rename path; it does not affect the remote object key derived from the primary hashed key.

### Likelihood Explanation
Exploitability requires several strong preconditions: (1) `FF_HASH_CACHE_KEYS` must already be enabled runner-wide (this is a runner operator's/admin's setting, not attacker-controlled — it's off by default), (2) the cache backend must be local/shared filesystem (not a purely remote GoCloud/S3 cache, since `AlternateFile` is a local path only used by `cache-archiver`'s rename logic), and (3) the attacker needs to guess or know an existing, predictable path to another project's cache file on the shared filesystem. This makes the bug realistic only in narrow, non-default configurations, lowering overall likelihood substantially compared to the originally hypothesized "always reachable via cache:key" scenario.

### Recommendation
Apply `cachekey.Sanitize` (or an equivalent traversal-safe normalization) to the alternate key in `cacheAlternateKey` regardless of the `FF_HASH_CACHE_KEYS` state, or confine `getArchivePath`'s output to `build.CacheDir` (e.g., via `filepath.Rel` + reject paths starting with `..`, or `securejoin`-style containment checks) before using it in `os.Stat`/`os.Rename` calls in `tryRenameAlternateFile`.

### Proof of Concept
Go unit test outline for `shells/abstract_test.go` / `commands/helpers/cache_archiver_test.go`:
```go
func TestCacheAlternateKey_PathTraversal(t *testing.T) {
    build := &common.Build{
        CacheDir: "/cache",
        Runner: &common.RunnerConfig{RunnerSettings: common.RunnerSettings{
            FeatureFlags: map[string]bool{featureflags.HashCacheKeys: true},
        }},
    }
    cfg, _, err := newCacheConfig(build, "../../../etc/other-project/cache")
    require.NoError(t, err)
    // Assert AlternateArchiveFile stays within CacheDir
    assert.True(t, strings.HasPrefix(cfg.AlternateArchiveFile, "/cache/"),
        "alternate archive path escaped cache root: %s", cfg.AlternateArchiveFile)
}
```
Expected current (failing) result: `AlternateArchiveFile` resolves outside `/cache/`, demonstrating the traversal; after the recommended fix, the assertion should pass.

		}

	archiveFile, err := getArchivePath(hashedKey)

	}

	// alternateKey is always the "other" naming scheme relative to the current FF setting:
	// - FF ON:  primary=hashed, alternate=unhashed → enables upgrade of old unhashed artifacts
