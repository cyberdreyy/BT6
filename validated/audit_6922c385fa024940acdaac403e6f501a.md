### Title
Removed multisig member's stale confirmation still counts toward execution threshold, allowing a request to execute below the required live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
The multisig contract's `delete_member` only purges *requests that were created by* the removed member; it never scans other still-pending requests to strip that member's recorded `confirm()` vote. Because `confirm()` counts votes purely by size of the stored `HashSet<String>` [1](#0-0) , a vote cast by a member who is subsequently removed remains valid and can supply the deciding confirmation on a still-open request, letting that request execute with fewer than `num_confirmations` currently-live approvals.

### Finding Description
`confirm()` looks up `self.confirmations.get(&request_id)` and executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations` [2](#0-1) . The set only ever stores the string form of a `MultisigMember`; nothing ties an existing entry to the member's continued membership.

`delete_member` removes the member from `self.members` and deletes only the requests *that member added* (`r.member == member`): [3](#0-2) 

It does not iterate `self.confirmations` to remove the departing member's vote from other requests that member merely *confirmed* (but did not create). Consequently, any request created by a different member and already carrying that now-removed member's confirmation keeps counting that stale vote.

This breaks the intended equality:
`confirmations counted toward execution == confirmations cast by currently-live members`

After removal, the left side can still include a vote from an account no longer in `self.members`, so the right side (true live approvals) is strictly smaller than the threshold that is actually enforced.

The same structural flaw exists in the legacy contract `multisig/src/lib.rs`, where `DeleteKey` likewise only purges requests whose `signer_pk == pk` [4](#0-3)  without scrubbing that key's confirmations from other pending requests.

### Impact Explanation
This directly matches the "Critical" category: a multisig request executed below the required threshold of legitimate, currently-authorized signers. A malicious or compromised member can lock in a vote for an attacker-favorable request (e.g., `Transfer`, `AddKey`, `FunctionCall` moving funds/access) before being detected and removed; their vote persists as valid "confirmation weight" after removal, so the transaction can later be pushed through by fewer genuinely-authorized members than `num_confirmations` requires — including transfers of NEAR held by the multisig account.

### Likelihood Explanation
This requires no privileged foundation/owner action beyond the multisig's own normal governance flow (adding/removing members is a documented, expected multisig operation, not an out-of-scope assumption). Any member — including one that is later judged malicious/compromised and removed — can trigger it simply by confirming a pending request created by someone else before removal. No RPC interception, redeploy, or external key theft is needed.

### Recommendation
- Short term: When removing a member (`delete_member`/`DeleteKey`), iterate all entries in `self.confirmations` and strip the departing member's identifier from every set, not just requests they created.
- Long term: Re-validate, at execution time inside `confirm()`, that every account/key present in a request's confirmation set is still a current member (e.g., intersect the stored confirmation set with `self.members` before comparing against `num_confirmations`), so a member's authority is always evaluated against the live membership set rather than a possibly-stale snapshot.

### Proof of Concept
1. Deploy with members `[A, B, C, D]`, `num_confirmations = 3`.
2. `D` calls `add_request(R)` for an attacker-favorable action (e.g. `Transfer`).
3. `C` (malicious/compromised member) calls `confirm(R)` → `confirmations[R] = {C}` (len 1 < 3, not yet executed).
4. Honest members detect `C` is malicious and remove it: `A` adds `DeleteMember{C}`, is confirmed by `B` and `D` (3 confirmations) → `delete_member` executes, removing `C` from `self.members` and deleting only requests where `r.member == C`. `R` (added by `D`) is untouched, and `confirmations[R]` still contains `C`.
5. `A` calls `confirm(R)` → `confirmations[R] = {C, A}` (len 2 < 3).
6. `B` calls `confirm(R)` → `confirmations[R].len() + 1 = 3 >= num_confirmations(3)` → `execute_request(R)` runs.
7. Result: `R` executed with confirmations from only 2 currently-live members (`A`, `B`) plus one phantom vote from removed member `C` — a multisig request executed below the true live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
