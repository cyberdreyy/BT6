### Title
Sweep-based partial withdrawal double-counts balance already reserved by a pending partial withdrawal request - ([File: specs/electra/beacon-chain.md])

### Summary
`is_partially_withdrawable_validator` (used by the per-epoch validator sweep) computes "excess balance" as `balance > max_effective_balance` without subtracting the amount a validator has already reserved via `state.pending_partial_withdrawals` (tracked by `get_pending_balance_to_withdraw`). Because `process_withdrawal_request` reserves excess balance for a future payout without immediately decrementing `state.balances`, the same excess Gwei can be paid out twice: once later via `get_pending_partial_withdrawals` and once earlier via the sweep, which sees the not-yet-debited balance as "still excess."

### Finding Description
When a validator submits a `WithdrawalRequest`, `process_withdrawal_request` computes the payable amount while correctly excluding balance already promised to other pending withdrawals: [1](#0-0) 
It appends a `PendingPartialWithdrawal` to the queue but does **not** touch `state.balances[index]` — the debit only happens later when the sweep in `get_expected_withdrawals`/`apply_withdrawals` actually processes the queued item, potentially many epochs later depending on churn: [2](#0-1) 

Meanwhile, the *unrelated* validator-sweep withdrawal path independently decides whether a validator has "excess" balance using only the validator's raw balance vs. `max_effective_balance`, with no knowledge of amounts already reserved in `state.pending_partial_withdrawals`: [3](#0-2) 
This predicate is invoked every block by `get_validators_sweep_withdrawals`, which pays out `balance - get_max_effective_balance(validator)`: [4](#0-3) 

Later, when the originally-queued pending partial withdrawal becomes due, `get_pending_partial_withdrawals` re-checks eligibility with `is_eligible_for_partial_withdrawals`, which only requires `balance > MIN_ACTIVATION_BALANCE` (32 ETH) — not `balance > effective_balance` — so it does not detect that the excess was already paid out by the sweep: [5](#0-4) [6](#0-5) 
It therefore pays `min(balance - MIN_ACTIVATION_BALANCE, withdrawal.amount)` again, i.e. it re-pays the same excess a second time.

This is directly analogous to the reported bug: an amount that is already "reserved"/committed elsewhere (the report's "available flow" from the main pool; here, the amount already promised in `pending_partial_withdrawals`) is counted a second time as freely "available" by an independent accounting path (the report's `getAvailableLiquidity`; here, `is_partially_withdrawable_validator`'s excess-balance check), producing a double payout of the same underlying value.

### Impact Explanation
This breaks the fundamental Gwei-conservation invariant: the total ETH withdrawn to a validator's execution address for "excess above effective balance" can exceed the actual excess the validator ever accrued, and the validator's on-chain `balance` can be driven below its `effective_balance` while the validator is still active (not exited). Concretely, a validator with `balance = effective_balance + X` can end up having `X` withdrawn via the sweep and then `X` withdrawn again via its own previously-queued `WithdrawalRequest`, receiving `2X` for a single `X` of real excess. This is Gwei created beyond what was ever deposited/earned for that validator, which falls into the "Gwei created" Critical/High impact category defined by the scope.

### Likelihood Explanation
No coalition, malicious peer, or client bug is required — this can be triggered purely by an honest validator's own withdrawal-address owner submitting one ordinary `WithdrawalRequest` for a partial withdrawal and then simply waiting for the automatic per-epoch validator sweep to reach that validator index before the requested withdrawal's `withdrawable_epoch` arrives (which is a normal, frequent occurrence, especially when churn delays the requested withdrawal). This requires only correct-per-spec node behavior, not any protocol violation, so it is reachable by any single participant against their own validator, causing every honest node following the spec to identically produce the double payment (so it does not cause a chain split, but it does violate the Gwei-conservation guarantee that no unauthorized/duplicate value can be created).

### Recommendation
`is_partially_withdrawable_validator` (and the sweep's payout amount) should subtract `get_pending_balance_to_withdraw(state, validator.index)` from `balance` before comparing to `max_effective_balance`, mirroring the `has_excess_balance` check already used in `process_withdrawal_request`: [7](#0-6) 
so that balance already committed to a queued pending partial withdrawal is never simultaneously treated as sweep-available excess.

### Proof of Concept
1. Validator `V` has compounding withdrawal credentials, `effective_balance = MAX_EFFECTIVE_BALANCE_ELECTRA` (2048 ETH), `state.balances[V] = 2050 ETH` (2 ETH excess), `exit_epoch = FAR_FUTURE_EPOCH`, and `state.pending_partial_withdrawals` contains no entry for `V`.
2. At epoch `E`, `V`'s withdrawal-address owner submits a `WithdrawalRequest` for 2 ETH via `process_withdrawal_request` (`specs/electra/beacon-chain.md:1871-1938`). Since `pending_balance_to_withdraw == 0`, `has_excess_balance` is true, so `to_withdraw = min(2050-32-0, 2) = 2`; a `PendingPartialWithdrawal(V, amount=2, withdrawable_epoch = E + Δ)` is appended, with `Δ` epochs of delay due to churn. `state.balances[V]` is unchanged (still 2050 ETH).
3. Before epoch `E+Δ`, the automatic validator sweep (`get_validators_sweep_withdrawals`, `specs/electra/beacon-chain.md:1407-1454`) reaches index `V` in some block. `is_partially_withdrawable_validator(V, balance=2050)` returns true because `2050 > 2048` and nothing about the pending queue is checked (`specs/electra/beacon-chain.md:688-703`). A sweep withdrawal for `2050-2048 = 2` ETH is created and applied, reducing `state.balances[V]` to 2048 ETH.
4. At epoch `E+Δ`, `get_pending_partial_withdrawals` processes the original queued entry (`specs/electra/beacon-chain.md:1360-1398`). `balance = 2048`. `is_eligible_for_partial_withdrawals(V, 2048)` returns true because `2048 > MIN_ACTIVATION_BALANCE (32 ETH)` — it does not check against `effective_balance`. `withdrawal_amount = min(2048-32, 2) = 2` ETH is withdrawn again.
5. Result: `V` has received `2 + 2 = 4` ETH in withdrawals from a single 2 ETH excess, and `state.balances[V]` is now 2046 ETH — below its `effective_balance` of 2048 ETH — while `V` was never exited. This 2 extra ETH is Gwei created without any corresponding deposit, contribution, or slashing loss elsewhere.

def is_eligible_for_partial_withdrawals(validator: Validator, balance: Gwei) -> bool:
    """
    Check if ``validator`` can process a pending partial withdrawal.
    """
    has_sufficient_effective_balance = validator.effective_balance >= MIN_ACTIVATION_BALANCE
    has_excess_balance = balance > MIN_ACTIVATION_BALANCE
    return (
        validator.exit_epoch == FAR_FUTURE_EPOCH
        and has_sufficient_effective_balance
        and has_excess_balance
    )

def get_pending_balance_to_withdraw(state: BeaconState, validator_index: ValidatorIndex) -> Gwei:
    balance = Gwei(0)
    for withdrawal in state.pending_partial_withdrawals:
        if withdrawal.validator_index == validator_index:
            balance += withdrawal.amount
    return balance
