### Title
Claimed instant-withdraw receipts keep their per-epoch basis, so a same-epoch default double-counts them in `defaultPendingClaimBasis` and permanently locks the diluted recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` ledger but never deletes `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If the pool defaults in the same `epochNumber` while `pendingInstantWithdraws` is still non-zero, `finalizeDefaultRecovery` counts already-paid receipts in the default claim basis, diluting `defaultRecoveryPrice` for legitimate claimants. The stale per-epoch entries can never be paid out: re-claiming underflows on `instantWithdrawsRequests[_user] -= claimBasis`. The reserve portion backing those phantom claims is frozen forever. This is the vault analog of path traversal: a stale, unvalidated index (the epoch key) reaches into an accounting bucket it should no longer reference.

### Finding Description

Path traversal lets an attacker-controlled identifier reach a resource outside its intended scope. The analog here is the epoch-indexed instant-withdraw ledger: `requestInstantWithdraw` writes `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` (contracts/strategies/idle/IdleCreditVault.sol:371-372), but the funded-claim path zeroes only the aggregate counter (contracts/strategies/idle/IdleCreditVault.sol:387-392). The per-epoch indices are only cleared in the default path `_claimDefaultedInstantWithdrawRequest` (contracts/strategies/idle/IdleCreditVault.sol:847-853).

After a funded claim, the stale epoch indices survive. If `pendingInstantWithdraws != 0` at finalization, `defaultPendingClaimBasis` adds the full `instantWithdrawClaimsByEpoch[epochNumber]` — including basis whose underlying was already paid out at par — into `totalBasis` (contracts/strategies/idle/IdleCreditVault.sol:644-648), lowering `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (contracts/strategies/idle/IdleCreditVault.sol:688). Honest claimants are haircut by phantom basis, while the backing for the stale basis is unclaimable: re-claiming reverts via underflow at `instantWithdrawsRequests[_user] -= claimBasis` (contracts/strategies/idle/IdleCreditVault.sol:848), so that slice of `defaultRecoveryReserve` is permanently stranded.

### Impact Explanation

Two concrete harms once a default finalizes in the same epoch as already-funded instant claims:

1. Recovery dilution: `defaultRecoveryPrice` is computed over an inflated `totalBasis`, so every legitimate defaulted-epoch claimant (normal withdraw receipts, unfunded instant receipts, and active AA/BB holders via the NAV burn/mint at contracts/strategies/idle/IdleCreditVault.sol:701-705) receives a smaller recovery multiplier than their true pro-rata share.
2. Permanent freezing: the reserve fraction corresponding to the stale basis can never be withdrawn — the only code path that pays it reverts — locking underlying in the strategy forever, absent an owner `transferToken` rescue.

### Likelihood Explanation

Requires: (a) instant withdrawals enabled and funded claims processed in epoch N, (b) `pendingInstantWithdraws` still non-zero in epoch N (a partially funded instant queue, which the code explicitly anticipates — see comments at contracts/strategies/idle/IdleCreditVault.sol:636-640), and (c) a borrower default in epoch N finalized via `finalizeDefaultRecovery`. All steps use only honest privileged calls; an unprivileged instant-withdraw requester triggers the stale state simply by claiming normally before default. The underflow guard is arithmetic, not an intentional fix.

Caveat I could not fully verify in this pass: whether the IdleCDOEpochVariant call path permits `claimInstantWithdrawRequest` to pay out while `pendingInstantWithdraws` remains non-zero for the same epoch (i.e., whether partially funded queues and user claims can coexist). If the CDO strictly orders full funding before any claim, the stale-basis window may be unreachable and the issue reduces to dust-level accounting inconsistency.

### Recommendation

In `claimInstantWithdrawRequest`, iterate or track the user's instant receipt epochs (or store the latest instant request epoch analogous to `lastWithdrawRequest`) and decrement both `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` when the funded claim is paid, so the per-epoch ledger cannot be double-counted by default finalization.
