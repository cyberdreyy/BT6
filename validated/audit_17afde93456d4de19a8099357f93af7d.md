### Title
Instant-withdraw claims pay out before borrower funding arrives, draining underlyings reserved for funded withdraw receipts - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug reads `optlen` without checking that a byte is actually available to parse — a length is trusted without verifying the backing data exists. The analog in `IdleCreditVault` is `claimInstantWithdrawRequest`: it burns the user's receipt and pays out `instantWithdrawsRequests[_user]` from the vault's raw underlying balance via `_transferFundedClaim`, without checking that the borrower-funded amount for instant withdrawals was actually collected through `collectInstantWithdrawFunds`. The payout source is trusted (the vault's token balance) without verifying it belongs to instant-withdraw claimants.

### Finding Description
`requestInstantWithdraw` burns the CDO's strategy tokens and mints a 1:1 receipt to the user, increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`. The matching cash leg is supposed to arrive later: the borrower sends underlyings to the CDO, and `collectInstantWithdrawFunds` pulls `_amount` into the vault while decrementing `pendingInstantWithdraws`.

`claimInstantWithdrawRequest` then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

There is no check that `pendingInstantWithdraws` was funded — no per-request funded flag, no comparison of the vault balance against `pendingInstantWithdraws`, no epoch/delay gate on the vault side. The only gate is `allowInstantWithdraw` in `IdleCDOEpochVariant.claimInstantWithdrawRequest`, which is an operational flag, not a funding proof.

The vault's underlying balance legitimately contains cash backing other users' already-funded claims: `collectWithdrawFunds` pulls `pendingWithdraws` from the borrower into the vault at `stopEpoch` (and `lossRecoveryPriceByEpoch` claims in the loss path), while `_transferFundedClaim` only carves out `defaultRecoveryReserve`. Funded-but-unclaimed normal withdraw receipts sit in the same balance with no segregation from instant-withdraw payouts.

So during a running epoch with `allowInstantWithdraw` enabled (e.g. set via `setInstantWithdrawParams`, or the close-pool path where `allowInstantWithdraw = _isRequestingAllFunds`), an attacker who deposited earlier (KYC'd lender, holds tranche tokens) can:

1. Call `requestWithdraw` → CDO calls `requestInstantWithdraw`; receipt minted, `pendingInstantWithdraws` increased, but no borrower funds collected yet.
2. Immediately call `claimInstantWithdrawRequest` → vault burns the receipt and transfers `amount` of underlyings taken from cash earmarked for other users' funded normal-withdraw receipts.
3. When the real funded claimants later call `claimWithdrawRequest`, `_transferFundedClaim` reverts or pays less — their payout was consumed by the instant claimer.

The broken invariant is "one receipt, one payout": the instant receipt is paid from a funding pool that was never charged for it, because the vault never verified the receipt's cash leg existed — the same shape as fetching `optlen` without checking a byte remains in the buffer.

### Impact Explanation
Direct theft. The attacker receives underlying equal to their instant receipt while the victim's funded withdraw claim becomes unpayable (`_transferFundedClaim` reverts on insufficient balance, or the balance is simply gone). Loss equals the attacker's instant-withdraw amount, bounded by the vault's unreserved underlying balance — which is exactly the sum of all funded, unclaimed withdraw receipts and any interest deposited via `strategy.deposit`. A large tranche holder can drain the full funded-receipt balance.

### Likelihood Explanation
Requires `allowInstantWithdraw == true` while the vault holds unfunded instant claims and positive funded-receipt cash. The manager enabling instant withdrawals is an honest, expected operation (the instant-withdraw feature exists to be used), and funded-but-unclaimed normal receipts are the normal state after any `stopEpoch`. The attacker only needs a tranche position and two transactions within the same epoch; no privileged cooperation is needed. The main uncertainty is whether any CDO-side path forces `collectInstantWithdrawFunds` before `allowInstantWithdraw` is set — from the code inspected, `collectInstantWithdrawFunds` is a separate pull (`getInstantWithdrawFunds` → manager-triggered), and nothing in `claimInstantWithdrawRequest` reads `pendingInstantWithdraws` or a funded marker, so the race window exists whenever claims are enabled before collection.

### Recommendation
Track a funded instant-withdraw balance: in `collectInstantWithdrawFunds`, add `_amount` to a `fundedInstantWithdraws` counter; in `claimInstantWithdrawRequest`, require `fundedInstantWithdraws >= amount` and decrement it, instead of paying from the free balance. Alternatively record a per-epoch/per-request funded flag and revert claims until `collectInstantWithdrawFunds` has run for that epoch. `_transferFundedClaim` should never be reachable for receipts whose cash leg hasn't been collected.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
// Foundry fork PoC sketch against test/foundry/IdleCreditVault.t.sol harness
function testInstantClaimStealsFundedReceipt() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // victim deposits and requests a normal withdraw
    _depositWithUser(victim, amount, true);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // epoch ends; borrower funds pendingWithdraws into the vault,
    // victim's receipt is now funded but unclaimed
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // attacker (KYC'd tranche holder) deposits in the new epoch
    _depositWithUser(attacker, amount, true);

    // manager honestly enables instant withdraws for the running epoch
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, FULL_ALLOC, true); // allowInstantWithdraw = true

    uint256 victimFunded = IdleCreditVault(address(strategy)).withdrawsRequests(victim);
    assertGt(victimFunded, 0);

    // attacker creates an instant receipt — no borrower funding collected yet
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attackerTrancheBal, address(AAtranche)); // instant path

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();           // pays from vault balance

    assertGt(underlying.balanceOf(attacker) - balPre, 0); // attacker paid from victim's funded cash

    // victim's funded claim now reverts / underpays
    vm.prank(victim);
    vm.expectRevert();                                 // insufficient unreserved balance
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertion: `pendingInstantWithdraws` is nonzero at claim time (no `collectInstantWithdrawFunds` ran), yet `_transferFundedClaim` still pays out — demonstrating the payout source was consumed without a funding check.
