### Title
OIDC callback continues session creation and login after email-claim/session-persistence errors instead of aborting - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`handleTokenExchange`, the OIDC callback handler reachable by any unauthenticated client hitting `POST /oidc-exchange`, contains two code paths where an error condition is logged and an HTTP error body is written, but execution is **not aborted** (missing `return`). Instead, the function falls through to create an authenticated session and returns `200 OK` with `Success: true`, directly mirroring the reported bug class of "handler reports an error condition but continues execution instead of aborting it."

### Finding Description
In `core/sessions/oidcauth/oidc.go`, `handleTokenExchange` processes the OIDC provider's token-exchange response and, on success, creates a local session with a role mapped from the IdP's claims: [1](#0-0) 

If the `email` claim is missing or of an unexpected type, `ok` is `false`; the code logs an error and writes a `500` response body via `c.String(...)`, but there is no `return` statement. Execution continues into role mapping, session-row insertion, audit logging (`AuthLoginSuccessNo2FA`), setting the session cookie, and finally a second, overriding response `c.JSON(http.StatusOK, ...)`: [2](#0-1) 

A second instance of the same defect exists a few lines later: if the `INSERT INTO oidc_sessions` fails, the error is logged and a `500` body is written, but again there is no `return` — the handler proceeds to audit-log a successful login and set the session cookie regardless of whether the session row was actually persisted: [3](#0-2) 

The net effect for the missing-email case: an OIDC identity provider response (or a compromised/misconfigured/malicious IdP, or a race/bug causing a malformed ID token) that lacks a valid `email` claim will still result in:
1. A row inserted into `oidc_sessions` with `user_email = ''` (empty string, lowercased) and a role derived purely from the group claims.
2. An audit log entry recording a successful, unauthenticated-related login (`AuthLoginSuccessNo2FA`) with an empty email.
3. `ginSession.Set(webauth.SessionIDKey, clSession.ID)` + `ginSession.Save()`, giving the browser a valid, authenticated session cookie.
4. The client-visible response ends up `200 OK` with `{"success":true}` (the earlier `c.String(500, ...)` write is overwritten because gin allows a handler to write multiple times, and the last write to the header controls the client-observed status/body), so the client cannot detect that email extraction failed.

This directly matches the report's second and third examples: an error is detected (`chainConfig` missing analog / unexpected data analog) but the code does not `return`, so it "will bail later" or accept unexpected/incomplete state instead of raising an explicit error.

### Impact Explanation
This creates a valid, cookie-backed, role-bearing session (`SessionUserKey`/`SessionIDKey` equivalent — `AuthorizedUserWithSession` looks up by `oidc_sessions.id`) for a user whose identity (`email`) could not be established, while the client is told the operation succeeded. This is an authentication/identity integrity bypass: role assignment (Admin/Edit/Run/Read, driven only by group claims) is decoupled from a valid user identity, and session bookkeping (audit log, `Sessions()` listing) will misrepresent who is logged in (empty-email entries). Depending on how downstream code keys off `user_email` for authorization decisions, this is a route to cross-user identity confusion in the audit trail and could weaken the RBAC identity binding the OIDC design otherwise enforces.

### Likelihood Explanation
Reaching this code requires only a normal OIDC login flow completing token exchange and returning an ID token whose claims lack an `email` field of type `string` — this can occur with misconfigured IdPs, IdP claim customization, or a malicious/compromised IdP endpoint (which the OIDC exchange trusts implicitly once the token is verified). No special privilege is needed by the calling client; `POST /oidc-exchange` is reachable pre-authentication as part of the login flow.

### Recommendation
Add `return` immediately after each error-logging block in `handleTokenExchange`:
- After `c.String(http.StatusInternalServerError, "Failed to get email from claims")` (currently missing at line ~230).
- After `c.String(http.StatusInternalServerError, "Error creating session")` (currently missing at line ~260).

Additionally, treat a missing/invalid `email` claim as a hard authentication failure (do not proceed to create a session, write an audit-success entry, or set the session cookie), consistent with the report's recommendation to implement strict validation of untrusted (IdP-supplied) data and to be explicit/raise errors on unexpected conditions rather than silently continuing.

### Proof of Concept
1. Point the node's `WebServer.OIDC.ProviderURL` at a test/malicious OIDC provider (or configure a real provider to omit the `email` claim / use a non-standard claim name for email).
2. Initiate `/oidc-login`, complete the provider's consent flow, and let it redirect back with a `code`.
3. Client calls `POST /oidc-exchange` with `{code, state}`.
4. Server exchanges the code, verifies the ID token, extracts group claims successfully, but `claims["email"]` is missing/not a string.
5. Observe: server logs "Failed to get email from claims", writes (but does not return) a 500 body, then continues to insert an `oidc_sessions` row with empty `user_email`, sets the session cookie, and finally responds `200 OK {"success":true}`.
6. The returned session cookie is valid and authorizes further API calls via `AuthenticateBySession`, as shown in [4](#0-3) , despite the identity (`email`) never having been established.
