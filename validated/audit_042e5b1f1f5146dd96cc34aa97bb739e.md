### Title
Stale `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` inflate the default-recovery reserve and claim basis, causing recovery insolvency and frozen claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The per-epoch instant-withdraw counters `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are incremented in `requestInstantWithdraw` (lines 371-372) but are only ever decremented inside `_claimDefaultedInstantWithdrawRequest` (lines 847-853). A normally-funded instant withdrawal that is claimed via `claimInstantWithdrawRequest` (lines 380-393) or funded via `collectInstantWithdrawFunds` (lines 398-403) never clears them. Later, if a default is finalized in the same epoch, `defaultPendingClaimBasis()` (line 647) and `_defaultPrefundedInstantReserve()` (lines 719-721) read these stale counters, overstating both the claim basis and, worse, the reserve of supposedly already-held underlying. This mirrors the audited bug: a status transition (claim/funding) fails to update an array-length-style counter that is later reused to compute a critical threshold.

### Finding Description
`requestInstantWithdraw` accumulates per-epoch state:

- `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (line 371)
- `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (line 372)
- `pendingInstantWithdraws += _amount` (line 374)

When the CDO funds the request, `collectInstantWithdrawFunds` decreases `pendingInstantWithdraws` (line 401) but leaves the by-epoch mappings untouched. When the user claims, `claimInstantWithdrawRequest` zeroes only `instantWithdrawsRequests[_user]` (line 391). So `instantWithdrawClaimsByEpoch[epoch]` permanently accumulates every instant request ever made in that epoch, including fully paid ones.

At default finalization, `finalizeDefaultRecovery` computes:

- `prefundedReserve = instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` when the former is larger (lines 716-723), intended to represent instant-claim funds already held by the strategy.
- `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` (line 686), which sets `defaultRecoveryReserve` (line 691) and drives `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688).
- `basis += instantWithdrawClaimsByEpoch[epochNumber]` in `defaultPendingClaimBasis` whenever `pendingInstantWithdraws != 0` (lines 646-648).

Because the by-epoch totals still include already-paid claims, `prefundedReserve` counts tokens that left the strategy long ago. `defaultRecoveryReserve` is then set higher than the contract's true earmarked balance, while real balance is lower. Claimants drawing via `_transferDefaultRecovery` (lines 912-917) decrement the inflated reserve but transfer real tokens; the reserve/balance mismatch means the last claimants' transfers revert (insufficient balance) — their defaulted receipts are permanently unfunded. Additionally, `_transferFundedClaim`'s guard `balance - reserve < _amount` (lines 899-905) treats the phantom `A+B` as untouchable reserve, reverting legitimate funded withdraw claims and post-default requests, freezing those funds.

### Impact Explanation
Direct insolvency and permanent freezing of unclaimed recovery/funded claims, quantifiable as the sum of all instant withdrawals that were funded and claimed earlier in the default epoch. An unprivileged user (any tranche holder able to call `requestInstantWithdraw`/`claimInstantWithdrawRequest` via the CDO) inflates the reserve by cycling funded instant withdraws; the honest borrower's subsequent default crystallizes the inflated reserve, so the shortfall is borne by other claimants whose claims revert. The stale basis also perturbs `recoveryPrice`, mispricing every defaulted-epoch receipt and the active tranche NAV (`defaultBBNav`, line 700).

### Likelihood Explanation
Likelihood is moderate: it requires (a) at least one instant withdraw that is funded and claimed within an epoch, and (b) a borrower default finalized in that same epoch while `pendingInstantWithdraws != 0` (i.e., at least one other instant request remains unfunded at finalization). No privileged malicious behavior is needed — honest manager/borrower actions suffice — and each funded-then-claimed instant cycle linearly grows the phantom reserve. Existing guards do not stop it: `_ensureDefaultRecoveryInitialized` only reverts on nonzero `pendingInstantWithdraws` at *initialization* (line 926), not on stale by-epoch data, and `_transferFundedClaim`'s reserve guard actively converts the overstatement into reverts for honest claimants.

### Recommendation
Mirror the audited fix pattern: keep the by-epoch counters consistent on every transition that consumes them. In `claimInstantWithdrawRequest`, subtract the claimed amount from `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` for the epoch in which the request was made (storing the request epoch per user, similar to `lastWithdrawRequest`, may be needed). Alternatively, derive the prefunded reserve from actual `underlyingToken.balanceOf(address(this))` attributable to instant claims rather than from cumulative request counters, and have `defaultPendingClaimBasis` use only the still-unclaimed per-epoch receipts.

### Proof of Concept
Reproducible Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol` setup):

1. Deposit via `cdoEpoch`, `startEpoch`. In epoch N, attacker calls `cdoEpoch.requestInstantWithdraw` for amount A; manager funds via the CDO (`collectInstantWithdrawFunds` path) so `pendingInstantWithdraws` returns to 0; attacker calls `claimInstantWithdrawRequest` and receives A. Assert `creditVault.instantWithdrawClaimsByEpoch(N) == A` — stale.
2. Attacker repeats with amount B (fund, claim). Stale total is now `A + B`.
3. Victim user calls `requestInstantWithdraw` for C; it is left unfunded, so `pendingInstantWithdraws == C` at finalization.
4. Borrower defaults; CDO calls `finalizeDefaultRecovery(recovered, source)`. `_defaultPrefundedInstantReserve` returns `(A+B+C) - C = A+B`, inflating `defaultRecoveryReserve` by `A+B` tokens the strategy no longer holds.
5. Assert `defaultRecoveryReserve > underlyingToken.balanceOf(strategy) - otherLiabilities`; the victim's `claimInstantWithdrawRequest` (or a funded `claimWithdrawRequest`) reverts/underpays once earlier claims drain the real balance, while `_transferFundedClaim` reverts for any funded claimant because `balance - reserve < amount`.

Expected result: documented `A + B` quantified shortfall; last claimants permanently unable to withdraw, satisfying the insolvency/permanent-freeze acceptance bar.
