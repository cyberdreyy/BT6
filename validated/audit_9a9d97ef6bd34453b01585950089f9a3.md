## Finding: Analysis of `switch_operator` / `distribute_internal` interaction

I traced the exact mechanics rather than the specific hypothesis in the question, and found a related but distinct bug in how commission recipients are resolved after `switch_operator`.

### How `distribute_internal` actually decides whether to apply the beneficiary redirect [1](#0-0) 

The redirect check is:
```move
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};
```
Here `recipient` is the **fixed address stored as the pool_u64 shareholder key** at the time `add_distribution` was called, and `operator` is the parameter passed into `distribute_internal` by the caller of the top-level `distribute(staker, operator)` entry function — which is always resolved via the `Store.staking_contracts` map key that currently holds this `StakingContract` [2](#0-1) .

### The bug introduced by `switch_operator`

In `switch_operator`, before the operator is switched, `distribute_internal` is called (paying out already-inactive funds correctly, since `operator == old_operator` at that point), followed by `request_commission_internal(old_operator, ...)`, which calls `stake::unlock_with_cap` and `add_distribution(old_operator, staking_contract, old_operator, commission_amount)` [3](#0-2) . This newly-unlocked commission is only `pending_inactive` — it has not yet crossed the lockup boundary into `inactive`, so it is **not** paid out by the `distribute_internal` call that already ran; it just sits in `distribution_pool` as a shareholder entry keyed by the raw address `old_operator`.

Immediately after, `stake::set_operator_with_cap` moves the pool's operator to `new_operator`, and the `StakingContract` struct (including its `distribution_pool` with the stale `old_operator` shareholder entry) is re-inserted into `Store.staking_contracts` under key `new_operator` [4](#0-3) .

From this point forward, the *only* way to reach `distribute_internal` for this `StakingContract` is via `distribute(staker, new_operator)`, so `operator` inside `distribute_internal` will always be `new_operator`. When the loop reaches the leftover shareholder entry (`recipient == old_operator`), the check `recipient == operator` (`old_operator == new_operator`) is **false**, so `beneficiary_for_operator(old_operator)` is never invoked. The coins are deposited directly to the raw `old_operator` account address instead of to whatever beneficiary `old_operator` had configured via `set_beneficiary_for_operator` [5](#0-4) .

### Correction of the originally proposed hypothesis

The proof idea in the question assumes the pending distribution's payout is resolved via a `beneficiary_for_operator` lookup evaluated at distribute-time (which could be stale/changed). That is not what happens: for a residual commission entry created during `switch_operator`, the beneficiary lookup is **never invoked at all** once the operator key changes — the funds simply go to the raw `old_operator` address regardless of any beneficiary that was ever set for `old_operator` (before or after the switch). So the specific "changed beneficiary vs. beneficiary at switch time" proof would not demonstrate anything, since no `beneficiary_for_operator` call happens for that entry post-switch.

### Assessment against review scope

The commission funds are not stolen by an attacker or redirected to an arbitrary third party — they still land in `old_operator`'s own account, just bypassing the beneficiary indirection that AIP-40 (`operator_beneficiary_change_enabled`) is meant to guarantee. This is a real "wrong account credited" defect in the commission/beneficiary payout accounting per the required impact list (beneficiary payout corruption), triggered purely by a legitimate staker calling `switch_operator` (a normal, unprivileged, staker-only entry function) while a commission request from the prior operator is still in its unlock/lockup window.

### Title
Stale commission distribution entries created during `switch_operator` bypass `beneficiary_for_operator` redirection and pay the raw old-operator address instead — (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`switch_operator` forces a `request_commission_internal` call for `old_operator` right before re-keying the `StakingContract` under `new_operator` in the staker's `Store`. Any commission unlocked by that call that hasn't finished its lockup period remains as a `distribution_pool` shareholder entry keyed by `old_operator`'s raw address. Because `distribute_internal`'s beneficiary redirect only fires when `recipient == operator` (where `operator` is the *current* key under which the contract is stored, i.e. `new_operator` after the switch), this stale entry can never match, and its payout permanently bypasses `beneficiary_for_operator(old_operator)`, going instead directly to `old_operator`'s own account.

### Impact Explanation
Operators who rely on `set_beneficiary_for_operator` to route commission to a separate custodial/payout address will silently lose that redirection for any commission requested in the window immediately preceding a `switch_operator` call, if the unlocked amount hasn't fully exited lockup before the switch. This corrupts the beneficiary payout guarantee described in the module's own documentation, crediting the operator's raw address instead of the intended beneficiary.

### Likelihood Explanation
This triggers on the ordinary combination of staker actions (`switch_operator` while there is unpaid/newly-unlocked commission still in lockup) with no special privilege needed — the staker legitimately owns the staking contract and is entitled to call `switch_operator`. The condition (residual pending_inactive commission at switch time) is a normal occurrence given lockup periods are on the order of days.

### Recommendation
When re-keying a `StakingContract` from `old_operator` to `new_operator` in `switch_operator`, either (a) rewrite any residual `distribution_pool` shareholder entries whose key equals `old_operator` to resolve `beneficiary_for_operator(old_operator)` at the time of the switch (snapshotting it), or (b) track distribution recipients using a resolved beneficiary address at `add_distribution` time rather than relying on a live-recomputed `operator == recipient` comparison against a key that can be re-mapped later.

### Proof of Concept
1. Staker creates a staking contract with `old_operator`, commission > 0.
2. Stake pool accrues rewards; `old_operator` optionally calls `set_beneficiary_for_operator` to set `beneficiary_A`.
3. Staker calls `switch_operator(staker, old_operator, new_operator, commission)` while the pool's lockup has not yet fully expired for the freshly-unlocked commission (i.e. the `request_commission_internal` call inside `switch_operator` unlocks new commission that stays `pending_inactive`).
4. Advance epochs until the lockup expires, then call `distribute(staker, new_operator)`.
5. Assert: the commission tied to the old-operator's residual entry is deposited to `old_operator`'s own address, not to `beneficiary_A`, demonstrating the beneficiary redirect is bypassed for that entry — even though `beneficiary_A` was properly registered for `old_operator` both before and after the switch.

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
