### Title
Donation-triggered ERC4626 deposit overflow can repeatedly DoS `startEpoch` - ([contracts/strategies/idle/ProgrammableBorrower.sol:201](contracts/strategies/idle/ProgrammableBorrower.sol#L201))

### Summary
An unprivileged user can temporarily prevent a programmable-borrower epoch from starting by filling the configured ERC4626 vault until its remaining deposit capacity exactly equals the next CDO transfer, then donating 1 wei to `ProgrammableBorrower`. `IdleCDOEpochVariant.startEpoch()` transfers the surplus funds to the borrower and immediately calls `onStartEpoch()`, which deposits the borrower's entire raw token balance, including the unsolicited wei, into the ERC4626 vault. [1](#0-0) [2](#0-1)  If the vault's remaining capacity was exactly the legitimate transfer amount, the 1 wei donation makes `vault.deposit()` exceed `maxDeposit()` and revert, reverting the whole `startEpoch()` transaction. [3](#0-2) 

### Finding Description
`startEpoch()` first marks the epoch running, pauses deposits, disables new withdrawal requests, sends the surplus underlying to `_borrower()`, and then invokes the programmable-borrower hook. [4](#0-3) [1](#0-0)  `onStartEpoch()` measures the borrower's complete ERC20 balance and calls `_depositToVault()` with that complete balance. [5](#0-4)  `_depositToVault()` performs an uncapped `vault.deposit(_assetAmount, address(this))`, so a direct donation changes the deposit size even though it was not part of the CDO's lifecycle transfer. [3](#0-2) 

The sequence is:

1. During the buffer phase, calculate the expected CDO surplus that will be sent to the programmable borrower. [6](#0-5) 
2. As an ERC4626 vault user, deposit into the configured vault until `vault.maxDeposit(address(programmableBorrower)) == expectedSurplus`.
3. Transfer 1 wei of the underlying directly to `ProgrammableBorrower`.
4. The manager calls `startEpoch()`. [7](#0-6) 
5. The CDO transfers `expectedSurplus`, making the borrower balance `expectedSurplus + 1`.
6. `onStartEpoch()` attempts `vault.deposit(expectedSurplus + 1)`, which exceeds the remaining capacity and reverts. [2](#0-1) [3](#0-2) 
7. The entire `startEpoch()` call rolls back, including `isEpochRunning`, `epochEndDate`, the pause, and the CDO-to-borrower transfer.

This differs from the CDO's own donation handling: `_deposit()`, `requestWithdraw()`, `depositDuringEpoch()`, `startEpoch()`, and `stopEpoch()` explicitly skim raw CDO balances before accounting. [8](#0-7) [9](#0-8)  No equivalent isolation exists for raw balances on `ProgrammableBorrower`, which instead treats its entire balance as vault deposit input. [2](#0-1) 

### Impact Explanation
The attacker can repeatedly revert `startEpoch()` for the cost of dust donations and vault-capacity positioning, temporarily preventing the pool from deploying queued capital and beginning the next epoch. [10](#0-9)  The affected amount is the full `_toBorrower` surplus calculated by the CDO, because the ERC20 transfer and hook are atomic within the reverting manager transaction. [11](#0-10)  The issue is temporary rather than permanent because privileged remediation can remove the donation or change vault capacity, but the attacker can continue front-running recovery attempts while the vault remains exactly saturated.

### Likelihood Explanation
Likelihood is conditional on the configured ERC4626 vault having a usable deposit limit that can be positioned to equal the next borrower transfer. [12](#0-11)  An attacker may act directly as an ERC4626 vault user to consume capacity and can donate to the borrower without passing KYC or holding tranche tokens. [2](#0-1)  Existing CDO skim checks do not stop this attack because the donated tokens are held by the programmable borrower rather than by `IdleCDOEpochVariant`. [9](#0-8) 

### Recommendation
Pass the exact principal amount transferred by `IdleCDOEpochVariant` into `onStartEpoch()` and deposit only that accounted amount rather than `underlyingToken.balanceOf(address(this))`. [11](#0-10) [13](#0-12)  Alternatively, cap the vault deposit at `vault.maxDeposit(address(this))` and leave the excess idle, but the accounting baseline must then exclude the undeployed donated balance so it is not later interpreted as vault PnL. [14](#0-13)  The more robust design is an explicit `amountReceived` hook parameter plus a separate donation/skimming path for unsolicited balances.

### Proof of Concept
A Foundry fork test should use the deployed programmable borrower, its configured underlying, and its configured ERC4626 vault:

```solidity
function testDonationDosStartEpoch() public {
    uint256 expectedSurplus = /* CDO balance that startEpoch will send */;

    // Fill the external ERC4626 until the borrower can deposit exactly
    // the legitimate CDO transfer amount.
    uint256 remaining = vault.maxDeposit(address(programmableBorrower));
    uint256 attackerDeposit = remaining - expectedSurplus;
    deal(address(underlying), attacker, attackerDeposit + 1);
    vm.startPrank(attacker);
    underlying.approve(address(vault), attackerDeposit);
    vault.deposit(attackerDeposit, attacker);
    assertEq(vault.maxDeposit(address(programmableBorrower)), expectedSurplus);

    // One unsolicited wei pushes the subsequent deposit over the cap.
    underlying.transfer(address(programmableBorrower), 1);
    vm.stopPrank();

    vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);
    vm.prank(manager);
    vm.expectRevert();
    cdoEpoch.startEpoch();

    assertFalse(cdoEpoch.isEpochRunning());
}
```

The critical assertion is that `onStartEpoch()` does not distinguish the manager's `expectedSurplus` transfer from the attacker's 1 wei donation before calling `vault.deposit()`. [5](#0-4) [3](#0-2)

```text
  function onStartEpoch(uint256 _pendingWithdraws) external nonReentrant {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;
    uint256 currentVaultAssets = _currentVaultAssets();
    uint256 bufferStartAssets = bufferStartVaultAssets;
    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;
    // Snapshot total assets before re-depositing idle cash so the epoch principal baseline uses the
    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.
    uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
    // Any idle balance left on the contract between epochs is parked immediately into the vault.
    _depositToVault(underlyingToken.balanceOf(address(this)), 0);
    // Reset the epoch accounting baseline from the exact pre-start total assets so the new epoch
    // does not treat the just-deposited idle balance as fresh vault profit or loss.
    epochStartVaultAssets = startAssets;
```
