### Title
Stale rejection weight is never cleared when a signer later re-signs the same block, allowing the miner's aggregated-weight tally to diverge from actual current signer votes - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The node-side `StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` per block from raw `BlockResponse` messages. When a signer that already sent a `Rejected` response later sends an `Accepted` response for the *same* block (a state transition the signer-side state machine explicitly allows, `LocallyRejected -> LocallyAccepted : re-evaluated`, per `docs/signer-flows.md` section 2 and `BlockInfo::check_state`), the listener adds the signer's weight to `total_weight_approved` but never removes the earlier contribution from `total_weight_rejected`. The two counters, which are supposed to represent disjoint partitions of signer weight, become double-counted for that signer, analogous to the PoolTogether bug where a balance update wasn't mirrored by the corresponding supply update.

### Finding Description
`StackerDBListener::run` processes `BlockResponse::Accepted` and `BlockResponse::Rejected` messages independently: [1](#0-0) 

For `Accepted`, weight is added to `total_weight_approved` guarded only by `!block.gathered_signatures.contains_key(&slot_id)` — i.e., "have I counted this signer's *approval* yet" — with no check of, or adjustment to, `total_weight_rejected`. [2](#0-1) 

For `Rejected`, weight is added to `total_weight_rejected` guarded by `block.responded_signers.insert(slot_id)` returning true (first response ever from that slot). Once a slot's rejection has been counted, nothing decrements `total_weight_rejected` for that slot except an explicit, unrelated call to `reset_rejections`: [3](#0-2) 

`reset_rejections` is called only from `SignerCoordinator::get_block_status` on a `SignatureTimeout` (i.e., the whole rejection window is cleared and re-armed for a re-proposed block), not whenever an individual signer flips from reject to accept on the *original* block: [4](#0-3) 

On the signer side, a block can legitimately move `LocallyRejected -> LocallyAccepted` on re-evaluation (documented state diagram) when a new proposal for the same block arrives and `should_reevaluate_reject_reason` says the prior reject reason is reconsiderable — the signer then re-sends a fresh `BlockResponse::Accepted` for the same `signer_signature_hash`: [5](#0-4) [6](#0-5) 

Because the coordinator's `BlockStatus` only tracks per-slot membership in `gathered_signatures` (for approvals) and a *single* combined `responded_signers` set (used only to gate rejection counting), there is no bookkeeping that removes a slot's weight from `total_weight_rejected` when that same slot later shows up in `gathered_signatures`. The two totals, `total_weight_approved` and `total_weight_rejected`, are meant to be checked as complementary fractions of `total_weight` (70% vs. 30%), but after a reject-then-accept flip from one signer, the sum `total_weight_approved + total_weight_rejected` can exceed the real distinct signer weight that voted, because one signer's weight is counted in both buckets simultaneously — an aggregated-weight-vs-verified-accepts equality break, analogous to the PoolTogether report's unmatched supply/balance update.

### Impact Explanation
This directly affects the miner-side rejection/acceptance decision in `SignerCoordinator::get_block_status`, which computes:

- Reject the block: `total_weight_rejected.saturating_add(weight_threshold) > total_weight`
- Accept the block: `total_weight_approved >= weight_threshold` [7](#0-6) 

Because stale rejection weight from a signer who has since switched to accepting the same block is never removed from `total_weight_rejected`, the blocking-minority check can trip using a mix of "phantom" rejected weight (from a signer whose true, most recent, and valid vote is now Accepted) plus genuinely-current rejections from others. This can cause the coordinator to declare a block dead (`NakamotoNodeError::SignersRejected`) even though the actual, up-to-date signer opinions would allow the 70% approval threshold to be reached — a liveness wedge that discards a potentially valid block and forces costly re-proposal/timeout cycles, achievable by a single signer flipping its vote plus normal miner/gossip machinery, with no majority collusion required. This matches the "wedge the state machine" / "aggregated-weight vs verified-accepts" category called out in scope.

### Likelihood Explanation
The trigger requires only one signer (any signer, not a majority) to legitimately reject a proposal once and later accept the identical block after a reconsiderable reject reason and a re-proposal (a normal, expected operational sequence per `should_reevaluate_block`/`should_reevaluate_reject_reason`, not any protocol violation). No cryptographic forgery, no majority collusion, and no bug in a third-party library is needed — only ordinary re-evaluation behavior that the signer-side state machine explicitly supports. The window in which the stale rejection weight persists lasts until an unrelated `SignatureTimeout` triggers `reset_rejections`, which can be the majority of a block's live lifetime.

### Recommendation
Track approvals and rejections per-slot with a single "latest response" resolution instead of independent monotonic counters: when a slot's `Accepted` response is recorded, remove any previously counted weight for that slot from `total_weight_rejected` (and vice versa if an already-approved slot later legitimately rejects, consistent with existing intent expressed in `reset_rejections`'s comment about approvals being irrevocable — if that irrevocability is intentional, then rejections must be defined as revocable and cleared explicitly on a later accept from the same slot, not just on a timeout-driven `reset_rejections`). Concretely, replace the flat `total_weight_rejected`/`total_weight_approved` counters with derivations computed from `gathered_signatures` and an equivalent per-slot rejection map, so the two totals are always computed from disjoint, current per-slot state rather than accumulated independently.

### Proof of Concept
1. Node proposes block B; `StackerDBListenerComms::insert_block` initializes `BlockStatus` with zeroed weights and empty `responded_signers`/`gathered_signatures`.
2. Signer S (weight w) validates B, but a chainstate/pre-commit re-check causes it to `mark_locally_rejected` and broadcast `BlockResponse::Rejected` for B's `signer_signature_hash`. The listener processes this at lines 486-591: `responded_signers.insert(slot_S)` succeeds, `total_weight_rejected += w`.
3. Before any `SignatureTimeout`/`reset_rejections` occurs, a re-proposal for the identical block arrives (or the underlying reject reason becomes stale) and `should_reevaluate_reject_reason` returns true; S re-evaluates, transitions `LocallyRejected -> LocallyAccepted`, and broadcasts a fresh `BlockResponse::Accepted` for the same hash (per `stacks-signer/src/v0/signer.rs:1505-1533` and `signerdb.rs` state machine).
4. The listener processes the Accepted message at lines 386-465: since `slot_S` is not in `gathered_signatures` yet, it adds `w` to `total_weight_approved`. `total_weight_rejected` is left untouched at its previous value (still including `w`).
5. `BlockStatus` now reports both `total_weight_approved` and `total_weight_rejected` including S's weight `w` simultaneously — `total_weight_approved + total_weight_rejected` exceeds the true weight of distinct signers who have responded, and if other signers' rejections push `total_weight_rejected.saturating_add(weight_threshold) > total_weight` using this stale contribution, `SignerCoordinator::get_block_status` returns `NakamotoNodeError::SignersRejected` for a block that current signer opinion would otherwise approve.

Note: I was not able to execute this scenario in a live test harness (no test/terminal access in this mode); the analysis is based on static reading of `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, `stacks-node/src/nakamoto_node/signer_coordinator.rs`, and the signer-side re-evaluation logic in `stacks-signer/src/v0/signer.rs` / `stacks-signer/src/signerdb.rs`. Confirming the exact runtime timing window (how often a reject-then-accept flip happens before a `SignatureTimeout`/`reset_rejections` fires) would benefit from a Devin session with test execution access.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
