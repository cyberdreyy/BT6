### Title
Multiple pending withdraw receipts across epochs bypass the loss-adjusted haircut — `lastWithdrawRequest` indexes only the latest epoch, letting a haircutted receipt be paid at par - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The analog of CVE-2020-11099 (attacker-controlled index causes a read into the wrong buffer region) is `_claimLossAdjustedWithdrawRequest`: it uses `lastWithdrawRequest[_user]` — a single-slot "latest epoch" marker — as the index into `lossRecoveryPriceByEpoch`. If a user holds receipts from two different epochs, the haircut stored for the earlier loss epoch is never consulted, and `_claimFundedWithdrawRequest` pays the full aggregate `withdrawsRequests[_user]` at par even though the borrower only funded the loss-adjusted amount for the earlier epoch.

### Finding Description
- `requestWithdraw` records receipts per epoch (`withdrawsRequestsByEpoch[_user][currentEpoch]`) but stores only one `lastWithdrawRequest[_user] = currentEpoch` marker [1](#0-0) .
- On a `stopEpochWithDuration` loss, `collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` — i.e., keyed by the *request epoch*, matching the per-epoch receipt key [2](#0-1) .
- `claimWithdrawRequest` first tries the loss-adjusted path, but `_claimLossAdjustedWithdrawRequest` only probes `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. If the user's *last* request epoch has no loss price (returns 0), it silently skips the older haircutted receipt [3](#0-2) .
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — the aggregate across *all* epochs, including the haircutted epoch's `withdrawsRequestsByEpoch` amount — at par via `_transferFundedClaim` [4](#0-3) .
- `_clearWithdrawClaimForEpoch` only clears the probed epoch's bucket, so nothing prevents the stale-epoch receipt from being summed into the par payout [5](#0-4) .

Broken invariant: "one receipt, one haircut-adjusted payout". The strategy holds only the borrower-funded loss-adjusted underlying for the epoch-A receipt, yet pays par.

### Impact Explanation
Attacker over-claims underlying equal to `epochA_amount * (1 - lossRecoveryPrice)`. That excess is paid from strategy-held underlyings reserved for other pending claimants → direct theft / insolvency of the withdraw reserve. Loss scales with the attacker's epoch-A receipt size and the haircut depth (up to nearly the full receipt when `lossRecoveryPrice ≈ 0`, noting the `lossRecoveryPrice == 0` revert guard in `collectWithdrawFunds` only blocks exact-zero prices).

### Likelihood Explanation
Fully attacker-driven: a KYC-passing lender requests a withdraw in the epoch where `stopEpochWithDuration` realizes a loss, then requests a second withdraw in the following (healthy) epoch, waits one epoch, and calls `claimWithdrawRequest`. No privileged misbehavior required — the honest manager's `stopEpochWithDuration` and the borrower's partial funding are normal protocol flows. The only precondition is a non-zero realized loss epoch, which is a designed feature.

### Recommendation
Iterate the user's outstanding receipt epochs (or track a bitmap/list of epochs with non-zero `withdrawsRequestsByEpoch`) and apply `lossRecoveryPriceByEpoch` per epoch in `_claimLossAdjustedWithdrawRequest`, rather than keying solely on `lastWithdrawRequest[_user]`; the par path in `_claimFundedWithdrawRequest` should exclude any epoch with a non-zero loss price.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (APR != 0 standard epoch variant)
// 1. Epoch N running: attacker deposits via CDO, then queue/strategy requestWithdraw(X).
//    -> withdrawsRequestsByEpoch[attacker][N] = X; lastWithdrawRequest[attacker] = N.
// 2. Honest manager calls cdoEpoch.stopEpochWithDuration(..., lossAmount > 0).
//    Borrower funds only X * lossPrice / RECOVERY_FULL via collectWithdrawFunds.
//    -> lossRecoveryPriceByEpoch[N] = lossPrice (< RECOVERY_FULL); pendingWithdraws = 0.
// 3. Epoch N+1 running: attacker calls requestWithdraw(Y).
//    -> withdrawsRequestsByEpoch[attacker][N+1] = Y; lastWithdrawRequest[attacker] = N+1.
// 4. Epoch N+1 stops (no loss); attacker waits so epochNumber > N+1.
// 5. attacker -> IdleCDO.claimWithdrawRequest:
//    _claimLossAdjustedWithdrawRequest reads lossRecoveryPriceByEpoch[N+1] == 0 -> skipped.
//    _claimFundedWithdrawRequest pays withdrawsRequests[attacker] = X + Y at par,
//    although only (X*lossPrice/RECOVERY_FULL + Y) was ever funded.
// assert underlying paid > funded reserve for the attacker's receipts.
```
