### Title
Loss-adjusted withdraw receipts escape the haircut by re-requesting, then claim at par — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
When `stopEpochWithDuration` realizes a loss, pending withdraw receipts are funded at a haircut via `lossRecoveryPriceByEpoch[epochNumber]`. The loss-adjusted claim path is keyed solely to `lastWithdrawRequest[_user]` — the user's *most recent* request epoch. An unprivileged lender whose receipt was haircutted can submit a new withdraw request in a later epoch, which overwrites `lastWithdrawRequest[_user]` and makes `_claimLossAdjustedWithdrawRequest` look up `lossRecoveryPriceByEpoch[newEpoch]` (zero). The old haircutted basis is never cleared or priced, so it falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` — including the unfunded loss portion — at full par. This is the codebase analog of the double-free/UAF class: the same claim basis is effectively consumed twice, once "spent" by the haircut accounting and once paid again at par.

### Finding Description
- `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`): when the borrower funds `_amount < pendingBasis`, it sets `pendingWithdraws = 0` and records `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis`. The strategy only ever receives the reduced `_amount`.
- `requestWithdraw` (`IdleCreditVault.sol:282-294`): sets `lastWithdrawRequest[_user] = currentEpoch` and adds to `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][currentEpoch]`. There is a single `lastWithdrawRequest` slot per user — no per-epoch history of pending loss claims.
- `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:789-801`): reads `lossEpoch = lastWithdrawRequest[_user]` and looks up `lossRecoveryPriceByEpoch[lossEpoch]`. If the user's latest request is a *later* epoch (which had no loss), the price is 0 and the function returns early, leaving the old epoch's `withdrawsRequestsByEpoch[_user][oldEpoch]` and `withdrawsRequests[_user]` intact.
- `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:319-350`): once `epochNumber > lastWithdrawRequest[_user]` (and `epochEndDate != 0`), it pays `withdrawsRequests[_user]` — which still contains the full pre-haircut basis of the loss-epoch receipt — via `_transferFundedClaim`, burning receipts 1:1.

So the flow: epoch N ends with a loss → user's receipt of basis B is funded only `B * lossRecoveryPrice / 1e18`. The user requests a new withdraw in epoch M > N → `lastWithdrawRequest` becomes M → the loss-adjusted path for epoch N is unreachable → after epoch M+1 the funded claim pays the *full* B (plus the new request). The strategy only holds `B * lossRecoveryPrice` for that receipt, so the excess `B * (1 - lossRecoveryPrice)` is paid out of funds belonging to other claimants, active LPs, or the default-recovery reserve.

### Impact Explanation
Direct theft of unclaimed yield / other users' principal, quantified as `claimBasis * (1 - lossRecoveryPriceByEpoch[lossEpoch]) / 1e18` per attacker receipt. With a 50% loss haircut, an attacker with a large pending receipt doubles that portion of their payout. The strategy's underlying balance is under-collateralized by exactly the stolen amount, so either later claimants' funded claims revert (permanent freezing of honest users' withdrawals) or the default-recovery reserve is drained. Note `_transferFundedClaim` (line 897+) explicitly avoids spending `defaultRecoveryReserve`, so the theft lands on honest funded claims and active-LP backing — still a direct loss.

### Likelihood Explanation
Requirements are all unprivileged: (1) a KYC-passing lender requests a withdraw during a buffer/running epoch; (2) the honest manager calls `stopEpochWithDuration` with a realized loss — a normal adverse-market event, not attacker-controlled but a designed code path; (3) the attacker deposits/holds additional tranche tokens and calls `requestWithdraw` again in any subsequent epoch; (4) after one more epoch passes, `claimWithdrawRequest` pays the full pre-haircut basis. No privileged cooperation is needed, no reentrancy, no race — just sequencing around honest manager calls. The only constraint is that `epochEndDate != 0` (pool not closed) when claiming.

### Recommendation
Track loss-adjusted receipts per epoch rather than keying on `lastWithdrawRequest`. Options:
- Iterate over all epochs with `lossRecoveryPriceByEpoch[e] != 0` for the user (e.g., keep a per-user list of request epochs, or check `withdrawsRequestsByEpoch[_user][e]` against every epoch that has a recorded loss price), or
- In `_claimFundedWithdrawRequest`, subtract from `withdrawsRequests[_user]` any basis whose epoch has a nonzero `lossRecoveryPriceByEpoch` and route it through the haircutted path regardless of `lastWithdrawRequest`, or
- Store per-user-per-epoch loss price resolution eagerly: when a new `requestWithdraw` would move `lastWithdrawRequest` past a pending loss epoch, settle/clear that epoch's basis first.

### Proof of Concept
Foundry fork PoC sketch (following `test/foundry/IdleCreditVault.t.sol` conventions, `_useStandardEpochVariant` / `_startEpochAndCheckPrices` / `_stopEpochWithDuration`-style helpers):

```solidity
function testLossReceiptReRequestParClaim() external {
    _useStandardEpochVariant();
    address attacker = makeAddr('attacker');
    address honest = makeAddr('honest');

    // Both users deposit; attacker holds AA tranche tokens
    uint256 tAtt = _depositWithUser(attacker, 100e6);
    _depositWithUser(honest, 100e6);

    // Epoch 0: attacker requests withdraw of all tranches
    _startEpochAndCheckPrices(0);
    uint256 basis = cdoEpoch.requestWithdraw(tAtt, address(AAtranche)); // == pendingWithdraws

    // Borrower repays with a realized loss: stopEpochWithDuration funds only half
    // (lossRecoveryPriceByEpoch[1] == 0.5e18). pendingWithdraws -> 0, strategy
    // receives basis/2 underlying.
    _stopEpochWithLoss(basis / 2); // collects _amount < pendingBasis

    // Epoch 1 (running): attacker requests a NEW withdraw from remaining tranche
    // tokens -> lastWithdrawRequest[attacker] = newEpoch, overwrote loss epoch.
    uint256 tAtt2 = _depositWithUser(attacker, 10e6);
    _startEpochAndCheckPrices(1);
    cdoEpoch.requestWithdraw(tAtt2, address(AAtranche));

    // Epoch 2 passes so epochNumber > lastWithdrawRequest[attacker]
    _startEpochAndCheckPrices(2);
    _stopCurrentEpochWithApr(10e18);

    // _claimLossAdjustedWithdrawRequest looks up lossRecoveryPriceByEpoch[newEpoch]
    // == 0 and skips; _claimFundedWithdrawRequest pays withdrawsRequests[attacker]
    // == basis + newRequest at PAR, while strategy only holds basis/2 + newRequest.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    // Attacker received the un-haircutted basis: excess = basis * (1 - 0.5)
    assertGe(paid, basis + tAtt2_value, 'paid full basis instead of haircut');
    // Invariant broken: strategy underlyings now short by basis * (1 - lossRecoveryPrice)
    // -> honest user's subsequent claimWithdrawRequest reverts on transfer.
}
```

Key assertion: `paid` equals `withdrawsRequests[attacker]` at par even though the loss-epoch portion was only funded at `lossRecoveryPriceByEpoch`, demonstrating a `basis * (1 - price)` overpayment drained from funds owed to `honest`.
