## Analog Vulnerability Found

### Title
Paused vault units remain freely transferable via standard ERC20 `transfer`/`transferFrom`, allowing sale of frozen/un-redeemable shares to unaware buyers - ([File: v3/src/core/MultiDepositorVault.sol])

### Summary
`MultiDepositorVault` blocks `enter`/`exit` (mint/redeem) with the `whenNotPaused` modifier when the vault is paused, but the underlying ERC20 unit token's standard `transfer`/`transferFrom` functions are never gated by pause state. The `_update` override only checks the `beforeTransferHook` and `areUserUnitsLocked`, so a holder can dump paused (and thus temporarily un-redeemable) vault units on a DEX or OTC counterparty who is unaware the vault is frozen. This directly mirrors the disclosed Primitive Protocol issue where paused/expired option tokens remained freely transferable even though minting/exercising was blocked.

### Finding Description
`enter` and `exit` in `MultiDepositorVault` are gated with `whenNotPaused`: [1](#0-0) 

However, the token's transfer path (`_update`, invoked by the inherited OZ `ERC20.transfer`/`transferFrom`) has no pause check at all — it only consults the `beforeTransferHook` and the provisioner's `areUserUnitsLocked` flag: [2](#0-1) 

`pause()` is reachable by the guardian (a normal, expected operational trigger — typically fired in response to a detected pricing/oracle issue or exploit): [3](#0-2) 

Because `PriceAndFeeCalculatorV2.isVaultPaused`/`convertTokenToUnitsIfActive` also reverts when paused, the last valid price becomes frozen and redemption via `ProvisionerV2` is disabled while the vault is paused: [4](#0-3)  — yet nothing stops an ordinary holder from calling the vault's own `transfer`/`transferFrom` to move units to any counterparty (secondary market, DEX pool, OTC buyer) during this window.

### Impact Explanation
A holder with early knowledge that the vault is about to be/has been paused (e.g., due to a detected oracle fault, insolvency, or exploit) can offload their vault units to an unaware buyer before the market prices in the freeze. The buyer receives units that cannot be redeemed (via `enter`/`exit`) until the vault is unpaused, and may ultimately be worth less than paid if the pause was triggered by an adverse event — a direct value transfer/freeze of the buyer's funds with no recourse, since `exit` reverts while paused.

### Likelihood Explanation
No privileged/guardian collusion is required beyond the guardian's ordinary, expected act of pausing (a normal operational safety feature); the "attacker" is simply an ordinary vault-unit holder using the standard ERC20 `transfer` function, which requires no special permission and is always publicly reachable.

### Recommendation
Add a pause check to `MultiDepositorVault._update` (excluding mint/burn paths already gated at `enter`/`exit`) so that peer-to-peer transfers of vault units are also blocked while the vault is paused, or explicitly document this as expected behavior and require integrators/DEXs to check `paused()` before accepting vault units.

### Proof of Concept
1. Deploy `MultiDepositorVault` + `ProvisionerV2` + `PriceAndFeeCalculatorV2` per test harness; have `attacker` deposit via `enter` to mint units.
2. Call `vault.pause()` from the guardian address.
3. From `attacker`, call `vault.transfer(victim, amount)` — assert it succeeds (no revert).
4. From `victim`, attempt to redeem via `provisioner.requestRedeem`/sync redeem path leading to `vault.exit` — assert it reverts with the pause-related error, proving the victim received a temporarily frozen/un-redeemable asset that was still freely transferable.

    /// @notice Internal function to update token balances with transfer hook checks
    /// @param from The address tokens are transferred from
    /// @param to The address tokens are transferred to
    /// @param amount The amount of tokens to transfer
    /// @inheritdoc ERC20
    function _update(address from, address to, uint256 amount) internal override {
        IBeforeTransferHook hook = beforeTransferHook;
        if (address(hook) != address(0)) {
            // Requirements: perform before transfer checks
            hook.beforeTransfer(from, to, provisioner);
        }

        // Requirements: check that the from address does not have its units locked
        // from == address(0) is to allow minting further units for user with locked units
        // to == address(0) is to allow burning units in refundDeposit
        require(
            from == address(0) || to == address(0) || !IProvisionerV2(provisioner).areUserUnitsLocked(from),
            Aera__UnitsLocked()
        );

        // Effects: transfer the tokens
        return super._update(from, to, amount);
    }
