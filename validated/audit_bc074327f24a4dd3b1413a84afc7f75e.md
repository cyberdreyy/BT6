### Title
Miner's `StackerDBListener` double-counts stale rejection weight after a signer switches its vote to acceptance, causing spurious `SignersRejected` on an already-approved block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The report's underlying bug class is a state-mismanagement/accounting bug: state recorded when the debt was burnt directly (the shortfall) is never reconciled against a later payout, so two independently-tracked balances (debt-owed vs proceeds-paid) drift apart and a party benefits from stale accounting. The closest in-scope analog is in the miner's signer-response tally: `total_weight_approved` and `total_weight_rejected` are two independently-accumulated counters over the same signer weight budget, and nothing clears a signer's earlier vote from one bucket when it later casts the opposite vote in the other bucket.

### Finding Description
`StackerDBListener` tracks, per block, `total_weight_approved` and `total_weight_rejected`, gated by two different membership sets:

- On `Accepted`, the weight is only guarded by `block.gathered_signatures.contains_key(&slot_id)`: [1](#0-0) 

- On `Rejected`, the weight is guarded by `block.responded_signers.insert(slot_id)`: [2](#0-1) 

If a signer for slot `S` first sends `Rejected` (its weight is added to `total_weight_rejected`, and `slot_id` is inserted into `responded_signers`), and *later* sends `Accepted` for the same block (a legitimate flow: a locally-rejected block can be re-evaluated and locally accepted, per the documented `LocallyRejected -> LocallyAccepted` transition), the acceptance code checks `gathered_signatures`, not `responded_signers`. Since `gathered_signatures` never contained this slot, the code adds `S`'s weight to `total_weight_approved` as well - without ever subtracting it from `total_weight_rejected`.

The result: `S`'s weight is now counted in *both* `total_weight_approved` and `total_weight_rejected` simultaneously, breaking the invariant that a signer's weight should count toward at most one side of the tally (the "aggregated-weight vs verified-accepts" equality called out in scope).

This matters because `signer_coordinator.rs` evaluates rejection weight and acceptance weight independently, checking the rejection condition first: [3](#0-2) 

Because stale rejection weight from a signer that has since switched to `Accepted` is never cleared, `block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` can become true purely from accumulated *stale* rejections, even while the same or other signers' current votes would otherwise reach the 70% approval threshold. Since the rejection branch is checked first, the miner can conclude `SignersRejected` (excluding transactions, temporarily or permanently) on a block that the live signer set would otherwise approve.

### Impact Explanation
This is a coordinator-level accounting bug reachable by ordinary vote reconsideration from a single non-majority signer (no majority collusion required): one signer rejecting and later accepting the same block proposal is enough to inflate `total_weight_rejected` with weight that no longer represents a live rejection. This can cause the miner to spuriously treat a legitimately-approvable block as globally rejected, permanently/temporarily excluding transactions and wedging tenure block production - a liveness issue in the coordinator that aggregates signer responses for block production, which is explicitly in scope (`signer_set`/coordinator).

### Likelihood Explanation
Vote flip-flopping (reject-then-accept) is a documented, legitimate state transition (`LocallyRejected -> LocallyAccepted` "re-evaluated") that occurs naturally when a signer's earlier rejection reason becomes stale and it re-evaluates the same proposal favorably. No majority or malicious collusion is needed - a single signer taking this normal path is sufficient to introduce the accounting skew. However, whether this skew is large enough in practice to flip the coordinator's before/after threshold comparison depends on how many signers are near the 30%/70% boundary at the time, so likelihood of *observable* misbehavior is moderate rather than certain per-flip.

### Recommendation
Track a signer's most-recent verdict as a single source of truth (e.g., a `HashMap<slot_id, Verdict>` where `Verdict` is `Accepted` or `Rejected`), and derive `total_weight_approved`/`total_weight_rejected` by summing over that map rather than by two independently-incremented counters. When a new verdict for a slot supersedes an old one, subtract the stale entry's weight from its previous bucket before adding it to the new one, mirroring the `check_state`-guarded, single-authoritative-state approach already used for `BlockState` in `signerdb.rs`.

### Proof of Concept
1. Miner proposes block `B`; signer `S` (weight `w`) evaluates it and sends `BlockResponse::Rejected` (e.g., because of a transient `check_block_against_signer_db_state` failure).
   - `stackerdb_listener.rs`: `block.total_weight_rejected += w`; `responded_signers.insert(S)`.
2. Conditions change (the rejection's cause becomes stale per `should_reevaluate_reject_reason`), and `S` legitimately re-evaluates and sends `BlockResponse::Accepted` (a signature) for the same `B`.
   - `stackerdb_listener.rs` acceptance path only checks `gathered_signatures.contains_key(&S)` (false, since `S` never accepted before) and adds `block.total_weight_approved += w`. `total_weight_rejected` is left unchanged, still containing `w`.
3. Now `total_weight_approved + total_weight_rejected` includes `w` twice, violating the intended one-vote-per-signer accounting.
4. In `signer_coordinator.rs`'s wait loop, if enough other signers' rejections (real, live ones) combine with `S`'s stale rejected weight, `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can trip and return `Err(NakamotoNodeError::SignersRejected{...})` even though `total_weight_approved` (which now correctly includes `S`) may have also reached `weight_threshold` - the miner discards a block/set of transactions that the live signer set was willing to approve.
