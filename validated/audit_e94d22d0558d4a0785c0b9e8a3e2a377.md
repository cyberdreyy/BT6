### Title
Front-running `setVault` allows the old vault to drain idle underlying using its standing allowance - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower` grants the configured ERC4626 vault an unlimited underlying-token allowance during initialization and revokes that allowance only when `setVault` is called. [1](#0-0) [2](#0-1) 

### Finding Description
Initialization grants `vault` unlimited spending rights over `underlyingToken`. [1](#0-0) 

When the owner or manager calls `setVault`, the function verifies that epoch accounting is inactive and that the old-vault share balance is zero, then calls `underlyingToken.safeApprove(address(vault), 0)`. [3](#0-2) 

That revocation transaction is not atomic with any protection against the old spender. [4](#0-3) 

A malicious or compromised old vault can observe the pending `setVault` transaction and front-run it with `underlyingToken.transferFrom(address(programmableBorrower), attacker, idleBalance)`. [2](#0-1) 

Because the unlimited allowance remains active until the revocation transaction executes, the front-running `transferFrom` succeeds. [1](#0-0) 

### Impact Explanation
The old vault can steal the entire underlying balance held directly by `ProgrammableBorrower`, causing a loss equal to `underlyingToken.balanceOf(address(programmableBorrower))`. [5](#0-4) 

This can occur in the buffer or otherwise inactive-epoch phase because `setVault` requires `epochAccountingActive == false` and `vault.balanceOf(address(this)) == 0`. [6](#0-5) 

The zero-share check prevents switching while a vault position remains recorded, but it does not protect cash that was already redeemed or repaid to the contract. [7](#0-6) 

The broken invariant is asset solvency: funds accounted for as borrower-facility assets can be removed by the previous spender immediately before its authorization is revoked. [8](#0-7) 

### Likelihood Explanation
Exploitation requires the previously configured vault to be malicious or compromised and an owner or manager to submit a public `setVault` transaction while the adapter holds idle underlying. [3](#0-2) 

The opportunity is deliberately created by the migration flow: the contract has already unwound all vault shares, so redeemed cash can be present, while the old vault's unlimited ERC20 allowance has not yet been removed. [3](#0-2) 

No epoch guard, KYC check, borrower check, or reserve check prevents the old spender from calling the token directly before `safeApprove(oldVault, 0)` executes. [9](#0-8) 

### Recommendation
Do not maintain an unlimited standing ERC20 allowance for a replaceable external vault. [1](#0-0) 

Use exact, transaction-scoped approvals around each vault deposit and reset the allowance to zero immediately after the deposit. [10](#0-9) 

Alternatively, make the vault immutable and deploy a replacement `ProgrammableBorrower` for migration, or execute the revocation through a private transaction channel so the old spender cannot observe and front-run it. [11](#0-10) 

### Proof of Concept
The following Foundry sequence demonstrates the race on a fork or fixture where `pb` is an initialized `ProgrammableBorrower`, `oldVault` is its configured vault, `underlying` is its configured asset, and `manager` can call `setVault`. [12](#0-11) 

```solidity
function testOldVaultFrontRunsAllowanceRevocation() public {
    uint256 stolen = 1_000e6;

    // ProgrammableBorrower is in the buffer phase and has unwound the old vault,
    // leaving underlying cash in the adapter.
    deal(address(underlying), address(pb), stolen);
    vm.mockCall(
        oldVault,
        abi.encodeWithSelector(IERC4626.balanceOf.selector, address(pb)),
        abi.encode(0)
    );

    assertEq(
        underlying.allowance(address(pb), oldVault),
        type(uint256).max,
        "old vault lacks standing allowance"
    );

    // The malicious old vault observes manager.setVault(newVault) and front-runs it.
    vm.prank(oldVault);
    underlying.transferFrom(address(pb), attacker, stolen);

    // The manager transaction still succeeds and revokes the now-useless allowance.
    vm.mockCall(
        newVault,
        abi.encodeWithSelector(IERC4626.asset.selector),
        abi.encode(address(underlying))
    );
    vm.prank(manager);
    pb.setVault(newVault);

    assertEq(underlying.balanceOf(attacker), stolen, "old vault did not steal cash");
    assertEq(underlying.balanceOf(address(pb)), 0, "adapter cash was not drained");
    assertEq(underlying.allowance(address(pb), oldVault), 0, "old vault was not revoked");
}
```

The critical ordering is `oldVault.transferFrom(...)` before `pb.setVault(newVault)`, because `setVault` revokes the old spender only after the function body begins executing. [2](#0-1)

  /// @notice Set the vault used to deploy idle funds.
  /// @dev Owner or manager. This does not migrate an existing position. The operator must first
  /// withdraw from the old vault and wait until epoch accounting is inactive, otherwise assets can
  /// remain stranded there and the live accounting views will stop including them after the switch.
  /// @param _vault new ERC4626 vault address
  function setVault(address _vault) external {
    _checkOnlyOwnerOrManager();
    if (_vault == address(0) || IERC4626(_vault).asset() != address(underlyingToken)) {
      revert InvalidAddress();
    }
    // Switching the accounting source is only safe once the current epoch is fully settled and the
    // old vault position has been unwound.
    if (epochAccountingActive || vault.balanceOf(address(this)) != 0) revert NotAllowed();
    underlyingToken.safeApprove(address(vault), 0);
    vault = IERC4626(_vault);
    _allowUnlimitedSpend(address(underlyingToken), _vault);
    emit VaultUpdated(_vault);
