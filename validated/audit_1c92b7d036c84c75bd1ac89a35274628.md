### Title
Raw internal error text leaked to unauthenticated callers via AuthenticateByToken → jsonAPIError - ([File: core/web/auth/auth.go])

### Summary
In `AuthenticateByToken`, when `FindUserByAPIToken` fails with any error other than `sql.ErrNoRows` or `clsessions.ErrUserSessionExpired`, the raw underlying error is returned unmodified and propagated to `Authenticate`, which passes it to `jsonAPIError`. That helper calls `err.Error()` directly into the JSON response body sent to the (unauthenticated) caller.

### Finding Description
`AuthenticateByToken` (`core/web/auth/auth.go` lines 93-99) calls `authr.FindUserByAPIToken(ctx, token.AccessKey)` [1](#0-0)  using only an `X-API-KEY`/`X-API-SECRET` header pair supplied by any unauthenticated caller. If the lookup fails with anything other than `sql.ErrNoRows` or `clsessions.ErrUserSessionExpired` (e.g., a DB timeout, connection failure, or other backend error), the function returns the raw `err` value untouched, rather than wrapping it in a generic `auth.ErrorAuthFailed`.

That returned error propagates up through the `Authenticate` middleware loop, which since it is not `auth.ErrorAuthFailed`, aborts and calls `jsonAPIError(c, http.StatusUnauthorized, err)` [2](#0-1) . `jsonAPIError` (`core/web/auth/helpers.go`) does not redact or genericize non-`JSONAPIErrors` errors — it directly serializes `err.Error()` into the response body via `models.NewJSONAPIErrorsWith(err.Error())` [3](#0-2) .

Nothing in the request path filters or redacts this error before it reaches the HTTP response: no role check, no presenter, and no generic-message substitution exists for this branch. The severity depends entirely on what the concrete `Authenticator` implementation (e.g., `localauth`, `ldapauth`, `oidcauth` — see `core/sessions/localauth/orm.go`, `core/sessions/ldapauth/ldap.go`, `core/sessions/oidcauth/oidc.go`) returns as the underlying error on non-not-found failures; if that includes driver-level messages (e.g., pq/database driver errors that can embed connection details or query context in some error wrapping styles), those details are returned to the client.

### Impact Explanation
This is an information-disclosure issue: an unauthenticated attacker who triggers a transient backend failure during `FindUserByAPIToken` (e.g., a DB outage, timeout, or unexpected query error) could receive raw internal error text in the 401 response body. Depending on what error strings the underlying auth provider (postgres driver, ldap client, oidc client) produces, this could reveal internal implementation details, though direct secret/connection-string leakage would require the underlying driver to embed such data in its error `Error()` string, which is not something this code path controls. This is a low-severity confinement/hardening issue rather than a direct key or credential leak, since typical Go SQL driver errors surfaced via `database/sql`/`pgx` rarely embed connection strings in `Error()`.

### Likelihood Explanation
No privileges are required — any unauthenticated client sending a request with `X-API-KEY`/`X-API-SECRET` headers reaches this code path. Triggering the non-`ErrNoRows` branch, however, requires the backend to actually fail in some way other than "row not found" (e.g., DB connectivity issue, timeout), which is not attacker-controllable on demand under normal operating conditions. This makes exploitation opportunistic/environment-dependent rather than reliably reproducible by the attacker alone.

### Recommendation
In `AuthenticateByToken`, do not return the raw `err` for non-not-found failures; log it internally and return a generic error (e.g., `auth.ErrorAuthFailed` or a new sentinel like `errors.New("internal authentication error")`) so `jsonAPIError` never serializes internal error strings to unauthenticated callers. Apply the same treatment to the analogous branch in `AuthenticateExternalInitiator` (`errors.Wrap(err, "finding external initiator")`) since it has the same pattern.

### Proof of Concept
Go handler-level test plan:
1. Create a mock `Authenticator` (using `core/sessions/mocks` or an inline mock satisfying the `Authenticator` interface).
2. Configure `FindUserByAPIToken` to return `nil, errors.New("dial tcp 10.0.0.5:5432: connect: connection refused")` (simulating a DB connectivity error, not `sql.ErrNoRows`).
3. Build a `gin.Engine` wrapping a test route with `auth.Authenticate(mockAuthr, auth.AuthenticateByToken)`.
4. Send a request with `X-API-KEY`/`X-API-SECRET` headers set to arbitrary values.
5. Assert the HTTP status is 401 and the response body via `models.NewJSONAPIErrorsWith` contains the literal string `"dial tcp 10.0.0.5:5432: connect: connection refused"` — confirming the raw error text is leaked.
6. After the fix, assert the response body only contains a generic message (e.g., `"unauthorized"`), and assert the raw text is logged server-side (e.g., via `c.Errors` or logger, not the JSON body).

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
