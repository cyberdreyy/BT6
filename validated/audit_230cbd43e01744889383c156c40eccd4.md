### Title
Instant-withdraw receipts can be claimed before borrower funding arrives, draining other users' funded withdraw claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` mints the user a 1:1 strategy-token receipt and only raises `pendingInstantWithdraws` — no underlying moves. The matching `claimInstantWithdrawRequest` burns that receipt and immediately transfers underlying from the vault's own balance, with no check that the borrower has actually funded the instant queue (which only happens when the CDO calls `collectInstantWithdrawFunds` at the next `startEpoch`). Like CVE-2022-32742 — where an SMB1 write was fulfilled with server memory the client never supplied — the claim is fulfilled with vault-held underlying the requester never supplied: funds already collected for other users' funded normal withdraw receipts (or prefunded instant reserves).

### Finding Description
In `requestInstantWithdraw`, the CDO's strategy tokens are burned and an equal receipt is minted to the user; `pendingInstantWithdraws` grows but no underlying is pulled (`IdleCreditVault.sol:356-375`). The underlying is only sourced later: `collectInstantWithdrawFunds` does `underlyingToken.safeTransferFrom(idleCDO, ...)` when the CDO collects instant funds at epoch start (`IdleCreditVault.sol:398-403`).

`claimInstantWithdrawRequest` then burns the full `instantWithdrawsRequests[_user]` and pays it out via `_transferFundedClaim` from the vault's balance — with no epoch gate and no check against `pendingInstantWithdraws` (`IdleCreditVault.sol:380-393`). The vault's underlying balance legitimately contains unfunded receipts' backing: underlying collected via `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`) sits in the strategy until each user calls `claimWithdrawRequest`. The CDO-side `claimInstantWithdrawRequest` only checks the `allowInstantWithdraw` flag (`IdleCDOEpochVariant.sol:975-979`), not whether the instant bucket was funded.

Attack path: APR drops mid-epoch → attacker's `requestWithdraw` routes to `requestInstantWithdraw` (`IdleCDOEpochVariant.sol:761-770`) → attacker calls `claimInstantWithdrawRequest` in the same transaction/epoch, before `startEpoch` collects instant funds → vault pays the attacker out of other users' already-funded normal withdraw receipts → those users' later `claimWithdrawRequest` reverts on insufficient balance.

### Impact Explanation
Direct theft with quantified loss up to `min(instant receipt claimed, vault underlying balance of funded-but-unclaimed receipts)`. In fixed-APR deployments the instant path triggers whenever `lastEpochApr > unscaledApr + instantWithdrawAprDelta` (`IdleCDOEpochVariant.sol:761-769`), an unprivileged user-reachable condition while APR is being set down. Every unfunded instant claim paid early converts some other user's funded receipt into an unbacked one — a solvency/one-receipt-one-payout violation.

### Likelihood Explanation
Requires: instant withdrawals enabled (`!disableInstantWithdraw`, non-programmable borrower — confirmed in `_isInstantWithdrawEnabled`), `allowInstantWithdraw` flag set, an APR decrease, and unclaimed funded receipts sitting in the vault — a normal state between `stopEpoch` funding and user claims. All roles involved are unprivileged; the honest-manager calls (`startEpoch`/`stopEpoch`) are sequenced around, not performed by, the attacker. Caveat: if `allowInstantWithdraw` is normally only enabled at the same instant funds are collected, the window shrinks; I could not fully confirm the flag's lifecycle or the exact `_transferFundedClaim` balance accounting within the available iterations.

### Recommendation
Gate `claimInstantWithdrawRequest` on actual funding: e.g., track a funded instant bucket incremented in `collectInstantWithdrawFunds` and decrement `pendingInstantWithdraws` on claim, or record the request epoch and require `epochNumber`/`startEpoch` collection to have passed before paying. Alternatively, reserve underlying per instant claim at funding time (as `defaultRecoveryReserve` does) so early claims cannot consume normal receipts' backing.

### Proof of Concept
Foundry fork PoC sketch:
```solidity
// Setup: deposit so user A has a funded, unclaimed normal withdraw receipt.
idleCDO.depositAA(A_AMOUNT);          // user A
cdoEpoch.requestWithdraw(A shares);   // user A normal request
cdoEpoch.startEpoch();                // manager, honest
// borrower repays; stopEpoch funds pendingWithdraws -> vault holds A's underlying
cdoEpoch.stopEpoch(0, 0);             // manager, honest; collectWithdrawFunds pulls funds
// user A does NOT claim yet; vault balance = A's funded receipt

// Attacker B: deposits, then APR drops so requestWithdraw goes instant.
idleCDO.depositAA(B_AMOUNT);          // attacker
strategy.setApr(lowerApr);            // manager-configured lower APR next epoch (honest call)
cdoEpoch.requestWithdraw(B shares);   // attacker -> requestInstantWithdraw, receipt minted, pendingInstantWithdraws += B
// Vault received NO underlying for B's receipt.
uint256 balBefore = underlying.balanceOf(attacker);
cdoEpoch.claimInstantWithdrawRequest(); // burns B's receipt, pays B out of A's funded underlying
assertGt(underlying.balanceOf(attacker) - balBefore, 0);
// Later: user A's claimWithdrawRequest() reverts on insufficient vault balance.
vm.expectRevert(); cdoEpoch.claimWithdrawRequest(); // pranked as A
```
