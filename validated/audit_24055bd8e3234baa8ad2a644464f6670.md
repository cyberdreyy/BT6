### Title
APR0 withdraw receipts escape the loss-recovery haircut applied to same-epoch normal receipts — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` realizes a loss and the borrower under-funds pending withdrawals, `collectWithdrawFunds` stores a `lossRecoveryPriceByEpoch[epochNumber]` haircut that is later applied to normal receipts via `_claimLossAdjustedWithdrawRequest`. APR0 receipts for that same epoch are tracked only in `apr0Users[_user]` and are excluded from `withdrawsRequestsByEpoch`, so they are never reduced by the recovery price — they are paid at par through `_claimFundedWithdrawRequest` (settledPrincipal + principal + settledInterest). This breaks the loss-socialization invariant: two users who requested withdrawals in the same defaulted/loss epoch receive different prices depending solely on the pool's APR mode.

### Finding Description
- `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` when funding is short (lines 411–430).
- Loss-adjusted claims key off `withdrawsRequestsByEpoch[_user][lossEpoch]` (line 265), which is only incremented in the non-APR0 branch (line 293). APR0 requests route to `_requestWithdrawApr0` (line 286) and are never recorded per-epoch.
- In `_claimFundedWithdrawRequest` (lines 319–350), the payout is `normalAmount + apr0PrincipalAmount + apr0InterestAmount` transferred at full value via `_transferFundedClaim` — there is no lookup of `lossRecoveryPriceByEpoch` for `apr0User.principalEpoch`.
- The guard in `requestWithdraw` (lines 263–271) compares `apr0Users[_user].principalEpoch` only against `lastWithdrawRequest[_user]`, i.e. the user's latest request epoch, not any prior loss epoch, so an APR0 user can even keep requesting after a loss epoch without settling the haircut.
- Result: in an epoch where `pendingBasis` is under-funded, an APR0-mode receipt claims 100% while a normal receipt in the identical epoch claims only `recoveryPrice` fraction. The excess paid to APR0 claimants is drawn from the vault reserve/`collectWithdrawFunds` balance that backstops other receipts, directly reducing what same-epoch claimants and LPs recover.

### Impact Explanation
Direct value extraction: an APR0 withdrawer in a loss epoch receives `principal * RECOVERY_FULL` instead of `principal * lossRecoveryPrice`. With a 50% recovery price and 1M USDC of APR0 pending requests, ~500k USDC is overpaid relative to the intended waterfall, producing an equivalent shortfall for other receipt holders or active tranche holders (the difference is absorbed by the vault's funded claim balance / NAV). This is theft via broken loss-waterfall, quantified by `(RECOVERY_FULL - lossRecoveryPrice) * apr0Pending / RECOVERY_FULL`.

### Likelihood Explanation
Requires a pool operating in `unscaledApr == 0` mode (a supported, explicitly coded flow: `_requestWithdrawApr0`, `_settleApr0`, `apr0TotalPrincipal`) and a `stopEpochWithDuration`/`collectWithdrawFunds` partial funding — i.e. a borrower shortfall, which is exactly the scenario the loss-recovery machinery was added for. No privileged misbehavior needed: an unprivileged lender holding APR0 receipts simply calls `claimWithdrawRequest` through the CDO and is overpaid. The gap is structural, not timing-dependent.

### Recommendation
In `_claimFundedWithdrawRequest` (and `_settleApr0`), apply `lossRecoveryPriceByEpoch[apr0User.principalEpoch]` to `apr0User.principal`/`settledPrincipal` the same way normal receipts are haircut, and track unsettled APR0 principal per epoch (e.g. `apr0RequestsByEpoch`) so `requestWithdraw`'s pending-loss guard also catches APR0 receipts from earlier loss epochs, not only `principalEpoch == lastWithdrawRequest`.

### Proof of Concept
Foundry fork sketch on `test/foundry/IdleCreditVault.t.sol` harness:
1. Deploy `IdleCDOEpochVariant` + `IdleCreditVault` with `unscaledApr == 0`; lender A deposits and calls `requestWithdraw` (routes to `_requestWithdrawApr0`).
2. `stopEpoch` → `startEpoch` → borrower under-funds: CDO calls `collectWithdrawFunds(0.5 * pendingWithdraws)`, storing `lossRecoveryPriceByEpoch[e] = 0.5e18`.
3. In a parallel run, lender B uses a fixed-APR pool with identical deposit/request/under-funding.
4. Assert: B claims `amount * 0.5`, while A claims full `amount` — demonstrating same-epoch receipts priced inconsistently and the excess drained from the funded claim reserve.

Note: within my limited search depth I could not fully trace `_settleApr0`/`_claimLossAdjustedWithdrawRequest` internals or confirm this wasn't previously acknowledged; if `_settleApr0` already applies the recovery price, this finding does not hold.
