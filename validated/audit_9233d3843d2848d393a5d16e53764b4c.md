### Title
Stale confirmations from removed multisig members still count toward the K-of-N threshold, allowing requests to execute below quorum - ([File: multisig2/src/lib.rs])

### Summary
`DeleteMember` (and the analogous `DeleteKey` in the original `multisig` contract) only purges the pending *requests* that the removed member itself created. It does not purge the *confirmations* that member gave on requests created by other members. A removed member's stale confirmation therefore keeps counting toward `num_confirmations`, letting a request execute with fewer live, currently-authorized confirmations than the configured threshold.

### Finding Description
`confirm()` counts entries in the `confirmations: HashSet<String>` associated with a request and executes once the count reaches `num_confirmations`: [1](#0-0) 

Membership changes are only handled by `delete_member`, which removes the member from `self.members` and deletes any *requests the member itself authored*, but does not scan or clean the `confirmations` set of other pending requests that member may have confirmed: [2](#0-1) 

`remove_request` (invoked only when a request completes or is explicitly deleted) similarly has no path that is triggered on member removal for requests authored by *other* members: [3](#0-2) 

The original `multisig` contract has the identical gap in `DeleteKey` handling, which purges only requests keyed by the deleted `signer_pk`, not confirmations that key gave to requests signed by other keys: [4](#0-3) 

The custody binding that should hold is: *confirmations counted toward `num_confirmations` == confirmations from currently live/authorized members*. This invariant is broken because a member's confirmation is durable data that outlives their membership.

### Impact Explanation
This lets a `MultiSigRequestAction::Transfer` (or `AddKey`, `FunctionCall`, etc.) execute with only `num_confirmations - 1` (or fewer) *live* member confirmations, plus one stale confirmation from an account/key that has since been revoked (e.g., because it was compromised or intentionally removed for misbehavior). This is exactly the "multisig request executed below threshold" scenario called out as Critical impact — funds can move, or privileged actions (adding a full-access key, deploying new code) can be authorized, without the intended number of currently-trusted signers agreeing.

### Likelihood Explanation
This requires a realistic and even expected operational sequence: a member is removed (e.g. compromised key rotation, offboarding a signer) while they have an outstanding confirmation on a request created by someone else. Since `DeleteMember`/`DeleteKey` are provided precisely to revoke compromised or departing signers, and nothing in the codebase warns operators that pending confirmations by that signer on requests they didn't create must be manually deleted/re-created, this is a plausible operational trap rather than a purely theoretical one.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over **all** pending requests' confirmation sets (not just requests authored by the removed member) and strip the removed member's/key's confirmation from each. Alternatively, revalidate at `confirm()`/execution time that every entry in a request's `confirmations` set still corresponds to a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy multisig with members `[A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request` creating `R1 = Transfer{amount, receiver_id}`.
3. `B` calls `confirm(R1)` → `confirmations(R1) = {B}` (1/3).
4. Separately, members decide to revoke `B` (e.g. suspected key compromise): `C` creates and the group confirms a `DeleteMember{member: B}` request, which executes `delete_member` — this removes `B` from `self.members` but does **not** touch `confirmations(R1)`, since `R1` was authored by `A`, not `B` (`delete_member` filter is `r.member == member`).
5. Now `members = [A, C, D]`, but `confirmations(R1)` still contains the stale entry from `B`.
6. `A` calls `confirm(R1)` → `confirmations(R1) = {B, A}` (2/3).
7. `C` calls `confirm(R1)` → count reaches 3 ≥ `num_confirmations` → `execute_request` fires the `Transfer`, even though only 2 of the 3 confirmations (`A`, `C`) came from currently live members — `B`'s confirmation was from an already-revoked signer.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
