### Title
`/v2/config` and `/v2/config/v2` routes lack role gating, exposing full effective TOML config to view-role users - ([File: core/web/router.go])

### Summary
The routes `authv2.GET("/config", cc.Show)` and `authv2.GET("/config/v2", cc.Show)` are registered with only the base `authv2` group authentication (session or API token) and no `auth.RequiresEditRole`/`auth.RequiresAdminRole` wrapper, unlike nearly every other sensitive route in the same function. [1](#0-0)  This allows any authenticated user, including one with the lowest `UserRoleView` role, or a restricted API token bound to a view-role user, to call `ConfigController.Show` and retrieve the full effective node configuration.

### Finding Description
`v2Routes` builds `authv2` as a group requiring only `auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)`, with no role check at the group level. [2](#0-1)  Individual routes are then expected to additionally wrap handlers with `auth.RequiresRunRole`, `auth.RequiresEditRole`, or `auth.RequiresAdminRole` as seen throughout the same function (e.g. bridge types, keys, jobs, transfers). [3](#0-2)  The config routes are the exception: `cc.Show` is passed directly with no such wrapper. [1](#0-0) 

`ConfigController.Show` returns the effective TOML config (or user-only config with `?userOnly=true`) via `cfg.ConfigTOML()`, wrapped in a `ConfigV2Resource` and serialized as the JSON API response — with no role check inside the handler itself. [4](#0-3)  The role-check helpers `RequiresRunRole`, `RequiresEditRole`, and `RequiresAdminRole` in `core/web/auth/auth.go` are the only mechanisms that enforce minimum roles; since they aren't applied here, any user who passes basic `Authenticate` (session cookie or `X-API-KEY`/`X-API-SECRET` token) reaches the handler regardless of role, including `clsessions.UserRoleView`. [5](#0-4) 

### Impact Explanation
This matches Chainlink's "sensitive information disclosure" impact class: a low-privilege authenticated user (view role) can retrieve the node's full effective configuration TOML, which can include network/database connection settings, feature flags, chain/RPC endpoints, and other operational details useful for further attacks (though not raw secrets, since `ConfigTOML()` presumably applies its own redaction upstream — that redaction logic was not located in this scope). This is a horizontal/vertical authorization exactness violation: a view-role principal accesses data intended to require an elevated role, consistent with every other config/administrative endpoint in the file being gated.

### Likelihood Explanation
Trivial and fully reproducible: any valid session cookie or API token for a user with `UserRoleView` is sufficient. No special conditions, timing, or race is required — a single `GET /v2/config` (or `/v2/config/v2`) request as a view-role user succeeds.

### Recommendation
Wrap both routes with the appropriate minimum role check, consistent with the surrounding routes, e.g.:
```go
authv2.GET("/config", auth.RequiresEditRole(cc.Show))
authv2.GET("/config/v2", auth.RequiresEditRole(cc.Show))
```
(or `auth.RequiresAdminRole` if config data is deemed admin-only per the intended threat model).

### Proof of Concept
Add a table-driven test in `core/web/auth/auth_test.go` style (`TestRBAC_Routemap_ViewOnly` pattern):
1. Set up the router via `web.NewRouter` with a test `chainlink.Application`.
2. Create a session/token for a user with `sessions.UserRoleView`.
3. Issue `GET /v2/config` and `GET /v2/config/v2` with that session/token.
4. Assert response status is `200 OK` (not `401`/`403`), and response body contains a non-empty `config` field from `ConfigV2Resource`.
5. Compare against a control case using a route wrapped with `RequiresAdminRole` (e.g. `GET /v2/keys/eth/import` with a bogus body) to confirm the view-role user correctly gets `403 Forbidden` there, demonstrating the inconsistency: config endpoints permit view role while comparable admin-tier endpoints correctly reject it.

```go
func (cc *ConfigController) Show(c *gin.Context) {
	cfg := cc.App.GetConfig()
	var userOnly bool
	if s, has := c.GetQuery("userOnly"); has {
		var err error
		userOnly, err = strconv.ParseBool(s)
		if err != nil {
			jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("invalid bool for userOnly: %w", err))
			return
		}
	}
	var toml string
	user, effective := cfg.ConfigTOML()
	if userOnly {
		toml = user
	} else {
		toml = effective
	}
	jsonAPIResponse(c, ConfigV2Resource{toml}, "config")
}
```

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
