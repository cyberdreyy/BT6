### Title
Stale Cached Role/Session Grants Elevated Access After Upstream LDAP/OIDC Revocation - (File: core/sessions/oidcauth/oidc.go, core/sessions/ldapauth/ldap.go)

### Summary
When using the pluggable LDAP or OIDC `AuthenticationProvider`, a user's role and session validity are cached locally in `oidc_user_api_tokens`/`ldap_user_api_tokens` and `oidc_sessions`/`ldap_sessions` tables at login/token-issuance time, and are only re-validated against the upstream identity provider on a periodic sync interval (`reaper.go`), not on every request.

### Finding Description
`FindUserByAPIToken` for both providers reads a locally cached role and expiry, explicitly documented as skipping any upstream check per-request: [1](#0-0)  and the LDAP equivalent [2](#0-1) . The package doc for LDAP explicitly states: "User session and roles are cached and revalidated with the upstream service at the interval defined in the local LDAP config... This sync happens for every auth endpoint hit, and via the defined sync interval." [3](#0-2) 

This mirrors the Blur `ExecutionDelegate` bug class: a privilege grant (role/session) can outlive its intended validity window because revocation on the authoritative source (upstream LDAP/OIDC group membership, i.e., the "owner") does not immediately propagate to the node's local trust store, and the actual authorization check (`FindUserByAPIToken`/`AuthorizedUserWithSession`) trusts the stale local cache rather than re-verifying against the source of truth in real time. Enforcement of RBAC (`RequiresAdminRole`, `RequiresEditRole`, `RequiresRunRole`) in `core/web/auth/auth.go` [4](#0-3)  is only as strong as the freshness of the cached `user.Role` value it reads from `GetAuthenticatedUser`.

### Impact Explanation
If an operator revokes or demotes a user in the upstream identity provider (e.g., removes them from the admin group after a compromise or offboarding), that user's already-issued API token or session cookie continues to authenticate with the old (potentially elevated, e.g., `admin`) role until the next scheduled sync interval elapses. During that window, the "revoked" credential functions exactly like Blur's `revokedApproval` being front-runnable — the node keeps honoring a grant the true owner (upstream IdP) intended to have already been withdrawn — enabling unauthorized job runs, key/secret access, or admin actions gated by `RequiresAdminRole`.

### Likelihood Explanation
Requires an unprivileged/former-privileged actor who already possesses a valid, previously-issued API token or session cookie (no additional bypass of authentication itself is needed) and who is deliberately or accidentally deprovisioned upstream. Likelihood depends heavily on the operator-configured `UpstreamSyncInterval`; the documented mechanism exists specifically because this window is a known tradeoff, which increases confidence this is a real, not hypothetical, exposure. However, exploiting it requires an already-authenticated token before revocation, which somewhat limits it to insider/former-employee scenarios rather than a fully anonymous unprivileged-client attack — I could not verify the exact default sync interval value or confirm whether any additional per-request freshness check exists beyond what these snippets show, due to not finding the constructor/default config wiring within available tool calls.

### Recommendation
Reduce the trust window by validating role/session freshness against the upstream provider synchronously on sensitive actions (e.g., before honoring `RequiresAdminRole`/`RequiresEditRole`), or shorten the default `UpstreamSyncInterval` and force immediate token invalidation on any detected role change, in addition to the periodic reaper sync.

### Proof of Concept
Conceptual sequence (not independently executed):
1. Admin user authenticates via OIDC, receives session cookie; `oidc_sessions` row created with `user_role='admin'` [5](#0-4) .
2. Upstream IdP administrator removes the user's admin group claim.
3. Before the next `UpstreamSyncInterval` sync/reaper run, the user replays the same session cookie against an admin-only endpoint; `AuthorizedUserWithSession`/`FindUserByAPIToken` returns the stale cached `admin` role, and `RequiresAdminRole` passes the request through [6](#0-5) .

// FindUserByAPIToken retrieves a possible stored user and role from the oidc_user_api_tokens table store
func (oi *oidcAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (clsessions.User, error) {
	if !oi.config.UserAPITokenEnabled() {
		return clsessions.User{}, errors.New("API token is not enabled")
	}

	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc user API token table for given token, user role and email are cached so
		// no further upstream OIDC query is performed, sessions and tokens are synced against the upstream server
		// via the UpstreamSyncInterval config and reaper.go sync implementation
		var foundUserToken struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundUserToken,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_user_api_tokens WHERE token_key = $1",
			apiToken, oi.config.UserAPITokenDuration().Duration(),
		); err != nil {
			return err
		}
		if !foundUserToken.Valid {
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundUserToken.UserEmail,
			Role:  foundUserToken.UserRole,
		}
		return nil

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	return sessions.User{
		Email: foundUserToken.UserEmail,
		Role:  foundUserToken.UserRole,
	}, nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
