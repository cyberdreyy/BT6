### Title
Lockup contracts can keep depositing/staking NEAR into a staking pool after it is removed from the whitelist - (File: lockup/src/owner.rs)

### Summary
The whitelist check for a staking pool is performed exactly once, in `select_staking_pool`, at selection time. Once a pool is recorded in `self.staking_information`, none of the subsequent NEAR-moving owner methods (`deposit_to_staking_pool`, `deposit_and_stake`, `stake`, `unstake`, `withdraw_from_staking_pool`, `unstake_all`, `refresh_staking_pool_balance`) re-verify that the pool is still whitelisted. If the NEAR Foundation removes the pool from the whitelist contract afterward (e.g., because it turned out to be malfunctioning, malicious, or otherwise unsafe), any lockup account that already selected it before removal is unaffected and can keep depositing and staking new NEAR into it.

### Finding Description
`select_staking_pool` (`lockup/src/owner.rs#L12-L41`) calls `ext_whitelist::is_whitelisted` and only on a `true` result does `on_whitelist_is_whitelisted` (`lockup/src/owner_callbacks.rs#L7-L25`) persist `staking_information` with the given `staking_pool_account_id`. From that point forward, `staking_information.staking_pool_account_id` is treated as a permanently trusted destination for NEAR transfers via cross-contract calls such as `ext_staking_pool::deposit_and_stake` (`lockup/src/owner.rs#L151-L159`) and `ext_staking_pool::deposit` (`lockup/src/owner.rs#L105-L113`). There is no mechanism — neither a periodic re-check nor a callback from the whitelist contract — that revokes or blocks further deposits once `remove_staking_pool` (`whitelist/src/lib.rs#L97-L104`) is called by the foundation. The binding that should hold is: `staking_pool_account_id trusted by lockup == staking_pool_account_id currently in WhitelistContract.whitelist`. This equality is only checked at selection time, and diverges permanently the moment the foundation removes the pool while it is still selected by existing lockup accounts.

### Impact Explanation
This falls under the "wrongly whitelisted or wrongly parameterised deployment" / "funds frozen or moved" category: an account that has already selected a since-delisted staking pool can continue transferring NEAR into it via `deposit_and_stake`/`deposit_to_staking_pool`, sidestepping the very protection the whitelist delisting was meant to provide (e.g., if the pool was delisted because it was found to be unable to return delegated funds, as documented in `whitelist/README.md` — "the staking pool should guarantee that the delegated tokens can not be lost or locked ... only approved (whitelisted) accounts ... can receive delegated tokens"). Continued deposits to a delisted, potentially broken pool risk permanent loss/freezing of the owner's NEAR.

### Likelihood Explanation
Requires the foundation to remove a previously-whitelisted pool (a normal, documented remediation action per `whitelist/README.md#L19`) while at least one lockup account has already selected it. This is a realistic post-incident scenario since the whole purpose of `remove_staking_pool` is to react to a compromised or defective pool.

### Recommendation
Re-validate `is_whitelisted` for the currently selected `staking_pool_account_id` at the start of each NEAR-moving operation (`deposit_to_staking_pool`, `deposit_and_stake`, `stake`), rejecting the call (or forcing `unselect_staking_pool`/withdrawal-only mode) if the pool is no longer whitelisted, similar to the recommended split between "post-action" and "liquidation" checks in the original report — here, split into "new deposits/stake require current whitelist membership" versus "withdraw/unstake remain allowed regardless of whitelist status" so existing funds are not trapped.

### Proof of Concept
1. Foundation whitelists `pool.near` via `WhitelistContract::add_staking_pool` (`whitelist/src/lib.rs#L75-L88`).
2. Owner calls `select_staking_pool("pool.near")` on their lockup contract; `on_whitelist_is_whitelisted` stores `staking_information` (`lockup/src/owner.rs#L12-L41`, `lockup/src/owner_callbacks.rs#L7-L25`).
3. Foundation discovers `pool.near` is compromised and calls `remove_staking_pool("pool.near")` (`whitelist/src/lib.rs#L97-L104`); `is_whitelisted("pool.near")` now returns `false`.
4. Owner still calls `deposit_and_stake(amount)` on their lockup contract (`lockup/src/owner.rs#L127-L166`); since this method never re-checks the whitelist, the call succeeds and NEAR is transferred to the now-delisted `pool.near`, exactly as it would have before delisting.
