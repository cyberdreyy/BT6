### Title
Missing solvency check in epoch-queue claims lets rounding-inflated payouts permanently freeze later claimants - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The external report flags a transfer executed without verifying that the contract holds a sufficient balance. The direct analog lives in `IdleCDOEpochQueue`: `claimDepositRequest` and `claimWithdrawRequest` compute each user's payout from a stored epoch price and `safeTransfer` tokens out, without ever checking that the queue's balance can cover the aggregate of all claims. Because `epochPrice`/`epochWithdrawPrice` are computed with truncating division, the sum of individual claims can exceed the tokens actually received by the queue, so the last claimants' transfers revert and their receipts are frozen permanently — there is no partial-claim or top-up path.

### Finding Description
In `processDeposits`, the queue mints `_trancheMinted` tranche tokens for `_pending` underlyings and stores `epochPrice[_epoch] = _pending * ONE_TRANCHE / _trancheMinted` (rounds down). Each user later redeems `amount * ONE_TRANCHE / epochPrice[_epoch]` in `claimDepositRequest` (contracts/IdleCDOEpochQueue.sol:388). Since `epochPrice` is floored, `1/epochPrice >= _trancheMinted/_pending`, and each user's claim is `>=` its exact pro-rata share; the aggregate of floored per-user claims can exceed `_trancheMinted`. The same pattern exists in `processPrefundedDeposits` (line 270) and on the withdraw side where `epochWithdrawPrice[_epoch] = _underlyingsRequested * ONE_TRANCHE / _pending` (line 318) is followed by per-user payouts `amount * _withdrawPrice / ONE_TRANCHE` in `claimWithdrawRequest` (line 409). No function checks `balanceOf(address(this)) >= payout` before transferring, and a failed `safeTransfer` is not handled: the user's receipt (`userDepositsEpochs`/`userWithdrawalsEpochs`) remains set but can never be paid because earlier claimants already drained the balance.

### Impact Explanation
Once aggregate claims exceed the queue-held balance by even 1 wei (which truncating division permits whenever `P * ONE % M != 0` across multiple claimants, and which is amplified in the withdraw path when `processWithdrawalClaims` rebases the price on `_received`), the last claimant(s) calling `claimDepositRequest`/`claimWithdrawRequest` get a revert inside `safeTransfer`. Their whole claim — not just the wei shortfall — is unclaimable, and the queue has no admin function to top up or forgive the deficit, so the receipt is permanently frozen. This is a broken "one receipt, one payout" solvency invariant: the protocol implicitly guarantees each queued depositor/withdrawer a payout but only funds `M`/`_received` tokens while distributing `> M`/`> _received` in expectation.

### Likelihood Explanation
No privileged attacker is needed: an ordinary KYC-passing lender submitting a queue deposit or withdraw request sized so that `pending * ONE_TRANCHE` is not divisible by `minted`/`underlyingsRequested` creates the shortfall deterministically during the buffer phase (`epoch` not running, `isEpochRunning()` gating in `_checkAllowed`). The deficit magnitude is bounded by the number of claimants in wei, but the frozen amount equals the last claimant's entire receipt, so a single crafted dust claim positioned to be processed last (or a victim simply claiming last) yields a disproportionate frozen amount. Existing guards do not stop it: `processWithdrawalClaims` rebases price but never verifies cumulative solvency, `_transferFundedClaim`-style reserve checks exist only inside `IdleCreditVault`, not in the queue, and there is no skim/donation mechanism in `IdleCDOEpochQueue` to restore balance.

### Recommendation
Track per-epoch liabilities explicitly and cap or check payouts, e.g. in `claimDepositRequest`/`claimWithdrawRequest`:

```solidity
uint256 payout = amount * ONE_TRANCHE / epochPrice[_epoch];
require(
  IERC20Detailed(tranche).balanceOf(address(this)) >= payout,
  'Insufficient queue balance'
);
IERC20Detailed(tranche).safeTransfer(msg.sender, payout);
```

Better, store the total tokens actually received per epoch (`epochClaimable`) and pay `amount * epochClaimable[_epoch] / epochTotalReceipts[_epoch]` with a `min(payout, balance)` fallback for the final claimant, mirroring the `_received != _pending` rebase already used in `processWithdrawalClaims`.

### Proof of Concept
Foundry fork sketch against `test/foundry/IdleCDOEpochQueue.t.sol` helpers:

```solidity
function testClaimDepositRequestInsolvency() external {
  // Two queued AA depositors whose amounts make pending*ONE % minted != 0
  _depositWithUser(ALICE, 333 * ONE_SCALE + 1); // crafted dust remainder
  _depositWithUser(BOB,   777 * ONE_SCALE + 2);

  vm.prank(manager);
  queue.processDeposits(); // mints M tranche tokens, stores floored epochPrice

  uint256 epoch = strategy.epochNumber();
  uint256 aliceOut = 333e18 * ONE_TRANCHE / queue.epochPrice(epoch);
  uint256 bobOut   = 777e18 * ONE_TRANCHE / queue.epochPrice(epoch);
  assertGt(aliceOut + bobOut, tranche.balanceOf(address(queue)));

  vm.prank(ALICE);
  queue.claimDepositRequest(epoch);          // succeeds
  vm.prank(BOB);
  vm.expectRevert();                          // ERC20: transfer amount exceeds balance
  queue.claimDepositRequest(epoch);          // BOB's receipt frozen permanently
}
```

The identical sequence applies to `claimWithdrawRequest` after `processWithdrawRequests`/`processWithdrawalClaims` when `epochWithdrawPrice` floors `_underlyingsRequested * ONE_TRANCHE / _pending`.
