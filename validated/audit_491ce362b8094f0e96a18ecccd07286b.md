### Title
Instant `updateMultiplier` failsafe lets a B20Asset OPERATOR_ROLE holder front-run pending ERC-8056 conversion calls to manipulate the exchange rate - (File: crates/common/precompiles/src/b20_asset/logic/v2.rs)

### Summary
The `B20Asset` precompile (`AssetV2`) exposes two multiplier setters: the scheduled `updateUIMultiplier(newMultiplier, effectiveAt)`, which requires a future `effectiveAt` and therefore cannot change the effective rate within the same block a dependent transaction is submitted, and the instant `updateMultiplier(newMultiplier)`, which takes effect immediately at `now` and is reachable by any `OPERATOR_ROLE` holder with a single signed transaction. This mirrors the reported `SwapperImpl.sol#setOracle` pattern: a privileged party can front-run a pending user transaction that depends on a currently-readable conversion rate, and change that rate atomically before the user's transaction executes, extracting value or otherwise deceiving the counterparty about the terms of the exchange.

### Finding Description
`updateMultiplier` is documented as an "Instant failsafe: sets the current multiplier immediately" [1](#0-0)  and its implementation writes the new multiplier synchronously, effective at the current block timestamp, requiring only `OPERATOR_ROLE` (or the factory-privileged bypass): [2](#0-1) 

This multiplier directly determines the ERC-8056 "Scaled UI Amount" conversion functions `toScaledBalance`/`toUIAmount` and `toRawBalance`/`fromUIAmount`, which downstream integrators (vaults, bridges, off-chain quoting systems, corporate-action tooling) use to convert between the underlying raw token accounting and the UI-facing amount: [3](#0-2) 

Because `updateMultiplier` changes this rate with no delay (unlike the scheduled `updateUIMultiplier`, which enforces `effectiveAt > now` [4](#0-3) ), an `OPERATOR_ROLE` holder observing a pending transaction that reads `multiplier()`/`toUIAmount()`/`toRawBalance()` on-chain to size a transfer, redemption, or settlement amount can submit `updateMultiplier` with a favorable value and have it mined immediately before the victim transaction, changing the conversion the victim's transaction relies on within the same block — the same "authorized setter used to front-run a rate a counterparty is relying on" pattern flagged in the external report against `SwapperImpl.sol#setOracle`.

### Impact Explanation
Any protocol or user contract built on top of `B20Asset`'s ERC-8056 surface that computes a raw amount from a UI amount (or vice versa) in the same transaction it submits (e.g., "redeem X UI amount of shares" converted via `toRawBalance` immediately before transferring) can be deceived into transferring more or fewer raw tokens than intended if the operator changes the multiplier atomically beforehand via `updateMultiplier`. This is a value-manipulation/theft vector against integrators relying on the instantaneous multiplier, analogous to the discount-oracle price manipulation in the reported issue.

### Likelihood Explanation
Exploitation requires only that the token's `OPERATOR_ROLE` (a role the token issuer/operator controls) is held by a party willing to abuse it, and that some contract or user computes conversion amounts from the currently-read multiplier before submitting a transaction — a pattern explicitly enabled and documented by the precompile's own "instant failsafe" semantics. No cross-chain state or unusual preconditions are needed; a single signed transaction from the operator suffices to alter the rate before the victim's transaction lands.

### Recommendation
Treat `updateMultiplier` as a genuine emergency-only failsafe: restrict its use to true emergency conditions, or require the same scheduling/delay guarantee as `updateUIMultiplier` (e.g., a minimum future `effectiveAt`) for any multiplier change that is reachable from routine operator actions, so dependent conversions cannot be atomically front-run within the block that a counterparty transaction is submitted.

### Proof of Concept
1. `OPERATOR_ROLE` holder observes a pending transaction from a third-party contract/user that calls `toRawBalance(uiAmount)` (or `fromUIAmount`) on-chain and then transfers the computed raw amount.
2. Before that transaction is included, the operator submits `updateMultiplier(newMultiplier)` (test coverage confirms it applies instantly and is read immediately by `toScaledBalance`/`toRawBalance`, see `golden_update_multiplier_emits_ui_event_at_now`-style flow) [5](#0-4) .
3. The victim transaction's `toRawBalance`/`toUIAmount` call now resolves against the manipulated multiplier, causing it to transfer an amount inconsistent with what the victim intended when it was built/signed, exactly as `SwapperImpl.setOracle` front-running degrades a swapper's quoted price.

    fn update_multiplier(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        new_multiplier: U256,
        privileged: bool,
    ) -> Result<()> {
        let now = token.accounting().timestamp()?;
        self.ensure_operator_role(token, caller, privileged)?;
        if new_multiplier.is_zero() || new_multiplier > Self::MAX_UI_MULTIPLIER {
            return Err(BasePrecompileError::revert(IB20Asset::InvalidMultiplier {}));
        }
        let pending_multiplier = U256::from(token.accounting().pending_multiplier()?);
        let pending_effective_at = U256::from(token.accounting().pending_effective_at()?);
        let live_pending = pending_effective_at > now;

        let old = self.effective_multiplier(token)?;
        token.accounting_mut().set_multiplier(new_multiplier)?;
        if pending_effective_at != U256::ZERO {
            token.accounting_mut().clear_pending_multiplier_and_effective_at()?;
        }

        let product =
            balance.checked_mul(multiplier).ok_or_else(BasePrecompileError::under_overflow)?;

    fn to_raw_balance(&self, token: &B20AssetToken<S, A>, balance: U256) -> Result<U256> {
        let multiplier = self.effective_multiplier(token)?;
        let product = balance
            .checked_mul(B20AssetStorage::WAD)
            .ok_or_else(BasePrecompileError::under_overflow)?;
        Ok(product / multiplier)
    }
