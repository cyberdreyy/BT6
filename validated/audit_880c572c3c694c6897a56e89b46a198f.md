### Title
Deterministic, permission-less lockup address allows front-running/squatting of a victim owner's canonical lockup with attacker-chosen terms - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the lockup sub-account name purely from `owner_account_id` (`hex::encode(&env::sha256(owner_account_id.as_bytes())[..20])`) and enforces no access control beyond `MIN_ATTACHED_BALANCE`. Any unprivileged account can call `create` first for any `owner_account_id`, permanently occupying that deterministic sub-account with self-chosen `vesting_schedule`, `release_duration`, `lockup_duration` and `whitelist_account_id` before the real grantor ever calls `create` for that owner.

### Finding Description
The invariant broken is: `terms_at(hex(sha256(owner_account_id)).<factory>) == terms_chosen_by_owner's_grantor`. In practice, `terms_at(...)` is set by whoever calls `create` first, because:

- `create` computes the target account id solely from the caller-supplied `owner_account_id`, which is public information known before any real grant is made: [1](#0-0) 
- There is no check on who is allowed to call `create` for a given `owner_account_id` — only a minimum-deposit check exists: [2](#0-1) 
- All lockup parameters (`vesting_schedule`, `release_duration`, `lockup_duration`, `staking_pool_whitelist_account_id`) are attacker-supplied arguments that get baked into the deployed contract's `LockupArgs`: [3](#0-2) 

Exploit flow:
1. Attacker learns/guesses the intended `owner_account_id` of a future grant (these are typically well-known, e.g. team/investor account names).
2. Attacker calls `create(owner_account_id, malicious_lockup_duration, malicious_lockup_timestamp, malicious_vesting_schedule, malicious_release_duration, malicious_whitelist_account_id)` with at least `MIN_ATTACHED_BALANCE` attached, creating and deploying the lockup contract at `hex(sha256(owner_account_id)).<factory>` with terms of the attacker's choosing, but with `owner_account_id` still set to the real victim (so the victim's account, not the attacker's, is recorded as `owner_account_id` in the deployed contract).
3. When the legitimate grantor later calls `create` for the same `owner_account_id` with the intended real terms, the `Promise::new(lockup_account_id).create_account()...` batch fails because the sub-account already exists; the whole action batch fails atomically, and `on_lockup_create` detects `!is_promise_success()` and refunds the grantor's attached deposit: [4](#0-3) 

The grantor's deposit is refunded (not stolen), but the canonical, expected lockup address for that owner is now permanently squatted with attacker-chosen parameters — e.g. a `staking_pool_whitelist_account_id` pointing at an attacker-controlled fake whitelist contract, or a vesting/release schedule the real grantor never intended. This matches the explicitly listed Critical impact category: "a lockup deployed with parameters its rightful creator never chose." No existing guard (`assert_self`, `is_promise_success`, the `MIN_ATTACHED_BALANCE` check) prevents this, because none of them restrict *who* may call `create` for a given `owner_account_id`, nor tie the deterministic address derivation to any grantor-only capability.

### Impact Explanation
- The real grantor's deposit is safely refunded on failure, so no NEAR is directly stolen from the grantor in this specific call.
- However, the owner's canonical lockup address is permanently occupied by a contract whose terms (`vesting_schedule`, `release_duration`, `lockup_duration`, `staking_pool_whitelist_account_id`) were chosen by the attacker, not the grantor — this is squarely the "lockup deployed with parameters its rightful creator never chose" Critical category.
- Because `owner_account_id` in the squatted contract is set to the real victim, the victim (not the attacker) has owner-level control of that contract; the attack blocks the real grant from ever being deployed at the expected address and can also mislead the victim into interacting with an attacker-controlled `staking_pool_whitelist_account_id` presented as if it were the protocol's trusted whitelist.
- Repeatable against any account name the attacker can predict, at a cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) per squatted address.

### Likelihood Explanation
`create` is a public, unprivileged, `#[payable]` method requiring only `MIN_ATTACHED_BALANCE`; the sub-account name is fully determined by the public `owner_account_id` argument, so any attacker who can anticipate a future grantee's account id can pre-emptively squat it before the grantor acts. This requires no special role, no victim key, and no foundation privileges — only funds to cover the minimum deposit.

### Recommendation
Restrict lockup creation for a given `owner_account_id` to an authorized grantor (e.g., require `predecessor_account_id() == foundation_account_id` or an allow-listed set of granters), or otherwise bind lockup address derivation/creation rights to a value only the legitimate grantor controls (e.g., a grantor-provided nonce/signature), so that an unprivileged account cannot pre-create a lockup at another owner's canonical derived address.

### Proof of Concept
Add a `cargo test` in `lockup-factory/src/lib.rs` tests module modeled on `test_create_lockup_rollback`:
1. Set predecessor to an attacker account (not the foundation/grantor), call `contract.create(victim_owner_account_id, attacker_lockup_duration, None, attacker_vesting_schedule, attacker_release_duration, Some(attacker_whitelist_account_id))` with `MIN_ATTACHED_BALANCE` attached; run `on_lockup_create` with `PromiseResult::Successful(vec![])` to confirm the squat succeeds — assert the deployed address equals `lockup_account()` (the same deterministic address derived from `victim_owner_account_id`) and that the terms match the attacker's chosen values (not the intended grantor's values).
2. Then set predecessor to the legitimate grantor account, call `contract.create(victim_owner_account_id, real_lockup_duration, ..., real_vesting_schedule, ...)` for the same owner; simulate `PromiseResult::Failed` (since `create_account` on an existing account fails) and confirm `on_lockup_create` returns `false` and refunds the grantor's deposit — proving the grantor can never deploy the intended lockup at that address, and the address permanently retains attacker-chosen terms from step 1.
3. Assert `terms_at(lockup_account()) != real_terms_chosen_by_grantor`, demonstrating the broken binding.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
