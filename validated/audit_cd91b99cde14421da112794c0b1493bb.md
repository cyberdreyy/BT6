### Title
Post-default withdraw requests drain `defaultRecoveryReserve` without adding claim basis, permanently blocking defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the reported bug (an urgent claim/close path that reverts because a required allocated balance was never topped up), `IdleCreditVault` lets users create **post-default** withdraw requests that are later paid 1:1 out of `defaultRecoveryReserve`, even though that reserve was sized at finalization only for the defaulted epoch's active + pending claim basis. Every post-default claim decrements the reserve with no offsetting contribution, so once post-default claims consume enough of it, `defaultRecoveryReserve -= _amount` underflows and the remaining defaulted-epoch receipts can never be claimed — the exact "insufficient allocated balance blocks the claim" failure mode.

### Finding Description
In `finalizeDefaultRecovery`, the reserve is set to `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and the recovery price to `reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis` covers only active CDO basis plus `defaultPendingClaimBasis()` (pending normal + unfunded instant receipts). Nothing accounts for requests created *after* finalization.

Yet `requestWithdraw` has an explicit post-finalization branch:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:247-257
if (defaultRecoveryFinalized) {
  if (_hasWithdrawRequest(_user) || instantWithdrawsRequests[_user] != 0 || postDefaultRequests[_user] != 0) {
    revert NotAllowed();
  }
  _burn(msg.sender, _amount);
  _mint(_user, _amount);
  postDefaultRequests[_user] = _amount;
  return;
}
```

The receipt is minted, but no underlying is added to `defaultRecoveryReserve` — the burned strategy tokens were the CDO's, and the comment itself notes the CDO passes an "already-haircut amount" priced via the post-finalization `virtualPrice`. The claim path then pays the full receipt from the shared reserve:

```solidity
// _claimPostDefaultWithdrawRequest -> _transferDefaultRecovery
defaultRecoveryReserve -= _amount;   // 912-916
underlyingToken.safeTransfer(_user, _amount);
```

Invariant broken: reserve solvency per claim basis. `defaultRecoveryReserve` is exactly `recoveryPrice * totalBasis / RECOVERY_FULL`; subtracting post-default payouts leaves `reserve < remaining defaulted-epoch entitlements`, so the last claimants' `_transferDefaultRecovery` reverts on underflow — permanently freezing their recovery even though funds sized for them were consumed by post-default receipts.

### Impact Explanation
Direct theft / permanent freezing of unclaimed recovery funds. Any tranche holder with tokens outstanding at default (or who acquires them after) can request a post-default withdraw and withdraw reserve value at par (they already absorbed the haircut in the request amount, i.e. they surrender `(1 - recoveryPrice) * amount`, but they extract `amount` of reserve that was denominated against defaulted claimants). The shortfall falls on defaulted-epoch receipt holders and active-LP recovery claimants whose claims then revert permanently. Loss is bounded by the total post-default request volume, up to the entire remaining reserve.

### Likelihood Explanation
- Attacker is unprivileged: only needs to hold tranche tokens (KYC-passed lender) after `finalizeDefault`.
- Reachability: the dedicated `defaultRecoveryFinalized` branch in `requestWithdraw` and `_claimPostDefaultWithdrawRequest` are purpose-built, so the post-default request/claim UX is intended and enabled by the honest owner/manager path (the CDO must route `requestWithdraw`/`claimWithdrawRequest`; defaulted state does not block these strategy calls, only new requests by users with existing receipts).
- No existing guard stops it: `_transferFundedClaim`'s reserve guard does not apply (post-default claims go through `_transferDefaultRecovery`), `_skimDonatedAssets` is CDO-side, and nothing adds post-default receipts to `totalBasis` or tops up the reserve.
- Uncertainty I could not fully resolve within the iteration limit: whether the CDO's `requestWithdraw` flags are re-enabled post-finalization for ordinary users. However, the mere existence of the post-default code paths (and the comment "Preserve request/claim UX after default") strongly indicates they are reachable; if some flag currently blocks them, the branch is dead code and the finding degrades to latent risk on any future enablement.

### Recommendation
Treat post-default requests like defaulted-epoch claims: either (a) fund the reserve for them — pull/hold underlying equal to the post-default claim amount and add it to `defaultRecoveryReserve` at request or claim time, or (b) pay post-default claims from non-reserve balance via `_transferFundedClaim` (which already enforces `balance - reserve >= amount` and would revert harmlessly if no post-default funding exists), or (c) disable new withdraw requests entirely once `defaultRecoveryFinalized` until all defaulted claims are settled.

### Proof of Concept
Foundry fork PoC outline:

```solidity
// test/foundry/PostDefaultReserveDrain.t.sol
function testPostDefaultClaimDrainsRecoveryReserve() external {
    // 1. Alice (victim) and Mallory deposit AA pre-epoch; epoch starts.
    idleCDO.depositAA(10_000 * ONE_SCALE);   // Alice
    depositAs(mallory, 10_000 * ONE_SCALE);  // Mallory holds tranche tokens
    _startEpochAndCheckPrices(0);

    // 2. Borrower underfunds stopEpoch -> _handleBorrowerDefault.
    deal(defaultUnderlying, borrower, owed / 2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted());

    // 3. Owner finalizes recovery with partial funds (recoveryPrice < 1).
    vm.prank(owner);
    cdoEpoch.finalizeDefaultRecovery(recovered, recoverySource);
    uint256 reserveBefore = strategy.defaultRecoveryReserve();

    // 4. Alice requests withdraw in the defaulted epoch (basis enters totalBasis
    //    via pendingWithdraws recorded before default OR via her request before default).

    // 5. Mallory requests a withdraw AFTER finalization -> postDefaultRequests branch.
    vm.prank(mallory);
    cdoEpoch.requestWithdraw(amount, address(AAtranche));

    // 6. Mallory claims: _claimPostDefaultWithdrawRequest pays 1:1 from reserve,
    //    decrementing defaultRecoveryReserve with no basis added.
    vm.prank(mallory);
    cdoEpoch.claimWithdrawRequest();
    uint256 reserveAfter = strategy.defaultRecoveryReserve();
    assertEq(reserveBefore - reserveAfter, malloryClaim); // reserve drained at par

    // 7. Alice's defaulted-epoch claim now underflows:
    //    defaultRecoveryReserve -= amount reverts -> her recovery is permanently frozen.
    vm.prank(alice);
    vm.expectRevert(); // arithmetic underflow in _transferDefaultRecovery
    cdoEpoch.claimWithdrawRequest();
}
```

Sequence: buffer → running → defaulted → finalized. Attacker `mallory` is an ordinary tranche holder; all privileged calls (stopEpoch, finalizeDefaultRecovery) are honest. The freeze persists because no path re-tops `defaultRecoveryReserve`.
