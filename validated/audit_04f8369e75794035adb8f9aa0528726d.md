### Title
Vote account withdrawal after VAT-filtering snapshot causes validator panic in `maybe_burn_vat_from_staked_accounts` - (File: `runtime/src/bank.rs`)

### Summary
The Alpenglow "Validator Admission Ticket" (VAT) burn logic assumes that every vote account it processes still holds enough lamports to pay the per-epoch burn, because those accounts were previously "filtered" by `clone_and_filter_for_vat`. That filtering is done against a cached/snapshot view of vote-account balances, while the actual burn later reads the *live* account and blindly does `checked_sub(...).expect(...)`. An ordinary vote-account withdraw authority can invalidate the filtering assumption between snapshot time and burn time by simply calling the normal `Withdraw` vote instruction, which has no knowledge of (and does not enforce) the VAT minimum. This causes an `.expect()` panic instead of a graceful error, i.e. a deterministic validator crash — the same class of bug as the referenced Dopex report, where a withdrawal path failed to keep an accounting invariant in sync with a value trusted later by a different, security-critical function, but here manifesting as a hard panic rather than a mere revert.

### Finding Description
`maybe_burn_vat_from_staked_accounts` explicitly documents its precondition and then violates it by re-loading live state: [1](#0-0) 

It iterates `epoch_stakes.stakes().vote_accounts()` — the result of `clone_and_filter_for_vat`, which is only guaranteed to reflect balances *at the time the epoch-stakes snapshot was taken* — but then calls `self.get_account(vote_pubkey)` to fetch the **current** account and performs:

```rust
account.set_lamports(
    account.lamports().checked_sub(vat_to_burn_per_epoch)
        .expect("Vote accounts should have already been filtered to contain enough balance for the VAT"),
);
```

The filtering criterion (`minimum_vote_account_balance_for_vat`) requires rent-exempt minimum **plus** one epoch's VAT burn: [2](#0-1) 

However, the on-chain `Withdraw` instruction that any vote account's authorized withdrawer can invoke only enforces the rent-exempt minimum (plus any pending delegator rewards); it has no concept of the VAT reserve: [3](#0-2) 

So a validator operator (an ordinary, unprivileged signer — the vote account's withdraw authority) can:
1. Ensure the vote account is included by `clone_and_filter_for_vat` (i.e., it has ≥ rent-exempt-minimum + VAT-per-epoch at snapshot time, which is the normal steady state for an actively-staked vote account).
2. After the snapshot/epoch-stakes for that epoch is fixed, submit a `Withdraw` instruction draining the account down to just the rent-exempt minimum (which vote_state::withdraw permits, since it knows nothing about the VAT reserve).
3. When the bank later executes `maybe_burn_vat_from_staked_accounts` for that epoch using the stale filtered snapshot, `self.get_account(vote_pubkey)` returns the drained (live) balance, `checked_sub(vat_to_burn_per_epoch)` returns `None`, and `.expect(...)` panics.

This is structurally identical to the Dopex bug: a value relied upon by a later, critical accounting operation (`lowerDepeg` / VAT burn) is invalidated by a legitimate withdrawal path (`withdraw` / vote `Withdraw`) that the critical function does not re-validate against current state, but trusts as still true.

### Impact Explanation
Unlike the original Solidity finding — which merely causes one admin transaction to revert — this Rust code path panics via `.expect()`. Since `maybe_burn_vat_from_staked_accounts` runs deterministically inside bank/epoch-boundary processing on every validator (it is part of consensus-critical state transition, executed identically by all nodes replaying or producing the same slot), a panic here crashes the validator process. If the same account/timing conditions are met on every validator (which they are, since it is derived from the same deterministic ledger state), this becomes a cluster-wide, consensus-halting denial of service rather than a localized failure.

### Likelihood Explanation
Reachability requires only an ordinary, permissionless action: calling the vote program's `Withdraw` instruction with the vote account's authorized withdrawer key, which any vote-account operator legitimately controls. No special privilege, RPC access, or malicious infrastructure is needed — only timing the withdrawal relative to when the epoch's VAT-filtered snapshot was taken. I was not able to fully verify, within the available tool budget, the exact call site/epoch-delay of `maybe_burn_vat_from_staked_accounts` relative to `compute_new_epoch_caches_and_rewards`'s `filtered_distribution_vote_accounts` (i.e., whether the window for a withdraw transaction is one slot or up to an epoch, given Solana's activation-delay for epoch stakes), so the precise exploit window size is uncertain and should be confirmed with a live Devin session.

### Recommendation
`maybe_burn_vat_from_staked_accounts` should not assume the live account balance still satisfies the VAT-filter precondition. Either:
- Re-check `account.lamports() >= vat_to_burn_per_epoch` (or the full VAT minimum) immediately before burning, and skip/handle accounts that no longer qualify (e.g., via `saturating_sub` plus re-filtering, or by removing the account from the stake/vote sets for that epoch), or
- Make the VAT reserve a first-class constraint enforced by the vote program's `Withdraw` instruction itself (so a withdraw that would drop a vote account below its VAT reserve for the current epoch is rejected on-chain), or
- Operate on a captured/frozen snapshot of vote account lamports (taken at the same time as `clone_and_filter_for_vat`) rather than re-reading live account state at burn time.

### Proof of Concept
1. Operate a vote account that is actively staked and has balance ≥ `rent_exempt_minimum + vat_to_burn_per_epoch`, so it passes `clone_and_filter_for_vat` / `minimum_vote_account_balance_for_vat` and is included in the epoch's filtered `VersionedEpochStakes`.
2. As the vote account's authorized withdrawer, submit a `VoteInstruction::Withdraw` transaction (see `withdraw` in `programs/vote/src/vote_state/mod.rs:1062-1129`) that reduces the account's lamports down to exactly the rent-exempt minimum — this instruction only checks rent-exemption and pending delegator rewards, not the VAT reserve, so it succeeds.
3. When the bank subsequently invokes `maybe_burn_vat_from_staked_accounts` (`runtime/src/bank.rs:2648-2694`) for that vote account using the (now stale) filtered epoch-stakes snapshot, `self.get_account(vote_pubkey)` returns the drained balance, `checked_sub(vat_to_burn_per_epoch)` underflows, and the `.expect("Vote accounts should have already been filtered to contain enough balance for the VAT")` call panics, crashing the validator process executing/replaying that slot.

                    ),
