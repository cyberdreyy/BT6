### Title
`deployCreditVault` / `deployRevolvingCreditVault` accept `feeReceiver == address(0)`, permanently burning all vault fees - (File: contracts/IdleCreditVaultFactory.sol)

### Summary
The external bug class is a privileged setter that lacks a zero-address check, allowing a critical protocol address to be irreversibly set to `address(0)`. The strongest analog in idle-tranches is the permissionless `IdleCreditVaultFactory.deployCreditVault()` path: any EOA can deploy a fully functional credit vault while passing `cvParams.feeReceiver = address(0)`, which is forwarded unchecked into `cv.setFeeParams(par.feeReceiver, ...)`. Once set, all performance and management fees accounting for that vault flow to the zero address — an irreversible loss of protocol yield for the lifetime of the vault.

### Finding Description
`deployCreditVault()` is callable by anyone (`IdleCreditVaultFactory.sol:92`). It validates `strategyData.manager != address(0)` (line 99) and minimum fee levels via `_checkMinimumFees` (line 310), but never validates `cvParams.feeReceiver`. The value is passed verbatim into `_configureCreditVault`, which calls `cv.setFeeParams(par.feeReceiver, par.fees, feeSplit, par.managementFee)` (line 302). The factory then transfers ownership of both the `IdleCDOEpochVariant` credit vault and the `IdleCreditVault` strategy to `treasury` (lines 113-114), after which the fee configuration is controlled by the honest treasury — but the zero `feeReceiver` already baked in persists unless treasury notices and corrects it, and any fees accrued in the interim are burned.

The same path exists in `deployRevolvingCreditVault()` (lines 126-166), which also forwards `cvParams.feeReceiver` unchecked via `_configureCreditVault`.

Note: this finding assumes `IdleCDOCreditVault.setFeeParams`/`IdleCDO.setFeeParams` does not itself revert on `feeReceiver == address(0)` (the historical IdleCDO implementation treats `feeReceiver` as a plain payout target and does not validate it, since `fee == 0` configurations were originally supported). If `setFeeParams` does enforce a nonzero receiver, the deployment would revert and the finding collapses — this must be confirmed against that function before finalizing.

### Impact Explanation
Every epoch, `_updateAccounting`/`_calculateManagementFee` accrue performance and management fees denominated in underlying and route them to `feeReceiver`. With `feeReceiver == address(0)`:

- For tokens that allow transfers to `address(0)` (e.g., USDC), the fee amounts are burned — a permanent, quantified loss equal to the full protocol fee share for the vault's lifetime until corrected. This matches the "theft or permanent freezing of unclaimed yield" acceptance bar, with the loss borne by the honest `treasury`/protocol.
- For tokens that revert on zero-address transfers, every `stopEpoch`/fee-collection call would revert — a permanent freeze of the epoch state machine (epoch cannot close, withdrawals gated on epoch progression are stuck). This is "permanent freezing" impact.

Because ownership is transferred to `treasury` at the end of the same transaction, the misconfiguration is locked behind the honest owner exactly like the external bug's `minting_multisig` lock-in.

### Likelihood Explanation
Deployment via the factory is the intended onboarding path for new credit vaults, and the deployer is unprivileged — any EOA can call it. Two realistic scenarios:

1. Mistake: a third-party integrator or ops script deploys a vault omitting `feeReceiver` (it defaults to `address(0)` in an uninitialized struct). Fees then leak/burn silently.
2. Griefing: an attacker deploys a legitimately-configured vault that honest KYC'd lenders subsequently deposit into (the vault is whitelisted via Keyring and owned by the real `treasury`, so it is indistinguishable from an "official" vault), with `feeReceiver = address(0)` so all protocol fees are destroyed.

No existing guard stops this: `_checkMinimumFees` only enforces fee *rates* are nonzero, and the `manager == address(0)` check covers only the manager field.

### Recommendation
Add an explicit zero-address check in both deploy functions:

```solidity
if (cvParams.feeReceiver == address(0)) revert Is0();
```

Alternatively/additionally, enforce `feeReceiver != address(0)` inside `IdleCDOCreditVault.setFeeParams` (and `IdleCDO.setFeeParams`) so the invariant holds regardless of the caller, matching the recommended mitigation of the external report.

### Proof of Concept
Foundry fork test sketch (against a mainnet fork with USDC as underlying):

```solidity
function test_FeeReceiverZero_BurnsFees() public {
    IdleCreditVaultFactory factory = IdleCreditVaultFactory(factoryAddr);

    IdleCreditVaultFactory.CreditVaultParams memory cv = IdleCreditVaultFactory.CreditVaultParams({
        implementation: cvImpl,
        limit: 1_000_000e6,
        underlying: USDC,
        apr: 1000,                       // 10%
        epochDuration: 30 days,
        bufferPeriod: 1 days,
        instantWithdrawDelay: 0,
        instantWithdrawAprDelta: 0,
        disableInstantWithdraw: true,
        keyringPolicy: 0,
        feeReceiver: address(0),         // <-- missing zero check
        fees: 10_000,                    // 10% performance fee
        managementFee: 500,
        isInterestMinted: false,
        isDepositDuringEpochDisabled: false
    });
    IdleCreditVaultFactory.StrategyData memory sd = IdleCreditVaultFactory.StrategyData({
        implementation: stratImpl, manager: manager, borrower: borrower, borrowerName: "b"
    });
    IdleCreditVaultFactory.AncillaryParams memory ap; // all zero -> no keyring/queue/escrow

    factory.deployCreditVault(cv, sd, ap); // succeeds: no Is0() revert on feeReceiver

    // Attacker/honest lender deposits, epoch runs, borrower repays with interest.
    // On stopEpoch, the fee share (10% of interest) is transferred to address(0):
    // USDC balance of address(0) increases by feesAccrued; treasury receives nothing.
    // assertEq(IERC20(USDC).balanceOf(address(0)), feesAccrued);
}
```

Expected: deployment succeeds and fee accounting routes all accrued performance/management fees to `address(0)`, demonstrating permanent loss of protocol yield with no privileged-role misbehavior involved.
