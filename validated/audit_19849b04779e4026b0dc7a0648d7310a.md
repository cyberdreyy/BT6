### Title
Stale cached vote/stake account entries not evicted from `StakesCache` when account owner changes away from the stake/vote program - (File: runtime/src/stakes.rs)

### Summary
`StakesCache::check_and_store` mirrors the reported `RdpxDecayingBonds` bug class: a secondary/cached representation of "ownership" (here, whether an account is a stake or vote account) is derived once and never reconciled when the authoritative field — the account's actual `owner` — changes to something other than the stake or vote program while the account retains a non-zero balance.

### Finding Description
`check_and_store` is the single choke point that keeps the bank-level `Stakes<StakeAccount>` cache in sync with on-chain account state after every transaction commit and direct account store [1](#0-0) , and after successful transaction execution [2](#0-1) .

The function only has code paths that (a) remove a cache entry when the account's lamports drop to zero and its *current* owner is the vote or stake program, or (b) upsert/remove an entry when the *current* owner is the vote or stake program (based on whether the deserialization succeeds). There is no branch for the case where an account was previously cached as a vote/stake account and its owner is changed to a *different* program while lamports remain non-zero — the function silently returns without touching the cache, exactly as documented by the inline `TODO`: [3](#0-2) 

The surrounding logic that only handles removal via the zero-lamport path and upsert/removal only for the vote/stake-program-owned branches is here: [4](#0-3) 

This is the direct structural analog of the `RdpxDecayingBonds.bonds[bondId].owner` field never being refreshed on `transferFrom`: a duplicated "ownership/classification" value is written once at creation/insertion time and has no update path for the transition away from that classification (short of the fully-drained/zero-lamport case).

### Impact Explanation
If a stake or vote account is reassigned to a different program while keeping non-zero lamports, `StakesCache` continues to report it as an active stake delegation or vote account. Since `Stakes<StakeAccount>` feeds bank-level stake-weighted computations (delegated stake totals, `vote_accounts()`), a stale/ghost entry could distort these consensus-relevant aggregates, i.e. state used for stake-weighted calculations would diverge from the authoritative accounts-db state instead of being purely cosmetic. This matches the "bricked/incorrect cached state that can't self-heal" impact described in the original finding, escalated in the Agave context to consensus-relevant stake bookkeeping rather than pure display data.

### Likelihood Explanation
Likelihood is low-to-moderate in practice: `BorrowedInstructionAccount::set_owner` only allows an owner change when the account is currently owned by the invoking program, the account is writable, and the account's data is zero-initialized [5](#0-4) , which constrains how an actively-delegated stake/vote account (non-zero, non-empty data) could be reassigned through the normal system-program `Assign` path while keeping lamports. The primary realistic trigger is through direct/administrative account rewrites (e.g. runtime migrations that call `store_accounts`/`store_account` outside normal instruction processing), which still route through `check_and_store` and are therefore also affected. Agave engineers already flagged this exact gap as a `TODO` referencing solana-labs/solana#24200, indicating the maintainers are aware the reconciliation path is incomplete but have not closed it.

### Recommendation
In `StakesCache::check_and_store`, when the account's current owner is *not* the vote or stake program, explicitly attempt eviction from both `vote_accounts` and `stake_delegations`/`delegated_stakes` (a cheap map lookup keyed by pubkey) so a previously-cached entry cannot persist once ownership has moved away from the stake/vote program, closing the gap noted in the existing `TODO`.

### Proof of Concept
1. Cache a stake or vote account normally via `check_and_store` (owner = stake/vote program, lamports > 0) — entry is inserted into `Stakes<StakeAccount>`.
2. Force a subsequent call to `check_and_store` for the same pubkey with an `AccountSharedData` whose `owner()` is neither the vote program nor the stake program, but whose `lamports() > 0` (achievable through any code path that calls `Bank::store_account`/`store_accounts` directly with a rewritten account, bypassing the `Assign` zero-data restriction that gates normal instruction-driven owner changes).
3. Observe that `StakesCache::stakes()` still returns the stale vote/stake entry for that pubkey, since neither the zero-lamport removal branch nor the owner-match upsert/remove branches in `runtime/src/stakes.rs` lines 99-164 execute for this transition.

    /// Assignes the owner of this account (transaction wide)
    pub fn set_owner(&mut self, pubkey: &[u8]) -> Result<(), InstructionError> {
        // Only the owner can assign a new owner
        if !self.is_owned_by_current_program() {
            return Err(InstructionError::ModifiedProgramId);
        }
        // and only if the account is writable
        if !self.is_writable() {
            return Err(InstructionError::ModifiedProgramId);
        }
        // and only if the data is zero-initialized or empty
        if !is_zeroed(self.get_data()) {
            return Err(InstructionError::ModifiedProgramId);
        }
        // don't touch the account if the owner does not change
        if self.get_owner().to_bytes() == pubkey {
            return Ok(());
        }
        self.touch()?;
        self.account.copy_into_owner_from_slice(pubkey);
        Ok(())
    }
