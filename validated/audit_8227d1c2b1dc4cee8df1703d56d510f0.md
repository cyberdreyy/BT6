This report's underlying bug class ("assumed exact/complete value diverges from live reality") maps cleanly onto the multisig contracts' confirmation-count logic: the recorded number of confirmations for a pending request is trusted as a proxy for "number of currently-authorized members that approved it," but a member's confirmation is never invalidated when that member is later removed from the multisig. This breaks the intended equality `execute request only if confirmations from num_confirmations distinct *live* members`.

### Title
Stale confirmations from removed multisig members are counted toward the execution threshold, allowing requests to execute below the effective quorum - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
In both `multisig/src/lib.rs` and `multisig2/src/lib.rs`, `confirm()` decides whether to execute a request purely by comparing the size of the stored `confirmations` set to `num_confirmations`. When a member is removed via the `DeleteKey` (`multisig`) or the member-deletion path (`multisig2`), the cleanup logic only removes *requests originally created by* that member; it never scrubs that member's confirmation out of the `confirmations` set of *other, still-pending* requests. A confirmation cast by a member who is later removed therefore continues to count permanently toward the threshold of any request they confirmed before being removed, letting a request execute with fewer distinct *live* member approvals than `num_confirmations` requires.

### Finding Description
`confirm()` in `multisig2/src/lib.rs`: [1](#0-0) 

only checks `confirmations.len() as u32 + 1 >= self.num_confirmations`; it never re-validates that the accounts/keys already present in `confirmations` are still members. Membership cleanup happens in `delete_member`: [2](#0-1) 

which removes only `self.requests` entries where `r.member == member` (requests *created* by the removed member), and clears `self.confirmations` solely for those deleted requests. It performs no scan of `self.confirmations` for other pending requests to strip out the departed member's stale approval.

The same pattern exists in the original `multisig/src/lib.rs` for the `DeleteKey` action: [3](#0-2) 

which filters cleanup by `r.signer_pk == pk` (the request creator only), leaving that key's confirmations on other pending requests intact, and the actual threshold check in `confirm()`: [4](#0-3) 

The invariant the contract is supposed to enforce is: *a request only executes once `num_confirmations` distinct, currently-authorized members have approved it.* The actual behavior is: *a request executes once the stored confirmation-set size reaches `num_confirmations`, regardless of whether every confirming identity is still a member at execution time.* These two diverge as soon as any confirming member is removed between their confirmation and the request's execution.

### Impact Explanation
This is a threshold/authorization-boundary violation matching the "Critical: a multisig request executed below threshold" category. A multisig configured for `k`-of-`n` approval can end up executing a sensitive action (e.g., `Transfer`, `FunctionCall`, `AddKey`) with fewer than `k` currently-authorized approvers, because one or more of the counted confirmations belong to accounts/keys that are no longer members. This directly weakens the custody guarantee the multisig is meant to provide over NEAR held by the account.

### Likelihood Explanation
This requires only ordinary multisig operations that are expected to occur over the contract's lifetime: member rotation/removal (a normal, unprivileged-relative-to-the-contract operation for any authorized member acting within their existing confirm rights) combined with a pre-existing pending request that the soon-to-be-removed member had already confirmed. No exploitation of an owner-only or foundation-only privilege beyond what a regular multisig member already has is needed; the flaw is purely in the bookkeeping the contract itself performs when membership changes, so it can be triggered any time member turnover happens while requests are outstanding.

### Recommendation
When removing a member (`delete_member` in `multisig2`, and the `DeleteKey` action in `multisig`), iterate over `self.confirmations` for *all* pending requests (not only those created by the removed member) and remove the departed member's entry from each set. Alternatively, validate at `confirm()`-time (right before comparing against `num_confirmations`) that every entry in the stored confirmation set still corresponds to a current member, discarding stale entries (and persisting the pruned set) before performing the threshold comparison.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(R)` for a `Transfer` action — `confirmations(R) = {A}`.
3. `B` calls `confirm(R)` — `confirmations(R) = {A, B}` (below threshold, not yet executed).
4. Members `B, C, D` (3-of-4, satisfying the real threshold) submit and confirm a separate request `R2` containing a `DeleteKey`/member-removal action for `A`. `R2` executes via `execute_request`; `delete_member(A)` runs, but since `A` did not *create* `R`, `R`'s `confirmations` set is left untouched — it still contains `A`.
5. `members` is now `{B, C, D}`; `A` is no longer authorized.
6. `C` calls `confirm(R)`. `confirmations(R).len() + 1 = 3 >= num_confirmations (3)`, so `execute_request(R)` runs — the `Transfer` executes with only `B` and `C` being genuine, currently-live approvers (plus the phantom stale approval from removed member `A`), i.e., below the intended 3-live-member threshold.     /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));

        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );

            let request = self.remove_request(request_id);

            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
