### Title
Stale per-epoch instant-withdraw basis is never cleared on a funded claim, causing double-counted default recovery basis and permanently frozen instant receipts - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` pays and burns a user's instant-withdraw receipt but only zeroes the aggregate `instantWithdrawsRequests`; it never clears `instantWithdrawsRequestsByEpoch[user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If a borrower default is later finalized while `epochNumber` still equals the epoch in which that already-claimed instant request was made, the stale basis is (a) re-included in `defaultPendingClaimBasis`, inflating the recovery denominator, and (b) re-read by `_claimDefaultedInstantWithdrawRequest`, which subtracts the stale `claimBasis` from `instantWithdrawsRequests` and underflow-reverts, permanently freezing any instant receipt the user opened after the funded claim.

### Finding Description
The analog to CVE-2017-16827 (invalid free / dangling pointer after a symbol table is freed) is an improperly "freed" receipt: the claim path releases the funds but leaves the per-epoch accounting entry dangling.

In `requestInstantWithdraw`, three ledgers are written for the same receipt: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

`claimInstantWithdrawRequest` clears only the first ledger: it burns `instantWithdrawsRequests[_user]`, sets it to 0, and transfers the funded amount [2](#0-1) . The per-epoch entries `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are only ever cleared inside `_claimDefaultedInstantWithdrawRequest` [3](#0-2)  — i.e., only on the post-default path, never on the normal funded-claim path.

On `finalizeDefaultRecovery`, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0` [4](#0-3) . That condition is exactly "some other user's current-epoch instant request was not fully funded," which is the trigger for `defaultInstantWithdrawsFinalized = true` [5](#0-4) .

Because `epochNumber` is only bumped inside `deposit()` when an epoch is running [6](#0-5) , a default finalized in the same epoch in which the instant request was made keeps the stale entry keyed at `defaultRecoveryEpoch`.

Attack / breakage sequence (unprivileged tranche-token holder / lender):

1. Epoch E running. Attacker A calls `requestInstantWithdraw(X)` via the CDO. Ledgers: `instantWithdrawsRequests[A] = X`, `instantWithdrawsRequestsByEpoch[A][E] = X`, `instantWithdrawClaimsByEpoch[E] += X`, `pendingInstantWithdraws += X`.
2. Another user B also requests instant withdraw `Y`; the CDO funds only part (e.g., collects A's `X` via `collectInstantWithdrawFunds`), leaving `pendingInstantWithdraws = Y != 0`.
3. A calls `claimInstantWithdrawRequest`: receives `X` underlying, receipt burned, `instantWithdrawsRequests[A] = 0` — but `instantWithdrawsRequestsByEpoch[A][E] = X` and `instantWithdrawClaimsByEpoch[E]` still contain the stale `X`.
4. Borrower defaults in epoch E; `finalizeDefaultRecovery` runs. `defaultPendingClaimBasis` counts `instantWithdrawClaimsByEpoch[E]` including A's already-paid `X`, so `recoveryPrice = reserve / totalBasis` is depressed. A's stale entry is unbacked: either the reserve is diluted for every recovery claimant, or early claimants drain it.
5. A (or any victim) opens a new instant request `Z` post-default — `requestInstantWithdraw` has no `defaultRecoveryFinalized` gate and writes `instantWithdrawsRequests[A] = Z`, `instantWithdrawsRequestsByEpoch[A][E] = X + Z`.
6. A calls `claimInstantWithdrawRequest`: `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` is true, so `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = instantWithdrawsRequestsByEpoch[A][E] = X + Z` and executes `instantWithdrawsRequests[A] -= claimBasis` → `Z - (X + Z)` underflows and reverts. The new receipt `Z` can never be claimed, and the strategy-token receipt has already been minted/burned bookkeeping-wise into an unclaimable state.

### Impact Explanation
Two distinct harms, both satisfying the acceptance criteria:

- **Permanent freezing of funds**: any user who claimed an instant withdrawal in the defaulting epoch and later opens a new instant request has every subsequent `claimInstantWithdrawRequest` revert on the underflow in `instantWithdrawsRequests[_user] -= claimBasis` [7](#0-6) . The frozen amount equals the new receipt `Z`, bounded only by the user's deposited balance — quantifiable, e.g., a 100k USDC receipt is permanently unclaimable.
- **Recovery dilution / reserve drain**: `instantWithdrawClaimsByEpoch[E]` retains already-paid basis, so `defaultRecoveryPrice` is set below the fair ratio [8](#0-7) , underpaying every defaulted receipt and active-holder claim, or letting an attacker whose stale entry survives the subtraction (`instantWithdrawsRequests` ≥ stale basis via a large enough new request recorded *before* the subtraction order changed) over-claim from `defaultRecoveryReserve`.

### Likelihood Explanation
Requires a specific but realistic sequence: instant withdrawals must be enabled, a user must claim a funded instant receipt, another instant request must remain unfunded, and the borrower must default within the same `epochNumber`. Instant withdrawals are a supported vault mode, defaults are an explicitly handled state (`finalizeDefaultRecovery`, `defaultRecoveryEpoch`), and no guard clears or checks the stale per-epoch entry — so the bug triggers deterministically whenever the sequence occurs. The attacker needs no privileges: only tranche tokens and ordinary request/claim calls.

### Recommendation
Clear the per-epoch ledgers in the funded-claim path too: in `claimInstantWithdrawRequest`, zero `instantWithdrawsRequestsByEpoch[_user][requestEpoch]` and decrement `instantWithdrawClaimsByEpoch[requestEpoch]` for every epoch that contributed to the claimed amount (tracking the request epoch at request time if necessary). Alternatively, reconcile `instantWithdrawsRequestsByEpoch` against `instantWithdrawsRequests` inside `_claimDefaultedInstantWithdrawRequest` so already-paid receipts cannot re-enter the default claim basis. Add a test: fund and claim an instant request, leave a second instant request unfunded, finalize a default in the same epoch, then verify the recovered price ignores the paid basis and a new instant request remains claimable.

### Proof of Concept
Foundry fork PoC sketch (against `IdleCreditVault` + `IdleCDOEpochVariant` test harness, same setup as `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. Enable instant withdraws (manager), deposit userA & userB, startEpoch.
// 2. epoch E running:
//    cdoEpoch.requestInstantWithdraw for userA (X) and userB (Y).
// 3. Fund only X from CDO -> collectInstantWithdrawFunds(X); pendingInstantWithdraws = Y.
// 4. userA: claimInstantWithdrawRequest -> receives X; assert
//    strategy.instantWithdrawsRequests(userA) == 0 but
//    strategy.instantWithdrawsRequestsByEpoch(userA, E) == X   // stale
// 5. Trigger borrower default and call finalizeDefaultRecovery.
//    assert defaultPendingClaimBasis() included stale X via
//    instantWithdrawClaimsByEpoch[E] (inflated denominator).
// 6. userA: requestInstantWithdraw(Z) again (allowed, no default gate).
// 7. userA: claimInstantWithdrawRequest ->
//    _claimDefaultedInstantWithdrawRequest: claimBasis = X + Z;
//    instantWithdrawsRequests[userA] (Z) -= (X + Z) -> panic underflow, claim reverts.
//    userA's Z receipt is permanently unclaimable.
```

The key assertion is step 4: the per-epoch mapping retains basis for a receipt whose underlying was already transferred — the direct analog of freeing memory while leaving a dangling pointer that a later routine dereferences.
