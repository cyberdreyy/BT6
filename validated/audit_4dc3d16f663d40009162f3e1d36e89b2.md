### Title
Unbounded overwrite of `savedCallbacks[MessageId]` in `HandleLegacyUserMessage` enables cross-user response hijacking - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` unconditionally stores the caller-supplied callback into `h.savedCallbacks[msg.Body.MessageId]` with no check for an existing entry and no binding to the original sender's identity. Since `MessageId` is fully attacker-controlled (copied verbatim from the client JSON-RPC request `ID` field), an unprivileged, arbitrarily-signed request that reuses another pending request's `MessageId` silently replaces the legitimate caller's callback, so the eventual DON response for that ID is delivered to the attacker instead of the original caller.

### Finding Description
The message flows from `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`), which calls `common.ValidatedMessageFromReq`/decodes the client-provided JSON-RPC request, sets `m.Body.MessageId = req.ID` directly from client input [1](#0-0) , then invokes `h.HandleLegacyUserMessage(ctx, msg, callback)` [2](#0-1) .

Inside `HandleLegacyUserMessage`, after payload decoding, timestamp/staleness, and method checks, the handler stores the callback keyed purely by the attacker-chosen `MessageId` with no existence check and no sender binding: [3](#0-2) 

Because `msg.Body.MessageId` only needs to pass length/format validation in `Message.Validate()` (non-empty, ≤ max length, no null suffix) [4](#0-3) , any signer (attacker) can choose an arbitrary `MessageId` string, including one they know or guess is currently pending for another legitimate caller (default client IDs are frequently short/sequential/predictable, and even accidental collisions produce the same effect).

When the map already holds a `savedCallback` for that ID from a legitimate, still-in-flight request, the attacker's assignment at line 412 silently overwrites it — there is no `found` check comparable to the one used on read in `handleWebAPITriggerMessage` (`if found { ... }`) [5](#0-4) . Later, when a DON node responds with that same `MessageId`, `handleWebAPITriggerMessage` looks up and deletes `savedCallbacks[msg.Body.MessageId]` and delivers the response to whichever callback is currently stored — now the attacker's — via `savedCb.SendResponse(...)` [6](#0-5) . The legitimate caller's original callback reference is discarded/orphaned and will only resolve via gateway-side timeout (`callback.Wait(ctx)` timeout path) [7](#0-6) , never receiving the real DON response.

There is no per-sender scoping of `MessageId`, no idempotency/duplicate rejection, and no "request binding" check tying a response back to the exact `Callback` instance that originally registered it. The `MaxAllowedMessageAgeSec`/timestamp check only guards staleness of `payload.Timestamp`, not uniqueness of `MessageId`, so an attacker can freely pick a fresh timestamp while colliding on an older/still-pending `MessageId`.

### Impact Explanation
This is cross-user response confusion: an unprivileged gateway client can redirect another user's DON/workflow trigger response to itself, and cause the legitimate caller's request to silently fail/time out. Depending on payload content, this could expose response data (e.g., HTTP response bodies from `web_api_target`/compute results) intended for another caller to the attacker — matching the "attacker-controlled data returned to another user" / cross-user response confusion impact class.

### Likelihood Explanation
The attacker needs only the ability to send a validly-signed gateway request (any key holder, unauthenticated by the DON itself) and knowledge/guess of a `MessageId` that is concurrently in flight for another caller. Because `MessageId` is client-chosen with no server-enforced global uniqueness or per-sender namespacing, collisions are trivially producible (e.g., always sending predictable/sequential/common IDs), making this reliably repeatable rather than a rare race.

### Recommendation
Reject the request (or generate a fresh server-side ID) if `msg.Body.MessageId` already exists in `h.savedCallbacks` for a different pending request; alternatively, scope `savedCallbacks` keys by `(sender, MessageId)` and verify the responding message's sender/request binds to the original registrant before overwriting or delivering a response. Add a `found` check before the store at handler.go:412 mirroring the read-side check in `handleWebAPITriggerMessage`.

### Proof of Concept
Go test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build two signed `api.Message`s with identical `Body.MessageId` (`"dup-id"`) but different signers/keys and different payload contents, both with fresh `payload.Timestamp`.
2. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` — assert `h.savedCallbacks["dup-id"]` is set to the callback tied to `cbA`.
3. Before any DON response arrives, call `handler.HandleLegacyUserMessage(ctx, msgB, cbB)` with the same `MessageId`.
4. Assert the handler either rejects `msgB` (e.g., returns an error/duplicate-ID error response via `cbB`) or that `h.savedCallbacks["dup-id"]` still references `cbA` (not overwritten).
5. Currently, the assignment at handler.go:412 unconditionally overwrites, so `h.savedCallbacks["dup-id"]` now points to `cbB`; simulate a DON response for `"dup-id"` via `handler.HandleNodeMessage` and show `cbB.Wait(ctx)` receives the response while `cbA.Wait(ctx)` times out — demonstrating the hijack.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
