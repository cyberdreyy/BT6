### Title
Floor-rounding in `get_locked_amount`/`get_unvested_amount` understates locked tokens, permitting early transfer of lockup/vesting funds - (File: lockup/src/getters.rs)

### Summary
`lockup/src/getters.rs` computes the unreleased (still-locked) and unvested portions of a lockup using floor (truncating) integer division. Because this value gates `get_owners_balance`/`get_liquid_owners_balance`, which in turn gate `transfer()` in `lockup/src/owner.rs`, rounding the locked amount **down** lets the owner transfer out slightly more than the schedule actually entitles them to — the same rounding-direction defect described in the reference report (a value used as a withdrawal cap must round up, not down).

### Finding Description
`get_locked_amount` computes the still-locked "unreleased" balance as:
```
let unreleased_amount = U256::from(lockup_amount) * time_left / U256::from(release_duration);
``` [1](#0-0) 
and `get_unvested_amount` computes the still-locked "unvested" balance the same way:
```
let unvested_amount = U256::from(lockup_amount) * time_left / total_time;
``` [2](#0-1) 

Both divisions are plain integer (floor) division, which always rounds the *locked* quantity **down**. `get_locked_amount` returns `max(unreleased_amount, unvested_amount)` [3](#0-2) , and this is exactly the value subtracted from the account balance to compute the owner's spendable balance:
```
pub fn get_owners_balance(&self) -> WrappedBalance {
    (env::account_balance() + self.get_known_deposited_balance().0)
        .saturating_sub(self.get_locked_amount().0)
        .into()
}
``` [4](#0-3) 
`get_liquid_owners_balance` further caps this by the actual account balance [5](#0-4) , and `transfer()` uses `get_liquid_owners_balance` as the sole authorization check before moving NEAR out of the contract:
```
assert!(
    self.get_liquid_owners_balance().0 >= amount.0,
    ...
);
...
Promise::new(receiver_id).transfer(amount.0)
``` [6](#0-5) 

The binding that should hold is:
`locked_amount_reported ≥ locked_amount_actual (by schedule)`, i.e. the contract must never under-report how much is still locked, otherwise `owners_balance = balance - locked_amount` is over-reported and the owner can transfer tokens that the release/vesting schedule has not yet unlocked. Because the division floors, whenever `lockup_amount * time_left` is not an exact multiple of `release_duration` (or `total_time` for vesting), `unreleased_amount`/`unvested_amount` is strictly less than the exact schedule value, so `get_locked_amount()` under-reports by up to `release_duration - 1` parts, in yoctoNEAR terms typically 0 or a handful of yoctoNEAR per call, but reproducible and attacker-controlled by choosing the block timestamp at which `transfer` is called (any timestamp where the division has a nonzero remainder).

### Impact Explanation
This breaks the custody binding "releasable amount ≤ schedule value" for a lockup contract, which per the rules maps to **Critical — locked or unvested tokens released early**. The owner (an unprivileged party relative to the vesting/lockup schedule enforced by the foundation) can call `transfer()` at a timestamp chosen so the division truncates, and withdraw yoctoNEAR amounts still legitimately locked/unvested according to the schedule, ahead of schedule. While the per-call magnitude is small (bounded by the divisor), it is a genuine violation of the schedule invariant and is entirely attacker (owner)-controlled and repeatable across many `transfer()` calls over the life of the lockup, since each call re-evaluates `get_locked_amount()` at the current timestamp with independent rounding error.

### Likelihood Explanation
High likelihood of being triggered: the owner already controls the call timing of `transfer()` (a normal, unprivileged/expected operation for this contract, not requiring the foundation, a redeploy, or any other excluded precondition), and simply needs `block_timestamp` such that `lockup_amount * time_left mod release_duration != 0` (or the analogous vesting condition), which is the generic case for arbitrary timestamps rather than a rare edge case.

### Recommendation
Round the "still locked" quantities (`unreleased_amount` and `unvested_amount`) **up**, not down, so the reported locked amount is never smaller than the true schedule value. E.g. change:
```
let unreleased_amount = (U256::from(lockup_amount) * time_left + U256::from(release_duration) - 1)
    / U256::from(release_duration);
```
and similarly for `unvested_amount`, mirroring the ceiling-division helper pattern already used elsewhere in this codebase (`staking-pool/src/internal.rs`'s `*_rounded_up` functions) [7](#0-6) .

### Proof of Concept
1. Deploy a lockup contract with `lockup_amount = L`, `release_duration = R`, transfers enabled, `lockup_timestamp` in the past.
2. Choose `block_timestamp` such that `end_timestamp - block_timestamp = time_left` where `L * time_left` is not a multiple of `R` (trivial to arrange, e.g. `time_left` chosen so remainder is `R-1`).
3. Call `get_locked_amount()` — observe it returns `floor(L * time_left / R)`, which is strictly less than the exact fractional locked amount `L * time_left / R`.
4. Call `transfer(amount, receiver)` with `amount = get_liquid_owners_balance()` (the maximum allowed by the flawed check) — the transfer succeeds even though, under exact arithmetic, part of `amount` was still supposed to be locked. Repeating across many blocks/timestamps accumulates additional early-released yoctoNEAR that should have remained locked until the schedule caught up.
