### Title
Out-of-range `account_indexes` values in `ConfidentialMintBurn` instructions cause an out-of-bounds panic in `parse_confidential_mint_burn_instruction` / `parse_signers` - (File: transaction-status/src/parse_token/extension/confidential_mint_burn.rs)

### Finding Description
`check_num_token_accounts` only validates the *count* of entries in `account_indexes`, not their *values*. Every match arm in `parse_confidential_mint_burn_instruction` then indexes `account_keys` directly with attacker-controlled `u8` values taken from `account_indexes`, e.g. `account_keys[account_indexes[0] as usize]` in the `InitializeMint`, `Mint`, `Burn`, and `ApplyPendingBurn` arms, and inside `parse_signers` (called with `account_indexes` and an `offset`) for the owner/multisig-owner fields. [1](#0-0) 

Because `account_indexes` come straight from the compiled instruction's `accounts` byte array (a raw `Vec<u8>` supplied by whoever crafted the transaction), a value such as `255` is entirely valid as a `u8` but will be far larger than `account_keys.len()` for any realistic transaction (which typically has well under 256 accounts). `account_keys` indexing (`Index<usize>` for the underlying `&[Pubkey]`/`AccountKeys` wrapper) performs standard Rust slice indexing, which panics with "index out of bounds" rather than returning a `Result`. `check_num_token_accounts` cannot prevent this because it never looks at the actual index values, only `account_indexes.len()`.

This code path is reached by RPC methods such as `getParsedTransaction`/`getParsedBlock`, which decode historical on-chain transactions (including ones submitted by the attacker themselves) through `parse_token` → `parse_confidential_mint_burn_instruction`. An attacker can submit (or otherwise get included) a transaction whose `ConfidentialMintBurn`-program instruction has `accounts = [255, 255]` (satisfying the "at least 2 accounts" length check for `ApplyPendingBurn`), and then request `getParsedTransaction` for it, triggering the panic during the JSON parsing of the transaction's instruction.

### Impact Explanation
A single crafted, previously-submitted transaction that is later fetched through `getParsedTransaction`/`getParsedBlock` causes the JSON-RPC-serving process to panic while formatting the instruction, i.e., a decoder panic reachable via one read-only RPC call on attacker-controlled on-chain data. This matches the accepted "decoder panic and misreporting" impact class in the rules, scoped to a single client/single-request DoS of the RPC decode path (not affecting consensus or requiring elevated privileges).

### Likelihood Explanation
High feasibility: the attacker needs only to submit one ordinary transaction invoking the SPL Token-2022 `ConfidentialMintBurn` program with a malformed `accounts` field (any signer/writable bytes are fine; the RPC parser doesn't validate account privileges, only count), then issue a single `getParsedTransaction` call. No special validator/staked/gossip access is required, and the same pattern applies to every extension parser in `transaction-status/src/parse_token/extension/` that indexes `account_keys[account_indexes[i] as usize]` without validating `account_indexes[i] < account_keys.len()`.

### Recommendation
Add a bounds check on each `account_indexes[i]` value against `account_keys.len()` before indexing (or use `account_keys.get(...)` and return `ParseInstructionError::InstructionNotParsable` on `None`) in `parse_confidential_mint_burn_instruction` and in the shared `parse_signers` helper in `transaction-status/src/parse_token.rs`, and audit all other extension parsers for the same pattern.

### Proof of Concept
```rust
// transaction-status/src/parse_token/extension/confidential_mint_burn.rs (test module)
#[test]
fn test_apply_pending_burn_out_of_range_indexes_does_not_panic() {
    use solana_instruction::{AccountMeta, Instruction};
    use solana_message::Message;
    use solana_pubkey::Pubkey;

    // Build an ApplyPendingBurn instruction with the correct discriminant/data
    // but only 2 real accounts in the message, while accounts field of the
    // compiled instruction is crafted with out-of-range u8 indexes [255, 255].
    let mint = Pubkey::new_unique();
    let owner = Pubkey::new_unique();
    let mut instruction = apply_pending_burn(
        &spl_token_2022_interface::id(),
        &mint,
        &owner,
        &[],
    )
    .unwrap();

    // Simulate a message with far fewer accounts than 256, but keep a crafted
    // CompiledInstruction whose `accounts` bytes are out-of-range.
    let message = Message::new(&[instruction.clone()], None);
    let mut compiled = message.instructions[0].clone();
    compiled.accounts = vec![255, 255]; // out-of-range indexes, but len()==2 passes check_num_token_accounts

    let result = std::panic::catch_unwind(|| {
        parse_token(&compiled, &AccountKeys::new(&message.account_keys, None))
    });

    // Expected (fixed) behavior: returns Err(ParseInstructionError::...) instead of panicking.
    assert!(result.is_ok(), "parser panicked on out-of-range account_indexes");
}
```
Expected assertion: the call should return a `Result::Err` gracefully; currently it panics with an out-of-bounds index inside `account_keys[account_indexes[0] as usize]` (or within `parse_signers`), demonstrating the vulnerability.
