### Title
Loss-adjusted stop haircut is applied only to the user's latest request epoch, letting earlier unfunded pending receipts claim at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` allows a user to hold unfunded withdraw receipts across multiple epochs (a new request only reverts if the *latest* `lastWithdrawRequest` epoch has a `lossRecoveryPrice`). When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` applies one aggregate `lossRecoveryPriceByEpoch[epochNumber]` haircut to the entire `pendingWithdraws` bucket — which includes receipts from *all* prior epochs. But `_claimLossAdjustedWithdrawRequest` only clears and haircuts the bucket stored under `lastWithdrawRequest[_user]` (the newest epoch). The older per-epoch receipt remains in `withdrawsRequests[_user]`/`withdrawsRequestsByEpoch` and is then paid at par via `_claimFundedWithdrawRequest`, even though its share of funding was already reduced by the loss. A lender with receipts spanning two epochs therefore over-claims, draining funded underlyings owed to other pending claimants.

### Finding Description
- `requestWithdraw` records per-epoch basis in `withdrawsRequestsByEpoch[_user][currentEpoch]` and updates `lastWithdrawRequest[_user] = currentEpoch` (IdleCreditVault.sol:282-293). The guard at lines 263-271 only blocks a new request when the *previous* `lastWithdrawRequest` epoch has a nonzero `lossRecoveryPriceByEpoch` — it does not require claiming older *funded-pending* receipts.
- `epochNumber` is incremented by the strategy at each `stopEpoch`, so receipts requested in consecutive buffers while still unfunded (e.g., borrower underfunding, or sequential requests in the same pending aggregate) get different epoch tags while sharing one `pendingWithdraws` total.
- `collectWithdrawFunds(_amount < pendingBasis)` stores a single `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` (lines 411-421) — i.e., the haircut is applied to the whole aggregate.
- On claim, `_claimLossAdjustedWithdrawRequest` (lines 789-801) computes `lossEpoch = lastWithdrawRequest[_user]` and calls `_clearWithdrawClaimForEpoch(_user, lossEpoch)`, which only zeroes `withdrawsRequestsByEpoch[_user][lossEpoch]` and subtracts that one epoch's `normalAmount` from `withdrawsRequests[_user]` (lines 815-819). The earlier-epoch `withdrawsRequestsByEpoch` entry survives, and `claimWithdrawRequest` then adds `_claimFundedWithdrawRequest(_user)` which pays `withdrawsRequests[_user]` (the leftover older-epoch amount) at par from the same, already-haircut, funded balance.

### Impact Explanation
Direct theft / insolvency: one user receives `E2 * lossRecoveryPrice + E1 * 1.0` while the strategy only collected `(E1 + E2 + others) * lossRecoveryPrice` from the borrower. The excess is paid from underlyings reserved for other pending claimants, so later claimants' funded requests revert on transfer or are underpaid permanently. Loss equals the un-haircut portion of stale-epoch receipts — up to `(1 - lossRecoveryPrice) * earlierEpochBasis`, which can exceed the funded reserve when the haircut is deep.

### Likelihood Explanation
Requires (a) a user to hold unfunded receipts in two distinct epochs — reachable because `requestWithdraw` never forces claiming a merely *unfunded* old receipt, and (b) a subsequent `stopEpochWithDuration` loss (`_lossAmount > 0`) executed by the honest manager, a flow explicitly supported by `previewLossAdjustedWithdrawFunds`. Both are unprivileged-attacker-reachable sequences around honest manager calls; the fix commits made for loss epochs guard only the `lastWithdrawRequest` epoch, leaving the multi-epoch gap.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, iterate/clear **all** epochs with `withdrawsRequestsByEpoch[_user][e] != 0` (or aggregate a per-user pending basis) and apply `lossRecoveryPrice` to the full claim basis, not just `lastWithdrawRequest`. Alternatively, in `requestWithdraw`, revert whenever the user has *any* unfunded pending receipt (`withdrawsRequests[_user] != 0 || apr0Users[_user].principal != 0`), not only when the last epoch carries a loss price — mirroring the stricter check already used in the `defaultRecoveryFinalized` branch (lines 247-251).

Foundry fork sketch (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testMultiEpochLossAdjustedOverclaim() external {
    // 1. user deposits AA, requests withdraw in epoch N buffer -> receipt E1
    vm.prank(user);
    uint256 e1 = cdoEpoch.requestWithdraw(half, address(AAtranche));
    // 2. startEpoch, then stopEpoch with _amount < pendingBasis path avoided;
    //    borrower only partially funds so pendingWithdraws persists,
    //    or simply: user requests again in next buffer (epoch N+1) -> receipt E2
    _startEpochAndCheckPrices(0);
    _stopEpochPartialFunding();            // pendingWithdraws stays > 0, epochNumber++
    vm.prank(user);
    uint256 e2 = cdoEpoch.requestWithdraw(rest, address(AAtranche));
    // 3. next epoch: manager calls stopEpochWithDuration with _lossAmount > 0
    _startEpochAndCheckPrices(0);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, duration, loss); // collectWithdrawFunds sets lossRecoveryPriceByEpoch[epochNumber]
    // 4. user claims: E2 haircut + E1 paid at par -> total > funded share
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    // assert user received e2*price/1e18 + e1  (over-claim vs aggregate haircut)
    // assert a second claimant's claim now reverts/underpays -> insolvency
}
```

Key assertions: `underlying.balanceOf(user)` delta ≈ `e1 + e2 * lossRecoveryPrice / 1e18` while the strategy only received `(e1 + e2 + otherPending) * lossRecoveryPrice / 1e18`; a subsequent legitimate claim then fails on `_transferFundedClaim` due to insufficient balance.
