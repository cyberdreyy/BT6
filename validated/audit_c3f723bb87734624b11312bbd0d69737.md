## Title
`createDstEscrow` accepts unchecked fee parameters, causing `EscrowDst.withdraw` to permanently revert and enabling theft of the maker's source-chain funds - (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowDst.sol`)

### Summary
The reported Aave bug (`_calculateMaxBorrowCollateral`) is caused by an unchecked/unvalidated subtraction whose subtrahend can exceed the minuend, making the intended operation permanently revert once a threshold is crossed. The same root cause exists in `BaseEscrowFactory.createDstEscrow` → `EscrowDst._withdraw`: the fee amounts embedded in `Immutables.parameters` are validated against the transferred amount only on the source-chain path (`_postInteraction`), but `createDstEscrow` performs no equivalent check, so a destination escrow can be deployed whose `integratorFeeAmount + protocolFeeAmount` exceeds `immutables.amount`.

### Finding Description
On the source path, `BaseEscrowFactory._postInteraction` explicitly guards against invalid fee configuration: [1](#0-0) 

This check ensures `integratorFeeAmount + protocolFeeAmount < takingAmount` for the fee parameters that get embedded (via `DstImmutablesComplement.parameters`) for the *intended* destination escrow.

However, `createDstEscrow` is a separate, permissionless entry point that takes an arbitrary `IBaseEscrow.Immutables calldata dstImmutables` directly from the caller (the taker/resolver) and performs no validation of the embedded fee parameters before deploying the clone and funding it: [2](#0-1) 

The fee values are later read back and subtracted, unchecked for sufficiency, in `EscrowDst._withdraw`: [3](#0-2) 

If `integratorFeeAmount + protocolFeeAmount > immutables.amount`, the line `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` underflows and reverts under Solidity 0.8 checked arithmetic. Because `withdraw`/`publicWithdraw` both funnel into `_withdraw`, **every** withdrawal attempt on that specific dst escrow instance will revert forever — there is no way to ever pay the maker from that escrow.

Critically, `cancel()` does not perform this subtraction and pays the full `immutables.amount` back to the taker: [4](#0-3) 

This is the same shape of bug as the Aave report: a threshold/limit value derived from attacker-influenced (or otherwise unchecked) inputs is subtracted from a base amount without validating that the base amount is sufficient, and once the invariant is violated, the "repay"/"withdraw" action becomes permanently unusable while the alternative ("cancel"/liquidation) path remains open to the party who caused the imbalance.

### Impact Explanation
A malicious taker/resolver (unprivileged, permissionless caller of `createDstEscrow`) can:
1. Deploy an `EscrowDst` with a correct token balance, correct hashlock, and correct amount (so it passes surface-level verification), but with `parameters` encoding `integratorFeeAmount + protocolFeeAmount > amount`.
2. Obtain the secret from the maker off-chain (per the documented flow, the maker releases the secret once they see the destination escrow appears correctly funded) — the corrupted fee split is not something a maker's balance check would necessarily catch.
3. Use the secret to call `withdrawTo` on `EscrowSrc` on the source chain and claim the maker's locked source tokens.
4. Never successfully call `withdraw` on the (permanently broken) `EscrowDst` — the maker never receives destination funds.
5. After the `DstCancellation` timelock elapses, call `cancel()` on `EscrowDst` to reclaim their own deposited destination tokens (since `cancel` performs no fee subtraction).

Net effect: the malicious taker keeps both the maker's source-chain tokens and their own destination-chain tokens, while the maker receives nothing. This is direct theft of user funds via the live swap lifecycle, matching the Critical/High impact criteria for this bounty (theft of user funds / permanent freezing of the maker's destination-side payout).

### Likelihood Explanation
The path is reachable by any unprivileged address calling the public `createDstEscrow` function with self-chosen `Immutables.parameters`; no privileged role is required. The only precondition is that the maker's/relayer's off-chain verification of the destination escrow does not independently recompute and cross-check `integratorFeeAmount + protocolFeeAmount < amount` before releasing the secret — which is plausible since the contract itself provides no on-chain guarantee of this invariant at `createDstEscrow` time (unlike the source-chain `_postInteraction` path, which does enforce it). This asymmetry between the two creation paths is itself the bug.

### Recommendation
Add the same validation used in `_postInteraction` to `createDstEscrow`, e.g.:
```solidity
(uint256 protocolFeeAmount, uint256 integratorFeeAmount, , ) = abi.decode(dstImmutables.parameters, (uint256, uint256, address, address));
if (protocolFeeAmount + integratorFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
before deploying/funding the escrow, so that an `EscrowDst` can never be created in a state where `_withdraw` is guaranteed to revert.

### Proof of Concept
1. Attacker (taker) computes `dstImmutables` with `amount = X` and `parameters = abi.encode(protocolFeeAmount, integratorFeeAmount, protocolFeeRecipient, integratorFeeRecipient)` such that `protocolFeeAmount + integratorFeeAmount > X`.
2. Attacker calls `createDstEscrow{value: ...}(dstImmutables, srcCancellationTimestamp)` — succeeds because no fee-sanity check exists (`contracts/BaseEscrowFactory.sol:165-185`).
3. Maker's off-chain checker sees the deployed escrow has balance `X` at the correct hashlock/address and releases the secret.
4. Attacker calls `EscrowSrc.withdrawTo(secret, attacker)` on the source chain, draining the maker's locked tokens.
5. Attacker (or anyone) calls `EscrowDst.withdraw(secret, dstImmutables)`; the call reverts at `contracts/EscrowDst.sol:92` due to underflow (`immutables.amount - integratorFeeAmount - protocolFeeAmount`), for the lifetime of the withdrawal window.
6. After `DstCancellation` timelock, attacker calls `EscrowDst.cancel(dstImmutables)` (`contracts/EscrowDst.sol:64-73`), reclaiming the full `X` destination tokens plus the safety deposit — while the maker's source tokens are already gone.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
