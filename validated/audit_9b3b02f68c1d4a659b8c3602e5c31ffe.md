### Title
Unrestricted, un-delayed `commission_bps` updates allow a validator to retroactively steal stake rewards after credits are earned - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The legacy `update_commission` instruction restricts commission **increases** to the first half of an epoch via `is_commission_update_allowed`, preventing a validator from raising its cut right before rewards are paid out. The newer basis-points commission instruction, `update_commission_bps` (SIMD-0291/SIMD-0123), explicitly removes this timing restriction ("No commission update rule, per SIMD-0249 and SIMD-0291"), and the epoch-reward redemption path can use the *current* commission value at redemption time unless a separate `delay_commission_updates` mechanism is active. This mirrors the bounty-manager exploit: a party controlling a reward-split parameter can raise it after the underlying "votes" (here, epoch credits earned by delegated stake) are already locked in, and reap an outsized share of the reward at settlement.

### Finding Description
`update_commission_bps` sets `inflation_rewards_commission_bps` (or `block_revenue_commission_bps`) with only a signer check by the authorized withdrawer — no epoch-timing restriction at all: [1](#0-0) 

Contrast this with the legacy commission path, which blocks commission increases past the epoch midpoint specifically to stop last-moment commission hikes: [2](#0-1) [3](#0-2) 

At epoch-reward calculation time, the commission value used to split the stake's earned points into `staker_rewards`/`voter_rewards` is read either from the *current* vote account state or, only if `delay_commission_updates` is enabled, from a snapshot taken in an earlier epoch: [4](#0-3) 

The actual split then happens in `calculate_stake_rewards`/`commission_split`, using whatever `commission_bps` was passed in: [5](#0-4) [6](#0-5) 

Just like the bounty case — where `maxRewardPerVote` is read at `claim()` time rather than being fixed when votes were locked — the validator's commission is read at reward-redemption time (end of epoch) rather than being fixed to the rate that was in effect while stakers were earning credits throughout the epoch. Since `update_commission_bps` has no timing gate, a validator can wait until the very last slot of the epoch (or even the reward-calculation window itself, before `delay_commission_updates` snapshots take effect) and bump `inflation_rewards_commission_bps` to 10000 (100%), causing `commission_split`/`commission_split_preserve_lamports` to award the entire epoch's earned reward to the voter and 0 to every delegated staker for stake that had already earned its credits over the whole epoch.

### Impact Explanation
If `delay_commission_updates` is not simultaneously enforced for basis-point commissions, this allows a validator operator to unilaterally and retroactively confiscate the inflation-reward share that should go to all of its delegators for an entire epoch's worth of already-earned credits, by raising commission to 100% just before redemption and then lowering it back afterward (no restriction on decreases either way). This is a stake/reward-accounting corruption: delegators receive systematically less than the protocol-intended split for work (voting/credits) already performed, without any recourse, since the change is fully valid per current program rules.

### Likelihood Explanation
Likelihood depends entirely on whether `delay_commission_updates` is active wherever `commission_rate_in_basis_points` (bps commission) is enabled. The code comment explicitly frames `delay_commission_updates` as the safeguard for "the effect of commission updates," implying awareness that immediate commission changes are dangerous for reward fairness — yet `update_commission_bps` was deliberately built with "No commission update rule" per SIMD-0249/SIMD-0291, which is inconsistent with that safeguard if the two features are not required to ship together. I could not fully verify from available code whether `delay_commission_updates` is unconditionally paired with bps-commission activation across all cluster configurations, so likelihood should be treated as feature-flag-dependent rather than universally exploitable today.

### Recommendation
Require that `commission_bps` updates are always subject to the same delayed-effect mechanism (`delay_commission_updates`) used for the legacy commission field, regardless of the `commission_rate_in_basis_points`/SIMD-0291 rollout state, so that the commission rate applied at reward redemption always reflects the rate in effect at the start of (or throughout) the epoch that earned the credits — not the rate at redemption time. Alternatively, reinstate an epoch-midpoint restriction on commission-bps increases analogous to `is_commission_update_allowed`.

### Proof of Concept
1. Validator sets `inflation_rewards_commission_bps` low (e.g., 0) at the start of an epoch so delegators are attracted and accrue credits normally throughout the epoch via `programs/vote/src/vote_state/mod.rs::update_commission_bps`.
2. Near the end of the epoch, before the stake-reward-partition calculation runs (or before any `delay_commission_updates` snapshot is taken, if that feature is not concurrently enforced), the validator calls `update_commission_bps` again to set `inflation_rewards_commission_bps = 10000` (100%). This call succeeds because `update_commission_bps` has no epoch-timing check.
3. `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` reads `vote_state.inflation_rewards_commission()` (now 100%) at redemption time and calls `redeem_rewards`, which routes all `stake_reward` to the validator via `commission_split`.
4. Delegators receive `staker_rewards = 0` for credits they earned across the whole epoch; the validator collects the entire pool.
5. The validator then lowers commission back to its original low value for the next epoch to keep attracting delegators, and repeats.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Given the current slot and epoch schedule, determine if a commission change
/// is allowed
pub fn is_commission_update_allowed(slot: Slot, epoch_schedule: &EpochSchedule) -> bool {
    // always allowed during warmup epochs
    if let Some(relative_slot) = slot
        .saturating_sub(epoch_schedule.first_normal_slot)
        .checked_rem(epoch_schedule.slots_per_epoch)
    {
        // allowed up to the midpoint of the epoch
        relative_slot.saturating_mul(2) <= epoch_schedule.slots_per_epoch
    } else {
        // no slots per epoch, just allow it, even though this should never happen
        true
    }
}

fn commission_split(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let on = u128::from(on);
            // Calculate mine and theirs independently and symmetrically instead of
            // using the remainder of the other to treat them strictly equally.
            // In Tower, this is also to cancel the rewarding if either of the parties
            // should receive only fractional lamports, resulting in not being rewarded at all.
            // Thus, note that we intentionally discard any residual fractional lamports.
            let mine = on
                .checked_mul(u128::from(split))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let theirs = on
                .checked_mul(u128::from(
                    MAX_BPS
                        .checked_sub(split)
                        .expect("commission cannot be greater than MAX_BPS"),
                ))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;

            (mine as u64, theirs as u64, true)
        }
    }
}
