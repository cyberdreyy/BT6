## Analysis

The bug class in the report is: a function accepts attacker-controlled input and forwards it to a privileged/trusted downstream action without validating who is allowed to make that request. The closest reachable analog in this codebase is the legacy Web API trigger path in the Gateway service.

### Root cause

`core/services/gateway/gateway.go`'s `ProcessRequest` routes any request carrying a `DonId` as a "legacy request." It only calls `msg.Validate()` (which checks signature length, message-ID length/format, DON-ID length, etc.) before dispatching to `h.HandleLegacyUserMessage(ctx, msg, callback)`: [1](#0-0) 

`msg.Validate()` in `core/services/gateway/api/message.go` only checks field lengths/format and extracts the signer — it performs no authorization/allowlist check on who the signer is: [2](#0-1) 

The actual `HandleLegacyUserMessage` implementation, in `core/services/gateway/handlers/capabilities/handler.go`, validates payload decoding, a timestamp, and message staleness, but explicitly skips authorization with a `TODO`: [3](#0-2) 

After that check, the message is forwarded, unconditionally, to every member node of the DON: [4](#0-3) 

By contrast, the newer/rewritten Vault and HTTP-capabilities gateway paths do enforce authorization before dispatch — e.g. `GatewayHandler.HandleGatewayMessage` for Vault runs requests through `requestProcessor.ProcessRequest` which wraps an `Authorizer` (allowlist/JWT): [5](#0-4) 

This confirms the missing-allowlist path is isolated to the legacy `capabilities.handler.HandleLegacyUserMessage` code, not a general gateway property.

### Title
Missing allowlist/authorization check in legacy Web API trigger handler allows any signed request to reach DON nodes - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The Gateway's legacy user-message path for the WebAPI capability (`handler.HandleLegacyUserMessage`) forwards any well-formed, self-signed `web_api_trigger` request to every node in the target DON without checking whether the sender is authorized/allowlisted to use that DON's capability, as flagged by the code's own `// TODO: apply allowlist and rate-limiting here` comment.

### Finding Description
`gateway.ProcessRequest` treats any inbound message with a non-empty `DonId` as a legacy request and dispatches it after only calling `msg.Validate()`, which merely checks that fields are correctly sized/formatted and extracts the ECDSA signer from the signature — it never checks the signer against a DON/service allowlist. `HandleLegacyUserMessage` then performs payload decoding, a `Timestamp` presence check, and a staleness check, but has no equivalent to the newer `Authorizer`/allowlist chain used by the Vault (`gw_handler.go`) or v2 HTTP-capabilities handlers. Because any client can generate their own ECDSA keypair, sign an arbitrary message, and submit it to the gateway's public HTTP endpoint, this means any unprivileged actor can construct a valid `web_api_trigger` request for any known `DonId` and have it broadcast to all DON nodes as if it were an authorized workflow trigger.

### Impact Explanation
An unauthorized actor can trigger the `web_api_trigger` capability flow against a target DON's nodes, causing the DON to process an attacker-supplied trigger payload (a `webapicap.TriggerRequestPayload`) and potentially execute downstream workflow logic/HTTP calls associated with that DON, all without being on any allowlist. This is a request-impersonation / authorization-bypass class issue: any request reaching the nodes appears to a downstream node as a legitimately dispatched gateway request, since the node-facing connection is trusted at the transport layer.

### Likelihood Explanation
Likelihood is high for any deployment still using the legacy DON-ID-keyed configuration path with the `capabilities` handler (as opposed to the newer service-centric config using Vault/v2-HTTP handlers), since the vulnerable code path is reached directly from the public-facing `ProcessRequest` HTTP entrypoint with no additional precondition beyond knowing/guessing a valid `DonId`.

### Recommendation
Add an authorization/allowlist check (mirroring the `Authorizer`/`AllowListBasedAuth` pattern already used in `core/capabilities/vault/gw_handler.go`) inside `handler.HandleLegacyUserMessage` before forwarding to `don.SendToNode`, verifying the message's recovered `Sender` against the DON's configured allowlist and applying rate-limiting, per the existing `TODO` comment at `core/services/gateway/handlers/capabilities/handler.go:384`.

### Proof of Concept
1. Generate an arbitrary ECDSA keypair (no registration required).
2. Craft a `MessageBody` with a known/guessable `DonId`, `Method: "web_api_trigger"`, and a `webapicap.TriggerRequestPayload` containing a non-zero `Timestamp`.
3. Sign the message and submit it via the gateway's user-facing HTTP endpoint (which calls `gateway.ProcessRequest`).
4. Observe that `msg.Validate()` passes (format-only checks) and `handler.HandleLegacyUserMessage` forwards the request to all DON member nodes via `don.SendToNode`, with no allowlist check ever performed on the recovered signer address.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
