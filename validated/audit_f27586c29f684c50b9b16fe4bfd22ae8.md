### Title
Stale role caching in `AuthorizedUserWithSession` allows privilege persistence after role downgrade - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`AuthorizedUserWithSession` authorizes a session purely by reading the `user_role` column that was written once at session-creation time into `oidc_sessions`, and never re-validates that role against the identity provider or a canonical source at request time. A user whose OIDC group membership (or locally-set role) is downgraded after they have obtained a session retains their old, higher-privileged role for the full remaining `SessionTimeout` window.

### Finding Description
`handleTokenExchange` computes `role` from the ID token's group claims via `IDClaimsToUserRole` and inserts it into `oidc_sessions` at login time: `INSERT INTO oidc_sessions (id, user_email, user_role, created_at) ...` [1](#0-0) . `AuthorizedUserWithSession`, which is invoked on every authenticated request to resolve the caller's `clsessions.User`, then simply reads back this cached `user_role` column and treats it as authoritative for the rest of the session's lifetime, only checking `created_at + SessionTimeout >= now()` for freshness: [2](#0-1) .

No code path re-queries the identity provider's current group claims or a canonical `users`/role table for OIDC sessions during authorization. The only cleanup process, `sessionReaper`, purges rows solely based on age (`created_at < before`), not based on any role change detection: [3](#0-2) . Unlike `core/sessions/ldapauth/sync.go`, which appears to implement an explicit upstream sync job, no equivalent role re-sync exists in the OIDC package for the interactive session table — `UpstreamSyncInterval` is referenced only in configuration/docs, and the in-code comment in `FindUserByAPIToken` claiming "sessions and tokens are synced against the upstream server via the ... reaper.go sync implementation" does not match what `reaper.go` actually does (it never touches `user_role`) [4](#0-3) .

Consequently: if an admin (or edit/run) user is authenticated and later has their identity-provider group membership downgraded (or is removed from the admin group), any session cookie/`sessionID` issued before the downgrade continues to authorize the old, higher role for the remainder of `SessionTimeout`, because the authorization check only consults the cached `oidc_sessions.user_role` value and never re-derives it from current claims.

### Impact Explanation
This is a role/authorization-bypass class issue: privilege persists past an intended downgrade. A demoted admin (or any role) can continue performing admin-gated actions — managing jobs, keys, bridges, other users, etc. — using their stale session token until it naturally expires per `SessionTimeout`, rather than immediately losing access. The severity is bounded by the configured `SessionTimeout` duration but is a genuine violation of the stated invariant that "authorization is exact and reflects current role."

### Likelihood Explanation
Requires: (1) the OIDC authentication driver is enabled, (2) a user obtains a session while holding a higher role, and (3) that user's role is subsequently downgraded at the identity provider (or locally) while their old session/cookie is retained. No admin/database access is needed by the "attacker" beyond already having been legitimately authenticated at the higher role prior to demotion — this is fully reachable through the normal `/oidc-exchange` login flow and ordinary request replay of the existing session cookie against any admin-gated route, with no additional exploitation needed once the precondition (role downgrade with valid old session) is met.

### Recommendation
Re-validate the role at authorization time for OIDC sessions rather than trusting the cached `oidc_sessions.user_role`: either re-query/re-verify current group claims from the identity provider (e.g., via introspection or a fresh claims check) on each `AuthorizedUserWithSession` call or a bounded freshness window, or implement an active background sync job (as hinted by the `UpstreamSyncInterval` config and misleading comment) that updates/invalidates `user_role` in `oidc_sessions` promptly upon detecting a downgrade, and have `AuthorizedUserWithSession` treat any role mismatch as session invalidation, forcing re-authentication.

### Proof of Concept
Go integration test plan for `oidc_test.go`:
1. Insert a fake OIDC session row directly reflecting a prior admin login: `INSERT INTO oidc_sessions (id, user_email, user_role, created_at) VALUES ('sess-1', 'user@test.com', 'admin', now())`.
2. Simulate a downgrade event that would occur upstream (e.g., update local canonical source of truth, or note that no such source exists for OIDC and skip straight to step 3).
3. Call `oi.AuthorizedUserWithSession(ctx, "sess-1")` and assert it still returns `Role: clsessions.UserRoleAdmin` even though the "current" claims/role should now be lower — demonstrating the stale-role trust.
4. Extend to a handler-level test: perform a login producing role `edit`, manually flip `oidc_sessions.user_role` to `admin` (simulating a compromised or stale row / a race with a real downgrade), then hit an admin-gated route with the session cookie and assert it returns `200 OK` instead of `403`, proving the authorization layer relies solely on the cached column with no live re-check.

func (sr *sessionReaper) Work(ctx context.Context) {
	recordCreationStaleThreshold := sr.config.SessionReaperExpiration().Before(
		sr.config.SessionTimeout().Before(time.Now()))
	err := sr.deleteStaleSessions(ctx, recordCreationStaleThreshold)
	if err != nil {
		sr.lggr.Error("unable to reap stale sessions: ", err)
	}
}

// DeleteStaleSessions deletes all sessions before the passed time.
func (sr *sessionReaper) deleteStaleSessions(ctx context.Context, before time.Time) error {
	_, err := sr.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE created_at < $1", before)
	return err
}
