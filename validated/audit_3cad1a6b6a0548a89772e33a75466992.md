### Title
APR0 withdraw receipt permanently reverts `stopEpoch` once APR is set back to non-zero — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2016-1284 is a crafted-input → assertion-abort → daemon-halt bug: a specific flag combination reaches a `REQUIRE` path that kills the whole process. The closest analog in this codebase is `IdleCreditVault.prepareStopEpochWithApr0`: once any lender has an open APR=0 withdraw principal (`apr0TotalPrincipal != 0`), the function `revert NotAllowed()` whenever `unscaledApr != 0`. Since this function is invoked on the CDO's epoch-stop path, a single unprivileged `requestWithdraw` made while the vault is in APR0 mode turns into a stateful "assertion" that aborts every subsequent `stopEpoch` as long as the APR stays non-zero, freezing all vault funds.

### Finding Description
In `requestWithdraw`, when `unscaledApr == 0` and the pool is not closed, the request is routed into the APR0 bucket:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:285-286
if (unscaledApr == 0 && !isClosed) {
  _requestWithdrawApr0(_amount, _user);
}
```

which increments the global bucket `apr0TotalPrincipal` (line 576). At epoch end the CDO calls `prepareStopEpochWithApr0`, which contains an unconditional abort:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:499-508
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

The bucket `apr0TotalPrincipal` is only cleared at line 540 — after the revert point. So if the APR is changed to a non-zero value (a routine, honest manager/CDO action via `setAprs`/`setAprsWithBuffer`/`setApr`, lines 206-235, which have no check against an open APR0 bucket) while any APR0 request is pending, every `stopEpoch`/`stopEpochWithDuration` call reverts. The attacker's contribution is a single ordinary withdraw request during an APR0 epoch; the abort then fires on the privileged epoch-state-machine path, exactly like the crafted flag value hitting the `REQUIRE` in `rdataset.c`.

### Impact Explanation
While the condition holds, the epoch cannot be stopped: borrower repayments cannot be booked, pending withdraw receipts cannot be funded (`collectWithdrawFunds` is only reached via stopEpoch), and new epochs cannot start. All underlying held by the vault and all pending user claims are frozen. The freeze is temporary only to the extent the manager can restore `unscaledApr = 0`; if the intended operation is a non-zero APR (the normal case), either the vault stays bricked or APR0 interest accounting must be abandoned, and any APR0 requester effectively blocks the APR transition itself — one lender's cheap withdraw request vetoes the pool's return to a yield-bearing regime. Loss is quantified as 100% of TVL frozen plus forfeited APR0-user claims until the APR is forced back to 0.

### Likelihood Explanation
Triggering requires only: (1) the vault in APR0 mode (`unscaledApr == 0`, a supported operating mode per the dedicated `apr0Users`/`apr0RateByEpoch` plumbing), and (2) a later APR change to non-zero — an ordinary management action with no guard coupling it to `apr0TotalPrincipal`. Any tranche-token holder can create the poisoning state with a minimal `requestWithdraw`. No privileged maliciousness is needed, and no existing guard (`_onlyIdleCDO`, `isClosed` check, `NotAllowed` on re-request) prevents it; the revert is itself the bug.

### Recommendation
Do not revert in `prepareStopEpochWithApr0` when `unscaledApr != 0`. Instead, settle the open APR0 bucket with zero incremental interest (skip the allocation, emit an event, and still execute `apr0TotalPrincipal = 0`), or perform the APR validity check at APR-set time (`setApr` should refuse a non-zero APR while `apr0TotalPrincipal != 0`, or the request side should refuse APR0 requests unless the APR is locked for the epoch). This removes the persistent abort from the epoch state machine.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Assume standard IdleCreditVault/IdleCDOEpochVariant fork setup from
// test/foundry/IdleCreditVault.t.sol (_startEpochAndCheckPrices helpers).

// 1. Manager sets APR to 0 (supported mode).
vm.prank(manager);
strategy.setAprs(0, 0);

// 2. Lender deposits AA and requests a withdraw during the APR0 epoch.
idleCDO.depositAA(10_000 * ONE_SCALE);
cdoEpoch.requestWithdraw(aaBal / 2, address(AAtranche));
assertGt(strategy.apr0TotalPrincipal(), 0); // poison state armed

// 3. Manager legitimately restores a non-zero APR for the next period
//    (no guard links this to apr0TotalPrincipal).
vm.prank(manager);
strategy.setAprs(5e18, 5e18);

// 4. Every subsequent stopEpoch aborts inside prepareStopEpochWithApr0.
vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
cdoEpoch.stopEpoch(); // via manager/owner call used by the harness

// 5. Freeze persists for any non-zero APR: stopEpoch can never clear the
//    bucket, borrower funding and pending receipts stay frozen.
```
