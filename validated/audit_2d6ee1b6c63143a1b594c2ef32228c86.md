### Title
EI run-role callers can bypass webhook-UUID removal and trigger legacy webhook jobs by int32 ID due to `isUser` check being satisfied by EI-synthesized user role - (File: core/web/pipeline_runs_controller.go)

### Summary
`PipelineRunsController.Create` only blocks UUID-formatted job IDs to enforce removal of webhook-UUID triggering, and gates the int32-ID path behind an `isUser` check intended to exclude external initiators (EIs). However, `auth.AuthenticateExternalInitiator` sets the same `SessionUserKey` context value used by `GetAuthenticatedUser`, giving EI-authenticated requests a synthetic run-role `User`, so `isUser` evaluates true for EIs too, defeating the intended restriction.

### Finding Description
The `Create` handler rejects only UUID-shaped `idStr` values with `job.ErrJobTypeRemoved`, and otherwise permits any int32-parseable ID to reach `prc.App.RunJobV2(ctx, jobID, nil)` provided `isUser` is true, per the code and comment "only users are allowed to run jobs using int IDs - EIs not allowed" at core/web/pipeline_runs_controller.go:109-124. The `isUser` check calls `auth.GetAuthenticatedUser(c)`, which merely checks for the presence of `SessionUserKey` in the gin context (core/web/auth/auth.go:177-187). But `AuthenticateExternalInitiator`, the auth method used for EI-authenticated requests, explicitly injects `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` in addition to `SessionExternalInitiatorKey` (core/web/auth/auth.go:143-151), specifically so EI callers inherit "run" role for other endpoints requiring `RequiresRunRole`. This causes `GetAuthenticatedUser` (and thus `isUser`) to also return true for EI callers, meaning the code comment's intended EI exclusion is not actually enforced by this check. If a webhook-type job still exists in the database (e.g., created prior to webhook job type removal, as simulated by `cltest.MustInsertWebhookSpec` direct-DB insertion in the existing test), an EI holding valid run-role credentials could supply that job's int32 ID instead of its UUID and have `RunJobV2` invoked on it, since no job-type check exists anywhere in the `Create` handler for the int32 path.

### Impact Explanation
If confirmed end-to-end (pending verification of route auth wiring and `RunJobV2`'s internal job-type handling), this would allow an EI credential holder — an unprivileged external caller per the threat model — to trigger execution of a webhook-type job pipeline that was supposed to be permanently disabled from external triggering, potentially executing bridge/task pipelines and consuming resources or triggering unintended on-chain-adjacent effects tied to that job. This falls under "unauthorized job run" impact class.

### Likelihood Explanation
Requires: (1) at least one webhook-type job still present in the node's database (only possible via pre-existing/legacy jobs or direct DB manipulation, since new webhook job creation is blocked), and (2) valid EI credentials with run role. Given EI credentials are a lower-privilege bearer than admin/edit users and the check is a straightforward header-based token, this is feasible if precondition (1) holds, but likelihood is uncertain since it depends on legacy job survival post-migration, which I could not verify without additional investigation into migration/deprecation handling.

### Recommendation
Fix `GetAuthenticatedUser`/EI detection so the `isUser` check in `Create` actually distinguishes real user sessions from EI-synthesized ones — e.g., check `auth.GetAuthenticatedExternalInitiator(c)` is absent, not merely that `SessionUserKey` is set. Additionally, add an explicit job-type check in `Create` (or in `RunJobV2`) to reject runs against `job.Webhook`-type jobs regardless of ID format, rather than relying solely on UUID-shape detection.

### Proof of Concept
1. Insert a webhook job directly into the DB via `cltest.MustInsertWebhookSpec` (as done in `TestPipelineRunsController_RunExistingWebhookJobRejected`), and record its int32 `ID`.
2. Set up an EI in the test app's DB with run-role credentials (see existing EI test helpers used elsewhere, e.g., `cltest.NewApplication...` external initiator setup).
3. As the EI, send `POST /v2/jobs/<int32-ID>/runs` with valid `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (not UUID).
4. Assert whether the response is `422 Unprocessable Entity` (expected/secure) or `200 OK` with a created pipeline run (vulnerable) — confirming whether `isUser` truly excludes EI or not.
5. Additionally trace `RunJobV2` in core/services/chainlink/application.go to confirm whether it independently checks and rejects `job.Webhook` type jobs, which would mitigate this regardless of the `isUser` gap.
