## Title
Unchecked BLS12-381 G1/G2 point addition/subtraction syscalls permit invalid-subgroup point aggregation - (File: syscalls/src/lib.rs)

### Summary
The `SyscallCurveGroupOps` builtin function exposes BLS12-381 G1/G2 `add`/`sub`/`mul` operations to any BPF program via `solana_bls12_381_syscall::bls12_381_g1_addition_unchecked` / `bls12_381_g2_addition_unchecked` (and the corresponding `_subtraction_unchecked` variants). Unlike `bls12_381_g1_point_validation`/`bls12_381_g2_point_validation` (used by the separate `SyscallCurvePointValidation` builtin), the group-op path performs no subgroup (or, depending on the underlying crate, no on-curve) validation on `left_input_addr`/`right_input_addr` before combining them, analogous to the point-aggregation flaw described in CL-2021-20 for the BLST Go bindings, where points were combined/aggregated without the library enforcing that inputs belonged to the correct prime-order subgroup. [1](#0-0) 

### Finding Description
`SyscallCurveGroupOps` translates two raw points directly from guest memory and passes them straight into `bls12_381_g1_addition_unchecked` / `bls12_381_g2_addition_unchecked` (and the `_subtraction_unchecked` twins) with no call to `bls12_381_g1_point_validation` / `bls12_381_g2_point_validation` in between: [2](#0-1) [3](#0-2) 

Compare this with the dedicated validation syscall, which is the only place in the codebase that calls the "checked" `bls12_381_g1_point_validation`/`bls12_381_g2_point_validation` functions: [4](#0-3) 

Because addition/subtraction is explicitly named "unchecked", any Solana program can invoke this syscall (once `enable_bls12_381_syscall` is active) with attacker-chosen 96/192-byte point encodings that are on-curve but not in the correct r-order subgroup (i.e., have non-trivial cofactor components), or that are otherwise not validated the same way as the dedicated validation path. This is the same bug class as CL-2021-20: BLST's point-aggregation entry points (`Aggregate`) did not enforce subgroup membership on inputs, so a maliciously crafted "public key" or "signature" share outside the correct subgroup could poison an aggregate without being individually detected, invalidating the pairing-equation guarantees that on-chain BLS-based programs (multisig/threshold-signature contracts, oracle aggregation, zk-verifier point accumulation, etc.) build on top of these syscalls.

Any program built on top of `sol_curve_group_op`/`sol_curve_pairing_map` to implement custom BLS aggregation (which is exactly the intended use-case advertised by SIMD-0388) inherits this gap: it can aggregate points into a running sum via repeated `ADD` calls and then feed the result into `SyscallCurvePairingMap` for signature/proof verification, with no subgroup check ever performed unless the calling program manually invokes `SyscallCurvePointValidation` on every single input first — which is easy to omit given the two syscalls are independent and nothing in `SyscallCurveGroupOps` enforces it.

### Impact Explanation
If a downstream on-chain program uses `sol_curve_group_op` to accumulate BLS12-381 points (public keys or signature shares) without separately and correctly invoking `sol_curve_validate_point` on each input, an attacker can supply a small-subgroup / invalid-subgroup point that still satisfies "on-curve" but not "in correct subgroup", corrupting the aggregate. Depending on how the aggregate is subsequently verified (e.g., via `SyscallCurvePairingMap`), this can let an attacker forge or bypass an aggregate-signature/proof check that the program relies on for fund release or state transitions — a concrete unauthorized state/fund mutation in any program built on this primitive. Severity depends entirely on downstream program usage; the syscall itself is a building block, so this is a Medium-severity primitive-level gap rather than a directly exploitable core-protocol bug (the core BLS vote/certificate verification path in `bls-cert-verify`/`bls-sigverify` uses the separate `solana_bls_signatures` crate with `PopVerified`/full-validation aggregation, not this raw syscall).

### Likelihood Explanation
Likelihood is Medium: exploitation requires a specific downstream program to misuse the "unchecked" group-op syscalls for cryptographic point aggregation without independently subgroup-validating inputs. Given that `sol_curve_group_op` is explicitly documented/intended to let arbitrary programs implement BLS-based schemes on-chain, and the "unchecked" naming is easy to overlook, this is a realistic footgun reachable by any ordinary deployed program and triggerable by any transaction that invokes it with crafted point bytes.

### Recommendation
- Rename/document `bls12_381_g1_addition_unchecked`/`bls12_381_g2_addition_unchecked`/`_subtraction_unchecked` clearly to state they perform no subgroup validation, and add prominent syscall documentation (and SDK helper wrappers) warning callers they must validate inputs via `sol_curve_validate_point` before aggregating.
- Consider adding a "checked" variant of `SyscallCurveGroupOps` for BLS12-381 that performs subgroup validation on both inputs before combining, gated by its own compute-cost line item, for programs implementing signature/pubkey aggregation.
- Audit `program-runtime/src/execution_budget.rs` / `compute-budget/src/compute_budget.rs` cost fields to ensure a "checked" variant's added validation cost is properly metered.

### Proof of Concept
Conceptually:
1. Deploy a program that repeatedly calls `sol_curve_group_op(BLS12_381_G1, ADD, ...)` to combine attacker-supplied G1 points into a running "aggregate public key," exactly the pattern shown in the syscall's own doc comment ("Elliptic Curve Group Operations ... BLS12-381") [5](#0-4) .
2. Craft one input point that lies on the BLS12-381 G1 curve but outside the prime-order subgroup (cofactor multiple), pass it as `right_input_addr`.
3. Observe that `bls12_381_g1_addition_unchecked` returns `Some(result_point)` and the syscall reports `SUCCESS` without any subgroup check being performed, unlike the separate validation path shown at [6](#0-5) , confirming the aggregate now contains an unvalidated subgroup component that a naive downstream pairing check (`SyscallCurvePairingMap`, [7](#0-6) ) would not have rejected on its own.

Note: I could not locate the source of the `solana_bls12_381_syscall` crate itself (it appears to be an external/vendored dependency not indexed in this repo), so I cannot confirm from source exactly which validation steps `_unchecked` omits versus the crate's internal on-curve check; this should be verified directly against that crate's implementation before treating this as conclusively exploitable.

declare_builtin_function!(
    /// Elliptic Curve Pairing Map
    ///
    // Currently, the following curves are supported:
    // - BLS12-381
    SyscallCurvePairingMap,
    fn rust(
        invoke_context: &mut InvokeContext<'_, '_>,
        curve_id: u64,
        num_pairs: u64,
        g1_points_addr: u64,
        g2_points_addr: u64,
        result_addr: u64,
    ) -> Result<u64, Error> {
        use {
            solana_define_syscall::curve_constants::*,
            solana_bls12_381_syscall::{
                PodG1Point as PodBLSG1Point, PodG2Point as PodBLSG2Point,
                PodGtElement as PodBLSGtElement,
            },
        };

        let check_aligned = invoke_context.get_check_aligned();
        match curve_id {
            BLS12_381_LE | BLS12_381_BE => {
                let execution_cost = invoke_context.get_execution_cost();
                let cost = execution_cost
                    .bls12_381_one_pair_cost
                    .saturating_add(
                        execution_cost
                            .bls12_381_additional_pair_cost
                            .saturating_mul(num_pairs.saturating_sub(1)),
                    );
                invoke_context.compute_meter.consume_checked(cost)?;

                let memory_mapping = invoke_context.memory_contexts.memory_mapping_mut()?;
                let g1_points = translate_slice::<PodBLSG1Point>(
                    memory_mapping,
                    g1_points_addr,
                    num_pairs,
                    check_aligned,
                )?;

                let g2_points = translate_slice::<PodBLSG2Point>(
                    memory_mapping,
                    g2_points_addr,
                    num_pairs,
                    check_aligned,
                )?;

                let endianness = if curve_id == BLS12_381_LE {
                    solana_bls12_381_syscall::Endianness::LE
                } else {
                    solana_bls12_381_syscall::Endianness::BE
                };

                if let Some(gt_element) = solana_bls12_381_syscall::bls12_381_pairing_map(
                    solana_bls12_381_syscall::Version::V0,
                    g1_points,
                    g2_points,
                    endianness,
                ) {
                    translate_mut!(
                        memory_mapping,
                        check_aligned,
                        let result_ref_mut: (&mut MaybeUninit<PodBLSGtElement>) = map(result_addr)?;
                    );
                    result_ref_mut.write(gt_element);
                    Ok(SUCCESS)
                } else {
                    Ok(1)
                }
            }
            _ => {
                Err(SyscallError::InvalidAttribute.into())
            }
        }
    }
);
