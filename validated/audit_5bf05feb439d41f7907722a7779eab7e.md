### Title
Unredacted bridge `OutgoingToken` disclosed via `Index`/`Show` GET endpoints to any authenticated bridge-reader - ([File: core/web/bridge_types_controller.go])

### Summary
`BridgeTypesController.Index` and `.Show` build `presenters.BridgeResource` via `NewBridgeResource`, which unconditionally serializes `OutgoingToken` (no `omitempty`/redaction), unlike `IncomingToken` which is explicitly commented as "only provided when creating a Bridge." [1](#0-0)  Any client able to reach the read-only `GET /v2/bridge_types` (paginated) or `GET /v2/bridge_types/:BridgeName` endpoints therefore receives the bridge's outgoing credential in plaintext for every bridge, and pagination via `paginatedResponse` lets an attacker enumerate the full bridge catalog across all pages. [2](#0-1) 

### Finding Description
`Index` fetches all bridges page by page from `BridgeORM().BridgeTypes` and maps each into a `BridgeResource` before calling `paginatedResponse`, and `Show` does the same for a single bridge by name. [3](#0-2)  `NewBridgeResource` copies `b.OutgoingToken` directly onto the JSON-serialized resource with no redaction, while the sibling field `IncomingToken` is explicitly gated to creation-time only via a code comment and is only set manually in `Create`. [4](#0-3) [5](#0-4)  This asymmetry indicates `OutgoingToken` was not intended to be treated identically to a public field, yet it is returned on every list/show call.

I was not able to confirm the exact role gating configured in `core/web/router.go` for the `bridge_types` routes within the available tool output (the grep results for that file did not return visible route/role content in this session), so I cannot definitively state whether "view" role tokens are actually authorized to call these GET endpoints, or whether they are restricted to admin/edit roles only. This is a material gap: if the routes are admin-only, there is no privilege violation, only defense-in-depth concern; if view-role tokens can reach these routes (which is the general Chainlink pattern — GET/read endpoints permitted to lower-privilege API tokens), then the finding is a genuine authorization/exposure bug because a read-only credential grants a node-wide secret (the bridge adapter's outgoing authentication token) that could be reused to authenticate as the node against the external adapter or replay it elsewhere.

### Impact Explanation
If reachable by view-role credentials, this matches the Chainlink bounty class "sensitive information disclosure via API" — full harvesting of all configured bridge `OutgoingToken` values (external-adapter credentials) by the lowest privileged authenticated role, using ordinary pagination to walk `/v2/bridge_types`. This does not constitute an authentication bypass by itself but is a legitimate credential-exposure/least-privilege violation if view-scoped tokens can call these routes.

### Likelihood Explanation
Exploitability depends entirely on confirming the router's role requirement for `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName`, which I could not verify from available search output in this session. Assuming the standard Chainlink pattern of read routes being permitted to `view`-role API tokens, the attack requires only a valid low-privilege session/API token and a handful of paginated GET requests — no further exploitation complexity.

### Recommendation
Confirm the role requirement in `core/web/router.go` for the bridge_types read routes. If `view` role is permitted, either (a) restrict `Index`/`Show` to `admin`/edit-capable roles matching the UI's bridge-management workflow, or (b) redact `OutgoingToken` from the `BridgeResource` returned by `Index`/`Show` (mirroring the `IncomingToken` creation-only exposure pattern) and only reveal it on creation/update responses to the authorized actor.

### Proof of Concept
Go handler-level integration test plan (`core/web/bridge_types_controller_test.go`):
1. Seed several bridges with distinct `OutgoingToken` values via `BridgeORM().CreateBridgeType`.
2. Construct an HTTP client authenticated with a `view`-role session/API token (using existing test helpers, e.g. `cltest.CreateJobRunViaJSON`/`cltest.NewTestClient` equivalents used elsewhere in `bridge_types_controller_test.go`).
3. Call `GET /v2/bridge_types?size=<n>&page=1..N` iterating through all pages.
4. Assert the aggregated JSON responses contain non-empty `outgoingToken` values for all seeded bridges, proving the view-role token retrieved every bridge's outgoing credential.
5. Repeat with `GET /v2/bridge_types/:BridgeName` to confirm `Show` exposes the same field to the same role.

Note: this PoC's validity is conditioned on the router actually granting `view` role access to these two routes — that mapping should be verified in `core/web/router.go` before treating this as a confirmed, in-scope authorization bypass rather than an intended read-access disclosure.

// Index lists Bridges, one page at a time.
func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
