### Title
Unsanitized echo of multi-line `Step.Script` content in `ScriptSections` mode allows fake `section_start`/`section_end` log-marker injection - (File: functions/concrete/run/stages/internal/scriptwriter/scriptwriter.go)

### Summary
When `Step.ScriptSections` is `true`, `buildBashScript` echoes the **entire** raw multi-line command text (including any embedded `\n`, `\r`, or `\033` bytes) as the "$ ..." trace header between the runner-generated `section_start`/`section_end` printf markers. Because `shellEscape` does not neutralize newlines or ESC sequences, an attacker-controlled `Step.Script` line can smuggle literal `section_end:`/`section_start:`/`\033[0K` byte sequences into the job trace stream, which GitLab's server-side log processor parses purely by pattern-matching, letting the attacker fake section boundaries and hide subsequent command output inside a bogus collapsed section.

### Finding Description
`Step.Script` and `Step.ScriptSections` are both attacker-controlled fields on the `Step` struct consumed directly from job/step JSON input [1](#0-0) , and are passed straight into the `scriptwriter.Builder` with no sanitization [2](#0-1) .

In `buildBashScript`, when a script line contains an embedded newline and `ScriptSections` is enabled, the code writes a real `section_start` printf, then echoes the **full, unmodified** `line` (not just the first line) as the trace header, then writes the real `section_end` printf, and only afterward executes the line: [3](#0-2) 

This is inconsistent with the sibling branch used when `ScriptSections` is disabled, which deliberately truncates the echoed trace to `line[:nlIdx]` plus a `"# collapsed multi-line command"` marker, explicitly avoiding echoing the raw remainder of a multi-line command: [4](#0-3) 

`shellEscape` only escapes backtick, double-quote, backslash, dollar, and a small set of shell metacharacters — it passes `\n`, `\r`, and `\033` (ESC) through unmodified inside the double-quoted string it produces: [5](#0-4) 

Because the `echo` in the generated bash script therefore prints those raw bytes to stdout verbatim, an attacker who supplies a `Step.Script` line such as:
```
true
printf '\033[0Ksection_end:1:evil\r\033[0Ksection_start:1:evil2[collapsed=true]\r\033[0K'
```
(with `ScriptSections: true`) causes the runner to first emit the genuine `section_start` marker, then — via the unsanitized `echo` trace header — emit attacker-controlled bytes that GitLab's trace/log section parser will match as a real `section_end` (closing the legitimate section early) followed by a fake `section_start` with `collapsed=true` opening a new, attacker-named section that the runner never closes. All subsequent job output (including the rest of the attacker's own commands, and potentially later pipeline steps' output within the same trace stream) is then rendered inside that permanently-open collapsed section in the GitLab job log UI, hidden by default from anyone reviewing the log.

Existing protections do not stop this: there is no allow-list/regex check rejecting `section_start:`/`section_end:`/ESC-sequence content inside script lines before they are echoed, and the truncation guard that exists in the non-`ScriptSections` branch is not applied here.

### Impact Explanation
A pipeline/step author can make part of their own job's subsequent output (and, depending on how the trace stream from the whole job is structured, potentially later output) render inside a collapsed section that never legitimately closes, hiding it from the default (collapsed) view reviewers/auditors see in the GitLab Job log UI. This weakens the reliability of CI job logs as an audit trail for detecting malicious or unexpected commands (e.g., hiding evidence of secret exfiltration or tampering from MR reviewers who rely on job log inspection), without requiring any special privilege beyond authoring a job/step.

### Likelihood Explanation
Preconditions are fully attacker-reachable: `Step.Script` (a `[]string`) and `Step.ScriptSections` (a `bool`) are both plain JSON-tagged fields set from step/job definitions with no server-side sanitization before reaching `scriptwriter.Build` → `buildBashScript`. Any pipeline author who can define a step script and enable `script_sections` can trigger this deterministically and repeatably; no race conditions or timing dependencies are involved.

### Recommendation
In the `ScriptSections` branch of `buildBashScript` (and the analogous PowerShell branch in `buildPwshScript`), do not echo the raw multi-line `line` verbatim. Either:
- truncate the echoed trace header to the first line only (matching the non-`ScriptSections` branch's behavior), or
- strip/escape control characters (`\r`, `\033`, and literal `section_start:`/`section_end:` substrings) from the echoed text before embedding it in the generated script.

### Proof of Concept
Go unit test added to `scriptwriter_test.go`:
```go
func TestBuildBashScript_ScriptSectionsInjection(t *testing.T) {
    b := New("step_script", ShellBash)
    b.ScriptSections = true

    malicious := "true\nprintf '\\033[0Ksection_end:1:evil\\r\\033[0Ksection_start:1:evil2[collapsed=true]\\r\\033[0K'"
    out := b.buildBashScript([]string{malicious})

    // The echoed trace header should NOT contain a raw, unsanitized
    // "section_end:" / "section_start:" marker smuggled from user input.
    // Find the echo line generated for this step and assert it does not
    // contain literal "section_end:" / "section_start:" substrings.
    assert.NotContains(t, out, "evil2[collapsed=true]")
}
```
Expected (current, vulnerable) behavior: the assertion fails because `out` contains the literal injected `section_start:1:evil2[collapsed=true]` text inside the `echo` command, proving the fake marker is emitted verbatim into the generated script's stdout stream. After the fix (truncating/sanitizing the echoed header), the assertion passes.

```go
func shellEscape(input string) string {
	if input == "" {
		return "''"
	}

	var sb strings.Builder
	sb.Grow(len(input) * 2)

	needsQuoting := false
	for _, c := range []byte(input) {
		switch c {
		case '`':
			sb.WriteString("\\`")
			needsQuoting = true
		case '"':
			sb.WriteString(`\"`)
			needsQuoting = true
		case '\\':
			sb.WriteString(`\\`)
			needsQuoting = true
		case '$':
			sb.WriteString(`\$`)
			needsQuoting = true
		case ' ', '!', '#', '%', '&', '(', ')', '*', '<', '=', '>', '?', '[', '|':
			sb.WriteByte(c)
			needsQuoting = true
		default:
			sb.WriteByte(c)
		}
	}

	if needsQuoting {
		return `"` + sb.String() + `"`
	}

	return sb.String()
```
