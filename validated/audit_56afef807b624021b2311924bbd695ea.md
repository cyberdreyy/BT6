### Title
Zero-amount token transfers in `fullfillWriteOffRequest` revert on tokens that disallow zero transfers, blocking write-off fulfillment - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`fullfillWriteOffRequest` performs up to three underlying-token transfers and one tranche-token transfer without zero-amount guards. When a write-off request's `underlyings` is 0, or when the configured `exitFee` rounds `_totFee` to 0, the corresponding `safeTransferFrom`/`safeTransfer` calls execute with `amount == 0`. Underlyings in IdleCreditVault deployments are arbitrary ERC20s chosen at initialization; some ERC20s (e.g., LEND) revert on zero-value transfers, making the write-off path unusable.

### Finding Description
In `contracts/IdleCreditVaultWriteOffEscrow.sol`, `fullfillWriteOffRequest` does:

```solidity
underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings); // L139: unguarded
...
if (_exitFee > 0) {
  _totFee = (_underlyings * _exitFee) / FULL_VALUE;
  underlyingToken.safeTransfer(feeReceiver, _totFee);                      // L146: _totFee may be 0
}
underlyingToken.safeTransfer(_user, _underlyings - _totFee);               // L149: may be 0
```

Two zero-amount cases exist:
1. `currentRequest.underlyings == 0` (e.g., write-off request created after the tranche's virtual price fell to 0 or dust): `_underlyings` only needs `>= currentRequest.underlyings`, so `0` is accepted, and `safeTransferFrom(..., 0)` runs.
2. `_underlyings * exitFee < FULL_VALUE` (100_000): `_totFee` truncates to 0 while `_exitFee > 0`, so `safeTransfer(feeReceiver, 0)` runs.

Everywhere else in the codebase this class was already hardened: `_transferUnderlyings`, `_transferUnderlyingsFrom`, `_transferFundedClaim`, `_transferDefaultRecovery`, `collectWithdrawFunds`, `collectInstantWithdrawFunds`, `deposit`, and `sendInterestAndDeposits` all early-return on `amount == 0` (`IdleCDOCreditVault.sol` L580-607, `IdleCreditVault.sol` L400, L427-429, L583, L602, L898, L913). The escrow is the outlier.

### Impact Explanation
On an underlying that reverts for zero transfers, `fullfillWriteOffRequest` always reverts for such requests. The escrowed tranche tokens cannot be bought out by the borrower/fulfiller, so the write-off settlement path is blocked — temporary freezing of escrowed tranche positions. Recovery requires the user to call `deleteWriteOffRequest` (returning tranche tokens) or the owner to unset `exitFee`/the fulfiller to overpay enough to make `_totFee` nonzero, none of which are available for the `_underlyings == 0` case without abandoning the escrowed write-off flow. Loss is bounded to the escrowed position's value and is temporary rather than permanent.

### Likelihood Explanation
Low-to-medium likelihood. It requires (a) a vault whose underlying token reverts on zero transfers — possible since `IdleCreditVault.initialize` accepts any `_underlyingToken` — and (b) a write-off request priced at 0 or dust underlyings, or a nonzero `exitFee` combined with small fulfill amounts. Anyone can call `fullfillWriteOffRequest`, but honest fulfillers paying the exact `currentRequest.underlyings` hit the revert deterministically once conditions hold.

### Recommendation
Add zero-amount guards consistent with the rest of the codebase:

```solidity
if (_underlyings != 0) {
  underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
}
uint256 _exitFee = exitFee;
uint256 _totFee;
if (_exitFee > 0) {
  _totFee = (_underlyings * _exitFee) / FULL_VALUE;
  if (_totFee != 0) underlyingToken.safeTransfer(feeReceiver, _totFee);
}
if (_underlyings - _totFee != 0) underlyingToken.safeTransfer(_user, _underlyings - _totFee);
```
