### Title
Malicious `maker`/`order.receiver` can permanently DoS `EscrowDst.withdraw`/`publicWithdraw` by rejecting native-token transfer, freezing resolver funds until forced cancellation - (File: `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw()` sends the destination-chain payout directly to `immutables.maker` (derived from the maker-controlled `order.receiver`) using `_uniTransfer` → `_ethTransfer`, which performs a raw `call` and reverts the whole transaction on failure with no wrap-fallback, exactly the same root cause pattern as the Notional H-8 report (unwrapped native transfer to a potentially hostile recipient blocks a required state transition).

### Finding Description
When a maker fills an order with a native-token (`token == address(0)`) destination leg, the recipient of the payout in `EscrowDst._withdraw` is `immutables.maker.get()`, which is set from `order.receiver` (or `order.maker` by default) by the maker themselves in `BaseEscrowFactory._postInteraction`: [1](#0-0) 
An unprivileged maker can set `order.receiver` to a contract whose `receive()`/fallback always reverts. Then, both `withdraw` and `publicWithdraw` call `_withdraw`, which unconditionally sends the payout natively to that address via `_uniTransfer` → `_ethTransfer`: [2](#0-1) [3](#0-2) 
`_ethTransfer` uses a raw `call` and reverts the entire transaction with `NativeTokenSendingFailure` if the recipient rejects the value, exactly mirroring the Notional `withdrawWrappedNativeToken=false` pattern that let a hostile recipient block settlement. There is no fallback to wrap ETH (e.g., into WETH) so the transfer cannot be forced through. This is confirmed by the repository's own tests, which explicitly assert the whole withdrawal reverts when the recipient rejects native ETH: [4](#0-3) 

Because `withdraw`/`publicWithdraw` are the only mechanisms that reveal the secret on the destination chain, blocking them prevents the resolver (taker) from ever completing the atomic swap through the intended path. The only recovery is `cancel()`, which is gated behind the `DstCancellation` timelock and pays the taker back directly (bypassing the hostile maker): [5](#0-4) 

### Impact Explanation
This fits the "temporary freezing of funds during the live swap lifecycle" High-impact bucket: an unprivileged maker can force the resolver's already-committed destination-chain principal + safety deposit to sit frozen and unusable from the start of the withdrawal window until the `DstCancellation` timelock elapses, purely by choosing a reverting `order.receiver` contract, with zero cost or risk to themselves (their own source-side funds are simply returned to them once `EscrowSrc.cancel` executes). This also silently causes the resolver to lose the accrued integrator/protocol fee for that fill, since a forced cancellation bypasses fee distribution entirely.

### Likelihood Explanation
Likelihood is high given the trigger only requires setting a normal LOP `order.receiver` field to a contract with a reverting receive function — no privileged role, no timing race, no gas griefing tricks required. It is directly reachable from the live order-fill → `createDstEscrow` → `withdraw` path used by every native-asset destination swap.

### Recommendation
Do not let recipient failure block a critical state transition: when the native transfer to `maker`/fee recipients fails, fall back to wrapping the native asset (WETH) and sending the wrapped ERC20 instead, or use a pull-payment/escrow-of-last-resort pattern for stuck native transfers, similar to the recommendation accepted for the Notional H-8 fix (which ultimately removed the direct transfer in favor of a safer settlement flow).

### Proof of Concept
1. Maker creates an order with `order.receiver` = `MaliciousReceiver` (a contract whose `receive()` always reverts) and destination token = native ETH (`address(0)`).
2. Resolver fills the order; `BaseEscrowFactory._postInteraction` sets `immutablesComplement.maker = MaliciousReceiver` [6](#0-5) .
3. Resolver deploys and funds `EscrowDst` via `createDstEscrow` with native value.
4. During the withdrawal window, resolver calls `withdraw(secret, immutables)`; `_withdraw` attempts `_uniTransfer(token=0, MaliciousReceiver, amount)` → `_ethTransfer` reverts with `NativeTokenSendingFailure`, exactly reproduced by the existing repo test `test_NoFailedNativeTokenTransferWithdrawalDstNative` [4](#0-3) .
5. `publicWithdraw` (callable by any access-token holder) fails identically since it also routes through `_withdraw`.
6. Resolver's funds remain locked in `EscrowDst` until `DstCancellation` timelock passes and `cancel()` is called, at which point the resolver only recovers principal — the swap never completes and any fee is lost.

```text
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```

```text
    function _uniTransfer(address token, address to, uint256 amount) internal {
        if (token == address(0)) {
            _ethTransfer(to, amount);
        } else {
            IERC20(token).safeTransfer(to, amount);
        }
    }

    /**
     * @dev Transfers native tokens to the recipient.
     */
    function _ethTransfer(address to, uint256 amount) internal {
        (bool success,) = to.call{ value: amount }("");
        if (!success) revert NativeTokenSendingFailure();
    }
```
