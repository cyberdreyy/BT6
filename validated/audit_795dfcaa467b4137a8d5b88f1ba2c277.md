### Title
Builder payment misdirected/escaped when `BuilderIndex` is reused before a pending payment settles - ([File: specs/gloas/beacon-chain.md])

### Summary
`process_execution_payload_bid` records a promised builder payment (`BuilderPendingPayment.withdrawal.builder_index`) by numeric `BuilderIndex`, not by builder pubkey. Builder indices are explicitly documented as reusable/reassignable to a different pubkey once a builder exits and is swept to zero balance. Because settlement of the pending payment happens one to two epochs later (after `process_builder_pending_payments` and the subsequent withdrawal sweep), a committing builder can exit and free its index before the payment is applied, causing the debit to fall on whatever builder later occupies that same index — this is the direct analog of the CREATE1 "deploy at the same address" report, where an identity bound to a mutable positional slot (nonce/index) is silently reassigned between commitment and use.

### Finding Description
When a bid is accepted, the beacon chain records the builder's payment obligation keyed only by index: [1](#0-0) 

This `BuilderPendingWithdrawal.builder_index` is the sole reference used later, both to accrue attester weight and, once quorum is reached, to actually debit balance: [2](#0-1) [3](#0-2) 

Meanwhile, `get_index_for_new_builder`/`process_builder_deposit_request` explicitly reuse an exited, zero-balance builder's index for an entirely new pubkey, and the spec itself flags this as index-reassignment behavior that implementers must account for: [4](#0-3) 

The withdrawal execution against `state.builders[*].balance` is applied strictly by index at sweep/withdrawal time (per the Output Space semantics of `get_builder_withdrawals`/decrease-by-min(amount,balance)), so whichever builder occupies `builder_index` at settlement time — not necessarily the one who signed the bid — is the one whose Gwei is decreased.

Attack sequence:
1. Builder A (`builder_index = IDX`) submits a winning `ExecutionPayloadBid` with `value = V`, `fee_recipient = proposer's address`. `process_execution_payload_bid` records `BuilderPendingPayment{withdrawal.builder_index=IDX, amount=V}` with weight 0.
2. PTC/attester votes accrue weight on this pending payment across the slot; by epoch boundary weight reaches quorum, and `process_builder_pending_payments` promotes it into `state.builder_pending_withdrawals` (still keyed by `IDX`), to be applied by a later `process_withdrawals` sweep.
3. Before that sweep executes, builder A submits a valid `BuilderExitRequest` (checked only against `get_pending_balance_to_withdraw_for_builder`, not against unresolved-but-not-yet-swept `builder_pending_withdrawals`) and gets fully swept to zero balance, making `IDX` reusable per `get_index_for_new_builder`.
4. Any unrelated builder B later deposits and is assigned the freed `IDX` (deterministic first-fit reuse, not requiring collusion with A).
5. When the pending withdrawal for `IDX` finally executes, it decreases `state.builders[IDX].balance` — now B's balance — by `min(V, balance)`, either wrongfully taking B's Gwei to cover A's commitment, or (if B's balance < V) silently truncating the payment so the proposer's promised fee_recipient receives less than `V`, i.e., the payment "escapes."

This breaks the equality that a builder payment can only be paid from the balance of the builder who actually signed and committed to the bid — exactly analogous to the CREATE1 report where a message destined for one deployed identity is captured by whatever unrelated party later occupies that same slot/address.

### Impact Explanation
This falls under the High-impact category: "a builder payment or withdrawal misdirected, doubled, or escaped, without majority stake or a foreign key requirement." An innocent builder B can have Gwei debited from its own balance to satisfy a commitment it never signed, or the promised proposer payment can be partially/fully lost because it is applied against an occupant with insufficient balance. Neither outcome requires a malicious peer, client bug, or coalition — only ordinary use of `process_builder_exit_request` / `process_builder_deposit_request` by unrelated actors within the timing window between bid acceptance and payment settlement.

### Likelihood Explanation
The timing window is bounded but non-trivial: a pending payment can persist up to roughly two epochs (payment recorded this epoch, promoted at the next epoch boundary, swept afterward), while a builder's full exit-and-sweep cycle (`MIN_BUILDER_WITHDRAWABILITY_DELAY` plus the sweep cadence) is on a similar or longer time-scale, so the race condition is plausible but requires reasonably precise timing by builder A and normal churn from unrelated deposits reusing the freed slot. This is a design-level identity/reference-binding issue rather than a purely theoretical one, since the spec authors already acknowledge index reassignment as intended behavior, but do not appear to account for its interaction with in-flight `BuilderPendingPayment`/`BuilderPendingWithdrawal` records still referencing the stale index.

### Recommendation
Bind `BuilderPendingWithdrawal`/`BuilderPendingPayment` to the builder's pubkey (or a monotonically-unique, non-reusable identifier) rather than to the mutable `BuilderIndex`, or block index reuse (`get_index_for_new_builder`) for any index that still has an unresolved/pending payment or withdrawal referencing it, mirroring how `process_builder_exit_request` already checks `get_pending_balance_to_withdraw_for_builder` before allowing exit.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))

*Note*: Builder indices are reusable. When a builder exits, its index may later
be reassigned to a different builder with a new public key. Any deposit sent to
an exited builder will be withdrawn to the builder’s execution address. Exited
builders cannot be reactivated, although a newly registered builder’s public key
may have previously appeared in the builder set. Implementations that rely on
caching should account for this behavior.

```python
def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:
    # Ignore deposits with unexpected withdrawal credential prefixes
    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
        return

    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        if is_valid_builder_deposit_signature(request):
            add_builder_to_registry(
                state,
                request.pubkey,
                PAYLOAD_BUILDER_VERSION,
                ExecutionAddress(request.withdrawal_credentials[12:]),
                request.amount,
                state.slot,
            )
    else:
        builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
        builder = state.builders[builder_index]

        # If exited and swept, reset the withdrawable epoch
        if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
            epoch = get_current_epoch(state)
            builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY

        # Increase balance by deposit amount
        builder.balance += request.amount
