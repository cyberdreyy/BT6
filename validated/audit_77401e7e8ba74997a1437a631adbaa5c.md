### Title
JWT replay-cache check-then-record race allows single-use HTTP trigger token to authorize multiple workflow executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` decides whether a JWT (`jti`) has already been used by calling `isReplay` (a read-locked lookup) and only *afterwards* calls `recordUsage` (a separately write-locked insert) once the signature and authorized-key checks pass [1](#0-0) . This mirrors the reported bug class: a security check (`checkSkewMax`/here, `isReplay`) is evaluated against state that has not yet been updated by the corresponding state-mutating step (`updateGlobalPositionData`/here, `recordUsage`), and the two are not executed atomically, so concurrent requests can both pass the check before either updates the state.

### Finding Description
`isReplay` and `recordUsage` are two independent, separately-locked operations on the same map [2](#0-1) :
```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()
	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	cache.cache[jti] = time.Now()
}
```
In `Authorize`, the sequence is: verify JWT → check `isReplay` → look up authorized key → `recordUsage` [1](#0-0) . There is no lock held across the whole "check-then-mark-used" critical section, so two (or more) HTTP trigger requests carrying the exact same signed JWT (same `jti`) that arrive concurrently can both call `isReplay` before either has called `recordUsage`. Both will observe `exists == false`, both will pass the authorized-key check, and both will be treated as valid, distinct authorizations — even though the JWT is supposed to be single-use per the code's own comment ("JWT token has already been used") and error message.

This is called from the HTTP Trigger request path (`httpTriggerHandler.authorizeRequest` → `workflowMetadataHandler.Authorize`), which is reachable directly by an unpriviledged external caller submitting `HTTPTriggerRequest`/`MethodWorkflowExecute` messages to the gateway [3](#0-2) .

### Impact Explanation
The replay cache is the sole mechanism preventing a single signed authorization token from being used to trigger more than one workflow execution. A successful race bypasses that guarantee, letting an external, unprivileged caller execute a workflow multiple times from one authorization artifact — an unauthorized job/run bypass and a quota/anti-replay bypass on the internet-facing HTTP trigger gateway path, consistent with the "unauthorized job run" / "quota bypass" categories called out as in-scope impacts.

### Likelihood Explanation
Exploitation only requires an external caller to send the same signed JSON-RPC request (same body/signature/`jti`) twice in rapid succession (e.g., two parallel HTTP connections) to the gateway. No privileged access or node compromise is needed — this is a garden-variety TOCTOU race in Go map/lock usage that is trivially triggerable by any client capable of duplicating an HTTP POST.

### Recommendation
Make the check-and-mark operation atomic: hold a single write lock across both the existence check and the insertion (or use `sync.Map`/`LoadOrStore` semantics) so that only one of two concurrent callers with the same `jti` can succeed. For example, replace the two functions with a single `checkAndRecord(jti string) bool` that takes the write lock once, checks for prior existence, and — if absent — inserts and returns "not a replay" in the same critical section; return "replay" otherwise. Update `Authorize` to call this atomic method instead of separate `isReplay`/`recordUsage` calls.

### Proof of Concept
1. Register a workflow and obtain a validly signed JWT-authenticated `HTTPTriggerRequest` (as done in the existing rate-limit test harness) with a fixed `jti`.
2. Fire two (or more) concurrent goroutines/HTTP requests carrying the identical signed request/JWT to the gateway's HTTP trigger endpoint.
3. Observe that both requests can independently reach `Authorize`, both call `isReplay(jti)` before either calls `recordUsage(jti)` (raceable because there is no lock held across the two calls), and both are authorized and forwarded to workflow execution — instead of the second being rejected with "JWT token has already been used."

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
```

```go
func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
```
