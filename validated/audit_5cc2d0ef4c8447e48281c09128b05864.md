## Title
Malicious current-tenure miner can indefinitely suppress its own inactivity timeout by repeatedly resubmitting rejected reorg proposals, wedging the tenure — (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_latest_block_in_tenure` treats *any* rejected reorg-style block proposal as valid "miner activity" and refreshes `last_activity_time` for the proposing miner's own tenure, even though the proposal itself is invalid and never gets signed. Since the signer's only mechanism for invalidating an unresponsive/misbehaving current miner (`SortitionState::is_timed_out`) is driven purely by elapsed time since `last_activity_time`, a malicious current-sortition-winner miner can keep this clock perpetually fresh by repeatedly resending invalid/conflicting proposals faster than `block_proposal_timeout`, without ever producing a signable block. This blocks the state-machine transition that would let the prior miner take over via tenure extend, wedging the tenure — the same "reset-the-timer via a minimally qualifying action" pattern as the `AuctionLoanLiquidator.placeBid` DoS.

### Finding Description
`SortitionData::check_latest_block_in_tenure` decides whether a proposed block confirms enough of a tenure's tip. When the proposal is a reorg attempt (its chain length doesn't exceed the tenure's last signed/pre-committed block) and it arrives within `reorg_attempts_activity_timeout` of the last known good state, the code deliberately counts it as valid miner activity and calls `signer_db.update_last_activity_time(&block.header.consensus_hash, ...)` for the *proposing* miner's own tenure, before rejecting the proposal: [1](#0-0) 

That `last_activity_time` is exactly the input `SortitionState::is_timed_out` uses to decide if the current miner should be marked `InvalidatedBeforeFirstBlock` and superseded by the prior tenure's miner: [2](#0-1) 

This timeout check is exactly what gates the fallback transition in `check_proposal`: [3](#0-2) 

The equality being broken is the intended equivalence: *"miner produced no valid, signable activity for `block_proposal_timeout` ⇒ miner is invalidated and the prior tenure may extend."* Here, a stream of proposals that are always invalid (never crossing the pre-commit/sign threshold) still satisfies the activity check, so the equivalence never fires as long as the attacker resubmits inside the freshness window.

Compounding this, the one existing mitigation for exactly this reorg-attempt class of behavior — marking the miner invalid once ≥30% of rejection weight is `ReorgNotAllowed` — is explicitly skipped once the active signer protocol version uses global signer state, which is the current default path: [4](#0-3) 

So for global-state protocol versions there is no independent rejection-weight-based invalidation to fall back on; `is_timed_out`/`last_activity_time` is the sole liveness backstop, and it is exactly the value the attacker controls.

### Impact Explanation
This is a **High**-severity liveness wedge per the accepted impact categories: a single one-slot miner (the current sortition winner) can keep its own tenure perpetually "active" in signer bookkeeping without ever proposing a block that reaches pre-commit/signature, while simultaneously blocking the prior miner from being allowed to extend (since the prior miner can only take over once the current miner is marked `InvalidatedBeforeFirstBlock` via the timeout). No majority of signers, no other signer's key, and no StackerDB/transport flooding is required — only a modest, legitimate-looking cadence of resubmitted (individually invalid) block proposals from the malicious miner.

### Likelihood Explanation
The attacker need only be the current sortition winner (achievable by any miner who wins a single sortition) and resend a conflicting/reorg proposal at an interval shorter than `block_proposal_timeout` (default 120_000 ms) while staying inside `reorg_attempts_activity_timeout_ms` (default 200_000 ms) of the referenced tenure's last signed/accepted block: [5](#0-4) [6](#0-5) 

Since default `reorg_attempts_activity_timeout_ms` (200s) exceeds default `block_proposal_timeout_ms` (120s), a proposal cadence well within both windows is trivial to sustain, and this path is reachable purely through message crafting by the current miner — no majority collusion needed.

### Recommendation
- Do not let a rejected/invalid reorg proposal refresh `last_activity_time` unconditionally; require the proposal to at least reach `PreCommitted` (or some validated-progress state) before counting it as activity, mirroring the existing fix that stopped pre-commits alone from suppressing inactivity (`changelog.d/precommit-suppresses-miner-timeout.fixed`) — the same reasoning applies one level earlier to raw rejected proposals.
- Cap the number of times/duration a single tenure's `last_activity_time` can be refreshed purely by rejected reorg attempts, independent of `block_proposal_timeout`.
- Restore an equivalent of the ≥30% `ReorgNotAllowed` rejection-weight invalidation for global-state protocol versions instead of unconditionally skipping it.

### Proof of Concept
1. Miner M wins the current sortition and becomes `SortitionMinerStatus::Valid` for tenure T.
2. M crafts a tenure-change/reorg block proposal at height ≤ the known tip of the parent tenure (an intentionally-invalid reorg attempt) and broadcasts it.
3. Each signer runs `check_latest_block_in_tenure`; since the proposal doesn't exceed the parent tenure's tip, it is rejected, but because it is within `reorg_attempts_activity_timeout`, `update_last_activity_time(&T, now)` is called (`stacks-signer/src/chainstate/mod.rs:403-417`).
4. M repeats step 2 every < `block_proposal_timeout` seconds.
5. `SortitionState::is_timed_out(T, ...)` (`stacks-signer/src/chainstate/v1.rs:55-94`) never observes `elapsed > block_proposal_timeout`, so `check_proposal` never flips M's status to `InvalidatedBeforeFirstBlock` (`stacks-signer/src/chainstate/v1.rs:144-163`).
6. The prior miner is never permitted to extend its tenure, and M never produces a block that reaches pre-commit/signature — the tenure stalls indefinitely under M's control.

impl SortitionState {
    /// Check if the given sortition identified by its ConsensusHash has timed out based on current signed blocks
    /// and the time at which the burn block for it was first recorded in the provided signerdb
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }

# before the signer marks that miner as inactive.
#
# When a new sortition happens, the signer gives the winning miner this
# much time to propose a block. If no proposal arrives, the signer marks

# that must be satisfied before the signer will accept a tenure extend
# from the PREVIOUS miner (the other gate is `tenure_idle_timeout_secs`).
#
# WARNING: Interacts with miner's `tenure_extend_wait_timeout_ms` (default 120_000ms).
# The miner waits `tenure_extend_wait_timeout_ms` before attempting to extend.

# If miner's value < this value:
