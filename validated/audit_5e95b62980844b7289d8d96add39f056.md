### Title
Unauthenticated Pipeline Run Resume Endpoint Allows Unprivileged Actors to Inject Arbitrary Task Results - (File: core/web/router.go, core/web/pipeline_runs_controller.go)

### Summary
The `USSD` bug is a missing-access-control finding: privileged state-mutating functions (`mintRebalancer`/`burnRebalancer`) were callable by any address, letting an unprivileged caller corrupt protocol state (`totalSupply`) that downstream logic implicitly trusts. The equivalent unprivileged-actor pattern in this Chainlink node repo is the `PATCH /v2/resume/:runID` route, which is registered with **no authentication middleware at all** and allows any network caller who knows/guesses a run UUID to inject arbitrary result data into a suspended pipeline run.

### Finding Description
In `core/web/router.go`, the `v2Routes` function registers the resume endpoint on the *unauthenticated* group before any auth middleware is applied: [1](#0-0) 

```go
func v2Routes(app chainlink.Application, r *gin.RouterGroup) {
	unauthedv2 := r.Group("/v2")

	prc := PipelineRunsController{app}
	psec := PipelineJobSpecErrorsController{app}
	unauthedv2.PATCH("/resume/:runID", prc.Resume)
	...
```

All other mutating routes in the same file (jobs, keys, bridges, external initiators, transfers, etc.) are wrapped in `authv2` with `auth.Authenticate(...)` plus a role check (`RequiresEditRole`/`RequiresAdminRole`/`RequiresRunRole`), as seen throughout `router.go` (e.g. lines 265, 270, 394-396, 442-443). `unauthedv2.PATCH("/resume/:runID", ...)`, however, bypasses `auth.Authenticate` entirely — there is no session, API token, or external-initiator check.

The handler itself, `PipelineRunsController.Resume`, decodes an attacker-supplied JSON body into a `pipeline.ResumeRequest`, converts it to a `pipeline.Result`, and calls `prc.App.ResumeJobV2(ctx, taskID, result)`: [2](#0-1) 

The only "control" is that `taskID` must be a valid UUID matching a pending async task (typically corresponding to a bridge/external-adapter callback or webhook-triggered task awaiting resumption). The audit log entry name itself, `audit.UnauthedRunResumed`, explicitly acknowledges the request is unauthenticated.

This mirrors the USSD root cause: a state-mutating function (`mintRebalancer`/`burnRebalancer` there, `ResumeJobV2` here) that should require a specific caller/role (the external adapter that owns the pending task, analogous to `onlyBalancer`) instead accepts calls from any unprivileged actor, relying only on knowledge of an identifier (task/run UUID) rather than real authentication.

### Impact Explanation
- **Result/state injection**: An attacker who can enumerate or guess a pending run UUID can complete or corrupt any in-flight pipeline task with attacker-controlled data, poisoning the outputs of jobs (e.g., price feeds, VRF fulfillment pipelines, keeper/automation jobs) that depend on the external callback's result.
- **Denial of service**: An attacker can resume tasks with error results or malformed data before the legitimate external adapter responds, causing job pipelines to fail, stall, or produce incorrect on-chain transactions — directly analogous to the DoS/malfunction impact described for the USSD rebalancer (`totalSupply` corruption breaking `collateralFactor` and `rebalance()`).
- **Cross-consumer confusion**: Because there is no access-control binding the resumer to the original requester (bridge/EA) of that specific task, any external caller can interfere with another user's/job's pending run.

### Likelihood Explanation
Run/task UUIDs are v4 UUIDs (128-bit), so blind guessing is impractical; however, likelihood increases materially if:
- UUIDs leak via logs, error responses, webhooks sent to third-party adapters, or client-side exposure (operators often pass the run/task ID to external bridge adapters as part of the callback URL, meaning any party controlling network traffic to/from that adapter, or any bridge operator, effectively already has legitimate knowledge of the ID).
- Since the endpoint is fully internet-facing (unauthenticated group, no rate limiting shown here beyond default gin routing), any party who *does* obtain a runID (e.g., a compromised or malicious bridge/adapter, or a MITM on the adapter callback) can trigger this without any credential check — unlike every other mutating endpoint in the router which requires session/token + role.
- This is a known, intentional design (bridges must call back without holding a full session), but it results in an endpoint with **zero access control** enforcing only "possession of a UUID," which is exactly the same weak-guarantee pattern flagged as the root cause in the referenced report.

### Recommendation
- Bind resume authorization to the specific external initiator/bridge that owns the pending task (e.g., validate an `OutgoingToken`/`OutgoingSecret` shared secret established at bridge/EA creation, similar to `ExternalInitiator.OutgoingSecret` already present in `core/bridges/external_initiator.go`) rather than trusting UUID possession alone.
- Add rate limiting specifically to `/v2/resume/:runID` to reduce brute-force/guessing risk.
- Ensure task/run UUIDs are never leaked in logs, client-facing APIs, or error messages, and rotate/short-lived binding tokens per pending task where feasible.

### Proof of Concept
1. Identify or intercept a pending task's `runID` (UUID) — e.g., from a bridge/external-adapter callback URL, application logs, or a compromised adapter.
2. Send, without any authentication headers/session/API token:
```
PATCH /v2/resume/<runID> HTTP/1.1
Content-Type: application/json

{"error": null, "value": "<attacker-controlled-result>"}
```
3. The request hits `unauthedv2.PATCH("/resume/:runID", prc.Resume)` [1](#0-0)  with no `auth.Authenticate` check, and `PipelineRunsController.Resume` [3](#0-2)  directly calls `prc.App.ResumeJobV2(ctx, taskID, result)`, completing the pending task with attacker-supplied data and returning HTTP 200.

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
```
