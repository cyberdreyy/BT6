### Title
Unclamped ERC4626 vault valuation in `ProgrammableBorrower.totalInterestDueNow`/`onStopEpoch` lets a vault depositor permanently freeze epoch settlement - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The kernel bug scales an externally-supplied sync-packet size by a local stride and stores it without clamping it against `ep->maxframesize`, so an oversized value propagates into the playback queue and breaks the endpoint's frame limit. The analog in idle-tranches is `ProgrammableBorrower._vaultNetInterest()` / `onStopEpoch()`: the contract computes epoch PnL and withdrawal capacity directly from the external ERC4626 vault's `convertToAssets()` with no clamp against real assets or expected obligations. A user of that vault can donate underlying to the vault to inflate `convertToAssets`, producing an oversized "earned assets" figure that propagates into `stopEpoch`, where the subsequent `vault.withdraw(shortfall)` cannot be honored and reverts, permanently blocking epoch settlement.

### Finding Description
In `ProgrammableBorrower`, `_vaultNetInterest()` computes `earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault` where `_currentVaultAssets()` is `vault.convertToAssets(vault.balanceOf(this))` — an externally-controlled valuation with no upper bound (contracts/strategies/idle/ProgrammableBorrower.sol:337-349, 546-549).

`totalInterestDueNow()` feeds this unclamped value into the epoch interest read by `IdleCDOEpochVariant.stopEpoch` (ProgrammableBorrower.sol:330-334). Then `onStopEpoch()` uses the same inflated figure: when the on-hand balance is below `_amountRequired`, it checks `shortfall > _currentVaultAssets()` to decide whether the vault can cover the deficit (ProgrammableBorrower.sol:240-245). If `convertToAssets` is inflated, that check passes even though the vault cannot actually pay out the shortfall, so the code proceeds to `vault.withdraw(shortfall, ...)`, which reverts inside the `try`, and the `catch` reverts with `StopEpochVaultLiquidityUnavailable()` (ProgrammableBorrower.sol:246-253).

This mirrors the kernel bug exactly: an externally-derived size (`convertToAssets` / sync packet size) is consumed as an authoritative capacity/interest figure without being clamped to the real maximum (actual vault-held assets / `ep->maxframesize`), and the oversized value then drives an operation (`vault.withdraw` / queue packet transfer) that exceeds the real limit.

### Impact Explanation
An attacker who is an ordinary depositor in the borrower facility's ERC4626 vault (an allowed attacker class) donates underlying directly to the vault to inflate its share price. During the running epoch, `stopEpoch` then requires more than the vault can deliver. Because the inflated `convertToAssets` defeats the `shortfall > _currentVaultAssets()` coverage check, the code never falls through to IdleCDO's default path and instead reverts `StopEpochVaultLiquidityUnavailable()` on every attempt. The donation is persistent, so `stopEpoch` is permanently uncallable: the epoch cannot be stopped, settled, or defaulted, and all lender NAV (quantified as the full pool TVL locked in the facility) is frozen in the running epoch. This is a permanent freezing of funds, not a gas/DoS-only issue — withdrawals via `requestWithdraw`/`claimWithdrawRequest` depend on epoch settlement.

### Likelihood Explanation
Requires a programmable-borrower deployment whose configured vault uses a standard (non-virtualized) ERC4626 that does not isolate donations from `convertToAssets` — the common case. The attacker needs only enough capital to push `convertToAssets` above the real redeemable amount plus the stop-time shortfall, and KYC/whitelist checks do not apply to the external vault's other users. No privileged role is needed; the honest borrower and manager cannot prevent it since the inflation is external. The one caveat I could not fully verify within the index: whether `IdleCDOEpochVariant.stopEpoch` treats a `StopEpochVaultLiquidityUnavailable` revert as retryable-but-blocking vs. recoverable via `_emergencyShutdown`/`restoreOperations`; if emergency shutdown bypasses `onStopEpoch`, the impact degrades to temporary freezing until owner intervention. `_emergencyShutdown` is owner-gated, so the freeze is still real for all unprivileged users.

### Recommendation
Clamp the externally-derived value at its real bound, as the kernel fix does with `ep->maxframesize`:
- In `onStopEpoch`, cap the withdrawal amount at what the vault can actually deliver, e.g., `uint256 realAvailable = vault.maxWithdraw(address(this));` and use `shortfall > realAvailable` (not `convertToAssets`) for the coverage check; withdraw `min(shortfall, realAvailable)` and let IdleCDO's `transferFrom` failure drive the default path when real liquidity is short.
- In `_vaultNetInterest`/`totalInterestDueNow`, cap `earnedAssets`/`_currentVaultAssets()` at real redeemable value (`vault.maxWithdraw`) or at `principalAssets + borrowerInterestAccruedNow()` so donated vault inflation cannot inflate the pool-facing interest figure.

### Proof of Concept
Foundry fork PoC sketch (modeled on `test/foundry/ProgrammableBorrowerEpochInvariant.t.sol` setup):

```solidity
// contracts: IdleCDOEpochVariant cdoEpoch, ProgrammableBorrower pb,
// ERC4626 vault (donation-inflatable), underlying USDC
address attackerVaultUser = makeAddr("vaultUser");

// 1. Lenders deposit; manager starts an epoch; borrower draws funds.
idleCDO.depositAA(100_000e6);
vm.prank(manager); cdoEpoch.startEpoch();
vm.prank(borrower);  pb.borrow(50_000e6);

// 2. Attacker inflates vault.convertToAssets via direct donation.
deal(usdc, attackerVaultUser, 10_000e6);
vm.prank(attackerVaultUser); IERC20(usdc).transfer(address(vault), 10_000e6);
// For a donation-susceptible vault, convertToAssets(pbShares) now reports
// earnedAssets > real redeemable liquidity, inflating totalInterestDueNow().

// 3. Warp past epoch end; honest manager tries to stop the epoch.
//    Borrower repays its contractual debt but cannot cover the fake PnL.
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
// onStopEpoch: shortfall <= inflated _currentVaultAssets() passes the guard,
// vault.withdraw(shortfall) reverts (insufficient real assets), caught ->
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0);

// 4. Repeat after additional time: still reverts -> epoch settlement,
//    defaults, and all withdraw claims are permanently blocked;
//    lender NAV (~100_000e6) is frozen.
vm.warp(block.timestamp + 30 days);
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0);
```

If the configured ERC4626 vault is donation-resistant (virtual shares/assets offset), the same primitive may still be reachable via a vault user moving the share price through deposits/withdrawals around `stopEpoch`, though with reduced reliability.
