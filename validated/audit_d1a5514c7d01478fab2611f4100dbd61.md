## Finding confirmed

Comparing `multisig-factory/src/lib.rs::create` against its sibling factories (`lockup-factory/src/lib.rs::create` and `staking-pool-factory`) is decisive: both `lockup-factory::create` and the staking-pool-factory equivalent chain a `.then(ext_self::on_..._create(...))` callback that calls `is_promise_success()` and, on failure, explicitly does `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` to refund the caller. `multisig-factory::create` has no such callback at all. ### Title
Unrefunded deposit on failed multisig creation onto a pre-existing named account - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` builds a single batched promise (`create_account`, `deploy_contract`, `transfer`, `function_call`) with no `.then()` callback, unlike `LockupFactory::create` and the staking-pool-factory's `create_staking_pool`, which both attach a callback (`on_lockup_create` / `on_staking_pool_create`) that checks `is_promise_success()` and refunds the attached deposit back to the original caller if the batch fails. Because `multisig-factory` lacks this callback, any deposit attached to a `create` call whose batch fails (e.g. because `name.multisig-factory` already exists) is never returned to the caller.

### Finding Description
The intended binding is: `balance(caller) - attached_deposit == balance(new_multisig_account)` on success, OR `balance(caller)` is restored (refund) when the batched receipt fails. `MultisigFactory::create` at `multisig-factory/src/lib.rs:29-49` schedules `Promise::new(account_id).create_account().deploy_contract(CODE).transfer(env::attached_deposit()).function_call("new", ...)` as one outgoing action receipt and returns it directly with no `.then()` callback to itself.

An attacker who front-runs a legitimate `create(name, ...)` call by calling `create(name, attacker_members, attacker_num_confirmations)` themselves (one block earlier) will successfully create and fund `name.<factory>` under their own chosen members/confirmations. When the legitimate transaction executes afterward, the receiver account already exists, so the batched `CreateAccount` action fails and the whole action receipt fails; none of `deploy_contract`/`transfer`/`function_call` for the victim's request are applied to the target account. Since there is no callback (unlike `lockup-factory::on_lockup_create` at `lockup-factory/src/lib.rs:171-198`, which explicitly `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` on failure), the victim's attached deposit is not returned to them — the NEAR protocol's failed-receipt refund returns the balance to the predecessor of the failed receipt (the `multisig-factory` contract account itself), which has no state and no function to move that balance back out. The result: the victim's deposit is stranded inside the factory account, the desired multisig at `name.<factory>` is instead controlled by the attacker's chosen members, and the victim believes their multisig was created (or their funds returned) when neither happened.

### Impact Explanation
The legitimate creator's attached NEAR deposit is silently stranded inside the `multisig-factory` contract balance rather than being delivered to the new multisig or refunded to them, and the desired account name ends up controlled by parameters (`members`, `num_confirmations`) the rightful creator never chose. This is an accounting divergence — the caller's wallet/dApp will believe the deposit created their multisig, while in reality it sits unrecoverable in the factory account. This is repeatable for any name the attacker chooses to target, at the cost of one deposit for the attacker's own (successful) `create` call.

### Likelihood Explanation
The precondition is simply visibility of a pending `create` transaction for a desired `name` (public mempool) and the ability to send a competing transaction that lands first — no special privilege is required, matching the "unprivileged attacker" model. The attacker's only cost is their own gas/deposit to create the account first (which they keep control of).

### Recommendation
Add a `.then()` callback to `MultisigFactory::create` (mirroring `LockupFactory::on_lockup_create`) that checks `is_promise_success()` and refunds `env::attached_deposit()` back to `env::predecessor_account_id()` if the batched creation failed.

### Proof of Concept
A `near-sdk-sim` / `near-workspaces` test that: (1) has account A call `create("target", attacker_members, k)` and succeeds; (2) has account B call `create("target", victim_members, k)` with an attached deposit and asserts the returned promise/receipt fails since `target.factory` already exists; (3) asserts B's account balance is NOT restored to pre-call value (no refund occurs) — demonstrating the deposit lands in `factory`'s own balance instead of `target.factory` or being returned to B, in contrast to an equivalent `lockup-factory` test (`test_create_lockup_rollback` in `lockup-factory/src/lib.rs:353-388`) which explicitly verifies the refund-to-predecessor path exists there.

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
