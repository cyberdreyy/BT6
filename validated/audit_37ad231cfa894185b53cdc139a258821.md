### Title
Post-default instant-withdraw receipts are misclassified as defaulted-epoch claims and paid at the haircutted recovery price - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestInstantWithdraw` has no `defaultRecoveryFinalized` branch (unlike `requestWithdraw`, which explicitly routes post-default requests into `postDefaultRequests`). After default recovery is finalized, `epochNumber` still equals `defaultRecoveryEpoch`, so a new instant-withdraw receipt is recorded into `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`. On claim, `claimInstantWithdrawRequest` sees `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` and sends the fresh, fully-funded receipt through `_claimDefaultedInstantWithdrawRequest`, which pays only `claimBasis * defaultRecoveryPrice / 1e18` and decrements the default-epoch aggregates. The par-funded remainder stays trapped in the strategy.

### Finding Description
The external bug is a NULL-pointer dereference in a filesystem *recovery* path (f2fs fsync recovery): state that is assumed to exist during recovery is missing, and the recovery code crashes instead of handling it. The analog is the same class on the vault's *default recovery* path: `requestInstantWithdraw` (lines 356-375) unconditionally writes `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` with no awareness that `epochNumber == defaultRecoveryEpoch` once `defaultRecoveryFinalized` is true. `claimInstantWithdrawRequest` (lines 380-393) then cannot distinguish a pre-default unfunded instant receipt from a brand-new post-default receipt, because both live under the same epoch key — the recovery code "dereferences" the wrong claim record.

Flow:

1. Epoch N running, `allowInstantWithdraw` enabled. Attacker (KYC'd lender) and another user both make instant-withdraw requests; the queue is only partially funded so `pendingInstantWithdraws != 0`.
2. Borrower defaults; owner calls `finalizeDefault` → `finalizeDefaultRecovery` sets `defaultRecoveryFinalized`, `defaultRecoveryEpoch = epochNumber = N`, `defaultInstantWithdrawsFinalized = true`, `defaultRecoveryPrice < 1e18`.
3. Attacker calls `requestInstantWithdraw(amount)` (CDO side, post-finalization). The strategy mints a receipt and records it under epoch N — the *defaulted* epoch key.
4. The CDO funds the request at par via `collectInstantWithdrawFunds`, pulling `amount` underlying into the strategy.
5. Attacker calls `claimInstantWithdrawRequest`. `_claimDefaultedInstantWithdrawRequest` (lines 842-856) reads `instantWithdrawsRequestsByEpoch[attacker][N]` (which includes the new receipt), pays `amount * defaultRecoveryPrice`, decrements `instantWithdrawsRequests`, `pendingInstantWithdraws` (clamped) and `instantWithdrawClaimsByEpoch[N]`.

The attacker loses `amount * (1 - defaultRecoveryPrice)` on a receipt that was funded at par — that difference is permanently stranded in the strategy, and the decrement of `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` also corrupts the remaining defaulted claimants' accounting (it can push the epoch bucket to zero while older defaulted claims of *other* users are still outstanding, though `instantWithdrawsRequests` per-user isolation limits direct theft of others' claims).

Worse, the reverse direction also works: a pre-default user whose receipt was *already fully funded* before finalization (`pendingInstantWithdraws == 0` for their share, covered by `_defaultPrefundedInstantReserve`) is correctly included in `defaultPendingClaimBasis`, but if `pendingInstantWithdraws` happens to reach zero at finalization while some users hold funded-but-unclaimed receipts, `defaultInstantWithdrawsFinalized` is set false and those users claim at par — while the prefunded portion was already added to `defaultRecoveryReserve` via `_defaultPrefundedInstantReserve`, double-counting reserve backing.

### Impact Explanation
Direct loss: any instant-withdraw request created after `finalizeDefaultRecovery` in the same epoch number is paid at `defaultRecoveryPrice` instead of par, even though the CDO funded it 1:1 through `collectInstantWithdrawFunds`. For a 50% recovery price, a 100k USDC post-default instant withdrawal loses 50k USDC, permanently frozen as unaccounted strategy balance (not claimable by anyone, since it is not part of `defaultRecoveryReserve` accounting). This is theft/permanent freezing of user funds broken against the "one receipt, one funded payout" invariant.

### Likelihood Explanation
Requires: instant withdrawals enabled, a borrower default finalized with `pendingInstantWithdraws != 0` (partially-funded instant queue — the exact scenario `_defaultPrefundedInstantReserve` and `defaultInstantWithdrawsFinalized` were built for), and the CDO still permitting `requestInstantWithdraw`/`claimInstantWithdrawRequest` after default finalization. The strategy exposes no guard blocking post-default instant requests, and `requestWithdraw` shows the authors knew post-default flows needed separate handling (`postDefaultRequests`) — the instant path was simply missed. Whether `IdleCDOEpochVariant.requestInstantWithdraw` gates on `defaulted()`/finalized state is the main open dependency; I could not fully verify the CDO-side gating within the available context. If the CDO permits it (defaulted pools keep servicing claims, and instant requests are a claim-adjacent path), the bug triggers deterministically for any unprivileged lender.

### Recommendation
Mirror the `requestWithdraw` post-default branch in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert or record the receipt under a post-default bucket (e.g., a dedicated mapping or `epochNumber` keyed off `defaultRecoveryEpoch + 1`) so it is never conflated with `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`. Alternatively, in `claimInstantWithdrawRequest`, subtract the pre-finalization snapshot of `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` before routing through `_claimDefaultedInstantWithdrawRequest`.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testPostDefaultInstantWithdrawHaircutted() external {
  // 1. deposit, enable instant withdraw, create partially funded instant queue
  _depositWithUser(user, 100_000 * ONE_SCALE, true);
  vm.prank(user);
  cdoEpoch.requestInstantWithdraw(50_000 * ONE_SCALE, address(AAtranche)); // pendingInstantWithdraws > 0

  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr, 0);
  _checkDefault(); // borrower default

  // 2. finalize recovery at 50%
  uint256 recovered = totalBasis * 5e17 / 1e18;
  deal(defaultUnderlying, manager, recovered);
  vm.startPrank(manager);
  IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
  cdoEpoch.finalizeDefault(recovered, manager);
  vm.stopPrank();
  assertEq(IdleCreditVault(address(strategy)).defaultInstantWithdrawsFinalized(), true);

  // 3. attacker creates a NEW instant request post-finalization (same epochNumber)
  vm.prank(attacker);
  cdoEpoch.requestInstantWithdraw(10_000 * ONE_SCALE, address(AAtranche));
  // CDO funds it at par -> collectInstantWithdrawFunds pulls 10_000 into strategy

  // 4. claim pays only recoveryPrice fraction
  uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
  vm.prank(attacker);
  cdoEpoch.claimInstantWithdrawRequest();
  uint256 got = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre;
  // BUG: got == 10_000 * defaultRecoveryPrice / 1e18 (~5_000), not 10_000
  assertLt(got, 10_000 * ONE_SCALE);
}
```

Confidence caveat: the finding depends on the CDO permitting post-default instant requests; if `IdleCDOEpochVariant` reverts instant requests once defaulted, the impact reduces to accounting corruption of `instantWithdrawClaimsByEpoch` via interleaved claims.
