### Title

Unprivileged ERC4626 liquidity drain can indefinitely block epoch settlement and freeze tranche withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary

A programmable-borrower credit vault parks undeployed pool principal in a public ERC4626 vault and recalls it inside `ProgrammableBorrower.onStopEpoch`. An unprivileged user of that external vault can withdraw or borrow away its available liquidity before `IdleCDOEpochVariant.stopEpoch` is executed. The programmable borrower’s shares still cover the requested amount, but the ERC4626 `withdraw` call reverts for lack of liquidity, causing `onStopEpoch` to revert with `StopEpochVaultLiquidityUnavailable` and preventing the epoch from stopping. [1](#0-0) [2](#0-1) 

### Finding Description

The strongest analog to the external “pre-created pair prevents settlement” bug is the programmable-borrower vault-liquidity dependency. `stopEpoch` calls `onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)` before collecting funds. [2](#0-1) 

When the programmable borrower lacks sufficient on-hand underlying, it compares the shortfall to `_currentVaultAssets()` and calls `vault.withdraw(shortfall, address(this), address(this))`. If the shares economically cover the shortfall, the code proceeds; if the vault reports sufficient assets but cannot currently return them, the revert is rethrown as `StopEpochVaultLiquidityUnavailable`. [3](#0-2) 

The CDO does not catch this hook failure, so the entire privileged `stopEpoch` transaction reverts. The prior state remains `isEpochRunning == true`, deposits remain paused from `startEpoch`, and both normal withdrawal-request flags remain disabled. [4](#0-3) [5](#0-4) 

Unlike an insolvency shortfall, this is only a liquidity condition: the attacker does not need to make the programmable borrower’s shares worthless. A public MetaMorpho or similar ERC4626 vault participant can remove available underlying through ordinary redemptions or by borrowing from markets backing the vault, while the programmable borrower’s `convertToAssets` value remains sufficient. [6](#0-5) 

### Impact Explanation

All active tranche principal and queued withdrawals remain locked while the epoch cannot be stopped. Because deposits were paused and withdrawal requests were disabled at epoch start, users cannot enter the ordinary withdrawal flow while the external vault remains illiquid. [4](#0-3) 

The freeze is temporary rather than permanent: if vault liquidity is replenished, the same manager transaction can be retried successfully. Nevertheless, an attacker with sufficient market capacity can repeatedly drain available liquidity around each settlement attempt, extending the freeze. For a vault with `N` underlying deposited, the amount affected is the full epoch NAV plus pending withdrawals, while the attacker’s cost is the collateral, fees, and interest needed to keep the ERC4626 vault illiquid. [7](#0-6) [3](#0-2) 

### Likelihood Explanation

Likelihood depends on the selected ERC4626 vault’s liquidity profile. The programmable-borrower integration is designed for an external vault, and the code explicitly distinguishes economically covered positions from withdrawable liquidity. [8](#0-7) 

Any independent vault shareholder or borrower can create this condition without compromising the honest owner, manager, guardian, configured borrower, or queue. The attacker does not need to be KYC-approved by the credit vault because the action occurs entirely through the external ERC4626 vault or its underlying markets. [9](#0-8) 

Existing guards do not prevent the condition: `_checkOnlyIdleCDO` protects the hook itself, `nonReentrant` protects execution, and the `shortfall > _currentVaultAssets()` check correctly detects insolvency rather than illiquidity. They do not ensure that an economically covered ERC4626 position can actually be withdrawn at settlement time. [1](#0-0) [10](#0-9) 

### Recommendation

Treat ERC4626 illiquidity as an expected settlement outcome rather than a hard revert. `onStopEpoch` should return a distinct failure result when a covered withdrawal fails, allowing `IdleCDOEpochVariant` to enter a bounded liquidity-recovery path or mark the specific amount pending instead of reverting the entire state transition. [2](#0-1) 

Prefer `redeem` over `withdraw` when available so the programmable borrower can redeem its own shares without depending on a precise asset-denominated liquidity calculation. The system should also restrict integrated vaults to sufficiently liquid markets, monitor free liquidity before `epochEndDate`, and expose a permissionless liquidation/claim path if settlement remains blocked for longer than a configured grace period. [3](#0-2) 

### Proof of Concept

A Foundry fork PoC can reproduce the condition against the programmable-borrower deployment pattern using a public MetaMorpho vault:

```solidity
// test/foundry/ProgrammableBorrowerLiquidityDos.t.sol
function testExternalVaultLiquidityDrainBlocksStopEpoch() external {
    uint256 depositAmount = 10_000 * oneScale;

    // Honest KYC-passed lender deposits and the honest manager starts an epoch.
    idleCDO.depositAA(depositAmount);
    _startEpochAndCheckPrices(0);

    // The configured borrower need not act maliciously.
    // Leave most funds parked in the external ERC4626 vault.

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Unprivileged attacker removes the ERC4626 vault's currently withdrawable
    // liquidity through the vault's ordinary public mechanisms:
    // - redeem attacker-controlled vault shares; and/or
    // - borrow remaining idle assets from the Morpho markets in the vault's
    //   withdrawal queue, supplying valid collateral.
    //
    // The programmable borrower still owns economically valuable shares:
    uint256 required = strategy.pendingWithdraws();
    uint256 shares = morphoVault.balanceOf(address(programmableBorrower));
    uint256 covered = morphoVault.convertToAssets(shares);
    assertGe(covered, required);

    // But ERC4626 withdraw cannot source the cash and reverts.
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Settlement was reverted, not converted into a default.
    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    assertFalse(cdoEpoch.allowAAWithdrawRequest());
    assertFalse(cdoEpoch.allowBBWithdrawRequest());
    assertTrue(cdoEpoch.paused());
}
```

The critical assertion is that `convertToAssets` reports enough backing while the public ERC4626 cannot satisfy the withdrawal. That distinction is exactly what `ProgrammableBorrower.onStopEpoch` checks before reverting the settlement transaction. [3](#0-2)

    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // if we want to close the pool and the borrower still owes any amount, consider it a failure and let IdleCDO handle it as a default instead of a close. 
    if (_isRequestingAllFunds && (borrowerPrincipal != 0 || borrowerInterestDebt != 0 || borrowerInterestAccrued != 0)) {
      return false;
    }

    uint256 onHand = underlyingToken.balanceOf(address(this));
    if (_amountRequired > onHand) {
      uint256 shortfall = _amountRequired - onHand;
      // If the vault shares do not economically cover the shortfall, let IdleCDO's later
      // transferFrom fail and use the existing default path. Only an otherwise-covered ERC4626

          epochWithdrawnFromVault += shortfall;
        }
        emit WithdrawnFromVault(shortfall, shares, address(this));
      } catch {
        revert StopEpochVaultLiquidityUnavailable();

  /// @param _newApr New apr to set for the next epoch
  /// @param _interest Interest gained in the epoch
  /// @param _lossAmount Loss amount to split between active LPs and pending receipts
  function _stopEpoch(uint256 _newApr, uint256 _interest, uint256 _lossAmount) private {
    _checkOnlyOwnerOrManager();
    bool _isRequestingAllFunds = _interest == 1;
    _checkProgrammableBorrowerMode();

    IdleCreditVault _strategy = IdleCreditVault(strategy);
    uint256 _pendingWithdrawFees = pendingWithdrawFees;

    _checkNotAllowed(
      // Check that epoch is running
      !isEpochRunning || 
      // Check that end date is passed
      block.timestamp < epochEndDate || 
      // Check that there are no pending instant withdraws, ie `getInstantWithdrawFunds` was called
      // before closing the epoch
      _pendingInstant() != 0 ||
      // Check that overridden interest, if passed (ie > 1), is greater than pending withdraw fees and the apr is 0 
      // otherwise withdrawal requests may not be fullfilled as they consider also the interest gained in the next epoch 
      (_interest > 1 && (_interest < _pendingWithdrawFees || _newApr != 0)) ||
      // Closing already recalls all principal, so applying a separate loss burn would strand returned cash.
      (_isRequestingAllFunds && _lossAmount != 0)
    );
