### Title
Unfunded instant-withdraw receipts are paid at par from shared vault reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` mirrors the double-free pattern of CVE-2019-20892: a receipt that was never funded is "released" (burned and zeroed) and paid out anyway. The claim path burns the user's full `instantWithdrawsRequests[_user]` balance and calls `_transferFundedClaim`, but it never checks `pendingInstantWithdraws` or whether `collectInstantWithdrawFunds` actually pulled the corresponding underlyings from the IdleCDO. An unprivileged lender who requests an instant withdraw during the running epoch — i.e., after the current epoch's funding point — can immediately claim and be paid out of underlying held by the vault that belongs to other users' funded withdraw claims or unforwarded deposits.

### Finding Description
- `requestInstantWithdraw` (IdleCreditVault.sol:356-375) mints receipt tokens to the user, increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, and `pendingInstantWithdraws`. The only place `pendingInstantWithdraws` is decremented is `collectInstantWithdrawFunds` (lines 398-403), which the CDO calls when it actually pulls funds — i.e., at epoch start when the borrower wires liquidity (`getInstantWithdrawFunds` flow).
- `claimInstantWithdrawRequest` (lines 380-393) performs no funding check. Unless `defaultRecoveryFinalized`, it takes `amount = instantWithdrawsRequests[_user]`, burns the receipt tokens, zeroes the ledger, and unconditionally calls `_transferFundedClaim(_user, amount)`, which transfers `underlyingToken` held by the vault.
- The vault's underlying balance is commingled: it holds funded normal-withdraw reserves collected via `collectWithdrawFunds`, funded instant-withdraw reserves, and deposited funds not yet forwarded via `sendInterestAndDeposits`. A claim against an unfunded instant receipt is paid from this pool — the same "free" operation releasing a resource that belongs to another allocation.
- The CDO-side gate is only `allowInstantWithdraw` (IdleCDOEpochVariant.sol:975-979); there is no epoch-phase or `pendingInstantWithdraws` check. The epoch queue itself relies on instant claims being processable "during the epoch" (IdleCDOEpochQueue.sol:331-351), so no outer guard compensates.

Broken invariant: one receipt, one funded payout. The receipt is cleared and paid while its backing (`pendingInstantWithdraws` share) was never collected.

### Impact Explanation
Direct theft / insolvency. The attacker receives underlying equal to the full requested amount even though zero underlyings were collected for that request. The payout drains the vault's reserve intended for other users' funded withdraw requests and instant claims; those users' later claims revert on insufficient balance (permanent freezing/theft of unclaimed funded withdrawals). Loss is bounded by the attacker's deposited principal but is fully extractable: deposit X, request instant withdraw of X mid-epoch, claim X out of reserves, leaving a `pendingInstantWithdraws` hole the next `collectInstantWithdrawFunds` will still try to fund — effectively double-counting the same debt.

### Likelihood Explanation
- Attacker requirements: a KYC-passing lender (unprivileged), `allowInstantWithdraw` enabled on the CDO, and the vault holding any positive underlying balance (funded reserves from a previous `stopEpoch`/`collectWithdrawFunds`, or unforwarded deposits).
- Sequence: during a running epoch, call `requestWithdraw` which routes to the instant bucket when instant withdraws are allowed mid-epoch; call `claimInstantWithdrawRequest` in the same transaction or before the next `startEpoch` funding. No privileged role is involved; the honest manager/borrower actions are not needed.
- Precondition is common: any epoch in which funded normal-withdraw reserves sit in the vault (i.e., after at least one stopEpoch with matured receipts) provides the payout liquidity.
- Residual uncertainty: whether `IdleCDOEpochVariant.requestWithdraw` routes to `requestInstantWithdraw` during the running phase in all configurations, and the exact gating of `getInstantWithdrawFunds` timing, could not be fully confirmed within the available context (line-level grep of the CDO returned only match counts). If instant requests are only creatable strictly before `startEpoch` funding, the attack surface narrows to the partial-funding case (borrower funds less than `pendingInstantWithdraws`), which still permits the same unfunded-claim drain pro rata.

### Recommendation
- In `claimInstantWithdrawRequest`, only pay the funded portion: track funded instant receipts per epoch (e.g., decrement `instantWithdrawsRequests`/per-epoch entries only when `collectInstantWithdrawFunds` marks them funded, or maintain `fundedInstantWithdraws` and cap `amount` at `instantWithdrawsRequests[_user] - unfunded share`).
- Alternatively, gate the CDO claim on `pendingInstantWithdraws` having been collected, or revert while `instantWithdrawsRequests[_user]` exceeds the funded reserve attributable to that user.
- Add an invariant test: `sum(instantWithdrawsRequests)` must never exceed underlying collected via `collectInstantWithdrawFunds` minus already-claimed funded amounts.

### Proof of Concept
Reproducible Foundry fork/unit PoC sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Precondition: allowInstantWithdraw == true; vault holds funded reserves
// from a prior stopEpoch (e.g., user0's matured normal withdraw claim of R).

// 1) Epoch running. Attacker (KYC'd lender) holds AA tranches worth X.
vm.prank(attacker);
cdoEpoch.requestWithdraw(xShares, address(AAtranche)); // routes to requestInstantWithdraw mid-epoch

// Vault state: instantWithdrawsRequests[attacker] = X, pendingInstantWithdraws = X,
// but collectInstantWithdrawFunds has NOT been called (borrower funds only at next startEpoch).

// 2) Attacker claims immediately, same phase.
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest(); // IdleCreditVault.claimInstantWithdrawRequest pays par

assertEq(underlying.balanceOf(attacker) - balPre, X); // paid from reserves
// 3) user0's funded claim of R now reverts or underpays: vault balance short by X.
vm.prank(user0);
vm.expectRevert(); // ERC20 transfer amount exceeds balance
cdoEpoch.claimWithdrawRequest();
```

Expected outcome: attacker receives `X` underlying with no borrower funding; `pendingInstantWithdraws` still shows `X` owed, so the next `collectInstantWithdrawFunds` double-counts the debt while legitimate claimants are frozen.
