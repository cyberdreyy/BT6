### Title
Dust-sized APR0 withdraw request permanently bricks `stopEpoch` if APR is later raised - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
A KYC-passing lender can deposit a dust amount, request a withdraw while the epoch APR is 0, and thereby set `apr0TotalPrincipal` to a tiny non-zero value. If the manager subsequently configures a non-zero APR for a later epoch, `prepareStopEpochWithApr0` unconditionally reverts with `NotAllowed` before the APR0 bucket is cleared, so every `stopEpoch` call fails and the pool is frozen until the manager manually restores a 0 APR. The bug mirrors CVE-2020-8618: a small attacker-supplied input reaches a hard assertion/revert that denies service to everyone.

### Finding Description
- `requestWithdraw` routes to `_requestWithdrawApr0` whenever `unscaledApr == 0` and the pool is not closed, and adds the user's principal to the global `apr0TotalPrincipal` bucket (contracts/strategies/idle/IdleCreditVault.sol:285-294). There is no minimum amount; a 1-wei request suffices.
- At epoch stop, `prepareStopEpochWithApr0` (contracts/strategies/idle/IdleCreditVault.sol:490-508) is called by `IdleCDOEpochVariant.stopEpoch`. It takes the fast path only when `apr0TotalPrincipal == 0`; otherwise it enforces `unscaledApr == 0` and reverts `NotAllowed` if APR was raised.
- The revert happens *before* `apr0TotalPrincipal = 0` at line 540, so the dust bucket is never cleared by a failed stop. Once APR > 0, every subsequent `stopEpoch` reverts identically.
- The attacker pays essentially nothing: the request is dust, the receipt tokens are minted to the attacker, and they can even later claim a loss-adjusted/funded withdrawal normally.

### Impact Explanation
While `stopEpoch` reverts, the epoch cannot end: `epochNumber` never advances, so `_claimFundedWithdrawRequest` keeps reverting via `epochNumber <= lastWithdrawRequest[_user]` (contracts/strategies/idle/IdleCreditVault.sol:326-328), and all deposited principal plus all queued withdraw claims remain locked in `IdleCDOEpochVariant`/`IdleCreditVault`. Recovery requires the owner/manager to diagnose the condition and set `unscaledApr` back to 0 — a manual privileged intervention the protocol's own `setAprsWithBuffer` flow can inadvertently break again if APR is re-raised while new APR0 dust exists. This is a temporary freezing of all vault funds caused by a near-zero-cost unprivileged action.

### Likelihood Explanation
Low-to-moderate. The attack requires (a) the vault operating with `unscaledApr == 0` (the APR0 mode explicitly supported), (b) the attacker passing KYC/`isWalletAllowed`, and (c) the manager later setting a non-zero APR — a routine operational change (`setAprs`/`setAprsWithBuffer`, contracts/strategies/idle/IdleCreditVault.sol:217-235) that neither checks nor warns about open APR0 principal. Nothing in `requestWithdraw`, `setAprs`, or the epoch state machine prevents the sequence.

### Recommendation
Make the invariant state-clearing atomic with the check: in `prepareStopEpochWithApr0`, close `apr0TotalPrincipal` (and mark open APR0 requests for principal-only settlement, forfeiting interest) *before* enforcing `unscaledApr == 0`, so a changed APR cannot wedge the epoch. Alternatively, reject `setApr(s)` to a non-zero APR while `apr0TotalPrincipal != 0`, or impose a minimum `requestWithdraw` amount. Emitting the open APR0 bucket in a view function would also let operators detect the condition.

### Proof of Concept
```solidity
// Foundry fork PoC (extend test/foundry/IdleCreditVault.t.sol harness)
// Preconditions: epoch running with unscaledApr == 0, KYC'd attacker.
function testPocApr0DustBricksStopEpoch() external {
    // owner disables AYS, manager sets APR to 0
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // attacker deposits 1 wei-equivalent and requests withdraw -> apr0TotalPrincipal = dust
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1, true); // dust KYC deposit
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // honest manager raises APR for next epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(10, 10);

    // every stopEpoch now reverts: funds frozen
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // no withdraw claim can proceed because epochNumber never advances
}
```
