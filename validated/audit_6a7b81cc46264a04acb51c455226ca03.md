### Title
Owner-Address Silent Padding/Truncation in Vault Secret Label Derivation Allows Loose Address Validation - (File: core/capabilities/vault/vaultutils/labels.go)

### Summary
The Chainlink Vault capability's gateway-facing handler accepts a user-supplied `Owner` string for every secret identifier in `CreateSecrets`/`UpdateSecrets`/`DeleteSecrets`/`ListSecretIdentifiers` requests [1](#0-0) . The owner value is validated only against a generic alphanumeric-character/length check [2](#0-1) , never against a canonical, exact-length Ethereum address format. Downstream, the security-critical binding between a secret and its owner — the TDH2 encryption label — is derived by calling go-ethereum's `common.HexToAddress(owner)` [3](#0-2) , which (exactly like the reported Starknet `addAddressPadding`/`validateAndParseAddress` bug) silently left-pads short hex strings and silently truncates overlong ones into a 20-byte address instead of erroring.

### Finding Description
`WorkflowOwnerToLabel` is the function that converts the `owner` field of a `SecretIdentifier` into the 32-byte label that cryptographically binds an encrypted secret to a workflow owner:
```go
func WorkflowOwnerToLabel(owner string) [32]byte {
	var label [32]byte
	addr := common.HexToAddress(owner)
	copy(label[12:], addr.Bytes())
	return label
}
``` [3](#0-2) 

`common.HexToAddress` has the same "lax validation" behavior flagged in the external report: it does not enforce that the input is exactly 40 hex characters. Short inputs are left-padded with zero bytes, and inputs longer than 20 bytes are silently truncated to the last 20 bytes, with no error returned in either case.

The only gate on the `Owner` string before this call is `ValidateSecretIdentifier`, which merely requires the string to match `^[a-zA-Z0-9_]+$` and fall under a configured max length [4](#0-3) . It never checks that owner is a well-formed, canonical 40-hex-character address (with or without `0x` prefix). This is called from the write path (`validateWriteRequest`) before `EnsureRightLabelOnSecret` computes the expected label using the same lax `WorkflowOwnerToLabel` [5](#0-4) [6](#0-5) .

Separately, the owner-equality check used for gateway-side authorization, `NormalizeOwner`, does only `strings.ToLower(strings.TrimPrefix(owner, "0x"))` — plain string manipulation with no canonicalization to a fixed-length address [7](#0-6) . This function is the single comparison primitive used throughout `authorizer.go` to decide whether the caller is allowed to touch a given secret identifier [8](#0-7) .

Because two different pieces of code decide "same owner" using two different notions of equality — `NormalizeOwner` (raw string compare) for authorization, and `common.HexToAddress` (byte-padded/truncated 20-byte address) for the cryptographic label — an owner string that is not a canonical 40-hex-character address can pass the authorization string-compare while resolving to a completely different (and possibly attacker-influenced) 20-byte label than what a human or dApp caller believes they're operating on. This mirrors the reported issue precisely: the exposed API does not enforce "exact address length" before doing address-shaped operations on the input, allowing under-length/over-length inputs to be silently coerced.

### Impact Explanation
If an owner string is accepted with the wrong length (e.g., due to caller error, or a workflow/JWT-derived owner value formatted inconsistently between the authorization path and the label-derivation path), the TDH2 label used to seal/open a secret could silently collide with, or diverge from, the label intended by the legitimate owner. Because the label is the mechanism that scopes ciphertext decryption/re-encryption rights to a specific owner, this class of bug is the type of "confusable identity" bug that historically enables cross-user secret disclosure or write confusion. It does not require an on-chain address collision to cause harm at the request-validation layer — it only requires the two normalization functions in this codebase to disagree on what "the same owner" means, which they currently do (string-level trim/lowercase vs. byte-level hex decode/pad/truncate).

### Likelihood Explanation
The `Owner` field is a plain externally supplied JSON-RPC string traveling from a gateway-facing, unauthenticated-at-the-network-layer message envelope into the vault handler (`core/capabilities/vault/gw_handler.go`), so it is fully attacker-influenced up to the point where `NormalizeOwner`/`isValidIDComponent` gate it. Both of those gates accept any alphanumeric string of bounded length that need not be a well-formed 40-hex-character address, which is a low bar to clear.

### Recommendation
Enforce a single, canonical address validation function everywhere an "owner" string is accepted from the network: require it to be exactly 40 hex characters (optionally `0x`-prefixed) before it is used in `NormalizeOwner`, `isValidIDComponent`/`ValidateSecretIdentifier`, or `WorkflowOwnerToLabel`. Reject (don't silently pad/truncate) any owner string that is not already in this canonical form, and make `NormalizeOwner` perform the same canonicalization (e.g., parse via `common.HexToAddress` and re-serialize to a fixed-width hex string) that `WorkflowOwnerToLabel` uses internally, so the authorization-equality check and the cryptographic-label derivation are guaranteed to agree on every input.

### Proof of Concept
Not independently reproduced end-to-end in this analysis; the concrete PoC would require confirming whether any code path can present an owner string to `EnsureRightLabelOnSecret`/`WorkflowOwnerToLabel` that differs (in length/representation) from the string compared by `NormalizeOwner` for the same logical owner (e.g., via JWT-derived owner formatting, or a caller supplying a non-canonical-but-alphanumeric owner value that still passes `isValidIDComponent`). This would need to be validated further with a Devin session that can execute the Go test suite (`core/capabilities/vault/validator_test.go`, `core/capabilities/vault/vaultutils/*_test.go`) and trace all callers/producers of the `Owner` string to determine whether an actually exploitable divergence between the two normalization functions exists in practice.

func EnsureRightLabelOnSecret(publicKey *tdh2easy.PublicKey, secret, owner string) error {
	cipherText, err := verifyEncryptedSecret(publicKey, secret)
	if err != nil {
		return err
	}
	if cipherText == nil {
		return nil
	}
	if owner == "" {
		return errors.New("owner must not be empty for secret label verification")
	}

	expected := vaultutils.WorkflowOwnerToLabel(owner)
	secretLabel := cipherText.Label()
	if secretLabel == expected {
		return nil
	}

	return fmt.Errorf("secret label [%s] does not match workflow owner label [%s]",
		hex.EncodeToString(secretLabel[:]), hex.EncodeToString(expected[:]))
}

func validateEncryptedSecretOwnerMismatch(encryptedSecrets []*vaultcommon.EncryptedSecret, workflowOwner string) error {
	if len(encryptedSecrets) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}
	for idx, encryptedSecret := range encryptedSecrets {
		if encryptedSecret == nil {
			return fmt.Errorf("encrypted secret must not be nil at index %d", idx)
		}
		if encryptedSecret.Id == nil {
			return fmt.Errorf("secret ID must not be nil at index %d", idx)
		}
		if vaultutils.NormalizeOwner(encryptedSecret.Id.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("encrypted secret owner at index %d %q does not match authorized workflow owner %q", idx, encryptedSecret.Id.Owner, workflowOwner)
		}
	}
	return nil
}

func validateSecretIdentifierOwnerMismatch(ids []*vaultcommon.SecretIdentifier, workflowOwner string) error {
	if len(ids) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}
	for idx, id := range ids {
		if id == nil {
			return fmt.Errorf("secret ID must not be nil at index %d", idx)
		}
		if vaultutils.NormalizeOwner(id.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("secret identifier owner at index %d %q does not match authorized workflow owner %q", idx, id.Owner, workflowOwner)
		}
	}

}
