### Title
Builder payment recipient (`fee_recipient`) is unauthenticated at the consensus layer, allowing a builder to redirect the proposer's payment to an arbitrary address - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas (EIP-7732) fork, a proposer accepts a builder's `SignedExecutionPayloadBid` and includes it in a block. The bid carries `bid.fee_recipient`, the execution-layer address that receives the builder's payment. The *only* place the protocol checks that this address matches the address the proposer actually asked for (via `SignedProposerPreferences`) is a soft, bypassable p2p gossip-validation rule. The authoritative state-transition function that actually queues/settles the payment, `process_execution_payload_bid`, never checks `bid.fee_recipient` against anything. This is structurally the same bug class as CWE-601 (open redirect): a "destination" field supplied by an untrusted party is trusted and acted upon without validation by the authoritative code path, with validation only optionally performed by a filter that can be, and by spec design explicitly may be, skipped.

### Finding Description
`process_execution_payload_bid` in `specs/gloas/beacon-chain.md` is the sole consensus-level checker for a bid before it is committed to state: [1](#0-0) 

It validates the builder's identity/version, balance sufficiency, BLS signature, blob-commitment count, slot, parent linkage, and prev-randao — but it never reads or checks `bid.fee_recipient` against the proposer's declared preference. The unchecked value is then written straight into the pending payment / withdrawal record that will eventually pay out Gwei: [2](#0-1) 

The *only* place `fee_recipient` is cross-checked against the proposer's intent is in the p2p gossip validation rules, and even there it is an `IGNORE` (a soft, local, unenforced filtering rule), not a `REJECT`: [3](#0-2) 

Critically, the spec text itself sanctions bypassing this gossip check entirely: the validator guidance explicitly allows proposers to source the bid "by other off-protocol means" instead of listening to gossip: [4](#0-3) 

and the builder guidance for constructing `bid.fee_recipient` only says it "should" be obtained from the matching `SignedProposerPreferences" — it is not an assertion enforced by any state-transition code: [5](#0-4) 

Because `process_execution_payload_bid` (the function that all conforming nodes run to validate a block) places no constraint on `bid.fee_recipient`, any syntactically valid signed bid — with `fee_recipient` set to any address the builder likes, including the builder's own address or a third party's — is a fully valid state transition. The equality that should hold — "the builder payment is delivered to the address the proposer requested" — is not enforced by the code that actually authorizes the payment; it depends entirely on an optional, off-chain/gossip-only convention.

### Impact Explanation
This falls under the High-impact category "a builder payment or withdrawal misdirected." A builder (who fully controls the content of the bid it signs) can set `fee_recipient` to any address instead of the one the targeted proposer published in `SignedProposerPreferences`. If the proposer's validator/builder software obtains the bid via the allowed off-gossip channel (explicitly permitted by spec) or simply forwards whatever bid content it receives without re-deriving and independently enforcing the match itself (the spec's canonical `process_execution_payload_bid` gives it no reason to, since that function accepts the block regardless), the Gwei payment queued in `BuilderPendingPayment`/`BuilderPendingWithdrawal` and ultimately disbursed via `process_withdrawals` is misdirected away from the intended recipient — with the misdirection invisible to state-transition validation and therefore invisible to every other honest node, which will accept the block as fully valid.

### Likelihood Explanation
Likelihood is elevated because the bug does not require a client bug, a network partition, or a coalition: it requires only a single dishonest/self-interested builder submitting a bid outside gossip (a use explicitly sanctioned by the spec), or gossip validators simply not universally enforcing/propagating the `IGNORE` semantics strongly enough to prevent a proposer from ever seeing a mismatched bid through a direct peer connection. Given `IGNORE` (not `REJECT`) is the strongest gossip-level defense, and the check is entirely absent from the authoritative `process_execution_payload_bid`, the security property "builder pays whoever the proposer designated" is not a consensus invariant at all — it is best-effort networking hygiene.

### Recommendation
Add an explicit check to `process_execution_payload_bid` (or an equivalent block-validity assertion) that `bid.fee_recipient` matches the proposer's most recently valid `SignedProposerPreferences` for `bid.slot` (matched by `dependent_root`/`proposal_slot` as already done at the gossip layer), and reject the block/bid at the state-transition level if it does not. Alternatively, if flexibility for proposers to accept any address is intended, this should be explicitly documented as a deliberate design choice (proposer opts in to trusting whatever `fee_recipient` a bid carries) rather than left ambiguous, since currently the spec text implies (via `SignedProposerPreferences`) that the recipient is meant to be authenticated but never actually enforces it on-chain.

### Proof of Concept
1. Proposer `P` for slot `S` broadcasts `SignedProposerPreferences` with `fee_recipient = A` (its own address), signed correctly per `get_signed_proposer_preferences` [6](#0-5) .
2. Builder `B` constructs `ExecutionPayloadBid` for slot `S` with `bid.fee_recipient = C` (an address `B` controls, `C != A`), satisfying every other field (`parent_block_hash`, `parent_block_root`, `prev_randao`, `block_hash`, valid BLS signature, sufficient balance) — none of which reference `fee_recipient`.
3. `B` sends this signed bid directly to `P` off-gossip (explicitly permitted: "The block proposer MAY obtain these signed messages by other off-protocol means" [7](#0-6) ), bypassing the `IGNORE`-level gossip check in `specs/gloas/p2p-interface.md` lines 977-979.
4. `P` includes the bid in its block. `process_execution_payload_bid` runs the checks at lines 2087-2122 of `specs/gloas/beacon-chain.md`; all pass because none of them examine `fee_recipient`.
5. The pending payment/withdrawal is recorded with `fee_recipient = C` (lines 2124-2141), and this value flows unchanged through `apply_parent_execution_payload` / `settle_builder_payment` to the eventual `BuilderPendingWithdrawal` and payout in `process_withdrawals`.
6. Every honest node applying the same block accepts it as valid — the payment intended for `A` is paid to `C` instead, with no fork or rejection anywhere in the protocol.

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

def get_signed_proposer_preferences(
    store: Store,
    state: BeaconState,
    head_root: Root,
    proposal_slot: Slot,
    validator_index: ValidatorIndex,
    fee_recipient: ExecutionAddress,
    target_gas_limit: Uint64,
    privkey: int,
) -> SignedProposerPreferences:
    proposal_epoch = compute_epoch_at_slot(proposal_slot)
    dependent_root = get_shuffling_dependent_root(store, head_root, proposal_epoch)
    preferences = ProposerPreferences(
        dependent_root=dependent_root,
        proposal_slot=proposal_slot,
        validator_index=validator_index,
        fee_recipient=fee_recipient,
        target_gas_limit=target_gas_limit,
    )
    domain = get_domain(state, DOMAIN_PROPOSER_PREFERENCES, proposal_epoch)
    signing_root = compute_signing_root(preferences, domain)
    signature = bls.Sign(privkey, signing_root)
    return SignedProposerPreferences(message=preferences, signature=signature)

##### Signed execution payload bid

To obtain `signed_execution_payload_bid`, a block proposer building a block on
top of a `state` MUST take the following actions in order to construct the
`signed_execution_payload_bid` field in `BeaconBlockBody`:

- Listen to the `execution_payload_bid` gossip global topic and save an accepted
  `signed_execution_payload_bid` from a builder. The block proposer MAY obtain
  these signed messages by other off-protocol means.
- The `signed_execution_payload_bid` MUST satisfy the verification conditions
  found in `process_execution_payload_bid` with the alias
  `bid = signed_execution_payload_bid.message`, that is:
  - For external builders, the signature MUST be valid.
  - For self-builds, set `bid.builder_index` to `BUILDER_INDEX_SELF_BUILD`.
  - For self-builds, the signature MUST be `bls.G2_POINT_AT_INFINITY` and the
    `bid.value` MUST be zero.
