### Title
Unauthenticated access to plugin pprof symbol endpoint exposing internal LOOPP debug/pprof data - ([File: core/web/router.go], [File: core/web/loop_registry.go])

### Summary
The route `POST /plugins/:name/debug/pprof/symbol` is registered in `loopRoutes` without any authentication middleware, unlike the sibling `metricRoutes`/`debugRoutes` which wrap pprof and debug endpoints behind `auth.Authenticate`. Any unauthenticated caller can invoke `LoopRegistryServer.pluginPPROFPOSTSymbolHandler`, which reads the raw POST body and proxies it directly to the plugin's internal `/debug/pprof/symbol` endpoint, returning the plugin's symbol/address mapping response to the caller.

### Finding Description
`loopRoutes` registers all LOOPP-related endpoints on the `api` group, which only carries the session-cookie middleware and rate limiter — no authentication: [1](#0-0) 

Compare this to `metricRoutes`, which is explicitly commented as "Debug routes accessible via authentication" and mounted only under the authenticated `authv2` group: [2](#0-1) [3](#0-2) 

and `debugRoutes`, which wraps `/debug/vars` in `auth.Authenticate(..., auth.AuthenticateBySession)`: [4](#0-3) 

`loopRoutes` does neither for `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, or `/plugins/:name/debug/pprof/symbol` — these are mounted directly on `api` with no `auth.Authenticate(...)` wrapper: [1](#0-0) 

The handler itself performs no authentication or authorization check; it looks up the plugin by name, forwards the caller-supplied body to the plugin's internal pprof symbol endpoint, and returns the raw response: [5](#0-4) 

Because the `api` gin.RouterGroup applies only `rateLimiter` and `sessions.Sessions` (cookie session store setup, not an auth check) before `loopRoutes` is invoked: [6](#0-5) 

any network client that can reach the node's HTTP API (unauthenticated) can send `POST /plugins/<name>/debug/pprof/symbol` with an arbitrary body and receive the plugin's pprof symbol table (address-to-function-name mappings), which is internal reconnaissance data normally gated behind authentication for all other pprof/debug endpoints in this codebase.

### Impact Explanation
This allows an unauthenticated attacker to retrieve internal LOOPP plugin symbol/address mappings via pprof's symbol resolution, which is intended to require authentication (per the explicit `metricRoutes`/`debugRoutes` pattern elsewhere in the same file). This is an authentication-bypass style information disclosure of internal runtime/debug data that aids further reconnaissance or exploitation of the node/plugin process, matching Chainlink's "unauthorized information disclosure of node internals" bounty impact class. It is lower severity than key/secret disclosure since pprof symbol output only reveals function/address mappings, not credentials or funds directly, but it is a clear violation of the "debug endpoints require authentication" invariant enforced everywhere else in the router.

### Likelihood Explanation
No credentials, session, or API token are required — a plain unauthenticated HTTP POST to `/plugins/:name/debug/pprof/symbol` reaches the handler directly since the route bypasses `auth.Authenticate`. It requires only network reachability to the node's API port and knowledge/discovery of a valid plugin name (obtainable via the also-unauthenticated `/discovery` and `/plugins/:name/metrics` routes registered in the same `loopRoutes` function). This makes it fully reproducible and repeatable with zero privileges.

### Recommendation
Wrap the `loopRoutes` registrations (at minimum the `/plugins/:name/debug/pprof/*` and `/plugins/:name/debug/pprof/symbol` routes) with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)` (or an appropriate token-based scheme), consistent with `debugRoutes` and `metricRoutes`. If `/discovery` and `/plugins/:name/metrics` must remain open for Prometheus scraping, restrict pprof-specific subroutes separately, mirroring how `metricRoutes` is isolated from the unauthenticated `discoveryHandler`.

### Proof of Concept
Go handler-level integration test plan:
1. Build a `gin.Engine` using `web.NewRouter(app, nil)` with a test `chainlink.Application` that has a `LoopRegistryServer` registry containing a fake plugin `"testplugin"` with a mock HTTP server on `EnvCfg.PrometheusPort` serving `/debug/pprof/symbol`.
2. Issue `httptest.NewRequest("POST", "/plugins/testplugin/debug/pprof/symbol", bytes.NewReader([]byte("0x1234")))` with **no** `Authorization` header, `Cookie`, or session.
3. Serve via `router.ServeHTTP(w, req)`.
4. Assert `w.Code == http.StatusOK` (not `401 Unauthorized`) and that `w.Body` contains the mock plugin's symbol response — proving the request reached `pluginPPROFPOSTSymbolHandler` and was forwarded/returned without any authentication check.
5. As a control, repeat the same unauthenticated request against `/debug/vars` and confirm it returns `401` (via `auth.Authenticate`), demonstrating the inconsistency/vulnerability specific to the `loopRoutes` pprof endpoint.

func (l *LoopRegistryServer) pluginPPROFPOSTSymbolHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/symbol", l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	body, err := io.ReadAll(gc.Request.Body)
	if err != nil {
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "error reading plugin pprof request body: %s", err))
		return
	}
	l.doRequest(gc, "POST", pluginURL, bytes.NewReader(body), timeout, pluginName)
}
