## Title
Confirmations from deleted multisig members remain valid and count toward execution threshold, allowing a request to execute below the true live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in `multisig2/src/lib.rs` only removes pending requests that were *created* by the member being deleted; it does not scrub that member's existing confirmations from *other* pending requests. `confirm` never re-validates that the accounts recorded in a request's confirmation set are still current members. As a result, a confirmation cast by a member who is later removed continues to count toward `num_confirmations`, letting a request execute with fewer live-member approvals than the configured threshold.

### Finding Description
`MultiSigContract::confirm` tallies confirmations purely by set size against `self.num_confirmations`: [1](#0-0) 

`delete_member` removes the deleted member from `self.members`, deletes their access key, and purges **only the requests they originally authored** (`r.member == member`), together with those requests' confirmation sets: [2](#0-1) 

It does not scan `self.confirmations` for entries where the deleted member appears as a *confirmer* of a request authored by someone else. `assert_valid_request`, called from both `delete_request` and `confirm`, only checks that the *caller* is currently a member — it performs no validation of previously stored confirmations: [3](#0-2) 

Consequence: if member `M1` confirms a request `R` authored by `M2`, and `M1` is subsequently removed via `DeleteMember`, `R`'s confirmation set still contains `M1`. A later confirmation by any other single current member reaches `num_confirmations` and executes `R`, even though only one currently-valid member actually approved it at that time.

### Impact Explanation
This breaks the core custody binding of the contract: "confirmations counted" no longer equals "live members who approved." The documented guarantee is a strict K-of-N scheme where K approvals from current members are required before any `Transfer`, `AddKey`, `FunctionCall`, etc. is executed. With this flaw, a request can be executed with fewer than K live-member approvals, effectively executing a multisig request below its threshold — this matches the Critical impact category ("a multisig request executed below threshold"). Since `MultiSigRequestAction::Transfer`/`FunctionCall`/`AddKey` can move NEAR or grant access, a stale confirmation can be leveraged to push through a transfer or privilege-escalating action that would not otherwise have reached quorum among the current membership.

### Likelihood Explanation
The bug is triggered through ordinary multisig operations, no external contract or malicious validator is needed:
1. A request `R` is created by member `M2` and confirmed by member `M1` (below threshold, left pending).
2. Members later remove `M1` (e.g., as routine key rotation or because `M1`'s key is suspected compromised) via a normal `DeleteMember` request — this is exactly the scenario the removal feature is meant to support (revoking a member's authority).
3. Any remaining current member confirms `R`, and it executes using `M1`'s stale confirmation, which should have been invalidated as soon as `M1` was removed.
Because member removal is an expected/likely maintenance operation (e.g., removing a compromised or departing member) and there is no special coordination required beyond normal contract usage, likelihood is not negligible — the very act of revoking a member fails to revoke their prior influence on outstanding requests.

### Recommendation
When a member is deleted, iterate over all pending requests' confirmation sets (not just requests authored by that member) and remove any confirmation entry belonging to the deleted member. Alternatively, validate at `confirm`-time that every entry in the stored confirmation set still corresponds to a current member (pruning stale ones) before comparing the count to `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new` with members `[M1, M2, M3]` and `num_confirmations = 2`.
2. `M2` calls `add_request` with `MultiSigRequest { receiver_id: <self>, actions: [Transfer { amount }] }` → request `R` created, confirmations `{}`.
3. `M1` calls `confirm(R)` → confirmations `{M1}` (1 < 2, stays pending) — see `confirm` logic at [4](#0-3) .
4. Members submit and confirm a separate `DeleteMember { member: M1 }` request (using `M2`+`M3`, i.e., normal threshold-satisfying removal of `M1`). `delete_member` executes: it deletes `M1`'s key/account and purges only requests where `r.member == M1` — request `R` (authored by `M2`) is untouched, and `R`'s confirmation set still contains `M1` — see [2](#0-1) .
5. `M3` calls `confirm(R)` → confirmations becomes `{M1, M3}`, size 2 `>= num_confirmations (2)` → `R` executes the `Transfer`, even though `M1` is no longer a member and only one currently valid member (`M3`) actually approved `R`.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
