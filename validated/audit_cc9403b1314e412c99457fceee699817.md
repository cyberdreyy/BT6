### Title
Unauthenticated flood of `web_api_trigger` requests causes premature eviction of legitimate pending callbacks - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The legacy capabilities gateway handler accepts any self-signed `web_api_trigger` message with no allowlist or per-sender rate limiting, inserting an entry into the shared `h.savedCallbacks` map keyed by an attacker-controlled `MessageId`. Because `pruneCallbacks` evicts strictly by insertion age once the map exceeds `MaxSavedCallbacks`, an attacker can flood the map faster than pruning runs and force eviction of legitimate, still-unexpired callbacks that were inserted before the flood.

### Finding Description
`HandleLegacyUserMessage` requires only `msg.Validate()` to succeed, which checks signature well-formedness and message field lengths, and extracts a signer address from the signature — it does not check that the signer/sender is an authorized or known caller [1](#0-0) . The comment `// TODO: apply allowlist and rate-limiting here` confirms no allowlist or per-user rate limiting exists at this call site [4](#0-3) . Any attacker who can reach the gateway's HTTP ingress and generate an ECDSA keypair can therefore submit unlimited `web_api_trigger` messages, each with an attacker-chosen `MessageId` (bounded only by `MessageIdMaxLen`), each unconditionally inserted into `h.savedCallbacks` under the global mutex `h.mu` [5](#0-4) .

`pruneCallbacks` runs on a fixed 30s ticker (`defaultCallbackPruneIntervalSec`) and, once the map exceeds `MaxSavedCallbacks` (default 20000), sorts all entries by `createdAt` and deletes the oldest half regardless of whether they have actually expired via `CallbackMaxAgeSec` [6](#0-5) . Because eviction is purely age/insertion-order based and applies to the whole shared map (not per-sender), a legitimate user's callback inserted moments before an attacker's flood is, by definition, "older" than the flood entries and will be evicted first — even though it is still well within `CallbackMaxAgeSec` and awaiting a DON response. When the DON's response later arrives, `handleWebAPITriggerMessage` looks up `msg.Body.MessageId` in `savedCallbacks`; if it was evicted, `found` is `false` and the response is silently dropped [7](#0-6) . From the user's perspective, `callback.Wait(ctx)` in `gateway.go`'s `ProcessRequest` will time out, returning a `handler timeout` error instead of the actual DON response [8](#0-7) .

Between two 30s prune ticks there is no size check at insertion time, so the map can grow arbitrarily large during a burst, and the note `// could briefly exceed under heavy load` on `defaultMaxSavedCallbacks` acknowledges this [9](#0-8) .

Note: this is the legacy handler path (`handler.go`); the newer v2 `httpTriggerHandler` in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go` does implement `authorizeRequest`, `checkRateLimit`, and duplicate-ID rejection before saving a callback [10](#0-9) , so this issue is specific to the legacy handler that the question targets.

### Impact Explanation
An unauthenticated (self-signing) attacker can cause denial-of-service against other users' pending gateway requests: legitimate `web_api_trigger` responses can be silently dropped and the caller receives a timeout error instead of the real DON response. This is an availability/isolation violation (one attacker's traffic evicting another user's in-flight state) rather than direct fund loss or secret disclosure, matching a "denial of service / broken isolation between users" bounty class rather than a critical compromise.

### Likelihood Explanation
Exploitation requires only the ability to reach the gateway's user-facing HTTP ingress and generate a local ECDSA keypair to self-sign a well-formed `web_api_trigger` message — no DON membership, no credentials, and no privileged role. The attacker must sustain an insertion rate exceeding the pruning cadence (every 30s) for the duration a target's request is expected to remain pending (`CallbackMaxAgeSec`, default 120s), which is readily achievable given no user-side rate limiting or allowlist gates this code path. This is fully repeatable and requires no race against a specific `MessageId` (no need to guess victim IDs, since bulk age-based eviction of the whole map suffices).

### Recommendation
- Add per-sender rate limiting and/or an allowlist check to `HandleLegacyUserMessage` before inserting into `h.savedCallbacks`, as the existing TODO comment indicates was intended.
- Enforce a hard cap check at insertion time (reject/backpressure new callbacks when `len(h.savedCallbacks) >= MaxSavedCallbacks`) instead of only reactively pruning every 30s.
- Change eviction policy so that only expired (`CallbackMaxAgeSec`-exceeded) entries are ever removed, and if capacity must still be enforced, base eviction on rate/sender attribution rather than blindly deleting the globally oldest entries, so an attacker's own flood is evicted preferentially over legitimate pending callbacks.

### Proof of Concept
Go handler-level test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` via `NewHandler` with small `MaxSavedCallbacks` (e.g. 10) and `CallbackPruneIntervalSec`/`CallbackMaxAgeSec` set to deterministic small values, using a fake `don.SendToNode` that no-ops.
2. Insert one legitimate callback via `HandleLegacyUserMessage` with a signed message from "victim" key, record its `MessageId`, and capture its `callback`.
3. Immediately flood `HandleLegacyUserMessage` with N > MaxSavedCallbacks messages self-signed by freshly generated attacker keys, each with unique random `MessageId`s, all with `createdAt` timestamps after the victim's entry.
4. Manually invoke `h.pruneCallbacks()` (or wait for the ticker) and assert that the victim's `MessageId` has been deleted from `h.savedCallbacks` due to insertion-order-based eviction, despite being well within `CallbackMaxAgeSec`.
5. Simulate the DON's response for the victim's `MessageId` via `HandleNodeMessage`/`handleWebAPITriggerMessage` and assert that `savedCb` is `found == false`, i.e., the response is silently dropped and the victim's `callback.Wait(ctx)` times out rather than resolving with the true response — proving eviction does not respect `CallbackMaxAgeSec` and can be triggered by an unprivileged attacker's insertion volume alone.
