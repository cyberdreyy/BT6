### Title
Miner's per-signer response tally double-counts a signer that rejects then later accepts, corrupting `total_weight_approved`/`total_weight_rejected` invariant - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` (used by `SignerCoordinator` to decide whether a proposed block has reached the 70% signing threshold or the >30% blocking-rejection threshold) tracks two independent, monotonically increasing counters per block: `total_weight_approved` and `total_weight_rejected`. The guard that prevents a signer from being counted twice is asymmetric: it protects "accept-then-reject" (sticky acceptance) but not "reject-then-accept". A signer who rejects and later legitimately changes their vote to accept the same block ends up counted in *both* tallies, because the acceptance branch only checks `gathered_signatures` (never touched by a rejection) before adding weight, while the earlier rejection weight is never removed.

### Finding Description
In `handle_stackerdb_chunk` (stacks-node/src/nakamoto_node/stackerdb_listener.rs), the two response branches are:

- Acceptance branch (lines 443-465): weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, and `slot_id` is then inserted into **both** `gathered_signatures` and `responded_signers`. [1](#0-0) 

- Rejection branch (lines 515-518): weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time seen in `responded_signers`), but `slot_id` is **not** added to `gathered_signatures`. [2](#0-1) 

Because of this asymmetry:
- Accept → Reject: the reject branch's `responded_signers.insert(slot_id)` returns `false` (already inserted by the earlier accept), so the stale acceptance is correctly "sticky" and no double count occurs — matches the documented behavior ("approvals are sticky") in `docs/signer-flows.md`. [3](#0-2) 
- Reject → Accept: the accept branch only checks `gathered_signatures`, which the rejection never populated, so the check passes and `total_weight_approved` is incremented for a signer who is *already* counted in `total_weight_rejected`. The earlier rejection weight is never subtracted.

This breaks the accounting invariant that a single signer's weight should be attributed to at most one side of the tally, i.e. `total_weight_approved + total_weight_rejected <= total_weight` for the set of distinct responding signers can be violated. The explicit design intent that a signer/block pair must not be counted for both an acceptance and a rejection is documented and enforced at the signer's own `SignerDb` layer (`add_block_signature` removes any prior rejection row; `add_block_rejection_signer_addr` refuses to record a rejection if a signature already exists), and is unit-tested there (`reject_then_accept` / `accept_then_reject`). [4](#0-3) [5](#0-4) [6](#0-5) 

However, this exact same guarantee is not reproduced in the node-side `BlockStatus` tally that the miner's `SignerCoordinator` consults to decide the fate of the proposal (accept and push, or abandon as `SignersRejected`): [7](#0-6) 

### Impact Explanation
Because `total_weight_rejected` retains stale weight from a signer that has since switched to accepting, the miner's coordinator can:
1. Prematurely conclude `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` and abandon a block as `SignersRejected` even though the *current* set of dissenting signers no longer meets the actual blocking minority, because a flipped signer's stale rejection weight is still counted alongside their new (legitimate) acceptance weight in the other counter.
2. In general it corrupts the equality the coordinator relies on to determine consensus outcome, which can wedge/stall block production (miner gives up on a block/tenure and re-mines unnecessarily), a liveness impact on block production rather than a per-signer safety violation.

This is a node/coordinator-side miscount ("aggregated-weight vs verified-accepts" mismatch) rather than an individual signer signing something invalid, so it maps most closely to a liveness-affecting accounting bug in the block-approval tally used by the mining/coordination logic that consumes signer responses.

### Likelihood Explanation
This requires only a single honest signer changing its vote from reject to accept for the same block within one proposal round — a legitimate and expected occurrence (e.g., after `should_reevaluate_reject_reason` allows reconsideration, per `docs/signer-flows.md` section 3), no majority collusion or malicious signer is required. It can also be triggered by a single Byzantine/faulty signer simply sending reject then accept for the same block to bias the tally deliberately.

### Recommendation
In `stackerdb_listener.rs`, unify the exclusivity check across both branches: before adding weight to `total_weight_approved`, also check (and account for) whether the slot_id is already present in `responded_signers` due to a prior rejection, and if a signer flips from reject to accept, subtract their weight from `total_weight_rejected` (or otherwise recompute both totals from a single per-signer "current vote" map rather than two independently-incremented saturating counters), mirroring the mutual-exclusion logic already implemented and tested in `stacks-signer/src/signerdb.rs`'s `add_block_signature`/`add_block_rejection_signer_addr`.

### Proof of Concept
1. Miner proposes block B and asks signers for votes via `SignerCoordinator`/`StackerDBListener`.
2. Signer S sends `BlockResponse::Rejected` for B. `responded_signers` gets S's slot; `total_weight_rejected += weight(S)`. [2](#0-1) 
3. Signer S later reconsiders and sends `BlockResponse::Accepted` for the same B (a supported, tested flow per `stacks-signer/src/signerdb.rs`'s `reject_then_accept`).
4. In `stackerdb_listener.rs`, the acceptance branch checks only `gathered_signatures` (empty for S), so it adds `total_weight_approved += weight(S)` as well. [8](#0-7) 
5. Now `total_weight_approved + total_weight_rejected` counts S's weight twice, and `total_weight_rejected` never gets corrected even though S's live vote is "accept" — corrupting the equality the coordinator uses in `signer_coordinator.rs` (lines 512-545) to decide the block's fate.

**Uncertainty note:** I was unable to fully inspect `StackerDBListener::reset_rejections` (referenced from `signer_coordinator.rs` on a timeout path) within the available search budget, so I cannot rule out that some other, later-timeout-only code path partially mitigates the corrupted `total_weight_rejected` value in some scenarios; the double-count itself, however, is directly confirmed from the branch logic cited above.
