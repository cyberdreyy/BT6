## Finding

### Title
Lockup Factory lets an unprivileged caller substitute the trusted staking-pool whitelist for a victim's lockup contract - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` accepts a caller-supplied `whitelist_account_id` parameter that, if present, silently overrides the factory's canonical `whitelist_account_id` before it is baked into the newly deployed lockup contract's immutable `staking_pool_whitelist_account_id` field. [1](#0-0)  Any account can call `create`, pay the minimum deposit, name an arbitrary `owner_account_id` (the intended beneficiary), and pass its own attacker-controlled "whitelist" contract instead of the real NEAR Foundation whitelist. The deployed `LockupContract` never re-validates that `staking_pool_whitelist_account_id` is the canonical foundation whitelist. [2](#0-1) 

### Finding Description
The lockup/staking-pool trust model in this codebase is: the `whitelist` contract is the single, foundation-curated source of truth for which staking-pool account IDs are safe to delegate to. [3](#0-2)  A `LockupContract` owner picks a staking pool via `select_staking_pool`, which cross-checks the pool against `self.staking_pool_whitelist_account_id` before accepting it: [4](#0-3)  and the callback simply trusts whatever boolean the whitelist contract returns: [5](#0-4) 

The binding that should hold is:
`lockup.staking_pool_whitelist_account_id == <canonical NEAR-Foundation-controlled whitelist contract>`

However, `LockupFactory::create` lets the caller override this value per-deployment:
```
// Defaults to the whitelist account ID given on init call.
let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
    account_id.into()
} else {
    self.whitelist_account_id.clone()
};
``` [6](#0-5) 

There is no check that the predecessor calling `create` is the foundation, the factory owner, or even the `owner_account_id` being funded. There is also no check that `whitelist_account_id`, when supplied, equals the factory's own `self.whitelist_account_id`. The `LockupContract::new` initializer only validates that the supplied whitelist account ID is a syntactically valid NEAR account, not that it is the real registry: [7](#0-6) 

So an unprivileged attacker can:
1. Deploy a trivial "fake whitelist" contract whose `is_whitelisted` always returns `true`.
2. Call `LockupFactory::create(owner_account_id: <victim>, ..., whitelist_account_id: Some(<fake_whitelist>))`, paying the `MIN_ATTACHED_BALANCE` (the attacker's own NEAR, which becomes the lockup's locked balance for the victim).
3. The resulting `LockupContract` for `<victim>` is permanently initialized with `staking_pool_whitelist_account_id = <fake_whitelist>` — this field is set once at `new` and there is no owner or foundation method to change it later.
4. When the victim owner later calls `select_staking_pool(<attacker_staking_pool>)`, the fake whitelist answers `is_whitelisted = true`, so `on_whitelist_is_whitelisted` accepts the attacker's staking pool as legitimate. [5](#0-4) 
5. The victim then deposits/stakes locked NEAR into the attacker's malicious "staking pool" via `deposit_and_stake`; the attacker's pool contract can refuse to honor unstake/withdraw, permanently freezing or stealing the locked NEAR.

This is the same bug class as the referenced report: an unprivileged party can pass an unvalidated address into a deployment function where the system is supposed to only trust addresses from an approved registry — here the "approved registry" is the staking-pool whitelist contract, and the "malicious template" is a fake whitelist contract that always approves.

### Impact Explanation
This crosses the custody/trust boundary described in the rules: "an account trusted as a pool or whitelist versus the code and arguments that trust was granted for." Because the poisoned whitelist is embedded at lockup-contract creation and is immutable afterward, any owner of a lockup contract deployed this way is permanently exposed to being tricked into staking with an attacker-controlled pool, resulting in NEAR being moved to a party not entitled to it and/or permanently frozen. This matches the Critical impact bar ("a wrongly whitelisted or wrongly parameterised deployment", "funds permanently frozen").

### Likelihood Explanation
`create` is a public, payable method with no access control on the caller, on `owner_account_id`, or on `whitelist_account_id`. Deploying a one-function fake whitelist contract is trivial. The only friction is the `MIN_ATTACHED_BALANCE` (3.5 NEAR) the attacker must fund the malicious lockup with — and that funding becomes the bait that is later stolen back once the victim stakes into the attacker's pool, so the attacker's cost is recoverable/likely offset by the eventual theft.

### Recommendation
Remove the caller-suppliable `whitelist_account_id` override from `LockupFactory::create`, or restrict it so the factory always uses `self.whitelist_account_id` (the value fixed at factory `new`) unless the call is authorized by the foundation account. If per-deployment overrides are required (e.g., for testnets), gate them behind `assert_eq!(env::predecessor_account_id(), self.foundation_account_id)` so only a trusted party can select a non-default whitelist contract.

### Proof of Concept
```
# 1. Attacker deploys a "fake whitelist" contract that always approves any pool:
pub fn is_whitelisted(&self, staking_pool_account_id: AccountId) -> bool { true }

# 2. Attacker calls the lockup factory, naming the victim as owner and their fake whitelist:
near call lockup-factory.near create '{
  "owner_account_id": "victim.near",
  "lockup_duration": "0",
  "lockup_timestamp": null,
  "vesting_schedule": null,
  "release_duration": null,
  "whitelist_account_id": "fake-whitelist.attacker.near"
}' --accountId attacker.near --amount 3.5

# 3. Victim, unaware the embedded whitelist is fake, later does:
near call <victim-lockup-account> select_staking_pool '{"staking_pool_account_id":"evil-pool.attacker.near"}' --accountId victim.near
near call <victim-lockup-account> deposit_and_stake '{"amount":"..."}' --accountId victim.near
# The fake whitelist approves evil-pool.attacker.near, so the deposit/stake succeeds,
# after which the attacker's pool contract can withhold the staked NEAR indefinitely.
```
This mirrors the referenced PoC pattern in the external report (deploy an attacker-controlled contract and pass it directly into a deployment call that should have validated it against an approved registry), applied here to `lockup-factory/src/lib.rs`'s unchecked `whitelist_account_id` parameter.

**File:** whitelist/README.md (L1-19)
```markdown
# Whitelist contract for staking pools

The purpose of this contract is to maintain the whitelist of the staking pool contracts account IDs that are approved
by NEAR Foundation.

In order for the lockup contracts to be able delegate to a staking pool, the staking pool should faithfully implement the spec.
The staking pool should guarantee that the delegated tokens can not be lost or locked, such as the lockup contract should be
able to recover delegated tokens back to the lockup from a staking pool. In order to enforce this, only approved (whitelisted)
accounts of staking pool contracts can receive delegated tokens from lockup contracts.

If NEAR Foundation has to approve every single staking pool account it might lead to a bottleneck and centralization
To address this NEAR Foundation can whitelist the account IDs of staking pool factory contracts.

The whitelisted staking pool factory contract will be able to whitelist accounts of staking pool contracts.
A factory contract creates and initializes a staking pool contract in a secure and permissionless way.
This allows anyone on the network to be able to create a staking pool contract for themselves without needing approval from the NEAR
Foundation. This is important to maintain the decentralization of the decision making and network governance.

To be able to address mistakes, NEAR Foundation has the ability to remove staking pools and staking pool factories from the whitelists.
```

        self.assert_owner();

        );
        self.assert_staking_pool_is_not_selected();

    /// Called after a given `staking_pool_account_id` was checked in the whitelist.
    pub fn on_whitelist_is_whitelisted(
        &mut self,
        #[callback] is_whitelisted: bool,
        staking_pool_account_id: AccountId,
    ) -> bool {
        assert_self();
        assert!(
            is_whitelisted,
            "The given staking pool account ID is not whitelisted"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();
        self.staking_information = Some(StakingInformation {
            staking_pool_account_id,
            status: TransactionStatus::Idle,
            deposit_amount: 0.into(),
        });
        true
    }
