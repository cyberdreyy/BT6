### Title
Builder withdrawal amount is not capped when queued into the payload, but the balance deduction is capped — mismatch mints Gwei on the execution layer - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas builder-withdrawal machinery, `get_builder_withdrawals()` copies the *requested* pending-withdrawal amount verbatim into the `Withdrawal` that is committed to `state.payload_expected_withdrawals` (and thus must be honored by the execution layer), while the later balance deduction in `apply_withdrawals()` silently caps the deduction to `min(withdrawal.amount, builder_balance)`. If a builder's pending-withdrawal amount ever exceeds its current balance at processing time, the execution layer credits the fee recipient the full requested amount while the beacon state only debits the smaller, capped amount — creating Gwei that was never backed by any account's balance.

### Finding Description
`get_builder_withdrawals` builds the withdrawal entry directly from the queued `BuilderPendingWithdrawal.amount`, with no comparison to the builder's current balance: [1](#0-0) 

This `Withdrawal` (amount uncapped) is placed into `state.payload_expected_withdrawals`, which the spec states the execution payload **is required to honor** verbatim: [2](#0-1) 

But when the corresponding balance deduction actually happens, `apply_withdrawals` caps the deduction to the builder's available balance instead of the full committed withdrawal amount: [3](#0-2) 

This is the exact analog of the reported `_claimRewardsOnBehalf()` bug: the amount recorded/paid out is silently capped to the available balance (`min(withdrawal.amount, builder_balance)`), but the promised/committed amount used elsewhere (here, the amount baked into the execution-layer withdrawal that credits `fee_recipient`) is not adjusted to match. In the Solidity case this caused *lost* rewards (a user gets less than accounted); here it is the mirror failure — the execution layer credits the *full, uncapped* amount to `fee_recipient` while the source (`builder.balance`) is only debited the smaller, capped amount, so the difference is minted with no corresponding deduction anywhere in the beacon state. This breaks the equality "every Gwei credited to an address on withdrawal must be removed from exactly one account's balance."

The repository's own tests demonstrate and lock in this exact capped-deduction/uncapped-payload-amount behavior: [4](#0-3) 

### Impact Explanation
If a `BuilderPendingWithdrawal.amount` can exceed the builder's balance at the time it is processed (e.g., multiple pending withdrawals queued against the same builder whose cumulative total exceeds the balance, since builders cannot be slashed to explain balance shrinkage otherwise), the execution layer withdrawal list will credit `fee_recipient` with more Gwei than was ever removed from `state.builders[builder_index].balance`. This is Gwei created and paid to an address, which is a Critical-class impact ("Gwei created ... paid to a non-owner") under the standard for this scan, since it mints unbacked ETH into the execution layer through a beacon-chain-committed withdrawal.

### Likelihood Explanation
This requires only that the sum of pending withdrawal amounts queued for a given builder can exceed that builder's balance at processing time — this repository's own design notes state builders cannot be slashed, so the only way for balance to fall below a previously-queued withdrawal amount is via other, earlier-processed builder withdrawals draining the same balance, or insufficient validation when the `BuilderPendingWithdrawal` request itself was enqueued. I was not able to fully trace the request-enqueuing code path (e.g., a `process_builder_pending_payments`/payment-request handler) within the available iterations to confirm whether amount-vs-balance is checked at enqueue time; this is a gap in my verification. The unit test explicitly exercising and asserting the capped-deduction/uncapped-payload-amount pairing indicates the scenario is reachable and already anticipated by spec authors, but its down-stream execution-layer accounting consequence (Gwei minted with no corresponding debit) does not appear to be addressed.

### Recommendation
Cap the `amount` field written into the `Withdrawal` object in `get_builder_withdrawals` to `min(withdrawal.amount, state.builders[builder_index].balance)` (using the balance projected through any prior withdrawals in the same payload, consistent with how validator sweep/partial withdrawals already use `get_balance_after_withdrawals`), so the amount committed to the execution payload can never exceed what `apply_withdrawals` will actually be able to deduct.

### Proof of Concept
1. Queue a `BuilderPendingWithdrawal` for `builder_index` with `amount = 5 ETH` while `state.builders[builder_index].balance = 1 ETH` (exactly as constructed in `test_builder_withdrawal_insufficient_balance`): [5](#0-4) 
2. `get_builder_withdrawals` emits `Withdrawal(..., amount=5 ETH)` into `state.payload_expected_withdrawals`, which the execution payload must honor by crediting `fee_recipient` with 5 ETH.
3. `apply_withdrawals` only deducts `min(5 ETH, 1 ETH) = 1 ETH` from `state.builders[builder_index].balance`, per: [6](#0-5) 
4. Net effect: 4 ETH is credited on the execution layer to `fee_recipient` with no corresponding beacon-state debit anywhere — Gwei created from nothing.
