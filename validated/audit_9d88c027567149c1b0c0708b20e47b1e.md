### Title
Unbounded per-slot signature index scan before limit filtering in `find_address_signatures_for_slot` - ([File: ledger/src/blockstore.rs])

### Summary
`Blockstore::find_address_signatures_for_slot` iterates the entire `address_signatures_cf` range for `(pubkey, slot)` and materializes every matching entry into a `Vec` with no `limit` parameter or early-exit condition. Because `get_confirmed_signatures_for_address2` (the backing implementation of the `getSignaturesForAddress` RPC) always calls this function first for the initial/highest slot before applying `.take(limit)`, a single low-rate RPC call can force the validator to build a result vector sized to the number of transactions referencing that address within one slot, regardless of the caller-supplied `limit`.

### Finding Description
`find_address_signatures_for_slot` opens a forward iterator over the `AddressSignatures` column family starting at `(pubkey, slot, 0, Signature::default())` and pushes every entry until `transaction_slot > slot || address != pubkey`: [1](#0-0) 

This function takes no `limit` argument at all, so it cannot cap the number of pushed entries. It is invoked unconditionally by `get_confirmed_signatures_for_address2` to fetch "signatures in `slot`" (the `highest_slot`, or the slot derived from `before`) before the main reverse-iteration/limit loop runs: [2](#0-1) 

The `.take(limit)` truncation only happens afterward, on the combined `address_signatures` vector: [3](#0-2) 

`get_signatures_for_address` in the RPC layer passes the caller's `limit` straight through to `get_confirmed_signatures_for_address2`, but that `limit` has no effect on the initial-slot fetch: [4](#0-3) 

Root cause: if an attacker submits/authors a large number of transactions in a single slot that all reference one static address (e.g., as fee payer or a shared account key), the `AddressSignatures` CF will contain a correspondingly large contiguous run of entries for `(pubkey, slot, *)`. A subsequent `getSignaturesForAddress(address, limit=1)` whose `highest_slot`/`before`-derived slot equals that slot causes `find_address_signatures_for_slot` to walk and allocate a `Vec` for the *entire* run before any limit is applied — the caller's `limit=1` does not bound this initial scan/allocation cost.

### Impact Explanation
This is an unbounded-cost-for-a-single-low-rate-call issue: CPU time (RocksDB iteration) and memory (Vec allocation, `(Slot, Signature, u32)` tuples) scale with the number of transactions referencing the target address in one slot, not with the requested `limit`. Since a slot's transaction count is bounded by block-level limits (CU budget, entry count), the worst case is not unbounded relative to the whole chain, but it is unbounded relative to the request parameter (`limit`), which is exactly the invariant the question targets: per-request cost should be bounded independent of on-chain data volume for that call.

### Likelihood Explanation
Feasible but costly: the attacker must get many fee-paying transactions referencing the same address included in a single slot (this is realistic since nothing prevents many serial transactions from sharing a writable/readable account within one block, only overall block CU/size limits apply). No leader/validator control is required — an ordinary unprivileged client can submit enough transactions and later issue a single `getSignaturesForAddress` call with `limit=1` whose initial slot lookup lands on that slot, triggering the disproportionate scan.

### Recommendation
Add an early-exit bound to `find_address_signatures_for_slot`, e.g., accept a `limit: usize` parameter (or an already-collected count from the caller) and `break` the iteration loop once `signatures.len() >= limit`, mirroring the bound already applied to the reverse-iteration loop later in `get_confirmed_signatures_for_address2`.

### Proof of Concept
```rust
// ledger/src/blockstore/tests.rs
#[test]
fn test_find_address_signatures_for_slot_no_limit_applied() {
    let ledger_path = get_tmp_ledger_path_auto_delete!();
    let blockstore = Blockstore::open(ledger_path.path()).unwrap();
    let address = solana_pubkey::new_rand();
    let slot = 1;

    // Simulate an attacker packing one slot with many transactions
    // referencing the same address.
    const N: usize = 50_000;
    for x in 0..N {
        let mut sig_bytes = [0u8; 64];
        sig_bytes[..8].copy_from_slice(&(x as u64).to_le_bytes());
        let signature = Signature::from(sig_bytes);
        blockstore
            .write_transaction_status(
                slot,
                signature,
                vec![(&address, true)].into_iter(),
                TransactionStatusMeta::default(),
                x,
            )
            .unwrap();
    }
    blockstore.set_roots(std::iter::once(&slot)).unwrap();

    // Call with limit = 1: expect the underlying per-slot fetch to be
    // bounded, but it currently returns/builds a Vec of size N.
    let sig_infos = blockstore
        .get_confirmed_signatures_for_address2(address, slot, None, None, 1)
        .unwrap();
    assert_eq!(sig_infos.infos.len(), 1); // outer result correctly limited

    // Direct call demonstrates the unbounded internal allocation:
    let raw = blockstore.find_address_signatures_for_slot(address, slot).unwrap();
    assert_eq!(raw.len(), N); // FAILS the desired invariant: should be capped near `limit`
}
```
Expected assertion for a fixed implementation: `find_address_signatures_for_slot` (or an equivalent limited variant) should stop iterating once a caller-supplied bound is reached, so `raw.len()` would be `<= limit`-related bound rather than `N`.

    fn find_address_signatures_for_slot(
        &self,
        pubkey: Pubkey,
        slot: Slot,
    ) -> Result<Vec<(Slot, Signature, u32)>> {
        let (lock, lowest_available_slot) = self.ensure_lowest_cleanup_slot();
        let mut signatures: Vec<(Slot, Signature, u32)> = vec![];
        if slot < lowest_available_slot {
            return Ok(signatures);
        }
        let index_iterator = self.address_signatures_cf.iter(IteratorMode::From(
            (
                pubkey,
                slot.max(lowest_available_slot),
                0,
                Signature::default(),
            ),
            IteratorDirection::Forward,
        ))?;
        for ((address, transaction_slot, transaction_index, signature), _) in index_iterator {
            if transaction_slot > slot || address != pubkey {
                break;
            }
            signatures.push((transaction_slot, signature, transaction_index));
        }
        drop(lock);
        Ok(signatures)
    }
