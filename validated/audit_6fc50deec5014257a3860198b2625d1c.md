### Title
Pending BB withdrawals bypass the junior-first loss waterfall - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
A BB holder can convert junior tranche exposure into an untyped withdrawal receipt before a realized loss is processed. The loss is then split pro rata between pending receipts and active tranche NAV, rather than first exhausting the BB position represented by the pending receipt. [1](#0-0) 

### Finding Description
`requestWithdraw` burns the requesting tranche position’s principal, mints an equal strategy-token receipt, and records only an aggregate pending amount; it does not preserve whether the receipt originated from AA or BB. [2](#0-1) 

During `stopEpochWithDuration`, `previewLossAdjustedWithdrawFunds` computes `pendingLoss = _lossAmount * pendingBasis / totalBasis` and leaves only the remainder as `activeLoss`. [3](#0-2)  The CDO then funds `pendingToFund`, burns `activeLoss`, and applies the active remainder through the ordinary BB-first waterfall. [4](#0-3) [5](#0-4) 

If the pending receipt was created from BB, its junior identity is lost. Consequently, BB principal that should absorb losses before AA is treated as an anonymous seniority-free claim, while active BB-first accounting can no longer identify it as junior capital. [6](#0-5) 

For example, with 100 NAV split into 50 AA and 50 BB, a BB holder requests withdrawal of all 50 BB during the running epoch. A subsequent realized loss of 40 should leave the BB receipt with only 10 and preserve AA at 50. Instead, the pending and active bases are equal, so 20 loss is assigned to pending receipts and 20 to active NAV; because the former BB NAV was removed when the request was made, the active 20 loss falls on AA. The BB receipt holder receives 30 instead of 10, shifting 20 of loss onto AA. [7](#0-6) [3](#0-2) 

### Impact Explanation
This breaks the senior/junior loss-waterfall invariant: pending BB claims can escape first-loss treatment and transfer loss to active AA holders or AA pending claims. [8](#0-7) 

In the 50 AA / 50 BB example, an honest realized loss of 40 produces a 20-unit economic transfer from AA claimants to the former BB holder. The vault remains globally funded after the haircut, but the remaining assets are paid according to the wrong claimant seniority, making senior recoveries lower than promised. [9](#0-8) 

### Likelihood Explanation
The attack only requires an unprivileged, KYC-passing BB holder to call `requestWithdraw` before an honest manager stops the epoch with a nonzero `_lossAmount`. [10](#0-9) [11](#0-10) 

No malicious owner, manager, borrower, guardian, or privileged action is required. The vulnerable state is reached during the normal running-epoch withdrawal flow, and the loss allocation is later executed by the existing stop-epoch path. [4](#0-3) 

The existing `Default` guard does not prevent this because the realized loss can remain below total basis while still exceeding the remaining active junior NAV after BB has moved into pending receipts. [12](#0-11) [8](#0-7) 

### Recommendation
Preserve tranche seniority for pending withdrawals, or prevent pending BB receipts from diluting first-loss allocation.

A robust fix is to record pending withdrawal basis separately by tranche, for example `pendingWithdrawsAA` and `pendingWithdrawsBB`, at request time. On a successful stop with `_lossAmount`, apply the loss in this order:

1. pending BB basis;
2. active BB basis;
3. pending AA basis;
4. active AA basis, subject to the intended receipt-versus-active ordering.

Store a separate recovery price per pending-tranche bucket, or otherwise store each receipt’s class and haircut, rather than using one aggregate `lossRecoveryPriceByEpoch`. [13](#0-12) 

If aggregate accounting must remain, pending withdrawals should continue to be represented internally by their original tranche NAV until their loss allocation is calculated.

### Proof of Concept
The following test uses the existing Foundry test-suite state and assumes `attacker` is already KYC-allowed. APR is set to zero so withdrawal interest does not obscure the loss allocation.

```solidity
function test_PendingBBWithdrawalEscapesJuniorLoss() external {
    address attacker = makeAddr("kyc_bb_attacker");
    address senior = makeAddr("kyc_aa_victim");

    uint256 amount = 50_000 * ONE_SCALE;

    // Honest setup: equal AA and BB exposure, no epoch yield.
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    depositAs(senior, amount, true);       // senior deposits AA
    depositAs(attacker, amount, false);    // attacker deposits BB
    _startEpochAndCheckPrices(0);

    // Attacker converts BB exposure into an anonymous pending receipt.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(BBtranche));

    uint256 loss = 40_000 * ONE_SCALE;
    uint256 duration = cdoEpoch.epochDuration();
    uint256 borrowerPayment =
        IdleCreditVault(address(strategy)).pendingWithdraws() -
        (loss / 2); // pendingLoss = 20 under equal bases

    deal(defaultUnderlying, borrower, borrowerPayment);
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Honest manager crystallizes a 40% loss.
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, duration, loss);

    // Correct BB-first result:
    // attacker receipt should be 10, senior AA should still have 50.
    //
    // Actual aggregate result:
    // pendingLoss = 40 * 50 / 100 = 20
    // attacker can claim 30, while active AA NAV is reduced to 30.
    assertEq(
        IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(1),
        0.5e18,
        "pending BB receipt only bore half the loss"
    );

    uint256 aaNav = cdoEpoch.lastNAVAA();
    assertApproxEqAbs(
        aaNav,
        30_000 * ONE_SCALE,
        2,
        "AA absorbed loss that should have hit pending BB first"
    );
}
```

This reproduces the invariant violation without relying on a malicious privileged role: the attacker performs only `depositBB` and `requestWithdraw`, while the honest manager performs the ordinary loss-bearing stop. [14](#0-13) [11](#0-10)

  /// @notice Preview how a realized stop-epoch loss is split between active LPs and pending receipts.
  /// @dev Without pending receipts, a loss cannot exceed its active basis. When pending receipts
  /// exist, all pending receipts share their aggregate portion of the loss pro rata because the
  /// pending bucket does not retain tranche identity. The remaining active loss is later applied
  /// by the CDO through its ordinary BB-first waterfall.
  /// @param _lossAmount realized loss amount
  /// @return pendingToFund amount of pending withdrawals that should be funded by the borrower
  /// @return activeLoss amount of loss that remains assigned to active LPs
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
