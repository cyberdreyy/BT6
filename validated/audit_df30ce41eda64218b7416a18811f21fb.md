### Title
Missing Zero EVM Recipient Address Validation Enables Permanent Token Burn in Bridge Transfer - (File: `crates/sui-framework/packages/bridge/sources/bridge.move`, `bridge/evm/contracts/SuiBridge.sol`)

### Summary
The Sui bridge's `send_token` (Move) and `_transferTokensFromVault` (Solidity) functions both lack zero address validation for the EVM recipient address. Any ordinary user can submit a bridge transfer specifying `0x0000000000000000000000000000000000000000` as the EVM recipient, causing bridged tokens to be permanently burned at `address(0)` on EVM.

### Finding Description
In `bridge.move`, `send_token` validates only that `target_address.length() == EVM_ADDRESS_LENGTH` (20 bytes) and `token_amount > 0`, but does not check whether those 20 bytes are all zeros:

```move
assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
assert!(token_amount > 0, ETokenValueIsZero);
// No check: target_address != x"0000000000000000000000000000000000000000"
``` [1](#0-0) 

The same gap exists in `send_token_v2`: [2](#0-1) 

In `SuiBridge.sol`, `_transferTokensFromVault` checks `tokenAddress != address(0)` (the token contract address) but does **not** check `recipientAddress != address(0)`:

```solidity
require(tokenAddress != address(0), "SuiBridge: Unsupported token");
// No check: require(recipientAddress != address(0), ...)
if (tokenID == BridgeUtils.ETH) {
    vault.transferETH(payable(recipientAddress), amount);
} else {
    vault.transferERC20(tokenAddress, recipientAddress, amount);
}
``` [3](#0-2) 

The same gap exists in `SuiBridgeV2._transferTokensFromVault`: [4](#0-3) 

The bridge committee signs any well-formed message (correct byte length, valid token ID, valid chain ID). A 20-byte all-zero EVM address passes every existing format check in `BridgeUtils.decodeTokenTransferPayload`, which only enforces `recipientAddressLength == 20`: [5](#0-4) 

Once the committee signs the message, `transferBridgedTokensWithSignatures` (callable by anyone) executes the vault transfer to `address(0)`, permanently burning the tokens. [6](#0-5) 

### Impact Explanation
Tokens transferred to `address(0)` on EVM are permanently unrecoverable:
- **ETH path**: `vault.transferETH(payable(address(0)), amount)` sends native ETH to the zero address — irretrievable.
- **ERC20 path**: `vault.transferERC20(tokenAddress, address(0), amount)` burns ERC20 tokens at the zero address — most ERC20 implementations permit this and the tokens are gone.

This constitutes **unintended permanent burning of bridged assets**, which falls under the "High or Medium: unintended permanent burning below the 10B cap" impact class in the allowed impact gate.

### Likelihood Explanation
Low-to-Medium. A user who accidentally provides a zero EVM address — through a UI bug, a copy-paste error, or a programmatic mistake — will permanently lose their bridged tokens with no recovery path. The bridge provides no warning, no revert, and no refund mechanism for this case. The `send_token` function on Sui accepts the call, burns the tokens on-chain, and the committee signs the resulting message without any zero-address gate.

### Recommendation
1. **`bridge.move` — `send_token` and `send_token_v2`**: Add an explicit zero-address check alongside the length check:
   ```move
   let zero_evm = vector::tabulate!(EVM_ADDRESS_LENGTH, |_| 0u8);
   assert!(target_address != zero_evm, EInvalidEvmAddress);
   ```
2. **`SuiBridge.sol` — `_transferTokensFromVault`**: Add a recipient zero-address guard:
   ```solidity
   require(recipientAddress != address(0), "SuiBridge: Invalid recipient address");
   ```
3. **`SuiBridge.sol` — `bridgeERC20` / `bridgeETH`**: Validate that the Sui-side `recipientAddress` bytes are not all zeros before accepting the deposit, mirroring the reverse direction.

### Proof of Concept
1. User calls `bridge::bridge::send_token` on Sui with `target_address = x"0000000000000000000000000000000000000000"` (20 zero bytes) and any supported token (e.g., 1 WBTC).
2. `send_token` passes all existing checks (`length == 20`, `amount > 0`), burns the token on Sui, and records a pending bridge message.
3. Bridge committee validators observe the on-chain event and sign the bridge message — no zero-address check exists in committee validation (`committee.verify_signatures` only verifies cryptographic signatures).
4. Anyone calls `SuiBridge.transferBridgedTokensWithSignatures` on EVM with the signed message.
5. `BridgeUtils.decodeTokenTransferPayload` decodes `recipientAddress` as `address(0)` — the 20-byte length check passes.
6. `_transferTokensFromVault` is called with `recipientAddress = address(0)`; `tokenAddress != address(0)` passes (the token contract is valid).
7. `vault.transferETH(payable(address(0)), amount)` or `vault.transferERC20(tokenAddress, address(0), amount)` executes — tokens are permanently burned.
8. `isTransferProcessed[nonce] = true` is set, making the burn irreversible even if the protocol is later patched.
