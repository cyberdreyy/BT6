### Title
`/debug/vars` (expvar) is reachable by any authenticated session user regardless of role, including View-role - ([File: core/web/router.go])

### Summary
`debugRoutes` mounts `expvar.Handler()` behind only `auth.Authenticate(..., auth.AuthenticateBySession)`, with no role-based wrapper (`RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole`) applied, unlike every other sensitive endpoint in `v2Routes`. Any user with a valid session cookie — including one created with `UserRoleView` — can therefore retrieve `expvar` output containing internal Go runtime/process variables (memstats, command-line args, and any custom-registered vars).

### Finding Description
`debugRoutes` is defined as: [1](#0-0) 
It wraps the group only with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)`, which validates the session cookie and sets the authenticated `User` in context, but performs no role check: [2](#0-1)  and [3](#0-2) .

By contrast, every other authv2 route that returns sensitive data is explicitly wrapped with `auth.RequiresRunRole`, `auth.RequiresEditRole`, or `auth.RequiresAdminRole`, e.g. `authv2.GET("/users", auth.RequiresAdminRole(uc.Index))` [4](#0-3) . Those wrappers check `user.Role` against `clsessions.UserRoleView/Run/Edit/Admin` and reject with 401/403 accordingly: [5](#0-4) . `debugRoutes` has no equivalent check, so any of the four defined roles — `admin`, `edit`, `run`, `view` (`core/sessions/user.go` lines 29-34) — passes through to `expvar.Handler()` unrestricted.

A user logging in with only View-role credentials via `POST /sessions` obtains a valid session cookie, and can then `GET /debug/vars` and receive a 200 response with the full expvar JSON dump (Go runtime memstats, GC stats, cmdline, and any app-registered counters), which is otherwise intended for privileged/operational access.

### Impact Explanation
This is an authorization-scope violation: a low-privilege View-role user obtains disclosure of internal Go runtime/process state that is not part of any documented View-role capability. While `expvar`'s default output does not include secrets by design, it can leak sensitive operational metadata (build/config command-line, GC/memory profiles, and any custom vars the application registers), aiding further reconnaissance/attacks, and constitutes exact-role authorization bypass since the invariant "authorization is exact per declared role" does not hold for this endpoint. This maps to Chainlink's "information disclosure through role/authorization bypass" impact class rather than a critical fund/key compromise.

### Likelihood Explanation
Very high feasibility: it requires only a legitimate View-role account (the lowest privilege role) or its session cookie — no special conditions, no admin, no misconfiguration. The request sequence is a single `GET /debug/vars` after standard session login, fully reproducible by a table test analogous to existing role-authorization tests for other endpoints (e.g. tests around `RequiresAdminRole`/`RequiresEditRole`).

### Recommendation
Wrap `debugRoutes`'s `/debug/vars` handler with an appropriate role check (e.g. `auth.RequiresAdminRole` or at minimum `auth.RequiresEditRole`), matching the pattern used for other sensitive `authv2` routes, so that View/Run-role sessions are rejected with 401/403.

### Proof of Concept
Go handler-level integration test plan (in `core/web/router_test.go` or similar):
1. Bootstrap the app/router via `NewRouter` (or existing test harness used for other route auth tests).
2. Create a user with `sessions.UserRoleView` and log in via `POST /sessions` to obtain a valid session cookie (reuse helpers used in existing session/auth tests, e.g. `cltest.MustCreateUser`/`cltest.CreateSessionRequest` or similar found in `core/web/*_test.go`).
3. Issue `GET /debug/vars` with the View-role session cookie attached.
4. Assert response status is `200 OK` and the body is valid JSON containing expvar keys such as `"cmdline"` and `"memstats"`.
5. As a regression guard, add a companion assertion that after applying the fix (role wrapper), the same request returns `401`/`403` for View-role sessions while still returning `200` for the intended privileged role.

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

	}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
