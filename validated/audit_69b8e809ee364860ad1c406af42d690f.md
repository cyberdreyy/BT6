### Title
Strict `>` boundary check in `get_tenure_last_block_info` treats an exactly-on-time signature as timed out - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::get_tenure_last_block_info` decides whether a tenure's last signed block is still "fresh" (and therefore still vetoes conflicting/lower proposals) using a strict `>` comparison against `get_epoch_time_secs()`. At the exact boundary second, the function falls into the "timed out" branch instead of the "still valid" branch, which is the same class of off-by-one boundary error as the reported `reclaimContract()`/`settleContract()` mismatch (one side uses `<`, the other `>`, and the edge case silently resolves toward the wrong branch instead of being covered by both).

### Finding Description
In `stacks-signer/src/chainstate/mod.rs`:
```rust
if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
    > get_epoch_time_secs()
{
    // The last accepted block is not timed out, return it
    Ok(Some(block_info))
} else {
    // The last accepted block is timed out
    ...
    Ok(None)
}
``` [1](#0-0) 

This is the sole gate the signer uses to decide whether it still remembers a signed tip for a tenure via `check_latest_block_in_tenure`, which calls `get_tenure_last_block_info` and, if it returns `None` (timed out), stops treating the tenure's previously signed block as a veto for competing/lower proposals: [2](#0-1) .

At exactly `signed_over_time + timeout == now`, the comparison evaluates false, and the code takes the "timed out" branch, returning `None`. Once `None` is returned, `check_latest_block_in_tenure` skips the "does this proposal build strictly higher" veto derived from the last signed block and falls through to comparing against the pre-commit and then the node's `get_tenure_tip` view instead.

This differs from the Sherlock report's exact mechanism (two separate functions with complementary strict inequalities creating a gap at the boundary), but the underlying bug class is the same: a single-second equality boundary is mis-assigned to the wrong branch of a "still valid" vs. "expired" decision, and this decision gates whether a previously signed block continues to protect against a conflicting/lower block proposal.

### Impact Explanation
Practically, this is a one-second race window, not a majority-controlled or attacker-controlled precise boundary: no external party can force `get_epoch_time_secs()` to equal `signed_over_time + timeout` to the exact second on demand, since `get_epoch_time_secs()` is the signer's local wall-clock read at evaluation time, not a value under an adversary's control. The consequence of hitting this window is that the signer momentarily treats its own already-signed tip as "timed out" one second earlier than the nominal timeout, falling back to the pre-commit and node-tip checks in `check_latest_block_in_tenure` rather than rejecting outright on the age of `block_info`. Because the subsequent checks (`get_last_accepted_block` pre-commit check, and the node's own `get_tenure_tip`, which itself enforces its independently-persisted canonical view) still run, this boundary tightening does not by itself let an invalid, non-canonical, or conflicting block get signed — it just shortens the "definitely still-valid" window by up to one second under an unlikely coincidence of timing.

### Likelihood Explanation
Low. It requires the miner's/attacker's competing proposal to be evaluated in the exact clock-second where `signed_over_time + tenure_last_block_proposal_timeout` equals the signer's `get_epoch_time_secs()`, which is not something a proposer can reliably engineer, and even when it happens the fallback logic (pre-commit + node's tenure tip) still protects the signer.

### Recommendation
Change the comparison in `get_tenure_last_block_info` to be inclusive of the boundary, matching the intended "not yet timed out at exactly the timeout second" semantics:
```rust
if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
    >= get_epoch_time_secs()
{
    Ok(Some(block_info))
} else {
    ...
    Ok(None)
}
``` [3](#0-2) 

### Proof of Concept
Not concretely reproducible without control over the signer's monotonic wall clock at the exact evaluation instant; the finding is a code-level boundary defect analogous to the reported bug class rather than a demonstrated exploit path, since downstream checks (pre-commit veto, node's own tenure tip) continue to guard against unsafe acceptance even when this boundary is hit.

        tenure_last_block_proposal_timeout: Duration,
        reorg_attempts_activity_timeout: Duration,

            tenure_id,
            signer_db,
            tenure_last_block_proposal_timeout,
        )?;

        if let Some(info) = last_block_info {
            // N.B. this block might not be the last globally accepted block across the network;
            // it's just the highest one in this tenure that we know about.  If this given block is
            // no higher than it, then it's definitely no higher than the last globally accepted
            // block across the network, so we can do an early rejection here.
            if block.header.chain_length <= info.block.header.chain_length {
                warn!(
                    "Miner's block proposal does not confirm as many blocks as we expect";
                    "proposed_block_consensus_hash" => %block.header.consensus_hash,
                    "signer_signature_hash" => %block.header.signer_signature_hash(),
                    "proposed_chain_length" => block.header.chain_length,
                    "expected_at_least" => info.block.header.chain_length + 1,
                );
                if info.signed_group.is_none_or(|signed_time| {
                    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
                }) {
                    // Note if there is no signed_group time, this is a locally accepted block (i.e. tenure_last_block_proposal_timeout has not been exceeded).
                    // Treat any attempt to reorg a locally accepted block as valid miner activity.
                    // If the call returns a globally accepted block, check its globally accepted time against a quarter of the block_proposal_timeout
                    // to give the miner some extra buffer time to wait for its chain tip to advance
                    // The miner may just be slow, so count this invalid block proposal towards valid miner activity.
                    if let Err(e) = signer_db.update_last_activity_time(
                        &block.header.consensus_hash,
                        get_epoch_time_secs(),
                    ) {
                        warn!("Failed to update last activity time: {e}");
                    }
                }
                return Ok(false);
            }
