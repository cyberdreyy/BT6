### Title
Default finalization keys instant-withdraw recovery to `epochNumber` while funded-claim fallback pays the same receipts at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records instant-withdraw receipts under the `epochNumber` at request time (`instantWithdrawsRequestsByEpoch[user][epochNumber]`), but both the default-recovery claim basis (`defaultPendingClaimBasis`) and the defaulted-claim clearing path (`_claimDefaultedInstantWithdrawRequest`) key the same receipts to `epochNumber`/`defaultRecoveryEpoch` at finalization time. Because `epochNumber` is incremented in `deposit()` during `stopEpoch`, an instant receipt made in epoch N and still unfunded when the borrower defaults in epoch N+1 is excluded from the recovery basis, never haircut, and then paid at par through `_transferFundedClaim` — mirroring the BLS bug where the same signature is validated under a different public key in the individual vs. aggregate check.

### Finding Description
In `requestInstantWithdraw` the receipt is booked per request epoch:

```solidity
uint256 currentEpoch = epochNumber;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```
(contracts/strategies/idle/IdleCreditVault.sol:367-374)

`epochNumber` is bumped inside `deposit()` whenever the epoch is running (i.e., during `stopEpoch`), lines 607-611. So a receipt created in epoch N keeps its per-epoch bucket at N even after the epoch rolls to N+1.

Default finalization, however, reads the *current* epoch:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
    basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```
(line 644-649) and `defaultRecoveryEpoch = epochNumber` (line 693). If the unfunded instant receipt was recorded in epoch N but finalization happens at epoch N+1, `instantWithdrawClaimsByEpoch[N+1]` is zero/stale, so the receipt contributes nothing to `totalBasis`, gets no share of `defaultRecoveryReserve`, and is not haircut by `defaultRecoveryPrice`.

The claim path compounds the inconsistency. `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest`, which only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — i.e., epoch N+1 — and returns 0 for this user. It then falls through to:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```
(lines 387-392) which pays the full face value of the receipt, unhaircutted, via `_transferFundedClaim`. `_transferFundedClaim` only protects `defaultRecoveryReserve` via a balance guard (lines 900-905); it does not verify the claim was actually funded by `collectInstantWithdrawFunds`, and it never decrements `pendingInstantWithdraws`.

### Impact Explanation
An unprivileged lender whose instant-withdraw receipt straddles an epoch boundary (request in epoch N, borrower defaults in epoch N+1 before `collectInstantWithdrawFunds` fully funds `pendingInstantWithdraws`) is paid 100% of face value while every other defaulted claimant — normal withdrawers, same-epoch instant withdrawers, and active AA/BB holders via the `defaultRecoveryPrice`/`defaultBBNav` multiplier — is haircut to `recoveryPrice`. The excess is drawn from strategy-held underlying that is not part of the isolated reserve, breaking the "one recovery multiplier for all receipt classes" invariant documented in `defaultPendingClaimBasis` and directly stealing from defaulted-epoch claimants and/or the CDO's remaining funded claims. Loss is quantified as `instantWithdrawsRequests[user] * (1 - defaultRecoveryPrice)` of unjustified par payout.

### Likelihood Explanation
Requires an instant-withdraw request left partially unfunded across a `stopEpoch` (pendingInstantWithdraws > 0) followed by a borrower default finalized in a later epoch — an ordinary sequence in stressed conditions, which is precisely when the recovery code path runs. No privileged misbehavior needed: the honest borrower simply fails to fully fund instant claims, the manager stops the epoch, and default is later declared. The attacker is just a tranche-token holder using the public request/claim UX.

### Recommendation
Make request recording, basis accounting, and claim clearing use one consistent epoch key, mirroring the fix applied in the BLS aggregator (both validation stages must use the same public key). Options: (a) on finalization, aggregate `instantWithdrawClaimsByEpoch` over all epochs with nonzero `pendingInstantWithdraws` rather than only `epochNumber`; (b) in `claimInstantWithdrawRequest`, revert (or route through the recovery path) whenever `defaultInstantWithdrawsFinalized` is true and any instant receipt remains, instead of falling through to `_transferFundedClaim`; and (c) have the funded-claim path verify `pendingInstantWithdraws`/funded-bucket consistency before paying at par.
