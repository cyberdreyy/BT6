### Title
Signer `BlockRejection`/`BlockAccepted` signatures do not cover `reason_code`/`response_data`, allowing the rejection reason to be forged in transit - ([File: libsigner/src/v0/messages.rs])

### Summary
A signer's `BlockRejection` (and `BlockAccepted`) message signature only commits to the `signer_signature_hash` of the block being voted on — not to the `reason`, `reason_code`, or `response_data` (which carries the `RejectReason`/`RejectReasonPrefix` used downstream for weighted-consensus decisions). Any party able to relay or re-inject a StackerDB chunk (a one-slot miner running its own relay, or any gossip participant) can therefore take an already-validly-signed rejection from a legitimate signer and swap in a different `reason_code`/`response_data.reject_reason` while the signature still verifies, because `verify()`/`recover_public_key()` only recompute the hash over `signer_signature_hash`.

### Finding Description
`BlockRejection::hash()` is defined as: [1](#0-0) 
It builds the signed digest solely from `self.signer_signature_hash` inside a `"block-rejection"` structured-data domain — the `reason`, `reason_code`, and `response_data` fields of `BlockRejection` are not part of the digest. `verify()` and `recover_public_key()` recompute exactly this same hash and check the signature against it: [2](#0-1) 

Meanwhile, on the wire, `reason`, `reason_code`, `signer_signature_hash`, `chain_id`, `signature`, `metadata`, and `response_data` are all serialized as independent fields: [3](#0-2) 

On receipt, `handle_block_rejection` recovers the public key, authenticates the signer against the known signer set, and then feeds the *unauthenticated* `response_data.reject_reason` directly into vote-tallying and threshold logic: [4](#0-3) 

That `RejectReasonPrefix` is stored per-signer (`add_block_rejection_signer_addr`, which forbids only a *later* differing reason from the *same signer_addr*, i.e. only the last one persists — it does not re-verify that the code matches an untampered original) and is used to compute per-reason weight, in particular the `ReorgNotAllowed` weight that flips `sortition_state.cur_sortition.miner_status` to `InvalidatedBeforeFirstBlock`: [5](#0-4) 

Because the signature never commits to `reason_code`/`response_data`, this is directly analogous to the reported Monero bug: a value that carries privileged, decision-changing semantics (`"(all)"` there, `ReorgNotAllowed`/`RejectReasonPrefix` here) travels through a path that treats it as trusted/authenticated (bound to a valid, checked signature) when it is in fact unauthenticated and freely substitutable in transit.

### Impact Explanation
This breaks the "signed vs. validated" equality that the rest of the protocol relies on: every signer that stores a rejection reason assumes that reason was actually asserted (and signed for) by the sending signer, when in fact only the block hash and signer identity are authenticated, not the reason. Concretely:
- A miner or gossip relay can rewrite a benign rejection (e.g. `ValidationFailed`) into `ReorgNotAllowed` without any signer key, nudging the 30% `ReorgNotAllowed`-weight computation toward incorrectly marking the current miner `InvalidatedBeforeFirstBlock` — a liveness/safety-relevant state change driven by forged data.
- Conversely, it can strip/relabel a genuine `ReorgNotAllowed` rejection into an innocuous reason, suppressing miner-invalidation that should have occurred, weakening the anti-reorg guard.
- Since `RejectReasonPrefix` also feeds `should_reevaluate_reject_reason`-style logic and per-reason weight tallies used across the signer set, this is a "rejection recounted"-class miscount: the recorded reason for a cryptographically-attested rejection can diverge from what the signer actually sent, corrupting any code path that branches on the specific reason rather than just "rejected/not rejected."

This qualifies as at least a High-severity signer safety/liveness issue: it corrupts the miner-invalidation decision (a chainstate-state-machine equality) using attacker-controlled, unauthenticated data riding on a validly-signed envelope, reachable by a single miner/relay with no majority and no signer key.

### Likelihood Explanation
Likelihood is moderate-to-high in the affected (pre-global-state, `v0`) protocol path: `store_and_process_block_rejection`'s `ReorgNotAllowed` branch is explicitly gated to run "only for active signer protocol versions < Global state activation," so it is exercised in mixed/legacy fleets. Exploitation requires only the ability to intercept/re-relay a StackerDB chunk containing a legitimately-signed `BlockRejection` (StackerDB chunk propagation is peer-to-peer gossip, not authenticated end-to-end for this sub-field) — no signer private key, no majority, and no consensus vote is needed to tamper with the `reason_code`/`response_data` bytes before the message reaches other signers.

### Recommendation
Include `reason_code`/`response_data` (and `chain_id`) in the signed digest for `BlockRejection` (and audit `BlockAccepted` similarly for any decision-relevant unsigned fields), e.g. by folding a hash/commitment of `response_data` and `reason_code` into the `"block-rejection"` structured-data message before signing, and reject messages whose reconstructed content hash doesn't match what was signed. Alternatively, sign over the full canonical serialization of the decision-relevant fields rather than just `signer_signature_hash`.

### Proof of Concept
1. Signer S validly rejects block B with `RejectReason::ValidationFailed(...)`, producing `BlockRejection { reason, reason_code: RejectCode::ValidationFailed(...), signer_signature_hash: H, signature: sig, response_data: { reject_reason: RejectReason::ValidationFailed(...), .. }, .. }` where `sig` is computed only from `H` per `hash()` (`libsigner/src/v0/messages.rs:1802-1807`).
2. A network relay/miner intercepts the StackerDB chunk before it reaches other signers and rewrites `reason_code`/`response_data.reject_reason` to `RejectReason::ReorgNotAllowed`, leaving `signer_signature_hash` and `signature` untouched.
3. Any receiving signer's `handle_block_rejection` calls `rejection.recover_public_key()`/implicit `verify()` against `H` and `sig`, which still succeeds because they never depended on `reason_code`/`response_data` (`libsigner/src/v0/messages.rs:1816-1836`).
4. The receiving signer stores the forged `ReorgNotAllowed` code via `store_and_process_block_rejection` → `add_block_rejection_signer_addr`, and if enough (attacker-relabeled) rejections accumulate past 30% weight, `sortition_state.cur_sortition.miner_status` is set to `InvalidatedBeforeFirstBlock` (`stacks-signer/src/v0/signer.rs:2295-2369`) — a state change driven by content the signer S never actually attested to.

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
