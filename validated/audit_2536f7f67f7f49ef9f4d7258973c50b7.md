### Title
Self-operated staking contracts allow an operator's beneficiary redirect to permanently divert the staker's own principal - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract.move` keys its `distribution_pool` (a single `pool_u64::Pool`) purely by `address`, without distinguishing between the "staker" role and the "operator" role. Neither `create_staking_contract_with_coins` nor `switch_operator` prevent `operator == staker_address`. When that happens, the staker's own principal/reward shares (added under `staker_address`) and the operator's commission shares (added under `operator`) collapse into the *same* pool entry. `distribute_internal`'s redirect check only compares raw addresses (`recipient == operator`), so once a beneficiary is set via `set_beneficiary_for_operator`, the *entire* merged balance - not just the commission slice - is permanently sent to the beneficiary instead of the staker.

### Finding Description
`create_staking_contract_with_coins` performs no check that `operator != signer::address_of(staker)`: <cite repo="Thankgod67Ikhide/aptos-core--019" path="aptos-move/framework/aptos-framework/sources/staking_contract.move" start="455="a" end="468" /> Likewise `switch_operator` only checks that the new operator doesn't already have a contract, never that `new_operator != staker_address`: [1](#0-0) 

`unlock_stake` records the staker's withdrawal under the key `staker_address` in the same `distribution_pool` that `request_commission_internal` uses to record the operator's commission under the key `operator`: [2](#0-1) [3](#0-2)  Because `pool_u64` share-accounting is keyed only by raw address, if `staker_address == operator`, both entries collapse into one shareholder record - all further reward accrual and share transfers apply to that single combined balance.

`set_beneficiary_for_operator` lets the operator address unconditionally redirect payouts, with no validation that it isn't also the staker: [4](#0-3) 

Finally, `distribute_internal` redeems each shareholder's full balance and, purely by address comparison, reroutes it to the beneficiary if the address matches `operator`: [5](#0-4)  Since the staker's principal share and the operator's commission share are merged under the identical key when `staker == operator`, this check can no longer distinguish "commission owed to operator" from "principal owed to staker" - the whole balance goes to the beneficiary.

This is the same class of bug as the report: two conceptually distinct roles (source/destination chain in the bridge; staker/operator here) are expected to be routed independently, but the code uses a single shared identifier space with no uniqueness check between them, so when the identifiers collide the routing logic can no longer tell them apart and misdirects value.

### Impact Explanation
When triggered, the staker's entire withdrawn principal and rewards - not merely the operator's commission - are non-recoverably sent to whatever address was last set via `set_beneficiary_for_operator`. This is a permanent, non-recoverable loss/redirection of a staker's own stake balance to a third-party beneficiary account, matching the "permanent lock or non-recoverable loss of claim rights" and "beneficiary payout ... credits the wrong account or traps value" impact categories.

### Likelihood Explanation
Self-staking configurations (`operator == staker`) are a plausible, unprivileged, legitimate usage pattern (e.g., a solo validator managing its own `staking_contract` for commission/beneficiary bookkeeping, or a staker who later calls `switch_operator` to move to self-management). No validation anywhere in `create_staking_contract_with_coins` or `switch_operator` rejects this configuration, so it requires no privilege escalation - just calling documented entry functions in an unguarded order (create/switch operator to self, then call `set_beneficiary_for_operator`, then `unlock_stake`/`distribute`).

### Recommendation
Add an explicit check in `create_staking_contract_with_coins` and `switch_operator` that `operator != signer::address_of(staker)` / `new_operator != staker_address`, since the protocol's distribution-pool accounting fundamentally assumes these are distinct addresses. Alternatively, make the `distribution_pool` role-aware (e.g., a tagged key or separate pools for principal vs. commission) instead of relying on raw address equality to distinguish staker payouts from operator commission.

### Proof of Concept
1. Staker `S` calls `staking_contract::create_staking_contract(S, operator = S, voter, amount, commission_percentage, seed)`. No assertion blocks `operator == S`. [6](#0-5) 
2. `S` (acting as operator) calls `set_beneficiary_for_operator(S, beneficiary_addr)`. [7](#0-6) 
3. `S` calls `unlock_stake(S, operator = S, amount)`, which calls `add_distribution(operator, staking_contract, staker_address, amount)` with `staker_address == operator == S`, buying shares for `S` in the shared `distribution_pool`. [2](#0-1) 
4. After the lockup expires, anyone calls `distribute(S, S)`. In `distribute_internal`, the shareholder entry for `S` equals `operator`, so the redirect fires and the *entire* redeemed amount (S's principal + any commission) is sent to `beneficiary_addr` instead of `S`. [5](#0-4)

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
