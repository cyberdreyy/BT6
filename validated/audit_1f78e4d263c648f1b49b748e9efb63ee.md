### Title
`BlockRejection`/`BlockAccepted` signature hash omits `reason`, `reason_code`, and `response_data`, allowing rejection metadata to be forged without invalidating the signer's signature - (`libsigner/src/v0/messages.rs`)

### Summary
`BlockRejection::hash()` computes the value that gets signed (and later verified/recovered) using **only** `self.signer_signature_hash` (plus `chain_id`, which is folded into the SIP-018 domain tuple). None of `reason`, `reason_code`, or `response_data` (which contains the structured `RejectReason`, `tenure_extend_timestamp`, `failed_txid`, etc.) is covered by the signature. [1](#0-0) 

### Finding Description
`BlockRejection::new` and `BlockRejection::from_validate_rejection` set `reason`, `reason_code`, and `response_data` from caller-supplied/attacker-influenceable data (e.g. a text `reason` string, and a `RejectReason` such as `ConsensusHashMismatch{expected, actual}` carrying two `ConsensusHash` values), then sign only a narrow hash of `signer_signature_hash` + `chain_id`: [2](#0-1) [3](#0-2) 

`verify()` and `recover_public_key()` both re-derive the same narrow `hash()` and check/recover against it: [4](#0-3) 

Because `reason`, `reason_code`, and `response_data` are excluded from the signed payload, any two `BlockRejection` messages that share the same `signer_signature_hash` and `chain_id` produce the **same signature bytes** as long as they were signed by the same key, and a signature originally produced over one `(reason, reason_code, response_data)` tuple remains a **valid** signature if that tuple is swapped for a different one before the message is consumed via `verify()`/`recover_public_key()`. This is the direct analog of the reported bug class: a piece of "metadata" (the "title/summary" analog — here `reason`/`reason_code`/`response_data`) is mishandled because it is trusted/rendered/consumed downstream without being bound to the same authentication check that covers the "real" payload (`signer_signature_hash`).

Concretely, this breaks the equality "signed vs. validated": a consumer that calls `BlockRejection::verify()` or `recover_public_key()` to authenticate *which signer* asserted *which reason/response_data* is not actually getting a binding between the identity and the reason/response_data — it only gets a binding between the identity and the `signer_signature_hash` + `chain_id`. Any relay/gossip hop, or a malicious signer itself, can splice a different `reason_code`/`response_data`/`reason` onto an otherwise-valid signature for the same block hash, and it will still `verify()` successfully and `recover_public_key()` to the same (real) signer address. Since `response_data.reject_reason` carries structurally significant fields like `ConsensusHashMismatch { expected, actual }` and `failed_txid`, this can misrepresent *why* a signer rejected a block while still cryptographically "proving" that signer rejected it — i.e. a rejection can be recounted/reinterpreted with attacker-chosen semantics attached to a legitimate signature.

The same construction issue exists for `BlockAccepted`, which is signed similarly (only over `signer_signature_hash`), meaning the acceptance signature is likewise not bound to `metadata`/`response_data` fields carried alongside it.

Note: the outer StackerDB chunk itself is separately signed by the sender's key (`chunk.sign(signer_private_key)` in `stacks-signer/src/client/stackerdb.rs`), which does cover the full serialized `SignerMessage` bytes. I was not able to fully verify, within the given iteration budget, whether every consumer of `BlockRejection`/`BlockAccepted` (test_observer event pipeline, `stackerdb_listener.rs` tally logic, cross-checks in `postblock_proposal.rs`) relies on the outer StackerDB chunk signature exclusively, or whether any path re-derives trust from the inner `BlockRejection::verify()`/`recover_public_key()` alone (e.g. when messages are relayed, replayed from disk, or reconstructed from `test_observer` events without the original StackerDB chunk envelope). If any consumer trusts the inner signature independent of the chunk envelope, the equivocation/miscount impact described above is directly exploitable by a one-slot signer or gossip relay.

### Impact Explanation
If any node/tooling path authenticates a `BlockRejection`/`BlockAccepted` via `verify()`/`recover_public_key()` alone (rather than solely trusting the outer signed StackerDB chunk), an attacker can attach a different `reason_code`/`response_data` (e.g., swap `ConsensusHashMismatch{expected, actual}` for a different pair, or change `failed_txid`) to a legitimately-signed rejection/acceptance without invalidating the signature. This is a "rejection recounted/reinterpreted" style issue matching the required Critical impact category (mischaracterizing the semantics of a counted vote while it remains cryptographically valid for the same signer and block hash).

### Likelihood Explanation
This requires no majority of signers and no access to any signer's private key — it only requires the ability to intercept/relay/replay a `BlockRejection`/`BlockAccepted` message and rewrite non-signed fields before it reaches a consumer, which is within the stated threat model (a single miner/relay/gossip actor). The severity is gated on whether a downstream consumer trusts the inner signature in isolation from the outer StackerDB chunk signature — this could not be conclusively confirmed against all consumers in the available time.

### Recommendation
Include `reason`, `reason_code`, and `response_data` (or a hash of their canonical serialization) inside the SIP-018 structured data that `BlockRejection::hash()` / the equivalent `BlockAccepted` hash covers, so that the signature binds the signer's identity to the full asserted content, not just the block hash and chain id. Apply the same fix to `BlockAccepted`.

### Proof of Concept
1. Construct `BlockRejection::new(hash, RejectReason::ConsensusHashMismatch{expected: A, actual: B}, key, mainnet, ts1, ts2)`, producing signature `S` (only over `hash` + `chain_id`, per `BlockRejection::hash()` at `libsigner/src/v0/messages.rs:1803-1807`).
2. Take the wire bytes of this `BlockRejection` and replace the `response_data.reject_reason` with `RejectReason::ConsensusHashMismatch{expected: C, actual: D}` (or swap `reason`/`reason_code`), leaving `signer_signature_hash`, `chain_id`, and `signature` unchanged.
3. Call `.verify(&signer_pubkey)` — it returns `Ok(true)`, and `.recover_public_key()` still recovers the original signer's key, because `hash()` never incorporated the altered fields.
4. Any consumer that trusts `verify()`/`recover_public_key()` in isolation now believes the signer asserted the *tampered* reason/metadata with full cryptographic authenticity.

    /// The signature hash for the block rejection
    pub fn hash(&self) -> Sha256Sum {
        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
        structured_data_message_hash(data, domain_tuple)
    }

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
