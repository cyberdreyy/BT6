### Title
APR0 withdraw-request interest is never accrued when the epoch ends via default or pool close instead of a normal `stopEpoch` interest settlement - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
In the Carapace report, premium accrual was conditioned on a lending-pool payment occurring *after* the protection start, with no fallback when the pool defaulted first, so premium stayed booked in `totalPremium` but was never released. The same "accrual gated on a later settlement event" pattern exists in `IdleCreditVault`: interest owed to APR=0 withdraw requesters is only materialized inside `prepareStopEpochWithApr0`, which writes `apr0RateByEpoch[epochNumber]`. If the epoch terminates without that call producing a real override interest (`_interest <= 1`, i.e. the pool-close sentinel, or the epoch ends in borrower default/finalization), the per-epoch rate stays 0 forever and every APR0 request for that epoch permanently loses its interest, while normal withdraw receipts embed interest in their claim basis regardless.

### Finding Description
`requestWithdraw` routes APR=0 requests into `_requestWithdrawApr0`, which buckets `apr0Users[_user].principal` under `principalEpoch = epochNumber` and accumulates `apr0TotalPrincipal` (`contracts/strategies/idle/IdleCreditVault.sol:285-294, 567-577`). Unlike normal requests — where `_amount` minted to the user already includes the epoch's interest — APR0 requests accrue interest only lazily:

- `prepareStopEpochWithApr0` computes the pro-rata interest and stores `apr0RateByEpoch[epochNumber]` only inside `if (_expInterest > 1 && _expInterest > _pendingFees)` (lines 513-537). The `_interest == 1` "request all funds back" close-pool sentinel skips this entirely.
- `_settleApr0` and `_withdrawClaimAmountsForEpoch` both read `apr0RateByEpoch[_reqEpoch]` and silently treat a missing rate as zero interest (lines 558-562, 873-877). There is no expiration/default fallback equivalent to "accrue anyway at expiry".

Consequences:

1. **Close-pool path**: `stopEpoch(…, _expectedInterest = 1)` sets `epochEndDate = 0`. `_claimFundedWithdrawRequest` then allows immediate claims (the `epochEndDate() != 0` gate at line 326 is bypassed), and the comment at lines 334-336 explicitly notes `_settleApr0` "can still skip settlement for the current request epoch". APR0 users recover `settledPrincipal + principal` but `settledInterest` is 0 because no rate was ever written. The undistributed interest share instead accrues to remaining active tranche holders via the epoch pricing.
2. **Default path**: when the borrower defaults and `finalizeDefaultRecovery` runs without a prior successful `prepareStopEpochWithApr0` writing a rate, `_withdrawClaimAmountsForEpoch` returns `apr0InterestAmount = 0`, so the APR0 requester's claim basis into `defaultRecoveryReserve` excludes interest while a normal requester's `withdrawsRequestsByEpoch` basis already includes it (lines 679, 865-880). The same reserve is therefore distributed pro-rata against a smaller basis for APR0 users — a permanent loss of unclaimed yield relative to identical-timed normal requests.

### Impact Explanation
Permanent loss of unclaimed yield for a whole user class. Any lender whose withdraw request was booked while `unscaledApr == 0` forfeits the entire epoch interest that a normal requester in the same epoch keeps in claim basis. On default finalization this is a concrete transfer: `defaultRecoveryReserve` is fixed, and APR0 claimants' basis is understated by `principal * missingRate / 1e18`, so their haircut is proportionally deeper than other receipt holders'. On pool close the forgone interest is instead absorbed by active LPs. The loss equals the APR0 pro-rata share of realized epoch interest that `prepareStopEpochWithApr0` would have allocated — up to the full interest attributable to `apr0TotalPrincipal` for that epoch.

### Likelihood Explanation
Requires only honest privileged actions around unprivileged user positions: a borrower default or a manager-initiated pool close during an epoch that has open APR0 withdraw requests. APR=0 epochs are an explicitly supported mode (programmable-borrower deployments run APR=0 per line 662-663 of `IdleCDOEpochVariant.sol`), so the precondition `unscaledApr == 0` at request time is routine. No malicious actor is needed; the accrual simply never fires because the only code path that writes `apr0RateByEpoch` is skipped.

### Recommendation
Mirror the external fix ("check expiration and proceed anyway"): write `apr0RateByEpoch[epochNumber]` (or an equivalent settled-interest figure) on every epoch-terminating path, not just inside the `_expInterest > 1` branch of `prepareStopEpochWithApr0`. Specifically, allocate APR0 interest from the realized/default interest basis in the close-pool sentinel path and in the default finalization flow (`finalizeDefaultRecovery` / the CDO's `_handleBorrowerDefault`), so APR0 receipts carry the same claim-basis interest semantics as normal `withdrawsRequestsByEpoch` receipts.

### Proof of Concept
A reproducible Foundry fork PoC would: (1) configure a credit vault epoch with `unscaledApr = 0`; (2) have two KYC'd lenders request withdrawal in the same epoch, one normal-path and one while APR=0 so it lands in `apr0Users`; (3) warp past `epochEndDate` and trigger either `stopEpoch(0, 1)` (close pool) or borrower default followed by `finalizeDefaultRecovery`; (4) claim via `claimWithdrawRequest` for both users and assert the APR0 user's payout equals principal only (`apr0RateByEpoch[reqEpoch] == 0` ⇒ `settledInterest == 0` / `apr0InterestAmount == 0`), while the normal user's payout/recovery basis includes epoch interest. I was unable to fully trace the IdleCDO-side ordering of `prepareStopEpochWithApr0` vs `_handleBorrowerDefault` within the available iterations, so the PoC should also confirm whether `prepareStopEpochWithApr0` is invoked (and thus the rate written) before default finalization on every default path; if it is always invoked on default, the close-pool path (1) remains the confirmed gap.

**Uncertainty note**: if the CDO unconditionally calls `prepareStopEpochWithApr0` before default finalization, the default leg narrows to the close-pool sentinel case only; conversely if default bypasses it, both legs hold. Either way the missing fallback in `_settleApr0`/`_withdrawClaimAmountsForEpoch` is verifiable directly.
