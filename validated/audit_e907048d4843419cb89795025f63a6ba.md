## Analysis

I found a valid analog in `multisig2/src/lib.rs`. The custody binding that should hold is: **confirmations counted toward `num_confirmations` must come from members who are still in the live `members` set at the moment the threshold is evaluated**. This mirrors the reported bug class — a claim (recorded confirmation) diverging from the actual authorization state (current membership) — the same "recorded vs. actual" mismatch described in the FraxLend/SiloGateway report, but here applied to multisig authorization instead of collateral custody.

### Root cause

`add_member`/`delete_member` register or remove a `MultisigMember` in `self.members` [1](#0-0) . `confirm()` inserts `member.to_string()` into the `confirmations` set for a request and compares the set length against `self.num_confirmations` to decide whether to execute [2](#0-1) . Crucially, once a confirmation string is stored in the `HashSet<String>` for a request, it is never revalidated against the current `members` set on subsequent `confirm()` calls — `confirm()` only checks whether the *new* caller is a current member via `current_member()` (through `assert_valid_request`) [3](#0-2) ; it does not re-check that the *previously stored* confirmations still belong to current members.

`delete_member` only purges confirmations for requests where `r.member == member` (i.e., requests *originated* by that member) [4](#0-3) . It does not scan the `confirmations` map to strip that member's string out of confirmation sets on *other* pending requests that member had merely confirmed (not authored). Those stale confirmation strings remain counted in `confirmations.len()` for the purposes of the `>= self.num_confirmations` check in `confirm()`.

### Break in the binding

Binding that should hold: `num_confirmations` valid, live confirmations ≥ `self.num_confirmations` ⇒ request executes.
What actually holds: `confirmations.len()` (including possibly-stale entries from now-removed members) ≥ `self.num_confirmations` ⇒ request executes — i.e., a threshold satisfied partly by confirmations from accounts/keys that are no longer members can still authorize execution, including a `Transfer` action that moves NEAR out of the multisig account.

### Scenario
1. Multisig with members `{A, B, C}` and `num_confirmations = 2`.
2. `A` calls `add_request` to create a `Transfer` request; `B` calls `confirm` — confirmations = `{B}` (1 of 2), request stays pending.
3. Members vote to `DeleteMember { member: B }` via a separate fully-confirmed request. `delete_member` removes `B` from `self.members` and revokes `B`'s access key if key-based, but does **not** touch the confirmation entry `{B}` already stored against the pending Transfer request, because that request was authored by `A`, not `B` [4](#0-3) .
4. `C` later calls `confirm` on the pending Transfer request. `confirmations.len()` is `1` (`{B}`) `+ 1` (adding `C`) `= 2 >= num_confirmations`, so `execute_request` fires and the transfer executes — authorized in effect by only one currently-live member (`C`) plus a stale confirmation from the removed member `B`.

This demonstrates confirmations counted diverging from live members, letting a `Transfer` (or `FunctionCall`, `AddKey`, etc.) execute below the intended live-member threshold — a multisig request executed below threshold, matching the Critical impact category in scope.

### Title
Stale confirmations from removed multisig members count toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts previously stored confirmation entries toward `num_confirmations` without verifying those confirming members are still present in the live `members` set. `delete_member` only removes confirmations for requests *authored* by the removed member, not confirmations that member cast on other pending requests. As a result, a request can execute using a mix of stale (removed-member) and live confirmations that together reach the threshold, even though the number of currently authorized members that actually confirmed is below `num_confirmations`.

### Finding Description
`confirm()` reads `self.confirmations.get(&request_id)`, checks the calling member hasn't already confirmed, and if `confirmations.len() + 1 >= self.num_confirmations`, executes the request [5](#0-4) . Nothing in this path filters out entries in the `HashSet<String>` that belong to accounts/keys no longer in `self.members`. `delete_member()` cleans up `requests`/`confirmations` only for requests where `r.member == member`, i.e., requests the removed member originated, and clears `num_requests_pk` for that member — but any confirmation strings the removed member added to *other* members' requests remain in the `confirmations` map untouched [6](#0-5) . `assert_valid_request()` (called at the top of `confirm`) validates the *current caller* is a member, but performs no re-validation of previously accumulated confirmations [3](#0-2) .

### Impact Explanation
This lets a request (including `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`) execute with fewer live, currently-authorized confirmations than `num_confirmations` mandates, because stale confirmations from removed members still count. This is a multisig request executed below threshold — funds can move (or keys/contract code can change) without the intended quorum of *current* signers, directly matching the Critical impact category ("a multisig request executed below threshold").

### Likelihood Explanation
The precondition is a normal governance action (removing/rotating a member while a Transfer or other request is pending confirmation from someone other than the request author) — a routine operational sequence, not an edge case requiring privileged or malicious behavior beyond normal member turnover. Any of the remaining members completing confirmation afterward triggers the issue; no attacker-controlled deployment or foundation misconfiguration is required.

### Recommendation
When executing `delete_member`, iterate all pending `requests`/`confirmations` (not just those authored by the removed member) and strip the removed member's entry from every confirmation set; alternatively, at `confirm()` time, filter `confirmations` against `self.members` before comparing to `num_confirmations`, e.g. `confirmations.iter().filter(|m| self.members.contains(...)).count()`.

### Proof of Concept
1. `MultiSigContract::new([A, B, C], 2)`.
2. As `A`: `add_request(Transfer{amount})` → `request_id`.
3. As `B`: `confirm(request_id)` → confirmations = `{B}`, len 1 < 2, request stays pending.
4. Via a separately fully-confirmed request, execute `DeleteMember{member: B}` → `self.members = {A, C}`; `confirmations` map for `request_id` is untouched (still `{B}`) because that map entry belongs to a request authored by `A`, not `B` [4](#0-3) .
5. As `C`: `confirm(request_id)` → `confirmations.len() (1) + 1 = 2 >= num_confirmations (2)` → `execute_request` runs the `Transfer`, moving funds out of the multisig even though only `C` (one live member) plus one stale, no-longer-authorized entry (`B`) contributed to the count.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Add member to the list. Adds access key if member is key based.
    fn add_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        self.members.insert(&member.clone().into());
        match member {
            MultisigMember::AccessKey { public_key } => promise.add_access_key(
                public_key.into(),
                DEFAULT_ALLOWANCE,
                env::current_account_id(),
                MULTISIG_METHOD_NAMES.to_string(),
            ),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
