### Title
ERC4626 liquidity failures bypass epoch-default handling and can indefinitely freeze programmable-credit withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
In programmable-borrower mode, `IdleCDOEpochVariant._stopEpoch` treats an external ERC4626 withdrawal failure as a fully retryable hook revert rather than recording a failed settlement or entering borrower-default handling. [1](#0-0)  `ProgrammableBorrower.onStopEpoch` separately checks economic vault coverage through `_currentVaultAssets()`, but a covered withdrawal can still fail because ERC4626 `maxWithdraw` liquidity may be lower than `convertToAssets`. [2](#0-1)  An unprivileged user of that ERC4626 vault can exhaust its immediately withdrawable liquidity before the honest manager calls `stopEpoch`, causing every settlement attempt to revert while `isEpochRunning` remains true and `defaulted` remains false. [3](#0-2) 

### Finding Description
`ProgrammableBorrower` keeps idle facility capital in a configured ERC4626 vault and tracks that position as part of the revolving-credit facility. [4](#0-3)  At epoch end, `IdleCDOEpochVariant._stopEpoch` calls `onStopEpoch` before attempting to pull the required underlying amount from the programmable borrower. [5](#0-4) 

When the programmable borrower lacks enough cash, `onStopEpoch` compares the shortfall against `_currentVaultAssets()` and calls `vault.withdraw` when the shares appear economically sufficient. [6](#0-5)  If the ERC4626 vault rejects that withdrawal because current liquidity is unavailable, the catch block reverts `StopEpochVaultLiquidityUnavailable`. [7](#0-6) 

That revert occurs before the CDO’s `try this.getFundsFromBorrower` block and therefore bypasses both failure paths that call `_handleBorrowerDefault`. [5](#0-4)  The only alternative default trigger is the later catch around `getFundsFromBorrower`, which is unreachable while the hook itself reverts. [8](#0-7) 

Because the entire transaction rolls back, no failed-settlement counter, default flag, epoch advancement, or other terminal state is recorded. [9](#0-8)  A normal ERC4626 vault can validly report sufficient share value while limiting current withdrawals, so the availability check and the withdrawal operation represent inconsistent external “stores” analogous to the inaccessible-secondary-store failure in CVE-2024-6832. [2](#0-1) 

### Impact Explanation
An unprivileged ERC4626 vault participant can drain the vault’s immediately available underlying liquidity while leaving the programmable borrower’s shares economically valued above the required shortfall. [2](#0-1)  The manager’s subsequent `stopEpoch` call then reverts instead of defaulting or completing settlement. [1](#0-0) 

While this persists, the credit vault remains in the running epoch: deposits are paused, AA/BB withdrawal-request flags remain disabled, and pending withdrawal receipts cannot be funded through the normal stop flow. [3](#0-2)  For a facility holding `V` underlying and owing `W` pending withdrawals, the attacker can temporarily freeze up to `V` of facility assets and leave `W` of matured withdrawal claims unpaid for as long as ERC4626 liquidity remains unavailable. [10](#0-9) 

The privileged emergency exit does not guarantee recovery because it also depends on a successful external `vault.redeem`. [11](#0-10) 

### Likelihood Explanation
The attacker does not need any privileged Idle role; being an ordinary liquidity provider or authorized user of the configured ERC4626 vault is enough to remove its available liquidity. [12](#0-11)  The condition is particularly likely for ERC4626 lending or credit vaults where `totalAssets`/`convertToAssets` includes illiquid claims but current withdrawals are limited by cash reserves. [13](#0-12) 

The attacker only needs to sequence their external-vault withdrawal before the honest owner or manager calls `stopEpoch`; `stopEpoch` itself remains restricted and is not called by the attacker. [14](#0-13)  No oracle manipulation, borrower misbehavior, privileged compromise, or contract redeployment is required. [15](#0-14) 

### Recommendation
Do not let a covered ERC4626 withdrawal failure remain an unrecorded, indefinitely repeatable revert outside the default path. [7](#0-6)  Either return `false` from `onStopEpoch` so `IdleCDOEpochVariant` executes `_handleBorrowerDefault`, or persist a failed-settlement counter/timestamp and allow settlement to transition to default after a bounded number of liquidity failures. [1](#0-0) 

The availability check should also use `vault.maxWithdraw(address(this))` or an equivalent executable-liquidity measure rather than only comparing the shortfall with `convertToAssets`. [2](#0-1)  If transient vault outages must remain retryable, store the retry state so repeated failures eventually trigger an explicit terminal path instead of leaving the epoch open indefinitely. [16](#0-15) 

### Proof of Concept
The following Foundry fork PoC demonstrates the state-freezing sequence against a deployed programmable-borrower credit vault whose configured ERC4626 vault has illiquid accounted assets but insufficient current withdrawal liquidity.

```solidity
// test/foundry/ProgrammableBorrowerVaultLiquidityFreeze.t.sol
function test_vaultLiquidityFailureBypassesDefaultAndFreezesEpoch() public {
    // Existing fork fixture/deployed revolving-credit instance.
    // externalVault is the ERC4626 configured on programmableBorrower.
    uint256 required = strategy.pendingWithdraws();
    assertGt(required, 0);

    // The attacker is only an external ERC4626 vault shareholder.
    // They redeem enough external-vault shares to exhaust its current cash.
    vm.prank(externalVaultUser);
    externalVault.redeem(
        externalVault.balanceOf(externalVaultUser),
        externalVaultUser,
        externalVaultUser
    );

    // The programmable borrower's shares still economically cover the shortfall,
    // but its executable withdrawal limit is too low.
    uint256 pbShares = externalVault.balanceOf(address(programmableBorrower));
    assertGe(externalVault.convertToAssets(pbShares), required);
    assertLt(externalVault.maxWithdraw(address(programmableBorrower)), required);

    vm.warp(cdo.epochEndDate());

    // Every honest manager retry takes the hook-revert path rather than defaulting.
    for (uint256 i; i < 3; ++i) {
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdo.stopEpoch(0, 0);

        assertTrue(cdo.isEpochRunning());
        assertFalse(cdo.defaulted());
        assertTrue(cdo.paused());
        assertFalse(cdo.allowAAWithdrawRequest());
        assertFalse(cdo.allowBBWithdrawRequest());
    }

    // Pending withdrawal receipts remain unfunded.
    assertEq(strategy.pendingWithdraws(), required);
}
```

The key reproduced condition is `convertToAssets(pbShares) >= required` while `maxWithdraw(programmableBorrower) < required`; this is valid ERC4626 behavior when share value is backed by illiquid positions. [2](#0-1)  Each `stopEpoch` call reverts before `getFundsFromBorrower`, so the catch that would call `_handleBorrowerDefault` is never reached. [5](#0-4)
