### Title
Multisig confirmation count includes stale confirmations from removed keys/members, allowing request execution below the live-member threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
The multisig `confirm()` flow counts entries in the per-request `confirmations` set against `num_confirmations` without verifying that every counted confirmer is still an active key/member. When a key (or member) is removed via `DeleteKey`/`DeleteMember`, the cleanup logic only purges requests that key *originally authored*, not confirmations that key left on *other* still-pending requests. A stale confirmation from a since-removed key therefore continues to count toward the threshold, letting a request execute with fewer live approvals than `num_confirmations` requires.

### Finding Description
In `confirm()`, the number of confirmations is compared directly against `self.num_confirmations`: [1](#0-0) 

`assert_valid_request()` only checks that the *caller* is a valid signer and that the request/confirmations map entries exist — it never re-validates that the confirmers already recorded in the `confirmations` set are still live keys: [2](#0-1) 

When a key is removed via the `DeleteKey` action, cleanup only removes requests whose `signer_pk` (the request's *author*) matches the deleted key. It never scans other requests' `confirmations` entries to strip out that key's stale approval: [3](#0-2) 

The same pattern exists in `multisig2`, where `delete_member()` only removes requests authored by (`r.member == member`) the deleted member, leaving that member's confirmations on other pending requests untouched: [4](#0-3) [5](#0-4) 

This is structurally the same class of bug as the referenced RANGE.sol/Operator.sol issue: a count/threshold check (`_status.high.count >= config_.regenThreshold` vs. `confirmations.len() + 1 >= self.num_confirmations`) that is evaluated against stale accumulated state instead of the live, currently-valid state (current price vs. wall / active members vs. all recorded confirmers). Neither system re-derives the check from ground truth at trigger time.

### Impact Explanation
This breaks the fundamental K-of-N custody guarantee: `live confirmations required == num_confirmations`. A pending request can be executed (including `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`) with strictly fewer than `num_confirmations` *currently valid* approvals, because a removed key's leftover confirmation is still tallied. This matches the Critical impact category "a multisig request executed below threshold," and directly enables unauthorized transfer of NEAR held by the multisig account.

### Likelihood Explanation
The precondition is a normal, expected multisig lifecycle event — rotating out a compromised or departing key/member via `DeleteKey`/`DeleteMember` while other requests are still pending confirmation. This is not an edge case requiring unusual parameterization; any multisig that both (a) has outstanding unconfirmed requests and (b) rotates a key that had already confirmed one of them will have a stale confirmation silently retained, lowering the effective threshold for that request without anyone noticing (no error, no log distinguishing stale vs. live confirmations).

### Recommendation
When removing a key/member (`DeleteKey`/`DeleteMember`), iterate over all entries in `confirmations` (not just requests authored by that key) and remove the deleted key/member from each confirmation set, recomputing whether removal now under-fills the threshold. Alternatively, when confirming a request, filter the stored confirmation set to only currently valid keys/members before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy multisig with `num_confirmations = 3` and keys `{A, B, C, D}`.
2. Key `A` calls `add_request_and_confirm(R)` for a malicious `Transfer` request — `confirmations(R) = {A}`.
3. Key `B` calls `confirm(R)` — `confirmations(R) = {A, B}`, count = 2, below threshold, request stays pending.
4. Through a separate, unrelated, legitimately-passed multisig request, key `B` is removed via `DeleteKey { public_key: B }` (e.g. employee off-boarding). Per `execute_request`'s `DeleteKey` branch (`multisig/src/lib.rs:198-216`), only requests where `signer_pk == B` are purged; `R` (authored by `A`) is untouched, so `confirmations(R)` still contains `B`.
5. Key `C` (a live key) calls `confirm(R)`. `confirmations(R).len() + 1 == 3 >= num_confirmations`, so `execute_request(R)` fires — the `Transfer` executes with only `A` and `C` as truly live approvers, one short of the intended 3-of-4 threshold, because `B`'s stale confirmation was still counted.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
