## Title
`check_parent_tenure_choice` reorg-timing gate silently defaults to "permit reorg" on saturating-subtraction underflow - ([File: stacks-signer/src/chainstate/mod.rs])

## Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to reorg a previously-mined tenure. A reorg is only supposed to be permitted when the reorged tenure produced its first (and only) block "poorly timed" — i.e. very close to the next burn block. That recency test is computed with `saturating_sub`, which silently clamps to `0` whenever the two timestamps are out of the order the code assumes, and `0` always satisfies the "close enough" comparison. This lets the timing gate be bypassed and a legitimately-timed, already-approved/globally-accepted tenure block get superseded — the equivalent of the Teller bug where a grace-period subtraction was computed incorrectly and let a privileged action (seizing collateral / here, permitting a chain reorg and revoking signature protection) fire when it should not have. [1](#0-0) 

## Finding Description
`check_parent_tenure_choice` walks each tenure that would be reorged away and, for tenures that mined exactly one block, computes how close that block's local approval time was to the arrival of the sortition that reorgs it:

```rust
let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
    sortition_state_received_time.saturating_sub(approved_at)
} else {
    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
    0
};
if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
    // ... permit / supersede the reorg
}
``` [1](#0-0) 

The code assumes `sortition_state_received_time >= approved_at` (i.e. the reorging sortition always arrives after the reorged block's local approval). `saturating_sub` was chosen specifically to avoid a panic on unsigned underflow if that assumption is violated, but the substitute value it produces — `0` — is not a "safe" default: `Duration::from_secs(0) < first_proposal_burn_block_timing` is always true (for any nonzero timeout), so any inversion of the two timestamps is silently treated as "proposed suspiciously close to the burn transition" and the reorg is unconditionally allowed, exactly the branch that should be reserved for genuinely poorly-timed tenures.

`sortition_state_received_time` and `approved_at` come from two independent local records — `SignerDb::get_burn_block_receive_time` (stamped when the burn event is processed) and the reorged tenure's `local_block_info.approved_time` (stamped when that block was locally pre-committed/accepted) — recorded at different points in the event pipeline, under signer restart/backfill, event-processing delay, or clock skew between when these two independent code paths run. There is no invariant anywhere enforcing `received_time >= approved_time`; the function simply assumes it holds.

If it doesn't hold (e.g., the burn-block event is processed and its receive time persisted before the previous tenure's block approval time gets written back, which can happen when a signer restarts and replays/reorders processing of buffered burn and block-validation events), the "greater than one globally accepted block" guard is the only remaining protection — but that guard only blocks reorgs of tenures with **more than one** globally accepted block, not tenures with exactly one legitimately-timed, well-formed accepted block. For the single-block case, the timing check is the only line of defense, and it is defeated by this underflow-to-zero behavior.

## Impact Explanation
This breaks the "approved vs canonical" equality that the reorg-permission logic is meant to enforce: a tenure that mined and had a block *legitimately* (not close to the burn transition) globally/locally accepted can be wrongly marked as `superseded` (`mark_tenure_superseded`), meaning the signer's own prior signature over that block will no longer be treated as a conflict blocking the replacement (`reorg_permit_stands`, see `docs/signer-flows.md` sections 5 and 8). This is precisely the class of Critical impact called out in the rules — a signer ends up voting to accept a conflicting/non-canonical block replacing one it already signed, because the safety check that should have refused the reorg was bypassed by an arithmetic edge case rather than by a legitimate close-timing scenario.

## Likelihood Explanation
Triggering the underflow does not require a majority of signers or another signer's key — a single signer's own local bookkeeping (receive-time vs approved-time ordering) can misbehave under ordinary operational conditions (restart with buffered/backlogged burn-block and block-validation events, or clock skew between the two write paths), and a one-slot miner's ordinary tenure-reorg attempt (winning the next sortition and building off a different parent) is exactly the trigger path that exercises this code. This is lower likelihood than a guaranteed bypass (it requires the specific timestamp inversion), but it is reachable without any privileged access, a majority, or another signer's key, and the manifestation (a Critical safety-equality break) matches the impact bar in the rules.

## Recommendation
Replace the `saturating_sub` with a checked computation that treats an inverted timestamp order as an explicit error/`ConnectivityIssues`-style rejection (refuse the reorg, the conservative choice) rather than silently mapping it to `0` (the permissive choice). At minimum, log and refuse to permit the reorg when `approved_at > sortition_state_received_time`, since that ordering indicates the local records are unreliable and the timing test cannot be trusted either way — mirroring the "we did not sign over the reorged tenure's block" defensive branch that already exists nearby, but for the inverted-clock case instead of defaulting to "poorly timed / permit".

## Proof of Concept
Exact reproduction requires forcing `local_block_info.approved_time` to be recorded after `sortition_state_received_time` for the reorged tenure, which is a timing/ordering condition in signer event processing (e.g., replay of buffered `NewBurnBlock` and validation-response events across a signer restart) rather than a single deterministic function call; the existing unit tests exercise the intended-order path (`check_parent_tenure_choice_reorg_timing_bad` / `_ok` in `stacks-signer/src/chainstate/tests/v2.rs`) but do not cover the inverted-timestamp case, so I could not confirm from the indexed test files whether this inversion is reachable in practice within the current event-processing code, only that the arithmetic itself provides no protection against it if it occurs.
