Based on my research, I found a strong structural analog to the ERC721 "accrued interest never settled" bug class in the Agave vote program's SIMD-0123 (block revenue sharing) implementation, specifically around the `pending_delegator_rewards` field.

### Title
Non-decrementing `pending_delegator_rewards` balance allows repeated/unbounded distribution of the same deposited reward pool across multiple epochs - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs, programs/vote/src/vote_state/mod.rs)

### Summary
The vote program tracks delegator block-revenue rewards in a `pending_delegator_rewards` field on `VoteStateV4`, which is incremented 1:1 whenever any signer deposits lamports via the `DepositDelegatorRewards` instruction [1](#0-0) . Each rewarded epoch, `calculate_block_reward` computes each delegated stake's proportional share of this same `pending_delegator_rewards` value and pays it out, capping any single stake's share at the pool total [2](#0-1) . However, I could not find any code path that decrements or zeroes `pending_delegator_rewards` after it has been distributed — a repo-wide search for subtraction of this field returned no matches, and the only field mutation is the `checked_add` in `add_pending_delegator_rewards` [3](#0-2) . The only place the field goes to zero is a manual test-only assignment or the `withdraw` guard that blocks closing the account while it's non-zero [4](#0-3) .

### Finding Description
This mirrors the reported bug class exactly: a value meant to represent "amount owed/available to be claimed" is computed and paid out from, but the source-of-truth balance backing it is never reduced by the amount actually distributed. In the ERC721 market, `interestAccrued` grew without bound while claimed interest compounded freely elsewhere. Here, `pending_delegator_rewards` is deposited once (real lamports moved into the vote account) but then used every epoch as the numerator for `calculate_block_reward`'s proportional split to all currently active stake delegations of that vote account, with no evidence the pool is drawn down as it's consumed.

If this holds, a single deposit of `deposit` lamports via `DepositDelegatorRewards` would be redistributed in full (or up to `pending_delegator_rewards`) to delegators again in every subsequent rewarded epoch, rather than being consumed once. Since `DepositDelegatorRewards` is invocable by any signer, an attacker acting as their own validator/staker could deposit a small amount and then receive it back — potentially many times over — as their own stake continues to be rewarded epoch after epoch from the same undiminished pool, which is a self-perpetuating minting effect analogous to the "claim interest, never settle the corresponding debit" exploit in the source report.

### Impact Explanation
If `pending_delegator_rewards` is genuinely never decremented, this results in either:
- Unbounded/duplicated lamport creation in stake rewards derived from block revenue (a form of unconstrained fund minting), or
- Rapid insolvency for the vote account (if payouts are actually funded from the vote account's balance rather than freshly minted), consistent with the "Virtual Balance" insolvency scenario described in the source report.

Either outcome constitutes a concrete, unsigned fund-movement/minting issue reachable via a legitimate, unprivileged transaction (`DepositDelegatorRewards`), which fits the required impact bar.

### Likelihood Explanation
`DepositDelegatorRewards` requires SIMD-0185 (Vote State V4), SIMD-0291 (commission in basis points), SIMD-0232 (custom commission collector), and SIMD-0123 (block revenue sharing) to all be active [5](#0-4) , so this is a forward/feature-gated code path, not yet live on mainnet-beta at the time of this repo snapshot. Assuming those features are active, any signer can trigger the deposit step, and reward distribution runs automatically every epoch for any staked vote account, making the trigger trivially reachable once the feature set is enabled.

### Recommendation
Verify and, if missing, add logic to decrement `pending_delegator_rewards` by the amount actually distributed each epoch (or by the full block-reward payout total) at the point `calculate_block_reward` results are committed to stake accounts, ensuring the pool is monotonically consumed rather than replayed every epoch. Add an epoch-rewards integration test that deposits `X` lamports via `DepositDelegatorRewards`, runs reward distribution across two or more epochs, and asserts total delegator payouts never exceed `X`.

### Proof of Concept
Conceptual reproduction path (could not fully verify from static reading whether a decrement exists elsewhere in the distribution/payout commit path, e.g. in `distribution.rs`, which I did not have iterations left to fully inspect):
1. Enable SIMD-0123/0185/0232/0291 feature set; create a `VoteStateV4` vote account with an active stake delegation.
2. Any signer invokes `DepositDelegatorRewards { deposit: N }`, transferring `N` lamports into the vote account and setting `pending_delegator_rewards = N` via `add_pending_delegator_rewards` [6](#0-5) .
3. At epoch boundary, `calculate_block_reward` reads `pending_delegator_rewards` (still `N`) and pays the delegated stake its proportional share, up to `N` [7](#0-6) .
4. At the next epoch boundary, absent any decrement, `pending_delegator_rewards` is still `N`, so the same stake receives another payout of up to `N`, and so on indefinitely.

**Caveat**: Due to index size limits I was not able to fully trace every function in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` that commits `InflationRewardWithCommission`/block-reward results to stake accounts, so I cannot rule out a decrement occurring there. I recommend starting a full Devin session with complete repo access to confirm whether `pending_delegator_rewards` is decremented anywhere in the commit/distribution path before treating this as a confirmed exploit.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
