### Title
`solveRequestsDirect` omits the `solvingNotPaused` guard enforced everywhere else, letting anyone solve requests while solving is paused - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2` gates every synchronous entry/exit (`deposit`, `mint`, `redeem`, `withdraw`) and the guardian-mediated `solveRequestsVault` with the `solvingNotPaused(token)` modifier, which queries the configured `ISolvingGate` to check whether solving is currently paused for that token. `solveRequestsDirect`, the other public path that fills async deposit/redeem requests, is missing this modifier entirely, so it remains fully callable by any address even while the operator has paused solving via the gate.

### Finding Description
`deposit`, `mint`, `redeem`, `withdraw`, and `solveRequestsVault` are all declared with the `solvingNotPaused(token)` modifier, which invokes `_checkSolvingNotPaused` to consult `ISolvingGate.paused(provisioner, token)` [1](#0-0) . This gate exists precisely to let the operator halt processing of a token (e.g. during an oracle/price incident, migration, or other emergency) — the semantics documented in `ISolvingGate` are that "solving is currently paused for the given Provisioner and token" [2](#0-1) .

`solveRequestsDirect`, however, is declared as:
```
function solveRequestsDirect(IERC20 token, RequestV2[] calldata requests) external nonReentrant {
    require(!PRICE_FEE_CALCULATOR.isVaultPaused(MULTI_DEPOSITOR_VAULT), Aera__PriceAndFeeCalculatorVaultPaused());
    ...
``` [3](#0-2) 

It only checks the vault-level pause from the price/fee calculator; it never checks `solvingGate`/`solvingNotPaused`. As the contract's own docstring states, direct solving is open to "anyone willing to pay units (for deposits) or tokens (for redeems)" [4](#0-3) , i.e. it is an ordinary-user-reachable path, not a privileged one.

This is a direct analog of the CVE's root cause: a security restriction (solving pause / "security group") is correctly enforced on one enforcement point (`solveRequestsVault`, sync deposit/redeem/withdraw) but is not re-applied/checked on an alternate live path (`solveRequestsDirect`) that operates on the same underlying state (existing pending `RequestV2` async requests), allowing the intended restriction to be bypassed by any user routing through the unguarded path.

### Impact Explanation
When an operator pauses solving for a token via `solvingGate` (intended to stop new deposit/redeem settlement — e.g., because of a suspected bad price, oracle staleness, or other emergency), any already-outstanding fixed-price `RequestV2` deposit/redeem requests can still be solved by any caller through `solveRequestsDirect`, exactly as if solving were not paused. This defeats the purpose of the pause and can force settlement at stale/incorrect pricing terms embedded in the fixed-price requests during the window the operator intended to freeze activity, causing funds to move (units minted/burned, tokens transferred) against the operator's protective intent.

### Likelihood Explanation
No privileged role is required by the attacker; the exploiting party is simply an ordinary user/solver invoking a public function. The only precondition is that at least one outstanding `RequestV2` (deposit or redeem, fixed-price type) exists for a token that has had `solvingGate` set to paused — a normal, expected operational state, not a rare edge case. Given `solveRequestsDirect` explicitly targets "anyone," the barrier to exploitation is minimal.

### Recommendation
Add the `solvingNotPaused(token)` modifier to `solveRequestsDirect`, matching the treatment already applied to `solveRequestsVault` and the synchronous deposit/redeem/mint/withdraw functions, so the pause state is enforced consistently across every public settlement path.

### Proof of Concept
1. Deploy `ProvisionerV2` with `SOLVING_GATE_ENABLED = true`; set a mock `ISolvingGate` whose `paused(provisioner, token)` returns `true` for the target token via `setSolvingGate`.
2. Have user A call `requestDeposit(token, tokensIn, minUnitsOut, solverTip, deadline, maxPriceAge, isFixedPrice=true, receiver)` before the pause (escrowing tokens and recording the request hash).
3. Assert `solveRequestsVault(token, [request], "", "")` reverts (or is blocked) because `_checkSolvingNotPaused` sees the gate is paused.
4. Call `solveRequestsDirect(token, [request])` from an unrelated address B and assert it **succeeds**: units are transferred from B to the receiver and tokens are transferred from the provisioner to B, despite the gate reporting `paused == true`.
5. This demonstrates the settlement bypass of the operator-intended solving pause.
