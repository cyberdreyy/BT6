## Analysis Result

The report's bug class ("first depositor inflates an accounting variable that a later depositor's contribution rolls into, breaking a share/weight equality") maps directly onto the miner-side vote tally in `stackerdb_listener.rs`, where a single signer's weight can be double-counted into *both* the approval and rejection tallies because the two code paths dedup against two different bookkeeping structures.

### Title
Signer weight double-counted into both approval and rejection tallies via reject-then-accept message ordering - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tracks each block's tally in a `BlockStatus` struct with two independent maps/sets: `gathered_signatures` (used to dedup accept votes) and `responded_signers` (used to dedup reject votes) [1](#0-0) . Because the accept-handling branch only checks `gathered_signatures` before adding weight, while the reject-handling branch checks `responded_signers`, a single signer who first sends a `Rejected` response and later sends an `Accepted` response for the same block has its weight added to `total_weight_rejected` **and** to `total_weight_approved`, breaking the invariant that a signer's weight should count toward at most one side of the tally.

### Finding Description
When a `Rejected` message arrives first, `block.responded_signers.insert(slot_id)` succeeds (returns `true`), so the signer's weight is added to `total_weight_rejected`: [2](#0-1) 

When an `Accepted` message for the same slot arrives afterward, the dedup check is against a *different* structure, `gathered_signatures`, which does not yet contain the slot, so the code adds the same signer's weight to `total_weight_approved` as well: [3](#0-2) 

Nothing in the accept path checks or clears `responded_signers`/`total_weight_rejected` for this slot, and nothing in the reject path checks `gathered_signatures`. The two tallies are therefore not mutually exclusive by construction, only by convention — and only when accept precedes reject. A signer's StackerDB slot is gossiped as a sequence of chunk-write events; nothing prevents the slot owner from writing a `Rejected` chunk followed shortly by an `Accepted` chunk (bumping the slot version each time), both of which are processed as separate events by the listener since it observes the full event stream, not just the latest chunk. This can be triggered unilaterally by one signer, requiring no majority, no other signer's key, and no auth token — only ordinary StackerDB writes to the attacker's own slot.

This is a concrete instance of "aggregated-weight vs verified-accepts" and "a rejection recounted as an accept": the miner's `total_weight_approved` counter no longer accurately reflects the weight of signers who have a currently-standing acceptance without also having an outstanding, unretracted rejection recorded moments earlier — worse, the rejection is *also* still counted, so the same weight is asserted on both sides of an outcome that is supposed to be a single either/or decision.

### Impact Explanation
`signer_coordinator.rs` consumes exactly these two counters to decide whether to declare the block rejected or accepted: [4](#0-3) 
Because a flip-flopping signer's weight leaks into `total_weight_approved` even though that signer's outstanding vote (as tracked via `responded_signers`) is a rejection, the approval threshold can be reached using illegitimate weight that does not correspond to a coherent "this signer currently approves" state. In an adversarial or even just faulty-signer scenario, this inflates the approved tally beyond what genuine, currently-standing acceptances justify, undermining the aggregated-weight vs. verified-accepts equality that the 70%/30% threshold logic depends on for safety.

### Likelihood Explanation
Triggerable by exactly one signer (the slot owner) performing two sequential StackerDB writes for the same block hash — first a `BlockResponse::Rejected`, then a `BlockResponse::Accepted` — which is entirely within a single signer's own capability via normal StackerDB gossip, requiring no collusion, no majority, and no cryptographic forgery.

### Recommendation
Track vote state per slot in a single unified structure keyed by `slot_id` (e.g., an enum `Accepted(weight)`/`Rejected(weight)`), and dedup/transition both `total_weight_approved` and `total_weight_rejected` from that single source of truth so that switching from reject to accept (or vice versa) removes the previous side's weight before adding the new side's weight, guaranteeing a signer's weight is counted on at most one side at any time.

### Proof of Concept
1. Signer S (weight `w`) is added by the miner to `blocks[block_hash]` tracking via `StackerDBListener`.
2. S writes a StackerDB chunk containing `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `block_hash`. The listener processes it: `responded_signers.insert(slot_id)` → `true`, so `total_weight_rejected += w` (lines 515-518).
3. S then writes a new chunk version to the same slot containing `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same `block_hash`. The listener processes it: `gathered_signatures.contains_key(&slot_id)` is `false` (never touched by the reject path), so `total_weight_approved += w` (lines 443-465).
4. Result: `total_weight_approved` and `total_weight_rejected` both include `w` for the same signer S, violating the intended mutual exclusivity of the two tallies used by `signer_coordinator.rs` to decide block acceptance/rejection.
