### Title
Gateway `web_api_trigger` callback map keyed only by user-supplied `MessageId` allows cross-user response hijacking - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The legacy WebAPI capabilities gateway handler stores per-request callbacks in a shared map keyed solely by `msg.Body.MessageId`, a value taken directly from the incoming user's JSON-RPC message body. Because the map key is not bound to the connection/session that submitted it, an unprivileged gateway client can submit a message whose `MessageId` collides with (or is guessed to match) another in-flight user's request, causing the DON's eventual response for one user's request to be delivered to a different, attacker-controlled callback — a "cross-user response confusion" analogous to how the Mover `topupproxy`/`exchangeproxy` shared trust boundary let one caller mint results/events intended to authenticate a different, unrelated action.

### Finding Description
`HandleLegacyUserMessage` registers a callback for a request using the message's own `MessageId` as the map key, with no scoping to the caller's identity or connection: [1](#0-0) 

When any DON node later responds with a matching `MessageId`, `handleWebAPITriggerMessage` looks up and deletes the entry and forwards the *first* matching response to whichever callback is registered for that ID, with no verification that the callback belongs to the same requester whose request produced this DON message: [2](#0-1) 

The trust model comment in this same file explicitly acknowledges that responses are trusted to be routed correctly because the Gateway itself is trusted and DON/Gateway are mutually allow-listed — but this does not protect the *user-facing* side, where the `MessageId` namespace is shared across all connected gateway clients without any per-request ownership check. An attacker who can predict or race a victim's `MessageId` (e.g. via low entropy IDs, replay of an ID seen from a prior interaction, or targeted timing) can overwrite `h.savedCallbacks[msg.Body.MessageId]` with their own callback before or after the legitimate one is registered, and subsequently receive the response meant for the victim, or cause the victim to receive attacker-influenced routing/failure. Root cause: the map write at handler.go:412 has no ownership/session binding and simply performs a last-writer-wins overwrite (`h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}`), and the read/delete at handler.go:150-151 blindly trusts the caller identified only by an attacker/user-controlled `MessageId`.

### Impact Explanation
If `MessageId` is not guaranteed unique per caller/session (I could not fully verify uniqueness enforcement upstream of this handler within the available iterations), a malicious client of the gateway's internet-facing WebAPI trigger endpoint could hijack another legitimate user's DON response — a direct cross-user response confusion. This is analogous to the reported issue's core defect: an unprivileged actor exploiting a shared trust/identifier space intended to keep separate actions distinct in order to receive or forge attribution of a result destined for someone else.

### Likelihood Explanation
Exploitability depends on whether callers can control or predict `MessageId` values and on the concurrency/race window between callback registration and DON response delivery. Given the message is user-supplied JSON-RPC content, and no additional binding (e.g., session token, sender address) is enforced at the `savedCallbacks` map, this is plausible for an internet-facing, unauthenticated-by-default gateway endpoint. Confidence is moderate: I was unable to confirm within the tool budget whether an outer layer (e.g., JSON-RPC transport/session code) already enforces `MessageId` uniqueness or binds it to a connection before reaching this handler.

### Recommendation
Bind `savedCallbacks` keys to a value that couples the `MessageId` with the requester's connection/session identity (e.g., `sessionID + MessageId` or use the callback's underlying connection handle as part of the key), and reject registrations that would silently overwrite an existing unexpired entry rather than clobbering it.

### Proof of Concept
Conceptual: 
1. Victim submits a `web_api_trigger` request through the gateway's user-facing endpoint with `MessageId = X`; `HandleLegacyUserMessage` stores `savedCallbacks[X] = victimCallback`.
2. Before the DON responds, an attacker submits their own request also carrying `MessageId = X` (or a value they can predict/replay); this overwrites `savedCallbacks[X] = attackerCallback` at handler.go:412.
3. When the DON later responds to the original request with `MessageId = X`, `handleWebAPITriggerMessage` (handler.go:148-162) looks up `savedCallbacks[X]`, finds `attackerCallback`, and delivers the victim's response to the attacker instead. [1](#0-0) [2](#0-1)

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
