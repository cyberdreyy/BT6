### Title
A single APR0 withdraw request permanently bricks `stopEpoch` once APR is set non-zero — `prepareStopEpochWithApr0` reverts `NotAllowed` with no recovery path - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` hard-reverts when `apr0TotalPrincipal != 0` and `unscaledApr != 0` (line 506-508). An unprivileged KYC-passing lender can create the `apr0TotalPrincipal` bucket during an APR=0 epoch via `requestWithdraw` → `_requestWithdrawApr0`. If the (honest) manager or CDO ever sets the APR to a non-zero value while that bucket is open — a routine, permitted operation since `setApr` only bounds by `maxApr` — every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts. `apr0TotalPrincipal` can never be cleared, so the epoch can never be stopped and all lender principal is permanently frozen with the borrower.

### Finding Description
The epoch lifecycle has a lock-mishandling analog to the Xen bug: a guard that transitions a recoverable condition into an unrecoverable revert. In `requestWithdraw`, an APR=0 request increments the global bucket `apr0TotalPrincipal` and records the user's principal in `apr0Users` (lines 285-286, 567-577). At epoch end, the CDO calls `prepareStopEpochWithApr0`, which contains:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) { return ...; }
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();   // line 506-508 — permanent, no escape
}
```

The only place `apr0TotalPrincipal` is reset to zero is line 540 — *after* the revert, inside the same call, so it is unreachable once `unscaledApr != 0`. The only other decrement is in `_clearWithdrawClaimForEpoch` (line 827), reachable only on the default-finalization path, which itself requires the epoch to be stopped/finalized — circular and unreachable. There is no manager function to clear the bucket and no cancel-withdraw-request path in the vault.

The state lock is therefore: `apr0TotalPrincipal != 0 && unscaledApr != 0` ⇒ `stopEpoch` always reverts ⇒ `isEpochRunning` stays true, `epochEndDate` stays set, deposits stay paused, and `requestWithdraw`/`claimWithdrawRequest` remain epoch-gated forever. Because `startEpoch` requires `epochEndDate + bufferPeriod` to have passed and the pool not closed, no new epoch can ever begin either — the `_beforeUnpause` guard (`isEpochRunning`) also permanently blocks `unpause`/`restoreOperations` from reopening normal operations.

### Impact Explanation
Permanent freezing of all lender funds. Once locked, all underlying is with the borrower (epochs send principal+interest to the borrower at `startEpoch`), `isEpochRunning = true` forever, withdrawals requests are disabled (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` false since epoch start), and no honest actor — owner, guardian, or manager — has a call that can clear `apr0TotalPrincipal` or force `unscaledApr` semantics past the revert (setting APR back to 0 via `setApr(0)`/`setAprs(0,0)` is the only theoretical unlock, and it *is* permitted by `setApr` since `maxApr` is only an upper bound — however this requires the operator to discover and execute an undocumented recovery transaction; the invariant "epoch finalization must not be permanently gated by a stale user-level bucket" is still broken, and if APR is set via `setAprsWithBuffer` or governance processes that keep it non-zero the freeze is indefinite). Loss magnitude: 100% of vault TVL is inaccessible until manual operator remediation; if the manager cannot/will not set APR back to 0, the freeze is permanent.

### Likelihood Explanation
Attacker requirements are minimal: be KYC-passed (`isWalletAllowed`) and hold tranche tokens. During any APR=0 epoch (a supported, named operating mode), the attacker calls `requestWithdraw(0 dust amount, tranche)` — even a 1-wei request suffices to seed `apr0TotalPrincipal`. The trigger condition — `unscaledApr` becoming non-zero while the bucket is open — occurs through honest, routine operations: the manager calls `setAprs`/`setApr` to reprice the pool, or the owner changes the borrower APR between the request and `stopEpoch`. Nothing in `setApr` (lines 225-235) checks `apr0TotalPrincipal`, so the protection the codebase intended ("APR0 principal is only valid while APR is 0") is enforced by bricking finalization rather than by preventing the APR change or migrating the bucket.

### Recommendation
Replace the hard revert in `prepareStopEpochWithApr0` with graceful handling: when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, treat the APR0 bucket as zero-interest (skip the rate write at line 537) and still reset `apr0TotalPrincipal = 0`, letting the APR0 principals settle at par via `_settleApr0` on claim. Alternatively or additionally, make `setApr`/`setAprs` revert when transitioning `unscaledApr` from 0 to non-zero while `apr0TotalPrincipal != 0`, so the invalid state can never be entered. An explicit manager escape hatch (`clearApr0Principal`) is a weaker fallback but prevents permanent lock.

### Proof of Concept
Foundry fork PoC sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "./IdleCreditVault.t.sol"; // reuse existing fixture

contract Apr0StopEpochLockPoC is IdleCreditVaultTest {
    function testApr0RequestThenAprChangeBricksStopEpoch() external {
        // --- Setup: pool in APR=0 mode (unscaledApr == 0) ---
        // attacker: KYC-passed lender with AA tranche tokens
        address attacker = makeAddr("attacker");
        _depositWithUser(attacker, 100 * ONE_SCALE, true);
        idleCDO.depositAA(10_000 * ONE_SCALE);
        _startEpochAndCheckPrices(0);            // epoch running, APR = 0

        // --- Step 1: unprivileged request seeds apr0TotalPrincipal ---
        vm.prank(attacker);
        cdoEpoch.requestWithdraw(1, address(AAtranche)); // dust amount suffices
        assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

        // --- Step 2: honest manager reprices pool to non-zero APR ---
        // routine operation; setApr only checks maxApr
        vm.prank(manager);
        strategy.setAprs(1e18, 1e18); // unscaledApr = 1e18 (non-zero)

        // --- Step 3: epoch end; stopEpoch permanently reverts ---
        deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
        vm.warp(cdoEpoch.epochEndDate() + 1);
        vm.prank(manager);
        vm.expectRevert(NotAllowed.selector);
        cdoEpoch.stopEpoch(1e18, 0);

        // --- Step 4: no recovery path exists ---
        vm.prank(manager);
        vm.expectRevert(NotAllowed.selector);
        cdoEpoch.stopEpochWithDuration(1e18, 0, 7 days, 0);

        // funds remain locked: epoch still "running", deposits paused,
        // withdraw requests disabled, _beforeUnpause reverts on isEpochRunning
        assertTrue(cdoEpoch.isEpochRunning());
        vm.expectRevert(NotAllowed.selector);
        cdoEpoch.requestWithdraw(0, address(AAtranche));
        // unpause is blocked by _beforeUnpause: defaulted || isEpochRunning || skipDefaultCheck
        vm.prank(owner);
        vm.expectRevert(NotAllowed.selector);
        cdoEpoch.unpause();
    }
}
```

**Uncertainty caveat:** I verified the revert at `IdleCreditVault.sol:506-508`, the unreachable reset at line 540, the bucket seeding via `_requestWithdrawApr0`, and the `_beforeUnpause` gate (`IdleCDOEpochVariant.sol:636`). I did not fully trace `stopEpoch`'s call site of `prepareStopEpochWithApr0` (grep output was suppressed) — the PoC assumes it is invoked unconditionally, which the function's `_onlyIdleCDO` gating and docstring imply; the background agent should confirm the call is not skipped when `unscaledApr` changed, and confirm `setAprs` is callable by `manager` on the deployed configuration (it is, per `setApr`'s sender check at lines 229-230).
