### Title
Pause does not freeze `requestWithdraw` / `depositDuringEpoch` — users can still move value while the vault is "read-only" - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The Mattermost bug class is a restriction-state bypass: a channel set to "read-only" still allowed a state-changing action (pinning posts). The idle-tranches analog is the pause ("read-only") state of `IdleCDOEpochVariant`: `depositAA`/`depositBB` route through `_deposit`, which is `whenNotPaused`, but `requestWithdraw` and `depositDuringEpoch` — the other two value-moving user functions — have no `paused()` check at all. A guardian/owner pause intended to freeze the vault therefore still lets an unprivileged KYC-passing user file a withdrawal receipt (burning tranche tokens and minting strategy-token receipts at the current NAV/price) or deposit mid-epoch and push funds to the borrower.

### Finding Description
`IdleCDO._deposit` is overridden with `whenNotPaused` (`contracts/IdleCDOEpochVariant.sol:644`). The only other gate `_deposit` adds is `isWalletAllowed`. By contrast:

- `requestWithdraw` (`contracts/IdleCDOEpochVariant.sol:739-791`) only checks `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and the Keyring credential. Those flags are cleared by `_emergencyShutdown` (`lines 602-615`) and `_handleBorrowerDefault` (`lines 577-599`), but a plain `pause()` (owner/guardian via `GuardedLaunchUpgradable`/`HypernativeBatchPauser`, or `_pause()` invoked directly without emergency shutdown) leaves them `true`.
- `depositDuringEpoch` (`lines 656-669`) checks `isDepositDuringEpochDisabled`, `skipDefaultCheck` (the emergency flag), `isProgrammableBorrower`, `isAYSActive`, epoch timing and KYC — but not `paused()`. `restoreOperations` explicitly documents that a running epoch keeps the contract paused while still permitting `depositDuringEpoch` (`lines 619-632`), confirming `depositDuringEpoch` is designed to run while `paused() == true` whenever `skipDefaultCheck` is false.

So a pause that is not accompanied by `emergencyShutdown()` leaves both exit and entry paths open — exactly the "read-only channel that still accepts writes" pattern from CVE-2019-20883.

Attack sequence (running or buffer phase, fixed-APR mode):

1. Guardian calls `pause()` in response to a live incident (e.g., price manipulation, pending loss, borrower-solvency signal) without calling `emergencyShutdown`. `paused() == true`, `allowAAWithdrawRequest`/`allowBBWithdrawRequest` still `true`, `skipDefaultCheck == false`.
2. Attacker (any KYC-passing tranche holder) calls `requestWithdraw(0, AATranche)`. `_updateAccounting` runs at pre-incident prices, the receipt is minted at full `principal + interest - fees`, tranche tokens burned, and `IdleCreditVault.requestWithdraw` records a funded claim (`contracts/strategies/idle/IdleCreditVault.sol:271-295`).
3. After `stopEpoch` funds the receipts, the attacker calls `claimWithdrawRequest` and exits at par while paused-in-time accounting may have crystallized a loss that other holders still absorb.

The symmetric entry path: an attacker calls `depositDuringEpoch` during the pause, minting shares at the discounted `(_amount + trancheInterest) * supply / expectedFinal` formula (`line 724`) and transferring underlyings to the borrower, in a window where the operator explicitly froze the vault.

### Impact Explanation
Direct theft / loss-escape with quantified impact. The attacker converts an illiquid, incident-exposed tranche position into a hard, funded receipt (`withdrawsRequestsByEpoch`) at the last pre-pause price while honest users are frozen. If the pause precedes a `stopEpochWithDuration(_lossAmount)` or a default, the attacker's receipt is senior to the loss waterfall — `lossRecoveryPriceByEpoch`/`defaultRecoveryPrice` haircuts only apply per-epoch, and early requesters escape into the funded bucket while remaining holders absorb the BB-first loss. The stolen amount equals the attacker's full tranche balance (`requestWithdraw(0, ...)` withdraws the entire position) priced at pre-incident NAV, i.e., the difference between the pre-loss receipt value and the post-loss recovery value.

### Likelihood Explanation
Medium-low. Requires (a) a `pause()` that is not paired with `emergencyShutdown()` — a plausible operational pattern since `pause` is a lighter guardian/Hypernative action and `emergencyShutdown` permanently sets `skipDefaultCheck` requiring `restoreOperations` — and (b) the attacker being KYC-passed and holding tranche tokens, both allowed by the threat model. No privileged role is needed for the exploit itself. The precondition (a pause during a live incident) is exactly when the bypass is economically valuable, which is the scenario the restriction exists for.

### Recommendation
Add `whenNotPaused` (or an explicit `if (paused()) revert`) to `requestWithdraw` in `IdleCDOEpochVariant.sol:739`, and decide whether `depositDuringEpoch` should also revert when paused outside the intentional `restoreOperations`-during-epoch window (e.g., require `!paused() || !skipDefaultCheck`-consistent semantics). If `depositDuringEpoch` is deliberately allowed while paused post-restore, document that pause alone never freezes mid-epoch deposits; otherwise gate it on `paused()` too.

### Proof of Concept
Foundry fork PoC (extends `test/foundry/IdleCreditVault.t.sol` harness, which already deploys `cdoEpoch`, `idleCDO`, `strategy`, and mocks borrower/manager):

```solidity
function testPausedVaultStillAcceptsWithdrawRequest() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);          // attacker holds AA tranches
    _startEpochAndCheckPrices(0);

    // Guardian soft-pauses during an incident WITHOUT emergencyShutdown
    vm.prank(owner);                                       // or guardian
    cdoEpoch.pause();                                      // paused() == true, skipDefaultCheck == false

    // deposit is correctly frozen (read-only state enforced)
    vm.expectRevert(bytes("Pausable: paused"));
    idleCDO.depositAA(ONE_SCALE);

    // BUG: withdraw request is NOT frozen — same "read-only" bypass as CVE-2019-20883
    uint256 requested = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));
    assertGt(requested, 0, "receipt minted while paused");
    assertGt(IdleCreditVault(address(strategy)).withdrawsRequests(address(this)), 0);

    // BUG: mid-epoch deposit is also not frozen (no paused() check in depositDuringEpoch)
    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);
    address user = makeAddr('paused-depositor');
    deal(defaultUnderlying, user, amount);
    vm.startPrank(user);
    underlying.approve(address(cdoEpoch), amount);
    uint256 minted = cdoEpoch.depositDuringEpoch(amount, address(AAtranche)); // succeeds while paused
    assertGt(minted, 0);
    vm.stopPrank();

    // attacker later claims the funded receipt at par after stopEpoch
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(address(this)) - balPre, 0);
}
```

Key lines to cite: `requestWithdraw` lacks any `paused()` check (`contracts/IdleCDOEpochVariant.sol:739-745`), `_deposit` enforces `whenNotPaused` (`line 644`), `depositDuringEpoch`'s guard list omits `paused()` (`lines 658-669`), and the pause-without-emergency state leaves `allowAAWithdrawRequest`/`allowBBWithdrawRequest` true because only `_emergencyShutdown` clears them (`lines 602-615`).
