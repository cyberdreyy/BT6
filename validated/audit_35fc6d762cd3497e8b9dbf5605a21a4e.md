Confirmed vulnerability: both `multisig/src/lib.rs` and `multisig2/src/lib.rs` delete-member/delete-key logic only purges requests where the removed key/member was the **original requester** (`r.signer_pk == pk` / `r.member == member`), but do not purge confirmations that removed key/member cast on *other* still-pending requests it did not originate. This lets a stale, revoked signature keep counting toward `num_confirmations` on unrelated pending requests, breaking the intended "K live members must approve" custody binding.

### Title
Multisig requests can execute with confirmations from removed/deleted members below the live threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
`DeleteKey` (multisig) / `DeleteMember` (multisig2) only removes pending requests and confirmations for requests where the deleted key/member is the *original requester* of the request. It never scans `self.confirmations` for entries where that key/member is merely a *confirmer* on requests created by someone else. Consequently, after a key/member is removed, its stale confirmation remains counted, so a request can reach `num_confirmations` and execute even though fewer than `num_confirmations` currently-valid keys/members actually approved it — a multisig request executed below the intended live threshold.

### Finding Description
The binding the contract is supposed to preserve is:
```
confirmations counted on a pending request == confirmations from currently valid (live) members
```
In `multisig/src/lib.rs`, `execute_request`'s `DeleteKey` action handler [1](#0-0)  removes requests and their confirmations only for `request_ids` filtered by `r.signer_pk == pk`, i.e. requests that this pk itself created:
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter(|(_k, r)| r.signer_pk == pk)
    .map(|(k, _r)| k).collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
It does not iterate `self.confirmations` to strip this `pk` out of the confirmer set of *other* pending requests where `pk` had previously called `confirm()` but did not create the request.

The same pattern exists in `multisig2/src/lib.rs`'s `delete_member`, which filters `request_ids` by `r.member == member` [2](#0-1)  and similarly never scrubs `self.confirmations` entries where `member` confirmed a request created by a different member.

`confirm()` in both contracts only checks that the calling key/member hasn't already confirmed this specific request [3](#0-2) [4](#0-3) ; it never re-validates that every entry already present in the stored `HashSet<PublicKey>` / `HashSet<String>` still belongs to a currently valid member. It simply compares `confirmations.len() + 1 >= self.num_confirmations` and executes.

**Concrete break of the equality:**
- Before: member set = {A, B, C}, `num_confirmations = 3`. A creates `request_id = 5`. B confirms it (`confirmations[5] = {B}`).
- B is now removed via a `DeleteKey`/`DeleteMember` action (approved by some other quorum, or B itself if B still had signing rights before removal). Because `request_id = 5` was created by A, not B, the removal logic does not touch `confirmations[5]`, which still contains B's stale confirmation.
- After removal: live members = {A, C}, yet `confirmations[5]` still equals `{B}` plus whatever A/C add. If A confirms next (`add_request_and_confirm` or `confirm`), `confirmations[5].len() + 1 = 2` — this is fine for a 3-of-3 count only if B's stale entry is still summed in when C also confirms: A (creator, not auto-counted unless add_request_and_confirm), B (stale), C (confirm) → 3 confirmations reached and `execute_request` fires, even though B is no longer a member and never re-confirmed after removal — i.e. the multisig executed a request without 3 *live* approvals, only 2 live + 1 stale.

This is precisely the "confirmations counted versus live members" custody binding called out as in-scope, and it maps to the Critical impact category "a multisig request executed below threshold."

### Impact Explanation
Critical. A multisig request (e.g. a `Transfer` action moving NEAR out of the account, or an `AddKey`/`AddMember` action seizing control of the account) can be executed with fewer live, currently-authorized approvals than `num_confirmations` requires, because a stale confirmation from an already-removed key/member still counts toward the threshold. This directly undermines the core guarantee of the multisig (K-of-N live signers), enabling unauthorized movement of funds or unauthorized privilege escalation on the account.

### Likelihood Explanation
Medium. It requires: (1) a request to exist that was confirmed by a member prior to that member's removal but not yet fully confirmed/executed, and (2) that member to subsequently be removed via a `DeleteKey`/`DeleteMember` request. Removing compromised or departing members from a multisig is a normal, expected operational action (e.g., off-boarding an employee, rotating a compromised key), so the precondition is realistic and not contrived; it does not require ignoring documented initialization nor any owner/foundation misconfiguration — it is a straightforward flaw in the standard member-removal code path that ships with the contract.

### Recommendation
When executing `DeleteKey` (multisig) / `DeleteMember` (multisig2), iterate over all entries in `self.confirmations` (not just requests originated by the removed key/member) and remove the deleted key/member from every confirmer set. Alternatively, validate at `confirm()`/execution time that every public key/member currently present in a request's confirmation set is still a live member of the contract, discarding stale entries before comparing the count against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig` with `num_confirmations = 3` and members A, B, C (i.e., 3 valid access keys/accounts).
2. As A, call `add_request` with a `Transfer` action to request_id `R1` (not yet confirmed by A itself unless using `add_request_and_confirm`).
3. As B, call `confirm(R1)` → `confirmations[R1] = {B}`.
4. As A+C (2 confirmations, meeting whatever threshold is set for this admin action), submit and confirm a separate request containing `DeleteKey { public_key: B }`, executing it — this deletes B's access key on-chain and removes B's *own* created requests, but leaves `confirmations[R1] = {B}` untouched, per [1](#0-0) .
5. As C, call `confirm(R1)` → `confirmations[R1].len() + 1 == {B, C}.len() + 1 == 3 >= num_confirmations(3)`, per [5](#0-4) , so `execute_request` fires the `Transfer` even though only A (as creator, uncounted) and C actually approved live, with B's now-invalid stale signature making up the third "confirmation."

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
