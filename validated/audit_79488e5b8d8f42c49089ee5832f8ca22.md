### Title
Jovian DA-footprint gas is under-computed due to premature division before multiplication - (File: crates/common/l1-fees/src/params.rs)

### Summary
`L1FeeParams::jovian_da_footprint` divides the FastLZ-estimated compressed size by `1_000_000` *before* multiplying by the `da_footprint_gas_scalar`, instead of multiplying first and dividing last. This is the same rounding-order bug class described in the external report (threshold price truncated to zero/undervalued by dividing before multiplying), applied to Base's Jovian DA-footprint gas metering used in transaction/block gas accounting.

### Finding Description
`tx_estimated_size_fjord` returns the estimated compressed transaction size **scaled by 1e6** (`estimated_size_scaled`), floored at `MIN_TX_SIZE_SCALED = 100_000_000` [1](#0-0) .

`jovian_da_footprint` computes the footprint gas as:
```
floor(estimated_size_scaled / 1_000_000) * scalar
```
instead of the precision-preserving:
```
(estimated_size_scaled * scalar) / 1_000_000
``` [2](#0-1) 

Every other L1 cost function in the same file computes size/gas first, then multiplies by the fee scalar, and divides by the scale factor *last* (`estimatedSize * l1FeeScaled / 1e12` etc.), which is the correct precision-preserving order and mirrors `calculate_tx_l1_cost_fjord` [3](#0-2) . `jovian_da_footprint` alone reverses this order, truncating up to `999,999` scaled-size units *before* the scalar is applied, so the truncated remainder is effectively multiplied away rather than being a bounded rounding error of less than 1 gas unit.

This function is consumed directly by block/transaction execution and resource-metering paths, as confirmed by its use in `crates/common/evm/src/executor/block_executor.rs`, `crates/execution/txpool/src/validator.rs`, `crates/execution/payload/src/builder.rs`, `crates/execution/flashblocks/src/state_builder.rs`, and `crates/common/evm2/src/executor.rs` — i.e., it feeds tx admission (txpool), block building/resource metering, and flashblocks pending-state accounting, all paths reachable by any unprivileged transaction sender submitting calldata.

### Impact Explanation
Because the division happens before the multiplication, the DA-footprint gas charge is systematically under-computed whenever `estimated_size_scaled` is not an exact multiple of `1_000_000` (i.e., for the overwhelming majority of real-world calldata sizes, since the FastLZ estimate is `intercept + coef*fastlzSize`, rarely landing exactly on a 1e6 boundary). The under-count is amplified by the scalar: the lost fractional byte-count (up to just under 1 byte) is dropped *before* scaling, whereas the correct order would only lose less than 1 gas unit after scaling. For non-trivial scalars this can systematically under-price the DA footprint gas charged against every transaction, under-metering the true L1 data-availability resource cost enforced by Jovian's block building/resource limits and txpool admission. This directly affects fee/resource accounting integrity on a reachable path (any signed transaction with non-empty calldata), a "gas mismetering"/incorrect-accounting-of-resource-consumption class bug in the reachable txpool/block-building/EVM handler surface.

### Likelihood Explanation
High likelihood of the arithmetic error occurring: it triggers for essentially any calldata whose FastLZ-estimated size doesn't land on an exact 1e6 boundary, which is the common case, and requires no special crafting beyond ordinary transaction submission. It only manifests once Jovian is active and `da_footprint_gas_scalar` is configured (non-zero, non-`None`), which is the intended production configuration for that upgrade.

### Recommendation
Change `jovian_da_footprint` to multiply before dividing, matching the pattern used elsewhere in the file:
```rust
pub fn jovian_da_footprint(&self, input: &[u8]) -> u64 {
    let Some(scalar) = self.da_footprint_gas_scalar else {
        return 0;
    };
    U256::from(tx_estimated_size_fjord(input))
        .saturating_mul(scalar)
        .wrapping_div(U256::from(1_000_000u64))
        .saturating_to::<u64>()
}
```

### Proof of Concept
Using `tx_estimated_size_fjord` semantics: assume `da_footprint_gas_scalar = 999_999` and `estimated_size_scaled = 100_999_999` (i.e., just short of a full extra "byte unit" of 1_000_000).

- Current (buggy) order: `floor(100_999_999 / 1_000_000) = 100`; `100 * 999_999 = 99,999,900`.
- Correct order: `100_999_999 * 999_999 = 100,999,898,000,001`; `/ 1_000_000 = 100,999,898` (truncated).

The buggy computation yields `99,999,900` vs. the correct `100,999,898` — a shortfall of roughly 1,000,000 gas units (about 1% under-metering in this example, growing proportionally to the scalar value and the size of the truncated remainder), for a single ordinary transaction with attacker-controlled calldata size. This directly demonstrates systematic under-charging of the Jovian DA-footprint resource metric via unprivileged transaction submission. [2](#0-1)

/// Calculate the estimated compressed transaction size in bytes, scaled by 1e6.
/// This value is computed based on the following formula:

pub fn tx_estimated_size_fjord(input: &[u8]) -> u64 {
    let fastlz_size = flz_compress_len(input) as u64;

    fastlz_size
        .saturating_mul(L1_COST_FASTLZ_COEF)

}
