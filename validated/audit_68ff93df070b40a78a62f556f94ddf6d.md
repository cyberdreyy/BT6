### Title
Stale `interestForOverUnderPerformance` charged at request-time APR is never corrected when the epoch APR changes, overcharging the borrower and siphoning yield to remaining tranche holders - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external bug is an "unused worst-case reservation is never refunded" accounting error. The vault analog: `requestWithdraw` computes `interestForOverUnderPerformance` once, at the APR in force at request time, and `startEpoch` blindly adds it to `expectedEpochInterest` computed at the *new* epoch APR. When the APR changes between the request and `startEpoch` (e.g. `stopEpoch` sets `_newApr`, or `setApr`/`setAprs` during the buffer), the correction term is stale and the borrower is billed the wrong interest — the delta is never reconciled.

### Finding Description
`requestWithdraw` locks a tranche-holder's receipt during the buffer period:

```solidity
// contracts/IdleCDOEpochVariant.sol:773-784
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
pendingWithdrawFees += totalFees;
interestForOverUnderPerformance += diff;
```

`_calcInterestWithdrawRequest` derives `diff` entirely from the *current* strategy APR:

```solidity
// contracts/IdleCDOEpochVariant.sol:865-877
uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
uint256 _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
_diff = int256(interestWithoutSplitRatio) - int256(_interest);
```

Both terms scale linearly with `_getStrategyApr()`. For a BB request `diff` is negative; for an AA request positive.

At `startEpoch` the live term is recomputed at whatever APR is now set, but the stored `diff` is not:

```solidity
// contracts/IdleCDOEpochVariant.sol:260-262
int256 adjustedActiveInterest = int256(_calcInterest(getContractValue())) + interestForOverUnderPerformance;
if (adjustedActiveInterest < 0) adjustedActiveInterest = 0;
expectedEpochInterest = pendingWithdrawFees + uint256(adjustedActiveInterest);
```

`expectedEpochInterest` is then pulled from the borrower at `stopEpoch` (`_amountToPullFromBorrower = _expectedInterest`, `getFundsFromBorrower`, contracts/IdleCDOEpochVariant.sol:376,408). If the APR was raised after the BB request was booked, the correct `diff` should be proportionally more negative; instead the borrower pays `newAprInterest + staleDiff`, i.e. too much. The overpayment is split between AA/BB holders by `_virtualPriceAux`/`trancheAPRSplitRatio`, so an attacker holding tranche tokens harvests yield the borrower never owed. Symmetrically, an APR *cut* after an AA request leaves a too-large positive `diff` → `expectedEpochInterest` too high as well, and an APR cut after a BB request undercharges the borrower so remaining LPs lose yield.

### Impact Explanation
Direct mispricing of the borrower's repayment obligation. With BB principal `P`, split ratio `r`, APR change `Δapr`, epoch duration `T`, the un-refunded correction is roughly `P · Δapr · T/365d · (1 − r)/FULL_ALLOC` paid by the honest borrower in excess and distributed pro-rata to tranche holders including the attacker. The surplus is real underlying pulled from the borrower via `transferFrom` — theft of borrower funds converted into tranche-holder yield. No guard prevents it: `_skimDonatedAssets` only strips idle balance, `pendingWithdrawFees` is unrelated, and nothing re-derives `interestForOverUnderPerformance` at `startEpoch`.

### Likelihood Explanation
Requires only (a) a withdraw request during the buffer (open to any KYC'd tranche holder via `allowAA/BBWithdrawRequest`) and (b) an APR change between request and `startEpoch` — a routine manager action (`stopEpoch(_newApr)` already ran before the buffer; `setApr`/`setAprs` on `IdleCreditVault` remain callable during the buffer, as used in tests). An attacker can sandwich it: hold AA in wallet A, request a BB withdraw from wallet B at low APR, wait for a scheduled APR raise, then collect inflated AA yield after `stopEpoch`. The BB receipt's own shortfall is bounded by the fixed-receipt design, so the net is positive when AA share of the overcharge exceeds the BB receipt's forgone interest.

### Recommendation
Recompute the over/under-performance correction at `startEpoch` with the then-current APR instead of caching `diff` at request time: store per-request `principal` and tranche side (e.g. `withdrawnNAVAA`/`withdrawnNAVBB`), and at `startEpoch` derive `diff` as `interestWithoutSplitRatio − trancheShare` using `_getStrategyApr()` at that moment. Alternatively, disallow strategy APR changes while `interestForOverUnderPerformance != 0`, or settle requests at the epoch APR rather than request-time APR.

### Proof of Concept
Foundry fork PoC (against `test/foundry/IdleCreditVault.t.sol` harness conventions):

```solidity
function testStaleDiffOverchargesBorrower() external {
    // AA attacker wallet + BB wallet, 50/50 pool
    address alice = makeAddr("attackerAA");
    address bob = makeAddr("attackerBB");
    uint256 amt = 10_000 * ONE_SCALE;
    deal(defaultUnderlying, alice, amt);
    deal(defaultUnderlying, bob, amt);
    _depositAs(alice, amt, address(AAtranche));
    _depositAs(bob, amt, address(BBtranche));

    _startEpochAndCheckPrices(0);
    // stop epoch with LOW next APR (e.g. 1%)
    _stopEpochAndCheckPrices(0, 1e18, _expectedFundsEndEpoch());

    // Bob requests BB withdraw during buffer at 1% APR -> diff booked at 1%
    vm.prank(bob);
    cdoEpoch.requestWithdraw(0, address(BBtranche));
    int256 staleDiff = cdoEpoch.interestForOverUnderPerformance(); // negative, small magnitude

    // Manager legitimately raises APR to 20% during buffer
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(20e18, 20e18);

    // Record borrower obligation implied by expectedEpochInterest
    vm.prank(manager);
    cdoEpoch.startEpoch();
    uint256 charged = cdoEpoch.expectedEpochInterest();

    // Correct value: diff should scale with new APR (~20x magnitude)
    uint256 correctExpected = uint256(
        int256(cdoEpoch.getContractValue() * (strategy.getApr()/100) * cdoEpoch.epochDuration()
            / (365 days * 1e18)) + staleDiff * 20);
    assertGt(charged, correctExpected); // borrower overbilled by ~19x |staleDiff|
}
```

Uncertainty: I did not fully verify `setApr`/`setAprs` access gating and whether the same effect is reachable purely through `stopEpoch(_newApr)` without a second APR change; if strategy APR can only change via `stopEpoch`, the stale-window shrinks to requests booked before that call (e.g. requests still pending across epochs where `lastWithdrawRequest`/`withdrawsRequestsByEpoch` carry over), which should be checked against the request lifecycle before finalizing the PoC.
