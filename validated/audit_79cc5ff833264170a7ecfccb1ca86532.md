## Finding: Multisig confirmations survive key deletion, allowing requests to execute below the configured threshold [1](#0-0) 

### Title
Multisig request can execute below `num_confirmations` threshold because stale confirmations from deleted keys are not purged - (File: `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` authorizes execution purely by counting entries in the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` set for a request against `num_confirmations` [2](#0-1) . When a key is removed via `DeleteKey`, the contract only purges confirmations for requests that were *originated* by that key; confirmations that key placed on *other* requests (added by different signers) are left untouched [1](#0-0) . This breaks the intended invariant `count(confirmations from currently-authorized keys) >= num_confirmations` and replaces it with `count(confirmations ever recorded, including from revoked keys) >= num_confirmations`, letting a request execute with fewer live signers than the configured threshold.

### Finding Description
`DeleteKey` handling:
```rust
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [1](#0-0) 

`r.signer_pk` records only the key that *called `add_request`* for that specific request [3](#0-2) . It has nothing to do with which keys later called `confirm` on the request. So if key `B` confirms a request `R1` that was originated by key `A`, and `B` is later deleted, `R1`'s confirmation set still contains `B`'s public key indefinitely - it is never re-validated against the currently live set of access keys.

`confirm` then counts purely by set size:
```rust
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    ...
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(env::signer_account_pk());
        ...
    }
}
``` [2](#0-1) 

There is no check anywhere that every public key already present in `confirmations` is still a live access key on the account. The contract's own guarantee (`k`-of-`n` signatures, where `n` is the set of currently valid access keys) is violated because a stale, now-nonexistent key's confirmation continues to be counted.

### Impact Explanation
This is a **threshold bypass**: a `MultiSigRequestAction` (e.g. `Transfer`, `AddKey` granting a full-access key, `DeployContract`, arbitrary `FunctionCall`) can be executed with fewer currently-authorized signers than `num_confirmations` requires, because one or more "confirmations" belong to keys that have since been deleted from the account. This matches the explicit Critical-impact category "a multisig request executed below threshold" - funds can be transferred, or the account taken over (via `AddKey`) by less than the configured quorum of live keys.

### Likelihood Explanation
Key rotation (removing a departing or compromised signer via `DeleteKey`) is a normal, expected multisig operation, not an edge case. Any time a signer is removed after having confirmed (but not caused to execute) some still-pending request, that pending request permanently retains an extra "phantom" confirmation. The remaining signers - each acting within their normal, already-granted authority to call `confirm` - only need to supply `num_confirmations - 1` live confirmations (or fewer, if multiple keys were rotated out after confirming) to push the count over the threshold. No privileged actor, victim key compromise, or social engineering is required beyond ordinary multisig key-management usage.

### Recommendation
When a key is deleted, iterate all pending requests' confirmation sets (not just ones the key originated) and remove that key's public key from every set:
```rust
for (request_id, mut confirmations) in self.confirmations.iter() {
    if confirmations.remove(&pk) {
        self.confirmations.insert(&request_id, &confirmations);
    }
}
```
Alternatively, validate at `confirm`-time that every key counted toward the threshold is currently a valid access key on the account (more expensive, requires a way to enumerate/verify keys), or maintain an explicit "active signer" registry that `DeleteKey` prunes from all confirmation sets atomically.

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` (3-of-n threshold).
2. Key `A` calls `add_request` to create request `R1` (e.g. `Transfer`).
3. Key `B` calls `confirm(R1)` → `confirmations(R1) = {B}` (1 < 3, not executed).
4. Through normal multisig governance, `DeleteKey { public_key: B }` is requested and confirmed/executed - `B` is removed from the account's access keys. Because `R1.signer_pk == A`, not `B`, the `DeleteKey` handler at [4](#0-3)  does not touch `R1`'s confirmations; `confirmations(R1)` still equals `{B}`.
5. Key `C` calls `confirm(R1)` → `confirmations(R1) = {B, C}`, count = 2 < 3, not yet executed.
6. Key `D` calls `confirm(R1)` → check `2 + 1 >= 3` passes at [5](#0-4) , and `R1` executes.
7. Result: `R1` executed with only 2 live signers (`C`, `D`) instead of the required 3, because the deleted key `B`'s stale confirmation was still counted.
