I found a promising analog: stale per-epoch request state that isn't cleared on claim. Checking the default finalization path to confirm impact.### Title
Stale instant-withdraw receipt not stripped on funded claim corrupts later default recovery - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` pays a funded instant-withdraw receipt and zeroes the aggregate `instantWithdrawsRequests[_user]`, but it never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements the epoch-level `instantWithdrawClaimsByEpoch[epoch]`. Like the urllib3 bug where the request body survives a 303 method-change, the per-epoch "request body" survives the funded-claim transition. If the same `epochNumber` later becomes `defaultRecoveryEpoch`, `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch basis and re-charges the user for an already-paid receipt, reverting on underflow (permanent freeze) while simultaneously inflating the recovery accounting used to price `defaultRecoveryPrice` for every defaulted-epoch claimant.

### Finding Description
In `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393) the funded path performs:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Only the aggregate is cleared. `requestInstantWithdraw` (lines 356-375) recorded three pieces of state per request: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the global `instantWithdrawClaimsByEpoch[currentEpoch]`. The last two are never touched by the funded claim, so after a successful payout the vault still "remembers" the request under its request epoch — exactly the stale-body-after-redirect pattern.

The stale data becomes live again in `_claimDefaultedInstantWithdrawRequest` (lines 842-856):

```solidity
claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
instantWithdrawsRequests[_user] -= claimBasis;      // underflows by the stale amount
pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
_burn(_user, claimBasis);                            // burns more receipts than exist
```

Because `defaultRecoveryEpoch` is set to the `epochNumber` at default finalization and `epochNumber` only increments inside `deposit` during `stopEpoch` (lines 607-614), an instant request made during the buffer shares its epoch with the `stopEpoch` that can end in default. A user who claimed funded, then re-requested in the same epoch, has `instantWithdrawsRequestsByEpoch = A + B` but only `B` outstanding and only `B` receipt tokens: both the subtraction and the `_burn` revert, permanently freezing the legitimate `B` claim. The inflated `instantWithdrawClaimsByEpoch[defaultEpoch]` also skews the reserve/haircut math, mispricing `defaultRecoveryPrice` for all defaulted-epoch claimants.

The analogous staleness exists on the normal path too — `_claimFundedWithdrawRequest` (lines 319-350) clears `withdrawsRequests[_user]` and `lastWithdrawRequest[_user]` but not `withdrawsRequestsByEpoch[_user][epoch]` — though the instant path is the one re-read unconditionally by epoch in default finalization.

### Impact Explanation
Permanent freezing of a legitimate, funded instant-withdraw claim: the user's re-requested amount `B` (principal already burned from the CDO and receipt minted) can never be claimed after default finalization, and the inflated `instantWithdrawClaimsByEpoch`/`pendingInstantWithdraws` basis causes `defaultRecoveryPrice` to be computed against a claim base that includes funds already paid out, diluting or stranding recovery for other defaulted-epoch claimants. Loss magnitude is bounded by the stale request size `A` plus the frozen `B`, and the reserve distortion applies to the whole defaulted epoch.

### Likelihood Explanation
Requires (a) instant-withdraw mode enabled, (b) a user who claims a funded instant receipt and then re-requests within the same `epochNumber` (instant requests are designed to be repeatable), and (c) the borrower defaulting in that same epoch — an unprivileged-sequenceable condition since epoch transitions and defaults are driven by honest manager/borrower calls the attacker merely sequences around. No privileged misbehavior is needed; the only gate is that the same-epoch default must occur, which is precisely the scenario the default-recovery code was added to handle.

### Recommendation
In `claimInstantWithdrawRequest`, strip the request "body" when the funded claim is paid: iterate or track the request epoch and zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and subtract the claimed amount from `instantWithdrawClaimsByEpoch[epoch]` alongside `instantWithdrawsRequests[_user] = 0`. Symmetrically, clear `withdrawsRequestsByEpoch[_user][epoch]` in `_claimFundedWithdrawRequest` so stale per-epoch entries can never be reinterpreted by a later default or loss-adjusted epoch.

### Proof of Concept
Foundry fork PoC sketch (pattern follows `test/foundry/IdleCreditVault.t.sol`):

1. Configure pool with instant withdraws enabled; LP deposits AA, `requestInstantWithdraw` for amount `A` while `epochNumber == N`; CDO funds it via `collectInstantWithdrawFunds`.
2. LP calls `claimInstantWithdrawRequest` — paid `A`; assert `instantWithdrawsRequestsByEpoch[lp][N] == A` and `instantWithdrawClaimsByEpoch[N] == A` still (the stripped-body failure).
3. LP `requestInstantWithdraw` for `B` in the same epoch `N`.
4. Manager stops the epoch with the borrower underfunded so default finalization sets `defaultRecoveryEpoch = N` and `defaultInstantWithdrawsFinalized = true`.
5. `claimInstantWithdrawRequest` for LP: `vm.expectRevert()` on the underflow at `instantWithdrawsRequests[lp] -= (A + B)` — the `B` claim is permanently frozen, while `instantWithdrawClaimsByEpoch[N]` included the phantom `A` when the recovery price was set.

Uncertainty note: I could not read the `_handleBorrowerDefault`/`finalizeDefault` bodies in `IdleCDOEpochVariant.sol` within the available iterations to confirm exactly how `instantWithdrawClaimsByEpoch` feeds `defaultRecoveryPrice`; the core finding (stale per-epoch instant receipt surviving a funded claim and reverting in `_claimDefaultedInstantWithdrawRequest`) is fully supported by the vault code cited above.
