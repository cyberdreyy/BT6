### Title
Signer vote flip-flop is double/stale-counted in `BlockStatus` weight tallies, causing the miner coordinator to spuriously reach `SignersRejected` on a signable block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` maintains per-block vote weight in `BlockStatus` (`total_weight_approved`, `total_weight_rejected`, `responded_signers`, `gathered_signatures`, `failed_txids`). These counters are gated by two *different* membership sets (`gathered_signatures` for accept, `responded_signers` for reject) and are only ever incremented, never retracted, when a signer legitimately changes its vote on the same block (a flow the signer protocol explicitly allows: `LocallyRejected --> LocallyAccepted: re-evaluated`, per `docs/signer-flows.md:144`). This exactly mirrors the ERC1155Enumerable class of bug: a monotonically-increasing counter whose invariant ("current weight held by live votes") silently drifts because state removal/retraction was never implemented, only addition.

### Finding Description
`BlockStatus` is a single struct per block hash [1](#0-0) .

On an `Accepted` message, the gate that decides whether to add weight to `total_weight_approved` is `!block.gathered_signatures.contains_key(&slot_id)`, and after that check, the code unconditionally inserts `slot_id` into **both** `gathered_signatures` and `responded_signers`: [2](#0-1) 

On a `Rejected` message, the gate that decides whether to add weight to `total_weight_rejected` (and to the per-txid `failed_txids` tallies) is `block.responded_signers.insert(slot_id)` — i.e. "have we seen *any* response, accept or reject, from this slot before": [3](#0-2) 

Because the two paths gate on different sets, a single signer that legitimately re-evaluates its vote produces incorrect, non-retracting state:

1. **Reject → Accept (double count):** Signer first rejects. `responded_signers.insert(slot_id)` succeeds → `total_weight_rejected += w`. The signer later re-evaluates and accepts the same block (an explicitly supported transition). The accept branch checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (only `responded_signers` was touched by the reject), so it also does `total_weight_approved += w`. The signer's weight `w` is now counted in **both** `total_weight_rejected` and `total_weight_approved` simultaneously, and the stale rejection weight is never removed.
2. **Accept → Reject (stale approval):** Signer first accepts (`total_weight_approved += w`, and `responded_signers` also gets the slot inserted as a side effect). The signer later rejects; the reject branch's gate `responded_signers.insert(slot_id)` now returns `false` (already present from the accept), so the rejection is silently dropped — `total_weight_rejected` is not incremented, but the earlier `total_weight_approved` credit is never removed either.

In both cases, `total_weight_approved + total_weight_rejected` can now diverge from what actually-live signer votes represent, because weight from a superseded vote is never rolled back, exactly like `_currentIndex`/`_allTokensIndex` in the referenced report only ever increasing.

### Impact Explanation
These tallies directly drive the miner's coordination logic in `signer_coordinator.rs`: [4](#0-3) 

- `total_weight_rejected.saturating_add(weight_threshold) > total_weight` triggers `NakamotoNodeError::SignersRejected`, permanently excluding the block (and, via `failed_txids`, permanently banning transactions per `permanently_excluded_txids`/`temporarily_excluded_txids`) based on weight that includes a signer whose *current* vote is actually acceptance. This can make the miner incorrectly abandon (and ban txids from) a block that the live signer set would otherwise sign, i.e. a liveness wedge on block production driven purely by the normal reject→reconsider→accept path of a single signer — no majority collusion or forged signature required.
- Conversely, `total_weight_approved >= weight_threshold` can be satisfied while a stale, already-superseded acceptance is retained after the same signer subsequently rejected, keeping the coordinator waiting on/broadcasting stale approval weight instead of reflecting the signer's up-to-date position.

Note the actual on-chain `verify_signer_signatures` check (`stackslib/src/chainstate/nakamoto/mod.rs:1097`) recomputes weight strictly from the real signatures embedded in the header and dedupes by recovered public key, so this bug does not let a forged/insufficient signature set pass on-chain; the impact is confined to the miner-side `StackerDBListener`/`SignerCoordinator`'s block-production decision (false `SignersRejected`, stale txid bans, or a stalled wait), which is a liveness/availability defect in block production rather than a cryptographic safety break.

### Likelihood Explanation
Reachable by a single signer performing an ordinary, protocol-sanctioned vote re-evaluation (`should_reevaluate_reject_reason` / `LocallyRejected --> LocallyAccepted`), with no need for a majority, another signer's key, or any privileged access — the trigger is simply sending an Accept then Reject (or vice versa) for the same `signer_signature_hash` from one registered signer slot.

### Recommendation
Track weight per-slot with a single reconciled state (e.g., `HashMap<u32, Vote>` recording the signer's *current* vote and weight), and when a slot's vote changes, subtract the old contribution from the previous bucket (`total_weight_rejected`/`failed_txids`) before adding the new contribution to the other bucket, mirroring the ERC1155 patch's fix of updating supply before evaluating derived state, and ensuring the two accept/reject paths gate on the same membership set rather than two independent ones.

### Proof of Concept
1. Node's `StackerDBListener` creates a fresh `BlockStatus` for a proposed block (`total_weight_approved = 0`, `total_weight_rejected = 0`, empty `responded_signers`/`gathered_signatures`).
2. Signer S (weight `w`) broadcasts `BlockResponse::Rejected` for the block → `responded_signers.insert(slot_S)` succeeds → `total_weight_rejected = w` (`stackerdb_listener.rs:515-518`).
3. Signer S re-evaluates (e.g. the reject reason becomes stale per `should_reevaluate_reject_reason`) and broadcasts `BlockResponse::Accepted` for the *same* block.
4. Accept handler checks `gathered_signatures.contains_key(&slot_S)` → `false` (untouched by step 2) → `total_weight_approved = w`, and `gathered_signatures`/`responded_signers` are updated (`stackerdb_listener.rs:443-465`).
5. Now `block.total_weight_rejected == w` and `block.total_weight_approved == w` simultaneously for the same signer's single, most-recent vote (accept). If enough other signers are near the rejection boundary, `signer_coordinator.rs`'s check at lines 509-513 can fire `SignersRejected` using the stale `w` from step 2, discarding a block/txids that the live vote set (step 4) would not actually reject.
