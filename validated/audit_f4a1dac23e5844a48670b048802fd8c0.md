### Title
Anyone can steal lamports sitting in an `Uninitialized` account owned by the upgradeable BPF loader via the `Close` instruction, with no authority check - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `UpgradeableLoaderInstruction::Close` handler in the upgradeable BPF loader has a code path for accounts in the `UpgradeableLoaderState::Uninitialized` state that transfers *all* of that account's lamports to an attacker-supplied recipient without any authority or signer check, mirroring the `ArbitrumSwaps` bug class where a permissionless code path sweeps a balance that does not belong to the caller to an address of their choosing.

### Finding Description
In `process_loader_upgradeable_instruction`, the `Close` instruction only requires 2 accounts and dispatches on the state of the account being closed: [1](#0-0) 

For the `Uninitialized` branch, the code does:
```rust
UpgradeableLoaderState::Uninitialized => {
    let mut recipient_account =
        instruction_context.try_borrow_instruction_account(1)?;
    recipient_account.checked_add_lamports(close_account.get_lamports())?;
    close_account.set_lamports(0)?;
    ic_logger_msg!(log_collector, "Closed Uninitialized {}", close_key);
}
```
Unlike the `Buffer` and `ProgramData` branches, which call `common_close_account` and enforce that the authority account (instruction account index 2) matches the stored authority and has signed: [2](#0-1) 

the `Uninitialized` branch performs **no signer or ownership check whatsoever** on the caller. Any transaction can name (a) any account owned by `bpf_loader_upgradeable` that is currently in the `Uninitialized` state as account 0, and (b) an attacker-controlled account as the recipient (account 1), and the instruction will move 100% of account 0's lamports to the attacker's account.

`Uninitialized` loader accounts are produced whenever a buffer/programdata account is closed (their lamports are zeroed and state set to `Uninitialized`, but the account itself is not deleted from the ledger and remains owned by the loader). Because the System program's `Transfer` instruction allows crediting lamports to *any* writable account regardless of its owner, a party can top up such a residual `Uninitialized` loader-owned account (e.g., accidentally, or as part of a multi-step deploy flow) — after which those lamports sit in an account that is unprivileged (no authority field, no owner claim) yet is instruction-reachable. Anyone, not just the depositor, can then invoke `Close` with themselves as the recipient and drain it — exactly the same "shared/self-refund balance can be swept by anyone" pattern described in the `ArbitrumSwaps` report.

### Impact Explanation
Impact is medium: any lamports that end up parked in a loader-owned `Uninitialized` account (whether from user error, an interrupted deploy flow, or any other CPI that inadvertently credits such an account) can be permissionlessly stolen by an unrelated attacker who races/back-runs to call `Close` naming themselves as recipient. This is a concrete unauthorized fund mutation reachable from an ordinary user transaction against a builtin program.

### Likelihood Explanation
Likelihood is limited by how often lamports actually land in a loader-owned `Uninitialized` account after the state transition (normally `set_lamports(0)` already drains it during a legitimate close), but any subsequent lamport credit to that same pubkey (always possible via `system_instruction::transfer`, which does not check the recipient's owner) makes the funds immediately and permissionlessly stealable, with no signature required at all.

### Recommendation
Require account 1 (recipient) to be reached only in the same manner as the other branches, and require the caller (or an accompanying authority account) to have some ownership relationship or signature over the `Uninitialized` account before sweeping its lamports — e.g., either disallow `Close` on already-`Uninitialized` accounts entirely (since they have no legitimate owner to authorize the close), or require the closer to also be a signer that matches the account's own pubkey (as is required for other zero-authority flows, such as the nonce program's uninitialized-withdraw path in `programs/system/src/system_instruction.rs`, which does check `check_signer(from.get_key())` even in the `Uninitialized` case) [3](#0-2) .

### Proof of Concept
1. Deploy a buffer/program via the upgradeable loader, then close it normally with `UpgradeableLoaderInstruction::Close`, leaving the account in `Uninitialized` state at address `U`.
2. Send lamports directly to `U` via `system_instruction::transfer` (allowed since `Transfer`'s recipient-side check only requires writability, not owner match).
3. An attacker submits `UpgradeableLoaderInstruction::Close` with account 0 = `U` and account 1 = attacker's own account. No signature over `U` or any authority account is required by the `Uninitialized` branch at `programs/bpf_loader/src/lib.rs:701-709`.
4. All of `U`'s lamports are transferred to the attacker's account.
