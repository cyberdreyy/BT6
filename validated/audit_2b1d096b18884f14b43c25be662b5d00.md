## Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing execution of a request below the live-member threshold — (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
When a multisig member is removed via `DeleteMember` (in `multisig2`) or a key is removed via `DeleteKey` (in `multisig`), the cleanup logic only deletes **requests originally added by** that member/key. It does **not** scrub that member's/key's **confirmations recorded on other, still-pending requests** that were added by someone else. Those stale confirmations remain in the `confirmations` map and continue to count toward `num_confirmations` in `confirm()`, so a request can later be executed with fewer *live* member approvals than the configured threshold requires.

### Finding Description
`delete_member` in `multisig2/src/lib.rs` only removes requests whose original adder (`r.member`) equals the member being deleted: [1](#0-0) 

It never looks at `self.confirmations` entries where the removed member is merely one of several *confirmers* (not the original adder) of some other pending request. The equivalent `DeleteKey` handler in `multisig/src/lib.rs` has the same gap — it filters requests by `r.signer_pk == pk` (the request's original signer) and only clears confirmations for *those* requests: [2](#0-1) 

`assert_valid_request`, which gates both `confirm` and `delete_request`, never re-validates that the accounts/keys already present in `confirmations.get(&request_id)` are still current members — it only checks that the caller is a current member and that the request/confirmations entries exist: [3](#0-2) 

`confirm()` then simply counts the size of the stored confirmation set (which can include stale entries from removed members) plus the new confirmer against `num_confirmations`: [4](#0-3) [5](#0-4) 

**Binding broken:** `confirmations.len()` (as counted in `confirm`) should equal the number of *currently valid, live* members who approved the request. Instead, `confirmations.len()` can include members who have since been deleted, so:

```
live_valid_approvals < num_confirmations  while  confirmations.len() >= num_confirmations
```

**Exploit path:**
1. Multisig has members `{A, B, C}`, `num_confirmations = 2`.
2. `B` calls `add_request` for a `Transfer` request `X` (receiver of B's/attacker's choosing).
3. `A` calls `confirm(X)` — `confirmations[X] = {A}` (1 of 2, not yet executed).
4. Members legitimately remove `A` (e.g. key rotation) via a `DeleteMember`/`DeleteKey` request that reaches threshold from `{B, C}`. Because the cleanup only purges requests *added* by `A`, request `X` (added by `B`, merely confirmed by `A`) is untouched — `confirmations[X] = {A}` still exists even though `A` is no longer a member.
5. Now members `= {B, C}`, threshold still `2`. `B` alone calls `confirm(X)`. `confirmations.len() (1, stale A) + 1 = 2 >= num_confirmations (2)` → `execute_request` fires the `Transfer`.

The transfer executes with only **one** live member (`B`) actually approving in real time, even though the contract's stated guarantee is `K` (here 2) live members must approve. This is the direct analog of the CEI/state-freshness bug pattern in the source report ("act on stale state before finalizing"): the contract acts on a confirmation set that is not kept consistent with the current membership before evaluating the threshold and issuing the `Promise`.

### Impact Explanation
This is a Critical-severity authorization bypass: a multisig request (including `Transfer` of NEAR, `AddKey`/`FunctionCall`, etc.) can be executed below the configured `num_confirmations` threshold using a phantom approval from a removed member/key. This directly matches "a multisig request executed below threshold" in the impact list, and can result in NEAR being moved by fewer authorized parties than the contract's documented K-of-N guarantee.

### Likelihood Explanation
This requires no attacker to compromise any key or act maliciously beyond normal multisig operations: a routine key-rotation/member-removal (a common, expected operational action) combined with a previously-confirmed-but-not-yet-executed request is sufficient to leave a stale confirmation in place. Any remaining member can then trigger execution using the phantom vote, effectively becoming a unilateral approver despite the threshold being ≥2.

### Recommendation
When removing a member/key, iterate over **all** `requests` (not only those the member originally added) and strip the removed member/key from each request's `confirmations` set (re-checking whether the remaining count still meets `num_confirmations`, and leaving the request pending rather than allowing later confirms to count stale entries). Alternatively, validate on every `confirm()` call that all previously recorded confirmers are still current members before counting them toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. As `B`: `add_request({receiver_id: <attacker>, actions: [Transfer{amount}]})` → `request_id = X`.
3. As `A`: `confirm(X)` (1 confirmation recorded, not executed).
4. As `B` then `C`: `add_request_and_confirm`/`confirm` a `DeleteMember{member: A}` request until threshold met → `A` removed from `members`; note `X`'s stored confirmation set still contains `A` because `delete_member`'s cleanup filter (`r.member == member`) only matches requests *added* by `A`, not requests `A` merely confirmed.
5. As `B` (now one of only 2 remaining members): `confirm(X)` → `confirmations.len() == 1 (stale A) + 1 == 2 >= num_confirmations (2)` → `execute_request` fires the transfer, moving funds with only `B`'s live approval instead of the required 2 live approvals. [1](#0-0) [4](#0-3) [2](#0-1)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
