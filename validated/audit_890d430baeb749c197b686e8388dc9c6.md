### Title
Recipient-Controlled Revert in `BridgeVault.transferETH` Permanently Locks Bridged ETH — (`bridge/evm/contracts/BridgeVault.sol`)

### Summary

`BridgeVault.transferETH` uses a push-ETH pattern (`recipient.call{value: amount}("")`) and hard-requires success. If the recipient is a contract whose `receive`/`fallback` reverts, every attempt to execute the committee-signed claim message will revert, `isTransferProcessed[nonce]` is never set, and the ETH is permanently locked in the vault while the corresponding assets were already burned/locked on the Sui side.

### Finding Description

`BridgeVault.transferETH` unwraps WETH and pushes raw ETH to the recipient with a low-level call:

```solidity
wETH.withdraw(amount);
(bool success,) = recipientAddress.call{value: amount}("");
require(success, "ETH transfer failed");   // reverts entire tx on failure
```

`SuiBridge.transferBridgedTokensWithSignatures` calls `_transferTokensFromVault` (which calls `vault.transferETH`) **before** it marks the nonce consumed:

```solidity
_transferTokensFromVault(...);            // ← can revert here
isTransferProcessed[message.nonce] = true; // ← never reached
```

The same ordering exists in `SuiBridgeV2.transferBridgedTokensWithSignaturesV2`:

```solidity
_transferTokensFromVault(...);            // ← can revert here
isTransferProcessed[message.nonce] = true; // ← never reached
```

Because the nonce is never marked, the bridge node can retry indefinitely, but every retry reverts for the same reason. The ETH stays in the vault with no recovery path.

### Impact Explanation

Any user who bridges ETH from Sui to an EVM address that is a contract without a payable `receive`/`fallback` (e.g., a multisig, a proxy, a smart-contract wallet that rejects plain ETH) will have their funds permanently locked. The assets were already consumed on the Sui side; the EVM side can never complete the claim. This is a permanent fund lock matching the High/Medium impact class.

### Likelihood Explanation

Smart-contract wallets, multisigs (Gnosis Safe), and proxy contracts are common bridge recipients. Many do not accept plain ETH transfers. A user who specifies such an address as the recipient of an ETH bridge transfer will trigger this condition without any malicious intent. A malicious user can also deliberately deploy a reverting contract and specify it as the recipient to grief the bridge's nonce accounting (though the primary victim is themselves or the sender).

### Recommendation

Mark the nonce as processed **before** attempting the transfer (checks-effects-interactions), or switch to a pull-payment model: credit the recipient's claimable balance in storage and let them withdraw separately. This decouples the bridge's state update from the recipient's ability to accept ETH.

```solidity
// Fix: mark processed first, then attempt transfer
isTransferProcessed[message.nonce] = true;
_transferTokensFromVault(...);
```

Or use a pull pattern:

```solidity
pendingWithdrawals[recipient] += amount;
// recipient calls withdraw() separately
```

### Proof of Concept

1. Deploy a contract `Rejecter` with `receive() external payable { revert(); }` on the EVM chain.
2. From Sui, call the bridge to send ETH with `recipientAddress = address(Rejecter)`.
3. Bridge nodes gather quorum signatures and call `transferBridgedTokensWithSignatures`.
4. `vault.transferETH(payable(Rejecter), amount)` → `Rejecter.receive()` reverts → entire tx reverts.
5. `isTransferProcessed[nonce]` remains `false`.
6. Every subsequent retry by bridge nodes reverts identically.
7. ETH is permanently locked in `BridgeVault`; the Sui-side assets are already consumed.
