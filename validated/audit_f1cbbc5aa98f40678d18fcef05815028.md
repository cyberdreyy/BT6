### Title
Duplicate-block guard in `validate_tenure_change_payload` only checks globally-accepted blocks, allowing a signer to countersign two competing tenure-change blocks for the same tenure - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`validate_tenure_change_payload` rejects a second tenure-change proposal for the same tenure only if a prior block for that `consensus_hash` has reached the *globally-accepted* state in `signer_db`. It never checks whether this signer has already locally signed (but not-yet-globally-accepted) a competing block for the same tenure, leaving a window where the same signer can sign two conflicting tenure-change blocks for one tenure.

### Finding Description
The claimed equality is: "at most one tenure-change block should be signed per tenure by a given signer." The guard implementing this is: [1](#0-0) 

This calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, which only returns a block once it has reached network-wide (global) acceptance — not merely locally `Signed`/pre-committed. Contrast this with the separate, narrower-purpose helper `has_signed_block_in_tenure` used in `SortitionState::is_timed_out`, which is explicitly documented to track *any* signed block (including ones only locally signed, not globally accepted) for a different purpose (suppressing inactivity timeouts): [2](#0-1) 

That comment itself acknowledges the distinction between "signed" and "globally accepted" states elsewhere in the code, but `validate_tenure_change_payload`'s duplicate-block check does not use the equivalent "have I signed anything in this tenure" check — it uses only the globally-accepted lookup. So the exploit path is: an attacker wins a sortition, submits tenure-change block A for consensus_hash `CH`, gets a signer to locally sign it (state `Signed`, not yet `GloballyAccepted` because the weight threshold hasn't been reached across the network), then before that state propagates, submits a different tenure-change block B also for `CH` to the same signer. `check_proposal` → `validate_tenure_change_payload` looks up `get_last_globally_accepted_block(CH)`, finds `None` (A isn't global yet), and the duplicate check passes, allowing the signer to sign B as well.

I was not able to fully trace the entire remaining call chain in `stacks-signer/src/v0/signer.rs` (e.g., whether `check_proposal`'s per-block acceptance path re-invokes any earlier local "already voted for a different block in this reward cycle/tenure" gate before calling into `validate_tenure_change_payload`, or whether a different code path outside `chainstate/v1.rs` already blocks this at the signature/BlockResponse level) due to the final-iteration cutoff, so I cannot rule out that an independent guard elsewhere (outside the reviewed file/function) closes this window. Within the file and function actually named in the question, the equality as described does not hold — the check is scoped strictly to global acceptance and does not consider prior local signing in the same tenure.

### Impact Explanation
If unmitigated elsewhere, this breaks the equivocation-guard/uniqueness property for tenure-change blocks: a signer could contribute its signature weight to two different, conflicting tenure-change blocks for the same tenure before global acceptance resolves, which can materialize as a fork/equivocation at the signer-set level or as a liveness/safety wedge depending on how weights land. This matches the "High" severity category (loss of equivocation guard / potential conflicting-block signature) rather than a guaranteed deterministic double-sign, since it is restricted to the narrow window before global acceptance propagates.

### Likelihood Explanation
Exploitation requires only: (1) winning a single miner slot (attacker-controlled, unprivileged), and (2) racing two competing tenure-change proposals to a target signer inside the propagation window before `get_last_globally_accepted_block` reflects the first block's global status. Both conditions are within the stated unprivileged attacker capability (craft `BlockProposals`, gossip signer messages, control one miner slot). The window's exact size depends on network propagation/weight-threshold timing and is not deterministic, making this feasible but timing-dependent, and repeatable across tenures.

### Recommendation
Change the duplicate-block guard in `validate_tenure_change_payload` to use a signer-local "have I already signed/pre-committed any block in this tenure" check (e.g., an analogue of `has_signed_block_in_tenure`, or explicitly checking local `Signed`/pre-commit state in addition to `get_last_globally_accepted_block`) rather than relying solely on global acceptance, so that the equivocation guard covers the pre-global-acceptance window.

### Proof of Concept

2. Assert `signer_db.get_last_globally_accepted_block(&CH)` returns `None`.
