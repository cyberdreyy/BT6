Confirmed the bug pattern. Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` contain the same flaw in `DeleteKey`/`DeleteMember` handling: when removing a member/key, only requests **originated by** that member (`r.signer_pk == pk` / `r.member == member`) have their confirmations wiped. Confirmations that the removed member **added to other members' pending requests** are left untouched in the `confirmations` set, so a stale confirmation from a now-nonexistent member continues to count toward the `num_confirmations` threshold on those other requests.

### Title
Multisig request can execute with a confirmation from a deleted member counted toward threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`DeleteMember`/`DeleteKey` only purges confirmations for requests that the removed member itself created, not confirmations that member cast on requests created by other members. `confirm()` compares `confirmations.len()+1 >= num_confirmations` without re-validating that every entry in `confirmations` still belongs to a current member, so a stale confirmation inflates the count and a request can be executed with fewer *live* member confirmations than `num_confirmations` requires.

### Finding Description
In `multisig2/src/lib.rs::delete_member` (and the equivalent `DeleteKey` handling in `multisig/src/lib.rs::execute_request`): [1](#0-0) 
the removal loop filters `self.requests` by `r.member == member` (the *creator* of the request), then wipes confirmations only for those requests: [2](#0-1) 
If the deleted member had confirmed a *different* pending request (created by another member), that confirmation entry remains inside `self.confirmations` for that request, because it is never touched.

Later, when a live member confirms that request, `confirm()` counts entries in `confirmations` — including the stale one from the deleted member — against `num_confirmations`: [3](#0-2) 

The binding that should hold is: `confirmations.len()` counted at execution time == number of confirmations from members who are *currently* in `self.members`. After a `DeleteMember`/`DeleteKey` action removes a member who had confirmed some other pending request, that equality is broken: the stored count still includes the removed member, while the live member set no longer does. This is the direct analog of the reported generation-counter bug — a bookkeeping value (`genMintCount` / here, `confirmations`) is not correctly reconciled against the entity it is supposed to represent (post-generation-increment entities / here, currently-valid members) after a state transition (generation increment / here, member deletion).

The identical logic exists in the legacy `multisig` contract via `DeleteKey`: [4](#0-3) 

### Impact Explanation
This crosses the "a multisig request executed below threshold" Critical boundary listed in the rules. With `K`-of-`N` members, if a member confirms request A (not yet at threshold), is then removed via a separate `DeleteMember`/`DeleteKey` request, and later a smaller number of *live* members confirm request A, the request can execute (e.g. a `Transfer` moving NEAR out of the multisig account) having received confirmations from fewer than `K` currently-valid members. This effectively lowers the multisig threshold below its configured value, allowing collusion between fewer members than required to move funds, add/delete keys, or deploy new contract code.

### Likelihood Explanation
This requires no privileged access beyond being (or having been) one of the existing multisig members/keys — a normal, expected multisig participant, not the contract owner or a foundation account. The sequence (confirm a pending request, then have that member removed for any unrelated reason, then reach the confirmation threshold with the stale entry still counted) is a straightforward, deterministic call sequence achievable by parties who are always "entitled" to interact with the multisig (existing members), and does not depend on ignoring documented initialization or any external precondition beyond normal contract operation.

### Recommendation
When deleting a member/key, iterate over **all** pending requests (not only those the member created) and remove that member's/key's entry from every `confirmations` set, or alternatively, when counting confirmations in `confirm()`, filter out entries that no longer correspond to `self.members`/current access keys before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` to create request `R1` (e.g. `Transfer`), giving `R1` 1 confirmation (from `A`).
3. `B` calls `add_request_and_confirm` on a `DeleteMember { member: A }` request, and enough other members confirm it to execute — `A` is removed. Note that the delete-member loop only clears confirmations/requests where `r.member == A` (i.e. requests *created* by `A`), so `R1`'s confirmation set (containing `A`) is untouched even though `A` is no longer a member.
4. `B` and `C` (2 live members) call `confirm(R1)`. `confirmations.len()` for `R1` is now `3` (`A`(stale) + `B` + `C`), which satisfies `confirmations.len() as u32 + 1 >= num_confirmations` after `C`'s confirm (`2 + 1 >= 3`), so `R1` executes with only 2 genuinely live confirmations instead of the required 3.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
