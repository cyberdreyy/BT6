#No Vulnerability found for this question.

The scenario describes a race condition where "set_error's rollback" and "congestion-control fee computation" run "concurrently" with divergent evaluation orders. This premise does not match the actual architecture: `Runtime::apply` and its receipt-processing loop are single-threaded and strictly sequential per shard — there is no concurrent evaluation of rollback vs. congestion-info reads.

For each receipt, the sequence is deterministic and synchronous: `apply_action_receipt` runs `merge`/`set_error` on failure, then immediately commits or calls `state_update.rollback()` [1](#0-0) , and only afterward computes `tx_burnt_amount` from `gas_burnt`, `gas_refund_result`, and `result.tokens_burnt` [2](#0-1) . `CongestionInfo` deltas (`own_congestion_info`) are not read or mutated mid-receipt for fee/burn computation — they are accumulated separately via `DelayedReceiptQueueWrapper`/`ReceiptSink` and only finalized once, at the very end of chunk apply in `validate_apply_state_update`, after all receipts (including any that failed and rolled back) have already been fully processed [3](#0-2) . There is no code path where congestion-info reads for burn/fee accounting interleave with a receipt's rollback in a way that could produce two different orderings.

`total_balance_burnt` in `ApplyChunkResult` is derived by summing `tx_burnt_amount`, `other_burnt_amount`, and `slashed_burnt_amount` from `ChunkApplyStatsV1`, which are accumulated deterministically receipt-by-receipt during the single-threaded apply loop, then subtracting `subsidized_amount` [4](#0-3) . A failed `FunctionCall` with an attached deposit still contributes deterministic burnt gas to `tx_burnt_amount` via `set_error`, which discards `new_receipts`/`tokens_burnt`/`subsidized_amount` but is applied synchronously before the burnt-amount arithmetic runs — there is no window for a different node to observe congestion info "before vs after" the rollback, since both operations execute on the same thread in the same fixed order for every validator applying the same chunk. This is why state-transition determinism (and thus consensus) is preserved.

Since the premise (a genuine race/nondeterminism in congestion-info evaluation vs. rollback) has no support in the codebase's single-threaded, sequential apply pipeline, there is no reachable attacker-triggerable divergence between `total_balance_burnt` and the sum of per-receipt burns.
