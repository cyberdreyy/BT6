### Title
Post-default withdraw requests pay 1:1 from the finite default recovery reserve without adding backing, draining funds owed to pre-default claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug freed a peer object while concurrent users still held references to it, because the error path destroyed the object directly instead of decrementing its refcount. The analog here is the same class of error: `IdleCreditVault` treats the finite `defaultRecoveryReserve` as if it were exclusively owned by the pre-default claim basis it was sized for, while a second, uncounted class of claimants (`postDefaultRequests`) is allowed to draw from it 1:1. The reserve is the shared "refcounted" resource; post-default claims release/consume it without ever having been counted in the allocation basis, so the last claimants find the object already "freed".

### Finding Description
When the borrower defaults, `finalizeDefaultRecovery` computes `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and sets `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis` counts only active CDO balance plus `defaultPendingClaimBasis()` (pending normal + current-epoch instant receipts) at the moment of finalization. The reserve is therefore sized exactly to satisfy the pre-default claims at `recoveryPrice`, with no slack. [1](#0-0) 

After finalization, `requestWithdraw` no longer accrues `pendingWithdraws`. Instead it burns the CDO's strategy tokens, mints an equal amount of receipt tokens to the user, and records `postDefaultRequests[_user] = _amount`. No underlying is pulled into the strategy and the reserve/basis is not increased. [2](#0-1) 

Those receipts are then paid out by `_claimPostDefaultWithdrawRequest`, which burns the receipt and calls `_transferDefaultRecovery(_user, amount)` — i.e. it pays 1:1 out of the same `defaultRecoveryReserve` that was fully allocated to pre-default claims. [3](#0-2) 

Every post-default claim of `X` underlying therefore consumes reserve that belongs, at `recoveryPrice`, to pre-default claimants. There is no re-check that the reserve covers both classes: `claimWithdrawRequest` pays post-default claims first (`_claimPostDefaultWithdrawRequest` runs before `_claimDefaultedWithdrawRequest` and the loss-adjusted/funded paths), so a post-default requester is served ahead of the very claimants the reserve was sized for. [4](#0-3) 

### Impact Explanation
Direct theft / insolvency of recovery funds. Since `defaultRecoveryReserve = totalBasis * recoveryPrice / RECOVERY_FULL` exactly, each post-default payout of `X` tokens removes `X` from a pool that was already fully spoken for. Concretely: if `totalBasis = 1,000,000` and `recoveryPrice = 0.5e18`, the reserve holds 500,000. A single post-default claim of 100,000 leaves 400,000 against still-outstanding pre-default claims worth 500,000 at the recovery price — up to 100,000 of pre-default claims become permanently unpayable (transfer will revert or underpay), i.e. stolen by the post-default requester on a first-come-first-served basis. Any unprivileged user (KYC'd tranche holder) can open a post-default request via `cdoEpoch.requestWithdraw`, so the attacker needs no privilege.

### Likelihood Explanation
The path requires a borrower default followed by `finalizeDefaultRecovery`, which is a normal, supported lifecycle (the code explicitly preserves "request/claim UX after default"). Once finalized, any wallet can immediately `requestWithdraw` (the CDO haircut is applied to the minted amount, but the payout source is the still-un-haircutted reserve) and `claimWithdrawRequest` in the same phase, ahead of slower pre-default claimants. No existing guard prevents it: `requestWithdraw` explicitly permits the post-default path, `_claimPostDefaultWithdrawRequest` is served first in `claimWithdrawRequest`, and nothing sizes or tops up the reserve for these new liabilities. Caveat: I verified the reserve sizing and the claim ordering, but could not read `_transferDefaultRecovery`'s body in the available index — the finding assumes it transfers from the reserve balance without an independent solvency check, which the code comments ("backed by the reserve") and the finite-reserve accounting strongly imply.

### Recommendation
Either fund post-default requests separately (pull the underlying backing at request time or escrow it from a dedicated source, not `defaultRecoveryReserve`), or include outstanding `postDefaultRequests` in a running liability that `defaultRecoveryPrice` haircut accounting already reflects — e.g. pay post-default claims from `defaultRecoveryReserve` only after decrementing a per-claim budget, or simply pay them at `defaultRecoveryPrice` rather than 1:1 and track their basis. At minimum, order claims so pre-default basis is settled before post-default receipts draw on the shared reserve.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// 1. Users A (LP) and B (attacker, KYC'd) deposit into AA; startEpoch; requestWithdraw for A.
// 2. Warp past epochEndDate; borrower refuses repayment:
//    manager calls stopEpoch -> getFundsFromBorrower reverts -> _handleBorrowerDefault.
// 3. Owner recovers partial funds; finalizeDefault(R) -> strategy.finalizeDefaultRecovery
//    reserve = R, recoveryPrice = R * RECOVERY_FULL / totalBasis.
// 4. Attacker B: cdoEpoch.requestWithdraw(amount, tranche) // mints postDefaultRequests[B]
//    then cdoEpoch.claimWithdrawRequest() // pays B 1:1 from defaultRecoveryReserve FIRST
// 5. User A: cdoEpoch.claimWithdrawRequest()
//    assert: A receives < claimBasis * defaultRecoveryPrice / RECOVERY_FULL (or tx reverts
//    on insufficient reserve) -> pre-default claim stolen by exactly B's payout.
```

Invariant broken: one reserve, one payout — the recovery reserve is allocated to a fixed basis at finalization, then an uncounted second class of claims is allowed to consume it, identical in shape to freeing a refcounted object while external references remain.

    _onlyIdleCDO();

      // Post-default requests are already priced after the haircut and backed by the reserve,
      // so they must not fall through to the defaulted-epoch receipt logic.
      amount = _claimPostDefaultWithdrawRequest(_user);

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
