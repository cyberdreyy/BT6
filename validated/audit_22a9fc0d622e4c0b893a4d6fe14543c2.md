### Title
Global-rejection is not terminal against a late `store_and_process_block_signature` — a rejected block can still be reassembled and pushed to the node - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`store_and_process_block_signature` (the handler that tallies peer acceptances toward the 70% signing threshold) never checks whether the block has already reached terminal consensus, and even when the resulting state transition fails, it still falls through to broadcast the assembled signature set to the stacks-node. This is inconsistent with the sibling function `store_and_process_block_rejection`, which explicitly guards with `if block_info.has_reached_consensus() { return; }` before doing any further work.

### Finding Description
Two structurally symmetric consensus-tallying paths exist in `stacks-signer/src/v0/signer.rs`:

- `store_and_process_block_rejection` (`stacks-signer/src/v0/signer.rs:2267-2293`) explicitly returns early once `block_info.has_reached_consensus()` is true: [1](#0-0) 
- `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:2442-2538`) has no equivalent guard. It only bails out if `block_info.signed_group.is_some()`: [2](#0-1) 

Crucially, once the (locally computed) 70% acceptance threshold is reached, the code attempts `block_info.mark_locally_accepted(true)` but **ignores failure**: [3](#0-2) 

`BlockInfo::check_state` forbids `GloballyRejected -> LocallyAccepted` (global states are terminal against each other), so if the block was already `GloballyRejected`, `move_to` returns an `Err` [4](#0-3) . The code only logs a warning in that case (and only if `!block_info.has_reached_consensus()`, which is *false* here, so not even that) — it does **not** `return`. Execution falls through unconditionally to `self.signer_db.insert_block(block_info)` and then to `self.broadcast_signed_block(...)`, which assembles the accumulated signatures and calls `handle_post_block` → `stacks_client.post_block(block)`, pushing the block to the node regardless of the earlier rejection decision.

The two record-keeping tables that feed this path are asymmetric as well: `add_block_signature` deletes any prior rejection row for that signer before inserting a signature [5](#0-4) , but `add_block_rejection_signer_addr` only refuses to insert when a signature *already* exists for that signer/hash [6](#0-5) . Nothing removes previously-recorded *acceptance* signatures when the block later reaches global rejection, so the signature table used by `store_and_process_block_signature`'s weight tally (`get_block_signatures`, `stacks-signer/src/v0/signer.rs:2474-2477`) still contains all signatures ever seen for that hash, including stale ones collected before rejection became final. A late-arriving acceptance message (via normal StackerDB gossip, requiring no majority and no other signer's key — just a message this signer already treats as valid) can retrigger `store_and_process_block_signature`, recompute `total_signature_weight` from the stale+new set, cross the threshold, and reach the unconditional `broadcast_signed_block` call even though `block_info.state` is `GloballyRejected`.

This breaks the documented invariant that "Global states are terminal against each other" (`docs/signer-flows.md:135`, `stacks-signer/src/signerdb.rs` `check_state`) — the DB record correctly stays `GloballyRejected` (the guarded field), but the *action* taken (broadcasting the block to the node) is not gated by that same state, exactly mirroring the Gitea pattern where the `repository` field was correctly redacted but the associated `subject` metadata leaked through an un-gated sibling code path.

### Impact Explanation
This falls in the "a rejection recounted as an accept" category. A block that this signer's own bookkeeping has finalized as `GloballyRejected` can still be reassembled from stale signatures and pushed to the node via `post_block`, letting an already-rejected/potentially non-canonical block reach the node's acceptance path from this signer, independent of majority collusion — only ordinary message delivery/timing (validation OK → late signature arrivals after a rejection threshold was reached) is required. This matches the Critical impact bucket: "a signer signing an invalid, non-canonical, or conflicting block, a rejection recounted as acceptance."

### Likelihood Explanation
The precondition is a data race that is entirely plausible under normal gossip/timing: a signer accumulates `>30%` rejection weight and marks a block `GloballyRejected` while acceptance signatures continue to arrive late (network delay, catching-up signer, re-broadcast, etc.) and are processed afterward by `store_and_process_block_signature`. No attacker action beyond ordinary miner/gossip timing is needed; the code path is on the ordinary message-handling route (`handle_block_response` → `handle_block_signature` → `store_and_process_block_signature`).

### Recommendation
Add the same terminal-state guard used in `store_and_process_block_rejection` to `store_and_process_block_signature` (`if block_info.has_reached_consensus() { return; }` before any tallying), and make the `mark_locally_accepted` error path an explicit `return` rather than a log-and-continue, so `broadcast_signed_block` is never reached when the state transition failed. Additionally, consider pruning/ignoring signature rows recorded before a block reaches `GloballyRejected`, matching the deletion behavior already present in `add_block_signature` for the opposite direction.

### Proof of Concept
1. Block `B` is proposed and validated OK by signer `S`; `S` pre-commits and broadcasts, `S` and other signers begin exchanging acceptance/rejection votes.
2. Enough rejection weight (>30%) arrives at `S` before the 70% acceptance threshold is met; `store_and_process_block_rejection` calls `block_info.mark_globally_rejected()` and persists `state = GloballyRejected` (`stacks-signer/src/v0/signer.rs:2335-2341`).
3. Due to network delay, additional `BlockResponse::Accepted` messages for `B` (already in flight before the rejection) arrive afterward and are routed to `handle_block_signature` → `store_and_process_block_signature`.
4. Because there is no `has_reached_consensus()` guard, weight is retallied; if the accumulated (now stale) signature set crosses the 70% threshold, `mark_locally_accepted(true)` is attempted, fails silently against the terminal `GloballyRejected` state, but the function proceeds anyway to `self.signer_db.insert_block(block_info)` and `self.broadcast_signed_block(...)`, which calls `stacks_client.post_block(block)` — pushing `B` to the node even though `S` had already finalized it as globally rejected.

Note: I was unable to execute this scenario end-to-end (no test harness run in this session); the analysis is based on static code review of the cited functions and the documented state-machine invariants in `docs/signer-flows.md`. Confirming the exact weight arithmetic required (whether >30% reject and ≥70% accept can coexist given `compute_voting_weight_threshold`) would benefit from a live/unit test run, which a background Devin session with repo execution access could perform.
