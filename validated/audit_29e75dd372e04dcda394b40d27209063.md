## Finding [1](#0-0) 

### Title
Unsynchronized read of `authorizedKeys` map in `WorkflowMetadataHandler.Authorize` races with concurrent `syncMetadata` writes - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize`, which is invoked on every unprivileged incoming HTTP-trigger request to decide whether a signer is permitted to invoke a workflow, reads the shared `h.authorizedKeys` map without taking `h.mu`, while the periodic `syncMetadata` goroutine replaces this same map under `h.mu.Lock()`. This is analogous to the RewardDistributor bug class: a security-critical decision is made against a map/cache reference that can be concurrently swapped out from under the reader, producing an inconsistent or stale view of authorization state.

### Finding Description
`Authorize` reads the per-workflow authorized key set directly: [2](#0-1) 

Note there is no `h.mu.RLock()`/`RUnlock()` around this access, unlike every other accessor of the same handler state (`GetWorkflowID`, `GetWorkflowReference`, `WorkflowShards`), which all correctly take `h.mu.RLock()`: [3](#0-2) [4](#0-3) 

Meanwhile, `syncMetadata` runs periodically on a ticker (`MetadataAggregationIntervalMs`, default 60s) and replaces the entire `h.authorizedKeys` map (along with `workflowRefToID`, `workflowIDToRef`, `workflowShards`) while holding `h.mu.Lock()`: [5](#0-4) [6](#0-5) 

Because `h.authorizedKeys` in `Authorize` is read without synchronization while it is being reassigned concurrently by `syncMetadata`, the Go memory model does not guarantee `Authorize` observes a consistent map reference at the point of the field read and subsequent map index (`h.authorizedKeys[workflowID]`), nor does it guarantee memory visibility of the freshly-published map contents to the goroutine handling the HTTP request. This is a genuine data race (would be flagged by Go's race detector), and can manifest as:
- A crash/panic if the runtime happens to read a torn map header value (used for a DoS against the gateway's HTTP trigger path).
- Use of a stale `authorizedKeys` snapshot for an unbounded/unpredictable period, meaning key revocations or workflow re-registrations performed by `syncMetadata` are not reliably observed by concurrently-processing `Authorize` calls — i.e., the exact caching/staleness class described in the report, where a security-relevant value (here, the authorized-key set determining whether a signer may trigger a workflow) can be read from a value that is being concurrently mutated rather than atomically/safely published.

### Impact Explanation
`Authorize` is the sole authorization gate for the HTTP Trigger path reachable by unprivileged external callers (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`, per the README's flow: JWT verification then authorized-key check). A race here directly touches the "authentication or role bypass" / "unauthorized job run" category: under concurrent load, a caller's authorization check can be evaluated against an inconsistent view of the authorized-key map, which could permit continued acceptance of a signer whose key was just revoked/rotated by the latest `syncMetadata` pass, or crash the gateway handler goroutine.

### Likelihood Explanation
Likelihood is moderate: it requires overlap between an in-flight `Authorize` call and a `syncMetadata` tick (every `MetadataAggregationIntervalMs`, default 60s), which is a routine, frequently-recurring event under normal gateway operation, not an attacker-controlled precondition. Any node/DON reasonably active with trigger traffic will regularly hit this window.

### Recommendation
Take `h.mu.RLock()`/`RUnlock()` around the `h.authorizedKeys` lookup in `Authorize`, matching the pattern already used in `GetWorkflowID`, `GetWorkflowReference`, and `WorkflowShards`.

### Proof of Concept
Run `go test -race` against a test that concurrently calls `WorkflowMetadataHandler.Authorize` while a goroutine repeatedly invokes `syncMetadata` (or drives it via the aggregator ticking) — the race detector will report a data race on `h.authorizedKeys` between the unguarded read in `Authorize` (line 92) and the guarded write in `syncMetadata` (line 178), since Go's race detector does not consider partial locking discipline (write-locked, read-unlocked) as synchronized.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (h *WorkflowMetadataHandler) GetWorkflowID(workflowOwner, workflowName, workflowTag string) (string, bool) {
	h.mu.RLock()
	defer h.mu.RUnlock()
	workflowRef := workflowReference{
		workflowOwner: workflowOwner,
		workflowName:  workflowName,
		workflowTag:   workflowTag,
	}
	workflowID, exists := h.workflowRefToID[workflowRef]
	if !exists {
		return "", false
	}
	return workflowID, true
}

func (h *WorkflowMetadataHandler) GetWorkflowReference(workflowID string) (workflowReference, bool) {
	h.mu.RLock()
	defer h.mu.RUnlock()
	workflowRef, exists := h.workflowIDToRef[workflowID]
	return workflowRef, exists
}
