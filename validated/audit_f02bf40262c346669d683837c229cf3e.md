### Title
Unauthenticated `setApr`/`setAprs` grant any caller operator-rate scope while `idleCDO` is unset - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.setApr` (and the wrappers `setAprs` / `setAprsWithBuffer` that delegate to it) are public entry points meant to be reachable only by the IdleCDO or the manager — the "operator" scope. The guard explicitly skips the caller check when `idleCDO == address(0)`, so during the deployment/configuration window (after `initialize`, before `setWhitelistedCDO`, or on any vault whose CDO was never wired) **any unprivileged EOA can set the fixed APR** up to `maxApr` (default `DEFAULT_MAX_APR = 20e18`, i.e. ~2000%/yr scaled). This is a direct analog of GHSA-mhgq-xpfq-6r66: an unauthenticated route receives operator runtime scope.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol:225-235`:

```solidity
function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
}
```

`setAprs` (line 206) and `setAprsWithBuffer` (line 217) are `external` with **no** access control of their own; they write `unscaledApr` unconditionally and rely entirely on `setApr` for authorization. When `idleCDO` is unset, that authorization is a no-op, so an attacker can set both `lastApr` (up to 20e18) and `unscaledApr` (completely uncapped, since `unscaledApr` is written before the `maxApr` check and is never bounds-checked anywhere — line 207/218).

`unscaledApr` also gates accounting paths: `requestWithdraw` routes into `_requestWithdrawApr0` only when `unscaledApr == 0` (line 285), and `prepareStopEpochWithApr0` reverts if `unscaledApr != 0` (line 507). An attacker flipping `unscaledApr` during the unset window permanently disables APR0 settlement for users who already requested, or reclassifies the accounting mode of the vault, without holding any privileged role.

### Impact Explanation
- **Interest overstatement / borrower theft:** `lastApr` feeds `getApr()` and the CDO's `expectedEpochInterest`. Setting it to `maxApr` (20e18, ~2000%/yr) inflates the interest the honest borrower must repay at `stopEpoch`. A KYC-passing attacker who deposited before the change claims pro-rata inflated yield paid out of borrower funds — a direct transfer from the borrower to the attacker, up to `principal * 20e18 * epochDuration / YEAR`.
- **Accounting-mode hijack:** writing a nonzero `unscaledApr` before the CDO is wired makes every subsequent APR0 request revert at `prepareStopEpochWithApr0` (line 507: `if (unscaledApr != 0) revert NotAllowed()`), blocking `stopEpoch` for vaults operating in APR0 mode — a freeze of the epoch state machine — or silently switching users between the APR0 bucket and normal-receipt accounting mid-flight.
- The check skip was intended for owner-side setup, but the route is `public`/`external`, so the "operator scope" is reachable by anyone in that window — exactly the reported bug class (CWE-862 missing authorization).

### Likelihood Explanation
The window exists whenever a vault proxy is initialized but `setWhitelistedCDO` has not yet executed: front-running the configuration call on a public deployment script, an upgrade that re-points `idleCDO`, or a vault deployed without wiring. The `maxApr` cap is only a partial mitigation — 20e18 is a catastrophic rate — and `unscaledApr` has no cap at all. Once `idleCDO` is set the hole closes, which keeps the finding at medium rather than high severity, matching the upstream triage.

### Recommendation
- Move the "not yet set" escape out of the runtime path: require `msg.sender == owner()` when `idleCDO == address(0)`, or gate `setApr`/`setAprs`/`setAprsWithBuffer` behind `onlyOwner` until the CDO is wired, then restrict to `msg.sender == idleCDO || msg.sender == manager` afterwards.
- Bound `unscaledApr` (e.g., `require(_unscaledApr <= maxApr)`), since it is written before the authorization check and participates in accounting-mode branching.

### Proof of Concept
Foundry fork PoC sketch (against a deployed `IdleCreditVault` before `setWhitelistedCDO`, or a locally initialized instance):

```solidity
function test_UnauthSetAprWhileCdoUnset() public {
    // vault initialized; idleCDO == address(0) (setWhitelistedCDO not yet called)
    assertEq(vault.idleCDO(), address(0));

    address attacker = makeAddr("attacker"); // any EOA, no role

    vm.prank(attacker);
    vault.setAprs(20e18, 20e18);            // operator scope: sets unscaledApr + lastApr
    assertEq(vault.lastApr(), 20e18);
    assertEq(vault.unscaledApr(), 20e18);

    // attacker as KYC'd lender deposits via CDO once wired; borrower must repay
    // interest at 20e18 APR for the epoch -> inflated expectedEpochInterest,
    // stolen yield paid from borrower repayment at stopEpoch.
}
```

Key assertion: `vault.setAprs(...)` from a zero-privilege EOA succeeds because the `msg.sender` check at `IdleCreditVault.sol:229-231` is skipped while `idleCDO == address(0)`.
