### Title
Pending-response replay always resolves in favor of acceptance over rejection, regardless of message recency - (`stacks-signer/src/v0/signer.rs`, `stacks-signer/src/signerdb.rs`)

### Summary
When a `BlockAccepted`/`BlockRejected` pair for the same `(signer_signature_hash, signer_addr)` arrives before the proposal is locally known, both get parked in separate pending tables (`signer_pending_signature_responses`, `signer_pending_rejection_responses`). `process_pending_responses_for_block` always replays parked rejections before parked signatures, and `add_block_signature` unconditionally deletes any existing rejection row for that `(hash, addr)`. The result is that acceptance always overrides rejection on replay, independent of which message was actually sent later by the signer.

### Finding Description
The intended equality — exactly one of (accept, reject) should persist per `(signer_signature_hash, signer_address)`, with the *later* message winning — holds for the authoritative tables when a block is already known: `add_block_signature` deletes any stale rejection row before inserting the signature [1](#0-0) , and `add_block_rejection_signer_addr` refuses to insert a rejection if a signature already exists [2](#0-1) . Both `reject_then_accept` and `accept_then_reject` unit tests confirm this ordering-correct behavior for the *known-block* path [3](#0-2) .

However, when the block is *not yet* locally known, `handle_block_signature` and `handle_block_rejection` park the vote in two independent pending tables keyed only by `(signer_signature_hash, signer_addr)`, each with its own `INSERT OR REPLACE` [4](#0-3) [5](#0-4) . `INSERT OR REPLACE` dedupes only *within* each table — it does not arbitrate between a pending signature row and a pending rejection row for the same signer, so both can coexist simultaneously regardless of which was received later.

When the proposal finally arrives, `drain_pending_block_responses` pulls both tables' contents into a single `PendingBlockResponses` struct [6](#0-5) , and `process_pending_responses_for_block` replays them in a **fixed** order: pre-commits, then all rejections, then all signatures [7](#0-6) . Because rejections are always processed before signatures, and `store_and_process_block_signature` → `add_block_signature` unconditionally deletes any rejection row for that `(hash, addr)` [8](#0-7) , the acceptance always wins on replay — even if the rejection was the chronologically later, and thus authoritative, message from that signer.

Exploit flow: an unprivileged attacker who can gossip signer/StackerDB messages (the messages themselves need only be validly signed — the attacker can capture and replay previously-broadcast, genuinely signed `BlockAccepted`/`BlockRejected` messages from a target signer address) delivers, to a victim signer that has not yet seen the proposal for H1: (1) an old, genuine `BlockAccepted` for H1 from address A, and (2) a genuine, more recent `BlockRejected` for H1 from address A (e.g., captured from a case where signer A re-evaluated and rejected after initially accepting, or accepted after initially rejecting on a stale reason). Both land in the two pending tables keyed only by `(H1, A)`. When the proposal for H1 arrives, `process_pending_responses_for_block` resolves rejections first, then signatures — so A's stale acceptance is what survives in the victim's `block_signatures`/`block_rejection_signer_addrs` state, regardless of actual message recency.

### Impact Explanation
This breaks the "later message supersedes" safety property for the pending-response replay path, allowing a stale acceptance to be counted instead of a fresher, authoritative rejection for a given signer. Because acceptances tally toward the 70% signing threshold [9](#0-8) , this can shift a victim signer's local tally toward counting a signer's weight as "accept" when that signer's true/last on-record decision was "reject," directly matching the Critical "rejection recounted as acceptance" impact category. It is repeatable against any signer for any block proposal that has not yet arrived locally, since it only depends on the fixed rejections-before-signatures processing order.

### Likelihood Explanation
Preconditions: the victim signer must not yet have the block proposal for H1 in its DB (`block_lookup_by_reward_cycle(H1)` returns `None`), which is a routine timing window in gossip networks (proposal message can straggle relative to peer responses). The attacker needs no privileged key or auth token — only the capability to gossip/replay previously observed, validly signed StackerDB messages, consistent with "gossip signer/StackerDB messages a signer consumes." Both required messages (an old accept and a newer reject from the same address for the same hash) must exist somewhere in the network's history, which can occur naturally (e.g., re-evaluation flows) or be engineered by the attacker's own single miner-slot proposal maneuvers. Feasibility is moderate-to-high given only network-level replay is required; it is repeatable per proposal/signer pair.

### Recommendation
When replaying pending responses in `process_pending_responses_for_block`, resolve accept/reject conflicts for the same `(signer_signature_hash, signer_addr)` by comparing `received_time` (already stored in both pending tables) rather than by fixed processing order — only replay whichever of the pending signature/rejection rows is newer for that signer, discarding the other. Alternatively, merge the two pending tables into one keyed table with a "kind" column plus timestamp, so `INSERT OR REPLACE` naturally keeps only the last-received response per signer, mirroring the authoritative-table behavior in `add_block_signature`/`add_block_rejection_signer_addr`.

### Proof of Concept
Rust test in `stacks-signer/src/v0/signer.rs` test module (or `signerdb.rs`):
1. Create a `Signer` with a valid signer set including address `A`.
2. Simulate `handle_block_signature` with a `BlockAccepted` for hash `H1` from `A` at `received_time = t0`, with `block_lookup_by_reward_cycle(H1) == None` — assert it lands in `signer_pending_signature_responses` via `add_pending_block_signature_response`.
3. Simulate `handle_block_rejection` with a `BlockRejected` for `H1` from `A` at `received_time = t1 > t0` — assert it lands in `signer_pending_rejection_responses`.
4. Trigger `handle_block_proposal` for `H1` (proposal now known), which calls `drain_pending_block_responses` and `process_pending_responses_for_block`.
5. Assert (current buggy behavior): `signer_db.get_block_signatures(H1)` contains A's signature, and `signer_db.get_block_rejection_signer_addrs(H1)` is empty — i.e., the earlier accept survived over the later reject.
6. Expected fixed behavior: `signer_db.get_block_rejection_signer_addrs(H1)` should contain `A`'s rejection (since `t1 > t0`), and `get_block_signatures(H1)` should not contain A's signature — asserting the later message wins regardless of type.

    /// Retrieve and clear all pending block response entries matching the given block signer_signature_hash
    /// Returns PendingBlockResponses containing all matching pre-commits, approval signatures, and rejections
    pub fn drain_pending_block_responses(
        &self,
        block_sighash: &Sha512Trunc256Sum,
    ) -> Result<PendingBlockResponses, DBError> {
        let hash_str = block_sighash.to_string();

        // Delete and return pre-commits in one operation
        let pre_commits_qry = "DELETE FROM signer_pending_pre_commit_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr";
        let mut stmt = self.db.prepare(pre_commits_qry)?;
        let pre_commits_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            Ok(addr)
        })?;
        let pre_commits: Vec<_> = pre_commits_rows.collect::<Result<Vec<_>, _>>()?;

        // Delete and return signatures in one operation
        let signatures_qry = "DELETE FROM signer_pending_signature_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr, signature";
        let mut stmt = self.db.prepare(signatures_qry)?;
        let signatures_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let sig_str: String = row.get(1)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            let signature: MessageSignature = serde_json::from_str(&sig_str).map_err(|_| {
                SqliteError::InvalidColumnType(1, sig_str.clone(), rusqlite::types::Type::Text)
            })?;
            Ok((addr, signature))
        })?;
        let signatures: Vec<_> = signatures_rows.collect::<Result<Vec<_>, _>>()?;

        // Delete and return rejections in one operation
        let rejections_qry = "DELETE FROM signer_pending_rejection_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr, reject_code";
        let mut stmt = self.db.prepare(rejections_qry)?;
        let rejections_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let reject_code: u8 = row.get(1)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            let reject_reason = RejectReasonPrefix::from(reject_code);
            Ok((addr, reject_reason))
        })?;
        let rejections: Vec<_> = rejections_rows.collect::<Result<Vec<_>, _>>()?;

        let pending_block_responses = PendingBlockResponses {
            pre_commits,
            signatures,
            rejections,
        };
        if !pending_block_responses.is_empty() {
            debug!("Drained pending block responses for block {block_sighash}";
                "pre_commits_count" => pending_block_responses.pre_commits.len(),
                "signatures_count" => pending_block_responses.signatures.len(),
                "rejections_count" => pending_block_responses.rejections.len());
        }
        Ok(pending_block_responses)
    }

    fn process_pending_responses_for_block(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &mut BlockInfo,
        pending_responses: PendingBlockResponses,
    ) {
        let signer_signature_hash = block_info.block.header.signer_signature_hash();
        for stacker_address in pending_responses.pre_commits {
            debug!("{self}: Processing pending pre-commit.";
                "stacker_address" => %stacker_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
            );
            self.handle_block_pre_commit(
                stacks_client,
                sortition_state,
                &stacker_address,
                &signer_signature_hash,
            );
        }
        for (stacker_address, reject_reason) in pending_responses.rejections {
            debug!("{self}: Processing pending rejection.";
                "stacker_address" => %stacker_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
                "reject_reason" => ?reject_reason,
            );
            self.store_and_process_block_rejection(
                sortition_state,
                block_info,
                &stacker_address,
                reject_reason,
            );
        }
        let block_id = block_info.block.block_id();
        for (stackers_address, signature) in pending_responses.signatures {
            debug!("{self}: Processing pending signature.";
                "stacker_address" => %stackers_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_id,
            );
            self.store_and_process_block_signature(
                stacks_client,
                sortition_state,
                block_info,
                &stackers_address,
                &signature,
            );
        }
    }
