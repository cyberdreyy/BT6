### Title
`getLargestAccounts` cost scales with total on-chain account count instead of the requested `num` - ([File: accounts-db/src/accounts.rs])

### Summary
`Accounts::load_largest_accounts` always performs a full scan of the accounts index via `self.accounts_db.scan_accounts`, and only uses the bounded `BinaryHeap` (sized to `num`) to decide which entries to *keep*, not which entries to *visit*. As a result, a single `getLargestAccounts` RPC call costs O(total account count) regardless of the small, constant `num` requested.

### Finding Description
`Accounts::load_largest_accounts` builds a `BinaryHeap::new()` and then calls `self.accounts_db.scan_accounts(ancestors, bank_id, |option| {...}, &ScanConfig::default())`, iterating every account tuple yielded by the scan closure and only bounding the heap's *size* to `num` inside the closure body [1](#0-0) . The closure filters zero-lamport accounts and address filters, then conditionally pushes/pops from the heap, but there is no mechanism to stop `scan_accounts` from visiting the remaining index entries once `num` top entries have effectively been found — the underlying scan always walks the entire index. `Bank::get_largest_accounts` simply forwards `num`, `filter_by_address`, and `filter` straight into this function without any additional bounding of the scan itself [2](#0-1) .

Because Solana's accounts index is keyed by pubkey (not by balance), there is no secondary sorted-by-balance structure to allow a bounded top-`num` lookup; retrieving the true largest accounts inherently requires visiting every live account to compare balances. An attacker who is only able to fund many low-value accounts through ordinary account creation increases the total number of index entries that every future `getLargestAccounts` call — even from other, unrelated clients — must scan, without needing more than one RPC call themselves.

### Impact Explanation
This matches the "unbounded cost for a single low-rate call" scoped-impact category: the CPU/time cost of one JSON-RPC request is proportional to the total number of accounts on-chain (attacker-influenceable state) rather than to `num` or any other request-scoped constant. Since `getLargestAccounts` holds accounts-db read locks for the scan duration, a large index size directly increases wall-clock latency and CPU usage per call, which can degrade validator RPC responsiveness under legitimate call rates.

### Likelihood Explanation
The precondition (inflating total account count via ordinary funded account creation) requires no privileged access — anyone can create many low-lamport accounts on-chain over time using standard transactions. Once the total account count is large, every subsequent `getLargestAccounts` call, including a single call issued at or below `CLUSTER_SLOT_TIME_TARGET / 2` rate, will incur cost proportional to the inflated index size. The attack is fully repeatable and does not require concurrent calls or elevated privileges.

### Recommendation
Since no secondary balance-sorted index currently exists, mitigations are limited to: (1) restricting `getLargestAccounts` to nodes that opt in via explicit config (already the case for some heavy RPC methods) and documenting the linear-scan cost, or (2) maintaining an incrementally-updated top-N balances cache in `AccountsDb` that is refreshed periodically rather than recomputed via full scan on each call, decoupling the per-request cost from total account count.

### Proof of Concept
Rust benchmark/integration test plan (to run in `accounts-db` or `runtime` test suite):
1. Construct an `AccountsDb`/`Bank` and populate it with `N` funded accounts for increasing `N` (e.g., 10k, 100k, 1M), each with a low, distinct lamport balance.
2. For each `N`, call `bank.get_largest_accounts(20, &HashSet::new(), AccountAddressFilter::Exclude)` and measure wall-clock time using `std::time::Instant`.
3. Assert that measured time grows roughly linearly with `N` (e.g., time(1M) / time(10k) ≈ 100), confirming the scan cost is proportional to total account count rather than bounded by the constant `num = 20`.
4. Contrast with an expected O(1)-relative-to-`N` behavior if a maintained top-N cache were used, where growth would be flat.

```rust
    pub fn load_largest_accounts(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        num: usize,
        filter_by_address: &HashSet<Pubkey>,
        filter: AccountAddressFilter,
    ) -> ScanResult<Vec<(Pubkey, u64)>> {
        if num == 0 {
            return Ok(vec![]);
        }
        let mut account_balances = BinaryHeap::new();
        self.accounts_db.scan_accounts(
            ancestors,
            bank_id,
            |option| {
                if let Some((pubkey, account, _slot)) = option {
                    if account.lamports() == 0 {
                        return;
                    }
                    let contains_address = filter_by_address.contains(pubkey);
                    let collect = match filter {
                        AccountAddressFilter::Exclude => !contains_address,
                        AccountAddressFilter::Include => contains_address,
                    };
                    if !collect {
                        return;
                    }
                    if account_balances.len() == num {
                        let Reverse(entry) = account_balances
                            .peek()
                            .expect("BinaryHeap::peek should succeed when len > 0");
                        if *entry >= (account.lamports(), *pubkey) {
                            return;
                        }
                        account_balances.pop();
                    }
                    account_balances.push(Reverse((account.lamports(), *pubkey)));
                }
            },
            &ScanConfig::default(),
        )?;
```
