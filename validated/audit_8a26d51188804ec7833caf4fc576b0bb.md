### Title
Actor-id clobbering in `action_implicit_account_creation_transfer` lets an unrelated Transfer sender add an access key to a not-yet-deployed deterministic account, contradicting the "no hijacking" invariant - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
`create_deterministic_account` is documented as never changing `actor_id` so that follow-up owner-only actions (`AddKey`, `DeployContract`, etc.) get checked against the original predecessor and cannot be abused to hijack the account [1](#0-0) . However, its only caller for the funding-transfer path, `action_implicit_account_creation_transfer`, unconditionally sets `*actor_id = account_id.clone();` before dispatching to the `NearDeterministicAccount` branch, directly contradicting that invariant [2](#0-1) .

### Finding Description
`action_create_account` sets `actor_id = account_id` intentionally, because that's the normal `CreateAccount` + `AddKey`/`DeployContract` batching pattern for named accounts [3](#0-2) . `action_implicit_account_creation_transfer` reuses the exact same pattern uniformly for all implicit account types, including `AccountType::NearDeterministicAccount`, at line 224, before the type-specific `match` [4](#0-3) .

For `NearImplicitAccount` this is harmless because the account is keyed exclusively by a public key cryptographically derived from `account_id` itself, so "actor_id == account_id" merely mirrors normal self-authorization. For `NearDeterministicAccount` (NEP-616), however, the account model is explicitly keyless/ownerless — authority is meant to come only from the deterministically-derived contract code, never from an access key, which is exactly what the comment in `create_deterministic_account` states it is protecting against [5](#0-4) .

Exploit flow:
1. A `0s...` deterministic account does not exist yet (`nonexist` state).
2. An attacker (any unrelated account) sends a receipt containing a batch `[Transfer(deposit) , AddKey(attacker_pubkey, FullAccess)]` targeting the `0s...` address.
3. `action_implicit_account_creation_transfer` runs first (since account is `None`), sets `actor_id = account_id` at line 224, and calls `create_deterministic_account` for the `NearDeterministicAccount` branch, creating a bare, contract-less `Account` [6](#0-5) .
4. The subsequent `AddKey` action in the same batch is checked against the now-clobbered `actor_id` (== `account_id`), passing any self-permission check (`actor_id == account_id`) that normally gates `AddKey`/`DeployContract`/`Stake`/`DeleteKey`.
5. When the legitimate `DeterministicStateInit` action later arrives to deploy the intended contract (the `uninit -> active` transition), it operates on the already-existing `Some(account)` branch, so `create_deterministic_account` (and its actor_id-preserving contract) is never invoked again — the attacker's previously injected full-access key survives untouched [7](#0-6) .
6. The attacker now holds a standing full-access key on an account that the NEP-616 design intends to be controlled exclusively by its deterministic contract logic, defeating the "prevent hijacking" guarantee the comment describes.

### Impact Explanation
This is an authorization-escalation bug against NEAR's deterministic/keyless-account model (NEP-616): an unprivileged attacker who merely funds a not-yet-created `0s...` address before its rightful `DeterministicStateInit` deployment can install a persistent full-access key on that account. Depending on how funds/contracts are later deployed to that deterministic address, this can enable theft or hijacking of assets/contract state associated with the account, since the attacker retains a key granting the same rights as an owner despite the account having no legitimate "owner" by design.

### Likelihood Explanation
The attack requires only an ordinary funding transaction with a batched `AddKey` action sent to a computable `0s...` address before the legitimate deployer's `DeterministicStateInit` action executes — a pure account/transaction-ordering race that is cheap (minimal deposit + gas) and repeatable against any not-yet-initialized deterministic account whose target address is known or predictable ahead of deployment.

### Recommendation
In `action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs`), do not set `*actor_id = account_id.clone()` for the `AccountType::NearDeterministicAccount` branch; keep `actor_id` as the original predecessor for that case, consistent with the invariant documented in `create_deterministic_account`, so that `AddKey`/`DeployContract`/etc. batched in the same receipt continue to be checked against the true predecessor and are rejected for keyless deterministic accounts.

### Proof of Concept
Integration/test-loop test (extending `test-loop-tests/src/tests/deterministic_account_id.rs`):
1. Compute a valid `0s...` deterministic account id that does not yet exist.
2. Have an unrelated signer submit a transaction/receipt with actions `[Transfer(deposit), AddKey(attacker_pubkey, FullAccess)]` targeting that id.
3. Assert the receipt succeeds and the account now has an access key for `attacker_pubkey` (demonstrating the bypass), i.e. `AddKey` was NOT rejected despite `actor_id` semantics intending to disallow it.
4. Follow up with the legitimate `DeterministicStateInit` action deploying the real contract to the same account, and assert the attacker's key is still present afterward — confirming persistent unauthorized access survives legitimate deployment.

pub(crate) fn create_deterministic_account(
    initial_balance: Balance,
    storage_usage_config: &StorageUsageConfig,
) -> Account {
    // Unlike `CreateAccount`, this account creation does not change
    // actor_id. This is important to prevent hijacking the account.
    // Actor id remains the predecessor, so any actions following will
    // be checked against that for actor permissions, preventing
    // `AddKey`, `DeployContract`, or any other actions that only the
    // account owner is permitted to do.
    Account::new(
        initial_balance,
        Balance::ZERO,
        AccountContract::None,
        storage_usage_config.num_bytes_account,
    )
}

pub(crate) fn action_implicit_account_creation_transfer(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    fee_config: &RuntimeFeesConfig,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    account_id: &AccountId,
    deposit: Balance,
    block_height: BlockHeight,
    epoch_info_provider: &dyn EpochInfoProvider,
) {
    *actor_id = account_id.clone();
    match account_id.get_account_type() {
        AccountType::NearImplicitAccount => {
            let mut access_key = AccessKey::full_access();
            access_key.nonce = initial_nonce_value(block_height);

            // unwrap: here it's safe because the `account_id` has already been determined to be implicit by `get_account_type`
            let public_key = PublicKey::from_near_implicit_account(account_id).unwrap();

            *account = Some(Account::new(
                deposit,
                Balance::ZERO,
                AccountContract::None,
                fee_config.storage_usage_config.num_bytes_account
                    + public_key.trie_id_len() as u64
                    + borsh::object_length(&access_key).unwrap() as u64
                    + fee_config.storage_usage_config.num_extra_bytes_record,
            ));

            set_access_key(state_update, account_id.clone(), public_key, &access_key);
        }
        // Invariant: The `account_id` is implicit.
        // It holds because in the only calling site, we've checked the permissions before.
        AccountType::EthImplicitAccount => {
            let chain_id = epoch_info_provider.chain_id();

            // Use a deployed global contract for ETH implicit accounts.
            let global_contract_hash = eth_wallet_global_contract_hash(&chain_id);
            let storage_usage = fee_config.storage_usage_config.num_bytes_account
                + global_contract_hash.as_bytes().len() as u64;

            *account = Some(Account::new(
                deposit,
                Balance::ZERO,
                AccountContract::Global(global_contract_hash),
                storage_usage,
            ));
        }
        AccountType::NearDeterministicAccount => {
            *account = Some(create_deterministic_account(
                deposit,
                &apply_state.config.fees.storage_usage_config,
            ));
        }
