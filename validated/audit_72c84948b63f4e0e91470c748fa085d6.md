### Title
Cross-epoch instant-withdraw claims mispriced in default recovery because `defaultPendingClaimBasis` reads only the current-epoch per-epoch bucket while `pendingInstantWithdraws` is epoch-agnostic - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Ghidra UAF is a stale-iterator bug: `SleighBuilder::generatePointerAdd` held a pointer into `issued` that `PcodeCacher::allocateInstruction` invalidated by reallocating the vector. The credit-vault analog is a stale epoch key: `defaultPendingClaimBasis()` mixes a global aggregate (`pendingInstantWithdraws`, which accumulates unfunded instant receipts across all epochs) with a per-epoch map (`instantWithdrawClaimsByEpoch[epochNumber]`, keyed only to the epoch current at finalization). After `epochNumber` "reallocates" (advances at each `stopEpoch`), instant receipts opened in an older epoch remain recorded under the old epoch key but are still counted in the aggregate — the epoch pointer is invalidated while the aggregate keeps referencing them.

### Finding Description
- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[user][epochNumber] += amount`, `instantWithdrawClaimsByEpoch[epochNumber] += amount`, and the epoch-agnostic `pendingInstantWithdraws += amount` (IdleCreditVault.sol:366-374). Nothing prevents a user from leaving an unfunded instant receipt pending while the epoch advances and opening further requests in later epochs.
- `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` but never touches `instantWithdrawClaimsByEpoch`, so if the borrower only partially funds instant claims at a `stopEpoch`, the remainder stays pending under the *old* epoch key (IdleCreditVault.sol:398-403).
- On borrower default, `finalizeDefaultRecovery` computes `pendingBasis = defaultPendingClaimBasis()` = `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` (IdleCreditVault.sol:644-649). Old-epoch unfunded instant claims inflate `pendingInstantWithdraws` — which drives `defaultInstantWithdrawsFinalized` and `_defaultPrefundedInstantReserve` — but are missing from the recovery `totalBasis`, so `recoveryPrice = reserveAmount / totalBasis` is overstated (IdleCreditVault.sol:686-692).
- At claim time, `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (IdleCreditVault.sol:843-855). A user's older-epoch instant receipt survives in `instantWithdrawsRequests[user]` and is then paid **at par** by `claimInstantWithdrawRequest` via `_transferFundedClaim` (IdleCreditVault.sol:380-392). The reserve guard in `_transferFundedClaim` (line 899-905) treats the whole `defaultRecoveryReserve` as untouchable, so this stale claim either reverts (permanent freeze for that user) or, if other funded cash exists, drains cash that should not cover it.

Broken invariants: recovery `totalBasis` must equal all outstanding claims; "one receipt one payout" at `defaultRecoveryPrice`.

### Impact Explanation
Because old-epoch instant claims are excluded from `totalBasis` but the reserve is sized only for the counted basis, `defaultRecoveryPrice` is inflated. Early default-epoch claimants (normal, APR0, and default-epoch instant receipts via `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest`/`_transferDefaultRecovery`) are overpaid from `defaultRecoveryReserve`, draining it. Later claimants — including `postDefaultRequests` users whose receipts were promised 1:1 reserve backing — find the reserve exhausted and revert permanently. Meanwhile any user holding a pre-default unfunded instant receipt can never claim: their non-default-epoch remainder routes to `_transferFundedClaim`, which reverts against the reserve guard. Net effect: direct overpayment to early claimers plus permanent freezing of the residual claims; quantified loss equals the unfunded instant basis carried from prior epochs.

### Likelihood Explanation
Requires an unprivileged instant-withdraw requester whose request is only partially funded at `stopEpoch` (`collectInstantWithdrawFunds` called with less than `pendingInstantWithdraws`), the epoch advancing once, then a borrower default finalized via `finalizeDefaultRecovery`. Partial instant funding happens whenever the CDO's available cash at epoch end is insufficient — an ordinary liquidity condition, not a privileged action. The attacker is just a tranche holder using `requestInstantWithdraw`/`claimInstantWithdrawRequest`; borrower default is an environmental trigger, consistent with the rules.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, account for *all* outstanding instant claims, not just `instantWithdrawClaimsByEpoch[epochNumber]` — e.g., keep a global aggregate of unclaimed instant basis alongside `pendingInstantWithdraws`, or iterate/accumulate per-epoch entries. Symmetrically, `claimInstantWithdrawRequest` after finalization should clear each outstanding epoch's basis through the recovery price rather than paying non-default-epoch remainders at par.

### Proof of Concept
Foundry fork sketch (against an epoch-variant CDO + IdleCreditVault with instant withdraws enabled):

```solidity
// 1. Epoch N running: attacker (KYC'd LP) calls requestInstantWithdraw(X) via the CDO.
// 2. stopEpoch N: borrower returns only part of the cash; manager calls
//    getInstantWithdrawFunds with partial amount -> pendingInstantWithdraws = R > 0,
//    instantWithdrawClaimsByEpoch[N] = X (never decremented by collectInstantWithdrawFunds).
// 3. Epochs advance (epochNumber = M > N). Attacker does NOT claim.
// 4. Other users open normal withdraws / instant withdraws in epoch M.
// 5. Borrower defaults; manager finalizes via finalizeDefaultRecovery(recovered, source).
//    Assert: defaultPendingClaimBasis() == pendingWithdraws + instantWithdrawClaimsByEpoch[M]
//            (missing X from epoch N).
//    Assert: defaultRecoveryPrice > reserveAmount * 1e18 / (totalBasis + X)  // inflated.
// 6. First default-epoch claimant calls claimWithdrawRequest -> receives
//    claimBasis * inflatedPrice; reserve drains by more than fair share.
// 7. Attacker calls claimInstantWithdrawRequest:
//    _claimDefaultedInstantWithdrawRequest clears only epoch-M basis (0 for attacker),
//    then burns instantWithdrawsRequests[attacker] = X at par ->
//    _transferFundedClaim reverts (balance - reserve < X)  // permanent freeze,
//    or overpays if stray funded balance exists.
// 8. Final postDefaultRequests claimant reverts on _transferDefaultRecovery (reserve empty).
```
