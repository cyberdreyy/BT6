### Title
Time-of-check/time-of-use race in `get_transaction`'s confirmed-fork ancestor computation causes wrong-fork transaction data to be returned - (File: `rpc/src/rpc.rs`, `ledger/src/blockstore.rs`)

### Summary
`JsonRpcRequestProcessor::get_transaction` snapshots a "confirmed" bank, then hands its slot number (not the bank object itself) to an asynchronous blocking task that queries `Blockstore::get_complete_transaction`. That function re-derives the set of "confirmed but not yet rooted" ancestor slots by walking `Blockstore` on-disk `SlotMeta.parent_slot` links starting at the captured slot number, rather than from the actual bank/fork state at query time. Between the moment the slot number is captured and the moment the blockstore query executes on a separate thread, the blockstore's parent-chain for that slot can be mutated (fork switches, duplicate-slot handling, dead-slot marking, and repair/replay writes are all continuously running against the same `Blockstore`), producing an ancestor set that no longer corresponds to the currently confirmed fork. This is architecturally the same bug class described in the external report: an identifier captured at check-time (tab ID / slot number) is later dereferenced against live, mutable state (tab info / blockstore parent chain) that can have changed by use-time.

### Finding Description
In `rpc/src/rpc.rs`: [1](#0-0) 
`get_transaction` captures `confirmed_bank` (an `Arc<Bank>`, immutable snapshot) and then only passes `highest_confirmed_slot = confirmed_bank.slot()` — a bare integer — into a `spawn_blocking` closure that calls `blockstore.get_complete_transaction(signature, highest_confirmed_slot)`.

In `ledger/src/blockstore.rs`: [2](#0-1) 
`get_complete_transaction` re-derives fork membership from scratch using `AncestorIterator::new_inclusive(highest_confirmed_slot, self)`, which walks `Blockstore` `SlotMeta.parent_slot` pointers: [3](#0-2) 
This produces `confirmed_unrooted_slots`, later used by `get_transaction_status_with_counter` to decide whether a transaction's slot is acceptable: [4](#0-3) 

The check ("this bank/slot is confirmed") happens when `confirmed_bank` is fetched at the start of the async RPC handler. The use (walking blockstore's on-disk parent-chain metadata for that slot number, and accepting whichever transaction-status row matches) happens later, on a different thread, against `Blockstore` state that keeps evolving independently (replay, repair, duplicate-slot resolution, and `LedgerCleanupService`/`purge_slots` all mutate `SlotMeta` and transaction-status column families concurrently — the blockstore code itself repeatedly documents this class of race, e.g. `ensure_lowest_cleanup_slot`'s comment that "Blockstore callers, like rpc, can process concurrent read queries" while cleanup runs): [5](#0-4) 

Because `get_transaction_status_with_counter` scans across ALL slots on the signature index (not just ones the caller's actual bank fork agrees with) and accepts a match purely if `is_root(slot)` or `slot ∈ confirmed_unrooted_slots` computed from the possibly-stale ancestor walk, a transaction status recorded under a *different* (now-abandoned or newly-competing) version of that slot number's chain can be accepted and returned as if it belonged to the currently confirmed fork.

There is a partial mitigation for one path: after the blockstore result comes back, `get_transaction` re-checks `confirmed_bank.status_cache_ancestors().contains(&confirmed_transaction.slot)` using the *original* `confirmed_bank` object (rpc.rs:1808-1811), which is a genuinely fixed, frozen ancestor set. That check does correctly reject slots not in `confirmed_bank`'s real ancestor set. However, this only re-validates the *slot number* returned, not that the *specific transaction-status row* used to build the result actually came from data consistent with `confirmed_bank`'s version of that slot — the underlying `get_complete_transaction`/`AncestorIterator` walk (executed against mutable, concurrently-modified `Blockstore` metadata) is what actually selects which stored row is treated as "confirmed," and that selection is not re-derived from `confirmed_bank` itself.

### Impact Explanation
If a signature is stored under multiple slot rows in the transaction-status column family (which can occur across duplicate/rewritten blocks or forks sharing overlapping ancestry, and is not automatically deduplicated/purged instantly by `LedgerCleanupService`), the RPC's TOCTOU window between capturing `confirmed_bank.slot()` and resolving the ancestor chain on a background thread can let `get_complete_transaction` accept a transaction-status/meta record belonging to an abandoned or unrelated fork version of that slot number as if it were the currently confirmed one. This falls into the allowed "wrong-slot/fork data returned" impact category: an RPC client (e.g., wallet, block explorer, or another validator/service trusting RPC responses) can be served transaction status/metadata (success/failure, fee, balances, logs) that does not correspond to the transaction that actually executed on the currently canonical/confirmed chain, which is the exact "user believes they see confirmed information about the real event, but it is actually stale/wrong-fork data" pattern from the source report's exploit narrative.

### Likelihood Explanation
The race window exists on every `getTransaction` RPC call using `confirmed` commitment with `search_transaction_history` behavior implicit in `get_complete_transaction`'s ancestor walk, since the slot-vs-bank decoupling happens on every call (`spawn_blocking` always introduces a scheduling gap). Triggering it deterministically requires the target slot's on-disk `SlotMeta` parent-chain to be actively transitioning (duplicate-slot resolution, fork switch, or block replacement) concurrently with the RPC call and requires more than one transaction-status row for the queried signature to exist across competing slot versions — conditions that occur naturally during cluster forks/duplicate-block events but are not attacker-controlled on demand from a single unprivileged caller. This raises the likelihood above purely theoretical (the underlying scenario — signature reused across fork history and concurrent blockstore fork mutation — is a normal consensus condition, not a contrived one), but exploiting it reliably as a single deterministic RPC call is not demonstrated here.

### Recommendation
Recommendation, mirroring the source report's short-term fix ("stop relying on identifiers whose backing state can change between check and use; re-validate at use time against the same object used at check time"):
- In `get_complete_transaction`/`get_transaction_status_with_counter`, derive `confirmed_unrooted_slots` from the same `confirmed_bank`'s actual ancestor set (`confirmed_bank.status_cache_ancestors()` or an equivalent bank-derived ancestry) instead of re-walking mutable `Blockstore` `SlotMeta` metadata by raw slot number.
- Alternatively, pass the frozen `Arc<Bank>` (or its ancestor set) into the blocking blockstore call so that fork-membership decisions are made against a fixed snapshot rather than being independently recomputed against blockstore state that can change concurrently.
- Ensure the final acceptance check in `rpc.rs::get_transaction` validates not just the resulting slot number against `confirmed_bank`'s ancestors, but that the specific transaction-status row originated from data consistent with that same bank snapshot.

### Proof of Concept
A full reproduction requires driving a live cluster into a state where: (1) a signature is recorded under transaction-status rows for two different slot-number "versions" of the same slot (e.g., via duplicate-block/fork-switch scenarios exercised in `local-cluster` tests such as those using `AncestorIterator`/`set_dead_slot`/duplicate-shred injection, e.g. `local-cluster/tests/local_cluster.rs:5587-5621`), and (2) issuing `getTransaction` with `commitment: confirmed` for that signature concurrently with the fork-switch/duplicate-slot repair so the `spawn_blocking` ancestor walk in `get_complete_transaction` executes against the transitioning `SlotMeta` state. This was not run against a live cluster; the analysis is based on static code tracing of `rpc.rs::get_transaction` and `blockstore.rs::get_complete_transaction`/`get_transaction_status_with_counter`, and the exact reliability/timing needed to force the race is unverified.
