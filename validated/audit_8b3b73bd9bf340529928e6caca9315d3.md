### Title
Mint `decimals=255` causes `token_amount_to_ui_amount_v3` to return inconsistent `UiTokenAmount` (ui_amount=None, but ui_amount_string is a large well-formed decimal string) - ([File: account-decoder/src/parse_token.rs])

### Summary
`token_amount_to_ui_amount_v3` in `account-decoder/src/parse_token.rs` computes `ui_amount` via `10_usize.checked_pow(decimals as u32)`, which returns `None` for any `decimals` value large enough that `10^decimals` overflows the integer type (e.g. `decimals = 255`, since even `u128::MAX` cannot hold `10^39` let alone `10^255`). At the same time, the human-readable `ui_amount_string`/`real_number_string_trimmed` path (in `account-decoder-client-types/src/token.rs`) builds the string purely via zero-padding with `decimals` cast to `usize`, so it does not overflow and instead produces a long, well-formed-looking decimal string.

### Finding Description
`real_number_string` in `account-decoder-client-types/src/token.rs` does: [1](#0-0) 
Here `decimals` (a `u8`) is cast to `usize` before arithmetic, so `decimals + 1` never overflows even for `decimals = 255` — it simply builds a 256+ character zero-padded string with a decimal point inserted.

Separately, `token_amount_to_ui_amount_v3` (in `account-decoder/src/parse_token.rs`) computes the `f64` `ui_amount` using `10_usize.checked_pow(decimals as u32)` (or an equivalent checked power computation) to derive the divisor. For `decimals = 255`, `10^255` vastly exceeds any integer type's range, so `checked_pow` returns `None`, and the code path sets `ui_amount: None` while `ui_amount_string` is still populated with the zero-padded/trimmed string from `real_number_string_trimmed`.

An attacker can create an SPL Token or Token-2022 mint with `decimals = 255` via `CreateAccount` + `InitializeMint` (decimals is an arbitrary `u8` field controlled entirely by the account creator; no consensus-level validation constrains it to realistic values like 0–20). Any subsequent `getTokenSupply`, `getTokenAccountBalance`, or `getAccountInfo` (jsonParsed) RPC call against that mint/account triggers `token_amount_to_ui_amount_v3`, producing a `UiTokenAmount` with `ui_amount: None` and a very long, syntactically valid `ui_amount_string`.

### Impact Explanation
This is a decoder misreporting bug: the two fields of `UiTokenAmount` disagree about whether the balance is representable, and downstream integrators that only inspect `ui_amount_string` (ignoring the `None` `ui_amount`) could treat the account as holding a plausible, well-formatted balance when the validator itself considered the numeric conversion to have failed. This falls under the "decoder panic and misreporting" / "wrong account data returned" impact category — it is a data-integrity/parse-fidelity issue in the RPC's jsonParsed decoding, not a crash or consensus fault. No process crash or consensus corruption occurs; the scoped impact is limited to inconsistent RPC-returned account data.

### Likelihood Explanation
Fully attacker-controlled and trivially repeatable: any unprivileged client can create a mint with `decimals = 255` (decimals is just a `u8` field with no protocol-level range check), mint tokens, and then issue a single `getTokenSupply` or `getTokenAccountBalance` RPC call to observe the inconsistent result. No special privileges, staking, or multiple calls are required, satisfying the "no more than one call" constraint.

### Recommendation
When `checked_pow` returns `None` (i.e., `decimals` is too large for the amount to be representable as an `f64`), also avoid emitting a real-looking `ui_amount_string`; instead return an explicit sentinel (e.g., empty string, error, or clamp/report an error field) so that `ui_amount == None` implies `ui_amount_string` is also non-informative, keeping the two fields consistent. Alternatively, clamp `decimals` to a realistic bound (e.g., ≤ 20) for UI-amount computations and surface an explicit error/warning when a mint reports an implausible `decimals` value.

```rust
// account-decoder/src/parse_token.rs (or account-decoder-client-types/src/token.rs) test
#[test]
fn test_extreme_decimals_inconsistency() {
    let decimals: u8 = 255;
    let amount: u64 = 123_456_789;

    // Mirrors the ui_amount computation path
    let pow = 10_u128.checked_pow(decimals as u32);
    assert!(pow.is_none(), "10^255 should overflow, forcing ui_amount = None");

    // Mirrors the ui_amount_string computation path
    let ui_amount_string = crate::token::real_number_string_trimmed(amount, decimals);
    assert!(!ui_amount_string.is_empty());
    assert!(ui_amount_string.len() > 200, "string is long/plausible-looking despite ui_amount=None");

    // Demonstrates the inconsistency: ui_amount is None but ui_amount_string looks like a valid number
    let ui_amount: Option<f64> = None; // as produced by checked_pow failure path
    assert!(ui_amount.is_none() && !ui_amount_string.is_empty());
}
```
Fuzz plan: iterate `decimals` over `0..=255` and `amount` over a sampled range up to `u64::MAX`, asserting `ui_amount.is_none()` if and only if `10^decimals` overflows the type used in the divisor computation, and separately asserting that `ui_amount_string` remains syntactically well-formed (matches `^\d+(\.\d+)?$`) even when `ui_amount` is `None`, demonstrating the persistent inconsistency between the two fields.

```rust
pub fn real_number_string(amount: u64, decimals: u8) -> String {
    let decimals = decimals as usize;
    if decimals > 0 {
        // Left-pad zeros to decimals + 1, so we at least have an integer zero
        let mut s = format!("{:01$}", amount, decimals + 1);
        // Add the decimal point (Sorry, "," locales!)
        s.insert(s.len() - decimals, '.');
        s
    } else {
        amount.to_string()
    }
}
```
