### Title
Settled APR0 withdraw principal escapes the stopEpoch loss haircut and is paid at par, draining funded recovery for other claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault._withdrawClaimAmountsForEpoch` only counts a user's *open* APR0 bucket (`apr0Users[_user].principal` when `principalEpoch == _claimEpoch`) in the loss-adjusted claim basis. Once `_settleApr0` moves that principal into `settledPrincipal`/`settledInterest`, it becomes invisible to the loss-adjusted path, so a stopEpochWithDuration haircut is applied to the whole `pendingWithdraws` basis while a user holding a settled APR0 receipt plus a fresh request is paid the settled part at par.

### Finding Description
The bug class of the external report is "a sensitive value is persisted where later logic no longer accounts for it." Here, `_requestWithdrawApr0` calls `_settleApr0`, which moves a matured request's principal into `apr0Users[_user].settledPrincipal` and zeroes `principal`/`principalEpoch` (lines 545-565, 567-577). The strategy-level `pendingWithdraws` and `withdrawsRequestsByEpoch` are *not* reduced by settlement, so the settled amount is still part of the pending basis that `collectWithdrawFunds` haircuts via `lossRecoveryPriceByEpoch[epochNumber]` (lines 411-430).

On claim, `claimWithdrawRequest` runs `_claimLossAdjustedWithdrawRequest` for `lastWithdrawRequest[_user]` (lines 312, 789-801). That path calls `_clearWithdrawClaimForEpoch` → `_withdrawClaimAmountsForEpoch`, which builds `claimBasis` solely from `withdrawsRequestsByEpoch[_user][_claimEpoch]` plus *open* APR0 principal whose `principalEpoch == _claimEpoch` (lines 862-881). `settledPrincipal`/`settledInterest` are ignored. Execution then falls into `_claimFundedWithdrawRequest`, which pays `settledPrincipal + settledInterest` (and any remaining buckets) **at par** via `_transferFundedClaim` (lines 319-350).

The sequence for an unprivileged lender in APR0 mode (`unscaledApr == 0`, not closed):

1. Epoch N: deposit AA, then `requestWithdraw` → APR0 bucket, `pendingWithdraws += amount`.
2. Epoch N stops, epoch N+1 runs and stops: `_settleApr0` now settles (reqEpoch < epochNumber) — but settlement only happens lazily on user actions.
3. Epoch M (> N): the user calls `requestWithdraw` again for a new position. `_requestWithdrawApr0` settles the epoch-N principal into `settledPrincipal`, and records the new request at `principalEpoch = M`. `lastWithdrawRequest[user] = M`.
4. `stopEpochWithDuration`/`stopEpoch` realizes a loss: `collectWithdrawFunds` receives `_amount < pendingWithdraws`, stores `lossRecoveryPriceByEpoch[M] = _amount * 1e18 / pendingBasis` where `pendingBasis` includes the user's settled principal.
5. User calls `claimWithdrawRequest`: gets `claimBasis_M * lossRecoveryPrice` for the epoch-M receipt **plus** the full `settledPrincipal + settledInterest` at par, although the borrower only funded `pendingBasis * lossRecoveryPrice` in aggregate.

The guard at lines 263-271 does not stop this: it only blocks a *new* request when a loss price already exists for the user's `lastWithdrawRequest` epoch; here the loss happens *after* the request that triggered settlement, in the same epoch the request was made.

### Impact Explanation
Direct theft / insolvency. The strategy holds only `pendingBasis * lossRecoveryPrice` for the whole loss-adjusted epoch, but the attacking user extracts `settledPrincipal` at par in addition to their haircut share. Every extra unit paid at par is a unit missing for other claimants of the same (or funded) receipts, breaking the "one receipt, one haircutted payout" invariant and the pro-rata loss socialization promised by `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds`. The quantified excess is `settledPrincipal * (1 - lossRecoveryPrice)` per attacker; with a 50% loss price and e.g. 100k USDC settled principal rolled into a new epoch request, the attacker overdraws ~50k USDC that belongs to other pending or funded claimants, leaving the last claimers' transfers to revert or be unpaid.

### Likelihood Explanation
Requires the APR0 mode (`unscaledApr == 0`), which is a supported configuration exercised by the test suite, and a user who lets an APR0 request mature, then submits a second `requestWithdraw` in an epoch that ends with `stopEpochWithDuration`/`stopEpoch` underfunding. No privileged actor misbehavior is needed — the honest borrower simply repays less than `pendingWithdraws` in a loss epoch, which is a normal supported flow. The attacker only needs KYC'd tranche tokens and standard `requestWithdraw`/`claimWithdrawRequest` calls.

### Recommendation
Include settled APR0 amounts in the loss-adjusted claim basis: in `_withdrawClaimAmountsForEpoch` (or `_clearWithdrawClaimForEpoch`), when the claim epoch's loss price applies, account for `apr0Users[_user].settledPrincipal`/`settledInterest` that originated from epochs covered by the haircut — e.g., track a `settledEpoch` so settled buckets retain their request-epoch attribution — and reduce `pendingWithdraws` accordingly. Alternatively, prevent settlement from erasing epoch attribution, or pay the settled portion through `lossRecoveryPriceByEpoch` of its original request epoch.

### Proof of Concept
A Foundry fork PoC on the existing `IdleCreditVault.t.sol` harness:

```solidity
function testApr0SettledEscapesLossHaircut() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // APR0 mode

    uint256 amount = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amount);          // attacker (this contract)
    _transferBurnedTrancheTokens(address(this), true);
    address victim = makeAddr('victim');
    _depositWithUser(victim, amount, true);

    // Epoch 0: run and stop with interest so the APR0 bucket settles later
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Attacker requests withdraw of full position in epoch 0 (APR0 path)
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Epoch 1 runs and stops -> request matures
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Epoch 2 starts; attacker deposits again and requests withdraw.
    // _requestWithdrawApr0 settles epoch-0 principal into settledPrincipal.
    _startEpochAndCheckPrices(2);
    idleCDO.depositAA(amount);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Victim also requests withdraw in epoch 2 -> shares the same pendingBasis
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // stopEpochWithDuration: borrower funds only 50% of pendingWithdraws
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    deal(defaultUnderlying, borrower, /* active interest + */ pending / 2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(/* loss so pendingToFund == pending/2 */);

    // Attacker claims: haircut on epoch-2 receipt + full settledPrincipal at par
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 attackerPaid = underlying.balanceOf(address(this)) - balPre;

    // attackerPaid > claimBasis * lossRecoveryPriceByEpoch[2]
    // Victim's subsequent claim underflows / receives less than the same haircut.
}
```
