### Title
Claimed instant-withdraw receipts stay in `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, inflating default recovery basis and reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Hats.sol bug class is a pending request that survives the state transition which should have revoked it, so it is honored later under a stale assumption. The direct analog lives in `IdleCreditVault.claimInstantWithdrawRequest`: a fully paid instant-withdraw claim clears only the aggregate `instantWithdrawsRequests[_user]` but never deletes `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If the same epoch later defaults while other instant receipts are still unfunded, `finalizeDefaultRecovery` counts the already-paid (phantom) basis both as pending claim basis and as "prefunded" reserve, inflating `defaultRecoveryPrice` beyond the real backing and letting early claimants steal recovery funds.

### Finding Description
`requestInstantWithdraw` records three ledgers: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . `collectInstantWithdrawFunds` only reduces `pendingInstantWithdraws` [2](#0-1) .

The normal claim path pays the user at par and zeroes only the aggregate mapping. Neither per-epoch ledger is cleared:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [3](#0-2) 

At default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [4](#0-3) , and `_defaultPrefundedInstantReserve` credits `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` as underlying already held by the strategy [5](#0-4) . The phantom entry therefore inflates `totalBasis` and `prefundedReserve` by the same amount `A`, raising `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` without any corresponding tokens in the contract [6](#0-5) . The inflated price also mints phantom active NAV to the CDO via `_mint(idleCDO, activeFinalNAV - activeBalance)` [7](#0-6) .

Attack sequence (all attacker actions are unprivileged; manager/borrower calls are honest sequencing):

1. Running epoch `N`. Attacker (KYC-passed lender) calls `requestInstantWithdraw` for amount `A`. `instantWithdrawClaimsByEpoch[N] = A`, `instantWithdrawsRequestsByEpoch[attacker][N] = A`.
2. Honest manager calls `getInstantWithdrawFunds`; `collectInstantWithdrawFunds(A)` funds the request (`pendingInstantWithdraws` back to 0). Attacker calls `claimInstantWithdrawRequest` and receives `A` at par. The per-epoch entries remain set to `A`.
3. A victim requests an instant withdraw of `B` later in the same epoch `N` before `instantWithdrawDeadline`, or the funding only partially covered the queue. `instantWithdrawClaimsByEpoch[N] = A + B`, `pendingInstantWithdraws = B`.
4. Borrower defaults at `stopEpoch` of epoch `N` (insufficient repayment — a normal credit event, not attacker-caused). Manager calls `finalizeDefault(recovered, source)`.
5. Inside `finalizeDefaultRecovery`: `pendingBasis` includes `A + B`; `_defaultPrefundedInstantReserve` returns `(A + B) - B = A`, crediting `A` phantom tokens that were already paid out. `recoveryPrice` and `activeFinalNAV` are inflated; strategy tokens are minted to the CDO.
6. Any claimant calling `claimInstantWithdrawRequest`/`claimWithdrawRequest` first is paid `claimBasis * inflatedPrice / 1e18` from `defaultRecoveryReserve`, draining real tokens faster than pro-rata. The attacker can participate as an active tranche holder (whose NAV was minted upward) or simply front-run victims. Later claimants find the reserve exhausted; the vault becomes insolvent by roughly `A * (price_inflation)`.

A secondary effect: `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = instantWithdrawsRequestsByEpoch[attacker][N] = A` and then executes `instantWithdrawsRequests[_user] -= claimBasis` on an aggregate that is already 0, which reverts — permanently DoSing that user's `claimInstantWithdrawRequest` entry point [8](#0-7) .

### Impact Explanation
Direct theft / insolvency of the default recovery reserve, quantified by the stale claimed amount `A`: recovery price is inflated by a phantom prefund, so early claimants (including the attacker holding active tranche or other receipts) withdraw more than their fair share and later claimants receive nothing. Broken invariant: the isolated recovery reserve is backed 1:1 — `defaultRecoveryReserve` bookkeeping assumes `prefundedReserve` tokens are held, but `A` was already transferred out. No existing guard stops this: `_transferFundedClaim` only protects the reserve when paying funded claims, and `_ensureDefaultRecoveryInitialized` only gates legacy state [9](#0-8) .

### Likelihood Explanation
Requires three conditions: an instant-withdraw receipt claimed at par, a second unfunded instant receipt in the same epoch, and a borrower default finalized that epoch. Instant withdrawals and partial prefunding are supported paths (the prefunded-reserve logic exists precisely for partially funded queues), and borrower default is a designed-for event. The stale-entry underflow DoS additionally bricks the claim path for any user who claimed and then re-requests in the defaulted epoch. Medium likelihood, medium-high impact.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers for the request epoch when the receipt is fully paid, mirroring the report's `delete linkedTreeRequests[...]` fix:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
uint256 epoch = <request epoch for user>; // must be tracked or iterated
instantWithdrawClaimsByEpoch[epoch] -= instantWithdrawsRequestsByEpoch[_user][epoch];
instantWithdrawsRequestsByEpoch[_user][epoch] = 0;
_transferFundedClaim(_user, amount);
```

Because the current schema does not store which epoch(s) a user's aggregate receipt spans, this likely requires tracking the user's request epoch (e.g., a `lastInstantWithdrawRequest[_user]` marker) or bounding per-epoch iteration. Alternatively, compute `_defaultPrefundedInstantReserve`/`defaultPendingClaimBasis` from actually-funded amounts (`pendingInstantWithdraws` and collected balances) rather than from the cumulative `instantWithdrawClaimsByEpoch` counter.

A Foundry fork PoC (following the harness style of `test/foundry/IdleCreditVault.t.sol`, e.g. `testFundedInstantWithdrawRemainsClaimableAfterStopEpochDefault` at lines 2699–2723 and the partial-prefund default test at lines 4441–4483):

```solidity
function testStaleInstantEpochEntryInflatesRecovery() public {
    // 1. Attacker and victim deposit AA; epoch N starts.
    // 2. Attacker: cdoEpoch.requestInstantWithdraw / requestWithdraw AA -> strategy.requestInstantWithdraw(A, attacker)
    // 3. manager: getInstantWithdrawFunds() -> collectInstantWithdrawFunds(A); pendingInstantWithdraws == 0
    // 4. Attacker: claimInstantWithdrawRequest() -> receives A at par.
    //    assert instantWithdrawsRequestsByEpoch(attacker, N) == A   // stale, never cleared
    //    assert instantWithdrawClaimsByEpoch(N) == A                // stale
    // 5. Victim requests instant withdraw B in same epoch N (before deadline, unfunded).
    // 6. Borrower repays insufficiently; manager stopEpoch -> defaulted.
    // 7. manager: finalizeDefault(recovered, manager)
    //    assert strategy.defaultRecoveryPrice() > honestPrice
    //    where honestPrice recomputes reserve without phantom A.
    // 8. Victim/other claimant claims -> receives more than fair share;
    //    final claimant's transfer reverts / reserve underflows -> insolvency.
}
```

Uncertainty note: I verified the stale-entry persistence and the finalization math directly in `IdleCreditVault.sol`, but I could not fully confirm the CDO-side `getInstantWithdrawFunds` timing rules and whether a second same-epoch instant request can remain unfunded in the same transaction window; the prefunded-reserve code path exists specifically for partial funding, so the required state is reachable, but the PoC author should confirm the instant-withdraw deadline/queue gating in `IdleCDOEpochVariant.sol`.

    uint256 pendingInstant = pendingInstantWithdraws;

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
