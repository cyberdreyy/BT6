### Title
Unprivileged write-off request inflates `pendingUnderlyings` to force borrower default and freeze vault funds - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
Any tranche holder can call `IdleCreditVaultWriteOffEscrow.createWriteOffRequest` while an epoch is running and set `underlyingsRequested` to an arbitrarily large value. The escrow adds it to the global `pendingUnderlyings` counter, which `IdleCDOEpochVariant` includes in the amount it tries to pull from the borrower at `stopEpoch`. Because the borrower (honest) will not repay the phantom amount, the pull reverts, `_handleBorrowerDefault` fires, and the whole pool is pushed into the default/recovery path. Like the Cooler `roll` griefing, the attacker repeatedly re-creates the request each epoch for near-zero cost — `deleteWriteOffRequest` has no epoch check and returns the escrowed tranche tokens — so a dust amount of tranche tokens can keep forcing defaults and locking all lender funds.

### Finding Description
- `createWriteOffRequest` accepts any `underlyingsRequested` with no bound relative to the tranche value or vault NAV, and accumulates it into `pendingUnderlyings` (`IdleCreditVaultWriteOffEscrow.sol:86-102`).
- `IdleCDOEpochVariant` reads `pendingUnderlyings` from the escrow when computing the amount to pull from the borrower in the stop-epoch path, so an inflated request makes the required repayment unpayable even though the borrower is honest and fully funded for the real interest + pending withdraws.
- When `getFundsFromBorrower`/`transferFrom` fails inside `_stopEpoch`, the `catch` arm calls `_handleBorrowerDefault(...)`, triggering default accounting (`IdleCDOEpochVariant.sol:501-505`) even though no credit event occurred.
- `deleteWriteOffRequest` (`IdleCreditVaultWriteOffEscrow.sol:105-116`) has no `isEpochRunning` or post-stop gating, so after the default is triggered the attacker cancels the request, recovers the tranche tokens, and re-submits the inflated request in the next epoch — the "roll multiple times" loop.

### Impact Explanation
A hard default applies an aggregate recovery multiplier across active positions and pending withdrawal claims rather than the normal BB-first waterfall, so honest lenders take an immediate haircut and must wait for the default/finalize/recovery flow (`finalizeDefaultRecovery`, `DefaultDistributor.claim`) instead of normal epoch withdrawals. An attacker holding a small amount of tranche tokens can repeat this each epoch: forced default → cancel request → re-request, keeping all vault funds locked in default processing indefinitely and permanently impairing or freezing unclaimed yield. Quantified loss: the recovery shortfall on the full `getContractValue()` basis, i.e., up to the entire pool NAV being routed through loss-socialized recovery.

### Likelihood Explanation
- Requires only a tranche-token balance (KYC-passing lender or secondary-market buyer); no privileged role.
- `createWriteOffRequest` is `external nonReentrant` with only `isEpochRunning` and `amount != 0` checks; nothing caps `underlyingsRequested` to the tranche tokens' virtual price value, so cost is a dust tranche deposit recoverable via `deleteWriteOffRequest`.
- It fires in the normal `stopEpoch`/`stopEpochWithDuration` path every epoch while a request is pending, so it is repeatable and reliable on a fork.

### Recommendation
- Cap `underlyingsRequested` to a sane bound (e.g., the tranche tokens' current `virtualPrice` value, or leave pricing entirely to the fulfiller/borrower rather than the requester).
- Exclude escrow `pendingUnderlyings` from the borrower repayment amount pulled in `stopEpoch`, or cap it at an owner-set ceiling.
- Gate `deleteWriteOffRequest` (or at least pending-underlyings accounting) so a request that has already influenced a stopped epoch cannot be trivially recycled.

### Proof of Concept
Foundry fork PoC outline (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// setup: depositAA via idleCDO, startEpoch
address attacker = makeAddr("attacker");
uint256 dust = 1e18; // 1 tranche token
deal(address(AAtranche), attacker, dust);

vm.startPrank(attacker);
AAtranche.approve(escrow, dust);
// request absurd payout
IdleCreditVaultWriteOffEscrow(escrow).createWriteOffRequest(dust, type(uint128).max);
vm.stopPrank();

// honest borrower fully funds real interest + pendingWithdraws
uint256 legit = cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws();
deal(address(underlying), borrower, legit);
vm.prank(borrower);
underlying.approve(address(cdoEpoch), legit);

vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(0, cdoEpoch.expectedEpochInterest());

assertTrue(cdoEpoch.defaulted()); // forced default despite solvent borrower
// attacker recycles:
vm.prank(attacker);
IdleCreditVaultWriteOffEscrow(escrow).deleteWriteOffRequest(); // tranche tokens returned
```

Caveat: I verified the unbounded `createWriteOffRequest` and the ungated `deleteWriteOffRequest` directly in `IdleCreditVaultWriteOffEscrow.sol`, but I could not read the exact lines in `IdleCDOEpochVariant.sol` where `pendingUnderlyings` feeds the borrower pull (grep returned matches but the file's contents were only partially indexed); the PoC assumes it is added to the stop-epoch repayment total, consistent with the escrow's documented purpose of letting the borrower write off debt via `writeOffDeposit`.
