### Title
Unbounded iteration over `registeredWorkflows` in `triggerConnectorHandler.processTrigger` allows any unprivileged Gateway caller to trigger O(n·m) work per webhook message - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
`triggerConnectorHandler.processTrigger` iterates over every entry of `h.registeredWorkflows` (and, nested inside, every topic on the incoming payload) on each inbound `MethodWebAPITrigger` gateway message, with no cap on the number of registered workflows or topics per message. This mirrors the reported `NFTXEligiblityManager.distribute` bug class: an unbounded loop over a collection whose size is not capped, driven by unprivileged/external input, causing per-request cost to scale linearly (here, quadratically with topics) with the number of workflows registered on the node.

### Finding Description
`RegisterTrigger` inserts into the `registeredWorkflows` map with no upper bound check on the number of entries: [1](#0-0) 

Every inbound webhook trigger message received from the Gateway (which is reachable by any external, unauthenticated-to-the-node caller hitting the Gateway's HTTP trigger endpoint) is routed to `processTrigger`: [2](#0-1) 

`processTrigger` then performs a full, unbounded double loop — outer over `h.registeredWorkflows` and inner over `payload.Topics` (attacker-supplied) — for every single incoming message: [3](#0-2) 

There is no limit on:
- the number of workflows that can be registered via `RegisterTrigger` (no `maxRegistrations`/cap found),
- the number of `Topics` an external sender can include in a single trigger payload (`payload.Topics` is attacker-controlled, only checked for non-empty).

As registered workflows and/or attacker-supplied topics grow, the per-message CPU cost of `processTrigger` grows unbounded, directly analogous to the `_feeReceivers` loop in the referenced report: a collection with no size cap is fully iterated on every externally triggerable call.

### Impact Explanation
Each Gateway node that runs the `webapi` trigger capability performs this scan synchronously while holding `h.mu` (implicitly, since callers of `RegisterTrigger`/`UnregisterTrigger` take `h.mu.Lock()`, though `processTrigger` itself reads the map without a lock — a related but separate data-race concern). A caller with knowledge of a valid `sender` address for any registered workflow (or simply a Gateway-reachable sender) can send trigger messages with a large `Topics` array; the cost of processing that single message scales with `len(registeredWorkflows) × len(topics)`. As more workflows are onboarded to a shared web-API-trigger capable node, the fixed per-message cost paid by every trigger event increases, and a malicious/careless external caller can amplify this cost by supplying many topics in one request, degrading trigger processing latency/availability for all workflows sharing that node (a soft DoS on the node's webhook-trigger throughput). This does not directly enable fund movement or auth bypass, but it degrades availability of an internet-facing entry point in a way that scales with attacker input, which is the same class of bug flagged in the reference finding (self-confirmed but "keep the number of receivers small" — here there is no such enforced bound at all).

### Likelihood Explanation
Likelihood is moderate: it requires (a) that the operator has registered a non-trivial number of workflows on the webapi-trigger capability of a given node, and (b) that an external caller sends a trigger payload with an inflated `Topics` list. Both `RegisterTrigger` and inbound trigger messages are on paths that are reachable without node-operator privileges (workflow registration is done by workflow owners/tenants, and inbound trigger messages come from arbitrary external HTTP callers relayed through the Gateway). No authentication step in this path enforces an upper bound on topics or on the number of concurrently registered workflows.

### Recommendation
- Enforce a maximum number of `Topics` accepted per inbound trigger payload in `processTrigger` (reject with an error before iterating if `len(topics)` exceeds a sane bound).
- Enforce a maximum number of concurrently `registeredWorkflows` per `triggerConnectorHandler` instance, similar to other rate/size limits already present elsewhere in the gateway handlers (e.g., `ratelimit.RateLimiterConfig` patterns used in this same file).
- Consider indexing registered workflows by topic (a `map[topic][]*webapiTrigger`) instead of scanning the full `registeredWorkflows` map on every message, to make lookup cost proportional to matched topics rather than total registered workflows.
- Take the read lock (`h.mu`) around the read of `h.registeredWorkflows` in `processTrigger` for correctness in addition to the size-based fix.

### Proof of Concept
1. Register N workflows (e.g., N = 10,000) against a single Gateway node via `RegisterTrigger` (`core/capabilities/webapi/trigger/trigger.go:196-253`), each with a large `AllowedTopics` config — nothing in the code path enforces an upper bound on N or on `AllowedTopics` size.
2. Send a single `MethodWebAPITrigger` message via the Gateway with `payload.Topics` containing many (e.g., thousands of) attacker-chosen topic strings.
3. `HandleGatewayMessage` → `processTrigger` (`trigger.go:151-184`, `79-149`) executes a nested loop of size `N × len(Topics)` synchronously for this single message, consuming CPU proportional to both attacker input and total registrations — with no bound on either dimension.

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

	switch body.Method {
	case ghcapabilities.MethodWebAPITrigger:
		resp := h.processTrigger(ctx, gatewayID, body, sender, payload)
		var response ghcapabilities.TriggerResponsePayload
		if resp == nil {
			response = ghcapabilities.TriggerResponsePayload{Status: "ACCEPTED"}
		} else {
			response = ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: resp.Error()}
			h.lggr.Errorw("Error processing trigger", "gatewayID", gatewayID, "body", body, "response", resp)
		}
		err = h.sendResponse(ctx, gatewayID, body, response)
		if err != nil {
			h.lggr.Errorw("Error sending response", "body", body, "response", response, "err", err)
		}
		return nil
