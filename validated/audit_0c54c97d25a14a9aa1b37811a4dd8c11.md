### Title
Replay guard TTL is fully attacker-controlled via JWT `exp`, allowing a duplicate vault mutation replay - ([File: core/capabilities/vault/request_replay_guard.go])

### Summary
`RequestReplayGuard.CheckAndRecord` records a digest's expiry using whatever `expiresAtUnix` value is passed in, with no server-enforced minimum lifetime. That value comes directly from `AuthResult.ExpiresAt()`, which for JWT-based auth is derived as `claims.ExpiresAt + jwtValidationLeeway` [1](#0-0) . Because the JWT parser accepts tokens up to `jwtValidationLeeway` (1 minute) past their nominal `exp` [2](#0-1) , a token whose `exp` is deliberately set near `now - leeway` still validates successfully while producing an `authExpiresAt` at or very near the current time, collapsing the replay window to seconds instead of the intended full validation window.

### Finding Description
`CheckAndRecord` stores `g.seen[digest] = expiresAtUnix` verbatim and purges any entry once `now > expiry` [3](#0-2) . The `expiresAtUnix` argument is `authResult.ExpiresAt()`, called from `authorizer.AuthorizeRequest` immediately after auth succeeds [4](#0-3) .

For the JWT path, `authExpiresAt` is computed as `claims.ExpiresAt.UTC().Add(jwtValidationLeeway).Unix()` [1](#0-0) , and `jwt.Parse` is configured with `jwt.WithLeeway(jwtValidationLeeway)` (1 minute) [2](#0-1) . The `jwt.WithLeeway` option makes the library accept tokens whose `exp` is already up to `leeway` in the past. Consequently, a token with `exp = now - leeway` (or close to it) still passes validation, but `authExpiresAt = exp + leeway ≈ now`, producing a replay-guard TTL of essentially zero instead of the intended full JWT lifetime.

The digest recorded in the guard is bound to the request content (`req.Digest()` must match `claims.RequestDigest`) rather than to the client-supplied `req.ID`. Deduplication at the gateway handler level (`h.activeRequests`) is keyed by the caller-controlled JSON-RPC `req.ID`, not by digest [5](#0-4) , and completed requests are removed from that map once a response is sent [6](#0-5) . This means `activeRequests` provides no protection against a resubmission that uses a different `req.ID` value with identical `Params`/digest — it only prevents two concurrent requests from colliding on the *same* ID.

Given a second freshly-issued JWT bound to the same `request_digest` claim (per the described precondition, the attacker can mint/hold JWTs with an attacker-chosen short `exp`), the attacker can: (1) submit request A authorized by token T1 whose crafted `exp` makes `authExpiresAt ≈ now`; (2) as soon as the guard's cleanup logic purges the now-expired entry (which happens on the very next `CheckAndRecord`/`ClearExpired` call, potentially within the same processing window as the original mutation is still executing against the vault DON); (3) resubmit the identical request content (different `req.ID`, new token T2 with the same digest claim) — `CheckAndRecord` treats it as unseen and authorizes it again, causing the vault DON to execute the create/update/delete mutation a second time.

### Impact Explanation
This corresponds to duplicate execution of an authorized vault mutation (create/update/delete of a secret) from what should be a single one-shot authorized action — matching the "unauthorized/duplicated job run or state mutation" bounty impact class. The impact is scoped to duplicate processing of the attacker's own authorized action; it does not grant access to another user's secrets or escalate privileges, since digest/owner binding (`validateSecretOwnersMatchAuthorized`) is unaffected. The severity is bounded but real: it can cause race-y double-writes or double-deletes when a semantically single mutation is expected to be atomic/idempotent-once.

### Likelihood Explanation
Requires the attacker to be able to obtain multiple JWTs bound to the same `request_digest` claim with attacker-influenced `exp` values — a non-trivial precondition depending on how the token-issuing service (Auth0/CRE platform) exposes token minting for a given digest, but is stipulated as available per this audit's threat model. Given that precondition, the exploit is deterministic and reproducible: the leeway-based floor computation always yields the same near-zero-TTL behavior for any token whose `exp` is set near `now - jwtValidationLeeway`.

### Recommendation
Do not rely solely on the attacker/token-supplied `exp` for the replay-guard TTL. Enforce a server-side minimum replay-protection window (e.g., `max(claims.ExpiresAt + leeway, now + minimumReplayWindow)`), or better, track replay state based on server-observed request completion (e.g., keep the digest "seen" until the corresponding `activeRequest` is cleared/completed) rather than purely on a client-influenced expiry timestamp. Additionally, consider keying `activeRequests` (or an additional dedup guard) by the authorized digest rather than solely by the client-supplied `req.ID`, so a resubmission with a different ID but identical content cannot bypass in-flight tracking.

### Proof of Concept
1. Unit test in `core/capabilities/vault/request_replay_guard_test.go` style:
   - Create `RequestReplayGuard`, set `nowFunc` to a fixed `t0`.
   - Call `CheckAndRecord("digest-A", t0.Unix())` (expiry == now) — expect `nil` error.
   - Advance `nowFunc` by 1 second (simulating processing latency during which the DON is still executing the mutation).
   - Call `CheckAndRecord("digest-A", t0.Add(...).Unix())` again — expect `nil` (no `ErrRequestAlreadySeen`), demonstrating the digest was purged and reusable almost immediately.
2. Integration-level PoC in `core/capabilities/vault/jwt_based_auth_test.go` / `authorizer_test.go`:
   - Construct a valid JWT with `exp = now - jwtValidationLeeway + 1s` (just inside the leeway) and `authorization_details` containing a fixed `request_digest`.
   - Call `jwtBasedAuth.AuthorizeRequest` and confirm it succeeds, and assert `authResult.ExpiresAt()` is `~= now`.
   - Feed the same `AuthResult` through `authorizer.AuthorizeRequest` twice, with a short sleep in between, using two synthetically constructed `AuthResult`s (same digest, second one's `ExpiresAt` recomputed via a freshly "issued" token) to show the second call is not rejected by `ErrRequestAlreadySeen`.
3. Handler-level integration test in `core/services/gateway/handlers/vault/handler_test.go`:
   - Send `MethodSecretsDelete` (or create/update) with `req.ID = "id-1"` and JWT auth as above; let it complete (DON responds, entry removed from `activeRequests`).
   - Resend an identical `Params` payload with `req.ID = "id-2"` and a second JWT for the same digest.
   - Assert both requests reach `fanOutToVaultNodes`/produce two successful DON mutation calls, confirming `activeRequests` (keyed by `req.ID`) does not prevent the duplicate execution.

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) sendResponse(ctx context.Context, userRequest *activeRequest, resp gwhandlers.UserCallbackPayload) error {
	switch resp.ErrorCode {
	case api.StaleNodeResponseError:
	case api.FatalError:
	case api.NodeReponseEncodingError:
	case api.RequestTimeoutError:
	case api.HandlerError:
	case api.ConflictError:
	case api.LimitExceededError:
		h.metrics.requestInternalError.Add(ctx, 1, metric.WithAttributes(
			attribute.String("don_id", h.donConfig.DonId),
			attribute.String("error", resp.ErrorCode.String()),
		))
	case api.InvalidParamsError:
	case api.UnsupportedMethodError:
	case api.UserMessageParseError:
	case api.UnsupportedDONIdError:
		h.metrics.requestUserError.Add(ctx, 1, metric.WithAttributes(
			attribute.String("don_id", h.donConfig.DonId),
		))
	case api.NoError:
		h.metrics.requestSuccess.Add(ctx, 1, metric.WithAttributes(
			attribute.String("don_id", h.donConfig.DonId),
		))
	}

	err := userRequest.SendResponse(resp)
	if err != nil {
		h.lggr.Errorw("error sending response to user", "requestID", userRequest.req.ID, "error", err)
		return err
	}

	h.mu.Lock()
	defer h.mu.Unlock()
	delete(h.activeRequests, userRequest.req.ID)
	h.lggr.Debugw("response sent to user", "requestID", userRequest.req.ID, "errorCode", resp.ErrorCode)
	return nil
