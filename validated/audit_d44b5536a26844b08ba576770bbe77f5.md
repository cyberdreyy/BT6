### Title
Legacy DON-ID gateway path fans out messages from unregistered senders to all DON members due to missing sender/DON-membership check - (File: core/services/gateway/gateway.go / core/services/gateway/handlers/capabilities/handler.go)

### Summary
`gateway.ProcessRequest` resolves the legacy handler solely by `Body.DonId` and invokes `HandleLegacyUserMessage` as soon as `msg.Validate()` (a signature-format/recovery check only) passes, without verifying that the recovered `Body.Sender` is a member of the target DON. `HandleLegacyUserMessage` in the capabilities handler has an explicit `TODO: apply allowlist and rate-limiting here` and unconditionally forwards the request to every node in `donConfig.Members`.

### Finding Description
An attacker with any ECDSA keypair (not registered with any DON) can construct a legacy `api.Message` with a valid signature, set `Body.DonId` to any configured legacy DON, and send it to the gateway's user-facing HTTP endpoint. `msg.Validate()` [1](#0-0)  only checks field lengths/format and recovers the signer into `Body.Sender` — it performs no lookup against the DON's member/allowlist. `ProcessRequest` then looks up the handler purely by `handlerKey = msg.Body.DonId` and calls `h.HandleLegacyUserMessage(ctx, msg, callback)` [2](#0-1) . Inside the capabilities handler, `HandleLegacyUserMessage` performs payload decode/timestamp/method checks but never checks `msg.Body.Sender` against `h.donConfig.Members`, then loops over all `h.donConfig.Members` and calls `don.SendToNode` for each [4](#0-3) . This confirms the message from a non-member sender is still fanned out to every DON node.

### Impact Explanation
This allows an unauthenticated/unprivileged attacker to inject arbitrary `web_api_trigger` requests toward all nodes of any DON configured with the legacy handler, effectively bypassing the sender allowlist that is supposed to gate which external parties can trigger DON node work. This matches a request-forgery / allowlist-bypass impact class — unauthorized nodes receive attacker-controlled trigger payloads that they will process as if from a legitimate registered caller, potentially triggering workflow executions or consuming node resources without authorization.

### Likelihood Explanation
Trivially exploitable: no privileged credentials are needed, only an arbitrary keypair to sign a message satisfying `Validate()`'s syntactic checks. The DON ID is a public/discoverable configuration value. This is fully repeatable and requires no race conditions or special timing beyond the message's timestamp not being stale.

### Recommendation
In `HandleLegacyUserMessage` (or earlier in `ProcessRequest` for the legacy path), verify `msg.Body.Sender` against `h.donConfig.Members` (or an equivalent allowlist) before saving the callback and fanning out via `don.SendToNode`, rejecting with an authorization error if the sender is not a recognized member/allowed caller of the target DON.

### Proof of Concept
1. In a test using `newGatewayWithMockHandler` (or constructing the real `capabilities.handler` with a `config.DONConfig` containing known member addresses), sign an `api.Message` with a throwaway key not present in `donConfig.Members`, targeting the DON's `DonId` with method `web_api_trigger` and a valid `TriggerRequestPayload`.
2. Call `gateway.ProcessRequest` with the serialized JSON-RPC request.
3. Assert that `don.SendToNode` (mocked) is invoked for DON members despite the non-member signer — demonstrating the fan-out occurs.
4. After the fix, assert `HandleLegacyUserMessage` returns/sends an authorization error and `SendToNode` is never called.

	}

		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
