### Title
Stale Confirmations From Removed Multisig Members Count Toward Execution Threshold - (File: multisig2/src/lib.rs)

### Summary
In `multisig2/src/lib.rs`, `delete_member` only purges pending requests that were *created* by the removed member, but never purges that member's *confirmations* on requests created by other, still-active members. As a result, a signature collected from a member before they were removed continues to count toward `num_confirmations` after removal, allowing a request to execute with fewer genuinely live confirmations than the configured threshold requires.

### Finding Description
The invariant the multisig is supposed to enforce is: `confirmations counted for a request == confirmations from currently active members`. `confirm()` simply compares `confirmations.len() + 1` against `self.num_confirmations`: [1](#0-0) 

`delete_member` is the only place membership removal is handled, and it cleans up `requests`/`confirmations` **only for requests whose creator (`r.member`) equals the removed member**: [2](#0-1) 

It does not scan `self.confirmations` for entries where the removed member appears as a *confirmer* of a request created by someone else. Those stale entries remain in the `confirmations` `HashSet<String>` for that `request_id` and are still counted by the `>=` comparison in `confirm()`.

Concretely: with members {A, B, C, D} and `num_confirmations = 3`, A creates a request; A and C confirm (2 of 3, below threshold). Members subsequently remove C from the multisig (a legitimate/malicious governance action, e.g. because C's key was compromised or offboarded). C is deleted from `self.members`, but C's confirmation entry in the pending request's `confirmations` set is untouched. B later confirms: `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → the request executes, even though only A and B are actually live signers who approved it — one fewer live confirmation than the threshold requires.

The equality broken is:
`confirmations_recorded_for_request == confirmations_from_currently_live_members`
After C's removal this becomes `3 counted != 2 actually live`, yet the contract still executes the transfer/action.

### Impact Explanation
This lets a multisig execute a request (including `Transfer`, `FunctionCall`, `AddKey`, etc.) with fewer live-member approvals than `num_confirmations` mandates. Per the impact taxonomy, this is a Critical finding: "a multisig request executed below threshold." Funds or permissions controlled by the multisig can move without the intended level of authorization — effectively lowering the security threshold silently whenever a member who had confirmed an outstanding request is later removed.

### Likelihood Explanation
No privileged actor, redeploy, or victim key is required beyond the normal, documented multisig operations (`add_request`, `confirm`, and a legitimate `DeleteMember` action executed through the multisig itself). Member turnover (revoking a departing or suspected-compromised signer) is a routine, expected operation, and any request left pending with that member's prior confirmation becomes exploitable the moment the remaining members later add one more confirmation. This is a straightforward, unprivileged-from-the-remaining-signers'-perspective sequencing bug, not a theoretical edge case.

### Recommendation
When executing `DeleteMember` (and `AddKey`/`DeleteKey` analogs where relevant to `MultisigMember::AccessKey`), iterate over all pending `requests`/`confirmations` and remove the deleted member's entry from every confirmations set it appears in (not only requests it authored), and re-check whether the request still needs the confirmation count re-derived against the new active member set. Alternatively, validate at `confirm()`-time / execution-time that every account/key in a request's `confirmations` set still belongs to `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`. [3](#0-2) 
2. A calls `add_request_and_confirm(request)` → confirmations = {A}. [4](#0-3) 
3. C calls `confirm(request_id)` → confirmations = {A, C} (2/3, not executed). [5](#0-4) 
4. Members separately pass a `DeleteMember { member: C }` request through the multisig; `delete_member` removes C from `self.members` and only purges requests C had *created*, leaving the pending request's confirmations set `{A, C}` intact. [2](#0-1) 
5. B calls `confirm(request_id)`: `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request` runs the original request (e.g., a `Transfer`), even though C is no longer a member and only A and B are genuinely live approvers. [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
