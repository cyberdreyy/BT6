### Title
Multisig request execution counts stale confirmations from removed/compromised members, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
The `MultiSigContract` enforces a `k`-of-`n` confirmation threshold, but confirmations previously recorded by a member are never purged from *other pending requests* when that member is deleted via `DeleteMember` (or `DeleteKey` in `multisig` v1). Only requests the deleted member *authored* are cleaned up. This lets a request execute using a stale confirmation from an account that is no longer a member (e.g., removed because its key was compromised), breaking the binding: "confirmations counted must equal confirmations from currently-live members."

### Finding Description
`confirm()` checks the threshold purely by counting entries in the `confirmations` set for a request: [1](#0-0) 

When a member is removed, `delete_member()` only removes requests *created by* that member and clears their `num_requests_pk` counter — it does not scan `confirmations` for other pending requests the member has already confirmed: [2](#0-1) 

The same gap exists in the older `multisig` contract's `DeleteKey` handling, which likewise only purges requests signed (authored) by the deleted public key, not confirmations that key gave on other requests: [3](#0-2) 

`assert_valid_request()`/`current_member()` only validate the *caller* of the current call against the live `members` set — they never re-validate confirmations already stored from members who have since been removed: [4](#0-3) [5](#0-4) 

As a result, the effective binding the protocol relies on — "a request executes only if `num_confirmations` *live* members approved it" — is broken; it is actually "a request executes if `num_confirmations` *entries* (live or stale) exist in the confirmations set."

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." Concretely: if a member's key is compromised (the exact scenario in the referenced report) and that member had already confirmed one or more pending requests (e.g., a `Transfer` or `FunctionCall` request) before the compromise was detected and the member removed, those stale confirmations remain valid and countable. The remaining live members, believing they are enforcing a `k`-of-`n` policy among currently trusted signers, can inadvertently (or an attacker who still controls fewer live keys than `k` can maneuver to) push the request past the threshold using the compromised/removed member's leftover confirmation — executing fund transfers, key additions, or other privileged actions with fewer genuine approvals than the multisig's stated security threshold.

### Likelihood Explanation
This requires no privileged access beyond a scenario the multisig is explicitly designed to defend against: a key becoming compromised. It is a normal, expected operational event (the entire point of `DeleteMember`/`DeleteKey` is to respond to key compromise), and the flaw triggers automatically whenever a compromised member had confirmed — but not authored — a pending request prior to removal. No social engineering, redeploy, or foundation/owner action beyond routine multisig membership management is needed.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over all pending requests' `confirmations` sets (not just requests authored by that member) and strip that member's entry, or alternatively re-validate at execution time that every entry in a request's `confirmations` set still corresponds to a current member of `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Multisig deployed with members `[A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request` creating request `R` (e.g. `Transfer` to some `receiver_id`) — no auto-confirm.
3. `B` calls `confirm(R)` → `confirmations(R) = {B}`.
4. `C` calls `confirm(R)` → `confirmations(R) = {B, C}` (below threshold, request stays pending).
5. `B`'s key is compromised; the group detects this and submits/executes a separate `DeleteMember{ member: B }` request, which succeeds and removes `B` from `self.members`. Per `delete_member`, only requests *authored* by `B` are purged — `R` (authored by `A`) is untouched, and its `confirmations` set still contains `B`.
6. `D` calls `confirm(R)` → `confirmations(R).len() (2) + 1 >= num_confirmations (3)` → request `R` executes.
7. Result: `R` executed with confirmations from `{B (removed), C, D}` — i.e., only 2 of the 3 *live* members (`A, C, D`) actually approved it, yet the contract treated the removed member `B`'s stale confirmation as equivalent to a live approval, executing the request below the intended live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
