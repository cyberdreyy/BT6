## Title
Missing `return` After Failed Email Claim Extraction Allows Authenticated Session Creation on Error Path in `handleTokenExchange()` - (File: `core/sessions/oidcauth/oidc.go`)

### Summary
`handleTokenExchange()` extracts the `email` claim from a verified OIDC ID token via an unchecked type assertion. When the assertion fails, the handler writes an error response but — unlike every other failure branch in the same function — does not `return`, so execution falls through and completes the full login flow: a session is created, persisted, and a `200 OK` success response is written on top of the earlier error.

### Finding Description
In `handleTokenExchange()`, all prior validation failures correctly abort the request: [1](#0-0) [2](#0-1) 

But the email extraction block omits the `return`: [3](#0-2) 

Execution continues into role mapping, session insertion, audit logging, cookie save, and finally a second, conflicting response write: [4](#0-3) 

`ExchangeTokenResponse{Success: true}` is written via `c.JSON(http.StatusOK, ...)` after the earlier `c.String(http.StatusInternalServerError, ...)` call, and a valid session cookie (`webauth.SessionIDKey`) is set via `ginSession.Save()` regardless of the missing/malformed email. This is directly analogous to the reported bug class: a value is derived from an unverified/incorrect extraction path, is not gated by proper control flow, and is silently propagated into security-relevant downstream logic (session creation) rather than aborting the operation as the code's own error-handling intent requires.

### Impact Explanation
This is a fail-open defect in the OIDC authentication flow: the code's own logic determines the exchange should fail (writing a `500` error) when it cannot resolve the user's email, yet the request still succeeds in creating a persisted, cookie-backed authenticated session in `oidc_sessions` with the role derived from `IDClaimsToUserRole()` and an empty `user_email`. Any client whose verified ID token omits a string `email` claim (e.g., an IdP account without a verified/public email, or non-string email claim types) still receives a working session cookie and a role assigned from group claims, despite the intended rejection. This undermines the authentication gate for the web/API session used to determine role-based access (`clsessions.UserRoleAdmin/Edit/Run/View`), since a login attempt meant to be denied instead succeeds.

### Likelihood Explanation
Reachable directly by any client hitting the internet/browser-facing `/oidc-exchange` endpoint as part of the standard, unprivileged OIDC login flow: [5](#0-4)  Triggering it only requires completing an OIDC code exchange whose resulting ID token lacks a string `email` claim — a condition that is plausible with many real-world IdP configurations (unverified email, non-standard claim shape, or a misconfigured/self-registered account), making this a moderately likely occurrence in production rather than a purely theoretical edge case.

### Recommendation
Add the missing `return` immediately after writing the error response:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Additionally, apply the same fix pattern check to the `oidc_sessions` INSERT failure path at line 257-260, which also logs an error but does not `return`, allowing the flow to continue to `c.JSON(http.StatusOK, ...)` even when session persistence failed.

### Proof of Concept
1. Configure/complete an OIDC login using an identity provider account whose ID token does not include a string `email` claim (e.g., unverified email account, or an IdP that returns `email` as `null`/non-string).
2. Client calls `POST /oidc-exchange` with valid `code`/`state`.
3. Server logs `"Failed to get email from claims"` and writes a `500` response body, but does not return.
4. Server proceeds to compute a role via `IDClaimsToUserRole` from the (unrelated) ID claims, inserts a row into `oidc_sessions` with an empty `user_email`, sets the session cookie via `ginSession.Save()`, and writes a second `200 OK` `{"success":true}` response.
5. The returned session cookie is a valid, usable authenticated session recognized by `AuthorizedUserWithSession()`, despite the intended failure of the exchange.
