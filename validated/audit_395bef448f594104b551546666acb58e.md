### Title
Cross-Chain Nonce Collision in `isTransferProcessed` Enables Permanent Fund Lock — (File: `bridge/evm/contracts/SuiBridge.sol`)

---

### Summary

`SuiBridge.transferBridgedTokensWithSignatures` tracks processed token-transfer messages with a flat `mapping(uint64 nonce => bool isProcessed) public isTransferProcessed` keyed only by `message.nonce`. The source-chain identifier (`message.chainID`) is never included in that key. Because each supported source chain maintains its own independent nonce sequence starting at 0, two committee-signed transfers from different source chains that share the same nonce value will collide: whichever is submitted first marks `isTransferProcessed[N] = true`, and the second is permanently rejected with `"SuiBridge: Message already processed"`, locking the originating funds forever.

---

### Finding Description

`BridgeConfig` maintains a `mapping(uint8 chainId => bool isSupported) public supportedChains` that can hold multiple source-chain IDs. [1](#0-0) 

The `onlySupportedChain` modifier in `SuiBridge` only verifies that `message.chainID` is in that set; it does not enforce a single source chain. [2](#0-1) 

`MessageVerifier.verifyMessageAndSignatures` explicitly **skips** the chain-ID equality check and the sequential-nonce check for `TOKEN_TRANSFER` messages:

```solidity
if (messageType != BridgeUtils.TOKEN_TRANSFER) {
    require(message.chainID == committee.config().chainID(), ...);
    require(message.nonce == nonces[message.messageType], ...);
    nonces[message.messageType]++;
}
``` [3](#0-2) 

The only replay guard for token transfers is therefore:

```solidity
require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");
...
isTransferProcessed[message.nonce] = true;
``` [4](#0-3) [5](#0-4) [6](#0-5) 

`message.chainID` is never part of the key. Two distinct messages — one from `chainID=A, nonce=N` and one from `chainID=B, nonce=N` — map to the same slot `isTransferProcessed[N]`. The same flaw is inherited verbatim by `SuiBridgeV2.transferBridgedTokensWithSignaturesV2`, which reads and writes the same mapping. [7](#0-6) [8](#0-7) 

The multi-chain configuration is not hypothetical: `BridgeLimiterTest.t.sol` deploys a bridge with two source chains (chainID=11 and chainID=12) and exercises per-chain limits, confirming the design intent. [9](#0-8) 

---

### Impact Explanation

When two source chains are active, every nonce value is shared across both chains. The very first transfer from each chain (nonce=0) will collide. Whichever is submitted first succeeds; the second is permanently rejected. The originating assets (locked on the source chain at deposit time) can never be claimed on the EVM side and cannot be recovered on the source chain either, because the source-chain lock is irrevocable once the deposit event is emitted. This constitutes **permanent fund lock**, matching the High/Medium impact class in the HackenProof Sui Protocol scope.

---

### Likelihood Explanation

The bridge is explicitly designed to support multiple source chains. The `BridgeConfig.supportedChains` mapping accepts an arbitrary list of chain IDs at initialization and can be extended via governance. Each source chain's nonce counter starts at 0 and increments independently, so a collision at nonce=0 is guaranteed the moment a second source chain is added — no adversarial action is required. Any unprivileged user who holds a valid committee-signed message (which is public once the bridge node broadcasts it) can front-run the competing chain's submission and trigger the permanent block.

---

### Recommendation

Key `isTransferProcessed` by the composite `(chainID, nonce)` pair:

```solidity
// Before
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;

// After
mapping(uint8 chainID => mapping(uint64 nonce => bool isProcessed)) public isTransferProcessed;
```

Update both the read and write sites in `SuiBridge.transferBridgedTokensWithSignatures` and `SuiBridgeV2.transferBridgedTokensWithSignaturesV2`:

```solidity
require(!isTransferProcessed[message.chainID][message.nonce], "SuiBridge: Message already processed");
...
isTransferProcessed[message.chainID][message.nonce] = true;
```

---

### Proof of Concept

```solidity
// Setup: bridge configured with two source chains: chainID=0 and chainID=1

// Step 1 – Chain-0 transfer with nonce=0 (committee-signed, valid)
BridgeUtils.Message memory msgA = BridgeUtils.Message({
    messageType: BridgeUtils.TOKEN_TRANSFER,
    version: 1,
    nonce: 0,
    chainID: 0,          // source = chain 0
    payload: payloadA    // recipient = alice, 1 ETH
});
bridge.transferBridgedTokensWithSignatures(signaturesA, msgA);
// isTransferProcessed[0] = true  ← slot keyed only by nonce

// Step 2 – Chain-1 transfer with nonce=0 (also committee-signed, also valid)
BridgeUtils.Message memory msgB = BridgeUtils.Message({
    messageType: BridgeUtils.TOKEN_TRANSFER,
    version: 1,
    nonce: 0,
    chainID: 1,          // source = chain 1
    payload: payloadB    // recipient = bob, 1 ETH
});
bridge.transferBridgedTokensWithSignatures(signaturesB, msgB);
// REVERTS: "SuiBridge: Message already processed"
// Bob's funds are permanently locked on chain 1.
```

The collision is structural: `isTransferProcessed[0]` is the same storage slot regardless of whether `chainID` is 0 or 1. No signature forgery or privileged access is required — any user who possesses the committee-signed `msgA` bytes (publicly available from bridge-node broadcasts) can submit step 1 and permanently block step 2.
