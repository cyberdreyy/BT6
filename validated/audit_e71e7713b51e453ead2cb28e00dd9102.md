### Title
Zero-priced write-off requests let any fulfiller seize escrowed tranche tokens - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`createWriteOffRequest` validates that escrowed tranches are nonzero but allows `underlyingsRequested == 0`, while `fullfillWriteOffRequest` permits any caller to fulfill that request by paying any nonnegative amount. A zero-priced request can therefore be filled for dust and the fulfiller receives all escrowed tranche tokens. [1](#0-0) [2](#0-1) 

### Finding Description
A lender escrows `amount` tranche tokens through `createWriteOffRequest`, and the function rejects only `amount == 0`; it never rejects a zero requested payment. [1](#0-0) 

`fullfillWriteOffRequest` is externally callable by any wallet and rejects only an exact tranche-amount mismatch or `_underlyings < currentRequest.underlyings`. [3](#0-2) 

When `currentRequest.underlyings == 0`, a caller can provide a dust amount such as `1000` underlying units, receive a fee deduction of `1` unit under the default `exitFee == 100`, send `999` units to the lender, and receive the full escrowed tranche balance. [4](#0-3) 

This breaks the escrow’s one-claim-one-payment invariant because the stored exchange price permits the collateral to leave the contract without meaningful consideration. [5](#0-4) 

### Impact Explanation
An unprivileged fulfiller can steal `currentRequest.tranches` worth of escrowed AA or BB tranche tokens for a payment bounded only by the token’s minimum viable transfer amount. [2](#0-1) 

For example, a request escrowing `10_000e18` tranche tokens with `underlyingsRequested == 0` can be fulfilled for `1000` underlying units, approximately `$0.001` for a six-decimal stablecoin, while the attacker receives the entire tranche position. [6](#0-5) 

The acquired tranche tokens represent the lender’s claim on the credit vault, so the loss equals the market or redemption value of the full escrowed tranche balance rather than merely a protocol accounting artifact. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
Exploitation requires a lender to create a zero-priced request, but fulfillment is permissionless and can be performed by a bot monitoring such requests without KYC, borrower, owner, manager, or escrow privileges. [1](#0-0) [3](#0-2) 

Because unit mistakes are common and the function exposes no minimum-price check or slippage-style warning, a single malformed request is sufficient for an immediate dust-price purchase. [9](#0-8) [10](#0-9) 

### Recommendation
Reject zero-priced write-off requests in `createWriteOffRequest` with `if (underlyingsRequested == 0) revert NotAllowed()`. [1](#0-0) 

If intentional debt gifts must remain supported, implement a separate explicit transfer path rather than allowing the purchase flow to release escrowed collateral for zero consideration. [2](#0-1) 

### Proof of Concept
Add this regression test to `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`, which already provides the deployed `escrow`, `tranche`, `underlying`, and funded `LP` fixture:

```solidity
function testZeroPriceWriteOffCanBeFilledForDust() external {
    uint256 requestedTranches = 10_000e18;
    uint256 dustPayment = 1_000; // makes the default 0.1% fee nonzero
    address buyer = makeAddr("buyer");

    uint256 buyerTranchePre = tranche.balanceOf(buyer);
    uint256 lpUnderlyingPre = underlying.balanceOf(LP);

    // Victim accidentally creates a request that asks for zero underlyings.
    vm.prank(LP);
    escrow.createWriteOffRequest(requestedTranches, 0);

    deal(address(underlying), buyer, dustPayment);

    vm.startPrank(buyer);
    underlying.approve(address(escrow), dustPayment);
    escrow.fullfillWriteOffRequest(LP, requestedTranches, dustPayment);
    vm.stopPrank();

    assertEq(
        tranche.balanceOf(buyer) - buyerTranchePre,
        requestedTranches,
        "buyer seized all escrowed tranches for dust"
    );
    assertEq(
        underlying.balanceOf(LP) - lpUnderlyingPre,
        dustPayment - 1,
        "seller received only dust minus the exit fee"
    );
}
```

The test succeeds because `0` is accepted as the requested payment, `dustPayment >= 0` passes the underpayment check, and the function then transfers the full escrowed tranche amount to `msg.sender`. [9](#0-8) [6](#0-5)

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```
