### Title
`simulateTransaction`/`sendTransaction` preflight can panic the validator when the selected bank is not frozen - ([File: rpc/src/rpc.rs])

### Summary
The `sendTransaction` preflight path and `simulateTransaction` RPC handler call `Bank::simulate_transaction()`, which internally asserts the bank is frozen (`assert!(bank.is_frozen(), "simulation bank must be frozen")`). An unprivileged JSON-RPC caller selects the bank via `commitment` (defaulting to/allowing `processed`), and the `processed`-commitment bank returned by `JsonRpcRequestProcessor::bank()` is the current working/heaviest bank, which may not yet be frozen while replay/banking is still in progress on it. If simulation runs against such a bank, the assertion fails and the whole validator process panics from a single external RPC request.

### Finding Description
`JsonRpcRequestProcessor::bank()` resolves a bank for a request based on `commitment`. For `CommitmentLevel::Processed` it uses `self.block_commitment_cache...slot_with_commitment(...)` to pick "the heaviest slot" and fetches it from `bank_forks` [1](#0-0) . This heaviest/working bank is not guaranteed to be frozen — it may still be actively being replayed/banked.

Both `send_transaction` (used for preflight, when `skip_preflight` is false or when `preflight_commitment` resolves to `processed`) and `simulate_transaction` call `preflight_bank.simulate_transaction(&transaction, false)` on the bank obtained through this commitment-based lookup [2](#0-1) .

`Bank::simulate_transaction` (in `runtime/src/bank.rs`) requires the bank to be frozen; there is an existing regression test that documents and reproduces this exact panic:

```
#[test]
#[should_panic(expected = "simulation bank must be frozen")]
fn test_rpc_simulate_transaction_panic_on_unfrozen_bank() {
    ...
    assert!(!bank.is_frozen());
    ...
    // should panic because `bank` is not frozen
    let _ = io.handle_request_sync(&req, meta);
}
``` [3](#0-2) 

Notably, other tests explicitly call `bank.freeze()` before invoking `simulateTransaction`/`sendTransaction` in test setups specifically "to prevent a panic in `run_transaction_simulation()`" [4](#0-3) , and another test freezes the bank with the comment "Simulation bank must be frozen" before exercising `simulateTransaction` [5](#0-4) . This strongly indicates production code paths rely on the caller supplying an already-frozen bank, but the RPC layer does not guarantee this for the `processed`/default commitment path when the working bank is actively being replayed.

This is directly analogous to the reported bug class: a state-dependent operation (`MINTR.burnOhm` gated by `onlyWhileActive`) is invoked unconditionally without handling the "not ready/paused" state, causing an unhandled failure. Here, the analogous "not ready" state is "bank not frozen," and instead of a revert it results in a hard `panic!`, crashing the validator process rather than returning an RPC error to the caller.

### Impact Explanation
A `panic!` inside a JSON-RPC handler thread executing `simulate_transaction`/`send_transaction` preflight will abort the request-handling thread; depending on panic-handling configuration this can crash the whole validator process, causing a denial of service triggerable by a single unprivileged RPC call (`sendTransaction` without `skipPreflight`, or `simulateTransaction`), given a bank is not frozen at request time. This satisfies the "concrete validator-process crash ... from one request" acceptance criterion.

### Likelihood Explanation
The precise timing window (working bank not yet frozen when `commitment=processed`/default preflight commitment resolves to it) is a race condition tied to internal replay timing rather than something a remote caller can force from outside, so likelihood of hitting the exact window on a live cluster is uncertain and depends on validator internals/timing that I could not fully verify from the indexed code alone (e.g., whether the bank returned for "processed" during active replay could actually still be un-frozen at the time `preflight_bank.simulate_transaction()` executes, versus already being frozen by the time RPC threads observe it via `bank_forks`). The existing dedicated regression test in the codebase confirms the panic is reachable through the RPC handler under the right precondition, but does not by itself prove the precondition is externally forceable at will on a running validator.

### Recommendation
Guard the preflight/simulation code paths in `rpc/src/rpc.rs` (`send_transaction`'s preflight branch and `simulate_transaction`) to explicitly check `bank.is_frozen()` before calling `Bank::simulate_transaction`, returning a proper JSON-RPC error (e.g., a `RpcCustomError`) instead of relying on the internal `assert!` to enforce this invariant. Alternatively, ensure `JsonRpcRequestProcessor::bank()` only ever returns frozen banks for `processed` commitment (e.g., by defensively freezing a local clone or falling back to the highest already-frozen bank when the working bank is unfrozen).

### Proof of Concept
The existing test `test_rpc_simulate_transaction_panic_on_unfrozen_bank` in `rpc/src/rpc.rs` is a concrete, minimal reproduction: it constructs an `RpcHandler`, deliberately leaves the working bank unfrozen (`assert!(!bank.is_frozen())`), and issues a `simulateTransaction` JSON-RPC request with `sigVerify: true`, which panics with `"simulation bank must be frozen"` [3](#0-2) . This demonstrates that the handler path from an RPC request to `Bank::simulate_transaction()` can panic when the selected bank is not frozen; the open question (not resolvable from static code inspection alone) is exactly which external request/commitment/timing combination guarantees delivery of an unfrozen bank into that same code path on a live validator.
