## Title
RPC/transaction-status SPL-Token `*Checked` instruction parsers report attacker-chosen `decimals` instead of the mint's real decimals, causing misreported token amounts - (File: transaction-status/src/parse_token.rs)

### Summary
This is a strong analog to the reported bug class: a value that is supposed to represent verified on-chain truth (the "volatility"/mint decimals) is instead taken directly from attacker-controlled instruction data and used unchecked in a financial/display calculation, producing incorrect output that is returned to unprivileged RPC callers.

### Finding Description
The `parse_token` instruction parser in the `transaction-status` crate decodes SPL-Token `*Checked` instructions (`TransferChecked`, `ApproveChecked`, `MintToChecked`, `BurnChecked`) by unpacking the `TokenInstruction` enum directly from the raw compiled instruction bytes supplied by the transaction author, and immediately constructs a `SplTokenAdditionalDataV2` from the caller-supplied `decimals` field with no cross-check against the mint account's actual `decimals`: [1](#0-0) 
The same unvalidated pattern applies to `MintToChecked`, `BurnChecked`, and `TransferChecked`: [2](#0-1) [3](#0-2) 

The `decimals` value flows straight into `token_amount_to_ui_amount_v3`, which computes `ui_amount`/`ui_amount_string` purely from the caller-provided decimals with no reconciliation against the mint: [4](#0-3) 

By contrast, the RPC handlers that read live account state (`getTokenAccountBalance`, `getTokenSupply`) correctly derive `decimals`/additional data from the actual mint account stored in the bank rather than trusting user input: [5](#0-4) [6](#0-5) 

This inconsistency mirrors the root cause of the external report exactly: one code path derives a sensitive numeric parameter from verified system state, while a parallel code path (instruction parsing for `jsonParsed` transaction/instruction display, used by `getTransaction`, `getConfirmedTransaction`, `getBlock`, and pubsub transaction subscriptions) blindly trusts the value embedded by the transaction's author.

### Impact Explanation
On-chain SPL Token enforces that the supplied `decimals` in a `*Checked` instruction matches the mint's real decimals at execution time, but a mismatched decimals value only causes the *instruction to fail*; the transaction itself can still land in a block as a failed transaction (paid for, and retrievable via RPC). When any unprivileged client fetches that transaction/block with `jsonParsed` encoding (a single, cheap read), the parser reports a `tokenAmount.uiAmount`/`uiAmountString` computed from the attacker's arbitrary `decimals`, which can be wildly different from the token's real decimal precision. This is "wrong ... account data returned" from a single unprivileged query, satisfying the accepted impact class for decoder misreporting.

### Likelihood Explanation
Any user can craft and submit a transaction containing a `TransferChecked`/`ApproveChecked`/`MintToChecked`/`BurnChecked` instruction with an arbitrary `decimals` byte; it costs only the fee for one transaction, requires no privileged role, and the resulting misreporting occurs on every subsequent `jsonParsed` fetch of that transaction by any RPC/pubsub client (block explorers, wallets, indexers).

### Recommendation
When parsing `*Checked` token instructions for `jsonParsed` display, either omit the `decimals`-derived `uiAmount` fields when the parser cannot verify them against the actual mint, or resolve and use the mint's real decimals (as `rpc/src/parsed_token_accounts.rs` already does) rather than trusting the value embedded in the instruction. At minimum, downstream consumers should be warned that `tokenAmount` in parsed `*Checked` instructions is unverified until cross-checked against the mint account.

### Proof of Concept
1. Create a mint with, e.g., 6 decimals.
2. Craft a `TransferChecked` instruction referencing that mint but with `decimals` set to e.g. `0` or `18` instead of `6`.
3. Submit the transaction; the SPL Token program will reject the instruction with `MintDecimalsMismatch`, but the transaction still lands on-chain as a failed transaction.
4. Call `getTransaction`/`getConfirmedTransaction` with `"encoding": "jsonParsed"` for that signature.
5. Observe that `parse_token::parse_token` (`transaction-status/src/parse_token.rs`, `TransferChecked` arm) reports `tokenAmount` computed via `token_amount_to_ui_amount_v3(amount, &SplTokenAdditionalDataV2::with_decimals(decimals))` using the attacker's fabricated `decimals`, not the mint's real decimals.

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };
    UiTokenAmount {
        ui_amount,
        decimals,
        amount: amount.to_string(),
        ui_amount_string,
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}
