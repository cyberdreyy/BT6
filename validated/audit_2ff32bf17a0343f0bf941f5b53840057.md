### Title
Instant-withdraw claim path pays receipts without checking they were funded, letting a stale `allowInstantWithdraw` flag drain other users' withdrawal reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analogous to the SiYuan `/export/temp/` branch that skipped the `IsSubPath`/`IsSensitivePath` checks applied to the main export path, `IdleCreditVault.claimInstantWithdrawRequest` is a short-circuit claim branch that skips the funding/epoch gating applied to normal claims. `_claimFundedWithdrawRequest` enforces `epochNumber > lastWithdrawRequest[_user]` before paying; the instant branch pays `instantWithdrawsRequests[_user]` in full from the vault's shared underlying balance with only the CDO-side `allowInstantWithdraw` boolean as a guard — a flag that is never reset to `false` when a new epoch starts underfunded.

### Finding Description
In `contracts/IdleCDOEpochVariant.sol`, `allowInstantWithdraw` is only ever *set* to `true`:
- `startEpoch()` line 292, but only on the fully-funded path; when `pendingInstant > totUnderlyings` the function returns early at lines 286–289 **without clearing the flag**.
- `getInstantWithdrawFunds()` line 570 after the borrower pays.
- `finalizeDefault()` line 220.

There is no `allowInstantWithdraw = false` anywhere in the epoch lifecycle. Once any epoch enabled it, the flag stays `true` for all subsequent epochs.

`claimInstantWithdrawRequest` in `contracts/IdleCDOEpochVariant.sol` (lines 975–979) gates solely on that flag, then calls `IdleCreditVault.claimInstantWithdrawRequest` (lines 380–393), which burns the caller's entire `instantWithdrawsRequests[_user]` receipt and calls `_transferFundedClaim(_user, amount)` — a transfer of underlying held by the vault. That same vault balance is the commingled reserve for *all* funded receipts: normal withdraw funding is pushed into the vault by `collectWithdrawFunds` (lines 411–430) at `stopEpoch`, and instant funding by `collectInstantWithdrawFunds` (lines 398–403). The claim path performs no `pendingInstantWithdraws == 0` check and no per-epoch funding verification — `instantWithdrawsRequestsByEpoch` is recorded at request time but never consulted on the non-default claim path.

### Impact Explanation
Direct theft of other users' funded withdrawal reserves, plus permanent freezing of their claims (their later claims underflow the vault balance and revert). Attack sequence:

1. Epoch N ends with a lowered APR so requests route to instant withdrawals. Attacker requests; `startEpoch(N+1)` fully funds → `allowInstantWithdraw = true`. Attacker claims or not — flag persists.
2. Epoch N+1 runs and stops; other users' *normal* withdraw requests are funded by the borrower via `collectWithdrawFunds` → vault now holds their money.
3. APR is lowered again so the attacker's new `requestWithdraw` becomes an instant request (`instantWithdrawsRequests[attacker] += amount`, `pendingInstantWithdraws += amount`).
4. `startEpoch(N+2)`: contract underlyings < pending instant → early return at line 286; the unfunded gap must come from `getInstantWithdrawFunds`, but `allowInstantWithdraw` is still `true` from epoch N+1.
5. Attacker immediately calls `cdoEpoch.claimInstantWithdrawRequest()`: `claimInstantWithdrawRequest` burns the receipt and transfers the full amount from the vault, consuming the normal-withdraw reserve of step 2. Loss = `min(attackerReceipt, vaultUnderlyingBalance)` — up to the entire reserve owed to honest withdrawers, whose claims then revert permanently (pre-finalization) or are forced into the default flow.

The same commingling means that even among instant requesters, a partially-prefunded epoch lets the first claimer take the funded share of all other instant receipts, since each claim pays the user's full receipt balance rather than a funded pro-rata share.

### Likelihood Explanation
Requires only a KYC-passing lender (allowed attacker class) plus two conditions that honest privileged roles produce in normal operation: (a) `allowInstantWithdraw` having been enabled once by a fully-funded epoch or a prior `getInstantWithdrawFunds`, and (b) a subsequent epoch where instant demand exceeds contract underlyings at `startEpoch`. Both are reached by ordinary APR decreases and deposit/withdraw flows; no privileged misbehavior, oracle manipulation, or timing exoticism is needed. The attacker controls the size of their request, so condition (b) is trivially satisfiable by requesting a large instant withdraw when the buffer holds few deposits.

### Recommendation
Mirror the hardening applied to the main export path onto the short-circuit branch:
- Reset `allowInstantWithdraw = false` in `startEpoch()` before the funding logic, and only re-set it on full funding (line 292) or successful `getInstantWithdrawFunds`.
- In `IdleCreditVault.claimInstantWithdrawRequest`, revert unless `pendingInstantWithdraws == 0` (or track funded amounts per epoch and pay only the funded portion), instead of relying on the vault balance transfer as the implicit check.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testInstantClaimDrainsNormalReserve() external {
    uint256 amountWei = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amountWei);
    idleCDO.depositBB(amountWei);

    // Epoch 0 -> 1: lower APR so withdraws are instant; fully fund at startEpoch.
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());
    uint256 req1 = cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));
    _startEpochAndCheckPrices(1);            // allowInstantWithdraw = true
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    // (claims optional) flag stays true

    // Honest user's normal request funded at stopEpoch(1): vault now holds their reserve.
    address victim = makeAddr('victim');
    _depositWithUser(victim, amountWei, true);
    // victim requested normal withdraw during buffer of epoch 1 (higher APR epoch),
    // borrower repays at stopEpoch -> collectWithdrawFunds moves underlying to vault.
    _stopEpochAndCheckPrices(1, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Epoch 1->2 buffer: attacker requests a large instant withdraw.
    uint256 req2 = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));

    // startEpoch(2) with pendingInstant > contractTokenBalance -> early return,
    // allowInstantWithdraw still true, req2 is UNFUNDED.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Attacker claims immediately; vault pays from victim's funded reserve.
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(address(this)) - balPre, /* funded portion */ 0);

    // Victim's later claimWithdrawRequest reverts on insufficient vault balance.
}
```

The test passes the broken-invariant check if the attacker receives more underlying than the prefunded share of their own receipt and the victim's funded claim subsequently fails.

*Caveat:* I was unable to read the body of `_transferFundedClaim` within the available iterations; if it enforces an explicit per-user funded ledger (rather than a raw `safeTransfer` from the vault balance), the drain would be bounded to the attacker's funded share and this finding reduces to a design assumption. The `allowInstantWithdraw` never-reset issue is confirmed independently and is reportable regardless.
