### Title
Stale per-epoch instant-withdraw basis survives `claimInstantWithdrawRequest`, corrupting default-recovery accounting - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` clears the aggregate receipt ledger (`instantWithdrawsRequests[_user]`) but never clears the per-epoch ledgers `instantWithdrawsRequestsByEpoch[_user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]` that were written in `requestInstantWithdraw`. If the borrower later defaults in that same epoch while any instant request is still unfunded, `finalizeDefaultRecovery` counts the already-claimed basis again via `defaultPendingClaimBasis`, diluting `defaultRecoveryPrice` for every recovery claimant and permanently stranding the excess in `defaultRecoveryReserve`. This mirrors the XFS bug: cleanup clears a flag/ledger under the assumption that all associated state moved, while a skipped per-epoch mapping still records ownership.

### Finding Description
In `requestInstantWithdraw`, three pieces of state are written: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` (`IdleCreditVault.sol:366-372`).

In `claimInstantWithdrawRequest`, only the aggregate is cleared: `instantWithdrawsRequests[_user] = 0` — the two per-epoch mappings keep the basis forever (`IdleCreditVault.sol:387-392`). The funded-claim path assumes the cleared aggregate implies no remaining claim state.

On a later borrower default in that epoch, if `pendingInstantWithdraws != 0` (some other request was only partially funded at `startEpoch`), `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` — which still includes the already-claimed amount — into `totalBasis` (`IdleCreditVault.sol:644-649`, `679`). `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is therefore computed against phantom basis (`IdleCreditVault.sol:688`), and `defaultInstantWithdrawsFinalized` is set true (`:696`).

Post-finalization, `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` as claim basis (`:844`) and executes `instantWithdrawsRequests[_user] -= claimBasis` (`:848`). For a user who already claimed (aggregate = 0) and re-requested, this underflows/panics; for the aggregate accounting, `instantWithdrawClaimsByEpoch[defaultEpoch]` is over-decremented by stale amounts.

### Impact Explanation
- **Recovery dilution**: `totalBasis` is inflated by already-paid instant claims, so `defaultRecoveryPrice` is strictly lower than the true ratio. Every defaulted-epoch claimant — normal withdrawers, unfunded instant withdrawers, and active AA/BB holders via `activeFinalNAV` (`:699-705`) — receives less underlying per unit of claim.
- **Permanent reserve freeze**: because the phantom basis is never claimable (the claiming user's aggregate was zeroed), the corresponding slice of `defaultRecoveryReserve` can never be consumed by `_transferDefaultRecovery` and is locked in the strategy.
- **Claim DoS**: a user who claimed an instant receipt in the defaulting epoch and then re-requested reverts in `_claimDefaultedInstantWithdrawRequest` (`instantWithdrawsRequests[_user] -= claimBasis` underflows, or `_burn(_user, claimBasis)` exceeds minted receipts at `:854`), blocking their legitimate defaulted-epoch claim.

Loss is quantified as the stale `instantWithdrawClaimsByEpoch` share of `reserveAmount`, which exceeds the "temporary freezing / dust" reject categories because it directly misprices recovery for all claimants.

### Likelihood Explanation
Requires: instant withdrawals enabled (`disableInstantWithdraw == false`), a user claims a funded instant receipt, and in the same epoch another instant request remains unfunded (`pendingInstantWithdraws > 0`) when the borrower defaults and `finalizeDefaultRecovery` runs. The attacker is an ordinary tranche holder doing normal request/claim/re-request transactions — no privileged action needed. The honest-manager `finalizeDefaultRecovery` call then crystallizes the mispricing. Prefunded vault variants disable instant withdrawals, so exposure is limited to non-prefunded `IdleCreditVault` deployments with instant mode on.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch state the same way the aggregate is cleared: track the request epoch per user (or iterate `instantWithdrawsRequestsByEpoch[_user][lastRequestEpoch]`), decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, and zero the per-epoch user entry — analogous to `_clearWithdrawClaimForEpoch` for normal receipts. Alternatively, gate `defaultPendingClaimBasis`/`_claimDefaultedInstantWithdrawRequest` on the live aggregate (`min(byEpoch, instantWithdrawsRequests[user])`).

```text
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);

    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
