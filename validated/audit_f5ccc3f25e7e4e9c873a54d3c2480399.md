No vulnerability found for this question.

**Reasoning:**

`set_beneficiary_for_operator` stores the `BeneficiaryForOperator` resource keyed by the caller's own address, independent of whether that address currently holds an operator role for any pool [1](#0-0) . The comment explicitly documents this design choice: "The beneficiary address of an operator is stored under the operator's address. So, the operator does not need to be validated with respect to a staking pool." [2](#0-1) 

Commission payouts look up the beneficiary at distribution time via `beneficiary_for_operator(stake::get_operator(pool_address))`, using whichever address is the *current* operator of the pool — not a value cached at the time the beneficiary was set [3](#0-2) . This means beneficiary routing always reflects the live operator/beneficiary mapping, and the framework's own test explicitly validates the exact "operator switch" scenario the question describes: when a pool's operator changes from `operator1` (who has a beneficiary set) to `operator2`, subsequent commission goes to `operator2`, not to `operator1`'s beneficiary [4](#0-3) . The analogous test exists in `staking_contract.move`/`vesting.move` as well [5](#0-4) .

Applying this to the proposed attack: if address `A` calls `set_beneficiary_for_operator` before ever being an operator, it merely records "if `A` ever becomes an operator, `A`'s commission should go to beneficiary `X`" under `A`'s own account. This is a self-referential configuration of `A`'s own future commission routing — it does not touch, corrupt, or pre-empt any other account's `BeneficiaryForOperator` resource, and it cannot redirect commission away from whoever the owner actually intends to reward. The owner must still voluntarily call `set_operator(A)` to make `A` the operator — at that point, paying `A`'s self-designated beneficiary is the intended and documented behavior, not a hijack of value belonging to a "legitimate operator." There is no unprivileged path here that changes who can withdraw/earn stake or commission belonging to someone other than the account performing the action; the review bounds explicitly reject scenarios that assume the attacker already has (or is granted) the operator role by the victim's own choice.
