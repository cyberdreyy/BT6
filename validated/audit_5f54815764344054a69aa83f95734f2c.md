### Title
Stale confirmations from removed multisig members are never purged from other members' pending requests, allowing a request to execute with fewer than `num_confirmations` live members - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` only removes requests *created by* the member being deleted, together with those requests' confirmation sets, but it never scans `confirmations` for entries where the deleted member merely *confirmed* someone else's still-pending request. Once that member is removed, their confirmation string persists in that other request's `HashSet<String>`, so it keeps counting toward the `num_confirmations` threshold forever, even though the member no longer exists in `self.members`.

### Finding Description
The invariant that should hold is: `confirmations.get(&request_id).len()` (plus the caller) reaching `num_confirmations` implies that many **currently valid** members approved the request, i.e. every entry in `confirmations[request_id]` must correspond to a member still present in `self.members`.

`delete_member` breaks this binding: [1](#0-0) 
It computes `request_ids` only by filtering `self.requests` for entries whose *creator* (`r.member`) equals the member being deleted, then removes those requests and their confirmation sets. It never inspects the `confirmations` map for other, still-live requests that the removed member had previously confirmed.

`confirm` then counts votes purely by set size, with no re-validation that each entry in the set is still in `self.members`: [2](#0-1) 
And `assert_valid_request` only checks that the *caller* is a current member and that the request/confirmations exist — it never re-validates the identities already stored inside `confirmations[request_id]`: [3](#0-2) 

Exploit flow:
1. A multisig has members `A, B, C, D` with `num_confirmations = 3`. `C` holds only a restricted function-call key installed by `add_member` for `MULTISIG_METHOD_NAMES` (`add_request,delete_request,confirm,add_and_confirm_request`) — a "restricted key only" holder, not a full-access key.
2. `D` (or anyone else) creates a request `R` via `add_request` — the request's `member` field records `D` as creator.
3. `C` calls `confirm(R)`, adding `"C"`'s serialized identity into `confirmations[R]` (count = 1).
4. The group later removes `C` via a `DeleteMember` request (for unrelated reasons — compromise suspicion, offboarding, etc.). `delete_member` filters `self.requests` for `r.member == C`; since `R` was created by `D`, it is left untouched, and `confirmations[R]` (still containing `"C"`) is never touched either.
5. `C` is now gone from `self.members`, yet `confirmations[R]` still contains `"C"`.
6. If only `A` and `B` (the two remaining live approvers besides the creator) subsequently confirm `R`, the set becomes `{C, A, B}` → `len()+1 (self) ... actually len()==3 >= num_confirmations(3)` and `R` executes via `self.execute_request(request)` in `confirm`.
7. The request thus executes with only 2 genuinely live approving members (`A`, `B`) instead of the mandated 3, using a phantom vote from a member that has already been expunged from the multisig.

No existing guard prevents this: `assert_valid_request` checks caller membership and request existence only; `delete_member` cleans up only requests keyed by the removed member as creator, not confirmation entries keyed by other requests where the removed member was merely a confirmer.

### Impact Explanation
This directly matches the listed Critical impact category: **a multisig request executed below `num_confirmations` live members**. Any pending request (e.g. a `Transfer` moving NEAR out of the account, an `AddKey`/`AddMember` granting new privileged access, or a `FunctionCall`) can be pushed through with a stale vote from a removed member substituting for a genuine live approver, reducing the effective quorum by one for every removed member who had confirmed but not-yet-executed requests. This is repeatable for every member turnover event and for every request left pending across that turnover, and the blast radius is the full balance/control of the multisig account.

### Likelihood Explanation
The precondition is realistic and does not require anything exotic: multisig membership changes over time (`DeleteMember` is a normal governance action), and it is common to have outstanding, not-yet-fully-confirmed requests at the time a member is removed. The attacker only needs to be (or collude with) a current member — even one restricted to the `MULTISIG_METHOD_NAMES` function-call key — who confirms a request shortly before being removed (or is removed for unrelated reasons after confirming). The remaining honest members' normal confirmation activity on that same request then unknowingly completes the phantom quorum. No special deposit, gas, or privileged role beyond ordinary confirmed multisig membership is required, and the flaw is triggered purely by state (never cleaned by any code path), making it silently persistent until the affected request is executed or explicitly deleted.

### Recommendation
In `delete_member`, in addition to removing requests created by the deleted member, iterate over all remaining entries in `self.confirmations` and remove the deleted member's identity string from every confirmation set (or re-validate membership of each entry). Alternatively, in `confirm`, count only confirmations whose string corresponds to a currently existing entry in `self.members` before comparing against `num_confirmations`.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
