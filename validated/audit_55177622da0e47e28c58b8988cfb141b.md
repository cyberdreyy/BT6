### Title
Flash-loan sandwich can fill the `ProvisionerV2` sync-redeem epoch cap by bypassing the deposit lock via share transfer, causing temporary DoS on user exits - (File: `v3/src/core/ProvisionerV2.sol`)

### Summary
`ProvisionerV2` bounds sync redeems with a per-epoch numeraire cap tracked in `_syncRedeemEpochRedeemedNumeraire`, enforced in `_requireEpochCapNotExceeded` and consumed on every `redeem()` call [1](#0-0) . The only anti-flash-loan guard is a per-depositor lock, `userUnitsRefundableUntil[msg.sender]`, set on the *depositor's own address* when they sync-deposit and checked only against `msg.sender` at redeem time [2](#0-1) . Because vault shares (`MULTI_DEPOSITOR_VAULT` units) are standard transferable ERC20 tokens and the lock is keyed by address rather than by the units themselves, an attacker can mint shares with flash-loaned funds under address A, transfer the freshly minted shares to a fresh, never-deposited address B, and immediately redeem from B — bypassing the lock entirely and filling the epoch cap in one atomic transaction, exactly mirroring the disclosed Origami `preCheck`/`cap` flash-loan DoS.

### Finding Description
The attack path is:
1. `deposit()`/`mint()` (ordinary user function, `anyoneButVault`) converts `tokensIn` to units and calls `_syncDeposit`, which sets `userUnitsRefundableUntil[receiver] = block.timestamp + depositRefundTimeout` for the receiving address only [3](#0-2) .
2. The minted `MULTI_DEPOSITOR_VAULT` shares are standard ERC20 units; nothing in the deposit flow prevents the receiver from transferring them to a second, never-before-used address before redeeming.
3. `redeem()` only checks the lock against `msg.sender`, not against the original minting address or the units' provenance: `require(userUnitsRefundableUntil[msg.sender] < block.timestamp, Aera__UnitsLocked());` [2](#0-1) . For any fresh address, `userUnitsRefundableUntil` defaults to `0`, so the check always passes.
4. `redeem()` then computes `epochRedeemNumeraire` and calls `_syncRedeem`, which checks and increments the shared `_syncRedeemEpochRedeemedNumeraire` global counter against `epochCapNumeraire` [4](#0-3) . The cap (`_computeEpochCap`) is derived from the epoch-start TVL snapshot taken from the price/fee calculator anchor and does not grow from the attacker's own deposit within the same transaction [5](#0-4) .

By flash-loaning the deposit token, depositing under address A, transferring the minted shares to address B, and redeeming from B — all in one transaction — an attacker can drive `_syncRedeemEpochRedeemedNumeraire` up to `epochCapNumeraire`, exactly as the Origami report describes for `OrigamiCircuitBreakerAllUsersPerPeriod.preCheck`/`cap`. Every subsequent legitimate `redeem()` call within the same epoch then reverts with `Aera__SyncRedeemEpochCapExceeded()` until the epoch rolls over on the next price anchor update.

### Impact Explanation
This blocks all other users' synchronous exits (`redeem`) for the remainder of the epoch, a temporary freeze of legitimate withdrawal capacity — matching the Medium-severity "temporary freezing of funds" category under Immunefi guidance. No funds are stolen; the attacker only pays deposit/redeem multiplier premiums and flash-loan fees, but ordinary depositors relying on the sync-redeem path are denied timely exit.

### Likelihood Explanation
Requires only: (a) sync deposit and sync redeem enabled for a token (`syncDepositEnabled`/`syncRedeemEnabled`), (b) sufficient flash-loanable liquidity in the deposit token to approach `epochCapNumeraire`, and (c) an ordinary EOA/contract capable of performing deposit → transfer → redeem in one transaction. All three steps are callable by any address with no privileged role, satisfying the "ordinary user" requirement. The main uncertainty is whether the `MultiDepositorVault` share contract imposes any additional transfer-time restriction propagating the lock to the recipient; no such restriction was found in the reviewed code paths for `redeem`/`_syncDeposit`.

### Recommendation
Tie the redeem lock to the units themselves rather than the caller's address (e.g., track lock expiry per-unit via checkpoints, or disallow transfers of freshly minted shares for the `depositRefundTimeout` window), or require that sync deposit and sync redeem cannot occur for the same underlying capital within one block/transaction regardless of intermediate transfers — analogous to the original recommendation to disallow invest+exit in the same block.

### Proof of Concept
1. Fork mainnet at a block where a `ProvisionerV2` deployment has `syncDepositEnabled`/`syncRedeemEnabled` for a token and a configured `_syncRedeemAbsoluteCapNumeraire`.
2. From attacker contract, take a flash loan of the deposit token sized close to `epochCapNumeraire` (read via `getSyncRedeemEpochState()`).
3. Call `deposit(token, tokensIn, 0, addrA)` where `addrA` is `address(this)`.
4. Transfer the minted `MULTI_DEPOSITOR_VAULT` shares from `addrA` to a fresh, never-deposited address `addrB` (e.g., a newly deployed minimal proxy).
5. From `addrB`, call `redeem(token, tokensOut, unitsIn, addrB)`.
6. Assert: this call succeeds (no `Aera__UnitsLocked()` revert) and `getSyncRedeemEpochState().epochRedeemedNumeraire` now approaches `epochCapNumeraire`.
7. From a separate, legitimate user address with previously unlocked units, call `redeem()` for even a small amount and assert it reverts with `Aera__SyncRedeemEpochCapExceeded()`.
8. Repay the flash loan using proceeds from the redeem in step 5, demonstrating the attack is self-financing.

    /// @dev Reverts if the deposit hash already exists. Sets the refundable period for the user
    /// @param token The ERC20 token to deposit
    /// @param tokenAmount The amount of tokens to deposit
    /// @param unitAmount The amount of vault units to mint for the user
    /// @param receiver The address receiving the minted units
    function _syncDeposit(IERC20 token, uint256 tokenAmount, uint256 unitAmount, address receiver) internal {
        uint256 refundableUntil = block.timestamp + depositRefundTimeout;
        bytes32 depositHash = _getDepositHash(msg.sender, receiver, token, tokenAmount, unitAmount, refundableUntil);

        // Requirements: deposit hash is not set
        require(!syncDepositHashes[depositHash], Aera__HashCollision());
        // Effects: set hash as used
        syncDepositHashes[depositHash] = true;

        // Effects: set receiver's refundable until timestamp
        userUnitsRefundableUntil[receiver] = refundableUntil;

        // Interactions: enter vault
        IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).enter(msg.sender, token, tokenAmount, unitAmount, receiver);

        // Log deposit event
        emit Deposited(msg.sender, receiver, token, tokenAmount, unitAmount, depositHash);
    }

    /// @notice Checks that the sync redeem epoch cap is not exceeded and tracks the redemption
    /// @param epochRedeemNumeraire The pre-computed numeraire value of this redeem for epoch cap accounting
    /// @param epochCapNumeraire The effective epoch cap in numeraire
    /// @param epochRedeemedNumeraire The numeraire already redeemed in the current epoch (cached from _rollEpochIfNeeded)
    function _requireEpochCapNotExceeded(
        uint256 epochRedeemNumeraire,
        uint256 epochCapNumeraire,
        uint256 epochRedeemedNumeraire
    ) internal {
        epochRedeemedNumeraire += epochRedeemNumeraire;
        // Requirements: epoch cap is not exceeded
        require(epochRedeemedNumeraire <= epochCapNumeraire, Aera__SyncRedeemEpochCapExceeded());

        // Effects: increment global epoch redeemed counter
        // safe downcast because epochRedeemedNumeraire + epochRedeemNumeraire <= epochCapNumeraire
        // and epochCapNumeraire = min(relativeCap, absoluteCapNumeraire) where absoluteCapNumeraire is uint80
        _syncRedeemEpochRedeemedNumeraire = uint80(epochRedeemedNumeraire);
    }

    /// @notice Computes the effective epoch cap in numeraire
    /// @return epochCapNumeraire The effective epoch cap (min of relative and absolute)
    /// @return epochStartTvlNumeraire The epoch-start TVL in numeraire
    function _computeEpochCap() internal view returns (uint256 epochCapNumeraire, uint256 epochStartTvlNumeraire) {
        // Interactions: compute epoch-start TVL in numeraire from PFC
        epochStartTvlNumeraire = PRICE_FEE_CALCULATOR.getVaultValueAtLastUpdate(MULTI_DEPOSITOR_VAULT);

        uint256 relativeCapNumeraire = Math.mulDiv(epochStartTvlNumeraire, _syncRedeemRelativeCapBps, ONE_IN_BPS);
        epochCapNumeraire = Math.min(relativeCapNumeraire, _syncRedeemAbsoluteCapNumeraire);
    }
