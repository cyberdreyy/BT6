### Title
Signer vote flip from Rejected→Accepted double-counts weight, causing stale rejection tally to wedge block acceptance - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener`'s per-block vote aggregation tracks `total_weight_approved` and `total_weight_rejected` in a shared `BlockStatus` struct, gated by a single `responded_signers` set. When a signer first rejects a block and later legitimately re-evaluates and accepts the *same* `signer_signature_hash` (a normal, documented signer-state-machine behavior), the aggregator adds that signer's weight to `total_weight_approved` without ever removing it from `total_weight_rejected`. The two weight pools are meant to be mutually exclusive views of "current" signer opinion, but the code never reconciles a flip in the reject→accept direction, permanently inflating `total_weight_rejected` beyond the signer's true current position — an equivalent of using a stale "expected" tally instead of the verified/current one, exactly the class of bug in the Synthetix report (assumed value diverges from actual returned value and downstream logic is not adjusted for it).

### Finding Description
`BlockStatus` holds independent counters: [1](#0-0) 

On `Rejected`, weight is added to `total_weight_rejected` only if `responded_signers.insert(slot_id)` succeeds (i.e., first time this slot responds at all): [2](#0-1) 

On `Accepted`, weight is added to `total_weight_approved` only if `gathered_signatures` doesn't already contain the slot — a *different* set from `responded_signers`: [3](#0-2) 

Because the two guards check different sets, a signer that:
1. Sends `Rejected` first → `responded_signers` gets the slot, `total_weight_rejected += weight`.
2. Later (after re-evaluating the same proposal, as documented in `should_reevaluate_block`/`should_reevaluate_reject_reason`) sends `Accepted` for the same `signer_signature_hash` → since `gathered_signatures` does not yet contain the slot, `total_weight_approved += weight` is also applied.

The prior rejected weight is never subtracted. The result is that the same signer's weight is now counted in *both* `total_weight_approved` and `total_weight_rejected` simultaneously, and `total_weight_rejected` never reflects the signer's actual current (accepted) position.

This matters because `SignerCoordinator::get_block_status` checks the rejection threshold *before* the approval threshold: [4](#0-3) [5](#0-4) 

If enough signers reject-then-accept the same proposal (a scenario the miner itself drives by re-sending the same block proposal until pre-commit/threshold conditions change, per the documented proposal-resend flow), the stale `total_weight_rejected` can cross `total_weight - weight_threshold` even though the *current* set of rejecting signers is well under 30%, and even if `total_weight_approved` has legitimately reached the 70% signing threshold. Since the rejection branch is evaluated first, the coordinator declares `SignersRejected` and gives up / excludes txids, instead of accepting the block that in fact has sufficient live approval weight.

### Impact Explanation
This is a liveness wedge on block production reachable without a signer-set majority or key compromise: it only requires the natural re-evaluation flow (miner re-proposing the same block, one or more signers flipping their vote from reject to accept as chain state settles) which the current miner already performs automatically. The result is a legitimately-approved block being misreported as globally rejected by the node's aggregator, stalling tenure progress and forcing repeated re-proposals — matching the "High: a signer [set] wedged into never signing/accepting valid blocks" impact class, since the aggregated-weight equality (`total_weight_rejected`/`total_weight_approved` vs. true current signer positions) is broken.

### Likelihood Explanation
Vote flips from reject to accept for the same `signer_signature_hash` are an intended and reachable code path (`should_reevaluate_reject_reason`, re-proposal handling in `handle_block_proposal`), and the miner's own retry loop in `propose_block`/`get_block_status` resends the identical proposal on timeout, which is exactly the condition needed to trigger repeated evaluation by signers. No majority collusion or key access is required — only a subset of signers whose rejection reason becomes stale/reevaluable while the miner keeps resending.

### Recommendation
Track each signer's vote as a single mutually-exclusive state (e.g., `HashMap<slot_id, Vote>` with `Vote::{Accepted, Rejected}`) instead of two independent weight counters gated by different membership sets. When a slot's vote changes, subtract its weight from the old category's total before adding it to the new category's total, so `total_weight_approved` and `total_weight_rejected` always reflect only the *current* recorded vote per signer.

### Proof of Concept
1. Node proposes block B (`signer_signature_hash = H`).
2. Signer S (weight `w`) sends `BlockResponse::Rejected(H)` — `total_weight_rejected += w`, `responded_signers.insert(slot_S)`.
3. Chain state that caused S's rejection changes (e.g. a conflicting tenure goes stale, per `should_reevaluate_reject_reason`); the miner resends the same proposal for `H` (its normal retry behavior in `SignerCoordinator::propose_block`).
4. Signer S re-evaluates and now sends `BlockResponse::Accepted(H)` — because `gathered_signatures` doesn't contain `slot_S` yet, `total_weight_approved += w` is applied. `total_weight_rejected` is **not** decremented.
5. Repeat for enough signers so that `total_weight_rejected + weight_threshold > total_weight` while `total_weight_approved >= weight_threshold` also holds from the *current* true votes.
6. `get_block_status` evaluates the rejection branch first and returns `NakamotoNodeError::SignersRejected`, even though the live signer set has actually reached the real signing threshold — the tenure stalls/retries needlessly.
