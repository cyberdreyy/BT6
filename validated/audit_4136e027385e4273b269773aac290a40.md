### Title
Sync `redeem`/`withdraw` permanently revert when the configured pull-funds submit call to an external yield source fails - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.redeem`/`withdraw` (the sync exit path) always route through `_syncRedeem`, which calls `_pullFundsIfNeeded` whenever the vault's idle balance of the requested token is below the amount owed to the user. `_pullFundsIfNeeded` unconditionally executes `IBaseVault(MULTI_DEPOSITOR_VAULT).submit(data)` against a guardian-preconfigured SSTORE2 pointer, and the code comment explicitly states this call "reverts on failure." [1](#0-0)  This mirrors the reported pattern: a withdrawal path unconditionally depends on a call into an external, not-fully-protocol-controlled system (here, whatever contract the pull-funds operations target, e.g. a lending market or staking adapter) succeeding, with no fallback such as an "emergency" partial/forced exit.

### Finding Description
`redeem(token, unitsIn, minTokensOut, receiver)` and `withdraw(token, tokensOut, maxUnitsIn, receiver)` are both externally callable by any ordinary holder of vault units (`anyoneButVault`) and both end by calling `_syncRedeem`. [2](#0-1) 

`_syncRedeem` calls `_pullFundsIfNeeded(token, tokensOut)` before exiting the vault:
```
// Interactions: pull funds from yield source if vault idle balance is insufficient
_pullFundsIfNeeded(token, tokensOut);

// Interactions: exit vault — burns units from caller, sends tokens to receiver
IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).exit(msg.sender, token, tokensOut, unitsIn, receiver);
``` [3](#0-2) 

`_pullFundsIfNeeded` checks the vault's idle balance and, if it's less than the requested `tokensOut`, reads pre-stored operations (`pullFundsSubmitDataPointer`) and calls `IBaseVault(MULTI_DEPOSITOR_VAULT).submit(data)`:
```
function _pullFundsIfNeeded(IERC20 token, uint256 tokensOut) internal {
    uint256 idleBalance = token.balanceOf(MULTI_DEPOSITOR_VAULT);
    if (idleBalance >= tokensOut) return;

    address pointer = tokensDetails[token].pullFundsSubmitDataPointer;
    require(pointer != address(0), Aera__PullFundsSubmitDataNotSet());
    ...
    // Interactions: read submit data from SSTORE2 and call vault.submit (reverts on failure)
    bytes memory data = SSTORE2.read(pointer);
    IBaseVault(MULTI_DEPOSITOR_VAULT).submit(data);
}
``` [1](#0-0) 

`submit()` on `BaseVault` executes the pre-configured operations against their targets and `require(success, Aera__SubmissionFailed(i, result))` for each one, i.e. any single failed call bubbles up and reverts the whole `submit`. [4](#0-3) 

The `pullFundsSubmitDataPointer` is set once by an authorized admin via `setTokenDetails` to point at whatever external contract holds the vault's deployed liquidity (e.g. a lending pool, staking/vault adapter). That external contract is not controlled by the ordinary user calling `redeem`/`withdraw`, and — exactly as in the reported masterchef case where the reward-token transfer could revert due to insufficient balance in a third-party contract not controlled by the protocol — if that external contract's withdrawal call reverts (insufficient available liquidity, temporary pause, rate limiting, etc.), the entire pull-funds `submit()` call reverts, which reverts `_pullFundsIfNeeded`, which reverts `_syncRedeem`, which reverts the user's `redeem`/`withdraw` transaction. There is no catch/fallback (unlike the async/refund transfer helpers such as `_transferWithFallback` used elsewhere in the same contract for other failure cases). Every ordinary user attempting a sync `redeem`/`withdraw` for that token is blocked as long as the vault's idle balance is insufficient and the external pull-funds target cannot fully satisfy the withdrawal.

### Impact Explanation
This is a temporary freeze of user funds/yield: any holder of vault units who wants to synchronously redeem/withdraw a token is blocked from doing so whenever (a) idle vault balance is less than the amount requested, and (b) the external contract the guardian configured for pulling funds cannot currently satisfy the pull (own liquidity shortage, pause, etc.). Since deployed vaults are expected to keep most assets earning yield elsewhere (that is the entire purpose of `pullFundsSubmitDataPointer`), idle balance being insufficient is the normal, not edge, case. This matches Immunefi Medium severity for temporary freezing of user funds/yield.

### Likelihood Explanation
No privileged action, oracle manipulation, or attacker interaction is required — this is triggered purely by an ordinary user calling `redeem`/`withdraw` under expected operating conditions (assets deployed to a yield source, vault idle balance below the requested amount). The only prerequisite is that the external system targeted by the pull-funds operations is momentarily unable to honor a full withdrawal (a common, foreseeable condition for lending markets, LP/staking positions, etc., which are inherently outside the protocol's control), directly analogous to the master chef contract lacking sufficient reward-token balance in the source report.

### Recommendation
Do not let a failed pull-funds `submit()` call revert the entire sync redeem/withdraw. Options:
- Wrap the pull-funds `submit()` call in a try/catch (similar to `_pushFundsIfConfigured`'s swallow-on-failure pattern) and, on failure, fall back to redeeming only up to the vault's currently available idle balance, or queue the request as an async redeem instead of reverting outright.
- Alternatively, expose a partial/"emergency" pull-funds path so that even if the target's preferred exit reverts, a reduced-amount or forced withdrawal can still be attempted, ensuring sync redeem/withdraw never leaves users fully stuck.

### Proof of Concept
1. Deploy `ProvisionerV2` and `MultiDepositorVault` per repo test harness; configure `token` with `setTokenDetails` so `pullFundsSubmitDataPointer` points at SSTORE2 data whose operation targets a mock "yield adapter" contract that always reverts on its withdraw function (simulating a third-party contract with insufficient liquidity, mirroring the masterchef reward-token shortfall).
2. Fund the vault with units for a test user and move `token`'s idle balance in `MULTI_DEPOSITOR_VAULT` to below what the user will request (e.g., transfer/deploy most of the token elsewhere, leaving idle balance at 0).
3. Call `provisioner.redeem(token, unitsIn, minTokensOut, receiver)` from the test user.
4. Assert the transaction reverts with `Aera__SubmissionFailed` bubbled up from `BaseVault.submit`, and confirm the user's units remain locked/unburned and the receiver never gets `tokensOut` — demonstrating the sync exit path is fully blocked by the third-party call failure, with no available fallback.

    /// @notice Pull funds from yield source if vault idle balance is insufficient
    /// @param token The redeem token
    /// @param tokensOut The amount of tokens needed for the redeem
    function _pullFundsIfNeeded(IERC20 token, uint256 tokensOut) internal {
        // Interactions: check vault's idle balance of the redeem token
        uint256 idleBalance = token.balanceOf(MULTI_DEPOSITOR_VAULT);
        if (idleBalance >= tokensOut) return;

        // Requirements: pull-funds submit data must be configured
        address pointer = tokensDetails[token].pullFundsSubmitDataPointer;
        require(pointer != address(0), Aera__PullFundsSubmitDataNotSet());

        // Effects: compute shortfall and store in transient storage
        uint256 shortfall;
        unchecked {
            // Unchecked: idleBalance < tokensOut checked above
            shortfall = tokensOut - idleBalance;
        }
        _storeAmount(shortfall);

        // Interactions: read submit data from SSTORE2 and call vault.submit (reverts on failure)
        bytes memory data = SSTORE2.read(pointer);
        IBaseVault(MULTI_DEPOSITOR_VAULT).submit(data);
    }
