### Title
`check_parent_tenure_choice` trusts a possibly-stale local block count instead of the node's authoritative tenure block list, allowing a reorg of a multi-block tenure - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` gates a reorg on `signer_db.get_globally_accepted_block_count_in_tenure`, a purely local count derived from this signer's own `SignerDb` state [1](#0-0) . The node response used in the same call, `TenureForkingInfo`, already carries the authoritative `nakamoto_blocks: Option<Vec<NakamotoBlock>>` list for the tenure [2](#0-1) [3](#0-2) , but that field is never consulted for the ">1" safety gate, only `tenure.first_block_mined` is used afterward for the timing/existence checks [4](#0-3) .

### Finding Description
The intended equality is: locally-known `globally_accepted_blocks` count for a reorged tenure == the true number of globally accepted blocks in that tenure on the canonical chain. If a signer's local `SignerDb` is stale (e.g., the signer restarted or was slow to observe `NewBlock` events for a tenure it wasn't actively tracking), `get_globally_accepted_block_count_in_tenure` can return 0 or 1 even though the tenure in fact produced 2+ globally accepted blocks signed by other signers [5](#0-4) .

When that happens, `check_parent_tenure_choice`'s `globally_accepted_blocks > 1` gate is bypassed [1](#0-0) , and the function falls through to a weaker check based only on the *first* block in the tenure: `get_first_approved_block_in_tenure` plus a timing comparison against `first_proposal_burn_block_timing` [6](#0-5) . If that first block happens to have been proposed close to the sortition boundary (the legitimate "poorly timed" case the timing check is designed to permit), the tenure is marked superseded and the reorg is permitted (`Ok(true)`) — even though a second, later block was mined and globally accepted on top of it, which the `>1` rule was specifically meant to protect against ("disallow reorg if more than one block has already been signed", per the comment at line 210).

Crucially, the node already returns the full authoritative `nakamoto_blocks` list for the tenure in the same `TenureForkingInfo` response used at line 191 [7](#0-6) , so the count-of-blocks safety net does not need to rely on the local, possibly-incomplete `SignerDb` at all — the check could cross-reference `tenure.nakamoto_blocks.len()` from the node, but it does not.

Nothing else in the reachable path re-derives this count from the node: `check_latest_block_in_tenure`/`get_tenure_last_block_info` only look at the single "last" locally-known signed block, not a count [8](#0-7) , and the eventual `mark_tenure_superseded` recording happens only after `check_parent_tenure_choice` returns true, with no independent node-count check.

### Impact Explanation
This breaks canonicity: a signer with a stale local view can be induced by an attacker-controlled tenure-change proposal to treat a reorg of a genuinely multi-block, globally-accepted tenure as valid ("`ReorgNotAllowed`" is not raised) [9](#0-8) [10](#0-9) . That signer's acceptance/signature then contributes weight toward finalizing a competing chain that discards more canonical history than the `>1` rule intends. This matches the Critical/CANONICITY category: a signer signing a non-canonical/conflicting block, contributing to a chain-safety violation when combined with other miners/signers acting on similarly stale or malicious views.

### Likelihood Explanation
The precondition (a signer's local `SignerDb` missing some globally-accepted blocks for a tenure it did not actively participate in, e.g., due to a restart or being slow to observe `NewBlock` events for a tenure that isn't its currently-tracked one) is a realistic, non-privileged operational condition, not something requiring compromise. The attacker only needs to win a miner slot and craft a `BlockProposal`/tenure-change against the stale signer's public sortition view — no majority signer weight, no auth token, and no local access are needed. It is repeatable against any signer instance that happens to have a stale record for the targeted tenure at the time of the reorg attempt, and the "poorly timed first block" precondition already exists as a legitimate exemption in the code, so no additional attacker capability beyond normal proposal timing is required.

### Recommendation
Do not rely solely on the local `SignerDb` count for the `>1` safety gate. Cross-check against the authoritative `tenure.nakamoto_blocks` (or an equivalent node-reported block count/height range for the tenure) already present in the `TenureForkingInfo` response, and require both sources to agree that no more than one block was produced before permitting a reorg. At minimum, treat a `None`/missing local record as "unknown" (fail closed, refuse the reorg) rather than silently falling through to a per-first-block timing check when the node's own data shows more than one block exists in the tenure.

### Proof of Concept
Rust test in `stacks-signer/src/chainstate/tests/v2.rs` style, modeled on `refused_reorg_supersedes_nothing`/`check_parent_tenure_choice_reorg_timing_ok`:
1. Set up `setup_test_environment` as in existing tests to get a `SignerDb`, mock `StacksClient`, and `cur_sortition`/`last_sortition`.
2. Seed the `SignerDb` with 0 recorded `GloballyAccepted` rows for `last_sortition.data.consensus_hash` (simulating a stale/incomplete local view), but insert one `PreCommitted`/`approved_time`-bearing record for the tenure's first block whose `approved_time` is close to the mocked sortition-receive time (to satisfy the "poorly timed" branch).
3. Mock `client.get_tenure_forking_info` to return a `TenureForkingInfo` for that tenure with `first_block_mined: Some(...)` and `nakamoto_blocks: Some(vec![block1, block2])` (i.e., two real blocks existed on the node/network for that tenure).
4. Call `cur_sortition.data.check_parent_tenure_choice(&mut signer_db, &client, &Duration::from_secs(30))`.
5. Assert `result.unwrap() == true` (reorg wrongly permitted) and that `signer_db.get_globally_accepted_block_count_in_tenure(...)` returns `0` or `1`, demonstrating the equality break: local count (0/1) != true node-reported block count (2), yet the reorg was allowed.
6. As a contrast assertion, show that if `get_globally_accepted_block_count_in_tenure` were instead seeded to reflect 2 (as it should if the signer had not missed the second block), `check_parent_tenure_choice` returns `Ok(false)`, confirming the gate works correctly only when local state is complete.

    /// Return the count of globally accepted blocks in a tenure (identified by its consensus hash)
    pub fn get_globally_accepted_block_count_in_tenure(
        &self,
        tenure: &ConsensusHash,
    ) -> Result<u64, DBError> {
        let query = "SELECT COALESCE((MAX(stacks_height) - MIN(stacks_height) + 1), 0) AS block_count FROM blocks WHERE consensus_hash = ?1 AND state = ?2";
        let args = params![tenure, &BlockState::GloballyAccepted.to_string()];
        let block_count_opt: Option<u64> = query_row(&self.db, query, args)?;
        match block_count_opt {
            Some(block_count) => Ok(block_count),
            None => Ok(0),
        }
    }
