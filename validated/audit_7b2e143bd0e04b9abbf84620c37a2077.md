### Title
Direct `syscall.Kill()` on a stale PID bypasses Go's process-reuse protection, enabling cross-job signal delivery on PID recycling - ([File: helpers/process/killer_unix.go])

### Summary
`unixKiller.Terminate`/`ForceKill` call `syscall.Kill(pk.getPID(), sig)` directly using the raw PID cached in `pk.cmd.Process()`, bypassing the safety checks (`sigMu` lock + `done` flag) that Go's `os.Process.Signal()` normally uses to prevent signaling a PID after it has already been reaped. Combined with the racy `select` in `executors/shell/shell.go` between the wait channel and context cancellation, this can result in `SIGTERM`/`SIGKILL` being sent (as a process-group signal, `-pid`) to a PID that the kernel has already recycled for an unrelated, concurrently-started process/job.

### Finding Description
`osCmd.Start()` sets `Setpgid: true` with no explicit `Pgid`, so each job's process becomes leader of its own new process group whose pgid equals its own PID [1](#0-0) [2](#0-1) . `unixKiller.getPID()` negates that PID to target the whole process group via `kill(2)` [3](#0-2) , and `Terminate`/`ForceKill` invoke `syscall.Kill` directly on that value [4](#0-3) .

The only nil-check performed is `pk.cmd.Process() == nil`; there is no check for whether the process has already been reaped. Go's standard library specifically guards against this scenario in `os.Process.Signal()`/`Wait()` via a `sigMu` mutex and `done` flag so a signal cannot race with, or follow, a completed `Wait()` for the *same* PID value being recycled by the kernel — but Runner's code calls `syscall.Kill` directly, skipping that protection entirely.

The race is reachable through `executors/shell/shell.go`'s `Run()`: the process is waited on in a separate goroutine that writes to `waitCh`, while the main goroutine `select`s between `waitCh` and `cmd.Context.Done()` [5](#0-4) . When a job finishes naturally and its context also becomes `Done()` at nearly the same instant (e.g., timeout firing right as the script's last command completes), Go's `select` can pseudo-randomly choose the `ctx.Done()` branch even though `waitCh` already has a value ready — meaning the process has already been `Wait()`ed (reaped) by the other goroutine. `KillAndWait` is then invoked on an already-reaped `Commander`, and `Terminate()` sends `syscall.Kill(-staleFreedPID, SIGTERM)`. If, in the same window, the OS has already recycled that PID for a different, concurrently-started job's process (only feasible with a small PID space, e.g. a constrained container `pid_max`, or many jobs launching on a busy shared host), the signal is delivered process-group-wide to that unrelated job instead.

### Impact Explanation
If PID recycling coincides with the race window, an unrelated concurrently-running job's entire process group can receive `SIGTERM`/`SIGKILL`, terminating or corrupting that job's execution — a cross-job denial of service triggered purely by timing/PID exhaustion, not by any privilege escalation. This violates the invariant that a job must not affect another job's workload on a shared host/shell executor.

### Likelihood Explanation
This requires: (1) a job's own process to finish essentially simultaneously with its execution context becoming `Done()` (timeout/cancellation racing completion) — a narrow, non-attacker-controlled timing window; and (2) the OS PID namespace to be small/exhausted enough (e.g., constrained container `pid_max`) that a *different* concurrently-starting job immediately reuses the exact same PID. Both conditions must align within a very short window (microseconds to low milliseconds), so this is a low-probability, environment-dependent race rather than a deterministically attacker-triggerable bug — an attacker cannot directly force PID recycling or select's branch choice. It becomes materially more likely only when an operator has configured tight `pid_max`/cgroup PID limits on a busy shared host, which is an operational choice, not a Runner-input-driven trigger.

### Recommendation
Replace direct `syscall.Kill(pid, sig)` calls in `unixKiller.Terminate`/`ForceKill` with `pk.cmd.Process().Signal(sig)` (Go's `os.Process.Signal`), which enforces the `sigMu`/`done` guard against signaling a PID after it has been reaped/recycled. Additionally, tighten the `select` in `shell.go`/`command.go` to prefer draining `waitCh` first (e.g., a non-blocking check before entering the cancellation branch) to reduce the chance of invoking `KillAndWait` on an already-completed process.

### Proof of Concept
Go integration test in `helpers/process`:
1. Start `osCmd` A with a short-lived command; immediately call `cmd.Wait()` in a goroutine and let it complete/reap.
2. Concurrently, on a system/container with an artificially small `pid_max` (or by mocking `Process().Pid` to a PID freed by A and then forcing a new process B to take that same PID), start job B's `osCmd` and call `Start()`.
3. Call `unixKiller.Terminate()` using the stale `Commander` for A (post-`Wait()`).
4. Assert that job B's process/process-group does **not** receive `SIGTERM`, e.g. by asserting B's `Wait()` exit status is not `signal: terminated` and by using `os.Process.Signal()` (with `ErrProcessDone`) as the corrected implementation, verifying it errors out instead of firing at a recycled PID.

```go
func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}
```

```go
// getPID will return the negative PID (-PID) which is the process group. The
```
