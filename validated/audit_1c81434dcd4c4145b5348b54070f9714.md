### Title
Unfunded instant-withdraw receipts can be claimed immediately, draining other users' funded claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report is a heap over-read: the code reads data past the valid/funded boundary. The analog in this codebase is `IdleCreditVault.claimInstantWithdrawRequest`, which burns the **aggregate** `instantWithdrawsRequests[_user]` counter — including entries that were created after the last `collectInstantWithdrawFunds` call and are therefore still unfunded — and immediately transfers underlying out of the strategy. The aggregate counter "over-reads" past the funded prefix of the receipt queue, letting an unprivileged user pay out an unfunded receipt with money earmarked for other users' funded claims.

### Finding Description
Instant withdrawals follow a two-step funding model:

1. `requestInstantWithdraw` burns CDO strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, and `pendingInstantWithdraws` (`contracts/strategies/idle/IdleCreditVault.sol:356-375`).
2. The strategy only actually receives underlying when the CDO calls `collectInstantWithdrawFunds`, which is invoked at epoch start when the borrower's prefunded cash is moved (`contracts/strategies/idle/IdleCreditVault.sol:398-403`). The CDO comment confirms this timing: instant-withdraw funds "will get transferred from borrower when epoch starts" (`contracts/IdleCDOEpochVariant.sol:973-978`).

`IdleCDOEpochVariant._requestWithdraw` routes into `requestInstantWithdraw` **while the epoch is running**, whenever the current APR dropped by more than `instantWithdrawAprDelta` below `lastEpochApr` (`contracts/IdleCDOEpochVariant.sol:761-769`). Such a receipt is unfunded until the *next* `startEpoch` — no collection can happen mid-epoch because `collectInstantWithdrawFunds` pulls from the CDO, which holds no borrower cash mid-epoch.

However `claimInstantWithdrawRequest` performs no funded/unfunded bookkeeping at all:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

(`contracts/strategies/idle/IdleCreditVault.sol:387-392`)

There is no check against `pendingInstantWithdraws`, no per-epoch maturity gate (unlike `_claimFundedWithdrawRequest`, which reverts while `epochNumber <= lastWithdrawRequest[_user]` at line 326), and the IdleCDO wrapper only checks `allowInstantWithdraw` (`contracts/IdleCDOEpochVariant.sol:975-978`).

### Impact Explanation
The strategy's underlying balance backs funded receipts of *other* claimants (normal funded withdraws and previously collected instant claims), plus, after default finalization, the `defaultRecoveryReserve`. Any strategy balance above zero is claimable collateral for an unfunded instant receipt:

- **Direct theft**: attacker requests an instant withdraw mid-epoch, calls `claimInstantWithdrawRequest` in the same transaction sequence, and walks away with underlying that belongs to other users' already-funded receipts. Loss is bounded only by the strategy's underlying balance / the attacker's tranche position, so a small deposit can be rolled to drain the full funded-claim pool.
- **Insolvency / freezing of honest claims**: after the drain, honest users' `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on insufficient balance — permanently if the attacker withdraws the stolen funds.

Broken invariant: one receipt, one payout — receipts are paid before they are funded. Existing guards do not stop this: `_onlyIdleCDO` is satisfied via the legitimate `claimInstantWithdrawRequest` wrapper, `allowInstantWithdraw` is on by design in instant mode, and no epoch-maturity or pending check exists on this path (in contrast to the normal-withdraw path's `epochNumber <= lastWithdrawRequest` gate).

### Likelihood Explanation
Requires instant-withdraw mode (`allowInstantWithdraw`) and an APR decrease exceeding `instantWithdrawAprDelta` — a normal market condition, not a privileged action. The attacker only needs a KYC-passed wallet holding tranche tokens and an APR drop to trigger the `requestInstantWithdraw` branch. The strategy needs only to hold a nonzero funded-claim balance, which is the common state once any prior withdrawal was collected. No privileged actor misbehavior is involved; the borrower/manager act honestly.

### Recommendation
Track instant receipts per epoch and only pay out the portion that has been collected, mirroring the normal-withdraw gating:

- Reuse the existing `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch` maps: in `claimInstantWithdrawRequest`, settle only epochs whose funds have been collected (`collectInstantWithdrawFunds` already knows the collected amount — record a `collectedInstantByEpoch` watermark), and skip/revert on requests whose epoch is still unfunded.
- Alternatively, cap the claimable amount at `instantWithdrawsRequests[_user] - pendingInstantShare[_user]` derived from `pendingInstantWithdraws`, so unfunded receipts cannot be burned and paid.

### Proof of Concept
Foundry fork sketch (contracts under test: `IdleCDOEpochVariant`, `IdleCreditVault`):

```solidity
// Setup: instant-withdraw enabled vault, honest lender L deposits AA.
// Epoch N is running; borrower funds are already deployed.

// 1. Honest user H requests a normal withdraw earlier; at a prior startEpoch
//    collectInstantWithdrawFunds / collectWithdrawFunds moved underlying into
//    the strategy so IdleCreditVault holds `fundedBal` backing H's receipt.
assertGt(underlying.balanceOf(address(strategy)), 0);

// 2. Manager (honest) lowers APR so that
//    lastEpochApr > unscaledApr + instantWithdrawAprDelta.
//    Attacker A (KYC'd, holds AA tranches) calls:
vm.prank(attacker);
cdo.requestWithdraw(attackerTrancheBal, address(AAtranche));
// -> requestInstantWithdraw mints receipt, pendingInstantWithdraws += amt,
//    but NO underlying was collected (epoch running, no startEpoch yet).

// 3. Attacker immediately claims — no epoch-maturity or funded check:
vm.prank(attacker);
cdo.claimInstantWithdrawRequest();

// 4. Attacker received `amt` underlying even though the strategy was never
//    funded for this request; the transfer consumed honest user's funded pool.
assertEq(underlying.balanceOf(attacker), amt);
// Honest claim now reverts on insufficient strategy balance:
vm.expectRevert();
cdo.claimWithdrawRequest(); // or H's claimInstantWithdrawRequest
```

Key assertion: `pendingInstantWithdraws` increased at step 2 (receipt unfunded), yet step 3 paid out in full — the payout "read" past the funded boundary of the receipt queue, analogously to the heap over-read reading past valid input.

If it additionally enforces a per-epoch funded watermark, this specific path may be guarded and the analog invalid — verify that function body in a Devin session before finalizing severity.
