### Title
`get_builder_withdrawals` commits the full requested amount to the execution layer while `apply_withdrawals` deducts only a balance-capped amount, minting Gwei for the builder's fee recipient - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` (specs/gloas/beacon-chain.md:1802-1834) copies `withdrawal.amount` verbatim from `state.builder_pending_withdrawals` into the `Withdrawal` objects placed in `state.payload_expected_withdrawals`. `apply_withdrawals` (specs/gloas/beacon-chain.md:1920-1932), however, deducts only `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance`. The `Withdrawal` list is a commitment the execution layer is required to honor exactly (`specs/gloas/beacon-chain.md:1967-1980`: "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer"), so if `withdrawal.amount > builder_balance`, the fee recipient is paid the full uncapped `withdrawal.amount` on the execution layer while the beacon state only subtracts the smaller, balance-capped amount from the builder. This is analogous to the reported Stargate bug: a payout is computed/committed from one value (`amount`) while only a smaller value is actually charged against the source of funds, and the difference is not accounted for anywhere - except here the mismatch mints Gwei rather than losing it.

### Finding Description
The chain of code:
1. `process_execution_payload_bid` (specs/gloas/beacon-chain.md:2084-2141) records a `BuilderPendingPayment.withdrawal.amount = bid.value` after `can_builder_cover_bid` passes. [1](#0-0) 
2. `can_builder_cover_bid` (specs/gloas/beacon-chain.md:1167-1179) only checks solvency at bid-acceptance time, using `get_pending_balance_to_withdraw_for_builder`, which sums *all* currently-pending payments and withdrawals for that builder against current balance: [2](#0-1) 
3. `settle_builder_payment` moves the payment into `state.builder_pending_withdrawals` unconditionally, with no balance re-check: [3](#0-2) 
4. When the withdrawal is finally processed, `get_builder_withdrawals` builds the `Withdrawal` entry using the raw `withdrawal.amount` with no cap: [4](#0-3) 
5. `apply_withdrawals` caps only the *state* deduction to available balance: [5](#0-4) 
6. The spec explicitly states withdrawals are a binding commitment the execution layer must honor exactly, and are deducted immediately (unlike deposits) specifically "to not break the total supply invariant": [6](#0-5) 

The tests confirm this is not accidental — they explicitly assert the committed `withdrawal.amount` is the full **requested** amount while the balance deduction is capped: [7](#0-6) [8](#0-7) 

**Concrete state/equality break:** if a builder's balance can fall below the sum of its already-accepted `builder_pending_withdrawals`/`builder_pending_payments` amounts between bid-acceptance time and settlement time, the execution-layer `Withdrawal.amount` committed by the block (which the EL must pay to `fee_recipient`) exceeds the amount actually subtracted from any beacon-state balance. That is Gwei paid to a recipient that is not backed by an equal decrease anywhere in state — a violation of the "total supply invariant" the spec itself calls out at beacon-chain.md:1980.

The remaining open question is exactly how a builder's balance can shrink below its already-committed pending withdrawal/payment total before settlement, given `can_builder_cover_bid` is checked at bid-acceptance. Builder exit is blocked while `get_pending_balance_to_withdraw_for_builder != 0` (specs/gloas/builder.md builder exit request check, specs/gloas/beacon-chain.md:2286-2307), and builders cannot be slashed. Whether another path (e.g., overlapping bids across different in-flight slots each individually checked against the same not-yet-decremented balance, or bugs in how `builder_pending_payments` interacts with `builder_pending_withdrawals` sums across epoch boundaries as exercised in `test_builder_payment_after_missed_epochs`) can produce this condition was not fully confirmed with the available context — this requires deeper trace-through of `apply_parent_execution_payload`'s epoch-boundary eviction logic and multi-bid interleaving, which the current search could not exhaustively verify.

### Impact Explanation
If reachable, this breaks the Critical-tier "Gwei created... paid to a non-owner" criterion: an execution-layer payment is executed that the beacon chain does not actually debit from any account, effectively inflating total ETH in circulation and paying a builder's `fee_recipient` more than the protocol actually charges the builder.

### Likelihood Explanation
Uncertain / not fully proven. The direct case tested in the spec's own test suite (`test_builder_withdrawal_insufficient_balance*`) deliberately sets up an under-collateralized `builder_pending_withdrawals` entry via test helpers rather than through the normal bid/settlement path, so those tests do not by themselves prove the state is reachable through valid, spec-following block processing (`can_builder_cover_bid` is meant to prevent this at bid-acceptance). Confirming or refuting real reachability requires further analysis of whether the sum of concurrently outstanding bids/payments across pending slots can exceed a builder's balance by the time `settle_builder_payment`/`get_builder_withdrawals` runs.

### Recommendation
Either (a) cap the `amount` placed in the `Withdrawal` object in `get_builder_withdrawals` at `min(withdrawal.amount, state.builders[builder_index].balance)` so the EL-facing commitment matches what is actually deducted, or (b) re-verify at settlement time that `can_builder_cover_bid`-style solvency still holds and reject/adjust otherwise, ensuring the amount promised to the execution layer never exceeds the amount subtracted from beacon state.

### Proof of Concept
Not fully constructible from the available spec-only context (tests/helpers were excluded from consideration per scope, and the actual attacker-controlled path to under-collateralize a settled `builder_pending_withdrawals` entry through valid bids alone was not confirmed). The mechanical defect — `get_builder_withdrawals` using uncapped `withdrawal.amount` vs. `apply_withdrawals` capping the deduction — is directly demonstrated by the cited spec functions and by the repository's own tests (`test_builder_withdrawal_insufficient_balance`, `test_builder_withdrawal_insufficient_balance_realistic_bounds`), which show `withdrawal.amount` (committed to `payload_expected_withdrawals`) remaining at the full requested value while `builders[i].balance` is only decremented to zero.

#### New `get_pending_balance_to_withdraw_for_builder`

```python
def get_pending_balance_to_withdraw_for_builder(
    state: BeaconState, builder_index: BuilderIndex
) -> Gwei:
    balance = Gwei(0)
    for withdrawal in state.builder_pending_withdrawals:
        if withdrawal.builder_index == builder_index:
            balance += withdrawal.amount
    for payment in state.builder_pending_payments:
        if payment.withdrawal.builder_index == builder_index:
            balance += payment.withdrawal.amount
    return balance
```

#### New `can_builder_cover_bid`

```python
def can_builder_cover_bid(
    state: BeaconState, builder_index: BuilderIndex, bid_amount: Gwei
) -> bool:
    builder_balance = state.builders[builder_index].balance
    pending_withdrawals_amount = get_pending_balance_to_withdraw_for_builder(state, builder_index)
    min_balance = MIN_DEPOSIT_AMOUNT + pending_withdrawals_amount
    if builder_balance < min_balance:
        return False
    return builder_balance - min_balance >= bid_amount

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()

##### New `get_builder_withdrawals`

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
