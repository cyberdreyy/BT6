### Title
Signer wedges into never emitting a `BlockResponse` after re-proposal following `LocallyRejected` due to `check_state` forbidding `LocallyRejected -> PreCommitted` - (File: `stacks-signer/src/signerdb.rs`)

### Summary
`BlockInfo::check_state` in `stacks-signer/src/signerdb.rs` only permits the `PreCommitted` state to be entered from `Unprocessed`, never from `LocallyRejected`. If a signer previously rejected a block (moving it to `LocallyRejected` via `mark_locally_rejected`) and the same block (same `signer_signature_hash`) is later re-validated as valid by the node, `mark_pre_committed()` will return `Err` because the state machine disallows that transition, even though the block is now confirmed valid.

### Finding Description
`check_state` explicitly encodes the transition table: [1](#0-0) 

For `BlockState::PreCommitted`, the only permitted prior state is `Unprocessed` (`matches!(prev_state, BlockState::Unprocessed)`), with the general same-state short-circuit (`if *prev_state == state { return true }`) as the only other allowed case. There is no rule that permits `LocallyRejected -> PreCommitted`.

`mark_locally_rejected` sets `valid = Some(false)` and calls `move_to(BlockState::LocallyRejected)`: [2](#0-1) 

`mark_pre_committed` sets `valid = Some(true)`, records `approved_time`, and calls `move_to(BlockState::PreCommitted)`, which internally calls `check_state`: [3](#0-2) [4](#0-3) 

So once a `BlockInfo` for a given `signer_signature_hash` has reached `LocallyRejected`, any subsequent call to `mark_pre_committed()` for that same in-memory/persisted `BlockInfo` record is guaranteed to fail with `Err("Invalid state transition from LocallyRejected to PreCommitted")`, regardless of whether the underlying block content is now judged valid by node validation.

I was able to fully confirm the state-machine defect in `signerdb.rs` from the source. I was **not able to fully re-verify**, within the available tool budget, the exact downstream handling in `stacks-signer/src/v0/signer.rs::handle_block_validate_ok` — specifically whether that function, upon receiving `Err` from `mark_pre_committed`, only logs a warning and returns without calling `send_block_response` (as the question asserts), or whether it has other fallback logic (e.g., falling through to `mark_locally_rejected`/re-sending the prior rejection, or resetting `BlockInfo` to `Unprocessed` on a genuinely new proposal with a different DB row). Grep confirmed that `handle_block_validate_ok`, `check_block_against_signer_db_state`, and `should_reevaluate_reject_reason` all exist in `v0/signer.rs`, but I could not read their bodies before running out of tool calls.

### Impact Explanation
If the downstream behavior is as described (silent log-and-return with no `send_block_response` call on `mark_pre_committed` failure), this breaks the bounded-liveness guarantee for that specific `signer_signature_hash`: the signer neither accepts nor rejects a block it has already determined to be currently valid, and other signers/miners waiting on this signer's `BlockResponse` for that hash never receive one. This matches the **High** severity category ("a signer wedged into never signing valid blocks (liveness)"), scoped to the specific block hash rather than the whole signer process, and lasts until a distinct new proposal (different hash) supersedes it.

### Likelihood Explanation
The preconditions are attacker-cheap and match the unprivileged-attacker profile: win one miner slot, propose a block, have it rejected by the signer for a transient/reversible reason, then re-propose the identical block (same `signer_signature_hash`) later so the same `BlockInfo` DB row is reused and revalidated as `Ok`. This requires no majority of signers, no node operator access, and no auth token — only proposal crafting and gossip. It is repeatable per affected block hash but the actual triggering conditions (which reject reasons are "reevaluable" via `should_reevaluate_reject_reason`, and whether the DB lookup key in `handle_block_validate_ok`/`check_block_against_signer_db_state` reuses the same `BlockInfo` row rather than creating a fresh `Unprocessed` one) could not be fully confirmed from the code read so far.

### Recommendation
Extend `check_state` to allow `LocallyRejected -> PreCommitted` (and symmetric `LocallyAccepted -> PreCommitted`) when the block is being re-validated and found valid, or have `handle_block_validate_ok` reset the stored `BlockInfo` to `Unprocessed` before calling `mark_pre_committed` when re-validating a previously `LocallyRejected` block for a reversible reason. Additionally, ensure the `Err` path from `mark_pre_committed`/`move_to` always still results in a terminal `BlockResponse` being sent (either the previous rejection resent, or an explicit new decision), never a silent return.

```rust
    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
```
