### Title
Unauthenticated Pipeline Run Resume Endpoint Allows Arbitrary Task ID Manipulation - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `/v2/resume/:runID` endpoint is mounted on the completely unauthenticated route group (`unauthedv2`) in `core/web/router.go`, bypassing all of the session/token/external-initiator authentication methods applied to every other `v2` route. `PipelineRunsController.Resume` accepts an attacker-supplied `runID` (a task UUID) and an arbitrary JSON `ResumeRequest` body, and directly calls `prc.App.ResumeJobV2` to inject a result and resume that pipeline run — with no ownership or ACL check tying the caller to that run.

### Finding Description
In `core/web/router.go`, the resume route is deliberately excluded from the authenticated group:
```go
unauthedv2 := r.Group("/v2")
...
unauthedv2.PATCH("/resume/:runID", prc.Resume)
``` [1](#0-0) 

Compare this to every other mutating v2 route, which requires `auth.Authenticate(...)` with `AuthenticateByToken`/`AuthenticateBySession`/`AuthenticateExternalInitiator`: [2](#0-1) 

`PipelineRunsController.Resume` parses only a `runID` (task UUID) from the URL and a `ResumeRequest` body, then calls `App.ResumeJobV2` without validating that the caller is authorized to complete that specific task: [3](#0-2) 

This is structurally the same bug class as the SumSub finding: a GET/PATCH endpoint that accepts a caller-controlled identifier (`userId`/`levelName` in the SumSub case, `runID`/result payload here) and performs a sensitive state-changing action — issuing a token there, injecting a pipeline task result and resuming execution here — without any authentication or per-resource authorization check. The audit log entry name itself, `audit.UnauthedRunResumed`, confirms this route is knowingly unauthenticated by design, which increases the severity if `runID`s are guessable or leaked (e.g., via job run history responses, logs, or bridge/external-adapter callbacks).

### Impact Explanation
If a `runID` (task UUID) is disclosed or guessable (e.g., observed in logs, external adapter callback URLs, or via any endpoint that returns run details), any unauthenticated network client can supply an arbitrary result body to `ResumeJobV2`, forging the outcome of a Chainlink job's async/bridge task and resuming the pipeline with attacker-controlled data. This can corrupt job run results, pipeline outputs, and downstream on-chain reports/transactions built from those results — a direct integrity compromise and potential unauthorized fund/state-affecting action, matching the OWASP API2/API5 categories cited in the source report (broken authentication / broken function-level authorization on a sensitive state-changing action).

### Likelihood Explanation
Likelihood depends on whether `runID` values are exposed to unprivileged/external parties. Chainlink's design intentionally uses this endpoint as the callback target for asynchronous bridge/external-initiator tasks, meaning the UUID is handed out to external systems by design (hence "Unauthed" in the audit event name). If any external adapter, log, or client leaks or logs this UUID, or if UUIDs can be enumerated/replayed once observed, exploitation requires no credentials at all — only knowledge of a valid pending `runID`. This is a lower-effort attack than the SumSub case (which required only knowing a `userId`), since UUIDs are less guessable, but the complete absence of authentication is a stronger structural match to the report than any other reachable client-facing route in the codebase.

### Recommendation
- Require the resume request to include a secret/token bound to the specific pending task (e.g., a per-task resume token issued when the task was created), verified server-side before resuming.
- Alternatively, restrict this endpoint to only be callable by the specific bridge/external-adapter it targets, using a scoped token (similar to the `X-Chainlink-EA-*` external-initiator scheme) rather than leaving it fully open.
- Ensure `runID`s are treated as sensitive values and are not leaked in logs, error messages, or other API responses to unprivileged callers.
- Add resource-level checks so that resuming a task requires proof of authorization tied to that specific pending task, not just knowledge of its UUID.

### Proof of Concept
1. Create/observe a pending pipeline run task and obtain its `runID` (task UUID) — e.g., by monitoring an external adapter callback or job run logs.
2. Send an unauthenticated request:
   ```
   curl -X PATCH "http://<node>/v2/resume/<runID>" \
        -H "Content-Type: application/json" \
        -d '{"error": null, "value": "<attacker-controlled-result>"}'
   ```
3. The server returns `HTTP 200` and resumes the pipeline with the attacker-supplied result, as confirmed by `core/web/pipeline_runs_controller.go` `Resume` calling `prc.App.ResumeJobV2` with no auth check, on a route explicitly excluded from `auth.Authenticate(...)` in `core/web/router.go`.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
```
