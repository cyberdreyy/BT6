### Title
`getTransaction`/`getBlock` pre/post token balances misreport `uiAmount` for interest-bearing and scaled-UI-amount SPL Token-2022 mints - (File: `runtime/src/transaction_balances.rs`)

### Summary
`svm_token_info_to_token_balance` constructs the `TransactionTokenBalance.ui_token_amount` field using only the mint's raw `decimals`, via `SplTokenAdditionalDataV2::with_decimals(decimals)`, deliberately dropping the `InterestBearingConfig`/`ScaledUiAmountConfig` scaling that all other token-balance RPC paths (`getTokenAccountBalance`, `getTokenSupply`, `getParsedAccountInfo`/`getTokenAccountsByOwner`) apply.

### Finding Description
`token_amount_to_ui_amount_v3` computes `ui_amount`/`ui_amount_string` differently depending on which `SplTokenAdditionalDataV2` is supplied: if `interest_bearing_config` or `scaled_ui_amount_config` is set, it applies the SPL Token-2022 extension's `amount_to_ui_amount` scaling function; otherwise it does a naive `amount / 10^decimals` calculation. [4](#0-3) 

For live account/RPC balance queries, the code correctly fetches the mint account and extracts these extension configs before converting the amount: [3](#0-2) [5](#0-4) 

However, `SvmTokenInfo::unpack_token_account` (used to populate pre/post token balances for `getTransaction`/`getBlock`/`getConfirmedTransaction` transaction metadata) only extracts `decimals` from the mint, discarding any interest-bearing or scaled-UI-amount extension state: [6](#0-5) 

`svm_token_info_to_token_balance` then converts this raw amount using bare decimals only, explicitly noting in a comment that consideration for interest/scaling is skipped: [1](#0-0) 

For a Token-2022 mint configured with `InterestBearingConfig` or `ScaledUiAmountConfig`, this produces a `uiAmount`/`uiAmountString` in `preTokenBalances`/`postTokenBalances` that diverges from the value reported by `getTokenAccountBalance`/`getTokenSupply`/`getAccountInfo(jsonParsed)` for the exact same account and amount at the exact same slot—directly analogous to the Lido adapter's `price()` silently omitting the stETH→ETH conversion step and returning an incomplete/incorrect converted value.

### Impact Explanation
This falls under "wrong ... account data returned" from a single unprivileged JSON-RPC query. Any client relying on `getTransaction`/`getBlock` token balance deltas (e.g. wallets, explorers, indexers, exchanges reconciling deposits/withdrawals) for interest-bearing or scaled-UI-amount Token-2022 mints will compute or display incorrect UI balances/deltas, while the raw `amount` string field is unaffected (only `ui_amount`/`ui_amount_string` are wrong). Because this is called out as deliberate/known behavior in the source comment rather than an oversight, actual severity is bounded — no consensus state is affected and the raw on-chain `amount` remains correct, but downstream UI-facing consumers can be misled, mirroring the Medium-severity judged outcome of the original Lido report.

### Likelihood Explanation
Any Token-2022 mint using the `InterestBearingMint` or `ScaledUiAmount` extension, combined with any transaction touching a related token account, triggers this in every `getTransaction`/`getBlock` response — no special conditions or privileges required, purely a read query against normal transaction metadata.

### Recommendation
Thread the mint's `SplTokenAdditionalDataV2` (interest-bearing/scaled-UI-amount config plus decimals) through `SvmTokenInfo`/`svm_token_info_to_token_balance`, consistent with how `get_mint_owner_and_additional_data`/`get_additional_mint_data` build it for other RPC token-balance paths, so pre/post token balances reflect the same UI-amount semantics as `getTokenAccountBalance`/`getParsedAccountInfo`. At minimum, document this divergence prominently in the public RPC docs for `getTransaction`/`getBlock` so downstream integrators are aware `uiAmount` in token balance deltas does not reflect Token-2022 scaling extensions.

### Proof of Concept
1. Create a Token-2022 mint with the `ScaledUiAmountConfig` extension set to a non-1.0 multiplier (or `InterestBearingConfig` with nonzero rate).
2. Perform a transfer touching an account of that mint, and fetch the transaction via `getTransaction`.
3. Compare `meta.preTokenBalances[i].uiTokenAmount.uiAmount` / `postTokenBalances[i].uiTokenAmount.uiAmount` against the value returned by `getTokenAccountBalance` for the same account at the same slot — the transaction-status value is computed with `SplTokenAdditionalDataV2::with_decimals(decimals)` only (`runtime/src/transaction_balances.rs:53-59`), omitting the multiplier/interest applied by `getTokenAccountBalance` (`rpc/src/rpc.rs:2055-2072`), producing differing `uiAmount` values for the identical underlying token amount.

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };
