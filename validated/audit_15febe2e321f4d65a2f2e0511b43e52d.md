### Title
Lockup creator can substitute a malicious `staking_pool_whitelist_account_id`, letting an attacker-controlled "staking pool" drain locked/unvested funds - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create()` lets the *caller who funds the lockup* (not the NEAR Foundation) optionally override the staking-pool whitelist contract that the deployed lockup will trust for its entire lifetime, instead of forcing use of the factory's own vetted `whitelist_account_id`.

### Finding Description
The `whitelist/README.md` states the whole point of the whitelist contract is to guarantee that a lockup's staking-pool delegate "should guarantee that the delegated tokens can not be lost or locked… only approved (whitelisted) accounts of staking pool contracts can receive delegated tokens from lockup contracts" [1](#0-0) . This binding is: `staking_pool_whitelist_account_id used by the lockup == the Foundation-controlled whitelist`.

However, `LockupFactory::create()` accepts an `Option<ValidAccountId> whitelist_account_id` argument supplied by whoever calls `create` (the funder), and if present it is used verbatim as the `staking_pool_whitelist_account_id` baked into the newly created lockup contract, instead of the factory's own `self.whitelist_account_id`: [2](#0-1) 

There is no validation that the passed-in `whitelist_account_id` equals the factory's trusted whitelist, no restriction to Foundation-only callers, and this parameter is directly serialized into the `LockupArgs` sent to the new lockup's `new()` call: [3](#0-2) .

Inside the lockup contract, `select_staking_pool()` trusts whatever whitelist contract was configured at construction time to vouch for a staking pool account, with no additional check: [4](#0-3) . Once whitelisted, `deposit_to_staking_pool()`/`deposit_and_stake()` will move up to the entire on-chain account balance (including locked/unvested principal, not just released/liquid funds) to that "staking pool" account: [5](#0-4) , gated only by `get_account_balance() >= amount`, not by the vesting/lockup schedule.

Because `create()` lets the funder pick their own whitelist contract (e.g., one that whitelists any account, including one they fully control), the owner can get their own throwaway "staking pool" contract whitelisted by this fake whitelist and then call `select_staking_pool` + `deposit_to_staking_pool`/`deposit_and_stake` to move the full locked balance to that attacker-controlled account — funds which are supposed to remain locked/vesting under the lockup schedule and, in the vesting case, subject to `terminate()` clawback by the foundation. This breaks the "lockup's releasable amount vs. its schedule" custody binding: the schedule says funds are non-transferable until vested, but the whitelist substitution lets the actual custodian binding (staking pool == vetted, fund-safe contract) be forged, releasing locked NEAR early into a wallet the owner fully controls.

### Impact Explanation
This matches the Critical impact category: "locked or unvested tokens released early." Vesting-locked or lockup-duration-locked NEAR — which per the lockup design should only reach the owner's liquid balance according to the vesting/release schedule (and remain clawback-able by the foundation for unvested vesting schedules) — can be extracted early by routing it through a self-controlled fake "staking pool" whitelisted by a self-controlled fake whitelist contract supplied at lockup-creation time.

### Likelihood Explanation
Likelihood is high for self-funded/self-created lockups: the README explicitly advertises that "any user" can create and fund a lockup contract via the factory [6](#0-5) , and the `whitelist_account_id` override is an ordinary, unauthenticated argument to `create()` — no special privilege beyond calling the public `create` method and attaching the minimum deposit is required, and there is a test in the codebase (`test_create_lockup_with_custom_whitelist_success`) confirming this override path is functional and reachable: [7](#0-6) .

### Recommendation
Remove the caller-supplied `whitelist_account_id` override in `LockupFactory::create()`, or, at minimum, restrict it so it can only ever be the factory's own vetted `self.whitelist_account_id` (i.e., drop the `Option` parameter entirely, or validate `account_id == self.whitelist_account_id` before use), ensuring every lockup deployed by the factory always trusts the single Foundation-controlled staking-pool whitelist.

### Proof of Concept
1. Attacker calls `LockupFactory::create(owner_account_id = attacker_or_puppet, ..., whitelist_account_id = Some("attacker-whitelist"))`, attaching `MIN_ATTACHED_BALANCE` plus the amount they want to "lock" (this can be tokens the attacker actually controls, e.g. as a beneficiary receiving a vesting grant, or simply funds they choose to lock to appear compliant while retaining an escape hatch) — see `lockup-factory/src/lib.rs:107-166`.
2. `attacker-whitelist` is a contract the attacker deploys beforehand that implements `is_whitelisted(...) -> bool` always returning `true`.
3. The new lockup is created with `staking_pool_whitelist_account_id = "attacker-whitelist"` instead of the Foundation's `staking-pool-whitelist` (see `LockupArgs` construction, `lockup-factory/src/lib.rs:140-157`).
4. As owner, attacker calls `select_staking_pool("attacker-pool")` on the lockup; `attacker-whitelist.is_whitelisted("attacker-pool")` returns `true`, so the lockup accepts it (`lockup/src/owner.rs:12-41`, `lockup/src/owner_callbacks.rs`).
5. Attacker calls `deposit_to_staking_pool(full_locked_amount)` — this passes the `get_account_balance() >= amount` check (which is not schedule-aware) and transfers the full locked/unvested NEAR balance to `attacker-pool`, an account fully controlled by the attacker (`lockup/src/owner.rs:81-120`).
6. The attacker now holds the NEAR in `attacker-pool`, outside the lockup contract and outside the vesting/lockup release schedule, and outside the foundation's ability to `terminate()`/claw back unvested tokens.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        self.assert_owner();
        assert!(
            env::is_valid_account_id(staking_pool_account_id.as_bytes()),
            "The staking pool account ID is invalid"
        );
        self.assert_staking_pool_is_not_selected();

            &env::current_account_id(),

        self.assert_owner();

        self.assert_staking_pool_is_idle();
        self.assert_no_termination();
        assert!(
            self.get_account_balance().0 >= amount.0,
            "The balance that can be deposited to the staking pool is lower than the extra amount"
