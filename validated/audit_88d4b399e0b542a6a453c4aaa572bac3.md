This confirms the design conclusively. Any new receipt created from within a `FunctionCall` execution is always stamped with `predecessor_id: account_id.clone()` — i.e., the account whose contract code is currently running — regardless of what key or permission authorized the *outer* receipt that invoked it. [1](#0-0) [2](#0-1) [3](#0-2) 

**Why the described exploit doesn't work as a privilege-escalation bug:**

1. `FunctionCallPermission` is only checked at two points: `verify_function_call_permission` (`runtime/runtime/src/verifier.rs:166-208`), which validates a *directly signed* `SignedTransaction`, and the analogous check inside `apply_delegate_action` (`runtime/runtime/src/actions.rs:656-710`) for meta-transactions. Both checks operate on the action list of the outer transaction/delegate action *before* it is converted into a receipt — they never re-run once contract code starts executing. [4](#0-3) 

2. Once inside `action_function_call` / `execute_function_call`, any promise the contract creates (`promise_batch_create`, `promise_batch_action_transfer`, `promise_batch_action_function_call`, etc.) is built through `ReceiptManager`, and when the outcome is finalized every resulting receipt is assigned `predecessor_id: account_id.clone()`, where `account_id` is the account that is currently executing the contract (the receiver of the *current* receipt), not the signer of the outer transaction and not any access key. [5](#0-4) 

3. Consequently, in the scenario described — a narrow `FunctionCallPermission` key on the granter's account restricted to call a specific method on attacker's contract with `deposit == 0` — the receipt actually delivered to attacker's contract has `receiver_id = attacker_contract`. Any promise attacker's contract subsequently issues "back to the granter's account" has `predecessor_id = attacker_contract` (its own account), not the granter. The deposit on that promise is funded from and checked against **attacker's own contract account balance** (`account.amount().checked_add(function_call.deposit)` in `action_function_call`, and later balance checks during `apply_action`), never against the granter's balance or the narrow key's allowance. [6](#0-5) 

4. There is no mechanism, and no code path, by which a receipt generated from inside a `FunctionCall` execution inherits or is checked against the `AccessKeyPermission` that authorized the outer transaction. Access-key permission is a **transaction-admission-time** concept (checked in `verifier.rs` / the delegate-action equivalent), not a runtime "credential" attached to receipts or promises. The invariant "a promise never carries privileges its creator lacked" holds trivially because a promise's privileges are simply whatever its creator account (the currently executing contract's own account) already has over its own balance — that account was never restricted by the narrow key in the first place; only the *narrow key's owner's* ability to directly submit actions was restricted.

This means the premise of the question — that a callback receipt might "execute with the permissions of whichever account produced it" in a way that escalates beyond the original key — actually describes the *correct*, intended design: the callback executes with the permissions of its producer (the currently running contract account), and that producer can only spend its own funds, never the granter's, through this path.

/// Validates FunctionCall permission constraints:
/// - Transaction must have exactly one action
/// - Action must be FunctionCall with zero deposit
/// - Receiver must match permission's receiver
/// - Method name must be in allowed list (if list is non-empty)
fn verify_function_call_permission(
    function_call_permission: &FunctionCallPermission,
    tx: &Transaction,
) -> Result<(), InvalidTxError> {
    if tx.actions().len() != 1 {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::RequiresFullAccess,
        ));
    }
    let Some(Action::FunctionCall(function_call)) = tx.actions().get(0) else {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::RequiresFullAccess,
        ));
    };
    if function_call.deposit > Balance::ZERO {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::DepositWithFunctionCall,
        ));
    }
    let tx_receiver = tx.receiver_id();
    let ak_receiver = &function_call_permission.receiver_id;
    if tx_receiver != ak_receiver {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::ReceiverMismatch {
                tx_receiver: tx_receiver.clone(),
                ak_receiver: ak_receiver.clone(),
            },
        ));
    }
    if !function_call_permission.method_names.is_empty()
        && function_call_permission
            .method_names
            .iter()
            .all(|method_name| &function_call.method_name != method_name)
    {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::MethodNameMismatch {
                method_name: function_call.method_name.clone(),
            },
        ));
    }
    Ok(())
}
