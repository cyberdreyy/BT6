Confirmed: `assert_valid_request` in both `multisig/src/lib.rs` and `multisig2/src/lib.rs` only checks that the request/confirmations map entries exist and that the *caller* is currently a valid member/signer — it never re-validates the *existing* confirmations already stored in the `confirmations` set against current membership. Combined with `delete_member`/`DeleteKey` only purging requests *originated by* the removed member/key (not confirmations they cast on *other* pending requests), stale confirmations from removed members persist and are counted toward `num_confirmations`.

### Title
Stale confirmations from removed multisig members/keys still count toward execution threshold - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
The multisig contracts (`multisig/src/lib.rs` and `multisig2/src/lib.rs`) allow a pending request to be executed by counting confirmations that were cast by members/keys which have since been removed from the multisig, violating the intended invariant that `num_confirmations` live, currently-authorized approvals are required before a request executes.

### Finding Description
`confirm()` in [1](#0-0)  checks `confirmations.len() as u32 + 1 >= self.num_confirmations` purely by counting entries already stored in the `confirmations: LookupMap<RequestId, HashSet<String>>` map, and only validates that the *current caller* is a live member via `current_member()` inside `assert_valid_request` ( [2](#0-1) ). It never re-checks that the *other, already-recorded* confirmations in the set still belong to current members.

When a member is removed via `delete_member` ( [3](#0-2) ), the cleanup logic only deletes requests that were *added by* (`r.member == member`) the removed member — it clears `confirmations`/`requests` for requests that member originated, but does nothing to strip that member's confirmation entries from *other* pending requests they had previously confirmed. The equivalent `DeleteKey` handling in the v1 contract has the same gap ( [4](#0-3) ).

The binding that should hold is: `confirmations counted toward threshold == confirmations from members that are members at execution time`. Because stale entries are never purged, this becomes `confirmations counted > confirmations from live members` once a confirming member is removed after confirming but before the request reaches quorum.

### Impact Explanation
This lets a request execute (an arbitrary `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, `DeployContract`, etc. to `receiver_id`) with fewer *live, currently authorized* approvals than `num_confirmations` mandates — i.e., a multisig request executed below the intended live-member threshold. Per the impact criteria this is a Critical-class issue ("a multisig request executed below threshold"), since it allows moving NEAR or performing privileged self-actions with insufficient current authorization.

### Likelihood Explanation
This requires no admin cooperation beyond the multisig's own normal governance actions (a member confirms a request, then that same member's removal is later separately approved by quorum — a plausible sequence, e.g. offboarding a member who had pending approvals, or an adversarial member/key deliberately confirming several pending requests before being removed). It requires only ordinary member-level access (not the foundation, not a redeploy, not a victim key), and is fully reachable through public contract methods `confirm`, `add_request`, and `execute_request` via `DeleteMember`/`DeleteKey`.

### Recommendation
When a member/key is removed, purge that member's confirmation entries from every pending request's `confirmations` set (not just requests they originated), or alternatively re-validate at execution time (inside `confirm()`, right before comparing against `num_confirmations`) that every account/public key present in the `confirmations` set is still a current member, discarding stale entries before counting.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. `B` calls `add_request(R)` where `R` is `Transfer { amount }` to some attacker-controlled `receiver_id` (or any `MultiSigRequest`) — `add_request` at [5](#0-4) .
3. `A` calls `confirm(R)` — only 1/2 confirmations, request stays pending; `A`'s entry is stored in `confirmations[R]`.
4. Separately, quorum (`B`+`C`) approves and executes a `DeleteMember { member: A }` request, removing `A` from `self.members` via `delete_member` ( [3](#0-2) ). Note this cleanup does not touch `confirmations[R]`.
5. `C` (a legitimate, still-current member) calls `confirm(R)`. `confirmations.len()` (which still contains stale `A`) becomes `2 >= num_confirmations(2)`, so `R` executes via `execute_request` — even though only `B` (added) and `C` (confirmed) are actually current, live members; `A`'s stale confirmation was illegitimately counted.

            .unwrap_or_else(|| env::panic_str("Must be validated above"));

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
