### Title
Global rejection ("`GloballyAccepted`" globally-rejected timing gap) does not exist here — reorg permission for an established tenure can be granted based on `approved_time=None`, letting a poorly-timed *tenure-change* proposal reorg an already-signed, well-established competing tenure - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs:170-295`) decides whether a miner is allowed to reorg a prior tenure. For each reorged tenure with exactly one globally-accepted block, it fetches `signer_db.get_first_approved_block_in_tenure(...)` and computes `proposal_to_sortition = sortition_state_received_time - local_block_info.approved_time`. If `approved_time` is `None` the code substitutes `0`, i.e. treats the block as if it were signed an instant before the competing sortition arrived — always satisfying `proposal_to_sortition < first_proposal_burn_block_timing` and therefore *always permitting* the reorg, regardless of how long ago the tenure was actually established.

### Finding Description
`get_first_approved_block_in_tenure` (`stacks-signer/src/signerdb.rs:1518-1527`) returns a block matching `signed_self IS NOT NULL OR signed_group IS NOT NULL OR approved_time IS NOT NULL`, ordered by height ascending. `approved_time` is populated by `mark_pre_committed` (and by local/group acceptance). The comment on `mark_locally_accepted`/`mark_globally_accepted` states these "preserve already-set timestamps" — but a first-inserted row can, in principle, carry a `NULL approved_time` while still satisfying the selection predicate through `signed_self`/`signed_group` alone (both those columns are populated by different code paths than `approved_time`, and the two are not enforced to be set together outside of the normal in-process flow captured by tests). Whenever `local_block_info.approved_time` is `None` for the *first* qualifying row that `check_parent_tenure_choice` looks at, the code explicitly falls back to treating the block as a "late-arriving proposal" (comment at line 256) and hard-codes `proposal_to_sortition = 0`.

Because `Duration::from_secs(0) < first_proposal_burn_block_timing` is true for any positive configured timing window, this branch **always** takes the "poorly timed, allowing the reorg" path (line 259-274) and marks the tenure as `superseded_tenures`, i.e. the tenure that is being reorged away — even if it was established minutes/hours ago and has one fully `GloballyAccepted` block that the whole signer set has already signed — is granted a **reorg permit**, and the signer's own past signature over that tenure's block is voided as a conflict (`record_superseded_tenure` → `mark_tenure_superseded`, consumed later by `reorg_permit_stands`/`get_signed_conflicts` in `handle_block_pre_commit`, section 5 of docs/signer-flows.md).

This breaks the "approved-parent vs canonical" equality the whole reorg-timing mechanism (`first_proposal_burn_block_timing`) exists to protect: the intended invariant is *only* tenures whose first block was signed "too close" to the next sortition (i.e., genuinely a race the incoming miner couldn't have RBF'd around) may be reorged. The `None`-timestamp fallback silently converts *any* row lacking a recorded `approved_time` (e.g., a stale DB entry, replayed insert, or any code path that only ever sets `signed_group`/`signed_self` without also stamping `approved_time`, which the schema does not enforce as an invariant) into "definitely poorly timed," collapsing the timing check to a no-op reorg-allow.

This is directly analogous in structure to the referenced October CMS bug class: a security decision (auth/session validity in the CVE; reorg permission here) is made using a fallback value substituted for a piece of state that should have been authoritative but, due to a gap in how that state is populated/derived, is silently treated as satisfying the security condition instead of correctly failing closed.

### Impact Explanation
If exploitable, this is a **Critical** issue per the rubric: it lets a signer sign a *conflicting/non-canonical replacement* for a tenure that should have been protected (more than `first_proposal_burn_block_timing` old, already globally accepted), because the guard that is supposed to distinguish "genuinely raced" tenures from "established" ones is bypassed by the `None`-timestamp default. That is exactly the "approved-parent vs canonical" equality break called out in the rules (a tenure treated as a legitimate reorg target when it is not), and it also removes the signer's own conflict protection (`mark_tenure_superseded`) over the tenure's block, undermining the one-per-height / conflict-guard machinery documented in section 5 of `docs/signer-flows.md`.

### Likelihood Explanation
I was **not able to fully confirm** a concrete, miner-only-triggerable path that leaves `approved_time` unset on the row `get_first_approved_block_in_tenure` returns, within the time available. The unit tests found (`stacks-signer/src/signerdb.rs:4056-4148`, `has_approved_block`/`has_signed_block`) explicitly exercise `approved_time = None` combined with `signed_self`/`signed_group` set (e.g. lines 4078, 4127-4134), which is the exact SQL predicate `get_first_approved_block_in_tenure` uses (`signed_self IS NOT NULL OR signed_group IS NOT NULL OR approved_time IS NOT NULL`) — confirming such rows are a reachable, tested DB state, but the tests do not exercise `check_parent_tenure_choice` against that specific combination to prove the reorg is granted. I could not trace, within the effort budget, whether normal signer control flow (`mark_locally_accepted`, `mark_globally_accepted`, `BlockInfo::from`) guarantees `approved_time` is always set whenever `signed_self`/`signed_group` is set, or whether there is a legitimate path (e.g., DB migration, a block record inserted via a different path than `handle_block_proposal`, or a restart/replay scenario) that produces the mismatched state a remote miner could induce without any signer cooperation.

### Recommendation
- Verify (or add an explicit invariant/test) that `approved_time` is always set whenever `signed_self` or `signed_group` is set, and add a migration/backfill or a runtime assertion to catch violations.
- In `check_parent_tenure_choice`, do not default the missing-timestamp case to `0` (i.e., "most poorly timed possible"). Instead, fail closed: treat a missing `approved_time` on an otherwise-signed block as unable to prove favorable timing, and refuse the reorg (return `Ok(false)`) unless a genuine timestamp can be produced.
- Add a regression test that inserts a `BlockInfo` with `signed_group` set but `approved_time = None` for the first block of a reorged tenure, and asserts `check_parent_tenure_choice` refuses the reorg (mirroring the existing `check_parent_tenure_choice_reorg_timing_bad`/`_ok` tests in `stacks-signer/src/chainstate/tests/v2.rs`).

### Proof of Concept
Not fully constructed — I could not confirm within this session a concrete sequence in which a single miner (plus normal gossip) causes a `BlockInfo` row with `signed_self`/`signed_group` set but `approved_time` unset to be the one returned by `get_first_approved_block_in_tenure` for an established tenure. A reproduction would need to:
1. Get tenure T's first block signed/globally accepted by the full signer set (giving it `signed_group`/`GloballyAccepted`), while ensuring the specific signer under test never itself calls `mark_pre_committed`/`mark_locally_accepted` for that block (so `approved_time` stays `NULL` on that signer's local row) — e.g. via a validation timeout, an outdated-peer signature fallback path (`store_and_process_block_signature`, `stacks-signer/src/v0/signer.rs:2462-2466`), or a restart between receiving the group signature and processing its own pre-commit.
2. Wait well past `first_proposal_burn_block_timing`.
3. Have a second miner win the next sortition and propose a tenure-change block whose `parent_tenure_id` reorgs tenure T.
4. Observe whether `check_parent_tenure_choice` incorrectly returns `true` (permitting the reorg) due to the `0`-substitution, using the `reorg_timing_testing` test harness pattern in `stacks-signer/src/chainstate/tests/v2.rs:340-380` as a template but forcing `approved_time = None` on the local block info instead of populating it via the normal test setup.

This step (constructing and running that exact PoC) requires code execution/tests, which is outside the scope of this read-only investigation; I flag it as the remaining validation needed to fully confirm exploitability versus a purely theoretical (unreachable-in-practice) code path.
