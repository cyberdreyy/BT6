### Title
Stale rejection weight is never reversed when a signer flips from Rejected to Accepted for the same block — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The Cocaine gem CVE-2013-4457 is a bug class about a value being "recorded" via one interpolation path and then not being correctly re-derived/invalidated when reused, leading to an unintended, unsanitized outcome. The structurally closest analog reachable by a single miner/signer plus gossip in this repo is in the node-side StackerDB listener: `total_weight_rejected` and `total_weight_approved` are accumulated independently, keyed off two different dedup sets (`gathered_signatures` vs `responded_signers`), so a signer that rejects and later accepts the same block contributes its weight to **both** tallies, and the stale rejection weight is never cleared.

### Finding Description
`StackerDBListener::run_stackerdb_listener_thread` (or its inline event loop) processes `BlockResponse` messages per block, tracked in `BlockStatus`:

- On `BlockResponse::Rejected`: weight is added to `block.total_weight_rejected` gated by `block.responded_signers.insert(slot_id)` (only added once, on first rejection). [1](#0-0) 

- On `BlockResponse::Accepted`: weight is added to `block.total_weight_approved` gated by a **different** set, `!block.gathered_signatures.contains_key(&slot_id)`, and `responded_signers.insert(slot_id)` is called unconditionally with no check on the return value. [2](#0-1) 

Because the two accumulators are gated by different sets and neither branch ever decrements the other counter, a signer that first sends a `Rejected` response (which the code base's own changelog and tests confirm is a supported, legitimate flow — a signer can "reconsider a block proposal it previously rejected" and later accept a re-proposed block) causes:
1. `total_weight_rejected` to be incremented once (on the reject).
2. `total_weight_approved` to be incremented later (on the accept), since `gathered_signatures` was still empty for that slot.
3. `total_weight_rejected` is **never decremented**, because the reject-count gate (`responded_signers`) is orthogonal to the accept-count gate (`gathered_signatures`).

The reverse order (accept-then-reject) is correctly protected, since the reject branch's gate (`responded_signers.insert`) will fail (already `true` from the earlier accept), so a signer cannot pad the rejection count after signing — but the accept-after-reject direction has no equivalent protection.

This breaks the "aggregated-weight vs verified-accepts" equality that `signer_coordinator.rs` relies on: `total_weight_rejected` is meant to represent the currently-live weight of signers still refusing the block, but it can permanently retain the weight of signers who have since accepted.

### Impact Explanation
`get_block_status` in `signer_coordinator.rs` treats the block as **irrecoverably rejected** once `total_weight_rejected + weight_threshold > total_weight` (i.e., >30% weight has ever rejected), causing the miner to abandon the proposal and retry with excluded transactions: [3](#0-2) 

Because `total_weight_rejected` can include stale weight from signers who have since flipped to `Accepted` for that exact same block, this stale weight can push the tally over the 30% blocking-minority threshold even though the *current* opinion of every signer would allow the block to reach 70% acceptance. This produces a liveness wedge: a block that is actually signable (or already collecting enough live signatures) is discarded by the miner/coordinator because of an accounting artifact, forcing the miner to abandon a canonical/valid tenure block and re-propose. This matches the allowed "liveness wedge" impact class (a valid block prevented from ever completing signing due to accounting rather than an actual lack of consensus).

It also means `total_weight_rejected + total_weight_approved` can exceed `total_weight` for a single outstanding block, i.e., the aggregated tallies no longer reflect a coherent partition of signer weight — the core invariant the threshold arithmetic depends on.

### Likelihood Explanation
This requires no majority, no other signer's key, and no StackerDB-sync trickery: it is triggered purely by the documented, supported behavior of a single signer legitimately changing its own response on the same `signer_signature_hash` (reject, then later accept a re-proposed/re-considered version of the same block) — a flow explicitly implemented and tested elsewhere in the signer (`signer_can_accept_rejected_block`, and the CHANGELOG entry "For some rejection reasons, a signer will reconsider a block proposal that it previously rejected"). Because the node-side listener's dedup sets for the two counters are not unified, this ordinary path deterministically leaves the rejection weight stale. A miner or gossip-observed signer flow alone is sufficient to reach this state; it does not require a majority of signers or any invalid signature.

### Recommendation
Use a single per-slot decision record (e.g. an enum `{Accepted, Rejected}` keyed by `slot_id`) instead of two independently-gated sets (`gathered_signatures` and `responded_signers`). When a signer's response transitions from `Rejected` to `Accepted` (or vice versa) for the same `signer_signature_hash`, subtract the previous contribution from the corresponding total before adding the new one, so `total_weight_rejected` and `total_weight_approved` always reflect only the *current* recorded decision of each signer for that block.

### Proof of Concept
1. Node broadcasts block proposal `B` (`signer_signature_hash = H`) to the signer set with `weight_threshold` at 70% and blocking minority at >30%.
2. Signer `S` (weight `w`, chosen so `w` alone is <30% of total but pushes `total_weight_rejected` close to/over the blocking-minority threshold together with pre-existing rejections) initially rejects `B` (e.g. due to a transient validation error) → `stackerdb_listener` increments `total_weight_rejected += w` via the `Rejected` branch (`responded_signers.insert(slot_id)` succeeds).
3. The condition that caused `S`'s rejection clears (or the block is reproposed and `S` reconsiders, per the supported "signer reconsider" logic in `stacks-signer`), and `S` now sends `Accepted` for the same `H`.
4. In the `Accepted` branch, `gathered_signatures` does not yet contain `S`'s `slot_id`, so `total_weight_approved += w` is applied — but `total_weight_rejected` is never decremented; it still includes `w` from step 2.
5. If other signers' rejections (from unrelated, legitimate reasons) bring `total_weight_rejected` (now inflated by `S`'s stale contribution) over `total_weight - weight_threshold`, `signer_coordinator::get_block_status` returns `NakamotoNodeError::SignersRejected` even though, counting only current opinions, the block might still be on track to reach the 70% acceptance threshold — demonstrating the wedge/inflated-tally condition purely from the documented single-signer reconsideration flow, requiring no majority collusion.

**Confidence caveat:** I was unable to view the `BlockStatus` struct definition and the `reset_rejections`/`update_idle_timestamp` helper bodies in full within this session (index truncation), so I could not fully verify whether some other code path resets `total_weight_rejected` on a later accept for the same slot. If such a reset exists elsewhere and I simply did not locate it, this finding would be mitigated; a Devin session with full file access would be needed to confirm this definitively. [4](#0-3)
