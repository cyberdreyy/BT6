### Title
Non-saturating multiplication in transaction fee burn/reward split - (File: runtime/src/bank/fee_distribution.rs)

### Summary
`Bank::calculate_reward_and_burn_fee_details()` computes the burned portion of a block's collected transaction fees using plain (non-checked, non-saturating) `u64` arithmetic: [1](#0-0) 

```rust
let burn = fee_details.transaction_fee * self.burn_percent() / 100;
```

This is the same bug class described in the Astaria report: a multiply-then-divide calculation performed with raw operators instead of the checked/saturating helpers used everywhere else in the fee/cost pipeline, creating a latent overflow risk if the multiplicand ever grows large enough.

### Finding Description
Every other fee- and cost-related computation in this codebase is deliberately written with `saturating_mul`/`saturating_add`/`checked_mul` to avoid silent overflow or panics, e.g.: [2](#0-1) [3](#0-2) [4](#0-3) 

`calculate_reward_and_burn_fee_details`, which sits directly downstream of these fee calculations and is invoked at the end of every slot in `distribute_transaction_fee_details()`, breaks this pattern by using plain `*`/`/` on `fee_details.transaction_fee`: [5](#0-4) 

`fee_details.transaction_fee` is a `CollectorFeeDetails` field accumulated across all transactions in a block (accumulation site is in `runtime/src/bank.rs`, which I was not able to fully inspect before running out of tool budget). If that accumulation uses `saturating_add` (consistent with the rest of the codebase's style), `transaction_fee` is capped at `u64::MAX`, and `u64::MAX * 50` would overflow a `u64` before the `/100` is applied. In debug builds this triggers a panic (arithmetic overflow); in release builds (the ones actually deployed) `*` wraps silently, producing an incorrect (and potentially much smaller, garbage) `burn` value that then flows into `deposit` via `transaction_fee.saturating_sub(burn)`.

### Impact Explanation
If overflow occurs, the code computes a corrupted `burn`/`deposit` split for the block's collected fees. Since `distribute_transaction_fee_details()` subtracts the (wrong) `total_burn` from `self.capitalization` and credits `deposit` to the leader's collector account, this can cause a state divergence in fee accounting/capitalization and misallocate lamports between "burned" and "collector-deposited" — a concrete state-mutation bug in consensus-critical fee bookkeeping, reachable purely from the accumulated fees of ordinary user transactions filling a block.

### Likelihood Explanation
Reaching `transaction_fee` values anywhere near `u64::MAX / 50` (~3.7×10^17 lamports, dwarfing total token supply) within one block is not plausible under current fee-structure limits, since per-transaction fees are bounded by signature counts and `lamports_per_signature`, and Solana's total lamport supply is far below this threshold. I was unable to confirm the exact accumulation bound in `runtime/src/bank.rs` due to running out of investigation budget, so I cannot rule out an unusual future fee-structure change (e.g., a large `lamports_per_signature` combined with many signature-verification instructions) pushing `transaction_fee` into the unsafe range. As it stands today, likelihood is low, but the code is a genuine latent defect relative to the rest of the codebase's saturating-arithmetic convention.

### Recommendation
Replace the raw operators with the same saturating/checked idiom used elsewhere in the fee pipeline, e.g.:
```rust
let burn = fee_details.transaction_fee.saturating_mul(self.burn_percent()) / 100;
```
or use `checked_mul` and fail safe (clamp to `u64::MAX` or treat as an internal invariant violation) to keep this function's behavior consistent with the "no raw arithmetic on validator-controlled or attacker-influenceable accumulators" convention followed throughout `fee/src/lib.rs`, `cost-model/src/cost_model.rs`, and `core/src/transaction_priority.rs`.

### Proof of Concept
Not independently reproducible without confirming the exact upper bound enforced on `CollectorFeeDetails::transaction_fee` accumulation in `runtime/src/bank.rs`; the report above documents the code-level divergence from the codebase's saturating-arithmetic convention rather than a demonstrated in-block overflow trigger.
