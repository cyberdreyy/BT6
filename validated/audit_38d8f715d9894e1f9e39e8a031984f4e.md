### Title
Per-epoch `isEpochInstant` flag misclassifies mixed instant/normal withdrawal claims, stranding the unfunded part and rebasing the epoch price — ([File: contracts/IdleCDOEpochQueue.sol](contracts/IdleCDOEpochQueue.sol))

### Summary
Analogous to the `retainERC4626` flag left stale when `_updateMultiDeposit` compacts failed entries out of a multi-deposit, `IdleCDOEpochQueue.processWithdrawRequests` reduces a whole epoch of queued withdrawals to a single boolean, `isEpochInstant[_epoch]`. When `IdleCDOEpochVariant.requestWithdraw` fulfills only part of the queued amount through the instant-withdraw path and routes the remainder through the normal `withdrawsRequests` ledger, `processWithdrawalClaims` later executes only one claim path, and the epoch price is rebased on the partial `_received` amount while the unfunded remainder is orphaned in the strategy.

### Finding Description
In `IdleCDOEpochQueue.processWithdrawRequests` (contracts/IdleCDOEpochQueue.sol:315-328) the queue calls `cdo.requestWithdraw(_pending, tranche)` for the aggregate pending amount and then records a single classification flag for the entire epoch:

```solidity
uint256 _underlyingsRequested = _cdo.requestWithdraw(_pending, tranche);
isEpochInstant[_epoch] = _strategy.instantWithdrawsRequests(address(this)) > _instantWithdraws;
```

The flag is set to `true` if *any* instant receipt was created, even when only a fraction of `_pending` became an instant request and the rest was recorded as a normal `withdrawsRequests` entry in `IdleCreditVault` (contracts/strategies/idle/IdleCreditVault.sol:292-293). This is the same bug class as the external report: a filtered/split set of items where a parallel flag is not realigned per item — here the flag is per-epoch while the underlying claim is split per-type.

Later, `processWithdrawalClaims` (IdleCDOEpochQueue.sol:347-351) picks exactly one path based on that boolean:

```solidity
if (isEpochInstant[_epoch]) {
  _cdo.claimInstantWithdrawRequest();
} else {
  _cdo.claimWithdrawRequest();
}
```

In a mixed epoch:
- `claimInstantWithdrawRequest` burns only `instantWithdrawsRequests[queue]` and transfers only the funded instant amount (IdleCreditVault.sol:387-392). The normal portion sitting in `withdrawsRequests[queue]` / `pendingWithdraws` is never claimed.
- `_received < _pending`, so `epochWithdrawPrice[_epoch]` is rebased downward (IdleCDOEpochQueue.sol:355-357), permanently underpaying every user who claimed against that epoch.
- `epochPendingClaims[_epoch]` and `pendingClaims` are cleared, so the orphaned normal receipt is invisible to the queue. On a *subsequent* non-instant epoch, `processWithdrawalClaims` calls `claimWithdrawRequest`, which sweeps **all** funded receipts for the queue address — including the leftover from the earlier epoch — and credits the proceeds to the later epoch's price, overpaying later claimants at the expense of earlier ones.

### Impact Explanation
Direct misallocation of user funds: early-epoch withdrawers receive a rebased (lower) price because part of their claim was never collected, while the orphaned strategy-side receipt is later swept into a different epoch's claim, paying users who never owned that receipt. Broken invariant: one receipt one payout / fair epoch pricing — the same class of harm as the `retainERC4626` misalignment (users get the wrong claim semantics for their position), here producing quantifiable underpayment of earlier withdrawers and overpayment of later ones.

### Likelihood Explanation
Requires instant withdrawals to be enabled (`setInstantWithdrawParams`) and a `stopEpoch` that triggers instant fulfillment for only part of the queued amount — i.e., the APR/liquidity conditions that produce a mixed instant+normal epoch, a scenario the codebase itself exercises (`testProcessWithdrawalClaimsMixedInstantAndNormalEpoch`). No privileged attacker is needed; any queue user's request contributes to the mixed epoch. The sequence is driven by honest manager calls (`processWithdrawRequests`, `processWithdrawalClaims`), so it is timing-dependent rather than attacker-steerable, which lowers likelihood relative to a pure unprivileged exploit.

### Recommendation
Replace the single `isEpochInstant[_epoch]` boolean with per-type claim tracking. For each processed epoch, record both the instant portion and the normal portion (e.g., `epochInstantClaims[_epoch]` and `epochNormalClaims[_epoch]`), and in `processWithdrawalClaims` invoke `claimInstantWithdrawRequest` and/or `claimWithdrawRequest` according to which ledgers hold a balance for the queue — mirroring the report's fix of constructing a realigned parallel array instead of reusing a stale flag.

### Proof of Concept
A Foundry fork test would: enable instant withdrawals on the standard epoch variant; queue AA withdrawals during epoch N; stop the epoch under conditions where the borrower/liquidity covers only part of the queue instantly (mixed instant+normal); call `processWithdrawRequests` (flag set `true` from the instant delta); process claims — `claimInstantWithdrawRequest` collects only the instant part, `_received < epochPendingClaims[epoch]`, price rebased down; user `claimWithdrawRequest(epoch)` pays less than `trancheAmount * epochPrice`; the residual `withdrawsRequests[queue]` remains in `IdleCreditVault` and is swept into a later epoch's `processWithdrawalClaims`.

**Caveat:** I could not read `IdleCDOEpochVariant.requestWithdraw`/`getInstantWithdrawFunds` within the available iterations to confirm the exact split conditions; the finding hinges on a single `requestWithdraw` call being able to create both an instant receipt and a normal receipt for the same `_pending` amount, which the existing mixed-epoch test strongly suggests but which should be verified before reporting.
