### Title
Dust queued withdrawal permanently reverts `processWithdrawRequests`, freezing all same-epoch queued withdrawals - ([File: contracts/IdleCDOEpochQueue.sol](contracts/IdleCDOEpochQueue.sol))

### Summary
Analogous to CVE-2020-5416 (a single specially-crafted request knocking a router out of the serving pool), a single dust `requestWithdraw` in `IdleCDOEpochQueue` makes the manager-only `processWithdrawRequests` for that epoch revert unconditionally, knocking the entire batch of queued withdrawals out of processing.

### Finding Description
`processWithdrawRequests` aggregates every queued withdrawal for the current epoch into one call to `IdleCDOEpochVariant.requestWithdraw(_pending, tranche)`, then derives the epoch price as:

```solidity
uint256 _underlyingsRequested = _cdo.requestWithdraw(_pending, tranche);
uint256 _epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending;
if (_epochPrice == 0) {
  revert Is0();
}
``` [1](#0-0) 

In `IdleCDOEpochVariant.requestWithdraw`, a 1-wei tranche amount yields `_underlyings = _trancheToUnderlyings(1, _tranche) = 1 * tranchePrice / 1e18`, which rounds to 0 whenever `tranchePrice < 1e18` (i.e., any sub-peg tranche, e.g., BB after a BB-first loss epoch). With `_underlyings == 0`, `IdleCreditVault.requestWithdraw` returns early and the CDO burns the dust tranche, returning `_underlyingsRequested == 0`. The queue then hits `revert Is0()` and the whole `processWithdrawRequests` transaction reverts. [2](#0-1) [3](#0-2) 

An attacker (any KYC-passed wallet holding ≥1 wei of the tranche token) calls `queue.requestWithdraw(1)` while the epoch is running. From then on, every `processWithdrawRequests()` call for that epoch reverts, because the attacker's dust is mixed into the aggregate `_pending` and there is no privileged or third-party way to remove a specific user's queued request — `deleteWithdrawRequest` only clears `msg.sender`'s own entry and `processWithdrawRequests` is `onlyOwnerOrManager`. [4](#0-3) [5](#0-4) [6](#0-5) 

Existing guards do not stop it: `requestWithdraw` has no minimum amount, `_checkAllowed` only enforces epoch-running + Keyring allowlist (which the attacker satisfies), and the `Is0` revert was added to catch zero prices but has the side effect of bricking the whole batch. The related `isEpochWithdrawZero` fix only covers a zero *payout* after successful processing, not the zero *request* case. [7](#0-6) 

### Impact Explanation
Temporary freezing of funds: all honest users' queued withdrawal requests for the targeted epoch cannot be converted into funded claims. The epoch's `epochPendingWithdrawals` can never be processed while the dust request remains, so no `epochWithdrawPrice`/`epochPendingClaims` is set and `claimWithdrawRequest` keeps reverting (`epochWithdrawPrice[epoch] == 0` path / `NotAllowed`). Victims can individually recover only by calling `deleteWithdrawRequest` (getting their tranche tokens back and re-queueing next epoch), but the attacker can repeat the attack every epoch for ~1 wei of a sub-peg tranche, indefinitely deferring withdrawals through the queue. Quantified worst case: 100% of the epoch's queued withdrawal volume is delayed for at least one full epoch cycle, repeatable at near-zero cost.

### Likelihood Explanation
Requires a tranche price below 1e18, which is the normal state of the BB tranche after any realized loss (BB-first waterfall) or of AA after deep losses — precisely the stressed conditions under which withdrawal demand spikes and the queue is most used. The attack costs the attacker a single wei of tranche token plus gas, needs only ordinary KYC-gated queue access, and no privileged action can clear the malicious request once queued. Medium likelihood, medium impact — consistent with the Medium rating of the source advisory.

### Recommendation
- Enforce a minimum `requestWithdraw` amount in `IdleCDOEpochQueue` (e.g., `amount >= MIN_REQUEST`) so a dust request cannot round `_underlyingsRequested` to 0.
- Alternatively, in `processWithdrawRequests`, treat a zero `_underlyingsRequested` gracefully: set `isEpochWithdrawZero[_epoch]`, clear `epochPendingWithdrawals`, and let users delete/reclaim their tranches, instead of reverting.
- Add a privileged sweep (or make `deleteWithdrawRequest` callable by owner/manager for any user) so a poisoned epoch can be unblocked without the attacker's cooperation.

// test/foundry/IdleCDOEpochQueue.t.sol style
function testPocDustWithdrawBlocksEpochProcessing() external {
    _stopCurrentEpoch();
    // epoch 1 running after startEpoch
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // --- drive BB price below 1e18 via a loss epoch (stopEpochWithDuration with _lossAmount) ---
    // ... realize a loss so tranchePrice(BB) < ONE_TRANCHE ...

    // Victim queues a normal withdrawal
    uint256 victimTranches = 100e18;
    _requestWithdrawWithUser(victim, victimTranches);

    // Attacker queues a 1-wei withdrawal while epoch is running
    deal(address(BBtranche), attacker, 1);
    vm.startPrank(attacker);
    BBtranche.approve(address(queueBB), 1);
    queueBB.requestWithdraw(1);
    vm.stopPrank();

    _stopCurrentEpoch(); // enter buffer of next epoch

    // Manager cannot process the epoch's withdrawals — always reverts
    vm.expectRevert(abi.encodeWithSelector(Is0.selector));
    vm.prank(manager);
    queueBB.processWithdrawRequests();

    // Victim's withdrawal is stuck; only self-service deleteWithdrawRequest recovers tranche tokens
    vm.prank(victim);
    queueBB.claimWithdrawRequest(strategy.epochNumber()); // reverts NotAllowed
}
```

  function deleteWithdrawRequest(uint256 _requestEpoch) external {
    // if the epoch withdraw price is already set, withdrawal requests were already processed so
    // the withdraw request can't be deleted. Withdraw requests can be deleted even if the epoch is running
    _checkNotAllowed(epochWithdrawPrice[_requestEpoch] != 0 || isEpochWithdrawZero[_requestEpoch]);

    uint256 amount = userWithdrawalsEpochs[msg.sender][_requestEpoch];
    if (amount == 0) {
      return;
    }
    // reset user withdraw request for the epoch
    userWithdrawalsEpochs[msg.sender][_requestEpoch] = 0;
    // update pending withdraw requests
    epochPendingWithdrawals[_requestEpoch] -= amount;
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, amount);
  }
