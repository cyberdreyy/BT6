### Title
`simulateTransaction` RPC call can abort the validator via `assert!(self.is_frozen())` in `Bank::simulate_transaction` when the request resolves to an unfrozen working bank - (`rpc/src/rpc.rs`, `runtime/src/bank.rs`)

### Summary
`rpc::simulate_transaction` resolves the target bank via `meta.get_bank_with_config(RpcContextConfig { commitment, min_context_slot })`, which for the default/`processed` commitment level resolves to the current working bank via `JsonRpcRequestProcessor::bank(commitment)`. That bank is then passed unconditionally into `Bank::simulate_transaction`, which contains a hard `assert!(self.is_frozen(), "simulation bank must be frozen")` [1](#0-0) . If the bank returned to the RPC handler has not yet been frozen (i.e., it is the actively-building tip/working bank), this assertion fires and aborts the validator process on a single, unprivileged JSON-RPC request.

### Finding Description
The RPC entrypoint decodes the transaction and fetches the bank purely based on `RpcContextConfig` (commitment + `min_context_slot`), with no check that the returned bank is frozen: [2](#0-1) 

`get_bank_with_config` only validates `min_context_slot`, not freeze state, before returning the bank to the caller: [3](#0-2) 

`Bank::simulate_transaction` is called on that bank unconditionally and enforces the frozen invariant via a hard `assert!`, which is a process-aborting panic in production builds rather than a recoverable `Result`/JSON-RPC error: [1](#0-0) 

Critically, the repository's own test suite already demonstrates and names this exact failure mode: a `RpcHandler` is started, the working bank is deliberately left unfrozen, and a `simulateTransaction` request is issued through `io.handle_request_sync`, with the test explicitly annotated `#[should_panic(expected = "simulation bank must be frozen")]`: [4](#0-3) 

This confirms the code path `rpc.simulate_transaction -> meta.get_bank_with_config -> bank.simulate_transaction -> assert!(self.is_frozen())` is directly reachable from the JSON-RPC layer with no guard against an unfrozen bank, and that hitting it results in a Rust panic rather than a `Result::Err`. All other RPC methods that use `get_bank_with_config` (`getBalance`, `getSlot`, `getAccountInfo`, etc.) do not touch `is_frozen()`-asserting code, so `simulateTransaction` is the specific RPC surface where this unchecked precondition becomes reachable and dangerous.

### Impact Explanation
A successful trigger causes a Rust `assert!` panic inside the JSON-RPC request-handling thread. Depending on panic-handling configuration (`panic = "abort"` / default panic hook aborting the process for validator binaries), this can abort the entire validator process from a single unprivileged JSON-RPC call — a denial-of-service / crash impact matching the Agave bounty category for a validator crash triggered by a single client request, which is explicitly in-scope per the rules (`single unprivileged JSON-RPC request`, no need for repeated calls, no leader/gossip/staked control required).

### Likelihood Explanation
The exploitability hinges entirely on whether, in a running validator, the bank returned by `JsonRpcRequestProcessor::bank(commitment)` for the default (`processed`) commitment level can ever be an unfrozen bank (i.e., the actively-building "working bank" of the current fork tip, as opposed to a bank that is only exposed to RPC once frozen). I was not able to retrieve and fully verify the implementation of `bank(commitment)` (specifically its `Processed` branch, e.g., whether it calls `bank_forks.working_bank()` directly) before running out of tool iterations, so I cannot conclusively confirm production reachability from the code alone. However:
- The existing in-repo test explicitly names and reproduces this exact panic via the public JSON-RPC entrypoint (`io.handle_request_sync`) with a bank that has not called `freeze()`, which is strong evidence that no guard currently exists between "how the RPC layer selects a bank for a given commitment" and "what `Bank::simulate_transaction` requires."
- If `bank(Some(CommitmentConfig::processed()))` (or the default when no commitment is specified) can return a bank prior to `ReplayStage`/`PohRecorder` freezing it (which is the case for the currently-building leader/tip bank in many bank-selection implementations), then any unprivileged client sending a single `simulateTransaction` request during that narrow window would trigger the abort — no special privileges, timing precision beyond "ask while a bank is mid-build," or elevated access required.

Given this uncertainty in the production bank-selection code (unable to verify within the given iterations), likelihood should be treated as plausible-but-unconfirmed at the "does `bank(commitment)` ever return an unfrozen bank in production" step; the panic path itself, once such a bank is obtained, is unconditionally reachable and unguarded.

### Recommendation
Add an explicit frozen-bank check in `simulate_transaction`'s RPC handler (or convert `Bank::simulate_transaction`'s `assert!` into an `Err`/`Result` path) before invoking `bank.simulate_transaction`, e.g., return `RpcCustomError` (analogous to `MinContextSlotNotReached`) when `!bank.is_frozen()`, and/or ensure `get_bank_with_config` never returns an unfrozen bank for `processed`/default commitment.

### Proof of Concept
The repository already contains a self-documenting reproduction of this exact bug as a unit test (currently written as `#[should_panic]`, i.e. asserting the crash is "expected" rather than being fixed): [4](#0-3) 

To validate as a security regression test, this test should be rewritten to assert the RPC call returns a JSON-RPC error response (no panic) instead of `#[should_panic]`:
```rust
#[test]
fn test_rpc_simulate_transaction_no_panic_on_unfrozen_bank() {
    let rpc = RpcHandler::start();
    let bank = rpc.working_bank();
    let recent_blockhash = bank.confirmed_last_blockhash();
    let RpcHandler { meta, io, mint_keypair, .. } = rpc;

    let bob_pubkey = Pubkey::new_unique();
    let tx = system_transaction::transfer(&mint_keypair, &bob_pubkey, 1234, recent_blockhash);
    let tx_serialized_encoded = bs58::encode(wincode::serialize(&tx).unwrap()).into_string();

    assert!(!bank.is_frozen());

    let req = format!(
        r#"{{"jsonrpc":"2.0","id":1,"method":"simulateTransaction","params":["{tx_serialized_encoded}", {{"sigVerify": true}}]}}"#,
    );

    // Should return a JSON-RPC error, not panic/abort the process
    let res = io.handle_request_sync(&req, meta);
    assert!(res.is_some());
    let json: serde_json::Value = serde_json::from_str(&res.unwrap()).unwrap();
    assert!(json.get("error").is_some(), "expected JSON-RPC error, got {json:?}");
}
```

impl JsonRpcRequestProcessor {
    fn get_bank_with_config(&self, config: RpcContextConfig) -> Result<Arc<Bank>> {
        let RpcContextConfig {
            commitment,
            min_context_slot,
        } = config;
        let bank = self.bank(commitment);
        if let Some(min_context_slot) = min_context_slot
            && bank.slot() < min_context_slot
        {
            return Err(RpcCustomError::MinContextSlotNotReached {
                context_slot: bank.slot(),
            }
            .into());
        }
        Ok(bank)
    }

            &self,
            meta: Self::Metadata,
            data: String,
            config: Option<RpcSimulateTransactionConfig>,
        ) -> Result<RpcResponse<RpcSimulateTransactionResult>> {
            debug!("simulate_transaction rpc request received");
            let RpcSimulateTransactionConfig {
                sig_verify,
                replace_recent_blockhash,
                commitment,
                encoding,
                accounts: config_accounts,
                min_context_slot,
                inner_instructions: enable_cpi_recording,
            } = config.unwrap_or_default();
            let tx_encoding = encoding.unwrap_or(UiTransactionEncoding::Base58);
            let binary_encoding = tx_encoding.into_binary_encoding().ok_or_else(|| {
                Error::invalid_params(format!(
                    "unsupported encoding: {tx_encoding}. Supported encodings: base58, base64"
                ))
            })?;
            let (_, mut unsanitized_tx) =
                decode_and_deserialize::<VersionedTransaction>(data, binary_encoding)?;

            let bank = &*meta.get_bank_with_config(RpcContextConfig {
                commitment,
                min_context_slot,
            })?;
            let mut blockhash: Option<RpcBlockhash> = None;
            if replace_recent_blockhash {
                if sig_verify {
                    return Err(Error::invalid_params(
                        "sigVerify may not be used with replaceRecentBlockhash",
                    ));
                }
                let recent_blockhash = bank.last_blockhash();
                unsanitized_tx
                    .message
                    .set_recent_blockhash(recent_blockhash);
                let last_valid_block_height = bank
                    .get_blockhash_last_valid_block_height(&recent_blockhash)
                    .expect("bank blockhash queue should contain blockhash");
                blockhash.replace(RpcBlockhash {
                    blockhash: recent_blockhash.to_string(),
                    last_valid_block_height,
                });
            }

            let transaction =
                sanitize_transaction(unsanitized_tx, bank, bank.get_reserved_account_keys())?;

            let verification_error = if sig_verify {
                transaction.verify().err()
            } else {
                None
            };

            let simulation_result = if let Some(err) = verification_error {
                TransactionSimulationResult::new_error(err)
            } else {
                bank.simulate_transaction(&transaction, enable_cpi_recording)
            };
