The `ProvisionerV2` async request flow contains the exact analog of the reported pattern: escrow refunds are routed to the request's `receiver` field instead of the original depositor/requester who supplied the escrowed tokens.

## Root cause

Async `requestDeposit`/`requestRedeem` validate the `receiver` parameter only for non-zero address — they do **not** require `receiver == msg.sender` or receiver approval (unlike the sync `deposit`/`mint`/`redeem`/`withdraw` paths, which call `_requireValidReceiver`): [1](#0-0) 

So an ordinary user can create a request with an arbitrary `receiver` while `msg.sender` supplies the escrowed tokens via `safeTransferFrom`: [2](#0-1) 

When the request is cancelled (`cancelRequest`) or refunded after expiry (`refundRequest`), the refund routine `_clearHashAndTransferRefund` is called with `requester = msg.sender`/`request.user` and passes it into `_transferWithFallback` alongside `request.receiver`: [3](#0-2) 

`_transferWithFallback` tries to send the escrowed principal to `receiver` **first**, and only falls back to the original `requester` if that transfer reverts: [4](#0-3) 

This is used identically by `cancelRequest` (self-cancel path) and by `_solveRequestDirect`'s expired-refund branch: [5](#0-4) [6](#0-5) 

## Why this matches the reported pattern

The disclosed Dinari bug: escrowed tokens taken from the requester on order creation are returned to `orderRequest.recipient` on cancellation instead of the party that funded the escrow, risking permanent loss if `recipient` is an address that cannot use/forward the funds. Here, the same broken invariant exists: a depositor/redeemer escrows funds under their own `msg.sender`, but the refund/cancellation logic preferentially pays out to `request.receiver` — an arbitrary address the depositor merely names for the *successful-solve* case — rather than to the depositor themselves.

Concretely: Alice calls `requestDeposit(token, tokensIn, minUnitsOut, solverTip, deadline, maxPriceAge, isFixedPrice, receiver=Bob)`. Tokens move from Alice to the Provisioner as escrow. If Alice self-cancels (deposit cancellations enabled) or the request simply expires and anyone calls `refundRequest`, `_transferWithFallback` sends the refunded principal to Bob (since `Bob != Alice` and a plain ERC20 transfer to Bob succeeds), not back to Alice. If Bob is unaware, unwilling, or a contract without a sweep/forward mechanism, Alice's principal is effectively lost — no privileged role, oracle, or guardian action is required; this is a pure ordinary-user transaction sequence exploitable by the depositor's own careless/malicious `receiver` choice, or exploitable against a depositor if a UI/aggregator pre-fills a third-party receiver.

## Assessment

This is a legitimate, function-exact analog on the deployed `ProvisionerV2` async deposit/redeem/cancel/refund path — same root cause (wrong recipient on escrow return), same broken invariant (escrow must return to whoever posted it, not to the intended output receiver), reachable by an ordinary user with no privileged actor involved.
