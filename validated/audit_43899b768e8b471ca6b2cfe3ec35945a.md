### Title
Unbounded response memory allocation in `getMultipleAccounts` via base64/jsonParsed encoding of max-size accounts, capped only by account count - ([File: rpc/src/rpc.rs])

### Summary
`get_multiple_accounts` enforces only a count limit (`MAX_MULTIPLE_ACCOUNTS`) on the number of pubkeys requested, but `encode_account`/`encode_ui_account` impose no data-size limit for `Base64`, `Base64Zstd`, or `JsonParsed` encodings — only `Base58`/`Binary` are capped by `MAX_BASE58_BYTES` (128 bytes). An attacker who grows N ≤ `MAX_MULTIPLE_ACCOUNTS` accounts to the maximum permitted account size and requests them in one `getMultipleAccounts` call forces the validator to allocate and hold in memory the full raw data plus base64-encoded copies for all accounts simultaneously, scaling cost with attacker-controlled on-chain data rather than a fixed per-request bound.

### Finding Description
The RPC entrypoint `AccountsDataImpl::get_multiple_accounts` only checks pubkey-count against `max_multiple_accounts` (defaulting to `MAX_MULTIPLE_ACCOUNTS`), with no check on aggregate or per-account data size [1](#0-0) . It then calls `JsonRpcRequestProcessor::get_multiple_accounts`, which loops over every pubkey and spawns a blocking task calling `get_encoded_account` for each one, accumulating all results into a single `Vec` before returning [2](#0-1) .

The actual encode step, `encode_account`, only rejects requests when the requested encoding is `Binary`/`Base58` and the sliced data exceeds `MAX_BASE58_BYTES` (128 bytes); for `Base64`, `Base64Zstd`, and `JsonParsed` it unconditionally calls `encode_ui_account` with no size guard [3](#0-2) . Inside `encode_ui_account`, the `Base64` branch performs `BASE64_STANDARD.encode(slice_data(account.data(), ...))` on the full account data, and the `JsonParsed` branch falls back to the same unbounded base64 path whenever parsing fails [4](#0-3) . Since the RPC's default encoding for `getMultipleAccounts` is `Base64` (not `Base58`), the `MAX_BASE58_BYTES` guard never applies in the default/attacker-chosen path [5](#0-4) .

Consequently, the only limits governing this call are: (1) pubkey count, via `MAX_MULTIPLE_ACCOUNTS`/`rpc_max_multiple_accounts` [6](#0-5) , and (2) whatever cap the runtime enforces on individual account data size (the program-level max account size, commonly 10MiB). Neither of these bounds the aggregate memory footprint of the response: raw account data (up to N × 10MB), the base64-encoded copies (~1.33× that), and the final serialized JSON string are all built and held simultaneously in the RPC worker before being written to the response.

### Impact Explanation
This matches the "unbounded cost for a single low-rate call" category: a single, non-privileged `getMultipleAccounts` request can force the validator's JSON-RPC service to allocate memory proportional to attacker-controlled on-chain state (N accounts × up to 10MB each, plus ~1.33× base64 encoding overhead and JSON serialization overhead), rather than a fixed, documented per-request cost. Repeated at the permitted rate (one call per `CLUSTER_SLOT_TIME_TARGET / 2`), this can degrade RPC node memory/availability without requiring more than one client or elevated privileges.

### Likelihood Explanation
Feasible for any unprivileged actor with enough funds to create/resize `MAX_MULTIPLE_ACCOUNTS` accounts to max size (a one-time setup cost of rent/fees, not privileged access), after which every subsequent `getMultipleAccounts([...])` call against those same accounts reproduces the large allocation. It requires no validator/leader control, no mocked paths, and no more than one call per node, satisfying the scope's rate constraint.

### Recommendation
Add an aggregate/per-account data-size guard in `encode_account`/`get_multiple_accounts` analogous to the existing `MAX_BASE58_BYTES` check for `Base58`/`Binary`, applied to `Base64`, `Base64Zstd`, and `JsonParsed` encodings as well (e.g., cap total requested bytes across all N accounts, or require `dataSlice` when large accounts are requested in bulk), so the per-call memory cost is bounded independent of attacker-controlled account size.

### Proof of Concept
Rust integration test sketch (in `rpc/src/rpc.rs` test module, using `RpcHandler`):
```rust
#[test]
fn test_get_multiple_accounts_unbounded_memory() {
    let rpc = RpcHandler::start();
    let bank = rpc.working_bank();
    let max_multiple_accounts = MAX_MULTIPLE_ACCOUNTS; // e.g. 100
    let max_account_size = 10 * 1024 * 1024; // 10MB, program-enforced max

    let mut pubkeys = Vec::new();
    for _ in 0..max_multiple_accounts {
        let pubkey = Pubkey::new_unique();
        let data = vec![0u8; max_account_size];
        let account = AccountSharedData::create_from_existing_shared_data(
            42, Arc::new(data), Pubkey::default(), false, 0,
        );
        bank.store_account(&pubkey, &account);
        pubkeys.push(pubkey.to_string());
    }

    let request = create_test_request(
        "getMultipleAccounts",
        Some(json!([pubkeys, {"encoding": "base64"}])),
    );
    // Measure peak resident memory / allocator stats around this call.
    let result: RpcResponse<Value> = parse_success_result(rpc.handle_request_sync(request));
    // Assert: no documented bound exists limiting the aggregate response
    // size to less than max_multiple_accounts * max_account_size * 1.33,
    // demonstrating the request cost scales with attacker data, not a
    // fixed per-request limit.
    assert!(result.value.as_array().unwrap().len() == max_multiple_accounts);
}
```
Expected observation: peak allocation during `encode_account`/`encode_ui_account` scales linearly with `max_multiple_accounts * max_account_size`, with no enforced ceiling comparable to `MAX_BASE58_BYTES` for the `Base64`/`JsonParsed` paths, confirming the missing bound.

        &self,
        pubkeys: Vec<Pubkey>,
        config: Option<RpcAccountInfoConfig>,
    ) -> Result<RpcResponse<Vec<Option<UiAccount>>>> {
        let RpcAccountInfoConfig {
            encoding,
            data_slice,
            commitment,
            min_context_slot,
        } = config.unwrap_or_default();
        let bank = self.get_bank_with_config(RpcContextConfig {
            commitment,
            min_context_slot,
        })?;
        let encoding = encoding.unwrap_or(UiAccountEncoding::Base64);

        let mut accounts = Vec::with_capacity(pubkeys.len());
        for pubkey in pubkeys {
            let bank = Arc::clone(&bank);
            accounts.push(
                self.runtime
                    .spawn_blocking(move || {
                        get_encoded_account(&bank, &pubkey, encoding, data_slice, None)
                    })
                    .await
                    .expect("rpc: get_encoded_account panicked")?,
            );
        }
        Ok(new_response(&bank, accounts))
    }

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
