I've confirmed the mechanics of this wedge with sufficient evidence. Here is the finding.

### Title
Late "outdated-peer" acceptances after self-signing are never re-tallied toward the group threshold, permanently wedging block finalization - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`store_and_process_block_signature` re-derives the group signature threshold only at the moment it is called without being diverted. Once a signer has already signed a block (`signed_self` is set), every subsequent `BlockResponse::Accepted` from a peer who has not first broadcast an explicit `BlockPreCommit` for that block is silently diverted into `handle_block_pre_commit`, which — for an already-signed block — does nothing and returns. The peer's signature is still written to `block_signatures`, but the code path that recomputes `total_signature_weight` against `compute_voting_weight_threshold` and calls `mark_locally_accepted(group)` / `broadcast_signed_block` is never re-entered. A block can therefore sit with enough recorded signature weight in the local DB to cross the 70% threshold, yet this signer never recognizes it and never pushes it to its node.

### Finding Description
In `store_and_process_block_signature` [1](#0-0) , every incoming `BlockAccepted` signature is first stored via `add_block_signature`. If the sender is not this signer itself and has not yet sent a `BlockPreCommit` for the block (`has_committed` false), the message is rerouted to `handle_block_pre_commit` and the function `return`s immediately — it never reaches the weight-threshold computation below.

`handle_block_pre_commit` [2](#0-1)  records the pre-commit and computes the *pre-commit* threshold, but as soon as it sees `block_info.signed_self.is_some()` it logs "Doing nothing..." and returns without touching `signed_group` or re-checking the *signature* weight at all:
```
if block_info.signed_self.is_some() {
    debug!("... Received pre-commit for a block that we have already signed. Doing nothing...");
    return;
}
``` [3](#0-2) 

The only place that recomputes `total_signature_weight` and can trigger `mark_locally_accepted(true)` / `broadcast_signed_block` is the non-diverted tail of `store_and_process_block_signature` [4](#0-3) . That tail is reached only when `signer_address == &self.stacks_address` (i.e. the signer's own signature) or when the sender already has a recorded pre-commit. The one guaranteed occurrence of the non-diverted path is exactly when the signer signs itself, via `handle_block_pre_commit`'s SIGN branch calling back into `handle_block_signature`:
```
self.handle_block_signature(stacks_client, sortition_state, &accepted);
``` [5](#0-4) 

That single self-signing moment is the *only* checkpoint at which this signer will ever compute whether the aggregated signature weight (self + whatever peer signatures happen to already be stored) meets the 70% threshold. If, at that instant, the recorded weight is still short of threshold, the function returns with `signed_group` unset:
```
if min_weight > total_signature_weight {
    info!("... have not yet reached the acceptance threshold.");
    return;
}
``` [6](#0-5) 

From then on, any further peer acceptance that arrives from a signer who has not first broadcast a `BlockPreCommit` for this specific block hash is diverted into `handle_block_pre_commit`, which does nothing because `signed_self` is already set. The comment in the docs even documents the intended, narrower purpose of this fallback ("that peer's weight still counts toward the threshold that produces _our_ signature") [7](#0-6)  — it is designed to help a signer decide whether to sign, not to keep re-checking the group threshold after it already has. There is no other trigger in the codebase that re-derives `total_signature_weight` for a block once `signed_self` is set and `signed_group` is not: a duplicate delivery of the same address's signature is short-circuited earlier by `add_block_signature` returning `false` [8](#0-7) , and rejections do not affect it.

The equality this breaks is: "aggregated signature weight recorded in `signerdb` ≥ threshold" should imply "signer marks the block `GloballyAccepted`-eligible and pushes it (`broadcast_signed_block`/`handle_post_block`) to its node." Because the recheck is gated behind a one-time diversion decision keyed on whether the *sender* had previously broadcast an explicit pre-commit, a benign version-skew (some signers still on pre-`BlockPreCommit` software) or a single non-cooperative signer that always omits its pre-commit broadcast while still sending its final acceptance can cause this signer to never observe that consensus was in fact reached, even though the bytes needed to prove it are already sitting in its own `block_signatures` table.

### Impact Explanation
This is a liveness wedge on a single signer's ability to recognize and act on already-achieved consensus: the affected signer never calls `mark_locally_accepted(true)`/`broadcast_signed_block` for a block that (per its own stored signatures) has already crossed the 70% threshold, so it will not push the block to its node. If the timing/version-skew condition is common across the fleet (e.g. many signers on the older, no-pre-commit software, or a griefing signer that consistently skips pre-commit broadcast while still signing), no signer independently notices the threshold was crossed, stalling that block/tenure indefinitely. This matches the "High" bucket: a signer effectively wedged into never recognizing/acting on a block it has already signed, requiring no majority collusion — only one non-cooperating (or out-of-date) peer's ordering relative to this signer's own signing moment.

### Likelihood Explanation
The trigger requires only ordinary gossip: any signer's `BlockResponse::Accepted` that reaches a peer after that peer has already signed the same block, without a preceding `BlockPreCommit` from the sender for that exact hash. This condition arises naturally from: (a) mixed-version fleets where older/legacy signers only ever send `BlockResponse::Accepted` and never `BlockPreCommit` (explicitly the scenario the code comment anticipates), or (b) simple message reordering/latency where a `BlockPreCommit` and `BlockResponse::Accepted` race and the accept is processed first for a block this signer already signed. No majority, no private key material, and no elevated access are required — a lone slow/old/adversarial signer can produce this ordering via normal StackerDB gossip.

### Recommendation
In `store_and_process_block_signature`, do not unconditionally divert-and-return when the block is already `signed_self`. After `add_block_signature` succeeds, always recompute `total_signature_weight` (including any signature that also needs to be recorded as a pre-commit for bookkeeping) and check it against `compute_voting_weight_threshold` before returning, regardless of whether the sender's pre-commit was previously observed. Equivalently, `handle_block_pre_commit`'s early return for `signed_self.is_some()` should first re-check the accumulated signature weight (or delegate to the exact code path that does) instead of unconditionally doing nothing.

### Proof of Concept
1. Signer S receives a block proposal, validates it, pre-commits, and — once its local pre-commit weight threshold is reached — signs it (`signed_self` set), per the SIGN branch in `handle_block_pre_commit` [9](#0-8) . At this moment `store_and_process_block_signature` checks `total_signature_weight` and finds it still below the 70% threshold (only S's own signature plus whichever few peers had already both pre-committed and signed are counted), so it returns without setting `signed_group` [6](#0-5) .
2. A peer P (either running legacy pre-`BlockPreCommit` signer software, or simply slow/adversarial about broadcasting its `BlockPreCommit`) sends `BlockResponse::Accepted` for the same block to S, without S ever having received a `BlockPreCommit` from P for that hash.
3. S's `handle_block_signature` → `store_and_process_block_signature` stores P's signature via `add_block_signature` (now enough combined weight exists to cross 70%), but since `signer_address != self.stacks_address` and `has_committed(block_hash, P) == false`, it diverts to `handle_block_pre_commit` and returns [10](#0-9) .
4. `handle_block_pre_commit` sees `block_info.signed_self.is_some()` and returns immediately without ever recomputing `total_signature_weight` [3](#0-2) .
5. Repeat step 2–4 for enough peers P2, P3, … to nominally cross the 70% weight threshold in `block_signatures`. S never calls `mark_locally_accepted(true)` or `broadcast_signed_block` for this block, so S never pushes it to its node, even though S's own signerdb shows sufficient aggregated weight — a liveness wedge unresolvable without an external trigger (e.g. a fresh proposal re-evaluation or a `NewBlock` event from the node itself).
