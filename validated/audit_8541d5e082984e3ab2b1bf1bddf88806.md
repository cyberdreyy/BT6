### Title
Unhandled-recipient-abort in `staking_contract::distribute_internal` lets an operator or stale distribution recipient permanently freeze a staker's stake and commission payouts - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::distribute_internal` pays out every pending share in the `distribution_pool` in a single all-or-nothing loop using `aptos_account::deposit_coins`, which aborts if the recipient has not registered a `CoinStore<AptosCoin>` and has disabled `allow_arbitrary_coin_transfers` [2](#0-1) [3](#0-2) . Because `distribute_internal` is an unavoidable prerequisite step inside `unlock_stake`, `request_commission`, and `switch_operator` [4](#0-3) [5](#0-4) , a single "poisoned" recipient in the shared distribution pool (e.g., the operator's designated beneficiary) can make the entire transaction always revert, permanently freezing the staker's ability to unlock or withdraw their own stake and commission — the same root cause the external report describes (a transfer call that isn't safely handled and can revert the whole flow), applied here to APT coin deposits instead of an ERC20 `transfer`.

### Finding Description
`distribute_internal` iterates the `distribution_pool`'s shareholders and unconditionally calls `aptos_account::deposit_coins` for each one: [6](#0-5) 

`aptos_account::deposit_coins` aborts when the target has no registered `CoinStore<CoinType>` and does not accept arbitrary/unregistered transfers: [7](#0-6) 

Any account holder can flip that flag against themselves at will: [1](#0-0) 

The operator fully controls who is a distribution recipient for their own commission: `request_commission_internal` records the commission distribution against `operator`, and at payout time `distribute_internal` redirects the operator's share to `beneficiary_for_operator(operator)` — an address the operator can set to anything via `set_beneficiary_for_operator`: [8](#0-7) [9](#0-8) 

If the operator designates (or later switches to) a beneficiary address that has no `CoinStore<AptosCoin>` and has called `set_allow_direct_coin_transfers(false)` on itself, every future call to `distribute_internal` for that staker/operator pair will abort while trying to pay that beneficiary — since the loop processes all shareholders in one atomic transaction and cannot skip a failing one. Because `unlock_stake`, `request_commission`, and `switch_operator` all invoke `distribute_internal` before performing their own logic, the staker is permanently blocked from unlocking, withdrawing, or reassigning away from the malicious operator through the normal API, even though the staker never granted the operator control over the staker's own funds.

### Impact Explanation
This breaks the "Unlock, reactivate, withdraw ... paths must not redirect value or strand it permanently" invariant for `staking_contract`. A party holding only the operator/beneficiary role — not staker ownership — can strand the staker's principal and any unpaid rewards indefinitely, since:
- `unlock_stake` cannot execute (blocked before `staking_contract.principal -= amount`) [10](#0-9) .
- `switch_operator`, the staker's only self-service way to get away from a bad operator, is also blocked, since it also forces a `distribute_internal` first [11](#0-10) .
- `request_commission` and plain `distribute` are blocked too, so no one can drain the poisoned recipient's queued distribution out of the way either.

This is a high-impact, non-recoverable loss-of-claim-rights scenario reachable without any special privilege beyond being (or being appointed as) the operator of a staking contract, which is an ordinary role in this flow rather than a governance/admin role.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: it requires the operator to intentionally weaponize the beneficiary mechanism (or a staker to select/keep a malicious operator), which is plausible in a competitive validator/operator marketplace and requires no elevated privileges — only ordinary transactions (`set_beneficiary_for_operator`, `account::create_account` for an unregistered address, `set_allow_direct_coin_transfers(false)`) available to any operator.

### Recommendation
Make distribution resilient to a single failing recipient, e.g.:
- Wrap each `aptos_account::deposit_coins` call so a failure only skips/re-queues that recipient's share instead of aborting the whole distribution (for example, check `coin::is_account_registered` / `can_receive_direct_coin_transfers` first and, if the recipient cannot currently receive funds, leave their shares in the pool or redirect to a claimable escrow instead of calling `deposit_coins` inline).
- Alternatively, decouple `distribute_internal` from the critical paths (`unlock_stake`, `request_commission`, `switch_operator`) so a stuck distribution never blocks unrelated staker operations, or process shareholders independently (try/catch-like pattern via separate entry calls) so one failing recipient cannot revert payouts to everyone else.

### Proof of Concept
1. Staker creates a staking contract with `operator` O, then adds stake and lets the validator run and earn rewards (`staking_contract::create_staking_contract`, `add_stake`).
2. O calls `aptos_framework::account::create_account(auth_key = B)` for a fresh address `B` (this does **not** call `register_apt`, so `B` has no `CoinStore<AptosCoin>`).
3. From `B`'s own signer, call `aptos_account::set_allow_direct_coin_transfers(B_signer, false)`.
4. O calls `staking_contract::set_beneficiary_for_operator(O_signer, B)`.
5. Staker or O calls `staking_contract::request_commission(caller, staker, operator)` (or `unlock_stake`, or `switch_operator`). Internally `distribute_internal` tries `aptos_account::deposit_coins(B, ...)` for O's commission, which now aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. Every subsequent call to `unlock_stake`, `switch_operator`, `request_commission`, or `distribute` for this staker/operator pair now reverts identically, permanently freezing the staker's stake and any pending payouts.
