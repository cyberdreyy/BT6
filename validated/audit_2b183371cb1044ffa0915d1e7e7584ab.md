### Title
Unauthenticated flood of `HandleLegacyUserMessage` requests can evict a victim's pending `savedCallbacks` entry via `pruneCallbacks`, causing silent loss of webAPI trigger responses - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` inserts every syntactically-valid `web_api_trigger` request into the shared `h.savedCallbacks` map without any per-sender quota, allowlist check, or authentication of the caller beyond a self-generated ECDSA signature. `pruneCallbacks` only bounds the map size by evicting the globally oldest entries once `len(savedCallbacks) > MaxSavedCallbacks`, so an attacker who floods the gateway with enough uniquely-keyed, freshly-signed requests can force eviction of an older, still-pending, legitimate victim callback before the DON's response arrives.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go:217-292`) routes any legacy request (unauthenticated HTTP caller, arbitrary self-generated key) that passes `msg.Validate()` (signature well-formedness only) to `h.HandleLegacyUserMessage`. Inside `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`), validation only checks payload decodability, a non-zero timestamp, message freshness (`MaxAllowedMessageAgeSec`), and that the method is `MethodWebAPITrigger`. There is an explicit `// TODO: apply allowlist and rate-limiting here` comment at line 384 confirming no sender-based admission control exists before the entry is stored: [1](#0-0) 

Each accepted request is unconditionally inserted keyed only by attacker-controlled `msg.Body.MessageId`: [2](#0-1) 

`pruneCallbacks` runs on a periodic ticker (`CallbackPruneIntervalSec`, default 30s) and, after removing age-expired entries, if the map still exceeds `MaxSavedCallbacks` (default 20000), sorts all remaining entries by `createdAt` and deletes the oldest half indiscriminately — with no notion of sender identity or fairness: [3](#0-2) 

Since an attacker can generate arbitrary ECDSA keys locally, sign arbitrary unique `MessageId`s, and submit `MaxSavedCallbacks+1` (or enough to exceed the trim threshold) legacy requests in one prune interval, any victim's callback that was saved slightly earlier will be among the oldest and evicted. The victim's response never arrives — `handleWebAPITriggerMessage` looks up `h.savedCallbacks[msg.Body.MessageId]` when the DON eventually replies and finds nothing (`found == false`), silently dropping the response with no callback ever invoked: [4](#0-3) 

No component in the path (`gateway.ProcessRequest`, `msg.Validate()`, `HandleLegacyUserMessage`) enforces a per-sender cap on outstanding callbacks or authenticates the sender beyond self-signed message format, so nothing stops the flood from reaching insertion.

### Impact Explanation
Concrete impact: an unauthenticated, unprivileged attacker can cause denial of response delivery for a legitimate victim's pending webAPI trigger request — the victim's HTTP call to the gateway will time out (`callback.Wait(ctx)` in `gateway.go:278` returns a timeout error) even though the request was otherwise valid and the DON was going to respond correctly. This is an availability/isolation violation: an unauthenticated flood starves a legitimate subscriber's request, matching a Denial-of-Service impact class rather than fund loss or key disclosure.

### Likelihood Explanation
Feasibility is moderate to high: the attacker needs no privileges — only the ability to send signed gateway HTTP requests using self-generated keys, and knowledge (or timing luck) of when a victim's request was submitted. The default `MaxSavedCallbacks` is 20000, so the attacker must generate and submit roughly that many uniquely-keyed signed requests within roughly one prune interval (default 30s) to force an eviction cycle that reaches the victim's entry — feasible with automated tooling and parallel connections. Precise targeting of a specific victim message requires the attacker to know the request timing (the victim's request must be older than the attacker's flood, but still unexpired), which is a somewhat narrow window (`CallbackMaxAgeSec`, default 120s) but is a realistic race for an attacker who observes the victim's request.

### Recommendation
Enforce a per-sender (or per-key) quota on the number of outstanding entries a single sender can hold in `savedCallbacks`, reject/rate-limit excess requests at admission time (implementing the existing `// TODO: apply allowlist and rate-limiting here`), and avoid an eviction policy that indiscriminately deletes the globally oldest entries irrespective of sender fairness — e.g., track and cap per-sender counts, or apply proportional/fair eviction across senders rather than a strict global age-sort.

### Proof of Concept
Go unit test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with a small `MaxSavedCallbacks` (e.g., 10) via `HandlerConfig` for test speed.
2. Save one "victim" callback into `h.savedCallbacks` with an early `createdAt` timestamp using `handler.HandleLegacyUserMessage` with a valid signed `web_api_trigger` message from a victim key, and record its `MessageId`.
3. Loop and call `HandleLegacyUserMessage` `MaxSavedCallbacks` additional times, each with a uniquely signed message from a freshly generated attacker ECDSA key and unique `MessageId`, all with `createdAt` timestamps after the victim's.
4. Directly invoke `handler.pruneCallbacks()` (bypassing the ticker for test determinism).
5. Assert: `handler.savedCallbacks[victimMessageId]` no longer exists (evicted), while a subset of the attacker's most-recent entries remain — demonstrating the victim's still-valid, unexpired callback was dropped purely due to flooding, with no per-sender protection preventing it.
6. Additionally simulate the DON responding late for the victim's `MessageId` via `handleWebAPITriggerMessage` after eviction and assert the victim's original `callback.Wait` never receives a response (times out), confirming the response is silently lost.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
