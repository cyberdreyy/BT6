### Title
APR=0 withdraw receipts settle performance fees with the `fee` value at stopEpoch time, so a mid-epoch fee increase retroactively reduces an in-flight requester's payout - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.requestWithdraw()` locks management and performance fees at request time for normal withdrawals (`_totalWithdrawFees`, lines 773-778), so the minted receipt is fixed and immune to later `setFeeParams` changes. However, in the APR=0 mode the receipt minted in `IdleCreditVault.requestWithdraw()` (lines 283-286, `_requestWithdrawApr0`) only covers the post-management-fee principal bucket; the interest share is settled later at `stopEpoch`/`claimWithdrawRequest` via `_settleApr0`, which computes net interest using the *current* `cdoEpoch.fee()` (see test expectation `_calcApr0NetForPrincipal(..., cdoEpoch.fee())`). A user who requests a withdrawal expecting fee F can therefore receive materially less if `setFeeParams` raises `fee` (up to `FULL_ALLOC` = 100%) before the epoch settles — with no user-specified maximum fee and no timelock.

### Finding Description
`requestWithdraw` in `IdleCDOEpochVariant.sol` (lines 739-791) splits into two paths:

- Normal path: `interest` and `totalFees` are computed immediately (`_calcInterestWithdrawRequest` + `_totalWithdrawFees`, using the current `fee` inside `_netGainAfterFees`, lines 889-905) and the receipt `_underlyings = principal + interest - totalFees` is fixed forever.
- APR=0 path (`unscaledApr == 0`): `IdleCreditVault.requestWithdraw` mints the user a receipt for the principal bucket only and records `apr0Users[_user]` / `apr0TotalPrincipal`; the interest component is settled at stopEpoch when the pool gain is distributed pro-rata, net of `fee` **as read at that later time**.

Because `setFeeParams` (owner) can be invoked at any point in the epoch with no notice period and `fee` may be raised to 100%, a requester's deferred interest is valued under a fee regime that did not exist when the request was priced. The management fee duration (`_withdrawRequestManagementFeeDuration`) and principal haircut are locked, but the performance fee on the APR0 interest share is not — it is charged on `poolInterest` at settle time against `apr0Users` principal that was committed under the old fee.

This is the direct analog of the PortalV2 fee issue: an in-flight transaction's economics are altered by a permissioned fee update the transactor could not bound.

### Impact Explanation
A lender that calls `requestWithdraw` during a zero-APR epoch expecting performance fee `fee0` can have the entire interest portion confiscated: if `fee` is raised to `FULL_ALLOC` before `stopEpoch`, `_settleApr0` distributes zero net interest to `apr0Users` principal and the whole `poolInterest` attributable to that receipt accrues to `feeReceiver`/`unclaimedFees` instead. The receipt still pays principal, but the yield the user reasonably expected is permanently redirected to fees — theft of unclaimed yield proportional to `poolInterest * receiptPrincipal / totalPrincipal * (fee1 - fee0)/FULL_ALLOC`.

### Likelihood Explanation
Requires the vault to operate in APR=0 mode (`unscaledApr == 0`, used when `isAYSActive` is disabled / APR set to 0 — a supported configuration exercised by `testApr0*`) and an honest-but-unannounced `setFeeParams` fee increase landing between `requestWithdraw` and the settling `stopEpoch`. The external report's precondition (admin raises fee mid-flight, no timelock, no user cap) holds verbatim: `setFeeParams` is a single-step owner call and `requestWithdraw` exposes no `maxFee`/`minOut` parameter on the APR0 path.

### Recommendation
Snapshot the `fee` (and `managementFee`) used to price each withdraw receipt at `requestWithdraw` time and apply that snapshot during `_settleApr0`/`stopEpoch` settlement for that epoch's pending receipts (e.g., store a per-epoch `feeAtRequest` alongside `apr0Users`/`withdrawsRequestsByEpoch`), or add a timelock/notice period on `setFeeParams` so in-flight receipts settle under the fee observed at request time.

### Proof of Concept
```solidity
// Foundry fork test — APR=0 retroactive fee increase on pending receipt
function testApr0RequesterChargedRetroactiveFeeIncrease() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // APR0 mode

    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _forceLastEpochAprToZero();

    // User requests withdraw while fee == 0: expects full pro-rata pool interest
    uint256 trancheReq = IERC20(AAtranche).balanceOf(address(this)) / 2;
    uint256 principal = cdoEpoch.requestWithdraw(trancheReq, address(AAtranche));
    uint256 poolPrincipal = cdoEpoch.getContractValue();

    _startEpochAndCheckPrices(1);

    // Owner raises performance fee to 100% while the request is in-flight
    _setFeeParams(TL_MULTISIG, FULL_ALLOC, FULL_ALLOC, cdoEpoch.managementFee());

    uint256 poolInterest = 1_000 * ONE_SCALE;
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    deal(defaultUnderlying, borrower, poolInterest + pending + amount);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, poolInterest);

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();

    uint256 expectedAtRequest = principal + poolInterest * principal / (poolPrincipal + principal);
    uint256 actual = underlying.balanceOf(address(this)) - balPre;
    // With fee == 100% the receipt only pays principal; the entire interest share
    // went to feeReceiver despite the request being priced under fee == 0.
    assertLt(actual, expectedAtRequest, "retroactive fee ate receipt interest");
    assertEq(actual, principal, "receipt pays principal only after 100% fee");
}
```
