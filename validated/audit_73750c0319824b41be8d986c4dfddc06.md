## Title
Fail-open on node-unreachable in `check_latest_block_in_tenure` lets the pre-commit "last look" sign a non-canonical block — ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_latest_block_in_tenure` treats a failed `client.get_tenure_tip` RPC call as `Ok(true)` ("assume proposal is higher"), a fallback whose safety rationale only holds at proposal-arrival time (because a subsequent node validation call is the real backstop). The same function is reused, via `check_block_against_signer_db_state`, at the validate-ok recheck and at the pre-commit-threshold "one last look" recheck, where no further node validation exists to catch a false pass, so a transient RPC failure at that exact moment converts what would be a `SortitionViewMismatch` rejection into a silent pass and the block gets signed.

### Finding Description
The equality that must hold: at the moment the signer signs, `check_block_against_signer_db_state` must return the same verdict a reachable node would give — a rejection (`SortitionViewMismatch`) must never be swallowed into a pass just because the RPC happened to fail at that instant.

`check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs`, lines 376-478) first checks purely local signerdb records (`get_tenure_last_block_info`, `get_last_accepted_block`). Only when neither local record vetoes the proposal does it call the node: [1](#0-0) 

If `client.get_tenure_tip(tenure_id)` errors, the function returns `Ok(true)` — i.e. "the check passes" — with the comment justifying this because "this proposal ultimately must be passed to the `stacks-node` proposal endpoint to do the validation" [2](#0-1) .

That justification is true only for the call site inside proposal-arrival's `check_proposal`, where a full `/v3/block_proposal` node validation still follows. But the identical function is also invoked from `check_block_against_signer_db_state`, which is the recheck run:
- right after node validation returns OK (`handle_block_validate_ok`), and
- at the pre-commit weight-threshold "one last look" before signing (`handle_block_pre_commit`): [3](#0-2) [4](#0-3) 

At these two points there is no further node validation downstream — this recheck *is* the last checkpoint. When `Ok(true)` is returned because the RPC errored, `check_block_against_signer_db_state` returns `None` (no rejection at all — not even a logged `ConnectivityIssues`), and the caller proceeds straight to `mark_pre_committed`/pre-commit broadcast or, at the pre-commit-threshold call site, straight past the recheck into the conflict-and-sign logic (`SIGN: mark_locally_accepted, handle_block_signature`).

Attack outline: an attacker holding a single miner slot proposes/gossips a competing block B while a canonical, previously-signed/tenure-active block already occupies or exceeds that height in the tenure the node actually knows about. If, at the exact instant the victim signer's pre-commit weight for B crosses 70% and runs its "one last look" (`check_block_against_signer_db_state` → `check_latest_block_in_tenure`), the signer's `get_tenure_tip` RPC to its own node experiences any transient failure (a routine occurrence during burn-chain forks/tenure churn, which the attacker can attempt to time by racing tenure-change/fork conditions), the fallback silently reports "proposal is higher / passes," and the signer signs B even though a reachable node would have reported the tip already at/above B's height (`SortitionViewMismatch`).

Existing guards do not prevent this:
- The local-only checks (`get_tenure_last_block_info`, `get_last_accepted_block`) only catch conflicts the signer already has recorded; they say nothing about the node's authoritative tip, which is exactly what the RPC call is meant to supply.
- `check_block_against_signer_db_state`'s own `Err(e)` handling (which does map to an explicit `ConnectivityIssues` rejection) is never reached here, because `check_latest_block_in_tenure` absorbs the RPC error internally and returns `Ok(true)` rather than propagating `Err`.
- The section-5 conflict guard (`get_signed_conflicts`/`conflict_still_blocks`) only fires for blocks the signer itself already signed/tracked as conflicting; it does not reconstruct the canonical tip independently.

### Impact Explanation
This breaks the canonicity/fail-closed safety property: the signer's signature (the irreversible act) is placed over a block that a reachable node would have rejected as not confirming the canonical tenure tip. A shared or repeated occurrence of this timing across enough signers could contribute a signature toward a non-canonical/conflicting block reaching the group threshold — matching the Critical category ("a signer signing an invalid, non-canonical, or conflicting block").

### Likelihood Explanation
Preconditions: attacker needs only one miner slot (to produce the competing/non-canonical proposal) plus the ability to gossip proposals/pre-commits, consistent with the stated threat model. The exploit further requires the victim signer's own node RPC to be transiently unreachable at the precise instant of the pre-commit-threshold recheck or validate-ok recheck — a narrow timing window, but one whose occurrence is a normal operational hazard (node under load during a burn-chain reorg/tenure churn, which an attacker racing tenure changes can attempt to induce indirectly). This is not majority-signer or privileged-role dependent, and is repeatable per occurrence of the timing window, though not deterministically triggerable by the attacker alone.

### Recommendation
Do not fall back to "assume passes" on RPC failure inside `check_latest_block_in_tenure` when it is invoked from `check_block_against_signer_db_state` (the validate-ok and pre-commit-threshold recheck paths). Instead, propagate the error as `RejectReason::ConnectivityIssues` and treat that as a hard, non-signing outcome (equivalent to a rejection, not a pass) at those two call sites, reserving the "assume higher" fallback strictly for the proposal-arrival `check_proposal` path where a subsequent node validation is the real backstop. Concretely, thread a flag/parameter through `check_latest_block_in_tenure` (or duplicate the small tip-fetch branch) so callers at validate-ok/pre-commit-threshold can distinguish "node unreachable" from "node says pass" and reject/hold rather than silently pass.

### Proof of Concept
Rust test plan (extending the existing sibling-race harness in `stacks-signer/src/v0/tests.rs`, e.g. `run_sibling_scenario`):
1. Set up two tenures/blocks such that the canonical (reachable) node's `/v3/tenures/tip_metadata/<tenure>` response for the block's own tenure already reflects a competing block at/above the proposed block's `chain_length` (i.e., the true, reachable answer to `check_latest_block_in_tenure` is `Ok(false)` → `SortitionViewMismatch`).
2. Drive the signer through proposal, node validation OK, and pre-commit accumulation up to the ≥70% weight threshold, as `run_sibling_scenario`/`handle_block_pre_commit` already do.
3. At the exact call inside `handle_block_pre_commit`'s recheck (`check_block_against_signer_db_state` → `check_latest_block_in_tenure` → `client.get_tenure_tip`), mock the HTTP endpoint to return a connection error only for that specific call (e.g., toggle the mock server to close/refuse exactly once at that point), instead of the tip response from step 1.
4. Assert two things:
   - Side A (true/reachable state): with the tip endpoint answering normally, the block is rejected with `RejectReason::SortitionViewMismatch` and `block_info.signed_self.is_none()`.
   - Side B (the bug): with the RPC forced to error only at the pre-commit-threshold recheck, assert the current code incorrectly proceeds to `SIGN`/`mark_locally_accepted` (`block_info.signed_self.is_some()`), demonstrating the equality break — a rejection that should have occurred is instead a signature.
5. The fix should make Side B match Side A: the block must end up `mark_locally_rejected` with `RejectReason::ConnectivityIssues`, never signed, when the tip RPC fails at this recheck.
