### Title
Stale instant-withdraw receipt entries (`instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`) are never cleared on a normal claim, inflating default-recovery basis and permanently freezing later recovery claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The CVE is a use-after-free: memory is referenced after being freed. The analog in `IdleCreditVault` is a *receipt used after being consumed*: `claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch receipt `instantWithdrawsRequestsByEpoch[_user][epoch]` or the per-epoch total `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults in the same epoch while another instant request is still unfunded (`pendingInstantWithdraws != 0`), `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` read these stale entries as if the already-paid claims were still outstanding. `finalizeDefaultRecovery` then books a phantom claim basis and a phantom prefunded reserve, diluting `defaultRecoveryPrice` for every claimant and overstating `defaultRecoveryReserve` beyond the strategy's actual balance, so the last recovery claimants' transfers revert permanently.

### Finding Description
In `claimInstantWithdrawRequest` (contracts/strategies/idle/IdleCreditVault.sol:380-393) the claim path burns `instantWithdrawsRequests[_user]` and pays the user, but never touches `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` or `instantWithdrawClaimsByEpoch[currentEpoch]`. Those mappings are only mutated in `requestInstantWithdraw` (lines 371-372) and in `_claimDefaultedInstantWithdrawRequest` (lines 847-853). `collectInstantWithdrawFunds` (lines 398-403) decrements only `pendingInstantWithdraws`.

Sequence:

1. Epoch N running/buffer. User A calls `requestInstantWithdraw(X)`. State: `instantWithdrawsRequests[A]=X`, `instantWithdrawsRequestsByEpoch[A][N]=X`, `instantWithdrawClaimsByEpoch[N]=X`, `pendingInstantWithdraws=X`.
2. CDO collects funds via `collectInstantWithdrawFunds(X)` → `pendingInstantWithdraws=0`. A calls `claimInstantWithdrawRequest` → receives X; `instantWithdrawsRequests[A]=0`. The per-epoch entries still hold X (the "freed" receipt still referenced).
3. User B (or A) calls `requestInstantWithdraw(Y)` in the same epoch N: `instantWithdrawClaimsByEpoch[N]=X+Y`, `instantWithdrawsRequestsByEpoch[B][N]=Y`, `pendingInstantWithdraws=Y`.
4. Borrower defaults mid-epoch; CDO calls `finalizeDefaultRecovery` while `epochNumber` is still N.

Inside finalization:

- `defaultPendingClaimBasis` (lines 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` = X+Y, although X was already paid out and has no backing.
- `_defaultPrefundedInstantReserve` (lines 716-723) computes `instantBasis - pendingInstant` = (X+Y) − Y = X and counts X as already-held reserve even though those underlyings left the strategy in step 2.
- `defaultRecoveryReserve` is set to `_recoveredAmount + prefundedReserve + existing` (line 686/691) — inflated by phantom X relative to the real balance.
- `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688) is computed over an inflated basis, so every defaulted-epoch receipt (normal and instant) and every active tranche NAV gets a lower recovery price than warranted.
- `defaultInstantWithdrawsFinalized` becomes true (line 696). When A later calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads `claimBasis = instantWithdrawsRequestsByEpoch[A][N] = X` and executes `instantWithdrawsRequests[A] -= claimBasis` (line 848) → `0 - X` underflows and reverts, so the stale entry can never be cleaned. More importantly, because `defaultRecoveryReserve` was overstated by the phantom prefunded amount, the last claimants drawing on the reserve hit `underlyingToken.safeTransfer` with insufficient balance and their claims revert permanently.

### Impact Explanation
Two direct fund impacts, both quantified by X (the already-claimed instant amount still present in per-epoch storage):

- **Dilution / mispriced recovery:** `totalBasis` is inflated by X, lowering `defaultRecoveryPrice` for all defaulted-epoch withdraw receipts and instant receipts (lines 782, 855 pay `claimBasis * defaultRecoveryPrice / RECOVERY_FULL`) and crystallizing a worse NAV for active AA/BB tranche holders via the `_burn(idleCDO, ...)` repricing at lines 699-705. Every honest claimant's payout is permanently reduced.
- **Permanent freezing of recovery funds:** `defaultRecoveryReserve` is credited X more underlyings than the strategy holds. `_transferDefaultRecovery` (lines 912-917) does an unconditional `safeTransfer`, so once the real balance is exhausted all remaining claims revert — claimants at the tail of the queue permanently lose up to X of recovery.

Broken invariant: one receipt one payout — the consumed instant receipt still counts as outstanding basis and as prefunded reserve.

### Likelihood Explanation
Requires (a) an instant withdraw that is funded and claimed, (b) a further unfunded instant request so `pendingInstantWithdraws != 0`, and (c) a borrower default finalized while `epochNumber` still equals the request epoch (default paths such as `_handleBorrowerDefault`/`finalizeDefault` run inside the epoch). All steps use only unprivileged or honest-privileged actions: any tranche holder can request/claim instant withdrawals; the borrower default and finalization are honest privileged calls the attacker merely sequences around. No guard prevents claiming an instant receipt in its request epoch, and no path clears the per-epoch entries on a normal claim.

### Recommendation
In `claimInstantWithdrawRequest`, also clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (and decrement `instantWithdrawClaimsByEpoch[epochNumber]`) for the portion being paid — or track per-epoch entries only for still-unfunded requests. Alternatively, derive `instantWithdrawClaimsByEpoch` usage in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` from actually-unclaimed receipts so already-paid claims cannot be double-counted as basis or as prefunded reserve.

### Proof of Concept
Foundry fork test skeleton (against the epoch CDO + `IdleCreditVault` strategy, mirroring `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `cdoEpoch.requestInstantWithdraw`, etc.):

```solidity
function testStaleInstantReceiptInflatesDefaultRecovery() public {
    // epoch N is running; userA deposits AA and requests an instant withdraw of X
    address userA = makeAddr("userA");
    address userB = makeAddr("userB");
    _depositWithUser(userA, 10_000 * ONE_SCALE, true);
    _depositWithUser(userB, 10_000 * ONE_SCALE, true);

    vm.prank(userA);
    cdoEpoch.requestInstantWithdraw(X, AAtranche);
    // CDO funds and collects X, userA claims -> paid, but per-epoch entries stay
    vm.prank(manager); // or the whitelisted caller used in tests
    cdoEpoch.getInstantWithdrawFunds(X);
    vm.prank(userA);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(strategy.instantWithdrawsRequestsByEpoch(userA, strategy.epochNumber()), X); // stale!

    // second instant request Y in the SAME epoch, left unfunded
    vm.prank(userB);
    cdoEpoch.requestInstantWithdraw(Y, AAtranche);

    // borrower defaults mid-epoch; finalizeDefaultRecovery runs while epochNumber == N
    // ... trigger default + finalizeDefaultRecovery via honest manager/owner calls ...

    // basis includes X+Y instead of Y; prefunded reserve counts X already paid out
    assertGt(strategy.defaultRecoveryReserve(), underlying.balanceOf(address(strategy)));
    // last recovery claimant's transfer reverts: permanent freeze of ~X
}
```

Expected result: `instantWithdrawClaimsByEpoch[N]` equals X+Y although only Y is outstanding; `defaultRecoveryReserve` exceeds the strategy's real underlying balance by X; tail recovery claims revert.
