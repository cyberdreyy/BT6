### Title
Stale instant-withdraw epoch buckets are never cleared on claim, so `finalizeDefaultRecovery` double-counts paid-out claims as basis and phantom reserve — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The kernel bug frees a shared request slot (`list_del_init`) before the giveback callback finishes, letting a concurrent enqueue reuse it mid-callback. The analog here: `claimInstantWithdrawRequest` marks a user's instant receipt "free" (`instantWithdrawsRequests[_user] = 0`) but never clears the per-epoch bookkeeping (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) that was set in `requestInstantWithdraw`. If the borrower defaults in the same epoch, `finalizeDefaultRecovery` re-reads those stale buckets and counts already-paid-out underlying as both claim basis and prefunded reserve, inflating `defaultRecoveryPrice` beyond what the reserve can pay. Additionally, the stale per-epoch entry permanently reverts `_claimDefaultedInstantWithdrawRequest` via underflow for affected users.

### Finding Description
`requestInstantWithdraw` records the receipt in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, and `instantWithdrawClaimsByEpoch[epoch]` [1](#0-0) . The funded-claim path clears only the aggregate: `instantWithdrawsRequests[_user] = 0; _transferFundedClaim(_user, amount)` — the per-epoch entries survive the "giveback" [2](#0-1) .

Those stale entries are then reused by default finalization in the same epoch:

- `defaultPendingClaimBasis()` adds the full `instantWithdrawClaimsByEpoch[epochNumber]` — including claims already paid out — whenever `pendingInstantWithdraws != 0` [3](#0-2) .
- `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant` and treats the difference as underlying already held in the strategy — but the claimed portion was transferred out to users, so it is phantom reserve [4](#0-3) .
- `finalizeDefaultRecovery` folds that phantom amount into `reserveAmount` and computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over a basis that also includes the paid-out claims [5](#0-4) .

The result is an overpriced recovery multiplier: aggregate payouts `totalBasis * price` exceed real held funds by exactly the stale claimed amount. Early claimants (the attacker) withdraw at the inflated price via `_transferDefaultRecovery`, and later claimants' transfers revert on insufficient balance — direct theft plus insolvency. There is no skim/guard for this: `_transferDefaultRecovery` pays from `defaultRecoveryReserve` accounting, not actual balance reconciliation.

Separately, the stale `instantWithdrawsRequestsByEpoch[_user][N]` makes `instantWithdrawsRequests[_user] -= claimBasis` underflow in `_claimDefaultedInstantWithdrawRequest` for any user who claimed part of an epoch-N instant receipt before the default (per-epoch basis is always ≥ the remaining aggregate, and post-default `requestInstantWithdraw` adds to the same epoch key, so the underflow cannot be escaped) [6](#0-5) . The user's remaining receipt is permanently unclaimable, and the `requestWithdraw` post-default guard (`instantWithdrawsRequests[_user] != 0` → `NotAllowed`) locks them out of the post-default request path too [7](#0-6) .

### Impact Explanation
Direct theft and insolvency: every underlying claimed through a funded instant withdrawal in the default epoch is counted twice — once paid to the claimer, once as phantom prefunded reserve that inflates `defaultRecoveryPrice` for all defaulted receipts. An attacker holding a defaulted normal withdraw receipt (`withdrawsRequestsByEpoch[N]`) claims early at the inflated price and extracts up to the full stale instant amount from the recovery reserve, leaving later claimants (honest KYC'd lenders) with unpayable receipts — permanent loss quantified as exactly the sum of same-epoch funded instant claims. Independent permanent freeze: users who partially claimed instant receipts in the default epoch can never claim the remainder (underflow revert) nor open post-default requests.

### Likelihood Explanation
Requires: instant withdrawals enabled (manager/owner config — honest), at least one funded+claimed instant receipt and one still-pending instant receipt (so `pendingInstantWithdraws != 0` and `defaultInstantWithdrawsFinalized = true`) in the same epoch, then a borrower default finalized via `finalizeDefault` → `finalizeDefaultRecovery`. All attacker steps are unprivileged user actions (`requestInstantWithdraw`, `claimInstantWithdrawRequest`, `claimWithdrawRequest`) sequenced around honest owner/manager/borrower calls. No privileged misbehavior needed; the accounting gap is deterministic once the sequence occurs.

### Recommendation
Mirror the upstream fix — track the epoch slot's real lifetime: in `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount (needs a per-user record of which epoch each funded instant receipt belongs to, e.g. `lastInstantWithdrawRequest[_user]` analogous to `lastWithdrawRequest`), so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only count still-outstanding claims. Alternatively settle instant receipts per epoch at claim time the same way `_clearWithdrawClaimForEpoch` does for normal requests.

### Proof of Concept
Foundry fork PoC (against the `IdleCreditVault.t.sol` harness, epoch variant with instant withdrawals enabled):

```solidity
function testStaleInstantClaimInflatesRecovery() external {
    // Epoch N running; instant withdraws enabled via setInstantWithdrawParams
    _stopCurrentEpoch();                 // enter buffer, epoch N pending
    _depositWithUser(attacker, 200e6);   // attacker normal position
    _depositWithUser(victim,  100e6);
    vm.prank(manager); cdoEpoch.startEpoch();

    // Attacker instant-request 100e6 and gets it funded + claimed intra-epoch
    _requestInstantWithdrawWithUser(attacker, 100e6);
    vm.prank(manager); cdoEpoch.getInstantWithdrawFunds(100e6); // collectInstantWithdrawFunds
    vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest(); // pays out, leaves stale epoch buckets

    // Victim instant-request 50e6 stays UNFUNDED -> pendingInstantWithdraws = 50e6
    _requestInstantWithdrawWithUser(victim, 50e6);

    // Attacker also files a normal withdraw receipt in epoch N
    _requestWithdrawWithUser(attacker, 100e6);

    // Borrower defaults in same epoch N; owner stops with loss
    deal(address(underlying), strategy.borrower(), 0, true);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(cdoEpoch.owner()); cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted());

    // Finalize with real recovered funds R only
    uint256 R = 150e6;
    deal(address(underlying), manager, R, true);
    vm.startPrank(manager);
    underlying.approve(address(strategy), R);
    cdoEpoch.finalizeDefault(R, manager);
    vm.stopPrank();

    // Recovery price was computed over basis including the 100e6 already paid to
    // attacker AND phantom prefundedReserve = 150e6-50e6 = 100e6.
    uint256 price = strategy.defaultRecoveryPrice();

    // Attacker claims early at inflated price -> drains reserve
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker); cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - pre;

    // Sum of all defaulted claims now exceeds real reserve by 100e6:
    // victim's recovery claim reverts (insufficient balance) -> insolvency
    vm.prank(victim);
    vm.expectRevert(); // safeTransfer fails or pays less than basis*price
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Key asserts: `strategy.instantWithdrawClaimsByEpoch(N)` remains `150e6` after attacker's claim (proving the stale bucket), and `got` exceeds `attackBasis * realR / totalRealBasis` by the phantom `100e6` share. The DoS variant: a user who claimed a funded instant receipt and holds a residual unfunded one sees `claimInstantWithdrawRequest` revert on the `instantWithdrawsRequests[_user] -= claimBasis` underflow permanently.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
