### Title
`InitializeNonceAccount` sets the nonce authority with no signer/ownership check, enabling front-running theft of nonce account funds - (File: `programs/system/src/system_instruction.rs`, `programs/system/src/system_processor.rs`)

### Summary
The `SystemInstruction::InitializeNonceAccount` handler transitions a System-owned account from `State::Uninitialized` to `State::Initialized`, permanently fixing the nonce `authority` field supplied in the instruction data. Unlike other System Program instructions that mutate account ownership/authority (`Allocate`, `Assign`), this handler performs no check that the nonce account itself, or any related party, signed the transaction. Any unprivileged party can race to submit this instruction against an eligible account and set themselves as the nonce authority, exactly mirroring the reported "initializer front-running" bug class where an unauthenticated init step allows an attacker to seize a critical address field before the legitimate deployer.

### Finding Description
`initialize_nonce_account` only validates writability, sufficient rent-exempt balance, and that the current state is `Uninitialized` — it never checks that the account (or any signer) authorizing the write is the intended owner: [1](#0-0) 

The dispatcher in `system_processor.rs` likewise borrows the account and calls the initializer without any signer verification for account index 0: [2](#0-1) 

This is inconsistent with sibling System Program handlers in the same file that mutate similarly sensitive fields, which explicitly require `address.is_signer(signers)`: [3](#0-2) 

It is also inconsistent with the analogous "initialize" flow in the Vote program, which explicitly calls `verify_authorized_signer(&vote_init.node_pubkey, signers)` before initializing critical account state: [4](#0-3) 

The safety of `InitializeNonceAccount` therefore depends entirely on convention: it is expected to be bundled atomically in the same transaction as `SystemInstruction::CreateAccount` (which does require the new account's signature), as done by the CLI helper `create_nonce_account`. Whenever account creation/funding (`CreateAccount`/`CreateAccountWithSeed`/`Allocate`+`Assign`) and nonce initialization are not atomically bundled — e.g., programs or wallets that pre-fund/allocate an 80-byte, system-owned, rent-exempt account in one transaction and initialize it as a nonce account in a later, separate transaction — any third party can observe the pending/completed creation and submit their own `InitializeNonceAccount(attacker_pubkey)` instruction first.

### Impact Explanation
This falls squarely in the in-scope "fee/rent/nonce accounting" category and is reachable from an ordinary user transaction with no special privilege. A successful front-run permanently sets `nonce::state::Data.authority` to the attacker's key. Since `AdvanceNonceAccount`, `AuthorizeNonceAccount`, and `WithdrawNonceAccount` all gate on `verify_authorized_signer` matching this `authority` field, the attacker becomes sole controller of the account and can subsequently call `WithdrawNonceAccount` to drain all lamports (the rent-exempt deposit funded by the victim) to an address of their choosing — a concrete unauthorized fund theft, directly analogous to the reported `_rewardPool` hijack.

### Likelihood Explanation
Exploitation requires only that account creation/funding and `InitializeNonceAccount` are not executed atomically in a single transaction — a pattern that can arise in custom program flows, wallets, or scripts that build nonce accounts across multiple transactions (e.g., due to transaction size constraints, retries, or programmatic multi-step account setup). Any observer of the mempool/gossip layer (or of a delayed/dropped initializer transaction that needs to be resent) can win the race by submitting `InitializeNonceAccount` with a higher priority fee, requiring no special privileges beyond normal transaction submission.

### Recommendation
Require that `InitializeNonceAccount` — like `Allocate`/`Assign` — verify the nonce account key is present in the transaction's signer set (or otherwise bind initialization to the same signer(s) who created/funded the account) before transitioning it out of `Uninitialized` state, consistent with the pattern already used in the Vote program's `initialize_account`.

### Proof of Concept
1. Victim (or a wallet/program) submits a transaction that allocates an 80-byte, system-owned account `N` and funds it to the rent-exempt minimum (e.g., via `Allocate`+`Assign`+`Transfer`, or `CreateAccount` in a separate transaction from initialization).
2. Before the victim's follow-up `InitializeNonceAccount(victim_authority)` transaction lands (or if it is delayed/needs resubmission), the attacker submits their own transaction invoking `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` against account `N`, paying a higher priority fee, with `N` not marked as signer.
3. `initialize_nonce_account` (`programs/system/src/system_instruction.rs:163-211`) accepts this because it never checks any signer relation to account `N`; it only checks `State::Uninitialized` and rent-exemption, both satisfied. The account is set to `State::Initialized(Data{ authority: attacker_pubkey, .. })`.
4. The victim's subsequent `InitializeNonceAccount` now fails with `InstructionError::InvalidAccountData` since the state is no longer `Uninitialized`.
5. The attacker calls `SystemInstruction::WithdrawNonceAccount`, signing as `attacker_pubkey` (the recorded authority), draining `N`'s lamports to an address they control.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }

pub fn initialize_account<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    vote_init: &VoteInit,
    signers: &HashSet<Pubkey, S>,
    clock: &Clock,
) -> Result<(), InstructionError> {
    VoteStateHandler::check_vote_account_length(vote_account, target_version)?;
    let versioned = vote_account.get_state::<VoteStateVersions>()?;

    if !versioned.is_uninitialized() {
        return Err(InstructionError::AccountAlreadyInitialized);
    }

    // node must agree to accept this vote account
    verify_authorized_signer(&vote_init.node_pubkey, signers)?;

    VoteStateHandler::init_vote_account_state(vote_account, vote_init, clock, target_version)
}
