### Title
Cross-job pipeline run disclosure via unscoped runID lookup in PipelineRunsController.Show - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Show` handles `GET /v2/jobs/:ID/runs/:runID` but only parses `:runID` and calls `App.PipelineORM().FindRun(ctx, id)`, never checking that the returned run's `PipelineSpec.JobID` matches the `:ID` path parameter. Any authenticated low-privilege user (view/run role) who can enumerate or guess a `runID` belonging to a job they are not scoped to can retrieve that run's full data by placing it under any job path.

### Finding Description
`Show` builds a `pipeline.Run{}`, sets its ID from `c.Param("runID")`, and fetches it directly: [1](#0-0) 

`c.Param("ID")` (the job ID segment of the route) is never read or compared in `Show`, unlike `Index`, which does parse and use `:ID` to scope the query: [2](#0-1) 

The ORM's `FindRun` signature confirms the lookup is keyed only by run ID, with no job-scoping parameter: [3](#0-2) 

Since Chainlink UI/API and job run IDs are sequential integers, and the route accepts any `:ID`/`:runID` combination without cross-validation, a low-privilege user who is only supposed to view/run their assigned job(s) can substitute a runID belonging to another job into the URL and the handler will happily return that run's presenter payload, including task run inputs/outputs, which can contain sensitive request/response data (e.g., API call parameters, decoded outputs) from a job they do not own or have permission to see.

I was unable to fully verify with the tools available whether the router-level middleware imposes any per-job authorization/role restriction beyond generic "authenticated session/API token" checks (i.e., whether Chainlink RBAC assigns access at a per-job granularity at all, as opposed to node-wide roles like admin/edit/run/view). Based on the code inspected, Chainlink's session roles (admin/edit/run/view) appear to be node-wide, not per-job, so this may not be a privilege-escalation issue in the traditional multi-tenant sense but rather a path/ID-consistency defect. Since I could not locate a per-job ACL enforcement mechanism in this codebase, this reduces to an isolation invariant violation of the REST resource hierarchy rather than a confirmed cross-tenant secret leak (there does not appear to be a per-job "owner" concept — jobs on a single Chainlink node belong to the same node operator).

### Impact Explanation
Impact is limited: it does not defeat authentication or the node-wide RBAC role check, since any authenticated user with access to `/v2/jobs/*/runs/*` already has access to the `Index` endpoint that lists all runs for any job ID they can query, and there is no per-job ownership boundary in the current session/role model. The finding is best characterized as a REST resource-path inconsistency (returning a resource whose parent does not match the requested path), not a Chainlink bounty-tier privilege escalation or secret-disclosure class, absent evidence of per-job ACLs in this codebase.

### Likelihood Explanation
Trivial to trigger for any authenticated caller who can already list/view job runs (which, given the flat role model observed, is the same population that could call `Index` for the target job's own ID and get the same information anyway).

### Recommendation
Have `Show` set `jobSpec.SetID(c.Param("ID"))` and verify `pipelineRun.PipelineSpec.JobID == jobSpec.ID` (or pass the job ID into a job-scoped `FindRun` variant) after fetching, returning 404 if they don't match, mirroring the scoping already done in `Index`.

### Proof of Concept
Handler-level Go test: create two jobs A and B via `App.AddJobV2`/`RunJobV2`, obtain run IDs `runA` (job A) and `runB` (job B), then issue `GET /v2/jobs/{A.ID}/runs/{runB}` with a valid session; assert the current behavior returns HTTP 200 with `runB`'s data (job B's payload) despite the path claiming job A, and that after the fix it returns 404.

```go
func (prc *PipelineRunsController) Index(c *gin.Context, size, page, offset int) {
	id := c.Param("ID")

	// Temporary: if no size is passed in, use a large page size. Remove once frontend can handle pagination
	if c.Query("size") == "" {
		size = 1000
	}

	var pipelineRuns []pipeline.Run
	var count int
	var err error

	ctx := c.Request.Context()
	if id == "" {
		pipelineRuns, count, err = prc.App.JobORM().PipelineRuns(ctx, nil, offset, size)
	} else {
		jobSpec := job.Job{}
		err = jobSpec.SetID(c.Param("ID"))
		if err != nil {
			jsonAPIError(c, http.StatusUnprocessableEntity, err)
			return
		}

		pipelineRuns, count, err = prc.App.JobORM().PipelineRuns(ctx, &jobSpec.ID, offset, size)
	}
```

```go
func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
	jsonAPIResponse(c, res, "pipelineRun")
}
```
