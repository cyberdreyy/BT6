### Title
Instant-withdraw receipts keyed to a stale epoch are excluded from default recovery basis, draining or freezing the reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` records receipt basis under `instantWithdrawsRequestsByEpoch[user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` at request time. `epochNumber` is incremented inside `deposit()` whenever the CDO deposits while `isEpochRunning()` (i.e., during `stopEpoch`). If the instant queue is only partially funded at that stop (`pendingInstantWithdraws != 0`, a case the code explicitly acknowledges), the still-unfunded receipts remain keyed under the old epoch while `epochNumber` has moved on. A later `finalizeDefaultRecovery` computes `defaultPendingClaimBasis()` using `instantWithdrawClaimsByEpoch[epochNumber]` — the new epoch key — so those receipts are silently dropped from the recovery basis, and `_claimDefaultedInstantWithdrawRequest` looks them up under `defaultRecoveryEpoch` (also the new key) and finds zero.

### Finding Description
Analogous to `kh_put_iv` dereferencing a corrupted handle — the write went to a valid structure under the wrong key — here accounting is written and later read under mismatched epoch keys:

- `requestInstantWithdraw` keys claims by the request-time `epochNumber` [1](#0-0) 
- `deposit()` bumps `epochNumber` when called during a running epoch (stopEpoch flow) [2](#0-1) 
- `defaultPendingClaimBasis` only adds `instantWithdrawClaimsByEpoch[epochNumber]` — the current key — even though `pendingInstantWithdraws` (the unfunded remainder) is global and still includes the older-epoch receipts [3](#0-2) 
- `defaultRecoveryEpoch` is set to the current `epochNumber` at finalization, and `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`, so the stale-keyed claim is never haircutted [4](#0-3) [5](#0-4) 

Sequence: epoch N running → user calls `requestInstantWithdraw` (basis keyed under N) → `stopEpoch` funds the instant queue only partially (the code's own comment at `_defaultPrefundedInstantReserve` confirms partial coverage is possible) → `deposit()` during stopEpoch sets `epochNumber = N+1` → borrower defaults in epoch N+1 → `finalizeDefaultRecovery` runs. The epoch-N instant claims are absent from `totalBasis`, so `recoveryPrice = reserve / totalBasis` is computed against too small a basis.

### Impact Explanation
Two fund-impacting outcomes, both broken "one receipt, one haircutted payout" invariants:

1. If the stale-keyed user's claim would consume default reserve, `_transferFundedClaim` reverts (`balance - reserve < amount`), permanently freezing that user's withdrawal — their receipt tokens are burned-claimable only through a path that always reverts.
2. If the strategy holds other funded underlyings, the user is paid at par while legitimate defaulted claimants share only `defaultRecoveryPrice < 1` — a direct wealth transfer and reserve drain; conversely, if the receipt was unfunded, the overstated `recoveryPrice` (basis too small) overpays earlier default claimants and leaves the reserve short for later ones, i.e., insolvency for the last claimants.

### Likelihood Explanation
Requires: an instant withdrawal that survives a `stopEpoch` partially unfunded (explicitly supported: `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0`), followed by a borrower default in a later epoch. No privileged misbehavior needed — the borrower default path is an in-scope scenario and the epoch-key rollover happens automatically in `deposit()`. The attacker merely holds a normally-acquired receipt and claims first.

### Recommendation
In `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest`, account for unfunded instant receipts across all epochs, not just `epochNumber` — e.g., track a global `instantWithdrawClaimsTotal` updated on request/claim/collect and use it as the default-epoch basis, or iterate/accumulate per-epoch keys. Alternatively, roll a user's pending instant basis forward into the new `epochNumber` key inside `deposit()`/`stopEpoch` when `pendingInstantWithdraws` remains non-zero.

```solidity
pragma solidity 0.8.10;
import "../TestIdleCDOBase.sol"; // existing fork harness

contract StaleEpochInstantClaimPoC is TestIdleCDOBase {
  function test_staleEpochInstantClaimExcludedFromDefaultBasis() public {
    // --- Epoch N: running ---
    // user (KYC'd lender) deposits via CDO, then requests instant withdraw of 1000 underlyings
    _depositWithTranche(AA, user, 1000 * ONE_SCALE);
    vm.prank(address(idleCDO));
    strategy.requestInstantWithdraw(1000 * ONE_SCALE, user);
    // instantWithdrawsRequestsByEpoch[user][N] == 1000e18, instantWithdrawClaimsByEpoch[N] == 1000e18

    // --- stopEpoch: CDO only partially funds instant queue ---
    // getInstantWithdrawFunds covers only part; pendingInstantWithdraws stays > 0
    // deposit() during stopEpoch sees isEpochRunning() -> epochNumber becomes N+1
    vm.prank(owner);
    idleCDO.stopEpoch(); // with borrower returning insufficient instant funds
    assertEq(strategy.epochNumber(), N + 1);
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // --- Borrower defaults in epoch N+1; recovery is finalized ---
    _simulateBorrowerDefault();
    vm.prank(owner);
    idleCDO.finalizeDefaultRecovery(recovered, recoverySource);

    // BUG 1: user's epoch-N claim is not in totalBasis:
    // defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[N+1] (==0)
    // -> defaultRecoveryPrice is overstated
    uint256 price = strategy.defaultRecoveryPrice();
    assertGt(price, expectedTrueHaircut); // priced as if the 1000e18 claim did not exist

    // BUG 2: user calls claimInstantWithdrawRequest -> _claimDefaultedInstantWithdrawRequest
    // reads instantWithdrawsRequestsByEpoch[user][N+1] == 0 and skips the haircut,
    // then pays instantWithdrawsRequests[user] at par via _transferFundedClaim:
    // - either reverts because it would dip into defaultRecoveryReserve (funds frozen forever)
    // - or pays 100% while honest defaulted claimants receive `price` < 1 (theft of recovery)
    vm.prank(address(idleCDO));
    strategy.claimInstantWithdrawRequest(user); // expect: reserve drained OR permanent NotAllowed revert
  }
}
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
