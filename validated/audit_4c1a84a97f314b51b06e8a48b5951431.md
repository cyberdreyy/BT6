### Title
`parse_transfer_fee_instruction`/`parse_signers` mislabels a non-signer account as `authority`/`multisigAuthority` for `TransferCheckedWithFee` - ([File: transaction-status/src/parse_token/extension/transfer_fee.rs])

### Summary
`parse_transfer_fee_instruction` decodes `TransferCheckedWithFee` by blindly treating `account_indexes[3]` as the transfer authority and delegating to `parse_signers`, which only branches on the *number* of remaining account indexes (single vs. multisig) rather than verifying `account_keys.is_signer()`/message-header signer status for that position. A transaction can be crafted where the account occupying index 3 is not actually a signer, yet `jsonParsed` output will still report it under `authority` (or `multisigAuthority`), because the field is populated purely positionally.

### Finding Description
`parse_token` dispatches into `parse_transfer_fee_instruction` (transaction-status/src/parse_token/extension/transfer_fee.rs, `TransferCheckedWithFee` arm) after only checking `check_num_token_accounts(account_indexes, 4)`, i.e. that there are at least 4 account indexes and that the max index is within `account_keys` bounds [1](#0-0) [2](#0-1) . It then calls `parse_signers(map, 3, account_keys, account_indexes, "authority", "multisigAuthority")`, which — based on the test-observed behavior — decides single vs. multisig purely by whether more account indexes exist past position 3, and unconditionally maps `account_keys[account_indexes[3]]` into the `authority` (or `multisigAuthority`) JSON field, with no call to any signer-status check against the compiled instruction/message header (`AccountKeys`/`is_signer`) [3](#0-2) .

Because the SPL Token(-2022) program itself enforces the actual "must be a signer" constraint at execution time (returning `MissingRequiredSignature` if the account passed as authority isn't a signer), a transaction with a non-signer account at index 3 is a syntactically valid, fee-payer-signed transaction that either: (a) is submitted via `simulateTransaction` with `encoding: jsonParsed` — where the parsed instruction fields are derived from the raw `CompiledInstruction` independent of simulated execution outcome — or (b) actually lands on-chain as a *failed* transaction (`meta.err` set) that is still retrievable via `getTransaction` with `jsonParsed` encoding, since failed transactions and their parsed instruction info are preserved in the ledger/blockstore.

In both reachable paths, `parse_signers` reports the destination (or any other non-signing account placed at index 3) as `authority`, without any indication that it is not a validated signer.

### Impact Explanation
This falls under the "decoder ... misreporting" category in scope. A downstream integrator (explorer, indexer, compliance tool) relying on `jsonParsed` `authority`/`multisigAuthority` fields from `getTransaction`/`simulateTransaction` to establish who authorized a token-fee transfer can be misled into attributing authorization to an account that never signed anything. The impact is confined to metadata misrepresentation; it does not affect consensus, validator liveness, or account state.

### Likelihood Explanation
Fully feasible with a single unprivileged RPC call: an attacker only needs to construct a `TransferCheckedWithFee` instruction whose 4th account is an arbitrary non-signer pubkey (this doesn't require the transaction to succeed) and send it once via `simulateTransaction` (`encoding: jsonParsed`), or have it included on-chain as a failed transaction and later fetched via `getTransaction` (`encoding: jsonParsed`). No special privileges, staking, or elevated access are needed, and it is repeatable at will.

### Recommendation
In `parse_signers` (transaction-status/src/parse_token.rs), before labeling the account at `index` as the sole `authority`, verify the account's actual signer status using `account_keys.is_signer(account_indexes[index] as usize)` (or equivalent message-header signer metadata) rather than inferring single-vs-multisig purely from `account_indexes.len()`. If the account is not a signer, either fall back to the multisig-authority path (which already treats the account as non-signing) or surface it distinctly (e.g. an `unexpectedNonSignerAuthority` marker) so downstream consumers are not misled.

### Proof of Concept
```rust
// transaction-status/src/parse_token/extension/transfer_fee.rs (added test)
#[test]
fn test_transfer_checked_with_fee_nonsigner_authority_mislabeled() {
    use solana_message::{CompiledInstruction, Message, MessageHeader};

    let source = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let destination = Pubkey::new_unique();
    let fake_authority = Pubkey::new_unique(); // NOT a signer

    // Manually build account_keys/message so `fake_authority` is placed
    // at position 3 of the instruction's accounts but is NOT within the
    // signer prefix of the message header.
    let account_keys = vec![/* fee payer (signer) */ Pubkey::new_unique(), source, mint, destination, fake_authority];
    let header = MessageHeader {
        num_required_signatures: 1, // only the fee payer signs
        num_readonly_signed_accounts: 0,
        num_readonly_unsigned_accounts: 3,
    };
    let data = /* TransferFeeInstruction::TransferCheckedWithFee pack */ vec![/* ... */];
    let compiled_ix = CompiledInstruction {
        program_id_index: 5, // spl-token-2022 program id appended
        accounts: vec![1, 2, 3, 4], // source, mint, destination, fake_authority
        data,
    };

    let account_keys = AccountKeys::new(&account_keys, None);

    // fake_authority (index 4 in account_keys) is not a signer.
    assert!(!account_keys.is_signer(4));

    let parsed = parse_token(&compiled_ix, &account_keys).unwrap();

    // BUG: parser reports fake_authority as "authority" despite it not
    // being a signer in the message header.
    assert_eq!(
        parsed.info["authority"],
        json!(fake_authority.to_string())
    );
    // Expected (fixed) behavior: this assertion should fail once the fix
    // verifies signer status and refuses to report a non-signer as
    // "authority".
}
```
Expected outcome pre-fix: the test passes, confirming `authority` is populated from a non-signer account purely by position. Post-fix, `parse_signers` should require `account_keys.is_signer(...)` to be true before using the `authority` field, causing this assertion to fail (or the field to be routed elsewhere).
