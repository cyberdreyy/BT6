### Title
KYC credential TOCTOU: withdraw claims pay out without re-checking `isWalletAllowed` — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`requestWithdraw` gates withdrawal eligibility with `isWalletAllowed(msg.sender)` (Keyring credential check) at request time, but the payout functions `claimWithdrawRequest` and `claimInstantWithdrawRequest` — called at least one full epoch (30+ days) later — never re-verify the credential. A lender whose Keyring credential is revoked between request and claim can still withdraw funded underlying from `IdleCreditVault`. This mirrors the SWUpdate TOCTOU: a validation (signature/credential check) is performed at time T0, while the privileged action (execution/payout) consumes the stale validation at T1 after the checked condition has changed.

### Finding Description
In `IdleCDOEpochVariant.requestWithdraw`, eligibility is checked once: `(_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) || !isWalletAllowed(msg.sender)` [1](#0-0) . The same single-point check exists in `_deposit` and `depositDuringEpoch` [2](#0-1) . `isWalletAllowed` is a live external call to the Keyring contract: `IKeyring(_keyring).checkCredential(keyringPolicyId, _user)` [3](#0-2) .

The claim paths contain no such check: `claimWithdrawRequest` just forwards `msg.sender` to the strategy [4](#0-3) , and `claimInstantWithdrawRequest` only checks `allowInstantWithdraw` [5](#0-4) . In `IdleCreditVault`, both claim functions burn the receipt and call `_transferFundedClaim`/`_transferDefaultRecovery` unconditionally once epoch gating passes [6](#0-5) .

The design intentionally inserts a long delay between check and use: normal receipts must wait at least one epoch (`epochNumber <= lastWithdrawRequest` reverts) [7](#0-6) , and instant receipts wait for `instantWithdrawDelay` funding. This delay is the TOCTOU window: any credential revocation, sanctions listing, or policy update applied to the Keyring registry during that window is never re-evaluated before cash leaves the vault.

### Impact Explanation
A wallet that becomes non-compliant (revoked credential, sanctions hit, policy change) after requesting a withdraw still receives full underlying payout from the strategy's funded reserve — including `defaultRecoveryReserve` payouts via `_claimDefaultedWithdrawRequest`/`_claimPostDefaultWithdrawRequest` [8](#0-7) . For a regulated credit vault whose entire access model is Keyring credentialing, the enforcement is illusory at the point where value actually leaves the system. Loss magnitude equals the claimant's funded receipt basis; systemically it means the funded withdrawal reserve can be drained to wallets the protocol's own compliance layer has already disqualified.

### Likelihood Explanation
Requires a Keyring credential revocation to land between request and claim — a routine administrative event, not an attacker-controlled primitive, so likelihood is moderate. However the window is structurally guaranteed to exist (minimum one full epoch plus buffer for normal claims, `instantWithdrawDelay` for instant claims), and once defaulted/closed the pool pays claims for an unbounded time after revocation. No existing guard compensates: `requestWithdraw`'s post-default revert (`_hasWithdrawRequest` check), the skim, and epoch gating are all orthogonal to credential validity.

### Recommendation
Re-run `isWalletAllowed(msg.sender)` inside `claimWithdrawRequest` and `claimInstantWithdrawRequest` in `IdleCDOEpochVariant` before forwarding to the strategy, so the credential state is checked at time-of-use rather than relying on the stale time-of-check. If revocation during the mandatory wait should not strand users, define explicit policy (e.g., allow claim to a still-allowlisted address) — but do not pay out under a revoked credential silently.

### Proof of Concept
```solidity
// Foundry fork test against an IdleCDOEpochVariant deployment with keyring set.
function testKycToctouOnClaim() external {
    // Setup: pool between epochs (buffer phase), USER holds AA tranches and is KYC'd.
    // 1) USER requests withdraw while credential is valid -> passes isWalletAllowed.
    vm.prank(USER);
    uint256 basis = cdo.requestWithdraw(aaBal, address(AAtranche));

    // 2) Epoch runs and stops; request funded via collectWithdrawFunds.
    _startEpoch();
    vm.warp(cdo.epochEndDate() + 1);
    vm.prank(manager);
    cdo.stopEpoch(0, 0); // borrower repays, pendingWithdraws funded into strategy

    // 3) Keyring admin revokes USER's credential after funding.
    keyringMock.revoke(keyringPolicyId, USER);
    assertFalse(cdo.isWalletAllowed(USER));

    // 4) Despite revocation, USER still claims full funded amount.
    uint256 balPre = underlying.balanceOf(USER);
    vm.prank(USER);
    cdo.claimWithdrawRequest(); // succeeds: no credential re-check
    assertEq(underlying.balanceOf(USER) - balPre, basis);
}
```

Caveat: the same gap exists for the instant-withdraw path (`claimInstantWithdrawRequest`) and for defaulted-epoch claims (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`, `_claimPostDefaultWithdrawRequest`), all of which pay from funded reserves without consulting `isWalletAllowed`. Whether revoked-but-claimable is treated as a loss event depends on the compliance model, but mechanically the checked condition and the consuming action are separated by a full epoch with no re-validation — the exact structure of the reported TOCTOU class.
