### Title
Client-Controlled `MessageId` Enables Cross-User Response Confusion in Gateway WebAPI Handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The Connext report describes a single caller-supplied parameter (`slippageTol`) being reused across two unrelated protection contexts, letting one value's misuse corrupt a second, independent operation. The analogous flaw in this repo is the Gateway's `WebAPIHandler`, which uses a single caller-supplied `MessageId` both as the correlation key for delivering a DON node's response back to the originating unprivileged HTTP client and as the sole binding between a request and its callback, with no per-sender/session scoping or uniqueness enforcement.

### Finding Description
`Message.Validate()` only checks that `MessageId` has a non-zero, bounded length and doesn't end in a null byte — it never ties the ID to a specific caller/session, nor rejects collisions with in-flight IDs: [1](#0-0) 

`HandleLegacyUserMessage` (reachable from any unprivileged client hitting the gateway's user-facing endpoint) stores the caller's callback keyed purely by this client-supplied `msg.Body.MessageId`, unconditionally overwriting any prior entry for that key with no uniqueness/ownership check: [2](#0-1) 

When a DON node later responds with `MethodWebAPITrigger`, `handleWebAPITriggerMessage` looks up and deletes the callback solely by `MessageId` and forwards the node's response to whichever callback is currently associated with that ID — again with no verification that the response corresponds to the same sender who registered the callback: [3](#0-2) 

Because the map (`h.savedCallbacks`) is shared globally across all users of a DON and keyed only by an attacker-chosen string, two independent unprivileged callers who submit requests with the same `MessageId` (accidentally or intentionally) will collide: the second registration silently overwrites the first at line 412, so the earlier caller's callback is discarded and never receives a response (or, depending on timing, the second registration is what receives the node's answer intended in response to the first request's outbound message id).

### Impact Explanation
This produces cross-user response confusion / hijacking of another user's pending gateway request: an unprivileged client can pick a `MessageId` value expected/likely to be used by another concurrent caller (or race to register first) to clobber that caller's callback, causing that caller's request to silently hang/never complete, or to have their in-flight callback slot claimed by the attacker, who then receives whatever response the DON returns for that message id instead of the legitimate requester. This is a request/response integrity violation at the gateway, an internet-facing component that brokers between unprivileged HTTP clients and DON capability nodes.

### Likelihood Explanation
`MessageId` is fully attacker-controlled input in the signed message body and is never checked for global uniqueness or bound to the submitting sender before being used as the sole callback-map key, so the collision is trivially reproducible by any unprivileged client that can predict or brute-force another client's message id, or by two clients racing with the same id. No privileged access or node-level compromise is required — the bug is client-request reachable.

### Recommendation
Scope callback correlation to `(sender, MessageId)` (or another unguessable, gateway-generated correlation token) rather than `MessageId` alone; reject registration when a live (non-expired) `MessageId` collision already exists instead of silently overwriting; and validate that a node's response `MessageId` is delivered only to the callback registered by the same original sender.

### Proof of Concept
1. Attacker sends a `HandleLegacyUserMessage` request with `message_id = "X"` to the gateway targeting a DON, registering `savedCallbacks["X"] = attackerCallback` (`core/services/gateway/handlers/capabilities/handler.go:411-414`).
2. Before the DON responds, a legitimate user's independent request also uses (or is forced by the attacker to reuse) `message_id = "X"`, overwriting `savedCallbacks["X"]` with `victimCallback`.
3. When the DON later returns the response tagged with `MessageId = "X"` (intended as the reply to the attacker's original request), `handleWebAPITriggerMessage` looks it up by ID only and delivers it to whichever callback is currently stored — resulting in either the attacker's original response being lost, or the victim receiving a response not generated for their request (or vice versa), demonstrating cross-user response confusion at `core/services/gateway/handlers/capabilities/handler.go:148-162`.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
