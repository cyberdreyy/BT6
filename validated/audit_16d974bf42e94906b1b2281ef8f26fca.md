### Title
Loss-adjusted withdraw receipts are keyed to the wrong epoch, letting pending withdrawers claim at par after a stopEpoch loss — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` has already been incremented by `deposit()` inside the same `stopEpoch` flow. User receipts are indexed by `lastWithdrawRequest[_user]`, which was stamped with the pre-increment epoch at `requestWithdraw` time. The two records disagree on which epoch "owns" the loss boundary — the same class of bug as the CRLF/chunk-boundary desync in the reference advisory: two parsers of the same stream assign a record to different boundaries. The result is that `_claimLossAdjustedWithdrawRequest` never matches a loss-adjusted receipt and the funded-claim path pays the full basis at par.

### Finding Description
The lifecycle is:

1. During running epoch `N`, a user calls `requestWithdraw` on the CDO; `IdleCreditVault.requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` (= `N`) and records `withdrawsRequests[_user][N]` / `withdrawsRequests[_user]` (`IdleCreditVault.sol:260–294`). [1](#0-0) 
2. At `stopEpochWithDuration(_lossAmount)`, the CDO calls back into the strategy. `deposit()` detects `isEpochRunning()` and executes `epochNumber += 1` — the counter now reads `N+1` (`IdleCreditVault.sol:607–611`). [2](#0-1) 
3. `collectWithdrawFunds(_amount)` with `_amount < pendingWithdraws` then writes `lossRecoveryPriceByEpoch[epochNumber]` — i.e., under key `N+1`, while every pending receipt is stamped `N` (`IdleCreditVault.sol:411–429`). [3](#0-2) 
4. On `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = `0` and returns early (`IdleCreditVault.sol:789–801`). [4](#0-3) 
5. Execution falls into `_claimFundedWithdrawRequest`, whose gate `epochNumber <= lastWithdrawRequest[_user]` now passes (`N+1 > N`), and it pays `withdrawsRequests[_user]` at par from the strategy balance (`IdleCreditVault.sol:319–350`). [5](#0-4) 

Note the asymmetry that confirms the boundary bug: APR0 state is keyed consistently because `prepareStopEpochWithApr0` runs *before* the increment (`apr0RateByEpoch[epochNumber]` written under `N`, matching `principalEpoch == N` and the `_reqEpoch >= epochNumber` settle gate at `IdleCreditVault.sol:537`, `545–565`), whereas `collectWithdrawFunds` runs *after* it. The loss-adjusted path is the only ledger on the wrong side of the epoch boundary. [6](#0-5) 

Caveat: I could not open `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` to confirm the exact call order (`prepareStopEpochWithApr0` → `deposit` → `collectWithdrawFunds`) because file contents for that section were not retrievable within the search budget. The finding holds if and only if `collectWithdrawFunds` executes after the `deposit()` that bumps `epochNumber`, which is the natural ordering (funds are collected after accounting is deposited).

### Impact Explanation
Insolvency / direct overpayment. When the borrower funds only `_amount < pendingBasis` after a partial loss, each pending withdrawer is entitled to `basis * lossRecoveryPrice / RECOVERY_FULL`. Because the haircut record is unreachable, every claimant receives the full `basis`. The first claimants drain the strategy's collected `(_amount)` plus any other held underlying (including default-recovery reserve via `_transferFundedClaim`/`_transferDefaultRecovery` paths at `IdleCreditVault.sol:897+`), and later claimants' transfers revert on insufficient balance — permanent freezing of unclaimed yield for the tail claimants and theft of the unapplied loss (quantified: `pendingBasis − _amount`, i.e., the entire `pendingLoss` computed in `previewLossAdjustedWithdrawFunds`). The "BB-first loss" waterfall invariant and the "one receipt one haircut payout" invariant are both broken.

### Likelihood Explanation
Requires only: an epoch with pending withdraw requests and a `stopEpochWithDuration(_lossAmount)` where the borrower returns less than `pendingBasis` — an ordinary partial-loss stop, performed by the honest manager/borrower. The attacker is any unprivileged tranche holder with a pending withdraw request; no privileged misbehavior is needed. Any KYC-passing lender who requests a withdraw in a lossy epoch triggers it.

### Recommendation
Key the loss record by the epoch the receipts were created in, not the post-increment counter. Either (a) record `lossRecoveryPriceByEpoch[epochNumber - 1]` (or capture the pre-increment epoch before `deposit()`), or (b) stamp receipts with the epoch in which they will be funded (`lastWithdrawRequest[_user] = currentEpoch + 1` for pending-funded receipts), consistent with how `apr0RateByEpoch` is written pre-increment. Add a regression test asserting `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` immediately after a lossy stop.

### Proof of Concept
```solidity
// Foundry fork test against mainnet-deployed IdleCreditVault + IdleCDOEpochVariant
function testLossReceiptKeyedToWrongEpoch() external {
    // 1. depositAA(amount); startEpoch(); -> running epoch N
    // 2. requestWithdraw(trancheAmount, AA) as unprivileged user
    //    => lastWithdrawRequest[user] == N, pendingWithdraws == requested
    uint256 epochAtRequest = strategy.epochNumber();
    assertEq(strategy.lastWithdrawRequest(user), epochAtRequest);

    // 3. warp past epochEndDate; borrower repays partially so that
    //    collectWithdrawFunds(_amount) is called with _amount < pendingBasis
    //    via cdoEpoch.stopEpochWithDuration(loss, ...)
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(underlying, borrower, fundedAmountLessThanPending);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(lossAmount, 0);

    // 4. BUG: loss price is stored under N+1, receipt is stamped N
    assertEq(strategy.lossRecoveryPriceByEpoch(epochAtRequest), 0);        // receipt's epoch: no loss
    assertGt(strategy.lossRecoveryPriceByEpoch(epochAtRequest + 1), 0);    // haircut orphaned one epoch ahead

    // 5. user claims FULL basis instead of basis * lossRecoveryPrice
    uint256 balPre = IERC20(underlying).balanceOf(user);
    cdoEpoch.claimWithdrawRequest();   // does not revert: epochNumber (N+1) > lastWithdrawRequest (N)
    assertEq(IERC20(underlying).balanceOf(user) - balPre, fullRequestedBasis); // should be haircut
}
```

If step 4 shows the haircut stored under `epochAtRequest` instead (i.e., `collectWithdrawFunds` runs before the `epochNumber` increment inside `stopEpoch`), the finding does not hold and should be downgraded; that ordering must be confirmed in `IdleCDOEpochVariant.stopEpochWithDuration`.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
