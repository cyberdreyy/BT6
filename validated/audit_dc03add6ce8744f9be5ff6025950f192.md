### Title
Non-constant-time session token comparison enables timing side-channel to recover another job's session `Token` - (File: session/session.go)

### Summary
`Session.withAuthorization` in [1](#0-0)  compares the session `Token` against the client-supplied `Authorization` header using Go's built-in `!=` string operator, which is not constant-time. No `crypto/subtle.ConstantTimeCompare` or `hmac.Equal` is used anywhere in the runner codebase for this check, confirmed by the absence of any `subtle.` usage in the repository.

### Finding Description
`generateEndpoint`/`generateToken` create both the session path and the `Token` from `helpers.GenerateRandomUUID(32)` (32 random bytes hex-encoded to a 64-character string), as seen in [2](#0-1) . Both the `/exec` and `/proxy/` handlers are wrapped with `withAuthorization` at registration time in `setMux`: [3](#0-2) . The check itself,
```go
if s.Token != r.Header.Get("Authorization") {
```
at [4](#0-3) , is a plain Go string inequality. Go's runtime string-equality implementation (`runtime.memequal`) compares length first and, for equal-length inputs, performs a linear/word-wise byte scan that can return as soon as a mismatch is found — this is the classic non-constant-time comparison pattern (CWE-208). No other check (rate limiting, constant-time compare, or generic response delay) exists in `withAuthorization` to mask this signal; on failure it immediately writes a 401 with `http.Error`, with no artificial timing normalization.

An attacker who already knows (or is given, per the question's stated precondition) the target job's session endpoint path and can reach the `SessionServer.AdvertiseAddress` could, in principle, send many requests with different candidate `Authorization` values and use response-latency statistics to infer whether a given prefix of their guess matches the real token, incrementally narrowing the 256-bit token search space byte-by-byte instead of needing the full keyspace.

### Impact Explanation
If a practical distinguishable timing signal exists, the scoped impact is real: an attacker recovering the full session `Token` for a job they don't own can attach to that job's interactive terminal via `execHandler`, or reach `proxyHandler` to interact with that job's service containers — a cross-job session hijack, matching the "job/session/trace/backend auth state must not let one job impersonate another" invariant.

### Likelihood Explanation
Feasibility is low but not purely academic. Preconditions required: (1) network reachability to the specific session server for a job the attacker does not own, and (2) prior knowledge of that job's 64-hex-character session endpoint path (itself an independent 32-byte `GenerateRandomUUID` value not covered by this check) — this second precondition is a strong, separate requirement in real deployments since the endpoint is not otherwise guessable and is normally only disclosed to authorized viewers of that job. Even granting both, recovering a 64-character token via network timing requires resolving a per-byte/per-word timing signal that is typically on the order of nanoseconds against network/TLS/HTTP jitter on the order of microseconds-to-milliseconds, requiring very large sample counts per candidate byte and a low-jitter vantage point (e.g., same host/LAN) to be statistically distinguishable — consistent with the question's own "network-adjacent" precondition. This makes the attack theoretically valid but requires substantial statistical averaging and favorable network conditions to be practical.

### Recommendation
Replace the direct string comparison with a constant-time comparison, e.g.:
```go
if subtle.ConstantTimeCompare([]byte(s.Token), []byte(r.Header.Get("Authorization"))) != 1 {
```
(ensuring both operands are length-normalized/hashed first, since `ConstantTimeCompare` itself is not constant-time when lengths differ) or compare HMACs of both values. Consider also adding basic rate-limiting/backoff on repeated failed `Authorization` attempts to the session server.

### Proof of Concept
Go statistical timing test (to be run locally against a `httptest.Server` wrapping `Session.Handler()`):
1. Create a `Session` via `NewSession`, capture `s.Token`.
2. For N trials, send requests with `Authorization` equal to: (a) the correct token, (b) a token sharing the correct first `k` characters then random, (c) a fully random token — over a loopback/low-jitter connection.
3. Measure response latency for each category across thousands of trials; compute mean/variance.
4. Assert whether latency for (b) grows monotonically with `k` and is statistically distinguishable (e.g., via a t-test) from (c) — this would confirm a measurable side channel from the `!=` comparison at [4](#0-3) .
5. Re-run the same test after swapping in `subtle.ConstantTimeCompare` and confirm the timing distinguishability disappears, validating the fix.

```go
func (s *Session) withAuthorization(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		logger := s.log.WithField("uri", r.RequestURI)
		logger.Debug("Endpoint session request")

		if s.Token != r.Header.Get("Authorization") {
			logger.Error("Authorization header is not valid")
			http.Error(w, http.StatusText(http.StatusUnauthorized), http.StatusUnauthorized)
			return
		}

		next.ServeHTTP(w, r)
	})
}
```
