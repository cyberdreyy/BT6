### Title
Stale reorg-permit records let `Signer::reorg_permit_stands` permanently excuse a live, canonical conflict, letting a signer sign a genuine sibling block - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`SignerDb::mark_tenure_superseded` records that tenure `X` was legitimately reorged by permitting tenure `Y`, and `Signer::reorg_permit_stands` later excuses `X`'s signed block from the sibling-conflict guard as long as `Y`'s Bitcoin sortition remains canonical. But if `Y` itself is subsequently, legitimately reorged away (e.g. by tenure `Z`, which builds back onto `X`), `X`'s record is never updated or cleared — it still says "superseded by `Y`" — and `Y`'s Bitcoin sortition, once mined, stays canonical forever. This makes the permit for `X` stand indefinitely even though `X` is now live and canonical again, letting the pre-commit path skip `conflict_still_blocks`'s node-derived liveness check and sign a fresh sibling block at `X`'s height.

### Finding Description
The permit-tracking mechanism is:

- `SortitionData::check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs:170-295`) permits a tenure `Z` to reorg tenure `Y` if `Y` produced ≤1 globally accepted block and was poorly timed, then calls `record_superseded_tenure` (`chainstate/mod.rs:297-315`), which invokes `SignerDb::mark_tenure_superseded(Y.consensus_hash, ..., superseded_by = Z.consensus_hash, Z.burn_block_hash)`.
- `SignerDb::mark_tenure_superseded` (`stacks-signer/src/signerdb.rs:1642-1660`) does an `INSERT OR REPLACE` keyed only on the *superseded* tenure's consensus hash. It never inspects or updates any other tenure's row, and nothing ever chains/re-validates one permit against another.
- `Signer::reorg_permit_stands` (`stacks-signer/src/v0/signer.rs:1222-1248`) decides whether a recorded permit still excludes a conflict by asking only whether the *permitting* tenure's burn block (`superseded_by.burn_block_hash`) is still canonical via `get_sortition_by_burn_hash`. It does not check whether the permitting tenure is still the one actually replacing the conflict at the Stacks level.

Sequence that breaks the equality "permit stands ⇔ the permitting tenure is still what actually supersedes the conflict":

1. Tenure `X` mines and gets one block signed at height `h` (`X` is genuine, well-formed).
2. Tenure `Y` (next sortition) reorgs `X`. `Y` mines zero blocks (or is badly timed), so `check_parent_tenure_choice` legitimately permits the reorg and calls `mark_tenure_superseded(X, ..., superseded_by=Y)`. This is a correct decision at the time — `X` really is dead once `Y`'s chain is live.
3. Tenure `Z` (next sortition) reorgs `Y` *back onto* `X` (`Z.parent_tenure_id == X`). Because `Y` itself mined zero blocks (or was badly timed), this reorg is also legitimately permitted, and `mark_tenure_superseded(Y, ..., superseded_by=Z)` is recorded. Crucially, `X`'s row is untouched — `check_parent_tenure_choice` for `Z` only evaluates tenures between `prior_sortition` and `parent_tenure_id` exclusive of the parent, i.e. only `Y`, never `X`.
4. `X` is now live and canonical again (`Z` builds on it), but `SignerDb`'s record for `X` still reads `superseded_by = Y`. `Y`'s Bitcoin sortition, having actually occurred, remains canonical forever absent a real Bitcoin-level fork — so `reorg_permit_stands` for `X`'s conflict returns `true` permanently.
5. Any later block `W` proposed in an unrelated tenure `V` that happens to land at the same or lower height than `X`'s block (a genuine sibling, e.g. from a natural short Bitcoin race, not a reorg of `X`) reaches `handle_block_pre_commit`'s conflict scan (`stacks-signer/src/v0/signer.rs:1383-1421`). The scan finds `X` as a fresh conflict, but because `reorg_permit_stands(X)` returns `true`, the `&&` short-circuits and `conflict_still_blocks` (the only check that actually asks the node whether `X` is still reachable/canonical) is never invoked. The conflict is silently excluded and the signer proceeds to sign `W`.

This bypasses the intended backstop entirely: `conflict_still_blocks` would correctly report `X` as still live (its sortition is canonical and the node's chain still reaches it), which should hold `W` back exactly as documented ("A sibling at the same height therefore keeps blocking"). The stale permit short-circuits that node-derived truth.

### Impact Explanation
This breaks chain safety directly: a signer can be induced to place a valid signature on `W` while an already-signed, still-canonical block `X` occupies the same height in a sibling tenure — the exact double-sign scenario the sibling-conflict guard exists to prevent (per `docs/signer-flows.md` section 5: "signing both would be the double-sign this guard exists for"). If enough signer weight independently reaches the same stale-permit state (any signer that processed the `X→Y→Z` sequence will have the same stale row), a conflicting/duplicate block can be finalized, matching the Critical category ("a signer signing an invalid, non-canonical, or conflicting block"). The bug is repeatable: it reproduces for every subsequent sibling attempt at or above `h` as long as the stale record remains (it only clears via `prune_superseded_tenures` once the permitting tenure's burn height falls `MAX_FORK_DEPTH` (100) blocks below the tip).

### Likelihood Explanation
Preconditions are attacker-affordable with a single miner slot won repeatedly over consecutive sortitions plus normal gossip of proposals/pre-commits:
- Step 2 and 3 require winning two more consecutive/near-consecutive sortitions and choosing to mine zero (or badly-timed) blocks in `Y` — trivial for a miner who controls their own tenure content.
- Step 5 needs a genuine sibling at `X`'s height in an unrelated tenure; this can arise from an ordinary short Bitcoin-level race (not attacker-exclusive), which is common enough on Bitcoin's testnet/mainnet cadence, or the attacker can engineer it directly since they hold their own BTC hash power for a slot.
- No majority signer collusion, no auth_token, and no local host access are required — only crafting/timing of the attacker's own tenures and normal message gossip.

### Recommendation
`reorg_permit_stands` must verify liveness of the permitting tenure at the Stacks level, not merely Bitcoin-sortition canonicity. Either:
- Chain-invalidate `superseded_by` records when the permitting tenure is itself superseded (recursively re-point `X`'s permit to the tenure that ultimately still supersedes it, or clear it), or
- Change `reorg_permit_stands` to also confirm that the permitting tenure's tip (via `get_tenure_tip`) is still reachable/canonical from the node's current view, not just that its burn sortition occurred, so `conflict_still_blocks`-equivalent liveness reasoning is applied to the permitting tenure too.

### Proof of Concept
Rust test plan (extending `stacks-signer/src/v0/tests.rs` alongside `run_cross_tenure_scenario`/`SupersededPermitCanonical`):

```rust
#[test]
fn stale_reorg_permit_excuses_still_live_conflict() {
    // 1. Tenure X: block A signed at height h.
    // 2. mark_tenure_superseded(X, ..., superseded_by = Y) -- simulate a legitimate
    //    permit granted when Y (empty tenure) reorged X.
    // 3. mark_tenure_superseded(Y, ..., superseded_by = Z) -- simulate Z legitimately
    //    reorging Y *back onto* X (Y also produced 0 blocks). X's row is untouched.
    // 4. Mock node: Y's burn hash still resolves (canonical in Bitcoin history);
    //    X's own tenure tip/sortition also resolves live (Z really did build on X).
    // 5. Assert: signer.reorg_permit_stands(&stacks_client, conflict_over_A) == true
    //    even though X is verifiably live per the node.
    // 6. Propose sibling block W in tenure V at height h (or lower), drive pre-commit
    //    to threshold via handle_block_pre_commit, and assert block_info_w.state ==
    //    BlockState::LocallyAccepted / signed_self.is_some() -- i.e. the signer signed
    //    a conflicting sibling to the still-live A, instead of refusing per
    //    conflict_still_blocks.
}
```
Key assertions on both sides of the equality:
- Before fix: `reorg_permit_stands(conflict_over_A) == true` while `conflict_still_blocks(conflict_over_A, ...)` (evaluated directly) would return `true` (node still reaches `A`'s tenure) — demonstrating the two disagree and the wrong one wins.
- After fix: `reorg_permit_stands` returns `false` once `Y` is no longer the tenure actually superseding `X` (or the permit chain correctly resolves to `Z`, which does not supersede `X`), and the sibling `W` is correctly refused.
