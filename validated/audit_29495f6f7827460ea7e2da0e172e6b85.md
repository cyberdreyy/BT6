### Title
Distinguishable error response reveals disabled OIDC API-token feature vs. invalid token - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`oidcAuthenticator.FindUserByAPIToken` returns a distinct, non-generic error (`"API token is not enabled"`) when `UserAPITokenEnabled()` is false, whereas an invalid/unknown token produces `sql.ErrNoRows`. In `webauth.AuthenticateByToken`, only `sql.ErrNoRows` and `clsessions.ErrUserSessionExpired` are normalized to the generic `auth.ErrorAuthFailed`; any other error (including the "not enabled" error) is passed through unchanged to `jsonAPIError`, producing a different JSON error body for the same HTTP 401 status code.

### Finding Description
- An unauthenticated attacker can send any HTTP request to a route protected by `webauth.Authenticate(authr, webauth.AuthenticateByToken)` with arbitrary `X-API-KEY`/`X-API-SECRET` headers.
- `AuthenticateByToken` calls `authr.FindUserByAPIToken(ctx, token.AccessKey)` [1](#0-0) .
- In `oidcAuthenticator.FindUserByAPIToken`, if the OIDC API-token feature is disabled, the function short-circuits and returns `errors.New("API token is not enabled")` before ever touching the database [2](#0-1) .
- If the feature is enabled but the token does not exist, the underlying `tx.GetContext` query returns `sql.ErrNoRows`, which propagates unwrapped out of `FindUserByAPIToken` [3](#0-2) .
- Back in `AuthenticateByToken`, the error-mapping logic only normalizes `sql.ErrNoRows` and `clsessions.ErrUserSessionExpired` into the generic `auth.ErrorAuthFailed` message ("Authentication failed"); any other error (like the disabled-feature error) is returned as-is [4](#0-3) .
- `jsonAPIError` then serializes whichever error was returned directly into the JSON response body via `err.Error()`, so the two cases produce different response bodies even though both return HTTP 401 [5](#0-4) .

This is an oracle: sending any bogus API token pair to a node reveals, via the response body text, whether `UserAPITokenEnabled` is turned on for the OIDC auth driver, with zero credentials required — the request just needs to hit any token-protected route.

### Impact Explanation
This maps to a minor "sensitive information disclosure / feature-state leak" class rather than an authentication bypass: the attacker learns whether the OIDC API-token login path is enabled on the node, which could inform them whether pursuing token-guessing/brute-force against that surface is worthwhile versus wasting effort. It does not by itself grant access to any account, secret, or funds, and the same generic `401` status code (no privilege change) is returned in both cases — only the JSON error text differs.

### Likelihood Explanation
Trivial to exploit and fully repeatable: no valid credentials, session, or role are needed — a single unauthenticated HTTP request with a random API key/secret pair to any token-guarded endpoint is enough to observe the distinguishing error string. This is only reachable when the node's session/auth driver is configured to use OIDC (`oidcauth`); other drivers such as LDAP contain the analogous but differently worded issue (`ldapauth.FindUserByAPIToken` also returns a distinct `"API token is not enabled "` error not mapped to `sql.ErrNoRows`) [6](#0-5) .

### Recommendation
In `oidcAuthenticator.FindUserByAPIToken` (and the LDAP equivalent), return `sql.ErrNoRows` (or another sentinel already normalized by `AuthenticateByToken`, e.g. `clsessions.ErrUserSessionExpired`) instead of a bespoke `"API token is not enabled"` error when the feature flag is off, so that `AuthenticateByToken` maps both the disabled-feature and invalid-token cases to the same generic `auth.ErrorAuthFailed` response. Alternatively, update `webauth.AuthenticateByToken` to treat any non-nil error from `FindUserByAPIToken` uniformly as `auth.ErrorAuthFailed` (excluding true 5xx/system failures), ensuring uniform failure responses regardless of internal cause.

### Proof of Concept
Go table test in `core/web/auth/auth_test.go` style:
```go
func TestAuthenticateByToken_DisabledVsInvalidTokenUniformity(t *testing.T) {
    cases := []struct {
        name string
        err  error
    }{
        {"disabled_feature", errors.New("API token is not enabled")},
        {"invalid_token", sql.ErrNoRows},
    }
    var bodies []string
    for _, tc := range cases {
        authr := stubAuthProvider{err: tc.err}
        router := gin.New()
        router.Use(webauth.Authenticate(authr, webauth.AuthenticateByToken))
        router.GET("/", func(c *gin.Context) { c.String(http.StatusOK, "") })

        w := httptest.NewRecorder()
        req := mustRequest(t, "GET", "/", nil)
        req.Header.Set(webauth.APIKey, "any")
        req.Header.Set(webauth.APISecret, "any")
        router.ServeHTTP(w, req)

        assert.Equal(t, http.StatusUnauthorized, w.Code)
        bodies = append(bodies, w.Body.String())
    }
    // Currently FAILS: bodies[0] ("API token is not enabled") != bodies[1] (generic "Authentication failed")
    assert.Equal(t, bodies[1], bodies[0], "disabled-feature and invalid-token responses must be identical")
}
```
Expected (post-fix) assertion: both responses are byte-identical (`{"errors":[{"detail":"Authentication failed"}]}`), proving uniform-failure behavior.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
