### Title
`claimInstantWithdrawRequest` does not update `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, inflating default-recovery basis and phantom prefunded reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the Teller finding (where `_withdraw` moves funds but leaves `_bidCollaterals` stale, corrupting `getCollateralInfo`/`getCollateralAmount`), `IdleCreditVault.claimInstantWithdrawRequest` pays out an instant-withdraw receipt and clears only the per-user aggregate `instantWithdrawsRequests[_user]`, but never decrements the per-epoch trackers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. Those per-epoch trackers are exactly what `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` read during `finalizeDefaultRecovery`, so already-paid claims are counted again when a borrower default is finalized, corrupting both the recovery price and the reserve accounting.

### Finding Description
When a user claims a funded instant withdrawal, the function zeros `instantWithdrawsRequests[_user]`, burns the receipt, and transfers underlying — but leaves the epoch-level records untouched:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [1](#0-0) 

Neither `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` nor `instantWithdrawClaimsByEpoch[currentEpoch]` (both incremented in `requestInstantWithdraw`) is decremented. [2](#0-1) 

If the borrower later defaults in that same epoch while `pendingInstantWithdraws != 0` (i.e., the instant queue was only partially prefunded at `startEpoch`), finalization computes:

- `defaultPendingClaimBasis()` = `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — still including the already-claimed and already-paid amount. [3](#0-2) 

- `_defaultPrefundedInstantReserve()` = `instantClaimsByEpoch - pendingInstantWithdraws`, treating the paid-out portion as underlying still held by the strategy. [4](#0-3) 

`finalizeDefaultRecovery` then computes `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`. Both numerator and denominator are corrupted: the "prefunded" tokens were already transferred to the claimant (phantom reserve), and the basis counts a claim that no longer exists. [5](#0-4) 

Additionally, `_claimDefaultedInstantWithdrawRequest` keys off `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, which still holds the cleared claim. The only thing preventing a literal second payout is that the user's receipt tokens were already burned, so `_burn` reverts — meaning the stale record also DoS-blocks `claimInstantWithdrawRequest` for that user after finalization. [6](#0-5) 

### Impact Explanation
The phantom prefunded reserve inflates `recoveryPrice` above what actual holdings support. Early recovery claimants (any holder of defaulted-epoch receipts — unprivileged users) are paid at this overstated ratio via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` by the inflated payout while the real token balance is smaller. The final claimants' `safeTransfer` fails or they receive less than their fair share — a direct wealth transfer from later claimants to earlier ones and theft/permanent freezing of unclaimed recovery funds. Quantified loss = the already-claimed instant amount re-counted as both basis and reserve (up to the full prefunded instant queue of the defaulted epoch). [7](#0-6) 

### Likelihood Explanation
Requires a specific but legitimate sequence, all triggerable by honest privileged roles plus one unprivileged claimant: (1) APR drops by more than `instantWithdrawAprDelta` at a `stopEpoch`, enabling instant withdrawals; (2) users request instant withdrawals in epoch N; (3) the next `startEpoch` partially collects instant funds (`collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` only by what was funded); (4) a funded claimant calls `claimWithdrawRequest`/`claimInstantWithdrawRequest` — clearing the aggregate but not the per-epoch records; (5) the borrower fails to fund the following `stopEpoch`, triggering `_handleBorrowerDefault` → `finalizeDefault` → `finalizeDefaultRecovery` while `pendingInstantWithdraws != 0` and `epochNumber` still equals the request epoch. No guard prevents this: `defaultInstantWithdrawsFinalized` is set precisely when `pendingInstantWithdraws != 0`, and `_transferFundedClaim` explicitly permits spending the balance above the reserve.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch records alongside the aggregate, e.g. `instantWithdrawsRequestsByEpoch[_user][epoch] = 0` (using a stored request-epoch marker) and `instantWithdrawClaimsByEpoch[epoch] -= amount`, mirroring how `_claimDefaultedInstantWithdrawRequest` and `_clearWithdrawClaimForEpoch` maintain per-epoch bookkeeping. Alternatively, record the request epoch per user so the correct bucket can be decremented.

### Proof of Concept
A Foundry test in `test/foundry/IdleCreditVault.t.sol` (reusing `_startEpochAndCheckPrices`/`_stopEpochAndCheckPrices` helpers and the existing `stdstore` default-injection pattern from `testLazyInitializeClearsOnlyStaleClosedCounters`):

```solidity
function testStaleInstantEpochAccountingInflatesRecovery() external {
    // 1. Deposit AA+BB, run one epoch, stop with APR below
    //    lastEpochApr - instantWithdrawAprDelta to enable instant withdraws.
    idleCDO.depositAA(10_000 * ONE_SCALE);
    idleCDO.depositBB(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr - (cdoEpoch.instantWithdrawAprDelta() + 1), _expectedFundsEndEpoch());

    // 2. User requests instant withdraw (epoch N), receipt minted.
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));
    uint256 epoch = creditVault.epochNumber();

    // 3. startEpoch partially collects instant funds so that
    //    pendingInstantWithdraws > 0 but > 0 was funded; user claims the funded part.
    //    (drive via manager startEpoch with limited borrower liquidity)
    vm.prank(user);
    cdoEpoch.claimInstantWithdrawRequest();

    // stale per-epoch records remain:
    assertEq(creditVault.instantWithdrawsRequestsByEpoch(user, epoch), requested); // BUG: not cleared
    assertEq(creditVault.instantWithdrawClaimsByEpoch(epoch), requested);          // BUG: not decremented

    // 4. Borrower defaults while pendingInstantWithdraws != 0 and epochNumber == epoch.
    //    Finalize recovery; observe recoveryPrice / reserve inflated by `requested`:
    //    defaultPendingClaimBasis() includes `requested` twice (once paid, once pending)
    //    and _defaultPrefundedInstantReserve() counts the paid amount as held reserve.
    // 5. First defaulted-epoch claimant is overpaid; last claimant's
    //    _transferDefaultRecovery safeTransfer reverts on insufficient balance.
}
```

The assertion on the stale `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` entries demonstrates the un-updated bookkeeping; the finalization step demonstrates the resulting overstated `recoveryPrice` and phantom `defaultRecoveryReserve`, leading to overpayment of early claimants and insolvency for later ones.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
