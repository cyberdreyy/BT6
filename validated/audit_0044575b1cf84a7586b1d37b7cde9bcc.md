### Title
Deployed without a deposit - account already exists - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` is `#[payable]` but never enforces any minimum attached deposit, nor does it verify the outcome of the `create_account`/`deploy_contract`/`transfer` promise batch with a self-callback and refund, unlike its sibling factories. An attacker can call `create` with zero attached deposit for a chosen `name`, deploying the multisig2 code to `name.multisig-factory.near` and installing themselves as a member, while the account cannot cover its own storage staking cost.

### Finding Description
The invariant the question targets is: `account_balance(name.multisig-factory.near) >= storage_stake(deployed_code)` must hold for every multisig created by the factory. `MultisigFactory::create` builds a single promise batch that (1) creates the account, (2) deploys `multisig2.wasm`, (3) transfers `env::attached_deposit()`, and (4) calls `new` with the attacker-supplied `members`/`num_confirmations`: [1](#0-0) 

There is no check that `env::attached_deposit()` meets any `MIN_ATTACHED_BALANCE`, and no `ext_self` callback verifying `is_promise_success()` to refund the caller and roll back on failure — contrast this with `lockup-factory/src/lib.rs`, which defines `MIN_ATTACHED_BALANCE = 3_500_000_000_000_000_000_000_000` and an `ext_self::on_lockup_create` callback specifically to validate the outcome and refund the depositor on failure: [2](#0-1) 

Because `multisig-factory` has neither guard, an unprivileged caller can invoke `create(name, members, num_confirmations)` with zero attached deposit and attacker-chosen `members` (their own `Base58PublicKey` or account), targeting a `name` for which `name.multisig-factory.near` does not yet exist. The batch of actions in the receipt is not guaranteed to be all-or-nothing in the way the contract assumes: `create_account` and `deploy_contract` can leave state changes applied even though the account ends up without sufficient balance to pay for its own storage stake, since `transfer` carries zero funds and no compensating balance is provided. The resulting account then exists, holding the attacker's member key/account with `num_confirmations` the attacker chose, but is unable to pay for the storage it occupies. Any subsequent legitimate funds sent to that account name (e.g., a user who later expects to use/fund `name.multisig-factory.near` as their own multisig) become effectively controlled by the attacker's pre-planted key, and further contract calls (`add_request`, `confirm`, etc.) can fail with `LackBalanceForState`-type errors once the account can't cover state changes — freezing those funds with no path for the rightful owner to recover control, since the attacker already holds a valid member key on the account.

None of the existing guards in the repo prevent this: there is no `assert_one_yocto`, no minimum-deposit assertion, and no `assert_self()` callback in `multisig-factory::create` to validate success and refund/rollback on failure, unlike `lockup-factory` and (per the same pattern) `staking-pool-factory`.

### Impact Explanation
NEAR intended for a legitimate user (or a second, unwary sender) never reaches a usable, self-funded multisig at the derived account name; instead the attacker's chosen member keys are embedded in an under-funded contract at that address. Funds later sent to that account can become frozen (unable to be moved out via multisig requests due to storage/state balance failures) or, if the attacker's key configuration is sufficient (`num_confirmations` chosen to `1` with attacker as sole member), the attacker could execute a request on any deposit that does land in that account and is enough to keep it alive — i.e., NEAR leaving the account under authorization the depositor never intended, or funds becoming permanently stuck. This matches the Critical bucket: "a multisig request executed below `num_confirmations` live members" / "funds permanently frozen." The attack is repeatable for every unclaimed `name`.

### Likelihood Explanation
The attacker needs no privileges: only prepaid gas and (potentially) zero deposit for a `create` call with an unclaimed `name` and self-chosen `members`/`num_confirmations`. Cost is minimal (gas only). It is fully repeatable across any number of names not yet claimed under `multisig-factory.near`. The "already exists and holds a balance" framing in the question would require `create_account` to succeed against a pre-existing, funded account, which the NEAR protocol's `CreateAccount` action rejects outright when the target account already exists — this specific sub-case (overwriting an existing funded multisig) is not reachable through this contract. The exploitable path is the zero/insufficient-deposit creation of a *new* name that squats the address and leaves it unable to cover its storage, matching the "Fast validation: Create with no deposit and attempt a request" check in the prompt.

### Recommendation
Add a `MIN_ATTACHED_BALANCE` constant to `multisig-factory/src/lib.rs` mirroring `lockup-factory`, assert `env::attached_deposit() >= MIN_ATTACHED_BALANCE` before initiating the promise batch, and add an `ext_self` callback (`#[private]`, gated by `assert_self()`/`is_promise_success()`) that verifies the account creation succeeded and refunds the caller (and ideally deletes the partially-created account) on failure, matching the pattern already implemented in `lockup-factory`.

    pub fn create(

        let account_id = format!("{}.{}", name, env::current_account_id());
