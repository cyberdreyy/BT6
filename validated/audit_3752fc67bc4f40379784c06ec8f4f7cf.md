## Analysis

The bug class from the report is: a permission/authorization check consumes or counts a credential that no longer reflects the current authoritative state (limited "uses" being spent for parties whose approval wasn't actually needed). The direct structural analog in this repo is in the multisig contracts: `confirmations` recorded against a request are never invalidated when the confirming member is removed from the multisig, so a stale (now non-member) confirmation is still counted toward the live `num_confirmations` threshold.

### Root cause

In `multisig2/src/lib.rs`, `delete_member()` only purges *requests originated by* the removed member — it never scrubs that member's entry out of the `confirmations` sets of *other* pending requests it had confirmed: [1](#0-0) 

Compare with `confirm()`, which blindly trusts the size of the stored `confirmations` set against the *current* `num_confirmations` threshold, without verifying that every entry in that set is still a current member: [2](#0-1) 

The equivalent legacy contract has the same gap — `DeleteKey` only removes requests where `r.signer_pk == pk` (requests originated by that key), not confirmations the key placed on other pending requests: [3](#0-2) [4](#0-3) 

This breaks the intended equality: `execute if |{live members who confirmed}| >= num_confirmations`. Instead the code checks `|{historical confirmation entries, including removed members}| >= num_confirmations`, so a request can execute with fewer *live* member approvals than the threshold requires — directly matching the rules' explicit example, "confirmations counted versus live members," and the "Critical - a multisig request executed below threshold" impact bucket.

### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, letting a request execute below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm()` counts every entry stored in a request's `confirmations: HashSet<String>` against `self.num_confirmations`, but `delete_member()` never removes a departing member's confirmation entries from requests it did not originate. A pending request that received a confirmation from a member who is later removed keeps that confirmation "alive" in storage, so the request can reach the confirmation threshold and execute using fewer than `num_confirmations` currently-valid signatures.

### Finding Description
`delete_member()` only cleans up requests that the removed member originated (`r.member == member`) and its own `num_requests_pk` entry: [5](#0-4) 
It never iterates `self.confirmations` to strip the removed member's string from the `HashSet<String>` of requests *added by other members that this member had merely confirmed*.

`confirm()` then executes purely based on the stored set's cardinality: [6](#0-5) 
`confirmations.len() as u32 + 1 >= self.num_confirmations` treats every historical entry as an equally valid, currently-authorized signer, with no re-validation against `self.members`.

The intended custody binding is: *a request executes only when the number of confirmations from members who are currently part of the multisig meets `num_confirmations`.* The actual code enforces: *a request executes when the number of historically recorded confirmation strings (regardless of current membership) meets `num_confirmations`.* These diverge whenever membership changes between a confirmation and execution — exactly the "recorded claim vs. current entitlement" mismatch called out in the rules.

The legacy `multisig/src/lib.rs` contract has the identical defect via `DeleteKey`, which only purges requests signed by the removed key, not confirmations it placed on other requests: [7](#0-6) 

### Impact Explanation
This crosses the "threshold" authorization boundary explicitly listed as Critical impact: "a multisig request executed below threshold." A `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, `DeployContract`, etc. request can be pushed to execution with fewer live-member approvals than the multisig's own configured `num_confirmations`, meaning funds or privileged actions controlled by the multisig account can move without the number of *current* signers the multisig was designed to require.

### Likelihood Explanation
The trigger requires only ordinary, in-scope multisig operations available to legitimate members — no owner privilege beyond normal multisig membership, no redeploy, and no external actor. Any multisig that (a) has a partially-confirmed pending request and (b) later removes one of its confirmers (a routine membership rotation) is affected. Because member turnover in a k-of-n scheme is a normal operational event, the precondition is easily and naturally reached, not merely theoretical.

### Recommendation
When removing a member in `delete_member()`, iterate all entries in `self.confirmations` and strip the removed member's identifier from every set (not only the sets belonging to requests the member originated). Alternatively, have `confirm()` (and the pre-execution check) recompute the confirming set intersected with `self.members` before comparing against `num_confirmations`, so stale confirmations from removed members never count toward the threshold. Apply the analogous fix to `multisig/src/lib.rs`'s `DeleteKey` handling.

### Proof of Concept
1. Initialize `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `B` calls `add_request_and_confirm(R)` for a `Transfer` request → `confirmations[R] = {B}` (1/3).
3. `C` calls `confirm(R)` → `confirmations[R] = {B, C}` (2/3); execution not yet triggered.
4. Members `A, B, D` submit and confirm a separate request `DeleteMember { member: C }`, which passes (3 confirmations) and executes, removing `C` from `self.members`. `delete_member()` only scans for requests where `r.member == C` (none, since `C` didn't originate `R`), so `confirmations[R]` is left untouched, still containing `"C"`.
5. Members are now `[A, B, D]` (3 members, `num_confirmations` still 3).
6. `A` calls `confirm(R)`. Code computes `confirmations[R].len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request(R)` runs the `Transfer`, even though only `A` and `B` are actually live members who approved it — one short of the required 3 live-member confirmations, since `C`'s stale entry was counted.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
