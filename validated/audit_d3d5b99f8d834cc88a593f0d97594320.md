### Title
Cheap per-account compute-unit griefing via `CostTracker::would_fit` account cost limit - ([File: cost-model/src/cost_tracker.rs])

### Summary
Agave's `CostTracker` gates block/account inclusion purely on *requested* compute units (`TransactionCost::sum()`), while the fee actually charged for that reservation is decoupled from the size of the reservation — `compute_unit_price` can be set arbitrarily low (even 0), so a transaction can occupy a large fraction of `MAX_WRITABLE_ACCOUNT_UNITS` for a hot account while paying almost nothing. This mirrors the Optimism `ResourceMetering` bug: the "buy-in" check enforces a hard resource cap per slot but the price paid to buy that resource is not tied to scarcity, letting an attacker cheaply exhaust the shared budget and force victim transactions writing to the same account out of the block.

### Finding Description
`CostTracker::would_fit` rejects a transaction if its cost would push the block or any of its writable accounts' accumulated cost over fixed limits: [1](#0-0) 

`MAX_WRITABLE_ACCOUNT_UNITS` (24,000,000 CU) and `MAX_BLOCK_UNITS` (60,000,000 CU) are static per-slot caps: [2](#0-1) 

The cost a transaction "reserves" against these caps is its *requested* `compute_unit_limit`, not its actual execution cost, as computed by `CostModel::get_estimated_execution_cost` / `CostModel::calculate_cost`: [3](#0-2) 

Meanwhile, the fee a user is actually charged is `signature_fee + compute_unit_price * compute_unit_limit`, where `compute_unit_price` is an arbitrary user-chosen value with no floor tied to the cost reserved: [4](#0-3) [5](#0-4) 

Because the account-cost check in `would_fit` compares raw CU sums against `MAX_WRITABLE_ACCOUNT_UNITS`/`MAX_BLOCK_UNITS` with no relationship to the fee actually paid, an attacker can set `compute_unit_price = 0` (or near 0) and repeatedly submit transactions that write-lock a popular/contended account while requesting a large `compute_unit_limit`. This lets the attacker consume the account's or block's entire CU budget for that slot for essentially the base signature fee only (5000 lamports/signature), causing any subsequent legitimate transaction writing to that account in the same slot to be rejected in banking stage with `WouldExceedMaxAccountCostLimit`/`WouldExceedMaxBlockCostLimit`: [6](#0-5) 

The rejected transaction is not "reverted" (Solana transactions failing at this check are simply not included/committed) but it is functionally the same griefing outcome described in the Optimism report: the victim's transaction is excluded from the block at the will of a cheap attacker, and must be retried (as shown by the "retryable" bookkeeping in `try_add_processed_transaction_costs` / `cancel_processed_transactions_for_retry`): [7](#0-6) 

### Impact Explanation
This is a low-cost mechanism for an attacker to censor or grief any transaction that writes to a specific contended account (e.g. a popular program's state account, an AMM pool, a stake/vote account) for an entire slot, without needing large stake or elevated priority fees, since the CU-reservation check is independent of the price paid. This undermines the guarantee that "paying more gets you in" for competitors targeting the same account, and can be used to systematically deny inclusion of victims' transactions targeting hot accounts, matching the "censorship resistance undermined" and "bridging/asset-interaction griefed at low cost" impacts in the source report.

### Likelihood Explanation
Reaching this path only requires an ordinary user to submit ordinary transactions through normal RPC/TPU ingestion with a `ComputeBudgetInstruction::SetComputeUnitLimit` and low `SetComputeUnitPrice`; no special program deployment, privileged access, or validator collusion is required. This is easily performed at the client level.

### Recommendation
Decouple/relate the account-cost and block-cost admission checks in `CostTracker::would_fit` from the price paid, e.g. by requiring a minimum `compute_unit_price` proportional to how close the target account/block already is to its cost limit (dynamic local fee-market pricing), or by charging fees based on the requested (reserved) CU rather than only signature count plus optional priority fee, so that reserving a large share of a scarce per-account/per-block budget is proportionally costly, rather than flat-rate. This is analogous to the source recommendation of avoiding a fixed, cheaply-reachable resource cap decoupled from actual payment.

### Proof of Concept
1. Identify a hot/contended account `A` (e.g. a widely used AMM state account) that a victim transaction `V` intends to write-lock in an upcoming slot.
2. Attacker crafts transactions `T1..Tn`, each containing `ComputeBudgetInstruction::set_compute_unit_limit(~1,400,000)` and `ComputeBudgetInstruction::set_compute_unit_price(0 or minimal)`, each write-locking account `A`.
3. Submit enough of these (~17 transactions, since `MAX_WRITABLE_ACCOUNT_UNITS = 24_000_000` and each transaction can request up to the per-tx CU cap) ahead of/alongside `V` in the same slot, paying only the base signature fee (5000 lamports) per transaction — total cost on the order of ~0.085 SOL, independent of `V`'s value.
4. Once `CostTracker::would_fit` (`cost-model/src/cost_tracker.rs:272-310`) reports `WouldExceedAccountMaxLimit` for account `A` in that slot, `V` is rejected in `consumer.rs` (`core/src/banking_stage/consumer.rs:689-708`) and excluded from the block, forcing it to retry — reproducing the griefing/censorship pattern from the Optimism report at negligible attacker cost relative to the resource reserved.

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }

        Ok(())
    }

                        feature_set,
                    ),
                ),
                Err(_) => (0, 0),
            };

        (programs_execution_costs, loaded_accounts_data_size_cost)
    }

fn get_prioritization_fee(compute_unit_price: u64, compute_unit_limit: u64) -> u64 {
    let micro_lamport_fee: MicroLamports =
        (compute_unit_price as u128).saturating_mul(compute_unit_limit as u128);
    micro_lamport_fee
        .saturating_add(MICRO_LAMPORTS_PER_LAMPORT.saturating_sub(1) as u128)
        .checked_div(MICRO_LAMPORTS_PER_LAMPORT as u128)
        .and_then(|fee| u64::try_from(fee).ok())
        .unwrap_or(u64::MAX)
}

    /// Returns `(added_transaction_costs, retryable_indexes)`.
    ///
    /// `added_transaction_costs` has one entry per input transaction. `Some(cost)` means
    /// the processed transaction's actual cost was added to the cost tracker.
    /// `None` means no cost added for that transaction due to: the transaction was
    /// not processed, its cost was rejected by the cost tracker, a prior
    /// cost-tracker rejection canceled the rest of the batch, or an
    /// all-or-nothing cost failure rolled back the batch.
    fn try_add_processed_transaction_costs<'a, Tx: TransactionWithMeta>(
        bank: &Bank,
        transactions: &'a [Tx],
        mut transaction_costs: Vec<Option<TransactionCost<'a, Tx>>>,
        processing_results: &mut [TransactionProcessingResult],
        processed_counts: &mut ProcessedTransactionCounts,
        error_counters: &mut TransactionErrorMetrics,
        all_or_nothing: bool,
    ) -> (Vec<Option<TransactionCost<'a, Tx>>>, Vec<RetryableIndex>) {
        let mut retryable_transaction_indexes = Vec::with_capacity(processing_results.len());
        let mut all_or_nothing_error = None;
        let mut remaining_batch_error = None;
        let mut cost_tracker = bank.write_cost_tracker().unwrap();

        for (index, transaction_cost) in transaction_costs.iter_mut().enumerate() {
            let Some(cost) = transaction_cost.as_ref() else {
                continue;
            };

            match cost_tracker.try_add(cost) {
                Ok(_) => {}
                Err(err) => {
                    let transaction_error = TransactionError::from(err);
                    *transaction_cost = None;
                    if all_or_nothing {
                        all_or_nothing_error = Some((index, transaction_error));
                        break;
                    } else {
                        remaining_batch_error = Some((index, transaction_error));
                        break;
                    }
                }
            }
        }

        if let Some((failed_index, transaction_error)) = all_or_nothing_error {
            for transaction_cost in transaction_costs[..failed_index].iter().flatten() {
                cost_tracker.remove(transaction_cost);
            }
            transaction_costs.iter_mut().for_each(|cost| *cost = None);
            retryable_transaction_indexes.clear();

            Self::cancel_processed_transactions_for_retry(
                transactions,
                processing_results,
                processed_counts,
                error_counters,
                &mut retryable_transaction_indexes,
                failed_index,
                &transaction_error,
                0,
            );
        } else if let Some((failed_index, transaction_error)) = remaining_batch_error {
            transaction_costs[failed_index..]
                .iter_mut()
                .for_each(|cost| *cost = None);

            Self::cancel_processed_transactions_for_retry(
                transactions,
                processing_results,
                processed_counts,
                error_counters,
                &mut retryable_transaction_indexes,
                failed_index,
                &transaction_error,
                failed_index,
            );
        }

        (transaction_costs, retryable_transaction_indexes)
    }
