### Title
`meta_oracle::combine` Accepts Arbitrarily Stale Prices Because It Never Validates Against Current Clock Time, and `max_timestamp` Tracks the Last Oracle's Timestamp Rather Than the Maximum — (`crates/sui-oracle/move/oracle/sources/meta_oracle.move`)

### Summary

The `MetaOracle` framework in `crates/sui-oracle/move/oracle/sources/meta_oracle.move` contains two compounding bugs that allow arbitrarily stale price data to be returned as "trusted" output:

1. `combine` computes a staleness window relative to `max_timestamp` but never compares `max_timestamp` against the current blockchain time (`Clock`). If all oracle data is hours or days old, it still passes the filter.
2. `add_simple_oracle` overwrites `max_timestamp` with each oracle's timestamp rather than tracking the actual maximum, so the staleness window is anchored to the wrong reference point.

### Finding Description

**Bug 1 — No current-time validation in `combine`**

`combine` computes:

```move
let min_timestamp = max_timestamp - time_window_ms;
```

and then accepts any oracle data whose `timestamp > min_timestamp`. This is a purely relative check between oracle data points. The `Clock` object — Sui's canonical source of current time — is never consulted. If all three oracle operators stopped updating their feeds two hours ago, all three data points would still pass the filter as long as they are within `time_window_ms` of each other, and the function would return a median price that is two hours stale. [1](#0-0) 

**Bug 2 — `max_timestamp` is not the actual maximum**

`add_simple_oracle` unconditionally overwrites `max_timestamp` with each oracle's timestamp:

```move
if (option::is_some(&oracle_data)) {
    meta_oracle.max_timestamp = data::timestamp(option::borrow(&oracle_data));
};
```

The field is named `max_timestamp` but the code performs a plain assignment, not a max-assignment. The final value is the timestamp of the **last** oracle added that has data, not the highest timestamp among all oracles. [2](#0-1) 

**Consequence of both bugs combined**

Consider three oracles added in this order, with `time_window_ms = 60_000` ms and current chain time = 10_000_000 ms:

| Oracle | Stored timestamp (ms) |
|--------|----------------------|
| oracle1 | 100_000 |
| oracle2 | 110_000 |
| oracle3 | 120_000 |

After `add_simple_oracle` for all three, `max_timestamp = 120_000` (last oracle's value, not the true max — though here they happen to be equal). `min_timestamp = 120_000 − 60_000 = 60_000`. All three data points satisfy `timestamp > 60_000`, so all three pass. The median is returned as "trusted" data even though the most recent data point is `10_000_000 − 120_000 = 9_880_000 ms ≈ 2.7 hours` old.

Now consider oracles added in reverse order (newest first, oldest last):

| Oracle | Stored timestamp (ms) |
|--------|----------------------|
| oracle1 | 120_000 |
| oracle2 | 110_000 |
| oracle3 | 100_000 |

After `add_simple_oracle`, `max_timestamp = 100_000` (last oracle's value). `min_timestamp = 100_000 − 60_000 = 40_000`. All three pass. The staleness window is now anchored to the oldest data point, making the filter even weaker.

**`get_latest_data` has no staleness check at all**

`simple_oracle::get_latest_data` returns whatever is stored in the dynamic field with no freshness validation. Any consumer that calls it directly (as shown in the framework's own usage pattern) receives potentially arbitrarily stale data. [3](#0-2) 

### Impact Explanation

Any on-chain protocol that uses this oracle framework for price-sensitive operations — lending collateral valuation, liquidation thresholds, swap rates — will silently consume stale prices. This can cause:

- Incorrect collateral valuations, enabling under-collateralized borrowing or blocking legitimate withdrawals.
- Incorrect liquidation triggers: a user's position may be liquidated based on a price that is hours old and no longer reflects market reality, causing unexpected loss of collateral.
- Incorrect swap amounts, causing users to receive less value than expected.

The framework is published in the Sui repository as a reusable component and its own documentation and test module demonstrate it being used for financial exchange-rate calculations. [4](#0-3) 

### Likelihood Explanation

Oracle operators can go offline due to network issues, software bugs, or deliberate inaction. When they do, the last stored value in the `SimpleOracle` object persists indefinitely. Any caller — including an ordinary SUI holder — can invoke a protocol built on this framework and trigger execution with stale prices. No privileged access is required; the `SimpleOracle` objects are shared objects readable by anyone. [5](#0-4) 

### Recommendation

1. **Pass `Clock` to `combine` and enforce an absolute staleness bound.** After computing `max_timestamp`, assert that it is within an acceptable window of the current time:

```move
fun combine<T: copy + drop>(
    meta_oracle: MetaOracle<T>,
    clock: &Clock,
    max_age_ms: u64,
): (vector<T>, vector<address>) {
    let now = clock::timestamp_ms(clock);
    // ...
    assert!(max_timestamp + max_age_ms >= now, EStalePriceData);
    let min_timestamp = max_timestamp - time_window_ms;
    // ...
}
```

2. **Fix `add_simple_oracle` to track the actual maximum timestamp**, not just the last oracle's timestamp:

```move
if (option::is_some(&oracle_data)) {
    let ts = data::timestamp(option::borrow(&oracle_data));
    if (ts > meta_oracle.max_timestamp) {
        meta_oracle.max_timestamp = ts;
    }
};
```

3. **Add a staleness parameter to `get_latest_data`** so callers can enforce a freshness bound at the point of consumption.

### Proof of Concept

1. Oracle operator submits price data at chain time T=120_000 ms via `submit_data` (which records `clock::timestamp_ms(clock)` as the timestamp).
2. Oracle operator goes offline. No further updates are submitted.
3. At chain time T=10_000_000 ms (≈2.7 hours later), a user calls a protocol that invokes `trusted_fx` (or equivalent) with `time_window_ms=60_000`.
4. `add_simple_oracle` is called for each oracle. `max_timestamp` ends up as the last oracle's stored timestamp (e.g., 120_000 ms).
5. `combine` computes `min_timestamp = 120_000 − 60_000 = 60_000`. All stored data points (timestamps ~100_000–120_000) satisfy `timestamp > 60_000` and pass the filter.
6. `median` returns a `TrustedData` value containing a price that is 2.7 hours old, with no error or revert.
7. The consuming protocol uses this stale price for collateral valuation or liquidation, producing incorrect results. [1](#0-0) [6](#0-5) [7](#0-6)
