## Finding [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
A single signer's weight can be counted in both `total_weight_approved` and `total_weight_rejected` simultaneously (mismatched dedup guards) - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The node-side `StackerDBListener` tallies signer weight for the mining-round threshold check in `signer_coordinator.rs`. The dedup guard used to prevent double-counting an `Accepted` response uses a different set (`gathered_signatures`) than the one used to dedup a `Rejected` response (`responded_signers`). If a signer sends `Rejected` first and later reconsiders and sends `Accepted` for the same block, both weight totals get incremented for that signer, breaking the invariant that a signer's weight should be tallied toward at most one side.

### Finding Description
In the `Accepted` branch, the code only adds weight to `total_weight_approved` if the slot isn't already in `gathered_signatures`, but unconditionally inserts into both `gathered_signatures` and `responded_signers` afterward: [1](#0-0) 

In the `Rejected` branch, the dedup check is instead against `responded_signers`: [4](#0-3) 

Consider the sequence: signer X sends `Rejected` first. `responded_signers.insert(slot_id)` succeeds, so `total_weight_rejected += weight(X)`. Later, X sends `Accepted` for the same block (the v0 signer protocol explicitly allows a signer to reconsider a rejection under some conditions, per `handle_block_pre_commit`'s comment that "we do not change our votes on rejected blocks unless we receive a new block proposal ... and the reject reason allows us to reconsider," so a follow-up `Accepted` after an earlier `Rejected` for the same slot is a reachable, protocol-sanctioned sequence). Because `gathered_signatures` does not yet contain X's slot, the guard at line 443 passes and `total_weight_approved += weight(X)` as well — X's weight is now counted in *both* totals, with no corresponding decrement of `total_weight_rejected`.

(The reverse order, `Accepted` then `Rejected`, is correctly guarded: `responded_signers` already contains the slot from the earlier accept, so the reject-branch increment at line 517 is skipped.)

This asymmetry means `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, corrupting the aggregated-weight bookkeeping that `signer_coordinator.rs` relies on to decide whether to push or reject a block: [3](#0-2) 

Because the rejection branch is checked first in this if/else-if chain, a stale (never-decremented) rejection weight from a signer who has since switched to `Accepted` can push `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` to true even though the same signer's current, valid weight is also sitting in `total_weight_approved`, potentially at or above `weight_threshold`.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality the coordinator depends on: the node can compute a rejection outcome that includes double-booked weight from a signer who no longer opposes the block, causing the coordinator to abort a block round (`NakamotoNodeError::SignersRejected`) that should otherwise have reached the true 70% acceptance threshold. This is a liveness fault reachable by a single signer's ordinary reconsideration flow (no majority required), stalling block propagation for that round even though sufficient real signer weight supports the block.

### Likelihood Explanation
The sequence Rejected → Accepted for the same block/slot is explicitly anticipated by the v0 signer's own reconsideration logic (`handle_block_pre_commit` docs/comments about reconsidering rejected blocks), so this is not a contrived edge case — a single signer following normal reconsideration behavior triggers the double count without any malicious intent or coordination.

### Recommendation
Use a single, unified dedup/accounting mechanism for both response kinds — e.g., track each slot's *current* vote kind (Approved/Rejected) in one map, and when a slot's vote flips, subtract the previous weight contribution from the old bucket before adding it to the new one, rather than using two independently-checked sets (`gathered_signatures` vs `responded_signers`).

### Proof of Concept
1. Node starts a mining round with signer X holding weight `w`, `weight_threshold` = 70% of total.
2. X broadcasts `BlockResponse::Rejected` for hash H → `responded_signers.insert(slot_X)` succeeds → `total_weight_rejected += w`.
3. X later broadcasts `BlockResponse::Accepted` for the same H (a legitimate reconsideration) → `gathered_signatures.contains_key(slot_X)` is false → `total_weight_approved += w` as well.
4. Now both `total_weight_approved` and `total_weight_rejected` include `w`; if enough other signers already rejected, `total_weight_rejected + weight_threshold > total_weight` can be satisfied purely from stale weight, causing `signer_coordinator.rs` to return `SignersRejected` even though `total_weight_approved` may independently also reach `weight_threshold`.
