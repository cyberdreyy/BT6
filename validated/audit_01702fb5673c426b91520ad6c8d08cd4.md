## Title
Out-of-bounds panic in JSON-RPC instruction parsing via unvalidated `CompiledInstruction` account indices - (File: `transaction-status/src/lib.rs`)

### Summary
The reported beacon-kit bug is a case of "structural correlation trusted without validation": a sidecar's `BeaconBlockHeader` field is supposed to correlate with the actual `BeaconBlock`/proposer, but this correlation is never checked, letting an attacker supply an inconsistent value. The closest reachable analog in Agave is in the JSON-RPC transaction/instruction-encoding path: `CompiledInstruction.program_id_index` and `CompiledInstruction.accounts[..]` are supposed to correlate with (index into) the transaction's `account_keys`/`AccountKeys` list, but several code paths index into that list without first validating the indices are in bounds.

### Finding Description
`parse_ui_instruction` and its helper `make_ui_partially_decoded_instruction` in [1](#0-0)  directly index `account_keys[instruction.program_id_index as usize]` and `account_keys[i as usize]` for each `i` in `instruction.accounts`, with no bounds check.

This is unlike the individual program-specific parsers (`parse_system`, `parse_token`, `parse_address_lookup_table`, `parse_associated_token`, etc.), which explicitly guard against out-of-range indices with the pattern:
```rust
match instruction.accounts.iter().max() {
    Some(index) if (*index as usize) < account_keys.len() => {}
    _ => { return Err(ParseInstructionError::InstructionKeyMismatch(..)); }
}
```
as seen in [2](#0-1)  and [3](#0-2) . Those checks even carry the comment "Runtime should prevent this from ever happening" — i.e., they exist purely as defense-in-depth against inputs that bypass the normal sanitize/execute path.

`parse_ui_instruction` is called from every message-encoding implementation used to build RPC JSON responses — legacy `Message::encode`, `v0::Message::encode`/`encode_with_meta`, and `v1::Message::encode` — see [4](#0-3)  and [5](#0-4) . These are invoked whenever an RPC client requests `jsonParsed` (or even `json`, via `UiCompiledInstruction::from`) encoding for `getTransaction`, `getBlock`, `getConfirmedBlock`, etc.

While the primary hot ledger path sanitizes transactions before storage (bounding these indices), transactions/metadata served from long-term storage (BigTable, via `storage-proto`) are decoded straight from protobuf with `program_id_index: uint32` and no re-validation against the length of `account_keys`, as defined in [6](#0-5) . Nothing on the RPC decode/encode path re-checks that these indices are within bounds of the (possibly independently reconstructed) `account_keys`/`loaded_addresses` before calling into `parse_ui_instruction`.

### Impact Explanation
An out-of-bounds slice/vector index in Rust triggers a panic. If a stored/legacy transaction with a malformed or corrupted `program_id_index`/`accounts` index (larger than the account key list) is fetched and JSON-parsed by an unprivileged RPC client, the panic occurs inside the request-handling thread. Depending on how the JSON-RPC runtime handles thread panics, this can propagate to worker/thread-pool termination or misreport data, matching the accepted "decoder panic and misreporting" impact class for a single low-rate RPC call.

### Likelihood Explanation
This requires either a validator serving historical/BigTable-backed blocks with an inconsistency between stored `CompiledInstruction` indices and stored `account_keys`, or a bug elsewhere that produces such an inconsistency (e.g. loaded-address resolution supplying fewer addresses than referenced). Because the individual `parse_*` program handlers all independently re-implement this same bounds check as defense-in-depth (explicitly commented "Runtime should prevent this from ever happening"), the generic `parse_ui_instruction`/`make_ui_partially_decoded_instruction` fallback path lacking the same guard is an inconsistency in defense-in-depth rather than a normally-reachable condition under the intended sanitize pipeline.

### Recommendation
Add the same bounds validation used by the individual instruction parsers to `parse_ui_instruction` and `make_ui_partially_decoded_instruction` in [1](#0-0)  before indexing `account_keys`, returning a partially-decoded/best-effort representation (or an RPC error) instead of panicking when `program_id_index` or any `accounts[i]` is out of range.

### Proof of Concept
Not exploitable without an existing way to persist/serve a transaction whose stored `CompiledInstruction.program_id_index`/`accounts` exceed the length of its `account_keys`/`loaded_addresses` (e.g., via a corrupted BigTable-stored block or a bug in address-lookup-table resolution). Given such a record, any unprivileged `getTransaction`/`getBlock` RPC call requesting `jsonParsed` (or `json`) encoding for that slot/signature reaches `parse_ui_instruction`/`make_ui_partially_decoded_instruction` and panics on the out-of-bounds index.

fn make_ui_partially_decoded_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiPartiallyDecodedInstruction {
    UiPartiallyDecodedInstruction {
        program_id: account_keys[instruction.program_id_index as usize].to_string(),
        accounts: instruction
            .accounts
            .iter()
            .map(|&i| account_keys[i as usize].to_string())
            .collect(),
        data: bs58::encode(instruction.data.clone()).into_string(),
        stack_height,
    }
}

pub fn parse_ui_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiInstruction {
    let program_id = &account_keys[instruction.program_id_index as usize];
    if let Ok(parsed_instruction) = parse(program_id, instruction, account_keys, stack_height) {
        UiInstruction::Parsed(UiParsedInstruction::Parsed(parsed_instruction))
    } else {
        UiInstruction::Parsed(UiParsedInstruction::PartiallyDecoded(
            make_ui_partially_decoded_instruction(instruction, account_keys, stack_height),
        ))
    }
}
