### Title
Unauthorized griefer can indefinitely reset an exited builder's `withdrawable_epoch`, stalling its final balance sweep - ([File: specs/gloas/beacon-chain.md])

### Summary
`process_builder_deposit_request` in `specs/gloas/beacon-chain.md` resets an existing, exited-and-fully-swept builder's `withdrawable_epoch` forward by `MIN_BUILDER_WITHDRAWABILITY_DELAY` whenever *any* deposit request targets that builder's pubkey, and — unlike the new-builder registration path — this top-up path performs **no signature check**. Any party can therefore repeatedly submit trivial deposit requests for a builder that has already exited and been swept, perpetually re-arming the withdrawability timer and preventing the builder's balance from ever becoming sweepable, mirroring the analog bug where an authorized actor could indefinitely re-arm `readOnlyState.lastSetTimestamp` in `StakingProxy.setReadOnlyMode` and block `ZrxVaultBackstop`'s catastrophic-failure timeout.

### Finding Description
`process_builder_deposit_request` (specs/gloas/beacon-chain.md) branches on whether the requested pubkey already exists in `state.builders`: [1](#0-0) 

- If the pubkey is **new**, the request is only honored after `is_valid_builder_deposit_signature(request)` succeeds.
- If the pubkey **already exists** (the `else` branch), there is **no signature verification at all** — the deposit is accepted purely because the pubkey matches an existing registry entry, and if the builder is `exited and swept` (`withdrawable_epoch != FAR_FUTURE_EPOCH and balance == 0`), its `withdrawable_epoch` is reset to `current_epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY`.

Because `BuilderDepositRequest`s originate as EL execution requests keyed only by `pubkey`/`withdrawal_credentials`, and the top-up path does not check that the caller controls the builder's private key or its `execution_address`, **any unprivileged party** can submit a request carrying an already-registered, exited/swept builder's pubkey with a trivial `amount`. Each such request re-triggers the `withdrawable_epoch` reset condition, pushing the builder's ability to be fully swept out (`get_builders_sweep_withdrawals`, which requires `builder.withdrawable_epoch <= epoch`) further into the future: [2](#0-1) 

This is structurally identical to the reported bug class: a state whose purpose is to expire/finalize after a fixed delay (`ZrxVaultBackstop`'s 40-day read-only timeout / here, the builder's exit-withdrawability delay) is guarded by a "set only if not already active" style timestamp, but the guard omits the "already active" check and instead updates the timestamp unconditionally whenever the triggering call is repeated — letting an unrelated party indefinitely postpone the terminal state transition.

### Impact Explanation
This breaks the equality that an exited builder's committed funds become withdrawable after `MIN_BUILDER_WITHDRAWABILITY_DELAY` once swept to zero. An unprivileged third party (not the builder, not requiring the builder's signature) can mutate `builder.withdrawable_epoch` — a builder-owned piece of state — without authorization, indefinitely delaying (griefing) that builder's exit finality. This matches the "validator or builder mutated without its authority" impact class: the builder's exit/withdrawal timeline is altered by someone other than the builder.

### Likelihood Explanation
The attack requires only submitting an execution-layer deposit request (e.g., a minimal `MIN_DEPOSIT_AMOUNT` deposit transaction) referencing a known, already-exited-and-swept builder's pubkey — something observable on-chain (`state.builders[]` is public state) — and no signature or authorization over that pubkey is enforced on the top-up branch. The attacker's own cost is limited to the gas/deposit amount sent (which credits the victim builder's balance, not lost); no special privilege, race condition, or majority stake is required, making this trivially repeatable by any observer targeting any exited builder.

### Recommendation
On the "builder already exists" branch of `process_builder_deposit_request`, require the same authorization check used for new registrations (`is_valid_builder_deposit_signature`, or verification that the request's source/withdrawal credentials match the builder's own `execution_address`/pubkey control) before allowing a top-up to reset `withdrawable_epoch`. Alternatively, do not reset `withdrawable_epoch` for exited-and-swept builders at all when the top-up is unauthenticated — instead treat unauthenticated deposits to exited builders similarly to how a fully-swept validator's excess deposit is handled (credited without re-arming the exit timer), analogous to the read-only-mode fix's guidance that repeated triggers of an already-active state should be a no-op.

### Proof of Concept
1. Builder `B` (index `i`) voluntarily exits via `process_builder_exit_request`, setting `builders[i].withdrawable_epoch = current_epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY`. [3](#0-2) 
2. Once that epoch passes, `get_builders_sweep_withdrawals` sweeps `builders[i].balance` to zero, satisfying `withdrawable_epoch != FAR_FUTURE_EPOCH and balance == 0`. [2](#0-1) 
3. Any unrelated party (attacker) constructs an EL `BuilderDepositRequest` with `pubkey = B.pubkey`, `withdrawal_credentials` matching the required builder prefix, and `amount = MIN_DEPOSIT_AMOUNT` (or smaller), and gets it included via `apply_parent_execution_payload` → `process_builder_deposit_request`. [1](#0-0) 
4. Since `B.pubkey` is already in `builder_pubkeys`, execution enters the `else` branch with **no signature check**, sees `withdrawable_epoch != FAR_FUTURE_EPOCH and balance == 0`, and resets `withdrawable_epoch = current_epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY` again.
5. The attacker repeats step 3 once per `MIN_BUILDER_WITHDRAWABILITY_DELAY` window, keeping `B`'s balance perpetually locked and un-sweepable, without ever needing `B`'s signature or consent.

Note: I could not locate the exact numeric value/definition line for `MIN_BUILDER_WITHDRAWABILITY_DELAY` or the body of `is_valid_builder_deposit_signature` within the indexed context (only line ranges around the call sites were retrievable); confirming the precise signature-check semantics would benefit from a full read of `specs/gloas/beacon-chain.md` in a Devin session, since the index may not have surfaced every relevant helper definition.

def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
            withdrawal_index += 1

        builder_index = (builder_index + 1) % len(state.builders)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:
    # Ignore deposits with unexpected withdrawal credential prefixes
    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
        return

    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        if is_valid_builder_deposit_signature(request):
            add_builder_to_registry(
                state,
                request.pubkey,
                PAYLOAD_BUILDER_VERSION,
                ExecutionAddress(request.withdrawal_credentials[12:]),
                request.amount,
                state.slot,
            )
    else:
        builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
        builder = state.builders[builder_index]

        # If exited and swept, reset the withdrawable epoch
        if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
            epoch = get_current_epoch(state)
            builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY

        # Increase balance by deposit amount
        builder.balance += request.amount

def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
