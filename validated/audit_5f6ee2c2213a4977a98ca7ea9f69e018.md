### Title
EIP-8130 sponsor authorization does not bound the L1/operator fee component, allowing a governance-driven fee-scalar increase to charge a sponsoring payer beyond the amount they cryptographically authorized - ([File: crates/execution/eip8130/src/fee.rs])

### Summary
In the Teller report, the marketplace fee is only fetched from mutable state at `lenderAcceptBid` execution time, so a value the lender never explicitly capped can be inflated between bid submission and acceptance, letting the market owner redirect most of the loan value to itself. Base's EIP-8130 sponsored-transaction mechanism has the same structural gap: the payer's signed authorization commits only to `max_fee_per_gas` and `gas_limit` via `FeeCheck::max_fee_charge`, but the actual amount debited from the payer at inclusion also includes the OP-stack L1 data fee and Isthmus operator fee, which are read from mutable L1Block/SystemConfig state (`operator_fee_scalar`, `operator_fee_constant`, `l1_base_fee_scalar`) at execution time and are not part of what the payer signed.

### Finding Description
`Eip8130Signed`/`TxEip8130` lets a `sender` designate a distinct `payer` who authorizes gas sponsorship by signing `payer_signature_hash`, which commits to the transaction body (including `max_fee_per_gas`, `gas_limit`) [1](#0-0) . `FeeCheck` describes the payer's worst-case commitment purely in terms of `gas_limit`, `payer_auth_cost` and `max_fee_per_gas`: `max_fee_charge = (gas_limit + payer_auth_cost) * max_fee_per_gas` [2](#0-1) , and this is the value that is actually balance-checked against the payer in the pool validator via `FeeCheck::validate_balance` [3](#0-2) .

However, on top of this signed-and-validated amount, the validator (and, by the same logic, block execution) additionally computes an `additional_fee` — the OP-stack L1 data fee and Isthmus operator fee — using the *current* `L1BlockInfo` read from mutable predeploy state, and adds it into `payer_max_cost` without it ever being part of what the payer authorized: [4](#0-3) . The operator fee itself is a function of `operator_fee_scalar`/`operator_fee_constant`, values that live in the `L1Block` predeploy's storage and are set via governance-controlled `SystemConfig` `ConfigUpdate` deposits derived from L1 [5](#0-4) [6](#0-5) . A test confirms the operator/L1 fee is computed against whatever scalars are active and simply summed on top of the signed gas cap: [7](#0-6) . At the handler level, `before_execution` similarly charges `l1_fee + operator_fee` on top of the standard upfront gas cost and rejects only if the *payer's total balance* can't cover it — it never checks these fees against anything the payer signed [8](#0-7) .

Because `operator_fee_scalar`/`operator_fee_constant` (and `l1_base_fee_scalar`) can be changed by a `ConfigUpdate` on L1 that propagates into L2 derivation at the next epoch boundary [9](#0-8) , a party who can influence or predict this governance update (or simply an update that lands between when a sponsor co-signs an EIP-8130 payer authorization off-chain and when that transaction is eventually included) can cause the payer to be charged materially more L1/operator fee than existed when they authorized sponsorship — with no cap, no "minAmountOut"-style protection, and no re-consent step, mirroring the Teller `lenderAcceptBid` pattern where the fee is fetched fresh at execution instead of being pinned by the authorizing party.

### Impact Explanation
A sponsor (payer) in an EIP-8130 sponsored transaction only cryptographically commits to `gas_limit * max_fee_per_gas` (plus `payer_auth_cost`). The operator fee and L1 data fee are unbounded extra charges sourced from governance-mutable state and are debited from the same payer balance without the payer's consent to that specific amount. If `operator_fee_scalar`/`operator_fee_constant` are increased between authorization and inclusion (a normal, permitted governance action, not requiring a malicious sequencer/builder), the payer can be charged an amount they never signed for, draining sponsor funds beyond the explicitly authorized cap — a direct analog of the reported "fee fetched at execution time, not committed at authorization time" bug class, resulting in unauthorized value extraction from the sponsoring payer's account.

### Likelihood Explanation
This does not require any malicious sequencer, builder, or peer — the only actors involved are the legitimate protocol governance path that updates `operator_fee_scalar`/`operator_fee_constant`/`l1_base_fee_scalar` via ordinary `SystemConfig` updates, and normal EIP-8130 transaction submission/inclusion latency (across pool admission and eventual block building, or even just crossing an epoch boundary). Any sponsor relationship set up ahead of time (recurring sponsorship, session keys, dApp-subsidized gas) is exposed each time a fee-scalar update occurs during the window between payer signature and inclusion.

### Recommendation
Include a payer-signed cap on the total sponsored cost that also bounds the L1/operator fee component (e.g., extend `TxEip8130`/`payer_signature_hash` to commit to a `max_l1_and_operator_fee` or equivalently fold a conservative, payer-approved cap into `FeeCheck::max_fee_charge`), and reject inclusion if the L1BlockInfo-derived `additional_fee` at execution time would push the payer's total debit above that committed cap — rather than silently charging whatever the current fee scalars imply.

### Proof of Concept
Conceptual sequence (no local execution environment available to run this):
1. A sponsor (Bob) authenticates a `payer_signature_hash` for an EIP-8130 transaction on behalf of Alice, with `gas_limit = 200_000`, `max_fee_per_gas = 1e9`, and observes current `operator_fee_scalar = OLD_SCALAR` (e.g. from `L1Block`), computing an expected total debit of `gas_charge + additional_fee(OLD_SCALAR)`.
2. Before the transaction is included, a `ConfigUpdate` (`OperatorFee` type) is committed on L1, as modeled in `operator_fee_config_update_propagates_to_l1_info` [10](#0-9) , raising `operator_fee_scalar` to `NEW_SCALAR` (e.g., 3x higher).
3. Once the epoch containing this update is derived, `L1BlockInfo::operator_fee_scalar` reflects `NEW_SCALAR` [5](#0-4) .
4. The previously-signed, unmodified EIP-8130 transaction is then included; `BaseTxHandlerHooks::before_execution` computes `operator_fee` against the new scalar and charges Bob's balance for it, on top of the amount he explicitly signed for via `payer_signature_hash` [8](#0-7) .
5. Bob is debited more than the total he cryptographically authorized, with no on-chain mechanism having ever bound the operator/L1 fee component to his signature.

This confirms the root cause (fee computed from mutable, governance-controlled state at execution time rather than pinned by the authorizing signer) but I was not able to execute an end-to-end test in this environment; a Devin session with repository access would be needed to build and run a concrete harness test analogous to `eip8130_payer_max_cost_includes_l1_and_operator_fees` that varies `operator_fee_scalar` between signing and inclusion to empirically confirm the exact debited delta.

    /// Signing-hash preimage for the payer, per [EIP-8130].
    ///
    /// `keccak256(EIP8130_PAYER_TYPE || rlp([all body fields through `payer`]))`
    /// with the `sender` slot replaced by the recovered sender address. The
    /// payer commits to the full transaction body — including the `payer` slot
    /// itself — and only the `sender_auth` / `payer_auth` slots (which live in
    /// the signed wrapper) are excluded.
    ///
    /// [EIP-8130]: https://eips.ethereum.org/EIPS/eip-8130
    pub fn payer_signature_hash(&self, resolved_sender: Address) -> B256 {
        let sender = Some(resolved_sender);
        let payload_length = self.rlp_encoded_fields_length_with_sender(&sender);
        let mut buf = Vec::with_capacity(1 + length_of_length(payload_length) + payload_length);
        buf.put_u8(Eip8130Constants::EIP8130_PAYER_TYPE);
        Header { list: true, payload_length }.encode(&mut buf);
        self.rlp_encode_fields_with_sender(&sender, &mut buf);
        keccak256(&buf)
    }

/// Updates the L1 block values for an Isthmus upgraded chain.
/// Params are packed and passed in as raw msg.data instead of ABI to reduce calldata size.
/// Params are expected to be in the following order:
///   1. _baseFeeScalar       L1 base fee scalar
///   2. _blobBaseFeeScalar   L1 blob base fee scalar
///   3. _sequenceNumber      Number of L2 blocks since epoch start.
///   4. _timestamp           L1 timestamp.
///   5. _number              L1 blocknumber.
///   6. _basefee             L1 base fee.
///   7. _blobBaseFee         L1 blob base fee.
///   8. _hash                L1 blockhash.
///   9. _batcherHash         Versioned hash to authenticate batcher by.
///  10. _operatorFeeScalar   Operator fee scalar
///  11. _operatorFeeConstant Operator fee constant
pub fn parse_l1_info_tx_isthmus(data: &[u8]) -> Result<L1BlockInfo, BaseBlockExecutionError> {
    if data.len() != 172 {
        return Err(BaseBlockExecutionError::L1BlockInfo(
            L1BlockInfoError::UnexpectedCalldataLength,
        ));
    }

    // https://github.com/ethereum-optimism/op-geth/blob/60038121c7571a59875ff9ed7679c48c9f73405d/core/types/rollup_cost.go#L317-L328
    //
    // data layout assumed for Ecotone:
    // offset type varname
    // 0     <selector>
    // 4     uint32 _basefeeScalar (start offset in this scope)
    // 8     uint32 _blobBaseFeeScalar
    // 12    uint64 _sequenceNumber,
    // 20    uint64 _timestamp,
    // 28    uint64 _l1BlockNumber
    // 36    uint256 _basefee,
    // 68    uint256 _blobBaseFee,
    // 100   bytes32 _hash,
    // 132   bytes32 _batcherHash,
    // 164   uint32 _operatorFeeScalar
    // 168   uint64 _operatorFeeConstant

    let l1_base_fee_scalar = U256::try_from_be_slice(&data[..4])
        .ok_or(BaseBlockExecutionError::L1BlockInfo(L1BlockInfoError::BaseFeeScalarConversion))?;
    let l1_blob_base_fee_scalar = U256::try_from_be_slice(&data[4..8]).ok_or({
        BaseBlockExecutionError::L1BlockInfo(L1BlockInfoError::BlobBaseFeeScalarConversion)
    })?;
    let l1_base_fee = U256::try_from_be_slice(&data[32..64])
        .ok_or(BaseBlockExecutionError::L1BlockInfo(L1BlockInfoError::BaseFeeConversion))?;
    let l1_blob_base_fee = U256::try_from_be_slice(&data[64..96])
        .ok_or(BaseBlockExecutionError::L1BlockInfo(L1BlockInfoError::BlobBaseFeeConversion))?;
    let operator_fee_scalar = U256::try_from_be_slice(&data[160..164]).ok_or({
        BaseBlockExecutionError::L1BlockInfo(L1BlockInfoError::OperatorFeeScalarConversion)
    })?;
    let operator_fee_constant = U256::try_from_be_slice(&data[164..172]).ok_or({
        BaseBlockExecutionError::L1BlockInfo(L1BlockInfoError::OperatorFeeConstantConversion)
    })?;

    Ok(L1BlockInfo {
        l1_base_fee,
        l1_base_fee_scalar,
        l1_blob_base_fee: Some(l1_blob_base_fee),
        l1_blob_base_fee_scalar: Some(l1_blob_base_fee_scalar),
        operator_fee_scalar: Some(operator_fee_scalar),
        operator_fee_constant: Some(operator_fee_constant),
        ..Default::default()
    })
}

impl TxHandlerHooks<BaseEvmTypes> for BaseTxHandlerHooks {
    fn before_execution(
        host: &mut Evm<'_, BaseEvmTypes>,
        envelope: &BaseTxEnvelope,
        caller: Address,
        upfront_fee: U256,
    ) -> HandlerResult<()> {
        // Charge the upfront gas cost, the L1 data fee, and the operator fee (on the gas limit)
        // from the caller. Both fees are stashed for settlement so it charges/refunds against the
        // exact amounts collected here, without recomputing them.
        let l1_fee = Self::l1_fee(host, envelope);
        let operator_fee = Self::operator_fee(host, envelope, envelope.gas_limit());
        let ext = host.ext_mut();
        ext.l1_fee = l1_fee;
        ext.operator_fee = operator_fee;
        // `validate_sender` only checks the gas cost and value; the L1 and operator fees are
        // charged on top here via `charge_upfront`'s wrapping subtraction, so reject an
        // underfunded caller up front rather than let its balance wrap to a spurious value.
        Self::ensure_can_pay_fees(host, envelope, caller, l1_fee, operator_fee)?;
        charge_upfront(
            host,
            caller,
            upfront_fee.saturating_add(l1_fee).saturating_add(operator_fee),
        )
    }
