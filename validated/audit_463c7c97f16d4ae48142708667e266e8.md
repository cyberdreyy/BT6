### Title
Loss-adjusted withdraw receipt escapes its haircut and is paid at par when the user makes a later withdraw request - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the user's *most recent* request epoch. If a user's earlier epoch was loss-adjusted by `stopEpochWithDuration` (`collectWithdrawFunds` storing `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL`), and the user then files a new withdraw request in a later, fully funded epoch, the loss-adjusted receipt is never cleared through the haircut path. Instead, `_claimFundedWithdrawRequest` pays the entire aggregate `withdrawsRequests[_user]` (old haircutted basis + new basis) at par. This mirrors the reported bug class — a resource acquired on one path (the haircut obligation recorded at loss time) that is silently dropped on a later path (claim keyed only to the newest epoch), releasing value that should have been withheld.

### Finding Description
- `collectWithdrawFunds` records a pro-rata loss for pending receipts: when `_amount < pendingWithdraws` it stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and pulls only the reduced amount into the vault (`IdleCreditVault.sol:411-430`). The per-user basis in `withdrawsRequests[_user]`/`withdrawsRequestsByEpoch` is left intact; the haircut is meant to be applied lazily at claim time.
- On claim, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest` first (`IdleCreditVault.sol:312`). That function does `uint256 lossEpoch = lastWithdrawRequest[_user]; uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch]; if (lossRecoveryPrice == 0) return 0;` (`IdleCreditVault.sol:789-800`) — it checks **only the latest request epoch**.
- `requestWithdraw` overwrites `lastWithdrawRequest[_user] = currentEpoch` on every new request (`IdleCreditVault.sol:282`) while *accumulating* `withdrawsRequests[_user] += _amount`.
- After the newer epoch stops (`epochNumber > lastWithdrawRequest[_user]`), `_claimFundedWithdrawRequest` computes `amount = withdrawsRequests[_user] + apr0 buckets` and calls `_transferFundedClaim(_user, amount)` paying the full aggregate (`IdleCreditVault.sol:326-349`), with no deduction for the earlier loss-adjusted epoch.
- The older loss receipt can also never be claimed at its haircut: once `lastWithdrawRequest` moves past epoch N, `lossRecoveryPriceByEpoch[N]` is unreachable, so the only payable path is the at-par funded path.

Sequence (attacker = ordinary tranche-token holder):
1. Buffer phase: user requests withdraw; receipt lands in epoch N (`withdrawsRequestsByEpoch[user][N] = X`, `lastWithdrawRequest = N`).
2. Honest manager calls `stopEpochWithDuration(..., _lossAmount)`; `collectWithdrawFunds` funds pending receipts at e.g. 50% → `lossRecoveryPriceByEpoch[N] = 0.5e18`, vault receives only `pendingToFund`.
3. User does not claim. Next buffer: user requests withdraw again (`lastWithdrawRequest = N+1`, `withdrawsRequests` grows by Y).
4. Epoch N+1 stops fully funded. User calls `claimWithdrawRequest`: loss path reads epoch N+1 → price 0 → skipped; funded path pays `X + Y` at par instead of `0.5*X + Y`.

### Impact Explanation
Direct theft / insolvency. The vault only collected `(X * lossRecoveryPrice) / RECOVERY_FULL + Y` underlying for these receipts but pays out `X + Y`. The excess `X * (1 - lossRecoveryPrice)` is taken from strategy-held underlying belonging to other receipt holders and depositors (deposits sit in the vault during buffer). Broken invariant: loss socialization / one-receipt-one-payout — a receipt whose loss was already realized is paid as if fully funded. Loss is quantifiable: `shortfall = basis_N * (RECOVERY_FULL - lossRecoveryPriceByEpoch[N]) / RECOVERY_FULL`, up to the full old receipt when the loss price is near zero.

### Likelihood Explanation
Requires only unprivileged actions: two `requestWithdraw` calls by the same user across two epochs, plus an honest manager `stopEpochWithDuration` with a nonzero loss in the first epoch — an intended protocol feature for partial borrower repayment. No existing guard stops it: the epoch gating in `_claimFundedWithdrawRequest` (`epochNumber <= lastWithdrawRequest`) passes after the new epoch ends, and `_clearWithdrawClaimForEpoch` is never reached for the old epoch because the loss path keys on `lastWithdrawRequest` only. A user facing a haircutted claim is economically incentivized to do exactly this.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, iterate or track all epochs with a nonzero `lossRecoveryPriceByEpoch` for the user (e.g., check `lossRecoveryPriceByEpoch` for every epoch present in `withdrawsRequestsByEpoch[_user]`, or maintain a per-user list of loss-adjusted epochs), clearing each at its haircut before falling through to the funded path. Alternatively, settle the haircut eagerly at `collectWithdrawFunds` time by writing down each user's `withdrawsRequests`/`withdrawsRequestsByEpoch` basis pro rata, so the aggregate can never exceed what was actually funded.

### Proof of Concept
```solidity
// Foundry fork test against EzraCole/idle-tranches--001
// Setup: standard IdleCDOEpochVariant + IdleCreditVault deployment, attacker is KYC'd AA holder.
function testLossReceiptPaidAtParAfterNewRequest() external {
    uint256 X = 10_000 * ONE_SCALE;
    uint256 Y = 1_000 * ONE_SCALE;
    _depositWithUser(attacker, X + Y, true); // AA tranche

    // Epoch N: request withdraw of X
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(X, address(AAtranche));

    _startEpochAndCheckPrices(0);
    uint256 epochN = strategy.epochNumber();

    // Fund pending receipts at 50% via honest stopEpochWithDuration with loss
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 totalBasis = activeBasis + pendingBasis;
    uint256 loss = totalBasis / 2;
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(loss);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(address(underlying), strategy.borrower(), repay, true);
    vm.prank(strategy.borrower());
    underlying.approve(address(cdoEpoch), repay);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), loss);

    uint256 lossPrice = strategy.lossRecoveryPriceByEpoch(epochN);
    assertLt(lossPrice, 1e18); // haircut recorded

    // Epoch N+1: same user files a new request of Y (moves lastWithdrawRequest forward)
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(Y, address(AAtranche));
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Claim: loss path checks epoch N+1 (price 0) and is skipped;
    // funded path pays withdrawsRequests[attacker] = X + Y at par.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    uint256 expected = X * lossPrice / 1e18 + Y; // correct payout
    assertGt(paid, expected);                    // BUG: paid X + Y instead
    // Excess drained from vault = X * (1e18 - lossPrice) / 1e18
}
```
