### Title
Missing caller authorization in `state-manipulation::replace`/`clean` allows any unprivileged caller to arbitrarily rewrite the deployed account's storage - (File: `state-manipulation/src/lib.rs`)

### Summary
The `state-manipulation` contract exposes two low-level entrypoints, `replace` and `clean`, that write/remove arbitrary raw storage keys on the account the contract is deployed to. Neither entrypoint checks `predecessor_account_id`/`signer_account_id` against any owner or privileged identity before mutating storage. Once this contract is deployed on top of an account (as its README instructs: "Deploy this contract into the account that already has another contract deployed to it"), any caller who can send a function call to that account — not just the account's legitimate owner — can invoke `replace` to overwrite the account's `STATE` (or any other key) and fabricate arbitrary balances, share counts, or other custody-critical fields, or invoke `clean` to erase them.

### Finding Description
`replace` (`state-manipulation/src/lib.rs:75-92`) and `clean` (`state-manipulation/src/lib.rs:94-108`) both read the raw call input and directly call `storage_write`/`storage_remove` on the account's key-value store: [1](#0-0) [2](#0-1) 

There is no call to `env::predecessor_account_id()` (or equivalent `near_sys` predecessor check) anywhere in the file, and no comparison against an owner/foundation account ID stored in state — unlike every other privileged action in this codebase (e.g. `assert_owner` in `staking-pool/src/internal.rs:184-190`, `assert_called_by_foundation` in `whitelist/src/lib.rs:135-141`, or `assert_owner`/`assert_self` in the lockup contract). Because these two exported functions are plain `#[no_mangle]` entrypoints with no macro-generated access guard, the binding "recorded state == what the legitimate owner authorized" is broken: any account (unprivileged attacker) that can call `replace`/`clean` on the deployed contract's account can write or delete any key, including the `STATE` blob that stores balances, share counts, lockup amounts, staking pool totals, etc., for whatever contract this tool is layered on top of.

Before the attacker's call: state reflects legitimately-authorized values (e.g., `total_staked_balance`, `lockup_amount`, an account's `unstaked`/`stake_shares`).
After the attacker's call: those same fields can be set to any attacker-chosen value via `replace`, or wiped via `clean`, with no re-validation of invariants (share price, lockup constraints, whitelist membership, etc.) that the wrapped contract would normally enforce on every mutating call.

### Impact Explanation
This is a Critical-tier issue under the stated impact bucket "claims exceeding assets held" / "a wrongly parameterised deployment": once `state-manipulation` is deployed on an account, control over that account's business-logic state is no longer restricted to the account's owner. An unprivileged party can inflate recorded balances/shares/stake beyond what NEAR is actually custodied, or corrupt/erase the ledger entirely (e.g., zero out `total_stake_shares` while leaving locked NEAR on the account, freezing funds).

### Likelihood Explanation
Likelihood is high for any account where this contract is deployed as documented (layered on top of an existing contract account) and left reachable without additional access-key restrictions, since the exported functions accept calls from any predecessor and perform no identity check whatsoever. The contract's own documentation confirms its intended use is exactly this "deploy on top of an existing contract" pattern.

### Recommendation
Add a predecessor/owner check to both `replace` and `clean` (e.g., require `predecessor_account_id() == current_account_id()` or an explicit configured owner account written during a proper `#[init]`), so that only the account's legitimate controller (holder of a full-access key on that account, verified some other way, or a dedicated owner field) can invoke these storage-mutating entrypoints.

### Proof of Concept
1. Deploy `state-manipulation` (compiled with the `replace` feature) onto an account that also hosts, e.g., a `staking-pool` or `lockup` contract's storage.
2. From any unrelated, unprivileged account, call:
```
near call <target-account> replace '{"entries":[["<base64 of state key>", "<base64 of attacker-chosen serialized state>"]]}' --accountId attacker.near --gas 100000000000000
```
3. Because `replace` (`state-manipulation/src/lib.rs:75-92`) performs no predecessor check, the call succeeds and the target account's `STATE` (or any other key) is overwritten with attacker-controlled bytes — e.g., inflating `total_staked_balance`/`stake_shares` or a delegator's `unstaked` balance beyond what NEAR is actually held by the account.

```rust
#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    #[derive(serde::Deserialize)]
    struct ReplaceInput<'a> {
        #[serde(borrow)]
        entries: Vec<(&'a str, &'a str)>,
    }

    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(
            &base64::decode(key).unwrap(),
            &base64::decode(value).unwrap(),
        );
    }
}
```

```rust
#[cfg(feature = "clean")]
#[no_mangle]
pub fn clean() {
    #[derive(serde::Deserialize)]
    struct CleanInput<'a> {
        #[serde(borrow)]
        keys: Vec<&'a str>,
    }

    let input = input().unwrap();
    let args: CleanInput = serde_json::from_slice(&input).unwrap();
    for key in args.keys {
        storage_remove(&base64::decode(key).unwrap());
    }
}
```
