### Title
Default-recovery basis only counts current-epoch instant receipts — older unfunded `instantWithdrawsRequests` are excluded from `defaultPendingClaimBasis` and permanently frozen behind the reserve guard - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The audit bug was an optimization list (`_endingDelegations`) that caused only a subset of positions to be refreshed. The direct analog in `IdleCreditVault` is the per-epoch instant-withdraw accounting: `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` only look at `instantWithdrawClaimsByEpoch[epochNumber]` (the *current* epoch), while `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` are *aggregate* counters that include requests made in earlier epochs that were never funded or claimed. When `finalizeDefaultRecovery` runs, only the current-epoch subset is included in the recovery basis and reserve; older receipts stay in `instantWithdrawsRequests` but can never be paid, because `_transferFundedClaim` refuses to spend the recovery reserve.

### Finding Description
`requestInstantWithdraw` records basis both per-user aggregate (`instantWithdrawsRequests[_user]`, `pendingInstantWithdraws`) and per-epoch (`instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`) at `IdleCreditVault.sol:366-374`. If a partially-funded instant queue spans an epoch boundary — which the code explicitly contemplates ("that cash covered only part of the instant queue", line 638-640) — the leftover basis sits in the *old* epoch's bucket, since `instantWithdrawClaimsByEpoch` is never rolled forward or cleaned up except inside `_claimDefaultedInstantWithdrawRequest` for `defaultRecoveryEpoch` only (line 843-853).

At default finalization:

- `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` when `pendingInstantWithdraws != 0` (lines 644-649). Old-epoch instant basis is silently dropped even though `pendingInstantWithdraws` still counts it.
- `_defaultPrefundedInstantReserve()` likewise computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` (lines 716-723). If the old-epoch claim exceeds `pendingInstant`, it can even make the subtraction wrong-direction or zero, distorting `reserveAmount` (line 686).

At claim time, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844). The user's remaining `instantWithdrawsRequests[_user]` (the old-epoch portion) then falls through to `amount = instantWithdrawsRequests[_user]` and `_transferFundedClaim` (lines 387-392). But `_transferFundedClaim` reverts when `balance - reserve < amount` (lines 899-905), and the strategy's balance after finalization is essentially only `defaultRecoveryReserve`, which was computed on the *subset* basis. The old-epoch instant claim therefore permanently reverts.

### Impact Explanation
Two-sided impact, both with fund loss:

1. **Inflated recovery price / overpayment of the subset**: old-epoch instant claims are omitted from `totalBasis` at line 680, so `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is too large. Current-epoch defaulted claimants and post-default LPs are paid at the inflated ratio, consuming reserve that a fair accounting would have shared.
2. **Permanent freezing of the excluded claimants' funds**: old-epoch instant receipt holders hold strategy-token receipts (minted 1:1 at line 363) that can never be claimed — `_claimDefaultedInstantWithdrawRequest` clears nothing for them and `_transferFundedClaim` reverts against the reserve guard. Their claim is neither haircutted nor paid; it is permanently frozen, which is within the accepted impact set.

### Likelihood Explanation
Requires a specific but reachable sequence: an unprivileged lender makes an instant-withdraw request that is only partially funded by `collectInstantWithdrawFunds` in its epoch, the unfunded remainder survives into a later epoch (no code path rolls `instantWithdrawClaimsByEpoch` forward or forces collection), and the borrower then defaults with `finalizeDefaultRecovery` executed by the honest manager/CDO. The attacker needs only to be a tranche-token holder calling `requestInstantWithdraw`/`claimInstantWithdrawRequest` at the right times — every privileged actor remains honest. The mechanism (partially-funded instant queue crossing epochs) is explicitly described in the contract's own comments, so the preconditions are realistic, though it depends on a default occurring while a stale instant bucket exists.

### Recommendation
Replace the "current-epoch only" lookups with epoch-agnostic accounting:

- Track total instant claim basis separately (e.g., a `instantWithdrawClaimsTotal` counter incremented in `requestInstantWithdraw` and decremented on claim/collection), and use it in `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` instead of `instantWithdrawClaimsByEpoch[epochNumber]`.
- In `_claimDefaultedInstantWithdrawRequest`, clear the user's *entire* unfunded instant basis (all epochs), not only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — e.g., iterate/compact per-epoch entries or key the haircut to the aggregate `instantWithdrawsRequests[_user]` remainder.
- Alternatively, prevent instant requests from surviving unfunded across `stopEpoch`/`startEpoch` so the subset assumption becomes an enforced invariant rather than an implicit one.

### Proof of Concept
Foundry fork sketch against `test/foundry/IdleCreditVault.t.sol` setup:

```solidity
// 1. Setup vault + cdoEpoch, deposit AA so pool has liquidity, epoch running.
idleCDO.depositAA(10_000 * ONE_SCALE);
_startEpochAndCheckPrices(0);

// 2. User A requests instant withdraw late in epoch N.
//    CDO collects only part of it (partial funding): pendingInstantWithdraws > 0.
vm.prank(userA);
cdoEpoch.requestInstantWithdraw(amountA);          // mints receipt, bumps instantWithdrawClaimsByEpoch[N]
// manager/CDO collects less than pendingInstantWithdraws via collectInstantWithdrawFunds
// -> instantWithdrawClaimsByEpoch[N] stays > pendingInstantWithdraws... remainder unfunded.

// 3. Epoch rolls: stopEpoch + startEpoch bump epochNumber to N+1.
//    userA never claims; old bucket instantWithdrawClaimsByEpoch[N] is never cleared.

// 4. In epoch N+1 user B requests another instant withdraw (current-epoch basis).
vm.prank(userB);
cdoEpoch.requestInstantWithdraw(amountB);          // instantWithdrawClaimsByEpoch[N+1]

// 5. Borrower defaults; manager finalizes.
//    defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[N+1]
//    -> userA's epoch-N instant basis is EXCLUDED from totalBasis.
//    recoveryPrice is inflated; reserve is under-provisioned for userA.

// 6. userA calls claimInstantWithdrawRequest():
//    _claimDefaultedInstantWithdrawRequest clears only [userA][defaultRecoveryEpoch=N+1] => 0.
//    falls through: amount = instantWithdrawsRequests[userA] (old epoch, nonzero)
//    _transferFundedClaim: balance - defaultRecoveryReserve < amount => revert NotAllowed.
vm.prank(userA);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimInstantWithdrawRequest();            // userA's receipt permanently frozen
```

Assert additionally that `defaultRecoveryPrice` computed in step 5 exceeds the fair ratio `reserveAmount * 1e18 / (basis + instantWithdrawClaimsByEpoch[N])`, quantifying the overpayment to included claimants and the frozen amount for `userA`.
