### Title
Carried `unclaimedFees` become permanently locked after pool close or borrower default - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` tracks accrued management/performance fees in the `unclaimedFees` counter, which reduces `getContractValue()` (i.e., every tranche holder's NAV). The only payout paths for this counter are inside `stopEpoch` / `_stopEpochWithDuration` (`_transferFeeUnderlyings` in cash mode, `_mintSharesAtCurrPrice` to `feeReceiver`/`owner` in minted mode, and `_depositFees` on harvest). When accrued fees exceed the cash available at `stopEpoch`, the shortfall is left in `unclaimedFees` (`unclaimedFees -= _fees` at `contracts/IdleCDOEpochVariant.sol:459`, with the comment "Any fee that cannot be paid in cash remains accrued and continues reducing NAV").

The problem: there are two terminal states in which the carried fee can never be paid and never be released back to users:

- **Pool close** (`stopEpoch(0, 1)`): `epochEndDate = 0`, `epochDuration = 0`, `disableInstantWithdraw = true`. No further epoch can run, so `stopEpoch` — the only code that spends `unclaimedFees` — can never execute again. The test `testClosePoolRecallsGrossPrincipalBackingCarriedFees` shows the borrower is made to return gross principal *including* the backing for the carried fee, and `unclaimedFees` remains nonzero forever.
- **Borrower default** (`_handleBorrowerDefault` from the `catch` path of `stopEpoch`/`stopEpochWithDuration`): fee settlement is skipped entirely, `unclaimedFees` keeps subtracting from NAV through `getContractValue()`, and no later function (claim, default distribution, recovery finalize) ever disburses or clears it.

### Finding Description
In `_updateAccounting` (`contracts/IdleCDOCreditVault.sol:222-236`) the vault adds `(nav - _lastNAV) * fee / FULL_ALLOC` plus `_accrueManagementFee()` accruals into `unclaimedFees`, and `getContractValue()` nets this counter out of NAV. This is sound only because `stopEpoch` normally converts the accrual into a payment. Once the vault reaches a terminal state where `stopEpoch` cannot run again, the invariant "accrued fee is eventually paid or released" breaks:

- The underlying tokens that economically back the carried `unclaimedFees` (recalled gross principal in close mode; whatever residual value remains in default mode) sit in the vault/strategy with no function that can route them to `feeReceiver`/`owner` or return them to tranche holders.
- Users permanently bear the NAV haircut (their `tranchePrice` / claim amounts are computed on a NAV reduced by `unclaimedFees`), yet no beneficiary ever receives the deducted amount — it is a dead-weight loss and a permanent freeze of real funds, the exact analog of the Ubiquity report's "fee collected in collateral with no way to withdraw or track it" (here it *is* tracked, in `unclaimedFees`, which makes the frozen amount precisely quantifiable).

### Impact Explanation
Permanent freezing of funds equal to the carried `unclaimedFees` balance at close/default time. With a nonzero `managementFee` (e.g., 1–2% of NAV per epoch duration as in the Foundry tests), one underfunded `stopEpoch` (gross interest < accrued management fee, exactly the `testStopEpochCarriesManagementFeesAboveGrossInterest` scenario) followed by a close-pool stop or a default permanently locks `accruedManagementFee - paidInterest` worth of underlying in the contract. Users lose that value from their recoverable NAV, and `feeReceiver`/`owner` never collect it — there is no sweep or fallback that maps to this counter.

### Likelihood Explanation
The trigger requires a low-yield or loss epoch (management fee > gross interest) followed by a close-pool stop or a borrower default — all ordinary, non-malicious operational paths driven by honest privileged actors. An unprivileged attacker cannot create the state directly, but any tranche holder suffers the loss once the state is entered, and nothing requires misbehavior by owner/manager/borrower. Likelihood is moderate; impact (permanent lockup of a quantifiable fee amount plus the unjustified NAV haircut) matches the High severity of the source report.

### Recommendation
On terminal transitions (`_isRequestingAllFunds` close path and `_handleBorrowerDefault`/`finalizeDefault`), either:
- force-settle the carried `unclaimedFees` from the recalled/recovered underlying before freezing the epoch machine, or
- zero out `unclaimedFees` (crediting the amount back to NAV/`lastNAVAA`) so tranche holders recover the full residual value rather than leaving untransferable backing in the contract.

Add a test asserting `unclaimedFees == 0` or a corresponding payout once `epochEndDate == 0` or `defaulted == true`.

### Proof of Concept
A Foundry PoC (fork/mainnet-style, matching the existing harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: deposit AA, set managementFee = 2%, feeReceiver = TL_MULTISIG
// epoch 1: startEpoch, borrower returns only lowGrossInterest
vm.prank(manager); cdoEpoch.stopEpoch(0, lowGrossInterest);
uint256 carried = cdoEpoch.unclaimedFees();
assertGt(carried, 0);

// epoch 2: close pool; borrower repays gross principal (incl. fee backing)
vm.prank(manager); cdoEpoch.startEpoch();
deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager); cdoEpoch.stopEpoch(0, 1);

assertEq(cdoEpoch.unclaimedFees(), carried);          // never cleared
assertEq(cdoEpoch.epochEndDate(), 0);                 // terminal: no more stopEpoch
// feeReceiver balance for `carried` never increased; the backing underlying
// remains in the vault/strategy with no function able to release it.
// Every user claim is priced on getContractValue() which excludes `carried`.
```

Note on confidence: I verified the fee accrual, the capped payout, and the terminal close path from `contracts/IdleCDOEpochVariant.sol` and `contracts/IdleCDOCreditVault.sol`, and the carried-fee behavior is explicitly exercised by the repo's own tests. I was unable to fully read `_handleBorrowerDefault`/`finalizeDefaultRecovery`/`DefaultDistributor` to confirm no residual fee-release path exists post-default; if a recovery distribution implicitly releases the fee backing, the default branch of this finding weakens, but the close-pool branch (backed by `testClosePoolRecallsGrossPrincipalBackingCarriedFees`) stands on its own.
