### Title
`DuplicateBlockFound` guard in the v1 chainstate path checks only globally-accepted state, letting a signer sign a conflicting second tenure-change block - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The Perennial bug lets an attacker bypass a safety check because it is only enforced against a not-yet-finalized proxy of state (a check that runs once, at one point in the flow, rather than against the freshest local truth). The Stacks-signer codebase has a structurally identical gap: the `DuplicateBlockFound` tenure-change guard is implemented twice — once in `chainstate/v1.rs` and once in `chainstate/v2.rs` — and only the v2 copy was hardened to look at locally-signed state; the v1 copy was left checking only *globally accepted* state.

### Finding Description
`validate_tenure_change_payload` exists to stop a second tenure-change ("tenure-start") block from being accepted for a tenure a signer has already signed a block in — this is the permanent, non-reevaluable safety rail (`RejectReason::DuplicateBlockFound` is excluded from `should_reevaluate_reject_reason`, [1](#0-0) ).

In `chainstate/v2.rs` (used at `SUPPORTED_SIGNER_PROTOCOL_VERSION = 2`, [2](#0-1) ), the check is: [3](#0-2) 
This uses `get_last_signed_block`, which counts a block the signer has only *locally* accepted (signed by itself) — not yet globally accepted by the network/node.

In `chainstate/v1.rs`, the same guard instead does: [4](#0-3) 
This uses `get_last_globally_accepted_block`, which returns `None` for a block the signer has already signed but that hasn't yet reached global acceptance (i.e., the group hasn't yet reached 70% and the node hasn't yet processed it).

The stacks-signer CHANGELOG documents this exact class of fix having been applied for tenure-change duplicate detection ("When checking tenure change blocks, ensure there are no locally accepted blocks in the tenure, not just globally accepted blocks", [5](#0-4) ), but that fix was made only in `v2.rs` — the `v1.rs` copy of the same logic retains the old, weaker check. The `docs/signer-flows.md` documentation notes that this proposal-time duplicate check "never runs again" after arrival, and that the later pre-commit-time conflict guard (`get_signed_conflicts` / `conflict_still_blocks`) is what's relied on to cover the same ground once the check is stale ( [6](#0-5) ). But that later guard is explicitly designed to *stop blocking* a stale, unconfirmed signed conflict once its freshness window elapses and the node has not yet confirmed the tenure — that is a deliberate stall-recovery escape hatch for ordinary sibling races, documented at: [7](#0-6) 

So the v1 gap is not merely cosmetic: a proposal that should have been permanently and immediately rejected as `DuplicateBlockFound` instead slips past the proposal-time gate, gets validated and pre-committed like a normal proposal, and is only defended by the *temporary* freshness-based conflict guard at signing time — a guard whose entire purpose is to eventually let a stale, unconfirmed conflict stop blocking. `SortitionsView` (v1) is still live in the codebase and reachable whenever the negotiated active signer protocol version falls back to 0/1, which the code explicitly supports (see the downgrade/majority-negotiation logic and test, [8](#0-7) , [9](#0-8) ).

### Impact Explanation
Once the "sticky" proposal-time rejection is bypassed, a v1-protocol signer can end up treating a genuinely conflicting tenure-change block (targeting a tenure it has already signed a block for) as an ordinary competing sibling proposal. If that first signature later becomes stale (per `tenure_last_block_proposal_timeout`) without the node having confirmed the tenure at/above the relevant height — the exact "reorg recovery" branch documented in section 5 of `docs/signer-flows.md` — the signer will go on to sign the second, conflicting tenure-change block. This is a signer producing two conflicting signatures for the same tenure/slot, matching the Critical bar: "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
This requires: (1) the negotiated active signer protocol version to be 0 or 1 (a supported, tested fallback state, not an edge case the code treats as unreachable), and (2) a miner or byzantine actor to submit a second tenure-change proposal for the same tenure timed so that it reaches the signer after the first block is locally-but-not-globally accepted, and to survive long enough for the first signature's freshness window to lapse without global confirmation (e.g. under network delay or partial signer-set failure to submit acceptances promptly). This is plausibly triggerable by a single miner/relay controlling the timing of the second proposal and by unfavorable but realistic network conditions — no majority of signers or another signer's key is required, consistent with the "one-slot miner (plus gossip)" scope constraint.

### Recommendation
Bring `chainstate/v1.rs`'s `validate_tenure_change_payload` in line with `chainstate/v2.rs`: replace the `get_last_globally_accepted_block` lookup with `get_last_signed_block` (or otherwise treat any locally-accepted block in the tenure as a `DuplicateBlockFound` condition), so the same tenure cannot pass the proposal-time gate a second time regardless of whether the first block has yet been observed as globally accepted by the node.

### Proof of Concept
1. Configure the signer set so the negotiated active signer protocol version is 0 or 1 (e.g. via `restart_first_n_signers_with_supported_version` as exercised in `downgrade_signer_protocol_version`, [10](#0-9) ), so `chainstate/v1.rs`'s `SortitionsView::check_proposal` path is in use.
2. Miner proposes tenure-start block A for tenure T. Signers validate, pre-commit, and sign A (`mark_locally_accepted`) before the node or the rest of the signer set has finished confirming it globally.
3. Before A reaches global acceptance, a second tenure-change proposal B for the same tenure T arrives (e.g. re-proposed by the miner, or crafted by an attacker exploiting timing). At proposal time, `validate_tenure_change_payload` (v1.rs, lines 505-518) calls `get_last_globally_accepted_block(T)`, which returns `None` because A is only locally accepted — the `DuplicateBlockFound` rejection is skipped.
4. B proceeds to normal validation/pre-commit. If A's signature freshness window (`tenure_last_block_proposal_timeout`) elapses before the node's canonical tip reaches A's height (e.g. due to delayed group-threshold submission or node connectivity issues), the section 5 pre-commit logic's "OWN -- yes / TIP -- no — never confirmed --> SIGN" branch ( [11](#0-10) ) permits signing B.
5. The signer has now signed two conflicting blocks (A and B) for the same tenure — the exact class of double-signature the `DuplicateBlockFound` guard exists to prevent.

    fn determine_active_signer_protocol_version(&mut self) -> Option<SortitionStateVersion> {
        let local_version = self.get_signer_protocol_version();
        if let Ok(update) = self
            .local_state_machine
            .try_into_update_message_with_version(local_version)
        {
            self.global_state_evaluator
                .insert_update(self.stacks_address.clone(), update);
        };
        let local_state_version = SortitionStateVersion::from_protocol_version(local_version);
        self
            .global_state_evaluator
            .determine_latest_supported_signer_protocol_version().map(|version| {
                SortitionStateVersion::from_protocol_version(version)
            })
            .or_else(|| {
                // Don't default if we are in a global consensus activation state as its pointless
                if local_state_version.uses_global_state() {
                    None
                } else {
                    warn!("{self}: No consensus on signer protocol version. Defaulting to local state version: {local_version}.");
                    Some(local_state_version)
                }
            })
    }
