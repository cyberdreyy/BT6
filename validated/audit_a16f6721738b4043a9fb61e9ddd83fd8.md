### Title
Signer permanently wedged on stale `NotLatestSortitionWinner` rejection despite the underlying miner-validity gate flipping - ([File: stacks-signer/src/v0/signer.rs], [File: stacks-signer/src/chainstate/v1.rs])

### Summary
`should_reevaluate_reject_reason` treats `RejectReason::NotLatestSortitionWinner` as terminal (never re-evaluable), but the condition that produces this reason in `SortitionsView::check_proposal` (v1) is `cur_sortition.miner_status != Valid`, a value that monotonically flips from `Valid` to `InvalidatedBeforeFirstBlock` as the current miner times out. Once flipped, the exact block previously rejected as "not the latest sortition winner" becomes the legitimate continuation (fallback to the last sortition's miner), yet the signer will resend the stale rejection forever instead of re-checking it.

### Finding Description
The wedge: for a tracked `BlockInfo` in `LocallyRejected` state, `handle_block_proposal` → `should_reevaluate_block` (`stacks-signer/src/v0/signer.rs:1483-1572`) calls `should_reevaluate_reject_reason(block_info)` (`stacks-signer/src/v0/signer.rs:2706-2739`). For `RejectReason::NotLatestSortitionWinner` this returns `false`, and `should_reevaluate_block` falls into the `determine_response` branch, permanently re-sending the cached rejection (`signer.rs:1530-1532`) with no path back to a fresh `check_block_against_state` call for that exact `signer_signature_hash`.

The rejection is produced in `SortitionsView::check_proposal` (`stacks-signer/src/chainstate/v1.rs:301-316`):
```
ProposedBy::LastSortition(last_sortition) => {
    if self.cur_sortition.miner_status != SortitionMinerStatus::InvalidatedBeforeFirstBlock {
        return Err(RejectReason::NotLatestSortitionWinner);
    }
}
```
`cur_sortition.miner_status` starts as `Valid` and is only ever mutated to `InvalidatedBeforeFirstBlock` by the timeout check earlier in the same function (`v1.rs:144-163`), based on `SortitionState::is_timed_out`, which is purely a function of elapsed wall-clock time since the current tenure's last activity. This transition is one-directional (`Valid → Invalidated`), and once it happens, a proposal built by the *last* sortition's miner — which was previously rejected with `NotLatestSortitionWinner` because the current miner was still considered active — becomes the exact scenario the code is designed to accept (fallback to the prior miner when the new miner never got a signed block).

Attack/exploit flow:
1. Attacker wins sortition N (an unprivileged, single miner-slot action) and proposes block A extending their own tenure.
2. Sortition N+1 occurs with a different (legitimate) miner as `cur_sortition`. Because `cur_sortition.miner_status == Valid`, the signer rejects block A with `RejectReason::NotLatestSortitionWinner` and caches `block_info.reject_reason = Some(NotLatestSortitionWinner)` in `LocallyRejected` state.
3. The N+1 miner fails to produce a signed block before `block_proposal_timeout` elapses (a normal, attacker-unforced but attacker-awaitable liveness event). `SortitionState::is_timed_out` now returns true, flipping `cur_sortition.miner_status` to `InvalidatedBeforeFirstBlock` the next time any proposal is evaluated.
4. Block A (attacker's original, byte-identical proposal from the last sortition) is now exactly the case `ProposedBy::LastSortition` with `cur_sortition.miner_status == InvalidatedBeforeFirstBlock` — i.e., it would now pass `check_proposal`.
5. The attacker simply re-gossips the identical, previously-rejected `BlockProposal` for A. Because it is `KNOWN` (matched by `signer_signature_hash`) and its cached `reject_reason` is `NotLatestSortitionWinner`, `should_reevaluate_reject_reason` returns `false` forever, so `should_reevaluate_block` never re-invokes `check_block_against_state`/`SortitionsView::check_proposal`. `determine_response` just re-emits the old `LocallyRejected` verdict.

Existing guards do not catch this: the age check (`block_proposal_max_age_secs`) is only applied on the "new proposal" path in `handle_block_proposal`, after `should_reevaluate_block`, so it is never reached once the proposal is `KNOWN` and re-evaluation is refused. No periodic background task re-scans `LocallyRejected` blocks against a refreshed `SortitionsView` independent of a new proposal arriving.

### Impact Explanation
This is a liveness break (matches "a signer wedged into never signing valid blocks") for the specific block/height involved: once a signer has locally rejected a last-sortition proposal as `NotLatestSortitionWinner`, that signer can never sign that identical block again even after the fallback-eligibility condition it depends on becomes true, because the reject-reason gate is misclassified as terminal instead of re-evaluable. If a large fraction of signers hit the same rejection at the same point (which is plausible, since `check_proposal` is deterministic given the same view snapshot and most signers evaluate proposals near-simultaneously), the tenure/height can stall until a fresh proposal with different content is created and a new `signer_signature_hash` bypasses the cache — but in tenure-extend scenarios where the miner must resign the *same* header, or where the miner simply retransmits (attacker action, no cooperation needed from the miner), this becomes a genuine, height-specific liveness wedge. This is scoped to the v1 (local `SortitionsView`) code path only; it does not manifest when `state_version.uses_global_state()` is true (`signer.rs:865-869`), since `check_block_against_global_state` is used instead.

### Likelihood Explanation
Preconditions: (1) attacker must win one miner slot (BTC sortition) to build a block proposed against the "last sortition" role — within the allowed threat model; (2) the signer network must be running in the v1 (non-global-state) signer protocol; (3) the next miner (whoever wins the subsequent sortition) must fail to get a signed block before `block_proposal_timeout` — an ordinary liveness condition, not attacker-forced, but the attacker can wait for it opportunistically or, per the threat model where an attacker "can win a single miner slot," could win consecutive slots and simply not propose for the second one to force this transition themselves. Repeatable: the attacker need only re-gossip the stored `BlockProposal` message (pure StackerDB gossip, no key material beyond their own miner key, no auth_token) as many times as needed once the timeout has elapsed.

### Recommendation
Move `RejectReason::NotLatestSortitionWinner` (and audit the other reasons keyed off `SortitionMinerStatus`/timing state such as `ReorgNotAllowed`, `InvalidMiner`) into the re-evaluable set in `should_reevaluate_reject_reason`, or more precisely, key re-evaluability off whether the reject reason was derived from a state that can legitimately transition to "resolved" (miner-status timeouts), not just from a fixed enumeration. Alternatively, invalidate/clear cached `LocallyRejected` verdicts whenever `SortitionsView` is refreshed and `cur_sortition.miner_status` transitions to `InvalidatedBeforeFirstBlock`, forcing a fresh `check_block_against_state` pass on any block that was previously rejected due to that miner's validity.

### Proof of Concept
Rust test plan (in `stacks-signer/src/v0/tests.rs` or the chainstate v1 test module), mirroring the harness patterns already used (`run_sibling_scenario`, `check_proposal` unit tests in `stacks-signer/src/chainstate/tests/v1.rs`):
1. Construct a `SortitionsView` with `cur_sortition.miner_status = SortitionMinerStatus::Valid` and a `last_sortition` populated.
2. Build block `A` signed by the last sortition's miner key; call `check_proposal` and assert it returns `Err(RejectReason::NotLatestSortitionWinner)`.
3. Drive this through the signer: call `handle_block_proposal` with `A`'s `BlockProposal`, assert `block_info.state == BlockState::LocallyRejected` and `block_info.reject_reason == Some(RejectReason::NotLatestSortitionWinner)`.
4. Mutate the mocked view/signer_db so `SortitionState::is_timed_out` for `cur_sortition` returns `true` (e.g., set `get_last_activity_time`/`get_burn_block_receive_time_ch` far enough in the past), simulating the current miner timing out.
5. Re-invoke `check_proposal` directly on the mutated view with the identical block `A` and assert it now returns `Ok(())` (the gate has flipped).
6. Re-send the identical `BlockProposal` for `A` through `handle_block_proposal` a second time and assert `should_reevaluate_reject_reason` still returns `false`, and the signer emits the same stale `BlockRejection { reason_code: NotLatestSortitionWinner }` via `send_block_response`, rather than accepting/signing — demonstrating the signer is wedged even though the direct `check_proposal` call in step 5 shows the block is now valid.
