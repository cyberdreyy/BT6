### Title
Stale-snapshot clobber of a signer's own persisted signature during pending-response replay — ([File: stacks-signer/src/v0/signer.rs])

### Summary
`process_pending_responses_for_block` replays a block's early votes (pre-commits, then rejections, then signatures) against a single `&mut BlockInfo` that was fetched from `signerdb` *once*, before the replay began. Processing the pending pre-commits can, inside the same replay, cause this signer to reach the pre-commit threshold and sign the block itself — a state change that `handle_block_pre_commit` persists to the database using its *own*, freshly-fetched copy of `BlockInfo`. The rejection replay that runs immediately afterward is still holding the original, now-stale, `BlockInfo` snapshot, and if it reaches the global-rejection threshold it writes that stale snapshot back to signerdb, silently erasing the `signed_self` flag (and the `LocallyAccepted` state) that was just persisted by the nested pre-commit call.

### Finding Description
`handle_block_proposal` (`stacks-signer/src/v0/signer.rs:1670-1727`) fetches or creates a `BlockInfo`, `insert_block`s it, then calls:

```
self.process_pending_responses_for_block(stacks_client, sortition_state, &mut block_info, pending_responses);
``` [1](#0-0) 

`process_pending_responses_for_block` iterates the drained early votes in a fixed order — pre-commits, then rejections, then signatures — reusing the *same* `block_info: &mut BlockInfo` reference for all three loops: [2](#0-1) 

For each pending pre-commit, it calls `self.handle_block_pre_commit(..., &signer_signature_hash)`. That function does its **own independent** `block_lookup_by_reward_cycle` fetch (a separate in-memory copy, not the caller's `block_info`), and if the accumulated pre-commit weight crosses the 70% threshold it signs the block itself and persists the result: [3](#0-2) 

Because this write goes through `handle_block_pre_commit`'s local `block_info`, the caller's `block_info` (held by `process_pending_responses_for_block`) is **not** updated — it still reflects the pre-replay state (`signed_self = None`, state not yet `LocallyAccepted`).

The next loop in `process_pending_responses_for_block` processes pending rejections against this stale `block_info` via `store_and_process_block_rejection`: [4](#0-3) 

If the accumulated rejection weight from other signers crosses the blocking-minority threshold (>30%), this function marks the block globally rejected **on the stale copy** and writes it back to signerdb: [5](#0-4) 

This `insert_block(block_info)` call persists the *stale* `signed_self = None` / pre-signature `state`, overwriting the `signed_self = Some(...)` / `LocallyAccepted` record that the nested pre-commit-triggered self-signature had just written to the same row moments earlier in the same replay. The signer's own database now shows that it never signed this block, even though it broadcast a signature for it.

This is the direct analog of the reentrancy bug in the report: an outer computation snapshots state, a nested/reentrant call mutates the persisted "true" state based on a different view, and the outer function later commits its stale snapshot, silently undoing/miscounting the nested update.

### Impact Explanation
`signed_self` (and the derived `get_signed_conflicts` query used throughout section 5 of the pre-commit logic) is the local equivocation guard that prevents a signer from later signing a conflicting sibling block at the same height. If this flag is erased from signerdb by the stale write described above, a subsequent conflicting proposal at the same height will not be found by `get_signed_conflicts`/the "already signed" checks in `handle_block_pre_commit` (`block_info.signed_self.is_some()` check at line 1316) or `store_and_process_block_signature`, and the signer can go on to sign a second, conflicting block at the same height — a Critical-class outcome ("a signer signing … a conflicting block") per the accepted impact criteria.

### Likelihood Explanation
The trigger requires:
1. Early votes (pre-commits and rejections) for a not-yet-locally-known block arriving before the proposal itself — a state explicitly supported and expected by the "pending" tables (`add_pending_block_pre_commit_response`, `add_pending_block_rejection_signer_addr`-style paths feeding `drain_pending_block_responses`).
2. Enough pre-commit weight from other signers (any honest signers count) to cross 70% before the proposal is locally known.
3. A blocking minority (>30% weight, not a majority) of signers to have also broadcast rejections for the same block hash before the proposal arrived.

Both (2) and (3) are reachable by ordinary gossip timing/latency differences and a modest fraction of misbehaving/faulty signers sending conflicting BlockPreCommit and BlockResponse(Rejected) messages for the same signature hash — no majority control and no auth_token/key compromise is required, only ordinary StackerDB message timing plus a <30%-or-more minority sending an inconsistent rejection. This is a plausible, if narrow, race that a coordinated minority of signers (or even accidental timing skew across signers with different pre-commit/rejection message arrival order) can trigger.

### Recommendation
`process_pending_responses_for_block` must not operate on a stale, single-shot `BlockInfo` snapshot across nested state-mutating calls. After each pending-response callback that can itself mutate and persist the block's state (`handle_block_pre_commit`, `store_and_process_block_rejection`, `store_and_process_block_signature`), re-fetch the current `BlockInfo` from signerdb before continuing the loop (or before the subsequent loop's writes), instead of reusing the caller's original in-memory copy. Alternatively, make each of these state-mutation paths perform a read-modify-write against signerdb atomically (e.g., re-read immediately before any `insert_block` write, or transactionally check `signed_self`/`state` haven't changed since the snapshot was taken) so a nested call's persisted state can never be silently clobbered by a stale outer write.

### Proof of Concept
1. A block B is proposed at height H but this signer receives it late.
2. Before B's `BlockProposal` arrives, several peer signers' `BlockPreCommit` messages for B arrive and are parked via the pending-pre-commit table (weight not yet ≥70% individually, but collectively will be once replayed).
3. Also before B's proposal arrives, a set of signers whose combined weight exceeds the blocking-minority threshold (>30%) send `BlockResponse::Rejected` for B's hash; these are parked in the pending-rejection table.
4. B's `BlockProposal` finally arrives; `handle_block_proposal` validates it, calls `insert_block`, then `process_pending_responses_for_block(&mut block_info, pending_responses)`.
5. The pre-commit loop runs first: replaying the parked pre-commits pushes the pre-commit weight over 70%; `handle_block_pre_commit` (using its own DB-fetched copy) signs B locally (`mark_locally_accepted(false)`) and persists `signed_self = Some(...)` to signerdb (`stacks-signer/src/v0/signer.rs:1466-1479`).
6. The rejection loop then runs on the caller's original stale `block_info` (fetched before step 5); replaying the parked rejections crosses the global-rejection threshold, and `store_and_process_block_rejection` calls `mark_globally_rejected()` and `insert_block(block_info)` using the stale copy (`stacks-signer/src/v0/signer.rs:2335-2341`), overwriting the just-persisted `signed_self = Some(...)` record with the pre-replay `signed_self = None` state.
7. SignerDB for block B now shows this signer never signed it, even though it broadcast a signature. A later conflicting sibling proposal at height H bypasses the `signed_self`/`get_signed_conflicts` equivocation check and can be signed as well.
