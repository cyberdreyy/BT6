## Finding [1](#0-0) 

### Title
Operator commission bypasses `beneficiary_for_operator` and is credited to the old operator's own address after `switch_operator()` — ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`staking_contract::distribute_internal` redirects a commission payout to `beneficiary_for_operator(operator)` only when `recipient == operator`, where `operator` is the *current* operator parameter passed by the caller of `distribute()`/`request_commission()`. When a staker calls `switch_operator()`, a pending commission distribution entry is created under the **old operator's** address inside the same `distribution_pool`, but that entire struct is subsequently re-indexed under the **new operator**. Any later `distribute()` call is made with `operator = new_operator`, so the stale entry (`recipient == old_operator`) never matches `operator`, and the beneficiary redirect silently fails — the commission is paid directly to the old operator's own account instead of their configured beneficiary.

### Finding Description
`switch_operator()` performs, in order:
1. `distribute_internal(staker_address, old_operator, &mut staking_contract)` — pays out only already-*inactive* funds using `old_operator` as the `operator` parameter (correct redirect here). [2](#0-1) 

2. `request_commission_internal(old_operator, &mut staking_contract)` — computes any newly accrued, not-yet-requested commission and calls `add_distribution(operator=old_operator, staking_contract, recipient=old_operator, commission_amount)`, then `stake::unlock_with_cap(...)`. This creates a **new** shareholder entry in `distribution_pool` keyed by `old_operator`, representing pending_inactive (not yet withdrawable) stake. [3](#0-2) 

3. `stake::set_operator_with_cap(&staking_contract.owner_cap, new_operator)` and `staking_contracts.add(new_operator, staking_contract)` — the whole `StakingContract` (including the `distribution_pool` still containing the `old_operator` shareholder entry) is re-keyed to `new_operator`. [4](#0-3) 

When the lockup expires and anyone later calls `distribute(staker, new_operator)` (or `request_commission` triggers a forced `distribute_internal`), the lookup fetches the `StakingContract` by `new_operator` and invokes:

```
distribute_internal(staker, new_operator, staking_contract)
```

Inside, the redirect logic is:
```
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};
``` [5](#0-4) 

For the stale shareholder entry created in step 2, `recipient == old_operator` while `operator == new_operator`. The condition is false, so `recipient` is never remapped to `beneficiary_for_operator(old_operator)`. The commission coins are `aptos_account::deposit_coins(recipient, ...)`-ed directly to `old_operator`'s own account instead of the beneficiary address the old operator explicitly configured via `set_beneficiary_for_operator`. [6](#0-5) 

This is analogous to the report's root cause: value that should be routed through an intermediate/derived address (SPARTA staying at the Router instead of following the member; here, commission staying at the operator's own key instead of following to the beneficiary) is misrouted because a redirect step is skipped due to a mismatched identity check across an intervening state transition (operator switch / SPARTA transfer chain).

### Impact Explanation
The `beneficiary_for_operator` mechanism exists specifically so an operator can route commission payouts to a separate, presumably more secure, custody address distinct from the operator's own (often hot/validator) signing key. This bug lets the **staker** — simply by calling the permissionless-to-them `switch_operator`/`switch_operator_with_same_commission` — cause any commission accrued but not yet finalized at the time of the switch to bypass the old operator's beneficiary configuration entirely and land in the old operator's raw account. This is a credit-to-wrong-account / beneficiary-payout corruption as defined in the Required Impacts: funds intended for the beneficiary are instead delivered to a different (operator) address without the operator's or beneficiary's consent, undermining the security guarantee the beneficiary feature is meant to provide.

### Likelihood Explanation
High reachability: `switch_operator` and `switch_operator_with_same_commission` are ordinary, unprivileged staker operations (the staker acts on their own stake), requiring no special permissions beyond stake ownership. The only precondition is that the operator has some already-accrued-but-not-yet-inactive commission and has configured a beneficiary — both are normal, expected states in production usage (operators routinely set beneficiaries per the framework's own commentary, and commission naturally accrues continuously while validating).

### Recommendation
In `distribute_internal`, resolve the beneficiary redirect based on the recipient's own identity, not the enclosing call's `operator` parameter, e.g.:
```
if (recipient == operator || staking_contract_had_operator(recipient)) {
    recipient = beneficiary_for_operator(recipient);
};
```
Simplify by always attempting `beneficiary_for_operator(recipient)` for any recipient that is (or was) an operator address recorded in the distribution — or, more robustly, snapshot the intended beneficiary at the time `add_distribution` is called rather than resolving it lazily by comparing against the current `operator`.

### Proof of Concept
1. Staker creates a staking contract with `operator_1`, commission 10%.
2. `operator_1` calls `set_beneficiary_for_operator(operator_1, custody_addr)`.
3. Validator earns rewards; commission accrues but staker has not yet called `distribute`/`request_commission`.
4. Staker calls `switch_operator(staker, operator_1, operator_2, new_commission_percentage)`. Internally, `request_commission_internal` creates a `distribution_pool` entry `{recipient: operator_1, amount: pending_commission}`, then the whole contract (including this entry) is moved to be keyed by `operator_2`.
5. Stake pool lockup expires; anyone calls `distribute(staker, operator_2)`.
6. Inside `distribute_internal(staker, operator_2, staking_contract)`, the loop reaches the `operator_1` shareholder entry: `recipient(operator_1) == operator(operator_2)` is false, so `beneficiary_for_operator(operator_1)` is never consulted.
7. Result: the pending commission is deposited straight into `operator_1`'s own account, not `custody_addr`, silently violating the beneficiary configuration operator_1 had set up.

    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
