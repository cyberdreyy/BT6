### Title
Bridge outgoing token disclosed to any authenticated user regardless of role via GraphQL `bridge`/`bridges` queries - ([File: core/web/resolver/bridge.go])

### Summary
The GraphQL `Bridge` type resolver exposes the raw `bridges.BridgeType.OutgoingToken` field to any authenticated GraphQL caller, with no role-based restriction beyond session authentication. Since `OutgoingToken` is stored and returned in plaintext (unlike `IncomingTokenHash`, which is hashed), any user who can reach the `bridge`/`bridges` GraphQL queries can read the bridge's outgoing authentication secret.

### Finding Description
The GraphQL schema explicitly defines the `outgoingToken` field as part of the public `Bridge` type: [1](#0-0) 

`BridgeResolver.OutgoingToken()` returns the value directly from the `bridges.BridgeType` struct with no masking or redaction: [2](#0-1) 

`BridgePayloadResolver`/`BridgesPayloadResolver` wrap `BridgeType` objects without stripping this field before returning them to `ToBridge()`/`Results()`: [3](#0-2) 

At the model level, `BridgeType.OutgoingToken` is stored as plaintext, in contrast to `IncomingTokenHash`, which is a one-way hash of the incoming token — indicating the incoming token was deliberately designed to never be recoverable after creation, while the outgoing token has no equivalent protection: [4](#0-3) 

The REST presenter (`core/web/presenters/bridges.go`) exhibits the identical pattern — `OutgoingToken` is serialized in every bridge JSON:API response with no `omitempty`, whereas `IncomingToken` is only populated (and only present) at creation time: [5](#0-4) 

The `Resolver.Bridge`/`Resolver.Bridges` query handlers in `core/web/resolver/query.go` call `authenticateUser(ctx)` before invoking the app's `BridgeORM`, but this only verifies that a session exists — it performs no per-field or per-role redaction of the outgoing token before constructing the `BridgeResolver`/`BridgePayloadResolver`.

### Impact Explanation
This corresponds to Chainlink's "credential/secret disclosure" bounty class: disclosure of the bridge's `OutgoingToken` (the shared secret the node uses to authenticate itself to an external adapter/EI) allows any low-privileged authenticated user (e.g., a view-role user) to obtain a credential that can be replayed to impersonate the node when communicating with the external adapter, or to forge responses back to the node using that shared secret.

### Likelihood Explanation
Any authenticated GraphQL client that can reach the `bridge(name)` or `bridges` query and has a valid session (regardless of assigned role) can trigger this — no admin, database, or host access is required, only an authenticated session with query-level access to the GraphQL API. The behavior is deterministic and repeatable for every bridge that has been created.

### Recommendation
Do not return `OutgoingToken` in plaintext from `BridgeResolver.OutgoingToken()` (and the equivalent REST `BridgeResource`) except to users with sufficient privilege (e.g., admin role), or redact/mask the token in list/read queries the same way `IncomingToken` is only ever returned once at creation time.

### Proof of Concept
1. Create a bridge via `CreateBridge` mutation (or `bridges.NewBridgeType`) with a known `OutgoingToken`.
2. Authenticate a GraphQL test client as a `view`-role user (per `authenticateUser` session setup used in `core/web/resolver/bridge_test.go`).
3. Execute `query { bridge(name:"x") { ... on Bridge { outgoingToken } } }` and `query { bridges { results { outgoingToken } } }`.
4. Assert the response's `outgoingToken` field equals the raw secret created in step 1, demonstrating it is not redacted for the view role.
