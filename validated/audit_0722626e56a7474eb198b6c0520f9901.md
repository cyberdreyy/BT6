## Title
JupLend deposit CPI drains other depositors' liquidity when the underlying mint has a Token-2022 transfer fee - (File: `programs/marginfi/src/instructions/juplend/deposit.rs`)

### Summary
The external report describes an AlgebraPool bug where a balance-diff calculation (`balanceToken0().sub(balance0Before)`) is treated as an "exact" transfer amount, which silently breaks once a fee-on-transfer token skims part of the transfer. `juplend_deposit` in marginfi has the analogous root cause: it computes `expected_shares` from the caller-supplied `amount` before any transfer happens, moves tokens with `transfer_checked(amount)` into the shared liquidity vault, and then calls the JupLend CPI with the same original `amount` — never re-deriving it from the observed pre/post vault balance. Unlike `lending_pool_emissions_deposit` (`programs/marginfi/src/instructions/marginfi_group/configure_bank.rs:100-109`), which explicitly rejects mints with `utils::nonzero_fee`, there is no such check anywhere in the JupLend deposit path. [1](#0-0) 

### Finding Description
`juplend_deposit` computes the shares it expects to receive using the raw, caller-supplied `amount`: [2](#0-1) 

It then transfers `amount` from the user to the bank's liquidity vault: [3](#0-2) 

and immediately CPIs into JupLend with the *same* `amount` (not the amount actually received in the vault): [4](#0-3) [5](#0-4) 

The `mint` account passed into `JuplendDeposit` is a generic `InterfaceAccount<'info, Mint>` with no constraint rejecting Token-2022 mints carrying a `TransferFeeConfig` extension, and unlike `lending_pool_emissions_deposit`, `juplend_deposit` never calls `utils::nonzero_fee`. If the bank's underlying mint charges a transfer fee, `cpi_transfer_user_to_liquidity_vault(amount)` only credits the vault with `amount - fee`, but `cpi_juplend_deposit(amount, ...)` still instructs JupLend to move the full pre-fee `amount` out of the *shared* liquidity vault into the fToken position. Because the vault is a pooled account funded by all depositors of that bank, the missing `fee` worth of tokens is silently sourced from other depositors' balances rather than the current depositor. The depositor is then credited `expected_shares` computed from the full pre-fee `amount` via `bank_account.deposit_no_repay`, i.e., they receive shares as if no fee were ever deducted: [6](#0-5) 

This is the exact same bug class as the report: a "balance diff after transfer" style flow is assumed to equal the nominal requested amount, and that assumption silently breaks for fee-on-transfer tokens — except here the consequence is not merely a broken feature (as in the DEX case) but value redirection/socialized loss among bank depositors, since it moves real principal out of the shared vault to fund a share credit that doesn't correspond to actual capital contributed.

The `require_eq!` sanity checks in this function (`minted_shares == expected_shares`) only validate that the *JupLend-side* CPI accounting matches expectations; they never validate that the *vault* actually received `amount` before the CPI attempts to move `amount` out of it. Because the vault typically holds a nonzero balance from other users, this is not a fixed revert but a silent shortfall.

### Impact Explanation
If a group admin ever configures a JupLend-integration bank on a Token-2022 mint with an active `TransferFeeConfig`, every deposit into that bank drains `fee`-worth of tokens from the shared liquidity vault (i.e., from other depositors' principal) to cover the depositor's own transfer fee, while crediting the depositor shares based on the pre-fee amount. Repeated over many deposits, this durably misallocates real liquidity vault assets versus the shares outstanding, understating available liquidity for withdrawals/liquidations and creating a bad-debt-like discrepancy — a genuine, durable financial-accounting inconsistency, not a theoretical one.

### Likelihood Explanation
Requires: (1) a group admin configuring a JupLend bank against a fee-charging Token-2022 mint (no code currently prevents this, unlike the emissions-deposit path which explicitly checks `nonzero_fee`), and (2) at least one user depositing into that bank. Given marginfi already supports T22 fee-on-transfer mints elsewhere (test fixture `BankMint::T22WithFee`) and explicitly handles them in deposit/withdraw/repay paths but not in the JupLend integration, this is a plausible configuration oversight rather than a purely theoretical scenario. It does not require any special permission beyond ordinary bank creation, which in marginfi is typically admin-gated but is not restricted to only "safe" mints for JupLend banks specifically.

### Recommendation
Either (a) explicitly reject mints with a nonzero Token-2022 transfer fee (and active transfer hooks) for JupLend/Drift/Kamino/Solend integration banks at bank-creation/configuration time, mirroring the `utils::nonzero_fee` / `utils::has_transfer_hook` checks already used in `lending_pool_emissions_deposit`, or (b) make `juplend_deposit` fee-aware: measure the vault's actual balance delta after `cpi_transfer_user_to_liquidity_vault` and use that observed amount (not the pre-fee `amount`) both for the `cpi_juplend_deposit` call and for computing `expected_shares`/crediting `share_amount`.

### Proof of Concept
1. Admin creates a JupLend-tagged bank (`ASSET_TAG_JUPLEND`) whose underlying mint is a Token-2022 mint with a `TransferFeeConfig` (e.g., 1% fee) — nothing in `JuplendDeposit`'s account constraints or `juplend_deposit` logic rejects this.
2. User A deposits 1,000 tokens; `cpi_transfer_user_to_liquidity_vault(1_000)` moves only 990 tokens into the vault (10 skimmed as T22 fee), but `expected_shares` and `cpi_juplend_deposit` both use the full 1,000.
3. `cpi_juplend_deposit(1_000, ...)` pulls the full 1,000 out of the shared liquidity vault into JupLend, meaning the extra 10 tokens are sourced from the vault's existing balance (funded by other depositors), not from User A.
4. `require_eq!(minted_shares, expected_shares, ...)` passes because JupLend's own accounting is internally consistent with the 1,000 CPI amount, masking the fact that only 990 came from User A.
5. `bank_account.deposit_no_repay(minted_shares)` credits User A shares equivalent to a full 1,000 deposit, even though only 990 of principal actually originated from them — the 10-unit shortfall is absorbed by the vault (i.e., other depositors), repeatable on every deposit to progressively misstate backing assets vs. shares outstanding.
