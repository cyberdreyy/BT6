### Title
`IdleCreditVault.deposit` mints strategy tokens 1:1 with the nominal amount, breaking solvency for fee-on-transfer underlying tokens - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The credit-vault strategy mints claim tokens (its own `strategyToken`, priced at exactly `oneToken` via `price()`) equal to the nominal `_amount` parameter instead of the amount actually received from the transfer. For a fee-on-transfer underlying, the vault mints more claims than the underlying it holds, permanently inflating the vault's recorded NAV over its real balance. The same nominal-amount assumption exists in `collectWithdrawFunds`, `collectInstantWithdrawFunds` and `finalizeDefaultRecovery`, which decrement claim basis by the requested amount while receiving less.

### Finding Description
In `IdleCreditVault.deposit`, called from `IdleCDOCreditVault._deposit`, the vault pulls funds and mints receipts against the input amount:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:596-617
function deposit(uint256 _amount) external virtual override returns (uint256) {
    _onlyIdleCDO();
    if (_amount > 0) {
        underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
        _mint(msg.sender, _amount);          // mints _amount, but only _amount - fee arrived
    }
    ...
}
```

`IdleCDOCreditVault._deposit` itself correctly measures the received amount for minting tranche shares (`_contractTokenBalance(_token) - _preBal` at `contracts/IdleCDOCreditVault.sol:203-206`), but then calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the *nominal* amount (`contracts/IdleCDOCreditVault.sol:211`). Two failures result:

1. `deposit` tries to pull `_amount` from the CDO, which only received `_amount - fee` from the user. Unless the CDO holds other depositors' buffered underlying, `safeTransferFrom` reverts and deposits are blocked. If buffered funds exist, the missing `fee` is silently taken from other users' liquidity.
2. The strategy mints `_amount` strategy tokens while holding only `_amount - fee` underlying. Since `price()` is fixed at `oneToken` (`IdleCreditVault.sol:174-176`), `getContractValue` / NAV accounting in the CDO counts the full `_amount`, while the vault's balance is short by `fee`.

The same mismatch exists on the funding paths:
- `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`) reduces `pendingWithdraws` by `_amount` but receives `_amount - fee`.
- `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`) reduces `pendingInstantWithdraws` by `_amount` while receiving less.
- `finalizeDefaultRecovery` (`IdleCreditVault.sol:706-709`) sets `defaultRecoveryReserve = _recoveredAmount + ...` while only `_recoveredAmount - fee` actually arrives.

### Impact Explanation
Insolvency of the strategy. Strategy-token supply (the 1:1 claim on underlying, used by `_burn`-tied withdraw receipts, `pendingWithdraws`, `defaultRecoveryReserve`) exceeds the underlying actually held. Earlier claimants withdraw at par through `_transferFundedClaim`/`_transferDefaultRecovery`, and the last claimant's `safeTransfer` reverts on insufficient balance — a permanent loss for that claim equal to the accumulated transfer fees. On the deposit path, each deposit either reverts (freezing the vault's deposit function) or drains other users' buffer.

### Likelihood Explanation
Requires the vault's `token` to be (or become) a fee-on-transfer ERC20. The codebase places no restriction on the underlying at `initialize`, and the pull-fund sites never measure the post-transfer balance. No privileged misbehavior is needed; the discrepancy accrues on every ordinary `deposit` / `collectWithdrawFunds` call.

### Recommendation
Measure the received amount with a balance delta at every `safeTransferFrom` site and account for that:

```solidity
uint256 before = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
uint256 received = underlyingToken.balanceOf(address(this)) - before;
_mint(msg.sender, received);
```

Apply the same pattern in `collectWithdrawFunds`, `collectInstantWithdrawFunds`, `finalizeDefaultRecovery`, and pass the *received* amount (not `_amount`) from `IdleCDOCreditVault._deposit` into `strategy.deposit`. Alternatively, explicitly document that the vault only supports non-fee-on-transfer underlyings.

### Proof of Concept
Foundry fork-style PoC using a fee-on-transfer mock (1% fee on `transferFrom`):

```solidity
// Mock FOT token
contract FoTToken is ERC20 {
    constructor() ERC20("FoT", "FOT") {}
    function mint(address to, uint256 amt) external { _mint(to, amt); }
    function _transfer(address f, address t, uint256 a) internal override {
        uint256 fee = a / 100;
        super._transfer(f, t, a - fee);
        super._burn(f, fee);
    }
}

function testFotInsolvency() public {
    FoTToken fot = new FoTToken();
    // deploy IdleCreditVault + IdleCDOCreditVault with `fot` as token
    // (standard test setup: owner, manager, borrower, epoch started)

    fot.mint(lender1, 1_000e6);
    fot.mint(lender2, 1_000e6);

    vm.startPrank(lender1);
    fot.approve(address(cdo), 1_000e6);
    cdo.depositAA(1_000e6); // strategy mints 1_000e6 tokens, holds only 990e6
    vm.stopPrank();

    // CDO pulled 1_000e6 nominal from lender1 but only 990e6 reached the CDO;
    // strategy.deposit then pulls 1_000e6 from the CDO -> reverts (or drains buffer)
    // If buffered funds covered it, strategy now has 1_000e6 tokens minted
    // backed by 990e6 underlying.

    // Second lender withdraws first -> paid at par
    // First lender's claim then reverts: underlying balance < claim
}
```

Concretely, with a standalone assertion on the strategy: after `cdo.depositAA(1_000e6)` succeeds (buffered funds present), `vault.balanceOf(address(cdo)) == 1_000e6` while `fot.balanceOf(address(vault)) == 990e6`; a full redemption of all minted strategy tokens reverts at `underlyingToken.safeTransfer` inside `_transferFundedClaim`/`_transferDefaultRecovery` for the final claimant.
