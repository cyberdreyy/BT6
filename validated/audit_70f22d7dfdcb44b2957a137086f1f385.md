## Title
Confirmations from a deleted access key remain counted toward `num_confirmations`, allowing execution of other requests below the live-member threshold - (File: `multisig/src/lib.rs`)

### Summary
`DeleteKey` in `execute_request` removes only the requests *originated* by the deleted key and clears `num_requests_pk` for that key, but it never scans and purges that key's entries from `confirmations` on requests originated by *other* keys. `confirm()` counts entries in the stale `confirmations` set against the fixed `num_confirmations` threshold without checking whether the confirming key still exists on the account. This mirrors the analog "unit not recalculated on curve modification" bug class: a derived/cached count (`confirmations.len()`) silently diverges from the true set of live members after the underlying membership changes, and the code that consumes it (`confirm`) never re-validates against reality.

### Finding Description
In `multisig/src/lib.rs`, the `DeleteKey` branch of `execute_request` is: [1](#0-0) 

It only removes requests where `r.signer_pk == pk` (i.e., requests *added by* the deleted key), and only clears `num_requests_pk` for that key. It does **not** iterate `self.confirmations` to strip the deleted key's public key from confirmation sets of requests that were *added by other keys* but already confirmed by the now-deleted key.

`confirm()` then works purely off the stored `HashSet<PublicKey>` size versus the constant threshold `num_confirmations`: [2](#0-1) 

There is no re-validation in `confirm()` (or in `assert_valid_request`) that every public key present in `confirmations` still exists as a live access key on the account. Once a key is deleted via one `DeleteKey` request/execution, any *other* pending request that this key had previously confirmed keeps that confirmation "banked" in `self.confirmations`. A binding is broken here: the intended equality is `confirmations.len() >= num_confirmations` should mean "at least `num_confirmations` **currently valid** members approved," but the actual state is "at least `num_confirmations` **public keys that were ever recorded**, some possibly already revoked, approved."

### Impact Explanation
This crosses the "multisig request executed below threshold" boundary explicitly listed as Critical impact. Concretely:
- A K-of-N multisig is set up with N keys.
- One key (say key X) confirms request A (a `Transfer`, `FunctionCall`, or `AddKey`/access-granting request) that is not yet at threshold, and confirms it early, then a separate request deletes key X (e.g. because it's compromised, an employee left, or as routine key rotation).
- Because `DeleteKey`'s cleanup only removes requests *authored* by X, request A's confirmation set still contains X's public key.
- The remaining live members then confirm request A. The stale confirmation from the now-nonexistent key X still counts toward `num_confirmations`, letting request A execute with fewer *live* signer approvals than the configured threshold intends — e.g., a 3-of-4 multisig can execute with only 2 live keys' approval plus 1 phantom (revoked) approval.
- Since request actions include `Transfer`, `FunctionCall` (arbitrary contract calls), and `AddKey`, this can result in unauthorized movement of funds or unauthorized privilege grants controlled by fewer real approvers than the threshold guarantees.

### Likelihood Explanation
This requires no adversarial timing exploit beyond ordinary contract usage: any account operating this multisig that (a) has an outstanding un-executed request with a partial confirmation, and (b) later executes a `DeleteKey` for the key that gave that partial confirmation (a normal key-rotation/compromise-response action) will end up in this state. No malicious collusion or privileged bypass is needed beyond the normal permitted operations of the contract; it is a straightforward sequencing of legitimate multisig actions.

### Recommendation
When executing `DeleteKey`, iterate all entries in `self.confirmations` (not just requests authored by the deleted key) and remove the deleted public key from every confirmation set. Alternatively, in `confirm()`, validate that all keys in a confirmation set are still valid access keys before counting them toward `num_confirmations` (though this is harder without querying account keys on-chain, as noted in the contract's own "Gotchas" section). The safer and simpler fix is the former: on `DeleteKey`, scan `self.confirmations.iter()` and remove `pk` from every set, decrementing effective participation for that key everywhere, not only in requests it originated.

### Proof of Concept
1. Deploy multisig with keys `[X, Y, Z, W]`, `num_confirmations = 3`.
2. Key `Y` calls `add_request` (not `add_request_and_confirm`) for `receiver_id = self`, action `Transfer{amount}`. Request id `R1`, 0 confirmations.
3. Key `X` calls `confirm(R1)` → confirmations = `{X}` (1/3).
4. Separately, keys `Y`, `Z`, `W` create and execute a `DeleteKey{public_key: X}` request (3 confirmations reached, meets threshold, executes, removes `X`'s access key from the account).
   - `execute_request`'s `DeleteKey` branch only removes requests where `signer_pk == X` — `R1` was authored by `Y`, so it is untouched; `R1`'s confirmation set `{X}` is not cleared.
5. Key `Y` calls `confirm(R1)` → confirmations = `{X, Y}` (2/3).
6. Key `Z` calls `confirm(R1)` → confirmations.len()+1 = 3 >= 3 → `R1` executes the `Transfer`.
   - Only `Y` and `Z` are live keys that actually approved; `X`'s stale confirmation (recorded before its key was deleted) made up the third "confirmation," so the transfer executed with only 2 of 3 required *live* approvals. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
