Confirmed: the `Message.Validate()` in `core/services/gateway/api/message.go` only checks length bounds on `MessageId`, but crucially the `MessageId` is required to be signed by the client (part of `GetRawMessageBody`), so a legacy user message's `MessageId` is fully attacker-chosen but must be paired with a valid signature from *some* registered node/user key — however, in `handler.go`'s `HandleLegacyUserMessage`, the mapping keyed by `MessageId` has no uniqueness check against a concurrently in-flight request from a different sender.

### Title
Cross-user response hijacking via unvalidated, attacker-controlled `MessageId` reuse in legacy WebAPI gateway trigger callback map - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` stores the pending user callback in a shared map keyed solely by the client-supplied `msg.Body.MessageId`, with no check for whether that ID is already associated with another in-flight request. `handler.handleWebAPITriggerMessage` looks up and *deletes* the callback purely by `MessageId` when a DON node responds, and delivers the response to whatever callback is registered under that key at that time.

### Finding Description
In `core/services/gateway/handlers/capabilities/handler.go`:
- `HandleLegacyUserMessage` unconditionally overwrites `h.savedCallbacks[msg.Body.MessageId]` with the new request's callback: [1](#0-0) 
- `handleWebAPITriggerMessage` routes the DON's response purely by `MessageId`, with no verification that the response corresponds to the same requester/session that originally submitted it: [2](#0-1) 
- The `MessageId` itself is fully caller-controlled — it comes straight from the JSON-RPC request `ID` field via `DecodeJSONRequest`, with only length/charset checks in `Validate()`, no uniqueness enforcement: [3](#0-2) [4](#0-3) 

This mirrors the H-12 root cause pattern: a critical routing/attribution decision (which party's action/result applies) is made using an attacker-supplied identifier that is never validated for uniqueness/ownership before being trusted to route a privileged response — analogous to how the TOFT bug trusted `msg.sender`/unvalidated params to route fund transfers to an attacker-controlled destination.

An unprivileged/unauthenticated gateway client can submit a legitimate-looking `web_api_trigger` legacy request using a `MessageId` that happens to collide with (or is raced against) another user's currently pending request. Because storage into `savedCallbacks` is a simple map write with no ownership check, the attacker's callback overwrites the victim's. When the DON eventually responds using that shared `MessageId`, `handleWebAPITriggerMessage` delivers the (potentially sensitive) trigger response to the attacker's callback instead of the original requester, per the code cited above. Note: by contrast, the newer v2 HTTP trigger handler (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`) explicitly detects and rejects a duplicate/reused request ID ("token has already been used") — confirming this uniqueness/ownership check is a recognized requirement that was omitted in the legacy handler path.

### Impact Explanation
If exploitable in a deployment still using the legacy WebAPI trigger DON-ID path, this allows cross-user response confusion: an unauthenticated/unprivileged actor can intercept another user's `web_api_trigger` response payload (which may include workflow trigger data returned by DON nodes), or cause denial of the legitimate requester's callback. This is a concrete "cross-user response confusion" per the accepted class.

### Likelihood Explanation
Exploitation likelihood depends on:
1. Whether the legacy WebAPI gateway path (`HandleLegacyUserMessage` / `handleWebAPITriggerMessage`) is still deployed/reachable in production (the newer v2 handler in the same repo has since added a request ID reuse check, suggesting the legacy path may be deprecated or less used).
2. The attacker's ability to guess or race a concurrently pending `MessageId` used by a victim — `MessageId` values are caller-chosen and not necessarily random/secret, so if a victim's client uses a predictable ID (e.g., derived from workflow name/timestamp) this is feasible; if victims use random UUIDs, this narrows to a race-condition/second-mover overwrite rather than pure guessing.

I could not fully verify from the index whether the legacy path (`gateway.handlers[donID]` / `isLegacyRequest` branch in `core/services/gateway/gateway.go`) is still actively wired into a production DON configuration or is a deprecated compatibility path — this would need to be confirmed via a Devin session with full repo access to check current gateway job/service configs.

### Recommendation
- Enforce single-use, per-sender uniqueness on `MessageId` in `HandleLegacyUserMessage`, rejecting (rather than silently overwriting) a request when the ID is already registered and not yet expired, mirroring the "token has already been used" check already present in `http_trigger_handler.go`.
- Bind the saved callback to the authenticated sender/signer address extracted during `Message.Validate()` (`m.Body.Sender`), and verify that the node response's originating requester matches before dispatching the response.

### Proof of Concept
1. Victim submits a legacy `web_api_trigger` request to the gateway with `MessageId = "X"`, signed with their key; `HandleLegacyUserMessage` stores `h.savedCallbacks["X"] = victimCallback` and forwards to all DON members [5](#0-4) .
2. Before the DON responds, attacker submits their own legacy `web_api_trigger` request also using `MessageId = "X"` (signed with attacker's own key — signature validity only proves attacker's identity, not the message ID's uniqueness). This overwrites `h.savedCallbacks["X"] = attackerCallback`.
3. When a DON node responds with `MessageId = "X"` (destined for the victim's original trigger), `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, finds the attacker's callback, and delivers the victim's response to the attacker [6](#0-5) .

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {

	return nil
}

func (*JsonRPCCodec) DecodeJSONRequest(request jsonrpc2.Request[json.RawMessage]) (*Message, error) {
	var msg Message
	err := json.Unmarshal(*request.Params, &msg)
	if err != nil {
		return nil, err
	}
	msg.Body.MessageId = request.ID
	msg.Body.Method = request.Method
	return &msg, nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
