### Title
Legacy Gateway `web_api_trigger` messages are fanned out to all DON members without any sender allowlist check - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`(h *handler) HandleLegacyUserMessage` validates only payload shape, message age, and method name before forwarding the request to every `donConfig.Members` node via `don.SendToNode`. The code contains an explicit `// TODO: apply allowlist and rate-limiting here` right before the method check, and no allowlist, quota, or per-sender authorization check exists anywhere in the function or its call path.

### Finding Description
The gateway ingress path (`gateway.go:ProcessRequest`) decodes the raw request, calls `msg.Validate()` (structural/signature validation only, per `api.Message.Validate` referenced from `core/services/gateway/handlers/common/message_util.go`), and dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)`. [1](#0-0) 

Inside `HandleLegacyUserMessage`, the checks performed are: payload JSON decode success, non-zero `Timestamp`, message-age staleness, and `msg.Body.Method == MethodWebAPITrigger`. Immediately before the method check sits the comment `// TODO: apply allowlist and rate-limiting here`, and no code enforces an allowlist tying the message `Sender` to `donConfig` or a specific workflow/subscription. [2](#0-1) 

After these checks, `common.ValidatedRequestFromMessage` only verifies that `MessageId` and `Method` are non-empty — it performs no sender authorization — and the resulting request is saved as a callback and forwarded to **every** `h.donConfig.Members`. [3](#0-2) [4](#0-3) 

The existing unit test suite for this handler explicitly documents this gap with the note: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated`, and does not test rejection of unallowlisted senders — only malformed payload, stale message, and invalid method are tested. [5](#0-4) 

By contrast, the newer v2 HTTP capability gateway (`core/services/gateway/handlers/capabilities/v2/http_handler.go`) implements per-workflow rate limiting (`userRateLimiter` from `cresettings.Default.PerWorkflow.HTTPTrigger.RateLimit`) and a dedicated `WorkflowMetadataHandler` for authorization on trigger requests, confirming that the legacy `handler.go` path lacks the equivalent protection that is considered necessary in the newer implementation. [6](#0-5) [7](#0-6) 

### Impact Explanation
Any holder of a valid signing keypair (not necessarily allowlisted for the targeted DON/workflow) can craft a self-signed `api.Message` with `Method: MethodWebAPITrigger` and any `DonId` that maps to a configured legacy handler, causing the gateway to broadcast the request to all `donConfig.Members` nodes. This matches the "unauthorized job run" / "resource exhaustion" bounty class: unauthorized triggering of workflow-node processing and consumption of node resources for a DON/workflow the sender does not own, without any per-sender allowlist or quota gate.

### Likelihood Explanation
Feasibility is high and repeatable: the attacker needs only an ECDSA keypair to sign a `Message`, no DON-specific credential or allowlist membership. Only structural checks (payload shape, non-stale timestamp, and method name) gate the request; none of them verify the sender is authorized for that `DonId`/workflow. This is directly reachable through the public gateway ingress path (`gateway.go:ProcessRequest`).

### Recommendation
Implement the sender allowlist/quota check called out in the TODO comment before forwarding to `don.SendToNode`: verify `msg.Body.Sender` (or the corresponding public key/digest) against a per-DON/per-workflow allowlist and apply per-sender rate limiting analogous to `nodeRateLimiter`/`userRateLimiter` used elsewhere in the codebase (e.g., the v2 HTTP handler's `PerWorkflow.HTTPTrigger.RateLimit`), rejecting non-allowlisted or quota-exceeded senders with `api.HandlerError`/`api.UnauthorizedError` prior to saving the callback and broadcasting to DON members.

### Proof of Concept
1. In `core/services/gateway/handlers/capabilities/handler_test.go`, add a test case `"sad case sender not allowlisted"`:
   - Generate a fresh ECDSA keypair unrelated to any configured DON member/allowlist config (reuse the existing `triggerRequest(t, privateKey, ...)` helper used by other subtests).
   - Call `handler.HandleLegacyUserMessage(ctx, msg, cb)`.
   - Assert the callback response has `ErrorCode` indicating rejection (e.g., a new `api.Unauthorized`/`api.HandlerError`) and that `don.SendToNode` (mocked) was **never** called for any member.
2. Run against current code: the mocked `don.SendToNode` will be invoked once per `donConfig.Members` entry regardless of sender, and the callback will receive a forwarded/successful path instead of a rejection — demonstrating the missing allowlist enforcement.

// ValidatedRequestFromMessage converts a legacy Gateway Message to a JSON-RPC request
func ValidatedRequestFromMessage(msg *api.Message) (*jsonrpc.Request[json.RawMessage], error) {
	if msg == nil {
		return nil, errors.New("nil message")
	}
	if msg.Body.MessageId == "" {
		return nil, errors.New("message ID is empty")
	}
	if msg.Body.Method == "" {
		return nil, errors.New("method is empty")
	}
	params, err := json.Marshal(msg)
	if err != nil {
		return nil, fmt.Errorf("failed to marshal message: %w", err)
	}
	rawParams := json.RawMessage(params)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      msg.Body.MessageId,
		Method:  msg.Body.Method,
		Params:  &rawParams,
	}
	return req, nil
}
