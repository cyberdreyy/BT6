### Title
External-initiator credentials are treated as a valid "user" and can trigger arbitrary job runs by integer job ID via `PipelineRunsController.Create` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` sets the same context key used for authenticated users (`SessionUserKey`) to a synthetic `clsessions.User{Role: clsessions.UserRoleRun}`, so `auth.GetAuthenticatedUser(c)` returns `isUser=true` for EI callers. This causes `PipelineRunsController.Create` to enter the branch explicitly commented as "only users are allowed to run jobs using int IDs - EIs not allowed," letting an EI credential holder invoke `prc.App.RunJobV2` for any numeric job ID, not just a job bound to that initiator.

### Finding Description
The route is registered in `core/web/router.go` at the `userOrEI` group: [1](#0-0) 
This group authenticates via `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, or `auth.AuthenticateBySession`, and wraps `prc.Create` with `auth.RequiresRunRole`.

Inside `auth.AuthenticateExternalInitiator`, after validating the EI's access-key/secret against the DB, it stores the EI object under `SessionExternalInitiatorKey` but also fabricates a `clsessions.User{Role: clsessions.UserRoleRun}` and stores it under `SessionUserKey`: [2](#0-1) 

`RequiresRunRole` reads this fabricated user and, seeing `Role != UserRoleView`, allows the request through: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code explicitly intends to distinguish EI callers from real users via `auth.GetAuthenticatedUser(c)`, with a comment stating EIs are not allowed to use this int-ID path: [4](#0-3) 

Because `GetAuthenticatedUser` cannot distinguish a real DB-backed user from the synthetic EI-derived user (both are `*clsessions.User` objects retrieved from the same context key), `isUser` is `true` for EI callers too, and the numeric job ID is parsed and passed straight into `prc.App.RunJobV2(ctx, jobID, nil)` with no check that the job is associated with the calling EI. The webhook/UUID-bound job type (which previously tied an EI to a specific job) has been removed (`job.ErrJobTypeRemoved`), so there is no remaining mechanism binding an EI to a specific job for the integer-ID path — any registered EI can trigger a run of any job by supplying its numeric ID.

### Impact Explanation
An external-initiator credential holder — a restricted credential type intended only to trigger its own registered webhook — can trigger arbitrary job runs for any job in the node by integer ID, contradicting the code's own stated security boundary ("EIs not allowed"). Depending on the job (e.g., a job with an on-chain transaction task), this could result in unauthorized job execution and unintended fund movement or repeated/DoS-style job triggering, matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Exploitation only requires a valid, low-privilege EI `AccessKey`/`Secret` (registered by any account able to create an external initiator, or leaked/compromised EI credentials) and knowledge of/guessing a numeric job ID. No user session, API token, or elevated role is needed. The request is a single unauthenticated-as-user POST to `/v2/jobs/:ID/runs` with the EI headers, making this trivially repeatable.

### Recommendation
Do not overload `SessionUserKey` for EI identity. Introduce a distinct check (e.g., verify absence of `SessionExternalInitiatorKey` or use a dedicated flag) in `PipelineRunsController.Create` so the int-ID run path can genuinely exclude EI-authenticated requests, consistent with the existing code comment. Alternatively, if EI-triggered runs by integer ID are actually intended, remove the misleading comment and add explicit binding logic ensuring an EI can only trigger jobs it is associated with.

### Proof of Concept
1. Register an `ExternalInitiator` via `POST /v2/external_initiators` (or via `cltest.CreateExternalInitiatorViaWeb`), capturing `AccessKey`/`Secret`.
2. Create an unrelated job (e.g., via `cltest.MustInsertJobSpec`) with a known integer `job.ID` not referencing the EI at all.
3. Send `POST /v2/jobs/<jobID>/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the EI's credentials (using `cltest.UnauthenticatedPost` with those headers, mirroring `TestRunner_WebhookJobRemoved` pattern at `core/services/job/runner_integration_test.go:838-846` but pointing at a non-UUID/int job ID).
4. Assert response is `200 OK` and a new row appears in `pipeline_runs` for that job (via `prc.App.PipelineORM().FindRun`), proving `RunJobV2` was invoked for the EI caller despite the "EIs not allowed" comment.
5. Additionally, add/extend a Go unit test for `auth.GetAuthenticatedUser` invoked after `auth.AuthenticateExternalInitiator` in a `gin.Context`, asserting `isUser == true`, directly demonstrating the identity confusion at `core/web/auth/auth.go:148` and `core/web/auth/auth.go:178-187`.

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
