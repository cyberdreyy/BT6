### Title
Claimed instant withdrawals are never removed from `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, so paid-out funds are double-counted in default recovery and claimants are left insolvent - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
CVE-2016-9846 is a resource leak: `update_cursor_data_virgl` allocates memory on every cursor update without freeing the previous buffer, so repeated attacker-driven calls accumulate un-released resources. The analog in `IdleCreditVault` is the instant-withdraw receipt accounting: `requestInstantWithdraw` records per-epoch entries in `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch`, but the normal claim path `claimInstantWithdrawRequest` never releases them — the "allocation" is never freed. Later, `finalizeDefaultRecovery`/`_defaultPrefundedInstantReserve` reads that stale, leaked accounting and treats already-paid-out funds as both outstanding claim basis and already-held reserve.

### Finding Description
When a user requests an instant withdrawal, the vault records the receipt twice: in the aggregate `instantWithdrawsRequests` and in the per-epoch mappings [1](#0-0) . The funded claim path burns the receipt and zeroes only the aggregate — it never clears `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` or decrements `instantWithdrawClaimsByEpoch[currentEpoch]` [2](#0-1) . Only the defaulted-receipt path `_claimDefaultedInstantWithdrawRequest` clears those entries [3](#0-2) .

`collectInstantWithdrawFunds` reduces `pendingInstantWithdraws` but not the per-epoch claim mappings [4](#0-3) . At default finalization, `defaultPendingClaimBasis` adds the full (stale) `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0` [5](#0-4) , and `_defaultPrefundedInstantReserve` counts `instantBasis - pendingInstant` — i.e. the already-claimed amount — as underlying "already held" by the strategy [6](#0-5) . Those funds were already transferred out to the claimant, so the reserve credit is phantom.

### Impact Explanation
Concrete sequence (epoch N, partial instant funding, then borrower default):

1. Users A and B each request 100 USDC instant withdrawals → `pendingInstantWithdraws = 200`, `instantWithdrawClaimsByEpoch[N] = 200`.
2. The CDO funds only 100 via `collectInstantWithdrawFunds` → `pendingInstantWithdraws = 100`; A claims and receives the 100 (leaving B's 100 unfunded).
3. Borrower defaults; the CDO calls `finalizeDefaultRecovery`. Basis includes the stale 200 instead of the real 100 owed, and `_defaultPrefundedInstantReserve` credits `200 - 100 = 100` of phantom "already-held" reserve into `defaultRecoveryReserve` [7](#0-6) .
4. `defaultRecoveryPrice` is computed against real funds that are short by exactly the leaked amount. When defaulted claimants withdraw via `_transferDefaultRecovery`, the last claimant's transfer reverts on insufficient balance — a 100 USDC permanent insolvency/freezing of recovery payouts per leaked unit.

This breaks the solvency/one-receipt-one-payout invariant: one unit of underlying backs two claims (A's paid claim and A's residual entry in the recovery basis/reserve). The loss is quantified as the sum of all same-epoch instant withdrawals that were funded and claimed before default, which an unprivileged tranche holder directly controls by requesting and claiming instant withdrawals.

### Likelihood Explanation
Requires three honest-actor-aligned conditions: (a) instant withdrawals enabled and partially funded in the same epoch, (b) an instant claimant actually claims before the borrower defaults, (c) a default occurs while `pendingInstantWithdraws > 0`. The attacker only needs to be a KYC'd tranche holder making ordinary `requestInstantWithdraw`/claim calls — no privileged action and no reliance on malicious roles. The stale-mapping leak exists unconditionally in `claimInstantWithdrawRequest`; only the default-finalization path exposes the insolvency. Medium likelihood gated by the default requirement, but the accounting leak itself is deterministic and repeatable by any lender.

### Recommendation
Clear the per-epoch instant receipt when a funded instant claim is paid: in `claimInstantWithdrawRequest`, zero `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (or track/store the request epoch) and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount, mirroring `_claimDefaultedInstantWithdrawRequest`. Ensure `pendingInstantWithdraws`, per-user by-epoch entries, and `instantWithdrawClaimsByEpoch` stay consistent so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only ever see live, unpaid claims.

### Proof of Concept
Foundry fork test sketch (modeled on `test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: deposit users A and B, start epoch, enable instant withdraws
// epoch N running:
cdoEpoch.requestInstantWithdraw(A, 100e6);   // pendingInstant=100, claimsByEpoch[N]=100
cdoEpoch.requestInstantWithdraw(B, 100e6);   // pendingInstant=200, claimsByEpoch[N]=200
// CDO partially funds: getInstantWithdrawFunds moves only 100 -> pendingInstant=100
// A claims normally:
vm.prank(A); cdoEpoch.claimInstantWithdrawRequest();
// assert stale leak:
assertEq(vault.instantWithdrawsRequestsByEpoch(A, vault.epochNumber()), 100e6); // never cleared
assertEq(vault.instantWithdrawClaimsByEpoch(vault.epochNumber()), 200e6);        // still counts paid claim
// borrower defaults mid-epoch; owner calls _handleBorrowerDefault -> finalizeDefaultRecovery
// reserve credited 100e6 phantom (200-100) while only B's 100e6 is real pending debt
// B (or another defaulted claimant) claims last -> safeTransfer reverts / payout diluted by ~50%
assertLt(underlying.balanceOf(address(vault)), requiredPayout); // insolvency == leaked claim amount
```

The assertion that `instantWithdrawsRequestsByEpoch[A][epoch]` remains non-zero after a fully funded claim is the direct "leaked allocation" evidence, reproducible without any privileged misbehavior.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
