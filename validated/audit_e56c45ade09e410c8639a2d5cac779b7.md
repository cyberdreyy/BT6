### Title
Masker `Close()` flushes unmatched secret prefix bytes unmasked on stream teardown, leaking partial secret on job cancellation - ([File: common/buildlogger/internal/masker/masker.go])

### Summary
When a job's process is killed via context cancellation (including via `executors.WithContext`'s `CancelFunc` chain), the executor's `Run()` immediately closes the per-command stdout/stderr writer chain. If a masked secret's bytes were mid-match in the masker at that moment, `masker.Close()` writes the unmatched prefix of the real secret value to the trace instead of `[MASKED]`, violating the masking invariant.

### Finding Description
Every executor (`executors/shell/shell.go:72-133`, `executors/instance/instance.go:82-95`, `executors/ssh/ssh.go:55-73`, docker's `steps.go`) follows the same pattern: `stdout := s.BuildLogger.Stream(...)`, `defer stdout.Close()`, run the command, and on `<-cmd.Context.Done()` kill the process and return. `cmd.Context` is ultimately derived from the job's build context, which is exactly what `executors.Environment.WithContext`'s returned `context.Context`/`CancelFunc` feeds into (`common/build.go:1592-1596`, `executors/environment.go:12-15`). Cancelling that context (autoscaler instance disappearing, prepare/build timeout, manual job cancel) makes the shell executor's select case fire, killing the child process and returning, which runs the deferred `stdout.Close()`/`stderr.Close()`.

Each `Stream()` call builds an independent per-stream wrap chain ending in `masker.New` (`common/buildlogger/build_logger.go:213-224`). The `masker` type tracks partial phrase matches in `m.matching` across `Write()` calls (`common/buildlogger/internal/masker/masker.go:48-138`). If the child process is killed exactly after writing some but not all bytes of a masked value (e.g. echoing a variable across multiple writes/reads before being SIGKILLed), `m.matching` is `>0` and `<len(m.phrase)` when `Close()` fires:

```
func (m *masker) Close() error {
	var werr error
	if m.matching == len(m.phrase) {
		_, werr = m.next.Write(mask)
	} else {
		_, werr = m.next.Write(m.phrase[:m.matching])   // <-- raw secret prefix, unmasked
	}
	...
}
``` [1](#0-0) 

This is asymmetric with `tokensanitizer`'s `Close()` (`common/buildlogger/internal/tokensanitizer/token_masker.go:205-225`), which unconditionally emits `[MASKED]` when `m.masked` is true (i.e., when in the middle of collecting secret alphabet characters), specifically to avoid leaking secret content on teardown. The generic `masker` has no equivalent protection: `m.phrase[:m.matching]` is a literal prefix of the actual secret value.

### Impact Explanation
On job cancellation (or any early process kill) that truncates output mid-secret, a prefix of the CI/CD masked variable's real value is written unmasked into the persisted job trace. Since masked/protected variables are frequently values a lower-privileged pipeline author is not supposed to learn (e.g. protected deploy tokens used on protected branches), this provides a viable oracle/leak path: an attacker who can trigger echoing of the secret in controlled chunks and cancel the job at the right point can exfiltrate the secret's prefix into logs they can read, repeated over multiple pipeline runs to reconstruct more of the value.

### Likelihood Explanation
Reachable and deterministic given the right timing: an unprivileged pipeline author fully controls the job script (can force chunked writes with delays, e.g. `printf` in pieces with `sleep`) and can trigger cancellation of their own job via the GitLab UI/API at will, or rely on `GetBuildTimeout`/`GetPrepareTimeout` context cancellation. No race in the writer chain itself is required — `Write`/`Close` on a given stream are always sequential — the bug is a deterministic Close-time fallback, not a data race. It is repeatable by construction, only requiring the attacker to line up cancellation with the secret being split across writes.

### Recommendation
Change `masker.Close()`'s partial-match branch to emit `[MASKED]` (or drop the bytes entirely) instead of `m.phrase[:m.matching]` whenever `m.matching > 0`, mirroring the protective behavior already used in `tokensanitizer.Close()`. This trades a rare false-positive mask for eliminating any possibility of a raw secret-prefix leak on stream teardown.

### Proof of Concept
```go
func TestMaskerCloseWithPartialMatchLeaksPrefix(t *testing.T) {
    buf := new(bytes.Buffer)
    secret := "super-secret-token-value"
    m := masker.New(internal.NewNopCloser(buf), [][]byte{[]byte(secret)})

    // simulate a chunked write truncated by process kill/context cancel
    // before the final matching byte arrives
    _, err := m.Write([]byte(secret[:len(secret)-5]))
    require.NoError(t, err)

    // simulate stream teardown triggered by cmd.Context.Done() -> Close()
    require.NoError(t, m.Close())

    out := buf.String()
    assert.NotContains(t, out, secret[:len(secret)-5],
        "partial secret prefix must not appear unmasked in trace after teardown")
}
```
Expected current behavior (bug): assertion fails — `buf` contains the raw prefix `super-secret-token-va`. After applying the fix (emit `[MASKED]` for any `m.matching > 0` in `Close()`), the assertion passes.
