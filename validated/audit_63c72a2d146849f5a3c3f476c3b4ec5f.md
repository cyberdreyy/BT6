### Title
Zip archive extraction lacks path-traversal validation, allowing `os.Remove`/`os.OpenFile(O_TRUNC)` outside the intended extraction root - (File: helpers/archives/zip_extract.go)

### Summary
`extractZipFile`/`extractZipFileEntry`/`extractZipSymlinkEntry` use `file.Name` from the zip archive directly as a filesystem path with no validation against absolute paths or `..` traversal components, then call `os.Remove(file.Name)` followed by `os.OpenFile(..., O_CREATE|O_TRUNC)` (or `os.Symlink`) without any check that the resolved path stays inside the extraction root. This is a classic "zip-slip" pattern that allows a crafted archive entry name to delete/truncate/overwrite arbitrary files reachable by the runner helper process, outside the job's cache/artifact directory.

### Finding Description
`extractZipFile` (helpers/archives/zip_extract.go:61-83) only special-cases `.git` paths via `errorIfGitDirectory` (helpers/archives/path_check_helper.go:21-31), which is solely a warning heuristic, not a security boundary. For regular files, `extractZipFileEntry` (zip_extract.go:41-59) does:
```
_ = os.Remove(file.Name)
out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
```
`file.Name` comes straight from the untrusted zip's central directory entries (`archive.File[i].Name`). There is no `filepath.Clean`, no absolute-path rejection, and no "resulting path must have extraction-dir prefix" check anywhere in this file or in `ExtractZipArchive`/`ExtractZipFile`. `extractZipDirectoryEntry` (`os.Mkdir(file.Name, ...)`) and `extractZipSymlinkEntry` (`os.Remove` + `os.Symlink`) have the same gap, and `extractZipFile` itself calls `os.MkdirAll(filepath.Dir(file.Name), 0o777)` unconditionally before dispatching on entry type — creating arbitrary parent directory structure for any traversal path.

By contrast, the sibling tar+zstd extractor explicitly guards against this: `commands/helpers/archive/tarzstd/tarzstd_extractor.go:58-64` computes `filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects any resulting path that doesn't have the extraction dir as prefix. No equivalent check exists in the zip path (`helpers/archives/zip_extract.go`, used via `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go:26-33` and the fastzip extractor).

Exploit flow: a pipeline author supplies a cache/artifact zip (cache and artifact archives are attacker-controlled content within a job) containing an entry named e.g. `../../../some/sensitive/or/adjacent/path` (or an absolute path, depending on OS zip handling). When the runner helper extracts this archive during cache-restore/artifact-download, `extractZipFile` resolves the entry to a path outside the intended extraction root, `os.Remove` silently deletes whatever exists there (no existence/ownership check — errors are discarded with `_ =`), and `os.OpenFile(O_TRUNC)` recreates it with attacker content and 0-safe permissions from the archive. This isn't limited to name-collision within the extraction root as posed in the question — it's a strictly stronger primitive: full path traversal, since nothing restricts entries to the extraction root at all.

### Impact Explanation
Depending on filesystem layout and helper process privileges, this can delete or truncate files outside the job's build/cache directory that are reachable by the runner helper's user (e.g. sibling job working directories on a shared host/shell executor, or other files within the same container/volume mount as the extraction root). This matches the scoped impact: helper state corruption / DoS affecting the job or files adjacent to the extraction root, and is strictly worse than pure name-collision because it's unrestricted path traversal, not merely a same-directory clash.

### Likelihood Explanation
Feasible for any unprivileged pipeline author who controls artifact/cache zip contents (trivial to construct via Python's `zipfile` with a crafted `ZipInfo.filename` containing `../`). No special permissions or admin action needed; the archive is processed automatically during cache restore or artifact download by the runner helper. Fully repeatable and deterministic.

### Recommendation
Before performing any filesystem operation on `file.Name`, canonicalize the target path (`filepath.Join(extractionRoot, file.Name)` then `filepath.Abs`) and reject entries whose resolved path is not prefixed by the extraction root (mirroring the check already present in `commands/helpers/archive/tarzstd/tarzstd_extractor.go:58-64`). Apply this check in `extractZipFile` before dispatching to `extractZipDirectoryEntry`, `extractZipSymlinkEntry`, and `extractZipFileEntry`, and before the `os.MkdirAll(filepath.Dir(file.Name), 0o777)` call. Additionally, avoid unconditional `os.Remove` without first confirming the target path is one that was itself created during this extraction (or at least resides strictly under the extraction root).

### Proof of Concept
Go unit test in `helpers/archives/zip_extract_test.go` style:
1. In a temp extraction dir, create a sentinel file at a path one level above the extraction root, e.g. `../sentinel.txt`, with known content.
2. Build an in-memory zip with a single entry named `../sentinel.txt` (or `..%2Fsentinel.txt` depending on encoding) containing attacker content.
3. `cd` into the extraction dir and call `archives.ExtractZipFile(archivePath)` (as `ExtractZipFile`/`ExtractZipArchive` do not take an extraction-root parameter — extraction always happens relative to CWD).
4. Assert: before extraction, sentinel file exists with original content; after extraction, assert it is unexpectedly overwritten/truncated with attacker content — demonstrating `os.Remove`+`os.OpenFile(O_TRUNC)` escaped the intended extraction root due to missing path-traversal validation.
