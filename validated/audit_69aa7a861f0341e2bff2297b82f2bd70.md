### Title
Unbounded growth of `GitLabClient.clients` map keyed by per-job tokens, never evicted after job completion - (File: `network/gitlab.go`)

### Summary
`GitLabClient.getClient` caches an HTTP `client` per unique `URL_Token_CAFile_CertFile` key and never removes entries from the `n.clients` map. Because `UpdateJob`, `PatchTrace`, and `DownloadArtifacts` are invoked with the job-scoped `common.JobCredentials`, whose `Token` is unique and short-lived per job, every job that runs on the shared runner process permanently adds a new entry to the map.

### Finding Description
`getClient` builds the cache key from `credentials.GetURL()`, `credentials.GetToken()`, `credentials.GetTLSCAFile()`, and `credentials.GetTLSCertFile()`, then unconditionally stores a new `*client` under that key if not already present: [1](#0-0) 

The `requestCredentials` interface that keys this cache is implemented both by runner-scoped `RunnerCredentials` (used for `ProcessJob`, which polls with the fairly static runner registration token) and by job-scoped `JobCredentials` (used for `UpdateJob`/`PatchTrace`/`DownloadArtifacts`, whose `Token` is generated fresh by GitLab for each job run and is unique per job): [2](#0-1) 

There is no eviction, TTL, or `delete(n.clients, key)` call anywhere in the file — the `connectionMaxAge` option only affects HTTP transport connection reuse (`withMaxAge`), not map-entry cleanup. As a result, each new job token that flows through `UpdateJob`/`PatchTrace`/`DownloadArtifacts` produces a permanent new map entry (plus its underlying `http.Client`/transport) that lives for the lifetime of the runner process, regardless of whether the job succeeds, fails, or is canceled.

An unprivileged pipeline author does not need any special privilege to trigger this: simply running ordinary CI jobs is sufficient, since GitLab issues a unique `JobCredentials.Token` for every job, and the runner process automatically calls `getClient` with that token during normal `UpdateJob`/`PatchTrace`/artifact-download flows.

### Impact Explanation
Because the runner process (and its `GitLabClient` instance) is shared across all jobs/projects assigned to that runner, an attacker who can queue many jobs (e.g., via a pipeline with many stages/jobs, or scheduled pipelines) causes linear, unbounded growth of `n.clients` and the associated per-entry `http.Client`/transport/connection pool state. Over time this increases memory usage and file descriptor/goroutine consumption for the whole runner process, degrading or eventually crashing job polling and execution for other, unrelated projects sharing that runner — a cross-tenant availability impact rather than a sandbox escape.

### Likelihood Explanation
This requires no special access — any project with jobs on a shared runner can generate an arbitrary number of jobs over time (CI is designed to run many jobs). Each job naturally receives a distinct `JobCredentials.Token`, so the map growth is deterministic and repeatable, not probabilistic. The only constraint is the number of jobs run over the runner's uptime, which is entirely attacker-controlled via triggering pipelines.

### Recommendation
Do not key/cache HTTP clients using job-scoped tokens for `UpdateJob`/`PatchTrace`/`DownloadArtifacts`. Either derive the cache key from stable, low-cardinality runner identity fields (URL + runner token + TLS file paths) and pass the job token as a per-request credential rather than a cache key, or add an eviction mechanism (LRU/TTL, or explicit removal keyed off job completion/cancellation) to `n.clients` so that job-scoped entries are removed once `PatchTrace`/`UpdateJob` reports the job as finished.

### Proof of Concept
Go unit test in `network/gitlab_test.go`:
1. Construct a `GitLabClient` (as in existing tests).
2. Loop `N` times (e.g., N=10000), calling `getClient` (or the higher-level `UpdateJob`/`PatchTrace` with mocked HTTP responses) with a `common.JobCredentials{URL: sameURL, Token: uuid.NewString()}` for each iteration to emulate distinct jobs.
3. Simulate job completion (e.g., call whatever "job finished" hook exists, or just let the call return).
4. Assert `len(gitLabClient.clients) < someBound` (e.g., not equal to `N`) — expected to fail on current code, proving unbounded growth, since no delete/eviction path exists in `getClient`. [1](#0-0)

func (n *GitLabClient) getClient(credentials requestCredentials) (*client, error) {
	n.lock.Lock()
	defer n.lock.Unlock()

	if n.clients == nil {
		n.clients = make(map[string]*client)
	}
	key := fmt.Sprintf(
		"%s_%s_%s_%s",
		credentials.GetURL(),
		credentials.GetToken(),
		credentials.GetTLSCAFile(),
		credentials.GetTLSCertFile(),
	)
	c, ok := n.clients[key]
	if ok {
		return c, nil
	}

	c, err := newClient(
		credentials,
		n.apiRequestsCollector,
		withMaxAge(n.connectionMaxAge),
		withHttpClientOptions(n.httpClientOptions),
		withCertificateDirectory(n.certDirectory),
	)
	if err != nil {
		return nil, fmt.Errorf("new client: %w", err)
	}

	n.clients[key] = c

	return c, nil
}
