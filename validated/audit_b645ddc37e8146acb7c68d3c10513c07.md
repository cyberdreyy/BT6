### Title
Unsanitized `AlternateArchiveFile` path traversal when `FF_HASH_CACHE_KEYS` is enabled - ([File: shells/abstract.go])

### Summary
`newCacheConfig` in `shells/abstract.go` computes `AlternateArchiveFile` from `cacheAlternateKey(humanKey, hashEnabled)`, and when `FF_HASH_CACHE_KEYS` is on, `humanKey` is the raw, **unsanitized** cache key (since `sanitizer` becomes a no-op). That raw `humanKey` is fed straight into `getArchivePath`, which does `path.Join(build.CacheDir, key, "cache.zip")`. Because `path.Join`/`path.Clean` only prevents traversal past the filesystem root `/`, not past `build.CacheDir`, a crafted key containing `..` segments lets the resulting alternate archive path resolve outside `build.CacheDir`.

### Finding Description
In `newCacheConfig` (`shells/abstract.go:133-208`): [1](#0-0) 

when `HashCacheKeys` is on, `sanitizer` is replaced with an identity function, so `humanKey` (`shells/abstract.go:152`) is exactly `rawKey` — the user-controlled, `ExpandValue`-expanded cache key (`shells/abstract.go:138-141`) with no path-traversal cleanup applied.

The primary `hashedKey` is safe because it's always SHA-256 hex (`hasher` is set to the sha256 function under the FF): [2](#0-1) 

However, `AlternateKey`/`AlternateArchiveFile` is computed differently, via `cacheAlternateKey`: [3](#0-2) 

When `hashEnabled` (i.e., `FF_HASH_CACHE_KEYS` on) is true, `cacheAlternateKey` returns `humanKey` itself — the raw unsanitized key — as the alternate key: [4](#0-3) 

`getArchivePath` then builds the file path with `path.Join(build.CacheDir, key, "cache.zip")` (`shells/abstract.go:175`). `path.Join` internally calls `path.Clean`, which only guarantees the result cannot climb above the filesystem root `/`; it does **not** stop `..` segments from climbing above `build.CacheDir` when `CacheDir` is not `/`. So a `key`/cache-key value such as `../../../../tmp/x` (or, more relevantly, a value that walks up to a sibling project/job's cache directory on a shared/host-based cache root) collapses `path.Join(build.CacheDir, "../../other", "cache.zip")` into a path outside `build.CacheDir`.

This directly contradicts the documented purpose of `cachekey.Sanitize` (`cache/cachekey/cachekey.go:20-26`), whose comment states traversals are "resolved... within a virtual root so '..' can never escape beyond the root" — but that sanitizer is explicitly bypassed for `humanKey` under the FF, and the `AlternateArchiveFile`/`AlternateKey` path was not given the FF-off protection (identity hash) that the primary key gets.

Existing test coverage (`shells/abstract_test.go:4185-4209`, the `"hashed, key from job"`/`"hashed, key from user"` cases in `TestNewCacheConfig`) only exercises benign keys (`some-job/some-ref`, `some/user/key`); it never asserts that `AlternateArchiveFile` stays confined to `CacheDir` for keys containing `..` or absolute-looking segments while the hashing FF is enabled — so this case is not caught by current tests.

Attacker-controlled inputs reaching this code: the cache `key:` field in `.gitlab-ci.yml` (expanded via `ExpandValue`, which also expands job variables like `CI_JOB_NAME`/`CI_COMMIT_REF` if referenced), or the default `${jobName}/${gitRef}` composition — both attacker-influenceable by an unprivileged pipeline author.

### Impact Explanation
The `AlternateArchiveFile` is used by the cache-archiver/extractor helper (`--alternate-file` flag, wired in `addCacheUploadCommand`/`addExtractCacheCommand` in `shells/abstract.go`) to read the "other" naming-scheme's timestamp/archive during upgrade/downgrade between hashed and unhashed cache key formats. If that path can be steered outside `build.CacheDir` via a crafted key, the runner helper may read or write a `cache.zip` at an attacker-chosen filesystem location relative to `CacheDir`. On a shared-cache host (e.g., shell executor with `Shared: true`, or Docker/Kubernetes executors sharing a persistent cache volume across projects), this can allow cross-project cache poisoning (writing a malicious alternate archive that a later job on a different project inadvertently upgrades/downgrades into) or reading another job/project's `cache.zip` contents where cache paths for different projects are predictable/adjacent. The exact blast radius depends on the concrete `CacheDir` layout deployed, which I could not fully verify from the indexed files (I was unable to trace the full runtime directory-naming convention linking `CacheDir` to per-project subpaths before running out of investigation budget) — but the code-level primitive is confirmed: **`AlternateArchiveFile` is not confined to `build.CacheDir` when `FF_HASH_CACHE_KEYS` is enabled and the cache key contains `..`/absolute-like segments.**

### Likelihood Explanation
- Precondition: `FF_HASH_CACHE_KEYS` feature flag enabled (this is a supported, user/operator-toggleable flag, not admin-only-secret).
- Attacker only needs to define a `cache: key:` in their own `.gitlab-ci.yml` (or via a variable expanding to one) containing `../` sequences — trivially reproducible, no special privileges beyond being a normal pipeline author.
- The identity of `humanKey` used for `AlternateArchiveFile` is deterministic and directly attacker-supplied, making this reliably repeatable.

### Recommendation
Sanitize/confine `AlternateKey`/`AlternateArchiveFile` independently of the `HashCacheKeys` FF: always run the humanKey through a path-confinement step (e.g., `cachekey.Sanitize`, or explicitly reject/clean any `..`/absolute segments) before it is used to build any filesystem path in `getArchivePath`, regardless of whether `HashCacheKeys` skips sanitization for the *primary* hashed key. Additionally, `getArchivePath` should verify (e.g., via `filepath.Rel`/prefix check against `build.CacheDir` after `filepath.Clean`) that the resulting path is still contained within `build.CacheDir`, and error out otherwise, as defense in depth.

### Proof of Concept
Add to `shells/abstract_test.go` `TestNewCacheConfig` a case such as:

```go
"hashed, alternate key escapes cache dir": {
    cacheDir: "/some/cache/dir",
    buildDir: "/some/build/dir",
    userKey:  "../../../../etc/passwd-dir",
    ffs: map[string]bool{
        featureflags.HashCacheKeys: true,
    },
    // Assertion: AlternateArchiveFile must remain within cacheDir.
},
```

Assertion logic: after calling `newCacheConfig(build, "../../../../etc/passwd-dir")` with `HashCacheKeys` on, compute `absAlt := filepath.Join(buildDir, cfg.AlternateArchiveFile)` (or, if `UsePowershellPathResolver` is set, use `cfg.AlternateArchiveFile` directly) and assert `strings.HasPrefix(filepath.Clean(absAlt), filepath.Clean(cacheDir)+string(filepath.Separator))`. With the current code, this assertion fails because `AlternateArchiveFile` resolves to a path outside `cacheDir` (e.g. `.../etc/passwd-dir/cache.zip`), confirming the bug. A fuzz test over `newCacheConfig(build, userKey)` with path-traversal/separator-laden `userKey` values, asserting `getArchivePath` output (both `ArchiveFile` and `AlternateArchiveFile`) never resolves outside `build.CacheDir`, would also reproduce this reliably for the `AlternateArchiveFile` field specifically when `HashCacheKeys` is on.

// cacheAlternateKey returns the "other" archive key relative to the current FF_HASH_CACHE_KEYS setting.
// When hashing is enabled, the alternate is the unhashed (human-readable) key.
// When hashing is disabled, the alternate is the SHA256-hashed key.
func cacheAlternateKey(humanKey string, hashEnabled bool) string {
	sha256Key := fmt.Sprintf("%x", sha256.Sum256([]byte(humanKey)))
	if hashEnabled {
		return humanKey
	}
	return sha256Key
}
