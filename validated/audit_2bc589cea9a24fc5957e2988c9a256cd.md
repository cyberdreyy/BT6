### Title
Unbounded memory consumption via `getProgramAccounts` RPC when secondary account index is not configured - (File: `rpc/src/rpc.rs`)

### Summary
The Geth GraphQL DoS (CVE-2023-42319) stems from an endpoint that lets an unauthenticated remote client trigger unbounded server-side resource consumption via a single crafted query, with no server-side cap on the work/memory a query can incur. The analogous RPC surface in agave is `getProgramAccounts` (and its siblings `getTokenAccountsByOwner`/`getTokenAccountsByDelegate`), which, when the validator does not have the `ProgramId` secondary account index enabled (the default for most operators unless `--account-index program-id` is explicitly configured), takes a code path that performs a full unindexed accounts scan with **no byte-size limit**, in contrast to the indexed path which enforces `scan_results_limit_bytes`.

### Finding Description
`JsonRpcRequestProcessor::get_filtered_program_accounts` branches on whether the `ProgramId` account index is configured: [1](#0-0) 

When the index is present, it calls `get_filtered_indexed_accounts`, which passes `byte_limit_for_scans` (`self.config.scan_results_limit_bytes`) down into `Bank::get_filtered_indexed_accounts` → `Accounts::load_by_index_key_with_filter`, which tracks accumulated result size and aborts the scan once the configured byte limit is exceeded: [2](#0-1) [3](#0-2) 

However, when the index is **not** configured, the code explicitly takes the alternate branch with the comment "this path does not need to provide a mb limit because we only want to support secondary indexes," and calls `bank.get_filtered_program_accounts`, which delegates to `Accounts::load_by_program_with_filter` — a scan that has **no byte-limit / abort mechanism at all**: [4](#0-3) [5](#0-4) 

This means any external RPC client can call `getProgramAccounts` with a program ID that matches a large number of accounts (e.g., a widely-used program such as the SPL Token program, or any attacker-deployed program with many accounts created cheaply), forcing the validator to materialize the full unfiltered/filtered result set into memory (`collector: Vec<KeyedAccountSharedData>`) with no size cap, then serialize the entire response — comparable to the "memory consumption and daemon hang" described in the GraphQL advisory, where the vendor's stance was that the query endpoint was not designed to withstand hostile clients.

The only mitigations present are filter-count limits (`MAX_GET_PROGRAM_ACCOUNT_FILTERS = 4`) and generic HTTP body-size limits on requests (not responses): [6](#0-5) [7](#0-6) 

None of these bound the size of the *scan result* on the non-indexed path the way `scan_results_limit_bytes` does on the indexed path.

### Impact Explanation
An unauthenticated RPC caller can force a public-facing validator/RPC node to perform an expensive full-database scan and build/serialize an unbounded in-memory result set, exhausting heap memory and/or causing the RPC service thread (single-threaded server per `rpc_service.rs` `.threads(1)`) to hang or the process to OOM. This is a denial-of-service against the RPC endpoint, not consensus-affecting, but it is the same bug class (unbounded resource consumption via a query the server accepts but cannot bound) as the reported Geth GraphQL CVE.

### Likelihood Explanation
Likelihood is high for any validator/RPC operator who exposes `getProgramAccounts` without configuring the `ProgramId` secondary index (the index must be explicitly enabled via `--account-index program-id`; it is not the default in `JsonRpcConfig`). This configuration is common on public RPC endpoints that don't run with that specific index for every program, since the index carries its own memory overhead trade-off. No privileged access, special account state, or crafted transaction is required — a single JSON-RPC HTTP call suffices.

### Recommendation
Enforce a byte/result-size limit (equivalent to `scan_results_limit_bytes`) on the non-indexed path in `get_filtered_program_accounts` (`rpc/src/rpc.rs`), i.e., route `bank.get_filtered_program_accounts` (or `Accounts::load_by_program_with_filter`) through the same size-accumulation/abort mechanism used in `load_by_index_key_with_filter`, rather than assuming that only the indexed path needs bounding. Consider also capping total accounts scanned/returned server-side by default, independent of the secondary index configuration.

### Proof of Concept
1. Configure/run a validator or RPC node with default `JsonRpcConfig` (no `--account-index program-id`).
2. Deploy or select a program ID that owns a very large number of accounts (or repeatedly create many small accounts owned by an attacker-controlled program).
3. Send `{"jsonrpc":"2.0","id":1,"method":"getProgramAccounts","params":["<program_id>"]}` to the node's JSON-RPC HTTP endpoint.
4. Observe unbounded memory growth in the RPC thread while `get_filtered_program_accounts` → `load_by_program_with_filter` collects all matching accounts with no size limit, corresponding to code at: [4](#0-3) [5](#0-4)

    pub async fn get_filtered_indexed_accounts(
        &self,
        bank: &Arc<Bank>,
        index_key: &IndexKey,
        program_id: &Pubkey,
        filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let bank = Arc::clone(bank);
        let index_key = index_key.to_owned();
        let program_id = program_id.to_owned();
        let byte_limit_for_scans = self.config.scan_results_limit_bytes;
        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(
                    &index_key,
                    |account| {
                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.
                        account.owner().eq(&program_id)
                            && filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                    },
                    byte_limit_for_scans,
                )
            })
            .await
            .expect("Failed to spawn blocking task")?;
        if sort_results {
            // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
            accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
        }
        Ok(accounts)
    }

    /// Accumulate size of (pubkey + account) into sum.
    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }

    fn maybe_abort_scan(
        result: ScanResult<Vec<KeyedAccountSharedData>>,
        config: &ScanConfig,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        if config.is_aborted() {
            ScanResult::Err(ScanError::Aborted(
                "The accumulated scan results exceeded the limit".to_string(),
            ))
        } else {
            result
        }
    }

    pub fn load_by_index_key_with_filter<F: Fn(&AccountSharedData) -> bool>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        index_key: &IndexKey,
        filter: F,
        byte_limit_for_scan: Option<usize>,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let sum = AtomicUsize::default();
        let config = ScanConfig::default().recreate_with_abort();
        let mut collector = Vec::new();
        let result = self
            .accounts_db
            .index_scan_accounts(
                ancestors,
                bank_id,
                *index_key,
                |some_account_tuple| {
                    Self::load_while_filtering(&mut collector, some_account_tuple, |account| {
                        let use_account = filter(account);
                        if use_account
                            && Self::accumulate_and_check_scan_result_size(
                                &sum,
                                account,
                                &byte_limit_for_scan,
                            )
                        {
                            // total size of results exceeds size limit, so abort scan
                            config.abort();
                        }
                        use_account
                    });
                },
                &config,
            )
            .map(|_| collector);
        Self::maybe_abort_scan(result, &config)
    }
