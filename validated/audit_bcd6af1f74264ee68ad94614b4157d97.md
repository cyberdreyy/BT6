### Title
Missing pre-dispatch, per-caller request-ID isolation allows cross-workflow ID-squatting DoS in v2 HTTP gateway handler - ([File: core/services/gateway/handlers/capabilities/v2/http_handler.go])

### Summary
The v2 gateway dispatcher `gatewayHandler.HandleJSONRPCUserMessage` performs no request-ID ownership/namespace check before forwarding to `httpTriggerHandler.HandleUserTriggerRequest`. The only collision check is the downstream `setupCallback` map keyed solely on the raw JSON-RPC `id` string, shared globally across all workflows/callers, so any authenticated caller can pre-empt or block another caller's in-flight request merely by reusing the same `id`.

### Finding Description
`gatewayHandler.HandleJSONRPCUserMessage` unconditionally forwards every incoming JSON-RPC request straight to the trigger handler with no ID validation of its own: [1](#0-0) 

Inside `HandleUserTriggerRequest`, request-ID checks occur only in `validateRequestID` (format only: non-empty, no `/`) and later in `setupCallback`, both of which run after per-workflow authorization (`authorizeRequest`) but neither of which scopes uniqueness to the caller/workflow: [2](#0-1) [3](#0-2) 

The `callbacks` map is declared as `map[string]savedCallback // requestID -> savedCallback` with no workflow/owner component in the key: [4](#0-3) 

Because `authorizeRequest` (per-workflow auth) executes before `setupCallback` (global uniqueness), authorization succeeds independently for each caller/workflow, and only afterward does the global map collide. Consequently, two different authenticated callers (different JWTs/workflows) submitting requests with the same `id` concurrently: whichever request reaches `setupCallback` first "wins" and is registered; the second is rejected with `jsonrpc.ErrConflict` ("requestID has already been used") even though it belongs to a completely different, fully-authorized workflow/caller. There is no response data leakage across callers (the rejected request is never stored, and `HandleNodeTriggerResponse` additionally checks shard membership before routing), but a caller who can predict or observe another workflow's `id` (e.g., low-entropy IDs, replayed test IDs, or coordinated submission) can deny that workflow's legitimate trigger request by ID-squatting first.

### Impact Explanation
This maps to a low-severity availability/isolation issue: a caller in one workflow can cause another distinct, authenticated workflow's HTTP trigger request to be rejected (denial of service for that single request) purely by colliding on the JSON-RPC `id`, despite having no relationship to that workflow. It does not achieve response cross-leakage, key/secret disclosure, or job/fund manipulation — the impact is confined to request rejection/blocking (an availability/isolation violation), matching Chainlink's "Denial of service" / minor isolation-violation bounty class rather than a critical compromise.

### Likelihood Explanation
Requires two distinct authenticated callers (any two valid JWTs/workflow credentials — no elevated privilege) and requires the attacker to guess or otherwise learn the victim's chosen `id` ahead of the victim's send, and to win the race to `setupCallback`. Since `id` values are typically caller-chosen (often random UUIDs) this is not trivially exploitable in practice, but the isolation gap is real: the dispatcher and validation layers do not attempt to scope IDs per-caller/per-workflow at any point before the global map check, so if IDs are ever predictable (e.g., sequential, replayed, or based on external/legacy execution ID schemes) the collision is directly exploitable and repeatable.

### Recommendation
Scope the in-flight-request uniqueness key to `(workflowID or authorized key, requestID)` instead of `requestID` alone, e.g., key `h.callbacks` by a composite of `workflowID` + `req.ID` (or the caller's authorized key) so that IDs are only required to be unique within a caller/workflow's own namespace, eliminating cross-workflow collision entirely.

### Proof of Concept
Handler-level integration test in `http_trigger_handler_test.go`:
1. Register two workflows W1 (owner A) and W2 (owner B) in `workflowMetadataHandler`, each assigned to different shards/DONs, each with valid distinct auth credentials.
2. Construct two `jsonrpc.Request[json.RawMessage]` with identical `ID = "collide-1"`, one targeting W1's `workflowID` with A's auth, the other targeting W2's `workflowID` with B's auth.
3. Call `HandleUserTriggerRequest` for both concurrently (e.g., via goroutines with a `sync.WaitGroup`), using two separate mock `handlers.Callback` instances that capture `SendResponse` payloads.
4. Assert: both requests pass `authorizeRequest` independently (no auth error), but exactly one callback records a `jsonrpc.ErrConflict` error response ("requestID: collide-1 has already been used") while the other proceeds normally — demonstrating that a caller belonging to an unrelated workflow can force a conflict/rejection on another caller's identical `id` purely at the shared global `callbacks` map, with no per-workflow ID namespace check occurring earlier in `HandleJSONRPCUserMessage` or `validatedTriggerRequest`.

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
