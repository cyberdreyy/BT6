## Analysis

The M-7 root cause is a **manually specified external-contract interface (function selectors) that was not verified against the actual deployed contract**, causing calls to revert. The strongest reachable analog in marginfi-v2 is the Solend integration, which uses a hand-rolled, manually-encoded CPI interface instead of an IDL-derived one, unlike every other third-party integration in the codebase.

Kamino, Drift, and JupLend integrations all generate their CPI account layouts and instruction discriminators from real, distilled on-chain IDLs via Anchor's `declare_program!` macro [1](#0-0) [2](#0-1) , with a documented workflow (`distill_kamino_macro_idl.py`, `distill_drift_juplend_macro_idl.py`) that fetches the live IDL and regenerates the macro-facing types [3](#0-2) .

Solend is the outlier: its "mock" crate declares the **real mainnet Solend program ID** (`So1endDq2YkqhipRh3WViPa8hdiSpxWy6z3Z6tMCpAo`) [4](#0-3) , but instead of using an IDL macro, it hand-encodes instruction discriminators and account orderings as raw constants: [5](#0-4) . These hand-built `Instruction { program_id: ID, accounts: [...], data: [...] }` structures are constructed manually for `init_obligation`, `deposit_reserve_liquidity_and_obligation_collateral`, and `withdraw_obligation_collateral_and_redeem_reserve_collateral` [6](#0-5) [7](#0-6) [8](#0-7) .

Critically, this "mocks" crate is not test-only scaffolding — it is imported directly into **production instruction handlers** that CPI into the real, hardcoded `SOLEND_PROGRAM_ID`: [9](#0-8) [10](#0-9) [11](#0-10) 

This is exactly the class of bug in M-7: a hardcoded interface (function selector/account layout) baked into the codebase and asserted to match a specific hardcoded external program address, without being mechanically derived from (and kept in sync with) that program's authoritative on-chain interface. If Solend ever changes its instruction argument encoding, discriminator values, or required account list/ordering (analogous to Uniswap's Router → Router 2 migration), every `solend_deposit`, `solend_init_obligation`, and `solend_withdraw` call will either revert outright or — more dangerously — silently succeed against a mismatched account list, since Anchor's account-struct validation only checks the accounts marginfi itself defines (e.g. `#[account(address = SOLEND_PROGRAM_ID)]`), not that the hand-built `Instruction.data`/`accounts` vector still matches Solend's actual current instruction ABI.

### Title
Solend integration uses hand-rolled, unverified instruction encoding instead of IDL-derived CPI, risking interface mismatch with the real Solend program - (File: programs/solend-mocks/src/cpi.rs)

### Summary
Unlike the Kamino, Drift, and JupLend integrations — which build their CPI call data and account layouts from real, distilled Anchor IDLs via `declare_program!` — the Solend integration hand-encodes instruction discriminators (`6`, `14`, `15`) and account orderings as raw byte constants in `programs/solend-mocks/src/cpi.rs`, while declaring the real mainnet Solend program ID and using it directly in production CPI calls from `programs/marginfi/src/instructions/solend/{deposit,withdraw,init_obligation}.rs`.

### Finding Description
`solend-mocks` declares `declare_id!("So1endDq2YkqhipRh3WViPa8hdiSpxWy6z3Z6tMCpAo")`, the real Solend mainnet program [4](#0-3) . Rather than generating the CPI surface from Solend's actual IDL (as is done for Kamino/Drift/JupLend), the crate defines the instruction discriminators and account metas by hand, with a comment noting they were "verified against solend-sdk" at some point in time [12](#0-11) . These hand-built instructions are wired directly into marginfi's production Solend deposit/withdraw/init_obligation handlers, which target the hardcoded `SOLEND_PROGRAM_ID` constant [13](#0-12) . There is no mechanism (analogous to the `distill_*` IDL scripts used for the other three integrations) that re-verifies these hardcoded discriminators/account orderings against Solend's live, canonical interface. This mirrors the root cause of M-7: an externally-integrated contract's real function signature/ABI silently diverging from a hardcoded interface baked into the calling contract.

### Impact Explanation
If the real Solend program's instruction ABI (discriminator values, argument encoding, or required account ordering) diverges even slightly from what is hand-coded here — through a Solend upgrade, deprecation, or migration to a newer program version — every marginfi CPI call into Solend will either revert (denial of service on all Solend-backed banks, freezing already-deposited collateral since withdraw/repay would also break) or, in the worse case, be interpreted with a different account/argument mapping by the Solend program, potentially misrouting deposited liquidity or misreporting obligation state used by marginfi's own accounting (`get_solend_obligation_deposit_amount`, `validate_solend_obligation`). Either outcome has direct financial effect on funds held in Solend-backed Banks.

### Likelihood Explanation
Likelihood is tied entirely to whether/when the real Solend program's ABI changes relative to what was hand-encoded at implementation time. This is a live external-dependency risk rather than a bug that is definitely already triggered on-chain today, but it is structurally identical to the confirmed M-7 root cause: hardcoded interface constants for a named, hardcoded external program address that are not derived from (or continuously validated against) that program's authoritative interface. The absence of an IDL-macro-based generation path for Solend (present for every other integration) is the concrete, reachable weakness.

### Recommendation
Generate the Solend CPI surface from Solend's actual Anchor/SDK IDL using the same `declare_program!` + IDL-distillation workflow already used for Kamino, Drift, and JupLend (`idls/`, `distill_*` scripts), instead of hand-encoding discriminators and account metas in `programs/solend-mocks/src/cpi.rs`. This ensures the instruction data and account layout marginfi sends to `SOLEND_PROGRAM_ID` is mechanically kept in sync with Solend's real, current interface, eliminating the class of mismatch that caused M-7 in the Uniswap integration.

### Proof of Concept
Not applicable as an on-chain exploit today — no test in the current codebase demonstrates a live mismatch between the hand-rolled discriminators (`INIT_OBLIGATION_DISCRIMINATOR = 6`, `DEPOSIT_DISCRIMINATOR = 14`, `WITHDRAW_DISCRIMINATOR = 15`) and Solend's current mainnet program. The finding is the architectural absence of IDL-based verification for this specific integration, which is the same class of defect (hardcoded interface not guaranteed to match the real deployed contract) that produced M-7.
