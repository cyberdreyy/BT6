## Title
Cross-request response hijack via unauthenticated `MessageId` reuse in the WebAPI gateway handler's `savedCallbacks` map - (`File: core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The Paladin finding is a state-overwrite bug: a map entry (`userQuestPeriodRewards[...]`) keyed by user/questId/period is unconditionally overwritten (`=`, not accumulated/checked) on a second claim, silently destroying prior state. The closest reachable analog in this chainlink repo is `handler.savedCallbacks`, a map keyed purely by the client-supplied `msg.Body.MessageId`, which is written with unconditional assignment on every incoming legacy user message with no check for an existing, still-pending entry.

### Finding Description
`HandleLegacyUserMessage` unconditionally stores the caller's callback in a shared map keyed only by `msg.Body.MessageId`: [1](#0-0) 

There is no uniqueness check (unlike `common.requestCache.NewRequest`, which explicitly rejects duplicate `{sender, id}` keys, see `core/services/gateway/handlers/common/requestcache.go:57-63`). `MessageId` is part of the client-controlled `api.MessageBody` and is not scoped by sender identity in this map. When a DON node later responds with the same method (`MethodWebAPITrigger`), the gateway looks the callback up purely by `MessageId` and forwards the response to whichever callback is currently registered under that key: [2](#0-1) 

Because the assignment at line 412 is a plain overwrite with no idempotency guard, if two calls to `HandleLegacyUserMessage` occur with the same `MessageId` (e.g., an unprivileged caller submits a request reusing/guessing another caller's `MessageId`, or a client legitimately retries before the first response arrives), the second caller's `savedCallback` silently replaces the first one in the map. The first caller's original callback reference is lost; when the DON eventually responds to the *original* request, the response is instead routed to the second (potentially different) caller's callback via `savedCb.SendResponse(...)`. This is a direct structural analog of `userQuestPeriodRewards[...] = claimedAmount` clobbering an earlier user's recorded value — here it's a live callback per in-flight request being clobbered, causing the true owner's request to be silently dropped (until pruned/timed out) and its outcome delivered to another party's callback instead.

### Impact Explanation
This can lead to cross-user response confusion at the internet-facing gateway boundary: one unprivileged user's inflight request/response can be intercepted or, symmetrically, dropped and starved until it times out, purely by reuse of a `MessageId`. Since gateway `MessageId` values are attacker/client observable/controllable inputs in the legacy message flow, this weakens the request/response integrity guarantee the gateway is supposed to provide between the many concurrent user callers and DON responses.

### Likelihood Explanation
Likelihood depends on how `MessageId` is generated/validated upstream of `HandleLegacyUserMessage` (not fully visible in this pass) and whether uniqueness/sender binding is enforced elsewhere in the request pipeline before this handler is invoked. The sibling `requestCache` implementation used by other gateway handlers demonstrates that this codebase treats duplicate-ID enforcement as a real, necessary safeguard (`errors.New("request already exists")`), which this handler's `savedCallbacks` map lacks — suggesting the gap is plausible but its exploitability hinges on whether `MessageId` uniqueness/ownership is verified by an earlier layer that I was not able to fully trace in the remaining iteration budget.

### Recommendation
- Key `savedCallbacks` by `(sender/session identity, MessageId)` rather than `MessageId` alone, mirroring `common.requestCache`'s `globalId{sender, id}` design.
- Reject (rather than silently overwrite) an incoming legacy message whose `MessageId` already has a live, unexpired entry in `savedCallbacks`.
- Verify at the layer that constructs/accepts `api.Message` for `HandleLegacyUserMessage` that `MessageId` is bound to the authenticated caller (or otherwise unguessable/unique per caller), consistent with how `handleWebAPITriggerMessage` matches purely by `MessageId`.

### Proof of Concept
Not independently verified end-to-end (would require confirming whether an earlier layer already enforces `MessageId` uniqueness/ownership before `HandleLegacyUserMessage` is reached — this could not be fully confirmed in the available tool budget). Conceptually:
1. Caller A sends a legacy user message with `MessageId = "X"`; `savedCallbacks["X"] = callbackA`.
2. Before the DON responds, Caller B sends a legacy user message reusing `MessageId = "X"`; `savedCallbacks["X"]` is overwritten to `callbackB` (line 412, no existence check).
3. The DON's response to A's original message arrives with `MessageId = "X"`; `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, deletes the entry, and delivers A's response to B via `callbackB.SendResponse(...)` — while A's original callback is silently discarded.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
