### Title
Stale confirmations from removed members allow request execution below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` counts a request as approved once `confirmations.len() + 1 >= self.num_confirmations`, but `delete_member()` only purges confirmations for requests *originated* by the removed member, not confirmations that member previously *cast* on other members' still-pending requests. A member removed via `DeleteMember` therefore continues to count toward the approval threshold of any request it confirmed before removal, letting a request execute with fewer live, authorized confirmations than `num_confirmations` requires.

### Finding Description
`confirm()` looks up the confirmation set for a request and, once its size plus the new confirmation reaches `num_confirmations`, executes the request: [1](#0-0) 

The set is keyed by `member.to_string()` and is never validated against current membership at confirm-time — only `current_member()` of the *new* confirmer is checked, not the members whose confirmations are already stored in the set: [2](#0-1) 

`delete_member()` removes stored requests/confirmations only for requests where `r.member == member` (i.e., requests the removed member *created*): [3](#0-2) 

It does **not** scan `self.confirmations` for entries containing the removed member's string as a confirmer on requests created by *other* members. Consequently, if member `M` confirms request `R` (created by member `Y`), and `M` is later removed via a `DeleteMember` action (approved by the live members), `R`'s confirmation set still contains `M`'s string. When a subsequent live member confirms `R`, the code counts `M`'s stale confirmation toward `num_confirmations`, causing `execute_request()` to run — potentially transferring NEAR, adding a full-access key, or adding/removing further members — with fewer *live* approvals than the threshold mandates.

This mirrors the reported bug class: an incomplete state-transition (removing a member) fails to properly invalidate a dependent classification (which confirmations still count), causing a downstream authority check (`confirmations counted >= num_confirmations`) to diverge from the true state (live members who actually approved), and an action proceeds that shouldn't have.

The same structural issue exists in the older `multisig/src/lib.rs` contract, where `DeleteKey` only clears confirmations/requests originated by the deleted key (`r.signer_pk == pk`), not confirmations that key cast on other pending requests: [4](#0-3) 

### Impact Explanation
This breaks the custody/authorization binding "confirmations counted == live members who approved." A multisig meant to require `k` live signers can be tricked into executing a `Transfer`, `AddKey`, `AddMember`/`DeleteMember`, or `FunctionCall` request with a mix of live and already-revoked approvals — i.e., a request executed below the intended live-confirmation threshold. Per the impact rubric this is Critical: "a multisig request executed below threshold."

### Likelihood Explanation
Exploitability requires: (1) a member confirms a pending request, (2) that same member is later removed via a separate, properly-approved `DeleteMember`/`DeleteKey` request (a routine operational action, e.g. rotating out a compromised or departing signer), and (3) the original pending request is still outstanding and gets one more confirmation from a remaining live member. This is a plausible, realistic sequence for any multisig doing normal key/member rotation while requests are in flight — no malicious deployment or foundation misconfiguration is needed, only ordinary operational timing.

### Recommendation
When executing a `DeleteMember`/`DeleteKey` action, iterate over **all** active requests' confirmation sets (not just those the member originated) and remove the deleted member's/key's entry from each. Alternatively, at `confirm()` time, filter the stored confirmation set to only members currently present in `self.members` before comparing its size against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]` and `num_confirmations = 2`.
2. Member `B` creates request `R1` (e.g., `Transfer`) via `add_request`. `A` confirms — `confirmations(R1) = {A}` (not yet executed, needs 2).
3. Member `C` confirms `B`'s later `add_request_and_confirm` for a `DeleteMember{member: A}` request `R2`, reaching threshold and executing removal of `A` from `self.members`. Per `delete_member`, only requests where `r.member == A` are purged; `R1` (created by `B`, confirmed by `A`) is untouched — `confirmations(R1)` still `= {A}`.
4. `A` is no longer a member (`current_member()` would return `None` for `A` now), yet `confirmations(R1) = {A}` remains stored.
5. Member `B` (or `C`) confirms `R1`: `confirmations.len() + 1 = 2 >= num_confirmations (2)` → `execute_request(R1)` runs the `Transfer`, even though only one genuinely live member (`B`/`C`) plus a stale, now-invalid confirmation from removed member `A` "approved" it. [5](#0-4) [3](#0-2)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
