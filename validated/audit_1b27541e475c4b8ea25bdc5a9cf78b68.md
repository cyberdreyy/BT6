## Title
BlockRejection's inner signature omits `reason_code`/`response_data` (including `failed_txid`) from the signed payload, allowing a byzantine relayer to recount a signer's rejection as backing a different reason/txid — ([File: libsigner/src/v0/messages.rs])

## Summary
`BlockRejection::hash()` only commits to `self.signer_signature_hash` (plus `chain_id` in the domain tuple). The `reason`, `reason_code`, and `response_data` (which carries `failed_txid`) are transmitted alongside the signature but are **not part of the signed message**. Any relayer that can re-package/forward a signer's rejection (the "gossip" path noted in scope) can therefore swap these fields while `verify()`/`recover_public_key()` still succeed, causing downstream code that trusts `reason_code`/`failed_txid` under a validated signature to attribute a fabricated reason/txid to a legitimate signer.

## Finding Description
`BlockRejection::hash()` builds the signed digest solely from `signer_signature_hash`: [1](#0-0) 
`sign()`/`verify()`/`recover_public_key()` all operate over this same restricted hash: [2](#0-1) 
Yet the struct carries `reason`, `reason_code`, and `response_data` (with `failed_txid`) as separate, unsigned fields: [3](#0-2) 

On the miner/node side, `stackerdb_listener.rs` recovers the pubkey from the rejection and, once it matches the expected signer, tallies `total_weight_rejected` **and separately accumulates `failed_txid` weight/`problematic_weight` based on `reason_code` and `response_data.failed_txid`** — fields that were never covered by the signature: [4](#0-3) 
This `failed_txid`/`problematic_weight` tally is later used to decide which transactions get temporarily or permanently excluded from future block proposals: [5](#0-4) 

On the signer side, `handle_block_rejection` performs the same recover-and-authenticate-by-address check and then stores/processes the rejection using `rejection.response_data.reject_reason`, again without that field being covered by the signature: [6](#0-5) 

Because only `signer_signature_hash` is signed, a valid `(signature, signer_signature_hash)` pair from signer S is compatible with *any* `reason`/`reason_code`/`response_data` combination. Whether this is exploitable in practice hinges on whether the wire-level StackerDB chunk transport re-authenticates the full serialized message bytes on every hop between peers, or whether the signed sub-field is ever detached and re-combined with different content by an intermediate relay/gossip layer before signer/node logic inspects it. I was not able to fully confirm within the available context whether the StackerDB chunk-level signature (`chunk.sig`, checked via `chunk.recover_pk()`) is re-verified over the *entire* chunk bytes on every relay hop in `stackslib/src/net/relay.rs` / `stackslib/src/net/stackerdb/*`, which would mean the chunk envelope already binds all these fields together and closes this gap at the transport layer. That verification step is the deciding factor for exploitability and should be confirmed before treating this as production-exploitable, but the fact remains that **the `BlockRejection` payload's own cryptographic signature does not bind `reason_code`/`response_data`/`failed_txid` to the signer's intent** — a violation of defense-in-depth even if the outer StackerDB chunk signature currently happens to cover the same bytes.

## Impact Explanation
If any component ever forwards, caches, replays, or reconstructs a `BlockRejection` payload independently of the original StackerDB chunk envelope (e.g. across `SignerMessages` events synthesized from partially-modified state, test/mock paths, or future protocol versions/relays that don't re-verify chunk-level signatures), the `reason_code`/`failed_txid` can be forged under a legitimate signer's valid signature. This is a "rejection recounted as/attributed differently" class of issue — a byzantine minority (a single relayer, not a majority of signers) could inflate `problematic_weight` for a chosen txid under real signer signatures, causing the node to permanently ban a transaction (`permanently_excluded_txids`) it never actually deemed problematic, per the aggregation logic in `signer_coordinator.rs` and `stackerdb_listener.rs` cited above.

## Likelihood Explanation
Likelihood is capped as **uncertain/lower** because current transport (StackerDB chunk signature over the whole chunk) may already provide the missing binding, making this a defense-in-depth gap rather than a directly demonstrated live vulnerability in the present codebase paths I could inspect. It becomes directly exploitable the moment any code path treats `reason_code`/`response_data` as attributable to the signer without re-validating them against the original, whole, untampered chunk bytes.

## Recommendation
Include `reason_code`, `response_data` (or at minimum `failed_txid` and the `ProblematicTransaction`/`BadTransaction` reason discriminant), and `chain_id` in the `BlockRejection::hash()` structured-data payload, mirroring how `BlockAccepted`/block-header signatures already bind the exact content they authorize. This removes any reliance on the transport layer to keep these fields glued to the signature and makes `BlockRejection` self-contained and tamper-evident, consistent with domain-separated signing already used elsewhere in `libsigner/src/v0/messages.rs`.

## Proof of Concept
1. Take a genuine `BlockRejection` message signed by signer `S` for `signer_signature_hash = H` with `reason_code = RejectCode::ValidationFailed(ValidateRejectCode::BadTransaction)` and `response_data.failed_txid = None`.
2. Because `BlockRejection::hash()` only depends on `H` and `chain_id`, construct a new `BlockRejection` with the same `signer_signature_hash`, same `signature`, but `reason_code = RejectCode::ValidationFailed(ValidateRejectCode::ProblematicTransaction)` and `response_data.failed_txid = Some(target_txid)`.
3. `recover_public_key()`/`verify()` on this modified struct still succeeds and resolves to `S`'s address, per `libsigner/src/v0/messages.rs:1816-1838`.
4. If this modified struct reaches `stackerdb_listener.rs`'s handler (bypassing/absent a whole-chunk re-signature check), it is credited toward `S`'s `total_weight_rejected` and `problematic_weight` for `target_txid`, per `stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-546`, potentially tipping `target_txid` into `permanently_excluded_txids` in `signer_coordinator.rs:525-535` without `S` ever having flagged it as such.

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
}

    /// Handle an observed rejection from another signer
    fn handle_block_rejection(
        &mut self,
        rejection: &BlockRejection,
        sortition_state: &mut Option<SortitionsView>,
    ) {
        debug!("{self}: Received a block-reject signature: {rejection:?}");

        let block_hash = &rejection.signer_signature_hash;
        let signature = &rejection.signature;

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {
            debug!("{self}: Received block rejection with an unrecovarable signature. Will not store.";
               "signer_signature_hash" => %block_hash,
               "signature" => %signature
            );
            return;
        };

        // authenticate the signature -- it must be signed by one of the stacking set
        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }

        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {
            if let Err(e) = self.signer_db.add_pending_block_rejection_response(
                block_hash,
                &signer_address,
                (&rejection.response_data.reject_reason).into(),
            ) {
                warn!("{self}: Failed to add pending block rejection response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block rejection";
            "signer_pubkey" => public_key.to_hex(),
            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "reject_reason" => ?rejection.response_data.reject_reason,
        );

        self.store_and_process_block_rejection(
            sortition_state,
            &mut block_info,
            &signer_address,
            (&rejection.response_data.reject_reason).into(),
        );
    }
