### Title
Loss-adjusted withdraw receipts escape their haircut because `IdleCreditVault` looks up `lossRecoveryPriceByEpoch` only via the single `lastWithdrawRequest` marker instead of checking whether the user's actual receipt epoch was haircut - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a proxy check: `list_first_entry()` non-NULL was used to mean "list is non-empty". The analog in `IdleCreditVault` is the use of the single scalar `lastWithdrawRequest[user]` as a proxy for "the epoch that carries this user's pending receipts". Both `requestWithdraw`'s loss-guard and `_claimLossAdjustedWithdrawRequest` consult only `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]`, while `collectWithdrawFunds` writes the haircut under `lossRecoveryPriceByEpoch[epochNumber]` at stop time — an aggregate that covers all pending receipts regardless of which epoch each user requested in. When a user's `lastWithdrawRequest` diverges from the epoch key under which the loss price is stored, the receipt is claimed at par from a reserve that was only partially funded, draining other claimants' money.

### Finding Description
`requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` and accumulates into the global `pendingWithdraws` [1](#0-0) . At `stopEpoch`, `collectWithdrawFunds` applies a single haircut to the whole aggregate and stores it under `lossRecoveryPriceByEpoch[epochNumber]` — whatever `epochNumber` is at that moment, not the request epoch of any individual user [2](#0-1) . `epochNumber` is incremented inside `deposit()` when the CDO pushes epoch funds during `_stopEpoch` [3](#0-2) .

Claim-time lookup then uses only the head marker: `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and returns 0 if unset [4](#0-3) , after which `_claimFundedWithdrawRequest` pays the full `withdrawsRequests[_user]` at par once `epochNumber > lastWithdrawRequest[_user]` [5](#0-4) .

The divergence is reachable two ways:

1. **Ordering mismatch in a single epoch**: if `deposit()` bumps `epochNumber` before `collectWithdrawFunds` runs inside `_stopEpoch`, the haircut is stored under epoch N+1 while users who requested during the preceding buffer have `lastWithdrawRequest = N` (or vice versa if collected pre-bump and the request is recorded post-bump).
2. **Multi-epoch receipts**: `pendingWithdraws` is one aggregate bucket, so a loss at stop haircut-covers receipts from several request epochs, but only the epoch stored as the key is ever consulted. A user whose `lastWithdrawRequest` doesn't equal that key — e.g., they requested again in a later buffer, which is explicitly allowed when the earlier receipt wasn't loss-adjusted (`requestWithdraw` only reverts if `lossRecoveryPriceByEpoch[lastWithdrawRequest] != 0` at request time, which is still unset before the next stop) — slips past both the guard and the claim path.

In either case the claim falls through to `_claimFundedWithdrawRequest`, burns the full receipt, and `_transferFundedClaim` pays the un-haircut amount [6](#0-5) .

### Impact Explanation
The borrower funds only `_amount < pendingBasis` at `collectWithdrawFunds`, so the strategy holds fewer underlyings than outstanding receipt basis by exactly the loss. Every user whose `lastWithdrawRequest` misses the stored epoch key withdraws at par; the strategy's funded balance is exhausted early and honest claimants' funded receipts revert permanently (`balance - reserve < amount` → `NotAllowed`), a combination of direct theft by early claimants and permanent freezing of later claims. Loss equals the unapplied haircut amount: up to `(1 - lossRecoveryPrice) × affected basis`.

### Likelihood Explanation
Triggering requires only normal, unprivileged usage: request a withdraw in a buffer epoch, let `stopEpochWithDuration` realize a loss (honest manager action during borrower stress — precisely when the feature exists), then claim. No privileged misbehavior, no default needed. Exploitability hinges on the keying divergence between `epochNumber` at `collectWithdrawFunds` time and users' `lastWithdrawRequest`; the code itself acknowledges receipts may span epochs ("The aggregate may also include older funded receipts") but still uses the single-marker lookup.

### Recommendation
Store the loss epoch explicitly per receipt or per pending cohort: e.g., key `lossRecoveryPriceByEpoch` by the epoch recorded in `withdrawsRequestsByEpoch`, iterate/record all affected user epochs, or maintain a per-user list of unclaimed receipt epochs rather than a single `lastWithdrawRequest`. At minimum, have `collectWithdrawFunds` record the haircut under the epoch(s) actually contributing to `pendingWithdraws` and make `_claimLossAdjustedWithdrawRequest` check each epoch where `withdrawsRequestsByEpoch[user][e] != 0` — the equivalent of replacing `list_first_entry() != NULL` with a real emptiness check.

```solidity
// 1. user1 deposits AA, user2 deposits AA; epoch0 runs and stops (buffer of epoch1).
// 2. user1: cdoEpoch.requestWithdraw(x1, AA)          -> lastWithdrawRequest[u1] = E_a
// 3. epoch1 runs; user1 requests again in next buffer -> lastWithdrawRequest[u1] = E_b,
//    guard passes because lossRecoveryPriceByEpoch[E_b] == 0 at request time.
// 4. borrower shortfall: manager calls stopEpochWithDuration(newApr, interest, dur, loss)
//    -> collectWithdrawFunds stores lossRecoveryPriceByEpoch[E_stop] = 0.7e18,
//       where E_stop = epochNumber at collect time (E_b's predecessor or successor,
//       i.e. != lastWithdrawRequest[u1]).
// 5. user1: cdoEpoch.claimWithdrawRequest()
//    -> _claimLossAdjustedWithdrawRequest reads lossRecoveryPriceByEpoch[E_b] == 0 -> skip
//    -> _claimFundedWithdrawRequest: epochNumber > E_b gate passes -> pays full basis at par
// 6. user2 (same haircut cohort, lastWithdrawRequest == E_stop): claims 0.7x.
// 7. Final honest claimant: _transferFundedClaim reverts -> funded receipts frozen.
assertEq(strategy.balanceOf(user1), 0);
assertGt(u1Payout, fundedShareU1);          // claimed at par despite 30% loss
// vault underlying balance now < remaining funded claims -> last claim reverts NotAllowed
```
Note: the exact `epochNumber` key written by `collectWithdrawFunds` depends on whether `deposit()`'s `epochNumber += 1` executes before it inside `_stopEpoch`; both orderings produce a miss for some users, but the PoC should assert `lossRecoveryPriceByEpoch[user.lastWithdrawRequest] == 0` while `withdrawsRequestsByEpoch[user][stopEpoch] != 0` to pin the divergence on the forked deployment.

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
