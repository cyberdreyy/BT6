### Title
Permissionless liquidation-record PDA can be pre-created by a griefer, causing composite receivership-liquidation transactions to revert - ([File: programs/marginfi/src/instructions/marginfi_account/init_liquid_record.rs])

### Summary
`marginfi_account_init_liq_record` initializes a `LiquidationRecord` PDA whose seeds are derived purely from the (public) `marginfi_account` key, with no binding to the caller/`fee_payer`. Because the instruction is explicitly documented and implemented as permissionless, and `validate_instructions` in `liquidate_start.rs` allows `INIT_LIQUIDATION_RECORD` to appear as the first instruction of a receivership bundle, any third party can pre-create the record for a victim account. This mirrors the reported BatonLaunchpad bug class: a `create2`-style deterministic PDA whose seed is not bound to the legitimate caller's identity, allowing an attacker to squat the address and cause the legitimate party's subsequent "create" (Anchor `init`) instruction to revert.

### Finding Description
The PDA is derived as:
```rust
seeds = [LIQUIDATION_RECORD_SEED.as_bytes(), marginfi_account.key().as_ref()]
``` [1](#0-0) 

The only signer required is `fee_payer` (to pay rent) — there is no `has_one`/`authority` check tying the instruction to the account owner or to the liquidator who intends to use it, and the docstring in `lib.rs` explicitly labels it `(permissionless)`: [2](#0-1) 

The `Anchor` `init` constraint on `liquidation_record` will fail with an "account already in use" style error if the account already exists at that PDA. Since the seed set contains no attacker-unpredictable or caller-bound component (just the victim's public `marginfi_account` pubkey, which is known ahead of time to any observer), any address that will legitimately be created by a liquidator's `marginfi_account_init_liq_record` call can be pre-created by a griefer first — exactly the `create2`/deterministic-salt collision pattern described in the source report (front-running with a colliding salt to force a revert), except here the "salt" (marginfi_account key) is entirely public and requires no guessing.

`start_liquidation` explicitly recognizes `INIT_LIQUIDATION_RECORD` as a valid *first* instruction inside an atomic liquidation bundle: [3](#0-2) 
meaning the codebase's own design anticipates bundling `init_liq_record` + `start_liquidation` (+ withdraw/repay + `end_liquidation`) into a single atomic transaction. The `p0-cli` reference implementation works around the race by checking existence first and conditionally including the init instruction: [4](#0-3) 
This check-then-act pattern is itself subject to a classic TOCTOU race: a griefer watching the mempool/RPC for the liquidator's "does not exist" check (or simply watching for accounts becoming unhealthy) can front-run with their own `marginfi_account_init_liq_record` call before the liquidator's bundled transaction lands, causing the still-included `init` instruction (and therefore the entire atomic receivership bundle, since `end_liquidation` must be present too) to revert.

### Impact Explanation
This is a temporary denial-of-service on the receivership liquidation flow: a malicious actor can grief a specific liquidator's attempt to begin liquidating/deleveraging an unhealthy account by squatting the `LiquidationRecord` PDA first, forcing the liquidator's composite transaction to fail. Because liquidation is time-sensitive (undercollateralized positions), repeated griefing could delay liquidation of a specific account, which has a real (if narrow) financial-risk implication for the protocol (bad debt accumulation) — analogous in class/severity to the "Medium" DoS rated in the source report.

### Likelihood Explanation
Likelihood is similar to the original report: Medium-to-Low. It is easy and cheap to execute (a single permissionless transaction, and the griefer's rent is fully recoverable later via `marginfi_account_close_liq_record`, which returns rent to the original `record_payer`) [5](#0-4) , but the attacker gains no direct financial upside from griefing a specific liquidator, only the ability to delay a particular liquidation attempt. It also requires the griefer to observe/predict which account is about to be liquidated and front-run at the right moment.

### Recommendation
- Allow `marginfi_account_init_liq_record` to succeed idempotently when the record already exists for the given `marginfi_account` (e.g., use `init_if_needed` or explicitly check-and-skip instead of hard-failing), OR
- Have `start_liquidation`/liquidator tooling create the liquidation record as a *separate, non-atomic* prerequisite step and verify its existence via `has_one = liquidation_record` before assembling the atomic bundle (removing the `init` step from the same bundle as `end_liquidation`), eliminating the TOCTOU window, OR
- At minimum, document this front-running risk for integrators/liquidator bots and recommend they always re-check existence immediately before submission (e.g., simulate the transaction) rather than relying on an earlier read.

### Proof of Concept
1. Observe (via RPC) an unhealthy `marginfi_account` `M` that a liquidator intends to liquidate via a receivership bundle `[init_liq_record(M), start_liquidation, withdraw/repay ..., end_liquidation]`.
2. Compute the `LiquidationRecord` PDA deterministically: `Pubkey::find_program_address([LIQUIDATION_RECORD_SEED, M.as_ref()], marginfi::ID)` — this requires no signature or private information from the victim/liquidator.
3. Submit `marginfi_account_init_liq_record` for `M` with any `fee_payer` (attacker's own wallet), landing before the liquidator's bundle.
4. The liquidator's bundled `init_liq_record` instruction fails with an Anchor "account already in use" error because the PDA already exists, reverting the entire atomic transaction (including `start_liquidation`/`end_liquidation`), per the accounts constraints in [6](#0-5) .
5. The attacker can later reclaim their rent via `marginfi_account_close_liq_record` once the 60-day inactivity condition (or zero-activity condition) is met [7](#0-6) , making the griefing essentially cost-free apart from a temporary rent lockup.
