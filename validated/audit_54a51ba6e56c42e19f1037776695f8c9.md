### Title
Post-default withdraw requests drain the shared `defaultRecoveryReserve` at par, stealing funds reserved for defaulted-epoch receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.finalizeDefaultRecovery` sizes `defaultRecoveryReserve` to exactly cover the default-epoch claim basis at `defaultRecoveryPrice`. After finalization, `requestWithdraw` mints new "post-default" receipts whose claims are paid **1:1** from the same reserve via `_transferDefaultRecovery`, but no new underlying is ever added to back them. A post-default requester therefore consumes recovery funds priced for defaulted claimants, and can front-run them to drain the reserve, leaving legitimate defaulted receipts unpayable.

### Finding Description
In `finalizeDefaultRecovery` the reserve is fixed once: [1](#0-0) 

`reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` covers only `totalBasis * recoveryPrice`. After `defaultRecoveryFinalized = true`, the `requestWithdraw` post-default branch mints the user a receipt and records `postDefaultRequests`: [2](#0-1) 

The comment says the CDO passes an "already-haircut" amount, but the payout path `_claimPostDefaultWithdrawRequest` pays the full recorded amount at par, decrementing `defaultRecoveryReserve`: [3](#0-2) [4](#0-3) 

No function tops up the reserve after finalization: `reserveDefaultRecovery` reverts once `defaultRecoveryFinalized` is set (line 631), and `collectWithdrawFunds`/`collectInstantWithdrawFunds` only handle pre-default flows. The reserve is thus a zero-sum pot shared between (a) defaulted-epoch receipts entitled to `claimBasis * defaultRecoveryPrice` and (b) post-default receipts paid at 1:1. Since post-default claimants were never in `totalBasis`, every post-default payout is unbacked dilution of defaulted claimants.

### Impact Explanation
Direct theft / permanent loss of recovery funds. With `recoveryPrice < 1e18`, an attacker holding tranche tokens after default finalization calls `requestWithdraw` (via the CDO redeem path) to create a `postDefaultRequests` entry, then `claimWithdrawRequest`, receiving `amount` at par from the reserve. Because the reserve was sized only for `totalBasis * recoveryPrice`, these par payouts consume the haircut dust first and then the funds owed to defaulted receipts. If the attacker moves before defaulted claimants claim, the last claimants' `_transferDefaultRecovery` underflows/reverts — their recovery is permanently unclaimable. Broken invariant: one receipt one payout / solvency of the isolated recovery reserve.

### Likelihood Explanation
Requires only an unprivileged tranche-token holder acting after `finalizeDefaultRecovery` (defaulted + finalized phase). The only guard is that the *same user* must first claim old receipts (`_hasWithdrawRequest` check, lines 248–251), which a fresh attacker address trivially satisfies. Attack is repeatable by any number of sybil tranche holders until the reserve is exhausted. No privileged cooperation needed; sequencing is entirely around honest manager/owner calls.

### Recommendation
Track a separate post-default payout bucket. Either (a) fund post-default requests from a distinct balance (e.g., borrower repayments pulled in `requestWithdraw`), or (b) enlarge the reserve and `totalBasis` accounting so post-default claims are included pro-rata at `defaultRecoveryPrice` rather than paid at par. At minimum, `_transferDefaultRecovery` should not allow post-default claims to spend reserve below the amount earmarked for outstanding defaulted-epoch receipts.

  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
