## Analysis

The Qpid Broker-J CVE describes a pre-authentication attacker causing unbounded recursive type-nesting that overflows the stack. The closest analog in this codebase is in the fault-proof program's Merkle Patricia Trie (MPT) decoder.

`TrieNode::decode` in `crates/proof/mpt/src/node.rs` recursively decodes RLP-encoded trie nodes with **no depth bound**: an `Extension` node's inline (unblinded) child is decoded via a direct recursive call to `Self::decode(buf)` inside `try_decode_leaf_or_extension_payload`, and a `Branch` node recurses through `Vec::<Self>::decode`. Nothing in this code path caps how many `Extension`/`Branch` layers can be nested inside a single preimage blob.

Critically, the only integrity check on a decoded preimage is that the top-level byte blob hashes to the requested key (`keccak256`) — verified once, at the call sites in `crates/proof/proof/src/l1/chain_provider.rs` and `crates/proof/proof/src/l2/chain_provider.rs`, both of which call `TrieNode::decode(...)` immediately after fetching the preimage from the oracle. There is no check that nested/embedded child nodes are individually bounded (e.g. real MPT nodes only embed children when they RLP-encode under 32 bytes, and even then real chain state limits nesting to ~64 levels by key length) — the decoder itself does not enforce either constraint.

In the fault-proof/dispute-game context, arbitrary preimage bytes can be supplied to the preimage oracle by any dispute-game participant, as long as they hash-match a claimed key. This is exactly the "pre-authentication attacker" analog: a dispute participant can construct a single preimage blob that RLP-encodes thousands of nested `Extension`/inline `Branch` levels compacted into a small buffer, then have that preimage served to `TrieNode::decode` during fault-proof program execution (e.g. via `OracleL1ChainProvider::trie_node_by_hash` / `OracleL2ChainProvider::trie_node_by_hash`), triggering unbounded recursion and a stack overflow in the honest verifier's proof program. ### Title
Unbounded recursive nesting in `TrieNode::decode` can crash the fault-proof program via stack overflow - (File: `crates/proof/mpt/src/node.rs`)

### Summary
`TrieNode::decode` recursively decodes RLP-encoded Merkle Patricia Trie nodes without any nesting-depth limit. `Extension` nodes decode their embedded child via a direct recursive call to `Self::decode`, and `Branch` nodes recurse through `Vec::<Self>::decode`. A dispute-game participant can submit a preimage to the preimage oracle whose bytes hash-match the requested key but whose content encodes thousands of nested extension/branch levels, causing unbounded native-stack recursion when the fault-proof program (`OracleL1ChainProvider`/`OracleL2ChainProvider`) decodes it.

### Finding Description
`TrieNode::decode` peeks the RLP header and, for lists with 2 elements, calls `try_decode_leaf_or_extension_payload`, which recurses into `Self::decode(buf)` again when the child pointer is embedded rather than blinded (`crates/proof/mpt/src/node.rs:454-461`). For a 17-element list it decodes a `Vec<Self>`, recursing per element (`crates/proof/mpt/src/node.rs:578-581`). No caller enforces a maximum recursion depth. The only validation performed before decoding is that the fetched preimage bytes hash to the requested `PreimageKey` (`crates/proof/proof/src/l1/chain_provider.rs:132-140`, `crates/proof/proof/src/l2/chain_provider.rs:180-188`); the *internal* nesting structure of that preimage is unconstrained. Because embedded (non-blinded) child nodes are not checked against the real 32-byte embedding limit used by canonical Ethereum tries, an attacker can pack many nesting levels compactly into one preimage blob that is well within any normal size cap, independent of any real state-trie depth (which in practice caps out around 64 levels for 32-byte keys).

### Impact Explanation
In the dispute-game / fault-proof flow, preimages are supplied by participants (any party can register a preimage under its own hash in the preimage oracle). A malicious participant can craft a compact but deeply-nested trie-node preimage and cause the honest verifier's fault-proof execution to recurse until it hits a stack overflow, crashing the program mid-execution. This can prevent the honest party from completing/validating a dispute-game step, potentially leading to a wrong provable output root prevailing or halting resolution of the fault-proof program — a concrete denial-of-service against the proof system's correctness guarantees.

### Likelihood Explanation
Likelihood is high: constructing an RLP blob with thousands of nested 2-element list headers is trivial and requires no privileged access — only registering a preimage whose hash the attacker controls (by construction, since they choose the bytes). No authentication or special role is needed to reach `TrieNode::decode` from the preimage-oracle-fed proof program.

### Recommendation
Add an explicit maximum recursion/nesting depth to `TrieNode::decode` (and its list variant), returning a decode error once exceeded, mirroring canonical Ethereum trie depth bounds (e.g., cap around 64-65 levels, matching the maximum possible key-nibble depth), or convert the decoder to an iterative/worklist-based implementation instead of native recursion.

### Proof of Concept
Construct nested RLP bytes for `N` levels of `Extension` nodes, each formed as `rlp([extension_path_bytes, next_level_bytes])` where `next_level_bytes` is kept short enough to remain embedded (avoiding the `Blinded` 32-byte-string branch), repeated recursively N times (N in the thousands). Feed the resulting byte slice into `TrieNode::decode(&mut bytes.as_slice())` (as would happen via `OracleL1ChainProvider::trie_node_by_hash` after registering these bytes in the preimage oracle under their own keccak256 hash) to trigger a stack overflow.

impl Decodable for TrieNode {
    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.
                    buf.advance(header.length());
                    // Decode the leaf or extension node's raw payload.
                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }
        } else {
            match header.payload_length {
                0 => {
                    buf.advance(header.length());
                    Ok(Self::Empty)
                }
                32 => {
                    let commitment = B256::decode(buf)?;
                    Ok(Self::new_blinded(commitment))
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }
        }

    type Error = OracleProviderError;

    fn trie_node_by_hash(&self, key: B256) -> Result<TrieNode, Self::Error> {
        // On L1, trie node preimages are stored as keccak preimage types in the oracle. We assume
        // that a hint for these preimages has already been sent, prior to this call.
        crate::block_on(async move {
            TrieNode::decode(
                &mut self
                    .oracle
                    .get(PreimageKey::new(*key, PreimageKeyType::Keccak256))
                    .await
                    .map_err(OracleProviderError::Preimage)?
                    .as_ref(),
            )
            .map_err(OracleProviderError::Rlp)
        })
    }
