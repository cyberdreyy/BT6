### Title
Legacy pending withdrawals permanently block default recovery after strategy upgrade - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
An upgraded `IdleCreditVault` with `defaultRecoveryInitialized == false` cannot finalize borrower-default recovery while any legacy `pendingWithdraws` remain, because `_ensureDefaultRecoveryInitialized()` reverts once the CDO is running or defaulted. [1](#0-0)  An unprivileged lender can leave a pending withdrawal before an honest implementation upgrade; if the borrower defaults before a successful zero-loss epoch stop clears the aggregate pending balance, recovery finalization becomes permanently unavailable. [2](#0-1) 

### Finding Description
Newly initialized vaults set `defaultRecoveryInitialized` to `true`, but a pre-existing proxy upgraded to this implementation has the appended boolean at its default `false` value. [3](#0-2)  The production upgrade task treats legacy pending withdrawals as a warning rather than a hard precondition, allowing an upgrade while `pendingWithdraws != 0` if the vault has not already defaulted. [4](#0-3) 

After such an upgrade, a partial-loss stop cannot clear the legacy pending bucket because `collectWithdrawFunds()` requires `defaultRecoveryInitialized` before recording `lossRecoveryPriceByEpoch`. [2](#0-1)  If the borrower defaults first, `finalizeDefaultRecovery()` calls `_ensureDefaultRecoveryInitialized()`, which reverts whenever `pendingWithdraws != 0` and either `epochEndDate() != 0` or `defaulted()` is true. [5](#0-4) [1](#0-0) 

The resulting state is unrecoverable through the exposed recovery path: `defaultRecoveryFinalized`, `defaultRecoveryPrice`, `defaultRecoveryEpoch`, and `defaultRecoveryReserve` are never established. [6](#0-5)  Defaulted withdrawal claims are only reachable after `defaultRecoveryFinalized` is set, so affected receipts and any already-held recovery reserve remain frozen. [7](#0-6) 

### Impact Explanation
The invariant broken is one-receipt-one-payout and default-recovery availability: a valid lender receipt can make the entire recovery-finalization path revert before any haircut or reserve distribution is recorded. [8](#0-7)  The quantifiable frozen amount is the outstanding `pendingWithdraws` claim basis plus any prefunded or reserved recovery assets held by the strategy; externally supplied recovery cannot be pulled because finalization reverts first. [9](#0-8) 

This is not merely a transient epoch delay because `_ensureDefaultRecoveryInitialized()` has no successful path once the CDO is defaulted and the legacy pending aggregate is nonzero. [1](#0-0) 

### Likelihood Explanation
The attack precondition is a pending withdrawal existing when an honest owner performs a strategy implementation upgrade, followed by borrower default before a successful zero-loss stop funds that aggregate. [4](#0-3)  A KYC-passing lender can create or leave the pending receipt using the normal `requestWithdraw()` path, and no privileged actor needs to behave maliciously. [10](#0-9) 

Likelihood is constrained by the required upgrade timing and subsequent default, but the operational task explicitly permits this intermediate state rather than enforcing a clean migration condition. [4](#0-3) 

### Recommendation
Make `pendingWithdraws == 0` or a successfully closed vault a hard precondition for upgrading to recovery-aware strategy implementations, rather than only logging that legacy receipts must be funded. [4](#0-3)  Alternatively, provide an explicit migration that marks recovery accounting initialized and preserves enough legacy per-user claim basis for defaulted receipt payouts. [11](#0-10) 

### Proof of Concept
Place this regression test in `test/foundry/IdleCreditVault.t.sol`; the `stdstore` writes reproduce the existing tests’ method for simulating a legacy receipt and an uninitialized post-upgrade flag. [12](#0-11) 

```solidity
function testLegacyPendingWithdrawPermanentlyBlocksDefaultRecovery() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    address legacyUser = makeAddr("legacyPendingBeforeDefault");

    _depositWithUser(legacyUser, 10_000 * ONE_SCALE, true);

    vm.prank(legacyUser);
    uint256 claimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertEq(creditVault.pendingWithdraws(), claimBasis);

    // Simulate a legacy pending receipt whose per-epoch ownership mapping did not exist.
    stdstore
        .target(address(creditVault))
        .sig(creditVault.withdrawsRequestsByEpoch.selector)
        .with_key(legacyUser)
        .with_key(creditVault.epochNumber())
        .checked_write(uint256(0));

    // Simulate the appended flag after a plain proxy implementation upgrade.
    stdstore
        .target(address(creditVault))
        .sig(creditVault.defaultRecoveryInitialized.selector)
        .checked_write(false);

    _startEpochAndCheckPrices(0);
    assertGt(cdoEpoch.epochEndDate(), 0);

    // Borrower defaults before a successful zero-loss stop funds pendingWithdraws.
    stdstore
        .target(address(cdoEpoch))
        .sig("defaulted()")
        .checked_write(true);

    vm.prank(address(cdoEpoch));
    vm.expectRevert(NotAllowed.selector);
    creditVault.finalizeDefaultRecovery(0, address(0));

    assertFalse(creditVault.defaultRecoveryFinalized());
    assertEq(creditVault.pendingWithdraws(), claimBasis);
}
```

The revert occurs inside `_ensureDefaultRecoveryInitialized()` before the routine can set the recovery price or reserve. [1](#0-0)
