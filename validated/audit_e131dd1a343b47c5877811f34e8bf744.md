Based on my investigation, I found a genuine analog to the "diluting rewards per second" bug class in the signer's inactivity-timeout mechanism.

### Title
A single miner can indefinitely suppress the tenure-inactivity timeout by reproposing invalid/conflicting blocks, wedging the signer set into never falling back to a prior miner - (`stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_latest_block_in_tenure` treats certain rejected/losing block proposals as "miner activity" and calls `update_last_activity_time`, which resets the clock used by `SortitionState::is_timed_out` to decide whether the current miner has gone inactive and should be abandoned in favor of the prior tenure's miner. Because a proposal that merely *conflicts* with an already-known block (not just a genuinely new, higher block) still counts as activity, the current miner can keep resending old/losing proposals to perpetually reset this timer — extending the "duration" the same way `notifyRewardAmount()` extended `periodFinish` with a trivial call — and the block-proposal timeout is never reached.

### Finding Description
`is_timed_out` (`stacks-signer/src/chainstate/v1.rs:55-94`, `v2.rs:48-89`) measures `elapsed = now - last_activity` against `block_proposal_timeout`, where `last_activity` comes from `signer_db.get_last_activity_time(sortition)` [1](#0-0) . That timer is written by `update_last_activity_time` inside `check_latest_block_in_tenure` in two branches that do **not** require the proposal to be a legitimately new, higher block:

1. When a proposal's height does not exceed the tenure's last *signed* block and the existing signature is still fresh (or absent), the code explicitly treats the reorg attempt as "valid miner activity" and calls `update_last_activity_time` [2](#0-1) .
2. When a proposal conflicts with a block that is only *pre-committed* (unsigned) at or above that height, the code again calls `update_last_activity_time`, explicitly commenting "count miner activity only — a pre-commit never vetoes" [3](#0-2) .

Both branches are reachable purely by the current tenure's own miner (a one-slot actor) resending or lightly mutating a proposal it controls — it needs no majority, no other signer's key, and no StackerDB/transport trickery. Each such message is a cheap "call" analogous to `notifyRewardAmount(1)`: it doesn't produce a valid block, but it resets the timer (`last_activity_time`) that the equality/liveness check `elapsed > block_proposal_timeout` depends on, exactly as the reward-dilution bug repeatedly extended `periodFinish` with a trivially small deposit.

`is_timed_out` is checked from `check_proposal` (v1) and from the housekeeping path `check_miner_inactivity`/`handle_pending_update` (both versions) documented in `docs/signer-flows.md` section 8 [4](#0-3) . If the current miner is stalled/malicious (e.g. deliberately refusing to produce a genuinely higher, valid block, or persistently proposing something already superseded) but keeps sending losing proposals at the same or lower height, `last_activity_time` is repeatedly bumped, `elapsed` never exceeds `block_proposal_timeout`, and the signer set never falls back (`FALL["fall back to prior tenure: make_miner_state(prior sortition)"]`) to the prior miner, per the documented state machine.

### Impact Explanation
This is a High-severity liveness wedge: a signer (the whole signer set, since this logic is symmetric and driven by validation of the same miner-authored messages) can be kept from ever timing out an unproductive/malicious current miner and falling back to the previous tenure's miner. The tenure-timeout fallback exists precisely to recover liveness when a miner stalls; an attacker-miner that can indefinitely suppress it can stall block production for as long as it likes while still appearing "active," which matches the "signer wedged into never signing valid blocks" / stale-state impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker need only be the currently-active miner (a normal, expected role, not requiring signer collusion) and needs to resend or slightly vary block proposals it already controls — the same "resend the same/old proposal" capability the miner already legitimately uses on `SignatureTimeout` (see `signer_coordinator.rs` `propose_block` loop, which itself resends on timeout) [5](#0-4) . No majority of signers or extra secrets are required.

### Recommendation
Restrict `update_last_activity_time` bumps to proposals that represent genuine new activity: e.g., only count a proposal toward "miner activity" once per unique `signer_signature_hash`/height, or require the conflicting proposal to be strictly newer/higher than anything already seen from that miner in the tenure, rather than crediting activity for repeated submissions of the same or already-superseded block. Alternatively, bound the number of activity-timer resets attributable to a single conflicting proposal (dedupe by signature hash) so the timeout duration cannot be extended indefinitely by cheap repeated messages, mirroring the fix pattern used for the reward-dilution bug (restrict who/what can extend the window, and cap how much a single call can extend it).

### Proof of Concept
1. Current miner M wins a sortition and proposes block `B0` at height `h`; signers pre-commit/sign it, recording `last_activity_time = t0` for the tenure.
2. Once `B0` is signed/known, M (or a proposer acting on M's behalf) repeatedly sends a new proposal `B1` at the same height `h` (or slightly mutated, still ≤ h, or conflicting with only a pre-committed unsigned block) before `block_proposal_timeout` elapses since `t0`.
3. Each such proposal triggers `check_latest_block_in_tenure`'s early-reject branches, both of which call `signer_db.update_last_activity_time(tenure, now)` per `stacks-signer/src/chainstate/mod.rs:411-416` and `442-446`, resetting the clock `is_timed_out` reads.
4. As long as M resends such a losing/conflicting proposal more frequently than `block_proposal_timeout`, `elapsed` in `is_timed_out` never exceeds the threshold, so `check_miner_inactivity`/`check_proposal`'s inactivity branch never fires and the signer set never falls back to the prior tenure's miner, wedging the tenure open indefinitely without M ever producing a valid, higher block.
