### Title
Tar+zstd extractor's directory-containment check is bypassed by pre-existing symlinks, allowing writes outside `e.dir` on a later extraction — (File: commands/helpers/archive/tarzstd/tarzstd_extractor.go)

### Summary
`extractor.Extract` validates that the *nominal* path derived from `hdr.Name` lies inside `e.dir`, but it never validates or restricts `hdr.Linkname` for symlink entries, and it never checks whether a path component already exists as a symlink before writing through it. A job can restore a cache/artifact archive that plants a symlink under a benign relative name pointing to an arbitrary target, and a subsequent extraction (a later cache restore or artifact download in the same job/workspace) that writes a regular file at that same relative name will have `os.Create` transparently follow the symlink, writing content wherever the symlink points.

### Finding Description
The containment check operates purely on the string form of the target path: [1](#0-0) 

This check only verifies that `filepath.Join(e.dir, hdr.Name)` lexically starts with `e.dir`; it does not resolve any existing filesystem entries along that path, so it cannot detect that an intermediate component is already a symlink pointing elsewhere. Symlink targets (`hdr.Linkname`) are also never validated: [2](#0-1) [3](#0-2) 

`hdr.Linkname` is attacker-controlled: it comes directly from the tar header of a cache or artifact archive the job produced/uploaded and later has restored (`cache_extractor.go`/`artifacts_downloader.go` both call `archive.NewExtractor(...).Extract(...)` with the job's build directory as `e.dir`): [4](#0-3) [5](#0-4) 

Within a single `Extract()` call, symlink creation is deferred until after all regular files in that same archive are written (`deferred` map processed in a second pass), so a same-archive TOCTOU write-through is not directly possible. However, extraction runs are not idempotent/isolated across invocations: a first cache-restore (or artifact-download) run can leave a symlink named e.g. `safe/output.txt` → `/root/.ssh` sitting in the job workspace. A subsequent, separate extraction in the same job (e.g., restoring a second cache key, or a later artifact/cache step) that contains a *regular file* entry named `safe/output.txt` will pass the lexical containment check (the string `e.dir/safe/output.txt` still starts with `e.dir`) and then call `os.Create(path)` at line 88, which follows the pre-existing symlink and writes the tar entry's content to whatever `hdr.Linkname` pointed at, entirely outside `e.dir`.

None of the existing checks stop this: the containment check is string-based and never re-`Lstat`s intermediate path segments, and `os.Create`/`os.MkdirAll` (line 66) both follow symlinks by default.

### Impact Explanation
Concretely, this is an uncontrolled-write primitive: a job that controls the contents of its own cache/artifact archives can plant a symlink and, via a second cache-restore or artifact-download step in the *same* job, overwrite file contents at an arbitrary filesystem location reachable by the process performing extraction (the `gitlab-runner cache-extractor` / `artifacts-downloader` helper). The severity of this depends heavily on the executor:
- Under the Docker executor (the common, non-excluded case), the extractor process runs inside the per-job helper container, so the write lands in that container's own filesystem/volume, not literally the Docker host, unless the job's build-directory volume is shared with sibling job containers on the same runner (which would then allow cross-project file corruption/exfiltration within that shared volume).
- Under the shell executor, or configurations where the build directory is a bind-mount of a real host path shared across jobs, this would allow direct host file write — but that scenario is explicitly excluded per the audit rules ("shell executor trust on a shared host").

So the bug itself (missing symlink-target validation / lexical-only path check) is real and reachable by an unprivileged job, but the "host file access" framing in the question requires an executor/mount configuration that falls under excluded, documented-trust scenarios to reach literal host paths.

### Likelihood Explanation
Highly feasible and repeatable: the attacker only needs to control the contents of a cache or artifact zip/tar it uploads (trivial via a `.gitlab-ci.yml` job script) and trigger two extraction phases in the same job (e.g., `cache: paths` restore followed by a later `artifacts` download step, or two sequential cache keys). No special privileges beyond normal pipeline authoring are needed.

### Recommendation
- Validate/reject symlink `Linkname` values that are absolute or that resolve (via `filepath.Join(e.dir, hdr.Linkname)` when relative) outside `e.dir`.
- Before creating a file/dir at `path` (both in the immediate write path at line 87-99 and in `os.MkdirAll` at line 66), `os.Lstat` each existing path segment and refuse to write through it if it is a symlink whose resolved target is outside `e.dir`, or simply refuse to overwrite any pre-existing symlink instead of following it (e.g., `os.Remove` the pre-existing symlink first, or open with `O_NOFOLLOW`-equivalent behavior on platforms that support it).
- Apply the same hardening to any other extractor in `commands/helpers/archive/*` that processes symlink entries.

### Proof of Concept
```go
func TestTarZstdExtractor_SymlinkEscapeAcrossExtractions(t *testing.T) {
    dir := t.TempDir()

    // Step 1: archive containing a symlink "safe" -> outside target (e.g. a sibling dir)
    outside := t.TempDir()
    buf1 := new(bytes.Buffer)
    tw := tar.NewWriter(zstdWriter(buf1))
    tw.WriteHeader(&tar.Header{
        Name:     "safe",
        Typeflag: tar.TypeSymlink,
        Linkname: filepath.Join(outside, "pwned.txt"), // absolute, outside e.dir
        Mode:     0777,
    })
    tw.Close()

    ext1, _ := tarzstd.NewExtractor(bytes.NewReader(buf1.Bytes()), int64(buf1.Len()), dir)
    require.NoError(t, ext1.Extract(context.Background()))

    // Step 2: a *separate* extraction run with a regular file named "safe"
    buf2 := new(bytes.Buffer)
    tw2 := tar.NewWriter(zstdWriter(buf2))
    tw2.WriteHeader(&tar.Header{Name: "safe", Typeflag: tar.TypeReg, Size: int64(len("attacker-data")), Mode: 0666})
    tw2.Write([]byte("attacker-data"))
    tw2.Close()

    ext2, _ := tarzstd.NewExtractor(bytes.NewReader(buf2.Bytes()), int64(buf2.Len()), dir)
    require.NoError(t, ext2.Extract(context.Background()))

    // Assertion: write must NOT have escaped e.dir
    _, err := os.Stat(filepath.Join(outside, "pwned.txt"))
    assert.True(t, os.IsNotExist(err), "write escaped e.dir via pre-existing symlink")
}
```
Expected (buggy) result: `outside/pwned.txt` is created with content `"attacker-data"`, proving the write escaped `e.dir` via the symlink planted in the first extraction. A fixed implementation should either fail the second `Extract()` call or refuse to follow the symlink, keeping the assertion `os.IsNotExist(err)` true.
