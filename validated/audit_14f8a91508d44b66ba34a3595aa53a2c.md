### Title
Multisig executes requests using confirmations from removed (non-member) accounts, allowing execution below the current live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`confirm()` counts votes from a `confirmations: LookupMap<RequestId, HashSet<String>>` set that is populated once and never revalidated. `DeleteMember` only purges requests *originated* by the removed member and their `num_requests_pk` entry; it never scans other pending requests' `confirmations` sets to strip out that member's stale votes. As a result, a request can reach `num_confirmations` using a vote cast by an account that is no longer a member at execution time, executing a K-of-N action with fewer than K currently-authorized live signers.

### Finding Description
`confirm()` only validates that the *caller* is a current member via `current_member()`, then checks the stored confirmation count against the threshold: [1](#0-0) 

`DeleteMember` execution (`delete_member`) removes the member from `self.members`, deletes the member's own outstanding requests (filtered by `r.member == member`), and clears `num_requests_pk`, but does nothing to `self.confirmations` entries belonging to *other* pending requests where that member had already voted: [2](#0-1) 

Because `confirmations` is keyed by `request_id -> HashSet<String>` of member identifiers and is never re-checked against the live `self.members` set at confirm-time (`assert_valid_request` only checks the request exists, not that every recorded confirmer is still a member), a vote cast by a subsequently-removed member remains valid and counts toward the threshold on any request that was pending before the removal.

The binding that should hold is: *confirmations counted == confirmations from currently live members*. This binding is broken: confirmations counted can include votes from accounts no longer in `self.members`.

### Impact Explanation
This lets a `MultiSigRequestAction` (e.g. `Transfer`, `FunctionCall`, `AddKey`/full-access-key grant, `DeployContract`) execute with fewer live-member approvals than `num_confirmations` requires, because a stale vote from a removed member is counted as if it were a current approval. This is exactly the listed Critical scenario "a multisig request executed below threshold" — it can result in unauthorized transfers of NEAR/wNEAR, unauthorized contract redeploys, or unauthorized key additions on the multisig account, i.e. funds moved by a party (or a coalition below the intended threshold) not fully entitled to authorize the action.

### Likelihood Explanation
Requires: (1) a K-of-N multisig with a pending request that has fewer than K confirmations, (2) one of the confirmers subsequently removed via a separate `DeleteMember` request, and (3) a remaining live member submitting the final confirmation to push the stale-inclusive count to K. This is a normal, foreseeable operational sequence for any long-lived multisig that rotates members while requests are in flight (e.g. removing a compromised or departing signer) — no attacker-controlled deployment or victim key theft is needed beyond ordinary member-management operations, making this a realistic, unprivileged-outcome-affecting scenario once a member rotation occurs while a request is outstanding.

### Recommendation
When executing `DeleteMember` (and the v1 `DeleteKey` equivalent), iterate all entries in `confirmations` (not just requests originated by the removed member) and remove the removed member's identifier from every confirmation set; alternatively, revalidate at `confirm()` time that every entry in the stored confirmation set is still contained in `self.members` before counting it toward the threshold (i.e., intersect confirmations with `self.members` on each `confirm` call rather than trusting the stored snapshot).

### Proof of Concept
1. Deploy multisig2 with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request` for `Transfer{amount}` → request `R` (0 confirmations).
3. `B` calls `confirm(R)` → confirmations = `{B}` (1 < 3).
4. `C` calls `confirm(R)` → confirmations = `{B, C}` (2 < 3).
5. Members `A, B, D` create+confirm a separate `DeleteMember{member: C}` request reaching threshold 3, executing `delete_member` — this removes `C` from `self.members` and clears `C`'s own originated requests, but leaves `confirmations[R] = {B, C}` untouched.
6. `D` (still a live member) calls `confirm(R)`: `confirmations.len() as u32 + 1 == 3 >= self.num_confirmations (3)` → `execute_request` runs the `Transfer`.
7. Result: the transfer executed with approvals effectively from only 2 live members (`B`, `D`) plus one stale vote from a removed non-member (`C`), i.e., below the intended 3-of-N live-member threshold — `funds moved`/`request executed below threshold` as defined in the Critical impact category.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
