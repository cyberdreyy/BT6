### Title
Cross-user response confusion via attacker-controlled `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each in-flight user request's callback in `h.savedCallbacks` keyed solely by the client-supplied `msg.Body.MessageId`, with no uniqueness check or binding to the requester's identity/connection. Because the `MessageId` is fully attacker-controlled (it is taken directly from the JSON-RPC request ID with no server-side generation or ownership enforcement), an attacker can submit a request using the same `MessageId` as another in-flight legitimate request, silently overwriting the victim's saved callback so that the DON's response to the victim's request is delivered to the attacker instead.

### Finding Description
The `MessageId` field is populated straight from the caller-supplied JSON-RPC `ID` with no server-side randomization or per-sender scoping: [1](#0-0) 

In the gateway entry point, requests are dispatched to `HandleLegacyUserMessage` for every incoming HTTP call, and each call gets an independent `Callback` (`handlerscommon.NewCallback()`), but nothing ties `MessageId` uniqueness/ownership to a specific caller before it's used as the map key: [2](#0-1) 

`HandleLegacyUserMessage` then unconditionally overwrites any existing entry for that `MessageId` without checking whether one is already in flight: [3](#0-2) 

When the DON later replies (echoing the same `MessageId` from the original signed message it received), `handleWebAPITriggerMessage` looks the callback up purely by `MessageId`, deletes it, and forwards the raw response to whichever callback is currently stored — with no verification that it belongs to the same requester who initiated the request: [4](#0-3) 

Exploit flow: Victim submits a signed legacy trigger request with `MessageId = X`; it is stored in `savedCallbacks["X"]` bound to Victim's HTTP connection callback. Before the DON responds, Attacker submits their own independently-signed legacy request also using `MessageId = X` (fully valid — Attacker owns their own signature over their own body, the code never validates `MessageId` uniqueness across requesters). This overwrites `savedCallbacks["X"]` with Attacker's callback. When the DON responds to the original (Victim's) request with `MessageId = X`, `handleWebAPITriggerMessage` finds Attacker's callback in the map and delivers Victim's response to Attacker's HTTP connection, while Victim's own request eventually times out with no response ever delivered (`RequestTimeoutError`).

None of the existing checks stop this: `msg.Validate()`/signature checks only prove that each message is properly signed by its own sender, not that the `MessageId` is unique or bound to that sender; `len(jsonRequest.ID) > 200` is only a size cap; there is no ID-uniqueness or requester-binding check anywhere in `HandleLegacyUserMessage`.

### Impact Explanation
This is unauthorized cross-user response confusion: an attacker (any unprivileged, unauthenticated-but-signed gateway client) can cause a DON's response destined for a legitimate victim request to be delivered to the attacker's own connection instead. Depending on payload content, this can expose the victim's trigger/workflow response data to the attacker and simultaneously deny the legitimate response to the victim (denial of service on that specific request through silent starvation/timeout).

### Likelihood Explanation
Exploitability requires the attacker to submit a signed request (any account can sign — no privilege required) with a `MessageId` that matches an in-flight victim `MessageId`, timed to land after the victim's request is stored but before the node's response is processed. Because `MessageId` values are frequently simple/sequential/predictable client-chosen IDs (there's no requirement for cryptographic randomness), and the race window is only bounded by node-response latency (up to `MaxAllowedMessageAgeSec`/`CallbackMaxAgeSec`, tens of seconds), this is feasible to reproduce reliably, especially against predictable ID schemes, and is trivially reproducible in a unit test with two goroutines racing on the same fixed `MessageId`.

### Recommendation
Do not key `savedCallbacks` solely on the client-supplied `MessageId`. Either (a) generate the map key server-side (e.g., a gateway-generated UUID or a hash of `sender+MessageId+nonce`) and use that internally while still tracking the client's `MessageId` for the response mapping, or (b) reject/queue collisions: before storing, check if `msg.Body.MessageId` already exists in `savedCallbacks` and if so return an error (e.g., duplicate/in-use message ID) rather than silently overwriting, or (c) scope the map key by `(sender, MessageId)` tuple so cross-sender collisions are impossible.

### Proof of Concept
Go test plan (table/integration style) in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Set up `handler` with a mock `DON` that captures/echoes requests.
2. Craft `victimMsg` and `attackerMsg`, both signed with different valid keys but with identical `MessageId = "collide-1"`.
3. In goroutine A: call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`.
4. In goroutine B (started slightly after A acquires the lock once, or synchronized via a barrier): call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)`.
5. Simulate the DON responding to the victim's original request: call `handler.HandleNodeMessage(ctx, victimNodeResponse, nodeAddr)` where `victimNodeResponse.Body.MessageId == "collide-1"`.
6. Assert that `attackerCallback.Wait(ctx)` receives the response intended for the victim (proving cross-delivery), and that `victimCallback.Wait(ctx)` times out/never receives a response — demonstrating that isolation is violated: exactly one callback should have received the legitimate response tied to its own request, but instead the wrong (attacker's) callback received it.

```go
func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
```
