### Title
Queued deposits can exceed the TVL limit and block epoch processing - (File: `contracts/IdleCDOEpochQueue.sol`)

### Summary

`IdleCDOEpochQueue.requestDeposit` only applies the cumulative TVL-limit check when the queue is configured as the AA prefunded queue, while ordinary queued deposits are accumulated without validating the resulting aggregate amount. [1](#0-0)  During the buffer period, `processDeposits` attempts to deposit the entire `epochPendingDeposits[_epoch]` amount in one `depositAA` or `depositBB` call. [2](#0-1)  If that aggregate exceeds `limit`, the CDO deposit path reverts with `ContractLimitReached`, leaving the whole epoch queue unprocessed. [3](#0-2) 

### Finding Description

Queued deposits are assigned to `epochNumber() + 1`, transferred into the queue, and accumulated in `epochPendingDeposits[nextEpoch]`. [4](#0-3)  The prefunded AA flow validates `epochPendingDeposits[nextEpoch] + amount` through `checkPrefunding`, which applies `_guarded`, but the non-prefunded path skips that validation entirely. [5](#0-4) [6](#0-5) 

An allowed depositor can therefore queue an amount that is valid for their own balance and allowance but makes the aggregate pending amount exceed the CDO’s remaining TVL capacity. [7](#0-6)  Later, the manager cannot process the epoch because the implementation deposits all pending queue funds atomically rather than processing individual requests or a capped amount. [8](#0-7) 

Deposit claims remain unavailable while `epochPrice[_epoch]` is unset or pending deposits remain nonzero. [9](#0-8)  Users can individually cancel only their own unprocessed request, so an honest manager cannot remove the attacker’s oversized request and cannot force the remaining queue to be processed. [10](#0-9) 

### Impact Explanation

An attacker can permanently prevent processing of a queued-deposit epoch for as long as their oversized request remains in `epochPendingDeposits[_epoch]`. [8](#0-7)  Other depositors can recover their principal through `deleteRequest`, but they cannot receive tranche shares through that epoch unless the attacker cancels. [10](#0-9) [11](#0-10) 

The frozen amount is all non-attacker deposits queued for the same epoch, while the attacker needs only `remainingCapacity + 1` after accounting for prior pending deposits; if the pool is already near its configured limit, the griefing cost can be one wei of underlying plus any amount needed to keep the aggregate above the cap. [3](#0-2) 

### Likelihood Explanation

The attack requires a running epoch, an allowed wallet, and enough underlying to push `epochPendingDeposits[nextEpoch]` over the remaining TVL capacity. [12](#0-11) [13](#0-12)  These are ordinary depositor capabilities, and the missing check only affects the non-prefunded queue mode. [5](#0-4) 

The attacker’s queued funds remain recoverable through `deleteRequest`, so the exploit does not permanently sacrifice the attacker’s principal. [10](#0-9) 

### Recommendation

Validate the aggregate queued amount at request time for every queue mode, not only the prefunded AA path. [5](#0-4) 

Add a CDO-side view such as `checkQueuedDeposit(nextEpochPending + amount)` that applies the same `_guarded` accounting used by direct deposits, and invoke it before accepting any queued AA or BB deposit. [6](#0-5)  Alternatively, expose the remaining capacity in the queue and reject `requestDeposit` when `epochPendingDeposits[nextEpoch] + amount` exceeds `limit - getContractValue()`. [3](#0-2) 

For defense in depth, `processDeposits` should also have a recovery path for requests that become oversized because TVL changes while they are queued, such as owner-assisted removal/refund of excess requests rather than making one bad request block the whole epoch. [14](#0-13) 

### Proof of Concept

The following Foundry fork test can be added to `test/foundry/IdleCDOEpochQueue.t.sol`; the existing setup etches the current implementation and creates a non-prefunded queue. [15](#0-14) 

```solidity
function testQueuedDepositCanBypassTVLLimitAndBlockEpoch() public {
  address victim = makeAddr("victim");
  address attacker = makeAddr("attacker");

  uint256 victimAmount = 1e6;
  uint256 attackerAmount = 1;

  uint256 currentValue = cdoEpoch.getContractValue();
  vm.prank(cdoEpoch.owner());
  cdoEpoch._setLimit(currentValue + victimAmount);

  deal(address(underlying), victim, victimAmount);
  deal(address(underlying), attacker, attackerAmount);

  vm.startPrank(victim);
  underlying.approve(address(queue), victimAmount);
  queue.requestDeposit(victimAmount);
  vm.stopPrank();

  vm.startPrank(attacker);
  underlying.approve(address(queue), attackerAmount);
  queue.requestDeposit(attackerAmount);
  vm.stopPrank();

  uint256 queuedEpoch = strategy.epochNumber() + 1;
  assertEq(queue.epochPendingDeposits(queuedEpoch), victimAmount + attackerAmount);

  _stopCurrentEpoch();

  vm.prank(manager);
  vm.expectRevert(ContractLimitReached.selector);
  queue.processDeposits();

  assertEq(queue.epochPrice(queuedEpoch), 0);
  assertEq(queue.epochPendingDeposits(queuedEpoch), victimAmount + attackerAmount);

  vm.prank(victim);
  vm.expectRevert(NotAllowed.selector);
  queue.claimDepositRequest(queuedEpoch);

  // The victim can refund only their own request. The attacker's request remains
  // and continues to make aggregate processing exceed the configured limit.
  vm.prank(victim);
  queue.deleteRequest(queuedEpoch);

  assertEq(queue.epochPendingDeposits(queuedEpoch), attackerAmount);

  vm.prank(manager);
  vm.expectRevert(ContractLimitReached.selector);
  queue.processDeposits();
}
```

The second `processDeposits` call still reverts because the attacker’s one-wei request keeps the aggregate queued deposit above the configured remaining capacity. [8](#0-7)

  function processDeposits() external {
    // only owner or strategy manager can process deposits
    _checkOnlyOwnerOrManager();
    // prefunded-enabled queues do not use the old buffer-period processing path
    _checkNotAllowed(_isPrefundedQueueEnabled());

    IdleCDOEpochVariant _cdo = IdleCDOEpochVariant(idleCDOEpoch);
    uint256 _epoch = IdleCreditVault(strategy).epochNumber();
    uint256 _pending = epochPendingDeposits[_epoch];

    if (_pending == 0) {
      return;
    }

    // deposit underlyings in the CDO contract, if the epoch is running it will revert
    uint256 _trancheMinted;
    if (tranche == _cdo.AATranche()) {
      _trancheMinted = _cdo.depositAA(_pending);
    } else {
      _trancheMinted = _cdo.depositBB(_pending);
    }
    // save current implied tranche price for this epoch based on underlyings deposited and tranche tokens minted
    epochPrice[_epoch] = _pending * ONE_TRANCHE / _trancheMinted;
    epochPendingDeposits[_epoch] = 0;
