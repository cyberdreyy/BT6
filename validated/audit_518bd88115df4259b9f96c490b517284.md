This is a real, self-contained finding: `LockupFactory::create` accepts `whitelist_account_id: Option<ValidAccountId>` directly from the caller with no validation that it matches `self.whitelist_account_id`, and no restriction requiring the caller to be the `owner_account_id`, the foundation, or any privileged party.

### Title
Unprivileged caller can inject an arbitrary staking-pool whitelist into another account's lockup deployment - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` lets any unprivileged account attach `MIN_ATTACHED_BALANCE`, specify `owner_account_id = victim`, and pass an arbitrary `whitelist_account_id` that is written verbatim into the deployed lockup's `staking_pool_whitelist_account_id` field, bypassing the factory's own `self.whitelist_account_id`. Because the deployed lockup account address is deterministic (`sha256(owner_account_id)` + factory account), the attacker can pre-emptively create the victim's lockup with a malicious whitelist before any legitimate deployment happens, permanently binding that owner to a whitelist contract that always returns "whitelisted" for any staking pool.

### Finding Description
The broken binding: `staking_pool_whitelist_account_id` in the deployed lockup's `LockupArgs` should equal `self.whitelist_account_id` (the factory's whitelist set at `LockupFactory::new`) [1](#0-0) , but the `create` method allows this to be overridden by caller-supplied input with no authorization check: [2](#0-1) 

The `whitelist_account_id: Option<ValidAccountId>` parameter is only format-validated (`ValidAccountId`), not checked against `self.whitelist_account_id`, nor is there any assertion that `env::predecessor_account_id() == owner_account_id` or any other privileged relationship. Any account (the "attacker") can call `create` with `owner_account_id = victim`, `whitelist_account_id = Some(fake_whitelist.near)`, and `MIN_ATTACHED_BALANCE` attached. The resulting `LockupArgs.staking_pool_whitelist_account_id` is set to `fake_whitelist.near` and persisted into the new lockup's state via `LockupContract::new` [3](#0-2) , which only validates the account ID format, not its provenance.

Because `lockup_account_id` is derived deterministically solely from `owner_account_id` (`sha256(owner_account_id.as_bytes())` + factory account) [4](#0-3) , an attacker can front-run the intended/legitimate lockup creation for any victim account. Since `Promise::new(lockup_account_id).create_account()` fails if the account already exists, whoever creates it first "wins" — permanently poisoning that owner's lockup address with an attacker-chosen whitelist, since lockups aren't redeployable once created.

Later, when the victim (as `owner_account_id`) calls `select_staking_pool`, the contract checks the pool against `self.staking_pool_whitelist_account_id` — the attacker's fake contract — instead of the real whitelist [5](#0-4) . A fake whitelist that always answers `true` defeats the purpose of the check entirely, so any staking pool (including attacker-controlled ones) is falsely reported "whitelisted," letting the owner unknowingly stake into a malicious pool.

`is_promise_success()` / `on_lockup_create`'s refund-on-failure logic [6](#0-5)  and [7](#0-6)  are irrelevant guards here — they only handle deployment failure/refund and do not validate `staking_pool_whitelist_account_id` at all.

None of the existing guards (`assert_owner`, `assert_self`, `is_promise_success`, `is_valid_account_id`) prevent this, since the whitelist override is an intentional, unguarded feature of `create`'s public API (also exercised in the existing `test_create_lockup_with_custom_whitelist_success` test, confirming the parameter is reachable and unconstrained) [8](#0-7) .

### Impact Explanation
This matches the Critical category "a lockup deployed with parameters its rightful creator never chose." The victim's future lockup account is bound to a whitelist contract they never authorized. If the attacker's fake whitelist always returns `true`, the victim's `select_staking_pool` call will falsely validate any staking pool as vetted, potentially causing the victim's locked/vesting NEAR to be staked into an attacker-run pool that keeps deposits (rewards/principal never returned) — a Critical-severity loss of the victim's funds once staking is subsequently completed by the (deceived) owner. The attack is repeatable against any `owner_account_id` that hasn't yet had its deterministic lockup account created, and requires no owner or foundation privilege.

### Likelihood Explanation
The only precondition is possessing `MIN_ATTACHED_BALANCE` (3.5 NEAR) and knowing/guessing a target `owner_account_id` before their legitimate lockup is deployed — both trivial for any unprivileged account. Since lockup account IDs are deterministic and publicly computable from `owner_account_id`, an attacker can watch for or preempt legitimate lockup creations for high-value targets. Cost is only the attached deposit (refunded to attacker's control since attacker is `predecessor_account_id` in `on_lockup_create` if it were to fail, but on success it goes to the new lockup, funded by attacker, recoverable by no one but usable as bait). This is fully repeatable across any number of victim accounts.

### Recommendation
Remove the caller-supplied `whitelist_account_id` override from `create`, or restrict it: always use `self.whitelist_account_id` for `staking_pool_whitelist_account_id`, or require the override to be authorized (e.g., only allow it when `predecessor_account_id == foundation_account_id`, or when the override exactly matches an allow-listed set of whitelist contracts maintained by the factory owner).

fn test_create_lockup_custom_whitelist_not_factory_whitelist() {

    // Attacker (predecessor != owner, != foundation) supplies a different whitelist.
    context.is_view = false;
    context.predecessor_account_id = String::from(attacker_account()); // unprivileged
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());

    let attacker_whitelist = custom_whitelist_account_id(); // e.g. "fake_whitelist.near"
    contract.create(
        victim_account_id(),          // owner_account_id = victim, not attacker
        lockup_duration.into(),
        None,
        None,
        None,
        Some(attacker_whitelist.clone()),
    );

    // near-workspaces / near-sdk-sim receipt inspection) and assert:
    // deployed_lockup_args.staking_pool_whitelist_account_id == attacker_whitelist
    // != contract.whitelist_account_id (the factory's rightful whitelist)

    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
