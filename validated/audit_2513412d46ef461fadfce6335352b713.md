### Title
`BlockRejection` signature does not bind `reason_code`/`response_data` (incl. `reject_reason`, `failed_txid`) to the signer identity - (File: `libsigner/src/v0/messages.rs`)

### Summary
### Finding Description
`BlockRejection` carries two categories of data: an identity-authenticating signature, and a set of "reason" fields (`reason: String`, `reason_code: RejectCode`, and the entire `response_data: BlockResponseData`, which itself contains `reject_reason: RejectReason`, `failed_txid: Option<Txid>`, `tenure_extend_timestamp`, etc.). The signature is produced and checked exclusively over a hash that binds only `signer_signature_hash` and `chain_id`: [1](#0-0) 

`sign()` and `verify()` both call `self.hash()`, which is `structured_data_message_hash(Value::buff_from(signer_signature_hash bytes), domain("block-rejection","1.0.0",chain_id))` - none of `reason`, `reason_code`, or `response_data` participate in the digest: [2](#0-1) 

By contrast, `BlockAccepted`'s signature is a raw ECDSA signature over the block's `signer_signature_hash` bits (this is the actual consensus block-signature format), so the domain separation on the reject side was clearly a deliberate anti-confusion measure between accept/reject - but it only protects that one axis. It does **not** protect the *reason metadata* attached to a rejection.

Downstream, this reason metadata is trusted as if it were authenticated data coming from the specific signer identity that `recover_public_key()`/`verify()` establish:

- `handle_block_rejection` recovers the public key, checks `is_valid_signer`, and then feeds `(&rejection.response_data.reject_reason).into()` into `store_and_process_block_rejection` and into the pending-rejection table, keyed by that signer's address: [3](#0-2) 
- The node-side StackerDB listener performs the identical pattern for `BlockResponse::Rejected`: it recovers/authenticates the public key and then uses `reason_code` and `response_data.failed_txid` (fields *outside* the signed digest) to attribute rejection weight to specific transactions: [4](#0-3) 

Because `reason`/`reason_code`/`response_data` sit outside the signed hash, any party that can produce or relay the byte stream carrying a `BlockRejection` (e.g., a signer re-broadcasting, a relaying node, or any code path that reconstructs/forwards the message rather than passing through an unmodified StackerDB chunk) can substitute an arbitrary `reason_code`, `reject_reason`, or `failed_txid` while the `verify()`/`recover_public_key()` check still reports the message as authentically signed by the original signer's key - because that check is mathematically indifferent to those fields. This breaks the implicit equality the rest of the codebase assumes: "if `verify()` succeeds, everything in this `BlockRejection` came from that signer."

This is the direct analog to the Cally `createVault()` bug: a self-declared "type/kind" field (`tokenType` in Cally; `reason_code`/`reject_reason`/`failed_txid` here) is trusted by downstream logic to correspond to the object that was actually cryptographically checked (`token`'s real type in Cally; the signer's authenticated intent here), but the check performed does not verify that correspondence.

### Impact Explanation
This falls under "a rejection recounted as an accept" / "miscounted response" impact category by a different route: the *reason* a rejection carries can be forged independent of signer identity, which:
1. Lets a relay/attacker poison `failed_txids` weight tracking on the node side by attaching an authenticated-looking `RejectCode::ValidationFailed(BadTransaction|ProblematicTransaction)` and an arbitrary `failed_txid` to a signer's rejection they never actually issued for that reason, causing the miner to misattribute rejection weight to an unrelated transaction (potential censorship/DoS of a legitimate transaction under a false rejection-weight signal), and
2. Lets an attacker manipulate the signer-side `reject_reason`, which gates `should_reevaluate_block`/`should_reevaluate_reject_reason` (per `docs/signer-flows.md` section 3, `REASON` branch), affecting whether a previously-rejected block is treated as re-evaluable. Forging `reject_reason` to a value that either forces or blocks re-evaluation could wedge a signer's state machine around a specific block's disposition, or cause the group's rejection tally to be interpreted inconsistently with the interpretation the actual (unforged) rejection reason would have produced across observers.

Because the signature itself remains valid for the identity it purports to belong to, this is a genuine "signed vs. validated" equality break rather than a spoofable-identity attack; it does not require a majority of signers or another signer's key - a single relaying party (or a malfunctioning/malicious library consumer) reconstructing the message is sufficient.

### Likelihood Explanation
Likelihood is moderate: exploitation requires a code path where the `BlockRejection`'s bytes are reconstructed or forwarded independent of the StackerDB chunk-level signature that would otherwise bind the full byte content (chunk writes are typically self-signed over their full payload). The vulnerability is real and provable in the `libsigner` message layer itself - the message-level signature's own security contract is weaker than its consumers (`is_valid_signer` gates in `stacks-signer/src/v0/signer.rs`, and the node's `stackerdb_listener.rs`) assume. I could not fully verify, within the given search budget, whether every consumption path of `BlockRejection` in this codebase is always wrapped by an outer StackerDB chunk signature that would additionally bind these fields end-to-end (which would reduce the practical exploitability to defense-in-depth rather than a directly triggerable exploit). This is a limitation of the analysis, not evidence that the issue is unreachable.

### Recommendation
Include `reason`, `reason_code`, and the serialized `response_data` (or at minimum a hash of them) in the digest signed/verified by `BlockRejection::hash()`, mirroring how `signer_signature_hash` is bound today, so that `verify()`/`recover_public_key()` authenticate the entire semantic content of the rejection, not merely the block identifier and chain id.

### Proof of Concept
1. Take any validly-signed `BlockRejection` `r` from signer `S` for block `H` (e.g., `reason_code = RejectCode::SortitionViewMismatch`, `response_data.reject_reason = RejectReason::ConsensusHashMismatch{..}`).
2. Construct `r' = r` but with `reason_code = RejectCode::ValidationFailed(ValidateRejectCode::ProblematicTransaction)` and `response_data.failed_txid = Some(victim_txid)`, leaving `signer_signature_hash`, `chain_id`, and `signature` unchanged.
3. Call `r'.verify(&S_pubkey)` / `r'.recover_public_key()`: both succeed, because `hash()` only depends on `signer_signature_hash` and `chain_id`, per [5](#0-4)  - identical to `r`.
4. Feed `r'` into `handle_block_rejection`/the node's `stackerdb_listener.rs` handler: `is_valid_signer`/pubkey checks pass, and the forged `reject_reason`/`failed_txid` are then trusted and used for state/weight decisions, even though signer `S` never actually rejected the block for that reason.

    /// The signature hash for the block rejection
    pub fn hash(&self) -> Sha256Sum {
        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
        structured_data_message_hash(data, domain_tuple)
    }

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

        &mut self,
        rejection: &BlockRejection,
        sortition_state: &mut Option<SortitionsView>,

        debug!("{self}: Received a block-reject signature: {rejection:?}");

        let block_hash = &rejection.signer_signature_hash;
        let signature = &rejection.signature;

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {
            debug!("{self}: Received block rejection with an unrecovarable signature. Will not store.";
               "signer_signature_hash" => %block_hash,
               "signature" => %signature
            );
            return;
        };

        // authenticate the signature -- it must be signed by one of the stacking set
        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }

        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {

                &signer_address,
                (&rejection.response_data.reject_reason).into(),
            ) {
                warn!("{self}: Failed to add pending block rejection response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block rejection";

            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,

            "reject_reason" => ?rejection.response_data.reject_reason,
        );

            sortition_state,
            &mut block_info,
            &signer_address,
