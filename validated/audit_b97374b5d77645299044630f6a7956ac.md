### Title
External Initiator Can Trigger Arbitrary Job Runs via `/jobs/:ID/runs` Because the "Users Only" Check Is Bypassed - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` is reachable both by logged-in users and by External Initiators (EIs) through the shared `userOrEI` route group, but it contains a comment-documented restriction that only real users (not EIs) may trigger jobs by their numeric ID. That restriction is implemented with `auth.GetAuthenticatedUser(c)`, which is also populated for EI-authenticated requests, so the intended check never actually excludes EIs. An EI credential (issued only for triggering a single named webhook job) can therefore run **any** job on the node by numeric ID.

### Finding Description
The router wires External Initiators, API tokens, and session cookies into the *same* middleware group and lets them all reach `PipelineRunsController.Create`: [1](#0-0) 

Inside `AuthenticateExternalInitiator`, once the EI credential is verified, the code sets **both** `SessionExternalInitiatorKey` and `SessionUserKey` (the second one to a synthetic `User{Role: UserRoleRun}`): [2](#0-1) 

`Create` then tries to gate numeric-ID job execution to "users" only, using `GetAuthenticatedUser`: [3](#0-2) 

But `GetAuthenticatedUser` simply reads `SessionUserKey`: [4](#0-3) 

Since `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` is `true` for EI-authenticated requests exactly the same as for real logged-in users. The comment "only users are allowed to run jobs using int IDs - EIs not allowed" therefore does not hold: the code path meant to enforce that separation checks the wrong/shared piece of state, similar to how the ERC721F bug relied on an overridden function (`transferFrom`) for access control while a parallel, unguarded code path (`safeTransferFrom`) reached the same sensitive operation without going through the check. Here, the "run by int ID must be a real user" invariant is likewise bypassable through a parallel authenticated path (EI auth) that shares the same session marker the guard inspects.

### Impact Explanation
An External Initiator credential — normally scoped only to trigger the specific webhook job it was registered against, via the job's `externalJobID`/string-UUID route — can instead call `POST /v2/jobs/:ID/runs` with any job's numeric database ID and trigger a run for **any** job configured on the node (OCR jobs, direct-request jobs, flux monitor jobs, etc.), not just its own. This is an authorization/scope bypass: `prc.App.RunJobV2(ctx, jobID, nil)` is invoked without any check that the caller (the EI) is entitled to run that particular job. Because RunJobV2 can trigger job execution (and, depending on job type, on-chain transactions/fund movement pipelines), this is an unauthorized job run with potential fund-movement impact, exactly the class of impact called out as acceptable in scope.

### Likelihood Explanation
Exploitation only requires possession of any valid External Initiator access key/secret pair (which is a deliberately less-privileged, narrowly-scoped credential intended for triggering one specific webhook job). No admin/session cookie or elevated API token is required — this fits the "unprivileged actor" analog since EIs are the least-privileged authenticated principal in the system, explicitly meant to be restricted from directly listing/running arbitrary jobs (as shown by the `viewOnlyAllowed/EditAllowed` RBAC map excluding EIs from most `authv2` routes and by the explicit code comment expressing intent to exclude EIs from numeric-ID runs).

### Recommendation
In `PipelineRunsController.Create`, distinguish a genuine `User` session from an External-Initiator-derived session instead of relying on the shared `SessionUserKey`. For example, check `auth.GetAuthenticatedExternalInitiator(c)` first and reject/short-circuit when an EI is present, or set a dedicated marker for "real user" sessions that EI authentication does not populate, then require the numeric-ID branch to see only that marker.

### Proof of Concept
1. Create a webhook job A and register an External Initiator `EI1` scoped to it (`POST /v2/external_initiators`), obtaining `AccessKey`/`Secret`.
2. Create a second, unrelated job B (e.g., another webhook or OCR job) with numeric DB ID `B_ID`.
3. Send:
```
POST /v2/jobs/B_ID/runs
X-Chainlink-EA-AccessKey: <EI1 AccessKey>
X-Chainlink-EA-Secret: <EI1 Secret>
```
4. `Authenticate` succeeds via `AuthenticateExternalInitiator`, which sets `SessionUserKey`. `PipelineRunsController.Create` parses `B_ID` as an int32, `GetAuthenticatedUser` returns `ok=true`, and `prc.App.RunJobV2(ctx, B_ID, nil)` runs job B — a job `EI1` was never registered against.

// GetAuthenticatedUser extracts the authentication user from the context.
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
