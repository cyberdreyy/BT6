### Title
Front-run of `MultisigFactory::create()` permanently freezes the caller's attached deposit - ([File: multisig-factory/src/lib.rs])

### Summary
`MultisigFactory::create()` derives a fully deterministic sub-account name from a caller-supplied `name` parameter and immediately issues a `create_account()` promise funded with the caller's `attached_deposit`. Unlike the sibling factories in this codebase (`lockup-factory`, `staking-pool-factory`), it has **no callback** that checks whether the account creation succeeded and refunds the deposit if it failed. This is the same bug class as the external report (a `CREATE2`/account-creation front-run causing the intended contract creation to fail), but here the outcome is not merely a bad-UX revert — it is a genuine, unrecoverable loss of NEAR for the caller.

### Finding Description
`create()` computes `account_id = format!("{}.{}", name, env::current_account_id())` and issues: [1](#0-0) 

```
Promise::new(account_id)
    .create_account()
    .deploy_contract(CODE.to_vec())
    .transfer(env::attached_deposit())
    .function_call(... "new" ...)
```

There is no `.then(ext_self::on_create(...))` callback anywhere in this contract, confirmed by grepping the crate for `on_create`, `callback`, `is_promise_success` — no matches exist in `multisig-factory/src/**`.

Compare this to the two other factories in the repo, which explicitly guard against this exact scenario:
- `lockup-factory` attaches `on_lockup_create`, which checks `is_promise_success()` and, on failure, does `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` to return the deposit to the original caller. [2](#0-1) 
- `staking-pool-factory` has the identical pattern in `on_staking_pool_create`, additionally maintaining a `staking_pool_account_ids` set to reject duplicate names before spending gas on the sub-call. [3](#0-2) 

`MultisigFactory::create()` has neither protection: no pre-check for name collision, and no post-failure refund path.

**Attack path:** An attacker observes a pending `create(name, members, num_confirmations)` transaction for a victim in the mempool (the `name` parameter is public). The attacker submits their own `create()` call for the same `name` with a negligible attached deposit and gets it mined first. When the victim's transaction executes, the `create_account()` action for `{name}.{multisig-factory}` fails because the account already exists. Because there is no callback, NEAR's runtime refunds the failed receipt's unused deposit to the **predecessor of that failed receipt**, which is the `multisig-factory` contract itself (not the original caller who called the payable `create` function). The caller's `attached_deposit` — which had already been logically transferred out of their control into the factory's outgoing promise — is not returned to them by any contract logic.

### Impact Explanation
This breaks the custody binding of "NEAR debited from caller == NEAR the caller (or their intended multisig) ends up controlling." The victim's deposit (which the README example shows can be up to 50 NEAR) becomes NEAR sitting in/passing through the `multisig-factory` account with no code path to return it to the depositor, i.e., permanently frozen/lost funds for that user, triggerable at will by any unprivileged attacker for the cost of a front-run transaction and a minimal deposit of their own. This matches the "Critical — funds permanently frozen" impact bucket.

### Likelihood Explanation
Likelihood is high in practice: the attack requires only observing a pending, unconfirmed `create()` transaction (name is plaintext in the call args) and submitting a competing transaction with higher priority/gas — no privileged access, no victim key, and no redeploy is needed. The same race can also occur accidentally (two independent users picking the same friendly `name`), so this is not purely a targeted-attacker scenario; it's a reachable failure mode any time two `create()` calls collide on `name`.

### Recommendation
Add a callback (`on_create`), analogous to `on_lockup_create` / `on_staking_pool_create`, that checks `is_promise_success()` after the account-creation promise chain and refunds `attached_deposit` back to `env::predecessor_account_id()` on failure. Additionally, consider tracking created names (or rejecting via `env::is_valid_account_id` + existence pre-check where feasible) to reject duplicate `name` values before spending gas, mirroring the `staking_pool_account_ids` set pattern in `staking-pool-factory`.

### Proof of Concept
1. Victim submits `create({"name": "dao", "members": [...], "num_confirmations": N})` with `--amount 50` NEAR attached.
2. Attacker observes this pending transaction, and submits `create({"name": "dao", "members": [attacker], "num_confirmations": 1})` with a minimal deposit, and has it included first.
3. `dao.<factory>` account now exists, owned/controlled per the attacker's `create()` call.
4. Victim's transaction executes; the `create_account()` action for `dao.<factory>` fails (`AccountAlreadyExists`), the whole promise batch for the victim's call fails.
5. No callback exists in `multisig-factory/src/lib.rs` to detect this failure and refund the deposit to the victim; the victim's 50 NEAR is not returned to them (it is refunded by protocol-level receipt handling to the factory account, not to the victim's account), a permanent loss for the victim.

```rust
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```
