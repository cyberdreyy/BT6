## Analog Found

### Title
Coordinator double-counts a signer's weight in both `total_weight_approved` and `total_weight_rejected` when a signer revokes its rejection and later accepts the same block — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The Aegis `YUSD` bug is fundamentally an **asymmetric accounting bug**: the code releases the full collateral amount using a value computed before a deduction is applied, so the same underlying value gets "spent" twice (once as released collateral, once as an un-backed fee), breaking the invariant that liabilities equal backing. The `StackerDBListener` coordinator on the node side has the analogous class of bug: it tracks per-signer voting weight using two *different, asymmetric* guards for the "accept" and "reject" paths, so a signer's weight can be counted into **both** `total_weight_approved` and `total_weight_rejected` simultaneously, breaking the invariant that a single signer's weight should only ever back one side of the aggregated tally at a time.

### Finding Description
`BlockStatus` tracks `responded_signers: HashSet<u32>`, `gathered_signatures: BTreeMap<u32, MessageSignature>`, `total_weight_approved`, and `total_weight_rejected`. [1](#0-0) 

On an **Accepted** response, the guard that decides whether to add weight is `!block.gathered_signatures.contains_key(&slot_id)` — i.e. "have I already recorded a signature from this slot": [2](#0-1) 

On a **Rejected** response, the guard is instead `block.responded_signers.insert(slot_id)` — i.e. "has this slot responded at all (accept or reject)": [3](#0-2) 

These two guards are asymmetric:
- **Accept → Reject** for the same slot is correctly protected: `responded_signers` already contains the slot from the earlier acceptance, so `insert` returns `false` and the reject weight is never added.
- **Reject → Accept** for the same slot is **not** protected: the accept-path guard only checks `gathered_signatures`, which is empty for that slot (the signer only rejected before, never signed). So the accept path adds the signer's weight to `total_weight_approved`, while the earlier reject weight is **never removed** from `total_weight_rejected`. The same signer's weight is now counted on both sides of the tally simultaneously.

This is not a hypothetical edge case — the signer protocol explicitly documents rejection as a *revocable* opinion that can be followed by a later signature over the same block: [4](#0-3) 

The only cleanup path, `reset_rejections`, only fires on a *proposal timeout* (a new proposal round) and explicitly does not touch approvals, and does not run at all on a simple late-arriving Accepted for an already-rejected slot: [5](#0-4) 

### Impact Explanation
`total_weight_rejected` and `total_weight_approved` are the miner's ground truth for deciding a block's fate: [6](#0-5) 

Because a single signer's weight can remain "stuck" in `total_weight_rejected` even after that signer switches to accepting the same block, the coordinator can compute `total_weight_rejected.saturating_add(weight_threshold) > total_weight` using ghost weight that no longer represents any live rejection — declaring the block `SignersRejected` (with associated txid exclusion side effects) even though a legitimate majority actually supports it. This is a liveness wedge on block/tenure production reachable by ordinary signer behavior (no majority collusion, no other signer's key, no auth token) — a single signer that rejects then later accepts (an explicitly sanctioned protocol behavior) corrupts the miner's aggregate tally for that block.

### Likelihood Explanation
This requires only one signer to send `Rejected` followed later by `Accepted` for the same `signer_signature_hash` — a scenario the signer-flows documentation explicitly describes as valid ("rejection is a revocable opinion"), e.g. a signer rejects due to a transient chainstate mismatch, then a later pre-commit/re-evaluation cycle causes it to sign the very same block. No special privileges, timing races with other signers, or majority weight are needed to trigger the double count; it happens automatically on the miner's local tally for every such flip.

### Recommendation
Use one consistent guard for both message kinds — e.g. track "which side" (if any) each `slot_id` last voted, and when a slot's vote flips from rejected to accepted (or vice versa), subtract the previously-counted weight before adding it to the new side, rather than gating "accept" and "reject" on two different sets (`gathered_signatures` vs. `responded_signers`).

### Proof of Concept
1. Coordinator inserts a fresh `BlockStatus` for block `B` via `insert_block` (`total_weight_approved = 0`, `total_weight_rejected = 0`, `responded_signers = {}`, `gathered_signatures = {}`). [7](#0-6) 
2. Signer `S` (slot `k`, weight `w`) sends `BlockResponse::Rejected` for `B`. `responded_signers.insert(k)` succeeds → `total_weight_rejected += w`.
3. `S` later re-evaluates and sends `BlockResponse::Accepted` for the *same* `B` (a protocol-sanctioned behavior per the docs). The accept-path guard `!gathered_signatures.contains_key(&k)` is true (still empty for `k`), so `total_weight_approved += w` and `gathered_signatures.insert(k, sig)`.
4. Now `total_weight_rejected` still includes `w` from step 2, and `total_weight_approved` also includes `w` from step 3 — `S`'s weight is double-counted across both totals, even though `S` currently has exactly one live vote (accept). If enough such flips occur, `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can trigger `SignersRejected` purely from stale weight, aborting a block that in reality has sufficient live support.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
