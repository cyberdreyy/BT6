### Title
Global unbounded/unisolated `savedCallbacks` cache lets any signer flood-evict a victim's pending gateway response - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` accepts any correctly self-signed `MethodWebAPITrigger` message from any ECDSA key (no sender allowlist, per the explicit `// TODO: apply allowlist and rate-limiting here` at handler.go:384 and the corroborating `// TODO: Validate Senders and rate limit check` at handler_test.go:365) and stores a `savedCallback` in a single global map keyed only by `MessageId`. `pruneCallbacks` evicts entries strictly by global age ordering once the map exceeds `MaxSavedCallbacks`, with no per-sender accounting, so a high-volume attacker can force eviction of another user's still-pending callback before the legitimate DON response arrives.

### Finding Description
The request path is: `gateway.ProcessRequest` (core/services/gateway/gateway.go:218-292) decodes and validates message structure/signature via `msg.Validate()` (core/services/gateway/api/message.go:54-88), which only checks length/format and recovers a signer address from the signature — it does **not** check that signer against any allowlist of authorized users/nodes. It then dispatches to `h.HandleLegacyUserMessage` (handler.go:341-421).

Inside `HandleLegacyUserMessage`, after payload/timestamp checks, the handler stores the callback unconditionally: [1](#0-0) 
There is no per-sender quota or rate limiting anywhere on this path — the only rate limiter in the file, `h.nodeRateLimiter`, is applied to *outgoing* node-originated messages in `handleWebAPIOutgoingMessage` (handler.go:166-168), not to inbound user triggers.

`pruneCallbacks` (handler.go:299-339) only triggers eviction based on total map size vs. `MaxSavedCallbacks`, sorting **all** entries (regardless of sender) by `createdAt` and deleting the oldest half once the global count is exceeded: [2](#0-1) 
Because `MessageId` is attacker-chosen (bounded only by length ≤128 per `MessageIdMaxLen`, message.go:22,61-63) and any self-generated keypair can produce a valid signature, an attacker can trivially mint `MaxSavedCallbacks + N` unique signed `web_api_trigger` messages faster than the DON responds, causing the victim's earlier-created `savedCallback` entry to be sorted into the oldest half and deleted by the periodic `pruneCallbacks` ticker (fired every `CallbackPruneIntervalSec`, default 30s, via `Start`, handler.go:269-285) before the legitimate node reply reaches `handleWebAPITriggerMessage` (handler.go:148-162), which does a plain `delete`+lookup with no distinction of who is allowed to consume it.

### Impact Explanation
This is a cross-user denial/loss-of-response bug: an unprivileged, self-authenticated (self-signed, not node/operator) attacker can silently cause another legitimate user's `HandleLegacyUserMessage` call to never receive its DON response — the callback is deleted from `savedCallbacks` and the caller's `callback.Wait(ctx)` in `gateway.ProcessRequest` (gateway.go:278) will simply time out (`RequestTimeoutError`), because when the genuine node response later arrives, `handleWebAPITriggerMessage`'s lookup (`found`) will be false and the response is dropped (handler.go:154-160, `if found` guard). This matches an isolation/availability-adjacent impact: shared, un-partitioned bounded state allows one unauthenticated party to extinguish another party's in-flight request, without any authentication bypass or privilege escalation being required.

### Likelihood Explanation
Feasibility is high: no allowlist enforcement exists on this path (confirmed by the TODOs and the absence of address-based checks in `Message.Validate()`), so the only "credential" required is possessing/generating a private key and correctly signing a `web_api_trigger` message. `MaxSavedCallbacks` defaults to 20000 (handler.go:44), which is a meaningful but not insurmountable number for a scripted flood, especially since the DON round-trip for real requests can be significantly slower than raw message submission, giving attackers a large exploitation window. The attack is fully repeatable and does not require timing races beyond volume/rate advantage over legitimate traffic and the 30-second `CallbackPruneIntervalSec` prune cadence.

### Recommendation
- Enforce the still-pending sender allowlist/rate-limiting called out in the `TODO` at handler.go:384 before storing any `savedCallback`, so an unauthorized/unrecognized signer cannot occupy cache slots at all.
- Add a per-sender quota (e.g., cap in-flight `savedCallbacks` per `msg.Body.Sender`) independent of the global `MaxSavedCallbacks` limit, so no single sender's flood can starve another sender's pending entries.
- Consider rejecting new trigger submissions once the global cache is full (backpressure) rather than silently evicting the oldest entries, or at minimum exempt/prioritize entries close to expiry rather than pure FIFO-by-creation eviction.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with a small `MaxSavedCallbacks` (e.g., 10) for test speed via `HandlerConfig`.
2. Seed `h.savedCallbacks` with one "victim" entry created via `HandleLegacyUserMessage` using a distinct signer key and `MessageId="victim-1"`, capturing its `handlers.Callback`.
3. Loop, generating `MaxSavedCallbacks` additional signed `web_api_trigger` messages from N different attacker-generated ECDSA keys (or the same key with different `MessageId`s), each via `HandleLegacyUserMessage`, all with `createdAt` after the victim's.
4. Call `handler.pruneCallbacks()` directly (or wait for the ticker).
5. Assert: `handler.savedCallbacks["victim-1"]` no longer exists (`require.NotContains`/lookup returns not found).
6. Then simulate the victim's real DON response by calling `handler.HandleNodeMessage`/`handleWebAPITriggerMessage` with a matching `resp` for `"victim-1"`, and assert the victim's `callback.Wait(ctx)` times out / never receives `UserCallbackPayload`, proving the response is silently dropped due to the eviction — confirming isolation is violated because eviction accounting is global, not per-sender.

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)

		}
	}
