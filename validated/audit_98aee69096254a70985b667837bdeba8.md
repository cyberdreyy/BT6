### Title
`filter_map_rewards` uses O(addresses) linear-scan filtering per reward, giving O(rewards × addresses) cost per `getInflationReward` call - (File: `rpc/src/rpc.rs`)

### Summary
`RpcSolImpl::filter_map_rewards` filters the block's `Rewards` vector against the caller-supplied `addresses` list using `addresses.contains(&reward.pubkey)`, a `Vec<String>` linear scan, rather than a `HashSet`/`HashMap` lookup. Because `addresses.len()` is capped by `MAX_GET_INFLATION_REWARD_ADDRESSES` but the length of the on-chain `Rewards` vector for the epoch-boundary block is not bounded, the per-request CPU cost of a single `getInflationReward` call scales with the total number of vote/stake accounts rewarded that epoch, which an unprivileged actor can grow by creating additional vote accounts.

### Finding Description
`get_inflation_reward` (`rpc/src/rpc.rs:700-898`) fetches the epoch-boundary block and calls `Self::filter_map_rewards(epoch_boundary_block.rewards, ..., &addresses, ...)` at [1](#0-0) . `filter_map_rewards` itself is defined as: [2](#0-1) 

The filter predicate `addresses.contains(&reward.pubkey)` performs a linear scan of the `addresses: &[String]` slice for every element of the block's `Rewards` vector. `addresses` is bounded by `MAX_GET_INFLATION_REWARD_ADDRESSES` (checked client/param-side before reaching this code), but `epoch_boundary_block.rewards` is not bounded by any client-supplied parameter — it reflects however many vote (and, for pre-partitioned-reward epochs, stake) accounts received a reward at the epoch boundary, i.e., the size of the network's active vote-account set. Since vote accounts are cheap to create by any unprivileged actor and persist as long-lived on-chain state, an attacker can inflate this vector's length over time by registering many vote accounts, causing every subsequent `getInflationReward` call (by any client, not just the attacker) to perform O(rewards_len × addresses_len) comparisons instead of O(rewards_len) or O(addresses_len).

Although `reward_map` immediately after filtering is a `HashMap` [3](#0-2) , that only benefits lookups downstream; the expensive linear-scan filtering happens before the map is built, so the HashMap does not mitigate the quadratic-ish behavior in `filter_map_rewards`.

The `min_context_slot`/commitment and `MAX_GET_INFLATION_REWARD_ADDRESSES` guards only bound the caller-controlled `addresses` parameter; there is no guard limiting or paginating the size of `epoch_boundary_block.rewards`, so this cost is not stopped by any existing check.

### Impact Explanation
This is a single-call, unbounded-cost issue: one `getInflationReward` request (within the allowed rate of ≤1 per `CLUSTER_SLOT_TIME_TARGET / 2`) forces the validator to do CPU work proportional to the total number of vote (and historically stake) accounts network-wide rather than to any value the calling client controls or pays for. As the on-chain vote-account population grows (attacker-influenceable by creating vote accounts, a legitimate on-chain write later surfaced via this API), the fixed-rate cost of servicing this RPC method increases without bound, matching the "unbounded cost for a single low-rate call" bounty category for RPC.

### Likelihood Explanation
Feasible and repeatable: any unprivileged party can create vote accounts on-chain (subject only to rent/SOL cost, not to validator/leader/gossip control), which increases the length of `Rewards` returned for every subsequent epoch boundary block indefinitely. Once the network has amassed a large vote-account count (which happens naturally over time and can be accelerated by an attacker), a single, rate-compliant `getInflationReward` call with a `MAX_GET_INFLATION_REWARD_ADDRESSES`-sized address list will always pay the O(rewards × addresses) cost, so the condition is persistent, not a one-off race.

### Recommendation
Replace the `Vec<String>` linear-scan filter in `filter_map_rewards` with a `HashSet<&str>`/`HashSet<String>` (or `HashMap`) built once from `addresses` before filtering, so each reward lookup is O(1) instead of O(addresses.len()). This reduces the per-call cost to O(rewards_len + addresses_len) instead of O(rewards_len × addresses_len), removing the multiplicative blow-up while keeping the request semantics identical.

### Proof of Concept
Rust benchmark/unit test plan for `rpc/src/rpc.rs`:
```rust
#[test]
fn bench_filter_map_rewards_scaling() {
    use std::time::Instant;
    let addresses: Vec<String> = (0..MAX_GET_INFLATION_REWARD_ADDRESSES)
        .map(|_| Pubkey::new_unique().to_string())
        .collect();

    for &n in &[10_000usize, 100_000, 1_000_000] {
        let rewards: Vec<Reward> = (0..n)
            .map(|_| Reward {
                pubkey: Pubkey::new_unique().to_string(),
                lamports: 1,
                post_balance: 1,
                reward_type: Some(RewardType::Voting),
                commission: None,
                commission_bps: None,
            })
            .collect();

        let start = Instant::now();
        let _: Vec<_> = RpcSolImpl::filter_map_rewards(
            Some(rewards),
            0,
            &addresses,
            &|reward_type| reward_type == RewardType::Voting,
        )
        .collect();
        let elapsed = start.elapsed();
        println!("n={n}: {:?}", elapsed);
        // Assert wall-clock grows roughly linearly with n * addresses.len(),
        // and exceeds an acceptable bound (e.g. > 50ms) for large n,
        // demonstrating unbounded per-request cost.
    }
}
```
Expected result: elapsed time scales with `n * addresses.len()` (quadratic-ish with respect to both inputs combined), confirming unbounded per-request CPU growth. After replacing `addresses.contains(&reward.pubkey)` with a `HashSet::contains`, re-run the same benchmark and assert elapsed time scales linearly with `n` only, independent of `addresses.len()`.
