### Title
Stale per-epoch instant-withdraw receipt basis is reused after claim, inflating default recovery basis and freezing claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` burns the aggregate receipt balance `instantWithdrawsRequests[_user]` and pays it out, but never clears the per-epoch accounting entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` that were written by `requestInstantWithdraw`. These stale entries are the analog of a use-after-free: memory that should have been released on claim is later re-read by `defaultPendingClaimBasis()` and `_claimDefaultedInstantWithdrawRequest()` when a default is finalized in the same epoch, double-counting an already-paid receipt.

### Finding Description
In `IdleCreditVault.sol`:

- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (lines 366-374).
- `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]` and zeroes only that aggregate mapping (lines 387-392). The per-epoch entries are never decremented on a normal funded claim — they are only cleared inside `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which runs solely after default finalization.
- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0` (lines 644-649).
- After finalization, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and calls `_burn(_user, claimBasis)` (lines 844-854).

Attack sequence (unprivileged KYC-passing lender, fixed-APR mode with instant withdrawals enabled, epoch running/stopped with borrower repaying less than owed → `defaulted`):

1. Epoch E buffer: attacker requests instant withdraw of amount X (e.g., via `requestWithdraw` when APR dropped). `instantWithdrawsRequestsByEpoch[attacker][E] = X`, `instantWithdrawClaimsByEpoch[E] = X`.
2. At `startEpoch`, CDO funds the instant queue (`collectInstantWithdrawFunds`); attacker calls `claimInstantWithdrawRequest`, is paid X in full, and X receipt tokens are burned. The per-epoch entries remain = X.
3. Attacker (or any user) makes a second small instant request `ε` in the same epoch E, keeping `pendingInstantWithdraws != 0` and `instantWithdrawsRequestsByEpoch[attacker][E] = X + ε`.
4. Borrower repays less than owed; `stopEpoch` marks `defaulted`, manager calls `finalizeDefault`. `defaultPendingClaimBasis()` counts `instantWithdrawClaimsByEpoch[E] = X + ε` although X was already paid — `defaultRecoveryPrice = reserveAmount / totalBasis` is diluted downward, so every honest pending/active claimant is underpaid, and the unspent `defaultRecoveryReserve` remainder is locked in the strategy forever (nothing else spends it).
5. When the attacker calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = X + ε` and tries `_burn(attacker, X + ε)` while the attacker only holds `ε` receipt tokens → revert → the second legitimate claim is permanently frozen; the same underflow/`instantWithdrawsRequests[_user] -= claimBasis` revert blocks all honest users whose epoch-E entries include already-claimed amounts.

### Impact Explanation
Two broken invariants: (a) one receipt one payout — an already-claimed receipt is counted again in the default recovery basis, diluting `defaultRecoveryPrice` for all defaulted-epoch claimants and permanently locking the excess `defaultRecoveryReserve`; (b) solvency/liveness — `_claimDefaultedInstantWithdrawRequest` burns more receipt tokens than users hold, so any user who claimed an instant withdrawal and re-requested in the same epoch has their surviving claim permanently frozen (DoS with direct fund impact, since recovered funds can never be distributed correctly). Loss is proportional to the double-counted amount X: with X large relative to the epoch basis, recovery price can be driven arbitrarily low.

### Likelihood Explanation
Requires instant-withdraw mode enabled (`allowInstantWithdraw`, APR-drop-triggered requests), an attacker able to claim a funded instant receipt and re-request within one epoch, and a subsequent borrower default in that epoch. Defaults are a designed-for state (`finalizeDefaultRecovery`, `defaultRecoveryPrice`), instant withdrawals are a designed-for flow, and nothing prevents a same-epoch re-request after claim. All attacker steps are unprivileged user actions; the manager/owner calls are honest sequencing.

### Recommendation
Mirror the normal-receipt pattern: when paying a funded instant claim in `claimInstantWithdrawRequest`, also clear `instantWithdrawsRequestsByEpoch[_user][epoch]` for the request epoch(s) and decrement `instantWithdrawClaimsByEpoch[epoch]` (and/or track the request epoch per user as done with `lastWithdrawRequest`), so a paid receipt cannot re-enter `defaultPendingClaimBasis` or `_claimDefaultedInstantWithdrawRequest` accounting.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: deposit as `attacker` (KYC'd), APR high
// 1. drop APR so requestWithdraw routes to requestInstantWithdraw
vm.prank(manager); strategy.setApr(0); // or via setAprsWithBuffer below lastEpochApr - delta
vm.prank(attacker); cdoEpoch.requestWithdraw(X, AAtranche);
// 2. startEpoch funds instant queue; attacker claims X
_startEpochAndCheckPrices(0);
vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest(); // paid X
// 3. same epoch: attacker requests epsilon again
vm.prank(attacker); cdoEpoch.requestWithdraw(eps, AAtranche);
// 4. borrower underpays -> default, finalizeDefault with recovered < basis
_stopEpochAndCheckPrices(0, apr, 0); _checkDefault();
finalizeDefault(recovered, manager);
// assert: defaultRecoveryPrice lowered by stale X in basis
// assert: attacker claimInstantWithdrawRequest reverts on _burn(X + eps)
// assert: honest claimants receive less than claimBasis * par expectation; reserve dust locked
```

Uncertainty note: the exact epoch index used by `defaultPendingClaimBasis`/`defaultRecoveryEpoch` relative to when `epochNumber` is incremented in `deposit()` (lines 607-614) should be confirmed in the PoC — the stale entries must coincide with `defaultRecoveryEpoch`, which holds for requests recorded under the epoch that defaults (the common buffer/request path shown above).
