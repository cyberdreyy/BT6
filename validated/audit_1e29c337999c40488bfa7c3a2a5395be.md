## Finding

### Title
Stale rejection weight is never retracted when a signer flips a Rejected vote to Accepted, causing a signer's weight to be double-counted on both sides of the tally - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` (node-side signer coordinator component) tracks per-block signer responses in a `BlockStatus` struct with two separate guards: `responded_signers: HashSet<u32>` and `gathered_signatures: BTreeMap<u32, MessageSignature>`. The `Accepted` handler gates weight-addition on `gathered_signatures`, while the `Rejected` handler gates weight-addition on `responded_signers`. Because these are two different sets, a signer that first rejects a block and later legitimately changes its mind and accepts it has its weight added to `total_weight_approved` **without** the earlier contribution to `total_weight_rejected` ever being removed. [1](#0-0) 

### Finding Description
In the `Accepted` branch, the weight-add guard is:
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [2](#0-1) 

In the `Rejected` branch, the weight-add guard is instead:
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [3](#0-2) 

Sequence that breaks the invariant "each signer's weight counts toward exactly one side of the tally at a time":
1. Signer S sends `Rejected` for block X. `responded_signers.insert(slot_id)` is `true` (first insertion) → `total_weight_rejected += S.weight`.
2. S later reconsiders and sends `Accepted` for the same block X — this is an explicitly sanctioned scenario per the project's own design docs, which state "a rejection is a revocable opinion" (`docs/signer-flows.md`, section 6/5) — the signer-side state machine allows re-evaluating a stale/locally-rejected block and later signing it.
3. The `Accepted` handler checks `gathered_signatures.contains_key(&slot_id)`, which is still empty for S (only `responded_signers` was touched on the reject path). The guard is `true`, so `total_weight_approved += S.weight`.
4. `responded_signers.insert(slot_id)` in the accept path (line 465) is a no-op (already present from step 1) and its return value is unused, so nothing corrects `total_weight_rejected`.

Result: S's weight is now counted in *both* `total_weight_approved` and `total_weight_rejected` simultaneously, permanently — there is no code path that decrements `total_weight_rejected` when a signer's vote is superseded.

### Impact Explanation
`total_weight_rejected` feeds the miner-side coordinator's decision to abandon a block as globally rejected:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { ... });
}
``` [4](#0-3) 

Because the stale rejection weight from a signer who has since flipped to acceptance is never removed, `total_weight_rejected` can retain "phantom" weight indefinitely. Combined with real, live rejections from other signers, this phantom weight can push the tally over the blocking-minority threshold (`total_weight - weight_threshold`) even though the actual live rejecting weight is lower — causing the miner to prematurely treat an otherwise-signable block as globally rejected (`SignersRejected`), and to permanently/temporarily exclude transactions (`permanently_excluded_txids`/`temporarily_excluded_txids`) based on inflated weight tallies. This is a liveness wedge on the mining/signing pipeline: a block that the live signer set would actually approve can be dropped by the coordinator due to miscounted (double-counted) weight, matching the accepted impact class "a rejection recounted as acceptance" / "a signer wedged into never signing valid blocks" (here: the coordinator wedged into never accepting an otherwise-valid block).

### Likelihood Explanation
This requires only a single one-slot signer (no majority) to send a `Rejected` message followed later by an `Accepted` message for the same `signer_signature_hash` — a normal, explicitly-supported re-evaluation flow (the signer-side state machine legitimately transitions `LocallyRejected -> LocallyAccepted` on re-evaluation, per `docs/signer-flows.md` section 2's state diagram: `LocallyRejected --> LocallyAccepted : re-evaluated`). No malicious behavior, majority collusion, or key compromise is needed — it can happen from ordinary network reordering/latency (a stale rejection delivered after the signer has already reconsidered) or from the signer's own legitimate reject→accept transition documented in the codebase.

### Recommendation
Track approval and rejection state per-slot in a single reconciled structure (e.g. one `HashMap<u32, Vote>` instead of two independently-guarded sets), and when a signer's vote changes from Rejected to Accepted (or vice versa), subtract the previously-counted weight from the old bucket before adding it to the new one. Alternatively, gate both branches on the same `responded_signers`-style "first vote wins" semantics *and* explicitly recompute both `total_weight_approved`/`total_weight_rejected` from a per-signer vote map each time, rather than incrementally mutating two independently-guarded running totals.

### Proof of Concept
1. Start a reward cycle with N signers, weight_threshold set to 70%.
2. Miner proposes block X.
3. Signer S (weight w) sends `BlockResponse::Rejected` for X — `total_weight_rejected += w` via `responded_signers.insert`.
4. S re-evaluates (e.g. due to a state re-check that flips its verdict, or reprocessing) and sends `BlockResponse::Accepted` for the same X — `total_weight_approved += w` via the separate `gathered_signatures` guard, while `total_weight_rejected` still retains `w` from step 3.
5. With additional real rejections from other signers whose combined weight plus S's stale `w` exceeds `total_weight - weight_threshold`, `get_block_status` in `stacks-node/src/nakamoto_node/signer_coordinator.rs` returns `NakamotoNodeError::SignersRejected` even though the live (non-stale) rejecting weight is below the blocking-minority threshold.
