### Title
pprof debug endpoints reachable by any authenticated view-role user without role check - ([File: core/web/router.go])

### Summary
`metricRoutes(authv2)` is called inside `v2Routes` and mounts `/v2/debug/pprof/*` on the `authv2` router group, which is protected only by `auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)` with no additional role wrapper. Every other sensitive admin-only handler in the same group is explicitly wrapped with `auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole`, but the pprof routes are registered with no such wrapper, so any successfully authenticated user — including the lowest-privilege `UserRoleView` — can invoke full pprof handlers.

### Finding Description
In `core/web/router.go`, `v2Routes` builds `authv2` as `r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession))` [1](#0-0) . This `Authenticate` middleware only verifies that the request has a valid session or API token; it does not check `user.Role` at all — see `Authenticate` in `core/web/auth/auth.go`, which simply loops through the auth methods and calls `c.Next()` once one succeeds, with no role assertion [2](#0-1) .

At the end of the `authv2` block, `metricRoutes(authv2)` is invoked directly, with the comment "Debug routes accessible via authentication" [3](#0-2) . Inside `metricRoutes`, all pprof endpoints (`/`, `/cmdline`, `/profile`, `/symbol`, `/trace`, `/allocs`, `/block`, `/goroutine`, `/heap`, `/mutex`, `/threadcreate`) are registered with no role-check wrapper — contrast this with every neighboring route in the same function (`/users`, `/keys/*`, `/jobs`, `/transfers`, etc.), which are wrapped in `auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole` [4](#0-3) .

The role-check functions (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`) demonstrate the codebase's intended layered authorization model: `UserRoleView` is explicitly the minimum/lowest role and is denied even "run" privilege actions [5](#0-4) . Since pprof handlers (`pprof.Profile`, `pprof.Trace`, heap/goroutine dumps) expose raw process memory, goroutine stacks, and CPU/heap profiles — which can contain key material, secrets in memory, or internal state — omitting any role gate here breaks the codebase's own authorization intent (`AUTHORIZATION_EXACTNESS`): a `view`-role authenticated user (or even a `run`-role token holder) can request `GET /v2/debug/pprof/heap` and receive `200 OK` with a full heap dump, when the equivalent sensitivity level of other endpoints in this file requires `admin`.

### Impact Explanation
This maps to Chainlink's "sensitive information disclosure" impact class: a low-privilege authenticated user (view role) can extract full memory/heap dumps (`/v2/debug/pprof/heap`), goroutine stacks (`/v2/debug/pprof/goroutine`), CPU/execution traces (`/v2/debug/pprof/trace`), and profiling data — data conventionally treated as admin-only due to the risk that process memory may contain private keys, session tokens, API secrets, or database credentials resident in Go's heap. This is a real authorization gap distinguishing this node's own role model (view < run < edit < admin) from what is enforced on this route group.

### Likelihood Explanation
Exploitation requires only a valid `view`-role session or API token — the lowest privilege level the system issues to any authenticated user. No admin credentials, social engineering, or additional exploitation chain is needed; a single unauthenticated-to-view-role login followed by one HTTP GET is sufficient and fully repeatable.

### Recommendation
Wrap the `metricRoutes` registrations (or the `pprofGroup` itself) with `auth.RequiresAdminRole`, consistent with the sensitivity of the other admin-gated endpoints in `v2Routes`, e.g.:
```go
pprofGroup.GET("/heap", auth.RequiresAdminRole(ginHandlerFromHTTP(pprof.Handler("heap").ServeHTTP)))
```
or apply `auth.RequiresAdminRole` as group-level middleware to `pprofGroup`.

### Proof of Concept
Extend the existing role-based route table test (referenced as `routesRolesMap` in the router test suite) with an entry for `/v2/debug/pprof/heap` (and ideally `/v2/debug/pprof/profile`, `/trace`, `/goroutine`) expecting `admin` role requirement:
1. Set up a test server via `NewRouter` with a view-role authenticated session/token, per existing router test helpers.
2. `GET /v2/debug/pprof/heap` with the view-role session cookie/token.
3. Assert response status is `http.StatusForbidden` (matching behavior of other admin-only routes like `/v2/keys/eth/:keyID` DELETE).
4. Currently, the actual observed result will be `http.StatusOK` with pprof heap dump content, demonstrating the missing role check.

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
