### Title
Claimed instant-withdraw receipts leave stale `instantWithdrawClaimsByEpoch` basis that is double-counted as recovery reserve at default finalization - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Jetty analog (per-request state that is allocated but never released, eventually exhausting a shared resource) maps to `IdleCreditVault`'s instant-withdraw receipt accounting. `requestInstantWithdraw` records per-epoch claim basis in `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`, but the normal claim path `claimInstantWithdrawRequest` only clears the aggregate `instantWithdrawsRequests[_user]` — the per-epoch basis is never released. When a borrower default is later finalized in the same epoch, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` treat that stale basis as still-outstanding and treat already-paid-out cash as still-held reserve, inflating `defaultRecoveryPrice` and leaving the recovery reserve insolvent for later claimants.

### Finding Description
- `requestInstantWithdraw` increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` [1](#0-0) .
- `claimInstantWithdrawRequest` burns the user's receipt, zeroes only `instantWithdrawsRequests[_user]`, and pays out underlying via `_transferFundedClaim`. It never decrements `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch` [2](#0-1) .
- `collectInstantWithdrawFunds` reduces `pendingInstantWithdraws` by the amount actually pulled from the CDO, so when funding was partial (`pendingInstant < instantWithdrawClaimsByEpoch[epoch]`) the remainder stays non-zero [3](#0-2) .
- At default finalization, `defaultPendingClaimBasis` adds the *entire* `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, including receipts whose holders already claimed and were paid [4](#0-3) .
- `_defaultPrefundedInstantReserve` then credits `instantBasis - pendingInstant` as underlying already sitting in the strategy, even though part of it was transferred out to claimants [5](#0-4) . This overstated `reserveAmount` flows directly into `recoveryPrice` in `finalizeDefaultRecovery` [6](#0-5) .
- `_claimDefaultedInstantWithdrawRequest` pays `claimBasis * defaultRecoveryPrice` against a per-epoch entry that may belong to an already-paid receipt [7](#0-6) .

### Impact Explanation
The recovery price is computed as `reserveAmount / totalBasis` where both terms are inflated by phantom (already-claimed) instant receipts. Two failure modes result, both with direct fund impact:

1. **Dilution/insolvency:** `reserveAmount` includes `prefundedReserve` cash that was already paid out and no longer sits in the strategy. `defaultRecoveryPrice` is therefore set against funds that do not exist; the aggregate of all haircut claims exceeds the real reserve balance, so the last claimants (normal withdraw receipts via `_claimDefaultedWithdrawRequest`, instant receipts, or post-default requests drawing on `defaultRecoveryReserve`) revert on transfer or receive nothing — permanent loss of their recovery share.
2. **Double payment path:** an attacker who claimed a funded instant receipt still has `instantWithdrawsRequestsByEpoch[attacker][defaultEpoch] != 0`. Their `_claimDefaultedInstantWithdrawRequest` call attempts `instantWithdrawsRequests[_user] -= claimBasis`, which reverts (underflow) since the aggregate was cleared — blocking only their own call — but the stale basis already damaged the global recovery price for everyone else regardless.

### Likelihood Explanation
Requires a specific but ordinary sequence: instant withdrawals triggered in a buffer (APR drop ≥ `instantWithdrawAprDelta`, which is a normal market event), `startEpoch` funding the instant queue only partially or fully while some receipts remain claimable, at least one user claiming during the running epoch, then a borrower repayment failure at `stopEpoch` triggering `_handleBorrowerDefault` and later `finalizeDefault`. None of these require privileged misbehavior — the borrower default is an external credit event, and claiming a funded receipt is a legitimate user action. The stale-basis cleanup gap exists unconditionally in the claim path.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch basis for the epoch the receipt belongs to (track request epoch for instant receipts analogous to `lastWithdrawRequest`, or decrement `instantWithdrawsRequestsByEpoch[_user][e]` and `instantWithdrawClaimsByEpoch[e]` by the claimed amount). Alternatively, make `_defaultPrefundedInstantReserve` and `defaultPendingClaimBasis` derive the still-outstanding basis from unclaimed receipt balances (e.g., strategy-token receipt balances) rather than the cumulative per-epoch counter, so that already-paid claims cannot be counted as both outstanding basis and held reserve.

### Proof of Concept
Foundry fork outline (setup mirrors `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. Deposit AA, warp past buffer, drive APR down to trigger instant mode.
idleCDO.depositAA(10_000 * ONE_SCALE);
// owner/manager: strategy.setAprs(lowApr) so lastEpochApr > currentApr + delta

// 2. Attacker requests instant withdraw during buffer.
cdoEpoch.requestWithdraw(0, address(AAtranche)); // routes to requestInstantWithdraw
uint256 instantAmt = strategy.instantWithdrawsRequests(attacker);

// 3. Manager starts epoch; CDO cash covers instant queue only partially
//    (arrange pendingInstant > totUnderlyings, or fully funded then claim after
//    allowInstantWithdraw is set). collectInstantWithdrawFunds leaves
//    pendingInstantWithdraws > 0 for the unfunded remainder.
vm.prank(manager); cdoEpoch.startEpoch();

// 4. Warp past instantWithdrawDeadline; attacker claims funded portion.
vm.warp(cdoEpoch.instantWithdrawDeadline() + 1);
cdoEpoch.claimInstantWithdrawRequest();
// instantWithdrawsRequests[attacker] == 0 but
// instantWithdrawsRequestsByEpoch[attacker][epochNumber] == instantAmt  // STALE

// 5. Borrower fails to repay at stopEpoch -> _handleBorrowerDefault.
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager); cdoEpoch.stopEpoch(0, 0);
assertTrue(cdoEpoch.defaulted());

// 6. finalizeDefaultRecovery counts the stale basis twice:
//    pendingBasis includes instantWithdrawClaimsByEpoch[epoch] (incl. attacker's
//    already-paid amount) and prefundedReserve credits cash already paid out.
uint256 reserveBefore = underlying.balanceOf(address(strategy));
cdoEpoch.finalizeDefault(recoveredAmount, recoverySource);

// 7. Show insolvency: sum of all pending haircut claims at defaultRecoveryPrice
//    exceeds the real strategy balance; a later legitimate claimant's
//    claimWithdrawRequest() reverts / underpays.
vm.prank(victim); cdoEpoch.claimWithdrawRequest(); // underpaid or reverts
```

Uncertainty note: the exact severity depends on `_transferFundedClaim`'s reserve handling (lines ~897-915, not fully read) — if it debits `defaultRecoveryReserve` when non-zero the accounting divergence shifts but the stale `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` entries remain uncleared either way, which is the core leak. The PoC should assert both the inflated `defaultRecoveryPrice` and the final reserve shortfall to confirm quantified loss.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

    _onlyIdleCDO();

      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
