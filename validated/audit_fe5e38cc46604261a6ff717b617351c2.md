### Title
Unfunded instant-withdraw requests block already-funded instant-withdraw claims of other users - (contracts/IdleCDOEpochVariant.sol + contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report describes a withdrawal limit tied to a shrinking aggregate (`totalPoolSize`): later withdrawals are blocked even though funds remain, because the limit is recomputed globally instead of being fixed per-request. The analog in idle-tranches is the instant-withdraw path. Each user's payout amount is fixed at request time (`instantWithdrawsRequests[_user]` in `IdleCreditVault`), and funds for it are delivered to the strategy via `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`. However, `claimInstantWithdrawRequest` is gated by the *global* `pendingInstantWithdraws` counter / `allowInstantWithdraw` flag rather than by whether that user's receipt was funded. A new, unfunded instant request from any KYC'd tranche holder pushes `pendingInstantWithdraws` above zero and reverts claims of users whose receipts are already fully funded and sitting in the strategy.

### Finding Description
- `IdleCDOEpochVariant.requestWithdraw` routes to `IdleCreditVault.requestInstantWithdraw` when the epoch APR dropped below `lastEpochApr - instantWithdrawAprDelta`, recording a fixed per-user receipt (`instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`) and bumping the aggregate `pendingInstantWithdraws` (IdleCreditVault.sol:356-375).
- After `instantWithdrawDeadline`, manager calls `getInstantWithdrawFunds`, which pulls `_pendingInstant()` from the borrower and calls `collectInstantWithdrawFunds`, decrementing `pendingInstantWithdraws` and setting `allowInstantWithdraw = true` (IdleCDOEpochVariant.sol:558-574).
- Claims pay `instantWithdrawsRequests[_user]` at par from strategy-held underlyings via `_transferFundedClaim` (IdleCreditVault.sol:380-393), but the CDO-side claim reverts with `NotAllowed` while any newer request remains unfunded — confirmed by the protocol's own test: after epoch-1 instant requests are funded, a new epoch-2 request makes `claimInstantWithdrawRequest` revert until the manager funds it again (`test/foundry/IdleCreditVault.t.sol` ~4854-4892, "if we claim right away it reverts as there are pending instant not fulfilled").

So the claimable amount/limit for an already-funded claimant shrinks to zero purely because aggregate pending instant withdrawals grew — the same "limit recomputed from a mutable pool-wide quantity at withdrawal time" bug class.

### Impact Explanation
Temporary freezing of funds. An unprivileged attacker who passes `isWalletAllowed` (any KYC'd lender holding tranche tokens) can, once `instantWithdraw` mode is active (APR decreased across an epoch boundary), submit a small instant-withdraw request each epoch. Every other user's already-funded instant receipts become unclaimable until the honest manager calls `getInstantWithdrawFunds` again after the next `instantWithdrawDeadline`, and the borrower actually returns liquidity. Repeating the request each epoch keeps `pendingInstantWithdraws > 0` and extends the freeze indefinitely at the cost of locking only the attacker's own request amount. All funded claimants' underlyings are already isolated in the strategy, so the block is purely accounting/gating, not solvency.

### Likelihood Explanation
Requires instant-withdraw mode to be enabled (epoch APR decrease beyond `instantWithdrawAprDelta`), an `instantWithdrawDeadline`/`instantWithdrawDelay` window each epoch, and an attacker holding any tranche balance and passing the Keyring wallet check. All are reachable by an ordinary KYC-passing lender without privileged help. Severity is bounded to temporary freezing (no theft), since funding eventually unblocks claims, matching the "inconsistent withdrawal behavior throughout the period" impact of the reference report.

### Recommendation
Track funded vs. unfunded instant claims separately instead of gating all claims on the global `pendingInstantWithdraws`. For example, record `fundedInstantWithdraws`/`claimableInstantByEpoch` when `collectInstantWithdrawFunds` runs, and let `claimInstantWithdrawRequest` pay a user up to the funded portion of their receipt (or maintain a per-epoch `instantFundedAmount` price like `epochWithdrawPrice`/`lossRecoveryPriceByEpoch`) so claims settle against the snapshotted funded amount rather than the live aggregate counter.

### Proof of Concept
Reproducible in the existing fork suite `test/foundry/IdleCreditVault.t.sol`:

```solidity
// reuse setUp from IdleCreditVault.t.sol
uint256 amount = 10000 * ONE_SCALE;
idleCDO.depositAA(amount);            // victim
// attacker deposits a small amount on BB
_depositWithUser(attacker, ONE_SCALE, true);

_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch()); // APR drop -> instant mode
uint256 requestedAA = cdoEpoch.requestWithdraw(0, address(AAtranche)); // victim instant request

_startEpochAndCheckPrices(1);
vm.warp(block.timestamp + cdoEpoch.instantWithdrawDeadline() + 1);
_getInstantFunds();                   // victim's receipt is now fully funded in strategy

_stopEpochAndCheckPrices(1, initialProvidedApr / 4, _expectedFundsEndEpoch());

// attacker (unprivileged, KYC'd tranche holder) files a new instant request
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(BBtranche));

_startEpochAndCheckPrices(2);
// victim's already-funded claim now reverts because aggregate pendingInstantWithdraws > 0
vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
cdoEpoch.claimInstantWithdrawRequest();
// freeze persists until manager funds attacker's request after next instantWithdrawDeadline
```

This is exactly the sequence already asserted in `testClaimInstantWithdrawRequestAfterAnEpochWithInstantWithdraw`, reinterpreted with the second requester being an independent attacker account rather than the same user.
