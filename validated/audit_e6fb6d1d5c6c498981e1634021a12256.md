### Title
Post-default instant withdraw requests are recorded in the defaulted epoch bucket and processed as defaulted receipts, corrupting `instantWithdrawClaimsByEpoch` and freezing user funds — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The ext4 bug class is a stale-state read: a state flag (`EXT4_STATE_MAY_INLINE_DATA`) was cleared by a prior transition, but the underlying data was still interpreted under the old semantics, so the kernel read freed memory. The vault analog is `requestInstantWithdraw`: after `finalizeDefault`/`defaultInstantWithdrawsFinalized`, the "defaulted epoch" lifecycle is logically over, but the function still writes every new instant request into `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `epochNumber` remains equal to `defaultRecoveryEpoch` forever after default (no further `stopEpoch` can run on a defaulted pool). The new, already-haircut post-default receipt is therefore stored in — and later read back from — the terminated default-epoch bucket, exactly like reading stale `i_data` after the inline flag was cleared.

### Finding Description
- `requestInstantWithdraw` (IdleCreditVault.sol:356-375) unconditionally records `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount` and `instantWithdrawClaimsByEpoch[epochNumber] += _amount`. Unlike `requestWithdraw` (lines 247-257), which routes post-default requests into the isolated `postDefaultRequests` bucket, the instant path has no post-default branch — no `defaultRecoveryFinalized` check at all.
- `claimInstantWithdrawRequest` (lines 380-393) first calls `_claimDefaultedInstantWithdrawRequest` whenever `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. That function (lines 842-856) reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and assumes anything found there is a pre-default receipt.
- Since `epochNumber` is only bumped by `stopEpoch` and the pool is defaulted, any post-default instant request lands in `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`. On claim it is treated as a defaulted receipt: the user is paid `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` — a second haircut on an amount the CDO already haircut via the lowered `virtualPrice` (double-haircut loss).
- Worse, `_claimDefaultedInstantWithdrawRequest` decrements `instantWithdrawClaimsByEpoch[defaultEpoch]` and `pendingInstantWithdraws` by `claimBasis` (lines 852-853). The defaulted epoch's claim counter was already fully consumed during default finalization, so this subtraction underflows and reverts under Solidity 0.8 checked arithmetic. The post-default receipt becomes permanently unclaimable — a permanent freeze of the user's funds, and the corrupted counters desynchronize `instantWithdrawsRequests[_user]`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws`, breaking the "one receipt one payout" and reserve-accounting invariants for subsequent claimants.
- No existing guard stops it: `_ensureDefaultRecoveryInitialized` is a no-op once initialized, `_onlyIdleCDO` passes because the CDO legitimately relays user instant-withdraw requests, and the `defaultRecoveryFinalized` branch present in `requestWithdraw` is simply absent here.

### Impact Explanation
Any KYC'd tranche holder (unprivileged attacker/victim — the CDO relays `requestInstantWithdraw` on their behalf) who requests an instant withdrawal after default finalization either (a) has the claim permanently revert due to underflow of the already-consumed `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]`, freezing their full receipt amount, or (b) is paid only `defaultRecoveryPrice`-scaled value, losing `1 - recoveryPrice` of an already-haircut claim. Loss: the full receipt amount in case (a); the recovery haircut in case (b). `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` corruption can additionally block or mis-fund other users' instant claims.

### Likelihood Explanation
Requires only that the borrower has defaulted and finalization has run (`defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`), then any user requesting an instant withdraw — a supported flow, since the code deliberately keeps post-default withdraw UX alive via `postDefaultRequests` for the normal path and the instant path is not gated off. Deterministic once the precondition holds.

### Recommendation
Mirror the normal-withdraw fix: in `requestInstantWithdraw`, when `defaultRecoveryFinalized` is true, do not write into `instantWithdrawsRequestsByEpoch[_user][epochNumber]`/`instantWithdrawClaimsByEpoch`; either revert, or record the receipt under a dedicated post-default key (e.g., `type(uint256).max` or a `postDefaultInstantRequests` bucket) and pay it 1:1 from funded liquidity in `claimInstantWithdrawRequest` without touching `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` or `pendingInstantWithdraws`. Add a regression test requesting an instant withdraw after `finalizeDefaultRecovery`.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol style PoC
function testPostDefaultInstantWithdrawRecordedInDefaultEpoch() external {
    // 1. deposit, run an epoch, force borrower default
    _depositWithUser(victim, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    deal(defaultUnderlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(cdoEpoch.owner());
    cdoEpoch.stopEpoch(0, 0); // default
    // 2. manager finalizes recovery (instant bucket too)
    vm.prank(manager);
    cdoEpoch.finalizeDefaultRecovery(recovered, manager); // sets defaultInstantWithdrawsFinalized
    assertEq(strategy.epochNumber(), strategy.defaultRecoveryEpoch()); // epoch frozen
    // 3. victim requests instant withdraw post-default (CDO relays)
    vm.prank(victim);
    cdoEpoch.requestInstantWithdraw(shares, tranche);
    // receipt lands in the terminated default-epoch bucket
    assertGt(strategy.instantWithdrawsRequestsByEpoch(victim, strategy.defaultRecoveryEpoch()), 0);
    // 4. claim: underflows instantWithdrawClaimsByEpoch[defaultEpoch] (already consumed)
    vm.prank(victim);
    vm.expectRevert(); // arithmetic underflow -> funds frozen
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Confidence note: the per-epoch-bucket misclassification is directly supported by the code read (lines 356-375, 380-393, 842-856); I did not fully re-verify that `epochNumber` cannot advance after finalization or the exact `finalizeDefaultRecovery` entry-point name within my tool budget, so the PoC harness calls may need minor adjustment to match the CDO's actual finalize/instant-request API.
