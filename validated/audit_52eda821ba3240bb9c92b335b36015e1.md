### Title
APR0 withdraw receipts requested in a prior epoch are permanently frozen after default finalization because `defaultRecoveryEpoch` classification does not match their `principalEpoch` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analogous to the Securitize `euRetailInvestorsCount` bug — where a counter is incremented under one investor classification and decremented under another — `IdleCreditVault` records an APR=0 withdraw request in the aggregate `pendingWithdraws` borrower-claim counter, but keys the per-user receipt to `apr0Users[user].principalEpoch` (the request epoch). When the epoch rolls over and a borrower default is later finalized, `defaultRecoveryEpoch` is set to the *current* `epochNumber`, so `_claimDefaultedWithdrawRequest` computes a zero claim basis for any APR0 receipt requested in an earlier epoch. The claim then falls through to `_claimFundedWithdrawRequest`, which reverts in `_transferFundedClaim` because the user's money was swept into `defaultRecoveryReserve`. The receipt can never be claimed.

### Finding Description
At request time (`requestWithdraw`, `contracts/strategies/idle/IdleCreditVault.sol:243-295`):

- `pendingWithdraws += _amount` unconditionally (open pool), line 279.
- If `unscaledApr == 0`, the user's basis goes into `apr0Users[user].principal` with `principalEpoch = epochNumber` (lines 285-286, `_requestWithdrawApr0` at 567-577); `withdrawsRequestsByEpoch` is **not** populated for that request.

When `stopEpoch` runs, `deposit()` bumps `epochNumber += 1` (line 610) and `prepareStopEpochWithApr0` stores `apr0RateByEpoch[epochNumber]` and zeroes `apr0TotalPrincipal` — but the user's `principalEpoch` remains the *old* epoch N.

If the borrower defaults in a later epoch and the CDO calls `finalizeDefaultRecovery`, `defaultRecoveryEpoch = epochNumber` (now ≥ N+1) and `defaultRecoveryReserve` is sized using `defaultPendingClaimBasis()` = the aggregate `pendingWithdraws`, which **includes** the stale APR0 receipt (lines 644-649, 686-693).

On `claimWithdrawRequest(_user)` (lines 301-314):

1. `_claimPostDefaultWithdrawRequest` → 0.
2. `_claimDefaultedWithdrawRequest` calls `_withdrawClaimAmountsForEpoch(_user, defaultRecoveryEpoch)`; `withdrawsRequestsByEpoch[user][N+1] == 0` and `apr0User.principalEpoch (N) != N+1`, so `claimBasis == 0` and it returns 0 — the user's reserve-backed claim is unreachable (lines 772-784, 862-881).
3. `_claimLossAdjustedWithdrawRequest` → 0 (no `lossRecoveryPriceByEpoch[N]` unless a stop-loss occurred).
4. `_claimFundedWithdrawRequest` passes the epoch gate (`epochNumber N+1 > lastWithdrawRequest N`), `_settleApr0` settles the principal/interest, and `_transferFundedClaim` reverts: `balance - defaultRecoveryReserve < amount` because the user's funds are inside the reserve (lines 326-349, 897-907).

The whole call reverts, so the user can never withdraw — and `requestWithdraw` post-default also reverts via `_hasWithdrawRequest` (lines 247-251). Same bug class as the report: value counted under one classification (aggregate `pendingWithdraws`/default-epoch basis), but the decrement/claim path classifies by a stale marker (`principalEpoch` vs `defaultRecoveryEpoch`), producing an inconsistent state and a reverting payout.

### Impact Explanation
Permanent freezing of funds for every APR0 withdraw requester whose request epoch precedes the default epoch. Their principal (and any settled APR0 interest) is counted in `defaultRecoveryReserve` at finalization yet can never be paid out: `_transferFundedClaim` reverts and `_claimDefaultedWithdrawRequest` returns 0. The reserve is also stranded — no other claimant can receive that portion, so it is permanently locked in the strategy. Loss equals the full unsettled APR0 principal + interest carried into the default epoch.

### Likelihood Explanation
Requires three honest, unprivileged/operational conditions: (1) a lender requests a withdraw while `unscaledApr == 0` (APR0 mode is a supported pool mode), (2) at least one `stopEpoch` runs so `epochNumber` advances past the request epoch while the APR0 receipt stays unsettled (settlement is lazy — only inside claim paths), and (3) a borrower default is finalized in a later epoch. No malicious privileged role is needed; the default itself is a normal protocol event, not attacker-caused. Existing guards do not prevent it: `_clearWithdrawClaimForEpoch`'s `apr0TotalPrincipal` floor (line 827) only protects the global counter, not the per-user epoch mismatch, and `_transferFundedClaim`'s reserve guard actively enforces the freeze.

### Recommendation
In `_claimDefaultedWithdrawRequest` / `_withdrawClaimAmountsForEpoch`, treat any outstanding APR0 `principal`/`settledPrincipal`/`settledInterest` as defaulted-epoch basis regardless of `principalEpoch` once `defaultRecoveryFinalized` (or check `principalEpoch <= defaultRecoveryEpoch`), mirroring how the aggregate `pendingWithdraws` already counts them. Alternatively, settle/lazily re-key APR0 receipts into `withdrawsRequestsByEpoch` at `prepareStopEpochWithApr0` so the default-epoch classification matches the aggregate basis.

### Proof of Concept
Foundry fork PoC (against an idle credit vault in APR0 mode):

```solidity
// Assume: vault strategy = IdleCreditVault, CDO = IdleCDOEpochVariant, unscaledApr == 0.
// user = KYC'd lender (unprivileged).

// --- Epoch N (running) ---
cdo.requestWithdraw(amount, AATranche);            // user requests; unscaledApr == 0
// IdleCreditVault.requestWithdraw: pendingWithdraws += amount;
// apr0Users[user].principal = amount; principalEpoch = N; apr0TotalPrincipal += amount;

// --- stopEpoch N -> epochNumber becomes N+1 ---
vm.prank(manager);
cdo.stopEpoch(newApr /* still 0 */, 0);
// deposit() -> epochNumber = N+1; prepareStopEpochWithApr0 zeroes apr0TotalPrincipal,
// sets apr0RateByEpoch[N]. apr0Users[user].principalEpoch is still N. User does NOT claim.

// --- Epoch N+1: borrower defaults ---
// borrower fails to repay; guardian/owner flow calls _handleBorrowerDefault then:
cdo.finalizeDefaultRecovery(recovered, recoverySource);
// defaultRecoveryEpoch = N+1; defaultRecoveryReserve sized with pendingWithdraws
// which still includes user's `amount`.

// --- User tries to claim ---
vm.expectRevert(); // NotAllowed from _transferFundedClaim (balance - reserve < amount)
cdo.claimWithdrawRequest();                        // routes to vault.claimWithdrawRequest(user)

// Also blocked from re-requesting:
vm.expectRevert();
cdo.requestWithdraw(1, AATranche);                 // _hasWithdrawRequest(user) == true
```

The invariant broken is "one receipt, one payout": the user's strategy-token receipt was funded into the recovery reserve but no claim path can release it.

Caveat: I verified the claim routing and counter logic in `IdleCreditVault.sol` directly, but did not trace every CDO-side call (`_handleBorrowerDefault` gating, exact `epochNumber` bump site beyond `deposit()` at line 610); the epoch-number rollover is confirmed by the `isEpochRunning()` branch at `IdleCreditVault.sol:607-610` and `_settleApr0`'s `_reqEpoch >= epochNumber` check at line 553.
