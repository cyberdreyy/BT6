### Title
Signer rejection under-counting via stale `signer_addr`-only primary key in `block_rejection_signer_addrs` - ([File: stacks-signer/src/signerdb.rs])

### Summary
`SignerDb::add_block_rejection_signer_addr` records a signer's rejection vote for a specific block (`signer_signature_hash`) in the `block_rejection_signer_addrs` table, but the table's primary key is `signer_addr` alone rather than `(signer_addr, signer_signature_hash)`. Once a signer address has a row for one block hash, any later attempt to record a rejection for a *different* block hash from that same address hits a duplicate-key error on plain `INSERT`, and the vote is silently dropped by the caller. This mirrors the GMX report's root cause: a value fixed at an earlier point (the depositor/refundee — here, the first-rejected block hash tied to a signer address) is carried forward and used unmodified in a later, unrelated operation (a subsequent rejection for a different block), causing that later operation to permanently fail.

### Finding Description
The current table definition is: [1](#0-0) 

Note `PRIMARY KEY (signer_addr)` — it does not include `signer_signature_hash`.

`add_block_rejection_signer_addr` looks up any *existing* row scoped to the given `(block_sighash, addr)` pair: [2](#0-1) 

If the signer already has a row for a *different* sighash (because it earlier rejected a different block), this lookup returns `None` (it's scoped by the *current* `block_sighash`), so the code falls into the `None` branch and issues a plain `INSERT`: [3](#0-2) 

Because the table's actual primary key is `signer_addr` only, this `INSERT` collides with the pre-existing row (from the earlier, different block) and returns a SQLite constraint-violation error. This error propagates via `?` out of `add_block_rejection_signer_addr`, and callers treat DB errors as a soft failure — they log a warning and stop processing that particular rejection instead of counting it: [4](#0-3) 

From that point forward, *every* rejection this signer address records for *any subsequent block* will hit the same constraint violation (the stale row for the first block never gets replaced), so the signer's rejection is permanently excluded from `get_block_rejection_signer_addrs`: [5](#0-4) 

This breaks the equality between "verified rejections a signer actually issued" and "aggregated rejection weight counted toward the global-rejection threshold" computed here: [6](#0-5) 

### Impact Explanation
A single miner slot can trivially cause a signer to reject two different block proposals with different `signer_signature_hash` values (e.g., propose an invalid/late block, get it rejected, then propose a second distinct invalid block at a different height/consensus hash). After the second rejection, that signer's vote is silently and permanently dropped from the rejection tally for all future blocks. This under-counts `total_reject_weight` for every subsequent proposal review, which can delay or prevent the network from reaching the "global rejection" threshold on genuinely invalid/conflicting proposals — a liveness wedge affecting the block-rejection consensus mechanism, and it breaks the aggregated-weight-vs-verified-rejections equality without requiring a majority of signers or any privileged access.

### Likelihood Explanation
High reachability: any miner (single slot) can produce two distinct rejected proposals in the ordinary course of operation (this can also happen organically from forks/re-proposals, not just adversarially), and the SQL primary-key/no-`ON CONFLICT` mismatch is a deterministic code defect, not a probabilistic race.

### Recommendation
Change the primary key of `block_rejection_signer_addrs` to `(signer_addr, signer_signature_hash)` (with an appropriate migration), and/or replace the plain `INSERT` in `add_block_rejection_signer_addr`'s `None` branch with an `INSERT OR REPLACE`/`ON CONFLICT` that is scoped correctly per-block, so that a signer's rejection is tracked independently per block hash instead of being globally singleton per address.

### Proof of Concept
1. Signer `S` receives block proposal `A` (sighash `H_A`) and rejects it → `add_block_rejection_signer_addr(H_A, S, reason)` inserts a row `(H_A, S)` successfully.
2. Miner proposes a different, unrelated block `B` (sighash `H_B`, different height/tenure). Signer `S` rejects `B` → `add_block_rejection_signer_addr(H_B, S, reason)` queries for `(H_B, S)`, finds nothing, attempts `INSERT INTO block_rejection_signer_addrs (H_B, S, ...)`, which fails with a `UNIQUE`/primary-key constraint violation on `signer_addr = S` since row `(H_A, S)` already occupies that key.
3. The error propagates to `handle_block_rejection`, which logs a warning and returns without counting `S`'s rejection of `B`.
4. For every subsequent block proposal `C, D, ...`, the same failure recurs for signer `S`, permanently excluding `S`'s rejection weight from `get_block_rejection_signer_addrs` and thus from the `total_reject_weight` threshold computation in `stacks-signer/src/v0/signer.rs`.

    /// Get all signer addresses that rejected the block (and their reject codes)
    pub fn get_block_rejection_signer_addrs(
        &self,
        block_sighash: &Sha512Trunc256Sum,
    ) -> Result<Vec<(StacksAddress, RejectReasonPrefix)>, DBError> {
        let qry =
            "SELECT signer_addr, reject_code FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1";
        let args = params![block_sighash];
        let mut stmt = self.db.prepare(qry)?;

        let rows = stmt.query_map(args, |row| {
            let addr: String = row.get(0)?;
            let addr = StacksAddress::from_string(&addr).ok_or(SqliteError::InvalidColumnType(
                0,
                "signer_addr".into(),
                rusqlite::types::Type::Text,
            ))?;
            let reject_code: i64 = row.get(1)?;

            let reject_code = u8::try_from(reject_code)
                .map_err(|_| {
                    SqliteError::InvalidColumnType(
                        1,
                        "reject_code".into(),
                        rusqlite::types::Type::Integer,
                    )
                })
                .map(RejectReasonPrefix::from)?;

            Ok((addr, reject_code))
        })?;

        rows.collect::<Result<Vec<_>, _>>().map_err(|e| e.into())
    }
