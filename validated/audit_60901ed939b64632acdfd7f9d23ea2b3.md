### Title
`staking_contract::set_beneficiary_for_operator` accepts an unvalidated beneficiary, permanently blocking staker withdrawals and commission distribution - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
This mirrors the `VaultBooster` class of bug: a function accepts a user-controlled input (an address) without validating that it is "supported" (i.e., able to receive the asset), so a subsequent shared operation permanently traps value belonging to unrelated, unprivileged parties.

### Finding Description
`staking_contract::distribute`/`distribute_internal` withdraws the pool's total withdrawable stake in one call and then loops over every shareholder in the shared `distribution_pool`, paying each one via `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient is not registered for the coin and has disabled direct coin transfers: [2](#0-1) 

The operator-controlled entry point `set_beneficiary_for_operator` in `delegation_pool.move` (and its `staking_contract` counterpart, referenced by `vesting.move` and listed in the module's own function inventory) stores `new_beneficiary` with **no check** that the address can actually receive APT: [3](#0-2) 

Contrast this with `vesting::set_beneficiary`, whose own comment explicitly states this exact hazard is why a registration check was added — because without it, `distribute()` fails for *everyone* once it hits an unpayable beneficiary: [4](#0-3) 

A search for `assert_account_is_registered_for_apt` across the repo shows it is only referenced in `vesting.move` and `delegation_pool.move`, and is absent from `staking_contract.move`, confirming `staking_contract::set_beneficiary_for_operator` lacks this guard even though `distribute()` in the very same file has the identical "loop over one shared distribution pool" hazard that motivated the check in `vesting.move`.

### Impact Explanation
Because `distribute()` withdraws stake for **all** shareholders in a single transaction and aborts entirely if any single recipient (the operator's beneficiary) cannot accept the deposit, an operator can set a beneficiary address that has called `aptos_account::set_allow_direct_coin_transfers(false)` (or is otherwise unable to receive). Every subsequent call to `distribute()` (and the implicit `distribute_internal()` calls inside `request_commission`/`unlock_stake`) will then permanently revert, since the poisoned beneficiary entry is always redeemed as part of the same shared `distribution_pool`. This strands the staker's already-unlocked, otherwise-withdrawable stake — funds belonging to an unprivileged staker who did nothing wrong — with no recovery path from within the module, matching the "permanent lock / non-recoverable loss of claim rights in stake ... flows" and "operator commission ... payout ... traps value" impact categories.

### Likelihood Explanation
The operator role is untrusted-by-design relative to the staker in `staking_contract` (this is precisely why `beneficiary_for_operator`/commission separation exists). Triggering the condition requires only: (1) the operator calling `set_beneficiary_for_operator` with an address under their control, and (2) that address calling `aptos_account::set_allow_direct_coin_transfers(false)` (a normal, permissionless action). No special privileges beyond the operator role — which the operator already legitimately holds — are needed to weaponize this against the staker's funds.

### Recommendation
Add the same guard used in `vesting::set_beneficiary` to `staking_contract::set_beneficiary_for_operator` (and its `delegation_pool` analog): call `aptos_account::assert_account_is_registered_for_apt(new_beneficiary)` (or an equivalent `can_receive_direct_coin_transfers` check) before accepting the new beneficiary. Additionally, consider hardening `distribute_internal` so that a single unpayable recipient cannot abort the whole distribution loop (e.g., skip/hold that recipient's share separately instead of reverting the entire transaction).

### Proof of Concept
Not independently executed in this session (index-only environment; no test runner available). Conceptual PoC:
1. Staker creates a staking contract with `operator` via `staking_contract::create_staking_contract`.
2. `operator` calls `aptos_account::set_allow_direct_coin_transfers(false)` from an address `B` they control.
3. `operator` calls `staking_contract::set_beneficiary_for_operator(operator, B)` — succeeds with no validation. [3](#0-2) 
4. Staker calls `unlock_stake` to withdraw part of their stake; lockup expires.
5. Any party calls `staking_contract::distribute` — it withdraws total inactive stake and iterates the shared `distribution_pool`; when it reaches beneficiary `B`, `aptos_account::deposit_coins` aborts because `B` disabled direct transfers. [1](#0-0) 
6. The entire `distribute()` transaction reverts every time it is called, permanently blocking the staker's payout until the operator's beneficiary re-enables transfers (a decision entirely outside the staker's control).

Note: I was unable to directly view the exact source text of `staking_contract::set_beneficiary_for_operator` in this session (grep did not match the exact string, likely due to line-wrapping/formatting), though its existence and behavior are corroborated by the module's function trace listing and by the absence of `assert_account_is_registered_for_apt` anywhere in `staking_contract.move`. A Devin session with full file access could confirm the exact function body before implementing the fix.

```text
    public entry fun set_beneficiary_for_operator(
        operator: &signer,
        new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
        } else {
            move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
        };

        emit(SetBeneficiaryForOperator {
            operator: operator_addr,
            old_beneficiary,
            new_beneficiary,
        });
    }
```
