### Title
Post-default claim pays older loss-adjusted withdraw receipts at par because `_claimDefaultedWithdrawRequest` wipes `lastWithdrawRequest` before the loss-adjusted path runs - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug pattern — acquiring a reference on a node whose ownership was already dropped (`refcount_inc` on a 0 refcount) — maps here to a claim path that pays out on a stale/over-strong basis after the epoch marker that guards it was cleared. When `defaultRecoveryFinalized` is true, `claimWithdrawRequest` first clears the defaulted-epoch receipt via `_claimDefaultedWithdrawRequest`, which resets `lastWithdrawRequest[_user]` to 0. That destroys the only pointer `_claimLossAdjustedWithdrawRequest` uses to find an older, haircut-bearing receipt epoch (`lossRecoveryPriceByEpoch`). The leftover basis then falls through to `_claimFundedWithdrawRequest`, which pays it at par and burns the receipt tokens — an un-owned, un-haircut payout from the funded reserve.

### Finding Description
`claimWithdrawRequest` runs three claim legs in order:

1. `_claimDefaultedWithdrawRequest(_user)` — clears `withdrawsRequestsByEpoch[_user][defaultEpoch]`, decrements `withdrawsRequests`, and in `_clearWithdrawClaimForEpoch` resets `lastWithdrawRequest[_user] = 0` whenever it equals the cleared epoch [1](#0-0) [2](#0-1) .
2. `_claimLossAdjustedWithdrawRequest(_user)` — reads `lossEpoch = lastWithdrawRequest[_user]` and returns early when `lossRecoveryPriceByEpoch[lossEpoch] == 0`. With `lastWithdrawRequest` now 0, this leg always skips [3](#0-2) .
3. `_claimFundedWithdrawRequest(_user)` — the guard `epochNumber <= lastWithdrawRequest[_user]` passes trivially (0), then pays `withdrawsRequests[_user]` (which still contains the older loss-adjusted epoch's `normalAmount`, since `_clearWithdrawClaimForEpoch` only subtracted the default epoch's piece) at par via `_transferFundedClaim`, burning the full receipt [4](#0-3) .

So a user holding a receipt from a `stopEpochWithDuration` loss epoch (owed `claimBasis * lossRecoveryPrice / RECOVERY_FULL`) plus a receipt from the later defaulted epoch is paid: haircut on the default receipt + **full par** on the loss receipt. The loss haircut that `collectWithdrawFunds` reserved for socialization [5](#0-4)  is silently refunded to this user, draining the strategy's funded underlying that backs other claimants (par receipts, post-default reserve is separate; the funded bucket is shared).

### Impact Explanation
The attacker over-claims `(claimBasis_lossEpoch * (RECOVERY_FULL - lossRecoveryPrice)) / RECOVERY_FULL` underlyings — direct theft of the loss haircut from the contract's funded-claim balance, i.e. insolvency for later claimants of up to the full loss-adjusted basis. Broken invariant: loss waterfall / "one receipt one (correctly priced) payout". No existing guard stops it: `defaultRecoveryFinalized` routing is what triggers the ordering bug, and `lastWithdrawRequest == 0` defeats both the epoch-wait check and the loss-price lookup.

### Likelihood Explanation
Requires an unprivileged lender to hold two unclaimed receipts: one in a `stopEpochWithDuration` loss epoch, then a later request in the epoch that gets defaulted and finalized. NOTE comments in `_claimFundedWithdrawRequest` explicitly allow a user to stack requests across epochs ("he will have to wait for another epoch to claim both requests"), so the state is reachable through normal user actions. The manager/borrower actions (loss stop, default, `finalizeDefaultRecovery`) are all honest-role calls as required.

### Recommendation
Resolve all outstanding claim legs before clearing `lastWithdrawRequest`. Either (a) iterate: claim loss-adjusted receipts for every epoch `e` with `lossRecoveryPriceByEpoch[e] != 0` present in `withdrawsRequestsByEpoch[_user]`, or (b) in `_clearWithdrawClaimForEpoch`, when resetting `lastWithdrawRequest`, restore it to the next older pending request epoch instead of 0 so the loss-adjusted leg still finds it. Alternatively, subtract the loss-adjusted epoch's basis from `withdrawsRequests` at `collectWithdrawFunds` time so the par path can never see it.

### Proof of Concept
Foundry fork PoC (against `IdleCreditVault` via `IdleCDOEpochVariant`):

```solidity
// Setup: deposit, epochs run normally.
// 1. Epoch N: user requests withdraw W1 (receipt epoch N+1).
//    Manager stops epoch N+1 via stopEpochWithDuration(.., lossAmount) so
//    collectWithdrawFunds stores lossRecoveryPriceByEpoch[N+1] < 1e18.
//    (Borrower funds pendingToFund only.)
// 2. User requests withdraw W2 during buffer -> receipt epoch N+2.
// 3. Borrower defaults; manager calls _handleBorrowerDefault /
//    finalizeDefaultRecovery -> defaultRecoveryFinalized = true,
//    defaultRecoveryEpoch = N+2.
// 4. User calls IdleCDOEpochVariant.claimWithdrawRequest()
//    -> strategy.claimWithdrawRequest(user):
//       a. _claimDefaultedWithdrawRequest clears epoch N+2 basis,
//          sets lastWithdrawRequest[user] = 0.
//       b. _claimLossAdjustedWithdrawRequest: lossEpoch = 0 -> returns 0.
//       c. _claimFundedWithdrawRequest: epochNumber > 0 passes;
//          pays withdrawsRequests[user] (== W1 basis) at PAR.
// Assert: received == W2*defaultRecoveryPrice/1e18 + W1
//         instead of W2*defaultRecoveryPrice/1e18 + W1*lossRecoveryPrice/1e18.
assertEq(underlying.balanceOf(user) - pre,
         expectedFullParW1 + haircutW2); // over-claim of W1 haircut
```

The delta `W1 - W1 * lossRecoveryPriceByEpoch[N+1] / RECOVERY_FULL` is unbacked: the borrower only funded `pendingToFund` for that epoch, so the excess comes from underlying reserved for other users' funded claims.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
