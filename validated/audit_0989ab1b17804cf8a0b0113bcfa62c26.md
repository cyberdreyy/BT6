**Analysis:** The premise requires a `BlockInfo` with `state == GloballyAccepted` while both `signed_self` and `signed_group` are `None`. Tracing every production path that transitions a block to `GloballyAccepted` shows this state is unreachable:

- `BlockInfo::mark_globally_accepted` unconditionally stamps `signed_group.get_or_insert(get_epoch_time_secs())` before moving state to `GloballyAccepted` — [1](#0-0) .
- The `NewBlock` event handler (the exact scenario cited in the question — "the signer only ever saw the block via a NewBlock node event") calls this same `mark_globally_accepted` before persisting the block, so `signed_group` is always set on that path too — [2](#0-1) .
- The other place that promotes a block to `GloballyAccepted` (inside `check_latest_block_in_tenure`, when the node's tenure tip matches a locally-known block) also calls the same `mark_globally_accepted` — [3](#0-2) .

Since every code path that sets `state = GloballyAccepted` routes through `mark_globally_accepted`, and that function always back-fills `signed_group` if unset, a real `BlockInfo` can never reach `GloballyAccepted` with both `signed_self` and `signed_group` equal to `None`. `get_tenure_last_block_info`'s comment and logic explicitly rely on this invariant when it takes `signed_self.max(signed_group)` — [4](#0-3) .

Even granting a contrived/corrupted DB row bypassing these setters, the described exploit still fails: `check_latest_block_in_tenure` falls through past `get_tenure_last_block_info` and `get_last_accepted_block` (whose pre-commit veto only applies when `state == PreCommitted`, not `GloballyAccepted`) to query the node's own tenure tip via `client.get_tenure_tip`, and rejects any proposal not exceeding that height — [5](#0-4) . Since a globally-accepted block was, by definition, pushed to and processed by the node, the node-tip fallback independently vetoes the conflicting lower/equal proposal, closing the gap the question hypothesizes.

The scenario requires an unreachable internal state that no code path (reachable by an unprivileged attacker crafting proposals/messages) can produce, and even if it were produced, the node-tip backstop in `check_latest_block_in_tenure` prevents the described sibling-block acceptance.
