### Title
Unauthenticated `fullfillWriteOffRequest` lets anyone seize escrowed tranche tokens for zero payment on zero-price write-off requests - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
The external report describes a bug class where credentials/assets are insufficiently protected in transit, letting an unauthorized party intercept value meant for a counterparty. The analog in idle-tranches is `IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest`: it is callable by any wallet, and `createWriteOffRequest` does not enforce a non-zero `underlyingsRequested`. A lender who creates a request asking for 0 underlyings (or a dust amount) can have their entire escrowed tranche balance pulled by any EOA, which pays nothing and receives the tranche tokens directly. The guard at line 129 only enforces `_underlyings >= currentRequest.underlyings`, so a zero-price request is fulfillable at zero cost.

### Finding Description
`createWriteOffRequest` only rejects `amount == 0`; `underlyingsRequested` may be 0 or arbitrarily small [1](#0-0) . `fullfillWriteOffRequest` is explicitly permissionless ("this function can be called by any wallet") and requires only that the fulfiller covers `currentRequest.underlyings` [2](#0-1) . On the fulfillment path the contract unconditionally sends the full `currentRequest.tranches` to `msg.sender` while sending `_underlyings - fee` to the user [3](#0-2) . Therefore any attacker can:

1. Observe a `userRequests[victim]` with `underlyings == 0` (created legitimately or accidentally, e.g., a lender testing the flow or mis-setting parameters).
2. Call `fullfillWriteOffRequest(victim, currentRequest.tranches, 0)` in the same epoch.
3. Receive all of the victim's escrowed tranche tokens while transferring 0 underlying.

Because tranche tokens are claim-Backed receipt tokens redeemable against the vault via `IdleCDOEpochVariant.writeOffDeposit` or normal withdraw flows, this is a direct theft of the lender's escrowed position, not just griefing. Even for non-zero requests, the permissionless design means any third party (not only the borrower the docstring implies) can force-close the exchange and capture the tranche side of the trade, but the zero-underlying case is the clean theft.

### Impact Explanation
Direct theft of user funds: the victim's escrowed tranche tokens are transferred to an arbitrary attacker with no payment. Loss is quantified as the full `currentRequest.tranches` balance, redeemable against the pool at current tranche price. Broken invariant: "one receipt one payout" — the escrow releases the lender's receipt without receiving the promised consideration.

### Likelihood Explanation
Requires a live request with `underlyings == 0`. `createWriteOffRequest` permits it with no minimum bound, and no protocol guard (epoch gating, KYC, only-borrower check) restricts the fulfiller. The attack needs one attacker transaction during a running epoch; likelihood hinges on whether lenders ever post zero or dust-priced requests, which the code does nothing to prevent.

### Recommendation
Enforce `underlyingsRequested > 0` (and possibly a sanity floor) in `createWriteOffRequest`, and/or restrict `fullfillWriteOffRequest` to the configured `borrower` (or an explicit allowed-fulfiller role) so the "credential" — the right to settle the exchange — is authenticated rather than open to any MiTM caller.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultWriteOffEscrow} from "../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

// Fork: deploy IdleCDOEpochVariant + escrow per existing test setup, start an epoch.
contract EscrowSeizeTest is Test {
    IdleCreditVaultWriteOffEscrow escrow; // deployed impl behind proxy
    IERC20Detailed tranche;             // AA or BB tranche of the CDO
    address lender = makeAddr("lender");
    address attacker = makeAddr("attacker");

    function test_seizeZeroPriceRequest() public {
        // epoch running: lender deposits 100 tranche tokens, requests 0 underlyings
        vm.startPrank(lender);
        tranche.approve(address(escrow), 100e18);
        escrow.createWriteOffRequest(100e18, 0);
        vm.stopPrank();

        uint256 lenderBefore = tranche.balanceOf(lender);

        // attacker fulfills with 0 underlyings, receives the tranche tokens
        vm.prank(attacker);
        escrow.fullfillWriteOffRequest(lender, 100e18, 0);

        assertEq(tranche.balanceOf(attacker), 100e18, "attacker seized escrowed tranches");
        assertEq(tranche.balanceOf(lender), lenderBefore, "lender got nothing back");
    }
}
```

Note: if zero-priced requests are deemed out-of-scope user error, the remaining issue (any EOA can front-run the borrower and capture the tranche leg of a priced request) is weaker — the fulfiller still pays the user, so it is trade interception rather than free theft, and arguably intended by the permissionless design comment. The concrete theft path requires the `underlyings == 0` precondition not blocked by the code.

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

```text
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }
```
