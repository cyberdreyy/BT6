### Title
Unbounded decompression allocation via `Base64Zstd`-encoded account override in `simulateTransaction` - ([File: account-decoder-client-types/src/lib.rs])

### Summary
`UiAccountData::decode` decompresses client-supplied `Base64Zstd` account payloads with `zstd::stream::read::Decoder::read_to_end`, which has no cap on the decompressed output size. This routine is reachable from RPC account-override paths (e.g. `simulateTransaction`'s accounts config, via `UiAccount::to_account`/`to_account_shared_data`), letting a single unprivileged client submit a small, highly compressed payload that forces the validator to allocate an arbitrarily large buffer in-process.

### Finding Description
`UiAccountData::decode` handles `UiAccountEncoding::Base64Zstd` by base64-decoding the client string and then piping it through `zstd::stream::read::Decoder::new(...).read_to_end(&mut data)`: [1](#0-0) 
There is no `set_parameter`/`window_log_max` restriction on the decoder and no incremental size check on `data` while reading — `read_to_end` will keep growing the `Vec<u8>` until the stream is exhausted or the process runs out of memory. This decode routine is invoked from `UiAccount::to_account`/`to_account_shared_data`, which are the standard way client-supplied `UiAccount` structures (such as those in `simulateTransaction`'s `accounts` override config) are converted into `Account`/`AccountSharedData` for use by the RPC-side transaction simulation: [2](#0-1) 
`rpc/src/rpc.rs` references `to_account_shared_data`/`to_account`/`accounts_override`/`simulate_transaction` together, consistent with the simulate-transaction handler consuming client-controlled `UiAccount` overrides through this same decode path.

Zstd achieves very high compression ratios on crafted repetitive input (well beyond 1000:1), so a payload of only a few kilobytes of base64 text can decompress into gigabytes of data. Because the base64 string length limits typically enforced on RPC inputs bound only the *compressed* size, they do not bound the *decompressed* output size that `read_to_end` will allocate — the invariant "cost bounded by explicit limits" is violated for this single low-rate request.

### Impact Explanation
A single `simulateTransaction` call with an `accounts` override containing a crafted `Base64Zstd` blob can cause the validator's JSON-RPC handling thread to attempt an unbounded/very large heap allocation, leading to excessive memory pressure or an out-of-memory crash of the validator process from one unprivileged request. This matches the "unbounded cost for a single low-rate call" / RPC resource-exhaustion category.

### Likelihood Explanation
The precondition is only that `simulateTransaction` (or any other consumer of `UiAccountData::decode` for account overrides) accepts `Base64Zstd`-encoded account data from an untrusted client, which is a standard, documented RPC encoding option. No special privileges, config, or multiple calls are needed — one request suffices, making this highly reproducible.

### Recommendation
Bound the decompressed output in `UiAccountData::decode`'s `Base64Zstd` branch: configure the zstd decoder with `set_parameter(zstd::stream::raw::DParameter::WindowLogMax(..))` and/or wrap the reader with a hard byte cap (e.g., read into a fixed-capacity buffer using `Read::take(MAX_ACCOUNT_DATA_LEN)` and reject if the stream is not fully consumed), so decompression aborts once the output would exceed the maximum legitimate account size (`MAX_PERMITTED_DATA_LENGTH`).

### Proof of Concept
```rust
// account-decoder-client-types/tests/zstd_bomb.rs
use {
    account_decoder_client_types::{UiAccountData, UiAccountEncoding},
    base64::{engine::general_purpose::STANDARD, Engine},
};

#[test]
fn zstd_decompression_bomb_is_unbounded() {
    // Craft a small zstd stream that decompresses to e.g. 4 GiB of zeros.
    let huge = vec![0u8; 4 * 1024 * 1024 * 1024];
    let compressed = zstd::stream::encode_all(huge.as_slice(), 19).unwrap();
    assert!(compressed.len() < 100 * 1024); // tiny compressed payload

    let blob = STANDARD.encode(&compressed);
    let data = UiAccountData::Binary(blob, UiAccountEncoding::Base64Zstd);

    // Expected (fixed) behavior: decode() should reject/truncate before
    // allocating the full 4GiB buffer, e.g. return None or an error
    // once output exceeds MAX_PERMITTED_DATA_LENGTH.
    let decoded = data.decode();
    assert!(decoded.map_or(true, |d| d.len() <= solana_sdk::system_instruction::MAX_PERMITTED_DATA_LENGTH as usize));
}
```
Current code will allocate the full 4 GiB buffer (or OOM) instead of failing fast, demonstrating the missing output-size cap.

impl UiAccount {
    pub fn to_account_shared_data(&self) -> Option<AccountSharedData> {

        Some(AccountSharedData::create_from_existing_shared_data(
            self.lamports,
            data,
            Pubkey::from_str(&self.owner).ok()?,

            self.rent_epoch,
        ))
    }

            data,
