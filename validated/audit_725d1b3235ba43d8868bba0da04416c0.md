### Title
Stale confirmations from revoked/deleted keys let a multisig request execute below the configured confirmation threshold - (File: multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts entries in the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` set for a request and executes the request once that count reaches `num_confirmations`. When a key is removed via the `DeleteKey` action, the code only deletes *requests originally authored* by that key; it does not remove that key's already-recorded confirmations on any *other* pending request. As a result, a request can execute with a `confirmations` count that includes one or more keys that are no longer valid signers on the account, so the number of *live* keys that actually approved the request is smaller than `num_confirmations`.

### Finding Description
The custody binding intended here is: `confirmations counted == confirmations from currently authorized keys`, and execution should require `num_confirmations` live approvals before `Promise::transfer` or any other privileged action fires.

- `confirm()` [1](#0-0)  checks only the size of the stored `HashSet<PublicKey>` against `num_confirmations`, with no re-validation that each key in that set is still an authorized key on the account.
- The `DeleteKey` action handler [2](#0-1)  removes only requests where `r.signer_pk == pk` (i.e., requests *created* by the deleted key) and clears `num_requests_pk` for that key — it never scans `self.confirmations` to strip the deleted key from confirmation sets of *other* pending requests that key had already confirmed.
- `remove_request` / `assert_valid_request` [3](#0-2)  likewise never validate confirming keys are current members; they only check the request/confirmations maps are internally consistent.

Concretely: key A creates request R (Transfer). Key B confirms R (now 1 confirmation, `num_confirmations = 3`). Members then remove key B via a `DeleteKey` request (e.g., because B is suspected compromised or is leaving). R is untouched by that removal since R was authored by A, not B — so R still carries B's stale confirmation. Now only 2 more *live* confirmations (not 3) are needed to push R over threshold, because B's already-counted confirmation persists despite B no longer being an authorized signer.

### Impact Explanation
This crosses the "confirmations counted versus live members" custody boundary called out for this scope. A `Transfer`, `FunctionCall`, `AddKey`, or `DeleteKey` request can be executed by the contract with effectively fewer than `num_confirmations` currently-authorized signers, i.e., a multisig request executed below threshold — moving NEAR out of the account, or granting/revoking access keys, with less real authorization than the deployment's threshold guarantees. This matches the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
No privileged role is required beyond being one of the existing multisig signers (any legitimate confirming key qualifies as "B" in the scenario), and key rotation/removal via `DeleteKey` is a normal, documented operation of this contract (the README even acknowledges consequences of deleting keys, but only discusses the lockout case, not this stale-confirmation case). Any account that routinely rotates or revokes compromised keys while requests are in flight is exposed.

### Recommendation
When executing `DeleteKey` (and equivalently in `multisig2`'s `DeleteMember`), iterate all pending requests' confirmation sets and remove the deleted key/member from every set, not only from requests it authored. Alternatively, re-validate at `confirm()`-time (or at execution time) that every public key contained in a request's confirmation set is still present in the current key/member set before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` with keys `[A, B, C]` (`num_confirmations = 3`).
2. As `A`, call `add_request` with a `Transfer { amount }` request `R` (`receiver_id` = some account) — `R` has 0 confirmations, signer_pk = A.
3. As `B`, call `confirm(R)` — `R.confirmations = {B}` (1 of 3, not yet executed).
4. As a quorum of `A, C` (or any 3 keys, whichever separate flow the operators use), submit and confirm a `DeleteKey { public_key: B }` request; this executes, removing B from the account's keys via `promise.delete_key(B)`, but since `R` was authored by `A` (not `B`), the `DeleteKey` handler's `filter(|(_k, r)| r.signer_pk == pk)` loop [4](#0-3)  does not touch `R`; `R.confirmations` still contains `B`.
5. As `C`, call `confirm(R)` — `R.confirmations` becomes `{B, C}`, size 2, so `confirm()`'s check `confirmations.len() as u32 + 1 >= self.num_confirmations` (2 + 1 >= 3) is satisfied and `R` executes the `Transfer`, even though only `A` (implicitly, as requester) and `C` are still valid keys — i.e., only 2 live signers actually authorized this transfer, not the required 3.

    // removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .expect("Failed to remove existing element");
        // decrement num_requests for original request signer
        let original_signer_pk = request_with_signer.signer_pk;
        let mut num_requests = self.num_requests_pk.get(&original_signer_pk).unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_signer_pk, &num_requests);
        // return request
        request_with_signer.request
    }
