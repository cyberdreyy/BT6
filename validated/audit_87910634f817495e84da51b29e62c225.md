### Title
Floor-vs-ceiling threshold mismatch lets `GlobalStateEvaluator` capitulate to a miner/state view below the real 70% signing threshold - (File: `libsigner/src/v0/signer_state.rs`)

### Summary
The signer's local state-machine agreement check (`GlobalStateEvaluator::reached_agreement`/`reached_disagreement`) computes the 70%/30% weight thresholds with plain integer **floor** division, while the block-signature threshold used everywhere else in the protocol (`NakamotoBlockHeader::compute_voting_weight_threshold`) computes the same 70% cutoff with an explicit **ceiling**. For the same `total_weight`, these two computations can disagree by one unit of weight, so a signer can "reach agreement" on a global miner view / protocol version / burn view / tx-replay-set at a weight that is strictly below the weight actually required to cross the 70% supermajority bar used for block approval and rejection accounting.

### Finding Description
`NakamotoBlockHeader::compute_voting_weight_threshold` (the function used to decide whether enough signers have pre-committed/signed/rejected a block) rounds up: [1](#0-0) 
```
pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
    let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
    let total_weight = u64::from(total_weight);
    let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
    u32::try_from((total_weight * threshold) / 10 + ceil)...
}
```

`GlobalStateEvaluator::reached_agreement` / `reached_disagreement`, which decide whether the signer's *local state machine* (protocol version, burn view, current-miner state, tx-replay set) has reached global consensus, use the same `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` constant but with plain floor division and no ceiling correction: [2](#0-1) 
```
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10
}

pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10
}
```

For any `total_weight` where `total_weight * 7` is not a multiple of 10 (e.g. `total_weight = 13`: `13*7=91`, `91/10=9` floor, but the block-signing threshold ceils to `10`), the two functions disagree on where the 70% line sits: `reached_agreement` accepts `9/13 ≈ 69.2%` as sufficient, while the real block-approval math (`compute_voting_weight_threshold`, used in `stacks-signer/src/v0/signer.rs` pre-commit/rejection tallying, `stackerdb_listener.rs`, `signer_coordinator.rs`, and `verify_signer_signatures`) requires `10/13 ≈ 76.9%`.

`GlobalStateEvaluator` (via `determine_global_state`, `determine_latest_supported_signer_protocol_version`, `determine_global_burn_view`, `find_majority_prefix_replay_set`) is exactly the mechanism the signer uses to decide what the network-wide agreed miner view, protocol version, and tx-replay set are, per the flow documented for `capitulate_miner_view` / `capitulate_viewpoint`: *"bucket peers' miner states by weight; adopt a threshold view."* [3](#0-2) 

Because this adoption uses the weaker (floor) threshold, a signer can capitulate to (i.e., commit to building/signing on top of) a miner/tenure view, tx-replay set, or protocol version that a fraction of signers strictly below the "true" 70% supermajority (as enforced for actual block signatures) support.

### Impact Explanation
This is a threshold/equality mismatch between two components that are both supposed to implement the same "70% weight" consensus rule but that disagree by design for certain `total_weight` values that are not multiples of 10. This falls in the "aggregated-weight vs verified-accepts" bug class: the aggregated weight computed by `GlobalStateEvaluator` for global-state agreement is checked against a *looser* threshold than the weight verified elsewhere (`verify_signer_signatures`, `compute_voting_weight_threshold`) for the actual block signature quorum. A signer can therefore lock its local state machine (current miner, parent tenure last block, protocol version, replay set) onto a value that does not actually have the real supermajority behind it, causing it to diverge from signers that compute the "correct" (ceiling) threshold-based view in the rest of the codebase, or to act on a state that is short of the consensus bar the rest of the network enforces for block approval/rejection. This matches the High-severity class: "a signer... acting on a stale reward set/threshold."

### Likelihood Explanation
This is triggerable purely through normal gossip of `StateMachineUpdate` messages from the existing signer set (no majority key compromise, no node access needed) whenever the total signer weight for a reward cycle is not an exact multiple of 10 (a very common situation, since weights are derived from stacked-STX proportions and are not guaranteed to sum to a multiple of 10). Any signer set with such a weight distribution will trigger the off-by-one discrepancy on every global-state evaluation, not just under adversarial conditions.

### Recommendation
Make `GlobalStateEvaluator::reached_agreement` and `reached_disagreement` use the exact same rounding rule (ceiling division for the 70% majority, and the correctly complementary rule for the 30% blocking minority) as `NakamotoBlockHeader::compute_voting_weight_threshold`, ideally by sharing a single threshold-computation helper instead of reimplementing the arithmetic in two places with different rounding behavior.

### Proof of Concept
1. Configure a reward cycle where signer weights sum to `total_weight = 13` (e.g., weights `[9, 2, 1, 1]`), which is achievable with an ordinary stacked-STX distribution.
2. `NakamotoBlockHeader::compute_voting_weight_threshold(13)` returns `10` (`13*7=91`, `91/10=9`, remainder → ceil → `10`), i.e., a block needs `10/13` weight to be signed/approved.
3. `GlobalStateEvaluator::reached_agreement(9)` (with `total_weight = 13`) returns `true` (`13*7/10 = 9`, floor, no ceiling), so a `StateMachineUpdate` view supported by only `9/13 ≈ 69.2%` weight is treated as the agreed global state (miner view / protocol version / replay set), even though this is below the `10/13` bar that the same constant enforces for actual block signatures elsewhere in the codebase.
4. This lets the local signer capitulate to (and subsequently build tenure/miner decisions around) a state that a genuine 70%-threshold check (as used for block approval) would not have accepted, producing an inconsistency between the signer's adopted global view and the network's real supermajority.
