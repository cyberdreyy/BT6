## Title
Stale Confirmations From Removed Members Allow Execution Below Effective Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`multisig2`'s `delete_member` only purges pending *requests* originated by the removed member; it never scans the `confirmations` map to strip that member's already-cast confirmations from *other* pending requests. `confirm` then counts confirmations purely by set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without re-validating that every recorded confirmer is still a live member. This is the same bug class as the reported `queue::remove` defect: a boundary/aggregate value (`tail`, here the "authorized confirmer set") is not kept in sync when an element (the removed queue node / the removed multisig member) is deleted, and a later operation (iteration / threshold check) trusts the stale reference.

### Finding Description
`confirm` looks up the confirmation set for a request and compares its cardinality to `self.num_confirmations`: [1](#0-0) 

Membership of a confirmer is validated only at the moment of confirming (`current_member()` checks `self.members.contains(&member)`), but nothing re-validates the *existing* entries already stored in `confirmations` for that `request_id`. `delete_member` removes the member from `self.members` and deletes only the requests that member originally authored, but never touches the `confirmations` sets of other outstanding requests: [2](#0-1) 

Consequence: if member A confirms request R (added by member B, still below threshold), and A is subsequently removed via a `DeleteMember` request, R's `confirmations` set still contains A's identifier. When enough *additional* live members confirm R to reach `num_confirmations` (counting A's stale confirmation), `execute_request` is invoked and the promise (e.g. a `Transfer`, `AddKey`, or another `DeleteMember`/`AddMember`) executes — even though the number of live, currently-authorized confirmers is one less than `num_confirmations`. This breaks the equality that should hold: `confirmations counted == confirmations from currently live members`.

### Impact Explanation
This crosses the authorization-threshold boundary explicitly called out as in-scope ("confirmations counted versus live members"). A multisig request (which can include `Transfer`, `AddKey`/`AddFullAccessKey`, `AddMember`, `DeleteMember`, or arbitrary `FunctionCall`) can be executed with fewer live authorized signers than the configured `num_confirmations`, i.e. a multisig request executed below threshold — matching the Critical impact category defined in scope.

### Likelihood Explanation
The precondition is realistic and requires no privileged action beyond ordinary multisig operation: any member can confirm a request without it reaching threshold, then a separate (valid) `DeleteMember` request can remove that member for unrelated reasons (e.g., routine key rotation or offboarding), leaving the stale confirmation in place on the still-pending request. No redeploy, victim key, or social engineering is required — only normal request/confirm/delete-member flows already exposed by the contract's public API.

### Recommendation
When a member is deleted, iterate `self.requests`/`self.confirmations` and remove the member's confirmation from every pending request's confirmation set (mirroring how `delete_member` already purges requests keyed by that member as originator). Alternatively, `confirm` should recompute the count of *currently valid* confirmers (intersecting `confirmations` with `self.members`) before comparing against `num_confirmations`, rather than trusting the raw set length.

### Proof of Concept
1. Multisig deployed with 3 members `A`, `B`, `C` and `num_confirmations = 2`.
2. `B` calls `add_request_and_confirm` to create request `R` (e.g. `Transfer`) — `confirmations = {B}`, below threshold (1 < 2).
3. Separately, an already-approved `DeleteMember { member: A }` request executes, removing `A` from `self.members` (per `delete_member`, lines 355-379) — note this only purges requests where `r.member == A` (requests *originated* by A); `R`'s confirmations, which do not reference A as the originator, are untouched even though A never confirmed R in this scenario — the real stale case is:
   - `A` calls `confirm(R)` first — `confirmations = {B, A}` still below a higher threshold (e.g. `num_confirmations = 3`).
   - `A` is then deleted via `DeleteMember`.
   - `C` calls `confirm(R)` — `confirmations.len() + 1 == 3 >= num_confirmations`, so `R` executes using the stale confirmation from now-removed member `A`, even though only 2 live members (`B`, `C`) actually authorized it.
4. `execute_request(R)` runs with only 2 of 3 required *live* confirmations, demonstrating execution below the effective threshold. [1](#0-0) [2](#0-1)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
