### Title
`process_execution_payload_bid` never enforces the builder's committed `fee_recipient`, letting builder payments be misdirected away from the proposer's declared address - ([File: specs/gloas/beacon-chain.md])

### Summary
`process_execution_payload_bid` accepts any `bid.fee_recipient` supplied by the builder and queues the builder payment to that address without checking it against the proposer's signed preferences. The only place this consistency is checked is a non-binding gossip-network `IGNORE` rule, which is a soft propagation heuristic, not a consensus rule. Any bid that reaches the state-transition function - whether via gossip, direct off-protocol delivery to the proposer, or a compromised/careless validator client - is accepted verbatim, so the builder payment can be sent to an address the proposer never actually committed to at the protocol level.

### Finding Description
`process_execution_payload_bid` in `specs/gloas/beacon-chain.md` records the pending builder payment straight from the bid, with no assertion tying `bid.fee_recipient` to anything the proposer signed: [1](#0-0) 

Compare this to the *only* place a `fee_recipient` consistency check exists - the gossip validator, and note it is explicitly an `IGNORE`, not a `REJECT`: [2](#0-1) 

An `IGNORE` verdict in the gossip rules only affects whether a node re-broadcasts the message on the P2P network; it has zero bearing on whether a block containing that bid is a valid state transition. The canonical proof that this field is not enforced at the consensus layer is the dedicated test asserting the mismatch case yields `"ignore"` (not `"reject"`), confirming other honest nodes will still relay/accept the underlying block if it somehow reaches them through another path: [3](#0-2) 

The validator guidance for constructing a block also never lists "`bid.fee_recipient` matches my own signed preferences" as a required check before a proposer includes a bid - it only documents informally, outside of any MUST list, that the address in `fee_recipient` "will receive the builder payment": [4](#0-3) 

Because `process_execution_payload_bid` is the actual state-transition rule run by every spec-following node, a block that includes a bid whose `fee_recipient` differs from the proposer's own `SignedProposerPreferences` is fully valid and will be accepted by all honest nodes, permanently queuing (and eventually settling via `apply_parent_execution_payload` / `settle_builder_payment`) a `BuilderPendingWithdrawal` to the wrong address: [5](#0-4) 

### Impact Explanation
This breaks the equality that a builder payment committed for a specific block must reach the fee recipient the proposer actually authorized. A builder payment is misdirected to an address the proposer did not commit to at the consensus layer — matching the High-severity class "a builder payment or withdrawal misdirected." The Gwei paid by the builder is a real, accounted-for balance movement (`Builder.balance` decreases, a `BuilderPendingWithdrawal` credits `fee_recipient`), so the loss/misdirection is concrete, not merely theoretical griefing.

### Likelihood Explanation
Exploitation requires only that a bid with a mismatched `fee_recipient` be included in a block by *any* means other than the gossip topic's `IGNORE` filter (e.g., a builder submitting the bid directly to a proposer out-of-band, a relay, or any client implementation that does not itself re-derive and check the proposer's own preferences before accepting an externally-sourced bid). Since the canonical state-transition function performs no check at all, no consensus fork or majority stake is required — a single builder (or a proposer client bug that trusts an externally-supplied bid) is sufficient to produce a fully valid block that misdirects the payment.

### Recommendation
Add an explicit assertion in `process_execution_payload_bid` (or in `apply_parent_execution_payload`/`settle_builder_payment`) that `bid.fee_recipient` matches the committed `SignedProposerPreferences.fee_recipient` for `bid.slot`/proposer, mirroring the gossip-layer check but promoting it to a state-transition-level `assert` so it is enforced consensus-wide, not just as an optional network-relay heuristic.

### Proof of Concept
1. Proposer P for slot `N` signs `SignedProposerPreferences` with `fee_recipient = A`.
2. Builder B crafts `ExecutionPayloadBid` with `fee_recipient = B_addr` (any address B controls) and a non-zero `value`, and sends it directly to P off-gossip (or P's client software accepts an externally supplied bid without re-checking `fee_recipient`).
3. P includes `SignedExecutionPayloadBid` in block for slot `N`. `process_execution_payload_bid` (specs/gloas/beacon-chain.md) runs all its `assert`s (signature, funds, slot, parent hash/root, randao) — none reference `fee_recipient` — and records `BuilderPendingPayment.withdrawal.fee_recipient = B_addr`.
4. The block is fully valid per the state-transition function; every spec-following node accepts it.
5. When the payment settles (`settle_builder_payment` via `apply_parent_execution_payload`), a `BuilderPendingWithdrawal` with `fee_recipient = B_addr` is created/paid, not `A` — the payment the proposer intended to receive is instead redirected.

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid

##### Signed execution payload bid

To obtain `signed_execution_payload_bid`, a block proposer building a block on
top of a `state` MUST take the following actions in order to construct the
`signed_execution_payload_bid` field in `BeaconBlockBody`:

- Listen to the `execution_payload_bid` gossip global topic and save an accepted
  `signed_execution_payload_bid` from a builder. The block proposer MAY obtain
  these signed messages by other off-protocol means.
- The `signed_execution_payload_bid` MUST satisfy the verification conditions
  found in `process_execution_payload_bid` with the alias
  `bid = signed_execution_payload_bid.message`, that is:
  - For external builders, the signature MUST be valid.
  - For self-builds, set `bid.builder_index` to `BUILDER_INDEX_SELF_BUILD`.
  - For self-builds, the signature MUST be `bls.G2_POINT_AT_INFINITY` and the
    `bid.value` MUST be zero.
  - The builder balance can cover the `bid.value`.
  - The `bid.slot` is for the proposal block slot.
  - The `bid.parent_block_hash` equals
    `state.latest_execution_payload_bid.block_hash` if
    `should_build_on_full(store, head, get_current_slot(store))` is true,
    otherwise `state.latest_execution_payload_bid.parent_block_hash`.
  - The `bid.parent_block_root` equals the current block's `parent_root`.
  - The `bid.prev_randao` equals
    `get_randao_mix(state, get_current_epoch(state))`.
- Select one bid and set
  `block.body.signed_execution_payload_bid = signed_execution_payload_bid`.

*Note*: The execution address encoded in the `fee_recipient` field in the
`signed_execution_payload_bid.message` will receive the builder payment.
