### Title
Permanent freezing of ETH sent to the ActivationRegistry precompile at the pre‑Cobalt (Beryl) fork - (File: crates/common/precompiles/src/activation/dispatch.rs)

### Summary
The `ActivationRegistry` native precompile at address `0x8453000000000000000000000000000000000001` deliberately accepts calls carrying nonzero ETH `value` when the active fork is pre‑Cobalt (Beryl), instead of rejecting them like every other native precompile in the codebase (`PolicyRegistry`, `B20Factory`, `B20AssetToken`, `NonceManager`, `TransactionContext` all unconditionally revert with `NonPayable` on any nonzero `call_value`). Because a precompile has no contract code and no owner-controlled sweep/withdraw entry point, any ETH value transferred into its address as part of a successful call becomes permanently unspendable — structurally identical to the `MPROVesting.sol` `receive()`-without-withdraw bug class described in the report.

### Finding Description
`ActivationRegistryStorage::dispatch_with_observer` guards the nonpayable check with an upgrade condition: [1](#0-0) 

```
// Activation-registry selectors are all nonpayable; reject attached ETH from Cobalt
// onward. Pre-Cobalt (Beryl) preserves the historical accept-and-strand behavior so
// replay of live-installed activation calls remains byte-identical.
if upgrade >= BaseUpgrade::Cobalt && !ctx.call_value().is_zero() {
    return recorder.record_base_error_result(
        ctx,
        BasePrecompileError::revert(IActivationRegistry::NonPayable {}),
    );
}
```

For `BaseUpgrade::Beryl` (i.e. `upgrade < Cobalt`), the value check is skipped entirely and execution falls through to `self.inner(calldata, admin_config)`, which processes the call and returns success for read-only, unauthenticated selectors such as `isActivated(bytes32)`. The project's own unit test explicitly documents this as the attacker path: [2](#0-1) 

```
#[test]
fn dispatch_rejects_call_with_nonzero_value_at_cobalt() {
    ...
    // A read-only, unauthenticated selector — the exact path an attacker uses to strand ETH.
    let calldata = IActivationRegistry::isActivatedCall { feature: B256::ZERO }.abi_encode();
    ...
}

#[test]
fn dispatch_accepts_nonzero_value_before_cobalt() {
    // Consensus safety: pre-Cobalt (Beryl) must NOT emit the new NonPayable revert, otherwise
    // replay of live-installed activation calls that carried ETH would diverge.
    ...
    assert!(output.is_success(), "pre-Cobalt must accept nonzero value (legacy behavior)");
```

By contrast, every sibling native precompile enforces the nonpayable check unconditionally, with no fork gate: [3](#0-2) [4](#0-3) [5](#0-4) 

The EVM's value-transfer semantics credit `value` to the callee's account balance as part of executing a successful `CALL`, independent of what the target's code (or, for a precompile, the native handler) does with it. Because the `ActivationRegistry` address has no bytecode and is dispatched only through this native precompile handler — which never spends, forwards, or exposes the accrued balance — any ETH sent to it during (or replayed as) the Beryl fork window is permanently locked at that address with no code path to move it out.

### Impact Explanation
This is a direct, permanent freezing-of-funds bug: any signed transaction from an unprivileged, anonymous caller can send ETH with a call to `0x8453...0001` using any nonpayable, unauthenticated read-only selector (e.g. `isActivated`), and while the fork is Beryl, the call succeeds and the ETH is stranded forever at a precompile address that can never execute code to release it. This matches the accepted impact class "permanent freezing of funds" and is materially the same root cause as the reported `MPROVesting.sol` issue: a payable/value-accepting entry point with no corresponding withdrawal mechanism.

### Likelihood Explanation
The path requires no privilege, no coordination, and no chain-specific race condition — a single ordinary transaction carrying `value > 0` targeting the activation registry address during Beryl (including any devnet/testnet/genesis window still on that upgrade, or during historical-Beryl block replay) suffices. The bug is intentionally preserved by design ("Consensus safety... must NOT emit the new NonPayable revert") for replay-compatibility, meaning it is a known, currently-live characteristic of the precompile rather than a hypothetical edge case.

### Recommendation
Since the pre-Cobalt behavior must be preserved bit-for-bit for consensus/replay reasons, the safe fix is not to change the Beryl dispatch path (which would fork historical execution), but to add a privileged sweep mechanism reachable only by a protocol-controlled account (e.g. a system-level transaction or admin-gated future precompile method) that can debit the accrued balance at `0x8453...0001` and redirect it to a recoverable destination going forward, or to document/monitor the address so any pre-Cobalt-accrued balance is accounted for in future upgrades. At minimum, confirm no live chain remains on Beryl with a public RPC surface where this path is reachable, and add explicit balance-draining/migration logic when transitioning such chains to Cobalt.

### Proof of Concept
1. Configure or observe a Base chain instance whose active hardfork resolves to `BaseUpgrade::Beryl` (pre‑Cobalt).
2. From any unprivileged EOA, send a transaction to `0x8453000000000000000000000000000000000001` with `value = 1 wei` (or more) and calldata `IActivationRegistry::isActivatedCall{ feature: B256::ZERO }.abi_encode()`.
3. Per `dispatch_with_observer` (lines 50–58), the nonzero-value check is skipped because `upgrade < BaseUpgrade::Cobalt`; `self.inner(...)` runs the read-only `isActivated` handler and returns success.
4. The EVM credits the `value` to the precompile address's balance as part of the successful call.
5. No entry point in `ActivationRegistryStorage`, `ActivationRegistry::install*`, or any other production code path spends, transfers, or exposes this balance — the ETH is permanently unrecoverable, mirroring the `MPROVesting.sol` `receive()`-without-withdraw defect from the reference report.
