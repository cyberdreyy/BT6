The reported CVE describes a `python-multipart`/Starlette issue where a shared HTTP server processes an attacker-controlled number of multipart fields with no cap, causing OOM against other users' requests. The closest structural analogs in this codebase are the unbounded `RequestV2[] calldata requests` arrays accepted by `ProvisionerV2.solveRequestsDirect` and `ProvisionerV2._solveRequestsVault`, which loop over `requests.length` with no explicit maximum count [1](#0-0) [2](#0-1) .

However, this does not reproduce the broken invariant from the advisory. In the CVE, an attacker's request forces a shared server to spend unbounded CPU/memory servicing other users' traffic, degrading service for everyone. Here, the caller of `solveRequestsDirect`/`solveRequestsVault` supplies and pays gas for their own `requests` array; there is no way for one user's call to force another user's transaction to process an oversized array, and Ethereum's per-block gas limit already bounds any single call's resource consumption — an oversized array simply causes the caller's own transaction to run out of gas or fail, not a shared-server OOM. There's no mechanism by which an ordinary user can impose this cost on the vault, other depositors, or unclaimed yield; the "victim" of any such gas exhaustion is the caller itself. This fails the required "concrete theft or freezing of user funds" bar and doesn't match the CVE's precondition of unbounded attacker input consumed by a shared resource on behalf of third parties.

No other reachable path (deposit/mint, redeem, cancel/refund, price/fee conversion, oracle binding) showed an unbounded-loop-over-attacker-controlled-array pattern that is processed on behalf of, or at the expense of, other users' funds.

        TokenDetailsV2 memory tokenDetails = tokensDetails[token];
        bool depositsExist;
        for (uint256 i = 0; i < length; i++) {

            if (_isRequestTypeDeposit(request.requestType)) {
                // Requirements: async deposit is enabled
                if (!tokenDetails.asyncDepositEnabled) {
                    // Log async deposit disabled event
                    emit AsyncDepositDisabled(i);
                    continue;

                    depositsExist = true;

                    // Requirements + Effects + Interactions: solve auto price deposit
                    solverTip += _solveDepositVaultAutoPrice(

                    );
