### Title
Instant-withdraw receipts can be claimed at par before the borrower has funded them, draining funded normal-withdraw liquidity - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` burns the caller's full instant-withdraw receipt and pays it out at par without checking whether that receipt has actually been funded yet. The strategy tracks the still-unfunded remainder in `pendingInstantWithdraws` (debited only when `collectInstantWithdrawFunds` pulls cash from the CDO at `startEpoch` or later borrower repayment), but the claim path ignores it. This is the direct analog of the netfs bug: a read/claim path trusts a receipt flag without waiting for the in-flight "writeback" (queue funding) to complete.

### Finding Description
In `requestInstantWithdraw` the vault mints the user a receipt and increments `pendingInstantWithdraws` (lines 356-375). Funding arrives asynchronously via `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and transfers underlyings (lines 398-403). `IdleCDOEpochVariant.startEpoch` documents that the CDO's available cash may cover only part of the instant queue and that the borrower is expected to return the difference before `instantWithdrawDeadline` — so the state `instantWithdrawsRequests[user] > funded share` is a normal, reachable state.

Yet `claimInstantWithdrawRequest` (lines 380-393) does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

There is no `pendingInstantWithdraws == 0` check, no per-user funded accounting, and no `instantWithdrawDeadline` gate on the CDO side (`IdleCDOEpochVariant.claimInstantWithdrawRequest` only checks `allowInstantWithdraw`). `_transferFundedClaim` only protects `defaultRecoveryReserve`; it happily spends underlyings that belong to *other* users' funded normal withdraw requests or the funded portion of other instant claims held in the strategy.

The broken invariant is "one receipt, one funded payout": a claimant is paid out of liquidity earmarked for other receipts while the funding writeback is still pending.

### Impact Explanation
An attacker requests an instant withdraw, waits for `startEpoch` to partially fund the queue (or for the strategy to already hold underlyings belonging to matured normal `withdrawsRequests`), and calls `claimWithdrawRequest`/`claimInstantWithdrawRequest` to receive the full par amount immediately. The payout consumes underlyings owed to other claimants, causing direct theft / permanent freezing of their claims: later legitimate claimants' `safeTransfer` reverts for insufficient balance, and `pendingInstantWithdraws` was already decremented only for the funded part, so the deficit is socialized onto honest users rather than the borrower.

### Likelihood Explanation
Requires instant withdrawals enabled (`allowInstantWithdraw`) and a moment where `pendingInstantWithdraws > 0` while the strategy holds other users' funded liquidity — exactly the gap `startEpoch` creates between partial collection and the borrower's deadline repayment. The attacker needs only to be a KYC-passing tranche holder able to trigger the instant-withdraw path (e.g., via the APR-delta condition in `requestWithdraw`). One caveat I could not fully verify in the available context: whether the CDO's `startEpoch` always succeeds in fully funding the instant queue in practice, or whether an additional keeper/guard blocks claims until `instantWithdrawDeadline`. If full funding is guaranteed atomically at `startEpoch`, the window reduces to cases where the strategy holds matured funded withdrawals alongside a deliberately underfunded instant queue (which the code explicitly anticipates via `_defaultPrefundedInstantReserve`).

### Recommendation
Gate `claimInstantWithdrawRequest` on the receipt being funded, e.g. revert while `pendingInstantWithdraws != 0` (or track funded vs unfunded per user and pay only the funded portion), analogous to how `claimWithdrawRequest` blocks until `epochNumber > lastWithdrawRequest`. Alternatively, pay unfunded instant claims pro-rata through `lossRecoveryPriceByEpoch`-style accounting instead of at par.

### Proof of Concept
Foundry fork sketch:

```solidity
// setup: deposit via AA tranche, enable instant withdraws (apr drop path)
uint256 shares = idleCDO.depositAA(100_000e6);

// user B (victim) makes a normal withdraw request; epoch stops, funds collected
cdoEpoch.requestWithdraw(victimShares, address(AAtranche)); // as victim
// manager starts epoch: CDO's cash only partially covers instant queue
cdoEpoch.startEpoch(); // collectInstantWithdrawFunds funds < pendingInstantWithdraws

// attacker requested instant withdraw during buffer via requestWithdraw when
// lastEpochApr > unscaledApr + instantWithdrawAprDelta
// pendingInstantWithdraws > 0 but attacker's receipt is fully claimable
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest(); // pays par, drains victim's funded withdrawal liquidity
assertGt(underlying.balanceOf(attacker) - balPre, 0);

// victim's matured claim now reverts on insufficient strategy balance
vm.prank(victim);
vm.expectRevert();
cdoEpoch.claimWithdrawRequest();
```
