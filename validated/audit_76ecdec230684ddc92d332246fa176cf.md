### Title
APR0 withdraw request bricks `stopEpoch` after any mid-epoch APR raise, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` hard-reverts (`NotAllowed`) whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` (lines 505–508). An unprivileged KYC-passing lender can put the strategy into this state cheaply: during any APR=0 epoch the attacker calls `requestWithdraw` (dust amount), which routes to `_requestWithdrawApr0` and sets `apr0TotalPrincipal > 0` (lines 285–286, 567–577). A subsequent honest APR change — either the manager calling `setAprs`/`setAprsWithBuffer` mid-epoch (lines 206–220), or the CDO setting the next epoch's scaled APR via `_setScaledApr` inside `stopEpoch` — flips `unscaledApr` to non-zero while the APR0 bucket is still open. Every `stopEpoch` / `stopEpochWithDuration` call then reverts, because `prepareStopEpochWithApr0` is invoked on the stop path before the bucket can be closed (`apr0TotalPrincipal = 0` is only reached on line 540, after the revert check). Like the decompileIF out-of-bounds read, a malformed input state crashes the core routine — here the crash permanently reverts the only path that recalls borrower funds.

### Finding Description
- `requestWithdraw` on `IdleCreditVault` sends requests into the APR0 bucket whenever `unscaledApr == 0` and the pool is not closed: `_requestWithdrawApr0` increments `apr0Users[_user].principal` and `apr0TotalPrincipal` (lines 285–286, 570–576). No minimum amount, no cooldown — a 1-wei request suffices.
- `prepareStopEpochWithApr0` is called by `IdleCDOEpochVariant.stopEpoch` to compute realized interest. Its first action after detecting a non-zero APR0 bucket is `if (unscaledApr != 0) revert NotAllowed()` (lines 505–508). The bucket is only cleared at line 540, so the revert is hit before any cleanup.
- `unscaledApr` can legitimately become non-zero while the bucket is open: the manager (an honest, non-attacker role) may call `setAprs`/`setAprsWithBuffer` at any time, and `_setScaledApr` in `IdleCDOEpochVariant` (line 544–546) sets the next-epoch APR during `stopEpoch`. If the vault owner/manager announces a rate raise for the next epoch — a normal operation — the state becomes unrecoverable through the normal stop path.
- No guard prevents this: `requestWithdraw` has no check that APR will remain 0; `setAprs` has no check that `apr0TotalPrincipal == 0`; there is no admin escape hatch that zeroes `apr0TotalPrincipal` other than a successful `stopEpoch`, which is exactly what reverts.

### Impact Explanation
While `unscaledApr != 0` and `apr0TotalPrincipal != 0` coexist, `stopEpoch` always reverts, so the epoch can never close: borrower funds cannot be recalled, `pendingWithdraws` cannot be funded, and all lender TVL (plus all queued withdraw/instant-withdraw receipts) stays locked with the borrower. The freeze persists until the manager sets `unscaledApr` back to 0 — i.e., the attacker forces the protocol to keep the pool at 0% APR for the rest of the epoch and delays every claim. Quantified loss: the full vault TVL is frozen for the remaining epoch duration, and the protocol forfeits the announced yield (all interest at the raised APR) for that period. If the borrower defaults during the induced freeze, receipt holders additionally eat the default-epoch delay. Cost to attacker: gas plus a dust deposit/withdraw request.

### Likelihood Explanation
Requires an APR0 epoch (a supported, advertised mode — `_requestWithdrawApr0` exists specifically for it) and a later rate raise, both normal operations. The attacker transaction is a single dust `requestWithdraw` by any KYC'd lender. The "malicious input" is entirely unprivileged; the trigger is an honest manager action that the code should tolerate but instead reverts on. Main uncertainty: if `_setScaledApr` inside `stopEpoch` runs strictly after `prepareStopEpochWithApr0`, the CDO-driven path alone cannot create the state and exploitation relies on the manager's manual `setAprs` mid-epoch — still a routine action, but narrows the window.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert on `unscaledApr != 0`. Instead, settle the open APR0 bucket at the rate that was valid for its request lifecycle: if the APR was raised, either settle APR0 principal with zero interest (drop the `_apr0NetInterest` block but still zero `apr0TotalPrincipal`) or snapshot the APR at request time per epoch (`apr0RateByEpoch`-style guard) and reject only the interest split, never the whole stop. Additionally, add a check in `setAprs`/`setAprsWithBuffer`/`setApr` refusing to set `unscaledApr != 0` while `apr0TotalPrincipal != 0`, so the invalid state cannot be entered at all.

### Proof of Concept
```solidity
// Foundry fork test against an IdleCreditVault-backed CDO in APR0 mode
function testApr0RequestBricksStopEpochAfterAprRaise() external {
    // epoch N running with unscaledApr == 0 (APR0 mode)
    _setAprs(0, 0); // manager sets pool to 0% APR

    // Attacker: KYC'd lender, dust deposit + withdraw request during APR0 epoch
    uint256 dust = 1e6; // 1 USDC
    _depositWithUser(attacker, dust);
    _startEpoch();
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(trancheBalanceOf(attacker), address(AAtranche));
    assertGt(strategy.apr0TotalPrincipal(), 0); // attacker's seed planted

    // Honest manager announces a rate for the next epoch (or raises APR mid-epoch)
    vm.prank(manager);
    strategy.setAprs(5e18, 5e18); // unscaledApr != 0 while bucket open

    // Epoch ends; every stop attempt reverts -> borrower funds cannot be recalled
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.expectRevert(NotAllowed.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    vm.expectRevert(NotAllowed.selector);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, epochDuration, 0);

    // All TVL frozen; only recovery is manager reverting APR to 0
    vm.prank(manager);
    strategy.setAprs(0, 0);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // succeeds — pool forced to stay at 0% APR
}
```
