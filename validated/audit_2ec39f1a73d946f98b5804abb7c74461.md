### Title
Origination fee can be avoided via rounding-down truncation on small borrows - (File: `programs/marginfi/src/instructions/marginfi_account/borrow.rs`)

### Summary
The origination fee charged on `lending_account_borrow` is computed in `I80F48` fixed-point and then truncated to a `u64` with `checked_to_num()`, which rounds toward zero (floor). For any nonzero `protocol_origination_fee` rate, this allows a borrower to structure borrows in small enough increments that the computed fee rounds down to exactly `0`, letting them accrue debt while paying no origination fee at all — the same rounding-avoidance pattern described in the referenced Yieldy `instantUnstake` report, where fee-avoidance is achieved by repeatedly transacting amounts small enough that `amount * fee_rate < 1`.

### Finding Description
In `lending_account_borrow`, the fee is computed and truncated like this: [1](#0-0) 

```rust
let (origination_fee_u64, share_amount): (u64, I80F48);
if !origination_fee_rate.is_zero() {
    origination_fee = I80F48::from_num(amount_pre_fee)
        .checked_mul(origination_fee_rate)
        .ok_or_else(math_error!())?;
    origination_fee_u64 = origination_fee.checked_to_num().ok_or_else(math_error!())?;

    // Incurs a borrow that includes the origination fee (but withdraws just the amt)
    share_amount =
        bank_account.borrow(I80F48::from_num(amount_pre_fee) + origination_fee)?;
} else {
    ...
}
```

`origination_fee` is `amount_pre_fee * origination_fee_rate`, computed in `I80F48` (high precision). However, `origination_fee_u64 = origination_fee.checked_to_num()` truncates this to a whole `u64`, discarding any fractional native-unit amount. For any `amount_pre_fee` small enough that `amount_pre_fee * origination_fee_rate < 1` native unit, `origination_fee_u64` becomes exactly `0`, and — because the code branches only on `origination_fee.is_zero()` up front, not on whether the truncated fee is zero — a borrower can simply issue many small borrows below that threshold to accumulate an arbitrarily large debt position while permanently paying `0` in origination fees.

This is structurally identical to the referenced report's root cause: fee is derived via a subtraction/rounding scheme (`amount - fee` pattern in Yieldy; here `to_num()` truncation of a fee amount) rather than a scheme that rounds the fee up so it can never be `0` unless the rate itself is `0`.

By contrast, the repay-side origination fee calculation in the same codebase already applies `.ceil()` to round up, explicitly noting "Round up when repaying" — confirming the team is aware fee rounding direction matters, but the borrow-side calculation was left rounding down.

### Impact Explanation
This is a durable revenue-leak / value-redirection issue: any group admin who sets a nonzero `protocol_origination_fee` on a bank (a legitimate, permissionless-to-use, unprivileged-user-reachable configuration knob already exercised in tests, e.g. `protocol_origination_fee: I80F48!(0.018)`) can be systematically deprived of fee revenue by any ordinary borrower who splits their borrow(s) into sub-threshold chunks (`amount_pre_fee < 1 / origination_fee_rate` native units). The fee is meant to flow to `collected_group_fees_outstanding` / `collected_program_fees_outstanding`, i.e., real protocol/group revenue that is subsequently withdrawn via `LendingPoolCollectBankFees` / `LendingPoolWithdrawFees`. This chunking bypass silently starves that revenue stream with no on-chain event, warning, or feasible detection distinguishing it from ordinary usage.

### Likelihood Explanation
The origination fee is documented as "historically always zero" as of the current guides, which limits current live impact. However, it is a fully supported, admin-configurable rate (`BankConfigOpt.interest_rate_config.protocol_origination_fee`) that any group can enable at any time, and the borrow instruction itself requires no special privilege — any user account can call `lending_account_borrow` repeatedly. Once a nonzero rate is configured, exploiting the rounding is trivial and requires only splitting a borrow into `N` small transactions instead of one large one, with no additional cost besides transaction fees (which, on Solana, are negligible relative to typical loan sizes).

### Recommendation
Round the origination fee up (ceiling) rather than truncating down when converting `I80F48` fee amounts to `u64`, mirroring the approach already used on the repay side (`.ceil()`), e.g.:

```rust
origination_fee_u64 = origination_fee.ceil().checked_to_num().ok_or_else(math_error!())?;
```

This ensures the fee can only be exactly `0` when the configured `origination_fee_rate` itself is `0`, eliminating the rounding-based fee-avoidance vector, consistent with the mitigation recommended in the referenced report (make the fee round up rather than the net amount round down).

### Proof of Concept
1. Group admin configures a bank with `protocol_origination_fee = 0.01` (1%), as already done in test fixtures (`DEFAULT_SB_PULL_WITH_ORIGINATION_FEE_BANK_CONFIG`) — [2](#0-1) .
2. A borrower with sufficient collateral calls `lending_account_borrow` repeatedly with `amount_pre_fee = 99` native units (below the `1 / 0.01 = 100` unit threshold) instead of borrowing `9900` units in one call.
3. Each individual call computes `origination_fee = 99 * 0.01 = 0.99`, which truncates via `checked_to_num()` to `origination_fee_u64 = 0` — [3](#0-2) .
4. Repeating this `100` times accrues the same total debt (`9900` units) as one large borrow, but `collected_group_fees_outstanding` / `collected_program_fees_outstanding` never increase, whereas a single `9900`-unit borrow would have recorded `99` units of fee.
