This confirms the mechanics. `_validateImmutables` (via `_deriveAddress`/CREATE2 check in `EscrowDst`) only checks that the supplied `immutables` hash matches the deployed clone address — it does not check `parameters` length or content beyond hashing it. So a destination escrow can be deployed and funded successfully with a malformed `parameters` field, and later both `withdraw()` and `publicWithdraw()` will unconditionally revert in `_withdraw()` when `ImmutablesLib.integratorFeeAmountCd()`/`protocolFeeAmountCd()` decode the too-short blob, while `cancel()` is unaffected since it never touches `parameters`.

### Title
Destination escrow creator can permanently disable `withdraw`/`publicWithdraw` by supplying an undersized `parameters` blob to `createDstEscrow` - (File: `contracts/EscrowDst.sol`, `contracts/libraries/ImmutablesLib.sol`)

### Summary
`BaseEscrowFactory.createDstEscrow()` accepts `dstImmutables.parameters` verbatim from the caller with no length or content validation [1](#0-0) . The clone's address/salt is derived from `hashMem(immutables)`, which just hashes whatever bytes are supplied, so any `parameters` length deploys and funds successfully [2](#0-1) . `EscrowDst._withdraw()` unconditionally calls `immutables.integratorFeeAmountCd()` and `protocolFeeAmountCd()`, each of which reverts with `IndexOutOfRange` if `parameters.length` is smaller than `0x40`/`0x20` respectively [3](#0-2) [4](#0-3) . A 33-byte blob satisfies the 0x20 check but fails the 0x40 check, so both `withdraw()` and `publicWithdraw()` always revert for that specific escrow instance [5](#0-4) . `cancel()` is unaffected because it never reads `parameters`, transferring `immutables.amount` back to the taker after the cancellation timelock [6](#0-5) .

### Finding Description
The `Immutables.parameters` bytes field is meant to carry `(protocolFeeAmount, integratorFeeAmount, protocolFeeRecipient, integratorFeeRecipient)` for the destination side, a 0x80-byte ABI encoding [7](#0-6) . However, nothing in `createDstEscrow` enforces this shape or minimum length before deploying and funding the clone. Whoever calls `createDstEscrow` — the resolver/taker in the normal flow — fully controls this field, and can pass a blob that is long enough to pass the `onlyValidImmutables` hash check and receive the deposited tokens/native currency, but too short for `ImmutablesLib`'s fee-decoding routines used later in `_withdraw`.

Because `_withdraw` reads `integratorFeeAmountCd()` before `protocolFeeAmountCd()`, any `parameters.length` in `[0x20, 0x40)` (e.g., 33 bytes) causes every subsequent call to `withdraw()` and `publicWithdraw()` to revert with `IndexOutOfRange`. This defeats the protocol's `publicWithdraw` safety-valve, which exists specifically so that an access-token holder can complete the payout to the maker if the taker withholds the secret or refuses to submit the private withdrawal. With the malformed parameters, neither path can ever succeed, so the maker's destination-side payout can never be completed for that escrow instance — the only remaining outcome is `cancel()` after the cancellation timelock, which returns the deposited amount to the taker, not the maker.

### Impact Explanation
This matches the "temporary freezing of funds during the live swap lifecycle" bucket: funds deposited into the destination escrow become permanently non-withdrawable via the intended payout path (both private and public), and can only be recovered by the taker through cancellation once the cancellation window opens — never reaching the maker. This also nullifies the `publicWithdraw` censorship-resistance mechanism for the affected escrow, which is a core protocol guarantee, not merely a cosmetic issue.

### Likelihood Explanation
Likelihood is limited by the fact that `createDstEscrow` is normally called by the same party (taker/resolver) who is funding the escrow with their own funds, so the party best positioned to exploit this is also the one funding it — i.e., realizing this griefing pattern requires the escrow creator (typically the taker) to deliberately misencode `parameters`. It does not require any owner/governance/privileged whitelist status since `createDstEscrow` is fully permissionless with respect to `parameters` content.

### Recommendation
Validate `dstImmutables.parameters.length` (e.g., require it equals `0x80`, the exact size needed by `protocolFeeAmount`, `integratorFeeAmount`, `protocolFeeRecipient`, and `integratorFeeRecipient`) inside `createDstEscrow` before deploying/funding the clone, so malformed blobs are rejected atomically at creation time rather than causing a stuck escrow discovered only at withdrawal time.

### Proof of Concept
1. Caller invokes `escrowFactory.createDstEscrow{value: safetyDeposit + amount}(dstImmutables, srcCancellationTimestamp)` where `dstImmutables.parameters` is a 33-byte blob (passes `parameters.length >= 0x20` but `< 0x40`) [1](#0-0) .
2. The clone deploys and is funded successfully — `_validateImmutables`/`hashMem` only hash the bytes, they don't enforce a minimum length [2](#0-1) .
3. After the withdrawal window opens, the taker calls `EscrowDst.withdraw(secret, immutables)`; it reverts with `ImmutablesLib.IndexOutOfRange` inside `integratorFeeAmountCd()` [8](#0-7) [9](#0-8) .
4. During the public withdrawal window, any access-token holder calling `publicWithdraw` hits the identical revert, confirming the safety-valve is neutralized [10](#0-9) .
5. Only `cancel()` succeeds after `DstCancellation`, sending `immutables.amount` back to `immutables.taker`, not the maker [6](#0-5) .

    function hashMem(IBaseEscrow.Immutables memory immutables) internal pure returns(bytes32 ret) {
        // Compute the EIP-712 hash for the immutables struct
        // Patch the last word (bytes parameters) in the struct with the hash of it
        bytes memory parameters = immutables.parameters;
        assembly ("memory-safe") {
            let parametersHash := keccak256(add(parameters, 0x20), mload(parameters))
            let patchLocation := sub(add(immutables, IMMUTABLES_SIZE), 0x20)
            let backup := mload(patchLocation)

            // Patch the last word with the hash of parameters to compute the EIP-712 hash
            mstore(patchLocation, parametersHash)
            ret := keccak256(immutables, IMMUTABLES_SIZE)

            mstore(patchLocation, backup) // Restore the original value
        }
    }
