I found a concrete analog in `multisig2/src/lib.rs` — the `confirm()`/`delete_member()` logic never invalidates confirmations that a removed member already cast on *other* pending requests, letting a stale confirmation from a no-longer-member count toward the execution threshold. This directly maps to the reported bug class ("confirmations counted versus live members").### Title
Stale confirmations from removed multisig members count toward the execution threshold, allowing a request to execute below the intended quorum - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges confirmations for requests *created by* the removed member, but never scrubs that member's confirmation entries on other, still-pending requests that the member had merely *confirmed*. Because `confirm()` counts entries in the `confirmations` `HashSet<String>` without checking whether each entry still corresponds to a current member of `self.members`, a confirmation cast by an account/key that has since been removed still counts toward `num_confirmations`. This lets a request execute with fewer genuinely-authorized (live) confirmers than the configured threshold, directly breaking the "confirmations counted versus live members" custody binding.

### Finding Description
`confirm()` computes eligibility purely from the stored confirmation set size: [1](#0-0) 

Membership removal (`delete_member`) only cleans up:
1. requests that were *created* by the removed member (`r.member == member`), and
2. that member's `num_requests_pk` entry.

It does **not** scan `self.confirmations` for entries where the removed member had confirmed a request created by someone else: [2](#0-1) 

The confirmation set stored per request is just a `HashSet<String>` of member string-representations, decoupled from live membership at read time: [3](#0-2) 

Sequence that breaks the binding `confirmations_counted == live_members_who_confirmed`:
1. Members = {A, B, C}, `num_confirmations = 3`.
2. A creates and self-confirms a malicious `Transfer` request `R` (confirmations = {A}).
3. B confirms `R` (confirmations = {A, B}); 2/3, not yet executed.
4. Through an unrelated, legitimately-passed `DeleteMember{member: B}` request (e.g., B is leaving, or B's key was compromised and is being revoked), B is removed from `self.members`. `delete_member` only deletes requests *created by* B — `R` was created by A, so `R`'s confirmation set is untouched and still contains B's string.
5. C confirms `R`. `confirm()` sees `confirmations.len() (2) + 1 >= num_confirmations (3)` → executes the transfer.

At execution time, the *live* members are only {A, C} — B is gone — yet the contract believes 3-of-3 was reached. Only 2 genuinely current members actually authorized the transfer.

This is the direct analog of the reported griefing bug class: in the original report, a delegatee's recorded voting-power array contained entries (delegated NFTs) that no longer reflected genuine backing, letting an attacker manipulate a counted total. Here, the "recorded claims" is the confirmation `HashSet`, and the "backing" is live multisig membership — an entry can persist and be counted after its authorizing basis (membership) is gone.

### Impact Explanation
This is Critical per the stated impact classes: "a multisig request executed below threshold." A `Transfer`, `AddKey`, `FunctionCall`, or `DeployContract` action can be pushed through with genuinely-live authorization strictly below the configured `num_confirmations`, i.e., NEAR can move (or contract code can be redeployed/keys added) without the intended quorum of currently-trusted parties.

### Likelihood Explanation
Requires no privileged access beyond being one of the multisig's own members (unprivileged relative to the multisig's trust boundary — it is exactly the "unauthorized move" scenario the rules ask to evaluate for; no foundation/owner/redeploy assumption is needed). The only precondition is that member turnover (removal) occurs while a request that removed member had confirmed is still pending — a very plausible operational event (revoking a departing employee's key, rotating compromised keys, etc.), and the attacker (any remaining or colluding member) only needs to time the final confirmation after the removal.

### Recommendation
When removing a member in `delete_member`, iterate over all pending `requests`/`confirmations` (not just requests created by that member) and strip the removed member's entry from every confirmation set, re-checking whether removal should also decrement any thresholds already close to met. Alternatively, validate membership of every entry in a request's confirmation set at `confirm()`-time (i.e., recompute `confirmations.iter().filter(|m| self.members.contains(m)).count()`) before comparing against `num_confirmations`, rather than trusting the raw stored set size.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
