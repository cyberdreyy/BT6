## Analysis: Builder payment destroyed by unrelated proposer slashing (Gloas `process_proposer_slashing`)

This maps to the FeeVault "unclaimed value lost on component swap" bug class: a `BuilderPendingPayment` that has already accrued attestation weight (i.e., proof that the builder delivered the payload) can be wiped out — with no payout and no possibility to reclaim it — by a `ProposerSlashing` operation that is unconditional and unrelated to payload delivery.

### Title
Builder payment destroyed by proposer-slashing before settlement/quorum check - (specs/gloas/beacon-chain.md)

### Summary
`process_execution_payload_bid` records a `BuilderPendingPayment` keyed only by slot index and tagged with the slot's `proposer_index`, with `weight=0` initially. `process_attestation` increments `payment.weight` as attesters confirm the payload was delivered on time. Settlement into `builder_pending_withdrawals` (the actual future payment) normally happens either immediately via `settle_builder_payment` in `apply_parent_execution_payload`, or later at the epoch boundary in `process_builder_pending_payments`, which is expected to use the accumulated `weight` to decide whether quorum was reached. [1](#0-0) 

However, `process_proposer_slashing` unconditionally clears the `builder_pending_payments` entry for the slashed proposer's slot as soon as any valid `ProposerSlashing` naming that proposer/slot is included, with no regard to `payment.weight` (quorum already reached) or to whether the payload was already marked available: [2](#0-1) 

### Finding Description
The settlement path (`settle_builder_payment`) and the epoch-boundary path (`process_builder_pending_payments`) are the only two mechanisms meant to decide whether a `BuilderPendingPayment` becomes a real `BuilderPendingWithdrawal`. Settlement of a slot's payment happens only when the *very next* block is built on top of the FULL parent (`apply_parent_execution_payload`): [3](#0-2) 

If the immediate successor block instead treats the parent as EMPTY (e.g., because the builder's envelope did not propagate/reveal on time, or the proposer of slot S+1 chose to build on the empty variant), the payment for slot S is **not** settled and remains sitting in `builder_pending_payments`, accruing `weight` from any subsequent attestations that still vote it as delivered/on-time, until the epoch-boundary quorum check runs.

During that window, a `ProposerSlashing` for the slot-S proposer (submitted by anyone, using two conflicting signed headers for slot S — an action fully controlled by that validator's own key, not requiring any coalition) will delete the pending payment entirely via `state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()`, discarding both the recorded withdrawal (`fee_recipient`, `amount`, `builder_index`) and the already-accumulated `weight` that would otherwise have proven quorum. No withdrawal is ever created for that builder payment — the Gwei that should have gone to the bid's `fee_recipient` is permanently destroyed, with no corresponding refund to the builder or the proposer's stake either.

This mirrors the FeeVault issue exactly: switching state (here, invalidating the builder-payment component tied to a proposer) drops already-accrued, but not-yet-claimed/settled, value, and there is no compensating mechanism (analogous to calling `claimFees()` first) to flush the pending payment into `builder_pending_withdrawals` before the state mutation occurs.

### Impact Explanation
This falls under "Gwei ... paid to a non-owner" / "Gwei destroyed" (Critical impact category): the fee recipient who was promised payment for an honestly delivered, possibly already-quorum-confirmed payload never receives it, and the value simply vanishes from `state.builder_pending_payments` without any corresponding credit anywhere in the state.

### Likelihood Explanation
Triggering requires:
1. A slot where the immediate child block does not settle the parent's payment right away (parent treated as empty by the next proposer) — a normal occurrence under any missed-payload/slow-reveal conditions, not requiring an adversarial coalition.
2. A `ProposerSlashing` naming that same proposer/slot being included within the 2-epoch window — achievable by the proposer's own double-signing (an action solely under that single validator's control) or, if that validator equivocates for any reason (bug, restart with duplicate keys, or malicious self-interest to grief a builder), by any relayer submitting the slashing evidence.

This does not require majority stake, a coalition, or external malicious peers — a single validator behaving badly with its own signing key is sufficient, and the code path shows no defense against it (the fix already applied — restricting the clear to `payment.proposer_index == header_1.proposer_index`, per the accompanying test `test_builder_payment_not_deleted_foreign_equivocation` — only prevents *other* validators from griefing an unrelated proposer's payment; it does not prevent the payment's own proposer from destroying it). [4](#0-3) 

### Recommendation
Before clearing a `builder_pending_payments` entry in `process_proposer_slashing`, either (a) settle it first if `payment.weight` already meets/exceeds the quorum threshold used by `process_builder_pending_payments` (i.e., route through the same weight-based decision instead of an unconditional wipe), or (b) defer the clearing itself to the normal settlement/eviction machinery and only mark the proposer's association as invalidated for future accounting, so an already-delivered/attested payload's payment cannot be destroyed by an unrelated slashing event.

### Proof of Concept
1. Proposer P proposes block at slot S with a non-zero-value bid from builder B; `process_execution_payload_bid` records `builder_pending_payments[idx] = {weight:0, withdrawal:{fee_recipient, amount, builder_index=B}, proposer_index=P}`. [5](#0-4) 
2. Attesters for slot S see the payload delivered on time; `process_attestation` increments `payment.weight` toward/above quorum. [6](#0-5) 
3. The proposer of slot S+1 builds on the EMPTY variant of slot S (bid.parent_block_hash != state.latest_execution_payload_bid.block_hash), so `process_parent_execution_payload` never calls `apply_parent_execution_payload`/`settle_builder_payment` for slot S — the payment remains pending, un-evicted, with its accrued `weight`. [7](#0-6) 
4. Within the 2-epoch window, a `ProposerSlashing` naming P (two conflicting headers for slot S, e.g. P double-signed) is included in a later block. `process_proposer_slashing` finds `payment.proposer_index == P` and sets `builder_pending_payments[idx] = BuilderPendingPayment.empty()`, discarding the withdrawal and the accrued weight. [8](#0-7) 
5. Result: builder B's payment to `fee_recipient` never becomes a `builder_pending_withdrawals` entry and is never paid, even though the payload was delivered and (per accumulated `weight`) could already have met quorum.

```markdown
def apply_parent_execution_payload(
    state: BeaconState,
    requests: ExecutionRequests,
) -> None:
    parent_bid = state.latest_execution_payload_bid
    parent_slot = state.latest_block_header.slot
    parent_epoch = compute_epoch_at_slot(parent_slot)

    assert len(requests.withdrawals) <= MAX_WITHDRAWAL_REQUESTS_PER_PAYLOAD
    assert len(requests.consolidations) <= MAX_CONSOLIDATION_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_deposits) <= MAX_BUILDER_DEPOSIT_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_exits) <= MAX_BUILDER_EXIT_REQUESTS_PER_PAYLOAD

    # Process execution requests from parent's payload. The execution
    # requests are processed at state.slot (child's slot), not the parent's slot.
    def for_ops(operations: Sequence[Any], fn: Callable[[BeaconState, Any], None]) -> None:
        for operation in operations:
            fn(state, operation)

    for_ops(requests.deposits, process_deposit_request)
    for_ops(requests.withdrawals, process_withdrawal_request)
    for_ops(requests.consolidations, process_consolidation_request)
    for_ops(requests.builder_deposits, process_builder_deposit_request)
    for_ops(requests.builder_exits, process_builder_exit_request)

    # Settle the builder payment
    if parent_epoch == get_current_epoch(state):
        payment_index = SLOTS_PER_EPOCH + parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_epoch == get_previous_epoch(state):
        payment_index = parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_bid.value > 0:
        # Parent is older than the previous epoch, its payment entry has been
        # evicted from builder_pending_payments. Append the withdrawal directly.
        state.builder_pending_withdrawals.append(
            BuilderPendingWithdrawal(
                fee_recipient=parent_bid.fee_recipient,
                amount=parent_bid.value,
                builder_index=parent_bid.builder_index,
            )
        )

    # Update parent payload availability and latest block hash
    state.execution_payload_availability[parent_slot % SLOTS_PER_HISTORICAL_ROOT] = Boolean(True)
    state.latest_block_hash = parent_bid.block_hash
```

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid

```python
@with_gloas_and_later
@spec_state_test
def test_builder_payment_not_deleted_foreign_equivocation(spec, state):
    """
    Test that a proposer slashing does NOT delete a builder pending payment recorded for
    a different proposer. This guards against a griefing vector: the clear is keyed only
    by header slot, so without the proposer check any validator equivocating on a slot
    could clear an honest proposer's payment for that slot.

    Input State Configured:
        - builder_pending_payments: current-epoch entry recorded for the payment proposer
        - proposer_slashing: valid slashing of a different validator for the same slot,
          within the 2-epoch window

    Output State Verified:
        - validators[slashed_index].slashed: True
        - builder_pending_payments: entry left intact (slashed validator is not the
          payment's proposer)
    """
    active = spec.get_active_validator_indices(state, spec.get_current_epoch(state))
    payment_proposer = active[0]  # the payment is recorded for this proposer
    slashed_proposer = active[-1]  # equivocates on the slot, not the payment's proposer
    assert payment_proposer != slashed_proposer
```
