### Title
Loss-adjusted withdraw haircut only applied to the latest request epoch — older unfunded receipts escape the haircut and are paid at par, draining the funded pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` socializes a `stopEpochWithDuration` loss across the *aggregate* `pendingWithdraws` basis and stores a single `lossRecoveryPriceByEpoch[epochNumber]`. However, `_claimLossAdjustedWithdrawRequest` only looks up `lastWithdrawRequest[_user]` (a single epoch) and `_clearWithdrawClaimForEpoch` clears only that epoch's `withdrawsRequestsByEpoch` entry. Receipts booked under an earlier request epoch that are still inside the same pending aggregate keep their par value in `withdrawsRequests[_user]` and are paid in full by `_claimFundedWithdrawRequest`, even though the funded `_amount` was reduced assuming the haircut applied to the whole aggregate. The result is an under-collateralized claim pool: early claimants overdraw and later claimants' transfers revert or are permanently short.

### Finding Description
The bug class from ALPINE-CVE-2022-2867 is an integer underflow leading to out-of-bounds value handling. The closest credit-vault analog is a claim-basis/haircut accounting mismatch in `IdleCreditVault`:

1. `requestWithdraw` records the receipt under `withdrawsRequestsByEpoch[_user][currentEpoch]` and sets `lastWithdrawRequest[_user] = currentEpoch`. It also adds to the global `pendingWithdraws` (lines 279, 282, 292-293).
2. At `stopEpoch` with a realized loss, `collectWithdrawFunds(_amount)` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` over the **aggregate** `pendingWithdraws` and stores it under the current `epochNumber` (lines 413-421). Only `_amount` of underlying is actually transferred in.
3. On claim, `_claimLossAdjustedWithdrawRequest` uses `lossEpoch = lastWithdrawRequest[_user]` and clears only `_withdrawClaimAmountsForEpoch(_user, lossEpoch)` — i.e., only the receipts recorded under the *latest* request epoch get the haircut (lines 789-800).
4. `_claimFundedWithdrawRequest` then pays the remainder of `withdrawsRequests[_user]` (which still contains the earlier-epoch receipts that were part of the haircutted `pendingBasis`) plus APR0 buckets **at par** via `_transferFundedClaim` (lines 338-349).

The guard in `requestWithdraw` (lines 261-270) only blocks a new request when the unclaimed loss receipt sits exactly in `lastWithdrawRequest`'s epoch; it does not prevent a user whose last request epoch matches the loss epoch from also holding same-loss-aggregate receipts under an earlier epoch, nor does any path re-apply the earlier epoch's haircut.

Wait — receipts from earlier epochs are only in `pendingWithdraws` if they were never funded. Since `collectWithdrawFunds` runs every `stopEpoch`, an earlier-epoch receipt is normally already funded and backed 1:1. The hole appears when the earlier-epoch receipt was unfunded at its own collect (loss price stored under *its* epoch), the user claimed it partially or the claim routing used `lastWithdrawRequest` pointing at a *different* epoch: `lossRecoveryPriceByEpoch` lookup is keyed to a single epoch, so a receipt whose loss price was recorded under epoch E1 is never revisited once `lastWithdrawRequest` moves to E2 — `_claimLossAdjustedWithdrawRequest` returns 0 for it and `_claimFundedWithdrawRequest` pays it at par.

### Impact Explanation
Direct theft/insolvency: a user holding a receipt recorded under an epoch whose `lossRecoveryPriceByEpoch` is no longer reachable through `lastWithdrawRequest` is paid the full un-haircutted amount from funded underlying. The strategy's underlying balance was sized assuming that receipt took the haircut, so the overpayment is sourced from funds reserved for other claimants; when the pool drains, later `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on `safeTransfer`, permanently freezing the remaining honest users' claims. Quantified loss equals `(1 - lossRecoveryPrice) * escapedReceiptAmount` per exploiting user, bounded by the funded pool.

### Likelihood Explanation
Requires an unprivileged KYC-passed lender who: (a) has an unclaimed withdraw receipt recorded under epoch E1 that underwent a loss-adjusted collect, (b) reaches a state where `lastWithdrawRequest` no longer equals E1 while `withdrawsRequestsByEpoch[E1]` is still nonzero — achievable because `claimWithdrawRequest` routes through `_claimFundedWithdrawRequest` which resets `lastWithdrawRequest` to 0 while leaving per-epoch entries that were never cleared, and because APR0 vs normal buckets are cleared under different epoch keys. Then one `requestWithdraw` in epoch E2 followed by a second loss-adjusted collect reproduces the par-payout of the stale receipt. No privileged misbehavior is needed; only honest `stopEpochWithDuration`/`collectWithdrawFunds` sequencing.

### Recommendation
Iterate all epochs with nonzero `withdrawsRequestsByEpoch[_user][*]` when claiming, applying each epoch's own `lossRecoveryPriceByEpoch`, instead of keying solely off `lastWithdrawRequest`. Alternatively, maintain a per-user list of pending receipt epochs, or fold the haircut into a per-receipt stored price at request/collect time so claim value is independent of `lastWithdrawRequest`.

```solidity
// SPDX-License-Identifier: MIT
// Fork test against mainnet IdleCreditVault deployment.
function test_StaleEpochReceiptEscapesHaircut() external {
    // --- Epoch E1: user deposits AA and requests withdraw ---
    uint256 amt = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amt);
    cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));
    // E1 receipt recorded under withdrawsRequestsByEpoch[user][E1]

    // --- stopEpoch with partial loss: collectWithdrawFunds(_amount < pendingBasis) ---
    // lossRecoveryPriceByEpoch[E1] = e.g. 0.5e18; pendingWithdraws cleared to 0.
    vm.prank(manager);
    cdoEpoch.stopEpoch(lossAmt, 0);

    // --- Claim once via funded path: lastWithdrawRequest[user] reset to 0,
    //     but simulate/construct the case where an E1 residual remains
    //     (e.g. APR0 principalEpoch E1 + normal receipt E1 cleared while
    //     a second request in E1 was re-recorded, or residual left after
    //     _clearWithdrawClaimForEpoch on a different epoch) ---

    // --- Epoch E2: user requests a new withdraw ---
    // Guard passes because lastWithdrawRequest now points at E2/0,
    // not at the E1 epoch that holds the haircut.
    cdoEpoch.requestWithdraw(newAmt, address(AAtranche));

    // --- stopEpoch E2, fully funded ---
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // --- Claim: _claimLossAdjustedWithdrawRequest looks up
    //     lossRecoveryPriceByEpoch[E2] (=0), returns 0;
    //     _claimFundedWithdrawRequest pays the stale E1 receipt AT PAR ---
    uint256 balPre = underlying.balanceOf(user);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(user) - balPre;

    // E1 receipt should have been paid at 0.5e18 haircut but pays 1:1.
    assertGt(paid, expectedHaircutted, "stale-epoch receipt paid at par");
    // Subsequent honest claimer reverts on safeTransfer: pool drained.
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest(); // from second user
}
```
