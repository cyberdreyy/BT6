## Finding: Confirmed — but the actual root cause differs from the hypothesis

The stated hypothesis (a "stale `beneficiary_for_operator` entry" causing `request_commission_internal` to look up the wrong beneficiary) does not hold: `request_commission_internal`/`add_distribution` never resolve `beneficiary_for_operator` at all — they simply record the raw operator address as the distribution-pool shareholder [1](#0-0) . The beneficiary substitution only happens later, inside `distribute_internal`, which redirects payout **only if** the stored shareholder equals the `operator` parameter passed into that same call [2](#0-1) .

However, tracing `switch_operator` does reveal a real, related bug that produces the same class of impact (commission misrouted away from the intended beneficiary):

### Finding Description
`switch_operator` removes the `StakingContract` from the map keyed by `old_operator`, forces a full `distribute_internal` (which correctly resolves `beneficiary_for_operator(old_operator)` because `operator == old_operator` at that point), then calls `request_commission_internal(old_operator, ...)` to record any newly accrued (but not yet inactive) commission, and only after that re-inserts the same `StakingContract` object into the map under the new key `new_operator` [3](#0-2) .

The commission entry added by that final `request_commission_internal` call records the distribution-pool shareholder as `old_operator` (the raw address) [4](#0-3) . That entry is not paid immediately — `stake::unlock_with_cap` only starts the unlock; actual payout happens whenever `distribute`/`distribute_internal` is next invoked for this contract, at which point it is looked up under the **new** key, `new_operator`.

When that later distribution occurs, `distribute_internal` is called with `operator = new_operator`, and the beneficiary-redirect check is `if (recipient == operator)` [5](#0-4) . Since the stored `recipient` is `old_operator` and the passed-in `operator` is now `new_operator`, this comparison fails, so the beneficiary substitution is skipped entirely and the coins are deposited straight to the raw `old_operator` address — bypassing `beneficiary_for_operator(old_operator)` even if `old_operator` had a beneficiary configured.

### Impact Explanation
Any commission that accrues between the last `distribute` and a `switch_operator` call will, once finally paid out, be sent directly to the old operator's own account instead of to the beneficiary they configured via `set_beneficiary_for_operator`. This is a beneficiary-payout corruption: value that should go to the designated beneficiary is credited to the operator's raw address instead. This falls under the "Operator commission, beneficiary payout ... corruption that credits the wrong account" impact category.

### Likelihood Explanation
Requires only a normal, unprivileged staker calling `switch_operator`/`switch_operator_with_same_commission` on their own contract while the old operator has unpaid, not-yet-distributed commission and a beneficiary configured — a plausible, low-friction sequence of legitimate calls with no special privileges needed beyond being the staker of that contract (which is the intended caller of this function).

### Recommendation
When `request_commission_internal` is invoked from within `switch_operator` (i.e., right before the operator key changes), resolve `beneficiary_for_operator(old_operator)` at that time and record it directly as the distribution recipient (or force a full `distribute_internal` after `request_commission_internal` but before the key swap), so that the beneficiary-redirect check in `distribute_internal` is not defeated by the later operator-key change.

### Proof of Concept
1. Staker creates a staking contract with `old_operator`, commission > 0.
2. `old_operator` calls `set_beneficiary_for_operator(beneficiary)`.
3. Rewards accrue on the pool.
4. Staker calls `switch_operator(staker, old_operator, new_operator, commission)`. This internally calls `request_commission_internal(old_operator, ...)`, recording a distribution entry with `recipient = old_operator`, then moves the `StakingContract` to key `new_operator`.
5. After lockup passes, call `distribute(staker, new_operator)` (or trigger any path invoking `distribute_internal(staker, new_operator, ...)`).
6. Assert: coins land in `old_operator`'s account, not `beneficiary`'s account — confirming the beneficiary redirect is bypassed once the operator key has changed.

Note: I was unable to view lines 807–870 of `staking_contract.move` (the file view was truncated), which contain `set_beneficiary_for_operator` and the `distribute` entry function signature; the analysis above is based on the surrounding code and the visible `distribute_internal` logic. If further verification of `distribute`'s exact call signature is needed, a full read of that file section (or a Devin session with filesystem access) would be required.

            get_staking_contract_amounts_internal(staking_contract);

            operator,

            operator,
            commission_amount
        );
