### Title
Stale `instantWithdrawClaimsByEpoch` after a funded instant claim inflates default-recovery basis and phantom prefunded reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out funded instant receipts but never clears the per-epoch accounting entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` that were incremented in `requestInstantWithdraw`. If a borrower default is later finalized in the *same* epoch while another instant request is still unfunded, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` read these stale entries: already-paid claims are counted both as outstanding claim basis and as underlying "prefunded reserve" that no longer exists in the strategy. The finalized `defaultRecoveryPrice` is therefore computed against phantom assets, overpaying recovery claimants at the expense of active LPs / other receipt holders, or leaving the reserve underfunded so later claims permanently revert.

### Finding Description
In `requestInstantWithdraw`, the strategy records per-epoch claim data:

```solidity
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
``` [1](#0-0) 

Once the manager collects the instant funds, `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws`, and `claimInstantWithdrawRequest` pays the user. But it only zeroes the aggregate `instantWithdrawsRequests[_user]` — the per-epoch mappings are untouched:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

Compare with `_claimDefaultedInstantWithdrawRequest`, which *does* decrement `instantWithdrawsRequestsByEpoch`, `instantWithdrawsRequests`, `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch` — confirming these counters are meant to track only outstanding claims [3](#0-2) .

At default finalization the stale entries corrupt two computations:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
``` [4](#0-3) 

```solidity
if (instantBasis > pendingInstant) {
  prefundedReserve = instantBasis - pendingInstant;
}
``` [5](#0-4) 

The analog to CVE-2018-0202's missing input/state validation (out-of-bounds read of stale data) is exact: finalization reads per-epoch state that should have been invalidated at claim time, treating funds already disbursed as both outstanding liability and on-hand reserve.

### Impact Explanation
Concrete sequence in one epoch (unprivileged users only; manager/borrower honest):

1. Epoch N running, APR lowered so instant withdrawals are enabled. User A requests an instant withdraw of 1000 — `instantWithdrawClaimsByEpoch[N] = 1000`.
2. Manager calls `getInstantWithdrawFunds`; `collectInstantWithdrawFunds` pulls 1000 into the strategy, `pendingInstantWithdraws` → 0. A claims 1000 immediately (no epoch-wait on the instant path). `instantWithdrawClaimsByEpoch[N]` stays 1000.
3. Attacker B requests an instant withdraw of dust amount `d`. Now `pendingInstantWithdraws = d`, `instantWithdrawClaimsByEpoch[N] = 1000 + d`.
4. Borrower fails to fund; pool defaults; `finalizeDefaultRecovery` runs in epoch N. `pendingInstantWithdraws != 0`, so `defaultPendingClaimBasis` adds `1000 + d` (real outstanding instant basis is only `d`), and `_defaultPrefundedInstantReserve` reports `1000` of phantom prefunded reserve that was already paid to A.
5. `reserveAmount` is overstated by ~1000 and `recoveryPrice = reserveAmount / totalBasis` is computed against assets the strategy does not hold. B's `_claimDefaultedInstantWithdrawRequest` pays `d * price` out of `defaultRecoveryReserve`, drawing on underlying that economically belongs to active-LP recovery; alternatively the inflated price drains the real reserve so subsequent legitimate claimants' `_transferDefaultRecovery` reverts on insufficient balance — permanent freezing of unclaimed recovery.

Loss is bounded by total instant withdrawals funded-and-claimed within the defaulting epoch — directly quantifiable, up to the full prefunded amount, and every such claim inflates the mispricing.

### Likelihood Explanation
Requires: instant withdrawals enabled (APR below `instantWithdrawAprDelta` threshold), at least one funded-then-claimed instant request and one still-pending instant request in the same epoch, then a borrower default before epoch end. All attacker actions (request instant withdraw, claim) are permissionless. The trigger — a borrower default coinciding with a partially-pending instant queue — is a scenario the codebase explicitly supports (`getInstantWithdrawFunds` default path, `defaultInstantWithdrawsFinalized`), so it is plausible rather than exotic.

### Recommendation
In `claimInstantWithdrawRequest` (and any funded instant-claim path), clear the per-epoch records alongside the aggregate:

```solidity
uint256 epoch = /* request epoch(s) being claimed */;
instantWithdrawsRequestsByEpoch[_user][epoch] = 0;
instantWithdrawClaimsByEpoch[epoch] -= amount;
```

Since a user may hold receipts across epochs while only the aggregate is stored, either track the oldest unfunded epoch per user or decrement `instantWithdrawClaimsByEpoch` at funding time in `collectInstantWithdrawFunds`, keeping it strictly equal to the unfunded remainder mirrored by `pendingInstantWithdraws`. Add a regression test: fund+claim an instant request, open a second pending instant request, force default, and assert `defaultPendingClaimBasis` equals only the pending amount.

    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    if (defaultRecoveryFinalized || !cdo.defaulted()) revert NotAllowed();
    if (_recoveredAmount != 0 && _recoverySource == address(0)) revert NotAllowed();

    // Active holders are still represented by strategy tokens owned by the CDO. Add the
    // default-epoch net interest so they use the same claim basis as pending redeemers.
    // Split gross backing by saved NAV and default interest by the configured APR split.
    // The CDO strategy-token balance is its gross active value before `unclaimedFees`.
    // Using it directly restores those waived unpaid fees to active recovery basis.
    uint256 activeBalance = balanceOf(idleCDO);
    uint256 activeInterest = _defaultActiveInterestBasis(cdo);
    uint256 activeBasis = activeBalance + activeInterest;
    defaultBBNav = _defaultBBBasis(cdo, activeBalance, activeInterest);
    // Pending receipts have already left active CDO NAV, so they are added as a separate basis.
    uint256 pendingBasis = defaultPendingClaimBasis();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (totalBasis == 0) revert NotAllowed();

    // Some recovery funds may already be in this strategy: partially prefunded instant requests
    // and borrower-send funds that failed at epoch start. Count both without pulling them again.
    uint256 prefundedReserve = _defaultPrefundedInstantReserve();
    uint256 reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve;
    // Recovery can be above par if the recovered funds exceed the computed basis.
    uint256 recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis;

    defaultRecoveryFinalized = true;
    defaultRecoveryReserve = reserveAmount;
    defaultRecoveryPrice = recoveryPrice;
    defaultRecoveryEpoch = epochNumber;
    // A non-zero pending instant bucket means current-epoch instant receipts were not fully funded
    // and must be paid through the same recovery ratio as normal pending receipts.
    defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0;
    // Bring active CDO NAV to the same recovery ratio. IdleCDOEpochVariant then calls
    // _forceUpdateAccounting so tranche prices/virtualPrice expose the crystallized loss.
    uint256 activeFinalNAV = (activeBasis * recoveryPrice) / RECOVERY_FULL;
    defaultBBNav = defaultBBNav * recoveryPrice / RECOVERY_FULL;
    if (activeBalance > activeFinalNAV) {
      _burn(idleCDO, activeBalance - activeFinalNAV);
    } else if (activeFinalNAV > activeBalance) {
      _mint(idleCDO, activeFinalNAV - activeBalance);
    }
    if (_recoveredAmount != 0) {
      // Pull external recovery last: if the transfer fails, the whole finalization reverts.
      underlyingToken.safeTransferFrom(_recoverySource, address(this), _recoveredAmount);
    }
