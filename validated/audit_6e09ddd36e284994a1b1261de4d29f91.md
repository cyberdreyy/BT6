### Title
Arbitrary APR manipulation before `idleCDO` is set — `setApr`/`setAprs` skip the caller check while the whitelisted CDO pointer is unset - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug (CVE-2024-57799) is a use-before-initialization ordering flaw: a callback runs before `platform_set_drvdata()` stores the device pointer, so state is consumed while unset. The direct analog in `IdleCreditVault` is the `idleCDO` pointer, which is **not** set in `initialize()` — it is wired later via the owner-only `setWhitelistedCDO()`. During that gap, `setApr`, `setAprs`, and `setAprsWithBuffer` intentionally skip their only access check ("if cdo is not yet set we skip the check"), letting **any** unprivileged EOA write `lastApr` and `unscaledApr` on a live vault. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`initialize()` sets `token`, `borrower`, `manager`, `maxApr = DEFAULT_MAX_APR` (20e18), `lastApr`, and `unscaledApr`, but leaves `idleCDO == address(0)`. `setApr` reads `idleCDO`; only when it is non-zero does it enforce `msg.sender == idleCDO || msg.sender == manager`. Therefore, between `initialize()` and `setWhitelistedCDO()` — two separate owner transactions that an attacker can interleave on a public chain — any EOA can:

- Call `setApr(20e18)` to set the maximum allowed APR for the upcoming epoch, forcing the honest borrower to owe 20%/epoch-duration interest that accrues to tranche holders (the attacker, a KYC-passing lender who deposits right after).
- Call `setAprs(_unscaledApr, _apr)` or `setAprsWithBuffer` to independently set `unscaledApr`. Setting `unscaledApr = 0` silently re-routes all subsequent `requestWithdraw` calls into the APR0 bucket (`_requestWithdrawApr0`), while `lastApr` remains non-zero — and `prepareStopEpochWithApr0` later reverts `NotAllowed` if `unscaledApr != 0` while `apr0TotalPrincipal != 0`, or conversely mis-settles interest, corrupting epoch interest accounting. [4](#0-3) [5](#0-4) [6](#0-5) 

The honest manager can later overwrite the APR, but cannot do so atomically; the attacker can re-set it any number of times until `setWhitelistedCDO` lands, and can time the write to immediately precede `startEpoch`/deposit so inflated `expectedEpochInterest` is locked in for the epoch.

### Impact Explanation
- Direct theft from the honest borrower: with, e.g., 1M USDC TVL and `lastApr` pushed to the 20e18 cap, the attacker LP claims a large share of up to ~20% annualized-scaled epoch interest the borrower is contractually obligated to repay. Attacker profit is bounded by `maxApr` and their share of tranche supply, but requires only KYC-lender status and gas.
- Epoch-accounting corruption / forced mis-settlement via `unscaledApr` manipulation: withdraw requesters get bucketed into APR0 accounting inconsistently with the interest the borrower actually owes, or `stopEpoch` becomes uncallable (`unscaledApr != 0` revert with nonzero `apr0TotalPrincipal`), temporarily freezing pending withdrawals until owner intervention. [7](#0-6) 

### Likelihood Explanation
Requires only that `initialize()` and `setWhitelistedCDO()` execute in different transactions on a public mempool (the factory/deploy flow does not atomically wire the CDO into the strategy — `setWhitelistedCDO` is a separate `onlyOwner` call). Any EOA can front-run or back-run; no privileged role is needed. The attacker must be a KYC-passing lender to extract value via tranche deposits, which is within the allowed threat model.

### Recommendation
Mirror the upstream fix ("set drvdata before enabling runtime PM"): wire `idleCDO` **before** the privileged surface becomes callable. Concretely, either (a) accept `_idleCDO` in `initialize()` and set it there, or (b) gate `setApr`/`setAprs`/`setAprsWithBuffer` behind `msg.sender == manager` when `idleCDO == address(0)` instead of skipping the check entirely. `setWhitelistedCDO` should also revert if the vault was already configured by a different CDO.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {TransparentUpgradeableProxy} from "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";

contract UninitializedCDOAprTest is Test {
    function test_AnyoneCanSetAprBeforeCDOWired() public {
        address underlying = address(new MockERC20());
        IdleCreditVault impl = new IdleCreditVault();
        bytes memory init = abi.encodeWithSelector(
            IdleCreditVault.initialize.selector,
            underlying, address(this), address(0xMGR), address(0xBRW), "B", 1e18
        );
        IdleCreditVault v = IdleCreditVault(address(
            new TransparentUpgradeableProxy(address(impl), address(this), init)));

        // idleCDO is unset until owner calls setWhitelistedCDO in a later tx
        assertEq(v.idleCDO(), address(0));

        address attacker = address(0xATTACKER);
        vm.prank(attacker);
        v.setApr(20e18);                    // inflates APR up to maxApr cap
        assertEq(v.lastApr(), 20e18);

        vm.prank(attacker);
        v.setAprs(0, 5e18);                 // attacker also controls unscaledApr
        assertEq(v.unscaledApr(), 0);       // misroutes future requestWithdraw into APR0 bucket
    }
}
```
Run on a fork against a deployed-but-unwired vault: attacker deposits into tranches after inflating `lastApr`, epoch starts, borrower repayment includes attacker-crafted interest.

Caveat: I could not fully verify in this iteration whether `IdleCreditVaultFactory` wires `setWhitelistedCDO` in the same transaction as `initialize`; if it does so atomically, the attack window collapses and the finding reduces to the still-present `unscaledApr`/`setApr` governance gap during any window where `idleCDO` is unset (e.g., fresh implementation pending wiring). The unsafe check itself at `IdleCreditVault.sol:229-231` is confirmed.

  function setApr(uint256 _apr) public {
    address _cdo = idleCDO;

    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
  }
