### Title
Runloop overwrites a still-active per-cycle signer before its pending block validations/proposals complete, discarding in-flight signing state - ([File: stacks-signer/src/runloop.rs])

### Summary
`RunLoop` keeps only two live `ConfiguredSigner` slots, keyed by `reward_cycle % 2` [1](#0-0) . When the burnchain view advances, `refresh_runloop` calls `refresh_signer_config(next_reward_cycle)` to populate the slot for cycle `N+2` (same parity as the outgoing cycle `N`) *before* it calls `cleanup_stale_signers`, and `refresh_signer_config` performs an unconditional `self.stacks_signers.insert(reward_index, new_signer_config)` with no check on whether the signer currently occupying that slot still has unresolved work.

### Finding Description
The only place that guards against clobbering a signer that still has in-flight work is `cleanup_stale_signers`, which explicitly checks `!signer.has_unprocessed_blocks()` before removing a stale entry [2](#0-1) . But `refresh_signer_config` — the function that actually replaces the slot's contents — has no equivalent check:

```
fn refresh_signer_config(&mut self, reward_cycle: u64) {
    let reward_index = reward_cycle % 2;
    let new_signer_config = match self.get_signer_config(reward_cycle) { ... };
    self.stacks_signers.insert(reward_index, new_signer_config);
}
``` [3](#0-2) 

In `refresh_runloop`, the ordering is:
1. Advance `current_reward_cycle_info` to the new cycle `N+1`.
2. If not configured for `next_reward_cycle = N+2`, call `refresh_signer_config(N+2)` — this reuses slot `(N+2)%2 == N%2`, i.e. the exact slot still holding cycle `N`'s signer.
3. Only *after* that does it call `cleanup_stale_signers(current_reward_cycle)`. [4](#0-3) 

So if cycle `N`'s signer object still has unresolved work (pending block proposals it has submitted for validation, or block-validation responses it is waiting on — tracked via `check_submitted_block_proposal`/`check_pending_block_validations` in `stacks-signer/src/v0/signer.rs`) at the moment the runloop needs to configure cycle `N+2`, `refresh_signer_config` replaces that `Signer` object with a brand-new one (`Signer::new(...)`) that has no memory of the outgoing signer's in-flight proposals/validations. Any pending validation response for the destroyed signer's tenure is orphaned: `run_one_pass` only dispatches events to the signer objects present in `self.stacks_signers.values_mut()` [5](#0-4) , and after the overwrite the cycle-`N` object no longer exists to receive it.

This is the structural analog of the reported bug: a manager-controlled state transition (advancing the reward cycle / refreshing the signer configuration) is allowed to replace/reset state for a still-open unit of work ("distribution") before that work is provably settled ("distributed or closed"), permanently losing the in-flight state. Here the equivalent of "tokens left on the contract" is a block proposal/validation the outgoing signer had committed to but never resolves, because its whole in-memory signer state (and specifically its bookkeeping for “do not double-sign a conflicting block” / “track submitted proposal”) is discarded rather than drained first.

### Impact Explanation
If cycle `N`'s signer had an outstanding submitted block proposal or a pending validation response in flight when its slot gets recycled for cycle `N+2`, that signer instance is destroyed and its pending work is silently dropped. The consequence is a per-signer liveness wedge: that signer never completes signing (or rejecting) a block it was actively evaluating, i.e., "a signer wedged into never signing valid blocks" — matching the High-impact bucket. Because `cleanup_stale_signers`'s `has_unprocessed_blocks()` guard exists specifically to avoid tearing down a signer with unresolved work, but is checked only for *deletion*, not for the *insert* that happens moments earlier in the same refresh pass, the protection is bypassed for the overwrite path.

### Likelihood Explanation
This requires no majority collusion and no external key material — it is purely a function of timing within a single signer's own runloop as the reward cycle boundary is crossed while a block validation round-trip to the node is still outstanding (e.g., a slow/laggard `stacks-node` validation response, or a miner submitting a proposal right at the cycle boundary to keep the round-trip open). Because `is_in_next_prepare_phase` triggers `refresh_signer_config(next_reward_cycle)` for several blocks before the actual cycle switch [6](#0-5) , and the real switch also re-triggers refresh for the (by-then) current cycle, the overwrite executes deterministically on every reward-cycle transition where the previous cycle's signer object still has unprocessed work — this is a narrow but structurally reachable timing window, not a purely theoretical one.

### Recommendation
Before calling `self.stacks_signers.insert(reward_index, new_signer_config)` in `refresh_signer_config`, check whether the entry currently at `reward_index` is a `RegisteredSigner` with `has_unprocessed_blocks() == true` and whose `reward_cycle()` differs from the target. If so, defer the refresh (skip the insert and retry on a later pass) instead of unconditionally overwriting it — mirroring the guard already applied in `cleanup_stale_signers`.

### Proof of Concept
1. Signer is registered for cycle `N`; near the cycle-`N`→`N+1` boundary it receives (and submits for validation) a block proposal, and `check_pending_block_validations` has not yet resolved it (validation response not yet received).
2. `run_one_pass` receives a `NewBurnBlock` event pushing `current_reward_cycle_info` to `N+1`, and `is_in_next_prepare_phase` is true for cycle `N+2` [7](#0-6) .
3. `refresh_signer_config(N+2)` executes: `reward_index = (N+2) % 2 == N % 2`, so `self.stacks_signers.insert(N%2, new_signer_for_cycle_N+2)` replaces the still-pending cycle-`N` `Signer` object.
4. `cleanup_stale_signers(N+1)` then runs, but the cycle-`N` object is already gone — its `has_unprocessed_blocks()` check never gets a chance to protect it.
5. The pending validation response for cycle `N`'s block proposal, when it eventually arrives, has no `Signer` instance in `self.stacks_signers` to process it against; that in-flight block is never signed/rejected by this signer.

    /// Refresh signer configuration for a specific reward cycle
    fn refresh_signer_config(&mut self, reward_cycle: u64) {
        let reward_index = reward_cycle % 2;
        let new_signer_config = match self.get_signer_config(reward_cycle) {
            Ok(Some(new_signer_config)) => {
                let signer_mode = new_signer_config.signer_mode.clone();
                let new_signer = Signer::new(&self.stacks_client, new_signer_config);
                info!("{new_signer} Signer is registered for reward cycle {reward_cycle} as {signer_mode}. Initialized signer state.");
                ConfiguredSigner::RegisteredSigner(new_signer)
            }
            Ok(None) => {
                warn!("Signer is not registered for reward cycle {reward_cycle}");
                ConfiguredSigner::not_registered(reward_cycle)
            }
            Err(e) => {
                warn!("Failed to get the reward set info: {e}. Will try again later.");
                return;
            }
        };

        self.stacks_signers.insert(reward_index, new_signer_config);
    }
