### Title
Loss-adjusted withdrawals only haircut the latest request epoch — earlier pending receipts still claim at par, leaving the vault underfunded and later claimants frozen - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2024-42120 ("check pipe index before accessing `pipe_ctx[MAX_PIPES]`"), `IdleCreditVault` fails to validate *which* epoch a pending withdraw receipt belongs to before applying a loss haircut. `collectWithdrawFunds` computes a single `lossRecoveryPrice` over the **aggregate** `pendingWithdraws` basis but stores it only under `lossRecoveryPriceByEpoch[epochNumber]` [1](#0-0) . The claim path then looks up the haircut only via `lastWithdrawRequest[_user]` and applies it only to `withdrawsRequestsByEpoch[_user][lossEpoch]` [2](#0-1) . A user holding unfunded receipts in an *earlier* epoch escapes the haircut entirely and claims at par from a reserve sized only for `totalBasis * price`.

### Finding Description
- `requestWithdraw` lets a user stack requests across epochs. The only epoch-related guard checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — i.e., it only blocks a *new* request once a loss price already exists for the user's latest epoch [3](#0-2) . There is no check that all of a user's pending receipts share one epoch, and no per-epoch haircut for older entries.
- When `stopEpochWithDuration` underfunds, `collectWithdrawFunds` divides the funded `_amount` by the **whole** `pendingWithdraws` (all epochs combined) and writes `lossRecoveryPriceByEpoch[epochNumber]` [1](#0-0) .
- `claimWithdrawRequest` pays `claimBasis * lossRecoveryPrice` only for the loss epoch, then routes the remaining `withdrawsRequests[_user]` (the older-epoch basis) through `_claimFundedWithdrawRequest` at 100% [4](#0-3) .
- Result: a mixed-epoch user is owed `basis_old + basis_loss * price`, while the vault only received `(basis_old + basis_loss) * price`. Shortfall = `basis_old * (1 - price)`.

### Impact Explanation
Insolvency / permanent freezing of unclaimed withdrawals. Either (a) the combined claim reverts in `safeTransfer` because the strategy holds less underlying than the obligation, permanently freezing both receipts until the borrower tops up, or (b) if the user withdraws via separate calls/orderings where the old-epoch par claim succeeds first, the loss-epoch receipt and any *other* users' pending claims are left unbacked — first-come claimants are paid in full at the expense of later ones. With a 50% loss price and equal old/new bases, a quarter of every funded loss-adjusted epoch is unbacked.

### Likelihood Explanation
Requires only an unprivileged KYC-passed lender who (1) requests a withdraw in epoch N, (2) does not claim, (3) requests again in epoch N+1, after which (4) the honest manager calls `stopEpochWithDuration`/`stopEpoch` with a realized loss — an expected, designed code path (loss socialization on pending receipts is an intended feature per `previewLossAdjustedWithdrawFunds` [5](#0-4) ). No privileged misbehavior needed; any borrower underfunding event triggers it.

### Recommendation
Track per-epoch pending bases (e.g., `pendingWithdrawsByEpoch`), and in `collectWithdrawFunds` either reject underfunding when receipts span multiple epochs or store the loss price for every epoch contributing to `pendingBasis`. Additionally, enforce in `requestWithdraw` that a user has no outstanding receipt in any earlier unfinalized epoch, so `lastWithdrawRequest` cannot skip a haircutted epoch.

### Proof of Concept
Foundry fork sketch (against a running `IdleCreditVault`/`IdleCDOEpochVariant` deployment):

```solidity
// setup: user is KYC'd lender holding tranche tokens; epoch running
// Epoch N: request 100e6
cdo.requestWithdraw(100e6 * price, tranche); // -> strategy.requestWithdraw
// epoch N stops cleanly, epoch N+1 runs
// Epoch N+1: user requests another 100e6 WITHOUT claiming epoch N receipt
cdo.requestWithdraw(100e6 * price, tranche);

// stopEpochWithDuration realizes a loss: pendingBasis = 200e6, borrower funds 100e6
// collectWithdrawFunds stores lossRecoveryPriceByEpoch[N+1] = 0.5e18, pendingWithdraws = 0

// user calls claimWithdrawRequest:
//   _claimLossAdjustedWithdrawRequest -> pays 100e6 * 0.5 = 50e6
//   _claimFundedWithdrawRequest       -> pays withdrawsRequests[user] = 100e6 at par
// required payout = 150e6, funded reserve = 100e6
// -> safeTransfer reverts (insufficient balance): both receipts frozen,
//    or another claimant's funded claim is drained
assertLt(strategy.underlyingBalance(), 150e6);
vm.expectRevert(); cdo.claimWithdrawRequest(); // or later claimant reverts
```

The invariant broken is solvency of the funded-claim reserve: funded amount must equal the sum of all claims payable from it, but the epoch-indexed haircut is applied to only a subset of the basis used to compute it.

  function claimWithdrawRequest(address _user) external returns (uint256 amount) {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized) {
      // Post-default requests are already priced after the haircut and backed by the reserve,
      // so they must not fall through to the defaulted-epoch receipt logic.
      amount = _claimPostDefaultWithdrawRequest(_user);
      if (amount != 0) return amount;
      // Only receipts created in the defaulted epoch are haircutted here; old fulfilled
      // receipts are handled below at par if they were already funded before default.
      amount = _claimDefaultedWithdrawRequest(_user);
    }
    amount += _claimLossAdjustedWithdrawRequest(_user);
    return amount + _claimFundedWithdrawRequest(_user);

  /// @notice Claim a funded non-default withdraw request at par.
  /// @param _user address of the user
  /// @return amount amount claimed
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
