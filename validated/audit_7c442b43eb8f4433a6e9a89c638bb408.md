### Title
Stale cross-tenure conflicts bypass all node-verification in `handle_block_pre_commit`, letting a signer double-sign at the same height - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
In `Signer::handle_block_pre_commit`, once a previously-signed conflicting block's `last_endorsed` timestamp ages past `freshness_cutoff`, the only remaining guard (the "OWN tenure" check at lines 1432-1457) is scoped to conflicts whose `consensus_hash` equals the proposed block's own tenure. A stale conflict recorded in a *different* tenure is filtered out of that check entirely and receives **no** node-derived verification at all — not `conflict_still_blocks`, not even a plain `get_tenure_tip` call — before the signer proceeds to `SIGN`.

### Finding Description
`handle_block_pre_commit` fetches all signed conflicts at or above the proposed height via `get_signed_conflicts` [1](#0-0) , then applies two successive filters before signing:

1. A `find` over conflicts requiring `last_endorsed > freshness_cutoff` AND `!reorg_permit_stands` AND `conflict_still_blocks` (which internally calls `get_sortition_by_burn_hash` / `get_tenure_tip`) [2](#0-1) . Because of the `last_endorsed > freshness_cutoff` short-circuit, a conflict whose endorsement has gone stale never reaches `conflict_still_blocks` — no cryptographic/node proof of orphaning is ever requested for it.
2. A second `any` filter that only matches conflicts where `conflict.consensus_hash == block_info.block.header.consensus_hash` (i.e., the **same** tenure as the proposal) [3](#0-2) . This is the only place a stale conflict is checked against the node (`get_tenure_tip`), and it is scoped exclusively to same-tenure conflicts.

The code comment explicitly documents the assumption that cross-tenure stale conflicts are "settled by the chainstate checks above" [4](#0-3) , referring to `check_block_against_signer_db_state` run earlier in the same handler [5](#0-4) . But that earlier check only validates B's own tenure (or, for a tenure-change block, B's *parent* tenure) via `check_latest_block_in_tenure` [6](#0-5)  — it never examines the specific conflicting tenure T1 that produced block A. So once A's `last_endorsed` (`MAX(signed_self, signed_group)`, per `get_signed_conflicts` [7](#0-6) ) crosses `tenure_last_block_proposal_timeout` seconds in the past, a fully live, canonical, un-orphaned tenure T1's signed block A stops blocking signature of a sibling B in tenure T2 at the same height — with zero calls to `get_sortition_by_burn_hash` or `get_tenure_tip` on T1.

This matches the documented flowchart: the `FRESH -- "no — all stale"` branch routes straight to the `OWN` decision node, which only asks "a conflict in this block's OWN tenure?" — a cross-tenure stale conflict answers "no" and falls straight through to `SIGN` [8](#0-7) .

### Impact Explanation
This breaks the UNIQUENESS/equivocation-guard invariant that a signer must sign at most one block per height across tenures. If exploited, the victim signer produces two valid signatures over conflicting blocks A (tenure T1) and B (tenure T2) at the same Stacks height, which is exactly the equivocation the pre-commit conflict guard exists to prevent. This is a Critical chain-safety violation (signer signing a conflicting block), and it is repeatable every time a stale window elapses on a genuine sibling-tenure pair.

### Likelihood Explanation
The precondition (two genuinely competing tenures at the same height, e.g. from a Bitcoin fork) is a real, if uncommon, occurrence that the `conflict_still_blocks`/`reorg_permit_stands` machinery was specifically built to arbitrate — its entire purpose is deciding whether such cross-tenure conflicts are still live. The attack requires no majority signer weight and no auth token: the attacker only needs to win a sortition producing tenure T2, gossip its proposal, and wait out `tenure_last_block_proposal_timeout` (a config value, typically minutes) after A was signed. The cost is purely time, not privilege escalation.

### Recommendation
Do not exempt cross-tenure conflicts from node verification once they go stale. Either always run `conflict_still_blocks` (dropping the `last_endorsed > freshness_cutoff` guard for the node-derived death checks, keeping it only as a round-trip optimization when the conflict is *not* in the proposal's own tenure) or explicitly call `get_tenure_tip`/`get_sortition_by_burn_hash` against every stale conflict's tenure — not just same-tenure ones — before falling through to `SIGN`.

### Proof of Concept
Extend `stacks-signer/src/v0/tests.rs` with a variant of `run_sibling_scenario`/`run_cross_tenure_scenario` where:
1. Block A is signed in tenure T1 at height h (`assert_a_signed`).
2. Advance time past `tenure_last_block_proposal_timeout` so A's `last_endorsed` is stale.
3. Feed block B in a *different* tenure T2 at height h through validation and pre-commit threshold, with the mock node's `/v3/sortitions/burn/:hash` and `/v3/tenures/tip_metadata/:T1` endpoints configured to prove T1 is still canonical and live (i.e., a real fork was never resolved).
4. Assert that `handle_block_pre_commit` does **not** mark B as `LocallyAccepted`/signed unless `get_sortition_by_burn_hash` for T1 returned 404 — currently the test would show B gets signed purely because A is stale, with no such call ever made.
