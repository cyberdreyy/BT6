### Title
Claimed instant-withdraw receipts leak their basis into `instantWithdrawClaimsByEpoch`, diluting default recovery for all claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The bug class of CVE-2017-11532 is a resource leak: an allocation (memory) is created per operation but never released, so state accumulates stale capacity. The on-chain analog lives in `IdleCreditVault`: `requestInstantWithdraw` allocates claim basis into `instantWithdrawClaimsByEpoch[currentEpoch]` and `instantWithdrawsRequestsByEpoch[user][currentEpoch]`, but the normal funded-claim path `claimInstantWithdrawRequest` never releases those per-epoch allocations. Only `pendingInstantWithdraws` (via `collectInstantWithdrawFunds`) and `instantWithdrawsRequests` are decremented. The per-epoch basis therefore leaks, and it is later consumed by `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` during `finalizeDefaultRecovery`. [1](#0-0) [2](#0-1) 

### Finding Description
In `requestInstantWithdraw` the strategy mints receipt tokens and records three pieces of state:

- `instantWithdrawsRequests[_user] += _amount` (aggregate per user)
- `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`
- `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`
- `pendingInstantWithdraws += _amount`

When a claim is paid through the non-default path `claimInstantWithdrawRequest`, the code burns the receipt, zeroes `instantWithdrawsRequests[_user]`, and transfers funded underlyings — but it does **not** clear `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrement `instantWithdrawClaimsByEpoch[epoch]`. The only place those per-epoch entries are cleared is `_claimDefaultedInstantWithdrawRequest`, which runs only after `defaultInstantWithdrawsFinalized`. [3](#0-2) 

This matters when instant receipts are only partially funded. `pendingInstantWithdraws` is the unfunded remainder; users whose claims can be satisfied withdraw via `_transferFundedClaim` while others stay pending. If the borrower then defaults in that same epoch and the manager/owner calls `IdleCDOEpochVariant.finalizeDefault` → `finalizeDefaultRecovery`:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` — which still includes the basis of users **already paid in full** — to the total claim basis.
- `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant`, where `instantBasis` includes the already-claimed amounts, inflating the counted prefunded reserve. [4](#0-3) [5](#0-4) 

The result is `totalBasis` in `finalizeDefaultRecovery` is larger than the true outstanding claim basis, so `defaultRecoveryPrice` is computed artificially low. Every legitimate claimant (active LPs via NAV burn/mint and pending receipt holders) receives `basis * deflatedPrice`, and the residual underlying sits as permanently unclaimable dust in `defaultRecoveryReserve` — there is no path that pays it out, since all claims are priced against the same deflated `defaultRecoveryPrice`. [6](#0-5) 

### Impact Explanation
Permanent loss of recovery funds. The leaked per-epoch basis inflates the denominator in `defaultRecoveryPrice = reserveAmount * 1e18 / totalBasis`, so every honest defaulted-epoch claimant and active LP is paid less than entitled, and the difference (equal to the already-claimed instant basis times the haircut) is locked in the strategy as recovery dust with no claim path. Quantitatively, if X of instant receipts were already paid in the default epoch, `totalBasis` is inflated by X and claimants lose roughly `X / (trueBasis + X)` of the recovery pool to dead dust. The broken invariant is "one receipt one payout": a paid receipt keeps contributing claim basis.

### Likelihood Explanation
Requires: (1) instant-withdraw mode enabled (`!disableInstantWithdraw && !isProgrammableBorrower` and the APR-drop condition in `IdleCDOEpochVariant.requestWithdraw`), (2) an unprivileged tranche holder requesting an instant withdraw, (3) the instant queue being only partially funded so `pendingInstantWithdraws != 0` while some users have already claimed, and (4) a borrower default finalized in the same epoch. All attacker steps are unprivileged (deposit → request instant withdraw → claim when funded). No privileged misbehavior is needed; default finalization by honest manager/owner is what crystallizes the loss. Medium likelihood: it needs the coincidence of partial instant funding and a default in the same epoch window.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch accounting alongside the aggregate: record the request epoch (e.g., via a `lastInstantWithdrawRequest` marker or by iterating `instantWithdrawsRequestsByEpoch[_user]`), then decrement `instantWithdrawClaimsByEpoch[epoch]` and zero `instantWithdrawsRequestsByEpoch[_user][epoch]` for the claimed amount. Alternatively, make `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` derive current-epoch instant basis from still-outstanding receipts only.

// Foundry fork PoC (extend test/foundry/IdleCreditVault.t.sol harness)
function testInstantClaimBasisLeakDilutesDefaultRecovery() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());

    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                       // test contract LP
    address alice = makeAddr('alice');
    _depositWithUser(alice, amount, true);           // KYC'd attacker LP

    _startEpochAndCheckPrices(0);

    // stop epoch with a lower APR so both requestWithdraw calls take the instant path
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(reducedApr, 0);               // lastEpochApr > unscaledApr + delta

    // Alice and the LP both request instant withdraws (receipts minted in epoch N+1)
    uint256 aliceReq = _requestInstant(alice);
    uint256 lpReq    = _requestInstant(address(this));

    // CDO collects only enough to fund Alice's receipt -> pendingInstantWithdraws > 0
    _collectInstantPartial(aliceReq);                // collectInstantWithdrawFunds(aliceReq)
    cdoEpoch.claimInstantWithdrawRequest(alice);     // paid in full; per-epoch basis NOT cleared

    // borrower defaults in the same epoch; finalize recovery
    _defaultAndFinalize(recoveryAmount);

    uint256 basis = strategy.defaultPendingClaimBasis();
    // BUG: basis still counts aliceReq even though Alice was already paid
    assertGt(basis, lpReq, 'claimed instant basis leaked into default basis');

    // recoveryPrice is deflated; honest claimants are underpaid and dust is locked
    uint256 dust = underlying.balanceOf(address(strategy)) - strategy.defaultRecoveryReserve();
    // after all claims, strategy retains ~ aliceReq * (1 - haircut) unclaimable underlyings
}
```

Key assertion: after all claims settle, `instantWithdrawClaimsByEpoch[defaultEpoch]` retains Alice's already-paid amount and the strategy holds residual underlyings that no claim path can reach, while every claimant's payout was reduced by the inflated `totalBasis`.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
