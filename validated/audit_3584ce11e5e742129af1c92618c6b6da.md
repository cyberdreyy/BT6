### Title
Unbounded, Undelayed Vote Commission Update (`update_commission_bps`) Enables Front-Run Extraction of Block Revenue/Inflation Rewards From Delegators - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The original report's root cause is a caller-controlled value-extraction path with no bound/delay protecting the counterparty (`_swapToVolt()`'s hardcoded `amountOutMin = 0`), reachable through a permissionless entry point (`collectFees()`), that the code comments themselves acknowledge is deliberately unprotected. The closest analog in this repository is the vote program's `update_commission_bps` instruction, which the code explicitly documents as having **no timing/delay protection**, unlike the legacy `update_commission` path.

### Finding Description
The legacy commission-update function enforces a documented protection window: increases are disallowed in the back half of an epoch unless the `delay_commission_updates` feature relaxes it, and reward calculation additionally uses a snapshot of vote-account state from a prior epoch specifically "to prevent last minute commission rugs." [1](#0-0) [2](#0-1) 

In contrast, `update_commission_bps` (added per SIMD-0291/SIMD-0249/SIMD-0123 for `InflationRewards` and `BlockRevenue` commission) contains no such delay or minimum-notice rule at all — the comment states this plainly: [3](#0-2) 

The only gate is a signature check from the vote account's authorized withdrawer; there is no epoch-boundary restriction, no minimum-notice window, and no snapshot delay analogous to the one applied to legacy commission for inflation-reward computation. This mirrors the DeFi finding's pattern exactly: a value-affecting parameter (`amountOutMin` there, `commission_bps` here) is left unconstrained "by design" per the code's own comments, in a path that is reachable and triggered on every block/epoch without requiring any cooperation from the parties whose funds are affected (delegators/stakers, analogous to the protocol's fee depositors).

### Impact Explanation
Because `update_commission_bps` has no delay, a validator operator can raise their `BlockRevenue` or `InflationRewards` commission immediately before a reward/commission distribution event and revert it afterward, extracting a larger share of rewards than delegators/stakers expect for that period — an unauthorized value transfer from stakers to the validator operator that the legacy path was specifically hardened against (`snapshot_epoch_vote_accounts`/`delay_commission_updates`) but this new path is not. [4](#0-3) 

### Likelihood Explanation
The instruction is a standard, permissionless-to-invoke (subject only to the vote account's own withdraw-authority signature) builtin-program instruction routed through `vote_processor.rs`'s dispatch, requiring no privileged node access, no leaked keys, and no consensus-layer changes — it is reachable purely via an ordinary signed transaction against the vote program. [5](#0-4) 

### Recommendation
Apply the same protection used for legacy commission updates — a delay window (e.g., disallow increases in the back half of an epoch, per `is_commission_update_allowed`) and/or a snapshot-based read (as used for `commission_rate_in_basis_points` via `get_cached_vote_accounts`) — to `update_commission_bps` for both `InflationRewards` and `BlockRevenue` kinds, rather than relying solely on the withdraw-authority signature.

### Proof of Concept
1. Validator operator holds the vote account's authorized withdrawer key.
2. Immediately before a slot/epoch boundary where block revenue or inflation rewards will be computed/distributed, operator submits an `UpdateCommissionBps` instruction raising `block_revenue_commission_bps` or `inflation_rewards_commission_bps` to the maximum allowed value — this succeeds unconditionally since `update_commission_bps` performs no epoch-timing check. [6](#0-5) 
3. Reward/commission calculation reads the vote account's (now inflated) commission at the time of computation for the `BlockRevenue`/current-epoch case (no snapshot delay applies to this code path the way it does for legacy commission), causing stakers to receive a smaller share than they would have under the previous commission rate.
4. Operator lowers the commission back down after the distribution completes, with no on-chain record forcing a delay, repeating the extraction at will.

**Note:** I was unable to fully trace every downstream consumer of `block_revenue_commission_bps` (e.g., whether any block-revenue-sharing distribution path already applies its own snapshot delay analogous to `get_cached_vote_accounts`) within the available index; this should be verified against the full `block_revenue_sharing`/SIMD-0123 distribution implementation before treating this as conclusively unmitigated.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

    /// Get cached vote account state from the past few epochs so that some vote
    /// state configuration changes are delayed before being used in reward
    /// calculation.
    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        // Vote account state from the beginning of the rewarded epoch.
        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }
    }
