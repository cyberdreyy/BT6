### Title
Stale confirmations from removed multisig members still count toward the confirmation threshold, allowing execution below the configured K-of-N - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
This is the same class of bug as the reported issue: state recorded by one part of the contract (a lender's LP balance / here, a confirmer's vote) is not invalidated when the underlying authorization it depends on is revoked (bucket bankruptcy / here, member removal), and a downstream function (`claimRewards` / here, `confirm`) still trusts the stale record. In the multisig contracts, `delete_member` (and the analogous `DeleteKey` action in `multisig/src/lib.rs`) only purges confirmations for requests that the removed member *created*, not confirmations that the removed member cast on requests created by someone else. Those stale confirmations remain counted toward `num_confirmations` in `confirm`, so a request can execute with fewer live/authorized signers than the configured threshold.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member` cleans up state for a removed member as follows: [1](#0-0) 

It filters `self.requests` for entries whose `MultiSigRequestWithSigner.member` (the request **creator**) equals the member being deleted, and only for those does it call `self.confirmations.remove(&request_id)`. Requests created by *other* members, on which the removed member had already cast a confirmation via `confirm`, are left completely untouched — their `confirmations: HashSet<String>` entry still contains the removed member's identifier.

`confirm` then trusts that stale set purely by count: [2](#0-1) 

`assert_valid_request` (called at the top of `confirm`) only validates that the *current caller* is a member; it never re-validates that previously stored confirmations still belong to current members: [3](#0-2) 

So the binding the contract is supposed to enforce is:
```
confirmations.len() (at execution) == number of *currently valid* members who approved
```
but after a member removal that binding becomes:
```
confirmations.len() (at execution) == (live approvals) + (stale approvals from removed members)
```//
The same root cause exists in the original `multisig/src/lib.rs`, where `DeleteKey` only removes confirmations for requests whose `signer_pk` (creator) equals the deleted key: [4](#0-3) 

and `confirm` again just compares set length against `self.num_confirmations`: [5](#0-4) 

### Impact Explanation
This falls under the Critical impact category "a multisig request executed below threshold." Concretely: with members `{A, B, C}` and `num_confirmations = 2`, if member `B` creates request `R` (e.g. a `Transfer`) and member `A` confirms it (`confirmations = {A}`), then later `A`'s key is compromised and the remaining members remove `A` via `DeleteMember`/`DeleteKey` (a routine, legitimate remediation action), `R` is **not** cleaned up because `R.member == B`, not `A`. `R` still shows one confirmation from `A`, a member who has since been explicitly revoked/untrusted. A single additional confirmation from `C` (`confirmations.len() + 1 == 2 >= num_confirmations`) is now sufficient to execute `R`, meaning the transaction executes on the authority of only one currently-trusted signer (`C`) plus a vote from a party the multisig has explicitly deemed no longer authorized. The K-of-N authorization guarantee the multisig is built to provide is broken, and funds can move (or keys/members can be added/removed, or arbitrary `FunctionCall`s executed) without the intended number of live, trusted approvals.

### Likelihood Explanation
This requires no exotic conditions: it only needs (1) a pending multi-confirmation request that has received at least one confirmation, and (2) any member removal event (`DeleteMember`/`DeleteKey`), which is a normal, expected operational action (e.g. rotating out a compromised or departing signer). Because member removal is a routine security response, and the cleanup logic silently omits confirmations cast on requests created by others, this scenario is easily triggered in normal contract usage, not just via a crafted attack.

### Recommendation
When removing a member (`delete_member` / `DeleteKey` action), iterate over **all** pending requests' confirmation sets (not just requests created by that member) and strip out the removed member's/key's confirmation entry, re-checking whether the request should now be considered still-pending. Alternatively, validate at `confirm`/execution time that every account/key in the stored `confirmations` set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. `B` calls `add_request` with a `Transfer` action to some receiver — this stores `MultiSigRequestWithSigner { member: B, ... }` and an empty confirmation set for `request_id = R`.
3. `A` calls `confirm(R)` — `confirmations(R) = {A}` (1 < 2, so it doesn't execute yet).
4. The organization detects `A`'s key is compromised and submits/executes a `DeleteMember { member: A }` request (confirmed by `B` and `C`). `delete_member` only removes requests where `r.member == A`; since `R.member == B`, `R` and its confirmation set `{A}` are left intact, and `A` is removed from `self.members`.
5. `C` calls `confirm(R)`. `confirmations(R).len() (=1) + 1 = 2 >= num_confirmations (2)`, so `R` executes — approved by only one currently valid member (`C`) plus a stale vote from removed member `A`, instead of two currently-authorized members.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
