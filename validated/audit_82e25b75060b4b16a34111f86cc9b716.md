### Title
Permissionless `LockupFactory::create` lets an attacker squat a victim's deterministic lockup address with attacker-chosen parameters - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the lockup contract's account id deterministically from `owner_account_id` alone (`sha256(owner_account_id)[..20].<factory>`) and never checks that the caller (`env::predecessor_account_id()`) is the owner, the foundation, or otherwise authorized to create a lockup for that owner. Any unprivileged account can call `create` for `owner_account_id = "victim.near"` with minimal deposit and permissive parameters, permanently occupying the canonical lockup address before the legitimate grantor does.

### Finding Description
The binding that should hold is:

`LockupArgs_at(sha256("victim.near")[..20].<factory>) == LockupArgs_sent_by(the entitled grantor for "victim.near")`

In `lockup-factory/src/lib.rs`, `create` computes the target account deterministically from only the `owner_account_id` argument: [1](#0-0) 

and then issues `Promise::new(lockup_account_id).create_account().deploy_contract(...).transfer(...).function_call("new", LockupArgs{...})` with whatever `lockup_duration`, `vesting_schedule`, `release_duration`, and `whitelist_account_id` the caller supplied: [2](#0-1) 

There is no assertion tying `env::predecessor_account_id()` to `owner_account_id`, no `assert_called_by_foundation`, and no reservation/allowlist mechanism. The only guard is `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE)`, which any account can satisfy with `3.5` NEAR: [3](#0-2) 

Since NEAR account creation via `create_account()` fails on an account that already exists, whichever `create()` call lands first wins the address; the second call's promise chain fails and is rolled back via `on_lockup_create`, which only refunds the deposit and returns `false` - it does not retry or reassign the address: [4](#0-3) 

Because `owner_account_id` is copied verbatim into `LockupArgs.owner_account_id`, the deployed lockup still legally shows `victim.near` as owner - but the attacker chose `lockup_duration = 0`, `vesting_schedule = None`, `release_duration = None`, and (if desired) `whitelist_account_id` pointing to an attacker-controlled staking pool whitelist. No existing guard (`assert_self`, `is_promise_success`, `MIN_ATTACHED_BALANCE` check) validates that the parameters or the caller are authorized for that specific owner.

### Impact Explanation
This deploys "a lockup deployed with parameters its rightful creator never chose" at the canonical, deterministic address for `victim.near` - explicitly listed as Critical impact in the rules. The real grantor's later `create()` call for the same `owner_account_id` fails because the account already exists, permanently blocking the foundation/grantor from ever funding `victim.near`'s canonical lockup address with the intended terms (real vesting schedule, real amount, restricted whitelist). This is repeatable against any account whose upcoming grant is known or guessable ahead of time (e.g., via public announcement), at a fixed, low cost per victim (`MIN_ATTACHED_BALANCE` ≈ 3.5 NEAR, refundable in the failure case and recoverable by the attacker on success since they remain in control of funding/whitelist parameters of a lockup that nominally can't be spent by them but permanently denies the real allocation).

### Likelihood Explanation
Preconditions are minimal and match the stated attacker capabilities: knowledge of the future owner account id (public announcement, on-chain intent, mempool observation of the real `create` call, or common naming conventions), and the ability to send a transaction with `MIN_ATTACHED_BALANCE` attached. No special role, key, or contract ownership is required. The attack is a simple race/front-run and is trivially repeatable across any number of victim accounts.

### Recommendation
Restrict who may call `create` for a given `owner_account_id` - e.g., require `env::predecessor_account_id() == owner_account_id.as_ref()` or `env::predecessor_account_id() == foundation_account_id`, or introduce an explicit reservation/allowlist step controlled by the foundation before permissionless creation is allowed. Alternatively, incorporate `predecessor_account_id` into the derived lockup account id so only the intended party can claim/reserve the canonical address for their own grant.

### Proof of Concept
```rust
// lockup-factory/src/lib.rs tests module (near-workspaces or near-sdk-sim style)

#[test]
fn test_attacker_squats_victim_lockup_before_real_grantor() {
    // Setup factory as in existing tests (LockupFactory::new(...))
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    let owner = account_tokens_owner(); // "victim.near" equivalent

    // Attacker front-runs: unrelated predecessor, near-zero lockup duration, no vesting, no whitelist restriction
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = MIN_ATTACHED_BALANCE; // exactly minimum
    testing_env!(context.clone());
    contract.create(owner.clone(), 0u64.into(), None, None, None, None);

    // Simulate successful account creation callback for attacker's call
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let attacker_result = contract.on_lockup_create(
        lockup_account(), // sha256(owner)[..20].factory - deterministic, independent of caller
        MIN_ATTACHED_BALANCE.into(),
        String::from("attacker.near"),
    );
    assert_eq!(attacker_result, true); // attacker's squat succeeded

    // Real grantor now tries to create the legitimate lockup for the same owner
    context.predecessor_account_id = String::from("foundation.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(owner.clone(), LOCKUP_DURATION.into(), None, Some(real_vesting_schedule), None, None);

    // In a real near-workspaces integration test, this second create_account() promise
    // fails because "lockup_account()" already exists on-chain.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed); // account exists -> create_account fails
    let real_result = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from("foundation.near"),
    );
    assert_eq!(real_result, false); // real grantor's lockup was never deployed; deposit refunded, address permanently squatted
}
```
This demonstrates the broken binding: `LockupArgs` deployed at `sha256("victim.near")[..20].<factory>` are the attacker's chosen zero-duration, no-vesting args, not the real grantor's, and the real grantor's subsequent call for the same `owner_account_id` fails permanently.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
