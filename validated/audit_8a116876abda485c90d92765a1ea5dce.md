### Title
APR0 re-request overwrites `apr0Users[_user].principalEpoch`, repricing accrued interest at the wrong epoch rate - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The EsEMBR bug class is "balance/state changes without first settling accrued entitlements, so rewards are computed on stale state." The strongest analog is the APR=0 withdraw-request flow in `IdleCreditVault`: APR0 requests keep accrual accounting in a single per-user slot (`apr0Users[_user].principal` / `principalEpoch`), and interest is settled later at `stopEpoch` via `apr0RateByEpoch[principalEpoch]`. A user who opens a second APR0 `requestWithdraw` in a later epoch — before claiming the first receipt — has the earlier epoch tag overwritten, so the combined principal is priced at the new epoch's `apr0RateByEpoch` instead of each tranche of principal at its own epoch's rate.

### Finding Description
`requestWithdraw` burns the CDO's strategy tokens for principal and mints a receipt, then for `unscaledApr == 0` pools routes to `_requestWithdrawApr0` which writes into the single `apr0Users[_user]` struct and bumps `principal`/`principalEpoch` to `epochNumber` (contracts/strategies/idle/IdleCreditVault.sol:243-295). The only same-slot guard is the `lossRecoveryPriceByEpoch[lossEpoch] != 0` check (lines 261-271), which triggers solely after a loss-adjusted epoch; in ordinary epochs nothing forces the user to settle or claim the pending APR0 request first. Because `_withdrawClaimAmountsForEpoch` (lines 862-881) only counts `apr0User.principal` when `principalEpoch == _claimEpoch` and applies `apr0RateByEpoch[principalEpoch]` to the whole accumulated principal, overwriting `principalEpoch` either (a) makes the epoch-N principal invisible to the epoch-N claim path, or (b) applies epoch-(N+1)'s rate retroactively to epoch-N principal. Either way the receipt's claim basis diverges from the interest actually accrued — the same stale-accrual broken invariant as the EsEMBR burn-without-update bug.

### Impact Explanation
When `apr0RateByEpoch` changes between consecutive epochs (it is set per epoch at settlement), a user gains interest at the newer, higher rate on principal that only accrued the older rate — stealing yield from the shared `pendingWithdraws`/APR0 settlement bucket funded by the borrower — or permanently loses claim basis for the earlier request's principal/interest, freezing that portion of the receipt as unclaimable dust in the vault. Quantification: `principal_N * (apr0RateByEpoch[N+1] - apr0RateByEpoch[N]) / RECOVERY_FULL` per occurrence.

### Likelihood Explanation
Requires an APR0 pool (`unscaledApr == 0`, e.g., programmable-borrower deployments) with a rate change across epochs and a user re-requesting before claiming. The epoch-gate in `_claimFundedWithdrawRequest` (line 326) only delays claiming; it does not block a second request, and `_hasWithdrawRequest` is only enforced after `defaultRecoveryFinalized` (line 249). Medium likelihood: needs a specific vault mode and a rate change, but no privileged collusion.

### Recommendation
In `_requestWithdrawApr0`, either revert when `apr0Users[_user].principal != 0` with a different `principalEpoch` (mirroring the post-default `_hasWithdrawRequest` guard), or settle the outstanding epoch's interest into `settledPrincipal`/`settledInterest` before accumulating new principal — i.e., update accrual before mutating the balance, matching the EsEMBR fix pattern.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (APR0 / programmable-borrower vault)
// 1. Epoch N running with unscaledApr == 0. User deposits into AA tranche.
vm.prank(user);
cdo.depositAA(amount); // or requestWithdraw path entry
// 2. User requests withdraw -> apr0Users[user] = {principal: P, principalEpoch: N}
cdo.requestWithdraw(0, AATranche);
// 3. Epoch N stops: apr0RateByEpoch[N] = r1 (e.g. 2%). Epoch N+1 starts.
cdo.stopEpoch(); // borrower repays, rate r1 stored
// 4. WITHOUT claiming, user deposits again and requests withdraw in epoch N+1.
cdo.depositAA(amount2);
cdo.requestWithdraw(0, AATranche); // principal += P2, principalEpoch overwritten to N+1
// 5. Epoch N+1 stops: apr0RateByEpoch[N+1] = r2 (e.g. 8%).
// 6. User claims: _withdrawClaimAmountsForEpoch prices (P + P2) at r2,
//    instead of P at r1 + P2 at r2. User is overpaid (P*(r2-r1)) stolen from
//    the shared settlement bucket, or epoch-N basis is orphaned if the code
//    path reads only the current principalEpoch.
assertEq(vault.apr0Users(user).principalEpoch, N + 1);
// interest credited = (P+P2)*r2/FULL rather than P*r1/FULL + P2*r2/FULL
```

Caveat: I could not read the body of `_requestWithdrawApr0`/`_settleApr0` within the available search budget; the finding assumes principal accumulates into the single slot rather than reverting on an unsettled prior epoch — if it already settles or reverts, the analog does not hold.
