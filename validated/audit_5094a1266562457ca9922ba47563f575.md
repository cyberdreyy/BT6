### Title
Stale SPL Token owner index entries in `AccountsIndex` corrupt `getTokenAccountsByOwner` RPC results ([File: accounts-db/src/accounts_index.rs])

### Summary
`AccountsIndex::update_secondary_indexes` (and its helper `update_spl_token_secondary_indexes`) only ever *inserts* a new `(owner_key -> token_account_pubkey)` mapping into `spl_token_owner_index` when a token account's packed `owner` field changes; it never removes the mapping for the *previous* owner key while the account stays alive in the primary index. This is the same bug class as the reported `stakingIndicesByPrincipalUnstaker` issue: a mapping keyed on a mutable "current owner/unstaker" field is updated on the "add" side but never cleaned up on the "remove" side when that owner changes.

### Finding Description
`update_secondary_indexes` re-derives the packed owner/mint from the account's current data on every write and calls `SecondaryIndex::insert(owner_key, pubkey)`: [1](#0-0) 

There is no corresponding call that removes the old `(old_owner_key -> pubkey)` entry when the owner data changes. The only removal path for `spl_token_owner_index`/`spl_token_mint_index`/`program_id_index` entries is `purge_secondary_indexes_by_inner_key_if`, which is driven off `handle_dead_keys` — i.e. it only fires when the pubkey is entirely removed from the primary `AccountsIndex` (ref count reaches zero / fully purged), not when the account is merely rewritten with different data while remaining alive: [2](#0-1) 

The `update_secondary_indexes` doc comment even acknowledges the asymmetry, but only discusses the zero-lamport tombstone case, not the "owner field changed while account stays alive" case: [3](#0-2) 

SPL Token (and Token-2022) support changing a token account's `owner` field in place via the `SetAuthority` instruction with `AuthorityType::AccountOwner`, without closing/reopening the account. Every ordinary user can invoke this instruction on any token account they control. After such a change:
1. `update_secondary_indexes` is invoked again on the rewritten account (same pubkey, new owner bytes in `account_data`).
2. `insert(new_owner_key, pubkey)` correctly adds the new mapping.
3. The old `(old_owner_key -> pubkey)` mapping in `spl_token_owner_index` is left behind indefinitely — it is never removed, because the pubkey never became a "dead key" in the primary index (it's still alive, just with different data).

This causes `spl_token_owner_index.reverse_index` and `.index` to grow monotonically stale entries: an account will be listed under every historical owner it has ever had, not just its current one, until the account is eventually fully purged from the accounts index (e.g. closed to zero lamports and its slot list garbage-collected).

### Impact Explanation
This secondary index directly backs the `getTokenAccountsByOwner`/`getProgramAccounts`-with-`SplTokenOwner`-filter RPC path (`AccountIndex::SplTokenOwner`, wired through `account_secondary_indexes.rs` and `rpc/src/rpc.rs`). A stale entry means an RPC node with the `spl-token-owner` secondary index enabled will report a token account as still belonging to `old_owner_key` after the account's owner authority has legitimately reassigned it to `new_owner_key`. This is an RPC/state-query correctness bug (incorrect state reported to clients that rely on the account index rather than a raw scan), not a fund-movement bug in itself, but it can mislead wallets, exchanges, or automated systems that trust `getTokenAccountsByOwner` results to determine which accounts a user actually controls — a stale/false-positive membership claim that a security-sensitive consumer might treat as "this account is (still) mine" or as evidence of a party's true holdings.

### Likelihood Explanation
High for triggering the stale state: any ordinary user can call SPL Token's `SetAuthority(AccountOwner)` on a token account they own, and the bug fires deterministically every time thereafter (no race condition needed) as long as the validator/RPC node has the SPL-token-owner secondary index enabled (`--account-index spl-token-owner`, common on RPC-serving validators). No consensus impact and no fund loss occurs from the index bug alone, which limits severity, but the incorrect index state persists and compounds over the life of the account.

### Recommendation
In `update_secondary_indexes`/`update_spl_token_secondary_indexes`, when re-indexing an account whose secondary key has changed, remove the stale `(old_key -> pubkey)` mapping before/while inserting the new one. This requires either tracking the previously-indexed owner/mint per pubkey (e.g., via the `reverse_index` already maintained in `SecondaryIndex`) or performing a diff-and-remove using `remove_by_inner_key_if` keyed on the account's current data, mirroring how `purge_secondary_indexes_by_inner_key_if` already removes entries for fully-dead keys — but triggered on in-place field changes as well, not only on account death.

### Proof of Concept
1. Enable the SPL-token-owner secondary index on a validator/RPC node.
2. Create an SPL Token account `A` with owner `OwnerX`; observe `spl_token_owner_index.get(&OwnerX)` includes `A`.
3. Submit `SetAuthority { account: A, authority_type: AccountOwner, new_authority: OwnerY }` signed by `OwnerX` (a normal, permitted operation).
4. After the transaction lands and the account is rewritten/flushed, call `getTokenAccountsByOwner` for `OwnerX` — it will still return account `A`, even though `A` is now solely controlled by `OwnerY`, because `spl_token_owner_index` still contains the stale `OwnerX -> A` mapping from step 2 that was never removed by `update_secondary_indexes` ( [1](#0-0) ).

    fn update_spl_token_secondary_indexes<G: spl_generic_token::token::GenericTokenAccount>(
        &self,
        token_id: &Pubkey,
        pubkey: &Pubkey,
        account_owner: &Pubkey,
        account_data: &[u8],
        account_indexes: &AccountSecondaryIndexes,
    ) {
        if *account_owner == *token_id {
            if account_indexes.contains(&AccountIndex::SplTokenOwner)
                && let Some(owner_key) = G::unpack_account_owner(account_data)
                && account_indexes.include_key(owner_key)
            {
                self.spl_token_owner_index.insert(owner_key, pubkey);
            }

            if account_indexes.contains(&AccountIndex::SplTokenMint)
                && let Some(mint_key) = G::unpack_account_mint(account_data)
                && account_indexes.include_key(mint_key)
            {
                self.spl_token_mint_index.insert(mint_key, pubkey);
            }
        }
    }
