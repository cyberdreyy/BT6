### Title
Depositor who requests withdrawal during the buffer is charged upfront management fees exceeding credited interest, receiving back less than deposited principal - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
In `IdleCDOEpochVariant`, an unprivileged KYC'd lender can deposit during the buffer period and immediately call `requestWithdraw`. The receipt minted in `IdleCreditVault.requestWithdraw` pays `principal + interest - totalFees`, where `totalFees` includes an upfront management fee charged for `epochDuration + remaining buffer`. Because the credited epoch interest is computed on a different (and shorter) basis than the fee, a user who withdraws right after depositing receives less underlying than they deposited — the exact bug class of the external report.

### Finding Description
`requestWithdraw` at `contracts/IdleCDOEpochVariant.sol:739-791` computes the withdrawal receipt as:

```
principal = _trancheToUnderlyings(_amount, _tranche)          // line 772
(interest, diff) = _calcInterestWithdrawRequest(...)          // line 773
totalFees = _totalWithdrawFees(principal, interest)           // line 774
_underlyings = principal + interest - totalFees               // line 776
```

`_calcInterestWithdrawRequest` (lines 856-878) grants the requester interest only for `epochDuration` (the buffer-portion of the scaled APR is deliberately stripped: `* _duration / (_duration + _buffer)`). However `_totalWithdrawFees` (lines 900-906) charges `_calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration())`, and `_withdrawRequestManagementFeeDuration` (lines 925-931) returns `epochDuration + (epochEndDate + bufferPeriod - block.timestamp)` — i.e., a full epoch **plus all remaining buffer time**.

Two consequences:

1. **Principal loss on deposit→withdraw.** When `mgmtFee >= interest` (low vault APR, non-trivial `managementFee`, or long buffer), `_totalWithdrawFees` returns `_mgmtFee` outright, so `_underlyings = principal + interest - mgmtFee < principal`. A lender who deposits in the buffer and requests withdrawal in the same block gets a receipt worth less than deposited, with the difference routed to `feeReceiver`/`pendingWithdrawFees`.

2. **Timing-dependent unfairness.** Two lenders requesting withdrawal on the same principal during the same buffer — one right after `stopEpoch`, one just before `startEpoch` — receive receipts that differ by `mgmtFee * remainingBuffer / 365 days`, although both receipts mature at the same `stopEpoch` and are claimable at the same time. The fee is charged on time the request simply sits in the queue, not on time the funds were lent.

No guard prevents this: `requestWithdraw` is open to any `isWalletAllowed` user whenever `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are true (the whole buffer window), and `_skimDonatedAssets`, epoch gating, and `Default` checks do not touch the fee path.

### Impact Explanation
Direct loss of user principal, bounded by `principal * managementFee * (epochDuration + bufferPeriod) / 365 days`. With a 10% annualized management fee and a 30+5 day cycle this is ~0.96% of principal lost for a round-trip that takes one transaction, plus the interest-vs-fee basis mismatch (fee charged on epoch+buffer, interest credited on epoch only). The loss is paid to fee receivers, not recovered by the user.

### Likelihood Explanation
Medium-low: it requires `managementFee` to be non-zero and the user to request withdrawal during the buffer (the only window where requests are accepted). No privileged misbehavior is needed — any whitelisted lender triggers it by depositing then calling `requestWithdraw`. The loss is small per round-trip but is systematic, deterministic, and hits exactly the "user changes their mind" scenario.

### Recommendation
- Compute the upfront management fee on the same duration basis as the credited interest (`epochDuration` only, or the actual time the receipt will wait until claim), not `epochDuration + remaining buffer`.
- Alternatively cap `totalFees` at `interest` so a withdrawal receipt can never be worth less than the current tranche-token value (`principal`), or skip fees for requests made in the same buffer as the deposit before funds enter an epoch.

### Proof of Concept
Foundry fork test (sketch, follows existing harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: cdoEpoch (IdleCDOEpochVariant) with underlying USDC, strategy IdleCreditVault,
// borrower seeded; manager sets managementFee = 10% (10000 bps of FULL_ALLOC scaled),
// APRs low (e.g. 1e18), epochDuration = 30 days, bufferPeriod = 5 days.
_setFeeParams(TL_MULTISIG, 10000, FULL_ALLOC, cdoEpoch.managementFee()); // 10% mgmt fee
// seed pool so tranche price is ~1e18 and epoch machinery works
idleCDO.depositAA(1000 * ONE_SCALE);            // prior LP seeds NAV
// fresh user during buffer
deal(underlying, alice, 1000e6);
vm.startPrank(alice);
IERC20(underlying).approve(address(cdoEpoch), 1000e6);
idleCDO.depositAA(1000e6);
uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));
vm.stopPrank();
// requested = principal + interest - mgmtFee(principal, 35 days) < 1000e6
assertLt(requested, 1000e6);                    // user already at a loss
// after next epoch stops, claim pays out only `requested`
cdoEpoch.claimWithdrawRequest();
assertLt(IERC20(underlying).balanceOf(alice), aliceBalBefore);
```

The same sequence issued at `epochEndDate + bufferPeriod - 1` versus right after `stopEpoch` yields materially different receipts for identical principal and claim time, demonstrating the timing-dependent overcharge.
