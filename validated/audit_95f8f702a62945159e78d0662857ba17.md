## Analysis

This maps the "missing address validation" bug-class (an entity that should occupy exactly one of two mutually-exclusive roles is allowed to occupy both, corrupting a balance/threshold calculation) onto the signer weight-accounting done by the **node-side** stackerdb listener/coordinator, which duplicates (with a missing guard) logic that `stacks-signer`'s own `signerdb.rs` already protects against.

### Title
Node-side rejection weight is never retracted when a signer later accepts the same block, corrupting the rejection/acceptance weight equality — (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`stacks-signer`'s local storage explicitly prevents a signer's weight from being counted in both the "accepted" and "rejected" tallies for the same block: `add_block_rejection_signer_addr` refuses to record a rejection if a signature already exists [1](#0-0) , and adding a signature clears any prior rejection row for that signer/block, as proven by the `reject_then_accept` unit test [2](#0-1) . The node's `StackerDBListener`/`SignerCoordinator`, which independently re-implements the same accept/reject weight tally to decide when the miner may push a block, has no equivalent guard: an `Accepted` message is only checked against `gathered_signatures` and never against `responded_signers`/prior reject state, so a signer that first rejects and later legitimately re-accepts the same block ends up counted in **both** `total_weight_rejected` and `total_weight_approved`.

### Finding Description
`stacks-signer/src/v0/signer.rs::should_reevaluate_reject_reason` shows that a signer legitimately flips from "rejected" to "reconsider/accept" for several reject reasons (e.g. `NoSortitionView`, `ConnectivityIssues`, `UnknownParent`) [3](#0-2) . This is a normal, one-signer-triggerable event (no majority needed, no key compromise needed).

On the node side, `stackerdb_listener.rs` maintains a shared `BlockStatus` with `total_weight_approved`, `total_weight_rejected`, `gathered_signatures` (keyed by slot) and `responded_signers` (a set keyed by slot). In the `Rejected` arm, weight is only added the first time a slot responds at all:
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [4](#0-3) 

But the `Accepted` arm only checks `gathered_signatures`, never `responded_signers`, before adding weight:
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [5](#0-4) 

So the guard only works in the accept→reject direction (a reject arriving after an accept is a no-op because `responded_signers` already contains the slot). In the reject→accept direction, the stale rejection weight already added to `total_weight_rejected` is never removed, and the accept weight is separately added to `total_weight_approved`. The two counters, which are supposed to be mutually exclusive per-signer partitions of `total_weight`, now double-count that signer, and `total_weight_approved + total_weight_rejected` can exceed the real live opinion of the signer set.

`SignerCoordinator::wait_for_signatures` checks the (now-corrupted) rejection tally first:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { ... });
} else if block_status.total_weight_approved >= self.weight_threshold {
    return Ok(...);
}
``` [6](#0-5) 

### Impact Explanation
Because `total_weight_rejected` can retain stale weight from signers who have since re-accepted the same block, the coordinator can incorrectly conclude that the blocking minority (>30% by weight) has been reached and abort the block with `SignersRejected`, even though the true, current signer opinion no longer supports that rejection and would actually reach the 70% acceptance threshold if counted correctly. This is a wedge on block progress caused purely by the node's own weight-accounting bug — it does not require a majority, another signer's key, or the `auth_token`; a single signer flipping opinion in-protocol is enough to leave permanently-stale weight in the reject bucket for that block/slot. This falls under the allowed "liveness wedge" impact category (miner never manages to push an otherwise-signable block), rooted entirely in the accept/reject weight equality being broken.

### Likelihood Explanation
The reject→accept transition is an intended, documented protocol behavior (`should_reevaluate_reject_reason`), and can happen simply from network/gossip timing (e.g. a signer briefly can't reach a sortition/parent and rejects, then catches up and reconsiders) — no attacker coordination required, matching the "one-slot miner (plus gossip)" scope.

### Recommendation
In the `Accepted` arm of `stackerdb_listener.rs`, when a slot that is already present in `responded_signers` due to a prior rejection now sends an acceptance, decrement `total_weight_rejected` by that signer's weight (and remove any tracked reject bookkeeping for the slot) before adding it to `total_weight_approved`, mirroring the retraction logic already implemented in `stacks-signer/src/signerdb.rs::add_block_rejection_signer_addr`/`add_block_signature`.

### Proof of Concept
1. Miner proposes block `B`; `weight_threshold` = 70, `total_weight` = 100.
2. Signer A (weight 35) sends `BlockResponse::Rejected` for `B` with reason `NoSortitionView`. `stackerdb_listener.rs` sets `responded_signers.insert(A_slot)=true` and `total_weight_rejected = 35` [4](#0-3) .
3. The underlying condition clears (sortition view resolves); per `should_reevaluate_reject_reason`, signer A reconsiders and sends `BlockResponse::Accepted` for the same `B` [3](#0-2) .
4. `stackerdb_listener.rs`'s Accepted arm only checks `gathered_signatures` (empty for A), so it adds A's weight to `total_weight_approved` as well, without touching `total_weight_rejected` [5](#0-4) . Now `total_weight_rejected = 35` (stale) and `total_weight_approved = 35`.
5. A separate genuine rejecting signer B (weight ≥ 31) — enough to cross `total_weight_rejected.saturating_add(70) > 100` — sends its own real rejection. `total_weight_rejected` becomes ≥66, tripping `SignersRejected` in `SignerCoordinator::wait_for_signatures` [6](#0-5) , even though signer A's 35 weight is stale and A's real, current vote is "accept" — the true live rejecting weight is only 31 (< 30% blocking minority in this example would actually still need checking, but the scenario demonstrates that stale weight directly contributes to crossing the threshold that live weight alone would not reach).
