### Title
Unbounded zstd compression CPU cost for attacker-controlled account data in `encode_ui_account` (Base64Zstd) - ([File: account-decoder/src/lib.rs])

### Summary
`encode_ui_account`'s `Base64Zstd` branch invokes `zstd::stream::write::Encoder` on the full (or sliced) account data with no size cap or complexity check, unlike the `Base58`/`Binary` paths which enforce `MAX_BASE58_BYTES`. An attacker who owns an account can fill it with up to the max permitted account size of high-entropy bytes and force compression of that data on every single `getAccountInfo`/`getMultipleAccounts`/`getProgramAccounts` request specifying `encoding: "base64+zstd"`.

### Finding Description
In `encode_ui_account`, the `Base64Zstd` arm unconditionally compresses `slice_data(account.data(), data_slice_config)`: [1](#0-0) 

Compare this to the `Base58`/`Binary` path, which explicitly rejects data slices larger than `MAX_BASE58_BYTES` before encoding, and to `rpc/src/rpc.rs::encode_account`, which enforces the same `MAX_BASE58_BYTES` limit specifically for `Binary`/`Base58` but performs no analogous size or CPU-cost gating for `Base64` or `Base64Zstd`: [2](#0-1) 

`encode_bs58` itself checks slice length against `MAX_BASE58_BYTES` and returns an error string instead of encoding when data is too large: [3](#0-2) 

No equivalent check exists for `Base64Zstd`. `encode_ui_account`/`encode_account` is reached directly from `get_encoded_account`, which backs `getAccountInfo`, `getMultipleAccounts`, and `getProgramAccounts` RPC handlers: [4](#0-3) 

An attacker can write an account near the maximum permitted account data length filled with high-entropy (incompressible) bytes using an ordinary transaction (e.g., via `system_processor`'s allocate/write instructions or any program under attacker control), then issue a single `getAccountInfo(pubkey, {encoding: "base64+zstd"})` call. Zstd compression cost on incompressible data does not shrink with early termination the way it does on compressible data — the compressor still processes the entire input attempting to find matches, so CPU time scales with input size and is maximized precisely when data is high-entropy. This makes the per-request CPU cost dependent on attacker-authored account content and size rather than being bounded independently of it, violating the invariant that a single low-rate call's cost should be bounded by explicit limits.

### Impact Explanation
This falls into the "unbounded cost for a single low-rate call" scoped-impact category. A single `getAccountInfo` call with `base64+zstd` encoding against a max-size, high-entropy account forces the validator's RPC-serving thread to perform zstd compression proportional to the account size (up to the maximum permitted account data length) with no cap, unlike the existing `MAX_BASE58_BYTES` guard used for base58/binary encodings. Repeated at the permitted single-client rate (one call per `CLUSTER_SLOT_TIME_TARGET / 2`), this yields disproportionate, attacker-controllable CPU consumption on the RPC path relative to typical request costs, without requiring multiple clients or elevated privileges.

### Likelihood Explanation
Feasible and repeatable by any unprivileged client: the attacker needs only to own an account (which any user can create/write to, e.g., via allocate/write system instructions or a program they control) and fill it with attacker-chosen bytes up to the maximum account size, then repeatedly issue `getAccountInfo` with `encoding=base64+zstd` at the permitted call rate. No special validator/config access is required, and the vulnerable code path (`encode_ui_account`) is reachable from standard, widely used JSON-RPC methods.

### Recommendation
Add an explicit size/complexity cap for the `Base64Zstd` branch of `encode_ui_account` (and/or `encode_account`), analogous to `MAX_BASE58_BYTES` for `Base58`/`Binary`, rejecting or falling back to plain `Base64` encoding when the sliced account data exceeds a documented threshold. Alternatively, bound the compression level/effort (e.g., use a fast compression level, or use `zstd::bulk` with a hard byte limit and early bailout) so worst-case CPU time per request is capped regardless of entropy, and factor this cost explicitly into the RPC request cost accounting.

```rust
    let _ = encode_ui_account(

        &account,
        UiAccountEncoding::Base64Zstd,
        None,
        None,
    );
    let elapsed = start.elapsed();

    // Expected (fails today): compression of high-entropy max-size data should be
    // bounded by a documented per-request CPU budget (e.g., a few milliseconds),
    // enforced via a size cap or fast-path fallback to Base64 -- not linear in
    // attacker-controlled account size with no upper bound.
    assert!(
        elapsed.as_millis() < 50,
```

```rust
fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
```
