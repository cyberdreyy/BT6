### Title
Cross-user response hijacking via `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each in-flight request's callback keyed solely by the client-supplied `msg.Body.MessageId` string, with no binding to the sender's signer/address. Any authenticated (but otherwise unprivileged) gateway client can submit a second request reusing another user's in-flight `MessageId`, silently overwriting `h.savedCallbacks[MessageId]`, so the eventual DON response is delivered to the attacker's callback instead of (or as a denial of service against) the original submitter.

### Finding Description
`HandleLegacyUserMessage` saves the callback with: [1](#0-0) 
This map key is purely `msg.Body.MessageId`, a string field controlled entirely by the client. `Message.Validate()` only checks length/format of `MessageId`, never uniqueness or binding to the signer: [2](#0-1) 
The signature over the message (computed via `GetRawMessageBody`) proves who sent that particular message, but it does not prevent a *different* signer from choosing the *same* `MessageId` string as another user's in-flight request — the signature check only validates authenticity/integrity of the attacker's own message, not exclusivity of the ID space.

When the DON eventually responds, `handleWebAPITriggerMessage` looks up and deletes by `MessageId` alone and forwards to whichever callback is currently stored: [3](#0-2) 
If attacker's `HandleLegacyUserMessage('X')` call lands after victim's `HandleLegacyUserMessage('X')` but before the DON's response for `'X'` arrives, the map entry is overwritten with the attacker's `callback`. The subsequent DON response for `'X'` is then delivered via `savedCb.SendResponse(...)` to the attacker's callback — the victim's original callback reference is lost entirely, so the victim's HTTP request will hang until any surrounding request-level timeout at the transport layer, and the attacker receives the response payload that was intended to trigger the victim's workflow. This is a direct violation of the isolation invariant between per-user in-flight requests, using only unauthenticated/unprivileged access to the gateway's user-facing endpoint (no operator/admin/node access required).

### Impact Explanation
This maps to cross-user response confusion / request impersonation: an unprivileged gateway client can cause another user's trigger response to be delivered to the attacker (potential data/secret disclosure if the trigger response payload contains sensitive data), and/or cause denial of service against the legitimate user's request. This matches the "cross-user response confusion" impact class called out in the audit scope.

### Likelihood Explanation
Exploitability depends on the attacker being able to predict or observe another user's in-flight `MessageId` before the DON responds. If `MessageId` values are generated by clients using non-random/sequential or externally observable values, this is trivially exploitable; even with random client-chosen IDs, nothing in the protocol prevents deliberate reuse, and the collision window is bounded only by DON round-trip latency (which can be seconds), making a race feasible for a determined attacker who can guess or sniff the ID. No special credentials beyond normal gateway API access are needed — this is exploitable by any unauthenticated/unprivileged HTTP client of the gateway's legacy user message endpoint.

### Recommendation
Namespace `savedCallbacks` keys by both the sender (signer address extracted during `Message.Validate()`) and `MessageId` (e.g., `sender + ":" + MessageId`), or reject/overwrite-protect insertion with `sync.Map`'s `LoadOrStore` semantics so a colliding `MessageId` from a different sender is rejected with an error response rather than silently overwriting the existing callback. Additionally consider validating that resubmission of an identical `MessageId` from the *same* sender is idempotent rather than replacing the pending callback.

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler via `NewHandler`.
2. Build two `api.Message` with identical `Body.MessageId = "X"` but signed by two different private keys (simulate user A and attacker), each with a distinct `handlers.Callback` mock capturing `SendResponse` calls.
3. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` then immediately `h.HandleLegacyUserMessage(ctx, msgAttacker, callbackAttacker)`.
4. Assert `h.savedCallbacks["X"].Callback == callbackAttacker` (overwrite occurred) — expected/fixed behavior: either the second call fails validation/is rejected, or the map key is per-sender so both are stored independently.
5. Simulate DON response with `MessageId = "X"` via `h.handleWebAPITriggerMessage(ctx, respMsg, nodeAddr)`.
6. Assert `callbackAttacker.SendResponse` was invoked and `callbackA.SendResponse` was never invoked — demonstrating the victim's response was silently redirected/lost.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
