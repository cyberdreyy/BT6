### Title
A dust `requestWithdraw` during a 0-APR epoch permanently bricks `stopEpoch` once APR is raised, freezing all vault funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary

Analogous to the Envoy Gateway nil-dereference (a single unprivileged object causing a deterministic panic in a shared reconcile path that stalls processing controller-wide), a single dust `requestWithdraw` made while `unscaledApr == 0` writes an entry into the global `apr0TotalPrincipal` bucket. If the manager/borrower then sets a non-zero APR for the next epoch — a routine, honest operation — `prepareStopEpochWithApr0` reverts `NotAllowed` on every subsequent `stopEpoch` call. Because `apr0TotalPrincipal` can only be cleared inside that same reverting function (or via the post-default path), there is no in-protocol escape: the epoch state machine is permanently stuck and all LP funds are frozen.

### Finding Description

In `IdleCreditVault.requestWithdraw`, when `unscaledApr == 0` and the pool is not closed, the request is routed to `_requestWithdrawApr0`, which increments both the per-user `apr0Users[_user].principal` and the global `apr0TotalPrincipal` counter (`contracts/strategies/idle/IdleCreditVault.sol:285-286`, `:567-577`).

At the next `stopEpoch`, `IdleCDOEpochVariant` calls `prepareStopEpochWithApr0`, which contains the guard:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:502-508
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

`apr0TotalPrincipal` is only reset at line 540 — *after* the revert check — and the only other decrement path is `_clearWithdrawClaimForEpoch(_isClearingApr0 = true)`, reachable solely through `_claimDefaultedWithdrawRequest` after a default finalization (`:821-831`). `_settleApr0`, which runs inside normal claims, zeroes the per-user `principal` but never decrements `apr0TotalPrincipal` (`:545-565`), and `epochNumber` (the maturation gate for funded claims) is only bumped through the `deposit` call inside `stopEpoch` (`:607-610`), which never executes because `prepareStopEpochWithApr0` reverts first.

The intent of the guard is to prevent APR0 requests from accruing interest under a non-zero APR, but the implemented mechanism converts a user-created state into a global, unrecoverable revert in the epoch tick — the exact shape of the Envoy bug: one cheap unprivileged object → deterministic panic of the shared handler → all downstream processing stalls until admin intervention.

Attack sequence:
1. Vault runs an epoch with `unscaledApr == 0` (a legitimate configuration set by the manager).
2. Attacker (any KYC-passing lender) deposits a minimal amount and calls `requestWithdraw(1 wei, ...)` during the buffer period. `apr0TotalPrincipal = 1`.
3. Borrower/manager sets the next epoch APR to any non-zero value via `setAprs`/`setAprsWithBuffer` — a normal honest action (`IdleCreditVault.sol:206-220`).
4. `stopEpoch` calls `prepareStopEpochWithApr0`, hits `unscaledApr != 0` with `apr0TotalPrincipal != 0`, and reverts. Every retry reverts identically. `epochEndDate`, `epochNumber`, interest distribution, withdraw funding, and all claims stall permanently. Only an implementation upgrade (or borrower default + finalization, which is a catastrophic path) can release the funds.

### Impact Explanation

Permanent freezing of all funds held by the vault strategy and all unclaimed withdraw receipts. Honest LPs cannot deposit, withdraw, or claim; the borrower cannot repay through `stopEpoch`; `epochNumber` never advances so even already-funded requests stay immature. The cost to the attacker is a dust deposit and two transactions; the frozen amount is the entire vault TVL plus pending withdraw basis. This satisfies the "permanent freezing" impact class with quantified loss equal to the full pool NAV.

### Likelihood Explanation

The trigger requires only: (a) one epoch configured at `unscaledApr == 0` — a supported, documented mode (APR0 flow has dedicated accounting and tests), and (b) a later honest APR increase, which happens whenever the borrower's rate is renegotiated. No privileged actor misbehavior, no timing race, and no external dependency is needed. Any KYC'd lender with dust capital can stage the trap in advance; the blast radius is the whole vault, not just the attacker's position.

### Recommendation

Do not revert in `prepareStopEpochWithApr0` when `unscaledApr != 0`. Instead, settle the open APR0 bucket with zero incremental interest (skip the `_apr0NetInterest` block) and clear `apr0TotalPrincipal = 0` unconditionally, letting each user's principal migrate to `settledPrincipal` via `_settleApr0` at their next claim. Alternatively, keep the revert but provide a manager escape hatch that force-settles/cancels the APR0 bucket, or refund APR0 requesters at `requestWithdraw` time if APR was raised before their request matured. Also consider decrementing `apr0TotalPrincipal` inside `_settleApr0`/claims so stale buckets can drain without a stopEpoch.

### Proof of Concept

Foundry fork PoC (scaffold; assumes the standard `IdleCDOEpochVariant` + `IdleCreditVault` deployment helpers used in `test/foundry/`):

```solidity
// test/foundry/Apr0StopEpochBrick.t.sol
function test_dustApr0Request_bricksStopEpoch_afterAprRaised() external {
  // --- Setup: vault live, epoch buffer open, unscaledApr == 0 ---
  // manager has set apr to 0 for the current epoch:
  vm.prank(manager);
  strategy.setAprs(0, 0);

  // --- Attacker: KYC'd lender, dust deposit + withdraw request in buffer ---
  address attacker = makeAddr('attacker');
  _whitelist(attacker);                        // Keyring allow
  uint256 dust = 1;                            // 1 wei of underlying
  _depositWithUser(attacker, dust);            // cdoEpoch.depositAA(dust)
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(dust, address(aaTranche));
  assertEq(strategy.apr0TotalPrincipal(), dust);

  // --- Honest manager raises APR for next epoch ---
  vm.prank(manager);
  strategy.setAprsWithBuffer(5e18, cdoEpoch.epochDuration(), cdoEpoch.bufferPeriod());

  // --- Honest borrower repayment at epoch end: stopEpoch reverts forever ---
  vm.warp(cdoEpoch.epochEndDate() + 1);
  _fundBorrowerRepayment();                    // borrower approves + sends owed funds
  vm.prank(manager);
  vm.expectRevert(NotAllowed.selector);
  cdoEpoch.stopEpoch(0);

  // Retries and claims all revert identically; epochNumber never advances.
  vm.warp(block.timestamp + 365 days);
  vm.prank(manager);
  vm.expectRevert(NotAllowed.selector);
  cdoEpoch.stopEpoch(0);

  // LP funds (pre-existing deposits) are permanently frozen:
  assertEq(strategy.apr0TotalPrincipal(), dust);   // bucket can never be cleared
  assertTrue(cdoEpoch.isEpochRunning());           // epoch state machine stuck
}
```

Uncertainty note: I verified `prepareStopEpochWithApr0` is referenced from `IdleCDOEpochVariant.sol` (grep matched it among the stopEpoch code paths), but I was not able to read the full `stopEpoch` body to confirm the exact call ordering and whether any wrapper catches the revert. If `stopEpoch` swallows the error or `apr0TotalPrincipal` has another clearing path I did not see, the persistence claim would need re-checking; the revert condition itself, the dust-trigger, and the absence of any user-level cancellation are confirmed from `IdleCreditVault.sol`.
