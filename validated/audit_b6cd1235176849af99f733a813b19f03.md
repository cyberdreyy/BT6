### Title
Instant-withdraw "fast path" in `requestWithdraw` bypasses upfront withdrawal fees owed to feeReceiver - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
Analogous to XSA/CVE-2016-6258 — where Xen's PV pagetable "fast-path" update skipped the safety checks applied on the slow path, letting an unprivileged guest escalate — `IdleCDOEpochVariant.requestWithdraw` has a fast path that lets a withdrawing user skip checks/charges that the normal path enforces. When the APR drops between epochs (`lastEpochApr > unscaledApr + instantWithdrawAprDelta`), the request is routed to `creditVault.requestInstantWithdraw` and returns early, completely skipping `_totalWithdrawFees`, `pendingWithdrawFees` accrual, and `interestForOverUnderPerformance` bookkeeping.

### Finding Description
In `requestWithdraw` (contracts/IdleCDOEpochVariant.sol:739-791), the normal (slow) path computes `_calcInterestWithdrawRequest`, then `_totalWithdrawFees(principal, interest)` — an upfront management fee charged for the whole time the receipt sits outside live NAV (`_withdrawRequestManagementFeeDuration` = one full epoch plus any remaining buffer, lines 925-931) plus the performance fee on projected interest — and adds it to `pendingWithdrawFees` (line 778) which is later paid out to `feeReceiver`.

The instant branch (lines 761-770) takes `_underlyings = _trancheToUnderlyings(_amount, _tranche)` and immediately calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)`, burning the full-priced strategy tokens and minting a 1:1 receipt, with:

- no `_totalWithdrawFees` deduction — the receipt is redeemed at par from `collectInstantWithdrawFunds` / `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393, `_transferFundedClaim`),
- no increment of `pendingWithdrawFees`,
- no `interestForOverUnderPerformance` adjustment, even though an AA withdrawal removes principal that would have generated overperformance for BB.

The instant receipt is not economically different in wait time from a normal receipt: funds must still be pulled from the borrower via `getInstantWithdrawFunds` after `instantWithdrawDeadline` in the next epoch (lines 558-574), i.e. the receipt sits outside live NAV for buffer + part/all of an epoch — exactly the duration the management fee is meant to compensate. The Xen analog holds: the fast path performs the same privileged state transition (leaving live NAV, creating a funded claim on borrower cash) while omitting the invariant-enforcing logic (fee accrual) of the slow path.

### Impact Explanation
Every instant withdrawal permanently avoids the upfront management fee `_calculateManagementFee(principal, epochDuration + remainingBuffer)` and the performance fee on projected interest. For example, with `managementFee` = 1% annualized, a 30-day epoch, 5-day buffer, and a request made right at buffer start, a 1,000,000 USDC instant request skips ≈ `1e6 * 1% * 35/365 ≈ 958` USDC of fees; repeated every epoch cycle this compounds to ~1% of withdrawn TVL per year routed around `feeReceiver`. Because `pendingWithdrawFees` is never incremented, the loss is a direct, quantified theft of unclaimed yield (management/performance fees) from `feeReceiver`, not a rounding artifact. The missing `interestForOverUnderPerformance` diff additionally misstates `expectedEpochInterest` at the next `startEpoch` for AA exits, slightly mispricing BB's expected yield share.

### Likelihood Explanation
Requirements: `isInstantWithdrawEnabled` (non-prefunded, non-programmable variant, `disableInstantWithdraw == false`) and a decrease of `unscaledApr` by more than `instantWithdrawAprDelta` between epochs — a routine, honest manager operation whenever the borrower's rate is renegotiated down. Any KYC'd tranche holder (attacker within rules) can then call `requestWithdraw` and unconditionally take the fast path; there is no opt-in or additional check. No privileged cooperation and no oracle manipulation is needed; it triggers deterministically whenever the APR decreases, which is the designed trigger for instant withdrawals.

### Recommendation
Route instant withdrawals through the same fee accounting as the slow path before minting the instant receipt: compute `(interest, diff) = _calcInterestWithdrawRequest(...)`, charge `_totalWithdrawFees(principal, interest)` (or at minimum the upfront management-fee component for the receipt's time outside NAV), increment `pendingWithdrawFees` and `interestForOverUnderPerformance`, and pass the net-of-fee amount to `requestInstantWithdraw` while burning only principal via `_withdrawOps`. Alternatively, deduct the management fee at claim time inside `claimInstantWithdrawRequest`.

### Proof of Concept
Foundry fork sketch (based on `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testInstantWithdrawEvadesWithdrawFees() external {
    _setFeeParams(TL_MULTISIG, 10000, FULL_ALLOC, 1000); // 10% perf fee, 1% mgmt fee
    uint256 amountWei = 1_000_000 * ONE_SCALE;

    uint256 mintedAA = idleCDO.depositAA(amountWei);
    idleCDO.depositBB(amountWei);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    uint256 principal = cdoEpoch.maxWithdrawable(address(this), address(AAtranche));
    uint256 expectedMgmtFee = _calcManagementFee(
        principal, cdoEpoch.epochDuration() + remainingBuffer());

    // APR dropped (initialProvidedApr -> /2), so this takes the instant fast path
    uint256 requested = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));

    // BUG: nothing accrued for feeReceiver even though the receipt waits outside NAV
    assertEq(cdoEpoch.pendingWithdrawFees(), 0, "fast path skipped withdraw fees");

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.instantWithdrawDeadline() + 1);
    _getInstantFunds();
    cdoEpoch.claimInstantWithdrawRequest(); // paid at par, no fee deducted
    // feeReceiver loses ~expectedMgmtFee vs. an identical normal-path request
}
```

Compare with the same-size `requestWithdraw` executed when APR does not drop: `pendingWithdrawFees` increases by `_totalWithdrawFees` and the claim pays `principal + interest - fees`. The difference between the two payouts for the same tranche tokens and same wait is the quantified loss.
