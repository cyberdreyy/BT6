### Title
Multisig confirmations survive member removal, allowing a request to execute below the live-member threshold - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts entries in a request's `confirmations` set against `num_confirmations` without verifying that every recorded confirmer is still a current member. `delete_member` (and the v1 analog `DeleteKey`) only purges confirmations/requests that the removed member itself *created* — it does not scan other pending requests' `confirmations` sets to strip out the removed member's prior confirmation. A confirmation given by a member who is later removed therefore keeps counting toward the approval threshold on any request it was cast on, letting the request execute with fewer live, currently-authorized approvals than `num_confirmations` requires.

### Finding Description
The intended custody binding is: `confirmations recorded on a request == confirmations from members currently in self.members`. This binding is broken because member removal is not propagated to confirmation records on requests not authored by the removed member.

In `multisig2/src/lib.rs`:
- `confirm()` [1](#0-0)  increments/executes purely based on `confirmations.len()` reaching `self.num_confirmations`, with no re-validation that stored confirmers are still valid members.
- `delete_member()` [2](#0-1)  only removes requests where `r.member == member` (i.e., requests *created* by the removed member) and clears `num_requests_pk` for that member. It never iterates `self.confirmations` for *other* requests to remove the departing member's stale confirmation entries.
- `self.members.remove(&member)` deletes the member from the authorized set, but any `confirmations` bitset already containing that member's `to_string()` on an unrelated pending request is left untouched.

The identical pattern exists in the v1 contract `multisig/src/lib.rs`: `DeleteKey` only cleans requests signed by that key [3](#0-2) , and `confirm()` similarly just compares `confirmations.len() + 1 >= self.num_confirmations` [4](#0-3) .

Equality before/after the attacker action:
- Before: request R has confirmations `{A, B}` from members A and B, with `num_confirmations = 3` and members `{A, B, C, D}`. R is not yet executable (2 < 3).
- Attacker action: member A is removed via a `DeleteMember` request (executed by unrelated members, e.g. C+D+B), reducing live members to `{B, C, D}`.
- After: R's `confirmations` set still contains `{A, B}` (2 entries) even though A is no longer authorized. A single additional confirmation from any remaining member (e.g. C) makes `confirmations.len() + 1 = 3 >= num_confirmations = 3`, and R executes — despite only 2 currently-valid members (B, C) having actually approved it, one short of the configured 3-of-N threshold.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." Because the multisig account custodies NEAR (and can be granted access keys / hold wNEAR, staking-pool ownership, etc.), a request such as `Transfer` or `AddKey`/`FunctionCall` can be pushed through with fewer live approvals than the deployer configured, i.e., funds can be moved or the account taken over by fewer real authorized parties than intended.

### Likelihood Explanation
No foundation, redeploy, or victim key is required — this is triggered purely through the contract's own designed workflow: any request can be confirmed by a member who is later legitimately removed by the group (a routine operational action, e.g. offboarding an employee/rotating a compromised key), and the removal is performed exactly as documented. The bug is latent and requires no malicious deployment or ignored initialization; it is simply a missing cleanup step in `delete_member`/`DeleteKey`. Any team that adds a pending, unconfirmed/partially-confirmed request and later performs a normal member-removal request is exposed.

### Recommendation
When executing `DeleteMember` (or `DeleteKey` in v1), iterate over all entries in `self.requests`/`self.confirmations` and remove the departing member's confirmation from every request's confirmation set (not only requests it authored), or alternatively re-validate at `confirm()` time that the set of confirmers is a subset of `self.members` (filtering out stale/removed members) before comparing the count to `num_confirmations`.

### Proof of Concept
1. Deploy multisig2 with members `{A, B, C, D}` and `num_confirmations = 3`.
2. Member D creates a `Transfer` request R (`add_request`).
3. Member A confirms R (`confirm(R)`) — `confirmations = {A}` (1 of 3).
4. Member B confirms R — `confirmations = {A, B}` (2 of 3, not yet executed).
5. Members B, C, D create and confirm a `DeleteMember { member: A }` request and execute it (3-of-4 threshold met with B, C, D). `delete_member` removes A from `self.members` but does not touch R's `confirmations` set, which still contains A.
6. Member C confirms R (`confirm(R)`) — `confirmations.len() + 1 = 3 >= num_confirmations (3)` → R executes via `execute_request`, transferring funds, even though only B and C are currently valid members who approved it (2 of 3 live members), one short of the required threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
