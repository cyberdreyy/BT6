### Title
Unprivileged front-running of `LockupFactory::create` lets an attacker deploy a victim's lockup at the deterministic derived address with attacker-chosen terms - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the new lockup's account name purely from `hex::encode(&env::sha256(owner_account_id.as_bytes())[..20])` and takes every other lockup parameter (`lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, `whitelist_account_id`) directly from the caller with no check that the caller is the owner, the grantor, or the foundation. Since NEAR account creation via `Promise::create_account()` fails if the target account already exists, whoever calls `create()` first for a given `owner_account_id` permanently claims that address, so an attacker can pre-empt the legitimate grantor and install attacker-chosen terms (including an attacker-deployed contract used as `staking_pool_whitelist_account_id`) at the address the protocol and tooling treat as "the victim's lockup."

### Finding Description
The invariant the question asks to validate is:
`lockup_account_id = hex::encode(sha256(owner_account_id)[..20]) . factory` should carry `terms == terms_chosen_by(owner's grantor)`.

Tracing `create`: [1](#0-0) 
The only guard is `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)` — there is no `assert_called_by_foundation`, no check that `env::predecessor_account_id()` matches `owner_account_id` or any allow-listed grantor, and `whitelist_account_id` is taken verbatim from the caller: [2](#0-1) 

The account name is fully deterministic from `owner_account_id` alone: [3](#0-2) 

The lockup is then created via `Promise::new(lockup_account_id).create_account().deploy_contract(...).transfer(...).function_call("new", LockupArgs{...})`: [4](#0-3) 

On NEAR, `create_account()` on an already-existing account fails, and the failure is only detected asynchronously in the callback, which just decides whether to refund the caller — it performs no comparison against any "canonical" set of terms because none exists: [5](#0-4) 

Root cause: the factory has no registry, no owner-signature check, and no reservation mechanism — the address is squattable by race, and the first successful `create()` call for a given `owner_account_id` wins, permanently fixing `vesting_schedule`, `release_duration`, `lockup_duration/timestamp`, and — critically — `staking_pool_whitelist_account_id` (`TransfersInformation`/whitelist used by the lockup contract to gate delegation to staking pools). `LockupArgs.staking_pool_whitelist_account_id` defaults to the factory's configured whitelist only if the caller omits it; a caller can instead supply any `AccountId`, including one for a contract they deployed and control, which the lockup contract will then trust as its staking-pool whitelist for that owner's funds: [6](#0-5) 

Exploit flow:
1. Attacker learns (from off-chain/legal terms, or simply guesses) the `owner_account_id` that will receive a real grant, before the grantor calls `create()`.
2. Attacker deploys their own "whitelist"/staking-pool contract.
3. Attacker calls `LockupFactory::create(owner_account_id, ..., vesting_schedule=<favorable to attacker/none>, whitelist_account_id=Some(attacker_contract))` with `MIN_ATTACHED_BALANCE` NEAR attached.
4. The account `hex(sha256(owner_account_id))[..20].factory` is created and initialized with attacker-chosen terms and an attacker-controlled whitelist before the grantor's legitimate `create()` call.
5. When the real grantor later calls `create()` for the same `owner_account_id`, `create_account()` fails (account already exists), `on_lockup_create` detects this via `is_promise_success()` and simply refunds the deposit — the grantor cannot ever install the correct lockup at that address.
6. `owner_account_id`'s deposited/vested NEAR is now controlled by a lockup contract whose staking/whitelist parameters were chosen by the attacker, not the grantor, at the exact address every downstream integration (explorers, the foundation's tooling, `get_lockup_master_account_id`-based derivations) will treat as authoritative for that owner.

None of the existing guards (`assert_self`, `is_promise_success`, `MIN_ATTACHED_BALANCE` check) address this — they only guard the self-callback and deposit sizing, not caller authorization or address squatting.

### Impact Explanation
This matches Critical impact: "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The attacker permanently seizes the deterministic lockup address for an arbitrary target owner, fixes vesting/whitelist terms, and can point the owner's future staking delegation at a contract the attacker controls (a fake staking-pool/whitelist "poll" contract), setting up subsequent fund diversion once the real grant's NEAR lands in that lockup. The attack is repeatable against any `owner_account_id` whose lockup hasn't yet been created, is not limited to one victim, and requires no privilege beyond a plain NEAR account and `MIN_ATTACHED_BALANCE` (3.5 NEAR).

### Likelihood Explanation
Preconditions: attacker needs an ordinary NEAR account, `MIN_ATTACHED_BALANCE` NEAR, and knowledge (or a guess) of an `owner_account_id` that has not yet had its lockup created — grant recipients and their account IDs are frequently public/predictable (e.g. matching a well-known naming scheme) before the grantor executes the on-chain creation. Attacker cost is minimal (one deposit, refundable to the grantor on collision does not apply here — the attacker's creation succeeds, the grantor's later attempt is the one that gets refunded), and the race is winnable simply by front-running with normal transaction submission; no privileged role, key compromise, or contract redeploy is required. This is fully repeatable per target account.

### Recommendation
Require an authorization signal that only the legitimate grantor/owner possesses before allowing `create()` to succeed for a given `owner_account_id` — e.g., restrict `create()` to be callable only by `foundation_account_id` (as the trusted grantor), or require `env::predecessor_account_id() == owner_account_id`, or introduce a commit/reveal or allow-list of pending grants keyed by `owner_account_id` that only the foundation can populate before the actual lockup contract is deployed. Additionally, validate `whitelist_account_id` against a foundation-controlled allow-list rather than accepting an arbitrary caller-supplied `AccountId`.

### Proof of Concept
```rust
// lockup-factory/src/lib.rs tests module (cargo test)
#[test]
fn test_attacker_squats_owner_lockup_address() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker (not the grantor/foundation, not account_tokens_owner) calls create() first
    // for the victim's owner_account_id, naming their own "whitelist"/poll contract.
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(),           // victim's owner_account_id - attacker doesn't own this
        lockup_duration,
        None,
        None,                              // attacker's chosen vesting_schedule (none/favorable)
        None,
        Some(ValidAccountId::try_from("attacker-controlled-pool.near").unwrap()), // attacker's whitelist
    );

    // Simulate the create_account succeeding (attacker wins the race)
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    assert_eq!(contract.on_lockup_create(lockup_account(), ntoy(30).into(), String::from("attacker.near")), true);

    // Now the real grantor tries to create the legitimate lockup for the same owner_account_id.
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    // The account already exists -> create_account fails -> on_lockup_create refunds and returns false,
    // proving the legitimate grantor can never install correct terms at this address.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(account_tokens_owner()),
    );
    assert_eq!(res, false); // legitimate creation permanently blocked; attacker's terms remain live
}
```
This demonstrates: (a) `create()` has no authorization check tying `owner_account_id` to the caller, (b) the derived address is squattable via front-running, and (c) the legitimate grantor's subsequent `create()` call fails and is refunded, leaving the attacker-parameterised lockup as the sole contract living at that owner's derived address.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
