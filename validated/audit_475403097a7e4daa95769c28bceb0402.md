### Title
Loss-haircutted withdraw receipt is redeemed at par when the user has a newer request — `lastWithdrawRequest` lookup misses the older loss epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimWithdrawRequest` resolves loss-adjusted receipts by looking up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. only the user's *most recent* request epoch. If a user has a receipt from an older epoch that was haircut by `stopEpochWithDuration` (partial funding) and then makes a second withdraw request in a later epoch before claiming, the older receipt falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` — the full, unhaircutted aggregate basis — at par. The strategy only received the haircutted funding for the loss epoch, so the user is paid the missing loss amount out of underlyings that back other claimants.

### Finding Description
In `collectWithdrawFunds` (lines 411-430), when the borrower underfunds a stop (`_amount < pendingBasis`), the vault stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`, zeroes `pendingWithdraws`, and pulls only the haircutted `_amount`. Users are meant to recover the haircut via `_claimLossAdjustedWithdrawRequest` (lines 789-801), which uses `lastWithdrawRequest[_user]` as the epoch key, clears `withdrawsRequestsByEpoch[_user][lossEpoch]` and decrements the aggregate `withdrawsRequests[_user]` before paying `claimBasis * lossRecoveryPrice / RECOVERY_FULL`.

The bug: `lastWithdrawRequest[_user]` is overwritten by `requestWithdraw` (line 282) on every new request. A user with an unclaimed loss-adjusted receipt in epoch N who requests again in epoch N+1 gets `lastWithdrawRequest = N+1`. On the next `claimWithdrawRequest`:

- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N+1] == 0` and returns 0, never clearing the epoch-N basis out of `withdrawsRequests[_user]`.
- `_claimFundedWithdrawRequest` (lines 319-350) then pays `amount = withdrawsRequests[_user] + ...` at par — including the epoch-N principal that was only funded at `lossRecoveryPrice`.

The only solvency guard, `_transferFundedClaim` (lines 897-907), is inactive when `defaultRecoveryReserve == 0`, so the overpayment succeeds as long as the strategy holds enough underlying (e.g., funds deposited for other epochs' claims), leaving later claimants short — or the deficit reverts and permanently freezes remaining claims.

### Impact Explanation
The attacker recovers `(1 - lossRecoveryPrice) * epochNBasis` more than funded. Example: user requests 100,000 underlying in epoch N; stop funds only 70% → strategy holds 70,000 against that receipt. After a second request of 1 wei in epoch N+1 (funded at par), claim pays 100,000 + 1 → 30,000 stolen from underlyings owed to other receipts, breaking the "one receipt, funded payout" invariant and causing insolvency or permanent freezing for remaining claimants.

### Likelihood Explanation
Requires a partial-loss `stopEpochWithDuration` (borrower underfunds) and an affected receipt holder making any subsequent withdraw request before claiming — both reachable by ordinary users in normal operation. The attacker is just a tranche holder; sequencing around honest manager calls (stopEpoch, collectWithdrawFunds) is allowed. Cost is one extra `requestWithdraw` of minimal size.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, do not rely on `lastWithdrawRequest` as the sole lookup key. Either iterate the user's claim epochs via `withdrawsRequestsByEpoch`, or track the earliest unclaimed loss epoch per user. Alternatively, in `requestWithdraw`, revert (or force-claim) when the user's previous request epoch has a non-zero `lossRecoveryPriceByEpoch` entry that has not been cleared — symmetric to the existing post-default guard that requires claiming an open prior receipt (`testPostDefaultWithdrawRequiresClaimingOpenPriorReceipt`).

### Proof of Concept
Foundry fork sketch (mirror the setup helpers in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossReceiptPaidAtParAfterSecondRequest() external {
    address user = makeAddr('loss-user');
    uint256 amount = 100_000 * ONE_SCALE;
    _depositWithUser(user, amount, true);

    // Epoch N: user requests withdraw of half
    vm.prank(user);
    uint256 basis = cdoEpoch.requestWithdraw(AAtranche.balanceOf(user) / 2, address(AAtranche));

    _startEpochAndCheckPrices(0);
    // stopEpoch with a loss: borrower returns only 70% of pending
    // (manager calls stopEpochWithDuration/collectWithdrawFunds so
    //  lossRecoveryPriceByEpoch[N] = 0.7e18 and only 0.7*basis is funded)
    _stopEpochWithPartialFunding(basis * 7 / 10);

    // Epoch N+1: instead of claiming, user files a second tiny request
    vm.prank(user);
    cdoEpoch.requestWithdraw(1, address(AAtranche));
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();

    // BUG: paid basis*1 + 1 at par instead of basis*0.7
    assertEq(underlying.balanceOf(user) - balPre, basis + 1);
    // strategy is now short ~0.3*basis vs other funded claims
}
```

Key assertion: the claim succeeds and transfers the full pre-haircut basis, whereas `IdleCreditVault` only ever received `basis * lossRecoveryPrice / 1e18` for the epoch-N receipt — the difference is drawn from underlyings owed to other claimants.
