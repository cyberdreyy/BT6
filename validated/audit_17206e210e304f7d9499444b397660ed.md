### Title
`fullfillWriteOffRequest` lacks fulfiller access control, letting anyone front-run the borrower's negotiated write-off and steal the discounted tranche fill — (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` can be invoked by any wallet to settle a lender's open write-off request. The intended flow is an off-chain agreement between a lender and the borrower: the lender escrows tranche tokens at an agreed underlying price and the borrower fulfills the request to acquire the tranches and burn them via `writeOffDeposit`, retiring debt at a discount. Because the fulfiller identity is never constrained, an unprivileged attacker can observe the pending request and the borrower's fulfill transaction, front-run it, pay the lender the requested underlyings, and pocket the tranche tokens — capturing the borrower's negotiated discount and permanently DoSing that write-off.

### Finding Description
In `contracts/IdleCreditVaultWriteOffEscrow.sol`, `createWriteOffRequest` escrows a lender's tranche tokens along with a desired `underlyings` amount. `fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings)` (lines 123–155) then:
- requires the stored request to exactly match `_tranches` and `_underlyings >= currentRequest.underlyings` (line 129),
- pulls underlyings from `msg.sender`, deducts `exitFee`, pays the remainder to the lender `_user` (lines 139–149),
- transfers the escrowed tranche tokens to `msg.sender` (line 151).

There is no check that `msg.sender` is the borrower (or any intended counterparty), and the NatSpec even documents "this function can be called by any wallet" (line 122). This is the same defect class as `MarketERC20::permit` missing `msg.sender == spender`: a state-consuming action meant for a specific counterparty is executable by anyone who sees it, so the intended actor's transaction can be front-run and invalidated.

The borrower's negotiated benefit is concrete: in a write-off deal the tranches are priced below their claim value (otherwise the borrower would not agree, since they plan to burn them via `IdleCDOEpochVariant.writeOffDeposit`, which removes debt `1:1` with underlyings). An attacker who front-runs pays `_underlyings` and receives tranches whose redemption/claim value is higher — directly extracting the discount the borrower bargained for — while `delete userRequests[_user]` (line 135) guarantees the borrower's subsequent fulfill reverts with `WrongRequest`/`Is0`.

### Impact Explanation
- Direct value extraction: the spread between the tranches' value and the underlyings paid is transferred from the borrower to the attacker. If a lender escrows 100 tranche tokens for 80 underlyings, the front-runner pays 80, receives tranches worth ~100 of claim value, and the borrower loses the ~20-unit debt-reduction benefit it negotiated.
- Liveness/DoS of the write-off mechanism: each fill deletes the request, so the borrower's fulfillment path for that agreement is permanently consumed; the lender must re-create a request, and any fill remains front-runnable.
- Existing guards do not stop this: `nonReentrant`, `Is0`, and `WrongRequest` only validate request shape; nothing binds the fulfiller to `borrower` or to any counterparty embedded in the request.

### Likelihood Explanation
Write-off requests are stored on-chain in `userRequests` and the borrower's fulfill transaction is visible in the mempool, so detection and front-running are trivial for any EOA. The attacker only needs `_underlyings` of the underlying token and an approval — no privileged role. The attack is profitable whenever the negotiated price is below tranche claim value, which is the normal case for a write-off discount. It requires an active write-off agreement during a running epoch, which limits frequency but not feasibility.

### Recommendation
Bind the fulfiller or the counterparty in the request, mirroring `require(msg.sender == spender)` in the original report:

```diff
struct WriteOffRequest {
    uint256 tranches;
    uint256 underlyings;
+   address fulfiller; // address(0) = open to anyone
}
```

and in `fullfillWriteOffRequest`:

```diff
 if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
     revert WrongRequest();
 }
+if (currentRequest.fulfiller != address(0) && msg.sender != currentRequest.fulfiller) {
+    revert NotAllowed();
+}
```

Alternatively, restrict fulfillment to `msg.sender == borrower` if write-offs are only ever meant for debt retirement.

### Proof of Concept
Foundry fork test outline (mainnet fork of a deployed escrow with an active request):

```solidity
function test_frontRunWriteOffFill() public {
    // Setup: lender Alice creates request during running epoch
    vm.startPrank(alice);
    tranche.approve(address(escrow), 100e18);
    escrow.createWriteOffRequest(100e18, 80e6); // 100 tranches for 80 USDC
    vm.stopPrank();

    // Borrower intends to fulfill and writeOffDeposit; attacker sees tx in mempool
    uint256 attackerUsdcBefore = usdc.balanceOf(attacker);
    uint256 borrowerTranchesBefore = tranche.balanceOf(borrower);

    vm.startPrank(attacker);
    usdc.approve(address(escrow), 80e6);
    // Front-run: identical params, attacker as msg.sender
    escrow.fullfillWriteOffRequest(alice, 100e18, 80e6);
    vm.stopPrank();

    // Attacker captured the tranches (the borrower's negotiated discount)
    assertEq(tranche.balanceOf(attacker), 100e18);
    assertEq(tranche.balanceOf(borrower), borrowerTranchesBefore); // borrower got nothing
    assertEq(usdc.balanceOf(attacker), attackerUsdcBefore - 80e6);

    // Borrower's fulfill now reverts: request consumed
    vm.startPrank(borrower);
    usdc.approve(address(escrow), 80e6);
    vm.expectRevert(Is0.selector);
    escrow.fullfillWriteOffRequest(alice, 100e18, 80e6);
    vm.stopPrank();
}
```

The lender receives the agreed underlyings, so only the borrower is harmed — but the harm is real: the negotiated debt-discount is stolen and the write-off is permanently blocked for that request, exactly like the front-run `permit` DoSing the intended spender's action in the reference finding.
