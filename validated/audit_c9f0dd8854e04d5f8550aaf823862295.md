### Title
`action_create_account` allows squatting/pre-creation of NEAR-implicit account IDs, bypassing the "implicit accounts cannot be created via CreateAccount" invariant - (File: runtime/runtime/src/actions.rs)

### Summary
`action_create_account` only validates the target `account_id` against `is_top_level()`, a registrar-only length threshold, and `is_sub_account_of(predecessor_id)`; it never checks `account_id.get_account_type() != NamedAccount`. Because a 64-lowercase-hex string contains no `.` and therefore satisfies `is_top_level()`, and its length (64) already exceeds `min_allowed_top_level_account_length` (32), **any unprivileged account** — not only the registrar — can execute `CreateAccount` with a target `account_id` equal to a victim's NEAR-implicit (hex-public-key) address, install its own key via a batched `AddKey`, and permanently squat that address before the legitimate key holder's funds arrive.

### Finding Description
`action_create_account` (runtime/runtime/src/actions.rs:167-210) performs exactly two checks:
- If `account_id.is_top_level()`, it only blocks creation when `account_id.len() < min_allowed_top_level_account_length` AND `predecessor_id != registrar_account_id` [1](#0-0) .
- Otherwise it requires `account_id.is_sub_account_of(predecessor_id)` [2](#0-1) .

There is no call to `get_account_type()` anywhere in this function, and no rejection when the target `account_id` matches the `NearImplicitAccount` pattern (64 lowercase hex chars). Since a 64-hex-char string has no dot, `is_top_level()` returns true; since its length (64) is not below `min_allowed_top_level_account_length` (32 on mainnet), the registrar-only branch is never triggered — the length/registrar gate only restricts *short* top-level names, not implicit-length ones. Consequently **any** account (not just the registrar) can submit:

```
Transaction { predecessor: attacker.near, actions: [
  CreateAccount { account_id: "<64-hex-victim-pubkey>" },
  AddKey { public_key: attacker_key, permission: FullAccess }
]}
```

`action_create_account` sets `*actor_id = account_id.clone()` after creation (runtime/runtime/src/actions.rs:203), so the subsequent `AddKey` action in the same receipt executes with `actor_id` equal to the newly created account, authorizing the attacker to install their own full-access key on it.

Because the account now already exists (created as a `NamedAccount` with `AccountContract::None` and no keys until the attacker's `AddKey`), the protocol's implicit-account auto-creation path (triggered only when the target account does not yet exist and the first action is a `Transfer` to a `NearImplicitAccount`-typed `receiver_id`) is bypassed for any future transfer to that hex address — that logic only fires for a non-existent account. The genuine holder of the private key corresponding to that hex string can never claim the account through the normal implicit-account mechanism, since it is no longer non-existent and no key matching their public key was ever added.

This directly contradicts the stated protocol invariant in docs/DataStructures/Account.md:117 ("Implicit account can not be created using CreateAccount"), which `action_create_account` does not actually enforce.

### Impact Explanation
An unprivileged attacker can pre-emptively squat any NEAR-implicit account address (i.e., any hex-encoded public key) by creating it as a named account and installing their own key, before the legitimate key holder ever uses it. Any subsequent `Transfer` sent by a third party to that address — the normal way funds are sent to a NEAR-implicit account — credits the balance to an account fully controlled by the attacker, resulting in theft of the transferred funds. This matches the "theft of user funds" / "authorization escalation across accounts" bounty category.

### Likelihood Explanation
- No privileged role is required: `registrar_account_id` is irrelevant because 64 ≥ `min_allowed_top_level_account_length`.
- The attacker only needs to know the victim's implicit account_id in advance, which is exactly the public information victims routinely share to receive NEAR transfers (it is the hex encoding of their public key).
- Cost to the attacker is limited to the standard account-creation/storage-staking deposit, and the attack is fully repeatable against any target hex address not yet claimed on-chain.
- The attack requires no special timing beyond acting before the victim's private key is otherwise registered on-chain (e.g., before the victim receives any prior transfer that would auto-create the implicit account).

Note: I was not able to fully verify within this session whether `runtime/runtime/src/verifier.rs` (which also references `CreateAccount`) performs any additional semantic check on `account_id` type for `CreateAccount` actions at validation time; the core creation logic in `action_create_account` itself, however, contains no such check.

### Recommendation
In `action_create_account`, reject the action when `account_id.get_account_type() != AccountType::NamedAccount` (i.e., explicitly disallow creating any account whose `account_id` is of `NearImplicitAccount` type), returning an `ActionErrorKind` error, regardless of `is_top_level()`/registrar/sub-account checks passing.

### Proof of Concept
Add a unit test in `runtime/runtime/src/actions.rs` (or an integration test in `integration-tests/src/tests/standard_cases/mod.rs`):
1. Construct a 64-lowercase-hex `AccountId` (a valid NEAR-implicit-style id) and verify `account_id.get_account_type() == AccountType::NearImplicitAccount`.
2. Call `action_create_account` with `predecessor_id` set to an arbitrary funded, non-registrar account and this `account_id`.
3. Assert today's actual behavior: `result.result` is `Ok(())` and `account` is `Some(Account { .. AccountContract::None .. })` — demonstrating the account is silently created.
4. Assert the expected/fixed behavior: the call should instead set `result.result` to an `Err(ActionErrorKind::...)` (e.g., a new `CreateAccountNotAllowed`/implicit-specific error), and `account` should remain `None`.
5. As an end-to-end confirmation, in an integration/test-loop test, batch `CreateAccount` + `AddKey(attacker_key)` targeting a hex `account_id` corresponding to a known keypair, then submit a `Transfer` from a third party to the same `account_id`, and assert the transferred balance is only accessible via the attacker's key and not via the original keypair — confirming fund misdirection.
