## Analog Found: Stale confirmations from removed multisig members count toward quorum

### Title
Removing a multisig member/key does not purge their existing confirmations on other pending requests, allowing a request to execute below the intended live-member threshold - (`multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
The reported bug is a class of "stale state counted toward a live-set boundary": the ZeroLocker `merge` lets an *expired* lock's end time be silently extended, letting a party cross a schedule boundary (max lock duration / reward-checkpoint continuity) that should have been reset. The same bug class — treating a party's earlier state as still valid after the party is no longer a bona-fide member of the trusted set — is reachable in this repository's multisig contracts: `DeleteMember` (`multisig2`) and `DeleteKey` (`multisig`) remove a departing member from the members set, but never scrub that member's *existing confirmations* recorded on other, still-pending requests. Those stale confirmations continue to count toward `num_confirmations` in `confirm()`, so a request can execute with fewer currently-live confirming members than the threshold requires.

### Finding Description
`confirm()` in both `multisig2/src/lib.rs` and `multisig/src/lib.rs` counts entries in the per-request `confirmations` set and executes the request once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

When a member is removed via `delete_member` (multisig2) or the `DeleteKey` action (multisig v1), the cleanup logic only removes **requests originated by that member** (`r.member == member` / `r.signer_pk == pk`) and only that member's own `num_requests_pk` bookkeeping entry: [2](#0-1) [3](#0-2) 

Neither routine iterates over the `confirmations` map to strip the departing member's prior confirmations from *other* requests they merely confirmed (but did not create). Those confirmation entries remain keyed by the member's `to_string()` (multisig2) or `PublicKey` (multisig v1) inside the `HashSet` for that `request_id`.

Binding that should hold: `confirmations_counted(request) == confirmations_from_current_members(request)`. After a `DeleteMember`/`DeleteKey` execution, this equality is broken: `confirmations_counted(request) > confirmations_from_current_members(request)` for any request the removed member had confirmed before being removed.

### Impact Explanation
This lets a request reach the confirmation threshold and execute (`Transfer`, `FunctionCall`, `AddKey`, etc.) using fewer than `num_confirmations` distinct *current* members — i.e. "a multisig request executed below threshold," matching the Critical impact bucket. Because `execute_request` can perform `Transfer` of NEAR held by the multisig account, this directly threatens custody of funds controlled by the contract: NEAR can move on the authority of a stale confirmation from an account/key that has already been revoked from the trust set.

### Likelihood Explanation
No special privilege is required beyond being (at the relevant time) any member of the multisig — a routine operational sequence (member churn plus overlapping in-flight requests) triggers it. It only requires: (1) a request created and partially confirmed, (2) removal of one of the confirming members via a separate, otherwise-legitimate `DeleteMember`/`DeleteKey` request, and (3) enough remaining live confirmations to reach the (unchanged) threshold together with the stale one. This is plausible in any multisig with active member turnover and multiple concurrent pending requests, which the `active_requests_limit` mechanism (default 12 per member) explicitly anticipates.

### Recommendation
On `delete_member` / `DeleteKey`, iterate the `confirmations` map and remove the departing member's entry from every pending request's confirmation set (not just requests they originated). Alternatively, re-validate at `confirm()`-time / execution-time that every entry inside `confirmations` for the request still corresponds to a current `member` of `self.members` before counting it toward the threshold.

### Proof of Concept
1. Initialize multisig with members `A, B, C, D` and `num_confirmations = 3`.
2. `A` calls `add_request` to create `R1` (e.g. `Transfer{amount}`).
3. `B` calls `confirm(R1)` → `confirmations = {B}` (1 < 3, stored, not executed).
4. `C` calls `confirm(R1)` → `confirmations = {B, C}` (2 < 3, stored, not executed). [4](#0-3) 
5. Separately, `A`, `B`, `D` confirm a `DeleteMember{member: C}` request reaching quorum; `delete_member` removes `C` from `self.members` but does **not** touch `R1`'s confirmations set, since `R1` was not created by `C`. [5](#0-4) 
6. `D` calls `confirm(R1)` → `confirmations.len() (2, including removed member C) + 1 >= 3` → `R1` executes via `execute_request`, transferring NEAR, even though only `B` and `D` are still live confirming members (2 of 3 required live confirmations, not 3).

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
