### Title
Buffer-phase deposit captures vault PnL and borrower interest accrued before the deposit, because `getContractValue` excludes `ProgrammableBorrower` assets - ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol), [File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
The GeVault bug is "fee/yield collected only after shares are minted, so a flash-depositor steals pre-accrued yield." The analog exists in programmable-borrower mode: yield earned by the borrower's ERC4626 sleeve and borrower interest repaid during the buffer period are tracked in `ProgrammableBorrower.bufferedVaultDelta` / `bufferInterest`, but are **not** part of `getContractValue()`. A KYC'd attacker can deposit during the buffer at a NAV that excludes this accrued yield, then receive a pro-rata share of it when the next `stopEpoch` folds `totalInterestDueNow()` into tranche prices.

### Finding Description
`IdleCDOCreditVault.getContractValue()` only counts the CDO's own `strategyToken` and `token` balances minus `unclaimedFees` [1](#0-0) . In programmable mode the pool's lent capital lives in `ProgrammableBorrower` (as ERC4626 vault shares + cash), so this NAV view excludes all yield parked there.

`ProgrammableBorrower` tracks exactly the excluded yield:
- `bufferedVaultDelta`: ERC4626 PnL generated between `onStopEpoch` and the next `onStartEpoch` [2](#0-1) .
- `bufferInterest`: borrower interest repaid while the pool is in buffer [3](#0-2) .
- `onStartEpoch` snapshots `bufferedVaultDelta` into the epoch baseline [4](#0-3)  and `totalInterestDueNow()` later returns `vaultInterest + borrowerInterestAccruedNow() + bufferInterest` at `stopEpoch` [5](#0-4) , where it raises tranche prices for **all** current holders.

Meanwhile `_deposit` mints shares via `_updateAccounting()` → `getContractValue()` [6](#0-5) , which never reads `ProgrammableBorrower` state. Deposits are only paused inside `startEpoch` (`_pause()` at line 246), so the entire buffer window is open to any `isWalletAllowed` user. `depositDuringEpoch` is correctly blocked for programmable borrowers [7](#0-6) , but that guard does not cover buffer deposits.

Attack sequence (buffer phase, programmable/minted-interest mode):
1. Epoch N stops; ERC4626 vault keeps earning. Attacker watches `bufferedVaultDelta`/`bufferInterest`/`totalInterestDueNow` grow (all public).
2. Just before `startEpoch`, attacker calls `depositAA`/`depositBB`. `_updateAccounting` checkpoints a NAV that excludes the buffered yield, so shares are minted at a price not including that gain.
3. Manager calls `startEpoch` → `onStartEpoch` carries `bufferedVaultDelta` into `epochStartVaultAssets` baseline accounting, and `stopEpoch` later adds it to `expectedEpochInterest`, raising `priceAA`/`priceBB` for everyone including the attacker.
4. Next buffer, attacker calls `requestWithdraw`/`claimWithdrawRequest` and exits with principal + a pro-rata cut of yield earned entirely before they entered.

Existing guards do not stop this: `_skimDonatedAssets` only removes raw `token` donations to the CDO, `_accrueManagementFee` only checkpoints fees, and KYC is available to unprivileged lenders.

### Impact Explanation
Direct theft/dilution: the attacker captures `attackerShares / totalSupply` fraction of `bufferedVaultDelta + bufferInterest` that was generated by pre-existing LPs' capital. With a large buffer-period vault yield (e.g., 100k on 1M NAV) a flash-sized 9M deposit captures ~90% of it; the attacker bears almost no risk since the accrued value is observable on-chain before depositing. The symmetric loss case is avoided by simply not depositing when `bufferedVaultDelta < 0`.

### Likelihood Explanation
Requires a programmable-borrower vault where idle capital sits in a yield-bearing ERC4626 during buffer (the designed configuration), and the buffer period must be long enough to accrue meaningful yield or buffer borrower repayments. Any KYC-passing lender can execute it with no privileged role. Likelihood is moderate-to-high whenever buffer yield is nonzero; magnitude scales with buffer duration and vault APY.

### Recommendation
Include pending programmable-borrower yield in the deposit-time NAV, or gate buffer deposits until accrued buffer yield is realized. Concretely, in `IdleCDOCreditVault._updateAccounting`/`_deposit` (or a dedicated NAV path), add `IdleCreditVault(strategy)`'s view of `IProgrammableBorrower(borrower).totalInterestDueNow()` (or the buffer components `bufferedVaultDelta`/`bufferInterest`) to `getContractValue` when `isProgrammableBorrower && !isEpochRunning`, so `_mintSharesAtCurrPrice` prices in pre-deposit yield. Alternatively, restrict `depositAA`/`depositBB` while a positive unclaimed buffer delta exists, or settle buffer yield into `unclaimedFees`/NAV at `stopEpoch`/`startEpoch` before reopening deposits.

### Proof of Concept
Foundry fork/test sketch (extend `test/foundry/IdleCreditVault.t.sol` programmable-borrower setup):

```solidity
function testBufferDepositStealsBufferedVaultYield() external {
    // programmable borrower vault (APR=0 tranche mode), e.g. ERC4626Mock as `vault`
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                       // honest LP
    _transferBurnedTrancheTokens(address(this), true);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, /*newApr*/ 0, _expectedFundsEndEpoch()); // buffer begins

    // Simulate ERC4626 vault yield during buffer: donate assets to the vault
    uint256 bufferedGain = 1_000 * ONE_SCALE;
    deal(defaultUnderlying, address(erc4626Vault), bufferedGain);
    // bufferedVaultDelta is now > 0 (readable via ProgrammableBorrower views after next startEpoch)

    // Attacker (KYC'd user) deposits during buffer at NAV excluding bufferedGain
    address attacker = makeAddr('attacker');
    _whitelistUser(attacker);
    uint256 attackDeposit = 90_000 * ONE_SCALE;
    deal(defaultUnderlying, attacker, attackDeposit);
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(idleCDO), attackDeposit);
    uint256 minted = idleCDO.depositAA(attackDeposit);
    vm.stopPrank();

    // Run epoch and stop it: totalInterestDueNow() folds bufferedGain into tranche price
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, 0, _expectedFundsEndEpoch());

    // Attacker withdraws and captures ~90% of bufferedGain it never earned
    uint256 price = cdoEpoch.virtualPrice(address(AAtranche));
    uint256 attackerValue = minted * price / ONE_TRANCHE_TOKEN;
    assertGt(attackerValue, attackDeposit + bufferedGain * 9 / 10 - 1);
}
```

Uncertainty note: exact wiring of `bufferedVaultDelta` into `totalInterestDueNow` at the next stop (vs. buffer) was verified via `onStartEpoch`/`_vaultNetInterest`, but I could not fully trace whether an additional checkpoint inside `stopEpoch`/`prepareStopEpochWithApr0` excludes buffer yield from minted-interest crediting; if the buffer delta is credited only to tranche holders existing at `epochStart` snapshot rather than pro-rata at stop, severity drops. The core NAV exclusion at deposit time is confirmed.
