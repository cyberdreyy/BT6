### Title
Rejection-weight aggregation permanently drops a signer's vote after its first rejection, due to a `PRIMARY KEY (signer_addr)`-only schema in `block_rejection_signer_addrs` - (File: `stacks-signer/src/signerdb.rs`)

### Summary
The `block_rejection_signer_addrs` table, which records which signers rejected which block (used to tally rejection weight for the global-rejection threshold), is declared with `PRIMARY KEY (signer_addr)` only — not `(signer_signature_hash, signer_addr)`. `add_block_rejection_signer_addr` looks up an existing row scoped by `(signer_signature_hash, signer_addr)`, finds none for a *new* block even though the same `signer_addr` already owns a row for a *different* (earlier) block, and then issues a plain `INSERT`, which fails on the real primary-key (`signer_addr`) uniqueness constraint. The caller treats this as a soft failure (logs a warning) and continues, silently omitting that signer's vote from the rejection tally for every block after the first one it ever rejected.

### Finding Description
The table is created as: [1](#0-0) 

Note the primary key is `(signer_addr)` alone, even though the comment above it explicitly reasons about `signer_signature_hash` uniquely identifying a block — the composite key that the logic actually needs is not what was declared.

`add_block_rejection_signer_addr` queries for an existing row scoped to `(signer_signature_hash, signer_addr)`: [2](#0-1) 

If that specific `(block, signer)` pair has no row (which is always true the first time this signer rejects *this particular* block, even if it has already rejected a *different* block earlier), the code falls into the `None` branch and performs a bare `INSERT`: [3](#0-2) 

Because the table's actual primary key is only `signer_addr`, this `INSERT` collides with the row the same address already owns for the earlier block, and `self.db.execute(insert_qry, ...)` returns a `DBError` (SQLite constraint violation) instead of succeeding.

The caller, `store_and_process_block_rejection`, does not treat this error as fatal to the flow — it only logs and falls through to keep tallying: [4](#0-3) 

It then reads back the persisted rejection set to compute `total_reject_weight`: [5](#0-4) 

Since the failed `INSERT` never persisted the new rejection, `get_block_rejection_signer_addrs` for the current block will never include this signer's vote, and this repeats for every subsequent block that signer rejects for the remainder of the signer-db's life (the key collision recurs on every insert attempt once one row exists for that address).

This directly breaks the aggregated-weight vs. verified-rejections equality that the global-rejection tally depends on: `self.signer_db.get_block_rejection_signer_addrs(block_hash)` is supposed to return the true set of rejecting signers and their weights, but it will structurally omit any signer address that has rejected more than one distinct block over the life of the database.

### Impact Explanation
This degrades the liveness of the global-block-rejection mechanism: as the fleet operates, most signers will eventually reject more than one proposal (stale proposals, duplicate tenure-change proposals, reorg-not-allowed proposals, etc., are all routine and common per `docs/signer-flows.md` §3–6). Every additional rejection an address makes after its first ever recorded rejection is dropped from the persisted rejection set, permanently under-counting that signer's contribution to `total_reject_weight` for every future block. Because `total_reject_weight.saturating_add(min_weight) <= total_weight` is the gate that decides whether the 30%+ rejection threshold has been met, this under-count can prevent a genuinely-invalid/non-canonical block from ever reaching `mark_globally_rejected`, wedging that side of the state machine (the block just sits, retried/re-evaluated, never terminally rejected) rather than the two known-good terminal outcomes (`LocallyAccepted`→`GloballyAccepted` or the rejection path). This is a liveness wedge on the rejection tally, reachable by ordinary chain activity without needing a majority of signers or another signer's key — any single signer address rejecting two different blocks over its lifetime triggers it.

### Likelihood Explanation
High likelihood of being triggered organically: a signer only needs to send two rejections for two different blocks over the lifetime of its `signer_db` (no reward-cycle scoping in the key) for the bug to manifest, and rejections for stale/duplicate/invalid proposals are a normal, frequent occurrence per the documented flows (`docs/signer-flows.md` §3, §6). No majority collusion, no key compromise, and no direct attacker control of the DB is required — a normal miner submitting a second bad/duplicate proposal is enough to have any given signer's second rejection silently dropped.

### Recommendation
Change the primary key of `block_rejection_signer_addrs` to the composite `(signer_signature_hash, signer_addr)` (matching the query patterns already used throughout `add_block_rejection_signer_addr`/`get_block_rejection_signer_addrs`), with an accompanying schema migration to rebuild the table (similar in style to `MIGRATE_BLOCKS_TABLE_2_BLOCKS_TABLE_3`). Additionally, `store_and_process_block_rejection` should treat an `Err` from `add_block_rejection_signer_addr` as a reason to abort further weight computation for this event rather than silently continuing with a query that is now known to be incomplete.

### Proof of Concept
1. Signer `S` (address `A`) rejects block `B1` (any RejectReason). `add_block_rejection_signer_addr(B1, A, code1)` inserts a row `(B1, A, code1)` successfully — this is the only row `A` will ever successfully own, because the real primary key is `(A)`.
2. Later, the same signer `S` rejects a different block `B2` (e.g., a stale re-proposal, or `DuplicateBlockFound`). `add_block_rejection_signer_addr(B2, A, code2)`:
   - The `SELECT ... WHERE signer_signature_hash = B2 AND signer_addr = A` finds nothing (correctly, since no row exists for `B2`).
   - Code proceeds to `INSERT INTO block_rejection_signer_addrs (B2, A, code2)`, which violates the actual table `PRIMARY KEY (signer_addr)` because row `(B1, A, code1)` already occupies key `A`. SQLite returns a constraint-violation error, propagated as `DBError`.
3. `store_and_process_block_rejection` logs a warning on `Err(e)` but does not `return`; it proceeds to call `get_block_rejection_signer_addrs(B2)`, which returns the persisted rows for `B2` — `A`'s vote is absent.
4. `total_reject_weight` for `B2` is computed without `A`'s weight, permanently, for `B2` and every future block `A` ever rejects, unless/until the whole `signer_db` file is wiped.

**Unresolved/uncertain aspects:** I could not find a later `ALTER TABLE`/migration that redefines `block_rejection_signer_addrs` with a composite primary key elsewhere in the indexed codebase (only one `CREATE TABLE` definition and one index-creation statement (`CREATE_INDEXES_3`) reference this table across `stacks-signer/src/signerdb.rs`), but the size limits on the index mean I cannot rule out with full certainty that some later schema-version migration alters this table outside what was surfaced by search. If such a migration exists and changes the primary key, this finding would not apply to current releases; a Devin session with full repository access could confirm this by checking every `SchemaVersion` migration block in `stacks-signer/src/signerdb.rs` for `block_rejection_signer_addrs`.
