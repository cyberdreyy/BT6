### Title
`lending_account_withdraw` silently returns less than requested with no slippage protection during deleverage/bankruptcy wind-down - (File: programs/marginfi/src/instructions/marginfi_account/withdraw.rs)

### Summary
The TAP `Escrow.redeem()` bug class — a function that silently returns `min(requested, available)` instead of reverting when the full amount can't be honored, giving no way for the caller to enforce a minimum acceptable output — has a direct analog in marginfi-v2's `lending_account_withdraw`. When a bank has the `TOKENLESS_REPAYMENTS_COMPLETE` flag set, the withdrawal amount actually paid out is silently clamped to whatever liquidity remains in the vault, with no parameter allowing the user to specify a minimum acceptable amount and no revert if less than requested is delivered.

### Finding Description
In `lending_account_withdraw`, after the user's share/balance accounting is computed as `amount_pre_fee` (either the explicit `amount` or the full balance via `withdraw_all`), the code performs an unconditional clamp: [1](#0-0) 

```
// If in deleverage mode and deleverage is complete, you get what's left!
let amount_pre_fee = if bank.get_flag(TOKENLESS_REPAYMENTS_COMPLETE) {
    let actual = accessor::amount(&bank_liquidity_vault.to_account_info())?;
    ...
    u64::min(amount_pre_fee, actual)
} else {
    amount_pre_fee
};
```

There is no `amount` in the instruction that lets the caller state a minimum acceptable withdrawal, and no check that the clamped `amount_pre_fee` is `>=` some caller-supplied floor — the transaction proceeds and transfers whatever `min(requested, actual)` computes to, exactly like the reported `Escrow.redeem()` pattern of `min(escrowBalance, aggregatedAmount)`. This is reachable by any ordinary (unprivileged) account holder calling the permissionless `lending_account_withdraw` instruction — it is not gated behind an admin or privileged role check; only the *bank* needs the `TOKENLESS_REPAYMENTS_COMPLETE` flag (set automatically or by risk admin per `guides/ADMIN/BANK_STATE.md`) which is a normal operational state a bank enters during deleverage wind-down.

The tests confirm this is executable end-to-end and that the user is expected to simply "get what's left": [2](#0-1) [3](#0-2) 

The share/asset accounting for the user's balance is already fully decremented for `amount_pre_fee` (based on `bank_account.withdraw()`/`withdraw_all()`) **before** the clamp is applied — i.e., the accounting was already computed on the pre-clamp amount, and the clamp only affects how many tokens are physically transferred out via `bank.withdraw_spl_transfer`. If `amount_pre_fee` (post clamp) is less than the true value of shares burned, the difference is simply lost to the user with no possibility of reverting or re-attempting for the full amount, and the on-chain event still reports the clamped `amount_pre_fee` — masking the shortfall in only the emitted logs, not restoring the shares. [4](#0-3) [5](#0-4) 

### Impact Explanation
A user withdrawing from a bank in `TOKENLESS_REPAYMENTS_COMPLETE` state can have their shares burned for the full requested amount while only receiving whatever fraction of that amount happens to remain in the liquidity vault at the instant their transaction lands — with zero on-chain guarantee or revert path. In a race among multiple depositors during a wind-down (deleverage/bankruptcy resolution), the vault balance can be depleted by earlier withdrawers, so later withdrawers silently receive far less value than their burned shares represented, with no way to protect themselves by specifying a minimum acceptable output. This is a concrete value-redirection/misvaluation issue with direct financial effect on ordinary users, matching the TAP bug class exactly (no slippage protection on a "get what you get" redemption path).

### Likelihood Explanation
This requires only that a bank be in the documented `TOKENLESS_REPAYMENTS_COMPLETE` state (a normal, non-privileged, expected end state of the deleverage/bankruptcy wind-down flow per `guides/ADMIN/BANK_STATE.md`) and that multiple ordinary users race to withdraw while remaining vault liquidity is insufficient to cover all outstanding claims — a realistic and even expected scenario during wind-down, as evidenced by the existing test explicitly exercising "gets just what's left in the liquidity vault!". No admin/privileged action or governance compromise is needed to trigger the loss; it can occur under ordinary wind-down conditions.

### Recommendation
Add an optional `min_amount_out` (or similar) parameter to `lending_account_withdraw` (and equivalent instructions gated by the same clamp) that the caller can specify. After computing the clamped `amount_pre_fee`, require `amount_pre_fee >= min_amount_out` (when supplied) or revert with a clear error (e.g., `InsufficientVaultLiquidity`), so users are not silently short-changed and can choose to wait, retry, or take other action instead of unknowingly accepting a partial redemption.

### Proof of Concept
1. Admin sets `TOKENLESS_REPAYMENTS_ALLOWED` on a bank and performs deleverage repayments; once liabilities reach zero, `TOKENLESS_REPAYMENTS_COMPLETE` auto-sets (per `guides/ADMIN/BANK_STATE.md` bit 6).
2. Two depositors, User A and User B, each hold shares in the bank worth 1000 tokens, but the liquidity vault only holds 1000 tokens total (typical post-bankruptcy state, as modeled in `tests/specs/bankruptcy/zb02_e2eSunset.spec.ts`).
3. User A calls `lending_account_withdraw` with `withdraw_all = true`, requesting the full 1000 tokens they are entitled to. Their shares are burned in full (`bank_account.withdraw_all`), but the clamp `u64::min(amount_pre_fee, actual)` reduces the payout to whatever remains after prior withdrawals in the vault.
4. If User B's transaction landed first (or interleaves), User A may receive 0 or a fraction of the 1000 tokens they were owed, with the transaction succeeding and their position permanently closed — with no parameter to have reverted the transaction to protect against this outcome, exactly mirroring the TAP `redeem()` no-slippage-protection bug class.
