### Title
Fail-open handling of `get_tenure_tip` RPC error lets a signer sign a block that conflicts with a previously signed block whose reorg permit no longer stands - (File: stacks-signer/src/v0/signer.rs)

### Summary
In `Signer::process_pre_commit`/pre-commit signing path in `stacks-signer/src/v0/signer.rs`, when a pre-committed block has a same-tenure conflict whose reorg permit no longer stands, the code queries the node for `get_tenure_tip` to decide whether the conflicting tenure has already advanced past the proposed block's height. If that RPC call fails, the error is only logged ("Treating the tenure as unconfirmed") and execution falls through to the signing path instead of refusing to sign, exactly the same "unexpected failure path silently substitutes a permissive default" pattern described in the external `CLOCK()` report, where a failed call falls back to a value that skews a downstream safety-relevant computation.

### Finding Description
The relevant logic: [1](#0-0) 

The comments explain the intended invariant: a conflict is only allowed to be overridden ("no longer blocks") if either (a) the conflicting sortition's reorg permit still stands under `reorg_permit_stands`, or (b) the node confirms via `get_tenure_tip` that the conflicting tenure has *not yet* advanced to or above the proposed block's height. This is a safety gate meant to prevent the signer from signing two conflicting blocks at the same height/tenure once a reorg is no longer sanctioned.

When `stacks_client.get_tenure_tip(...)` returns `Err(e)`, the code only warns and does not `return`, so control falls through the `if` block: [2](#0-1) 

Falling through means the function proceeds past the conflict check exactly as if the tip query had confirmed the conflicting tenure was *not* yet built up to the proposed height — i.e., the failure is treated as "permit stands / no blocking tip", not as "unknown, so refuse." The function then proceeds to `mark_locally_accepted` and eventually signs the block: [3](#0-2) 

This mirrors the reported pattern precisely: an external call (`CLOCK()`/`get_tenure_tip`) that is expected to supply ground truth for a safety-relevant decision (`block.timestamp` vs `block.number` / "has the conflicting tenure already advanced") fails, and the catch/error path silently substitutes a value that is on the *permissive* side of the check rather than the safe side, corrupting the very equality the check exists to preserve (here: "a signature is only superseded when the conflicting tenure's reorg permit has been revoked and the node confirms the conflicting tenure hasn't already advanced past this height").

Other same-tenure/no-conflict checks in this function correctly fail closed on error, e.g., the `get_signed_conflicts` DB query: [4](#0-3) 

which returns without signing on error — this shows the intended pattern (fail closed) that the `get_tenure_tip` branch does not follow.

### Impact Explanation
If this path is reachable in a scenario where `reorg_permit_stands` has already determined the permit is revoked (i.e., this is a genuine, still-relevant conflict) but the `get_tenure_tip` RPC transiently fails (network hiccup, node busy, RPC error), the signer will sign a *second, conflicting* block for the same tenure/height whose predecessor it already signed or accepted — potentially enabling two conflicting blocks at the same height to both carry this signer's signature. This directly breaks the "signed vs validated"/"one-per-height" equality this repo's rules call out as Critical: a signer produces a conflicting signature it should have refused. It also weakens the reorg-timing safety rules the surrounding comments describe as deliberately conservative ("a signature must not be superseded while it's still fresh").

### Likelihood Explanation
This requires no majority of signers and no key compromise — a single node experiencing a transient RPC failure on `get_tenure_tip` at the moment a pre-commit threshold is reached with a live same-tenure conflict is sufficient to trigger the fall-through. This is a plausible operational condition (node under load, RPC timeout, disconnection) rather than a contrived edge case, making the likelihood moderate but the impact of triggering it high (a conflicting signature is produced automatically without attacker control beyond timing).

### Recommendation
On `Err(e)` from `stacks_client.get_tenure_tip(...)` in this branch, fail closed: treat the query failure the same as "the conflicting tenure may already be at or above the proposed height" and `return` (refuse to sign for now, as with the other `Err` branches in this function), rather than falling through to the signing path. This mirrors the report's recommendation to make the fallback conservative/safe (return `block.timestamp`, i.e., a value that does not corrupt the safety-relevant comparison) instead of defaulting to a value that happens to satisfy the permissive branch of the check.

### Proof of Concept
1. Signer A signs block `B1` for tenure `T` at height `H` and later the reorg permit for the sortition that justified overriding `T` is revoked (`reorg_permit_stands` returns `false` for the recorded conflict), because e.g. `check_parent_tenure_choice`'s sanctioned sortition is no longer canonical.
2. A new competing block `B2` for tenure `T` at the same height `H` reaches the pre-commit threshold.
3. In `process_pre_commit` (stacks-signer/src/v0/signer.rs:1432-1457), the conflict for `B1` is found (`conflict.consensus_hash == B2.consensus_hash` and `!reorg_permit_stands(...)`), so the code calls `stacks_client.get_tenure_tip(&B2.header.consensus_hash)`.
4. The RPC call fails (e.g., node temporarily unreachable) — `Err(e)` branch executes, logging a warning but not returning.
5. Execution falls through to the "no conflict blocks" logging and then to `mark_locally_accepted`/signing logic below, causing signer A to sign `B2`, a block that conflicts with the already-signed `B1` at the same height, despite the reorg permit for overriding `B1`'s tenure having been revoked.
