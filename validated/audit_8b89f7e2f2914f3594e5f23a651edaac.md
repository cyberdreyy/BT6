Based on my investigation, here is my assessment.

### Title
Stale rejection weight is never retracted when a signer flips from Reject to Accept on the same block, corrupting the miner's aggregated-weight vs. verified-accepts equality - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
### Finding Description
`StackerDBListener::run` maintains a shared `BlockStatus` per block (`total_weight_approved`, `total_weight_rejected`, `responded_signers`, `gathered_signatures`) inside `Arc<(Mutex<HashMap<...>>, Condvar)>` [1](#0-0) . On `BlockResponse::Accepted`, weight is added to `total_weight_approved` guarded by `gathered_signatures.contains_key(&slot_id)`, and `responded_signers.insert(slot_id)` is also set [2](#0-1) . On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` guarded only by `responded_signers.insert(slot_id)` [3](#0-2) .

The stacks-signer protocol legitimately allows a signer to flip its verdict on the *same* `signer_signature_hash` from Reject to Accept: `should_reevaluate_reject_reason` marks several reject reasons (`ConnectivityIssues`, `NoSignerConsensus`, `UnknownParent`, etc.) as re-evaluable, and a re-proposal of the identical block routes back through fresh evaluation, potentially resulting in `mark_locally_accepted` and a new `BlockResponse::Accepted` for a block the same signer previously rejected [4](#0-3) .

When that flip happens, the listener's Accept branch only checks `gathered_signatures` (empty for that slot, since the signer never signed before) — it does not check or clear the signer's prior contribution to `total_weight_rejected`. There is no code path in `stackerdb_listener.rs` that decrements `total_weight_rejected` for a signer who later accepts. `reset_rejections` only clears rejection state on proposal-timeout retries driven by the miner itself, not on a signer-side vote flip [5](#0-4) . As a result, that signer's weight becomes simultaneously present in both `total_weight_approved` and `total_weight_rejected` — the aggregated-weight state no longer reflects "verified current accepts" vs. "verified current rejects"; it is a monotonically stale union of every vote that signer ever cast for that hash.

### Impact Explanation
`total_weight_rejected` directly drives a liveness decision: `if block.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight { cvar.notify_all(); }` [6](#0-5) , which wakes `get_block_status` in `signer_coordinator.rs` and can cause the miner to treat the proposal as rejected and resend/replace it [7](#0-6) . Because rejection weight from signers who have since accepted is never retracted, the rejection tally is inflated with stale, superseded opinions. This can cause the miner to prematurely conclude a block was rejected — a liveness degradation (the miner abandons/re-proposes blocks based on a corrupted, permanently-inflated rejection count) rather than the true current signer sentiment. In borderline weight distributions this stale inflation can flip the miner's decision between "wait for approvals" and "treat as rejected," which is exactly the class of "aggregated-weight vs. verified-accepts" equality violation called out in scope.

I was not able to fully trace whether this counter divergence can, in this codebase's current logic, cause a concrete safety violation (e.g., two conflicting blocks both reaching real 70% signer threshold and both being broadcast) — the final signature/consensus decision for actually broadcasting a block is governed by the signer-side `signerdb.rs`/`v0/signer.rs` per-signer state machine (`add_block_signature`, `has_reached_consensus`), which is unaffected by this node-side listener bug. The node-side `blocks` map is a miner optimization/liveness structure, not the canonical signer consensus ledger. Given the ambiguity in whether this crosses into a Critical safety break versus a High/liveness-only issue, I am reporting this as a liveness-affecting bug with unclear escalation to a Critical safety break, rather than asserting an unverified Critical conclusion.

### Likelihood Explanation
Triggering requires only a single miner proposing a block and a single signer (plus the natural gossip in signer StackerDB messages) that first rejects for a re-evaluable reason (e.g., transient connectivity issue, `UnknownParent` due to async parent processing) and then, on the same or a re-sent proposal, accepts it after conditions change. This is a normal, one-signer, no-majority-required interaction (rules explicitly permit "a one-slot miner (plus gossip)" as trigger), and the re-evaluable reject reasons are common transient conditions (network races, node restart timing), making this readily reachable in ordinary operation rather than requiring adversarial coordination.

### Recommendation
When a signer's `BlockResponse::Accepted` is received for a block hash where that signer's address/pubkey is already present in `responded_signers` due to a prior `Rejected` response, retract that signer's weight from `total_weight_rejected` before adding it to `total_weight_approved` (and symmetrically for accept→reject, keep the current invariant that an existing signature cannot be revoked, consistent with `add_block_rejection_signer_addr`'s "cannot add rejection if a signature already exists" rule in `signerdb.rs`). Concretely, track weight contributions per-slot (not just presence in `responded_signers`) so the tally can be recomputed/adjusted atomically under the same mutex when a signer's recorded opinion changes.

### Proof of Concept
1. Miner proposes block B (`signer_signature_hash = H`) with signer S among the reward set.
2. S's local evaluation currently fails with a re-evaluable reason, e.g. `RejectReason::ConnectivityIssues` (transient node RPC hiccup) or `NoSignerConsensus`; S broadcasts `BlockResponse::Rejected(H)`.
3. `StackerDBListener::run` processes the rejection: `responded_signers.insert(slot_id)` succeeds, `total_weight_rejected += weight(S)` [3](#0-2) .
4. The transient condition clears; the miner (or another path) causes B to be re-evaluated by S; `should_reevaluate_reject_reason` returns true for the reason recorded, so S re-runs `check_block_against_state` and now accepts B, signing it and broadcasting `BlockResponse::Accepted(H)` [4](#0-3) .
5. `StackerDBListener::run` processes the acceptance: `gathered_signatures` for S's slot is empty, so `total_weight_approved += weight(S)` is added [2](#0-1) . `total_weight_rejected` is never decremented.
6. Result: `BlockStatus` for H now shows S's weight counted in both `total_weight_approved` and `total_weight_rejected` simultaneously — an aggregated state that never corresponds to S's actual, current single vote, corrupting both the approval-threshold and rejection-threshold computations used to drive miner liveness decisions.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }

            | RejectReason::NotRejected

            | RejectReason::IrrecoverablePubkeyHash
