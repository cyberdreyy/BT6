### Title
EI-authenticated requests bypass `isUser` check in `PipelineRunsController.Create`, allowing external initiators to trigger jobs by numeric ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the int32 job-ID run path behind `_, isUser := auth.GetAuthenticatedUser(c)` with the comment "only users are allowed to run jobs using int IDs - EIs not allowed." However, `AuthenticateExternalInitiator` explicitly injects a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` into the exact same context key (`SessionUserKey`) that `GetAuthenticatedUser` reads from, so an EI-authenticated request satisfies `isUser` identically to a real session/token user.

### Finding Description
`core/web/auth/auth.go`'s `AuthenticateExternalInitiator` function, after validating the EI `AccessKey`/`Secret` against `bridges.AuthenticateExternalInitiator`, does: [1](#0-0) 
This sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` — a fabricated user object with no `Email`/`ID` — into the same key used by `AuthenticateBySession`/`AuthenticateByToken`.

`GetAuthenticatedUser` has no way to distinguish the origin of the stored value; it only checks whether `SessionUserKey` is set: [2](#0-1) 

`PipelineRunsController.Create` uses exactly this function to gate the numeric-job-ID run path, with a comment explicitly stating EIs must be excluded: [3](#0-2) 

Because `isUser` is `true` for any request that passed `AuthenticateExternalInitiator` (a legitimate EI credential holder), the `strconv.ParseInt`/`RunJobV2` branch becomes reachable using only EI `AccessKey`/`Secret` headers, contradicting the stated design invariant that EIs cannot trigger int-ID job runs. The root cause is that user identity/role classification is being conflated: EI auth is implemented by mimicking a full user session rather than being represented as a genuinely distinct, restricted principal that the `isUser` check can exclude.

### Impact Explanation
This is a request-impersonation / authorization-bypass finding: a caller holding only external-initiator credentials (a narrower-scoped credential intended only for external triggers, historically scoped to webhook/UUID-addressed jobs) can escalate to trigger arbitrary jobs by their numeric database ID via `App.RunJobV2`, which can execute pipeline tasks including on-chain interacting tasks (e.g., VRF dummy log generation triggering the on-chain pipeline). This matches the "unauthorized job run" impact class and represents an authentication/identity-confusion bypass of an explicit, documented access-control invariant.

### Likelihood Explanation
The only precondition is possession of a valid EI `AccessKey`/`Secret` pair (an unprivileged, restricted credential type by design) and knowledge of a target job's numeric ID (not secret, exposed via `/v2/jobs` listings or otherwise enumerable). No operator/admin access is required. The exploit is a single crafted HTTP request and is fully repeatable.

### Recommendation
Do not represent EI authentication using the same `clsessions.User`/`SessionUserKey` mechanism as real user sessions. Introduce a distinct context marker (e.g., only setting `SessionExternalInitiatorKey` and checking `GetAuthenticatedExternalInitiator` for exclusion) or add an explicit flag distinguishing "real user" vs. "synthetic EI-derived user" so `PipelineRunsController.Create` can positively assert the caller is not an EI (e.g., check `_, isEI := auth.GetAuthenticatedExternalInitiator(c); if isEI { reject }` in addition to/instead of relying solely on `isUser`).

### Proof of Concept
Handler/integration test plan (Go, `core/web/pipeline_runs_controller_test.go` style):
1. Set up an app instance with a registered `ExternalInitiator` (AccessKey/Secret) via `bridges` store, and a job with a known int32 ID (e.g., an OCR job as in `setupPipelineRunsControllerTests`).
2. Build an HTTP client that sends `POST /v2/jobs/<intJobID>/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` (the `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader` values) instead of session cookie or `X-API-KEY`/`X-API-SECRET`.
3. Assert current (vulnerable) behavior: response is `200 OK` with a `pipelineRun` JSON:API resource (i.e., `RunJobV2` was invoked), instead of the expected `422 Unprocessable Entity` with `"bad job ID"`.
4. Unit-level PoC: directly call `auth.AuthenticateExternalInitiator(ctx, store)` against a `gin.Context`, then call `auth.GetAuthenticatedUser(ctx)` and assert `isUser == true`, demonstrating the identity-confusion root cause independent of routing.
