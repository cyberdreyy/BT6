### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing execution below the configured `K`-of-`N` quorum - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges requests that were *created* by the removed member, but never scans existing `confirmations` sets to strip the removed member's confirmation from requests they had merely *confirmed*. Because `confirm()` decides whether to execute a request purely by comparing `confirmations.len()` to `num_confirmations` [1](#0-0) , a stale confirmation left behind by a now-removed member still occupies a slot in that count, letting a request execute with fewer currently-valid (live) confirming members than `num_confirmations` requires.

### Finding Description
The binding that should hold is:
`confirmations.len() == number of distinct *current* members who confirmed`

`delete_member` only cleans up requests where the deleted member is the request's creator (`r.member == member`), removing those requests and their confirmations entirely [2](#0-1) . It removes the member from `num_requests_pk` and `self.members` [3](#0-2) , but it never iterates `self.confirmations` to drop the removed member's `member.to_string()` entry from confirmation sets of *other* requests that this member had confirmed (but not created).

`confirm()` then trusts the raw set size:
```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
}
``` [4](#0-3) 

There is no re-validation that every entry in `confirmations` still corresponds to a member present in `self.members` at execution time. A confirmation recorded by a member who is later removed remains counted forever.

### Impact Explanation
This breaks the "confirmations counted versus live members" custody binding directly called out in scope. With `num_confirmations = K`, a request can be pushed to execution with only `K-1` (or fewer) genuinely current confirmations plus one or more stale confirmations from members who have since been removed from the multisig. This is explicitly listed as a Critical impact: "a multisig request executed below threshold." Any `MultiSigRequestAction` (including `Transfer`, `AddKey`, `AddMember`, `DeleteMember`, `DeployContract`, `FunctionCall`) can be executed this way, meaning NEAR can be moved, or control of the account changed, without the intended number of currently authorized approvers.

### Likelihood Explanation
This does not require a malicious validator, redeploy, or any privileged foundation action — it only requires the ordinary, expected lifecycle of a multisig account: a member confirms a pending request, and later that member is removed via a legitimate `DeleteMember` request (e.g., because they left the organization or their key was rotated). No special collusion beyond normal quorum operation is needed for the stale confirmation to persist; it is a pure state-management bug, not an edge case requiring rare conditions.

### Recommendation
In `delete_member`, iterate over all entries of `self.confirmations` (not just requests created by the removed member) and remove the removed member's identity string from every confirmation set. Alternatively, `confirm()`/`execute_request()` should re-validate at execution time that every account/key present in the stored confirmation set is still a current member of `self.members`, discounting any stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `X` (e.g., `Transfer` to some receiver), then `A` calls `confirm(X)` → `confirmations = {A}`, size 1.
3. Separately, members submit and confirm a `DeleteMember { member: A }` request that reaches quorum and executes via `execute_request` → `delete_member` runs: since request `X` was not created by `A` (it was, in this scenario, created by A — adjust: have `B` create request `X` and `A` merely confirm it), only requests created by `A` are purged; request `X` (created by `B`, confirmed by `A`) is untouched, and `A`'s stale entry remains in `confirmations` for `X`.
4. `self.members` no longer contains `A`, but `self.confirmations.get(&X)` still contains `A`'s entry, so `confirmations.len() == 1`.
5. `B` calls `confirm(X)` → `len() + 1 == 2 < 3`, so it just adds `B`, `confirmations = {A, B}`.
6. `C` calls `confirm(X)` → `len() + 1 == 3 >= 3`, so `execute_request` runs the `Transfer`, even though only `B` and `C` are the actual current live members who approved it — one confirmation slot came from `A`, a member no longer part of the multisig, defeating the configured 3-of-3 threshold.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
