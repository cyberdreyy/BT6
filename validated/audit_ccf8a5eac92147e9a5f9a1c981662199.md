### Title
Unprivileged view-role users can enumerate every bridge's `OutgoingToken` via unauthorized `GET /v2/bridge_types` - ([File: core/web/bridge_types_controller.go])

### Summary
`BridgeTypesController.Index` is registered in `v2Routes` with only the base `authv2` authentication middleware and no role gate, unlike the sibling create/update/destroy routes which use `auth.RequiresEditRole`. The presenter it uses always serializes `OutgoingToken` (not `omitempty`), so any authenticated low-privilege (view) API token can list all bridges and read every bridge's outgoing token.

### Finding Description
In `core/web/router.go`, the bridge routes are:
```go
authv2.GET("/bridge_types", paginatedRequest(bt.Index))
authv2.POST("/bridge_types", auth.RequiresEditRole(bt.Create))
authv2.PATCH("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Update))
authv2.DELETE("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Destroy))
``` [1](#0-0) 

`authv2` itself only requires generic authentication (`auth.AuthenticateByToken` or `auth.AuthenticateBySession`), not a specific role: [2](#0-1) 

`BridgeTypesController.Index` fetches all bridges from `BridgeORM().BridgeTypes` and maps each to `presenters.NewBridgeResource`, returning them in a paginated response with no role-based filtering: [3](#0-2) 

`presenters.BridgeResource` marks `IncomingToken` as `omitempty` (intentionally suppressed outside of Create), but `OutgoingToken` has no `omitempty` tag and is unconditionally populated by `NewBridgeResource` from `b.OutgoingToken`: [4](#0-3) 

Thus any caller who can pass the generic `authv2` authentication gate — including a view-role or run-role API token that has no edit/admin privileges — can call `GET /v2/bridge_types` and receive every bridge's `name`, `url`, and `outgoingToken` in the response, node-wide. There is no additional role check or token redaction applied specifically to `Index`, unlike mutation endpoints on the same resource.

### Impact Explanation
`OutgoingToken` is the bridge's shared secret used by the Chainlink node to authenticate calls it makes to the external adapter; disclosure of these tokens to a low-privilege API consumer lets that consumer directly call the external adapter with a valid token, i.e. secret/credential disclosure across privilege boundaries. This corresponds to a "sensitive data exposure via authorization bypass" / secret disclosure bounty class — a view-role token holder obtains admin-controlled operational secrets (bridge outgoing tokens) it should never see, given that `RequiresEditRole`/`RequiresAdminRole` protect every other mutating and equally sensitive bridge operation.

### Likelihood Explanation
Minimal precondition: any valid authenticated credential accepted by `authv2` (i.e., any API token created by an admin for a view-only or run-only user, or a valid session), no edit/admin role needed. The request is a single unauthenticated-in-role `GET /v2/bridge_types` call, fully repeatable and paginated to enumerate the entire bridge table. This is trivially reachable and does not depend on any race condition or unusual configuration.

### Recommendation
Wrap the `Index` route with a role gate consistent with the resource's sensitivity, e.g. `authv2.GET("/bridge_types", auth.RequiresEditRole(paginatedRequest(bt.Index)))`, or, if view access to bridge names/URLs must remain available to low-privilege roles, strip `OutgoingToken` from the list-view presenter (e.g., add `omitempty`/mask it in `Index`'s resource mapping and only include it in `Create`/`Show`+edit role contexts).

### Proof of Concept
Go handler-level integration test (extending `bridge_types_controller_test.go`):
1. Start `cltest.NewApplication`, create two bridges as an admin via `app.BridgeORM().CreateBridgeType`, capturing their `OutgoingToken` values.
2. Create a second API token/session scoped to `user.RoleView` (or whichever minimal role exists, per `sessions`/`auth` test helpers used elsewhere, e.g. `cltest.CreateUserWithRole`/`cltest.CreateSession` with a view/run role) and build an HTTP client authenticated with that credential (`app.NewHTTPClient(viewUser)`).
3. Call `GET /v2/bridge_types` using the view-role client.
4. Parse the paginated JSON:API response into `[]presenters.BridgeResource`.
5. Assert `resp.StatusCode == http.StatusOK` and that each `resources[i].OutgoingToken` equals the value stored for that bridge (`bt[i].OutgoingToken`), proving the low-privilege token retrieved the full secret set — demonstrating the missing role gate and unredacted `OutgoingToken` field.

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}
