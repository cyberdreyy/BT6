Based on my research, I found a genuine analog in the transaction-status decoding path: an unchecked-index panic, structurally identical in "bug class" to the reported missing-bounds-guard issue (the Solidity report is about missing safety wrapping before doing arithmetic on untrusted-shaped data; the Rust analog is missing a bounds check before indexing a `Vec` with an untrusted-derived index, both causing a runtime abort on otherwise well-formed external input).

### Title
Unchecked account-key indexing in `make_ui_partially_decoded_instruction` can panic the RPC node - (File: `transaction-status/src/lib.rs`)

### Summary
`make_ui_partially_decoded_instruction` indexes `account_keys` directly with `instruction.program_id_index` and each entry of `instruction.accounts` without first validating these indices are within bounds, unlike the sibling parser functions in the same crate.

### Finding Description
`make_ui_partially_decoded_instruction` is the fallback path used by `parse_ui_instruction` whenever the dedicated per-program parser (`parse`) fails to recognize/parse an instruction: [1](#0-0) . That fallback indexes directly into `account_keys` for both the program id and every account index without any bounds check: [2](#0-1) 

Contrast this with every dedicated instruction parser in the same crate (`parse_system`, `parse_bpf_loader`, `parse_associated_token`, etc.), which explicitly guard against out-of-range indices before ever indexing `account_keys`: [3](#0-2) [4](#0-3) 

These guards exist specifically because, as their comments note, "Runtime should prevent this from ever happening" — i.e., they are defensive checks for exactly the scenario where a compiled instruction's account indices could exceed the account-keys list (e.g. divergent/legacy-encoded data, address-lookup-table resolution edge cases, or any caller that constructs/re-parses a `CompiledInstruction` outside of the strict runtime sanitizer). `make_ui_partially_decoded_instruction` lacks this same guard, so any code path that reaches it with an out-of-range `program_id_index` or `accounts` entry will panic via a `Vec` index-out-of-bounds instead of returning a graceful parse error.

This function is invoked generically for `jsonParsed`/inner-instruction encoding of any instruction whose custom parser fails — including instructions belonging to arbitrary, attacker-deployed programs (since `parse()` only recognizes a fixed allow-list of native/SPL programs and falls through to this function for everything else) [1](#0-0) .

### Impact Explanation
If reached with an out-of-range index, this causes a Rust panic during JSON-RPC response encoding, crashing (or, in default panic=unwind builds, aborting the request-handling thread of) the validator's JSON-RPC process — a concrete unprivileged-caller-triggered crash from a single request, which matches the accepted impact class of "concrete validator-process crash ... from one request."

### Likelihood Explanation
Likelihood is bounded by whether an index can actually be out of range at this call site given upstream sanitization guarantees; under the current runtime, `CompiledInstruction`s that reach RPC encoding are normally produced from already-sanitized `SanitizedMessage`s where indices are validated. This mirrors the original report's own low-likelihood rating — the code path exists and is unguarded, but triggering it requires a way to get an out-of-range index to this specific fallback (e.g. via `simulateTransaction` with `innerInstructions`/`jsonParsed` encoding on transactions/messages whose account key resolution differs from what the per-program parsers defensively check for, or via any future code path that calls this function directly with unvalidated data).

### Recommendation
Add the same bounds check used in `parse_system`/`parse_associated_token`/`parse_bpf_loader` (validate `instruction.program_id_index` and `instruction.accounts.iter().max()` against `account_keys.len()`) inside `make_ui_partially_decoded_instruction`, returning a partially-decoded instruction with an error/placeholder or having `parse_ui_instruction` fall back to raw/unparsed encoding instead of panicking.

### Proof of Concept
Not concretely demonstrable from static analysis alone: reaching `make_ui_partially_decoded_instruction` with an out-of-range `program_id_index`/`accounts` entry requires identifying a caller/API surface (e.g. `simulateTransaction` with `innerInstructions: true` and `encoding: jsonParsed`) that supplies a `CompiledInstruction` whose indices were not validated against `account_keys` before this function is invoked. I could not fully trace, within the available index, every caller of `parse_ui_instruction`/`map_inner_instructions` to confirm an end-to-end unprivileged trigger; a full Devin session with the complete build/tests would be needed to construct a concrete failing RPC request.

fn make_ui_partially_decoded_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiPartiallyDecodedInstruction {
    UiPartiallyDecodedInstruction {
        program_id: account_keys[instruction.program_id_index as usize].to_string(),
        accounts: instruction
            .accounts
            .iter()
            .map(|&i| account_keys[i as usize].to_string())
            .collect(),
        data: bs58::encode(instruction.data.clone()).into_string(),
        stack_height,
    }
}

pub fn parse_ui_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiInstruction {
    let program_id = &account_keys[instruction.program_id_index as usize];
    if let Ok(parsed_instruction) = parse(program_id, instruction, account_keys, stack_height) {
        UiInstruction::Parsed(UiParsedInstruction::Parsed(parsed_instruction))
    } else {
        UiInstruction::Parsed(UiParsedInstruction::PartiallyDecoded(
            make_ui_partially_decoded_instruction(instruction, account_keys, stack_height),
        ))
    }
}
