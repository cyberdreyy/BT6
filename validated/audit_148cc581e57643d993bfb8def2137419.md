I'll check the remaining relevant code: `ProgrammableBorrower` vault accounting/liquidity functions and the `IdleCreditVault` claim paths.### Title
`ProgrammableBorrower.onStopEpoch` checks vault *valuation* (`convertToAssets`) instead of *redeemable liquidity* (`maxWithdraw`), so an unprivileged ERC4626 vault depositor can permanently brick `stopEpoch` and freeze all LP funds — (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The kernel bug is a deadlock caused by a completion path synchronously requesting a resource that recursively re-enters the same submission channel. The credit-vault analog: `IdleCDOEpochVariant.stopEpoch` synchronously calls `ProgrammableBorrower.onStopEpoch`, which must synchronously pull liquidity from an external shared ERC4626 vault. The coverage check uses share *valuation* (`convertToAssets`) while the actual pull uses `vault.withdraw` (bounded by *liquidity*). When these diverge — which any unprivileged vault depositor can force — the nested withdraw reverts, the hook reverts with `StopEpochVaultLiquidityUnavailable`, and the entire epoch-stop path deadlocks. Because the revert happens inside `stopEpoch` before any state transition, there is no forward progress path: every retry hits the same wall as long as the attacker keeps vault liquidity capped below the shortfall.

### Finding Description
In `onStopEpoch`, when IdleCDO needs more cash than the borrower adapter holds on hand, the code computes `shortfall` and decides coverage via `_currentVaultAssets()` = `vault.convertToAssets(balanceOf(this))` [1](#0-0) [2](#0-1) . `convertToAssets` measures NAV per share, not withdrawable liquidity. For any yield-bearing ERC4626 that itself deploys assets (the stated purpose of this contract — "keep undrawn capital parked inside an ERC4626 vault" [3](#0-2) ), `totalAssets`/share price can far exceed the vault's instantaneous `maxWithdraw` liquidity. If `shortfall <= _currentVaultAssets()` but `shortfall > vault.maxWithdraw(address(this))`, `vault.withdraw` reverts and the hook reverts with `StopEpochVaultLiquidityUnavailable`.

Because `stopEpoch` calls this hook mid-transaction [4](#0-3) , the revert rolls back the whole stop: `isEpochRunning` stays true, withdraw requests maturing at epoch end can never be fulfilled, and deposits remain paused from `startEpoch` [5](#0-4) . An unprivileged attacker who is simply a depositor in the same ERC4626 vault (an allowed role: "a user of the programmable borrower's ERC4626 vault") can front-run each `stopEpoch` attempt by draining vault liquidity just below the shortfall (or keeping it drained via a leveraged loop), making the revert permanent for as long as they sustain it. The same mismatch exists in `_borrow` [6](#0-5) , but there the borrower is honest; the exploitable path is the epoch-stop one, which must execute for LP funds to become withdrawable.

The design comment acknowledges "transient ERC4626 liquidity failures can be retried" [7](#0-6) , but nothing bounds the retry: there is no partial-withdraw fallback (`maxWithdraw` amount), no default escalation when the failure is liquidity-rather-than-solvency, and owner escape hatches (`emergencyExitVault`, `rescueTokens`) are subject to the same vault liquidity constraint or only move on-hand tokens [8](#0-7) . Broken invariant: epoch liveness / guaranteed settlement of matured withdrawal receipts.

### Impact Explanation
All LP principal and accrued yield in the epoch (~full pool TVL) is frozen for the duration of the attack: `claimWithdrawRequest` payouts depend on `stopEpoch` succeeding, and deposits stay paused. Attacker cost is the capital needed to suppress vault liquidity, which can be far smaller than pool TVL depending on the vault's structure (e.g., a vault where most assets are lent out and only a thin liquid buffer exists). This is a temporary/indefinite freeze with direct fund impact.

### Likelihood Explanation
Requires the configured vault to be a shared-liquidity ERC4626 where `convertToAssets` can exceed `maxWithdraw` — precisely the intended integration (idle funds parked for yield). The attacker needs only to be a vault depositor and to monitor/execute around the honest manager's `stopEpoch` call. Medium likelihood; no privileged role needed.

### Recommendation
In `onStopEpoch`, cap the attempted withdrawal at `vault.maxWithdraw(address(this))` (and/or use `maxRedeem` with `redeem`): if `shortfall > maxWithdraw`, withdraw what is available and either pull the rest from on-hand or signal a partial-settlement path instead of reverting unconditionally. Alternatively, return `false`/a distinct status so IdleCDO can route through the existing default/recovery machinery rather than leaving the epoch permanently un-stoppable, and consider a time-boxed escalation after N failed stops.

    //    shortfall <= _currentVaultAssets()  => proceeds to vault.withdraw
    //    vault.withdraw(shortfall) reverts   => StopEpochVaultLiquidityUnavailable
