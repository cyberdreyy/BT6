### Title
Multisig request can execute below quorum because stale confirmations from removed members are never purged from other pending requests - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` authorizes execution of a request purely by comparing `confirmations.len()` (a `HashSet<String>` of member identifiers who called `confirm`) against `self.num_confirmations`. When a member is removed via `DeleteMember`, `delete_member` only deletes requests that were *created* by that member; it never scans other pending requests' `confirmations` sets to strip out that member's prior confirmation. A confirmation cast by a member who is later removed therefore keeps counting toward quorum on any request they had confirmed before removal, letting a request execute with fewer *live* approving members than `num_confirmations` requires.

### Finding Description
`confirm()` in [1](#0-0)  checks only the cardinality of the `confirmations` set for a request and, once satisfied, calls `execute_request`, which for a `Transfer` action immediately sends NEAR to `receiver_id` via `Promise::new(...).transfer(...)` (see the `MultiSigRequestAction::Transfer` arm of `execute_request` at [2](#0-1) ).

`delete_member`, invoked from `execute_request`'s `DeleteMember` arm, is the only place that cleans up state when a member is removed: [3](#0-2) . It removes the member from `self.members`, deletes their access key, deletes `num_requests_pk` for them, and deletes any request whose *creator* (`r.member`) equals the removed member — but it does **not** iterate `self.confirmations` to remove the deleted member's identifier from confirmation sets of requests created by *other* members that the removed member had already confirmed.

The binding that should hold is:
```
confirmations_counted(request) == number_of_current_live_members_who_approved(request)
```
After a `DeleteMember` execution, this equality breaks for any request the removed member had confirmed but that was not their own: the stale entry stays in the `HashSet<String>`, so `confirmations.len()` overcounts live approvals.

### Impact Explanation
This directly matches the "Critical" impact category "a multisig request executed below threshold." A `Transfer`, `AddKey`/full-access-key grant, `DeployContract`, or `FunctionCall` request can be pushed to execution with one fewer *live* confirming member than `num_confirmations` mandates, because a stale confirmation from an already-removed member fills the quorum gap. This is a genuine authorization-boundary violation of the multisig's threshold guarantee, not a griefing/DoS issue, and requires no owner/foundation action beyond the multisig's own documented member-management flow (`DeleteMember`), which is a normal, expected multisig operation.

### Likelihood Explanation
The scenario requires only ordinary multisig usage: a member confirms a pending request created by someone else, and later that confirming member is removed via a routine `DeleteMember` action (e.g., because a key is rotated, an employee leaves, or a compromised key is revoked — the exact scenario the `DeleteMember` feature exists for). No malicious deployment, redeploy, or out-of-scope actor is needed; any of the multisig's own current members executing a completely legitimate `DeleteMember` request will trigger the state divergence. The remaining members do not need to intend anything malicious — they simply are unaware that a stale confirmation is still "banked" against a pending request, and completing quorum on that request with fewer live approvers than intended will silently under-authorize the action.

### Recommendation
When removing a member in `delete_member`, iterate all entries in `self.confirmations` (not just requests whose `member` field equals the removed member) and remove the removed member's identifier from every confirmation set. Alternatively, revalidate at `confirm()` time that every identifier in the stored `confirmations` set is still present in `self.members` (filtering out stale entries, or recomputing the effective confirmation count from only current members) before comparing against `num_confirmations`.

### Proof of Concept
Assume `num_confirmations = 2` and members `{A, B, C, D}`.

1. `A` calls `add_request(request_0)` where `request_0` is `Transfer { amount }` to some receiver — [4](#0-3) . `confirmations[0] = {}`.
2. `B` calls `confirm(0)`. Since `len(0)+1 = 1 < 2`, this only inserts: `confirmations[0] = {"B"}` — [5](#0-4) .
3. Separately, `C` and `D` create and confirm `request_1 = DeleteMember { member: B }` to reach quorum (2 confirmations), which executes and removes `B` from `self.members`, deletes `B`'s access key, and only cleans up requests created by `B` (there are none) — [3](#0-2) . `confirmations[0]` still equals `{"B"}`.
4. `C` calls `confirm(0)`. `confirmations[0].len() + 1 = 2 >= num_confirmations (2)`, so `remove_request(0)` and `execute_request(request_0)` run, transferring `amount` to the receiver — [6](#0-5) .

Result: `request_0` executed with only one currently-live confirming member (`C`), while the stale confirmation from the already-removed member `B` was counted toward the 2-of-4 threshold. The multisig's quorum guarantee is violated, and NEAR was moved (or a key/contract-upgrade action executed) with fewer live approvals than `num_confirmations` requires.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
