## Analysis

`createDstEscrow()` accepts `dstImmutables` entirely from the caller and performs no validation on the length or contents of `dstImmutables.parameters` before using it as the CREATE2 salt and funding the clone: [1](#0-0) 

`EscrowDst._withdraw()` (invoked by both the private `withdraw()` and the anti-censorship `publicWithdraw()`) unconditionally decodes fee amounts, and — only if a fee amount is non‑zero — decodes the matching fee recipient from `immutables.parameters`: [2](#0-1) 

`ImmutablesLib` enforces per-field minimum lengths that are decoupled from each other: `protocolFeeAmountCd`/`integratorFeeAmountCd` only require 0x20/0x40 bytes, while the recipient getters require 0x60/0x80 bytes: [3](#0-2) 

Because a `parameters` blob of exactly 64 bytes (`0x40`) satisfies the fee-amount length checks but fails the fee-recipient length checks, an attacker can encode non-zero `integratorFeeAmount`/`protocolFeeAmount` values with no recipient words, causing `integratorFeeRecipientCd()`/`protocolFeeRecipientCd()` to always revert with `IndexOutOfRange`. Since `_withdraw()` is shared by both `withdraw()` and `publicWithdraw()`, this doesn't just block the taker's own private withdrawal — it also defeats the `publicWithdraw()` "public backstop" that is specifically designed to let any access-token holder force payout if the taker is unresponsive or malicious, since it reverts for the identical reason. Only `cancel()` remains callable, and `cancel()` bypasses the fee-decoding path entirely, returning `immutables.amount` to `immutables.taker` (not to the maker) once `DstCancellation` is reached: [4](#0-3) 

This confirms the invariant break: a destination escrow can be successfully funded via `createDstEscrow()` and yet become permanently unwithdrawable through the intended payout path, with the only recovery route returning funds to the taker who set up the malformed parameters rather than paying the maker — undermining the specific safety mechanism (`publicWithdraw`) meant to guard against exactly this kind of uncooperative/malicious taker behavior.

### Title
Malformed `parameters` blob in `createDstEscrow()` permanently bricks both `EscrowDst.withdraw()` and `publicWithdraw()` - (File: `contracts/EscrowDst.sol`, `contracts/libraries/ImmutablesLib.sol`)

### Summary
`createDstEscrow()` never validates the length of the attacker-supplied `dstImmutables.parameters` blob. `ImmutablesLib`'s fee-amount getters (`0x20`/`0x40`-byte minimums) and fee-recipient getters (`0x60`/`0x80`-byte minimums) are checked independently. Supplying a 64-byte `parameters` blob with non-zero encoded fee amounts passes the amount checks but fails the recipient checks inside `EscrowDst._withdraw()`, which is shared by both `withdraw()` and `publicWithdraw()`.

### Impact Explanation
Both the private and public withdrawal paths for the funded destination escrow permanently revert, so the maker can never be paid through the intended mechanism. The only remaining exit is `cancel()`, which does not touch the fee-decoding logic and refunds the escrowed amount to the taker (the party who deployed the malformed escrow) instead of the maker — turning what is supposed to be a temporary freeze recoverable by any access-token holder into an unrecoverable payout path for the intended recipient. This matches "temporary freezing of funds during the live swap lifecycle" (High) and, combined with the fact that the public-withdrawal safety valve — designed precisely to protect against a malicious/unresponsive taker — is also defeated, edges toward loss of the maker's expected destination-chain payout.

### Likelihood Explanation
The only requirement is that the caller of `createDstEscrow()` (the taker/resolver funding the destination clone) crafts a 64-byte `parameters` field with non-zero fee-amount words and no recipient words. No privileged role, governance action, or malicious infrastructure component is needed beyond controlling the `createDstEscrow` call itself, which is a normal, unprivileged part of the swap flow.

### Recommendation
Validate `dstImmutables.parameters.length` in `createDstEscrow()` (e.g., require it to be exactly `0` or the full expected `4 x 32`-byte fee-encoding length), or make `ImmutablesLib`'s fee-recipient/fee-amount length checks consistent/atomic so that a length sufficient to decode a fee amount is always sufficient to decode its paired recipient, preventing a "partial" fee encoding from ever reaching `_withdraw()`.

### Proof of Concept
1. Attacker (as taker) calls `createDstEscrow(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.parameters = abi.encode(uint256 dustProtocolFee, uint256 dustIntegratorFee)` — exactly 64 bytes, omitting the two recipient words. [1](#0-0) 
2. Escrow deploys successfully and is funded (no length check on `parameters`).
3. After `DstWithdrawal`, attacker (or anyone after `DstPublicWithdrawal`) calls `withdraw()`/`publicWithdraw()` with the same immutables; `_withdraw()` calls `integratorFeeAmountCd()` (succeeds, `>=0x40`) then `integratorFeeRecipientCd()` (reverts, requires `>=0x80`). [5](#0-4) [6](#0-5) 
4. Both withdrawal entrypoints revert every time; only `cancel()` after `DstCancellation` succeeds, refunding the amount to the taker instead of the maker. [4](#0-3)

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
