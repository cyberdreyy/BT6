### Title
Time-based staleness bypass lets a signer sign two conflicting blocks at the same height across tenures - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The signer's pre-commit-to-signature path guards against equivocation (signing two conflicting blocks at the same stacks height) by consulting previously signed/accepted blocks via `get_signed_conflicts`. A conflict only blocks signing if it is "fresh" (`last_endorsed > freshness_cutoff`, where `freshness_cutoff` is derived from the purely local, miner-influenceable `tenure_last_block_proposal_timeout`), the reorg permit for it doesn't stand, and the node confirms it `conflict_still_blocks`. Because these are combined with `&&` short-circuiting, once the local staleness window elapses the signer stops asking the node whether the earlier-signed block is still canonical/live for *cross-tenure* conflicts, and simply signs the new, conflicting block.

### Finding Description
In `stacks-signer/src/v0/signer.rs` (around line 1393-1457), the signer computes:

```rust
let freshness_cutoff = get_epoch_time_secs().saturating_sub(
    self.proposal_config.tenure_last_block_proposal_timeout.as_secs(),
);
if let Some(conflict) = conflicts.iter().find(|conflict| {
    conflict.last_endorsed > freshness_cutoff
        && !self.reorg_permit_stands(stacks_client, conflict)
        && self.conflict_still_blocks(stacks_client, conflict, block_info.block.header.chain_length)
}) { /* refuse to sign */ }
``` [1](#0-0) 

If `conflict.last_endorsed <= freshness_cutoff` (i.e., the earlier signature/acceptance is older than `tenure_last_block_proposal_timeout`, default 30s per `DEFAULT_TENURE_LAST_BLOCK_PROPOSAL_TIMEOUT_SECS`), the `&&` chain short-circuits and `conflict_still_blocks` — the only check that actually asks the stacks-node whether the earlier block is still part of the canonical/pending chain — is never invoked for that conflict. The subsequent node-verified fallback check (lines 1432-1457) only re-examines conflicts `where conflict.consensus_hash == block_info.block.header.consensus_hash`, i.e. only same-tenure conflicts. A stale conflict belonging to a *different* tenure (a genuinely different sibling block at the same/higher height) is therefore never verified against the node at all once it ages past the timeout, and the signer proceeds to `mark_locally_accepted` and sign the new block. [2](#0-1) 

The design rationale documented in `docs/signer-flows.md` explicitly states that a signature, once produced, is a "bearer instrument" that can still be aggregated toward the 70% threshold by other signers regardless of what this signer later does: "a rejection is a revocable opinion, while a signature is a bearer instrument — once public it can still be aggregated toward the 70% threshold if rejecting signers change their minds — so a block we signed binds us no matter what state it later fell to." [3](#0-2) 

This means the `tenure_last_block_proposal_timeout` window behaves exactly like the sequencer "grace period" in the external report: it is a purely local, wall-clock gate that a miner can wait out. Once past it, the safety check (asking the node if the old block is still canonical) is skipped for cross-tenure conflicts, and the signer will happily add its signature to a second, conflicting block at the same height — even though its earlier signature for the first block remains valid and gossiped, and could still be aggregated by other signers toward that first block's own 70% threshold.

A single miner (one slot) can engineer this:
1. Propose block A at height H in tenure T1; get it locally/globally accepted and signed by this signer, but stall/withhold broadcast so it does not reach the 70% global threshold quickly.
2. Wait past `tenure_last_block_proposal_timeout` (or induce a new burn block/tenure change so that `last_endorsed` on the DB entry stops being refreshed).
3. Start tenure T2 and propose block B at the same height H, conflicting with A (a sibling block, not a legitimate replacement, since the earlier block was never proven non-canonical by the node).
4. The signer's own freshness check treats A as "stale" for staleness purposes and skips the node-verification (`conflict_still_blocks`) for the cross-tenure case, and signs B too.
5. If block A's earlier gossiped signature (from this and other signers) is later aggregated to reach the 70% threshold (nothing revokes it), both A and B can independently accumulate qualifying signature weight — this signer having signed both.

### Impact Explanation
This breaks the core invariant that a signer must never sign two conflicting blocks at the same height (equivocation). Per the stated impact categories, this is Critical: "a signer signing an invalid, non-canonical, or conflicting block." The failure requires no majority of signers, no other signer's key, and no auth token/local access — it is purely a function of one miner's proposal timing relative to a per-signer configurable timeout that a miner does not control but can simply wait past (default 30s, and further widened by `reorg_attempts_activity_timeout`/tenure timing races).

### Likelihood Explanation
Likelihood is meaningful but not trivial: it requires the earlier block's global signature threshold to be delayed past the freshness window (achievable via network conditions, targeted broadcast withholding by the miner, or naturally slow signers) while simultaneously the miner produces a conflicting sibling proposal at the same height in a new tenure. Given `tenure_last_block_proposal_timeout` defaults to only 30 seconds and is directly exposed/configurable, and tenure changes/forks are routine events the miner controls the timing of, this is a realistic window for a motivated single miner to exploit, matching the "one-slot miner (plus gossip)" scope of this analysis.

### Recommendation
Do not let the local staleness clock alone gate whether a signature-blocking conflict is skipped for cross-tenure conflicts. Always invoke `conflict_still_blocks` (the node-verified check) regardless of freshness, i.e., change the `find` predicate so that `conflict_still_blocks` is evaluated unconditionally (or at minimum evaluated for cross-tenure conflicts as well as same-tenure ones), and only use the freshness/staleness timeout as an optimization to skip the `reorg_permit_stands`/node round-trip when the node has already confirmed the conflicting tenure is dead. In short, mirror the fix pattern from the referenced report: don't let a timing window silently disable a safety check — verify against ground truth (the node's live view) before ever signing a second block at a previously-signed height.

### Proof of Concept
Conceptual PoC (cannot be executed without a running network, but derivable purely from the code path):
1. Configure/observe a `tenure_last_block_proposal_timeout` of 30s (default).
2. Miner proposes block A (height H, tenure T1); signer signs/locally-accepts it (`last_endorsed` set) but broadcast to the wider network / other signers is deliberately delayed so global 70% threshold is not reached within 30s.
3. Wait > 30s (past `tenure_last_block_proposal_timeout`).
4. Trigger new sortition, propose block B at height H in tenure T2, unrelated to and conflicting with A (not permitted by `check_parent_tenure_choice`'s reorg-timing carve-out, since A already reached global/local acceptance well past the reorg-permit window).
5. Follow the pre-commit path in `signer.rs` up to `get_signed_conflicts` — the conflict entry for A has `last_endorsed <= freshness_cutoff`, so the `find` predicate short-circuits `false` without calling `conflict_still_blocks`; the later same-tenure-only check at lines 1432-1457 does not apply because `conflict.consensus_hash != block.header.consensus_hash`.
6. The signer proceeds to `mark_locally_accepted` and signs block B, while its earlier signature for block A is still valid and circulating — this signer has now signed two conflicting blocks at the same height H. [4](#0-3) [5](#0-4)

    /// Get the last signed block from the given tenure if it has not timed out.
    /// Even globally accepted blocks are allowed to be timed out, as that
    /// triggers the signer to consult the Stacks node for the latest globally
    /// accepted block. This is needed to handle Bitcoin reorgs correctly.
    ///
    /// The timeout window is measured from the last time a signature actually covered the
    /// block: our own (`signed_self`) or the observed group/global acceptance
    /// (`signed_group`), whichever is later, matching how `get_signed_conflicts` measures
    /// endorsement freshness. `approved_time` is deliberately not used: it is stamped at
    /// pre-commit, which carries no signature, so it would close the window early. This also
    /// means a globally accepted block we never signed ourselves gets a full window from the
    /// time its acceptance was observed, rather than timing out instantly for lack of a
    /// timestamp.
    pub fn get_tenure_last_block_info(
        consensus_hash: &ConsensusHash,
        signer_db: &SignerDb,
        tenure_last_block_proposal_timeout: Duration,
    ) -> Result<Option<BlockInfo>, ClientError> {
        // Get the last signed block in the tenure
        let last_signed_block = signer_db
            .get_last_signed_block(consensus_hash)
            .map_err(|e| ClientError::InvalidResponse(e.to_string()))?;

        let Some(block_info) = last_signed_block else {
            return Ok(None);
        };

        // `approved_time` may hold the pre-commit time; use the actual signature time.
        let Some(signed_over_time) = block_info.signed_self.max(block_info.signed_group) else {
            return Ok(None);
        };

        if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
            > get_epoch_time_secs()
        {
            // The last accepted block is not timed out, return it
            Ok(Some(block_info))
        } else {
            // The last accepted block is timed out
            info!(
                "Last accepted block has timed out";
                "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                "signed_over_time" => signed_over_time,
                "state" => %block_info.state,
            );
            Ok(None)
        }
    }
