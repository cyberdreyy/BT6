### Title
Response-cache key omits WorkflowID, causing cross-workflow HTTP response confusion - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The `responseCache` used by the HTTP Handler V2 gateway caches outbound HTTP action responses keyed by `OutboundHTTPRequest.Hash()`, which per its own test suite explicitly excludes `WorkflowID` from the hash while including `WorkflowOwner`. This contradicts the component's documented invariant ("Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage") and allows a cached response fetched on behalf of one workflow to be served to a different workflow belonging to the same owner, when the two workflows issue outbound HTTP requests with identical method/URL/headers/body.

### Finding Description
The `ResponseCache` interface documents that `Fetch`/`Set` cache by a hash of the request [1](#0-0) , and the implementation's own comment states the cache key is "a hash of the request (method, URL, headers, body, workflowOwner)" — notably omitting `workflowID` [2](#0-1) .

The project's own README, however, documents a stronger isolation guarantee: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [3](#0-2) .

The test suite proves the actual behavior contradicts this documentation: setting different `WorkflowID` values on otherwise-identical requests produces the *same* hash, while different `WorkflowOwner` values produce different hashes: [4](#0-3) 

The cache lookup/store path is driven directly by untrusted, node-forwarded `OutboundHTTPRequest` data with no workflow-ID-derived component in the key: [5](#0-4) 

And this cache is invoked per outgoing HTTP action, keyed only via `req.Hash()`: [6](#0-5) 

This is structurally analogous to the `CollateralManager` bug in the external report: a documented/intended invariant ("revenue vs. principal separation" / "workflow-scoped cache isolation to prevent cross-workflow leakage") is not actually enforced by the accounting/keying logic, and the discrepancy silently mixes data across scopes that are supposed to be kept separate — in this case, mixing cached responses across distinct workflow executions of the same owner rather than mixing principal into revenue.

### Impact Explanation
If two different workflows owned by the same `WorkflowOwner` issue outbound HTTP action requests that happen to have the same method, URL, headers, and body (e.g., calling the same third-party API endpoint with the same static parameters, which is a realistic and common pattern for shared integrations), a response fetched and cached for Workflow A can be transparently returned to Workflow B (and vice versa) as long as `CacheSettings.MaxAgeMs`/`Store` are set and the TTL window overlaps. This is a cross-workflow response confusion: one workflow can silently receive HTTP action output that was actually produced/cached for another workflow's request, which can leak data intended only for the other workflow's execution context into a workflow that never made that particular call, or cause a workflow to act on stale/foreign data believing it made a fresh request.

### Likelihood Explanation
This does not require any malicious actor — it is triggered by normal usage: any workflow owner running multiple workflows that hit identical external endpoints with `CacheSettings.Store=true` (a supported, documented capability configuration) will encounter this behavior deterministically, since the cache key computation itself omits `WorkflowID`. This is an unprivileged-client-reachable code path — outbound HTTP action requests originate from workflow node capability configuration reaching the internet-facing gateway handler.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) as part of the `OutboundHTTPRequest.Hash()` computation used as the cache key, consistent with the documented "Workflow Isolation" guarantee in the README. Alternatively, update the documentation to accurately reflect that isolation is only owner-scoped and evaluate whether that is an acceptable security boundary; if per-workflow isolation is intended (as documented), the `Hash()` function must be corrected and the existing test `"having different workflowID results in same Hash"` must be updated to assert the opposite behavior.

### Proof of Concept
1. Workflow A (owner `0xabc`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings: {Store: true, MaxAgeMs: 600000}}`.
2. The gateway calls `responseCache.Fetch`, misses, executes the HTTP call, and stores the response keyed by `req.Hash()` (which does not include `WorkflowID`) — [7](#0-6) .
3. Workflow B, owned by the same `0xabc` but a completely different workflow, issues an identical `OutboundHTTPRequest` (same method/URL/headers/body, differing only in `WorkflowID`) within the TTL window.
4. Per `TestRequestHash`'s "having different workflowID results in same Hash" assertion, `req.Hash()` for Workflow B equals that of Workflow A, so `Fetch` returns Workflow A's cached response to Workflow B without making a fresh request — [8](#0-7) .

// isExpiredOrNotCached returns true if the cached response is expired or not cached.
// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

// Fetch fetches a response from the cache if it exists and
// the age of cached response is less than the max age of the request.
// If the cached response is expired or not cached, it fetches a new response from the fetchFn
// and caches the response if it is cacheable and storeOnFetch is true.
//
// The mutex is only held during cache map access (microseconds), not during fetchFn execution.
// Singleflight deduplicates concurrent requests to the same cache key so only one fetchFn
// runs per key, while requests to different keys execute in parallel.
// Cache read and write happen inside the singleflight callback to ensure the key remains
// in-flight until the result is stored, preventing duplicate fetches.
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

### 3.2 Caching Behavior
