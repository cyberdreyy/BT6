### Title
Loss-epoch withdraw receipts lose their "loss" classification once a newer request overwrites `lastWithdrawRequest`, letting them be claimed at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a missing type flag: legacy PIC interrupts were never marked `IRQ_LEVEL`, so the core replayed (resent) an interrupt that should never be resent. The analog in `IdleCreditVault` is a missing *persistent* loss classification on withdraw receipts. A receipt created in an epoch that ended via `stopEpochWithDuration(_lossAmount)` is only reachable through the loss-adjusted claim path while it remains the user's *latest* request epoch (`lastWithdrawRequest[_user]`). As soon as the user files one more withdraw request in a later healthy epoch, the marker moves forward, `lossRecoveryPriceByEpoch[lossEpoch]` is no longer consulted, and the entire aggregate `withdrawsRequests[_user]` — including the haircut-epoch receipt — is paid out at par by `_claimFundedWithdrawRequest`.

### Finding Description
`requestWithdraw` only records `lastWithdrawRequest[_user] = currentEpoch` and accumulates `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` (IdleCreditVault.sol:282-293). When an epoch ends with a loss, `lossRecoveryPriceByEpoch[epoch]` is set and the borrower funds only the reduced amount; receipts of that epoch must be paid through `_claimLossAdjustedWithdrawRequest`, which looks up the haircut solely via `uint256 lossEpoch = lastWithdrawRequest[_user]` and `lossRecoveryPriceByEpoch[lossEpoch]` (IdleCreditVault.sol:789-800).

If the user skips claiming after the loss epoch and instead calls `requestWithdraw` again once a new epoch runs, `lastWithdrawRequest[_user]` is overwritten with the new (healthy) epoch number. On the next `claimWithdrawRequest`:

- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[newEpoch] == 0` and returns 0 — the loss-epoch haircut is silently skipped.
- `_claimFundedWithdrawRequest` then computes `amount = withdrawsRequests[_user] + apr0 buckets`, burns the full receipt balance, and calls `_transferFundedClaim(_user, amount)` (IdleCreditVault.sol:338-349). Since `withdrawsRequestsByEpoch` still contains the loss-epoch portion inside the aggregate, that portion is paid 1:1 instead of at `claimBasis * lossRecoveryPrice / RECOVERY_FULL`.

The queueless per-epoch bookkeeping (`withdrawsRequestsByEpoch`) is never consulted on the funded path to re-apply per-epoch prices, so the "loss" property of the older receipt is effectively never set — exactly the "no trigger-type flag, so core code mishandles the item" pattern of CVE-2023-52993.

### Impact Explanation
The borrower only funds `pendingWithdraws` reduced by the loss haircut for that epoch. Paying the loss-epoch receipt at par therefore pays out underlyings the strategy never received: the excess comes out of funds reserved for other users' funded claims (and, after default finalization, is only partially shielded by the `defaultRecoveryReserve` guard in `_transferFundedClaim`, IdleCreditVault.sol:897-906). In a mixed state this is direct theft of other claimants' funded withdrawals; at minimum it makes the last claimants' transactions revert (`NotAllowed` / failed transfer), i.e. permanent freezing of their funded claims. Loss scales with the un-claimed loss-epoch basis multiplied by `(1 - lossRecoveryPrice/RECOVERY_FULL)`.

### Likelihood Explanation
Only unprivileged actions are needed: the attacker (any KYC-passing lender / tranche holder) requests a withdraw in an epoch, the honest manager/borrower later ends that epoch with `_lossAmount > 0`, and the attacker simply requests another withdraw in the next epoch instead of claiming, then claims once `epochNumber > lastWithdrawRequest`. No privileged misbehavior, no timing race, and it works whenever the vault continues operating after a partial-loss epoch — a supported flow (`stopEpochWithDuration` keeps the epoch machine running). It requires a real loss epoch to occur, hence medium likelihood.

### Recommendation
Track loss-adjusted basis per epoch instead of keying the haircut off `lastWithdrawRequest`. In `_claimFundedWithdrawRequest` (or before it), iterate or otherwise consult `withdrawsRequestsByEpoch` against `lossRecoveryPriceByEpoch` for *all* epochs contributing to the aggregate claim — e.g. keep a per-user set/checkpoint of request epochs, or store a separate `lossAdjustedRequests[_user][epoch]` bucket that is excluded from `withdrawsRequests` so the funded path can never see it. Alternatively, force settlement of all prior receipts at `requestWithdraw` time (claim-or-price-lock the old basis at its epoch's recovery price) before recording the new request.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/IdleCreditVault.t.sol` style):

```solidity
// setup: deposit via AA/BB, start epoch 0
// attacker requests withdraw of `tranches` in epoch E (requestWithdraw)
// honest borrower repays only principal - loss; manager calls
//   cdoEpoch.stopEpochWithDuration(_lossAmount) -> lossRecoveryPriceByEpoch[E] = r < 1
//   pendingWithdraws funded with reduced amount
// manager startEpoch() -> new epoch E+1 running
// attacker calls requestWithdraw(smallAmount) again -> lastWithdrawRequest = E+1
// warp past epochEndDate; manager stopEpoch normally -> epochNumber = E+2 > E+1
// attacker calls cdoEpoch.claimWithdrawRequest()
// assert: attacker received (E_basis + E+1_basis) at par, i.e. E_basis * (1 - r) more
//   than funded; assert strategy underlying balance now insufficient for another
//   user's identical funded claim (their claimWithdrawRequest reverts)
```

Key assertions: `strategy.lossRecoveryPriceByEpoch(E) != 0` yet the attacker never pays the haircut, and a second honest user's funded `claimWithdrawRequest` reverts or receives less than `withdrawsRequests[user2]` at par, quantifying the theft.
