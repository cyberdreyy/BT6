## Title
Stale post-switch operator commission share bypasses beneficiary redirection and loses operator commission-exemption - (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::switch_operator` leaves a residual, not-yet-withdrawable commission share for `old_operator` inside the staking contract's shared `distribution_pool` when the old operator had unpaid/unrequested rewards at switch time. Both `distribute_internal` and `update_distribution_pool` identify "the operator" purely by comparing a shareholder address to the **currently passed-in** `operator` parameter (which becomes `new_operator` after the switch), not by checking whether the shareholder address itself is a registered operator. As a result, `old_operator`'s stale share is (a) no longer redirected to `old_operator`'s registered beneficiary when finally paid out, and (b) no longer exempt from having commission re-charged against it by `update_distribution_pool` on behalf of the new operator.

### Finding Description
In `switch_operator` [1](#0-0) , the function calls `distribute_internal` and `request_commission_internal` while `operator` is still `old_operator`, then swaps the pool's operator to `new_operator` and re-inserts the *same* `StakingContract` (and therefore the same `distribution_pool`) under the `new_operator` key. If `old_operator` had accrued, unrequested rewards, `request_commission_internal` calls `add_distribution(old_operator, staking_contract, old_operator, commission_amount)` [2](#0-1) , which creates a pending share for `old_operator` in `distribution_pool` via `distribution_pool.buy_in(recipient, coins_amount)` [3](#0-2) . Since `stake::unlock_with_cap` only moves this into `pending_inactive`, it is not withdrawable and remains in the pool at switch time (this is documented as expected in `pending_attribution_snapshot`'s comments: "In operator-switch scenarios, the previous operator may still have a non-zero pending attribution") [4](#0-3) .

Later, once the lockup expires, anyone can call the permissionless `distribute` entry function, which now looks up the contract under `new_operator` [5](#0-4) . Inside `distribute_internal`, the payout loop redirects a share to the beneficiary only if `recipient == operator`, where `operator` is the function's parameter (`new_operator`), not a general "is this shareholder itself an operator with a beneficiary" check: [6](#0-5) 

Because the leftover shareholder key is `old_operator` and the function's `operator` argument is now `new_operator`, `recipient == operator` is false, so `beneficiary_for_operator(old_operator)` is never consulted and the payout goes directly to `old_operator`'s raw account address instead of the beneficiary `old_operator` explicitly configured via `set_beneficiary_for_operator` [7](#0-6) .

A secondary consequence exists in `update_distribution_pool`, which is invoked on every subsequent `add_distribution`/`distribute_internal` call for the new contract state. It exempts only the current `operator` parameter from having new commission charged against its share growth [8](#0-7) . Since the stale shareholder is `old_operator` (not `new_operator`), the pool now treats `old_operator`'s residual share like an ordinary staker share, and further reward growth on that stale balance gets skimmed as commission and transferred to `new_operator` — commission the new operator has no legitimate claim to.

### Impact Explanation
This falls under "Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account or traps value." The registered beneficiary mechanism (`BeneficiaryForOperator`) exists specifically so operators can redirect payouts to a separate, presumably more trusted/secure address (e.g., cold wallet vs. hot validator operator key). A `switch_operator` performed while any unpaid/unrequested commission exists for the old operator silently defeats that redirection for the stranded share, and additionally lets the new operator skim extra "commission" off the old operator's stale balance it has no economic right to.

### Likelihood Explanation
Likely to occur in normal operation, not a contrived edge case: any staker calling `switch_operator` (a legitimate, unprivileged, self-service action) while the old operator has *any* unclaimed accrued rewards will create the stale share. There is no requirement that the staker or old operator behave maliciously — the bug fires purely from ordinary timing (switching operators without first calling `request_commission`/`distribute` to flush the old operator's pending distribution to zero, which the API does not enforce or auto-flush completely: `request_commission_internal` only extracts current rewards into a still-unlockable share, it does not wait for/complete distribution).

### Recommendation
In `distribute_internal`'s payout loop, the beneficiary-redirect check should test whether the **recipient itself** is a registered operator with a beneficiary (e.g., by checking `exists<BeneficiaryForOperator>(recipient)` or maintaining a small set/list of "commission recipient" addresses recorded on the contract at `add_distribution` time), rather than comparing `recipient == operator` against the currently active operator parameter. Similarly, `update_distribution_pool`'s commission-exemption logic should exempt any known "commission recipient" address recorded historically for that pool, not just the currently active `operator`. As an additional mitigation, `switch_operator` could be required/forced to fully resolve (not just request) any pending commission for `old_operator` before permitting the switch, e.g. by looping `distribute_internal`+`request_commission_internal` until the old operator's share is zero, or by disallowing the switch while `pending_attribution_snapshot(staker, old_operator, old_operator) > 0`.

### Proof of Concept
Extend the existing `test_operator_can_set_beneficiary`-style test in `staking_contract.move`'s test module:
1. `setup_staking_contract(staker, operator1, INITIAL_BALANCE, commission=10)`.
2. `set_beneficiary_for_operator(operator1, beneficiary_address)`.
3. `stake::end_epoch()` to accrue rewards (do **not** call `request_commission`/`distribute` for operator1 first, unlike the existing test).
4. Call `switch_operator(staker, operator1_address, operator2_address, new_commission)` — this internally calls `request_commission_internal` for `operator1`, creating a pending share for `operator1` in the shared `distribution_pool`, now stored under `operator2`'s contract entry.
5. `stake::fast_forward_to_unlock(pool_address)` so the pending share becomes withdrawable.
6. Call `distribute(staker_address, operator2_address)` (a permissionless entrypoint).
7. Assert: `coin::balance<AptosCoin>(operator1_address)` increased by the pending commission amount, while `coin::balance<AptosCoin>(beneficiary_address)` remained unchanged — showing the commission bypassed the beneficiary redirection that `set_beneficiary_for_operator` was supposed to guarantee.

    fun update_distribution_pool(
        distribution_pool: &mut Pool,
        updated_total_coins: u64,
        operator: address,
        commission_percentage: u64
    ) {
        // Short-circuit and do nothing if the pool's total value has not changed.
        if (distribution_pool.total_coins() == updated_total_coins) { return };

        // Charge all stakeholders (except for the operator themselves) commission on any rewards earnt relatively to the
        // previous value of the distribution pool.
        let shareholders = &distribution_pool.shareholders();
        shareholders.for_each_ref(
            |shareholder| {
                let shareholder: address = *shareholder;
                if (shareholder != operator) {
                    let shares = pool_u64::shares(distribution_pool, shareholder);
                    let previous_worth = pool_u64::balance(distribution_pool, shareholder);
                    let current_worth =
                        pool_u64::shares_to_amount_with_total_coins(
                            distribution_pool, shares, updated_total_coins
                        );
                    let unpaid_commission =
                        (current_worth - previous_worth) * commission_percentage / 100;
                    // Transfer shares from current shareholder to the operator as payment.
                    // The value of the shares should use the updated pool's total value.
                    let shares_to_transfer =
                        pool_u64::amount_to_shares_with_total_coins(
                            distribution_pool, unpaid_commission, updated_total_coins
                        );
                    pool_u64::transfer_shares(
                        distribution_pool, shareholder, operator, shares_to_transfer
                    );
                };
            }
        );
