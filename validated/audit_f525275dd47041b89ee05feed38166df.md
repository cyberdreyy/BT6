### Title
Dust instant-withdraw requests repeatedly freeze all users' funded instant-withdraw claims — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report's core bug class is an unprivileged participant degrading the shared execution path so that only favorable actors can participate while others are locked out. In idle-tranches, the closest on-chain analog lives in the instant-withdraw flow: `requestInstantWithdraw` permanently increments the global `pendingInstantWithdraws` bucket, and `IdleCDOEpochVariant.claimInstantWithdrawRequest` reverts for every user while that bucket is unfunded. Any tranche holder can therefore submit a dust-sized instant-withdraw request during the buffer period to block all previously funded instant-withdraw claims until the borrower/manager funds the queue, and can repeat this every epoch.

### Finding Description
When the epoch APR drops by more than `instantWithdrawAprDelta`, `IdleCDOEpochVariant.requestWithdraw` routes the request to `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` [1](#0-0) . Inside `IdleCreditVault.requestInstantWithdraw`, the requested amount is added to the *global* `pendingInstantWithdraws` counter with no minimum amount and no per-user gating [2](#0-1) .

Claims are gated globally: the test suite confirms that `claimInstantWithdrawRequest` reverts with `NotAllowed` whenever any instant request remains unfunded (`pendingInstantWithdraws > 0`), even when the claiming user's own receipt is already fully funded [3](#0-2) . The only way to unblock claims is `getInstantWithdrawFunds` / `collectInstantWithdrawFunds`, which pull underlying from the CDO/borrower and decrement `pendingInstantWithdraws` [4](#0-3) .

Attack sequence (buffer phase, fixed-APR mode with instant withdrawals enabled):
1. Attacker deposits a dust amount earlier (or already holds a dust tranche balance).
2. In a buffer period where `lastEpochApr > unscaledApr + instantWithdrawAprDelta`, the attacker calls `cdoEpoch.requestWithdraw(dustTrancheAmount, tranche)`. The request is converted to an instant-withdraw receipt and adds a dust amount to `pendingInstantWithdraws`.
3. Every other user's call to `claimInstantWithdrawRequest` reverts with `NotAllowed` until `instantWithdrawDelay` elapses and the manager calls `getInstantWithdrawFunds`, which requires the honest borrower to supply funds.
4. The attacker repeats step 2 every buffer period for a cost bounded by the dust tranche principal, keeping instant claims frozen for `instantWithdrawDelay` per epoch indefinitely.

### Impact Explanation
All funded instant-withdraw receipts in the vault are temporarily unclaimable for up to `instantWithdrawDelay` per epoch, repeatedly, at a cost to the attacker of only a dust tranche position. This is a temporary freezing of user funds driven by a purely unprivileged action (a tranche-token holder calling `requestWithdraw`), matching the "keep other participants out of the execution path" consequence of the external report. Note: unlike the Gravity Bridge case there is no reward the attacker captures; the impact is availability-only, and honest manager/borrower funding eventually unblocks the queue.

### Likelihood Explanation
Requires only that instant withdrawals are enabled and the APR drops by more than `instantWithdrawAprDelta` between epochs — a normal market condition, not an adversarial configuration. The attacker needs no privileged role; `requestInstantWithdraw` is reachable through the permissionless `requestWithdraw` path. The griefing is economically cheap (dust principal) and repeatable each epoch.

Caveat: the revert-on-unfunded-pending behavior is exercised as expected behavior in the test suite [5](#0-4) , so if the sponsor considers "claims wait until the instant queue is funded" intended design, this may be judged a known limitation rather than a new issue.

### Recommendation
Track funded and unfunded instant-withdraw receipts separately (e.g., a `fundedInstantWithdraws` watermark), and let `claimInstantWithdrawRequest` pay out funded receipts regardless of the still-unfunded remainder. Alternatively, enforce a non-trivial minimum instant-withdraw amount and/or per-epoch cooldown so a dust request cannot hold the global bucket hostage.

### Proof of Concept
Foundry fork PoC sketch (building on the existing `IdleCreditVault.t.sol` harness):

```solidity
// Running: epoch N ended with APR drop so instant withdrawals trigger.
// 1. Honest user requests instant withdraw in buffer.
uint256 honestReq = cdoEpoch.requestWithdraw(honestTrancheBal, address(AAtranche));

// 2. Manager funds the queue; pendingInstantWithdraws -> 0.
_startEpochAndCheckPrices(N + 1);
vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
_getInstantFunds();
assertEq(strategy.pendingInstantWithdraws(), 0);

// 3. Epoch ends, APR drops again (lastEpochApr > unscaledApr + delta).
_stopEpochAndCheckPrices(N + 1, initialProvidedApr / 4, _expectedFundsEndEpoch());

// 4. Attacker (dust tranche holder, e.g. 1 wei of tranche) requests withdraw.
vm.prank(attacker);
cdoEpoch.requestWithdraw(1, address(AAtranche));
assertGt(strategy.pendingInstantWithdraws(), 0);

// 5. Honest user's funded claim now reverts until manager funds again.
vm.expectRevert(NotAllowed.selector);
vm.prank(honestUser);
cdoEpoch.claimInstantWithdrawRequest();
```

The assertion at step 5 mirrors the already-tested revert path [5](#0-4) , confirming no guard prevents a dust request from freezing unrelated users' funded claims for the duration of `instantWithdrawDelay`.
