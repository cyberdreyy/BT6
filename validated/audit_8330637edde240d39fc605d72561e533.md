### Title
Strict `require_eq!` on JupLend deposit/withdraw share/amount math is a rounding-brittle invariant that can DoS marginfi's JupLend integration - (File: programs/marginfi/src/instructions/juplend/deposit.rs)

### Summary
The external report describes a class of bug where a lending-integration instruction hard-fails a transaction (and blocks all future mints/redemptions) when an on-chain invariant demands *exact* equality between an internally-computed expected value and an externally-observed value, with no tolerance for legitimate rounding drift. In marginfi-v2's JupLend integration, `juplend_deposit` and `juplend_withdraw` use the exact same pattern: they pre-compute an "expected" share/amount value using local math, then CPI into the external JupLend program, then assert **exact equality** (`require_eq!`) between the externally observed delta and the internally predicted one.

### Finding Description
In `juplend_deposit` (`programs/marginfi/src/instructions/juplend/deposit.rs`), marginfi:
1. Computes `expected_shares` via `expected_shares_for_deposit_from_rates(amount, liquidity_exchange_price, token_exchange_price)`.
2. CPIs into JupLend's `deposit`.
3. Measures `minted_shares` from the observed change in the fToken vault's account balance.
4. Enforces `require_eq!(minted_shares, expected_shares, MarginfiError::JuplendDepositFailed)`. [1](#0-0) 

Similarly, `juplend_withdraw` (`programs/marginfi/src/instructions/juplend/withdraw.rs`) computes `shares_to_burn` from `expected_shares_for_withdraw_from_rate` before calling into `bank_account.withdraw()` and CPI-ing to JupLend's withdraw, and later verifies the received underlying/burned shares match the pre-computed expectation. [2](#0-1) 

This mirrors the jito_restaking_standard bug class exactly: an on-chain program independently re-derives a value that should match an external protocol's actual output, then requires bit-for-bit equality rather than a tolerance/inequality check. If JupLend's own internal rounding (e.g., differing floor/ceil semantics between deposit and withdraw math, precision changes across their own upgrades, fee-on-transfer edge cases, or any future protocol-side rounding tweak) ever diverges from marginfi's locally re-implemented formula by even 1 unit, the `require_eq!` reverts the transaction. Because this check runs unconditionally on every deposit/withdrawal, and there is no fallback/tolerance path, any systemic divergence (e.g., a JupLend protocol upgrade, a socialized-loss event pushing `token_exchange_price` into an edge case, or float/int rounding boundary) would durably brick all further JupLend deposits/withdrawals through marginfi for that bank — a denial-of-service exactly analogous to the reported `mint_sy.supply` vs `token_vrt_escrow.amount` invariant failure.

The code comments in `withdraw.rs` even acknowledge this risk conceptually ("Sanity check: recalculated shares should never exceed...", dust-case handling for "Socialized loss reducing JupLend's exchange price... Future protocol changes affecting share/price invariants") but no such tolerance exists for the exact-match check itself, unlike other genuinely-fixed invariants elsewhere in the codebase (e.g., the fuzz-harness bank-solvency invariant explicitly uses a tolerance band rather than strict equality, and Token-2022 transfer-fee deposit/withdraw paths in the core lending flow explicitly relax exact-equality checks to inequalities to avoid this exact failure mode). [3](#0-2) [4](#0-3) 

### Impact Explanation
If the strict-equality assumption between marginfi's locally re-implemented JupLend math and JupLend's actual on-chain execution ever diverges — due to a JupLend-side protocol change, an edge-case in exchange-price computation, or precision mismatch not anticipated by marginfi's `expected_shares_for_deposit_from_rates` / `expected_shares_for_withdraw_from_rate` helpers — every subsequent `juplend_deposit`/`juplend_withdraw` call against that bank would revert with `MarginfiError::JuplendDepositFailed` (or the withdraw equivalent). This is a durable freeze of user funds routed through the JupLend integration: users could not deposit or withdraw via marginfi's JupLend bank, even though the underlying JupLend position and funds remain intact and recoverable only through unusual/administrative paths. This has direct financial effect (frozen liquidity/inability to redeem).

### Likelihood Explanation
This is a genuine architectural risk rather than a currently demonstrated live bug — I could not confirm from the available index whether `expected_shares_for_deposit_from_rates` / `expected_shares_for_withdraw_from_rate` can currently diverge from JupLend's actual on-chain math under any known JupLend state transition (fee changes, socialized loss, rounding-boundary conditions). The comment block in `withdraw.rs` explicitly reasons through several such edge cases and argues they are currently unreachable given JupLend's *current* single-level floor-rounding design and price floor of `1e12`. This significantly reduces near-term likelihood, but the invariant remains fragile to any future change on the JupLend side that marginfi does not control, exactly the pattern that caused the original jito_restaking_standard DoS.

### Recommendation
Replace the strict `require_eq!` checks in `juplend_deposit` (`minted_shares == expected_shares`) and the analogous checks in `juplend_withdraw` with a small, explicitly-bounded tolerance (e.g., allow a ±1 native-unit rounding discrepancy, matching the tolerance pattern already used in the fuzz-test suite's `JUPLEND_ROUNDING_TOLERANCE_NATIVE` and `assert_eq_with_tolerance!`). Alternatively, keep the exact-match assertion but add a monitored fallback/circuit-breaker admin instruction that can pause/adjust the check independently of a full program upgrade, so a future JupLend-side rounding change cannot permanently brick the integration without requiring a governance-speed program redeploy.

### Proof of Concept
Not independently reproducible from the indexed code alone: exploiting this requires driving JupLend's on-chain `token_exchange_price`/`liquidity_exchange_price` state (external program, not in scope here) into a configuration where its actual minted/burned share count differs by ≥1 unit from marginfi's locally computed `expected_shares_for_deposit_from_rates` / `expected_shares_for_withdraw_from_rate` values — for example, via a JupLend protocol upgrade or an edge-case interest/fee accrual not modeled by marginfi's copy of the formula. Given the indexing limits, I was unable to fully inspect `expected_shares_for_deposit_from_rates` and `expected_shares_for_withdraw_from_rate` implementations or JupLend's own rounding code to confirm a concrete divergence exists today; a Devin session with full repository/file access would be needed to trace these formulas line-by-line against the live JupLend program to determine whether a present-day divergence is achievable.

pub fn assert_bank_solvency(trident: &mut Trident, bank_pk: Pubkey, tolerance: I80F48) {
    let bank = trident
        .get_account_with_type::<Bank>(&bank_pk, None)
        .expect("bank account must deserialize");

    let asset_share_value = from_wrapped(bank.asset_share_value.value);
    let liability_share_value = from_wrapped(bank.liability_share_value.value);
    let total_asset_shares = from_wrapped(bank.total_asset_shares.value);
    let total_liability_shares = from_wrapped(bank.total_liability_shares.value);

    let total_deposits = total_asset_shares
        .checked_mul(asset_share_value)
        .expect("total_deposits overflow");
    let total_liabilities = total_liability_shares
        .checked_mul(liability_share_value)
        .expect("total_liabilities overflow");

    let outstanding_fees = from_wrapped(bank.collected_group_fees_outstanding.value)
        + from_wrapped(bank.collected_insurance_fees_outstanding.value)
        + from_wrapped(bank.collected_program_fees_outstanding.value);

    let vault_balance = I80F48::from_num(token_balance(trident, bank.liquidity_vault));
    let net_vault = vault_balance - outstanding_fees;
    let net_book = total_deposits - total_liabilities;

    let drift = (net_vault - net_book).abs();

    invariant!(
        drift <= tolerance,
        "bank solvency drift > {tolerance} units. bank: {bank_pk}\n  vault_balance: {vault_balance}\n  outstanding_fees: {outstanding_fees}\n  net_vault (vault - fees): {net_vault}\n  total_deposits: {total_deposits}\n  total_liabilities: {total_liabilities}\n  net_book (deposits - liabs): {net_book}\n  drift: {drift}"
    );
