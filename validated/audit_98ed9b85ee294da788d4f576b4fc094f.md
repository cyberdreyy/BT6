### Title
ETH received by `ConvexStrategyETH` is permanently locked — `receive()` accepts native ETH but no function can move the ETH balance - (File: contracts/strategies/convex/ConvexStrategyETH.sol)

### Summary
The external report describes a contract that can hold ETH but offers no distribution path. The strongest analog in this codebase is `ConvexStrategyETH`: it declares an unguarded `receive() external payable` so that `IWETH9.withdraw()` inside `_depositInCurve` can send it ETH, but the only rescue mechanism in `ConvexBaseStrategy.transferToken` operates exclusively on ERC20 tokens via `IERC20Detailed(_token).safeTransfer`. Any ETH that lands in the contract outside the exact WETH-unwrap flow (accidental plain transfer, forced `selfdestruct` send, or ETH dust returned by a Curve interaction) has no exit path and is locked forever.

### Finding Description
`ConvexStrategyETH` is the Convex strategy variant for 2-coin ETH-denominated Curve pools (e.g., stETH/ETH, rETH/ETH). Its `_depositInCurve` unwraps the contract's full WETH balance and forwards it as `msg.value` to `add_liquidity`:

```solidity
_weth.withdraw(_balance);
ICurveDeposit_2token(_curvePool(curveLpToken)).add_liquidity{value: _balance}(_depositArray, _minLpTokens);
```

This requires the contract to accept ETH, hence the bare `receive() external payable {}` at `contracts/strategies/convex/ConvexStrategyETH.sol:35`. Unlike the comparable `LidoCDOTrancheGateway`, whose `receive()` reverts unless `msg.sender == wethToken` (`contracts/strategies/lido/LidoCDOTrancheGateway.sol:99-101`), `ConvexStrategyETH`'s `receive()` accepts ETH from **any** sender at **any** time.

The emergency rescue function inherited from `ConvexBaseStrategy` is ERC20-only:

```solidity
function transferToken(address _token, uint256 value, address _to) external onlyOwner nonReentrant {
    IERC20Detailed(_token).safeTransfer(_to, value);
}
```

(`contracts/strategies/convex/ConvexBaseStrategy.sol:423-429`)

No other function touches `address(this).balance`: `_depositInCurve` always sends exactly the WETH-derived `_balance` as `value`, so a pre-existing stray ETH balance is never consumed, never counted in `price()` (which is computed purely from `totalLpTokensStaked - _lockedLpTokens()` over `totalSupply()`), and never forwarded anywhere. The strategy token accounting is denominated in `curveLpToken`, so stray ETH is also invisible to the vault/share math — it is simply bricked.

### Impact Explanation
Permanent freezing of funds: any ETH balance of the strategy is unrecoverable under the deployed code. Sources of a nonzero balance include:

- Any EOA or contract calling `receive()` with value (an unprivileged sender can force the balance nonzero, e.g., to grief or by user error).
- ETH forcibly sent via `selfdestruct` from an attacker contract — no opt-in possible.
- ETH refunds/dust from the Curve pool or WETH contract edge behavior.

The loss equals `address(strategy).balance` at any point, which is quantifiable on-chain but cannot be returned to sender or swept to the treasury. In the external report the severity hinged on the contract being non-upgradeable; here `ConvexBaseStrategy` is behind an upgradeable proxy, so a governance-driven upgrade could add an ETH sweep — but under the current deployed code the ETH is frozen, and no user-facing or owner-facing function can access it.

### Likelihood Explanation
Medium-low. The contract is designed to hold zero ETH between transactions (`@dev This contract should not have any funds at the end of each tx`), and nothing in the intended flows leaves a residual ETH balance, since `add_liquidity{value: _balance}` consumes exactly the WETH withdrawal. However, the open `receive()` means any accidental or forced ETH transfer permanently lands; the protocol cannot rely on `transferToken` for recovery, and recovery requires a full implementation upgrade. The fix pattern already exists in-repo: `LidoCDOTrancheGateway` gates `receive()` to the WETH contract, which would have prevented this entirely.

### Recommendation
Add an ETH rescue path in `ConvexBaseStrategy` (or in `ConvexStrategyETH` specifically), e.g.:

```solidity
function transferETH(address payable _to, uint256 _amount) external onlyOwner nonReentrant {
    require(_to != address(0), "IS_0");
    (bool ok,) = _to.call{value: _amount}("");
    require(ok, "ETH transfer failed");
}
```

and/or restrict the `receive()` hook so it only accepts ETH from `WETH`, mirroring `LidoCDOTrancheGateway`:

```solidity
receive() external payable {
    require(msg.sender == WETH, "only-weth");
}
```

Restricting `receive()` is the cleaner fix: it eliminates the stray-ETH surface altogether (selfdestruct-forced ETH is the only residual case) while still allowing the WETH unwrap in `_depositInCurve`.

### Proof of Concept
Foundry fork test against mainnet (WETH at `0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2`, Convex booster at `0xF403C135812408BFbE8713b5A23a04b3D48AAE31`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ConvexStrategyETH} from "../contracts/strategies/convex/ConvexStrategyETH.sol";

contract LockedEthTest is Test {
    ConvexStrategyETH strategy; // deployed proxy instance
    address owner = address(0xO);  // strategy owner

    function test_EthIsPermanentlyLocked() public {
        // 1) Unprivileged sender pushes ETH into the strategy
        address alice = address(0xA11CE);
        vm.deal(alice, 1 ether);
        vm.prank(alice);
        (bool ok,) = address(strategy).call{value: 1 ether}("");
        assertTrue(ok); // receive() accepts arbitrary ETH

        assertEq(address(strategy).balance, 1 ether);

        // 2) Owner tries the only rescue function available — ERC20 only.
        //    address(0) / ETH have no ERC20 transfer path; this reverts.
        vm.prank(owner);
        vm.expectRevert();
        strategy.transferToken(address(0), 1 ether, owner);

        // 3) ETH balance is unchanged — no code path can move it.
        assertEq(address(strategy).balance, 1 ether);
    }
}
```

contract SelfDestructSend {

Uncertainty note: the finding's severity is reduced because the strategy is upgradeable (an owner upgrade could add an ETH sweep), and it does not arise in intended flows — the impact is the permanent lock of ETH that arrives via error or force. If the tranche/strategy is treated as out-of-scope legacy code per the engagement rules, then no valid analog exists in the credit-vault surface (IdleCreditVault, epoch machinery, WriteOffEscrow, DefaultDistributor are all non-payable ERC20-only contracts and cannot receive ETH at all).
