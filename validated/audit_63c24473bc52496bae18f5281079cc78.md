### Title
Griefing `stopEpoch` by draining programmable-borrower vault liquidity permanently freezes the epoch - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`IdleCDOEpochVariant._stopEpoch` calls `ProgrammableBorrower.onStopEpoch`, which synchronously waits on an external ERC4626 `vault.withdraw` before the CDO can finalize the epoch. An unprivileged user of that vault can keep its withdrawable liquidity below the needed shortfall while the borrower's `convertToAssets` valuation still covers it, making `stopEpoch` revert forever and freezing every LP withdrawal.

### Finding Description
The kernel bug is a deadlock: unregistering an IRQ affinity notifier synchronously waits for a callback that itself blocks on a lock held by the canceller — the shutdown path wedges on a resource the other side can hold.

The analog is in `ProgrammableBorrower.onStopEpoch` at `contracts/strategies/idle/ProgrammableBorrower.sol:231-268`:

```solidity
if (_amountRequired > onHand) {
    uint256 shortfall = _amountRequired - onHand;
    if (shortfall > _currentVaultAssets()) return true;          // insolvent -> default path
    try vault.withdraw(shortfall, address(this), address(this)) { ... }
    catch { revert StopEpochVaultLiquidityUnavailable(); }        // covered-but-illiquid -> revert
}
```

`_currentVaultAssets()` values the position by `vault.convertToAssets(shares)` (`ProgrammableBorrower.sol:545-549`), which prices total vault assets — including assets lent out or otherwise not withdrawable. In any shared ERC4626 lender (the intended usage: idle funds parked in a yield vault that other users borrow/withdraw from), `maxWithdraw` can be far below `convertToAssets`. In that state `vault.withdraw` reverts, `StopEpochVaultLiquidityUnavailable` propagates out of `onStopEpoch`, and critically this happens **before** the `try this.getFundsFromBorrower`/`catch` block in `IdleCDOEpochVariant._stopEpoch` (`IdleCDOEpochVariant.sol:395-408`), so it is not routed to the default path — the entire `stopEpoch`/`stopEpochWithDuration` reverts.

There is no alternate path to stop the epoch: `isEpochRunning` stays true, `epochEndDate` is past, `expectedEpochInterest`/`pendingWithdraws` are never finalized, so `claimWithdrawRequest`/`claimInstantWithdrawRequest` against the ended epoch never become claimable, and `startEpoch` cannot run while an epoch is running. The borrower cannot draw (`epochPendingWithdraws` was zeroed only on success — actually it isn't reached), and honest operators have no lever: `emergencyExitVault` hits the same liquidity wall, and `setVault` reverts while `vault.balanceOf > 0`. The only escape is someone donating underlying directly to the borrower contract to cover the shortfall.

### Impact Explanation
An unprivileged vault user (in scope per rules: "a user of the programmable borrower's ERC4626 vault") keeps the vault's withdrawable liquidity below the shortfall — e.g., by borrowing against the vault (Morpho-style) or holding its free liquidity withdrawn — each time liquidity refills. Every `stopEpoch` call reverts, so:
- all pending withdraw requests for the epoch are frozen indefinitely,
- no new epoch can start, all LP principal in the running epoch is frozen,
- the loss is the full pool NAV (`getContractValue`) for the duration of the grief, which the attacker can sustain arbitrarily long.

This is the same shape as the kernel deadlock: the cancel/finalize path blocks synchronously on a resource the attacker can hold, and the design assumed the wait would always terminate.

### Likelihood Explanation
Likelihood is moderate-to-high. It requires no privileged role — any vault depositor/borrower suffices — and no upfront loss beyond vault borrowing costs. It triggers whenever vault utilization makes `maxWithdraw < shortfall <= convertToAssets(shares)` at epoch end, a normal state for high-utilization lending vaults even without active malice. The code itself acknowledges this path ("transient ERC4626 liquidity failures can be retried") but offers no bound on retries and no operator override, turning a "transient" assumption into an attacker-held deadlock.

### Recommendation
- In `onStopEpoch`, check `vault.maxWithdraw(address(this))` (not `convertToAssets`) before attempting the withdrawal: if `shortfall > maxWithdraw`, withdraw what is available and return `true` so the CDO's `transferFrom` shortfall flows into the existing default/accounting path, or partially withdraw and leave the gap to `getFundsFromBorrower`.
- Alternatively, wrap the `onStopEpoch` call in `IdleCDOEpochVariant._stopEpoch` in a try/catch that routes reverts into `_handleBorrowerDefault` after a configurable grace period, or add an owner/manager `forceDefault()` escape when repeated stops revert.

### Proof of Concept
Foundry fork/test sketch (mock vault implementing ERC4626 with a `maxWithdraw` limit, as in `test/foundry/ProgrammableBorrowerEpochInvariant.t.sol`'s `setVaultWithdrawLimit` handler):

```solidity
// epoch running; queue has pending withdraws; borrower holds most funds in vault
uint256 shares = programmableBorrower.vaultSharesBalance();
uint256 covered = vault.convertToAssets(shares);          // e.g., 100k

// attacker (vault user) drains/borrows liquidity so maxWithdraw < needed shortfall
vault.setWithdrawLimit(covered - 1); // or: attacker borrows until util ~100%

// required amount at stop
uint256 required = pendingWithdraws + expectedInterest;   // shortfall <= covered

vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(); // StopEpochVaultLiquidityUnavailable bubbles out of _stopEpoch
cdoEpoch.stopEpoch(0, 0);

// repeat: epoch stays running, claims stay frozen; every retry reverts
assertTrue(cdoEpoch.isEpochRunning());
assertFalse(cdoEpoch.defaulted());
```

Note: `stopEpoch` does not fall into `_handleBorrowerDefault` here because the revert happens inside the `onStopEpoch` hook call, before the `try this.getFundsFromBorrower` block; the state machine wedges in "running" with no recovery path short of an external underlying donation to the borrower contract.
