### Title
Funded instant-withdraw claims never clear per-epoch receipt basis, poisoning default recovery (`defaultPendingClaimBasis` / `_claimDefaultedInstantWithdrawRequest`) - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The SAIL bug is a type confusion: pixel format (buffer size) is derived from `pixmap_depth` while the byte-swap loop independently uses `bits_per_pixel`, so two fields describing the same dimension diverge. The analog in `IdleCreditVault` is the split between the aggregate per-user instant-claim counter `instantWithdrawsRequests[_user]` (the "access width" — what is paid and burned) and the per-epoch claim basis `instantWithdrawsRequestsByEpoch[_user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]` (the "buffer size" — what default finalization uses to size and pay recovery). The funded claim path clears only the aggregate counter, leaving the per-epoch basis permanently stale.

### Finding Description
`requestInstantWithdraw` writes three counters: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]` (IdleCreditVault.sol:366-372). The funded claim path `claimInstantWithdrawRequest` clears only `instantWithdrawsRequests[_user]` and never touches the per-epoch entries (IdleCreditVault.sol:387-392). The defaulted claim path `_claimDefaultedInstantWithdrawRequest` does clear them (IdleCreditVault.sol:844-853), but it only runs when a default is finalized with `defaultInstantWithdrawsFinalized = true`.

Because `epochNumber` is bumped at `stopEpoch`, an instant request made during the buffer and funded at `startEpoch` (`collectInstantWithdrawFunds` in IdleCDOEpochVariant.sol:279-282) is claimed while `epochNumber == N`, but its `[user][N]` and `claimsByEpoch[N]` entries remain forever. If a borrower default is finalized in that same epoch `N` (e.g., `getInstantWithdrawFunds`/`stopEpoch` → `_handleBorrowerDefault` → `finalizeDefaultRecovery` with `defaultRecoveryEpoch = epochNumber`, IdleCreditVault.sol:693), two things go wrong:

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (IdleCreditVault.sol:644-648). That count still includes the attacker's already-paid-at-par claim `X`, inflating `totalBasis` and diluting `defaultRecoveryPrice` for every defaulted claimant.
2. The reserve absorbed funds sized on the inflated basis, but the phantom basis `X` can never be paid out: for the attacker, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = [A][N] = X + anyNewRequest`, which always exceeds `instantWithdrawsRequests[A]` by exactly `X`, so the subtraction at line 848 underflows and reverts. The corresponding reserve share (`recoveryPrice * X / RECOVERY_FULL`) is stranded in `defaultRecoveryReserve` permanently, and all honest defaulted claimants receive a strictly lower recovery price than the reserve could have supported.

The net effect mirrors the SAIL overflow: accounting resolves claim funding through one field (aggregate counter) while recovery sizing/payment walks a second, inconsistent field (per-epoch basis), producing an out-of-bounds read of the claims space — recovery value is allocated to a receipt that was already redeemed at par.

### Impact Explanation
When a default is finalized in the same epoch as a funded instant claim, every other defaulted receipt holder (pending normal/APR0 withdrawers and unfunded instant claimants) is haircut by `X / totalBasis` more than warranted. The over-reserved amount `X * realBasis / totalBasis`-equivalent is locked in `defaultRecoveryReserve` forever — there is no withdrawal path for recovery dust — so this is a permanent loss of unclaimed recovery yield for honest users plus permanently frozen underlying. Loss scales with the attacker's instant claim size `X`, bounded by the contract's liquid balance at `startEpoch` (the attacker must be claimable at par, so `X <= totUnderlyings`).

### Likelihood Explanation
Preconditions: (a) instant withdrawals enabled, (b) attacker holds a receipt-funded instant claim already paid at par during epoch `N`, (c) at least one instant request remains unfunded (`pendingInstantWithdraws != 0`) so `defaultInstantWithdrawsFinalized` is set (IdleCreditVault.sol:696), and (d) an honest borrower default is finalized within epoch `N` before the next `stopEpoch`. Condition (b)+(c) coexist whenever `startEpoch` partially prefunds the queue (`pendingInstant > totUnderlyings` path at IdleCDOEpochVariant.sol:286-289 skips `collectInstantWithdrawFunds` only when fully unfunded; partial funding leaves a remainder) or when a new unfunded instant request lands after funding. Condition (d) is triggered by the honest borrower's `onStopEpoch` returning false or `sendFundsToBorrower` reverting — routine default handling, not attacker-controlled but a normal protocol path. The attacker is an ordinary tranche holder/instant withdrawer, fully unprivileged.

### Recommendation
Clear the per-epoch instant basis on the funded claim path, mirroring the defaulted claim path. In `claimInstantWithdrawRequest`, after computing `amount`, iterate (or track) the user's contributing epochs and decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` for the funded portion, or store the epoch of each funded claim so the cleanup is O(1). At minimum, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` must exclude instant receipts that were already claimed at par, so funded claims can never re-enter default basis accounting.

### Proof of Concept
Foundry fork sketch (based on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testFundedInstantClaimPoisonsDefaultBasis() external {
    // enable instant withdraws
    uint256 d = cdoEpoch.instantWithdrawDelay();
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(d, 1000, false);

    address attacker = makeAddr('attacker');
    address victim   = makeAddr('victim');
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    _depositWithUser(victim,   10_000 * ONE_SCALE, true);

    // epoch N-1 runs; stopEpoch bumps epochNumber to N
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    IdleCreditVault cv = IdleCreditVault(address(strategy));
    uint256 epochN = cv.epochNumber();

    // both request instant withdraw in buffer of epoch N
    vm.prank(attacker);
    uint256 claimA = cdoEpoch.requestWithdraw(0, address(AAtranche)); // X
    vm.prank(victim);
    uint256 claimV = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // startEpoch partially funds the queue: attacker (front-run) claims X at par
    _startEpochAndCheckPrices(1);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();          // paid in full
    // victim's request stays unfunded -> pendingInstantWithdraws > 0
    assertGt(cv.pendingInstantWithdraws(), 0);

    // BUG 1: stale per-epoch basis for attacker is still counted
    assertEq(cv.instantWithdrawsRequestsByEpoch(attacker, epochN), claimA); // never cleared

    // honest borrower defaults inside epoch N
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();              // triggers _handleBorrowerDefault

    // basis includes already-paid claimA
    uint256 basis = cv.defaultPendingClaimBasis();
    assertGt(basis, cv.pendingWithdraws() + cv.pendingInstantWithdraws());

    // finalize with recovery sized on inflated basis -> diluted price
    uint256 recovered = /* recovered for real basis */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // victim claims haircut by phantom basis; attacker's defaulted claim underflow-reverts,
    // stranding claimA * price of reserve forever
    vm.expectRevert();
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    uint256 dust = cv.defaultRecoveryReserve();
    vm.prank(victim);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(cv.defaultRecoveryReserve(), 0);        // permanently locked phantom share
}
```

Uncertainty note: I could not fully verify the exact `requestWithdraw` → `requestInstantWithdraw` routing conditions and whether `startEpoch` can leave a strictly partial instant fund (`collectInstantWithdrawFunds` at IdleCDOEpochVariant.sol:282 funds `min(pendingInstant, totUnderlyings)`, which supports the partial case). The core accounting gap — funded claims never clearing `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch` — is directly visible at IdleCreditVault.sol:387-392 versus 844-853 and holds regardless.
