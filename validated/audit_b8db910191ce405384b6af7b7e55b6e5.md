### Title
Stale-epoch instant-withdraw receipts excluded from `defaultPendingClaimBasis`, leaving them permanently unpayable after default finalization - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`defaultPendingClaimBasis()` counts only `instantWithdrawClaimsByEpoch[epochNumber]` — i.e., instant-withdraw requests recorded in the *current* epoch. Requests recorded in an earlier epoch that remain unfunded (`pendingInstantWithdraws > 0`) when a borrower default is finalized are silently dropped from the recovery basis. Their holders can never be paid from `defaultRecoveryReserve` (the funded-claim path explicitly refuses to spend the reserve), so their receipts are permanently frozen while same-epoch claimants consume the entire reserve at an inflated recovery price.

### Finding Description
Instant-withdraw claims are tracked per epoch at request time:

- `requestInstantWithdraw` increments `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (IdleCreditVault.sol:367-374).
- `collectInstantWithdrawFunds` only decrements the global `pendingInstantWithdraws` (IdleCreditVault.sol:398-403); it never clears `instantWithdrawClaimsByEpoch[oldEpoch]`. If borrower funding at `stopEpoch` is partial, the unfunded remainder survives into the next epoch, where `epochNumber` has already been bumped by `deposit` (IdleCreditVault.sol:609-610).
- On default finalization, `defaultPendingClaimBasis()` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — only the *current* epoch's claims (IdleCreditVault.sol:644-649). The stale-epoch claims still contribute to `pendingInstantWithdraws != 0` (which sets `defaultInstantWithdrawsFinalized = true`, line 696) but are excluded from `basis`, so `recoveryPrice = reserveAmount / totalBasis` is computed as if they did not exist.
- After finalization, `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — the stale user's entry at the old epoch index is untouched, so `claimBasis == 0` there (lines 842-856). The user then falls through to the par claim path, which calls `_transferFundedClaim`, a transfer explicitly designed to *not* draw from `defaultRecoveryReserve` (lines 897-900). With the strategy's only underlying being the reserve, the claim either reverts or pulls other claimants' recovery funds.

This mirrors CVE-2017-7495's "needs-flushing-before-commit list" bug class: per-epoch pending-claim state is not rolled forward ("flushed") when the epoch commits, so stale entries are mishandled by the later default-finalization commit.

### Impact Explanation
Two failure modes, both with fund impact:

1. The recovery price is inflated because the denominator excludes stale-epoch instant claims, so entitled claimants (normal withdrawers and same-epoch instant claimants) receive more than their pro-rata share until the reserve drains.
2. Stale-epoch instant claimants' receipts become permanently unpayable: their per-epoch entry at `defaultRecoveryEpoch` is zero so `_claimDefaultedInstantWithdrawRequest` skips them, and `_transferFundedClaim` cannot legitimately source funds. Their strategy-token receipt is effectively frozen/burned value — direct theft of their unfunded claim by other claimants (bounded by `pendingInstantWithdraws` attributable to prior epochs, up to the full instant queue if funding failed entirely).

### Likelihood Explanation
Requires a borrower default while `pendingInstantWithdraws > 0` contains claims whose request epoch is earlier than `epochNumber` — i.e., a `stopEpoch` where borrower repayment underfunded the instant queue, followed by default in a subsequent epoch. Underfunded instant funding is precisely the scenario the code anticipates (the `_defaultPrefundedInstantReserve` partial-funding logic, lines 716-723), so the precondition is a designed-for state, not an edge case. Attacker requirement is minimal: any KYC-passing tranche holder who made an instant-withdraw request is a victim; the beneficiaries are simply other claimants claiming first — no privileged role needed.

### Recommendation
In `defaultPendingClaimBasis()` (and `_defaultPrefundedInstantReserve`), aggregate unfunded instant claims across all epochs rather than only `instantWithdrawClaimsByEpoch[epochNumber]` — e.g., track a global `instantWithdrawClaimsTotal` incremented at request and decremented at claim/collection, and use it (or iterate/carry-forward stale epoch buckets when `epochNumber` bumps). Correspondingly, `_claimDefaultedInstantWithdrawRequest` should clear `instantWithdrawsRequestsByEpoch` for *all* epochs with unfunded basis, not just `defaultRecoveryEpoch`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
// Foundry fork test against deployed/standard IdleCreditVault + IdleCDOEpochVariant setup
function testStaleEpochInstantClaimsExcludedFromDefaultBasis() external {
    uint256 amount = 100_000 * ONE_SCALE;

    // --- Epoch N: deposit and start epoch ---
    idleCDO.depositAA(amount); // user1 (this contract) deposits
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // --- User requests instant withdraw mid-epoch N ---
    uint256 instantAmt = 10_000 * ONE_SCALE;
    idleCDO.requestInstantWithdraw(instantAmt, address(AAtranche));
    uint256 reqEpoch = creditVault.epochNumber();
    assertGt(creditVault.instantWithdrawClaimsByEpoch(reqEpoch), 0);

    // --- stopEpoch N: borrower repays interest but underfunds instant queue ---
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(underlying, borrower, expectedInterestOnly); // no extra for instant queue
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, expectedInterestOnly);
    // collectInstantWithdrawFunds pulled < instantAmt; remainder stays pending
    assertGt(creditVault.pendingInstantWithdraws(), 0);

    // --- Epoch N+1 starts: epochNumber bumped, claim bucket now "stale" ---
    vm.prank(manager);
    cdoEpoch.startEpoch();
    uint256 curEpoch = creditVault.epochNumber();
    assertGt(curEpoch, reqEpoch);
    assertEq(creditVault.instantWithdrawClaimsByEpoch(curEpoch), 0); // BUG: stale bucket not carried forward

    // --- Borrower defaults; recovery finalized ---
    // (trigger _handleBorrowerDefault / finalizeDefault / finalizeDefaultRecovery
    //  per the vault's default flow with partial recoveredAmount)
    uint256 basis = creditVault.defaultPendingClaimBasis();
    // BUG: basis excludes the stale instant claim even though
    // pendingInstantWithdraws != 0 set defaultInstantWithdrawsFinalized = true
    assertLt(basis, creditVault.pendingWithdraws() + instantAmt);

    // --- Victim claim path ---
    vm.prank(user1);
    // _claimDefaultedInstantWithdrawRequest reads epoch `curEpoch`, finds 0;
    // falls through to funded par claim which cannot draw from the reserve:
    // either reverts (permanent freeze) or drains other claimants' recovery.
    idleCDO.claimInstantWithdrawRequest();
}
```

**Caveat:** I was unable to read `IdleCDOEpochVariant.sol` internals within the iteration budget, so two assumptions need confirmation in the full code: (a) that `stopEpoch` can complete while `pendingInstantWithdraws > 0` (partial `collectInstantWithdrawFunds`), and (b) the exact revert-vs-drain behavior inside `_transferFundedClaim` (IdleCreditVault.sol:897+, truncated). If stopEpoch reverts when instant claims are unfunded, the stale bucket cannot cross an epoch boundary and the finding is invalid.
