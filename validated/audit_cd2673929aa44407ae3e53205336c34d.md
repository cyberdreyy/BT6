### Title
Unprivileged ERC4626 vault user can force a borrower default at `stopEpoch` by manipulating the programmable borrower's vault share valuation/liquidity - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The external bug class is "a component fetches a critical resource over an unauthenticated channel, letting a network-position attacker substitute it". The vault analog is `IdleCDOEpochVariant.stopEpoch` trusting data delivered through an unauthenticated external channel: in programmable mode it resolves the entire epoch's settlement interest via `IProgrammableBorrower(_borrower()).totalInterestDueNow()` (contracts/IdleCDOEpochVariant.sol:1001-1005), which is computed from `vault.convertToAssets(vaultSharesBalance())` on an external, permissionless ERC4626 vault (contracts/strategies/idle/ProgrammableBorrower.sol:330-347). Any user of that ERC4626 vault — an explicitly in-scope unprivileged attacker — can move the share price and, more critically, drain the vault's redeemable liquidity right before the honest manager calls `stopEpoch`, so `onStopEpoch`/`_beforeStopEpoch` cannot free `_amountRequired`. The CDO then treats an illiquid-but-solvent borrower as defaulted (`_handleBorrowerDefault`), crystallizing a hard default on LP tranche prices.

### Finding Description
In programmable mode, `_resolveStopEpochInterest` delegates epoch settlement to the borrower contract (IdleCDOEpochVariant.sol:1001-1005). `totalInterestDueNow` derives its vault sleeve from `_currentVaultAssets()` = `convertToAssets` of the external vault (ProgrammableBorrower.sol:337-341). Two manipulation paths exist for an ordinary vault depositor:

1. **Liquidity starvation → forced default.** `availableToBorrow`/stop-epoch funding requires the borrower to redeem vault shares (`_currentVaultAssets` counted as backing, ProgrammableBorrower.sol:349-355). If an attacker withdraws their own ERC4626 position immediately before `stopEpoch`, `maxWithdraw` for the borrower drops below the shortfall; the redeem inside `onStopEpoch` fails or under-delivers, the CDO's `transferFrom` of `_totBorrowed` reverts, and the pool enters the default path (`defaulted = true`, `testDefaultedVaultCannotBeUnpausedOrRestartedBeforeFinalization` shows restart is then blocked). This is not a borrower insolvency — the shares still hold value — yet LPs are pushed into `finalizeDefault`, where recovery is priced by `defaultRecoveryPrice` and every defaulted-epoch receipt and active NAV takes a haircut proportional to whatever `_recoveredAmount` the manager later sources. The attacker profits by holding tranche tokens or post-default receipts bought cheaply, or simply by the haircut differential versus the par value the vault shares retain.

2. **Interest deflation.** Because `loss` is computed as `principalAssets - earnedAssets` (ProgrammableBorrower.sol:340-346), any transient reduction in `convertToAssets` (e.g., a vault that realizes bad debt or an illiquidity-driven exchange-rate dip at the sampled block) floors `totalInterestDueNow` at a lower value with no cap — unlike the inflation direction, which is at least bounded by the `maxApr` check at IdleCDOEpochVariant.sol:377-380. The minted-interest accounting then credits less yield to tranche holders than the shares are actually worth.

The broken invariant is solvency/fair settlement: the pool's default flag and tranche prices are decided by an externally supplied value (`convertToAssets`) that an unprivileged third party can shift at the exact settlement block — the direct equivalent of substituting the resource fetched over the insecure channel.

### Impact Explanation
- Path 1 produces a full protocol default while the borrower is solvent: tranche prices are crystallized at the recovery ratio, pending receipts are haircut, and LP funds are frozen until `finalizeDefault`. Loss magnitude = (1 − recoveryPrice) × total active NAV plus defaulted-epoch receipt basis, potentially the entire TVL if recovery is delayed or partial.
- Path 2 silently reduces `lastEpochInterest`/`expectedEpochInterest`, stealing or destroying unclaimed yield for AA/BB holders up to the full vault-sleeve PnL.

### Likelihood Explanation
Requires the deployment to run in programmable-borrower mode (`isProgrammableBorrower = true`) against an ERC4626 vault that accepts permissionless deposits — which is the documented use case (MetaMorpho vaults in the test suite, `ProgrammableBorrowerCreditVault.t.sol`). No privileged role is needed: the attacker only deposits/redeems in the external vault in the same block or window around `stopEpoch`. Uncertainty: whether `onStopEpoch` swallows redemption failure gracefully or reverts determines if path 1 yields a default or merely a delayed stop; the invariant harness (`ProgrammableBorrowerAccountingInvariant.t.sol:332-367`) shows the abort path is taken whenever `shortfall > maxW`, which is attacker-controllable via a same-block withdrawal.

### Recommendation
- At settlement, value the vault sleeve conservatively: use `maxWithdraw`/`maxRedeem` (realizable liquidity), not `convertToAssets`, when deciding between "default" and "temporarily illiquid", and treat redeem shortfall as a delayed/extended epoch rather than a hard default.
- Snapshot the vault share price at epoch start (`epochStartVaultAssets` per share) and clamp interest/loss to realized deltas instead of spot `convertToAssets`.
- Consider a settlement grace window or TWAP-style check on the vault share price so single-block liquidity moves cannot flip the default flag.

### Proof of Concept
Foundry fork PoC sketch (mainnet fork as in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`, block ~23032567):

```solidity
// Setup mirrors test setUp: cdoEpoch + IdleCreditVault strategy + ProgrammableBorrower
// proxy pointing at a real MetaMorpho vault, isProgrammableBorrower = true,
// isInterestMinted = true, strategy APRs = 0.

function testVaultLiquidityDrainForcesDefault() external {
    uint256 amount = 10_000 * oneScale;
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);            // borrower funds parked in MetaMorpho vault

    // Attacker: an ordinary depositor in the same ERC4626 vault
    address attacker = makeAddr("vaultUser");
    deal(USDC, attacker, LARGE_AMOUNT, true);
    vm.startPrank(attacker);
    underlying.approve(vaultAddress, LARGE_AMOUNT);
    uint256 shares = IMMVault(vaultAddress).deposit(LARGE_AMOUNT, attacker);
    vm.stopPrank();

    // Warp to epoch end; attacker redeems max, draining vault liquidity so that
    // vault.maxWithdraw(programmableBorrower) < shortfall inside onStopEpoch
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(attacker);
    IMMVault(vaultAddress).redeem(shares, attacker, attacker);

    uint256 pricePre = cdoEpoch.virtualPrice(address(aaTranche));

    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                // borrower transfer fails -> default path

    assertEq(cdoEpoch.defaulted(), true, "solvent borrower forced into default");
    assertLt(cdoEpoch.virtualPrice(address(aaTranche)), pricePre, "LP NAV crystallized at a loss");
    // Even though morphoVault.convertToAssets(programmableBorrower shares) still
    // covers the principal — the "default" was purely attacker-induced illiquidity.
}
```

Expected result: `stopEpoch` sets `defaulted`, blocks `startEpoch`/`unpause`, and `finalizeDefault` later pays receipts at a recovery ratio below par — a permanent loss and temporary freezing of all LP funds caused solely by an unprivileged ERC4626 vault user's withdrawal, the on-chain analog of intercepting the settlement value delivered over an unauthenticated channel.
