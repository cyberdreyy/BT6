### Title
`base_insertValidatedTransaction` skips signature verification and trusts the caller-declared `sender`, letting an unverified transaction reach block inclusion - (File: `crates/execution/txpool/src/builder/rpc.rs`)

### Summary
The Zebra CVE root cause is a verification cache that treats a transaction as fully authenticated based on a partial identity (ZIP‑244 `txid`, which excludes the authorization/signature data), so a differently-signed transaction sharing that identity is inserted into a block without its signature actually being checked. The Base builder RPC `base_insertValidatedTransaction` has the same class of flaw: it binds an attacker-declared `sender` field to arbitrary raw transaction bytes via `Recovered::new_unchecked`, deliberately **never verifying that `sender` actually signed the transaction**, and then admits the result straight into the block-building pool.

### Finding Description
`BuilderApiImpl::insert_validated_transaction` decodes the raw EIP‑2718 bytes and immediately constructs: [1](#0-0) 

using `Recovered::new_unchecked(consensus_tx, sender)`, where `sender` is a plain field taken from the caller's JSON‑RPC request, not recovered from an ECDSA signature over the transaction: [2](#0-1) 

The doc comments on the trait and implementation explicitly describe this as intentional design: "allowing the builder to skip signature verification" and "since the sender addresses are trusted from the forwarding mempool node": [3](#0-2) 

The resulting `pool_tx` is then admitted with `add_external_transaction` / `add_transaction`, which for a standard (non‑EIP‑8130) transaction runs through `add_validated_protocol_transaction`, admission-checks (balance/nonce/fee) against whatever address the caller supplied, and, if accepted, becomes eligible for direct block inclusion by the payload builder: [4](#0-3) 

This mirrors the Zebra defect precisely: the code path that is supposed to gate inclusion on cryptographic authorization ("txid"/hash-based trust) instead trusts an externally supplied identity claim and skips the actual authenticity check, so a transaction body can be committed to a block while impersonating an arbitrary account.

The only mitigating factor asserted in comments is that the endpoint is meant to be reached only "from the forwarding mempool node" — i.e. it assumes a trust boundary at the network layer. However, nothing in the RPC handler itself (`BuilderApiImpl::insert_validated_transaction`) enforces caller identity, IP allow-listing, mTLS, or a shared secret; the trust boundary is asserted only in a doc comment, not implemented in code inspected here.

### Impact Explanation
If this RPC endpoint is reachable by any party other than the intended internal forwarder (e.g., exposed on a shared or misconfigured RPC listener, or if the "trusted forwarding" assumption is violated), an attacker can:
- Submit any raw transaction bytes with an arbitrary `sender` address of their choosing (no signature required to match), causing the builder to treat it as fully authenticated.
- Have the builder execute state-changing calls, transfers, or account nonce increments as if signed by a victim account, without ever possessing that account's private key.
- This is a direct "unauthorized operation" / theft-of-funds primitive: value can be moved from any address the attacker names, and the builder will commit it to a block, exactly analogous to Zebra's consensus failure — an unauthorized state transition gets included as if properly authorized.

Because this reaches block inclusion (not just mempool acceptance), it is a High-severity issue equivalent in class (unauthorized fund movement via unverified authorization) to the referenced CVE's impact.

### Likelihood Explanation
Likelihood depends entirely on whether `base_insertValidatedTransaction` is exposed beyond a private, network-isolated builder‑to‑forwarder channel. The code itself contains no authentication, allow-listing, or signature check to enforce the "trusted forwarder" assumption — it is a purely code-level trust decision documented in comments only. Any deployment that exposes this RPC namespace on a shared HTTP/WS listener, or fails to firewall it from public ingress, makes this trivially and remotely exploitable by an unprivileged, anonymous RPC client — matching the required threat model (single RPC request from an anonymous client).

### Recommendation
- Do not accept a caller-supplied `sender` without cryptographic verification. Either require full signature verification (defeating the purpose of the optimization) or, if the trusted-forwarder model is retained, enforce it at the RPC layer itself (mutual TLS, a shared authentication token/HMAC over the request, or strict IP allow-listing) rather than relying solely on network topology and documentation.
- Add defense-in-depth: verify that the RPC method is registered on a separate, non-public listener/module set, and add an explicit runtime check (e.g., a shared secret header or signed request) that fails closed if the trust boundary is misconfigured.
- Audit deployment/ops configuration to confirm the `base_insertValidatedTransaction`/builder RPC namespace is never bound to a publicly reachable interface.

### Proof of Concept
1. Assume (or misconfigure) network access to the builder's RPC listener where the `base` namespace (including `insertValidatedTransaction`) is exposed.
2. Craft an EIP‑2718-encoded transaction (`raw`) with an empty/arbitrary/garbage signature calling `transfer` or similar from victim account `V`'s balance, and set `sender = V` in the `ValidatedTransaction` payload (see wire format in `crates/execution/txpool/src/wire.rs:75-90`).
3. Call:
```
base_insertValidatedTransaction({ "sender": "<V>", "raw": "<encoded tx bytes>", "extensions": {} })
```
4. `BuilderApiImpl::insert_validated_transaction` decodes `raw`, builds `Recovered::new_unchecked(consensus_tx, V)` (crates/execution/txpool/src/builder/rpc.rs:123), and inserts it via `add_external_transaction` (line 139) without ever checking that `V` produced a valid ECDSA signature over `raw`.
5. If `V` has sufficient balance/nonce state, the pool admits the transaction and the payload builder can include it in a produced block, moving `V`'s funds without `V`'s authorization — the existing system test `test_insert_validated_transaction_single` (`etc/systems/tests/tx_forwarding.rs:152-229`) demonstrates the full acceptance-to-inclusion path using this exact RPC call.
