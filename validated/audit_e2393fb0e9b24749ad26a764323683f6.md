### Title
Gateway forwards unauthenticated MethodWebAPITrigger requests to entire DON with no sender allowlist at the gateway layer - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` validates only message structure, timestamp freshness, and method name before broadcasting the request to every DON member via `don.SendToNode`, with an explicit `// TODO: apply allowlist and rate-limiting here` marking the missing check. Any holder of a valid signing key can submit a `MethodWebAPITrigger` message and have it forwarded to all DON nodes, consuming node/network capacity, even though downstream `processTrigger` ultimately enforces `allowedSenders`.

### Finding Description
In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` (lines 341-421) performs: payload decoding, `Timestamp` presence check, staleness check based on `MaxAllowedMessageAgeSec`, then immediately proceeds to the `// TODO: apply allowlist and rate-limiting here` comment before checking that `msg.Body.Method == MethodWebAPITrigger` [1](#0-0) . No check exists that the sender is a known/subscribed workflow owner, and no gateway-level rate limiting is applied to legacy user messages at this call site (the `nodeRateLimiter` field is only used in `handleWebAPIOutgoingMessage` for node-originated messages, not here) [2](#0-1) . After building the JSON-RPC request via `common.ValidatedRequestFromMessage`, the handler saves a callback and loops over every `h.donConfig.Members`, calling `don.SendToNode` for each one unconditionally [3](#0-2) .

`common.ValidatedRequestFromMessage`/`Validate()` only checks structural completeness (message ID, method non-empty) — it does not perform any sender-authorization/allowlist check [4](#0-3) . Actual sender authorization (`allowedSenders`) is enforced later, inside each DON node's capability, in `processTrigger` in `core/capabilities/webapi/trigger/trigger.go` — but only *after* the message has already reached and been processed by every node in the DON [5](#0-4) .

### Impact Explanation
This confirms the gateway/user-request layer has no allowlist or per-sender rate limit before fanning a signed request out to all DON members, matching a "quota/allowlist bypass leading to unauthorized resource consumption" class of impact — every DON node must receive, deserialize, and evaluate the message against every registered workflow's `allowedTopics`/`allowedSenders` before rejecting it. This is a denial-of-service / resource-exhaustion vector against the whole DON, not just a single victim node, since the fan-out is to `h.donConfig.Members` unconditionally. It does **not** result in unauthorized trigger execution, since `processTrigger`'s `allowedSenders` check correctly blocks execution for unregistered senders [6](#0-5) , so the exploitable impact is scoped to unauthorized broadcast/capacity consumption at the gateway and node ingestion layer, not fund movement or authorization bypass of workflow execution itself.

### Likelihood Explanation
Feasible and repeatable: an attacker needs only an ECDSA keypair to sign a legacy gateway message (no subscription or DON registration required), a fresh `Timestamp`, and method `MethodWebAPITrigger`. There is no rate limiter or allowlist gating this handler before the `don.SendToNode` fan-out, so repeated submissions with distinct `MessageId`s will each independently trigger broadcast to all DON members.

### Recommendation
Implement the marked TODO: before forwarding, validate `msg.Body.Sender` against a gateway-level allowlist (e.g., derived from aggregated `allowedSenders` across registered DON workflow configs, or a dedicated gateway config allowlist) and apply the existing `nodeRateLimiter` (or a new per-sender limiter) to `HandleLegacyUserMessage`, rejecting/aborting via `callback.SendResponse` with an authorization error before reaching the `don.SendToNode` loop.

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with a `donConfig` containing N members and a mock `handlers.DON`.
2. Build a legacy `api.Message` with `Method: MethodWebAPITrigger`, a valid `Timestamp`, signed by an arbitrary/never-registered ECDSA key (not present in any `AllowedSenders` list of any workflow config).
3. Call `HandleLegacyUserMessage` with this message and a mock `Callback`.
4. Assert `mockDON.SendToNode` was called exactly `len(donConfig.Members)` times (once per member) and no error/rejection occurred prior to fan-out, confirming there is no allowlist rejection at the gateway layer despite the sender never being subscribed to any workflow.

// ValidatedRequestFromMessage converts a legacy Gateway Message to a JSON-RPC request
func ValidatedRequestFromMessage(msg *api.Message) (*jsonrpc.Request[json.RawMessage], error) {
	if msg == nil {
		return nil, errors.New("nil message")
	}
	if msg.Body.MessageId == "" {
		return nil, errors.New("message ID is empty")
	}
	if msg.Body.Method == "" {
		return nil, errors.New("method is empty")
	}
	params, err := json.Marshal(msg)
	if err != nil {
		return nil, fmt.Errorf("failed to marshal message: %w", err)
	}
	rawParams := json.RawMessage(params)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      msg.Body.MessageId,
		Method:  msg.Body.Method,
		Params:  &rawParams,
	}
	return req, nil
}
