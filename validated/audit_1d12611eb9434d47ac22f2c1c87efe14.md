## No vulnerability found for this question.

**Reasoning:**

The equality claimed by the question — canonicity of `consensus_hash` at `BlockValidateOk` time vs. at `mark_locally_accepted` time — does not need to hold, and the code does not rely on it holding, because the guard structure is different from what the question assumes.

`check_block_has_valid_tenure` runs once, inside the node's `NakamotoBlockProposal::validate`, against a `SortitionHandleConn` opened for that call [1](#0-0) . This is a one-shot, best-effort admission check ("DO NOT CALL FROM CONSENSUS CODE" is explicitly noted on the neighboring helper) [2](#0-1) , not a consensus gate — the question itself scopes node-side consensus acceptance as out-of-scope background, and that is exactly the layer that ultimately re-validates canonicity when the signed block is actually appended (`check_nakamoto_tenure`/`check_valid_consensus_hash`) [3](#0-2) .

On the signer side, between `BlockValidateOk` and the eventual signature, the signer does re-check state twice (`check_block_against_signer_db_state` at validate-ok, and again at the pre-commit threshold) [4](#0-3) [5](#0-4) , plus a dedicated conflict guard (`conflict_still_blocks`/`reorg_permit_stands`) right before `mark_locally_accepted` [6](#0-5) . These re-checks are per-evaluation, node-derived, and specifically designed (per the documented rationale) to be robust to a burnchain reorg landing between validation and signing: `conflict_still_blocks`'s first question is precisely "is this tenure's sortition still canonical?", answered fresh from the node (`get_sortition_by_burn_hash`, gated by `get_peer_info` tip height) rather than trusted from validate-time state [7](#0-6) . This is proven correct by an existing integration test that injects exactly this scenario: a burnchain reorg orphaning a signed tenure's sortition, and asserting the signer's re-derivation at signing time reflects the new canonical state [8](#0-7) .

The one real asymmetry documented in the codebase is that this canonicity re-derivation applies to *conflicting* blocks the signer already signed, not to a fresh re-verification of the *currently proposed* block's own tenure canonicity at the exact instant of signing — `check_latest_block_in_tenure`'s failure/404 handling for the proposal's own tenure fails open ("assume proposal is higher") rather than distinguishing an orphaned tenure [9](#0-8) . However, this asymmetry does not establish the specific attacker-controlled, single-slot-plus-gossip exploit the question requires: it is a liveness/fail-open design choice explicitly justified in the code's own documentation ("Whenever the node cannot be asked, the conflict keeps blocking... wrongly signing cannot be taken back") rather than a demonstrated path by which an unprivileged single-miner-slot attacker can force a signature over a block whose *own* tenure was reorged out, given that the very block being signed must first pass the node's block-proposal endpoint (`has_consensus_hash`) and there is no reachable code path shown where the attacker — without control over Bitcoin reorg timing beyond what is already accounted for by the documented and tested reorg-handling logic — can force the specific interleaving described. No reachable code was found supporting a concrete, reproducible exploit distinct from the already-tested and documented reorg-tolerance mechanisms.

    ///    burn block when it arrived, and `/v3/sortitions` resolves it against the node's

    ///    is void, so the conflict is dead no matter what state its block is in.
    ///
    /// 2. Does the node's canonical Stacks chain still reach the block?
    ///    * If it does, the block is real chain state, so it keeps blocking. (If the reorg-timing

    ///      never reaches this check at all.)
    ///    * If it does not, and the block was once globally accepted, the node had it and a

    ///    * If it does not, and the block was never globally accepted, the node may simply never

    fn conflict_still_blocks(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
        proposed_height: u64,
    ) -> bool {
        if let Ok(burn_block) = self
            .signer_db
            .get_burn_block_by_ch(&conflict.consensus_hash)
        {
            match stacks_client.get_sortition_by_burn_hash(&burn_block.block_hash) {
                Ok(_) => {
                    // The tenure's sortition is still canonical: the conflict is live at the
                    // burn chain level, so fall through to the block-level questions.
                }
                Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                    // A 404 only proves the sortition was orphaned if the node's burnchain
                    // view actually covers the burn block's height: a node still catching up
                    // 404s canonical burn blocks it hasn't processed yet (and the
                    // endpoint also 404s on internal data misses). Only trust it once the
                    // node's burnchain tip is at or past the stored burn block.
                    match stacks_client.get_peer_info() {
                        Ok(peer_info) if peer_info.burn_block_height >= burn_block.block_height => {
                            info!("{self}: A conflicting block's tenure was orphaned by a burnchain fork. The conflict no longer blocks.";
                                "conflicting_consensus_hash" => %conflict.consensus_hash,
                                "conflicting_block_height" => conflict.stacks_height,
                                "burn_block_hash" => %burn_block.block_hash,
                            );
                            return false;
                        }
                        Ok(peer_info) => {
                            info!("{self}: The node does not know a conflicting block's burn block, but its burnchain tip has not reached that height, so this does not prove the tenure was orphaned. Leaving the conflict in place.";
                                "conflicting_consensus_hash" => %conflict.consensus_hash,
                                "burn_block_hash" => %burn_block.block_hash,
                                "burn_block_height" => burn_block.block_height,
                                "node_burn_block_height" => peer_info.burn_block_height,
                            );
                            return true;
                        }
                        Err(e) => {
                            warn!("{self}: Failed to fetch the node's burnchain tip while checking a conflicting block's tenure: {e:?}. Leaving the conflict in place.";
                                "conflicting_consensus_hash" => %conflict.consensus_hash,
                            );
                            return true;
                        }
                    }
                }
                Err(e) => {
                    warn!("{self}: Failed to check whether a conflicting block's tenure is still canonical: {e:?}. Leaving the conflict in place.";
                        "conflicting_consensus_hash" => %conflict.consensus_hash,
                    );
                    return true;
                }
            }
        }
        let node_reaches_conflict = match stacks_client.get_tenure_tip(&conflict.consensus_hash) {
            Ok(tip) => tip.anchored_header.height() >= conflict.stacks_height,
            // A 404 is an answer, not a failure: the node has no blocks in that tenure at all.
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => false,
            Err(e) => {
                warn!("{self}: Failed to fetch the canonical tip of a conflicting block's tenure: {e:?}. Leaving the conflict in place.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "conflicting_block_height" => conflict.stacks_height,
                );
                return true;
            }
        };
        node_reaches_conflict
            || (!conflict.globally_accepted && conflict.stacks_height <= proposed_height)
    }

    fn conflict_in_an_orphaned_tenure_does_not_block_signing() {

            info_b.signed_self.is_some(),

        );
    }
