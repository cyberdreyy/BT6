### Title
Withdrawn stake account's already-computed epoch reward is silently burned instead of preserved for later re-crediting - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
The Redacted Cartel finding describes reward loss when a metadata/merkle-root update overwrites a pending claim before the claimant acts on it. The Agave analog is in the partitioned epoch-rewards distribution pipeline: a stake account's reward is computed once (at the epoch boundary, "calculation" phase) and is only actually credited several blocks later during its assigned "distribution" partition. If, in the intervening window, the staker submits an ordinary `Withdraw` (or fully drains the account) transaction, the stake account is removed from `StakesCache` and, at distribution time, `Bank::build_updated_stake_reward` cannot find it and the reward is discarded via `DistributionError::AccountNotFound`, being counted as "burned" rather than paid.

### Finding Description
`Bank::store_stake_accounts_in_partition` iterates the pre-computed `PartitionedStakeReward`s for the current partition and calls `Bank::build_updated_stake_reward` for each one: [1](#0-0) 

That helper looks up the stake account strictly by pubkey in the live `stakes_cache_accounts` map, and returns `DistributionError::AccountNotFound` if it is missing: [2](#0-1) 

Any `AccountNotFound` (or other) error causes the reward to be moved into the "burned" bucket instead of being minted to the user: [3](#0-2) 

A stake account is removed from `StakesCache` — and thus becomes invisible to this lookup — whenever its lamport balance reaches zero, which is exactly what a normal `Withdraw` stake instruction produces once the account is fully drained: [4](#0-3) 

The reward calculation phase computes and records a `PartitionedStakeReward` for every eligible stake pubkey at the epoch boundary, but the reward isn't actually paid out until its scheduled partition/block during the following `SLOTS_PER_EPOCH`-bounded distribution window — a delay the runtime itself intentionally spreads over many blocks (`REWARD_CALCULATION_NUM_BLOCKS`/`num_partitions`). A user is completely free to submit a normal `Withdraw` transaction against their own stake account (assuming it is already deactivated/fully cooled down, e.g. because they deactivated it in the prior epoch) during this gap. Because the reward calculation phase has already fixed the reward amount and partition assignment (`hash_rewards_into_partitions` on a snapshot taken at the epoch boundary), the stake pubkey's slot in the schedule cannot be changed to account for the account's disappearance — mirroring exactly the C4 report's "metadata was fixed before claim, but the underlying entity changed state before the claim executed" pattern.

### Impact Explanation
When this path is hit, the previously-computed reward for that stake pubkey is never credited to the staker (who withdrew their funds early, an entirely legitimate action) — it is instead treated as "burned," being subtracted from total capitalization on the burn side of `distribute_epoch_rewards_in_partition`. This is real economic loss to a delegator/staker triggered purely by their own permitted transaction, and it is deterministic and reproducible across the whole cluster (every validator would compute and burn the same amount), so it does not cause consensus divergence, but it does directly and irreversibly destroy legitimately earned stake rewards for the affected account. The impact is bounded to a single stake account's single epoch's reward per occurrence, but is trivially reproducible by any staker who withdraws in the wrong window.

### Likelihood Explanation
This requires no privileged or malicious actor — it is reachable by any staker performing routine actions (deactivate stake, wait for cooldown, then withdraw), if the withdrawal transaction lands in the block window between the epoch-boundary reward calculation and the account's assigned distribution partition/block. Because reward distribution is deliberately spread over multiple blocks (`get_reward_distribution_num_blocks`), this window is non-trivial and can span many slots, making accidental triggering plausible for any staker who withdraws shortly after an epoch boundary, and trivially reproducible by anyone probing for it deliberately.

### Recommendation
Before finalizing the burn path in `Bank::build_updated_stake_reward`/`store_stake_accounts_in_partition`, distinguish "account no longer exists because it was fully withdrawn/closed by its rightful owner" from actual anomalies, and instead of burning the reward, either (a) credit it directly to the destination the lamports were withdrawn to (if traceable), or (b) hold/redirect the reward to a claimable escrow that the original staker (or the `withdraw_authority`) can later reclaim, rather than unilaterally destroying already-earned rewards. At minimum, the existing recalculation path (`recalculate_partitioned_rewards_if_active`/`recalculate_stake_rewards`) demonstrates that stake-cache state can be re-derived; a similar mechanism could detect and gracefully redirect rewards for closed accounts rather than silently burning them.

### Proof of Concept
1. A staker deactivates their stake account in epoch N (via ordinary `DeactivateStake`), and the stake fully cools down.
2. At the epoch N→N+1 boundary, `Bank::process_new_epoch` → `begin_partitioned_rewards` computes and records a `PartitionedStakeReward` for this now-fully-deactivated stake pubkey (matching the `DeactivatedStake` reward-type test path in `test_build_updated_stake_reward`), and assigns it to some partition/block within the epoch's distribution window via `hash_rewards_into_partitions`. [5](#0-4) 
3. Before that assigned distribution block height is reached, the staker submits an ordinary `Withdraw` instruction (via the CLI's `process_withdraw_stake` or an equivalent transaction) for the full remaining balance of the stake account. [6](#0-5) 
4. This transaction succeeds and drains the account to zero lamports, causing `StakesCache::check_and_store` to call `remove_stake_delegation`, deleting the pubkey from `stake_delegations`. [4](#0-3) 
5. When the bank reaches the pre-assigned distribution block, `distribute_partitioned_epoch_rewards` → `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` looks up the pubkey and fails with `DistributionError::AccountNotFound`, moving the previously-computed reward into `stake_reward_lamports_burned` instead of crediting it anywhere. [7](#0-6) 
6. The staker's already-earned reward for that epoch is permanently lost.
