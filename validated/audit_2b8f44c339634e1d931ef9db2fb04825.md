### Title
Fixed harvest release window lets late depositors claim previously accrued rewards - ([contracts/IdleCDO.sol](contracts/IdleCDO.sol))

### Summary

`harvest` records all newly sold rewards and releases them over the fixed `releaseBlocksPeriod`, while `harvest` itself accepts no duration or accrual-period parameter. Because locked rewards are excluded from NAV, an unprivileged depositor can enter immediately after an honest harvest, receive shares priced without those rewards, and then receive part of the reward when it unlocks. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

`IdleCDO.initialize` sets `releaseBlocksPeriod` to `6400`, approximately one day. [4](#0-3) 

During `harvest`, the contract sells strategy rewards, sets `latestHarvestBlock` to the current block, stores the entire sale proceeds in `harvestedRewards`, and calls `_updateAccounting`. [5](#0-4) 

`getContractValue` subtracts `_lockedRewards()`, which initially excludes essentially all newly harvested rewards from NAV. [2](#0-1) [3](#0-2) 

A caller can therefore deposit immediately after the harvest transaction. `_deposit` updates accounting before taking funds, but at that point the new reward remains locked and does not raise the tranche price; `_mintSharesAtCurrPrice` then mints shares using that depressed price. [6](#0-5) [7](#0-6) 

As blocks advance, `_lockedRewards` decreases linearly, increasing NAV. The next deposit, withdrawal, harvest, or accounting update crystallizes the gain across all outstanding tranche shares, including shares minted by a user who deposited only after the reward had already been harvested. [8](#0-7) [9](#0-8) 

### Impact Explanation

An attacker can permanently take part of yield accrued by existing holders before the attacker deposited.

For a single-tranche example with `T` existing NAV, harvested reward `R`, zero performance fee, and attacker deposit `A`, the attacker receives approximately `R * A / (T + A)` after the release completes. With `T = 1,000,000`, `A = 1,000,000`, and `R = 10,000`, this is approximately `5,000` underlying; with the default 15% performance fee, the attacker still receives approximately `4,250` before fee dilution effects. The attacker can withdraw after enough blocks pass because the same-block check only prevents withdrawing in the deposit block. [10](#0-9) 

The impact grows when an honest keeper harvests less frequently than `releaseBlocksPeriod`: rewards representing multiple days of accrual are still distributed over the same fixed `6400` blocks to whoever holds shares after the harvest. [11](#0-10) 

### Likelihood Explanation

`harvest` is expected to be invoked externally by the owner or rebalancer, and its transaction is publicly observable. Any allowed depositor can monitor the transaction and deposit in the next block; no privileged role is required for the exploitation transaction itself. [12](#0-11) 

The only meaningful constraint is the pool’s normal deposit eligibility and guarded-launch limit. The reward-locking mechanism does not stop post-harvest deposits, and there is no check requiring depositors to have been present during the period that generated the reward. [6](#0-5) 

### Recommendation

Track the period during which harvested rewards accrued and mint shares only after accounting for the reward attributable to existing holders.

A direct fix is to pass an explicit reward accrual duration to `harvest` and release rewards over that duration, rather than always using `releaseBlocksPeriod`. A stronger fix is to snapshot eligible tranche supply or maintain a reward-per-share index for each harvest so shares minted after harvest cannot receive previously generated rewards. Any configurable release period should also handle remaining rewards safely, rather than allowing a new harvest to overwrite `harvestedRewards` before prior rewards have fully unlocked. [13](#0-12) 

### Proof of Concept

The following Foundry sequence demonstrates the invariant break using a deployed `IdleCDO` fixture with a strategy that can return underlying-denominated reward proceeds:

```solidity
function testPostHarvestDepositorExtractsLockedRewards() public {
    uint256 initialDeposit = 1_000_000e6;
    uint256 reward = 10_000e6;
    uint256 attackDeposit = 1_000_000e6;

    // Existing depositor owns the vault before rewards are harvested.
    underlying.approve(address(cdo), initialDeposit);
    uint256 victimShares = cdo.depositAA(initialDeposit);

    // Make the reward available to the CDO/strategy according to the fixture.
    strategy.setPendingRewardValue(reward);

    // Honest rebalancer harvests. The reward is now stored but excluded from NAV.
    vm.prank(rebalancer);
    cdo.harvest(skipFlags, skipRewards, minAmounts, sellAmounts, extraData);
    assertApproxEqAbs(cdo.getContractValue(), initialDeposit, 1);

    // Attacker deposits in the block immediately after the harvest.
    deal(address(underlying), attacker, attackDeposit);
    vm.roll(block.number + 1);
    vm.startPrank(attacker);
    underlying.approve(address(cdo), attackDeposit);
    uint256 attackShares = cdo.depositAA(attackDeposit);
    vm.stopPrank();

    // Wait until the fixed release period completes.
    vm.roll(block.number + cdoReleaseBlocksPeriod + 1);

    uint256 victimBefore = victimShares * cdo.virtualPrice(cdo.AATranche()) / 1e18;
    uint256 attackerValue = attackShares * cdo.virtualPrice(cdo.AATranche()) / 1e18;

    // With zero performance fee, attacker extracts approximately:
    // reward * attackDeposit / (initialDeposit + attackDeposit) = 5_000e6.
    assertGt(attackerValue, attackDeposit);
    assertApproxEqAbs(attackerValue - attackDeposit, reward / 2, 2);
    assertApproxEqAbs(victimBefore, initialDeposit + reward / 2, 2);

    vm.prank(attacker);
    uint256 redeemed = cdo.withdrawAA(attackShares);
    assertApproxEqAbs(redeemed, attackDeposit + reward / 2, 2);
}
```

The key observation is that `virtualPrice` immediately after `harvest` excludes the newly locked reward, while the same attacker-held shares participate when that reward later becomes part of NAV. [14](#0-13) [3](#0-2)

  /// @return _locked amount of harvested rewards that are still not available to be redeemed
  function _lockedRewards() internal view virtual returns (uint256 _locked) {
    uint256 _releaseBlocksPeriod = releaseBlocksPeriod;
    uint256 _blocksSinceLastHarvest = block.number - latestHarvestBlock;
    uint256 _harvestedRewards = harvestedRewards;

    // NOTE: _harvestedRewards is never set to 0, but rather to 1 to save some gas
