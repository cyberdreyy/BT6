### Title
Writable shared `scripts` emptyDir lets an attacker-controlled service container tamper with the helper binary the build container execs - ([File: executors/kubernetes/steps_pod.go])

### Summary
In Concrete/native-steps mode, `stepsServiceContainer` mounts the same `scripts` `emptyDir` volume used to stage the trusted `gitlab-runner-helper` binary into every user-declared service container, with no `ReadOnly` restriction. Because service images/specs are attacker (job-author) controlled and start concurrently with the build container, a malicious service container can overwrite the binary at `stepsRunnerBinaryPath()` before or while the build container execs it as its `Command`, and before the Runner's own `pods/exec` dialer later invokes `steps proxy` against that same path.

### Finding Description
`stepsVolumeMounts` (executors/kubernetes/steps_pod.go, `func (s *executor) stepsVolumeMounts()`) unconditionally mounts the `scripts` volume at `s.scriptsDir()` with no read-only flag, and is used both by `stepsBuildContainer` and by `stepsServiceContainer`: [1](#0-0) 

`stepsServiceContainers` builds one such container per user-declared service, using attacker-controlled `service.Name`/spec, and calls `stepsServiceContainer`, which sets `VolumeMounts: s.stepsVolumeMounts()` on the service container the same way the build container does: [2](#0-1) [3](#0-2) 

The `scripts` volume is also where the init container copies the `gitlab-runner-helper` binary that the build container's `Command` (`stepsRunnerBinaryPath(), "steps", "serve", ...`) execs, and that the Runner's own `pods/exec` dialer later invokes as `steps proxy`: [4](#0-3) [5](#0-4) 

The init container runs first and populates the binary, but once it completes, the build container and all service containers start concurrently (Kubernetes gives no cross-container start ordering guarantee among a pod's non-init containers). Because the service container mount of `scripts` is writable, a job author can declare a `services:` entry whose image immediately overwrites `<scriptsDir>/gitlab-runner-helper` with attacker-controlled content, racing the build container's own exec of that same path. Existing checks do not stop this: `verifyAllowedImages` only gates which *image* may run, not what that image's process may write into a shared, writable volume; there is no `ReadOnly: true` on the service container's `scripts` mount, and there's no distinct "helper" trust boundary in Concrete mode — the doc/comments even say Concrete pods have no helper container, no init-permissions container, and no logs volume isolating this role.

This is a concrete instance of the role-confusion invariant: content originating from the "service" role (arbitrary job-declared image, potentially outside any build-image allowlist an operator configured) can end up executing in the "build" role's trusted execution path (`steps serve`) and in the path exercised by the Runner-side `pods/exec` dialer (`steps proxy`), because both roles share one writable filesystem location for a binary that is implicitly trusted.

### Impact Explanation
An attacker who can only declare a `services:` image (which may be less restricted than the primary build `image:` under an operator's `allowed_images`/`allowed_services` policy) can substitute the `gitlab-runner-helper` binary that the build container execs and that the Runner's `pods/exec` dialer later runs to establish the steps protocol. Since the steps protocol is used to inject job/environment variables (potentially including masked/secret values) into the build process, a substituted binary controlled by the service role could intercept or exfiltrate that data, or execute attacker code in the build container's process/security context instead of the intended helper — i.e., service-role content executing with build-role trust/capability.

### Likelihood Explanation
This requires no special privileges beyond normal CI pipeline authoring (defining a `services:` entry with an image the attacker controls, or a job whose service image has been supplied/compromised at the level a normal pipeline author can already reach). The race is timing-dependent (must win against the build container's own process start) but is repeatable across retries/job runs, and is deterministic in one respect: as long as the volume is writable and shared, the window exists on every run, only success probability varies.

### Recommendation
- Mount the `scripts` volume as `ReadOnly: true` in `stepsServiceContainer`'s `VolumeMounts` (service containers do not need write access to the binary-staging directory), or use a separate emptyDir for the helper binary that is never mounted into service containers at all.
- If service containers legitimately need a shared scratch/cache path, give them a distinct volume from the one carrying `stepsRunnerBinaryPath()`.
- Consider verifying the helper binary's integrity/hash immediately before `steps serve`/`steps proxy` invocation as defense in depth.

```go
func TestStepsServiceContainers_ScriptsMountMustBeReadOnly(t *testing.T) {

        "evil": {Name: "attacker/evil:latest"},
    }
    containers, err := ex.stepsServiceContainers()
    require.NoError(t, err)
    for _, m := range containers[0].VolumeMounts {
        if m.Name == "scripts" {
            assert.True(t, m.ReadOnly, "service containers must not have write access to the scripts volume carrying the helper binary")
        }
    }
}

Integration-level PoC job: define a `services:` entry whose entrypoint loops writing garbage/a malicious payload to `${CI_PROJECT_DIR}/../scripts/gitlab-runner-helper` (or the equivalent path under `s.scriptsDir()`), and observe that the build container's `steps serve` invocation intermittently fails/execs the attacker payload, confirming the shared writable mount crosses the service/build role boundary.

func (s *executor) stepsServiceContainers() ([]api.Container, error) {
	services := make([]api.Container, len(s.options.Services))

	for i, name := range s.options.getSortedServiceNames() {
		service := s.options.Services[name]
		kubernetesOptions := service.ExecutorOptions.Kubernetes.Expand(s.Build.GetAllVariables())
		securityContext := s.getSecurityContextWithUIDGID(
			string(kubernetesOptions.User),
			name,
			s.Config.Kubernetes.ServiceContainerSecurityContext,
		)

		c, err := s.stepsServiceContainer(name, *service, securityContext)
		if err != nil {
			return nil, err
		}
		services[i] = c
	}

	return services, nil
}
```
