### Title
Withdraw receipts are permanently bound to the requester address; if the payout transfer to that address ever fails, the claim is frozen forever with no way to update the recipient - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
In `IdleCreditVault`, every withdrawal claim pays out only to the original requesting address: `claimWithdrawRequest(_user)` burns the receipt and calls `_transferFundedClaim(_user, amount)` / `_transferDefaultRecovery(_user, amount)`, which `safeTransfer` underlying directly to `_user` (lines 301-350, 897-917). At the same time, the receipt token is deliberately non-transferable: `_transfer` reverts unless `msg.sender == idleCDO` (lines 939-942), and `setCanTransfer` can only ever set the flag to `false` — it is documented as "permanently disabled because receipt claims are address-bound" (lines 944-951). There is no function anywhere to redirect or re-assign a pending claim to a different payout address.

### Finding Description
This mirrors the Gitcoin `MerklePayoutStrategy` bug where a grantee address could not be updated after `isReadyForPayout` was set, leaving payouts permanently failing. Here the same invariant is enforced even more strictly:

- The claim destination is hardcoded to `_user` at request time (`requestWithdraw`/`requestInstantWithdraw` record `withdrawsRequests[_user]`, `lastWithdrawRequest[_user]`, `instantWithdrawsRequests[_user]`, lines 271-294, 356-375).
- All payout paths (`_claimFundedWithdrawRequest`, `_claimPostDefaultWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `_claimLossAdjustedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) end in `underlyingToken.safeTransfer(_user, ...)` — no recipient parameter exists.
- The escape hatch that would normally mitigate this (transferring the receipt to a fresh address) is explicitly disabled by the `_transfer` override and the irreversibly-locked `canTransfer` flag.

If the underlying token's `transfer` to `_user` reverts — e.g., the credit vault's underlying is a blacklistable stablecoin such as USDC/USDT and the user's address is blacklisted between request and claim, or `_user` is a contract wallet whose receive path now reverts — every claim for that user reverts permanently. Because the receipt cannot be moved and the recipient cannot be updated, the funded underlying backing that claim is locked in the vault forever.

There is a second-order consequence: the stuck claim keeps `withdrawsRequests[_user]`/`apr0Users[_user]`/`instantWithdrawsRequests[_user]` non-zero forever, and (for instant claims) `pendingInstantWithdraws` never decreases, which can additionally block `_ensureDefaultRecoveryInitialized` (line 926 reverts when `pendingInstantWithdraws != 0`), coupling one user's frozen payout to strategy-level accounting.

### Impact Explanation
Permanent freezing of the user's entire matured claim — 100% of `withdrawsRequests[_user] + settledPrincipal + settledInterest` (or the default-haircutted equivalent via `_transferDefaultRecovery`). The funds are on the contract balance but unreachable by the entitled user and unrecoverable without an `onlyOwner` `transferToken` rescue that would break reserve accounting (`defaultRecoveryReserve` accounting in `_transferFundedClaim`/`_transferDefaultRecovery`). This matches the external report's medium classification: payout functionality broken for the affected user, funds recoverable only via trusted intervention.

### Likelihood Explanation
Medium-low. It requires the claimant address to become unable to receive the underlying after the receipt is created. This is a realistic scenario for exactly the reasons cited in the original report: centralized-stablecoin blacklisting, compromised keys (the receipt cannot even be migrated to safety), or smart-contract wallets whose token-receive logic changes on upgrade. No attacker action is needed; the failure mode is structural — the protocol deliberately removed the only mitigation (transferable receipts) without adding an alternative recipient-update path.

### Recommendation
Allow the receipt holder to change the claim recipient or make claims transferable under control, e.g.:

- Add a `claimWithdrawRequestFor(address _receiver)` path where the CDO/strategy verifies `msg.sender`/authorization from the receipt owner and pays `_receiver` instead of `_user`; or
- Re-enable bounded receipt transfers (e.g., allow transfers when no default is pending) so a user whose address is compromised or blacklisted can migrate the receipt; or
- Add a pull-to-arbitrary-address claim signed by the receipt owner, keeping `defaultRecoveryReserve` accounting unchanged.

### Proof of Concept
Reproducible Foundry fork PoC (based on the existing harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Underlying = real USDC on mainnet fork.
// 1. KYC'd user deposits and requests a normal withdraw.
_depositWithUser(victim, 100_000e6, true);
vm.prank(victim);
uint256 claimAmt = cdoEpoch.requestWithdraw(0, address(AAtranche));

// 2. Epoch runs and stops; borrower's repayment funds the claim.
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

// 3. Victim's address gets blacklisted on USDC (or victim is a contract
//    whose onERC20Received now reverts).
vm.prank(USDC_BLACKLIST_ROLE);
usdc.blacklist(victim);

// 4. Claim always reverts: payout destination is hardcoded to `victim`.
vm.prank(victim);
vm.expectRevert(); // USDC transfer to blacklisted addr reverts
cdoEpoch.claimWithdrawRequest();

// 5. No escape: receipt cannot be transferred...
vm.prank(victim);
vm.expectRevert(NotAllowed.selector);
IERC20(address(strategy)).transfer(freshAddr, claimAmt);

// ...and canTransfer can never be re-enabled.
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
IdleCreditVault(address(strategy)).setCanTransfer(true);

// 6. Funds remain in the vault; victim's claim is permanently frozen.
assertEq(usdc.balanceOf(address(strategy)) >= claimAmt, true);
```

The same PoC applies to the instant-withdraw path (`claimInstantWithdrawRequest` → `safeTransfer(_user, ...)`) and to all post-default paths (`_transferDefaultRecovery`), since every one of them hardcodes `_user` as the sole possible recipient.
