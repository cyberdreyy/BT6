### Title
Loss-adjusted withdrawal receipts are keyed one epoch ahead of `lastWithdrawRequest`, letting requesters claim the full pre-haircut amount - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` at the moment it is called during `stopEpochWithDuration`. However, `epochNumber` is already incremented inside `deposit()` when it runs during a still-running epoch (i.e. inside `stopEpoch`), while each user's `lastWithdrawRequest` still points to the epoch in which the request was made. The claim path `_claimLossAdjustedWithdrawRequest` looks up the loss price via `lastWithdrawRequest`, finds nothing, and the funded-claim path then pays the entire receipt at par even though the borrower only funded the haircut amount. This mirrors the reported bug class: the boundary entry ("head") of the per-epoch sequence has no matching record, so the special case is skipped.

### Finding Description
- `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` (epoch N) and adds `_amount` to `pendingWithdraws` and `withdrawsRequestsByEpoch[_user][N]` (lines 259–294).
- `deposit()` increments `epochNumber` whenever `isEpochRunning()` is still true, i.e. when deposits are pulled in during `stopEpoch`/`stopEpochWithDuration` before the running flag is cleared (lines 607–610).
- `collectWithdrawFunds` then writes `lossRecoveryPriceByEpoch[epochNumber]`, i.e. under N+1, while zeroing `pendingWithdraws` (lines 411–425).
- On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = 0 and returns early (lines 789–795). `_claimFundedWithdrawRequest` then passes its gate because `epochNumber (N+1) > lastWithdrawRequest (N)` and pays `withdrawsRequests[_user]` in full from strategy-held underlying (lines 326–349).
- The same misalignment also defeats the re-request guard in `requestWithdraw` (lines 261–271): a user whose receipt was haircutted at epoch N is not detected, because the guard only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest]` which was never written for N.

### Impact Explanation
Any lender whose withdrawal request is pending in an epoch that ends with a `stopEpochWithDuration(_lossAmount > 0)` shortfall can claim 100% of the receipt instead of `lossRecoveryPrice` of it. The strategy only received the haircut amount from the borrower, so the excess is paid out of underlying belonging to other LPs or reserved claims: direct theft / insolvency equal to `claimBasis * (1 - lossRecoveryPrice)` per affected receipt, aggregate across all pending receipts of that epoch.

### Likelihood Explanation
Requires a realized epoch loss routed through `stopEpochWithDuration` (honest manager/borrower sequence, allowed by the rules) plus a pre-existing pending withdraw request — a normal, expected flow the loss-adjusted accounting was explicitly built for. The user then just calls `claimWithdrawRequest`; no privileged role is needed by the attacker.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the epoch the pending receipts were requested in (the epoch before the `epochNumber` bump), or defer the `epochNumber` increment in `deposit()` until after `collectWithdrawFunds` has run. Alternatively, look up the loss price by iterating `withdrawsRequestsByEpoch`/the request epoch recorded at request time rather than relying on `lastWithdrawRequest` matching the write epoch.

### Proof of Concept
```solidity
// Foundry fork test sketch (contracts/strategies/idle/IdleCreditVault.sol)
// Setup: running epoch N, unscaledApr != 0, KYC'd user deposits and calls
// cdoEpoch.requestWithdraw(amount, AAtranche).
// strategy.requestWithdraw stores lastWithdrawRequest[user] = N.

// manager calls stopEpochWithDuration(_lossAmount > 0) such that the
// borrower funds only pendingToFund < pendingWithdraws:
//   - inside stopEpoch, CDO deposit() bumps epochNumber to N+1
//   - collectWithdrawFunds(pendingToFund) writes
//     lossRecoveryPriceByEpoch[N+1] = price < 1e18, pendingWithdraws = 0

IdleCreditVault vault = IdleCreditVault(strategy);
assertEq(vault.lastWithdrawRequest(user), N);
assertEq(vault.lossRecoveryPriceByEpoch(N), 0);       // the "head" entry is missing
assertGt(vault.lossRecoveryPriceByEpoch(N + 1), 0);   // haircut stored one epoch ahead

uint256 claimBasis = vault.withdrawsRequests(user);
uint256 balPre = underlying.balanceOf(user);
vm.prank(user);
cdoEpoch.claimWithdrawRequest();                     // passes: epochNumber(N+1) > N
// user receives full claimBasis instead of claimBasis * price / 1e18
assertEq(underlying.balanceOf(user) - balPre, claimBasis);
// the haircut amount is stolen from other LPs' underlying held by the vault
```

Note: the validity of this finding depends on `collectWithdrawFunds` being invoked after the `epochNumber` increment inside `stopEpochWithDuration`; that ordering in `IdleCDOEpochVariant` could not be fully verified within the available search budget and should be confirmed in the PoC run.
