### Title
Loss-adjusted withdraw receipt escapes haircut by re-requesting after `stopEpochWithDuration` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analogous to the Footium stale-proof bug (a status valid at issuance time stays usable after the holder's status changed), `IdleCreditVault` resolves which withdraw receipts bear a `stopEpochWithDuration` loss haircut solely from `lastWithdrawRequest[_user]`. A lender whose receipt is haircutted can make a dust `requestWithdraw` in the next buffer, overwriting `lastWithdrawRequest`, so the loss epoch is never looked up and the haircutted receipt is paid at par through the funded-claim path.

### Finding Description
When a loss epoch is processed via `stopEpochWithDuration`, `lossRecoveryPriceByEpoch[lossEpoch]` is set and the borrower only funds the haircutted amount (`pendingToFund`). `_claimLossAdjustedWithdrawRequest` (contracts/strategies/idle/IdleCreditVault.sol:789-801) finds the loss epoch exclusively via `lastWithdrawRequest[_user]`:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

`requestWithdraw` (IdleCreditVault.sol:282) unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and appends to `withdrawsRequests[_user]`/`withdrawsRequestsByEpoch[_user][currentEpoch]`. The old epoch-N entry in `withdrawsRequestsByEpoch`/`withdrawsRequests` is left intact.

After the dust request, `lastWithdrawRequest` points to epoch N+1 where `lossRecoveryPriceByEpoch == 0`, so the loss-adjusted claim is skipped. `_claimFundedWithdrawRequest` (IdleCreditVault.sol:326-349) then only requires `epochNumber > lastWithdrawRequest` and pays out the *aggregate* `withdrawsRequests[_user]` — which still includes the epoch-N haircutted amount — at full par via `_transferFundedClaim`.

`lossRecoveryPriceByEpoch` is keyed per epoch but retrieval is keyed to only the *latest* request; there is no per-epoch iteration or oldest-epoch marker, so a previous epoch's haircut status is never re-checked — exactly the "relegated club replays old division proof" pattern.

### Impact Explanation
The attacker receives `receiptAmount * (1 - lossRecoveryPrice)` extra underlying that was never funded by the borrower. These funds are drawn from the vault/strategy NAV belonging to remaining lenders and to the pending-claims pool, causing direct insolvency of up to the full haircut portion of the attacker's receipt. In a near-total loss (`lossRecoveryPrice ≈ 0`), the attacker recovers ~100% par on a receipt that should have paid ~0.

### Likelihood Explanation
The attacker only needs to hold a tranche withdraw receipt in a loss epoch — a routine state. Executing a dust `requestWithdraw` during the next buffer period is permissionless and cheap. Requires a `stopEpochWithDuration` loss event (manager-initiated, honest), and one additional epoch to elapse before claiming. No privileged collusion needed.

### Recommendation
Track loss epochs per request epoch rather than only via `lastWithdrawRequest`. Either iterate `withdrawsRequestsByEpoch` for epochs with `lossRecoveryPriceByEpoch != 0`, or store a `lossEpochByUser`/queue of unclaimed loss-epochs that is checked in `claimWithdrawRequest` regardless of newer requests; also skip the haircutted portion when computing the funded-claim payout, e.g. subtract amounts belonging to epochs with a recorded recovery price before paying at par.

### Proof of Concept
Foundry fork, extending `test/foundry/IdleCreditVault.t.sol` helpers (`_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `stopEpochWithDuration` as used in `IdleCDOEpochQueue.t.sol:811-835`):

```solidity
function testLossReceiptEscapeViaDustRequest() external {
    // 1. attacker deposits AA during buffer of epoch N
    uint256 mintedAA = idleCDO.depositAA(10000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);

    // 2. attacker requests full withdraw -> receipt created in epoch N
    uint256 receipt = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));

    // 3. manager stops epoch N with a loss (e.g. 50% haircut on pending)
    //    borrower funds only pendingToFund (haircutted) amount
    cdoEpoch.stopEpochWithDuration(interest, 0, duration, lossAmount); // sets lossRecoveryPriceByEpoch[N]

    // 4. during next buffer, attacker deposits dust + requests dust withdraw
    idleCDO.depositAA(1); // tiny
    cdoEpoch.requestWithdraw(dustTranches, address(AAtranche));
    // lastWithdrawRequest[attacker] now = N+1, lossRecoveryPriceByEpoch[N+1] == 0

    // 5. advance one epoch so epochNumber > lastWithdrawRequest
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, apr, expected);

    // 6. claim: _claimLossAdjustedWithdrawRequest misses epoch N;
    //    _claimFundedWithdrawRequest pays receipt at PAR
    uint256 balPre = underlying.balanceOf(attacker);
    cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - balPre,
             receipt * lossRecoveryPrice / RECOVERY_FULL); // paid above haircut
}
```

Uncertainty: exact helper signatures for `stopEpochWithDuration` and whether `requestWithdraw` is callable in the same buffer where the loss was recorded (it is, per tests at IdleCDOEpochQueue.t.sol:848-851 which request right after `startEpoch`), but the invariant relies on `requestWithdraw` being permitted while the loss-epoch receipt is still pending, which the code allows since `_claimFundedWithdrawRequest`'s gating is only epoch-based.
