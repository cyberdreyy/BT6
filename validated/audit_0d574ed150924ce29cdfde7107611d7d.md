### Title
`/debug/vars` exposed to any authenticated session role via session-only auth with no role gate - ([File: core/web/router.go])

### Summary
The `debugRoutes` function wires `/debug/vars` behind `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)` only, with no `auth.RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` wrapper. Any user holding a valid session cookie—including the lowest-privilege View role—can reach the Go `expvar` handler, while an API-token-only credential (no `AuthenticateByToken` in the method list) cannot.

### Finding Description
`debugRoutes` in `core/web/router.go` registers the route as:
```go
func debugRoutes(app chainlink.Application, r *gin.RouterGroup) {
	group := r.Group("/debug", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	group.GET("/vars", expvar.Handler())
}
``` [1](#0-0) 

Compared with other routes in the same file (e.g. `v2Routes`), which explicitly wrap handlers with `auth.RequiresRunRole`, `auth.RequiresEditRole`, or `auth.RequiresAdminRole` after authentication, `/debug/vars` has no such role check — only `Authenticate` is applied, and `Authenticate` itself performs no role validation, it only confirms *some* valid credential was presented via one of the supplied `authMethod`s. [2](#0-1) 

`AuthenticateBySession` succeeds for any user with a valid, unexpired session regardless of `user.Role` (`View`, `Run`, `Edit`, `Admin`), setting `SessionUserKey` in context without any role filtering: [3](#0-2) 

Since `AuthenticateByToken` is not included in the method list for `/debug/vars`, a pure API-token holder (without ever establishing a session) cannot reach this endpoint, while a stolen/valid session cookie of any role can. This matches the described asymmetry exactly.

### Impact Explanation
A View-role session (the lowest privilege, normally read-only/dashboard access) can retrieve the standard Go `expvar` JSON output, which by default includes `cmdline` (process command-line arguments, which can reveal file paths, flags, or config locations) and `memstats` (detailed runtime memory statistics). No custom `expvar.Publish`/`NewString`/`NewInt`/`NewMap` calls were found elsewhere in this codebase, so no application-specific secrets are directly published into expvar today; the concrete impact is internal runtime/process metadata disclosure to a low-privilege session, an information-disclosure issue rather than key/secret exposure, and it is scoped only by session presence, not role.

### Likelihood Explanation
Precondition: possession of any valid session cookie (e.g. a View-role user's cookie, whether legitimately obtained or stolen via XSS/token theft). No admin, edit, or run privilege is needed. The request is a single unauthenticated-role-check `GET /debug/vars` with the session cookie attached — trivially repeatable, no rate limiting bypass or timing needed beyond normal session rate limits already applied to the `/` group.

### Recommendation
Add a role gate to the `/debug/vars` route consistent with other sensitive internal endpoints, e.g. wrap the handler with `auth.RequiresAdminRole` (or at minimum `RequiresEditRole`) so that View-role sessions cannot access runtime debug data:
```go
group.GET("/vars", auth.RequiresAdminRole(func(c *gin.Context) { expvar.Handler().ServeHTTP(c.Writer, c.Request) }))
```

### Proof of Concept
Handler-level integration test plan:
1. Build the router via `NewRouter` with a mock `AuthenticationProvider`.
2. Create a session for a user with `Role: clsessions.UserRoleView` and persist a valid `clsession_id` cookie via the session store (mirroring pattern used in `core/web/auth/auth_test.go`).
3. `httptest.NewRequest("GET", "/debug/vars", nil)` with the `Cookie` header set to the View-role session cookie.
4. Serve the request through the router and assert:
   - Response status is `200 OK`.
   - Response body is valid JSON containing `cmdline` and `memstats` keys (expvar payload).
5. Contrast test: issue the same request with only `X-API-KEY`/`X-API-SECRET` headers (API token, no session) and assert `401 Unauthorized`, confirming `AuthenticateByToken` is excluded from this route's method list.

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}
```

// Authenticate is middleware which authenticates the request by attempting to
// authenticate using all the provided methods.
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
