### Title
Stale beneficiary redirect in `staking_contract::distribute_internal` after `switch_operator` pays commission to former operator instead of their configured beneficiary - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`switch_operator` records the outgoing operator's unpaid commission as a distribution-pool share keyed by the *old* operator address before moving the `StakingContract` record to the new operator's key. When that distribution is later paid out via `distribute`/`distribute_internal`, the code only redirects a share to `beneficiary_for_operator(...)` if the shareholder address equals the *current* `operator` parameter passed into the function. Since the old operator is no longer the current operator, this comparison fails and the funds are paid directly to the old operator's own account instead of the beneficiary address they had configured with `set_beneficiary_for_operator`.

### Finding Description
In `switch_operator`, before moving the contract to the new operator, the code force-distributes inactive stake and requests outstanding commission under the **old** operator identity: [1](#0-0) 

`request_commission_internal` records this pending commission as a share in `staking_contract.distribution_pool` keyed by the operator address passed in (`old_operator`): [2](#0-1) 

The `StakingContract` (including its `distribution_pool`, which may still contain an old-operator share if the amount wasn't zero or a later `distribute()` wasn't yet called before the switch) is then re-added under the `new_operator` key in the `Store.staking_contracts` map.

When `distribute()` is eventually called for this pool, it looks up the contract by the **current** operator (`new_operator`) and calls `distribute_internal(staker, new_operator, staking_contract)`: [3](#0-2) 

Inside `distribute_internal`, the redirect-to-beneficiary logic only fires when the distribution-pool shareholder equals the `operator` argument (i.e., the *current* operator): [4](#0-3) 

Because the shareholder recorded for the old operator's pending commission is `old_operator`, and the function's `operator` parameter is now `new_operator`, `recipient == operator` is false. The payment therefore goes directly to `old_operator`'s account rather than `beneficiary_for_operator(old_operator)`, silently bypassing the beneficiary redirection that `set_beneficiary_for_operator` is documented to guarantee ("An operator can set one beneficiary for staking contract pools, not a separate one for each pool"): [5](#0-4) 

The beneficiary mapping is stored globally per-operator address (not per staking contract), so the expectation is that it should apply universally to that operator's commission regardless of which contract instance or key it is paid from - but the point-in-time `recipient == operator` check breaks this invariant specifically across an operator switch.

### Impact Explanation
This is a share/beneficiary-accounting corruption that credits the wrong account, explicitly one of the impacts in scope ("Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account or traps value"). An operator who has configured a beneficiary (e.g., a custodial/treasury address, an exchange deposit address, or a compliance-mandated payout account) for regulatory, security, or operational reasons will have their outstanding, already-requested commission silently rerouted to their own raw operator address instead of the intended beneficiary the moment the staker executes `switch_operator`. This can defeat security assumptions (e.g., an operator's hot key funds ending up unswept, or a beneficiary-based custody/tax arrangement being bypassed) without any error or event indicating the redirection failed.

### Likelihood Explanation
The trigger conditions are straightforward and reachable in normal staking operations without any privileged/attacker-only precondition:
1. Operator sets a beneficiary via `set_beneficiary_for_operator` (an unprivileged, operator-controlled action).
2. Operator accrues commission that is not fully distributed before the staker calls `switch_operator` (a normal, permitted staker action, not requiring the operator's consent).
3. Anyone (per the `distribute` doc, "allow anyone to distribute already unlocked funds") calls `distribute(staker, new_operator)`.

Because `switch_operator` itself is a completely ordinary, expected lifecycle action (changing operators is common), and the misrouting is deterministic and silent, this is very likely to manifest whenever a beneficiary is configured and an operator switch occurs with a non-zero pending commission balance.

### Recommendation
In `distribute_internal`, the beneficiary redirect should not be gated on `recipient == operator` (the *current* operator argument) but should instead check whether the recipient itself has a configured beneficiary, e.g., replace:
```
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};
```
with a lookup keyed on the shareholder itself, e.g. `if (exists<BeneficiaryForOperator>(recipient)) { recipient = beneficiary_for_operator(recipient); }`, guarded appropriately so it does not misfire for staker-owned shares (stakers should not normally have a `BeneficiaryForOperator` resource, but explicit differentiation between staker and operator shareholder classes in the distribution pool would make this robust and auditable).

### Proof of Concept
1. Staker creates a staking contract with `operator1` and commission > 0; `operator1` calls `set_beneficiary_for_operator(operator1, beneficiary1)`.
2. Stake pool accrues rewards; `operator1`'s commission accrues but is not yet distributed (validator lockup not yet expired, or `distribute` simply not yet called).
3. Staker calls `switch_operator(staker, operator1, operator2, new_commission)`. This internally calls `request_commission_internal(operator1, ...)`, adding a distribution-pool share for `operator1`, then moves the `StakingContract` under `operator2`'s key.
4. Lockup expires; anyone calls `distribute(staker, operator2)`.
5. `distribute_internal(staker, operator2, staking_contract)` iterates shareholders, finds `operator1`'s recorded share, compares `operator1 == operator2` (false), and pays the commission coins directly to `operator1`'s account instead of `beneficiary1`, contrary to the beneficiary configuration and documented guarantee.

This can be confirmed against the existing test `test_set_beneficiary_for_operator` at [6](#0-5)  pattern, which tests beneficiary payout and operator switching separately but never exercises the combined "pending commission at time of switch + later distribute" scenario, leaving this misrouting path untested.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

        // Request to unlock the commission from the stake pool.
        // This won't become fully unlocked until the stake pool's lockup expires.
        stake::unlock_with_cap(commission_amount, &staking_contract.owner_cap);

        let pool_address = staking_contract.pool_address;
        emit(
            RequestCommission {
                operator,
                pool_address,
                accumulated_rewards,
                commission_amount
            }
        );

        commission_amount
    }

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
