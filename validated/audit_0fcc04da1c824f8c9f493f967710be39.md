### Title
Multisig requests can execute below the live confirmation threshold because confirmations from deleted keys are never purged from other pending requests - (File: multisig/src/lib.rs)

### Summary
The multisig contract's `DeleteKey` action only removes requests that were *originated* by the deleted key, but it never scans the `confirmations` map to strip that key's confirmation from *other* still-pending requests. Because `confirm()` only compares the raw confirmation count against `num_confirmations`, a stale confirmation left behind by a removed key still counts toward the threshold, allowing a request (including a `Transfer`) to execute with fewer live, authorized confirmations than the configured threshold.

### Finding Description
`MultiSigContract::confirm` determines whether to execute a request purely by comparing the size of the stored `HashSet<PublicKey>` for that `request_id` against `self.num_confirmations`: [1](#0-0) 

Confirmations are only removed as part of `remove_request`, which is invoked either when a request is deleted/executed itself, or from the `DeleteKey` action's cleanup — but that cleanup filters strictly by `r.signer_pk == pk` (i.e. requests *added* by the removed key), not by scanning `self.confirmations` for the removed key's presence in *other* requests: [2](#0-1) 

So if key `A` confirms a pending request `R1` (added by a different key `C`), and later `A`'s key is legitimately removed via a separate, fully-confirmed `DeleteKey{A}` request, `R1`'s confirmation set still contains `A`. `A`'s access key no longer exists on-chain, yet its stale confirmation continues to count toward `R1`'s threshold in `confirm()`.

This breaks the intended equality: `confirmations.len() >= num_confirmations` is supposed to represent "at least `num_confirmations` currently-authorized keys have approved," but after a key removal it can instead represent "some currently-authorized keys plus one or more revoked keys have approved."

### Impact Explanation
This falls under the "Critical" impact class explicitly called out in the rules: a multisig request (e.g. a `Transfer` of NEAR, an `AddKey`, or a `FunctionCall`) can be **executed below the effective/live threshold**, because a phantom confirmation from a removed signer is still tallied. In a 3-of-4 multisig, an attacker/insider who previously held a now-revoked key can leave behind a permanent "vote" that lets any 2 of the remaining 3 live keys push through a transfer or key change that should have required 3 live approvals — undermining the entire security guarantee of the multisig scheme (fund custody and key-management authorization).

### Likelihood Explanation
This requires no special privilege beyond normal multisig operation: any organization that ever confirms a pending request, then later rotates/revokes that same signer's key (a common, expected operational action — e.g., an employee leaving, device compromise, key rotation), will have any of that signer's un-executed confirmations remain valid on other outstanding requests. Since active requests can persist for a while (subject only to `REQUEST_COOLDOWN` and `active_requests_limit`), the window in which a stale confirmation can be exploited is realistic and doesn't require compromising the removed key itself after revocation.

### Recommendation
When executing a `DeleteKey` action, iterate over `self.confirmations` and remove the deleted `public_key` from every request's confirmation set (not just requests it originated), decrementing/re-evaluating any request that had reached threshold only because of that stale entry. Alternatively, validate confirmations against the account's currently active access keys at `confirm()`/execution time rather than trusting the persisted `HashSet<PublicKey>` blindly.

### Proof of Concept
1. Deploy the multisig with `num_confirmations = 3` and four access keys `A, B, C, D`.
2. Key `C` calls `add_request` for `MultiSigRequest { receiver_id: <self>, actions: [Transfer { amount }] }` → `request_id = R1` (unconfirmed, 0 confirmations).
3. Key `A` calls `confirm(R1)` → `confirmations[R1] = {A}`.
4. Separately, keys `B`, `C`, `D` fully confirm a `DeleteKey{A}` request, which executes: `A`'s on-chain access key is deleted, and `remove_request` cleans up only requests where `signer_pk == A` (not `R1`, since `R1` was added by `C`). `confirmations[R1]` still equals `{A}`. [2](#0-1) 
5. Key `B` calls `confirm(R1)` → `confirmations[R1] = {A, B}`, count = 2 (still < 3).
6. Key `D` calls `confirm(R1)` → `confirmations[R1] = {A, B, D}`, count = 3 ≥ `num_confirmations`, so `execute_request` fires the `Transfer`. [3](#0-2) 
7. The transfer executes with only `B` and `D` — 2 live, currently-authorized signers — having actually approved it, even though the contract was configured to require 3 live confirmations; the third "confirmation" came from a key that had already been revoked.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
