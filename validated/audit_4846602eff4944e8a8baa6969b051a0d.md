### Title
`claimInstantWithdrawRequest` pays the aggregate receipt balance at par, bypassing per-epoch funding isolation and draining other claimants' funded reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2022-0305 is a site-isolation bypass: a compromised principal escapes its compartment and consumes resources belonging to other compartments. The closest analog in this codebase is the instant-withdraw receipt system in `IdleCreditVault`: receipt **funding is tracked per epoch** (`instantWithdrawClaimsByEpoch`, `pendingInstantWithdraws`), but the **claim path burns and pays the aggregate `instantWithdrawsRequests[user]` at par**. A user holding one old funded receipt can attach a new unfunded request to it and withdraw both at full value, spending underlying that is funded-reserved for other epochs' claimants.

### Finding Description
Instant-withdraw accounting is compartmentalized by epoch:

- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[user][epochNumber]` and increments the global unfunded bucket `pendingInstantWithdraws` (lines 356-375).
- `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` by what the borrower/CDO actually funded (lines 398-403). If start-epoch funding is partial, the remainder stays unfunded while still living inside `instantWithdrawsRequests`.
- `_defaultPrefundedInstantReserve` and `defaultPendingClaimBasis` explicitly acknowledge that `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` is the *funded* portion and that per-epoch identity is required to distinguish funded from unfunded receipts (lines 644-649, 716-723).

Yet `claimInstantWithdrawRequest` ignores this per-epoch isolation:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:380-393
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It pays the **entire aggregate** at par as long as the strategy holds enough tokens. Only the *default* path (`_claimDefaultedInstantWithdrawRequest`, lines 842-856) clears receipts per-epoch; the normal funded path never checks which epoch a receipt belongs to or whether it was actually funded. `_transferFundedClaim` only protects `defaultRecoveryReserve`, not other claimants' funded instant receipts (lines 897-907).

Attack sequence (running-epoch mode, instant withdraws enabled):

1. **Epoch N (buffer):** Attacker (KYC-passed tranche holder) calls `requestInstantWithdraw` for amount X. Epoch starts; borrower funds X via `collectInstantWithdrawFunds`. Attacker does **not** claim.
2. **Epoch N+1 (running):** Attacker requests instant withdraw again for amount Y. `instantWithdrawsRequests[attacker] = X + Y`; `pendingInstantWithdraws += Y`. Epoch ends with partial funding: borrower only covers part (or none) of the new requests, so `pendingInstantWithdraws` remains non-zero for epoch N+1 receipts.
3. Attacker calls `IdleCDOEpochVariant.claimInstantWithdrawRequest()` → `IdleCreditVault.claimInstantWithdrawRequest` burns `X + Y` receipts and transfers `X + Y` underlying at par, even though only X was ever funded. The strategy balance only contained funded amounts; the payout consumes funded reserves belonging to other users' epoch N+1 (or defaulted) receipts.

The broken invariant is **one receipt, one funded payout** — per-epoch funding isolation is bypassed by aggregate claiming, exactly mirroring the site-isolation bypass class.

### Impact Explanation
Direct theft with quantified loss: the attacker extracts up to `Y` underlying beyond what was funded for their receipts. Every wei over-funded to the attacker is taken from the strategy's underlying balance that was collected for other claimants; those users' subsequent `claimInstantWithdrawRequest` calls revert on insufficient balance, causing theft *and* freezing of their funded claims. The same over-claim drains reserves that `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` assumed were still backing current-epoch receipts, so if a default is later finalized the accounting (`defaultRecoveryPrice` over `totalBasis`) is computed against funds already leaked — worsening the haircut for all remaining claimants.

### Likelihood Explanation
Requires only: (a) an unprivileged KYC-passed tranche holder, (b) two instant-withdraw requests in consecutive epochs, and (c) one epoch where instant funding is partial — which the code explicitly supports (`pendingInstantWithdraws` may remain non-zero, and `_defaultPrefundedInstantReserve` exists precisely for partial-funding cases). No privileged action, no oracle manipulation, no reentrancy needed; `allowInstantWithdraw` gating in `IdleCDOEpochVariant.claimInstantWithdrawRequest` does not check per-epoch funding status. The missing check is structural, not configuration-dependent.

### Recommendation
In `claimInstantWithdrawRequest`, settle receipts per-epoch instead of using the aggregate:

- Track the funded amount per epoch (e.g., a `fundedInstantByEpoch` mapping populated by `collectInstantWithdrawFunds`), and pay only `min(userEpochBasis, remainingEpochFunding)` per claim epoch.
- Alternatively, when `pendingInstantWithdraws != 0`, cap each claim at the user's pro-rata share of the funded portion of `instantWithdrawClaimsByEpoch[epochNumber]`, and carry the unfunded remainder into the default-recovery basis exactly as `_claimDefaultedInstantWithdrawRequest` already does.
- As a defense-in-depth check, `_transferFundedClaim` could also exclude `pendingInstantWithdraws`-related funded sub-reserves, not only `defaultRecoveryReserve`.

### Proof of Concept
Foundry fork PoC (sketch — deploy `IdleCDOEpochVariant` + `IdleCreditVault` with instant withdraw enabled, a real/mock borrower, two users):

```solidity
function test_AggregateInstantClaimBypassesEpochFunding() public {
    // --- Epoch N: attacker requests instant withdraw, borrower funds it fully
    vm.startPrank(attacker); // KYC'd lender holding tranche tokens
    cdo.requestInstantWithdraw(X, AA);            // mints receipt, pendingInstant += X
    vm.stopPrank();

    vm.prank(manager); cdo.stopEpoch(interest);   // collects X into the strategy
    // attacker intentionally does NOT claim

    // --- Epoch N+1: attacker queues a second instant request
    vm.prank(attacker);
    cdo.requestInstantWithdraw(Y, AA);            // instantWithdrawsRequests[attacker] = X + Y

    // startEpoch funds only Z < (other users' receipts + Y) -> pendingInstantWithdraws stays > 0
    vm.prank(manager); cdo.stopEpoch(interest2);

    // --- Exploit: single claim pays X + Y at par although only X (+ maybe part) was funded
    uint256 balBefore = underlying.balanceOf(address(strategy));
    vm.prank(attacker);
    cdo.claimInstantWithdrawRequest();            // burns X + Y receipts
    assertEq(underlying.balanceOf(attacker), attackerPrev + X + Y);

    // --- Damage: honest user's funded receipt can no longer be paid
    vm.prank(victim);
    vm.expectRevert();                            // strategy balance drained
    cdo.claimInstantWithdrawRequest();
}
```

Key assertion: `claimInstantWithdrawRequest` transfers `instantWithdrawsRequests[user]` in full regardless of how much of that aggregate was funded per epoch, so the strategy's residual balance is insufficient for the remaining claimants — confirming both the theft and the freezing of unclaimed funded receipts.

**Caveat:** verification was limited to `IdleCreditVault.sol` and the CDO entry points shown; if `IdleCDOEpochVariant`'s instant-withdraw orchestration guarantees that *all* pending instant receipts are always fully funded before any claim is possible (i.e., `pendingInstantWithdraws == 0` is an enforced precondition at claim time), the finding reduces to an accounting-fragility issue. The presence of `_defaultPrefundedInstantReserve` and the unfunded-remainder handling in `defaultPendingClaimBasis` indicates partial funding is an expected state, which supports exploitability.
