### Title
Cross-user response hijacking via `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Finding Description
`HandleLegacyUserMessage` stores each pending trigger callback keyed only by the attacker-controlled `msg.Body.MessageId` with a plain map assignment and no existence check: [1](#0-0) 

`MessageId` is fully controlled by the requesting client — it comes straight from the JSON-RPC request `ID` / legacy message body, is only bounds-checked for length/format (`MessageIdMaxLen = 128`, no null suffix), and is never derived from or bound to the caller's identity: [2](#0-1) [3](#0-2) 

When a node later responds, `handleWebAPITriggerMessage` looks up and deletes whatever callback is currently registered under that `MessageId` and forwards the response to it, without checking that the entry corresponds to the request that was actually sent to that node: [4](#0-3) 

Exploit flow: User A submits a signed `web_api_trigger` legacy request with `MessageId=X`; the gateway saves `callbackA` under key `X` and forwards the request to all DON members. Before a node responds, User B submits their own signed request with the same `MessageId=X`; the assignment at line 412 silently overwrites the map entry with `callbackB`, and B's request is also forwarded to the DON. When a node responds to A's original message (still carrying `MessageId=X`), `handleWebAPITriggerMessage` finds `callbackB` (since A's entry was overwritten), deletes it, and delivers A's node response to B via `callbackB.SendResponse(...)`. A's own `ProcessRequest` call is left blocked on `callback.Wait(ctx)` and eventually times out with `RequestTimeoutError`, since `callbackA` was silently dropped from the map: [5](#0-4) 

No signature check, allowlist, or role check in the path prevents this, because those checks validate that a request came from a legitimate signer — they do nothing to enforce `MessageId` uniqueness or scope callback storage by sender/session.

### Impact Explanation
This is a cross-user response confusion: an unprivileged but authenticated user (any run/edit-role client able to submit a `web_api_trigger` legacy gateway request) can cause another concurrently in-flight user's trigger response to be delivered to themselves, and can silently deny/DOS that other user's request (which times out). This matches the "cross-user response confusion / hijacking of pipeline run result" impact class called out in the question.

### Likelihood Explanation
Exploitation only requires two authenticated callers submitting `web_api_trigger` messages with the same `MessageId` within the ~120s default callback window (`defaultCallbackMaxAgeSec`), and no coordination with the victim is needed beyond guessing/predicting or intentionally colliding on a `MessageId` (128-char attacker-chosen string, so an attacker could simply guess common/sequential/incrementing IDs used by client libraries, or run many collision attempts against a busy DON to increase odds). This is fully reproducible in a unit test and does not require a malicious node or any special privilege beyond normal signed request submission.

### Recommendation
Scope `savedCallbacks` keys by both `MessageId` and the caller's identity (e.g., sender/session key), and/or reject a new registration if an unexpired entry already exists for that `MessageId` (return an error to the second submitter instead of silently overwriting). Additionally, `handleWebAPITriggerMessage` should verify that the responding node's message actually corresponds to the request that was sent for that specific callback (e.g., by embedding/checking an expected DON member or request nonce) rather than trusting the map lookup alone.

### Proof of Concept
Go unit test plan for `handler_test.go`:
1. Construct two legacy `api.Message` requests with the same `DonId`/method (`web_api_trigger`) but different signers (A and B), both using `MessageId = "X"`.
2. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` then `h.HandleLegacyUserMessage(ctx, msgB, callbackB)` before any node response arrives; assert `h.savedCallbacks["X"]` now points to `callbackB`'s wrapper (not `callbackA`'s), proving the overwrite.
3. Simulate a node response for A's original request by calling `h.HandleNodeMessage` with `resp.ID = "X"` and a node address belonging to the DON; assert that `callbackB.SendResponse` is invoked (i.e., B receives A's data) and `callbackA.SendResponse` is never invoked.
4. Assert `h.savedCallbacks` no longer contains key `"X"`, confirming A's callback is permanently orphaned/timed out.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.

	}
	return nil
