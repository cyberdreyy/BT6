### Title
Lockup owner can keep delegating locked/unvested NEAR to a staking pool after it is removed from the whitelist - ([File: lockup/src/owner.rs])

### Summary
`select_staking_pool` checks the staking‑pool whitelist exactly once, at selection time, and stores the result permanently in `staking_information`. Every subsequent staking action (`deposit_to_staking_pool`, `deposit_and_stake`, `stake`, `unstake`, `withdraw_from_staking_pool`, `refresh_staking_pool_balance`) trusts that stored selection forever and never re-queries the whitelist contract, so a pool that is later removed from the whitelist (e.g. because the NEAR Foundation determined it is unsafe) can still receive further delegated NEAR from the lockup contract.

### Finding Description
`select_staking_pool` is the only place that consults the whitelist: [1](#0-0) 

The whitelist result is cached into `self.staking_information` in the callback: [2](#0-1) 

All later delegation calls only check `assert_owner`, `assert_staking_pool_is_idle`/`assert_no_termination`, and the owner's own balance — never the whitelist again — before sending funds to `self.staking_information.staking_pool_account_id`: [3](#0-2) [4](#0-3) 

Meanwhile the whitelist contract allows the foundation (or a whitelisted factory) to remove a pool at any time: [5](#0-4) 

The contract's own documented guarantee is that the whitelist mechanism prevents the owner from losing tokens by delegating to an unsafe pool: [6](#0-5) 

The equality this guarantee assumes is: `pool trusted at delegation time == pool currently whitelisted`. Because the check is performed once and cached, this equality only holds at the moment of `select_staking_pool`; it can silently diverge afterward — exactly the same "evaluate once, trust forever" pattern as the Goldilocks `boost()` bug, where a previously-valid NFT's validity was cached in `boostMagnitude` and never re-checked on extension.

### Impact Explanation
If a pool is de-whitelisted after being selected (because it turned out to be malicious, buggy, or its keys were compromised), the lockup owner (or anyone driving those owner-only calls, e.g. an automated integration) can still call `deposit_to_staking_pool`/`deposit_and_stake`/`stake` to push additional locked/unvested NEAR into that now-untrusted pool. Because lockup contracts routinely hold NEAR Foundation-owned unvested tokens (subject to termination clawback) as well as the owner's locked tokens, this can result in funds becoming unrecoverable from a pool that the whitelist mechanism was specifically designed to keep out of reach — i.e., a "wrongly whitelisted/trusted deployment" continuing to receive value after the trust decision it relied on has been revoked. This falls under the Critical impact category: a wrongly whitelisted/parameterized deployment continuing to be trusted for actions its authorization was withdrawn for.

### Likelihood Explanation
This requires no special privileges beyond the normal owner-only staking flow that already exists in the contract (`select_staking_pool` → later `deposit_to_staking_pool`/`stake`/etc.), and no deviation from documented initialization. It only requires the ordinary, expected event of the whitelist changing after selection (pool de-listed), which the whitelist contract explicitly supports via `remove_staking_pool`. There is no re-validation anywhere in the staking action code path, so the vulnerable state is reachable by design, not by misconfiguration.

### Recommendation
Re-check `is_whitelisted` (via `ext_whitelist::is_whitelisted`) for the currently selected `staking_pool_account_id` before executing `deposit_to_staking_pool`, `deposit_and_stake`, and ideally `stake`, failing the action (or forcing `unselect_staking_pool`/withdrawal flow) if the pool is no longer whitelisted, mirroring the fix pattern recommended in the referenced report (re-evaluate trust at the time of every use, not just at initial selection).

### Proof of Concept
1. NEAR Foundation whitelists `pool.near` in the `whitelist` contract.
2. Owner calls `select_staking_pool("pool.near")`; the callback `on_whitelist_is_whitelisted` succeeds and stores `staking_information` with `pool.near` as the selected pool ( [2](#0-1) ).
3. Foundation later calls `whitelist.remove_staking_pool("pool.near")` after detecting the pool is unsafe ( [5](#0-4) ).
4. Owner still calls `lockup.deposit_and_stake(amount)`; the method only checks `assert_owner`, `assert_staking_pool_is_idle`, `assert_no_termination`, and balance — no whitelist re-check — and transfers `amount` of (potentially unvested/foundation-owned) NEAR to `pool.near` ( [4](#0-3) ).
5. The additional funds are now delegated to a pool the foundation explicitly revoked trust from, breaking the "owner can not lose tokens by using staking methods" guarantee.

    pub fn select_staking_pool(&mut self, staking_pool_account_id: AccountId) -> Promise {
        self.assert_owner();
        assert!(
            env::is_valid_account_id(staking_pool_account_id.as_bytes()),
            "The staking pool account ID is invalid"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();

        env::log(
            format!(
                "Selecting staking pool @{}. Going to check whitelist first.",
                staking_pool_account_id
            )
            .as_bytes(),
        );

        ext_whitelist::is_whitelisted(
            staking_pool_account_id.clone(),
            &self.staking_pool_whitelist_account_id,
            NO_DEPOSIT,
            gas::whitelist::IS_WHITELISTED,
        )
        .then(ext_self_owner::on_whitelist_is_whitelisted(
            staking_pool_account_id,
            &env::current_account_id(),
            NO_DEPOSIT,
            gas::owner_callbacks::ON_WHITELIST_IS_WHITELISTED,
        ))
    }

    pub fn deposit_to_staking_pool(&mut self, amount: WrappedBalance) -> Promise {
        self.assert_owner();
        assert!(amount.0 > 0, "Amount should be positive");
        self.assert_staking_pool_is_idle();
        self.assert_no_termination();
        assert!(
            self.get_account_balance().0 >= amount.0,
            "The balance that can be deposited to the staking pool is lower than the extra amount"
        );

        env::log(
            format!(
                "Depositing {} to the staking pool @{}",
                amount.0,
                self.staking_information
                    .as_ref()
                    .unwrap()
                    .staking_pool_account_id
            )

        );

        self.set_staking_pool_status(TransactionStatus::Busy);

                .unwrap()
                .staking_pool_account_id,
            amount.0,
            gas::staking_pool::DEPOSIT,
        )

            amount,
            &env::current_account_id(),
            NO_DEPOSIT,

        ))

    /// Called after a given `staking_pool_account_id` was checked in the whitelist.
    pub fn on_whitelist_is_whitelisted(
        &mut self,
        #[callback] is_whitelisted: bool,
        staking_pool_account_id: AccountId,
    ) -> bool {
        assert_self();
        assert!(
            is_whitelisted,
            "The given staking pool account ID is not whitelisted"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();
        self.staking_information = Some(StakingInformation {
            staking_pool_account_id,
            status: TransactionStatus::Idle,
            deposit_amount: 0.into(),
        });
        true
    }

    /// Removes the given staking pool account ID from the whitelist.
    /// Returns `true` if the staking pool was present in the whitelist before, `false` otherwise.
    /// This method can only be called by the NEAR foundation.
    pub fn remove_staking_pool(&mut self, staking_pool_account_id: AccountId) -> bool {
        self.assert_called_by_foundation();
        assert!(
            env::is_valid_account_id(staking_pool_account_id.as_bytes()),
            "The given account ID is invalid"
        );
        self.whitelist.remove(&staking_pool_account_id)
    }

### Guarantees

With the guarantees from the staking pool contracts, whitelist, and voting contract, the lockup contract provides the following guarantees:
- The owner can not lose tokens or block contract operations by using methods under the staking section.
- The owner can not prevent the foundation from withdrawing the unvested balance in case of termination.
- The owner can not withdraw tokens locked due to lockup period, disabled transfers, or vesting schedule.
- The owner can withdraw rewards from the staking pool before tokens are unlocked unless the vesting termination prevents it.
