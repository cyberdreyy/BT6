### Title
Removing a token from `ProvisionerV2` locks out existing unit holders from redeeming/withdrawing that asset - ([File: v3/src/core/ProvisionerV2.sol])

### Finding Description
`ProvisionerV2.removeToken()` deletes the entire `tokensDetails[token]` entry [1](#0-0) , which zeroes out `syncRedeemEnabled` and `asyncRedeemEnabled` for that token. Both exit paths gate on these flags: `redeem()`/`withdraw()` call `_requireSyncRedeemsEnabled(token)` [2](#0-1) , and `requestRedeem()` requires `tokensDetails[token].asyncRedeemEnabled` [3](#0-2) . Once an admin removes a token (or disables it via `setTokenDetails`), any user already holding vault units minted against a synchronous deposit of that token loses every normal path to redeem back into that token until it is re-added — mirroring the ThunderNFT `Pool.withdraw()` pattern where `is_asset_supported()` blocked withdrawal of an already-deposited, subsequently delisted asset.

### Impact Explanation
Unlike the ThunderNFT case, `cancelRequest`/`refundRequest` for *pending, not-yet-solved* async requests do not check `tokensDetails` (only global cancellation toggles) [4](#0-3) , so in-flight requests can still be refunded. However, users who already completed a *synchronous* deposit and hold vault units have no alternative exit for that specific token once it is delisted — `redeem`/`withdraw` revert via `_requireSyncRedeemsEnabled`, and `requestRedeem` reverts via the `asyncRedeemEnabled` check. If the vault only accepts that token (or the user only wants that token back), funds are frozen until governance calls `setTokenDetails` to re-enable it.

### Likelihood Explanation
This requires only a routine, non-malicious admin action (`removeToken` or `setTokenDetails` disabling redeem flags) — the exact scenario described in the source report, not privileged/malicious collusion. This is a design symmetry gap rather than a demonstrated exploitable theft; I was unable to fully confirm whether every deployed vault configuration always exposes an alternative redemption token that would prevent an actual freeze, given available context.

### Recommendation
Decouple "can enter with this token" from "can exit with units already backed by this token." Allow `redeem`/`withdraw`/`requestRedeem` to proceed for tokens that were previously accepted and for which the vault still holds a balance, independent of the current `syncRedeemEnabled`/`asyncRedeemEnabled` admin flags, or provide an explicit emergency-redeem path unaffected by `removeToken`/`setTokenDetails`.

### Proof of Concept
Not independently verified with a Foundry run in this session — would require: (1) deploy `ProvisionerV2` + `MultiDepositorVault`, (2) `setTokenDetails` enabling sync deposit/redeem for `TOKEN`, (3) user `deposit()`s to mint units, (4) admin calls `removeToken(TOKEN)`, (5) assert user's `redeem()`/`withdraw()`/`requestRedeem()` calls all revert with `Aera__SyncRedeemDisabled`/`Aera__AsyncRedeemDisabled`-style errors despite holding valid units, demonstrating the freeze until `setTokenDetails` is called again.

    function cancelRequest(IERC20 token, RequestV2 calldata request) external nonReentrant {
        // Requirements: self-cancel caller must be request user
        require(msg.sender == request.user, Aera__CallerIsNotRequestUser());

        if (_isRequestTypeDeposit(request.requestType)) {
            // Requirements: deposit cancellation toggle must be enabled
            require(_depositCancellationsEnabled, Aera__DepositRequestCancellationDisabled());

            uint256 refundAmount = request.tokens;
            // Requirements: pre-deadline self-cancel applies cancellation fee
            if (block.timestamp < request.deadline) {
                uint256 cancellationFee = _computeDepositCancellationFeeTokens(token);
                // Requirements: cancellation fee cannot exceed escrowed amount
                require(cancellationFee <= refundAmount, Aera__CancellationFeeExceedsRequestAmount());
                if (cancellationFee != 0) {
                    unchecked {
                        // unchecked: safe because cancellationFee <= refundAmount is enforced above
                        refundAmount -= cancellationFee;
                    }
                    // Interactions: transfer cancellation fee to vault
                    token.safeTransfer(MULTI_DEPOSITOR_VAULT, cancellationFee);
                }
            }

            // Effects + interactions: clear hash, emit refund event, and transfer net token amount with fallback
            _clearHashAndTransferRefund(token, request, msg.sender, refundAmount, token);
        } else {
            // Requirements: redeem cancellation toggle must be enabled
            require(_redeemCancellationsEnabled, Aera__RedeemRequestCancellationDisabled());

            // Interactions: compute redeem request size in numeraire with protocol-favoring rounding
            uint256 requestNumeraire = PRICE_FEE_CALCULATOR.convertUnitsToNumeraire(
                MULTI_DEPOSITOR_VAULT, request.units, Math.Rounding.Ceil
            );
            // Requirements: redeem self-cancel must not exceed configured cap
            require(requestNumeraire <= _redeemCancellationCapNumeraire, Aera__RequestAmountExceedsRefundCap());

            // Effects + interactions: clear hash, emit refund event, and transfer net unit amount with fallback
            _clearHashAndTransferRefund(token, request, msg.sender, refundAmount, IERC20(MULTI_DEPOSITOR_VAULT));
        }

    function requestRedeem(
        IERC20 token,
        uint256 unitsIn,
        uint256 minTokensOut,
        uint256 solverTip,
        uint256 deadline,
        uint256 maxPriceAge,
        bool isFixedPrice,
        address receiver
    ) public anyoneButVault returns (bytes32 redeemHash) {
        // Requirements: units amount and min token out are positive, async redeems are enabled
        _validateNonZeroAmounts(unitsIn, minTokensOut);
        require(tokensDetails[token].asyncRedeemEnabled, Aera__AsyncRedeemDisabled());

        // Requirements: common request validation
        _validateRequest(receiver, solverTip, deadline, isFixedPrice);

        RequestType requestType = _getRequestType(isFixedPrice, false);

        // Interactions: transfer units from sender to provisioner
        IERC20(MULTI_DEPOSITOR_VAULT).safeTransferFrom(msg.sender, address(this), unitsIn);

        redeemHash = _getRequestHashParams(
            token, msg.sender, receiver, requestType, minTokensOut, unitsIn, solverTip, deadline, maxPriceAge
        );

        // Requirements: hash has not been used
        require(!asyncRequestHashes[redeemHash], Aera__HashCollision());

        // Effects: set hash as used
        asyncRequestHashes[redeemHash] = true;

        // Log redeem requested event
        emit RedeemRequested(
            msg.sender,
            receiver,
            token,
            minTokensOut,
            unitsIn,
            solverTip,
            deadline,
            maxPriceAge,
            isFixedPrice,
            redeemHash
        );
    }
