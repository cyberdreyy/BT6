### Title
Global (non-per-sender) cache capacity check in `requestCache.NewRequest` allows single-sender-class DoS/quota bypass - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces `maxCacheSize` as a single global counter (`len(c.cache) >= int(c.maxCacheSize)`), with no per-sender accounting. Since `globalId{sender, id}` only deduplicates by sender+messageId but the size check ignores sender identity entirely, any party able to submit signed gateway requests under distinct self-generated keys can fill the entire shared cache and block all other users' `NewRequest` calls until timeouts free slots.

### Finding Description
The relevant code is: [1](#0-0) 

`key := globalId{request.Body.Sender, request.Body.MessageId}` is only used to reject duplicate `(sender, id)` pairs; the capacity check `len(c.cache) >= int(c.maxCacheSize)` operates on the total map size across all senders, with no per-sender bucket or quota. An attacker who can sign gateway requests with `maxCacheSize` distinct sender keys (trivial — generating EOAs/keys is free) can occupy every cache slot, causing subsequent `NewRequest` calls from any other legitimate sender to fail with "request cache is full" until the attacker's own entries time out (`c.timeout`) or are resolved. This is confirmed directly by the existing `TestRequestCache_MaxSize` test showing the cache errors once the global size limit is reached regardless of sender: [2](#0-1) .

The second half of the question — that an attacker can then submit a forged response via `ProcessResponse` to win a race for a "subsequently admitted victim key" — is **not substantiated by this code**. `ProcessResponse` is invoked by the gateway only for messages routed from authenticated DON/node connections (keyed by `globalId{response.Body.Receiver, response.Body.MessageId}`), not from arbitrary unprivileged callers submitting signed requests through the normal ingress path. There is no code here (or found via search of callers such as `core/services/gateway/handlers/capabilities/v2/response_cache.go`) showing that an unprivileged requester can directly invoke `ProcessResponse` with attacker-controlled response content bypassing node-response authentication. That portion of the attack chain requires a compromised/malicious node or DON channel, which is explicitly out of scope per the audit rules.

### Impact Explanation
The confirmed impact is a resource-exhaustion / quota-bypass condition: a single unprivileged actor (using multiple self-owned signing keys) can deny service to all other gateway users of the shared `requestCache` by exhausting the global `maxCacheSize` slots, since there is no per-sender limit. This matches the "allowlist/quota bypass" impact class, but is a denial-of-service against a shared cache resource, not authentication bypass, key disclosure, or fund movement. The claimed escalation to targeted response impersonation via `ProcessResponse` race timing is not supported by the code path and is rejected.

### Likelihood Explanation
Precondition is trivial: the attacker only needs the ability to sign and submit `maxCacheSize` distinct requests with unique sender identifiers, which requires no privilege beyond generating keys, matching the "unprivileged attacker" threat model. This is fully repeatable and requires no timing precision for the DoS portion itself.

### Recommendation
Enforce a per-sender quota in addition to (or instead of) the global `maxCacheSize`, e.g., track counts keyed by `request.Body.Sender` and reject/rate-limit when a single sender exceeds a configurable per-sender cap, independent of overall cache occupancy. Consider combining this with authentication/allowlist checks upstream of `NewRequest` (if not already enforced there) so that gateway capacity cannot be monopolized by a single identity class.

### Proof of Concept
Go unit test plan (extends `requestcache_test.go`):
1. Create `cache := common.NewRequestCache[requestState](time.Hour, N)` with small `N` (e.g., 5).
2. Loop `i in 0..N`, generate a unique sender string per iteration (`fmt.Sprintf("attacker_%d", i)`), call `cache.NewRequest(lggr, req, callback, initialState)` — assert all succeed.
3. Attempt one more `NewRequest` call from a distinct "victim" sender — assert it returns `errors.New("request cache is full")`, proving no per-sender isolation exists.
4. (Optional, to demonstrate scope boundary) Attempt to call `cache.ProcessResponse` directly with an attacker-forged `api.Message` targeting the victim's `globalId` before the victim's request is ever admitted — assert it returns `"request not found"`, confirming that without the victim's request already being in cache (i.e., without control over the authenticated node-response channel), no impersonation is achievable through this code path alone.

func TestRequestCache_MaxSize(t *testing.T) {
	t.Parallel()

	cache := common.NewRequestCache[requestState](time.Hour, 2)
	callback := common.NewCallback()
	lggr := logger.Test(t)
	initialState := &requestState{}

	req := &api.Message{Body: api.MessageBody{MessageId: "aa", Sender: "0x1234"}}
	require.NoError(t, cache.NewRequest(lggr, req, callback, initialState))

	req.Body.MessageId = "bb"
	require.NoError(t, cache.NewRequest(lggr, req, callback, initialState))

	req.Body.MessageId = "cc"
	require.Error(t, cache.NewRequest(lggr, req, callback, initialState))
}
