### Title
Mid-epoch deposits change tranche NAV shares but `trancheAPRSplitRatio` is never refreshed, so the epoch interest split at `stopEpoch` is computed on stale weights — ([File: contracts/IdleCDOEpochVariant.sol:656-733](contracts/IdleCDOEpochVariant.sol))

### Summary
The external bug is an ordering flaw: validator-set updates are checkpointed before balance-changing operations (`ProcessBlock`), so the effects of those operations are silently ignored for the whole epoch. The direct analog in `IdleCDOEpochVariant` is `depositDuringEpoch`: it mutates the AA/BB NAV composition by minting new tranche tokens mid-epoch but never calls `_updateSplitRatio`, while the interest that accrues on that new principal is only split later — at `stopEpoch`'s `_updateAccounting` — using the stale `trancheAPRSplitRatio` snapshotted before the deposit.

### Finding Description
In the normal `_deposit` path, after minting shares the contract rebalances the interest split to match the new tranche TVL ratio: `_updateSplitRatio(_getAARatio(true))` (IdleCDOCreditVault.sol:208). `depositDuringEpoch` (IdleCDOEpochVariant.sol:656) deliberately runs while `isEpochRunning`, mints tranche tokens at a discounted price, bumps `expectedEpochInterest`, and mints strategy tokens — but it never updates `trancheAPRSplitRatio` and `stopEpoch`/`_updateAccounting` never refresh it either (the only `_updateSplitRatio` call inside `_stopEpoch` is in the minted-fee branch, and it runs after `_updateAccounting` at line 448 vs line 436).

`_virtualPriceAux` splits the entire epoch gain as `totalGain * splitRatio / FULL_ALLOC` regardless of actual NAV proportions. The split ratio is the mechanism that maps "interest share" to "tranche share"; every other mutating path re-syncs it. A mid-epoch deposit therefore leaves the checkpoint stale for the rest of the epoch: the whole epoch interest (including interest earned on the new principal) is divided with pre-deposit weights.

Concretely, with `isDepositDuringEpochDisabled == false` and BB deposits enabled, an attacker holding BB calls `depositDuringEpoch` with a large BB deposit. The minted BB supply grows, but `trancheAPRSplitRatio` still reflects the old (small) BB share, so BB's gain share `FULL_ALLOC - ratio` is over-weighted relative to the new NAV mix — or, symmetrically, an AA deposit when the stale ratio under-weights AA lets AA claim extra interest. In either direction one tranche's holders are paid interest that belongs to the other tranche, and the discrepancy is never corrected: the minted BB's prorated interest (`trancheInterest`) was already credited to the depositor via discounted minting, while the stale split still hands the *aggregate* epoch gain to the wrong side.

### Impact Explanation
Direct, quantified misallocation of epoch yield between tranche classes: the favored tranche's holders extract the disfavored tranche's interest share for the entire epoch, proportional to `|stale ratio − post-deposit ratio| × epoch interest`. With a large deposit relative to existing TVL the skew can be a substantial fraction of the epoch's interest. This violates the fair-mint/fair-split invariant (interest must follow `trancheAPRSplitRatio` consistent with current NAV), and no guard stops it: deposits during epoch are a first-class, KYC-gated feature, `_skimDonatedAssets` doesn't apply (funds go to the borrower), and the `Default` check is unrelated.

### Likelihood Explanation
Requires the pool to run with `isDepositDuringEpochDisabled = false` (a supported configuration; the flag exists precisely to enable it) and a non-disabled target tranche. Any KYC-passing lender can trigger it with a single `depositDuringEpoch` call during a running epoch; the loss crystallizes automatically at the next `stopEpoch` → `_updateAccounting`. No privileged collusion needed — owner/manager `stopEpoch` calls are honest and simply apply the stale ratio.

### Recommendation
Inside `depositDuringEpoch`, after `_mintShares` and `mintStrategyTokens`, call `_updateSplitRatio(_getAARatio(true))` so the interest split checkpoint reflects the post-deposit tranche composition — mirroring what `_deposit` does — or explicitly compute the minted-share entitlement so the depositor's interest is carved out of `expectedEpochInterest` rather than split with stale weights. Add an invariant test asserting `getCurrentAARatio`/`trancheAPRSplitRatio` consistency after mid-epoch deposits.

### Proof of Concept
Foundry fork sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testDepositDuringEpochStaleSplitRatio() external {
    // config: owner sets isDepositDuringEpochDisabled=false, isBBDepositEnabled=true
    // seed: AA deposits A, BB deposits B -> trancheAPRSplitRatio = A/(A+B) share
    idleCDO.depositAA(90_000 * ONE_SCALE);   // lender A
    vm.prank(manager); strategy.setBBEnabled(); 
    idleCDO.depositBB(10_000 * ONE_SCALE);   // lender B
    _startEpochAndCheckPrices(apr);          // epoch running, split ratio ~ A-side

    uint256 ratioPre = idleCDO.trancheAPRSplitRatio();

    // attacker: KYC'd lender deposits large BB mid-epoch
    uint256 bbBefore = BBtranche.totalSupply();
    vm.prank(attacker);
    idleCDO.depositDuringEpoch(90_000 * ONE_SCALE, address(BBtranche));

    // BUG: split ratio unchanged although BB is now ~50% of NAV
    assertEq(idleCDO.trancheAPRSplitRatio(), ratioPre); // stale checkpoint

    // end of epoch: borrower repays principal+interest, manager stops epoch
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(underlying, borrower, expectedRepay);
    vm.prank(manager);
    cdoEpoch.stopEpoch(newApr, 0);

    // BB gained FULL_ALLOC-ratioPre of total gain despite being ~50% of NAV
    // -> BB price inflated, AA price shorted vs pro-rata expectation
    uint256 priceBB = idleCDO.virtualPrice(address(BBtranche));
    assertGt(priceBB, expectedBBPriceProRata); // attacker redeems more BB value than entitled
}
```

The assertion `trancheAPRSplitRatio` remaining at `ratioPre` after a deposit that doubles BB's NAV share demonstrates the ignored state change; the post-`stopEpoch` `virtualPrice(BB)` exceeding the pro-rata price quantifies the yield stolen from AA holders.
