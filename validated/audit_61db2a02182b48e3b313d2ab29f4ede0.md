### Title
Missing `burn_block_receive_time` row forces unconditional reorg rejection in `check_parent_tenure_choice`, diverging affected signer from canonical view - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
In `SortitionData::check_parent_tenure_choice`, when `signer_db.get_burn_block_receive_time(&self.burn_block_hash)` returns `Ok(None)`, the timing-based permission check that allows a legitimate reorg is entirely skipped and the function falls straight through to `return Ok(false)`. This means a signer with a gap in its local receive-time history (fresh signer, DB reset, or a race where the `NewBurnBlock` event was processed before the row was durably recorded) will reject a reorg that every other signer with intact receive-time history correctly permits, regardless of how the reorg is timed.

### Finding Description
The equality that must hold is CANONICITY: every honest signer's `check_parent_tenure_choice` result for the same `(parent_tenure_id, prior_sortition, tenures_reorged)` input must agree, so the approved parent/tenure converges to the same canonical choice network-wide.

Tracing the code:
- `sortition_state_received_time = signer_db.get_burn_block_receive_time(&self.burn_block_hash)?` at [1](#0-0) .
- The per-superseded-tenure timing check is only performed when this value is `Some`; the timing arithmetic (`proposal_to_sortition`, comparison against `first_proposal_burn_block_timing`) and the `continue`/permit branch live entirely inside that `if let Some(...)` body [2](#0-1) .
- When the value is `None`, `checked_proposal_timing` is simply set to `false` with no timing evaluation at all, and execution falls through to the unconditional `return Ok(false)` right after [3](#0-2) .

So for a signer missing that DB row, *any* reorg whose reorged tenure has a mined+locally-known first block is rejected outright — even one that the timing rule would have explicitly permitted for every other signer (i.e., where `proposal_to_sortition < first_proposal_burn_block_timing` would have been true). The comment at line 197 ("this value *should* always be some, but try to do the best we can if it isn't") signals the intent was graceful degradation, but the actual fallback is "always reject," not a best-effort recomputation.

No retry path recomputes or backfills this row from within `check_parent_tenure_choice`, `record_superseded_tenure`, or the callers (`is_tenure_valid` in the same file). Since `get_burn_block_receive_time` is keyed by the specific historical `burn_block_hash` of this sortition, and the write path only occurs when the signer's runloop processes the live `NewBurnBlock` notification for that hash, a signer that missed/lost that one-time event has no way, in this code path, to ever populate the row for that sortition again.

### Impact Explanation
This breaks the CANONICITY equality across the honest signer set: the affected signer's approved parent/tenure diverges from the majority's for this specific reorg. Practically, the signer will keep returning `Ok(false)` for every subsequent block proposal built on that same (canonical) sortition, because the underlying missing DB row and the fixed `burn_block_hash` never change — it is wedged out of signing that tenure's canonical blocks. This matches the "signer wedged into never signing valid blocks (liveness)" category (High). It does not by itself cause a Critical chain-safety violation, since the bug fails toward rejection (conservative), not toward accepting/signing something invalid.

### Likelihood Explanation
The precondition — a missing `burn_block_receive_time` row for the specific sortition under evaluation — is a victim-side/environmental condition (new signer bootstrap, DB reset, or a durability race), not something a remote unprivileged attacker can directly cause through crafted `BlockProposal`/StackerDB gossip alone. An attacker (single miner slot) can win the tenure and legitimately propose a reorg that the timing rule is designed to permit, but whether it triggers this divergence in any given signer depends entirely on that signer's own local DB state, which is outside attacker control. This weakens the "attacker forces it" framing in the question: the bug is real and reachable, but it manifests as a general robustness/liveness defect under normal operation (any miner's legitimate reorg proposal triggers it for an affected signer), not as something an attacker can reliably target or repeat against a chosen victim.

### Recommendation
When `sortition_state_received_time` is `None`, do not silently fall through to rejection with no timing evidence. Either: (1) fail closed only after attempting to resolve the receive time via the stacks-node/client (e.g., derive an equivalent timestamp from `burn_header_timestamp` or query historical burn block info), or (2) explicitly treat this as a distinguished "insufficient local information" condition and use the same fallback approach used elsewhere in this function (e.g., asking the node) rather than defaulting the outcome to `false`. At minimum, log this divergence loudly and consider backfilling `burn_block_receive_time` for missed sortitions during signer startup/sync so the gap is not permanent.
