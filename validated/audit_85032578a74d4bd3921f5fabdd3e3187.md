### Title
Loss-adjusted withdraw receipts escape their haircut because `lossRecoveryPriceByEpoch` is keyed on the post-increment `epochNumber` while receipts are keyed on the request epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` stores the funded recovery ratio under the *current* `epochNumber`. User receipts, however, are indexed by `lastWithdrawRequest[user]` / `withdrawsRequestsByEpoch[user][requestEpoch]`, which is the epoch in which `requestWithdraw` was called — one epoch earlier. The loss-adjusted claim path therefore reads `lossRecoveryPriceByEpoch` at the wrong index (an off-by-one / out-of-bounds epoch read, the vault analog of the CVE's buffer over-read) and falls through to the par-funded claim path.

### Finding Description
- `requestWithdraw` records the receipt under `currentEpoch = epochNumber` (line 260) and sets `lastWithdrawRequest[user] = currentEpoch` (line 282) [1](#0-0) .
- `epochNumber` is incremented inside `deposit()` when `isEpochRunning()` is true, i.e. during the stop-epoch funding deposit (lines 607–611) [2](#0-1) .
- `collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` using whatever `epochNumber` is at that moment (line 421) [3](#0-2) .
- `_claimLossAdjustedWithdrawRequest` looks the price up at `lastWithdrawRequest[user]` — the request epoch, not necessarily the epoch under which the haircut was stored (lines 789–800) [4](#0-3) .

If `collectWithdrawFunds` executes after the epoch-bumping deposit inside `stopEpochWithDuration`, the haircut is stored under `requestEpoch + 1`. Every pending receipt then sees `lossRecoveryPriceByEpoch[requestEpoch] == 0`, skips `_claimLossAdjustedWithdrawRequest`, and `_claimFundedWithdrawRequest` pays the full `withdrawsRequests[user]` at par (lines 319–349) — even though only `pendingToFund < pendingBasis` was collected (lines 414–421). The symmetric guard in `requestWithdraw` (lines 263–271) also reads the request epoch, so it never blocks new requests on top of the orphaned haircut entry [5](#0-4) .

Even if the ordering is correct for the normal stop flow, a second related over-read exists: `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` while `_claimDefaultedInstantWithdrawRequest` clears `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — consistent only if `defaultRecoveryEpoch == epochNumber` at finalization and no prior partial funding already consumed `pendingInstantWithdraws`, leaving residual basis readable across epochs (lines 644–648, 842–856) [6](#0-5) .

### Impact Explanation
Broken invariant: loss waterfall / one receipt one haircut. If the haircut is stored under the incremented epoch, loss-adjusted pending receipts withdraw 100% of their basis while the strategy only received `pendingToFund`. First claimants drain the funded underlyings at par; later claimants (including post-loss depositors' funded receipts) either revert via the `defaultRecoveryReserve`/balance check in `_transferFundedClaim` (lines 897–907) or are left unpaid — direct insolvency equal to `pendingBasis - pendingToFund` of the epoch [7](#0-6) .

### Likelihood Explanation
Requires an unprivileged lender to hold a pending `requestWithdraw` receipt in an epoch that ends via `stopEpochWithDuration(_lossAmount > 0)` — a normal, non-privileged user action. The trigger (`stopEpochWithDuration`) is a manager/owner call, which is honest-but-sequenceable per scope. Whether the bug is exploitable depends on `IdleCDOEpochVariant.stopEpoch` calling `collectWithdrawFunds` after the deposit that increments `epochNumber`; this ordering could not be fully confirmed within available iterations and is the key item to verify in the PoC.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the receipts' request epoch (e.g., `epochNumber - 1` when called during the stop-epoch deposit window, or store the pending-receipt epoch explicitly before bumping `epochNumber`), or store the haircut epoch in a dedicated variable consumed by both `requestWithdraw`'s guard and `_claimLossAdjustedWithdrawRequest`. Add a unit test asserting `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` immediately after a loss-adjusted stop for a user who requested in that epoch.

// test/foundry/LossEpochMismatch.t.sol
function testLossHaircutKeyedOnWrongEpoch() external {
    uint256 amountWei = 10000 * ONE_SCALE;
    _depositWithUser(user1, amountWei, true);
    _startEpochAndCheckPrices(0);

    // user1 requests withdraw during the buffer; receipt keyed to epochNumber N
    uint256 reqEpoch = strategy.epochNumber();
    vm.prank(user1);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertEq(strategy.lastWithdrawRequest(user1), reqEpoch);

    // stopEpochWithDuration realizes a partial loss; collectWithdrawFunds stores
    // lossRecoveryPriceByEpoch[epochNumber] — check which epoch index is used
    deal(address(underlying), strategy.borrower(), 0, true);
    _stopEpochWithLoss(_lossAmount); // borrower repays less than pendingWithdraws

    // If the haircut was stored under reqEpoch+1, this read returns 0:
    uint256 storedAtReq = strategy.lossRecoveryPriceByEpoch(reqEpoch);
    uint256 storedAtNext = strategy.lossRecoveryPriceByEpoch(reqEpoch + 1);
    assertTrue(storedAtReq == 0 && storedAtNext != 0, "haircut keyed on post-increment epoch");

    // user1 claims at par despite only partial funding -> drains shared funded bucket
    uint256 balPre = underlying.balanceOf(user1);
    vm.prank(user1);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(user1) - balPre;
    uint256 haircutPay = strategy.withdrawsRequestsByEpoch(user1, reqEpoch) * storedAtNext / 1e18;
    assertGt(paid, haircutPay, "receipt paid above its haircut");
}

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
