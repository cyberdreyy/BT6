## Analog Found

### Title
Signer's stale rejection weight is never retracted after it accepts the same block, letting a single signer's weight be double-counted across mutually-exclusive tallies and wedge block finalization - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner's `StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` for a given block using two *different* dedup keys — `gathered_signatures` (a map keyed by `slot_id`) for acceptances and `responded_signers` (a set keyed by `slot_id`) for rejections. Because these are separate data structures instead of a single "current vote per signer" table, a signer who first rejects and later accepts the same block hash gets counted in **both** running sums permanently. This mirrors the reported `PoolGovernance::proposeEpoch` bug: a vote's weight is added to a tally without first removing/checking any weight the same voter previously contributed to a rival tally.

### Finding Description
In `handle_stackerdb_chunk_event` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`):

- On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` gated by `block.responded_signers.insert(slot_id)`: [1](#0-0) 

- On `BlockResponse::Accepted`, weight is added to `total_weight_approved` gated by a *different* structure, `block.gathered_signatures.contains_key(&slot_id)`: [2](#0-1) 

Sequence that breaks the invariant:
1. Signer `S` (slot `k`, weight `w`) sends `Rejected` for block `H`. `responded_signers.insert(k)` succeeds → `total_weight_rejected += w`.
2. `S` later sends `Accepted` for the *same* `H` (this is not merely theoretical — the signer-side logic explicitly allows reconsidering a rejected block and switching to acceptance, see `docs/signer-flows.md`: "we do not change our votes on rejected blocks unless we receive a new block proposal for it and the reject reason allows us to reconsider"). The check is `!block.gathered_signatures.contains_key(&slot_id)`, which is still `true` because `k` was never inserted into `gathered_signatures` by the reject path. So `total_weight_approved += w` as well, and `k` is inserted into `gathered_signatures`.
3. `total_weight_rejected` is never decremented — `w` now permanently counts toward *both* tallies, even though `S`'s current, live vote is "accept."

There is no code path anywhere in this file that subtracts weight from `total_weight_rejected` when a signer's vote later flips to `Accepted` (or vice versa the other direction is at least blocked by the `responded_signers` gate, but this direction is not). `BlockStatus` fields are simple `saturating_add` accumulators with no per-signer "current decision" reconciliation: [3](#0-2) 

The consumer of these tallies, `SignerCoordinator::wait_for_block_acceptance` (or equivalent in `signer_coordinator.rs`), checks the rejection condition *first* and returns `Err(SignersRejected)` before ever checking the approval condition: [4](#0-3) 

So once accumulated stale rejection weight (from signers who have since flipped to acceptance) crosses the blocking-minority threshold, the miner gives up on the block (`SignersRejected`) even if `total_weight_approved` has already reached, or would otherwise reach, the 70% approval threshold from the *current* set of signer decisions. This breaks the "aggregated-weight vs verified/current-accepts" equality that the threshold logic assumes.

### Impact Explanation
This is a liveness wedge triggerable by a single signer (no majority required): that signer's own stale, retracted rejection weight can never be un-counted, so it silently accumulates toward the blocking-minority threshold. Once crossed, the miner unconditionally treats the block as globally rejected and excludes transactions, even though the true, current signer weights (each signer's latest vote) may already satisfy the 70% approval threshold. This can cause the coordinator to reject a block that should have been signed and accepted, wedging tenure production for that block. It matches the "High" impact bucket — a signer state machine (here, the miner's coordinator, whose correctness the signer-set weight bookkeeping directly serves) getting wedged based on a stale/miscounted aggregate rather than the verified, current set of votes.

### Likelihood Explanation
High. It requires only a single signer to legitimately (or intentionally) send a `Rejected` message followed later by an `Accepted` message for the same `signer_signature_hash` — a pattern the signer-side logic itself documents as valid reconsideration behavior. No majority collusion, no other signer's key, and no StackerDB/auth bypass is needed; the attacker/reconsidering signer only ever uses their own slot and their own valid signature.

### Recommendation
Track a single "current vote" per signer (e.g., a `HashMap<slot_id, VoteKind>` or reuse `gathered_signatures`'s presence together with a parallel rejection map) and recompute `total_weight_approved`/`total_weight_rejected` by removing the previous vote's weight before adding the new one — analogous to the recommended fix in the report (decrement the old tally before incrementing the new one), e.g.:
```rust
// On Accepted:
if let Some(prev) = block.rejected_signers.remove(&slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_sub(signer_entry.weight);
}
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
}
...
// On Rejected:
if block.gathered_signatures.remove(&slot_id).is_some() {
    block.total_weight_approved = block.total_weight_approved.saturating_sub(signer_entry.weight);
}
if block.rejected_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
}
```

### Proof of Concept
1. Start a tenure where the miner proposes block `B` with `signer_signature_hash = H`.
2. From signer slot `k` (weight `w`), publish `BlockResponse::Rejected{ signer_signature_hash: H, .. }` on StackerDB. Observe `total_weight_rejected += w` via the `responded_signers.insert(k)` gate. [5](#0-4) 
3. From the same slot `k`, overwrite the chunk with `BlockResponse::Accepted{ signer_signature_hash: H, .. }`. Observe `total_weight_approved += w` via the `gathered_signatures.contains_key(k)` gate, while `total_weight_rejected` is unchanged (still includes `w`). [2](#0-1) 
4. Repeat with other signers over subsequent blocks/proposals (each only needs to flip vote once) so `total_weight_rejected` accumulates past the blocking-minority threshold (`total_weight - weight_threshold`) purely from stale, retracted rejections, while `total_weight_approved` independently also reaches the 70% threshold from current votes.
5. In `SignerCoordinator`'s wait loop, the rejection branch is checked first and returns `Err(SignersRejected)`, discarding a block that the live signer set would otherwise approve. [4](#0-3)
