### Title
Post-default instant withdraws bypass `defaultInstantWithdrawsFinalized` teardown and drain the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` was hardened for the post-default state (SES_EXITING analog: the defaulted epoch's receipt bucket is "torn down" and replaced by `postDefaultRequests`), but `requestInstantWithdraw` has no equivalent guard. After `finalizeDefaultRecovery`, a tranche-token holder can still open an instant withdraw in `epochNumber == defaultRecoveryEpoch`; the subsequent `claimInstantWithdrawRequest` treats that brand-new receipt as a defaulted-epoch claim and pays it out of `defaultRecoveryReserve`, which was sized only for pre-finalization claimants.

### Finding Description
The kernel bug skips sessions whose status is `SES_EXITING` during reconnect teardown. The vault analog is the defaulted epoch's instant-receipt bucket, which is "torn down" by `finalizeDefaultRecovery` yet still accepts new members.

In `finalizeDefaultRecovery`:
- `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` — sized from `defaultPendingClaimBasis()` = `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` (only if `pendingInstantWithdraws != 0`). [1](#0-0) 
- `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` and `defaultRecoveryEpoch = epochNumber`. [2](#0-1) 

`requestInstantWithdraw` (lines 356-375) has no `defaultRecoveryFinalized` branch at all — unlike `requestWithdraw`, which routes post-default requests into `postDefaultRequests` and reverts if old receipts are unclaimed. [3](#0-2)  It burns CDO strategy tokens, mints the receipt to the user, and increments `instantWithdrawsRequestsByEpoch[user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` — where `epochNumber` still equals `defaultRecoveryEpoch` because no further `stopEpoch` can bump it. [4](#0-3) 

`claimInstantWithdrawRequest` then calls `_claimDefaultedInstantWithdrawRequest`, which looks up `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — hitting the attacker's freshly-created receipt — and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve` via `_transferDefaultRecovery`. [5](#0-4) [6](#0-5) 

This claim basis was never included in `totalBasis` at finalization, so it is completely unbacked. `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch` decrements are clamped/aggregate, so the payout succeeds while reserve accounting silently absorbs the theft. `allowInstantWithdraw` remains `true` after a borrower default (confirmed by `testStopEpochWithDefault` / `testFundedInstantWithdrawRemainsClaimableAfterStopEpochDefault`), so the CDO exposes the instant-withdraw entry point post-default.

### Impact Explanation
Direct theft of the default recovery reserve. Each unit requested post-default mints a receipt that is paid `defaultRecoveryPrice`-per-unit out of a reserve that was sized only for active holders and pending-epoch claimants. An attacker holding tranche tokens (or flash-acquiring them) before/around finalization can convert a share priced at the post-haircut virtual price into an immediate reserve payout, draining funds owed to legitimate defaulted-epoch redeemers and active holders who claim through `DefaultDistributor`. Loss is bounded by the reserve size but is effectively total for a low recovery price: an attacker can repeatedly request and claim until the reserve is exhausted, leaving honest claimants with zero.

### Likelihood Explanation
Requires a borrower default with `pendingInstantWithdraws != 0` at finalization (so `defaultInstantWithdrawsFinalized` is set) and a non-zero recovery reserve. Borrower default is a protocol-native state, not attacker-controlled, but defaults are the scenario this code explicitly targets. The attacker needs only tranche tokens — an unprivileged permissionless position. No privileged cooperation is required, and no existing guard (`_onlyIdleCDO`, KYC, epoch gating, skim) blocks the sequence since instant withdraws are intentionally left enabled post-default.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is true, either revert or route the request into a post-default bucket (`postDefaultRequests`-style) that is paid 1:1 from funded liquidity and never enters `instantWithdrawsRequestsByEpoch[defaultRecoveryEpoch]`/`instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]`. At minimum, record post-default instant requests under a distinct epoch key so `_claimDefaultedInstantWithdrawRequest` cannot match them.

### Proof of Concept
Foundry fork PoC sketch (concrete sequence; not executed here):

```solidity
// Setup: deposit AA+BB, startEpoch, let a normal user requestInstantWithdraw,
// partially fund via getInstantWithdrawFunds so pendingInstantWithdraws != 0.
// Then default the borrower and finalize:
cdoEpoch.finalizeDefault(recovered, manager); // defaultRecoveryFinalized = true

// Attack: attacker holds AAtranche tokens.
// CDO-side instant request routes to strategy.requestInstantWithdraw:
vm.prank(attacker);
cdoEpoch.requestWithdraw(attackerTrancheBal, address(AAtranche)); // instant path when allowed
// strategy now has instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch] > 0

uint256 reservePre = creditVault.defaultRecoveryReserve();
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
// _claimDefaultedInstantWithdrawRequest pays attacker from reserve even though
// his claim was created after totalBasis was fixed.
assertLt(creditVault.defaultRecoveryReserve(), reservePre);

// Legit defaulted claimants now underflow/underpay:
vm.prank(victim);
cdoEpoch.claimInstantWithdrawRequest(); // pays less or reverts on depleted reserve
```

Uncertainty: the exact CDO entry point name/params for post-default instant requests and whether `requestWithdraw` vs a dedicated instant path is used post-default was not fully traced into `IdleCDOEpochVariant.sol` (grep returned match counts, not bodies). The vault-side defect — missing `defaultRecoveryFinalized` handling in `requestInstantWithdraw` combined with epoch-key reuse in `claimInstantWithdrawRequest` — is confirmed by the cited code.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
