### Title
Unauthenticated cache-cold-start amplification via MethodPublicKeyGet fan-out - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
`HandleJSONRPCUserMessage` explicitly bypasses `h.requestProcessor.ProcessRequest` for `vaulttypes.MethodPublicKeyGet` and instead calls `h.getCachedPublicKey()`; when the cache is empty (e.g., immediately after gateway startup, before the periodic `fetchVaultPublicKey` ticker populates it, or if the DON is slow/unreachable so the cache never fills), every request creates a new `activeRequest` via `h.newActiveRequest` and fans out to all DON nodes via `h.fanOutToVaultNodes`. Nothing in this code path enforces a per-sender or global rate limit on unauthenticated `MethodPublicKeyGet` traffic before the fan-out occurs.

### Finding Description

The only guards on `req.ID` are non-empty and ≤200 chars [2](#0-1) , and `newActiveRequest` only rejects a request if that exact same `req.ID` string is already active [3](#0-2) ; it does not track or throttle by sender/IP. When `getCachedPublicKey()` returns `nil, nil` (cache empty), `handlePublicKeyGet` calls `fanOutToVaultNodes`, which sends the request to every DON member node via `h.don.SendToNode` [4](#0-3) [5](#0-4) .

The `nodeRateLimiter` field on `handler` (configured via `Config.NodeRateLimiter`) is only applied in `HandleNodeMessage` to throttle *inbound* node responses [6](#0-5) ; it does not throttle inbound user requests reaching `HandleJSONRPCUserMessage`. Tracing the call path up through `gateway.ProcessRequest` (`core/services/gateway/gateway.go`) and `httpServer.handleRequest` (`core/services/gateway/network/httpserver.go`), the only protections present at the HTTP boundary are JSON decoding, an ID-length check, and `MaxRequestBytesLimiter` (body-size limiting) — no per-sender/global request-rate limiter is applied before `h.HandleJSONRPCUserMessage` is invoked for this handler. By contrast, other gateway handlers (e.g., the HTTP trigger v2 handler) do implement an explicit `userRateLimiter`/`checkRateLimit` before fan-out, confirming rate limiting is an available but here-unapplied pattern for this specific unauthenticated path.

Because `MethodPublicKeyGet` is intentionally exempted from `h.requestProcessor.ProcessRequest` (the authorization/allowlist/JWT/quota checks applied to all other methods), an attacker needs zero credentials to reach the fan-out code as long as they can send a well-formed JSON-RPC request with a unique `req.ID` while the cache is cold.

### Impact Explanation
This is a scoped, unauthenticated amplification vector against the DON: each distinct request during a cold-cache window results in one message being broadcast to every node in `donConfig.Members`, and each spawns a tracked `activeRequest` held in `h.activeRequests` (cleaned up on timeout/response). A burst of many concurrent unique-ID requests during a cold-cache window (gateway restart, DON unavailability, or a cache invalidation gap) causes N× fan-out to all nodes and N pending in-memory `activeRequest` objects, consuming node-facing bandwidth/CPU and gateway memory without any authentication. This maps to an unauthenticated allowlist/quota-bypass amplification issue (DoS-adjacent) rather than a data-disclosure or fund-movement bug — it does not itself achieve key/secret disclosure, request impersonation, or authorization bypass, since `MethodPublicKeyGet` only returns a public key (not privileged information) and cross-user response confusion isn't possible via distinct `req.ID`s.

### Likelihood Explanation
Preconditions: attacker only needs network access to the gateway's public HTTP endpoint and no credentials at all, matching the "fully unauthenticated attacker" scenario. The cold-cache window is finite (the ticker in `Start` refreshes the cache every minute via `fetchVaultPublicKey`, and once a successful response is cached via `tryCachePublicKeyResponse`, subsequent requests are served synchronously without fan-out) — so the exploitable window is limited to gateway startup, DON unavailability, or a race where cache-population itself is stalled. Repeatability is bounded by this window unless the attacker can also keep the cache perpetually invalid (not shown to be possible from this code alone). This is a real, reachable, low-effort gap, but its practical severity depends on how long the cold window realistically lasts and whether upstream infra (LB/WAF rate limiting) mitigates it — those external controls are outside this file and not verifiable here.

### Recommendation
Apply a per-sender/global rate limiter (similar to `userRateLimiter`/`checkRateLimit` pattern used in `http_trigger_handler.go`) to unauthenticated `MethodPublicKeyGet` requests in `HandleJSONRPCUserMessage` before calling `newActiveRequest`/`handlePublicKeyGet`, so that cache-miss fan-outs are bounded per source even without a sender identity (e.g., keyed by remote IP or a lightweight global token bucket). Additionally, consider coalescing concurrent cache-miss requests into a single in-flight fan-out (singleflight pattern) so N concurrent unique-ID requests during a cold cache trigger only one fan-out to nodes rather than N.

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/vault/handler_test.go`:
1. Construct a `handler` with an empty `cachedPublicKeyGetResponse`/`cachedPublicKeyObject` (simulating a cold cache) and a mocked `don.SendToNode` recording invocation counts.
2. Concurrently invoke `handler.HandleJSONRPCUserMessage(ctx, req, callback)` N times (e.g., N=100) with `req.Method = vaulttypes.MethodPublicKeyGet` and unique `req.ID` values, no `req.Auth`.
3. Assert current behavior: `don.SendToNode` is called `N * len(donConfig.Members)` times and `len(h.activeRequests) == N` immediately after dispatch — demonstrating unconditional fan-out with no per-source rejection.
4. Add an assertion (as the fix criterion) that a rate limiter should reject requests beyond a configured burst — expected post-fix behavior: `don.SendToNode` call count is bounded (e.g., capped near `burst * len(donConfig.Members)`) and excess requests receive a `LimitExceededError`/`RequestTimeoutError`-style rejection instead of creating an `activeRequest`.

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) handlePublicKeyGet(ctx context.Context, ar *activeRequest) error {
	l := logger.With(h.lggr, "method", ar.req.Method, "requestID", ar.req.ID)

	publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
	if cachedPublicKey != nil {
		l.Debugw("returning cached public key response")
		return h.sendSuccessResponse(ctx, l, ar, &jsonrpc.Response[json.RawMessage]{
			Version: jsonrpc.JsonRpcVersion,
			ID:      ar.req.ID,
			Method:  ar.req.Method,
			Result:  (*json.RawMessage)(&publicKeyResponseBytes),
		})
	}

	l.Debugw("cache stale: forwarding request to nodes", "now", h.clock.Now())
	return h.fanOutToVaultNodes(ctx, l, ar)
}

func (h *handler) fanOutToVaultNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var nodeErrors []error
	for _, node := range h.donConfig.Members {
		err := h.don.SendToNode(ctx, node.Address, &ar.req)
		if err != nil {
			nodeErrors = append(nodeErrors, err)
			l.Errorw("error sending request to node", "node", node.Address, "error", err)
		}
	}

	if len(nodeErrors) == len(h.donConfig.Members) && len(nodeErrors) > 0 {
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("failed to forward user request to nodes"), nil))
	}

	l.Debugw("successfully forwarded request to Vault nodes")
	return nil
}
