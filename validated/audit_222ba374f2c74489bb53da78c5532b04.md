### Title
Withdraw-request overwrite of `lastWithdrawRequest` skips the loss-adjusted haircut and pays a defaulted-on receipt at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` writes the haircut as `lossRecoveryPriceByEpoch[epochNumber]` and clears `pendingWithdraws`, but the per-user receipt accounting in `withdrawsRequests`/`withdrawsRequestsByEpoch` is left untouched. The later claim path locates a loss-adjusted epoch exclusively via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. If the same user issues any new `requestWithdraw` in a subsequent buffer/epoch before claiming, `lastWithdrawRequest[_user]` is overwritten to the new epoch. `_claimLossAdjustedWithdrawRequest` then looks up the wrong (new) epoch, finds price 0, returns 0, and `_claimFundedWithdrawRequest` pays the aggregate `withdrawsRequests[_user]` — including the haircutted epoch's basis — at par. This is the credit-vault analog of the CVE's "over-read past the intended element" bug class: the claim reads the wrong epoch slot and escapes the recorded loss.

### Finding Description
Relevant code:

- Loss haircut recorded per-epoch, `pendingWithdraws` zeroed, user aggregates untouched (`contracts/strategies/idle/IdleCreditVault.sol:411-430`).
- Loss-adjusted claim keyed only by `lastWithdrawRequest[_user]` (`IdleCreditVault.sol:789-801`):
  `uint256 lossEpoch = lastWithdrawRequest[_user]; uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];`
- Every new `requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:282`) while accumulating `withdrawsRequests[_user] += _amount` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (lines 292-293).
- Funded path pays the whole aggregate `normalAmount = withdrawsRequests[_user]` at par once `epochNumber > lastWithdrawRequest[_user]` (`IdleCreditVault.sol:326-349`); `_clearWithdrawClaimForEpoch` is only invoked from the loss/defaulted paths, so a skipped loss epoch is never removed from the aggregate.

Attack sequence (attacker = ordinary KYC'd tranche holder):

1. Epoch N running → buffer opens. Attacker calls `IdleCDOEpochVariant.requestWithdraw` → vault `requestWithdraw`: mints receipt tokens, `lastWithdrawRequest[attacker] = N`, `withdrawsRequests[attacker] = X`, `withdrawsRequestsByEpoch[attacker][N] = X`, `pendingWithdraws += X`.
2. `stopEpochWithDuration` realizes a loss; borrower funds only `pendingToFund`. `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[N] = funded/basis < RECOVERY_FULL` and sets `pendingWithdraws = 0`.
3. In epoch N+1 buffer the attacker calls `requestWithdraw` again (any amount Y). `lastWithdrawRequest[attacker] = N+1`; `withdrawsRequests[attacker] = X + Y`; `withdrawsRequestsByEpoch[attacker][N+1] = Y`.
4. After `stopEpoch` ends epoch N+1 (or pool close, `epochEndDate == 0`), attacker calls `IdleCDOEpochVariant.claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N+1] == 0` → returns 0 (line 791-792).
   - `_claimFundedWithdrawRequest` passes the `epochNumber > lastWithdrawRequest` check, computes `amount = X + Y (+ apr0)`, burns receipts, and calls `_transferFundedClaim` paying the full unhaircutted sum (lines 338-349).
5. The haircut that should have hit the attacker's epoch-N receipt is never applied. The strategy pays out more than it collected for that epoch's receipts, directly draining value belonging to other LPs/receipt holders (insolvency transfer), or — symmetric — an honest user who re-requests before claiming forfeits the loss accounting while the reserve math assumed a haircut, creating a shortfall for later claimants.

### Impact Explanation
Direct over-payment of underlying: the attacker recovers `X` at 100% instead of `X * lossRecoveryPrice / RECOVERY_FULL`. The stolen amount is `(X * (RECOVERY_FULL - lossRecoveryPrice)) / RECOVERY_FULL`, i.e., exactly the share of realized epoch loss the haircut assigned to that receipt. Loss is borne by the vault's underlying balance, shortchanging other funded claims and active LPs — a broken "one receipt one payout" / loss-waterfall invariant with quantifiable theft.

### Likelihood Explanation
High once a loss event occurs: the exploit needs only two ordinary `requestWithdraw` calls by the same unprivileged lender across consecutive epochs, plus waiting one epoch — all normal user flows with no privileged cooperation. The only precondition is a `stopEpochWithDuration` loss (or any path that writes `lossRecoveryPriceByEpoch`), which the codebase explicitly supports and has dedicated tests for. No access-control, KYC, skim, or epoch gating stops it; `defaultRecoveryInitialized` is already set on that path.

### Recommendation
Track loss-adjusted epochs independently of the mutable `lastWithdrawRequest` pointer: e.g., iterate/record the request epochs per user, store a per-epoch loss marker checked inside `_claimFundedWithdrawRequest`/`_clearWithdrawClaimForEpoch`, or subtract each loss-adjusted epoch's basis from `withdrawsRequests[_user]` at `collectWithdrawFunds` time (as `pendingWithdraws` already is) so the funded aggregate can never include a haircutted receipt. At minimum, when writing `lossRecoveryPriceByEpoch[epochNumber]`, ensure a later request cannot cause that epoch's basis to remain payable at par.

### Proof of Concept
Foundry fork test (scaffold follows `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// contracts: IdleCDOEpochVariant cdoEpoch, IdleCreditVault strategy, AAtranche
function testLossHaircutBypassedBySecondRequest() external {
    // 1) deposit, start epoch 0, stop it to enter buffer of epoch 1
    idleCDO.depositAA(10000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager); cdoEpoch.stopEpoch(0, 0);           // epochNumber -> 1

    // 2) attacker requests withdraw in epoch 1
    uint256 req1 = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));
    assertEq(strategy.lastWithdrawRequest(address(this)), 1);

    _startEpochAndCheckPrices(1);

    // 3) stopEpochWithDuration realizes a loss -> lossRecoveryPriceByEpoch[1] < RECOVERY_FULL
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = strategy.pendingWithdraws();
    uint256 loss = pending / 2; // borrower funds only half of pending receipts
    // fund active-side loss + pendingToFund as the flow requires, then:
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(loss, 30 days);          // writes lossRecoveryPriceByEpoch[1]
    assertLt(strategy.lossRecoveryPriceByEpoch(1), 1e18);

    // 4) BEFORE claiming, attacker files a second withdraw request (epochNumber -> 2)
    uint256 req2 = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 4, address(AAtranche));
    assertEq(strategy.lastWithdrawRequest(address(this)), 2); // epoch-1 haircut pointer overwritten

    _startEpochAndCheckPrices(2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws());
    vm.prank(manager); cdoEpoch.stopEpoch(0, 0);            // epochNumber -> 3

    // 5) claim: loss-adjusted path looks up epoch 2 (price 0), funded path pays req1 at par
    uint256 balBefore = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(address(this)) - balBefore;

    // BUG: full req1 paid although lossRecoveryPriceByEpoch[1] mandated a haircut
    assertApproxEqAbs(got, req1 + req2, 2); // should have been req1*price/1e18 + req2
}
```

Key assertions demonstrating the bug: `lossRecoveryPriceByEpoch[1] < RECOVERY_FULL` is never consumed (it stays non-zero after the claim), `lastWithdrawRequest` was overwritten to 2, and the funded claim pays `withdrawsRequests[user]` which still contains the epoch-1 basis.   function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
