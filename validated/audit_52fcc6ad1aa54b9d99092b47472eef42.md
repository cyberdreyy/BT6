Found a direct structural analog to the report's root cause: a signature-verification routine that omits fields it is supposed to bind, letting content be re-attributed under a "valid" signature.

### Title
`BlockRejection`'s signed digest omits `reason_code`/`response_data`, making one signature valid for any rejection reason - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()`, which is the exact digest used by `sign()`, `verify()`, and `recover_public_key()`, commits only to `signer_signature_hash` and `chain_id`. It never includes `reason`, `reason_code`, or `response_data` (which carries `reject_reason`, `failed_txid`, `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`). This is the same bug class as the report: a proof/signature check that leaves out fields that must be bound for the check to mean what callers assume it means.

### Finding Description
`BlockRejection::hash()` builds the signed digest from only `signer_signature_hash`: [1](#0-0) 

`sign()`, `verify()`, and `recover_public_key()` all operate over this same narrow digest: [2](#0-1) 

But `BlockRejection` carries several other consequential fields that are never covered by the signature: [3](#0-2) 

Because Stacks/secp256k1 signing is deterministic (RFC6979-style), a signer's signature for a given `(signer_signature_hash, chain_id)` pair is *always the same bytes*, no matter what `reason_code`/`response_data` accompanies it. Consequently the signature does not authenticate "signer X rejected block H for reason R"; it only authenticates "signer X produced *some* signature over H". Anyone holding one broadcast `(H, S)` pair - which is public, since `BlockRejection`s are gossiped over the `.signers` StackerDB contract - can attach a different `reason_code`/`response_data` to that same `H`/`S` and it will still pass `verify()`/`recover_public_key()`.

This matters because production code trusts those unauthenticated fields for consequential accounting. The miner-side `StackerDBListener` uses `reason_code` and `response_data.failed_txid` to accumulate per-txid "problematic transaction" weight, and separately extracts `tenure_extend_timestamp`/`read_count_extend_timestamp` to drive idle/read-count timers: [4](#0-3) [5](#0-4) 

Signer-side, `handle_block_rejection` also authenticates solely via `rejection.recover_public_key()` before trusting `response_data.reject_reason` for weight tallying and reorg decisions: [6](#0-5) 

For comparison, `BlockAccepted`'s signature is a plain signature over the raw `signer_signature_hash` bytes with no domain wrapper at all - the two response types don't even share the same signing convention, underscoring that the `BlockRejection` scheme was deliberately built to look like a Clarity structured-data (on-chain-style) attestation, yet fails to bind the very content (`reason_code`, `failed_txid`, extend timestamps) that a structured-data attestation is normally meant to authenticate: [7](#0-6) 

### Impact Explanation
This breaks the intended non-malleability of the `BlockRejection` attestation: a signature that is supposed to prove "signer X rejected block H *for reason R*" instead only proves "signer X produced a signature over H", and is deterministically identical no matter what `R` is attached. Anywhere the code treats `rejection.verify()` / `rejection.recover_public_key()` succeeding as proof of the accompanying `reason_code`/`response_data` (per-txid blame tallying in `stackerdb_listener.rs`, `reject_reason`-driven reorg/weight logic in `signer.rs`), that trust is misplaced: the cryptographic check does not actually cover those fields. This is a "cross-context-valid signature" in the sense the analog rules describe - the same signature validates across multiple different claimed rejection reasons/response payloads that the signer never jointly authorized.

The practical blast radius is bounded by the fact that writing a forged chunk into a signer's own StackerDB slot still requires that signer's private key at the transport (`SlotMetadata`) layer, so an outside party cannot impersonate another signer's slot. The exposure is that the signer's *own* attestation of "why" is repudiable/reframable after the fact (any prior `(H, S)` they published can be paired with a different `reason_code`/`response_data` and still verifies), and any code path that consumes `BlockRejection` content independent of a fresh, full StackerDB chunk-level signature check inherits this weakness.

### Likelihood Explanation
The root cause is unconditionally present and trivially demonstrable: two `BlockRejection`s for the same `signer_signature_hash` with different `reason_code`/`response_data`, both signed by the same key, are deterministically byte-identical in their `signature` field, and both pass `verify()`/`recover_public_key()`. No majority, no other signer's key, and no consensus assumption is needed to observe or reproduce this - only the ability to construct/relay a `BlockRejection` struct, which any single signer (over their own slot) can already do.

### Recommendation
Include `reason_code` (or the full `response_data`) inside the domain-signed message in `BlockRejection::hash()`, mirroring how `PerAddressTrancheVestingMerkle` was fixed by adding the omitted `tranches` field to the Merkle-proof preimage. Concretely, extend the `Value` passed into `structured_data_message_hash` to cover `reason_code` and the fields of `response_data` that downstream logic treats as authenticated, so that a valid signature is bound to the full claim, not just the block hash.

### Proof of Concept
1. Signer X calls `BlockRejection::new(H, RejectReason::ValidationFailed(BadTransaction), sk_X, ...)` → gets `BlockRejection{reason_code: ValidationFailed(BadTransaction), signature: S, ...}` per [8](#0-7) ; this is broadcast on `.signers` StackerDB and observed by every node/miner.
2. Anyone (or signer X later) constructs `BlockRejection{signer_signature_hash: H, chain_id: same, reason_code: ValidationFailed(ProblematicTransaction), response_data: {failed_txid: Some(arbitrary_txid), ...}, signature: S}` - same `S`, different `reason_code`/`response_data`.
3. `rejection.hash()` is unchanged (depends only on `H`/`chain_id`), so `rejection.verify(pubkey_X)` and `rejection.recover_public_key()` both succeed exactly as before, per [2](#0-1) .
4. If this forged object reaches `StackerDBListener`'s rejection handler (assuming it can be delivered into the slot, e.g. by the owning signer itself, or via any path that doesn't re-derive the full chunk signature), the code at [9](#0-8)  accepts the new `reason_code`/`failed_txid` as authenticated and tallies `problematic_weight` against `arbitrary_txid`, even though signer X's actual cryptographic commitment never covered that claim.

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }

    /// Handle an observed rejection from another signer
    fn handle_block_rejection(
        &mut self,
        rejection: &BlockRejection,
        sortition_state: &mut Option<SortitionsView>,
    ) {
        debug!("{self}: Received a block-reject signature: {rejection:?}");

        let block_hash = &rejection.signer_signature_hash;
        let signature = &rejection.signature;

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {
            debug!("{self}: Received block rejection with an unrecovarable signature. Will not store.";
               "signer_signature_hash" => %block_hash,
               "signature" => %signature
            );
            return;
        };

        // authenticate the signature -- it must be signed by one of the stacking set
        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }

        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {
            if let Err(e) = self.signer_db.add_pending_block_rejection_response(
                block_hash,
                &signer_address,
                (&rejection.response_data.reject_reason).into(),
            ) {
                warn!("{self}: Failed to add pending block rejection response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block rejection";
            "signer_pubkey" => public_key.to_hex(),
            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "reject_reason" => ?rejection.response_data.reject_reason,
        );

        self.store_and_process_block_rejection(
            sortition_state,
            &mut block_info,
            &signer_address,
            (&rejection.response_data.reject_reason).into(),
        );
