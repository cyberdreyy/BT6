### Title
Web API Trigger allows re-registration with stale `allowedSenders`/`allowedTopics` due to non-atomic Unregister/Register from unprivileged gateway messages - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
The `removeContract` bug class describes a function that "disables" an entity but fails to clear the associated permission/policy data structures, allowing the entity to later be re-enabled with stale, unintended policies. The `triggerConnectorHandler` in `core/capabilities/webapi/trigger/trigger.go` has an analogous issue: `RegisterTrigger`/`UnregisterTrigger` mutate a shared `registeredWorkflows` map keyed only by `TriggerID`, and each entry embeds its own `allowedSenders`/`allowedTopics` policy. Because `UnregisterTrigger` only performs `delete(h.registeredWorkflows, req.TriggerID)` without any coordination/versioning tied to the workflow's current on-chain/registry-authorized configuration, and registration is driven by external gateway messages, a new `RegisterTrigger` call for the same `TriggerID` fully replaces the map entry's allow-list with attacker-influenced/stale config since there is no validation that the new registration's `allowedSenders` matches the workflow's actual authorized senders.

### Finding Description
`RegisterTrigger` stores a `webapiTrigger{allowedSenders, allowedTopics, ...}` struct in `h.registeredWorkflows[req.TriggerID]` without verifying that `req.Config.AllowedSenders` reflect the legitimately authorized senders for that specific `WorkflowID`/`TriggerID` combination — it only checks the map key `TriggerID` is not already registered: [1](#0-0) 

`UnregisterTrigger` merely deletes the map entry and closes the channel — it does not clear or invalidate any residual per-workflow policy state that could allow a subsequent registration under the same `TriggerID` to be trusted without fresh validation of the caller's authorization to set `allowedSenders`: [2](#0-1) 

The actual sender authorization check performed at trigger-execution time relies entirely on this in-memory `allowedSenders` map populated at registration time, with no secondary authoritative source (e.g., workflow registry / capabilities registry) cross-check: [3](#0-2) 

### Impact Explanation
If registration is not strictly bound to the authoritative source of truth for which senders/topics a given `WorkflowID` is entitled to use, an attacker who can trigger a new `RegisterTrigger` call (e.g., by controlling workflow config content that is not independently validated) could overwrite the trust boundary for a given trigger ID without a corresponding cleanup/audit trail — mirroring the "stale policy after disable" root cause in the report, since removal (`UnregisterTrigger`) does not invalidate any policy state tied to `WorkflowID`, only the map entry keyed by `TriggerID`.

### Likelihood Explanation
This requires that `RegisterTrigger`/`UnregisterTrigger` be reachable with attacker-influenced `Config` from a workflow spec, which is plausible in the CRE/workflow-engine architecture where workflow authors supply their own trigger configuration. However I could not fully confirm from the available code that an unprivileged network caller (as opposed to only the local workflow engine) can invoke `RegisterTrigger` directly, and the actual sender allowlist is workflow-author-supplied by design (a workflow declares who may trigger it) rather than being an app-enforced privilege boundary set by a separate administrator.

### Recommendation
Ensure `UnregisterTrigger` fully purges all per-`TriggerID`/`WorkflowID` policy state, and ensure `RegisterTrigger` re-validates `allowedSenders`/`allowedTopics` against the authoritative workflow configuration/registry each time a trigger is (re-)registered, rather than trusting the caller-supplied `Config` at face value on every registration.

### Proof of Concept
Not constructed — I could not confirm from the indexed code alone that an unprivileged/external actor can directly invoke `RegisterTrigger` with attacker-controlled `AllowedSenders`, which is required to demonstrate concrete exploitability of this analog beyond the structural code-pattern similarity.

func (h *triggerConnectorHandler) UnregisterTrigger(ctx context.Context, req capabilities.TriggerRegistrationRequest) error {
	h.mu.Lock()
	defer h.mu.Unlock()
	workflow, ok := h.registeredWorkflows[req.TriggerID]
	if !ok {
		return fmt.Errorf("triggerId %s not registered", req.TriggerID)
	}

	close(workflow.ch)
	delete(h.registeredWorkflows, req.TriggerID)
	return nil
}
