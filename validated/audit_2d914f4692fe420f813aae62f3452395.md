### Title
Cross-user response confusion via MessageId collision in web API trigger callbacks - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each user's `handlers.Callback` in `h.savedCallbacks` keyed solely by the attacker/user-supplied `msg.Body.MessageId`, with no binding to sender address, signature, or tenant. `handleWebAPITriggerMessage` later looks up and delivers a node's response to whichever callback is currently stored under that MessageId, so a second registration with the same MessageId silently overwrites the first and receives the first requester's response.

### Finding Description
`HandleLegacyUserMessage` unconditionally does a plain map assignment with no existence check: [1](#0-0) 
The `msg.Body.MessageId` used as the key comes directly from the user-controlled request. For legacy requests the message body (including `MessageId`) is parsed straight from the caller-supplied JSON before signature-derived `Sender` is even filled in, and for JSON-RPC-style legacy wrapping the ID is copied verbatim from the client-supplied `req.ID`: [2](#0-1) 
`Message.Validate()` only checks length/format of `MessageId` and derives `Sender` from the signature for authentication of the *message contents*, but this signer/sender is never incorporated into the `savedCallbacks` map key: [3](#0-2) 
When a node response arrives, `handleWebAPITriggerMessage` looks up and deletes by `MessageId` only, and delivers the first response to whatever callback is currently registered for that ID: [4](#0-3) 

Exploit flow: victim A submits a `web_api_trigger` request signed with A's key using `MessageId = X` (chosen by A, or default from some external system with low entropy/predictable IDs), causing `savedCallbacks[X] = A's callback`. Before the DON nodes respond, attacker B submits their own `web_api_trigger` request also using `MessageId = X` (an attacker can freely choose their own MessageId; only the signature over the body needs to be valid for their own key). This overwrites `savedCallbacks[X]` with B's callback. When the DON node's first response for `X` (destined for A's original trigger) arrives at `handleWebAPITriggerMessage`, it is delivered to whichever callback occupies the map slot — now B's — because there is no sender binding in the lookup key. B thus receives A's node response, and A's original request will simply time out at `callback.Wait(ctx)` in `gateway.ProcessRequest`, since its callback object is orphaned from the map. Nothing in the message validation, signature check, or DON allowlist prevents this because those checks only validate that a message body+signature pair is internally consistent — none of them bind a per-request MessageId's usage exclusively to its original signer.

### Impact Explanation
This is a cross-user response confusion vulnerability: an unprivileged external client (any signed gateway request submitter) can hijack the trigger response intended for another user simply by colliding on `MessageId`. Since the response payload for `web_api_trigger` may contain outputs derived from the node's WebAPI trigger handling (delivered to whichever HTTP client is currently attached to that ID), this results in a legitimate user's response being disclosed to a different unauthorized entity — an information-disclosure / improper request-isolation issue, matching Chainlink's "unauthorized action on another user's job/response" bounty impact class. Note that the amount of "action" or sensitive data disclosed depends on what the WebAPI trigger response contains in that flow; at minimum the availability of A's request is also broken (A never gets a response, its request silently times out).

### Likelihood Explanation
Exploitability requires only: (1) the attacker's ability to submit their own signed gateway request with an attacker-chosen `MessageId` — trivially available to any client, since `MessageId` is fully user-supplied; and (2) a MessageId collision with an in-flight victim request. If victim MessageIds are unpredictable UUIDs, this is a low-probability blind race; but if any calling system uses predictable, short, or attacker-influenced/observable MessageIds (e.g., sequence numbers, workflow execution IDs, or IDs echoed back to the attacker through another channel), the attacker can deterministically target and win the race, since the collision window lasts the entire trigger round-trip to the DON (potentially the `CallbackMaxAgeSec` window, default 120s), which is a large window for a race in practice.

### Recommendation
Bind `savedCallbacks` entries and lookups to the message sender in addition to MessageId — e.g., use a composite key such as `sender + ":" + MessageId`, or store the expected sender address alongside the callback and verify it matches the sender recovered from the node's forwarded/original request before delivering the response. Additionally, reject (rather than silently overwrite) registration of a `MessageId` that is already active in `savedCallbacks`, returning an explicit "duplicate/conflict" error to the second caller instead of clobbering the first callback's entry.

### Proof of Concept
Go unit test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler with a stub `handlers.DON` that just records `SendToNode` calls (no actual network).
2. Create two fake `handlers.Callback` objects/mocks, `callbackA` and `callbackB`, each able to record the `UserCallbackPayload` passed to `SendResponse`.
3. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` where `msgA.Body.MessageId = "X"`, signed by key A.
4. Call `h.HandleLegacyUserMessage(ctx, msgB, callbackB)` where `msgB.Body.MessageId = "X"` (same ID), signed by key B — assert (expected fix) that this call fails/returns a conflict error instead of overwriting; in the current code assert it succeeds and overwrites (`h.savedCallbacks["X"].Callback == callbackB`), proving the vulnerability.
5. Construct a node response message with `MessageId = "X"` corresponding to A's original trigger content, call `h.handleWebAPITriggerMessage(ctx, nodeRespMsg, nodeAddr)`.
6. Assert (vulnerable behavior) `callbackB.SendResponse` was invoked with A's response payload, and `callbackA.SendResponse` was never invoked — demonstrating cross-user delivery.
7. After applying the recommended fix (composite key / duplicate rejection), re-run the same test and assert either step 4 is rejected, or `callbackA` (not `callbackB`) correctly receives the response for its own MessageId.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
