### Title
APR0 withdraw requests permanently revert `stopEpoch` once the epoch APR changes — stale read of `unscaledApr` across epochs - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a read of `sysctl_fib_multipath_use_neigh` that races with concurrent writes — a value sampled once is assumed stable while another actor can change it. The closest analog in the credit vault is `unscaledApr`: `requestWithdraw` samples it once to decide whether a receipt enters the APR0 bucket, while `prepareStopEpochWithApr0` samples it again one epoch later and reverts if it has since become non-zero. A lender can therefore plant an APR0 receipt, wait for a normal epoch rollover that changes the APR, and every subsequent `stopEpoch`/`stopEpochWithDuration` reverts, freezing all vault funds.

### Finding Description
`requestWithdraw` reads `unscaledApr == 0` at request time and, if true, records the principal in `apr0Users[_user]` and increments `apr0TotalPrincipal` via `_requestWithdrawApr0`. [1](#0-0) [2](#0-1) 

The value is read again at stop time in `prepareStopEpochWithApr0`, which assumes the read is still valid: if `apr0TotalPrincipal != 0` while `unscaledApr != 0`, it reverts with `NotAllowed()`. [3](#0-2) 

Crucially, the only line that resets `apr0TotalPrincipal` (line 540) sits *after* the revert, so the bucket can never be closed once the APR is non-zero — the revert is permanent for any non-zero APR. `unscaledApr` is changed between epochs by the honest CDO/manager through `setAprsWithBuffer`/`setAprs` during `startEpoch`. [4](#0-3) [5](#0-4) 

### Impact Explanation
Any KYC-passing lender can, during an APR0 epoch, call `requestWithdraw` (even for a small principal). When the honest manager/CDO starts the next epoch with a positive APR (`setAprsWithBuffer`), `prepareStopEpochWithApr0` reverts on every `stopEpoch` call: borrower repayments, LP principal and yield are all frozen inside the vault. The freeze repeats indefinitely — if the manager resets APR to 0 to unbrick, the attacker files another APR0 receipt and the next non-zero epoch bricks again. This is permanent/temporary freezing of all LP and borrower funds, an accepted impact class.

### Likelihood Explanation
The attacker only needs one `requestWithdraw` during any APR0 epoch (APR0 mode is a supported configuration). The APR change itself is performed by honest privileged roles as part of normal epoch rollover, so no malicious privileged behavior is required. No existing guard helps: the `unscaledApr != 0` check is exactly the stale-value read, and `apr0TotalPrincipal` cannot be cleared because the revert precedes its reset.

### Recommendation
Do not require `unscaledApr` to be unchanged across the request/settle lifecycle. Either (a) snapshot the APR-per-epoch at request time (e.g., `apr0RateByEpoch`-style per-epoch flag) and settle APR0 buckets based on the epoch they were created in, skipping rather than reverting when the current APR is non-zero; or (b) move the `apr0TotalPrincipal = 0` reset before the revert so a single stale bucket cannot permanently brick `stopEpoch`, and settle orphaned APR0 principal at par without interest.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Precondition: vault in APR0 mode (unscaledApr == 0), epoch running or buffer.
// 1. Attacker (KYC lender) deposits AA and requests a withdraw:
idleCDO.requestWithdraw(amountAA); // routes into apr0Users, apr0TotalPrincipal > 0

// 2. Honest manager/CDO rolls the epoch and sets a positive APR:
vm.prank(manager);
strategy.setAprsWithBuffer(10e18, 30 days, 7 days); // unscaledApr = 10e18, scaled lastApr

// 3. Borrower repays; manager stops the epoch:
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
idleCDO.stopEpoch(); // -> prepareStopEpochWithApr0 reverts: unscaledApr != 0 && apr0TotalPrincipal != 0

// 4. Every retry reverts; apr0TotalPrincipal can never reach its reset at line 540.
// Assert: underlying remains locked in IdleCreditVault / borrower; LP claims impossible.
```
