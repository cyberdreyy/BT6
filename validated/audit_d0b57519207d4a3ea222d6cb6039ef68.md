## Analysis

The Sherlock bug class is: two logically-equivalent checks meant to answer the same underlying question about "which state has this account/tenure already committed to" use *different, inconsistent* representations of that state — one lags behind reality — letting a normal operation slip past a guard it should have hit, breaking a one-per-slot equality/invariant.

The exact analog exists in the signer's tenure-change duplicate-block guard: v1's `validate_tenure_change_payload` still checks for a prior signed block in the tenure using `get_last_globally_accepted_block` (only counts blocks that reached the 70% *global* threshold), while v2's version of the same check was patched — with an explicit regression test — to use `get_last_signed_block` (locally OR globally accepted, i.e., anything this signer has actually put a signature over). [1](#0-0) 

versus the fixed v2 code and its regression test: [2](#0-1) [3](#0-2) 

`get_last_signed_block` and `get_last_globally_accepted_block`/`get_last_accepted_block` are deliberately distinct queries in `signerdb.rs`, with explicit doc-comments warning that using the wrong one for a validation decision is unsafe: [4](#0-3) 

### Title
V1 chainstate's tenure-change duplicate check uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, letting a v1 signer accept a conflicting second tenure-start block it already signed - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`SortitionState::validate_tenure_change_payload` in the v1 chainstate path rejects a tenure-change proposal with `DuplicateBlockFound` only if a block in the same tenure is already **globally accepted** (`signer_db.get_last_globally_accepted_block`). It ignores blocks the signer has itself **locally accepted** (signed with its own key) but which have not yet crossed the 70% global threshold. The v2 chainstate path had exactly this defect and was fixed to use `get_last_signed_block` (locally OR globally accepted), backed by a regression test explicitly describing the old, buggy behavior. V1 never received the equivalent fix.

### Finding Description
`validate_tenure_change_payload` (v1) is the sole gate, run only once at proposal time, that is supposed to stop a signer from processing a second, competing tenure-start block for a tenure it has already committed a signature to: [5](#0-4) 

It queries `get_last_globally_accepted_block`, which by construction only returns blocks with `state == GloballyAccepted`: [6](#0-5) 

A block the signer has `mark_locally_accepted`'d — meaning **it already put its own signature over it** — sits in `BlockState::LocallyAccepted` until the network-wide 70% threshold is separately observed. `get_last_globally_accepted_block` misses that block entirely, so v1's duplicate check sees "no accepted block yet in this tenure" and lets a second, competing tenure-start proposal for the same tenure proceed past the one check purpose-built to catch this. v2 fixed this precise defect by switching to `get_last_signed_block`, which correctly includes `LocallyAccepted` (and `GloballyAccepted`) states: [7](#0-6) 

and the fix is validated by a dedicated regression test whose comment states the exact bug: *"previously, the check used `get_last_globally_accepted_block`, which would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change."* [3](#0-2) 

Per the documented flow, this duplicate check runs **only** at proposal time and is never re-run at validate-ok or at signing: [8](#0-7) 

so a v1 signer that incorrectly clears this gate has no second purpose-built defense against re-signing a conflicting tenure-start block for the same tenure; it depends entirely on the general same-height conflict guard in `handle_block_pre_commit`, which is explicitly designed to eventually permit signing a replacement once the earlier signed block's endorsement goes stale (`freshness_cutoff` / `reorg_attempts_activity_timeout`) — i.e., the fallback is designed to let old signatures stop blocking, not to preserve the "one signed tenure-start block per tenure" property that the proposal-time check exists to enforce. [9](#0-8) 

### Impact Explanation
This breaks the "one signed block per tenure-start position" equality that the duplicate-block guard exists to enforce, on the v1 code path — a signer can accept, validate, and eventually sign a second, conflicting tenure-start block for a tenure it already signed a first tenure-start block for, before that first block reaches global acceptance. Two conflicting signed blocks for the same tenure/height is exactly the "signer signing a conflicting block" category called Critical in scope.

### Likelihood Explanation
Triggerable by a single miner controlling one sortition slot: propose a tenure-start block, wait for it to be locally (but not yet globally) accepted, then re-propose a second, distinct tenure-start block for the same tenure (e.g., different transaction set) before the first reaches the 70% global threshold. No majority of signers, no other signer's key, and no StackerDB/transport exploit is required — only the ordinary proposal flow through a v1-configured signer.

### Recommendation
Change `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to query `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, mirroring the fix already applied in `chainstate/v2.rs`, and add a v1 regression test analogous to `check_tenure_change_rejects_when_locally_accepted_block_exists`.

### Proof of Concept
1. Miner proposes tenure-start block `A` for tenure `T`; signer (running v1 protocol) validates and locally accepts it (`mark_locally_accepted`), i.e., signs it, but the network has not yet reached the 70% global threshold.
2. Miner proposes a second, distinct tenure-start block `B` for the same tenure `T` (different tx set), before `A` becomes globally accepted.
3. v1's `validate_tenure_change_payload` calls `get_last_globally_accepted_block(&T)`, which returns `None` because `A` is only `LocallyAccepted`, so the `DuplicateBlockFound` check is skipped and `B`'s proposal passes.
4. `B` proceeds to node validation and eventually to the section-5 pre-commit conflict logic in `signer.rs`, where it may still be signed if `A`'s endorsement has gone "stale" per `reorg_attempts_activity_timeout`/freshness rules — producing two signer signatures over conflicting tenure-start blocks for tenure `T`.

    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(

                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),

        }
    }

        if !self.check_state(state) {
            return Err(format!(
                "Invalid state transition from {} to {state}",
                self.state

        }
        self.state = state;
        Ok(())
    }
