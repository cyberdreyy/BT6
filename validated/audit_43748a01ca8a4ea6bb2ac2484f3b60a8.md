## Analysis Result

### Title
V1 tenure-change duplicate-block check uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, letting a signer pre-commit to a conflicting sibling tenure-start block before the `handle_block_pre_commit` conflict guard catches it - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
This maps to the Grav bug class of "one code path patched, an equivalent alternate path left with the old, weaker check." Grav patched `filter()` but left `map()`/`reduce()` invoking the same unsafe primitive. In this repo, the v2 tenure-change duplicate check was fixed (regression test confirms) to use `get_last_signed_block` (covers `LocallyAccepted`/`PreCommitted`/`GloballyAccepted`), but the v1 implementation — still reachable whenever the negotiated `active_signer_protocol_version < GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` (2) — still uses the older, narrower `get_last_globally_accepted_block`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`SortitionsView::validate_tenure_change_payload` in `v1.rs` rejects a second tenure-start block for the same tenure with `RejectReason::DuplicateBlockFound` only if `signer_db.get_last_globally_accepted_block(...)` returns `Some`: [1](#0-0) 

The v2 equivalent, `validate_tenure_change_payload` in `v2.rs`, was fixed to query `get_last_signed_block` instead, precisely because `get_last_globally_accepted_block` "would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change" — this is stated verbatim in the v2 regression test: [3](#0-2) [4](#0-3) 

`docs/signer-flows.md` explicitly documents this divergence as a known asymmetry between v1 and v2, treating it as accepted behavior rather than a defect: [5](#0-4) 

v1 is not a dead code path: `SortitionStateVersion::from_protocol_version` selects V1 whenever the negotiated `active_signer_protocol_version` is below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` (currently 2), and v0/signer.rs's `check_block_against_local_state` (the pre-global-state-activation path) is what invokes `crate::chainstate::v1::SortitionsView::check_proposal`: [6](#0-5) [7](#0-6) 

Test infrastructure confirms the network can legitimately run — even transiently, during rollouts/downgrades — at protocol versions 0/1 (i.e., v1 semantics) for a subset or all signers: [8](#0-7) [9](#0-8) 

Since `get_last_globally_accepted_block` only returns blocks that have already reached `GloballyAccepted` state (i.e., `signed_group` threshold observed), a block that is merely `LocallyAccepted` (this signer's own `signed_self` set, but `signed_group` not yet observed) is invisible to the v1 duplicate check. There is a real, non-adversarial window between a signer self-signing tenure-start block A (crossing the local 70% pre-commit weight threshold in `handle_block_pre_commit`) and A being recognized network-wide as `GloballyAccepted`. A miner can, during that window, submit a second tenure-start block B for the same tenure; a v1-mode signer's `check_proposal` → `validate_tenure_change_payload` will not see A via `get_last_globally_accepted_block` and will not reject B with `DuplicateBlockFound`.

### Impact Explanation
This is the same equality-breaking bug class called out in the rules ("a signer signing an invalid/non-canonical/conflicting block"). If the proposal-time gap in v1 lets B proceed to node validation and pre-commit tallying, the last line of defense is the separate, unrelated conflict guard in `handle_block_pre_commit` (`get_signed_conflicts`), which is invoked at pre-commit-threshold time, not at proposal time: [10](#0-9) 

I was not able to fully verify, within the remaining budget, whether `get_signed_conflicts` in `signerdb.rs` also includes `LocallyAccepted` (self-signed, not-yet-globally-accepted) blocks as "signed" conflicts for the *same* signer evaluating B — if it does, this backstop closes the gap and the impact is limited to a wasted/duplicate pre-commit round rather than an actual double signature. If it does not (e.g., if it only tracks blocks this signer has locally recorded as conflicting via a different code path, or if the freshness/`conflict_still_blocks` logic lets a stale-but-real conflict through in a race), a v1-mode signer could end up signing two conflicting tenure-start blocks for the same tenure, which is a Critical-severity equality break (conflicting signed blocks at the same height in the same tenure). Given the uncertainty over the interaction with `get_signed_conflicts`, I present this at High rather than confirmed Critical, pending review of `signerdb.rs`'s `get_signed_conflicts` definition.

### Likelihood Explanation
No majority collusion or malicious signer is required — a single miner (one block-production slot) racing a second tenure-start proposal against normal signer gossip is sufficient to open the window; the window is a designed part of the state machine (self-sign vs. group-observed) rather than a contrived edge case. The precondition is simply that the negotiated protocol version places affected signers on the v1 code path, which is an officially supported, tested configuration in this codebase (protocol negotiation/downgrade tests exist).

### Recommendation
Update `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to query `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, matching the fix already applied to v2, so that `LocallyAccepted`/`PreCommitted` blocks in the current tenure are also treated as duplicates. Additionally, verify (and if needed extend) `get_signed_conflicts` to ensure it independently catches this case regardless of protocol version, so the proposal-time check and the pre-commit-time backstop are consistent across v1 and v2.

### Proof of Concept
1. Configure a signer set (or a subset, e.g. via `restart_first_n_signers_with_supported_version`) to negotiate `active_signer_protocol_version < 2`, forcing v1 chainstate logic, as shown in `downgrade_signer_protocol_version`/`multiversioned_signer_protocol_version_calculation`.
2. Miner proposes tenure-start block A for tenure T (`TenureChangeCause::BlockFound` + coinbase). All v1 signers pass `check_proposal` (no prior block in T), the node validates OK, pre-commit round reaches 70%, and each signer calls `mark_locally_accepted` in `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs:1467`).
3. Before this signer observes enough peer `Accepted` messages to promote A to `GloballyAccepted` in its own `signer_db`, the miner submits a differing tenure-start block B for the same tenure T (same `consensus_hash`, different transactions/timestamp).
4. The v1 signer's `check_proposal` → `validate_tenure_change_payload` calls `get_last_globally_accepted_block(&B.header.consensus_hash)`, which returns `None` because A is only `LocallyAccepted` — the `DuplicateBlockFound` rejection at `v1.rs:505-518` does not fire, unlike what the fixed v2 path (and its regression test `check_tenure_change_rejects_when_locally_accepted_block_exists`) would do.
5. B proceeds toward validation/pre-commit; whether it culminates in an actual double signature depends on whether `get_signed_conflicts` (consulted later in `handle_block_pre_commit`) independently flags A as a conflict — this final step needs to be confirmed by inspecting `signerdb.rs`.

    /// Version 2: Global Signer State evaluation
    V2,

impl SortitionStateVersion {
    /// Convert the protocol version to a sortition state version
    pub fn from_protocol_version(version: u64) -> Self {
        if version < GLOBAL_SIGNER_STATE_ACTIVATION_VERSION {
            Self::V1
        } else {
            Self::V2
        }
    }
