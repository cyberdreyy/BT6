### Title
Front-run `requestWithdraw` dust inflates `pendingWithdraws` and forces a spurious borrower default at `stopEpoch` - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`stopEpoch` pulls `expectedInterest + pendingWithdraws` from the borrower via `transferFrom` inside `getFundsFromBorrower`, and any failure of that single pull is caught and routed to `_handleBorrowerDefault`. Because `requestWithdraw` is permissionless for any KYC'd tranche holder during the buffer period and increases `IdleCreditVault.pendingWithdraws` by an arbitrary amount, an attacker can front-run the manager's `stopEpoch` call with a dust (or full-balance) withdraw request. The borrower — who approved/held exactly the pre-computed repayment — then under-funds the pull by as little as 1 wei, the `transferFrom` fails, and the pool is pushed into `defaulted` state even though the borrower was fully willing and able to repay.

### Finding Description
Relevant flow:

- `IdleCDOEpochVariant._stopEpoch` (contracts/IdleCDOEpochVariant.sol:330-505) computes `_pendingWithdraws = _strategy.pendingWithdraws()` at line 364, then calls `try this.getFundsFromBorrower(_amountToPullFromBorrower + _pendingWithdraws)` at line 408. The `catch` at line 501-504 calls `_handleBorrowerDefault(_amountToPullFromBorrower + _pendingWithdraws)`.
- `IdleCreditVault.requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:243-295) adds `_amount` to `pendingWithdraws` at line 279 and records `lastWithdrawRequest[_user] = currentEpoch`.
- `IdleCDOEpochVariant.requestWithdraw` (contracts/IdleCDOEpochVariant.sol:739-791) only requires `allowAAWithdrawRequest`/`allowBBWithdrawRequest` (set `true` in the buffer at lines 481-482) and `isWalletAllowed(msg.sender)` (KYC). There is no epoch-stop cutoff: requests remain open during the entire buffer, including the same block in which the manager calls `stopEpoch`.

Attack sequence (buffer phase, fixed-APR mode):

1. Pool is in buffer; borrower has approved exactly `expectedInterest + pendingWithdraws_before` (the honest pre-computed amount — tests such as `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol:487-503` show repayment funded with exactly `interest + pendingWithdraw`).
2. Manager broadcasts `stopEpoch(newApr, 0)`.
3. Attacker (KYC'd tranche holder) front-runs it with `cdoEpoch.requestWithdraw(dust, AATranche)`. This burns a dust amount of strategy-token principal and increments `pendingWithdraws` by `dust`.
4. `stopEpoch` now computes `_pendingWithdraws = pendingWithdraws_before + dust` and tries to pull `expected + pendingWithdraws_before + dust` from the borrower. The borrower's allowance/balance covers only `expected + pendingWithdraws_before`, so `transferFrom` reverts.
5. The `catch` invokes `_handleBorrowerDefault`, setting `defaulted = true` and freezing the normal epoch/claim flow for all LPs.

The invariant broken is fair settlement: a genuine solvent borrower is recorded as defaulted purely because a permissionless accounting write moved the required pull between the borrower's funding and the manager's stop call.

### Impact Explanation
All LP funds are forced into the default path: `isEpochRunning` is cleared and `defaulted` set, so `claimWithdrawRequest`/`claimInstantWithdrawRequest` switch to default-recovery semantics and active tranche holders must wait for `finalizeDefault`/`DefaultDistributor` recovery flows instead of normal epoch settlement. This is temporary freezing of the entire pool TVL plus forced loss-socialization accounting (pending receipts and active NAV get haircut bookkeeping via `defaultPendingClaimBasis`/`postDefaultRequests` machinery), all triggered by an unprivileged dust transaction. Quantified: 100% of pool NAV is locked out of the normal claim path for the duration of default finalization, and any shortfall in `defaultRecovery` bookkeeping is socialized across tranche holders.

### Likelihood Explanation
Medium-high. The attacker only needs a KYC'd wallet and a nonzero tranche balance; a dust request costs a few wei of principal plus gas. Every epoch boundary exposes the same mempool race, and borrowers that fund repayment exactly (the documented/tested pattern) have no slack. The same griefing applies to `stopEpochWithDuration`. It is partially mitigated only if the real borrower always maintains approval/balance headroom greater than the maximum tranche supply an attacker could request — but nothing in the contracts enforces that, and an attacker holding a large tranche position can raise `pendingWithdraws` beyond the borrower's available cash legitimately owed anyway.

### Recommendation
Decouple withdrawal-request intake from the stop transaction, e.g.:

- Close `allowAAWithdrawRequest`/`allowBBWithdrawRequest` at `epochEndDate` (or at `epochEndDate - instantWithdrawDelay`), so `pendingWithdraws` is frozen before `stopEpoch` can run; or
- Snapshot `pendingWithdraws` when the buffer begins and have `stopEpoch` fund only requests recorded up to that snapshot (later requests roll into the next epoch); or
- On pull failure, retry the transfer with the funded remainder rather than defaulting — i.e., treat `transferFrom` shortfall as partial funding via `collectWithdrawFunds(_amountReceived)` loss-adjusted path instead of unconditional `_handleBorrowerDefault`.

### Proof of Concept
Foundry fork PoC (against the existing `IdleCreditVault` harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testFrontrunRequestWithdrawForcesDefault() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);
    idleCDO.depositBB(amount);
    _startEpochAndCheckPrices(0);

    // attacker: KYC'd tranche holder with a position
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, amount, false);
    uint256 attackerTranches = IERC20(AAtranche).balanceOf(attacker);

    // epoch ends; buffer begins; borrower funds exactly what stopEpoch needs
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 expected = cdoEpoch.expectedEpochInterest()
        + IdleCreditVault(address(strategy)).pendingWithdraws();
    deal(defaultUnderlying, borrower, expected);
    vm.prank(borrower);
    IERC20(defaultUnderlying).approve(address(cdoEpoch), expected);

    // mempool front-run: dust withdraw request in the same block
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attackerTranches, address(AAtranche));

    // manager's stopEpoch now under-pulls by the attacker's request amount
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialApr, 0);

    // solvent borrower was forced into default; all funds routed to recovery flow
    assertTrue(cdoEpoch.defaulted(), "spurious default from front-run pendingWithdraws");
}
```

Caveat: I could not fully verify within the index whether production borrowers always over-approve (unlimited allowance) — if they do, the same attack still works whenever the attacker's requested `pendingWithdraws` exceeds the borrower's on-hand balance, which any sufficiently large tranche holder can arrange. If borrower excess funding is guaranteed off-chain by convention, the issue degrades to conditional rather than unconditional.
