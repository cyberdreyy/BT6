### Title
Stale role escalation via cached `user_role` in `oidc_sessions` table not revalidated against current user role - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`AuthorizedUserWithSession` authorizes requests solely based on the `user_role` value cached in the `oidc_sessions` row at session-creation time, only checking expiration (`created_at + session_timeout >= now()`), and never re-checks the user's current role against the `users` table or the identity provider. If an admin downgrades a user's role after their session was created, the OIDC session continues to authorize the user with the old, higher-privileged role until the session naturally expires or is explicitly revoked.

### Finding Description
`handleTokenExchange` (lines 233-260) maps ID token claims to a role once, at token exchange time, and inserts that role into `oidc_sessions.user_role`. Similarly, `CreateSession` (lines 412-439, used for local-admin fallback login) caches `foundUser.Role` into the same table. `AuthorizedUserWithSession` (lines 351-391) is the sole per-request authorization function: it runs

```go
"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1"
```

and returns `clsessions.User{Email: foundSession.UserEmail, Role: foundSession.UserRole}` directly from the cached column, with the only validity check being the timestamp comparison, not a check of the row's role against the authoritative role in the `users` table or upstream IdP claims. `reaper.go`'s `sessionReaper.Work`/`deleteStaleSessions` only purges rows whose `created_at` predates a threshold — it does not resynchronize or revoke sessions when a role changes; it is a pure age-based cleanup job, unrelated to role currency.

There is no code path anywhere in `oidcauth` that re-fetches the user's current role from `users` (or re-verifies against the OIDC provider) on each authenticated request. Consequently, a session created while a user held role `Admin`/`Edit`/`Run` continues to carry that role in every subsequent `AuthorizedUserWithSession` call for the full `SessionTimeout()` duration, even if an admin subsequently downgrades the account (e.g., updates the `users.role` column or revokes the corresponding OIDC group membership at the IdP).

### Impact Explanation
This is a stale-privilege / authorization-bypass issue: a user whose access was reduced by an administrator (e.g., from Admin/Edit/Run down to View, or account disabled at the IdP) retains their previous elevated capabilities across the node's HTTP API for as long as `SessionTimeout()` allows (configurable, potentially hours). This maps to the "Authorization is exact" security property violation and Chainlink's role/authorization-bypass impact class — a demoted user could still create/manage jobs, bridges, keys, or other privileged resources reachable via the RBAC middleware that trusts the role returned by `AuthorizedUserWithSession`.

### Likelihood Explanation
Requires only: (1) OIDC (or local fallback) authentication enabled, (2) a user who already has a valid, unexpired `oidc_sessions` row obtained via normal login, and (3) a subsequent admin action that lowers that user's role/claims. No additional privilege is needed by the attacker beyond having authenticated once before the downgrade — this is exactly the "unprivileged user with a prior session" scenario, fully reproducible and deterministic (not timing-dependent beyond `SessionTimeout()`).

### Recommendation
On each `AuthorizedUserWithSession` (and `FindUserByAPIToken`) call, revalidate the cached role against the authoritative source: either re-query the `users` table for local/admin accounts, or trigger/consult a periodic upstream role-resync (shorter than `SessionTimeout()`) that updates or invalidates `oidc_sessions.user_role` when the upstream claims change, and immediately invalidate/downgrade sessions when an admin changes a user's role (e.g., add a `role_updated_at` check or delete affected sessions on role change).

### Proof of Concept
Go integration test in `core/sessions/oidcauth/oidc_test.go`:
1. Insert an `oidc_sessions` row with `user_role = 'admin'` (simulating `handleTokenExchange` at login time), plus a corresponding `users` row with `role = 'admin'`.
2. Call `oi.AuthorizedUserWithSession(ctx, sessionID)`; assert `Role == UserRoleAdmin`.
3. Update the `users` table (or simulate an upstream claim change) to downgrade the role to `view`.
4. Call `oi.AuthorizedUserWithSession(ctx, sessionID)` again with the same `sessionID`; assert that the returned role is still `UserRoleAdmin` (demonstrating the bug) instead of the expected `UserRoleView`.
5. Optionally wait past `config.SessionTimeout()` and confirm the session is purged/expired, showing the only enforced control is time-based expiry, not role currency.
