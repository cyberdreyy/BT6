### Title
`getTokenAccountBalance`/`getParsedTokenAccounts` trust an unvalidated "mint" account owner, allowing spoofed decimals/extension data to be reported - (File: rpc/src/parsed_token_accounts.rs, rpc/src/rpc.rs)

### Summary
The Solidity report shows `borrow()` trusting a caller-supplied pool/NFT contract address without checking it against `controller.accreditedAddresses`, letting an attacker substitute a malicious contract that returns forged values. The closest reachable analog in this repo is `get_mint_owner_and_additional_data` and `get_parsed_token_account`, which fetch the "mint" address embedded in a token account's own data and decode it as an SPL `Mint`, without ever checking that the fetched account is actually owned by the SPL Token/Token-2022 program.

### Finding Description
`get_token_account_mint` extracts the mint pubkey directly from the first 32 bytes of an (already-validated) token account's data [1](#0-0) . That pubkey is then used to fetch "the mint account" from the bank and decode it as a `Mint`/`SplTokenAdditionalDataV2`, but the code never verifies `mint_account.owner()` equals a known SPL Token program id in this path: [2](#0-1) 

and equivalently in `get_parsed_token_account`: [3](#0-2) 

Because a Solana account's data is fully attacker-controlled by whatever program owns it, an attacker can create an arbitrary account under their own program (or even a plain system account) whose byte layout happens to unpack successfully via `StateWithExtensions::<Mint>::unpack`, and set the `mint` field of *their own* real SPL token account (which does pass the `is_known_spl_token_id` owner check) to point at that spoofed account. Note that `rpc/src/rpc.rs`'s `get_token_account_balance` does perform the ownership check on the token *account* but calls the same unchecked `get_mint_owner_and_additional_data` for the mint [4](#0-3) , so the decimals/extension-config data returned for the balance calculation is fully attacker-forged, analogous to `H4ck.sol` forging `getPayoutPerRes`.

### Impact Explanation
This allows an unprivileged RPC caller to force `getTokenAccountBalance`, `getAccountInfo`/`getMultipleAccounts` (jsonParsed) and `getProgramAccounts`/`getTokenAccountsByOwner` (jsonParsed) via `get_parsed_token_accounts` to report a fabricated `decimals` value (and forged `InterestBearingConfig`/`ScaledUiAmountConfig` extension state) for their own account, producing a wrong `uiAmount`/`uiAmountString` in the RPC response — i.e., "wrong-slot/fork/account data returned" for a JSON-RPC query, which matches the accepted impact class. This is purely a display/misreporting issue scoped to the attacker's own crafted accounts; it does not corrupt on-chain consensus state (the raw `amount`/lamports fields returned are still accurate) and there is no evidence of an arithmetic panic since `token_amount_to_ui_amount_v3` uses `checked_pow` for the plain-decimals path.

### Likelihood Explanation
High reachability: any user can create arbitrary accounts and set an SPL token account's `mint` field to any pubkey they like without any on-chain program (they simply need a real token-account-shaped account they control, or can construct one for simulation-only paths via `overwrite_accounts`). No special privilege beyond a normal RPC client is required, and the flawed functions are directly reachable from public JSON-RPC methods.

### Recommendation
Before decoding an account as a `Mint`/using its extension data, verify `mint_account.owner()` is one of the known SPL Token / Token-2022 program ids in `get_mint_owner_and_additional_data` (and in `get_parsed_token_account`'s inline path), returning an error (or falling back to no additional data) if the owner check fails — mirroring the `is_known_spl_token_id` checks already applied to the token account and to `get_token_supply`'s mint lookup.

### Proof of Concept
Not independently executed; based on static analysis of the cited code paths:
1. Create account `M` owned by an attacker-controlled program (or any program), with data crafted to successfully `StateWithExtensions::<Mint>::unpack` (e.g., valid SPL `Mint` layout with `decimals = 0` and a forged `InterestBearingConfig`/`ScaledUiAmountConfig` extension).
2. Create a genuine SPL token account `T` (owned by `spl_token`/`spl_token_2022`) with its `mint` field set to `M`'s pubkey and an arbitrary `amount`.
3. Call `getTokenAccountBalance(T)` or `getAccountInfo(T, {encoding:"jsonParsed"})`.
4. Because `get_mint_owner_and_additional_data`/`get_parsed_token_account` never check `M`'s owner, the RPC response's `uiAmount`/`uiAmountString` (and any interest-bearing/scaled-UI display fields) reflect the attacker-forged `decimals`/extension configuration rather than a value from a real SPL mint.

Given the limited severity (display-only misreporting confined to the caller's own accounts, no crash/consensus impact identified), confidence in this being a high-severity finding is moderate; verification that no panic path exists in `InterestBearingConfig::amount_to_ui_amount`/`ScaledUiAmountConfig::amount_to_ui_amount` for adversarial inputs was not completed due to tool/iteration limits.

    pubkey: &Pubkey,
    account: AccountSharedData,
    // only used for simulation results
    overwrite_accounts: Option<&HashMap<Pubkey, AccountSharedData>>,

        });

    encode_ui_account(
        pubkey,
        &account,
        UiAccountEncoding::JsonParsed,
        additional_data,
        None,
    )
}

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

    pub fn get_token_account_balance(
        &self,
        pubkey: &Pubkey,
        commitment: Option<CommitmentConfig>,
    ) -> Result<RpcResponse<UiTokenAmount>> {
        let bank = self.bank(commitment);
        let account = bank.get_account(pubkey).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find account".to_string())
        })?;

        if !is_known_spl_token_id(account.owner()) {
            return Err(Error::invalid_params(
                "Invalid param: not a Token account".to_string(),
            ));
        }
        let token_account = StateWithExtensions::<TokenAccount>::unpack(account.data())
            .map_err(|_| Error::invalid_params("Invalid param: not a Token account".to_string()))?;
        let mint = &Pubkey::from_str(&token_account.base.mint.to_string())
            .expect("Token account mint should be convertible to Pubkey");
        let (_, data) = get_mint_owner_and_additional_data(&bank, mint)?;
        let balance = token_amount_to_ui_amount_v3(token_account.base.amount, &data);
        Ok(new_response(&bank, balance))
    }
