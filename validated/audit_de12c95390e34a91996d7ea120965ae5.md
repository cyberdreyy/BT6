### Title
Pending receipts from earlier epochs escape the `lossRecoveryPriceByEpoch` haircut and are paid at par, leaving later claimants underfunded - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` tracks each user's pending withdraw receipts per epoch (`withdrawsRequestsByEpoch[user][epoch]`), but the loss haircut applied by `collectWithdrawFunds` is stored under a single key, `lossRecoveryPriceByEpoch[epochNumber]`, and `_claimLossAdjustedWithdrawRequest` only clears the receipt booked in `lastWithdrawRequest[_user]` — the user's most recent request epoch. A user with receipts spread across two epochs has only the latest-epoch receipt haircutted; the older receipt stays in `withdrawsRequests[_user]` and is paid 1:1 through `_claimFundedWithdrawRequest`, even though the borrower funded only `pendingWithdraws * lossRecoveryPrice` for the aggregate. The overpaid withdrawal drains funded underlyings owed to other pending redeemers.

This is the closest analog to CVE-2021-3631: a flawed one-label-per-object scheme (single `lastWithdrawRequest` marker and a single per-epoch haircut) lets an object (the older-epoch receipt) acquire the wrong access/price and reach funds reserved for another compartment.

### Finding Description
Relevant code:

- `requestWithdraw` records the receipt under `currentEpoch` and unconditionally overwrites `lastWithdrawRequest[_user] = currentEpoch` at `contracts/strategies/idle/IdleCreditVault.sol:282-293`. The only guard (lines 261-271) blocks a new request when `lossRecoveryPriceByEpoch[lastWithdrawRequest]` is already set — it does not prevent accumulating receipts in *multiple* epochs before any loss occurs.
- `collectWithdrawFunds` sets `pendingWithdraws = 0` and stores a single haircut `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` at lines 411-430. `pendingBasis` is the *aggregate* of all users' receipts across all epochs.
- `_claimLossAdjustedWithdrawRequest` (lines 789-801) reads `lossEpoch = lastWithdrawRequest[_user]` and calls `_clearWithdrawClaimForEpoch(_user, lossEpoch, false)`, which zeros only `withdrawsRequestsByEpoch[_user][lossEpoch]` and decrements `withdrawsRequests[_user]` by that epoch's piece (lines 815-820). Receipts booked under any earlier epoch are untouched.
- `_claimFundedWithdrawRequest` (lines 319-350) then pays the entire remaining `withdrawsRequests[_user]` at par via `_transferFundedClaim`, gated only by `epochNumber > lastWithdrawRequest[_user]` — which passes because `_clearWithdrawClaimForEpoch` resets `lastWithdrawRequest[_user]` to 0 when it equals the loss epoch (lines 832-835).

Sequence (attacker = ordinary KYC'd lender; manager/owner honest):

1. Epoch N (running or buffer): attacker calls `requestWithdraw` → `withdrawsRequestsByEpoch[attacker][N] = X`, `lastWithdrawRequest = N`.
2. Epoch N+1: attacker calls `requestWithdraw` again → `withdrawsRequestsByEpoch[attacker][N+1] = Y`, `lastWithdrawRequest = N+1`. Guard passes because no loss price exists yet.
3. Honest manager stops the epoch with a loss (`stopEpochWithDuration` / borrower shortfall): borrower funds `pendingBasis * P` where `P = lossRecoveryPrice`. `pendingWithdraws` is zeroed; only `lossRecoveryPriceByEpoch[<stop epoch>]` records the haircut. The strategy now holds `pendingBasis * P` underlying for all receipts.
4. Attacker calls `IdleCDOEpochVariant.claimWithdrawRequest` → `IdleCreditVault.claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` pays `Y * P` for the epoch-N+1 receipt.
   - `_claimFundedWithdrawRequest` pays the epoch-N receipt `X` at **full par**, instead of `X * P`.
5. The attacker receives `X + Y*P` while the strategy reserved `(X + Y + others) * P` total. Every honest pending redeemer who claims afterwards is underfunded; the last claimant's `_transferFundedClaim` underpays or reverts on insufficient balance.

### Impact Explanation
Direct theft of other users' funded withdrawal proceeds. The haircut was computed against the aggregate `pendingBasis`, so paying any subset of that basis at par makes the reserve insolvent by `X * (1 - P)` per multi-epoch attacker. Loss scales with the attacker's oldest-epoch receipt size and the severity of the stop-epoch loss; with a 50% haircut the attacker steals half their older receipt's value from other pending claimants, and the last claimer permanently loses that amount (or is frozen until insolvency is resolved).

### Likelihood Explanation
Requirements: an unprivileged lender makes withdraw requests in two distinct epochs (buffer/running phases are long; nothing restricts re-requesting), and a `stopEpochWithDuration`/`collectWithdrawFunds` partial-funding event occurs — i.e., an honest borrower repayment shortfall, which is the designed loss path of this vault. No privileged misbehavior needed. One caveat: the exact epoch key used by `collectWithdrawFunds` relative to the `epochNumber` increment inside `deposit()` during `stopEpoch` could not be fully verified from `IdleCDOEpochVariant.sol` within this pass; the exploit requires the haircut to be stored under the same `epochNumber` in effect at request time for epoch N+1 (consistent with `_claimLossAdjustedWithdrawRequest` resolving via `lastWithdrawRequest`). If it is stored under the post-increment epoch instead, the same multi-epoch gap exists but keyed one epoch off, and the inconsistency would itself mis-haircut claims. Either way, the invariant "all pending receipts share one haircut" is broken by the single-epoch label.

### Recommendation
Track the loss haircut globally or per receipt, not per single epoch:

- Store a list/bitmap of loss epochs per user, or maintain `withdrawsRequestsByEpoch` haircut as a global `pendingLossRecoveryPrice` applied to *all* receipts in `withdrawsRequests[_user]` (the aggregate basis that was haircutted) when `pendingWithdraws` was zeroed.
- Alternatively, in `requestWithdraw`, revert whenever the user has any unclaimed pending receipt (not only when the last epoch carries a loss price) once `defaultRecoveryInitialized` is true, collapsing `withdrawsRequests` to a single-epoch bucket.
- In `_claimLossAdjustedWithdrawRequest`, apply `lossRecoveryPrice` to the whole remaining `withdrawsRequests[_user]` basis and clear every per-epoch entry, not just `lastWithdrawRequest`.

### Proof of Concept
Foundry fork PoC sketch (mainnet USDC fork, existing `IdleCDOEpochVariant` + `IdleCreditVault` deployment):

```solidity
// test/foundry/LossRecoveryMultiEpochEscape.t.sol
function test_MultiEpochReceiptEscapesHaircut() external {
    _stopCurrentEpoch();                       // epoch 0 -> buffer
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");
    uint256 ta = _depositWithUser(attacker, 100e6);
    uint256 tv = _depositWithUser(victim,   100e6);

    vm.prank(manager); cdoEpoch.startEpoch();  // epoch 1 running
    _requestWithdrawWithUser(attacker, ta / 2); // receipt in epoch 1
    _stopCurrentEpoch();                        // epochNumber -> 2
    vm.prank(manager); cdoEpoch.startEpoch();  // epoch 2 running
    _requestWithdrawWithUser(attacker, ta / 2); // receipt in epoch 2
    _requestWithdrawWithUser(victim, tv);       // receipt in epoch 2

    // borrower repays only 50% -> collectWithdrawFunds stores
    // lossRecoveryPriceByEpoch[2] = 0.5e18, pendingWithdraws = 0
    _stopCurrentEpochWithPartialRepay(50e16);

    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    // attacker got: epoch1 receipt at PAR + epoch2 receipt at 50%
    // strategy underlying is now short by (epoch1 receipt) * 50%

    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest(); // pays < expected 50% haircut or reverts
}
```

Expected result: `underlyingToken.balanceOf(attacker)` exceeds `totalReceipt * lossRecoveryPrice` share by `epoch1Receipt * (1e18 - lossRecoveryPrice) / 1e18`, and the victim's claim is underpaid by the same amount.
