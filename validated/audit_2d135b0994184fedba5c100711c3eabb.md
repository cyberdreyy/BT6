### Title
Defaulted-epoch instant receipts are dropped from recovery accounting because `instantWithdrawClaimsByEpoch` / `instantWithdrawsRequestsByEpoch` are read under the post-stop epoch number — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
When a `stopEpoch` increments `epochNumber` before the borrower funding transfer fails and the pool goes into default, any instant-withdraw receipts recorded under the pre-stop epoch become invisible to `finalizeDefaultRecovery` and `_claimDefaultedInstantWithdrawRequest`, which index both mappings by the *new* `epochNumber`. The result is an uninitialized-slot read: unfunded instant claimants are excluded from the recovery basis and can never collect their haircut payout — their minted receipt tokens are permanently frozen or their claims revert.

### Finding Description
`requestInstantWithdraw` records the receipt under the epoch at request time:

- `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`, with `currentEpoch = epochNumber` [1](#0-0) 

`epochNumber` is bumped inside `deposit()`, which the CDO calls while the epoch is still running (i.e., during `stopEpoch`, before the borrower `transferFrom` that can fail and trigger the default path): [2](#0-1) 

If the funding pull fails, `epochNumber` is already N+1 while the instant receipts still sit under epoch N. `finalizeDefaultRecovery` then:

- reads `instantWithdrawClaimsByEpoch[epochNumber]` (= N+1 → `0`) inside `defaultPendingClaimBasis`, so the instant basis is excluded from `totalBasis` even though `pendingInstantWithdraws != 0` [3](#0-2) 
- reads the same wrong key in `_defaultPrefundedInstantReserve`, so already-collected instant cash is not counted as reserve [4](#0-3) 
- sets `defaultRecoveryEpoch = epochNumber` (N+1) [5](#0-4) 

Later, `_claimDefaultedInstantWithdrawRequest` looks up `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (N+1 → `0`) and returns without clearing anything [6](#0-5) . `claimInstantWithdrawRequest` then falls through to burn `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim`, which reverts whenever `balance - reserve < amount` — i.e., whenever the strategy balance is fully consumed by the recovery reserve [7](#0-6) .

This is the direct analog of the CVE-2015-7802 bug class (read of uninitialized/stale state): epoch-indexed storage is dereferenced at an epoch key that was never written, silently zeroing a real claim basis instead of reverting or carrying the data forward.

### Impact Explanation
Permanent freezing / theft of unclaimed yield with quantified loss:

- Instant-withdraw requesters whose receipts were created in epoch N and left unfunded receive `0` recovery basis. Their receipt tokens (minted 1:1 in `requestInstantWithdraw`) can never be redeemed at the recovery price: either the claim reverts on the reserve guard (permanent freeze), or, if any non-reserve balance exists, they are paid at par from the funded bucket, draining underlyings owed to funded normal-withdraw claimants.
- Because the instant basis is missing from `totalBasis`, `recoveryPrice` is computed on a smaller denominator, so the shared reserve is over-distributed to other claimants until it is exhausted, after which remaining claims revert.

### Likelihood Explanation
Requires only ordinary sequencing, no privileged misbehavior: a lender requests an instant withdraw during epoch N; the honest manager calls `stopEpoch`, which bumps `epochNumber` via `deposit()`; the borrower funding `transferFrom` fails (real default scenario); the honest owner calls `finalizeDefault`. Any instant requester not yet funded at that moment is permanently affected. Note: I verified the strategy-side accounting but had limited iterations to fully trace `IdleCDOEpochVariant.stopEpoch`/`_handleBorrowerDefault` ordering; the finding assumes `deposit()` (and thus the `epochNumber += 1`) executes before the failing borrower pull, which matches the documented call order in `deposit`'s own comment.

### Recommendation
Key default-recovery instant accounting by the epoch in which receipts were recorded, not the current `epochNumber`. Options: snapshot `instantWithdrawClaimsByEpoch[epochNumber]` into a pending bucket at `stopEpoch` (as is done for `pendingWithdraws`), or track a separate `instantRequestEpoch`/global `pendingInstantBasis` aggregate that survives epoch increments, and use that same epoch key in `_claimDefaultedInstantWithdrawRequest` and `_defaultPrefundedInstantReserve`.

### Proof of Concept
Foundry fork PoC sketch (on `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity

//    -> falls through to _transferFundedClaim -> reverts when reserve covers balance
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
