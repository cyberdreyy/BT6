## Finding

### Title
Missing `VestingSchedule::assert_valid()` check in `LockupContract::new` allows an owner to self-assign a vesting schedule that instantly fully-vests (or breaks) their tokens - (File: `lockup/src/lib.rs`)

### Summary
The bug report describes an escrow configuration that is never validated at the point of creation, later breaking a custody invariant when the config is used. The exact same pattern exists in the `lockup` contract: `VestingSchedule` defines an `assert_valid()` invariant check (`start_timestamp <= cliff_timestamp <= end_timestamp` and `start_timestamp < end_timestamp`), but this check is never invoked by `LockupContract::new`, the only place a raw (non-hashed) `VestingSchedule` is accepted and persisted.

### Finding Description
`VestingSchedule::assert_valid()` is defined to guarantee the invariant the rest of the contract logic depends on: [1](#0-0) 

The lockup contract's own copy of this type carries the same guarantee in `lockup/src/types.rs`, but `LockupContract::new` — the initializer that stores `vesting_schedule` directly into `vesting_information` when a plain `VestingSchedule` (not a privacy-preserving hash) is supplied — never calls `assert_valid()` on it: [2](#0-1) 

The `lockup-factory` contract also passes the caller-supplied `vesting_schedule` straight through to the deployed lockup's `new` without any server-side validation: [3](#0-2) 

Since the account calling `create` (and thus supplying `vesting_schedule`) is the token owner themselves (as shown in the factory's own test, where `predecessor_account_id` is `account_tokens_owner`): [4](#0-3) 

the owner unilaterally controls the vesting parameters with no invariant enforcement. This value is then relied upon by `get_unvested_amount`/`get_locked_amount`, which assume `start_timestamp < end_timestamp` and `cliff_timestamp <= end_timestamp`: [5](#0-4) 

The equality this contract is supposed to preserve is:
`locked_amount(t) == max(unreleased_lockup(t), unvested_amount(t; schedule))`, where `unvested_amount` is guaranteed to interpolate from `lockup_amount` at `start_timestamp` down to `0` at `end_timestamp` **only if** `start_timestamp < end_timestamp` and `cliff_timestamp` sits between them. With no `assert_valid()` call, the owner can pick `end_timestamp <= start_timestamp` (or an already-past `end_timestamp`/`cliff_timestamp`) at contract creation time, which either:
- Sets `block_timestamp >= vesting_schedule.end_timestamp.0` immediately true, so `get_unvested_amount` unconditionally returns `0` from day one — the owner's tokens are treated as fully vested even though the intended employment/vesting period (as understood by the foundation counter-party) has not elapsed, or
- Causes `end_timestamp.0 - start_timestamp.0` (an unsigned subtraction) to underflow if `end_timestamp < start_timestamp`, producing either a panic (permanently reverting every call that touches `get_locked_amount`, e.g. `transfer`, `stake`, `select_staking_pool`) or a wrapped huge `total_time` that skews the vesting ratio unpredictably.

### Impact Explanation
This breaks the "locked/unvested tokens are released early" custody guarantee that the vesting mechanism (and the foundation's early-termination-refund logic) is built on: the entire purpose of `vesting_schedule` is to let the foundation later `terminate_vesting` and reclaim the unvested portion. If `unvested_amount` is coerced to `0` from the outset, the foundation's future termination path recovers nothing regardless of actual elapsed employment/vesting time — value the foundation is entitled to is permanently unavailable to it. Alternatively, an underflow panic freezes the owner's entire lockup contract (all owner methods depend on `get_locked_amount`/`get_owners_balance`), matching "funds permanently frozen." Both fall under the Critical/High impact classes defined in scope (locked/unvested tokens released early; funds frozen).

### Likelihood Explanation
High. No privileged role is required — the token owner supplies `vesting_schedule` directly as an argument to `lockup-factory::create` (or to `LockupContract::new` if deployed directly), and there is zero validation anywhere in the call path (`lockup-factory/src/lib.rs::create` and `lockup/src/lib.rs::new`) before the value is persisted and used by getters that are relied on for every transfer/staking operation.

### Recommendation
Call `vesting_schedule.assert_valid()` inside `LockupContract::new` (lockup/src/lib.rs) whenever a plain `VestingScheduleOrHash::VestingSchedule` variant is provided, mirroring the pattern already used for `RewardFeeFraction::assert_valid()` in `staking-pool/src/lib.rs::new`. Additionally, consider having `lockup-factory::create` reject vesting schedules that don't pass `assert_valid()` before spending gas on account creation, and/or restrict who may supply a non-hashed vesting schedule (e.g., require it be countersigned/set by the foundation) rather than letting the token owner define it unilaterally.

### Proof of Concept
1. Owner calls `LockupFactory::create` (or `LockupContract::new` directly) with:
   ```json
   "vesting_schedule": {
     "VestingSchedule": {
       "start_timestamp": "2000000000000000000",
       "cliff_timestamp": "1000000000000000000",
       "end_timestamp": "1000000000000000000"
     }
   }
   ```
   i.e. `cliff_timestamp`/`end_timestamp` earlier than `start_timestamp`, or `end_timestamp` already in the past relative to `block_timestamp`.
2. `LockupContract::new` (lockup/src/lib.rs:216-243) accepts this without calling `assert_valid()` and stores it as `VestingInformation::VestingSchedule(vs)`.
3. Immediately after deployment, `get_unvested_amount` (lockup/src/getters.rs:123-150) sees `block_timestamp >= vesting_schedule.end_timestamp.0` and returns `0` — the owner's tokens under vesting are treated as fully vested from the very first block, even though no real vesting time has elapsed, permanently defeating any future `terminate_vesting` refund the foundation would otherwise be entitled to.

    pub fn get_unvested_amount(&self, vesting_schedule: VestingSchedule) -> WrappedBalance {
        let block_timestamp = env::block_timestamp();
        let lockup_amount = self.lockup_information.lockup_amount;
        match &self.vesting_information {
            VestingInformation::Terminating(termination_information) => {
                termination_information.unvested_amount
            }
            VestingInformation::None => U128::from(0),
            _ => {
                if block_timestamp < vesting_schedule.cliff_timestamp.0 {
                    // Before the cliff, nothing is vested
                    lockup_amount.into()
                } else if block_timestamp >= vesting_schedule.end_timestamp.0 {
                    // After the end, everything is vested
                    0.into()
                } else {
                    // cannot overflow since block_timestamp < vesting_schedule.end_timestamp
                    let time_left = U256::from(vesting_schedule.end_timestamp.0 - block_timestamp);
                    // The total time is positive. Checked at the contract initialization.
                    let total_time = U256::from(
                        vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0,
                    );
                    let unvested_amount = U256::from(lockup_amount) * time_left / total_time;
                    // The unvested amount can't be larger than lockup_amount because the
                    // time_left is smaller than total_time.
                    unvested_amount.as_u128().into()
                }
            }
