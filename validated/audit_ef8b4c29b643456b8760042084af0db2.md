### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing execution below the real threshold - (`File: multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges pending *requests* that were originally created by the removed member; it never scans the `confirmations` map to strip that member's votes from other requests they merely *confirmed*. Because `confirm()` tallies confirmation-set size against `num_confirmations` without re-validating that every recorded signer is still a current member, a request can reach and pass the threshold using fewer live-member confirmations than actually required.

### Finding Description
`confirm()` compares the stored confirmation count to the threshold and, once satisfied, executes the request: [1](#0-0) 

`assert_valid_request()` only checks that the *caller* confirming right now is a current member; it does not re-validate the members already present in the stored `confirmations` set: [2](#0-1) 

`delete_member()` removes requests whose *signer* (creator) equals the removed member, and removes that member's own `num_requests_pk` counter and access key, but it never inspects `self.confirmations` for entries belonging to requests *created by other members* that the removed member had already confirmed: [3](#0-2) 

Consequence: if member `A` confirms request `X` (created by `B`, not yet at threshold), and `A` is later removed from `members` via a legitimate `DeleteMember` request, `A`'s entry remains inside `confirmations.get(X)`. When enough remaining members later call `confirm(X)`, the stale `A` entry is counted in `confirmations.len() + 1 >= num_confirmations`, so the request executes with one fewer *live* confirmation than `num_confirmations` actually requires. This breaks the equality the contract is supposed to enforce: `live confirmations on a request == num_confirmations before execution`. Instead, `live confirmations + stale (former-member) confirmations >= num_confirmations` is what actually gates execution.

The equivalent code path in the legacy `multisig` contract has the same gap: `DeleteKey` only removes requests where `r.signer_pk == pk` (the request's creator), not confirmations the deleted key cast on other members' requests: [4](#0-3) 

### Impact Explanation
This lets any `MultiSigRequest` — including `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, `DeployContract`, etc. — execute against the multisig-controlled account with fewer genuinely-authorized confirmations than the configured `num_confirmations`. That is exactly the "multisig request executed below threshold" Critical impact: NEAR (or any assets/keys controlled by the multisig account) can be moved or the account's key set altered with a weaker security guarantee than the members configured, without any of the remaining current members detecting that a phantom, no-longer-valid confirmation is being relied upon.

### Likelihood Explanation
No privileged/foundation action or attacker-controlled deployment is required beyond the multisig's own normal, expected operations: creating a request, confirming it, and later removing a member who had confirmed but not created it — all legitimate multisig member actions. Membership churn (onboarding/offboarding signers) is a routine multisig lifecycle event, so any organization that removes a member while unrelated requests are still pending will silently retain that member's stale confirmation weight.

### Recommendation
When removing a member (`delete_member`) or a key (`DeleteKey` in `multisig`), iterate over all entries in `self.confirmations` (not just requests created by that member) and strip the removed member's/key's identifier from every confirmation set. Alternatively, when tallying in `confirm()`, filter the stored confirmation set to only members currently present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = {A, B, C}` and `num_confirmations = 2`.
2. `B` calls `add_request` to create request `X` (e.g. `Transfer` of funds) — 0 confirmations so far.
3. `A` calls `confirm(X)` → `confirmations[X] = {A}` (count 1, below threshold of 2), per `confirm` logic at `multisig2/src/lib.rs:292-315`.
4. Members execute a separate, properly-confirmed `DeleteMember { member: A }` request to remove `A` from the multisig (e.g., because `A` left the organization). `delete_member` runs at `multisig2/src/lib.rs:355-379`, which only removes requests *created by* `A`; request `X` (created by `B`) is untouched, so `confirmations[X]` still contains `A`.
5. `C` (a current, legitimate member) calls `confirm(X)`. In `confirm()`, `confirmations.len() as u32 + 1 >= self.num_confirmations` evaluates `1 + 1 >= 2` → true, so `execute_request` fires and the transfer executes.
6. Result: request `X` executed with only one truly-current-member confirmation (`C`), while `num_confirmations = 2` was supposed to require two live members' approval — the removed member `A`'s stale confirmation counted toward the threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
