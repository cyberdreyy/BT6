### Title
Legacy Gateway `HandleLegacyUserMessage` lacks sender allowlist check, permitting request forwarding by any unregistered signer - ([File: core/services/gateway/gateway.go])

### Summary
`ProcessRequest` in `gateway.go` calls `msg.Validate()` for legacy requests (DonId != ""), which only verifies the signature format is well-formed and recovers `Body.Sender` from the ECDSA signature, but never checks that the recovered sender is a member of an allowlist before dispatching to `h.HandleLegacyUserMessage`. The `capabilities` handler's `HandleLegacyUserMessage` explicitly documents this gap with `// TODO: apply allowlist and rate-limiting here` and proceeds to forward the request to all DON nodes regardless of who signed it.

### Finding Description
In `core/services/gateway/gateway.go`, `ProcessRequest` handles the legacy path as follows: [1](#0-0) 
`msg.Validate()` recovers and populates `Body.Sender` from the signature but does not compare it against any allowed/registered subscriber set for `handlerKey` (the `DonId`). The lookup at line 258 (`h, ok = g.handlers[handlerKey]`) only checks that the DON ID itself is configured — it does not gate on the sender's identity.

The request is then dispatched unconditionally to `h.HandleLegacyUserMessage(ctx, msg, callback)`: [2](#0-1) 

In the concrete legacy handler implementation, `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` performs payload decoding, staleness checks, and method validation, but the code explicitly flags the missing authorization step: [3](#0-2) 
After these checks, the message is forwarded to every member of the DON without any sender allowlist check: [4](#0-3) 

Because the only "authentication" performed is a well-formed ECDSA signature (which any attacker can trivially produce with a freshly generated keypair), any external actor can address the message to an existing `DonId` and have it accepted and forwarded to that DON's nodes, since `msg.Validate()` never checks `Body.Sender` membership against a configured/allowed subscriber list for that DON.

### Impact Explanation
This allows unauthenticated/unregistered senders to impersonate a legitimate DON subscriber and submit legacy trigger requests (e.g., `web_api_trigger`) that get forwarded to and processed by the target DON's nodes, potentially causing unauthorized workflow triggers, resource consumption on DON nodes, and confusion/request forgery for the targeted DON, matching the impact class of authentication/authorization bypass and request impersonation.

### Likelihood Explanation
The precondition is trivial: an attacker only needs to generate an ECDSA keypair (no registration or credentials required) and sign a legacy `Message` targeting any existing, correctly-configured `DonId`. There is no rate limiting or allowlist enforced before `HandleLegacyUserMessage` forwards the request, as confirmed by the explicit `TODO: apply allowlist and rate-limiting here` comment in the code. This makes the attack fully repeatable with no privileged access.

### Recommendation
Before forwarding a legacy message to the DON handler, verify that the recovered `Body.Sender` is present in a configured allowlist/subscriber registry for the target `DonId` (e.g., cross-reference against `donConfig.Members` or a dedicated user allowlist), rejecting the request with an authorization error if not found. This check should occur either in `gateway.ProcessRequest` right after `msg.Validate()`, or at the very start of `HandleLegacyUserMessage`, replacing the existing TODO with actual enforcement.

### Proof of Concept
Go handler-level integration test plan:
1. Configure a `capabilities` handler with a `DonConfig` that has a defined member/subscriber allowlist (or an existing test config).
2. Generate a random, never-registered ECDSA private key.
3. Construct a legacy `api.Message` with `Body.DonId` set to the configured DON ID and `Body.Method = "web_api_trigger"`, with a valid `Timestamp` in payload.
4. Sign the message with the random unregistered key so that `msg.Validate()` succeeds (signature format and `Body.Sender` population correct).
5. Call `gateway.ProcessRequest` (or directly `handler.HandleLegacyUserMessage`) with this message.
6. Assert: currently the message is accepted and forwarded via `don.SendToNode` to all DON members (i.e., `SendToNode` mock is invoked) — proving the lack of allowlist enforcement.
7. After the fix, assert that the response is an authorization error and `don.SendToNode` is never invoked for unregistered senders.
