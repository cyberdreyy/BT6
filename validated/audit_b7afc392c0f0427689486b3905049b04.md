### Title
Missing canonicity check on parent tenure in `check_block_has_valid_parent` allows signing atop an orphaned tenure - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
`check_block_has_valid_tenure` (line 454-472) only checks that the *proposed block's own* `consensus_hash` is on the canonical sortition fork, and it is invoked exactly once, against `self.block.header.consensus_hash` [1](#0-0) . In the tenure-start branch of `check_block_has_valid_parent`, the parent's tenure (`parent_header.consensus_hash`) is fetched purely from `chainstate.db()` and handed to `check_block_builds_on_highest_block_in_tenure` without ever being checked against `db_handle.has_consensus_hash(...)` or any other canonical-sortition-fork test.

### Finding Description
The intended equality is: *canonical-tenure status of the block's own consensus hash == canonical-tenure status of the parent block's consensus hash*, both enforced before a signer signs. In practice only the first half is enforced:

- `check_block_has_valid_tenure(db_handle, tenure_id)` verifies `db_handle.has_consensus_hash(tenure_id)` [2](#0-1)  and is called once, on `self.block.header.consensus_hash`, using a `db_handle` opened at the block's own burn view (`sort_tip`) [3](#0-2) .
- `check_block_has_valid_parent` (line 480-524) branches on `is_wellformed_tenure_start_block()`. For a tenure-start block it loads `parent_header` via `NakamotoChainState::get_block_header(chainstate.db(), &block.header.parent_block_id)` [4](#0-3)  and then calls `check_block_builds_on_highest_block_in_tenure(chainstate, sortdb, &parent_header.consensus_hash, &block.header.parent_block_id)` [5](#0-4) .
- `check_block_builds_on_highest_block_in_tenure` only calls `NakamotoChainState::find_highest_known_block_header_in_tenure(chainstate, sortdb, tenure_id)` to find the tallest header recorded under that consensus hash in the local chainstate DB, and compares heights against `parent_header` [6](#0-5) . Nowhere in this function is `db_handle.has_consensus_hash(tenure_id)` (or any sortdb-canonical-fork query) invoked for `parent_header.consensus_hash`.

Because `chainstate.db()` stores block headers that were validated when their tenure *was* canonical, a subsequent Bitcoin reorg can orphan that tenure while its headers remain in the local Nakamoto headers table. A miner can then win a *new*, canonical tenure and craft a tenure-start block whose `parent_block_id` points at the tip of the now-orphaned tenure. `check_block_has_valid_tenure` only ever checks the new block's own (canonical) consensus hash, and `check_block_has_valid_parent`/`check_block_builds_on_highest_block_in_tenure` never re-validate that the parent tenure's consensus hash is still on the canonical sortition fork — they only check relative block heights within that (possibly stale) tenure's header set.

### Impact Explanation
This breaks the CANONICITY safety property that block validation is supposed to guarantee to signers: a signer relying solely on `validate()`/`check_block_has_valid_parent` could sign a tenure-start block whose parent chain traverses through an orphaned (non-canonical) tenure, i.e., a block that does not actually extend the canonical Stacks chain. This is a Critical-severity outcome under the stated impact categories (signing a non-canonical/conflicting block).

### Likelihood Explanation
Requires the attacker to win one miner slot (as allowed) for a tenure that follows a Bitcoin fork event orphaning a prior tenure whose headers are still present in local chainstate, and to craft `parent_block_id` pointing into that orphaned tenure. This is fully within an unprivileged single-miner-slot attacker's capability (gossiped BlockProposal only) and is repeatable whenever such reorg conditions recur.

### Recommendation
In the tenure-start branch of `check_block_has_valid_parent`, after fetching `parent_header`, explicitly call `check_block_has_valid_tenure` (or an equivalent `db_handle.has_consensus_hash` check against the canonical sortition handle) on `parent_header.consensus_hash` before proceeding to `check_block_builds_on_highest_block_in_tenure`, mirroring the check already performed for the block's own tenure at line 602.

### Proof of Concept
Rust test plan (chainstate-level, mirroring existing `postblock_proposal.rs` unit tests):
1. Set up a `SortitionDB` + `StacksChainState` fixture with two forks: fork A produces tenure T1 (processed and stored in `chainstate.db()`), then a Bitcoin reorg makes fork B canonical, orphaning T1's sortition (T1's consensus hash no longer satisfies `db_handle.has_consensus_hash`).
2. Mine canonical tenure T2 on fork B.
3. Construct a well-formed tenure-start Nakamoto block `blk` with `header.consensus_hash = T2` (canonical) and `header.parent_block_id` pointing to the tip block of orphaned tenure T1 (still present in `chainstate.db()`).
4. Call `NakamotoBlockProposal::check_block_has_valid_tenure(&db_handle_at_T2, &blk.header.consensus_hash)` — assert `Ok(())` (T2 is canonical).
5. Call `NakamotoBlockProposal::check_block_has_valid_parent(&chainstate, &sortdb, &blk)` — current code returns `Ok(())` because it never checks T1's canonicity; assert this is the bug (test currently fails to reject).
6. After applying the fix (adding a canonical check on `parent_header.consensus_hash`), re-run step 5 and assert `Err(BlockValidateRejectReason { reason_code: ValidateRejectCode::NonCanonicalTenure, .. })`.

    fn check_block_builds_on_highest_block_in_tenure(
        chainstate: &StacksChainState,
        sortdb: &SortitionDB,
        tenure_id: &ConsensusHash,
        parent_block_id: &StacksBlockId,
    ) -> Result<(), BlockValidateRejectReason> {
        let Some(highest_header) = NakamotoChainState::find_highest_known_block_header_in_tenure(
            chainstate, sortdb, tenure_id,
        )
        .map_err(|e| BlockValidateRejectReason {
            reason_code: ValidateRejectCode::ChainstateError,
            reason: format!("Failed to query highest block in tenure ID: {:?}", &e),
            failed_txid: None,
        })?
        else {
            warn!(
                "Rejected block proposal";
                "reason" => "Block is not a tenure-start block, and has an unrecognized tenure consensus hash",
                "consensus_hash" => %tenure_id,
            );
            return Err(BlockValidateRejectReason {
                reason_code: ValidateRejectCode::NoSuchTenure,
                reason: "Block is not a tenure-start block, and has an unrecognized tenure consensus hash".into(),
                failed_txid: None,
            });
        };
        let Some(parent_header) =
            NakamotoChainState::get_block_header(chainstate.db(), parent_block_id).map_err(
                |e| BlockValidateRejectReason {
                    reason_code: ValidateRejectCode::ChainstateError,
                    reason: format!("Failed to query block header by block ID: {:?}", &e),
                    failed_txid: None,
                },
            )?
        else {
            warn!(
                "Rejected block proposal";
                "reason" => "Block has no parent",
                "parent_block_id" => %parent_block_id
            );
            return Err(BlockValidateRejectReason {
                reason_code: ValidateRejectCode::UnknownParent,
                reason: "Block has no parent".into(),
                failed_txid: None,
            });
        };
        if parent_header.anchored_header.height() != highest_header.anchored_header.height() {
            warn!(
                "Rejected block proposal";
                "reason" => "Block's parent is not the highest block in this tenure",
                "consensus_hash" => %tenure_id,
                "parent_header.height" => parent_header.anchored_header.height(),
                "highest_header.height" => highest_header.anchored_header.height(),
            );
            return Err(BlockValidateRejectReason {
                reason_code: ValidateRejectCode::InvalidParentBlock,
                reason: "Block is not higher than the highest block in its tenure".into(),
                failed_txid: None,
            });
        }
        Ok(())
    }

    pub(crate) fn check_block_has_valid_tenure(
        db_handle: &SortitionHandleConn,
        tenure_id: &ConsensusHash,
    ) -> Result<(), BlockValidateRejectReason> {
        // Verify that the block's tenure is on the canonical sortition history
        if !db_handle.has_consensus_hash(tenure_id)? {
            warn!(
                "Rejected block proposal";
                "reason" => "Block's tenure consensus hash is not on the canonical Bitcoin fork",
                "consensus_hash" => %tenure_id,
            );
            return Err(BlockValidateRejectReason {
                reason_code: ValidateRejectCode::NonCanonicalTenure,
                reason: "Tenure consensus hash is not on the canonical Bitcoin fork".into(),
                failed_txid: None,
            });
        }
        Ok(())
    }
