### Title
APR0 withdraw bucket poisons `stopEpoch` when APR is raised mid-flight — temporary freezing of all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2023-38545 is a state-variable-misses-transition bug: a flag decided at handshake start gets the wrong value by the time the data is consumed. The closest analog in idle-tranches is the APR0 withdrawal bucket in `IdleCreditVault`: whether a withdrawal is booked into the APR0 bucket is decided at request time by reading `unscaledApr == 0`, but the bucket is settled at `stopEpoch` time by `prepareStopEpochWithApr0`, which *reverts* if `unscaledApr != 0`. An unprivileged lender can request a withdrawal while APR is 0, and if the honest manager later raises the APR before the epoch stops (a normal, permitted operation), every subsequent `stopEpoch` reverts, freezing the vault until APR is set back to 0.

### Finding Description
In `requestWithdraw`, the accounting bucket is chosen by a snapshot of `unscaledApr` at request time:

```solidity
if (unscaledApr == 0 && !isClosed) {
  _requestWithdrawApr0(_amount, _user);
} else {
  withdrawsRequests[_user] += _amount;
  ...
}
```

`_requestWithdrawApr0` increments the global `apr0TotalPrincipal`. Later, when the CDO stops the epoch, `prepareStopEpochWithApr0` enforces a *second, inconsistent* check of the same flag at settle time:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

So an attacker (any KYC'd lender / tranche holder) performs:

1. Buffer phase, `unscaledApr == 0` → `cdoEpoch.requestWithdraw(amount, tranche)` → `apr0TotalPrincipal > 0`.
2. Honest manager calls `setAprs(newApr, scaledApr)` with `newApr != 0` — routine rate-setting, not malicious.
3. Manager calls `stopEpoch` → CDO calls `prepareStopEpochWithApr0` → reverts `NotAllowed()`.
4. Every `stopEpoch` reverts while `unscaledApr != 0` and `apr0TotalPrincipal != 0`. Neither counter can be cleared by any other path: `apr0TotalPrincipal` is only reset inside the same reverting function (line 540) or decrementally in `_clearWithdrawClaimForEpoch`, which only runs under `defaultRecoveryFinalized` or a loss-adjusted epoch — neither reachable.

The only recovery is the manager setting APR back to 0, stopping the epoch, then re-raising it. That is exactly the curl bug shape: the request-time classification (`unscaledApr == 0`) and the settle-time validation disagree across the slow, multi-transaction epoch lifecycle.

### Impact Explanation
Temporary freezing of all vault funds: while `stopEpoch` reverts, no lender can exit (claims require the epoch to advance past `lastWithdrawRequest`), borrower repayments cannot be booked, and `startEpoch` cannot proceed. Duration of the freeze is bounded by manager response, but the attacker can re-arm it cheaply: each time APR is 0, a dust-size `requestWithdraw` re-poisons the bucket. Cost to the attacker is only the upfront management fee on the requested principal.

### Likelihood Explanation
Requires the APR-0 product mode (used for pools where yield is realized at `stopEpoch` via override interest rather than fixed APR — the APR0 tests show this is a supported configuration). In that mode APR transitions from 0 to a positive value are a normal operational event, so the trigger sequence is realistic, and the attacker only needs one small withdrawal to arm it. Existing guards do not prevent it: the `unscaledApr != 0` revert is the bug, not a mitigation, and there is no path for a pending APR0 requester to migrate their bucket when APR changes.

### Recommendation
Do not gate `prepareStopEpochWithApr0` on `unscaledApr != 0` reverting. Either settle the open APR0 bucket at whatever rate the epoch actually realized (pro-rata share of `_interest` is already computed independently of `unscaledApr`), or migrate `apr0TotalPrincipal` into the normal `pendingWithdraws`/`withdrawsRequests` bucket when `setAprs` transitions away from 0, so request-time classification cannot conflict with settle-time state.

### Proof of Concept
```solidity
// Foundry fork PoC (setup mirrors test/foundry/IdleCreditVault.t.sol APR0 tests)
function testApr0RequestPoisonsStopEpochAfterAprRaise() external {
    // Pool running in APR0 mode
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // Attacker deposits and requests a small withdraw while APR == 0
    uint256 amount = 1 * ONE_SCALE;
    _depositWithUser(attacker, amount, true);
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _forceLastEpochAprToZero();

    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // Honest manager raises APR for the next epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(1e18, 1e18);

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, type(uint128).max);

    // stopEpoch permanently reverts while APR != 0 -> vault frozen
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 1000 * ONE_SCALE);
}
```
