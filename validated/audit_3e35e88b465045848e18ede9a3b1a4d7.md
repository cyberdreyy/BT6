### Title
Stale confirmations from removed multisig members still count toward the confirmation threshold, allowing request execution below the live-member quorum - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
The multisig contracts allow a request to execute once `confirmations.len() + 1 >= num_confirmations`. Confirmations are stored as pubkeys/member identifiers in a `HashSet` per request. When a member is removed via `DeleteMember`/`DeleteKey`, the code only purges *outstanding requests initiated by* that member — it never scans other pending requests' `confirmations` sets to strip out that member's stale confirmation. A request that already collected a confirmation from a member who is later removed keeps that confirmation "alive" and can still count toward the quorum, letting a request execute with fewer currently-authorized signers than `num_confirmations` requires.

### Finding Description
`confirm()` in both `multisig/src/lib.rs` and `multisig2/src/lib.rs` counts a request as approved once the confirmation set size reaches `num_confirmations`, then calls `execute_request`: [1](#0-0) 

The removal logic on member deletion (`delete_member` in `multisig2`, `DeleteKey` handling in `multisig`) only removes requests whose *own initiating* member/key matches the one being deleted — it does not touch `confirmations` entries where that member/key merely *confirmed* (but did not create) some other still-pending request: [2](#0-1) [3](#0-2) 

Because `confirmations` is a plain `HashSet<String>`/`HashSet<PublicKey>` with no live-membership re-validation at execution time, and `assert_valid_request`/`current_member()` only validate the *caller* of the current `confirm()` call (not the historical confirmers already recorded for the request), a confirmation from a member who has since been removed remains a valid vote toward `num_confirmations`: [4](#0-3) 

The binding that should hold is: *confirmations counted toward execution == confirmations from currently-live members*. This is broken — `confirmations_counted ⊇ confirmations_from_removed_members`, yet the code treats them as equally valid.

### Impact Explanation
This lets a multisig request execute (e.g., an arbitrary `Transfer`, `FunctionCall`, or `AddKey`/`AddMember` action) with fewer live, currently-authorized signers than the configured threshold — a request executed below quorum. Since multisig contracts in this repo commonly custody NEAR funds and control access keys for the account, this directly breaks the intended "K of N live members must approve" custody binding and can result in unauthorized fund transfers or unauthorized key/permission changes signed off by a quorum that, at execution time, no longer holds real authority over the account.

### Likelihood Explanation
This requires no privileged action beyond normal, permitted multisig operations: any member of the multisig confirming a request and later the multisig removing that member (a routine "rotate keys/members" operation) is enough to create a stale-but-still-counted confirmation. No malicious deployment, redeploy, or off-chain compromise is needed — only ordinary usage patterns (partial confirmation followed by later membership rotation) that any of the existing members can trigger or that occur naturally during key rotation.

### Recommendation
When a member/key is deleted, also scan `confirmations` for *every* pending request (not just requests they initiated) and remove their entry from each confirmation set; alternatively, at `confirm()`/execution time, re-validate that every public key/member recorded in a request's `confirmations` set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
Using `multisig2::MultiSigContract` with `num_confirmations = 3` and members `{A, B, C, D, E}`:
1. Member `D` calls `add_request` to create request `R` (e.g., `Transfer` to an attacker-controlled account), then `A` and `B` `confirm(R)` → confirmations = `{D, A, B}`... actually simpler: `D` and `E` `confirm(R)` → confirmations = `{D, E}` (2 of 3 needed).
2. Separately, members `A`, `B`, `C` create and confirm a `DeleteMember` request removing both `D` and `E` (their own quorum of 3 live members) — `D` and `E` are now removed from `self.members` and their access keys deleted; this path only cleans requests *initiated* by `D`/`E`, not `R`, since `R` was initiated by neither.
3. Member `A` now calls `confirm(R)`. `assert_valid_request`/`current_member()` validate that `A` is a live member (true), and `confirmations.len() + 1 == 3 >= num_confirmations` — so `R` executes, even though the votes backing it are `{D, E, A}` where `D` and `E` are no longer members at all. Effectively only 1 of the 3 required *live* members actually approved `R` at execution time. [5](#0-4) [6](#0-5)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
