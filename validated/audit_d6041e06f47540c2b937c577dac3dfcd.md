### Title
Multisig `new()` does not reject `num_confirmations == 0`, allowing any single key to execute requests without real multisig authorization - ([File: multisig/src/lib.rs])

### Summary
Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` implement the "missing zero check" bug class from the external report: their `new()` initializers accept an unchecked `num_confirmations: u32` parameter and store it directly without asserting it is greater than zero (and, for `multisig2`, without re-validating it after member changes beyond the initial creation check). This is the closest in-scope analog to the reported issue, since it breaks the "confirmations counted versus live members/threshold" custody binding called out in the rules.

### Finding Description
`MultiSigContract::new` stores `num_confirmations` with no validation: [1](#0-0) 

The `confirm()` method authorizes execution once `confirmations.len() + 1 >= self.num_confirmations`: [2](#0-1) 

If `num_confirmations` is `0` (e.g., due to a front-end bug, a scripting error, or a malformed deployment argument — the exact "front-end bug passes zero" scenario described in the external report), then on the very first call to `confirm()`, the check `0 as u32 + 1 >= 0` is trivially true, so the request executes immediately with a single confirming key. This defeats the entire purpose of the multisig: a threshold of "0 of N" collapses to "any 1 of N", i.e., the equality `confirmations required == threshold configured` no longer holds, and a single access key can move funds, add/delete keys, or deploy new contract code that should have required multiple approvals.

Additionally, `execute_request`'s `SetNumConfirmations` action lets a single confirmation flow (if `num_confirmations == 1`) reset `num_confirmations` to `0`, permanently degrading the contract's security assumptions with no floor check: [3](#0-2) 

### Impact Explanation
This maps to the report's "Critical" bucket: "a multisig request executed below threshold." If the intended threshold is `k` but `num_confirmations` is zero (or later set to zero via `SetNumConfirmations`), any single member's confirmation is sufficient to execute arbitrary `Transfer`, `AddKey`, `DeleteKey`, `DeployContract`, or `FunctionCall` actions — a full authorization bypass of the confirmations-vs-threshold binding.

### Likelihood Explanation
Reaching this state requires either (a) the initializing party passing `0` for `num_confirmations` at deployment, or (b) a legitimate `SetNumConfirmations{0}` request being confirmed under the existing (non-zero) threshold. Both are plausible through front-end/tooling bugs, matching the exact "bug in the front end" exploit scenario in the external report. `multisig2::new` does check `members.len() >= num_confirmations`, which is trivially satisfied when `num_confirmations == 0`, so it does not protect against this case either: [4](#0-3) 

### Recommendation
- Short term: In `multisig/src/lib.rs::new` and `multisig2/src/lib.rs::new`, assert `num_confirmations > 0` (and `num_confirmations <= members.len()` where applicable). In the `SetNumConfirmations` action handler inside `execute_request`, also assert the new value is greater than zero before assigning it.
- Long term: Comprehensively validate all threshold/count parameters at every mutation point (not just at `new`), and add regression tests asserting that `new(0)` and `SetNumConfirmations{0}` both panic.

### Proof of Concept
1. Deploy the multisig contract with `new({"num_confirmations": 0})` (or drive `num_confirmations` to `0` via a confirmed `SetNumConfirmations{num_confirmations: 0}` request while the threshold is `1`).
2. Any holder of a single access key calls `add_request_and_confirm` with a `Transfer` action to their own account.
3. In `confirm()`, `confirmations.len() as u32 + 1 >= self.num_confirmations` evaluates `1 >= 0 == true` immediately, so `execute_request` runs and transfers funds out with only one confirmation, even though the multisig was nominally supposed to require multiple keys.
