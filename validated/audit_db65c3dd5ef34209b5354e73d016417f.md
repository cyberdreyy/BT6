## Analysis

The Fortuna bug is a **"confirmations misused as finality"** class: a service treats "N blocks have passed" or "the tip has caught up to height H" as proof that a prior commitment can never come back, when the underlying chain's actual finality model allows a much deeper reorg. The strongest analog in this repo is not in the node's block-validation endpoint (which checks the canonical Bitcoin fork directly and is out of scope as "node consensus acceptance"), but in the **signer's own reorg-liveness heuristic** that governs whether it is safe to sign a *replacement* for a block it has already signed.

### Title
Signer treats a single unconfirmed sortition 404 as proof a conflicting tenure is dead, enabling a double-sign on a shallow burnchain reorg - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
Before signing a block that conflicts with one it has already put a signature over, the v0 signer runs `conflict_still_blocks`/`reorg_permit_stands` to decide whether the earlier, conflicting signature is still "live." Part of that decision asks the node whether the conflicting tenure's burn block is still on the canonical Bitcoin fork via `/v3/sortitions/burn/:hash`. A `404` is accepted as proof that "a burnchain fork orphaned the tenure" as soon as the node's burnchain tip (`get_peer_info`) has merely *reached* the stored burn block's height — with no additional confirmation-depth requirement [1](#0-0) . This is exactly the "confirmations vs. true finality" conflation described in the external report, transplanted onto Bitcoin's probabilistic-finality burn chain: reaching a height is not the same as that height being irreversible, and shallow (1-block) reorgs at the tip are a normal, single-miner-triggerable event on Bitcoin.

### Finding Description
The conflict-freshness logic explicitly documents its own trust model: a `404` from the sortition-by-burn-hash lookup is "not proof — the same endpoint 404s a perfectly canonical burn block when the node is still catching up... so it is only trusted once the node's burnchain tip is at or past the stored burn block's height" [1](#0-0) . The guard requires the tip to be *at or past* — i.e., zero or more confirmations beyond the disputed block — not a depth sufficient to rule out a further reorg. Once that (weak) condition is met, the routine falls through to `LIVE`/`OWN` branches that let the signer treat the previously-signed conflicting block as dead and sign the new proposal instead: "it does not, and the block was globally accepted — the node once did have it, so a reorg moved past it. That is proof it is dead" [2](#0-1) .

This mirrors the same architectural mistake that `SortitionData::check_latest_block_in_tenure` makes elsewhere in the chainstate: it substitutes an elapsed-time/height heuristic (`tenure_last_block_proposal_timeout`, `reorg_attempts_activity_timeout`) for genuine finality when deciding whether a previously-signed tip can be superseded [3](#0-2) . Both paths assume that once the node's reported tip has "moved past" a point, that point cannot return — an assumption that Bitcoin's probabilistic finality does not guarantee at shallow depths, and that the signer code itself calls out as unreliable ("a node error can wipe the local state machine," "a fact recorded once at observation time can be silently wrong") [4](#0-3) .

The consequence: a single miner who wins one competing block at the same burnchain height as the tenure whose block the signer already signed can cause a momentary 404/height-match that satisfies this guard. If the original fork then reasserts itself (a routine, sub-majority event at 0–1 confirmations), the signer has already released a *second* signature over a conflicting Stacks block at the same height, in violation of the one-signature-per-height/no-double-sign invariant the pre-commit conflict guard exists to enforce (`get_signed_conflicts`, which explicitly spans all tenures precisely because "two blocks at the same height are siblings no matter which tenure they belong to") [5](#0-4) .

### Impact Explanation
This is a **Critical** analog: it produces a signer signing a **conflicting block** — the exact "a signer signing an invalid/non-canonical/conflicting block" outcome the scope calls out. If enough signers hit the same narrow window (all polling the same node/tip state near the same burnchain height), two mutually exclusive blocks can each cross the 70% threshold, splitting the canonical chain.

### Likelihood Explanation
No majority of signers, no other signer's key, and no StackerDB/auth-token access is required — only a single miner able to produce one competing block at the disputed height (or a naturally occurring shallow chain-tip race), which is far below "majority hash power." The bug is latent in every signer independently since each queries the node's `/v3/sortitions/burn/:hash` and `get_peer_info` on its own, so the race window is small but real and repeats on every reorg-adjacent tenure transition.

### Recommendation
Require a minimum confirmation depth (not just "tip ≥ height") before a `404`/orphaned-sortition determination is used to clear a signed conflict, and/or treat the 404-based clearing as reversible until the burnchain tip is a fixed number of blocks past the disputed height, mirroring the "wait for finality, not just confirmations" recommendation from the Fortuna report. Re-validate any signature released under this guard against the node's tip once more confirmations accrue, and refuse to forward a signature to the aggregate/broadcast step if the underlying 404 evidence is retracted.

### Proof of Concept
1. Signer S has signed block A in tenure T at burn height H (`mark_locally_accepted`/`signed_self`), recorded via `get_signed_conflicts`.
2. A single miner produces a competing burn block at height H, causing the node to momentarily report tenure T's sortition as 404/orphaned while its `get_peer_info` tip is exactly at H (satisfying the "at or past" check in `conflict_still_blocks`'s node-liveness path) [1](#0-0) .
3. A miner proposes block B, conflicting with A at the same height in a different tenure; S's conflict guard treats A as dead ("a reorg moved past it. That is proof it is dead") and signs B [2](#0-1) .
4. The original fork containing T reasserts itself as canonical (the competing block was itself orphaned moments later, a routine shallow-reorg outcome).
5. Signer S has now released valid signatures over both A and B at the same height — a double-sign — and if enough peer signers experienced the same race, both blocks can independently reach the 70% signing threshold.

*Caveat:* I was not able to retrieve the full source body of `conflict_still_blocks`/`reorg_permit_stands` in `stacks-signer/src/v0/signer.rs` before the iteration limit was reached; this finding is built on the authoritative design description in `docs/signer-flows.md` (which explicitly documents the trust model and anchors these exact function names) plus the directly-verified `chainstate/mod.rs` confirmation-based heuristic and `signerdb.rs` cross-tenure conflict semantics. A session with further tool access could pull the exact `conflict_still_blocks` implementation to confirm the height-comparison operator precisely.
