### Title
Stale-epoch withdraw receipts escape the `stopEpochWithDuration` loss haircut and can freeze later claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` computes a single `lossRecoveryPrice` over the **aggregate** `pendingWithdraws` basis but stores it under `lossRecoveryPriceByEpoch[epochNumber]`, i.e. only the current epoch. A lender whose receipt was created in an earlier epoch (and simply never claimed) is looked up only via `lastWithdrawRequest[_user]` → that older epoch → price 0, so they are paid at par through `_claimFundedWithdrawRequest`. They escape the pro-rata loss that `previewLossAdjustedWithdrawFunds` explicitly assigned to the whole pending bucket, and the haircutted funds can become insufficient for the in-epoch claimant, whose claim then reverts.

### Finding Description
In `IdleCreditVault.sol`:

- `requestWithdraw` records receipts per user **and** per epoch (`withdrawsRequestsByEpoch[_user][currentEpoch]`), but `pendingWithdraws` is a single global aggregate across all epochs (lines 277–294). `lastWithdrawRequest[_user]` stores only the user's most recent request epoch (line 282).
- At `stopEpochWithDuration(_lossAmount)`, `previewLossAdjustedWithdrawFunds` spreads the loss pro-rata over `activeBasis + pendingBasis`, where `pendingBasis = pendingWithdraws` includes receipts from *all* prior epochs (lines 440–460). The borrower only funds `pendingToFund = pendingBasis * price`.
- `collectWithdrawFunds` then sets `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws` (lines 411–430).
- On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 789–801). A user whose receipt lives in an **older** epoch has a zero price there, falls through to `_claimFundedWithdrawRequest`, and — because `epochNumber > lastWithdrawRequest[_user]` — is paid `withdrawsRequests[_user]` **at par** (lines 319–349).
- The guard at lines 263–271 only blocks a *new request* when the user's *own* previous epoch had a loss price; it does nothing for a user whose old-epoch receipt simply rides through a later epoch's haircut.

Broken invariant: fair loss socialization. The loss was priced assuming all pending receipts share it, but only current-epoch receipts actually bear it. The old-epoch receipt is effectively "marked public" (treated as a fully-funded claim) when it was included in the shared haircutted bucket — the direct analog of a private response cached and served as public.

### Impact Explanation
- The stale-epoch claimant withdraws 1:1 while the current-epoch claimant is paid `basis * price`.
- Strategy underlyings received = `pendingBasis * price`. Outflow needed = `stale + curBasis * price` > received (since `price < 1` and `stale > 0`). If the stale claimant goes first, the current-epoch claimant's `safeTransfer` inside `_transferFundedClaim` reverts on insufficient balance — their recovery is temporarily frozen (until new borrower funds arrive, which in a stressed/loss epoch may be never), and they absorb more than their pro-rata share of the loss.
- Example: stale receipt 900k, current receipt 100k, loss price 50%. Borrower funds 500k. Stale claimant takes 900k... (payout capped by balance → takes 500k, still > their fair 450k) or if ordering is reversed, current claimant gets 50k and stale claimant then finds only 450k < 900k and also reverts. Either way, solvency of the receipt bucket is broken by `stale * (1 - price)` — up to 450k in this example.

### Likelihood Explanation
Requires: (a) a lender requests a normal withdraw and intentionally lets it sit unclaimed past one epoch — trivially achieved since claims are open indefinitely once `epochNumber > lastWithdrawRequest`; (b) another lender requests in a later epoch; (c) the manager/borrower calls `stopEpochWithDuration` with a partial loss, which is a normal, honest actor flow. Any KYC-passing lender can be the attacker (they need only make the earlier request and time their claim). No privileged collusion needed; the mis-pricing is deterministic.

### Recommendation
Apply the stored `lossRecoveryPrice` to **all** pending receipts included in `pendingBasis`, not just `epochNumber`-keyed ones. Options: keep a global "pending receipts created before cutoff" flag, record the haircut against each contributing epoch, or maintain a `pendingReceiptsCutoffEpoch`/`maxPendingEpoch` marker so `_claimLossAdjustedWithdrawRequest` checks `lossRecoveryPriceByEpoch` for every epoch ≤ the user's receipt epoch that had a nonzero price. Alternatively, force stale receipts to be claimed before allowing a new epoch to accumulate pending basis (extend the lines 263–271 guard to block *any* unclaimed prior receipt when a loss is priced).

### Proof of Concept
Foundry fork sketch (`test/` style, epoch CDO + `IdleCreditVault`):

```solidity
// setup: epoch CDO with IdleCreditVault strategy, borrower funded, APR > 0
// epoch N (running):
cdo.depositAA(staleUser, 900_000e6);          // stale attacker, KYC'd lender
vault.requestWithdraw via cdo -> withdraw(900_000e6) // receipt in epoch N
// manager stopEpoch -> epochNumber becomes N+1; staleUser does NOT claim
// epoch N+1:
cdo.depositAA(victim, 100_000e6);
victim requests withdraw(100_000e6);          // pendingWithdraws = 1_000_000
// honest manager stops epoch with a loss:
cdo.stopEpochWithDuration(dur, interest, loss = 500_000e6);
//   previewLossAdjustedWithdrawFunds -> pendingToFund = 500_000 (price = 0.5)
//   collectWithdrawFunds(500_000) -> lossRecoveryPriceByEpoch[N+1] = 0.5e18, pendingWithdraws = 0
// attack:
vm.prank(cdo); // staleUser claim path
vault.claimWithdrawRequest(staleUser);
//   lastWithdrawRequest[stale]=N -> priceByEpoch[N]==0 -> _claimFundedWithdrawRequest pays full 900k...
//   capped by balance=500k: staleUser receives 500k (fair share was 450k)
// then:
vault.claimWithdrawRequest(victim); // tries to pay 100k*0.5=50k, balance=0 -> safeTransfer reverts
// victim's 50k recovery is frozen; stale user over-received by 50k vs pro-rata
```

Key assertions: `underlyingToken.balanceOf(staleUser)` increases by `min(900k, funded)`, `victim`'s claim reverts, and `lossRecoveryPriceByEpoch[N] == 0` while `lossRecoveryPriceByEpoch[N+1] == 0.5e18` even though the price was computed over both receipts' basis.
