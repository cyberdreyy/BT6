Any address can set an arbitrary `receiver` for `requestRedeem`.

### Title
Single blacklisted/malicious `receiver` in a batched redeem request reverts and freezes an entire `solveRequestsVault` batch - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`requestRedeem` lets `msg.sender` specify an arbitrary `receiver` with no ownership/approval check on that address [1](#0-0) . When the guardian later batches multiple pending redeem requests into a single `solveRequestsVault` call, `_solveRequestsVault` iterates the array and, for each non-expired redeem, performs a raw `token.safeTransfer(request.receiver, ...)` with no per-request try/catch or fallback [2](#0-1) . If one `receiver` is a USDC-blacklisted address, that transfer reverts and unwinds the whole transaction, blocking every other user's redeem/deposit in the same batch.

### Finding Description
The vulnerability path is `requestRedeem(token, unitsIn, minTokensOut, solverTip, deadline, maxPriceAge, isFixedPrice, receiver)` → guardian calls `solveRequestsVault` → `_solveRequestsVault` → `_solveRedeemVaultAutoPrice` / `_solveRedeemVaultFixedPrice`.

- `requestRedeem` is callable by "anyoneButVault" and only validates `receiver != address(0)` via `_validateRequest`, with no check that `receiver == msg.sender` [3](#0-2) . A user can set `receiver` to any known USDC-blacklisted address (there are 200+ publicly known ones per the underlying report), or one that could become blacklisted after the request is created but before it is solved.
- Inside `_solveRequestsVault`, requests are processed in an unprotected `for` loop with no per-iteration try/catch, only per-guard checks (price age, hash validity, amount bounds) that emit events and `return 0` on failure — they do not guard against a downstream transfer revert [4](#0-3) .
- Critically, in the "not expired" branches of `_solveRedeemVaultAutoPrice`/`_solveRedeemVaultFixedPrice`, tokens are sent via a bare `token.safeTransfer(request.receiver, ...)` [5](#0-4) [6](#0-5) , unlike the expired/refund branch of the same functions which uses `_transferWithFallback`, a helper that falls back to the original requester if the transfer to `receiver` fails [7](#0-6) . This asymmetry is the broken invariant: the refund path anticipated transfer failure and mitigated it, but the "happy path" solve did not.
- Because the whole batch is a single atomic transaction, any revert unwinds all other users' state changes (units already burned via `exit`, tips accrued, etc.), so no other request in that batch can be solved. The guardian must first detect and manually exclude the malicious/blacklisted request before resubmitting, which delays settlement for all co-batched users.

### Impact Explanation
This causes a temporary freeze of other users' pending redeem/deposit funds and unclaimed yield within the same `solveRequestsVault` batch, since the transaction reverts and no requests in the batch are processed until the guardian identifies and excludes the offending request. This matches Immunefi's Medium severity classification for temporary freezing of user funds. It does not cause permanent loss, but it delays settlement and can be triggered by an ordinary user (no privileged role, no oracle/keeper compromise required) simply by choosing a known-blacklisted (or later-blacklisted) `receiver` address for `requestRedeem`.

### Likelihood Explanation
Feasible for any ordinary user: `requestRedeem`/`requestRedeem(...,receiver)` are public, unauthenticated calls that accept `token` (must have `asyncRedeemEnabled`, e.g. a USDC-like blocklist token) and any non-zero `receiver`. The attacker needs only enough units to submit a minimal redeem request naming a known-blacklisted address as `receiver`, then wait for the guardian to include it in a batch with other pending requests via `solveRequestsVault`. This requires the underlying token to support blocklisting (USDC does) and that async redeems for that token are enabled and solved in batches — both realistic, in-scope conditions per the report's asset list (USDC).

### Recommendation
Wrap the token transfer to `request.receiver` in `_solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice` (the non-expired/solved branches) with the same `_transferWithFallback` pattern already used in the refund branches, or process each request via try/catch inside `_solveRequestsVault` so a single failing transfer only skips/defers that one request (emitting a "solve failed" event) instead of reverting the entire batch.

### Proof of Concept
1. Fork mainnet at a block where a known address `B` is on USDC's blocklist (e.g., one of the addresses in `TokenUtils.sol`'s referenced blocklist).
2. Deploy/attach to `ProvisionerV2`/`MultiDepositorVault` with USDC as an enabled async-redeem token.
3. As user A (attacker), acquire vault units and call `requestRedeem(USDC, unitsIn, minTokensOut, 0, deadline, maxPriceAge, false, B)` where `B` is blacklisted.
4. As user C (victim), separately call `requestRedeem(USDC, unitsInC, minTokensOutC, 0, deadline, maxPriceAge, false, C)` with a valid receiver.
5. As guardian, call `solveRequestsVault(USDC, [requestA, requestC], "", "")`.
6. Assert the whole transaction reverts (USDC transfer to `B` reverts due to blocklist), and that `requestC`'s hash remains `true` in `asyncRequestHashes`/unprocessed — i.e., victim C's legitimate redeem could not be solved in that batch, demonstrating the freeze, even though C's request had nothing wrong with it.

    function _solveRequestsVault(IERC20 token, RequestV2[] calldata requests) internal {
        // Requirements: vault is not paused in the priceAndFeeCalculator
        require(!PRICE_FEE_CALCULATOR.isVaultPaused(MULTI_DEPOSITOR_VAULT), Aera__PriceAndFeeCalculatorVaultPaused());

        // Interactions: get price age
        uint256 priceAge = block.timestamp - PRICE_FEE_CALCULATOR.getVaultPriceTimestamp(MULTI_DEPOSITOR_VAULT);

        uint256 solverTip;
        RequestV2 calldata request;

        uint256 length = requests.length;
        TokenDetailsV2 memory tokenDetails = tokensDetails[token];
        bool depositsExist;
        for (uint256 i = 0; i < length; i++) {
            request = requests[i];
            if (_isRequestTypeDeposit(request.requestType)) {
                // Requirements: async deposit is enabled
                if (!tokenDetails.asyncDepositEnabled) {
                    // Log async deposit disabled event
                    emit AsyncDepositDisabled(i);
                    continue;
                }

                if (!depositsExist) {
                    depositsExist = true;
                    token.forceApprove(MULTI_DEPOSITOR_VAULT, type(uint256).max);
                }

                if (_isRequestTypeAutoPrice(request.requestType)) {
                    // Requirements + Effects + Interactions: solve auto price deposit
                    solverTip += _solveDepositVaultAutoPrice(
                        token, tokenDetails.asyncDepositMultiplier, request, priceAge, i
                    );
                } else {
                    // Requirements + Effects + Interactions: solve fixed price deposit
                    solverTip += _solveDepositVaultFixedPrice(
                        token, tokenDetails.asyncDepositMultiplier, request, priceAge, i
                    );
                }
            } else {
                // Requirements: async redeem is enabled
                if (!tokenDetails.asyncRedeemEnabled) {
                    // Log async redeem disabled event
                    emit AsyncRedeemDisabled(i);
                    continue;
                }

                if (_isRequestTypeAutoPrice(request.requestType)) {
                    // Requirements + Effects + Interactions: solve auto price redeem
                    solverTip += _solveRedeemVaultAutoPrice(

                    solverTip += _solveRedeemVaultFixedPrice(
                        token, tokenDetails.asyncRedeemMultiplier, request, priceAge, i

                }
            }

    /// @notice Validates common request parameters shared by requestDeposit and requestRedeem
    /// @param receiver The address receiving funds when request is solved
    /// @param solverTip The tip offered to the solver
    /// @param deadline Timestamp until which the request is valid
    /// @param isFixedPrice Whether the request is a fixed price request
    function _validateRequest(address receiver, uint256 solverTip, uint256 deadline, bool isFixedPrice) internal view {
        // Requirements: receiver is not zero address
        require(receiver != address(0), Aera__ZeroAddressReceiver());
        // Requirements: deadline is in the future and not too far in the future
        require(deadline > block.timestamp, Aera__DeadlineInPast());
        unchecked {
            require(deadline - block.timestamp <= MAX_SECONDS_TO_DEADLINE, Aera__DeadlineTooFarInFuture());
        }
        // Requirements: vault is not paused in the PriceAndFeeCalculator
        require(!PRICE_FEE_CALCULATOR.isVaultPaused(MULTI_DEPOSITOR_VAULT), Aera__PriceAndFeeCalculatorVaultPaused());
        // Requirements: fixed price requests cannot have a solver tip
        require(solverTip == 0 || !isFixedPrice, Aera__FixedPriceSolverTipNotAllowed());
