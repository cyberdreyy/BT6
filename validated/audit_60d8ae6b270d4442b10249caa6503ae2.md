### Title
Unbounded concurrent `/exec` requests against a session can exhaust the shared session-server's goroutines/FDs, denying terminal service to all jobs on that runner - (File: session/session.go)

### Summary
`Session.execHandler` performs a blocking wait (up to 1 minute) on `terminalSetCh` for every incoming `/exec` WebSocket-upgrade request, and this handler is served by a single shared `http.Server` (`session/server.go`) that multiplexes ALL active job sessions on the runner host. A job author who holds the (correctly-scoped) session token for their own job can open many concurrent `/exec` connections before `SetInteractiveTerminal` is called, each pinning a goroutine + file descriptor for up to a minute, with no per-session or global rate/connection limiting anywhere in the path.

### Finding Description
`session.Server` (`session/server.go:50-90`) creates exactly one `http.Server{}` per runner process, with no `ReadTimeout`, `WriteTimeout`, `MaxHeaderBytes`, or connection-count limiter configured, and dispatches every inbound connection to `handleSessionRequest` (`session/server.go:133-145`), which looks up the target `Session` by URL and forwards to that session's `mux`. Because there is only one listener/`http.Server` for the entire runner (`net.Listen` + `s.httpServer.Serve` in `NewServer`/`Start`), every job's session shares the same underlying goroutine pool and connection capacity [1](#0-0) .

`Session.execHandler` (`session/session.go:146-191`) requires the request to already pass `withAuthorization`, which checks the per-session random token (`s.Token != r.Header.Get("Authorization")`) before any further processing [2](#0-1) . So an outside attacker without the token cannot reach `execHandler` at all - the auth check happens strictly before the blocking wait, defeating the "unauthorized" framing of the question. However, the legitimate holder of that token (the pipeline author whose job has the web terminal feature enabled, per `createSession` in `commands/multi.go:1309-1335`) can freely open many concurrent WebSocket-upgrade requests to their own `/exec` endpoint. Each such request:
- passes `websocket.IsWebSocketUpgrade` check,
- creates a `context.WithTimeout(r.Context(), time.Minute)`,
- blocks in `select { case <-s.terminalSetCh: case <-ctx.Done(): }` if `SetInteractiveTerminal` hasn't fired yet [3](#0-2) .

Nothing in `execHandler`, `withAuthorization`, `setMux`, or `Server.handleSessionRequest` limits the number of concurrent in-flight requests per session or globally. Since the whole runner's session traffic (for potentially many concurrently running jobs) flows through the single shared `http.Server`, flooding one session's `/exec` endpoint with many parallel pending upgrades consumes goroutines/file descriptors from the same process-wide pool used to serve every other job's terminal session on that runner host.

### Impact Explanation
This is a denial-of-service against the session/terminal subsystem, not the job execution itself: it can starve the shared session server's goroutines/FDs, delaying or preventing terminal WebSocket accept for concurrently running jobs on the same runner instance (including the attacker's own legitimate later `SetInteractiveTerminal` call, if resources are exhausted before it fires). Impact is bounded to interactive-terminal availability (a debug feature) and does not affect job script execution, sandbox isolation, or secret confidentiality; each pending request is capped at the 1-minute context timeout, so the effect is self-healing rather than permanent, and OS-level connection limits determine actual severity.

### Likelihood Explanation
Requires: (1) the runner has `[session_server]` configured (feature opt-in), (2) the executor supports interactive web terminals, (3) the attacker is the author of a job that has such a session created for it (i.e., they legitimately obtain a valid `Token`/`Endpoint` for their own job, as GitLab exposes this to users who trigger "Debug" web terminals). Given a valid token, sending many parallel WebSocket-upgrade requests is trivial and fully reproducible; no privilege beyond normal pipeline/job-terminal access is needed.

### Recommendation
Add per-session concurrency limiting in `execHandler` (e.g., a semaphore/counter capping simultaneous pending `/exec` connections per `Session`, rejecting excess with `429`/`503` immediately instead of queuing goroutines), and/or configure the shared `http.Server` in `session/server.go` with sane `ReadHeaderTimeout`/`MaxHeaderBytes` and a bounded listener (e.g. `netutil.LimitListener`) to cap total concurrent connections across all sessions on the runner host.

### Proof of Concept
Go integration test in `session/session_test.go`:
1. Create a `Session` via `NewSession`, do NOT call `SetInteractiveTerminal`.
2. Launch N (e.g. 5,000) concurrent goroutines making authorized WebSocket-upgrade requests to `<endpoint>/exec` with the correct `Authorization` token, each expected to block up to 1 minute.
3. Assert: (a) process goroutine count / open FD count grows roughly linearly with N and is unbounded by any session-level guard (demonstrating the missing limiter); (b) after calling `SetInteractiveTerminal`, verify how quickly a legitimate single new `/exec` request can obtain `terminalConn` - if system resources (goroutines/FDs) are near exhaustion from the flood, this call is delayed or fails, violating the expectation that the job's own terminal attach should complete promptly.

func (s *Session) withAuthorization(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		logger := s.log.WithField("uri", r.RequestURI)
		logger.Debug("Endpoint session request")

		if s.Token != r.Header.Get("Authorization") {
			logger.Error("Authorization header is not valid")
			http.Error(w, http.StatusText(http.StatusUnauthorized), http.StatusUnauthorized)
			return
		}

		next.ServeHTTP(w, r)
	})
}
