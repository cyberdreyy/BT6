### Title
Builder index reuse allows a settled bid payment to double-spend into a newly registered builder's balance - (File: `specs/gloas/beacon-chain.md`)

### Summary
The Gloas builder registry (`state.builders`) reuses freed slots by `BuilderIndex`. When a builder exits and is swept to zero balance, `get_index_for_new_builder` immediately treats its slot as reusable, checking only `withdrawable_epoch <= current_epoch and balance == 0`. It does not check whether the exited builder still has an outstanding `BuilderPendingPayment` or `BuilderPendingWithdrawal` entry referencing that same `builder_index`. Because those payment records only carry the numeric `builder_index` (and a separately-captured `fee_recipient`), when they finally settle they will debit `state.builders[builder_index].balance` of whatever builder currently occupies that slot — which, after reuse, is a different, unrelated builder.

### Finding Description
A builder's payment record is created at bid time and only settles up to ~2 epochs later: [1](#0-0) 

The pending payment is later promoted to a `BuilderPendingWithdrawal` (still keyed only by `builder_index`) either by `settle_builder_payment` or `process_builder_pending_payments`: [2](#0-1) [3](#0-2) 

When that withdrawal is finally applied, the beacon state decreases the balance of whatever builder currently sits at `builder_index`, not necessarily the original bidder: [4](#0-3) 

Meanwhile, a builder's index becomes reusable purely based on `withdrawable_epoch` and `balance == 0`, with no check for outstanding payment/withdrawal entries still pointing at that index: [5](#0-4) 

The spec's own note acknowledges index reuse is deliberate and explicitly warns implementers to account for it, which suggests the authors were aware of aliasing but the guard implemented (`get_pending_balance_to_withdraw_for_builder`) is only enforced at *exit-initiation* time, not enforced again at slot-reuse time: [6](#0-5) [7](#0-6) 

The full-balance sweep (`get_builders_sweep_withdrawals`) withdraws the *entire* `builder.balance` once `withdrawable_epoch <= epoch and balance > 0`, with no reservation of funds tied to an outstanding pending payment/withdrawal for that same builder: [8](#0-7) 

Putting this together: a builder X can (1) place a winning bid, creating a `BuilderPendingPayment` keyed to `builder_index = X` with `fee_recipient` captured directly in the record; (2) initiate exit once that specific payment has *not yet* accrued balance obligations (or accrue a new bid after exit initiation, since `process_execution_payload_bid` does not gate on `is_active_builder`); (3) be fully swept to zero balance via `get_builders_sweep_withdrawals`, which pays out X's *entire* current balance (including the amount reserved to cover the still-pending bid) to X's own `execution_address`; (4) have its slot immediately reused by a new builder Y via `get_index_for_new_builder`/`add_builder_to_registry`, since the only checks are `withdrawable_epoch <= epoch` and `balance == 0`; (5) later, when X's original pending payment finally settles (up to ~2 epochs of latency built into `builder_pending_payments`), `apply_withdrawals` decreases `state.builders[X].balance`, which is now Y's balance, and issues an on-chain `Withdrawal` object to X's `fee_recipient` for the bid amount.

The net effect breaks the equality that a builder's balance decrease must correspond to that same builder's own committed payment: X receives its bid payment a second time (once via the full sweep of its balance, once via the delayed pending withdrawal payout), while Y's freshly-deposited balance is silently debited by that same amount with no action or authorization from Y. This is Gwei paid to a non-owner (X) and Gwei destroyed/misdirected from Y's account.

### Impact Explanation
This falls into the Critical impact bucket: "Gwei created, destroyed or paid to a non-owner." A former builder can extract funds twice — once through the ordinary full-balance sweep upon exit, and again through a delayed pending-payment settlement that, due to index reuse, is charged against an unrelated builder's balance rather than the original bidder's (now-zero) balance. The victim (a newly registered builder) loses funds it never committed to any payment, with no coalition, malicious peer, or client bug required — purely a consequence of how the spec processes state transitions.

### Likelihood Explanation
This requires no external actors, no coalition, and no execution-layer bug: a single builder controls the timing of its own bid, its own exit request, and can predict when it will be swept and when its old payment records will settle (both are deterministic functions of state). The only preconditions are (a) placing a bid that creates a payment record, (b) initiating exit (which is only checked to have zero pending balance for that builder_index *at the moment of the exit request*, not thereafter — and `process_execution_payload_bid` does not block bids from a builder that has already initiated exit, since it checks `version`/`can_builder_cover_bid`/signature but not `is_active_builder`), and (c) the natural ~epoch-scale latency between a bid, its payment settlement, and the sweep/slot-reuse cycle, all of which are ordinary spec-following behaviors reachable by a single participant.

### Recommendation
Do not treat a builder's index as reusable purely based on `withdrawable_epoch <= current_epoch and balance == 0`. `get_index_for_new_builder` (and/or `process_builder_deposit_request`) should additionally require `get_pending_balance_to_withdraw_for_builder(state, index) == 0` before permitting reuse, mirroring the check already used to gate exit initiation. Alternatively, `BuilderPendingWithdrawal`/`BuilderPendingPayment` settlement should not touch `state.builders[builder_index].balance` at all when paying out to a captured `fee_recipient` (since the destination address is already fixed at bid time), removing the aliasing hazard entirely.

### Proof of Concept
1. Builder X (index `i`) submits a winning `ExecutionPayloadBid` with `value = V > 0`; `process_execution_payload_bid` records `state.builder_pending_payments[SLOTS_PER_EPOCH + slot % SLOTS_PER_EPOCH]` with `builder_index = i`, `fee_recipient = X`.
2. Before that payment entry reaches quorum/settlement, X submits a `BuilderExitRequest`. At this instant `get_pending_balance_to_withdraw_for_builder(state, i)` may still be `0` if the payment hasn't accrued weight yet, or X can further submit new low-value bids after exit initiation since `process_execution_payload_bid` never checks `is_active_builder`.
3. `get_builders_sweep_withdrawals` eventually sweeps X once `withdrawable_epoch <= epoch and balance > 0`, paying X's entire current `balance` (which still nominally "backs" the pending bid) to `X.execution_address`, and setting `builders[i].balance = 0`.
4. With `withdrawable_epoch <= current_epoch` and `balance == 0`, `get_index_for_new_builder` returns `i` for the next new builder deposit. Builder Y registers via `process_builder_deposit_request`, occupying `builders[i]` with a fresh nonzero balance.
5. `process_builder_pending_payments` (or `settle_builder_payment`) later promotes X's original payment to `state.builder_pending_withdrawals`, still keyed `builder_index = i`, `fee_recipient = X`.
6. `get_builder_withdrawals` → `apply_withdrawals` executes: it issues a `Withdrawal(amount=V, address=X)` to the execution layer (X gets paid a second time), and decreases `state.builders[i].balance` (now Y's balance) by `V` — debiting Y for a payment Y never made or agreed to.

Note: I was not able to fully verify the exact body of `can_builder_cover_bid` and `is_active_builder` in this session (only their headers/other call sites were retrieved), so I cannot rule out an additional balance-reservation mechanism inside `can_builder_cover_bid` that might reduce (but, per the sweep logic shown, would not eliminate) the double-spend window. Confirming or refuting that would require reading those two function bodies directly, which is recommended as a follow-up before treating this as fully proven.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
            withdrawal_index += 1

        builder_index = (builder_index + 1) % len(state.builders)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))

def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
