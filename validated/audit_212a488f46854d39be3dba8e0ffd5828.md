Based on my research, this scenario is not a vulnerability — it's the exact, already-documented and already-tested design of the system.

**Analysis:**

The question's premise is correct on one point: `PubkeyHashMismatch`/`IrrecoverablePubkeyHash` checks in `GlobalStateView::check_proposal` (v2) and `SortitionsView::check_proposal` (v1) only verify that `Hash160::from_data(&miner_pk.to_bytes_compressed())` equals the winning `current_miner_pkh`/`miner_pkh`. [1](#0-0) [2](#0-1) 

This check is trivially satisfiable twice by the legitimate winning key signing two distinct block bodies — high-S signatures are explicitly allowed for miner signatures (unlike transactions), so malleability isn't even required; the same key can simply sign two different headers. [3](#0-2) 

However, the codebase already documents and tests exactly this scenario as an expected equivocation case, with the **uniqueness/conflict guard** — not the pkh check — as the designated backstop. Per `docs/signer-flows.md`, the `DuplicateBlockFound` check in `check_proposal`/`validate_tenure_change_payload` only runs at proposal arrival and does not re-run at pre-commit or signing time, which is explicitly why "section 5's own-tenure conflict guard" exists to cover the gap. [4](#0-3) 

The actual signing-time guard lives in `stacks-signer/src/v0/signer.rs`: before signing, the signer queries `get_signed_conflicts` for any signed/pre-committed sibling at the same or higher height in *any* tenure and refuses to sign while that conflict is fresh and still live (via `conflict_still_blocks` and `reorg_permit_stands`). [5](#0-4) 

This is directly proven by existing tests, including `signer_refuses_to_sign_second_sibling_tenure_start`, which constructs exactly the attack the question describes — two sibling tenure-start blocks from the same winning miner key — and asserts that block B is pre-committed but never signed because the signer already signed conflicting sibling A. [6](#0-5) [7](#0-6) 

The test module's own doc comment explicitly frames this as the known async-validation timing gap where two siblings can both reach pre-commit, but states the signature-level guard (not the pkh check) is what "stops a single winning miner from obtaining two signer certificates for one sortition." [6](#0-5) 

This matches precisely what the audit question asks to verify — that the UNIQUENESS guard, not the pkh check, is the actual backstop — and confirms the guard is present, functioning, and covered by regression tests (`stale_sibling_still_refused_when_canonical_tip_at_height`, `stale_sibling_replaced_when_canonical_tip_below`). [8](#0-7)

        // A pre-commit may be superseded by a competing proposal at the same height (e.g. a
        // re-proposed tenure-start block after the first failed to reach consensus), but a
        // signature must not be superseded while it's still "fresh". A signed block at the
        // same or higher height in ANY tenure is a conflict: two blocks at the same height are
        // siblings no matter which tenure they belong to (e.g. the next tenure's tenure-start
        // block conflicts with the current tenure's block at the same height). Blocks in
        // tenures whose reorg we sanctioned under the reorg-timing rules are excluded, but
        // only while the sortition the permit was granted to is still canonical
        // (`check_parent_tenure_choice` records the permit, `reorg_permit_stands` re-derives
        // its validity from the node); every other question about whether a conflict is
        // still live is derived from the node in `conflict_still_blocks`.
        //
        // Unlike the chainstate check above, a refusal here is "for now" rather than a
        // broadcast rejection: a later pre-commit re-evaluation may still sign the block once
        // the conflicting signature has gone stale.
        let conflicts = match self
            .signer_db
            .get_signed_conflicts(block_info.block.header.chain_length, &block_hash)
        {
            Ok(conflicts) => conflicts,
            Err(e) => {
                warn!("{self}: Failed to query the signed blocks. Refusing to sign block {block_hash}: {e:?}");
                return;
            }
        };
        let freshness_cutoff = get_epoch_time_secs().saturating_sub(
            self.proposal_config
                .tenure_last_block_proposal_timeout
                .as_secs(),
        );
        // A fresh signature only blocks while the block it covers could still be part of the
        // chain: see `conflict_still_blocks`, which asks the node whether it is. Check
        // freshness first: it is a local timestamp comparison, while `reorg_permit_stands`
        // and `conflict_still_blocks` each query the node, so stale conflicts cost no
        // round-trips.
        if let Some(conflict) = conflicts.iter().find(|conflict| {
            conflict.last_endorsed > freshness_cutoff
                && !self.reorg_permit_stands(stacks_client, conflict)
                && self.conflict_still_blocks(
                    stacks_client,
                    conflict,
                    block_info.block.header.chain_length,
                )
        }) {
            warn!(
                "{self}: Reached the pre-commit threshold for a block, but we have recently signed or accepted a different block at the same or higher height. Refusing to sign.";
                "signer_signature_hash" => %block_hash,
                "block_height" => block_info.block.header.chain_length,
                "conflicting_signer_signature_hash" => %conflict.signer_signature_hash,
                "conflicting_block_height" => conflict.stacks_height,
                "conflicting_consensus_hash" => %conflict.consensus_hash,
            );
            return;
