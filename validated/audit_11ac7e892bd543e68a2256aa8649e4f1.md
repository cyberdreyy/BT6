### Title
Post-default withdraw requests are paid at par from a recovery reserve that never accounted for them, draining funds reserved for defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
This mirrors the reported bug class: a value used inside a critical accounting computation is not constrained to the set of claims the computation actually covered. In `IdleCreditVault`, `defaultRecoveryReserve` is sized once inside `finalizeDefaultRecovery` against `totalBasis = activeBasis + pendingBasis` (`contracts/strategies/idle/IdleCreditVault.sol:680-692`). Yet after `defaultRecoveryFinalized`, `requestWithdraw` still mints fresh receipts and records them in `postDefaultRequests` (`:253-257`), and `_claimPostDefaultWithdrawRequest` pays them 1:1 out of `defaultRecoveryReserve` via `_transferDefaultRecovery` (`:760-767`, `:912-917`). Those post-default claims were never part of `totalBasis`, so the reserve is spent on obligations it was never computed to cover.

### Finding Description
- `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` where `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve`, then stores `defaultRecoveryReserve = reserveAmount`. No post-finalization request can increase the reserve.
- After finalization, `requestWithdraw` (still callable by the CDO for users, i.e., tranche holders) burns `_amount` strategy tokens and sets `postDefaultRequests[_user] = _amount`. The comment states the amount is "already-haircut" because `virtualPrice` was lowered — correct for the requester — but the payout path ignores `defaultRecoveryPrice` entirely.
- `_claimPostDefaultWithdrawRequest` calls `_transferDefaultRecovery(_user, amount)` which does `defaultRecoveryReserve -= _amount` and transfers `_amount` at par. Post-default claimants therefore extract full-face payouts while defaulted-epoch claimants (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) are entitled only to `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from the same reserve.
- Consequence: the first post-default claims consume reserve earmarked for earlier defaulted receipts. When cumulative claims exceed `reserveAmount`, `defaultRecoveryReserve -= _amount` reverts underflow, permanently freezing the tail of defaulted-epoch claimants' recovery; equivalently, earlier claimants get their correct share and later ones get zero — a broken "one receipt, pro-rata payout" invariant.

### Impact Explanation
Direct theft and permanent freezing of unclaimed yield/recovery. Example: recovery finalized with basis 1,000 and reserve 500 (`recoveryPrice = 0.5e18`). A user with a pre-default claim basis of 400 requests withdraw post-default: the CDO haircut gives them `postDefaultRequests = 200` (at the 0.5 virtualPrice). Claiming pays 200 at par from the reserve, leaving 300 for the remaining 600 of basis — those claimants can now only recover ~0.5 * (300/600)... i.e., their claims partially freeze once the reserve underflows. Each post-default requester recovers at 1:1 what pre-default claimants recover at `recoveryPrice`, extracting funds they never paid for.

### Likelihood Explanation
Requires a borrower default followed by `finalizeDefaultRecovery` (privileged but honest per scope) and any tranche holder calling `requestWithdraw` post-default — an unprivileged lender action that the code explicitly supports rather than blocks. No guard checks that post-default payouts fit within a reserve margin reserved for pre-default basis; `_transferFundedClaim`'s reserve-protection check (`:899-905`) only protects the reserve from *funded* claims, while post-default claims deliberately route through `_transferDefaultRecovery`. Uncertain aspect: if the CDO-side `claimWithdrawRequest` flow pulls additional underlying into the strategy for post-default claims before calling the strategy, the reserve drain may be offset — that call path in `IdleCDOEpochVariant.sol` was identified but not fully traced within available iterations.

### Recommendation
Either (a) fund post-default requests outside the reserve — pull the underlying from the CDO/borrower into the strategy at request or claim time and pay via `_transferFundedClaim` — or (b) account for them inside the reserve by incrementing `defaultRecoveryReserve` whenever a post-default receipt is created, with an explicit bound so `defaultRecoveryReserve` can never fall below the sum of still-outstanding defaulted-epoch entitlements (`basis_remaining * defaultRecoveryPrice / RECOVERY_FULL`). Add a reserve-floor check in `_transferDefaultRecovery` distinguishing claim classes.

### Proof of Concept
Foundry fork PoC sketch:
1. Deploy `IdleCDOEpochVariant` + `IdleCreditVault` on a mainnet fork; lender deposits AA/BB during buffer, `startEpoch` runs.
2. Lender A calls `requestWithdraw` (receipt minted); borrower defaults; owner triggers `_handleBorrowerDefault`/`finalizeDefaultRecovery` with `recoveryPrice < 1`.
3. Lender B (or A) calls `requestWithdraw` post-default → `postDefaultRequests` set.
4. B calls `claimWithdrawRequest` → receives `amount` at par; assert `defaultRecoveryReserve` decreased by full `amount` while A's outstanding claim `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` now exceeds `defaultRecoveryReserve` → A's claim reverts (frozen recovery).

If the CDO-side trace shows pre-funding of post-default claims, this reduces to a bookkeeping-hardening issue and should be re-scored; otherwise it is a reserve-insolvency bug.
