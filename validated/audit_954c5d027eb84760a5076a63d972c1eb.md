### Title
CPU exhaustion in `ParkedPredicateIndex::affected_by_state` — a self-destruct triggers a full linear scan of all parked-predicate blockers, enabling attacker-amplified O(n·m) work per included block/flashblock - (File: crates/execution/payload/src/validity.rs)

### Summary
`ParkedPredicateIndex` maintains a `blockers: HashMap<ValidityPredicateKey, HashSet<TxHash>>` reverse index of transactions parked on unsatisfied validity predicates (EIP-8130 `base_sendRawTransactionValidity` / builder validity ingress). `affected_by_state`, called once per included transaction during block/flashblock building, contains a selfdestruct branch that iterates **every entry of the entire `blockers` map** — not just entries for the touched address — for each account that self-destructs in that transaction's state diff.

### Finding Description
`ParkedPredicateIndex::affected_by_state` in [1](#0-0)  walks the touched-account set of a transaction's `EvmState`. For accounts marked `is_selfdestructed()`, it does not use a keyed/indexed lookup; instead it scans the whole `self.blockers` map to find any `ValidityPredicateKey::Storage` entries whose address matches:

```rust
if account.is_selfdestructed() {
    for (key, hashes) in &self.blockers {
        if matches!(key, ValidityPredicateKey::Storage(key_address, _) if key_address == address) {
            effects.affected_transactions.extend(hashes.iter().copied());
            effects.woken_buckets += 1;
        }
    }
}
```

This is a linear scan over the number of *distinct* watched storage keys across the whole pool of parked transactions, invoked once per self-destructing address per transaction. This is structurally the same bug class as the reported hickory-proto issue: an unbounded, attacker-controllable candidate set (`blockers` entries) is linearly re-scanned on every relevant event, instead of the address-keyed index that the non-selfdestruct branch already uses (`self.blockers.get(&ValidityPredicateKey::Storage(*address, *slot))`, an O(1) hash lookup, see lines 186–194 of the same file).

An attacker can grow the candidate set cheaply and then trigger the expensive scan repeatedly:
1. Submit many EIP-8130 transactions with distinct `ValidityPredicate::Storage{address, slot}` predicates that remain unsatisfied, so they get parked in `ParkedPredicateIndex` and populate many distinct buckets in `blockers` (bounded per-transaction to `DEFAULT_MAX_VALIDITY_PREDICATES = 64` [2](#0-1) , but unbounded pool-wide — nothing caps the total number of distinct `(address, slot)` buckets across all parked transactions in the pool).
2. Submit ordinary transactions that `SELFDESTRUCT` a contract account (any account, need not be watched) in each flashblock/transaction slot.

Every self-destruct then forces the builder to scan the full `blockers` map. This call site is on the sequencer/block-builder hot path used for both full-block building (`crates/execution/payload/src/builder.rs`, predicate rescan loop around lines 1413–1465) and per-flashblock building (`crates/builder/core/src/flashblocks/context.rs`, lines 1489–1494 call `predicate_index.affected_by_state(&state)` once per included transaction).

### Impact Explanation
This directly impacts the sequencer/builder's ability to build blocks/flashblocks in time. Because `affected_by_state` executes inline in the per-transaction execution loop (not bounded by the existing `predicate_eval_hard_cutoff` budget, which only bounds the *rescan* of woken transactions, not the wakeup scan itself), a moderately sized pool-wide `blockers` map combined with repeated self-destructs can materially slow down or stall block/flashblock construction — a CPU-exhaustion/DoS on block production, analogous in class (CWE-407/CWE-770, algorithmic complexity DoS) to the hickory-proto report. Severity is Medium: it degrades builder throughput/liveness rather than causing loss of funds, but it is reachable purely through unprivileged transaction submission (mempool + ordinary contract calls), matching the required "concrete... node halt" class of impact if the scan cost dominates the block-time budget.

### Likelihood Explanation
Likelihood is limited by real-world constraints: growing `blockers` to a large number of distinct storage-keyed buckets requires the attacker to keep many EIP-8130 validity-predicate transactions parked simultaneously (fee-paying, subject to a configurable per-tx max-predicate limit and a bounded validity-transaction lifetime, `DEFAULT_MAX_VALIDITY_EXPIRY_SECS = 60` [3](#0-2) ), and the pool overall is presumably size-limited by standard mempool admission (protocol pool limits observed via `gate_protocol_admission`/`guard.try_admit` in [4](#0-3) ). I could not find a specific cap on the total *number of distinct parked buckets* pool-wide (as opposed to per-transaction predicate count), so the achievable `blockers` size is bounded mainly by general mempool slot/size limits rather than a validity-specific cap — this is the residual uncertainty in this finding. Triggering self-destructs is cheap and can be repeated every flashblock. Given these caveats, likelihood is Medium.

### Recommendation
Replace the selfdestruct linear scan with an address-indexed lookup structure (e.g., a secondary `HashMap<Address, HashSet<B256 /*slot*/>>` or by indexing `blockers` keys by address prefix) so a self-destruct only touches buckets belonging to the destroyed address, achieving the same O(1)/O(k) cost the balance and per-slot branches already have. Additionally consider bounding the total number of distinct parked predicate buckets pool-wide (not just per-transaction), and account the `affected_by_state` scan cost against the existing `predicate_eval_hard_cutoff` budget so a pathological pool state cannot silently blow past the flashblock/block time budget.

### Proof of Concept
Conceptual reproduction (not executed):
1. Submit `N` valid EIP-8130 transactions via `base_sendRawTransactionValidity`, each carrying a `ValidityPredicate::Storage{address_i, slot_i, ...}` predicate against a distinct `(address_i, slot_i)` pair that is currently unsatisfied, causing each to be parked with a unique bucket in `ParkedPredicateIndex.blockers` (see `park`, [5](#0-4) ).
2. Repeatedly submit plain transactions that call `SELFDESTRUCT` on arbitrary (even unrelated) contract accounts.
3. Each such transaction's post-execution `affected_by_state` call ( [6](#0-5) ) iterates all `N` buckets in `blockers` looking for a match, costing O(N) instead of O(1); with `M` self-destructing transactions in the block/flashblock window, aggregate scanning cost is O(N·M), growing unboundedly with attacker-controlled `N` and `M`, unlike the O(1) per-slot/O(1) per-balance lookups used elsewhere in the same function.

    pub fn affected_by_state(&self, state: &EvmState) -> StateChangeEffects {
        let mut effects = StateChangeEffects::default();
        for (address, account) in state {
            if account.info.balance != account.original_info().balance
                && let Some(hashes) = self.blockers.get(&ValidityPredicateKey::Balance(*address))
            {
                effects.affected_transactions.extend(hashes.iter().copied());
                effects.woken_buckets += 1;
            }

            // Selfdestruct can clear slots that were not loaded during this execution. Wake every
            // storage blocker for the account so those predicates are re-read from committed state.
            if account.is_selfdestructed() {
                for (key, hashes) in &self.blockers {
                    if matches!(key, ValidityPredicateKey::Storage(key_address, _) if key_address == address)
                    {
                        effects.affected_transactions.extend(hashes.iter().copied());
                        effects.woken_buckets += 1;
                    }
                }
            } else {
                for (slot, value) in &account.storage {
                    if value.is_changed()
                        && let Some(hashes) =
                            self.blockers.get(&ValidityPredicateKey::Storage(*address, *slot))
                    {
                        effects.affected_transactions.extend(hashes.iter().copied());
                        effects.woken_buckets += 1;
                    }
                }
            }
        }
        effects
    }
