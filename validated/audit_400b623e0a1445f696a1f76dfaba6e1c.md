## Title
Multisig confirmations from removed members remain counted toward the threshold, allowing requests to execute below the live-member quorum — (File: `multisig2/src/lib.rs`)

## Summary
`MultiSigContract::delete_member` only purges requests **authored by** the removed member; it never scans the `confirmations` map to strip that member's votes from requests authored by *other* members. Since `confirm()` counts the raw size of the stored `HashSet<String>` in `confirmations` against `num_confirmations`, a stale vote cast by a member before removal still counts after removal, letting a request execute with fewer live-member approvals than the configured threshold.

## Finding Description
The binding that must hold is:

```
confirmations counted for request R  ==  confirmations from accounts currently in `members`
```

`confirm()` enforces the threshold purely by set size: [1](#0-0) 

`delete_member` removes only the requests the deleted member *authored*, and cleans `num_requests_pk`, but does not touch `confirmations` entries belonging to requests authored by other members that this member had already confirmed: [2](#0-1) 

Compare with `remove_request`, which is the only other place `confirmations` are cleaned, and it operates per-request, not per-member: [3](#0-2) 

Because of this gap, a member's `String` identity persists inside the `confirmations: LookupMap<RequestId, HashSet<String>>` entry for any request they confirmed before being removed via `DeleteMember`. `assert_valid_request` (called by `confirm`) only validates that the *current caller* is a live member — it never re-validates the members already present in the stored confirmation set: [4](#0-3) 

So the post-removal state diverges from reality: `confirmations.len()` includes ghost votes from accounts no longer in `members`, while the true "live confirmations" is strictly smaller.

## Impact Explanation
This breaks a settlement/authorization binding explicitly called out as in-scope ("confirmations counted versus live members"). A malicious or compromised member can cast a confirmation on a damaging request (e.g. `Transfer`, `AddKey`, `FunctionCall`) and then be legitimately removed by the remaining members (for being compromised, malicious, or simply rotated out). The removal does not retract their earlier vote. If the removal reduces membership at all, or simply leaves the ghost vote in place, the remaining live members can unknowingly reach `num_confirmations` with fewer real, currently-authorized approvals than the multisig's policy requires — e.g. a 3-of-4 multisig can end up executing a `Transfer` with only 2 live confirmations plus 1 phantom vote from an account that has since been stripped of its key and membership. This is exactly the Critical impact category: "a multisig request executed below threshold," which for a multisig custodying NEAR/wNEAR/other assets translates directly into unauthorized fund movement, unauthorized key addition, or unauthorized contract deployment.

## Likelihood Explanation
The precondition (a member confirms a request, then is later removed while other pending requests they confirmed remain active) is a normal operational sequence for any multisig that rotates members or reacts to a compromised key — it requires no bug-adjacent or attacker-controlled deployment step, no foundation/owner privilege beyond what the multisig already exposes to its own members, and no race condition beyond ordinary request lifecycle timing (`REQUEST_COOLDOWN` only gates `delete_request`, not this scenario). Any multisig instance using `add_request` + `confirm` (rather than exclusively `add_request_and_confirm`) is exposed whenever a member-rotation happens while requests are outstanding.

## Recommendation
When deleting a member in `delete_member`, iterate over **all** active requests' `confirmations` sets (not just the ones the member authored) and remove the deleted member's identity string from each. Alternatively, at confirmation-count time in `confirm()`, filter the stored `HashSet` down to entries that are still present in `self.members` before comparing against `num_confirmations`.

## Proof of Concept
1. Deploy `MultiSigContract::new([A, B, C, D], 3)` (3-of-4 multisig).
2. `A` calls `add_request(Transfer{amount: X})` → `request_id = R` (no confirmation, `confirmations[R] = {}`).
3. `D` calls `confirm(R)` → `confirmations[R] = {D}` (1 < 3, stored, not yet executed) — via `confirm` logic at [5](#0-4) 
4. The group later legitimately removes `D` (e.g. compromised key) with a separate fully-confirmed `DeleteMember{D}` request. `delete_member` runs and only removes requests **authored by D** — `R` was authored by `A`, so `confirmations[R]` still equals `{D}` and is untouched: [6](#0-5) 
5. Members are now `[A, B, C]`, `num_confirmations` is still 3.
6. `A` calls `confirm(R)` → `confirmations[R] = {D, A}` (2 < 3, stored).
7. `C` calls `confirm(R)` → `2 + 1 >= 3` → `execute_request` fires the `Transfer` — with only 2 live confirmations (`A`, `C`) plus one phantom vote from the already-deleted `D`, even though the current 3-member multisig (`A,B,C`) never actually reached its own 3-of-3 quorum on the live membership.

This demonstrates a multisig request executed below the intended live-member threshold, matching the Critical impact criterion.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
