### Title
Griefing `stopEpoch` by draining the programmable borrower's ERC4626 vault liquidity — `onStopEpoch`'s `vault.withdraw` reverts indefinitely while shares still cover the shortfall, so no default path triggers and pending withdrawals freeze - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
When the borrower is a `ProgrammableBorrower`, `_stopEpoch` calls `IProgrammableBorrower(_borrower()).onStopEpoch(...)` before pulling funds. Inside `onStopEpoch`, if on-hand cash is insufficient, the borrower calls `vault.withdraw(shortfall, ...)`. If that external call reverts (e.g., the ERC4626 vault's idle liquidity is lent out or was drained), the hook reverts with `StopEpochVaultLiquidityUnavailable` and the whole `stopEpoch` reverts. Crucially, the code distinguishes "economically uncovered" shortfall (`shortfall > _currentVaultAssets()`, which returns `true` so the later `transferFrom` fails into the default path) from "covered but not withdrawable" (revert). An unprivileged user of the same ERC4626 vault can keep its idle liquidity below the needed shortfall, making every `stopEpoch` revert while shares still value-cover the amount — so the vault never falls back to `_handleBorrowerDefault` and the epoch machine is stuck. ### Finding Description
- `_stopEpoch` (owner/manager) requires the epoch be running and past `epochEndDate`, then calls `onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)`.
- In `onStopEpoch`, `shortfall = _amountRequired - onHand`. If `shortfall <= _currentVaultAssets()` (shares are economically sufficient) the code attempts `vault.withdraw(shortfall, ...)`; on revert it does `revert StopEpochVaultLiquidityUnavailable()`. There is no time-based escape: the revert propagates through `stopEpoch` since the try/catch only wraps `getFundsFromBorrower`, not the hook.
- `epochPendingWithdraws` is only cleared after a successful withdraw, and `isEpochRunning` stays `true`, so `pendingWithdraws` in `IdleCreditVault` are never funded and `claimWithdrawRequest`/`claimInstantWithdrawRequest` cannot pay out.
- The attacker needs only to be an ordinary user of the borrower's ERC4626 vault (explicitly in-scope): withdraw/borrow vault idle liquidity so `vault.withdraw(shortfall)` reverts while `convertToAssets(shares) >= shortfall`. Repeating this around each `stopEpoch` attempt keeps the freeze alive. This is distinct from the honest-illiquidity case the code intentionally makes retryable (`testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable`) — here the retry is indefinitely forced by a third party with no way for management to force a default or shutdown via this path. ### Impact Explanation
Temporary (potentially indefinite while vault liquidity is suppressed) freezing of all LP withdrawals: pending `pendingWithdraws` are never collected, fees cannot be collected, and the pool cannot close/recall funds (`stopEpoch(0,1)` also reverts via the same hook). Loss scales with total `pendingWithdraws` + accrued interest blocked per epoch.

### Likelihood Explanation
Requires a programmable-borrower deployment whose ERC4626 vault shares are held/usable by third parties and whose idle liquidity can be manipulated (e.g., Morpho-style vault where liquidity is lent out). An attacker sustaining the drain bears borrow/holding costs, and retrying later works if liquidity returns, so it is griefing rather than theft — but the only privileged remedy is swapping `setVault` or waiting, both external to the stuck `stopEpoch` path.

### Recommendation
In `onStopEpoch`, treat a covered-but-failed `vault.withdraw` the same as the uncovered case after N attempts or a deadline (e.g., record `stopEpochFailures` and let IdleCDO route to `_handleBorrowerDefault`/`_emergencyShutdown`), or cap the revert path so `stopEpoch` can proceed by pulling whatever `vault.maxWithdraw` allows and accounting the remainder as a loss/default rather than reverting unconditionally.

### Proof of Concept
Foundry fork sketch (mirrors `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable`):

```solidity
// setup: programmable borrower mode, isInterestMinted, real or mock ERC4626 vault
idleCDO.depositAA(amount);
cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
_startEpoch(); // funds parked into vault via onStartEpoch/_depositToVault

uint256 pendingWithdraws = strategy.pendingWithdraws();

// ATTACKER (unprivileged vault user): drain vault idle liquidity so that
// vault.maxWithdraw(programmableBorrower) < pendingWithdraws, while
// convertToAssets(borrowerShares) >= pendingWithdraws (shares still cover).
vault.drainIdleLiquidity(); // e.g., borrow from underlying Morpho market / large redeem

vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0);

// epoch stuck: still running, never defaulted, withdraws unfunded
assertTrue(cdoEpoch.isEpochRunning());
assertFalse(cdoEpoch.defaulted());
assertEq(strategy.pendingWithdraws(), pendingWithdraws);
vm.expectRevert(); strategy.claimWithdrawRequest(...); // frozen
```

Note: this sits close to the already-acknowledged "retryable vault liquidity failure" design (`StopEpochVaultLiquidityUnavailable` is intentional per the code comment and test). If the audit scope treats that design decision as previously acknowledged, this reduces to the residual point that a *third-party* can force the condition indefinitely, which may not be considered a valid finding under the "previously acknowledged" rule.
