### Title
BB tranche holders can dodge the junior-first loss waterfall by front-running `stopEpochWithDuration` with `requestWithdraw` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report describes users converting a locked-position into a withdrawal receipt to escape loss socialization. The direct analog exists in this codebase: `requestWithdraw` burns tranche tokens and mints a fixed-denomination strategy-token receipt that is pooled into a tranche-less `pendingWithdraws` bucket. When the manager later realizes a loss via `stopEpochWithDuration(_lossAmount)`, `previewLossAdjustedWithdrawFunds` splits the loss **pro rata** between the pending bucket and active LPs, while the active-side remainder is applied BB-first. A BB holder who front-runs a loss-bearing `stopEpochWithDuration` therefore converts junior exposure into blended pro-rata exposure and forces AA holders to absorb the escaped junior loss.

### Finding Description
`requestWithdraw` in `IdleCDOEpochVariant.sol` has no "epoch running" gate and is callable after `epochEndDate` has passed but before the manager calls `stopEpoch`/`stopEpochWithDuration` (i.e., during the window in which a realized loss is about to be socialized): [1](#0-0) 

The requester's tranche tokens are burned at the **pre-loss** tranche price and NAV is reduced, so the BB tranche's active basis shrinks: [2](#0-1) 

When `stopEpochWithDuration` runs, the loss is split pro rata between `pendingBasis` and `activeBasis` with no tranche identity on the pending side: [3](#0-2) 

The remaining `activeLoss` is then applied through the ordinary BB-first waterfall via `_forceUpdateAccounting`: [4](#0-3) 

The receipt holder later claims the haircut amount through `lossRecoveryPriceByEpoch`, so they still bear a loss — but only the pro-rata share, not the junior-first share: [5](#0-4) 

Broken invariant: the loss waterfall. Junior (BB) capital is supposed to absorb losses before senior (AA). By converting BB tokens into a pending receipt in the same transaction window in which the loss is realized, the BB holder's capital is treated identically to AA capital in the pending bucket.

### Impact Explanation
Example: AA NAV = 9,000, BB NAV = 1,000, loss = 2,000 at epoch end.
- Honest path: BB is fully wiped (1,000), AA absorbs the remaining 1,000 (−11.1%).
- Attack path: BB front-runs with `requestWithdraw`. Pending basis ≈ 1,000, total basis ≈ 10,000 → `pendingLoss` ≈ 200, `activeLoss` = 1,800 applied entirely to AA (−20%).
- BB holder escapes ~800 of loss (~80% of their junior obligation), which is transferred to AA holders. If the whole BB tranche exits, the seniority protection of AA is effectively void for that loss event.

### Likelihood Explanation
The attacker is an unprivileged KYC-passed BB tranche holder. `stopEpochWithDuration(_lossAmount)` is a public manager transaction; a loss-bearing stop is observable in the mempool (or anticipated when borrower stress is known), and `requestWithdraw` is permissionless for allowed wallets during the `epochEndDate`→`stopEpoch` window. No privileged cooperation is needed. The only prerequisite is that loss socialization is pending, which is exactly the state where users are most motivated to exit.

### Recommendation
Preserve tranche identity for pending receipts (store per-epoch AA/BB pending basis, e.g., `pendingWithdrawsByTranche`), and in `previewLossAdjustedWithdrawFunds` apply the pending bucket's loss BB-first as well — i.e., allocate loss to pending-BB receipts up to their basis before sharing the remainder pro rata. Alternatively, block `requestWithdraw` between `epochEndDate` and the next `stopEpoch` call, or settle the epoch atomically (price the request against a post-loss price by requiring the loss to be realized before new requests are priced).

// Fork test in test/foundry/IdleCreditVault.t.sol style
function testBBDodgesLossWaterfallViaRequestWithdraw() external {
    uint256 aaAmount = 9_000 * ONE_SCALE;
    uint256 bbAmount = 1_000 * ONE_SCALE;
    address bbUser = makeAddr("bbUser");

    idleCDO.depositAA(aaAmount);
    _depositBBWithUser(bbUser, bbAmount);   // helper: fund + depositBB

    // isolate loss effect: run epoch at 0% apr
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    _startEpochAndCheckPrices(0);

    uint256 lossAmount = 2_000 * ONE_SCALE;
    uint256 duration = cdoEpoch.epochDuration();

    // fund borrower so the stop can pull expectedInterest + adjusted pending
    uint256 totFunds = _expectedFundsEndEpoch();
    deal(defaultUnderlying, borrower, totFunds);

    // --- attack: BB front-runs the loss-bearing stop after epochEndDate ---
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(bbUser);
    cdoEpoch.requestWithdraw(0, address(BBtranche)); // BB NAV drained into pendingWithdraws

    uint256 priceAAPre = cdoEpoch.virtualPrice(address(AAtranche));

    // manager realizes the loss
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, duration, lossAmount);

    // BB receipt only haircut pro rata: ~200 of 2,000 instead of full 1,000 wipe
    uint256 recoveryPrice = IdleCreditVault(address(strategy))
        .lossRecoveryPriceByEpoch(strategy.epochNumber());
    assertGt(recoveryPrice, 0);
    assertGt(recoveryPrice, RECOVERY_FULL / 10); // BB lost ~20%, not 100%

    // AA absorbed ~1,800 instead of ~1,000 spillover
    uint256 priceAAPost = cdoEpoch.virtualPrice(address(AAtranche));
    uint256 expectedAA = priceAAPre * 8_000 / 10_000; // honest path
    assertLt(priceAAPost, expectedAA - 1);            // AA strictly worse off
}
