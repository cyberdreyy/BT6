Found the concrete cross-context signature issue.

### Title
`BlockAccepted` acceptance signature is bound only to `signer_signature_hash`, not to `chain_id` — cross-network (mainnet/testnet) signature replay - (File: `libsigner/src/v0/messages.rs`)

### Summary
`BlockRejection` messages bind their signature to `(name, version, chain_id)` via SIP018 structured data (`BlockRejection::hash`, `BlockRejection::new`) [1](#0-0) . `BlockAccepted`, however, is signed directly over the raw `signer_signature_hash` bytes with no domain separation at all: `create_block_acceptance` does `self.private_key.sign(block.header.signer_signature_hash().bits())` [2](#0-1) , and the verifier recovers the pubkey the same way: `Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s(block_hash.bits(), signature)` [3](#0-2) .

### Finding Description
`NakamotoBlockHeader::signer_signature_hash()` is computed purely from block-header fields (version, chain_length, burn_spent, consensus_hash, parent_block_id, tx_merkle_root, state_index_root, timestamp, miner_signature, pox_treatment, problematic_txs) [4](#0-3) . It contains **no chain_id and no reward-cycle/signer-set marker**. A signer's own key is the same across mainnet and testnet deployments run by the same operator (and the block header format is identical across chain ids other than the actual on-chain consensus_hash/tx contents, which are chain-specific but not intrinsically tied to a particular `chain_id` field in the signed digest).

Because the `BlockAccepted` acceptance signature is `sign(signer_signature_hash)` with zero domain separation, any acceptance signature is only bound to a specific block header hash — not to "this chain" or "this reward cycle" the way rejections are (`BlockRejection::hash` explicitly folds in `self.chain_id` via `make_structured_data_domain("block-rejection", "1.0.0", self.chain_id)` [5](#0-4) ). This is the same class of bug as the Mattermost report: a value that is supposed to gate a security-relevant decision (which context a message applies to) is not actually bound into the authenticated artifact, so a valid artifact from one context can be replayed in another where the "same-origin" check is implicit rather than cryptographically enforced.

Concretely: `handle_block_signature` only checks (a) the signature recovers to a pubkey, and (b) that pubkey's address `is_valid_signer` — i.e., is in `self.signer_addresses` for the *current* reward cycle/signer set [6](#0-5) . There is no chain_id or reward-cycle check inside the acceptance path at all. If the same signing key is registered in the reward set of two different contexts (e.g. testnet and a fork/sibling deployment sharing keys, or across two reward cycles where the same signer re-enrolls), a `BlockAccepted` produced honestly for a block in context A is a byte-for-byte valid acceptance for any other block that happens to share the same `signer_signature_hash` in context B, since nothing about B is bound into what was signed.

### Impact Explanation
This does not by itself let one signer forge another's key. But it collapses the guarantee that "an acceptance signature proves this specific signer, in this specific chain context, endorsed this specific block" down to "this key signed this 32-byte digest" — with no cryptographic assurance that the signer intended it for this chain_id. Combined with the block-header hash's own lack of chain-id binding, this is a latent cross-context-valid-signature primitive: the same signature bytes that count toward the 70% acceptance threshold on one network could, in principle, be replayed as a valid acceptance on another network/context using the same key material and colliding header fields, undermining the "signed vs validated for this context" equality that the acceptance threshold logic depends on (`store_and_process_block_signature`, `NakamotoBlockHeader::verify_signer_signatures`) [7](#0-6) [8](#0-7) .

### Likelihood Explanation
Low-to-moderate as a directly exploitable attack today, since it additionally requires the same signer to be registered with the same key across the two contexts and the header fields to coincide — but it is a real inconsistency: `BlockRejection` was deliberately given chain-id domain separation while `BlockAccepted` was not, which is exactly the kind of asymmetric input-sanitization gap (one path sanitized/bound, the sibling path left bare) that the Mattermost CSRF report exemplifies.

### Recommendation
Bind `BlockAccepted`'s signature to the same domain-separated structured-data scheme already used for `BlockRejection` (name/version/`chain_id`), so an acceptance signature is provably scoped to a specific network/context and cannot be reinterpreted outside it. Also consider whether `signer_signature_hash` itself should include `chain_id`/reward-cycle context for the same reason.

### Proof of Concept
Not independently reproducible from index contents alone (would require constructing two signer contexts sharing key material and colliding header hashes to demonstrate a live cross-context replay); the code-level asymmetry is directly shown by comparing `BlockAccepted::new`/signing path [2](#0-1)  against `BlockRejection::hash`/`sign` [1](#0-0) .

    /// Inner calculation of the message digest for stackers to sign.
    /// This includes all fields _except_ the stacker signature.
    fn signer_signature_hash_inner(&self) -> Result<Sha512Trunc256Sum, CodecError> {
        let mut hasher = Sha512_256::new();
        let fd = &mut hasher;
        write_next(fd, &self.version)?;
        write_next(fd, &self.chain_length)?;
        write_next(fd, &self.burn_spent)?;
        write_next(fd, &self.consensus_hash)?;
        write_next(fd, &self.parent_block_id)?;
        write_next(fd, &self.tx_merkle_root)?;
        write_next(fd, &self.state_index_root)?;
        write_next(fd, &self.timestamp)?;
        write_next(fd, &self.miner_signature)?;
        write_next(fd, &self.pox_treatment)?;
        if Self::version_includes_problematic_txs(self.version) {
            write_next(fd, &self.problematic_txs)?;
        }
        Ok(Sha512Trunc256Sum::from_hasher(hasher))
    }
