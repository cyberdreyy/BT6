### Title
Stale pre-default APR0 receipt escapes default-recovery haircut and is paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimWithdrawRequest` in `IdleCreditVault` handles defaulted receipts via `_claimDefaultedWithdrawRequest`, which only clears claim basis whose `principalEpoch == defaultRecoveryEpoch` (see `_withdrawClaimAmountsForEpoch`). An APR0 request made in an **earlier** epoch and never claimed is neither cleared nor haircut: it falls through to `_claimFundedWithdrawRequest`, where `_settleApr0` converts it to `settledPrincipal` + `settledInterest` and the contract pays it at **par** through `_transferFundedClaim`, which only requires `balance - defaultRecoveryReserve >= amount`. Any underlying sitting in the strategy above the recovery reserve (e.g. borrower repayments after finalization) can be drained at par by the stale receipt, while every other defaulted creditor only receives `defaultRecoveryPrice` on the same claim basis that was already counted in `defaultPendingClaimBasis` / `pendingWithdraws` during `finalizeDefaultRecovery`. This is a use-after-free analogue: a receipt that default accounting treated as consumed/haircut basis remains live and is later paid at 100 cents on the dollar.

### Finding Description
Relevant code paths in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` records APR0 requests with `apr0Users[_user].principalEpoch = epochNumber` and adds `_amount` to `pendingWithdraws` (lines 279, 285-286, 567-577).
- `finalizeDefaultRecovery` sizes `defaultRecoveryReserve` against `defaultPendingClaimBasis()` which includes all of `pendingWithdraws`, i.e. the stale APR0 principal is counted as haircut basis at `recoveryPrice` (lines 644-649, 679-692).
- `_claimDefaultedWithdrawRequest` → `_clearWithdrawClaimForEpoch(_user, defaultRecoveryEpoch, true)` only zeroes the apr0 principal when `apr0User.principalEpoch == defaultRecoveryEpoch` (lines 771-784, 811-837). For `principalEpoch < defaultRecoveryEpoch` the principal survives.
- The same `claimWithdrawRequest` call then reaches `_claimFundedWithdrawRequest`: the epoch gate `epochNumber <= lastWithdrawRequest[_user]` passes because `lastWithdrawRequest` stores the old request epoch and `epochNumber` was bumped by the intervening `stopEpoch`; `_settleApr0` settles `reqEpoch < epochNumber`, moving `principal` → `settledPrincipal` and crediting `settledInterest` at `apr0RateByEpoch[reqEpoch]` (lines 326-341, 545-565).
- The full `normalAmount + settledPrincipal + settledInterest` is paid via `_transferFundedClaim`, which only guards against dipping into `defaultRecoveryReserve` — any non-reserve balance (post-default borrower repayments sent to the strategy, late `collectWithdrawFunds` pulls, or donated underlying) is payable at par (lines 897-907).
- Additionally, `pendingWithdraws` is only decremented by the haircut basis in `_claimDefaultedWithdrawRequest` (line 778); the stale APR0 principal stays in `pendingWithdraws` forever, corrupting borrower-facing debt accounting.

Broken invariant: one receipt, one haircut — all claim basis included in `totalBasis` at finalization must be paid at `defaultRecoveryPrice`, not at par.

### Impact Explanation
After default finalization at `recoveryPrice = R < 1e18`, an attacker holding a stale APR0 receipt of principal `P` claims `P + interest` at par instead of `P * R / 1e18`, extracting an excess of roughly `P * (1 - R) / 1e18` plus interest, from funds that economically belong to the recovery pool or other claimants. In a stressed pool (e.g. `R = 20%`), an attacker with a 1M USDC stale receipt steals ~800k USDC-equivalent of recovery value versus honest claimants, and can front-run honest recovery claims whenever new funds arrive at the strategy.

### Likelihood Explanation
Reachable by an unprivileged lender in the ordinary APR0 flow: (1) request withdraw during an APR0 epoch, (2) the epoch ends normally (`stopEpoch` sets `apr0RateByEpoch`), (3) borrower defaults in a later epoch before the user claims — entirely plausible since claims are permissionless and deferrable by design, and (4) any underlying above the reserve reaches the strategy. The attacker simply delays claiming, which the protocol explicitly supports ("old withdraw requests can still be claimed"). No privileged cooperation is required.

### Recommendation
In `_clearWithdrawClaimForEpoch` (or `_claimDefaultedWithdrawRequest`), clear **all** open APR0 principal regardless of `principalEpoch` — not only the default-epoch bucket — and include it in `claimBasis` at `defaultRecoveryPrice`. At minimum, `_claimFundedWithdrawRequest` should revert or be skipped when `defaultRecoveryFinalized` and the user still holds a pre-default APR0 position that was part of `defaultPendingClaimBasis`. Also decrement `pendingWithdraws` for every cleared APR0 principal so aggregate accounting stays consistent.

### Proof of Concept
Foundry fork PoC sketch against `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
// 1. Start APR0 epoch (unscaledApr == 0). Lender deposits via IdleCDOEpochVariant.
// 2. Lender calls requestWithdraw(P, lender, principal) -> apr0Users[lender].principalEpoch = epochNumber (N).
// 3. borrower repays; manager calls stopEpoch -> epochNumber = N+1, apr0RateByEpoch[N] set.
// 4. Lender does NOT claim. New epoch starts; borrower defaults:
//    IdleCDOEpochVariant._handleBorrowerDefault() -> finalizeDefault(0, source)
//    -> strategy.finalizeDefaultRecovery(...) with recoveryPrice R < 1e18,
//    defaultRecoveryEpoch = N+1. lender's apr0 principal was in pendingWithdraws,
//    i.e. counted in totalBasis and priced at R.
// 5. Post-finalization, underlying arrives at the strategy beyond the reserve
//    (borrower repayment via sendInterestAndDeposits path / direct transfer / late funding).
// 6. lender calls IdleCDOEpochVariant.claimWithdrawRequest() ->
//    _claimDefaultedWithdrawRequest: claimBasis==0 (principalEpoch N != N+1) -> nothing haircut;
//    _claimFundedWithdrawRequest: epochNumber(N+1) > lastWithdrawRequest(N) -> proceeds;
//    _settleApr0 settles principal+interest; _transferFundedClaim pays P + interest at par.
// assert: lender received ~P + interest while defaultRecoveryPrice < 1e18,
//         and pendingWithdraws still contains P (double-counted basis).
```

Expected result: `lender` balance increases by `P + apr0RateByEpoch[N]*P/1e18` at par, i.e. `P*(1-R)/1e18` more than the haircut amount every other defaulted receipt receives, paid out of post-default inflows/reserve-adjacent funds.
