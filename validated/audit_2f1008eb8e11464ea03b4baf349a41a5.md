## Title
Builder-controlled `fee_recipient` in `SignedExecutionPayloadBid` is enforced only at the gossip layer, not by state transition or by the validator's block-construction checklist - ([File: specs/gloas/beacon-chain.md])

## Summary
Gloas (EIP-7732) lets a proposer commit to a preferred payout address by gossiping a `SignedProposerPreferences.fee_recipient`. Builders are expected to honor that address in `bid.fee_recipient` when constructing their `SignedExecutionPayloadBid`. However, this match is only checked in the **gossip validation** function; it is absent both from the **state-transition** function that actually settles the payment and from the **validator duty checklist** that lists every condition a bid must satisfy before a proposer includes it in a block. Since the spec itself explicitly allows proposers to obtain bids "by other off-protocol means" (bypassing gossip), a builder can hand a proposer (or a relay/proposer software strictly following the documented checklist) a bid whose `fee_recipient` points to an address the builder controls instead of the proposer's committed address, and the chain will accept and pay it.

## Finding Description
The invariant "the builder pays the *proposer's declared* address" is documented in prose (`specs/gloas/builder.md`) and enforced as a gossip-only check: [1](#0-0) 

But the state-transition function that actually records/settles the payment, `process_execution_payload_bid`, never checks `bid.fee_recipient` against anything — it only validates builder activity/funds/signature, slot, parent hash/root, and randao: [2](#0-1) 

The payment recorded here (`fee_recipient=bid.fee_recipient`) is later turned into a real payout with no re-check, in `apply_parent_execution_payload` / `settle_builder_payment`: [3](#0-2) 

Critically, the validator honest-behavior checklist in `specs/gloas/validator.md`, which explicitly enumerates every condition `signed_execution_payload_bid` "MUST satisfy" before a proposer includes it in a block (signature, balance, slot, parent hash/root, randao), never lists a fee_recipient match against the proposer's own `SignedProposerPreferences`: [4](#0-3) 

Yet the spec explicitly sanctions obtaining bids outside the fee_recipient-checking gossip topic: [5](#0-4) 

This is the same bug class as the Audius `AudiusAdminUpgradeabilityProxy`: the intended restriction ("only the governance/proposer-committed address can receive control/payment") is bolted onto one front-door entry point (gossip / `upgradeTo`) but is missing from the actual privileged mutation path (state transition / `upgradeToAndCall`) and from the documented duty checklist that a spec-compliant client would implement.

## Impact Explanation
A builder that pays out-of-band bids to a proposer (or to any relay/proposer implementation that faithfully implements only the checklist in `validator.md` plus `process_execution_payload_bid`) can set `bid.fee_recipient` to an address it controls instead of the proposer's committed `fee_recipient`. Because neither the state-transition function nor the documented validator duty requires this match, the block is fully valid and the builder payment is minted to the builder's own address rather than the proposer's declared one — a Gwei amount paid to a party never authorized to receive it by the block's committed `SignedProposerPreferences`. This matches the "builder payment ... misdirected" High-impact category.

## Likelihood Explanation
The precondition is realistic and spec-sanctioned: bids may be obtained "by other off-protocol means" rather than gossip (`specs/gloas/builder.md:97-98`), so the fee_recipient check that exists only in `validate_execution_payload_bid_gossip` is trivially skipped without any protocol violation. Any implementation that codes exactly to the documented `validator.md` checklist and `process_execution_payload_bid` — without independently re-deriving the fee_recipient check from the gossip spec — is non-compliant on this one field yet otherwise fully spec-conformant.

## Recommendation
Add an explicit `fee_recipient` match assertion to `process_execution_payload_bid` (state transition) so that the invariant is enforced at the consensus layer, not merely at the optional gossip layer. Additionally, add the fee_recipient match to the enumerated list of conditions in `specs/gloas/validator.md` that a bid "MUST satisfy" before a proposer includes it in a block, so the documented honest-validator behavior is complete and self-consistent with the security assumption stated in `builder.md`.

## Proof of Concept
1. Proposer `P` broadcasts `SignedProposerPreferences{fee_recipient: P_addr, proposal_slot: S, ...}` on the `proposer_preferences` topic.
2. Malicious builder `B` sends `P` a `SignedExecutionPayloadBid` directly (off-protocol channel, explicitly permitted), with `bid.fee_recipient = B_addr` and a valid signature/balance/slot/parent fields.
3. `P`'s block-production logic, implemented strictly per `specs/gloas/validator.md` ("MUST satisfy" list at lines 204-217), finds all listed conditions satisfied (signature valid, balance sufficient, slot/parent/randao correct) — fee_recipient is not in that list — and includes the bid.
4. `process_execution_payload_bid` accepts the block (no fee_recipient check exists there either) and records `BuilderPendingWithdrawal(fee_recipient=B_addr, amount=bid.value, builder_index=B)`.
5. `apply_parent_execution_payload`/`settle_builder_payment` eventually pay `B_addr`, not `P_addr` — the builder's payment for the block never reaches the proposer's declared address, even though the block's own `SignedProposerPreferences` committed to `P_addr`.

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid

##### Signed execution payload bid

To obtain `signed_execution_payload_bid`, a block proposer building a block on
top of a `state` MUST take the following actions in order to construct the
`signed_execution_payload_bid` field in `BeaconBlockBody`:

- Listen to the `execution_payload_bid` gossip global topic and save an accepted
  `signed_execution_payload_bid` from a builder. The block proposer MAY obtain
  these signed messages by other off-protocol means.
- The `signed_execution_payload_bid` MUST satisfy the verification conditions
  found in `process_execution_payload_bid` with the alias
  `bid = signed_execution_payload_bid.message`, that is:
  - For external builders, the signature MUST be valid.
  - For self-builds, set `bid.builder_index` to `BUILDER_INDEX_SELF_BUILD`.
  - For self-builds, the signature MUST be `bls.G2_POINT_AT_INFINITY` and the
    `bid.value` MUST be zero.
  - The builder balance can cover the `bid.value`.
  - The `bid.slot` is for the proposal block slot.
  - The `bid.parent_block_hash` equals
    `state.latest_execution_payload_bid.block_hash` if
    `should_build_on_full(store, head, get_current_slot(store))` is true,
    otherwise `state.latest_execution_payload_bid.parent_block_hash`.
  - The `bid.parent_block_root` equals the current block's `parent_root`.
  - The `bid.prev_randao` equals
    `get_randao_mix(state, get_current_epoch(state))`.
- Select one bid and set
  `block.body.signed_execution_payload_bid = signed_execution_payload_bid`.

*Note*: The execution address encoded in the `fee_recipient` field in the
`signed_execution_payload_bid.message` will receive the builder payment.

## Builder activities

Builders have two optional activities: submitting bids and submitting payloads.
Builders can submit bids to produce execution payloads. They can broadcast these
bids in the form of `SignedExecutionPayloadBid` objects. These objects encode a
commitment to reveal an execution payload in exchange for a payment. When their
bids are chosen by the corresponding proposer, builders are expected to
broadcast an accompanying `SignedExecutionPayloadEnvelope` object honoring the
commitment. If a proposer accepts a builder's bid, the builder will pay the
proposer what it promised whether it submits the payload or not.
