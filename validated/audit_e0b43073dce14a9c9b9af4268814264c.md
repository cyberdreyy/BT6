Found a concrete analog: `TransactionsController.Index` in `core/web/evm_transactions_controller.go` indexes `tx.TxAttempts[0]` without checking that the slice is non-empty, directly reachable from an authenticated node-operator API GET request.

### Title
Index out of range panic in `TransactionsController.Index` when a transaction has no attempts - (File: core/web/evm_transactions_controller.go)

### Summary
The `Index` handler for the `/v2/transactions` endpoint iterates over transactions returned by `TransactionsWithAttempts` and unconditionally accesses `tx.TxAttempts[0]` to build the response resource, with no check that `TxAttempts` is non-empty.

### Finding Description
`Index` calls `tc.App.TxmStorageService().TransactionsWithAttempts(c, offset, size)` and then, for every returned tx, does: [1](#0-0) 
```go
func (tc *TransactionsController) Index(c *gin.Context, size, page, offset int) {
	txs, count, err := tc.App.TxmStorageService().TransactionsWithAttempts(c, offset, size)
	ptxs := make([]presenters.EthTxResource, len(txs))
	for i, tx := range txs {
		tx.TxAttempts[0].Tx = tx
		ptxs[i] = presenters.NewEthTxResourceFromAttempt(tx.TxAttempts[0])
	}
	paginatedResponse(c, "transactions", size, page, ptxs, count, err)
}
```
There is no guard for `len(tx.TxAttempts) == 0`. This is the same bug class flagged in the external report (Solidity `lenders` array indexed without checking `lenders.length == 0`) — a slice/array is assumed non-empty and indexed at `[0]` without a length check, causing a runtime panic (index out of range) instead of a graceful error/empty response. Note `FindTxAttempt` in `core/web/evm_transfer_controller.go` guards this correctly by looping until `len(etx.TxAttempts) > 0` before indexing `etx.TxAttempts[0]`, confirming the missing check in `Index` is an inconsistency/omission rather than an invariant guaranteed elsewhere in code.

### Impact Explanation
Any transaction stored in the txmgr's transaction table that has zero attempts (e.g., a transaction in an early/edge state such as `unstarted` or one that failed before an attempt could be persisted) would cause a Go runtime panic (`index out of range`) when a user calls `GET /v2/transactions`. This is a request-triggered denial-of-service against the node's admin/API HTTP handler for any caller authorized to hit this endpoint (session or API-token authenticated user, per `core/web/auth/auth.go`), causing that request goroutine to panic; depending on the gin recovery middleware configuration, this returns a 500 or can destabilize the API server for that request.

### Likelihood Explanation
Likelihood is moderate — it depends on this node ever persisting a `Tx` row without at least one `TxAttempt`, which is not something the reviewer verified is impossible in all code paths of `TxmStorageService`. Given the same defensive check exists in the sibling function `FindTxAttempt`, the underlying data model does not appear to guarantee `TxAttempts` is always non-empty at every point in the tx lifecycle, making this reachable under normal node operation without any malicious actor being required — an authenticated but otherwise unprivileged/low-privilege API consumer viewing transactions could trigger it.

### Recommendation
Add a length check before indexing, mirroring the report's fix pattern, e.g.:
```go
for i, tx := range txs {
    if len(tx.TxAttempts) == 0 {
        continue // or return an appropriate partial resource without panicking
    }
    tx.TxAttempts[0].Tx = tx
    ptxs[i] = presenters.NewEthTxResourceFromAttempt(tx.TxAttempts[0])
}
```

### Proof of Concept
1. Have the node create/persist a `Tx` record whose `TxAttempts` slice is empty at query time (e.g., query timing where an attempt hasn't yet been written, or any state that permits zero attempts).
2. As an authenticated API user, call `GET /v2/transactions` (routed to `TransactionsController.Index`).
3. The handler executes `tx.TxAttempts[0].Tx = tx` on the zero-length slice, causing an `index out of range [0] with length 0` panic in the request handler. [2](#0-1)
