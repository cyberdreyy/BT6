### Title
Claimed instant-withdraw receipts are never removed from `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, inflating the default-recovery claim basis and enabling double recovery payouts - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The analog of CVE-2020-36782 (a counter incremented on an operation without a matching decrement, leaking the reference) is in `IdleCreditVault`: `requestInstantWithdraw` increments three counters (`instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch[user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`), but the normal funded claim path `claimInstantWithdrawRequest` clears only the first one. The per-epoch receipt bookkeeping is decremented only on the defaulted claim path (`_claimDefaultedInstantWithdrawRequest`). Already-paid instant receipts therefore remain permanently counted in the epoch aggregate that `defaultPendingClaimBasis` uses to compute the default-recovery haircut.

### Finding Description
- `requestInstantWithdraw` adds `_amount` to `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 371-374).
- `claimInstantWithdrawRequest` burns the receipt and sets `instantWithdrawsRequests[_user] = 0`, then transfers funded underlying — but never touches the two per-epoch mappings (lines 380-393). The `ByEpoch` mappings are only cleared inside `_claimDefaultedInstantWithdrawRequest` (lines 847-853), which runs solely after default finalization.
- `defaultPendingClaimBasis` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (lines 644-649). Any other still-unfunded instant request in the same epoch makes the whole stale epoch aggregate — including receipts already paid at par — count as defaulted claim basis.
- `finalizeDefaultRecovery` divides the fixed recovered amount over this inflated basis, so `defaultRecoveryPrice` is set too low, and the reserve includes a phantom share that no legitimate claimant will ever draw.
- Additionally, a user who claimed and then re-requests in the same epoch has `instantWithdrawsRequestsByEpoch[user][epoch] = oldClaimed + new`. On default, `_claimDefaultedInstantWithdrawRequest` pays recovery on the already-paid portion — a double payout — and `instantWithdrawsRequests[user] -= claimBasis` only works because the new request re-inflated it.

### Impact Explanation
When a borrower default is finalized in an epoch where instant receipts were already claimed and at least one instant request is still pending, the recovery haircut `defaultRecoveryPrice` is computed over phantom (already-paid) basis. Legitimate recovery claimants — pending withdraw receipt holders, defaulted-epoch instant receipt holders, and active LPs whose NAV is reduced by the same ratio — are underpaid, while a share of `defaultRecoveryReserve` is stranded forever (permanent freezing). If the previously-claiming user re-requested in the same epoch, they additionally receive recovery tokens for a receipt already redeemed at par — direct theft from the reserve at the expense of other claimants. Loss scales with the size of the claimed instant receipts.

### Likelihood Explanation
Requires only unprivileged user actions: request instant withdraw, wait for `getInstantWithdrawFunds` funding, claim, then have any pending instant receipt outstanding in the same epoch when a default is finalized. `epochNumber` is bumped only by stopEpoch/deposit-at-stopEpoch (lines 607-614), so multiple instant requests and claims can share one epoch. No privileged misbehavior is needed; the honest borrower defaulting is the trigger. No existing guard (`_transferFundedClaim` reserve check, `NotAllowed` reverts, epoch gating) detects the stale accounting.

### Recommendation
In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` for the user's request epoch(s) alongside clearing `instantWithdrawsRequests[_user]` — mirroring the decrement logic in `_claimDefaultedInstantWithdrawRequest`. Since `instantWithdrawsRequests` is aggregated across epochs, either store a per-user list of request epochs or bound claims so the per-epoch entries are cleared proportionally.

### Proof of Concept
```solidity
// Foundry fork test sketch (USDC pool, see test/foundry/IdleCreditVault.t.sol setup)
function testStaleInstantClaimInflatesDefaultBasis() external {
    _setUpCreditVault(); // existing harness: depositAA, enable allowInstantWithdraw
    address alice = makeAddr("alice");
    address bob = makeAddr("bob");
    _depositWithUser(alice, 10_000 * ONE_SCALE, true);
    _depositWithUser(bob, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // Alice requests instant withdraw, manager funds it, Alice claims at par
    vm.prank(alice);
    cdoEpoch.requestInstantWithdraw(cdoEpoch.maxInstantWithdraw(alice), address(AAtranche));
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();
    vm.prank(alice);
    cdoEpoch.claimInstantWithdrawRequest();

    // BUG: per-epoch aggregates still hold Alice's paid receipt
    uint256 epoch = strategy.epochNumber();
    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), /* alice receipt */);

    // Bob requests instant withdraw in the SAME epoch; still unfunded at default
    vm.prank(bob);
    cdoEpoch.requestInstantWithdraw(cdoEpoch.maxInstantWithdraw(bob), address(AAtranche));

    // Borrower defaults; default is finalized for `epoch`
    _triggerDefaultAndFinalize(epoch);

    // Bob's recovery price is diluted by Alice's already-paid receipt;
    // his claim is worth less than (hisBasis * recovered / realBasis)
    uint256 bobBalPre = underlying.balanceOf(bob);
    vm.prank(bob);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 paid = underlying.balanceOf(bob) - bobBalPre;
    assertLt(paid, fairRecovery(bob), "recovery diluted by stale claimed receipt");
}
```
Key assertion: `strategy.instantWithdrawClaimsByEpoch(epoch)` is nonzero after Alice's successful claim, proving the receipt-basis leak that `defaultPendingClaimBasis` (lines 644-649) later consumes.
