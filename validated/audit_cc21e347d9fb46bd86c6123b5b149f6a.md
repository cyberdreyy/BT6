This confirms the vulnerability. `MessageId` is fully attacker-chosen — `Validate()` places no constraint linking `MessageId` to the signer's identity; the signature only covers the message body fields (including `MessageId`) so anyone can sign an arbitrary `MessageId` of their choosing with their own key [1](#0-0) . The gateway's `ProcessRequest` only limits ID length to 200 chars and passes the client-supplied `jsonRequest.ID`/`msg.Body.MessageId` straight through to `HandleLegacyUserMessage` without any per-sender uniqueness check [2](#0-1) . Inside `HandleLegacyUserMessage`, the callback is stored keyed only by `msg.Body.MessageId`, unconditionally overwriting any prior entry with the same key [3](#0-2) , and the eventual node response is matched and delivered purely by `msg.Body.MessageId` via `handleWebAPITriggerMessage` [4](#0-3) .

### Title
Cross-user callback hijack via colliding attacker-chosen MessageId in HandleLegacyUserMessage - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`h.savedCallbacks` is keyed solely by the client-supplied `msg.Body.MessageId`, which is never bound to the sender's identity by signature verification. An unauthenticated attacker who can guess or observe a victim's `MessageId` can submit a second, independently-signed request using the same `MessageId`, silently overwriting the victim's saved callback entry so the eventual DON response is delivered to the attacker instead of the victim (or is lost entirely).

### Finding Description
`Message.Sign`/`Message.Validate` compute a signature over the full message body including `MessageId`, but they do not enforce that `MessageId` is unique to a sender — any signer can choose any `MessageId` value and produce a valid signature over it [5](#0-4) [1](#0-0) . The gateway's `ProcessRequest` decodes the request, validates the signature, and dispatches to `HandleLegacyUserMessage` using the caller-controlled `MessageId`, only capping its length at 200 characters [6](#0-5) . In `HandleLegacyUserMessage`, after validating the payload/timestamp/method, the handler unconditionally stores (overwrites) `h.savedCallbacks[msg.Body.MessageId]` under a mutex with no check for a pre-existing entry [3](#0-2) . When a node later responds with `MethodWebAPITrigger` and the same `MessageId`, `handleWebAPITriggerMessage` looks up and deletes the current map entry and sends the raw response to whatever callback is stored there at that moment [4](#0-3) . If an attacker races a second `HandleLegacyUserMessage` call with the identical `MessageId` before the victim's node response arrives, the attacker's callback overwrites the victim's, and the eventual response (potentially containing the victim's requested data/result) is delivered to the attacker's HTTP connection, while the victim's original request either times out or silently receives nothing.

### Impact Explanation
This is a cross-user response confusion / request hijacking vulnerability: an attacker can redirect a legitimate victim's trigger response to themselves, or deny the victim's response entirely, purely by guessing/observing a `MessageId` and submitting their own independently signed request in a race. No node/DON compromise is required, matching the "cross-user response redirection / DoS of victim's pending request" bounty class of unauthorized access to another user's request/response state.

### Likelihood Explanation
The attacker only needs to be an unauthenticated HTTP client capable of signing a legacy gateway message with any key they control (trivially available — a self-generated ECDSA key). The precondition is knowledge or predictability of the victim's `MessageId` and winning a short race window between the victim's initial request and the DON's response. `MessageId`s are often generated client-side or may follow predictable patterns (e.g., sequential IDs, timestamps, or reused/observed values from prior interactions), making this feasible in realistic deployments, and it is fully repeatable since there is no rate limiting or per-sender namespacing on `MessageId`.

### Recommendation
Namespace `savedCallbacks` keys by both `MessageId` and the verified `msg.Body.Sender` (e.g., `sender+":"+MessageId`), or reject `HandleLegacyUserMessage` calls when an existing, unexpired callback with the same `MessageId` (regardless of sender) is already present. Additionally, validate node responses in `handleWebAPITriggerMessage` against the original sender/DON member set to ensure only the DON node addressed for that specific request can trigger a response consumption.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Generate two distinct ECDSA keys, `victimKey` and `attackerKey`.
2. Build `victimMsg := triggerRequest(t, victimKey, ..., messageID="dup-id", ...)` and `attackerMsg := triggerRequest(t, attackerKey, ..., messageID="dup-id", ...)` (both valid, non-stale, correct method/payload).
3. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`, then immediately `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)` before any node response arrives.
4. Assert `len(handler.savedCallbacks) == 1` and that the stored entry's `Callback` is `attackerCallback`, not `victimCallback`.
5. Simulate the DON responding with `MessageId "dup-id"` via `handler.HandleNodeMessage`, and assert the response is delivered to `attackerCallback.Wait()` while `victimCallback.Wait()` times out/never receives a response — proving cross-user hijack of the callback correlation.
