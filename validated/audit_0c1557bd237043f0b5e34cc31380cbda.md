### Title
Post-default withdraw requests drain the fixed default recovery reserve at par, stealing finalized recovery funds from defaulted-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestWithdraw` has a dedicated post-default path: once `defaultRecoveryFinalized` is set, a user with no outstanding requests can burn tranche tokens and receive a `postDefaultRequests` receipt. `_claimPostDefaultWithdrawRequest` then pays that receipt 1:1 out of `defaultRecoveryReserve` — the same finite underlying reserve that was sized once inside `finalizeDefaultRecovery` to cover defaulted-epoch pending receipts and active-holder recovery at `defaultRecoveryPrice`. Critically, `reserveDefaultRecovery` reverts when `defaultRecoveryFinalized` is true, so the reserve can never be replenished after finalization. Every post-default claim is therefore an unpriced draw on funds earmarked for someone else — a direct analog of the mppx bug class: creating fresh obligations ("reopening the channel") against a finalized settlement pool that was computed without them, and paying them at par while earlier claimants are haircutted.

### Finding Description
In `IdleCreditVault.requestWithdraw`, when `defaultRecoveryFinalized == true`, the vault mints a receipt and records `postDefaultRequests[_user] = _amount` with no funding added anywhere (lines 247-257). The corresponding claim path `_claimPostDefaultWithdrawRequest` pays `amount` via `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= _amount` and transfers at par (lines 760-767, 912-917).

The reserve, however, was fixed at finalization: `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis = activeBasis + pendingBasis` — post-default requests did not exist and are not in `totalBasis` (lines 679-693). Defaulted-epoch claimants receive only `claimBasis * defaultRecoveryPrice` per unit of basis (lines 772-784), while post-default claimants receive the full amount. And `reserveDefaultRecovery` explicitly reverts if `defaultRecoveryFinalized` (line 631), so nothing can ever top the reserve up.

Sequence (all post-finalization calls are unprivileged — any KYC'd tranche holder):
1. Epoch defaults; `finalizeDefault` / `finalizeDefaultRecovery` sets `defaultRecoveryPrice = p < 1` and `defaultRecoveryReserve = p * totalBasis`.
2. Attacker calls `requestWithdraw(amount, attacker, principal)` → `postDefaultRequests[attacker] = amount`.
3. Attacker calls `claimWithdrawRequest` → `_claimPostDefaultWithdrawRequest` pays `amount` at par and decrements the reserve.
4. Honest defaulted-epoch claimants calling `claimWithdrawRequest` later hit `_transferDefaultRecovery` → `defaultRecoveryReserve -= _amount` underflows / safeTransfer fails → their haircutted recovery is permanently unclaimable.

Existing guards do not stop this: the post-default path intentionally allows requests (it only reverts if the user has other pending requests), `claimWithdrawRequest` checks no price for that bucket, and `allowAAWithdrawRequest`/`allowBBWithdrawRequest` gating lives on the CDO side while the strategy-level accounting flaw is what breaks solvency.

### Impact Explanation
Direct theft / permanent freezing of defaulted users' recovery funds. Loss is bounded by the reserve itself: each post-default claim of `X` removes `X` from a pot that must still pay out `defaultRecoveryPrice * totalBasis` to defaulted claimants and (through the CDO/DefaultDistributor recovery path) to active holders. With `defaultRecoveryPrice` significantly below 1, an attacker effectively redeems tranche value at a better rate than defaulted-epoch claimants and can render the tail of legitimate recovery claims unpayable — a quantified shortfall equal to the sum of post-default claims.

### Likelihood Explanation
Requires a defaulted pool that was finalized with `defaultRecoveryPrice < 1` (the common case for a default) plus an unprivileged user holding tranche tokens with no open requests — i.e., any ordinary AA/BB lender who did not request a withdrawal before default. No privileged cooperation is needed; `requestWithdraw` and `claimWithdrawRequest` are user-facing. One caveat I could not fully verify within the available context: whether `IdleCDOEpochVariant.requestWithdraw` passes an already-recovery-priced `_amount` such that the par payout from the reserve is intended to equal what the claimant would have received anyway. Even if so, the reserve was still sized without these claims, so the drawdown shortfall for earlier-basis claimants stands unless the CDO separately funds each post-default request — and `reserveDefaultRecovery` (the only reserve-increasing function) is unusable post-finalization.

### Recommendation
Either disallow new withdraw requests once `defaultRecoveryFinalized` is set, or fund each post-default receipt out of a source other than `defaultRecoveryReserve` (e.g., require the CDO to transfer the corresponding underlying into the strategy in the same call and track it in a separate bucket), and apply `defaultRecoveryPrice` to post-default claims if they must share the reserve so all claimants are haircutted symmetrically.

### Proof of Concept
Foundry fork test outline (in the style of `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `_checkDefault`):

```solidity
function testPostDefaultRequestDrainsRecoveryReserve() external {
    // victim deposits and requests withdraw in epoch 0
    address victim = makeAddr('victim');
    _depositWithUser(victim, 10_000 * ONE_SCALE, true);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // attacker deposits but keeps tranche tokens (no request)
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);

    _startEpochAndCheckPrices(0);
    // borrower underpays -> default
    deal(defaultUnderlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);
    _checkDefault();

    // finalize with 50% recovery
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    uint256 recovered =
        (cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest()
         - cdoEpoch.pendingWithdrawFees() + creditVault.defaultPendingClaimBasis()) / 2;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    underlying.approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();
    assertLt(creditVault.defaultRecoveryPrice(), ONE_TRANCHE, 'need haircut');
    uint256 reservePre = creditVault.defaultRecoveryReserve();

    // attacker opens a post-default request and claims at par
    uint256 attackerTranches = IERC20Detailed(address(AAtranche)).balanceOf(attacker);
    vm.startPrank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    uint256 balPre = underlying.balanceOf(attacker);
    cdoEpoch.claimWithdrawRequest();
    vm.stopPrank();
    uint256 attackerPaid = underlying.balanceOf(attacker) - balPre;
    assertGt(attackerPaid, 0, 'post-default claim paid');
    assertEq(creditVault.defaultRecoveryReserve(), reservePre - attackerPaid, 'reserve drained');

    // victim's defaulted claim now reverts or is short
    vm.prank(victim);
    vm.expectRevert(); // underflow in defaultRecoveryReserve -= amount or failed transfer
    cdoEpoch.claimWithdrawRequest();
}
```
