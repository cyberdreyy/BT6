### Title
Post-default withdraw claims drain `defaultRecoveryReserve`, stealing recovery earmarked for defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` pays post-default withdraw receipts from `defaultRecoveryReserve` even though that reserve was sized at finalization to cover only defaulted-epoch claims (active LPs + pending receipts). Post-default receipts are backed by fresh deposits held in the strategy's token balance, but `_claimPostDefaultWithdrawRequest` routes payment through `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve`. Every post-default claim therefore consumes reserve allocated to defaulted-epoch claimants, so later defaulted-epoch claimants either receive less than `claimBasis * defaultRecoveryPrice` or their claim reverts permanently.

### Finding Description
The analog of CVE-2018-8106 (a heap over-read that consumes bytes beyond a buffer's allocated region and crashes downstream readers) is a recovery-reserve over-consumption: post-default claims "read past" the reserve's allocated basis, corrupting the payout of every claim that comes after.

At finalization, `defaultRecoveryReserve` is set to `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis = activeBasis + pendingBasis` contains only claims that existed at default time [1](#0-0) .

After finalization, `requestWithdraw` mints fresh receipts and records `postDefaultRequests[_user]` — a bucket that was never part of `totalBasis` and whose underlying backing (post-default deposits at the post-haircut `virtualPrice`) sits in the strategy's balance but is never added to the reserve [2](#0-1) .

When that post-default receipt is claimed, `_claimPostDefaultWithdrawRequest` calls `_transferDefaultRecovery(_user, amount)` at par [3](#0-2) , and `_transferDefaultRecovery` unconditionally does `defaultRecoveryReserve -= _amount` [4](#0-3) . Symmetrically, defaulted-epoch claimants draw the same reserve via `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest` [5](#0-4) .

The broken invariant is "one receipt one payout": total payouts = `totalBasis * recoveryPrice` (defaulted claims) **plus** `sum(postDefaultRequests)` (post-default claims), but only `reserveAmount` backs the first sum while the second sum is backed by a separate, unreserved balance. Since both draw down the same counter, whoever claims first wins; the reserve is exhausted early and the last defaulted-epoch claimants' `_transferDefaultRecovery` reverts on underflow or pays them with post-default depositors' funds.

Notably, the funded-claim path has an explicit guard preventing it from touching the reserve (`balance - reserve < _amount` reverts) [6](#0-5)  — the contract already recognizes the reserve must be isolated, but the post-default path violates that same isolation in the opposite direction.

### Impact Explanation
Direct theft / permanent freezing of unclaimed recovery. An attacker (any KYC-passing lender) deposits after default finalization, calls `requestWithdraw`, then `claimWithdrawRequest`, receiving their post-default receipt 1:1 out of the recovery reserve. Each unit claimed reduces `defaultRecoveryReserve` below what honest defaulted-epoch claimants are owed at `defaultRecoveryPrice`. Loss magnitude: `min(sum(postDefaultRequests), defaultRecoveryReserve)` is stolen from defaulted claimants; the final defaulted claimants' transactions revert, permanently freezing their recovery (there is no other path that replenishes the reserve — `deposit` and `mintStrategyTokens` never increment it).

### Likelihood Explanation
Requires a borrower default followed by `finalizeDefaultRecovery` (honest privileged flow, allowed by scope). Post-default deposit/withdraw is an explicitly supported mode ("Preserve request/claim UX after default"), so no exotic state is needed — only that at least one post-default withdraw claim executes before all defaulted-epoch claimants have claimed. Anyone may claim at any time after finalization, so ordering is purely attacker-chosen. No existing guard stops it: `_hasWithdrawRequest` only forces old receipts to be claimed first, and the reserve guard in `_transferFundedClaim` does not apply to `_transferDefaultRecovery`.

### Recommendation
Pay post-default receipts from the unreserved balance instead of the recovery reserve: in `_claimPostDefaultWithdrawRequest`, use `_transferFundedClaim`-style logic (or a dedicated transfer) rather than `_transferDefaultRecovery`. Concretely, since post-default receipts are backed 1:1 by post-default deposits held in the strategy balance, the claim should transfer underlying without decrementing `defaultRecoveryReserve`, e.g. by adding a path that skips the reserve accounting, or by tracking a `postDefaultReserve` counter that is incremented when post-default deposits arrive and consumed by `_claimPostDefaultWithdrawRequest`.

### Proof of Concept
Foundry fork PoC outline (against the existing `IdleCreditVault.t.sol` harness):

1. Deposit as `victim` (epoch N), `startEpoch`, warp past `epochEndDate`, drive `stopEpoch` into borrower default and call `finalizeDefault`/`finalizeDefaultRecovery` so `defaultRecoveryFinalized = true`, `defaultRecoveryPrice < 1e18`, `defaultRecoveryReserve = R`.
2. Attacker `depositAA` post-default (minted at post-haircut price), then `cdoEpoch.requestWithdraw(amount)` → `postDefaultRequests[attacker] = amount`.
3. `cdoEpoch.claimWithdrawRequest()` for attacker → pays `amount` 1:1 and executes `defaultRecoveryReserve -= amount` (now `R - amount`), even though the `amount` paid was backed by the attacker's own deposit sitting in the strategy balance.
4. `victim` calls `cdoEpoch.claimWithdrawRequest()` → `_claimDefaultedWithdrawRequest` computes `amount = claimBasis * defaultRecoveryPrice / 1e18` and calls `_transferDefaultRecovery`, which reverts (`defaultRecoveryReserve -= amount` underflows) or transfers funds backed by post-default deposits.
5. Assert: victim's expected recovery is unreachable; attacker extracted `amount` of reserve in excess of their deposit backing.

Alternatively, ordering the attacker's claim after the victim's shows the victim receives their recovery but the attacker's post-default claim then reverts — either ordering demonstrates that `reserve` is double-counted across two disjoint claim bases.

  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }
