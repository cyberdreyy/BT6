### Title
Node-unreachable fallback in pre-commit conflict re-check lets a signer sign a conflicting block in the same tenure - (File: stacks-signer/src/v0/signer.rs)

### Summary
`Signer::handle_block_pre_commit` re-derives, at the moment a block crosses the pre-commit signing threshold, whether a previously-signed sibling block in the *same tenure* still blocks the new signature. When the node RPC call used for this re-derivation (`get_tenure_tip`) fails or times out, the code does not fail closed (refuse to sign); it falls through and treats the tenure as "unconfirmed," letting the signature go out anyway. This mirrors the external report's bug class ("external call failure causes an operation that should be safely aborted/retried to instead proceed"), except here the consequence is a signer producing a second, conflicting signature over the same tenure/height rather than a mere DoS.

### Finding Description
`handle_block_pre_commit` is the only place a signature is actually produced, and it is explicitly the *only* remaining guard against a same-tenure duplicate once the cheaper, local `check_block_against_signer_db_state` recheck no longer vetoes (because the earlier signed conflict has gone stale relative to `tenure_last_block_proposal_timeout`): [1](#0-0) 

Once past that recheck, the code queries `get_signed_conflicts` for any block previously signed at the same height in the same tenure, and — if the conflict is in the block's *own* tenure and no reorg permit stands — asks the node for the tenure's current canonical tip to decide if that tip has already advanced past (or to) the proposed height: [2](#0-1) 

The critical asymmetry is in the `Err(e)` branch of that RPC call: unlike the *cross-tenure* conflict path (`conflict_still_blocks`, `reorg_permit_stands`), which explicitly treats every node error as "leave the conflict in place" (fail safe / keep blocking): [3](#0-2) [4](#0-3) 

the *own-tenure* branch does the opposite: on error it logs a warning and treats the tenure as unconfirmed, which lets execution fall through to sign the new block regardless of the still-standing earlier signature: [5](#0-4) 

This design choice, and the fact that this is the sole guard for this case, is explicitly documented: [6](#0-5) 

### Impact Explanation
This breaks the equivocation guard that the pre-commit re-check is designed to enforce: a single signer can end up producing signatures over two conflicting blocks (same height, same tenure) — once for the earlier block A (now stale per the freshness cutoff, but not yet reflected in the node's canonical tip), and again for a later, conflicting block B, purely because the node's `/v3/tenures/tip`-style RPC call happened to fail or time out at the wrong moment. Per the stated impact classes, "a signer signing an invalid, non-canonical, or conflicting block" is Critical: it directly threatens the one-signature-per-height/tenure safety property the whole pre-commit/threshold design exists to protect, and if enough signers hit the same transient RPC failure window, both conflicting blocks could independently accumulate pre-commit/signature weight.

### Likelihood Explanation
No majority of signers, leaked keys, or auth token is required — only: (1) a miner (or a race between two proposals in the same tenure) producing two conflicting blocks at the same height that are both independently validated before either reaches the pre-commit threshold, so the proposal-time `DuplicateBlockFound` check never fires against them; (2) enough time passing that the first signature goes stale per `tenure_last_block_proposal_timeout` (a config value, default tens of seconds); and (3) a single transient RPC failure/timeout to the local stacks-node at the moment the second block's pre-commit threshold is evaluated. Network hiccups and node RPC timeouts under load are common and not attacker-controlled with certainty, but the trigger scenario (dueling proposals in one tenure) is fully within a single miner's control, matching the "one-slot miner plus gossip" threat model.

### Recommendation
Make the own-tenure conflict re-check fail closed like its cross-tenure counterparts: on `get_tenure_tip` error, treat the conflict as still blocking (refuse to sign "for now") rather than as unconfirmed. If availability is a concern, retry with backoff or defer the decision to a later re-evaluation instead of defaulting to the unsafe "sign" outcome.

### Proof of Concept
1. Miner in tenure T proposes block A at height H; enough signers pre-commit, and this signer's copy reaches threshold, passes `check_block_against_signer_db_state`, and signs A via `handle_block_pre_commit` (`mark_locally_accepted` → `create_block_acceptance`) — see [7](#0-6) . A is never actually adopted by this signer's local node (e.g., broadcast delay/partition).
2. Time passes beyond `tenure_last_block_proposal_timeout`, so A's endorsement becomes stale for the purposes of the local `check_block_against_signer_db_state` recheck (per [1](#0-0) , LSB only vetoes while "fresh").
3. The same miner proposes conflicting block B at height H in tenure T. B is validated and reaches pre-commit threshold; `get_signed_conflicts` returns A as a same-tenure conflict at [8](#0-7) .
4. During the own-tenure recheck at [9](#0-8) , the call to `stacks_client.get_tenure_tip(...)` fails (timeout/connection error/etc.). The `Err(e)` branch logs a warning and does not `return`, so execution falls through to the signing path and the signer signs B — producing two signer signatures over conflicting blocks A and B at the same height in tenure T.

```markdown
Order matters here: the chainstate re-check runs first and produces an explicit
(sticky) rejection when the block now conflicts with a signed one. The conflict
guard behind it is the silent backstop for what that re-check cannot see, and
silence keeps the door open to sign later once the conflict goes stale. Two
blind spots make the guard necessary:

- the re-check only ever looks at _one_ tenure (a tenure-change block's parent,
  or any other block's own), so a signed sibling at the same height in a third
  tenure is invisible to it;
- the `DuplicateBlockFound` check that would catch a second block in the same
  tenure lives in `check_proposal` and runs only at proposal arrival, never
  again. A block that crosses the pre-commit threshold minutes later has no
  other guard, which is what the own-tenure branch above covers.

Freshness alone is not enough to hold a signature back, because a signature can
outlive the block it covers: a Bitcoin reorg can kill the block, and a dead
signature must not stall the chain restarting beneath it until it goes stale. So
`conflict_still_blocks` derives, per evaluation, whether the conflict could still
end up in the chain. Deriving this here — instead of recording it when a fork is
observed — is deliberate: the node's view mid-reorg is a moving target (burn
block events fire before the sortition transaction commits, and a node error can
wipe the local state machine), so a fact recorded once at observation time can be
silently wrong, while a question asked per evaluation self-corrects on the next
pre-commit or re-proposal. Two questions, in order:

1. **Is the conflict's tenure still on the canonical burn chain?** The signer
   saved the tenure's burn block when it arrived (section 8), and
   `/v3/sortitions/burn/:hash` resolves it against the node's canonical fork. A
   404 means a burnchain fork orphaned the tenure: everything it built is void,
   and the conflict is dead no matter what state its block is in. But a 404
   alone is not proof — the same endpoint 404s a perfectly canonical burn block
   when the node is still catching up (and on internal data misses), so it is
   only trusted once the node's burnchain tip (`get_peer_info`) is at or past
   the stored burn block's height; below that, the conflict keeps blocking and
   the next evaluation retries. If the burn block was never saved (a restart,
   or the tenure predates us), the question is skipped rather than guessed.
2. **Does the node's canonical Stacks chain still reach the block itself?**
   - **it does** — real chain state; keep blocking;
   - **it does not, and the block was globally accepted** — the node once _did_
     have it, so a reorg moved past it. That is proof it is dead;
   - **it does not, and the block was never globally accepted** — a block is
     not handed to the node until the whole signer set has signed it, so this
     may mean "not yet seen" rather than "dead". A sibling at the same height
     therefore keeps blocking, since signing both would be the double-sign this
     guard exists for; a block _above_ the proposal does not, because it is no
     sibling and abandoning an unconfirmed block to restart beneath it is a
     reorg, not an equivocation.

A conflict is any block a signature was ever put over — ours, or a group
threshold we observed — whatever its state now. In particular rejection, even
_global_ rejection, does not clear one: a rejection is a revocable opinion,
while a signature is a bearer instrument that can still be aggregated toward
the 70% threshold if rejecting signers change their minds. Only staleness or
node-derived death (the two questions above) clears a conflict.

Whenever the node cannot be asked, the conflict keeps blocking: that only delays
the replacement until the signature goes stale, whereas wrongly signing cannot be
taken back. The one recorded exception is a tenure whose reorg we sanctioned
under the reorg-timing rules (section 8): there the node still serves the
conflict as fully live — replacing it is only legitimate because we permitted it
— so no question asked of the node about the _conflict_ could clear it. Instead
the record carries the permitting tenure's sortition, and `reorg_permit_stands`
asks the node whether that sortition is still canonical: while it is, the
conflict is excluded outright; if a burnchain fork orphaned it, the reorg we
sanctioned can no longer happen and the conflict gets its voice back. A false
404 there needs no tip-height guard — it merely restores a conflict, which at
worst delays the replacement. For the own-tenure question below, an unreachable
node is instead treated as unconfirmed and the signature goes out.
```
