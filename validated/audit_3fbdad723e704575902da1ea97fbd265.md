Based on my investigation, this scenario is a real, valid bug in gitlab-runner's process-management layer.

### Title
Grandchild fd inheritance of job trace stdout/stderr pipes causes `Commander.Wait()`/stream `Close()` to hang, exhausting log-streaming resources - (File: helpers/process/commander.go, helpers/process/job_unix.go, executors/custom/command/command.go)

### Summary
`NewOSCmd` in `helpers/process/commander.go` assigns `c.Stdout`/`c.Stderr` directly from `CommandOptions.Stdout/Stderr`, which for the custom executor (and shell/instance/ssh executors) are non-`*os.File` `io.WriteCloser` chains produced by `buildlogger.Logger.Stream`. Because these are not `*os.File`, Go's `os/exec` internally allocates real OS pipes and spawns copy goroutines whose completion `exec.Cmd.Wait()` blocks on; a job-script-spawned detached grandchild that inherits the pipe's write end and doesn't exit keeps that pipe open indefinitely, hanging `osCmd.Wait()` (and thus `command.waitForCommand()`/`c.waitCh`) and the subsequent trace-stream `Close()`.

### Finding Description
`process.NewOSCmd` wires `exec.Cmd.Stdout`/`Stderr` straight from `CommandOptions.Stdout/Stderr` [1](#0-0) . In the custom executor's `Run`, this writer is `e.BuildLogger.Stream(buildlogger.StreamWorkLevel, buildlogger.Stdout)` [2](#0-1) , which returns a chain of custom `io.WriteCloser` wrappers (masker/timestamper/sync), never an `*os.File` [3](#0-2) . The same non-`*os.File` pattern applies to the shell, instance, and kubernetes-log executors as well.

When `exec.Cmd.Stdout`/`Stderr` are not `*os.File`, the Go standard library creates real OS pipes and starts goroutines to copy from the pipe into the writer; `Cmd.Wait()` is documented to block until those copy goroutines finish, which only happens once *all* holders of the pipe's write end (including any inherited grandchild) close it — not merely once the direct child process exits. `osCmd.Wait()` is a thin passthrough to `exec.Cmd.Wait()` with no `WaitDelay` set [4](#0-3) , and `CommandOptions`/`NewOSCmd` never configure `WaitDelay` [5](#0-4) . `WaitDelay` is the stdlib-provided mechanism (Go 1.20+) specifically meant to bound this exact grandchild-fd-inheritance hang by force-closing the pipes after a timeout; it is not used anywhere in this code path.

The exploit path: a CI job (attacker-controlled `script:`) run under the custom executor is executed by the driver's `RunExec` process, whose stdout/stderr are the pipes described above. If the job script itself spawns a detached/backgrounded process (e.g. `setsid some_long_running &` without redirecting its own inherited stdout/stderr) that survives the direct child's exit, that grandchild retains an open duplicate of the pipe write-end file descriptor. `command.waitForCommand()` calls `c.cmd.Wait()` [6](#0-5) , which blocks indefinitely because the underlying `exec.Cmd.Wait()` is waiting on the copy-goroutines/pipe closure, not just process exit. `command.Run()`'s `select` on `c.waitCh`/`c.context.Done()` [7](#0-6)  then falls to the `KillAndWait` path on context cancellation, but `KillAndWait` only signals/kills the direct process group via `syscall.Kill(getPID(), ...)` on the negative PID (process group) [8](#0-7)  — if the grandchild used `setsid`/detached itself from the job's process group, it is not in that group and is not killed, so it can continue holding the pipe open even after force-kill, at which point `KillAndWait` gives up after `forceKillTimeout` returning a `KillProcessError`, but the pipe/stream `Close()` in `custom.go`'s `defer opts.out.Close()` [2](#0-1)  can still block since the underlying `Write`/`Close` machinery is tied to the same leaked pipe/goroutine resources.

No existing check in the custom executor guards against this: there is no `WaitDelay`, no timeout on the internal pipe-copy goroutines, and process-group-based killing does not cover processes that detach from the group (`setsid`, double-fork daemonization) before the parent driver process exits.

### Impact Explanation
This ties up the shared runner-process log-streaming resources (goroutines, pipe file descriptors, and — if `Close()` also blocks — the underlying `buildlogger.Logger` write path) for the duration the detached grandchild lives, which an attacker fully controls (it can be made effectively infinite, e.g. `sleep infinity`). Since these are process-wide OS pipes and goroutines rather than per-job isolated resources, a job author can cause resource leakage/exhaustion (leaked fds/goroutines) on the runner host that can accumulate across repeated job runs and potentially degrade or block log delivery for other concurrently running jobs sharing the same runner process, matching the scoped impact.

### Likelihood Explanation
Preconditions are fully attacker-reachable by a normal CI job author: only a custom-executor runner is required (a supported, common runner configuration), and the job's own `script:` (fully job-author-controlled) is what spawns the detached grandchild — no admin misconfiguration beyond "use custom executor" is needed. This is straightforward to trigger reliably with a one-line script (`setsid nohup sleep infinity >/dev/null 2>&1 &` while leaving stdout/stderr fds duplicated, or more precisely leaving the fd un-redirected on a detached child) and reproducible every time.

### Recommendation
Set `exec.Cmd.WaitDelay` on the underlying `exec.Cmd` in `helpers/process/commander.go`/`job_unix.go` (and the Windows equivalent) so `Wait()` cannot hang indefinitely on inherited pipes; upon `WaitDelay` expiry, Go will forcibly close the pipes, allowing `Wait()`/stream `Close()` to return, and killed/leaked grandchildn should be logged. Additionally, consider killing the full process tree/session (not just the process group) in `killer_unix.go` (e.g., via a session ID or cgroup) to also terminate detached grandchildren.

### Proof of Concept
Go integration test in `helpers/process`:
```go
func TestOSCmd_Wait_GrandchildInheritsPipe(t *testing.T) {
    var buf syncBuffer // io.WriteCloser wrapper, NOT *os.File
    opts := CommandOptions{
        Stdout: &buf,
        Stderr: &buf,
    }
    // script: launches a detached grandchild that duplicates stdout fd and sleeps
    cmd := NewOSCmd("/bin/sh", []string{"-c", "setsid sh -c 'sleep 30' & exit 0"}, opts)
    require.NoError(t, cmd.Start())

    done := make(chan error, 1)
    go func() { done <- cmd.Wait() }()

    select {
    case <-done:
        // expected: Wait returns promptly after direct child exits
    case <-time.After(3 * time.Second):
        t.Fatal("Wait() hung due to grandchild holding stdout/stderr pipe open")
    }
}
```
Assertions: `cmd.Wait()` must return within a bounded timeout (e.g. 3s) even though the detached grandchild is still running and holding the pipe fd; currently it will hang until the grandchild (`sleep 30`) exits, demonstrating the leak/hang.

// wrap wraps the underlying writer with "filters". Order here somewhat
// matters, and the order they're instantiated in is the reverse order in which
// writes are processed, e.g. last added filter is the first to process data.
//
// order:
// - sync writer to ensure that multiple writes cannot happen concurrently
// - mask phrases (masker.New)
// - mask sensitive URL parameters (urlsanitizer.New)
// - mask secrets with a prefixed token (tokentanitizer.New)
// - split log lines and add timestamps (timestamper.New)
func (l *Logger) wrap(w io.WriteCloser, streamID int, streamType StreamType) io.WriteCloser {
	if l.timestamping {
		w = timestamper.New(w, timestamper.StreamType(streamType), uint8(streamID), true)
	}

	w = tokensanitizer.New(w, l.maskTokenPrefixes)
	w = urlsanitizer.New(w)
	w = masker.New(w, l.maskPhrases)
	w = internal.NewSync(w)

	return w
}

func (c *command) waitForCommand() {
	err := c.cmd.Wait()

	eerr, ok := err.(*exec.ExitError)
	if ok {
		exitCode := getExitCode(eerr)
		switch {
		case exitCode == BuildFailureExitCode:
			err = c.parseBuildFailure(eerr)
		case exitCode != SystemFailureExitCode:
			err = &ErrUnknownFailure{Inner: eerr, ExitCode: exitCode}
		}
	}

	c.waitCh <- err
}

func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}

// getPID will return the negative PID (-PID) which is the process group. The
// negative symbol comes from kill(2) https://linux.die.net/man/2/kill `If pid
// is less than -1, then sig is sent to every process in the process group whose
// ID is -pid.`
func (pk *unixKiller) getPID() int {
	return pk.cmd.Process().Pid * -1
}
