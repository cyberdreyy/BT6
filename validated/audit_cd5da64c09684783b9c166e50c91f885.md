### Title
v1 `validate_tenure_change_payload` duplicate-block check ignores locally-accepted (only-signed) blocks, allowing equivocation on tenure-start - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`SortitionsView::validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` rejects a competing tenure-start block only if `signer_db.get_last_globally_accepted_block` finds a prior block in the same tenure, whereas the v2 equivalent in `stacks-signer/src/chainstate/v2.rs` deliberately checks `signer_db.get_last_signed_block`, which also covers locally-accepted-but-not-globally-accepted blocks. A signer running v1 chainstate can therefore be induced to sign a second, competing tenure-change block for a tenure in which it has already signed (but only locally accepted) a prior block.

### Finding Description
The uniqueness property that must hold is: for a given tenure-start (i.e., a specific `consensus_hash`), a signer must sign at most one block. v1 implements this guard as: [1](#0-0) 

which only queries `get_last_globally_accepted_block`. If the signer previously signed a block for that tenure but it never reached global acceptance (e.g., insufficient signers reached consensus, or a partition), this call returns `None`, and the duplicate check passes.

v2 explicitly fixes this by using `get_last_signed_block`, with an inline comment explaining the rationale that a locally-or-globally signed block still carries this signer's actual signature and must not be double-signed for a competing tenure-start block, while a merely pre-committed (unsigned) block does not count: [2](#0-1) 

This asymmetry means that a v1-pinned signer, upon receiving a second tenure-change `BlockProposal` for the same `consensus_hash`/tenure (crafted by the attacker who won that miner slot, or via a naturally occurring competing block for the same sortition), will call `check_proposal` → `validate_tenure_change_payload` → `get_last_globally_accepted_block` (returns `None`) → `Ok(())`, and proceed to sign the second block, exactly as the call sequence in the question describes. The other checks in `check_proposal` (miner pubkey match, parent tenure choice, bitvec, tenure-extend cause) do not check for a previously-signed sibling block at the same tenure-start height; they only validate that the *proposed* block's own commit metadata is internally consistent, not that it is unique versus a prior locally-signed sibling.

### Impact Explanation
This breaks the UNIQUENESS chain-safety property: a signer can be made to produce two distinct signatures for two different blocks at the same (tenure, height) pair. If enough v1-pinned signers are convinced similarly (attacker only needs to gossip both competing proposals and win/exploit a miner slot for the second one), this can result in two sibling tenure-start blocks each collecting signer signatures — a classic equivocation/fork condition at the signer layer, matching the "Critical: signer signing a … conflicting block (chain safety) … signature valid across chain/cycle/tenure boundaries" category.

### Likelihood Explanation
Preconditions: the target signer must be running v1 chainstate (deployed naturally in a mixed-version signer set, or forced via a protocol-version pin as noted in the question) and must have a `BlockInfo` for the tenure that is locally signed but not yet globally accepted — a state reachable during normal degraded signer-set participation, not merely through attacker action. The attacker's incremental work is limited to winning a single miner slot and gossiping a competing tenure-change `BlockProposal` that references the same tenure consensus hash — well within the stated unprivileged-attacker capability (one miner slot plus StackerDB/gossip message crafting), and is repeatable across tenures.

### Recommendation
Change v1's `validate_tenure_change_payload` to use `signer_db.get_last_signed_block` (or equivalent local-or-global signed check) instead of `get_last_globally_accepted_block`, matching the v2 semantics, so that any block this signer has already signed for the tenure — regardless of global acceptance — blocks a second competing tenure-start signature.

### Proof of Concept
Add a test in `stacks-signer/src/chainstate/tests/v1.rs` (or wherever v1 chainstate unit tests live) that:
1. Inserts a `BlockInfo` for a tenure's first block into `SignerDb` and marks it as locally signed/accepted only (not globally accepted) — i.e., ensure `get_last_globally_accepted_block(&consensus_hash)` returns `None` while `get_last_signed_block(&consensus_hash)` (or the underlying signed-block query) would return `Some`.
2. Construct a second `NakamotoBlock` with a `TenureChangePayload` targeting the same `consensus_hash`/tenure and a `ProposedBy` matching the sortition data.
3. Call `SortitionsView::validate_tenure_change_payload` (v1) on the second block and assert it returns `Ok(())` — demonstrating the missed duplicate.
4. As the comparison side of the equality, run the same setup through `GlobalStateView::validate_tenure_change_payload` (v2) and assert it returns `Err(RejectReason::DuplicateBlockFound)`, proving the asymmetry and that v2's `get_last_signed_block` check correctly blocks the same scenario that v1 allows.
