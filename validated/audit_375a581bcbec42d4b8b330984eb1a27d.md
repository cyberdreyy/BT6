## Title
Stake delegation mutated between reward calculation and reward distribution causes a `distribute_epoch_rewards_in_partition` panic on every replaying validator - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

## Summary
`TieredPercentageBountyV1` snapshotted a token balance at `closeCompetition` time and later paid out based on that stale snapshot; a subsequent legitimate action (a refund) invalidated the snapshot and broke payout. Agave's partitioned epoch-rewards machinery has the same "snapshot now, act on it later" pattern for stake delegations: `Bank::calculate_stake_rewards_and_commissions` snapshots each stake account's `delegation.stake` at the epoch boundary and bakes the post-reward delegation value into a `PartitionedStakeReward`. Distribution of that reward happens several blocks later, in `Bank::build_updated_stake_reward`, which re-reads the *current* delegation from `StakesCache` and asserts it is still consistent with the value computed at calculation time.

## Finding Description
`Bank::build_updated_stake_reward` in [1](#0-0)  loads the *current* stake account from `stakes_cache_accounts` (i.e., the live `StakesCache` at distribution time, not the state captured at calculation time). When the rent-adjustment feature path is not taken, it performs: [2](#0-1)

`stake.delegation.stake` here is read live from `StakesCache` at *distribution* time, while `new_stake.delegation.stake` (`partitioned_stake_reward.inflation.stake`) was computed at *calculation* time (epoch boundary) — see `recalculate_stake_rewards`'s own comment about this exact hazard: [3](#0-2) . Reward calculation happens once at the epoch boundary, but distribution is spread over `distribution_starting_block_height .. distribution_end_exclusive`, a window that can span up to 10% of the epoch's slots, as computed in `get_reward_distribution_num_blocks`: [4](#0-3) .

During that multi-block window, the stake authority for any of the stake accounts already included in the calculated `PartitionedStakeRewards` can submit an ordinary, unprivileged `Split` or `Merge` stake-program instruction against their own stake account. Both instructions legitimately change `delegation.stake` on the affected account (Split reduces the source account's stake, Merge combines two accounts' stakes) without any restriction tied to pending reward distribution — the code comment in `store_stake_accounts_in_partition` merely asserts (as an unverified assumption) that "stake accounts are checked in calculation, and further state mutation prevented by stake-program restrictions" [5](#0-4) , but no actual mechanism enforces this in the code being reviewed.

When the block containing that account's assigned reward partition is later processed, `build_updated_stake_reward` compares the now-stale calculated `new_stake.delegation.stake` against the live (mutated) `stake.delegation.stake`, and the `assert_eq!` fails, causing an `assert_eq!` panic during deterministic bank/reward distribution (`distribute_epoch_rewards_in_partition`, invoked from `distribute_partitioned_epoch_rewards`, which runs on every validator replaying/producing that block: [6](#0-5) ).

This mirrors the OpenQ bug class precisely: a value snapshotted for a payout calculation (percentage-tier balance / stake delegation) is invalidated by a subsequent, otherwise-legitimate user action (refund / stake split) performed before the snapshot is consumed, and the mismatch is fatal to the payout path rather than being reconciled.

## Impact Explanation
Because `distribute_epoch_rewards_in_partition` executes deterministically as part of block processing (not inside a sandboxed transaction), an `assert_eq!` panic here crashes the bank-processing thread on every validator that replays or produces the affected block. Since every conforming validator performs the exact same computation on the exact same state, this is not a localized DoS against one node — it is a cluster-wide halt triggered by a single unprivileged `Split`/`Merge` transaction sent by any staker whose stake account happens to fall in the not-yet-distributed reward partition for the current epoch.

## Likelihood Explanation
This bug is only reachable while the non-rent-adjusted branch is taken, i.e., when the `relax_post_exec_min_balance_check` feature (gating `adjust_delegations_for_rent`) is not active for the epoch: [7](#0-6) . Whether this feature is active cluster-wide cannot be determined from the repository alone; if it is active on the target cluster, this specific `assert_eq!` path is currently dead code and the likelihood is effectively zero. If the feature is inactive (e.g., on a cluster still on the pre-SIMD-0392 code path, or during any feature-gate transition period), the trigger only requires an ordinary staker to submit a `Split` or `Merge` instruction on their own stake account inside the reward-distribution window of the epoch in which their account is scheduled to be rewarded — a normal, permissionless operation.

## Recommendation
- Do not assert hard equality between the delegation value computed at calculation time and the live delegation at distribution time; instead, always recompute the final delegation from the *current* stake state plus the reward, mirroring what `adjust_delegation_for_rent` already does unconditionally, regardless of feature-gate status.
- Alternatively, disallow `Split`/`Merge`/`Delegate` instructions from being processed against stake accounts that have an outstanding reward scheduled but not yet distributed for the current epoch, so the "further state mutation prevented by stake-program restrictions" comment in `store_stake_accounts_in_partition` reflects an enforced invariant rather than an assumption.
- Replace the `assert_eq!` with a recoverable error path (as already done for `AccountNotFound` and `ArithmeticOverflow` in the same function) so a mismatch degrades to a burned/logged reward instead of panicking the bank.

## Proof of Concept
1. Wait for (or force, in a test harness) an epoch boundary so that a target stake account `S` (owned by attacker-controlled authority) is included in `PartitionedStakeRewards` computed by `calculate_stake_rewards_and_commissions`, with the reward-distribution window spanning `get_reward_distribution_num_blocks` blocks.
2. Before the block height reaches the partition assigned to `S` (i.e., while `distribute_partitioned_epoch_rewards` is still in `EpochRewardPhase::Distribution` for a later partition index), submit an ordinary `Split` (or `Merge`) instruction from `S`'s stake authority, reducing/changing `S`'s `delegation.stake`.
3. When block processing reaches the block height/partition index assigned to `S`, `Bank::distribute_partitioned_epoch_rewards` → `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` → `build_updated_stake_reward` is invoked for `S`.
4. If `adjust_delegations_for_rent` is `false` for this epoch, the `assert_eq!` at [8](#0-7)  fails because `stake.delegation.stake` (post-Split, live) plus the reward no longer equals `new_stake.delegation.stake` (pre-Split, calculated), panicking the bank-processing code path on every validator that processes this block.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
