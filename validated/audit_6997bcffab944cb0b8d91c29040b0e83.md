### Title
Malicious taker-supplied fee parameters in `createDstEscrow` cause underflow revert in `EscrowDst._withdraw`, permanently blocking withdrawal - (File: contracts/BaseEscrowFactory.sol, contracts/EscrowDst.sol)

### Summary
This is a direct analog of the reported stETH vault bug: an unchecked subtraction that assumes a value relationship (`totalAssets >= lastRoundAssets` in the stETH report, `immutables.amount >= integratorFeeAmount + protocolFeeAmount` here) that is not actually enforced on the code path that matters, allowing an unprivileged actor to corrupt state so the subtraction underflows and reverts, freezing funds.

### Finding Description
`EscrowDst._withdraw` computes the maker's payout as: [1](#0-0) 
```
uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
...
uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
```
This subtraction is safe **only** if `integratorFeeAmount + protocolFeeAmount < immutables.amount`. On the source-escrow path (`_postInteraction`), this invariant is explicitly enforced: [2](#0-1) 

However, `createDstEscrow` — the function used to deploy the destination escrow — accepts the entire `Immutables` struct, including the `parameters` field that encodes `protocolFeeAmount`/`integratorFeeAmount`, directly from the caller (the taker/resolver) with **no equivalent check**: [3](#0-2) 

The taker fully controls `dstImmutables`, including `amount`, `parameters` (fee amounts/recipients), and funds the escrow according to `dstImmutables.amount` (native or ERC20). Nothing prevents the taker from setting `protocolFeeAmount + integratorFeeAmount > amount` while still funding the escrow correctly for the `createDstEscrow` balance checks (which only check `msg.value`/`transferFrom` equal `immutables.amount` + safety deposit, not fee consistency).

Once such an escrow is deployed, any call to `withdraw`/`publicWithdraw` (by the maker, taker, or a public access-token holder) reaches `_withdraw`, and the final subtraction `immutables.amount - integratorFeeAmount - protocolFeeAmount` underflows and reverts, exactly mirroring the stETH `totalAssets - lastRoundAssets` underflow pattern.

### Impact Explanation
The maker can never withdraw from this destination escrow during the withdrawal/public-withdrawal windows since `_withdraw` always reverts. Because `cancel` does not perform this subtraction (it always sends `immutables.amount` back to the taker) — [4](#0-3)  — once the cancellation timelock passes, the malicious taker can reclaim the full destination amount for themselves via `cancel`, while having already withdrawn the corresponding source-chain funds using the revealed secret. This results in the maker permanently losing the destination-side leg of the swap — a temporary freezing of funds during the live swap lifecycle that resolves into an actual loss for the maker once the taker cancels, matching the High/Medium impact bar (theft/permanent loss of funds, or a contract path that can be broken by an unprivileged actor's supplied balances).

### Likelihood Explanation
Any taker calling `createDstEscrow` is by protocol design an ordinary (unprivileged) participant, not a privileged resolver role in the bounty's excluded sense — this is the standard entry point for initiating the destination side of an atomic swap. Crafting `parameters` with `protocolFeeAmount + integratorFeeAmount > amount` requires no special access, only calldata control over `dstImmutables`, making this trivially reachable.

### Recommendation
Add the same guard used in `_postInteraction` to `createDstEscrow`, rejecting fee parameters that are not strictly less than `dstImmutables.amount` before deployment/funding:
```solidity
(uint256 integratorFeeAmount, uint256 protocolFeeAmount) = (dstImmutables.integratorFeeAmount(), dstImmutables.protocolFeeAmount());
if (integratorFeeAmount + protocolFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
Alternatively/additionally, guard the subtraction in `EscrowDst._withdraw` itself so a bad fee configuration cannot brick withdrawal, analogous to placing the stETH yield-transfer logic behind an `if (totalAssets > lastRoundAssets)` check.

### Proof of Concept
1. Attacker (taker) builds `dstImmutables` with `amount = X`, but encodes `parameters` such that `protocolFeeAmount + integratorFeeAmount > X`.
2. Attacker calls `createDstEscrow{value: safetyDeposit (+X if native)}(dstImmutables, srcCancellationTimestamp)` — this succeeds because `createDstEscrow` only checks that funding matches `amount`, not fee consistency (`contracts/BaseEscrowFactory.sol:165-185`).
3. Maker (or anyone) later calls `withdraw(secret, dstImmutables)` during the withdrawal window — `_withdraw` reverts on `immutables.amount - integratorFeeAmount - protocolFeeAmount` (`contracts/EscrowDst.sol:92`).
4. Withdrawal remains impossible through the entire withdrawal and public-withdrawal windows.
5. After the cancellation timelock elapses, the taker calls `cancel(dstImmutables)`, which sends the full `amount` back to the taker (`contracts/EscrowDst.sol:70`) — the taker recovers the destination funds while having already withdrawn the source-chain funds with the revealed secret, resulting in maker's total loss of the swap's destination-side value.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
