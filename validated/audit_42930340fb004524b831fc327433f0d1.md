### Title
Missing replay protection for legacy `api.Message` (`web_api_trigger`) requests allows replay of validly-signed messages - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`Message.Sign`/`Message.SignKS` (`core/services/gateway/api/message.go`) produce a signature over `MessageId`, `Method`, `DonId`, `Receiver`, and `Payload`, but neither `Message.Validate` nor `gateway.ProcessRequest` nor the legacy `handler.HandleLegacyUserMessage` check whether a given `(Sender, MessageId)` pair (or signature) has already been processed. As a result, a previously captured, still-fresh (within `MaxAllowedMessageAgeSec`) signed legacy message can be resubmitted to the gateway's HTTP endpoint and will be forwarded to the DON a second time.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`) decodes the raw request, calls `msg.Validate()` for legacy (DonId-based) requests, and then dispatches to `handler.HandleLegacyUserMessage`. `Message.Validate` (`core/services/gateway/api/message.go:54-88`) checks field lengths and re-derives the sender from the signature via `ExtractSigner`, but performs no uniqueness/nonce check on `MessageId` or the signature itself.

In `core/services/gateway/handlers/capabilities/handler.go:341-421`, `HandleLegacyUserMessage` only rejects messages that are structurally invalid, use the wrong method, or are stale by payload timestamp (`payload.Timestamp` vs `MaxAllowedMessageAgeSec`, lines 359-383). It then unconditionally stores/overwrites an entry in `h.savedCallbacks` keyed by `msg.Body.MessageId` and re-broadcasts the request to every DON member: [1](#0-0) 

There is no lookup against a replay/digest cache before this send, unlike the parallel `RequestCache.NewRequest` implementation used by `confidentialrelay` handler (`core/services/gateway/handlers/common/requestcache.go:50-63`, which explicitly returns `"request already exists"`), the vault `RequestReplayGuard` (`core/capabilities/vault/request_replay_guard.go`), and the JWT `jwtReplayCache` used by the v2 workflow trigger handler (`core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go:392-412`). The legacy `capabilities/handler.go` path was never wired to any of these protections; the code even contains a `// TODO: apply allowlist and rate-limiting here` marker acknowledging the gap.

Because the map write at line 412 simply overwrites any existing `savedCallbacks[msg.Body.MessageId]` entry rather than rejecting a duplicate, and the `don.SendToNode` loop executes regardless, resubmitting identical raw bytes causes the gateway to relay the trigger request to the DON a second time — a fresh dispatch, not a no-op — before the still-fresh timestamp expires.

### Impact Explanation
An attacker who can observe a legitimate, still-valid signed `web_api_trigger` message (e.g., relayed over a network path the attacker can view, or a message that legitimately passes through less-trusted intermediaries) can resend the exact same bytes to the gateway HTTP endpoint and force the DON nodes to receive and process the trigger request again. For workflow triggers tied to real-world actions (e.g., firing external price updates or automation events into a workflow), this can cause duplicate/unintended re-execution of a capability call attributable to another user's original signed request, violating the "one request → one execution" attribution invariant. This maps to Chainlink's "unauthorized job run" / request-impersonation impact class, though impact severity is bounded by the short freshness window and by the fact that this only affects the legacy `web_api_trigger` method, not the newer JWT/vault-protected paths, which already have replay guards.

### Likelihood Explanation
No privileged access is required — only network visibility to the raw signed bytes of a genuine gateway request. The replay must occur within `MaxAllowedMessageAgeSec` of the original payload timestamp, and it is fully repeatable for any number of resends within that window since nothing marks the `MessageId`/signature as consumed. This is a straightforward, deterministic exploitation path, contingent only on the attacker being able to capture one valid signed message.

### Recommendation
Add a replay guard to the legacy `HandleLegacyUserMessage` path, analogous to `common.RequestCache.NewRequest`'s "request already exists" check or the vault `RequestReplayGuard`: before overwriting `savedCallbacks[msg.Body.MessageId]` and dispatching to nodes, reject the message if `(Sender, MessageId)` (or the signature) was already seen within the freshness/TTL window, returning a duplicate-request error to the caller instead of resending.

### Proof of Concept
Go handler-level integration test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build a valid signed `api.Message` for `MethodWebAPITrigger` via `triggerRequest(...)` (as already used in `TestHandlerReceiveHTTPMessageFromClient`).
2. Call `handler.HandleLegacyUserMessage(ctx, msg, cb1)`; assert `don.SendToNode` is invoked once per DON member and succeeds.
3. Immediately call `handler.HandleLegacyUserMessage(ctx, msg, cb2)` with the *same* `msg` (identical `MessageId`/signature) before its timestamp/`MaxAllowedMessageAgeSec` window expires.
4. Assert (current buggy behavior) that `don.SendToNode` is called again for the second submission and no error is returned — demonstrating the message is processed a second time — versus the expected/fixed behavior where the second call returns a "duplicate request"/"already processed" error and `don.SendToNode` is not invoked again.
