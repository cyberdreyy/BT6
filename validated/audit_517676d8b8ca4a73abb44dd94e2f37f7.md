### Title
`get_builder_withdrawals()` commits an uncapped withdrawal amount while `apply_withdrawals()` only deducts the builder's actual (possibly lower) balance, minting unbacked Gwei on the execution layer - (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` builds `Withdrawal.amount` directly from the queued `BuilderPendingWithdrawal.amount` without checking it against the builder's current balance, while `apply_withdrawals` deducts only `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance`. Because a builder's balance can shrink between the time a pending withdrawal is queued and the time it is swept, the beacon block can commit (via `state.payload_expected_withdrawals`, which the execution layer is required to honor exactly) to paying out more Gwei than is actually removed from the consensus-layer state, breaking the base-fee/total-supply invariant.

### Finding Description
`get_builder_withdrawals` (called from `get_expected_withdrawals`) builds the withdrawal that is committed to the execution layer straight from the queue entry, with no balance cap: [1](#0-0) 

`apply_withdrawals`, which actually mutates consensus-layer state, caps the deduction to the builder's *current* balance: [2](#0-1) 

These two functions disagree on the "available" amount exactly like the reported `VaultBooster._computeAvailable()` bug: the committed/output value (`withdrawal.amount`, analogous to the reported contract's `boost.available`) is not re-clamped against the real backing balance at execution time, while the state-mutation side (`apply_withdrawals`, analogous to `_computeAvailable`'s `min(deltaAmount, availableBalance)`) clamps only the *delta*, not the *final result* that gets paid out.

A `BuilderPendingWithdrawal` is enqueued with an amount that was valid *when queued* (e.g. from `process_execution_payload_bid` / `settle_builder_payment`, which validate `can_builder_cover_bid` at bid time): [3](#0-2) [4](#0-3) 

But `can_builder_cover_bid` is only evaluated once, at the moment a *new* bid is accepted. It does not re-verify existing balance sufficiency after the fact, and a builder can win further bids or accrue additional pending payments/withdrawals in the queue ahead of an earlier entry, draining `builder.balance` before that earlier `BuilderPendingWithdrawal` is swept by `get_builder_withdrawals`/`apply_withdrawals`. When that happens, `get_builder_withdrawals` still emits `Withdrawal(amount=withdrawal.amount)` — the full, now-unbacked, originally-queued amount — into `state.payload_expected_withdrawals`, which per the spec's own note must be honored exactly by the execution layer: [5](#0-4) 

Meanwhile `apply_withdrawals` only removes `min(withdrawal.amount, builder_balance)` from the consensus-layer `builder.balance`. The result is that the EL credits `withdrawal.amount` Gwei to `fee_recipient`, while the CL removes strictly less than that from any account. The spec's own test suite explicitly documents and asserts this exact mismatch as expected behavior: [6](#0-5) 

and the input/output specification report for the function even states the discrepancy as a "balance threshold" rule rather than flagging it as an inconsistency: [7](#0-6) 

### Impact Explanation
This breaks the "Gwei created... paid to a non-owner" invariant category: the withdrawal that the execution layer is contractually bound to honor (`payload_expected_withdrawals`) can specify a payout larger than what is actually deducted from the corresponding builder's consensus-layer balance. That is Gwei manufactured on the EL side with no matching removal on the CL side — a critical, spec-level total-supply violation, not merely a failed-transfer/DoS as in the original contract bug (since EL withdrawals cannot revert or fail-partially: they must credit the committed amount).

### Likelihood Explanation
Reachable without any malicious peer, client bug, or coalition: an honest builder can legitimately win multiple bids across slots (each individually validated via `can_builder_cover_bid` against the balance *at bid time*), producing several queued `BuilderPendingWithdrawal`/`BuilderPendingPayment` entries whose sum can exceed later-available balance once earlier entries in the same queue are drained first, or once a subsequent lower bid still validates only against a smaller minimum required balance. The queue ordering (`update_builder_pending_withdrawals` slices from the front) and the fact that `get_builder_withdrawals` never re-checks `builder.balance` at sweep time make this a straightforward sequencing issue, not a low-probability edge case.

### Recommendation
Clamp the amount that is placed into the committed `Withdrawal` object in `get_builder_withdrawals` to the builder's current balance (accounting for all withdrawals already queued ahead of it in the same block, similar to how `get_balance_after_withdrawals` is used for validator withdrawals), so that `Withdrawal.amount` always equals the amount actually deducted in `apply_withdrawals`. Equivalently, `apply_withdrawals` should not silently under-deduct; the two functions must agree on the same balance-capped value before either is used.

### Proof of Concept
1. Builder `B` wins bid A for slot `n` when `balance(B) = 5 ETH`; `can_builder_cover_bid` passes and a `BuilderPendingPayment`/`BuilderPendingWithdrawal` for `5 ETH` (minus reserve) is queued.
2. Before that withdrawal is swept, `B` wins another bid for slot `n+1` for `4 ETH`, which the check `can_builder_cover_bid` validates only against `balance(B)` and `pending_withdrawals_amount` *at that instant* (per `specs/gloas/beacon-chain.md:1171-1179`); this can be structured across two blocks so each individual check passes.
3. When `get_builder_withdrawals` finally sweeps the first queued withdrawal, `builder.balance` may already be reduced by other queued/settled payments below the queued amount.
4. `get_builder_withdrawals` still emits `Withdrawal(amount = queued_amount)` (uncapped) into `payload_expected_withdrawals` (`specs/gloas/beacon-chain.md:1815-1834`).
5. `apply_withdrawals` only deducts `min(queued_amount, builder.balance)` from `state.builders[...].balance` (`specs/gloas/beacon-chain.md:1922-1932`), which is strictly less than `queued_amount`.
6. The execution layer, bound to honor `payload_expected_withdrawals` exactly, credits `fee_recipient` the full uncapped `queued_amount`, exceeding what was removed from the consensus layer — this exact scenario (`withdrawal.amount` = 5 ETH vs. capped balance deduction = 1 ETH) is reproduced verbatim by the spec's own unit test `test_builder_withdrawal_insufficient_balance`.
