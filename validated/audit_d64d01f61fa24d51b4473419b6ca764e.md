### Title
`check_parent_tenure_choice` permits unbounded-depth reorgs by validating each superseded tenure independently instead of bounding total reorg depth - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` walks the list of tenures returned by `client.get_tenure_forking_info` and rejects the reorg only if some *individual* tenure in that list has more than one globally-accepted block (or fails the late-proposal timing check). It never bounds the number of tenures being superseded, so a miner whose new tenure's `parent_tenure_id` points arbitrarily far back in history can have an entire run of N one-block (or zero-block) tenures superseded in a single call, as long as each one individually satisfies the "<=1 block" rule.

### Finding Description
The function is reached from `SortitionState::is_tenure_valid` → `check_parent_tenure_choice`, which is the gate signers use to decide whether a proposed tenure's parent choice is a legitimate reorg [1](#0-0) .

Once `self.prior_sortition != self.parent_tenure_id`, the code fetches `tenures_reorged` from the node and loops over *every* tenure between the prior sortition and the claimed parent tenure [2](#0-1) . For each tenure in that list, the only hard rejection is `globally_accepted_blocks > 1` [3](#0-2) ; a tenure with zero blocks is unconditionally pushed to `superseded_tenures` [4](#0-3) , and a tenure with exactly one late-arriving block is also pushed to `superseded_tenures` if the proposal-to-sortition timing is short [5](#0-4) . If every tenure in the (arbitrarily long) list clears these per-tenure checks, the loop finishes, and *all* of them are marked superseded and the reorg is permitted: `Ok(true)` [6](#0-5) .

Nowhere in this function (or its caller chain, `is_tenure_valid`) is `tenures_reorged.len()` — i.e., the depth of the reorg — checked against any bound such as `MAX_FORK_DEPTH`. That constant only appears in `stacks-signer/src/v0/signer.rs`, unrelated to this call path. The doc comment at the top of the function frames the intended guarantee as permitting only a reorg of "the single-tenure-depth" kind (built to tolerate one poorly-timed miner tenure at a burn-block boundary) [7](#0-6) , but the implementation enforces this per-tenure, not in aggregate — so a chain of N tenures, each individually a "valid single-hop reorg candidate," is accepted as one big reorg of depth N.

An attacker who wins one sortition can set the `parent_tenure_id` in their tenure-change/block proposal to point back past any number of prior tenures. If those historical tenures each happen to carry `<=1` globally accepted block (common when tenures are short, empty, or end near a burn-block boundary — a legitimately unprivileged, gossip-only attacker does not even need to have mined those prior tenures themselves), `check_parent_tenure_choice` will walk through and supersede all of them in a single approval, and `record_superseded_tenure` will mark every one of them superseded in the signer DB [8](#0-7) .

### Impact Explanation
This breaks canonicity: signers are induced to sign a block that discards N tenures' worth of chain history via one signer-check pass, when the check's intent (per its own doc comment) is to permit only a single-tenure-deep reorg. Because signing this block finalizes an N-deep reorg once enough signers repeat the same (locally consistent) evaluation, this is a Critical, chain-safety-breaking issue — signers "signing" a much deeper reorg than the rule is designed to sanction, using only one attacker-controlled miner slot's proposal.

### Likelihood Explanation
The attacker needs only to win one sortition (one BTC-funded miner slot) and craft a `parent_tenure_id` referencing a distant ancestor tenure; no majority-signer collusion, no auth token, and no local host access are required. The precondition — a run of N consecutive tenures each with `<=1` globally-accepted block — is realistic in networks with irregular block production (idle tenures, tenure-extends, or tenures cut short near burn-block boundaries), and is entirely determined by pre-existing chain history the attacker merely needs to identify, not forge. The exploit is repeatable each time such a run of thin tenures exists.

### Recommendation
Bound the aggregate reorg depth in `check_parent_tenure_choice` itself — e.g., reject the reorg if `tenures_reorged.len()` (excluding the built-upon tenure) exceeds a small constant (such as 1, or a proper `MAX_FORK_DEPTH`), independent of whether each individual tenure passes the per-tenure `<=1 block` / timing checks. This restores the documented invariant of only permitting single-hop reorgs.

### Proof of Concept
Extend `refused_reorg_supersedes_nothing` in `stacks-signer/src/chainstate/tests/v2.rs`:
1. Build a chain of N (e.g., 5) consecutive tenures, each with exactly one globally-accepted block, each timed so it passes the "poorly timed" late-proposal check (or with zero blocks) — mirroring the setup helpers already used in `refused_reorg_supersedes_nothing`.
2. Construct `tenures_reorged` as a `Vec<TenureForkingInfo>` containing all N tenures, with `client.get_tenure_forking_info` mocked to return this full chain.
3. Call `check_parent_tenure_choice` with `parent_tenure_id` set to the tenure before all N, and `prior_sortition` set to the tip.
4. Assert that the current implementation returns `Ok(true)` and that all N tenures get marked superseded via `signer_db.mark_tenure_superseded`/`get_tenure_forking_info` lookups — demonstrating the N-deep reorg is accepted in one call, contradicting the intended single-hop-only guarantee.
