### Title
Reward attributed to shares bought after it accrued — bare-donation front-running of `internal_ping` epoch batching (`staking-pool/src/internal.rs`)

### Summary
`internal_ping` only distributes rewards once per epoch and is a no-op if called again within the same epoch, and a bare `Transfer` to the pool account never invokes `internal_ping` at all. An attacker can send an unaccounted-for `Transfer` to the pool, then `deposit`+`stake` within the same epoch — before the next epoch-boundary `ping` — buying "stake" shares at the pre-reward price. When `ping` eventually fires in the next epoch, the untracked balance increase is priced in and split across all shares then outstanding, including the attacker's newly purchased shares, siphoning value from the depositors who held shares while the balance increase actually happened.

### Finding Description
The invariant claimed is: for a balance increase Δ that materializes on-chain at some point in epoch E, Δ must be split only among `total_stake_shares` as they existed when Δ arrived, i.e. `shares_outstanding_at_Δ_time == shares_outstanding_at_reward_distribution_time`. The contract breaks this because reward accounting is deferred and batched per-epoch rather than per-event.

`internal_ping` at [1](#0-0)  only executes the reward calculation when `env::epoch_height()` differs from `self.last_epoch_height`; otherwise it returns `false` immediately without reading or updating `last_total_balance`. A bare `Transfer` sent directly to the pool account (outside any method call) never triggers `internal_ping` at all — it silently increases `env::account_balance()` while `self.last_total_balance` stays stale.

`stake()` calls `internal_ping()` first and `internal_stake()` second, per [2](#0-1) . If the epoch has not changed since the last ping, `internal_ping()` is a no-op, so `internal_stake` at [3](#0-2)  mints new shares using `self.total_staked_balance` / `self.total_stake_shares` that do not yet reflect the balance already sitting in the account from the bare transfer.

Exploit flow:
1. Any account triggers a ping in epoch E (e.g., another user's `deposit`), setting `last_epoch_height = E`, `last_total_balance = current balance`.
2. Attacker sends a bare `Transfer` of `X` NEAR straight to the pool account. This bypasses every contract method, so it is invisible to `last_total_balance`.
3. Still in epoch E, attacker calls `deposit` then `stake` (or `deposit_and_stake`). `internal_ping()` is a no-op (same epoch), so `internal_stake` mints shares at the stale, pre-`X` price.
4. Epoch changes to E+1. Anyone calling any pool method triggers `internal_ping`, which now computes `total_reward = total_balance - last_total_balance ≈ X` (the untracked donation) and adds it to `self.total_staked_balance`, raising the share price for every share currently outstanding — including the attacker's shares bought in step 3 at the old price.
5. The attacker's new shares capture a pro-rata portion of `X` that should have accrued entirely to the shares that existed *before* the attacker joined in epoch E, since those pre-existing holders are the ones whose value the pool represented while `X` was sitting unaccounted on the balance.

None of the existing guards prevent this: `internal_ping`'s balance assertion at [4](#0-3)  only checks the balance didn't decrease, and there is no check that shares minted mid-epoch are excluded from a later cross-epoch reward distribution. The behavior is even acknowledged for the "accidental transfer" case in the README ("tokens from the transfer will be distributed to the active stake participants of the contract in the next epoch" — [5](#0-4) ), but the README does not account for an attacker deliberately timing a stake purchase between the donation and the eventual `ping` to capture part of that donation (or any other unaccounted-for balance delta, such as gas rebates or a failed-withdraw refund) for themselves.

### Impact Explanation
Value that should accrue entirely to shares outstanding before the attacker's stake is instead split proportionally with the attacker's newly minted shares, mis-crediting rewards away from the legitimate earlier depositors/owner to the attacker. This matches the "High — rewards or owner fees attributed to the wrong party" category: no funds leave the contract to an outside address, but the internal accounting (`total_stake_shares` / `total_staked_balance` and each account's `stake_shares`) diverges from what it should be, and other depositors permanently settle for less than their fair share of the reward. The attack is repeatable every epoch and against every staking pool deployed from this codebase, since it only depends on generic `internal_ping`/`stake` ordering.

### Likelihood Explanation
The attacker needs only: (1) enough NEAR to make a bare `Transfer` to the pool account and to deposit+stake in the same transaction/epoch, and (2) the ability to call `deposit`/`stake` before any other account's action crosses the epoch boundary — epochs last roughly half a day on NEAR mainnet, giving ample time. No special privilege, ownership, or race against validators is required; it is a self-serve attack any unprivileged account can execute directly against any staking pool built from this contract.

### Recommendation
Make `internal_ping` unconditionally reconcile `last_total_balance` against the current balance before any share-changing action (`stake`/`unstake`) is allowed to proceed within the same epoch, or otherwise snapshot/quarantine any balance increase detected outside of `deposit`'s attached-deposit path (e.g., segregate "unaccounted" balance and only fold it into `total_staked_balance` at the moment it is first observed, independent of whether the epoch has changed) so that newly minted shares can never retroactively claim a portion of a balance delta that existed before they were minted.

### Proof of Concept
Using the existing `staking-pool/src/lib.rs` unit-test `Emulator` harness (or `near-sdk-sim`/`RuntimeStandalone`):
1. Initialize pool, have `alice` deposit and stake `S` NEAR, `simulate_stake_call()`, note `total_stake_shares = T`, `total_staked_balance = S`.
2. Within the same epoch (no `skip_epochs`), simulate a bare transfer by increasing `emulator.amount` by `X` directly (mirroring a `Transfer` action) without calling `ping`.
3. Still same epoch, have attacker `bob` `deposit(A)` then `stake(A)`; assert `bob`'s minted shares equal `A * T / S` (i.e., unaffected by `X`).
4. `emulator.skip_epochs(1)`, then call `ping()`.
5. Assert `alice`'s recomputed `get_account_staked_balance` is strictly less than `S + X` (the value she would get if the reward had been distributed before `bob` staked), and `bob`'s `get_account_staked_balance` is strictly greater than `A` (he received part of `X` despite having contributed no legitimate reward-generating activity), proving reward `X` (accrued while only `alice`'s shares existed) was diluted onto shares minted after the fact.

```rust
    pub(crate) fn internal_stake(&mut self, amount: Balance) {
        assert!(amount > 0, "Staking amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);

        // Calculate the number of "stake" shares that the account will receive for staking the
        // given amount.
        let num_shares = self.num_shares_from_staked_amount_rounded_down(amount);
        assert!(
            num_shares > 0,
            "The calculated number of \"stake\" shares received for staking should be positive"
        );
        // The amount of tokens the account will be charged from the unstaked balance.
        // Rounded down to avoid overcharging the account to guarantee that the account can always
        // unstake at least the same amount as staked.
        let charge_amount = self.staked_amount_from_num_shares_rounded_down(num_shares);
        assert!(
            charge_amount > 0,
            "Invariant violation. Calculated staked amount must be positive, because \"stake\" share price should be at least 1"
        );

        assert!(
            account.unstaked >= charge_amount,
            "Not enough unstaked balance to stake"
        );
        account.unstaked -= charge_amount;
        account.stake_shares += num_shares;
        self.internal_save_account(&account_id, &account);

        // The staked amount that will be added to the total to guarantee the "stake" share price
        // never decreases. The difference between `stake_amount` and `charge_amount` is paid
        // from the allocated STAKE_SHARE_PRICE_GUARANTEE_FUND.
        let stake_amount = self.staked_amount_from_num_shares_rounded_up(num_shares);

        self.total_staked_balance += stake_amount;
        self.total_stake_shares += num_shares;
```

```rust
    pub(crate) fn internal_ping(&mut self) -> bool {
        let epoch_height = env::epoch_height();
        if self.last_epoch_height == epoch_height {
            return false;
        }
        self.last_epoch_height = epoch_height;

        // New total amount (both locked and unlocked balances).
        // NOTE: We need to subtract `attached_deposit` in case `ping` called from `deposit` call
        // since the attached deposit gets included in the `account_balance`, and we have not
        // accounted it yet.
        let total_balance =
            env::account_locked_balance() + env::account_balance() - env::attached_deposit();

        assert!(
            total_balance >= self.last_total_balance,
            "The new total balance should not be less than the old total balance"
        );
        let total_reward = total_balance - self.last_total_balance;
```
