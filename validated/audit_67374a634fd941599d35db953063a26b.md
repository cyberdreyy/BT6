### Title
Block-rejection metadata (`reason_code`, `response_data`, `reason`) is unsigned, allowing a relayer to recategorize a valid rejection's reason without invalidating its signature - (File: `libsigner/src/v0/messages.rs`)

### Summary
Mirrors the RubiconMarket `cancel` bug class: the report shows a check that infers a security-relevant fact from a field that isn't actually authenticated for that purpose (`msg.sender == recipient` used as a stand-in for "is this a V1 or V2 offer"), so an attacker-controlled/incidental value flips the classification and breaks downstream logic. In `stacks-signer`, `BlockRejection::hash()` signs only `signer_signature_hash`, not `reason_code`/`response_data`/`reason`, so those fields are unauthenticated even though `store_and_process_block_rejection` uses `reason_code` to decide whether to mark the current miner as having attempted an invalid reorg.

### Finding Description
`BlockRejection::hash()` builds the structured-data hash over `signer_signature_hash` only: [1](#0-0) 

`verify()`/`recover_public_key()` operate over that same restricted hash: [2](#0-1) 

Because `reason_code`, `reason`, and `response_data` are not part of the signed payload, a signature that is valid for a given `signer_signature_hash` remains valid regardless of what those other fields say. Anything that relays or re-serializes the message (a gossiping peer, a StackerDB write path, or the node's own listener code) can therefore swap in a different `reason_code`/`response_data` while keeping the original signer's signature intact, and the recipient's checks (`recover_public_key`, `verify`) will not detect the tampering: [3](#0-2) 

The consumer, `store_and_process_block_rejection`, trusts `reject_reason`/`reason_code` for two purposes: bucketing per-txid rejection weight, and—more importantly—deciding whether 30%+ of weight rejected specifically for `RejectReasonPrefix::ReorgNotAllowed`, which flips `sortition_state.cur_sortition.miner_status` to `InvalidatedBeforeFirstBlock`: [4](#0-3) 

and the coordinator-side per-txid weight logic that decides which transactions get permanently/temporarily excluded also keys off the (unauthenticated) `reason_code`/`failed_txid` pairing: [5](#0-4) 

So the same equality the report's bug class targets — "is this classification field trustworthy for the decision that depends on it?" — is broken here: the signature only vouches for `signer_signature_hash`, not for the reason the signer gave for rejecting.

### Impact Explanation
This does not on its own let an attacker forge a rejection from a key they don't hold — the signature must still verify. But because the signed payload excludes the reason fields, a single relaying party (which does not need majority weight, another signer's key, or local access) can rewrite a genuinely-signed rejection's reason_code/response_data in transit through StackerDB gossip, causing:
- Miscounted-reason-code tallying, potentially triggering (or suppressing) `InvalidatedBeforeFirstBlock` for the current miner incorrectly — a liveness/safety-relevant state flip that is not backed by what the signer actually attested to.
- Mis-attribution of `failed_txid` info (`problematic_weight`/`total_weight`), affecting which transactions get excluded from future proposals on the coordinator side.

This is a state miscount driven by an equality that should hold (signed reason == effective reason) but doesn't, matching the "rejection recounted" impact class, though the effect here is on reason classification/miner-invalidation rather than a straight accept/reject flip.

### Likelihood Explanation
Reachable by any StackerDB-adjacent relayer/observer without needing a majority, another signer's private key, or local access — the same one-slot/gossip actor model called out in the rules. However, I could not fully verify within the available tool budget whether the wire encoding used elsewhere (e.g., a wrapping SIP-018/StackerDB envelope, or a separate chunk-level signature over the whole serialized message) re-signs the entire message bytes at a layer above `BlockRejection`, which would neutralize this at the transport level. I was not able to locate and read that chunk-signing code before running out of iterations, so this should be verified against `libsigner`'s StackerDB chunk write/read path before treating this as conclusively exploitable.

### Recommendation
Include `reason_code`, `reason`, and the material fields of `response_data` in the structured-data hash signed/verified in `BlockRejection::hash()`, so any tampering with the classification invalidates the signature, analogous to fixing the RubiconMarket root cause (making the check depend on the actual authoritative field rather than an incidental proxy).

### Proof of Concept
Conceptual (not fully validated against the outer StackerDB chunk signature, see caveat above):
1. Signer S sends a valid `BlockRejection` with `reason_code = ValidationFailed(BadTransaction)` and a correctly signed `signature` over `hash() = H(signer_signature_hash)`.
2. A relaying party intercepts the StackerDB chunk before other signers/the coordinator observe it and rewrites `reason_code` to `ReorgNotAllowed` (or vice versa) and/or edits `response_data.failed_txid`.
3. `recover_public_key()`/`verify()` at the receiver still succeed because `hash()` did not cover the tampered fields.
4. `store_and_process_block_rejection` and the node-side `stackerdb_listener.rs` weight tallies (lines 501-546, 2352-2368 cited above) process the forged `reason_code`, potentially invalidating the miner or mis-attributing txid rejection weight based on data the original signer never actually asserted.

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
