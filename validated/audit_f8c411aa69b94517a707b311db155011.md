### Title
Builder payment quorum uses current `get_total_active_balance` instead of the value at bid/attestation time - ([File: specs/gloas/beacon-chain.md])

### Summary
The Gloas builder-payment mechanism decides whether a builder's escrowed bid becomes a real payment by comparing an accumulated attester "weight" against a quorum threshold that is *not* fixed when the payment obligation is created. The threshold is recomputed from the chain's current total active balance at settlement time (up to ~2 epochs later), so the same attester support that would have satisfied the quorum at commitment time can silently fail (or, symmetrically, succeed when it should not) purely because total active balance moved in the interim — the exact "current value substituted for a value that should have been fixed at commitment time" pattern described in the report.

### Finding Description
When a block's execution-payload bid records a payment obligation, the quorum needed to release it is defined as: [1](#0-0) 

`get_builder_payment_quorum_threshold` is a function of `get_total_active_balance(state)` **at the moment it is called**, not a value captured when the bid/payment was created in `process_execution_payload_bid`: [2](#0-1) 

Attester support ("weight") toward that payment accumulates over the following slots/epochs using each attester's *current* `effective_balance` at attestation-processing time: [3](#0-2) 

Finally, `process_builder_pending_payments` — run at epoch boundaries, up to two epochs after the bid was made — re-derives the quorum from whatever `get_total_active_balance(state)` is *at that later point* and compares it to the weight accumulated earlier: [4](#0-3) 

This is structurally identical to the reported OptimisticAsserter bug: a value that should represent "what the participants agreed to at commitment time" (there: `burnedBondPercentage` at assertion time; here: the quorum implied by total active balance at bid/attestation time) is instead evaluated using the *current* value of a state-wide parameter at settlement time. Just as validators/depositors joining or leaving the active set naturally move `get_total_active_balance`, the required quorum for an already-fully-supported payment can shift after the fact, without any of the attesters or the builder changing their behavior.

### Impact Explanation
If total active balance grows between the epoch the bid/attestations occurred and the epoch `process_builder_pending_payments` runs (e.g., normal validator activations/deposits), the quorum threshold rises, and a payment that had genuinely met quorum given the balance *at the time attesters voted* can be silently dropped (weight zeroed, `BuilderPendingPayment` reset, no `BuilderPendingWithdrawal` appended) — the builder never gets paid despite sufficient contemporaneous support. Conversely, if total active balance shrinks (exits), the recomputed quorum is lower than what was actually required when attesters voted, allowing a payment to clear quorum that would not have met the "real" contemporaneous bar. Either direction is a builder payment being escaped/withheld or granted based on a threshold the participants never actually satisfied against — a builder payment misdirected/escaped condition.

### Likelihood Explanation
This does not require any malicious actor, coalition, or client bug — it only requires normal chain activity (deposits, activations, exits) occurring in the ~2-epoch window between bid creation and settlement in `process_builder_pending_payments`, which is a routine, unprivileged occurrence on any live network with churn.

### Recommendation
Cache the quorum threshold (or the `total_active_balance` used to derive it) in the `BuilderPendingPayment` at the time the bid is recorded in `process_execution_payload_bid`, and use that cached value in `process_builder_pending_payments` instead of recomputing `get_builder_payment_quorum_threshold(state)` from the settlement-time state.

### Proof of Concept
1. At slot `S` (epoch `E`), a builder's bid of value `V` is recorded via `process_execution_payload_bid`, creating a `BuilderPendingPayment` with `weight = 0`.
2. Attesters for slot `S` vote and their current effective balances accumulate into `payment.weight` via `process_attestation`, reaching a total that is `>= get_builder_payment_quorum_threshold(state)` as evaluated at epoch `E`.
3. Before the payment is settled (which can happen up to `SLOTS_PER_EPOCH` slots later, in `process_builder_pending_payments`), a wave of validator activations increases `get_total_active_balance(state)` for epoch `E+1`/`E+2`.
4. `process_builder_pending_payments` recomputes `quorum = get_builder_payment_quorum_threshold(state)` using the *new*, higher total active balance, so `payment.weight < quorum` even though the same attesters fully satisfied quorum relative to the balance that existed when they actually voted.
5. The payment entry is reset to empty with no `BuilderPendingWithdrawal` appended — the builder receives nothing for a payload that had, at the time of voting, met the quorum bar.

def get_builder_payment_quorum_threshold(state: BeaconState) -> Uint64:
    """
    Calculate the quorum threshold for builder payments.
    """
    per_slot_balance = get_total_active_balance(state) // Uint64(SLOTS_PER_EPOCH)
    quorum = per_slot_balance * BUILDER_PAYMENT_THRESHOLD_NUMERATOR
    return Uint64(quorum // BUILDER_PAYMENT_THRESHOLD_DENOMINATOR)

#### New `process_builder_pending_payments`

```python
def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
