### Title
View-role users can retrieve bridge `OutgoingToken` and credential-bearing `URL` via `GET /v2/bridge_types/:BridgeName` - ([File: core/web/bridge_types_controller.go])

### Summary
`BridgeTypesController.Show` is reachable by any authenticated user regardless of role (unlike `Create`/`Update`/`Destroy`, which are wrapped in `auth.RequiresEditRole`), and it serializes the full `presenters.BridgeResource`, including the bridge's `OutgoingToken` and raw `URL`, both of which can contain credentials intended only for edit+ users.

### Finding Description
`BridgeTypesController.Show` calls `presenters.NewBridgeResource(bt)` and returns it directly via `jsonAPIResponse` with no field filtering based on caller role: [1](#0-0) 

`presenters.NewBridgeResource` populates `OutgoingToken` and `URL` unconditionally from the stored `bridges.BridgeType`: [2](#0-1) 

Critically, the `OutgoingToken` field's JSON tag lacks `omitempty` and is not conditionally cleared for lower-privileged roles, so it is always present in the serialized response: [3](#0-2) 

`OutgoingToken` is the bearer token the node uses to authenticate to the external adapter when invoking the bridge, and `URL` may embed basic-auth credentials (e.g. `https://user:pass@host/path`) — both are sensitive operational secrets. `IncomingToken` itself is comparatively safe here: it is only populated by the `Create` handler from the just-generated `bta.IncomingToken` value returned by `bridges.NewBridgeType`, and is never repopulated by `NewBridgeResource` from the persisted `bridges.BridgeType` in `Show`/`Update`/`Destroy`/`Index`, since the ORM entity does not retain the plaintext incoming token. So the concrete exploitable exposure is `OutgoingToken` (and any credentials embedded in `URL`), not `IncomingToken`.

Because `Show` (and `Index`) are not wrapped in `auth.RequiresEditRole` while `Create`/`Update`/`Destroy` are, a session/API-token authenticated as `UserRoleView` can call `GET /v2/bridge_types/:BridgeName` and receive the bridge's `OutgoingToken`/URL credentials that are otherwise gated for edit+ roles on mutating endpoints — violating SECRET_CONFINEMENT and AUTHORIZATION_EXACTNESS.

### Impact Explanation
A view-role authenticated user (the lowest privilege tier that can still log in to the node's UI/API) can read another operator's bridge outgoing-authentication token and any credentials embedded in the bridge URL, without needing edit or admin rights. This maps to Chainlink's "secret/credential disclosure" bounty class: exposure of adapter authentication material allows the attacker to impersonate the node when calling the external adapter, or to reuse leaked URL credentials against the adapter service directly.

### Likelihood Explanation
Minimal precondition: possession of any valid `view`-role session or API token — the lowest privilege level supported by the node. The endpoint is a plain, unauthenticated-by-role GET request (`GET /v2/bridge_types/:BridgeName`), fully repeatable, requiring no special conditions beyond knowing/guessing a bridge name (bridge names are also enumerable via the unguarded `Index`/paginated list endpoint).

### Recommendation
Either (a) wrap `BridgeTypesController.Show` (and `Index`) in `auth.RequiresEditRole` so only edit+ users can see bridge secrets, or (b) keep `Show`/`Index` view-accessible but strip/redact `OutgoingToken` and any credential portion of `URL` from `presenters.BridgeResource` for callers below edit role (e.g., add `omitempty` and conditionally populate `OutgoingToken` only when the caller's role satisfies edit+, mirroring how `IncomingToken` is already excluded from persisted round-trips).

### Proof of Concept
1. Unit test in `core/web/presenters/bridges_test.go`: construct a `bridges.BridgeType` with a non-empty `OutgoingToken` and `URL` containing embedded credentials, call `presenters.NewBridgeResource`, marshal to JSON, and assert `outgoingToken`/credential-bearing URL fields are present — demonstrating no redaction occurs regardless of caller context.
2. Handler-level integration test in `core/web/bridge_types_controller_test.go`: create a bridge as an edit/admin user (capturing its `OutgoingToken`), then authenticate a second client session with `UserRoleView`, issue `GET /v2/bridge_types/:BridgeName`, expect `http.StatusOK` (not 401/403), and assert the JSON response body's `data.attributes.outgoingToken` equals the original token — proving disclosure to a view-only role.
