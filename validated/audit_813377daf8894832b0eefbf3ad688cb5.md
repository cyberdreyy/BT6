### Title
GetSources retry loop ignores context cancellation, letting attacker-controlled `MaxAttempts`/backoff prolong runner activity after job cancel - ([File: functions/concrete/run/stages/get_sources.go])

### Summary
The `GetSources.Run` retry loop (`functions/concrete/run/stages/get_sources.go:150-167`) has no check on `ctx.Done()` between attempts, and `retry.SleepWithNotice` (`functions/concrete/run/stages/internal/retry/retry.go:21-24`) calls plain `time.Sleep(d)` instead of a context-aware sleep. Because `GIT_STRATEGY`/`GIT_STRATEGY_ATTEMPTS`-style parameters (surfaced here as `GetSources.MaxAttempts` and `UseExponentialBackoffStageRetry`) are populated from job/pipeline-controlled CI variables (e.g. `GET_SOURCES_ATTEMPTS`), a pipeline author can pick a large `MaxAttempts` and force the runner to keep retrying/backing off for a long time even after the job has been canceled from GitLab.

### Finding Description
`GetSources.Run` runs:
```go
for attempt := 1; attempt <= s.MaxAttempts; attempt++ {
    if attempt > 1 {
        if s.UseExponentialBackoffStageRetry {
            retry.SleepWithNotice(e, backoff.Duration())
        }
        ...
    }
    err = s.getSourcesOnce(ctx, e, gitEnv)
    if err == nil { break }
}
``` [1](#0-0) 

- `s.getSourcesOnce` ultimately shells out via `git(ctx, ...)` → `e.Command(ctx, ...)`, so an `exec.CommandContext`-backed process is killed promptly on context cancellation, making each attempt fail fast (`err != nil`) once the job is canceled.
- The loop's only exit condition on error is `attempt <= s.MaxAttempts`; there is no `select { case <-ctx.Done(): return ctx.Err() }` anywhere in the loop body.
- `retry.SleepWithNotice` sleeps unconditionally via `time.Sleep(d)`, with no `ctx.Done()` select, so once inside a backoff sleep the goroutine cannot be interrupted by cancellation at all. [2](#0-1) 

Consequence: after cancellation, each remaining attempt still (a) fails almost instantly (git process killed), (b) still runs `retry.SleepWithNotice(backoff.Duration())` for up to 5 minutes (backoff `Min: 5s, Max: 5m, Factor: 1.5, Jitter: true`), and (c) still counts toward `MaxAttempts`. The loop therefore burns roughly `MaxAttempts × (up to 5 min)` of wall-clock time regardless of cancellation, instead of returning as soon as `ctx` is done.

`MaxAttempts` and `UseExponentialBackoffStageRetry` are fields of the job-supplied `GetSources` config struct (JSON-tagged, populated from job variables such as `GET_SOURCES_ATTEMPTS`), i.e. attacker/job-author controlled input, not an admin-only setting. [3](#0-2) 

### Impact Explanation
This is a resource-consumption / delayed-cancellation issue, not a sandbox escape or secret leak: a canceled job keeps a runner concurrency slot occupied and keeps sleeping/retrying long after GitLab has told it to stop, for a duration approximately linear in `MaxAttempts` (bounded per-attempt at 5 minutes). A pipeline author who can set `GET_SOURCES_ATTEMPTS`/`GIT_STRATEGY=fetch` to a very large value and trigger transient fetch failures (or simply cancel their own job) can force the runner to stay busy far longer than the job's actual lifetime, delaying availability of that runner for subsequent jobs (self-inflicted or shared-runner-affecting DoS depending on scheduling).

### Likelihood Explanation
High feasibility for the narrow scope described: no special privileges are needed beyond normal pipeline authoring (setting a CI/CD variable and canceling a job), and the missing `ctx.Done()` check is a straightforward, always-reachable code path whenever `GIT_STRATEGY` is `fetch`/`clone` and a fetch attempt fails after cancellation. It's fully repeatable and deterministic.

### Recommendation
- Add a `select { case <-ctx.Done(): return ctx.Err() default: }` check at the top of each loop iteration in `GetSources.Run`, immediately after computing `err`, and before calling `retry.SleepWithNotice`.
- Replace `time.Sleep(d)` in `retry.SleepWithNotice` with a context-aware sleep, e.g. using a `time.Timer` combined with `select { case <-ctx.Done(): ...; case <-timer.C: }`, and thread `ctx` into `SleepWithNotice`.
- Optionally clamp/validate `MaxAttempts` server-side/runner-side to a sane upper bound independent of job input.

### Proof of Concept
Go unit test outline (`functions/concrete/run/stages/get_sources_test.go`):
```go
func TestGetSourcesRun_CancelDuringBackoffDoesNotShortenRetry(t *testing.T) {
    s := GetSources{
        GitStrategy: gitStrategyFetch,
        MaxAttempts: 5,
        UseExponentialBackoffStageRetry: true,
        RepoURL: "https://example.invalid/repo.git", // always fails
    }
    ctx, cancel := context.WithCancel(context.Background())
    start := time.Now()
    go func() {
        time.Sleep(50 * time.Millisecond) // cancel almost immediately
        cancel()
    }()
    err := s.Run(ctx, testEnv(t))
    elapsed := time.Since(start)

    require.Error(t, err)
    // Expected (if fixed): elapsed should be close to first-failure time, e.g. < 1s.
    // Actual (bug): elapsed scales with MaxAttempts * backoff (multiple 5s-5min sleeps),
    // proving cancellation was not honored.
    assert.Less(t, elapsed, 2*time.Second, "retry loop did not respect context cancellation")
}
```
Fuzz/parameterized variant: sweep `MaxAttempts` in {1, 10, 100, 1000} with a mocked fast-failing `getSourcesOnce`, cancel `ctx` at t=0, and assert `elapsed` stays roughly constant (bounded by fix) rather than growing linearly with `MaxAttempts` (bug).

// NewBackoff returns a 5s→5min jittered exponential-backoff schedule (factor 1.5).
func NewBackoff() *backoff.Backoff {
	return &backoff.Backoff{
		Min:    5 * time.Second,
		Max:    5 * time.Minute,
		Jitter: true,
		Factor: 1.5,
	}
}

func SleepWithNotice(e *env.Env, d time.Duration) {
	e.Noticef("Retrying in %v", d)
	time.Sleep(d)
}
