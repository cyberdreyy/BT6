### Title
Unauthenticated `opp2p_*` namespace exposes peer topology and allows peer/network manipulation without the `--rpc.enable-admin` gate - (File: crates/consensus/service/src/actors/rpc/actor.rs)

### Summary
The Base consensus node's public JSON-RPC/WS server merges the `opp2p_*` (`BaseP2PApi`) namespace whenever a P2P network sender exists, independent of the privileged `admin` namespace gate. Any anonymous RPC client reaching the node's HTTP or WebSocket endpoint can call these methods without the `--rpc.enable-admin` flag, both reading sensitive network/topology data and mutating P2P connectivity state.

### Finding Description
`RpcActor::start` merges `P2pRpc::new(p2p_network).into_rpc()` whenever `p2p_network` is `Some`, with no admin check, whereas the truly privileged `AdminRpc` module is merged only `if self.config.admin_enabled()`: [1](#0-0) 

`p2p_network` is always populated with `Some(network_rpc)` at node construction time, unconditionally, regardless of whether the admin API is enabled: [2](#0-1) 

The `BaseP2PApi` (`opp2p` namespace) trait itself documents that these are administrative methods that should be access-controlled: "Administrative RPC methods should be exposed only to authorized clients, as they can affect network connectivity and peer relationships. Consider implementing appropriate authentication and access controls in production deployments": [3](#0-2) 

Yet in practice the trait is exposed unconditionally via `opp2p_self`, `opp2p_peers`, `opp2p_peerStats`, `opp2p_discoveryTable` (read methods disclosing full peer topology, connection details, and discovery-table contents), as well as mutating methods `opp2p_blockPeer`, `opp2p_unblockPeer`, `opp2p_blockAddr`, `opp2p_blockSubnet`, `opp2p_connectPeer`, `opp2p_disconnectPeer`, `opp2p_protectPeer`/`opp2p_unprotectPeer`: [4](#0-3) 

The concrete implementation forwards these calls straight to the network actor with no additional authorization layer: [5](#0-4) 

This is the same bug class as CVE-2017-2600: monitoring/administrative data and controls intended to require elevated privilege end up reachable by any low-privilege/anonymous remote API caller because the privilege gate was applied to a different module than the one actually exposing the sensitive/administrative surface.

### Impact Explanation
Any unauthenticated remote RPC client can:
- Enumerate the node's full peer set, connection state, and discovery table (`opp2p_peers`, `opp2p_discoveryTable`, `opp2p_peerStats`, `opp2p_self`) — information disclosure of node topology useful for targeted eclipse/DoS attacks against that specific node.
- Actively disconnect or block legitimate peers (`opp2p_blockPeer`, `opp2p_disconnectPeer`, `opp2p_blockAddr`, `opp2p_blockSubnet`) or force connections to attacker-controlled peers (`opp2p_connectPeer`), degrading or manipulating the node's P2P connectivity — a resource/availability-affecting action on the consensus P2P layer for a rollup node, potentially isolating it from the network (partial node halt / eclipse condition) which impacts unsafe-block propagation to that node.

### Likelihood Explanation
Any operator who runs the node with a P2P network configured (the default) exposes this namespace on the public RPC port regardless of whether they intended to enable admin-level control, since the module is not tied to `--rpc.enable-admin`. Reaching it requires only sending standard JSON-RPC requests to the node's public HTTP/WS endpoint — no authentication, signature, or special access is needed.

### Recommendation
Gate the `P2pRpc` module merge behind the same `config.admin_enabled()` check used for `AdminRpc` (or introduce a separate, explicit flag for the P2P-admin surface), so that peer-topology disclosure and P2P mutation methods are not exposed on the default/public RPC listener. At minimum, split `opp2p_*` into read-only (`opp2p_self`, `opp2p_peerCount`, `opp2p_peerStats`) methods that may remain public and mutating/administrative methods (`block*`, `unblock*`, `connectPeer`, `disconnectPeer`, `protect*`) that must require the admin gate, consistent with the module's own documented security model.

### Proof of Concept
1. Start a Base consensus node without `--rpc.enable-admin` (default configuration, matching the devnet compose files where `--rpc.enable-admin` is only passed to specific validator/`base-rpc` services, e.g. `etc/docker/docker-compose.yml:635` for one node type but not others).
2. As an anonymous client, send `curl -X POST -d '{"jsonrpc":"2.0","method":"opp2p_peers","params":[false],"id":1}' http://<node>:<rpc_port>` — the response returns the full `PeerDump` with connection details.
3. Send `curl -X POST -d '{"jsonrpc":"2.0","method":"opp2p_blockPeer","params":["<peer_id>"],"id":1}' http://<node>:<rpc_port>` — the node blocks/drops the specified peer, demonstrating unauthorized manipulation of P2P connectivity without any admin credential.

impl BaseP2PApiServer for P2pRpc {
    async fn opp2p_self(&self) -> RpcResult<PeerInfo> {
        Metrics::rpc_calls("opp2p_self").increment(1.0);
        let (tx, rx) = tokio::sync::oneshot::channel();

            .await
            .map_err(|_| ErrorObject::from(ErrorCode::InternalError))?;
