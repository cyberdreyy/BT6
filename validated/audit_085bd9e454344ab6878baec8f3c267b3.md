### Title
First-depositor share inflation via direct token donation lets an attacker steal subsequent lenders' deposits - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault` prices tranche shares as `NAV / trancheSupply` (`_virtualPriceAux`, `contracts/IdleCDOCreditVault.sol:336`), and NAV is computed by `getContractValue()` which includes the raw ERC20 balance of the vault (`_contractTokenBalance(token)`). A KYC-passing attacker can be the first BB/AA depositor with 1 wei of underlying, then donate a large amount of `token` directly to the vault, inflating the tranche price. Any subsequent victim depositing less than the inflated per-share price mints 0 tranche tokens (`_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice` rounds to 0 at `contracts/IdleCDOCreditVault.sol:346`), while the vault still pulls their tokens via `_transferUnderlyingsFrom` (`contracts/IdleCDOCreditVault.sol:204`). The attacker then redeems their dust share for essentially the entire NAV. This is the credit-vault analog of CVE-2021-23223's "improper initialization": the share/NAV state is improperly initialized on first deposit with no minimum-liquidity or dead-share seeding.

### Finding Description
The sequence in the buffer/pre-epoch phase:

1. Attacker (KYC'd, unprivileged) calls `depositBB(1)` on a fresh vault. `_updateAccounting` sees `lastNAV == 0`, so `_virtualPriceAux` returns `oneToken` and the attacker is minted ~1 wei of tranche tokens.
2. Attacker `transfer`s `D` underlying directly to the `IdleCDOCreditVault` contract. There is no donation isolation/skim: `getContractValue()` counts `_contractTokenBalance(token)`, so NAV jumps from 1 to `1 + D` while tranche supply stays ~1 wei.
3. On the next accounting touch (`_updateAccounting` inside the victim's `_deposit`), `priceBB` is updated to roughly `(1 + D) * 1e18 / 1`.
4. Victim calls `depositBB(A)` with `A < 1 + D` (e.g. `D = 100k USDC`, `A = 50k USDC`). Their tokens are pulled, `_minted = A * 1e18 / priceBB = 0`, and `_mintShares` mints 0 while still crediting `lastNAVBB += A`.
5. Attacker calls `withdrawBB`/`requestWithdraw` for their 1 wei share and is paid out at the inflated price, recovering `D + A` minus dust.

The broken invariant is fair mint/burn: shares are minted at a price manipulable by permissionless donations, so a depositor can pay assets and receive zero shares. Existing guards do not stop this: `_guarded` only enforces a maximum TVL limit (no minimum first deposit), `_updateAccounting` runs before the donation-aware mint and actually *absorbs* the donation into price, `whenNotPaused`/KYC only restrict who can call (the attacker is a legitimate lender), and `mint(0)` does not revert.

### Impact Explanation
Direct theft of deposits: every victim deposit smaller than the donation-inflated share price becomes the attacker's withdrawable NAV. With `D ≈ 100,000 USDC` the attacker captures all deposits below ~100k USDC; by front-running larger deposits the donation can be sized accordingly, bounded only by the attacker's capital. Loss is equal to the sum of victim deposits made while the inflated price stands.

### Likelihood Explanation
Requires being the first depositor in a tranche (fresh vault or a tranche class with zero supply, which the code explicitly handles by resetting price to `oneToken`), plus capital for the donation. Both are achievable by an unprivileged KYC'd lender, and the attack is repeatable across epochs/vaults whenever a tranche's supply returns to zero.

### Recommendation
Enforce a minimum initial deposit and/or permanently lock (burn or mint to the vault) a minimum amount of tranche tokens on the first mint, per the standard dead-shares mitigation. Additionally, exclude unsolicited direct transfers from `getContractValue()` (track an internal "expected" token balance updated only in `_deposit`/`_withdraw` paths) or add a skim/sweep so donations cannot move the share price. Revert when `_minted == 0` for a nonzero `_amount`.

### Proof of Concept
Foundry fork PoC outline (against a deployed `IdleCDOCreditVault` and its underlying):

```solidity
function testFirstDepositorInflation() external {
    // vault freshly deployed; BB tranche supply == 0
    uint256 D = 100_000e6;          // donation (USDC example)
    uint256 victimAmt = 50_000e6;

    // 1. attacker seeds vault
    deal(address(usdc), attacker, D + 1);
    vm.startPrank(attacker);
    usdc.approve(address(vault), type(uint256).max);
    vault.depositBB(1);              // mint ~1 wei tranche @ price 1e18
    usdc.transfer(address(vault), D);// donation: NAV = D + 1, supply = ~1 wei
    vm.stopPrank();

    // 2. victim deposits -> mints 0 shares
    deal(address(usdc), victim, victimAmt);
    vm.startPrank(victim);
    usdc.approve(address(vault), victimAmt);
    vault.depositBB(victimAmt);      // pulls tokens, mints 0 tranche tokens
    vm.stopPrank();
    assertEq(IERC20(vault.BBTranche()).balanceOf(victim), 0);

    // 3. attacker withdraws, recovering donation + victim deposit
    vm.prank(attacker);
    vault.requestWithdrawBB(1);      // or withdrawBB depending on epoch phase
    // ... epoch machinery ...
    // attacker balance ~= D + victimAmt
}
```
