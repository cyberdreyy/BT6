### Title
Base L1 `SystemConfig` owner can set the operator fee scalar/constant arbitrarily high to unexpectedly extract value from already-signed L2 transactions - (File: `crates/common/genesis/src/updates/operator_fee.rs`)

### Summary
The reported TellerV2 bug is that a privileged owner can change a fee parameter (`protocolFee`) at will, and that change applies retroactively to transactions a counterparty already committed to, letting the owner extract value the counterparty never agreed to. Base's L2 execution layer has an analogous unbounded, owner-controlled fee parameter: the Isthmus **operator fee** (`operator_fee_scalar` / `operator_fee_constant`), which is set by the L1 `SystemConfig` contract owner and applied to L2 transactions with no bounds check, no user opt-in, and no relation to the fee caps the transaction sender actually signed.

### Finding Description
`OperatorFeeUpdate` decodes an L1 `ConfigUpdate(OperatorFee)` log into a `scalar: u32` and `constant: u64` and applies it directly to `SystemConfig` with no range/sanity validation: [1](#0-0) 

This update is triggered purely by the L1 `SystemConfig` contract owner (`systemConfigOwner`, an off-chain governance-controlled EOA/multisig role) emitting a `ConfigUpdate` log; the derivation pipeline reads it from L1 receipts and updates the on-chain `SystemConfig` used to build subsequent L1 attributes deposits: [2](#0-1) 

Once the update propagates through an epoch change, every future L2 block's L1-info deposit carries the new `operator_fee_scalar`/`operator_fee_constant`, as demonstrated by the harness test: [3](#0-2) 

These scalars are then used by `L1FeeParams::operator_fee_charge` (in `crates/common/l1-fees/src/params.rs`) to compute an operator fee that is charged **on top of** the EIP-1559 `max_fee_per_gas`/`max_priority_fee_per_gas` the sender explicitly signed. The `BaseTxHandlerHooks` handler charges this fee upfront from the caller's balance and credits it to `Predeploys::OPERATOR_FEE_VAULT`: [4](#0-3) [5](#0-4) 

Crucially, a transaction sender's EIP-1559 fee cap only bounds the base-fee + priority-fee portion of the payment; it says nothing about, and cannot cap, the operator fee, which is an independent multiplier/constant chosen unilaterally by the `SystemConfig` owner (analogous to TellerV2's `protocolFee()` being independent of what the borrower committed to in `submitBid`). A sender who signs and broadcasts a transaction has no way to know or bound what operator fee will be in effect by the time it is included, because the scalar can be changed on L1 at any point before inclusion — exactly the "fee changed between submission and acceptance" scenario in the original report.

### Impact Explanation
If the `SystemConfig` owner sets `operator_fee_scalar`/`operator_fee_constant` to a very high value, every subsequently included L2 transaction is charged a much larger, unbudgeted amount that is debited directly from the sender's account balance and routed to `OPERATOR_FEE_VAULT` — a direct, unauthorized value extraction from L2 users that they did not consent to via their signed fee caps. Because `operator_fee_scalar` is a `u32` and `operator_fee_constant` a `u64` with no upper bound enforced in `OperatorFeeUpdate::apply`, the owner can push the multiplier/constant to the maximum representable value, and (per the Jovian schedule) the effective fee can be amplified further by `OPERATOR_FEE_JOVIAN_MULTIPLIER`. This can drain sender balances up to their full balance (since the charge happens via `charge_upfront`/`ensure_can_pay_fees`, which only checks the sender can afford it — not that the sender agreed to it) and represents theft of funds from L2 users who had no way to bound this side-channel fee at signing time.

### Likelihood Explanation
This requires control of the `SystemConfig` owner role on L1 (a privileged governance/multisig key), which mirrors the "requires an evil owner" caveat in the original report — the severity there was also rated Medium for the same reason. Given that the operator fee parameter has no protocol-level bound, no time-lock, and no user commitment mechanism, exploitation requires no additional preconditions beyond that single privileged L1 action, making this straightforward to trigger once that role is compromised or acts maliciously.

### Recommendation
Enforce a protocol-level ceiling on `operator_fee_scalar`/`operator_fee_constant` (e.g., a maximum multiplier analogous to the borrower/fee-cap coupling recommended in the original report), and/or require transactions to explicitly commit to (or cap) the operator fee they are willing to pay, similar to how `max_fee_per_gas` bounds the base+priority fee. At minimum, add validation in `OperatorFeeUpdate::apply`/`TryFrom<&SystemConfigLog>` (in `crates/common/genesis/src/updates/operator_fee.rs`) to reject scalar/constant values above a sane, chain-governance-approved maximum, and consider a delay/time-lock before an operator-fee change takes effect so senders can react to changed fee terms before their pending transactions are included.

### Proof of Concept
1. As the L1 `SystemConfig` owner, emit a `ConfigUpdate(OperatorFee)` log with `operator_fee_scalar = u32::MAX` and `operator_fee_constant = u64::MAX` (as constructed by `enqueue_operator_fee_update` in `actions/harness/src/l1/miner.rs:376-400`).
2. Wait for an L1 epoch change; the derivation pipeline's `StatefulAttributesBuilder` picks up the new `SystemConfig` values and encodes them into the L1-info deposit transaction for the next L2 block (as verified by `operator_fee_config_update_propagates_to_l1_info` in `actions/harness/tests/upgrade/operator_fees.rs:579-687`).
3. Any user's already-signed L2 EIP-1559 transaction is now included under the new config: `BaseTxHandlerHooks::before_execution` computes `operator_fee = Self::operator_fee(host, envelope, envelope.gas_limit())` using the inflated scalar/constant and charges it from the sender via `charge_upfront`, crediting `Predeploys::OPERATOR_FEE_VAULT` at settlement — with no relationship to, or cap from, the sender's signed `max_fee_per_gas`/`max_priority_fee_per_gas` (`crates/common/evm2/src/handler.rs:108-163`).
4. The sender pays an operator fee they never agreed to and had no way to bound, extracting value analogous to the TellerV2 `protocolFee()` exploit.

```rust
impl TxHandlerHooks<BaseEvmTypes> for BaseTxHandlerHooks {
    fn before_execution(
        host: &mut Evm<'_, BaseEvmTypes>,
        envelope: &BaseTxEnvelope,
        caller: Address,
        upfront_fee: U256,
    ) -> HandlerResult<()> {
        // Charge the upfront gas cost, the L1 data fee, and the operator fee (on the gas limit)
        // from the caller. Both fees are stashed for settlement so it charges/refunds against the
        // exact amounts collected here, without recomputing them.
        let l1_fee = Self::l1_fee(host, envelope);
        let operator_fee = Self::operator_fee(host, envelope, envelope.gas_limit());
        let ext = host.ext_mut();
        ext.l1_fee = l1_fee;
        ext.operator_fee = operator_fee;
        // `validate_sender` only checks the gas cost and value; the L1 and operator fees are
        // charged on top here via `charge_upfront`'s wrapping subtraction, so reject an
        // underfunded caller up front rather than let its balance wrap to a spurious value.
        Self::ensure_can_pay_fees(host, envelope, caller, l1_fee, operator_fee)?;
        charge_upfront(
            host,
            caller,
            upfront_fee.saturating_add(l1_fee).saturating_add(operator_fee),
        )
    }
```

```rust
    fn settle_transaction(
        host: &mut Evm<'_, BaseEvmTypes>,
        envelope: &BaseTxEnvelope,
        gas: GasSettlement<BaseEvmTypes>,
    ) -> HandlerResult<TxResult<BaseEvmTypes>> {
        let caller = gas.caller;
        let basefee = host.block_env().basefee;
        let l1_fee = host.ext().l1_fee;
        // The operator fee charged upfront (on the gas limit), stashed in before_execution.
        let operator_fee_charged = host.ext().operator_fee;

        // Default settlement refunds the caller's unused gas and pays the coinbase the priority
        // fee. The base fee is credited to its vault below (the OP-stack does not burn it).
        let mut result = default_settle_gas(host, gas)?;
        let gas_used = result.tx_gas_used();

        // Refund the operator fee down from the amount charged (on the gas limit) to the gas
        // actually used; the net is credited to the operator-fee vault below.
        let operator_fee_used = Self::operator_fee(host, envelope, gas_used);
        let operator_fee_refund = operator_fee_charged.saturating_sub(operator_fee_used);
        Self::credit(host, caller, operator_fee_refund)?;

        // Distribute the collected OP-stack fees to their vaults.
        Self::credit(host, Predeploys::L1_FEE_VAULT, l1_fee)?;
        Self::credit(
            host,
            Predeploys::BASE_FEE_VAULT,
            basefee.saturating_mul(U256::from(gas_used)),
        )?;
        Self::credit(host, Predeploys::OPERATOR_FEE_VAULT, operator_fee_used)?;
```
