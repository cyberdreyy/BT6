### Title
Stale rejection weight not cleared when a signer switches its vote to Accepted, causing a spurious `SignersRejected` outcome - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side vote tally in `StackerDBListener::run_loop` maintains two independent running totals per block, `total_weight_approved` and `total_weight_rejected`, inside `BlockStatus` [1](#0-0) . When a signer's vote transitions from `Rejected` to `Accepted` for the same block, the code correctly adds the signer's weight to `total_weight_approved`, but never removes the previously-added weight from `total_weight_rejected`. This is directly analogous to the Lybra `_repay` bug: a running accounting total (`poolTotalPeUSDCirculation` / here `total_weight_rejected`) is not corrected for a state change that has already happened (fee already transferred out / here the signer already switched its vote), leaving a stale, overstated value that downstream logic relies on for a threshold decision.

### Finding Description
In the `Accepted` handling branch, the weight is only added to `total_weight_approved` guarded by `gathered_signatures.contains_key(&slot_id)`, not by whether the signer previously rejected: [2](#0-1) 

In the `Rejected` handling branch, weight is added to `total_weight_rejected` guarded only by `responded_signers.insert(slot_id)` returning `true` (i.e., first-ever response of any kind): [3](#0-2) 

Sequence that produces the bug:
1. Signer S (slot_id = k, weight = w) sends `Rejected` for block B. `responded_signers.insert(k)` → `true`, so `total_weight_rejected += w`.
2. Signer S later sends `Accepted` for block B (legitimate and explicitly supported behavior — the signer-side `SignerDb::add_block_signature` even deletes the corresponding rejection row when this happens, see `stacks-signer/src/signerdb.rs`) [4](#0-3) . On the miner/coordinator side, `gathered_signatures.contains_key(&k)` is still `false` (S never accepted before), so `total_weight_approved += w` is applied correctly — but nothing decrements `total_weight_rejected` by `w`. The weight `w` now double-counts: it sits in both `total_weight_approved` and the stale `total_weight_rejected`.

This breaks the equality the coordinator relies on: each signer's weight is meant to count toward at most one side of the approve/reject tally at any time, but after a vote flip it is counted on both sides simultaneously, with the reject side never being corrected.

### Impact Explanation
`SignerCoordinator::gather_signatures` (the consumer of `BlockStatus`) uses these two totals to decide the fate of the block: [5](#0-4) 
and to reset only the rejection side on timeout, explicitly noting that approvals must never be cleared because "an old approval could always be used to make a block reach the approval threshold" — the code has no symmetric protection for stale rejections [6](#0-5) .

Because the stale rejection weight persists indefinitely (until a timeout-triggered `reset_rejections` call, which is not guaranteed to happen before the threshold check runs), later legitimate rejections from *other* signers can combine with this phantom, already-withdrawn rejection weight to cross the blocking-minority threshold (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`), causing the coordinator to return `NakamotoNodeError::SignersRejected` and abandon a block that, based on the signers' actual current opinions, should still be eligible for acceptance. This is a liveness-affecting mis-accounting: the miner acts on a stale/inflated rejection tally rather than the true, current signer-weight state, exactly mirroring the report's "understatement/overstatement of a running total due to incorrect accounting after a state-changing action" bug class.

### Likelihood Explanation
This requires only a single signer (any weight) to legitimately change its mind from reject to accept on a block — a scenario explicitly exercised and expected by the codebase itself (see the `reject_then_accept` test in `stacks-signer/src/signerdb.rs`) [7](#0-6) . No majority collusion, no malicious key material, and no timing manipulation beyond ordinary message delivery via StackerDB gossip is needed; it is triggerable by one signer's normal vote revision.

### Recommendation
When processing an `Accepted` message for a `slot_id` that is already present in `responded_signers` due to a prior `Rejected` message (or vice versa), subtract the signer's weight from the previous bucket before/while adding it to the new one, keeping `total_weight_approved` and `total_weight_rejected` mutually exclusive per signer, e.g.:
```rust
if block.responded_signers.contains(&slot_id) && !block.gathered_signatures.contains_key(&slot_id) {
    // this signer previously rejected; undo that weight before counting the acceptance
    block.total_weight_rejected = block.total_weight_rejected.saturating_sub(signer_entry.weight);
}
```
and apply the symmetric correction in the `Rejected` branch for a signer switching away from a prior acceptance.

### Proof of Concept
1. Configure a reward set with `total_weight = 100`, `weight_threshold = 70` (blocking minority = 30).
2. Signer S (weight = 25) sends `BlockResponse::Rejected` for block B → `total_weight_rejected = 25` (no trigger yet, since `25 + 70 = 95 ≤ 100`).
3. Signer S reconsiders and sends `BlockResponse::Accepted` for block B → `total_weight_approved = 25` (via the `!gathered_signatures.contains_key` branch), while `total_weight_rejected` remains `25`, uncorrected, per lines 443-465 and 515-519 of `stackerdb_listener.rs`.
4. A different signer T (weight = 10) later sends `BlockResponse::Rejected` for block B → `total_weight_rejected = 35`.
5. `SignerCoordinator::gather_signatures` evaluates `35 + 70 = 105 > 100` and returns `Err(NakamotoNodeError::SignersRejected { .. })`, aborting block B — even though the only currently rejecting signer weight is `10` (from T), well under the `30` blocking-minority threshold, because S's withdrawn rejection (`25`) was never removed from the tally.
