### Title
`NakamotoBlockProposal::validate` derives its "canonical" sortition handle from an attacker-controlled burn view, letting a reorged-out tenure pass `check_block_has_valid_tenure` - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
`validate()` computes `sort_tip` by looking up the snapshot for `burn_view_consensus_hash` via `SortitionDB::get_block_snapshot_consensus`, and then builds `db_handle = sortdb.index_handle(&sort_tip.sortition_id)` from that specific snapshot rather than from the sortition DB's actual canonical tip. `check_block_has_valid_tenure` is then evaluated against that fixed handle, so the "canonical" check is only canonical relative to whatever fork `sort_tip` happens to sit on, not the DB's true canonical fork.

### Finding Description
The equality that must hold is: the tenure approved by `check_block_has_valid_tenure` must be an ancestor of the sortition DB's *current canonical* burn chain tip. Instead, the code establishes the reference point as follows: [1](#0-0) 

`burn_view_consensus_hash` comes from `NakamotoChainState::get_block_burn_view(sortdb, &self.block, &parent_stacks_header)`, and for a `TenureChange` with cause `Extend`, this value is sourced from data inside the attacker's own proposed block (the `TenureChange` payload), which is fully attacker-controlled. `SortitionDB::get_block_snapshot_consensus` then resolves that consensus hash to whatever snapshot the DB has recorded for it — the sortitions table retains historical/orphaned burn-view snapshots as well as canonical ones, and this lookup is keyed by consensus hash, not filtered to the currently-canonical fork.

The resulting `sort_tip.sortition_id` is then used to build the `SortitionHandleConn` (`db_handle`) that both `check_block_has_valid_tenure` and downstream checks operate against: [2](#0-1) 

`has_consensus_hash` walks the ancestor chain rooted at the handle's own tip (`sort_tip.sortition_id`), so it only proves that `tenure_id` is an ancestor of that (potentially stale/orphaned) snapshot — not that it is an ancestor of the sortition DB's real canonical tip. If a miner won a slot on a tenure that was later reorged out of the canonical Bitcoin fork, that tenure's consensus hash and its associated burn-view snapshot remain in the sortdb's `snapshots` table. By crafting a `TenureChange` (cause `Extend`) whose declared burn view resolves to that stale, now-orphaned snapshot, and setting `block.header.consensus_hash` to the orphaned tenure's hash, the attacker causes `sort_tip` to be pinned to the orphaned fork, and `check_block_has_valid_tenure` will pass even though that tenure is no longer part of the canonical chain.

### Impact Explanation
This breaks the CANONICITY safety property described: a signer receiving `BlockValidateOk` (via the node's `/v3/block_proposal` validation, exercised through `NakamotoBlockProposal::validate`) would be told a non-canonical, reorged-out tenure is valid, and could sign it — a Critical chain-safety violation (signing a non-canonical/conflicting block). Because the check is purely local logic evaluated per-request, a single attacker with one winning miner slot on the abandoned fork can repeat this whenever they can construct a proposal whose declared burn view still resolves to a lingering orphaned snapshot in the node's sortition DB.

### Likelihood Explanation
Exploitation requires: (1) the attacker previously won a tenure that was later reorged out (feasible for any miner via normal Bitcoin fork competition — no privilege beyond "win a single miner slot" needed), (2) the orphaned snapshot for that tenure/burn-view must still be present in the target node's `sortdb` (true by design, since sortition history is retained), and (3) the attacker crafts a `TenureChange`-Extend block whose burn-view fields point at that stale snapshot and gossips it as a `BlockProposal`. All of this is achievable with only the attacker's own miner key and gossip capability — no majority-signer collusion, no auth token, no local access. This is repeatable for every orphaned tenure still resident in the sortdb history.

### Recommendation
`validate()` must not treat `sort_tip` (derived from an attacker/tenure-supplied `burn_view_consensus_hash`) as authoritative for canonicity checks. Before running `check_block_has_valid_tenure`, the code should verify that `sort_tip.sortition_id` (or `burn_view_consensus_hash`) is itself an ancestor of / equal to the sortdb's actual current canonical tip (e.g., via `SortitionDB::get_canonical_burn_chain_tip` and an ancestor-of check), rejecting the proposal with `NonCanonicalTenure`/`NoSuchTenure` if the referenced burn view is not on the canonical fork.

### Proof of Concept
Rust test plan (stackslib, using the `TestPeer` sortition harness):
1. Boot two `TestPeer` sortition tips A and B from a common ancestor, mining tenure `T` on fork A.
2. Advance fork B past fork A's height so the node's sortdb canonical tip switches to B, orphaning tenure `T` (its snapshot remains queryable via `get_block_snapshot_consensus`, confirmable by directly calling it against `T`'s consensus hash and observing `Some(..)`).
3. Craft a `NakamotoBlockProposal` whose `block.header.consensus_hash == T`'s consensus hash, with a `TenureChange` (`Extend`) whose burn-view fields resolve `get_block_burn_view` to `T`'s (now orphaned) snapshot.
4. Call `NakamotoBlockProposal::validate(...)` and assert whether it returns `Ok(BlockValidateOk)` (vulnerable) or a `NonCanonicalTenure` rejection (patched) — asserting the sort_tip/canonical-tip equality explicitly by comparing `sort_tip.sortition_id` against `SortitionDB::get_canonical_burn_chain_tip(sortdb.conn())` before and after the reorg.

    pub(crate) fn check_block_has_valid_tenure(
        db_handle: &SortitionHandleConn,
        tenure_id: &ConsensusHash,
    ) -> Result<(), BlockValidateRejectReason> {
        // Verify that the block's tenure is on the canonical sortition history
        if !db_handle.has_consensus_hash(tenure_id)? {
            warn!(
                "Rejected block proposal";
                "reason" => "Block's tenure consensus hash is not on the canonical Bitcoin fork",
                "consensus_hash" => %tenure_id,
            );
            return Err(BlockValidateRejectReason {
                reason_code: ValidateRejectCode::NonCanonicalTenure,
                reason: "Tenure consensus hash is not on the canonical Bitcoin fork".into(),
                failed_txid: None,
            });
        }
        Ok(())
    }
