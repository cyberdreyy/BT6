### Title
Instant-withdraw receipts are claimable before being funded, letting a claimant drain other users' funded withdraw claims — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays out the full `instantWithdrawsRequests[_user]` balance immediately from the strategy's underlying balance, without checking that the request matured across an epoch or that the manager actually funded it via `collectInstantWithdrawFunds`. Normal withdraw requests enforce `epochNumber > lastWithdrawRequest[_user]`; instant requests have no equivalent gating. An unprivileged KYC'd tranche holder can therefore withdraw unfunded instant receipts against underlying that belongs to other users' already-funded claims — the same missing-input/state-validation bug class as CVE-2020-12351.

### Finding Description
`requestInstantWithdraw` burns CDO strategy tokens, mints receipts to the user, and bumps `pendingInstantWithdraws` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (IdleCreditVault.sol:356-375). No timestamp or maturity marker is stored.

Funding is a separate manager-driven step: `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` and pulls underlying from the CDO (IdleCreditVault.sol:398-403).

But `claimInstantWithdrawRequest` performs no maturity/funding validation at all:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:387-392
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

The only gate is the CDO-side `allowInstantWithdraw` flag (IdleCDOEpochVariant.sol:975-979). `_transferFundedClaim` protects only `defaultRecoveryReserve` (IdleCreditVault.sol:897-907); underlying held for other users' funded normal claims, or freshly repaid borrower funds sitting in the strategy, is unprotected and spendable.

### Impact Explanation
An attacker who obtains an instant-withdraw receipt while the APR-drop condition holds (`lastEpochApr > unscaledApr + instantWithdrawAprDelta` in `requestWithdraw`, IdleCDOEpochVariant.sol:761-769) can call `claimInstantWithdrawRequest` in the same transaction/epoch, before any `collectInstantWithdrawFunds`. The payout is drawn from the vault's underlying balance, which is the shared pool backing already-funded normal withdraw receipts. Result: direct theft of other users' funded claims, breaking the "one receipt, one funded payout" invariant and potentially leaving legitimate claimants' `claimWithdrawRequest` calls reverting on insufficient balance (permanent freezing of unclaimed yield/principal). Loss is bounded by the strategy's spendable underlying balance at claim time.

### Likelihood Explanation
Requires instant withdrawals to be enabled (`!disableInstantWithdraw`, `!isProgrammableBorrower`, `allowInstantWithdraw`) and an APR decrease between epochs — an honest-manager configuration, not attacker-controlled, so it cannot be triggered on demand. However, once the condition exists, any KYC-passing tranche holder can execute it atomically with `requestWithdraw` → `claimInstantWithdrawRequest`, and there is no economic cost. Medium likelihood, high impact when reachable. I could not fully confirm whether `allowInstantWithdraw` is only ever set after funding; if it is, the window narrows but the contract still lacks the defensive check that exists for normal requests.

### Recommendation
Mirror the normal-claim gating for instant receipts: record the request epoch (already tracked via `instantWithdrawsRequestsByEpoch`) and require `epochNumber > requestEpoch`, or track a `fundedInstantWithdraws` counter credited by `collectInstantWithdrawFunds` and cap claims at the funded amount. Alternatively, deduct from `pendingInstantWithdraws` at claim time and revert if the request was never collected.

### Proof of Concept
Foundry fork PoC sketch (against the existing `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// 1. victim deposits AA, requests normal withdraw; epoch 0 runs and
//    stopEpoch funds the receipt (underlying now sits in the strategy).
// 2. manager sets a lower APR for epoch 1 so
//    lastEpochApr > unscaledApr + instantWithdrawAprDelta.
// 3. attacker (KYC'd) calls cdoEpoch.requestWithdraw(attackerTrancheBal, AAtranche)
//    -> routes into creditVault.requestInstantWithdraw.
// 4. In the same block, attacker calls cdoEpoch.claimInstantWithdrawRequest().
//    Observed: _transferFundedClaim pays `amount` from the strategy balance
//    even though collectInstantWithdrawFunds was never called and
//    pendingInstantWithdraws is unchanged.
// 5. victim.claimWithdrawRequest() now reverts/underpays: funded balance stolen.
assertGt(underlying.balanceOf(attacker), attackerPre, "unfunded instant claim paid");
assertEq(creditVault.pendingInstantWithdraws(), amount, "claim bypassed funding");
```

Key assertion: payout succeeds while `pendingInstantWithdraws > 0` and `collectInstantWithdrawFunds` was never invoked, demonstrating the missing maturity/funding validation at `IdleCreditVault.sol:387-392`.
