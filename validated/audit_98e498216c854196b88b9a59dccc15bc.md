### Title
Node-side signer weight tally double-counts a signer who rejects then later accepts, letting stale rejection weight survive alongside acceptance weight - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side `StackerDBListener` accumulates `total_weight_approved` and `total_weight_rejected` per block in a shared `BlockStatus` struct, but the two match arms that update these counters use **inconsistent guards**. The `Rejected` arm gates its weight addition on `block.responded_signers.insert(slot_id)` (i.e., "have we ever heard from this signer before, for either verdict"), while the `Accepted` arm gates only on `block.gathered_signatures.contains_key(&slot_id)` (i.e., "has this signer already sent an Accept"), never checking `responded_signers`. A signer that Rejects and later legitimately re-evaluates to Accept (an explicitly supported flow per the signer's own state machine: `LocallyRejected --> LocallyAccepted : re-evaluated`) therefore has its weight added to `total_weight_rejected` on the first message and *also* added to `total_weight_approved` on the second, with the stale rejection weight never removed.

### Finding Description
`BlockStatus` tracks weight tallies used by the mining coordinator to decide, per proposed block, whether enough signer weight has approved or rejected it: [1](#0-0) 

In the `Accepted` handler, the only de-duplication check is against `gathered_signatures`: [2](#0-1) 

In the `Rejected` handler, the de-duplication check is against the shared `responded_signers` set: [3](#0-2) 

Walk through the two orderings for one signer slot:
- Accept, then Reject: `responded_signers` already contains the slot from the Accept, so `.insert(slot_id)` returns `false` in the Reject arm and the reject weight is correctly **not** added again. This is the case the project already hardened against (see the signer-side fix noted in the changelog, "Do not count both a block acceptance and a block rejection for the same signer/block").
- Reject, then Accept: `responded_signers` contains the slot from the Reject, but the Accept arm never consults `responded_signers` — it only checks `gathered_signatures`, which is still empty for this slot. The Accept arm therefore adds this signer's weight to `total_weight_approved`, while the earlier reject weight remains in `total_weight_rejected` forever (nothing ever subtracts it).

The result is that `total_weight_approved + total_weight_rejected` can exceed `total_weight` and can include the *same* signer's weight in both buckets, which breaks the aggregated-weight-vs-verified-accepts equality the tally is supposed to preserve (each signer should contribute to exactly one live bucket, matching the signer-side `signerdb.rs` invariant demonstrated by `reject_then_accept`/`accept_then_reject` tests): [4](#0-3) 

This node-side tally directly drives `SignCoordinator::get_block_status`'s decision logic, which checks the rejection-crosses-blocking-minority condition *before* the acceptance-crosses-threshold condition: [5](#0-4) 

Because stale rejection weight is never cleared once a signer flips to Accept, a block that later achieves genuine ≥70% approval can simultaneously carry an inflated, stale `total_weight_rejected` (accumulated from signers who initially rejected for a transient reason — e.g. a not-yet-processed Bitcoin block, exactly the scenario exercised in `signers_reprocess_bitcoin_block_not_found_proposals`) — pushing it over the blocking-minority threshold and causing the coordinator to abandon a validly-signed block.

### Impact Explanation
This is a liveness wedge on the mining coordinator: transient/superseded rejections (a normal, expected occurrence per the signer re-evaluation flow) permanently pollute the rejection tally for a given block hash and are never reconciled against the signer's later acceptance. This can cause the coordinator to incorrectly treat an actually-approved block as globally rejected (`NakamotoNodeError::SignersRejected`), forcing unnecessary re-mining/timeouts, i.e. the coordinator acts on a stale/incorrect weight tally rather than the verified, exclusive per-signer decision — closely analogous to the reported bug class of an aggregated counter being incremented in a branch where it should not be.

### Likelihood Explanation
No majority collusion or malicious signer is required — a single honest signer that rejects a proposal for a transient reason (bitcoin-block-not-found, stale sortition view, etc.) and then correctly re-evaluates to Accept the same proposal (a normal, supported code path) is enough to trigger the double count. This is reachable purely through the ordinary gossip/response flow already exercised by existing integration tests such as `signers_reprocess_bitcoin_block_not_found_proposals`.

### Recommendation
Make the `Accepted` arm's guard symmetric with the `Rejected` arm's: check `block.responded_signers` (not just `gathered_signatures`) before adding to `total_weight_approved`, and/or when a signer's verdict flips, subtract any previously-added weight from the opposite bucket before adding to the new one, so each signer contributes to exactly one live bucket at a time — mirroring the invariant already enforced in `stacks-signer/src/signerdb.rs`.

### Proof of Concept
1. Miner proposes block `B`; signer slot `S` (weight `w`) sends `BlockResponse::Rejected` for `B` (e.g., because its node has not yet processed the referenced Bitcoin block). `stackerdb_listener.rs` records `responded_signers.insert(S)` and `total_weight_rejected += w`.
2. `S` re-evaluates after the Bitcoin block is processed and sends `BlockResponse::Accepted` for the same `B`.
3. The `Accepted` arm checks only `gathered_signatures.contains_key(&S)` (false) and adds `total_weight_approved += w`, without checking or clearing `S` from the rejection tally.
4. `total_weight_rejected` still includes `w` from step 1, and `total_weight_approved` now also includes `w` from step 3 — `S`'s weight is counted in both buckets simultaneously, inflating both totals beyond what distinct, live per-signer votes justify.
