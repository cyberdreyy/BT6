## Finding

### Title
`set_beneficiary_for_operator` skips pool synchronization, redirecting already-accrued commission to a new beneficiary - (File: `aptos-move/framework/aptos-framework/sources/delegation_pool.move`, `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
This is a direct structural analog of the Angle `SavingsVest.setParams` bug: a state-changing parameter update (`beneficiary`) is applied without first "accruing"/settling the value that was earned under the *previous* parameter value. In both `delegation_pool` and `staking_contract`, the operator's beneficiary is looked up **dynamically at payout time** rather than being snapshotted when commission is earned/requested, and the function that changes the beneficiary does not force a settlement first — unlike every sibling parameter-changing function in the same modules, which do.

### Finding Description
In `delegation_pool.move`, every other operator/owner state-changing entry function synchronizes the pool before mutating state, explicitly to make sure uncommitted commission is paid under the *old* parameters first:

- `set_operator` calls `synchronize_delegation_pool(pool_address)` before changing the operator: [1](#0-0) 
- `update_commission_percentage` explicitly documents and calls `synchronize_delegation_pool` "to ensure the operator is paid its uncommitted commission rewards with the old commission percentage" before changing it: [2](#0-1) 

But `set_beneficiary_for_operator` mutates `BeneficiaryForOperator` directly with **no synchronization call at all**: [3](#0-2) 

The commission itself is computed and paid to `beneficiary_for_operator(operator)` looked up **at synchronization time**, not at accrual time: [4](#0-3) 

The exact same pattern exists in `staking_contract.move`. `distribute_internal` resolves the recipient of the operator's share dynamically at distribution time: [5](#0-4) 

while `request_commission_internal` records the pending distribution keyed by the `operator` address itself (not a snapshotted beneficiary): [6](#0-5) 

`set_beneficiary_for_operator` again performs no settlement before flipping the beneficiary, and the code comment itself acknowledges the race but does not close it: it merely tells the caller they *should* call `distribute` first, without enforcing it: [7](#0-6) 

Because commission that has already been unlocked/requested (via `request_commission`, `unlock_stake`, `update_commision`, or accrued-but-not-yet-synchronized rewards in `delegation_pool`) is still keyed by `operator`, and the beneficiary used at final payout is resolved at payout time via `beneficiary_for_operator(operator)`, an operator can:
1. Let commission accrue while beneficiary A is set.
2. Call `set_beneficiary_for_operator(B)` at any time, with no synchronization/distribution forced.
3. At the next `synchronize_delegation_pool` / `distribute` call, **all** outstanding commission — including the portion that accrued while A was the beneficiary — is paid to B instead of A.

This exactly mirrors the Angle bug class: a parameter (`protocolSafetyFee`/`vestingPeriod` ↔ `beneficiary`) is changed without accruing/settling first, corrupting the accounting for value that should have belonged to the pre-change state.

### Impact Explanation
This falls squarely under the required impact "Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account or traps value." The previous beneficiary permanently loses their claim right to commission that was already earned/requested under their name — a non-recoverable loss of claim rights, since once distributed to the new beneficiary the funds cannot be clawed back. Depending on deployment (e.g., beneficiary contracts relying on this commission stream, revenue-sharing arrangements between operators and third-party beneficiaries), this can mean real-value redirection of funds away from the party who has an accounting-recorded entitlement to it.

### Likelihood Explanation
The trigger requires only an operator calling their own `set_beneficiary_for_operator`/`staking_contract::set_beneficiary_for_operator` function — an action fully within the operator's normal, unprivileged capability with respect to their own beneficiary designation. No special timing beyond "have accrued but not-yet-synchronized/distributed commission" is needed, which is the common case since synchronization/distribution happens periodically, not on every reward accrual. The race window exists continuously between distribution events.

### Recommendation
Force a settlement of all outstanding/accrued commission for the current beneficiary before allowing the beneficiary to change:
- In `delegation_pool::set_beneficiary_for_operator`, call `synchronize_delegation_pool(pool_address)` for every delegation pool controlled by the operator before updating `BeneficiaryForOperator` (mirroring `update_commission_percentage`'s pattern).
- In `staking_contract::set_beneficiary_for_operator`, iterate the operator's `Store` and call `distribute_internal` + `request_commission_internal` for each staking contract before flipping the beneficiary (mirroring `update_commision`'s pattern at lines 580-592).

### Proof of Concept
1. Operator O runs a delegation pool with beneficiary A set via `set_beneficiary_for_operator(A)`.
2. Delegators stake, epochs pass, rewards accrue in `active`/`pending_inactive` shares pools without a `synchronize_delegation_pool` call happening (no delegator action triggers one).
3. O calls `set_beneficiary_for_operator(B)` — no synchronization occurs, so the accrued-but-uncommitted commission is not paid to A.
4. Any subsequent user action (e.g., a delegator's `add_stake`/`unlock`) triggers `synchronize_delegation_pool`, which computes `commission_active`/`commission_pending_inactive` from stake pool drift and pays it via `buy_in_active_shares`/`buy_in_pending_inactive_shares` to `beneficiary_for_operator(operator)` — now B — even though this commission accrued while A was configured as beneficiary.
5. A's expected commission is unrecoverably paid to B. [8](#0-7)

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensure payment to the current beneficiary, one should first call `synchronize_delegation_pool`
    /// before switching the beneficiary. An operator can set one beneficiary for delegation pools, not a separate
    /// one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer,
        new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
        } else {
            move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
        };

        emit(SetBeneficiaryForOperator {
            operator: operator_addr,
            old_beneficiary,
            new_beneficiary,
        });
    }

    /// Synchronize delegation and stake pools: distribute yet-undetected rewards to the corresponding internal
    /// shares pools, assign commission to operator and eventually prepare delegation pool for a new lockup cycle.
    public entry fun synchronize_delegation_pool(
        pool_address: address
    ) acquires DelegationPool, GovernanceRecords, BeneficiaryForOperator, NextCommissionPercentage {
        assert_delegation_pool_exists(pool_address);
        let pool = borrow_global_mut<DelegationPool>(pool_address);
        let (
            lockup_cycle_ended,
            active,
            pending_inactive,
            commission_active,
            commission_pending_inactive
        ) = calculate_stake_pool_drift(pool);

        // zero `pending_active` stake indicates that either there are no `add_stake` fees or
        // previous epoch has ended and should release the shares owning the existing fees
        let (_, _, pending_active, _) = stake::get_stake(pool_address);
        if (pending_active == 0) {
            // renounce ownership over the `add_stake` fees by redeeming all shares of
            // the special shareholder, implicitly their equivalent coins, out of the active shares pool
            redeem_active_shares(pool, NULL_SHAREHOLDER, MAX_U64);
        };

        // distribute rewards remaining after commission, to delegators (to already existing shares)
        // before buying shares for the operator for its entire commission fee
        // otherwise, operator's new shares would additionally appreciate from rewards it does not own

        // update total coins accumulated by `active` + `pending_active` shares
        // redeemed `add_stake` fees are restored and distributed to the rest of the pool as rewards
        pool.active_shares.update_total_coins(active - commission_active);
        // update total coins accumulated by `pending_inactive` shares at current observed lockup cycle
        pending_inactive_shares_pool_mut(pool).update_total_coins(pending_inactive - commission_pending_inactive);

        // reward operator its commission out of uncommitted active rewards (`add_stake` fees already excluded)
        buy_in_active_shares(pool, beneficiary_for_operator(stake::get_operator(pool_address)), commission_active);
        // reward operator its commission out of uncommitted pending_inactive rewards
        buy_in_pending_inactive_shares(
            pool,
            beneficiary_for_operator(stake::get_operator(pool_address)),
            commission_pending_inactive
        );
