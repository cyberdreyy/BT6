### Title
User enumeration via distinct error messages and timing in CreateSession - ([File: core/sessions/localauth/orm.go])

### Summary
`CreateSession` calls `FindUser` (a DB lookup by email) before performing any constant-time or hashed comparisons, and returns the raw DB error immediately when the email does not exist, while a wrong-password attempt for a valid email triggers a bcrypt comparison and returns a distinct `"Invalid password"` error. This asymmetry (different error text and different execution cost — DB miss vs. bcrypt hash comparison) is directly forwarded to the HTTP client by `SessionsController.Create` via `jsonAPIError(c, http.StatusUnauthorized, err)`, giving an unauthenticated caller an oracle to enumerate registered emails.

### Finding Description
In `core/sessions/localauth/orm.go`: [1](#0-0) 

- If `sr.Email` does not match any row, `FindUser`/`findUser` returns a DB error (e.g. "sql: no rows in result set") and `CreateSession` returns immediately with `"", err` — no bcrypt work is performed [2](#0-1) .
- If the email exists, the function proceeds to `constantTimeEmailCompare` (which will normally pass because `user.Email` came from the same lookup) and then calls `utils.CheckPasswordHash` — a bcrypt comparison, which is computationally expensive and takes measurably longer than a DB-not-found path — before returning `"Invalid password"` [3](#0-2) .

These two error values are propagated unmodified to the HTTP layer. `SessionsController.Create` forwards `err` from `CreateSession` directly as the JSON API error body with status 401, without normalizing the message or timing: [4](#0-3) 

Additionally, `Create` performs an unconditional `GetUserWebAuthn(ctx, sr.Email)` lookup prior to calling `CreateSession` at all [5](#0-4) ; while a "no rows" result there isn't treated as an error, this is an additional non-constant-time DB query keyed on attacker-supplied email that adds to the measurable difference between existing and non-existing accounts.

The combination — different error content ("no matching row"-style error vs. "Invalid password") and different processing cost (DB lookup miss vs. bcrypt compare) — allows an unauthenticated caller to distinguish "email doesn't exist" from "email exists, wrong password" purely from the `/sessions` endpoint response, both by content and by timing.

### Impact Explanation
This enables account/email enumeration on the Chainlink node's admin login endpoint. It does not by itself grant authentication bypass or secret disclosure, but it materially narrows a credential-stuffing/targeted brute-force attack surface by confirming which emails are valid node-operator accounts, matching a "sensitive data exposure / information disclosure enabling further attack" class rather than a critical account-takeover class.

### Likelihood Explanation
Fully unauthenticated and trivially repeatable: an attacker just needs network access to `POST /sessions` with attacker-chosen emails and can compare responses (error text) or measure timing across many samples to statistically distinguish existing vs. non-existing accounts. No credentials or special role are required, and the difference in error text is deterministic (present on essentially every request), making content-based enumeration reliable even without needing to measure timing.

### Recommendation
- In `CreateSession`, when `FindUser` fails (email not found), do not return early with a distinct error; instead, run a dummy/constant-cost password hash comparison (e.g., against a fixed dummy bcrypt hash) before returning, and normalize the returned error to the exact same generic message/type (e.g., `"invalid credentials"`) used for the wrong-password path.
- In `SessionsController.Create`, replace direct exposure of internal auth errors with a single generic `401 invalid credentials` message for all authentication failure branches (bad email, bad password, MFA-related failures where appropriate) so response bodies are indistinguishable.
- Move or gate the `GetUserWebAuthn` pre-check in `Create` so it does not leak account existence timing separately from `CreateSession`, or perform it in constant time regardless of user existence.

### Proof of Concept
Go handler-level integration test plan for `core/web/sessions_controller_test.go` (or `core/sessions/localauth/orm_test.go`):
1. Seed one valid user (`existing@example.com`) with a real bcrypt-hashed password.
2. Case A: `POST /sessions` with `{"email":"existing@example.com","password":"wrongpass"}` — capture response body and elapsed time over N repeated requests.
3. Case B: `POST /sessions` with `{"email":"nonexistent@example.com","password":"wrongpass"}` — capture response body and elapsed time over N repeated requests.
4. Assert: response bodies for Case A and Case B are currently different (`"Invalid password"` vs. an error derived from the DB "no rows" error) — demonstrating content-based enumeration; this assertion should fail after the fix (bodies must be identical, e.g., both `"invalid credentials"`).
5. Optionally add a unit test directly on `orm.CreateSession` using a stubbed `sqlutil.DataSource` with an injected artificial delay for the "found" branch vs. immediate return for the "not found" branch, asserting the timing delta remains within a fixed tolerance after remediation (dummy hash comparison added to the not-found path).

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```
