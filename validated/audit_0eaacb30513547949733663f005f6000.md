### Title
Dust queued deposit at the prefunding cutoff permanently bricks `stopEpochWithDuration`, freezing all pool funds - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
On `IdleCDOEpochVariantPrefunded` pools with a prefunded `IdleCDOEpochQueue`, any KYC-passing lender can permanently prevent the epoch from being stopped by depositing 1 wei into the queue in the last block before `prefundedDepositWindow` closes. `stopEpochWithDuration` atomically calls `prefundedDepositsToProcess()`, which reverts whenever `epochPendingDeposits[epoch] != 0`, and there is no remaining path to move or remove the queued deposit: `processDepositsToBorrower` reverts after the cutoff, `processDeposits` is disabled for prefunded queues, and only the depositor can `deleteRequest`. The result is a permanent freeze of every depositor's funds — the direct analog of the InnoDB "repeatable crash / hang" availability bug.

### Finding Description
The prefunded flow has three coupled checks:

1. `requestDeposit` accepts deposits while `block.timestamp + prefundedDepositWindow < epochEndDate` (and while nothing is yet prefunded) — `IdleCDOEpochQueue.sol:114-117`.
2. `processDepositsToBorrower` (owner/manager only) moves `epochPendingDeposits` → `epochPrefundedDeposits`, but only under the identical window condition `block.timestamp + prefundedDepositWindow < epochEndDate` — `IdleCDOEpochQueue.sol:163-164`.
3. `stopEpochWithDuration` → `_afterStopEpochWithDuration` → `prefundedDepositsToProcess()`, which **hard-reverts** if `epochPendingDeposits[epoch] != 0` — `IdleCDOEpochQueue.sol:277-282`, invoked from `IdleCDOEpochVariantPrefunded.sol:72-88`. The direct `stopEpoch` selector is also blocked while a queue is configured (`IdleCDOEpochVariantPrefunded.sol:43`), so there is no alternative stop path.

Because both the deposit acceptance bound and the prefunding bound are the same `epochEndDate - prefundedDepositWindow` timestamp, an attacker who deposits dust in the last valid block leaves no valid block in which `processDepositsToBorrower` can still run. The revert in `prefundedDepositsToProcess` is inside the same transaction as the base stop accounting, so the whole stop reverts — every future `stopEpochWithDuration` call reverts identically.

Cleanup paths all fail:
- `processDeposits` reverts for prefunded queues (`_checkNotAllowed(_isPrefundedQueueEnabled())`, `IdleCDOEpochQueue.sol:226`).
- `processDepositsToBorrower` reverts once `block.timestamp + window >= epochEndDate`.
- `deleteRequest` is only callable by the depositor (`userDepositsEpochs[msg.sender]`, `IdleCDOEpochQueue.sol:184-199`); the attacker simply does not call it.
- `requestWithdraw`/`claimWithdrawRequest` on the CDO do not touch `epochPendingDeposits`; the queue revert is evaluated on every stop regardless.

Broken invariant: epoch lifecycle progress (a running epoch must always be stoppable) — violated by a single stuck wei. Cost to attacker: 1 wei of underlying, locked in the queue (refundable, but attacker abstains).

### Impact Explanation
Permanent freezing of all user funds in the pool. With `stopEpochWithDuration` permanently reverting: the epoch can never end, `epochNumber` never increments, `requestWithdraw` receipts can never be claimed (claims require `epochNumber > lastWithdrawRequest`), the borrower is never made to repay or default, and `depositAA`/`depositBB` stay gated. The entire NAV of the pool plus all pending withdraw receipts are frozen indefinitely. Loss magnitude: full pool TVL.

### Likelihood Explanation
Requirements: the deployment uses `IdleCDOEpochVariantPrefunded` with `epochQueue` set and `prefundedDepositWindow > 0` — the intended prefunded configuration. Attacker needs only Keyring clearance (`_checkAllowed` → `isWalletAllowed`, `IdleCDOEpochQueue.sol:105,415-421`), which the model treats as an unprivileged lender. The attack is a single `requestDeposit(1)` timed to the last block before `epochEndDate - prefundedDepositWindow`; no front-running of a specific honest tx is even needed if the manager simply hasn't prefunded yet — any dust deposited before the cutoff that isn't prefunded before the cutoff suffices, and a determined attacker can keep depositing dust late in the window to make each prefunding attempt lose the race. Existing guards (`checkPrefunding` TVL cap, `epochPrefundedDeposits != 0` block, skim) do not prevent a dust pending deposit.

### Recommendation
Give the protocol a path to clear raw pending deposits after the window closes, e.g.:
- In `processDepositsToBorrower`, allow post-cutoff forwarding (drop or relax the `block.timestamp + _prefundedWindow < epochEndDate` check), or
- Add an owner/manager-only `refundPendingDeposits(epoch)` that returns `epochPendingDeposits` pro-rata to depositors and zeroes the counter, or
- In `prefundedDepositsToProcess`, treat leftover pending deposits as refundable (skip the revert and let `deleteRequest` handle them) instead of reverting the entire stop.

### Proof of Concept
Foundry fork test sketch (deploy per `test/foundry/IdleCDOEpochQueue.t.sol` setup with prefunded queue enabled and `prefundedDepositWindow = PREFUNDED_DEPOSIT_WINDOW`):

```solidity
function testDustPendingDepositBricksStop() external {
    // setup: prefunded queue enabled, window set
    vm.prank(manager);
    cdoEpoch.setEpochQueue(address(queue));
    vm.prank(manager);
    queue.setPrefundedDepositWindow(PREFUNDED_DEPOSIT_WINDOW);

    // honest lenders have deposits and borrower's funds outstanding
    _depositWithUser(lender, 1000e6);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // attacker (KYC'd) deposits 1 wei in the last block before the cutoff
    address attacker = makeAddr('attacker');
    deal(address(underlying), attacker, 1);
    vm.warp(cdoEpoch.epochEndDate() - PREFUNDED_DEPOSIT_WINDOW - 1);
    vm.startPrank(attacker);
    underlying.approve(address(queue), 1);
    queue.requestDeposit(1);            // still accepted
    vm.stopPrank();

    // manager can no longer prefund the dust: window closed
    vm.warp(cdoEpoch.epochEndDate() - PREFUNDED_DEPOSIT_WINDOW + 1);
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    queue.processDepositsToBorrower();
    // non-prefunded path also blocked
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    queue.processDeposits();

    // borrower repays in full — epoch still cannot be stopped
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(address(underlying), borrower, type(uint112).max);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), type(uint256).max);
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector); // epochPendingDeposits != 0
    cdoEpoch.stopEpochWithDuration(0, 1e6, cdoEpoch.epochDuration(), 0);

    // permanent: repeat calls revert forever; lender funds and
    // queued withdraw receipts are frozen. Attacker's cost: 1 wei.
}
```
