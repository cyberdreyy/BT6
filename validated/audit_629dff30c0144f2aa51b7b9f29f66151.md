Based on the code I could trace, I found a plausible but only partially verifiable scaling issue in `StatusCache`. I was unable to locate the definition of `DurableNonce::from_blockhash` (it lives in the external `solana-nonce` crate, outside this index), so part of the causal chain relies on inference from call sites rather than direct code inspection. I flag this uncertainty explicitly below.

### Title
Unbounded growth of `StatusCache::cache` via durable-nonce blockhash diversity inflates cost of `get_status_any_blockhash` - ([File: runtime/src/status_cache.rs])

### Finding Description
`StatusCache::insert` keys its top-level map `cache: KeyStatusMap<T>` (`HashMap<Hash, (Slot, usize, KeyMap<T>)>`) by `transaction_blockhash` [1](#0-0) . For ordinary transactions this key space is bounded because the bank only accepts `recent_blockhash` values inside the `MAX_RECENT_BLOCKHASHES`-deep blockhash queue [2](#0-1) . However, for durable-nonce transactions, `check_transaction_age`/`check_nonce_transaction_validity` accept a `recent_blockhash` that is *not* required to be in the recent blockhash queue at all — it only has to match the nonce account's on-chain stored `durable_nonce` [3](#0-2) , and `validate_transaction_nonce` in the SVM performs the same on-chain-state-only check [4](#0-3) . Each such transaction's `recent_blockhash` (the nonce's previously stored `durable_nonce`, itself `DurableNonce::from_blockhash(&some_historical_blockhash)`) is then used verbatim as the `transaction_blockhash` key inserted into `self.cache` via `update_transaction_statuses` [5](#0-4) .

Because these nonce-derived hash values are not confined to the current ~300-slot blockhash-queue window, an attacker who maintains many nonce accounts last-advanced at many distinct historical slots can submit transactions using these old, distinct nonce hashes, each producing a new, unpurged entry in `self.cache`. The shuttle test comments in this same file explicitly acknowledge this: "unlike `clear_slot_entries()`, `purge_slots()` can't overlap with regular blockhashes since they'd have expired ... However, nonces don't expire, so they can overlap" [6](#0-5) . Entries are only evicted from `self.cache` once the *containing slot's root* ages past `max_root_entries` via `purge_roots` [7](#0-6) , not based on the age of the nonce hash itself — so distinct nonce-derived keys accumulate for up to `MAX_RECENT_BLOCKHASHES` (~300) slots before eviction.

`get_status_any_blockhash`, used by `Bank::get_signature_status_slot` (the function backing `getSignatureStatuses`/transaction-status RPC lookups [8](#0-7) , invoked from `rpc.rs::get_signature_statuses`/`get_transaction_status` [9](#0-8) ), does a linear scan over **all** distinct blockhash keys in `self.cache`: [10](#0-9) 
This means one JSON-RPC `getSignatureStatuses` call's cost scales with the number of distinct blockhash keys resident in `self.cache`, which — via durable-nonce diversity — is influenced by attacker-controlled on-chain nonce-account state rather than solely by a fixed protocol constant.

**Uncertainty**: I could not verify the internal implementation of `DurableNonce::from_blockhash` (defined in the `solana-nonce` crate, not present in this index). Call sites show it is invoked with the bank's per-slot `environment_config.blockhash` [11](#0-10) , which is identical for every nonce account advanced within the same slot — implying diversity in `self.cache` keys comes only from nonce accounts last advanced in *different* historical slots (accumulated over time), not from many nonce accounts advanced in the *same* slot. Confirming the exact hash derivation (whether it mixes in slot number only, or nothing else) requires reading that external crate, which is out of the indexed codebase.

### Impact Explanation
This is an unbounded-per-request-cost issue (RPC DoS category): the cost of a single `getSignatureStatuses` call becomes proportional to attacker-inflatable on-chain nonce-account diversity rather than a fixed request-scoped bound, degrading `get_status_any_blockhash` from effectively O(1)/O(small-constant) to O(number of distinct nonce-derived blockhashes retained in `StatusCache`).

### Likelihood Explanation
Exploitation requires the attacker to (a) create and fund many nonce accounts over time (rent-exempt minimum per account, an unprivileged/self-funded cost) and (b) advance them at different historical slots so each carries a distinct stored `durable_nonce`, then (c) submit transactions using those nonces so they land (need not be rooted) within the ~300-slot retention window before `purge_roots` prunes older entries. This is entirely achievable by a single unprivileged client over time without leader/validator control, though it requires sustained setup (many nonce accounts, many prior slots) rather than a single burst, and the per-slot transaction count is itself bounded by normal block capacity.

### Recommendation
Bound `get_status_any_blockhash`'s work independent of `self.cache` size — e.g., cap the number of blockhash buckets searched per call, or maintain a separate, protocol-bounded index (keyed only by the true MAX_RECENT_BLOCKHASHES window) for RPC signature lookups, with durable-nonce-derived, out-of-window hashes tracked/evicted separately and not fully retained for the entire root-purge horizon. Alternatively, require `get_status_any_blockhash`-style RPC lookups to specify `minContextSlot`/blockhash hints to avoid a full-cache scan, or cap `self.cache`'s total distinct-key count with LRU eviction independent of `purge_roots`'s slot-based logic.

    pub fn insert<K: AsRef<[u8]>>(
        &mut self,
        transaction_blockhash: &Hash,
        key: K,
        slot: Slot,
        res: T,
    ) {
        let max_key_index = key.as_ref().len().saturating_sub(CACHED_KEY_SIZE + 1);

        // Get the cache entry for this blockhash.
        let (max_slot, key_index, hash_map) = self
            .cache
            .entry(*transaction_blockhash)
            .or_insert_with(|| (slot, 0, HashMap::new()));

        // Update the max slot observed to contain txs using this blockhash.
        *max_slot = std::cmp::max(slot, *max_slot);

        // Grab the key slice.
        let key_index = (*key_index).min(max_key_index);
        let mut key_slice = [0u8; CACHED_KEY_SIZE];
        key_slice.clone_from_slice(&key.as_ref()[key_index..key_index + CACHED_KEY_SIZE]);

        // Insert the slot and tx result into the cache entry associated with
        // this blockhash and keyslice.
        let forks = hash_map.entry(key_slice).or_default();
        forks.push((slot, res.clone()));

        self.add_to_slot_delta(transaction_blockhash, slot, key_index, key_slice, res);
    }
