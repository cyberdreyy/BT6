### Title
Non-ErrNoRows DB errors during external initiator auth leak underlying error text ("finding external initiator: ...") in the 401 response body - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` only maps `sql.ErrNoRows` to the generic `auth.ErrorAuthFailed`; any other DB-layer error returned by `FindExternalInitiator` is wrapped with `pkgerrors.Wrap(err, "finding external initiator")` and passed through unchanged to `jsonAPIError`, which serializes `err.Error()` directly into the JSON response body sent to the client.

### Finding Description
The relevant code is: [1](#0-0) 
`FindExternalInitiator` executes `SELECT * FROM external_initiators WHERE access_key = $1` using the attacker-supplied `access_key` header value [2](#0-1) . If this query returns any error other than `sql.ErrNoRows` (e.g., a malformed/oversized access key causing a driver-level error, a connection/timeout error, or any other Postgres error), the error is wrapped with the string `"finding external initiator"` and returned unmodified — it is NOT converted to `auth.ErrorAuthFailed`.

This error then propagates through `Authenticate`'s loop [3](#0-2) , which calls `jsonAPIError(c, http.StatusUnauthorized, err)`. `jsonAPIError` in `core/web/auth/helpers.go` checks if the error is a `*models.JSONAPIErrors`; since it is a plain wrapped error, it falls through to `c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))`, directly embedding `err.Error()` (i.e., `"finding external initiator: <underlying driver/DB error>"`) into the HTTP response body returned to the unauthenticated caller [4](#0-3) .

The attacker controls the `access_key` header value sent in the request and can attempt to trigger DB-level errors (e.g., by sending a value that causes an encoding/type error, or oversized/malformed input) to potentially surface backend error text.

### Impact Explanation
This is an information-disclosure issue: it could leak internal error strings (e.g., driver error text, query fragments) to an unauthenticated attacker. However, the standard Postgres/sqlx text-column query (`access_key` is a string column compared to a string parameter) makes it hard to trigger a non-`ErrNoRows`, attacker-triggerable DB error through normal HTTP input — most malformed input (empty, wrong length, non-matching string) simply results in `sql.ErrNoRows`, which is already sanitized. Realistic triggers for a different error class (connection failure, context cancellation, statement timeout) are largely operational/infrastructure conditions, not something an unprivileged HTTP client can force deterministically via crafted request content alone. There is no evidence the underlying `AccessKey` value or SQL statement text itself would appear in the error string, since `lib/pq`/sqlx errors for a no-match `SELECT` don't include bound parameter values.

### Likelihood Explanation
Low. The attacker would need to induce a database-level error other than "no rows" through header input alone, which the current query shape does not appear to make straightforward from unprivileged HTTP requests (no evidence of a code path where header content can trigger, e.g., a type-cast failure or oversized value error deterministically). No concrete attacker-controlled input was found in the codebase that reliably drives `FindExternalInitiator` down this non-`ErrNoRows` branch.

### Recommendation
As defense-in-depth, treat all errors from `store.FindExternalInitiator` (not just `sql.ErrNoRows`) as `auth.ErrorAuthFailed` for the response returned to the client, while still logging the wrapped underlying error server-side for diagnostics, mirroring the pattern already used in `AuthenticateByToken` for `sql.ErrNoRows` / `ErrUserSessionExpired`.

### Proof of Concept
Handler-level Go test plan:
1. Construct a mock `Authenticator`/`store` whose `FindExternalInitiator` returns a non-`sql.ErrNoRows` error, e.g., `errors.New("pq: some internal db failure detail")`.
2. Wrap `auth.Authenticate(mockStore, auth.AuthenticateExternalInitiator)` as gin middleware and perform an HTTP request with `static.ExternalInitiatorAccessKeyHeader` set to an arbitrary value.
3. Assert the response status is `401`.
4. Assert the response JSON body's error message equals/contains the mock's raw error text (`"finding external initiator: pq: some internal db failure detail"`), demonstrating that the internal error message is echoed back to the unauthenticated caller instead of a generic `auth.ErrorAuthFailed` message.
5. As a contrast case, also test with `store.FindExternalInitiator` returning `sql.ErrNoRows` and assert the body only contains the generic auth failure message, confirming the inconsistency between the two branches.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
