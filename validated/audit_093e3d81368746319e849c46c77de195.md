### Title
Builder payments can be over-committed and silently truncated instead of reverting - ([File: specs/gloas/beacon-chain.md])

### Summary
`process_execution_payload_bid` in `specs/gloas/beacon-chain.md` gates a new bid on `can_builder_cover_bid(state, builder_index, amount)`, but a builder's `balance` is not decremented at bid-acceptance time — only later, at settlement, via `apply_withdrawals`. Because settlement can be delayed for up to roughly two epochs (through `builder_pending_payments` → `process_builder_pending_payments` / `settle_builder_payment`), a single builder can have several bids "in flight" simultaneously, each individually checked against the *same*, not-yet-decremented `balance`. When these payments eventually settle, `apply_withdrawals` does not assert sufficient funds — it silently clamps: `state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)`. This is the same failure pattern as the Vultisig bug: a shared resource (`builder.balance`) is checked/consumed by multiple claims without reserving per-claim amounts, so whichever payment settles first gets paid in full, and later legitimate payments are silently short-paid (escape) rather than causing a revert or being rejected up front.

### Finding Description
- Bid acceptance: `process_execution_payload_bid` asserts `can_builder_cover_bid(state, builder_index, amount)` and, if `amount > 0`, records a `BuilderPendingPayment` in `state.builder_pending_payments[...]` [1](#0-0) . The builder's `balance` is **not** reduced here.
- Settlement is deferred: `apply_parent_execution_payload` settles the payment for the parent block only when its containing block is processed, calling `settle_builder_payment` (current/previous epoch) or, if evicted, directly appending a `BuilderPendingWithdrawal` [2](#0-1) . `process_builder_pending_payments`, run once per epoch, only promotes payments whose accumulated attestation `weight >= quorum` into `builder_pending_withdrawals`; unpromoted/oldest entries are simply evicted [3](#0-2) .
- Actual balance deduction happens only when the resulting `BuilderPendingWithdrawal` is turned into a real `Withdrawal` and applied: `apply_withdrawals` clamps the deduction to whatever balance remains — `builder_balance -= min(withdrawal.amount, builder_balance)` — rather than asserting the balance is sufficient [4](#0-3) .

Because the affordability check (`can_builder_cover_bid`) happens once per bid against the *current* `balance` and the balance is only actually spent much later, nothing prevents a builder from bidding an amount it can "afford" in slot N, then bidding the same (or another large) amount again in slot N+1..N+k before slot N's payment has settled — each check passes against the same unspent balance. When multiple pending payments for the same builder are eventually processed by `apply_withdrawals`/`get_builder_withdrawals`, the first ones consume the real balance in full, and the later ones are silently truncated by the `min(...)` clamp in `apply_withdrawals` instead of failing. This mirrors the Vultisig root cause exactly: an all-or-nothing/first-come-first-served draw against a shared balance with no per-claim reservation, so a payment the block already committed to (a signed, accepted bid with a recorded `BuilderPendingPayment`) ends up only partially honored for a later, equally-legitimate claimant, with no assertion failure to signal the shortfall.

### Impact Explanation
This falls under the "High" impact category explicitly listed in scope: a builder payment "misdirected, doubled, or escaped." A fee recipient who was promised `amount` Gwei by a signed, on-chain-recorded `BuilderPendingPayment`/`BuilderPendingWithdrawal` can receive less than committed, with the shortfall vanishing (not refunded to the builder, not paid to anyone) because `apply_withdrawals` clamps silently rather than reverting or re-queuing the unpaid remainder. Since this happens deterministically inside state-transition logic that all honest nodes execute identically, it does not itself cause a chain split, but it is a genuine Gwei/payment-integrity violation matching the report's core equality break ("a payment applied that the block did not commit to" / less than committed).

### Likelihood Explanation
Likelihood depends on whether `can_builder_cover_bid` (definition not directly located in this pass) checks the builder's balance net of all currently outstanding, unsettled bids/pending payments, or only the raw `balance` field. The `min(withdrawal.amount, builder_balance)` clamp present in `apply_withdrawals` is strong circumstantial evidence that the spec authors anticipated balance possibly being insufficient at settlement time — which would be unnecessary if bid acceptance always reserved funds up front. I was not able to retrieve the body of `can_builder_cover_bid` in this session to confirm definitively whether it nets out pending, unsettled commitments; this is the key open question that determines whether the issue is fully live or already mitigated.

### Recommendation
- Have `can_builder_cover_bid` check `builder.balance` net of the sum of all amounts already committed in `state.builder_pending_payments` and `state.builder_pending_withdrawals` for that `builder_index`, not just the raw balance.
- Alternatively, reserve (deduct) the bid amount from `builder.balance` immediately at bid-acceptance time (mirroring how `apply_withdrawals` deducts on settlement) and refund it if the payment is evicted without reaching quorum.
- Remove or tighten the `min(withdrawal.amount, builder_balance)` clamp in `apply_withdrawals` so that an under-funded settlement is either impossible by construction or is provably a no-op condition, rather than a silent partial payment.

### Proof of Concept
Conceptual sequence (state-transition level, no malicious peer required — a single builder acting alone controls only their own commitments, but the honest proposer/fee-recipient is the one who loses funds):
1. Builder `B` has `balance = X`.
2. At slot `s0`, `B` bids `value = X` to proposer `P0`. `can_builder_cover_bid` passes (`X <= X`), bid recorded in `builder_pending_payments`. `B.balance` still `= X` (unchanged).
3. Before slot `s0`'s payment settles (within the ~2-epoch window before `process_builder_pending_payments` evicts/promotes it), at slot `s1`, `B` bids `value = X` again to a different proposer `P1`. `can_builder_cover_bid` again passes against the same unspent `balance = X`.
4. Both payments reach quorum and are queued as `BuilderPendingWithdrawal`s with `amount = X` each.
5. `apply_withdrawals` processes `P0`'s withdrawal first: `B.balance` (still `X`) → `min(X, X) = X` paid, `B.balance` becomes `0`.
6. `apply_withdrawals` processes `P1`'s withdrawal: `min(X, 0) = 0` paid — `P1` receives nothing, silently, even though the chain recorded a `BuilderPendingPayment`/`BuilderPendingWithdrawal` committing `X` to `P1`.

This cannot be exercised directly against the referenced code without confirming `can_builder_cover_bid`'s exact check, which I could not view in this session — flagged above as the remaining uncertainty.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid
