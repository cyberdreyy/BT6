### Title
Stale per-epoch instant-withdraw claim flags inflate default recovery basis and let an early claimant drain the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The ksmbd bug is a data race caused by reading/writing a shared flags field under inconsistent locking. The direct analog in this codebase is `instantWithdrawClaimsByEpoch` / `instantWithdrawsRequestsByEpoch`: these per-epoch "pending claim" counters are written on request and on the *defaulted* claim path, but are never cleared or decremented on the normal (funded) claim path. When a borrower default is finalized in an epoch where some instant receipts were already claimed, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` read stale per-epoch flags that still count the already-paid receipts, overstating both the recovery basis and the reserve. The resulting `defaultRecoveryPrice` is inflated, so a claimant who races to claim first is paid above their fair share while later honest claimants' transfers revert on insufficient balance.

### Finding Description
`requestInstantWithdraw` increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]` and `pendingInstantWithdraws` (IdleCreditVault.sol:356-375). The normal claim path `claimInstantWithdrawRequest` burns the aggregate receipt and zeroes only `instantWithdrawsRequests[_user]` (lines 387-392). It never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]` — the per-epoch flags stay set forever, mirroring the kernel bug where some `m_flags` updates ran without `ci->m_lock` while others held it.

On default finalization, `finalizeDefaultRecovery` calls `defaultPendingClaimBasis()`, which adds `instantWithdrawClaimsByEpoch[epochNumber]` to the claim basis whenever `pendingInstantWithdraws != 0` (lines 644-649), and `_defaultPrefundedInstantReserve()`, which treats `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` as already-held reserve backing (lines 716-723). Both are inflated by the stale counter S of instant receipts that were already claimed and burned. `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688) then moves toward or above par, and `defaultRecoveryReserve` is credited with S tokens that do not exist.

An attacker therefore keeps one real defaulted-epoch receipt (a normal `requestWithdraw` recorded in `withdrawsRequestsByEpoch[user][defaultEpoch]`), claims it via `claimWithdrawRequest` → `_claimDefaultedWithdrawRequest` → `_transferDefaultRecovery` at the inflated price, and drains real underlying beyond their fair share. Subsequent honest claimants' `underlyingToken.safeTransfer` calls revert once the actual balance is exhausted, permanently freezing the remainder of the recovery.

### Impact Explanation
Theft plus permanent freezing of unclaimed recovery proceeds. If S is the stale already-claimed instant amount, and the true recovery is `R` against true basis `B` (R < B, i.e. a real loss), the stored price becomes `(R+S)/(B+S)` instead of `R/B`, a strict overvaluation. The attacker with claim basis `c` extracts `c·(R+S)/(B+S)` instead of `c·R/B`; every unit of overpayment is subtracted from what remains for honest defaulted-epoch claimants, whose `safeTransfer` in `_transferDefaultRecovery` then reverts on insufficient token balance — their claims are frozen permanently because `defaultRecoveryReserve` accounting believes funds remain while the vault is empty. Loss is up to `S` tokens redistributed to early claimants plus stranded claims.

### Likelihood Explanation
Requirements: (1) the attacker (any KYC-passed lender) makes an instant withdraw request and claims it normally in epoch N — the per-epoch flags are never cleared, so this persists; (2) at least one honest instant receipt in epoch N remains unfunded at finalization (`pendingInstantWithdraws != 0`), which occurs whenever the CDO's collected cash covers only part of the instant queue — exactly the partial-prefund scenario the code comments describe; (3) the borrower defaults in epoch N. The attacker additionally holds a normal withdraw request in epoch N (no guard prevents holding both request types in the same epoch pre-default). The attacker is an ordinary lender sequencing around honest manager/borrower calls; no privileged role is required. The epoch must be the same for the stale flag and the default, so window alignment is needed, but instant requests and defaults both happen during running epochs.

### Recommendation
Clear per-epoch instant claim state on the funded claim path, mirroring how `_clearWithdrawClaimForEpoch` clears `withdrawsRequestsByEpoch`. In `claimInstantWithdrawRequest`, decrement `instantWithdrawClaimsByEpoch[epoch-of-request]` and zero `instantWithdrawsRequestsByEpoch[_user][epoch]` for the epochs being paid (or track the request epoch per user). Alternatively, make `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` derive the instant basis from live receipts rather than the never-cleared epoch aggregate. Unify the invariant: every path that settles a receipt must update the same set of counters.

### Proof of Concept
Foundry fork test outline (mainnet fork of an IdleCDOEpochVariant + IdleCreditVault deployment with `allowInstantWithdraw` enabled):

```solidity
// test/foundry/InstantClaimStaleFlag.t.sol
function testStaleInstantFlagInflatesRecovery() public {
    // Epoch N running (fixed-APR mode, instant withdraws allowed).
    // 1. Attacker (KYC'd lender): requestInstantWithdraw(A); manager stopEpoch funds
    //    instant queue partially, leaving honest user's instant request H unfunded
    //    (pendingInstantWithdraws = H > 0).
    // 2. Attacker claimInstantWithdrawRequest() -> burns A, zeroes aggregate,
    //    but instantWithdrawClaimsByEpoch[N] still = A + H.
    // 3. Attacker also requestWithdraw() in epoch N -> withdrawsRequestsByEpoch[N] = W.
    // 4. Borrower defaults; owner calls finalizeDefaultRecovery(recovered, source).
  //    assert: defaultPendingClaimBasis() includes A + H, not just H.
    //    _defaultPrefundedInstantReserve() = (A+H) - H = A  (phantom reserve).
    //    recoveryPrice = (R + A) / (B + A)  >  R / B.
    // 5. Attacker claimWithdrawRequest() first:
    //    receives W * (R+A)/(B+A) / RECOVERY_FULL  > fair  W*R/B.
    // 6. Honest defaulted claimants call claimWithdrawRequest():
    //    underlyingToken.safeTransfer reverts (balance < amount) ->
    //    vm.expectRevert on the final honest claim.
    // Loss: attacker extracted ~W*A/(B+A) extra; honest claims of same total
    // are permanently unpayable.
}
```

Uncertainty: step 1's partial funding requires CDO cash `< pendingInstantWithdraws` at epoch start (reachable when the borrower draws most funds); the stale-flag mechanism itself is unconditional — `claimInstantWithdrawRequest` demonstrably never touches `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` (lines 380-393 vs. 847-853), so the inflated basis in `finalizeDefaultRecovery` follows directly whenever `pendingInstantWithdraws != 0` at finalization.
