Confirmed: the accepted-branch adds weight based on `gathered_signatures.contains_key(&slot_id)` while the rejected-branch adds weight based on `responded_signers.insert(slot_id)`, and these are two separate, never-reconciled ledgers, exactly mirroring the `pendingLockedBalance_a`/`pendingLockedBalance_b` split-accounting bug in the report.

### Title
Signer weight double-booked in both `total_weight_rejected` and `total_weight_approved` when a signer switches its vote, sticking `total_weight_rejected` forever - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The one-slot miner's coordinator (`StackerDBListener`) tracks two independent running counters per block, `total_weight_approved` and `total_weight_rejected`, inside `BlockStatus`. A signer is legitimately allowed to change its vote for the same `signer_signature_hash` (the docs' own `BlockState` diagram shows `LocallyRejected --> LocallyAccepted : re-evaluated`), but the coordinator has no code path that removes a signer's weight from `total_weight_rejected` once it has been added there, even after that same signer later accepts.

### Finding Description
In the `Rejected` arm, weight is added to `total_weight_rejected` guarded only by `block.responded_signers.insert(slot_id)`: [1](#0-0) 

In the `Accepted` arm, weight is added to `total_weight_approved` guarded only by `!block.gathered_signatures.contains_key(&slot_id)`, then `responded_signers.insert(slot_id)` is called unconditionally afterward: [2](#0-1) 

These two guards check two *different* maps (`responded_signers` vs `gathered_signatures`), so:
- If slot `S` rejects first: `responded_signers.insert(S)` → true → `total_weight_rejected += w_S`.
- If `S` later accepts the same block (a legitimate re-evaluation per the documented state machine): `gathered_signatures.contains_key(S)` is false → `total_weight_approved += w_S` is *also* executed.

`total_weight_rejected` is never decremented anywhere in this file — there is no code path that removes a slot's weight from `total_weight_rejected` when that slot subsequently accepts. The two ledgers, which should be a partition of signer weight (a signer's current opinion is either "reject" or "accept", not both), permanently diverge: `w_S` is now counted in both buckets simultaneously, for the lifetime of this `BlockStatus` entry.

This is the same bug class as the referenced report: `pendingLockedBalance_b` in `PartyBFacetImpl.sol` was decremented on one path (`filledLockedValues`) but never brought back into sync with the true outstanding commitment on the other side, silently inflating a value that downstream logic (`partyBAvailableForQuote`) treats as ground truth. Here, `total_weight_rejected` is incremented on one path and never reconciled with the signer's later, superseding vote, silently inflating a value that `SigningCoordinator::gather_signatures` treats as ground truth for the reject-threshold decision.

### Impact Explanation
`SigningCoordinator::gather_signatures` checks the (now permanently poisoned) `total_weight_rejected` *before* checking `total_weight_approved`: [3](#0-2) 

Consider signers whose combined weight is just under the 30% blocking minority who reject a block first (e.g. due to a transient reason such as `check_block_against_signer_db_state` momentarily failing), then legitimately re-evaluate and accept once conditions clear (this exact flow is the documented `should_reevaluate_reject_reason` / re-proposal path on the signer side). Their weight sticks in `total_weight_rejected` forever while also correctly accumulating in `total_weight_approved`. Once enough of these switches accumulate, `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can become true purely from stale rejection weight that no longer reflects any signer's actual current vote, at the same moment `total_weight_approved >= weight_threshold` is also true from real, current votes. Because the reject-check is evaluated first, the coordinator returns `Err(SignersRejected)` and the miner discards a block that has genuinely reached the 70% signing threshold from the live signer set. This wedges block production: a valid, sufficiently-signed block is thrown away because of an accounting artifact, not because the signer set actually rejects it — a liveness break of the "aggregated-weight vs verified-accepts" equality the coordinator is supposed to enforce.

### Likelihood Explanation
No majority collusion, no signer keys, and no StackerDB transport tampering are required — this is triggered purely by the ordinary, protocol-sanctioned behavior of one or more single signers changing their vote on the identical block hash after their initial rejection reason becomes stale (a scenario the signer's own state machine explicitly supports and that can happen during normal operation whenever a rejection reason is re-evaluable, e.g., a transient chain-state mismatch that resolves before the pre-commit/accept threshold is reached).

### Recommendation
Maintain a single per-slot "current vote" ledger instead of two independently-incremented counters, or explicitly subtract `signer_entry.weight` from `total_weight_rejected` (and clear any associated `failed_txids` weight) whenever a slot that had previously been recorded as rejecting is now recorded in `gathered_signatures`, and symmetrically subtract from `total_weight_approved` if a previously-accepting slot later rejects. Recompute `total_weight_approved`/`total_weight_rejected` from the authoritative per-slot vote state rather than accumulating them as append-only counters.

### Proof of Concept
1. Node starts `SigningCoordinator::gather_signatures` for a proposed block, with `weight_threshold` = 70% and blocking minority just under 30%.
2. Signer slot `S` (weight ~29% of total) sends `BlockResponse::Rejected` for the block's `signer_signature_hash` (e.g. because its local `check_block_against_signer_db_state` transiently fails). `StackerDBListener` records: `responded_signers.insert(S)` → true, `total_weight_rejected += w_S` (≈29%).
3. Shortly after, `S`'s local chainstate re-check clears (matching the documented `should_reevaluate_reject_reason` re-evaluation path), and `S` legitimately sends `BlockResponse::Accepted` for the *same* `signer_signature_hash`.
4. `StackerDBListener`'s `Accepted` arm checks `gathered_signatures.contains_key(&S)` → false (S never appeared there) → `total_weight_approved += w_S`. `responded_signers.insert(S)` is a no-op (already present) but this has no bearing on `total_weight_rejected`, which is never touched in this arm.
5. As the remaining honest signers (≥71% weight, enough to reach `weight_threshold`) send `Accepted`, `total_weight_approved` legitimately reaches ≥70%.
6. Meanwhile `total_weight_rejected` still holds `S`'s stale ~29% forever. If any other signer, even one with a small fraction of weight, also rejects-then-accepts (or if `S`'s ~29% alone is close enough to the 30% cutoff combined with normal small-scale reject noise from slow/late signers), `total_weight_rejected.saturating_add(weight_threshold) > total_weight` becomes true.
7. `SigningCoordinator::gather_signatures`'s reject-check runs first and returns `Err(SignersRejected{...})`, discarding a block that has already legitimately reached the 70% acceptance threshold from the live signer set — confirmed via the code at `stacks-node/src/nakamoto_node/signer_coordinator.rs` lines 509-545 and the vote-recording code at `stacks-node/src/nakamoto_node/stackerdb_listener.rs` lines 443-465 and 515-518.
