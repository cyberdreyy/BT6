### Title
Unrestricted `create()` lets anyone squat a victim's derived lockup address with attacker-chosen terms - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the lockup account name purely from `hex::encode(&env::sha256(owner_account_id)[..20])` and imposes no restriction on who may call it or what terms they submit for that `owner_account_id` [1](#0-0) . Any unprivileged account can pre-create the deterministic lockup address for a victim owner with attacker-chosen `vesting_schedule`, `release_duration`, and `whitelist_account_id`, permanently occupying the address the real grantor was going to use.

### Finding Description
Binding claimed to hold: `lockup_account_id(owner) → terms chosen by owner's real grantor`. The code never enforces this - `create` is `#[payable]` with the only gate being `env::attached_deposit() >= MIN_ATTACHED_BALANCE` [2](#0-1) ; there is no `assert_called_by_foundation`, no owner-signature check, and no reservation/registry of which owners already have (or are entitled to) a lockup before the promise executes.

The account name is 100% deterministic from `owner_account_id` alone: `format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id())` [3](#0-2) . Since `owner_account_id` is an attacker-supplied argument with no proof of relationship to that identity, the attacker can call `create()` themselves, naming the real victim as `owner_account_id`, and picking `vesting_schedule`, `release_duration`, `whitelist_account_id` of their choice, funding it with only `MIN_ATTACHED_BALANCE`.

All the account-creation actions (`create_account`, `deploy_contract`, `transfer`, `function_call("new", ...)`) are chained on a single `Promise` (not `.then()`-separated), so they execute as one batch of actions on one receipt [4](#0-3) . Per NEAR's action-execution model, a later action failing in that batch does not roll back state already applied by earlier successful actions in the same receipt. This means:
- If the attacker's chosen `new()` args are internally valid, the batch succeeds fully: a fully initialized lockup with attacker-chosen owner/vesting/whitelist now sits at the victim's canonical derived address, funded only by the attacker's minimal deposit.
- If `new()` panics (e.g., a foundation/vesting-schedule assertion fails), `create_account`, `deploy_contract`, and `transfer` may have already committed, but `is_promise_success()` in `on_lockup_create` [5](#0-4)  sees failure and refunds `attached_deposit` to the attacker from the factory's own balance (`Promise::new(predecessor_account_id).transfer(attached_deposit.0)`) [6](#0-5)  - the attacker gets their deposit back while the account name remains permanently occupied by an uninitialized, keyless, un-deletable contract, since no full access key was ever added.

Either way, when the legitimate grantor later calls `create()` for the same real `owner_account_id`, the batch's `create_account` action fails immediately (account already exists), so the real grant is refused at the address the protocol treats as canonical for that owner - the invariant "the lockup at owner's derived address carries terms the owner's real grantor chose" is broken by construction. Existing guards (`assert_self`, `is_promise_success`, `MIN_ATTACHED_BALANCE`) do nothing to prevent the initial squat because none of them check caller-owner relationship or pre-existence before deployment is attempted.

### Impact Explanation
Two concrete outcomes, both matching listed Critical categories:
1. **"A lockup deployed with parameters its rightful creator never chose"** - the attacker-funded, attacker-parameterized lockup at the victim's canonical address can carry a malicious `staking_pool_whitelist_account_id` (pointing to an attacker-controlled fake whitelist/pool) or malicious vesting/release terms, and the real grant for that owner can never be deployed at the expected address afterward.
2. **"Funds permanently frozen"** - in the failed-`new()` variant, the address is deployed-but-uninitialized with no access key, permanently blocking any future legitimate lockup for that owner at their canonical address, while the attacker recovers their deposit cost-free via the callback refund.

Blast radius: any owner_account_id whose real lockup has not yet been created is squattable by any unprivileged account, repeatable across every future grantee before their grant is issued.

### Likelihood Explanation
Preconditions: attacker only needs `MIN_ATTACHED_BALANCE` (3.5 NEAR) and knowledge of the intended owner's account ID (typically public/predictable, e.g., an employee's near account before their token grant is issued). No privileged role, multisig, or foundation access is required - fully within the defined unprivileged attacker capability. Cost is minimal and, in the failing-callback variant, largely recoverable.

### Recommendation
Restrict `create()` (or at least require some proof of authorization, such as `assert_called_by_foundation`/an allowlist of permitted grantors, or a commit-reveal binding the caller to the intended owner) before deploying to the deterministic address; alternatively, check `env::account_balance()` at the target account / query existing state before attempting `create_account`, and consider requiring the owner or a trusted authority to co-sign/pre-register before a lockup can be created for them.

### Proof of Concept
`cargo test` (in `lockup-factory/src/lib.rs` test module), modeled on `test_create_lockup_rollback`:
1. Set predecessor to `attacker`, `attached_deposit = MIN_ATTACHED_BALANCE`, call `contract.create(victim_owner_id, lockup_duration, None, Some(malicious_vesting_schedule_or_hash), None, Some(attacker_whitelist_account_id))`.
2. Simulate the deployment succeeding (`PromiseResult::Successful`), call `on_lockup_create` and assert it returns `true` - the squat succeeded with attacker-chosen `staking_pool_whitelist_account_id`.
3. Then, with predecessor set to `real_grantor`, `attached_deposit = real_amount`, call `contract.create(victim_owner_id, real_duration, ..., real_vesting_schedule, ..., real_whitelist)` again for the same `victim_owner_id`; because `lockup_account_id` is identical (same hash of owner id), assert that the subsequent deployment's `create_account` action would fail (simulate via `PromiseResult::Failed` in `on_lockup_create`) and that the deposit is refunded to `real_grantor`, proving the legitimate lockup for `victim_owner_id` never gets created with the real grantor's chosen terms - i.e. `lockup_account(victim_owner_id).vesting_schedule == malicious_vesting_schedule ≠ real_vesting_schedule`, violating the claimed binding.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
