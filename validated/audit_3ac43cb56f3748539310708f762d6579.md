### Title
Signer equivocation: v1 tenure-change duplicate-block check uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, allowing a signer to sign two conflicting blocks in the same tenure - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
The v1 signer's `validate_tenure_change_payload` duplicate-block guard queries only globally-accepted blocks, while the v2 equivalent (and the later pre-commit-time guard) treat "locally accepted" (signed) blocks as equally binding. This canonicalization drift lets a locally-signed-but-not-yet-globally-accepted tenure-start block fail to be recognized as a conflict at proposal time. If the pre-commit-time backstop's node-lookup also cannot see the earlier block (because it was never pushed to the node, which only happens after the whole signer set signs), the signer ends up placing a second, conflicting signature at the same height/tenure — an equivocation.

### Finding Description
Two logically-equivalent predicates for "has this signer already committed to a block in this tenure?" are evaluated with different underlying data across code paths, exactly the kind of canonicalization drift the external report describes for `@fastify/middie` (auth middleware and router disagreeing on path normalization → an authorization gate is skipped while the protected route still resolves).

- v1's tenure-change duplicate check: [1](#0-0) 
uses `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, which only matches rows in `BlockState::GloballyAccepted`: [2](#0-1) 

- v2's equivalent check instead uses `get_last_signed_block`, which matches *locally or globally* accepted blocks: [3](#0-2) 

- The docs explicitly flag this asymmetry and note the check "never runs again": [4](#0-3) 

- v2 has a regression test proving the bug class exists and was fixed for v2 (i.e., the maintainers already recognize a locally-accepted-only block was previously missed by `get_last_globally_accepted_block`): [5](#0-4) 
No equivalent regression test or fix exists for v1's `validate_tenure_change_payload`, which still calls `get_last_globally_accepted_block` at v1.rs:505-506.

Because the duplicate check "never runs again" after proposal time, the only backstop is the pre-commit-time own-tenure-conflict check in `handle_block_pre_commit`: [6](#0-5) 
This backstop only refuses to sign if `stacks_client.get_tenure_tip` reports the node's canonical tip for that tenure already at or above the proposed height. A block this signer only *locally* accepted (its own `signed_self`, not yet `signed_group`) is not pushed to the node — global acceptance/broadcast to the node happens only once the 70% group threshold is reached — so `get_tenure_tip` can legitimately report a tip below the conflicting block's height, and the backstop does not fire.

### Impact Explanation
This breaks the core safety invariant that a signer must never place a signature over two conflicting blocks in the same tenure (equivocation guard). Concretely:
1. Signer signs tenure-start block A in tenure T (locally accepted, `signed_self` set, but not yet globally accepted/pushed to node).
2. Miner (or a colluding/faulty proposer) re-proposes a different tenure-start block B for the same tenure T (e.g., different transactions/height-equal chain_length).
3. v1's `check_proposal` → `validate_tenure_change_payload` checks `get_last_globally_accepted_block(T)`, which returns `None` (A is only locally accepted), so the `DuplicateBlockFound` rejection is skipped and B is accepted for validation.
4. B accumulates pre-commit weight; at threshold, `handle_block_pre_commit`'s conflict check runs `get_signed_conflicts` (which *does* find A, since it checks `signed_self`/`signed_group` in any tenure) but only refuses if `get_tenure_tip` shows the node's tip at/above B's height — which it won't, since A was never pushed to the node.
5. The signer signs B, producing two conflicting signed blocks (A and B) from the same signer at the same tenure/height — an equivocation that a one-slot miner (with ordinary gossip, no majority of signers needed) can trigger.

This is a Critical-class break under the stated impact categories: a signer signing a conflicting block.

### Likelihood Explanation
No majority of signers, no other signer's key, and no privileged access is required. The only actors needed are: (a) a miner proposing two competing tenure-start blocks for the same tenure (ordinary, adversary-controlled behavior), and (b) normal gossip/pre-commit timing so that block A never reaches the 70% group threshold before B's proposal arrives — a realistic race that already exists in the pre-commit/threshold design (the whole point of the pre-commit backstop in section 5 is to handle exactly this "signed a different block before threshold" race). Because v1 lacks the fix that v2 already received, any deployment still running the v1 signer protocol is exposed to this timing window.

### Recommendation
Change v1's `validate_tenure_change_payload` (stacks-signer/src/chainstate/v1.rs, around lines 505-518) to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, mirroring the v2 fix, so both code paths agree on the same equality predicate: "has this signer already signed (locally or globally accepted) a block in this tenure?" Add a v1 regression test analogous to `check_tenure_change_rejects_when_locally_accepted_block_exists` in `stacks-signer/src/chainstate/tests/v2.rs` to lock in the fix.

### Proof of Concept
1. Run a v1-protocol signer; have it locally accept (sign) a tenure-start block A for tenure `T` (e.g., via `mark_locally_accepted`), without letting it be pushed to the node/reach global acceptance.
2. Propose a second, distinct tenure-start block B also for tenure `T` (same `consensus_hash`, differing tx set/timestamp so it hashes differently).
3. Call `SortitionsView::check_proposal` (v1) on B — as in `check_tenure_change_rejects_when_locally_accepted_block_exists` but on the v1 code path — and observe it returns `Ok(())` instead of `RejectReason::DuplicateBlockFound`, because `get_last_globally_accepted_block(T)` returns `None` for A.
4. Drive B through validation and pre-commit accumulation to threshold while the node's `get_tenure_tip(T)` response for the mocked `StacksClient` still reports a height below B's `chain_length` (simulating A never having been pushed to the node); observe `handle_block_pre_commit` signs B via `mark_locally_accepted`, yielding two signatures (over A and B) from the same signer for tenure `T`.
