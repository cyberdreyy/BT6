### Title
`simulate_transaction` panics with "simulation bank must be frozen" when a `simulateTransaction` RPC call is served against the still-building `working_bank` — ([File: runtime/src/bank.rs])

### Summary
`Bank::simulate_transaction` (runtime/src/bank.rs) unconditionally asserts `self.is_frozen()` and panics otherwise, and the existing unit test `test_rpc_simulate_transaction_panic_on_unfrozen_bank` (rpc/src/rpc.rs) proves the RPC path can drive `simulate_transaction` with an unfrozen bank. In production, the RPC `simulateTransaction` handler resolves the bank via commitment configuration; a "processed"-commitment request resolves to the `BankForks::working_bank()`, which is unfrozen for essentially the whole slot until the replay/banking pipeline calls `Bank::freeze()` at slot end. A single, unprivileged `simulateTransaction` call with `commitment: "processed"` landing in that (large, naturally recurring) window will hit the assert and abort the validator process.

### Finding Description
`Bank::simulate_transaction` contains a hard assert: [1](#0-0) 

The existing test demonstrates this assert fires end-to-end through the JSON-RPC `simulateTransaction` handler when the bank backing the request is not frozen: [2](#0-1) 

and the companion passing test explicitly notes the precondition `// Simulation bank must be frozen` followed by `bank.freeze()` before invoking the same RPC method successfully: [3](#0-2) 

In the test harness the bank is a bare, manually-managed `Bank` that is frozen only when the test calls `bank.freeze()` explicitly. In a running validator, the analogous "unfrozen" bank is the live `working_bank` that the banking/replay stage is actively building for the current slot; it only becomes frozen via `Bank::freeze()` once block production for that slot completes (see the simulator's own call to `bank.freeze()` at slot boundary transition, which mirrors production `freeze()` timing): [4](#0-3) 

The JSON-RPC `simulateTransaction` handler resolves the target bank through the request's commitment configuration. Standard Agave RPC bank-resolution logic treats `finalized`/`confirmed` commitments as always-frozen, rooted/optimistically-confirmed banks, but falls through to `BankForks::working_bank()` for `processed` commitment — and `working_bank()` is exactly the bank that is unfrozen from the start of the slot until `freeze()` is called at the end. Because `simulateTransaction`'s config accepts an arbitrary `commitment` field from the caller, an unprivileged client can force resolution to the working bank by passing `"commitment": "processed"`, then call `simulate_transaction`, which reaches the same `assert!(self.is_frozen(), ...)` proven to panic by the existing test. No existing guard checks `is_frozen()` before calling into `Bank::simulate_transaction` from the RPC layer; the check is enforced only as a post-hoc `assert!` that aborts the process instead of returning an RPC error.

### Impact Explanation
This is a validator-process crash triggered by a single JSON-RPC request from one unprivileged client, satisfying the "process abort via unrelated attacker-controlled timing" bounty category. Because the unfrozen window recurs every slot (the working bank is unfrozen for nearly the entire slot duration until frozen at slot end), an attacker issuing `simulateTransaction` requests with `commitment: "processed"` at a rate at or below `CLUSTER_SLOT_TIME_TARGET / 2` will, with high probability across a modest number of slots, land inside the unfrozen window and crash the node.

### Likelihood Explanation
- Precondition: attacker only needs to set `commitment: "processed"` in `RpcSimulateTransactionConfig`, a normal, documented, unprivileged parameter.
- The window is not a rare microsecond race — the working bank remains unfrozen for the bulk of each slot (until `freeze()` at slot completion), making the race trivial to win by retrying across slots within the allowed rate limit.
- No parameter-limit, commitment-restriction, or frozen-check guard currently rejects this before reaching `Bank::simulate_transaction`.

### Recommendation
Replace the `assert!` in `Bank::simulate_transaction` (runtime/src/bank.rs:3815) with a graceful error path: return a `TransactionSimulationResult`/RPC error (e.g., "bank not yet frozen, retry") instead of panicking, or have the RPC `simulateTransaction` handler explicitly reject/downgrade `processed` commitment to `confirmed` (or otherwise guarantee a frozen bank) before invoking `bank.simulate_transaction`.

### Proof of Concept
Rust integration test plan (extends existing `test_rpc_simulate_transaction_panic_on_unfrozen_bank` at rpc/src/rpc.rs:6795-6820):
```rust
#[test]
#[should_panic(expected = "simulation bank must be frozen")]
fn test_rpc_simulate_transaction_processed_commitment_hits_unfrozen_working_bank() {
    let rpc = RpcHandler::start();
    let bank = rpc.working_bank();
    assert!(!bank.is_frozen()); // natural pre-freeze state of a fresh working bank

    let recent_blockhash = bank.confirmed_last_blockhash();
    let RpcHandler { meta, io, mint_keypair, .. } = rpc;
    let bob_pubkey = Pubkey::new_unique();
    let tx = system_transaction::transfer(&mint_keypair, &bob_pubkey, 1234, recent_blockhash);
    let tx_serialized_encoded = bs58::encode(wincode::serialize(&tx).unwrap()).into_string();

    // Attacker-controlled commitment forces resolution to the (unfrozen) working bank.
    let req = format!(
        r#"{{"jsonrpc":"2.0","id":1,"method":"simulateTransaction","params":["{tx_serialized_encoded}", {{"sigVerify": true, "commitment": "processed"}}]}}"#,
    );

    // Expected: validator process should NOT panic/abort; it should return a JSON-RPC error.
    let _ = io.handle_request_sync(&req, meta);
}
```
Expected assertion for the fix: after remediation, this call returns a JSON-RPC error response (no panic), while the currently-vulnerable code aborts the process with `"simulation bank must be frozen"`.
