### Title
Unfunded instant-withdraw receipts are paid at par, letting a user drain underlying reserved for other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` mints a strategy-token receipt and increments `instantWithdrawsRequests[_user]` plus the unfunded counter `pendingInstantWithdraws`, but `claimInstantWithdrawRequest` pays out the *entire* aggregate `instantWithdrawsRequests[_user]` from the strategy's underlying balance without ever checking that the request was actually funded. Funding is tracked only by `pendingInstantWithdraws`, which is decremented in `collectInstantWithdrawFunds` when the CDO forwards borrower funds — yet the claim path never reads that counter. This is the memory-corruption analog of CVE-2019-8782: stale/uninitialized state (a receipt that exists but has no backing) is treated as valid payable memory, giving arbitrary extraction instead of arbitrary code execution.

### Finding Description
In `IdleCreditVault.sol`:

- `requestInstantWithdraw` burns CDO strategy tokens, mints the receipt to the user, and does `instantWithdrawsRequests[_user] += _amount`, `instantWithdrawsRequestsByEpoch[_user][epoch] += _amount`, `pendingInstantWithdraws += _amount` (lines 356-375). Nothing requires the request to be funded before a claim.
- `collectInstantWithdrawFunds` is what actually makes a receipt funded: it does `pendingInstantWithdraws -= _amount` and pulls underlying from the CDO (lines 398-403). Until the CDO calls it (at `getInstantWithdrawFunds` during the next `startEpoch`), the receipt is pure accounting with no underlying behind it.
- `claimInstantWithdrawRequest` (lines 380-393) then does:
  - `amount = instantWithdrawsRequests[_user]` — the aggregate across epochs, not per-epoch,
  - `_burn(_user, amount)`,
  - `_transferFundedClaim(_user, amount)` which only guards `defaultRecoveryReserve` (lines 897-907) and otherwise transfers whatever `underlyingToken.balanceOf(this)` holds.

Compare with the normal withdraw path: `_claimFundedWithdrawRequest` enforces `epochNumber <= lastWithdrawRequest[_user]` → revert (line 326), i.e., a request cannot be claimed in the epoch it was created. The instant path has no equivalent gating — no epoch check, no `pendingInstantWithdraws` check, no per-epoch funded tracking. The only thing standing between an unfunded receipt and the strategy's underlying is the assumption that the strategy never holds underlying it shouldn't pay out — an assumption that is false whenever funded normal receipts, funded instant receipts of other users, repaid borrower funds awaiting `stopEpoch`, or prefunded instant reserves sit in the contract.

Concretely: during a buffer phase or between `stopEpoch` funding and user claims, the strategy holds underlying backing `pendingWithdraws` claimants and prior funded instant receipts. An attacker (any KYC-passed lender holding tranche tokens) calls the CDO's instant-withdraw request path (`requestWithdraw` → `creditVault.requestInstantWithdraw` when the APR delta triggers, or when instant mode is enabled), then immediately calls `claimInstantWithdrawRequest`. The strategy pays `instantWithdrawsRequests[attacker]` at par from the common underlying pool, stealing funds earmarked for other users' funded receipts. Attacker profit is bounded only by the strategy's spendable underlying balance at that moment.

### Impact Explanation
Direct theft of underlying belonging to other withdraw claimants. Every wei held by `IdleCreditVault` to satisfy funded `pendingWithdraws` / funded instant receipts / repaid-but-undistributed funds can be taken by an attacker whose own receipt is entirely unfunded, breaking the "one receipt, one funded payout" invariant. Loss is quantified as `min(attackerReceipt, strategyUnderlyingBalance - defaultRecoveryReserve)`; in a pool where borrowers just repaid for `stopEpoch`, that can be the full epoch withdrawal pool.

### Likelihood Explanation
Requires only an unprivileged tranche holder able to trigger the instant-withdraw path (APR drop ≥ `instantWithdrawAprDelta`, or instant mode enabled) while the strategy holds positive underlying. No privileged role, no oracle manipulation, no donation needed. The missing `pendingInstantWithdraws`/epoch check in `claimInstantWithdrawRequest` is visible by direct comparison with `_claimFundedWithdrawRequest`'s epoch gate; no existing guard (skim, `_transferFundedClaim` reserve check, `NotAllowed` on double post-default requests) covers pre-funding claims. One caveat I could not fully rule out within available context: the CDO-side wrapper `IdleCDOEpochVariant.claimInstantWithdrawRequest` may add timing gating (e.g., `instantWithdrawDelay` or a per-epoch funding flag); even if it does, the strategy-level invariant remains broken and any path that reaches the strategy claim with a nonzero balance pays unfunded receipts.

### Recommendation
Gate instant claims on actual funding: track per-epoch funded instant amounts (or require `instantWithdrawsRequests[_user] <= fundedInstantClaims`), and revert in `claimInstantWithdrawRequest` when `pendingInstantWithdraws` still covers the user's unfunded remainder. Alternatively, only clear `instantWithdrawsRequestsByEpoch` for epochs whose `collectInstantWithdrawFunds` has executed, mirroring the `epochNumber <= lastWithdrawRequest` gate used for normal receipts. Fuzz test: request instant withdraw while strategy holds funded-claim underlying, then claim before `collectInstantWithdrawFunds`.

### Proof of Concept
Foundry fork outline (extends `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// 1. Seed pool: userA deposits AA, epoch 0 runs and stops normally with borrower repay,
//    so strategy holds underlying for pendingWithdraws/funded instant claims.
// 2. Attacker (KYC'd lender) deposits AA, waits for epoch where
//    lastEpochApr > unscaledApr + instantWithdrawAprDelta (or instant mode enabled).
// 3. attacker: cdoEpoch.requestWithdraw(trancheBal, AAtranche)
//    -> creditVault.requestInstantWithdraw mints receipt, pendingInstantWithdraws += amt.
//    No collectInstantWithdrawFunds has run for this epoch.
// 4. attacker: cdoEpoch.claimInstantWithdrawRequest()
//    -> strategy burns receipt and transfers amt from underlying balance
//       that belongs to userA's funded pendingWithdraw receipt.
// 5. assert underlying.balanceOf(attacker) increased by amt while
//    creditVault.pendingInstantWithdraws() still == amt (unfunded),
//    and userA's later claim reverts/underpays on insufficient balance.
```

If step 4 reverts only because of a CDO-side timing guard not visible in the indexed snippet, the same theft is reachable one epoch later: the attacker's receipt persists in `instantWithdrawsRequests` and `claimInstantWithdrawRequest` pays the aggregate including epochs the strategy never funded, whenever any underlying balance exists.
