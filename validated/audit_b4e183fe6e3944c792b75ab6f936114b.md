### Title
Rate limiter is trivially bypassable for any withdrawal/borrow by wrapping it in a self-issued flashloan flag — ([File: programs/marginfi/src/utils/general.rs])

### Finding Description
`record_withdrawal_outflow` skips both the bank-level and group-level rate limiter entirely whenever `should_skip_rate_limit(marginfi_account.account_flags)` is true: [1](#0-0) 

`should_skip_rate_limit` returns `true` if any of `ACCOUNT_IN_FLASHLOAN`, `ACCOUNT_IN_RECEIVERSHIP`, or `ACCOUNT_IN_DELEVERAGE` is set: [2](#0-1) 

`ACCOUNT_IN_FLASHLOAN` is set by the fully permissionless `lending_account_start_flashloan` instruction, gated only by `has_one = authority` (i.e. it only requires the account owner's own signature, no admin/governance role) and a sysvar check that an `end_flashloan` instruction for the same account exists later in the transaction: [3](#0-2) 

Between `start_flashloan` and `end_flashloan`, the account's `ACCOUNT_IN_FLASHLOAN` flag remains set for the whole transaction, so any `lending_account_withdraw` or `borrow` call inside that window goes through `record_withdrawal_outflow` with the flag set, skipping `bank.rate_limiter.try_record_outflow` and the group hourly/daily checks and event emission entirely, regardless of `native_amount`: [4](#0-3) 

`lending_account_end_flashloan` unsets the flag and only performs a solvency/health check (`check_account_init_health`) — it does **not** verify that any borrowed/withdrawn funds were actually returned or that net outflow is zero: [5](#0-4) 

The doc comment on `record_withdrawal_outflow` states the intent is to skip rate limiting because flashloans "net" to zero outflow, but nothing in the code enforces that netting — the only requirement is that the account remains healthy at the end of the transaction. A sufficiently over-collateralized user can therefore withdraw or borrow an arbitrary `native_amount` (any size, as long as it doesn't breach their own health factor) inside a `start_flashloan`/`end_flashloan` wrapper and simply never repay it, permanently moving funds out of the bank's liquidity vault while completely bypassing the configured bank-level and group-level rate limiter caps.

### Impact Explanation
The rate limiter exists as a circuit-breaker/risk-control mechanism to cap outflow velocity per bank and per group (hourly/daily), independent of a user's own solvency. Any unprivileged, solvent account holder can defeat this control entirely on ordinary withdraw/borrow calls simply by issuing them inside a self-controlled `start_flashloan`/`end_flashloan` pair — no special privilege, oracle manipulation, or third-party account is required. This undermines the "rate limiter cannot be trivially bypassed by an unprivileged flow selection" invariant and produces durable, unbounded (up to the user's own collateral) outflow that is not captured by `RateLimitFlowEvent` or the bank/group counters, defeating the entire purpose of the feature.

### Likelihood Explanation
Fully feasible and repeatable by any account owner with sufficient collateral: no admin action, oracle control, or race condition is needed — only a normal signed transaction containing `lending_account_start_flashloan`, the withdraw/borrow instruction(s), and `lending_account_end_flashloan`. This can be repeated every transaction/block, by every user, to permanently drain amounts beyond configured caps.

### Recommendation
Do not treat "inside a flashloan" as unconditionally rate-limit-exempt. Either (a) track net outflow across the flashloan span and apply the rate limiter to the net amount at `lending_account_end_flashloan` (failing the transaction if net outflow exceeds capacity), or (b) apply the rate limiter to every withdraw/borrow unconditionally and instead give flashloan flows credit for offsetting inflows recorded within the same transaction, rather than skipping recording altogether based solely on the flag.

### Proof of Concept
Rust unit/integration test plan:
1. Configure a bank with `bank.rate_limiter` (hourly/daily) enabled with a small cap (e.g. 1000 native units) and a group with `group.rate_limiter` enabled.
2. Fund a test user's marginfi account with collateral sufficiently larger than the rate limit cap (e.g. deposit 1,000,000 units of an unrelated highly-weighted asset) so post-withdrawal health remains positive.
3. Build a transaction: `lending_account_start_flashloan` → `lending_account_withdraw(native_amount = 100,000)` (100x the bank's rate limit) → `lending_account_end_flashloan` (no repay instruction in between).
4. Assert the transaction succeeds (no `BankHourlyRateLimitExceeded`/`GroupHourlyRateLimitExceeded` error).
5. Assert `bank.rate_limiter.hourly.cur_window_outflow` is unchanged (still 0) after the transaction, and no `RateLimitFlowEvent` was emitted, despite the vault balance decreasing by 100,000 and the withdrawal persisting after `end_flashloan`.
6. Contrast with a directly identical `lending_account_withdraw` call outside of a flashloan wrapper, which should fail with `BankHourlyRateLimitExceeded`, confirming the rate limiter is only bypassed via the flashloan flag path.

/// Checks if rate limiting should be skipped based on account flags.
/// Returns true for flashloan, liquidation, and deleverage operations.
pub fn should_skip_rate_limit(account_flags: u64) -> bool {
    (account_flags & ACCOUNT_IN_FLASHLOAN) != 0
        || (account_flags & ACCOUNT_IN_RECEIVERSHIP) != 0
        || (account_flags & ACCOUNT_IN_DELEVERAGE) != 0
}

pub fn lending_account_start_flashloan(
    ctx: Context<LendingAccountStartFlashloan>,
    end_index: u64,
) -> MarginfiResult<()> {
    check_flashloan_can_start(
        &ctx.accounts.marginfi_account,
        &ctx.accounts.ixs_sysvar,
