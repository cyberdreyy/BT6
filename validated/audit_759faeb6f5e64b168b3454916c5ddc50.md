### Title
Post-default instant withdraw receipts are minted and paid at par, stealing unfinalized recovery/funded-claim liquidity - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` contains an explicit post-default branch (lines 247–257) that routes new requests into `postDefaultRequests` and blocks them while any receipt is outstanding. `requestInstantWithdraw` (lines 356–375) has no `defaultRecoveryFinalized` handling at all: after default finalization it still burns the CDO's strategy tokens, mints a 1:1 receipt to the user, and increments `instantWithdrawsRequests`/`pendingInstantWithdraws`. `claimInstantWithdrawRequest` then pays `instantWithdrawsRequests[_user]` in full via `_transferFundedClaim`, which only protects `defaultRecoveryReserve` — not the residual vault balance backing already-funded-but-unclaimed normal withdraw receipts.

### Finding Description
The bug class (an attacker-influenced write to a slot that accounting assumes is unreachable, analogous to an out-of-bounds/duplicate-entry write through a "sorted" lookup) maps here to an attacker-influenced write into the instant-withdraw receipt bucket in a state (`defaultRecoveryFinalized == true`) where the accounting model assumes no new instant receipts can be created:

- `requestWithdraw` was hardened: post-default requests revert if `_hasWithdrawRequest(_user) || instantWithdrawsRequests[_user] != 0 || postDefaultRequests[_user] != 0`, and the minted amount goes to `postDefaultRequests`, paid from `defaultRecoveryReserve` via `_transferDefaultRecovery`.
- `requestInstantWithdraw` performs `_ensureDefaultRecoveryInitialized()` only, then unconditionally mints a receipt and bumps `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `pendingInstantWithdraws`. Note `epochNumber` is frozen post-default, so `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` is also written — creating a fresh "default-epoch" receipt after finalization.
- `claimInstantWithdrawRequest`: if `defaultInstantWithdrawsFinalized`, `_claimDefaultedInstantWithdrawRequest` runs first — and the attacker's new receipt sits at `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, so it is paid `claimBasis * defaultRecoveryPrice / 1e18` out of `defaultRecoveryReserve` while also decrementing `instantWithdrawClaimsByEpoch[defaultEpoch]` (underflow-protected arithmetic on an epoch aggregate that honest claimants still need is not checked; subtraction of a larger attacker basis can revert or, if it succeeds on the `pendingInstantWithdraws` clamp path, corrupts the accounting). Any remainder is then paid at par by `_transferFundedClaim`, which only verifies `balance - reserve >= amount`.

Concretely, two theft modes exist:
1. If `defaultInstantWithdrawsFinalized` is true, the attacker's post-default receipt is treated as a default-epoch claim and pays out `amount * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve`, diluting every honest defaulted-epoch claimant (the reserve was sized in `finalizeDefaultRecovery` to exactly cover `totalBasis * recoveryPrice`; a new basis added afterward is not funded).
2. Regardless of `defaultInstantWithdrawsFinalized`, `_transferFundedClaim` will pay the request at par from any vault balance above `defaultRecoveryReserve` — i.e., underlyings that were collected via `collectWithdrawFunds`/`collectInstantWithdrawFunds` to back older funded receipts that users have not yet claimed.

### Impact Explanation
Direct theft / insolvency of unclaimed claims. After a borrower default is finalized (`defaultRecoveryFinalized == true`), an attacker holding tranche tokens (or KYC'd lender) calls the CDO's instant-withdraw request path, receives a minted receipt, and immediately calls `claimInstantWithdrawRequest`. The payout comes either from `defaultRecoveryReserve` (diluting honest default claimants — every wei stolen is a wei an honest defaulted-epoch receipt holder cannot recover) or from the funded-claim float (stealing pending payouts of users who requested withdrawals before the default and haven't claimed). Loss is bounded by the attacker's tranche position, which can be arbitrarily large; the reserve/float drained is up to `min(attackerBasis, reserve + funded float)`.

### Likelihood Explanation
Requirements: `allowInstantWithdraw` enabled, a defaulted-then-finalized vault, and the CDO's instant-withdraw entry point reachable post-default (the strategy-side code itself does not gate on `defaultRecoveryFinalized`; `claimInstantWithdrawRequest` is explicitly callable — only `!allowInstantWithdraw` is checked in `IdleCDOEpochVariant.claimInstantWithdrawRequest`, and the CDO-side `claimInstantWithdrawRequest` at `IdleCDOEpochVariant.sol:975` is still externally callable). Whether `IdleCDOEpochVariant.requestInstantWithdraw` additionally blocks requests while `defaulted()` could not be fully confirmed within this analysis — if it does not, the exploit is a two-transaction sequence executable by any tranche holder. The missing symmetric guard in `requestInstantWithdraw` (present in `requestWithdraw`) strongly suggests this path was not considered post-default.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is true, either revert or route the request into `postDefaultRequests` semantics (haircut-at-request, paid from `defaultRecoveryReserve`), and enforce the same "no outstanding receipts" precondition. Additionally, `claimInstantWithdrawRequest` should not let `_claimDefaultedInstantWithdrawRequest` clear a basis at `defaultRecoveryEpoch` that was created after finalization — snapshot the epoch or track pre/post-finalization instant bases separately.

### Proof of Concept
Foundry fork PoC outline (mirroring `test/foundry/IdleCreditVault.t.sol` harness):
1. Deploy vault/CDO with `allowInstantWithdraw = true`; users deposit AA/BB; run epoch 0; borrower defaults; manager calls the default path so `finalizeDefaultRecovery` stores `defaultRecoveryPrice` < 1 and `defaultRecoveryReserve` = R, with `defaultInstantWithdrawsFinalized` true (leave an instant request unfunded at stop).
2. Attacker (fresh KYC'd lender holding tranche tokens minted pre-default, or receiving them) calls `cdoEpoch.requestInstantWithdraw(amount)` post-finalization. Observe `instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch] == amount` — a default-epoch receipt created after the recovery price was fixed.
3. Attacker calls `cdoEpoch.claimInstantWithdrawRequest()`: receives `amount * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve`.
4. Assert `defaultRecoveryReserve` decreases below `sum(honestBasis) * defaultRecoveryPrice / 1e18`, i.e., an honest defaulted claimant's `claimInstantWithdrawRequest`/`claimWithdrawRequest` now reverts on `defaultRecoveryReserve -= amount` underflow or pays less than `claimBasis * defaultRecoveryPrice / 1e18` — quantified stolen amount = `amount * defaultRecoveryPrice / 1e18`.

Caveat: reachability depends on `IdleCDOEpochVariant` permitting instant-withdraw requests while `defaulted()`; if the CDO reverts, step 2 fails and the residual risk reduces to mode 2 (funded-float theft) only where the instant path remains open.
