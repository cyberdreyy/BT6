### Title
Stale `instantWithdrawClaimsByEpoch` basis inflates default-recovery reserve and dilutes/freezes recovery payouts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analog to CVE-2016-9103 (reading a value before it is written/cleared, leaking stale data): `claimInstantWithdrawRequest` clears a user's funded instant receipt via `instantWithdrawsRequests` only, but never clears `instantWithdrawsRequestsByEpoch[user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults in the same epoch, `finalizeDefaultRecovery` reads that stale per-epoch basis through `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, counting already-paid-out instant claims as both claim basis and already-held reserve. The recovery price is diluted and `defaultRecoveryReserve` is overstated, so later claimants cannot be paid — or are paid from underlying that belongs to active LPs.

### Finding Description
Instant withdraw accounting keeps three pieces of state per epoch:

- `instantWithdrawsRequests[_user]` — per-user aggregate receipt (cleared on claim)
- `instantWithdrawsRequestsByEpoch[_user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]` — per-epoch basis used only by default finalization
- `pendingInstantWithdraws` — unfunded remainder owed by the borrower/CDO

The funded claim path only touches the first:

`contracts/strategies/idle/IdleCreditVault.sol:387-392`
```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

and `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` (lines 398-403). Neither updates `instantWithdrawClaimsByEpoch[epochNumber]`. The per-epoch entries are only cleared in the default path `_claimDefaultedInstantWithdrawRequest` (lines 847-853), which runs *after* the stale data has already been consumed.

At finalization, both readers use the stale aggregate:

`defaultPendingClaimBasis` (lines 644-649):
```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

`_defaultPrefundedInstantReserve` (lines 716-723):
```solidity
uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
if (instantBasis > pendingInstant) {
  prefundedReserve = instantBasis - pendingInstant;
}
```

The invariant assumed is `instantWithdrawClaimsByEpoch[N] - pendingInstantWithdraws == underlying held by the strategy for prefunded claims`. Once any user claims a funded instant receipt, that invariant is permanently broken for epoch N: the basis was never decremented, so the "already-held" difference includes tokens the strategy already transferred out.

### Impact Explanation
Concretely, in epoch N: users A and B request instant withdraws; CDO calls `collectInstantWithdrawFunds` for A's share only (`pendingInstantWithdraws` drops from A+B to B; A's underlying enters the strategy); A calls `claimInstantWithdrawRequest` and is paid. `instantWithdrawClaimsByEpoch[N]` still holds A+B.

Borrower defaults before epoch end. `finalizeDefaultRecovery` computes:

- `pendingBasis` inflated by A's already-paid claim → `totalBasis` too large → `recoveryPrice` lower than fair → every genuine claimant (active AA/BB LPs and pending withdrawers) is haircut more than the true loss warrants.
- `prefundedReserve` = (A+B) − B = A is added to `reserveAmount`, but those A tokens were already transferred out. `defaultRecoveryReserve` is overstated by A.

When claimants draw the reserve via `_transferDefaultRecovery` (lines 912-917), `defaultRecoveryReserve -= amount` bookkeeping succeeds while `underlyingToken.safeTransfer` either (a) drains underlying belonging to active LP claims — direct theft of up to A tokens from other users — or (b) reverts once the real balance is exhausted, permanently freezing the last claimants' recovery share.

### Likelihood Explanation
Requires an epoch in which instant withdrawals are only *partially* funded (CDO collects less than the full pending amount), at least one funded claimant redeems, and the borrower then defaults in the same epoch while `pendingInstantWithdraws != 0`. Instant withdraws and mid-epoch partial funding are normal flows, and defaults are a designed-for state (`finalizeDefaultRecovery` exists precisely for this), so the scenario is reachable without privileged misbehavior: the attacker need only be an ordinary instant-withdraw requester whose claim leaves stale basis behind; the loss falls on other claimants. No existing guard catches it — `_transferDefaultRecovery` trusts `defaultRecoveryReserve`, and the reserve-balance check in `_transferFundedClaim` only protects the reserve, not the strategy's other funds.

### Recommendation
Clear the per-epoch instant basis whenever a receipt leaves the pending set. In `claimInstantWithdrawRequest`, after computing `amount`, subtract it from `instantWithdrawsRequestsByEpoch[_user][epochAtRequest]` and from `instantWithdrawClaimsByEpoch[epochAtRequest]` (this requires knowing the request epoch — e.g., iterate or store the user's last instant-request epoch analogous to `lastWithdrawRequest`). Alternatively, make `collectInstantWithdrawFunds` reduce `instantWithdrawClaimsByEpoch` proportionally. Add a regression test: partially fund two instant requests, claim the funded one, default in the same epoch, and assert `defaultPendingClaimBasis`/`defaultRecoveryReserve` only reflect the still-unpaid basis.

```solidity
    //   instantWithdrawClaimsByEpoch[epochNumber] still == 200 (BUG: stale read source)
    // Borrower defaults in same epoch (epochNumber unchanged).
    // finalizeDefaultRecovery:
    //   defaultPendingClaimBasis includes 200 instead of 100
    //   _defaultPrefundedInstantReserve = 200 - 100 = 100 counted as "held",

    // assert recoveryPrice < fair price and final _transferDefaultRecovery
    // either reverts (frozen recovery) or overpays early claimants from active funds.

```

I could not fully confirm whether `epochNumber` can differ between instant request and finalization in every path (it increments on `deposit` during stopEpoch, so default-in-same-epoch is required for this exact exploit shape); if finalization only ever occurs in a later epoch the stale entry is harmless. That boundary is worth verifying during the PoC.
