This confirms the key finding: `--accounts-index-scan-results-limit-mb` has **no default value** (no `.default_value()` call), meaning `scan_results_limit_bytes` defaults to `None` unless an operator explicitly sets it [1](#0-0) . When `byte_limit_for_scan` is `None`, `accumulate_and_check_scan_result_size` always returns `false`, meaning the scan is completely unbounded [2](#0-1) . Even when the limit is configured, `index_scan_accounts` still iterates over every pubkey returned by `get_index_key_pubkeys(&index_key)` and performs a full `do_load` for each before the per-account filter and size-accumulation check runs, so cost before the abort fires is proportional to the number of indexed pubkeys under that owner, not bounded independently of account count [3](#0-2) .

### Title
Unbounded per-request CPU/memory cost in `getTokenAccountsByOwner` via SplTokenOwner secondary-index scan with no default byte limit and no account-count cap - ([File: rpc/src/rpc.rs, accounts-db/src/accounts.rs, accounts-db/src/accounts_db.rs])

### Summary
`getTokenAccountsByOwner` routes to `get_filtered_spl_token_accounts_by_owner`, which — when the `SplTokenOwner` secondary index is enabled — calls `get_filtered_indexed_accounts` → `Bank::get_filtered_indexed_accounts` → `Accounts::load_by_index_key_with_filter` → `AccountsDb::index_scan_accounts`. This walks every pubkey the index has recorded for the given owner, loading and filtering each one, with cost bounded only by an optional `byte_limit_for_scan` (`scan_results_limit_bytes`) that has no CLI default and, even when set, only checks accumulated *matched* result bytes after each account is already loaded and filtered.

### Finding Description
The call path is: `rpc_accounts_scan::AccountsScanImpl::get_token_accounts_by_owner` → `JsonRpcRequestProcessor::get_token_accounts_by_owner` [4](#0-3)  → `get_filtered_spl_token_accounts_by_owner`, which for an owner-indexed key calls `get_filtered_indexed_accounts` [5](#0-4)  → `get_filtered_indexed_accounts` which passes `byte_limit_for_scans = self.config.scan_results_limit_bytes` into `bank.get_filtered_indexed_accounts` [6](#0-5)  → `Bank::get_filtered_indexed_accounts` → `Accounts::load_by_index_key_with_filter` → `AccountsDb::index_scan_accounts`.

`index_scan_accounts` iterates `self.accounts_index.get_index_key_pubkeys(&index_key)` — i.e., every pubkey the `SplTokenOwner` secondary index has recorded for that owner — and for each one performs a `do_load` (full account fetch from storage/cache) before invoking `scan_func`, which runs `filter_allows` for every `RpcFilterType` and only then feeds the account size into `accumulate_and_check_scan_result_size` [3](#0-2) [7](#0-6) .

Two compounding issues:
1. `byte_limit_for_scan` is `Option<usize>` and defaults to `None` because the corresponding CLI arg `accounts-index-scan-results-limit-mb` has no `.default_value()` [1](#0-0) . With `None`, `accumulate_and_check_scan_result_size` unconditionally returns `false`, so `config.abort()` is never triggered and the scan never aborts [2](#0-1) .
2. Even with a byte limit configured, the limit only bounds the accumulated size of the *filtered-in* (matching) accounts, not the number of pubkeys/loads/filter evaluations performed to reach that limit — a `do_load` plus a `filter_allows` chain runs unconditionally for every indexed pubkey before the size check can possibly trigger an abort for that iteration, and there is no separate cap on the raw pubkey count from `get_index_key_pubkeys`.

An attacker who is an unprivileged client can create arbitrarily many SPL token accounts owned by the same wallet (each a normal, permissionless on-chain instruction), which get inserted into the `spl_token_owner_index` via `update_spl_token_secondary_indexes` [8](#0-7) . A single subsequent `getTokenAccountsByOwner` RPC call then forces the validator to perform `do_load` + multi-filter evaluation (and, for `jsonParsed` encoding, additional parsing via `get_parsed_token_accounts`) for every one of those accounts within a single request/thread, with the response size unbounded by default and CPU/memory work scaling linearly with attacker-controlled account count.

### Impact Explanation
This is a single-request unbounded-cost RPC issue: one JSON-RPC call from one client can force per-account load/filter/decode work proportional to an attacker-controlled quantity of on-chain token accounts, with no independent count cap and (in the common/default configuration) no byte limit at all. This matches the "RPC DoS via single low-rate call with unbounded cost" bounty category — it is a legitimate scoped finding because it requires only one call (not multiple clients or unfiltered `getProgramAccounts`) and exploits the indexed path specifically named in the question (`SplTokenOwner` secondary index), not the unindexed `getProgramAccounts` fallback which is explicitly out of scope.

### Likelihood Explanation
Preconditions are realistic and attacker-controlled: (1) validator operator has enabled the `SplTokenOwner` account secondary index (a supported, documented feature for RPC nodes serving `getTokenAccountsByOwner`/`getProgramAccounts`-by-owner), and (2) an unprivileged attacker creates many token accounts for a single owner key, which is permissionless and requires only rent-exempt lamports and standard SPL Token/Token-2022 `InitializeAccount` instructions. No leaked keys, validator control, or multiple clients are needed. The `scan_results_limit_bytes` guard defaults to unset, so on many real-world configurations there is no size bound either, making the likelihood high wherever this index is enabled without explicit manual tuning of `--accounts-index-scan-results-limit-mb`.

### Recommendation
- Give `accounts-index-scan-results-limit-mb` a sane non-`None` default so `scan_results_limit_bytes` is always bounded unless an operator explicitly opts into unlimited.
- Add an explicit, independent cap on the number of pubkeys processed from `get_index_key_pubkeys` per scan (checked before `do_load`/filtering), not just on accumulated matched-result bytes, so that work is bounded by index-key cardinality irrespective of filter selectivity.
- Consider checking the abort condition before performing the `do_load` for the next pubkey in `index_scan_accounts`'s loop (it already checks `config.is_aborted()` at loop top, but the limit can currently only fire after a filtered-in match; add a raw iteration-count based abort as well).

### Proof of Concept
Integration test plan (accounts-db + rpc crates):
1. Enable `AccountIndex::SplTokenOwner` via `AccountSecondaryIndexes` test utilities (`spl_token_owner_index_enabled()`).
2. In a loop, create N SPL Token accounts (packed 165-byte `Account` state) all owned by the same `owner_key`, inserting them into a test `Bank`/`AccountsDb` so they populate `spl_token_owner_index`.
3. Leave `scan_results_limit_bytes` as `None` (default CLI behavior) and issue one `getTokenAccountsByOwner` RPC request (or call `get_filtered_spl_token_accounts_by_owner` directly) for `owner_key`.
4. Measure wall-clock time and peak allocations of the single call as N scales from e.g. 1,000 to 1,000,000; assert that latency/memory grows ~linearly with N and that no request-level abort occurs regardless of N (confirming invariant violation: "cost of one request bounded by explicit limits, not by on-chain data volume" fails).
5. Repeat with `scan_results_limit_bytes = Some(small_value)` and many small matching accounts, confirming that although the eventual result set is capped, the number of `do_load` + `filter_allows` invocations performed before abort still scales with the total indexed pubkey count for the owner (e.g., by instrumenting/counting calls into the `scan_func` closure), showing the byte limit does not cap iteration count independent of index cardinality.
