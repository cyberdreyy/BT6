## Analysis

This exploit path is valid. The vulnerability lies in how `rescueFunds` is gated versus how the normal cancellation flow works on `EscrowSrc`.

`BaseEscrow.rescueFunds` only checks three things: the caller is the `taker`, the immutables hash validates, and `block.timestamp >= immutables.timelocks.rescueStart(RESCUE_DELAY)`. `rescueStart` is computed purely as `deployedAt + RESCUE_DELAY`, completely independent of whether the escrow was ever cancelled, withdrawn, or is still holding the maker's live principal. [1](#0-0) [2](#0-1) 

Meanwhile the legitimate return path for a stalled source escrow is `EscrowSrc.cancel`/`publicCancel`, which sends `immutables.amount` back to `immutables.maker`: [3](#0-2) [4](#0-3) 

Both `cancel` and `publicCancel` have `onlyAfter(...)` guards but **no upper bound**, so they remain callable indefinitely once their window opens. There is nothing in the code that prevents `rescueFunds` from being called for the exact same `token`/`amount` as the live, un-cancelled maker principal — the function performs an unconditional `_uniTransfer(token, msg.sender, amount)` with `msg.sender == taker`.

Consequently, when a taker deploys `EscrowSrc` for a single-fill order and never creates the destination escrow (e.g., abandons the swap), the taker — who is a normal, unprivileged order-filler, not an admin — has a direct economic incentive **not** to call `cancel`/`publicCancel` (which only nets them the small safety deposit and sends the principal to the maker). Instead, they can simply wait until `RESCUE_DELAY` elapses and call `rescueFunds(immutables.token, immutables.amount, immutables)` to redirect the maker's entire original principal to themselves. The only real-world backstop is a third-party access-token holder calling `publicCancel` first — an off-chain, unenforced race — not an on-chain guarantee.

This matches the "Src rescue can drain maker principal" pattern described in the question, and README's own description of rescue as being "for assets... accidentally stuck" is not enforced anywhere in code — `rescueFunds` cannot distinguish dust from live principal. [5](#0-4) 

### Title
Taker can drain the maker's live source-escrow principal via `rescueFunds` instead of returning it through `cancel` - (`contracts/BaseEscrow.sol`, `contracts/EscrowSrc.sol`)

### Summary
`rescueFunds` is callable by the `taker` on any `EscrowSrc` clone once `RESCUE_DELAY` has elapsed from deployment, with no check that the escrow has already been resolved (cancelled/withdrawn) or that the requested `token`/`amount` correspond to accidental leftover dust rather than the live maker principal.

### Finding Description
For a single-fill order where the taker deploys the source escrow but never creates the corresponding destination escrow, the swap stalls. The intended unwind path is `EscrowSrc.cancel` (taker-only, after `SrcCancellation`) or `EscrowSrc.publicCancel` (any access-token holder, after `SrcPublicCancellation`), both of which return `immutables.amount` of `immutables.token` to `immutables.maker`. However, since these functions have no closing time bound, and `BaseEscrow.rescueFunds` opens at `deployedAt + RESCUE_DELAY` with only a `taker`-caller check and no state/balance-provenance check, the taker can bypass the maker-return path entirely: they simply never call `cancel`, wait for `RESCUE_DELAY` to pass, and then call `rescueFunds(immutables.token, immutables.amount, immutables)` to redirect the still-fully-funded maker principal to their own address. [1](#0-0) 

### Impact Explanation
This is direct theft of user (maker) funds at rest, matching the Critical bucket ("direct theft of user funds at rest or in motion... caused by these production contracts"). The maker's entire principal, which should return to them via cancellation once the swap is abandoned, is instead seized by the taker.

### Likelihood Explanation
High for the taker specifically: they know their own escrow's exact `deployedAt`/`RESCUE_DELAY` and can submit `rescueFunds` at the earliest valid block, whereas the only competing safeguard (`publicCancel` by an unrelated access-token holder) depends on an external actor noticing and acting first — an unenforced, off-chain race rather than an on-chain guarantee. The taker has clear economic motive to withhold `cancel` (which only earns them the safety deposit) in favor of `rescueFunds` (which nets them the full principal).

### Recommendation
`rescueFunds` should not be able to move funds that correspond to the still-outstanding `immutables.amount`/`immutables.token` obligation of an unresolved escrow — e.g., require the escrow to have already emitted `EscrowWithdrawal`/`EscrowCancelled` (via a stored resolved flag) before allowing rescue of the original `token`, or explicitly exclude `immutables.token` up to `immutables.amount` from what `rescueFunds` can withdraw until the escrow is resolved.

### Proof of Concept
1. Maker signs an order; taker fills it via Limit Order Protocol, causing `EscrowFactory.postInteraction` to deploy `EscrowSrc` funded with the maker's `amount` of `token` plus safety deposit.
2. Taker never calls `EscrowFactory.createDstEscrow` on the destination chain — the swap stalls.
3. Time passes `SrcCancellation`/`SrcPublicCancellation`, but no access-token holder calls `publicCancel` (e.g., low-value swap not worth a keeper's gas, or taker races them).
4. Once `block.timestamp >= immutables.timelocks.rescueStart(RESCUE_DELAY)`, taker calls `EscrowSrc.rescueFunds(immutables.token, immutables.amount, immutables)`.
5. `_uniTransfer` sends the full `immutables.amount` to `msg.sender` (the taker), confirmed by the existing test pattern of rescue transferring the full requested amount with no balance/state precondition. [6](#0-5)
