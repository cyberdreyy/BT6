### Title
Stale confirmations from a deleted multisig member still count toward the confirmation threshold, allowing requests to execute below the live-member quorum - (File: multisig2/src/lib.rs)

### Summary
The `multisig2` contract lets `K` of `N` members confirm a `MultiSigRequest` before it executes. When a member is removed via `DeleteMember`, the contract only purges confirmation records for requests *created* by that member; it never scans other pending requests' confirmation sets to strip out that member's prior `confirm()` votes. Consequently a removed member's stale confirmation can still count toward `num_confirmations` on requests they never created, letting a request execute with fewer than `K` currently-valid member approvals.

### Finding Description
`confirm()` accepts a vote from `self.current_member()` and stores it (as a serialized string) in `self.confirmations: LookupMap<RequestId, HashSet<String>>`: [1](#0-0) 

When a member is removed, `delete_member()` is invoked from `execute_request()` for the `DeleteMember` action: [2](#0-1) 

`delete_member()` cleans up confirmations only for requests whose `r.member == member` — i.e. requests *added* (signed) by the removed member — and clears that member's own `num_requests_pk` entry: [3](#0-2) 

It never iterates `self.confirmations` to remove the deleted member's `to_string()` entry from other, still-pending requests where that member merely voted via `confirm()` (but did not create the request). Those `HashSet<String>` entries remain in storage.

`confirm()` later computes quorum purely from `confirmations.len()`:
```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
``` [4](#0-3) 

This length includes any stale entries left by since-removed members, so the binding "confirmations counted == currently live members who approved" is broken: `confirmations.len()` can exceed the number of live members who actually still endorse the pending request.

### Impact Explanation
This is a Critical-class issue per the multisig binding: "a multisig request executed below threshold." A transfer, `FunctionCall`, `AddKey`, or any other sensitive action can be executed with the account's actual live signer quorum count being one (or more) below the configured `K`, because a departed/revoked member's old vote is silently carried over and treated as a live approval. This directly undermines the K-of-N custody guarantee the contract is designed to provide — funds or account authority can move with fewer authorized approvals than intended.

### Likelihood Explanation
Likelihood is realistic in normal multisig lifecycle usage, not a contrived edge case: membership changes (removing a compromised key, offboarding an employee, rotating keys) are a routine multisig operation, and it is common to have multiple requests pending simultaneously (the contract even enforces `active_requests_limit` to allow up to 12 concurrent per-member requests). Any request that received a partial confirmation from a member before that member was later deleted will retain the stale vote indefinitely (`confirmations` for that request is never re-validated against `self.members`), so the divergence surfaces whenever the remaining members supply just enough new confirmations to hit `num_confirmations`.

### Recommendation
When executing `DeleteMember`, iterate over all pending requests' confirmation sets (not only those created by the removed member) and strip the removed member's string identifier from each. Alternatively, validate confirmations against current membership at `confirm()`/execution time — e.g., filter `confirmations` to only members currently in `self.members` before comparing against `self.num_confirmations`, so a member removed after voting no longer contributes to quorum.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A.add_request(R)` creates transfer request `R` (id 0). No auto-confirmation.
3. `D.confirm(0)` → `confirmations(0) = {D}`.
4. `B.confirm(0)` → `confirmations(0) = {D, B}` (2/3, not yet executed).
5. Separately, members `A, B, C` create and confirm a `DeleteMember{D}` request (3-of-4 quorum reached with live members), removing `D` from `self.members`. `delete_member()` only purges requests created *by* `D`; request `0` was created by `A`, so its confirmations `{D, B}` are untouched.
6. `C.confirm(0)` → `confirmations(0).len() + 1 = 3 >= num_confirmations (3)` → `execute_request(R)` fires the transfer.
7. Result: request `R` executed with confirmations attributed to `D, B, C`, but `D` was no longer a member at execution time — only 2 live members (`B`, `C`) actually endorsed it, one below the configured 3-of-N threshold. [3](#0-2) [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
