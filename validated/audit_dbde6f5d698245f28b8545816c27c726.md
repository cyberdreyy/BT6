### Title
Memory leak of shared-allocator regions on mid-batch allocation failure in `check_resolve_pubkeys` / `check_batch` - ([File: core/src/banking_stage/consume_worker.rs])

### Summary
`ExternalWorker::check_resolve_pubkeys` allocates a `SharablePubkeys` region from the shared `rts_alloc::Allocator` once per transaction inside a loop over the whole batch. If the allocation for a later transaction in the batch fails, the function returns early via `?` without freeing the `pubkeys_allocation`s that were already successfully allocated for earlier transactions in the same loop, and without freeing the `responses_ptr` region that `check_batch` allocated before calling into `check_resolve_pubkeys`. This mirrors the kernel bug class in the report (EVT_TRANSACTION error paths failing to free previously-allocated memory before returning an error), just applied to agave's cross-process shared allocator used by the external-scheduler transaction-checking path.

### Finding Description
`check_batch` first allocates a `CheckResponse` region for the whole batch via `allocate_check_response_region`: [1](#0-0) 

It then calls `check_resolve_pubkeys`, which iterates over every transaction in the batch and, for transactions whose account keys exceed static account keys (i.e., transactions using address-lookup-table resolution), allocates a separate `pubkeys_allocation` from the same shared allocator: [2](#0-1) 

The allocation call uses `.ok_or(ExternalConsumeWorkerError::AllocationFailure)?`, which returns immediately from `check_resolve_pubkeys` on failure: [3](#0-2) 

Because the loop processes transactions sequentially and each successful iteration writes a `pubkeys_allocation` offset only into a local `response.resolved_pubkeys` (never stored anywhere else that could later be freed), any `pubkeys_allocation`s from earlier iterations of the *same* call are abandoned in the allocator's bookkeeping the moment the function returns `Err`. The error then propagates up through `check_batch`'s `?` at the call site: [4](#0-3) 

which also means the `responses_ptr`/`CheckResponse` region allocated earlier in `check_batch` (line 497-501) is never freed either — `check_batch` simply propagates the error without any cleanup path, unlike the deliberate (and explicitly commented) leak-on-purpose in `return_not_included_with_reason`: [5](#0-4) 

The error then bubbles further through `process_message` → `iterate` → `run`, none of which attempt to reclaim allocator memory for the aborted request: [6](#0-5) 

This shared allocator (`rts_alloc::Allocator`) is a fixed-size arena shared across the process boundary between agave and the external scheduler/pack process, and its accounting model requires every `allocate()` to be matched by exactly one `free()`: [7](#0-6) 

Leaked allocations permanently reduce the usable capacity of this fixed-size arena for the lifetime of the process, exactly analogous to the kernel CVE's `devm_kfree` omission on error paths.

### Impact Explanation
A stream of transactions carrying address-lookup-table references (so that `account_keys().len() > num_static_account_keys()`) sent to the external-scheduler check path can trigger `pubkeys_allocation` calls repeatedly. Under allocator pressure (fragmentation or exhaustion from concurrent batches), a failure partway through a batch leaks all previously-successful `pubkeys_allocation`s for that batch plus the batch's `CheckResponse` region. Because this occurs on the check path, which is reachable purely from submitted transactions containing ALT references, an unprivileged sender can repeatedly induce this condition to progressively shrink the usable shared-memory arena. Given the arena has a fixed size, sustained leakage can eventually exhaust it, causing all subsequent allocations in `check_batch`/`check_resolve_pubkeys` to fail — and, per the same code path, each subsequent failure leaks further, worsening the condition — ultimately starving the worker of shared memory needed to process transaction checks/execution for the leader, resulting in a transaction-triggered degradation/DoS of the leader's transaction-checking pipeline.

### Likelihood Explanation
This requires: (1) the external-scheduler feature (`#[cfg(unix)] mod external`) to be in use, (2) the shared allocator to reach a state where an allocation genuinely fails mid-batch (arena exhaustion/fragmentation), and (3) repeated triggering by an attacker submitting many ALT-referencing transactions to accelerate exhaustion. The allocator is a fixed, bounded resource shared across the whole worker for its lifetime, so any leak is permanent and cumulative, making repeated exploitation straightforward once the feature path is active; however, actually forcing individual allocation failures requires sustained load or a sufficiently small configured arena size, which somewhat limits immediate exploitability under default configuration.

### Recommendation
In `check_resolve_pubkeys`, on `AllocationFailure` for a transaction mid-batch, free all previously-allocated `pubkeys_allocation` regions from earlier iterations of the same call before propagating the error. Additionally, in `check_batch`, ensure that if `check_resolve_pubkeys` (or any subsequent step) returns an error, the `responses_ptr`/`CheckResponse` region allocated at the top of `check_batch` is freed before returning, rather than relying on `?` to silently drop it. Consider tracking allocated sub-regions in a `Vec` that is unwound/freed via a guard (e.g., an RAII wrapper around `rts_alloc::Allocator` allocations) so that any early return frees all outstanding allocations for the in-flight request.

### Proof of Concept
1. Configure/run the external-scheduler worker (`ExternalWorker`) with a shared allocator sized small enough to be exhausted by repeated allocations (or under sustained concurrent load in production sizing).
2. Submit a batch of check-mode `PackToWorkerMessage`s where multiple transactions use address lookup tables such that `account_keys().len() > num_static_account_keys()` for each, forcing `check_resolve_pubkeys` to call `self.allocator.allocate(...)` once per such transaction within the same `check_batch` invocation.
3. Continue sending such batches until the allocator's free space becomes fragmented/exhausted so that an `allocate()` call inside the loop returns `None` for a transaction that is not first in the batch.
4. Observe that `check_resolve_pubkeys` returns `Err(ExternalConsumeWorkerError::AllocationFailure)` via the `?` operator at line 718, and that `check_batch` propagates this error without freeing either the earlier-in-the-batch `pubkeys_allocation`s or the `responses_ptr` region allocated at line 497-501.
5. Repeat across many batches; measure the allocator's remaining capacity via `Allocator::clean_remote_free_lists`/allocator stats (called each iteration at line 313) to confirm capacity monotonically decreases and never recovers for the leaked regions, eventually causing persistent `AllocationFailure` for all future check/execute batches.
