### Title
Junior (BB) holders escape the BB-first loss waterfall by queuing withdraw requests, diluting losses onto senior (AA) receipts and weakening AA protection - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the Sentiment report (one pool's risk settings liquidate positions in another pool because collateral is not partitioned per risk bucket), `IdleCreditVault` mixes AA and BB withdraw receipts into a single tranche-agnostic `pendingWithdraws` bucket. When `stopEpochWithDuration` realizes a loss, `previewLossAdjustedWithdrawFunds` splits the loss pro rata between the whole pending bucket and active LPs, then applies the active remainder via the BB-first waterfall. A BB tranche holder can therefore convert junior capital into a blended receipt during the buffer period and shed part of the first-loss obligation onto AA pending receipts, while simultaneously shrinking the BB buffer that protects still-active AA holders.

### Finding Description
`requestWithdraw` in `IdleCreditVault` mints the user a strategy-token receipt and adds the amount to the aggregate `pendingWithdraws` without recording whether it came from AA or BB [1](#0-0) . On the CDO side, the request burns the user's tranche tokens and decreases that tranche's `lastNAV`, so the junior capital leaves the waterfall.

At epoch end, `_stopEpoch` calls `previewLossAdjustedWithdrawFunds(_lossAmount)`, which computes `pendingLoss = _lossAmount * pendingBasis / totalBasis` — a flat pro-rata share across all receipts regardless of seniority [2](#0-1) . The haircut is stored as `lossRecoveryPriceByEpoch[epochNumber]` and every receipt of that epoch claims at the same price via `_claimLossAdjustedWithdrawRequest` [3](#0-2) [4](#0-3) . Only `activeLoss` is applied BB-first through `_forceUpdateAccounting` [5](#0-4) .

Attack path (all unprivileged actions; the loss itself comes from an honest manager `stopEpochWithDuration` call):
1. During the buffer period (`allowBBWithdrawRequest == true`), the attacker — a BB holder anticipating a loss epoch — calls `IdleCDOEpochVariant.requestWithdraw` on the BB tranche. BB NAV drops and the receipt enters the shared pending bucket alongside AA receipts.
2. Manager runs the epoch and stops it with `_lossAmount`. The pending bucket takes only `loss * pendingBasis/(active+pending)`, shared equally with AA receipts, instead of the attacker's junior capital absorbing the loss first.
3. Active AA holders are doubly harmed: the escaped BB capital no longer buffers `activeLoss`, and AA pending receipts are haircut at the same rate as BB receipts.

Numeric example: AA active = 1000, BB active = 1000, attacker BB receipt = 1000 pending, loss = 1500. Pending loss = 1500 * 1000/3000 = 500 (attacker loses 500, AA pending receipts share pro-rata). Had the attacker stayed active, the BB waterfall would have assigned them 1500 * 1000/2000 = 750. The attacker saves ~250 per epoch, paid by AA receipt holders and by active AA holders whose effective junior cover shrank from 2000 to 1000.

### Impact Explanation
Broken loss-waterfall invariant: junior capital can opt out of first-loss absorption by transiting the tranche-agnostic pending bucket. Senior (AA) lenders and AA pending withdrawers absorb losses that BB capital was contracted to bear, and residual active AA holders lose buffer proportionally to the queued BB amount. Loss scales with BB queue size and realized loss; repeatable every loss epoch.

### Likelihood Explanation
Requires only a BB tranche holder calling `requestWithdraw` in the buffer period before a loss-bearing `stopEpochWithDuration`. Requests are unprivileged (subject only to KYC gating, which the attacker class satisfies), no timing race is needed, and no privileged actor misbehaves. Any epoch ending with a realized loss while BB receipts are pending triggers the dilution.

### Recommendation
Retain tranche identity in pending receipts: track `pendingWithdrawsAA`/`pendingWithdrawsBB` (or per-epoch AA/BB basis maps) and apply `stopEpochWithDuration` losses to the pending bucket BB-first, mirroring the active waterfall — e.g., compute `pendingBBLoss = min(loss, pendingBBBasis)` before any AA receipt is haircut, and store separate `lossRecoveryPriceByEpochAA/BB`. Alternatively, order all claims through a single waterfall that ranks pending BB receipts at parity with active BB.

### Proof of Concept
Foundry-style PoC against the epoch variant test harness (same setup as `testStopEpochWithDurationLargeLossUsesBBFirstWaterfall` in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testBBWithdrawDodgesWaterfall() public {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);            // honest AA LP
    vm.prank(bob);
    idleCDO.depositBB(amount);            // attacker BB LP

    // attacker queues BB withdraw during buffer period
    vm.prank(bob);
    cdoEpoch.requestWithdraw(0, cdoEpoch.BBTranche()); // -> pending bucket, tranche-agnostic

    // epoch runs with apr = 0 to isolate the loss
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    _startEpochAndCheckPrices(0);

    // borrower funds the pending-to-fund portion
    uint256 loss = 12_000 * ONE_SCALE;    // > entire remaining BB NAV (10k)
    uint256 pending = strategy.pendingWithdraws();      // ~10k (bb + interest)
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(loss);
    deal(defaultUnderlying, borrower, pendingToFund);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), pendingToFund);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), loss);

    // attacker receipt only bears pendingShare of the loss instead of full BB-first wipe
    uint256 price = strategy.lossRecoveryPriceByEpoch(strategy.epochNumber() - 1);
    assertGt(price, 0);                   // attacker keeps > 0 although loss >= whole BB NAV
    // active AA also lost: activeLoss = loss - pendingLoss burned BB-first then spilled into AA
    assertLt(cdoEpoch.virtualPrice(cdoEpoch.AATranche()), ONE_SCALE);
}
```

Expected: the attacker's pending BB receipt is haircut only by `loss * pending/(pending+active)` (~4k of 10k), recovering ~6k; had it remained active BB it would have been wiped entirely. AA pending receipts are haircut at the same rate as junior receipts, and active AA absorbs spillover despite BB capital having exited the waterfall.

```text
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
