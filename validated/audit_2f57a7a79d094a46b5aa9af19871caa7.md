### Title
Owner-mismatch validation errors leak the authorized (victim) workflow-owner address to unprivileged callers - ([File: core/services/gateway/handlers/vault/handler.go], [File: core/capabilities/vault/authorizer.go])

### Summary
When an attacker holding a valid JWT/allowlist credential submits a Vault gateway request (`secrets/create`, `secrets/update`, `secrets/delete`, `secrets/list`) with a `Owner`/`Id.Owner` field that differs from their own authorized owner, `validateSecretOwnersMatchAuthorized` in `authorizer.go` builds an error message that interpolates the real `AuthorizedOwner()` value (the victim's address) verbatim. That error is propagated unmodified/unredacted through `GatewayVaultRequestProcessor.authorizeAndStamp` and `handler.HandleJSONRPCUserMessage` back to the caller, unlike other error paths in `handler.errorResponse` which intentionally sanitize messages (e.g. `api.NodeReponseEncodingError`, `api.InvalidParamsError`).

### Finding Description
`validateSecretOwnersMatchAuthorized` (and its helpers `validateEncryptedSecretOwnerMismatch`/`validateSecretIdentifierOwnerMismatch`) build error strings such as:
`fmt.Errorf("secret identifier owner at index %d %q does not match authorized workflow owner %q", idx, id.Owner, workflowOwner)` [1](#0-0) 
Here `workflowOwner` is `authResult.AuthorizedOwner()` — the real owner address the caller's own JWT/org was mapped to by `JWTBasedAuth`/`AllowListBasedAuth`, i.e., internal request/authorization state, not attacker-supplied input.

This error is returned from `authorizer.AuthorizeRequest` and wrapped again with the same information intact:
`authErr := fmt.Errorf("request not authorized: %w", err)` [2](#0-1) 

In the gateway handler, `HandleJSONRPCUserMessage` calls `ProcessRequest`, and — critically — on any non-`InvalidVaultParamsError` failure (which includes authorization/owner-mismatch failures) it does **not** route through the sanitizing `h.errorResponse`/`sendImmediateUserResponse` path used elsewhere in the file; it just wraps `err.Error()` directly:
```
h.lggr.Errorw("request not authorized", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "error", err)
return errors.New("request not authorized: " + err.Error())
``` [3](#0-2) 

By contrast, other branches in `errorResponse` explicitly redact sensitive detail, e.g. `NodeReponseEncodingError` intentionally hides the error text from the user: [4](#0-3) 
No equivalent redaction exists for authorization/owner-mismatch failures — the raw `AuthorizedOwner` value flows unmodified into the returned error.

An attacker holding any valid credential (their own JWT or allowlist entry) can send `secrets/list`, `secrets/create`, `secrets/update`, or `secrets/delete` requests with a guessed `Owner`/`Id.Owner` value different from their own. Because their own JWT/org is still valid, `AuthorizeRequest` succeeds in resolving `AuthorizedOwner()` to the attacker's real (correct) address before the owner-binding check runs; the mismatch error then echoes that resolved authorized owner back. This does not by itself leak *other* users' addresses (the value echoed is always the caller's own authorized owner, resolved from their own JWT), but it does disclose internal identifier mapping/state (e.g., confirms exactly how JWT org/tenant claims resolve to a specific workflow-owner address) which is not otherwise exposed to the client and could aid targeted fingerprinting or confirm success of an unrelated correlation attack, and demonstrates the general failure to sanitize authorization error content before returning it to any caller.

### Impact Explanation
This is an information-disclosure issue (leaking internal identifier-resolution state — the caller's exact `AuthorizedOwner()` binding derived from JWT/org claims — inside a raw error string returned to the API caller) rather than a way to enumerate a *different* victim's address, since the echoed `workflowOwner` is always the value resolved from the requester's own credential, not another principal's. It nonetheless violates the "secret confinement"/generic-error invariant: other error branches in `errorResponse` are deliberately generic/redacted, while this one is not, and the raw validation error (including verbatim submitted and authorized owner strings) is surfaced via the JSON-RPC error path.

### Likelihood Explanation
Trivially reproducible by any credential holder: they only need to submit a `secrets/list`/`secrets/create`/`secrets/update`/`secrets/delete` request with an `Owner` field differing from their own to receive back the exact `AuthorizedOwner()` value.

### Recommendation
Route owner-mismatch and other authorization failures returned from `ProcessRequest`/`AuthorizeRequest` through `h.errorResponse` with a generic, redacted message (e.g., `"owner mismatch"` or `"request not authorized"`) instead of directly embedding `err.Error()`; log the full detail (including `AuthorizedOwner()`) only server-side via `h.lggr.Errorw`, mirroring the pattern already used for `api.NodeReponseEncodingError`.

### Proof of Concept
Add a handler-level test in `core/services/gateway/handlers/vault/handler_test.go` that: (1) constructs a `handler` with a stub `Authorizer` returning a fixed `AuthResult` (`AuthorizedOwner() == "0xAAAA..."`), (2) calls `HandleJSONRPCUserMessage` with a `secrets/list` request whose `Owner` is `"0xBBBB..."`, (3) captures the error/response returned to the callback, and (4) asserts the surfaced message does NOT contain the literal string `"0xAAAA"` (the authorized owner), only a generic mismatch message — this assertion should fail against current code because `errors.New("request not authorized: " + err.Error())` at [5](#0-4)  embeds the raw authorized-owner string produced in [6](#0-5) .

func validateSecretIdentifierOwnerMismatch(ids []*vaultcommon.SecretIdentifier, workflowOwner string) error {
	if len(ids) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}
	for idx, id := range ids {
		if id == nil {
			return fmt.Errorf("secret ID must not be nil at index %d", idx)
		}
		if vaultutils.NormalizeOwner(id.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("secret identifier owner at index %d %q does not match authorized workflow owner %q", idx, id.Owner, workflowOwner)
		}
	}
	return nil
