### Title
Drift admin can permanently brick user withdrawals by depositing into more than 2 reward spot markets - ([File: programs/marginfi/src/instructions/drift/withdraw.rs])

### Summary
Marginfi's Drift-wrapped bank integration (`drift_withdraw`) is permissioned to accept at most 2 "reward" spot-market/oracle/mint account triples on top of the user's main asset position. Drift is a "RESTRICTED" external protocol whose admin can deposit into a user's Drift `MinimalUser` account at spot-position indices 2-7 (up to 6 additional reward markets). Marginfi's own mocked reward-tracking logic (`MinimalUser::validate_not_bricked_by_admin_deposits`) explicitly documents that once more than 2 reward assets accumulate (i.e. `active_deposits > 3`), the account becomes permanently unable to withdraw, because the `drift_withdraw` instruction accounts struct hard-codes only two optional reward slots (`drift_reward_spot_market` / `drift_reward_spot_market_2`) with no way to pass a third.

### Finding Description
`DriftWithdraw`'s account validation in [1](#0-0)  enforces `user.validate_reward_accounts(...)` and `user.validate_not_bricked_by_admin_deposits()`. The struct itself only exposes two optional reward oracle/spot-market/mint triples, as declared at [2](#0-1) .

The underlying Drift `MinimalUser` model has 8 spot positions, and admin deposits can land in indices 2-7 (6 slots) as documented at [3](#0-2) . The bricking check makes explicit that marginfi "supports 1 main asset + up to 2 reward assets" and that if the Drift admin deposits more than 2 reward assets, the account "has been bricked by Drift admin deposits" and withdrawal is permanently blocked with `TooManyActiveDeposits`: [4](#0-3) . The intermediate stage (2-3 active reward deposits, but missing accounts) is enforced via `validate_reward_accounts`, which fails with `DriftMissingRewardAccounts`: [5](#0-4) .

The only mitigation is `drift_harvest_reward`, a global-fee-wallet-only path that requires the caller to control `fee_state.global_fee_wallet` as the harvest destination authority (`associated_token::authority = fee_state.load()?.global_fee_wallet`): [6](#0-5) . This harvest path removes only one reward position at a time and is not callable by the affected user or a permissionless actor to unblock an arbitrary number of admin-injected reward markets; it depends on marginfi's own privileged fee wallet reacting in time, but does nothing to prevent the Drift admin (a RESTRICTED, uncontrolled external actor) from repeatedly injecting new reward deposits faster than harvesting can clear them, or from injecting more than 2 at once, permanently exceeding the two-reward-slot ceiling hard-coded into `DriftWithdraw`.

This is structurally identical to the Convex `BaseRewardPool.addExtraReward` bug class: an integrated protocol's admin has an unrestricted, unbounded ability to attach reward assets to a position that marginfi's fixed-arity withdrawal instruction cannot accommodate, permanently freezing user withdrawals from that position.

### Impact Explanation
Once a Drift admin deposits a 3rd (or more) reward asset into a user's Drift sub-account tracked by a marginfi bank, `drift_withdraw` becomes permanently unusable for that account (`TooManyActiveDeposits`), and the user's underlying deposited collateral in that bank is durably frozen — they cannot withdraw or realize their funds via `drift_withdraw`, and the fix depends entirely on the marginfi fee-wallet operator harvesting one reward at a time via `drift_harvest_reward`, a privileged, non-user-callable, single-market-at-a-time remedy. If admin deposits arrive faster than harvests, or exceed 2 at once, the freeze is effectively permanent. This constitutes a durable freeze of user funds with direct financial effect (inability to withdraw/realize collateral), matching Sherlock's accepted Medium severity classification for the Convex analog.

### Likelihood Explanation
Likelihood is low but non-zero and matches the accepted precedent: it requires a restricted external admin (Drift) to perform an atypical, protocol-harming action (dumping many reward assets into a specific user account) rather than a normal admin operation. Per the Sherlock judgment on the referenced issue and its duplicates, "external admin's actions leading to harm of the protocol" are considered valid Medium findings, and the design here explicitly acknowledges and names this exact bricking scenario in its own mocked implementation and error messages, indicating it is a recognized, reachable failure mode rather than a theoretical one.

### Recommendation
- Support a permissionless or user-callable harvest path (not gated to the global fee wallet) so any account holder can clear excess admin-injected reward positions on their own Drift sub-account before it exceeds the 2-reward-slot ceiling.
- Make `drift_withdraw` (or a dedicated instruction) accept a variable/looped set of reward accounts via `remaining_accounts` instead of a fixed 2-slot struct, so an arbitrary number of admin-added reward markets can be harvested/withdrawn in one transaction.
- Consider proactively capping/monitoring Drift sub-accounts used by marginfi banks and alerting or auto-harvesting before the 2-reward threshold is reached, and document this residual risk (as Zivoe's remediation ultimately did) so operators can react before a permanent freeze occurs.

### Proof of Concept
1. A user deposits into a marginfi Drift-wrapped bank; the bank's `liquidity_vault_authority` owns a Drift `User` account (`integration_acc_2`) holding the user's main asset in position 1 (non-USDC market).
2. The Drift protocol admin (RESTRICTED per marginfi's trust model, analogous to Convex's `rewardManager`) deposits into positions 2, 3, and 4 of the same Drift `User` account, e.g. via reward/incentive deposits, as simulated in `fundAndDepositAdminReward` ( [7](#0-6) ), performed 3+ times for distinct market indices.
3. `MinimalUser::count_active_deposits()` now returns 4 (1 main + 3 reward), so `validate_not_bricked_by_admin_deposits` returns `Err(TooManyActiveDeposits)` for every call to `drift_withdraw`, per [8](#0-7) .
4. The user cannot pass a 3rd reward account triple because `DriftWithdraw` only declares `drift_reward_spot_market`/`drift_reward_spot_market_2` (2 slots): [2](#0-1) . Every `drift_withdraw` call for this account now fails, and the user's funds are stuck until the privileged global fee wallet harvests down to ≤2 reward markets — which the user cannot force or control.

export const fundAndDepositAdminReward = async (
  driftAdmin: Keypair,
  bank: PublicKey,
  tokenMint: PublicKey,
  marketIndex: number,
  amount: BN,
) => {
  await createIntermediaryTokenAccountIfNeeded(bank, tokenMint);
  await createGlobalFeeWalletTokenAccount(tokenMint);

  const adminTokenAccount = getAssociatedTokenAddressSync(
    tokenMint,
    driftAdmin.publicKey,
  );

  const createAdminAtaIx = createAssociatedTokenAccountIdempotentInstruction(
    globalProgramAdmin.wallet.publicKey,
    adminTokenAccount,
    driftAdmin.publicKey,
    tokenMint,
  );

  const mintToAdminIx = createMintToInstruction(
    tokenMint,
    adminTokenAccount,
    globalProgramAdmin.wallet.publicKey,
    amount.toNumber(),
  );

  const fundTx = new Transaction().add(createAdminAtaIx).add(mintToAdminIx);
  await processBankrunTransaction(
    bankrunContext,
    fundTx,
    [globalProgramAdmin.wallet],
    false,
    true,
  );

  const bankAccount = await bankrunProgram.account.bank.fetch(bank);
  const spotMarket = await getSpotMarketAccount(
    driftBankrunProgram,
    marketIndex,
  );
  const [spotMarketPDA] = deriveSpotMarketPDA(
    driftBankrunProgram.programId,
    marketIndex,
  );

  const remainingAccounts: PublicKey[] = [];
  if (!spotMarket.oracle.equals(PublicKey.default)) {
    remainingAccounts.push(spotMarket.oracle);
  }
  remainingAccounts.push(spotMarketPDA);

  const adminDepositIx = await makeAdminDepositIx(
    driftBankrunProgram,
    {
      admin: driftAdmin.publicKey,
      integrationAcc2: bankAccount.integrationAcc2,
      adminTokenAccount: adminTokenAccount,
    },
    {
      marketIndex,
      amount,
      remainingAccounts,
    },
  );

  const depositTx = new Transaction().add(adminDepositIx);
  await processBankrunTransaction(
    bankrunContext,
    depositTx,
    [driftAdmin],
    false,
    true,
  );
};
