### Title
Default recovery mis-keys unfunded instant-withdraw receipts to `defaultRecoveryEpoch`, letting pre-default-epoch instant receipts claim at par and drain the recovery reserve - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault` records instant-withdraw receipts in two places: an epoch-agnostic global `pendingInstantWithdraws` / `instantWithdrawsRequests[user]`, and per-epoch buckets `instantWithdrawsRequestsByEpoch[user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]` (`IdleCreditVault.sol:366-374`). When a borrower default is finalized, `defaultPendingClaimBasis()` and `_claimDefaultedInstantWithdrawRequest()` assume every still-unfunded instant receipt belongs to `epochNumber`/`defaultRecoveryEpoch` — the same class of bug as the external report: data (the per-epoch receipt bucket) is fetched and applied without verifying that it actually corresponds to the receipt being settled, so a receipt "issued under a different epoch" is treated like an already-funded one, exactly like a CRL belonging to a different issuer certificate being accepted.

### Finding Description
The bug class of the external report is: *revocation data is used for validation without checking that it corresponds to the object being validated or is still current*. The vault analog lives in the default-finalization path:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the haircut basis only when `pendingInstantWithdraws != 0` (`IdleCreditVault.sol:644-648`). `pendingInstantWithdraws` is a global aggregate that survives across `stopEpoch` calls if `getInstantWithdrawFunds` was never executed for a running epoch (funding is a discretionary manager action, `IdleCDOEpochVariant.sol:558-570`). The per-epoch bucket, however, only counts receipts recorded under the *current* `epochNumber`.
- `finalizeDefaultRecovery` then computes `recoveryPrice = reserveAmount / totalBasis` and sets `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` (`IdleCreditVault.sol:679-696`). Any instant receipt created in an earlier epoch and left unfunded is excluded from `totalBasis`.
- On claim, `claimInstantWithdrawRequest` first tries `_claimDefaultedInstantWithdrawRequest`, which only clears `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (`IdleCreditVault.sol:842-855`). For a stale-epoch receipt that lookup returns 0, so execution falls through to `instantWithdrawsRequests[_user]`, burns the receipt, and pays the **full par amount** via `_transferFundedClaim` (`IdleCreditVault.sol:387-392`).

Because the stale receipt was never counted in `totalBasis`, its par payout is drawn from `defaultRecoveryReserve`, which was sized only for haircut-eligible claims. The result is identical in spirit to the reported bug: the contract validates a claim against epoch-keyed state that does not match the claim's actual issuance epoch — a receipt minted "under a previous epoch certificate" is honored as if it were fully funded.

### Impact Explanation
An attacker holding an unfunded instant-withdraw receipt from an epoch *prior* to the defaulted epoch receives a 100%-of-par payout from `defaultRecoveryReserve` instead of the `defaultRecoveryPrice` haircut applied to every other defaulted-epoch claimant. This directly steals from the shared recovery reserve: each such claim reduces the reserve below what finalized accounting assumed, so legitimate defaulted-epoch withdraw/instant claimants and post-default requesters are underpaid or their claims revert on insufficient reserve balance — i.e., theft plus partial insolvency of the recovery reserve, up to the total stale-receipt amount times `(1 - defaultRecoveryPrice)`.

### Likelihood Explanation
The preconditions are reachable with only unprivileged actions around honest privileged calls:

1. Instant withdrawals must be enabled on the pool (owner/manager configuration — allowed, they are honest).
2. The attacker (a KYC-passed tranche holder) calls `requestInstantWithdraw` during a running epoch.
3. The epoch ends without `getInstantWithdrawFunds` being called (or being called only partially — the code explicitly contemplates partial prefunding in `_defaultPrefundedInstantReserve`). `pendingInstantWithdraws` and the attacker's `instantWithdrawsRequests` carry into the next epoch untouched; nothing in `collectInstantWithdrawFunds`/epoch rollover clears them.
4. In a later epoch the borrower underfunds `stopEpoch` (borrower is honest but can legitimately fail to have funds — a normal credit default), `defaulted` is set, and `finalizeDefaultRecovery` runs with `defaultRecoveryEpoch` = later epoch.
5. The attacker calls `claimInstantWithdrawRequest`; the default-epoch lookup misses their stale receipt and they are paid at par from the reserve.

No malicious privileged role, oracle manipulation, or DoS is required. The only uncertainty I could not fully verify within this pass is whether `stopEpoch`/`startEpoch` hard-block while `pendingInstantWithdraws > 0`; the code's own comments ("partially prefunded instant requests") indicate a nonzero remainder at finalization is an expected state, and no path resets epoch-keyed instant claims on rollover.

### Recommendation
- In `finalizeDefaultRecovery`, include **all** unfunded instant receipts in the claim basis, not just `instantWithdrawClaimsByEpoch[epochNumber]` — e.g., track a global `instantWithdrawClaimsTotal` alongside `pendingInstantWithdraws`, or iterate/accumulate stale-epoch buckets, so `totalBasis` covers every receipt that `pendingInstantWithdraws != 0` triggers.
- In `_claimDefaultedInstantWithdrawRequest`, look up and clear the caller's receipts across all epochs with unsettled basis (or maintain a per-user aggregate of unfunded instant basis), instead of only `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`.
- Alternatively, enforce at `stopEpoch`/`startEpoch` that `pendingInstantWithdraws` is resolved (funded or cancelled) before the epoch can roll over, so instant receipts can never outlive their issuance epoch.

### Proof of Concept
Foundry fork outline (real USDC, deployed-style CDO + `IdleCreditVault`):

```solidity
// setup: KYC-attacker and victim hold AA tranches; instant withdraws enabled:
// cdoEpoch.setInstantWithdrawParams(instantDelay, apr, true)

// ---- Epoch 1 (running) ----
idleCDO.depositAA(victimAmount);          // victim
vm.prank(attacker);
idleCDO.depositAA(attackAmount);
cdoEpoch.startEpoch();

// attacker requests an instant withdraw; manager never calls getInstantWithdrawFunds
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(attackAmount * tranchePrice / 1e18, AA);
// assert(strategy.pendingInstantWithdraws() > 0)

// epoch ends, stop without funding instant queue -> pendingInstantWithdraws persists
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(newApr, 0);

// ---- Epoch 2: borrower defaults ----
cdoEpoch.startEpoch();
vm.warp(cdoEpoch.epochEndDate() + 1);
// borrower repays less than owed -> transferFrom in _stopEpoch fails -> _handleBorrowerDefault
deal(USDC, borrower, shortfall);
vm.prank(manager);
cdoEpoch.stopEpoch(newApr, 0);            // defaulted == true

// finalizeDefaultRecovery with partial recovery R < totalBasis
strategy.finalizeDefaultRecovery(recovered, recoverySource); // via CDO default-finalize flow
// assert: basis == pendingWithdraws + instantWithdrawClaimsByEpoch[epoch2]
//         -> attacker's epoch-1 receipt NOT included; defaultRecoveryPrice < 1e18

// attacker claims at PAR: _claimDefaultedInstantWithdrawRequest finds
// instantWithdrawsRequestsByEpoch[attacker][epoch2] == 0, falls through to par payout
uint256 balPre = usdc.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
assertEq(usdc.balanceOf(attacker) - balPre, attackReceiptFullPar); // no haircut!

// victim's defaulted-epoch claim now reverts/underpays: reserve drained below
// sum of haircut-eligible claims -> reserve insolvency
vm.prank(victim);
cdoEpoch.claimWithdrawRequest();          // receives less than claimBasis * defaultRecoveryPrice
```

The quantified loss equals `staleInstantReceipts * (1e18 - defaultRecoveryPrice) / 1e18`, taken directly from the recovery reserve that honest defaulted-epoch claimants were entitled to.

(Note: reproduction confidence is medium — it hinges on `stopEpoch` permitting rollover with `pendingInstantWithdraws > 0`, which the code structure strongly suggests but which should be confirmed by actually executing the fork PoC.)
