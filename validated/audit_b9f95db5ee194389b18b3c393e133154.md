### Title
Fee recipient's fees can be permanently frozen if the atomic protocol-fee transfer in `claimFees()` reverts due to a blacklisted `protocolFeeRecipient` - ([File: v3/src/core/FeeVault.sol])

### Summary
`FeeVault.claimFees()` bundles two independent ERC20 transfers—the vault fee recipient's fees and the protocol's fees—into a single atomic transaction. If the fee token (e.g., USDC) blacklists the `protocolFeeRecipient` address, the second `safeTransfer` reverts, causing the entire `claimFees()` call to revert and permanently blocking the legitimate fee recipient from claiming their own already-accrued, unrelated fees, exactly the same forced-push-transfer root cause described in the external GNS staking report.

### Finding Description
`claimFees()` is called by an ordinary (non-privileged) `feeRecipient` via `onlyFeeRecipient`: [1](#0-0) 

The flow is:
1. `feeCalculator.claimFees(balance)` computes and **effects** both `feeRecipientFees` and `protocolFees`, decrementing both accrual balances in `BaseFeeCalculator`: [2](#0-1) 
2. `FEE_TOKEN.safeTransfer(msg.sender, feeRecipientFees)` pushes the caller's own fees.
3. Unconditionally, if `protocolFees != 0`, `FEE_TOKEN.safeTransfer(protocolFeeRecipient, protocolFees)` is force-pushed in the **same transaction**.

Because steps 2 and 3 happen atomically in one call, a revert in step 3 unwinds the entire transaction — including the accrual decrements from step 1 and the fee recipient's own successful transfer in step 2. If the `FEE_TOKEN` is a blacklist-capable stablecoin (e.g., USDC) and `protocolFeeRecipient` becomes blacklisted (frozen by the issuer, sanctioned, or the contract is later flagged), `claimFees()` will revert for every future call, forever preventing the ordinary `feeRecipient` from claiming fees they are legitimately owed — even though nothing is wrong with the `feeRecipient` themselves.

This mirrors the reported GNS analog exactly: rewards for multiple parties are forced into one push-transfer transaction, so one recipient's incompatibility with the token (blacklist) blocks a completely unrelated, uninvolved user from harvesting their own legitimate claim. The interface itself flags the danger: `IFeeCalculator.claimFees` NatSpec states "Caller must perform the actual transfers to avoid permanent fee loss," yet `FeeVault.claimFees()` still performs both transfers unconditionally in one atomic call rather than using a pull/claim-balance pattern. Unlike `claimProtocolFees()` — which is a separate, independently callable function — there is no way for the `feeRecipient` to trigger only their own portion once `protocolFees != 0` and `protocolFeeRecipient` is blacklisted.

### Impact Explanation
The vault's designated `feeRecipient` — an ordinary, non-privileged party entitled to earned TVL/performance fees — can have their yield permanently frozen in the vault with no self-service recovery path once `protocolFeeRecipient` is blacklisted by the fee token. The only remedy is an admin calling `setProtocolFeeRecipient` (a `requiresAuth` action outside the fee recipient's control), which matches Immunefi's medium/high severity criteria for freezing of user funds/unclaimed yield without direct user recourse.

### Likelihood Explanation
Requires the fee token (e.g., USDC) to blacklist the `protocolFeeRecipient` address while `protocolFees > 0` is outstanding for the vault — a low-probability, third-party-driven event, consistent with the "Low likelihood" rating in the disclosed analog, but fully feasible given USDC's documented blacklist functionality and its use as a fee/numeraire token in Aera vaults.

### Recommendation
Decouple the two transfers so a failure in one cannot block the other: e.g., wrap the protocol-fee transfer in a try/catch (or use `trySafeTransfer`) that credits an internal `pendingProtocolFees` balance on failure and let the fee recipient's own transfer always complete; add a separate `claimPendingProtocolFees()` withdrawal path. Alternatively, always transfer `feeRecipientFees` to `msg.sender` first without conditioning the whole call's success on the protocol-fee leg, and let protocol fees accumulate for later, independent retrieval via `claimProtocolFees()`.

### Proof of Concept
1. Deploy a `FeeVault`-derived vault (e.g., `SingleDepositorVault`) with `FEE_TOKEN` = a mock USDC-like blacklistable ERC20, and a `BaseFeeCalculator`/`DelayedFeeCalculator` with `protocolFeeRecipient = P`.
2. Accrue fees for the vault such that both `vaultAccruals.accruedFees > 0` and `vaultAccruals.accruedProtocolFees > 0`, and fund the vault with enough `FEE_TOKEN` balance.
3. Blacklist `P` on the mock token (simulate `transfer` reverting when `to == P`).
4. As `feeRecipient`, call `claimFees()`.
5. Assert the call reverts (`Aera__ExecutionFailed`/SafeERC20 revert) even though `feeRecipientFees != 0` and the fee-recipient-bound transfer alone would have succeeded — demonstrating the fee recipient's legitimate fees remain permanently unclaimable while `P` stays blacklisted.

    function claimFees() external onlyFeeRecipient returns (uint256 feeRecipientFees, uint256 protocolFees) {
        address protocolFeeRecipient;

        // Interactions: claim the fees
        (feeRecipientFees, protocolFees, protocolFeeRecipient) =
            feeCalculator.claimFees(FEE_TOKEN.balanceOf(address(this)));

        // Requirements: check that the fee recipient has earned fees
        require(feeRecipientFees != 0, Aera__NoFeesToClaim());

        // Interactions: transfer the fees to the fee recipient
        FEE_TOKEN.safeTransfer(msg.sender, feeRecipientFees);
        // Log the fees claimed event
        emit FeesClaimed(msg.sender, feeRecipientFees);

        if (protocolFees != 0) {
            // Interactions: transfer the protocol fees to the protocol fee recipient
            FEE_TOKEN.safeTransfer(protocolFeeRecipient, protocolFees);
            // Log the protocol fees claimed event
            emit ProtocolFeesClaimed(protocolFeeRecipient, protocolFees);
        }
    }

    /// @inheritdoc IFeeCalculator
    function claimFees(uint256 feeTokenBalance) external virtual returns (uint256, uint256, address) {
        // Effects: hook called before claiming fees
        _beforeClaimFees();

        VaultAccruals storage vaultAccruals = _vaultAccruals[msg.sender];

        uint256 vaultEarnedFees = vaultAccruals.accruedFees;
        uint256 protocolEarnedFees = vaultAccruals.accruedProtocolFees;
        uint256 claimableProtocolFee = Math.min(feeTokenBalance, protocolEarnedFees);
        uint256 claimableVaultFee;
        unchecked {
            claimableVaultFee = Math.min(feeTokenBalance - claimableProtocolFee, vaultEarnedFees);
        }

        // Effects: update accrued fees
        unchecked {
            vaultAccruals.accruedProtocolFees = uint112(protocolEarnedFees - claimableProtocolFee);
            vaultAccruals.accruedFees = uint112(vaultEarnedFees - claimableVaultFee);
        }

        return (claimableVaultFee, claimableProtocolFee, protocolFeeRecipient);
    }
