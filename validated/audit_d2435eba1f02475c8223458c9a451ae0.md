### Title
Fee-on-transfer underlyings inflate credit-vault NAV because `IdleCreditVault.deposit` mints strategy tokens for the requested amount, not the received amount - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCDOCreditVault._deposit` correctly measures the underlying actually received (`balanceAfter - balanceBefore`) when minting tranche shares, but then forwards the *requested* `_amount` to `IIdleCDOStrategy(strategy).deposit(_amount)`. `IdleCreditVault.deposit` performs `safeTransferFrom` for `_amount` and unconditionally `_mint(msg.sender, _amount)` at a 1:1 rate. With a fee-on-transfer/deflationary token, the strategy receives `_amount - fee` but mints `_amount` strategy tokens to the CDO. Since `getContractValue` prices the vault as `strategyTokenBalance + tokenBalance - unclaimedFees` (strategy tokens are assumed 1:1 with underlyings), every such deposit permanently inflates NAV by the fee amount while real backing does not exist.

### Finding Description
In `contracts/IdleCDOCreditVault.sol:203-211`:

```solidity
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
// mint tranche tokens according to the current tranche price
_minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
...
// direct deposit in the strategy
IIdleCDOStrategy(strategy).deposit(_amount);   // <-- uses requested amount, not received
```

The depositor is fairly credited — shares are minted on the *received* delta (`_contractTokenBalance(_token) - _preBal`). However, the strategy call uses the unadjusted `_amount`.

In `contracts/strategies/idle/IdleCreditVault.sol:596-617`:

```solidity
function deposit(uint256 _amount) external virtual override returns (uint256) {
  _onlyIdleCDO();
  if (_amount > 0) {
    underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
    _mint(msg.sender, _amount);              // <-- mints requested amount, not received
  }
  ...
  totEpochDeposits += _amount;               // <-- epoch deposit counter also overstated
  return _amount;
}
```

The strategy mints `_amount` strategy tokens to the CDO even though only `_amount - fee` underlying arrived. There is no `balanceBefore`/`balanceAfter` delta check anywhere in this path.

Broken invariant — solvency: `getContractValue()` (`contracts/IdleCDOCreditVault.sol:125-128`) returns `_contractTokenBalance(strategyToken) + _contractTokenBalance(token) - unclaimedFees`, treating each strategy token as one unit of underlying. After a fee-on-transfer deposit of `A` with fee `f`:

- Strategy holds `A - f` underlying but `A` strategy tokens are outstanding to the CDO.
- `lastNAVAA`/`lastNAVBB` only grew by `A - f` (correct shares minted), yet the CDO's `strategyToken` balance grew by `A`.
- The `f` discrepancy is phantom NAV: it is attributed as a gain on the next `_updateAccounting()` (nav > lastNAV), accruing `unclaimedFees` and tranche-price gains on value that does not exist.

This propagates into the epoch flow: `totEpochDeposits` is overstated by `f`, and funds pushed to the borrower at `startEpoch` via `sendInterestAndDeposits`/funding calls are sized off the inflated strategy-token accounting, so the borrower can be credited (or requests funded) for more underlying than the strategy actually holds — a direct shortfall that materializes as a loss at `stopEpoch`/`stopEpochWithDuration` and is socialized through the BB-first waterfall.

No existing guard stops this: the skim logic only isolates unsolicited donations to the CDO, `_checkDefault`/Default reverts only react to NAV decreases (here NAV *increases*), and there is no assertion that strategy tokens minted equal underlying received.

### Impact Explanation
Every deposit made while the underlying charges a transfer fee inflates vault NAV by the fee amount and mints unbacked strategy-token claims to the CDO. The phantom NAV (i) accrues real `unclaimedFees` for the feeReceiver, (ii) inflates tranche prices/virtualPrice so subsequent depositors mint fewer shares per unit of real value and earlier holders can withdraw against non-existent backing, and (iii) overstates `totEpochDeposits`, letting the borrower/epoch funding draw more than the strategy holds. When the shortfall is realized (redeem/funding fails or a loss epoch is crystallized), the deficit is socialized through `_updateAccounting`'s BB-first loss waterfall — BB depositors absorb a loss that belongs to no real lending activity. Loss per deposit equals the token's transfer fee on `_amount`; repeatable per deposit.

### Likelihood Explanation
Requires the vault's `token` to be fee-on-transfer or deflationary. Mainnet Pareto credit vaults use USDC-class stables where no fee is charged today, but the vault is `initialize`d with an arbitrary `_guardedToken` and the code comment explicitly acknowledges the pattern it fails to apply. USDT supports fee-on-transfer and USDC is upgradeable, so this can activate without any code change. Any unprivileged depositor can trigger it via `depositAA`/`depositBB`; no privileged misbehavior needed. Likelihood is conditional on token fee activation — hence Medium — but once active, every deposit deterministically inflates NAV.

### Recommendation
In `IdleCreditVault.deposit`, mint strategy tokens based on the actually received amount:

```solidity
if (_amount > 0) {
  uint256 balBefore = underlyingToken.balanceOf(address(this));
  underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
  uint256 received = underlyingToken.balanceOf(address(this)) - balBefore;
  _mint(msg.sender, received);
  ...
  totEpochDeposits += received;
  return received;
}
```

Correspondingly, `IdleCDOCreditVault._deposit` should use the return value of `strategy.deposit(...)` (or the strategy-token balance delta) for any downstream accounting, and similarly `finalizeDefaultRecovery` should pull recovery based on received-delta when `_recoveredAmount` is transferred. If fee-on-transfer tokens are out of scope by policy, add an explicit check/revert when the received amount differs from `_amount` rather than silently mis-minting.

### Proof of Concept
Foundry fork PoC (buffer epoch, any mode):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";

contract FeeToken is ERC20 {
  uint256 public constant FEE_BPS = 100; // 1%
  constructor() ERC20("FEE", "FEE") {}
  function mint(address to, uint256 a) external { _mint(to, a); }
  function _transfer(address f, address t, uint256 a) internal override {
    uint256 fee = a * FEE_BPS / 10_000;
    super._transfer(f, t, a - fee);
    super._transfer(f, address(0xdead), fee);
  }
}

contract FeeOnTransferPoC is Test {
  function test_navInflation() public {
    FeeToken tok = new FeeToken();
    // deploy + initialize IdleCDOCreditVault with token=tok, strategy=IdleCreditVault
    // (idleCDO wired to the CDO; borrower/manager honest)
    address alice = address(0xA11CE);
    tok.mint(alice, 1_000e18);
    vm.startPrank(alice);
    tok.approve(address(cdo), type(uint256).max);
    cdo.depositAA(100e18);
    vm.stopPrank();

    // Strategy received 99e18 but minted 100e18 strategy tokens to the CDO
    assertEq(strategy.balanceOf(address(cdo)), 100e18);
    assertEq(tok.balanceOf(address(strategy)), 99e18);

    // getContractValue counts strategy tokens 1:1 => NAV inflated by 1e18
    assertEq(cdo.getContractValue(), 100e18);   // reported NAV
    // real redeemable backing is only 99e18 -> 1e18 phantom NAV per deposit
  }
}
```

Result: `cdo.getContractValue() == 100e18` while total underlying held across CDO+strategy is `99e18`. Repeating deposits compounds the phantom NAV; the first realized funding/withdrawal in excess of true backing either reverts (temporary freezing of the tail claim) or socializes the `f`-per-deposit shortfall onto BB tranche holders via the loss waterfall.
