### Title
`staking_contract::distribute_internal` can be permanently DoS'd by any single shareholder opting out of direct coin transfers, freezing all commission/stake distributions - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`distribute_internal` iterates over every recipient in the `distribution_pool` in a single transaction and calls `aptos_account::deposit_coins` for each one. `deposit_coins` aborts if the recipient's account is not registered for `AptosCoin` and has opted out of direct coin transfers via `set_allow_direct_coin_transfers(false)`. Since the loop pays out all shareholders atomically before returning, one delegator/staker (or the operator's beneficiary) who disables direct transfers can make `distribute()` abort every time it is called, permanently blocking commission and stake payouts to every other party sharing that staking contract — directly analogous to the `transfer()`-gas-limit DoS in the external report, where one recipient's inability to receive funds locks funds for everyone.

### Finding Description
`distribute_internal` withdraws the pool's total withdrawable stake, then loops `while (distribution_pool.shareholders_count() > 0)`, redeeming each shareholder's shares and calling `aptos_account::deposit_coins(recipient, ...)`: [2](#0-1) 

`aptos_account::deposit_coins` will `abort` with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient is not yet registered for `AptosCoin` and `can_receive_direct_coin_transfers(to)` is false (i.e., the account previously called `set_allow_direct_coin_transfers(account, false)`), which is a fully unprivileged, permissionless action any account can take on itself: [1](#0-0) [3](#0-2) 

Because the withdrawal from the stake pool (`stake::withdraw_with_cap`) and the shares redemption (`distribution_pool.redeem_shares`) happen *before* the failing deposit, and Move transactions revert atomically on abort, the entire `distribute` call — and therefore every other legitimate recipient's payout in the same distribution pool — fails. Since `distribution_pool.shareholders_count()` and the pending shares are not modifiable except by successfully completing this loop, there is no way to skip the blocking shareholder: `distribute()` will abort every single time it is invoked, for anyone, until that shareholder's coin-store state changes (which they, as an adversary, control and will not do).

Note that the developers were aware of a related risk for vesting beneficiaries specifically — `vesting::set_beneficiary` explicitly calls `assert_account_is_registered_for_apt(new_beneficiary)` "so distribute() wouldn't fail and block all other accounts from receiving APT" — but this check is registration-only and does not cover the `can_receive_direct_coin_transfers` opt-out flag, and more importantly there is no equivalent protection at all in `staking_contract.move`'s `distribute_internal`/`add_distribution` path for ordinary stakers, switched-out operators, or the current operator when their address ends up in the distribution pool.

### Impact Explanation
Any staker's principal, any operator's commission, and (via `vesting::withdraw_stake` which calls `staking_contract::distribute`) any vesting shareholder's unlocked/vested APT routed through a `staking_contract` can become permanently un-distributable. A single unprivileged party (the staker themselves, the operator, or a beneficiary set via `set_beneficiary_for_operator`) can call `aptos_account::set_allow_direct_coin_transfers(&signer, false)` on their own address before their pending distribution amount is redeemed, then indefinitely block `distribute()`/`unlock_stake()`-triggered distribution for every other shareholder in that same `StakingContract`'s `distribution_pool` (e.g. when `switch_operator` leaves the old operator's unpaid commission in the pool alongside the staker's principal). This is a permanent, non-recoverable trap of stake/commission value for all co-shareholders, satisfying the "Permanent lock or non-recoverable loss of claim rights" and "Operator commission ... corruption that... traps value" impact categories.

### Likelihood Explanation
Likelihood is high: `set_allow_direct_coin_transfers` is a standard, fully permissionless, unprivileged entry function available to any account, requiring no special role, and can be invoked at any time, including after already being a shareholder/operator/beneficiary in an active `staking_contract`. No coordination with the staker or operator is needed — the blocking account only needs to be a recipient in the `distribution_pool` (attainable simply by being the staker, the current/former operator, or an operator's beneficiary).

### Recommendation
In `distribute_internal`, do not let a single failing recipient revert the whole distribution: either (a) pre-validate that all pending recipients satisfy `aptos_account::can_receive_direct_coin_transfers`/registration before withdrawing and redeeming shares and refuse only that recipient's payout (leaving their shares un-redeemed and retryable), or (b) wrap the deposit in a way that on failure re-credits the shares back to the pool and continues distributing to the remaining shareholders instead of aborting the transaction, mirroring the guard already present in `vesting::set_beneficiary`.

### Proof of Concept
1. Staker `S` creates a `staking_contract` with operator `O`, commission 10% (`staking_contract::create_staking_contract`).
2. `O` calls `aptos_account::set_allow_direct_coin_transfers(&O_signer, false)` (unprivileged, self-only call), and does not register for `AptosCoin` beforehand (or does so before opting out, since the check is `!coin::is_account_registered`, which is true right after account creation without `coin::register`).
3. Stake pool earns rewards; `S` calls `staking_contract::unlock_stake`/`request_commission`, populating `O`'s share in `distribution_pool`.
4. Lockup expires; anyone calls `staking_contract::distribute(S, O)`.
5. `distribute_internal` withdraws the inactive/pending_inactive coins, redeems `O`'s shares, and calls `aptos_account::deposit_coins(O, ...)`, which aborts at `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` because `O` opted out and is unregistered — reverting the entire transaction.
6. Every subsequent call to `distribute` (by `S`, `O`, or anyone) fails identically, permanently trapping `S`'s own principal/rewards (which share the same `distribution_pool`) alongside `O`'s commission, since none of them can be paid out without the loop completing successfully.

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
