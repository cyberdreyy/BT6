### Title
Service containers in Concrete-mode steps pods share the writable helper binary volume with the build container, allowing an attacker-controlled service to tamper with the trusted helper before it executes - (File: executors/kubernetes/steps_pod.go)

### Summary
`stepsServiceContainers`/`stepsServiceContainer` mount the exact same `stepsVolumeMounts()` set — including the `scripts` emptyDir that holds the bootstrapped `gitlab-runner-helper` binary later exec'd by the build container — onto every user-declared service container. Because emptyDir volumes are read-write to every container that mounts them, an attacker who controls a service image/command (a normal CI pipeline capability) can overwrite the helper binary at `s.stepsRunnerBinaryPath()` before the build container's `steps serve` command executes it.

### Finding Description
`buildStepsBootstrapInitContainer` (executors/kubernetes/steps_pod.go:121-147) copies `gitlab-runner-helper` into the `scripts` emptyDir at `s.stepsRunnerBinaryPath()`, and the build container's command is overridden to `<path> steps serve` (steps_pod.go:314). Both the build container and every service container returned by `stepsServiceContainers` (steps_pod.go:363-383) get their volume mounts from the same `stepsVolumeMounts()` helper (steps_pod.go:349-350 and steps_pod.go:438), which mounts the `scripts` volume at `s.scriptsDir()` (steps_pod.go:532-538) without any read-only flag.

All containers in a pod (build + services) start once init containers finish; there is no ordering guarantee that the build container reads/execs the helper binary before an attacker-controlled service container's process writes into the shared `scripts` mount. A pipeline author fully controls `services:` image, command, and args (`getCommandAndArgs`, steps_pod.go:424), so they can specify a service whose entrypoint replaces `gitlab-runner-helper` in the shared `scripts` directory with attacker-supplied content before or during the race window when the build container invokes it. Since the build container blindly execs whatever is at that fixed path once the init container reports success, there is no re-validation (e.g., no checksum/signature check, no immutability re-assertion) of the helper binary's origin between bootstrap and build-phase execution.

Existing protections (`verifyAllowedImages`, security contexts) do not address this: they gate what images can run, not what those images can write to a volume mount shared with the container that later trusts the file. There's no read-only mount, no per-container private copy, and no re-verification.

### Impact Explanation
An attacker who already controls a service definition (a normal CI capability) can pivot into executing arbitrary code as the build container's identity/security context instead of the service container's. Since the build container may be configured (via `BuildContainerSecurityContext`) with different privileges, UID/GID, or capabilities than `ServiceContainerSecurityContext`, this is a genuine stronger-context execution / build-phase hijack: the attacker's payload runs disguised as the trusted `gitlab-runner-helper`, driving the `steps serve` process that manages the job's step execution, environment injection, and outcome reporting to GitLab.

### Likelihood Explanation
This requires only an unprivileged pipeline author defining a service in `.gitlab-ci.yml`/`config.toml` service list with a custom image/entrypoint — no cluster-admin or infrastructure compromise needed. It is a timing race (service must overwrite before/while build container execs the helper), but the window is not negligible: init container completion and the start of the build/service containers are not synchronized precisely, and the service entrypoint runs immediately, well before any user job step begins on the build side. It's repeatable across runs because the volume mount configuration is deterministic for every steps job with any declared service.

### Recommendation
Mount the `scripts` volume read-only in service containers (or omit it from `stepsServiceContainer`'s volume mounts entirely, since services do not need the helper binary), so only the build container can write/read the bootstrapped helper. Alternatively, give the build container its own private, non-shared location for the helper binary that is not mounted into any service container, and/or verify the helper binary's checksum/signature immediately before exec in `steps serve`.

### Proof of Concept
Go integration test plan for `executors/kubernetes/steps_pod_test.go`:
1. Call `stepsServiceContainers` with a service in `s.options.Services` and assert that the returned `api.Container.VolumeMounts` for the `scripts` volume either does not exist or has `ReadOnly: true`. This assertion should fail against current code (mount exists and is writable), demonstrating the shared writable mount.
2. As an e2e PoC: configure a job with one service whose image's entrypoint is a script that busy-loops writing a malicious payload to `<scriptsDir>/gitlab-runner-helper`, and a build image whose steps invoke normal step-runner behavior. Observe that on some fraction of runs, the build container's `steps serve` process executes attacker-controlled code (e.g., writes a marker file only the malicious payload knows, or crashes with attacker-chosen exit code) instead of the legitimate helper, confirming cross-container trust violation via the shared `scripts` emptyDir.
