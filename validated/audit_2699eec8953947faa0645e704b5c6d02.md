Based on analysis of the codebase, I found a valid analog in the multisig-factory contract, which contains a variant of this bug that is worse than pure griefing — it results in permanent loss of the victim's attached NEAR deposit, not just a reverted transaction.

### Title
Frontrunning `create()` on a colliding multisig name permanently strands the victim's attached deposit - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` lets any caller pick an arbitrary `name`, which is concatenated with the factory's own account id to derive the new multisig sub-account (`{name}.{current_account_id}`), and immediately dispatches a single chained promise (`create_account → deploy_contract → transfer → function_call("new")`) funded by the caller's attached deposit. Unlike its sibling factories (`staking-pool-factory`, `lockup-factory`), this contract has no callback to detect promise failure and refund the depositor.

### Finding Description
`create` derives the target account id purely from caller-supplied input: [1](#0-0) 

```rust
pub fn create(&mut self, name: AccountId, members: Vec<MultisigMember>, num_confirmations: u64) -> Promise {
    let account_id = format!("{}.{}", name, env::current_account_id());
    Promise::new(account_id)
        .create_account()
        .deploy_contract(CODE.to_vec())
        .transfer(env::attached_deposit())
        .function_call(b"new".to_vec(), ..., 0, env::prepaid_gas() - CREATE_CALL_GAS)
}
```

Any two callers can race with the same `name`. Because NEAR sub-account creation for `name.<factory>` can only be issued by the factory's own outgoing receipt, whichever `create(name, ...)` call is processed first by the factory succeeds and creates the account; the second caller's chained receipt fails at the `create_account` action because the account already exists. This mirrors exactly the account-id-collision/frontrunning bug class in the report, where a user-chosen identifier is trusted without a uniqueness reservation prior to dispatch.

The critical difference from the reference bug is what happens to the *loser's* attached deposit. In `staking-pool-factory` and `lockup-factory`, the equivalent creation flow is followed by an explicit `on_*_create` callback that checks `is_promise_success()` and manually refunds the depositor on failure: [2](#0-1) [3](#0-2) 

`multisig-factory` has no such callback at all — `create` is the entire public surface of the contract: [4](#0-3) 

Since the attached deposit is credited to the factory contract's own balance the moment the `#[payable]` call executes, and the outgoing `create_account`/`transfer` receipt fails atomically with no refund logic invoked, the deposit remains locked inside the factory's balance with no `withdraw`-style method to ever move it back out.

### Impact Explanation
This breaks the custody binding "value debited from the user equals value delivered to the intended destination (the new multisig, or back to the user on failure)". When a name collision occurs — whether from a benign concurrent submission or a deliberate frontrun by an unprivileged attacker who simply resubmits the same `name` with a lower nonce/higher gas price — the losing caller's attached NEAR (which must be non-trivial, since it needs to cover multisig account storage and the wasm deploy) is permanently stuck in the factory contract with no recovery path. This matches the "funds permanently frozen" Critical impact category.

### Likelihood Explanation
Exploitation requires no privileges, no key compromise, and no profit motive beyond griefing intent — any observer of the public mempool (or even an unrelated user who happens to pick the same `name`, e.g. a common label like `"team"` or `"treasury"`) can trigger it. It is not conditioned on validator or node behavior, redeploys, or foundation/multisig involvement, only on submitting a `create` call with a colliding `name` before the victim's call executes.

### Recommendation
Add an `on_create` callback analogous to `on_lockup_create`/`on_staking_pool_create`: chain `.then(ext_self::on_create(predecessor_account_id, attached_deposit, account_id, ...))`, check `is_promise_success()`, and refund the attached deposit to the predecessor if the account/deploy/init failed. Additionally, consider deriving the sub-account name deterministically or reserving it (e.g., an `UnorderedSet` of in-flight names, as `staking-pool-factory` does with `staking_pool_account_ids`) to reject collisions synchronously instead of relying on the cross-shard receipt to fail.

### Proof of Concept
1. Alice calls `create(name="team", members=[...], num_confirmations=1)` with attached deposit `D` NEAR.
2. Bob (attacker/incidental colliding user) submits `create(name="team", members=[bob_only], num_confirmations=1)` with attached deposit `D'` and it lands first in the same block/shard ordering.
3. Bob's chained receipt succeeds: `team.multisig-factory` is created, deployed, and initialized with Bob's members.
4. Alice's chained receipt's `create_account` action fails because `team.multisig-factory` already exists; the whole receipt (`create_account`, `deploy_contract`, `transfer`, `function_call`) fails atomically.
5. Because `MultisigFactory` has no callback, Alice's deposit `D`, already credited into the factory's balance when her `#[payable] create` call executed, is never returned — it is permanently unreachable, since the contract exposes no method to withdraw or reallocate it.

    /// Callback after a staking pool was created.

        &mut self,

        let staking_pool_created = is_promise_success();

                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids

                format!(

                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );

        }
