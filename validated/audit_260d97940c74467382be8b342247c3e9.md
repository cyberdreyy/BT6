### Title
Claimed instant-withdraw receipts are never removed from `instantWithdrawClaimsByEpoch`, corrupting default-recovery basis and prefunded-reserve accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears `instantWithdrawsRequests[_user]` but never decrements `instantWithdrawClaimsByEpoch[epoch]` or the per-user per-epoch entry `instantWithdrawsRequestsByEpoch[_user][epoch]`. Those per-epoch aggregates are only decremented inside the default-recovery path (`_claimDefaultedInstantWithdrawRequest`). As a result, once an instant receipt is funded and claimed, its basis remains readable — an analog of a buffer over-read: later accounting reads stale, already-consumed receipt data as if it were still live. `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` both over-read this stale entry, inflating `totalBasis` and counting already-paid-out underlyings as phantom recovery reserve.

### Finding Description
The buffer over-read in `IMA_ADPCM_nibble` reads past the end of valid sample data, treating stale/out-of-bounds bytes as real input. The analog here is per-epoch claim bookkeeping that keeps "reading" receipt basis after it has been consumed:

- `requestInstantWithdraw` increments `instantWithdrawClaimsByEpoch[currentEpoch]` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (IdleCreditVault.sol:366-374).
- `claimInstantWithdrawRequest` pays the user but only zeroes `instantWithdrawsRequests[_user]`; neither `instantWithdrawClaimsByEpoch` nor `instantWithdrawsRequestsByEpoch` is cleared (IdleCreditVault.sol:380-393). The only cleanup is `_claimDefaultedInstantWithdrawRequest`, which runs exclusively after default finalization (IdleCreditVault.sol:842-856).
- On default, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the haircut basis whenever `pendingInstantWithdraws != 0` (IdleCreditVault.sol:644-649), and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying already held for those claims (IdleCreditVault.sol:716-723).

Attack sequence (all unprivileged, single epoch, running phase, instant-withdraw mode i.e. `lastEpochApr > unscaledApr + instantWithdrawAprDelta`):

1. Attacker (KYC'd AA holder) calls `requestWithdraw`, takes the instant path; `instantWithdrawClaimsByEpoch[N] = a`, `pendingInstantWithdraws = a`.
2. Honest manager sequences `getInstantWithdrawFunds`/`collectInstantWithdrawFunds(a)` — `pendingInstantWithdraws = 0`, strategy holds `a` underlying.
3. Attacker calls `claimInstantWithdrawRequest` and receives `a`. Stale state: `instantWithdrawClaimsByEpoch[N]` still `= a`, `instantWithdrawsRequestsByEpoch[attacker][N]` still `= a`.
4. Any user requests a new instant withdraw `b` in the same epoch: `instantWithdrawClaimsByEpoch[N] = a + b`, `pendingInstantWithdraws = b`.
5. Borrower defaults (honest borrower; no funds returned). `finalizeDefaultRecovery` computes `pendingBasis += a + b` (over-read of `a`) and `prefundedReserve = (a + b) - b = a` — phantom, because `a` was already transferred out. `defaultRecoveryReserve` and `defaultRecoveryPrice` are set from `reserveAmount = _recoveredAmount + a`, while the real balance is `a` short.

### Impact Explanation
Two correlated harms, both meeting the acceptance bar:

- Recovery dilution: `recoveryPrice = reserveAmount / totalBasis` is computed over a basis inflated by `a` and a reserve inflated by phantom `a`. Every defaulted-epoch claimant (normal, APR0, instant) and active LP receives a distorted recovery ratio; `activeFinalNAV` minted/burned to the CDO is likewise mispriced, corrupting AA/BB tranche prices set by `_forceUpdateAccounting`.
- Permanent claim freeze: `defaultRecoveryReserve` records `a` more than the contract holds. When claimants drain the reserve via `_transferDefaultRecovery`, the last ~`a` of claims revert on `underlyingToken.safeTransfer` (insufficient balance), permanently freezing that portion of unclaimed recovery. Quantified loss: up to the full amount of any instant receipt funded and claimed earlier in the defaulted epoch.

### Likelihood Explanation
Requires an epoch in which (i) an instant withdraw is funded and claimed, (ii) a further instant request is opened in the same epoch, and (iii) the borrower defaults before epoch end. Instant mode activates only on an APR decrease exceeding `instantWithdrawAprDelta`, and same-epoch pre-funding plus default is a narrow window, so likelihood is low-to-moderate. No privileged misbehavior is needed: manager, borrower, guardian and owner act honestly; only unprivileged deposit/withdraw/claim ordering is required. Existing guards do not stop it: `_transferFundedClaim`'s reserve check protects the reserve from funded claims, not the reserve's own inflation, and no path clears `instantWithdrawClaimsByEpoch` on a normal claim.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch receipt data symmetrically with the default path: track the request epoch per user (e.g. `lastInstantWithdrawRequest` or iterate the user's per-epoch entry), decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, so `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` never read consumed basis. Alternatively, derive the prefunded reserve from actual underlying balance attributable to instant claims rather than from the cumulative claims-by-epoch counter.

### Proof of Concept
Foundry fork PoC (against the existing `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testClaimedInstantReceiptOverReadCorruptsRecovery() external {
    // Setup: instant withdraw mode (lastEpochApr > unscaledApr + delta)
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    // manager lowers APR so instant path is enabled
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // forces delta

    uint256 N = IdleCreditVault(address(strategy)).epochNumber();

    // 1) Attacker instant-withdraws `a` and gets funded + claimed in epoch N
    uint256 a = cdoEpoch.requestWithdraw(AA bal / 2, address(AAtranche));
    // CDO collects instant funds -> pendingInstantWithdraws = 0, strategy holds `a`
    _collectInstantFunds(a);
    cdoEpoch.claimInstantWithdrawRequest();

    // stale: never cleared
    assertEq(IdleCreditVault(address(strategy)).instantWithdrawClaimsByEpoch(N), a);

    // 2) Second instant request `b` in same epoch
    uint256 b = cdoEpoch.requestWithdraw(remaining, address(AAtranche));
    assertEq(IdleCreditVault(address(strategy)).instantWithdrawClaimsByEpoch(N), a + b);
    assertEq(IdleCreditVault(address(strategy)).pendingInstantWithdraws(), b);

    // 3) Borrower defaults; guardian/manager finalize recovery with R recovered
    _handleBorrowerDefault();
    uint256 R = 100 * ONE_SCALE;
    deal(defaultUnderlying, recoverySource, R);
    cdoEpoch.finalizeDefaultRecovery(R, recoverySource);

    // basis includes already-claimed `a`; prefunded reserve counts phantom `a`
    // defaultRecoveryReserve = R + a > actual balance (R)
    assertGt(
        IdleCreditVault(address(strategy)).defaultRecoveryReserve(),
        underlying.balanceOf(address(strategy))
    );

    // 4) Last claimants' claims revert -> permanent freeze
    vm.expectRevert(); // ERC20 insufficient balance on safeTransfer
    cdoEpoch.claimWithdrawRequest();
}
```

Note: I could not fully trace `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` call sites in `IdleCDOEpochVariant` within the available context, so the exact CDO-side helper that prefunds same-epoch instant claims should be confirmed during PoC implementation; the strategy-side stale-state defect (missing decrement on claim at IdleCreditVault.sol:387-392 vs. the decrement at line 853) is confirmed directly from the code.
