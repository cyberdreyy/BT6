### Title
Removed multisig members retain confirmation power via stale entries in `confirmations`, allowing requests to execute below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
The multisig contract's `confirm` method counts a request as approved once the size of its stored `confirmations` set reaches `num_confirmations`, but `delete_member` never purges a removed member's confirmation entries from requests that member merely *confirmed* (as opposed to *created*). This produces the exact TOCTOU-class divergence described in the reference report — a recorded/checked authorization value (confirmations counted) diverges from the current, live-authorized state (live members) — letting a request execute even though fewer *currently valid* members actually approved it than `num_confirmations` requires.

### Finding Description
`confirm()` determines whether a request has reached quorum purely by comparing the size of the stored confirmation set to `num_confirmations`: [1](#0-0) 

Confirmer identity is tracked as a serialized `MultisigMember` string inserted into `self.confirmations[request_id]`. `delete_member`, however, only scrubs requests *created* by the removed member — it does not scan `self.confirmations` for other requests where the removed member appears merely as a confirmer: [2](#0-1) 

Because `remove_request`/`delete_member` never iterate over `self.confirmations` values to strip a removed member's identity string from other requests' confirmation sets, a confirmation recorded while a member was valid is permanently retained in the count even after that member is removed via a `DeleteMember` action. `current_member()` (used to reject non-members from calling `confirm`) is only checked for the *caller* of `confirm`, not retroactively for confirmations already stored: [3](#0-2) 

This breaks the intended custody binding: `confirmations.len() >= num_confirmations` is supposed to be equivalent to "at least `num_confirmations` *currently valid* members approved this request," but after a member removal these two values diverge — the recorded count can meet threshold while the number of live, currently-valid approving members is strictly lower.

### Impact Explanation
This matches the Critical impact category "a multisig request executed below threshold." A pending high-value request (e.g. `Transfer`, `AddKey`, or `FunctionCall`) can execute with fewer live approvals than the multisig's configured `num_confirmations`, defeating the core security guarantee of the multisig (that a compromised/removed signer's authority is revoked). Funds or privileged actions (adding a full-access key, transferring NEAR) can move under a threshold that was never truly met by currently trusted members.

### Likelihood Explanation
The precondition is a normal, legitimate multisig operation: a member is removed (e.g., due to suspected key compromise, an employee leaving, or key rotation) after having already confirmed one or more still-pending requests. This is an ordinary lifecycle event for multisig wallets, not a contrived edge case, and any of the remaining/former members (or an actor colluding with a subsequently removed one) can benefit from the stale confirmation without needing any new privilege — they simply need `num_confirmations - 1` genuinely-current confirmations plus one stale one left over from before a removal.

### Recommendation
When executing `DeleteMember`, iterate all entries in `self.confirmations` and strip the removed member's identity string from every set (not just requests the member created), and re-check whether any request now falls below quorum requirements. Alternatively, re-validate at `confirm()`/execution time that every entry in `confirmations` still corresponds to a current member of `self.members` before comparing the set's length to `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. `A` calls `add_request(R)` for a `Transfer` to an attacker-controlled account (creator is not automatically a confirmer since `add_request` — not `add_request_and_confirm` — is used).
3. `B` calls `confirm(R)` → `confirmations[R] = {B}`, count = 1 < 3.
4. `C` calls `confirm(R)` → `confirmations[R] = {B, C}`, count = 2 < 3.
5. Via a separate, legitimately-approved multisig request, `C` is removed with `DeleteMember { member: C }` (see `execute_request` / `delete_member`, `multisig2/src/lib.rs:239-241` and `356-379`). Because `R` was not *created* by `C`, `delete_member`'s cleanup loop (lines 361-371) does not touch `confirmations[R]`, so `confirmations[R]` still equals `{B, C}` even though `C` is no longer in `self.members`.
6. `D` (a current, valid member) calls `confirm(R)`. In `confirm()` (line 304), `confirmations.len() as u32 + 1 = 3 >= self.num_confirmations (3)` is true, so `execute_request(R)` runs and the transfer executes.
7. Result: the transfer executed with confirmations from `B`, stale `C` (no longer a member), and `D` — only 2 live, currently-valid members actually approved it, one short of the configured 3-of-4 threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn current_member(&self) -> Option<MultisigMember> {
        let member = if env::current_account_id() == env::predecessor_account_id() {
            MultisigMember::AccessKey {
                public_key: env::signer_account_pk()
                    .try_into()
                    .unwrap_or_else(|_| env::panic_str("Failed to deserialize public key")),
            }

            MultisigMember::Account {
                account_id: env::predecessor_account_id(),
            }
        };
        if self.members.contains(&member) {
            Some(member)
        } else {
            None
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
