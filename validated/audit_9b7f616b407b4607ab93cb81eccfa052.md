### Title
Duplicate tenure-change block sneaks past v1's global-only `DuplicateBlockFound` check where v2 would reject it - (File: stacks-signer/src/chainstate/v1.rs, stacks-signer/src/chainstate/v2.rs)

### Summary
The external report's bug class is an inconsistency between two sibling entities that are supposed to enforce the same guarantee, where one entity's protective check is weaker/absent, letting an attacker route around it through the weaker path. The direct analog in this repo is the tenure-change duplicate-block guard `validate_tenure_change_payload`, which exists in both `stacks-signer/src/chainstate/v1.rs` and `stacks-signer/src/chainstate/v2.rs` but uses a different "already accepted" test in each version: v1 only counts **globally accepted** blocks, while v2 counts **locally or globally accepted** blocks. This mirrors the Footium case of two contracts implementing the "same" protection with different completeness, letting a bad actor exploit the weaker path.

### Finding Description
Per `docs/signer-flows.md:425-437`, the duplicate-tenure-start check runs only once, at proposal time, inside `check_proposal`/`validate_tenure_change_payload`, and is never re-run at validate-ok or at signing time. Critically, the two protocol versions differ in what state they consult when deciding "have we already accepted a block starting this tenure":
- v1's `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:319-326`, called from `check_proposal`) relies on `confirms_latest_block_in_same_tenure`/`get_tenure_last_block_info`-style helpers that, per the doc, use `get_last_globally_accepted_block` for the duplicate-tenure test — i.e., a block that other signers have only **locally** accepted (pre-committed / signed by this signer but not yet confirmed by the node) does not count as "already accepted" for a v1 signer.
- v2's `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v2.rs:176-184`) instead uses `get_last_signed_block`, which counts **both locally and globally accepted** blocks.

Because this check runs exactly once, at proposal arrival, and is *not* re-checked at `handle_block_validate_ok` or at the pre-commit threshold moment (per the doc's explicit statement that "the duplicate check never runs again"), a v1 signer can be induced to treat a second tenure-start block for the same tenure as fresh/valid at proposal time, purely because the first tenure-start block has only been locally (not yet globally) accepted. The only later backstop is the generic "signed conflicts at height ≥ h" guard in the pre-commit/signing flow (`signer.rs` section 5 in the doc, `get_signed_conflicts`), which is a different, height-based mechanism, not the tenure-scoped `DuplicateBlockFound` guard.

This creates the same asymmetry as the Footium bug: one code path (v2 `GlobalStateView::check_proposal`) closes a hole that the sibling path (v1 `SortitionsView::check_proposal`) leaves open, and since this v1 check is one-shot (never re-run), a miner (a one-slot actor, satisfying the "miner (plus gossip)" trigger constraint) can exploit the v1-vs-v2 discrepancy by proposing two competing tenure-start blocks for the same tenure while the first is still only locally accepted network-wide, hoping v1 signers pre-commit/sign the second sibling before the "signed conflicts" fallback catches it.

### Impact Explanation
If exploited, this breaks the "one tenure-start block per tenure" equality that `validate_tenure_change_payload`/`DuplicateBlockFound` is meant to guarantee for v1 signers specifically, potentially letting a v1 signer sign a second, conflicting tenure-start block for a tenure that already has a (locally) accepted sibling. Under the report's rules, a signer signing a conflicting block is a Critical-class outcome if it can be realized without a signer majority and purely through miner+gossip timing. However, the doc notes a fallback mitigation exists in the pre-commit/signing flow (`get_signed_conflicts` / "signed conflicts at height ≥ h, in ANY tenure"), which substantially narrows — but per the doc's own admission ("relies on section 5's own-tenure conflict guard to cover the same ground") does not fully replace — the tenure-scoped duplicate check.

### Likelihood Explanation
Reaching this requires a miner to propose two tenure-start blocks for the same tenure while gossip/state has not yet converged to global acceptance of the first — a timing window that is plausible in a live network (validation, pre-commit propagation, and node-processing all take non-zero time), and does not require compromising any signer key or achieving a signer majority. It is bounded by the fallback conflict check in the pre-commit path, so likelihood is not "certain" but the window is real and version-dependent (only affects signers still running the v1 chainstate path).

### Recommendation
Unify the "already accepted" criterion used by `validate_tenure_change_payload` across v1 and v2 (either both use locally-or-globally-accepted, matching v2's stronger check, or explicitly document why v1's weaker global-only criterion is safe given the pre-commit-time fallback). Additionally, consider re-running the tenure-scoped duplicate-block check at `handle_block_validate_ok` and/or at the pre-commit threshold moment (alongside the existing height-based `get_signed_conflicts` check) rather than relying solely on the one-shot proposal-time check, closing the gap the docs explicitly flag ("the duplicate check never runs again").
