### Title
`validate_tenure_change_payload` in v1 checks only globally-accepted blocks, letting a signer double-sign two tenure-change blocks at the same height in one tenure - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` in `chainstate/v1.rs` guards against a duplicate tenure-change proposal by calling `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, which only returns blocks in `BlockState::GloballyAccepted`. A block the signer has already `LocallyAccepted` (i.e., already signed) in the same tenure is invisible to this check, so a second, different tenure-change block proposed for the same tenure can pass proposal-time validation and be signed too. The equivalent v2 code was fixed to use `get_last_signed_block` (which covers both `LocallyAccepted` and `GloballyAccepted`), and a regression test (`check_tenure_change_rejects_when_locally_accepted_block_exists` in `v2.rs`) exists specifically to pin this down — but v1 was left with the old, narrower check.

### Finding Description
The safety property that must hold is: at most one block per (tenure, height) may ever receive this signer's signature. `SignerDb::get_last_signed_block` (in `stacks-signer/src/signerdb.rs`) is documented as the correct predicate for "what is the tenure's signed tip?", explicitly including `LocallyAccepted` states because a locally-accepted block already carries this signer's signature. `get_last_globally_accepted_block`, by contrast, only reflects blocks that have crossed the network-wide 70%+ threshold.

In `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:505-518`), the duplicate-tenure-change guard is:
```rust
let last_in_current_tenure = signer_db
    .get_last_globally_accepted_block(&block.header.consensus_hash)?;
if let Some(last_in_current_tenure) = last_in_current_tenure {
    return Err(RejectReason::DuplicateBlockFound);
}
``` [1](#0-0) 

Compare to the fixed v2 version (`stacks-signer/src/chainstate/v2.rs:344-357`), which uses `get_last_signed_block` and explicitly documents the rationale — pre-commits carry no signature and are safely supersedable, but locally- or globally- accepted blocks are signed and must conflict: [2](#0-1) 

`docs/signer-flows.md` explicitly documents this v1/v2 divergence as a known asymmetry: "v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)" and separately notes "Because the duplicate check never runs again" — i.e., this proposal-time-only check is the *sole* guard against a same-tenure duplicate tenure-change block; there is no re-check at validate-ok or at signing time for this specific tenure-change duplication rule. [3](#0-2) 

**Exploit flow (single unprivileged miner slot):**
1. Attacker wins a sortition slot for tenure `T`, proposes tenure-change block `C` at height `h` with consensus_hash `T`. `validate_tenure_change_payload` finds no prior block in tenure `T` (via `get_last_globally_accepted_block`), passes; the victim signer (running v1 chainstate, i.e. with `check_block_against_global_state=false`) signs `C`, which becomes `LocallyAccepted` in `signerdb` — never crossing to `GloballyAccepted` (e.g., because not enough other signers respond, or attacker only gossips to isolate this signer's view).
2. Minutes later, attacker crafts `C'`: same `consensus_hash` (same tenure `T`), same height `h`, but a different `parent_block_id`/tenure-change payload, hence a different `signer_signature_hash`. This is a genuinely new block for `handle_block_proposal`, so it goes through a fresh `check_block_against_state` → `check_proposal` → `validate_tenure_change_payload`, not through the `should_reevaluate_block` "PC" resend path (which only applies to already-known `signer_signature_hash`es).
3. `validate_tenure_change_payload` calls `get_last_globally_accepted_block(T)`, which returns `None` because `C` is only `LocallyAccepted`. The duplicate check silently passes.
4. All other checks (`check_tenure_change_confirms_parent`, `check_parent_tenure_choice`) are keyed off the *parent* tenure and node-reported tip, not off same-tenure sibling blocks, so they do not catch this. The victim signer signs `C'` too.

The signer has now placed a valid signature on two conflicting tenure-change blocks at the same height in the same tenure — a chain-safety violation (equivocation), achievable with a single miner/signer slot and ordinary StackerDB gossip, no majority collusion, no auth_token, no local access.

### Impact Explanation
This breaks the "at most one signed block per (tenure, height)" invariant — a signer signing two conflicting blocks (chain safety / equivocation), which is the Critical impact category ("a signer signing an invalid, non-canonical, or conflicting block"). If enough signers on the v1 (non-global-state) code path are independently targeted this way, both `C` and `C'` could separately accumulate signatures, producing two competing signed tenure-change blocks in one tenure — a hard fork / equivocation at the signer layer that the block-signing protocol is supposed to prevent by construction. It is repeatable per tenure by any single winning miner slot, at zero cost beyond normal mining/proposal gossip.

### Likelihood Explanation
Preconditions: the target signer must run the v1 chainstate path (`check_block_against_global_state=false`), the attacker needs to win one sortition slot for tenure `T` (ordinary, permissionless), have `C` reach `LocallyAccepted` (signed but not yet globally accepted — an easily reachable transient state, e.g. under normal network conditions before enough signers respond, or by simply being fast), then gossip a second, structurally different tenure-change block `C'` for the same `consensus_hash`. No majority of signers, no compromised keys, no auth_token, and no local host access are required — only crafting proposals and StackerDB gossip, matching the allowed attacker capability. This is feasible and repeatable per tenure.

### Recommendation
In `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload`, replace `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` with `signer_db.get_last_signed_block(&block.header.consensus_hash)`, matching the v2 fix, so that any `LocallyAccepted` (already-signed) block in the tenure also triggers `RejectReason::DuplicateBlockFound`.

### Proof of Concept
Add to `stacks-signer/src/chainstate/tests/v1.rs`, mirroring the v2 regression test:
```rust
#[test]
fn check_tenure_change_rejects_when_locally_accepted_block_exists_v1() {
    // setup_test_environment for v1::SortitionsView (as in existing v1.rs tests)
    // 1. Insert a BlockInfo for the current tenure's consensus_hash with
    //    existing_block_info.mark_locally_accepted(false).unwrap(); (NOT globally accepted)
    // 2. Build a second tenure-change block `block` for the SAME consensus_hash,
    //    with a different parent_block_id / signer_signature_hash.
    // 3. Call sortitions_view.check_proposal(&stacks_client, &mut signer_db, &block)
    //    (which dispatches into validate_tenure_change_payload).
    // 4. assert!(matches!(result, Err(RejectReason::DuplicateBlockFound)),
    //        "v1 must reject a duplicate tenure-change block even when the prior \
    //         block is only LocallyAccepted, got: {result:?}");
}
```
Before the fix, this assertion fails (the proposal is incorrectly accepted) because `get_last_globally_accepted_block` returns `None` for a `LocallyAccepted` block; after switching to `get_last_signed_block`, the test passes, closing the equivocation window.

Two things belong to the proposal path only and are **not** re-run at validate-ok
or at signing:

- `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we
  have already accepted a block in the tenure a tenure-change block is starting.
  v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1
  counts only globally accepted ones (`get_last_globally_accepted_block`).
- the v2 `check_proposal` wrapper checks miner pubkey hash, consensus hash, the
  pox bitvec, and tenure-extend rules before delegating here.

Because the duplicate check never runs again, a block that crosses the pre-commit
threshold long after it was proposed relies on section 5's own-tenure conflict
guard to cover the same ground.
