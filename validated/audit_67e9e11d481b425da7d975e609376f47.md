### Title
Instant-withdraw receipts are not bound to the epoch that was funded, so a later unfunded instant-withdraw request can steal another user's funded instant-withdraw payout - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays the aggregate `instantWithdrawsRequests[_user]` from the vault's underlying balance with no check that the user's request epoch was actually funded via `collectInstantWithdrawFunds`. Instant receipts are tracked per epoch (`instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`) for default accounting, but the claim path ignores the epoch entirely. A user whose instant request should not yet be servable (permission/funding not yet granted for that epoch) can still reach the payout path and drain underlying that was collected for earlier instant withdrawers — the same "opted-out/disabled surface still reachable" class as BIT-discourse-2024-53994.

### Finding Description
Instant withdrawals in the epoch design are windowed and conditional: they are only allowed during `instantWithdrawDelay`/`instantWithdrawDeadline` in `IdleCDOEpochVariant` when `allowInstantWithdraw` is set and the new APR drops by `instantWithdrawAprDelta`, and they are only payable once the CDO has moved underlying into the strategy via `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws`. However, `claimInstantWithdrawRequest` performs none of these checks:

```solidity
function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    _burn(_user, amount);
    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
}
```

`_transferFundedClaim` only guards the `defaultRecoveryReserve`; it happily spends any other underlying sitting in the vault, including underlying collected for *other epochs'* instant withdrawers or for funded normal withdraw requests. In contrast, the normal withdraw path (`_claimFundedWithdrawRequest`) enforces `epochNumber > lastWithdrawRequest[_user]` before paying, tying a receipt to a completed funding epoch. The instant path has no equivalent binding.

Attack sequence (running/buffer phases, instant mode):

1. Epoch N ends, epoch N+1 starts; instant-withdraw window opens. Victim V calls `requestInstantWithdraw(10k)` and the borrower/CDO funds it via `collectInstantWithdrawFunds` — 10k underlying now sits in the vault reserved for V.
2. V does not claim immediately (claims are permissionless in time — there is no expiry).
3. In a subsequent instant-withdraw window (next epoch boundary), attacker A calls `requestInstantWithdraw(10k)`. A's receipt is recorded against the new `epochNumber` and `pendingInstantWithdraws` rises again, but no funding has arrived yet for this epoch.
4. A immediately calls `claimInstantWithdrawRequest` through the CDO. Because the claim only looks at the aggregate `instantWithdrawsRequests[A]` and the vault balance (10k), A receives the 10k that was funded for V's epoch-N+1 receipt.
5. When V later claims, `_burn` succeeds but the vault balance is empty — V's `safeTransfer` reverts. V's funded receipt is permanently unpaid: the protocol considers it funded (`collectInstantWithdrawFunds` already ran and `pendingInstantWithdraws` was decremented), so it will never be refinanced.

Existing guards do not stop it: `_onlyIdleCDO` is satisfied since A goes through the CDO; `defaultRecoveryFinalized` paths are irrelevant pre-default; there is no per-epoch funded marker checked for instant claims the way `epochNumber <= lastWithdrawRequest` gates normal claims.

### Impact Explanation
Direct theft of funded withdraw proceeds. A's loss is zero (burned receipt tokens that represented an unfunded request); V loses the full funded amount (10k underlying in the example — equal to whatever the instant-withdraw tranche of the epoch was). The broken invariant is "one receipt, one payout": an unfunded epoch's receipt consumes a prior epoch's funding, leaving the legitimate funded receipt holder permanently frozen out.

### Likelihood Explanation
Requirements: a pool running `IdleCDOEpochVariant` with instant withdrawals enabled (the mode exists specifically for APR decreases), a funded-but-unclaimed instant receipt, and a later instant-withdraw window where a second user files a request before the first claims. There is no claim deadline, so the exposure window is the entire time between funding and the victim's claim, across subsequent epoch boundaries. One caveat I could not fully verify with the available context: whether `IdleCDOEpochVariant.requestInstantWithdraw` permits a new instant request while an older one remains unclaimed (no per-user "existing instant request" check was visible in `IdleCreditVault.requestInstantWithdraw`, which only blocks in the post-default path via `_ensureDefaultRecoveryInitialized`/`defaultRecoveryFinalized` gating in `requestWithdraw`, not in `requestInstantWithdraw`). If the CDO blocks concurrent requests, the attack requires the victim's funded epoch and a subsequent request epoch, which the per-epoch accounting explicitly supports.

### Recommendation
Bind instant receipts to their funding epoch the same way normal receipts are bound via `lastWithdrawRequest`/`epochNumber`:

- Record the request epoch at `requestInstantWithdraw` (already done in `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`) and, in `claimInstantWithdrawRequest`, only pay amounts whose epoch was funded — e.g., require `epochNumber > requestEpoch` or track a `instantFundedUpToEpoch`/`lastInstantFundedEpoch` counter set in `collectInstantWithdrawFunds` and revert (`NotAllowed()`) for requests made in unfunded epochs.
- Alternatively, escrow per-epoch funding (`fundedInstantByEpoch[epoch] += _amount` in `collectInstantWithdrawFunds`) and decrement it on claim, so a new epoch's receipts can never consume a prior epoch's balance.
- Reject new `requestInstantWithdraw` calls while `instantWithdrawsRequests[_user] != 0` (mirroring the post-default `NotAllowed()` check in `requestWithdraw`) to prevent aggregate-balance mixing.

### Proof of Concept
Foundry fork test sketch (extends `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testInstantWithdrawUnfundedEpochDrainsFundedReceipt() external {
    // Setup: deposit as victim and attacker, run epoch 0, stop epoch with lower APR
    // so the instant-withdraw window opens for epoch 1.
    idleCDO.depositAA(20_000 * ONE_SCALE);          // victim (this contract)
    _depositWithUser(attacker, 20_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                        // opens instant window

    // 1) Victim requests instant withdraw; CDO funds it.
    uint256 victimAmt = 10_000 * ONE_SCALE;
    cdoEpoch.requestInstantWithdraw(victimAmt, AAtranche);
    // borrower repays instant liquidity; CDO calls getInstantWithdrawFunds ->
    // strategy.collectInstantWithdrawFunds -> vault holds victimAmt.

    // 2) Next epoch boundary: new instant window opens.
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                        // victim still hasn't claimed

    // 3) Attacker files an instant request in epoch 2 (not yet funded) and
    //    immediately claims: he is paid the victim's funded 10k.
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(victimAmt, AAtranche);
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - pre, 0, "attacker paid from victim's funding");

    // 4) Victim's claim now reverts on insufficient vault balance -> frozen funds.
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Expected result on the current code: step 3 succeeds because `claimInstantWithdrawRequest` pays `instantWithdrawsRequests[attacker]` against the vault's live balance without checking that epoch-2 instant funding ever arrived; step 4 reverts inside `_transferFundedClaim`'s `safeTransfer`, permanently freezing the victim's funded receipt.
