## Analysis

The Gravity report is about a threshold/quorum check missing when the validator set changes, which can permanently disable the ability to reach quorum. The nearest reachable analog in this repo is in the multisig contracts (`multisig/src/lib.rs`, `multisig2/src/lib.rs`), where the "confirmations counted vs. live members" binding is broken: removing a member (`DeleteKey` / `DeleteMember`) purges only the *requests* that member originated, but never purges that member's *confirmations* recorded on other members' still-pending requests. A stale confirmation from a removed member therefore continues to count toward the K-of-N quorum for any request created by someone else. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Title
Confirmations from a removed member persist and count toward quorum on other members' pending requests, allowing a request to execute with fewer live-member confirmations than `num_confirmations` requires - (File: multisig2/src/lib.rs / multisig/src/lib.rs)

### Summary
When a multisig member is removed via `DeleteMember` (multisig2) or `DeleteKey` (multisig), the contract removes only the requests that the removed member itself created, but never scrubs that member's confirmation entries recorded on other still-pending requests. A confirmation cast by a now-removed member therefore remains counted forever, letting a request reach the `num_confirmations` threshold using fewer live members than the configured quorum.

### Finding Description
`delete_member` in multisig2 enforces the invariant `members.len() - 1 >= num_confirmations` before removing a member, and cleans up `self.requests`/`self.confirmations` only for requests where `r.member == member` (i.e., requests the removed member authored): [2](#0-1) 

It never inspects the `confirmations` map of *other* pending requests (created by different members) to strip out the removed member's vote. The equivalent `DeleteKey` action in multisig has the identical pattern - it filters `self.requests` by `r.signer_pk == pk` (the request's original signer) and clears confirmations only for those requests: [4](#0-3) 

`confirm` simply counts entries in the `confirmations` set for the request and executes once the count reaches `num_confirmations`, with no re-validation that every entry in that set still corresponds to a current member/key: [3](#0-2) 

**Equality broken:** the contract's intended binding is `confirmations counted == confirmations from live members`. After a member is removed, this becomes `confirmations counted == confirmations from live members + stale confirmations from removed members`, so the actual number of *live* approvals backing an executed request can be strictly less than `num_confirmations`.

### Impact Explanation
Concretely, with members `{A, B, C}` and `num_confirmations = 2`:
1. `B` creates `RequestX` (e.g., a `Transfer` or `AddKey` action).
2. `A` confirms `RequestX` → `confirmations = {A}` (1/2, pending).
3. Members later remove `A` via a properly-quorumed `DeleteMember{A}` request. `delete_member` only clears requests that `A` created; `RequestX` (created by `B`) is untouched, so its confirmation set still contains `A`.
4. `B` now calls `confirm(RequestX)` → `confirmations = {A, B}`, length 2 `>= num_confirmations (2)` → the request executes.

The request executes with agreement from only **one** live member (`B`); the second "confirmation" is a stale vote from a member who no longer has authority. This is exactly the class of bug flagged in the source report: a critical action (here, execution of an arbitrary multisig request, including fund transfers or granting a new full-access key) proceeds without the intended quorum of currently-authorized signers - i.e., a multisig request executed below threshold, which can result in unauthorized fund movement or unauthorized privilege grants.

### Likelihood Explanation
This requires no external/compromised key or foundation privilege beyond the normal lifecycle of any actively-used K-of-N multisig: membership changes (onboarding/offboarding signers, key rotation) are a routine, expected operation, and any request left pending across a member-removal event is silently exposed to this stale-confirmation accumulation. Any remaining member can then single-handedly push a request past quorum by combining their own confirmation with the residual one from a removed member. No admin/foundation collusion or protocol-level assumption violation is needed - only normal use of the documented member-management flow.

### Recommendation
When removing a member/key (`delete_member` / `DeleteKey`), iterate over **all** pending requests (not just those authored by the removed member) and strip the removed member's/key's entry from each request's `confirmations` set. Alternatively, revalidate at `confirm`-time (and at execution time) that every account/key present in a request's confirmation set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. As `B`, call `add_request` with a `Transfer` (or `AddKey`) action → `request_id = 0`.
3. As `A`, call `confirm(0)` → confirmations for request 0 = `{A}` (not yet executed).
4. As `B` and `C`, create and confirm a `DeleteMember{A}` request (2/2 quorum) → `A` removed from `members`; request 0 is untouched because it was authored by `B`, not `A`.
5. As `B`, call `confirm(0)` again → confirmations for request 0 becomes `{A, B}`, length `2 >= num_confirmations (2)` → request 0 executes, even though only `B` (one live member) actually approved it post-removal.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
