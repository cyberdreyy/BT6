### Title
Programmable-borrower vault losses are floored to zero instead of being accounted as bad debt, letting early withdrawers exit at par and socializing the hole to remaining tranche holders - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower.totalInterestDueNow()` computes the pool-facing epoch result as `max(0, gains - vaultLoss)`. When the ERC4626 vault sleeve suffers a loss larger than the epoch's gains, the deficit is silently clamped to zero instead of being reported as a negative result or triggering a default. `IdleCDOEpochVariant._stopEpoch` therefore completes normally, tranche NAV (`lastNAVAA`/`lastNAVBB` and strategy-token balance) is never reduced by the principal impairment, and `virtualPrice`/`tranchePrice` continue to quote the vault at par. Any tranche holder who requests and claims a withdrawal while the remaining vault liquidity still covers the request exits at an inflated price; the unaccounted loss concentrates on the last LPs, exactly the "unaccounted bad debt borne by remaining protocol users" pattern of the reference report.

### Finding Description
The programmable-borrower vault sleeve tracks epoch PnL via `_vaultNetInterest()`:

- `contracts/strategies/idle/ProgrammableBorrower.sol:330-347` — `totalInterestDueNow()` returns `totalGain > loss ? totalGain - loss : 0`. A net vault loss produces `0`, with no representation of the negative delta anywhere in the return path.
- `contracts/IdleCDOEpochVariant.sol:357-393` — `_stopEpoch` resolves `_interest` from `totalInterestDueNow()` (via `_resolveStopEpochInterest` / `expectedEpochInterest`). With a floored `0`, `_grossInterest = 0`; in minted-interest mode (`isInterestMinted` is forced on for programmable borrowers, `setIsInterestMinted` at `IdleCDOEpochVariant.sol:166-169`) `_amountToPullFromBorrower = 0`, so only `pendingWithdraws` are pulled.
- `ProgrammableBorrower.onStopEpoch` (`ProgrammableBorrower.sol:239-253`) withdraws only the cash `shortfall` for the amount being pulled; if the vault covers that shortfall the hook returns `true`, `getFundsFromBorrower` succeeds, and the epoch stops cleanly. Since the vault impairment is never written into tranche NAV, `_updateAccounting` sees no NAV decrease and prices remain at par.
- On the next `onStartEpoch` (`ProgrammableBorrower.sol:206-223`) the impaired vault balance becomes the new `epochStartVaultAssets` baseline — the loss is permanently absorbed into principal accounting without ever flowing through `_updateAccounting`, `stopEpochWithDuration`'s `_lossAmount` waterfall, or `_handleBorrowerDefault`/`finalizeDefault`, which are the protocol's only bad-debt mechanisms.

The vault loss is real (shares redeems for fewer assets), yet the CDO's solvency accounting treats principal as fully backed until someone actually tries to pull more liquidity than the vault holds. Only then does `onStopEpoch`'s `shortfall > _currentVaultAssets()` check (`ProgrammableBorrower.sol:245`) or the `transferFrom` failure route into `_handleBorrowerDefault` — i.e. the bad debt is recognized only after the liquidity hole is hit, so earlier withdrawers at par are paid out of other LPs' impaired principal.

Broken invariant: solvency / fair mint/burn — tranche price does not reflect the true contract value, and loss waterfall ordering is bypassed because the loss never enters NAV.

### Impact Explanation
An ERC4626 vault loss of `L` greater than epoch gains is not charged to any tranche. Tranche holders can `requestWithdraw`/`claimWithdrawRequest` (or a loss-aware attacker LP exits first) at the pre-loss `virtualPrice`, funded by `pendingWithdraws` pulls that drain the remaining vault liquidity (`_stopEpoch` pulls `pendingWithdraws` even when `_amountToPullFromBorrower` is 0, `IdleCDOEpochVariant.sol:376,408`). When remaining claims exceed impaired assets, the pool falls into `defaulted` and `finalizeDefault` haircuts only the leftover claimants — so the `L` shortfall is borne disproportionately (potentially entirely, with receipt claims at a steep haircut via `defaultRecoveryPrice`) by users who did not withdraw early. Quantified loss: up to the full vault impairment `L`, transferred from late/remaining LPs to early exiters.

### Likelihood Explanation
Requires a programmable-borrower deployment (an in-scope mode, `isProgrammableBorrower`) and a negative `convertToAssets` move in the external ERC4626 vault — explicitly an in-scope surface ("External vault and hooks: … ERC4626 price or liquidity moves"). A user of that vault can realize or induce a loss (e.g., a vault where a large redemption realizes losses, or donation/exchange-rate manipulation) during a running epoch, then an LP attacker withdraws at par before the deficit is discovered. No privileged misbehavior is needed: owner/manager run `startEpoch`/`stopEpoch` honestly; the accounting itself drops the loss.

### Recommendation
Do not clamp the net vault delta at zero in `totalInterestDueNow`. Return a signed value (or a separate `loss` output) so `IdleCDOEpochVariant._stopEpoch` can route a net vault loss through the existing `_lossAmount`/`burnStrategyTokens` + `_forceUpdateAccounting` path (or `_handleBorrowerDefault` when the impairment makes pending obligations unpayable). Concretely: surface `_vaultNetInterest().loss` exceeding gains to the CDO, and treat unpayable net losses as a default trigger rather than a successful zero-interest stop.

### Proof of Concept
Foundry fork PoC sketch (mock or fork the ERC4626 vault):

```solidity
// Setup: deploy IdleCDOEpochVariant + IdleCreditVault with isInterestMinted = true,
// ProgrammableBorrower as borrower wrapping an ERC4626 vault (e.g. a test vault whose
// share price we can move, or a real mainnet vault on fork).
function testVaultLossNotAccounted() external {
    // 1. Alice and Bob deposit AA tranches
    _depositWithUser(alice, 10_000e6, true);
    _depositWithUser(bob, 10_000e6, true);

    // 2. Manager starts epoch; ProgrammableBorrower.onStartEpoch deposits all cash into vault
    vm.prank(manager);
    cdoEpoch.startEpoch(); // epochAccountingActive = true, epochStartVaultAssets = 20_000e6

    // 3. Vault loses value: e.g. vault's underlying strategy loses, or attacker (a vault
    //    user) triggers a realized-loss redemption so convertToAssets drops.
    //    Simulate: burn/deal so vault total assets drop by 6_000e6 (> epoch interest).
    _simulateVaultLoss(6_000e6); // netDelta = -6_000e6, totalInterestDueNow() == 0

    // 4. Manager stops epoch — SUCCEEDS, no default, no loss burn
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    assertFalse(cdoEpoch.defaulted());          // BUG: not flagged as bad debt
    assertEq(strategy.totalInterestDueNow(), 0); // loss floored to zero

    // 5. Tranche price still ~par: NAV was never reduced
    assertApproxEqAbs(cdoEpoch.virtualPrice(address(AAtranche)), ONE_TRANCHE, 1e15);

    // 6. Alice exits at par through the normal withdraw flow, draining impaired liquidity
    vm.prank(alice);
    cdoEpoch.requestWithdraw(0, cdoEpoch.AATranche());
    // next epoch start/stop funds her receipt from remaining vault assets
    _runEpochToFund(alice);
    vm.prank(alice);
    cdoEpoch.claimWithdrawRequest();
    assertApproxEqAbs(underlying.balanceOf(alice), 10_000e6, 1e6); // paid ~full

    // 7. Bob can no longer be paid: vault holds only ~4_000e6 for his 10_000e6 claim.
    //    The next stop either defaults or pays him a deep recovery haircut —
    //    the 6_000e6 bad debt lands entirely on Bob.
}
```

Key assertion of the bug: after step 3, `ProgrammableBorrower.vaultLoss() > 0` and `totalInterestDueNow() == 0`, yet step 4 completes without `defaulted`, without `burnStrategyTokens`, and without any NAV reduction — confirming the loss escaped every accounting path.
