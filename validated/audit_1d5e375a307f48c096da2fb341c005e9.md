### Title
Dust withdraw request permanently bricks `processWithdrawRequests` via `Is0` revert — (File: contracts/IdleCDOEpochQueue.sol)

### Summary
`IdleCDOEpochQueue.requestWithdraw` accepts any non-zero tranche amount with no minimum. When the manager later calls `processWithdrawRequests`, the implied epoch price is computed as `_underlyingsRequested * ONE_TRANCHE / _pending`. For a sufficiently small aggregate `_pending` (a dust request, or honest requests dusted by an attacker), the underlying amount returned by `IdleCDOEpochVariant.requestWithdraw` rounds to zero, `_epochPrice` becomes 0, and the function reverts with `Is0()`. The revert rolls back the whole call, so `epochPendingWithdrawals[_epoch]` is never cleared and the manager can never process that epoch's withdrawals.

### Finding Description
In `processWithdrawRequests` (contracts/IdleCDOEpochQueue.sol:298-329):

- `_pending = epochPendingWithdrawals[_epoch]` aggregates *all* users' queued tranche tokens for the epoch.
- `_underlyingsRequested = _cdo.requestWithdraw(_pending, tranche)` returns `amount * virtualPrice / ONE_TRANCHE` (rounds down).
- `_epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending`; if it is 0, `revert Is0()` at line 320.

A KYC-passing attacker calls `requestWithdraw(1)` (or any amount whose implied underlyings round to 0) during a running epoch. When the buffer period starts, every `processWithdrawRequests` call reverts because the arithmetic produces a zero price before any state is updated. Because `_checkNotAllowed(pendingClaims)` and the per-epoch aggregate design mean the dust amount cannot be skipped, the only escape is the attacker voluntarily calling `deleteWithdrawRequest` — which they won't.

The codebase's own test `testProcessWithdrawRequestsWith0Price` (test/foundry/IdleCDOEpochQueue.t.sol:1431-1456) confirms the revert, but treats it only as a state assertion, not as the exploitable freeze it enables when the dust request is adversarial.

### Impact Explanation
All tranche tokens queued for withdrawal in that epoch are frozen inside the queue: `claimWithdrawRequest` reverts (`epochWithdrawPrice == 0 && !isEpochWithdrawZero`), and `processWithdrawRequests` can never succeed for that epoch. Honest users can individually recover their tranche tokens via `deleteWithdrawRequest` and re-request directly on the CDO, so the freeze is temporary rather than permanent, but every queued user's exit is blocked for the duration and normal queue-based withdrawals for the epoch are bricked. Cost to the attacker is ~1 wei of tranche tokens plus gas; the frozen amount is the entire `epochPendingWithdrawals[_epoch]` of other users.

### Likelihood Explanation
Requires only a KYC-passing wallet (attacker class: KYC-passing lender) and a dust `requestWithdraw` while an epoch is running. No privileged action, no timing race beyond submitting before the buffer period. The arithmetic path is deterministic — any aggregate `_pending` smaller than `ONE_TRANCHE / virtualPrice` triggers it, and the attacker can always top up to exactly the dust threshold.

### Recommendation
Enforce a minimum withdraw amount in `requestWithdraw` (e.g., revert if `amount * virtualPrice(tranche) / ONE_TRANCHE == 0`), or make `processWithdrawRequests` treat a zero `_epochPrice` as a claimable zero-payout epoch using the existing `isEpochWithdrawZero` marker instead of reverting. Alternatively, let the manager purge individual dust requests.

### Proof of Concept
```solidity
function testDustWithdrawBlocksEpochProcessing() external {
    _stopCurrentEpoch(); // enter epoch 1 buffer

    // honest user deposits and queues a normal withdraw
    address user1 = makeAddr('user1');
    uint256 tranches1 = _depositWithUser(user1, 100e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // attacker (KYC'd) queues a 1-wei withdraw in the same next epoch
    address attacker = makeAddr('attacker');
    _requestWithdrawWithUser(attacker, 1);
    // honest user queues the rest
    _requestWithdrawWithUser(user1, tranches1);

    _stopCurrentEpoch(); // epoch 2 buffer: requests become processable

    // every attempt to process reverts; epochPendingWithdrawals stays set
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(Is0.selector));
    queue.processWithdrawRequests();

    // honest user's claim is bricked
    vm.prank(user1);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    queue.claimWithdrawRequest(strategy.epochNumber());
}
```
