### Title
Anyone can rewrite the vault APR via `IdleCreditVault.setApr`/`setAprs` while `idleCDO == address(0)` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary

`IdleCreditVault.setApr()` (and `setAprs()`/`setAprsWithBuffer()`, which delegate to it) skips its caller check entirely whenever `idleCDO == address(0)`. This is the direct analog of the external `ResetSystem::resetGame()` report: a state-changing function that is supposed to be privileged (`only CDO or manager`) silently becomes permissionless during the setup window between `initialize()` and `setWhitelistedCDO()`, which are separate owner transactions. Any unprivileged EOA can front-run `setWhitelistedCDO` and set `unscaledApr`/`lastApr` to arbitrary values up to `maxApr` (20e18 scaled by default), corrupting the fixed-APR that `IdleCDOEpochVariant` uses to compute `expectedEpochInterest` and to choose the APR0 withdraw accounting branch.

### Finding Description

In `contracts/strategies/idle/IdleCreditVault.sol:225-235`, `setApr` only enforces the CDO/manager check when `idleCDO` is already set:

```solidity
function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
}
```

`setAprs` (`IdleCreditVault.sol:206-210`) writes `unscaledApr` **before** delegating to `setApr`, so during the same window an attacker controls both values with a single call. `initialize()` (`IdleCreditVault.sol:124-157`) sets sane values, but there is no atomicity with `setWhitelistedCDO` (`IdleCreditVault.sol:954-957`), which is a separate `onlyOwner` call.

The poisoned values are consumed by honest privileged flows:

- `IdleCDOEpochVariant._stopEpoch` / `startEpoch` compute `expectedEpochInterest = _calcInterest(getContractValue())` from the strategy APR (`IdleCDOEpochVariant.sol:260-274`), and `stopEpoch` pulls that amount from the borrower via `getFundsFromBorrower` → `transferFrom(borrower, ...)` (`IdleCDOEpochVariant.sol:550-553`).
- `requestWithdraw` selects the APR0 accounting path (`apr0Users`, `apr0TotalPrincipal`) whenever `unscaledApr == 0` (`IdleCreditVault.sol:285-294`).

Two concrete attacker payloads:

1. `setAprs(type-ish high, maxApr)` — inflates `lastApr`. `expectedEpochInterest` at the next `stopEpoch` is inflated to ~20%×TVL×(epoch+buffer)/epoch. If the honest borrower has pre-approved the CDO (standard revolving-credit setup, e.g. via `ProgrammableBorrower._allowUnlimitedSpend`), the CDO `transferFrom` pulls the excess from the borrower and distributes it to tranche LPs and `feeReceiver` — direct theft of up to ~20% of TVL annualized from an honest party. If the borrower has not approved the excess, the pull fails and `_handleBorrowerDefault` forces the vault into `defaulted`, freezing all withdraw receipts until `finalizeDefaultRecovery` runs and haircutting every receipt by `defaultRecoveryPrice`.

2. `setAprs(0, 0)` — sets `unscaledApr = 0`, silently switching the vault into APR0 mode for the whole epoch. `requestWithdraw` routes all requests into `apr0Users`/`apr0TotalPrincipal`, and `prepareStopEpochWithApr0` (`IdleCreditVault.sol:490-541`) computes pro-rata interest on a rate the borrower never agreed to; the epoch produces zero contractual interest and withdraw-request accounting diverges from the configured fixed-APR terms.

Broken invariant: **access control** on APR configuration → leads to theft of borrower funds or forced insolvency/default freezing.

### Impact Explanation

An unprivileged attacker monitoring the mempool front-runs the owner's `setWhitelistedCDO` with a single `setAprs` call costing ~50k gas. Result: either up to `maxApr` (20e18 scaled APR) of borrower interest is siphoned into LP/feeReceiver value at the first `stopEpoch`, or the vault is forced into `defaulted`, permanently freezing all pending withdraw receipts until an owner-driven `finalizeDefault` crystallizes losses. Impact scales with vault TVL and epoch duration.

### Likelihood Explanation

The window is exactly the gap between `initialize()` and `setWhitelistedCDO()` on a deployed vault proxy — a routine two-transaction deployment on a public chain. Once `idleCDO` is set, the attacker cannot act again, but a single poisoned `setAprs` persists until `startEpoch`/`stopEpoch` consumes it. It requires the manager to call `startEpoch`/`stopEpoch` without re-checking `lastApr`/`unscaledApr` off-chain; nothing on-chain re-validates the APR against a signed borrower term at epoch start.

### Recommendation

Enforce the caller check unconditionally, e.g. revert when `msg.sender != idleCDO && msg.sender != manager` regardless of `idleCDO == 0`, and instead gate the initial value set inside `initialize()` (or add an `onlyOwner` setup setter that auto-clears once `idleCDO` is set). Alternatively, perform `initialize` + `setWhitelistedCDO` atomically in `IdleCreditVaultFactory`, and have `startEpoch`/`setAprsWithBuffer` always refresh `lastApr` from CDO-supplied parameters rather than trusting a stale stored value.

### Proof of Concept

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "contracts/strategies/idle/IdleCreditVault.sol";
import {IdleCDOEpochVariant} from "contracts/IdleCDOEpochVariant.sol";

contract MissingAccessControlAprTest is Test {
    IdleCreditVault vault; // deployed behind proxy
    IdleCDOEpochVariant cdo;
    address attacker = makeAddr("attacker");
    address owner    = makeAddr("owner");

    function test_AnyoneCanSetAprBeforeWhitelistedCDO() public {
        // State right after initialize(): idleCDO == address(0)
        assertEq(vault.idleCDO(), address(0));

        uint256 max = vault.maxApr(); // DEFAULT_MAX_APR = 20e18
        vm.prank(attacker);
        vault.setAprs(0, max);        // no revert: unscaledApr = 0, lastApr = 20e18
        assertEq(vault.lastApr(), max);
        assertEq(vault.unscaledApr(), 0); // forces APR0 withdraw accounting

        // Owner unknowingly completes setup
        vm.prank(owner);
        vault.setWhitelistedCDO(address(cdo));

        // Owner/manager startEpoch; expectedEpochInterest is now computed
        // against attacker-controlled APR (or APR0 mode hijacked):
        //   IdleCDOEpochVariant.startEpoch -> _calcInterest(getContractValue())
        //   -> stopEpoch pulls inflated interest from borrower via transferFrom,
        //      or fails -> _handleBorrowerDefault -> defaulted = true.
        vm.prank(owner);
        cdo.startEpoch();
        // ... warp to epochEndDate, owner calls stopEpoch:
        //  - borrower overpays ~maxApr * tvl * epochDuration / YEAR  (theft), or
        //  - cdo.defaulted() == true (frozen receipts -> finalizeDefault haircut)
    }
}
```
