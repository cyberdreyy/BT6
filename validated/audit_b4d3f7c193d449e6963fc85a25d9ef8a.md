### Title
Stale rejection weight is never cleared when a signer later validly accepts the same block, letting leftover reject-weight force a wrongful global-rejection of a block that actually reached the acceptance threshold - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`stackerdb_listener.rs` maintains a `BlockStatus` struct per proposed block with two independently-incremented counters, `total_weight_approved` and `total_weight_rejected` [1](#0-0) . When a signer's vote for a given block *changes* from `Rejected` to `Accepted` (a state transition explicitly modeled as legitimate in the signer's own state machine, `LocallyRejected --> LocallyAccepted: re-evaluated`), the code adds the signer's weight into `total_weight_approved` but never subtracts the weight it had already added to `total_weight_rejected` for that same signer. This is the same bug class as the reported skale-manager issue: one derived/aggregate counter (`_effectiveDelegatedByHolderToValidator` / here `total_weight_rejected`) is left stale after the underlying per-holder/per-signer value changes (`_delegatedByHolderToValidator` / here the signer's actual vote), so downstream consensus/decision logic acts on inconsistent data.

### Finding Description
`BlockStatus` tracks, per block, `responded_signers`, `gathered_signatures`, `total_weight_approved`, and `total_weight_rejected` [1](#0-0) .

On `BlockResponse::Accepted`, the gate for adding weight is solely `!block.gathered_signatures.contains_key(&slot_id)`: [2](#0-1) 
This branch never checks or adjusts `total_weight_rejected`.

On `BlockResponse::Rejected`, the gate is `block.responded_signers.insert(slot_id)` (true only the first time this signer has *ever* responded, regardless of kind): [3](#0-2) 

Because `responded_signers` is shared across both response kinds, a signer that first sends `Rejected` (incrementing `total_weight_rejected`, inserting itself into `responded_signers`) and later, after a legitimate re-evaluation, sends a valid `Accepted` with a verified signature, will:
- pass the `Accepted` weight-addition gate (since `gathered_signatures` didn't contain their slot yet) and get counted into `total_weight_approved`, **while**
- their earlier weight contribution to `total_weight_rejected` is never removed.

The result is that a single signer's weight is now counted in *both* pools simultaneously, and `total_weight_approved + total_weight_rejected` can exceed the real, current total weight of votes that logically support each side. This breaks the "aggregated-weight vs verified-accepts/rejects" equality the tally is supposed to preserve.

### Impact Explanation
`signer_coordinator.rs::get_block_status` evaluates the reject branch **before** the accept branch: [4](#0-3) 
If `total_weight_rejected.saturating_add(weight_threshold) > total_weight`, the miner treats the block as globally rejected, bumps `naka_rejected_blocks`, and returns `SignersRejected` (excluding transactions temporarily/permanently) — even though the real, current set of votes (after the flip) may have accumulated enough valid, verified `total_weight_approved` to legitimately cross the 70% threshold. Because the stale reject weight is never cleared, a miner can be forced to treat a properly-signed, otherwise-acceptable block as dead, unnecessarily excluding transactions and abandoning tenures. This matches the High-impact category: a wedge that can push a signer/coordinator into "acting on a stale... state" and can prevent a valid block from ever completing, causing block-production liveness loss and unwarranted transaction exclusion. It is reachable by any single signer flipping its own vote (a legitimate transition per the signer's own state machine), without needing a majority.

### Likelihood Explanation
This requires only one signer (or its own re-evaluation logic) to send `Rejected` then later `Accepted` for the same block, which is an explicitly supported and expected transition in the signer's `BlockState` machine (`LocallyRejected --> LocallyAccepted: re-evaluated`). No majority collusion or malicious key is needed; a single honest signer that re-evaluates a block (e.g., after a transient rejection reason clears) triggers the desync automatically as part of normal, one-slot-miner-observable flow.

### Recommendation
When a signer's vote transitions from `Rejected` to `Accepted` for the same block (or vice versa), subtract that signer's weight from the stale bucket before/while adding it to the new one, mirroring the fix pattern from skale-manager PR #118 (reduce the derived aggregate alongside the underlying value). Concretely, track the response kind per `slot_id` (not just presence in `responded_signers`) and, on a kind change, adjust `total_weight_approved`/`total_weight_rejected` accordingly so the two counters never both include the same signer's weight at once.

### Proof of Concept
1. Coordinator proposes a block; signer `S` (weight `w`) sends `Rejected` — `total_weight_rejected += w`, `responded_signers.insert(S)` [3](#0-2) .
2. `S` later re-evaluates and sends a validly-signed `Accepted` for the same block — `gathered_signatures` doesn't yet contain `S`, so `total_weight_approved += w` [2](#0-1) ; `total_weight_rejected` is left unchanged at its earlier value.
3. Other signers respond, pushing `total_weight_rejected` (which still includes `S`'s stale contribution) past `total_weight - weight_threshold` before `total_weight_approved` reaches `weight_threshold`.
4. `get_block_status` hits the reject branch first and returns `SignersRejected`, discarding a block that, counting only current votes, had (or was close to having) enough real acceptance weight [4](#0-3) .
