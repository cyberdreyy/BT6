### Title
A single dust APR0 withdraw request permanently vetoes APR changes and bricks `stopEpoch`, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` records withdraw requests made while `unscaledApr == 0` into a global `apr0TotalPrincipal` bucket. `prepareStopEpochWithApr0` — called unconditionally at the top of every `stopEpoch`/`stopEpochWithDuration` — reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged KYC'd lender can place a dust-sized APR0 withdraw request, after which any honest APR increase by the manager makes `stopEpoch` revert forever, freezing all user funds in the running epoch until the APR is forced back to 0. The attacker can re-arm the grief every epoch the APR is 0, giving them a permanent veto on ever raising the vault APR.

### Finding Description
In `IdleCreditVault.requestWithdraw`, when `unscaledApr == 0` and the pool is not closed, the request is routed to `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` and stores `apr0Users[_user].principal`/`principalEpoch` (lines 285-286, 567-577) [1](#0-0) . The only paths that reduce `apr0TotalPrincipal` are `prepareStopEpochWithApr0` (sets it to 0 at line 540) and the defaulted-receipt clearing path.

`IdleCDOEpochVariant._stopEpoch` calls `_strategy.prepareStopEpochWithApr0(_interest)` at line 362, outside the `try/catch` that wraps borrower funding — a revert there propagates and the whole `stopEpoch` fails [2](#0-1) . Inside `prepareStopEpochWithApr0`, if `apr0TotalPrincipal != 0` and `unscaledApr != 0`, it reverts `NotAllowed` (lines 501-508) [3](#0-2) .

Meanwhile the manager is explicitly allowed to change `unscaledApr` at any time via `setAprs`/`setApr` — the guard only checks `msg.sender == idleCDO || msg.sender == manager` (lines 206-234) [4](#0-3) . There is no guard preventing an APR change while an APR0 request bucket is open.

Attack sequence:
1. Pool APR is 0 (common configuration; programmable-borrower pools are documented to run APR=0).
2. Attacker (any KYC-passing EOA) deposits a dust amount (e.g., 1 wei of underlying → 1 tranche token) and calls `IdleCDOEpochVariant.requestWithdraw` during the buffer. `unscaledApr == 0` routes it through `_requestWithdrawApr0`; `apr0TotalPrincipal = dust`.
3. Manager honestly sets a nonzero APR for the next epoch via `setAprs`/`setAprsWithBuffer` (e.g., borrower renegotiates rate).
4. Epoch runs; at `epochEndDate`, manager calls `stopEpoch` → `prepareStopEpochWithApr0` sees `_principal != 0` and `unscaledApr != 0` → revert. Every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts identically.
5. The epoch can never close: borrower principal is not recalled, no withdraw request can be claimed (claimants need `epochNumber > lastWithdrawRequest`, which only `stopEpoch` increments), and all tranche holders' funds remain locked. The only escape is the manager setting `unscaledApr` back to 0 — i.e., the attacker's dust request permanently vetoes any nonzero APR for as long as they keep one dust APR0 receipt pending.

Broken invariant: an unprivileged lender must not be able to force `stopEpoch` to revert or to constrain honest manager APR governance. Existing guards do not stop it — `setApr` has no pending-APR0 check, `requestWithdraw` legitimately accepts dust, and the revert at line 507 is reachable only through attacker-controlled pending state.

### Impact Explanation
Temporary freezing of 100% of vault TVL plus a persistent governance veto. While `stopEpoch` is bricked: the borrower keeps all loaned principal beyond `epochEndDate`, no withdraw request can be claimed, `epochNumber` never advances, and deposits/instant-withdraw settlement halt. Resolution requires reverting the APR to 0 — meaning as long as the attacker repeats a dust APR0 request each buffer period, the vault can never operate at a nonzero APR again without an indefinite freeze window. Attacker cost is a dust deposit plus one upfront management fee on dust (effectively zero), matching the CVE's "easily exploitable, low-privilege, complete availability loss" class.

### Likelihood Explanation
Requires only a KYC-passing lender and an APR=0 configuration window, which is the documented mode for programmable-borrower pools and a normal state between rate changes. No privileged cooperation, no oracle manipulation, and no large capital. The trigger condition (manager sets nonzero APR while a dust APR0 receipt is pending) is exactly the routine configuration change the protocol supports — the attacker merely needs to front-run or follow any APR announcement with a dust `requestWithdraw`. One caveat: this finding's validity depends on the APR-raise-during-pending-APR0 sequence being unintended; the revert is clearly a deliberate accounting guard, but its permissionless triggerability is the bug.

### Recommendation
Either (a) prevent the state from arising: revert in `setAprs`/`setApr`/`setAprsWithBuffer` when `apr0TotalPrincipal != 0` and the new `unscaledApr` would be nonzero, forcing the APR change to happen only after the bucket settles; or (b) make `prepareStopEpochWithApr0` handle a nonzero APR gracefully by skipping APR0 interest accrual (paying APR0 receipts principal-only, since they accrued while APR was 0) instead of reverting. Option (b) is preferable because it removes the freeze entirely rather than pushing a revert onto manager operations.

### Proof of Concept
Foundry-style PoC sketch (fill in with repo helpers `_depositWithUser`, `_requestWithdrawWithUser`, `_startEpochAndCheckPrices` from `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testPocApr0StopEpochDos() external {
    // Pool configured with unscaledApr == 0 (as in APR0 / programmable-borrower mode).
    // Honest LP deposits a normal amount so the vault has TVL.
    address lp = makeAddr('lp');
    _depositWithUser(lp, 100_000 * ONE_SCALE);

    // Epoch 0 runs at APR 0, then stops.
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch());

    // Buffer of epoch 1: APR is still 0.
    // Attacker deposits dust and requests withdraw -> APR0 bucket.
    address attacker = makeAddr('attacker');
    uint256 dust = 1; // 1 wei underlying
    _depositWithUser(attacker, dust);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // routes to _requestWithdrawApr0
    assertEq(strategy.apr0TotalPrincipal(), dust);

    // Manager honestly raises APR for the upcoming epoch.
    vm.prank(manager);
    strategy.setAprs(10e18, 10e18 * (cdoEpoch.epochDuration() + cdoEpoch.bufferPeriod()) / cdoEpoch.epochDuration());

    // Epoch 1 starts and runs to its end; borrower fully funds repayment.
    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), type(uint256).max);

    // stopEpoch reverts -> epoch can never close while APR stays nonzero.
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(10e18, 0);

    // Confirm persistent DoS: repeated attempts revert identically.
    vm.warp(block.timestamp + 30 days);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(10e18, 0);

    // lp cannot claim/new requests settle: epochNumber never advances,
    // borrower retains all principal past epochEndDate.
    vm.prank(lp);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();
}
```

Uncertainty note: I could not execute the PoC (read-only mode), and whether the development team considers the `unscaledApr != 0` revert an accepted design constraint is not documented in the indexed code; if they do, this should still be flagged because it converts an accounting guard into a permissionless freeze/veto vector.
