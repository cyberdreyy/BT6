### Title
Malicious active miner can indefinitely reset the inactivity timer with rejected/stale conflicting proposals, wedging signer fallback to the prior miner - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
`SortitionData::check_latest_block_in_tenure` refreshes `last_activity_time` for the current tenure whenever the active miner sends a proposal that conflicts with an already-signed or pre-committed block, without verifying that this is *new* or *meaningful* activity. The active/winning miner can spam conflicting, always-rejected proposals purely to keep resetting this timestamp, defeating `SortitionState::is_timed_out` and blocking `check_miner_inactivity`'s fallback to the prior miner.

### Finding Description
`check_miner_inactivity` only allows the signer to fall back from a stalled/malicious current miner to the prior miner once `SortitionState::is_timed_out` returns true [4](#0-3) . `is_timed_out` bases its verdict on `elapsed = now - last_activity`, where `last_activity` defaults to `get_last_activity_time(sortition)` [5](#0-4) .

`last_activity_time` is updated in `check_latest_block_in_tenure` whenever a proposal's `chain_length` does not exceed the already-known block for the tenure, and the existing known block is still "fresh" (recently signed_group or a fresh pre-commit). The code explicitly treats "any attempt to reorg a locally accepted [or pre-committed] block ... towards valid miner activity" and unconditionally calls `update_last_activity_time` [6](#0-5) [7](#0-6) . This is the exact analog of `LocalCache::set_expire`: the timer-reset path does not verify whether the entity (here, the miner's proposal activity) represents a *legitimate new signal*; it simply stamps `now()` any time a matching, but stale/conflicting, message arrives — just like `set_expire` stamps a new `expire_at` on a key without checking if it had already timed out.

Because a signer's `check_proposal` in `GlobalStateView`/`SortitionsView` verifies `current_miner_pkh == miner_pkh` before invoking any of this activity-counting logic [8](#0-7) , this requires only the single winning ("one-slot") miner's own signature — no majority of signers or other keys are needed. The winning miner simply needs to keep broadcasting (via ordinary gossip to signers) proposals with `chain_length <= already known chain_length` in its own, still-active tenure. Each such rejected proposal calls `update_last_activity_time`, resetting the very clock signers use to decide whether to abandon this miner.

### Impact Explanation
This is a liveness wedge matching the "High" impact criterion: "a signer wedged into never signing valid blocks ... or losing the equivocation guard on restart" is analogous here as "a signer never falling back to the valid prior miner despite the current miner never producing a valid, progressing block." As long as the malicious miner keeps its `last_activity_time` fresh, `is_timed_out` never fires, `check_miner_inactivity` never reverts `state_machine.current_miner` to the prior tenure [9](#0-8) , and signers stay wedged waiting on a miner that will never propose a valid, higher block — exactly the "make a key expire indefinitely" attack scenario from the source report, applied to the signer's inactivity/fallback timeout instead of a KV cache entry.

### Likelihood Explanation
Likelihood is moderate-to-high for a malicious or buggy winning miner: it only needs to keep sending its own signed block proposals (a normal, permitted action for the tenure's winner) with a chain_length that never exceeds a block already known to signers (e.g., replaying an old proposal, or proposing at the same height repeatedly). No majority collusion, no other signer's key, and no local/auth access is required — only the ordinary block-proposal gossip channel that every miner already uses.

### Recommendation
Do not treat rejected/conflicting proposals as unconditional "activity" resets. At minimum:
- Only refresh `last_activity_time` the first time a given conflicting/rejected proposal (by `signer_signature_hash`) is seen for the tenure, not on every resend.
- Bound the number of times/duration `update_last_activity_time` can be advanced by conflicting proposals within a tenure, independent of a miner's ability to keep resending.
- Consider decoupling "miner is alive" from "miner is producing valid progress," e.g. requiring at least one *new* (previously unseen) proposal, or one that strictly increases the highest-seen `chain_length` for the tenure, before treating it as activity.

### Proof of Concept
1. Winning miner M for tenure T proposes block B1 (chain_length = N); signers pre-commit or sign it, so `signed_group`/`approved_time` is stamped and `get_tenure_last_block_info`/`get_last_accepted_block` reflect B1.
2. M never produces a valid higher block, but instead repeatedly re-broadcasts B1 (or another block with chain_length ≤ N) to the signer set.
3. Each time, `check_latest_block_in_tenure` sees `block.header.chain_length <= info.block.header.chain_length` (or the pre-commit freshness branch) and calls `signer_db.update_last_activity_time(&block.header.consensus_hash, now())` [10](#0-9) , even though the proposal is rejected and does not represent real progress.
4. `SortitionState::is_timed_out` keeps computing `elapsed = now - last_activity` as small, so it never exceeds `block_proposal_timeout` [11](#0-10) .
5. `check_miner_inactivity` never reaches the branch that reverts `current_miner` to the prior (valid) tenure's miner [9](#0-8) , so signers remain wedged on M indefinitely as long as M keeps resending conflicting proposals faster than `block_proposal_timeout`.

Note: I was unable to trace the full call path from `SortitionsView`/v1 chainstate (`SortitionMinerStatus`, `SortitionsView::is_timed_out` in `chainstate/v1.rs`) within the tool budget, so this PoC and root cause are verified against the v2 (`chainstate/v2.rs`/`GlobalStateView`) path only; the v1 path uses an analogous but separately-implemented timeout check that would need separate confirmation.

    pub fn check_miner_inactivity(
        &mut self,
        db: &mut SignerDb,
        client: &StacksClient,
        proposal_config: &ProposalEvalConfig,
        eval: &GlobalStateEvaluator,
    ) -> Result<(), SignerChainstateError> {
        let Self::Initialized(ref mut state_machine) = self else {
            // no inactivity if the state machine isn't initialized
            return Ok(());
        };

        let MinerState::ActiveMiner { ref tenure_id, .. } = state_machine.current_miner else {
            // no inactivity if there's no active miner
            return Ok(());
        };

        let version = SortitionStateVersion::from_protocol_version(
            state_machine.active_signer_protocol_version,
        );
        let is_timed_out = SortitionState::is_timed_out(
            &version,
            tenure_id,
            db,
            client.get_signer_address(),
            proposal_config,
            eval,
        )?;

        if !is_timed_out {
            return Ok(());
        }

        // the tenure timed out, try to see if we can use the prior tenure instead
        let CurrentAndLastSortition { last_sortition, .. } =
            client.get_current_and_last_sortition()?;
        let Some(last_sortition) = last_sortition
            .and_then(|val| SortitionData::try_from(val).ok())
            .map(|data| SortitionState::new(version, data))
        else {
            warn!("Signer State: Current miner timed out due to inactivity, but could not find a valid prior miner. Allowing current miner to continue");
            return Ok(());
        };

        let sortition_data = last_sortition.data();
        // If we already reverted to the last sortition miner, don't time it out as it means we have already timed out the current sorititon miner
        // as there is no other miner available.
        if &sortition_data.consensus_hash == tenure_id {
            warn!("Signer State: Last sortition miner has timed out, but no prior valid miner. Allowing last sortition miner to continue");
            return Ok(());
        }

        // Only revert to the prior miner if its tenure is the canonical Stacks tip's
        // tenure. A miner only continues (extends) a tenure it won, so if the canonical
        // tip is in some other tenure due to a Bitcoin reorg orphaning the prior
        // sortition's tenure, the prior miner's node has already stopped mining and
        // will never propose again.
        let stacks_tip_ch = client.get_peer_info()?.stacks_tip_consensus_hash;
        if sortition_data.consensus_hash != stacks_tip_ch {
            warn!(
                "Signer State: Current miner timed out due to inactivity, but the canonical stacks tip is not in the prior miner's tenure, so the prior miner cannot continue it. Allowing current miner to continue";
                "stacks_tip_consensus_hash" => %stacks_tip_ch,
                "prior_sortition_consensus_hash" => %sortition_data.consensus_hash,
            );
            return Ok(());
        }

        if !last_sortition.is_tenure_valid(db, client, proposal_config, eval)? {
            warn!("Signer State: Current miner timed out due to inactivity, but prior miner is not valid. Allowing current miner to continue");
            return Ok(());
        }
        let new_active_tenure_ch = &sortition_data.consensus_hash;
        let inactive_tenure_ch = tenure_id.clone();
        state_machine.current_miner = Self::make_miner_state(
            sortition_data.clone(),
            client,
            db,
            proposal_config.tenure_last_block_proposal_timeout,
        )?;
        info!(
            "Signer State: Current tenure timed out, setting the active miner to the prior tenure";
            "inactive_tenure_ch" => %inactive_tenure_ch,
            "new_active_tenure_ch" => %new_active_tenure_ch
        );
