### Title
Builder withdrawal amount committed to the execution payload exceeds the amount actually debited from the builder's balance, minting Gwei - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` places the *uncapped, requested* `BuilderPendingWithdrawal.amount` into the `Withdrawal` object that becomes part of `state.payload_expected_withdrawals` (a payload the block commits to and that the execution layer must honor), while `apply_withdrawals` only ever debits the builder by `min(withdrawal.amount, builder_balance)`. When a builder's queued withdrawal requests exceed its actual balance, the execution layer is instructed to pay the fee recipient the full requested amount even though the beacon state only reduced (or did not reduce) the builder's balance by that amount — Gwei is paid out that was never actually backed by a balance decrease.

### Finding Description
`get_builder_withdrawals` builds each `Withdrawal` with `amount=withdrawal.amount`, taken directly and unmodified from `state.builder_pending_withdrawals[i].amount`: [1](#0-0) 

This `Withdrawal` is what is committed into `state.payload_expected_withdrawals`, and per the spec's own note, this commitment is binding — "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer": [2](#0-1) 

However, `apply_withdrawals` caps the actual state mutation at the builder's *current* balance: [3](#0-2) 

So if a builder has multiple pending withdrawals queued whose requested amounts, in total, exceed its balance (e.g., two entries each requesting `MIN_ACTIVATION_BALANCE` while the builder's real balance is 0 or less than the sum), each `Withdrawal` in the payload still shows the full requested amount, but the builder's balance can only be reduced down to zero once. This is explicitly acknowledged and tested: the spec's own test comments confirm that the committed `Withdrawal.amount` equals the *requested* amount, not the capped/actual amount deducted from the builder: [4](#0-3) [5](#0-4) 

This is structurally identical to the TRST-M-11 bug pattern: a "delta" that should be paired 1:1 with an underlying balance decrease gets floored/capped on one side (the balance-state side) while the committed obligation (the leverage math in TRST-M-11; the execution-layer payment obligation here) is left un-adjusted, so the two sides of the equality diverge.

### Impact Explanation
The execution layer is contractually bound (by the payload commitment / withdrawals root) to credit `fee_recipient` with the full `Withdrawal.amount` for every entry in `payload_expected_withdrawals`, regardless of whether the beacon state actually debited that much from the builder. When the requested amount exceeds the builder's real balance, this results in Gwei being paid to a recipient that was never subtracted from any account — i.e., Gwei is created from nothing and paid to a non-owner (the fee recipient), directly breaking the total-supply invariant the spec itself calls out as important: [6](#0-5) 

### Likelihood Explanation
Any builder (or anyone able to queue `BuilderPendingWithdrawal` entries for a builder) can trigger this by queuing withdrawal requests whose cumulative requested amount exceeds the builder's balance — no coalition, client bug, or foreign key is required, and the spec's own test suite constructs exactly this scenario (`test_builder_withdrawal_insufficient_balance`, `test_all_builder_withdrawals_zero_balance`).

### Recommendation
`get_builder_withdrawals` should cap the committed `Withdrawal.amount` at the builder's currently available balance (tracking balance consumed by earlier withdrawals within the same batch), analogous to how `get_pending_partial_withdrawals` and full-withdrawal logic elsewhere cap amounts at `min(requested, balance)` before committing to the payload, so the amount promised to the execution layer never exceeds the amount actually debited from `state.builders[...].balance`.

### Proof of Concept
1. Builder `B` has `balance = 0` (or any amount less than the sum of its queued withdrawal requests).
2. `state.builder_pending_withdrawals` contains two entries for `B`, each requesting `amount = MIN_ACTIVATION_BALANCE` to `fee_recipient = F`.
3. `get_expected_withdrawals` → `get_builder_withdrawals` emits two `Withdrawal` objects, each with `amount = MIN_ACTIVATION_BALANCE`, into `payload_expected_withdrawals` (test: `test_all_builder_withdrawals_zero_balance`, lines 850-905 of `test_process_withdrawals.py`, confirms exactly this configuration).
4. `apply_withdrawals` executes `state.builders[B].balance -= min(MIN_ACTIVATION_BALANCE, 0)` twice, leaving `B.balance == 0` both times — no Gwei is actually removed from any account.
5. Yet the execution payload commits to paying `F` a total of `2 * MIN_ACTIVATION_BALANCE`, which the execution layer must honor per the spec's binding-withdrawals note — Gwei is created and paid to `F` that was never deducted from anywhere.

def test_builder_withdrawal_insufficient_balance(spec, state):
    """
    Test builder withdrawal with insufficient balance.

    Input State Configured:
        - state.builders[0]: Builder exists with only 1 ETH balance
        - builder_pending_withdrawals: Contains 1 entry requesting 5 ETH
        - builders[0].balance: 1 ETH (insufficient for requested 5 ETH)

    Output State Verified:
        - payload_expected_withdrawals: Contains 1 withdrawal
        - withdrawal.amount: 5 ETH (requested amount)
        - builders[0].balance: 0 (deduction capped to available balance)
        - builder_pending_withdrawals: Reduced by 1 (processed even if capped)
        - next_withdrawal_index: Incremented by 1
    """
    builder_index = 0
    withdrawal_amount = spec.Gwei(5_000_000_000)
    available_balance = spec.Gwei(1_000_000_000)

    prepare_process_withdrawals(
        spec,
        state,
        builder_indices=[builder_index],
        builder_withdrawal_amounts={builder_index: withdrawal_amount},
        builder_balances={builder_index: available_balance},
    )

    pre_state = state.copy()
    yield from run_gloas_withdrawals_processing(spec, state)

    assert_process_withdrawals(
        spec,
        state,
        pre_state,
        withdrawal_count=1,
        builder_balances={builder_index: 0},
        builder_pending_delta=-1,
        withdrawal_index_delta=1,
        withdrawal_amounts_builders={builder_index: withdrawal_amount},
    )
