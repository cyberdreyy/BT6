### Title
Pending instant withdrawals permanently block programmable-borrower mode transition - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
A KYC-passing lender can leave an unfunded instant-withdraw receipt in the withdrawal queue immediately before the honest owner enables programmable-borrower mode. Once `isProgrammableBorrower` is enabled, `startEpoch` always rejects the non-zero `pendingInstantWithdraws` state, while the only paths that fund those receipts require an epoch to already be running, producing an epoch-state deadlock that freezes the vault until the owner abandons or rolls back the migration. [1](#0-0) [2](#0-1) 

### Finding Description
The affected transition is the switch between ordinary-borrower accounting and programmable-borrower accounting. `setIsProgrammableBorrower` only checks that no epoch is running; it does not check or settle queued instant withdrawals before changing the accounting mode. [3](#0-2) 

An attacker first requests an instant withdrawal during the buffer after an APR reduction. `requestWithdraw` routes the request to `IdleCreditVault.requestInstantWithdraw`, burns the live tranche position, and creates a receipt rather than a normal pending withdrawal. [4](#0-3)  The strategy then increments `pendingInstantWithdraws`. [5](#0-4) 

After the owner enables minted-interest accounting and programmable-borrower mode, `startEpoch` calls `_checkProgrammableBorrowerMode`, which reverts whenever `isProgrammableBorrower && _pendingInstant() != 0`. [6](#0-5)  This check runs before the later start-epoch logic that would normally transfer available cash to the strategy through `collectInstantWithdrawFunds`. [7](#0-6) 

The alternative funding path cannot resolve the state because `getInstantWithdrawFunds` requires `isEpochRunning == true` and also rejects programmable mode. [8](#0-7)  Consequently, the receipt requires an active epoch to be funded, while programmable-mode epoch startup requires the receipt to be absent.

### Impact Explanation
With a 10,000-underlying pool, the entire 10,000-underlying TVL is unavailable for the duration of the deadlock: new epochs cannot start while the owner keeps programmable mode enabled, ordinary borrowers cannot receive pool funds, lenders cannot make new deposits or requests, and the attacker's own instant receipt cannot be paid.

The issue is temporary rather than strictly unrecoverable because the honest owner can call `setIsProgrammableBorrower(false)` and restart the ordinary epoch flow. [2](#0-1)  The attacker therefore does not make the migration permanently impossible, but can force the migration to abort and keep the pool frozen until operations revert the intended mode transition.

### Likelihood Explanation
Likelihood is conditional on a planned ordinary-to-programmable borrower transition and an instant-withdraw window created by a sufficiently large APR reduction. The attacker only needs to be a KYC-passing tranche holder and submit one ordinary `requestWithdraw` transaction before the owner's configuration change; no privileged role, malicious borrower, failed external vault, oracle manipulation, or borrower default is required. [9](#0-8) 

### Recommendation
Make mode switching an atomic state transition rather than only flipping `isProgrammableBorrower`. At minimum, `setIsProgrammableBorrower(true)` should revert while `IdleCreditVault(strategy).pendingInstantWithdraws() != 0`, matching the invariant enforced by `_checkProgrammableBorrowerMode`. A stronger migration function should also require `isInterestMinted`, verify that `strategy.borrower()` is the intended programmable-borrower contract, and ensure that legacy instant and normal withdrawal queues are either settled or explicitly supported before enabling the new mode.

### Proof of Concept
Add this regression test to `test/foundry/IdleCreditVault.t.sol`, which already provides the deployment fixture and epoch helpers.

```solidity
function testPendingInstantWithdrawBlocksProgrammableModeMigration() external {
  uint256 amount = 10_000 * ONE_SCALE;
  address attacker = makeAddr('migration-griefer');

  // Enable the instant-withdraw path before the epoch begins.
  vm.prank(manager);
  cdoEpoch.setInstantWithdrawParams(3 days, 1, false);

  _depositWithUser(attacker, amount, true);
  _startEpochAndCheckPrices(0);

  // End the epoch and lower the next APR enough to route the request
  // through requestInstantWithdraw instead of the normal queue.
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  uint256 attackerTrancheBalance = IERC20(AAtranche).balanceOf(attacker);
  vm.prank(attacker);
  uint256 pendingBasis = cdoEpoch.requestWithdraw(attackerTrancheBalance, address(AAtranche));

  IdleCreditVault vault = IdleCreditVault(address(strategy));
  assertEq(vault.pendingInstantWithdraws(), pendingBasis);

  // The honest owner starts the programmable-borrower migration.
  vm.startPrank(owner);
  cdoEpoch.setIsInterestMinted(true);
  cdoEpoch.setIsProgrammableBorrower(true);
  vm.stopPrank();

  // Buffer has elapsed, but startup reverts before the instant queue can be funded.
  vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod());
  vm.prank(manager);
  vm.expectRevert(NotAllowed.selector);
  cdoEpoch.startEpoch();

  assertFalse(cdoEpoch.isEpochRunning());
  assertEq(vault.pendingInstantWithdraws(), pendingBasis);

  // getInstantWithdrawFunds cannot clear it because the epoch is not running
  // and because programmable mode independently disables that path.
  vm.prank(manager);
  vm.expectRevert(NotAllowed.selector);
  cdoEpoch.getInstantWithdrawFunds();

  // Rolling back the migration unfreezes the pool, proving temporary freezing.
  vm.prank(owner);
  cdoEpoch.setIsProgrammableBorrower(false);
  vm.prank(manager);
  cdoEpoch.startEpoch();
  assertTrue(cdoEpoch.isEpochRunning());
}
```

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
