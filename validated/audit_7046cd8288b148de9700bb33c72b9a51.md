### Title
IAM wildcard injection via cache:key broadens AssumeRole session-policy Resource beyond the intended object - (File: cache/s3v2/s3.go)

### Summary
`generateSessionPolicy` builds the AssumeRole session-policy `Resource` ARN with `fmt.Sprintf("arn:%s:s3:::%s/%s", s3Partition, bucketName, objectName)`, embedding the attacker-influenced `objectName` (which is derived from the `.gitlab-ci.yml` `cache:key`) verbatim into a live IAM policy string. `cachekey.Sanitize` only normalizes path separators, decodes `%2f`/`%2e`, and resolves `..` traversal - it never strips or rejects IAM wildcard metacharacters (`*`, `?`), so a pipeline author can widen the Resource ARN to a wildcarded prefix and thereby broaden the scoped AssumeRole session's S3 access beyond the single cache object the credentials were meant to be limited to.

### Finding Description
The JSON-safety fix already in place (`json.Marshal(doc)` instead of raw string formatting, see the test `TestGenerateSessionPolicy_JSONInjection` in `cache/s3v2/s3_test.go` lines 649-677) only prevents the cache key from breaking out of the JSON `Resource` *string value* — it does not, and cannot, prevent the literal characters `*` and `?` from being interpreted by AWS IAM's policy engine as wildcards once they appear inside that string value, because IAM wildcard matching operates on the resolved ARN string, not on JSON syntax.

`objectName` is built deterministically as `runner/<token>/project/<id>/<cacheKey>` and the `cacheKey` component originates from the job's `cache:key` field in `.gitlab-ci.yml`, sanitized only by `cachekey.Sanitize` in `cache/cachekey/cachekey.go` (lines 27-57), which:
- decodes `%2f`/`%2e` and normalizes `\` to `/`,
- resolves `.`/`..` via `path.Clean`,
- trims trailing whitespace from path segments.

It performs no filtering of `*` or `?`. Consequently a cache key such as `foo/*` or `*` survives sanitization unchanged and is concatenated directly into `objectName`, then into the `Resource` ARN in `generateSessionPolicy` at [1](#0-0) . The resulting AssumeRole `Policy` parameter (sent to STS at [2](#0-1) ) grants access to every object matching that wildcard prefix — i.e., every cache key/object under `runner/<token>/project/<id>/` that matches the pattern — rather than being confined to the single cache object the job actually requested.

The fixed prefix `runner/<token>/project/<id>/` is not attacker-controlled, so this does not enable cross-project or cross-runner access. However, it defeats the per-object least-privilege design intent of the scoped session credentials: within the same project, a job can deliberately choose a cache key containing `*`/`?` so that the temporary AWS credentials it receives can read/write *other* cache objects for that project (e.g., other branches' or other jobs' cache entries) that it was never meant to access with that credential set.

### Impact Explanation
Concrete scoped impact: an unprivileged pipeline author can widen the S3 permissions granted to their job's temporary AssumeRole credentials from "one specific cache object" to "any cache object under the project's cache prefix," enabling unauthorized read/overwrite of other cache entries within the same project (e.g., cache poisoning of another branch's cache, or exfiltration of cache contents belonging to other jobs/branches in the same project) that the least-privilege session-policy design was intended to prevent.

### Likelihood Explanation
Preconditions: the runner must be configured for S3 cache using `s3v2` with an assume-role setup (`RoleARN`/`UploadRoleARN` configured) — this is a supported, documented configuration, not an admin misconfiguration. No special privileges are needed beyond being able to set `cache:key` in `.gitlab-ci.yml`, which any pipeline author can do. The exploit is fully repeatable and deterministic (same key always produces the same wildcarded ARN).

### Recommendation
In `generateSessionPolicy` (or earlier, in `cachekey.Sanitize`), reject or escape literal `*` and `?` characters in the portion of `objectName` derived from the user-supplied cache key before using it to build the IAM `Resource` ARN — e.g., percent-encode/replace `*`→`%2A` and `?`→`%3F` (AWS treats percent-encoded forms literally in Resource matching context is not guaranteed either way, so the safer fix is to reject cache keys containing `*`/`?` outright, or use an unambiguous separator/hash of the key rather than the raw key when constructing the Resource ARN).

### Proof of Concept
Go unit test extending `cache/s3v2/s3_test.go`:
```go
func TestGenerateSessionPolicy_IAMWildcardInjection(t *testing.T) {
    cfg := aws.Config{Region: "us-east-1"}
    c := &s3Client{awsConfig: &cfg, s3Config: &cacheconfig.CacheS3Config{}}

    // Attacker-controlled cache:key sanitized by cachekey.Sanitize, e.g. "foo/*"
    craftedKey := "runner/TOKEN/project/123/foo/*"

    policy, err := c.generateSessionPolicy("test-bucket", craftedKey, true)
    require.NoError(t, err)

    var doc policyDocument
    require.NoError(t, json.Unmarshal([]byte(policy), &doc))
    resource := doc.Statement[0].Resource

    // Assert the Resource ARN contains an unescaped IAM wildcard character,
    // proving the granted access is broader than the single requested object.
    assert.Contains(t, resource, "*", "Resource ARN must not contain an unescaped IAM wildcard derived from an untrusted cache key")
}
```
Expected result on current code: the assertion passes (bug reproduced) because `resource` equals `"arn:aws:s3:::test-bucket/runner/TOKEN/project/123/foo/*"`, i.e., an IAM wildcard resource pattern rather than a single-object ARN. After a fix rejecting/escaping `*`/`?`, this test should fail to compile/build such a key, or the resource string should contain an escaped literal instead of an active wildcard.
