### Title
Honest APR/duration reconfiguration retroactively reprices withdraw receipts minted under the old epoch parameters, leaving claims underfunded or over-minted - (File: contracts/IdleCDOEpochVariant.sol / contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to `GOVERNANCE_TOKENS_PER_NFT` being changed after tokens were minted (so later burns use a rate inconsistent with the mint rate), the epoch vault commits its funding obligation at `stopEpoch` time via `setAprsWithBuffer(_unscaledApr, _duration, _buffer)`, which stores `unscaledApr` and scales `lastApr` by `(duration + buffer) / duration` [1](#0-0) . Withdraw receipts, however, are priced later at *request* time inside `_calcInterestWithdrawRequest`, which un-scales the interest using the **current** `epochDuration`, `bufferPeriod`, `trancheAPRSplitRatio`, and `lastApr`/`unscaledApr` [2](#0-1) . Any honest manager/owner change to `lastApr`/`unscaledApr` (explicitly allowed mid-epoch via `setApr`/`setAprs`, IdleCreditVault.sol:225-235) or to the epoch duration/buffer between epochs makes the receipt amount computed at `requestWithdraw` inconsistent with the interest the borrower was asked to fund at `stopEpoch`.

### Finding Description
`requestWithdraw` burns `_principal` strategy tokens from the CDO and mints `_amount` receipt tokens to the user, where `_amount = principal + interest − fees`, and adds `_amount` to `pendingWithdraws`, which `stopEpoch` must source from the borrower [3](#0-2) . The interest term is derived in `_calcInterestWithdrawRequest` as `_calcInterest(_managedContractValue()) * _duration / (_duration + _buffer)`, i.e. it un-scales the buffer-inflated APR using the values of `epochDuration`/`bufferPeriod` that exist **when the request is made**, not the values used in `setAprsWithBuffer` when `lastApr` was fixed. The same retroactivity applies to `trancheAPRSplitRatio` via `_calcTrancheInterestShare` [4](#0-3)  and to the `unscaledApr == 0` branch that routes receipts into the `apr0Users` bucket instead of `withdrawsRequestsByEpoch` [5](#0-4) . Because `setApr` checks `msg.sender != _cdo && msg.sender != manager` but does not gate on epoch phase, an honest mid-epoch APR update (e.g., manager repricing, or `unscaledApr` toggling to/from 0) changes the rate applied to withdrawals of principal that accrued under the old rate — the exact "burn amount computed under a changed parameter" defect from the external report.

### Impact Explanation
If the effective un-scaling after the change produces a *higher* interest than what was funded at `stopEpoch` (e.g., `bufferPeriod` or `epochDuration` reduced, or `lastApr` raised by the manager), `pendingWithdraws` and minted receipt tokens exceed the borrower-funded amount; `claimWithdrawRequest` → `_transferFundedClaim` then underpays or reverts for later claimers — insolvency/temporary freezing of unclaimed yield, quantified as `receipt interest delta = fundedInterest * |d/(d+b) − d'/(d'+b')|` on the whole pool NAV. If it produces *lower* interest, receipts are under-minted relative to the interest already reserved, and the surplus stays stuck (or users who requested before the change are over/under-charged versus users after). The `unscaledApr` toggle additionally splits one epoch's requests across two incompatible accounting buckets (`withdrawsRequestsByEpoch` vs `apr0Users`/`apr0RateByEpoch`), breaking the "one receipt, one payout" invariant since `apr0RateByEpoch` distributes realized interest pro-rata only over the `apr0TotalPrincipal` bucket [6](#0-5) .

### Likelihood Explanation
Likelihood is Medium: it requires only an honest, documented manager/owner action — `setApr`/`setAprs` are manager-callable by design, and epoch duration/buffer are owner-configurable between epochs — combined with an unprivileged `requestWithdraw` in the buffer period, which is the normal user flow. No existing guard stops it: nothing snapshots the scaling parameters per epoch, and the receipt is minted/burned irreversibly at request time.

### Recommendation
Snapshot `lastApr`/`unscaledApr`, `epochDuration`, `bufferPeriod`, and `trancheAPRSplitRatio` per epoch (e.g., `paramsByEpoch[epochNumber]` set inside `stopEpoch`/`setAprsWithBuffer`) and have `_calcInterestWithdrawRequest` un-scale using the snapshot of the epoch the request belongs to, mirroring how `apr0RateByEpoch` and `lossRecoveryPriceByEpoch` already pin per-epoch values. Alternatively, restrict `setApr`/`setAprs` and duration changes to closed-pool phase (`epochEndDate == 0`) or apply them only to the next epoch.

```solidity
function testRetroactiveDurationChangeUnderfundsClaims() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                    // honest lender
    _transferBurnedTrancheTokens(address(this), true);

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    // stopEpoch sets lastApr scaled by (duration+buffer)/duration via setAprsWithBuffer
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // HONEST owner action between epochs: shorten bufferPeriod (or epochDuration)
    vm.prank(owner);
    cdoEpoch.setBufferPeriod(newBuffer);          // newBuffer < bufferPeriod

    // Unprivileged user requests withdraw in buffer. Interest is un-scaled with
    // duration'/(duration'+buffer') > intended, inflating the receipt.
    uint256 requested = cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));
    uint256 funded  = IdleCreditVault(address(strategy)).pendingWithdraws();
    // pendingWithdraws / minted receipts now exceed what borrower repaid for the epoch
    assertGt(requested, expectedClaimUnderOldParams);

    _startEpochAndCheckPrices(1);
    // borrower repays only the interest committed at stopEpoch
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, expectedInterest + funded /* < actual owed */);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, expectedInterest);

    // A second user's claim (or this user's full claim) reverts / is shortpaid:
    vm.expectRevert();                            // underfunded claim -> frozen funds
    cdoEpoch.claimWithdrawRequest();
}
```

The symmetric variant sets `unscaledApr` to 0 mid-epoch via `manager` calling `IdleCreditVault.setAprs(0, 0)`: requests made before the change sit in `withdrawsRequestsByEpoch` (interest already baked into `_amount`), while later requests go into `apr0Users` and are settled pro-rata from `apr0RateByEpoch` — two different payout bases for receipts of the same epoch, directly paralleling the inconsistent `GOVERNANCE_TOKENS_PER_NFT` burn.

```text
  function setAprsWithBuffer(uint256 _unscaledApr, uint256 _duration, uint256 _buffer) external {
    unscaledApr = _unscaledApr;
    setApr(_duration == 0 ? _unscaledApr : _unscaledApr * (_duration + _buffer) / _duration);
  }

  /// @notice set the fixed apr

  /// here it will not be scaled to include the buffer period
  function setApr(uint256 _apr) public {
    address _cdo = idleCDO;

    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
  }
```

```text
  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
  }
```
