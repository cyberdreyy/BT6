### Title
Lockup owner can supply a self-controlled whitelist contract at deployment, bypassing the foundation-controlled staking-pool whitelist and releasing locked/unvested NEAR early - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create()` lets the *caller who is paying for and will own the lockup* pass an arbitrary `whitelist_account_id` that overrides the factory's default (foundation-controlled) whitelist and is baked into the deployed `LockupContract` as `staking_pool_whitelist_account_id`. That value is the sole security boundary `select_staking_pool` relies on to ensure delegated NEAR can only go to a foundation-vetted staking pool. Because the owner controls which account is trusted as "the whitelist," they can point it at their own account and defeat the entire custody guarantee the whitelist is supposed to enforce.

### Finding Description
`LockupFactory::create()` accepts an optional `whitelist_account_id` parameter and uses it instead of the factory's own `whitelist_account_id` when constructing the lockup's `LockupArgs`: [1](#0-0) 

This value becomes `staking_pool_whitelist_account_id` on the deployed `LockupContract`: [2](#0-1) 

The lockup contract's only defense against delegating funds to an untrustworthy account is `select_staking_pool`, which calls `is_whitelisted` on whatever `staking_pool_whitelist_account_id` was set at init time, and trusts the boolean result unconditionally: [3](#0-2) 

The whitelist's entire purpose, per its own documentation, is to guarantee that only staking pools that "faithfully implement the spec" and "guarantee that the delegated tokens can not be lost or locked" can receive delegated funds from lockup contracts: [4](#0-3) 

Once a pool is "whitelisted" (by the attacker-controlled whitelist contract returning `true`), the owner can move the full locked/unvested balance to it via `deposit_to_staking_pool`, which checks only that the pool is idle and there is no active foundation termination — it performs no lockup/vesting check at all: [5](#0-4) 

Because the "staking pool" account is entirely attacker-controlled (it can be a plain account with a full-access key, or a trivial contract that simply forwards any deposit to the owner), the NEAR transferred via `deposit_to_staking_pool`/`stake` is permanently and immediately under the owner's control, completely bypassing `transfer()`'s `assert_transfers_enabled()` and `get_liquid_owners_balance()` checks that are supposed to gate early release of locked/unvested tokens: [6](#0-5) 

### Impact Explanation
This breaks the custody binding "an account trusted as a whitelist versus the code and arguments that trust was granted for." The whitelist account ID is meant to always be the NEAR Foundation-controlled whitelist so that only spec-compliant staking pools can custody delegated NEAR. `LockupFactory::create()`'s optional `whitelist_account_id` argument lets the deploying party (the future lockup owner) substitute their own account as the "whitelist," which lets them declare any account — including one they fully control — as a valid staking pool. They can then move the entire locked/unvested balance out via `deposit_to_staking_pool`/`stake`, i.e., locked or unvested tokens are released early, which is explicitly a Critical-severity impact ("locked or unvested tokens released early", "wrongly whitelisted ... deployment").

### Likelihood Explanation
High. Any owner who deploys their own lockup through `LockupFactory::create()` and self-funds/self-selects the `whitelist_account_id` argument can carry out this attack unassisted, with no cooperation from the foundation, a validator, or any other privileged party. The only prerequisite is that they deploy the lockup themselves supplying a custom whitelist parameter, which the factory explicitly supports.

### Recommendation
Remove the caller-supplied `whitelist_account_id` override in `LockupFactory::create()`, or restrict it so it can only be set/changed by the foundation account, never by the account paying for/owning the lockup. The lockup contract should only ever trust the whitelist account ID configured by the factory/foundation at genesis, not one chosen by the party whose funds are being locked.

### Proof of Concept
1. Attacker calls `LockupFactory::create(owner_account_id: <attacker>, ..., whitelist_account_id: Some(<attacker-controlled-account>))`, attaching the minimum deposit plus the amount to be locked with a vesting schedule.
   - `lockup-factory/src/lib.rs` lines 107-133 accept and use the custom `whitelist_account_id` instead of the factory's own.
2. The deployed `LockupContract` is initialized with `staking_pool_whitelist_account_id = <attacker-controlled-account>` (`lockup-factory/src/lib.rs` lines 140-153).
3. Attacker deploys a trivial account/contract `<fake_pool>` (fully controlled by them) and makes `<attacker-controlled-account>::is_whitelisted("<fake_pool>")` return `true`.
4. Attacker (as lockup owner) calls `select_staking_pool("<fake_pool>")`; `lockup/src/owner.rs` lines 12-41 queries the attacker's own whitelist contract and accepts `<fake_pool>` as valid.
5. Attacker calls `deposit_to_staking_pool(amount)` / `stake(amount)` for the full locked/unvested balance; `lockup/src/owner.rs` lines 81-120 only check idle/no-termination status, not vesting, and transfer the NEAR to `<fake_pool>`.
6. Since `<fake_pool>` is fully controlled by the attacker, they now hold the NEAR outside the lockup contract entirely, before lockup/vesting would have permitted a `transfer()`.

    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,

        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        self.assert_owner();
        assert!(amount.0 > 0, "Amount should be positive");
        self.assert_staking_pool_is_idle();
        self.assert_no_termination();
        assert!(
            self.get_account_balance().0 >= amount.0,
            "The balance that can be deposited to the staking pool is lower than the extra amount"
        );

        env::log(
            format!(
                "Depositing {} to the staking pool @{}",

                self.staking_information
                    .as_ref()
                    .unwrap()
                    .staking_pool_account_id
            )
            .as_bytes(),
        );

        self.set_staking_pool_status(TransactionStatus::Busy);

        ext_staking_pool::deposit(
            &self

                .unwrap()
                .staking_pool_account_id,
