### Title
Missing re-initialization guard in `LockupContract::new` allows owner takeover and fund theft - (File: `lockup/src/lib.rs`)

### Summary
The lockup contract's `#[init]` function `new` is missing the `assert!(!env::state_exists(), "Already initialized")` guard that every other sibling contract in this repository enforces (`staking-pool`, `whitelist`, `voting`, `multisig`, `lockup-factory`, `staking-pool-factory`). Because `new` is a plain public method with no owner/predecessor check, any unprivileged account can invoke it again after legitimate initialization and overwrite `owner_account_id`, `lockup_information`, `vesting_information`, and `foundation_account_id`, seizing full owner control of the contract and its locked NEAR balance.

### Finding Description
`LockupContract::new` builds and returns a fresh `Self` struct that fully replaces contract state, with no check that state does not already exist: [1](#0-0) 

Compare this to every other initializer in the repo, which explicitly guards against re-initialization: [2](#0-1) [3](#0-2) 

`grep` across the repo confirms `state_exists` is checked in `lockup-factory`, `multisig`, `staking-pool-factory`, `staking-pool`, `voting`, and `whitelist`, but is absent from `lockup/src/lib.rs`.

All owner-privileged operations (including token transfer) gate solely on `owner_account_id` recorded in contract state: [4](#0-3) [5](#0-4) 

Since `new` has no `assert_owner()` or any predecessor check, and can be called again after legitimate deployment (because the missing `state_exists` guard means it is not restricted to a single call), an attacker can call `new` a second time with `owner_account_id` set to their own account. The re-invocation resets `lockup_information` (recomputing `lockup_amount = env::account_balance()`, i.e. all NEAR currently held by the account, including previously locked funds) and can set `transfers_information: TransfersEnabled` with a past timestamp and no vesting schedule/foundation. The attacker is now the recorded owner and, since transfers are enabled and there's no vesting lock, can immediately call `transfer()` to move out the account's liquid balance.

This breaks the custody binding that "an account trusted as the lockup owner" should equal "the account the NEAR Foundation/employer actually designated as owner at genesis" — an unprivileged party can substitute themselves in.

### Impact Explanation
This is Critical: an unprivileged attacker can become the recorded `owner_account_id` of an already-funded lockup contract and subsequently move locked/vested NEAR tokens out via the `transfer` owner method, i.e., "NEAR moved by a party not entitled to it" / "locked or unvested tokens released early."

### Likelihood Explanation
Likelihood is high for any lockup contract for which this repository's initializer code is deployed as-is: the vulnerability requires no privileged access, no misconfiguration by the deployer beyond using the shipped `new` function, and no owner/foundation key compromise — merely a second call to `new` against the already-deployed, funded lockup account. This is a pure code defect, not a documented/misused initialization flow, since the documented flow (atomic create+deploy+init) does not itself prevent later re-invocation of the public `new` method.

### Recommendation
Add `assert!(!env::state_exists(), "Already initialized");` at the start of `LockupContract::new` in `lockup/src/lib.rs`, consistent with `staking-pool`, `whitelist`, `voting`, and `multisig` contracts, to make the initializer callable exactly once.

### Proof of Concept
1. Foundation/deployer creates and funds the lockup account, then calls `new(owner_account_id="owner1", ...)` — establishing legitimate state with locked NEAR balance.
2. Attacker (any account) sends a transaction calling `new(owner_account_id="attacker", lockup_duration=0, transfers_information=TransfersEnabled{transfers_timestamp: <past>}, vesting_schedule=None, release_duration=None, staking_pool_whitelist_account_id=<any valid>, foundation_account_id=None)` against the same lockup account.
3. Because no `state_exists` guard exists, this call succeeds and overwrites contract state: `owner_account_id` becomes `"attacker"`, `lockup_information.lockup_amount` is recomputed from the current (already-funded) `env::account_balance()`, and transfers are enabled with no vesting/termination in effect.
4. Attacker calls `transfer(amount, receiver_id=attacker_controlled_account)`. `assert_owner()` passes (predecessor == attacker, the new `owner_account_id`), `assert_transfers_enabled()` passes, and the liquid balance check passes — the NEAR is moved to the attacker. [6](#0-5)

    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,

            env::is_valid_account_id(owner_account_id.as_bytes()),

            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),

        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
