### Title
External-initiator credentials are not bound to a specific job, allowing any authenticated EI to trigger runs of arbitrary jobs via POST /v2/jobs/:ID/runs - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` only validates the EI access-key/secret pair against the `external_initiators` table and then injects a synthetic `clsessions.User{Role: UserRoleRun}` into the Gin context, without ever recording which specific EI or job the request is bound to. `PipelineRunsController.Create` subsequently treats any request that has this injected user object as a fully privileged "user" request and calls `App.RunJobV2(ctx, jobID, nil)` for whatever integer job ID is in the URL, with no check that the authenticated external initiator is associated with that job.

### Finding Description
`core/web/auth/auth.go` (`AuthenticateExternalInitiator`, lines 119-151) authenticates the caller purely off the `ExternalInitiatorAccessKeyHeader`/`ExternalInitiatorSecretHeader` values and looks up an `ExternalInitiator` row: [1](#0-0)  Once authenticated it stores the `ExternalInitiator` under `SessionExternalInitiatorKey` **and separately** fabricates a generic `User` object with role `run` under `SessionUserKey`: [2](#0-1) 

`PipelineRunsController.Create` (`core/web/pipeline_runs_controller.go`) then branches purely on whether *any* `SessionUserKey` object is present (`isUser`), not on which external initiator authenticated or which job it is scoped to: [3](#0-2)  Because the EI auth path also sets `SessionUserKey`, `isUser` evaluates to `true` for a request authenticated only as an external initiator. The handler never calls `auth.GetAuthenticatedExternalInitiator(c)` to check that the EI is authorized for the requested `jobID`; it simply parses the path parameter as an `int32` and calls `prc.App.RunJobV2(ctx, jobID, nil)` for that ID. The only historical binding mechanism — UUID-based webhook job matching against an EI's configured `externalInitiators` spec — has been explicitly removed (`job.ErrJobTypeRemoved`, lines 103-107 of the same file), leaving the int32-ID path as the sole route to trigger job runs, and that path performs no initiator-to-job binding check at all.

Thus any holder of valid credentials for **any** external initiator (registered for job A) can send `POST /v2/jobs/<job B's integer ID>/runs` with job B's EI headers replaced by their own EI's headers and trigger a run of job B, a job they were never authorized to trigger.

### Impact Explanation
An attacker who possesses only a restricted external-initiator credential (created for one specific job/webhook integration) can trigger pipeline runs for any other job on the node by supplying that job's numeric ID. Depending on the target job's task graph, this can cause unauthorized external HTTP calls, unwanted VRF/OCR pipeline executions, consumption of node resources/funds tied to task execution (e.g., paid data-source calls, gas-consuming bridge tasks), and cross-tenant/cross-integration abuse — a violation of the "one request is attributable to exactly one authorized job" invariant. This falls under unauthorized action on another user's job resource.

### Likelihood Explanation
Exploitation only requires possession of one legitimately issued (even narrowly scoped) external-initiator access key/secret pair — no admin, session, or elevated role is needed. The target job ID is a small, easily enumerable integer exposed via the `/v2/jobs` listing or observable job resource IDs. The request is a single unauthenticated-relative-to-target-job HTTP POST, fully repeatable, and requires no timing or race conditions, making this highly feasible for any EI credential holder.

### Recommendation
In `PipelineRunsController.Create`, distinguish between a real authenticated `User` (session/API-token) and an external-initiator-derived pseudo-user (e.g., via `auth.GetAuthenticatedExternalInitiator(c)`), and when the caller is an external initiator, verify the target job's `ExternalInitiatorWebhookSpec`/associated EI ID matches the authenticated EI before calling `RunJobV2`. Do not conflate "has run-role" with "has run-role for this specific job" by reusing `SessionUserKey` for both user and EI auth paths.

### Proof of Concept
1. In `core/web/pipeline_runs_controller_test.go`, create two external initiators `EI-A` and `EI-B` via `cltest.CreateExternalInitiatorViaWeb`.
2. Create Job A configured to only be triggerable via `EI-A` (or simply any job with a known integer ID) and Job B similarly with `EI-B`.
3. Authenticate using `EI-A`'s access key/secret headers (`static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`).
4. POST to `/v2/jobs/<JobB integer ID>/runs` using `EI-A`'s credentials.
5. Assert: current behavior returns `200 OK` and creates a `pipeline_runs` row for Job B (verifiable via `PipelineORM().FindRun`), proving the run was accepted despite `EI-A` having no relationship to Job B — expected/fixed behavior should reject with `401/403`.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}
