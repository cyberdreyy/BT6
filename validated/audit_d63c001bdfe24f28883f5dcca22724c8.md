### Title
ERC4626 liquidity exhaustion can indefinitely block epoch settlement and withdrawals - ([File: `contracts/strategies/idle/ProgrammableBorrower.sol`](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower.onStopEpoch` converts an economically covered but temporarily unavailable ERC4626 withdrawal into a reverting `stopEpoch` path. An unprivileged participant in the vault's underlying liquidity market can exhaust withdrawable liquidity before epoch settlement, causing `stopEpoch` to revert while the epoch remains running and user deposits/withdrawal requests remain frozen.

### Finding Description
`IdleCDOEpochVariant.startEpoch` pauses ordinary deposits and disables AA/BB withdrawal requests for the duration of the running epoch. [1](#0-0)  At epoch end, `stopEpoch` calls `onStopEpoch` before pulling the required cash from the programmable borrower. [2](#0-1) 

`onStopEpoch` calculates the shortfall and, when the borrower's vault shares economically cover it, calls `vault.withdraw`. [3](#0-2)  If the ERC4626 vault lacks immediate liquidity, the catch block reverts with `StopEpochVaultLiquidityUnavailable` instead of returning a failure status or entering a bounded recovery path. [4](#0-3)  Because this revert occurs inside the hook rather than inside the `try this.getFundsFromBorrower` block, the entire `stopEpoch` transaction rolls back and `isEpochRunning` remains true. [2](#0-1) 

An attacker who borrows or withdraws all immediately available liquidity from the underlying ERC4626 venue can therefore repeatedly make the settlement call fail. This is most relevant for programmable-borrower deployments whose idle funds are parked in a shared external vault rather than held directly by the credit vault. [5](#0-4) 

### Impact Explanation
All LP funds represented by the programmable borrower's vault position can remain unavailable for withdrawal while the external vault has insufficient liquid assets. Normal withdrawal requests cannot be funded because `stopEpoch` cannot transition the epoch to the buffer state, and ordinary deposits/requests remain disabled while `isEpochRunning` is true. [2](#0-1) 

The freeze applies to the greater of the required epoch pull or the pending withdrawal amount that must be recalled, i.e. `_amountToPullFromBorrower + _pendingWithdraws`; in close-pool mode this extends to the recalled principal. [6](#0-5)  This is temporary freezing rather than direct theft: recovery depends on external vault liquidity becoming available or privileged intervention succeeding later.

### Likelihood Explanation
The attacker does not need a privileged IdleCDO or borrower role. Any sufficiently capitalized participant who can consume the ERC4626 venue's liquid assets can trigger the condition before the honest manager calls `stopEpoch`; maintaining the freeze requires keeping that liquidity unavailable, for example by maintaining an external borrow. The existing test suite explicitly demonstrates that an otherwise-covered but unavailable vault withdrawal reverts and leaves the epoch and borrower accounting active. [7](#0-6) 

### Recommendation
Separate external liquidity recall failure from epoch-finalization failure by adding a bounded path for unavailable liquidity. For example, let `onStopEpoch` return a distinct shortfall status, allow partial settlement/recall, or enter a time-bounded recovery/default state after a configured grace period rather than making every `stopEpoch` call revert indefinitely. Any fallback should preserve the distinction between transient vault illiquidity and borrower insolvency so an honest borrower is not incorrectly defaulted.

### Proof of Concept
The repository already contains the core regression setup: a programmable-borrower vault whose `withdraw` is capped below the pending withdrawal amount causes `stopEpoch` to revert, leaves `defaulted == false`, leaves `isEpochRunning == true`, and preserves pending withdrawals. [8](#0-7) 

A fork PoC replaces the synthetic cap with an external liquidity drain:

```solidity
// test/foundry/ProgrammableBorrowerCreditVault.t.sol
function testStopEpochLockedAfterExternalVaultLiquidityDrain() external {
    _setUpProgrammableBorrowerCreditVault(GAUNTLET_FORK_BLOCK, GAUNTLET_USDC_PRIME);

    IERC4626 externalVault = IERC4626(GAUNTLET_USDC_PRIME);
    address liquidityDrainer = makeAddr("liquidity-drainer");
    uint256 lpDeposit = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(lpDeposit);
    cdoEpoch.requestWithdraw(
        aaTranche.balanceOf(address(this)) / 2,
        address(aaTranche)
    );
    _startEpochAndCheckPrices(0);

    uint256 pending = strategy.pendingWithdraws();
    assertGt(pending, 0);

    // In the live ERC4626 venue, the unprivileged attacker consumes all
    // immediately withdrawable underlying liquidity through the venue's
    // borrow/withdraw mechanism before the manager stops the epoch.
    drainUnderlyingVaultLiquidity(liquidityDrainer, externalVault);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    assertEq(strategy.pendingWithdraws(), pending);

    // Repeating the same sequence continues to revert while external
    // liquidity remains exhausted, so receipt holders cannot claim.
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);
}
```
