### Title
Removed multisig members' stale confirmations still count toward execution threshold, allowing request execution below the live-member quorum - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` decides whether a request has reached quorum purely by counting the size of the stored `confirmations: HashSet<String>` for that request against `self.num_confirmations`. `delete_member` only purges confirmation entries for requests that were *originated* by the removed member; it never scrubs that member's signature from the `confirmations` set of *other* pending requests it had already confirmed. As a result, a removed member's stale confirmation is still counted at execution time, letting a request execute with fewer currently-live approving members than `num_confirmations` requires.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` computes quorum as: [1](#0-0) 

`confirmations.len() as u32 + 1 >= self.num_confirmations` — this only checks the count of confirmation strings stored, without verifying each confirming identity is still `self.members.contains(...)`.

`delete_member` cleans up requests/confirmations only for requests whose *creator* (`r.member`) equals the removed member: [2](#0-1) 

Note the filter is `if r.member == member` (the request's originator), not a scan for `member` appearing inside any request's `confirmations` HashSet. So if member `B` created request `X`, and separately confirmed request `Y` (created by someone else), removing `B` deletes request `X` (since `B` is its originator) but leaves `Y`'s confirmation set untouched — including `B`'s stale confirmation string still present in `self.confirmations.get(&Y)`.

Later, when a live member confirms `Y`, the code adds 1 to `confirmations.len()` (which already includes `B`'s stale entry) and compares to `num_confirmations`. This lets `Y` execute even though only `num_confirmations - 1` *currently live* members actually approved it — the same class of bug as the reported "inconsistent commit information" issue: the code uses a snapshot/cached value (the confirmation set) as if it reflects present truth (current live membership), without re-validating each element against the current authoritative state (`self.members`).

This directly parallels the report's core bug class: a count/commitment derived from stale state is trusted instead of being reconciled against the state at the actual point of use.

### Impact Explanation
This breaks the multisig's core custody invariant: "a multisig request executed below threshold." A `Transfer`, `FunctionCall`, `AddKey`, or `DeployContract` action can be executed on the multisig's held NEAR/assets with fewer live-member approvals than the configured `num_confirmations`, i.e., funds can move (or privileged self-actions like `AddKey`/`DeployContract` can be approved) without the required quorum of *current* members. This matches the Critical impact category: "a multisig request executed below threshold."

### Likelihood Explanation
Requires normal, permitted usage: multiple pending requests, a member confirming one request and later being removed via a legitimate `DeleteMember` action executed by quorum, and one more live confirmation on the earlier request. No compromised keys, foundation access, or social engineering needed — only ordinary operational sequencing (member churn while multiple requests are outstanding), which is a realistic and even expected operational pattern for a long-lived multisig account.

### Recommendation
When removing a member in `delete_member`, scan `self.confirmations` for *all* requests (not only those the member originated) and strip the removed member's entry from every confirmation set. Alternatively/additionally, in `confirm()` (and anywhere quorum is computed), filter confirmations to only those entries whose signer/account is still present in `self.members` before comparing against `num_confirmations`, so quorum is always evaluated against live membership rather than a potentially stale cached set.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. `C` calls `add_request(Y)` (e.g., `Transfer` of funds) — `Y` has an empty confirmation set.
3. `A` calls `confirm(Y)` → confirmations = `{A}` (1 < 3, not yet executed).
4. `B` calls `confirm(Y)` → confirmations = `{A, B}` (2 < 3, not yet executed).
5. Separately, members create and confirm a `DeleteMember { member: B }` request with 3 confirmations (e.g., from A, C, D) — this executes and removes `B` from `self.members`. Per `delete_member`, only requests originated by `B` are cleaned; `Y` (originated by `C`) is untouched, so `Y`'s confirmations set still contains `B`.
6. `C` (still a live member) calls `confirm(Y)`. `confirmations.len()` is 2 (`A`, `B` still present) `+ 1 = 3 >= num_confirmations (3)` → `Y` executes.
7. Result: `Y` executed with approvals effectively from only `A` and `C` — 2 out of the 3 currently-live members (`A, C, D`) — while `B`'s stale confirmation from before its removal was counted toward the threshold, violating the K-of-N live-member quorum guarantee. [1](#0-0) [3](#0-2)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
