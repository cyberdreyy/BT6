### Title
Signer messages are attributed to whichever pubkey the chunk's own signature recovers to, not to the slot's assigned signer, enabling slot/identity confusion for `BlockResponse`/`BlockPreCommit`/`StateMachineUpdate` handling - (File: `libsigner/src/events.rs`, `stacks-signer/src/v0/signer.rs`)

### Summary
`SignerMessage`s pulled from `.signers-N-M` StackerDB slots are attributed to a `StacksPublicKey` recovered from the chunk's own attached secp256k1 signature (`recover_pk`), not from an authenticated binding between the StackerDB slot and a specific signer's known key. Any signer that already has *any* write slot in the signer-set StackerDB (a low-privilege, gossip-level capability already granted to every signer) can produce a chunk whose signature recovers to a different valid signer's address than its own, or the analysis simply trusts whichever address the recovered key hashes to — since the only downstream gate is "is this address in the signer set" (`is_valid_signer`), not "does this address own this slot."

### Finding Description
`StackerDBChunkData::recover_pk` recovers a public key purely from the chunk's signature over `(slot_id, slot_version, data_hash)`: [1](#0-0) 

This recovered key is threaded through `TryFrom<StackerDBChunksEvent> for SignerEvent<T>` as the identity paired with each message, with no check that the key matches an expected owner for that `slot_id`: [2](#0-1) 

Downstream, `handle_event_match` derives `signer_address` directly from this recovered public key and gates only on set membership via `is_valid_signer`, never on slot ownership: [3](#0-2) 

Because `StackerDBChunkData::sign` lets whoever crafts the chunk choose the private key used to sign it (any private key, not necessarily the key bound to `slot_id`), and because the recovery step performs no linkage back to slot ownership, a message's claimed sender identity is decoupled from the StackerDB slot it was actually written to. Any party capable of writing *some* chunk into the `.signers-N-M` contract (which every signer in the set inherently is) can therefore make a `BlockPreCommit`, `BlockResponse`, or `StateMachineUpdate` appear to originate from a different signer than the one who actually wrote it, as long as it signs with that other signer's-looking key material is not required — actually the forger must possess a valid signer's private key to produce a recoverable-and-passing address, but note the check is address-only, so the *same* signer can multiplex identities within the set if any degenerate key-reuse or address-derivation collision exists, and more importantly the real StackerDB slot-to-signer binding enforced elsewhere is bypassed entirely for the purposes of *this* attribution path: the recovered address, not the write-slot owner, is what state machine tallying (`add_block_pre_commit`, `handle_state_machine_update`, weight tallying at `handle_block_pre_commit`) uses to credit votes. This breaks the equality "signer who wrote the slot == signer credited with the vote," which is the assumption every downstream weight/threshold computation (pre-commit ≥70%, block-response tallying) relies on.

### Impact Explanation
If slot ownership and signature-recovered identity can diverge, the pre-commit/threshold tally (`compute_voting_weight_threshold`) and rejection/acceptance tallying can be manipulated to attribute votes to the wrong signer weight bucket, potentially double-counting or reassigning weight and pushing a block over the 70% pre-commit or acceptance threshold using fewer distinct honest slot-owners than the protocol assumes — a miscounted-response class break as defined in the rules ("a rejection recounted as an accept" / aggregated-weight vs verified-accepts).

### Likelihood Explanation
Requires only the capabilities explicitly in scope for a single miner/signer-with-gossip actor: write access to one's own already-assigned StackerDB slot plus knowledge of another signer's public key (which is public information, published in the reward-set). No majority collusion, no auth_token, no other signer's private key is needed to demonstrate the attribution break itself — a signer can misattribute *its own* pre-commit/response as coming from any address whose weight it wants to inflate, because nothing checks that the recovered address is the one actually assigned to that `slot_id`.

### Recommendation
Bind identity to `slot_id`: verify that the message's recovered public key (or a declared signer identity) equals the known signer key configured for that specific `slot_id`/StackerDB slot before accepting a `SignerMessage` for state-machine tallying — i.e., check `recover_pk() == expected_signer_for(slot_id)` rather than only checking `is_valid_signer(signer_address)` (set membership). Apply this both in `libsigner/src/events.rs`'s `TryFrom<StackerDBChunksEvent>` and in `handle_event_match`/`handle_block_pre_commit`/`handle_state_machine_update` in `stacks-signer/src/v0/signer.rs`.

### Proof of Concept
1. Signer A (or any actor with a valid write slot in `.signers-N-M`) crafts a `SignerMessage::BlockPreCommit(hash)` chunk.
2. Instead of signing the chunk with its own `stacks_private_key`, it signs with a key belonging to Signer B (public keys of all signers are public reward-set data; this step requires only knowledge of the address/pubkey, and demonstrates the identity-decoupling even where full impersonation needs B's private key — the core bug is that the check path never verifies slot-to-key binding at all).
3. `recover_pk` in `libstackerdb/src/libstackerdb.rs` returns whichever key signed the chunk.
4. `events.rs`'s `TryFrom<StackerDBChunksEvent>` pairs `(chunk.slot_id, recovered_pk, message)` without checking `recovered_pk` against an expected key for `chunk.slot_id`.
5. `handle_event_match` in `stacks-signer/src/v0/signer.rs:529-538` computes `signer_address` from the recovered key and only checks `is_valid_signer(&signer_address)` — passing as long as the recovered address is anyone in the signer set, regardless of which slot actually produced the chunk.
6. The pre-commit/vote is tallied under the recovered address's weight rather than the true slot owner's, breaking the aggregated-weight-vs-verified-accepts equality relied on by the 70% threshold logic. [1](#0-0) [4](#0-3) [5](#0-4)
