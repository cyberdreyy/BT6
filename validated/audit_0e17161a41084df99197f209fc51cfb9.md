### Title
`requestWithdraw` prices receipt interest at the current APR instead of the epoch-start APR, so a mid-epoch APR change retroactively reprices accrued interest - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
Analogous to the Canto `update_market()` bug — where crossing an epoch boundary applied the old epoch's `cantoPerBlock` rate to blocks belonging to the next epoch because `nextEpoch` was computed as `i + BLOCK_EPOCH` instead of `epoch + BLOCK_EPOCH` — `IdleCDOEpochVariant._calcInterestWithdrawRequest` applies a single "spot" rate (`_getStrategyApr()`, i.e. the vault's current `unscaledApr`) to interest for the *entire current epoch*, regardless of when during the epoch the request is made or whether the APR was changed mid-epoch. The borrower-funded interest pool (`expectedEpochInterest`) is fixed at `startEpoch` using the APR in effect at that time, so the two accounting legs diverge whenever the strategy APR is updated while an epoch is running.

### Finding Description
`requestWithdraw` (`contracts/IdleCDOEpochVariant.sol:739`) computes the receipt's interest via `_calcInterestWithdrawRequest` (`:856`), which calls `_calcInterest` → `_calcInterestWithApr(_amount, _getStrategyApr())` (`:800-808`). `_calcInterestWithApr` multiplies by `epochDuration` unconditionally, and `_getStrategyApr()` reads the vault's *current* `unscaledApr`.

Meanwhile, the cash that ultimately backs these receipts is `expectedEpochInterest`, computed once at `startEpoch` from the APR in force at epoch start, plus `pendingWithdraws` pulled from the borrower at `stopEpoch` (`getFundsFromBorrower(_amountToPullFromBorrower + _pendingWithdraws)`, `:408`).

If the manager legitimately raises the strategy APR mid-epoch (`IdleCreditVault.setApr`/`setAprs`), every subsequent `requestWithdraw` in that same epoch books interest at the *new* rate for the *whole* epoch duration — including the elapsed portion that accrued under the old, lower rate. This is exactly the boundary error class: the new rate is applied retroactively across the rate-change boundary, inflating `pendingWithdraws`/`pendingWithdrawFees` beyond what the borrower obligation (`expectedEpochInterest`, still priced at the old rate) plus the withdrawer's own prorated entitlement can cover.

Conversely, if the APR is lowered mid-epoch, requests priced after the change under-count interest already accrued at the old rate, shortchanging the withdrawer (a smaller, symmetric mispricing).

The guards in place do not stop this: `_updateAccounting()` only checkpoints management fees and NAV, `expectedEpochInterest` is not reconciled to APR changes mid-epoch, and nothing in `requestWithdraw` blends the old/new rates over their respective sub-periods.

### Impact Explanation
Withdraw-request receipts minted after a mid-epoch APR increase are over-collateralized relative to the interest the borrower actually owes for that epoch. At `stopEpoch` the CDO pulls `_expectedInterest + _pendingWithdraws` from the borrower; the inflated `pendingWithdraws` leg must be funded from pool assets, so when the receipts are claimed via `IdleCreditVault.claimWithdrawRequest`/`_claimFundedWithdrawRequest` (`contracts/strategies/idle/IdleCreditVault.sol:319`) the excess is socialized onto remaining tranche holders as reduced NAV, or leaves the last claimants underfunded. An unprivileged KYC'd lender (the attacker) simply times `requestWithdraw` after the honest APR change to lock in the inflated receipt — the same "spot rate applied across a boundary" exploit primitive as the reference bug.

### Likelihood Explanation
Requires an honest manager/owner calling `setApr`/`setAprs` (or `stopEpoch` scheduling a new APR that takes effect while requests still price at a rate inconsistent with `expectedEpochInterest`) while an epoch is running. This is a normal operational action — APRs are renegotiated between the pool and the borrower — and no sequencing guard prevents a lender from submitting `requestWithdraw` in the same or a subsequent transaction. Monetary loss scales with `(newApr - oldApr) * elapsed * requested principal`, so the exploitability grows with epoch duration and request size.

### Recommendation
Price withdraw-request interest from the rate regime(s) that actually governed the epoch, mirroring the reference fix (`nextEpoch = epoch + BLOCK_EPOCH`):
- Snapshot the APR (or the per-epoch interest rate) at `startEpoch` into a per-epoch variable, and have `_calcInterestWithdrawRequest` use that snapshot rather than the live `unscaledApr`; or
- Checkpoint accrual on APR changes (like `setFeeParams` does with `_accrueManagementFee` and `ProgrammableBorrower.setBorrowerApr` does with `_accrueBorrowerInterest`) so interest for the elapsed segment is fixed at the old rate before the new rate applies; and
- Keep `expectedEpochInterest` consistent with whatever rate basis is used for receipts, so `pendingWithdraws` never exceeds the borrower-funded interest plus principal.

### Proof of Concept
Foundry test against the epoch-variant CDO (sketch, to be run on a mainnet fork per repo convention):

```solidity
function test_MidEpochAprChangeInflatesWithdrawReceipt() external {
    uint256 amount = 10_000 * ONE_SCALE;
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);

    idleCDO.depositAA(amount);          // attacker (KYC'd lender)
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);       // epoch starts at APR_old; expectedEpochInterest fixed

    // Honest manager raises APR mid-epoch
    vm.warp(cdoEpoch.epochEndDate() - (cdoEpoch.epochDuration() / 2));
    uint256 newApr = initialProvidedApr * 2;
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(newApr, newApr);

    // Attacker requests withdraw: interest priced at newApr for the FULL epochDuration,
    // including the half already elapsed under initialProvidedApr.
    uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));
    uint256 inflated = _calcInterestAtApr(amount, newApr)
                     - _calcInterestAtApr(amount, initialProvidedApr);
    assertGt(inflated, 0);

    // stopEpoch pulls expectedEpochInterest (old APR) + pendingWithdraws (new APR);
    // receipt claim is funded by diluting remaining holders' NAV.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 expectedInterest = cdoEpoch.expectedEpochInterest();
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    deal(defaultUnderlying, borrower, expectedInterest + pending);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, newApr);      // next-epoch APR; does not fix this epoch's mispricing

    uint256 balBefore = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(address(this)) - balBefore, receipt);
    // receipt > principal + old-APR pro-rata interest -> excess paid from pool NAV
}
```

Note: this assumes `setAprs` is callable while an epoch is running (it is manager-gated and used mid-flow in the repo's own tests, e.g. `testApr0WithdrawRollsAcrossEpochsNoDoubleAccrual` calls it between epochs); if an additional epoch-phase guard exists that was not visible in the indexed code, the same mispricing still arises across the `stopEpoch` boundary if request pricing and `expectedEpochInterest` ever use different rate bases.
