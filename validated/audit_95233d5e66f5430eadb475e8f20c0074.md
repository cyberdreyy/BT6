### Title
Claimed instant-withdraw receipts stay in the per-epoch ledger and corrupt default-recovery accounting, freezing remaining claimants — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` pays out a funded instant withdrawal by zeroing only the aggregate `instantWithdrawsRequests[_user]`, but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` untouched. Analogous to the reused OA batch buffer that silently appended another `MI_BATCH_BUFFER_END` on every call, the per-epoch receipt ledger silently retains basis that was already consumed. When a borrower default is later finalized for that epoch, `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch basis, underflows on `instantWithdrawsRequests[_user] -= claimBasis`, and inflates the unfunded instant-receipt total used for recovery pricing. ### Finding Description
`requestInstantWithdraw` appends basis to three ledgers per call: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]`, plus the global `pendingInstantWithdraws`. On the funded claim path, only `instantWithdrawsRequests[_user]` is reset to zero and `pendingInstantWithdraws` is decremented separately via `collectInstantWithdrawFunds`; the two per-epoch mappings are never decremented or cleared.

Later, if the facility defaults, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — which includes receipts already claimed — then executes `instantWithdrawsRequests[_user] -= claimBasis`. For any user who already claimed (so `instantWithdrawsRequests[_user] == 0` or smaller than `claimBasis`), this subtraction underflows and reverts, permanently blocking that user's defaulted-epoch claim path and leaving `instantWithdrawClaimsByEpoch[defaultEpoch]` permanently inflated. The same stale basis also means `pendingInstantWithdraws` is clamped by `claimBasis >= pending ? 0 : pending - claimBasis`, further desynchronizing the unfunded-remainder ledger from reality. [3](#0-2) 

### Impact Explanation
- Permanent freezing of defaulted-epoch recovery: a user who claimed a funded instant withdrawal and then re-requested in the same epoch (or whose stale basis otherwise exceeds `instantWithdrawsRequests`) can never execute `_claimDefaultedInstantWithdrawRequest` — the call always reverts on the underflow, so the legitimately unfunded portion of their receipt is unclaimable.
- Recovery-price corruption for all claimants: because the stale `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` entries remain counted as unfunded basis, the default-recovery reserve is spread over phantom claims, diluting `defaultRecoveryPrice` for every other default claimant (socialized loss quantified as the sum of already-claimed instant basis).
- Broken invariant: "one receipt one payout" — the per-epoch ledger counts consumed receipts as outstanding.

### Likelihood Explanation
Requires (a) an epoch in which instant withdrawals are requested and funded via `collectInstantWithdrawFunds`, (b) at least one user claiming before the epoch ends, and (c) a subsequent borrower default finalized in that same epoch — an unprivileged claim plus ordinary epoch sequencing by honest manager/borrower, matching the unprivileged-attacker scope. It also triggers for a single request→claim when default finalization reads the stale mapping even if `instantWithdrawsRequests[_user]` is zero, since `0 -= claimBasis` still reverts for `claimBasis > 0`, which additionally wedges `claimInstantWithdrawRequest` for users whose only remaining basis is defaulted. Note: this assessment is based on the claim/clearing paths shown; I was not able to fully verify whether `finalizeDefaultRecovery` or `defaultInstantWithdrawsFinalized` processing separately purges these per-epoch entries — if it does, the impact reduces to reserve dilution rather than a hard revert.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers symmetrically with the request: decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount (tracking the request epoch, or iterating/storing the user's pending request epoch like `lastWithdrawRequest`). Alternatively, in `_claimDefaultedInstantWithdrawRequest`, cap `claimBasis` at `instantWithdrawsRequests[_user]` and skip the underflowing decrement when the funded remainder is zero.

```solidity
function testInstantClaimStaleBasisBlocksDefaultRecovery() external {
    // 1. deposit, start epoch so allowInstantWithdraw path is reachable
    idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);

    // 2. request instant withdraw of half the position, let CDO fund it
    uint256 req = cdoEpoch.requestInstantWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 2, AAtranche);
    // manager fulfills instant requests (getInstantWithdrawFunds / collectInstantWithdrawFunds)
    vm.warp(block.timestamp + instantDelay);
    cdoEpoch.claimInstantWithdrawRequest(); // instantWithdrawsRequests[this] -> 0, byEpoch stale

    // 3. same epoch: request another instant withdraw (unfunded this time)
    cdoEpoch.requestInstantWithdraw(req, AAtranche);

    // 4. borrower defaults; manager finalizes default recovery for current epoch
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // default path
    // finalizeDefaultRecovery(...) per production flow

    // 5. claim now reverts: claimBasis = stale epoch basis > instantWithdrawsRequests[this]
    vm.expectRevert(); // underflow in `instantWithdrawsRequests[_user] -= claimBasis`
    cdoEpoch.claimInstantWithdrawRequest();
```

```text
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);

    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
