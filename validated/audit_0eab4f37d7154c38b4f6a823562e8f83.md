## Analog Vulnerability Found

### Title
`getTokenLargestAccounts` performs unbounded iteration over attacker-inflatable token accounts, enabling single-call RPC DoS - ([File: rpc/src/rpc.rs])

### Summary
The external report describes a pattern where a user can cheaply create unbounded on-chain state (predictions, at a fixed low cost each) that is later fully iterated in a single downstream call (`claimReward`), causing unbounded gas/compute cost and a DoS. The same bug class exists in `JsonRpcRequestProcessor::get_token_largest_accounts`, which backs the `getTokenLargestAccounts` JSON-RPC method: it enumerates **every** token account for a given mint with no limit, filter, or pagination, and a mint's number of token accounts can be inflated arbitrarily cheaply by any unprivileged user.

### Finding Description
`get_token_largest_accounts` calls `get_filtered_spl_token_accounts_by_mint`, which returns the full, unbounded list of `(Pubkey, AccountSharedData)` pairs for every account owned by the given mint (via the secondary `SplTokenMint` index when enabled, or a full program-account scan otherwise): [1](#0-0) 

The caller then iterates the entire result set to unpack every single token account and build a bounded top-N heap — but the O(N) cost of loading and unpacking every account is incurred regardless of the heap size: [2](#0-1) 

Unlike `getProgramAccounts`, this endpoint takes only a `mint_str` and `commitment` — there is no `filters`, `dataSlice`, or limit parameter a client can use to cap the scan: [3](#0-2) 

Because creating an SPL token account for an existing mint is permissionless and only costs rent-exempt lamports (recoverable by closing the account), an attacker can cheaply mint millions of token accounts under one mint — directly analogous to the report's `predict()` call, where a fixed small fee (5 USDC) lets an attacker unboundedly grow the `predictions` array that is later iterated in full by `claimReward()`. A single subsequent `getTokenLargestAccounts` RPC call — requiring only one request, well within the `CLUSTER_SLOT_TIME_TARGET / 2` exclusion threshold — then forces the validator/RPC node to decode and unpack every one of those accounts synchronously on a blocking thread.

### Impact Explanation
A single low-rate RPC call (`getTokenLargestAccounts`) can be made to consume unbounded CPU/memory proportional to attacker-controlled, cheaply-inflatable state (number of token accounts for a mint), potentially stalling the RPC-serving thread pool and degrading or crashing the serving node — the same "unbounded cost for a single low-rate call" class explicitly listed as in-scope.

### Likelihood Explanation
Likelihood is High: creating SPL token accounts is a routine, permissionless, cheap operation available to any unprivileged user, and the RPC method offers no size cap, pagination, or filter to bound the scan. No secondary-index configuration avoids this, since even the indexed path still returns and processes every matching pubkey unbounded.

### Recommendation
Bound the work performed by `getTokenLargestAccounts`/`get_filtered_spl_token_accounts_by_mint`: enforce a maximum number of accounts scanned/unpacked per call (returning an error or partial/paginated results beyond the limit), and/or require this endpoint be gated similarly to `getProgramAccounts` scans (secondary index requirement, config-enabled limits) so a single call cannot force unbounded iteration over attacker-inflatable state.

### Proof of Concept
1. Select or create an SPL token mint.
2. Programmatically create a very large number (e.g., hundreds of thousands) of associated/token accounts for that mint — each costs only rent-exempt lamports, no elevated privileges required.
3. Issue a single `getTokenLargestAccounts` RPC call for that mint.
4. Observe that the RPC node must load and `StateWithExtensions::<TokenAccount>::unpack` every one of the created accounts before returning the top 20 (`NUM_LARGEST_ACCOUNTS`), causing large, attacker-controlled latency/CPU cost from one request.

        &self,
        mint: Pubkey,
        commitment: Option<CommitmentConfig>,
    ) -> Result<RpcResponse<Vec<RpcTokenAccountBalance>>> {
        let bank = self.bank(commitment);
        let (mint_owner, data) = get_mint_owner_and_additional_data(&bank, &mint)?;
        if !is_known_spl_token_id(&mint_owner) {
            return Err(Error::invalid_params(
                "Invalid param: not a Token mint".to_string(),
            ));
        }

        let mut token_balances =
            BinaryHeap::<Reverse<(u64, Pubkey)>>::with_capacity(NUM_LARGEST_ACCOUNTS);
        for (address, account) in self
            .get_filtered_spl_token_accounts_by_mint(
                Arc::clone(&bank),
                mint_owner,
                mint,
                vec![],
                true,
            )
            .await?
        {
            let amount = StateWithExtensions::<TokenAccount>::unpack(account.data())
                .map(|account| account.base.amount)
                .unwrap_or(0);

            let new_entry = (amount, address);
            if token_balances.len() >= NUM_LARGEST_ACCOUNTS {
                let Reverse(entry) = token_balances
                    .peek()
                    .expect("BinaryHeap::peek should succeed when len > 0");
                if *entry >= new_entry {
                    continue;
                }
                token_balances.pop();
            }
            token_balances.push(Reverse(new_entry));
        }
