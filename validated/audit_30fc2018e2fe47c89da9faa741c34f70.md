### Title
Silent misreporting of SPL Token-2022 UI balances when a mint has both `InterestBearingConfig` and `ScaledUiAmountConfig` extensions - ([File: account-decoder/src/parse_token.rs])

### Summary
`token_amount_to_ui_amount_v3` converts a raw token amount into a human-readable `ui_amount`/`ui_amount_string` by applying at most one of two independent value-adjustment extensions (`InterestBearingConfig` or `ScaledUiAmountConfig`), silently dropping the second one if both are present on the same mint. This mirrors the reported bug class: a value-conversion function assumes only one "scaling" dimension applies and never composes/converts using the second, producing an incorrect reported value for unprivileged RPC/pubsub consumers who trust it as ground truth (analogous to assuming `1 USG == $1` and skipping the USG price conversion).

### Finding Description
`token_amount_to_ui_amount_v3` in [1](#0-0)  uses an `if / else if / else` chain: if `interest_bearing_config` is `Some`, it computes the UI amount purely from the interest-bearing math and returns; only if that branch is absent does it check `scaled_ui_amount_config`. There is no code path that applies both adjustments when a mint carries both extensions simultaneously.

The `SplTokenAdditionalDataV2` values passed into this function are built by independently probing for each extension without checking for mutual exclusivity, e.g. in [2](#0-1)  and in [3](#0-2) , both `interest_bearing_config` and `scaled_ui_amount_config` are populated via `.get_extension(...).ok()` regardless of whether the other extension is also present on the mint. Nothing in this code enforces that a mint can only have one of the two extensions, so if the SPL Token-2022 program allows both extensions to coexist on a mint, an unprivileged RPC caller querying that mint's token accounts will get a `ui_amount`/`ui_amount_string` computed from only one of the two value adjustments, silently ignoring the other (e.g., ignoring the `ScaledUiAmountConfig` multiplier when an interest-bearing rate is also configured).

This same conversion function is reused by multiple unprivileged-user-reachable RPC/decoding paths:
- `getTokenAccountBalance` and `getTokenSupply` RPC methods [4](#0-3) 
- Parsed account data returned by `getAccountInfo`/`getProgramAccounts` via `parse_token_v3` [5](#0-4) 
- Transaction pre/post token balance reporting (`getTransaction`, transaction subscriptions) via `svm_token_info_to_token_balance` [6](#0-5) 

### Impact Explanation
The impact is data misreporting: an unprivileged RPC/pubsub consumer (wallet, indexer, dApp, exchange) querying balances or transaction token balances for a mint that has both extensions active would receive a UI-displayed amount that does not reflect the compounded effect of both value adjustments, understating or overstating balances presented to end users. This falls within the accepted impact category of "wrong ... account data returned ... or ... misreporting" for a single, unprivileged, low-rate RPC call, with no validator-role or privileged access required to trigger it.

### Likelihood Explanation
Triggering requires only that a mint on-chain be configured (by its own mint/freeze authority, an ordinary unprivileged token-2022 mint creator) with both `InterestBearingConfig` and `ScaledUiAmountConfig` extensions and then have any user query its balance/supply/transaction history through standard RPC methods — no validator or operator privileges are needed. The likelihood that this exact combination is exercised in practice depends on whether SPL Token-2022 permits both extensions on the same mint; if permitted, every ordinary balance query against such a mint deterministically triggers the misreporting.

### Recommendation
In `token_amount_to_ui_amount_v3`, detect when both `interest_bearing_config` and `scaled_ui_amount_config` are present and compose their effects (e.g., first apply the scaled-ui-amount multiplier to the interest-bearing-adjusted amount, or vice versa, consistent with whatever composition order the SPL Token-2022 program itself uses) rather than only ever applying the first branch matched.

### Proof of Concept
1. Create an SPL Token-2022 mint with both the `InterestBearingConfig` extension (nonzero rate) and the `ScaledUiAmountConfig` extension (multiplier ≠ 1) initialized.
2. Mint tokens to an account and call `getTokenAccountBalance` (or `getTokenSupply`, or `getParsedAccountInfo`) via RPC as an unprivileged client.
3. Observe that the returned `ui_amount`/`ui_amount_string` reflects only the interest-bearing calculation (per the `if` branch order in [7](#0-6) ), with the scaled-ui-amount multiplier silently ignored, producing a balance inconsistent with the mint's actual configured value semantics.

pub fn parse_token_v3(
    data: &[u8],
    additional_data: Option<&SplTokenAdditionalDataV2>,
) -> Result<TokenAccountType, ParseAccountError> {
    if let Ok(account) = StateWithExtensions::<Account>::unpack(data) {
        let additional_data = additional_data.as_ref().ok_or_else(|| {
            ParseAccountError::AdditionalDataMissing(
                "no mint_decimals provided to parse spl-token account".to_string(),
            )
        })?;
        let extension_types = account.get_extension_types().unwrap_or_default();
        let ui_extensions = extension_types
            .iter()
            .map(|extension_type| parse_extension::<Account>(extension_type, &account))
            .collect();
        return Ok(TokenAccountType::Account(UiTokenAccount {
            mint: account.base.mint.to_string(),
            owner: account.base.owner.to_string(),
            token_amount: token_amount_to_ui_amount_v3(account.base.amount, additional_data),
            delegate: match account.base.delegate {
                COption::Some(pubkey) => Some(pubkey.to_string()),
                COption::None => None,
            },
            state: convert_account_state(account.base.state),
            is_native: account.base.is_native(),
            rent_exempt_reserve: match account.base.is_native {
                COption::Some(reserve) => {
                    Some(token_amount_to_ui_amount_v3(reserve, additional_data))
                }
                COption::None => None,
            },
            delegated_amount: if account.base.delegate.is_none() {
                None
            } else {
                Some(token_amount_to_ui_amount_v3(
                    account.base.delegated_amount,
                    additional_data,
                ))
            },
            close_authority: match account.base.close_authority {
                COption::Some(pubkey) => Some(pubkey.to_string()),
                COption::None => None,
            },
            extensions: ui_extensions,
        }));

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };

pub fn svm_token_info_to_token_balance(svm_info: SvmTokenInfo) -> TransactionTokenBalance {
    let SvmTokenInfo {
        account_index,
        mint,
        amount,
        owner,
        program_id,
        decimals,
    } = svm_info;
    TransactionTokenBalance {
        account_index,
        mint: mint.to_string(),
        ui_token_amount: token_amount_to_ui_amount_v3(
            amount,
            // NOTE: Same as parsed instruction data, ledger data always uses
            // the raw token amount, and does not calculate the UI amount with
            // any consideration for interest.
            &SplTokenAdditionalDataV2::with_decimals(decimals),
        ),
        owner: owner.to_string(),
        program_id: program_id.to_string(),
    }
}
