### Title
Stale per-epoch instant-withdraw receipt survives normal claim and is paid a second time from the default-recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary

The kernel bug leaves a head pointer (`skb->prev`) referencing a segment that was already unlinked and freed; a later consumer walks the stale tail pointer and dereferences freed state. The direct analog lives in `IdleCreditVault.claimInstantWithdrawRequest`: when an instant-withdraw receipt is claimed through the normal funded path, only the aggregate `instantWithdrawsRequests[_user]` is cleared. The per-epoch bookkeeping `instantWithdrawsRequestsByEpoch[_user][epoch]` and the epoch total `instantWithdrawClaimsByEpoch[epoch]` are left stale. If a borrower default is later finalized in that same epoch while other instant receipts are still unfunded (`pendingInstantWithdraws != 0`), `defaultPendingClaimBasis()` counts the already-paid amount again, and `_claimDefaultedInstantWithdrawRequest` pays the attacker a second time out of `defaultRecoveryReserve` — a one-receipt-two-payouts violation drawn from other claimants' recovery.

### Finding Description

`requestInstantWithdraw` records the receipt in three places: the per-user aggregate `instantWithdrawsRequests[_user]`, the per-epoch entry `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and the epoch total `instantWithdrawClaimsByEpoch[epochNumber]` [1](#0-0) .

The normal claim path unlinks only the aggregate, leaving the per-epoch entries dangling — the exact "stale `->prev` after unlinked segment" pattern:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][*]` and `instantWithdrawClaimsByEpoch[*]` are never touched [2](#0-1) . `collectInstantWithdrawFunds` likewise decrements only `pendingInstantWithdraws`, not the per-epoch claim ledger [3](#0-2) .

At default finalization, both stale values are re-consumed:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0`, inflating `totalBasis` and diluting `defaultRecoveryPrice` for every recovery claimant [4](#0-3) .
- `defaultInstantWithdrawsFinalized` is set to `pendingInstantWithdraws != 0`, re-arming the defaulted-epoch instant claim path [5](#0-4) .
- On the attacker's next `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, burns nothing additional of substance (the receipt tokens were already burned in step one — actually the second `_burn` may revert unless the attacker re-acquires receipt tokens; see Likelihood), and transfers `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve` [6](#0-5) , which prefers spending the recovery reserve before funded balance [7](#0-6) .

No guard stops this: `_onlyIdleCDO` is satisfied because claims route through `IdleCDOEpochVariant.claimInstantWithdrawRequest`; `defaultRecoveryFinalized`/`defaultInstantWithdrawsFinalized` enable rather than block the path; there is no check that the per-epoch entry was already paid.

### Impact Explanation

Quantified loss: an attacker who requested and already claimed `X` underlying via a funded instant withdrawal receives an additional `X * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve` — direct theft of funds earmarked for honest defaulted-epoch claimants. The stale amount also inflates `totalBasis`, lowering `defaultRecoveryPrice` for all recovery recipients, so honest users lose twice (dilution plus drained reserve). A secondary effect: `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` can underflow once stale claims exceed the epoch total, reverting subsequent default claims — permanent freezing of remaining recovery for other instant-withdraw claimants [8](#0-7) .

### Likelihood Explanation

The sequence requires only unprivileged actions around honest privileged calls, in the "running → defaulted → finalized" phase:

1. Epoch running, instant withdrawals enabled (manager sets `instantDelay`, honest). Attacker calls the CDO's instant-withdraw entry, which invokes `requestInstantWithdraw` for `X`.
2. Funds are collected for instant claims (`collectInstantWithdrawFunds`, called by the CDO during the normal instant flow), reducing `pendingInstantWithdraws`; attacker claims via `claimInstantWithdrawRequest` and receives `X`. Per-epoch entries remain stale.
3. Same epoch: another user's instant request remains unfunded (`pendingInstantWithdraws != 0` — partial funding is an explicitly supported state per `_defaultPrefundedInstantReserve` [9](#0-8) ).
4. Borrower defaults (honest owner calls `stopEpoch(0,0)`); manager calls `finalizeDefault`/`finalizeDefaultRecovery` with whatever recovery is available.
5. Attacker calls `claimInstantWithdrawRequest` again. One caveat to verify in the PoC: the second `_burn(_user, claimBasis)` requires the attacker to hold `claimBasis` strategy tokens; since receipts were burned in step 2, the attacker may need to hold a like amount of strategy-token balance (e.g., by depositing again or buying receipt tokens, which are held as user strategy tokens), which is cheap since the recovery price is ≤ par. If the burn reverts instead, the bug degrades to basis inflation (dilution of recovery) plus liveness issues — still a fund-impact invariant break, but the double-payout variant should be attempted first.

Likelihood is moderate: it needs a same-epoch combination of funded instant claims, residual unfunded instant claims, and a borrower default — all within ordinary protocol operation, no privileged misbehavior required.

### Recommendation

Mirror the kernel fix ("repoint `skb->prev` at the last retained segment before returning"): keep all three instant-withdraw ledgers consistent when a receipt is unlinked. In `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][epoch]` for each epoch contributing to the aggregate and decrement `instantWithdrawClaimsByEpoch[epoch]` accordingly (this requires tracking per-epoch composition, or clearing per-epoch entries when the aggregate is zeroed). Similarly, `collectInstantWithdrawFunds` should reduce the funded portion of `instantWithdrawClaimsByEpoch`, or `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` should derive the pending basis from actually-unclaimed receipts rather than a cumulative epoch counter. A defense-in-depth check in `_claimDefaultedInstantWithdrawRequest` that the user's receipt-token balance covers `claimBasis` before paying would blunt the double payout but not the basis inflation.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
