### Title
Unprivileged front-running of the owner-derived lockup account lets an attacker fix a victim's lockup terms before the grantor - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` is a public, unauthenticated `#[payable]` method that anyone can call for any `owner_account_id`, and the resulting lockup contract is deployed at a deterministic account, `hex::encode(&env::sha256(owner_account_id)[..20]).<factory>` [1](#0-0) . Since NEAR account names must be globally unique, an attacker can call `create` first for a victim's `owner_account_id` with attacker-chosen `vesting_schedule`, `lockup_duration`, `lockup_timestamp`, `release_duration`, and `whitelist_account_id`, permanently squatting that address before the real grantor (the entity that is supposed to fund and configure the victim's lockup) can create the legitimate one.

### Finding Description
The invariant the question describes is: `lockup_at(derived_address(owner)).terms == grantor_chosen_terms(owner)`. The code never enforces this. `create` only checks `env::attached_deposit() >= MIN_ATTACHED_BALANCE` [2](#0-1)  — there is no `assert_called_by_foundation`, no restriction that `predecessor_account_id` must equal `owner_account_id` or any foundation/grantor account, and no check that the derived `lockup_account_id` isn't already claimed by someone else's intended grant.

The account ID at which the lockup will live is fully deterministic from `owner_account_id` alone: `hex::encode(&env::sha256(owner_account_id.as_bytes())[..20])` [1](#0-0) . Any unprivileged caller can therefore compute this address ahead of the real grantor and race to call `create` with:
- `owner_account_id` = the victim's real intended owner,
- `vesting_schedule` = `None` or an attacker-favorable schedule,
- `whitelist_account_id` = an attacker-deployed staking-pool-whitelist contract that the lockup's `select_staking_pool` will treat as trusted,
- a large attached deposit (attacker's own funds, refundable on failure).

`Promise::new(lockup_account_id).create_account().deploy_contract(...).transfer(...).function_call("new", ...)` executes with the attacker's parameters [3](#0-2) . If it succeeds, `on_lockup_create` just logs success and returns `true` — it never re-validates parameters against the real grantor's intent [4](#0-3) . When the legitimate grantor later calls `create` for the same `owner_account_id`, `create_account()` will fail (account already exists), the whole promise batch fails, `is_promise_success()` returns `false`, and `on_lockup_create` merely refunds the legitimate caller's deposit back to them [5](#0-4) . The refund path only protects the *caller's deposit* — it does nothing to stop the attacker's already-deployed, attacker-parameterized contract from permanently occupying the owner's canonical lockup address.

None of the existing guards (`assert_self`, `is_promise_success`) address authorization of *who* may call `create` for a given owner; they only guard the callback's caller identity and promise-result branching [6](#0-5) .

### Impact Explanation
An attacker permanently squats the canonical lockup address for any chosen victim owner, fixing terms (vesting schedule, whitelist/staking-pool trust anchor, durations) before the legitimate grantor acts. Wallets, explorers, and the protocol itself treat "the account at `hex::encode(sha256(owner))...`" as *the* trusted lockup for that owner. Once the real grantor's funding transaction is sent, it fails and is refunded to the grantor — but by then the address is permanently occupied by the attacker's contract, and any party (including the real owner, unaware of the squat) who later sends NEAR to that address, or who relies on it being the legitimate lockup, has funds routed into an attacker-configured contract with an attacker-chosen `whitelist_account_id`, effectively "an account whitelisted or a lockup deployed with parameters its rightful creator never chose" — a Critical impact category per the rubric. This is repeatable against every `owner_account_id` the attacker targets, cost being only the deposit for account creation/storage (refundable capital, aside from gas), and blast radius covers any owner whose lockup hasn't been created yet.

### Likelihood Explanation
No privileged role is required — any account able to send a transaction with `attached_deposit >= MIN_ATTACHED_BALANCE` (3.5 NEAR) can call `create` for an arbitrary `owner_account_id` [7](#0-6) . The attacker's deposit is refundable if the attack fails (it won't, since the attacker moves first), and the derived address is a pure function of a publicly known account ID — trivial to precompute and front-run. The only real cost is transaction/gas fees; this is fully repeatable across all not-yet-created owner accounts.

### Recommendation
Restrict `create` so only the foundation (or another designated, per-owner-authorized entity) can create a lockup, and/or require some proof (e.g. a signed authorization or restrict `predecessor_account_id == owner_account_id` for self-service cases while foundation-issued grants use `assert_called_by_foundation`). At minimum, before creating the account, the factory should verify that no lockup already exists there for a reason other than the legitimate flow, and ideally the derived address should incorporate a value only the grantor knows/controls (e.g. a nonce or grantor-approved commitment) rather than being solely `sha256(owner_account_id)`.

### Proof of Concept
```rust
// lockup-factory/src/lib.rs tests module
#[test]
fn test_attacker_squats_owner_lockup_before_grantor() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    let lockup_duration: WrappedTimestamp = 63036000000000000u64.into();

    // Attacker calls create() for victim's owner_account_id with attacker's whitelist
    context.predecessor_account_id = String::from("attacker"); // unprivileged
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(),           // victim owner
        lockup_duration,
        None,
        None,                              // attacker-chosen vesting (none)
        None,
        Some(custom_whitelist_account_id()), // attacker-controlled whitelist
    );

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let created = contract.on_lockup_create(
        lockup_account(),
        ntoy(30).into(),
        String::from("attacker"),
    );
    assert!(created); // attacker's contract now lives at derived address

    // Real grantor later attempts to create the legitimate lockup for the same owner
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    // Because create_account() at the same derived address fails, promise fails
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let legit_created = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(account_tokens_owner()),
    );

    // Binding broken: legitimate grantor's terms never got applied; address is attacker's
    assert_eq!(legit_created, false); // grantor only gets a refund
    // whitelist_account_id at lockup_account() == custom_whitelist_account_id() (attacker's),
    // not whitelist_account_id() (the legitimate default) -- terms diverged from grantor intent.
}
```
This demonstrates the equality `lockup_at(derived_address(owner)).terms == grantor_chosen_terms(owner)` is violated: the address is occupied by attacker-chosen terms, and the legitimate grantor's call only produces a refund, never the intended configuration.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

pub fn assert_self() {

pub fn is_promise_success() -> bool {
    assert_eq!(env::promise_results_count(), 1, "Contract expected a result on the callback");
    match env::promise_result(0) {
        PromiseResult::Successful(_) => true,
        _ => false,
    }
