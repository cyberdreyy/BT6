Confirmed: `BlockStatus` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs:70-82` tracks `responded_signers`, `gathered_signatures`, `total_weight_approved`, and `total_weight_rejected` as monotonically-growing accumulators with no retraction path, and this is the analog worth reporting.### Title
Stale rejection weight is never retracted after a signer later accepts, letting the miner permanently miscount a block as rejected — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side `StackerDBListener` accumulates `total_weight_rejected` and `total_weight_approved` in `BlockStatus` from `BlockResponse::Rejected`/`Accepted` messages, but the two counters are de-duplicated against two *different* sets. A signer's weight, once added to `total_weight_rejected`, is never removed even if that same signer subsequently sends an `Accepted` for the same block. `signer_coordinator.rs`'s `send_and_wait` loop checks the rejection threshold using this permanently-accumulated (never-decremented) `total_weight_rejected`, so stale/superseded rejections can permanently push a block into `SignersRejected` even though the true, current state of signer opinion has since converged on acceptance.

### Finding Description
`BlockStatus` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs:70-82` tracks:
- `responded_signers: HashSet<u32>` — used only to de-dup rejection weight additions.
- `gathered_signatures: BTreeMap<u32, MessageSignature>` — used only to de-dup acceptance weight additions.
- `total_weight_approved` / `total_weight_rejected` — running sums, never decremented.

In the message-handling loop (`stackerdb_listener.rs:386-591`):

- **Rejected branch** (`stackerdb_listener.rs:486-518`): weight is added to `total_weight_rejected` only `if block.responded_signers.insert(slot_id)` succeeds — i.e., only the first time this `slot_id` appears in `responded_signers`, regardless of whether it got there via a prior `Accepted` or `Rejected` message.
- **Accepted branch** (`stackerdb_listener.rs:443-465`): weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)` — a completely separate de-dup set from `responded_signers`.

Because these are two independent sets, a signer who first sends `Rejected` (adding their weight to `total_weight_rejected` and inserting their slot into `responded_signers`) and later sends `Accepted` for the same block (their slot is not yet in `gathered_signatures`, so their weight is *also* added to `total_weight_approved`) ends up permanently counted in `total_weight_rejected` with no corresponding removal. There is no code path anywhere in this file that decrements `total_weight_rejected` when a later acceptance supersedes an earlier rejection.

`signer_coordinator.rs`'s `send_and_wait` (`stacks-node/src/nakamoto_node/signer_coordinator.rs:487-518`) consumes this permanently-accumulated value directly:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { ... });
}
```
This is checked *before* the acceptance-threshold branch (`else if block_status.total_weight_approved >= self.weight_threshold`), so once cumulative (never-retracted) rejection weight crosses the blocking-minority threshold (`total_weight - weight_threshold`, i.e. >30% by default), the miner unconditionally aborts the proposal as `SignersRejected`, even if every signer whose weight contributed to that rejection has since sent an `Accepted` for the very same block.

This is the same root-cause shape as the reported analog: a tracked aggregate (`claimableAssets` in the report, `total_weight_rejected` here) is supposed to reflect the *current* true state (verified accepts/rejects), but the code that updates it never actually reflects the transition that should invalidate the stale value — in the report the delta computation was always 0 because there was no mutation between the two reads; here, the delta (retraction) that should occur on a reject→accept transition simply never fires because the two tallies are guarded by disjoint dedup sets. The bug breaks the "aggregated-weight vs verified-accepts" equality: `total_weight_rejected` no longer represents the current rejecting weight, only the historical maximum ever observed.

The signer-side local DB (`stacks-signer/src/signerdb.rs`, see `reject_then_accept` test) *does* correctly clear a stored rejection when a later signature is added for the same signer/block — confirming that "a rejection is a revocable opinion" is the intended semantics elsewhere in the codebase, but this node-side tally was not given the equivalent retraction logic.

### Impact Explanation
This is a **liveness wedge**: a miner can be forced to give up mining a fully-signable block (`Err(NakamotoNodeError::SignersRejected)`) purely due to stale rejection weight from signers who have since flipped to accept, even though a true 70%+ weight majority currently supports the block. Any signers that briefly reject for a transient/recoverable reason (e.g., timing races, momentarily-stale chain view, `ProposalTooOld` before a fix) and then later accept the same proposal (a documented, expected pattern — see `stale_proposal_of_accepted_block_resends_acceptance` in the test suite) will have their weight stuck against the block forever at the miner-tally layer. If enough signers individually exhibit this reject→accept flip across a proposal's lifetime, cumulative "phantom" rejection weight can cross the 30% blocking minority and permanently stall block production for that proposal, forcing the miner to re-mine — this matches the "signer wedged into never signing valid blocks" / liveness class explicitly called out as in-scope (High impact).

### Likelihood Explanation
No majority collusion, no external key material, and no privileged access is required. Any single signer that legitimately (or a small number of colluding-but-not-majority signers) sends a `Rejected` message and later a genuine `Accepted` message for the same block — a completely ordinary, sanctioned sequence of events per the "sticky acceptance"/"revocable rejection" model documented elsewhere in this codebase — triggers the stuck accounting. This can happen organically under normal network conditions (timeouts, re-evaluation, `ProposalTooOld` retries) without any adversarial intent, making the likelihood high.

### Recommendation
Track, per slot_id, the signer's *current* vote (accept vs reject) rather than two independently-latched cumulative sums. On receiving an `Accepted` for a signer previously counted in `total_weight_rejected`, retract that weight from `total_weight_rejected` (and vice versa for a later `Rejected` after a prior `Accepted`, symmetric to how `gathered_signatures` already excludes a signer from being double counted). Concretely, replace `responded_signers: HashSet<u32>` and the two separate dedup checks with a single `HashMap<u32, Vote>` (`Vote::Accepted(MessageSignature) | Vote::Rejected`) and recompute `total_weight_approved`/`total_weight_rejected` from that map (or explicitly subtract the previous vote's weight before adding the new one), so the running tallies always reflect only the signer's most recent, current message.

### Proof of Concept
1. Configure `N` signers with weight_threshold at 70% (blocking minority 30%).
2. Miner proposes block `B`.
3. Signer S1 (weight 31, e.g. one large signer or the sum of several) sends `BlockResponse::Rejected(B)` — `stackerdb_listener.rs` adds 31 to `total_weight_rejected`, inserts S1's slot into `responded_signers`.
4. `signer_coordinator.rs::send_and_wait` observes `31 + 70 > 100` → returns `Err(SignersRejected)` immediately… 

   To construct a scenario where the *stale* weight specifically causes the problem (rather than a live rejection), spread the reject weight across signers below the immediate trip point, e.g.:
   - Signers S1..S5 each weight 7 (35 total) send `Rejected(B)` in quick succession — `total_weight_rejected` becomes 35, immediately tripping `35 + 70 > 100`.
   
   Even with a smaller reject weight below the trip point (e.g. total 25), have S1..S4 (weight 25) send `Rejected(B)`, then all four immediately send `Accepted(B)` (valid signatures) before the timeout: `total_weight_approved` becomes 25 (correctly added, since `gathered_signatures` didn't have them), but `total_weight_rejected` **remains 25** (never retracted). Now have 6 more signers with weight 46 send `Accepted(B)`, bringing `total_weight_approved` to 71 (≥70, i.e., real threshold reached) — genuinely enough for the block to be signable. But if any further, unrelated small rejection later pushes `total_weight_rejected` from 25 to 31 (crossing 30), the miner's loop trips the `SignersRejected` branch on the *stale* 25 (now 31) even though `total_weight_approved` already legitimately shows 71/100 — because the rejection check is evaluated first and uses weight contributed by signers (S1..S4) who no longer actually reject.
5. Assert: `block_status.total_weight_rejected` in `stackerdb_listener.rs:487-518` never decreases despite S1..S4 having sent `Accepted` afterward, and `signer_coordinator.rs:509-540` can return `SignersRejected` using weight that is provably stale (contradicted by the same signers' later, valid acceptances stored in `gathered_signatures`).
