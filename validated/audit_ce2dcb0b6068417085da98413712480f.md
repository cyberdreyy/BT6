Confirmed: both `multisig/src/lib.rs` and `multisig2/src/lib.rs` share the same flaw — deleting a key/member only purges confirmations for requests *authored* by that key/member, not confirmations that key/member cast on *other* still-pending requests. Those stale confirmations remain in the `confirmations` set and continue to count toward `num_confirmations`.

### Title
K-of-N Threshold Bypass via Stale Confirmations from Removed Multisig Members - (File: multisig2/src/lib.rs)

### Summary
The `Multisig`/`Multisig2` contracts implement an on-chain analog of the ERC-4337 signer-verification problem described in the report: they must check that a "signer" approving a request is still an authorized party. `SignatureChecker`/`EnumerableSet` guidance in the report is precisely about validating signers against the *current* member set. In `multisig2/src/lib.rs`, `delete_member` fails to do this for existing confirmations: it only strips confirmations from requests the removed member *authored* [1](#0-0) , leaving that removed member's confirmation string intact inside `confirmations` maps of requests authored by *other* members. `confirm` then simply counts `confirmations.len()` without re-validating that every entry still belongs to a current member [2](#0-1) . The same pattern exists in the legacy `multisig/src/lib.rs::DeleteKey` handler, which also only clears requests authored by the deleted key [3](#0-2) .

### Finding Description
The custody/authorization binding that should hold is:
`confirmations counted for execution == confirmations from accounts that are members at execution time`.

`current_member()` is used only to gate who is *allowed to add a new confirmation* [4](#0-3) ; it is never used to re-validate confirmations that were recorded earlier and are already sitting in the `confirmations: LookupMap<RequestId, HashSet<String>>` store [5](#0-4) .

When a member is removed via `DeleteMember`, `delete_member` walks `self.requests` and clears confirmations only for requests where `r.member == member`, i.e. requests that member *created* [6](#0-5) . It does nothing to scrub that member's entry out of the `confirmations` HashSet of requests created by *other* members. The `confirm` function then executes as soon as `confirmations.len() as u32 + 1 >= self.num_confirmations` [7](#0-6) , blindly trusting stale entries.

Net effect: the recorded confirmation count can exceed the number of confirmations actually cast by parties who are members at execution time, breaking the K-of-N custody invariant the multisig is supposed to enforce.

### Impact Explanation
This is Critical per the rules ("a multisig request executed below threshold"). A `Transfer` (or any other privileged action, including `AddKey`/`AddMember`) can be executed with fewer live-member approvals than `num_confirmations` requires, because a removed member's old confirmation on an unrelated, still-pending request continues to count. NEAR held by the multisig account can move (or full-access keys/members can be added) without the intended threshold of currently-authorized approvers, since one of the "approvals" belongs to someone who is no longer a member.

### Likelihood Explanation
No attacker privilege is required beyond ordinary, legitimate multisig operation: members regularly rotate (e.g. key compromise response, staff turnover), and it is entirely normal for a request to sit unconfirmed while membership changes happen in parallel. Any time (a) a member confirms request R, (b) that member is later removed via `DeleteMember`/`DeleteKey` while R is still pending, and (c) enough *other* current members confirm R to make `stale + new == num_confirmations`, the threshold is bypassed. This is a routine sequence of independently-legitimate actions, not a contrived attack requiring collusion or a malicious insider at the moment of exploitation — the flaw is in the accounting, not in any single party's intent.

### Recommendation
When counting confirmations in `confirm` (and analogously `get_confirmations`), filter `confirmations` against the *current* `self.members` set (or `EnumerableSet` per the report's own suggestion) rather than trusting the raw count. Additionally, `delete_member`/`DeleteKey` should proactively purge the departing member's entry from every request's confirmation set, not only requests it authored, so `confirmations.len()` always reflects live members.

### Proof of Concept
1. Deploy `MultiSigContract::new([A, B, C, D], 3)` (multisig2/src/lib.rs). [8](#0-7) 
2. `A` calls `add_request(Transfer{amount})` → request `R` created, `confirmations[R] = {}`. [9](#0-8) 
3. `B` calls `confirm(R)` → `confirmations[R] = {B}` (1/3, not yet executed). [2](#0-1) 
4. Independently, `A`, `C`, `D` create+confirm a `DeleteMember{B}` self-request that reaches 3 confirmations and executes, removing `B` from `self.members`. Because `B` is not the author of `R`, `delete_member` does not touch `confirmations[R]`; it remains `{B}`. [10](#0-9) 
5. Now `members = {A, C, D}`, `num_confirmations = 3`. `C` calls `confirm(R)` → `confirmations[R] = {B, C}` (2/3).
6. `D` calls `confirm(R)` → `confirmations[R] = {B, C, D}` = 3 ⇒ `3 >= num_confirmations` ⇒ `execute_request` fires the `Transfer`. [7](#0-6) 

Result: the transfer executes with only 2 real, currently-authorized approvals (`C`, `D`) plus one phantom vote from a removed member (`B`), even though the contract is configured to require 3 live signers — the custody binding `signers who approved == 3 current members` is broken while `recorded confirmations == 3` is satisfied.

            env::panic_str(
                "Predecessor must be a member or transaction signed with key of given account",
            )

            .num_requests_pk
            .get(&current_member.to_string())
            .unwrap_or(0)

        assert(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some.",
        );
        self.num_requests_pk
            .insert(&current_member.to_string(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            member: current_member,
            added_timestamp: env::block_timestamp(),
            request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
