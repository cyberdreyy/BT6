### Title
Stale-delegation assertion panic during partitioned epoch-reward distribution can crash bank replay - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
The H‑12 report describes a class of bug where a per-account "checkpoint" value (`claimed[]`) is computed against a stale snapshot of a mutable balance, and is never reconciled when that balance changes before the checkpoint is consumed, leading to either an underflow/panic or orphaned funds. Agave's partitioned epoch-reward distribution has a structurally analogous pattern: stake rewards are calculated once at the epoch boundary against a `Stake.delegation.stake` snapshot, but stored one partition at a time over many subsequent blocks by re-reading the *live* `StakesCache` state and asserting it still matches the snapshot's expected value.

### Finding Description
`store_stake_accounts_in_partition` / `build_updated_stake_reward` in [1](#0-0)  loads the *current* stake account for each `PartitionedStakeReward` (computed at the epoch boundary) from the live `stakes_cache_accounts` when the block for its partition is processed, potentially many blocks after the reward was originally calculated.

When the `relax_post_exec_min_balance_check` feature (`adjust_delegations_for_rent`) is **not** active, the code takes the legacy path that hard-asserts the live delegation equals the pre-reward snapshot plus the reward: [2](#0-1) 


Here `stake` is the *live* account state (`stakes_cache_accounts.get(...)`, i.e., whatever the stake account currently looks like when this block executes), while `new_stake.delegation.stake` is `partitioned_stake_reward.inflation.stake`, a value computed and frozen back at the epoch-boundary calculation phase (see `calculate_stake_rewards_and_commissions` / `recalculate_stake_rewards` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`). If any ordinary user transaction mutates the stake account's `delegation.stake` field between the calculation block and the block that later processes that account's reward partition (e.g., via `Split`, `Merge`, `Deactivate`, `DelegateStake`, or a `Withdraw` that changes the delegation), the live value will diverge from the frozen `expected_delegation`, and the `assert_eq!` fires.

Grepping the codebase for reward-interval guards (`RewardInterval::InsideInterval`, `get_reward_interval`) shows such checks are only referenced from `runtime/src/bank/partitioned_epoch_rewards/mod.rs` and the vote program (`programs/vote/src/vote_processor.rs`, `programs/vote/src/vote_state/mod.rs`) — not the stake program's instruction processor. I was not able to fully confirm within this session whether `programs/stake/src/stake_state.rs` (or equivalent) independently blocks `Split`/`Merge`/`Deactivate`/`DelegateStake` while `EpochRewardStatus::Active` is set; this is the one piece of the chain I could not directly verify due to running out of tool iterations. If no such guard exists in the stake program itself, an ordinary staker transaction landing in one of the intermediate reward-distribution blocks would deterministically hit this `assert_eq!` and panic bank processing for every validator replaying that block — a consensus-halting/replay-path panic, not merely a local crash, since all validators would hit the identical panic when replaying the same block. This directly mirrors the report's "stale checkpoint vs. live mutable balance" root cause, just realized as a hard assert rather than an arithmetic underflow.

### Impact Explanation
If the code path is reachable (i.e., no independent stake-program-level block on delegation-mutating instructions during the reward-distribution window, or reachable via features/paths where `adjust_delegations_for_rent` is false), an ordinary user could craft a transaction, submitted during any block within the multi-block reward-distribution phase, that mutates the delegation of a stake account that still has a pending reward in a later partition. This would cause every validator replaying that transaction's block to hit `assert_eq!(...)` and panic, which for Agave's bank processing is a process abort — a network-wide liveness/consensus incident rather than an isolated node crash, since replay must be deterministic across validators.

### Likelihood Explanation
Likelihood is uncertain and conditioned on unverified facts:
- The vulnerable branch only triggers when `relax_post_exec_min_balance_check` (`adjust_delegations_for_rent`) is inactive; on networks where this feature is already activated, `adjust_delegation_for_rent` is used instead, which does not assert but instead clamps/mutates the delegation, avoiding the panic.
- Whether the stake program independently rejects delegation-mutating instructions (`Split`, `Merge`, `Deactivate`, `DelegateStake`) while `EpochRewardStatus` is `Active` could not be confirmed in this session; if such a guard exists in `programs/stake`, this path is not reachable by ordinary users and the finding should be downgraded to informational/no-impact.

### Recommendation
1. Verify (and if absent, add) an explicit stake-program-level rejection of instructions that mutate `Stake.delegation.stake` while the bank's `EpochRewardStatus` is `Active`/`RewardInterval::InsideInterval`, mirroring the existing protection already present for vote-program instructions.
2. Replace the `assert_eq!` panic in `build_updated_stake_reward` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:289-293`) with a recoverable `DistributionError` (as already modeled by `DistributionError::ArithmeticOverflow`/`AccountNotFound`) so any unexpected staleness degrades to a burned/skipped reward rather than aborting the process, consistent with how `checked_add_lamports` failures are already handled a few lines above.
3. Add a regression test that intentionally mutates a pending-reward stake account's delegation between the calculation and distribution phases (with `adjust_delegations_for_rent` disabled) to confirm distribution degrades gracefully instead of panicking.

### Proof of Concept
Not directly reproducible without confirming the stake-program-side guard; the reachability of this path hinges on whether `programs/stake` currently blocks delegation-mutating instructions during `EpochRewardStatus::Active`, which I could not verify in the time available. Conceptually, the PoC scaffold, based on the existing test harness, would be:
1. Set up a bank with `relax_post_exec_min_balance_check` feature disabled, and a stake account with a pending partitioned reward (as in `test_delegation_adjustment_at_distribution`, [3](#0-2) ).
2. Between the calculation block and the block where that stake's partition is processed, submit a `Split`/`Merge`/`Deactivate` stake instruction from the staker that changes `delegation.stake`.
3. Advance to the block that calls `distribute_epoch_rewards_in_partition` for that account's partition and observe the `assert_eq!` panic in `build_updated_stake_reward`.

```rust
        distribution_epoch: u64,
        stake_history: &StakeHistory,

        stakes_cache_accounts: &imbl::HashMap<Pubkey, StakeAccount<Delegation>>,
```
