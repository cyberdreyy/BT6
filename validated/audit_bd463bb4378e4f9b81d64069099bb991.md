## Finding confirmed (with a correction to the exact framing)

The core technical premise is accurate: `VestingSchedule::assert_valid` (defined at [1](#0-0) ) is **never called** anywhere in the lockup contract or lockup-factory — not in `LockupContract::new` for either the `VestingHash` or even the plain `VestingSchedule` variant ( [2](#0-1) ), and not in `LockupFactory::create` ( [3](#0-2) ). This means an owner can hash an internally-inconsistent `VestingSchedule` (e.g. `start_timestamp == end_timestamp`, with `cliff_timestamp` set earlier) into `VestingInformation::VestingHash` at creation time, and it is only checked for hash-equality — never validated — when later revealed via `assert_vesting` ( [4](#0-3) ) during `terminate_vesting` ( [5](#0-4) ).

`get_unvested_amount`'s denominator `vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0` is only reached when `block_timestamp` is `>= cliff_timestamp` and `< end_timestamp` ( [6](#0-5) ). If `cliff_timestamp < start_timestamp == end_timestamp`, that window `[cliff_timestamp, end_timestamp)` is non-empty and any call to `terminate_vesting` with a timestamp in that window triggers a `U256` division by zero panic.

**However**, one important correction to the question's framing: NEAR aborts and reverts *all* state writes for a call that panics, and in `terminate_vesting` the panic occurs inside `get_unvested_amount` **before** `self.vesting_information` is ever reassigned to `Terminating(...)`. So the contract does *not* get stuck in a persisted "Terminating-adjacent limbo" state — the transaction simply fails and the lockup remains in its prior `VestingHash` state, retryable at another block timestamp.

The real, more precise and still-Critical impact is different: because `cliff_timestamp`/`start_timestamp`/`end_timestamp` aren't validated at all, the crafted schedule can also make `block_timestamp >= end_timestamp` true almost immediately (e.g. by setting `end_timestamp` very close to lockup creation time), which makes `get_unvested_amount` return `0` forever afterward, and `terminate_vesting`'s `assert!(unvested_amount.0 > 0, "The account is fully vested")` ( [7](#0-6) ) then permanently blocks the foundation from ever terminating and reclaiming unvested tokens — regardless of the real intended multi-year vesting term. Combined with the transient division-by-zero window, the owner can guarantee that the foundation's termination call either reverts (transient) or is permanently rejected as "fully vested" (permanent), defeating the vesting clawback mechanism entirely.

### Title
`assert_valid` is never invoked for hashed/plain vesting schedules, letting an owner craft a schedule that permanently defeats foundation termination - (`lockup/src/types.rs`, `lockup/src/lib.rs`, `lockup/src/getters.rs`, `lockup/src/foundation.rs`)

### Summary
`VestingSchedule::assert_valid` is dead code — it's defined but never called in `LockupContract::new` or `LockupFactory::create` for either `VestingScheduleOrHash::VestingHash` or `VestingScheduleOrHash::VestingSchedule`. An owner creating their own lockup can therefore commit a hash whose pre-image has `start_timestamp == end_timestamp` (with `cliff_timestamp` set earlier), so that when the foundation later reveals it via `terminate_vesting`, `get_unvested_amount` either divides by zero (transient panic, retryable) or, by choosing `end_timestamp` to lie in the near past, is permanently evaluated as "fully vested," making `terminate_vesting`'s `assert!(unvested_amount.0 > 0, ...)` fail forever.

### Finding Description
The binding is: `assert_valid()` should guarantee `start_timestamp < cliff_timestamp‑or‑equal <= end_timestamp` for every `VestingSchedule` that can ever be revealed and consumed by `get_unvested_amount`. In reality, `assert_valid` is never called: not for `Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash)` and not for `Some(VestingScheduleOrHash::VestingSchedule(vs)) => VestingInformation::VestingSchedule(vs)` in `LockupContract::new` ( [2](#0-1) ), nor anywhere in `LockupFactory::create` ( [3](#0-2) ).

The owner (an unprivileged user creating their own lockup via `LockupFactory::create` with a chosen `vesting_schedule: Some(VestingScheduleOrHash::VestingHash(hash))`) computes `hash = VestingScheduleWithSalt{ vesting_schedule, salt }.hash()` off-chain with an invalid `vesting_schedule` (e.g. `cliff_timestamp < start_timestamp == end_timestamp`). This hash is stored unchecked in `VestingInformation::VestingHash`.

When the foundation later calls `terminate_vesting(Some(vesting_schedule_with_salt))`, `assert_vesting` ( [8](#0-7) ) only checks hash equality, never `assert_valid`, and returns the raw (invalid) `VestingSchedule` to `get_unvested_amount` ( [9](#0-8) ). For `block_timestamp` in `[cliff_timestamp, end_timestamp)`, the function computes `U256::from(vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0)` which is `0`, causing a division-by-zero panic during the transaction. Since NEAR reverts all pending state writes on panic, and the assignment `self.vesting_information = VestingInformation::Terminating(...)` in `terminate_vesting` ( [10](#0-9) ) happens strictly after the panicking call, no persisted "Terminating limbo" state results — the call simply fails and can be retried at a different timestamp.

The durable, Critical-severity consequence is different: by choosing `end_timestamp` to be very close to (or already past) the current time, `get_unvested_amount` returns `0` for essentially the entire life of the lockup once `block_timestamp >= end_timestamp`, and `terminate_vesting`'s `assert!(unvested_amount.0 > 0, "The account is fully vested")` ( [7](#0-6) ) then makes termination permanently impossible — even though the honestly-intended multi-year vesting term has not elapsed. No existing guard (`assert_called_by_foundation`, hash-equality check in `assert_vesting`) catches this, because none of them validate the internal consistency of the revealed schedule.

### Impact Explanation
The foundation's ability to claw back unvested tokens from a terminated employee is permanently defeated for any lockup whose owner deliberately crafts an inconsistent hashed (or even plain) vesting schedule at creation time. This matches the "locked or unvested tokens released early" Critical category: tokens that were supposed to remain clawable by the foundation under the vesting agreement instead stay fully under the owner's control indefinitely, because `terminate_vesting` can never succeed with `unvested_amount > 0`. This is scoped to that owner's own lockup (the owner cannot use it against a victim's lockup since they don't control the victim's hash pre-image), but it is fully repeatable by any user creating a lockup with vesting via the public `LockupFactory::create`.

### Likelihood Explanation
Feasibility is high and cost is low: any unprivileged user can call `LockupFactory::create` (attaching the minimum deposit) with `vesting_schedule: Some(VestingScheduleOrHash::VestingHash(hash))` where `hash` is computed off-chain from a self-chosen invalid `VestingScheduleWithSalt`. No special permissions, keys, or foundation cooperation are required to *create* the malicious lockup. The only prerequisite is that the foundation must actually agree to fund/associate such a lockup with a real employee relationship expecting normal termination semantics — the bug matters when the foundation later relies on `terminate_vesting` and it silently can never succeed.

### Recommendation
Call `vesting_schedule.assert_valid()` (or the pre-image schedule's `assert_valid`) at the point the raw `VestingSchedule` becomes known to the contract for both paths: immediately in `LockupContract::new` for `VestingScheduleOrHash::VestingSchedule`, and inside `assert_vesting`/`terminate_vesting` right after the hash is successfully matched and the pre-image `VestingSchedule` is revealed, before it is passed to `get_unvested_amount`.

#[should_panic] // division by zero
fn test_hash_vesting_bypasses_assert_valid_div_by_zero() {
    let mut context = basic_context();
    testing_env!(context.clone());

    // Invalid schedule: cliff before start, start == end (never validated at creation)
    let bad_schedule = VestingSchedule {
        start_timestamp: to_ts(GENESIS_TIME_IN_DAYS + YEAR).into(),
        cliff_timestamp: to_ts(GENESIS_TIME_IN_DAYS + YEAR - 100).into(),
        end_timestamp: to_ts(GENESIS_TIME_IN_DAYS + YEAR).into(), // == start_timestamp
    };

    let hash = VestingScheduleWithSalt {
        vesting_schedule: bad_schedule.clone(),
        salt: SALT.to_vec().into(),
    }.hash();

    // Confirms assert_valid is never invoked at creation: this succeeds despite invalid schedule.
    let mut contract = LockupContract::new(
        account_owner(),
        to_nanos(YEAR).into(),
        None,
        TransfersInformation::TransfersEnabled {
            transfers_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into(),
        },
        Some(VestingScheduleOrHash::VestingHash(hash.into())),
        None,
        AccountId::from("whitelist"),
        Some(account_foundation()),
    );

    // block_timestamp within [cliff_timestamp, end_timestamp)
    context.block_timestamp = to_ts(GENESIS_TIME_IN_DAYS + YEAR) - 50;
    context.predecessor_account_id = account_foundation();
    testing_env!(context.clone());

    // Panics with division by zero inside get_unvested_amount
    contract.terminate_vesting(Some(VestingScheduleWithSalt {
        vesting_schedule: bad_schedule,
        salt: SALT.to_vec().into(),
    }));
}

    pub fn get_unvested_amount(&self, vesting_schedule: VestingSchedule) -> WrappedBalance {
        let block_timestamp = env::block_timestamp();
        let lockup_amount = self.lockup_information.lockup_amount;
        match &self.vesting_information {
            VestingInformation::Terminating(termination_information) => {
                termination_information.unvested_amount
            }
            VestingInformation::None => U128::from(0),
            _ => {
                if block_timestamp < vesting_schedule.cliff_timestamp.0 {
                    // Before the cliff, nothing is vested
                    lockup_amount.into()
                } else if block_timestamp >= vesting_schedule.end_timestamp.0 {
                    // After the end, everything is vested
                    0.into()
                } else {
                    // cannot overflow since block_timestamp < vesting_schedule.end_timestamp
                    let time_left = U256::from(vesting_schedule.end_timestamp.0 - block_timestamp);
                    // The total time is positive. Checked at the contract initialization.
                    let total_time = U256::from(
                        vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0,
                    );
                    let unvested_amount = U256::from(lockup_amount) * time_left / total_time;
                    // The unvested amount can't be larger than lockup_amount because the
                    // time_left is smaller than total_time.
                    unvested_amount.as_u128().into()
                }
            }
        }
