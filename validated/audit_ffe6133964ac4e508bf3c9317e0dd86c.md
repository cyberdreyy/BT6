## Title
Unbounded `getProgramAccounts` scan without size/count limit enables RPC node resource-exhaustion DoS - (File: `rpc/src/rpc.rs`)

### Summary
The reported Solidity bug describes an unbounded on-chain array (`pool`) that is only ever appended to and is fully iterated by user-facing functions, so once enough elements accumulate the iteration cost exceeds the block gas limit and locks the contract. The closest analog in Agave is the `getProgramAccounts` RPC path: when secondary indexing is not enabled for a program (the default), the full-account scan performed to answer the request has **no byte or count limit**, unlike the parallel indexed path which enforces `scan_results_limit_bytes`. Because any unprivileged user can create an unbounded number of accounts owned by an arbitrary program (subject only to rent), and this scan is triggered by an ordinary, unauthenticated RPC call, a large enough set of program-owned accounts can make the scan consume unbounded memory/CPU on the RPC node, causing timeouts or crashes.

### Finding Description
`JsonRpcRequestProcessor::get_filtered_program_accounts` in [1](#0-0)  branches on whether a secondary `ProgramId` account index is configured:
- If the index is enabled, it calls `get_filtered_indexed_accounts`, which explicitly passes `self.config.scan_results_limit_bytes` down to `bank.get_filtered_indexed_accounts` [2](#0-1) , and the accounts-db layer aborts the scan once the accumulated byte size exceeds this limit (`test_get_filtered_indexed_accounts_limit_exceeded` demonstrates the abort behavior) [3](#0-2) .
- If the index is **not** enabled (the common/default case for most programs), the code takes the `else` branch and calls `bank.get_filtered_program_accounts` with only a predicate filter — no byte or count limit is passed, and the accompanying comment states "this path does not need to provide a mb limit because we only want to support secondary indexes" [4](#0-3) .

That unbounded call flows to `Bank::get_filtered_program_accounts` [5](#0-4) , which calls `Accounts::load_by_program_with_filter` [6](#0-5) . This performs a full `accounts_db.scan_accounts` over the entire account set matching the owner filter and materializes every matching account (with data) into an in-memory `Vec<KeyedAccountSharedData>` with no early-exit size cap, unlike the indexed path's `accumulate_and_check_scan_result_size` mechanism visible nearby in the same file [7](#0-6) .

Because account creation (and thus growing the set of accounts owned by any given program) is an ordinary, unprivileged operation available to any transaction sender, and `getProgramAccounts` is a standard unauthenticated JSON-RPC method exposed by `rpc_accounts_scan::AccountsScan` [8](#0-7)  and `JsonRpcRequestProcessor::get_program_accounts` [9](#0-8) , an attacker can (1) create a very large number of low-cost accounts owned by an arbitrary (even attacker-owned) program, and (2) issue `getProgramAccounts` for that program without any indexing configured, forcing the RPC node to attempt to load and clone every matching account's full data into memory in a single unbounded pass.

### Impact Explanation
This is directly analogous to the reported unbounded-array DoS: the array of "pool"-like elements (here, on-chain accounts) has no growth cap, and the code path that services ordinary/public requests iterates over the entire set without a resource limit in the non-indexed branch. On a node this can:
- Exhaust process memory (OOM) or induce excessive GC/allocation pressure while cloning large numbers of accounts synchronously inside `spawn_blocking`.
- Starve the RPC thread pool / blocking task pool for the duration of the scan, degrading or denying service to other RPC clients on that node.

Impact is scoped to RPC-serving nodes (not consensus), but for public-facing RPC infrastructure this can constitute a real availability DoS.

### Likelihood Explanation
Likelihood is moderate-to-low in default production deployments: many operators disable `getProgramAccounts` entirely or restrict it, and enabling `AccountIndex::ProgramId` for hot programs mitigates the issue by enforcing `scan_results_limit_bytes`. However, for any program without secondary indexing configured (the default unless explicitly opted in via `--account-index program-id`), the unbounded path is reachable by any user who funds enough accounts and issues the RPC call, requiring no privileged access.

### Recommendation
Apply a byte-size (or account-count) limit to the non-indexed `get_filtered_program_accounts` path in the same way `scan_results_limit_bytes` is enforced for the indexed path, e.g., have `Bank::get_filtered_program_accounts` / `Accounts::load_by_program_with_filter` accept and enforce an optional byte limit and abort the scan with a `ScanError` once exceeded, mirroring `accumulate_and_check_scan_result_size` used by the indexed accounts path.

### Proof of Concept
1. Deploy or select a program ID that has no secondary `ProgramId` account index configured on the target RPC node (default configuration).
2. Submit many transactions (from an unprivileged wallet) creating accounts owned by that program id, sized to maximize memory footprint per account (up to `MAX_ACCOUNT_DATA_LEN`), until a very large aggregate data set is created.
3. Call the public `getProgramAccounts` RPC method against the target program id.
4. Observe that `get_filtered_program_accounts` takes the unindexed branch [4](#0-3) , causing `bank.get_filtered_program_accounts` to scan and materialize the entire account set into memory with no limit, degrading or crashing the RPC process while other RPC users on the node are starved.

    pub async fn get_filtered_indexed_accounts(
        &self,
        bank: &Arc<Bank>,
        index_key: &IndexKey,
        program_id: &Pubkey,
        filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let bank = Arc::clone(bank);
        let index_key = index_key.to_owned();
        let program_id = program_id.to_owned();
        let byte_limit_for_scans = self.config.scan_results_limit_bytes;
        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(
                    &index_key,
                    |account| {
                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.
                        account.owner().eq(&program_id)
                            && filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                    },
                    byte_limit_for_scans,
                )
            })
            .await
            .expect("Failed to spawn blocking task")?;
        if sort_results {
            // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
            accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
        }
        Ok(accounts)
    }

        &self,
        bank: Arc<Bank>,
        program_id: Pubkey,
        mut filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> RpcCustomResult<Vec<(Pubkey, AccountSharedData)>> {
        optimize_filters(&mut filters);
        if self
            .config
            .account_indexes
            .contains(&AccountIndex::ProgramId)
        {
            if !self.config.account_indexes.include_key(&program_id) {
                return Err(RpcCustomError::KeyExcludedFromSecondaryIndex {
                    index_key: program_id.to_string(),
                });
            }
            self.get_filtered_indexed_accounts(
                &bank,
                &IndexKey::ProgramId(program_id),
                &program_id,
                filters,
                sort_results,
            )
            .await
            .map_err(|e| RpcCustomError::ScanError {
                message: e.to_string(),
            })
        } else {
            // this path does not need to provide a mb limit because we only want to support secondary indexes
            let mut accounts = self
                .runtime
                .spawn_blocking(move || {
                    bank.get_filtered_program_accounts(
                        &program_id,
                        |account: &AccountSharedData| {
                            filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                        },
                    )
                    .map_err(|e| RpcCustomError::ScanError {
                        message: e.to_string(),
                    })
                })
                .await
                .expect("Failed to spawn blocking task")?;
            if sort_results {
                // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
                accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
            }
            Ok(accounts)
        }
    }
