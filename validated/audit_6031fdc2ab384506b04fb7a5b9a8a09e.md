## Title
Consensus layer does not verify `ExecutionPayloadBid.fee_recipient` against the proposer's committed preference, allowing a builder payment to be diverted to an attacker-chosen address - (File: specs/gloas/beacon-chain.md)

### Summary
In the Gloas builder-payment design, a builder's payment for winning a bid is supposed to be routed to the fee recipient address that the block proposer authorized via a signed `SignedProposerPreferences` message. The only place this binding is checked is a P2P gossip-layer `IGNORE` rule; the state-transition function `process_execution_payload_bid` that actually creates the on-chain payment obligation never checks `bid.fee_recipient` against the proposer's signed preference at all.

### Finding Description
`process_execution_payload_bid` records the pending builder payment straight from the bid's own `fee_recipient` field with no cross-check against any proposer-authorized value: [1](#0-0) 

The design intent, per the builder/validator docs, is that `bid.fee_recipient` MUST equal the address the proposer signed in `SignedProposerPreferences` for that slot: [2](#0-1) 

But this binding is enforced only as a gossip-network `IGNORE` (not even `REJECT`) condition: [3](#0-2) 

`IGNORE` in the p2p spec means the message is simply not relayed further on gossip — it is not slashable, not consensus-enforced, and can be trivially bypassed since builders are explicitly permitted to deliver bids to a proposer through "off-protocol means": [4](#0-3) 

Critically, the validator construction checklist for including a bid in `BeaconBlockBody` never instructs the proposer to independently verify that `bid.fee_recipient` matches its own broadcast preference — it only restates the on-chain assertions found in `process_execution_payload_bid` (signature, funds, slot, parent hash, prev_randao): [5](#0-4) 

Consequently, `state_transition` will accept a block whose bid pays out to any `fee_recipient` the builder chooses, regardless of what the current proposer actually signed as their preferred payout address, as long as the bid signature and value checks pass. The pending payment is later promoted to a `BuilderPendingWithdrawal` unconditionally using that unchecked `fee_recipient`: [6](#0-5) 

and ultimately paid out during `process_withdrawals` to that address — an address whose validity was never checked by any consensus rule, only by a discardable gossip heuristic.

### Impact Explanation
This breaks the equality that a builder payment must go to the fee recipient the proposer actually authorized: "a builder payment or withdrawal misdirected... escaped" is explicitly a High-severity category. A colluding or compromised relay/builder can construct a validly signed bid whose `fee_recipient` differs from the proposer's signed `SignedProposerPreferences` for that slot, and if that bid reaches the proposer outside the gossip-validated path (a documented, permitted path), the resulting on-chain payment goes to an address the proposer never approved — with no consensus-level mechanism to catch or punish it. Since two spec-following nodes/proposers relying on different bid-sourcing channels (gossip-filtered vs. off-protocol/relay-sourced) can accept different fee recipients for functionally identical bids, and the state-transition function itself treats both as equally valid, this is a "checked-only-at-the-edge" authorization gap directly analogous to the Calico floating-IP issue: a privileged actor's annotation/field is applied to consensus-relevant state without validation, because the validation logic exists only in an optional, bypassable layer rather than in the authoritative processing path.

### Likelihood Explanation
Exploitation requires only a bid signed by an active builder (a normal, expected participant, akin to the "privileged attacker" in the underlying CVE who can set an annotation) and a proposer client that includes bids obtained via non-gossip channels (explicitly sanctioned by the spec's own validator guide, e.g. relay/off-protocol delivery), which is a realistic real-world builder-market topology. No control of the majority stake, no client bug, and no fork-choice manipulation is required — only a mismatch between the gossip-side filter and the consensus-side rule.

### Recommendation
Add an explicit assertion in `process_execution_payload_bid` (or in `process_parent_execution_payload`/bid inclusion checks) that binds `bid.fee_recipient` to the proposer's most recently signed `SignedProposerPreferences` for `bid.slot`, mirroring the p2p `IGNORE` check as a consensus-level `REJECT`/`assert`, so that the state-transition function — not merely the gossip network — enforces which address may legitimately receive the builder's payment.

### Proof of Concept
1. Proposer `P` for slot `S` broadcasts `SignedProposerPreferences{proposal_slot=S, fee_recipient=A}`.
2. Builder `B` (active, funded) crafts and signs `ExecutionPayloadBid{slot=S, fee_recipient=X≠A, value=v, ...}` satisfying every other field required by `process_execution_payload_bid` (correct `parent_block_hash`, `parent_block_root`, `prev_randao`, valid signature, sufficient builder balance).
3. `B` delivers this bid to `P` directly (or via a relay) rather than over the `execution_payload_bid` gossip topic, bypassing the gossip-only `IGNORE` check in `p2p-interface.md`.
4. `P` includes the bid in its block; `state_transition` runs `process_execution_payload_bid`, which performs none of the checks in step 2 related to `fee_recipient` and stores `BuilderPendingPayment(withdrawal=BuilderPendingWithdrawal(fee_recipient=X, amount=v, builder_index=B))`.
5. After quorum/epoch processing, `process_withdrawals` pays `v` Gwei to address `X` instead of `A`, with the block considered fully valid by every spec-following node.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
