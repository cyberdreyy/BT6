### Title
Unauthenticated `/readyz?full=1` endpoint discloses internal health-check error details - ([File: core/web/router.go], [File: core/web/health_controller.go])

### Summary
`GET /readyz` is registered on the unauthenticated router group in `healthRoutes` with no `auth.Authenticate` wrapper, and `HealthController.Readyz` returns per-check `presenters.Check.Output` (raw `err.Error()` text) to any caller who adds `?full=<anything>` to the request. This lets a fully unauthenticated attacker retrieve internal error strings from health checks (e.g. DB, RPC, or other subsystem errors) that may contain sensitive connection details.

### Finding Description
In `healthRoutes` (core/web/router.go:220-228), `/readyz` is registered directly on `r` (the base `api` group created in `NewRouter`, core/web/router.go:78-88) with no authentication middleware — unlike routes such as `/v2/*` which are wrapped in `auth.Authenticate(...)`. 

In `HealthController.Readyz` (core/web/health_controller.go:43-81), when the request includes any `full` query parameter (`c.GetQuery("full")`), the handler iterates over `checker.IsReady()` errors and puts each `err.Error()` string directly into `presenters.Check.Output` (line 68), then serializes all checks as JSON via `jsonAPIResponse`. There is no redaction/sanitization of the error text before it is returned to the client.

Notably, the codebase already contains a sibling endpoint, `PublicReadyz` (core/web/health_controller.go:27-37), whose doc comment explicitly states it exists because `Readyz` can leak "internal service state" via per-check details, and that `PublicReadyz` "never returns per-check details regardless of query parameters, to avoid leaking internal service state on publicly reachable endpoints." This shows the leak in `Readyz` is a recognized risk that was mitigated with a new public-safe endpoint, but `/readyz` itself is still registered on the unauthenticated group and still exposes full detail with `?full=`.

An unauthenticated attacker can simply call `GET /readyz?full=1` and read whatever text is inside any failing health check's error, which for many `services.Checker` implementations can include connection strings, DSNs, hostnames/ports, or RPC endpoint errors bubbled up from underlying failing dependencies.

### Impact Explanation
This is an unauthenticated information-disclosure vulnerability. Depending on which health check fails and what its error message contains (e.g., DB DSN fragments, RPC endpoint URLs, or other backend connection info), an anonymous network client can learn internal infrastructure details about the node without any credentials, aiding further attacks (e.g. targeting exposed RPC/DB endpoints). This matches an information-disclosure class impact rather than a direct fund-movement/auth-bypass impact.

### Likelihood Explanation
No preconditions or credentials are required — the endpoint is reachable by anyone who can send HTTP requests to the node's web server, and the trigger is a single `GET /readyz?full=1` request. The vulnerability manifests whenever any registered health check is failing and its `Error()` text embeds sensitive detail, which is a plausible and repeatable operational state (e.g., during a DB or RPC outage).

### Recommendation
Either remove per-check detail exposure from `/readyz` for unauthenticated callers (mirroring `PublicReadyz`'s behavior of never exposing `full` details), or require authentication on `/readyz?full=` specifically, or sanitize/generalize the `Output` field (e.g., only report check name + pass/fail without raw error text) before returning it to unauthenticated clients.

### Proof of Concept
1. In `core/web/health_controller_test.go`, add a test similar to `TestHealthController_Readyz` that uses a mock `Checker` whose `IsReady()` returns `false` and an errors map containing an error like `errors.New("failed to connect to postgres: postgres://user:pass@10.0.0.5:5432/db")`.
2. Start the app with `client := app.NewHTTPClient(nil)` (no auth headers/session set).
3. Call `client.Get("/readyz?full=1")`.
4. Assert the response body (JSON) contains the raw error string (e.g., `postgres://user:pass@...`), demonstrating disclosure to an unauthenticated caller — expected assertion for a fixed implementation would be that the body is empty or contains only generic status, not the raw error text.
