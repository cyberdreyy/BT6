### Title
`depositDuringEpoch` under-charges the management fee by ignoring the buffer period, letting a mid-epoch depositor mint more tranche shares than fair — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
Analogous to the Tigris finding where `_handleOpenFees` omitted the referral fee component and therefore let a position be sized with too much margin, `depositDuringEpoch` computes the fee haircut applied to a mid-epoch deposit's prorated interest using only the remaining epoch time (`remaining`), while the deposit itself participates for `remaining + bufferPeriod`. The missing buffer duration means the deposited principal's management fee is under-deducted, `trancheInterest` is overstated, and the share-minting formula `(amount + trancheInterest) * supply / expectedFinal` mints too many tranche tokens — diluting every existing holder of that tranche.

### Finding Description
In `contracts/IdleCDOEpochVariant.sol` (`depositDuringEpoch`, lines 656–733), the depositor's own projected earnings are netted against fees as:

```solidity
uint256 trancheInterest = _calcTrancheInterestShare(
    _netGainAfterFees(interest, _calculateManagementFee(_amount, remaining)),
    _tranche
);
```

where `interest` was deliberately computed over `(remaining + buffer) / (epochDuration + buffer)` of the scaled APR (lines 691–697), i.e. the deposit earns for the remaining epoch **plus the entire buffer period**. The management-fee deduction, however, uses `_calculateManagementFee(_amount, remaining)` — only the remaining epoch, omitting the `bufferPeriod` portion of the participation window.

Elsewhere in the same contract, the withdrawal path correctly recognizes that funds locked through the buffer must pay the management fee for that buffer time: `_withdrawRequestManagementFeeDuration()` adds `bufferEnd - block.timestamp` to the charged duration (lines 925–930), and `requestWithdraw` deducts `_totalWithdrawFees` (which includes that buffer-adjusted management fee) before fixing the receipt (lines 773–778). The deposit path applies the same conceptual fee over a strictly shorter duration.

Because `trancheInterest` is overstated by roughly `_amount * managementFee * bufferPeriod / (365 days * FULL_ALLOC)` (before the AA/BB split), the minted amount

```solidity
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
```

is inflated, while `expectedEpochInterest += interest` (line 728) credits the deposit with interest already net of the too-small fee. At epoch stop the depositor redeems more underlying than the fair net-of-fee entitlement; the excess is paid from the NAV shared with the other tranche holders.

### Impact Explanation
Direct, quantifiable value extraction from existing tranche holders: an attacker who is a KYC-passing lender (`isWalletAllowed`) deposits mid-epoch in a running epoch (AYS inactive, non-programmable borrower, epoch not past `epochEndDate`) and is minted shares worth more than `principal + fair net interest`. The stolen amount scales with `deposit size * managementFee * bufferPeriod / year`. With e.g. a 2% management fee and a 5-day buffer on a 30-day epoch, each deposit over-mints by ~0.027% of principal per deposit — repeatable every epoch and aggregatable, since nothing limits `depositDuringEpoch` frequency beyond `_guarded` limits. Loss is borne permanently by existing holders via a lower tranche price at `stopEpoch`.

### Likelihood Explanation
Low-to-moderate per-transaction magnitude but trivially repeatable: requires only a whitelisted wallet, an active epoch in a non-AYS, non-programmable deployment, and `isDepositDuringEpochDisabled == false`. No privileged cooperation is needed; the over-mint is deterministic arithmetic, not a race. The per-deposit skim is bounded by the buffer-length management fee, so the issue is a persistent leakage/dilution vector rather than a single large drain — consistent with the medium severity of the analogous Tigris fee-omission finding.

### Recommendation
Charge the management fee over the same window used for the deposit's interest accrual:

```diff
uint256 trancheInterest = _calcTrancheInterestShare(
-   _netGainAfterFees(interest, _calculateManagementFee(_amount, remaining)),
+   _netGainAfterFees(interest, _calculateManagementFee(_amount, remaining + buffer)),
    _tranche
);
```

Apply the symmetric correction at line 706 when netting `expectedInt` for existing holders (use the elapsed/remaining window that actually matches the fee that will accrue until funds become claimable, i.e. include the buffer), mirroring the buffer-inclusive duration already used by `_withdrawRequestManagementFeeDuration()`.

### Proof of Concept
Foundry fork test sketch (setup mirrors `test/foundry/IdleCreditVault.t.sol`):

```solidity
// configuration: non-AYS vault, fixed-APR borrower, epochDuration = 30 days,
// bufferPeriod = 5 days, managementFee = 2_000 (2%), no performance fee for isolation
uint256 amount = 1_000_000 * ONE_SCALE;

// victim deposits and epoch starts
idleCDO.depositAA(amount);
_startEpochAndCheckPrices(0);

// attacker (whitelisted) deposits mid-epoch
vm.warp(cdoEpoch.epochEndDate() - 10 days);
uint256 attackerTranche = cdoEpoch.depositDuringEpoch(amount, address(AAtranche));

// let borrower repay interest and stop the epoch
deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
vm.warp(cdoEpoch.epochEndDate());
vm.prank(manager);
cdoEpoch.stopEpoch(initialProvidedApr, 0);

// expected mint if buffer were included in the fee haircut
uint256 interest = _calcInterestAtApr(amount, apr) * (10 days + 5 days) / (30 days + 5 days);
uint256 correctMgmt = _calcManagementFee(amount, mgmtFee, 10 days + 5 days);
uint256 currentMgmt = _calcManagementFee(amount, mgmtFee, 10 days); // what the code used
uint256 overMintedValue = (interest_delta = correctMgmt - currentMgmt);
// assert attacker redeem > principal + interest - correctMgmt
assertGt(attackerTranche * cdoEpoch.tranchePrice(AAtranche) / ONE_TRANCHE_TOKEN,
         amount + interest - correctMgmt);
// and victim NAV is lower than it would be absent the under-charge
```

Caveat: I verified the arithmetic inconsistency (fee duration `remaining` vs participation window `remaining + buffer`) directly in `depositDuringEpoch` and contrasted it with `_withdrawRequestManagementFeeDuration`, but I did not fully trace `_managedContractValue()` to confirm whether the buffer-time management fee is otherwise captured elsewhere; if it is intentionally excluded for mid-epoch deposits this reduces to an accounting inconsistency rather than a loss.
