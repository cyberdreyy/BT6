## Analysis Result

**Confirmed: Valid finding.**

### Title
Front-runnable lockup address lets an unprivileged attacker deploy attacker-chosen lockup terms at a victim's canonical lockup address - (`lockup-factory/src/lib.rs::create`)

### Summary
`LockupFactory::create` derives the lockup account id deterministically as `sha256(owner_account_id)[..20].{factory}` and lets **any caller** attach the minimum deposit to create a lockup naming an arbitrary `owner_account_id`, with attacker-chosen `lockup_duration`, `lockup_timestamp`, `vesting_schedule` (or vesting hash), and `release_duration`. Since the address depends only on the string `owner_account_id` and not on the caller/predecessor, an unprivileged attacker can pre-empt the canonical address for any victim account before that victim's legitimate grantor (employer/foundation) issues the real grant.

### Finding Description
The broken binding: `lockup_address(owner_account_id) == terms_chosen_by(owner_account_id's_grantor)`. In reality, `lockup_address` is a pure function of `owner_account_id` computed in `create`: [1](#0-0) 

specifically: [2](#0-1) 

There is no check binding `env::predecessor_account_id()` to `owner_account_id`, and no on-chain registry preventing repeated or first-come calls to `create` for a given `owner_account_id`. `LockupContract::new` itself performs no authentication of who is allowed to set the owner either — it only validates account-id syntax: [3](#0-2) 

Exploit flow: attacker calls `lockup_factory.create(owner_account_id: <victim>, lockup_duration, lockup_timestamp, vesting_schedule, release_duration, whitelist_account_id)` with `MIN_ATTACHED_BALANCE` attached, choosing e.g. a `VestingSchedule` whose `end_timestamp` is already in the past (so `get_unvested_amount` returns 0 immediately) combined with a long `release_duration`, or any other terms the victim's real grantor never agreed to. Because `Promise::new(lockup_account_id).create_account()` succeeds (the account doesn't exist yet), the attacker's transaction wins the race and permanently occupies the canonical address `sha256(victim).factory`. When the legitimate grantor later attempts the intended `create` (or the equivalent off-chain `createAccount` flow) for the same `owner_account_id`, the `CreateAccount` action fails because the account already exists, and `on_lockup_create` refunds the *legitimate* funder's deposit: [4](#0-3) 

The legitimate lockup with the grantor's intended terms can never be deployed at that address — the address now permanently carries the attacker's chosen parameters instead, with `owner_account_id` still legitimately set to the victim. No guard (`assert_owner`, `assert_self`, foundation check, whitelist check) restricts who may call `create` or `new` for a given `owner_account_id`; the only foundation-related restriction is that `foundation_account_id` is forced to the factory's own configured value when a vesting schedule is present: [5](#0-4) 

which does not prevent the rest of the terms (`lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`) from being attacker-chosen.

### Impact Explanation
This matches the explicitly listed Critical category: "a lockup deployed with parameters its rightful creator never chose." The victim's canonical lockup address ends up carrying vesting/release terms an attacker picked rather than the ones their employer/grantor intended, and the legitimate grant transaction is blocked (its `CreateAccount` action fails and funds are refunded to the would-be legitimate funder, not lost, but the intended deployment never happens). This is repeatable once per victim account id (the address is permanently squatted once created) and requires no privilege beyond a regular NEAR account and `MIN_ATTACHED_BALANCE` (3.5 NEAR).

### Likelihood Explanation
Any unprivileged account can call `create` on the public lockup factory with `MIN_ATTACHED_BALANCE` attached and an arbitrary `owner_account_id` string (does not require the victim's key or cooperation). The only cost is the attacker's own attached deposit, which becomes locked into a lockup contract owned by the named victim (not recoverable by the attacker), which is a real deterrent but does not stop a griefer motivated purely by blocking a specific grant, and the deterministic address makes the target fully predictable in advance.

### Recommendation
Bind lockup creation authorization to the intended owner or a trusted deployer: e.g., require a signature/attestation from `owner_account_id` (via a callback or an on-chain claim/allowlist step) before `create` is permitted to name that account as owner, or require `predecessor_account_id == owner_account_id`, or route lockup creation exclusively through a permissioned/foundation-gated call so arbitrary unprivileged accounts cannot pre-empt another account's canonical lockup address.

### Proof of Concept
`cargo test` plan (extending `lockup-factory/src/lib.rs` test module):
1. Initialize `LockupFactory` as in existing tests.
2. As an attacker predecessor (`attacker.testnet`), call `contract.create(victim_account_id, attacker_chosen_duration, Some(attacker_chosen_lockup_timestamp), Some(VestingScheduleOrHash::VestingSchedule(vesting_with_past_end_timestamp)), Some(attacker_chosen_release_duration), None)` with `MIN_ATTACHED_BALANCE` attached.
3. Assert the computed `lockup_account_id = sha256(victim).factory` equals the deterministic address (as done via `lockup_account()` helper in `test_utils.rs`).
4. Simulate a subsequent legitimate `create` call for the same `victim_account_id` from the real grantor; assert its `CreateAccount` promise fails (in `near-workspaces`/`RuntimeStandalone` this manifests as `Promise::new(...).create_account()` failing because the account exists), confirming the legitimate deployment is blocked at that address.
5. Assert the deployed lockup's `vesting_information`/`lockup_information` match the attacker-supplied terms, not any terms the victim's real grantor authorized — proving the equality `lockup_address(owner) == terms_chosen_by(owner's_grantor)` is broken.

    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,

        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),

                    owner_account_id,

                    lockup_timestamp,

                    },
                    vesting_schedule,
                    release_duration,

                env::predecessor_account_id(),

                gas::CALLBACK,
            ))

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
