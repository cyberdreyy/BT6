## Title
Stale-conflict blind spot lets a signer equivocate on cross-tenure sibling blocks at the same height — (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`Signer::handle_block_pre_commit` decides whether to sign a block that has crossed the pre-commit threshold by asking whether any previously-signed block at the same or higher height still "conflicts" with it [1](#0-0) . That decision is gated first on a purely local, time-based "freshness" test (`conflict.last_endorsed > freshness_cutoff`) before ever asking the node whether the older block is actually dead [2](#0-1) . If the conflict is judged "stale" and belongs to a *different* tenure than the new block, it is never re-verified against the node at all — the only remaining check (lines 1432-1457) applies exclusively to a conflict in the *same* tenure as the new proposal [3](#0-2) . This mirrors the reported pattern of trusting a time-based deadline as a proxy for real state instead of verifying the real state directly — here the local timeout is used as a proxy for "the earlier signature can no longer be pushed to consensus" instead of asking the node whether that block is still live.

### Finding Description
The pre-commit → signature path is the one place a `Signer` produces the irreversible act of a block signature [4](#0-3) . To avoid double-signing two blocks that could both end up on chain, the signer queries `get_signed_conflicts` for every block it previously signed or accepted at or above the new block's height, across *all* tenures, because "two blocks at the same height are siblings no matter which tenure they belong to" [5](#0-4) .

The actual veto logic is:
```
if let Some(conflict) = conflicts.iter().find(|conflict| {
    conflict.last_endorsed > freshness_cutoff
        && !self.reorg_permit_stands(stacks_client, conflict)
        && self.conflict_still_blocks(stacks_client, conflict, block_info.block.header.chain_length)
})
``` [6](#0-5) 

Because Rust's `&&` short-circuits, `conflict_still_blocks` — the only call that asks the node whether the earlier block is still reachable/canonical — is never invoked for a conflict whose `last_endorsed` timestamp is older than `freshness_cutoff` (`now - tenure_last_block_proposal_timeout`). The code comment explicitly documents that stale conflicts "cannot veto on its own" and are only re-examined if they share the *same* consensus hash as the new proposal [3](#0-2) ; a stale conflict in a *different* tenure receives no further scrutiny whatsoever before the signer proceeds to `mark_locally_accepted` and signs [7](#0-6) .

The design doc itself concedes the chainstate re-check that runs earlier in the same function only inspects *one* tenure (a tenure-change block's parent, or the proposal's own tenure), so "a signed sibling at the same height in a third tenure is invisible to it" — which is precisely why the conflict guard exists [8](#0-7) . The guard's freshness-based shortcut reopens exactly that blind spot for any sibling that is old enough to be "stale" by local clock, even though the doc's own reasoning explains that liveness must be re-derived from the node "per evaluation" because "a signature can outlive the block it covers" and vice versa [9](#0-8) .

### Impact Explanation
`tenure_last_block_proposal_timeout` is a per-signer local wall-clock value, not a chain-verified fact. A block A that this signer signed in tenure T1 at height H may still be actively collecting signatures from other signers (e.g., signers with clock skew, or who are slower to process, or who are still waiting on their own node's validation) well past this signer's local `tenure_last_block_proposal_timeout`. If a sibling block B at height H (or higher) surfaces in a different tenure T3 — legitimately passing T3's own one-tenure chainstate checks — and later crosses the pre-commit threshold, this signer will sign B without ever asking the node whether A is dead, because the staleness shortcut skips `conflict_still_blocks` entirely for cross-tenure conflicts. If enough of the signer set experiences the same stale/cross-tenure blind spot at slightly different times, both A and B can independently accumulate the 70% signature threshold and be pushed to the node as competing canonical blocks at the same height — the signer set equivocating, i.e. producing conflicting signed blocks. This falls under the Critical class defined by the rules ("a signer signing an invalid, non-canonical, or conflicting block").

### Likelihood Explanation
This requires no majority collusion and no key compromise: it is triggered purely by ordinary timing (a slow-to-finalize tenure plus a later competing tenure) combined with the built-in `tenure_last_block_proposal_timeout`, which is designed to be short enough to keep the network live (documented test defaults use values as low as 30 seconds) [10](#0-9) . A single miner with normal proposal capability (a "one-slot miner") can naturally produce this ordering by proposing a new tenure-start block once the old tenure has stalled past the timeout, without needing any signer collusion or protocol violation.

### Recommendation
Remove the staleness shortcut for cross-tenure conflicts, or at minimum invoke `conflict_still_blocks` (querying the node) for any conflict in a tenure different from the proposal's own tenure regardless of `last_endorsed` freshness, since only a node-derived fact (sortition orphaned, or tenure tip reached/passed the conflicting height) can safely prove a cross-tenure sibling is dead. Freshness should only be used as a cheap pre-filter to skip the node round-trip when it is certain to be safe, not as a substitute for the node check itself.

### Proof of Concept
1. Signer S validates and signs block A at height H in tenure T1 (`mark_locally_accepted`), setting `signed_self`/`signed_group` for A.
2. Block A stalls (e.g. slow signers, network partition) and does not reach global acceptance before `tenure_last_block_proposal_timeout` elapses relative to A's `last_endorsed` time.
3. A new tenure T3 (via legitimate tenure-extend or a subsequent sortition) proposes block B at height H (a sibling of A). B passes `check_block_against_signer_db_state`, because that check only evaluates T3's own tenure/parent choice, not third-tenure siblings.
4. B accumulates ≥70% pre-commit weight and reaches `handle_block_pre_commit` on signer S.
5. `get_signed_conflicts` returns A as a conflict at height H, but `A.last_endorsed` is now older than `freshness_cutoff`, so the `find` predicate in `stacks-signer/src/v0/signer.rs` lines 1403-1411 short-circuits before calling `conflict_still_blocks`; the same-tenure-only check at lines 1432-1457 does not apply since A and B are in different tenures.
6. Signer S signs B via `mark_locally_accepted`, while A may simultaneously still be alive and accumulating signatures elsewhere in the network, yielding two independently-signed conflicting blocks at height H.
