### Title
Stale Confirmations From Removed Members Are Not Purged, Allowing a Multisig Request To Execute With Fewer Live Signers Than `num_confirmations` - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
Both the v1 and v2 multisig contracts track, per pending request, a set of confirming keys/members in `confirmations`, and compare `confirmations.len() + 1 >= num_confirmations` to decide whether to execute a request. When a signer/member is removed (`DeleteKey` in v1, `DeleteMember` in v2), the code only purges requests that the removed signer *originally added* — it never scrubs that signer's existing confirmations from *other members'* pending requests. The binding "confirmations counted == confirmations from currently-live members" is broken.

### Finding Description
In `multisig/src/lib.rs` the `DeleteKey` action handler only removes requests where the request's `signer_pk` equals the key being deleted, and clears their confirmation sets: [1](#0-0) 

It never looks at `self.confirmations`, entries for requests added by *other* signers, in which the removed key may still be recorded as a confirmer. The `confirm()`/`execute_request()` machinery only checks `confirmations.len()`: [2](#0-1) 

The identical pattern exists in `multisig2/src/lib.rs`'s `delete_member`, which filters outstanding requests by `r.member == member` before wiping confirmations, again leaving stale confirmations from the removed member on requests originated by *other* members untouched: [3](#0-2) 

Consequently the count returned by `confirmations.len()` (and used against `num_confirmations`) can include a confirmation from a public key/member that is no longer part of the multisig's live signer set, i.e. `confirmations.len()` no longer equals "number of currently-authorized signers who approved this request."

### Impact Explanation
This breaks the core multisig custody guarantee (k-of-n distinct, currently-authorized signers must approve before funds move or privileged actions execute). Concretely:
1. Member A confirms a pending request (e.g., `Transfer` or `AddKey`) added by member B, but the threshold is not yet reached.
2. The multisig subsequently removes A (via `DeleteKey`/`DeleteMember` — a routine, legitimate operational action, e.g. because A left, A's key was compromised, or membership was rotated).
3. A's stale confirmation on B's still-pending request is never purged.
4. A single additional, currently-valid confirmer (C) pushes `confirmations.len() + 1 >= num_confirmations`, and the request executes — even though the actual number of *currently authorized* signers that approved it is one fewer than `num_confirmations` requires.

This is an authorization-threshold bypass: NEAR can be transferred, keys/members added, or contract code deployed (`Transfer`, `AddKey`/`AddMember`, `DeployContract`, `FunctionCall`) with fewer live-member confirmations than the configured `num_confirmations`, i.e., "a multisig request executed below threshold," which matches the Critical impact category.

### Likelihood Explanation
Likelihood is moderate: it requires normal, expected multisig operations (a member confirms a request, then later membership changes) rather than any single member's malicious action outside their granted authority. Membership churn (removing departing employees, rotating compromised keys) is a routine multisig operation, and any request left pending across such a rotation is silently affected. No special privilege beyond ordinary multisig usage is required to trigger the divergence; it manifests automatically whenever a confirmer is later removed while their confirmed request is still outstanding.

### Recommendation
When removing a key/member, iterate all pending requests' confirmation sets (not just the ones the removed signer authored) and strip the removed signer's/member's entry from each. Alternatively, when checking whether a request has reached its threshold, filter `confirmations` against the current live member set (`self.members` / valid access keys) rather than relying on the raw stored set length.

### Proof of Concept
Conceptual sequence for v1 `multisig/src/lib.rs` (3 keys A, B, C, `num_confirmations = 2`):
1. B calls `add_request(transfer_to_attacker)` → request pending, `confirmations = {}`.
2. A calls `confirm(request_id)` → `confirmations = {A}` (1 < 2, stays pending).
3. Multisig executes a separate, properly-confirmed request that includes `DeleteKey { public_key: A }` (e.g., because A's key was reported lost). `execute_request` only scrubs requests where `signer_pk == A`; the `transfer_to_attacker` request (added by B) is untouched, and `confirmations` for it still contains `A`.
4. C calls `confirm(request_id)` → `confirmations.len() as u32 + 1 == 2 >= num_confirmations`, so the transfer executes — funded by confirmations from A (no longer a valid key) and C, i.e., only one currently-live signer besides the pending threshold logic "trusting" the removed A.

The same flow applies to `multisig2/src/lib.rs` using `DeleteMember` in place of `DeleteKey`.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
