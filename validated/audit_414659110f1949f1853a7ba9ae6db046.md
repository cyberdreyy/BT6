### Title
Second `requestWithdraw` overwrites `lastWithdrawRequest`, orphaning a loss-adjusted receipt and letting it claim at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` resolves a user's loss-adjusted (haircutted) withdraw receipt by looking up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]`. `requestWithdraw` unconditionally rewrites `lastWithdrawRequest[user]` on every new request. A user who holds an unclaimed loss-adjusted receipt from an earlier epoch and files any new withdraw request "deregisters" the loss-epoch key from the index while the receipt itself survives in `withdrawsRequests[user]` / `withdrawsRequestsByEpoch[user][lossEpoch]` — mirroring the kernel bug where an object stays reachable through a stale reference after removal from the registry. The next `claimWithdrawRequest` misses the haircut entirely and pays the orphaned receipt at par through the funded path.

### Finding Description
- `requestWithdraw` records the current epoch marker and accumulates the receipt:
  - `lastWithdrawRequest[_user] = currentEpoch;` [1](#0-0) 
  - `withdrawsRequests[_user] += _amount; withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;` [2](#0-1) 
- A partial funding via `stopEpochWithDuration`/`collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` and clears `pendingWithdraws` — i.e., only the reduced amount is actually transferred into the strategy: [3](#0-2) 
- At claim time the loss epoch is recovered only through the single-slot index `lastWithdrawRequest`: [4](#0-3) 
- If `lastWithdrawRequest` now points at a later, healthy epoch, `lossRecoveryPriceByEpoch[laterEpoch] == 0` so `_claimLossAdjustedWithdrawRequest` returns 0 and execution falls through to `_claimFundedWithdrawRequest`, which pays the full `withdrawsRequests[_user]` aggregate (orphaned haircutted amount + new receipt) at par: [5](#0-4) 
- The stale `withdrawsRequestsByEpoch[user][lossEpoch]` entry remains nonzero afterward, but the aggregate was already paid and zeroed — the loss accounting for that epoch is never applied.

No guard stops this: `_checkNotAllowed`/`NotAllowed` gating only enforces the one-epoch wait; `requestWithdraw` has no "must claim outstanding receipt first" check; the claim path never iterates `withdrawsRequestsByEpoch` for older epochs with a nonzero `lossRecoveryPriceByEpoch`.

### Impact Explanation
The strategy funded only `claimBasis * lossRecoveryPrice / RECOVERY_FULL` for the loss-epoch receipts, yet pays out the full basis at par. The excess is taken from the strategy's funded-claim balance, so honest users' pending/funded withdraw receipts (and, once drained, later claimants) are shorted by exactly the haircut amount the attacker avoided — a direct theft/insolvency equal to `claimBasis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL` per orphaned receipt. With a near-total loss (small `lossRecoveryPrice`), essentially the entire receipt is stolen.

### Likelihood Explanation
An unprivileged tranche holder only needs to (1) have a withdraw request pending in an epoch that ends via `stopEpochWithDuration` with a loss, (2) file a second `requestWithdraw` of any size in a later epoch before claiming, (3) wait one epoch and call `claimWithdrawRequest`. All steps are normal user actions in running epochs; no privileged cooperation is required. The sequence relies on a loss event occurring, which is a normal protocol mode (`_lossAmount` stop path).

### Recommendation
Track loss-adjusted claims by their own epoch key rather than the mutable `lastWithdrawRequest` marker — e.g., iterate or store per-user loss-epoch pointers, or in `requestWithdraw` revert/force-settlement when `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` and the receipt is unclaimed. Alternatively, keep a per-user list/map of epochs with outstanding `withdrawsRequestsByEpoch` entries and check each against `lossRecoveryPriceByEpoch` in `claimWithdrawRequest` before the funded path runs.

### Proof of Concept
```solidity
// Foundry fork test skeleton against IdleCreditVault via IdleCDOEpochVariant
function testLossReceiptOrphanedBySecondRequest() external {
    // 1. Attacker deposits and requests withdraw in epoch N (running epoch)
    _depositWithUser(attacker, 100e6);
    vm.prank(manager); cdoEpoch.startEpoch();
    uint256 tranches = tranche.balanceOf(attacker) / 2;
    _requestWithdrawWithUser(attacker, tranches);   // lastWithdrawRequest = N, byEpoch[N] += x

    // 2. Honest manager stops epoch N with a loss: collectWithdrawFunds receives
    //    less than pendingWithdraws -> lossRecoveryPriceByEpoch[stopEpochKey] = price < RECOVERY_FULL
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 lossAmount = pendingBasis / 2; // 50% haircut
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(address(underlying), strategy.borrower(), repay, true);
    vm.prank(strategy.borrower()); underlying.approve(address(cdoEpoch), repay);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), lossAmount);

    // 3. Attacker files a new withdraw in the next running epoch:
    //    lastWithdrawRequest overwritten -> loss epoch key orphaned
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(attacker, 1); // dust request
    // attacker tranche tokens were minted as receipt; approve again as needed

    // 4. End that epoch normally; claim path skips loss-adjusted lookup
    _stopCurrentEpochWithApr(10e18);

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(address(cdoEpoch)); // via cdoEpoch.claimWithdrawRequest()
    cdoEpoch.claimWithdrawRequest();

    // 5. Paid at par: received > funded basis -> strategy drained for other claimants
    uint256 paid = underlying.balanceOf(attacker) - balPre;
    uint256 lossEpoch = /* epoch key used in collectWithdrawFunds */;
    uint256 price = strategy.lossRecoveryPriceByEpoch(lossEpoch);
    assertGt(price, 0);
    assertGt(paid, (tranches * price) / strategy.RECOVERY_FULL(), "haircut bypassed, paid at par");
}
```

Caveat: I could not fully verify (with remaining iterations) whether `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch` under the pre- or post-increment `epochNumber` relative to the value stored in `lastWithdrawRequest`. If the key used at loss time differs systematically from `lastWithdrawRequest`, the loss path may already be unreachable in more cases — which would strengthen rather than weaken the orphaning concern. The single-slot index overwrite in `requestWithdraw` and the silent `return 0` in `_claimLossAdjustedWithdrawRequest` are confirmed in the code.

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
