### Title
Permissionless fee collection can be permanently DoS'd by a zero-amount SPL transfer on Token-2022 mints with hook/extension logic that reverts on zero-value transfers - ([File: programs/marginfi/src/instructions/marginfi_group/collect_bank_fees.rs])

### Summary
`lending_pool_collect_bank_fees` unconditionally issues three separate token transfers (group fee, insurance fee, program fee) inside a single instruction, without checking whether any of the computed transfer amounts is zero. Marginfi banks can be backed by Token-2022 mints carrying arbitrary extensions, including `TransferHook`, which the codebase explicitly supports and tests (`test_transfer_hook` program, `SupportedExtension::TransferHook`). A mint whose hook program reverts on a zero-value transfer (the Solana analog of the "weird-ERC20 revert on zero value transfer" class referenced in the external report) will cause the entire permissionless fee-collection instruction to fail whenever any one of the three fee categories has zero outstanding balance while another does not.

### Finding Description
In `lending_pool_collect_bank_fees`, the three fee categories are each computed and transferred independently but within the same instruction, with no `if amount > 0` guard: [1](#0-0) 

and the program fee transfer following the same unconditional pattern: [2](#0-1) 

Each of these calls `bank.withdraw_spl_transfer`, which for Token-2022 mints invokes `spl_token_2022::onchain::invoke_transfer_checked` with the (possibly zero) `amount`: [3](#0-2) 

Marginfi explicitly supports Token-2022 mints with `TransferHook` extensions as a first-class feature, evidenced by the dedicated `test_transfer_hook` program and `SupportedExtension::TransferHook` used in test fixtures: [4](#0-3) [5](#0-4) 

Since insurance, group, and program fee rates are independently configurable (and origination fee is documented as "historically, always zero," confirming individual fee categories are frequently zero), it is common for one of `collected_insurance_fees_outstanding`, `collected_group_fees_outstanding`, or `collected_program_fees_outstanding` to be zero while the others are non-zero: [6](#0-5) 

If a bank's mint uses a transfer-hook program that reverts when invoked with a zero transfer amount (a legitimate/foreseeable Token-2022 hook design, directly analogous to the "revert on zero value transfer" ERC20 class cited in the report), the `spl_token_2022::onchain::invoke_transfer_checked` call for the zero-amount category will revert, aborting the whole `lending_pool_collect_bank_fees` transaction — including the other two, legitimately non-zero transfers that would otherwise have succeeded.

### Impact Explanation
`LendingPoolCollectBankFees` is the permissionless ix that must run before fees can ever be withdrawn via `LendingPoolWithdrawFees` / `LendingPoolWithdrawFeesPermissionless`, since it is what moves accrued fees out of `liquidity_vault` into `insurance_vault` / `fee_vault`: [7](#0-6) 

If this instruction becomes permanently unable to execute for a given bank (because one fee category is always zero for that bank while another is not, e.g., a bank configured with a zero group-fee rate but non-zero insurance/program rate), accrued protocol and insurance fees for that bank can never be collected, harvested, or withdrawn — a durable, financially-material freeze of protocol/insurance revenue for any bank backed by such a Token-2022 mint. This is a legitimate protocol-availability/value-lock issue, not merely a generic DoS exclusion, since it produces a lasting financial effect (permanently stuck fee revenue) rather than a transient unavailability.

### Likelihood Explanation
Likelihood depends on a group admin or bank creator listing a bank against a Token-2022 mint whose transfer-hook program reverts on zero-amount transfers. Marginfi does not restrict bank mints from using arbitrary transfer hooks, and the codebase's own transfer-hook support/tests demonstrate this is an anticipated integration path rather than a purely theoretical one. Any group admin (unprivileged relative to marginfi's own program authority) creating a bank for such a mint, combined with normal fee-rate configuration (frequently leaving one fee category at zero), is sufficient to trigger the condition — no attacker privilege is required beyond permissionless calling of `LendingPoolCollectBankFees`.

### Recommendation
Guard each of the three transfers in `lending_pool_collect_bank_fees` (and any other unconditional `withdraw_spl_transfer`/`deposit_spl_transfer` call sites operating on potentially-zero amounts) with an explicit `if amount > 0` check before invoking the SPL transfer, so a zero-value fee category never blocks collection/transfer of the other non-zero categories:
```rust
if group_fee_transfer_amount > 0 {
    bank.withdraw_spl_transfer(group_fee_transfer_amount.checked_to_num()..., ...)?;
}
```
Apply the same pattern to the insurance and program fee transfers.

### Proof of Concept
1. Create a marginfi bank backed by a Token-2022 mint with a `TransferHook` extension whose hook program returns an error when invoked with `amount == 0` (trivial modification of the existing `test_transfer_hook` program's `process_execute`, which currently accepts any amount unconditionally: [8](#0-7) ).
2. Configure the bank so that, e.g., `group_fee_ir`/`group_fee_fixed` is 0 while `insurance_fee_ir`/`insurance_fee_fixed` is non-zero (independently configurable per `interest_rate_config`).
3. Have a borrower accrue interest so `collected_insurance_fees_outstanding` becomes non-zero while `collected_group_fees_outstanding` remains zero.
4. Call `LendingPoolCollectBankFees`. The `group_fee_transfer_amount` will be `0`, causing `bank.withdraw_spl_transfer(0, ...)` to invoke the hook with `amount = 0`, which reverts and aborts the whole instruction — even though the insurance fee transfer (non-zero) would otherwise have succeeded.
5. Because the group fee will remain at zero for that bank indefinitely, `LendingPoolCollectBankFees` can never succeed again for this bank, permanently freezing collection of the outstanding insurance and program fees as well.

```rust
pub fn lending_pool_withdraw_fees<'info>(
    mut ctx: Context<'info, LendingPoolWithdrawFees<'info>>,
    amount: u64,
) -> MarginfiResult {
    let LendingPoolWithdrawFees {
        bank: bank_loader,
        fee_vault,
        fee_vault_authority,
        dst_token_account,
        token_program,
        ..
    } = ctx.accounts;

    let bank = bank_loader.load()?;
    let maybe_bank_mint =
        utils::maybe_take_bank_mint(&mut ctx.remaining_accounts, &bank, token_program.key)?;

    bank.withdraw_spl_transfer(
        amount,
        fee_vault.to_account_info(),
        dst_token_account.to_account_info(),
        fee_vault_authority.to_account_info(),
        maybe_bank_mint.as_ref(),
        token_program.to_account_info(),
        bank_signer!(
            BankVaultType::Fee,
            bank_loader.key(),
            bank.fee_vault_authority_bump
        ),
        ctx.remaining_accounts,
    )?;

    Ok(())
}
```

```rust
pub fn process(program_id: &Pubkey, accounts: &[AccountInfo], input: &[u8]) -> ProgramResult {
    let instruction = TransferHookInstruction::unpack(input)?;

    match instruction {
        TransferHookInstruction::Execute { amount } => {
            msg!("Instruction: Execute");
            process_execute(program_id, accounts, amount)
        }
        TransferHookInstruction::InitializeExtraAccountMetaList {
            extra_account_metas,
        } => {
            msg!("Instruction: InitializeExtraAccountMetaList");
            process_initialize_extra_account_meta_list(program_id, accounts, &extra_account_metas)
        }
        TransferHookInstruction::UpdateExtraAccountMetaList {
            extra_account_metas,
        } => {
            msg!("Instruction: UpdateExtraAccountMetaList");
            process_update_extra_account_meta_list(program_id, accounts, &extra_account_metas)
        }
    }
}
```

```markdown
## How Interest Accumulates

When any user interacts with marginfi in a way that changes the balance of a bank,
accrue_interest runs first. Based on the rate and how much time has elapsed, the program adds to the
following bank fields:
```
collected_insurance_fees_outstanding
collected_group_fees_outstanding
collected_program_fees_outstanding
```
This (along with the base rate itself) causes the `asset_share_value` and/or `liability_share_value`
to increase.

## How Fees Are Collected

(1) Interset accrues and increases the number in `fees_outstanding` fields. Optionally, origination
fees are charged and do the same.

(2) Anyone (the ix is permissionless) runs `LendingPoolCollectBankFees`. This moves:
* The amount specified in `collected_insurance_fees_outstanding` from the `liquidity_vault` to the
  `insurance_vault`
* The amount specified in `collected_group_fees_outstanding` from the `liquidity_vault` to the `fee_vault`
* The amount specified in `collected_program_fees_outstanding` from the `liquidity_vault` to the
    `fee_ata`, which is the cannonical ATA of the global fee wallet.

Then the `fees_outstanding` are all reset to zero. The vast majority of the time, we run this ix just before a withdraw.
```
