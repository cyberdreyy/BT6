### Title
Frontrunning APR0 `stopEpoch` with a last-second `requestWithdraw` captures a full-epoch pro-rata interest share - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
In a fixed-APR epoch where `unscaledApr == 0` (APR0 mode), any principal that enters the APR0 withdrawal bucket via `requestWithdraw` receives a pro-rata share of the **entire realized epoch interest** at the next `stopEpoch`, regardless of when during the epoch the request was made. An attacker holding tranche tokens can call `requestWithdraw` one second before `stopEpoch`, earn the same `apr0RateByEpoch` as a user who waited the whole epoch, and claim `settledInterest` immediately after the epoch is finalized — the exact analog of frontrunning `rewardValidators()` for instant rewards.

### Finding Description
`IdleCreditVault.prepareStopEpochWithApr0` splits realized interest pro-rata between the CDO TVL and the aggregate `apr0TotalPrincipal` bucket: [1](#0-0) 

```solidity
uint256 _apr0InterestGross = _interestNetOfFees * _principal / _totalPrincipalForSplit;
uint256 _apr0Fee = _apr0InterestGross * _cdo.fee() / FULL_ALLOC;
_apr0NetInterest = _apr0InterestGross - _apr0Fee;
_adjPendingWithdrawFees += _apr0Fee;
_expInterest -= _apr0NetInterest;
```

The per-epoch rate `apr0RateByEpoch[epochNumber] = _apr0NetInterest * 1e18 / _principal` is applied uniformly to every wei in the bucket. `_requestWithdrawApr0` timestamps each user's principal with the **current** `epochNumber` — there is no time-weighting or accrual window: [2](#0-1) 

`_settleApr0` then credits `settledInterest = principal * rate / 1e18` as soon as `stopEpoch` has bumped `epochNumber`: [3](#0-2) 

Attack trace (APR0 epoch running, `allowAAWithdrawRequest == true` during the running epoch, manager about to call `stopEpoch(0, overrideInterest)` with `overrideInterest > 1`, funded by the honest borrower):

1. Attacker (KYC'd lender holding AA tranche tokens from a prior buffer deposit) frontruns the `stopEpoch` transaction with `requestWithdraw(amount, AATranche)`, which routes into `_requestWithdrawApr0` and bumps `apr0TotalPrincipal`.
2. `stopEpoch` executes; `prepareStopEpochWithApr0` assigns the bucket `_apr0NetInterest = (interest - fees) * bucketPrincipal / (TVL + bucketPrincipal)` and stores `apr0RateByEpoch`.
3. After the epoch rolls, the attacker claims via `claimWithdrawRequest` / the APR0 settlement path and receives principal plus the full-epoch pro-rata interest, despite having "staked" in the bucket for seconds.
4. The stolen amount is directly subtracted from `_expInterest`, so AA/BB tranche prices rise less at `_updateAccounting` — the yield is taken from honest LPs.

The same per-epoch flat-rate behavior is visible in the test `testStopEpochMintInterestWithPendingWithdraws`, where pending withdrawers receive `pending + apr0NetInterest` at claim time (test/foundry/IdleCreditVault.t.sol:2514-2518).

### Impact Explanation
Direct theft of yield. Each APR0 epoch with a positive override interest lets a last-block requester skim `≈ realizedNetInterest * attackerPrincipal / (TVL + attackerPrincipal)`, paid for by diluting `_expInterest` that would otherwise accrue to AA/BB NAVs. Unlike the original report, there is also no meaningful lock-up cost on the interest leg: `apr0TotalPrincipal` is zeroed and `apr0RateByEpoch` is finalized in the same `stopEpoch`, so the profit is claimable immediately after. Repeatable every APR0 epoch.

### Likelihood Explanation
Medium. Preconditions: the vault runs an epoch with `unscaledApr == 0` while the manager still supplies positive realized interest via `stopEpoch` override (a supported mode per the Foundry tests), withdraw requests are enabled, and the attacker holds tranche tokens and passes `isWalletAllowed`. No privileged cooperation is needed; the attack is pure mempool sequencing around an honest manager call. It is weakened only when APR0 epochs settle with `_interest == 0`/`1`, which skips the split entirely.

### Recommendation
Time-weight APR0 principal (e.g., record `principal * timeInBucket` or snapshot a per-request entry timestamp and prorate the epoch interest by `epochEndDate - requestTime`), or require APR0 requests to be in the bucket before a cutoff (e.g., before `epochEndDate - minLead`) to accrue interest for that epoch. Alternatively, distribute APR0 interest over a smooth per-second rate instead of a single stepwise split at `stopEpoch`.

### Proof of Concept
Foundry fork PoC sketch (mirroring `testStopEpochMintInterestWithPendingWithdraws` setup in test/foundry/IdleCreditVault.t.sol:2443-2519):

```solidity
// Setup: AYS off, APR0 epoch (setAprs(0,0)), attacker already holds AA tranches
// from a deposit in the previous buffer period, KYC'd via keyring whitelist.
IdleCreditVault cv = IdleCreditVault(address(strategy));
idleCDO.depositAA(10_000e18);           // honest LP
deal(underlying, attacker, 10_000e18);
// attacker deposited in prior buffer -> holds attackerTranches
_startEpochAndCheckPrices(0);           // epoch N running, unscaledApr == 0

vm.warp(cdoEpoch.epochEndDate() - 1);   // last second of the epoch
vm.prank(attacker);
cdoEpoch.requestWithdraw(attackerTranches, address(AAtranche)); // joins apr0 bucket late

deal(underlying, borrower, pending + expectedInterest);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(0, interest);        // interest > 1 triggers APR0 split

// attacker now has settledInterest ~= net(interest) * attackerPrincipal / (TVL + attackerPrincipal)
// claimable immediately; assert attacker captured ~50% of epoch interest for ~1s of waiting.
```

Assert `apr0Users[attacker].settledInterest > 0` (or the equivalent payout via `claimWithdrawRequest`) equals the same rate as a request made at epoch start, and that `lastNAVAA`/`priceAA` post-stop are lower than the no-attack baseline by the stolen amount.
