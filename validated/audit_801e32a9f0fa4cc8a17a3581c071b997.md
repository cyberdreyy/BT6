### Title
Loss-adjusted withdraw receipts escape the haircut when a later request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` stores a user's withdraw-request epoch in a single slot, `lastWithdrawRequest[_user]`. When a `stopEpochWithDuration` loss is applied, the recovery price is recorded per epoch in `lossRecoveryPriceByEpoch[epochNumber]`, but `_claimLossAdjustedWithdrawRequest` only looks up the *latest* request epoch. An unprivileged tranche holder who requests a withdrawal in the loss epoch and then makes a second, dust-sized request in a later epoch causes the loss-adjusted lookup to miss entirely; the loss-adjusted receipt is then paid at par through `_claimFundedWithdrawRequest`, draining funded underlyings/reserve that belong to other claimants — the same "dereference the wrong (null) slot" shape as CVE-2017-7381, where a missing/mistaken pointer produces a crash instead of the intended path.

### Finding Description
- `requestWithdraw` records `withdrawsRequests[_user] += _amount` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, but collapses the epoch marker into one slot: `lastWithdrawRequest[_user] = currentEpoch` (IdleCreditVault.sol:282, 292-293).
- On a lossy stop, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` and zeroes `pendingWithdraws` (IdleCreditVault.sol:417-421). The haircut is only recoverable via that per-epoch price.
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and returns early when it is `0` (IdleCreditVault.sol:789-792). It never iterates `withdrawsRequestsByEpoch`, so a receipt sitting in an older loss epoch is invisible once `lastWithdrawRequest` is overwritten by a newer request.
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` in full at par (plus settled APR0 amounts) once `epochNumber > lastWithdrawRequest[_user]` (IdleCreditVault.sol:326-349), burning only the receipt tokens and transferring the full basis.

Attacker sequence (running → stopped-with-loss → later epochs):
1. Attacker (KYC'd tranche holder) calls `requestWithdraw(X)` in epoch N.
2. Honest borrower funds less than `pendingWithdraws` at `stopEpochWithDuration`; `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL` is stored.
3. Attacker calls `requestWithdraw(1 wei)` in epoch N+1 (after honest `startEpoch`), overwriting `lastWithdrawRequest = N+1`.
4. After the next `stopEpoch`, `epochNumber > N+1`, so `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` sees `lossRecoveryPriceByEpoch[N+1] == 0` and skips, then `_claimFundedWithdrawRequest` pays `X + 1` at par.
5. The attacker receives `X` un-haircut; the loss that was supposed to be socialized across epoch-N receipts is instead borne by the funded reserve / other claimants.

### Impact Explanation
Direct theft / insolvency: the attacker recovers the full pre-loss value of a receipt that the protocol explicitly haircut. The excess is paid from underlyings held for other funded receipts or the default recovery reserve (`_transferFundedClaim` only guards `balance - reserve`, so reserve is protected only if set; funded claims of honest users are drained first), leaving later honest claimants unable to withdraw — permanent freezing of their funds up to the escaped haircut amount.

### Likelihood Explanation
Requires only a tranche-token holder making two `requestWithdraw` calls across an epoch boundary around a `stopEpochWithDuration` with `_lossAmount > 0`. Lossy stops are an intended protocol mode (previewed by `previewLossAdjustedWithdrawFunds`), and no guard (`_checkNotAllowed`, epoch gating, skim) prevents re-requesting while a receipt is pending — the code comments even acknowledge re-requesting is allowed ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch"). Cost is one extra epoch of delay and dust capital.

### Recommendation
Track the loss-epoch per user instead of a single `lastWithdrawRequest` slot: e.g., iterate/`withdrawsRequestsByEpoch` for any epoch with `lossRecoveryPriceByEpoch[epoch] != 0` before falling through to the funded path, or record per-user loss-epoch markers (a list or the earliest unfunded epoch) so a later request cannot mask an earlier haircut. Alternatively, revert in `requestWithdraw` when the user has an unsettled loss-adjusted receipt.
