### Title
`runInContainer` consumes the shared `remoteProcessTerminated` channel without verifying the received status belongs to the current stage/request - (File: executors/kubernetes/kubernetes.go)

### Summary
`runInContainer` blocks on the executor-wide channel `s.remoteProcessTerminated` and unconditionally treats whatever `StageCommandStatus` arrives as the result of *its own* invocation, with no check that the `Script` field in that status corresponds to the `stage` argument it was called with. Because this channel and the companion `s.remoteStageStatus` field are shared executor state (one per job, not one per exec/attach call), an exit-status/log line produced by a different, still-in-flight or previously-aborted attach/exec session can be delivered to and consumed by a later, unrelated `runInContainer` call.

### Finding Description
`runInContainer` (executors/kubernetes/kubernetes.go, `func (s *executor) runInContainer`) starts a fresh attach session, then does: [1](#0-0) 
`exitStatus := <-s.remoteProcessTerminated` is read from a single field on the `executor` struct that is shared across the entire job lifetime, and is written to from `forwardLogLine`: [2](#0-1) 
`forwardLogLine` is invoked continuously by the background log-processing goroutine (`processLogs`, started once per job in `ensurePodsConfigured`) for every JSON status line seen in the container's combined log stream, and it pushes to `remoteProcessTerminated` any time `status.IsExited()` is true — it does not check which stage or which in-flight `runInContainer`/attach call is expecting that particular exit marker.

`runWithAttach` calls `runInContainer` once per stage in a `select`, and on `ctx.Done()` (build abort/cancellation) it fires a *second*, independent operation — `runInContainerWithExec` running a `kill -TERM` cancellation script — while the original `runInContainer` goroutine for the aborted stage may still be alive and blocked on `<-s.remoteProcessTerminated` in the background (the `select` only returns from the branch that fired; the losing goroutine keeps running): [3](#0-2) 
If the aborted stage's own trap script still manages to print its exit-status JSON marker (e.g. because the process finishes flushing right as/after the kill signal is sent), that stale status is captured by the still-running background reader for the *previous* stage. Meanwhile the *next* stage's `runInContainer` call (invoked by the caller once cancellation completes, or in later attach/exec flows such as `after_script`) issues its own `<-s.remoteProcessTerminated` read with no draining/reset of the channel and no verification against `exitStatus.BuildStage()`/`Script`. There is nothing in `runInContainer` that cross-checks `stage` (the argument) against the `Script` field carried in `StageCommandStatus` before extracting `*exitStatus.CommandExitCode`, so a status meant for one exec/attach session can be delivered to, and accepted by, a different one.

Existing protections are insufficient here: `checkScriptExecution` (referenced in the retry of `attach.Run()`) only validates stage identity on the *connection-retry* path when the initial attach request itself errors; it does not gate the terminal `<-s.remoteProcessTerminated` read that determines the final exit code returned by `runInContainer`.

### Impact Explanation
This allows the exit code/result of one stage's exec/attach session to be attributed to a different stage — i.e., wrong-result reporting: a stage could be reported as succeeded/failed based on another stage's or a stale/aborted session's exit code, or an unrelated background goroutine could silently swallow a legitimate exit status meant for the active stage. This matches the scoped "wrong-result reporting or output tampering" impact and is attacker-triggerable purely through job script/service timing (e.g., a job that races cancellation, or crafts output to encourage the trap script to still fire near a timeout boundary) — no cluster-admin or external compromise needed.

### Likelihood Explanation
Triggering requires timing control over when the trap-based JSON exit marker is emitted relative to job cancellation/timeout, or the interleaving of stage transitions with a lagging log-processing goroutine. This is feasible for a pipeline author who controls the job script (they can construct scripts whose trap fires right around a timeout, or exploit slow log delivery), but is a race condition rather than deterministically reproducible on every run — likelihood is moderate, contingent on scheduling and log-forwarding timing.

### Recommendation
- Include the stage/session identity in the exit-status marker emitted by the trap/detect-shell scripts, and have `runInContainer` validate `exitStatus.BuildStage() == stage` before accepting the result; otherwise loop/re-select rather than accept it.
- Use a per-invocation channel for exit-status delivery (create/allocate the channel inside `runInContainer` instead of a shared executor field), keyed by a request/session ID passed to the script and matched in `forwardLogLine`.
- On cancellation, explicitly drain/discard or cancel the previous stage's outstanding `remoteProcessTerminated` read (e.g., via context cancellation of the reader) before starting a new stage's `runInContainer`.

### Proof of Concept
Go unit test plan (in `executors/kubernetes/kubernetes_test.go`):
1. Construct an `executor` with `remoteProcessTerminated` as its real shared channel and two goroutines simulating two sequential calls to `runInContainer` for `stageA` and `stageB`.
2. Have `forwardLogLine` be invoked with a `StageCommandStatus{Script: &"stageA", CommandExitCode: &1}` line delayed until *after* `runInContainer(stageB, ...)` has started its read.
3. Assert that `runInContainer(stageB, ...)`'s returned error reflects `stageA`'s exit code (exit code 1) even though `stageB`'s own script never reported failure — demonstrating cross-stage state bleed through the shared channel and confirming lack of stage-correlation checking on the read path.
