### Title
Cross-user response leakage via unauthenticated MessageId collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each caller's `handlers.Callback` in `h.savedCallbacks` keyed solely by the attacker-controlled `msg.Body.MessageId`, with no binding to caller identity, session, or connection. Two concurrent unprivileged callers who submit the same `MessageId` can have their callback entries collide, causing `handleWebAPITriggerMessage`/`HandleNodeMessage` to deliver one caller's DON response to the other caller's HTTP connection.

### Finding Description
In `HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go:411-414), the handler unconditionally overwrites the map entry:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [1](#0-0) 

There is no check for an existing entry, no rejection of duplicate IDs, and no tie to the caller's identity/session — the key is purely the value of `msg.Body.MessageId`, which is part of the JSON body the caller supplies (`api.MessageBody.MessageId`) and is only constrained to be 1–128 bytes and not end in a null byte by `Message.Validate()`. [2](#0-1) 

Any two unauthenticated callers hitting `gateway.ProcessRequest` → `HandleLegacyUserMessage` (via `handlers.Handler` interface, dispatched in core/services/gateway/gateway.go:267-269) can choose the same `MessageId` value, since the gateway does not require a unique or session-bound ID and message signing only proves that the sender controls a given key, not that the ID is unique. [3](#0-2) 

When node responses come back, `handleWebAPITriggerMessage` looks up and deletes the callback strictly by `msg.Body.MessageId` and delivers the first DON response received under that key to whichever `Callback` currently occupies the slot:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
h.mu.Unlock()
if found {
    return savedCb.SendResponse(...)
}
``` [4](#0-3) 

If caller A registers `MessageId="X"` and caller B subsequently (even microseconds later, before A's DON responses arrive) registers the same `MessageId="X"`, B's callback silently replaces A's in the map. When the DON's response to A's original request arrives (carrying the same `MessageId="X"` since the gateway relays the ID unchanged to nodes, see `ValidatedRequestFromMessage`), the gateway looks up key "X" and finds B's callback, delivering A's (potentially sensitive, e.g. HTTP response body/secrets fetched via `web_api_target`/`compute_action`) response to B's HTTP connection. No authentication, allowlist, or per-caller isolation check exists in this path to prevent it — the code comment even acknowledges the ID space is a single global map (`// TODO: apply allowlist and rate-limiting here`). [5](#0-4) 

### Impact Explanation
This is a cross-user response confusion vulnerability: an unauthenticated caller can, by guessing or colliding a `MessageId`, receive another user's DON-computed response (which may include HTTP bodies/headers/secrets retrieved on that user's behalf via `web_api_target`/`compute_action` capabilities) or cause another user to receive the attacker's response instead of their own. This matches the "cross-user response confusion" impact class in the audit rules, and does not require any operator/admin access — only the ability to send an HTTP request to the gateway with a crafted `api.Message` and a chosen `MessageId`.

### Likelihood Explanation
Exploitation requires only: (1) knowledge or a plausible guess of another concurrently-in-flight caller's `MessageId` (which may be low-entropy, e.g. sequential/predictable client-generated IDs, or trivially "0"), and (2) timing the second request to land between the first caller's registration and the DON's response. No credentials, allowlist entry, or elevated role are needed — any address able to produce a validly-signed `api.Message` (self-signed, since `ExtractSigner` only recovers the signer from the attacker's own signature) can trigger this. The race window is realistic given DON response latency (network round trip to nodes), making repeated attempts feasible.

### Recommendation
Bind `savedCallbacks` entries to caller identity in addition to `MessageId` (e.g., key by `(sender-address, MessageId)` derived from `msg.Body.Sender` after `Validate()`/`ExtractSigner`), and reject (rather than silently overwrite) registration attempts when a non-expired entry already exists for that composite key. Additionally, validate uniqueness of `MessageId` per sender within the callback TTL window before inserting into `h.savedCallbacks`.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with a fake `handlers.DON` that records `SendToNode` calls.
2. Create two `handlers.Callback` mocks/fakes, `callbackA` and `callbackB`, each capturing whatever `UserCallbackPayload` they receive via a channel.
3. Build two distinct signed `api.Message` requests, `msgA` and `msgB`, both with `Body.MessageId = "X"` but different signers/payloads (simulating two unrelated users).
4. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` then, before any DON response arrives, call `h.HandleLegacyUserMessage(ctx, msgB, callbackB)` — assert `h.savedCallbacks["X"]` now holds `callbackB` (overwrite confirmed) and `callbackA` is gone from the map.
5. Simulate a DON node response addressed with `MessageId="X"` corresponding to A's original request (`h.handleWebAPITriggerMessage(ctx, respForA, nodeAddr)`).
6. Assert that `callbackB.SendResponse` was invoked with A's response payload while `callbackA.SendResponse` was never called — demonstrating cross-user leakage.
7. As a regression check for the fix, assert that after remediation, the second `HandleLegacyUserMessage` call with a colliding `MessageId` either returns an error/rejected response to caller B or is keyed distinctly (e.g., by sender+MessageId) so that `callbackA` still receives A's own response and `callbackB` never observes it.
