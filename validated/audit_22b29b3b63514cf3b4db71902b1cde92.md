## Finding: Unchecked-length slice access in `parse_l1_info` can panic on attacker-influenced calldata

### Title
Missing length validation in `parse_l1_info` causes an out-of-bounds slice panic (node DoS) - ([File: crates/execution/evm/src/l1.rs])

### Summary
`parse_l1_info` in `crates/execution/evm/src/l1.rs` slices `input[0..4]` and `input[4..]` without validating that `input.len() >= 4` inside the function itself [1](#0-0) . The function's own doc comment admits this: *"# Panics: If the input is shorter than 4 bytes"* [2](#0-1) . This is the same bug class as the reported FFmpeg CVE: a decoder that indexes attacker-influenced, variable-length input without first checking the buffer bound, producing an out-of-bounds read (in Rust, a slice-index panic rather than silent memory corruption).

### Finding Description
The only hardened entry point is `extract_l1_info_from_tx`, which checks `l1_info_tx_data.len() < 4` before calling `parse_l1_info` [3](#0-2) . However, `parse_l1_info` is `pub fn`, exported from `base-execution-evm`, and is called directly elsewhere in the codebase — `crates/execution/txpool/src/validator.rs` contains 3 call sites to `parse_l1_info`/related functions per the repository search. I was not able to fully verify, within the remaining tool budget, whether every one of those call sites re-validates `input.len() >= 4` before invoking `parse_l1_info` on data that ultimately derives from transaction calldata reachable by an unprivileged sender (e.g., a spoofed/legacy transaction whose `input` mimics an L1-info selector but is truncated below 4 bytes). If any call path in the txpool validator (or elsewhere) invokes `parse_l1_info` (or the selector-dispatch logic duplicated in it) on attacker-supplied bytes without first checking the 4-byte minimum, that call panics the calling thread.

Each of the per-fork sub-parsers (`parse_l1_info_tx_bedrock`, `parse_l1_info_tx_ecotone`, `parse_l1_info_tx_isthmus`, `parse_l1_info_tx_jovian`) do check the *exact* declared body length before their own indexed access [4](#0-3) [5](#0-4) , so the vulnerable code is specifically the selector-slicing prologue in `parse_l1_info` itself, prior to dispatch.

### Impact Explanation
If reachable with attacker-controlled, sub-4-byte input, this causes a Rust panic. Depending on the calling context (txpool admission thread, RPC-serving thread, or block-execution thread), this can range from a single request failure up to a node halt if the panic occurs in a non-isolated/synchronous execution path — matching the "node halt" / "RPC the node can no longer serve" impact classes called out in the validation rules.

### Likelihood Explanation
Likelihood depends entirely on whether any reachable caller (in particular the 3 usages inside `crates/execution/txpool/src/validator.rs`) passes unchecked, potentially-attacker-supplied byte slices into `parse_l1_info` without first checking `len() >= 4`. I could not confirm this within the available tool budget — the grep only located the call sites but I did not have an iteration left to read `validator.rs` and confirm the length-check discipline there. All confirmed callers I did inspect (`extract_l1_info_from_tx`, and the crate's own test module) correctly gate the call with a length check first.

### Recommendation
- Add an explicit `if input.len() < 4 { return Err(...) }` guard at the top of `parse_l1_info` itself, so the function is safe regardless of caller discipline (defense in depth, matching the pattern already used in `extract_l1_info_from_tx`).
- Audit every call site of `parse_l1_info` (especially the three in `crates/execution/txpool/src/validator.rs`) to confirm a length check precedes the call, and add regression tests (mirroring the `test_decode_tx_sigs_truncated_input`/`test_read_tx_data_truncated_payload` style tests already present elsewhere in this codebase) asserting that a sub-4-byte input returns an `Err` rather than panicking.

### Proof of Concept
Not fully constructible without confirming the exact txpool call path; conceptually: `parse_l1_info(&[0u8; 3])` (or any slice with `len() < 4`) directly panics via `input[0..4]` before any of the sub-parsers' length checks run — reproducible today as a unit test against the exported function itself [6](#0-5) .

**Caveat:** This is presented as the strongest analog found before the tool budget was exhausted, but full exploit-path confirmation (i.e., proving an unprivileged/anonymous caller can reach `parse_l1_info` with unchecked short input through the txpool validator) was not completed. If that confirmation fails, this reduces to a defense-in-depth/hardening issue rather than a directly exploitable one.

```rust
pub fn extract_l1_info_from_tx<T: Transaction>(
    tx: &T,
) -> Result<L1BlockInfo, BaseBlockExecutionError> {
    let l1_info_tx_data = tx.input();
    if l1_info_tx_data.len() < 4 {
        return Err(BaseBlockExecutionError::L1BlockInfo(L1BlockInfoError::InvalidCalldata));
    }

    parse_l1_info(l1_info_tx_data)
}
```

```rust
/// Caution this expects that the input is the calldata of the [`L1BlockInfo`] transaction (first
/// transaction) in the L2 block.
///
/// # Panics
/// If the input is shorter than 4 bytes.
pub fn parse_l1_info(input: &[u8]) -> Result<L1BlockInfo, BaseBlockExecutionError> {
    // Parse the L1 info transaction into an L1BlockInfo struct, depending on the function selector.
    // There are currently 4 variants:
    // - Jovian
    // - Isthmus
    // - Ecotone
    // - Bedrock
    if input[0..4] == L1_BLOCK_JOVIAN_SELECTOR {
        parse_l1_info_tx_jovian(input[4..].as_ref())
    } else if input[0..4] == L1_BLOCK_ISTHMUS_SELECTOR {
        parse_l1_info_tx_isthmus(input[4..].as_ref())
    } else if input[0..4] == L1_BLOCK_ECOTONE_SELECTOR {
        parse_l1_info_tx_ecotone(input[4..].as_ref())
    } else {
        parse_l1_info_tx_bedrock(input[4..].as_ref())
    }
}
```
