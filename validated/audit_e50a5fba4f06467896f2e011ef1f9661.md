### Title
Missing fee-sum validation in `createDstEscrow` causes permanent freezing of destination escrow funds via checked-arithmetic revert - (File: contracts/BaseEscrowFactory.sol)

### Summary
`createDstEscrow` never validates that `integratorFeeAmount + protocolFeeAmount <= amount` for the destination escrow, whereas the source path (`_postInteraction`) explicitly enforces this invariant. Since `EscrowDst._withdraw` performs `immutables.amount - integratorFeeAmount - protocolFeeAmount` under Solidity 0.8 checked arithmetic (no `unchecked` block), a destination escrow deployed with fee amounts that exceed the swap amount can never be withdrawn — every `withdraw`/`publicWithdraw` call reverts with an arithmetic underflow, and `cancel` is the only remaining exit path (returning the maker's tokens to the taker, not the maker).

### Finding Description
On the source chain, `BaseEscrowFactory._postInteraction` computes fee amounts and validates them before creating `immutables`: [4](#0-3) 

No equivalent check exists for the destination chain. `createDstEscrow` takes `dstImmutables` directly from calldata supplied by any caller (the taker/resolver creating the destination escrow), which embeds `integratorFeeAmount`/`protocolFeeAmount` inside the opaque `parameters` field of `Immutables`, and only validates the native value sent and the timelock ordering: [1](#0-0) 

Because `Immutables.parameters` is attacker-supplied calldata with no on-chain cross-validation against `amount`, a caller can set `integratorFeeAmount + protocolFeeAmount > amount`. Later, when the maker (or any accessTokenHolder in the public phase) tries to withdraw, `EscrowDst._withdraw` computes: [5](#0-4) 

The subtraction on line 92 is unchecked-free (default checked in 0.8.23), so if fees exceed `amount`, this reverts, permanently DoS-ing `withdraw` and `publicWithdraw` for that escrow. This mirrors the TRST-M-6 root cause class (checked arithmetic that should tolerate certain edge values, causing unconditional reverts) but manifests as a missing precondition check rather than a missing `unchecked` block — the fix direction differs (validate the invariant at creation time, as is already done on the source side) rather than wrapping in `unchecked` (which would silently corrupt fund distribution instead of reverting).

### Impact Explanation
This falls under the Medium-tier bounty scope: "smart contract unable to operate because required token/native balances can be broken by an unprivileged actor" — here, an unprivileged taker/resolver creating the destination escrow can render `withdraw`/`publicWithdraw` permanently unusable, forcing reliance on `cancel`, which sends the maker's expected destination tokens back to the taker rather than the maker, resulting in temporary/permanent freezing of the maker's expected funds during the live swap lifecycle.

### Likelihood Explanation
Likelihood depends on whether the resolver/taker who calls `createDstEscrow` is considered a privileged actor under the bounty's "privileged resolver" exclusion. In the standard flow, the same resolver that filled the source order is expected to construct consistent `dstImmutables` (derived deterministically from the order's postInteraction extraData and taker traits), so this typically requires a malicious or buggy resolver — which the bounty's attacker model explicitly excludes ("never owner, governance, privileged resolver, malicious relayer"). I could not confirm from the available code whether any additional off-chain/on-chain mechanism ties `dstImmutables.parameters` on the destination chain back to the values validated in `_postInteraction` on the source chain (e.g., via `immutablesComplement` matching enforced elsewhere, possibly off-chain by the maker before revealing the secret). Given the resolver-privilege ambiguity and lack of confirmed unprivileged reachability, I cannot assert this with full confidence as in-scope.

### Recommendation
Add an explicit check in `createDstEscrow` mirroring the source-side guard, e.g. `if (integratorFeeAmount + protocolFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();`, decoding fees from `parameters` before deployment, so malformed fee configurations are rejected at creation time rather than causing withdrawal to permanently revert.

### Proof of Concept
Not independently verified end-to-end (would require deploying `createDstEscrow` with a crafted `parameters` field where `integratorFeeAmount + protocolFeeAmount > amount`, then calling `withdraw` and observing the underflow revert); the code paths cited above support the described trigger and broken invariant, but I did not execute a test against the actual test suite to confirm no other layer intercepts this value before deployment.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
