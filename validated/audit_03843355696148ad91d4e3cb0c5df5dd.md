### Title
Operator can permanently lock a staker's entire stake and commission by weaponizing an unregistered, direct-transfer-disabled beneficiary - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`distribute_internal()` iterates over every shareholder in a `staking_contract`'s `distribution_pool` and pays each one via `aptos_account::deposit_coins` inside a single atomic loop. `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient has no registered `CoinStore<AptosCoin>` and has opted out of direct transfers via `set_allow_direct_coin_transfers(false)`. Because the operator fully controls its own beneficiary address (`set_beneficiary_for_operator`), it can point the beneficiary to an account it prepared to always revert on deposit. Since `distribute()` is permissionless and is also invoked internally by `unlock_stake`, `request_commission`, `update_commision`, and `switch_operator_with_same_commission`, this single reverting recipient blocks *all* of these entry points for the staker too — not just commission payment.

### Finding Description
`distribute_internal` (`staking_contract.move`, lines 856-920) buys every shareholder out of the `distribution_pool` in a `while` loop and deposits their share via: [1](#0-0) 

The recipient for the operator's share is resolved via `beneficiary_for_operator(operator)`, which the operator can freely repoint with `set_beneficiary_for_operator`: [2](#0-1) 

`aptos_account::deposit_coins` only auto-registers a `CoinStore` when the account is new or unregistered, and in that case gates on `can_receive_direct_coin_transfers`, which can be disabled unprivilegedly by the account owner via `set_allow_direct_coin_transfers(false)`: [3](#0-2) [4](#0-3) 

If an account has never registered `CoinStore<AptosCoin>` and has called `set_allow_direct_coin_transfers(false)`, any deposit attempt to it will always abort. An operator can prepare such an address, then call `set_beneficiary_for_operator` to route its commission there. From that point on, every call to `distribute_internal` reverts as soon as it tries to pay the poisoned beneficiary.

Critically, `distribute_internal` is not only reachable via the standalone permissionless `distribute()` entry function, it is unconditionally called first inside: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

This means `unlock_stake`, `request_commission`, `update_commision`, and `switch_operator` (via `switch_operator_with_same_commission`) all abort as soon as any inactive/pending_inactive stake exists to distribute, because they force-distribute before doing their own logic. The staker cannot unlock stake, cannot switch away from the operator, and cannot change the commission rate — the stake pool is effectively frozen for as long as the operator keeps this beneficiary configuration and there is a nonzero distributable balance.

This is the direct analog of the external report's bug class: a party in control of one of the transfer recipients in a shared, permissionless "pay everyone" loop can make their own leg always revert, which (unlike the original C4 finding, where the specific token contract could simply be avoided) locks not just their own payment, but the entire loop's payment to every other stakeholder — including funds not owned by the attacker.

### Impact Explanation
This breaks the "Unlock, reactivate, withdraw, synchronize, and beneficiary-update paths must not redirect value or strand it permanently" invariant and the "wrong-role control over ... beneficiary state" gate. A malicious or grieving operator can permanently strand the staker's principal and accumulated rewards in the stake pool, and also permanently prevent the staker from firing the operator (switch_operator forces distribution first), producing a non-recoverable loss of claim rights for a party (the staker) other than the attacker — a stake-lockup analog that is stronger than the original finding (which only blocked one specific tax payment, not the whole withdrawal/lifecycle of the pool).

### Likelihood Explanation
The precondition is fully unprivileged and cheap: the operator only needs to control an address, avoid ever registering `CoinStore<AptosCoin>` on it, call `set_allow_direct_coin_transfers(false)` from it, and call `set_beneficiary_for_operator` (gated only by the `operator_beneficiary_change_enabled` feature flag, not by any special permission) to point at it. No staker cooperation or misconfiguration is required.

### Recommendation
- In `distribute_internal`, do not let a single recipient's failed payout revert the whole distribution: either use a `deposit_coins`-style call that cannot abort (fail open, e.g. skip and re-queue the failing recipient's share rather than aborting the whole transaction), or process each shareholder's transfer in a way that isolates failures per-recipient.
- Alternatively, disallow beneficiary addresses that are not already registered/able to receive AptosCoin, or force-register the beneficiary account for `AptosCoin` at the time `set_beneficiary_for_operator` is called (similar in spirit to `vesting::set_beneficiary`, which calls `assert_account_is_registered_for_apt(new_beneficiary)` before accepting a new beneficiary): [9](#0-8) 
  `staking_contract::set_beneficiary_for_operator` has no equivalent check and should adopt the same guard.

### Proof of Concept
1. Operator `O` creates a fresh address `B` (or uses one it controls) that has never called `coin::register<AptosCoin>` / never received AptosCoin.
2. From `B`, call `aptos_account::set_allow_direct_coin_transfers(B_signer, false)`.
3. `O` calls `staking_contract::set_beneficiary_for_operator(O_signer, B)`.
4. Staker `S` has an active `staking_contract` with `O`; time passes and stake becomes inactive/pending_inactive (rewards or a partial unlock).
5. Anyone calls `staking_contract::distribute(S, O)` (or `S` calls `unlock_stake`, `update_commision`, or `switch_operator`), which internally calls `distribute_internal`.
6. The loop reaches recipient `B`, calls `aptos_account::deposit_coins(B, coins)`, which hits `assert!(can_receive_direct_coin_transfers(B), ...)` and aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
7. The entire transaction reverts — `S`'s unlocked stake/rewards are not distributed, `S` cannot unlock further stake, cannot switch operators, and cannot update commission, as long as `O` keeps this beneficiary configuration and any distributable balance remains.

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
