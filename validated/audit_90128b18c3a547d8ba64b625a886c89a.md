## Title
Reentrancy window during Drift/Kamino integration token transfers allows CPI re-entry into marginfi while `marginfi_account`/`bank` state is unlocked - (File: `programs/marginfi/src/instructions/drift/withdraw.rs`, `programs/marginfi/src/instructions/kamino/withdraw.rs`)

### Summary
The H-02 report describes a reentrancy bug where `lend()` transfers tokens to `currentLoanOwner` via an ERC777 mid-function, letting the attacker's token-receive hook re-enter `lend()` and overwrite `loanInfo` with attacker-favorable terms before the outer call finishes, because the loan state was not locked/finalized before the external transfer occurred. The marginfi analog is the pattern in `drift_withdraw` (and to a lesser extent `kamino_withdraw`, `drift_deposit`, `solend_deposit`) where the `AccountLoader` mutable borrows on `marginfi_account` and `bank` are dropped (scope closes) *before* a token transfer / external-protocol CPI is executed, and re-acquired only afterward.

### Finding Description
In `drift_withdraw`, the state-mutating block (accrue interest, `bank_account.withdraw`, `record_withdrawal_outflow`, `bank.update_bank_cache`) executes inside a scoped block that ends at [1](#0-0) , releasing the `RefMut` locks on both `bank` and `marginfi_account` at [2](#0-1) . Only *after* this scope closes does the function perform the Drift withdraw CPI and the outbound SPL/Token-2022 transfer to the caller-supplied `destination_token_account`: [3](#0-2) . Because `mint` is a generic `InterfaceAccount<Mint>` with no check against `TransferHook`/`TransferFee` extensions (unlike `lending_pool_emissions_deposit`, which explicitly rejects hook/fee mints via `nonzero_fee`/`has_transfer_hook` checks: [4](#0-3) ), a Token-2022 mint with an attacker-controlled `TransferHook` program attached can execute arbitrary CPI logic during `cpi_transfer_liquidity_vault_to_destination`'s `transfer_checked` call — at exactly the point where `marginfi_account` and `bank` are unlocked.

The codebase demonstrates awareness of CPI-based re-entry as an attack surface: `lending_account_start_flashloan`/`lending_account_end_flashloan` are explicitly guarded with `validate_not_cpi_by_stack_height()` and sysvar-based CPI detection specifically to prevent being invoked as a nested CPI: [5](#0-4) . No equivalent guard exists on `drift_withdraw`, `kamino_withdraw`, `drift_deposit`, or `solend_deposit`, all of which release account locks around external CPIs/transfers and support Token-2022 mints (test fixtures explicitly wire up `TEST_HOOK_ID` extra-account-metas for these flows): [6](#0-5) .

During the unlocked window, a transfer-hook CPI can call back into the marginfi program (e.g., re-invoke `drift_withdraw`/`lending_account_borrow`/`lending_account_withdraw` for the same `marginfi_account`) using values (`token_amount`, `expected_scaled_balance_change`, `price`, rate-limiter outflow accounting via `record_withdrawal_outflow`) that were computed by the *outer* invocation before the reentrant call executed. The outer call's post-transfer bookkeeping (event emission, health-cache/health-check, `record_withdrawal_outflow`) is only reconciled against the account state re-loaded at the end of the function: [7](#0-6) , so intermediate accounting (group/bank rate-limiter flow counters, deleverage withdraw-limit tracking) recorded by both the outer and the reentrant call is not atomically coupled to a single consistent balance snapshot.

### Impact Explanation
The rate limiter and deleverage withdraw-limit machinery (`record_withdrawal_outflow`, `group.check_deleverage_withdraw_limit`) exist to bound aggregate outflow and protect solvency for *all* depositors sharing a bank's liquidity vault, not just the caller. A reentrant sequence that records two outflow events (outer + hook-triggered reentrant call) against a single logical transaction, while the final health/consistency checks are only evaluated once at the end using freshly reloaded state, risks under-counting or double-counting protocol-wide risk-limiter state relative to actual token movement, which can degrade the effectiveness of protections meant to guard shared liquidity vault solvency for other lenders in the same bank/group. The absence of a hook/fee-mint restriction on Drift/Kamino/Solend integration banks (present in `lending_pool_emissions_deposit`) further indicates this class of mint was not vetted for these integration flows.

### Likelihood Explanation
Exploitation requires: (1) a bank whose mint is Token-2022 with an attacker-influenced/attacker-owned `TransferHook` program, and (2) that bank being usable in the Drift/Kamino/Solend integration flows. Since bank/mint selection in this codebase appears governed by group-admin configuration rather than fully permissionless end-user mint selection for these specific integrations, the likelihood is constrained to scenarios where a malicious or compromised group admin (or a permissionless group-creation flow, if present) can register such a mint. This is a plausible but non-trivial precondition, and the concrete state-corruption/drain outcome (beyond rate-limiter bookkeeping skew) has not been demonstrated end-to-end in this review.

### Recommendation
- Apply the same CPI-reentrancy guard used for flashloans (`validate_not_cpi_by_stack_height` / ixs-sysvar top-level-instruction check) to `drift_withdraw`, `kamino_withdraw`, `drift_deposit`, `solend_deposit`, and any other instruction that releases `marginfi_account`/`bank` locks before performing external CPIs or token transfers.
- Alternatively, restructure these instructions so the `AccountLoader` mutable borrows on `marginfi_account` and `bank` are held for the *entire* instruction (as already done in `kamino_withdraw`'s outer `marginfi_account` borrow), preventing any reentrant `load`/`load_mut` on the same accounts from succeeding during the CPI/transfer window.
- Extend the `has_transfer_hook`/`nonzero_fee` mint checks already used in `lending_pool_emissions_deposit` to bank configuration for Drift/Kamino/Solend integration banks, or explicitly document/enforce that such integrations disallow Token-2022 `TransferHook` mints.

### Proof of Concept
Not independently constructed/verified on-chain in this review; the finding is based on static analysis of the account-borrow scoping in `drift_withdraw` (locks released at `programs/marginfi/src/instructions/drift/withdraw.rs:205`, transfer performed at lines 221-246 while unlocked) combined with confirmed Token-2022 transfer-hook support in the test harness (`test-utils/src/marginfi_account.rs:820-843`, `programs/test_transfer_hook/src/lib.rs`) and the absence of an equivalent CPI-reentrancy guard to the one explicitly implemented for flashloans (`programs/marginfi/src/instructions/marginfi_account/flashloan.rs:75-96`). A full PoC would require deploying a bank backed by a Token-2022 mint with a custom `TransferHook` program that re-invokes a marginfi instruction during `Execute`, and observing whether rate-limiter/deleverage accounting or balance state becomes inconsistent.
