### Title
Unprotected `initializeConfig()` in `BridgeCommittee` Allows Any Caller to Inject a Malicious Config Before the Deployer — (`bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initialize()` deliberately omits setting the `config` field, leaving it as `address(0)`. A separate, access-control-free `initializeConfig(address _config)` function is expected to be called in a subsequent transaction. Because that function carries no `onlyOwner`, no committee-signature gate, and no `msg.sender` check, any external caller can race the deployer and inject a malicious `IBridgeConfig` implementation. Once set, `config` can never be changed (the only guard is the "already initialized" check), so the bridge is permanently bound to the attacker-supplied config. Every downstream operation that reads `committee.config()` — chain-ID verification, token-address resolution, and transfer-limit accounting — then operates on attacker-controlled data, enabling illegitimate token unlocks from the vault.

---

### Finding Description

`BridgeCommittee.initialize()` sets up committee members and stakes but never touches `config`:

```solidity
// bridge/evm/contracts/BridgeCommittee.sol  lines 30-57
function initialize(address[] memory committee, uint16[] memory stake, uint16 minStakeRequired)
    external initializer
{
    __CommitteeUpgradeable_init(address(this));
    __UUPSUpgradeable_init();
    // ... populates committeeStake / committeeIndex
    // config is NOT set here
}
```

The config is set in a completely separate, unguarded call:

```solidity
// bridge/evm/contracts/BridgeCommittee.sol  lines 63-66
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

The deployment script issues these as two distinct transactions:

```solidity
// bridge/evm/script/deploy_bridge.s.sol  lines 124-178
address bridgeCommittee = Upgrades.deployUUPSProxy("BridgeCommittee.sol",
    abi.encodeCall(BridgeCommittee.initialize, (...)), opts);
// ... deploy BridgeConfig ...
BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig));  // line 175
```

Between the `initialize` transaction and the `initializeConfig` transaction, `config == address(0)` and any address can call `initializeConfig` with an arbitrary `_config`. The "already initialized" guard then permanently locks in the attacker-supplied address.

The `config` object is consumed in three critical paths:

1. **`MessageVerifier.verifyMessageAndSignatures`** (line 46): calls `committee.config().chainID()` for every non-TOKEN_TRANSFER governance message, so chain-ID domain separation is controlled by the attacker.
2. **`SuiBridge.transferBridgedTokensWithSignatures`** (lines 67-89): calls `committee.config()` to resolve `tokenAddressOf(tokenID)` and `chainID()`. A malicious config can map any token ID to any ERC-20 address, redirecting vault transfers.
3. **`BridgeLimiter.initialize`** (line 46): calls `committee.config().isChainSupported()`, so the attacker can make any chain appear supported, bypassing the limiter. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

---

### Impact Explanation

An attacker who wins the front-run permanently installs a malicious `IBridgeConfig`. The committee's legitimate signatures remain valid (signature verification does not touch `config`), but every signed TOKEN_TRANSFER message is now decoded using attacker-controlled token-address mappings. The attacker can cause the vault to release any ERC-20 it holds in response to a legitimately committee-signed transfer message, constituting direct fund theft from the bridge vault. This matches the Critical impact class: bridge governance bypass enabling illegitimate unlock. [6](#0-5) [7](#0-6) 

---

### Likelihood Explanation

The deployment script issues `initialize` and `initializeConfig` as separate transactions. Any mempool observer can detect the `initialize` transaction, compute the resulting proxy address, and submit a `initializeConfig` call with a higher gas price before the deployer's `initializeConfig` lands. No special privilege is required — an ordinary EOA suffices. The deployer's subsequent `initializeConfig` call reverts silently ("Config already initialized"), and if the deployer does not verify the stored `config` address before funding the vault, the bridge goes live with the malicious config. [8](#0-7) 

---

### Recommendation

Add an access-control guard to `initializeConfig`. The simplest fix is to restrict it to the deployer or to the committee itself:

```solidity
// Option A: restrict to the address that called initialize()
// Store msg.sender during initialize() and check it here.

// Option B: fold config initialization into initialize() directly
function initialize(
    address[] memory committee,
    uint16[] memory stake,
    uint16 minStakeRequired,
    address _config          // add config here
) external initializer {
    __CommitteeUpgradeable_init(address(this));
    __UUPSUpgradeable_init();
    // ... populate stakes ...
    require(_config != address(0), "BridgeCommittee: zero config");
    config = IBridgeConfig(_config);
}
```

Folding `config` into the atomic `initializer`-guarded call eliminates the race window entirely, which is the direct fix for the root cause (analogous to calling the correct `__Essential_init(owner, addressManager)` overload in the Taiko bug). [9](#0-8) 

---

### Proof of Concept

1. Deployer broadcasts `BridgeCommittee.initialize(members, stakes, minStake)` — `config` is `address(0)`.
2. Attacker observes the pending transaction, deploys `MaliciousConfig` implementing `IBridgeConfig` with `tokenAddressOf(1) = address(USDC)` (remapping BTC token ID to USDC).
3. Attacker calls `BridgeCommittee(proxy).initializeConfig(address(maliciousConfig))` with higher gas — succeeds because `config == address(0)`.
4. Deployer's `initializeConfig` reverts: "Config already initialized."
5. Deployer funds the vault and the bridge goes live.
6. Committee signs a legitimate BTC TOKEN_TRANSFER message for 1 BTC.
7. Attacker submits the message to `SuiBridge.transferBridgedTokensWithSignatures`.
8. `committee.config().tokenAddressOf(1)` returns USDC address.
9. Vault transfers USDC to the attacker's address instead of BTC to the intended recipient. [2](#0-1) [10](#0-9)
