### Title
ETH sent to or refunded into `ConvexStrategyETH` is permanently locked — no withdrawal path exists - ([File: contracts/strategies/convex/ConvexStrategyETH.sol](contracts/strategies/convex/ConvexStrategyETH.sol))

### Summary
`ConvexStrategyETH` accepts ETH via an unrestricted `receive()` and can accumulate ETH refunds from `ICurveDeposit_2token.add_liquidity`, but neither it nor `ConvexBaseStrategy` exposes any function to move ETH out. The only rescue function, `transferToken`, handles ERC-20 tokens exclusively. Any ETH balance held by the strategy is therefore unrecoverable.

### Finding Description
`ConvexStrategyETH.sol:35` declares `receive() external payable {}` with no sender restriction:

```solidity
receive() external payable {}   // ConvexStrategyETH.sol:35
```

ETH can reach the contract through three paths:

1. **Direct ETH transfer** — any EOA or contract can call `strategy.call{value: X}("")` and the ETH is accepted.
2. **Curve refund dust** — `_depositInCurve` (lines 23-33) unwraps the contract's WETH balance and calls `add_liquidity{value: _balance}`. Curve ETH pools return any unused ETH to `msg.sender` (the strategy). That refund is captured by `receive()` and sits as balance.
3. **Force-sent ETH** — `selfdestruct` beneficiaries also increase the balance.

Once ETH is in the contract, there is no way out:

- `_depositInCurve` only consumes the **WETH** balance (`_weth.balanceOf(address(this))` at line 25); it never wraps or uses `address(this).balance`, so existing ETH is never recycled into the pool.
- `redeemRewards` in `ConvexBaseStrategy.sol:272-371` only routes ERC-20 reward tokens and WETH.
- The emergency rescue `transferToken` (`ConvexBaseStrategy.sol:423-429`) calls `IERC20Detailed(_token).safeTransfer(_to, value)` — ERC-20 only; passing a pseudo-address for ETH reverts or no-ops, so it cannot move the ETH balance.
- `price()` (`ConvexBaseStrategy.sol:378-389`) prices shares purely from `totalLpTokensStaked`, so the ETH contributes nothing to strategy value — it is not even trapped "productively"; it is simply lost.

This is the same bug class as the Derby `XChainController` report: a payable entry point with no corresponding ETH withdrawal.

### Impact Explanation
Permanent freezing of funds. Every wei of ETH that reaches `ConvexStrategyETH` — via mistaken direct sends, Curve `add_liquidity` refunds during honest `redeemRewards` harvests, or dust accumulated over repeated harvests — is locked in the strategy forever. No privileged role (owner, CDO) and no unprivileged user can ever recover it. Over the strategy's lifetime the harvest refund dust alone accrues monotonically, and any user error sending ETH adds to the irrecoverable balance.

### Likelihood Explanation
Medium. The refund path is exercised on every `redeemRewards` call for ETH-denominated Curve pools, since `add_liquidity{value: _balance}` computes consumption internally and refunds the difference — the strategy forwards the entire unwrapped WETH balance rather than the exact amount the pool will use, making residual refunds likely whenever pool ratios don't exactly match. Direct mistaken ETH transfers are also a well-documented occurrence for contracts holding ETH-facing functionality.

### Recommendation
Either sweep or consume the ETH balance:

- Add an owner-only ETH rescue, e.g. in `ConvexBaseStrategy` or `ConvexStrategyETH`:
  ```solidity
  function withdrawETH(address _to) external onlyOwner nonReentrant {
      (bool ok, ) = _to.call{value: address(this).balance}("");
      require(ok);
  }
  ```
- Alternatively, in `_depositInCurve`, wrap any pre-existing/refunded ETH: deposit `address(this).balance` of ETH back into WETH (`IWETH9(WETH).deposit{value: ...}`) before or after `add_liquidity`, so refunds are captured into the ERC-20 flow and swept by the next harvest.
- At minimum, gate `receive()` to only accept ETH from the Curve pool and WETH contracts, and handle the refund explicitly.

### Proof of Concept
Foundry fork test (mainnet, stETH/ETH-style pool deployment of `ConvexStrategyETH`):

```solidity
// test/foundry/ConvexStrategyETHStuck.t.sol
function testEthStuckInStrategy() public {
    // strategy: deployed ConvexStrategyETH proxy, initialized for an ETH-pair pool
    ConvexStrategyETH strategy = ConvexStrategyETH(payable(STRATEGY));

    uint256 dust = 1 ether;
    // Path 1: anyone can send ETH directly; receive() accepts it
    (bool ok, ) = address(strategy).call{value: dust}("");
    assertTrue(ok);
    assertEq(address(strategy).balance, dust);

    // Path 2: simulate a Curve add_liquidity refund left in the contract
    // (already covered by the send above; refunds land identically)

    // No recovery exists:
    // - transferToken only does IERC20Detailed.safeTransfer, cannot move ETH
    vm.startPrank(strategy.owner());
    // Any ETH rescue attempt via transferToken(ETH_ADDR, ...) reverts / no-ops
    // - _depositInCurve only uses WETH balance; ETH balance never consumed
    vm.stopPrank();

    // Invariant: ETH balance is permanently unrecoverable
    // (no code path in ConvexStrategyETH/ConvexBaseStrategy decreases address(this).balance)
}
```

The PoC demonstrates that after ETH lands in the strategy, exercising every state-changing function (`deposit`, `redeem`, `redeemRewards`, `transferToken`) leaves `address(strategy).balance` unchanged — the funds are stuck permanently.

Note: this finding assumes the Convex strategy contracts are in-scope for the audit surface; if `contracts/strategies/convex/` is treated as legacy/out-of-scope per the engagement rules, there is no other production contract in the repo with an open ETH entry point (the credit-vault surface — `IdleCreditVault`, `ProgrammableBorrower`, `IdleCDO*` — contains no `payable`/`receive` paths, and `LidoCDOTrancheGateway.receive` is restricted to the WETH contract and consumes its full balance each call), in which case the analog does not hold.
