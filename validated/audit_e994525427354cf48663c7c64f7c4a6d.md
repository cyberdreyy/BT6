## Analog Found: Attacker-Controlled Deposits Can Permanently Halt Derivation via Unrecoverable `BlockGasLimitExceeded` on the Deposit-Only Retry Path

### Title
Derivation pipeline permanently halts when even the Holocene deposit-only retry block fails execution — ([File: crates/proof/driver/src/core.rs])

### Summary
The LimboDAO bug class is: a single-slot state machine that has only one recovery path (accept-and-execute or reject) gets permanently stuck if that one path itself reverts. Base's derivation driver has the same structural weakness in `Driver::advance_to_target`: when normal block execution fails post-Holocene, the *only* recovery path is to strip non-deposit transactions and retry with a deposit-only block. If that retry *also* fails, the driver has no further fallback and returns a hard error, halting the derivation pipeline for that node permanently at that block height.

### Finding Description
`advance_to_target` executes the payload, and on failure (post-Holocene) attempts exactly one recovery: flush the channel and re-execute with only deposit transactions retained [1](#0-0) . If that retried, deposit-only execution *also* returns an error, the function propagates it as `DriverError::Executor(e)` with no further recovery attempted [2](#0-1) . This is the same "one recovery path, and if it fails you're stuck" pattern as the LimboDAO report: there is no third fallback (e.g., skipping the block, or producing an empty block without deposits).

`ExecutorError::is_deposit_only_retryable` classifies `BlockGasLimitExceeded`, `UnsupportedTransactionType`, `BlockExecutionError::Validation`, and signature `Recovery` errors as retryable via the deposit-only path [3](#0-2) . Critically, `BlockGasLimitExceeded` occurs when the *cumulative* gas of all transactions in the block (including the mandatory L1-attributes deposit transaction and any user deposits sourced from L1) exceeds the L2 block gas limit [4](#0-3) . Deposit transactions are not subject to normal fee-market admission control (they originate from L1, not the L2 mempool), and individual deposit transactions cannot fail at the per-transaction level — the OP-stack invariant "deposits cannot fail" only guards per-tx execution, converting reverts/halts into a `FailedDeposit` outcome rather than block-level rejection [5](#0-4) . Nothing in this per-tx handling prevents the *sum* of several attacker-supplied deposit gas limits (submitted to the L1 portal within a single sequencing epoch) from exceeding the L2 block gas limit on its own — i.e., even after stripping every non-deposit transaction, the deposit-only retry block still contains the same over-limit deposit set and fails identically with `BlockGasLimitExceeded`.

The identical retry-then-hard-fail structure is duplicated in the fault-proof/ZK program's block-advance routine, so the same halt condition affects the zkVM fault-proof client as well as any full/verifier node running the driver [6](#0-5) .

### Impact Explanation
If an unprivileged depositor crafts enough L1 `depositTransaction` calls (each within any per-tx gas ceiling enforced on L1) whose gas limits sum, together with the mandatory L1-attributes deposit transaction, to more than the configured L2 block gas limit, the resulting L2 slot can never be executed successfully — not on the first attempt (full tx set) and not on the deposit-only retry (which contains the exact same offending deposits). Every node running this derivation code — sequencer, verifier nodes, and the fault-proof program — reaches the same unrecoverable `DriverError::Executor(e)` at that block height and halts. This is a node/chain halt: safe-head progress for the whole network stops at a block no node can produce, matching the class of impact ("node halt", "chain split" if some nodes have different upgrade activation windows) explicitly listed as in-scope.

### Likelihood Explanation
Reaching this condition only requires calling the standard, public L1 deposit-transaction entry point (`OptimismPortal`-style `depositTransaction`) enough times within one sequencing window with attacker-chosen `gasLimit` values — no privileged role, sequencer cooperation, or contract bug is needed. The only defenses that could prevent this are L1-side per-deposit gas ceilings and the sequencing-window size relative to the L2 block gas limit; whether current configuration values make this economically/practically feasible (cost of L1 gas to reserve enough L2 deposit gas) determines exploitability, but the code path itself has no additional safety net once the deposit-only retry is entered.

### Recommendation
Add a further fallback below the deposit-only retry: if a deposit-only block still fails with `BlockGasLimitExceeded` (or another block-level, non-per-tx error), do not propagate a fatal `DriverError`; instead the pipeline should force-advance safely — e.g., by de-prioritizing/dropping the offending oversized deposit set into subsequent blocks (mirroring how the OP-stack spec already guarantees each *individual* deposit's inclusion but not necessarily all deposits from one epoch in one block), or by enforcing at L1-derivation time that a batch of deposits sourced from a single epoch can never exceed the L2 block gas limit, splitting them across multiple L2 blocks instead of packing them into one that can never execute.

### Proof of Concept
1. Configure an L2 chain with block gas limit `G`.
2. From an unprivileged L1 account, call the L1 deposit contract's `depositTransaction` repeatedly within a single sequencing window, choosing `gasLimit` values that individually pass L1-side admission but whose sum (plus the L1-attributes deposit's own gas) exceeds `G`.
3. When the sequencing window closes, the derivation pipeline builds the L2 block for that epoch. The full-tx execution fails, triggering the Holocene deposit-only retry per `advance_to_target` [7](#0-6) .
4. The deposit-only block still contains the same over-limit deposit set, so `execute_payload` fails again with `BlockGasLimitExceeded`.
5. `advance_to_target` returns `Err(DriverError::Executor(e))` [8](#0-7) , halting derivation for every node at that block height, with no further recovery path in the codebase.

impl ExecutorError {
    /// Returns whether this error represents an invalid payload that may use Holocene
    /// deposit-only recovery.
    ///
    /// Only errors caused by per-transaction invalidity are eligible: stripping
    /// non-deposit transactions cannot rescue a block whose header/attribute fields are
    /// themselves invalid (e.g. `InvalidExtraData`, `MissingEIP1559Params`), so those
    /// propagate as a hard halt instead.
    pub const fn is_deposit_only_retryable(&self) -> bool {
        matches!(
            self,
            Self::BlockGasLimitExceeded
                | Self::UnsupportedTransactionType(_)
                | Self::ExecutionError(BlockExecutionError::Validation(_))
                | Self::Recovery(_)
        )
    }
}
