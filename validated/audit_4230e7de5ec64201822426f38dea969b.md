### Title
`getLargestAccounts` RPC handler returns commitment-mismatched, stale cached results — ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_largest_accounts` (and its supporting `LargestAccountsCache`) caches results keyed only by the optional `RpcLargestAccountsFilter`, with freshness gated purely by a time-based TTL. It never validates the cached entry against the bank/slot that corresponds to the commitment level of the *current* request. This lets an unprivileged JSON-RPC caller receive account-balance data computed for a different commitment level/slot than the one they requested, silently, within the cache TTL window — the same root-cause pattern as the referenced Wild Credit bug: a stale, unrefreshed value is used in place of state recomputed against the caller's actual context.

### Finding Description
`get_largest_accounts` first resolves a bank for the caller-supplied commitment via `self.bank(config.commitment)` [1](#0-0) , but before using that bank it checks the cache with only the `filter` as the key:

```
fn get_cached_largest_accounts(&self, filter: &Option<RpcLargestAccountsFilter>) -> Option<(u64, Vec<RpcAccountBalance>)> {
    let largest_accounts_cache = self.largest_accounts_cache.read().unwrap();
    largest_accounts_cache.get_largest_accounts(filter)
}
``` [2](#0-1) 

If a hit is found, the handler returns it directly, using the cached `slot` for the response context, without checking whether that cached slot/data is consistent with the commitment (`processed`/`confirmed`/`finalized`) that the *current* caller requested:
```
if let Some((slot, accounts)) = self.get_cached_largest_accounts(&config.filter) {
    Ok(RpcResponse { context: RpcResponseContext::new(slot), value: accounts })
} else { ... }
``` [3](#0-2) 

The underlying `LargestAccountsCache` implementation confirms the cache key is only the `filter`, and validity is solely time-based:
```
pub(crate) fn get_largest_accounts(&self, filter: &Option<RpcLargestAccountsFilter>) -> Option<(u64, Vec<RpcAccountBalance>)> {
    self.cache.get(filter).and_then(|value| {
        if let Ok(elapsed) = value.cached_time.elapsed()
            && elapsed < Duration::from_secs(self.duration)
        {
            return Some((value.slot, value.accounts.clone()));
        }
        None
    })
}
``` [4](#0-3) 

Whichever commitment level's request happens to populate the cache first (via `set_cached_largest_accounts`, called with `bank.slot()` from whatever commitment resolved the bank) will serve *all* subsequent callers with any commitment level for the TTL duration:
```
self.set_cached_largest_accounts(&config.filter, bank.slot(), &accounts);
``` [5](#0-4) 

This mirrors the report's bug class: the code fails to "accrue"/refresh state relative to the caller's actual context (here, commitment/slot) before returning a value, and instead reuses a stale value computed under different, unrelated conditions.

### Impact Explanation
An unprivileged RPC client requesting `getLargestAccounts` with `commitment: "finalized"` can receive data and a slot number that were actually computed for a `"processed"` (or `"confirmed"`) request made by a completely different, unrelated client shortly before — i.e., wrong-slot/wrong-commitment data returned from a query. This violates the commitment-level guarantee the RPC API is supposed to provide (finalized data should never reflect potentially-rolled-back processed-only state, and vice versa), and can mislead consumers (e.g., exchanges, explorers, monitoring tools) who rely on `finalized` results being final/rooted.

### Likelihood Explanation
This is reachable by any unprivileged caller with a single `getLargestAccounts` RPC call — no special role or multiple-client coordination is required. The mismatch surfaces whenever two calls with different commitment levels for the same filter happen within the TTL window, which on any public/multi-tenant RPC endpoint (or even a single client alternating commitment levels) is a routine occurrence, not a rare race.

### Recommendation
Include the resolved bank's commitment level (or the resolved bank's slot/epoch) as part of the `LargestAccountsCache` key, or store a separate cache entry per commitment level, so that a hit is only served when it matches both the `filter` and the commitment context of the current request. Alternatively, validate that the cached slot is consistent with (e.g., `>=`/`==`) the bank resolved for the current request's commitment before returning it.

### Proof of Concept
1. Client A calls `getLargestAccounts` with `commitment: "processed"`. This populates `LargestAccountsCache` for filter `None` with `slot = <processed_slot>` and the corresponding balances.
2. Within `duration` seconds (the cache TTL), Client B calls `getLargestAccounts` with `commitment: "finalized"`.
3. In `get_largest_accounts`, `self.bank(config.commitment)` resolves the finalized bank, but the cache lookup at `get_cached_largest_accounts(&config.filter)` (keyed only by `filter`) returns Client A's `processed`-level cached result, which is returned to Client B as if it were finalized data — including the (possibly non-finalized) `slot` used as the response context.

Note: I could not verify the exact configured TTL (`duration`) value passed to `LargestAccountsCache::new` in `rpc_service.rs` within the available index; a Devin session with full repo access would be needed to confirm the exact production TTL constant if precise timing details are required.
