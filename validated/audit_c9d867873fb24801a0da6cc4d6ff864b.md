### Title
Settled APR0 withdraw receipts escape the epoch loss haircut because `apr0Users` collapses per-epoch basis into a single `settledPrincipal` bucket - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The PyOpenEXR bug is a key-collision class bug: two distinct channel identifiers (`left` vs `left.R/.G/.B`) are coalesced into one shared container, so the container is sized/keyed for only one of them and the write overflows. In `IdleCreditVault`, the same pattern exists for APR0 withdraw receipts: the loss-recovery haircut is keyed by request epoch (`lossRecoveryPriceByEpoch[epoch]` matched against `apr0Users[user].principalEpoch`), but `_settleApr0` folds the epoch-tagged `principal` into an epoch-less `settledPrincipal` scalar. Once folded, the epoch identity is lost, so a settled APR0 receipt skips the haircut check in `requestWithdraw` and the haircut basis in `_claimLossAdjustedWithdrawRequest`, and is later paid at par in `_claimFundedWithdrawRequest`.

### Finding Description
- `requestWithdraw` blocks a new request when a loss-adjusted receipt exists for `lastWithdrawRequest`, but the APR0 branch only checks `apr0Users[_user].principal != 0 && principalEpoch == lossEpoch`. `settledPrincipal` is not checked (`IdleCreditVault.sol:263-271`).
- `_settleApr0` moves `principal` to `settledPrincipal` and zeroes `principal`/`principalEpoch` (`IdleCreditVault.sol:556-564`). `_requestWithdrawApr0` calls `_settleApr0` before recording a new request (`IdleCreditVault.sol:567-577`), so a second request in a later epoch auto-settles the old loss-epoch principal into the untagged bucket.
- `_withdrawClaimAmountsForEpoch` — the basis used by `_claimLossAdjustedWithdrawRequest` — only counts `principal` when `principalEpoch == _claimEpoch`; `settledPrincipal` is never included (`IdleCreditVault.sol:862-881`).
- `_claimFundedWithdrawRequest` then pays `settledPrincipal + settledInterest` at par via `_transferFundedClaim` (`IdleCreditVault.sol:338-349`).

Attack sequence (APR0 mode, borrower-funded loss epoch):
1. Epoch N running, `unscaledApr == 0`. Attacker calls `requestWithdraw` via the CDO for `P` → `principal = P`, `principalEpoch = N`, `lastWithdrawRequest = N`.
2. `stopEpochWithDuration(_lossAmount)` at end of epoch N: `collectWithdrawFunds` funds less than `pendingWithdraws` and stores `lossRecoveryPriceByEpoch[N] = p < 1e18`; `epochNumber` becomes N+1.
3. Epoch N+1 running, APR still 0. Attacker requests a second withdraw of dust amount. `_requestWithdrawApr0` → `_settleApr0` settles P (reqEpoch N < epochNumber N+1) into `settledPrincipal`, clearing `principal`/`principalEpoch`. The guard at line 263-271 sees `principal == 0` and does not revert. New request is recorded with `principalEpoch = N+1`, `lastWithdrawRequest = N+1`.
4. Epoch N+1 ends (no loss). Attacker calls `claimWithdrawRequest`: `_claimLossAdjustedWithdrawRequest` uses `lossEpoch = lastWithdrawRequest = N+1` (no loss price) — the epoch-N haircut pointer was overwritten; `_claimFundedWithdrawRequest` pays `settledPrincipal = P` at 100% instead of `P * p`.

### Impact Explanation
Direct theft / insolvency among receipt holders. The borrower only funded `pendingToFund = pendingBasis - pendingLoss` for the loss epoch. Every other epoch-N receipt holder is capped at `p` per unit; the attacker drains `P` at par, so `(1 - p) * P` is stolen from the funded claim pool, leaving the last claimants unpaid. Loss scales with the attacker's share of the epoch-N pending bucket; repeatable across users controlled by the attacker.

### Likelihood Explanation
Requires only an unprivileged KYC-passed lender in APR0 mode and an honest `stopEpochWithDuration` loss plus one extra dust withdraw request — all callable in sequence around honest manager/borrower calls. No privileged collusion needed. The guard explicitly intends to force claim-before-rerequest for loss receipts ("must be claimed before opening a later request"), and it fails precisely for the settled-APR0 path.

### Recommendation
Include `settledPrincipal`/`settledInterest` provenance in the loss check and claim basis: either store the epoch for settled APR0 amounts (e.g., `settledPrincipalEpoch`), or extend the `requestWithdraw` guard to revert when `apr0Users[_user].settledPrincipal != 0` and a nonzero `lossRecoveryPriceByEpoch` exists for the epoch that produced it, and include settled amounts attributable to `lossEpoch` in `_withdrawClaimAmountsForEpoch`.

### Proof of Concept
```solidity
// Fork test on IdleCreditVault + IdleCDOEpochVariant in APR0 mode.
// Assumes standard helpers in test/foundry (depositWithUser, _stopCurrentEpoch, ...).

function testApr0SettledPrincipalEscapesLossHaircut() external {
    // --- epoch N running, unscaledApr == 0 ---
    _stopCurrentEpochWithApr(0);               // APR0 mode for next epoch
    address alice = makeAddr('alice');          // attacker (KYC'd)
    address bob   = makeAddr('bob');            // honest receipt holder
    _depositWithUser(alice, 100e6);
    _depositWithUser(bob,   100e6);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // both request withdraws in epoch N (APR0 path)
    _requestWithdrawWithUser(alice, 100e18);
    _requestWithdrawWithUser(bob,   100e18);

    // --- honest stopEpochWithDuration with a 50% loss ---
    _stopCurrentEpochWithLoss( /* lossAmount = 50% of basis */ );
    // collectWithdrawFunds stored lossRecoveryPriceByEpoch[N] ~= 0.5e18
    assertGt(strategy.lossRecoveryPriceByEpoch(1), 0);
    assertLt(strategy.lossRecoveryPriceByEpoch(1), 1e18);

    // --- epoch N+1 running, APR still 0 ---
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Bob tries to re-request: reverts (guard works for normal basis check)
    // Alice re-requests dust: _settleApr0 folds her P into settledPrincipal,
    // guard sees principal == 0 and passes.
    _requestWithdrawWithUser(alice, 1);        // dust, does NOT revert

    // --- epoch N+1 ends cleanly (fully funded) ---
    _stopCurrentEpochWithApr(0);

    // Alice claims: epoch-N receipt paid at par instead of at ~0.5 haircut
    uint256 balPre = underlying.balanceOf(alice);
    vm.prank(address(cdoEpoch));
    strategy.claimWithdrawRequest(alice);
    uint256 aliceGot = underlying.balanceOf(alice) - balPre;

    // expected if haircut applied: ~50e6 + dust; actual: ~100e6 + dust
    assertGt(aliceGot, 90e6);                  // haircut bypassed

    // Bob claims last: funded pool is short -> transfer underflows or
    // bob receives less than his lossRecoveryPrice share.
    vm.prank(address(cdoEpoch));
    strategy.claimWithdrawRequest(bob);        // underpaid / reverts
}
```

Key assertion: `claimWithdrawRequest` pays `settledPrincipal` at par because `_withdrawClaimAmountsForEpoch` never attributes `settledPrincipal` to `lossEpoch`, while `_transferFundedClaim` draws from the same underfunded pool as honest haircut recipients.
