### Title
Race between `DependencyTracker::declare_work()` and `TransactionStatusSender::send()` lets `TransactionStatusService` mark higher-numbered work "processed" before an earlier work's batch is even enqueued, causing premature `wait_for_dependency` release before its Blockstore write completes - (File: runtime/src/dependency_tracker.rs, runtime/src/transaction_execution.rs, rpc/src/transaction_status_service.rs)

### Finding Description
`TransactionStatusSender::send_transaction_status_batch` calls `dependency_tracker.declare_work()` to obtain a monotonically increasing sequence number and then, in a separate, unsynchronized step, sends the batch over the crossbeam channel: [1](#0-0) . `declare_work()` only atomically increments a counter; it does not hold any lock across the subsequent `self.sender.send(...)` call: [2](#0-1) .

Multiple banking-stage threads hold clones of the same `TransactionStatusSender` (via `Committer`, one per `Consumer`/banking thread), each independently calling `send_transaction_status_batch` on the shared bank. Because `declare_work()` (id assignment) and `sender.send()` (channel enqueue) are two separate, non-atomic operations, thread A can call `declare_work()` and get id `N`, then be preempted before calling `send()`; thread B can then call `declare_work()` to get `N+1` and successfully call `send()` first. The crossbeam channel preserves *send order*, not *work-id order*, so `TransactionStatusService::write_transaction_status_batch` receives and processes the message for `N+1` before the message for `N` even exists in the channel, and calls `dependency_tracker.mark_this_and_all_previous_work_processed(N+1)`: [3](#0-2) .

`mark_this_and_all_previous_work_processed(N+1)` sets `processed_work_id = N+1` and wakes all waiters, explicitly documented to mean "all work with id number less than 's' have been processed": [4](#0-3) . This is now false: work `N`'s batch has not been sent, let alone written to Blockstore.

Any concurrent caller of `wait_for_dependency(M)` where `M <= N+1` (e.g. `OptimisticallyConfirmedBankTracker::process_notification`, which is fed a `dependency_work` id read from `get_current_declared_work()` by `replay_stage.rs` at bank-freeze time) will return immediately: [5](#0-4) [6](#0-5) . Because `get_current_declared_work()` simply loads the atomic counter (which was already bumped to `N` by thread A's `declare_work()` call even though A hasn't sent yet), the value handed to the waiter can already satisfy the race window described above, and the tracker will falsely believe transaction batch `N` has been persisted to Blockstore when it has not.

### Impact Explanation
This causes `OptimisticallyConfirmedBankTracker` to proceed with updating the optimistically-confirmed bank and firing subscription notifications before the Blockstore write for an earlier transaction's status batch has completed. A client's `getTransaction` / `getTokenAccountBalance` / `getSignatureStatuses` request that lands in the small race window can be served against a Blockstore state missing (or holding a partially-applied older version of) the earlier transaction's metadata (e.g., an `InitializeMint`/`SetAuthority`/`MintTo` batch), so `parse_token.rs` decoding logic operating on stale/absent data returns wrong mint decimals or incorrect authority information to an RPC caller. This matches the "wrong-slot/fork/account data returned" bounty category from a single low-rate query.

### Likelihood Explanation
Preconditions are met by default whenever `dependency_tracker` is enabled (i.e., `initialize_rpc_transaction_history_services` wired with a `DependencyTracker`, `rpc/src/rpc.rs` / `core/src/validator.rs`): [7](#0-6) . Any client submitting ordinary transaction load to a leader causes multiple banking-stage threads to concurrently call `send_transaction_status_batch` on shared `TransactionStatusSender` clones, which is normal unprivileged behavior (no leader/validator control needed by the attacker — only many concurrent transactions to a normal leader). The race window (gap between `declare_work()`'s atomic fetch_add and the subsequent `send()`) is small but real; it is a scheduling race whose probability increases with transaction throughput and thread contention, so it is reproducible under sustained concurrent load, though not deterministically triggerable on demand from a single RPC call.

### Recommendation
Make id-assignment and channel-enqueue atomic with respect to other producers, e.g. by holding a single mutex around "declare_work + send" per `TransactionStatusSender`, or by having `TransactionStatusService`/`DependencyTracker` buffer and reorder incoming batches by `work_id` (only advancing `processed_work_id` up to the largest **contiguous** prefix actually received/written), instead of trusting arrival order in the channel to match declared work-id order.

### Proof of Concept
```rust
// runtime/src/dependency_tracker.rs (new test)
#[test]
fn test_out_of_order_declare_and_send_violates_invariant() {
    use std::sync::{Arc, Barrier};
    use crossbeam_channel::unbounded;

    let dependency_tracker = Arc::new(DependencyTracker::default());
    let (sender, receiver) = unbounded::<u64>();
    let barrier = Arc::new(Barrier::new(2));

    // Thread A: declare_work -> get N, then stall before sending.
    let dt_a = dependency_tracker.clone();
    let s_a = sender.clone();
    let b_a = barrier.clone();
    let handle_a = std::thread::spawn(move || {
        let id = dt_a.declare_work(); // gets N
        b_a.wait(); // synchronize so B runs its declare_work after A's, but sends first
        std::thread::sleep(std::time::Duration::from_millis(50));
        s_a.send(id).unwrap(); // simulate TransactionStatusSender::send happening late
        id
    });

    // Thread B: declare_work -> get N+1, sends immediately (wins the race).
    let dt_b = dependency_tracker.clone();
    let s_b = sender.clone();
    let b_b = barrier.clone();
    let handle_b = std::thread::spawn(move || {
        b_b.wait();
        let id = dt_b.declare_work(); // gets N+1
        s_b.send(id).unwrap(); // arrives in channel BEFORE A's message
        id
    });

    let id_a = handle_a.join().unwrap();
    let id_b = handle_b.join().unwrap();
    assert!(id_b > id_a);

    // Simulate TransactionStatusService: process messages strictly in channel
    // (arrival) order, calling mark_this_and_all_previous_work_processed for each.
    let first_received = receiver.recv().unwrap();
    assert_eq!(first_received, id_b); // N+1 arrives first
    dependency_tracker.mark_this_and_all_previous_work_processed(first_received);

    // A waiter for id_b's "dependency" now returns immediately...
    dependency_tracker.wait_for_dependency(id_b);

    // ...even though work id_a (< id_b) has NOT been processed/"written" yet:
    let second_received = receiver.recv().unwrap();
    assert_eq!(second_received, id_a);
    // This demonstrates the invariant "notify s implies all ids < s processed" is
    // violated: mark_this_and_all_previous_work_processed(id_b) fired before id_a's
    // corresponding batch was even consumed from the channel.
}
```
Expected result: the test passes, demonstrating that `wait_for_dependency(id_b)` unblocks and `mark_this_and_all_previous_work_processed(id_b)` is observed by a waiter before the message for the smaller `id_a` has even been received/processed — confirming the "notify id s implies all ids < s are processed" invariant can be broken by ordinary concurrent producers of `TransactionStatusSender`.

    /// Acquire the next work id number.
    /// The work id starts from 0 and increments by 1 each time it is called.
    pub fn declare_work(&self) -> u64 {

    /// Notify all waiting threads that a work has been processed with the given work id.
    /// This function will update the processed work id and notify all waiting threads only if the work
    /// id is greater than the procsessed work id. Notify a work of id number 's' will
    /// implicitly imply that all work with id number less than 's' have been processed.
    pub fn mark_this_and_all_previous_work_processed(&self, work_id: u64) {
        let mut processed_work_id = self.processed_work_id.lock().unwrap();
        if less_than(&processed_work_id, work_id) {
            *processed_work_id = Some(work_id);
            self.condvar.notify_all();
        }
    }
