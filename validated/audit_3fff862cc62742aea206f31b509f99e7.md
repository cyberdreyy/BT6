### Title
Default Oracle Confidence Tolerance (10%) With Hardcoded 5% Price-Bias Cap Understates True Price Uncertainty - ([File: programs/marginfi/src/state/price.rs])

### Summary
Marginfi's oracle confidence-interval handling has the same structural flaw as the reported `Engine.sol` issue: a wide "acceptable deviation/confidence" window is allowed to pass validation, but the actual price adjustment applied to health/valuation math is capped independently and more tightly, so the protocol continues to price collateral/liabilities as if uncertainty were smaller than it actually is.

### Finding Description
For both `PythPushOraclePriceFeed::get_confidence_interval` and `SwitchboardPullPriceFeed::get_confidence_interval`, the oracle's confidence interval is validated against `bank.config.oracle_max_confidence`. If the admin never sets this field (the default, `0`), the code falls back to a lenient default of 10% (`U32_MAX_DIV_10`): [1](#0-0)  and the equivalent Switchboard path [2](#0-1) .

After this 10% rejection check passes, the actual confidence value used to bias asset/liability prices is unconditionally clamped to a hardcoded 5% ceiling, regardless of the real oracle confidence: [3](#0-2) [4](#0-3) 

This behavior and the 5% constant are confirmed in `type-crate/src/constants.rs`: [5](#0-4) 

and explicitly documented in the `BankConfigCompact.oracle_max_confidence` field comment: "the confidence adjustment is capped at 5% regardless of this value... 0% = use the default (10%)": [6](#0-5) 

The clamped confidence interval is then what gets subtracted/added to the raw price for `PriceBias::Low`/`PriceBias::High` in health-check valuation: [7](#0-6) 
and this bias is used throughout account health calculations for both assets and liabilities: [8](#0-7) 

So under default configuration (no admin action needed — `oracle_max_confidence = 0` is simply the un-set default), an oracle can report legitimate confidence anywhere up to just under 10% of price without the transaction reverting, yet the health engine will only ever discount/inflate the price by at most 5%. This is directly analogous to the reported `MAX_PRICE_DEVIATION_UPPER_BOUND = 500` (5%) issue: a validation gate that is wider than the value actually used for risk-sensitive pricing, allowing the protocol to keep operating (minting/borrowing/valuing) on prices that don't reflect the true available uncertainty signal.

### Impact Explanation
During periods of real oracle uncertainty (e.g., 6–9% confidence, which passes the default 10% gate), the protocol undervalues the risk by capping the bias at 5%. This means:
- Assets are valued higher than the conservative bound truly implied by oracle confidence, inflating a user's initial/maintenance health and allowing larger borrows or preventing timely liquidation eligibility.
- Liabilities are valued lower than the conservative bound implied by oracle confidence, understating debt risk.

This creates a value-redirection/exploitable-misvaluation risk with real financial effect on protocol solvency (bad debt exposure) during volatile oracle conditions, reachable by any regular (unprivileged) borrower/depositor without needing an admin to misconfigure anything — the flaw exists in the unset/default configuration path.

### Likelihood Explanation
Requires the oracle confidence to genuinely sit between the 5% hard cap and the (default or admin-configured) rejection threshold (up to 10% by default, or higher if an admin raises `oracle_max_confidence`). This is plausible during normal market volatility spikes on less liquid assets, and is more likely to be hit precisely in the depeg/volatility scenarios that risk parameters are meant to protect against — the same scenario class the original report was concerned with (protocol keeps operating during meaningful price uncertainty). It does not require attacker-controlled oracle manipulation to occur, only genuine wide (but "valid") confidence readings, making it moderately likely under stress conditions rather than purely theoretical.

### Recommendation
Align the rejection threshold with the price-bias cap: either (a) lower the default/allowed `oracle_max_confidence` ceiling to match `MAX_CONF_INTERVAL` (5%), so a price that would be clamped is instead rejected outright rather than silently understated, or (b) remove the independent clamp and always apply the actual (validated) confidence interval as the bias, so the protocol's valuation reflects the same uncertainty bound it validated against. At minimum, tighten the default fallback (`U32_MAX_DIV_10` → 10%) to be closer to the 5% cap so the two thresholds are consistent.

### Proof of Concept
1. Bank is configured with default `oracle_max_confidence = 0` (never explicitly set — the common/default case, no admin action required).
2. Oracle (Pyth or Switchboard) reports a genuine confidence interval of, e.g., 8% of price — this passes validation because 8% < default 10% threshold (`price.rs` lines 1648-1670 / 1412-1428).
3. `get_confidence_interval` returns `min(8%, 5%) = 5%` due to the hardcoded `MAX_CONF_INTERVAL` clamp (`price.rs` lines 1672-1687 / 1430-1445).
4. Health calculations in `calc_weighted_asset_value_standalone` apply this 5% bias instead of the true 8% uncertainty (`marginfi_account.rs` lines 1296-1311), understating risk for both collateral and debt valuation during a period of real, validated 8% price uncertainty.

impl PriceAdapter for PythPushOraclePriceFeed {
    fn get_price_of_type(
        &self,
        price_type: OraclePriceType,
        bias: Option<PriceBias>,
        oracle_max_confidence: u32,
    ) -> MarginfiResult<I80F48> {
        let price = match price_type {
            OraclePriceType::TimeWeighted => self.get_ema_price()?,
            OraclePriceType::RealTime => self.get_unweighted_price()?,
        };

        match bias {
            None => Ok(price),
            Some(price_bias) => {
                let confidence_interval = self.get_confidence_interval(
                    matches!(price_type, OraclePriceType::TimeWeighted),
                    oracle_max_confidence,
                )?;

                let biased_price = match price_bias {
                    PriceBias::Low => price
                        .checked_sub(confidence_interval)
                        .ok_or_else(math_error!())?,
                    PriceBias::High => price
                        .checked_add(confidence_interval)
                        .ok_or_else(math_error!())?,
                };

                Ok(biased_price)
            }
        }
    }
