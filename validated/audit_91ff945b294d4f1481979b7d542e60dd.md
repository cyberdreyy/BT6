## Finding: Missing beneficiary-acceptance check in `staking_contract::set_beneficiary_for_operator` permanently locks commission distribution for all stakers of an operator

### Title
Operator can permanently DoS commission/stake distribution for all its stakers by setting an unregistered/opted-out beneficiary - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::set_beneficiary_for_operator` lets an operator redirect its commission payouts to any `new_beneficiary` address without any validation that the address can actually receive a direct APT transfer. [1](#0-0) 
This mirrors the external report's root cause exactly: an operation is allowed to target an arbitrary destination address with no existence/validity check, and the code that later "calls" that destination (here, `aptos_account::deposit_coins`) can revert unexpectedly. The framework itself acknowledges this exact hazard in `vesting.move::set_beneficiary`, which explicitly calls `assert_account_is_registered_for_apt(new_beneficiary)` "so `distribute()` wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered." [2](#0-1) 
That same guard is absent from `staking_contract::set_beneficiary_for_operator`.

### Finding Description
`distribute_internal` iterates every shareholder of a `StakingContract`'s `distribution_pool` in a single transaction, redeeming shares and then depositing coins to each recipient — including substituting the operator's beneficiary address when the recipient is the operator: [3](#0-2) 

The deposit goes through `aptos_account::deposit_coins`, which auto-creates the recipient account if it doesn't exist, but if the account exists and has opted out of unregistered/direct coin transfers (`can_receive_direct_coin_transfers` returns false), the call aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`: [4](#0-3) 

Since Move transactions are atomic, an abort mid-loop reverts the entire `distribute`/`distribute_internal` call — including the share redemptions already performed for *other* shareholders in that same distribution pool. Critically, `set_beneficiary_for_operator` sets **one beneficiary per operator address, not per staking contract** ("An operator can set one beneficiary for staking contract pools, not a separate one for each pool"), so a single malicious or careless beneficiary configuration poisons `distribute()` for every staker that has delegated to that operator. [5](#0-4) 

Compare this to `vesting::set_beneficiary`, which the framework authors explicitly hardened with `assert_account_is_registered_for_apt` for precisely this reason — that fix was never applied to `staking_contract::set_beneficiary_for_operator` (nor to the analogous `delegation_pool::set_beneficiary_for_operator`, though that path buys shares internally rather than calling `deposit_coins` directly, so it is not affected the same way).

### Impact Explanation
Any operator can call `set_beneficiary_for_operator(operator, new_beneficiary)` and set `new_beneficiary` to an address that has called `aptos_account::set_allow_direct_coin_transfers(false)` (an unprivileged, user-controlled setting). From that point on, `distribute()`/`distribute_internal()` for **every staker-operator pair under that operator** will permanently abort whenever there is any unlocked/inactive stake or commission to distribute, since the loop always attempts to pay the operator's commission portion to the poisoned beneficiary before completing. This traps the unlocked/withdrawable funds of unrelated stakers (their own inactive/pending_inactive stake) indefinitely, since `distribute` is the only entry point that withdraws and pays out `inactive`/`pending_inactive` stake from the pool. This satisfies "Permanent lock or non-recoverable loss of claim rights in stake ... commission, beneficiary ... flows" and "share-accounting corruption ... that traps value."

The operator itself, or a beneficiary account the operator does not fully control (e.g., set then later opted out), can trigger this — no privileged role is required beyond the operator role the attacker already legitimately holds over their own staking relationships, but the blast radius extends to unrelated stakers' funds, which they do not control.

### Likelihood Explanation
High likelihood: this requires only two ordinary, unprivileged entry-function calls — `staking_contract::set_beneficiary_for_operator` (by the operator) and `aptos_account::set_allow_direct_coin_transfers(false)` (by the beneficiary address, which can be the operator's own alternate account) — with no special preconditions, race, or governance action needed.

### Recommendation
Add the same guard used in `vesting::set_beneficiary` to `staking_contract::set_beneficiary_for_operator` (and audit `delegation_pool::set_beneficiary_for_operator` for the same class of issue): require `new_beneficiary` to be registered/able to accept direct APT transfers before allowing the update, e.g. call `aptos_account::assert_account_is_registered_for_apt(new_beneficiary)` or equivalent, and/or make `distribute_internal` resilient to a single failed payout (e.g., skip/queue that specific recipient rather than aborting the whole batch) so one poisoned beneficiary cannot block distribution to unrelated shareholders.

### Proof of Concept
1. Operator `O` runs `staking_contract::create_staking_contract` (or is added via `staking_contract::add_stake`) with staker `S1`, `S2`, ... each creating a `StakingContract` under `O`.
2. Attacker (could be `O` itself, or anyone who convinces `O`) sets `new_beneficiary = X` via `staking_contract::set_beneficiary_for_operator(O, X)`.
3. `X` calls `aptos_account::set_allow_direct_coin_transfers(false)` and never registers a `CoinStore<AptosCoin>` (or has none from `create_account`).
4. After stake unlocks (lockup expiry), any call to `staking_contract::distribute(S1, O)` or `distribute(S2, O)` iterates the distribution pool; when it reaches the operator's commission share and substitutes `recipient = X`, `aptos_account::deposit_coins(X, ...)` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The entire `distribute` transaction reverts, meaning `S1`/`S2`'s own unlocked stake also cannot be withdrawn via this path, for as long as `X` remains the beneficiary and keeps rejecting direct transfers.

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
