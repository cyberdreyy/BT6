### Title
Attacker-controlled cache key `-protected` suffix lets an unprotected-ref job silently produce/reuse the same cache volume name as a protected-ref job, enabling cache poisoning across refs of the same project - (File: executors/docker/volume.go)

### Summary
`createVolumesManager` computes `config.Protected` as `e.Build.IsProtected() || protectedKeyIdx >= 0` [1](#0-0)  where `protectedKeyIdx` is derived purely from the attacker-supplied `spec.Cache.Key` string. Because the resulting `Protected` boolean feeds directly into the cache-volume name via `withProtected` [2](#0-1) , a job running on an unprotected ref can force `Protected=true` purely by appending `-protected` to its own cache key, causing its cache volume's name to collide with the volume a genuinely protected-ref job would use for the same project/destination.

### Finding Description
The `Protected` flag can only move in one direction via the OR: an attacker cannot make an actually-protected ref compute `Protected=false` (the OR can't be negated by cache-key text), so the "downgrade protected → unprotected" framing in the question does not hold. What *is* real is the opposite, more subtle collision: an unprotected-ref job can *elevate* itself to `Protected=true` purely by choosing a cache key ending in `-protected`, with no relation to `e.Build.IsProtected()`.

`createCacheVolume` names/labels the volume as `UniqueName-cache-hash(destination)` plus a `-protected` suffix when `config.Protected` is true, and sets the `protected` label from `config.Protected` [3](#0-2) . `UniqueName` is `e.Build.ProjectRealUniqueName()`, which is scoped per-project, not per-ref/branch, so cache volumes are shared across the protected and unprotected refs of the same project by design (that's the entire point of Runner's project cache). Docker's `VolumeCreate` with an existing name reuses/returns the existing volume rather than recreating it, so whichever job runs first "owns" the volume's contents; any subsequent job that resolves to the same name (same `UniqueName`+destination+protected-suffix) mounts the very same data.

Consequently: a normal contributor with push access to a feature branch/MR (an unprotected ref) can set `cache: key: "foo-protected"` in their own `.gitlab-ci.yml`. Their job then computes `config.Protected=true` even though `e.Build.IsProtected()==false`, and their cache-volume name becomes identical to the one a legitimate protected-ref pipeline (e.g. a pipeline on `main`) would compute for the same cache path. If a shared/group runner executes both pipelines (the default, non-misconfigured scenario matching `DisableCache=false`, `CacheDir=''`), the attacker's job can write arbitrary files into that shared volume before the protected pipeline runs, and the protected pipeline will mount and trust that pre-populated volume.

No existing check in `addCacheVolume`/`createCacheVolume` verifies that a volume claiming `protected=true` was actually created by a protected-ref job, nor is reuse gated on matching the *reason* for protection (ref-protection vs. key-suffix opt-in) — both are conflated into a single boolean that determines the same physical volume name.

### Impact Explanation
This allows cache poisoning across pipeline refs of the same project: an unprivileged contributor to an unprotected branch/MR can plant malicious artifacts (e.g. tampered dependency caches, build tool caches) into the exact Docker volume that a later protected-ref pipeline (run by a maintainer, potentially with elevated secrets/permissions) will mount and trust, without ever needing push access to the protected branch itself. This is scoped to the same project (because `UniqueName` is project-scoped), not literally cross-project as the question speculates, but it does violate the stated invariant that protected-ref cache content must not be writable by an unprotected job.

### Likelihood Explanation
Preconditions match common, non-misconfigured defaults: `DisableCache=false`, `CacheDir=''` (Docker-volume based caching, the default), and a shared runner used across branches/MRs of the same project (typical for project/group runners). The only attacker action required is choosing a `cache:key` value ending in `-protected` in a `.gitlab-ci.yml` the attacker controls (their own branch or MR source branch) and knowing/guessing the cache destination path used by the target's real pipeline (often visible in the project's own `.gitlab-ci.yml`). This is easily repeatable and requires no privilege escalation.

### Recommendation
Do not let attacker-controlled cache-key text alone force the same physical Docker volume name/identity as a ref-protection-derived cache volume. Options:
- Namespace volumes separately by protection *reason* (e.g. include a distinct suffix/label for "key-opted-in protected" vs "ref-protected"), so they never collide.
- Only trust the `-protected` cache-key convention when `e.Build.IsProtected()` is also true, or otherwise validate/label such volumes distinctly and never let them be created/reused by jobs where `e.Build.IsProtected()==false`.
- When reusing an existing volume, verify the `protected` label against `e.Build.IsProtected()` (the true ref-protection status), not the OR'd config value, and refuse reuse (create a fresh, isolated volume) on mismatch.

### Proof of Concept
Go unit test outline for `executors/docker/internal/volumes` (or `executors/docker/volume_test.go`):
1. Build A: `e.Build.IsProtected() == false`, `spec.Cache = [{Key: "foo-protected"}]`. Call `createVolumesManager(e)`; assert `config.Protected == true` and derive volume name via `createCacheVolume`.
2. Build B: `e.Build.IsProtected() == true`, `spec.Cache = [{Key: "foo"}]`, same `ProjectRealUniqueName()` and same destination as Build A. Call `createVolumesManager(e)`; derive its volume name.
3. Assert the two computed volume names are identical (`UniqueName-cache-hash(dest)-protected` in both cases), demonstrating that Build A (unprotected ref) and Build B (protected ref) resolve to the same Docker volume identity despite Build A never actually running on a protected ref — proving the naming/label collision that enables cache poisoning.

Note: I could not directly view the implementation of `e.Build.ProjectRealUniqueName()`/`IsProtected()` in this pass (source not returned by search), so the exact scoping (per-project vs. per-something-else) of `UniqueName` is inferred from its usage and naming convention rather than confirmed line-by-line; this should be verified directly in `common/build.go` before treating the PoC as final.
