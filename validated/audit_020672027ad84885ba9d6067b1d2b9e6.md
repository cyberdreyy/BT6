### Title
Stale `L1BlockInfo.tx_l1_cost` cache can return the wrong transaction's L1 data fee to public callers - (File: `crates/common/evm/src/l1block.rs`)

### Summary
`L1BlockInfo::calculate_tx_l1_cost` memoizes its result in a `tx_l1_cost: Option<U256>` field that is *not* keyed by the input it was computed from: once set, every subsequent call on the same `L1BlockInfo` instance returns the cached value regardless of the `input` bytes passed in, until `clear_tx_l1_cost()` is explicitly called. [1](#0-0) 

This is the same bug class as the reported `viewPrice` issue: a read path (`calculate_tx_l1_cost`/`tx_cost`) can report a value computed for a *different* input/state than the one the caller currently cares about, and consumers of that read (fee checks, receipts, txpool admission) trust it as authoritative without confirming it reflects the current input.

### Finding Description
`L1BlockInfo` carries a single un-keyed cache slot: [2](#0-1) 

`calculate_tx_l1_cost` short-circuits on any pre-existing cached value before even looking at `input`: [3](#0-2) 

`tx_cost`/`tx_cost_with_tx` (used to compute total additional L1 + operator fee cost for a transaction) call through this same cached path: [4](#0-3) 

The design intent, per the field's own doc comment, is that the cache exists only "as a cache between validation and pre execution stages" for the *same* transaction within a single EVM handler pass — i.e. it's meant to avoid recomputing the identical value twice for one tx, not to be reused across different inputs. [5](#0-4) 

However, `L1BlockInfo` (or clones of it) is also read and mutated outside a single per-tx handler invocation:
- Txpool admission reads a shared `BaseL1BlockInfo` (`RwLock<L1BlockInfo>`), clones it, and calls `info.tx_cost(&encoded, ...)` per incoming transaction to compute `additional_fee` used in balance/fee-sufficiency checks during transaction validation. [6](#0-5) 
- The EIP-8130 path explicitly documents needing to "refresh the cached L1 block info for this block" before reuse, showing the authors are aware that a stale `L1BlockInfo` (including its cached `tx_l1_cost`) must be actively invalidated before being reused for a different transaction/context, but this is handled ad hoc per call-site rather than being an invariant enforced by the cache itself. [7](#0-6) 
- The receipt-fields builder pulls `l1_fee` for an arbitrary transaction directly off a mutable `L1BlockInfo` reference via `l1_tx_data_fee` → `calculate_tx_l1_cost`, with no guarantee from the type itself that the cache was cleared for the transaction currently being priced. [8](#0-7) [9](#0-8) 

Because `tx_l1_cost` is populated the moment *any* input is priced and is never automatically invalidated when `input` changes, any code path that clones/reuses an already-primed `L1BlockInfo` for a second, different transaction — without explicitly calling `clear_tx_l1_cost()` first — will silently report the first transaction's L1 fee for the second transaction. This mirrors the `viewPrice`-class bug exactly: a memoized read value is returned to a caller as if it reflects the current input, when it actually reflects a prior state.

### Impact Explanation
If a stale, un-cleared `L1BlockInfo` clone is reused when validating or pricing a *different* transaction (e.g., a reused validator-side `L1BlockInfo` clone processed across multiple transactions in the same `validate_one_with_state`/batch pass, or a receipt-builder call sequence that doesn't clear the cache per-tx), the consequence is a wrong L1 data fee (and, transitively, wrong `additional_fee`/`payer_max_cost`) being used to decide fee-sufficiency in the txpool, or a wrong `l1Fee` reported in a transaction receipt. In the txpool admission path this directly affects an unprivileged transaction sender's ability to get their transaction admitted (a transaction could be wrongly rejected as underfunded, or wrongly accepted as sufficiently funded based on another transaction's cheaper/costlier calldata), which is a concrete node-behavior correctness issue in the txpool admission path explicitly in scope.

### Likelihood Explanation
The bug is only latent — I was not able to fully verify (final iteration reached before file reads completed) whether `L1BlockInfo` clones taken via `self.block_info.l1_block_info.read().clone()` inside `validate_one_with_state`/`validate_one` are ever reused for more than one transaction's fee computation without an intervening `clear_tx_l1_cost()`, or whether the receipt-building loop clears the cache between per-transaction calls to `l1_block_info()`. The `.read().clone()` call shown at [6](#0-5)  creates a fresh clone per validated transaction, which — since the underlying `RwLock<L1BlockInfo>` is only updated block-to-block via `update_l1_block_info` — should start with `tx_l1_cost: None` for each validation call, making this specific path likely safe in practice. Given I could not inspect `crates/common/evm/src/receipt_builder.rs`, `crates/execution/evm/src/receipts.rs`, or the multi-transaction receipt-building loop that calls `ReceiptFieldsBuilder::l1_block_info` (tool access ran out before those reads completed), I cannot confirm whether any call site actually reuses one already-primed `L1BlockInfo` instance across multiple distinct transactions without clearing the cache in between. This uncertainty is a material gap in the analysis.

### Recommendation
Key the cache by the input it was computed for (e.g. store `Option<(B256, U256)>` hashing the enveloped tx, or store the tx hash alongside the cached cost) so `calculate_tx_l1_cost` can detect and recompute for a changed input automatically, rather than relying on every call site to remember to call `clear_tx_l1_cost()` before reuse. Alternatively, audit every call site that clones or reuses an `L1BlockInfo` across more than one transaction and guarantee `clear_tx_l1_cost()` is called before each new transaction's fee is computed, and add a test asserting that computing the L1 cost for transaction A followed immediately by transaction B on the same (uncleared) `L1BlockInfo` instance does not return A's cached cost for B.

### Proof of Concept
Given the code at [1](#0-0) , the following would demonstrate the stale-cache read (analogous to the reported `test_viewPriceNoDampenedPrice_AUDIT` PoC):
```rust
let mut info = L1BlockInfo { l1_base_fee: U256::from(1_000), l1_base_fee_scalar: U256::from(1_000), ..Default::default() };
let cost_tx_a = info.calculate_tx_l1_cost(TX_A_BYTES, spec_id); // primes tx_l1_cost
let cost_tx_b = info.calculate_tx_l1_cost(TX_B_BYTES, spec_id); // BUG: returns cost_tx_a, not TX_B's actual cost, because tx_l1_cost is still Some(..)
assert_eq!(cost_tx_a, cost_tx_b); // demonstrates the stale value is returned regardless of differing input
```
I was unable to confirm (due to running out of tool iterations) a concrete production call site where two different transactions are priced against the *same* `L1BlockInfo` instance without an intervening `clear_tx_l1_cost()`; this PoC demonstrates only the root-cause mechanism in `l1block.rs` itself, not a proven end-to-end exploitation path.

    /// Calculate the gas cost of a transaction based on L1 block data posted on L2, depending on the [`BaseSpecId`] passed.
    pub fn calculate_tx_l1_cost(&mut self, input: &[u8], spec_id: BaseSpecId) -> U256 {
        if let Some(tx_l1_cost) = self.tx_l1_cost {
            return tx_l1_cost;
        }
        // If the input is a deposit transaction or empty, the default value is zero.
        let tx_l1_cost = if input.is_empty() || input.first() == Some(&0x7E) {
            return U256::ZERO;
        } else if spec_id.is_enabled_in(BaseUpgrade::Fjord) {
            self.calculate_tx_l1_cost_fjord(input)
        } else if spec_id.is_enabled_in(BaseUpgrade::Ecotone) {
            self.calculate_tx_l1_cost_ecotone(input, spec_id)
        } else {
            self.calculate_tx_l1_cost_bedrock(input, spec_id)
        };

        self.tx_l1_cost = Some(tx_l1_cost);
        tx_l1_cost
    }

    pub fn l1_block_info<T: Encodable2718 + BaseTransaction>(
        mut self,
        chain_spec: &impl Upgrades,
        tx: &T,
        l1_block_info: &mut base_common_evm::L1BlockInfo,
    ) -> Result<Self, BaseEthApiError> {
        let raw_tx = tx.encoded_2718();
        let timestamp = self.block_timestamp;

        self.l1_fee = Some(
