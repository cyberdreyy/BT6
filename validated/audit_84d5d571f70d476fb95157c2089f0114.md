### Title
Miner-controlled proposal timing can force `first_proposal_burn_block_timing` to misclassify a globally-accepted tenure as "poorly timed," sanctioning an illegitimate reorg of a confirmed block - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_parent_tenure_choice` decides whether a miner is allowed to reorg a prior, already-mined tenure by comparing the gap between when signers approved that tenure's first block and when the next sortition arrived against a fixed "period" config, `first_proposal_burn_block_timing`. Because the "approval time" side of that gap is effectively set by when the miner chooses to broadcast its block proposal, a single miner (the one who signs the tenure whose replacement is being decided, or a colluding miner winning the next sortition) can manipulate that gap below the configured period and get the reorg of an already globally-accepted block sanctioned — the same "short period defeats a timing-based safety check" bug class as the TWAP report.

### Finding Description
`check_parent_tenure_choice` in [1](#0-0)  permits a miner to build off something other than the prior sortition (i.e., reorg previous tenures) only if every reorged tenure produced at most one globally accepted block, and that block was "poorly timed": the gap between the signer group's approval of it and the arrival of the next sortition is below `first_proposal_burn_block_timing`.

The actual comparison is: [2](#0-1) 

`proposal_to_sortition = sortition_state_received_time.saturating_sub(approved_at)`, and if `Duration::from_secs(proposal_to_sortition) < first_proposal_burn_block_timing`, the tenure is pushed into `superseded_tenures` and the reorg is permitted — even though the tenure had a globally-accepted (confirmed) block. `check_parent_tenure_choice` is invoked both from the v1/v2 proposal-time check (`check_proposal` / `validate_tenure_change_payload`) and is what ultimately lets a signer vote to sign a tenure-change block whose parent reorgs a previously canonical tenure: [3](#0-2)  and [4](#0-3) .

The default period is small by design — 30s in the sample dev config and 60s in the mainnet sample — and is explicitly documented as attacker-relevant: [5](#0-4) 
"Setting this too LOW allows dangerous reorgs of established tenures."

The `approved_at` timestamp used in the comparison is `local_block_info.approved_time`, recorded when the signer set pre-committed/approved the tenure's first block — a time that tracks closely with when the miner chose to *broadcast* the proposal, not with how long the tenure was actually live. A miner controls exactly when it proposes its tenure-start block. By deliberately delaying that proposal until just before the anticipated next sortition, the miner can force `sortition_state_received_time - approved_at` to be arbitrarily small — well under the configured `first_proposal_burn_block_timing` — regardless of how long the tenure otherwise ran or how widely its block was confirmed. This satisfies the "poorly timed" branch and gets the tenure marked `superseded_tenures`, unblocking a reorg of a block that had already reached global acceptance.

This is structurally identical to the TWAP report's bug class: a legitimate safety mechanism is parameterized by a time window (`_period` / `first_proposal_burn_block_timing`) that is meant to distinguish "genuinely too-short-to-matter" activity from meaningful activity, but the actor who benefits from crossing the threshold controls the very timestamp that is compared against it, so the window can be trivially manipulated to always read "short."

### Impact Explanation
If a miner can force `check_parent_tenure_choice` to sanction a reorg of a tenure that had already produced a globally-accepted (network-confirmed) block, downstream logic (`record_superseded_tenure` / `mark_tenure_superseded`) causes the signer's own prior signature over that block to stop counting as a conflict: [6](#0-5) . The signer will then go on to sign a *replacement* tenure-change block whose parent excludes a block the network had already treated as canonical — i.e., the signer signs a conflicting/non-canonical block relative to what was already globally accepted. This is a Critical-class outcome under the stated impact categories ("a signer signing an invalid, non-canonical, or conflicting block").

### Likelihood Explanation
This requires only the block's own miner (or the miner who wins the very next sortition and proposes the reorging tenure-change block) — a single, one-slot actor — to time its own proposal broadcast late in its tenure. No majority of signers, no other signer's key, and no StackerDB/auth bypass is needed; the manipulation lives entirely in when a miner chooses to publish a block it already controls. The mechanism is explicitly documented as sensitive to the configured period being "too low," confirming the timing-window is the load-bearing (and manipulable) safety boundary.

### Recommendation
Do not derive the "poorly timed" determination from a timestamp effectively controlled by the party who benefits from the reorg. Instead, anchor the measurement to something the reorging miner cannot manipulate — e.g., the tenure's actual start time (burn-block-derived), or require the comparison to use the *earliest possible* proposal time bound (sortition processing time) rather than the signer's locally recorded `approved_time`, which tracks the miner's chosen broadcast time. Alternatively, require additional corroboration (e.g., minimum observed miner activity duration from the node's own chainstate) before treating a tenure as "poorly timed" and superseding an already globally-accepted block.

### Proof of Concept
1. Miner M wins sortition for tenure A and mines block A1, which the signer set globally accepts (`get_globally_accepted_block_count_in_tenure` == 1).
2. M deliberately delays broadcasting A1's proposal until immediately before the next expected Bitcoin block/sortition, so that `local_block_info.approved_time` is very close to `sortition_state_received_time` for the next sortition (tenure B).
3. Tenure B's miner (M or a colluding miner) proposes a tenure-change block whose parent bypasses tenure A (`prior_sortition == tenure A`, but `parent_tenure_id` points elsewhere).
4. Each signer's `check_parent_tenure_choice` computes `proposal_to_sortition = sortition_state_received_time - approved_at`, finds it `< first_proposal_burn_block_timing` (30–60s per the sample configs), and marks tenure A as superseded: [7](#0-6) .
5. Signers proceed to sign tenure B's tenure-change block even though it reorgs away A1, a block that had already reached global acceptance — verifiable against the existing unit tests exercising this exact boundary condition, `check_parent_tenure_choice_reorg_timing_ok` / `check_proposal_reorg_timing_ok`, which show the "ok" (permitted-reorg) branch triggers whenever the measured gap is below the configured threshold: [8](#0-7) , [9](#0-8) .

# Reorg protection window. Measures the time between when the first block
# of a tenure was signed and when the next burn block (sortition) arrived.
#
# If a new miner tries to reorg a tenure that already produced blocks:
#   - If (burn_block_received - first_block_signed) < this value:
#     Reorg is ALLOWED (the tenure was "poorly timed" and the incoming
#     miner did not have sufficient time to RBF an outdated commit)
#   - If (burn_block_received - first_block_signed) >= this value:
#     Reorg is DENIED (the tenure was established long enough for the
#     incoming miner to RBF any outdated commit)
#
# WARNING: Setting this too LOW allows dangerous reorgs of established
# tenures. Setting it too HIGH blocks legitimate miner handoffs when
# the previous tenure's first block arrived shortly before the sortition.
#
# Default: 60
# Units: seconds
# first_proposal_burn_block_timing_secs = 60
