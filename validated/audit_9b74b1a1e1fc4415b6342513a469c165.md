### Title
External-initiator credentials can trigger runs on any job (no binding to registered bridge/job) - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates int-ID job runs on `auth.GetAuthenticatedUser(c)` returning a user, intending (per the code comment) to disallow external initiators (EIs) from running jobs by numeric ID. However, `auth.AuthenticateExternalInitiator` explicitly stores a synthetic `*clsessions.User{Role: UserRoleRun}` under the same `SessionUserKey` context key used by real session/token authentication, so `isUser` is `true` for EI-authenticated requests too. Combined with the fact that neither `Create` nor `RunJobV2` verify any relationship between the authenticated EI and the target job ID, any valid EI credential can trigger a run on an arbitrary job.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered with three chained auth methods, tried in order: `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, `auth.AuthenticateBySession`, wrapped in `auth.RequiresRunRole`: [1](#0-0) 

`AuthenticateExternalInitiator` looks up the EI by access key/secret, and on success sets **both** `SessionExternalInitiatorKey` and `SessionUserKey` to a fabricated `User` object with `Role: UserRoleRun`: [2](#0-1) 

`RequiresRunRole` only checks `user.Role != UserRoleView`, which the synthetic user passes: [3](#0-2) 

In `PipelineRunsController.Create`, the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed," and gates on `isUser`: [4](#0-3) 

But `auth.GetAuthenticatedUser` merely checks for presence/type of the `SessionUserKey` context value — it cannot distinguish a genuine authenticated user from the placeholder object set by the EI middleware: [5](#0-4) 

Because the EI middleware sets `SessionUserKey` (not just `SessionExternalInitiatorKey`), `isUser` evaluates `true` for EI-authenticated requests, defeating the intended "EIs not allowed" restriction. The handler then calls `prc.App.RunJobV2(ctx, jobID, nil)` using only the `jobID` parsed from the URL path — there is no lookup or check anywhere in this path that ties the authenticated `ExternalInitiator` (obtainable via `auth.GetAuthenticatedExternalInitiator(c)`) to the job/bridge being run. Any job ID supplied in the URL, regardless of which bridge/job the EI was registered against, will be executed.

### Impact Explanation
This breaks the intended REQUEST_BINDING between an EI's registered bridge/job and the jobs it is authorized to trigger. An EI credential — a relatively low-privilege, narrowly-scoped credential meant only to notify its own registered job of external events — can instead trigger pipeline runs on **any** job in the node by numeric ID, including jobs it has no legitimate relationship to. Depending on what those jobs do (e.g., initiating on-chain transactions, VRF fulfillment, OCR-related pipeline tasks), this can cause unauthorized job execution, resource exhaustion via repeated forced runs, or unintended state/side effects (fund movement) on jobs unrelated to that EI. This matches the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs valid credentials for **any** registered external initiator (a low-privilege credential type explicitly not meant to control arbitrary jobs) and knowledge/guessability of a target job's numeric ID (job IDs are sequential integers, obtainable via `/v2/jobs` listing endpoints reachable at edit/view roles, or brute-forced since they are small integers). No admin, operator, or host access is required. This is fully reproducible via a simple HTTP handler test.

### Recommendation
In `AuthenticateExternalInitiator`, avoid conflating EI identity with a generic user object under `SessionUserKey`; use a distinct signal (e.g., rely solely on `SessionExternalInitiatorKey`) so downstream handlers can differentiate EI-originated requests from real user requests. In `PipelineRunsController.Create`, explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject EI-authenticated requests for the `/jobs/:ID/runs` int-ID path (matching the existing code comment's intent), or alternatively verify that the run request's job ID matches the specific job the EI is registered to (`ExternalInitiator` → `Job`/bridge association) before invoking `RunJobV2`.

### Proof of Concept
Handler-level integration test plan (Go, using `cltest` test app similar to existing tests in `core/web/pipeline_runs_controller_test.go`):
1. Start a test `chainlink.Application` (`cltest.NewApplicationEVMDisabled(t)`).
2. Create two non-webhook jobs A and B via job ORM/spec insertion (e.g., cron or direct-request specs with int IDs).
3. Register an `ExternalInitiator` bound conceptually to job A's bridge (via `ExternalInitiatorsController.Create` or direct bridges ORM insertion), capturing its `AccessKey`/`Secret`.
4. Build an HTTP client that sets `static.ExternalInitiatorAccessKeyHeader` / `static.ExternalInitiatorSecretHeader` to the EI's credentials (no session cookie, no API token).
5. POST to `/v2/jobs/{B}/runs` (job B's int ID, unrelated to the registered EI) using the EI-authenticated client.
6. Assert the response status is `200 OK` and a `pipelineRun` resource is returned (via `presenters.NewPipelineRunResource`), proving job B's run was created despite the EI having no association to job B — i.e., `prc.App.RunJobV2` was successfully invoked for an out-of-scope job.
7. Cross-check: assert `auth.GetAuthenticatedExternalInitiator(c)` in the request context resolves to the EI registered for job A while the created run belongs to job B, confirming REQUEST_BINDING violation.

```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
```

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
