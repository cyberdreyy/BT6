### Title
Stale Confirmations From Deleted Multisig Members Allow Execution Below True Threshold - (File: multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
Both the original `multisig` contract and the newer `multisig2` contract allow a `DeleteKey`/`DeleteMember` action to purge only the *requests originally added* by the removed key/member, but never scrub that key's/member's *confirmations recorded on other still-pending requests*. As a result, a vote cast by a key that is later revoked continues to count toward the `num_confirmations` threshold, letting a request execute with fewer live, currently-authorized signers than the configured threshold.

### Finding Description
In `multisig/src/lib.rs`, `confirm()` adds `env::signer_account_pk()` to the `confirmations` `HashSet` for a request: [1](#0-0) 

When a `DeleteKey` action is executed, the cleanup logic only removes *requests whose original adder (`signer_pk`) equals the deleted key*, and clears `num_requests_pk` for that key — it does **not** scan `confirmations` on other requests to remove any confirmation entries that reference the deleted key: [2](#0-1) 

`assert_valid_request()`, called from `confirm()`, only checks that predecessor equals the current account and that the request/confirmation entries exist — it never re-validates that keys already present in the stored `confirmations` set are still active members: [3](#0-2) 

The equality this breaks is: **confirmations counted (`confirmations.len()`) should equal confirmations from currently live members**. Once a member's key is deleted, any earlier confirmation it gave on a request that it did *not itself add* stays cached in that request's `confirmations` set and is still summed against `num_confirmations` in `confirm()`.

The same pattern is reproduced in the newer `multisig2` contract: `delete_member()` filters requests by `r.member == member` (i.e., requests *added by* that member) and removes `num_requests_pk`, but does not purge that member's confirmations recorded on other requests: [4](#0-3) 

and `confirm()`/`assert_valid_request()` there likewise only check whether the *current* caller is a live member, not whether previously stored confirmations are still valid: [5](#0-4) [6](#0-5) 

### Impact Explanation
This falls under the Critical category "a multisig request executed below threshold." A request that legitimately needs `K` live confirmations can execute with fewer than `K` currently-authorized signers, because a stale confirmation from a since-removed key/member remains counted. Since `MultiSigRequestAction` includes `Transfer`, `DeployContract`, `AddKey`/`AddMember`, and arbitrary `FunctionCall`, an attacker or a departing/compromised member whose key is later revoked can still contribute a "ghost" vote that helps push a malicious request (e.g., transferring NEAR, deploying a malicious contract, or adding an attacker's own key) past the confirmation threshold with fewer genuinely live approvers than the multisig's security model promises.

### Likelihood Explanation
This does not require any special privilege beyond normal multisig operation: (1) a soon-to-be-removed member confirms a request (either benignly or maliciously, e.g., colluding before being removed), (2) that member's key/account is later deleted via a separate, otherwise legitimate `DeleteKey`/`DeleteMember` request, and (3) the original pending request is later brought to threshold by remaining members without realizing one "confirmation" belongs to a party no longer trusted. Because key/member rotation (revoking compromised or departing signers) is an expected, routine multisig operation, and the vulnerable code path is exercised by ordinary usage rather than an edge case, likelihood is meaningful for any long-lived multisig that rotates membership while requests are outstanding.

### Recommendation
When executing `DeleteKey` (multisig) / `DeleteMember` (multisig2), iterate over **all** pending requests' `confirmations` sets (not just requests originally added by that key/member) and remove the deleted key's/member's entry from each. Alternatively, validate at `confirm()`/threshold-check time that every public key/member present in a request's `confirmations` set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Multisig configured with `num_confirmations = 3` and members `K1, K2, K3, K4`.
2. `K1` calls `add_request` for a malicious `Transfer`/`FunctionCall` request `R` (1 confirmation from `K1` via `add_request_and_confirm`).
3. `K2` calls `confirm(R)` → confirmations = `{K1, K2}` (2/3, not yet executed). [7](#0-6) 
4. Separately, the group legitimately revokes `K2` (e.g., they left the org / key rotation) via a `DeleteKey { public_key: K2 }` request that reaches threshold and executes. Cleanup only removes requests where `r.signer_pk == K2` (i.e., requests *K2 added*) — request `R` (added by `K1`) is untouched, and `R`'s confirmations set still contains `K2`. [2](#0-1) 
5. `K3` (a legitimate, currently-live member) later calls `confirm(R)`. `confirmations.len() + 1 = 3 >= num_confirmations (3)`, so `R` executes — even though only `K1` and `K3` are still live members; `K2`'s revoked confirmation supplied the missing vote. [8](#0-7) 

This demonstrates a request executing with confirmations from fewer than `num_confirmations` currently-authorized members, breaking the multisig's authorization/threshold guarantee.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();

            // remove confirmations for this request

            self.requests.remove(&request_id);

            MultisigMember::Account { account_id: _ } => promise,
        }
