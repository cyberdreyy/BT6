### Title
Stale per-epoch instant-withdraw basis corrupts default-recovery accounting — claimed receipts double-counted in `instantWithdrawClaimsByEpoch` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests[_user]` and burns the receipt tokens, but never clears the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]`. If the borrower later defaults in the same epoch, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` treat already-claimed-and-paid instant receipts as still outstanding, inflating both the recovery claim basis and the phantom "prefunded" reserve. The result is a diluted `defaultRecoveryPrice`, an insolvent `defaultRecoveryReserve`, and reverts for the last claimants — the on-chain analog of an out-of-bounds write corrupting adjacent accounting structures (CVE-2016-8332 bug class).

### Finding Description
In `requestInstantWithdraw`, the vault records the receipt three ways: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 366–374). In the normal (non-default) claim path, only the aggregate is cleared: [1](#0-0) 

`instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are left stale forever. Those stale entries are only ever cleaned inside `_claimDefaultedInstantWithdrawRequest`, which runs exclusively when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` (lines 382–386, 842–856).

The corruption lands at `finalizeDefaultRecovery`:
- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the basis whenever `pendingInstantWithdraws != 0` (lines 644–649). Already-claimed receipts from the default epoch inflate `totalBasis`.
- `_defaultPrefundedInstantReserve()` adds `instantBasis - pendingInstant` as "already-held" reserve (lines 716–723). Claimed funds were transferred out, so this overstates real backing.

`recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is then computed against a phantom-bloated basis with phantom-bloated reserve (lines 686–692). Finally, the previously-claimed user retains `instantWithdrawsRequestsByEpoch[_user][defaultEpoch] != 0`, so their next claim enters `_claimDefaultedInstantWithdrawRequest` and hits `instantWithdrawsRequests[_user] -= claimBasis` on a zeroed aggregate — a revert that also blocks their legitimate funded claims in the same call path.

### Impact Explanation
- **Diluted recovery for all defaulted-epoch claimants**: `totalBasis` includes underlyings already paid out, so every real claimant receives `defaultRecoveryPrice`-scaled payouts computed over too-large a denominator.
- **Insolvent reserve / permanent freezing**: `defaultRecoveryReserve` is credited with "prefunded" underlying that no longer sits in the contract. Early claimants may overdraw relative to true backing; once `defaultRecoveryReserve` or the token balance is exhausted, remaining `_transferDefaultRecovery` calls underflow/revert (lines 912–917), permanently freezing honest users' recovery.
- **Per-user claim DoS**: the previously-claimed user cannot claim anything post-default because `_claimDefaultedInstantWithdrawRequest` reverts on the stale basis.

Broken invariant: one receipt one payout, and recovery reserve must equal real claim backing. Attacker is an unprivileged instant-withdraw requester; the sequence only requires an honest-manager default finalization afterward.

### Likelihood Explanation
Requires: (a) instant-withdraw mode active (APR drop exceeding `instantWithdrawAprDelta`, non-programmable deployment), (b) a user requests and successfully claims an instant withdrawal in epoch N, (c) another user's instant receipt remains unfunded (`pendingInstantWithdraws != 0`), and (d) the borrower defaults in epoch N before `stopEpoch` bumps the epoch counter. This is a plausible single-epoch sequence whenever the borrower partially funds instant withdrawals then defaults. No privileged misbehavior is needed — the stale-state write is caused entirely by the normal claim path.

### Recommendation
In `claimInstantWithdrawRequest` (and equivalently anywhere instant receipts are cleared outside the default path), also zero `instantWithdrawsRequestsByEpoch[_user][*]` and decrement `instantWithdrawClaimsByEpoch[*]` for the epochs being claimed — mirroring `_clearWithdrawClaimForEpoch` used for normal receipts. Alternatively, track a per-epoch "claimed" flag. Add an invariant test: after a funded instant claim, `instantWithdrawClaimsByEpoch` must equal the sum of unclaimed per-epoch bases.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
// epoch N running, instant withdraw enabled via APR drop
// 1) userA requests instant withdraw -> instantWithdrawsRequestsByEpoch[A][N] = amtA
//    instantWithdrawClaimsByEpoch[N] = amtA; pendingInstantWithdraws += amtA
// 2) userB requests instant withdraw -> claimsByEpoch[N] = amtA + amtB; pending += amtB
// 3) CDO collects only amtA: collectInstantWithdrawFunds(amtA) -> pending = amtB
// 4) userA claims (non-default path): aggregate cleared, BUT
//    instantWithdrawsRequestsByEpoch[A][N] and claimsByEpoch[N] stay = amtA + amtB
// 5) borrower defaults in epoch N; manager calls finalizeDefaultRecovery
//    -> defaultPendingClaimBasis includes stale amtA; _defaultPrefundedInstantReserve
//       adds (amtA + amtB) - amtB = amtA phantom reserve
//    -> defaultRecoveryPrice computed over inflated basis/reserve
// 6) userA calls claimInstantWithdrawRequest again ->
//    _claimDefaultedInstantWithdrawRequest: instantWithdrawsRequests[A](0) -= amtA  => revert
// 7) userB's defaulted claim pays at diluted price; reserve insolvent by ~amtA,
//    last claimant's _transferDefaultRecovery reverts -> recovery frozen
```

The stale-write site is lines 387–392 of `contracts/strategies/idle/IdleCreditVault.sol`; the corrupted readers are lines 644–649 and 716–723.

Caveat: exact entry points (whether instant requests route through `IdleCDOEpochVariant.requestWithdraw` APR-drop branch or a dedicated entry) and whether `collectInstantWithdrawFunds` can partially fund same-epoch receipts before default should be confirmed against the CDO stop/start-epoch wiring in a runnable PoC; the missing per-epoch cleanup in the claim path is directly visible in the code above.
