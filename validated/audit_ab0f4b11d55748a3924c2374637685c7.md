This confirms the finding: `ProposerPreferences.fee_recipient` (set by the proposer) and `ExecutionPayloadBid.fee_recipient` (set by the builder) are two independently-authored config fields, exactly analogous to the ERC721SeaDrop `owner`/`administrator` pair each able to write fields that the other relies on. The consistency check between them exists *only* in the soft, best-effort gossip layer (`validate_execution_payload_bid_gossip` in [1](#0-0) ), while the canonical state-transition function `process_execution_payload_bid` in [2](#0-1)  never checks `bid.fee_recipient` against any on-chain-committed proposer preference before recording the `BuilderPendingPayment`/paying out the builder fee.

### Title
Builder payment can be misdirected away from the proposer's committed fee recipient - (File: `specs/gloas/beacon-chain.md`)

### Summary
`process_execution_payload_bid` records a `BuilderPendingPayment` (and ultimately a Gwei transfer to `bid.fee_recipient`) purely from the builder-supplied `ExecutionPayloadBid.fee_recipient` field, without any state-level cross-check against the proposer's own `ProposerPreferences.fee_recipient`. The only place that ties the two together is a soft "IGNORE"-level gossip check, which is neither part of consensus validity nor binding on state transition.

### Finding Description
The proposer signals where it wants its builder-payment sent via `SignedProposerPreferences.fee_recipient`, constructed in [3](#0-2) . Builders are instructed (as a MUST, but unenforced on-chain) to copy this into `bid.fee_recipient` when constructing their bid, per [4](#0-3) .

The only code that compares `bid.fee_recipient` to `proposer_preferences.fee_recipient` is in the gossip validator, and it is explicitly a soft check: [5](#0-4) 
This raises `GossipIgnore`, not `GossipReject`, and even that only fires when matching preferences were previously *seen* on gossip — a condition an attacker can simply avoid (e.g. never observing/propagating the preferences, or a validator that never broadcasts them).

The canonical state-transition function that actually commits the bid and schedules payment, `process_execution_payload_bid`, contains no such check at all: [2](#0-1) 
It validates builder activity, balance sufficiency, signature, slot/parent/randao consistency — but never reads or validates `state`-stored proposer preferences against `bid.fee_recipient`. The `BuilderPendingWithdrawal.fee_recipient` recorded at line 2129 is taken verbatim from the builder's bid.

This exactly mirrors the reported bug class: two independent parties (proposer vs. builder) each control a config field that determines where a payment goes, and one party's field silently overrides/ignores the other's intent because the authoritative code path enforces no equality between them — only an easily-bypassed off-chain/soft check exists.

### Impact Explanation
A builder can construct and get included on-chain (with proposer cooperation or even proposer negligence/race conditions around preference broadcast) a bid whose `fee_recipient` differs from what the proposer declared it wants. Since `process_execution_payload_bid` is consensus-valid regardless of the mismatch, the builder's payment ends up at an address the proposer never authorized for that slot — a builder payment "misdirected" per the High-impact category (a builder payment or withdrawal misdirected). This can also be leveraged self-interestedly by the proposer itself: nothing in state transition stops a proposer from simply not broadcasting `ProposerPreferences` and instead colluding with a builder off-protocol to divert payment to an address that bypasses the intended gossip-level safety check entirely, since gossip-level protection is opt-in and reliant on `seen.proposer_preferences` being populated.

### Likelihood Explanation
Moderate-to-high: the gossip check is `IGNORE`-severity and keyed on p2p timing (`seen.proposer_preferences`), so it is trivially bypassed by not broadcasting preferences, by network partition/timing, or by out-of-band ("other means") bid delivery which `validator.md` explicitly permits ("The block proposer MAY obtain these signed messages by other off-protocol means"), completely sidestepping the gossip validator.

### Recommendation
Enforce the `bid.fee_recipient == proposer_preferences.fee_recipient` (and similarly the gas-limit compatibility) invariant inside `process_execution_payload_bid` itself (or an equivalent state-transition-level check), using an on-chain-committed proposer preference (e.g. requiring the proposer to include/attest its `SignedProposerPreferences` as part of the block, or storing the preference in state keyed by dependent root/slot) rather than relying solely on best-effort gossip propagation.

### Proof of Concept
1. Proposer P is scheduled to propose slot `S` and broadcasts `SignedProposerPreferences{proposal_slot=S, fee_recipient=A}`.
2. A colluding or malicious builder B never receives/observes that gossip message (or P simply relies on "other off-protocol means" per `validator.md`), and instead constructs `ExecutionPayloadBid{slot=S, fee_recipient=C, value=v}` where `C != A`.
3. P includes B's bid in its block; `process_execution_payload_bid` runs all its checks (lines 2094-2122) — none reference `fee_recipient` consistency — and succeeds, storing `BuilderPendingWithdrawal(fee_recipient=C, amount=v, builder_index=B)`.
4. At withdrawal time, `v` Gwei is paid to address `C`, not `A`, even though `A` was P's declared, signed preference — with no consensus rule ever having enforced the match.

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid

    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash

    # Record the pending payment if there is some payment

def get_signed_proposer_preferences(
    store: Store,
    state: BeaconState,
    head_root: Root,
    proposal_slot: Slot,
    validator_index: ValidatorIndex,
    fee_recipient: ExecutionAddress,
    target_gas_limit: Uint64,
    privkey: int,
) -> SignedProposerPreferences:
    proposal_epoch = compute_epoch_at_slot(proposal_slot)
    dependent_root = get_shuffling_dependent_root(store, head_root, proposal_epoch)
    preferences = ProposerPreferences(
        dependent_root=dependent_root,
        proposal_slot=proposal_slot,
        validator_index=validator_index,
        fee_recipient=fee_recipient,
        target_gas_limit=target_gas_limit,
    )
    domain = get_domain(state, DOMAIN_PROPOSER_PREFERENCES, proposal_epoch)
    signing_root = compute_signing_root(preferences, domain)
    signature = bls.Sign(privkey, signing_root)
    return SignedProposerPreferences(message=preferences, signature=signature)
