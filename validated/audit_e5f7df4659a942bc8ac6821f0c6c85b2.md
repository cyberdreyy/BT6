### Title
Loss-adjusted withdrawal haircut stored under the post-increment epoch is never applied — receipts claim at par and drain funded underlyings — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug reads stale buffer bytes as a record length and advances `fifo->out` past real data, so the bounds check (`len + recsize > kfifo_unused`) is bypassed and an OOB write follows. The analog in `IdleCreditVault` is the epoch marker used to look up a pending-receipt haircut: `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` (line 421), but `epochNumber` is incremented inside `deposit()` during `stopEpoch` (lines 607–611, "deposit done on stopEpoch (before setting the var to false)"). Receipts were tagged under the *pre-increment* epoch via `lastWithdrawRequest`/`withdrawsRequestsByEpoch` (lines 282, 293). When `collectWithdrawFunds` runs after the incrementing deposit in `stopEpoch`, the haircut lands on the new epoch key — a stale/wrong slot — so `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] == 0` (lines 790–792), treats it as "no loss", and falls through to `_claimFundedWithdrawRequest`, which pays the full unhaircutted basis because `epochNumber > lastWithdrawRequest` already passes the gate (line 326). ### Finding Description
`stopEpochWithDuration(_lossAmount)` flow: CDO computes `pendingToFund < pendingWithdraws` via `previewLossAdjustedWithdrawFunds` (lines 440–460), then calls `collectWithdrawFunds(pendingToFund)`. Inside, `lossRecoveryPrice = _amount * 1e18 / pendingBasis` is stored under the current `epochNumber`. But `deposit()` increments `epochNumber` when `isEpochRunning()` is still true during `stopEpoch` (line 610). If the deposit that moves borrower repayment into the strategy executes before `collectWithdrawFunds` — the natural order, since funding precedes haircut bookkeeping — the stored key is `requestEpoch + 1` while every `withdrawsRequestsByEpoch[user][requestEpoch]` and `lastWithdrawRequest[user] == requestEpoch`.

Consequences:
- `_claimLossAdjustedWithdrawRequest` finds `lossRecoveryPriceByEpoch[requestEpoch] == 0` and returns 0.
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[user]` at par (lines 338–349).
- The `requestWithdraw` stale-marker guard (lines 262–270) also reads the zero slot, so users are not even forced to claim the haircutted receipt first — matching the kernel's skipped `!kfifo_is_empty()` check that lets a stale read bypass the bound.
- The same off-by-one hits `apr0RateByEpoch[epochNumber]` written in `prepareStopEpochWithApr0` (line 537) vs `apr0Users[user].principalEpoch` set at request time (line 572): `_settleApr0` reads `apr0RateByEpoch[reqEpoch] == 0` (line 558), so APR0 users' interest is silently zeroed — permanent loss of unclaimed yield.

### Impact Explanation
The loss allocated to pending receipts (`pendingLoss = _lossAmount * pendingBasis / totalBasis`) is never crystallized against them. `pendingWithdraws` was zeroed in `collectWithdrawFunds`, so the receipt claimants are overpaid `pendingLoss` underlyings drawn from strategy-held funds that back active AA/BB LPs (and, post-default, the recovery reserve). Broken invariant: loss waterfall / fair burn — "one receipt one payout" is violated because the receipt pays 1:1 despite the funded shortfall. Quantified loss: `pendingLoss` in underlying per loss epoch, capped by `pendingBasis`; direct theft/insolvency, not just temporary freezing. For APR0 mode, users permanently lose `apr0RateByEpoch`-denominated interest.

### Likelihood Explanation
Trigger requires only a `stopEpoch` ending with a realized loss while `pendingWithdraws != 0` — a routine partial-repayment/shortfall event, not attacker contrivance. Any tranche holder with a pending receipt in that epoch then calls `claimWithdrawRequest` and is paid at par. No privileged role misbehavior needed; the honest manager/borrower sequence suffices. Caveat: the bug exists only if `collectWithdrawFunds` executes after the epoch-incrementing `deposit()` inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration`; that ordering lives in `IdleCDOEpochVariant.sol` and could not be fully confirmed from indexed snippets. If collect precedes the deposit, the keys align and this path is sound — the PoC below is decisive either way.

### Recommendation
Key the haircut by the request epoch, not the mutable counter: snapshot `uint256 reqEpoch = epochNumber` before the increment (or have the CDO pass the settled epoch to `collectWithdrawFunds`, and to `prepareStopEpochWithApr0` for `apr0RateByEpoch`). Alternatively, record `lossRecoveryPriceByEpoch` for *all* epochs that currently hold pending receipts, or move the `epochNumber += 1` increment out of `deposit()` to the end of `stopEpoch` so all stop-epoch bookkeeping shares one epoch id.

### Proof of Concept
Foundry fork test (scaffold as in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "./IdleCreditVault.t.sol"; // reuse fixtures: _depositWithUser, _startEpochAndCheckPrices

contract LossEpochKeyMismatchPoC is IdleCreditVaultTest {
    function testLossHaircutBypassedByEpochIncrement() external {
        IdleCreditVault vault = IdleCreditVault(address(strategy));

        // user deposits and requests withdraw during buffer of epoch N
        address user = makeAddr('victimReceipt');
        _depositWithUser(user, 100_000 * ONE_SCALE, true);
        uint256 reqEpoch = vault.epochNumber();
        vm.prank(user);
        uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche));
        assertEq(vault.lastWithdrawRequest(user), reqEpoch);
        assertEq(vault.withdrawsRequestsByEpoch(user, reqEpoch), basis);

        // start epoch, then stop with a realized loss -> collectWithdrawFunds(lossAdjusted)
        _startEpochAndCheckPrices(0);
        uint256 loss = basis / 10; // 10% loss for illustration
        deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
        vm.warp(cdoEpoch.epochEndDate() + 1);
        vm.prank(manager);
        cdoEpoch.stopEpochWithDuration(initialProvidedApr, loss); // or stopEpoch loss path

        // BUG: haircut keyed under reqEpoch+1 (post-increment), receipt epoch reads 0
        assertEq(vault.lossRecoveryPriceByEpoch(reqEpoch), 0, 'haircut stored under wrong epoch');
        assertGt(vault.lossRecoveryPriceByEpoch(reqEpoch + 1), 0, 'haircut landed post-increment');

        // user claims at PAR instead of 90% -> overpaid from strategy underlyings
        uint256 pre = underlying.balanceOf(user);
        vm.prank(user);
        cdoEpoch.claimWithdrawRequest();
        assertEq(underlying.balanceOf(user) - pre, basis, 'paid at par, haircut never applied');
    }
}
```

Expected on a buggy ordering: `lossRecoveryPriceByEpoch[reqEpoch] == 0`, receipt pays `basis` (100%) instead of `basis * lossRecoveryPrice / 1e18` (90%); the 10% difference is extracted from funds owed to remaining LPs. If the assertion `lossRecoveryPriceByEpoch[reqEpoch] > 0` holds instead, ordering is safe and this finding should be downgraded.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
