### Title
LDAP upstream sync aborts entirely on a single group-query error, allowing revoked Admin sessions/tokens to persist un-purged - ([File: core/sessions/ldapauth/sync.go])

### Summary
`LDAPServerStateSyncer.Work` fetches Admin, Edit, Run, and View group memberships sequentially from the upstream LDAP server, and `return`s immediately if any single `ldapGroupMembersListToUser` call errors, before ever reaching the transaction that purges stale `ldap_sessions`/`ldap_user_api_tokens` rows or downgrades roles. Because `AuthorizedUserWithSession` and `FindUserByAPIToken` only check locally cached role/email and a time-based expiry (never re-querying LDAP per request), a transient/intermittent error on any one group query causes the entire revocation-sync cycle for **all** roles (including the already-successfully-fetched Admin/Edit/Run/View lists) to be silently dropped, allowing a revoked Admin's session cookie or API token to remain fully privileged until a cycle completes with zero errors.

### Finding Description
`Work()` in `core/sessions/ldapauth/sync.go` performs, in order: query Admin group, query Edit group, query Run group, query View/Read group, dedupe into `upstreamUserStateMap`, then opens a DB transaction (`sqlutil.TransactDataSource`) that (a) deletes `ldap_sessions`/`ldap_user_api_tokens` rows whose email is not in `upstreamUserStateMap`, and (b) updates roles of remaining rows to match the fetched upstream state.

Each of the four group lookups (lines 134-156) is guarded by:
```go
if err != nil {
    l.lggr.Error("Error in ldapGroupMembersListToUser: ", err)
    return
}
```
This unconditional `return` on any single group query failure means the entire purge/demotion transaction (lines 189-283) is skipped for that sync cycle — not just for the failing group, but for all previously-fetched groups too. There is no partial-purge fallback, no retry with cached prior state, and no separate per-group failure handling.

Session/token validation never re-checks LDAP live: `AuthorizedUserWithSession` (`core/sessions/ldapauth/ldap.go:345-373`) and `FindUserByAPIToken` (`core/sessions/ldapauth/ldap.go:205-236`) trust the DB-cached `user_role`/`user_email` and only enforce time-based expiry — they do not consult the upstream server. Thus the only mechanism that can react to an upstream group-membership removal is this `Work()` sync. If the upstream LDAP server has any transient hiccup on a single group search (timeout, network blip, throttling) during a sync cycle, the entire revocation check is skipped that cycle, and if the flakiness recurs across cycles, the stale Admin session/token is never purged or demoted.

### Impact Explanation
This maps to the "authorization bypass / broken access control" bounty class: a session or API token whose privilege should have been revoked continues to grant full Admin capability (including key export, job management, and other admin actions) for as long as the sync keeps failing on any single group query, which is fully attacker-uncontrollable but plausible under real-world LDAP server conditions (rate limiting, transient timeouts, partial outages). The blast radius is bounded to a specific previously-legitimate (now revoked) credential holder, not an arbitrary unprivileged attacker, but it directly violates the "revoked identity must lose privilege promptly" invariant.

### Likelihood Explanation
Requires: (1) an LDAP-backed deployment (`LDAPAuth` provider) with `UpstreamSyncInterval`/`UpstreamSyncRateLimit` configured for periodic sync, (2) a previously valid Admin session or API token that has since been revoked upstream, and (3) the upstream LDAP server intermittently erroring on at least one group query per sync attempt. This is a fail-closed-for-the-wrong-thing / fail-open-for-privilege bug — a purely operational/environmental condition (LDAP flakiness) can extend a privileged credential's life indefinitely if failures happen to coincide with every sync cycle, though a single isolated failure only delays revocation until the next successful cycle. It does not require attacker action beyond continuing to use an already-issued credential; it is entirely dependent on upstream reliability, which the node operator does not control from inside the node.

### Recommendation
Restructure `Work()` so that a failure on one group query does not abort processing of already-successfully-fetched groups' purge logic. Options: (1) collect per-group errors and only skip purge/demotion for users belonging solely to the failed group's role tier, while still purging users entirely absent from all other successfully-queried groups; (2) treat any query failure as fail-secure by degrading/quarantining rather than skipping — e.g., if any group query fails, don't add new members but also don't rely on incomplete data to skip already-known revocations; or (3) separately track "last known good full upstream state" and only apply purge decisions once a fully successful sync completes, while additionally enforcing a hard staleness ceiling (e.g., force-expire any local ldap_sessions/tokens whose last full-successful-sync-confirmation exceeds N cycles) so indefinite persistence cannot occur even under continuous partial LDAP errors.
