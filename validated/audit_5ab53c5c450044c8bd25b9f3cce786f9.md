### Title
Funded instant-withdraw claims never clean up per-epoch receipt state, inflating default-recovery basis and reserve — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` and skips the per-epoch cleanup (`instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`). Like XSA-207, cleanup is skipped on the "normal" lifecycle path, leaving stale state that leaks into a later accounting pass. If the borrower defaults later in the same epoch while another instant receipt is still unfunded, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` count already-claimed-and-paid-out instant receipts again, overstating both the recovery basis and the "already-held" reserve. `finalizeDefaultRecovery` then computes an inflated `defaultRecoveryPrice` against funds that were already transferred out, so early claimants are overpaid from other users' recovery share and later claims revert on insolvency.

### Finding Description
In `requestInstantWithdraw`, the vault records the receipt in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the epoch aggregate `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

The funded-claim path only clears the aggregate:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

`instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are only decremented inside `_claimDefaultedInstantWithdrawRequest`, i.e. only on the post-default path [3](#0-2) . Because `epochNumber` does not change between requests, funding, claims, and default within one epoch, the stale entries collide with live accounting.

At finalization, `defaultPendingClaimBasis` adds the full current-epoch instant aggregate whenever `pendingInstantWithdraws != 0` [4](#0-3) , and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying already held in the strategy [5](#0-4) . Both silently include receipts that were already claimed and paid out via `_transferFundedClaim`, so `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and the derived `recoveryPrice` are computed on phantom funds [6](#0-5) .

### Impact Explanation
The reserve is credited with funds that no longer exist (they were already transferred to the funded claimant). `defaultRecoveryPrice` is therefore too high: every defaulted instant receipt, defaulted normal receipt, and post-default request paid via `_transferDefaultRecovery` receives more than its entitlement, with the excess funded by real underlying belonging to other claimants and active LPs whose claims come through `DefaultDistributor`. The loss equals the total amount of same-epoch instant receipts that were funded and claimed before finalization — attacker-controlled, since any tranche holder can size their own instant withdrawal. Once the real balance is exhausted, `_transferDefaultRecovery` reverts for all remaining claimants (reserve/balance mismatch), permanently freezing the tail claims while early claimants keep the overpayment — direct theft plus insolvency, not a mere post-default freeze: the recovery math itself pays out money that does not exist.

### Likelihood Explanation
Requires only unprivileged actors and honest privileged ones:
1. Epoch N running with `allowInstantWithdraw`; user A requests an instant withdraw.
2. Manager calls `getInstantWithdrawFunds` after the deadline; borrower funds it, A claims via `claimInstantWithdrawRequest` — funded path leaves `instantWithdrawClaimsByEpoch[N]` and `instantWithdrawsRequestsByEpoch[A][N]` stale.
3. Any user B requests a new instant withdraw in the same epoch (`epochNumber` unchanged), restoring `pendingInstantWithdraws != 0`.
4. `stopEpoch` is called and borrower repayment fails → `_handleBorrowerDefault`, then `finalizeDefaultRecovery` counts A's paid-out amount twice.

No malicious privileged role is needed; the honest borrower simply fails to repay in an epoch that happens to contain a mixed funded/unfunded instant set. The stale entries are guaranteed whenever the funded claim path executes before default in the same epoch, which is a normal operational sequence.

### Recommendation
Mirror the per-epoch cleanup on the funded claim path: in `claimInstantWithdrawRequest`, after computing `amount`, clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (or track and clear the correct request epoch) and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount, so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only ever observe still-outstanding receipts. Alternatively, have `collectInstantWithdrawFunds`/funding bookkeeping move claimed-vs-pending state into a separate "funded" bucket that default accounting excludes.

### Proof of Concept
Foundry fork PoC sketch (against `IdleCreditVault` + `IdleCDOEpochVariant`):

```solidity
// setup: standard epoch variant, instant withdraws enabled, epoch N running
// 1. userA deposits AA, requests instant withdraw of A_amt
vm.prank(userA);
cdoEpoch.requestInstantWithdraw(A_amt, address(AAtranche));

// 2. warp past instantWithdrawDeadline; manager pulls funds, A claims
vm.warp(cdoEpoch.instantWithdrawDeadline() + 1);
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds();
vm.prank(userA);
cdoEpoch.claimInstantWithdrawRequest();
// instantWithdrawClaimsByEpoch[N] still == A_amt  (stale)

// 3. userB requests instant withdraw in the SAME epoch
vm.prank(userB);
cdoEpoch.requestInstantWithdraw(B_amt, address(AAtranche));
// pendingInstantWithdraws == B_amt; instantWithdrawClaimsByEpoch[N] == A_amt + B_amt

// 4. borrower does not repay; stopEpoch -> _handleBorrowerDefault
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0); // borrower transfer fails -> defaulted

// 5. finalizeDefaultRecovery
uint256 basis = strategy.defaultPendingClaimBasis();
// basis == pendingWithdraws + (A_amt + B_amt)   [A_amt double counted]
// prefundedReserve == A_amt (funds already paid to A counted as held)
uint256 recovered = /* external recovery */;
vm.prank(address(cdoEpoch));
strategy.finalizeDefaultRecovery(recovered, recoverySource);
// assert: defaultRecoveryPrice * basis / 1e18 > actual strategy underlying balance
// B claims -> receives inflated payout; subsequent claimants' claims revert (insolvency)
```

The assertion that `instantWithdrawClaimsByEpoch[N]` still equals `A_amt + B_amt` after A's funded claim, and that `defaultRecoveryReserve` exceeds the strategy's real underlying balance by `A_amt`, is the smoking gun — it is verified with two `assertEq`s and does not depend on exact recovery amounts.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
