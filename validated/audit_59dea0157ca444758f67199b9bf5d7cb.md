### Title
Missing MessageId uniqueness check in `ValidatedMessageFromReq` enables cross-user response hijacking via `savedCallbacks` map collision - ([File: core/services/gateway/handlers/common/message_util.go])

### Summary
`ValidatedMessageFromReq` validates JSON-RPC version, method, and params presence, then delegates to `api.Message.Validate()`, but neither function checks that `req.ID` (used as `MessageId`) is not already in use by another in-flight request. Because `Message.Validate()`'s signature check (`ExtractSigner`) only proves *some* valid signer signed the message body — it does not bind the ID to a specific expected requester — any signer can submit a message with an attacker-chosen `MessageId` that collides with a legitimate pending request's ID.

### Finding Description
`ValidatedMessageFromReq` in [1](#0-0)  checks `req.Version`, non-empty `req.Method`, and non-nil `req.Params`, then unmarshals params into `api.Message`, sets `m.Body.MessageId = req.ID`, and calls `m.Validate()`. `Message.Validate()` in [2](#0-1)  checks field lengths/format and calls `ExtractSigner()` to recover `m.Body.Sender` from the ECDSA signature — but the recovered signer is whoever actually signed the payload, not verified against any expected sender tied to the `MessageId`. No component in this validation path checks whether `MessageId` already corresponds to an in-flight request.

Downstream, this un-deduplicated `MessageId` is used as the key into shared maps that route responses back to the original requester, e.g. `h.savedCallbacks[msg.Body.MessageId]` in the gateway's HTTP-facing handler [3](#0-2) , and later consumed in `handleWebAPITriggerMessage` [4](#0-3) , which retrieves and deletes the callback keyed purely by `MessageId` and forwards the node's response to whoever's callback is currently stored under that key. Because `HandleLegacyUserMessage` unconditionally overwrites `h.savedCallbacks[msg.Body.MessageId]` without checking for an existing entry [5](#0-4) , an attacker who submits a second, independently-signed request using the same `MessageId` as a legitimate in-flight request can overwrite the map entry with their own callback. When the DON node subsequently responds to the original legitimate request (still carrying the original `MessageId`), the gateway looks the callback up by ID only and delivers the response to the attacker's (now-installed) callback instead of the legitimate requester's.

An analogous non-deduplicated map exists on the node side in `outgoing_connector_handler.go`'s `responses.new(id)`, but there duplicate IDs at least return an explicit `"already have response for id"` error and cleanup — however, the `ValidatedMessageFromReq` function used to route the *inbound* gateway message into `HandleGatewayMessage` still performs no uniqueness check itself, and gateway->node messages routed by ID collision could similarly desynchronize the caller's blocked `select` on `ch`.

### Impact Explanation
Cross-user response confusion: an attacker can hijack the delivery of another (legitimate) user's job/request response by pre-guessing or racing to overwrite a `MessageId` before or during the legitimate request's flight, causing potentially sensitive execution results/responses to be delivered to the attacker's callback instead of the rightful requester. This matches the "cross-user response confusion" bounty impact class scoped in the question.

### Likelihood Explanation
Requires only an unauthenticated/unprivileged client able to sign and submit a JSON-RPC message to the gateway with an attacker-chosen `MessageId` (the ID is fully attacker-controlled and only needs a valid signature over the attacker's own message content — no relationship to the victim's key or session is required). Exploitation timing is race-dependent (attacker must submit before the legitimate node response arrives), which lowers but does not eliminate feasibility; it is repeatable since `MessageId` values may be predictable or observable depending on the calling client's ID-generation scheme.

### Recommendation
Enforce `MessageId` uniqueness/ownership at the point requests are admitted: reject a request whose `MessageId` already has a live entry in `savedCallbacks` (or return a conflict) instead of silently overwriting it, and/or bind the response-routing entry to the original request's signer/sender so that a response can only be routed if the responding message's context matches the original requester. This check belongs in `ValidatedMessageFromReq`/`Message.Validate()` (reject reused/unexpected IDs) and in `handler.go`'s `HandleLegacyUserMessage` where `savedCallbacks` is populated.

### Proof of Concept
Go handler-level test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two distinct signers (simulating two independent unauthenticated users), A and B.
2. Build `msgA` with `MessageId = "X"`, valid signature from A's key, method `web_api_trigger`, submitted via `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` — assert `h.savedCallbacks["X"]` now stores `callbackA`.
3. Before the DON responds, construct `msgB` with the same `MessageId = "X"`, valid signature from B's key, and submit via `h.HandleLegacyUserMessage(ctx, msgB, callbackB)` — assert this succeeds without error/rejection and `h.savedCallbacks["X"]` is now `callbackB` (overwritten).
4. Simulate the DON responding to the original request A by calling `h.handleWebAPITriggerMessage(ctx, respMsgWithID_X, nodeAddr)`.

func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
