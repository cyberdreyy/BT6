### Title
Loss-adjusted withdraw receipt is later re-typed as a fully-funded receipt and paid at par when the user files a second request - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` stores per-epoch withdraw receipts (`withdrawsRequestsByEpoch`) but keeps a single scalar `lastWithdrawRequest[_user]` as the only pointer used to decide whether the *latest* receipt suffered a `stopEpochWithDuration` loss (`lossRecoveryPriceByEpoch`). If a user lets a haircut receipt sit unclaimed and then files a second request in a later epoch, `lastWithdrawRequest` is overwritten, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[newEpoch] == 0` and silently skips the haircut path, and `_claimFundedWithdrawRequest` then pays the *entire* aggregate `withdrawsRequests[_user]` (old haircut basis included) at par. This is the credit-vault analog of the CVE-2019-11707 `Array.pop` type confusion: a receipt object of one type (loss-adjusted) is re-interpreted as another type (funded at par) after the bookkeeping slot that encoded its type is clobbered by a subsequent write.

### Finding Description
- On a partially-funded stop, `collectWithdrawFunds` sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` [1](#0-0) . The strategy has only received `X * price` underlying for that epoch's receipts.
- `requestWithdraw` unconditionally bumps `lastWithdrawRequest[_user] = currentEpoch` and adds to the aggregate `withdrawsRequests[_user]` [2](#0-1) .
- `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which indexes `lossRecoveryPriceByEpoch` strictly by `lastWithdrawRequest[_user]` — there is no way to claim an *earlier* loss epoch once the marker moved [3](#0-2) .
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` in full once `epochNumber > lastWithdrawRequest[_user]` [4](#0-3) . The aggregate still contains the epoch-`E` basis (`withdrawsRequestsByEpoch[_user][E]` was never cleared because `_clearWithdrawClaimForEpoch` is only reachable through the loss/default paths that never fired for `E`).

Broken invariant: one receipt, one payout at its correct price. The haircut receipt basis `X` is paid `X` instead of `X·price`, while the strategy only ever received `X·price` for it.

### Impact Explanation
The attacker over-withdraws `X·(1 − lossRecoveryPrice)` underlying from the vault. `_transferFundedClaim` only guards against spending `defaultRecoveryReserve` [5](#0-4) , so the excess is paid out of underlyings reserved for *other* users' funded receipts in the same epoch — i.e., direct theft / insolvency of the claim pool. Quantified loss: `(1 − recoveryPrice) × attacker's haircut-epoch request size`; with a 50% loss-adjusted stop and a 100k USDC receipt, the theft is 50k USDC taken from concurrent claimants, who are then left with permanently frozen/unpayable receipts.

### Likelihood Explanation
Requires only an unprivileged tranche holder and an honest `stopEpochWithDuration(_lossAmount)` loss event — a normal operating mode explicitly supported by the code. The attacker simply delays claiming (rational anyway: waiting costs nothing) and stacks a second request, so no privileged cooperation is needed and the sequence is trivially repeatable each loss epoch.

### Recommendation
Track haircut claims per epoch instead of via the single `lastWithdrawRequest` marker: e.g., iterate/store a per-user list of epochs with `lossRecoveryPriceByEpoch[e] != 0`, or make `_claimFundedWithdrawRequest` subtract each unsettled loss-epoch basis (`claimBasis·price`) and route it through the loss path before paying the remainder at par. Alternatively, revert in `requestWithdraw` when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` forces a stale haircut receipt.

    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(attacker, Y_TRANCHES); // lastWithdrawRequest overwritten
    _stopCurrentEpochWithApr(apr);                  // epoch E+1 fully funded

    // claim: loss path sees lossRecoveryPriceByEpoch[E+1]==0 -> skipped
    // funded path pays withdrawsRequests[attacker] = X + Y at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(cdoEpoch_owner_asIdleCDO); strategy.claimWithdrawRequest(attacker);
    // attacker received X + Y while vault only holds X*0.5 + Y

    // other funded claimants of epoch E+1 are now short X*0.5 -> revert/insolvency

Key assertion: `strategy.balanceOf` / underlying reserve for epoch E+1 claims is short exactly `X·(1 − 0.5)`, proving theft from other claimants rather than a self-funded payout.

    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
