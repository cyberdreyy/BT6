### Title
Instant-withdraw receipts pay the full recorded basis without verifying funded balance — unfunded claims drain strategy underlyings - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The FlatGeobuf bug verifies a length field exists but never checks the declared body fits inside the supplied buffer, so an attacker-controlled length materializes data past the funded region. The closest analog in `IdleCreditVault` is the instant-withdraw claim path: `claimInstantWithdrawRequest` trusts the recorded receipt length (`instantWithdrawsRequests[_user]`) and pays it in full via `_transferFundedClaim`, while the funded/unfunded split is tracked separately in `pendingInstantWithdraws` and is never consulted on the claim path. The receipt "length" is materialized into a payout without checking it is contained within the funded buffer.

### Finding Description
`requestInstantWithdraw` mints a 1:1 strategy-token receipt and records `instantWithdrawsRequests[_user] += _amount` plus `pendingInstantWithdraws += _amount` (`IdleCreditVault.sol:356-375`). Funding arrives later, out of band, through `collectInstantWithdrawFunds`, which only decrements `pendingInstantWithdraws` and pulls tokens from the CDO (`IdleCreditVault.sol:398-403`). Nothing ties a claim to what was actually funded.

In `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`) the vault does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`_transferFundedClaim` (`IdleCreditVault.sol:897-907`) only guards `defaultRecoveryReserve`; it does not check `pendingInstantWithdraws`, the per-epoch funded remainder, or that the payout is covered by underlying collected via `collectInstantWithdrawFunds`. The default-recovery path treats this mismatch explicitly: `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` (`IdleCreditVault.sol:644-649`, `716-723`) acknowledge that `instantWithdrawClaimsByEpoch` can exceed `pendingInstantWithdraws`-funded amounts, i.e. receipts exist that are not backed by collected funds. Yet pre-default the same gap is honored at par.

The result: a user holding an unfunded instant receipt (funding gap created because the CDO collected only part of `pendingInstantWithdraws`, or epoch stopped with a low-APR instant bucket before full funding) can claim the full recorded basis, withdrawing underlyings that belong to other receipt holders or to the funded pool — the vault "reads past the end of the funded buffer" and materializes it into a transfer.

### Impact Explanation
Direct theft of other users' funded underlyings. If an attacker holds an instant receipt of size `R` but only `F < R` was funded into the strategy, claiming pays `R`, siphoning `R - F` from balance reserved for other claimants and funded withdraws; subsequent honest claims then revert on insufficient balance or on the `defaultRecoveryReserve` guard, permanently freezing unclaimed yield. Loss is bounded by the unfunded instant basis, which can be the full `pendingInstantWithdraws` of an epoch.

### Likelihood Explanation
Requires an epoch phase where instant receipts exist that are not fully funded: a stopEpoch that leaves a nonzero `pendingInstantWithdraws` remainder, or default finalization before `defaultInstantWithdrawsFinalized` covers all claims. Any KYC-passing lender who opened an instant withdraw request can trigger it; the attacker does not need a privileged role. The missing check is a pure accounting gap in the strategy — `_onlyIdleCDO` is the only access guard and the CDO has no visibility into per-claim funded status inside the vault.

Caveat I could not fully verify within this scan: whether `IdleCDOEpochVariant.claimInstantWithdrawRequest` gates claims on the CDO side (e.g., on `getInstantWithdrawFunds`/funding state) before delegating to the strategy. The strategy itself enforces no funded-balance invariant, so if the CDO relies on the vault to hold funds rather than gating claims, the hole is exploitable as described.

### Recommendation
Track the funded instant-claim basis explicitly (e.g., a `fundedInstantWithdraws` counter incremented in `collectInstantWithdrawFunds` alongside `pendingInstantWithdraws -= _amount`), and in `claimInstantWithdrawRequest` cap or revert claims exceeding the funded remainder — i.e., verify the receipt body is "contained in the buffer" before materializing the payout, mirroring how `_transferFundedClaim` already isolates `defaultRecoveryReserve`.

### Proof of Concept
```solidity
// Fork test sketch (Foundry): epoch variant with instant withdraws enabled.
// 1. startEpoch; attacker deposits and calls requestInstantWithdraw(R) during
//    the instant window -> instantWithdrawsRequests[attacker] = R,
//    pendingInstantWithdraws = R. burn/mint receipt happens immediately.
// 2. At stopEpoch, CDO collects only F < R via collectInstantWithdrawFunds(F)
//    (low-APR stop or partial borrower funding), leaving pendingInstantWithdraws = R - F.
// 3. In the next epoch, cdoEpoch.claimInstantWithdrawRequest() ->
//    strategy.claimInstantWithdrawRequest(attacker) pays R in full through
//    _transferFundedClaim even though only F was funded:
//    assertEq(underlying.balanceOf(attacker) - pre, R);  // drains R - F of others' funds
// 4. A second honest claimant's funded claim then reverts or the reserve guard trips.
```
A reproduction would assert that `underlying.balanceOf(strategy)` after the attacker's claim is less than `defaultRecoveryReserve + sum(other funded claims)`, proving the payout exceeded the funded buffer.
