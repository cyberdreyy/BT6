### Title
EI-authenticated requests bypass the "EIs not allowed" restriction in `PipelineRunsController.Create` via synthetic user injection - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates integer-ID job runs behind `auth.GetAuthenticatedUser(c)` returning `isUser == true`, with an explicit comment that "EIs not allowed" to trigger numeric-ID job runs. However, `AuthenticateExternalInitiator` in `core/web/auth/auth.go` sets the exact same `SessionUserKey` context value used by `GetAuthenticatedUser` to a synthetic `clsessions.User{Role: clsessions.UserRoleRun}`, making `isUser` evaluate to `true` for EI-authenticated requests and defeating the intended restriction.

### Finding Description
`PipelineRunsController.Create` checks: [1](#0-0) 
`isUser` is derived purely from `auth.GetAuthenticatedUser(c)`, which just reads whatever `*clsessions.User` pointer is stored under `SessionUserKey` in the gin context: [2](#0-1) 

The problem is that `AuthenticateExternalInitiator` — the auth method used for external-initiator credential holders — stores a fabricated `clsessions.User` object under that same `SessionUserKey`: [3](#0-2) 

This means any request authenticated purely as an External Initiator (no real session/API-token user) will cause `GetAuthenticatedUser` to return `(user, true)` — indistinguishable at the type level from a real user session set by `AuthenticateBySession`/`AuthenticateByToken`. The `isUser` check in `PipelineRunsController.Create` was clearly intended to distinguish "real user" auth from "EI" auth (per the inline comment "only users are allowed to run jobs using int IDs - EIs not allowed"), but it cannot do so because both paths populate the same context key with the same concrete type. There is no distinguishing marker (e.g., checking `GetAuthenticatedExternalInitiator` is also unset, or using a different context key/role sentinel) to prevent this collapse.

### Impact Explanation
An External Initiator credential holder — a Role: run-equivalent but supposed to be limited to invoking jobs bound to their own initiator (typically via UUID/bridge-specific webhook paths) — can instead invoke `RunJobV2` for *any* integer job ID on the node, i.e., trigger arbitrary job runs unrelated to their EI binding. This is an authorization-bypass / privilege-confusion issue: an attacker who only holds narrow-scope EI credentials can trigger arbitrary job executions node-wide, matching a job-run authorization bypass class of impact (unauthorized job run).

### Likelihood Explanation
Precondition is only a valid set of External Initiator credentials (access key/secret), which is a comparatively low-privilege credential class distinct from admin/edit node users. Given valid EI credentials, exploitation requires nothing more than sending `POST /v2/jobs/{int-jobID}/runs` with the EI headers — a single HTTP request, fully repeatable, no timing or race requirements.

### Recommendation
Distinguish real authenticated users from synthetic EI-derived users in `PipelineRunsController.Create`. For example, check `auth.GetAuthenticatedExternalInitiator(c)` and reject if present (i.e., reject when both an EI and the synthetic run-role user exist), or have `AuthenticateExternalInitiator` avoid overwriting `SessionUserKey` with a `clsessions.User` and instead expose a distinct context key/type (e.g., a dedicated `IsExternalInitiator` marker) so `isUser` only reflects genuine session/token-authenticated users, restoring the intended "EIs not allowed" invariant for integer-ID job runs.

### Proof of Concept
Handler-level Go test plan:
1. Build a gin test context and directly set `c.Set(auth.SessionExternalInitiatorKey, ei)` then `c.Set(auth.SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})`, mirroring exactly what `AuthenticateExternalInitiator` does (or invoke `AuthenticateExternalInitiator` against a mock `Authenticator` returning a valid `bridges.ExternalInitiator`).
2. Set `c.Params = gin.Params{{Key: "ID", Value: "123"}}` where job 123 is a pre-created job in the test DB unrelated to the EI.
3. Call `(&PipelineRunsController{App: app}).Create(c)`.
4. Assert: `auth.GetAuthenticatedUser(c)` returns `isUser == true` even though authentication was via `AuthenticateExternalInitiator`, and assert the response is `200 OK` with a `pipelineRun` resource for job 123 (i.e., `RunJobV2` was invoked), demonstrating the EI successfully ran a job by integer ID despite the "EIs not allowed" comment/intent.
