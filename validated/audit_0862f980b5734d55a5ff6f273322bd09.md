## #Title
Permissionless staked-collateral bank creation can be front-run/squatted at the canonical `bank_seed`, griefing legitimate validator onboarding - (File: `programs/marginfi/src/instructions/marginfi_group/add_pool_permissionless.rs`)

### Summary
`lending_pool_add_bank_permissionless` lets *any* unprivileged caller create a staked-collateral `Bank` PDA for a given validator's stake pool, with the `Bank` address derived only from `(marginfi_group, bank_mint, bank_seed)` — none of which are bound to the caller's identity. Because `bank_seed` is a plain user-supplied `u64` and the canonical/expected value is `0` (as used throughout tests and tooling), an attacker can pre-emptively call this permissionless instruction with `bank_seed = 0` for any validator's public stake pool before the validator/protocol does, permanently occupying the canonical PDA slot and forcing the legitimate creation to fail or fall back to a non-canonical seed. This mirrors the reported Folks Finance bug class: a user-suppliable identifier used to seed a uniqueness-gated PDA, with no per-caller binding, enabling a front-running griefing attack.

### Finding Description
`LendingPoolAddBankPermissionless` derives the `bank` account as: [1](#0-0) 

The instruction accounts require only a `fee_payer: Signer` — there is no `admin`/`has_one` check tying the caller to the validator or group owner: [2](#0-1) 

The `bank_seed` parameter is a raw `u64` supplied entirely by the caller, with no requirement that it be related to any specific validator/authority — unlike, e.g., `MarginfiAccountInitializePda` where `authority.key()` is baked into the seeds (preventing exactly this kind of squat by a third party), here the PDA seeds are `(group, bank_mint, bank_seed)` only: [3](#0-2) 

Because `bank_mint`, `stake_pool`, `pool_onramp`, and `validator_vote_account` are all publicly derivable/observable (the LST mint is a PDA of the stake pool, the vote account is public), any unprivileged party can assemble a valid call for any validator's stake pool and race to create the bank at `bank_seed = 0` (the canonical value used by off-chain tooling/UI, e.g. `deriveBankWithSeed(..., new BN(0))`): [4](#0-3) [5](#0-4) 

Since the `bank` account uses `init` (Anchor's standard "must not already exist" constraint), whoever calls first at a given `(group, mint, seed)` wins the slot permanently; every subsequent call with the same seed fails with "already in use," exactly analogous to `UserLoanAlreadyCreated` reverting subsequent legitimate `createLoan` calls in the Folks Finance report.

### Impact Explanation
An attacker can pre-create the seed-`0` staked-collateral bank for any (or every) validator's LST before the intended/official onboarding flow runs, forcing:
- Failed transactions for whoever (validator operator, protocol ops, or automated onboarding scripts) attempts the "normal"/default `bank_seed = 0` call, consuming their fee-payer SOL and requiring manual recovery with a non-canonical seed.
- Durable inconsistency for off-chain systems, indexers, and UI that assume `bank_seed = 0` is canonical per `(group, mint)`, since the canonical slot is now permanently occupied by an account the attacker chose to spam-create (even though its config content is otherwise deterministic/default). This can be repeated across every validator's mint, since the caller need not have any relationship to the validator.
- This qualifies as griefing (no profit motive required) causing repeated protocol/ops disruption and wasted transaction/rent costs, consistent with the reported bug class impact category.

The instruction being fully permissionless (no `admin`/owner check) is what elevates this beyond simple "anyone can help onboard a validator" design intent into an exploitable squat vector, because the *seed choice* itself is not scoped per validator/caller.

### Likelihood Explanation
Likelihood is moderate: the attack requires no privileged access, no signatures from the victim, and all inputs (`stake_pool`, `validator_vote_account`, `bank_mint`) are public on-chain data. An attacker only needs to watch for new validators being onboarded (or pre-emptively squat all known validators) and submit a transaction with `bank_seed = 0` first. The cost to the attacker is only the rent for the vaults/bank account (recoverable is not applicable since `Bank` accounts aren't closable in this flow easily), making it a cheap, repeatable disruption vector, though it yields no direct profit — matching the "Griefing" impact class explicitly called out in the source report.

### Recommendation
Bind the seed derivation (or an explicit uniqueness/authorization check) to something the legitimate party controls, e.g.:
- Require the `validator_vote_account` (or its withdraw authority) to sign, or check a `has_one`/authority relationship before allowing bank creation for that validator's stake pool, similar to how `MarginfiAccountInitializePda` binds `authority.key()` into the PDA seeds.
- Alternatively, remove caller-supplied `bank_seed` for the permissionless staked path and instead derive it deterministically/exclusively from validator-owned data (e.g., the vote account pubkey) so no third party can squat an alternate/canonical slot ahead of the rightful party.
- At minimum, document/enforce that `bank_seed` collisions are non-canonical by design and have off-chain tooling never assume `bank_seed = 0` is reserved/guaranteed available, and provide a permissioned "retry with any free seed" fallback in tooling to reduce operational impact.

### Proof of Concept
1. Observe a validator's public `vote_account` and derive `stake_pool`/`lst_mint`/`sol_pool`/`pool_onramp` exactly as the legitimate flow would (all deterministic PDAs from public inputs), as done in `addBankPermissionless`: [6](#0-5) 
2. As an unrelated, unprivileged attacker-controlled `fee_payer`, submit `lending_pool_add_bank_permissionless(bank_seed = 0)` for that validator's stake pool before the legitimate onboarding transaction lands.
3. The `bank` PDA at `(group, lst_mint, 0)` is now initialized by the attacker's transaction (this succeeds because there is no admin/authority check gating the call, only the account uniqueness `init` constraint).
4. When the legitimate onboarding flow (validator, protocol ops, or UI default) later calls the same instruction with `bank_seed = 0` for that validator, the transaction fails since the `bank` account already exists — reproducing the same "already active/used" griefing pattern described in the Folks Finance report, where a user-suppliable identifier lets a third party pre-empt legitimate account creation for someone else.
