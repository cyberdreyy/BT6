Insecure wildcard-origin allowlist matching allows unrelated domains to bypass Gateway CORS restrictions - (File: core/services/gateway/network/httpserver.go)

### Summary
The Chainlink Gateway HTTP server, which is an internet-facing component that accepts JSON-RPC requests from external (unprivileged) clients, implements a `CORSAllowedOrigins` origin allowlist. The wildcard-matching logic uses an unanchored `strings.HasSuffix` comparison that does not enforce a subdomain boundary (`.`), so any origin whose hostname merely *ends with* the configured suffix is treated as an allowed subdomain, even when it is an entirely different registrable domain.

### Finding Description
`isAllowedOrigin` splits the configured allowed origin into scheme/host/port and, for entries starting with `*.`, strips the `*.` prefix and checks `strings.HasSuffix(originHost, allowedHost)`: [1](#0-0) 

Because `HasSuffix` performs a raw string suffix comparison with no check for a preceding `.` (or exact host boundary), an operator-configured wildcard such as `https://*.ethereum.org` (intended to allow only `*.ethereum.org` subdomains) will also match completely unrelated hostnames that merely share the trailing characters, e.g. `evilethereum.org`, `notethereum.org`, or `fake-ethereum.org`. This is the same class of flaw described in the external report: an origin-matching mechanism ("regex"/suffix check) that is not strict enough about domain boundaries, causing the allowlist to be silently bypassed for arbitrary attacker-controlled origins.

The matched origin is then reflected directly into the `Access-Control-Allow-Origin` response header: [2](#0-1) 

This header is what a browser uses to decide whether cross-origin JavaScript running on the attacker's page may read the Gateway's response.

### Impact Explanation
Any unprivileged, unauthenticated client controls the `Origin` header sent to the internet-facing Gateway HTTP server. By registering or controlling a domain that happens to share a suffix with a configured wildcard allow entry (e.g. registering `evil-ethereum.org` when `*.ethereum.org` is allow-listed), an attacker's website can have its origin echoed back in `Access-Control-Allow-Origin`, defeating the intent of the operator's curated allowlist. This is a concrete allowlist-bypass in the origin-validation logic of a component that mediates job/RPC requests, undermining the "defense-in-depth" boundary the allowlist is meant to provide and enabling cross-origin script from a look-alike/attacker domain to interact with the Gateway as if it were a trusted partner site.

### Likelihood Explanation
Likelihood is moderate to high: exploitation requires only sending a crafted `Origin` header from any domain the attacker controls (no credentials, no privileged access, no race condition needed), and the flawed comparison logic (`strings.HasSuffix` without a boundary check) is deterministic and always reachable whenever `CORSEnabled` and a wildcard entry are configured, which is a documented/sample configuration pattern. [3](#0-2) 

### Recommendation
Anchor wildcard matching to a proper subdomain boundary instead of a raw suffix check, e.g. require `originHost == allowedHost` or `strings.HasSuffix(originHost, "."+allowedHost)`, and reject malformed/ambiguous hostnames. Consider replacing manual string matching with `net/url`-based hostname parsing plus explicit label-by-label comparison, and add negative test cases for suffix-confusable domains (e.g. `evil`+allowed-suffix) to `httpserver_test.go`.

### Proof of Concept
Given Gateway config `CORSAllowedOrigins = ["https://*.ethereum.org"]` and `CORSEnabled = true`:
1. Attacker registers/controls `https://evilethereum.org` (not a subdomain of `ethereum.org`).
2. Attacker's page issues a request to the Gateway endpoint with `Origin: https://evilethereum.org`.
3. `isAllowedOrigin` computes `allowedHost = "ethereum.org"`, `originHost = "evilethereum.org"`, and `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true`, so the origin is treated as allowed.
4. The server responds with `Access-Control-Allow-Origin: https://evilethereum.org`, letting the attacker's cross-origin script read the Gateway's response, in violation of the intended allowlist. [4](#0-3)

func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
