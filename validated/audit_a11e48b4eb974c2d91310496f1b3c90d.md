### Title
Blacklisted USDC lenders cannot claim matured withdrawals because payout is hard-bound to the requesting address - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary

`IdleCDOEpochVariant.claimWithdrawRequest()` always uses `msg.sender` as both the receipt owner and the USDC payout recipient. If that address is added to the USDC blacklist after creating a withdrawal request, the final `safeTransfer` reverts permanently, leaving the matured claim and its backing funds stuck in the credit vault. [1](#0-0) [2](#0-1) 

### Finding Description

A lender creates a claim through `IdleCDOEpochVariant.requestWithdraw()`, and `IdleCreditVault.requestWithdraw()` mints an address-bound strategy-token receipt and records the claim under `_user`. [3](#0-2) 

After the request matures, `claimWithdrawRequest()` clears the accounting and burns the receipt associated with `_user`, but `_transferFundedClaim()` pays only `_user`. [4](#0-3) 

For a USDC-backed pool, `underlyingToken.safeTransfer(_user, _amount)` reverts once `_user` is blacklisted by Circle. Because the receipt cannot be transferred to another wallet and the claim path exposes no alternative recipient, the owner cannot route the matured payout to an unblacklisted address. [5](#0-4) [6](#0-5) 

The same issue affects instant withdrawals because `claimInstantWithdrawRequest()` also fixes `_user` as the payout destination. [7](#0-6) 

### Impact Explanation

A lender whose address is blacklisted after creating the request loses practical access to the full matured withdrawal amount, including principal and earned interest. The claim remains recorded and funded, but every attempt to collect it reverts at the USDC transfer, so the assets remain locked in `IdleCreditVault` for as long as the address remains blacklisted. [8](#0-7) [2](#0-1) 

This violates fair payout rather than vault solvency: the protocol has accounted for and reserved the user's claim, but delivers it to an immutable recipient. [9](#0-8) 

### Likelihood Explanation

The condition is external because Circle controls the USDC blacklist, but it is a realistic operational state for centralized stablecoins. Once true, exploitation of the frozen claim requires no privileged action inside the protocol and no race condition; every `claimWithdrawRequest()` transaction deterministically fails at the payout transfer. [2](#0-1) 

The address-bound receipt design removes the normal workaround of transferring the withdrawal position to a clean wallet before claiming. [6](#0-5) 

### Recommendation

Keep receipt ownership and accounting bound to `msg.sender`, but separate the payout destination from the receipt owner:

```solidity
// contracts/IdleCDOEpochVariant.sol
function claimWithdrawRequest(address recipient) external {
    if (recipient == address(0)) revert Is0();
    IdleCreditVault(strategy).claimWithdrawRequestFor(msg.sender, recipient);
}
```

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
function claimWithdrawRequestFor(address owner, address recipient)
    external
    returns (uint256 amount)
{
    _onlyIdleCDO();
    // Clear and burn claims under `owner`, but pass `recipient`
    // to `_transferFundedClaim` / `_transferDefaultRecovery`.
}
```

Apply the same owner/recipient split to instant withdrawals, post-default requests, loss-adjusted claims, and default recovery claims. Alternatively, add a consent-based ownership migration for strategy-token receipts so a blacklisted owner can move the claim to a clean address before payout. [4](#0-3) [10](#0-9) 

### Proof of Concept

The following test can be added to `test/foundry/IdleCreditVault.t.sol`. It creates a mature USDC claim, blacklists the owner through the live USDC `blacklister`, and shows that claiming always reverts while the claim remains uncleared:

```solidity
interface IFiatTokenBlacklist {
    function blacklister() external view returns (address);
    function blacklist(address account) external;
    function isBlacklisted(address account) external view returns (bool);
}

function testBlacklistedUserCannotClaimMaturedWithdrawal() external {
    address user = makeAddr("blacklisted-user");
    uint256 amount = 10_000 * ONE_SCALE;

    deal(USDC, user, amount);

    vm.startPrank(user);
    IERC20Detailed(USDC).approve(address(cdoEpoch), amount);
    cdoEpoch.depositAA(amount);
    uint256 claimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.stopPrank();

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(
        0,
        initialProvidedApr,
        _expectedFundsEndEpoch()
    );

    IFiatTokenBlacklist fiat = IFiatTokenBlacklist(USDC);
    vm.prank(fiat.blacklister());
    fiat.blacklist(user);
    assertTrue(fiat.isBlacklisted(user));

    uint256 balanceBefore = IERC20Detailed(USDC).balanceOf(user);

    vm.prank(user);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();

    assertEq(
        IERC20Detailed(USDC).balanceOf(user),
        balanceBefore,
        "blacklisted user received USDC"
    );
    assertEq(
        IdleCreditVault(address(strategy)).withdrawsRequests(user),
        claimBasis,
        "claim was not retained after failed transfer"
    );
}
```

The deposit and request complete before blacklisting, so the revert is isolated to the matured payout at `underlyingToken.safeTransfer(_user, _amount)`. [5](#0-4)

  function claimWithdrawRequest(address _user) external returns (uint256 amount) {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized) {
      // Post-default requests are already priced after the haircut and backed by the reserve,
      // so they must not fall through to the defaulted-epoch receipt logic.
      amount = _claimPostDefaultWithdrawRequest(_user);
      if (amount != 0) return amount;
      // Only receipts created in the defaulted epoch are haircutted here; old fulfilled
      // receipts are handled below at par if they were already funded before default.
      amount = _claimDefaultedWithdrawRequest(_user);
    }
    amount += _claimLossAdjustedWithdrawRequest(_user);
    return amount + _claimFundedWithdrawRequest(_user);
  }

  /// @notice Claim a funded non-default withdraw request at par.
  /// @param _user address of the user
  /// @return amount amount claimed
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }

  /// @notice Transfer default recovery reserve to a user.
  /// @param _user claim receiver
  /// @param _amount amount to transfer
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
