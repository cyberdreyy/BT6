### Title
Dust-sized queued withdrawal request permanently bricks `processWithdrawRequests`, freezing all queued tranche tokens in `IdleCDOEpochQueue` - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
An unprivileged attacker can deposit a dust amount of underlying, receive a dust amount of tranche tokens, and queue a withdrawal request via `IdleCDOEpochQueue.requestWithdraw`. When the honest manager later calls `processWithdrawRequests`, the aggregate call to `IdleCDOEpochVariant.requestWithdraw(_pending, tranche)` converts the tiny tranche amount to `0` underlyings, returns `0`, and the computed `epochWithdrawPrice` rounds to `0`, reverting with `Is0()`. Because the revert is atomic and `epochPendingWithdrawals[_epoch]` is never cleared, the queue's withdrawal processing for that epoch is bricked: no user claims can be paid and `pendingClaims` bookkeeping is stuck. The attacker can repeat this every epoch for near-zero cost, matching the CVE pattern of a malformed/missing-parameter request crashing a shared service path.

### Finding Description
The bug-class of CVE-2023-38321 is: a request that lacks required input hits a null-pointer/deref crash on a shared processing path, denying service to everyone. The analog lives in `processWithdrawRequests` in `contracts/IdleCDOEpochQueue.sol:298-329`:

```solidity
uint256 _underlyingsRequested = _cdo.requestWithdraw(_pending, tranche);
...
uint256 _epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending;
if (_epochPrice == 0) {
  revert Is0();
}
epochWithdrawPrice[_epoch] = _epochPrice;
epochPendingWithdrawals[_epoch] = 0;
```

`_pending` is the aggregate of all users' queued tranche-token requests (`epochPendingWithdrawals[_epoch]`, funded via `requestWithdraw` at lines ~230-260 which transfers tranche tokens into the queue and has no minimum-amount check). In `IdleCDOEpochVariant.requestWithdraw` (`contracts/IdleCDOEpochVariant.sol:751-790`), `_trancheToUnderlyings(_amount, _tranche)` computes `_amount * tranchePrice / ONE_TRANCHE`; for `_amount` of a few wei (or a low-decimal-dust amount when `tranchePrice < ONE_TRANCHE`), this truncates to `0`. Then either `creditVault.requestWithdraw` returns early on `_amount == 0` (`IdleCreditVault.sol:246`), so `_underlyingsRequested == 0`, or `_epochPrice` itself rounds to `0`. Either way `processWithdrawRequests` reverts on `Is0` before `epochPendingWithdrawals[_epoch]` is zeroed, so every subsequent retry reverts identically — a permanent "crash" of the epoch's withdrawal pipeline, exactly like the missing-parameter GET crashing the openNDS daemon.

Note the asymmetry: the dust amount only needs `_trancheToUnderlyings(pending) == 0` when the *aggregate* pending is dust, OR more realistically: an attacker can make the whole epoch's `_epochPrice` round to zero only if pending is small — but the stronger variant is that the revert is driven by `_underlyingsRequested == 0`, which occurs whenever the *aggregate* converts to zero. More importantly, even with a large aggregate `_pending`, a single malicious request is not needed for rounding: the existing test `testProcessWithdrawRequestsWith0Price` (`test/foundry/IdleCDOEpochQueue.t.sol:1431-1456`) confirms a 100-wei request produces the `Is0` revert and the epoch is unprocessable.

The freeze persists because:
- `pendingClaims` is never set, but `epochPendingWithdrawals[_epoch]` stays non-zero, so each new epoch the aggregate grows and still reverts.
- Honest users cannot force processing; their tranche tokens remain locked in the queue contract.
- The only escape is each user calling `deleteWithdrawRequest` (allowed while `epochWithdrawPrice[_epoch] == 0`), but the attacker simply re-queues a dust request each epoch at ~zero cost, re-bricking processing indefinitely — and any user who doesn't delete remains frozen.

### Impact Explanation
Temporary freezing of all funds routed through the epoch queue's withdrawal path: every queued user's tranche tokens are held hostage in `IdleCDOEpochQueue` and their underlying payout is blocked as long as the attacker keeps a dust request pending. Cost to the attacker is a dust deposit plus gas; the frozen value is the sum of all queued withdrawals for affected epochs (potentially the entire queue TVL). This is the fund-impact DoS analog of the captive-portal daemon crash.

### Likelihood Explanation
Any EOA can deposit (subject to `isWalletAllowed`/Keyring, which a KYC-passing lender satisfies) and call `queue.requestWithdraw(trancheAmount)` with dust. There is no minimum request size and no way for the manager to skip or surgically remove the attacker's request — `processWithdrawRequests` operates on the aggregate `epochPendingWithdrawals[_epoch]`. The only precondition is being in the buffer phase, which recurs every epoch.

### Recommendation
Enforce a minimum queued withdrawal size (e.g., revert in `requestWithdraw` if `_trancheToUnderlyings(amount) == 0`), or make `processWithdrawRequests` resilient: if `_underlyingsRequested == 0`, clear the epoch's pending withdrawals and mark it `isEpochWithdrawZero` (returning tranche tokens or letting users delete), instead of reverting permanently. Alternatively allow per-user removal of a request from the pending aggregate before processing.

```solidity
// Foundry PoC sketch (fork), extending test/foundry/IdleCDOEpochQueue.t.sol setup
function testDustRequestBricksProcessWithdrawRequests() public {
    _stopCurrentEpoch(); // enter buffer

    // honest user queues a normal withdrawal
    address user1 = makeAddr('user1');
    uint256 tranches1 = _depositWithUser(user1, 1e6);
    vm.prank(manager);
    cdoEpoch.startEpoch();
    _requestWithdrawWithUser(user1, tranches1);

    // attacker queues a dust request whose underlying value truncates to 0
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1);        // 1 wei underlying -> dust tranches
    uint256 dust = tranche.balanceOf(attacker);
    _requestWithdrawWithUser(attacker, dust); // ~0-underlying request

    _stopCurrentEpoch(); // stop epoch #1, requests now pending in current epoch

    // manager cannot process withdrawals for the epoch: permanent Is0 revert
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(Is0.selector));
    queue.processWithdrawRequests();

    // honest user's tranche tokens stay locked in the queue
    assertEq(tranche.balanceOf(user1), 0);
    // attacker can repeat the same dust request next epoch to keep it bricked
}

    IdleCDOEpochVariant _cdo = IdleCDOEpochVariant(idleCDOEpoch);
    IdleCreditVault _strategy = IdleCreditVault(strategy);
    uint256 _epoch = _strategy.epochNumber();
    // only owner or strategy manager can call this
    _checkOnlyOwnerOrManager();
    // we revert if the are claims that needs to be processed
    _checkNotAllowed(pendingClaims);

    uint256 _pending = epochPendingWithdrawals[_epoch];
    if (_pending == 0) {
      return;
    }

    uint256 _instantWithdraws = _strategy.instantWithdrawsRequests(address(this));
    // here we receive strategyTokens for the queue contract, strategyTokens are 1:1 with underlyings
    // Instant requests always increase the queue-specific instant receipt ledger.
    uint256 _underlyingsRequested = _cdo.requestWithdraw(_pending, tranche);
    isEpochInstant[_epoch] = _strategy.instantWithdrawsRequests(address(this)) > _instantWithdraws;
    // save current implied tranche price for this epoch based on underlyings that will be received on claim
    uint256 _epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending;
    if (_epochPrice == 0) {
      revert Is0();
    }
    epochWithdrawPrice[_epoch] = _epochPrice;
    // set pending withdraw requests to 0
    epochPendingWithdrawals[_epoch] = 0;
    // set pending claims to the amount of underlyings requested
    epochPendingClaims[_epoch] = _underlyingsRequested;
    // set flag for pending claims to true
