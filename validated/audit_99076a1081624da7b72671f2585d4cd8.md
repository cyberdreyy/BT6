### Title
Post-default instant-withdraw receipts are recorded under the already-finalized `defaultRecoveryEpoch` and paid from the recovery reserve without a finalized "unsafe" marker - (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`requestWithdraw` has an explicit `defaultRecoveryFinalized` branch that routes post-default receipts into `postDefaultRequests` with their own 1:1 pricing, but `requestInstantWithdraw` has no equivalent marking. A post-finalization instant request is silently attributed to `epochNumber`, which still equals `defaultRecoveryEpoch` after default. Depending on `defaultInstantWithdrawsFinalized`, the receipt is either paid from the default recovery reserve it was never included in, or falls through to the par/funded path and freezes.

### Finding Description
- `requestInstantWithdraw` (IdleCreditVault.sol:356-375) burns CDO strategy tokens, mints a receipt, and records `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount` plus `instantWithdrawClaimsByEpoch[epochNumber]` and `pendingInstantWithdraws`, with no `defaultRecoveryFinalized` check — unlike `requestWithdraw` (lines 247-258) which marks post-default receipts via `postDefaultRequests`. This is the analog of the missing `Content-Disposition` marker: the receipt is created in an "unsafe" (defaulted) context but carries no flag distinguishing it from a funded/normal receipt.
- After `finalizeDefaultRecovery`, `epochNumber` no longer advances, so `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` accumulates new receipts under the finalized epoch.
- `claimInstantWithdrawRequest` (lines 380-393) only applies the recovery haircut when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`:
  - If `defaultInstantWithdrawsFinalized == true`, `_claimDefaultedInstantWithdrawRequest` (lines 842-856) pays `claimBasis * defaultRecoveryPrice / 1e18` and decrements `defaultRecoveryReserve`. The new receipt's basis was never part of `totalBasis` in `finalizeDefaultRecovery` (lines 679-688), so each such claim withdraws reserve that was sized only for pre-finalization claimants. Legitimate defaulted claimants then revert on `defaultRecoveryReserve -= _amount` underflow in `_transferDefaultRecovery` (line 915).
  - If `defaultInstantWithdrawsFinalized == false` (finalized with `pendingInstantWithdraws == 0`), the receipt falls through to the funded path and hits the reserve guard in `_transferFundedClaim` (lines 897-907): since post-default strategy balance ≈ `defaultRecoveryReserve`, `balance - reserve < amount` reverts, permanently freezing the requester's receipt.

### Impact Explanation
Case (a): an unprivileged tranche-token holder creates instant-withdraw receipts after default finalization and drains `defaultRecoveryReserve` up to `defaultRecoveryPrice` per unit of receipt, causing insolvency for pre-default claimants whose `totalBasis` legitimately funded that reserve. Theft is bounded by the reserve but each wei stolen is a wei a defaulted claimant cannot recover — direct theft + permanent freezing of victim claims. Case (b): the requester's own funds are permanently frozen (no path to claim or re-request, since receipts are address-bound).

### Likelihood Explanation
Requires the pool to reach `defaulted()` + `finalizeDefaultRecovery`, and requires the CDO to still route `requestInstantWithdraw` after default (i.e., instant withdrawals not explicitly disabled while `defaulted()` — the strategy itself imposes no such gate, so the guard depends on `IdleCDOEpochVariant` behavior, which I could not fully verify within this review). No privileged misbehavior is needed; a KYC'd tranche holder suffices. Likelihood hinges on that single external gate.

### Recommendation
Mirror the `requestWithdraw` post-default branch in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert the request or route it into a post-default bucket (e.g., extend `postDefaultRequests`) that is paid 1:1 only against newly funded underlying, never against `defaultRecoveryReserve` or under `instantWithdrawsRequestsByEpoch[defaultRecoveryEpoch]`. Alternatively, key instant claims on a dedicated post-default epoch marker rather than reusing `defaultRecoveryEpoch`.
