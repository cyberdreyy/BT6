## Title
Silent `u32`→`u8` truncation when converting stored/BigTable protobuf transaction metadata back into RPC types can misreport token-balance account indices and inner-instruction indices - (File: `storage-proto/src/convert.rs`)

### Summary
`storage-proto/src/convert.rs` converts long-term/BigTable-stored protobuf transaction metadata (`generated::TokenBalance`, `generated::InnerInstructions`, which store `account_index`/`index` as `u32`) back into the internal RPC types `TransactionTokenBalance`/`InnerInstructions` (which use `u8`) via an unchecked `as u8` cast: [1](#0-0) [2](#0-1) 

This is the same bug class as the audited Sherlock finding: a value that is legitimately wider than the destination type is downcast without any bounds check, silently wrapping/truncating instead of erroring, resulting in incorrect data being reported to the caller.

### Finding Description
The protobuf schema intentionally stores `account_index`/`index` as `u32` (a wider type than the in-process representation), presumably to be forward-compatible with values that could exceed `u8::MAX`: [3](#0-2) [4](#0-3) 

However, the reverse conversions (protobuf → internal type), used when reading transactions/blocks back out of BigTable/long-term storage for RPC responses, cast with `value.account_index as u32 as u8` and `value.index as u8`. There is no `TryFrom`/bounds check and no error path — any value ≥ 256 wraps modulo 256, silently producing a *different, valid-looking* `account_index`/`index` rather than failing.

Compare this to the SVM-side collection code, which explicitly guards this exact conversion with a fallible `try_into()`: [5](#0-4) 

That guarded path proves that the maintainers recognize the index can legitimately not fit into a `u8` and choose to drop the token-balance record entirely rather than mis-tag it. The `storage-proto` reverse-conversion path was not given the same protection.

These `TransactionTokenBalance`/`InnerInstructions` values feed directly into JSON-RPC responses for `getTransaction`, `getConfirmedTransaction`, and `getBlock` when historical data is served from Bigtable long-term storage (`bigtable_ledger_storage`), which is reachable by any unprivileged RPC client that requests an old/archived transaction or block.

### Impact Explanation
If a stored protobuf record's `account_index` (for pre/post token balances) or `index` (for inner instructions) is ≥ 256 — which the schema explicitly allows for by using `u32` — the truncating cast silently maps it to `value % 256`, producing:
- A `pre_token_balances`/`post_token_balances` entry attributed to the *wrong* account index in the transaction's account-keys list, or
- An `inner_instructions` entry attributed to the *wrong* top-level instruction index.

This is a "wrong data returned to a query" outcome: a single, unprivileged `getTransaction`/`getBlock` RPC call against historical data can receive a response that misattributes token balance changes or inner-instruction groupings to the wrong account/instruction, with no error or warning surfaced to the client. This can mislead indexers, exchanges, and explorers that rely on `pre/postTokenBalances` and `innerInstructions` correctness for account reconciliation.

### Likelihood Explanation
Likelihood depends on whether any legitimate transaction has ever produced (or could produce) an `account_index`/`instruction index` ≥ 256 that was serialized into BigTable with the wider `u32` protobuf field before being read back. Because the protobuf format deliberately uses `u32` (wider than the `u8` used elsewhere in the client-facing types), this indicates the authors anticipated the possibility of values exceeding `u8::MAX` at least at the storage layer. Whether the current transaction/message format can actually produce such indices at the SVM layer is uncertained from what I could confirm — I was not able to fully verify the maximum possible size of `account_keys` for a v0 message with multiple address-lookup tables within the remaining investigation budget, so I cannot claim this is trivially triggerable today. This is a defense-in-depth / robustness gap rather than a confirmed exploit path, and it also cannot be forced to occur via a single RPC call by an attacker who doesn't control block production/history recording — it can only surface for whatever historical data already exists (or will exist) in BigTable.

### Recommendation
Replace the unchecked `as u8` casts in `storage-proto/src/convert.rs` (`generated::InnerInstructions` → `InnerInstructions`, `generated::TokenBalance` → `TransactionTokenBalance`) with fallible conversions (`u8::try_from`), mirroring the pattern already used in `svm/src/transaction_balances.rs::SvmTokenInfo::unpack_token_account`. On conversion failure, either drop the malformed entry (consistent with the SVM path) or surface an explicit decode error rather than silently returning wrapped/incorrect data.

### Proof of Concept
Not independently reproducible from the index alone — this would require constructing/injecting a `generated::TokenBalance { account_index: 256, .. }` or `generated::InnerInstructions { index: 256, .. }` protobuf message (e.g., via a BigTable-backed ledger-storage tool) and observing that `TransactionTokenBalance::from(...)`/`InnerInstructions::from(...)` in `storage-proto/src/convert.rs:662-669,688-715` yields `account_index == 0` / `index == 0` instead of erroring, which a subsequent `getTransaction`/`getBlock` RPC call would then return verbatim.
