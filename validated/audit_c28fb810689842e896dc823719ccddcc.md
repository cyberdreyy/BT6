### Title
Rejection weight never cleared on flip-to-accept lets phantom rejected-weight abort a legitimately-supported block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
In `StackerDBListener::run`, the two aggregate counters `BlockStatus.total_weight_approved` and `BlockStatus.total_weight_rejected` are maintained independently and are never reconciled against each other. When a signer's slot first carries a `Rejected` `BlockResponse` and later, for the *same* block hash, carries an `Accepted` response (a state transition the signer protocol explicitly allows, per `docs/signer-flows.md` §2: `LocallyRejected --> LocallyAccepted : re-evaluated`), the rejected-branch weight contribution is never subtracted. The signer's weight ends up counted in both `total_weight_rejected` and `total_weight_approved` simultaneously.

### Finding Description
`StackerDBListener` tallies weight per `BlockStatus` keyed by `signer_signature_hash`:

- On `BlockResponse::Accepted`, weight is added to `total_weight_approved` only once per `slot_id`, guarded by `!block.gathered_signatures.contains_key(&slot_id)`, and `slot_id` is inserted into `responded_signers` [1](#0-0) .
- On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` guarded only by `block.responded_signers.insert(slot_id)` (i.e., "have we ever recorded a response from this slot for this block") [2](#0-1) .

Neither branch removes or decrements the *other* counter when a signer's slot is later observed with the opposite verdict for the same `block_sighash`. Because each signer writes to a single fixed StackerDB slot that can be overwritten (Reject now, Accept later, following the documented `LocallyRejected -> LocallyAccepted` re-evaluation path, e.g., after a stale conflict clears — see `docs/signer-flows.md` lines 144-145, 301-341), the listener will process both events across two `StackerDBChunksEvent`s and increment both tallies for the same signer's weight. There is no code path that clears a stale `total_weight_rejected` contribution once that signer's later Accepted message is processed; the only reset mechanism found is `reset_rejections`, which is invoked solely on a rejection-timeout in `signer_coordinator.rs`'s `get_block_status`, not on a per-signer vote flip [3](#0-2) .

This breaks the intended invariant that `total_weight_approved` and `total_weight_rejected` are disjoint, verified-per-signer tallies whose sum cannot exceed `total_weight`. It is directly analogous to the Tapioca `totalBorrow` bug: a per-user state update (`userBorrowPart[user]`) is applied without updating the aggregate/global counter (`totalBorrow`), corrupting subsequent aggregate-based decisions. Here, the per-signer vote update (accept after reject) is applied without retracting the previous contribution to the aggregate rejected-weight counter, corrupting the aggregate-vs-verified-accepts equality that the coordinator relies on for its accept/reject decision.

### Impact Explanation
`SignerCoordinator::get_block_status` checks the reject condition *before* the accept condition each polling iteration:

```
total_weight_rejected.saturating_add(weight_threshold) > total_weight   => SignersRejected
else total_weight_approved >= weight_threshold                          => accepted
``` [4](#0-3) 

Because `total_weight_rejected` can retain phantom weight from a signer who has since switched to Accepted for that exact block, the miner can conclude `SignersRejected` for a block that has, in reality, already reached (or is about to reach) the 70% approval threshold with fully verified, up-to-date signatures. This is a liveness break of the miner/coordinator's accept path: it wedges block production against a block that legitimately has enough support, forcing the miner to abandon a valid block and re-propose, and it is triggerable by the ordinary, protocol-sanctioned re-evaluation behavior of a single signer (no majority collusion required) — it does not even require malice, only one signer changing its mind after a stale-conflict resolution while the miner is still polling. This matches the rule category "aggregated-weight vs verified-accepts" equality break.

Note: this does not on its own cause a signer to produce an invalid/non-canonical signature (the accept tally itself is still gated one-per-slot on real signatures), so the safety side of the invariant is not violated; the concrete consequence is the liveness-side miscount feeding the miner's reject/accept branch.

### Likelihood Explanation
The precondition is common under normal signer-flow operation: any signer whose earlier rejection reason becomes re-evaluable (per `should_reevaluate_reject_reason`/`should_reevaluate_block`, documented in `docs/signer-flows.md`) will naturally flip from `LocallyRejected` to `LocallyAccepted` and re-broadcast an `Accepted` `BlockResponse` for the same block hash while the miner is still actively polling `get_block_status` for that same block (a window that can last up to the rejection timeout). No majority collusion, no forged keys, and no protocol violation are required — just ordinary timing between a signer's re-evaluation and the miner's polling window.

### Recommendation
Track, per `BlockStatus`, the last known vote value per `slot_id` (accept vs reject) instead of independent one-shot flags, and when a slot's vote flips, subtract its weight from the previous tally before adding it to the new one, e.g.:

```rust
// on Accepted:
if let Some(prev) = block.vote_by_slot.insert(slot_id, Vote::Accepted) {
    if prev == Vote::Rejected {
        block.total_weight_rejected = block.total_weight_rejected.saturating_sub(signer_entry.weight);
    }
}
// analogous subtraction of total_weight_approved on a later Rejected message
```
so that `total_weight_approved + total_weight_rejected` always reflects the weight of currently-held, non-overlapping votes rather than an ever-growing union of every vote ever seen.

### Proof of Concept
1. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for block `B`. `stackerdb_listener.rs` records `total_weight_rejected += w` and `responded_signers.insert(slot_id)` [2](#0-1) .
2. Miner's `SignerCoordinator::get_block_status` polls and sees `total_weight_rejected` rising but not yet breaching `total_weight - weight_threshold`.
3. Signer `S`, per the sanctioned `LocallyRejected -> LocallyAccepted` re-evaluation path (`docs/signer-flows.md` lines 144-145), re-evaluates `B` as valid (e.g., a conflicting block it had blocked on went stale) and sends `BlockResponse::Accepted` for the *same* `B`.
4. `stackerdb_listener.rs` processes the new event: `gathered_signatures` does not yet contain `slot_id`, so it adds `total_weight_approved += w` [1](#0-0) . `total_weight_rejected` is left untouched at its old, now-stale value.
5. Now `total_weight_approved + total_weight_rejected > total_weight` is possible with enough such flips, and — critically — if enough *other, unrelated* signers also reject in the meantime, the stale `w` contribution can push `total_weight_rejected` over `total_weight - weight_threshold` even though the real, current rejecting weight (excluding `S`, who now accepts) would not have crossed that bound, causing `SignersRejected` to fire on a block that in reality still has a path to (or has already reached) 70% approval. [5](#0-4)
