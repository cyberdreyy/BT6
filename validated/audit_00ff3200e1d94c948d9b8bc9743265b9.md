### Title
Stale per-epoch instant-withdraw receipts inflate the default claim basis and corrupt recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` removes a user's instant-withdraw receipt from the aggregate ledger (`instantWithdrawsRequests[_user] = 0`) and pays out, but never clears the per-epoch bookkeeping entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults later in the same epoch, `defaultPendingClaimBasis()` counts those already-paid receipts as defaulted claims, inflating the recovery basis, diluting `defaultRecoveryPrice` for all victims, and then making the already-paid user's defaulted-claim path revert on underflow — freezing their share of the recovery reserve.

### Finding Description
The kernel bug class is "removed from the list before fully unmapped": an object is unlinked from one structure while a second structure still references it, so teardown/accounting sees inconsistent state. The analog lives in `IdleCreditVault`:

- `requestInstantWithdraw` writes three ledgers: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` (`contracts/strategies/idle/IdleCreditVault.sol:366-374`).
- `claimInstantWithdrawRequest` burns the receipt, zeroes only `instantWithdrawsRequests[_user]`, and calls `_transferFundedClaim` (`:387-392`). The two per-epoch mappings are never cleared on the funded path; they are only cleared in `_claimDefaultedInstantWithdrawRequest` (`:847-853`).
- On default finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (`:644-649`). That aggregate still contains amounts users already claimed at par, so `totalBasis` in `finalizeDefaultRecovery` is overstated and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is pushed down for every claimant (`:679-688`).
- After finalization, when the already-paid user calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — still nonzero — then executes `instantWithdrawsRequests[_user] -= claimBasis` (`:844-848`). Since the funded path already set that counter to 0, the subtraction underflows and reverts, permanently blocking that user's defaulted-epoch clearing and leaving `instantWithdrawClaimsByEpoch[defaultEpoch]` inconsistent. If the user re-requested a smaller instant withdraw in the same epoch after claiming, `claimBasis` exceeds the new balance and still underflows.

The broken invariant is "one receipt, one payout / consistent teardown": the receipt is burned and paid, but the epoch-level teardown structures still treat it as outstanding debt.

### Impact Explanation
Two concrete harms, both with fund impact, in the defaulted/finalized phase:

1. Recovery dilution (theft-by-miscounting): every already-claimed instant withdrawal included in `instantWithdrawClaimsByEpoch[epochNumber]` inflates `totalBasis`, lowering `defaultRecoveryPrice` for all genuine defaulted-epoch claimants (normal, APR0, and instant). Recovered funds that should go to real victims are instead reserved against phantom claims that can never be paid out (the paying path underflows), so the difference sits as stranded reserve dust while victims take a larger haircut than warranted.
2. Permanent freezing: the double-counted user's claim reverts on `instantWithdrawsRequests[_user] -= claimBasis` underflow, permanently locking both their legitimate recovery payout and the associated `instantWithdrawClaimsByEpoch` decrement.

Quantification: if instant withdrawals of amount X were claimed at par in the default epoch and `pendingInstantWithdraws != 0` at finalization, the recovery basis is overstated by X, so `defaultRecoveryPrice` is scaled by `totalBasis / (totalBasis + X)` — a direct, quantifiable loss to all other claimants proportional to the phantom basis.

### Likelihood Explanation
Likelihood is moderate. Preconditions: instant withdrawals enabled (`setInstantWithdrawParams`, honest manager action), a user claims an instant withdrawal funded via `collectInstantWithdrawFunds`, and the borrower defaults in the *same* epoch while `pendingInstantWithdraws` is still nonzero (partially unfunded instant queue — explicitly contemplated by the code comments at `:636-640` and `_defaultPrefundedInstantReserve`). No malicious privileged role is required: the triggering sequence is an ordinary user claim plus a borrower default, both in-scope events. The stale-ledger write is unconditional — it happens on every successful funded instant claim.

### Recommendation
In `claimInstantWithdrawRequest`, mirror the teardown performed in `_claimDefaultedInstantWithdrawRequest`: when paying a funded receipt, also decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` for the epoch(s) the receipt belongs to (track the request epoch at request time, analogous to `lastWithdrawRequest`), and reconcile with `pendingInstantWithdraws` so funded and unfunded portions stay consistent. Alternatively, clear per-epoch entries in `collectInstantWithdrawFunds` when the CDO funds the queue, so `instantWithdrawClaimsByEpoch` always equals still-outstanding basis.
