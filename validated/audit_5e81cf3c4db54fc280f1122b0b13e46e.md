### Title
Signer's global-state (v2) proposal check never verifies the current miner's timeout deadline before validating/signing a block — ([File: stacks-signer/src/chainstate/v2.rs])

### Summary
`GlobalStateView::check_proposal` (v2 chainstate) validates a block proposal against the signer's locally cached `MinerState::ActiveMiner` view, but it never calls `SortitionState::is_timed_out` to check whether the "active" miner's `block_proposal_timeout` deadline has already elapsed. The v1 chainstate path performs this exact check inline, at the top of `check_proposal`, before doing any other validation. This asymmetry lets a miner whose proposal window has already expired still get its (late) block validated and signed under the v2 path.

### Finding Description
In `stacks-signer/src/chainstate/v1.rs`, `SortitionsView::check_proposal` begins by checking whether the current miner has already timed out: [1](#0-0) 

If the timeout has elapsed, the sortition is marked `InvalidatedBeforeFirstBlock` and, if the proposal in question is for that same sortition, the proposal is rejected immediately with `RejectReason::InvalidMiner` — *before* any other check runs.

In `stacks-signer/src/chainstate/v2.rs`, the equivalent entry point `GlobalStateView::check_proposal` performs consensus-hash, pubkey, bitvec, tenure-change and tenure-extend checks, but at no point calls `SortitionState::is_timed_out`: [2](#0-1) 

The only place `SortitionState::is_timed_out` (v2 variant) is defined and used is: [3](#0-2) 

and per the documented event flow, this function is invoked exclusively from the asynchronous housekeeping path (`check_miner_inactivity`, triggered by burn-block events/ticks), not from the synchronous per-proposal `check_proposal` call: [4](#0-3) 

This means the equality the protocol relies on — "the signer's notion of the active miner is only valid while it has not exceeded `block_proposal_timeout`" — is enforced synchronously in v1 but only enforced *eventually* (on the next housekeeping tick) in v2. Between the moment the miner's deadline elapses and the next housekeeping tick that would flip `MinerState` away from `ActiveMiner`, a v2 signer's `check_proposal` will still treat that miner as valid and proceed to submit/sign a late block.

### Impact Explanation
This breaks the "signer signing an invalid/non-canonical block" invariant: the timeout mechanism exists specifically so that, once a miner is unresponsive past its allotted window, signers stop trusting that miner and fall back to the prior tenure (`FALL["fall back to prior tenure"]` in the housekeeping flow). A one-slot miner that intentionally proposes a block just past `block_proposal_timeout` but before the local housekeeping tick fires can have that late proposal validated and signed by v2-mode signers, while other signers whose housekeeping already ticked will have moved on to a different miner/tenure. This produces divergent views across the signer set on which block/tenure is canonical for that height — a concrete safety break (signing a block that should have been rejected as belonging to an already-invalidated miner), not merely a theoretical race.

### Likelihood Explanation
This requires no majority collusion — a single miner (the current tenure's winning miner) controls exactly when it submits its proposal and can trivially time it to land in the housekeeping gap. Since `check_miner_inactivity`/housekeeping runs on its own cadence rather than being invoked synchronously as part of `handle_block_proposal`/`check_proposal`, this gap is a normal operating condition, not a rare corner case.

### Recommendation
Move (or duplicate) the `SortitionState::is_timed_out` check into `GlobalStateView::check_proposal` itself, mirroring the v1 behavior: evaluate the timeout for the block's tenure/sortition synchronously as part of proposal validation, and reject with `RejectReason::InvalidMiner` (or invalidate the `MinerState::ActiveMiner` for that tenure) if the deadline has passed, rather than relying solely on the separate housekeeping tick to update `MinerState`.

### Proof of Concept
1. Signer boots with the v2/global-state signer protocol active; local `SignerStateMachine.current_miner` is `MinerState::ActiveMiner` for the current tenure.
2. The tenure's miner goes silent past `config.block_proposal_timeout`, but the signer's housekeeping tick (`handle_pending_update`/`check_miner_inactivity`) has not yet fired for this instance (e.g., no new burn block has arrived, or the periodic tick simply hasn't hit yet).
3. The (still-registered-as-active) miner now broadcasts a block proposal for the timed-out tenure.
4. `handle_block_proposal` → `check_block_against_global_state` → `GlobalStateView::check_proposal` runs: it never calls `SortitionState::is_timed_out`, so as long as consensus-hash/pubkey/bitvec/tenure checks pass, the proposal is accepted for validation/signing — even though it has already exceeded `block_proposal_timeout` and, under v1 semantics, would have been rejected with `InvalidMiner`.
5. Signers still on the pre-timeout `ActiveMiner` view sign the late block, while any signer whose housekeeping already advanced (or another signer entirely) has moved on — producing conflicting signed states for the same tenure/height.

impl SortitionState {
    /// Check if the sortition identified by the ConsensusHash is timed out based on
    /// the blocks within the signer db and the block proposal timeout
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        signer_db: &SignerDb,
        eval: &GlobalStateEvaluator,
        local_address: &StacksAddress,
        timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = signer_db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) =
            signer_db.get_burn_block_received_time_from_signers(eval, sortition, local_address)?
        else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = signer_db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };
        if elapsed > timeout {
            info!("Sortition has timed out";
                "sorition" => %sortition,
                "timeout" => %timeout.as_secs(),
                "elapsed" => %elapsed.as_secs()
            )
        }
        Ok(elapsed > timeout)
    }
