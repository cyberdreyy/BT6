### Title
`promise_batch_action_function_call_weight` zero-balance subsidy check is stateless per-call and can be claimed unlimited times within a single receipt execution - ([File: runtime/near-vm-runner/src/logic/logic.rs])

### Summary
The `skip_deduct` branch in `promise_batch_action_function_call_weight` (logic.rs:3101-3112) decides whether to subsidize a 1-yoctoNEAR deposit purely by re-checking `self.result_state.current_account_balance.is_zero()` at the moment of each call, without ever decrementing `current_account_balance` when the subsidy path is taken. Because the balance is left untouched by the subsidized branch, every subsequent `amount == 1` call in the same receipt execution observes the same zero balance and is independently routed into `subsidized_amount` again, with no per-receipt cap.

### Finding Description
```rust
let skip_deduct = amount == Balance::from_yoctonear(1)
    && self.config.one_yocto_on_promise
    && self.result_state.current_account_balance.is_zero();
if skip_deduct {
    self.result_state.subsidized_amount = self
        .result_state
        .subsidized_amount
        .checked_add(amount)
        .expect("subsidized_amount overflow");
} else {
    self.result_state.deduct_balance(amount)?;
}
``` [1](#0-0) 

The intent, per the adjacent comment, is to let a contract account with zero balance still attach exactly 1 yoctoNEAR to a promise (e.g. to satisfy `ft_transfer_call`-style one-yocto assertions) without an actual balance deduction. However, the check is evaluated fresh on every call to this host function and only reads `current_account_balance`; when the subsidized branch is taken, `deduct_balance` is skipped entirely, so `current_account_balance` never changes as a result of this call. Consequently, if a contract's balance is (or becomes, e.g. via an earlier `Transfer` action in the same batch) exactly zero, every later `promise_batch_action_function_call_weight(amount=1)` call within the same `FunctionCall` execution will independently re-satisfy `is_zero()` and add another 1 yoctoNEAR into `subsidized_amount`, rather than being limited to a single subsidized instance per receipt. There is no counter, flag, or “already subsidized once” guard visible in this function to prevent repeated claims.

An unprivileged attacker who deploys their own contract can trigger this purely through self-authored wasm: perform actions (or simply start from a zero-balance state) that leave `current_account_balance` at zero, then invoke `promise_batch_action_function_call_weight` with `amount = 1` multiple times (across one or several promise batches) inside the same host-function execution. Each call is gas-metered normally (`pay_action_base`/`pay_action_per_byte`/`prepay_gas` all still execute), so the attacker pays ordinary gas costs but is not required to fund the account balance for the deposits it attaches.

### Impact Explanation
This breaks the invariant that a receipt's `subsidized_amount` should reflect at most one genuinely-uncovered 1-yoctoNEAR deposit per zero-balance opportunity; instead it can be incremented arbitrarily many times off a single momentary zero-balance state. Downstream, each subsidized call still results in `ext.append_action_function_call_weight` attaching a real 1-yoctoNEAR deposit to the outgoing action without the corresponding deduction from the sender's account, i.e. value is granted to receiving promises without a matching debit. This is a balance-accounting/token-supply integrity issue (Balance manipulation / potential inflation category), though the per-call value (1 yoctoNEAR = 10⁻²⁴ NEAR) is economically negligible per instance and only accumulates linearly with the number of calls the attacker is willing to pay gas for.

### Likelihood Explanation
Preconditions are attacker-controlled and require no privileged access: deploy a contract, get its balance to zero (or exploit an account that is already at zero balance at that point in execution), and issue multiple `promise_batch_action_function_call_weight(amount=1)` calls in one execution. The attacker pays normal gas fees for each call, so the only cost is gas; the resulting exploitable balance-side-effect (unbounded subsidized yoctoNEAR credits) is repeatable in any transaction and does not require validator/node privileges, leaked keys, or social engineering.

### Recommendation
Track whether the zero-balance subsidy has already been granted within the current receipt/execution context (e.g. a one-shot flag or a strict cap on `subsidized_amount` per receipt, such as `subsidized_amount == 0` before allowing `skip_deduct`), rather than re-deriving eligibility solely from the current (unchanged) `current_account_balance`. Alternatively, ensure the subsidized branch still performs bookkeeping that changes the state checked by later calls (e.g., mark the account as "already subsidized this receipt") so repeat claims are rejected.

### Proof of Concept
1. Construct a `VMLogic` test harness (as used in `runtime/near-vm-runner/src/logic/tests/promises.rs`) with `config.one_yocto_on_promise = true` and `result_state.current_account_balance` set to zero.
2. Create two promise batches (or reuse one) and call `promise_batch_action_function_call_weight` twice, each with `amount_ptr` pointing to a 1-yoctoNEAR value.
3. Assert `result_state.subsidized_amount == 2` (yoctoNEAR) after the two calls, demonstrating the subsidy was claimed twice off a single unchanging zero-balance state.
4. Cross-check against `runtime/runtime/src/lib.rs` receipt-processing logic that consumes `subsidized_amount` to confirm no corresponding real balance deduction occurred for either call, validating that the sender's account balance is not reduced for the second deposit while both deposits are still forwarded to the receiving promises.
