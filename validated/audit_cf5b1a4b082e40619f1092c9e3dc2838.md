### Title
Metrics endpoint uses non-constant-time token comparison enabling timing side-channel - ([File: core/web/router.go])

### Finding Description
The metrics/debug endpoint registered via `prometheusUse` is protected by `prometheusHandler`, which authenticates requests by comparing the `Authorization` header against an expected `"Bearer " + token` string using Go's native `!=` operator: [1](#0-0) . This is a plain byte-wise/length-short-circuiting comparison, not a constant-time comparison (e.g. `subtle.ConstantTimeCompare` or `crypto/hmac.Equal`), which the codebase does use elsewhere for credential checks, e.g. in `core/sessions/session.go`, `core/bridges/bridge_type.go`, `core/bridges/external_initiator.go`. This route is wired in from `NewRouter` via `prometheusUse(prometheus, engine, ...)` when a `*ginprom.Prometheus` is supplied [2](#0-1)  and registered directly on the top-level `*gin.Engine` (not behind the `rateLimiter`/session group used for `/v2` and other API routes) via `e.GET(p.MetricsPath, prometheusHandler(p.Token, h))` [3](#0-2) .

An unauthenticated attacker reaching the node API port can therefore send repeated requests to the metrics path with varying `Authorization: Bearer <guess>` values and, in principle, use response-time differences to infer the correct token byte-by-byte, since Go string `!=` comparisons are not guaranteed constant-time and typically short-circuit on the first mismatching byte.

### Impact Explanation
If successfully exploited, this would let an attacker authenticate to the Prometheus metrics/debug handler without the correct token, exposing whatever the underlying `promhttp` handler and `metricRoutes`/`pprof` group expose (process metrics, and if `/debug/pprof` is reachable through this same path, potentially goroutine/heap/CPU profiling data). Note that `/debug/pprof` routes registered through `metricRoutes` are mounted under the authenticated `authv2` group (session/token auth required) [4](#0-3) , not under this Bearer-token metrics handler, so the scope reachable via this specific token check is limited to `p.MetricsPath` (Prometheus metrics only). The question's claim of "Critical — node blockchain private keys, key export bundles or node secrets retrieved from a running node" is not substantiated by the code: the `/metrics` endpoint served here does not return private keys, key export bundles, or secrets — it returns Prometheus counters/gauges via `promhttp.HandlerFor`. The realistic impact of a successful bypass is unauthorized disclosure of internal operational metrics (an information-disclosure issue), not direct key/secret theft.

### Likelihood Explanation
Exploiting this as a genuine timing side-channel over a network HTTP connection is difficult in practice: network jitter, TLS/HTTP framing overhead, and Go's/OS's non-deterministic scheduling generally dominate any nanosecond-level timing differences from a short string comparison, making remote byte-by-byte token recovery highly impractical without an unusually low-noise, low-latency vantage point (e.g., same host/LAN) and a very large number of samples. There is also no rate limiting on this specific route (it's registered on the bare `engine`, outside `rateLimiter`), which removes one practical obstacle, but the fundamental signal-to-noise problem for a real remote timing attack remains the primary hurdle it does not have any brute-force protection.

### Recommendation
Replace the raw string comparison in `prometheusHandler` with a constant-time comparison, e.g.:
```go
if subtle.ConstantTimeCompare([]byte(header), []byte(bearer)) != 1 {
    c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
    return
}
```
Additionally consider placing this endpoint behind the existing `rateLimiter` middleware to reduce brute-force/timing-sampling opportunities, consistent with other unauthenticated routes in `NewRouter`.

### Proof of Concept
Unit test plan (`core/web/router_test.go` or similar):
1. Call `prometheusHandler("expectedtoken1234", dummyHandler)` with a `gin.Context` where `Authorization: Bearer expectedtoken1234` — assert 200/handler invoked.
2. Call it with `Authorization: Bearer Xxpectedtoken1234` (single first-byte mismatch) vs. `Authorization: Bearer expectedtoken1234X` (mismatch at the end) and measure comparison time via `testing.Benchmark` over many iterations to demonstrate early-exit timing variance in the `!=` comparison, contrasted with a `subtle.ConstantTimeCompare`-based version showing flat timing regardless of mismatch position.
3. Assert functional behavior only changes for the fix (401 for any non-exact match) — this validates the fix does not break existing auth semantics while removing the timing signal.

Note: this PoC demonstrates the code-level absence of constant-time comparison; it does not demonstrate a practical remote key-theft exploit, since the endpoint gated by this token does not serve keys or secrets.

```go
func prometheusUse(p *ginprom.Prometheus, e *gin.Engine, handlerOpts promhttp.HandlerOpts) {
	var (
		r prometheus.Registerer = p.Registry
		g prometheus.Gatherer   = p.Registry
	)
	if p.Registry == nil {
		r = prometheus.DefaultRegisterer
		g = prometheus.DefaultGatherer
	}
	h := promhttp.InstrumentMetricHandler(r, promhttp.HandlerFor(g, handlerOpts))
	e.GET(p.MetricsPath, prometheusHandler(p.Token, h))
	p.Engine = e
}
```
