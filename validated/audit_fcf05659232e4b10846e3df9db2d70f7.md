### Title
Secp256k1 signature malleability in precompile/syscall enables replay of nonce-style anti-replay checks in on-chain programs - ([File: precompiles/src/secp256k1.rs], [File: syscalls/src/lib.rs])

### Summary
Agave's `secp256k1` native program precompile and the `sol_secp256k1_recover` syscall both accept ECDSA signatures without enforcing canonical (low-`s`) form, so for any valid `(r, s)` signature the alternate `(r, -s mod n)` signature (with the flipped recovery id) is also accepted as valid for the same message and pubkey/eth-address. This is the exact same malleability bug class as the Sherlock report on Titles' `TitlesGraph.checkSignature`, where a signature hash is used as a unique/used marker for authorization/anti-replay.

### Finding Description
The precompile verification routine `agave_precompiles::secp256k1::verify` parses the signature with `libsecp256k1::Signature::parse_standard_slice` and recovers the signer address without ever checking that `s` is in the lower half of the curve order [1](#0-0) . The crate's own test explicitly demonstrates and documents this: flipping the `s` value (and complementary recovery id) produces `alt_signature`, a distinct but fully valid signature for the same message/eth-address pair, and both pass `verify()` [2](#0-1) .

The same lack of canonicalization exists in the `SyscallSecp256k1Recover` builtin function that BPF programs invoke directly via `sol_secp256k1_recover`: it parses the signature with `libsecp256k1::Signature::parse_standard_slice` and calls `libsecp256k1::recover` with no `s`-value bound check [3](#0-2) . The SBF test suite for this syscall (`programs/sbf/rust/secp256k1_recover`) has a dedicated `test_secp256k1_recover_malleability` test proving that the flipped-`s` alternate signature recovers to the identical public key [4](#0-3) .

Any ordinary user-deployed program that uses either the secp256k1 native program (for verifying externally-signed ECDSA messages, e.g., Ethereum-style meta-transactions) or the `sol_secp256k1_recover` syscall, and that treats the raw signature bytes (or a hash of them) as a unique nonce/anti-replay identifier — exactly the pattern flagged in the Titles report — is directly vulnerable: an attacker (or the original signer) can derive a second, distinct valid signature for the same message by negating `s` and flipping the recovery id, bypassing any "signature already used" check keyed on the signature bytes.

### Impact Explanation
This is a reachable state-mutation bypass for any program built on top of Agave's secp256k1 precompile/syscall that relies on signature uniqueness for single-use authorization (e.g., withdrawal approvals, cross-chain bridge relays, one-time claims, meta-tx nonces). Because Agave provides no malleability protection at the platform level (neither the precompile nor the syscall enforce canonical `s`), every program that follows the common "hash the signature to mark it used" pattern inherits this replay/double-spend vulnerability, mirroring the exact impact described in the referenced Sherlock report (bypassing a single-acknowledgment restriction).

### Likelihood Explanation
High likelihood of being exploitable in practice wherever it's used: the malleable alternate signature is trivial and deterministic to compute from any observed valid signature (negate `s` mod the curve order, XOR the recovery id), requiring no additional secrets or brute force. The behavior is deterministic and already exercised/asserted as "working as intended" by Agave's own tests, meaning downstream program authors have no platform-level warning or guard preventing them from making the same signature-as-nonce mistake that Titles made.

### Recommendation
Add canonical/low-`s` (and, optionally, malleability) validation to both `agave_precompiles::secp256k1::verify` and `SyscallSecp256k1Recover`, rejecting signatures whose `s` exceeds `secp256k1n/2`, and clearly document in the syscall/program interfaces that raw ECDSA signatures must never be used as unique replay-protection identifiers without this canonicalization (or an explicit nonce should be required instead of relying on signature bytes).

### Proof of Concept
The existing `test_malleability` test in `precompiles/src/secp256k1.rs` [2](#0-1)  and `test_secp256k1_recover_malleability` in `programs/sbf/rust/secp256k1_recover/src/lib.rs` [4](#0-3)  both directly demonstrate: given a valid `(r, s, recovery_id)` signature, negating `s` and flipping `recovery_id` produces a second, distinct, fully-valid signature that recovers to the same address/pubkey — both are accepted by Agave with no rejection.
