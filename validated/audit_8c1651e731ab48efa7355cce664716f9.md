### Title
Uncapped builder withdrawal amount in committed payload vs. capped CL balance deduction causes unbacked Gwei payout - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` places the full **requested** `BuilderPendingWithdrawal.amount` into the `Withdrawal` object that is committed in `state.payload_expected_withdrawals` (and thus must be honored by the execution layer), while `apply_withdrawals` only decreases the builder's CL-tracked balance by `min(withdrawal.amount, builder_balance)`. When a builder's balance is smaller than the queued withdrawal amount, the execution layer pays the fee recipient the full committed amount, but the beacon state only removes the capped (smaller) amount from the builder's balance, minting unbacked Gwei.

### Finding Description
`get_builder_withdrawals` builds withdrawal entries directly from the queue without capping to the builder's current balance: [1](#0-0) 

`apply_withdrawals`, which runs later in the same `process_withdrawals` call, deducts only the capped amount from the builder's balance: [2](#0-1) 

The committed `Withdrawal.amount` (uncapped, from `get_builder_withdrawals`) is what gets written into `state.payload_expected_withdrawals`, which the execution layer is required to honor as an actual ETH payment to `withdrawal.address`: [3](#0-2) 

The equality that should hold is: *Gwei paid out to a withdrawal address by the execution layer == Gwei removed from the corresponding builder's CL-tracked balance*. Because the payload commitment uses the uncapped requested amount while the balance decrement is capped via `min()`, this equality is broken whenever `builder.balance < withdrawal.amount` at processing time — a state that is explicitly anticipated and tested in-repo: [4](#0-3) 

The test explicitly documents the mismatch: "withdrawal.amount: 5 ETH (requested amount)" is committed to the payload while "builders[0].balance: 0 (deduction capped to available balance)" is only 1 ETH — i.e., 4 ETH of the committed payment is unbacked by any CL balance reduction.

### Impact Explanation
This breaks the invariant that Gwei paid to a party must correspond to Gwei removed from an account inside the beacon state. If `builder.balance` can legitimately fall below a previously-queued `BuilderPendingWithdrawal.amount` (e.g., the builder is charged further pending payments/bids, or multiple queued withdrawals draw down the same balance between queueing and processing), the execution layer will mint/pay the difference to the withdrawal's `fee_recipient` with no corresponding CL-side accounting — a direct case of Gwei being created and paid out, which the scan rules classify as Critical impact ("Gwei created, destroyed or paid to a non-owner").

### Likelihood Explanation
`state.builder_pending_withdrawals` is a queue that can be populated over multiple slots (via `queue_builder_pending_payment`/related bid processing) before being drained by `get_builder_withdrawals`, and a builder's balance can be reduced in the interim by other bid/payment processing acting on the same builder. The repository itself anticipates and unit-tests the "insufficient balance" scenario, confirming this is a reachable state under normal (non-adversarial-client) spec execution, not merely a theoretical edge case.

### Recommendation
Cap the `Withdrawal.amount` produced in `get_builder_withdrawals` to `min(pending_withdrawal.amount, state.builders[builder_index].balance)` at the point the withdrawal object is constructed (mirroring the cap already applied later in `apply_withdrawals`), so that the amount committed to the execution payload can never exceed what is actually deducted from the builder's balance.

### Proof of Concept
1. Builder `B` accumulates `builder_pending_withdrawals` entries (or a single entry) whose total `amount` exceeds `B`'s current `balance` — attainable because payments/other processing between queueing and processing can reduce `B.balance` without correspondingly shrinking already-queued withdrawal amounts.
2. `process_withdrawals` runs: `get_expected_withdrawals` → `get_builder_withdrawals` emits a `Withdrawal(amount=pending.amount)` using the **uncapped** requested amount, per [5](#0-4) .
3. This withdrawal list is stored in `state.payload_expected_withdrawals`, which the execution layer must honor by paying `pending.amount` to `fee_recipient`.
4. `apply_withdrawals` then only decrements `B.balance` by `min(pending.amount, B.balance)`, per [6](#0-5) , leaving `pending.amount - B.balance` Gwei paid out on the EL side with no matching CL-side balance reduction — confirmed by the existing test assertions in [7](#0-6) .

```markdown
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
```
