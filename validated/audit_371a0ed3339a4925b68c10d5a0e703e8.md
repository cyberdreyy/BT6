## Analysis

**Claimed broken binding:** `refunded_deposit_to_predecessor + NEAR_left_on_lockup_account == attached_deposit` (exactly once), which the question claims can be violated if `create_account`/`deploy_contract`/`transfer` succeed but the trailing `function_call("new", …)` panics, leaving stranded funds on the new account while the factory still refunds the full deposit.

**Code path:**

`create()` builds a single promise/action-batch on `lockup_account_id`: `create_account().deploy_contract(CODE).transfer(env::attached_deposit()).function_call(b"new", …)`, followed by a *separate* `.then(ext_self::on_lockup_create(...))` callback receipt. [1](#0-0) 

`on_lockup_create` checks `is_promise_success()`; if false, it refunds the full `attached_deposit` to `predecessor_account_id`. [2](#0-1) 

**Why the premise is false:** `create_account`, `deploy_contract`, `transfer`, and `function_call` chained via `.create_account().deploy_contract().transfer().function_call()` (without intervening `.then()`) are all actions bundled into a **single action receipt** sent to `lockup_account_id`. NEAR's protocol executes the actions in one receipt atomically — if any action in that batch fails (e.g., the `function_call` to `new` panics), the entire receipt fails and none of its state changes (including `create_account`, `deploy_contract`, and the `transfer`) are persisted; the attached balance is not stranded on the target account, and the deposit is returned to the sending contract's balance. This is exactly what the existing unit test `test_create_lockup_rollback` models: it manually bumps `context.account_balance += ntoy(35)` to simulate the deposit flowing back to the factory account when the batched promise fails, then confirms `on_lockup_create` correctly returns `false` and refunds `predecessor_account_id`. [3](#0-2) 

Because the four actions are one atomic receipt rather than independently-committing steps, there is no reachable state where `create_account`/`transfer` "succeeded" while `function_call new` failed and left residual balance on `lockup_account_id`. `is_promise_success()` in the `.then()` callback correctly reflects the all-or-nothing outcome of that receipt, so the refund path in `on_lockup_create` never duplicates funds — the created account either fully exists with its balance (success branch, no refund) or never existed at all (failure branch, full refund, no stranded balance).

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
