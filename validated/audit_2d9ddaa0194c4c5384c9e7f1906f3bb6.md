### Title
Broken sequencer-uptime "invalid round" check allows stale/invalid asset prices to be accepted - ([File: v2/AeraVaultAssetRegistry.sol])

### Summary
`AeraVaultAssetRegistry.spotPrices()` implements a Chainlink L2 sequencer-uptime guard that mirrors the exact broken pattern disclosed against Size Credit's `PriceFeed.getPrice()`. When the sequencer feed returns an "invalid round" (`answer == 0` and `startedAt == 0`), the grace-period check silently passes because it is evaluated against `startedAt = 0`, defeating the purpose of the sequencer check and allowing the vault to accept prices that should have been rejected.

### Finding Description
In `spotPrices()`: [1](#0-0) 

```solidity
if (address(sequencer) != address(0)) {
    (, answer, startedAt,,) = sequencer.latestRoundData();
    if (answer != 0) {
        revert Aera__SequencerIsDown();
    }
    if (block.timestamp < startedAt + GRACE_PERIOD_TIME) {
        revert Aera__GracePeriodNotOver();
    }
}
```

This is mathematically the same broken relation as the Size finding (`block.timestamp - startedAt <= GRACE_PERIOD_TIME`), just rewritten as `block.timestamp < startedAt + GRACE_PERIOD_TIME` to avoid underflow. Per Chainlink's documented L2 sequencer-feed behavior, `startedAt` (and `answer`) can be `0` during an "invalid round" — i.e., when the sequencer's status has not yet been confirmed, due to network/oracle issues on the feed itself, independent of whether the sequencer is actually up. When that happens:
- `answer == 0` passes the `Aera__SequencerIsDown` check (since the code only reverts when `answer != 0`).
- `startedAt == 0` makes `block.timestamp < 0 + GRACE_PERIOD_TIME` (i.e., `block.timestamp < 3600`) essentially always false on any live chain, so `Aera__GracePeriodNotOver` never reverts.

As a result, calling `spotPrices()` (reachable by any external caller — it is a public view function with no access control) during an invalid round on the configured `sequencer` feed silently proceeds to price all registered assets via `_checkOraclePrice`, without ever having validated that the L2 sequencer status is actually confirmed/up-to-date. [2](#0-1) 

`spotPrices()` is the core valuation entrypoint consumed by the V2 vault/guardian machinery for solvency and submission checks, so any downstream consumer trusting these prices during a sequencer-invalid-round window inherits the same defect the confirmed Size Credit finding described.

### Impact Explanation
This is the identical root-cause/broken-invariant pattern as the confirmed Size Credit Medium finding: the sequencer-uptime safeguard is rendered ineffective specifically in the "invalid round" edge case, meaning price data can be treated as valid when the sequencer's status has not actually been confirmed. Since `spotPrices()` feeds vault valuation, this could let stale/unconfirmed prices be used by the vault's guardian/valuation logic during exactly the type of L2 disruption the check exists to protect against, which is the same failure mode Size classified as an Oracle bug.

### Likelihood Explanation
Requires: (1) an Aera V2 vault deployment on an L2 with a Chainlink sequencer-uptime feed configured (`address(sequencer) != address(0)`), and (2) the sequencer feed entering an "invalid round" state (a documented, real Chainlink occurrence, not a hypothetical). No privileged role is needed — `spotPrices()` is externally callable by any ordinary user/integrator, and any protocol logic that relies on it during that window inherits the flaw automatically.

### Recommendation
Add an explicit check that reverts (or otherwise short-circuits pricing) when `startedAt == 0`, per Chainlink's documented guidance, in addition to the existing `answer`/grace-period checks in `AeraVaultAssetRegistry.spotPrices()`.

### Proof of Concept
On a local fork with a mock `AggregatorV2V3Interface` sequencer feed:
1. Deploy `AeraVaultAssetRegistry` with the mock sequencer set as the `sequencer_` constructor param.
2. Configure the mock's `latestRoundData()` to return `answer = 0, startedAt = 0, updatedAt = block.timestamp` (simulating an "invalid round").
3. Call `spotPrices()` and assert it does **not** revert with `Aera__GracePeriodNotOver` or `Aera__SequencerIsDown`, demonstrating the grace-period guard is bypassed.
4. Compare against the expected behavior (revert) that would occur if the check instead validated `startedAt == 0` explicitly, confirming the guard is currently non-functional for this Chainlink-documented edge case.

Note: I was unable to confirm from the indexed code/config whether the `v2/AeraVaultAssetRegistry.sol` contract is presently deployed on an L2 with a live, non-zero `sequencer` address in production (no deployment manifests/addresses were found in the indexed files), so live-network applicability of this specific instance should be verified before treating it as bounty-eligible for a currently active deployment.

    /// @param asset Asset details to check.

    function _checkOraclePrice(AssetInformation memory asset)
        internal
        view
        returns (uint256 price)
    {
        (, int256 answer,, uint256 updatedAt,) = asset.oracle.latestRoundData();

        // Check price staleness
        if (answer <= 0) {
            revert Aera__OraclePriceIsInvalid(asset, answer);
        }
        if (
            asset.heartbeat > 0
                && updatedAt + asset.heartbeat + 1 hours < block.timestamp
        ) {
            revert Aera__OraclePriceIsTooOld(asset, updatedAt);
        }

    }
