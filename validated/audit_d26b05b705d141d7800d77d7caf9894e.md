### Title
Attacker-planted buffer account with padded `None`-authority metadata can cause slice-index panic in `SourceBuffer::new_checked_with_verified_build_hash` - ([File: runtime/src/bank/builtins/core_bpf_migration/source_buffer.rs])

### Summary
`SourceBuffer::new_checked_with_verified_build_hash` computes `end_offset` by scanning the *entire* account `data` buffer for the last non-zero byte instead of scanning only `data[offset..]`, where `offset = UpgradeableLoaderState::size_of_buffer_metadata()`. Because `size_of_buffer_metadata()` is a fixed constant sized to accommodate a `Some(Pubkey)` authority even when the actual state is `Buffer { authority_address: None }`, the bytes between the end of the real serialized state and `offset` are unused padding that bincode never inspects, and an attacker can freely set them to non-zero values while still passing `new_checked`'s state validation.

### Finding Description
`SourceBuffer::new_checked` at [1](#0-0)  only validates that `bincode::deserialize(&buffer_account.data()[..buffer_metadata_size])` yields a `UpgradeableLoaderState::Buffer{..}` variant. `bincode::deserialize` does not require consuming the whole slice, so when `authority_address` is `None`, only the enum discriminant (4 bytes) and the `Option` tag byte (1 byte) are actually read; the remaining bytes up to `buffer_metadata_size` (which is sized for the `Some(Pubkey)` case, as shown by the compensating subtraction of `serialized_size(&Pubkey::default())` in `account-decoder/src/parse_bpf_loader.rs`) are never examined during this check and can be set to arbitrary attacker-controlled values.

`new_checked_with_verified_build_hash` then does:
```rust
let offset = UpgradeableLoaderState::size_of_buffer_metadata();
let end_offset = data.iter().rposition(|&x| x != 0).map_or(offset, |i| i + 1);
let buffer_program_data = &data[offset..end_offset];
``` [2](#0-1) 

`rposition` is called on the full `data` slice, not `data[offset..]`. If the attacker plants a buffer account whose metadata region (bytes `[5, offset)`, i.e. the unused "authority padding" past the discriminant+tag) contains at least one non-zero byte at an index `<= offset - 2`, while the entire "ELF" region (`data[offset..]`) is all zero, the last non-zero byte found by `rposition` lies inside the metadata region at some index `i <= offset - 2`. Then `end_offset = i + 1 <= offset - 1 < offset`, and `&data[offset..end_offset]` panics with "slice index starts at more than ends" because `offset > end_offset`.

Exploit flow:
1. Attacker permissionlessly issues `InitializeBuffer` + `Write` instructions (ordinary, unprivileged BPF Upgradeable Loader instructions, see `process_loader_upgradeable_instruction` in `programs/bpf_loader/src/lib.rs`) to create and own the buffer account at the hard-coded migration `source_buffer_address` before the legitimate deploy authority does.
2. Attacker crafts the account data so that:
   - bytes `[0..4]` = Buffer variant discriminant,
   - byte `4` = `0x00` (`Option::None` tag for `authority_address`),
   - bytes `[5..offset)` contain at least one non-zero byte at index `≤ offset-2` (unused padding, not consumed by bincode's `Option::None` deserialization),
   - bytes `[offset..]` (the "ELF") are all zero.
3. `new_checked` succeeds because the state check only validates the deserializable prefix.
4. When the migration feature is activated and `Bank::migrate_builtin_to_core_bpf` calls `SourceBuffer::new_checked_with_verified_build_hash`, the mis-scoped `rposition` scan finds the attacker's padding byte, producing `end_offset < offset`, and the subsequent slice indexing panics, crashing bank processing.

This is a real decoder logic error: the invariant "decoders handle arbitrary attacker-authored account bytes without panicking" is violated because the code assumes the metadata region is always fully zero-filled when `authority_address` is `None`, but nothing enforces that on attacker-controlled account bytes.

### Impact Explanation
This is a validator-process panic (`SourceBuffer::new_checked_with_verified_build_hash`'s slice indexing) triggered purely by attacker-controlled on-chain account bytes reachable through the exact file/function named in scope. Since this code runs during `Bank::migrate_builtin_to_core_bpf` on the hot bank-processing path when a core-BPF migration feature activates, a panic here corresponds to a validator crash/consensus-halt category — the highest-severity class for decoder/consensus-processing bugs in the Agave bounty program.

### Likelihood Explanation
Preconditions are entirely within reach of an unprivileged attacker: creating and writing a buffer account at a specific, publicly-known, hard-coded pubkey (e.g. `agave_feature_set::replace_spl_token_with_p_token::PTOKEN_PROGRAM_BUFFER`) using only standard, permissionless `InitializeBuffer`/`Write` instructions, provided the attacker front-runs the legitimate authority in claiming that address. No special privileges, staked/leader/gossip control, or mocked paths are required — the account and its byte contents are fully attacker-authored and pass all existing owner/state checks in `new_checked`. The trigger (feature activation invoking the migration) is a normal scheduled validator event, not something requiring further attacker action once the account is planted, making this fully repeatable.

### Recommendation
Compute `end_offset` by scanning only the program-data region, not the whole account buffer:
```rust
let end_offset = data
    .get(offset..)
    .and_then(|program_data| program_data.iter().rposition(|&x| x != 0))
    .map_or(offset, |i| offset + i + 1);
```
This bounds the scan to `data[offset..]`, eliminating any dependency on the content of the (potentially attacker-controlled) padding bytes preceding `offset`, and removes the possibility of `end_offset < offset`.

### Proof of Concept
```rust
#[test]
fn test_new_checked_with_verified_build_hash_does_not_panic_on_malicious_padding() {
    let bank = create_simple_test_bank(0);
    let buffer_address = Pubkey::new_unique();

    let buffer_metadata_size = UpgradeableLoaderState::size_of_buffer_metadata();
    let elf_len = 32;
    let data_len = buffer_metadata_size + elf_len;
    let mut data = vec![0u8; data_len];

    // Discriminant for Buffer variant + Option::None tag for authority_address.
    bincode::serialize_into(
        &mut data[..5], // enough bytes for discriminant(4) + None tag(1)
        &UpgradeableLoaderState::Buffer { authority_address: None },
    )
    .unwrap();

    // Attacker-controlled non-zero byte inside the unused metadata padding
    // (index <= buffer_metadata_size - 2), not consumed by bincode when
    // authority_address is None.
    data[buffer_metadata_size - 2] = 0x01;

    // "ELF" region is entirely zero.
    // data[buffer_metadata_size..] already all zero.

    let space = data.len();
    let lamports = bank.get_minimum_balance_for_rent_exemption(space);
    let mut account = AccountSharedData::new(lamports, space, &bpf_loader_upgradeable::id());
    account.data_as_mut_slice().copy_from_slice(&data);
    bank.store_account_and_update_capitalization(&buffer_address, &account);

    // Should return an Err (e.g. BuildHashMismatch), not panic.
    let result = SourceBuffer::new_checked_with_verified_build_hash(
        &bank,
        &buffer_address,
        Hash::default(),
    );
    assert!(result.is_err());
}
```
Expected current behavior: this test panics with `"slice index starts at more than ends"` at `&data[offset..end_offset]`. After applying the recommended fix (scanning only `data[offset..]`), the function returns `Err(CoreBpfMigrationError::BuildHashMismatch(..))` instead of panicking.
