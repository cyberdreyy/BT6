### Title
Unrecovered panic in `normalizeHex` via unauthenticated, malformed `workflowID` (negative `strings.Repeat` count) - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`validateHexInput` only bounds `len(input)` (including any optional `"0x"` prefix) to `workflowIDLength` (66), but does not require the `"0x"` prefix nor enforce a fixed length on the stripped hex digits. `normalizeHex` then computes `expectedHexLength-len(hexStr)` and calls `strings.Repeat` with that value, which panics with a negative count when an attacker submits a 66-character hex string without the `0x` prefix, since `hexStr` (66 chars, unstripped) exceeds `expectedHexLength` (64).

### Finding Description
In `validateWorkflowID` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:278-285`) the raw, attacker-controlled `Params.Workflow.WorkflowID` is checked with `validateHexInput(workflowID, workflowIDLength)` (`workflowIDLength = 66`). That function only verifies:
- the string is lowercase,
- `len(input) <= 66`,
- after trimming an optional `"0x"` prefix, the remainder decodes as hex. [1](#0-0) 

Crucially, it does not require the `0x` prefix to be present, so a 66-character all-hex-digit string with no `0x` prefix passes this check (66 ≤ 66, and 66 is an even count so `hex.DecodeString` succeeds).

This validation runs in `validatedTriggerRequest` → `validateTriggerParams` → `validateWorkflowFields` → `validateWorkflowID`, which is invoked in `HandleUserTriggerRequest` **before** `authorizeRequest`, i.e. on unauthenticated input directly from `Params.Workflow.WorkflowID`. [2](#0-1) 

Later, `resolveWorkflowID` calls `normalizeHex(workflowID, workflowIDLength)` on the same string that passed validation: [3](#0-2) 

```go
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}
``` [4](#0-3) 

For a 66-character hex string with no `0x` prefix, `TrimPrefix` is a no-op, so `hexStr` stays 66 characters, `expectedHexLength = 64`, and `expectedHexLength-len(hexStr) = -2`. `strings.Repeat` panics on a negative count ("strings: negative Repeat count"). Because I could not locate any `recover()` guarding the request-handling goroutine in the gateway's `core/services/gateway` package (only test files contain `recover()`), this panic is very likely unrecovered and will crash the goroutine/process handling gateway trigger requests.

### Impact Explanation
An unauthenticated attacker sending a single crafted `workflows.execute` gateway trigger request with a 66-hex-character `workflowID` (no `0x` prefix) can trigger a Go runtime panic inside `normalizeHex`, before any authentication/authorization check runs. If unrecovered, this results in denial of service against the gateway node handling HTTP triggers — impacting availability for all users of that gateway/DON, not just the attacker. This is a DoS-class impact rather than a data-confusion/lookup-collision issue as literally framed in the question (the "numerically equal but stringwise different keys" scenario does not actually occur here because `validateHexInput`'s length bound combined with `normalizeHex`'s subtraction leads to a crash rather than silent truncation/collision).

### Likelihood Explanation
No privilege or credential is required — this is reachable pre-`authorizeRequest`, i.e., before any auth/allowlist check, directly from `Params.Workflow.WorkflowID` in the JSON-RPC gateway request body. The attacker only needs to submit a syntactically valid, lowercase, even-length hex string of exactly 66 characters without the `0x` prefix (e.g., 66 `'a'` characters). This is trivially and repeatably reproducible.

### Recommendation
Fix `validateHexInput`/`normalizeHex` to be consistent: either require the `0x` prefix and validate the *stripped* hex length equals exactly `length-2` (rejecting both too-long and too-short values) before calling `strings.Repeat`, or make `normalizeHex` defensively check `len(hexStr) > expectedHexLength` and return an error instead of computing a negative repeat count. Recommended minimal fix:
```go
func normalizeHex(input string, length int) (string, error) {
	hexStr := strings.TrimPrefix(input, "0x")
	expectedHexLength := length - 2
	if len(hexStr) > expectedHexLength {
		return "", fmt.Errorf("hex string too long")
	}
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex, nil
}
```
Also tighten `validateHexInput` to require the `0x` prefix explicitly and bound the trimmed-hex length rather than the raw input length.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler_test.go`:
```go
func TestNormalizeHex_OversizedInputWithoutPrefix_ShouldNotPanic(t *testing.T) {
	oversized := strings.Repeat("a", workflowIDLength) // 66 chars, no "0x" prefix
	require.NoError(t, validateHexInput(oversized, workflowIDLength)) // passes current validation
	require.NotPanics(t, func() {
		_ = normalizeHex(oversized, workflowIDLength)
	}, "normalizeHex must not panic on oversized/prefixless workflowID input")
}
```
Expected current behavior: the test fails/panics with `strings: negative Repeat count`, demonstrating the bug. After the fix, `normalizeHex` should return an error (or a safely truncated/rejected value) instead of panicking, and `validateWorkflowID`/`resolveWorkflowID` should surface a client-facing `jsonrpc.ErrInvalidRequest` rather than crashing.

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}
