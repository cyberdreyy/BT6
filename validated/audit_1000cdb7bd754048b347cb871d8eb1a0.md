### Title
Stale member confirmations let a `MultiSigRequest` execute below the configured `num_confirmations` threshold - (File: `multisig2/src/lib.rs`)

### Summary
`multisig2`'s `delete_member` only purges requests *created by* the removed member, but never scrubs that member's *confirmations* recorded on other members' still-pending requests. `confirm()` later counts those stale confirmations toward `num_confirmations` without re-validating that every confirming entry is still a live member, so a request can be executed with fewer live approvals than the contract's configured threshold requires.

### Finding Description
`MultiSigContract::confirm` treats reaching `num_confirmations` purely as a counter check on the stored `HashSet<String>` for a request: [1](#0-0) 

Nothing in this path re-verifies that each account/string already present in `confirmations` is still `self.members.contains(...)` at execution time — it only checks that the *new* confirmer (`current_member()`) is currently a member.

The member-removal path, `delete_member`, only cleans up requests that the removed member itself created (`r.member == member`); it does not scan `self.confirmations` for entries where the removed member appears as a *confirmer* on requests created by other members: [2](#0-1) 

Concretely, this breaks the equality that should hold: `confirmations counted at execution == confirmations from accounts that are members at execution time`. Instead, `confirmations counted == confirmations recorded historically`, which can include accounts no longer in `self.members`.

### Impact Explanation
This maps to the explicit Critical impact category "a multisig request executed below threshold." Example: `num_confirmations = 3`, members `{A, B, C, D}`.
1. `A` calls `add_request` for `Transfer{amount}` to some receiver.
2. `B` confirms — confirmations = `{B}`.
3. `C` confirms — confirmations = `{B, C}` (still `< 3`, so not yet executed).
4. The multisig later (via a separate, properly-confirmed `DeleteMember{C}` request) removes `C`, e.g., because `C`'s key was rotated/compromised or `C` left the organization. `delete_member` does not touch the confirmation set of `A`'s pending request, so it still contains `{B, C}`.
5. `D` confirms the pending request: `confirmations.len() + 1 == 3 >= num_confirmations(3)` → `execute_request` fires the `Transfer`.

The request executed with confirmations from only two currently-live members (`B`, `D`), plus one confirmation attributable to a member who was explicitly removed from the multisig (`C`). The multisig's `num_confirmations` invariant — the security boundary that determines whether a `Transfer`, `AddKey`, `FunctionCall`, etc. is authorized — is violated: it takes effect with fewer than the configured number of *currently trusted* signers.

### Likelihood Explanation
This does not require any signer to be malicious or any external actor; it is triggered by ordinary, expected multisig operations: (a) partial confirmation of a request, (b) legitimate removal of a member (e.g., off-boarding, key rotation, compromise response — a normal, anticipated multisig lifecycle event, not an "ignoring documented initialization" scenario), and (c) a subsequent confirmation by another still-live member. No collusion or privileged bypass is needed beyond the multisig's own normal `confirm`/`DeleteMember` flows; the bug is a missing invalidation step in `delete_member`, purely a code-logic defect.

### Recommendation
When a member is removed, scan all pending requests' confirmation sets and strip the removed member's entry (or invalidate/require re-confirmation of any request that had that member's confirmation). Alternatively, at the moment `num_confirmations` is evaluated in `confirm()`, re-validate every account/key in the stored confirmation set against current `self.members` and only count still-live members.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]` (as `AccessKey` or `Account` members) and `num_confirmations = 3`.
2. As `A`, call `add_request` with a `Transfer` action to a chosen `receiver_id`. Note `request_id`.
3. As `B`, call `confirm(request_id)` → confirmations set becomes `{B}`.
4. As `C`, call `confirm(request_id)` → confirmations set becomes `{B, C}` (2 < 3, request stays pending).
5. Through the normal `add_request` → `confirm` flow (reaching 3 confirmations from `A, B, D`, for example), execute a `DeleteMember{member: C}` request. This calls `delete_member`, which removes `C` from `self.members` but does not touch the confirmations HashSet of the request from step 2 (only removes requests *authored by* `C`).
6. As `D`, call `confirm(request_id)` on the original request from step 2. `confirmations.len() + 1 == 3 >= num_confirmations`, so `execute_request` runs the `Transfer`, even though `C` is no longer in `self.members` and only `B` and `D` are currently-live confirmers.

Note: I was unable to fully verify whether the original `multisig/src/lib.rs` (non-`multisig2`, key-based) implementation shares this exact flaw in the time available — `grep_search` found only one `delete_key`-adjacent match there versus two in `multisig2`, suggesting the request/confirmation-cleanup logic may differ; a full read of `multisig/src/lib.rs`'s `delete_key`/`remove_request` functions would be needed to confirm whether the same stale-confirmation gap exists there. Recommend a background agent additionally audit `multisig/src/lib.rs` for the same pattern.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
