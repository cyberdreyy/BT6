### Title
`IdleCDOPoLidoVariant::_withdraw` hands the redeemer an arbitrary PoLido NFT whose claim amount is never matched to `toRedeem`, allowing theft of other users' pending unstake claims - ([File: contracts/IdleCDOPoLidoVariant.sol](contracts/IdleCDOPoLidoVariant.sol))

### Summary
Analogous to `DropBox::tokenURI` returning data for a `tokenId` it never validated, `_withdraw` selects a PoLido withdrawal NFT by array position (`tokenIds[tokenIds.length - 1]`) without verifying that the NFT corresponds to the withdrawal just created or that its underlying claim amount matches `toRedeem`. The function liquidates `toRedeem`, then transfers whatever NFT happens to be last in `getOwnedTokens`, so a redeemer can receive an unrelated, larger pending claim. [1](#0-0) 

### Finding Description
In `_withdraw`, the contract calls `_liquidate(toRedeem, revertIfTooLow)` which requests an unstake of `toRedeem` stMATIC from Lido's `stMatic.requestWithdraw`, minting a new PoLido NFT to the vault. It then enumerates all NFTs owned by the vault via `stMatic.poLidoNFT().getOwnedTokens(address(this))` and transfers `tokenIds[tokenIds.length - 1]` to `msg.sender` — with no check that this token is the one just minted for this withdrawal, and no check that the stMATIC claim backing it (`token2WithdrawRequest`) equals `toRedeem`. [2](#0-1) 

Lido's `getOwnedTokens` uses ERC721Enumerable-style index bookkeeping: removing tokens swaps the last element into the vacated slot, so the last array element is not guaranteed to be the most recently minted NFT. When the vault holds several pending unstake NFTs (every previous withdrawer who received an NFT and anyone whose NFT hasn't been claimed yet leaves the vault holding none, but concurrent unclaimed-withdrawal NFTs remain owned by the vault only until transferred — in practice any NFT minted to the vault but not yet handed out stays in the list), a withdrawer burns tranche tokens worth a small `toRedeem` yet receives an NFT whose `claimTokens(tokenId)` on stMATIC pays a much larger amount belonging to the aggregate pool. There is no per-user NFT accounting anywhere in the contract, so the mapping between redeem size and NFT claim is never established. [3](#0-2) 

### Impact Explanation
Direct theft of other users' pending withdrawal claims. A redeemer who requests a withdrawal of e.g. 1 stMATIC-equivalent of tranche tokens while the vault holds an NFT claiming e.g. 1,000,000 MATIC from an earlier large withdrawal receives that NFT and can call `stMatic.claimTokens(tokenId)` to collect the full amount. The NAV accounting (`lastNAVAA -= toRedeem` / `lastNAVBB -= toRedeem`) only deducts the small `toRedeem`, so the vault's remaining NFTs under-collateralize outstanding tranche holders — solvency and "one receipt one payout" invariants are broken, and the loss is fully quantified as `NFT claim value - toRedeem`. [4](#0-3) 

### Likelihood Explanation
Requires only that the vault hold ≥1 NFT whose claim exceeds the attacker's `toRedeem` at the time of withdrawal — i.e., any large prior withdrawal whose NFT was minted to the vault and (due to index ordering) sits at the tail of `getOwnedTokens`. The attacker is an ordinary KYC'd tranche holder calling `withdrawAA`/`withdrawBB`; no privileged role, no oracle, no timing manipulation. The guards present (`_checkSameBlock`, `_checkDefault`, `nonReentrant`, `tokenIds.length != 0`) do not constrain which NFT is delivered or its size. The only mitigation is that the NFT handed out is often the one just minted when the vault holds exactly one NFT, but nothing in code enforces that. [5](#0-4) 

### Recommendation
Track the NFT minted by each withdrawal and bind it to the redeemer's claim amount. Concretely:

```diff
toRedeem = _liquidate(toRedeem, revertIfTooLow, ...);
IdleCDOTranche(_tranche).burn(msg.sender, _amount);
-uint256[] memory tokenIds = stMatic.poLidoNFT().getOwnedTokens(address(this));
-require(tokenIds.length != 0, "no NFTs");
-uint256 tokenId = tokenIds[tokenIds.length - 1];
+// Identify the NFT created by _liquidate (e.g., snapshot owned-token set
+// before/after, or read stMatic's request counter) and verify its claim:
+uint256 tokenId = /* newly minted id */;
+(uint256 amount2Withdraw,,, ) = stMatic.token2WithdrawRequest(tokenId);
+require(amount2Withdraw >= toRedeem, "NFT mismatch");
 stMatic.poLidoNFT().safeTransferFrom(address(this), msg.sender, tokenId);
```

Alternatively, since NFTs are fungible claims on MATIC, prefer transferring an NFT whose `token2WithdrawRequest` amount is closest to (and ≥) `toRedeem`, splitting accounting across multiple NFTs when needed. [2](#0-1) 

### Proof of Concept
Foundry fork test on Polygon mainnet (`IdleCDOPoLidoVariant` at its deployed proxy, `stMatic`/`poLidoNFT` at the hardcoded addresses). Sketch:

```solidity
// contracts/IdleCDOPoLidoVariant.sol:64-78
function testWithdrawGrabsForeignNft() public {
    // 1. Whale deposits and withdraws a large amount -> vault receives NFT_big
    //    with claim ~= BIG_MATIC. (Do NOT let the vault transfer it out:
    //    simulate by having the whale's withdrawal leave multiple NFTs in the
    //    vault — e.g., two withdraws where the second hands out NFT_small,
    //    leaving NFT_big owned by the vault at the tail of getOwnedTokens.)
    // 2. Warp forward but do NOT claim NFT_big.
    // 3. Attacker deposits dust and calls withdrawAA(dustTrancheAmount).
    //    _liquidate requests a dust unstake -> NFT_dust minted to vault.
    // 4. getOwnedTokens ordering returns NFT_big as the last element
    //    (enumerable swap-and-pop keeps it at the tail after previous removals).
    // 5. Assert: poLidoNFT.ownerOf(NFT_big) == attacker after withdraw.
    // 6. Attacker calls stMatic.claimTokens(NFT_big) and receives BIG_MATIC
    //    while having burned only dust tranche tokens; vault NAV decreased by
    //    dust only => remaining holders are under-collateralized by
    //    BIG_MATIC - dust.
}
```

The critical assertion is step 5: the NFT transferred to the redeemer is selected purely by array index, not by the request created in `_liquidate`, so any NFT still owned by the vault — regardless of its claim size — can be extracted for a dust-sized redemption. [6](#0-5)

    function _withdraw(uint256 _amount, address _tranche) internal override nonReentrant returns (uint256 toRedeem) {
        // check if a deposit is made in the same block from the same user
        _checkSameBlock();
        // check if _strategyPrice decreased
        _checkDefault();
        // accrue interest to tranches and updates tranche prices
        _updateAccounting();
        // redeem all user balance if 0 is passed as _amount
        if (_amount == 0) {
            _amount = IERC20Detailed(_tranche).balanceOf(msg.sender);
        }
        require(_amount != 0, "0");

        // Calculate the amount to redeem
        toRedeem = (_amount * _tranchePrice(_tranche)) / ONE_TRANCHE_TOKEN;

        // NOTE: modified from IdleCDO
        // request unstaking matic from poLido strategy and receive an nft.
        toRedeem = _liquidate(toRedeem, revertIfTooLow);
        // burn tranche token
        IdleCDOTranche(_tranche).burn(msg.sender, _amount);

        // NOTE: modified from IdleCDO
        // send an PoLido nft not matic to msg.sender
        uint256[] memory tokenIds = stMatic.poLidoNFT().getOwnedTokens(address(this));
        require(tokenIds.length != 0, "no NFTs");

        // update NAV with the _amount of underlyings removed
        if (_tranche == AATranche) {
            lastNAVAA -= toRedeem;
        } else {
            lastNAVBB -= toRedeem;
        }

        // update trancheAPRSplitRatio
        _updateSplitRatio(_getAARatio(true));

        uint256 tokenId = tokenIds[tokenIds.length - 1];
        stMatic.poLidoNFT().safeTransferFrom(address(this), msg.sender, tokenId);
