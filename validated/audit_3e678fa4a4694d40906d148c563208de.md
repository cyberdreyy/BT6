## Finding: v1 signer's tenure-duplicate-block guard has no canonical-state fallback and is silently bypassed if the first sibling's proposal was never locally observed

### Title
Signer can sign a second, conflicting tenure-start block because `DuplicateBlockFound` and its re-check are local-DB-only with no canonical fallback - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The bug-class in the XWiki advisory is: a privileged check exists on one entry point (normal edit) but a second entry point (Live Data's edit REST API) reaches the same mutation without going through all the same checks, because the checks were not "properly called" on every path. The stacks-signer codebase has the structurally identical shape around the tenure-start "already signed a block in this tenure" guard: it is enforced only once, at proposal time, via a local-signerdb-only lookup, and every later re-entry point that could still sign the block (validate-ok, pre-commit-threshold) uses a reduced re-check function that does not repeat it and has no fallback to the node's canonical view.

### Finding Description
For a tenure-change (tenure-start) block, the "have we already accepted a block in this tenure" guard is `validate_tenure_change_payload`, called only from `check_proposal` at proposal time: [1](#0-0) 

It relies exclusively on the local `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` — a query against this signer's own SQLite `blocks` table, with no RPC fallback to the stacks-node's canonical chain state.

By contrast, the sibling check that answers "does this block confirm the tenure's tip" (`check_latest_block_in_tenure` / `confirms_latest_block_in_same_tenure`) *does* have a node-RPC fallback (`get_tenure_tip`) precisely because local DB knowledge can be incomplete: [2](#0-1) 

The proposal-time-only nature of the duplicate check, and the fact that later re-checks skip it, is explicitly acknowledged in the project's own flow documentation: [3](#0-2) 

Both re-check call sites — after node validation succeeds, and again at the pre-commit-threshold moment right before the actual signature is produced — invoke `check_block_against_signer_db_state`, which only re-verifies `check_tenure_change_confirms_parent` (the *parent* tenure) or `check_latest_block_in_tenure` (the *own* tenure's height ordering), never `validate_tenure_change_payload`'s duplicate-tenure guard: [4](#0-3) [5](#0-4) [6](#0-5) 

The function itself is annotated as intentionally incomplete and dependent on having already run the full proposal check: [7](#0-6) 

The designated "safety net" for this gap is the sibling-conflict guard in `handle_block_pre_commit` (`get_signed_conflicts`), which the docs say exists precisely because the duplicate check "never runs again": [8](#0-7) 

But that safety net is *also* a purely local-DB query (it can only find conflicts among blocks this signer has itself stored a row for). If this signer never received/processed the first sibling's `BlockProposal` at all — plausible given StackerDB gossip has no delivery guarantee, and is explicitly called out elsewhere in the docs as something the code must tolerate ("a pre-commit for a block we have not seen proposed yet means the proposal has not reached us"): [9](#0-8) 

then the local `blocks` table has zero rows for that consensus hash: `get_last_globally_accepted_block` returns `None` at proposal time, and `get_signed_conflicts` finds nothing at pre-commit time. Every check in the chain silently passes on missing data instead of falling back to asking the node (as `check_latest_block_in_tenure` does via `get_tenure_tip`), so the signer proceeds to fully sign a second, conflicting tenure-start block for a tenure it may already have (elsewhere, invisibly to it) helped finalize.

### Impact Explanation
This breaks the "one-per-height"/"approved-parent vs canonical" equality: a single signer can be induced to place its signature on a tenure-start block that conflicts with another tenure-start block already globally accepted for the same tenure, purely because of a gossip-timing gap rather than any fork resolution logic. That is exactly the Critical class in the rules: "a signer signing an invalid, non-canonical, or conflicting block." A miner (one slot) can trigger this by presenting a signer with only its own private tenure-start proposal while ensuring (via normal network conditions or minor timing manipulation) that this signer never received the earlier sibling that other signers already accepted.

### Likelihood Explanation
This requires no majority collusion, no other signer's key, and no auth token — only ordinary gossip/timing conditions plus a miner (or any actor able to control which proposal a given signer receives first) producing two competing tenure-start blocks for the same tenure. StackerDB delivery is asynchronous and the signer code already anticipates and handles "proposal not yet received" as a normal, expected state (see the `handle_block_pre_commit` "unknown block" branch), which makes the missing-local-knowledge precondition realistic rather than exotic.

### Recommendation
Make the tenure-duplicate guard resilient to incomplete local knowledge the same way `check_latest_block_in_tenure` already is: when the local `blocks` table has no record for the tenure's consensus hash, query the node (`get_tenure_tip`/equivalent) before concluding "no conflict," instead of treating an empty local table as proof of no prior block. Additionally, re-run the full `validate_tenure_change_payload` (or at minimum its duplicate-block sub-check) inside `check_block_against_signer_db_state`, so the validate-ok and pre-commit-threshold re-checks cannot sign over a duplicate tenure-start block that the proposal-time check missed due to a gossip gap.

### Proof of Concept
1. Miner produces two competing tenure-start (`TenureChangeCause::BlockFound`) blocks A and B for the same tenure T, both confirming the same parent tenure tip.
2. Block A is gossiped to, validated, and signed by enough *other* signers to become globally accepted, but the StackerDB message carrying A's `BlockProposal` never reaches signer S (delayed/dropped gossip — no attacker collusion required).
3. Signer S is later sent block B directly. Its local `blocks` table has no row for tenure T, so `validate_tenure_change_payload`'s `get_last_globally_accepted_block` check (`stacks-signer/src/chainstate/v1.rs:505-518`) returns `None` and passes.
4. B passes node validation (plausible if the node hasn't converged either, or the tenure-change structurally validates against the shared parent). `handle_block_validate_ok` calls `check_block_against_signer_db_state`, which only checks the *parent* tenure, not T's own duplicate status — passes, block is pre-committed.
5. At the pre-commit threshold, `handle_block_pre_commit`'s `get_signed_conflicts(height_B, hash_B)` also finds nothing (no local row for A exists), so signer S signs B.
6. Signer S has now produced a valid signature over a block conflicting with an already-globally-accepted sibling in the same tenure.

**Uncertainty note:** I could not, within the available tool budget, read the full implementations of `get_signed_conflicts`, `reorg_permit_stands`, and `handle_block_signature` in `signerdb.rs`/`v0/signer.rs` (grep located them but I was not able to fetch their bodies before the iteration budget ended). It is possible those functions contain additional cross-checks (e.g., consulting `NewBlock` events broadcast independently of `BlockProposal` gossip) that further mitigate this scenario; a full review of those three functions is recommended to confirm whether any node-independent state (e.g., stacks-node's own mempool/chain-tip observation via `NewBlock`) closes this gap in practice.
