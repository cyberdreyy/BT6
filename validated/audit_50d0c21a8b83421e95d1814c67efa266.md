### Title
APR0 withdraw receipt permanently bricks `stopEpoch` once APR is raised above 0 - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` hard-reverts with `NotAllowed()` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` [1](#0-0) . This is the analog of the Wireshark crash: a malformed/invalid state combination hits a fatal check inside a routine that every epoch transition must execute, so the vault can never finalize another epoch and all user funds are permanently frozen.

### Finding Description
When the vault runs at `unscaledApr == 0`, an unprivileged tranche holder calling `requestWithdraw` routes into the APR0 bucket: `requestWithdraw` burns/mints receipts and calls `_requestWithdrawApr0`, which increments `apr0TotalPrincipal` [2](#0-1) . `apr0TotalPrincipal` is only ever reset to 0 inside `prepareStopEpochWithApr0` [3](#0-2) , which the CDO must call during `stopEpoch`.

Attack sequence:

1. Vault is in buffer/epoch with `unscaledApr == 0`. A KYC'd lender (any unprivileged user) calls `IdleCDOEpochVariant.requestWithdraw`, creating an APR0 receipt and leaving `apr0TotalPrincipal > 0` [4](#0-3) .
2. The honest owner/manager legitimately raises the APR (`setAprs`/`unscaledApr != 0`) for the next epoch — a normal privileged operation, e.g. re-enabling yield after a zero-rate period.
3. Manager calls `stopEpoch`. The CDO calls `prepareStopEpochWithApr0`, which reverts because `apr0TotalPrincipal != 0 && unscaledApr != 0` [5](#0-4) .
4. The revert is self-reinforcing: `apr0TotalPrincipal` can only be cleared inside the same function that reverts, and the per-user clearing path `_clearWithdrawClaimForEpoch` (which reduces `apr0TotalPrincipal`) is only reachable via `claimWithdrawRequest`, which requires `epochNumber > lastWithdrawRequest` — i.e., requires a successful `stopEpoch` first [6](#0-5) [7](#0-6) . Deposits, withdraws, claims and borrower repayment all deadlock behind an epoch transition that can never execute.

### Impact Explanation
Permanent freezing of all user funds: every tranche holder's NAV and every pending receipt becomes unclaimable because `epochNumber` can never advance and `stopEpoch`/`startEpoch` are the only ways to fund claims. The attacker needs only one small APR0 withdraw request (dust-sized principal suffices, since the revert checks `apr0TotalPrincipal != 0`, not a threshold). There is no admin escape hatch — `apr0TotalPrincipal` has no setter and `prepareStopEpochWithApr0` is `_onlyIdleCDO`.

### Likelihood Explanation
The user-side trigger is permissionless (any KYC-passing lender can `requestWithdraw` during an APR0 phase). The privileged side — raising APR from 0 — is an ordinary, honest manager action; APR0 epochs exist precisely as a transitional mode, so moving back to a positive APR is expected operational behavior. No malicious privileged role is required.

### Recommendation
In `prepareStopEpochWithApr0`, handle `unscaledApr != 0` gracefully instead of reverting: settle the APR0 bucket at the last recorded `apr0RateByEpoch`/zero interest and clear `apr0TotalPrincipal` before returning, or allow `stopEpoch` to close the bucket so future epochs proceed. Alternatively, let per-user claim/settlement paths reduce `apr0TotalPrincipal` even when the bucket's epoch hasn't rolled over, so no single stale receipt can wedge the state machine.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testApr0ReceiptBricksStopEpochAfterAprRaised() external {
    // Vault configured with unscaledApr == 0; user deposits and requests withdraw
    idleCDO.depositAA(10_000 * ONE_SCALE);
    _forceLastEpochAprToZero();              // unscaledApr == 0
    cdoEpoch.requestWithdraw(someTranches, address(AAtranche)); // apr0TotalPrincipal > 0

    // Honest manager restores a positive APR for next epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(1e18, 1e18); // unscaledApr != 0

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());

    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0); // prepareStopEpochWithApr0 reverts; epochNumber stuck
}
```

Every subsequent `stopEpoch` attempt reverts identically, and `claimWithdrawRequest`/`claimInstantWithdrawRequest` can never mature because `epochNumber` never increments.

      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
      !isWalletAllowed(msg.sender)
    );
  
    // we check if there are donated assets to the pool and transfer them to the feeReceiver if any
    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;
    // add expected fees to pending withdraw fees counter
    pendingWithdrawFees += totalFees;

    /// if there is an AA withdrawal the overperformance that the amount withdrawed would have generated for BB tranches
    /// is saved in interestForOverUnderPerformance. This is used to calculate the interest that should be added to the

    /// If there is a BB withdrawal this amount is subtracted from the expectedEpochInterest
    interestForOverUnderPerformance += diff;

    // The receipt is fixed now and leaves live NAV. Charge management fees upfront
    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
    creditVault.requestWithdraw(_underlyings, msg.sender, principal);
    // burn tranche tokens and decrease NAV without interest for the next epoch as it was not yet counted in NAV
    _withdrawOps(_amount, principal, _tranche);
  }
