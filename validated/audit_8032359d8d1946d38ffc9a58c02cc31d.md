### Title
Global contract deploy under `AccountId` mode lets any unprivileged account hijack another account's `GlobalContractCode{AccountId}` slot, retroactively rewriting code for every account that opted in via `UseGlobalContract` - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`action_deploy_global_contract` and `initiate_distribution` compute the global-contract identifier for `GlobalContractDeployMode::AccountId` from `account_id`, which is the **receiver** of the action's receipt, not from any signature/ownership proof over that account. Because `DeployGlobalContract` is not in the set of actions constrained to `predecessor_id == receiver_id` (unlike `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`), an attacker can direct a `DeployGlobalContractAction{deploy_mode: AccountId}` at an arbitrary `receiver_id` they do not control, overwriting `TrieKey::GlobalContractCode{AccountId(receiver_id)}` and silently rewriting the code every account that previously did `UseGlobalContract{AccountId(receiver_id)}` will execute.

### Finding Description
`action_deploy_global_contract` runs in the context of the receipt's receiver account (`account_id`/`account` parameters refer to whatever account the receipt targets): [1](#0-0) 

For `GlobalContractDeployMode::AccountId`, the global contract identifier is derived directly from that receiver `account_id`, with no check that the caller (predecessor) actually owns or controls that account: [2](#0-1) 

The resulting `GlobalContractDistributionReceipt` is later applied unconditionally, overwriting `TrieKey::GlobalContractCode{AccountId(receiver_id)}` with the attacker-supplied bytecode: [3](#0-2) 

Any account that previously executed `use_global_contract` with `GlobalContractIdentifier::AccountId(receiver_id)` resolves its code through `AccountContract::GlobalByAccount(id)` at that same trie key, so it now silently executes the attacker's code on its next invocation: [4](#0-3) 

The documentation for actions explicitly enumerates which action types require `predecessor_id == receiver_id`: `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`. `DeployGlobalContract` is conspicuously absent from this list: [5](#0-4) [6](#0-5) 

The only validation performed on `DeployGlobalContractAction` is a code-size check — no ownership/actor check ties the `AccountId` mode identifier to the transaction's signer/predecessor: [7](#0-6) 

Consequently, an attacker (as an ordinary predecessor account, e.g. via a `FunctionCall` from its own contract that issues a promise batch, or a meta-transaction relay) can construct a receipt whose `receiver_id` is set to `popular-project.near` (an account the attacker does not own) and whose action list is `[DeployGlobalContractAction{code: evil_wasm, deploy_mode: AccountId}]`. Because storage cost is charged against the *receiver's* balance (`account.amount().checked_sub(storage_cost)` inside `action_deploy_global_contract`), the attack even forces the victim account to pay for its own code substitution, or fails harmlessly if that account lacks spare balance — but if it has spare balance (a "well-known, already-adopted" popular contract account plausibly does), the substitution proceeds. None of the existing checks (signature/nonce on the outer transaction, access-key permission, contract-size limit, or the nonce-freshness check in `check_and_update_nonce`) validate that the entity requesting the `AccountId`-mode deploy actually controls `receiver_id`.

### Impact Explanation
This is an authorization-escalation bug that lets an unprivileged attacker overwrite the code resolved by every account that opted into a given `GlobalContractIdentifier::AccountId` — i.e., theft or loss of funds for any of those accounts once the substituted code executes with their storage/balance context on their next `FunctionCall`, satisfying the "Stealing or loss of funds" bounty category.

### Likelihood Explanation
Preconditions are minimal and match realistic mainnet usage: (1) a popular account has deployed a global contract under `AccountId` mode and other accounts have called `UseGlobalContract{AccountId(...)}` against it (an intended, documented usage pattern for shared/upgradable contracts), and (2) the target account has spare NEAR balance to cover the (attacker-supplied) storage cost, which is typical for a "popular project" account. The attacker only needs an ordinary funded account and the ability to submit a receipt whose action list contains `DeployGlobalContractAction`, e.g. via a `FunctionCall` from their own deployed contract using `promise_batch_action_deploy_global_contract` targeting the victim's `receiver_id`, or via a relayed meta-transaction. No validator, node, or special access is required, and the attack is repeatable indefinitely (each new global-contract nonce simply supersedes the prior one).

### Recommendation
Enforce that `GlobalContractDeployMode::AccountId` deploys require `predecessor_id == receiver_id`, mirroring the existing restriction already applied to `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, and `DeleteAccount`. Add this check either in `validate_deploy_global_contract_action` (given receiver/predecessor context) or in the actor-permission enforcement path (`runtime/runtime/src/actions.rs`) before `action_deploy_global_contract` is invoked, and add a protocol feature gate if this changes existing on-chain semantics.

### Proof of Concept
Test-loop integration test with three accounts: `owner` (deploys a benign global contract under `AccountId` mode and it gets adopted), `victim` (calls `use_global_contract` with `GlobalContractIdentifier::AccountId(owner)`), and `attacker` (an unrelated funded account with its own deployed contract).
1. `owner` submits `DeployGlobalContractAction{code: benign_wasm, deploy_mode: AccountId}` targeting itself; wait for distribution to complete across shards.
2. `victim` submits `UseGlobalContractAction{contract_identifier: AccountId(owner)}`; assert `victim`'s next `FunctionCall` executes `benign_wasm`'s logic.
3. `attacker` submits a `FunctionCall` (via its own contract or a raw promise-batch transaction) that creates a receipt with `receiver_id = owner` and action `DeployGlobalContractAction{code: evil_wasm, deploy_mode: AccountId}`, signed only with attacker's own keys (no key of `owner`).
4. After distribution receipts are applied, assert `view_global_contract_code(AccountId(owner))` returns `evil_wasm`, not `benign_wasm`.
5. Assert `victim`'s subsequent `FunctionCall` now executes `evil_wasm`'s logic (e.g., exfiltrates a token/balance controlled by `victim`), despite `victim` never having interacted with `attacker` and `owner` never authorizing the redeploy.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

## DeployGlobalContractAction

```rust
pub struct DeployGlobalContractAction {
    /// WebAssembly binary
    pub code: Vec<u8>,
    /// How this global contract should be referenced
    pub deploy_mode: GlobalContractDeployMode,
}

pub enum GlobalContractDeployMode {
    /// Contract is deployed under its code hash.
    /// Users will be able reference it by that hash.
    /// This effectively makes the contract immutable.
    CodeHash,
    /// Contract is deployed under the owner account id.
    /// Users will be able reference it by that account id.
    /// This allows the owner to update the contract for all its users.
    AccountId,
}
```

**Outcome**:

- First, the provided code is made available as global contract on the current shard.
- The same code propagates globally, shard by shard.
- Eventually, all accounts on all shards can reference the submitted code by the corresponding global contract identifier.

### Errors

**Validation Error**:

- `ContractSizeExceeded` if the provided WebAssembly code is larger than `max_contract_size` (4MiB).

**Execution Error**:

- `LackBalanceForState` if the account does not hold enough NEAR to cover the added storage.
```

fn validate_deploy_global_contract_action(
