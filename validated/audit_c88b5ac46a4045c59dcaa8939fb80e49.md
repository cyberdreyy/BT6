### Title
Cross-user response hijacking via unchecked `MessageId` collision in webAPI trigger callback map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` unconditionally stores a caller-supplied `msg.Body.MessageId` into the shared `h.savedCallbacks` map without checking whether an entry for that ID already exists. [1](#0-0)  A second unprivileged webhook caller who submits a trigger request using a victim's in-flight `MessageId` silently overwrites the victim's saved callback, so the DON's later legitimate response is routed by `handleWebAPITriggerMessage` to the attacker's callback instead of the victim's. [2](#0-1) 

### Finding Description
`MessageId` in `api.MessageBody` originates from the requesting client and is used directly as the map key with no uniqueness check:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [1](#0-0) 

Later, when any authenticated DON node replies with that `MessageId`, `handleWebAPITriggerMessage` looks up and deletes whatever callback currently sits under that key and delivers the response to it, with no verification that the callback belongs to the request that originated the DON's fan-out:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [3](#0-2) 

Because `HandleLegacyUserMessage` is the reachable entry point for an ordinary/unprivileged webhook caller submitting a `web_api_trigger` request (not a DON-node-only path), an attacker who can predict or observe a victim's outstanding `MessageId` (e.g., short/sequential/reused IDs, or IDs echoed to the caller via other channels) can send their own crafted `web_api_trigger` request carrying that same `MessageId`. This overwrites `h.savedCallbacks[id]` before the real DON reply arrives. When the DON subsequently responds for the original request, the response is delivered to the attacker's callback (`savedCb.SendResponse`) rather than the victim's — the victim never receives a response (or receives none/error), and the attacker receives the victim's workflow trigger result. No authentication, node compromise, or DON-member impersonation is required; the flaw is a pure state-management bug in the gateway handler triggered by an unauthenticated/low-privileged caller controlling `MessageId`.

The `msg.Body.Sender != nodeAddr` check in `HandleNodeMessage` only validates that the *node's reply* is self-consistent; it does nothing to bind a specific `savedCallback` entry to the request that created it, so it cannot prevent this collision/overwrite. [4](#0-3) 

### Impact Explanation
This is cross-user response injection/leakage for webhook-triggered workflow results: an unprivileged attacker can hijack a victim's trigger response (potentially containing sensitive workflow output) and simultaneously deny the victim's own response delivery, by exploiting predictable/observable `MessageId` values and the unconditional overwrite of `h.savedCallbacks`.

### Likelihood Explanation
Exploitability depends entirely on whether `MessageId` values are guessable, reused, or otherwise observable by another low-privileged party before the DON responds (a short race window of up to `CallbackMaxAgeSec`, default 120s). [5](#0-4)  No node/DON compromise, no admin/operator access, and no signature bypass is needed — only the ability to submit a gateway `web_api_trigger` message with a chosen `MessageId`, which is the exact primitive `HandleLegacyUserMessage` accepts from any caller. The generation scheme for `MessageId` was not fully verifiable in this review; if IDs are cryptographically random and never disclosed to other users, guessing is infeasible, but the code itself provides no defense-in-depth against collision regardless of ID entropy.

### Recommendation
In `HandleLegacyUserMessage`, reject the request (or generate a fresh unpredictable ID) if `h.savedCallbacks[msg.Body.MessageId]` already exists instead of silently overwriting it. Additionally, bind saved callbacks to the originating requester (e.g., store and check a requester-derived value together with the ID) so that `handleWebAPITriggerMessage` can validate that the responding flow corresponds to the same originator before invoking `SendResponse`.

### Proof of Concept
Go handler-level test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Call `HandleLegacyUserMessage` with `msg.Body.MessageId = "id-1"` and `callback = cbVictim` (a mock capturing `SendResponse` calls); assert `h.savedCallbacks["id-1"].Callback == cbVictim`.
2. Before any node reply, call `HandleLegacyUserMessage` again with the same `MessageId = "id-1"` but `callback = cbAttacker`.
3. Assert `h.savedCallbacks["id-1"].Callback` is now `cbAttacker` (overwrite occurred) — this alone demonstrates the flaw without needing step 4.
4. Simulate the DON node's genuine reply via `HandleNodeMessage`/`handleWebAPITriggerMessage` with `nodeAddr` being a legitimate DON member; assert `cbAttacker.SendResponse` was invoked and `cbVictim.SendResponse` was never called, proving cross-user response delivery.
5. Recommended fix verification: after the fix, step 2's second `HandleLegacyUserMessage` call should return an error (duplicate/collision rejected) and `h.savedCallbacks["id-1"].Callback` should remain `cbVictim`.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
```
