### Title
Stale cross-epoch instant-withdraw receipts are excluded from default recovery basis but still paid at par — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The ionic bug fails to unmap/clean all pages of a multi-buffer packet — only the first page is handled, the rest stay mapped and are later reused, corrupting state. The direct analog in `IdleCreditVault` is the instant-withdraw accounting across epochs: `defaultPendingClaimBasis()` (lines 644–649) and `_defaultPrefundedInstantReserve()` (lines 716–723) only ever look at `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — while `pendingInstantWithdraws` and per-user `instantWithdrawsRequests` are aggregates that can carry unfunded receipts forward from earlier epochs. An instant receipt created in epoch N and never fully collected (partial prefunding at `startEpoch` is explicitly contemplated by the comment at lines 637–640) persists into epoch N+1: its per-epoch basis sits in `instantWithdrawClaimsByEpoch[N]`, which is never visited again — the "SG page" that is never cleaned.

### Finding Description
Sequence (running epoch, instant-withdraw mode, honest manager/borrower):

1. Epoch N: attacker (KYC-passing lender) calls `requestInstantWithdraw`; `instantWithdrawsRequestsByEpoch[attacker][N]`, `instantWithdrawClaimsByEpoch[N]`, `instantWithdrawsRequests[attacker]` and `pendingInstantWithdraws` all increase. The CDO only partially collects via `collectInstantWithdrawFunds` (line 398–403 decrements `pendingInstantWithdraws` but never clears `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch` — the uncleaned buffer pages). The attacker simply does not claim.
2. Epoch N+1: the unfunded remainder rides along inside `pendingInstantWithdraws`.
3. Borrower defaults; `finalizeDefaultRecovery` runs:
   - `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` (N+1), omitting the attacker's epoch-N basis from `totalBasis`.
   - `_defaultPrefundedInstantReserve()` computes `instantBasis(N+1) - pendingInstantWithdraws`; because `pendingInstantWithdraws` still contains the epoch-N remainder, the prefunded reserve is understated (can even clamp to 0).
   - `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` → true.
4. Attacker calls `claimInstantWithdrawRequest`: `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[attacker][N+1]` (= 0), then the function falls through and pays the *entire* `instantWithdrawsRequests[attacker]` — including the epoch-N receipt — at par through `_transferFundedClaim`.

The epoch-N receipt was never haircutted into the recovery price and was never funded into the recovery reserve, yet it is paid in full.

### Impact Explanation
Two compounding effects:
- `totalBasis` is understated → `recoveryPrice` is inflated → defaulted-epoch claimants (normal + instant) are overpaid relative to the true recovery, draining `defaultRecoveryReserve` early; later claimants (including `postDefaultRequests` users) find the reserve empty — insolvency for them.
- The attacker's stale epoch-N receipt is paid 1:1 from strategy balance that was implicitly backing the recovery pool (the `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`, not the prefunded-but-uncounted cash). Net effect: the attacker recovers ~100% on a defaulted receipt while honest claimants are diluted; loss magnitude equals the stale receipt amount.

### Likelihood Explanation
Requires only that an instant-withdraw request remain partially unfunded across an epoch boundary — an acknowledged state (the code comments describe startEpoch cash covering "only part of the instant queue"), and nothing forces full collection before `stopEpoch`/`startEpoch`. The attacker is an ordinary whitelisted lender who makes one request and waits; all privileged actors behave honestly. Caveat I could not fully verify in the remaining budget: exact CDO-side ordering of `collectInstantWithdrawFunds` relative to epoch transitions, which determines how easily the unfunded-remainder state arises.

### Recommendation
Account for *all* outstanding instant receipt epochs, not just `epochNumber`: either track a global `instantWithdrawClaimsTotal` (sum over epochs) used by both `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, or clear/settle stale per-epoch instant receipts at epoch boundaries so only the current epoch can ever be pending at finalization. Add an invariant test asserting `Σ instantWithdrawsRequestsByEpoch == instantWithdrawsRequests` totals before `finalizeDefaultRecovery`.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol style PoC sketch
// Setup: cdoEpoch vault, attacker = KYC'd AA lender, borrower honest.

// Epoch N
cdoEpoch.startEpoch(...);                       // manager
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(attackAmt);     // instantWithdrawClaimsByEpoch[N] += attackAmt
// CDO collects only part (or none) of the instant queue:
// pendingInstantWithdraws still > 0 crossing into next epoch

// Epoch N+1
cdoEpoch.stopEpoch(apr, 0);                     // manager, honest
cdoEpoch.startEpoch(...);
// attacker does NOT claim; instantWithdrawsRequestsByEpoch[attacker][N] stays set

// Borrower defaults, manager/keeper finalize:
cdoEpoch.stopEpochWithDuration(0, lossDuration); // default path
strategy.finalizeDefaultRecovery(recovered, recoverySource);
// defaultPendingClaimBasis() omitted instantWithdrawClaimsByEpoch[N]

// Attacker claims stale receipt at par:
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
// _claimDefaultedInstantWithdrawRequest clears only epoch N+1 (=0 for attacker),
// then _transferFundedClaim pays full instantWithdrawsRequests[attacker]
assertGt(underlying.balanceOf(attacker) - balPre, attackAmt * defaultRecoveryPrice / 1e18);
// attacker paid at par; recoveryReserve underfunded -> later claimants revert/shortfall
```
