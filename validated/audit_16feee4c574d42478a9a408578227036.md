### Title
Cross-workflow HTTP response cache confusion due to `WorkflowID`-agnostic cache key - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The Gateway's HTTP capability response cache is documented as providing "Workflow-scoped caching" / "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage," but the actual cache key (`OutboundHTTPRequest.Hash()`) does not incorporate `WorkflowID` — only method, URL, headers, body, and `WorkflowOwner` are hashed. Any two different workflows owned by the same address (or, more importantly, executed under the same owner identity across separate workflow deployments) that issue an HTTP Action with identical method/URL/headers/body will read and write the same cache entry.

### Finding Description
`responseCache.Fetch`/`Set`/`isExpiredOrNotCached` all key the cache map by `req.Hash()` [1](#0-0) , and the type's own comment states the hash is derived from "method, URL, headers, body, workflowOwner" [2](#0-1) . Unit tests explicitly assert that changing `WorkflowID` does **not** change the hash, while changing `WorkflowOwner` does: [3](#0-2) [4](#0-3) 

Meanwhile, the component's own README explicitly claims per-workflow isolation as a security property: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [5](#0-4) . The code and the documented invariant diverge — the documented protection is not actually enforced by `Hash()`.

The cache is populated/read from `makeOutgoingRequest`, which is invoked whenever a workflow-DON node sends an `HTTPAction` outbound request; the cache lookup/store happens purely based on the request's hash, without any additional per-workflow gating: [6](#0-5) .

This mirrors the NextGen bug class: a value/state (here, a cached HTTP response) computed under one scope (owner-level) is silently reused across a narrower scope that downstream logic/documentation assumes is isolated (workflow-level), because the intervening scoping dimension (`WorkflowID`) was dropped from the derivation, exactly as the NextGen `getPrice` formula silently carried over circulating-supply state across mint phases that were assumed independent.

### Impact Explanation
If two different workflows belonging to the same `WorkflowOwner` issue HTTP Action requests with identical method/URL/headers/body (e.g., both call the same public API endpoint with the same parameters), one workflow's cached HTTP response — including any response body containing per-workflow-sensitive data returned by the third-party API — will be served to the other workflow within the TTL window (default 10 minutes) [7](#0-6) . This is a cross-workflow response confusion: a workflow can receive data intended for/derived from a different workflow's outbound request context, and can also indirectly influence what data another (co-owned) workflow observes by causing an earlier request to populate the shared cache entry (e.g., poisoning the cache with a stale or attacker-influenced response body if the target endpoint's response depends on caller-side state).

### Likelihood Explanation
Likelihood is moderate to low: it requires two workflows under the same `WorkflowOwner` to issue byte-identical outbound HTTP requests (same method, URL, headers, body) with `CacheSettings.Store`/`MaxAgeMs` set, which is plausible for common integration patterns (e.g., templated workflows hitting the same public price/data feed URL with the same static parameters). It does not require any privileged access — any workflow owner deploying multiple workflows, or any user whose workflows share infrastructure/templates, can trigger it unintentionally, and it directly contradicts the documented workflow-isolation guarantee that operators may rely on for correctness/security.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) in the `OutboundHTTPRequest.Hash()` computation so cache entries are truly scoped per-workflow as documented, matching the README's stated invariant. Add a regression test asserting that requests differing only in `WorkflowID` produce different hashes (inverse of the current test at lines 139-149), and update/remove the misleading test/comment that currently encodes the opposite behavior as expected.

### Proof of Concept
1. Deploy two distinct workflows, `wfA` and `wfB`, both owned by the same `WorkflowOwner` address.
2. Have both workflows issue an HTTP Action request with `CacheSettings.Store=true`, `MaxAgeMs>0`, identical `Method`, `URL`, `Headers`, and `Body`, but different `WorkflowID`.
3. `wfA`'s request executes first, populating the cache via `responseCache.Set`/`Fetch` keyed by `req.Hash()` (which excludes `WorkflowID`): [8](#0-7) .
4. `wfB`'s subsequent identical request within the TTL window hits `isExpiredOrNotCached`/`Fetch` and returns `wfA`'s cached `OutboundHTTPResponse` without ever calling the HTTP client, as demonstrated by the existing test pattern for cache hits: [9](#0-8) , and confirmed structurally by `TestRequestHash`'s "different workflowID results in same Hash" case: [3](#0-2) .

func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
