Confirmed bug: in `multisig2/src/lib.rs`, `delete_member` only purges confirmations/requests for requests that were *originated* (`r.member == member`) by the deleted member [1](#0-0) . It never scans `self.confirmations` to strip stale confirmation entries that the deleted member left behind on *other* requests, and `confirm()` counts confirmations purely by set length against `self.num_confirmations` [2](#0-1) . That said, given remaining tool budget was exhausted before I could trace every path (e.g., whether `DeleteMember`+`AddMember` cycles are common, or whether any other code path purges confirmations by member across all requests), I want to flag that this specific mechanism should be validated further with a live Devin session before treating it as fully proven — but the structural gap is clear from the code shown above.

### Title
Stale confirmations from deleted multisig members are not purged and still count toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` removes a member from `self.members` and deletes only the requests *they personally created*, but does not remove that member's confirmation entries recorded on other, still-pending requests. `confirm()` determines whether to execute a request purely by comparing the size of the stored confirmation set to `num_confirmations`, without re-validating that every confirming identity is still a live member. This breaks the equality that should hold: `confirmations counted == confirmations from currently-live members`.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` fetches the confirmation `HashSet<String>` for a request and executes the request once `confirmations.len() + 1 >= self.num_confirmations` [2](#0-1) . The identities stored in that set are `MultisigMember::to_string()` values recorded at the time each member called `confirm`.

`delete_member` is invoked when a `DeleteMember` request executes:
```
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    let request_ids: Vec<u32> = self.requests.iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    ...
    self.members.remove(&member);
    ...
}
``` [3](#0-2) 

This only removes requests where `r.member == member`, i.e. requests *originated* by the deleted member. It does not iterate `self.confirmations` for requests originated by *other* members on which the deleted member had already called `confirm` and left an entry in the confirmation `HashSet`. Those stale string entries remain in `self.confirmations` for those other, still-open requests.

Because `confirm()` never checks `self.members.contains(...)` for the strings already stored in a request's confirmation set — it only checks whether the *new* caller (`current_member()`) is a member — a confirmation that was legitimately cast by an account/key which has since been removed from the multisig continues to count toward `num_confirmations` for that pending request.

### Impact Explanation
This is a Critical-class finding under the given impact classes: "a multisig request executed below threshold." Concretely: suppose `num_confirmations = 3` and members {A, B, C, D}. A malicious or compromised member A creates a request and confirms it (1/3). B confirms (2/3, still pending, one short). The multisig then legitimately removes A via a `DeleteMember` request (e.g., because A's key was compromised or A is being offboarded) — this deletion request is a separate, distinct request from the pending one, so `delete_member`'s cleanup loop (which only strips requests where `r.member == A`) does not touch the still-pending B-created/A-confirmed request. A's confirmation entry is never purged. Now only C needs to confirm — bringing the count to 3 — even though the effective live signer set is {B, C, D}, and the entity that was one of the "3 confirmations" (A) has already been formally revoked as an authority. The contract executes the request, funds move (`Transfer`, `FunctionCall`, `AddKey`, etc.) despite the confirmation threshold not being satisfied by three genuinely-current authorized members at the time of execution — accounting divergence: "confirmations counted versus live members."

### Likelihood Explanation
This requires no attacker privilege beyond being (or having been) a legitimate multisig member at some point before removal — a normal operational event (key rotation, offboarding a member, replacing a compromised key) rather than a rare edge case. Any multisig that rotates membership while requests are in flight (which `REQUEST_COOLDOWN`/`active_requests_limit` design implies is expected/normal usage) is exposed. No foundation, victim key, or malicious validator is needed — an ordinary member removal combined with any pending request from a prior period is sufficient.

### Recommendation
When a member is deleted (`delete_member`), iterate all entries in `self.confirmations` (not only requests originated by that member) and remove the deleted member's `to_string()` entry from every confirmation set. Alternatively, have `confirm()` re-validate, at confirmation-count time, that each string in the stored confirmation set still corresponds to a current entry in `self.members` before comparing the count to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 3` and members `{A, B, C, D}` via `new` [4](#0-3) .
2. As A: `add_request_and_confirm(request_X)` — a `Transfer` request; confirmations = {A} (1/3) [5](#0-4) .
3. As B: `confirm(request_X)` — confirmations = {A, B} (2/3, still pending) [6](#0-5) .
4. Separately, create and fully confirm a `DeleteMember { member: A }` request via C/D/self-request path, which executes `delete_member` for A. Note the cleanup only removes requests where `r.member == A`; `request_X` was created by A (`r.member == A`) — to avoid this edge and demonstrate the general case, have B create `request_X` instead of A in step 2, then A confirms it in step 3 (so `r.member == B`, not A) before A is deleted. `self.confirmations` for `request_X` still contains "A" afterward.
5. As C: `confirm(request_X)` — `confirmations.len() + 1 = 3 >= num_confirmations(3)` → request executes, even though the live authorized member set is now `{B, C, D}` and A's confirmation, cast while a member, is stale and uncheckable against current membership at execution time [7](#0-6) .

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
