### Title
ETH Push-Transfer in `BridgeVault.transferETH` Permanently Locks User Funds When Recipient Cannot Receive ETH — (`bridge/evm/contracts/BridgeVault.sol`)

---

### Summary

`BridgeVault.transferETH` uses a push pattern to deliver unwrapped ETH to the recipient address. If the recipient is a contract that cannot receive ETH, the low-level call fails, the `require` reverts the entire transaction, and `isTransferProcessed[nonce]` is never set. The bridge message becomes permanently unprocessable, and the corresponding ETH is locked in the vault forever with no recovery path.

---

### Finding Description

`BridgeVault.transferETH` unwraps WETH and immediately pushes the resulting ETH to `recipientAddress`:

```solidity
wETH.withdraw(amount);
(bool success,) = recipientAddress.call{value: amount}("");
require(success, "ETH transfer failed");
```

This is called from `SuiBridge._transferTokensFromVault` (v1) and `SuiBridgeV2._transferTokensFromVault` (v2) whenever `tokenID == BridgeUtils.ETH`:

```solidity
if (tokenID == BridgeUtils.ETH) {
    vault.transferETH(payable(recipientAddress), amount);
}
```

Both `transferBridgedTokensWithSignatures` (v1) and `transferBridgedTokensWithSignaturesV2` (v2) call `_transferTokensFromVault` **before** marking the nonce as processed:

```solidity
_transferTokensFromVault(...);          // ← reverts here if recipient rejects ETH
isTransferProcessed[message.nonce] = true;  // ← never reached
```

Because the entire transaction reverts atomically, `isTransferProcessed[nonce]` stays `false`. Every subsequent attempt to process the same message will also revert (the recipient still rejects ETH), so the message is permanently stuck and the ETH locked in the vault is irrecoverable. There is no admin rescue function in `BridgeVault` or `SuiBridge` to redirect or recover the funds.

---

### Impact Explanation

A user who bridges ETH from Sui to Ethereum and specifies a contract address that cannot receive ETH (e.g., a contract with no `receive()` / `fallback()`, or one that explicitly reverts on ETH receipt) as the Ethereum recipient will have their ETH permanently locked in `BridgeVault`. The bridge committee cannot process the signed message, and no on-chain recovery path exists. This is a **permanent fund lock** matching the High/Medium impact class.

---

### Likelihood Explanation

Any ordinary bridge user can trigger this by specifying a non-payable contract address as the Ethereum recipient when initiating a Sui→Ethereum ETH bridge transfer. No privileged access is required. The Sui-side tokens are burned/locked at initiation, so the user has already committed funds before the Ethereum-side failure occurs. The condition is reachable from public input with no special preconditions beyond owning ETH on Sui.

---

### Recommendation

Replace the push pattern with a pull (claim) pattern for ETH deliveries:

1. In `BridgeVault`, instead of calling `recipientAddress.call{value: amount}("")`, store the claimable amount in a mapping: `pendingETH[recipientAddress] += amount`.
2. Add a `claimETH()` function that lets the recipient withdraw their balance.
3. Mark `isTransferProcessed[nonce] = true` unconditionally after crediting the mapping, so the bridge message is always finalized.

Alternatively, wrap the ETH transfer failure gracefully: if the push fails, keep the ETH as WETH in the vault and emit an event so the recipient can claim WETH instead.

---

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

// A contract that cannot receive ETH
contract NoETHReceiver {}

// PoC test (Foundry)
function testPermanentFundLock() public {
    // 1. Fund vault with WETH (simulating ETH bridged from Sui)
    vm.deal(deployer, 1 ether);
    IWETH9(wETH).deposit{value: 1 ether}();
    IERC20(wETH).transfer(address(vault), 1 ether);

    // 2. Deploy a contract that cannot receive ETH
    NoETHReceiver badRecipient = new NoETHReceiver();

    // 3. Build a valid bridge message with badRecipient as the Ethereum recipient
    //    (this is what the bridge committee would sign after observing the Sui-side event)
    bytes memory payload = abi.encodePacked(
        uint8(32), abi.encode(0),          // senderAddress
        uint8(chainID),                     // targetChain
        uint8(20), address(badRecipient),   // recipientAddress = non-payable contract
        BridgeUtils.ETH,                    // tokenID
        uint64(100_000_000)                 // 1 ETH in Sui decimals
    );
    BridgeUtils.Message memory message = BridgeUtils.Message({
        messageType: BridgeUtils.TOKEN_TRANSFER,
        version: 1,
        nonce: 42,
        chainID: 0,
        payload: payload
    });

    bytes32 msgHash = keccak256(BridgeUtils.encodeMessage(message));
    bytes[] memory sigs = _gatherCommitteeSignatures(msgHash);

    // 4. Bridge committee tries to release ETH — REVERTS with "ETH transfer failed"
    vm.expectRevert(bytes("ETH transfer failed"));
    bridge.transferBridgedTokensWithSignatures(sigs, message);

    // 5. Nonce is still unprocessed — message can never be finalized
    assertFalse(bridge.isTransferProcessed(42));

    // 6. ETH remains locked in vault as WETH — no recovery function exists
    assertEq(IERC20(wETH).balanceOf(address(vault)), 1 ether);
}
```
