### Title
Pipeline run `Show` endpoint ignores `:ID` job scope, allowing cross-job pipeline run disclosure - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Show` handles `GET /v2/jobs/:ID/runs/:runID` but only ever reads `c.Param("runID")`; it never validates that the resolved `pipeline.Run` belongs to the job identified by `:ID`. Any authenticated user authorized to view/run at least one job's runs can supply an arbitrary `runID` belonging to a different job and receive that job's full run data, including task inputs/outputs.

### Finding Description
In `Show`: [1](#0-0) 
the handler builds a `pipeline.Run{}`, sets its ID solely from `c.Param("runID")`, and then calls `prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)` — a lookup keyed purely by run ID with no join/filter against the job ID taken from `c.Param("ID")`. The `:ID` route parameter is read nowhere in this function. Contrast this with `Index`, which explicitly parses `:ID` into a `job.Job{}` and passes `&jobSpec.ID` to `PipelineRuns(ctx, &jobSpec.ID, ...)` to scope results to that job — `Show` has no equivalent scoping call.

Because authorization for this route is enforced at the role-middleware layer (requiring the caller to hold at least run/view role generally, not per-job ownership) and the handler itself performs no cross-check between the URL's job ID and the run's actual owning job, a caller who is legitimately permitted to call `/v2/jobs/<jobA>/runs/<anyRunID>` can substitute any `runID` value — including one belonging to `jobB` — and the handler will happily return `jobB`'s pipeline run resource (inputs, outputs, task run details) via `presenters.NewPipelineRunResource`.

### Impact Explanation
This is a cross-user/cross-job response confusion vulnerability: a low-privileged user scoped/expected to only see runs for jobs they are permitted to access can read full pipeline run data (task inputs and outputs, which may contain secrets, external adapter responses, or proprietary job logic) for jobs they have no relationship to, by guessing or enumerating small sequential run IDs. This matches the "unauthorized disclosure of another user's/job's data" bounty impact class.

### Likelihood Explanation
Exploitation only requires a valid session/API token with run or view role (the minimum role able to reach this route at all) and knowledge or brute-force enumeration of a `runID` (pipeline run IDs are typically small sequential integers), making this highly feasible and repeatable — no special timing, race condition, or elevated privilege is required.

### Recommendation
In `Show`, parse `c.Param("ID")` into the job spec (as `Index` already does), and either query `FindRun` with an additional filter on job ID, or after fetching the run, verify `pipelineRun` (or its associated `PipelineSpec.JobID`) matches the requested job ID, returning `404`/`403` on mismatch.

### Proof of Concept
1. Create two jobs, `jobA` and `jobB`, each with a distinct pipeline spec, and trigger a run for each via `POST /v2/jobs/:ID/runs`, capturing `jobA-runID` and `jobB-runID`.
2. As a user with run-role access, call `GET /v2/jobs/<jobA-ID>/runs/<jobB-runID>`.
3. Assert (current buggy behavior) that HTTP 200 is returned with `jobB`'s pipeline run resource (its `Outputs`/`Inputs`, matching `jobB`'s pipeline spec ID) — i.e. the response is NOT scoped/rejected despite requesting via `jobA`'s job ID.
4. After fix, assert the same request returns 404/403, and only `GET /v2/jobs/<jobB-ID>/runs/<jobB-runID>` succeeds.

func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
	jsonAPIResponse(c, res, "pipelineRun")
}
