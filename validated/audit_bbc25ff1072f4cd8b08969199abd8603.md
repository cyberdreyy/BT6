### Title
Donated withdrawal-receipt strategy tokens inflate NAV and mint unbacked withdrawal claims - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
An unprivileged KYC-passed tranche holder can convert most of their position into an `IdleCreditVault` withdrawal receipt, transfer those receipt strategy tokens back to the CDO, and cause `getContractValue()` to count them as new pool backing. `_skimDonatedAssets()` removes only raw `token`, not donated `strategyToken`.

The next accounting update treats the donated receipt as profit. The attacker’s remaining dust tranche position is therefore priced at the donated amount and can be withdrawn as a second, largely unbacked receipt. This breaks the one-receipt-one-payout and solvency invariants.

### Finding Description
`requestWithdraw()` first skims raw underlying donations, updates accounting, burns CDO-held strategy-token principal, and mints the user a receipt representing principal plus expected interest:

- `contracts/IdleCDOEpochVariant.sol:739`
- `contracts/strategies/idle/IdleCreditVault.sol:243`
- `contracts/strategies/idle/IdleCreditVault.sol:272-275`

The receipt token is the vault’s ERC20 `strategyToken`. Nothing prevents its holder from transferring it directly to the CDO. Pool NAV counts the CDO’s strategy-token balance, while `_skimDonatedAssets()` only transfers the raw underlying balance to `feeReceiver`:

```solidity
// contracts/IdleCDOEpochVariant.sol:793-796
function _skimDonatedAssets() internal {
  _transferUnderlyings(feeReceiver, _contractTokenBalance(token));
}
```

After donating the receipt to the CDO, the attacker calls `requestWithdraw()` for a remaining dust tranche balance. `_updateAccounting()` sees the donated strategy tokens as a NAV increase and assigns that gain to the still-active tranche. The dust position is then converted into a new withdrawal receipt priced near the donated amount.

The first receipt remains recorded in `pendingWithdraws`, and the second request creates an additional claim. Total pending withdrawals can therefore approach twice the original principal even though the attacker supplied no new underlying.

### Impact Explanation
This can create direct theft or insolvency.

With an initial position of `N`, the attacker requests approximately `N - dust`, receives a receipt for that amount plus its withdrawal interest, and donates that receipt to the CDO. Accounting prices the remaining dust at approximately the donated amount. The second request creates another receipt of approximately `N`.

At epoch stop, `pendingWithdraws` can total nearly `2N` while the pool received only `N` of underlying principal. If the borrower is funded and has sufficient allowance, the protocol pulls and pays nearly `2N`, giving the attacker roughly `N` of excess funds. If the borrower cannot cover the inflated obligation, the protocol defaults or pending claims become undercollateralized.

### Likelihood Explanation
Likelihood is high where deposits and withdrawal requests are enabled:

- The attacker needs only a KYC-allowed wallet and a tranche position.
- No privileged role, borrower misconduct, oracle manipulation, or external vault failure is required.
- Receipt strategy tokens are transferable ERC20 claims.
- The existing donation guard checks only the raw underlying token and does not isolate donated `strategyToken`.
- The attack works in the normal buffer phase and does not depend on APR, instant withdrawals, programmable-borrower mode, or defaults.

### Recommendation
Prevent CDO-held strategy tokens that are not produced by an authorized accounting operation from being counted as NAV.

At minimum:

1. Track an explicit internal active strategy-token balance instead of using raw `strategyToken` balance for NAV, or
2. Extend donation handling to identify and remove/stray-account donated `IdleCreditVault` receipt tokens, while preserving legitimately minted CDO strategy tokens.

The safer fix is explicit accounting: increase internal strategy-token backing only in `deposit()`, `mintStrategyTokens()`, fee minting, or another authorized path. Do not derive backing from `balanceOf(address(this))`, because ERC20 receipt holders can increase that balance without creating pool assets.

Add a regression test where a withdrawal receipt is transferred to the CDO and verify that neither `virtualPrice`, `getContractValue`, nor a subsequent withdrawal request increases.

### Proof of Concept
The following Foundry-style sequence is reproducible in the existing credit-vault fork/test setup after `idleCDO`, `AAtranche`, `underlying`, `strategy`, `borrower`, and `manager` are initialized.

```solidity
function testReceiptDonationInflatesWithdrawalClaim() external {
    uint256 initial = 100_000 * ONE_SCALE;
    uint256 dust = 1 * ONE_SCALE;

    // KYC-attacker deposits into AA.
    deal(defaultUnderlying, attacker, initial);
    vm.startPrank(attacker);
    underlying.approve(address(idleCDO), initial);
    idleCDO.depositAA(initial);

    // Convert almost the whole position into a normal withdrawal receipt.
    uint256 firstShares = AAtranche.balanceOf(attacker) - dust;
    uint256 firstReceipt = idleCDO.requestWithdraw(firstShares, address(AAtranche));

    // The receipt is ordinary ERC20 strategyToken. Donate it to the CDO.
    IERC20(address(strategy)).transfer(address(idleCDO), firstReceipt);
    vm.stopPrank();

    uint256 navBefore = idleCDO.getContractValue();
    uint256 pendingBefore = strategy.pendingWithdraws();

    // Donation is not skimmed because _skimDonatedAssets only handles token.
    // The dust AA position is repriced using the donated strategy tokens.
    vm.prank(attacker);
    uint256 secondReceipt = idleCDO.requestWithdraw(0, address(AAtranche));

    uint256 pendingAfter = strategy.pendingWithdraws();

    assertGt(navBefore, firstReceipt * 9 / 10);
    assertGt(secondReceipt, firstReceipt * 9 / 10);
    assertGt(pendingAfter - pendingBefore, initial * 9 / 10);
}
```

A complete fork PoC should then fund `borrower`, advance past `epochEndDate`, and call the honest manager’s normal epoch-stop flow. The attempted `collectWithdrawFunds` amount is nearly twice the attacker’s deposited principal, demonstrating either excess borrower extraction or protocol insolvency/default.
