### Title
Stale confirmations from removed multisig members can be counted toward the approval threshold, allowing a request to execute below the intended `K`-of-`N` threshold - ([File: multisig2/src/lib.rs])

### Summary
The `MultiSigContract` in `multisig2/src/lib.rs` maintains a per-request `HashSet` of confirmations (as member identifiers) and executes a request once `confirmations.len() + 1 >= num_confirmations`. When a member is removed via `delete_member`, the contract only purges confirmations for requests that member itself created (`r.member == member`); it does not scan and strip that member's confirmations from other, still-pending requests where they had previously called `confirm`. A stale confirmation from a deleted/deauthorized member therefore keeps counting toward the threshold on other requests.

### Finding Description
`confirm()` computes whether a request should execute purely from the size of the confirmations set for that `request_id`: [1](#0-0) 
`delete_member()` removes the member from `self.members` and cleans up only requests they authored, plus their `num_requests_pk` entry: [2](#0-1) 
There is no code path that iterates `self.confirmations` for requests authored by *other* members to strip out a confirmation previously cast by the now-deleted member. This breaks the intended equality that should hold at execution time:

`live_member_confirmations(request_id) == num_confirmations`

Instead, what is actually checked is:

`all_recorded_confirmations(request_id) including confirmations from members removed after they confirmed >= num_confirmations`

Concretely: with members {A, B, C, D} and `num_confirmations = 3`, suppose A creates request X and B, C confirm it (2 confirmations, one short of threshold — execution not yet triggered). The foundation/owner then removes C via `delete_member` (e.g., because C's key was compromised or C is being offboarded). `delete_member` only cleans up requests where `r.member == C` (requests C personally created) — request X was created by A, so C's confirmation on X is untouched. Now only members {A, B, D} are live, and effective quorum should require 3 of these 3 remaining members. But request X's confirmations set still contains B and C (2 confirmations, including the now-invalid C). If D subsequently confirms X, `confirmations.len() + 1 == 3 >= num_confirmations`, and the request executes — using only 2 truly live confirmations (B and D) plus one stale one (C), i.e., executed with fewer genuinely authorized approvals than the configured threshold.

### Impact Explanation
This crosses the exact "confirmations counted versus live members" authorization boundary called out as in-scope. A multisig request (e.g., a `Transfer` action moving NEAR, a `DeployContract` upgrade, or an `AddKey`/`DeleteMember` action) can be pushed to execution using a stale confirmation from a member who has already been removed from the trust set — effectively letting a request execute below the operative threshold of live signers. Per the Critical impact criteria ("a multisig request executed below threshold"), this is a Critical-severity finding: it allows a party who is no longer authorized to still contribute to authorizing a fund transfer or other privileged action.

### Likelihood Explanation
This requires a realistic and even routine operational sequence: (1) a request is created and partially confirmed, (2) one of the confirming members is later removed (a common security/maintenance action, e.g. rotating out a compromised or departing signer), and (3) the remaining members continue to confirm the still-pending request without realizing a stale confirmation is embedded. No attacker exploit code or privileged action beyond the ordinary `delete_member`/`confirm` flow is required — it can happen unintentionally during normal multisig membership rotation, and could also be intentionally exploited by a member who confirms a request and then arranges/waits for their own removal to be requested for other reasons, banking on their confirmation persisting.

### Recommendation
When removing a member in `delete_member`, iterate over all pending requests' confirmation sets (not just requests authored by that member) and remove the departing member's account/key from each `confirmations` entry. Alternatively, validate at `confirm()`/execution time that every entry in the confirmations set still corresponds to a current `self.members` entry before counting it toward `num_confirmations`, discarding stale entries lazily.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. As A, call `add_request` to create request `X` (e.g., a `Transfer` action).
3. As B, call `confirm(X)` → confirmations = {B}.
4. As C, call `confirm(X)` → confirmations = {B, C} (2/3, not yet executed).
5. As a member (or via a separate `DeleteMember` request/confirm flow), execute `delete_member(C)` — this removes C from `self.members`, but request `X` was authored by A, so `delete_member`'s cleanup loop (`r.member == member`) does not touch request X's confirmations; {B, C} remains stored for X.
6. As D, call `confirm(X)` → `confirmations.len() + 1 == 3 >= num_confirmations(3)` → request X executes.
7. Result: request X executed with only 2 confirmations from members still in `self.members` (B and D) despite `num_confirmations = 3`, because C's stale confirmation (recorded before removal) was still counted.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
