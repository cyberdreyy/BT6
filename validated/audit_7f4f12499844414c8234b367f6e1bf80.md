### Title
Unbounded per-call CPU/memory cost in `jsonParsed` account decoding of BPF Buffer/ProgramData accounts scales with attacker-controlled on-chain account size, with no RPC-side cap - ([File: account-decoder/src/parse_bpf_loader.rs])

### Summary
`parse_bpf_upgradeable_loader` unconditionally base64-encodes the entire remaining account data for `UpgradeableLoaderState::Buffer` and `UpgradeableLoaderState::ProgramData` variants with no size ceiling, unlike the sibling base58 path which enforces `MAX_BASE58_BYTES`. Since accounts owned by `bpf_loader_upgradeable` can be funded and written up to `MAX_ACCOUNT_DATA_LEN` (10 MiB) by any unprivileged actor, a single `getAccountInfo(pubkey, {encoding:'jsonParsed'})` call forces the RPC thread to base64-encode up to 10 MiB, with cost scaling by attacker-chosen account size rather than any RPC-enforced limit.

### Finding Description
The call path is: `JsonRpcRequestProcessor::get_account_info` (`rpc/src/rpc.rs:534-560`) → `get_encoded_account` (`rpc/src/rpc.rs:2552-2573`) → `encode_account` (`rpc/src/rpc.rs:2575-2601`) → `encode_ui_account` (`account-decoder/src/lib.rs:46-101`) → for `UiAccountEncoding::JsonParsed`, `parse_account_data_v3` → `parse_bpf_upgradeable_loader` (`account-decoder/src/parse_bpf_loader.rs:13-64`).

`encode_account` only enforces a size check (`MAX_BASE58_BYTES = 128`) for `Binary`/`Base58` encodings [1](#0-0) . For `Base64` and `JsonParsed` there is no equivalent guard [2](#0-1) . Inside `parse_bpf_upgradeable_loader`, both the `Buffer` and `ProgramData` branches call `BASE64_STANDARD.encode(&data[offset..])` on the full remaining account bytes with no length check [3](#0-2) [4](#0-3) .

An unprivileged attacker can create and fund a `Buffer` account owned by `bpf_loader_upgradeable` (e.g. via `create_buffer`/`write` instructions, which require no special authority beyond paying rent) and grow its data up to `MAX_ACCOUNT_DATA_LEN = 10 * 1024 * 1024` bytes [5](#0-4) . A single subsequent `getAccountInfo` call with `encoding: "jsonParsed"` on that pubkey then triggers `BASE64_STANDARD.encode` over the full 10 MiB payload synchronously on the RPC thread, with cost proportional to attacker-chosen `data().len()` and no RPC-side cap comparable to `MAX_BASE58_BYTES` or the transaction-size caps (`MAX_BASE64_SIZE`, etc.) used elsewhere in `rpc.rs` [6](#0-5) .

### Impact Explanation
A single unprivileged client, at ≤1 request per `CLUSTER_SLOT_TIME_TARGET/2`, can force the validator's JSON-RPC service to spend CPU/memory proportional to a 10 MiB base64 encode plus JSON serialization on every `getAccountInfo`/`getMultipleAccounts`/`getProgramAccounts`(jsonParsed) call against the attacker's own Buffer/ProgramData account. This matches the "unbounded cost for a single low-rate call" category: no crash, but a per-call multi-hundred-millisecond+ CPU/allocation stall bounded only by the attacker-authored account size rather than an explicit RPC-side limit, unlike the analogous and already-guarded base58 path.

### Likelihood Explanation
Fully feasible with no privileged access: fund a rent-exempt Buffer account, extend it with `write`/realloc-style instructions up to 10 MiB (standard, permitted operations for the BPF Upgradeable Loader), then issue one `getAccountInfo` call with `jsonParsed` encoding. Repeatable at will, bounded only by the attacker's willingness to pay rent for a large account.

### Recommendation
Add an explicit size guard in `parse_bpf_upgradeable_loader` (or upstream in `encode_ui_account`/`encode_account`) analogous to the `MAX_BASE58_BYTES` check for `Binary`/`Base58`, e.g. cap the base64-encoded `Buffer`/`ProgramData` payload size and fall back to returning an error/truncated marker (similar to the `"error: data too large for bs58 encoding"` pattern) when `data[offset..].len()` exceeds a defined threshold, so that decoding cost for `jsonParsed`/`Base64` on BPF loader accounts is bounded independent of attacker-controlled account size.

### Proof of Concept
```rust
// account-decoder/src/parse_bpf_loader.rs (integration-style test)
use std::time::Instant;
use bincode::serialize;
use solana_loader_v3_interface::state::UpgradeableLoaderState;
use solana_pubkey::Pubkey;

#[test]
fn test_parse_bpf_upgradeable_loader_cost_scales_with_attacker_size() {
    let authority = Pubkey::new_unique();
    for size_mb in [1usize, 5, 10] {
        let program = vec![7u8; size_mb * 1024 * 1024];
        let state = UpgradeableLoaderState::Buffer {
            authority_address: Some(authority),
        };
        let mut account_data = serialize(&state).unwrap();
        account_data.extend_from_slice(&program);

        let start = Instant::now();
        let _ = parse_bpf_upgradeable_loader(&account_data).unwrap();
        let elapsed = start.elapsed();

        // No cap exists today: elapsed time and allocation grow with size_mb.
        // Expected fix: cost should be bounded by an explicit constant
        // regardless of size_mb, or parse_bpf_upgradeable_loader should
        // return an error for payloads above a defined MAX size.
        println!("size={size_mb}MB elapsed={elapsed:?}");
    }
}
```
Expected (current, vulnerable) behavior: encode time grows roughly linearly with `size_mb` up to 10 MB, with no error returned and no RPC-layer size ceiling enforced before invoking `jsonParsed`/`Base64` decoding, contrasting with the `Base58` path which is explicitly capped in `encode_account` (`rpc/src/rpc.rs:2581-2596`).
