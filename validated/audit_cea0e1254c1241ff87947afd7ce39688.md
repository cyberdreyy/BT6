Based on my analysis of `multisig2/src/lib.rs`, I found a concrete analog that fits the required bug class ("confirmations counted versus live members").

### Title
Stale confirmations from deleted multisig members are counted toward the confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
The `MultiSigContract` in `multisig2/src/lib.rs` tracks per-request confirmations in a `HashSet<String>` keyed by request ID [1](#0-0) . When a member is removed via `delete_member`, the contract only purges requests and confirmation sets for requests that the removed member *originally created* (`r.member == member`), and clears the member's own `num_requests_pk` entry [2](#0-1) . It never scans other pending requests' `confirmations` sets to strip out entries the deleted member previously added as a *confirmer*. Consequently, a confirmation cast by a member before their removal remains permanently counted toward `num_confirmations` for any request they are not the creator of.

### Finding Description
`confirm()` computes whether a request should execute purely by comparing the size of the stored confirmation set against `num_confirmations`, with no re-validation that every entry in that set still corresponds to a current member: `if confirmations.len() as u32 + 1 >= self.num_confirmations { ... execute_request(...) }` [3](#0-2) . `delete_member` enforces that the remaining member count still meets `num_confirmations`, but this only guards *membership size*, not the validity of confirmations already recorded by a member who is being removed [4](#0-3) .

This breaks the intended equality: `confirmations counted == confirmations from live members`. In reality, after a `DeleteMember` action executes, a stale confirmation string from the removed member can still be sitting inside `self.confirmations` for any request they weren't the original signer of, and it continues to count toward the threshold.

### Impact Explanation
This allows a `K`-of-`N` request to execute with fewer than `K` *live* member confirmations, directly undermining the multisig's core security guarantee that `K` current members must approve any transfer, key change, or membership change. Per the impact criteria, this is "a multisig request executed below threshold" — Critical impact, since it can enable unauthorized transfers or contract mutations approved by fewer live signers than configured.

### Likelihood Explanation
The precondition is a normal, expected lifecycle event rather than any privileged misbehavior: a member confirms a pending request, and separately (for unrelated, legitimate reasons such as departure or key rotation) the multisig later votes to remove that member via `DeleteMember`. No malicious intent or elevated capability beyond ordinary use of `confirm`/`add_request`/`DeleteMember` is required for the stale entry to persist; it only takes one more legitimate confirmer to trip the flawed threshold check.

### Recommendation
When executing `DeleteMember`, iterate over all outstanding requests' `confirmations` sets and remove any entry matching the deleted member (not just requests the member created), or re-validate at `confirm()` time that every string in the confirmation set still `self.members.contains(...)` before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new([A, B, C], 2)`.
2. `A.add_request(transfer_request)` → creates request `R` with empty confirmations.
3. `B.confirm(R)` → `confirmations = {B}` since `0 + 1 < 2` [5](#0-4) .
4. Via a separately confirmed `DeleteMember{B}` request (approved by A and C), `B` is removed. `delete_member` only clears confirmations for requests `B` created, and `R` was created by `A`, so `R`'s confirmation set `{B}` is untouched [6](#0-5) . Members are now `{A, C}`.
5. `C.confirm(R)` → `confirmations.len() == 1` (stale `B`) `+ 1 >= 2` → `execute_request` runs the transfer [7](#0-6) .

Only one live member (`C`) actually confirmed `R` after `B`'s removal, yet the transfer executes as if two members approved it, bypassing the configured 2-of-3 threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
