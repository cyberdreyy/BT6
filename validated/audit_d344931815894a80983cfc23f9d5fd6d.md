### Title
EIP-8130 config-change channel sequence checked by strict equality creates a per-account front-running DoS - (File: crates/execution/eip8130/src/config.rs, crates/execution/eip8130/src/apply.rs)

### Summary
EIP-8130's `Multichain`/`Local` config-change channels validate a caller-supplied `sequence` field by strict equality against the account's live `state.multichain_sequence` / `state.local_sequence`, and that counter is advanced by *any* accepted config-change batch for the account before another pending batch for the same account lands. This mirrors the reported Lockbox pattern (`num_positions != id` reverting, and `num_positions` incrementing on every accepted call) at the level of an EIP-8130 account's channel sequence.

### Finding Description
`ConfigChangeAuthorizer::check_channel_sequence` requires `change.sequence == state.multichain_sequence` (or the local-channel equivalent) exactly, rejecting with `TxAuthError::BadSequence` on any mismatch: [1](#0-0) 

Every successfully applied batch then advances the same counter by exactly one via `AccountChangeApplier::advance_channel_sequence`: [2](#0-1) 

The test `stale_second_same_channel_entry_is_rejected` demonstrates exactly the front-running shape: two batches both claiming `sequence = 0` — once the first is applied and advances the channel to `1`, the second (identical intent) is rejected with `BadSequence { expected: 1, got: 0 }`: [3](#0-2) 

Any actor authorized to submit config changes for an account (which, per `SCOPE_OPERATOR`/self-key authorization, need not be the sole party controlling the account — e.g., an operator-scoped actor, or a payer/sponsor relationship) can observe a pending config-change transaction in the mempool and race to land a *different* (even a harmless/no-op-ish) change at the same expected sequence first. Because the txpool's admission path (`validate_eip8130_full`) also authorizes and applies against a snapshot before checking nonce/sequence state, an attacker who is even a partial co-authorized actor on the account can repeatedly re-observe the victim's re-submitted sequence and beat it, permanently starving the victim's legitimate config change (revoke, authorize, lock, etc.) from ever landing — a persistent, targeted DoS against a specific account's ability to update its own security configuration (e.g., revoking a compromised actor).

### Impact Explanation
This differs from the standard EVM nonce (which is exclusively owned/incremented by the account's own signed transactions) in that the multichain/local sequence for EIP-8130 accounts can be advanced by *any authorized actor's* signed batch for that account, not solely the account owner's canonical single signer. Where multiple actors (operator-scoped keys, delegated signers, or cross-chain relayers on the `Multichain` channel) are authorized, a malicious co-actor can perpetually front-run and invalidate a legitimate actor's attempt to update account configuration — most critically, blocking an urgent `RevokeActor` intended to remove a compromised key. This is a Medium-severity griefing/DoS against account security operations, not a full loss-of-funds primitive, since it requires the attacker to already hold a co-authorized actor role on the target account.

### Likelihood Explanation
Likelihood is Medium: it requires (a) an account with more than one authorized actor sharing the same channel (a supported, intended EIP-8130 configuration — e.g., operator-scoped delegated signers or multichain relayers), and (b) mempool visibility to detect the victim's pending sequence and race a replacement transaction ahead of it, which is straightforward MEV-style front-running available to any unprivileged party monitoring the public mempool.

### Recommendation
Avoid rejecting a config-change purely because the shared counter advanced from a *different* actor's batch. Options include: binding sequence slots per-`(account, actor)` rather than one shared per-channel counter (mirroring the existing 2D nonce-manager's per-`(account, nonce_key)` design in `crates/common/precompiles/src/nonce/storage.rs`), or admitting a config-change bounded by an actor-supplied nonce space that only that actor's prior batches can advance, so an unrelated co-actor's activity cannot invalidate a pending signed batch.

### Proof of Concept
1. Account `A` authorizes two actors: `Op1` (attacker, `SCOPE_OPERATOR`) and `Op2` (victim, needs to revoke a compromised key).
2. `Op2` signs and broadcasts `ConfigChange { channel: Multichain, sequence: N, changes: [RevokeActor(compromised_key)] }`.
3. `Op1` observes this in the mempool and immediately submits any valid `ConfigChange { channel: Multichain, sequence: N, changes: [...] }` (e.g., a benign self-authorize) with higher gas/fee.
4. `Op1`'s transaction lands first; `advance_channel_sequence` bumps `state.multichain_sequence` to `N+1` per `crates/execution/eip8130/src/apply.rs` lines 498-512.
5. `Op2`'s original transaction is now rejected at inclusion (and in the pool before that) with `TxAuthError::BadSequence { expected: N+1, got: N }`, exactly as reproduced by the `stale_second_same_channel_entry_is_rejected` test.
6. `Op2` must resubmit at `N+1`; `Op1` repeats the race indefinitely, permanently blocking the revoke of the compromised key.
