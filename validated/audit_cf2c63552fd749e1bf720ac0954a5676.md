### Title
`setFeeParams` checkpoints management fee but applies the new performance `fee` retroactively to unaccrued yield - (File: contracts/IdleCDOCreditVault.sol)

### Summary
The Angle M-06 bug class is "a yield-affecting parameter is changed without first crystallizing accrued yield under the old parameter, and a partial mitigation only checkpoints part of the state." The same pattern exists in `IdleCDOCreditVault.setFeeParams`: it calls `_accrueManagementFee()` before overwriting `managementFee`, correctly checkpointing the time-based fee, but it does not run `_updateAccounting()` before overwriting `fee`. Performance fees are charged lazily in `_updateAccounting` as `(nav - lastNAV) * fee / FULL_ALLOC`, so all yield accrued since the last checkpoint is taxed at the *new* rate rather than the rate in force while it accrued.

### Finding Description
- `setFeeParams` at `contracts/IdleCDOCreditVault.sol:461-470` does:
  ```solidity
  _accrueManagementFee();
  fee = _fee;
  feeSplit = _feeSplit;
  managementFee = _managementFee;
  ```
  `_accrueManagementFee` (lines 552-555) only checkpoints `managementFee` accrual into `unclaimedFees` and resets `latestHarvestBlock`.
- The performance fee is not checkpointed. In `_updateAccounting` (lines 230-232):
  ```solidity
  if (nav > _lastNAV) {
    unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;
  }
  ```
  `nav - lastNAV` is *all* gain accrued since the last deposit/withdraw/harvest, regardless of when it accrued. When `setFeeParams` raises `fee`, the next `_updateAccounting` applies the new, higher `fee` to the entire pending gain.
- This is the exact analog of M-06: the mitigation (accrue before param change) is partially implemented — only the management-fee leg is checkpointed — while the performance-fee leg and `trancheAPRSplitRatio` changes remain vulnerable. `setTrancheAPRSplitRatio` in `IdleCDO.sol:900-903` similarly changes the AA/BB yield split without calling `_updateAccounting()`, so pending yield is split at the new ratio retroactively.

### Impact Explanation
Whenever yield has accrued in the strategy since the last accounting (which is common — accounting only runs on deposits, withdrawal requests, and epoch stops), an honest owner/manager `setFeeParams` call that increases `fee` or `feeSplit` retroactively skims `(nav - lastNAV) * Δfee / FULL_ALLOC` from tranche holders' already-earned yield to `feeReceiver`/`owner`. Symmetrically, lowering `fee` retroactively gifts the fee recipient's entitled share of old yield back to LPs (accounting error in the other direction). Loss magnitude is bounded by `pending gain * Δfee`, which for a 10%→20% fee change on e.g. 100,000 underlying of accrued-but-uncheckpointed interest is ~10,000 underlying redirected away from AA/BB holders. In the epoch variant this can occur during the buffer phase right before `startEpoch`, where the inflated `unclaimedFees` then reduce the NAV feeding `expectedEpochInterest` and `lastEpochInterest` calculations.

### Likelihood Explanation
- `setFeeParams` is a routine owner operation; fee changes on live vaults are realistic governance actions (the function exists specifically for that).
- No attacker action is required beyond normal protocol use: an unprivileged user can also *frontrun* a pending fee-increase transaction with a `requestWithdraw` to lock receipts computed under the old fee via `_totalWithdrawFees`, while remaining LPs absorb the retroactively higher fee — directly matching the "users lose a portion of yield when parameters are changed" framing of the original finding.
- The only guard is that callers are honest; the code itself performs no checkpoint, exactly the acknowledged-but-incompletely-mitigated class from M-06.

### Recommendation
In `setFeeParams`, run full accounting under the old parameters before overwriting them — e.g. call `_skimDonatedAssets()` (epoch variant) and `_forceUpdateAccounting()` (or at least compute and add the pending performance fee `(getContractValue() - lastNAVAA - lastNAVBB) * fee / FULL_ALLOC` to `unclaimedFees`) before assigning `fee`/`feeSplit`. Apply the same treatment to `setTrancheAPRSplitRatio` in `IdleCDO.sol`/any credit-vault override: call `_updateAccounting()` first so accrued yield is split under the old ratio.

### Proof of Concept
```solidity
// test/foundry/RetroactiveFee.t.sol — fork-style, modeled on IdleCreditVault.t.sol
function testSetFeeParamsAppliesNewFeeRetroactively() external {
    uint256 amount = 1_000_000 * ONE_SCALE;
    uint256 interest = 10_000 * ONE_SCALE; // already accrued in strategy NAV, not yet checkpointed

    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // simulate accrued yield: strategy price/NAV increases by `interest`
    // while fee = oldFee (e.g. 10_000 = 10%)
    _accrueYield(interest);

    uint256 navBefore = cdoEpoch.getContractValue(); // amount + interest
    uint256 lastNAV = cdoEpoch.lastNAVAA() + cdoEpoch.lastNAVBB(); // amount

    // Owner raises performance fee from 10% to 20%.
    // _accrueManagementFee() runs but pending performance fee is NOT checkpointed.
    _setFeeParams(TL_MULTISIG, 20_000, FULL_ALLOC, cdoEpoch.managementFee());

    // Next interaction triggers _updateAccounting, which charges the NEW fee
    // on the ENTIRE (nav - lastNAV), including yield earned under the old 10% fee.
    vm.prank(owner);
    cdoEpoch.updateAccounting();

    uint256 expectedFees = interest * 10_000 / FULL_ALLOC;      // fee in force while yield accrued
    uint256 actualFees   = interest * 20_000 / FULL_ALLOC;      // charged retroactively
    assertEq(cdoEpoch.unclaimedFees(), actualFees, "new fee applied to old yield");
    assertGt(actualFees - expectedFees, 0, "LPs lose yield to feeReceiver");
}
```
