### Title
`JsonRpcRequestProcessor::bank()` silently falls back to the root bank when the commitment-selected slot is missing from `BankForks`, returning stale/wrong-slot data with no error - ([File: rpc/src/rpc.rs])

### Summary
The Chainlink report's root cause is that `latestRoundData` is consumed without validating that the returned data corresponds to the requested/expected round, allowing stale data to be silently used as if it were fresh. The analogous pattern in agave is `JsonRpcRequestProcessor::bank()`, the function almost all read-only JSON-RPC handlers (`getBalance`, `getAccountInfo`, `getSlot`, etc.) use to resolve a `CommitmentConfig` into an `Arc<Bank>`. When the slot computed for the requested commitment cannot be found in `BankForks`, the code does not return an error to the caller; it logs a warning and silently substitutes `r_bank_forks.root_bank()` instead.

### Finding Description
`bank()` computes a target `slot` from the requested commitment via `block_commitment_cache.slot_with_commitment(...)`, then looks it up in `BankForks`: [1](#0-0) 

If `r_bank_forks.get(slot)` returns `None`, the code does not propagate an error to the RPC client — it emits a `warn!` log and returns `r_bank_forks.root_bank()` instead, per the comment acknowledging this is "a known bug that should be fixed instead" (referencing solana-labs/solana#11078). This means an unprivileged RPC caller requesting data at a specific commitment level can receive an `Ok(...)` response computed against a completely different (older/root) bank/slot than the one they requested, with no indication in the response that a substitution occurred, exactly mirroring the Chainlink pattern of consuming unchecked/mismatched data as if it were the requested fresh data.

This `bank()` helper is the single point behind nearly all JSON-RPC read methods (10 call sites of `self.bank(commitment)` in `rpc/src/rpc.rs`), so any endpoint relying on it inherits this silent substitution behavior. Note that `get_bank_with_config()`, used by the newer `min_context_slot`-aware endpoints, does check the resolved bank's slot against `min_context_slot` and errors with `MinContextSlotNotReached`: [2](#0-1)  — but `bank()` itself has no equivalent staleness/slot-mismatch guard for the general (non-`min_context_slot`) path.

### Impact Explanation
An unprivileged client can trigger wrong-slot/fork data to be silently returned for a request that specified a particular commitment level (e.g. `confirmed`/`finalized`), because the substituted root bank may be far behind the requested slot. This matches the "wrong-slot/fork/account data returned" acceptance criterion: the client has no way to distinguish a legitimate response from one silently computed against a stale bank, which can mislead downstream consumers (wallets, indexers) into believing they observed the requested commitment level's state when they actually got older data.

### Likelihood Explanation
The fallback path is reachable whenever `BlockCommitmentCache`'s view of the commitment-slot momentarily diverges from what's currently retained in `BankForks` (e.g., during root advancement/pruning races, or after `BankForks` purges old banks before `BlockCommitmentCache` updates) — the same race the pre-existing code comment describes. This can be triggered by any single unprivileged JSON-RPC call during a normal, non-adversarial operational window (no crafted transactions or multiple clients needed), just an ordinary RPC read hitting the timing window.

### Recommendation
In `bank()`, when `r_bank_forks.get(slot)` returns `None`, return an explicit RPC error (e.g., a `RpcCustomError` analogous to `BlockNotAvailable`/`MinContextSlotNotReached`) instead of silently substituting `root_bank()`. At minimum, callers should be able to detect that the requested commitment slot was unavailable rather than receiving a masked, potentially stale bank.

### Proof of Concept
Not independently reproducible from static review alone (requires timing the race between `BlockCommitmentCache` slot updates and `BankForks` pruning); the vulnerable code path and its acknowledged-bug status are directly evidenced in-repo: [3](#0-2)

    fn get_bank_with_config(&self, config: RpcContextConfig) -> Result<Arc<Bank>> {
        let RpcContextConfig {
            commitment,
            min_context_slot,
        } = config;
        let bank = self.bank(commitment);
        if let Some(min_context_slot) = min_context_slot
            && bank.slot() < min_context_slot
        {
            return Err(RpcCustomError::MinContextSlotNotReached {
                context_slot: bank.slot(),
            }
            .into());
        }
        Ok(bank)
    }
