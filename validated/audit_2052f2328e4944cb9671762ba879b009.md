### Title
Permissionless `LockupFactory::create()` lets anyone front-run a victim's deterministic lockup address and deploy it with `vesting_schedule=None`, permanently stripping the NEAR Foundation's `foundation_account_id` binding - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` has no restriction tying `owner_account_id` to `predecessor_account_id`, so any unprivileged caller can invoke it for an arbitrary victim address and choose `vesting_schedule=None`. Because the resulting lockup account name is a pure deterministic function of `owner_account_id` (`sha256(owner_account_id)[..20].<factory>`), whoever's `create()` receipt executes first permanently occupies that address, and the real grantor's later attempt with the intended vesting schedule can never land there.

### Finding Description
The broken binding: for a given `owner_account_id = victim`, the eventual on-chain `(vesting_information, foundation_account_id)` at `sha256(victim)[..20].<factory>` should equal what the *legitimate* grantor's `vesting_schedule` argument would have produced. Instead it equals whatever the *first successful caller's* argument was.

Code path:
- `create()` computes the deterministic account id purely from `owner_account_id` with no check that `env::predecessor_account_id()` is the victim, the foundation, or any authorized party: [1](#0-0) 
- `foundation_account` is derived solely from whatever `vesting_schedule` value the caller passed: [2](#0-1) 
- The account is created via a single atomic multi-action promise (`create_account` + `deploy_contract` + `transfer` + `function_call`); whichever caller's receipt executes first wins the account name, and a second call targeting the same name fails at `create_account` because the account already exists: [3](#0-2) 
- The callback confirms this race behavior: on failure, the caller's attached deposit is refunded to them (not credited to the squatted account), while a success is simply logged: [4](#0-3) 
- Inside `LockupContract::new`, the invariant enforced is only internal self-consistency (`vesting_information == None` iff `foundation_account_id.is_none()`), not any binding to what the "real" grantor intended - it trusts whatever the factory passed in: [5](#0-4) 

Exploit flow: attacker observes/anticipates a grantor's intent to create a vesting lockup for `victim`, and submits `create(owner_account_id=victim, vesting_schedule=None, ...)` with the minimum attached deposit, timed to land before the grantor's transaction. Attacker's receipt succeeds first, deploying `LockupContract` at the deterministic address with `vesting_information: VestingInformation::None` and `foundation_account_id: None`. The grantor's subsequent `create()` call for the same `victim` fails at `create_account` (name taken) and is refunded via `on_lockup_create`'s failure branch - the grantor's real vesting-controlled funds never reach the squatted contract, but the deterministic name intended for `victim`'s Foundation-supervised lockup is now permanently occupied with parameters (`None`/`None`) the rightful grantor never chose.

No existing guard prevents this: there is no `assert_called_by_foundation`, no check that `predecessor_account_id == owner_account_id`, and no uniqueness reservation mechanism prior to account creation.

### Impact Explanation
This matches the explicitly listed Critical category "a lockup deployed with parameters its rightful creator never chose." The squatted lockup contract permanently occupies the one deterministic address `sha256(victim)[..20].<factory>` that the grantor's tooling would compute for `victim`, with `foundation_account_id = None`, meaning any future attempt to place vested/terminable tokens for `victim` at that canonical address is blocked and the NEAR Foundation's termination rights over that name are foreclosed. This is repeatable for any `owner_account_id` an attacker chooses to squat ahead of the real grantor, at a cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) per squatted name. The real grantor's attached deposit is refunded rather than lost, so no direct fund theft occurs from that specific transaction, but the parameter-integrity impact (wrong `vesting_information`/`foundation_account_id` bound to the intended deterministic name) is the Critical harm being asked about here.

### Likelihood Explanation
The precondition is simply winning a transaction race: the attacker needs to know (or guess) the `owner_account_id` a grantor intends to use and submit `create()` first, which is realistic given `owner_account_id`s (employee/vendor NEAR account names) are often predictable or publicly known/negotiated in advance. The attack costs only the minimum attached deposit and standard gas, is fully repeatable across any number of victim account names, and requires no privileged role - fully within the unprivileged attacker capability set defined by the rules.

### Recommendation
Add access control to `create()` so that only the intended owner (`predecessor_account_id == owner_account_id.as_ref()`) or an explicitly authorized party (e.g., the foundation account) can create a lockup for a given `owner_account_id`, or otherwise remove the fully-deterministic 1:1 mapping between `owner_account_id` and the lockup account name (e.g., incorporate a nonce/salt chosen by an authorized creator) so squatting a victim's canonical address is not possible.

### Proof of Concept
```rust
// lockup-factory/src/lib.rs tests module (extend existing tests)
#[test]
fn test_owner_squat_blocks_intended_vesting_lockup() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker front-runs with vesting_schedule = None for victim's account id.
    context.predecessor_account_id = String::from("attacker");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, /*vesting_schedule*/ None, None, None);

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    // Squat succeeds -> deterministic address now bound to VestingInformation::None / foundation_account_id: None
    assert!(contract.on_lockup_create(lockup_account(), ntoy(30).into(), String::from("attacker")));

    // Real grantor now tries to create the SAME deterministic account with a real vesting schedule.
    let vesting_schedule = Some(VestingScheduleOrHash::VestingHash(
        VestingScheduleWithSalt {
            vesting_schedule: new_vesting_schedule(10),
            salt: SALT.to_vec().into(),
        }.hash().into(),
    ));
    context.predecessor_account_id = String::from("real_grantor");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, vesting_schedule, None, None);

    // Underlying create_account fails because account name already exists -> refund path.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let created = contract.on_lockup_create(lockup_account(), ntoy(35).into(), String::from("real_grantor"));

    // Assert the equality is broken: intended vesting binding never applied at the deterministic address.
    assert_eq!(created, false, "Real grantor's vesting-enabled lockup could not be created at the squatted deterministic address");
    // (Separately, in lockup/src/lib.rs unit tests: assert the squatted contract's
    // vesting_information == VestingInformation::None and foundation_account_id == None,
    // versus a control contract created with the same owner but vesting_schedule = Some(...)
    // showing foundation_account_id == Some(foundation_account_id()).)
}
```

```rust
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```
