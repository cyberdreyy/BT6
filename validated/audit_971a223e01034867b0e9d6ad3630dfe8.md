### Title
Unprivileged `simulateTransaction` RPC call with `processed` commitment can crash the validator via an unguarded `assert!` - (File: `rpc/src/rpc.rs`, `runtime/src/bank.rs`)

### Summary
The `simulateTransaction` JSON-RPC method retrieves a bank via `JsonRpcRequestProcessor::bank()`/`get_bank_with_config()` and then unconditionally calls `Bank::simulate_transaction()`, which enforces `assert!(self.is_frozen(), "simulation bank must be frozen")`. When the client requests `commitment: "processed"`, the bank returned can be the currently-active (unfrozen) working bank, so the assertion can be tripped by an ordinary, unprivileged client — turning a client-controlled parameter into a validator-process panic, analogous to the Moonwell report's pattern of an invariant `assert()` that is reachable through normal, non-privileged call paths and bricks/crashes the system.

### Finding Description
`simulate_transaction` in the RPC handler resolves the bank to simulate against with: [1](#0-0) 
which calls `get_bank_with_config`, which in turn calls `self.bank(commitment)`: [2](#0-1) 

`bank()` resolves the slot for `Processed` commitment using `slot_with_commitment`, then fetches that slot's bank directly from `bank_forks`: [3](#0-2) 

`slot_with_commitment(CommitmentLevel::Processed)` simply returns `self.slot()`, i.e., `commitment_slots.slot`, which tracks the current (possibly still-building, unfrozen) bank slot rather than a slot guaranteed to be frozen: [4](#0-3) 

The simulation call then reaches: [5](#0-4) 
which hard-`assert!`s that the bank is frozen. Unlike `sendTransaction`'s preflight path (which is only safe because bank 0 is explicitly frozen up front in tests, per the comment "Freeze bank 0 to prevent a panic in `run_transaction_simulation()`" — see the test at lines 6948-6949), nothing in the production `simulateTransaction` code path guarantees the bank returned for `Processed` commitment is frozen before `Bank::simulate_transaction` is invoked. The existing regression test in the repo, `test_rpc_simulate_transaction_panic_on_unfrozen_bank`, explicitly documents and reproduces this exact panic: [6](#0-5) 

This test only avoids the panic in other simulate tests by manually calling `bank.freeze()` before simulating — a step production RPC serving does not perform for `processed` commitment when the working bank is still open for transaction processing.

### Impact Explanation
This is reachable by any unprivileged JSON-RPC client via a single `simulateTransaction` request with `{"commitment": "processed"}` against the currently-active (unfrozen) working bank. Triggering the `assert!` causes an immediate Rust panic. Because the RPC dispatch machinery does not appear to catch panics from within request handlers, this manifests as a validator process crash from one externally-triggerable JSON-RPC call — matching the "concrete validator-process crash ... from one request" impact category.

### Likelihood Explanation
Likelihood depends on timing: the working bank must still be unfrozen (i.e., mid-slot, before `Bank::freeze()` is called at the end of block production) at the moment the RPC request resolves the bank for `processed` commitment. Since validators are continuously building new banks, there is a recurring window during each slot where the working bank is unfrozen, making this a reliably repeatable race rather than a rare edge case; a client can simply retry `simulateTransaction` with `processed` commitment to hit the unfrozen window.

### Recommendation
- In `Bank::simulate_transaction` / the RPC `simulate_transaction` handler, do not `assert!` on an externally-influenced condition; instead return a proper `Result`/RPC error (e.g., reject or fall back to `simulate_transaction_unchecked`, or force a check whether the bank is frozen and return `RpcCustomError`/`Error::invalid_request` instead of panicking) when the bank is not frozen.
- Alternatively, ensure `get_bank_with_config`/`bank()` never returns an unfrozen bank for RPC read-only operations that require a frozen bank (e.g., explicitly reject/redirect `processed` commitment for `simulateTransaction`, or use a bank guaranteed frozen such as the optimistically-confirmed/latest-frozen bank).

### Proof of Concept
The repository already contains a test that reproduces the panic condition directly, confirming the code path and exact assertion message: [6](#0-5) 
In production, an equivalent externally-triggerable request is:
```json
{"jsonrpc":"2.0","id":1,"method":"simulateTransaction","params":["<any validly-formed b58 tx>", {"commitment": "processed"}]}
```
sent while the current working bank has not yet been frozen (i.e., mid-slot), which resolves through `bank()` → unfrozen bank → `Bank::simulate_transaction` → `assert!(self.is_frozen(), ...)` panic, crashing the validator process from a single unauthenticated RPC call.

        let RpcContextConfig {
            commitment,
            min_context_slot,
        } = config;
        let bank = self.bank(commitment);
        if let Some(min_context_slot) = min_context_slot

        {
            return Err(RpcCustomError::MinContextSlotNotReached {
                context_slot: bank.slot(),
            }
            .into());
        }

    fn bank(&self, commitment: Option<CommitmentConfig>) -> Arc<Bank> {
        debug!("RPC commitment_config: {commitment:?}");

        let commitment = commitment.unwrap_or_default();
        if commitment.is_confirmed() {
            let bank = self
                .optimistically_confirmed_bank
                .read()
                .unwrap()
                .bank
                .clone();
            debug!("RPC using optimistically confirmed slot: {:?}", bank.slot());
            return bank;
        }

        let slot = self
            .block_commitment_cache
            .read()
            .unwrap()
            .slot_with_commitment(commitment.commitment);

        match commitment.commitment {
            CommitmentLevel::Processed => {
                debug!("RPC using the heaviest slot: {slot:?}");
            }
            CommitmentLevel::Finalized => {
                debug!("RPC using block: {slot:?}");
            }
            CommitmentLevel::Confirmed => unreachable!(), // SingleGossip variant is deprecated
        };

        let r_bank_forks = self.bank_forks.read().unwrap();
        r_bank_forks.get(slot).unwrap_or_else(|| {
            // We log a warning instead of returning an error, because all known error cases
            // are due to known bugs that should be fixed instead.
            //
            // The slot may not be found as a result of a known bug in snapshot creation, where
            // the bank at the given slot was not included in the snapshot.
            // Also, it may occur after an old bank has been purged from BankForks and a new
            // BlockCommitmentCache has not yet arrived. To make this case impossible,
            // BlockCommitmentCache should hold an `Arc<Bank>` everywhere it currently holds
            // a slot.
            //
            // For more information, see https://github.com/solana-labs/solana/issues/11078
            warn!(
                "Bank with {:?} not found at slot: {:?}",
                commitment.commitment, slot
            );
            r_bank_forks.root_bank()
        })
