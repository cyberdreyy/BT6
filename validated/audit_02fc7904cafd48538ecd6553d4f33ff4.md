## Title
Multisig executes requests using confirmations from members who have since been removed, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges a removed member's *own* pending requests and that member's `num_requests_pk` entry; it never scans the `confirmations` map to strip that member's confirmation from requests that were *submitted by other members*. `confirm()` later authorizes execution purely by comparing `confirmations.len()` to `num_confirmations`, with no check that every confirming party is still a current member. A stale confirmation from a deleted member therefore still counts toward the K-of-N threshold, letting a request execute with fewer than K *live* signers.

### Finding Description
`confirm` executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations`, without validating that the stored confirmations belong to accounts/keys still present in `self.members`: [1](#0-0) 

`delete_member` only cleans confirmations for requests whose *original submitter* (`r.member`) equals the removed member — it does not touch the `confirmations` HashSet of requests submitted by *other* members that the removed member may have already confirmed: [2](#0-1) 

Concretely, with members `{A, B, C, D}` and `num_confirmations = 3`:
1. `B` calls `add_request` for a `Transfer` (or `AddKey`/`DeployContract`) request `R`. `A` calls `confirm(R)`; `confirmations[R] = {A}` (1 < 3, not yet executed).
2. Members separately pass a `DeleteMember { member: A }` request, removing `A` from `self.members`. `delete_member` iterates `self.requests` filtering `r.member == A` — since `R` was submitted by `B`, it is skipped, and `confirmations[R]` still contains `A`'s entry.
3. Now only `{B, C, D}` are live members, and `num_confirmations` is still 3 (allowed by the `members.len()-1 >= num_confirmations` check at member count 4→3).
4. `C` confirms `R`: `len()=1(+1)=2 < 3` → stored as `{A, C}`.
5. `D` confirms `R`: `len()=2(+1)=3 >= 3` → `execute_request` runs.

`R` executes with only two live members (`C`, `D`) actually approving it, plus a ghost confirmation from `A`, who is no longer a member. This breaks the intended equality `confirmations_counted == confirmations_from_live_members`; the binding "confirmations counted versus live members" is violated, and a K-of-N request executes with only K-1 live approvals.

The original `multisig/src/lib.rs` (v1) has the analogous flaw: `DeleteKey`'s cleanup filters `self.requests` by `r.signer_pk == pk` only, leaving stale confirmations by the removed key on other members' requests untouched: [3](#0-2) 

### Impact Explanation
This lets a request — including `Transfer` of NEAR funds, `AddKey`/`AddFullAccessKey`, `DeployContract`, or `FunctionCall` — execute despite lacking the number of confirmations from members currently entitled to approve it. This is a multisig request executed below the intended threshold, directly matching the Critical impact category ("a multisig request executed below threshold"), and can result in unauthorized transfer of NEAR held by the multisig account.

### Likelihood Explanation
Exploitability requires only ordinary multisig operation flow (no privileged access beyond being a normal member at some point): a member confirms a pending request, is later removed via a legitimate `DeleteMember`/`DeleteKey` request (a routine membership-rotation event), and the stale confirmation is silently retained. Any subsequent confirmations from current members can then combine with the stale one to cross the threshold. No attacker-controlled deployment or foundation privilege is needed — it is a natural consequence of the standard member-removal + confirm workflow.

### Recommendation
When removing a member (`delete_member` / `DeleteKey` handling), iterate all entries in `confirmations` (not just requests submitted by the removed member) and remove the removed member's identifier from every confirmation set. Alternatively, when counting confirmations in `confirm()`, filter the stored `confirmations` set down to identifiers still present in `self.members` before comparing against `num_confirmations`, so removed members can never contribute to reaching the threshold.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. As `B`, call `add_request` with a `Transfer` request `R` to some receiver.
3. As `A`, call `confirm(R)` → `confirmations[R] = {A}`.
4. Separately pass a `DeleteMember { member: A }` request (3 confirmations from other members) so `A` is removed; members become `{B, C, D}`.
5. As `C`, call `confirm(R)` → `confirmations[R] = {A, C}` (len 2, still below 3).
6. As `D`, call `confirm(R)` → `len()+1 = 3 >= num_confirmations(3)` → `execute_request` runs and transfers funds, even though only `C` and `D` (2 of 3 live members) actually approved it.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
