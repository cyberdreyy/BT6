### Title
EI credentials are silently granted `isUser==true` via a synthetic session User, allowing external-initiator holders to trigger arbitrary jobs by integer ID - (File: core/web/pipeline_runs_controller.go)

### Summary
`PipelineRunsController.Create` gates the integer-ID `RunJobV2` path on `isUser` returned by `auth.GetAuthenticatedUser`, intending (per its own comment) that "EIs not allowed" to run jobs via int ID. However, `AuthenticateExternalInitiator` explicitly injects a synthetic `*clsessions.User{Role: clsessions.UserRoleRun}` into the same `SessionUserKey` that real session/token authentication uses, so `GetAuthenticatedUser` cannot distinguish an EI-authenticated request from a genuine user, making `isUser` true for EI callers.

### Finding Description
In `core/web/pipeline_runs_controller.go`, `Create` does: [1](#0-0) 
`isUser` comes from `auth.GetAuthenticatedUser`, which merely checks presence of `SessionUserKey` in the gin context and type-asserts it to `*clsessions.User`: [2](#0-1) 

The root cause is in `AuthenticateExternalInitiator`, which — after validating EI access-key/secret — deliberately sets `SessionUserKey` to a fabricated user object, with an explicit comment acknowledging the design intent to grant EIs the "run" role: [3](#0-2) 

Because `GetAuthenticatedUser` reads exactly this key and cannot differentiate "real user session/token" from "EI-fabricated user," the `isUser` flag in `Create` is `true` for any successfully authenticated External Initiator, contradicting the comment "only users are allowed to run jobs using int IDs - EIs not allowed" at line 110. Consequently, an EI credential holder hitting `POST /v2/jobs/<int-ID>/runs` with valid EI access-key/secret headers passes the `uuid.Parse` check (since the ID is an int, not a UUID) and then satisfies `isUser`, reaching `prc.App.RunJobV2(ctx, jobID, nil)` for **any** integer job ID — not limited to a job associated with that specific external initiator. There is no ownership/ACL check correlating the authenticated EI record with the target job ID before invoking `RunJobV2`.

### Impact Explanation
This is an authorization-bypass / unauthorized-job-run issue: an entity holding only EI credentials (a lower-trust integration credential meant to trigger webhook-bound job runs) can invoke arbitrary job runs on the node by integer job ID, including jobs it has no legitimate relationship to. Depending on job type (e.g., jobs that move funds, write on-chain transactions, or trigger keeper/OCR actions), this could result in unauthorized triggering of node actions outside the EI's intended scope — matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Precondition is only possession of a valid External Initiator access key/secret pair (a credential explicitly designed to be lower-privilege than a full user session/API token). No admin or user session is required. The request is a single `POST /v2/jobs/<ID>/runs` with EI headers and a known/guessed integer job ID, which is trivially repeatable and requires no race condition or timing dependency.

### Recommendation
Distinguish EI-authenticated identity from genuine user identity instead of overloading `SessionUserKey`. Use a separate check (e.g., `auth.GetAuthenticatedExternalInitiator`) to explicitly reject or specially-scope EI-originated requests in `PipelineRunsController.Create`, and/or verify that the target job is actually bound to the authenticated external initiator before calling `RunJobV2`. At minimum, `isUser` should only be true when the request was authenticated via `AuthenticateBySession` or `AuthenticateByToken`, not via `AuthenticateExternalInitiator`.

### Proof of Concept
Go handler-level test plan:
1. Construct a `gin.Context` with a valid EI record and call `auth.AuthenticateExternalInitiator(c, store)` only (no `AuthenticateBySession`/`AuthenticateByToken` call).
2. Assert `auth.GetAuthenticatedUser(c)` returns `(*clsessions.User{Role: UserRoleRun}, true)`.
3. Set `c.Params` `ID` to a valid integer job ID belonging to an unrelated job/user, call `PipelineRunsController.Create(c)` with a mocked `chainlink.Application` whose `RunJobV2` is asserted to be invoked with that job ID.
4. Assert the response is `200 OK` with a pipeline run resource, demonstrating the "EIs not allowed" comment is violated and RunJobV2 executes for an EI-only-authenticated caller.
