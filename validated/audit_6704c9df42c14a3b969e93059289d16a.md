### Title
Goroutine leak in `triggerPodPhaseCheck` when `ctx.Done()` wins over pod-phase channel send - ([File: executors/kubernetes/util.go])

### Summary
`triggerPodPhaseCheck` creates an unbuffered channel and spawns a goroutine that blocks on `errc <- getPodPhase(...)` [1](#0-0)  . In `waitForPodRunning`, the `select` between this channel and `ctx.Done()` can resolve via `ctx.Done()` while the spawned goroutine is still mid-flight; once it finishes and attempts to send on `errc`, there is no receiver left, so the goroutine blocks forever [2](#0-1)  .

### Finding Description
`getPodPhase` issues a `client.CoreV1().Pods(pod.Namespace).Get(ctx, ...)` call using the caller-supplied `ctx` [3](#0-2)  . When the job's context is cancelled (e.g., the job/pipeline author cancels the job), the in-flight `Get` call typically returns promptly with a `context canceled` error, and `getPodPhase` returns its `podPhaseResponse`. Meanwhile, in `waitForPodRunning`'s `select`, the `ctx.Done()` case can win the race and the function returns immediately with `api.PodUnknown, ctx.Err()` [4](#0-3)  before the goroutine has delivered its result. The goroutine then executes `errc <- getPodPhase(...)` on the unbuffered `errc` channel with no remaining receiver (the loop/function that owned the receiving `select` has already returned), so the send blocks permanently. Because the channel is never read again and `close(errc)` is deferred after the blocked send, the goroutine — and its stack — is never reclaimed. This is purely a channel-synchronization bug (unbuffered channel + no-receiver-after-cancellation), not mitigated by any existing check, since there is no buffering, no `select` with `ctx.Done()` inside the goroutine's send, and no cleanup path.

### Impact Explanation
Every job cancellation that happens to race with an in-flight `getPodPhase` call leaks exactly one goroutine permanently blocked on a channel send. Since `waitForPodRunning` is invoked per job during pod-startup polling, and cancellation is a normal, attacker-triggerable action (any user can cancel their own job), a user or script that repeatedly starts and cancels jobs at the right moment can accumulate leaked goroutines over time in the shared runner manager process. This degrades the runner process (goroutine/stack memory growth) shared across all tenants/projects using that runner, which is a scoped, concrete availability impact as described.

### Likelihood Explanation
The race window depends on timing — the cancellation must occur after the `Get` API call has started but the result must reach the `select` after `ctx.Done()` has already been observed as ready. This is inherently probabilistic but fully attacker-controllable in aggregate: an attacker can programmatically create and cancel many jobs in rapid succession (e.g., via the GitLab API) to repeatedly probe this race, each attempt at some non-trivial chance of leaking a goroutine. Over many repetitions this becomes a reliable, cumulative leak.

### Recommendation
Make the channel buffered with capacity 1 (`make(chan podPhaseResponse, 1)`), or have the goroutine perform a non-blocking send guarded by a `select` on `ctx.Done()` around the channel write, e.g.:
```go
func triggerPodPhaseCheck(ctx context.Context, ...) <-chan podPhaseResponse {
    errc := make(chan podPhaseResponse, 1)
    go func() {
        defer close(errc)
        errc <- getPodPhase(ctx, c, pod, out, printPodWarningEvents, containers...)
    }()
    return errc
}
```
A buffered channel of size 1 guarantees the goroutine's single send always succeeds without a receiver, allowing the goroutine to exit and be garbage-collected immediately regardless of which `select` branch in the caller wins. The same fix should be applied to `triggerPodReachableCheck`, which has the identical pattern.

### Proof of Concept
Go unit test sketch:
```go
func TestTriggerPodPhaseCheck_NoGoroutineLeakOnCancel(t *testing.T) {
    before := runtime.NumGoroutine()
    for i := 0; i < 1000; i++ {
        ctx, cancel := context.WithCancel(context.Background())
        fakeClient := &fakeKubeInterface{
            getFunc: func(ctx context.Context) (*api.Pod, error) {
                <-ctx.Done() // simulate in-flight call unblocked exactly at cancellation
                return nil, ctx.Err()
            },
        }
        pod := &api.Pod{}
        ch := triggerPodPhaseCheck(ctx, fakeClient, pod, io.Discard, false)
        cancel()
        select {
        case <-ch:
        case <-ctx.Done():
            // simulate waitForPodRunning returning via ctx.Done() without draining ch
        }
    }
    time.Sleep(200 * time.Millisecond)
    runtime.GC()
    after := runtime.NumGoroutine()
    assert.LessOrEqual(t, after, before+5, "goroutines leaked from triggerPodPhaseCheck")
}
```
Expected (buggy) result: `after` grows roughly linearly with iteration count because leaked goroutines accumulate; after the fix (buffered channel), goroutine count stays flat.
