# Wrong-Recipient Redirection of Staker's Own Principal When `staker == operator` in a Self-Staking `staking_contract` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::create_staking_contract_with_coins` never asserts that `staker != operator`, so any unprivileged account can create a self-managed staking contract in which it is *both* the staker and its own operator. In that configuration, `distribute_internal`'s recipient-remapping logic — which is designed to redirect an *operator's* commission to that operator's configured beneficiary — cannot distinguish the operator's commission shares from the staker's own principal shares inside the shared `distribution_pool`, because both are keyed by the *same* address. If that address (acting as operator, e.g. for a completely unrelated staking contract with a different staker) ever calls `set_beneficiary_for_operator`, every future `unlock_stake`/`distribute` on the self-staked contract silently redirects the staker's *entire* withdrawal (including principal, not just commission) to the beneficiary address instead of back to the staker.

### Finding Description
`create_staking_contract_with_coins` at [1](#0-0)  only validates the commission percentage and minimum stake, never that `operator != signer::address_of(staker)`. Anyone can thus call `create_staking_contract(staker, operator = staker_address, ...)`.

Each `StakingContract` has a single shared `distribution_pool: Pool` used for *both* operator commission payouts and staker withdrawal payouts, as declared at [2](#0-1) .

- `request_commission_internal` records the operator's commission via `add_distribution(operator, staking_contract, operator, commission_amount)` at [3](#0-2) .
- `unlock_stake` subsequently records the staker's own withdrawal via `add_distribution(operator, staking_contract, staker_address, amount)` at [4](#0-3) .

`add_distribution` buys shares into the pool keyed by the `recipient` address using `pool_u64::buy_in`, which merges shares for an existing shareholder address rather than tracking them separately per role, as seen in `add_shares` at [5](#0-4) . When `staker_address == operator`, the commission buy-in and the principal buy-in collapse into one shareholder entry.

`distribute_internal`'s payout loop then redirects any recipient equal to `operator` to `beneficiary_for_operator(operator)`: [6](#0-5) 

Since the merged shareholder entry's address is indistinguishable from the operator, the *entire* combined balance (staker principal + operator commission) is sent to the beneficiary, not just the intended commission portion.

`set_beneficiary_for_operator` is a single global mapping keyed only by operator address — it is not scoped per staking-contract pool — as documented and implemented at [7](#0-6) . This means one call by an address acting as operator for some unrelated staker automatically also applies to that same address's own self-staked contract, if one exists.

### Impact Explanation
This breaks the "Owner, operator, voter, and beneficiary boundaries must hold" and "wrong-role control … credits the wrong account" invariants. A user who self-stakes (`staker == operator`) and who, in any other capacity, ever designates a beneficiary for their operator role, will have their own stake principal (not just commission) permanently redirected away from themselves to the beneficiary address on every subsequent `unlock_stake`/`distribute`/`switch_operator` call. This is a real loss of funds/claim rights for the self-staking account, not merely a commission miscalculation, and is fully reachable without any special privileges — an ordinary account can set this trap for itself (or be steered into it) simply by using the standard `create_staking_contract` + `set_beneficiary_for_operator` APIs.

### Likelihood Explanation
Nothing in `create_staking_contract`/`create_staking_contract_with_coins` prevents `staker == operator`, and `set_beneficiary_for_operator` is a normal, frequently-used entry function gated only by a feature flag (`operator_beneficiary_change_enabled`) at [8](#0-7) . Any account that operates for itself and also operates (or later starts operating) for anyone else and rotates its beneficiary will trigger this unintentionally — no attacker collusion, signature forgery, or governance privilege is required.

### Recommendation
- Short term: In `distribute_internal`, distinguish the operator's commission distribution from the staker's principal distribution independently of address equality (e.g., track commission amounts and staker amounts in separate pools/keys, or tag distribution entries with their role rather than inferring role solely from `recipient == operator`).
- Alternatively/also: assert `operator != signer::address_of(staker)` in `create_staking_contract_with_coins` to eliminate the self-staking-as-own-operator configuration, or scope `BeneficiaryForOperator` per `pool_address` rather than globally per operator address.
- Long term: audit all places where the same address can simultaneously hold two distinct roles (staker/operator, delegator/operator, admin/beneficiary) across the `staking_contract`, `delegation_pool`, and `vesting` modules, and ensure role-based redirection logic never conflates the roles when they collide on one address.

### Proof of Concept
1. Alice calls `staking_contract::create_staking_contract(alice, operator = alice_address, voter, amount, commission_percentage = 10, seed)` — allowed because there's no `staker != operator` assertion.
2. Time passes; rewards accrue on the pool.
3. Alice, in an unrelated capacity, is also `operator` for Bob's staking contract. She calls `staking_contract::set_beneficiary_for_operator(alice, beneficiary_address)` intending to redirect only her *commission income from Bob's contract*.
4. Alice calls `staking_contract::unlock_stake(alice, operator = alice_address, amount)` on her *own* self-staked contract.
   - `request_commission_internal` buys in `commission_amount` shares for `recipient = operator = alice_address`.
   - `unlock_stake` then buys in `amount` shares for `recipient = staker_address = alice_address` — merging into the same shareholder entry as the commission.
5. When `distribute_internal` runs (triggered by `unlock_stake`, `distribute`, or `switch_operator`), it sees the single shareholder `alice_address == operator`, and redirects the *entire* merged balance (Alice's own principal + her commission) to `beneficiary_address`, not to Alice.
6. Alice's own stake withdrawal is now permanently routed to `beneficiary_address` on every future distribution from this contract, until she notices and reconfigures.

    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
