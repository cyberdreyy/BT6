### Title
Post-default withdraw requests pay 1:1 out of the default recovery reserve that was funded only for defaulted-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
After `finalizeDefaultRecovery`, any wallet can call `requestWithdraw` and later `claimWithdrawRequest`. The post-default path mints the user a receipt and records `postDefaultRequests[_user] = _amount` without moving a single underlying into the strategy, yet `_claimPostDefaultWithdrawRequest` pays the full amount 1:1 from `defaultRecoveryReserve` via `_transferDefaultRecovery`. This is the chunk_free_object analog: a "chunk" (reserve token) is released to a caller whose claim was never allocated from that pool — the reserve was sized only for defaulted-epoch receipts and prefunded instant claims.

### Finding Description
The bug chain:

1. `finalizeDefaultRecovery` computes `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis` only covers active CDO basis and `defaultPendingClaimBasis()` (pending + defaulted-epoch instant receipts). The reserve exactly matches the obligations of defaulted-epoch claimants at `defaultRecoveryPrice` — there is no headroom for future requests. [1](#0-0) 

2. `requestWithdraw`, once `defaultRecoveryFinalized`, takes the post-default branch: it burns `_amount` strategy tokens from the CDO and mints them to the user, sets `postDefaultRequests[_user] = _amount`, and returns — no `underlyingToken` is transferred into the strategy and `defaultRecoveryReserve` is not increased. [2](#0-1) 

3. `claimWithdrawRequest` then routes to `_claimPostDefaultWithdrawRequest`, which burns the receipt and calls `_transferDefaultRecovery(_user, amount)`, decrementing `defaultRecoveryReserve -= _amount` and transferring reserve tokens the post-default claim was never backed by. [3](#0-2) [4](#0-3) 

The comment at line 253 ("the CDO passes an already-haircut amount because finalization lowered virtualPrice") explains the *size* of the claim but not its *funding*: the lowered `virtualPrice` means the user gives up more tranche tokens per receipt unit, but the corresponding underlying value stays in the CDO/active pool — it is never moved into `defaultRecoveryReserve`. No guard (`_ensureDefaultRecoveryInitialized`, `NotAllowed` checks, `_transferFundedClaim`'s reserve check) covers this path.

### Impact Explanation
Each post-default request/claim drains `defaultRecoveryReserve` by `_amount` at zero cost in reserve terms. Two concrete losses for the unprivileged attacker (any KYC-passed lender / tranche holder):

- **Direct theft**: the attacker receives underlying 1:1 while defaulted-epoch claimants are only entitled to `defaultRecoveryPrice < RECOVERY_FULL`. Claiming early, the attacker converts a haircut-priced receipt into full-price reserve tokens.
- **Permanent freezing / insolvency of honest claimants**: once the attacker drains the reserve below the sum of remaining defaulted-epoch claims, `_transferDefaultRecovery` underflows (`defaultRecoveryReserve -= _amount` reverts) and every remaining defaulted-epoch claimant's `claimWithdrawRequest`/`claimInstantWithdrawRequest` permanently reverts — their recovery is frozen forever.

Loss is quantified: up to `min(attacker tranche value at post-default virtualPrice, defaultRecoveryReserve)` stolen, and up to the full remaining reserve frozen for honest claimants.

### Likelihood Explanation
- Attacker requirement is minimal: any KYC-passing tranche holder (the `isWalletAllowed` gate only applies at deposit) who still holds tranche tokens after a default is finalized. Large holders survive default with tranche tokens by design.
- No timing race needed: `requestWithdraw` → `claimWithdrawRequest` are two permissionless calls any time after finalization; nothing rate-limits or caps `postDefaultRequests`.
- Repeatable: the post-default branch has no per-user cap beyond the "claim old requests first" check, so after each claim the attacker can request again, draining the reserve iteratively.
- Preconditions (borrower default + finalized recovery) are normal protocol operations, not attacker-controlled edge cases.

### Recommendation
Post-default claims must not spend `defaultRecoveryReserve`. Either:
- Route `_claimPostDefaultWithdrawRequest` through `_transferFundedClaim` and require the CDO to actually transfer the underlying backing the request into the strategy at `requestWithdraw` time (pull `underlyingToken` from the CDO along with the burn/mint), or
- Track a separate `postDefaultReserve` credited at request time and debit it in the claim, keeping `defaultRecoveryReserve` exclusively for defaulted-epoch claimants.

Also add an invariant check in `finalizeDefaultRecovery`/tests asserting `underlyingToken.balanceOf(strategy) >= defaultRecoveryReserve + fundedClaims` after every post-default request.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
function testPostDefaultClaimDrainsRecoveryReserve() external {
    // 1. user1 (honest) and attacker (KYC'd) deposit; startEpoch
    uint256 honestTranche  = _depositWithUser(honest, 100e6);
    uint256 attackerTranche = _depositWithUser(attacker, 100e6);
    vm.prank(manager); cdoEpoch.startEpoch();

    // 2. honest user requests withdraw pre-default; epoch runs
    _requestWithdrawWithUser(honest, honestTranche);

    // 3. borrower defaults; CDO calls finalizeDefaultRecovery with partial recovery
    //    (e.g. 50% recovered) -> defaultRecoveryPrice = 0.5e18, reserve = recovered + prefunded
    _defaultAndFinalizeRecovery(0.5e18 /* recoveryPrice */);

    // 4. Attacker requests a post-default withdraw (allowed: burns tranche-derived amount)
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attackerTranche, address(AAtranche));
    uint256 postReq = strategy.postDefaultRequests(attacker);
    assertGt(postReq, 0);

    // 5. Attacker claims: paid 1:1 from defaultRecoveryReserve
    uint256 reservePre = strategy.defaultRecoveryReserve();
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    assertEq(strategy.defaultRecoveryReserve(), reservePre - postReq); // reserve drained

    // 6. Honest defaulted-epoch claimant now reverts or receives less than
    //    claimBasis * defaultRecoveryPrice / 1e18
    vm.prank(honest);
    vm.expectRevert(); // underflow in _transferDefaultRecovery once reserve < owed
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertions: `postDefaultRequests[attacker]` is paid via `_transferDefaultRecovery` although no underlying was added to the reserve at request time (step 4 performs no `underlyingToken.safeTransferFrom` into the strategy — see `requestWithdraw` lines 247–257), and the honest claimant's payout reverts or is shorted by exactly the attacker's `postReq`.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
  }

  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
  }
