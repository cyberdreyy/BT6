## Analysis

The ZetaChain bug is a class of vulnerability where a piece of state that must persist across a restart (to preserve an invariant/guard) is instead reset to a default/empty value, silently defeating the guard. The strongest analog in this repo is the **signer's cross-tenure equivocation guard**, which lives entirely in the local, non-replicated `blocks` table of `SignerDb` and has no recovery path from either the stacks-node or StackerDB if that table is lost.

### Title
Loss of the cross-tenure equivocation guard when a signer's local `blocks` table is reset, enabling the signer to double-sign conflicting blocks - (File: stacks-signer/src/signerdb.rs, stacks-signer/src/v0/signer.rs)

### Summary
The signer prevents itself from putting a second signature over a block that conflicts with one it already signed by querying `SignerDb::get_signed_conflicts`, which scans the local SQLite `blocks` table for any block it (or the observed signer group) has signed at or above the proposed height, in **any** tenure [1](#0-0) . This record is purely local: unlike the miner-view `StateMachineUpdate`, which is replicated over StackerDB and reloaded into a fresh `SignerDb` on startup [2](#0-1) [3](#0-2) , there is no equivalent replication or reconstruction of `signed_self`/`signed_group` block records from any external source. If a signer's `blocks` table is reset (crash + fresh volume, disk corruption + recovery, redeploying with the wrong/blank `db_path`, or any other cause of restarting with an empty signer DB), the signer forgets every block it previously signed, and `get_signed_conflicts` will return an empty set even though a conflicting, previously-signed sibling still exists.

### Finding Description
The equivocation guard is deliberately layered on top of (not a substitute for) the "chainstate" checks in `check_block_against_signer_db_state`, precisely because those checks only look at **one** tenure at a time (a tenure-change block's parent tenure, or a block's own tenure), and can therefore never see a signed sibling in a third tenure [4](#0-3) . The pre-commit → signature path in `handle_block_pre_commit` explicitly relies on `get_signed_conflicts` to catch this blind spot before producing a signature [5](#0-4) .

Crucially, this data is not reconstructible after loss: `check_latest_block_in_tenure` (the chainstate check) does fall back to asking the stacks-node when the signer DB is out of sync [6](#0-5) , but that fallback only covers *one* tenure and only surfaces blocks the node has actually processed (globally accepted); it cannot recover a locally-accepted-only signature over a sibling block in a different, never-adopted tenure. There is no code path anywhere in `Signer::new` or `SignerDb::create_or_migrate` that repopulates the `blocks` table (or its `signed_self`/`signed_group`/`consensus_hash`/`stacks_height` fields) from StackerDB `BlockResponse` messages the way `StateMachineUpdate` chunks are replayed at startup [7](#0-6) .

Sequence:
1. Signer signs block `A` at height `H` in tenure `T1` (`signed_self` recorded in `blocks`).
2. The signer's local `SignerDb` is wiped or replaced with a fresh, empty database (e.g., operational restart against an empty `db_path`) while the signer keeps its private key and reward-cycle assignment.
3. A different miner (or the same miner, in a later tenure `T2`) proposes conflicting sibling block `B` at the same height `H`.
4. `get_signed_conflicts` on the now-empty `blocks` table returns nothing, so `handle_block_pre_commit`'s conflict check silently passes [5](#0-4) .
5. If `B` also passes the (single-tenure) chainstate check — trivially true if it targets a different, unrelated tenure — the signer signs `B`, producing two valid signatures from the same signer over two conflicting blocks at the same height.

### Impact Explanation
This breaks the safety invariant the pre-commit/conflict-guard design is built to guarantee: that an honest signer never contributes its weight/signature to two mutually conflicting blocks at the same height. A signer's vote is assumed to be single-use per height across all tenures; if it can be reused after a DB reset, its weight can count toward the 70% threshold for two different forks, undermining the assumption that no two conflicting blocks can both reach quorum. This falls under the explicitly listed Critical impact ("a signer signing an invalid, non-canonical, or conflicting block") and the High impact ("losing the equivocation guard on restart").

### Likelihood Explanation
No majority collusion or externally malicious signer is required — only a normal operational event (a signer's local DB being reset/lost) combined with an ordinary conflicting proposal that any single miner slot (plus gossip carrying the pre-commits/signatures) can naturally produce during a benign fork or reorg. The scenario is squarely inside the documented threat model: the codebase already acknowledges "the signer DB can be out-of-sync with the node" as a real operational condition [8](#0-7) , but only builds a node-fallback for the single-tenure chainstate check, not for the cross-tenure `get_signed_conflicts` guard.

### Recommendation
Persist the equivocation-relevant facts (which blocks/heights this signer, or the observed group, has signed) somewhere recoverable independent of the local `blocks` table — e.g., replicate a compact "signed heights" record over StackerDB (similar to `StateMachineUpdate`) and replay it into a fresh `SignerDb` at startup, the same way `Signer::new` already replays `StateMachineUpdate` chunks. Alternatively, before a freshly-initialized (schema-version-0 / empty) `SignerDb` is allowed to participate in signing, require the signer to reconstruct its known-signed-heights window from peers' recent `BlockResponse`/`BlockPreCommit` StackerDB chunks, mirroring the existing state-machine-update recovery path.

### Proof of Concept
1. Start a signer normally; have it sign block `A` (tenure `T1`, height `H`) so that `blocks.signed_self` is populated, confirmed via `SignerDb::get_signed_conflicts` returning the entry as in the existing test `test_write_signer_state`-style setup [9](#0-8) .
2. Stop the signer and delete/replace its sqlite `db_path` file so a brand-new `SignerDb` is created on next start (schema recreated from scratch, `blocks` table empty).
3. Restart the signer with the same identity/keys and reward cycle.
4. Propose conflicting sibling block `B` at height `H` in a different tenure `T2` and drive it through pre-commit to threshold.
5. Observe `get_signed_conflicts(H, hash_B)` returns `[]` (nothing survived the wipe), so `handle_block_pre_commit` proceeds to `mark_locally_accepted`/sign `B`, producing a second signature over a block conflicting with `A` at the same height — reproducing the pattern demonstrated by the `run_cross_tenure_scenario`/`fresh_conflict_in_another_tenure_blocks_signing` test [10](#0-9) , but with the guard disabled by the DB reset instead of by staleness.
