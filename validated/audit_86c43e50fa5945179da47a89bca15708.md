### Title
Unbounded recursive RLP decoding of Merkle-Patricia trie nodes causes stack-overflow DoS of the fault-proof program - ([File: crates/proof/mpt/src/node.rs])

### Summary
CVE-2016-4353 describes a Libksba BER decoder that recursed without a depth limit, letting attacker-crafted BER data blow the stack and abort the process. `base-proof-mpt`'s `TrieNode::decode` implements the analogous pattern for RLP-encoded Merkle-Patricia trie nodes: it recurses into itself for `Extension` nodes and into `Vec::<TrieNode>::decode` for `Branch` nodes, with no maximum nesting-depth check anywhere in the decode path.

### Finding Description
`TrieNode::decode` in [1](#0-0)  inspects the RLP header/list length and, for a 2-element list, calls `Self::try_decode_leaf_or_extension_payload`, which for an extension-type prefix recursively calls `Self::decode(buf)` again on the child element [2](#0-1) . For a 17-element list it calls `Vec::<Self>::decode(buf)`, which decodes each of the 16 branch slots by recursively invoking `TrieNode::decode` again.

Crucially, decoding does not require that non-empty children be "blinded" (i.e., represented as a 32-byte hash commitment) — that invariant is only enforced when *encoding*/*hashing* a `TrieNode` via `blind()`/`blinded_length()` [3](#0-2) . On decode, an inline (non-32-byte, non-empty) child of an `Extension` or `Branch` node is simply decoded as another nested `TrieNode`, without any check that limits how many times this can nest. Each nesting level only costs a few bytes of RLP header overhead, so an attacker can construct a single trie-node preimage blob that nests thousands of `Extension`/`Branch` levels within a modest byte budget, driving `TrieNode::decode` into unbounded native-stack recursion and crashing the process (stack overflow / abort) — the same bug class as CVE-2016-4353.

This decode path is reached directly from oracle preimage data supplied by the (untrusted) preimage server during fault-proof execution:
- `OracleL1ChainProvider::trie_node_by_hash` — `TrieNode::decode(&mut self.oracle.get(PreimageKey::new(*key, PreimageKeyType::Keccak256)).await?...)` [4](#0-3) 
- `OracleL2ChainProvider::trie_node_by_hash` — identical pattern for L2 [5](#0-4) 
- Disk/test providers show the same unguarded call pattern [6](#0-5) 

There is no depth counter, iteration limit, or maximum-nesting guard anywhere in `crates/proof/mpt/src/node.rs` or its helper `crates/proof/mpt/src/util.rs` (`rlp_list_element_length` only walks a single list's sibling elements, not nested depth) [7](#0-6) .

### Impact Explanation
The fault-proof program (`base-proof-*` client used inside the dispute-game/fault-proof VM) relies on a preimage oracle that is populated by an untrusted party during a dispute game — the preimage server can be operated or influenced by a dispute-game participant who controls what bytes are served for a given hash-keyed preimage lookup (subject only to the hash matching, which an attacker can satisfy by controlling the pre-image that hashes to a value they themselves committed as a trie root/child, e.g. via a crafted state/storage/receipts/transactions trie they control). A stack-overflow abort of the client program during trie traversal halts fault-proof execution non-gracefully, which can prevent the honest party from producing a valid execution trace/output root for that step of the dispute, i.e. a denial-of-service on the fault-proof program that can stall or invalidate a dispute-game resolution — undermining Base's proof system availability, one of the explicitly in-scope severities ("node halt" / "wrong provable output root" class impact).

### Likelihood Explanation
No signed transaction, private key, or special privilege is required — the trigger is simply crafting a trie-node preimage with deeply nested inline `Extension`/`Branch` structures, something well within reach of anyone who can supply data resolving to a hash referenced during trie traversal (e.g., a malicious L1 depositor/state actor or dispute participant constructing an adversarial trie). The recursive call sites are unconditionally reached whenever `trie_node_by_hash` decodes a node, with no gating logic, size cap on nesting depth, or iterative rewrite of the recursive algorithm.

### Recommendation
Bound the recursion depth explicitly in `TrieNode::decode` (and any other recursive `TrieNode` traversal such as `open`/`insert`/`collapse_if_possible`), e.g., by threading a depth counter/limit parameter through decode and returning an `alloy_rlp::Error` once a maximum trie depth (bounded by the maximum possible MPT depth for 32-byte keys, e.g. 64–128) is exceeded, or by converting the recursive decode into an explicit iterative/worklist-based algorithm that does not consume native stack per nesting level.

### Proof of Concept
1. Construct RLP bytes for a `TrieNode::Extension` whose child element is itself another RLP-encoded 2-element list (`Extension`) rather than a 32-byte blinded hash or empty node — repeat this nesting N times (e.g., N = 50,000), which alloy_rlp encoding permits since decode does not require children to be blinded.
2. Serve this blob as the preimage for the keccak256 hash referenced by a `trie_node_by_hash(key)` lookup (e.g., by having it be the value returned from the untrusted preimage oracle for a state/storage/receipts/transactions trie root or child hash reached during derivation/execution in the fault-proof program).
3. Call `TrieNode::decode(&mut blob.as_slice())` as done in `OracleL1ChainProvider::trie_node_by_hash` / `OracleL2ChainProvider::trie_node_by_hash` [8](#0-7) . The N nested recursive calls into `Self::decode` overflow the program's native call stack, aborting the fault-proof client process.

impl Decodable for TrieNode {
    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.
                    buf.advance(header.length());
                    // Decode the leaf or extension node's raw payload.
                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }
        } else {
            match header.payload_length {
                0 => {
                    buf.advance(header.length());
                    Ok(Self::Empty)
                }
                32 => {
                    let commitment = B256::decode(buf)?;
                    Ok(Self::new_blinded(commitment))
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }
        }
    }

pub(crate) fn rlp_list_element_length(buf: &mut &[u8]) -> alloy_rlp::Result<usize> {
    let header = Header::decode(buf)?;
    if !header.list {
        return Err(alloy_rlp::Error::UnexpectedString);
    }
    let len_after_consume = buf.len() - header.payload_length;

    let mut list_element_length = 0;
    while buf.len() > len_after_consume {
        let header = Header::decode(buf)?;
        buf.advance(header.payload_length);
        list_element_length += 1;
    }
    Ok(list_element_length)
}
