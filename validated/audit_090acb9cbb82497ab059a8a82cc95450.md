### Title
Permissionless creation of duplicate staked-collateral banks for the same validator/LST fragments risk limits and liquidity - ([File: programs/marginfi/src/instructions/marginfi_group/add_pool_permissionless.rs])

### Summary
`lending_pool_add_bank_permissionless` lets *any* fee payer create a new `Bank` for a validator's staked-collateral LST, gated only by the group having opted in via `StakedSettings` [1](#0-0) . The bank PDA is derived from `[marginfi_group, bank_mint, bank_seed]` where `bank_seed` is a caller-supplied `u64` [2](#0-1) . Because `bank_seed` is arbitrary and unrestricted, the same validator/mint pair can have unlimited distinct `Bank` PDAs registered by unrelated, uncoordinated callers — directly analogous to the IN3 `NodeRegistry` issue where uniqueness was enforced only on an exact byte-match (URL hash) rather than the underlying logical resource, allowing multiple registrations that map to the same real-world endpoint.

### Finding Description
The uniqueness check for this instruction is implicit: Anchor's `init` constraint on the `bank` account only prevents re-using the exact same `(group, bank_mint, bank_seed)` triple [2](#0-1) . There is no check that a bank does not already exist for this `bank_mint` (i.e., for this validator's LST) under a different `bank_seed`. Any user can call the instruction repeatedly with new seed values (0, 1, 2, ...) to create many independent `Bank` accounts for the same underlying stake pool/validator, each with its own fresh, independent `deposit_limit`, `total_asset_value_init_limit`, and share-accounting state copied from the current `StakedSettings` defaults [3](#0-2) . Just as the NodeRegistry uniqueness-by-hash failed to prevent registering multiple entries that are logically the "same" endpoint, this seed-based PDA scheme fails to prevent multiple logically-duplicate banks for the same validator.

### Impact Explanation
Each new duplicate bank starts with its own `deposit_limit` and `total_asset_value_init_limit` pulled fresh from `StakedSettings` [3](#0-2) . These per-bank caps exist specifically as an oracle-attack/exposure mitigation (see `total_asset_value_init_limit` documentation) [4](#0-3) . Since the caps are enforced per-bank rather than per-underlying-asset [5](#0-4) , an attacker (or even benign but uncoordinated actors) spamming duplicate banks for one validator's LST effectively multiplies the group's total exposure/deposit capacity to that single validator far beyond what `StakedSettings` intends, undermining the risk mitigation those caps are meant to provide. It also fragments liquidity for what should be one logical collateral asset across many `Bank` accounts, degrading integration/health-check assumptions that treat one mint as backed by one bank, and permanently bloats on-chain state (each duplicate bank, plus its 3 vault token accounts, is a real, non-reclaimable account creation, unless later closed by an admin).

### Likelihood Explanation
The instruction is explicitly permissionless with no signer-authority check tying the caller to the validator or to any prior registration of that mint [6](#0-5) ; only the `fee_payer` (any wallet) pays for and signs the creation. Any group that opts into staked-collateral support via `StakedSettings` is exposed. The only cost to an attacker is rent for the bank and 3 vault accounts, which is low relative to the potential for inflating a group's effective risk exposure to one validator.

### Recommendation
Enforce uniqueness at the level of the underlying asset, not just the PDA seed: before creating a new staked bank, check whether a `Bank` with `asset_tag == ASSET_TAG_STAKED` and the same `mint` (or same `validator_vote_account`) already exists in the group, and reject if so (or require an admin/governance step to approve additional banks for an already-registered validator). Alternatively, remove free-form `bank_seed` from the permissionless path and derive it deterministically from the validator identity (e.g., a fixed seed of `0` per validator per group), so only one canonical bank can ever be created per validator/mint per group without an explicit admin action via `lending_pool_add_bank_with_seed`.

### Proof of Concept
1. Group admin calls `init_staked_settings` to opt the group into permissionless staked-collateral bank creation [7](#0-6) .
2. Any user calls `lending_pool_add_bank_permissionless` with `validator_vote_account = V`, `bank_seed = 0`, creating `Bank_0` for validator `V`'s LST mint, with default deposit/init limits from `StakedSettings` [8](#0-7) .
3. The same or a different user calls the same instruction again with the same `validator_vote_account = V` but `bank_seed = 1`. This derives a different PDA `[group, mint, 1]`, passing the `init` uniqueness check trivially, and creates `Bank_1` — a second, independent bank for the exact same validator/mint, each with its own full `deposit_limit`/`total_asset_value_init_limit` [2](#0-1) .
4. Repeat with `bank_seed = 2, 3, ...` to create arbitrarily many banks for the same validator, multiplying the group's total risk-limit exposure to that single validator beyond what the `StakedSettings` caps were designed to bound.
