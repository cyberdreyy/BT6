### Title
Caller-Controlled Cache Freshness (`CacheSettings.MaxAgeMs`) Allows Consumption of Arbitrarily Stale Cached HTTP Data - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The Gateway's HTTP Action response cache determines whether a cached response is "fresh enough" to return using a `MaxAgeMs` value taken directly from the requester's own `OutboundHTTPRequest.CacheSettings`, rather than any bound tied to the actual update cadence/volatility of the underlying external data source. This mirrors the reported bug class: staleness is judged against a value that is decoupled from the true freshness properties of the data, so a request can treat data as "fresh" long after it should be considered stale.

### Finding Description
`responseCache.Fetch` computes `cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond` from the caller-supplied field of the current request and uses it as the sole freshness check against `cachedResp.storedAt`: [1](#0-0) 

Critically, the cache key (`req.Hash()`) is documented and tested to be **independent of `CacheSettings`**: two requests that differ only in `MaxAgeMs`/`Store` map to the identical cache entry: [2](#0-1) 

The hash is also independent of `WorkflowID`, only scoped by `WorkflowOwner`, method, URL, headers and body: [3](#0-2) [4](#0-3) 

This is invoked from the unprivileged/DON-facing outbound HTTP action path, where `req.CacheSettings.MaxAgeMs` comes straight from an unmarshaled node/workflow message: [5](#0-4) 

Consequently, one entry stored by a request with `Store: true` and a small/no explicit freshness intent can later be read back by a different request (same owner/URL/method/body, different `WorkflowID`) that supplies an arbitrarily large `MaxAgeMs`, causing genuinely stale HTTP response data (up to the global cache TTL, default 10 minutes per the README) to be accepted as "fresh," analogous to how a fixed `RESPONSE_TIMEOUT` constant in the reported bug allows Chainlink price data to be treated as fresh well past its true update cadence.

### Impact Explanation
Because HTTP Action responses feed directly into workflow computation/consensus (e.g., data-feed-style workflows), a workflow author can deliberately (or unintentionally, via misconfiguration) request a large `MaxAgeMs` to retrieve data cached by an earlier, unrelated workflow run under the same owner, receiving out-of-date external data without any bound rooted in the endpoint's actual update frequency. This can lead to stale-data-driven decisions/reports, similar in kind to the oracle staleness bug in the report — the "freshness" of data used by the system does not reflect its true recency.

### Likelihood Explanation
Any workflow owner controls the `CacheSettings.MaxAgeMs` and `Store` fields of their own `OutboundHTTPRequest` messages sent through the gateway, so triggering this requires no special privilege beyond normal workflow authoring — it is directly reachable from the unprivileged node/gateway message path (`HandleNodeMessage` → `makeOutgoingRequest` → `responseCache.Fetch`).

### Recommendation
Do not let the reader's `CacheSettings.MaxAgeMs` unilaterally validate staleness for entries it did not create. Either: (1) include `CacheSettings` (or at least an intended max-staleness bound set at store time) in the cache key so freshness intent is fixed per stored entry, or (2) enforce a per-endpoint/administratively-configured minimum freshness bound distinct from the caller-supplied value, so a requester cannot unilaterally accept data staler than the endpoint's true update cadence.

### Proof of Concept
1. Workflow (owner `0xAAA`, `WorkflowID=W1`) issues an `OutboundHTTPRequest` to `GET https://api.example.com/price` with `CacheSettings{Store: true, MaxAgeMs: 1000}`. Response is fetched and cached at `cache[hash] = {response, storedAt: t0}` via `responseCache.Fetch`/`Set` [6](#0-5) .
2. Two minutes later, the same owner's different workflow (`WorkflowID=W2`, same method/URL/headers/body) issues the same request but with `CacheSettings{MaxAgeMs: 600000}` (10 minutes).
3. Because `req.Hash()` ignores `CacheSettings` and `WorkflowID` [7](#0-6) , the lookup hits the same cache key, and `cachedResp.storedAt.Add(600000ms).After(time.Now())` is true, so the 2-minute-old response from W1 is returned to W2 as "fresh," even though W2 never observed the actual freshness policy that produced the cached value.

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```

```go
func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
```
