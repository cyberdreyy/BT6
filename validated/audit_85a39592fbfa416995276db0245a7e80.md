### Title
View-role authenticated user can retrieve bridge OutgoingToken via GET /v2/bridge_types/:BridgeName - (File: core/web/bridge_types_controller.go)

### Summary
`BridgeTypesController.Show` returns a full `presenters.BridgeResource` including the bridge's `OutgoingToken` field, which is serialized unconditionally (no `omitempty`, no redaction). The GET route for this handler is registered in `core/web/router.go` without a `RequiresEditRole`/admin gate, so any authenticated session or API token with only view-role privileges can retrieve the bridge's outgoing authentication token.

### Finding Description
`BridgeTypesController.Show` (`core/web/bridge_types_controller.go:125-146`) looks up the bridge via `btc.App.BridgeORM().FindBridge(ctx, taskType)` and returns it via `presenters.NewBridgeResource(bt)` with no field-level filtering.

`presenters.BridgeResource` (`core/web/presenters/bridges.go:11-22`) defines:
```go
IncomingToken          string       `json:"incomingToken,omitempty"`
OutgoingToken          string       `json:"outgoingToken"`
```
Only `IncomingToken` is annotated `omitempty` and is deliberately left empty except at `Create` time (`btc.App.GetAuditLogger()...` / `resource.IncomingToken = bta.IncomingToken` in `Create` only, `bridge_types_controller.go:98-99`). `OutgoingToken`, however, is copied unconditionally in `NewBridgeResource` (`bridges.go:37`) for every handler that returns a `BridgeResource` — `Show`, `Index`, `Update`, and `Destroy` — with no redaction logic.

The `Show` route (GET `/v2/bridge_types/:BridgeName`) is mapped in `core/web/router.go` alongside the other bridge-type routes; unlike `Create`/`Update`/`Destroy`, it is not wrapped with the `RequiresEditRole` (or admin-only) middleware used elsewhere in the same router group, meaning any authenticated session/token — including one restricted to view role — reaches `Show` and receives the full JSON payload, including `outgoingToken`.

The `OutgoingToken` is the bearer credential the Chainlink node uses to authenticate outbound HTTP requests to the configured external adapter/bridge URL (see `core/bridges/bridge_type.go` and `core/services/pipeline` bridge task use of this token when calling the adapter). Disclosure of this token allows an attacker to impersonate the bridge adapter or replay authenticated calls to whatever service the token protects.

### Impact Explanation
This is a credential/secret disclosure vulnerability: a low-privilege (view-role) authenticated principal can read another principal's operationally-sensitive bridge credential (`OutgoingToken`) via a routine GET request, violating the "secrets never leave" invariant and enabling impersonation of the bridge adapter integration. This maps to Chainlink's node "sensitive information disclosure" / authorization-bypass bounty class since it stems from a missing per-route privilege check combined with a presenter that doesn't redact secret fields for read paths.

### Likelihood Explanation
Requires only a valid view-role (or restricted API token) session — the lowest node privilege tier — and a single unauthenticated-to-node-but-authenticated-as-view-user GET request to a known/guessable bridge name. No timing, race, or complex chaining needed; fully deterministic and repeatable.

### Recommendation
- Add `RequiresEditRole` (or a dedicated read-scope check appropriate for secrets) to the `Show`/`Index` GET routes for bridge types in `core/web/router.go`, or
- Redact `OutgoingToken` in `presenters.NewBridgeResource` for read paths (e.g., add `omitempty` and only populate it on `Create`, mirroring `IncomingToken`'s handling), returning a masked/never value instead for `Show`/`Index`/`Update`/`Destroy`.

### Proof of Concept
Go handler-level test plan (extending `core/web/bridge_types_controller_test.go`):
1. Seed a bridge type via `bridges.ORM.CreateBridgeType` with a known `OutgoingToken` value, e.g. `"secret-outgoing-token"`.
2. Construct an authenticated HTTP client using a view-role-only session/token (as done elsewhere in `cltest` helpers for view-role clients).
3. Issue `GET /v2/bridge_types/<bridgeName>` using that client.
4. Assert HTTP 200 and parse response JSON body.
5. Assert `data.attributes.outgoingToken == "secret-outgoing-token"` is present — demonstrating the leak (test should fail/flag once fix applied, since token should be omitted or masked for non-edit roles). [1](#0-0) [2](#0-1)

```go
// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
```
