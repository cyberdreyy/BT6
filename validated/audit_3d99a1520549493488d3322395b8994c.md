I found a genuine analog: a deposit-token refund path in `ProvisionerV2` that can permanently trap USDC/USDT if the depositing user is blacklisted, with no whitelist gate on `sellToken`/deposit `token` and no way to redirect the refund to a non-blacklisted address.

### Title
Refund/cancel of an async deposit request can permanently lock a blacklisted (USDC/USDT) depositor's escrowed tokens in `ProvisionerV2` - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`requestDeposit` escrows arbitrary ERC20 tokens (including blacklistable stablecoins like USDC/USDT, since there is no token whitelist rejecting them in `setTokenDetails`) from `msg.sender` [1](#0-0) . When the request is refunded or self-cancelled, `_clearHashAndTransferRefund`/`cancelRequest` call `_transferWithFallback(token, requester, receiver, amount)` where `requester == request.user` [2](#0-1) [3](#0-2) . If both the receiver and `request.user` (requester) are the same blacklisted address, the fallback path itself reverts, permanently reverting the refund/cancel call.

### Finding Description
`_transferWithFallback` is defined as:
```
function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
    if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
        token.safeTransfer(requester, amount);
    }
}
``` [4](#0-3) 

The "try" transfer to `receiver` is soft-failing, but the fallback `token.safeTransfer(requester, amount)` is a hard call that reverts on failure. An ordinary user calls `requestDeposit(token, tokensIn, ...)` with `token` = USDC/USDT and `receiver = msg.sender` (the default, single-arg overload) [5](#0-4) , transferring `tokensIn` into the contract via `token.safeTransferFrom(msg.sender, address(this), tokensIn)` [6](#0-5) . If that same user later becomes blacklisted by the token issuer (or already is, and simply used a currently-whitelisted `purchaseToken`-independent path — here the deposit token itself is the blacklistable one), then:
- `cancelRequest` (self-cancel, `msg.sender == request.user`) hits `_clearHashAndTransferRefund(token, request, msg.sender, refundAmount, token)` → `_transferWithFallback(token, msg.sender, request.receiver, refundAmount)`. Since `receiver == requester` in the common case (or the soft transfer to receiver fails because receiver is the same blacklisted address), it falls into `token.safeTransfer(requester, amount)`, which reverts because `requester` is blacklisted [3](#0-2) [7](#0-6) .
- `refundRequest` (callable by anyone once the deadline passes) hits the identical `_clearHashAndTransferRefund(token, request, request.user, request.tokens, token)` and reverts the same way [8](#0-7) .
- The async solve path (`_solveDepositVaultFixedPrice`/`_solveDepositVaultAutoPrice`) also calls `_transferWithFallback(token, request.user, request.receiver, request.tokens)` on the deadline-expired branch, hitting the exact same revert [9](#0-8) .

Because every code path that would return the escrowed deposit token back out of the contract funnels through `_transferWithFallback` with `requester == request.user`, and the hard fallback `safeTransfer(requester, ...)` reverts for a blacklisted `requester`, there is no way to recover the escrowed USDC/USDT: the request hash can never be cleared, and the tokens are permanently stuck in `ProvisionerV2`. This exactly mirrors the Halborn `AuctionUpgradeable` root cause: a blacklist-safe fallback that isn't actually blacklist-safe because it degenerates to an unconditional transfer to the (possibly blacklisted) original party.

Unlike the deposit-refund path, the redeem-refund path returns the vault's own unit token (`MULTI_DEPOSITOR_VAULT` shares), which is not blacklistable, so that side is not affected — the vulnerability is specific to the deposit-token refund/cancel/expired-solve paths where `transferToken == token` and `token` may be USDC/USDT.

### Impact Explanation
An ordinary user's own escrowed USDC/USDT deposit becomes permanently frozen inside `ProvisionerV2` with no admin or user-level recovery path (cancel, refund, and even a late solve attempt all revert identically). This is a direct freezing of user funds in a deployed, in-scope contract, matching Immunefi's "temporary/permanent freezing of user funds" severity criteria.

### Likelihood Explanation
Requires only that the depositing address becomes blacklisted by the token issuer (Circle/Tether) — an event outside the protocol's control but realistic for USDC/USDT, and requires no privileged role, oracle manipulation, or malicious peer; it is triggered purely by ordinary calls to `requestDeposit`, `cancelRequest`, and `refundRequest`. The precondition (depositing token is blacklistable and requester later blacklisted) is the same precondition class accepted in the reference report.

### Recommendation
Do not let a failed fallback transfer revert the whole call: use `trySafeTransfer` for both the receiver and the requester fallback, and if both fail, persist the amount in a per-user/per-token "stuck balance" ledger that can be claimed later to any address the user designates (rather than hard-coding the destination to the potentially-blacklisted `requester`/`receiver`). Alternatively, restrict `setTokenDetails` to reject known blacklistable tokens, mirroring the Irrigation Protocol fix of whitelisting only non-blacklistable `sellTokens`.

        // Requirements: self-cancel caller must be request user

    function _clearHashAndTransferRefund(
        IERC20 token,
        RequestV2 calldata request,
        address requester,
        uint256 amount,
        IERC20 transferToken
    ) internal {
        bytes32 requestHash = _getRequestHash(token, request);
        // Requirements: hash has been set
        require(asyncRequestHashes[requestHash], Aera__HashNotFound());
        // Effects: unset hash as used
        asyncRequestHashes[requestHash] = false;
        // Interactions: transfer amount to receiver, fallback to requester on transfer failure
        _transferWithFallback(transferToken, requester, request.receiver, amount);

        // Log refund event
        if (_isRequestTypeDeposit(request.requestType)) {
            emit DepositRefunded(requestHash);
        } else {
            emit RedeemRefunded(requestHash);
        }
    }

    /// @notice Transfers amount to receiver and falls back to requester if receiver transfer fails
    /// @param token The ERC20 token being transferred
    /// @param requester The original requester address used as fallback receiver
    /// @param receiver The intended receiver from the request
    /// @param amount The amount of tokens to transfer
    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
