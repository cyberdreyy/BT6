## Title
Builder payment `fee_recipient` in `ExecutionPayloadBid` is unchecked at the state-transition layer, allowing the builder to misdirect the proposer's payment - (File: specs/gloas/beacon-chain.md)

## Summary
`process_execution_payload_bid` accepts a `SignedExecutionPayloadBid` whose `fee_recipient` field is chosen and signed unilaterally by the builder, and never validates it against the block proposer's committed `SignedProposerPreferences.fee_recipient` or any other authoritative proposer identity. The only place such a check exists is in the p2p gossip validator, which is a soft, non-authoritative filter (`GossipIgnore`), not a consensus rule enforced during state transition. This mirrors the Malda `EverclearBridge` bug: the "receiver" of a payment is embedded in an unchecked, attacker-controlled message field, letting the message's author redirect funds meant for someone else.

## Finding Description
In `specs/gloas/builder.md`, the protocol's stated invariant is: *"If a proposer accepts a builder's bid, the builder will pay the proposer what it promised."* [1](#0-0) 

The builder sets `bid.fee_recipient` to "an execution address to receive the payment," and the spec explicitly notes this is supposed to equal the proposer's declared preference from `SignedProposerPreferences`: [2](#0-1) 

However, that equality is checked **only** in the p2p gossip validator, as an `IGNORE` (non-authoritative) condition: [3](#0-2) 

The actual consensus-level acceptance function, `process_execution_payload_bid`, checks the builder's signature, active status, balance sufficiency, blob-commitment count, slot/parent-hash/randao consistency — but never checks `bid.fee_recipient` against anything: [4](#0-3) 

The resulting `BuilderPendingPayment.withdrawal.fee_recipient` is taken verbatim from the bid and is later flushed into `state.builder_pending_withdrawals` by either `process_builder_pending_payments` (quorum path) or `apply_parent_execution_payload`/`settle_builder_payment` (older-block path), again with no cross-check against the proposer's identity or preference: [5](#0-4) [6](#0-5) 

Finally, `get_builder_withdrawals` builds the actual EL `Withdrawal.address` straight from `withdrawal.fee_recipient`, and `apply_withdrawals` decreases the builder's balance and mints the withdrawal to that address: [7](#0-6) 

At no point in the authoritative state-transition path is `fee_recipient` bound to `get_beacon_proposer_index(state)` (which is recorded separately, only for weight/quorum accounting) or to the proposer's signed preferences. This breaks the equality the protocol claims to guarantee: *value committed as "payment to the proposer" == value actually paid to the proposer's address*.

## Impact Explanation
A builder (optionally colluding with, or simply not being cross-checked by, the block proposer) can set `bid.fee_recipient` to an address it controls instead of the proposer's declared address. Because gossip-layer validation is not part of consensus, a bid can reach a proposer out-of-band (e.g., via a relay, direct submission, or proposer-builder collusion) with a mismatched `fee_recipient` and still be perfectly valid at the state-transition level. The block will be accepted by every spec-following node, the builder's balance will be debited by `bid.value`, and the resulting Withdrawal — real Gwei — will be paid to the builder-chosen address rather than the proposer that was promised the fee. This is exactly the "a builder payment ... misdirected" category of High-impact issue: Gwei that the protocol nominally allocates to the block proposer is paid to a non-owner (the builder itself or an accomplice), while the block, the recorded `BuilderPendingPayment.proposer_index`, and PTC/attester incentives all still treat the payment as if it went to the honest proposer.

## Likelihood Explanation
The precondition is only that a builder submit (directly to a proposer, bypassing/ignoring gossip re-broadcast, or via collusion) a validly signed `ExecutionPayloadBid` with `fee_recipient` unequal to the proposer's `SignedProposerPreferences`. No coalition of majority stake, no client bug, and no external party is needed — the builder alone controls the field, and the proposer (if unsophisticated, using default relay/builder software, or colluding) can include it. Since the check exists only as a gossip-layer heuristic that is trivially bypassed by not gossiping the bid (delivering it privately, as MEV-relays already do), this is straightforward to realize in a spec-following implementation.

## Recommendation
Add an explicit assertion in `process_execution_payload_bid` (consensus layer) that `bid.fee_recipient` matches the fee-recipient address committed by the current slot's proposer (e.g., via a state-tracked/validated `SignedProposerPreferences` or an equivalent on-chain commitment), mirroring the fix applied to the Malda `EverclearBridge.sol` where the receiver was forced to equal the expected market address. Relying solely on a `GossipIgnore` p2p check is insufficient because it is not part of the authoritative state transition and can be bypassed by out-of-gossip bid delivery.

## Proof of Concept
1. Proposer `P`, assigned to slot `N`, broadcasts (or is expected to have) `SignedProposerPreferences` with `fee_recipient = 0xAAAA…`.
2. Builder `B` (active, sufficient balance) constructs `ExecutionPayloadBid` for slot `N` with `fee_recipient = 0xBBBB…` (an address `B` controls) and `value = V`, and signs it with its own key — this passes `verify_execution_payload_bid_signature`.
3. `B` delivers this bid directly to `P` out-of-band (e.g. via a relay/MEV-boost-style channel), never broadcasting it on the `execution_payload_bid` gossip topic (so the mismatched-`fee_recipient` `GossipIgnore` check in `validate_execution_payload_bid_gossip` never triggers).
4. `P` includes `signed_bid` in `block.body.signed_execution_payload_bid` and proposes the block. `process_execution_payload_bid(state, signed_bid)` runs during `process_block` and succeeds: no check compares `bid.fee_recipient` to `0xAAAA…` or to `P`'s identity. [8](#0-7) 
5. Once quorum is reached (`process_builder_pending_payments`) or the parent-block settlement path runs (`apply_parent_execution_payload` → `settle_builder_payment`), `BuilderPendingWithdrawal(fee_recipient=0xBBBB…, amount=V, builder_index=B)` is appended to `state.builder_pending_withdrawals`.
6. `process_withdrawals` → `get_builder_withdrawals` emits a `Withdrawal(address=0xBBBB…, amount=V, …)`; `apply_withdrawals` decreases `B`'s balance by `V`, and the EL mints `V` Gwei to `0xBBBB…` instead of `P`'s `0xAAAA…`.
7. Every spec-following node accepts this block and state transition as fully valid — the protocol's stated invariant ("the builder will pay the proposer what it promised") is broken, and `V` Gwei ends up paid to an address the proposer never authorized.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

```markdown
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
```

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid
