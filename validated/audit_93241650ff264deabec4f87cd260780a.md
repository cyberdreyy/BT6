### Title
System Program `CreateAccount` Griefing via Pre-funded Target Address - (File: programs/system/src/system_processor.rs)

### Summary
The System Program's `create_account` handler rejects account creation whenever the target address already holds any lamports, treating this as `SystemError::AccountAlreadyInUse`. Because any unprivileged party can send an arbitrary (even 1-lamport) transfer to any address — including PDAs whose creation is anticipated — an attacker can pre-fund a target address to permanently block a legitimate `SystemInstruction::CreateAccount` (or `CreateAccountWithSeed`) from succeeding, causing the dependent transaction/CPI to revert. This mirrors the GMX `createDeposit` report: a strict-equality/zero-balance precondition can be griefed by an unrelated inbound transfer of dust funds, denying the legitimate actor's operation.

### Finding Description
`create_account` in `programs/system/src/system_processor.rs` enforces:
```
if to.get_lamports() > 0 {
    ...
    return Err(SystemError::AccountAlreadyInUse.into());
}
``` [1](#0-0) 

This check runs before `allocate_and_assign` and `transfer`, and is invoked from both `SystemInstruction::CreateAccount` and `SystemInstruction::CreateAccountWithSeed` in the instruction dispatcher. [2](#0-1) 

Since lamport transfers via `SystemInstruction::Transfer` require no cooperation from the recipient (only the sender must sign), any unprivileged address — including a not-yet-created PDA computed deterministically off-chain (e.g. `Pubkey::create_with_seed`, `find_program_address`) — can be sent a trivial amount of lamports by anyone. If a legitimate user or program later attempts `create_account`/`create_account_with_seed` targeting that same address (a very common pattern for initializing PDAs, ATAs-equivalent accounts, escrow accounts, etc.), the instruction unconditionally fails with `AccountAlreadyInUse`, and the encompassing transaction (or CPI chain) reverts.

This is the exact bug class described in the GMX report: a strict precondition (`lamports == 0` here, `executionFee` equality there) can be violated by an unrelated party sending funds to the target account, denying the intended party's ability to complete their operation.

Notably, Agave developers have already implicitly acknowledged this exact issue by introducing `SystemInstruction::CreateAccountAllowPrefund`, gated behind the `create_account_allow_prefund` feature, which explicitly skips the zero-lamports check and is documented as "Intended for use where account has already had rent paid in whole or in part before creation." [3](#0-2) [4](#0-3) 

However, this fix is feature-gated and opt-in per-instruction; the original `CreateAccount`/`CreateAccountWithSeed` paths — which remain the default and by far the most widely used code path across the entire ecosystem (used by virtually every program that creates a PDA) — retain the vulnerable strict `lamports > 0` check.

### Impact Explanation
This is a griefing/DoS primitive against any protocol on Solana that creates deterministic addresses (PDAs, seed-derived accounts) via `system_instruction::create_account`/`create_account_with_seed`, which is an extremely common pattern (escrow accounts, vault accounts, order accounts, nonce-like accounts, etc.). An attacker who can predict the address (which is almost always true, since these addresses are deterministic and known before creation) can front-run legitimate initialization with a 1-lamport transfer, causing repeated failures until the victim/program adapts (e.g., by switching to `CreateAccountAllowPrefund`, or by draining/closing and retrying, which itself costs the victim gas and requires bespoke handling). This does not directly cause fund loss but is a reliable denial-of-service against account initialization flows relied upon throughout the ecosystem — directly analogous to the "Acknowledged" severity assigned to the original GMX report.

### Likelihood Explanation
Likelihood is high for any address whose derivation is public/predictable (virtually all PDAs and seed-based addresses are), since:
- Sending lamports to an arbitrary pubkey requires no special privilege — any `SystemInstruction::Transfer` signed by the attacker suffices.
- The `create_account` precondition check is unconditional and has no allowance for small dust amounts.
- The safe alternative (`CreateAccountAllowPrefund`) is feature-gated and not the default code path used by the vast majority of existing on-chain programs and client SDKs.

### Recommendation
- Encourage/require migration of common `create_account`-based initialization flows to `CreateAccountAllowPrefund` once the `create_account_allow_prefund` feature is activated network-wide, since it already resolves this exact issue by not requiring a zero-lamports precondition. [3](#0-2) 
- Consider making `create_account` itself tolerant of pre-existing lamports as long as the account is unowned by another program and has no data (rather than an unconditional `lamports > 0` rejection), matching the remediation direction suggested for the analogous GMX report (avoid strict equality/zero-balance preconditions that third parties can violate).
- Document this griefing vector for downstream program developers so they proactively adopt `CreateAccountAllowPrefund` or defensively check/handle a stray lamport balance before invoking `create_account`.

### Proof of Concept
1. Off-chain, compute the deterministic target address a protocol will use, e.g. via `Pubkey::create_with_seed(base, seed, owner)` or `Pubkey::find_program_address(seeds, program_id)`.
2. Attacker submits a standard `SystemInstruction::Transfer` sending 1 lamport from the attacker's own funded account to that target address — no signature or cooperation from the victim is required.
3. Victim (user or program) submits a transaction containing `SystemInstruction::CreateAccount` (or `CreateAccountWithSeed`) targeting the same address to initialize their PDA/account, as most protocols do.
4. Inside `create_account`, the check `if to.get_lamports() > 0` at [1](#0-0)  evaluates true (balance = 1 lamport from the attacker), and the instruction returns `SystemError::AccountAlreadyInUse`, causing the victim's transaction/CPI to fail.
5. This can be repeated indefinitely by the attacker for negligible cost (1 lamport + transaction fee) each time the victim retries with the standard `CreateAccount` instruction, unless the victim switches to `CreateAccountAllowPrefund` (feature-gated) or otherwise works around the stray balance.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
