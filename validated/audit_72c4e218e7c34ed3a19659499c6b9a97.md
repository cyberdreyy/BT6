### Title
Re-requesting a withdrawal overwrites `lastWithdrawRequest`, letting a loss-adjusted (haircut) receipt escape the loss and be paid at par — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.requestWithdraw` stores the epoch of a user's latest withdraw request in `lastWithdrawRequest[_user]`. The loss-adjusted claim path (`_claimLossAdjustedWithdrawRequest`) looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — i.e., it only checks the *most recent* request epoch. If a user whose epoch-N receipt was haircut by `stopEpochWithDuration(_lossAmount)` submits another `requestWithdraw` in a later epoch before claiming, the loss marker is overwritten ("freed"), the epoch-N haircut receipt becomes unreachable by the loss-adjusted path, and `_claimFundedWithdrawRequest` pays the aggregate `withdrawsRequests[_user]` at par. This mirrors the use-after-free/dangling-reference bug class of CVE-2023-39129: stale bookkeeping is reused after being overwritten, producing a payout inconsistent with the intended loss waterfall.

### Finding Description
- In `requestWithdraw`, `lastWithdrawRequest[_user] = currentEpoch` is set unconditionally and `withdrawsRequests[_user] += _amount` / `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` accumulate across epochs [1](#0-0) .
- `_claimLossAdjustedWithdrawRequest` derives the loss epoch solely from `lastWithdrawRequest[_user]`; any earlier loss-epoch receipt is invisible to it [2](#0-1) .
- `_claimFundedWithdrawRequest` then pays the full aggregate `withdrawsRequests[_user]` (which still includes the haircut epoch-N basis) once `epochNumber > lastWithdrawRequest[_user]` [3](#0-2) .
- The code comment confirms `pendingWithdraws` for the loss epoch "was already cleared when the borrower funded the loss-adjusted amount" — i.e., only the reduced amount was sourced [4](#0-3) .
- Re-requesting is explicitly supported ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch") — no guard prevents it [5](#0-4) .

Attack sequence (attacker is a plain KYC'd lender / tranche holder):
1. Attacker deposits, waits for `stopEpoch`, calls `requestWithdraw` in buffer → receipt recorded at `lastWithdrawRequest = N`, `withdrawsRequestsByEpoch[N] = P`.
2. Manager calls `stopEpochWithDuration` / loss-bearing stop with `_lossAmount > 0` → `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL`; borrower funds only `P * lossPrice` into the strategy.
3. In epoch N+1 buffer, attacker calls `requestWithdraw` again with any dust amount → `lastWithdrawRequest` becomes N+1; the loss marker for epoch N is overwritten.
4. Epoch N+1 stops; borrower funds the new (small) pendingWithdraws at par. Attacker calls `claimWithdrawRequest`: loss path looks up `lossRecoveryPriceByEpoch[N+1]` (zero → skipped), funded path pays `P + dust` at **par**.

### Impact Explanation
The attacker receives `P` instead of `P * lossRecoveryPrice`, extracting the haircut difference from the strategy's underlying balance. Those funds were never sourced by the borrower (only the loss-adjusted amount was funded), so the excess comes directly out of the reserve backing other pending/funded receipts and active tranche holders — a direct theft causing pro-rata insolvency for later claimants. Quantified loss: `(1 - lossRecoveryPrice/RECOVERY_FULL) * P` per attacker, repeatable by any holder each loss epoch; invariant broken: loss waterfall / fair burn.

### Likelihood Explanation
Requires a `stopEpochWithDuration`/`stopEpoch` that records a nonzero loss (borrower underpayment within duration mechanics — an honest-manager path, not attacker-controlled) plus one additional dust `requestWithdraw` by the attacker in the following buffer. Both steps are permissionless for a KYC-passing lender; no privileged cooperation needed. Conditions occur whenever a pool takes an in-epoch loss without full default.

### Recommendation
Track loss epochs per receipt rather than per latest request: either iterate the user's epochs with `lossRecoveryPriceByEpoch`, or record the loss price inside `withdrawsRequestsByEpoch`/`Apr0UserData` at stop time. At minimum, apply the haircut in `_claimFundedWithdrawRequest` per epoch bucket, or revert `requestWithdraw` when the user has an unclaimed loss-epoch receipt until it's claimed.

Note: I was unable to read `stopEpochWithDuration`'s exact write of `lossRecoveryPriceByEpoch` within the iteration limit; the claim relies on the observed keying by `lastWithdrawRequest` in `_claimLossAdjustedWithdrawRequest` and the aggregate-par payout in `_claimFundedWithdrawRequest`. If `lossRecoveryPriceByEpoch` is keyed by something other than the request epoch, or `requestWithdraw` is blocked while `withdrawsRequestsByEpoch` has an unfunded loss entry (no such check was found at lines 271–294), the finding should be re-validated.

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
