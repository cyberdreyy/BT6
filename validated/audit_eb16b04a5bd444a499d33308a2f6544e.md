### Title
Unanchored regex match in `overwriteRegexCheck` lets `KUBERNETES_NAMESPACE_OVERWRITE` bypass operator-intended namespace pattern - (File: executors/kubernetes/overwrites.go)

### Summary
`overwriteRegexCheck` validates `KUBERNETES_NAMESPACE_OVERWRITE` (and other overwrite variables) using `regexp.MatchString`, which succeeds if the pattern is found *anywhere* in the value rather than requiring the pattern to match the entire string. If the operator configures `namespace_overwrite_allowed` without explicit `^...$` anchors (a pattern the docs themselves show as a bare fragment like `ci-.*`), an unprivileged job can supply a namespace overwrite value that merely contains the allowed substring while the literal value used as the pod's namespace is attacker-controlled.

### Finding Description
`createOverwrites` reads the job-controlled variable `NamespaceOverwriteVariableName` ("KUBERNETES_NAMESPACE_OVERWRITE") and passes it to `evaluateOverwrite`, which delegates to `overwriteRegexCheck`: [1](#0-0) [2](#0-1) 

The check is `r.MatchString(value)`, and if it succeeds, `evaluateOverwrite` returns the raw `overwriteValue` unchanged, which becomes the pod's namespace verbatim: [3](#0-2) 

`regexp.MatchString`/`(*Regexp).MatchString` in Go reports whether the pattern matches **any substring** of the input; `^` and `$` are required by the caller to anchor to the start/end of the whole string. Neither the regex compilation, the check itself, nor any calling code enforces full-string anchoring — the burden is entirely on the operator's configured regex string being correctly anchored. GitLab Runner's own documented examples for `namespace_overwrite_allowed`/similar overwrite regexes commonly show bare fragments (e.g. `ci-.*`) without instructing operators that `^...$` is mandatory to prevent substring matches.

Exploit flow:
1. Precondition: operator sets `KubernetesConfig.NamespaceOverwriteAllowed = "ci-.*"` intending only namespaces literally starting with `ci-` to be selectable.
2. Attacker (unprivileged pipeline author) sets job variable `KUBERNETES_NAMESPACE_OVERWRITE=other-ns-ci-x` (or a value containing `ci-` anywhere, e.g. across a would-be multi-line context) — `regexp.MatchString("ci-.*", "other-ns-ci-x")` returns `true` because it finds `ci-x` as a substring starting mid-string.
3. `overwriteRegexCheck` returns no error, so `evaluateOverwrite` returns the full literal string `other-ns-ci-x` as `o.namespace`.
4. The Kubernetes executor schedules the job pod into namespace `other-ns-ci-x`, which is outside the operator's intended `ci-*` naming convention and may carry different (potentially broader) RBAC bindings/service-account permissions than the runner operator intended to expose to CI jobs.

Existing checks do not stop this: there is no additional namespace-existence/allowlist check beyond the regex, and the regex match is intentionally free-form to allow flexible operator patterns — but the implementation silently permits substring matches when operators don't anchor their pattern, which is an easy and non-obvious operator mistake (unlike, e.g., a full-match helper). This is a real gap between the intended invariant ("only operator-approved namespace patterns are selectable") and the actual mechanism (substring search) for any operator who does not explicitly anchor their regex.

### Impact Explanation
A job can end up scheduled into a Kubernetes namespace that the operator did not intend to permit, provided the operator's `namespace_overwrite_allowed` regex is not anchored with `^...$`. If that unintended namespace has a more permissive RBAC role binding or service account than the CI namespaces, the job pod inherits those elevated permissions — a namespace-scoped privilege escalation relative to the operator's intended CI sandboxing. Impact is scoped to whatever namespace happens to satisfy the substring match and exist in the cluster; it is not an arbitrary/wildcard bypass unless the cluster contains a namespace name that both contains the required substring and exists.

### Likelihood Explanation
Feasible in any deployment where the operator's `namespace_overwrite_allowed` regex is unanchored (a common, non-obvious mistake, and the pattern is a plain string operators write themselves — the docs do not explicitly mandate anchors). Fully reproducible/deterministic once such a config exists: any job variable is attacker-controlled input for pipeline authors with variable-setting permission (a low bar in typical CI setups). The precondition (operator's exact regex choice) is outside Runner's code but the *root cause* — using substring `MatchString` instead of enforcing full-string match or requiring/auto-adding anchors — is a Runner-side gap that removes a safety net an operator would reasonably expect.

### Recommendation
Enforce full-string matching in `overwriteRegexCheck` regardless of whether the operator's regex is anchored — e.g., wrap the compiled pattern so it must match the entire string (`^(?:` + regex + `)$`) before calling `MatchString`, or use `regexp.MustCompile(regex).FindString(value) == value` semantics. Additionally, document/require operators to anchor `namespace_overwrite_allowed` and similar `*_overwrite_allowed` regexes, or validate/auto-anchor them at config-load time in `common/config.go`.

func overwriteRegexCheck(regex, value string) error {
	var err error
	var r *regexp.Regexp
	if r, err = regexp.Compile(regex); err != nil {
		return err
	}
	if match := r.MatchString(value); !match {
		return &malformedOverwriteError{value: value, pattern: regex}
	}
	return nil
}
