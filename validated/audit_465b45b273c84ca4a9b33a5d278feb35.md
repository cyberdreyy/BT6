Unauthorized Seizure of Global Fee Admin via Front-Runnable `init_global_fee_state` Instruction - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
The `init_global_fee_state` instruction, intended to be called once during deployment to bootstrap the protocol-wide `FeeState` PDA, has no authorization check restricting who may call it. Any unprivileged party can front-run the legitimate deployer's call and become the permanent `global_fee_admin`, exactly matching the reported bug class of non-atomic, front-runnable deployment/initialization.

### Finding Description
`init_global_fee_state` creates the singleton `FeeState` PDA (seeded only by `FEE_STATE_SEED`) and sets `fee_state.global_fee_admin = admin_key` where `admin_key` is an arbitrary caller-supplied argument [1](#0-0) . The `InitFeeState` accounts struct only requires a generic `Signer` as `payer` and gates account creation solely via the Anchor `init` constraint (which only prevents re-initialization, not first-caller identity) [2](#0-1) . There is no check against the program's upgrade authority, a hardcoded pubkey, or any other privileged signer — a grep across the codebase found no `upgrade_authority`/`ProgramData` verification anywhere in the program.

This mirrors the reported `BatcherPaymentService` issue: deployment (deploying/upgrading the program, i.e. the `init` becoming callable) and initialization (setting the admin) are two separate, non-atomically-linked steps. Once the program is deployed/upgraded on a public cluster, anyone watching the mempool can send their own `init_global_fee_state` transaction before the deployer's initialization transaction lands, becoming `global_fee_admin` themselves.

The `global_fee_admin` role is highly privileged: it can arbitrarily edit the fee wallet destination, fee rates, and other protocol-wide fee parameters via `edit_global_fee_state` [3](#0-2) , override program fee toggling per-group via `config_group_fee` [4](#0-3) , and is referenced in pause/unpause logic [5](#0-4) .

### Impact Explanation
An attacker seizing `global_fee_admin` gains protocol-wide financial control: they can redirect the `global_fee_wallet` to their own address so that program fees collected from every marginfi group flow to them, and can tune `program_fee_fixed`/`program_fee_rate` and other fee parameters across the entire protocol via `edit_global_fee_state`. This is a durable, protocol-wide value-redirection vulnerability, not scoped to a single group or bank, since `FeeState` is a singleton PDA referenced by every group's `fee_state_cache`.

### Likelihood Explanation
This requires the attacker to observe a pending `init_global_fee_state` transaction (or simply attempt it proactively/regularly) on a public RPC/mempool before the legitimate deployer's transaction is finalized, and win the race. On Solana this is feasible via transaction front-running against a public RPC, or simply by any actor submitting the call speculatively immediately whenever a new marginfi program deployment/upgrade is detected, since no permission is required to attempt it — only speed. Given the instruction is explicitly documented as "runs once per program," the deploy operators likely expect a small window between deployment and initialization, consistent with the front-running risk pattern in the reported analog.

### Recommendation
Restrict `init_global_fee_state` (and similarly the `init_global_fee_state_v2` / `InitFeeStateV2` instruction, which has the same pattern [6](#0-5) ) to only be callable by a known, trusted authority — e.g., verify the `payer`/caller against the program's upgrade authority (via the `ProgramData` account) or a hardcoded expected admin pubkey — before allowing the PDA to be initialized. Alternatively, bundle the deployment and initialization into a single atomic transaction/instruction so no window exists for front-running.

### Proof of Concept
1. Deployer uploads/upgrades the marginfi program on mainnet (or any public cluster).
2. Deployer prepares to send an `init_global_fee_state` transaction naming themselves as `admin_key`.
3. Attacker monitors the mempool/RPC and, before the deployer's transaction confirms, submits their own `init_global_fee_state` transaction with `admin_key = attacker_pubkey` and `fee_wallet = attacker_wallet`, paying only PDA rent.
4. Because `InitFeeState` has no access control beyond the `init` constraint [2](#0-1) , the attacker's transaction succeeds first, permanently setting `global_fee_admin` and `global_fee_wallet` to attacker-controlled values.
5. The deployer's subsequent `init_global_fee_state` call fails (PDA already initialized), and the attacker now controls all protocol-wide fee configuration and fee wallet routing via `edit_global_fee_state`.
