### Title
Cross-user callback overwrite via colliding MessageId in `HandleLegacyUserMessage` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores the per-request callback keyed solely by `msg.Body.MessageId`, with no check for an existing entry and no binding to `msg.Body.Sender`. An attacker who submits a request with the same `MessageId` as a victim's in-flight legacy request silently overwrites the victim's saved callback, so the eventual node response for that MessageId is delivered to the attacker's connection instead of the victim's.

### Finding Description
`MessageId` is fully attacker/user-controlled: it originates from the JSON-RPC request `ID` field and is copied into `msg.Body.MessageId` in `ValidatedMessageFromReq` (`core/services/gateway/handlers/common/message_util.go:36-58`), then validated only for length/format in `Message.Validate` (`core/services/gateway/api/message.go:54-88`) — there is no uniqueness or ownership requirement on it. The signature covers `MessageId`, `Method`, `DonId`, `Receiver`, and `Payload` (`GetRawMessageBody`, `api/message.go:136-146`), so it proves the sender authored *that* message, but does nothing to prevent two independent signers from choosing an identical `MessageId` string.

In `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:411-414`):
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
```
this unconditionally overwrites any existing map entry for that `MessageId`. There is no check like `if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists { return error }`, and the key is not composed with `msg.Body.Sender`.

Exploit flow: victim A sends a legacy `web_api_trigger` request with `MessageId = X`, signed with A's key; `h.savedCallbacks[X]` is set to A's callback and the request is forwarded to DON nodes. Before a node responds, attacker B sends a second legacy request also using `MessageId = X` but signed with B's key. This passes `Message.Validate()` (no duplicate check) and overwrites `h.savedCallbacks[X]` with B's callback. When a DON node later responds for `MessageId = X`, `handleWebAPITriggerMessage` (`handler.go:148-162`) looks up and deletes `h.savedCallbacks[X]` and delivers the response via `savedCb.SendResponse(...)` — now B's callback, not A's. The victim's request appears to hang/never receive a response, while the attacker receives a response for a request they did not truly own (or, depending on transport wiring, can trigger delivery of the response content intended for the victim to their own connection).

No existing check (rate limiter, allowlist TODO, or message validation) stops this, since `MethodWebAPITrigger` messages only get `nodeRateLimiter` applied on the *outgoing* (node→gateway) path (`handleWebAPIOutgoingMessage`), not on the incoming user path, and the allowlist/rate-limiting for `HandleLegacyUserMessage` is explicitly marked `// TODO: apply allowlist and rate-limiting here` (`handler.go:384`).

### Impact Explanation
This is a cross-user response-confusion vulnerability: an unauthenticated/unprivileged gateway client can hijack delivery of another user's in-flight legacy web API trigger response by colliding on `MessageId`, or conversely deny the victim their response (denial of service on that request). This matches the "cross-user response confusion" impact class explicitly called out in the audit scope.

### Likelihood Explanation
Exploitability depends entirely on the attacker being able to predict or observe a victim's in-flight `MessageId` before the corresponding node response arrives — this repo's index does not show conclusively how MessageIds are generated by client tooling (e.g., `core/capabilities/webapi/trigger/trigger.go`, `core/scripts/gateway/web_api_trigger/invoke_trigger.go`) so their entropy/predictability could not be fully verified here. If IDs are low-entropy, sequential, derived from public data, or otherwise guessable/observable (e.g., leaked via logs, shared UUIDs, or race conditions where both requests are submitted concurrently with an ID the attacker chooses to match), the race is straightforward: send the malicious request with the identical `MessageId` shortly after the victim's request, before the DON node responds (the window is bounded by node processing latency plus `CallbackMaxAgeSec`, default 120s). No special privileges are required — any client able to reach the legacy gateway message endpoint with a valid signature over their own message can attempt this.

### Recommendation
Reject duplicate `MessageId`s instead of overwriting: before inserting into `h.savedCallbacks`, check if the key already exists and return an error (e.g., "duplicate message ID") rather than silently replacing the entry. Additionally, consider binding the callback lookup to `(MessageId, Sender)` or generating gateway-side unique IDs rather than trusting client-supplied IDs, to remove the possibility of cross-sender collisions entirely.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler via `NewHandler` with a stub `handlers.DON` (mock `SendToNode` that no-ops or records calls) and two mock `handlers.Callback` instances, `callbackA` and `callbackB`.
2. Build `msgA` with `Body.MessageId = "shared-id"`, signed with private key A (`msgA.Sign(keyA)`), valid `TriggerRequestPayload` and current timestamp.
3. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)`; assert no error and that `h.savedCallbacks["shared-id"].Callback == callbackA` (via exported test hook or by simulating a node response next).
4. Build `msgB` with the same `Body.MessageId = "shared-id"` but signed with private key B (`msgB.Sign(keyB)`).
5. Call `h.HandleLegacyUserMessage(ctx, msgB, callbackB)`.
6. **Expected secure behavior (currently failing):** the second call should return an error (e.g., "duplicate message ID") and `h.savedCallbacks["shared-id"].Callback` should remain `callbackA`.
7. **Current buggy behavior:** the second call succeeds, and `h.savedCallbacks["shared-id"].Callback == callbackB`. Then simulate a node response for `"shared-id"` via `h.HandleNodeMessage` with method `MethodWebAPITrigger`, and assert `callbackB.SendResponse` is invoked instead of `callbackA.SendResponse`, proving the victim's response was misdelivered to the attacker.
