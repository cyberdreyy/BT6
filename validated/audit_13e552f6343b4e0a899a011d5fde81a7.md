### Title
Delayed withdrawal transactions can bind users to an unintended epoch - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary

`IdleCDOEpochVariant.requestWithdraw` has no deadline or expected-epoch parameter. A signed transaction submitted during one withdrawal buffer can remain valid and be replayed or included during a later buffer. Because execution burns tranche tokens and records the receipt under the then-current `epochNumber`, the user can be exposed to a future borrower default instead of receiving the funded withdrawal from the intended epoch. [1](#0-0) 

### Finding Description

Withdrawal requests are accepted while `allowAAWithdrawRequest` or `allowBBWithdrawRequest` is enabled. [2](#0-1) 

`startEpoch` disables those flags, while a successful `stopEpoch` re-enables them for the following buffer period. [3](#0-2) [4](#0-3) 

Consequently, the only phase check is “is a withdrawal buffer currently open.” The transaction does not identify the buffer or epoch in which the user intended it to execute. When it executes, `requestWithdraw` prices the tranche tokens, calls `IdleCreditVault.requestWithdraw`, and burns the tranche tokens against the current epoch. [5](#0-4) 

The strategy then stores `epochNumber` in `lastWithdrawRequest[_user]` and records the request under that current epoch. [6](#0-5) 

A request submitted during epoch `N`’s buffer but included only during epoch `N + 1`’s buffer therefore becomes an epoch `N + 1` receipt. If the borrower defaults during epoch `N + 1`, that receipt is exposed to the default-recovery haircut rather than having been funded at the end of epoch `N`.

### Impact Explanation

The broken invariant is timely withdrawal finality: a request that should have become a funded claim in epoch `N` can instead become a pending receipt in epoch `N + 1`.

For example, a user holding 1,000 underlying-equivalent AA tranche tokens submits `requestWithdraw` during the epoch-`N` buffer. If that transaction had executed as intended, `stopEpoch` would have funded the pending request through `collectWithdrawFunds`. [7](#0-6) 

If the signed transaction is instead included in the next buffer, it creates a new request for epoch `N + 1`. A subsequent 50% recovery finalization reduces the claim to 500 underlying, producing a 500-underlying loss relative to the originally intended funded withdrawal.

This is not merely a stale-price inconvenience: the delay changes the credit exposure period and can move the user from “already funded withdrawal” to “default-epoch pending receipt.”

### Likelihood Explanation

The attack requires a signed `requestWithdraw` transaction to remain valid while missing its intended buffer and then be included during a later buffer. Ethereum transactions do not expire natively, and this function supplies no transaction-level deadline or expected epoch.

Execution is opportunistic rather than reliably controllable by an ordinary attacker. The economic loss additionally requires an adverse epoch transition, such as a borrower default after the intended withdrawal would have been funded. Existing phase flags prevent execution while an epoch is running, but they deliberately reopen every buffer and do not distinguish the intended buffer from a later one. [8](#0-7) 

### Recommendation

Bind each withdrawal request to the user’s intended execution window.

Add an `expectedEpoch` or equivalent epoch identifier to `requestWithdraw` and require:

```solidity
require(IdleCreditVault(strategy).epochNumber() == expectedEpoch, "Stale epoch");
```

A `deadline` timestamp may be added as well, but a timestamp alone is weaker because an entire epoch can be delayed. An explicit expected epoch prevents a transaction signed for one buffer from silently entering a later credit period.

If backward compatibility is required, introduce a new function such as `requestWithdrawForEpoch(uint256 amount, address tranche, uint256 expectedEpoch)` and deprecate the unbounded selector.

### Proof of Concept

A Foundry fork test can model delayed mempool inclusion by submitting the same calldata after an honest `startEpoch`/`stopEpoch` cycle:

```solidity
function testDelayedWithdrawRequestBindsToLaterEpoch() public {
    // Existing fixture has an AA deposit and an open withdrawal buffer
    // for strategy epoch N.
    uint256 intendedEpoch = creditVault.epochNumber();
    uint256 shares = AAtranche.balanceOf(user);
    uint256 requestValue = cdoEpoch.virtualPrice(address(AAtranche)) *
        shares / 1e18;

    // The signed requestWithdraw(0, AA) transaction misses its intended
    // buffer. Honest manager starts epoch N and later stops it normally.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(underlying, borrower, borrowerRepayment);
    vm.prank(manager);
    cdoEpoch.stopEpoch(nextApr, 0);

    // The delayed signed transaction is now replayed during the buffer
    // preceding epoch N + 1. It is accepted even though the user signed it
    // for epoch N.
    vm.prank(user);
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));

    assertEq(creditVault.lastWithdrawRequest(user), intendedEpoch + 1);
    assertEq(requested, requestValue);
    assertEq(AAtranche.balanceOf(user), 0);

    // Honest manager starts epoch N + 1 and the borrower fails to repay.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(underlying, borrower, 0);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Honest manager finalizes a 50% recovery.
    uint256 recovered = activeBasis / 2;
    deal(underlying, recoverySource, recovered);
    vm.startPrank(manager);
    IERC20(underlying).approve(address(creditVault), recovered);
    cdoEpoch.finalizeDefault(recovered, recoverySource);
    vm.stopPrank();

    vm.prank(user);
    uint256 claimed = cdoEpoch.claimWithdrawRequest();

    // Had the request executed in the intended epoch, it would already have
    // been funded at `requestValue`. Delayed inclusion makes it a receipt
    // in the defaulted epoch.
    assertEq(claimed, requestValue / 2);
    assertLt(claimed, requestValue);
}
```

  function requestWithdraw(uint256 _amount, address _tranche) external returns (uint256 _underlyings) {
    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
      !isWalletAllowed(msg.sender)
    );
  
    // we check if there are donated assets to the pool and transfer them to the feeReceiver if any
    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;
    // add expected fees to pending withdraw fees counter
    pendingWithdrawFees += totalFees;

    /// if there is an AA withdrawal the overperformance that the amount withdrawed would have generated for BB tranches
    /// is saved in interestForOverUnderPerformance. This is used to calculate the interest that should be added to the
    /// expectedEpochInterest at the startEpoch.
    /// If there is a BB withdrawal this amount is subtracted from the expectedEpochInterest
    interestForOverUnderPerformance += diff;

    // The receipt is fixed now and leaves live NAV. Charge management fees upfront
    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
    creditVault.requestWithdraw(_underlyings, msg.sender, principal);
    // burn tranche tokens and decrease NAV without interest for the next epoch as it was not yet counted in NAV
    _withdrawOps(_amount, principal, _tranche);
