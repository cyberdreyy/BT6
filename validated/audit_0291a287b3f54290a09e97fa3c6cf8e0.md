### Title
JWT Replay Protection Check-and-Record Race Allows Token Reuse in `WorkflowMetadataHandler.Authorize` - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The external report's bug class is a missing/late membership-flag update: an entry is checked and processed before the "already seen" flag is committed, allowing the same identity to be accepted multiple times where only-once semantics were intended. The same class of bug exists in the gateway's HTTP-trigger JWT replay-protection cache: the "already used" check and the "mark as used" write are two separate, non-atomic critical sections, so concurrent requests carrying the same JWT can both pass the replay check before either records usage.

### Finding Description
`WorkflowMetadataHandler.Authorize` verifies a caller-supplied JWT, checks whether its `jti` has already been used via `jwtCache.isReplay`, performs signer/key authorization, and only afterwards calls `jwtCache.recordUsage` to persist the `jti` as consumed: [1](#0-0) 

`isReplay` and `recordUsage` are independent, separately-locked operations on the same underlying map — there is no atomic check-and-set: [2](#0-1) 

Because the read (`isReplay`) and the write (`recordUsage`) are not combined under a single lock/transaction, two (or more) concurrent `Authorize` calls presenting the identical JWT (same `jti`) can both observe `isReplay == false` before either has called `recordUsage`. Both requests then proceed past the "already used" guard and are treated as independently valid, defeating the intended one-time-use replay protection — structurally the same root cause as the reported bug: a membership/seen flag that is set too late relative to where it's consulted, letting the same identity be processed more than once.

### Impact Explanation
This handler is reachable by any unprivileged external client submitting an HTTP-trigger workflow request with a JWT to the gateway (`http_trigger_handler.go` calls `metadataHandler.Authorize`). A single valid, otherwise-single-use JWT can be replayed to trigger duplicate authorized workflow executions if sent concurrently, undermining the anti-replay guarantee the cache is meant to provide and enabling request impersonation/duplication beyond the issuer's intent (e.g., a token meant to authorize exactly one trigger invocation being used to fire more than one). This is a genuine authentication/session-control weakening reachable from an unprivileged caller, matching the accepted analog categories (request impersonation / authentication bypass via race).

### Likelihood Explanation
Exploitation requires only sending the same signed JWT concurrently (e.g., two near-simultaneous HTTP requests), which is trivial for any external client capable of reaching the gateway's HTTP trigger endpoint — no special privileges or node compromise needed. The race window is small but real given the check and the write are two separate lock acquisitions with authorization logic (JWT verification, workflow ID lookup, key comparison) executing in between them, widening the window in which duplicate requests can win the race.

### Recommendation
Make the replay check and the usage recording atomic: acquire a single write lock and, in one critical section, verify `cache[jti]` does not exist and only then insert it (or use a `sync.Map`/mutex-guarded "check-then-insert" using `LoadOrStore` semantics), returning "already used" if the entry already existed. This mirrors the report's fix pattern of setting the membership flag at the point of insertion rather than after downstream processing completes.

### Proof of Concept
1. Register a workflow and obtain a valid JWT (`jti = X`) authorized for `workflowID`.
2. Fire two (or more) `Authorize(workflowID, token, req)` calls concurrently (e.g., via `go func(){...}()` in a test, or two near-simultaneous HTTP trigger requests to the gateway) using the identical token.
3. Both goroutines call `h.jwtCache.isReplay(claims.ID)` before either calls `h.jwtCache.recordUsage(claims.ID)`; both observe `exists == false` and proceed to pass authorization, each returning a valid `*gateway.AuthorizedKey` — i.e., the single-use JWT is accepted twice, confirmable by asserting both calls to `Authorize` return `nil` error.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
