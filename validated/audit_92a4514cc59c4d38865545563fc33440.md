Confirmed: `get_builder_withdrawals` appends `Withdrawal(amount=withdrawal.amount)` using the **raw requested amount** from `state.builder_pending_withdrawals`, with no cap against `builder.balance`. This uncapped amount is what gets committed into `state.payload_expected_withdrawals` and therefore into the EL payload that mints/pays the withdrawal. `apply_withdrawals` then only *deducts* `min(withdrawal.amount, builder_balance)` from the builder's CL-side balance. This is the exact analog of the LoopFi bug: the "swap output" (here, the committed/paid `withdrawal.amount`) can exceed the "debt owed" (here, `builder.balance`), and the excess is silently capped away on the accounting side instead of being reconciled — except here the capped difference isn't "stuck" in a contract, it is Gwei that the EL mints and pays to `withdrawal.fee_recipient` while the CL only ever removes the smaller, capped amount from `state.builders[builder_index].balance`.

### Title
Uncapped `get_builder_withdrawals` amount vs. capped `apply_withdrawals` deduction mints Gwei to builder's `fee_recipient` beyond builder balance - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` commits the *full requested* `withdrawal.amount` from `state.builder_pending_withdrawals` into the withdrawals list that becomes `state.payload_expected_withdrawals` (and is honored 1:1 by the execution layer), but `apply_withdrawals` only decreases `state.builders[builder_index].balance` by `min(withdrawal.amount, builder_balance)`. When a pending builder withdrawal's requested amount exceeds the builder's balance at apply time, the EL pays/mints the full requested amount to `fee_recipient` while the CL only subtracts the (smaller) available balance, creating Gwei that is paid out but never subtracted from any account — a net supply inflation credited to the withdrawal's `fee_recipient`.

### Finding Description
`get_builder_withdrawals` [1](#0-0)  iterates `state.builder_pending_withdrawals` and appends a `Withdrawal` whose `amount` equals `withdrawal.amount` verbatim — it never checks it against `state.builders[builder_index].balance`. This withdrawal list is included unmodified in `get_expected_withdrawals` [2](#0-1) , then written into `state.payload_expected_withdrawals` via `update_payload_expected_withdrawals` [3](#0-2) , which is the field the execution layer is required to honor.

However, `apply_withdrawals` caps the actual balance deduction: [4](#0-3) 

```python
if is_builder_index(withdrawal.validator_index):
    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
    builder_balance = state.builders[builder_index].balance
    state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
```

This is confirmed by the test `test_builder_withdrawal_insufficient_balance`, which explicitly asserts that a pending withdrawal requesting 5 ETH against a builder with only 1 ETH balance produces a `withdrawal.amount` of 5 ETH in `payload_expected_withdrawals` while `builders[0].balance` is only reduced to 0 [5](#0-4) . This is the mirror image of the LoopFi bug: there, an over-large repayment was *silently capped* leaving funds stuck in a contract; here, an over-large *commitment* is *not* capped, and only the deduction is capped, leaving no corresponding reduction anywhere in `state` for the paid-out excess.

The specification even documents (as a deliberate tradeoff for the ordinary validator-sweep path) that `decrease_balance` saturating can create "a net supply inflation" because "the execution layer mints the full committed amount regardless of any CL-side saturation" [6](#0-5) . That note is written in the context of ordinary validator balances shrinking between commitment and application via `process_pending_consolidations`. It does not address (and the invariant is materially different for) the builder-pending-withdrawal path, where the excess is not merely a race but is *structurally guaranteed by the withdrawal-request path itself*: `get_builder_withdrawals` never bounds the requested amount to the builder's balance in the first place, so any operator who submits (or accumulates) `builder_pending_withdrawals` entries whose total exceeds the builder's balance can force minted Gwei to be paid to the specified `fee_recipient` in excess of what was ever staked/held by that builder.

### Impact Explanation
This breaks the "Gwei created ... or paid to a non-owner" invariant. The excess portion of the withdrawal (`withdrawal.amount - builder_balance`) is minted/paid by the execution layer to `withdrawal.fee_recipient` (an address independent of, and settable independently from, the builder's own `execution_address`) without any corresponding balance ever existing for it in `state.builders[]`. This is a direct, protocol-level source of unbacked ETH issuance and misdirected payment, not merely a documented rounding/race tradeoff.

### Likelihood Explanation
This is reachable purely through spec-conformant state evolution: repeated/accumulated entries in `state.builder_pending_withdrawals` requesting more than a builder's current `balance` (e.g., multiple withdrawal requests queued before earlier ones drain the balance, or balance reduced by other builder-balance-consuming operations between request and processing) will trigger the mismatch. The project's own test suite already demonstrates and asserts this exact scenario as "expected" behavior, indicating it is a systemic, deterministically reachable path rather than an edge case requiring adversarial coordination.

### Recommendation
Cap the committed `withdrawal.amount` in `get_builder_withdrawals` to `min(withdrawal.amount, state.builders[builder_index].balance)` (analogous to how `get_pending_partial_withdrawals` caps validator partial-withdrawal amounts to `balance - MIN_ACTIVATION_BALANCE` [7](#0-6) ) so the amount placed into `payload_expected_withdrawals` never exceeds the builder's actual available balance, keeping the CL commitment and CL deduction consistent.

### Proof of Concept
1. Builder `B` has `state.builders[B].balance = 1 ETH`.
2. `state.builder_pending_withdrawals` contains an entry `{builder_index: B, fee_recipient: X, amount: 5 ETH}`.
3. On `process_withdrawals`, `get_builder_withdrawals` appends `Withdrawal(validator_index=convert(B), address=X, amount=5 ETH)` unconditionally [8](#0-7) .
4. This becomes `state.payload_expected_withdrawals`, which the EL must honor by paying `X` 5 ETH.
5. `apply_withdrawals` executes `state.builders[B].balance -= min(5 ETH, 1 ETH)` → `balance` becomes `0` [9](#0-8) .
6. Net effect: 4 ETH is paid to `X` by the EL with no corresponding decrease anywhere in the CL state — 4 ETH of unbacked Gwei created and paid to `X`. This exact numeric scenario is validated (as expected behavior) by `test_builder_withdrawal_insufficient_balance` [10](#0-9) .

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
