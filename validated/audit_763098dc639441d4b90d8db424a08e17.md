## Title
Permissionless Front-Running of the Global `FeeState` Initialization Hijacks Protocol Fee Admin and Fee Wallet - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
The Berally report describes a class of bug where a program's initializer creates a dependent resource at a deterministic address, and that resource has a global uniqueness guard with no fallback — allowing an attacker to front-run creation of that resource and permanently block/hijack the legitimate initialization. Marginfi has a structurally identical pattern in its one-time global `FeeState` initializer: the PDA seed is fixed (no attacker- or caller-selectable component), the `init` constraint makes the call irreversible once it lands, and the instruction accepts **admin identity and fee-wallet values directly as unauthenticated arguments** with no check restricting who may call it.

### Finding Description
`initialize_fee_state` derives the `FeeState` account from a single fixed seed, `FEE_STATE_SEED`, with no per-instance or caller-chosen component: [1](#0-0) 

The handler writes the caller-supplied `admin_key` and `fee_wallet` parameters directly into the account with no verification that the caller is the protocol deployer, no hardcoded deployer pubkey check, and no `has_one`/`address` constraint gating `payer`: [2](#0-1) 

Because `fee_state` uses Anchor's `init` constraint against the deterministic, hardcoded seed `FEE_STATE_SEED`, the account can only be created once. Unlike bank-creation flows (`lending_pool_add_bank_with_seed`, `lending_pool_add_bank_kamino`, etc.) where the caller freely chooses a `bank_seed` and can simply pick a different seed if front-run, this global `FeeState` PDA has no seed parameter to vary — there is exactly one possible address for it, forever, for a given program ID. This mirrors the Berally bug precisely: the vulnerable resource's address is fully deterministic and not selectable by the legitimate initializer, and the guard against re-creation (`init`, which fails on an already-initialized account) is absolute.

The same pattern repeats for the V2 fee state: [3](#0-2) 

Any signer can watch the mempool/validator for program deployment or upgrade activity, compute the fixed `FeeState`/`FeeStateV2` PDA address off-chain (since the seed is a constant), and submit `initialize_fee_state`/`init_global_fee_state_v2` first with attacker-controlled `admin_key` and `fee_wallet`. Once landed:
- The legitimate protocol team's later call to `initialize_fee_state` permanently fails ("already in use"), exactly as in the Berally report ("subsequent attempts... will always fail").
- Worse than a pure DoS, the attacker's `admin_key` becomes `fee_state.global_fee_admin`, and their `fee_wallet` becomes `fee_state.global_fee_wallet` — these fields gate protocol-wide fee configuration and receive `bank_init_flat_sol_fee` payments from every subsequent bank creation across the whole program (referenced from `lending_pool_add_bank`'s flat-fee transfer to `global_fee_wallet`, validated via `has_one = global_fee_wallet` in bank-add account structs, e.g. `LendingPoolAddBank`/`LendingPoolAddBankWithSeed`). [4](#0-3) [5](#0-4) 

### Impact Explanation
This is more severe than the Berally analog: it is not just a durable initialization DoS forcing "redeployment," but an outright hijack of the protocol-wide fee-admin role and fee-collection wallet at the earliest possible moment (program deployment). Because the PDA has no variable/selectable seed, there is no way for the legitimate deployer to "just pick a different seed" the way bank admins can with `bank_seed` — the only remedy is a program upgrade to change the hardcoded seed constant, which is the direct analog of "redeployment" in the original report. Until such a fix ships, all flat SOL fees routed to `global_fee_wallet` accrue to the attacker, and any logic gated on `global_fee_admin` (e.g., `edit_global_fee`, `panic_pause`/`panic_unpause`, `config_group_fee`) is controlled by the attacker rather than the protocol team.

### Likelihood Explanation
Exploitation requires only observing the program's initial deployment (or any subsequent redeploy of the fee-state instruction after a fix/rotation) and racing a single permissionless transaction — no privileged keys, staked collateral, or special timing beyond normal transaction-ordering competition are needed. This is a realistic, low-cost, high-reward race for any MEV-aware searcher monitoring new/upgraded program deployments.

### Recommendation
- Gate `InitFeeState`/`InitFeeStateV2` behind a hardcoded, immutable deployer/upgrade-authority check (e.g., `#[account(constraint = payer.key() == HARDCODED_DEPLOYER_PUBKEY)]`), or require the call to be bundled atomically with program deployment/upgrade so it cannot be front-run.
- Alternatively, make the initial `admin_key`/`fee_wallet` values fixed constants baked into the program rather than caller-supplied arguments, removing the ability for any caller to set arbitrary values.
- Add an explicit test asserting that `initialize_fee_state`/`init_global_fee_state_v2` cannot be called by an arbitrary, non-deployer signer.

### Proof of Concept
1. Protocol team deploys/upgrades the marginfi program containing `init_global_fee_state`/`init_global_fee_state_v2`.
2. Before the team's initialization transaction lands, an attacker computes the fixed PDA `Pubkey::find_program_address([FEE_STATE_SEED.as_bytes()], &program_id)` (no seed guessing required — it's a constant).
3. Attacker submits `initialize_fee_state(admin_key = attacker_key, fee_wallet = attacker_wallet, ...)` (or `init_global_fee_state_v2`) with higher priority fee, landing first.
4. The `FeeState` account is created and owned by the marginfi program with `global_fee_admin = attacker_key` and `global_fee_wallet = attacker_wallet`.
5. The protocol team's legitimate `initialize_fee_state` call fails with "already in use" — initialization is permanently blocked without a program upgrade to change the seed.
6. All subsequent `lending_pool_add_bank`/`lending_pool_add_bank_with_seed` calls transfer their flat SOL fee to the attacker's `global_fee_wallet`, and any fee-admin-gated instruction is now controlled by the attacker.

// Runs once per program to init the global fee state.
use anchor_lang::prelude::*;
use marginfi_type_crate::{
    constants::FEE_STATE_SEED,
    types::{FeeState, WrappedI80F48},
};

#[allow(unused_variables)]
pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}
