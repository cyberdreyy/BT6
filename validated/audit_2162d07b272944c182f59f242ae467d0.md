### Title
Legacy gateway user-message path skips allowlist and rate-limit checks - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
Analogous to the bridge report's core defect — a security-relevant check (compliance/authorization state) that is required on one path but structurally omitted on another — the `capabilities` gateway handler's `HandleLegacyUserMessage` function accepts and processes unprivileged, internet-facing client requests (`web_api_trigger`) while explicitly skipping allowlist and rate-limit enforcement, per its own `TODO` marker.

### Finding Description
`HandleLegacyUserMessage` is the entry point for legacy user (client) messages arriving at the gateway before they are dispatched to the workflow DON. It validates payload decodability, a non-zero timestamp, and message staleness, but before checking the method and forwarding the request to every DON member, it contains an explicit gap: [1](#0-0) 

The comment `// TODO: apply allowlist and rate-limiting here` sits directly before the method-type check and before the request is forwarded via `don.SendToNode` to every DON member: [2](#0-1) 

This mirrors the bridge bug class exactly: a security-relevant gate (allowlist/authorization state, analogous to compliance metadata) that other paths in the same codebase enforce (e.g. the `capabilities/v2` HTTP trigger handler documents "Authentication: Verifies JWT token ... checks authorized keys" and "Rate Limiting: Enforces per-workflow-owner rate limits" — see `core/services/gateway/handlers/capabilities/v2/README.md`) is instead conditionally/structurally absent on this legacy path, letting stale/no authorization state be trusted. [3](#0-2) 

By contrast, the sibling `HandleJSONRPCUserMessage` on this same handler type is unimplemented/rejected outright: [4](#0-3) 

confirming that `HandleLegacyUserMessage` is the actual reachable path exercised for `web_api_trigger` client requests.

### Impact Explanation
Any unprivileged external client able to reach the gateway's legacy message endpoint can submit `web_api_trigger` requests that get broadcast to every member of the DON without going through allowlist checks or per-node/per-caller rate limiting. This enables unauthorized workflow-trigger requests and resource-exhaustion/DoS against DON members, since the gateway is the internet-facing boundary responsible for keeping unauthenticated/unauthorized traffic away from the DON.

### Likelihood Explanation
This is not a hypothetical timing race — it is a hardcoded, unconditional omission on the only reachable message path for this handler (`HandleJSONRPCUserMessage` is a stub that errors out). Any request that passes payload decode, non-zero timestamp, and staleness checks reaches the DON fan-out unconditionally.

### Recommendation
Implement the allowlist and rate-limiting checks referenced by the `TODO` in `HandleLegacyUserMessage` before dispatching to DON members — mirroring the JWT/authorized-key and per-workflow-owner rate limiting enforced in the `capabilities/v2` HTTP trigger handler. At minimum, apply a conservative default-deny posture for any caller not present in an allowlist, rather than forwarding to the full DON membership.

### Proof of Concept
1. Send a well-formed `web_api_trigger` legacy message (valid JSON payload, non-zero `Timestamp` within `MaxAllowedMessageAgeSec`) to the gateway's legacy handler for a given DON, from a client with no prior registration/allowlisting.
2. Observe that `HandleLegacyUserMessage` proceeds past all checks (decode, timestamp, staleness) straight to `don.SendToNode` for every DON member, since no allowlist or rate-limit call exists in the code path.
3. Repeat rapidly from the same unauthenticated source to confirm the absence of rate limiting on this path (contrast with `handleWebAPIOutgoingMessage`, which does call `h.nodeRateLimiter.Allow(nodeAddr)` for node-originated traffic, but that limiter is not applied to inbound legacy user messages).

## 4. HTTP Trigger Message Handling

### 4.1 Process Flow

1. **Request Validation**: Validates JSON-RPC format, method, and parameters
2. **Workflow Resolution**: Resolves workflow ID from selector (ID, owner, name, tag)
3. **Authentication**: Verifies JWT token (ECDSA signature) and checks authorized keys
4. **Rate Limiting**: Enforces per-workflow-owner rate limits
5. **Node Distribution**: Sends request to all DON members with retry logic
6. **Response Aggregation**: Collects and aggregates responses from nodes (2f + 1 identical responses required, where f is max faulty nodes)
7. **User Response**: Returns aggregated result to the original requester
