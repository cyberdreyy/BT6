### Title
Permissionless `init_global_fee_state` allows front-running to hijack `global_fee_admin`, enabling `config_group_fee` protocol-wide fee-flag manipulation - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
`init_global_fee_state` has no authorization check beyond requiring an arbitrary `payer: Signer`, and it accepts a caller-supplied `admin_key: Pubkey` that is written directly into `FeeState.global_fee_admin` with no validation. Since the `fee_state` PDA is created via Anchor's `init` constraint (so it can only be initialized once, by whoever calls it first), any unprivileged user can race the legitimate deployer, call this instruction with `admin_key = attacker_pubkey`, and become the sole authority gating `config_group_fee` and `edit_fee_state` for the entire program.

### Finding Description
`InitFeeState` accounts require only: [1](#0-0) 
a mutable `payer: Signer`, the `fee_state` PDA (seeded solely by `FEE_STATE_SEED`, created with `init`), and `system_program`. There is no constraint tying `payer` to a hardcoded program authority, the upgrade authority, or any other privileged key.

`initialize_fee_state` then unconditionally sets: [2](#0-1) 
`fee_state.global_fee_admin = admin_key;` where `admin_key` is a fully attacker-controlled instruction argument.

Because the PDA uses Anchor's `init` (not `init_if_needed`), this instruction can succeed exactly once per program deployment — whichever transaction lands first "wins" and permanently sets `global_fee_admin`. Since the instruction is public and permissionless, an unprivileged attacker monitoring the network for a fresh program deployment (or a deployment where `init_global_fee_state` is not submitted atomically with deployment) can submit their own `init_global_fee_state(admin_key = attacker_key, ...)` transaction first.

Once this succeeds, every downstream authorization check that relies on `has_one = global_fee_admin` — including `ConfigGroupFee`: [3](#0-2) 
and `EditFeeState`: [4](#0-3) 
now authenticates against the attacker's key. The attacker can freely call `config_group_fee` for any group to toggle `enable_program_fee`, and can call `edit_fee_state` to rewrite all fee parameters, the fee wallet, and `pause_delegate_admin` for the whole protocol.

### Impact Explanation
If exploited, the attacker gains permanent, protocol-wide control of the `FeeState` account — the single global authority object shared by every marginfi group. This lets them arbitrarily enable/disable `enable_program_fee` on any group via `config_group_fee`, and rewrite fee wallet/fee rate/pause-delegate configuration via `edit_fee_state`. This matches the "protocol-wide fee-flag manipulation across all groups" scoped impact described in the question, consistent with a Medium-severity authorization issue since it requires winning a deployment-time race rather than a standing, always-exploitable authorization bypass.

### Likelihood Explanation
Exploitability is entirely dependent on the deployment operational practice: if `init_global_fee_state` is called in the same atomic transaction/bundle as program deployment (or before the program is made publicly invokable), the race window does not exist. If it is called as a separate, later transaction after deployment (as suggested by the "Runs once per program" comment implying a manual/administrative follow-up step), any unprivileged party watching the chain can front-run it. The instruction itself imposes zero privilege requirements on `payer`, so feasibility solely hinges on transaction ordering/timing, which is realistic on Solana given public mempool-like propagation and leader scheduling.

### Recommendation
Add an explicit authorization check to `InitFeeState`/`InitFeeStateV2` — e.g., require `payer` to match a hardcoded program-controlled pubkey, the program's upgrade authority (verified via `bpf_loader_upgradeable` state), or gate the call so it can only be included in the same transaction as program initialization/deployment. Alternatively, avoid taking `admin_key` as an unconstrained instruction argument and instead default `global_fee_admin` to the deploying/payer key with a subsequent explicit `edit_fee_state` transfer performed by a known, pre-verified authority.

### Proof of Concept
Rust integration test plan (bankrun/anchor test harness):
1. Do not call `init_global_fee_state` in test setup.
2. As an "attacker" `Keypair` with no special privileges, construct and send `InitGlobalFeeState { admin: attacker.pubkey(), .. }` with `payer = attacker`, `fee_state = FEE_STATE_SEED PDA`, `system_program`. Assert the transaction succeeds.
3. Load `FeeState` and assert `fee_state.global_fee_admin == attacker.pubkey()`.
4. Initialize a `MarginfiGroup` normally (unrelated to fee-state authority).
5. Send `ConfigGroupFee { marginfi_group, global_fee_admin: attacker.pubkey(), fee_state }` signed only by `attacker`, with `enable_program_fee = true`. Assert the transaction succeeds and `marginfi_group.group_flags` reflects the enabled fee flag — demonstrating an unprivileged actor now controls protocol-wide fee flags via a purely permissionless init front-run.
