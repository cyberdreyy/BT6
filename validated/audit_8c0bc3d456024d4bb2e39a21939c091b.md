### Title
Unbounded overwrite of `savedCallbacks[MessageId]` on concurrent duplicate (sender, MessageId) submissions causes cross-caller callback hijack/loss - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`Message.Validate()` in `core/services/gateway/api/message.go` performs only structural/signature checks and never enforces MessageId uniqueness [3](#0-2) . In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` stores the per-request callback in `h.savedCallbacks[msg.Body.MessageId]` with a plain map write that never checks for a pre-existing entry, so a second concurrent request with the same MessageId silently overwrites the first request's callback pointer [4](#0-3) . Unlike the generic `requestCache.NewRequest` (used by other handlers such as `confidentialrelay`/`vault`), which explicitly checks `_, ok := c.cache[key]` and returns `"request already exists"` on collision [5](#0-4) , this capabilities handler path performs no deduplication at all — it doesn't call `requestCache.NewRequest` in this flow, it uses its own unguarded map.

### Finding Description
- Attacker input: two HTTP/gateway requests signed by the same key (attacker's own key), each with an identical `Body.MessageId` value, sent concurrently.
- `Validate()` only checks signature format/length, MessageId length/null-byte-suffix, method/DonId/receiver formatting, and extracts the signer — it never checks whether that MessageId is already in-flight [6](#0-5) .
- Both messages pass validation and reach `HandleLegacyUserMessage` concurrently (goroutine-per-request, per the `Handler` interface contract) [7](#0-6) .
- Both goroutines acquire `h.mu`, each writes to the same map key `msg.Body.MessageId` in sequence: `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` [2](#0-1) . Whichever goroutine writes second replaces the first entry entirely — no error, no rejection.
- When node responses arrive, `handleWebAPITriggerMessage` looks up and deletes `savedCallbacks[msg.Body.MessageId]`, returning the response only to whatever callback is currently stored at that key [8](#0-7) . The first requester's callback is silently dropped, and it never receives a `SendResponse` call for its request — it will only be resolved later by the connection-manager-level HTTP timeout, not by this handler.
- This directly violates the intended one-request-to-one-callback invariant. Because `requestCache.NewRequest` (used elsewhere) does implement a collision check, this asymmetry indicates a genuine gap specific to `capabilities/handler.go`'s legacy path rather than intentional behavior.

### Impact Explanation
This is a cross-user response confusion bug: an unprivileged attacker sending two concurrent requests with the same `message_id` (trivial for the attacker to control since it is their own request, and the field is client-supplied) can cause a benign concurrent requester who happens to pick the same MessageId to have their callback overwritten, or — more importantly — an attacker can deliberately race their own second request against a legitimate victim's request only if MessageIds collide, which is unlikely for two different senders since it's keyed only by `MessageId` (not by sender+MessageId) in this handler, unlike `requestCache`'s `globalId{sender, id}`. However, since key is purely `msg.Body.MessageId` (not sender-scoped) here, **a malicious sender does not even need to match victim's sender** — colliding on any other pending request's raw MessageId (e.g., through predictable ID generation by clients, replay, or brute force of short-lived IDs) can hijack that unrelated response. This matches a "cross-user response confusion" impact class, though it requires either MessageId collision by chance/predictability across different senders, or the same sender racing itself (self-DoS, lower severity).

### Likelihood Explanation
Preconditions: attacker needs only a valid signing keypair (self-issued, no special role) and the ability to fire two concurrent HTTP requests with an identical `message_id` — both trivially satisfied by any unauthenticated/external caller of the gateway API. This is a race condition, reproducible reliably in a controlled test (concurrent goroutines), though timing-dependent in production due to network jitter between the two requests reaching the same handler instance.

### Recommendation
Add an existence check before inserting into `savedCallbacks`, e.g. under `h.mu`, reject or error out (returning an error to the caller) if `msg.Body.MessageId` (optionally scoped by `msg.Body.Sender`) already exists in the map, mirroring `requestCache.NewRequest`'s `"request already exists"` behavior. Consider migrating this handler to reuse `common.RequestCache` for consistency instead of maintaining an unguarded, hand-rolled map.

### Proof of Concept

1. Construct a `handler` with a mock `DON.SendToNode` that's a no-op, and two mock `handlers.Callback` implementations (`cb1`, `cb2`) that record whether/how many times `SendResponse` was invoked.
2. Build two `api.Message` values with identical `Body.MessageId` (`"dup"`), identical `Body.Sender` (or different senders to demonstrate the wider bug), valid signatures, method `MethodWebAPITrigger`.
3. Launch two goroutines calling `h.HandleLegacyUserMessage(ctx, msg1, cb1)` and `h.HandleLegacyUserMessage(ctx, msg2, cb2)` concurrently, synchronized via a barrier/WaitGroup to maximize race probability.
4. After both complete, inspect `h.savedCallbacks["dup"]` — assert it only contains one callback (expected: whichever won), and that no error was surfaced to the loser (currently: no error, silently lost).
5. Assert (currently failing) that either both are rejected except one, or an explicit error is returned to the second/losing caller instead of a silent overwrite.
6. Simulate a subsequent node response for `"dup"` via `HandleNodeMessage` with `MethodWebAPITrigger`, and assert only the winning callback's `SendResponse` was invoked — demonstrating the loser callback is permanently orphaned with no error and no response, confirming the invariant violation.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
