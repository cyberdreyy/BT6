### Title
Open APR0 withdraw receipt permanently reverts `stopEpoch` after any APR change, freezing all vault funds — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The hi846 bug is a failure-path resource leak: `ctrl_hdlr` is allocated but never freed when init fails. The credit-vault analog is the APR0 principal bucket (`apr0TotalPrincipal` / `apr0Users`): a resource allocated at `requestWithdraw` time that is only released inside `prepareStopEpochWithApr0` — but that same function reverts before releasing it if `unscaledApr` was changed to non-zero. Once an open APR0 receipt coexists with a non-zero APR, `stopEpoch` can never execute, freezing every lender's funds in the vault.

### Finding Description
`IdleCreditVault.requestWithdraw` routes requests into the APR0 path when `unscaledApr == 0`, recording per-user principal in `apr0Users[_user]` and the aggregate `apr0TotalPrincipal` (IdleCreditVault.sol:285-286, `_requestWithdrawApr0`). The bucket is closed only at `prepareStopEpochWithApr0`, called by the CDO during `stopEpoch`/`stopEpochWithDuration` (IdleCreditVault.sol:490-541).

The cleanup ordering is inverted — the guard fires before the resource is released:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) { return ...; }          // fast path
if (unscaledApr != 0) { revert NotAllowed(); } // line 506-508
...
apr0TotalPrincipal = 0;                        // line 540, unreachable if APR != 0
```

`setApr`/`setAprsWithBuffer` (IdleCreditVault.sol:217-235) enforce only the `maxApr` bound and CDO/manager access — there is no check that `apr0TotalPrincipal == 0` before allowing `unscaledApr` to leave 0. So a single open APR0 receipt plus a routine APR change makes `apr0TotalPrincipal != 0 && unscaledApr != 0` a state from which `prepareStopEpochWithApr0` always reverts. Since `stopEpoch` cannot settle interest, repay pending receipts, or bump `epochNumber` without it, the epoch can never end: `claimWithdrawRequest` reverts (`epochNumber <= lastWithdrawRequest`), queued claims can't be processed, and all lender principal is locked indefinitely.

The only escape is the manager setting `unscaledApr` back to 0 — which itself may be impossible or unsafe if the pool was legitimately repriced, and in any case the freeze persists for the entire period and blocks borrower repayment deadlines, cascading into default-adjacent paths (`_handleBorrowerDefault`) that the protocol cannot reach cleanly either.

Sequence:
1. Buffer/running phase, `unscaledApr == 0` (APR0 mode). Attacker (any KYC-passing lender) calls `IdleCDOEpochVariant.requestWithdraw`, creating `apr0Users[attacker].principal > 0` and `apr0TotalPrincipal > 0`. Cost: one tranche deposit.
2. Honest manager (or CDO at next `startEpoch` via `setAprsWithBuffer`) sets a normal non-zero APR — a routine privileged call, per the threat model.
3. Epoch end: `stopEpoch` → `prepareStopEpochWithApr0` → `revert NotAllowed()` (line 507). Every subsequent `stopEpoch`/`stopEpochWithDuration` attempt reverts identically.

### Impact Explanation
Temporary freezing of all vault funds: while `apr0TotalPrincipal != 0 && unscaledApr != 0`, no epoch can be stopped, so no withdraw receipt can mature, no interest is settled, the borrower cannot repay, and emergency/default flows that depend on epoch progression are blocked. The locked amount equals total vault NAV plus all pending withdraw receipts — effectively the entire TVL for the duration of the freeze. This mirrors the kernel leak (an acquired resource never released on the failure path) in financial form: the accounting allocation is held hostage by its own cleanup precondition.

### Likelihood Explanation
Requires the conjunction of (a) an APR=0 epoch with at least one withdraw request and (b) an APR change to non-zero before that epoch is stopped. Both are ordinary operations: borrowers regularly renegotiate APR, and managers set APR each epoch via `setAprsWithBuffer`. An unprivileged lender can deliberately create condition (a) — opening a dust-sized APR0 withdraw request costs only the principal's opportunity cost and is fully recoverable later — then wait for any honest repricing to brick the epoch machine. Likelihood is therefore meaningful whenever pools cycle out of APR0 mode, which is the normal way the APR0 feature is used (a promotional/zero-interest epoch followed by repriced epochs).

### Recommendation
Move the APR-consistency check off the blocking path. Either (1) revert in `setApr`/`setAprsWithBuffer` when `apr0TotalPrincipal != 0` so the inconsistent state is unreachable, or (2) make `prepareStopEpochWithApr0` settle/close the APR0 bucket with zero interest when `unscaledApr != 0` instead of reverting, releasing `apr0TotalPrincipal` unconditionally (mirroring the kernel fix: free `ctrl_hdlr` on every exit path). Option 2 is safer because it cannot be bypassed via direct `setApr` calls from the manager after an upgrade.

### Proof of Concept
```solidity
// Fork: mainnet, existing harness style (test/foundry/IdleCreditVault.t.sol)
function testApr0ReceiptBlocksStopEpochAfterAprChange() external {
    // 1. APR0 mode: manager sets unscaled APR to 0
    vm.prank(manager);
    strategy.setAprsWithBuffer(0, cdoEpoch.epochDuration(), cdoEpoch.bufferPeriod());

    // 2. Attacker (KYC'd lender) deposits and requests a withdraw -> APR0 bucket allocated
    uint256 shares = _depositWithUser(attacker, 1e6); // dust deposit
    vm.prank(manager);
    cdoEpoch.startEpoch();                       // epoch running
    _stopCurrentEpochKeepApr0();                 // epoch ends, buffer opens
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(shares, address(AAtranche));
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // 3. Honest repricing: next epoch is started with a real APR
    vm.prank(manager);
    cdoEpoch.startEpoch();                       // CDO calls setAprsWithBuffer(apr>0)
    assertGt(strategy.unscaledApr(), 0);

    // 4. Epoch end: stopEpoch permanently reverts -> funds frozen
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);
    // every retry reverts; apr0TotalPrincipal is never cleared
}
```

Caveat: I could not fully verify the exact `stopEpoch` → `prepareStopEpochWithApr0` call chain signature and the `requestWithdraw` epoch-phase gating in `IdleCDOEpochVariant` within the search budget; the PoC assumes `stopEpoch` unconditionally calls `prepareStopEpochWithApr0`, which the `_onlyIdleCDO` guard on that function indicates. The revert condition itself (`apr0TotalPrincipal != 0 && unscaledApr != 0` → `NotAllowed`, IdleCreditVault.sol:506-508) and the absence of an `apr0TotalPrincipal` check in `setApr` (IdleCreditVault.sol:225-235) are confirmed directly in the code.
