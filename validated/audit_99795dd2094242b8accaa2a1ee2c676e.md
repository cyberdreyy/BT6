## Finding

### Title
Signer weight can be double-counted into both the approval and rejection tallies when a signer equivocates - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The mined-block signature coordinator's `StackerDBListener` tracks two separate weight tallies for a proposed block — `total_weight_approved` and `total_weight_rejected` — that are meant to be mutually exclusive per signer (a signer's weight should count toward at most one). The guard used to prevent double-counting on the `Accepted` path (`gathered_signatures.contains_key(&slot_id)`) is independent of the guard used on the `Rejected` path (`block.responded_signers.insert(&slot_id)`), and both paths write into the *same* shared `responded_signers` set only as a side effect. If a signer first rejects and later accepts the same block (or the reverse order in some cases), its weight is added to one tally by one guard while the other guard has already been satisfied by the other message, letting a single signer's weight land in **both** tallies simultaneously.

### Finding Description
`BlockStatus` tracks, per proposed block, `responded_signers`, `gathered_signatures`, `total_weight_approved`, and `total_weight_rejected`: [1](#0-0) 

In the `Accepted` branch, the weight increment is guarded solely by whether `slot_id` is already a key in `gathered_signatures`: [2](#0-1) 

In the `Rejected` branch, the weight increment is guarded by inserting into the shared `responded_signers` set: [3](#0-2) 

Trace the sequence for one signer, slot `S`, sending a `Rejected` message followed later by an `Accepted` message for the *same* block:

1. `Rejected` arrives first: `block.responded_signers.insert(S)` returns `true` (first time seen) → `total_weight_rejected += weight(S)`.
2. `Accepted` arrives later: the accept-path guard checks `!block.gathered_signatures.contains_key(&S)`, which is still `true` because nothing has touched `gathered_signatures` yet → `total_weight_approved += weight(S)` is executed. `block.responded_signers.insert(S)` is called again at line 465 but is a harmless no-op since `S` is already present.

The result is that `weight(S)` is now counted in *both* `total_weight_rejected` and `total_weight_approved` for the same block, even though a single signer's weight should only ever back one side of the equality. This directly breaks the "aggregated-weight vs verified-accepts equality" invariant the two tallies are supposed to enforce: `total_weight_approved` should only reflect weight from signers who currently endorse the block, and `total_weight_rejected` should only reflect weight from signers currently opposing it — not weight from a signer who has done both.

This is the same bug class as the external report: a paired pair of state values (there, `lCollateral`/`bCollateral`; here, `total_weight_approved`/`total_weight_rejected`) is meant to move together/consistently on a state transition, but only one side's guard accounts for the other side's prior state, so a signer's weight is "spent" once but recorded on both ledgers, over-allocating aggregate weight.

The consuming code in `run_signing_coordinator`/wait-loop treats these totals as mutually exclusive partitions of `total_weight` to decide the block's fate: [4](#0-3) 

Because the rejection branch is checked first (an `if`/`else if` chain), an equivocating signer's double-counted weight will most often just help push the block toward `SignersRejected` rather than a false accept in the same evaluation pass — but the underlying accounting corruption is real and not bounded to that one favorable ordering: any signer set where enough signers first reject then flip to accept (e.g., re-validating after a delayed proposal update) inflates `total_weight_approved` with weight that logically should have been excluded once that signer's earlier reject was recorded, letting the 70% threshold in `total_weight_approved >= self.weight_threshold` be satisfied with less than 70% of the true, currently-held distinct-signer weight.

### Impact Explanation
This falls under "aggregated-weight vs verified-accepts equality" broken and "a rejection recounted as an accept" — the two named Critical-tier impacts in the rules. A single signer (no majority required) can, by sending a rejection and later an acceptance for the same proposed block, have their weight simultaneously counted on both sides of the tally, corrupting the aggregate weight accounting that the coordinator uses to decide whether to push a block to the node or drop it as rejected.

### Likelihood Explanation
No majority coordination, no key compromise, and no special node access is needed — the trigger is simply for one signer (or gossip relaying one signer's two legitimate, independently-valid messages) to send a `Rejected` `BlockResponse` and later an `Accepted` `BlockResponse` for the same `signer_signature_hash`, which is a completely ordinary re-evaluation pattern already exercised elsewhere in the signer's own re-evaluation logic (`should_reevaluate_block`, `handle_block_pre_commit`, etc.), all reachable by a single miner-adjacent participant driving message order/timing.

### Recommendation
Guard both branches with the same authoritative signer-state check instead of two independently-tracked structures. For example, before adding weight in either branch, check and record the signer's *current* vote (accept/reject) in a single map keyed by `slot_id`; if the signer had previously voted the other way, subtract their weight from the old bucket before adding it to the new one (or reject the flip outright, since block votes should not be revocable to a different signature/vote payload once cast for a given sighash).

### Proof of Concept
1. Coordinator opens a `BlockStatus` for sighash `H` with `weight_threshold = T` and `total_weight = W`.
2. Signer slot `S` (weight `w`) broadcasts `BlockResponse::Rejected` for `H` → `responded_signers = {S}`, `total_weight_rejected = w`.
3. Signer slot `S` later broadcasts `BlockResponse::Accepted` for `H` with a valid signature over `H` → passes signature verification, `gathered_signatures` does not yet contain `S`, so `total_weight_approved = w` is also recorded (while `total_weight_rejected` still equals `w` from step 2, never decremented).
4. Now `total_weight_approved + total_weight_rejected = 2w`, i.e., signer `S`'s weight is present in both tallies for the same block, violating the intended mutual exclusivity, corrupting subsequent threshold comparisons in `signer_coordinator.rs`.
