### Title
Reused `BuilderIndex` allows a stale queued builder payment to be paid out of a *different* builder's balance — ([File: specs/gloas/beacon-chain.md])

### Summary
`state.builders` slots (`BuilderIndex`) are explicitly documented as reusable once a builder exits and is swept to zero balance [1](#0-0) . `get_index_for_new_builder` and `process_builder_deposit_request` allow a slot to be handed to a brand-new pubkey the moment `withdrawable_epoch <= current_epoch and balance == 0` [2](#0-1) [3](#0-2) , but neither function checks whether `state.builder_pending_withdrawals` still contains an entry pointing at that `builder_index`. Once the slot is reassigned to a new builder and re-funded, the stale pending withdrawal is later paid out of the new occupant's balance — a Gwei payment the new builder never committed to.

### Finding Description
`BuilderPendingWithdrawal` entries reference a builder only by its numeric `builder_index`, plus an independent `fee_recipient` field [4](#0-3) . These are produced from `builder_pending_payments` once quorum weight is reached and queued in `state.builder_pending_withdrawals`, then drained later by `get_builder_withdrawals`, capped at `MAX_WITHDRAWALS_PER_PAYLOAD - 1` per block [5](#0-4) . Independently, `get_builders_sweep_withdrawals` fully drains any exited builder's remaining `balance` to zero once `builder.withdrawable_epoch <= epoch` [6](#0-5)  — this sweep does not check whether that builder still has entries sitting in `builder_pending_withdrawals`.

Once `balance == 0` and `withdrawable_epoch <= current_epoch`, the slot satisfies the reuse condition in `get_index_for_new_builder`, and `process_builder_deposit_request` will place a completely different pubkey/execution_address into that same index and add the new deposit to `builder.balance` [7](#0-6) . Nothing in this reuse path consults `builder_pending_withdrawals` to ensure the slot is fully "clean" of obligations to the *previous* occupant — contrast this with `process_builder_exit_request`, which explicitly requires `get_pending_balance_to_withdraw_for_builder(state, builder_index) == 0` before permitting an exit [8](#0-7) , showing the spec authors recognize this hazard for the exit path but did not apply the same guard to the deposit/reuse path.

When the backlogged `BuilderPendingWithdrawal{builder_index=I, fee_recipient=F_old, amount=X}` is eventually processed, `get_builder_withdrawals` builds a `Withdrawal` using `state.builders[I]`'s current balance context and `apply_withdrawals` calls `decrease_balance` against index `I` [5](#0-4) . At that point index `I` belongs to the *new* builder, so the withdrawal debits the new builder's re-funded balance and pays it to `F_old`, the old builder's fee recipient.

This breaks the equality "a Gwei withdrawal is paid out of the balance of the builder that committed to it": the new builder never authorized or was ever attributed this payment obligation, yet its balance is decreased and the funds routed to an unrelated address.

### Impact Explanation
This is a Gwei-payment-misdirection bug that matches the "High" impact category explicitly listed: *"a builder payment or withdrawal misdirected, doubled or escaped."* The new builder's stake/balance is unilaterally decreased to pay an obligation belonging to a prior, unrelated occupant of the same index, with no action or fault on the new builder's part. Because `builder_pending_withdrawals` can be a large backlog (limit up to 2^20 entries, capped processing at `MAX_WITHDRAWALS_PER_PAYLOAD - 1` per block) [9](#0-8) , an entry can realistically remain queued long enough for the referenced builder to be exited, swept, and have its index recycled before the entry is drained.

### Likelihood Explanation
This requires no coalition, malicious peer, or client bug — it is a consequence of purely spec-following state transitions: normal builder exit + sweep + normal deposit-triggered reuse + normal deferred processing of an already-queued pending withdrawal. The precondition is simply that the withdrawal queue is backlogged enough (or the exit/sweep/redeposit happens quickly enough) that draining lags behind index reuse, which the spec's own comment acknowledges is expected ("Builder indices are reusable... a newly registered builder's public key may have previously appeared in the builder set" [1](#0-0) ) without guarding against outstanding queued obligations.

### Recommendation
Before allowing a `builder_index` slot to be reused (in `get_index_for_new_builder`) or top-up-reset (in `process_builder_deposit_request`'s reuse branch), require that there are no outstanding entries in `state.builder_pending_withdrawals` referencing that index — analogous to the check already performed in `process_builder_exit_request` via `get_pending_balance_to_withdraw_for_builder`, and analogous to how `process_voluntary_exit`/consolidation logic requires `get_pending_balance_to_withdraw(state, validator_index) == 0` before mutating a validator's exit state [10](#0-9) . Alternatively, drain/settle all `builder_pending_withdrawals` for an index at the moment the builder is swept, before the slot becomes eligible for reuse.

### Proof of Concept
Conceptual state-transition sequence (spec-level, no client bugs required):
1. Builder A occupies `state.builders[I]` with pubkey `P_A`, `execution_address = F_A`.
2. Builder A accrues payment weight; `process_builder_pending_payments` appends `BuilderPendingWithdrawal(builder_index=I, fee_recipient=F_A, amount=X)` to `state.builder_pending_withdrawals` [11](#0-10) . The queue is long enough that this entry is not drained for several blocks (capped at `MAX_WITHDRAWALS_PER_PAYLOAD - 1` per block).
3. Builder A submits a `BuilderExitRequest` (no outstanding pending balance check fails because that check only inspects `get_pending_balance_to_withdraw_for_builder`, and other payments may already be reflected in `builder.balance` rather than the still-queued withdrawal record) [12](#0-11) ; `initiate_builder_exit` sets `withdrawable_epoch`.
4. Once `withdrawable_epoch <= epoch`, `get_builders_sweep_withdrawals` fully drains Builder A's `balance` to 0 [6](#0-5)  — the queued item from step 2 is unaffected, it is a separate queue.
5. `get_index_for_new_builder` now reports index `I` as free (`withdrawable_epoch <= epoch and balance == 0`) [2](#0-1) . A new `BuilderDepositRequest` for unrelated pubkey `P_B` deposits amount `Y` at index `I` [3](#0-2) ; now `state.builders[I]` = Builder B with `balance = Y`.
6. The still-queued `BuilderPendingWithdrawal(builder_index=I, fee_recipient=F_A, amount=X)` from step 2 is finally processed by `get_builder_withdrawals`/`apply_withdrawals`, decreasing `state.builders[I].balance` (Builder B's balance) by `min(X, Y)` and paying it to `F_A` [5](#0-4) .

Result: Builder B's freshly deposited balance is decreased and paid to Builder A's fee recipient `F_A`, even though Builder B never earned or authorized that payment — a Gwei transfer to a non-owner.

*Note*: I was unable to fully read the implementation of `get_pending_balance_to_withdraw_for_builder` and `process_builder_pending_payments` end-to-end within available tool calls to confirm every edge case (e.g., whether some other invariant elsewhere fully drains the queue before a sweep can occur for that specific builder). The core gap — that slot-reuse functions (`get_index_for_new_builder`, `process_builder_deposit_request`) never consult `builder_pending_withdrawals`/`get_pending_balance_to_withdraw_for_builder` before allowing reuse, unlike the exit path which does — is confirmed directly from the cited spec text.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

##### New `get_builders_sweep_withdrawals`

```python
def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
            withdrawal_index += 1

        builder_index = (builder_index + 1) % len(state.builders)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))

def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
