### Title
Multisig requests can execute below the configured confirmation threshold because stale confirmations from removed members are not purged - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` only removes pending *requests authored by* the deleted member; it never scrubs that member's *confirmations* recorded on other members' still-pending requests. The `confirmations: LookupMap<RequestId, HashSet<String>>` set therefore keeps counting a "confirmation" from an account/key that is no longer a live multisig member, letting `confirm()` reach `num_confirmations` with fewer live-member approvals than the contract's own threshold requires.

### Finding Description
`confirm()` treats reaching `confirmations.len() + 1 >= self.num_confirmations` as sufficient to execute a request, counting whatever strings are already in the `confirmations` set for that `request_id`: [1](#0-0) 

Membership changes go through `delete_member`, which is only invoked from the `DeleteMember` action inside `execute_request`: [2](#0-1) 

`delete_member` cleans up only the requests where `r.member == member` (i.e., requests *created by* the removed member) and removes them along with their confirmations. It never inspects the `confirmations` sets of *other* pending requests to strip out an entry equal to the removed member's `to_string()`: [3](#0-2) 

The correct binding the contract is supposed to maintain is:
`confirmations_recorded_for(request) == confirmations_from_live_members_for(request)`

This is broken the moment a member who already confirmed pending request `R1` (authored by someone else) is removed via a separate, fully-confirmed `DeleteMember` request: `R1`'s confirmation set still contains the departed member's identifier, but that identifier no longer corresponds to a `self.members` entry. `confirm()`'s threshold check (`confirmations.len() as u32 + 1 >= self.num_confirmations`) has no re-validation that every entry in `confirmations` is still a current member, so the stale entry is still counted.

This is structurally the same bug class as the referenced PoolTogether Pods report: an aggregate/accounting value (there: total supply; here: the confirmation count backing the threshold) is updated on one path (deposit/confirm) but not reconciled when the underlying individual entity is later invalidated (withdraw/removed member), so the aggregate value used later for a critical decision (minting new pod tokens / authorizing a multisig execution) no longer reflects reality.

### Impact Explanation
Once a member is removed, any request that member had already confirmed needs only `num_confirmations - 1` *live* confirmations to execute, because the ghost confirmation still counts toward the threshold. This lets a `Transfer`, `AddKey`, `FunctionCall`, or further membership/threshold change execute with fewer live-member approvals than `num_confirmations` mandates — a direct violation of the "multisig request executed below threshold" Critical-impact category, since it can move NEAR/wNEAR or grant keys with insufficient authorization.

### Likelihood Explanation
No foundation, owner, redeploy, or malicious validator is required. It only needs the ordinary multisig workflow: one member confirms an existing request, and separately the required quorum removes that member for any legitimate reason (key rotation, compromise response, departure). This is a normal, expected sequence of multisig operations, not an edge case requiring social engineering, making the divergence easy to trigger unintentionally and straightforward to exploit by a member who anticipates being removed.

### Recommendation
When executing `DeleteMember`, iterate over all `self.requests` (not just those authored by the removed member) and remove the deleted member's entry from each request's `confirmations` set (mirroring how `Pod.sol` was fixed by unifying the scheduled-supply and scheduled-balance updates into a single code path). Additionally, `confirm()` should validate that every string in a request's stored `confirmations` set still corresponds to a current `self.members` entry before counting it toward the threshold, so membership changes and confirmation counts can never diverge.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. `D` calls `add_request` to create `R1` (e.g., `Transfer{amount}` to an attacker-controlled `receiver_id`) — `confirmations[R1] = {}` [4](#0-3) .
3. `A` calls `confirm(R1)` → `confirmations[R1] = {A}` (len 1 < 3, not executed) [1](#0-0) .
4. Separately, `B`, `C`, `D` fully confirm a `DeleteMember{member: A}` request (3 confirmations, meets threshold; `members.len()-1 = 3 >= num_confirmations = 3` so the safety check passes) → `delete_member` executes: `A` is removed from `self.members`, but `R1` was authored by `D`, so the cleanup loop (`filter_map(|(k,r)| r.member == member)`) does not touch `R1`, and `confirmations[R1]` still equals `{A}` [3](#0-2) .
5. Now only `B` and `C` remain as live members besides `D`. `B` calls `confirm(R1)` → `confirmations[R1].len() = 1`, `+1 = 2 < 3`, so it just adds `B`, giving `{A, B}`.
6. `C` calls `confirm(R1)` → `confirmations[R1].len() = 2`, `+1 = 3 >= num_confirmations (3)` → `execute_request` fires the `Transfer`, even though only two *live* members (`B`, `C`) approved it, with `A`'s stale ghost confirmation making up the third — one fewer live approval than the configured 3-of-4 policy requires.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
