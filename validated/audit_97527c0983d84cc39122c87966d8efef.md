## Title
Gateway WebAPI/Capabilities handler keys pending user callbacks only by attacker-controlled `MessageId`, causing cross-user response confusion - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The `capabilities` Gateway handler stores a pending user callback in a single global map keyed solely by the message's `MessageId`, a value fully supplied by the (unprivileged) caller in the incoming legacy request. When a node's response for that `MessageId` later arrives, the handler blindly looks the ID up in the map and delivers the response to whatever callback is currently registered under it — without verifying that the response actually belongs to the caller who is waiting. This mirrors the root cause of the referenced report: the code assumes a loosely-associated value (there, "first exchange's last swap token"; here, "whatever caller last registered under this ID") is authoritative, instead of validating an explicit binding between the responder's data and the original requester.

### Finding Description
In `HandleLegacyUserMessage`, the handler saves the caller's callback keyed purely by the message ID from the untrusted client payload, with no ownership/session binding: [1](#0-0) 

When a corresponding node response with the same `MessageId` arrives, `handleWebAPITriggerMessage` looks it up, deletes it, and forwards whatever it finds straight back to the caller waiting on that ID — there is no check that the response content or workflow context actually matches the specific request that registered the callback: [2](#0-1) 

The `MessageId` used as the map key originates from the legacy request body validated only for length/format, not uniqueness or ownership, in `Message.Validate()`: [3](#0-2) 

and is threaded straight from the client-supplied payload into the handler via `ValidatedRequestFromMessage`/gateway routing: [4](#0-3) 

Because the map assignment `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` simply overwrites any existing entry under the same key, two different unprivileged callers who submit requests to the same DON with the same (or colliding) `MessageId` concurrently will race: whichever callback is currently stored under that ID receives the node's reply, and the other caller's request is silently orphaned until it times out via `pruneCallbacks`. There is no per-caller/session scoping of the `MessageId` and no cross-check that the DON's eventual response actually corresponds to the payload the waiting caller submitted.

### Impact Explanation
An unprivileged client can deliberately choose a `MessageId` that collides with another in-flight request to the same DON (IDs are just short client-controlled strings, up to 200 chars). If it wins the race, it captures the response intended for a different user's workflow trigger — this is response/data leakage across users (cross-user response confusion) for whatever the DON node returns for `web_api_trigger`/`web_api_target`/`compute_action` messages. Conversely, a victim's own real response can be silently swallowed and delivered to the attacker's session, causing denial-of-service/timeout for the legitimate caller. This satisfies the "cross-user response confusion" acceptance criterion.

### Likelihood Explanation
Exploitability requires only unprivileged access to the Gateway's user-facing HTTP endpoint and the ability to submit a request with a chosen `MessageId` concurrently with (or shortly after) a target request — no authentication bypass or special privilege is needed, and the relevant code path is reachable directly from `gateway.ProcessRequest`. The main constraint is winning a timing race and knowing/guessing a target's `MessageId`; in shared/public gateway deployments where IDs might be predictable or default (e.g., scripts using fixed IDs, as seen in `core/scripts/gateway/web_api_trigger/invoke_trigger.go`), likelihood is non-trivial.

### Recommendation
Bind pending callbacks to more than a bare, attacker-chosen `MessageId`: incorporate a server-generated nonce/session identifier or the caller's origin/HMAC-derived key into the map key or into a namespaced sub-map keyed by `(callerIdentity, MessageId)`. Reject (rather than silently overwrite) registration of a `MessageId` already present in `savedCallbacks`, and validate that a returned node message actually corresponds to the specific outstanding request context before invoking `SendResponse`.

### Proof of Concept
1. Attacker sends a legacy `web_api_trigger` request to the Gateway's `/user` endpoint with `MessageId = "X"`, targeting DON `D`, and holds the connection open awaiting a response (registers callback under key `"X"` per `HandleLegacyUserMessage`).
2. Concurrently, a legitimate user submits an unrelated request to the same DON `D` using the same `MessageId = "X"` (e.g., colliding due to a client default/generation scheme) — this second registration overwrites the attacker's entry in `h.savedCallbacks["X"]`.
3. The DON node responds first for the legitimate user's request; `handleWebAPITriggerMessage` looks up key `"X"`, finds whichever registration is currently stored, deletes it, and forwards the response.
4. Depending on timing, either the attacker receives the legitimate user's response payload, or the legitimate user's request is orphaned (silently dropped) while the attacker's later-registered callback receives it — demonstrating the lack of per-caller binding in `core/services/gateway/handlers/capabilities/handler.go` lines 148-162 and 411-420.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
