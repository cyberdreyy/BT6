### Title
Miner-side signer vote tally double-counts a signer's weight when a rejection is followed by an acceptance for the same block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner's `StackerDBListener` tracks two independent accounting structures per proposed block — `gathered_signatures` (keyed by slot, gates the `Accepted` weight add) and `responded_signers` (a set, gates the `Rejected` weight add). The `Accepted` handler's idempotency check is gated on `gathered_signatures` only, never on `responded_signers`, so a signer that first rejects and later legitimately re-evaluates and accepts the same block has its weight added to `total_weight_approved` without ever having its earlier contribution to `total_weight_rejected` removed. The two running totals, which the coordinator treats as mutually exclusive partitions of `self.total_weight`, can now double-count one signer's weight, breaking the aggregated-weight vs. verified-responses invariant the threshold checks rely on.

### Finding Description
`stacks-node/src/nakamoto_node/stackerdb_listener.rs` maintains a `BlockStatus` per proposal with `responded_signers: HashSet<u32>`, `gathered_signatures: BTreeMap<u32, MessageSignature>`, `total_weight_approved`, and `total_weight_rejected` [1](#0-0) .

On `Rejected`, the weight-add is gated by inserting into `responded_signers` — a signer can only contribute to `total_weight_rejected` once, and if it had *already* signed (accepted) — hence `responded_signers` already contains its slot — the insert returns `false` and no further weight is added [2](#0-1) . So Accept→Reject is protected.

On `Accepted`, however, the weight-add is gated by `!block.gathered_signatures.contains_key(&slot_id)`, not by `responded_signers`: [3](#0-2) 
If this signer previously sent a `Rejected` message, `responded_signers` already contains its slot (added at line 465 is only reached for the `Accepted` path itself; the `Rejected` path sets it at line 515), but `gathered_signatures` does not. A subsequent `Accepted` from the same signer therefore passes the `!contains_key` check and adds `signer_entry.weight` to `total_weight_approved` — on top of the weight that was already added to `total_weight_rejected` when the earlier rejection was processed. Nothing decrements `total_weight_rejected` on this flip.

This flip is not a hypothetical or malicious-only path: `docs/signer-flows.md` documents `LocallyRejected --> LocallyAccepted : re-evaluated` as a normal state transition [4](#0-3) , and the stacks-signer CHANGELOG records that "some rejection reasons" legitimately cause a signer to "reconsider a block proposal that it previously rejected" (#5880). Each such reconsideration is broadcast as a fresh `BlockResponse::Rejected` then `BlockResponse::Accepted` pair over StackerDB, which is exactly the sequence the miner's coordinator listens to.

By contrast, the signer's own local database (`stacks-signer/src/signerdb.rs`) already defends against this class of double-count: `add_block_signature` explicitly deletes any prior `block_rejection_signer_addrs` row for that signer/block before inserting the signature [5](#0-4) , and `add_block_rejection_signer_addr` refuses to add a rejection if a signature already exists for that signer/block [6](#0-5) . The `CHANGELOG.md` entry "Do not count both a block acceptance and a block rejection for the same signer/block" documents this as an intentional fix [7](#0-6) . That fix was applied to the signer's own bookkeeping but the equivalent guard was never added to the miner-side `StackerDBListener`'s `BlockStatus` tally, leaving the same bug class present there.

### Impact Explanation
The coordinator (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) treats `total_weight_approved` and `total_weight_rejected` as disjoint tallies of `self.total_weight` to decide, respectively, whether to broadcast the block as signed or to abort as `SignersRejected` [8](#0-7) . Once one signer's weight is counted in both totals, `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, i.e., the aggregated weight no longer matches the verified set of signers' current responses (an "aggregated-weight vs. verified-accepts" equality break). Concretely: a signer's stale rejection weight remains permanently baked into `total_weight_rejected` even after that signer withdraws the rejection by accepting, so the blocking-minority (>30%) rejection threshold can be crossed and the coordinator can prematurely report `SignersRejected` for a block that in fact has enough live signer support, or the 70% acceptance path can be satisfied while a portion of the counted weight is not distinguishable from double-counted stale data — a miscounted response defeating the intended one-vote-per-signer weighting the threshold math depends on.

### Likelihood Explanation
No malicious majority, extra keys, or auth token is needed — only one signer's ordinary reconsideration flow (a documented, legitimate transition) needs to be observed by the miner in the reject-then-accept order for its weight to be double-tallied. This can happen during normal operation whenever a signer initially rejects (e.g., over a stale view) and then re-evaluates favorably after receiving updated information, which the codebase explicitly supports and tests for.

### Recommendation
Gate the `Accepted` weight-add on `responded_signers` (the same structure used to gate `Rejected`) instead of `gathered_signatures`, and when a flip from rejected to accepted (or vice versa) is detected, adjust the opposing total downward by that signer's weight before adding it to the new total — mirroring the delete-then-insert behavior already implemented in `stacks-signer/src/signerdb.rs`'s `add_block_signature`/`add_block_rejection_signer_addr`.

### Proof of Concept
1. Miner inserts a fresh `BlockStatus` for a proposal via `insert_block` (`total_weight_approved = 0`, `total_weight_rejected = 0`, both tracking sets empty) [9](#0-8) .
2. Signer S (slot `k`, weight `w`) sends `BlockResponse::Rejected` for the block (e.g., due to a reconsiderable reason). The listener's `Rejected` branch does `block.responded_signers.insert(k)` → `true`, so `total_weight_rejected += w` [2](#0-1) .
3. Signer S re-evaluates and legitimately sends `BlockResponse::Accepted` for the same block (a documented transition). The listener's `Accepted` branch checks `!block.gathered_signatures.contains_key(&k)` → `true` (still empty), so `total_weight_approved += w` is executed [3](#0-2) . `total_weight_rejected` is never decremented.
4. Now `total_weight_approved + total_weight_rejected` includes `w` twice for a single distinct signer, so `total_weight_rejected` retains S's weight as "still rejecting" even though S has since accepted — with enough additional signers rejecting, the coordinator can hit the `>30%` rejection abort threshold using this stale, double-counted weight [10](#0-9) , even though the true, current weight of signers still rejecting is lower than what the tally shows.
