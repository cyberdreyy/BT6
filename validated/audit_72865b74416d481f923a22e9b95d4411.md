### Title
Run-role authenticated user can execute arbitrary registered capabilities without job/workflow ownership binding via `POST /v2/execute_capability` when `build.IsDev()` is true - ([File: core/web/capability_controller.go])

### Summary
The route `POST /v2/execute_capability` is gated only by `build.IsDev()` and `auth.RequiresRunRole`, and its handler `CapabilityController.ExecuteCapability` executes any capability named in the request body against attacker-supplied `WorkflowID`/`WorkflowExecutionID` metadata with no check that the caller is authorized to invoke that specific job/workflow's capability. Any run-role authenticated caller can therefore trigger execution of any capability registered in `CapabilitiesRegistry`, including capabilities tied to jobs/workflows they do not own.

### Finding Description
The route is registered in `core/web/router.go`: [1](#0-0) 
This wraps the handler only with `auth.RequiresRunRole`, the lowest privileged authenticated role, with no per-job or per-workflow authorization check.

The handler itself, `CapabilityController.ExecuteCapability` in `core/web/capability_controller.go`, takes a `capabilityName` and an opaque, caller-controlled `capabilityRequest` byte payload, looks up the named capability directly from the global `CapabilitiesRegistry`, unmarshals the request (which embeds `WorkflowID`/`WorkflowExecutionID` metadata), and calls `Execute` on it: [2](#0-1) 

There is no code anywhere in this path that:
- Verifies the authenticated session/token belongs to the owner of the job/workflow referenced by `capabilityRequestOuter`/`capabilityRequest.Metadata.WorkflowID`.
- Restricts which capability names a run-role user may invoke.
- Cross-checks the capability against any job spec owned/authorized for that caller.

The unit tests in `core/web/capability_controller_test.go` confirm this behavior: `TestCapabilityController_ExecuteCapability` calls the handler directly (bypassing router role wiring) with an arbitrary `WorkflowID: "test-workflow"` in the request metadata and shows execution proceeds successfully with `http.StatusOK`, with no ownership/authorization check performed inside the handler: [3](#0-2) 

The gating condition `build.IsDev()` is the only guard preventing this route from existing in production builds; if that build flag is (mis)true in a "default-adjacent" build (e.g., a dev/staging binary mistakenly deployed, or a build where `IsDev()` returns true due to build-tag/ldflags misconfiguration), the endpoint becomes reachable to any run-role user.

### Impact Explanation
Any authenticated run-role user (the lowest privilege level, typically granted for triggering job runs) can invoke arbitrary capabilities registered on the node — potentially including capabilities that write on-chain, move funds, or perform privileged actions tied to workflows/jobs the caller does not own. This is a role/authorization bypass and unauthorized-action-on-another-user's-job class impact, since a run-role principal is meant to be scoped to running specific authorized jobs, not to freely invoke any capability in the registry with arbitrary attacker-chosen metadata.

### Likelihood Explanation
The precondition is that `build.IsDev()` evaluates true on the running binary — this is described in the question as a build/misconfiguration condition rather than something a network attacker can control directly. Given that precondition, exploitation requires only a run-role credential (the least-privileged authenticated role) and a single POST request with a valid capability name and marshaled `CapabilityRequest`; there are no additional secrets, timing, or race conditions needed, so it is trivially repeatable once the endpoint is reachable.

### Recommendation
Bind capability execution to the caller's authorized job/workflow: require the request to reference a job/workflow the authenticated identity owns or has explicit `run` permission for, verify that binding server-side (e.g., via a job store lookup keyed by the authenticated user) before calling `capability.Execute`, and reject requests whose `WorkflowID`/`WorkflowExecutionID` do not match an authorized job. Additionally, do not rely solely on `build.IsDev()` to gate a production-capable execution endpoint — ensure it is compiled out entirely (via build tags) rather than a runtime function check.

### Proof of Concept
1. In `core/web/capability_controller_test.go`, add a test that constructs a `gin.Engine`, wraps `controller.ExecuteCapability` with `auth.RequiresRunRole` and a fake run-role authenticated context (as done via `router.go` wiring), analogous to the existing `TestCapabilityController_ExecuteCapability`.
2. Register a mock `ExecutableCapability` in the registry that is conceptually tied to a job/workflow (`WorkflowID: "victim-workflow"`) not owned by the test's run-role identity.
3. Send a `CapabilityRequestOuter{CapabilityName: "victim-capability", CapabilityRequest: <marshaled request with WorkflowID "victim-workflow">}` as the run-role user.
4. Assert: `capability.Execute` is invoked (as shown by `mockRegistry.EXPECT().GetExecutable(...)` and `executableCap.EXPECT().Execute(...)` being satisfied) and the response is `http.StatusOK`, with no authorization check ever consulting job ownership — demonstrating that `ExecuteCapability` proceeds without ownership binding, as already evidenced by the existing `TestCapabilityController_ExecuteCapability` test at [4](#0-3) .

```go
func (cc *CapabilityController) ExecuteCapability(c *gin.Context) {
	body := c.Request.Body
	if body == nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("missing request body"))
		return
	}

	capabilityRegistry := cc.App.GetCapabilitiesRegistry()
	if capabilityRegistry == nil {
		jsonAPIError(c, http.StatusInternalServerError, errors.New("capability registry not initialized"))
		return
	}
	var capabilityRequestOuter CapabilityRequestOuter
	if err := c.BindJSON(&capabilityRequestOuter); err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	capability, err := capabilityRegistry.GetExecutable(c.Request.Context(), capabilityRequestOuter.CapabilityName)
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	capabilityRequest, err := pb.UnmarshalCapabilityRequest(capabilityRequestOuter.CapabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	resp, err := capability.Execute(c.Request.Context(), capabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	responseBytes, err := pb.MarshalCapabilityResponse(resp)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	c.JSON(http.StatusOK, gin.H{"capabilityResponse": responseBytes})
```

```go
func TestCapabilityController_ExecuteCapability(t *testing.T) {
	t.Parallel()
	mockApp := appmocks.NewApplication(t)
	mockRegistry := registrymock.NewCapabilitiesRegistry(t)
	mockApp.EXPECT().GetCapabilitiesRegistry().Return(&capabilities.Registry{
		CapabilitiesRegistryBase: mockRegistry,
	})

	executableCap := capmock.NewExecutableCapability(t)
	capabilityName := "test-capability"
	mockRegistry.EXPECT().GetExecutable(mock.Anything, capabilityName).Return(executableCap, nil)
	expectedResponse := commoncap.CapabilityResponse{
		Value: &values.Map{Underlying: map[string]values.Value{
			"result": &values.String{Underlying: "success"},
		}},
	}
	executableCap.EXPECT().Execute(mock.Anything, mock.AnythingOfType("capabilities.CapabilityRequest")).Return(expectedResponse, nil)

	controller := web.CapabilityController{App: mockApp}

	inputsMap, err := values.NewMap(map[string]any{
		"test": "input",
	})
	require.NoError(t, err)

	configMap, err := values.NewMap(map[string]any{
		"config": "value",
	})
	require.NoError(t, err)

	capabilityRequest := commoncap.CapabilityRequest{
		Metadata: commoncap.RequestMetadata{
			WorkflowID:          "test-workflow",
			WorkflowExecutionID: "test-execution",
		},
		Config: configMap,
		Inputs: inputsMap,
	}

	capabilityRequestBytes, err := pb.MarshalCapabilityRequest(capabilityRequest)
	require.NoError(t, err)
	requestBody := web.CapabilityRequestOuter{
		CapabilityName:    capabilityName,
		CapabilityRequest: capabilityRequestBytes,
	}
	reqJSON, err := json.Marshal(requestBody)
	require.NoError(t, err)

	w := httptest.NewRecorder()
	engine := gin.New()
	engine.POST("/v2/capabilities/execute", controller.ExecuteCapability)

	req, err := http.NewRequestWithContext(t.Context(), http.MethodPost, "/v2/capabilities/execute", bytes.NewBuffer(reqJSON))
	require.NoError(t, err)
	req.Header.Set("Content-Type", "application/json")

	engine.ServeHTTP(w, req)
	assert.Equal(t, http.StatusOK, w.Code)

	var response map[string]any
	err = json.Unmarshal(w.Body.Bytes(), &response)
	require.NoError(t, err)
	assert.Contains(t, response, "capabilityResponse")
}
```
