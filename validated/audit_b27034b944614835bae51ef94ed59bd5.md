### Title
Unauthenticated MessageId collision allows attacker to hijack another user's gateway callback via `savedCallbacks` overwrite - ([File: core/services/gateway/handlers/handler.dummy.go])

### Summary
`dummyHandler.HandleLegacyUserMessage` stores each request's callback in `d.savedCallbacks` keyed solely by the attacker-controlled `msg.Body.MessageId`, with no check for an existing entry before overwriting it. Because `MessageId` is chosen entirely by the caller and unrelated to their signer identity, any unauthenticated party who guesses or observes a victim's in-flight `MessageId` can submit a competing request with the same ID and silently replace the victim's callback, causing the eventual node response to be delivered to the attacker instead of the victim.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go`) decodes an incoming request, validates the message signature via `msg.Validate()`, and — for any legacy request whose signature is valid for *some* key (not necessarily a privileged one) — dispatches it to `h.HandleLegacyUserMessage(ctx, msg, callback)`. There is no per-caller/session gate beyond signature validity; any address can sign and submit a request with any `MessageId` value.

`Message.Validate()` (`core/services/gateway/api/message.go`, lines 54-88) only checks length/format constraints and that the signature matches some `Sender`; it never checks `MessageId` uniqueness or ties it to a caller identity: [1](#0-0) .

In `dummyHandler.HandleLegacyUserMessage`:
```
d.mu.Lock()
d.savedCallbacks[msg.Body.MessageId] = &savedCallback{msg.Body.MessageId, callback}
```
this unconditionally overwrites any existing entry under the same key without checking `_, exists := d.savedCallbacks[msg.Body.MessageId]` first. [2](#0-1) 

When the node eventually replies, `HandleNodeMessage` looks up the callback purely by `msg.Body.MessageId` (echoed back from the node) and delivers the response to whichever callback is currently stored — the attacker's, if they raced in after the victim: [3](#0-2) .

Exploit flow:
1. Victim sends a legacy request signed with their own key, `MessageId = "M"`.
2. Before the DON responds, attacker (any address, unauthenticated w.r.t. the victim's session) sends their own signed legacy request also using `MessageId = "M"`.
3. `d.savedCallbacks["M"]` is overwritten to point at the attacker's callback.
4. When the node responds with `ID = "M"`, `HandleNodeMessage` sends the (potentially victim-derived) response to the attacker's callback, and the victim's HTTP call to `gateway.ProcessRequest` will hang until timeout (`callback.Wait(ctx)` times out) — resulting in cross-user response leakage and/or DoS for the victim.

No component validates that `MessageId` is unique across concurrent in-flight requests or binds it to the requester's signer address, so this reachable from a fully unauthenticated/unprivileged HTTP client of the gateway.

### Impact Explanation
This breaks request/response isolation between independent gateway callers: an attacker can cause a victim's DON-issued response (which may include sensitive payload/computation results) to be delivered to the attacker's own connection, and simultaneously deny the victim their response (timeout/DoS). This matches "cross-user response confusion" / unauthorized access to another user's response data in the bounty impact classes for the gateway.

### Likelihood Explanation
The only precondition is that the attacker can predict or observe the victim's `MessageId` before the DON responds and can submit their own validly-signed legacy message (any key works — `Validate()` doesn't restrict which signer may use which `MessageId`). If callers use predictable IDs (e.g., sequential counters, timestamps, or externally observable identifiers) this is trivially exploitable by an unprivileged network client; even with random IDs, a same-origin or malicious integrating client that reuses/predicts IDs from its own application layer can exploit this against itself or other tenants sharing that gateway/DON.

### Recommendation
In `dummyHandler.HandleLegacyUserMessage` (and similarly in `core/services/gateway/handlers/capabilities/handler.go`'s `HandleLegacyUserMessage`), reject the request instead of overwriting when `msg.Body.MessageId` already exists in `savedCallbacks`, e.g.:
```go
d.mu.Lock()
if _, exists := d.savedCallbacks[msg.Body.MessageId]; exists {
    d.mu.Unlock()
    return errors.New("duplicate message ID")
}
d.savedCallbacks[msg.Body.MessageId] = &savedCallback{msg.Body.MessageId, callback}
d.mu.Unlock()
```
Additionally consider deriving the callback map key from `(Sender, MessageId)` rather than `MessageId` alone, so that even non-colliding IDs from different senders cannot be confused.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/handler.dummy_test.go`:
1. Create a `dummyHandler` with a `testConnManager`.
2. Sign two distinct `api.Message`s with two different private keys but the **same** `Body.MessageId = "shared-id"`.
3. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`.
4. Call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)` (same MessageId).
5. Build a node response with `ID = "shared-id"` and `Sender` matching the victim's node route, call `handler.HandleNodeMessage(ctx, resp, nodeAddr)`.
6. Assert: `attackerCallback.Wait(ctx)` returns the response while `victimCallback.Wait(ctx)` times out — demonstrating the callback overwrite and cross-user delivery. Expected/fixed behavior: the second `HandleLegacyUserMessage` call should return an error (duplicate MessageId) and leave the victim's callback intact.
