### Title
Stale `instantWithdrawClaimsByEpoch` inflates default-recovery reserve, permanently freezing later claimants' recovery - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` pays out instant receipts but never decrements `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`. Those per-epoch counters therefore keep "bits set" for receipts that were already paid — the same class of bug as the ext4 block bitmap whose padding bits past `blocks_per_group` stayed set and made the allocator believe invalid blocks were free. At `finalizeDefaultRecovery`, the stale basis is counted twice: once inside `defaultPendingClaimBasis` and again as a phantom "prefunded" reserve via `_defaultPrefundedInstantReserve`, which overstates `defaultRecoveryReserve` relative to the underlying actually held. Later claimants then hit `defaultRecoveryReserve -= _amount` underflow or insufficient-balance reverts and can never claim.

### Finding Description
- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[user][epoch] += amount` and `instantWithdrawClaimsByEpoch[epoch] += amount` (`IdleCreditVault.sol:366-374`). [1](#0-0) 
- The normal claim path `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]` and transfers underlying, but does **not** clear `instantWithdrawsRequestsByEpoch[_user][epoch]` nor `instantWithdrawClaimsByEpoch[epoch]` (`IdleCreditVault.sol:387-392`). [2](#0-1) 
- `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` only (`:401-402`). So after funding + claims, `pendingInstantWithdraws` may be non-zero while `instantWithdrawClaimsByEpoch[epochNumber]` still holds the full original claim basis — including amounts already paid out. [3](#0-2) 
- On default, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (`:644-649`), and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying already held (`:716-723`). Both use the stale counter. [4](#0-3) 
- `finalizeDefaultRecovery` then sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` (`:686-691`), crediting phantom reserve equal to receipts already paid out. [5](#0-4) 
- Every defaulted claim executes `defaultRecoveryReserve -= _amount` then `safeTransfer` (`:912-917`). When cumulative claims exceed the real underlying balance, the subtraction or the transfer reverts, permanently freezing the remaining claimants' recovery share. [6](#0-5) 

Broken invariant: one receipt one payout + solvency of the recovery reserve. The counted claim basis and reserve exceed the actual underlying held, exactly like the ext4 bitmap advertising more valid blocks than the group contains.

### Impact Explanation
After a borrower default is finalized, claimants who redeemed early consumed real underlying, but the finalized `defaultRecoveryReserve` still credits that amount as available. When total claims reach the phantom region, `_transferDefaultRecovery` reverts (SafeERC20 underflow/insufficient balance), so the last claimants' recovery funds are permanently frozen inside the strategy — only `transferToken` (owner rescue) could recover them, which contradicts the honest-owner assumption and is not a user remedy. Quantified loss: up to the sum of instant-withdraw receipts claimed (or funded via `collectInstantWithdrawFunds`) between the start of the defaulted epoch and default finalization.

### Likelihood Explanation
Requires a concrete but plausible sequence by unprivileged actors only: a lender requests an instant withdraw, the CDO collects funds and the user claims (all normal, honest flows), then a borrower default occurs in the same epoch while `pendingInstantWithdraws` remains non-zero (another user has a partially funded instant request), and the owner/guardian finalizes recovery. Any user holding a defaulted-epoch receipt can trigger it simply by claiming early — no privileged action needed. Medium likelihood: it needs the epoch-specific timing, but defaults are the designed-for scenario.

### Recommendation
Mirror the ext4 fix ("padding bits must be cleared/validated"): keep per-epoch receipt counters consistent with what is actually outstanding. In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` for the claimed amount (track which epoch a user's pending instant receipts belong to, or iterate stored epochs). Alternatively compute `_defaultPrefundedInstantReserve` and `defaultPendingClaimBasis` from the sum of live per-user `instantWithdrawsRequestsByEpoch` entries rather than the lifetime cumulative `instantWithdrawClaimsByEpoch`. Add a check in `finalizeDefaultRecovery` that `defaultRecoveryReserve <= underlyingToken.balanceOf(address(this))` after pulling external recovery.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

// Fork test: deploy/attach a real IdleCreditVault + IdleCDOEpochVariant pair on mainnet fork.
contract StaleInstantClaimsPoC is Test {
    IdleCreditVault vault;      // strategy
    address cdo;                // IdleCDOEpochVariant
    IERC20Detailed token;       // underlying
    address alice = address(0xA11CE); // instant withdrawer who claims early
    address bob   = address(0xB0B);   // instant withdrawer left pending
    address carol = address(0xCA);    // defaulted-epoch normal withdrawer

    function test_staleInstantBasisFreezesRecovery() public {
        // --- Epoch N running ---
        // 1) alice + bob each request instant withdraw of 100 via CDO
        vm.prank(cdo); vault.requestInstantWithdraw(100e6, alice);
        vm.prank(cdo); vault.requestInstantWithdraw(100e6, bob);
        // instantWithdrawClaimsByEpoch[N] = 200, pendingInstantWithdraws = 200

        // 2) CDO collects only alice's share and alice claims it
        deal(address(token), cdo, 100e6);
        vm.prank(cdo); vault.collectInstantWithdrawFunds(100e6);
        vm.prank(cdo); vault.claimInstantWithdrawRequest(alice);
        // pendingInstantWithdraws = 100, but instantWithdrawClaimsByEpoch[N] is STILL 200
        assertEq(vault.instantWithdrawClaimsByEpoch(vault.epochNumber()), 200e6);

        // 3) borrower defaults mid-epoch; CDO calls finalizeDefaultRecovery
        //    defaultPendingClaimBasis() = pendingWithdraws + 200  (should be 100)
        //    _defaultPrefundedInstantReserve() = 200 - 100 = 100 (phantom: already paid to alice)
        //    defaultRecoveryReserve is credited +100 that the vault does not hold.

        // 4) bob + carol claim recovery; when cumulative payouts exceed real balance,
        //    _transferDefaultRecovery underflows / transfer reverts => funds frozen.
        vm.prank(cdo);
        vm.expectRevert();
        vault.claimInstantWithdrawRequest(bob); // or claimWithdrawRequest(carol)
    }
}
```

The PoC asserts the divergence (`instantWithdrawClaimsByEpoch` = 200 vs `pendingInstantWithdraws` = 100) before finalization, which directly produces the overstated `defaultRecoveryReserve` and the subsequent claim revert — reproducible on a mainnet fork using an existing vault deployment and epoch cycle.
