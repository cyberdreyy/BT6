### Title
Confirmations from a removed multisig member remain counted toward the execution threshold, allowing requests to execute below the required number of live confirmations - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts the size of the stored `confirmations` set against `num_confirmations` to decide when to execute a request, but `delete_member` only purges confirmation records for requests *created by* the removed member, not confirmation records where the removed member was merely a *confirmer* of someone else's request. A member's stale "yes" vote therefore keeps counting toward the threshold even after that member is removed from the multisig, letting a request execute with fewer currently-authorized confirmations than `num_confirmations` requires.

### Finding Description
`confirm()` validates that the *caller* is currently a member via `assert_valid_request` → `current_member()`, but it never re-validates the members recorded in the already-stored `confirmations: HashSet<String>` for that request: [1](#0-0) 

Membership removal is handled in `delete_member`, invoked from `execute_request` for the `DeleteMember` action: [2](#0-1) 

Note the cleanup loop:
```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
This only deletes requests (and their confirmation sets) where `r.member == member`, i.e. where the removed member is the **requester**. It does nothing about entries in `self.confirmations` for *other, still-pending* requests where the removed member had previously called `confirm()` and left their identity string in the `HashSet<String>`.

The binding that should hold is:
```
number_of_distinct_current_members_who_confirmed(request) >= num_confirmations
```
but the code actually checks:
```
size_of_stored_confirmations_set(request) >= num_confirmations
```
These two are equal only as long as no confirmer is later removed from `members`. Once a confirmer is removed, the stored set still contains their now-invalid identity, so the equality is broken: `size_of_stored_confirmations_set(request) > number_of_distinct_current_members_who_confirmed(request)`.

### Impact Explanation
This is the multisig analog of the `VetoProposal` state-check mismatch: the wrapper-level book-keeping (`confirmations` set length) diverges from the real authorization state (current live membership) that the contract is supposed to enforce, and downstream logic (`execute_request`, including `Transfer`, `AddKey`, `FunctionCall`, `DeployContract` actions that move NEAR or grant access) trusts the stale count.

Concretely:
1. Members = {A, B, C, D}, `num_confirmations = 3`.
2. A creates and confirms request `R` (e.g. `Transfer` of the contract's NEAR balance to an attacker-controlled account): confirmations = {A}.
3. B confirms `R`: confirmations = {A, B} (still short by 1).
4. Separately, B is removed via a fully-confirmed `DeleteMember{B}` request. `delete_member` only removes requests where B was the *creator*; `R` (created by A) is untouched, so its confirmation set still contains B.
5. C (still a live member) confirms `R`: `confirmations.len() + 1 = 3 >= num_confirmations (3)` → `R` executes.

`R` is executed based on votes from A, B (no longer a member), and C — only 2 currently-authorized members actually approved it, one short of the configured 3-of-4 threshold. This is exactly the "multisig request executed below threshold" Critical scenario: NEAR can move (via `Transfer`, `FunctionCall` with deposit, or a `DeployContract`/`AddKey` action) with fewer live approvals than the contract's security model guarantees, or governance actions (further membership changes, confirmation-threshold changes) can be pushed through with a ghost vote from a removed party.

### Likelihood Explanation
No admin/owner/foundation cooperation beyond the normal multisig workflow is required — any two authorized events (a confirmed `DeleteMember` action, and a pending unrelated request that a soon-to-be-removed member had already confirmed) are enough to create the divergence. This is a realistic operational sequence for any multisig that rotates members while other requests are in flight, which is an expected, not edge-case, usage pattern (member rotation is a first-class supported action). No malicious validator, redeploy, or RPC interception is needed — only ordinary sequencing of already-supported contract calls by legitimate (but since-removed) key holders.

### Recommendation
When a member is removed in `delete_member`, also purge that member's identity string from the `confirmations` set of every other pending request (or re-validate, at `confirm()`-time and at request-creation time, that every string stored in `confirmations` still corresponds to a current member before counting it toward the threshold). Alternatively, recompute the confirmation count each time by intersecting the stored confirmer set with `self.members` rather than relying on stored set length.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
