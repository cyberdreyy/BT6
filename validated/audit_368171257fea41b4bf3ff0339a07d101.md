### Title
MerkleClaim leaf omits token/contract identity — proof reuse across clones lets claimees claim the wrong (more valuable) token - (File: contracts/MerkleClaim.sol)

### Summary
`MerkleClaim.claim()` verifies a Merkle proof against a leaf built only from `(to, amount)` (contracts/MerkleClaim.sol:58). Neither the distributed `token` address nor the clone contract address is bound into the leaf. Because the contract is explicitly designed to be cloned per distribution ("no ERC20, cloneable", contracts/MerkleClaim.sol:10), the same recipient list can be used to initialize multiple clones paying different tokens. Any claimee can then take their proof to the clone distributing a more valuable token and claim the full `amount` there, independently of the honest claim on the intended clone — `hasClaimed` is per-clone storage (contracts/MerkleClaim.sol:23,63) and offers no cross-clone protection.

### Finding Description
The verification data is:

```solidity
// contracts/MerkleClaim.sol:58
bytes32 leaf = keccak256(bytes.concat(keccak256(abi.encode(to, amount))));
```

Each clone stores its own `token` (set once in `initialize`, lines 37–44) and its own `hasClaimed` map, but the leaf does not commit to either. A leaf valid under root `R` is therefore valid for *every* clone initialized with `R`, regardless of which token that clone pays out. This is the direct analog of the external report's missing `Claim.token` / window binding: here the "window" is the clone, and the missing field is the token (or clone) identity.

Attack scenario: the team distributes the same allocation list across two clones — clone A holding DAI, clone B holding WETH — reusing the same `merkleRoot` (a natural outcome if the root encodes only recipients and amounts, which is all the leaf schema supports). Alice, entitled to 10e18 units in the list, calls `claim()` on clone B with her valid proof and receives 10 WETH instead of / in addition to 10 DAI. Every other listed recipient can do the same, draining clone B's balance; late legitimate claimants on B are left with nothing because `transfer` of the WETH balance (line 66) will revert once drained.

### Impact Explanation
Direct theft: any claimee converts an entitlement denominated in a cheap token into the same nominal amount of a more valuable token held by a sibling clone. Loss equals `amount * (price_B - price_A)` per claim, and total drainage of clone B's balance is bounded only by the sum of listed amounts — i.e., the entire distribution. Permanent freezing follows for honest claimants whose clones were drained.

### Likelihood Explanation
- Preconditions: two `MerkleClaim` clones initialized with the same `merkleRoot` but different `token`s, which is exactly the intended usage pattern (cloneable, same allocation list, different airdrop token or re-distribution round). Nothing in `initialize` prevents root reuse.
- Attacker is any EOA on the recipient list — unprivileged. No privileged-role cooperation needed.
- No existing guard stops it: `hasClaimed` is per-clone, the proof is identical for both clones, and `claim` has no token/window parameter to check against.

### Recommendation
Include the token (and ideally the clone/`address(this)` and a distribution/window index) in the leaf:

```solidity
bytes32 leaf = keccak256(bytes.concat(keccak256(abi.encode(address(this), token, to, amount))));
```

This binds each proof to a specific clone and token, making cross-clone reuse impossible even if the recipient lists are identical.

### Proof of Concept
Foundry fork-free PoC sketch (deploy two clones, one OpenZeppelin `MerkleProof`-compatible root):

```solidity
// test/foundry/MerkleClaimCrossClone.t.sol
function testCrossCloneClaim() public {
    MerkleClaim impl = new MerkleClaim();
    MerkleClaim cloneDAI = MerkleClaim(Clones.clone(address(impl)));
    MerkleClaim cloneWETH = MerkleClaim(Clones.clone(address(impl)));

    // leaves: keccak256(bytes.concat(keccak256(abi.encode(alice, 10e18))))
    bytes32 leafAlice = keccak256(bytes.concat(keccak256(abi.encode(alice, 10e18))));
    bytes32 leafBob   = keccak256(bytes.concat(keccak256(abi.encode(bob,   10e18))));
    bytes32 root = leafAlice < leafBob
        ? keccak256(abi.encodePacked(leafAlice, leafBob))
        : keccak256(abi.encodePacked(leafBob, leafAlice));
    bytes32[] memory proof = new bytes32[](1);
    proof[0] = leafBob;

    // same recipient list reused for a DAI round and a WETH round
    cloneDAI.initialize(root, address(dai));
    cloneWETH.initialize(root, address(weth));
    deal(address(dai),  address(cloneDAI),  100e18);
    deal(address(weth), address(cloneWETH), 100e18);

    vm.prank(alice);
    cloneWETH.claim(alice, 10e18, proof); // succeeds: leaf ignores token/clone
    assertEq(weth.balanceOf(alice), 10e18); // Alice got WETH meant for the WETH round's *own* list semantics
}
```

The WETH clone's `claim` succeeds purely because `(alice, 10e18)` exists in the shared tree — the proof was never bound to `weth` or to `cloneWETH`, and `hasClaimed` on cloneDAI is irrelevant. Repeating for every listed address drains the clone entirely.
