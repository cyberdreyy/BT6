### Title
Missing `mint_decimals` bounds validation can cause out-of-bounds panic in `calc_value`/`calc_amount` - (File: programs/marginfi/src/state/marginfi_account.rs)

### Summary
`calc_value` and `calc_amount`, the core asset/liability valuation functions used by the risk engine, index into the fixed 24-entry `EXP_10_I80F48` table using `mint_decimals` without any bounds check. No bank-creation instruction (other than the Drift-specific one) validates that `mint_decimals < 24` before storing it in a `Bank` account, despite the `Bank` struct's own documentation stating this invariant must hold.

### Finding Description
`calc_value`/`calc_amount` compute `EXP_10_I80F48[mint_decimals as usize]` directly. [7](#0-6)  `EXP_10_I80F48` is statically sized at 24 elements. [8](#0-7)  `Bank::new` is invoked with `bank_mint.decimals` (a raw `u8` from the mint account, unbounded by SPL Token program semantics) across multiple add-bank instructions with no explicit decimals check, except in the Drift path which caps at 19. [9](#0-8) 

### Impact Explanation
If a bank were ever created against a mint with `decimals >= 24`, every valuation call for that bank's positions (deposits, withdrawals, borrows, repays, liquidations, bankruptcy handling — all of which call `calc_value`/`calc_amount`) would panic due to an out-of-bounds array index, permanently freezing all interactions involving that bank and any account holding a position in it.

### Likelihood Explanation
Low-to-Medium: standard SPL/Token-2022 mints almost universally use decimals ≤ 9, and I could not confirm an unprivileged/permissionless path where an attacker fully controls the `bank_mint` account used at bank-creation time (the permissionless staked-collateral path derives the mint from a validated vote-account PDA chain, not an arbitrary mint). This is primarily reachable if a group admin creates a bank for an unusual, non-standard mint with extreme decimals via the generic/admin `add_pool` path, which I was unable to fully confirm lacks validation.

### Recommendation
Add an explicit `check!(mint_decimals < 24, MarginfiError::InvalidConfig)` (or equivalent) in `BankConfigImpl::validate()` or directly in each `lending_pool_add_bank*` instruction handler before constructing the `Bank`, so that out-of-range mints are rejected at bank-creation time with a clear error rather than causing a panic during later valuation calls.

### Proof of Concept
Not independently reproducible from the indexed code alone — would require confirming (in a live/test environment) whether the generic `lending_pool_add_bank` admin instruction accepts a mint with `decimals >= 24` and whether `calc_value`/`calc_amount` then panics on out-of-bounds indexing for that bank's balances.
