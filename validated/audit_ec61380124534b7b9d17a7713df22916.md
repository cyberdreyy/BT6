### Title
Unprivileged authenticated user can read bridge `OutgoingToken` webhook secret via `GET /v2/bridge_types/:BridgeName` - (File: core/web/router.go, core/web/bridge_types_controller.go, core/web/presenters/bridges.go)

### Summary
`BridgeTypesController.Show` (and `Index`) return the full `BridgeResource`, which always serializes `OutgoingToken` with no `omitempty` and no role-based redaction. The route is registered under the authenticated group `authv2` but, unlike `Create`, `Update`, and `Destroy`, `bt.Show` and `bt.Index` are not wrapped with `auth.RequiresEditRole` or any role check, so any authenticated principal (including the lowest "view" role) can fetch another bridge's `OutgoingToken`.

### Finding Description
In `core/web/router.go:268-273`, the bridge routes are set up as:
```go
bt := BridgeTypesController{app}
authv2.GET("/bridge_types", paginatedRequest(bt.Index))
authv2.POST("/bridge_types", auth.RequiresEditRole(bt.Create))
authv2.GET("/bridge_types/:BridgeName", bt.Show)
authv2.PATCH("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Update))
authv2.DELETE("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Destroy))
```
`bt.Show` and `bt.Index` are only gated by `authv2`'s generic `auth.Authenticate(...)` middleware (session or API token), with no `auth.RequiresEditRole`/`RequiresAdminRole` wrapper, while the mutating endpoints correctly require edit role.

`BridgeTypesController.Show` (`core/web/bridge_types_controller.go:125-146`) loads the bridge and calls `jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")`. `presenters.NewBridgeResource` (`core/web/presenters/bridges.go:29-42`) copies `b.OutgoingToken` directly into `BridgeResource.OutgoingToken`, which is tagged `json:"outgoingToken"` (no `omitempty`, unlike `IncomingToken` which is `omitempty` and only populated on `Create`). This means every call to `Show`/`Index` unconditionally serializes the outgoing token in the response body, confirmed by `core/web/presenters/bridges_test.go:39-57`, which shows `outgoingToken` always present in the marshaled JSON.

Since the authentication middleware for `authv2` accepts any valid session or API token regardless of role, and `Show`/`Index` have no role check, a user with only the "view" role (the lowest privilege tier) can call `GET /v2/bridge_types/:BridgeName` and receive the bridge's `OutgoingToken` in the response.

### Impact Explanation
The `OutgoingToken` is a secret credential the Chainlink node uses to authenticate itself when calling out to an external adapter (bridge). Disclosure of this token to a low-privileged, otherwise-unauthorized user lets that user impersonate the node to the external adapter for that bridge — a secret/credential disclosure vulnerability matching the "sensitive credential/secret exposure" bounty impact class.

### Likelihood Explanation
Exploitation requires nothing more than any valid authenticated principal — a "view" role user, a restricted API token holder, etc. — issuing a single `GET` request to a known or guessable bridge name. No additional bypass or misconfiguration is needed; this is fully reachable through the documented, unauthenticated-by-role route as registered in `router.go`. It's trivially repeatable for any bridge configured on the node.

### Recommendation
Wrap `bt.Show` and `bt.Index` with an appropriate role check (e.g., `auth.RequiresEditRole` or a new minimum role gate) consistent with the other bridge management endpoints, and/or strip `OutgoingToken` from `BridgeResource` for view-only/read endpoints (mirroring how `IncomingToken` is only populated on `Create`), so the secret is not exposed to lower-privileged roles.

### Proof of Concept
1. In `core/web/bridge_types_controller_test.go` (or a new test file), spin up the test application (`cltest.NewApplicationEVMDisabled` or existing helper used in bridge controller tests) with a bridge created via `bridges.NewBridgeType`/`orm.CreateBridgeType`, capturing the generated `OutgoingToken`.
2. Create an authenticated HTTP client using a session/API token with the lowest role ("view") — reuse existing test helpers such as `cltest.NewUserSession`/`cltest.APIClient` configured with `sessions.UserRoleView`.
3. Issue `GET /v2/bridge_types/<bridgeName>` using that view-role client.
4. Assert the response status is `200`, then unmarshal the JSON body's `data.attributes.outgoingToken` field and assert it is non-empty and equals the `OutgoingToken` stored in the DB — demonstrating disclosure despite the low-privilege role.

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

}

// GetName implements the api2go EntityNamer interface
func (r BridgeResource) GetName() string {
	return "bridges"
}

		OutgoingToken:          b.OutgoingToken,

	}
}
