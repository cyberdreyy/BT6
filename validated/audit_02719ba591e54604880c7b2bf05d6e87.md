### Title
DA-footprint gas metering divides before multiplying, truncating the Jovian DA-footprint estimate - (File: crates/common/evm/src/executor/block_executor.rs)

### Summary
The Jovian `daFootprintGasScalar` metering path performs integer division by `1e6` *before* multiplying by the scalar, instead of multiplying first and dividing last (the order used everywhere else in this codebase's fee math, e.g. Fjord/Ecotone L1 cost). This truncates the estimated compressed size to whole bytes before scaling, discarding the sub-byte fractional remainder that the scalar multiplication would otherwise have preserved.

### Finding Description
`tx_estimated_size_fjord` returns the FastLZ-estimated compressed size **scaled by 1e6** (bytes × 1e6), per `max(minTransactionSize, intercept + fastlzCoef*fastlzSize)`. [1](#0-0) 

The correct/consistent pattern elsewhere in the codebase multiplies by the scalar first, then divides by the scaling constant last, e.g. `calculate_tx_l1_cost_fjord`: [2](#0-1) 

However, the Jovian DA-footprint gas computation does the opposite — it divides by `1_000_000` first (floor-truncating to whole bytes) and only then multiplies by `da_footprint_gas_scalar`:

- `L1FeeParams::jovian_da_footprint` (engine-neutral math, used by the EVM2 executor path): [3](#0-2) 

- `BaseBlockExecutor::jovian_da_footprint_estimation` (revm block-execution path): [4](#0-3) 

- `state_builder.rs` (flashblocks pending-state estimation, same pattern): [5](#0-4) 

All three reachable metering call sites divide before multiplying, whereas the correct math (matching the sibling `calculate_tx_l1_cost_fjord`/`calculate_l1_fee_scaled_ecotone` functions and the existing `data_gas_fjord` in `flz.rs`) multiplies before dividing: [6](#0-5) 

This value is consumed on every non-deposit transaction post-Jovian to (a) enforce the per-tx/per-block DA-footprint budget during block execution, and (b) populate the consensus-visible `blob_gas_used` header/receipt field: [7](#0-6) [8](#0-7) 

### Impact Explanation
Because the estimated size is truncated to whole bytes *before* being multiplied by the scalar, any transaction whose scaled estimate is not an exact multiple of `1_000_000` loses precision, and that lost fraction is then further amplified/discarded relative to the scalar — the computed DA-footprint gas is systematically ≤ the mathematically correct value (never larger, due to `wrapping_div`/`saturating_div` flooring). Since `da_footprint_gas_scalar` can be in the hundreds/thousands (test fixtures use values like 400, 1000, 2000), the truncated fractional byte, when scaled, represents real gas that is silently dropped from the budget. This causes the DA-footprint metering (which caps how much L1-DA data a block can absorb, analogous to blob gas limits) to systematically undercount usage, letting more real DA bytes be admitted into a block than the intended budget allows — a resource-metering/gas-accounting correctness bug reachable by any ordinary transaction sender post-Jovian, since the discrepancy applies per-transaction on every block built or validated.

The bug is symmetric — both the block-executor (execution/validation) and the payload/flashblocks estimation paths use the same divide-then-multiply order — so it does not by itself cause a cross-implementation chain split; however, it is a real deviation from the reference OP-stack math (which multiplies before dividing, as documented at `tx_estimated_size_fjord`'s own comment and mirrored correctly by `calculate_tx_l1_cost_fjord`), and it corrupts the consensus-visible `blob_gas_used` field reported in block headers and RPC receipts.

### Likelihood Explanation
Triggered on every ordinary, unprivileged transaction once the Jovian fork is active and a non-zero `da_footprint_gas_scalar` is configured — no special permissions, precompile access, or crafted input beyond a normal transaction is required. The magnitude of the discrepancy depends on how close the scaled size is to a multiple of `1e6` and the size of the scalar, so it is a systematic, low-per-transaction but chain-wide/perpetual precision loss rather than a one-off edge case.

### Recommendation
Reorder the arithmetic to multiply by `da_footprint_gas_scalar` before dividing by `1_000_000`, mirroring `calculate_tx_l1_cost_fjord`/`data_gas_fjord`:
```rust
// before
let encoded = estimate_tx_compressed_size(...).saturating_div(1_000_000);
...
Ok(encoded.saturating_mul(da_footprint_gas_scalar))

// after
let scaled = estimate_tx_compressed_size(...);
...
Ok(scaled.saturating_mul(da_footprint_gas_scalar).saturating_div(1_000_000))
```
Apply the same fix consistently to `L1FeeParams::jovian_da_footprint` in `crates/common/l1-fees/src/params.rs`, `BaseBlockExecutor::jovian_da_footprint_estimation` in `crates/common/evm/src/executor/block_executor.rs`, and the flashblocks equivalent in `crates/execution/flashblocks/src/state_builder.rs`, and add a regression test asserting the multiply-first result exceeds (or matches) the divide-first result for a non-multiple-of-1e6 estimated size and non-trivial scalar.

### Proof of Concept
Using `tx_estimated_size_fjord` semantics (value scaled by 1e6) with a scalar of, say, `3`:
- Suppose `fastlz_size` yields an estimated size of `100_500_000` scaled units (i.e., 100.5 bytes-equivalent before the final /1e6).
- Current (buggy) order: `100_500_000 / 1_000_000 = 100` (floor) → `100 * 3 = 300`.
- Correct order: `100_500_000 * 3 = 301_500_000` → `/ 1_000_000 = 301` (floor).
- The buggy path under-reports the DA-footprint gas by `1` unit per transaction for this example; larger scalars or estimated sizes whose remainder mod `1e6` is larger widen the gap proportionally to the scalar, since the fractional byte-equivalent is discarded before scaling rather than after. This directly parallels the reported `AMM.sol` pattern where `division-before-multiplication` (`x / 1e6 * y` instead of `x * y / 1e6`) causes avoidable precision loss in a value that gates a resource budget. /// Calculate the estimated compressed transaction size in bytes, scaled by 1e6.
/// This value is computed based on the following formula:
/// max(minTransactionSize, intercept + fastlzCoef*fastlzSize)
pub fn tx_estimated_size_fjord(input: &[u8]) -> u64 {
    let fastlz_size = flz_compress_len(input) as u64;

    fastlz_size
        .saturating_mul(L1_COST_FASTLZ_COEF)
        .saturating_sub(L1_COST_INTERCEPT)
        .max(MIN_TX_SIZE_SCALED)
}

    fn jovian_da_footprint_estimation(
        &mut self,
        tx_env: &E::Tx,
        tx: impl RecoveredTx<R::Transaction>,
    ) -> Result<u64, BlockExecutionError> {
        // Try to use the enveloped tx if it exists, otherwise use the encoded 2718 bytes
        let encoded = tx_env
            .encoded_bytes()
            .map_or_else(
                || estimate_tx_compressed_size(tx.tx().encoded_2718().as_ref()),
                |encoded| estimate_tx_compressed_size(encoded),
            )
            .saturating_div(1_000_000);

        // Load the L1 block contract into the cache. If the L1 block contract is not pre-loaded the
        // database will panic when trying to fetch the DA footprint gas scalar.
        self.evm.db_mut().basic(Predeploys::L1_BLOCK_INFO).map_err(BlockExecutionError::other)?;

        let da_footprint_gas_scalar = L1BlockInfo::fetch_da_footprint_gas_scalar(self.evm.db_mut())
            .map_err(BlockExecutionError::other)?
            .into();

        Ok(encoded.saturating_mul(da_footprint_gas_scalar))
    }
