### Title
Instant-withdraw claims never decrement the per-epoch claim counters, corrupting default recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out an instant withdrawal but only clears the aggregate `instantWithdrawsRequests[_user]`. The per-epoch counters `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are left stale. If the same epoch later defaults with any still-unfunded instant request outstanding, `finalizeDefaultRecovery` counts already-paid claims in the default claim basis and treats the already-paid-out cash as prefunded reserve. The recovery price is diluted and `defaultRecoveryReserve` is overstated, so the last claimants' claims revert on `defaultRecoveryReserve -= _amount` underflow — permanently freezing part of the recovery fund.

### Finding Description
The epoch-scoped receipt bookkeeping is meant to track the *outstanding* claim basis per epoch:

- `requestInstantWithdraw` increments `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, `instantWithdrawsRequests[_user]`, and `pendingInstantWithdraws` (`IdleCreditVault.sol:366-374`).
- `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` only (`:398-403`).
- `claimInstantWithdrawRequest` zeroes `instantWithdrawsRequests[_user]` and pays the user, but never touches `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch` (`:380-393`).

The stale counters are then consumed by default finalization:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the basis whenever `pendingInstantWithdraws != 0` (`:644-649`).
- `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant` as underlying already held for instant claims (`:716-723`) — but that cash has already been transferred to the paid claimants, so the reserve is credited with phantom funds.
- `finalizeDefaultRecovery` sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (`:686-692`). Both numerator and denominator are inflated by the same paid amount, but the reserve inflation is not backed by real tokens, while the basis inflation dilutes every claimant's price.
- Claims then drain the real reserve via `_transferDefaultRecovery` (`defaultRecoveryReserve -= _amount`, `:912-917`). Because the reserve was overstated by phantom funds, the accounting says there is more reserve than tokens; once real claims consume the actual balance, subsequent `_transferDefaultRecovery` calls revert on underflow (SafeMath on the reserve subtraction / transfer failure), permanently bricking remaining claims.

The analogous "incremented/kept the wrong counter" defect: the per-epoch instant claim basis is never decremented on a successful claim, while the funded-side counter (`pendingInstantWithdraws`) is — exactly the class of desynchronized counters from the reference report, here with a direct fund-freezing impact instead of mis-scored voting power.

### Impact Explanation
Unprivileged user impact in a running epoch:

1. Any KYC'd lender calls the CDO's instant-withdraw path, gets funded by `collectInstantWithdrawFunds`, and claims via `claimInstantWithdrawRequest`. Their per-epoch basis entries remain.
2. The epoch then defaults (honest borrower event, e.g., via `stopEpochWithDuration`/`_handleBorrowerDefault`) while at least one other instant or normal withdraw request is still pending, so `defaultPendingClaimBasis()` includes the stale `instantWithdrawClaimsByEpoch[epochNumber]`.
3. `finalizeDefaultRecovery` computes a lower `recoveryPrice` (basis inflated by already-paid claims) and a `defaultRecoveryReserve` overstated by the phantom prefunded amount.
4. Legitimate default claimants are underpaid by the dilution, and once the real underlying is exhausted, every remaining `_claimDefaultedInstantWithdrawRequest`, `_claimDefaultedWithdrawRequest`, and `_claimPostDefaultWithdrawRequest` call reverts on `defaultRecoveryReserve -= _amount` underflow — permanently freezing the residual recovery balance (dust up to the full paid-out instant amount).

Quantified loss: up to the total of instant withdrawals paid out earlier in the defaulted epoch — claimants lose that amount of recovery either through price dilution or through bricked claims.

### Likelihood Explanation
Requires: (a) instant withdrawals enabled and at least one paid-and-claimed instant receipt in the epoch, and (b) a borrower default in that same epoch while some receipt basis remains unfunded. Both are normal-mode occurrences (instant mode, then `stopEpochWithDuration`/`_handleBorrowerDefault`); no privileged misbehavior is needed. The stale-counter state is created by the ordinary, intended claim flow — no guard (`_ensureDefaultRecoveryInitialized`, skim, flags) resets `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` on a successful claim, and the revert path in `_claimDefaultedInstantWithdrawRequest` (`instantWithdrawsRequests[_user] -= claimBasis` underflowing for the already-paid user) additionally bricks that user's claim wrapper.

### Recommendation
When a funded instant withdrawal is claimed, clear the per-epoch accounting symmetrically:

```solidity
// in claimInstantWithdrawRequest, after reading `amount`
uint256 currentEpoch = epochNumber;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] -= amount; // or track claim epoch explicitly
instantWithdrawClaimsByEpoch[currentEpoch] -= amount;
instantWithdrawsRequests[_user] = 0;
```

Note the receipt must be attributed to the epoch in which it was requested (which may differ from `epochNumber` at claim time if requests can be claimed across an epoch boundary); storing the request epoch per user (like `lastWithdrawRequest` for normal withdrawals) may be needed. Alternatively, exclude already-claimed receipts in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` by tracking a separate "outstanding instant claims" per-epoch counter that is decremented on claim.

### Proof of Concept
Foundry fork test sketch (against a live IdleCDOEpochVariant + IdleCreditVault deployment):

```solidity
function test_StaleInstantBasisCorruptsRecovery() public {
    // 1. Epoch N running with allowInstantWithdraw; pool funded.
    // userA deposits AA, requests instant withdraw of X.
    vm.prank(cdo);
    // IdleCDOEpochVariant.getInstantWithdrawFunds -> requestInstantWithdraw(X, userA)
    // startEpoch/collectInstantWithdrawFunds funds it:
    //   pendingInstantWithdraws -= X (now back to include only userB's Y below)
    // userA claims:
    vm.prank(cdo);
    vault.claimInstantWithdrawRequest(userA);
    // ASSERT BUG: stale per-epoch basis remains
    assertEq(vault.instantWithdrawsRequestsByEpoch(userA, epochN), X);      // not cleared
    assertEq(vault.instantWithdrawClaimsByEpoch(epochN), X + Y);            // still counts paid X

    // 2. userB has an unfunded instant request Y (pendingInstantWithdraws == Y > 0).
    // 3. Borrower defaults in epoch N -> CDO calls finalizeDefaultRecovery.
    //    basis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochN]  (includes paid X)
    //    prefundedReserve = (X + Y) - Y = X  -> phantom X added to reserve
    // 4. Recovery claims:
    //    - recoveryPrice diluted by X / totalBasis -> all claimants underpaid
    //    - after real reserve drained, last claimant reverts on
    //      defaultRecoveryReserve -= amount underflow -> residual funds frozen
    //    - userA's claimInstantWithdrawRequest also reverts on
    //      instantWithdrawsRequests[userA] -= X underflow (defensive, but shows
    //      the counter desync)
}
```

Key assertions proving the broken invariant ("one receipt, one payout"; reserve fully backed): `instantWithdrawClaimsByEpoch[epochN]` exceeds the sum of live `instantWithdrawsRequests`, `defaultRecoveryReserve` exceeds `underlyingToken.balanceOf(strategy)`, and a later `claimInstantWithdrawRequest`/`claimWithdrawRequest` for an unpaid claimant reverts.
