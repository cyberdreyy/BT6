### Title
Permissionless `lending_pool_emissions_deposit` allows sandwich-deposit theft of same-bank emissions rewards - ([File: programs/marginfi/src/instructions/marginfi_group/configure_bank.rs])

### Summary
`lending_pool_emissions_deposit` distributes an injected reward amount to bank depositors by raising `asset_share_value` in a single lump-sum calculation using the `total_asset_shares` value that exists *at the moment the instruction executes*. Because the instruction is explicitly documented as permissionless, and Solana allows composing multiple instructions atomically (or ordering transactions within a slot), an attacker can deposit a large amount into the bank immediately before an emissions-funding transaction and withdraw immediately after, capturing a pro-rata slice of the reward with zero net principal cost — the same "sandwich a reward-distribution event with deposit/withdraw" bug class described in the external Beedle `Staking.sol` report.

### Finding Description
`lending_pool_emissions_deposit` computes the reward distribution like this: [1](#0-0) 

1. `total_asset_shares` is read once, at call time.
2. `bank.accrue_interest(...)` runs (updates interest to current time only, not related to the emissions amount).
3. `amount` tokens are transferred into the liquidity vault.
4. `total_assets = bank.get_asset_amount(total_asset_shares)` is computed and `amount` is added to it.
5. `asset_share_value = (total_assets + amount) / total_asset_shares`.

This is exactly the "instantaneous snapshot" distribution pattern described in the report: the reward is split across *whatever* `total_asset_shares` exists at the instant of the call, without any time-weighting of how long depositors have held their shares. The patch notes explicitly confirm this instruction is permissionless and open to any caller providing a funding token account: [2](#0-1) 

Since Solana lets a single transaction execute an ordered sequence of instructions atomically (deposit → emissions_deposit → withdraw, or deposit → wait one slot for the funder's emissions tx → withdraw next slot), a bad actor can:
1. Deposit a large amount `X` into the bank, inflating `total_asset_shares` by `shares_X`.
2. Let/force the `lending_pool_emissions_deposit(amount)` call execute (either by immediately following a known/pending emissions funding transaction, or in the same atomic transaction if the attacker themselves also controls the funding source of `amount` in a batch with other unrelated legitimate funders, or more realistically by observing a mempool/upcoming emissions-funding transaction and sandwiching it).
3. Withdraw `X` immediately afterward, in a `lending_account_withdraw` instruction.

Because `shares_to_burn` for the withdrawal is computed from the (now inflated) `asset_share_value`, the attacker recovers their full principal `X` plus their pro-rata share of `amount`, at zero net cost — mirroring the report's "TKN in == TKN out" cost-free attack. The dilution comes directly out of the legitimate, long-term depositors' expected reward share, since the fixed `amount` is now divided across a larger `total_asset_shares` denominator that temporarily includes the attacker's shares.

### Impact Explanation
This allows any unprivileged user to redirect a portion of a legitimately funded reward/emissions payment away from genuine long-term depositors and to themselves, at no cost (a flash-loan-funded deposit works equally well since the deposited principal is fully recoverable). This is a real-value redirection with financial effect on other users' rewards, satisfying the "value redirection" / "exploitable misvaluation" criteria. Because `lending_pool_emissions_deposit` can carry meaningful token amounts (this is one of the officially supported reward-distribution mechanisms for wrapped/partner banks), the magnitude of value stolen scales with the emissions amount and the attacker's available capital (or flash-loan capacity) relative to existing bank TVL.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: the instruction is permissionless by design (any signer can call it), emissions-funding transactions are typically not secret (partners/admins likely call this on a schedule, and Solana transactions are visible in the mempool/leader schedule before finalization), and depositing/withdrawing large amounts from a bank is a normal, unrestricted user action with no cooldown or time-lock. An attacker only needs enough capital (or a flash loan) to temporarily dominate `total_asset_shares` at the moment the emissions call lands.

### Recommendation
- Add a minimum holding-period / time-weighted mechanism before shares are eligible to receive a lump-sum emissions distribution (e.g., only apply proportional emissions based on shares held over the accrual window rather than an instantaneous snapshot).
- Alternatively, restrict `lending_pool_emissions_deposit` to a privileged caller (emissions admin) executed within the same atomic transaction as a Solana feature that guarantees no attacker instructions can be interleaved (this alone doesn't prevent same-slot sandwiching, so a time/rate-limit is still recommended).
- Consider requiring deposits to "vest" for a minimum number of slots before being eligible for pro-rata emissions capture, or snapshot `total_asset_shares` from a prior slot rather than the current instruction's live state.

### Proof of Concept
Given the on-chain math above, the following sequence (analogous to the Beedle Foundry POC) demonstrates the exploit conceptually:
1. Attacker calls `lending_account_deposit` with a large amount `X` into bank `B`, inflating `total_asset_shares`.
2. Emissions funder (in the very next instruction of the same tx, or the very next transaction in the same slot) calls `lending_pool_emissions_deposit(amount)` on bank `B`, per [3](#0-2) .
3. `asset_share_value` rises for ALL current shares, including the attacker's freshly minted `shares_X`.
4. Attacker immediately calls `lending_account_withdraw` for their full position, recovering `X` plus `amount * shares_X / total_asset_shares` — a slice of the emissions that should have gone entirely to the pre-existing depositors.

This cannot be fully confirmed against a live Foundry/Anchor test in this session (index size limits prevented retrieving the complete `bank.rs` `get_asset_amount`/`accrue_interest` implementations and the full `LendingPoolEmissionsDeposit` `Accounts` struct to verify there is no additional time-lock guard). A Devin session with full repo access should be used to write an integration test analogous to `emissions_same_bank_deposit_updates_asset_share_value` in `programs/marginfi/tests/misc/emissions_deposit.rs` but adding an attacker deposit immediately before the emissions call and a withdrawal immediately after, to empirically confirm the captured share of emissions and rule out any unseen mitigations (e.g., a cooldown check in `BankAccountWrapper` or `validate_bank_state`).
```rust
pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();
```

```rust
async fn emissions_same_bank_deposit_updates_asset_share_value() -> anyhow::Result<()> {

    let depositor_b_usdc = test_f.usdc_mint.create_token_account_and_mint_to(60).await;
```
