### Title
Stale/duplicate weight counting in `StackerDBListener` block-response tally lets a single signer's rejection weight persist after it accepts, corrupting the approve/reject weight partition - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::handle_block_response` (the code processing `BlockResponse::Accepted`/`BlockResponse::Rejected` messages from signers) tracks whether a signer's weight has already been counted toward `total_weight_approved` / `total_weight_rejected` using **two different membership tests on two different collections**: the accept path gates on `block.gathered_signatures.contains_key(&slot_id)` while the reject path gates on `block.responded_signers.insert(slot_id)`. Because these two sets are not kept in sync with each other, a single signer that sends a `Reject` for a block and later sends an `Accept` for the same block (both fully valid, self-signed messages sent over the signer's own StackerDB slot) has its weight counted into **both** `total_weight_rejected` and `total_weight_approved`, and the stale `total_weight_rejected` contribution is never removed.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- Accept path [1](#0-0)  increments `total_weight_approved` only `if !block.gathered_signatures.contains_key(&slot_id)`, then unconditionally does `block.gathered_signatures.insert(slot_id, signature)` and `block.responded_signers.insert(slot_id)`.
- Reject path [2](#0-1)  increments `total_weight_rejected` only `if block.responded_signers.insert(slot_id)` (i.e., only the first time this slot is seen in `responded_signers` at all, whether from a prior accept or a prior reject).

Because the gating set for "already counted" differs between the two branches (`gathered_signatures` vs `responded_signers`), the two weight tallies are not mutually exclusive partitions of signer weight the way the surrounding logic assumes:

1. Signer sends `Reject` first: `responded_signers.insert(slot)` succeeds → `total_weight_rejected += w`.
2. The same signer later sends `Accept` for the same `signer_signature_hash`: `gathered_signatures.contains_key(slot)` is `false` (never touched by the reject path) → `total_weight_approved += w` is also applied, and `gathered_signatures`/`responded_signers` are updated. The signer's weight `w` is now counted in **both** `total_weight_approved` and `total_weight_rejected` for the same block, and nothing ever decrements the earlier `total_weight_rejected` contribution.

This directly parallels the hashconsing CVE's root cause: an aggregate/consensus data structure (there, the `HConsed`/hash-consing table; here, the accept/reject weight tally) is only sound if the identity check used to dedupe entries is applied consistently. Using two different, unsynchronized "already seen" predicates (`gathered_signatures` for one side, `responded_signers` for the other) for what should be a single per-signer, per-block state machine breaks that invariant, corrupting the aggregated state exactly like Send/Sync being granted to `HConsed<T>` without checking `T`'s real thread-safety broke the hash-consing invariant.

The rejection-tally threshold check `block.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` [3](#0-2)  uses this now-inflated, never-decayed `total_weight_rejected`, so it fires `cvar.notify_all()` for global rejection using weight that no longer reflects the current, live opinion of the signer set (the flip-flopping signer has since accepted).

### Impact Explanation
This is a High-severity liveness issue matching the allowed impact class "a signer [set] wedged into never signing valid blocks" at the tally level: a single signer (needs only its own key/slot — no majority) that legitimately changes its mind from reject to accept leaves a permanent, stale "rejected" weight contribution attributed to it. Combined with genuine rejections from other signers, this stale weight can push `total_weight_rejected` past the 30%-blocking threshold and cause the coordinator to treat a block as globally/irrecoverably rejected even though the actual, current signer sentiment (including the flipped signer) would have permitted acceptance — wedging the miner into resending/backing off unnecessarily. It also generally corrupts the approve/reject weight bookkeeping that downstream logging, monitoring, and (depending on ordering) `get_block_status` decisions in `signer_coordinator.rs` rely on for the "aggregated-weight vs verified-accepts" equality.

### Likelihood Explanation
Requires only a single signer (one StackerDB slot) sending two ordinary, validly-signed `BlockResponse` messages (`Reject` then `Accept`) for the same block — well within a normal signer's own control and consistent with legitimate re-evaluation flows already documented in the signer's own state machine (e.g., a signer refusing to sign due to a conflict and later signing once the conflict goes stale, as described in `docs/signer-flows.md` sections 5–6). No majority collusion, no external key, and no protocol violation is needed to trigger the divergent bookkeeping.

### Recommendation
Use a single, unified per-slot/per-block "final vote" tracking structure (e.g., one `HashMap<slot_id, BlockResponseKind>`) instead of two independently-gated collections (`gathered_signatures` vs `responded_signers`), so that a slot's weight is (a) counted exactly once regardless of which response type first arrives, and (b) properly moved from one tally to the other (decrementing the old bucket, incrementing the new one) when a signer's vote changes, rather than allowed to accumulate in both.

### Proof of Concept
1. Node broadcasts a block proposal; signer S (slot `k`, weight `w`) sends `BlockResponse::Rejected` for `signer_signature_hash` H. `responded_signers` gains `k`; `total_weight_rejected += w`.
2. Signer S later (validly, per its own re-evaluation logic) sends `BlockResponse::Accepted` for the same H with a fresh, correctly verified signature.
3. In the accept handler, `gathered_signatures.contains_key(&k)` is `false` (untouched by step 1), so `total_weight_approved += w` executes.
4. Result: `total_weight_rejected` still includes `w` from step 1 even though S has since accepted; `total_weight_approved` also includes `w`. `total_weight_rejected` never decreases, so it can combine with other signers' genuine rejections to cross the 30%-blocking threshold and trigger a "globally rejected" signal for a block that current signer sentiment would otherwise approve. This can be observed directly by instrumenting/logging `block.total_weight_approved` and `block.total_weight_rejected` around [1](#0-0)  and [2](#0-1)  while replaying the Reject→Accept sequence for one signer's slot.
