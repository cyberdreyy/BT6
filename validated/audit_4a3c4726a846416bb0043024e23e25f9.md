### Title
Missing bounds check on `program_id_index` causes panic/DoS in `parse_ui_instruction` used by `jsonParsed` RPC transaction encoding - (File: `transaction-status/src/lib.rs`)

### Summary
`parse_ui_instruction` and its helper `make_ui_partially_decoded_instruction` index directly into `account_keys` using `instruction.program_id_index` without first validating that the index is within bounds, unlike every other instruction parser in the same crate (`parse_system`, `parse_address_lookup_table`, `parse_associated_token`, etc.) which explicitly check `instruction.accounts.iter().max() < account_keys.len()` before indexing.

### Finding Description
`parse_ui_instruction` unconditionally does: [1](#0-0) 
```
let program_id = &account_keys[instruction.program_id_index as usize];
```
and if parsing fails, falls back to `make_ui_partially_decoded_instruction`, which does the same unchecked indexing: [2](#0-1) 

By contrast, every parser reachable from `parse()` (e.g. `parse_system`, `parse_address_lookup_table`, `parse_associated_token`) defensively checks the max account index against `account_keys.len()` before indexing, explicitly noting "Runtime should prevent this from ever happening" — i.e., these checks exist specifically as defense-in-depth against exactly this class of indexing panic: [3](#0-2) [4](#0-3) 

`parse_ui_instruction` has no such guard for `program_id_index`, meaning any code path that constructs a `CompiledInstruction`/`AccountKeys` pair where `program_id_index >= account_keys.len()` will panic with an index-out-of-bounds, rather than returning an error.

### Impact Explanation
A Rust slice-index panic in the RPC-serving thread on a `jsonParsed`-encoded `getTransaction`/`getBlock` request would crash or abort request handling. Whether this is exploitable by an unprivileged caller depends on whether an attacker can get a stored/replayed transaction with an out-of-range `program_id_index` (and matching `account_keys` length) to reach this function — this is normally prevented by message sanitization at ingestion (`sanitize()` on `Message`/`VersionedMessage`) before a transaction is ever accepted or executed, so in the primary path this defensive check should be unreachable in the same way the comment in the other parsers states "Runtime should prevent this from ever happening."

### Likelihood Explanation
Low-to-uncertain. I could not confirm within the available index a concrete unprivileged path (e.g. crafted/malformed stored blockstore entry, replay of an old block format, or an inconsistent versioned message with address-table lookups) that bypasses `Message::sanitize`/`VersionedMessage` validation and still reaches `parse_ui_instruction` with an out-of-bounds `program_id_index`. All other parsers treat this as belt-and-suspenders protection against a runtime invariant that "should" already hold, suggesting the authors considered such out-of-bounds indices theoretically reachable (perhaps via malformed/legacy blockstore data on `getConfirmedBlock`/`getTransaction` for historical slots) but did not add the same guard to `parse_ui_instruction`.

### Recommendation
Add the same defensive bounds check used elsewhere in the crate to `parse_ui_instruction` (and `make_ui_partially_decoded_instruction`) before indexing `account_keys` with `program_id_index`, returning a parse error (falling through to partially-decoded/raw rendering) instead of panicking, e.g.:
```rust
if (instruction.program_id_index as usize) >= account_keys.len() {
    // return an error / raw instruction instead of indexing
}
```

### Proof of Concept
I was unable to construct or verify a concrete unprivileged trigger path within the scope of this analysis — this would require confirming whether malformed historical blockstore-stored transactions (predating current sanitization rules) or `ledger-tool`/RPC block-decoding paths can produce a `CompiledInstruction` with `program_id_index >= account_keys.len()` that reaches `parse_ui_instruction` via `map_inner_instructions`/`parse_ui_inner_instructions` or top-level instruction encoding. Given the uncertainty in exploitability through the standard `getTransaction`/`getBlock` RPC path (message sanitization should reject such inputs before persistence), this finding should be treated as a **defense-in-depth gap** rather than a confirmed exploitable vulnerability. Further investigation would require locating the exact call sites in `solana_transaction_status_client_types::UiTransaction`/`UiMessage` encoding and the RPC handlers in `rpc/src/rpc.rs` that invoke `parse_ui_instruction`, which the index size limits prevented me from fully tracing in this session — a Devin agent with full repo access should verify this before treating it as a confirmed finding.

pub fn parse_ui_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiInstruction {
    let program_id = &account_keys[instruction.program_id_index as usize];
    if let Ok(parsed_instruction) = parse(program_id, instruction, account_keys, stack_height) {
        UiInstruction::Parsed(UiParsedInstruction::Parsed(parsed_instruction))
    } else {
        UiInstruction::Parsed(UiParsedInstruction::PartiallyDecoded(
            make_ui_partially_decoded_instruction(instruction, account_keys, stack_height),
        ))
    }
}
