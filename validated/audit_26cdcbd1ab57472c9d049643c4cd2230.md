### Title
Stale withdraw receipt escapes loss haircut: overwriting `lastWithdrawRequest` lets a loss-adjusted receipt be re-claimed at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
CVE-2026-3537 is an object-lifecycle (use-after-free) bug: an object is freed but a stale pointer still reaches it. The analog in `IdleCreditVault` is a stale withdraw receipt. When `collectWithdrawFunds` funds pending receipts at a loss-adjusted price, it stores the haircut in `lossRecoveryPriceByEpoch[epochNumber]` but leaves each user's basis inside the aggregate `withdrawsRequests[_user]`. The loss haircut is only reachable while `lastWithdrawRequest[_user]` still points at the loss epoch. A second `requestWithdraw` silently overwrites `lastWithdrawRequest[_user]` (line 282), orphaning the loss-adjusted receipt, which is then paid at par by `_claimFundedWithdrawRequest`.

### Finding Description
`collectWithdrawFunds` handles underfunded stop-epoch repayments by writing `lossRecoveryPriceByEpoch[epochNumber]` and pulling only `_amount < pendingBasis` (`IdleCreditVault.sol:411-430`). The per-user claim for that haircut lives only in `_claimLossAdjustedWithdrawRequest`, which indexes `lossRecoveryPriceByEpoch` with `lastWithdrawRequest[_user]` (lines 789-801). `_clearWithdrawClaimForEpoch` removes that epoch's slice from `withdrawsRequests[_user]` only when it is actually reached (lines 815-819).

In `requestWithdraw`, `lastWithdrawRequest[_user] = currentEpoch` is written unconditionally, and `withdrawsRequests[_user] += _amount` aggregates across epochs (lines 282-294). So:

1. Epoch N: user requests withdraw of `X`. `stopEpoch` funds receipts at a loss; `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL`.
2. Buffer/epoch N+1: user (or a new tranche position) calls `requestWithdraw` again. `lastWithdrawRequest[user]` becomes N+1; the epoch-N slice stays in `withdrawsRequests[user]`.
3. Epoch N+2: `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[N+1] == 0` and returns; `_claimFundedWithdrawRequest` then pays the **full** aggregate `withdrawsRequests[user]` (including the epoch-N basis that was only funded at `p`) at par (lines 338-349), gated only by `epochNumber > lastWithdrawRequest` (line 326).

The invariant "one receipt, haircut-adjusted payout" is broken: the freed-at-a-discount receipt object survives via the aggregate ledger.

### Impact Explanation
The attacker claims `(1 - p) * basis_epochN` more underlying than was funded for their epoch-N receipt. Since `pendingWithdraws` was zeroed in `collectWithdrawFunds`, the excess comes directly from strategy-held underlying reserved for other users' funded claims and default-recovery reserve — direct theft/insolvency of other LPs' withdrawals, quantified as the epoch-N `pendingLoss` share attributable to the attacker (`_lossAmount * userBasis / totalBasis` per `previewLossAdjustedWithdrawFunds`, lines 454-459).

### Likelihood Explanation
Requires only unprivileged actions: two `requestWithdraw` calls (one in the loss epoch via `IdleCDOEpochVariant.requestWithdraw`, one after) and a `claimWithdrawRequest`, plus honest manager/owner calling `stopEpochWithDuration`/`collectWithdrawFunds` at a loss — a normal, expected recovery flow. No privileged misbehavior needed. The only precondition is a partial-loss stop epoch while the user holds a pending receipt, which is exactly when users are most likely to re-request.

### Recommendation
In `requestWithdraw`, before overwriting `lastWithdrawRequest[_user]`, settle or reject: either revert if `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` (and the epoch slice hasn't been claimed), or eagerly clear that epoch's basis from `withdrawsRequests`/`withdrawsRequestsByEpoch` and record the discounted payout so it can't be re-claimed at par. Alternatively, iterate all epochs with nonzero `withdrawsRequestsByEpoch` having a `lossRecoveryPriceByEpoch` in `_claimLossAdjustedWithdrawRequest` instead of relying on `lastWithdrawRequest` alone.

    _requestWithdrawWithUser(attacker, tranches);

    // stopEpochWithDuration realizes a loss; borrower funds only part

    uint256 epochN = strategy.epochNumber() - 1;
    assertLt(strategy.lossRecoveryPriceByEpoch(epochN), RECOVERY_FULL);

    // buffer: attacker requests a second (small) withdraw -> overwrites lastWithdrawRequest
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(attacker, smallTranches);

    // next epoch passes so funded-claim gate opens
    _stopCurrentEpochWithApr(apr);

    // claim: loss-adjusted path finds lossRecoveryPriceByEpoch[newEpoch] == 0,
    // funded path pays full aggregate withdrawsRequests[attacker] at par

    vm.prank(address(cdoEpoch));

    uint256 haircutBasis = strategy.withdrawsRequestsByEpoch(attacker, epochN); // before clearing

    assertGt(paid, expectedFundedAmount, "loss haircut bypassed");

Key assertions: `lossRecoveryPriceByEpoch[epochN] > 0` yet the epoch-N basis is paid at `RECOVERY_FULL`, and the strategy's underlying balance is drained below the sum of remaining funded claims.
