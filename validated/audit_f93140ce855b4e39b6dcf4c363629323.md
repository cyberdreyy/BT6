### Title
Stale confirmations from deleted multisig members are still counted toward the execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts the number of *stored* confirmations against `num_confirmations` without re-validating that each confirming member is still a current member of the multisig. When a `DeleteMember` request is executed, `delete_member` only purges requests/`num_requests_pk` entries created *by* the deleted member, but never scans `self.confirmations` to strip that member's confirmation from *other* pending requests that member had previously confirmed. This breaks the equality "confirmations counted == confirmations from currently-live members", allowing a request to execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
`confirm()` [1](#0-0)  only checks `confirmations.len() as u32 + 1 >= self.num_confirmations` and then executes the request — it never re-checks that each account/key already present in the stored `confirmations: HashSet<String>` is still `self.members.contains(...)`.

`delete_member()` [2](#0-1)  removes the member from `self.members`, deletes any *requests the removed member itself created* (`r.member == member`), and clears `num_requests_pk` for that member — but it does not iterate `self.confirmations` to remove the deleted member's confirmation string from other members' pending requests.

Consequently, a confirmation recorded by member `Y` on request `A` (created by member `X`) remains in `confirmations` even after `Y` is removed via a separate `DeleteMember` request. When a later, distinct, currently-live member `Z` confirms request `A`, the stale count from `Y` is added to the live count, letting the request execute (e.g. `Transfer`, `DeployContract`, `AddKey`, `FunctionCall`) even though the number of *currently valid* member confirmations is one less than `num_confirmations`.

### Impact Explanation
This crosses the threshold-authorization boundary that the multisig is supposed to guarantee: a `k`-of-`n` request should only execute when `k` *live* members approved it, but here a request can execute with only `k-1` live approvals plus one stale approval from a removed member. Since multisig contracts on NEAR directly custody NEAR balances and control full-access keys, this can result in a `Transfer`, `AddKey`/`DeployContract` (account takeover), or arbitrary `FunctionCall` action being authorized below the documented signature threshold — matching the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
Exploitation requires the sequence: (1) a request is confirmed by fewer than `num_confirmations` members, (2) one of those confirming members is later removed via a `DeleteMember` action (a legitimate, expected multisig operation, e.g. offboarding a compromised or departing signer), and (3) another live member later confirms the still-pending request. This is a realistic operational sequence for any long-lived multisig that rotates members while requests are outstanding — no special privilege beyond normal, in-scope multisig actions is needed, and no external/foundation intervention is required.

### Recommendation
When executing `DeleteMember`, iterate all entries in `self.confirmations` (not just requests created by the removed member) and remove the deleted member's identifier from every confirmation set. Alternatively, in `confirm()`/`execute_request()`, revalidate that every entry in the stored `confirmations` set for a request is still contained in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize multisig with `members = [X, Y, Z]`, `num_confirmations = 3`.
2. `X` calls `add_request_and_confirm` for a `Transfer` request `A` → confirmations = `{X}` (1/3).
3. `Y` calls `confirm(A)` → confirmations = `{X, Y}` (2/3, not yet executed).
4. Separately, members confirm and execute a `DeleteMember { member: Y }` request; `delete_member` removes `Y` from `self.members` and only cleans up requests where `r.member == Y` — request `A` (created by `X`) is untouched, so `confirmations` for `A` still contains `Y`.
5. `Z` calls `confirm(A)` → `confirmations.len() + 1 == 3 >= num_confirmations`, so `execute_request` fires the `Transfer`, even though only `X` and `Z` are current live members who actually approved it (`Y`'s approval is stale/removed-member). [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
