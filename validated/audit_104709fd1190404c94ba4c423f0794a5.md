`CleanGitConfig` is a Runner-side option (`b.opts.gitCleanConfig`, set via `functions/concrete/builder/builder.go` line 178), not a per-job/pipeline variable, so an unprivileged pipeline author cannot toggle it directly. This limits the attacker-controlled precondition somewhat, but the code path itself still has a real logic gap worth analyzing on its own merits.

### Title
Stale/malicious `.git/config` `include.path` entries persist across jobs on the "existing repo" reuse path - (File: `functions/concrete/run/stages/get_sources.go`)

### Summary
`gitInit` only reconfigures `include.path` in `.git/config` when it detects an existing repo (i.e. `git remote add origin` fails), using `git config --replace-all include.path <absExtConfig> <pattern>` where `pattern = "^" `... actually `regexp.QuoteMeta(filepath.Base(extConfigFile)) + "$"` (no leading `^`), an unanchored, suffix-only regex. [1](#0-0)  Because the pattern only matches values that literally end in the basename `.gitlab-runner.ext.conf`, any pre-existing `include.path` entry pointing elsewhere (a different filename, or a value crafted by a prior job/attacker) is left completely untouched by `--replace-all`, and the new legitimate entry is simply appended alongside it.

### Finding Description
The `gitInit` "existing repo" branch is reached whenever `git remote add origin` fails, which happens on persistent build directories reused across jobs (shell/ssh/custom executors with `GIT_STRATEGY=fetch` against a project working directory that survives between job runs). [1](#0-0)  `cleanupGitState` only strips `.git/config` (and hooks) when `CleanGitConfig` is true; otherwise stale config content from a prior job is preserved verbatim. [2](#0-1) 

`git config --replace-all <name> <value> <value-pattern>` only replaces lines whose *value* matches `<value-pattern>`; if no existing line matches, it appends a new line instead of removing/overriding the non-matching ones. The pattern used here, `regexp.QuoteMeta(filepath.Base(extConfigFile)) + "$"`, matches only paths that literally end in `.gitlab-runner.ext.conf`. Any other `include.path` line already present in `.git/config` — e.g. one written by a previous job pointing at an attacker-influenced file (an arbitrary absolute path, a path in the working tree, or a path under a differently-named tmp dir from a prior job run) — will not match this pattern and will therefore survive the `--replace-all` call untouched, sitting alongside the newly appended current-job entry. Git processes all `include.path` directives in order, so both configs get sourced; a malicious leftover include can set `core.hooksPath`, `credential.helper`, `url.<x>.insteadOf`, `http.proxy`, etc., and those settings remain active for the current job's git operations even though Runner believes it "fixed" the config for the current job.

This is a persistence/isolation gap in the config-repair logic itself, independent of whether `CleanGitConfig` is user-controlled: the repair logic silently coexists with, rather than removing, non-matching stale `include.path` entries.

### Impact Explanation
On any environment that reuses a build directory across job runs (shell executor, ssh executor, custom executor without full workspace wipe) with `CleanGitConfig=false` (its behavior with default/legacy settings) and `GIT_STRATEGY=fetch`, an attacker who can run one job with write access to the shared working directory (e.g. a prior job on the same runner, or a job using `pre_clone_script`/similar to write directly into `.git/config`) can plant an `include.path` entry that does not end in `.gitlab-runner.ext.conf`. That entry persists into subsequent jobs sharing the same working directory, letting the attacker override git behavior (hooks path leading to code execution during subsequent `git checkout`/`submodule update`, credential-helper hijack to exfiltrate the next job's `CI_JOB_TOKEN`, or URL redirection via `insteadOf`) for jobs that run after them on the same executor/working directory.

### Likelihood Explanation
Requires: (1) a shared/persistent working directory across jobs (true by default for shell/custom/ssh executors, and even for some Docker-based setups reusing named volumes), (2) `CleanGitConfig` disabled (a Runner config choice, not attacker-controlled), and (3) the "existing repo" branch being taken (remote already exists — the common case for `fetch` strategy on a reused checkout). Since `CleanGitConfig` is admin/runner-config-controlled rather than pipeline-controlled, the primary attacker-controlled leg is planting the malicious `.git/config` content itself, which requires a preceding job run with filesystem write access to the same working directory. This is a plausible same-project, sequential-job scenario (e.g. two jobs from different branches/MRs of the same project scheduled onto the same runner slot) rather than a purely theoretical one.

### Recommendation
Anchor the match to the current `include.path` semantics more robustly: instead of matching by basename suffix, remove/replace **all** `include.path` entries whose value does not resolve to the same absolute path used for the current job's `extConfigFile` (or, simpler, strip all existing `include.path` lines from `.git/config` before adding the fresh one), rather than relying on a regex that only matches one specific basename. Alternatively, always fully clean and rewrite `.git/config`'s `[include]` section on the existing-repo path regardless of `CleanGitConfig`, since stale git config is a cross-job auth/execution risk, not merely a hygiene setting.

### Proof of Concept
Go integration test outline in `functions/concrete/run/stages/get_sources_test.go`:
1. Create a working dir with an existing `.git` repo containing a `[include]` `path = /tmp/evil/other.conf` entry (simulating a prior job's leftover config), where `/tmp/evil/other.conf` sets `core.hooksPath = /tmp/evil/hooks`.
2. Run `GetSources.Run` with `GitStrategy=fetch`, `CleanGitConfig=false`, against this working dir (forcing the "existing repo" branch by pre-creating `origin` remote).
3. After the run, read `.git/config` and assert:
   - It still contains the `include.path = /tmp/evil/other.conf` line (proving it was not removed), and
   - It also contains the new `include.path = <tmpDir>/.gitlab-runner.ext.conf` line.
4. Assert that `git config --get core.hooksPath` resolves to `/tmp/evil/hooks`, demonstrating the malicious include remains active for the current job's git operations.
