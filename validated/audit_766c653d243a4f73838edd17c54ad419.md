### Title
Response cache key omits `Mtls` credentials, allowing mTLS-authenticated content to be served to non-mTLS requests for the same URL - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
`responseCache` keys cached `OutboundHTTPRequest`/`OutboundHTTPResponse` pairs solely by `req.Hash()`, which per the type's own doc comment is derived from "method, URL, headers, body, workflowOwner" — the `Mtls` field is not part of the key. Because `gatewayHandler.send` (`core/services/gateway/handlers/capabilities/v2/http_handler.go:297-337`) treats `req.Mtls` as fully attacker/node-supplied ("all fields set on the request come from untrusted nodes", line 327-328), a request carrying a valid client certificate and one without any certificate can collide on the same cache entry.

### Finding Description
`makeOutgoingRequest` (`http_handler.go:403-454`) unmarshals the entire `OutboundHTTPRequest`, including `Mtls`, directly from the untrusted node message via `json.Unmarshal(*resp.Result, &req)`. If `req.CacheSettings.MaxAgeMs > 0`, the request/response pair is stored and retrieved through `responseCache.Fetch`/`Set`, both of which use `req.Hash()` as the sole cache key: [1](#0-0) [2](#0-1) 

The comment explicitly documents the hash composition as "method, URL, headers, body, workflowOwner" — no mention of `Mtls`. `gatewayHandler.send` itself instantiates a throwaway mTLS client specifically to avoid leaking authenticated connections between users: [3](#0-2) 

But this per-connection isolation is undermined by the cache layer: once an mTLS-authenticated fetch for a given `(method, URL, headers, body, workflowOwner)` tuple is cached, any subsequent request with the identical tuple — even one that supplies no `Mtls` credentials at all — will hit the same cache entry and receive the previously mTLS-gated response, because `Hash()` cannot distinguish the two requests. The existing test suite (`response_cache_test.go:94-176`) validates that `WorkflowOwner`, `Method`, and `URL` differentiate the hash, and that `CacheSettings`/`WorkflowID` do not — but there is no test asserting that presence/absence of `Mtls` affects `Hash()`, consistent with it being excluded.

### Impact Explanation
This is a response-cache-poisoning / cross-request credential confusion bug: content that should only be obtainable by presenting a valid client certificate to an mTLS-gated endpoint becomes cacheable and retrievable by any subsequent caller (potentially a different node, workflow, or trigger invocation) that reuses the same method/URL/headers/body, without ever presenting mTLS credentials. This matches the Chainlink bounty class of authentication bypass / unauthorized disclosure of gated data via request impersonation through the shared gateway cache.

### Likelihood Explanation
The precondition is only the ability to construct/relay an `OutboundHTTPRequest` for an HTTP Action with `CacheSettings.Store: true`/`MaxAgeMs > 0`, and an `Mtls` block with a valid cert for the target endpoint — reachable by any workflow authoring an HTTP action capability call whose fields are unmarshaled straight from node-relayed JSON-RPC without validation of `Mtls` against the requester's authorization. No admin/operator access is required; only crafting two capability requests (one with `Mtls`, one without) to the same URL/method/headers/body is needed, making this fully reproducible in a unit test.

### Recommendation
Include a fingerprint of the `Mtls` credential material (or simply a boolean/hash indicating mTLS was used, and ideally per-cert) as part of `OutboundHTTPRequest.Hash()`, so an mTLS-authenticated fetch and a non-mTLS fetch (or fetches using different certificates) can never collide on the same cache key. Alternatively, disable caching (`Store`) entirely for requests carrying `Mtls`.

### Proof of Concept
Add a test to `response_cache_test.go` analogous to `TestRequestHash`:
1. Build `req1 := createTestRequest("GET", url)` with `req1.Mtls = &gateway_common.MtlsAuth{PrivateKey: ..., Certificate: ...}`.
2. Build `req2 := createTestRequest("GET", url)` with `req2.Mtls = nil`, identical method/URL/headers/body/workflowOwner.
3. Assert `req1.Hash() != req2.Hash()` — expected to **fail** given current behavior, proving the omission.
4. Handler-level integration test: call `handler.responseCache.Set(req1, mtlsAuthedResp)` then `handler.responseCache.Fetch(ctx, req2, fetchFn, false)` and assert the mTLS-gated response is returned even though `req2` has no `Mtls`, confirming cross-credential leakage through the cache.

func (h *gatewayHandler) send(ctx context.Context, httpReq network.HTTPRequest, req gateway_common.OutboundHTTPRequest) (*network.HTTPResponse, error) {
	if req.Mtls == nil {
		return h.httpClient.Send(ctx, httpReq)
	}

	if h.httpClientFactory == nil {
		return nil, errors.New("nil http client factory, cannot make mtls request")
	}

	// Instantiate a throwaway HTTP client with the provided Mtls client certificate provided.
	// We do this to ensure that we don't accidentally leak auth'd connections to other users.
	// Note: this isn't a DOS vector because
	// a) we have a global rate limit above which limits abuse
	// b) we apply rate limits limiting the ability of sending nodes to spam requests
	// c) we apply per-owner rate limits in the action capability in the
	// workflow node limiting the ability of users to abuse this flow by spamming Mtls requests.
	// The client enforces the mtls concurrency limit internally (on the request's
	// capped-timeout context) before delegating to the underlying transport.
	client, err := h.httpClientFactory(network.HTTPClientConfig{
		Mtls: &gateway_common.MtlsAuth{
			PrivateKey:  req.Mtls.PrivateKey,
			Certificate: req.Mtls.Certificate,
		},
		ConcurrencyLimiter: h.mtlsConcurrencyLimiter,
	})
	if err != nil {
		return nil, fmt.Errorf("failed to instantiate http client for mtls request: %w", err)
	}
