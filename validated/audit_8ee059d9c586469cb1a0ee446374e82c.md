### Title
Stale confirmations from removed multisig members are not purged, allowing a request to execute below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
The multisig contracts allow a request to be approved by `num_confirmations` distinct members before execution. However, when a member is removed via `DeleteMember` (`multisig2`) or `DeleteKey` (`multisig`), the cleanup logic only purges *requests originated by* the removed member — it does not purge *confirmations the removed member previously cast on requests created by other members*. A stale confirmation from a member who has since been revoked therefore continues to count toward the `num_confirmations` threshold, letting a pending request execute with fewer genuinely "live" approvals than the configured K-of-N policy requires.

### Finding Description
In `multisig2/src/lib.rs`, `confirm` accumulates approvals in a `HashSet<String>` keyed by member identity and executes the request once the set size reaches `num_confirmations`: [1](#0-0) 

When a member is removed, `delete_member` only removes requests where that member was the *original signer* (`r.member == member`), and only clears the confirmations map for those specific requests. Confirmations that the removed member cast on other, still-pending requests (created by different members) are left untouched: [2](#0-1) 

The equivalent legacy contract `multisig/src/lib.rs` has the identical gap in its `DeleteKey` action handler, which filters outstanding requests by `r.signer_pk == pk` only, leaving stale confirmations by that key on requests signed by others intact: [3](#0-2) 

Because of this, the binding "confirmations counted == confirmations from members who are still live members" is broken. A member's approval persists as a permanent credit toward the threshold even after that member is formally removed from `self.members` (and their access key deleted on-chain).

### Impact Explanation
Consider a 4-member, 3-of-4 multisig (A, B, C, D):
1. A creates a sensitive request `R1` (e.g., `Transfer`, `AddKey`, or `AddMember` targeting an attacker-controlled key) via `add_request`.
2. D (compromised or malicious) calls `confirm(R1)` — confirmations = {D}. B also confirms — confirmations = {D, B} (2/3, not yet executed).
3. The team detects D is compromised and legitimately removes D through a properly-confirmed `DeleteMember { member: D }` request. `delete_member` deletes D's access key and drops D from `self.members`, but because D never *created* `R1`, D's confirmation on `R1` is not cleared.
4. Later, a remaining legitimate member C confirms `R1`, believing the request now needs a fresh third live approval. But confirmations = {D, B, C} = 3, so `R1` executes — approved using D's stale, revoked confirmation.

`R1` is thereby executed having received meaningful approval from only two currently-live members (B and C), while the third "vote" belongs to an entity the team explicitly revoked. This is functionally identical to the reported Party-governance issue: a party that should no longer have standing still counts toward bypassing the intended threshold/veto safeguard. Per the impact criteria, this is a multisig request executed below the intended live-member threshold, which can move NEAR/authorize key or membership changes that were never actually approved by K currently-trusted members — Critical impact.

### Likelihood Explanation
This requires no privilege escalation beyond what a legitimate member removal process already grants: it is triggered by the normal, expected security response of removing a compromised or departing member while a request is in flight. Any multisig with more than one concurrently pending request and any membership turnover is exposed; no attacker action beyond having previously held a legitimate confirmation is needed at the moment of exploitation.

### Recommendation
- When removing a member (`delete_member` in `multisig2`, `DeleteKey` in `multisig`), iterate over *all* pending requests' confirmation sets (not just those the member created) and strip the removed member's identity/key from each.
- Alternatively, re-validate at execution time (inside `confirm`, right before comparing `confirmations.len()` against `num_confirmations`) that every entry in the confirmations set still corresponds to a current member in `self.members`, discarding stale entries before counting.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` to create `R1` (e.g. an `AddKey` action granting a new full-access key) — confirmations = {A}.
3. `D` calls `confirm(R1)` — confirmations = {A, D} (2/3).
4. Members legitimately execute a `DeleteMember { member: D }` request (reaching threshold via A, B, C), which calls `delete_member`, removing D from `self.members` and deleting D's access key — `R1`'s confirmation set is untouched because `D` was not the signer of `R1`.
5. `B` calls `confirm(R1)` — confirmations = {A, D, B} = 3 ≥ `num_confirmations`, so `R1` executes, granting a full-access key even though D was revoked before the request finished collecting live approvals.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
