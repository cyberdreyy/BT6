### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing requests to execute below the real live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` only removes the requests that were *created by* the removed member; it never scrubs that member's confirmation from `confirmations` entries belonging to requests created by *other* members. Because `confirm()` blindly counts `HashSet<String>` size without checking that each confirming string still corresponds to a live member, a request can be executed with fewer real, current confirmations than `num_confirmations` requires.

### Finding Description
The contract stores confirmations as `confirmations: LookupMap<RequestId, HashSet<String>>`, keyed independently from `members: UnorderedSet<MultisigMember>` [1](#0-0) .

When a member is removed via `delete_member`, the code only cleans up requests where `r.member == member` (i.e., requests that member *created*), and removes their `num_requests_pk` entry: [2](#0-1) 

Nothing iterates over all outstanding requests to strip the removed member's entry from `confirmations` on requests created by *other* members that this member had already confirmed. That confirmation string remains embedded in the `HashSet<String>` forever.

`confirm()` then determines execution purely by set size, with no validation that each string in the set still maps to a `members`-set entry: [3](#0-2) 

So the equality the contract is supposed to guarantee — `confirmations.len() == number of distinct live members who approved this request` — is broken. After a member is removed, `confirmations.len()` can include confirmations from accounts/keys that are no longer in `members`.

### Impact Explanation
This breaks the "confirmations counted versus live members" custody binding: a `MultiSigRequest` (which can be a `Transfer`, `AddKey`, `DeleteMember`, `FunctionCall`, etc.) can be executed with strictly fewer *current* legitimate confirmations than `num_confirmations` mandates, because a stale confirmation from an already-removed member is silently counted toward the threshold. This matches the Critical impact category "a multisig request executed below threshold" — funds can move, keys can be added, or membership can be manipulated with less real consensus than the configured `k` in the k-of-n scheme.

### Likelihood Explanation
This requires no privileged access beyond normal multisig operation: any request that receives a confirmation from a member who is subsequently removed (a routine governance action, e.g. rotating a compromised key) leaves a permanently "banked" confirmation. Any remaining members, acting entirely through the contract's normal `confirm` flow, will unknowingly execute the request below the intended threshold once enough of *them* confirm — the removed member's stale vote fills the gap. This can also be engineered deliberately by a soon-to-be-removed member who pre-confirms a pending malicious request before being removed.

### Recommendation
When removing a member in `delete_member`, iterate all active requests (not just ones created by the removed member) and strip the removed member's entry from each request's `confirmations` set (mirroring how `_registerOperatorImpl`/`_unregisterOperator` hooks were added in the referenced fix). Alternatively, validate at `confirm()` time (or right before execution) that every string in the confirmations set still corresponds to a current member of `self.members`, discounting/removing any that don't before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig created with members `{A, B, C, D}` and `num_confirmations = 3`.
2. Member `X` (some other member, e.g. `B`) creates request `R` (e.g., `Transfer`).
3. Member `A` calls `confirm(R)` → `confirmations[R] = {A}`.
4. Governance removes `A` via a separate `DeleteMember{member: A}` request/execution — `delete_member` only touches requests `A` created, not `R`; `confirmations[R]` still contains `A`. Live members are now `{B, C, D}`, threshold still 3.
5. Member `C` calls `confirm(R)` → `confirmations[R] = {A, C}`, size 2, `2+1 < 3`, not yet executed.
6. Member `D` calls `confirm(R)` → `len()+1 = 2+1 = 3 >= 3` → `remove_request` + `execute_request(R)` fires, even though only two *live* members (`C`, `D`) ever actually approved `R` — one short of the configured 3-of-n threshold. [3](#0-2) [2](#0-1)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
