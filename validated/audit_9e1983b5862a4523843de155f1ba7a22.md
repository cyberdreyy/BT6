### Title
Permissionless front-running of `InitializeNonceAccount` allows hijacking of a funded, uninitialized nonce account - (File: `programs/system/src/system_instruction.rs`)

### Summary
`initialize_nonce_account`, invoked by the System Program's `SystemInstruction::InitializeNonceAccount` handler, sets the nonce authority of a System-Program-owned account without requiring any signature from the account itself, its would-be owner, or the original funder. Any account that is writable, system-owned, in `State::Uninitialized`, and rent-exempt can be "claimed" by whoever's transaction lands first with an arbitrary `authorized` pubkey, exactly mirroring the reported class: an unprivileged initializer step that consumes value/state previously staged by a victim (funding the account) but is finalized with attacker-chosen parameters via front-running.

### Finding Description
`initialize_nonce_account` only checks that the target account is writable and currently `Uninitialized` with sufficient rent-exempt balance before writing nonce state with the caller-supplied `nonce_authority`: [1](#0-0) 

Critically, there is no check that the account itself, its creator, or any privileged party signed this specific instruction — the function never calls `is_instruction_account_signer` for the nonce account, unlike `transfer` and `transfer_with_seed` in the same module which explicitly require the `from` account to sign: [2](#0-1) 

The dispatch path for `InitializeNonceAccount` confirms this — it only validates the recent-blockhashes sysvar and rent sysvar, never checking signers or ownership of `authorized`: [3](#0-2) 

This is directly analogous to the reported bug class: a victim stages value into an account (funds it via `CreateAccount`/`CreateAccountAllowPrefund`, or simply airdrops lamports to a pre-generated address) intending to finalize it themselves in a subsequent instruction/transaction with their own chosen `authorized` key — just as the pool's initial depositor pre-approves a vault expecting `Factory.createMarket` to run with intended parameters. If the funding step and the `InitializeNonceAccount` step are not atomically bundled in the same transaction (a common pattern for pre-funded/rent-prepaid accounts, e.g. `CreateAccountAllowPrefund` explicitly documents supporting accounts that "already had rent paid... before creation"), any unrelated actor can race ahead and submit their own `InitializeNonceAccount` instruction against the same address with a `nonce_authority` of their choosing, capturing exclusive control (advance/withdraw/authorize rights) over the account and its lamports.

### Impact Explanation
Successful exploitation lets an attacker seize permanent control of another party's funded, would-be nonce account by becoming its `nonce_authority`. This is a concrete unauthorized state mutation: the attacker gains sole rights to `AdvanceNonceAccount`, `WithdrawNonceAccount` (draining lamports above rent-exemption), and `AuthorizeNonceAccount`, effectively stealing durable-nonce control and, transitively, the ability to later withdraw the account's lamports. This matches the "unauthorized fund or state mutation" bar for the accepted impact classes.

### Likelihood Explanation
Exploitability depends on whether the funding and initialization occur as separate transactions/instructions. Standard client tooling that packages `CreateAccount` + `InitializeNonceAccount` in a single atomic transaction is not affected because Solana transactions execute all instructions atomically with no interleaving. However, any workflow that separates funding from initialization (pre-funded seed accounts, `CreateAccountAllowPrefund` flows, airdrops to a pre-generated key intended for later nonce initialization, or manual/scripted multi-step flows) creates the race window described. Given `InitializeNonceAccount` performs no signer check at all, the race requires no privileged access — any ordinary transaction submitter can attempt it, making likelihood moderate and entirely dependent on client-side transaction structuring rather than any special validator privilege.

### Recommendation
Require a signature check in `initialize_nonce_account` (or in the `InitializeNonceAccount` dispatch arm) analogous to the ones already present in `transfer`/`transfer_with_seed` — e.g., require the nonce account itself (or a designated funder/owner) to be a signer of the instruction before transitioning from `Uninitialized` to `Initialized`. This closes the same class of "front-run finalization with attacker-chosen parameters" issue described in the source report, mirroring the report's own recommendation to bind the sensitive step to the legitimate initiator rather than an arbitrary caller-supplied party.

### Proof of Concept
1. Victim generates a fresh keypair `N` (nonce-account-to-be) and, in one transaction, funds `N` with rent-exempt lamports via `SystemInstruction::CreateAccount` (owner = System Program, space = `nonce::state::State::size()`), intending to send a follow-up `InitializeNonceAccount(victim_authority)` instruction in a second transaction.
2. Attacker observes the first transaction land (account `N` now exists, system-owned, `Uninitialized`, rent-exempt, writable) and, before the victim's second transaction confirms, submits their own transaction containing only `SystemInstruction::InitializeNonceAccount(attacker_authority)` with account `N` marked writable (no signature from `N` needed, per `initialize_nonce_account` at `programs/system/src/system_instruction.rs:163-211`).
3. Attacker's transaction is processed first; `N`'s state transitions to `State::Initialized(Data { authority: attacker_authority, .. })`.
4. Victim's later `InitializeNonceAccount(victim_authority)` transaction now fails with `InstructionError::InvalidAccountData` because the state is already `Initialized` (see `programs/system/src/system_instruction.rs:202-209`), while the attacker retains full authority over `N`, including the ability to withdraw its lamports via `WithdrawNonceAccount`.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
