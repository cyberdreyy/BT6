### Title
Post-default instant withdraw requests are recorded in the defaulted-epoch bucket, corrupting `instantWithdrawClaimsByEpoch` and letting a tranche holder double-count claim basis — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` has an explicit `defaultRecoveryFinalized` branch that routes post-default requests into `postDefaultRequests` at the already-haircutted price. `requestInstantWithdraw` has no equivalent branch: after default finalization it still burns CDO strategy tokens, mints a 1:1 receipt, and writes into `instantWithdrawsRequestsByEpoch[_user][epochNumber]`. Because `epochNumber` stops advancing once the pool defaults, this writes into the same bucket keyed by `defaultRecoveryEpoch` that `_claimDefaultedInstantWithdrawRequest` later clears.

### Finding Description
In `requestInstantWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:356-375) there is no `defaultRecoveryFinalized` check, unlike `requestWithdraw` at lines 247-257 which forbids new requests while old funded receipts exist and redirects genuine post-default requests to the reserve-backed `postDefaultRequests` bucket. After `finalizeDefaultRecovery`, `epochNumber == defaultRecoveryEpoch` (no new epoch ever starts), so a post-default instant request inflates `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` (lines 371-374).

On claim, `claimInstantWithdrawRequest` (lines 380-393) first calls `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which computes `claimBasis` from that same epoch bucket. Two breaks follow:

1. `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` (line 853) subtracts an amount that includes post-default requests never counted in the original epoch aggregate, underflowing and reverting once the sum of late claims exceeds the recorded total — permanently freezing remaining defaulted-epoch instant claims.
2. `pendingInstantWithdraws` is incremented (line 374) for requests the borrower will never fund via `collectInstantWithdrawFunds`, leaving the unfunded-remainder bookkeeping permanently inconsistent.

The UAF analog: storage cleared/finalized at `finalizeDefaultRecovery` (epoch bucket treated as closed) is reused and mutated by new requests aliasing the same epoch key.

### Impact Explanation
Any tranche-token holder (or prior lender still holding tranches) can, after default finalization, permanently freeze the defaulted-epoch instant-withdraw claims of other users by forcing an underflow at line 853, and corrupt `pendingInstantWithdraws` so recovery accounting no longer matches reserve backing. This is permanent freezing of unclaimed recovery funds, satisfying the accepted-impact bar.

### Likelihood Explanation
Requires only that instant withdraws were enabled pre-default and that a user requests after finalization — both reachable by unprivileged actors through `IdleCDOEpochVariant.requestInstantWithdraw`/`claimInstantWithdrawRequest` (IdleCDOEpochVariant.sol:975-979 shows claims need only `allowInstantWithdraw`). Uncertainty: whether the CDO blocks instant requests post-default via epoch-state gating could not be fully verified in the CDO variant code; if `allowInstantWithdraw` remains true the path is open.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: after `defaultRecoveryFinalized`, either revert or route the receipt into `postDefaultRequests` (or a post-default instant bucket) instead of `instantWithdrawsRequestsByEpoch[_user][epochNumber]`. Also key defaulted-epoch clearing to a snapshot epoch captured at default time rather than live `epochNumber`.

### Proof of Concept
Foundry fork PoC sketch:
1. Deposit via `depositAA`, enable instant withdraws, `startEpoch`, `stopEpoch` once.
2. `requestInstantWithdraw` for user A; borrower underfunds next `stopEpoch` → default; `finalizeDefault`/`finalizeDefaultRecovery` with a recovery price < `RECOVERY_FULL`.
3. Attacker (holder of tranches) calls `requestInstantWithdraw` post-finalization — succeeds, writes to `instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch]`.
4. Attacker and user A call `claimInstantWithdrawRequest`; the second claimant's `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` underflows → revert, freezing A's recovery claim.
