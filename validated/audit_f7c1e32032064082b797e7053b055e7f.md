### Title
Unbounded zstd compression CPU cost on `getAccountInfo(encoding=base64+zstd)` for a single max-size account - ([File: account-decoder/src/lib.rs])

### Summary
`encode_ui_account` performs a synchronous zstd compression of the full account data on every call to `UiAccountEncoding::Base64Zstd` with no CPU-time budget, cache, or amortization independent of the existing data-size cap (`MAX_PERMITTED_DATA_LENGTH`, 10 MiB). A single `getAccountInfo` request against an attacker-stored, max-size, low-compressibility account forces the RPC-serving thread to spend CPU proportional to the account size compressing data on every request.

### Finding Description
`get_account_info` in `rpc/src/rpc.rs` resolves the account for the requested `pubkey`/`commitment`, then calls `get_encoded_account(&bank, &pubkey, encoding, data_slice, None)` inside `self.runtime.spawn_blocking(...)`. [1](#0-0) 

When `encoding == UiAccountEncoding::Base64Zstd`, `encode_ui_account` builds a `zstd::stream::write::Encoder` and streams the *entire* (optionally sliced) account data through it synchronously before returning the response:
```
UiAccountEncoding::Base64Zstd => {
    let mut encoder = zstd::stream::write::Encoder::new(Vec::new(), 0).unwrap();
    match encoder.write_all(slice_data(account.data(), data_slice_config))
        .and_then(|()| encoder.finish())
    { ... }
}
``` [2](#0-1) 

There is no cache of previously compressed results, no amortization across requests, and no separate CPU-time ceiling for the compression step — the only limit present anywhere in the account lifecycle is the data-size cap `MAX_PERMITTED_DATA_LENGTH` (10 MiB) enforced at account-write time (e.g. in `system_processor::allocate`, `transaction_accounts.rs`'s `can_data_be_resized`), which bounds *data size* but not *encode CPU time*. [3](#0-2) [4](#0-3) 

An attacker can, using ordinary system-program instructions, allocate an account up to `MAX_PERMITTED_DATA_LENGTH` and fill it with low-entropy/incompressible-adjacent data (worst case for zstd CPU-per-byte is data that is neither trivially compressible nor perfectly random, forcing the matcher to work through most of the window). Any single unauthenticated `getAccountInfo(pubkey, {encoding:"base64+zstd"})` call then triggers full-size compression on the node's blocking-task thread pool with no separate CPU budget distinct from the size cap.

The same encode path is reachable from `get_multiple_accounts` (looped per pubkey, same encoder call), from `get_program_accounts`/`filter_program_results`/`filter_account_result` (account and program-account pubsub notifications), all of which call `encode_ui_account` directly. [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
This is a scoped, single-request unbounded-CPU-cost issue: a lone unprivileged client, using at most one call per `CLUSTER_SLOT_TIME_TARGET / 2`, can repeatedly force full 10 MiB zstd compressions on the RPC blocking-thread pool by requesting the same or different max-size accounts with `base64+zstd` encoding. Because the cost model in `cost-model/src/block_cost_limits.rs` governs on-chain transaction execution cost, not RPC-side encoding cost, there is no accounting mechanism that caps or throttles this per-request CPU expenditure at the RPC layer. This matches the "RPC single-call unbounded cost" bounty category (unbounded cost for a single low-rate call), since the CPU work done per request scales with attacker-controlled on-chain account size and is not bounded by an independent RPC CPU-time limit.

### Likelihood Explanation
Feasible and fully repeatable: the attacker only needs (1) enough lamports to rent-fund and allocate one `MAX_PERMITTED_DATA_LENGTH`-sized account via ordinary `SystemInstruction::CreateAccount`/`Allocate` (bounded, standard operation) and (2) issue a single `getAccountInfo` call with `encoding=base64+zstd` at the permitted rate. No special privileges, staking, or leader/validator control are required, and the encode path is unconditionally reachable from the public JSON-RPC surface.

### Recommendation
Add an RPC-side cost/size or CPU-time guard for the `Base64Zstd` (and `JsonParsed`/other CPU-heavy encodings) path independent of the on-chain `MAX_PERMITTED_DATA_LENGTH` check — e.g., cap compression input size for RPC-served requests, use a lower/faster zstd compression level with a data-size-proportional deadline, or reject/degrade `base64+zstd` for accounts above a configurable RPC-only size threshold, returning a data-too-large style error similar to the existing `MAX_BASE58_BYTES` guard used for `encode_bs58`. [8](#0-7) 

### Proof of Concept
Rust benchmark/unit test plan in `account-decoder/src/lib.rs` (extending the existing `test_base64_zstd` test):
```rust
#[test]
fn test_base64_zstd_cpu_cost_scaling() {
    use std::time::Instant;
    use solana_account::{Account, AccountSharedData};

    // Low-entropy but not trivially compressible data (pseudo-random-ish pattern)
    let sizes = [1024usize, 1 << 20, 10 * 1024 * 1024 /* MAX_PERMITTED_DATA_LENGTH */];
    for size in sizes {
        let data: Vec<u8> = (0..size).map(|i| ((i * 2654435761) % 251) as u8).collect();
        let account = AccountSharedData::from(Account { data, ..Account::default() });
        let start = Instant::now();
        let _ = encode_ui_account(
            &Pubkey::default(), &account, UiAccountEncoding::Base64Zstd, None, None,
        );
        let elapsed = start.elapsed();
        println!("size={size} elapsed={elapsed:?}");
        // Assertion goal: elapsed time for a single RPC-level encode call
        // must be bounded by a fixed ceiling independent of `size`.
        // Currently no such ceiling exists — this assertion would fail today:
        // assert!(elapsed < Duration::from_millis(FIXED_CPU_BUDGET_MS));
    }
}
```
Expected result today: elapsed time scales near-linearly with `size` up to the full `MAX_PERMITTED_DATA_LENGTH`, demonstrating that a single `getAccountInfo(encoding=base64+zstd)` call incurs CPU cost proportional to attacker-controlled account size with no independent ceiling, confirming the finding.     pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum

            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION

        }
        Ok(())
    }
