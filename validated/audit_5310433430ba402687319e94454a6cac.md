### Title
Pre-commit signature path never re-verifies the proposal's own tenure is still on the canonical Bitcoin fork - (File: `stacks-signer/src/v0/signer.rs` / `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionsView::check_proposal` only certifies a block's `consensus_hash` as canonical at proposal time. The only re-check that runs later, at the pre-commit-threshold-to-signature transition (`handle_block_pre_commit` → `check_block_against_signer_db_state`), never re-derives whether the proposal's *own* tenure is still on the canonical burnchain fork the way `postblock_proposal.rs::check_block_has_valid_tenure` does via `has_consensus_hash`. It only compares block height against the node's `get_tenure_tip` for that same (possibly now-orphaned) tenure, and explicitly treats a lookup failure as "proposal is higher" (i.e., passes). A tenure orphaned between proposal and pre-commit can therefore still receive a signer signature.

### Finding Description
The claimed equality is: *tenure approved by signer at `check_proposal` time == tenure actually canonical at signature-issue time*. This equality is not enforced.

- `mark_pre_committed` (`stacks-signer/src/signerdb.rs:272-277`) sets `self.valid = Some(true)` once, and `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs:1250-1479`) only checks `if !block_info.valid.unwrap_or(false) { return; }` — it never re-derives `valid` from a fresh `SortitionsView::check_proposal`/`GlobalStateView::check_proposal` call.
- The only re-validation that does run before a signature is emitted is the explicit re-check at `stacks-signer/src/v0/signer.rs:1345-1366`, which calls `check_block_against_signer_db_state` (`stacks-signer/src/v0/signer.rs:1803-1880`). That function only:
  - for tenure-change blocks: calls `SortitionData::check_tenure_change_confirms_parent` (parent-tenure block count check), or
  - for all other blocks: calls `SortitionData::check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:366-478`), which compares chain length against `client.get_tenure_tip(tenure_id)` for the block's *own* tenure.
- `check_latest_block_in_tenure` never calls anything equivalent to `check_block_has_valid_tenure`'s `db_handle.has_consensus_hash(tenure_id)` (`stackslib/src/net/api/postblock_proposal.rs:454-472`) to ask "is this tenure still on the canonical Bitcoin fork at all?" It only asks the node for that tenure's tip height, and if the lookup errors it explicitly does `return Ok(true)` (assume proposal is higher, i.e., the check passes) — a fallback whose safety comment ("this proposal ultimately must be passed to the stacks-node for proposal processing") is true for the *proposal* path (which re-submits to `/v3/block_proposal`) but false for the *pre-commit-to-signature* path, where no fresh node validation submission occurs before the signature is produced.
- The separate conflict guard (`get_signed_conflicts` / `conflict_still_blocks` / `reorg_permit_stands`, `stacks-signer/src/v0/signer.rs:1383-1457`) does perform an explicit canonical-fork check via `get_sortition_by_burn_hash`, but only against *other already-signed conflicting blocks* recorded in signerdb. If there is no prior signed conflict (e.g., this is the first and only block signed for that height), this guard never runs, and canonicity of the proposal's own tenure is never questioned.

Attacker flow (one miner slot + gossip only):
1. Attacker wins a single sortition honestly and broadcasts a `BlockProposal` whose `consensus_hash` is the winning, canonical tenure at that moment.
2. `check_proposal` passes; the node validates it OK; signers `mark_pre_committed` (valid=Some(true)) and broadcast pre-commits.
3. Before pre-commit weight reaches 70%, a Bitcoin-level fork (a competing, faster-propagating block-commit near the tip — not requiring majority hash power, matching the "poorly timed block commits" reorg scenario the test suite explicitly models) orphans the attacker's sortition; the tenure's `consensus_hash` is no longer canonical.
4. `handle_block_pre_commit` fires once the threshold is reached. `check_block_against_signer_db_state` calls `check_latest_block_in_tenure`, which asks the node for `get_tenure_tip` of the now-orphaned tenure. Depending on whether the node's tip endpoint performs a canonical-fork check (unverified in this pass) it either errors — hitting the `return Ok(true)` fallback — or returns stale data that still permits height comparison to pass.
5. No guard calls `has_consensus_hash`/`check_valid_consensus_hash` equivalent logic here. The signer signs, producing a valid group signature over a block in a tenure that is no longer canonical.

### Impact Explanation
This breaks the canonicity/safety property: a signer signature becomes valid across a tenure/chain boundary that flipped after approval, matching the Critical category ("a signature valid across chain/cycle/tenure boundaries"). If enough signers hit the same stale `get_tenure_tip` fallback (a shared, deterministic code path, not signer-specific state), the group can finalize a 70%-signed block belonging to an orphaned tenure, which is a chain-safety violation, not merely a liveness stall. It is repeatable on every reorg race that lands inside the pre-commit window.

### Likelihood Explanation
Preconditions: attacker needs only to win one sortition (their own BTC, unprivileged) and have that sortition raced/orphaned by a faster competing block-commit before the 70% pre-commit weight is reached — the codebase's own test harness (`nakamoto_integrations.rs`, "this config disallows any reorg due to poorly timed block commits") demonstrates this race is a recognized, reachable, non-majority-hash-power scenario. No signer key, no auth_token, and no majority-signer collusion is required; the flaw is in the shared re-check logic every signer runs identically. The exact severity depends on the (unverified in this session) exact canonical-fork-check behavior of the node's `get_tenure_tip` RPC handler — if that handler *does* perform a `has_consensus_hash`-equivalent check and errors/404s on an orphaned tenure, the `Err -> Ok(true)` fallback is the exploitable gap; if it silently returns stale canonical-looking data, the gap is even wider. This uncertainty should be resolved by directly inspecting the `get_tenure_tip` RPC handler and `has_consensus_hash` call sites in `stackslib/src/net/api/` before finalizing severity, but the signer-side control-flow gap itself is confirmed by the code shown.

### Recommendation
In `check_block_against_signer_db_state` (and/or `check_latest_block_in_tenure`), before comparing tenure tip height, explicitly re-verify that the proposal's `consensus_hash` (and, for tenure-change blocks, `prev_tenure_consensus_hash`) is still on the canonical burnchain fork — mirroring `postblock_proposal.rs::check_block_has_valid_tenure`'s `has_consensus_hash` check — and treat both a non-canonical result and a node lookup failure as a hard rejection (not an "assume higher" pass-through) specifically on the pre-commit-to-signature path, since that path no longer round-trips through the node's `/v3/block_proposal` endpoint.
