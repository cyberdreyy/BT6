### Title
`setWhitelistedCDO` can re-point `idleCDO` while unclaimed withdraw/default claims are outstanding, permanently stranding user claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The `IdleCreditVault` strategy binds every fund-moving entry point to a single `idleCDO` address: receipt transfers (`_transfer`), claim payouts (`_transferFundedClaim` / `_transferDefaultRecovery` called from `claimWithdrawRequest`, `claimInstantWithdrawRequest`, and the defaulted-claim path). `setWhitelistedCDO` lets the owner overwrite `idleCDO` unconditionally — there is no check that `pendingWithdraws`, `pendingInstantWithdraws`, `apr0TotalPrincipal`, `defaultRecoveryReserve`, or outstanding receipt-token supply are zero. This is the direct analog of removing an authorized game while `lockedLiquidity` is still held: the deauthorized contract's bookkeeping stays in the strategy, but the new authorized contract has no relationship to the old claims.

### Finding Description
At `contracts/strategies/idle/IdleCreditVault.sol:954-957`:

```solidity
function setWhitelistedCDO(address _cdo) external onlyOwner {
  require(_cdo != address(0), "IS_0");
  idleCDO = _cdo;
}
```

Every claim path is gated by the current `idleCDO`:

- `_transfer` reverts unless `msg.sender == idleCDO` (`IdleCreditVault.sol:939-942`), so all strategy receipt tokens held by the old CDO's users become non-movable.
- Funded receipt payouts check `balance < reserve || balance - reserve < _amount` against `defaultRecoveryReserve` (`IdleCreditVault.sol:904`) and are invoked only through the CDO's claim functions, which in turn are restricted to the single `idleCDO` via `_checkOnlyIdleCDO` on `ProgrammableBorrower` hooks and the vault's CDO-facing methods.
- `defaultRecoveryReserve` is only spendable via `_transferDefaultRecovery` (`IdleCreditVault.sol:912-917`), again only reachable through the authorized CDO's claim flow.

After a `setWhitelistedCDO` swap, the old `IdleCDOEpochVariant` can no longer call the vault, so users holding pending epoch withdraw receipts (`pendingWithdraws`/`withdrawsRequestsByEpoch`), instant-withdraw requests (`pendingInstantWithdraws`), and defaulted recovery claims reserved in `defaultRecoveryReserve` have no authorized path to pull their underlyings. The tokens sit in the vault, counted by the reserve checks, but unreachable by the claimants.

### Impact Explanation
Permanent freezing of unclaimed yield and principal. All underlyings reserved for pending withdraw requests, pending instant withdraws, APR0 principal, and the isolated default recovery reserve become unreachable by their legitimate owners once `idleCDO` is re-pointed, because receipt claims are address-bound and the old CDO is no longer recognized. The loss equals the full value of outstanding claims at the time of the swap (potentially the entire TVL for a defaulted pool, since `defaultRecoveryReserve` isolates recovered funds for claimants).

### Likelihood Explanation
Likelihood is Medium-low: it requires an owner/ops action (CDO migration or misconfiguration). This is exactly the class of routine admin call the bug class targets — `setWhitelistedCDO` exists specifically to re-point the CDO, and unlike `ProgrammableBorrower.setVault` (`ProgrammableBorrower.sol:158-169`, which reverts while vault shares remain) and `setBorrower` (`ProgrammableBorrower.sol:176-186`, which reverts while borrower exposure exists), `setWhitelistedCDO` has no "outstanding claims" guard. Owner is honest but not infallible; the function permits a state that silently orphans user funds.

### Recommendation
Track outstanding per-CDO obligations and revert in `setWhitelistedCDO` while any are non-zero:

```solidity
if (pendingWithdraws != 0 || pendingInstantWithdraws != 0 ||
    apr0TotalPrincipal != 0 || defaultRecoveryReserve != 0 ||
    totalSupply() != 0) {
  revert NotAllowed();
}
```

This mirrors the guard already applied to `setVault` and `setBorrower` in `ProgrammableBorrower`, matching the external report's recommendation to keep locked liquidity per authorized caller.

```solidity
function testSetWhitelistedCDOStrandsPendingClaims() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);           // user deposits
    _startEpochAndCheckPrices(0);

    vm.prank(user);
    cdoEpoch.requestWithdraw(amount, address(AAtranche));  // creates pending claim in vault

    // owner migrates the whitelisted CDO while the claim is outstanding
    vm.prank(owner);
    strategy.setWhitelistedCDO(address(newCDO));

    // old CDO's claim path now reverts: _transfer / claim gated by idleCDO
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    vm.prank(user);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();     // user's underlyings frozen in vault
}
```
