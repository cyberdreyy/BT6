### Title
Missing Rewards-Pool Sufficiency Guard in `redeem_fungible_staked_sui` Blocks FungibleStakedSui Redemption — (File: `crates/sui-framework/packages/sui-system/sources/staking_pool.move`)

---

### Summary

`redeem_fungible_staked_sui` in the Sui staking framework calls `pool.rewards_pool.split(rewards_amount)` unconditionally. If the calculated `rewards_amount` exceeds the actual `rewards_pool` balance, Move's `balance::split` aborts, permanently blocking any holder of `FungibleStakedSui` from recovering their funds. The sibling function `withdraw_rewards` (used by `request_withdraw_stake`) explicitly guards against this with a `.min()` clamp and even carries a TODO comment acknowledging the condition can occur — but `redeem_fungible_staked_sui` has no such guard.

---

### Finding Description

`StakingPool` holds two separate balances:

- `sui_balance` (a `u64` counter) — tracks the total SUI in the pool including principal and rewards.
- `rewards_pool` (a `Balance<SUI>` object) — holds the actual reward tokens that are split out on withdrawal. [1](#0-0) 

When a user calls `redeem_fungible_staked_sui`, the function computes `rewards_amount` from the current exchange rate via `calculate_fungible_staked_sui_withdraw_amount`, then immediately splits that amount from `rewards_pool`: [2](#0-1) 

`balance::split` aborts if the requested amount exceeds the balance. There is no guard.

The sibling path `withdraw_rewards`, called by `request_withdraw_stake`, performs the same exchange-rate arithmetic but explicitly clamps the result: [3](#0-2) 

The TODO comment on that line reads: *"This may happen when we are withdrawing everything from the pool and the rewards pool balance may be less than reward_withdraw_amount."* The same arithmetic is used in `calculate_fungible_staked_sui_withdraw_amount`, so the same condition applies to `redeem_fungible_staked_sui`.

**Concrete trigger paths:**

1. **Cross-path drain**: Multiple `request_withdraw_stake` calls in the same epoch each use the `.min()` guard and can collectively drain `rewards_pool` to 0 while `sui_balance` still reflects a non-zero reward entitlement. A subsequent `redeem_fungible_staked_sui` call computes `rewards_amount > 0` and aborts.

2. **Rounding accumulation**: `calculate_fungible_staked_sui_withdraw_amount` uses `mul_div!` integer arithmetic. Across many partial redemptions, the sum of individually computed `rewards_amount` values can exceed the actual `rewards_pool` balance by 1 MIST or more, causing the final redemption to abort. [4](#0-3) 

---

### Impact Explanation

Any holder of `FungibleStakedSui` whose redemption hits this condition cannot recover their SUI. `FungibleStakedSui` has no alternative redemption path — `redeem_fungible_staked_sui` is the only function that converts it back to `Balance<SUI>`. [5](#0-4) 

Because the abort rolls back the entire transaction, the `FungibleStakedSui` object is not destroyed and the user can retry. However, if the rewards pool is drained again before the next epoch boundary (when `deposit_rewards` replenishes it), every retry aborts. In the worst case — a pool that consistently receives less reward than the exchange rate implies — the lock persists across epochs, constituting a permanent fund lock. This matches the **High/Medium** impact class (permanent or harmful fund lock) under the HackenProof Sui Protocol bounty. [6](#0-5) 

---

### Likelihood Explanation

The condition is acknowledged by the protocol team in `withdraw_rewards` itself. Any epoch in which `request_withdraw_stake` calls collectively exhaust `rewards_pool` before a `redeem_fungible_staked_sui` call is processed triggers the bug. No privileged access is required; an ordinary SUI holder who converted their `StakedSui` to `FungibleStakedSui` is the victim. The trigger is public and requires no special timing beyond normal epoch activity. [7](#0-6) 

---

### Recommendation

Apply the same `.min()` clamp used in `withdraw_rewards` before calling `split`:

```move
// In redeem_fungible_staked_sui, replace:
sui_out.join(pool.rewards_pool.split(rewards_amount));

// With:
let safe_rewards = rewards_amount.min(pool.rewards_pool.value());
sui_out.join(pool.rewards_pool.split(safe_rewards));
```

This mirrors the existing guard in `withdraw_rewards` and ensures the redemption never aborts due to a rewards-pool shortfall, regardless of how the pool was drained by concurrent `request_withdraw_stake` calls or rounding. [8](#0-7) 

---

### Proof of Concept

1. A staking pool has `rewards_pool = 100 SUI` and `sui_balance = 1100 SUI` (1000 principal + 100 rewards). Exchange rate: 1.1 SUI per pool token.

2. Ten stakers each call `request_withdraw_stake` for 10 pool tokens. Each call computes `reward_withdraw_amount = 1 SUI` and uses the `.min()` guard — all succeed, draining `rewards_pool` to 0.

3. A holder of `FungibleStakedSui` (10 pool tokens) calls `redeem_fungible_staked_sui`. `calculate_fungible_staked_sui_withdraw_amount` computes `rewards_amount = 1 SUI` from the exchange rate.

4. `pool.rewards_pool.split(1_000_000_000)` is called on a pool with `rewards_pool.value() == 0`. Move's `balance::split` aborts with an arithmetic underflow.

5. The user's `FungibleStakedSui` is not destroyed (abort rolls back state), but every subsequent attempt in the same epoch also aborts. The user's funds are locked until `deposit_rewards` is called at the next epoch boundary — and the same drain can recur. [5](#0-4) [9](#0-8)

public(package) fun redeem_fungible_staked_sui(
    pool: &mut StakingPool,
    fungible_staked_sui: FungibleStakedSui,
    ctx: &TxContext,
): Balance<SUI> {
    let FungibleStakedSui { id, pool_id, value } = fungible_staked_sui;
    assert!(pool_id == object::id(pool), EWrongPool);

    id.delete();

    let latest_exchange_rate = pool.pool_token_exchange_rate_at_epoch(ctx.epoch());
    let fungible_staked_sui_data: &mut FungibleStakedSuiData =
        &mut pool.extra_fields[FungibleStakedSuiDataKey {}];

    let (
        principal_amount,
        rewards_amount,
    ) = latest_exchange_rate.calculate_fungible_staked_sui_withdraw_amount(
        value,
        fungible_staked_sui_data.principal.value(),
        fungible_staked_sui_data.total_supply,
    );

    fungible_staked_sui_data.total_supply = fungible_staked_sui_data.total_supply - value;

    let mut sui_out = fungible_staked_sui_data.principal.split(principal_amount);
    sui_out.join(pool.rewards_pool.split(rewards_amount));

    pool.pending_total_sui_withdraw = pool.pending_total_sui_withdraw + sui_out.value();
    pool.pending_pool_token_withdraw = pool.pending_pool_token_withdraw + value;

    sui_out
}

fun calculate_fungible_staked_sui_withdraw_amount(
    latest_exchange_rate: PoolTokenExchangeRate,
    fungible_staked_sui_value: u64,
    fungible_staked_sui_data_principal_amount: u64, // fungible_staked_sui_data.principal.value()
    fungible_staked_sui_data_total_supply: u64, // fungible_staked_sui_data.total_supply
): (u64, u64) {
    // 1. if the entire FungibleStakedSuiData supply is redeemed, how much sui should we receive?
    let total_sui_amount = latest_exchange_rate.get_sui_amount(
        fungible_staked_sui_data_total_supply,
    );

    // min with total_sui_amount to prevent underflow
    let fungible_staked_sui_data_principal_amount = fungible_staked_sui_data_principal_amount.min(
        total_sui_amount,
    );

    // 2. how much do we need to withdraw from the rewards pool?
    let total_rewards = total_sui_amount - fungible_staked_sui_data_principal_amount;

    // 3. proportionally withdraw from both wrt the fungible_staked_sui_value.
    let principal_withdraw_amount = mul_div!(
        fungible_staked_sui_value,
        fungible_staked_sui_data_principal_amount,
        fungible_staked_sui_data_total_supply,
    );

    let rewards_withdraw_amount = mul_div!(
        fungible_staked_sui_value,
        total_rewards,
        fungible_staked_sui_data_total_supply,
    );

    // invariant check, just in case
    let expected_sui_amount = latest_exchange_rate.get_sui_amount(fungible_staked_sui_value);
    assert!(
        principal_withdraw_amount + rewards_withdraw_amount <= expected_sui_amount,
        EInvariantFailure,
    );

    (principal_withdraw_amount, rewards_withdraw_amount)
}

fun withdraw_rewards(
    pool: &mut StakingPool,
    principal_withdraw_amount: u64,
    pool_token_withdraw_amount: u64,
    epoch: u64,
): Balance<SUI> {
    let exchange_rate = pool.pool_token_exchange_rate_at_epoch(epoch);
    let total_sui_withdraw_amount = exchange_rate.get_sui_amount(pool_token_withdraw_amount);
    let mut reward_withdraw_amount = if (total_sui_withdraw_amount >= principal_withdraw_amount) {
        total_sui_withdraw_amount - principal_withdraw_amount
    } else 0;

    // This may happen when we are withdrawing everything from the pool and

    pool.rewards_pool.split(reward_withdraw_amount)
}
