## Analysis

**Analog found: `check_latest_block_in_tenure`'s activity-timer refresh doubles/extends the inactivity fallback window against a "fresh" but stale reference time — same pattern as the Asset.lotPrice oracle-timeout doubling.**

### Title
Rejected/conflicting block proposals reset the miner-activity clock to "now" instead of the actual event time, doubling the `block_proposal_timeout` fallback window - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_latest_block_in_tenure` calls `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` whenever a *rejected* conflicting proposal (lower/equal chain length, or one that races a fresh pre-commit) arrives, as long as the tenure's existing signed/accepted block is still within its own, separate freshness window (`tenure_last_block_proposal_timeout`). This is exactly the Asset.lotPrice pattern: a staleness clock (`last_activity_time`, consumed by `SortitionState::is_timed_out`'s `block_proposal_timeout`) is re-anchored to wall-clock "now" by an event whose own validity window is governed by a *different*, shorter timeout, rather than being tied to the actual last legitimate activity. In the worst case this stacks the shorter freshness window on top of the full inactivity window, doubling the effective time before the state machine falls back to the prior miner.

### Finding Description
`is_timed_out` (both v1 and v2) computes `elapsed = now - last_activity` and only falls back to the prior tenure's miner once `elapsed > block_proposal_timeout`: [1](#0-0) [2](#0-1) 

`last_activity_time` is written by `check_latest_block_in_tenure` whenever a competing/invalid proposal arrives for the *current* tenure, gated only by the freshness of the pre-existing signed/pre-committed block (via `tenure_last_block_proposal_timeout`/`reorg_attempts_activity_timeout`), not by any legitimate progress: [3](#0-2) 

The doc comment on `get_tenure_last_block_info` explicitly documents the freshness window this rides on (`tenure_last_block_proposal_timeout`), and `docs/signer-flows.md` confirms the same wiring into the miner-inactivity fallback (`check_miner_inactivity → is_timed_out`) that the reset is meant to feed: [4](#0-3) [5](#0-4) 

The bug: `update_last_activity_time` stamps `get_epoch_time_secs()` (call time), not the time of the underlying legitimate signature/acceptance that made the check "still fresh." So a single valid sortition-winning miner (a one-slot actor) who lets its own last signed block sit near the end of the `tenure_last_block_proposal_timeout` window, and then sends one more conflicting/lower-height proposal just inside that window, re-anchors `last_activity_time` to that later moment. From there, the full `block_proposal_timeout` restarts — even though no new legitimate activity occurred, only a rejected proposal. Because `block_proposal_timeout` (default 120s) and `tenure_last_block_proposal_timeout` (default 30s) are independent config knobs, worst case the fallback decision is delayed by up to `block_proposal_timeout + tenure_last_block_proposal_timeout`, i.e., it can be pushed out by nearly double relative to the intended single-`block_proposal_timeout` design.

### Impact Explanation
This directly wedges the liveness path documented as `check_miner_inactivity → SortitionState::is_timed_out → fall back to prior tenure`: [6](#0-5) 
A single one-slot winning miner can, with one appropriately-timed junk/conflicting proposal, extend by up to an entire `tenure_last_block_proposal_timeout` the time the signer set continues to treat it as "active" and thus refuses to accept the prior miner's tenure-extend or fall back — matching the required High-severity category: a signer wedged (delayed) from ever transitioning to sign the legitimate fallback miner's blocks, purely from a stale/misattributed timestamp rather than genuine activity.

### Likelihood Explanation
Reachable by any single sortition-winning miner with no cooperation from other signers or majority collusion: it only needs to (1) get a block signed/accepted near the tail of its freshness window and (2) submit one more conflicting/invalid proposal before that window lapses. Both actions are fully within a normal miner's unilateral capability and require no signer key, auth token, or majority.

### Recommendation
Anchor `last_activity_time` resets to the underlying event's own timestamp (e.g., the `signed_self`/`signed_group`/`approved_time` already used by `get_tenure_last_block_info`), not to `get_epoch_time_secs()` at the moment the conflicting proposal happens to be evaluated. Alternatively, cap the total extension `is_timed_out` can grant via these activity resets to no more than `block_proposal_timeout` from the tenure's actual start, so freshness resets can delay but never compound with call-time stamping to exceed the configured window.

### Proof of Concept
1. Miner M wins a sortition; near second 28 of `tenure_last_block_proposal_timeout=30s`, M's block is signed/accepted by signer S, setting `signed_group`/`approved_time` ≈ t0+28.
2. At t0+29, M submits a second, conflicting/lower-height block proposal for the same tenure.
3. `check_latest_block_in_tenure` sees `info` is still fresh (within the 30s window) and calls `update_last_activity_time(tenure, now=t0+29)`.
4. `is_timed_out` now measures elapsed time from t0+29, not t0+28 (the real last legitimate activity) nor from the burn-block-received baseline — so `block_proposal_timeout` (120s) restarts from t0+29 instead of expiring based on the original activity, pushing the fallback decision out to roughly t0+149 instead of t0+120, up to a `tenure_last_block_proposal_timeout` extension beyond the intended single-timeout design, delaying the signer set's transition to the prior/fallback miner.

    /// Check if the sortition identified by the ConsensusHash is timed out based on
    /// the blocks within the signer db and the block proposal timeout
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        signer_db: &SignerDb,
        eval: &GlobalStateEvaluator,
        local_address: &StacksAddress,
        timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = signer_db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) =
            signer_db.get_burn_block_received_time_from_signers(eval, sortition, local_address)?
        else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = signer_db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };
        if elapsed > timeout {
            info!("Sortition has timed out";
                "sorition" => %sortition,
                "timeout" => %timeout.as_secs(),
                "elapsed" => %elapsed.as_secs()
            )
        }
        Ok(elapsed > timeout)
    }
