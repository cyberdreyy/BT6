### Title
Reused `builder_index` lets a stale `BuilderPendingWithdrawal`/`BuilderPendingPayment` drain an unrelated, newly-registered builder's balance - (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_index_for_new_builder` reassigns a fully-exited, zero-balance builder's registry slot to a brand-new builder, but nothing invalidates or migrates outstanding `state.builder_pending_withdrawals` / `state.builder_pending_payments` entries that still reference that `builder_index`. When such a stale entry is later settled, `apply_withdrawals` blindly debits `state.builders[builder_index].balance` for whatever builder currently occupies that slot — the new, unrelated builder — while paying the withdrawal to the old builder's `fee_recipient`. This mirrors the reported bug class: an identity/owner reference (`bonds[bondId].owner`, here `builder_index`) is not kept in sync with the entity it is supposed to identify after that entity is effectively "transferred" (the slot is reassigned).

### Finding Description
- `get_index_for_new_builder` (specs/gloas/beacon-chain.md, "New `get_index_for_new_builder`") returns any index whose `builder.withdrawable_epoch <= current_epoch and builder.balance == 0`, allowing `add_builder_to_registry` to overwrite that slot with a completely different `pubkey`/`execution_address` for a new builder. [1](#0-0) 
- `process_builder_deposit_request` uses exactly this function to register new builders without any cross-check against `state.builder_pending_withdrawals` or `state.builder_pending_payments`. [2](#0-1) 
- Outstanding obligations tied to a builder are recorded only via `builder_index`, not by `pubkey`: `BuilderPendingWithdrawal{fee_recipient, amount, builder_index}` and `BuilderPendingPayment{weight, withdrawal, proposer_index}`. [3](#0-2) 
- `process_builder_exit_request` only blocks *exit initiation* while `get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0`; it does not prevent the slot from being *reused* once the builder has since been swept to zero balance and its `withdrawable_epoch` has passed, even if a stale pending withdrawal for that index is subsequently queued (e.g., a delayed `process_builder_pending_payments` settlement of a bid the builder won before initiating exit). [4](#0-3) [5](#0-4) 
- `apply_withdrawals` resolves the withdrawal target purely by `builder_index`, with no check that the builder at that index is still the same entity that earned the payment:
```python
if is_builder_index(withdrawal.validator_index):
    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
    builder_balance = state.builders[builder_index].balance
    state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
``` [6](#0-5) 

The equality broken is: *the Gwei debited from a builder's balance must correspond to an obligation that builder itself incurred.* Here, Builder B's balance is decreased for a payment owed by (now defunct) Builder A, and the withdrawal's `fee_recipient` (A's address) receives Gwei that was never staked or earned by A at that balance — it is effectively Gwei taken from B and paid to a non-owner (A's `fee_recipient`).

### Impact Explanation
This is a Critical-class issue: Gwei is destroyed from an honest builder's stake and paid to an unrelated `fee_recipient`, without the affected builder's authorization or any fault on its part. It also constitutes a builder balance mutation the builder never authorized. Because builder slot reuse is explicitly documented as expected behavior ("Builder indices are reusable... a newly registered builder's public key may have previously appeared in the builder set. Implementations that rely on caching should account for this behavior"), the spec authors anticipated identity churn on `builder_index` but the payment/withdrawal-queue tracking was not updated to be immune to it.

### Likelihood Explanation
Reachability requires: (1) a builder wins a bid and its payment is queued in `builder_pending_payments`/`builder_pending_withdrawals`; (2) that same builder is later swept to zero balance and exits (freeing its index); (3) the builder's own registry slot is claimed by a new depositor before the older queued payment/withdrawal is actually settled/processed. Because payment settlement is deferred (per-epoch quorum settlement, or an entire epoch delay via `SLOTS_PER_EPOCH`-offset payment slots, or the FIFO `builder_pending_withdrawals` queue backing up beyond `MAX_WITHDRAWALS_PER_PAYLOAD - 1` per slot), this timing window is realistically reachable by any two independent, honest builder operators without collusion — no malicious peer or coalition is required, only ordinary timing of deposits/exits/bids across epochs.

### Recommendation
Bind pending payments/withdrawals to the builder's identity rather than (or in addition to) its raw index — e.g., store the builder `pubkey` alongside `builder_index` in `BuilderPendingWithdrawal`/`BuilderPendingPayment` and verify it matches `state.builders[builder_index].pubkey` in `apply_withdrawals`/`get_builder_withdrawals` before debiting, or forbid `get_index_for_new_builder` from returning any index that still has an entry in `builder_pending_withdrawals` or `builder_pending_payments` (i.e., require `get_pending_balance_to_withdraw_for_builder(state, index) == 0` as an additional reuse condition, not just at exit-initiation time).

### Proof of Concept
Conceptual state-machine trace (spec-level, since Solidity harnesses don't apply here):
1. Builder A registers at `builder_index = 5` with `execution_address = A_addr`, wins a bid; its payment enters `builder_pending_payments[i]` with `withdrawal.builder_index = 5`, `withdrawal.fee_recipient = A_addr`, `amount = P`.
2. Builder A submits `BuilderExitRequest` while `get_pending_balance_to_withdraw_for_builder(state, 5) == 0` (no queued withdrawal yet) — `initiate_builder_exit` succeeds, setting `withdrawable_epoch`.
3. Several epochs later `process_builder_pending_payments` (epoch processing) finally settles A's earlier winning bid, appending `BuilderPendingWithdrawal(fee_recipient=A_addr, amount=P, builder_index=5)` to `state.builder_pending_withdrawals` — this happens *after* A's `withdrawable_epoch` has already passed and A has been fully swept (`builders[5].balance == 0`).
4. `get_index_for_new_builder` now returns `5` (since `withdrawable_epoch <= epoch` and `balance == 0`), and a brand-new Builder B registers via `process_builder_deposit_request`, overwriting `state.builders[5]` with B's `pubkey`/`execution_address` and deposit `balance = D`.
5. In a later slot, `process_withdrawals` → `get_builder_withdrawals` dequeues the stale entry from step 3 and `apply_withdrawals` executes `state.builders[5].balance -= min(P, D)` — debiting **Builder B**, while producing a `Withdrawal` paying `P` Gwei to `A_addr`, a `fee_recipient` B never designated.

Post-state: `state.builders[5].balance == D - min(P, D)` for Builder B, who neither won the bid nor authorized the payment, while `A_addr` receives Gwei it has no current stake backing. This is a concrete violation of "Gwei paid to a non-owner" reachable purely through ordinary protocol message sequencing (deposit, bid, exit, deposit) with no client bug or malicious coalition required.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

###### New `get_index_for_new_builder`

```python
def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))
```

def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:
    # Ignore deposits with unexpected withdrawal credential prefixes
    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
        return

    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        if is_valid_builder_deposit_signature(request):
            add_builder_to_registry(
                state,
                request.pubkey,
                PAYLOAD_BUILDER_VERSION,
                ExecutionAddress(request.withdrawal_credentials[12:]),
                request.amount,
                state.slot,
            )
    else:
        builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
        builder = state.builders[builder_index]

        # If exited and swept, reset the withdrawable epoch
        if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
            epoch = get_current_epoch(state)
            builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY

        # Increase balance by deposit amount
        builder.balance += request.amount

def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
