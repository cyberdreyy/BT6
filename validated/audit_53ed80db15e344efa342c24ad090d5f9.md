### Title
Claimed instant-withdraw receipts are never cleared from per-epoch accounting, inflating the default-epoch claim basis and leaving the recovery reserve insolvent - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is "private-browsing data not deleted when leaving private mode": state scoped to a mode survives the transition out of that mode. The analog in `IdleCreditVault` is per-epoch instant-withdraw accounting: `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`, but the normal funded-claim path `claimInstantWithdrawRequest` only zeroes the aggregate `instantWithdrawsRequests[user]` and never clears the per-epoch entries. That stale epoch-scoped data is later read as if it were live debt by `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` during `finalizeDefaultRecovery`, corrupting the recovery price and the reserve.

### Finding Description [1](#0-0) 
On request, the vault increments `instantWithdrawsRequestsByEpoch[user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]`. [2](#0-1) 
On a normal (funded) claim, only `instantWithdrawsRequests[user]` is reset to 0 and funds are transferred. Neither `instantWithdrawsRequestsByEpoch` nor `instantWithdrawClaimsByEpoch` is decremented — the only place they are cleared is `_claimDefaultedInstantWithdrawRequest`. [3](#0-2) [4](#0-3) 
At default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` and `_defaultPrefundedInstantReserve` adds `instantBasis - pendingInstant` to `reserveAmount`. Both therefore count receipts that were already paid out, as if they were still outstanding.

Attack sequence (running epoch, non-closed pool):
1. Epoch E starts; attacker requests an instant withdraw of X (`instantWithdrawClaimsByEpoch[E] += X`).
2. IdleCDO funds it via `collectInstantWithdrawFunds(X)`; `pendingInstantWithdraws` → 0, strategy holds X.
3. Attacker claims X via `claimInstantWithdrawRequest`. Per-epoch entries keep the stale value X.
4. Attacker redeposits and requests another instant withdraw of Y in the *same* epoch E: `instantWithdrawClaimsByEpoch[E] = X + Y`, `pendingInstantWithdraws = Y`.
5. Borrower defaults; `finalizeDefaultRecovery` runs while `epochNumber == E`. `defaultPendingClaimBasis` includes X+Y (overstated by X), and `_defaultPrefundedInstantReserve` returns (X+Y) − Y = X, crediting a phantom reserve of X that was already paid to the attacker.
6. `defaultRecoveryPrice = reserveAmount / totalBasis` is computed against an inflated reserve. `_transferDefaultRecovery` later does `defaultRecoveryReserve -= amount` and `safeTransfer` against a balance that is short by exactly X.

### Impact Explanation
Broken invariant: solvency of the isolated recovery reserve and fair loss waterfall. The phantom X makes `defaultRecoveryReserve` larger than the real token balance, so honest defaulted-epoch claimants' `_transferDefaultRecovery` calls revert once the real tokens are exhausted — permanent freezing of up to X of unclaimed recovery payouts (the last claimants absorb the shortfall). Additionally, the victim's own future claims hit the underflow at `instantWithdrawsRequests[user] -= claimBasis` (aggregate Y < stale basis X+Y), permanently freezing their defaulted receipt. Existing guards do not help: `_ensureDefaultRecoveryInitialized` only normalizes legacy counters and explicitly does not touch instant withdrawals ("Pending instant withdrawals are never cleared automatically"); `_transferFundedClaim`'s reserve guard protects the reserve but not the victims of the insolvency.

### Likelihood Explanation
Medium. Requires an honest-manager default (`_handleBorrowerDefault`/`finalizeDefault`) in the same epoch in which a user both claimed a funded instant withdraw and opened a new one — a plausible sequence during stressed epochs when instant liquidity is intermittently funded. The attacker only needs to be a KYC-passing lender making ordinary deposits and instant-withdraw requests; every step uses unprivileged entry points and honest privileged calls in their normal order. Loss scales linearly with the attacker's instant-withdraw size X.

### Recommendation
In `claimInstantWithdrawRequest` (or a shared helper), clear the per-epoch state when paying a funded instant receipt: delete `instantWithdrawsRequestsByEpoch[user][requestEpoch]` and decrement `instantWithdrawClaimsByEpoch[requestEpoch]` by the claimed amount, tracking each receipt's request epoch (e.g., via `lastWithdrawRequest`-style marker or a per-user epoch field) so the correct epoch bucket is decremented. Alternatively, make `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` compute the live instant basis from `pendingInstantWithdraws` plus per-user unclaimed balances rather than cumulative epoch counters.

### Proof of Concept
```solidity
// test/foundry/InstantWithdrawStaleEpoch.t.sol — Foundry fork test sketch
// Setup: deploy IdleCDOEpochVariant + IdleCreditVault per existing IdleCreditVault.t.sol harness.
function testStaleInstantEpochBasisInflatesDefaultRecovery() external {
    // Epoch E running
    _depositWithUser(attacker, 1_000e6, true);
    _depositWithUser(victim,   1_000e6, true);
    vm.prank(manager); cdoEpoch.startEpoch();

    // 1) attacker requests instant X, gets funded, claims -> stale per-epoch entry remains
    _requestInstantWithdraw(attacker, 100e6);           // instantWithdrawClaimsByEpoch[E] = 100e6
    _fundInstantWithdraws();                            // collectInstantWithdrawFunds -> pendingInstantWithdraws = 0
    vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest();
    assertEq(strategy.instantWithdrawsRequests(attacker), 0);
    // BUG: stale epoch-scoped data not cleared
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, strategy.epochNumber()), 100e6);

    // 2) attacker redeposits and requests instant Y in the same epoch
    _depositWithUser(attacker, 50e6, true);
    _requestInstantWithdraw(attacker, 50e6);            // instantWithdrawClaimsByEpoch[E] = 150e6

    // 3) borrower defaults and recovery is finalized in epoch E
    _triggerBorrowerDefault();                          // honest borrower/manager path
    uint256 basis = strategy.defaultPendingClaimBasis();
    // basis includes 150e6 for attacker instead of 50e6 -> inflated by 100e6
    assertEq(basis, strategy.pendingWithdraws() + 150e6);

    _finalizeDefaultRecovery();                         // reserveAmount overstated by 100e6
    // victim's defaulted claim pays out; the last claimant's _transferDefaultRecovery
    // reverts because defaultRecoveryReserve > actual underlying balance (short by 100e6)
    vm.expectRevert();                                  // SafeERC20 / underflow on final claimant
    vm.prank(lastClaimant); cdoEpoch.claimInstantWithdrawRequest();
}
```
