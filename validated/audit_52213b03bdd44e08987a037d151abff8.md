### Title
Unfunded instant-withdraw receipts can drain underlying reserved for funded withdraw claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` credits a user a claimable balance (`instantWithdrawsRequests[_user] += _amount`) and bumps the unfunded counter `pendingInstantWithdraws`, but `claimInstantWithdrawRequest` pays out the full recorded amount from the strategy's raw `underlyingToken` balance without checking whether the request was ever funded via `collectInstantWithdrawFunds`. This mirrors the CVE-2026-64440 pattern: an attacker-supplied quantity (the request amount, like `pIE->length`) is trusted to define how much state/balance the loop (here the claim path) consumes, with no bounds check against what was actually provisioned.

### Finding Description
In `IdleCreditVault`:

- `requestInstantWithdraw` (L356-375) burns CDO-side strategy tokens, mints a receipt, records `instantWithdrawsRequests[_user] += _amount`, `instantWithdrawsRequestsByEpoch[_user][epoch] += _amount`, and increments the *unfunded* remainder `pendingInstantWithdraws += _amount`. No underlying moves into the vault here.
- `collectInstantWithdrawFunds` (L398-403) is the only funding path: the CDO pulls `_amount` underlying into the vault and decrements `pendingInstantWithdraws`. Until it runs, the receipt is backed by nothing.
- `claimInstantWithdrawRequest` (L380-393) ignores `pendingInstantWithdraws` entirely: it reads `instantWithdrawsRequests[_user]`, burns the receipt, and calls `_transferFundedClaim(_user, amount)`.
- `_transferFundedClaim` (L897-907) only protects `defaultRecoveryReserve`, and only when `reserve != 0`. In normal (non-default) operation the reserve is zero, so the claim spends any underlying sitting in the strategy — including funds collected by `collectWithdrawFunds` (L411-430) that are earmarked for other users' funded normal withdraw receipts and loss-adjusted receipts payable via `_claimFundedWithdrawRequest`/`_claimLossAdjustedWithdrawRequest`.

The vault therefore conflates two buckets in a single token balance — "funded claims owed to withdraw requesters" and "unfunded instant receipts" — and pays the unfunded bucket first-come-first-served out of the funded one. `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` even encode this assumption explicitly (the funded part of instant claims is computed as `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`, i.e. the code admits `pendingInstantWithdraws != 0` means unfunded), yet the claim path does not enforce it.

### Impact Explanation
A tranche-token holder (unprivileged, KYC'd lender) requests an instant withdraw through the CDO, then immediately calls the claim path before any `collectInstantWithdrawFunds` occurs. The strategy transfers underlying that belongs to users whose normal withdraw requests were funded at `stopEpoch`/`stopEpochWithDuration`. When those users later call `claimWithdrawRequest`, `_transferFundedClaim` reverts on insufficient balance (or pays them less), so the theft is permanent: the attacker receives funded-claim money at par while honest claimants' receipts become unpayable. Loss is bounded by the smaller of the attacker's instant-request size and the vault's idle funded balance — up to the full `pendingWithdraws`-funded reserve plus any prefunded buffer. In the default path the same flaw degrades `defaultRecoveryReserve` isolation assumptions indirectly (unfunded instant claims are counted into `defaultPendingClaimBasis` while their would-be backing was already drained), worsening realized insolvency.

### Likelihood Explanation
Requires: vault holds funded underlying (common after any `stopEpoch` with pending withdraws, or in prefunded mode), attacker holds tranche tokens, and the CDO exposes instant withdraw + claim to users (the claim path only requires `_onlyIdleCDO`, i.e. routed through the public CDO user call). No privileged collusion, no default, no timing race beyond calling claim before funding is collected. The main uncertainty I could not fully verify within the iteration budget is whether `IdleCDOEpochVariant` wraps `claimInstantWithdrawRequest` with a funding check of its own; nothing in the vault enforces it, and the vault-level invariant (a receipt is payable only to the extent funded) is already broken regardless of CDO-side sequencing.

### Recommendation
Gate `claimInstantWithdrawRequest` on funded amounts: compute `claimable = instantWithdrawsRequests[_user]` capped by the funded portion (e.g. track per-user/per-epoch funded instant basis, or revert/`return` while `pendingInstantWithdraws` covers this user's request), and decrement `instantWithdrawClaimsByEpoch`/`instantWithdrawsRequestsByEpoch` consistently on claim. Alternatively, make `_transferFundedClaim` treat `pendingWithdraws`-funded balances as a protected reserve the same way it protects `defaultRecoveryReserve`.

### Proof of Concept
Fork test outline (Foundry, mainnet fork):

```solidity
// Setup: deploy/fork an IdleCDOEpochVariant + IdleCreditVault vault where
// borrower, manager, owner are honest. UserX deposits AA, requests a normal
// withdraw; epoch stops; borrower funds -> collectWithdrawFunds(pendingBasis)
// pulls underlying INTO the vault. Vault now holds funded claim money.

// Attack:
address attacker = makeAddr("attacker"); // KYC'd tranche holder
uint256 v = vault.balanceOf(address(vault)); // funded claim money on hand
uint256 amt = v; // attacker sizes request to vault balance
// attacker deposits enough to hold >= amt strategy-token value, then:
vm.prank(attacker);
cdo.requestInstantWithdraw(amt); // -> vault.requestInstantWithdraw(amt, attacker)
// NOTE: pendingInstantWithdraws == amt, zero underlying moved
vm.prank(attacker);
cdo.claimInstantWithdrawRequest(); // -> vault.claimInstantWithdrawRequest(attacker)
// _transferFundedClaim pays amt from vault balance: attacker steals funded claims.

// Honest user's funded receipt now unpayable:
vm.prank(userX);
vm.expectRevert();
cdo.claimWithdrawRequest(); // safeTransfer fails / underflow on drained balance
```

Key assertions: `pendingInstantWithdraws == amt` at claim time (proves unfunded), attacker underlying balance increases by `amt`, and the honest funded claim reverts.
