Based on my research, I found a concrete analog in the transaction-status decoding path that mirrors the "no cap on repeated units of work per single request" bug class from the report.

### Title
Unbounded loop count in SPL-Token `Batch` instruction decoding allows expensive single-call parsing DoS - (File: transaction-status/src/parse_token.rs)

### Summary
`parse_batch_instruction` iterates a `while` loop over attacker-controlled instruction `data` and `accounts` slices, invoking `parse_token` recursively for every packed sub-instruction it finds, with no upper bound on how many sub-instructions may be present in a single `Batch` instruction.

### Finding Description
The function `parse_batch_instruction` in `transaction-status/src/parse_token.rs` decodes a spl-token `Batch` instruction by walking its `data` buffer: for each iteration it reads a `num_accounts` byte and a `data_len` byte, slices out the corresponding `inner_accounts`/`inner_data`, builds a `CompiledInstruction`, and calls `parse_token` on it recursively, pushing the JSON result into an `instructions` vector. [1](#0-0) 

The only safeguard against unbounded recursive blow-up is a check that rejects a nested instruction whose data begins with byte `255` (i.e., another `Batch`), which prevents infinite recursive nesting, but it does not limit the *number* of sibling sub-instructions packed into a single `Batch`'s data buffer: [2](#0-1) 

Because each sub-instruction only needs 2 header bytes (`num_accounts`, `data_len`) when both fields are zero, an attacker who controls the instruction data of a `Batch` instruction (either as a top-level transaction instruction, or — more importantly — as a CPI-recorded inner instruction generated by a malicious on-chain program during execution) can pack an arbitrarily large number of trivial sub-instructions into the data blob, each of which triggers a full `parse_token` dispatch attempt (`TokenInstruction::unpack`, `TokenGroupInstruction::unpack`, `TokenMetadataInstruction::unpack`) on every parse. This parsing code path is invoked whenever an unprivileged client requests `jsonParsed` encoding, e.g. via `getTransaction`/`getBlock`, through `parse_ui_instruction`/`map_inner_instructions`: [3](#0-2) 

This is structurally analogous to the reported governance bug: a single object (a proposal / a `Batch` instruction) with an attacker-chosen count of sub-units (actions / packed sub-instructions) and no maximum limit, causing a downstream "processing" call (`endProposal()` / `parse_token` on `getTransaction`) to do unbounded work.

### Impact Explanation
Every unprivileged RPC client requesting a parsed transaction/block containing such a crafted `Batch` instruction pays the (potentially very large) linear parsing cost on the RPC-serving validator node for a single low-rate call, since there is no limit on the number of packed sub-instructions. This matches the "unbounded cost for a single low-rate call" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to get a transaction (or CPI-recorded inner instruction) containing a maximally-packed `Batch` instruction confirmed on-chain, and then have any unprivileged client request that transaction with `jsonParsed` encoding. No special privileges are needed to submit such a transaction or to query it once confirmed.

### Recommendation
Add an explicit maximum count of packed sub-instructions (or a maximum number of loop iterations) enforced in `parse_batch_instruction`, mirroring the recommendation in the original report ("max limit of N sub-units per container"), and fail parsing early (returning `PartiallyDecoded`) once the limit is exceeded rather than continuing to decode arbitrarily many entries.

### Proof of Concept
Construct a `Batch` instruction whose `data` is a sequence of `[0x00, 0x00]` pairs (each `num_accounts = 0`, `data_len = 0`), repeated as many times as fits in the max instruction data length reachable via CPI. When any client calls `getTransaction`/`getBlock` with `encoding: jsonParsed` for that transaction, `parse_batch_instruction`'s `while` loop performs one `parse_token` recursive call per pair, with cost scaling linearly (and expensively, due to the multiple `unpack` attempts per call) with the number of pairs, all triggered by a single RPC request. fn parse_batch_instruction(
    data: &[u8],
    program_id_index: u8,
    accounts: &[u8],
    account_keys: &AccountKeys,
) -> Result<ParsedInstructionEnum, ParseInstructionError> {
    let not_parsable = || ParseInstructionError::InstructionNotParsable(ParsableProgram::SplToken);
    let mut data_cursor: usize = 0;
    let mut account_cursor: usize = 0;
    let mut instructions = vec![];
    while data_cursor < data.len() {
        let num_accounts = *data.get(data_cursor).ok_or_else(not_parsable)? as usize;
        let data_len = *data.get(data_cursor + 1).ok_or_else(not_parsable)? as usize;
        data_cursor += 2;
        let data_end = data_cursor.checked_add(data_len).ok_or_else(not_parsable)?;
        let inner_data = data.get(data_cursor..data_end).ok_or_else(not_parsable)?;
        data_cursor = data_end;
        let account_end = account_cursor
            .checked_add(num_accounts)
            .ok_or_else(not_parsable)?;
        let inner_accounts = accounts
            .get(account_cursor..account_end)
            .ok_or_else(not_parsable)?;
        account_cursor = account_end;
        // Nested batches are not permitted by the program.
        if inner_data.first() == Some(&255) {
            return Err(not_parsable());
        }
        let inner_instruction = CompiledInstruction {
            program_id_index,
            accounts: inner_accounts.to_vec(),
            data: inner_data.to_vec(),
        };
        let parsed = parse_token(&inner_instruction, account_keys)?;
        instructions.push(serde_json::to_value(parsed).map_err(|_| not_parsable())?);
    }
    Ok(ParsedInstructionEnum {
        instruction_type: "batch".to_string(),
        info: json!({ "instructions": instructions }),
    })
}

pub fn parse_ui_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiInstruction {
    let program_id = &account_keys[instruction.program_id_index as usize];
    if let Ok(parsed_instruction) = parse(program_id, instruction, account_keys, stack_height) {
        UiInstruction::Parsed(UiParsedInstruction::Parsed(parsed_instruction))
    } else {
        UiInstruction::Parsed(UiParsedInstruction::PartiallyDecoded(
            make_ui_partially_decoded_instruction(instruction, account_keys, stack_height),
        ))
    }
}
