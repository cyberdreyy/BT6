I need to check the CDO-side `requestWithdraw` and `_transferFundedClaim` for a missing/zero-value bypass.### Title
Unset `epochEndDate == 0` bypasses the epoch wait and `pendingWithdraws` accounting for instant redemption - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Horilla OTP bug is a "missing value equals missing value" auth bypass: an expired OTP returns `None`, and an omitted `otp` field is also `None`, so `user_otp == otp` passes. The same bug class exists in `IdleCreditVault`: `epochEndDate == 0` is the *unset/default* value (never-started pool), but the code treats it exclusively as "successfully closed pool." Because the default (missing) value is conflated with the closed-pool sentinel, both the `pendingWithdraws` reservation in `requestWithdraw` and the one-epoch claim delay in `_claimFundedWithdrawRequest` are silently skipped whenever `epochEndDate` has never been set — i.e., before the first `startEpoch`.

### Finding Description
In `requestWithdraw`, `bool isClosed = IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0` causes the function to mint the user a full strategy-token receipt (`_mint(_user, _amount)`) while skipping `pendingWithdraws += _amount` — the comment assumes a closed pool "already recalled all funds and has no later stopEpoch" [1](#0-0) . Symmetrically, `_claimFundedWithdrawRequest` only enforces the one-epoch delay when `epochEndDate() != 0`, so when `epochEndDate` is still the default `0` the epoch-maturity check `epochNumber <= lastWithdrawRequest[_user]` is bypassed entirely [2](#0-1) . `claimWithdrawRequest` routes into this path whenever `defaultRecoveryFinalized` is false [3](#0-2) . Deposits before the first epoch transfer underlying directly into the strategy (`underlyingToken.safeTransferFrom` + `_mint`), so the strategy holds real liquid underlying to pay such a claim [4](#0-3) . The attack sequence is atomic: deposit → `requestWithdraw` (receipt minted, nothing reserved) → `claimWithdrawRequest` (no epoch wait) in a single transaction, entirely with an unprivileged KYC'd lender.

### Impact Explanation
The invariant broken is "one receipt, one reserved payout after one epoch." The receipt is minted but never counted in `pendingWithdraws`, so the strategy's solvency bookkeeping does not reserve for it; the payout is drawn from the same underlying that backs every other depositor's strategy tokens 1:1. If the CDO's `_amount` computation includes any accrued/expected interest for the tranche (the receipt is documented as "interest included"), the attacker extracts unearned yield from remaining LPs; even at par, the unreserved instant exit lets the first attacker drain strategy liquidity ahead of other pending claimants, effectively turning a queued redemption system into a free instant-withdraw lane before the pool ever runs.

### Likelihood Explanation
The trigger conditions are all attacker-controlled timing: a pool that has accepted deposits but has not yet run `startEpoch` (or any state where `epochEndDate` was never written) is exactly the default state after deployment and initial deposits. No privileged action is needed — only `requestWithdraw` followed immediately by `claimWithdrawRequest` from the same user. The only uncertainty is the exact `_amount` minted by the CDO-side `requestWithdraw` in this never-started state (whether it exceeds principal), which I could not fully trace within the indexed code; the accounting-gap portion (unreserved receipt paid from shared liquidity) does not depend on it.

### Recommendation
Distinguish "never started" from "closed": require an explicit closed flag (or `epochsStarted > 0`) instead of `epochEndDate() == 0` before skipping `pendingWithdraws` and the epoch-wait check, and revert `requestWithdraw`/`claimWithdrawRequest` outright when the pool has never run an epoch.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }
