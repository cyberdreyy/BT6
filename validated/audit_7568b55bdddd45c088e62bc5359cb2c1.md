### Title
Unbounded, no-per-sender-cap growth of `savedCallbacks` in `capabilities.handler` enables single-tenant resource-exhaustion DoS - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The `capabilities` gateway `handler`'s `savedCallbacks` map is keyed only by `msg.Body.MessageId` with no per-sender quota, and insertion is not gated by `MaxSavedCallbacks` — the cap is only enforced asynchronously by `pruneCallbacks()` on a `CallbackPruneIntervalSec` timer (default 30s), unlike `requestCache.NewRequest` which explicitly rejects with `"request cache is full"` when `len(cache) >= maxCacheSize`. A single caller who can submit enough unique-`MessageId` user triggers between prune cycles can exhaust the shared budget and cause legitimate entries from other users to be evicted or the map to grow unbounded, with no explicit "cache full" error returned to anyone.

### Finding Description
`HandlerConfig.MaxSavedCallbacks` and `CallbackPruneIntervalSec` are populated from static `handlerConfig json.RawMessage` at `NewHandler` construction time (`core/services/gateway/handlers/capabilities/handler.go:80-117`) and are not attacker-influenceable per request. However, enforcement of `MaxSavedCallbacks` is not applied at write time. The doc comment on the default itself acknowledges this: `defaultMaxSavedCallbacks = 20000 // could briefly exceed under heavy load` [1](#0-0) .

The only place the size limit is enforced is `pruneCallbacks()`, which runs on a ticker with period `CallbackPruneIntervalSec` (default 30s, started in `Start()`), and even then only trims down to `maxSize/2` after the map has already exceeded `MaxSavedCallbacks`: [2](#0-1) [3](#0-2) 

Because eviction is time/tick-based (oldest-first) rather than an admission check, any write into `savedCallbacks` between prune ticks is unconditional — there is no equivalent to `requestCache[T].NewRequest`'s explicit capacity check: [4](#0-3) 

Critically, `savedCallbacks` is keyed solely by `msg.Body.MessageId`, not by `(sender, MessageId)` like `requestCache`'s `globalId{sender, id}` key [5](#0-4) . This means the `capabilities.handler` has no per-sender partitioning or quota mechanism at all — the entire `MaxSavedCallbacks` budget is a single global pool shared by every caller of the handler instance, and nothing in the insertion path attributes or limits usage by sender.

The existing test suite confirms entries are gated only by message *validity* (correct trigger method, fresh timestamp, well-formed payload) — not by any per-sender or capacity check: [6](#0-5) 

and confirms the size-based eviction behavior only fires from `pruneCallbacks`, oldest-first, trimming to half of `MaxSavedCallbacks` — i.e., after the fact, not preventively: [7](#0-6) 

### Impact Explanation
An attacker who can submit valid, uniquely-`MessageId`'d trigger requests to the shared gateway handler can flood `savedCallbacks` past `MaxSavedCallbacks` before the next `CallbackPruneIntervalSec` tick. Since there is no per-sender cap and no admission-time rejection, this is a global-budget quota bypass: the attacker's flood can (a) cause unbounded transient memory growth in the gateway process, and (b) cause legitimate other-users' pending callbacks to be evicted early by the age-based `pruneCallbacks` trim (oldest entries removed first, so a burst of new attacker entries pushes older legitimate entries into the eviction set), or delay/starve their responses. This matches a shared-tenant resource-exhaustion / availability degradation impact class rather than a fund-loss or auth-bypass class.

### Likelihood Explanation
Feasibility depends on whether an unprivileged, restricted-token/gateway client can reach the code path that inserts into `savedCallbacks` (presumably `HandleLegacyUserMessage`, whose exact insertion line I was unable to directly view due to index truncation of `core/services/gateway/handlers/capabilities/handler.go` in the retrievable range). The only confirmed insertion/deletion sites I could directly verify are in `handleWebAPITriggerMessage` (delete-on-response) and the pruning logic; the write path itself was not directly visible in the indexed content, so I could not 100% confirm the exact unconditional-assignment line referenced in the question. This is a genuine gap in my verification — I recommend starting a Devin session to pull the full file contents of `core/services/gateway/handlers/capabilities/handler.go` (particularly the `HandleLegacyUserMessage` function body) to confirm the exact insertion code and any preceding validation/authorization/rate-limit checks before treating this as conclusively reachable by an unprivileged attacker. Given the corroborating evidence (default-value comment acknowledging overflow, and the prune-only enforcement design, and the message-ID-only keying with no sender attribution), the mechanism itself (lack of per-sender cap, lack of admission-time size check) is confirmed by the code shown above.

### Recommendation
1. Enforce `MaxSavedCallbacks` at insertion time (reject or apply backpressure) rather than relying solely on periodic `pruneCallbacks`, mirroring `requestCache.NewRequest`'s explicit `"request cache is full"` check.
2. Key `savedCallbacks` by `(sender, MessageId)` and add a per-sender quota (e.g., a configurable `MaxSavedCallbacksPerSender`) so a single sender cannot consume the entire global budget.
3. Return an explicit error/response to the caller when the per-sender or global cap is hit, instead of silently succeeding and letting age-based eviction possibly punish other tenants.

### Proof of Concept

1. Construct a `handler` via `setupHandler(t)` with `MaxSavedCallbacks` set low (e.g., 5) and `CallbackPruneIntervalSec` set large so no prune tick fires during the test.
2. From a single simulated attacker identity, submit `MaxSavedCallbacks + N` valid trigger messages with unique `MessageId`s via the handler's user-message entry point, each with its own `Callback`.
3. Assert `len(handler.savedCallbacks) > MaxSavedCallbacks` (i.e., no rejection occurred, unlike `TestRequestCache_MaxSize` which asserts `require.Error` on the `(N+1)`th `NewRequest` call in `core/services/gateway/handlers/common/requestcache_test.go:125-141`).
4. Submit one more "victim" message from a different sender/`MessageId` and assert it is accepted (no explicit "cache full" error) — demonstrating both the absence of a hard cap and the absence of any per-sender partition protecting the victim's share of the budget.
5. Optionally trigger `pruneCallbacks()` and assert that attacker-flooded (fresher) entries survive while a pre-existing victim entry (older `createdAt`) is evicted first, demonstrating cross-tenant impact.

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
