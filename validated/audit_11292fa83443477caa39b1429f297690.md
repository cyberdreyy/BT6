## Title
`BlockRejection` signature only binds `signer_signature_hash`, letting the block's rejection metadata be forged under a legitimate signer's identity - (File: `libsigner/src/v0/messages.rs`)

### Summary
`BlockRejection::hash()` computes the signed digest from only the `signer_signature_hash` and `chain_id`; it never includes `reason`, `reason_code`, or `response_data` (which carries `reject_reason`, `failed_txid`, `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`). Every verification path (`verify`, `recover_public_key`) checks the signature only against that narrow hash. Consequently, the metadata fields of a `BlockRejection` are unauthenticated: anyone who can place a message on the wire under a signer's already-observed signature can pair that valid signature with arbitrary `reason_code`/`response_data`, and every consumer (`Signer::handle_block_rejection`/`store_and_process_block_rejection` in `stacks-signer/src/v0/signer.rs`, and `stacks-node/src/nakamoto_node/stackerdb_listener.rs`) will accept it as an authentic statement from that signer.

Both the signer-side handler and the node-side coordinator trust `reason_code`/`response_data` once the (narrow) signature check passes:
- `stacks-signer/src/v0/signer.rs::handle_block_rejection` recovers the pubkey, checks `is_valid_signer`, and then feeds `(&rejection.response_data.reject_reason).into()` straight into `store_and_process_block_rejection`, which uses that reject-reason to (a) tally rejection weight toward global rejection and (b) specifically tally `RejectReasonPrefix::ReorgNotAllowed` weight to flip the miner's status to invalid: [4](#0-3) [5](#0-4) 

- `stacks-node/src/nakamoto_node/stackerdb_listener.rs` recovers the pubkey from the rejection and, once it matches the expected slot's pubkey, uses `rejected_data.reason_code` / `rejected_data.response_data.failed_txid` to accumulate per-txid "problematic" weight that later influences which transactions the miner drops from its next proposal, and uses `response_data.tenure_extend_timestamp` to update idle/read-count timestamps: [6](#0-5) 

Because none of `reason`, `reason_code`, or `response_data` is part of the signed digest, the signature over a genuine rejection for a given `signer_signature_hash` is valid no matter what those fields say. This is the same bug class as the DolphinScheduler advisory: input that is supposed to be constrained/validated by a trust boundary (here, "this metadata came from signer X, with signature verified") is not actually checked, and downstream logic (weight tallies, miner-invalidation, tx-blame accounting) acts on attacker-controlled content while believing it is authenticated.

### Impact Explanation
This breaks the "rejection recounted as an accept"/"aggregated-weight vs verified-accepts" equality class called out in scope: the *weight* correctly requires the real signer's signature over the real `signer_signature_hash`, but the *content* that weight is credited toward (which `RejectReasonPrefix`, which `failed_txid`, which extend timestamps) is unauthenticated. A party that can replay/re-emit a validly-signed rejection with a different `reason_code`/`response_data` can:
- Force a rejection that would otherwise carry, e.g., a `ProblematicTransaction` reason to instead be counted as `ReorgNotAllowed`, contributing to the 30%-weight threshold in `store_and_process_block_rejection` that flips `sortition_state.cur_sortition.miner_status` to `InvalidatedBeforeFirstBlock` — invalidating the current miner's tenure view based on a fabricated reason.
- Poison the node-side `failed_txids` accounting in `stackerdb_listener.rs` with an arbitrary `failed_txid`/`ProblematicTransaction` classification attributed to a signer who never made that claim, skewing which transactions the miner excludes from future block proposals.
- Corrupt the idle/read-count extension timestamps a genuine signer is credited with, since those are taken from the unauthenticated `response_data` on the exact same signature.

This falls under the High/Critical impact categories in scope (miscounted response / signer state skewed by unauthenticated content feeding directly into consensus-relevant weight tallies and miner-invalidation logic), though it stops short of directly producing an invalid signed block by itself.

### Likelihood Explanation
The primary open question — which I could not fully resolve in the time available — is the exact transport-layer authentication surrounding these messages: `BlockResponse`/`BlockRejection` chunks are normally written to StackerDB slots that are themselves protected by a per-chunk signature keyed to the slot owner (`chunk.sign(signer_private_key)` in the test helpers), which would make it hard for an outsider to forge a *new* chunk. However:
- The chunk-level signature (StackerDB slot ownership) and the *inner* `BlockRejection.signature` are two independent signatures serving two different purposes; the code explicitly re-verifies the inner signature and re-derives the signer identity from it (`recover_public_key`) rather than trusting slot ownership alone, which strongly suggests the inner signature is meant to be an independent, portable authentication token for the rejection's content — and it fails at that job because it doesn't cover the content.
- A signer that once emits a validly-signed rejection for a given `signer_signature_hash` (e.g., an early, low-severity rejection reason) has thereby produced a signature that remains valid forever for *any* `reason_code`/`response_data` paired with that same `signer_signature_hash`. Any relay, cache, gossip retransmission, or malicious observer of that message can graft a different reason/response body onto the same valid signature and reintroduce it into signer or node state, since nothing downstream re-derives the signature from the full message.

Given the uncertainty over exactly which relay paths (StackerDB replay, cross-signer forwarding, or node-side caching/relay in `stackerdb_listener.rs`) can be reached without the signer's private key, I present this as a probable-but-not-fully-proven analog; a background agent with terminal/test access would be needed to confirm whether an externally-reachable relay path exists that accepts a re-signed-hash/re-bodied message without a fresh, slot-authenticated chunk write.

### Recommendation
Include `reason_code`, `reason`, and `response_data` (or a hash of the fully serialized message) inside `BlockRejection::hash()`'s signed digest, so the signature authenticates the entire rejection content, not just the `signer_signature_hash`. Apply the same audit to `BlockAccepted`/other `SignerMessage` variants that carry a detached signature over a narrow sub-field to ensure no other message type has the same gap.

### Proof of Concept
Conceptual PoC (cannot be fully executed without terminal access to confirm the relay path):
1. Signer S broadcasts a legitimately signed `BlockRejection` for block `B` with `reason_code = ValidationFailed(BadTransaction)`, `response_data.failed_txid = None`.
2. Capture this message (it is broadcast in the clear over StackerDB / observer feeds).
3. Construct a new `BlockRejection` with the same `signer_signature_hash`, `chain_id`, and `signature`, but `reason_code = RejectCode::ValidationFailed(ValidateRejectCode::ProblematicTransaction)` and `response_data.failed_txid = Some(<victim_txid>)`.
4. Because `hash()` only depends on `signer_signature_hash` + `chain_id`, `recover_public_key()`/`verify()` on the forged struct still succeeds and recovers signer S's real public key.
5. Feed this forged message into `handle_block_rejection`/`stackerdb_listener` (via whatever relay path accepts it without a fresh slot-chunk signature) — it will be accepted as an authentic statement from S, corrupting `failed_txids` weight and/or rejection-reason tallies.         let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),

        // authenticate the signature -- it must be signed by one of the stacking set

        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,

                "signer_signature_hash" => %block_hash,
                "signature" => %signature

            return;

            }
            return;

            &mut block_info,
