## Title
Gateway `capabilities` handler shares HTTP-call context with node response delivery, letting an external endpoint consume the timeout budget needed to deliver the result — ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The `LayerZeroImpl._blockingLzReceive` bug lets a malicious external call soak up the gas budget that was supposed to also cover the critical "store the outcome" step, causing that step to fail and permanently break the communication pathway. The Chainlink Gateway has an analogous pattern: `handler.handleWebAPIOutgoingMessage` in `core/services/gateway/handlers/capabilities/handler.go` uses a single, timeout-bounded context for both (1) making the outbound HTTP request to an externally-controlled endpoint and (2) delivering the resulting response back to the requesting DON node via `don.SendToNode`. If the external endpoint consumes (close to) the full request timeout, the shared context is already expired when `SendToNode` is invoked, so the response is silently dropped instead of reaching the node.

### Finding Description
In `handleWebAPIOutgoingMessage`: [1](#0-0) 

`newCtx` is created once with `context.WithTimeout(context.WithoutCancel(ctx), timeout)` and is used both for the call into `h.sendHTTPMessageToClient(newCtx, req, msg)` (the outbound HTTP request to a URL supplied in the node's `Request.URL` payload) and, later, for `h.don.SendToNode(newCtx, nodeAddr, req)`, which delivers the response (success or error payload) back to the capability node over the gateway/DON connection.

If the external HTTP endpoint (attacker-controlled, since the URL and timing of the response are outside the gateway's control) delays its response until close to `payload.TimeoutMs`, the shared `newCtx` deadline elapses right around the same time `sendHTTPMessageToClient` returns. The subsequent `h.don.SendToNode(newCtx, nodeAddr, req)` call is then made with an already-expired (or nearly expired) context, causing the send to fail, which is logged and dropped: [2](#0-1) 

This is exactly the same class of bug already identified and fixed in the newer `v2` HTTP gateway handler, where the fix comment explicitly documents the root cause and remedy: [3](#0-2) 

And is regression-tested there: [4](#0-3) 

The legacy `capabilities/handler.go` handler (used for `MethodWebAPITarget`, `MethodComputeAction`, `MethodWorkflowSyncer`) still shares the context and does not have this fix.

### Impact Explanation
An external HTTP endpoint reachable from a workflow's HTTP target/compute-action request can cause the gateway to silently fail to deliver the response (success or error) back to the requesting DON node, even though the outbound call itself succeeded or failed cleanly. From the node's perspective the outgoing request simply never gets a reply, causing the corresponding workflow step/capability execution to stall or time out. This is a communication-breaking/DoS class issue analogous to the LZ report's "block the pathway," though its blast radius here is per-request rather than a permanently stuck channel, since the gateway itself does not persist any blocking state.

### Likelihood Explanation
The behavior is entirely determined by response timing of an externally reachable HTTP endpoint that is effectively chosen/controlled by the initiating workflow/node request (`payload.URL`), and requires no privileged capability — any endpoint that intentionally delays its response near `TimeoutMs` will reliably trigger the dropped delivery. This is a deterministic, easily reproducible timing condition rather than a rare race.

### Recommendation
Mirror the fix already applied in the v2 HTTP handler: use an independent, freshly-scoped context (derived from `context.WithoutCancel(ctx)`) for `h.don.SendToNode`, separate from the context used for the outbound HTTP call, so an expired/cancelled HTTP timeout cannot prevent delivering the result back to the node.

### Proof of Concept
1. Configure a workflow/node to send a `MethodComputeAction`/`MethodWebAPITarget` outgoing message with `TimeoutMs` set to, e.g., 2000ms and `URL` pointing to an attacker-controlled HTTP server.
2. The attacker's server delays its HTTP response until ~1999ms (just under the timeout), which `h.sendHTTPMessageToClient` will accept as it completes within `httpClient.Send`'s own deadline race but leaves `newCtx` with near-zero or negative remaining time.
3. `h.don.SendToNode(newCtx, nodeAddr, req)` is then invoked with an expired/near-expired context, causing `SendToNode` to fail (e.g., context deadline exceeded), which is logged via `l.Errorw("failed to send to node", ...)` and the response is dropped — the requesting node never receives its result.
This is directly demonstrated by the analogous, already-fixed scenario in `TestMakeOutgoingRequest_SendResponseUsesIndependentContext` [5](#0-4) , which reproduces the same shared-context timing failure against a slow mock endpoint before asserting the fix.

		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
		h.metrics.IncrementActionCapabilityRequestCount(ctx, nodeAddr, h.lggr)
		// Use a separate context for sending the response to the node so that an
		// expired HTTP request timeout does not prevent delivering the result.
		sendCtx, sendCancel := context.WithTimeout(baseCtx, sendResponseTimeout)
		defer sendCancel()
		err := h.sendResponseToNode(sendCtx, requestID, outboundResp, nodeAddr)

func TestMakeOutgoingRequest_SendResponseUsesIndependentContext(t *testing.T) {
	handler := createTestHandler(t)
	mockDon := handler.shards[0].connMgr.(*handlermocks.DON)
	mockHTTPClient := handler.httpClient.(*httpmocks.HTTPClient)

	outboundReq := gateway_common.OutboundHTTPRequest{
		Method:    "GET",
		URL:       "https://slow-endpoint.com/api",
		TimeoutMs: 50, // very short timeout so the HTTP context expires quickly
	}
	reqBytes, err := json.Marshal(outboundReq)
	require.NoError(t, err)

	id := fmt.Sprintf("%s/%s", gateway_common.MethodHTTPAction, uuid.New().String())
	rawRequest := json.RawMessage(reqBytes)
	resp := &jsonrpc.Response[json.RawMessage]{
		ID:     id,
		Result: &rawRequest,
	}

	// Simulate a slow HTTP endpoint that blocks until the context deadline expires.
	mockHTTPClient.EXPECT().Send(mock.Anything, mock.Anything).RunAndReturn(
		func(ctx context.Context, req network.HTTPRequest) (*network.HTTPResponse, error) {
			<-ctx.Done()
			return nil, ctx.Err()
		},
	)

	// The critical assertion: SendToNode must receive a non-expired context.
	// Before the fix, the same context was shared between the HTTP call and
	// sendResponseToNode, so an expired HTTP timeout would also prevent
	// delivering the response back to the node.
	mockDon.EXPECT().SendToNode(mock.MatchedBy(func(ctx context.Context) bool {
		return ctx.Err() == nil
	}), "node1", mock.Anything).Return(nil)

	err = handler.HandleNodeMessage(t.Context(), resp, "node1")
	require.NoError(t, err)
	handler.wg.Wait()
}
