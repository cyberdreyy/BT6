### Title
Missing decimal-scaling division in Jovian operator-fee computation causes grossly overcharged (or undercharged) transaction fees - ([File: crates/common/l1-fees/src/params.rs])

### Summary
`L1FeeParams::operator_fee_charge_inner` computes the Isthmus/Jovian operator fee component charged to every non-exempt transaction. In the pre-Jovian branch the raw product `gas * operator_fee_scalar` is explicitly divided by `OPERATOR_FEE_SCALAR_DECIMAL` (`1_000_000`, i.e. 6 decimals of fixed-point precision) to bring the result back to wei. In the Jovian branch, the same raw product is instead multiplied by `OPERATOR_FEE_JOVIAN_MULTIPLIER` (`100`) with **no corresponding division by the 1e6 scalar decimal factor**, leaving the result inflated by a factor of `1_000_000 / 100 = 10_000` relative to the intended fee. [1](#0-0) 

### Finding Description
`operator_fee_scalar` is stored and interpreted as a fixed-point value with 6 decimal digits of precision, exactly as documented by `OPERATOR_FEE_SCALAR_DECIMAL`: [2](#0-1) 

The correct de-scaling operation is `gas * operator_fee_scalar / OPERATOR_FEE_SCALAR_DECIMAL`, which is exactly what the non-Jovian branch does:
```rust
gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
```
For the post-Jovian branch, the same numerator (`gas * operator_fee_scalar`, still carrying the 1e6 fixed-point scale) is only multiplied by an additional constant `OPERATOR_FEE_JOVIAN_MULTIPLIER = 100` and is **never divided by `OPERATOR_FEE_SCALAR_DECIMAL`**:
```rust
gas.saturating_mul(operator_fee_scalar)
    .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
```
This is the same class of defect as the referenced CrabNetting report: a value carrying one fixed-point precision (6-decimal operator-fee scalar) is combined with a scaling constant that assumes a different (or no) precision reduction, producing a result that is off by orders of magnitude — here, `1_000_000 / 100 = 10,000×` too large versus the intended fee (or, if the multiplier was meant to *replace* rather than supplement the decimal division for a changed scalar precision, the fee is wrong in the opposite direction for any deployment that still supplies a 6-decimal scalar).

This function is invoked directly from consensus/execution-critical fee-accounting paths reachable by every ordinary signed transaction:
- `L1BlockInfo::calculate_tx_l1_cost`/operator fee usage in the EIP-8130 pre-charge path (`prepay`), which debits the payer's balance for `gas_charge + l1_cost + operator_cost` before executing calls: [3](#0-2) 
- The same `operator_fee_charge`/`operator_fee_charge_inner` constants are re-exported and used in `crates/common/evm/src/l1block.rs` for the standard (non-8130) fee-charging path: [4](#0-3) 

Because the operator fee scalar (`operator_fee_scalar`) and constant are values posted by the L1 attributes deposit transaction (attacker/sequencer-controlled data ingested by every node, but here the bug is in universally-applied arithmetic, not attacker-crafted data), every transaction processed post-Jovian activation on any chain configuration with a non-zero `operator_fee_scalar` will be charged (or would refund) an operator fee off by a factor of 10,000 relative to the value the operator intended to configure.

### Impact Explanation
Since `prepay` debits the payer's account balance for the miscalculated `operator_cost` before transaction execution and `settle_fees` presumably refunds/credits based on the same math, a systematic 10,000× scaling error in fee accounting:
- Can drain payer/sender balances far beyond what the protocol intends (unauthorized value extraction from every transaction sender/payer once Jovian operator fees are non-zero), or
- Can under-charge/refund incorrectly, allowing transactions to be admitted or executed while owing the correct operator fee, depending on which direction the scalar was configured/interpreted.

Both directions constitute an unauthorized transfer of funds (theft from users, or a permanent value leak/insolvency in the operator-fee sink) purely from ordinary signed transactions — meeting the High severity bar for wrong ETH-value transfers due to decimal mismatch, analogous to the CrabNetting report's WETH transfer miscalculation.

### Likelihood Explanation
This is not a rare edge case — it triggers on **every transaction** processed under the Jovian upgrade for any chain/network that configures a non-zero `operator_fee_scalar` (the L1 attributes deposit value posted each block). No attacker action is required beyond sending an ordinary transaction; the bug fires deterministically due to the fixed-point/multiplier constant mismatch, not through malicious input crafting. This significantly raises the likelihood versus typical audit findings requiring specific attacker setup.

### Recommendation
Apply the same `OPERATOR_FEE_SCALAR_DECIMAL` division to the Jovian branch that the pre-Jovian branch already applies, or otherwise ensure `OPERATOR_FEE_JOVIAN_MULTIPLIER` and `OPERATOR_FEE_SCALAR_DECIMAL` compose to the intended net precision (e.g. change the Jovian formula to `gas * operator_fee_scalar * OPERATOR_FEE_JOVIAN_MULTIPLIER / OPERATOR_FEE_SCALAR_DECIMAL`, matching the reference OP-stack Jovian operator-fee spec), and add a golden/reference test asserting parity with the upstream Jovian operator-fee formula (mirroring the existing `operator_fee_zero_before_isthmus_scalars` style tests) at non-trivial scalar values to catch scale regressions.

### Proof of Concept
Given `gas = 21_000`, `operator_fee_scalar = 1_000_000` (i.e. "1.0" in 6-decimal fixed point) and `operator_fee_constant = 0`:

- Pre-Jovian (correct scaling):
`21_000 * 1_000_000 / 1_000_000 = 21_000` (fee ≈ gas, as intended for a 1.0 scalar).

- Post-Jovian (current code):
`21_000 * 1_000_000 * 100 = 2_100_000_000_000` — i.e. `10^8` times larger than the pre-Jovian result for the identical nominal scalar value, confirming the missing `/ OPERATOR_FEE_SCALAR_DECIMAL` division. [1](#0-0)

    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }
