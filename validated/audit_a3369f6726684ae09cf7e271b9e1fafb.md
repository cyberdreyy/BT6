### Title
Miner-triggered sortition-view reset erases the current-miner invalidation flag, letting a timed-out/invalidated miner regain signing eligibility - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
In the v1 (`SortitionsView`) proposal-validation path, a single proposal carrying a consensus hash that matches neither the tracked current nor last sortition unconditionally triggers `reset_view`, which discards the signer's in-memory `SortitionState`, including the `SortitionMinerStatus` invalidation flag it had legitimately computed for the current miner (e.g. after a timeout). The one-slot miner can use this to erase that invalidation and re-propose the original (now again "Valid") block, causing signers to endorse a miner they had already correctly deemed invalid/inactive.

### Finding Description
`SortitionsView::check_proposal` tracks per-sortition validity in `SortitionMinerStatus` (`Valid`, `InvalidatedBeforeFirstBlock`, `InvalidatedAfterFirstBlock`). This flag is set in-memory when the miner times out or built off an invalid parent tenure [2](#0-1)  and is later required to be `Valid` before a proposal from `ProposedBy::CurrentSortition` is accepted [3](#0-2) .

However, when a proposal's `consensus_hash` matches neither `cur_sortition` nor `last_sortition`, and `reset_view_if_wrong_consensus_hash` is `true` (which it always is on the live `handle_block_proposal` path via `check_block_against_local_state`) [4](#0-3) , the code calls `self.reset_view(client)` and re-runs `check_proposal` [5](#0-4) . `reset_view` re-fetches `current_sortition`/`last_sortition` from the node and rebuilds fresh `SortitionState` values via `TryFrom<SortitionInfo>`, which always initializes `miner_status: SortitionMinerStatus::Valid` [6](#0-5) [7](#0-6) . If the node still reports the same sortition as "current" (which it will, since block-commit/leader-election state on the node is independent of the signer's own inactivity bookkeeping), the freshly rebuilt state for that same consensus hash comes back `Valid`, silently discarding the `InvalidatedBeforeFirstBlock`/`InvalidatedAfterFirstBlock` status that the signer itself had derived and that governs whether it may fall back to the prior sortition's miner.

Because `is_timed_out` only fires the invalidation transition when `miner_status == Valid` (`self.cur_sortition.miner_status == SortitionMinerStatus::Valid && SortitionState::is_timed_out(...)`), once the flag is reset to `Valid` the check runs again on the *next* proposal and can re-evaluate timeout state independently — but critically, any decision already made by *other* signers (or by this signer for the fallback/last-sortition miner) based on the invalidation is not synchronized; the reset is purely a local, single-signer state mutation triggered by attacker-chosen input (an out-of-view consensus hash) rather than by the trusted node's authoritative signal.

### Impact Explanation
This breaks the state machine's role as a one-per-tenure-decision equality: the `SortitionMinerStatus` invalidation is supposed to be sticky for the duration of the tenure so a signer that has already fallen back to (or is prepared to fall back to) the prior sortition's miner does not flip back and sign for the disqualified current miner. A one-slot miner can force this flip merely by sending a garbage/off-view proposal (any consensus hash outside `{cur_sortition, last_sortition}`) before re-sending its real, previously-disqualified proposal. If different signers experience this reset at different times relative to their own last-sortition fallback decisions, the signer set can end up split between signing for the disqualified current-tenure miner and the prior-tenure miner for overlapping heights — a conflicting-block/non-canonical-signature scenario (Critical bucket: "a signer signing an invalid/non-canonical/conflicting block").

### Likelihood Explanation
This requires no majority, no other signer's key, and no auth token — only the one active miner's ordinary ability to write two block proposals to its own StackerDB slot: first a proposal with an off-view consensus hash (any garbage value works, since `check_proposal` calls `reset_view` before doing any deeper checks on that value), then a re-proposal of the block it wants accepted. This is fully within the "one-slot miner (plus gossip)" reachable-path scope defined for this scan.

### Recommendation
Do not let `reset_view` unconditionally clobber `miner_status` for a sortition that the signer had already locally invalidated. Either (a) preserve `miner_status` across `reset_view` for any consensus hash the signer already has a `SortitionState` for (only replace stale/absent entries), or (b) re-derive invalidation immediately after `reset_view` using the same timeout/parent-tenure checks before allowing the reset state to be used to accept a proposal, rather than trusting the freshly-fetched `Valid` default.

### Proof of Concept
1. Signer's `SortitionsView.cur_sortition` becomes `InvalidatedBeforeFirstBlock` after `block_proposal_timeout` elapses with no signed block in the tenure (`check_proposal`, `stacks-signer/src/chainstate/v1.rs:144-163`).
2. The still-active miner sends a `BlockProposal` whose header `consensus_hash` is neither `cur_sortition.data.consensus_hash` nor `last_sortition.data.consensus_hash` (trivially satisfied, e.g. a stale/garbage hash).
3. `handle_block_proposal` → `check_block_against_local_state` calls `check_proposal(..., true, ...)`; since neither branch of the `ProposedBy` match succeeds, `reset_view_if_wrong_consensus_hash == true` triggers `self.reset_view(client)` (`v1.rs:254-265`), rebuilding `cur_sortition` with `miner_status: Valid` for the same consensus hash the node still reports as current (`v1.rs:97-105`, `546-563`).
4. The miner now re-sends its original, previously-timed-out-tenure block with the correct `consensus_hash`. `check_proposal` re-runs and, seeing `miner_status == Valid`, allows `ProposedBy::CurrentSortition` processing to proceed (`v1.rs:288-300`), where previously it would have required falling back to `last_sortition`.     /// Reset the view to the current sortition and last sortition
    pub fn reset_view(&mut self, client: &StacksClient) -> Result<(), ClientError> {
        let CurrentAndLastSortition {
            current_sortition,
            last_sortition,
        } = client.get_current_and_last_sortition()?;

        let cur_sortition = SortitionState::try_from(current_sortition)?;
        let last_sortition = last_sortition
            .map(SortitionState::try_from)
            .transpose()
            .ok()
            .flatten();

        self.cur_sortition = cur_sortition;
        self.last_sortition = last_sortition;
        Ok(())
    }
