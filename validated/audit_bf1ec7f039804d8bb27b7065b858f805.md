### Permanent Freezing of Funds via Uninitialized Hashlock in Partial Fills - ([File: contracts/BaseEscrowFactory.sol])

### Summary
A vulnerability exists in the `BaseEscrowFactory._postInteraction` function where partial fills for orders allowing multiple fills can result in the deployment of an `EscrowSrc` contract with an uninitialized (zero) hashlock. This occurs if the `lastValidated` state in `MerkleStorageInvalidator` has not been correctly updated by a preceding `takerInteraction` call. Because no preimage exists for a `bytes32(0)` keccak256 hash, the funds deposited into the escrow become permanently frozen. [1](#0-0) 

### Finding Description
In the 1inch Cross-chain Swap protocol, orders can be partially filled using a Merkle tree of secrets. The `MerkleStorageInvalidator` contract is responsible for tracking the progress of these fills via the `lastValidated` mapping, which is updated in `takerInteraction`. [2](#0-1) [3](#0-2) 

When `BaseEscrowFactory._postInteraction` is executed during an order fill, it checks if the order allows multiple fills. If it does, it retrieves the current `hashlock` (the `leaf` from the Merkle tree) from the `lastValidated` mapping using a key derived from the `orderHash` and the Merkle root. [4](#0-3) 

The issue is that if `lastValidated[key]` has not been set (e.g., due to a missing or failed `takerInteraction`), the `validated.leaf` value defaults to `bytes32(0)`. The function proceeds to deploy the `EscrowSrc` with this zero hashlock. [5](#0-4) [6](#0-5) 

### Impact Explanation
The impact is the permanent freezing of user funds. Once the `EscrowSrc` is deployed with `hashlock = bytes32(0)`, the `withdraw` and `publicWithdraw` functions become unusable. This is because they rely on the `onlyValidSecret` modifier, which requires `keccak256(secret) == hashlock`. [7](#0-6) [8](#0-7)  Since there is no known `bytes32` value that hashes to zero, the funds can never be withdrawn by the resolver. Furthermore, the user's funds are moved from their wallet to the escrow during the LOP fill, making this a direct loss of funds at rest. [9](#0-8) 

### Likelihood Explanation
The likelihood is medium. It requires a Resolver to execute a fill where the `takerInteraction` is either bypassed or fails to update the state correctly for the specific `orderHash` and root combination. While the Limit Order Protocol typically handles these interactions, a malicious or buggy resolver implementation could trigger the `postInteraction` on the factory directly or through a path that misses the state update, leading to the corrupted escrow state.

### Recommendation
Ensure that the `hashlock` retrieved from `lastValidated` is not zero before proceeding with escrow deployment. If it is zero, the transaction should revert.

```solidity
ValidationData memory validated = lastValidated[key];
hashlock = validated.leaf;
if (hashlock == bytes32(0)) revert InvalidSecretsAmount(); // Or a specific error
```

### Proof of Concept
1. A user signs a Fusion order allowing multiple fills (`allowMultipleFills` is true).
2. A Resolver initiates a fill but provides an interaction string that does not correctly trigger the `takerInteraction` on the `MerkleStorageInvalidator` for the current `orderHash`.
3. The Limit Order Protocol calls `BaseEscrowFactory._postInteraction`.
4. Inside `_postInteraction`, `lastValidated[key]` returns a default `ValidationData` struct with `index = 0` and `leaf = bytes32(0)`.
5. The check `_isValidPartialFill` may pass if the `makingAmount` corresponds to the first part (where `calculatedIndex` is 0). [10](#0-9) 
6. `EscrowSrc` is deployed with `immutables.hashlock = bytes32(0)`.
7. The user's tokens are transferred to the `EscrowSrc`.
8. Any attempt to call `EscrowSrc.withdraw` with any `secret` fails because `keccak256(secret)` never equals `bytes32(0)`.
