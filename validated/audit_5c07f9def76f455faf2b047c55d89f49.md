### Title
Any authenticated External Initiator can trigger runs of arbitrary jobs, not just jobs that name it as an allowed initiator - ([File: core/web/auth/auth.go -> AuthenticateExternalInitiator])

### Summary
`AuthenticateExternalInitiator` synthesizes a generic `UserRoleRun` session user for any successfully authenticated EI credential, and no controller ever calls `GetAuthenticatedExternalInitiator` to verify that the EI is actually bound to the target job. As a result, `PipelineRunsController.Create` treats any EI-authenticated request exactly like a normal Run-role user request and triggers `RunJobV2` for any integer job ID supplied, regardless of which EI(s) that job declares as authorized.

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) authenticates the EI token, then does: [1](#0-0) 
It sets both `SessionExternalInitiatorKey` and a synthetic `SessionUserKey` with `Role: clsessions.UserRoleRun`.

`GetAuthenticatedExternalInitiator` is defined to extract the bound EI object from context (`core/web/auth/auth.go:189-198`), but a repo-wide search shows it is referenced only inside `auth.go` itself — no controller, resolver, or middleware ever calls it to check which job(s) the authenticated EI is permitted to trigger.

In the router, the EI-or-user group wraps `POST /v2/jobs/:ID/runs` with `auth.RequiresRunRole(prc.Create)`: [2](#0-1) 
`RequiresRunRole` only checks `user.Role != UserRoleView` (`core/web/auth/auth.go:200-217`) — it never distinguishes an EI-derived session from a real user session, and never inspects `GetAuthenticatedExternalInitiator`.

Inside `PipelineRunsController.Create`: [3](#0-2) 
The comment states "only users are allowed to run jobs using int IDs - EIs not allowed," but the `isUser` check is `auth.GetAuthenticatedUser(c)`, which returns `true` for EI-authenticated requests too, because `AuthenticateExternalInitiator` populated `SessionUserKey`. So the intended EI exclusion is ineffective: any EI credential reaching this handler with a numeric job ID passes `isUser` and calls `prc.App.RunJobV2(ctx, jobID, nil)` for that arbitrary job ID with no binding check to the specific job's declared external initiators.

The only remaining binding enforcement was the UUID-keyed webhook-run path, which has since been fully disabled (`job.ErrJobTypeRemoved`, see `core/web/pipeline_runs_controller.go:103-107` and `TestRunner_WebhookJobRemoved` asserting 422 for that path). That leaves the integer-ID path as the sole functioning run-trigger route reachable by EI credentials, and it has no per-job EI authorization check at all.

### Impact Explanation
Any holder of a single valid EI access key/secret pair (obtained legitimately for one job) can invoke `POST /v2/jobs/{anyJobID}/runs` for any job in the node by integer ID, triggering pipeline execution regardless of the target job's configured/allowed initiators. This breaks the intended "one EI credential maps to exactly one authorized job" invariant, allowing unauthorized job-run triggering across the whole node (denial-of-wallet via unwanted task execution, unauthorized on-chain actions/writes if the pipeline includes ETH tx tasks, and resource exhaustion). This matches the "unauthorized job run" / authorization-bypass class in the bounty scope.

### Likelihood Explanation
Minimal precondition: possession of any one valid, non-revoked EI access key/secret (createable via `/external_initiators` by an Edit-role user, or already issued to a legitimate integrator). No admin/host access required. The exploit is a single unauthenticated-relative-to-target-job HTTP POST once EI headers are attached; fully repeatable and deterministic.

### Recommendation
In `AuthenticateExternalInitiator`, avoid granting a blanket `UserRoleRun` session usable on any endpoint; instead, keep the EI identity distinct (only set `SessionExternalInitiatorKey`) and have `PipelineRunsController.Create` call `auth.GetAuthenticatedExternalInitiator(c)` when present, then verify via the job's ORM/bridges layer that the given job's list of allowed external initiators includes this specific EI (`ei.ID`/`ei.Name`) before invoking `RunJobV2`. Reject with 401/403 otherwise.

### Proof of Concept
Handler-level integration test (extending `core/services/job/runner_integration_test.go` style):
1. Start app with `JobPipeline.ExternalInitiatorsEnabled = true`.
2. Create EI #1 and EI #2 via `POST /v2/external_initiators`.
3. Create Job A (integer ID) intended to be triggered only by EI #1, and Job B (integer ID) intended to be triggered only by EI #2 (using whatever current job-run mechanism is reachable, e.g. any job type accessible via `RunJobV2`).
4. Authenticate as EI #1 (set `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers) and `POST /v2/jobs/{JobB.ID}/runs`.
5. Assert expected: 401/403/422 (EI #1 not authorized for Job B).
6. Actual (pre-fix): 200/201 response with a created pipeline run, and `pipeline_runs` count increments for Job B — demonstrating EI #1 successfully triggered a job it was never bound to.
7. Repeat symmetric case for Job A with EI #1 to confirm legitimate use still works, isolating the bug to missing binding validation rather than broken run functionality.
