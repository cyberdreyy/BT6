### Title
Loss-adjusted withdraw receipts keyed to the wrong epoch bypass their haircut and drain the vault - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug class is a stale/dangling reference: a pointer to a `std::vector` element becomes invalid after the container mutates. The analog in `IdleCreditVault` is a stale epoch reference: `collectWithdrawFunds` stores the loss haircut under `epochNumber` **at collection time** (inside `stopEpoch`, after `deposit()` has already incremented `epochNumber`), while claims and the new-request guard resolve the haircut through `lastWithdrawRequest[_user]`, which still holds the **request** epoch. The two keys never match, so loss-adjusted receipts are paid at par and the "must claim before re-requesting" guard is dead code.

### Finding Description
In `requestWithdraw`, the user's request epoch is recorded as `lastWithdrawRequest[_user] = currentEpoch` (line 282), i.e. the epoch in which the request was opened (`epochNumber` before `stopEpoch`). [1](#0-0) 

`epochNumber` is incremented inside `deposit()` when a deposit lands while the epoch is still flagged running — exactly the `stopEpoch` funding deposit: [2](#0-1) 

`collectWithdrawFunds` (called by the CDO during `stopEpoch`/`stopEpochWithDuration` to pull the funded amount) stores the haircut under the **current** `epochNumber`: [3](#0-2) 

But `_claimLossAdjustedWithdrawRequest` and the `requestWithdraw` guard look up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the *request* epoch: [4](#0-3) [5](#0-4) 

When `collectWithdrawFunds` runs after the epoch-bumping deposit inside `stopEpoch`, the haircut is written to `lossRecoveryPriceByEpoch[N+1]` while every affected user's `lastWithdrawRequest` is `N`. Consequently:

1. `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N] == 0` and returns 0 — haircut skipped.
2. `_claimFundedWithdrawRequest` then runs: `epochNumber (N+1) <= lastWithdrawRequest (N)` is false, so no revert, and it pays `withdrawsRequests[_user]` **in full**, even though the borrower only funded `_amount < pendingBasis`. [6](#0-5) 
3. The guard in `requestWithdraw` that is supposed to force users to claim a haircutted receipt before re-requesting also reads `lossRecoveryPriceByEpoch[N] == 0` and never triggers, so users can keep stacking requests.

The vault only received the reduced `_amount`, but pays receipts at par. Early claimants over-receive; the underlying balance is exhausted before later claimants (or the default recovery reserve, protected by `_transferFundedClaim` only when `defaultRecoveryReserve != 0` [7](#0-6) ) are paid. The `lossRecoveryPriceByEpoch[N+1]` entry is orphaned forever — no user can ever have `lastWithdrawRequest == N+1` for a request made in epoch `N`.

### Impact Explanation
Direct insolvency/theft among unprivileged claimants in any epoch where `stopEpochWithDuration` realizes a loss on pending withdraw receipts: the first claimers withdraw up to `claimBasis` instead of `claimBasis * lossRecoveryPrice / 1e18`, draining underlyings funded for other receipts. Loss magnitude ≈ `(1 - lossRecoveryPrice) * pendingBasis`, bounded by the pending-withdraw bucket; later claimants' receipts become permanently unpayable. Note this exploitability depends on `IdleCDOEpochVariant.stopEpochWithDuration` invoking `collectWithdrawFunds` *after* the `deposit()` that bumps `epochNumber` — that call ordering could not be fully confirmed within this pass and is the one point to verify.

### Likelihood Explanation
Requires only an honest manager calling `stopEpochWithDuration`/`stopEpoch` with a realized loss while `pendingWithdraws > 0` — a normal operating path, no attacker privilege needed. Any tranche holder with a pending request then triggers the mispricing by an ordinary `claimWithdrawRequest`. If the ordering assumption holds, the bug fires deterministically on every loss-adjusted epoch.

### Recommendation
Key the haircut by the epoch that requests were actually made in, not the post-bump settlement epoch. Either store `lossRecoveryPriceByEpoch[epochNumber - 1]` in `collectWithdrawFunds` when `epochNumber` was already incremented for this settlement, or snapshot the request-epoch counter before `deposit()` bumps it and pass it explicitly. Alternatively, track pending receipts per request epoch (`withdrawsRequestsByEpoch` totals per epoch) and derive the haircut epoch from the pending-receipt bucket rather than the global counter.

    //    withdrawsRequestsByEpoch[alice][N] = 100, pendingWithdraws = 100.

    //    Inside: strategy.deposit(funded) executes first -> epochNumber = N + 1.

    //    _claimLossAdjustedWithdrawRequest reads lossRecoveryPriceByEpoch[N] == 0 -> skips.

    assertEq(underlying.balanceOf(alice), 100);   // expected haircutted: 50
