### Title
Claimed instant withdrawals remain in `instantWithdrawClaimsByEpoch`, inflating default recovery and insolventing the reserve - (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`requestInstantWithdraw` records each receipt in both `instantWithdrawsRequestsByEpoch` and aggregate `instantWithdrawClaimsByEpoch`. A normal funded claim clears only `instantWithdrawsRequests[_user]`; it does not remove the per-epoch or aggregate instant basis. If another same-epoch instant withdrawal remains unfunded and the borrower subsequently defaults, `finalizeDefaultRecovery` treats the already-paid receipt as both outstanding claim basis and prefunded recovery cash. This inflates `defaultRecoveryPrice`, overpays later claimants, and leaves the actual token balance below the recorded `defaultRecoveryReserve`.

### Finding Description
During an epoch in which instant withdrawals are enabled by an APR decrease, an unprivileged tranche holder can request an instant withdrawal, wait for the honest manager to fund it through `getInstantWithdrawFunds`, and claim it at par. `requestInstantWithdraw` increments `instantWithdrawsRequestsByEpoch[user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`, while `claimInstantWithdrawRequest` only zeroes `instantWithdrawsRequests[user]` and pays the user. [1](#0-0) [2](#0-1) 

A second user can create another instant withdrawal in the same epoch because `requestWithdraw` does not forbid requests while an epoch is running and the instant path delegates to `requestInstantWithdraw`. [3](#0-2)  If the borrower cannot fund that later request, `getInstantWithdrawFunds` calls `_handleBorrowerDefault`. [4](#0-3) 

At finalization, `defaultPendingClaimBasis` adds the entire current-epoch `instantWithdrawClaimsByEpoch`, including the first user's already-claimed receipt. [5](#0-4)  `_defaultPrefundedInstantReserve` also computes `instantWithdrawClaimsByEpoch - pendingInstantWithdraws`, counting the paid amount as underlying still held by the strategy. [6](#0-5)  `finalizeDefaultRecovery` then uses both inflated values to calculate `defaultRecoveryReserve` and `defaultRecoveryPrice`. [7](#0-6) 

The result is equivalent to the reported stale-allocation bug: a receipt that economically disappeared remains included in aggregate accounting. The defaulted-epoch claim path does decrement the aggregate, but only after finalization and only for the remaining claimant's own epoch bucket; it cannot remove another user's stale basis. [8](#0-7) 

### Impact Explanation
This creates direct recovery theft and protocol insolvency.

For example:

1. User A has a fully funded and claimed 100-token instant withdrawal.
2. User B has a 100-token instant withdrawal still unfunded.
3. Correct pending instant basis is 100, but `instantWithdrawClaimsByEpoch` remains 200.
4. If 140 tokens are recovered against a correct total basis of 200, the intended recovery price is 70%.
5. The contract instead records `140 + (200 - 100) = 240` reserve against a `300` total basis, producing an 80% recovery price.
6. User B receives 80 rather than 70, while the strategy only holds the real 140 plus any genuinely prefunded amount. The extra 10 paid to B is taken from later recovery claimants, and the recorded reserve remains permanently higher than the actual token balance.

Because `defaultRecoveryReserve` is decremented on each recovery transfer, the phantom prefunded amount eventually causes recovery claims to revert or leaves residual accounting that cannot be paid. [9](#0-8) 

### Likelihood Explanation
Likelihood is moderate. The sequence requires an APR-decrease instant-withdraw epoch, one funded and claimed instant receipt, a separate same-epoch unfunded instant receipt, and an honest borrower funding failure/default. All user actions are ordinary, unprivileged `requestWithdraw` and `claimInstantWithdrawRequest` calls; no malicious privileged role is required. The missing cleanup is unconditional once that sequence occurs.

### Recommendation
When a funded instant withdrawal is claimed, clear all accounting associated with that receipt:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
uint256 currentEpoch = epochNumber;

instantWithdrawsRequests[_user] = 0;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] = 0;
instantWithdrawClaimsByEpoch[currentEpoch] -= amount;
```

A safer implementation should derive the epoch from the stored request rather than assuming every open receipt belongs to `epochNumber`, since a user can potentially have receipts associated with different lifecycle states. The default-recovery claim path should also tolerate already-claimed funded receipts instead of relying on aggregate state to remain stale.

### Proof of Concept

```solidity
function testClaimedInstantReceiptInflatesDefaultRecovery() external {
    uint256 instantDelay = cdoEpoch.instantWithdrawDelay();
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, 1000, false);

    address claimedUser = makeAddr('claimed-instant-user');
    address pendingUser = makeAddr('pending-instant-user');
    address activeUser = makeAddr('active-user');
    uint256 amount = 10_000 * ONE_SCALE;

    _depositWithUser(claimedUser, amount, true);
    _depositWithUser(pendingUser, amount, true);
    _depositWithUser(activeUser, amount, true);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    vm.prank(claimedUser);
    uint256 claimedBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds();

    uint256 claimedBalPre = IERC20Detailed(defaultUnderlying).balanceOf(claimedUser);
    vm.prank(claimedUser);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(
        IERC20Detailed(defaultUnderlying).balanceOf(claimedUser) - claimedBalPre,
        claimedBasis,
        'first instant receipt was not fully claimed'
    );

    // A later same-epoch request remains unfunded.
    vm.prank(pendingUser);
    uint256 pendingBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    assertEq(
        creditVault.instantWithdrawClaimsByEpoch(creditVault.epochNumber()),
        claimedBasis + pendingBasis,
        'claimed receipt remains in aggregate basis'
    );

    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();
    _checkDefault();

    uint256 correctBasis =
        cdoEpoch.getContractValue()
        + cdoEpoch.expectedEpochInterest()
        - cdoEpoch.pendingWithdrawFees()
        + pendingBasis;

    uint256 recovered = correctBasis * 70 / 100;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // The stale claimed receipt is counted both as basis and as prefunded reserve,
    // so the finalized price exceeds the intended 70%.
    assertGt(creditVault.defaultRecoveryPrice(), 70e16);

    uint256 pendingBalPre = IERC20Detailed(defaultUnderlying).balanceOf(pendingUser);
    vm.prank(pendingUser);
    cdoEpoch.claimInstantWithdrawRequest();

    assertGt(
        IERC20Detailed(defaultUnderlying).balanceOf(pendingUser) - pendingBalPre,
        pendingBasis * 70 / 100,
        'pending claimant is overpaid from the phantom reserve'
    );
    assertLt(
        IERC20Detailed(defaultUnderlying).balanceOf(address(creditVault)),
        creditVault.defaultRecoveryReserve(),
        'recorded reserve exceeds actual recovery tokens'
    );
}
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
