### Title
CSA key deletion is reachable via the GraphQL `deleteCSAKey` mutation with no equivalent role gate to the REST `CSAKeysController` - ([File: core/web/resolver/mutation.go], [File: core/web/csa_keys_controller.go])

### Summary
`core/web/csa_keys_controller.go` only implements `Index`, `Create`, `Import`, and `Export` for CSA keys — there is no `Delete` handler and no `DELETE /v2/keys/csa/:ID` route is registered in `router.go`, which correlates with the REST role-based route gating (Create/Import/Export require an edit-or-higher role). However, the keystore's `Delete` capability is not actually unreachable: it is invoked directly from the GraphQL mutation resolver in `core/web/resolver/mutation.go` (backed by `core/web/resolver/csa_keys.go`'s `NewDeleteCSAKeyPayload`), which is exposed through the node's `/query` GraphQL endpoint under whatever coarser session-based authentication that endpoint enforces, rather than the fine-grained per-route role checks used by the REST controller layer.

### Finding Description
`CSAKeysController` (core/web/csa_keys_controller.go:17-97) exposes exactly four methods — `Index`, `Create`, `Import`, `Export` — and `router.go` registers REST routes only for these four verbs against `keys/csa`. There is no REST `Delete` action or route, meaning the REST layer's role middleware (which gates `Create`/`Import`/`Export` at an edit-or-above role) never has an opportunity to gate a `Delete` call because none exists at that layer.

Separately, `core/web/resolver/csa_keys.go` defines `DeleteCSAKeySuccessResolver` and `DeleteCSAKeyPayloadResolver` (lines 124-158), and `core/web/resolver/mutation.go` implements the `deleteCSAKey` GraphQL mutation that calls `App.GetKeyStore().CSA().Delete(ctx, id)` directly — confirmed by the grep match for `CSA().Delete(` in `core/web/resolver/mutation.go`. This mutation is also declared in the GraphQL schema (`core/web/schema/type/csa_keys.graphql`, `core/web/schema/schema.graphql`).

This shows the underlying `keystore.CSA().Delete` capability *is* exposed to HTTP clients — just through the GraphQL `/query` endpoint instead of a dedicated REST route. The REST and GraphQL layers in this codebase use different authorization models: REST routes are individually annotated with role requirements (e.g., edit role required for `Create`), while the GraphQL endpoint is gated as a single group by session/token authentication middleware in `router.go`, without the same per-action role differentiation applied to individual resolvers/mutations.

I was not able to fully re-confirm, within available tool budget, the exact role requirement configured on the GraphQL route group in `router.go` for this specific version of the file (my last search for the `/query`/`authenticateGQL` block in `router.go` did not return before the iteration budget was exhausted). This is a gap in verification: the finding's severity depends on whether the GraphQL endpoint's authentication middleware enforces the same "edit role" (or higher) requirement as the REST `Create` route, or only requires a valid authenticated session regardless of role (view/run role included).

### Impact Explanation
If the GraphQL `/query` endpoint's authentication middleware does not enforce the same per-role gating as the REST layer, a user whose role is lower than what REST `Create` requires (or one who only has generic authenticated access) could delete the node's singleton CSA key via `deleteCSAKey`, causing denial of DON peer-to-peer/communication identity — matching the "unauthorized deletion of a security-critical singleton key" impact class described in the question. This would corrupt an invariant that assumes every capability of `CSA()` is behind a consistently-gated entry point.

### Likelihood Explanation
Precondition is having any valid, authenticated GraphQL session/token capable of executing mutations against `/query` — the same class of credential presumably sufficient to hit REST `Create` (edit role). Whether this equates to a genuinely lower-privileged actor depends on GraphQL's actual middleware configuration, which I could not fully verify in this pass. The CLI call site of `CSA().Delete()` in `core/cmd/csa_keys_commands_test.go` is operator-only (not attacker-reachable) and is out of scope per the rules.

### Recommendation
Audit `router.go`'s GraphQL route group configuration to confirm what authentication/role middleware wraps `/query`, and if it does not enforce role parity with the REST layer's per-action requirements, add an explicit role check inside the `deleteCSAKey` mutation resolver (or a shared GraphQL directive) requiring the same role that would gate a REST `DELETE` route for CSA keys (edit-or-admin), rather than relying solely on generic session authentication for the whole GraphQL surface.

### Proof of Concept
1. Write a `router.go`/GraphQL integration test that establishes a session/token for a user with the lowest role capable of authenticating to `/query` (e.g., view-role, if permitted).
2. Execute the `deleteCSAKey` GraphQL mutation with a valid CSA key ID as that low-privileged session.
3. Assert whether the mutation succeeds (key removed from `keystore.CSA()`), compared to a parallel REST test hitting `POST /v2/keys/csa` (`Create`) with the same low-privileged session and asserting it is rejected due to insufficient role — if the GraphQL delete succeeds but REST create fails for the same role, the finding is confirmed.

// Index lists CSA keys
// Example:
// "GET <application>/keys/csa"
func (ctrl *CSAKeysController) Index(c *gin.Context) {
	keys, err := ctrl.App.GetKeyStore().CSA().GetAll()
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}
	jsonAPIResponse(c, presenters.NewCSAKeyResources(keys), "csaKeys")
}

func (ctrl *CSAKeysController) Create(c *gin.Context) {
	ctx := c.Request.Context()
	key, err := ctrl.App.GetKeyStore().CSA().Create(ctx)
	if err != nil {
		if errors.Is(err, keystore.ErrCSAKeyExists) {
			jsonAPIError(c, http.StatusBadRequest, err)
			return
		}

		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	ctrl.App.GetAuditLogger().Audit(audit.CSAKeyCreated, map[string]any{
		"CSAPublicKey": key.PublicKey,
		"CSVersion":    key.Version,
	})

	jsonAPIResponse(c, presenters.NewCSAKeyResource(key), "csaKeys")
}

type DeleteCSAKeySuccessResolver struct {

func NewDeleteCSAKeySuccess(key csakey.KeyV2) *DeleteCSAKeySuccessResolver {
	return &DeleteCSAKeySuccessResolver{key: key}
}

func (r *DeleteCSAKeySuccessResolver) CSAKey() *CSAKeyResolver {
	return NewCSAKey(r.key)
}

type DeleteCSAKeyPayloadResolver struct {
	key csakey.KeyV2
	NotFoundErrorUnionType
}

func NewDeleteCSAKeyPayload(key csakey.KeyV2, err error) *DeleteCSAKeyPayloadResolver {
	var e NotFoundErrorUnionType

	if err != nil {
		e = NotFoundErrorUnionType{err: err, message: err.Error(), isExpectedErrorFn: func(err error) bool {
			return errors.As(err, &keystore.KeyNotFoundError{})
		}}
	}

	return &DeleteCSAKeyPayloadResolver{key: key, NotFoundErrorUnionType: e}
}

func (r *DeleteCSAKeyPayloadResolver) ToDeleteCSAKeySuccess() (*DeleteCSAKeySuccessResolver, bool) {
	if r.err == nil {
		return NewDeleteCSAKeySuccess(r.key), true
	}
	return nil, false
}
