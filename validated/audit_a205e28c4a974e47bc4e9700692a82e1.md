### Title
Stale-epoch instant withdraw receipts escape the default haircut and drain funded claim reserves — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The external bug (ALPINE-CVE-2022-0561) is a null/stale source pointer used where a populated one was expected, causing a crash. The credit-vault analog is stale-epoch receipt state being consumed where only current-epoch state was expected. `IdleCreditVault.claimInstantWithdrawRequest` pays a user's *aggregate* `instantWithdrawsRequests` balance at par, but default finalization only haircuts and reserves for receipts recorded in `instantWithdrawClaimsByEpoch[epochNumber]` — the single default epoch. Unfunded instant receipts created in an earlier epoch are invisible to `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest`, so their holder withdraws at par from strategy underlyings that belong to other claimants.

### Finding Description
- `requestInstantWithdraw` records receipts per-epoch (`instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`) and globally in `instantWithdrawsRequests[_user]` / `pendingInstantWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:356-375).
- `pendingInstantWithdraws` is decremented only when the CDO calls `collectInstantWithdrawFunds` (line 398-403). If the CDO has insufficient liquidity at `getInstantWithdrawFunds`, the receipt stays unfunded and survives into later epochs — `instantWithdrawsRequestsByEpoch[_user][oldEpoch]` remains non-zero while `epochNumber` advances.
- On default, `defaultPendingClaimBasis` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the current epoch — so the old-epoch unfunded receipt never enters `totalBasis` and never shares the haircut (lines 644-649).
- `finalizeDefaultRecovery` sets `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0`, which is true whenever the old receipt exists (line 696).
- After finalization, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (lines 842-856). Then it reads `instantWithdrawsRequests[_user]` — which still contains the old-epoch amount — and pays it 1:1 via `_transferFundedClaim` (lines 387-392).
- `_transferFundedClaim` only guards `balance - defaultRecoveryReserve >= amount` (lines 897-907). The old receipt had no funding collected, so the payout is sourced from underlyings funding other users' normal funded receipts, or reverts once those are drained.

The invariant broken is "one receipt, one haircutted/funded payout": an unfunded pre-default receipt is treated as if it were a funded pre-default receipt, receiving par value instead of `defaultRecoveryPrice` or nothing.

### Impact Explanation
An attacker who holds an unfunded instant receipt from an epoch prior to the default epoch can call `claimInstantWithdrawRequest` (through `IdleCDOEpochVariant.claimInstantWithdrawRequest`) and receive the full un-haircutted amount. This steals underlyings reserved for legitimately funded receipts — direct theft with a loss equal to the attacker's unfunded receipt size. If the strategy lacks non-reserve balance, the claim reverts, permanently freezing the attacker's own receipt but also blocking claims for any user whose aggregate `instantWithdrawsRequests` mixes funded and unfunded components (the burn at line 389 is all-or-nothing).

### Likelihood Explanation
Requires the pool to be in instant-withdraw mode (`_isInstantWithdrawEnabled`, i.e. APR dropped by more than `instantWithdrawAprDelta`), an instant receipt remaining unfunded across an epoch boundary (borrower liquidity shortfall — a normal credit event, not attacker privilege), and a subsequent borrower default finalized via `finalizeDefaultRecovery`. Any KYC'd lender can be the receipt holder; no privileged role is needed. The sequence of epochs is constrained but all transitions use honest manager/borrower calls.

### Recommendation
In `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest`, account for *all* unfunded instant receipts, not only `instantWithdrawClaimsByEpoch[epochNumber]`. Either iterate/aggregate all per-epoch instant bases that contributed to `pendingInstantWithdraws`, or track a global `totalInstantClaimBasis` parallel to `pendingInstantWithdraws` so every unfunded receipt — regardless of request epoch — enters the recovery basis and is cleared at `defaultRecoveryPrice` in `claimInstantWithdrawRequest`.

### Proof of Concept
Foundry fork scenario (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testStaleEpochInstantReceiptEscapesDefault() external {
    // Setup: instant-withdraw enabled deployment, deposit AA, start epoch 0.
    idleCDO.depositAA(100_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);

    // Force APR drop > instantWithdrawAprDelta so requestWithdraw routes to instant path.
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // drops unscaledApr
    // ... trigger requestWithdraw so requestInstantWithdraw mints a receipt in epoch 0.
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Borrower does NOT refund enough at stopEpoch -> collectInstantWithdrawFunds
    // collects < pendingInstantWithdraws (or nothing); receipt stays unfunded.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, expectedInterest); // instant receipt partially unfunded

    // Epoch 1 runs; borrower then defaults (or stopEpochWithDuration loss -> default).
    _startEpochAndCheckPrices(1);
    // ... borrower default path: _handleBorrowerDefault -> finalizeDefault -> finalizeDefaultRecovery
    // Recovery price < 1 (e.g. 50%).

    // Attacker claims: _claimDefaultedInstantWithdrawRequest only clears
    // instantWithdrawsRequestsByEpoch[user][defaultEpoch] (epoch 1) == 0,
    // then pays full instantWithdrawsRequests[user] at par.
    uint256 balBefore = underlying.balanceOf(address(this));
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balBefore;

    // Assert attacker received par (100%) instead of defaultRecoveryPrice (e.g. 50%),
    // i.e. paid > receipt * defaultRecoveryPrice / 1e18.
    assertGt(paid, receipt * strategy.defaultRecoveryPrice() / 1e18);
}
```

Key assertion: `paid` equals the full receipt while every other defaulted claimant receives `claimBasis * defaultRecoveryPrice / 1e18`, and the overpayment reduces funded underlyings backing other users' pending claims (or makes their claims revert in `_transferFundedClaim`).
