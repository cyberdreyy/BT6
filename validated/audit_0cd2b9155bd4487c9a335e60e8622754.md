### Title
Credential-revoked wallets can still withdraw via unguarded claim paths and unrestricted tranche-token transfers - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The vault gates state-changing entry points (`_deposit`, `depositDuringEpoch`, `requestWithdraw`) behind `isWalletAllowed(msg.sender)`, but both payout legs — `claimWithdrawRequest()` and `claimInstantWithdrawRequest()` — perform no Keyring check. Combined with `IdleCDOTranche` being a plain ERC20 with no transfer restrictions, a user whose Keyring credential is revoked (the analog of a "suspended" partyB) can still extract all funds, directly or by routing tranche tokens through a still-credentialed account they control — exactly the same bypass shape as the Symmetrical report, where the suspension check existed on withdrawal but not on the path that actually moved funds.

### Finding Description
`IdleCDOEpochVariant.isWalletAllowed` checks `IKeyring(keyring).checkCredential(keyringPolicyId, _user)` [1](#0-0) . The check is enforced on deposit [2](#0-1) , mid-epoch deposit [3](#0-2) , and `requestWithdraw` [4](#0-3) . However:

1. `claimWithdrawRequest()` and `claimInstantWithdrawRequest()` forward `msg.sender` to `IdleCreditVault` with no credential check — `claimInstantWithdrawRequest` only requires `allowInstantWithdraw` [5](#0-4) .
2. `IdleCDOTranche` is a vanilla `ERC20` — there is no `_beforeTokenTransfer` hook, so a revoked wallet can freely `transfer()` tranche tokens [6](#0-5) .

Attack sequence (epoch running, Keyring enabled):

- Eve deposits while KYC'd, receives AA/BB tranche tokens.
- Keyring revokes Eve's credential (sanction/fraud). `requestWithdraw` now reverts for Eve [7](#0-6) .
- Bypass A: if Eve already has a pending request (`lastWithdrawRequest`) or an instant-withdraw receipt from the `requestInstantWithdraw` leg, she calls `claimWithdrawRequest()` / `claimInstantWithdrawRequest()` and receives underlying anyway — the payout leg is unchecked.
- Bypass B (full mirror of the report): Eve `transfer()`s her tranche tokens to a second KYC-passing wallet under her control (or a cooperating KYC'd lender), which calls `requestWithdraw(0, tranche)` — `_amount == 0` resolves to the full balance [8](#0-7)  — and later claims. The suspended party's entire position exits the system.

The codebase's own test acknowledges the intent to block revoked wallets from `requestWithdraw` [9](#0-8) , yet the transfer-and-claim route remains open.

### Impact Explanation
The access-control invariant ("only credentialed wallets may move value out of the vault") is broken. A revoked user recovers 100% of principal + accrued interest; the cost to the protocol is a compliance/sanctions failure identical in nature to the reported High. There is no direct theft of other users' funds — the loss is the failure of the suspension mechanism itself, matching the source finding's severity rationale.

### Likelihood Explanation
Requires only a revoked credential plus either a pre-existing withdraw request or a second credential-passing address. No privileged cooperation, no timing race, no oracle dependency — a plain ERC20 transfer plus one whitelisted counterparty suffices. Tranche tokens are designed to be transferable (secondary sales via `IdleCreditVaultWriteOffEscrow` exist), so the path is always available while the epoch machine permits withdraw requests.

### Recommendation
- Add `isWalletAllowed(msg.sender)` checks (or a conscious opt-out flag like the existing `keyringAllowWithdraw` pattern) to `claimWithdrawRequest()` and `claimInstantWithdrawRequest()` in `IdleCDOEpochVariant.sol`, if revocation is meant to freeze payouts.
- If revocation must be airtight, gate tranche-token transfers (e.g., a `_beforeTokenTransfer` hook consulting `isWalletAllowed` on the recipient), acknowledging this breaks secondary-sale composability. At minimum, document that Keyring revocation does not block claims or transfers as an accepted design limitation.

Key gap: `claimWithdrawRequest`/`claimInstantWithdrawRequest` at `contracts/IdleCDOEpochVariant.sol:967-979` lack the `isWalletAllowed` guard present on every other user entry point, and `contracts/IdleCDOTranche.sol` imposes no transfer restriction. Caveat: whether paying out already-matured requests to revoked wallets is intended is a design decision — the comment "old requests can still be claimed" suggests partial awareness; if intentional for claims, the transferable-token route (3b) still constitutes the unmitigated bypass.

contract IdleCDOTranche is ERC20 {
  // allowed minter address
  address public minter;
  // liquidity burned at first tranche deposit
  uint256 internal constant MIN_LIQUIDITY = 10**3;

  /// @param _name tranche name
  /// @param _symbol tranche symbol
  constructor(
    string memory _name, // eg. IdleDAI
    string memory _symbol // eg. IDLEDAI
  ) ERC20(_name, _symbol) {
    // minter is msg.sender which is IdleCDO (in initialize)
    minter = msg.sender;
  }

  /// @param account that should receive the tranche tokens
  /// @param amount of tranche tokens to mint
  function mint(address account, uint256 amount) external {
    require(msg.sender == minter, '6');
    // burn MIN_LIQUIDITY on first tranche deposit
    if (totalSupply() == 0) {
      _mint(address(1), MIN_LIQUIDITY);
      amount -= MIN_LIQUIDITY;
    }
    _mint(account, amount);
  }

  /// @param account that should have the tranche tokens burned
  /// @param amount of tranche tokens to burn
  function burn(address account, uint256 amount) external {
    require(msg.sender == minter, '6');
    _burn(account, amount);
  }
}
