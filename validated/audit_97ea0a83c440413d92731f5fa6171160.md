### Title
Stale rejected weight is never cleared when a signer re-evaluates from a rejection to an acceptance, letting a block be declared dead by a rejection-weight majority that no longer exists - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side StackerDB listener tallies `total_weight_approved` and `total_weight_rejected` per block independently, keyed by whether a slot has ever sent an `Accepted` or `Rejected` `BlockResponse`. The signer-side state machine explicitly allows a `LocallyRejected` block to transition to `LocallyAccepted` on re-evaluation (e.g., after `ConnectivityIssues`, `NoSortitionView`, `TestingDirective`, `ConsensusHashMismatch`, `NoSignerConsensus`, `NotRejected`, or `Unknown` rejection reasons), per `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`. When that flip happens, the signer broadcasts a new `Accepted` message, but the node's aggregator never removes that signer's weight from `total_weight_rejected`, so the same signer's weight is now counted in both tallies simultaneously.

### Finding Description
`StackerDBListener` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` maintains a `BlockStatus` struct per proposed block with independent counters `total_weight_approved`, `total_weight_rejected`, and a `responded_signers: HashSet<slot_id>` set: [1](#0-0) 

On `BlockResponse::Rejected`, the handler adds the signer's weight to `total_weight_rejected` guarded only by `block.responded_signers.insert(slot_id)` (i.e. "first response wins" for the rejected counter): [2](#0-1) 

On `BlockResponse::Accepted`, the handler adds the signer's weight to `total_weight_approved` guarded by `!block.gathered_signatures.contains_key(&slot_id)`, and unconditionally does `block.responded_signers.insert(slot_id)`: [3](#0-2) 

Neither branch subtracts weight from the *other* tally when a signer switches sides. Concretely: a signer sends `Rejected` first (weight added to `total_weight_rejected`, slot marked responded); later, per the signer's own state machine, it re-evaluates the same block (an allowed `LocallyRejected -> LocallyAccepted` transition documented at `docs/signer-flows.md` and gated by `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`) and sends `Accepted`. The node then adds that signer's weight to `total_weight_approved` as well — but the earlier contribution to `total_weight_rejected` is never removed. The node's own comment in `reset_rejections` acknowledges rejection weight is mutable/resettable ("Reset rejections for a block proposal ... Block approvals cannot be cleared because an old approval could always be used to make a block reach the approval threshold") but this reset only fires on a proposal-timeout retry path, not on a per-signer flip from reject to accept: [4](#0-3) 

This is structurally the same class of bug as the referenced report: a state change (a signer's vote flipping) is not propagated to the aggregate counter that was derived from the old state (`total_weight_rejected`), so the aggregate no longer reflects the true set of current signer votes — the same signer's weight is "double counted" across the accept and reject tallies. The rejection threshold check: [5](#0-4) 

can therefore trip (and notify the waiting miner thread that the block should be considered dead) using stale rejection weight from signers who have since accepted, even though the true, current rejection weight is lower than what's recorded.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality that the coordinator relies on to decide whether a block is globally accepted or globally rejected: the miner-side aggregator can conclude "over 30% rejected — 70% is now impossible" using inflated/stale rejection weight that includes signers who have already reverted to acceptance. That can cause the node to abandon a proposal (and re-mine) even when the live signer set's acceptance weight is actually sufficient or trending toward sufficiency, a liveness degradation of the block-production pipeline. It does not directly cause an invalid/non-canonical block to be signed (the `total_weight_approved` path independently gates real signatures, and the underlying chainstate `verify_signer_signatures` in `stackslib/src/chainstate/nakamoto/mod.rs` re-validates real signatures against the reward set), so this analog lands as a High-severity liveness wedge on the node/miner side rather than a Critical safety break: repeated proposal churn/rejection due to phantom stale-rejected weight can stall block production for a tenure until a timeout/retry path (`reset_rejections`) happens to clear it.

### Likelihood Explanation
This requires no majority collusion and no signer keys beyond the acting signer's own legitimate re-evaluation, which is an explicitly supported and documented state transition (`LocallyRejected -> LocallyAccepted`, gated by `should_reevaluate_reject_reason`). Any of the several reject reasons flagged as re-evaluable (`ConnectivityIssues`, `NoSortitionView`, `TestingDirective`, `ConsensusHashMismatch`, `NoSignerConsensus`, `NotRejected`, `Unknown`) can trigger it in normal operation (e.g., transient RPC/connectivity failures, or protocol-version consensus catching up), making this a realistically reachable condition rather than a purely theoretical one, though it needs a legitimate reject→accept flip from at least one signer to manifest, and needs the block's rejected weight to already be reasonably close to the 30% cutoff for the stale count to matter.

### Recommendation
Track a per-slot "current vote" (Accepted/Rejected) instead of independently-accumulating monotonic counters, or explicitly move the signer's weight from `total_weight_rejected` to `total_weight_approved` (and vice versa, if a rejection ever supersedes an already-recorded acceptance under the analogous flip) when a slot's response changes. At minimum, when processing a `BlockResponse::Accepted` for a `slot_id` already present in `responded_signers` due to a prior rejection, `total_weight_rejected` should be decremented by that signer's weight before/while `total_weight_approved` is incremented, keeping both tallies consistent with the set of signers' *current* votes rather than a union of all votes ever seen.

### Proof of Concept
Conceptual reproduction (network-observable, no privileged access required):
1. Configure N signers with signer1 controlling weight w1 such that existing `total_weight_rejected` is just under `total_weight - weight_threshold` (i.e., close to but below the 30%-rejected cutoff).
2. Have signer1 send `BlockResponse::Rejected` for block B with a reason in the re-evaluable set (e.g. force a transient RPC failure so the reason is `ConnectivityIssues`, or use the `TestingDirective` reject-all test hook seen in `stacks-node/src/tests/signer/v0/signers_consider_consensus_blocks.rs`). Node's `total_weight_rejected += w1`.
3. Clear the injected condition and have the miner re-propose block B (identical `signer_signature_hash`) so `should_reevaluate_block`/`should_reevaluate_reject_reason` on signer1 returns true and signer1 now validates and locally accepts B, broadcasting `BlockResponse::Accepted`.
4. On the node, observe `total_weight_approved += w1` (correct) while `total_weight_rejected` is left unchanged, still including `w1` from step 2.
5. Have any additional signers (whose combined rejected weight plus the stale `w1` crosses `total_weight - weight_threshold`) send genuine rejections; the node's check at `stacks-node/src/nakamoto_node/stackerdb_listener.rs:567-574` fires and the coordinator/miner thread is signaled that the block is dead, even though signer1's live vote is actually acceptance and the true current rejected weight (excluding the stale double-counted w1) may not have crossed the cutoff.

Note: this PoC path was reasoned from static code paths across `stacks-node/src/nakamoto_node/stackerdb_listener.rs` and `stacks-signer/src/v0/signer.rs`; I did not execute this against a running signer/node test harness, so the exact numeric thresholds and timing needed to trigger the observable livelock in a live `SignerTest` were not verified end-to-end.

    /// Insert a block into the block status map with initial values.
    pub fn insert_block(&self, block: &NakamotoBlockHeader) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        let block_status = BlockStatus {
            responded_signers: HashSet::new(),
            gathered_signatures: BTreeMap::new(),
            total_weight_approved: 0,
            total_weight_rejected: 0,
            failed_txids: HashMap::new(),
        };
        blocks.insert(block.signer_signature_hash(), block_status);
    }

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
