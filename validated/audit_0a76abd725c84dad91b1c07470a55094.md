### Title
Signer equivocation on v1 protocol: `DuplicateBlockFound` guard checks only globally-accepted tenure-start blocks, letting a signer sign two conflicting tenure-change blocks for the same tenure - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The external report's bug class is "code assumes only one specific effect occurs and accounts for it, but the real implementation lets an unaccounted-for alternative happen, breaking the safety invariant the accounting relied on." In this repo's v1 chainstate proposal validation, `validate_tenure_change_payload` guards against double-signing a tenure's first block by checking only for a **globally accepted** duplicate, whereas the v2 code path (a documented, deliberate fix) checks for any **signed** (locally or globally accepted) duplicate. This mismatch allows a v1 signer to sign two different, conflicting tenure-change blocks for the same tenure before either reaches global acceptance.

### Finding Description
`SortitionsView::validate_tenure_change_payload` in v1 checks for a duplicate first-block-of-tenure using: [1](#0-0) 
which calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` — i.e. it only rejects the second tenure-change block as `DuplicateBlockFound` if the signer's *first* block for that tenure already reached **global** acceptance (70% signature weight, or node-confirmed).

The v2 equivalent explicitly closed this gap by checking any block the signer has *signed* (`get_last_signed_block`, covering both locally- and globally-accepted states), with the comment documenting this was intentional: [2](#0-1) 

The documentation for the shared chainstate machinery confirms this `DuplicateBlockFound` check runs **only once, at proposal arrival**, and is never re-run at pre-commit or signing time for tenure-change blocks (since those only re-check the *parent* tenure, never their own): [3](#0-2) 

The only later backstop is the "own-tenure conflict" guard in `handle_block_pre_commit`, which asks the node whether its tenure tip has confirmed the conflicting block at or above the proposed height: [4](#0-3) 

This backstop only refuses to sign if `get_tenure_tip` reports the node's tenure tip **already at or above** the proposed height. But `get_tenure_tip` reflects the node's Stacks chain state, which only advances once a block is globally accepted and pushed to the node — exactly the precondition that has *not yet* occurred in this attack (the first tenure-change block B1 is only locally/`signed_self`, not globally accepted, so it was never pushed to the node). In that case the code path is "no — never confirmed → SIGN" per the documented pre-commit flowchart: [5](#0-4) 

Chaining these two gaps: a v1 signer that has already `signed_self` a first tenure-change block B1 for tenure T (but B1 has not yet reached the 70% global-acceptance threshold) can receive a second, competing tenure-change proposal B2 also targeting tenure T. At proposal time, `validate_tenure_change_payload` passes B2 because `get_last_globally_accepted_block(T)` is still `None` (B1 isn't global yet). B2 is validated, pre-committed, and once its own pre-commit threshold is reached, the only remaining safety net (`get_signed_conflicts` + the own-tenure `get_tenure_tip` check) also fails to block it, because the node has never seen B1 (it wasn't pushed) so its tenure tip for T is unconfirmed. The signer then signs B2 — producing two valid signatures from the same signer over two conflicting tenure-change blocks (B1 and B2) for the same tenure/height.

This breaks the "one-per-height" / no-equivocation invariant that `DuplicateBlockFound` and the conflict guard exist to enforce, and can let a byzantine or forking miner drive different subsets of v1 signers to sign two mutually-conflicting first blocks for the same tenure, undermining the assumption that reaching a 70% threshold on one candidate precludes reaching 70% on a competing one.

### Impact Explanation
This is a Critical-class issue per the rubric: a signer can be induced to place its signature over a conflicting/non-canonical block (a genuine double-sign/equivocation), which is exactly the safety property the pre-commit/threshold and `DuplicateBlockFound` machinery is designed to prevent. If enough v1 signers are tricked identically (each holding an unreached-threshold local signature over B1 when B2 arrives), aggregate signatures over two distinct tenure-start candidates for the same tenure become possible, which is a fork/equivocation at the signer-quorum level.

### Likelihood Explanation
Reachable with a single miner (one sortition winner, or any actor able to broadcast a second `BlockProposal`/`SignerMessageV0::BlockProposal` for the same tenure) plus normal signer gossip — no majority of signers or another signer's key is required to *trigger* the flawed check; only the natural timing window between "signed locally" and "globally accepted" needs to be exploited, which routinely exists during normal pre-commit/signature aggregation. It requires the network to still be running the v1 signer chainstate path (this codebase supports both v1 and v2, selecting based on active protocol version), so likelihood is contingent on v1 remaining an active/supported protocol version.

### Recommendation
Align `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` with the v2 fix: check `signer_db.get_last_signed_block(&block.header.consensus_hash)` (or equivalent "any block we have signed_self or signed_group") instead of `get_last_globally_accepted_block`, so a second tenure-change proposal for a tenure that already has a locally-signed candidate is rejected with `DuplicateBlockFound` at proposal time, matching the intended fix already present in v2.

### Proof of Concept
1. Run a v1-protocol signer set (protocol version selected such that `chainstate/v1.rs` `validate_tenure_change_payload` is in use).
2. Miner proposes tenure-change block B1 for tenure T. A given signer S validates it, precommits, and (since fewer than 70% of the set has yet precommitted/signed) reaches `signed_self` for B1 via `mark_locally_accepted` in `handle_block_pre_commit`/`store_and_process_block_signature`, but B1 never reaches the 70% global threshold and is never pushed to S's node (so the node's `get_tenure_tip` for T stays at the parent tenure).
3. Before B1's threshold is reached network-wide, the (byzantine or forking) miner broadcasts a second, conflicting tenure-change block B2 also for tenure T (e.g. same parent tenure, different transactions/ordering).
4. On S, `check_proposal` → `validate_tenure_change_payload` calls `get_last_globally_accepted_block(T)`, which returns `None` (B1 is only locally signed), so the `DuplicateBlockFound` rejection is skipped and B2 is accepted for validation/pre-commit.
5. Once B2's pre-commit threshold is reached on S, `handle_block_pre_commit`'s conflict-guard calls `get_tenure_tip(T)`; because B1 was never pushed to the node, this returns "unconfirmed for T" (or 404/below-height), so the guard does not block, and S proceeds to `SIGN` B2.
6. S now holds valid signatures (`signed_self`) over both B1 and B2 — two conflicting tenure-change blocks at the same height/tenure — demonstrating the equivocation.

(Note: full exercise of this scenario end-to-end, including exact timing thresholds and node RPC responses, would benefit from running the existing integration test harness in `stacks-node/src/tests/signer/v0/` and `stacks-signer/src/chainstate/tests/v1.rs`, which already contain scaffolding for `check_parent_tenure_choice`/`validate_tenure_change_payload` scenarios that could be adapted to assert this specific double-sign.)
