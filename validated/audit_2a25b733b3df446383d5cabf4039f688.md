### Title
JWT replay guard in workflow metadata handler is check-then-act, not atomic, allowing a single JWT to authorize concurrent duplicate workflow trigger requests - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The external report's root cause is a state-tracking value that is checked/consumed in one step but updated in a separate, non-atomic step, so the invariant the check depends on can be violated between the two steps. The `jwtReplayCache` used by `WorkflowMetadataHandler.Authorize` to prevent JWT replay on HTTP-trigger requests exhibits the same pattern: the "already used" check and the "mark as used" write are two independent locked operations rather than one atomic check-and-record, unlike the correctly-implemented `RequestReplayGuard` used elsewhere in the vault gateway handler.

### Finding Description
`Authorize` first calls `h.jwtCache.isReplay(claims.ID)` (RLock, read, RUnlock) and, only after further authorization-key checks succeed, calls `h.jwtCache.recordUsage(claims.ID)` (Lock, write, Unlock): [1](#0-0) 

`isReplay` and `recordUsage` are implemented as two separate, independently-locked methods: [2](#0-1) 

Because there is a window between the `isReplay` read and the `recordUsage` write during which no lock is held across both operations, two goroutines processing the same incoming JWT concurrently (e.g. the gateway receiving the same HTTP trigger request twice, or a client/attacker replaying the exact same signed request in parallel) can both pass `isReplay` before either calls `recordUsage`, so both proceed to be treated as authorized. This is structurally identical to the reported bug class: a credited/consumed value (`creditedNodeETH` in the report; here, "JWT already used" state) is read and later written in disjoint steps instead of being updated atomically at the point of use, breaking the invariant the rest of the system relies on.

Contrast this with the correct pattern already present in the same codebase for the Vault gateway handler, where check-and-record is a single atomic critical section under one lock: [3](#0-2) 

### Impact Explanation
A successfully-authorized HTTP trigger JWT is meant to authorize exactly one workflow execution (`Authorize` is the gate before dispatching `MethodWorkflowExecute` requests to DON nodes). The check-then-act race allows the same JWT to pass authorization more than once under concurrent delivery, resulting in duplicate/unauthorized additional workflow executions from a single authorized request — a request-impersonation/replay-bypass condition on an internet-facing gateway path reachable by unprivileged callers. This is a Medium-severity impact: it does not grant new privileges, but it breaks the "run at most once per JWT" invariant, potentially causing duplicate billing/side-effects or resource exhaustion via repeated triggering.

### Likelihood Explanation
Triggering the race requires the same JWT (jti) to reach `Authorize` concurrently — plausible via network-level retries, duplicate delivery, or an attacker deliberately firing the same signed request twice in short succession, since JWTs remain within their replay window (`JWTReplayPeriodMs`) and no synchronization spans the whole authorize-and-record path. This is a narrow timing window, so likelihood is Low-to-Medium in practice, but the flaw is deterministic in code review terms (the two calls are provably non-atomic).

### Recommendation
Merge `isReplay` and `recordUsage` into a single atomic check-and-record operation performed under one write lock, mirroring the `RequestReplayGuard.CheckAndRecord` pattern already used for the Vault gateway handler:

```go
func (cache *jwtReplayCache) checkAndRecord(jti string) error {
    cache.mu.Lock()
    defer cache.mu.Unlock()
    if _, exists := cache.cache[jti]; exists {
        return ErrReplay
    }
    cache.cache[jti] = time.Now()
    return nil
}
```

Call this once, immediately after JWT signature verification and before/instead of the separate `isReplay`/`recordUsage` calls in `Authorize`.

### Proof of Concept
1. Client signs a valid HTTP-trigger JWT with a given `jti` for a workflow it is authorized to call.
2. Client (or network retry logic, or an attacker replaying the captured request) sends two requests carrying the identical JWT to the gateway at nearly the same time.
3. Goroutine A calls `Authorize`: `isReplay(jti)` returns false (not yet recorded); it proceeds to validate authorized keys.
4. Before goroutine A reaches `recordUsage(jti)`, goroutine B calls `Authorize`: `isReplay(jti)` also returns false because A has not yet recorded it.
5. Both A and B pass authorization and both workflow-execute requests are dispatched to the DON, even though only one JWT-authorized execution was intended. [4](#0-3)

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
```

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```
