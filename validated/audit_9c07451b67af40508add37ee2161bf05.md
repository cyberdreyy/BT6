### Title
`get_block` silently returns `None` instead of erroring for cleaned-up confirmed slots because the cleanup check is only applied on the finalized path - (File: `rpc/src/rpc.rs`)

### Summary
`JsonRpcRequestProcessor::get_block` handles two branches depending on whether the requested slot is already finalized (rooted) or only optimistically confirmed. Both branches fetch block data from the `Blockstore`, but only the finalized branch validates whether a failed lookup is due to the slot's data having been purged/compacted by the blockstore cleanup service. The confirmed-slot branch omits this check entirely, so a purged-but-still-confirmed slot silently resolves to `Ok(None)` instead of the correct `BlockCleanedUp` error.

### Finding Description
In `get_block` [1](#0-0) , when the requested `slot` is `<= highest_super_majority_root` (finalized), the code fetches the block and explicitly runs `check_blockstore_root` and `check_slot_cleaned_up` on the result before treating a failure as "block not found": [2](#0-1) 

`check_slot_cleaned_up` specifically distinguishes "this slot never had a block" from "this slot's block data was compacted away by the cleanup service", surfacing the latter as `RpcCustomError::BlockCleanedUp` rather than silently returning `None`: [3](#0-2) 

However, in the `else if commitment.is_confirmed()` branch — used when the slot is not yet finalized but is present in `confirmed_bank.status_cache_ancestors()` — the code calls `blockstore.get_complete_block(slot, true)` and immediately converts the `Result` to an `Option` via `.ok()`, with no equivalent call to `check_slot_cleaned_up` (or `check_blockstore_root`): [4](#0-3) 

If `get_complete_block` fails with `BlockstoreError::SlotCleanedUp` (the block's shred/transaction-status data was purged, e.g. by `--limit-ledger-size` driven `purge_slots`/`BlockstoreCleanupService`, or by `rpc_scan_and_fix_roots`), `result.ok()` becomes `None`, `encoded_block_future` becomes `None.into()`, and `get_block` returns `Ok(None)` to the caller. This is exactly the class of bug from the external report: a mandatory post-condition check (`afterWithdrawChecks` in the original; `check_slot_cleaned_up` here) is applied only inside one branch of an if/else that covers two semantically-parallel code paths, and is silently skipped on the other path.

### Impact Explanation
An unprivileged RPC client issuing a single `getBlock` request with `commitment: "confirmed"` for a slot whose data has been cleaned up by the local cleanup service receives `Ok(None)`, which per the JSON-RPC API contract means "no block produced for this slot / block not yet available." In reality the block did exist and was confirmed; the correct signal is the distinguishable `BlockCleanedUp` error (which includes `first_available_block`) so the client knows to retry with `getBlock` against a different node, bigtable, or to fall back to a later slot. Returning `None` instead of an error is a case of wrong data being returned in response to a query — clients that treat `None` as an authoritative "slot skipped/no block" indicator can behave incorrectly (e.g., incorrectly conclude a validator skipped its slot, or miscount slot production), which is a functional correctness issue reachable by any unprivileged RPC caller.

### Likelihood Explanation
This path is reachable with a single, standard `getBlock` JSON-RPC call using `commitment: "confirmed"` for a slot that is still in `status_cache_ancestors()` (not yet finalized) but whose ledger data has already been purged — a legitimate, common runtime condition on validators running with bounded ledger size (`--limit-ledger-size`) or after `rpc_scan_and_fix_roots`/blockstore compaction. No special privileges, malicious input, or multiple calls are required, so likelihood of hitting the code path is moderate-to-high on nodes with ledger pruning enabled and low retention windows.

### Recommendation
Apply the same cleanup-detection check used in the finalized branch to the confirmed-slot branch: call `self.check_slot_cleaned_up(&result, slot)?` (and consider `check_blockstore_root` semantics as appropriate) on the `Result` returned by `blockstore.get_complete_block(slot, true)` before converting it with `.ok()`, so that a `BlockstoreError::SlotCleanedUp` is surfaced as `RpcCustomError::BlockCleanedUp` instead of silently becoming `None`.

### Proof of Concept
1. Run a validator with a small `--limit-ledger-size` so the `BlockstoreCleanupService` actively purges old slot data.
2. Identify a slot `S` that is present in `confirmed_bank.status_cache_ancestors()` (i.e., optimistically confirmed but not yet rooted/finalized) whose blockstore column-family entries have already been compacted away for that slot (achievable by tuning purge timing / using `purge_slots` directly in a test harness against `ledger/src/blockstore.rs`'s `get_complete_block`).
3. Call `getBlock` with `{"commitment": "confirmed"}` for slot `S`.
4. Observe the RPC returns `{"result": null}` instead of an error such as `{"code": ..., "message": "Block ... cleaned up, first available block: ..."}`, confirming the check that exists on the finalized path (`check_slot_cleaned_up`) is skipped on the confirmed path.

    fn check_slot_cleaned_up<T>(
        &self,
        result: &std::result::Result<T, BlockstoreError>,
        slot: Slot,
    ) -> Result<()> {
        let first_available_block = self
            .blockstore
            .get_first_available_block()
            .unwrap_or_default();
        let err: Error = RpcCustomError::BlockCleanedUp {
            slot,
            first_available_block,
        }
        .into();
        if let Err(BlockstoreError::SlotCleanedUp) = result {
            return Err(err);
        }
        if slot < first_available_block {
            return Err(err);
        }
        Ok(())
    }
