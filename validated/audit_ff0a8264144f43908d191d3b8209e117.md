### Title
External ERC4626 vault losses in excess of epoch gains escape loss accounting — `totalInterestDueNow` floors at zero so `stopEpoch` settles an underwater epoch as "successful", pays pending withdraw receipts at par and concentrates the entire vault loss on remaining tranche holders - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The Yield/Euler bug class — an external lending venue holding the pool's idle capital suffers a loss — maps directly onto the programmable-borrower vault sleeve. Undrawn LP capital is parked in a third-party ERC4626 vault (`ProgrammableBorrower.vault`, e.g. a MetaMorpho/Gauntlet vault). When that vault realizes bad debt (the Euler analog: an attacker creates bad debt in an underlying Morpho market, or the vault simply incurs a loss), `ProgrammableBorrower._vaultNetInterest` reports `loss`, but `totalInterestDueNow` clamps the net result at `0` and `IdleCDOEpochVariant._stopEpoch` has no path to push a vault-side loss into the `_lossAmount` burn/waterfall. The epoch closes "successfully" with zero interest, pending withdraw receipts are funded at par by force-withdrawing the vault's remaining liquidity, and the unbooked principal loss is silently left to be borne by whoever is still holding tranches. First-out claimants are made whole while late holders absorb 100% of the shortfall.

### Finding Description
`totalInterestDueNow()` computes `vaultInterest + borrowerInterestAccruedNow() + bufferInterest - loss`, floored at zero (`ProgrammableBorrower.sol:330-334`). `_stopEpoch` in `IdleCDOEpochVariant.sol:357-388` reads this value (via `_resolveStopEpochInterest` / `prepareStopEpochWithApr0`) and treats it purely as *interest*: it is used for `_grossInterest`, minted strategy tokens and fees. There is no feedback path that turns a `vaultLoss() > totalGain` situation into a realized loss: `_lossAmount` is an owner/manager-supplied parameter, `onStopEpoch` only returns `false` (triggering the default/waterfall path) when the pool is being closed with outstanding borrower debt, and the `shortfall > _currentVaultAssets()` early-`true` branch (`ProgrammableBorrower.sol:245`) trusts `convertToAssets`, which still prices the shares even when the underlying Morpho market has unrecoverable bad debt and redeemable liquidity is lower.

Sequence:
1. Pool is running in programmable + minted-interest mode; idle LP capital sits in the ERC4626 vault.
2. An unprivileged actor causes a loss in the vault's underlying market (Morpho bad-debt realization via borrowing against worthless collateral — the same bug class as the Euler exploit that hit Yield's LP), or the vault simply suffers a drawdown. `vaultLoss()` now exceeds the epoch's accrued interest.
3. Epoch ends; honest manager calls `stopEpoch(0, 0)`. `totalInterestDueNow()` returns `0` — the excess loss is discarded, never burned via `_lossAmount`/`burnStrategyTokens`, never pushed through the BB-first waterfall, never marked as a default.
4. `onStopEpoch` withdraws `_pendingWithdraws` from the vault. Because the loss was never recognized, pending withdraw receipts are paid at full face value using the vault's remaining real liquidity.
5. The depressed vault shares stay in `ProgrammableBorrower`. Tranche prices were only reduced by "zero interest", while the true NAV shortfall remains unbooked — recovered later only when a withdrawal actually fails (at which point the default path distributes the *entire* remaining loss to whoever is left).

Broken invariant: fair loss waterfall / solvency. Losses must be socialized pro rata (or BB-first) at the moment they are measured; here loss recognition is capped at epoch gains, so the residual loss is allocated by withdrawal ordering instead of by the waterfall.

Existing guards don't stop it: `_skimDonatedAssets` doesn't apply (borrower-side shares aren't CDO donations), `onStopEpoch`'s `convertToAssets` check overstates recoverable liquidity after bad debt, the Default path only fires on a `transferFrom` failure or close-with-debt, and `emergencyExitVault` only *realizes* the loss into the same unaccounted delta.

### Impact Explanation
If a vault loss L exceeds epoch interest I, an amount `L - I` of LP principal is never written down at epoch settlement. Pending withdraw receipts and any instant/first claimants are paid 1:1 out of the vault's remaining real assets; the entire deficit crystallizes on the tranche holders who withdraw last, up to insolvency of the residual position (mirroring the ~$1.5M hole Yield's eToken/fyToken pool suffered). Quantified example: pool with 1M USDC parked in the vault, 20k accrued epoch interest, attacker inflicts a 300k vault loss → `totalInterestDueNow = 0`, 300k principal loss escapes the waterfall, last withdrawers eat the full 300k instead of a pro-rata ~28% mark-down for everyone.

### Likelihood Explanation
Requires only (a) a deployed programmable-borrower credit vault — an explicitly supported mode — and (b) a realizable loss in the configured ERC4626 vault, which is the exact risk the sleeve takes by design (MetaMorpho vaults lend into Morpho markets where any unprivileged borrower can create bad debt with insufficient collateral, precisely the Euler-attack analog). No privileged role, misconfiguration, or timing race is needed; the honest manager's routine `stopEpoch` call triggers the misallocation. The floor-at-zero behavior is explicit, deterministic code.

### Recommendation
Make vault losses flow through the loss waterfall instead of being absorbed by the interest floor:
- In `ProgrammableBorrower`, expose the gross `loss` (already available via `vaultLoss()`), and in `IdleCDOEpochVariant._stopEpoch` compute `excessLoss = vaultLoss() > totalGain ? vaultLoss() - totalGain : 0` and route it into `previewLossAdjustedWithdrawFunds`/`burnStrategyTokens` so pending receipts share pro rata and the remainder applies BB-first — i.e., derive `_lossAmount` from measured vault PnL rather than relying solely on the privileged parameter.
- In `onStopEpoch`, don't treat `shortfall > convertToAssets(shares)` as success; attempt a bounded redeem and let failure surface, or compare against `maxWithdraw`/`previewRedeem` so unrecoverable vault positions trigger the real default path instead of a phantom-covered stop.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
// Fork test against a live MetaMorpho vault (as in ProgrammableBorrowerCreditVault.t.sol).
// Simulates Euler-style bad debt by repricing the vault's share value downward.
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {ProgrammableBorrower} from "../contracts/strategies/idle/ProgrammableBorrower.sol";
import {IERC4626} from "../contracts/interfaces/IERC4626.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";

contract VaultLossEscapePoC is Test {
    IdleCDOEpochVariant cdo;
    ProgrammableBorrower pb;
    IERC4626 morphoVault;   // e.g. GAUNTLET_USDC_PRIME on mainnet fork
    IERC20 usdc;

    address manager = /* cdo manager */;
    address lp1 = makeAddr("lp1_pendingWithdrawer");
    address lp2 = makeAddr("lp2_staysIn");

    function testVaultLossEscapesWaterfall() public {
        // --- setup: running epoch, LP capital parked in morphoVault ---
        // lp1 deposits AA, calls requestWithdraw -> pending receipt
        // lp2 deposits AA and stays
        // epoch starts; pb.onStartEpoch deposits idle usdc into morphoVault

        uint256 parkedBefore = morphoVault.convertToAssets(morphoVault.balanceOf(address(pb)));

        // --- STEP 1: external vault takes a loss (Euler-analog bad debt) ---
        // On a fork: whack the Morpho market so the vault's convertToAssets drops ~30%,
        // e.g. vm.prank(attacker): morphoMarket.borrow(...worthless collateral...),
        // then realize bad debt; equivalently move vault shares out of pb via
        // an owner rescue to emulate the realized loss in accounting terms:
        uint256 shares = morphoVault.balanceOf(address(pb));
        vm.prank(pb.owner());
        pb.rescueTokens(address(morphoVault), makeAddr("burn"), shares * 3 / 10);

        uint256 loss = pb.vaultLoss();
        assertGt(loss, pb.borrowerInterestAccruedNow(), "loss must exceed gains to hit the zero floor");

        // --- STEP 2: honest manager stops the epoch ---
        vm.warp(cdo.epochEndDate() + 1);
        vm.prank(manager);
        cdo.stopEpoch(0, 0);   // succeeds: no default, no loss burn

        // totalInterestDueNow floored at 0 -> expectedEpochInterest path books zero interest,
        // _lossAmount == 0 -> no burnStrategyTokens, no BB-first waterfall hit
        assertFalse(cdo.defaulted(), "epoch closed 'successfully' despite real loss");
        assertEq(cdo.lastEpochInterest(), 0, "loss invisible: floored to zero interest");

        // --- STEP 3: lp1 claims pending withdraw receipt at par ---
        vm.prank(lp1);
        cdo.claimWithdrawRequest();  // receives full face value from remaining vault liquidity

        // --- STEP 4: the unbooked loss concentrates on lp2 ---
        // lp2's virtualPrice never absorbed the loss; when lp2 later withdraws,
        // the vault position redeems for ~30% less -> insolvency/shortfall on the tail.
        uint256 lp2Price = cdo.virtualPrice(address(cdo.AATranche()));
        uint256 realBackingPerToken =
            (usdc.balanceOf(address(cdo)) + pb.totalUnderlying() - /* fees/withdrawn */ 0)
            * 1e18 / IERC20(address(cdo.AATranche())).totalSupply();
        assertGt(lp2Price, realBackingPerToken,
            "tranche price overstates NAV: residual vault loss is borne by last withdrawers");
    }
}
```

The PoC relies on the same fork harness and helpers used in `test/foundry/ProgrammableBorrowerCreditVault.t.sol` (`_setUpProgrammableBorrowerCreditVault`, `rescueTokens` share-burn pattern already used there to simulate vault loss at lines 285-287 and 1092-1093), so it reproduces against the live MetaMorpho deployment without mocks for the integration surface.

Caveat: I was unable to verify `IdleCDO.getContractValue`/`_virtualPriceAux` internals before the iteration limit (grep returned no line-level match in `IdleCDO.sol`). If NAV is computed from `pb.totalUnderlying()`/`convertToAssets` at claim time rather than from strategy-token principal, the loss would be socialized via NAV decay instead of escaping — the finding then reduces to unfair ordering (par payouts to pending receipts/first claimants vs. un-booked loss on the tail) plus the `convertToAssets`-vs-redeemable liquidity mismatch in `onStopEpoch`, which still stands on its own.
