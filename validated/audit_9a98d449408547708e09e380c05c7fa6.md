### Title
Signer can be tricked into signing two conflicting tenure-change blocks for the same tenure because DuplicateBlockFound only checks global, not local, acceptance - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` guards against re-signing a tenure-change block by calling `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [1](#0-0)  and rejecting with `RejectReason::DuplicateBlockFound` only if a block for that tenure has already reached `GloballyAccepted` state [2](#0-1) . If this signer has only locally accepted (signed) a first tenure-change block for a given `consensus_hash`, but that block never reaches global acceptance (e.g. rest of signer set rejects/times out), this check returns `None` and does not block a second, conflicting tenure-change proposal for the exact same tenure from passing this stage of validation.

### Finding Description
The uniqueness property that should hold is: for a given tenure (`consensus_hash`) at the tenure-change slot (height=1 in that tenure), a signer must sign at most one distinct block. `validate_tenure_change_payload` attempts to enforce this via the `DuplicateBlockFound` rejection, but the check is keyed off `get_last_globally_accepted_block`, which only returns a result once a threshold of signers has counter-signed the block into `GloballyAccepted` state — not the current signer's own local decision. This is visible directly in the code: the function retrieves `last_in_current_tenure` from the global-acceptance query and only errors if that returns `Some` [3](#0-2) , with no accompanying check against this signer's own locally-accepted/signed block for the same consensus hash.

An attacker who wins a miner slot can: (1) propose tenure-change block A for consensus_hash `CH`, get this signer to locally accept/sign it (`mark_locally_accepted`) while withholding it from enough other signers so it never reaches `GloballyAccepted`, then (2) propose a different tenure-change block B, also with `prev_tenure_consensus_hash` matching the same parent tenure and `consensus_hash = CH`. Because `get_last_globally_accepted_block(CH)` still returns `None`, `validate_tenure_change_payload` does not reject B for `DuplicateBlockFound`, and (assuming the other structural checks — parent match, `check_tenure_change_confirms_parent`, `check_parent_tenure_choice` — also pass for B) the signer proceeds to sign B, producing two different signed blocks (A and B) for the same tenure at the same slot from a single signer.

### Impact Explanation
This breaks the uniqueness/equivocation-guard safety property for block signing: a single signer producing valid signatures over two conflicting blocks at the same (tenure, height) is exactly the kind of equivocation the signer protocol is meant to prevent (chain safety). If such conflicting signatures accumulate independently on both branches (e.g., from other signers subjected to the same withholding attack, or in combination with partitioned gossip), it can contribute to two competing blocks each collecting signer signatures, undermining the single-canonical-chain guarantee. This matches the "Critical - a signer signing an invalid, non-canonical, or conflicting block (chain safety)" category.

### Likelihood Explanation
The precondition is narrow but attacker-feasible within the stated threat model (one miner slot + gossip, no majority of signers needed): the attacker must win the sortition (miner slot) for the tenure in question, and must be able to selectively gossip the first tenure-change block to this one victim signer while preventing it from reaching `GloballyAccepted` status network-wide (e.g., by not broadcasting it widely, or timing it so other signers reject/timeout first). Since the check is purely local per-signer (`signer_db.get_last_globally_accepted_block`), the attacker doesn't need to compromise any other signer — they only need control over which proposal(s) reach this one victim signer's StackerDB view. This is repeatable per tenure the attacker wins.

However, whether this is actually *reachable/exploitable* in the broader signer state machine depends on additional gates outside `v1.rs` that I was not able to fully verify within available context/tool budget — specifically whether `stacks-signer/src/v0/signer.rs` or `SignerDb` block-state bookkeeping (e.g., a check keyed on the local `signer_signature_hash`/BlockInfo state rather than just `get_last_globally_accepted_block`) independently blocks re-signing a different block once a local signature has been produced for that tenure/height. My search located `mark_locally_accepted`, `BlockInfo`, and related state-machine functions in `stacks-signer/src/signerdb.rs` (43 matches) and `stacks-signer/src/v0/signer.rs` (10 matches for related terms), but I was unable to read their full bodies before running out of tool iterations to confirm or rule out a secondary local-uniqueness guard.

### Recommendation
In `validate_tenure_change_payload`, augment the duplicate check to also query this signer's own local acceptance/signature state for the tenure's `consensus_hash` (not just global acceptance), e.g. checking for any locally-accepted or locally-signed block at height 1 of the same tenure with a different `signer_signature_hash`, and reject with `DuplicateBlockFound` (or a dedicated `RejectReason`) in that case as well.
