### Title
Permissionless `#[init] new()` on `staking-pool` and `lockup` allows front-running initialization to hijack ownership of a pre-funded contract - (File: `staking-pool/src/lib.rs`, `lockup/src/lib.rs`)

### Summary
Both `staking-pool/src/lib.rs::new()` and `lockup/src/lib.rs::new()` are permissionless `#[init]` functions whose only guard is `assert!(!env::state_exists(), ...)`. Per the documented deployment flow (see `staking-pool/README.md:198-207` and the manual multi-step `near create_account` / `near deploy` / `near call new` sequence, and the manually-scripted `deploy_lockup.sh`/`deploy_staking_pool_factory.sh`), account creation, code deployment, and funding happen in transactions separate from the `new` call. Whoever calls `new` first becomes the trusted owner (`owner_id`/`owner_account_id`) and sets the validator `stake_public_key`/`reward_fee_fraction` (staking pool) or lockup/vesting parameters (lockup), even though the account may already hold NEAR transferred by the legitimate deployer. This is the exact bug class from the report: a permissionless initializer that sets trust-critical parameters (there: price oracle/prices; here: owner/keys/fee) can be front-run, corrupting the binding between "who is trusted as owner" and "who the deployer intended." [1](#0-0) [2](#0-1) 

### Finding Description
`StakingContract::new` only checks `!env::state_exists()` before accepting caller-supplied `owner_id`, `stake_public_key`, and `reward_fee_fraction`, and it derives `total_staked_balance`/`total_stake_shares` from whatever `env::account_balance()` happens to be at call time: [1](#0-0) 

Similarly, `LockupContract::new` only checks account-ID validity and `!env::state_exists()` before accepting an attacker-supplied `owner_account_id`, `vesting_schedule`, `transfers_information`, etc., and sets `lockup_amount: env::account_balance()`: [2](#0-1) 

Neither function restricts the caller to a specific predecessor account. Per the documented (non-factory) deployment procedure, the account is created, funded, and code-deployed in earlier transactions, and `new` is invoked in a separate, later transaction: [3](#0-2) 

In this window — after the account exists, is deployed, and (per the docs) is already funded, but before the legitimate deployer's `new` transaction lands — any unprivileged party can submit their own `new` call. Because `new` has no predecessor/signer check, the attacker's transaction (if it lands first, via normal mempool ordering, gas-price bidding, or a chain reorg reordering the two transactions) becomes the one that succeeds; the legitimate deployer's subsequent `new` call then reverts with `"Already initialized"`. The attacker's call sets themselves as `owner_id`/`owner_account_id`, and for the staking pool, sets `stake_public_key` (their own validator key) and `reward_fee_fraction` (e.g. 100%), all binding to the NEAR balance that has already been deposited into that account.

The equality this breaks: **intended custody `owner_id == deployer-designated owner` becomes `owner_id == attacker`**, while the already-transferred NEAR balance (`env::account_balance()`) is unchanged and gets bound into the attacker-controlled contract state (`total_staked_balance`/`total_stake_shares` for staking-pool; `lockup_amount` for lockup).

### Impact Explanation
This is Critical under the "wrongly parameterised deployment" category: an unauthorized party becomes the trusted `owner_id` of a contract that already holds real NEAR.
- Staking pool: the attacker becomes the pool owner, controls the validator's `stake_public_key`, and can set `reward_fee_fraction` to the maximum, redirecting future delegator rewards to themselves. The pre-funded balance (`account_balance - STAKE_SHARE_PRICE_GUARANTEE_FUND`) is auto-restaked under the attacker's key via `internal_restake()`. [4](#0-3) 
- Lockup: the attacker becomes `owner_account_id`, and as owner can subsequently drive the contract toward transferring the already-funded balance out (subject to lockup/vesting logic they themselves set at init, e.g. `TransfersInformation::TransfersEnabled` with a past timestamp and no vesting schedule), moving NEAR to an account not entitled to it.

### Likelihood Explanation
Exploitation requires only observing a pending `new` transaction (public mempool) or benefiting from validator/relayer reordering — no privileged role, victim key, or contract redeploy is needed; it is directly reachable by any unprivileged account. It is mitigated in practice by the `-factory` contracts (`staking-pool-factory`, `lockup-factory`), which bundle `create_account`/`deploy_contract`/`transfer`/`function_call("new", ...)` into a single atomic receipt, closing the window: [5](#0-4) [6](#0-5) 
However, both `staking-pool/README.md` and `lockup/README.md` document (and the `scripts/deploy_lockup.sh` / older `scripts/deploy_old_lockup.sh` variants show) manual, multi-transaction deployment as a supported path, which is exactly where the race window exists.

### Recommendation
- Require the `new` call to be bundled atomically with account creation/funding (as already done by the factory contracts), and update the documentation/scripts that show manual multi-transaction deployment to remove the unsafe multi-step flow, or
- Add a `predecessor_account_id`/allow-list check to `new` (e.g., only the account itself, or a designated deployer key with a full-access key retained until init) so an arbitrary third party cannot claim ownership, or
- Have deployers add a full-access key temporarily and delete it only after `new` succeeds, and treat non-atomic deployment as unsupported.

### Proof of Concept
1. Deployer creates account `my_validator.near` via `near create_account` and funds it with 35 NEAR (per README).
2. Deployer deploys `staking_pool.wasm` via `near deploy`.
3. Deployer prepares to call `near call my_validator new '{"owner_id": "owner", "stake_public_key": "<deployer_key>", "reward_fee_fraction": {"numerator":10,"denominator":100}}'`.
4. Attacker, watching the mempool (or benefiting from a reorg), submits their own `near call my_validator new '{"owner_id": "attacker", "stake_public_key": "<attacker_key>", "reward_fee_fraction": {"numerator":100,"denominator":100}}'` with higher priority/earlier inclusion.
5. Attacker's transaction executes first; `env::state_exists()` is now true, so the deployer's later `new` call fails with `"Already initialized"`.
6. The 35 NEAR already sitting in `my_validator.near`'s balance becomes `total_staked_balance`, staked under the attacker's `stake_public_key`, with `owner_id = attacker` and a 100% reward fee, per `StakingContract::new`: [7](#0-6) 
7. The attacker now owns and fully controls a validator contract funded by the deployer's NEAR, and can direct all delegator rewards to themselves via owner-only fee-setting methods.

The analogous PoC applies to `lockup/src/lib.rs::new()`, where the attacker sets themselves as `owner_account_id` over an already-funded lockup account.

    #[init]
    pub fn new(
        owner_id: AccountId,
        stake_public_key: Base58PublicKey,
        reward_fee_fraction: RewardFeeFraction,
    ) -> Self {
        assert!(!env::state_exists(), "Already initialized");
        reward_fee_fraction.assert_valid();
        assert!(
            env::is_valid_account_id(owner_id.as_bytes()),
            "The owner account ID is invalid"
        );
        let account_balance = env::account_balance();
        let total_staked_balance = account_balance - STAKE_SHARE_PRICE_GUARANTEE_FUND;
        assert_eq!(
            env::account_locked_balance(),
            0,
            "The staking pool shouldn't be staking at the initialization"
        );
        let mut this = Self {
            owner_id,
            stake_public_key: stake_public_key.into(),
            last_epoch_height: env::epoch_height(),
            last_total_balance: account_balance,
            total_staked_balance,
            total_stake_shares: NumStakeShares::from(total_staked_balance),
            reward_fee_fraction,
            accounts: UnorderedMap::new(b"u".to_vec()),
            paused: false,
        };
        // Staking with the current pool to make sure the staking key is valid.
        this.internal_restake();
        this
    }

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }

    /// Restakes the current `total_staked_balance` again.
    pub(crate) fn internal_restake(&mut self) {
        if self.paused {
            return;
        }
        // Stakes with the staking public key. If the public key is invalid the entire function
        // call will be rolled back.
        Promise::new(env::current_account_id())
            .stake(self.total_staked_balance, self.stake_public_key.clone())
            .then(ext_self::on_stake_action(
                &env::current_account_id(),
                NO_DEPOSIT,
                ON_STAKE_ACTION_GAS,
            ));
    }
