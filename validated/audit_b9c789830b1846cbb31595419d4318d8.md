### Title
Denial of Service via lamport pre-funding griefing of `SystemInstruction::CreateAccount`/`CreateAccountWithSeed` - (File: programs/system/src/system_processor.rs)

### Summary
The System Program's `create_account` function enforces an "account is empty" invariant by rejecting account creation whenever the destination account already has a nonzero lamport balance. Because System-owned/uninitialized account addresses (especially seed-derived and PDA-style addresses) are publicly computable and lamport transfers to any address are permissionless, an unprivileged third party can pre-fund a target address with as little as 1 lamport before the legitimate owner submits their `CreateAccount` transaction, permanently breaking the invariant the instruction relies on and denying account creation at that address.

### Finding Description
`create_account` in `programs/system/src/system_processor.rs` checks the destination account's lamport balance and fails the whole instruction if it is nonzero: [1](#0-0) 

```
fn create_account(...) -> Result<(), InstructionError> {
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ic_msg!(invoke_context, "Create Account: account {:?} already in use", to_address);
            return Err(SystemError::AccountAlreadyInUse.into());
        }
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    transfer(from_account_index, to_account_index, lamports, invoke_context, instruction_context)
}
```

This is used identically for both `SystemInstruction::CreateAccount` and `SystemInstruction::CreateAccountWithSeed` in the instruction dispatcher [2](#0-1) .

Any ordinary, unprivileged user can submit a basic `SystemInstruction::Transfer` sending 1 lamport to any pubkey — including a seed-derived address (`Pubkey::create_with_seed`) whose derivation inputs (base, seed, owner) are all public and computable ahead of time — before the legitimate owner's `CreateAccount`/`CreateAccountWithSeed` transaction lands. Because the address is deterministically derived and cannot be changed once chosen (the base/seed/owner triple is fixed by the protocol/application that relies on it), this griefing permanently denies account creation at that specific address: `to.get_lamports() > 0` will be true forever afterward, and the instruction will always fail with `SystemError::AccountAlreadyInUse`, exactly mirroring the reported bug class where a third-party token transfer breaks a "balance must be zero/unmodified" invariant and permanently bricks a protocol operation.

The Agave maintainers have themselves acknowledged this exact griefing vector: a newer `SystemInstruction::CreateAccountAllowPrefund` was added specifically to allow account creation "without checking for 0 lamports," documented as intended for accounts that may have "already had rent paid in whole or in part before creation" [3](#0-2) , gated behind the `create_account_allow_prefund` feature flag [4](#0-3) . However, this new instruction is opt-in — the original `CreateAccount`/`CreateAccountWithSeed` paths used throughout the ecosystem (system CLI, stake account creation, nonce account creation, ATA-style flows, `stake-accounts`, `accounts-cluster-bench`, etc.) remain vulnerable to this griefing pattern since callers must explicitly choose the new instruction to be immune.

### Impact Explanation
An attacker can permanently deny creation of any not-yet-existing System-owned account whose address is predictable (seed-derived accounts, PDAs used as system accounts, deterministic stake/nonce/vote-adjacent accounts created via `create_account_with_seed`), simply by sending 1 lamport to it first. This is a low-cost, unprivileged, permanent DoS against any protocol or wallet flow that depends on `CreateAccount`/`CreateAccountWithSeed` succeeding at a specific deterministic address, forcing users into address changes or entirely different creation logic — directly analogous to the reported bricking of `sweepInterest` where an unauthorized balance mutation broke an assumed invariant and produced a permanent DoS with no fund-recovery path through the original code path.

### Likelihood Explanation
High. No privileges are required: any account can execute a basic lamport transfer to any pubkey, including one it does not control, and the destination pubkey for seed-derived accounts is publicly computable before the legitimate creation transaction is submitted. There is no cost barrier (a single lamport suffices) and no protocol prevents watching the mempool/RPC for an upcoming `CreateAccountWithSeed` and front-running it with a funding transfer.

### Recommendation
- For flows that must guarantee successful creation at a specific deterministic address, adopt (or default to) `SystemInstruction::CreateAccountAllowPrefund` rather than the legacy zero-balance-enforcing `CreateAccount`/`CreateAccountWithSeed` paths.
- Consider making the "already funded" check advisory/informational instead of an unconditional hard failure for the general-purpose `CreateAccount` instructions, or provide a well-documented idempotent/prefund-tolerant variant as the canonical recommendation in SDK helpers (`system_instruction::create_account_with_seed`, stake/vote account creation helpers) so downstream integrators are not silently exposed to this griefing vector.

### Proof of Concept
1. Attacker computes `to = Pubkey::create_with_seed(&base, seed, &owner)` for a known/observed `(base, seed, owner)` tuple about to be used by a victim's forthcoming `CreateAccountWithSeed` transaction (e.g., observed via RPC/mempool or predictable application logic).
2. Attacker submits an ordinary `SystemInstruction::Transfer` of 1 lamport to `to`.
3. Victim's `CreateAccountWithSeed` instruction executes `create_account`, hits `to.get_lamports() > 0`, and fails with `SystemError::AccountAlreadyInUse` [5](#0-4) .
4. Because `to` is a deterministic function of `(base, seed, owner)`, the victim cannot retry with the same parameters — the address is permanently unusable for `CreateAccount`/`CreateAccountWithSeed`, matching test expectations already codified in `test_create_already_in_use` [6](#0-5) .

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
