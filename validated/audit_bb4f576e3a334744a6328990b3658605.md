### Title
Unstake resets `unstaked_available_epoch_height` for entire unstaked balance, delaying withdrawal of an already-unlockable tranche - ([File: staking-pool/src/internal.rs])

### Summary
`inner_unstake` overwrites `account.unstaked_available_epoch_height` with a single scalar `env::epoch_height() + NUM_EPOCHS_TO_UNLOCK` on every call, while `account.unstaked` is a single aggregate balance with no per-tranche tracking. A delegator who unstakes again before withdrawing an earlier unstaked tranche will have that earlier tranche's already-elapsed unlock time overwritten by the later, longer lock, delaying withdrawal by up to `NUM_EPOCHS_TO_UNLOCK` epochs.

### Finding Description
The binding the contract needs to preserve is: for any already-unstaked amount X unstaked at epoch E, `account.unstaked_available_epoch_height` (the gate checked in `internal_withdraw`) must equal `E + NUM_EPOCHS_TO_UNLOCK` for that specific tranche X, independent of any later unstake action. Instead, `Account` stores a single scalar `unstaked` balance and a single scalar `unstaked_available_epoch_height` field [1](#0-0) , and `inner_unstake` unconditionally reassigns `account.unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK` for the whole account regardless of any unstaked balance the account already holds [2](#0-1) . `internal_withdraw` then gates *all* of `account.unstaked` (both old and new tranches merged into one balance) behind this single, most-recently-set epoch height [3](#0-2) .

Exploit flow: attacker (an ordinary delegator) calls `unstake(X)` at epoch E (sets gate to E+4, `account.unstaked = X`). At epoch E+2 they call `unstake(Y)` again, which merges Y into `account.unstaked` (now X+Y) and resets the gate to E+2+4 = E+6, discarding the fact that X was already eligible at E+4. At epoch E+4, calling `withdraw(X)` hits `assert!(account.unstaked_available_epoch_height <= env::epoch_height())` which is `E+6 <= E+4`, false, so the call panics with "The unstaked balance is not yet available due to unstaking delay", even though X's own 4-epoch delay has already elapsed.

No existing guard mitigates this: `assert_owner`, `assert_self`, etc. are irrelevant here, and there's no per-tranche accounting or FIFO/queue structure to separate X and Y's unlock times.

### Impact Explanation
No funds are moved incorrectly or released early; the effect is that X's own NEAR remains frozen inside the staking pool contract for extra epochs (in the worst case, up to nearly `NUM_EPOCHS_TO_UNLOCK` additional epochs) beyond its legitimate unlock time, but it is still recoverable in full once the new gate elapses. This matches the "funds frozen for at least one epoch but recoverable" High-severity category. This applies to the delegator's own funds only (self-inflicted by their own further unstake action) — it does not let the attacker extract more than they're owed, nor affect other delegators' balances, `total_staked_balance`, or share price. It is repeatable by any delegator who unstakes in more than one epoch before withdrawing.

### Likelihood Explanation
This is trivially reachable: it requires no special privileges, only ordinary `unstake` calls made by the same delegator across two different epochs before withdrawing the first tranche — a common realistic usage pattern (e.g., a user unstaking incrementally). No cost beyond gas, and it's fully deterministic and repeatable.

### Recommendation
Track the unlock schedule per unstake action rather than as a single scalar — e.g., maintain a small ordered list/queue of `(amount, available_epoch_height)` tranches per account (or at minimum, only extend the gate for the newly unstaked portion, not retroactively for already-unlockable balance), and have `withdraw`/`internal_withdraw` release only the tranches whose individual unlock epoch has passed.

### Proof of Concept
Using the existing `Emulator` test harness (`staking-pool/src/lib.rs` test module, e.g. as in `test_stake_unstake`) [4](#0-3) :
1. Deposit and stake `X+Y` for `bob` at epoch 0.
2. Call `unstake(X)` at epoch 0 (gate becomes epoch 4).
3. `emulator.skip_epochs(2)` (now epoch 2), call `unstake(Y)` (gate becomes epoch 6).
4. `emulator.skip_epochs(2)` (now epoch 4).
5. Call `withdraw(X)`; assert it panics with `"The unstaked balance is not yet available due to unstaking delay"`, demonstrating that X's legitimate unlock epoch (4) has already passed while the enforced gate (6) still blocks it.

    fn test_stake_unstake() {

        assert_eq!(

            deposit_amount
        );
        let locked_amount = emulator.locked_amount;
        // 10 epochs later, unstake half of the money.
        emulator.skip_epochs(10);

        emulator.locked_amount = locked_amount + ntoy(10);
        emulator.update_context(bob(), 0);
        emulator.contract.ping();
        assert_eq_in_near!(
            emulator.contract.get_account_staked_balance(bob()).0,
            deposit_amount + ntoy(10)
        );

        emulator.simulate_stake_call();
        assert_eq_in_near!(
            emulator.contract.get_account_staked_balance(bob()).0,
            deposit_amount / 2 + ntoy(10)
        );
        assert_eq_in_near!(
            emulator.contract.get_account_unstaked_balance(bob()).0,
            deposit_amount / 2
        );
        let acc = emulator.contract.get_account(bob());
        assert_eq!(acc.account_id, bob());
        assert_eq_in_near!(acc.unstaked_balance.0, deposit_amount / 2);
        assert_eq_in_near!(acc.staked_balance.0, deposit_amount / 2 + ntoy(10));
        assert!(!acc.can_withdraw);

        assert!(!emulator

        emulator.skip_epochs(4);
        emulator.update_context(bob(), 0);
        assert!(emulator
            .contract
            .is_account_unstaked_balance_available(bob()),);

    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);
