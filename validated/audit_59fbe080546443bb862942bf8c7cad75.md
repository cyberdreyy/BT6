The route `POST /v2/jobs/:ID/runs` is registered under `userOrEI` group, which chains `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, `auth.AuthenticateBySession` [1](#0-0) . `AuthenticateExternalInitiator` explicitly sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` for EI-authenticated requests [2](#0-1) . `GetAuthenticatedUser` retrieves whatever is stored at `SessionUserKey` and returns `ok=true` regardless of whether the origin was a real user session/token or a synthesized EI pseudo-user [3](#0-2) . `PipelineRunsController.Create` uses exactly this `isUser` boolean, with an explicit comment "only users are allowed to run jobs using int IDs - EIs not allowed", to gate the numeric-ID `RunJobV2` path [4](#0-3) .

### Title
EI-authenticated requests bypass the "EIs not allowed" numeric-ID job run restriction due to `isUser` conflating EI pseudo-users with real users - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates numeric-ID job runs on `isUser := auth.GetAuthenticatedUser(c)` with the explicit intent "EIs not allowed." However, `AuthenticateExternalInitiator` stores a synthesized `*clsessions.User{Role: clsessions.UserRoleRun}` under the same `SessionUserKey` used by real user authentication, so `GetAuthenticatedUser` cannot distinguish an EI-originated pseudo-user from a genuine user session/token. As a result, a valid External Initiator credential holder can trigger arbitrary numeric-ID jobs via `POST /v2/jobs/<int-id>/runs`.

### Finding Description
The route is registered as `userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))` on a group chaining `AuthenticateExternalInitiator`, `AuthenticateByToken`, `AuthenticateBySession` [1](#0-0) . When an attacker authenticates purely with valid EI access-key/secret headers, `AuthenticateExternalInitiator` succeeds and executes `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})`, reusing the identical context key (`SessionUserKey`) that `AuthenticateBySession`/`AuthenticateByToken` use to store real, database-backed `clsessions.User` objects [5](#0-4) .

Inside `Create`, the code does:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ... RunJobV2(ctx, jobID, nil) ...
}
```
`GetAuthenticatedUser` only checks that a `*clsessions.User` is present at `SessionUserKey` — it has no way to determine whether that value came from `AuthenticateExternalInitiator` (EI-only) versus `AuthenticateBySession`/`AuthenticateByToken` (real user) [3](#0-2) . Since `auth.Authenticate` runs each `authMethod` in order and stops on first non-`ErrorAuthFailed` result, an EI-only request (no session cookie, no API token) will succeed via `AuthenticateExternalInitiator` alone, populating `SessionUserKey` and satisfying `isUser == true` — directly contradicting the code comment's intended restriction.

### Impact Explanation
This is an authorization/authentication-soundness bypass: an EI credential holder — a lower-privilege, narrowly-scoped credential intended only for the EI-specific run flow — gains the ability to invoke `RunJobV2` on arbitrary numeric job IDs, i.e., trigger job runs the EI was never meant to access via this code path. This maps to Chainlink's "unauthorized job run" impact class; depending on the job (e.g., jobs that move funds, submit transactions, or interact with external systems), this could result in unauthorized fund movement or unintended on-chain actions.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs a valid EI access key/secret (already assumed to be an "unprivileged" attacker class per the threat model, i.e., "external-initiator credential holder"). No user session or API token is required. The request is a single `POST /v2/jobs/<int-id>/runs` with EI headers, fully reproducible and repeatable against any node exposing an EI credential.

### Recommendation
Distinguish EI-originated authentication from real user authentication instead of overloading `SessionUserKey`. For example, do not set `SessionUserKey` in `AuthenticateExternalInitiator`, and have `PipelineRunsController.Create` check `auth.GetAuthenticatedExternalInitiator(c)` explicitly to reject EI callers, or introduce a distinct marker (e.g., a boolean/context key) indicating the auth method actually used, so `isUser` reflects only session/token-authenticated users.

### Proof of Concept
Go handler-level integration test plan:
1. Set up a test chainlink application with an `ExternalInitiator` (`bridges.ExternalInitiator`) and a real job with a numeric ID (e.g., a cron/webhook-style job usable via `RunJobV2`).
2. Build a `POST /v2/jobs/<jobID>/runs` request including only `X-EI-ACCESS-KEY`/`X-EI-SECRET` headers matching the EI record; no session cookie or `X-API-KEY`/`X-API-SECRET`.
3. Route the request through `NewRouter`'s `userOrEI` group (`v2Routes`).
4. Assert current (buggy) behavior: response is `200 OK` and `PipelineORM().FindRun` shows a new pipeline run was created for that job — demonstrating `isUser` was true despite EI-only auth.
5. After the fix, assert the same request returns `422`/`401` with "bad job ID" or an authorization error, and no pipeline run is created, while an equivalent request using a real user session/token still succeeds.
