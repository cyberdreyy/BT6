### Title
Stale single-epoch `lastWithdrawRequest` pointer lets a stacked loss-adjusted receipt be paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The UPX bug is a stale/invalid index dereference: `elf_lookup` follows a pointer derived from crafted input and reads the wrong object. The credit-vault analog is `IdleCreditVault._claimLossAdjustedWithdrawRequest`, which looks up `lossRecoveryPriceByEpoch` using only `lastWithdrawRequest[_user]` — a single-slot epoch pointer that is overwritten by every new `requestWithdraw`. A user who holds an unclaimed receipt from a loss-adjusted epoch and then files a second withdraw request in a later, fully-funded epoch permanently loses the pointer to the haircut epoch, and the receipt is paid at 100% via `_claimFundedWithdrawRequest` even though only the haircutted amount was ever collected.

### Finding Description
`requestWithdraw` stores the request epoch in the scalar `lastWithdrawRequest[_user]` and records the basis per-epoch in `withdrawsRequestsByEpoch[_user][epoch]` (`IdleCreditVault.sol:282-293`). When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` collects less than `pendingWithdraws` and stores the haircut in `lossRecoveryPriceByEpoch[epochNumber]` while zeroing `pendingWithdraws` (`IdleCreditVault.sol:413-421`). The loss-adjusted claim path derives the lookup epoch solely from `lastWithdrawRequest[_user]` (`IdleCreditVault.sol:790-791`); there is no iteration over earlier epochs and `withdrawsRequestsByEpoch` still holds the old epoch's basis. `_clearWithdrawClaimForEpoch` is only invoked for that one epoch (`IdleCreditVault.sol:794`). The code comments confirm stacking is allowed: a user "does not claim a withdraw request and instead requests another withdraw" and both become claimable together after the newer epoch ends (`IdleCreditVault.sol:323-324`). After the second epoch ends, `claimWithdrawRequest` finds `lossRecoveryPriceByEpoch[lastWithdrawRequest] == 0` for the fully-funded epoch, so `_claimLossAdjustedWithdrawRequest` returns 0 and `_claimFundedWithdrawRequest` pays the aggregate `withdrawsRequests[_user]` at par (`IdleCreditVault.sol:338-349`), spending underlyings that were never collected for the first receipt.

### Impact Explanation
Broken invariants: loss waterfall and one-receipt-one-funded-payout. The contract only holds `lossRecoveryPrice * basis` for the haircut epoch plus the fully funded amount for the second epoch, yet pays the full aggregate. The excess `(1 - lossRecoveryPrice) * firstReceiptBasis` is drained from other users' funded withdraw receipts held in the same contract balance; `_transferFundedClaim` only shields `defaultRecoveryReserve`, not other funded receipts (`IdleCreditVault.sol:897-906`). If other claimants' funded receipts cover the shortfall it is direct theft; otherwise the transfer reverts and the victim's receipt is permanently frozen. Attacker quantification: attacker deposit size A in the loss epoch, loss fraction L — attacker extracts `L * A` belonging to other claimants.

### Likelihood Explanation
Requires only unprivileged actions: deposit via KYC'd lender flow, `requestWithdraw` in an epoch that ends with `stopEpochWithDuration(_lossAmount > 0)` (honest manager call realizing a borrower loss — a normal protocol phase, not a default), skip claiming, then `requestWithdraw` again in a subsequent epoch and claim after it ends fully funded. No privileged misbehavior, no oracle manipulation, and no guard (`_ensureDefaultRecoveryInitialized`, the NotAllowed epoch gate, skim, or the reserve check) intercepts the path because the funded-claim guard checks only `epochNumber > lastWithdrawRequest` and the reserve check only applies when `defaultRecoveryReserve != 0`.

### Recommendation
Replace the scalar `lastWithdrawRequest` lookup with per-epoch clearing: in `claimWithdrawRequest`, iterate or track all request epochs with `lossRecoveryPriceByEpoch[epoch] != 0` (e.g., keep a per-user epoch set or a pointer to the earliest unclaimed loss epoch), and exclude any epoch whose basis was already haircut from the par-funded claim in `_claimFundedWithdrawRequest`. Alternatively, revert in `requestWithdraw` when the user has an unclaimed receipt in an epoch with a pending or recorded loss price, forcing the user to claim through `_claimLossAdjustedWithdrawRequest` first.

### Proof of Concept
Foundry fork test sketch in the style of `test/foundry/IdleCreditVault.t.sol`:

```solidity
function testStackedReceiptSkipsLossHaircut() external {
  uint256 amountA = 10_000 * ONE_SCALE;
  uint256 amountB = 10_000 * ONE_SCALE;
  address attacker = makeAddr('attacker');
  address victim   = makeAddr('victim');

  _depositWithUser(attacker, amountA, true);
  _depositWithUser(victim,   amountB, true);

  // Epoch 0: attacker requests full withdraw
  vm.prank(attacker);
  uint256 receiptA = cdoEpoch.requestWithdraw(0, address(AAtranche));
  _startEpochAndCheckPrices(0);

  // Borrower repays with a realized loss: pending receipts are only partially funded
  uint256 loss = receiptA * 30 / 100; // 30% haircut on pending receipts
  _stopEpochWithLoss(0, loss);        // collectWithdrawFunds stores lossRecoveryPriceByEpoch[0] = 0.7e18

  // Attacker does NOT claim; requests a second withdraw in epoch 1
  _depositWithUser(attacker, amountB, true);
  vm.prank(attacker);
  uint256 receiptB = cdoEpoch.requestWithdraw(0, address(AAtranche));
  _startEpochAndCheckPrices(1);
  _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch()); // fully funded

  // Claim: lossRecoveryPriceByEpoch[lastWithdrawRequest=1] == 0 so the loss path is skipped;
  // _claimFundedWithdrawRequest pays receiptA + receiptB at par.
  uint256 balPre = underlying.balanceOf(attacker);
  vm.prank(attacker);
  cdoEpoch.claimWithdrawRequest();
  uint256 paid = underlying.balanceOf(attacker) - balPre;

  // Contract only collected 0.7*receiptA + receiptB for these receipts.
  assertEq(paid, receiptA + receiptB, 'haircut bypassed');
  // The extra 0.3*receiptA is taken from the contract balance backing victim's claims,
  // so victim's later claim either reverts (insufficient balance) or is shorted.
}
```

Key assertions demonstrating the invariant break: `IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(0) < 1e18` while the attacker still receives `receiptA` in full, and the strategy's remaining underlying balance is less than the sum of outstanding funded receipts (`victim`'s claim is impaired by exactly `receiptA - receiptA * lossPrice / 1e18`).
