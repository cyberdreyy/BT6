This confirms the vulnerability described in the question. `MultisigFactory::create` at [1](#0-0)  attaches the deposit inside a single `Promise` chain (`create_account().deploy_contract(...).transfer(...).function_call(...)`) with **no `.then()` callback to the factory itself**, unlike `StakingPoolFactory::create_staking_pool` which explicitly chains `.then(ext_self::on_staking_pool_create(...))` and refunds the depositor via `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` when `is_promise_success()` is false [2](#0-1) . `StakingPoolFactory` also tracks reserved names in `staking_pool_account_ids: UnorderedSet<AccountId>` and asserts uniqueness before creating the account [3](#0-2) , whereas `MultisigFactory` has no such state at all (`pub struct MultisigFactory {}`) [4](#0-3) .

### Title
Multisig factory `create` has no failure callback or refund path, permanently losing attached deposit on account-creation collision - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` builds the deterministic account id `format!("{}.{}", name, current_account_id())` from caller-supplied `name` only, then immediately schedules `create_account().deploy_contract(...).transfer(deposit).function_call("new", ...)` with no `.then()` callback and no on-chain registry of already-claimed/in-flight names. If two callers race to create an account with the same `name` in the same block, the NEAR runtime allows only one `create_account` to succeed; the loser's whole promise chain fails, but because there is no callback checking `is_promise_success()` and no refund `Promise`, the loser's attached deposit is consumed and never returned.

### Finding Description
Binding that should hold: `deposit_debited_from_caller == deposit_refunded_to_caller_on_failure`. In `create`, at [5](#0-4) , `env::attached_deposit()` is transferred as part of the promise chain targeting `account_id`. There is no subsequent `.then(ext_self::on_create(...))` callback like the pattern used in `staking-pool-factory` or `lockup-factory`, and no `UnorderedSet` reserving `account_id` before scheduling the promise (contrast with `staking_pool_account_ids.insert(&staking_pool_account_id)` guard in `staking-pool-factory/src/lib.rs`). Consequently:
- If the `create_account()` action fails (e.g., name collision from a same-block race, or account already exists), the entire promise batch fails on-chain, and the attached deposit that was earmarked for `transfer` is never delivered to the new account and never returned to the caller because no callback exists to inspect `is_promise_success()` and issue `Promise::new(predecessor_account_id).transfer(...)`.
- `assert_self()`/`is_promise_success()` guards exist in the sibling `staking-pool-factory` and are the standard mitigation pattern in this repo, but `MultisigFactory` does not use them at all, so no mechanism prevents the divergence.

### Impact Explanation
The losing caller's attached NEAR deposit is permanently lost/stuck — it is debited from the caller's account when the transaction executes but never delivered to any account (the new multisig account was never created) and never refunded. This matches the Critical category "funds permanently frozen," since NEAR leaves the caller's control with no path to recovery. Any unprivileged attacker or even two independent innocent users racing for the same popular `name` triggers this; it is repeatable across every distinct `name` collision attempt.

### Likelihood Explanation
The precondition is simply two transactions calling `create` with the same `name` landing in the same block (or the second landing after the first has already claimed the account) — no privileged role, special balance, or contract deployment is required, just an attached deposit and a chosen `name`. This is trivially triggerable by an attacker front-running or racing a victim's `create` call with the identical `name`, or even by a lone attacker calling `create` twice in the same block by accident/design, since the outcome (loss of deposit) is deterministic once collision occurs.

### Recommendation
Add an `ext_self` callback analogous to `on_staking_pool_create`/`on_create` used elsewhere in this codebase: schedule `.then(ext_self::on_create(predecessor_account_id, attached_deposit, &current_account_id(), NO_DEPOSIT, CALLBACK_GAS))`, and in that callback call `assert_self()`, check `is_promise_success()`, and if false, refund via `Promise::new(predecessor_account_id).transfer(attached_deposit)`. Optionally also track reserved/in-flight names to fail fast with a panic (refunding the whole transaction) instead of racing at the runtime level.

### Proof of Concept

1. Build a `VMContextBuilder` with `current_account_id = factory`, `predecessor_account_id = caller_b`, `attached_deposit = D`.
2. Call `contract.create("a".to_string(), members2, num_confirmations2)`.
3. Simulate the underlying `create_account` promise failing (as if `caller_a`'s earlier `create("a", ...)` already claimed `a.factory`) via `testing_env_with_promise_results(context, PromiseResult::Failed)` — but since `create` schedules no callback into the factory, there is no `on_create`-style method to invoke at all.
4.
