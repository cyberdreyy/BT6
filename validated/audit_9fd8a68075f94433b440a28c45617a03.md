### Title
Unclaimed APR0 withdraw receipt permanently bricks `stopEpoch` after APR change, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0()` hard-reverts whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. An unprivileged KYC-passing lender can open an APR0 withdraw request during a zero-APR epoch and simply never claim it. Once the honest manager sets a non-zero APR for a subsequent epoch, every `stopEpoch`/`stopEpochWithDuration` call reverts, permanently freezing the epoch state machine and all funds locked in the vault — a direct analog of the external report's "hang/freeze" bug class with full fund impact.

### Finding Description
In `IdleCDOEpochVariant.stopEpochWithDuration` the strategy hook `prepareStopEpochWithApr0(_interest)` is invoked on every stop (contracts/IdleCDOEpochVariant.sol:362). Inside the strategy: [1](#0-0) 

If `apr0TotalPrincipal` is non-zero and the *current* `unscaledApr` is non-zero, the function reverts with `NotAllowed()` instead of settling or skipping the stale bucket. There is no catch-all around this call, so the revert propagates and `stopEpoch` can never succeed.

`apr0TotalPrincipal` is only incremented in `requestWithdraw` when `unscaledApr == 0` (contracts/strategies/idle/IdleCreditVault.sol:285-286 via `_requestWithdrawApr0`) and is only decremented on the user's own claim path (`_settleApr0` inside `_claimFundedWithdrawRequest`, contracts/strategies/idle/IdleCreditVault.sol:330-347) or on a default-finalization claim (`_clearWithdrawClaimForEpoch`, line ~804). Nothing lets anyone else clear another user's APR0 bucket, and neither `startEpoch` nor `stopEpoch` sweeps stale APR0 principals.

Sequence (APR0 → APR>0 transition, running-epoch phase):

1. Manager runs an epoch with `unscaledApr == 0` (legitimate APR0 mode).
2. Attacker, a KYC-passing lender holding tranche tokens, calls `IdleCDOEpochVariant.requestWithdraw(amount, AATranche)` during the buffer/stopped phase. The strategy mints the receipt and records `apr0Users[attacker].principal` / `apr0TotalPrincipal`.
3. That epoch's `stopEpoch` succeeds: inside `prepareStopEpochWithApr0`, `unscaledApr` is still 0, so the revert check passes; the manager then sets `_newApr > 0` via `_setScaledApr(_newApr)` (contracts/IdleCDOEpochVariant.sol:471).
4. The attacker never calls `claimWithdrawRequest`, so `apr0Users[attacker].principal` (and `apr0TotalPrincipal`) stays non-zero.
5. At the next `epochEndDate`, the manager calls `stopEpoch`/`stopEpochWithDuration`. `prepareStopEpochWithApr0` now sees `_principal != 0` and `unscaledApr != 0` → `revert NotAllowed()`. This repeats forever: the epoch can never be stopped.

No existing guard prevents it: `requestWithdraw` is permissionless for allowed wallets (contracts/IdleCDOEpochVariant.sol:739-744), the attacker commits no further action, and the only cleanup path is the attacker's own voluntary claim. The only alternative exits — `finalizeDefault` — require a borrower default (out of scope; borrower is honest) and still route through the same stuck epoch accounting.

### Impact Explanation
Permanent freezing of all user funds. With `stopEpoch` bricked, `isEpochRunning` stays true, `allowAAWithdrawRequest`/`allowBBWithdrawRequest` stay closed, new withdraw requests revert, deposits are paused for the epoch, and no tranche holder can exit through the normal request/claim flow. The entire TVL of the credit vault (principal plus accrued interest owed by the borrower) is frozen indefinitely unless the attacker cooperates — analogous to ransom/griefing: the attacker can demand payment to claim and unbrick the vault.

### Likelihood Explanation
Low trigger cost, moderate precondition: the pool must run at least one epoch with `unscaledApr == 0` (an explicitly supported APR0 mode) and the manager later sets a non-zero APR (routine APR adjustment at any `stopEpoch`). The attacker only needs a KYC-passing wallet and a minimal tranche position to open the APR0 receipt. Once placed, the freeze is unconditional — no further attacker action and no privileged misbehavior required. Caveat: I could not fully verify within the iteration limit whether any additional path (e.g., a loss-adjusted `collectWithdrawFunds` clearing or manager recovery tool) resets `apr0TotalPrincipal` without user claims; the code comments indicate default-path claims decrement it, but no non-claim sweep was found.

### Recommendation
Do not hard-revert on the `(apr0TotalPrincipal != 0 && unscaledApr != 0)` combination in `prepareStopEpochWithApr0`. Options:
- Settle/expire stale APR0 principals inside `prepareStopEpochWithApr0` itself (e.g., move them to `settledPrincipal`/`settledInterest` at the stored epoch terms) so a withholding user cannot block the epoch machine.
- Or track APR0 principal per-epoch and only revert for principals whose lifecycle is genuinely still within an APR0 epoch, clearing `apr0TotalPrincipal` when the bucket's epoch has ended.
- Alternatively, allow `stopEpoch` to proceed and leave APR0 receipts claimable at their locked terms, since their settlement data (`apr0Users`, `lossRecoveryPriceByEpoch`) is already stored per user/epoch.

// Foundry fork PoC (against mainnet-forked IdleCreditVault deployment or the
// repo's own test harness in test/foundry/IdleCreditVault.t.sol)
function testApr0DustReceiptPermanentlyBricksStopEpoch() external {
    // 1. Configure pool in APR0 mode (manager action, pre-existing mode).
    vm.prank(manager);
    IdleCreditVault(strategy).setAprs(0, 0); // unscaledApr = 0

    // 2. Attacker (KYC'd lender) deposits, runs an APR0 epoch, then requests withdraw.
    _depositWithUser(attacker, 1 * ONE_SCALE, true); // dust-sized position suffices
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch());

    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attackerTrancheBalance, address(AAtranche));
    // apr0TotalPrincipal > 0 now; attacker never calls claimWithdrawRequest().

    // 3. Manager starts the next epoch and sets a NON-ZERO apr at stop.
    _startEpochAndCheckPrices(1);
    deal(underlying, borrower, _expectedFundsEndEpoch());
    vm.prank(borrower);
    IERC20(underlying).approve(address(cdoEpoch), _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // stopEpoch with newApr > 0 still sees unscaledApr == 0 inside the
    // prepareStopEpochWithApr0 check for THIS call, so it succeeds and
    // sets unscaledApr > 0 for the next epoch.
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 10e18);

    // 4. Next epoch: stopEpoch now reverts forever.
    _startEpochAndCheckPrices(2);
    deal(underlying, borrower, _expectedFundsEndEpoch());
    vm.prank(borrower);
    IERC20(underlying).approve(address(cdoEpoch), _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.expectRevert(NotAllowed.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(10e18, 10e18); // apr0TotalPrincipal != 0 && unscaledApr != 0

    // Repeatable indefinitely: isEpochRunning stays true, all withdraw
    // requests revert, vault TVL is frozen until attacker voluntarily claims.
}
