### Title
Delayed/permissionless global-fee-state and panic-pause propagation leaves a stale, out-of-sync cache in each `MarginfiGroup` — analogous to zAuction's "old contract accepted in parallel" upgrade defect - ([File: programs/marginfi/src/instructions/marginfi_group/propagate_fee_state.rs])

### Summary
Marginfi centralizes protocol-wide emergency pause state and fee configuration in a single `FeeState` PDA, but every group only sees a **cached copy** (`FeeStateCache` / `PanicStateCache`) embedded in the `MarginfiGroup` account. That cache is only updated when someone permissionlessly invokes `propagate_fee_state`. This mirrors the zAuction defect: the "authoritative" reference (`FeeState`) can be updated immediately by the admin, but consumers (each `MarginfiGroup`) keep operating against their last-propagated (stale) copy until a separate, decoupled sync step runs — creating a window where old and new states are simultaneously "active" across groups.

### Finding Description
`FeeState` is the single global source of truth for the pause state (`panic_state`) and program fee parameters, updated instantly by admin calls such as `panic_pause`/`panic_unpause`/`edit_global_fee_state`. [1](#0-0) 

Every `MarginfiGroup`, however, enforces the pause using its own **cached** copy, `panic_state_cache`, not the live `FeeState`: [2](#0-1) 

This cache is only refreshed when the permissionless `propagate_fee_state` instruction is separately invoked against that specific group: [3](#0-2) 

Both the test suite and the admin guide confirm this two-step, non-atomic design explicitly: pausing does *not* automatically propagate to groups — a second, independent call is required per group before that group actually honors the new state: [4](#0-3) 

This is structurally identical to the zAuction bug class: an "accountant"-like intermediary (`MarginfiGroup.panic_state_cache`/`fee_state_cache`) references upstream authoritative state (`FeeState`) that can be updated immediately, but the local reference is not atomically invalidated — it continues to operate under the old configuration until explicitly refreshed. In a protocol with many groups (each of which independently needs `propagate_fee_state` called), an admin's `panic_pause()` call takes effect instantly in `FeeState`, but any group that has not yet had `propagate_fee_state` invoked against it continues to accept deposits/borrows/withdraws/repays as if unpaused — i.e., two "versions" of protocol pause state active in parallel, exactly the scenario the zAuction report calls out ("This may create an unfavorable scenario where two contracts may be active in parallel").

### Impact Explanation
During an emergency pause (the entire purpose of `panic_pause` is incident response, e.g. an oracle exploit or accounting bug), any group whose cache has not been refreshed will keep accepting deposits, borrows, withdrawals, and repays, undermining the emergency stop. Given the propagation step is permissionless but requires an extra transaction *per group*, and there is no atomic, global enforcement, this materially weakens the guarantee that `panic_pause` immediately halts risk exposure protocol-wide — the actual reason the pause mechanism exists. This has direct financial effect: continued interaction with the protocol during exactly the window it was designed to prevent (e.g., ongoing exploitation of a bug/oracle failure) increases loss.

### Likelihood Explanation
This is not a hypothetical: it is an acknowledged operational two-step in the code and docs (pause the global `FeeState`, then separately propagate to each group). Any group operator or user is capable of delaying/omitting the `propagate_fee_state` call (it's permissionless but nobody is forced to submit it), and with more than a handful of groups, guaranteeing all of them are refreshed within the same block/slot as the pause is calling for coordination the protocol does not enforce on-chain.

### Recommendation
Avoid a "cache + manual propagate" pattern for security-critical state like pause/emergency-stop. Either:
- Read `FeeState.panic_state` directly (live) in the constraint checks on deposit/borrow/withdraw/repay/liquidate instructions instead of `MarginfiGroup.panic_state_cache`, or
- Make `panic_pause` atomically iterate/propagate to all groups in the same transaction (not scalable, but at minimum bound to a manageable number of groups), or
- At minimum, require `propagate_fee_state` (for at least the panic-state portion) to be automatically enforced (e.g., every user-facing instruction accepts the `fee_state` account as required and cross-checks its `panic_state` in addition to, or instead of, the cached copy) so no group can lag behind the live pause.

### Proof of Concept
1. Global admin observes an exploit in progress and calls `panic_pause` — `FeeState.panic_state.pause_flags` is set immediately. [5](#0-4) 
2. Group X (one of potentially many active `MarginfiGroup`s) has not yet had `propagate_fee_state` called against it; its `panic_state_cache.pause_flags` is still unset.
3. Because `LendingAccountDeposit`/`LendingAccountBorrow` (and other user flows) only check `group.load()?.is_protocol_paused()`, which reads the group's local (stale) `panic_state_cache`, users can continue to deposit/borrow/withdraw against Group X's banks during the incident window, exactly as tested (unpaused case) here: [6](#0-5) [7](#0-6) 
4. Only after someone (anyone, permissionlessly) submits `propagate_fee_state` for Group X does its cache catch up and start rejecting new operations with `ProtocolPaused`.

Note: I was unable to fully confirm within the available index whether any instruction paths force/imply automatic propagation (e.g., whether `add_bank` or another frequently-called ix opportunistically refreshes the cache) beyond `add_bank` refreshing only `fee_state_cache.last_update`, not the panic cache; this should be verified further in a live session against the full instruction set. [8](#0-7)

```rust
    /// not paused or timer has expired.
    fn is_protocol_paused(&self) -> bool {
        // Note: In rare event clock fails to unwrap, time = 0 always fails the is_expired check.
        let current_timestamp = Clock::get().map(|c| c.unix_timestamp).unwrap_or(0);

            && !self.panic_state_cache.is_expired(current_timestamp)
    }
```

```rust
pub fn propagate_fee(ctx: Context<PropagateFee>) -> Result<()> {
    let mut group = ctx.accounts.marginfi_group.load_mut()?;
    let fee_state = ctx.accounts.fee_state.load()?;

    group.fee_state_cache.global_fee_wallet = fee_state.global_fee_wallet;
    group.fee_state_cache.program_fee_fixed = fee_state.program_fee_fixed;
    group.fee_state_cache.program_fee_rate = fee_state.program_fee_rate;

    let clock = Clock::get()?;
    group.fee_state_cache.last_update = clock.unix_timestamp;

    group
        .panic_state_cache
        .update_from_panic_state(&fee_state.panic_state, clock.unix_timestamp);

    msg!(
        "Propagated fee and panic state to group. Panic state: paused={}",
        group.panic_state_cache.is_paused_flag()
            && !group.panic_state_cache.is_expired(clock.unix_timestamp)
    );

    Ok(())
```
