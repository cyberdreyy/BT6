### Title
Authenticate middleware leaks raw internal error strings (e.g. DB errors) from AuthenticateBySession to unauthenticated clients - ([File: core/web/auth/auth.go])

### Summary
`Authenticate` loops through auth methods and only continues on `auth.ErrorAuthFailed`; any other error is passed straight to `jsonAPIError`, which serializes `err.Error()` into the JSON response body. Unlike `AuthenticateByToken`, `AuthenticateBySession` does not sanitize non-`ErrorAuthFailed` errors returned by `AuthorizedUserWithSession`, so a DB-layer error (e.g. `sql.ErrConnDone`, connection/query errors) triggered by a garbage/stale session cookie is returned verbatim to the caller.

### Finding Description
`Authenticate` (`core/web/auth/auth.go:157-175`) iterates `methods` (`AuthenticateByToken`, `AuthenticateBySession`) and breaks the loop as soon as an error other than `auth.ErrorAuthFailed` is returned, then calls `jsonAPIError(c, http.StatusUnauthorized, err)`. `jsonAPIError` (`core/web/auth/helpers.go:15-23`) does `c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))` when the error isn't a `*models.JSONAPIErrors`, i.e. it puts the raw Go error string into the HTTP response body sent to the client.

`AuthenticateByToken` (`auth.go:78-112`) is careful: it converts `sql.ErrNoRows`/`clsessions.ErrUserSessionExpired` from `FindUserByAPIToken` into `auth.ErrorAuthFailed` before returning, so those don't leak.

`AuthenticateBySession` (`auth.go:55-71`) has no such conversion: if `authr.AuthorizedUserWithSession(ctx, sessionID)` returns any error other than what the concrete implementation happens to map to `ErrorAuthFailed`, it is returned unmodified:
```go
user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
if err != nil {
    return err
}
```
An attacker who fails `AuthenticateByToken` (e.g., by omitting the API key headers, which immediately yields `ErrorAuthFailed` and lets the loop continue) and then supplies any decodable-but-invalid session cookie value that causes `AuthorizedUserWithSession` to hit a DB-layer failure (e.g. transient connection error, context cancellation, or any error path not explicitly mapped to `ErrorAuthFailed` in the concrete implementation) will have that raw error propagated out of `Authenticate` and serialized into the JSON body returned with HTTP 401.

I could not fully verify inside this session which internal-error branches of the concrete `AuthorizedUserWithSession` implementations (`core/sessions/localauth/orm.go`, `core/sessions/ldapauth/ldap.go`, `core/sessions/oidcauth/oidc.go`) are or aren't mapped to `ErrorAuthFailed` — some drivers may wrap all failures as `ErrorAuthFailed` already, and I was not able to open those implementation files before running out of tool calls. If the concrete implementation always converts DB/backend errors to `auth.ErrorAuthFailed` before returning, then this specific propagation path is not reachable with attacker-controlled input, and the vulnerability would be limited to defense-in-depth rather than confirmed exploitability. Given the asymmetry with `AuthenticateByToken` (which explicitly guards against exactly this class of leak) and the direct code path in `Authenticate`/`jsonAPIError` that would leak any unguarded error, this is a credible, code-supported finding, but full exploitability depends on an implementation detail I couldn't verify in this pass.

### Impact Explanation
If reachable, this results in information disclosure: an unauthenticated (or minimally privileged) attacker can trigger backend/DB-layer error strings to be reflected in the HTTP 401 response body, potentially revealing internal implementation details (DB driver messages, query fragments, service names) that aid further reconnaissance/bypass attempts. This falls under Chainlink's information-disclosure impact class — lower severity than authentication bypass itself but still a real confinement violation of internal error data (SECRET_CONFINEMENT-adjacent info leak), not a full auth bypass.

### Likelihood Explanation
Requires no credentials — only an HTTP client capable of omitting/malforming API-key headers (to fall through to session auth) and supplying a session cookie value that reaches an error branch of `AuthorizedUserWithSession` not mapped to `ErrorAuthFailed`. Feasibility is contingent on the concrete implementation actually returning unmapped errors for some invalid-session inputs (e.g., malformed UUID causing driver-level error, or transient DB unavailability) — this could not be conclusively confirmed here.

### Recommendation
Mirror the pattern used in `AuthenticateByToken`: in `AuthenticateBySession`, explicitly check for `sql.ErrNoRows`/session-not-found conditions and map them to `auth.ErrorAuthFailed`, and additionally have `Authenticate`/`jsonAPIError` avoid ever serializing raw internal error strings for authentication failures — e.g., always respond with a generic "unauthorized" message for any error surfaced from `Authenticate`, logging the underlying error server-side instead of returning `err.Error()` to the client.

### Proof of Concept
Go handler-level integration test:
1. Build a `gin.Engine` with a route wrapped by `Authenticate(store, AuthenticateByToken, AuthenticateBySession)`.
2. Implement a fake `Authenticator`/`clsessions` store whose `FindUserByAPIToken` is never reached (no API key headers sent) and whose `AuthorizedUserWithSession` returns `sql.ErrConnDone` (or another raw, non-`ErrorAuthFailed` error) for any session ID.
3. Send a request with no `X-API-KEY`/`X-API-SECRET` headers and a garbage `clsession` cookie set via `sessions.Default`.
4. Assert response status is 401 and assert the JSON body's error `detail`/`Detail` field does NOT contain `sql.ErrConnDone.Error()` (`"sql: connection is already closed"`) or any other internal error substring — expect it to fail with current code, confirming the leak, and pass after the fix (generic "unauthorized"/`ErrorAuthFailed` message only).
