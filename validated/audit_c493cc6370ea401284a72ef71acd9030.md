I found a concrete, reachable analog to the reported bug class in the Agave `system_program`'s durable-nonce initialization path.

### Title
Missing signer check in `InitializeNonceAccount` allows front-running to hijack nonce authority and steal funds - (File: `programs/system/src/system_instruction.rs`)

### Summary
The `initialize_nonce_account` function, which is the system program's "call-once" initialization routine that binds a `nonce_authority` to a nonce account (transitioning it from `State::Uninitialized` to `State::Initialized`), never verifies that the target account or any designated authority actually signed the transaction. Any transaction that references an already-created, funded, but not-yet-initialized nonce account as writable can set an arbitrary `nonce_authority`, exactly mirroring the Solidity `transferPerpOwner` bug where a privileged "set owner once" call lacked an authorization check.

### Finding Description
`initialize_nonce_account` only validates writability and account state, never signer status: [1](#0-0) 

Compare this to its sibling functions in the same file, `withdraw_nonce_account` and `authorize_nonce_account`, which both take a `signers: &HashSet<Pubkey>` parameter and explicitly call `check_signer(...)`: [2](#0-1) [3](#0-2) 

`initialize_nonce_account` has no such parameter at all. The dispatcher in `system_processor.rs` confirms this — it simply borrows the account and calls the function without passing or checking any signer set for it: [4](#0-3) 

A durable-nonce account only reaches `State::Uninitialized` (with the required data size and rent-exempt balance) after `SystemInstruction::CreateAccount` succeeds — which does require the new account's private key to sign. However, `CreateAccount` and `InitializeNonceAccount` are not enforced to be atomic by the protocol; they are only bundled together by convention in client helpers such as `system_instruction::create_nonce_account`. Nothing in the runtime prevents a user (or intermediate infra) from submitting them as two separate transactions, creating a window where the created-but-uninitialized nonce account sits in the mempool/ledger waiting for a follow-up `InitializeNonceAccount` transaction.

Because `initialize_nonce_account` does not require the nonce account (or any other key) to sign, any third party can observe the pending "initialize" transaction (or simply detect an uninitialized nonce account on-chain) and submit their own `InitializeNonceAccount` instruction targeting the same account with a `nonce_authority` of their choosing, before the legitimate initialize transaction lands. Since the state transition is guarded only by `State::Uninitialized -> State::Initialized` (a one-time gate, just like the Solidity `perp != address(0)` check), whoever's transaction confirms first wins.

### Impact Explanation
This is worse than the referenced report's pure DoS: after hijacking the `nonce_authority`, the attacker can call `WithdrawNonceAccount`. In `withdraw_nonce_account`, once `State::Initialized`, only `check_signer(&data.authority)` is required to withdraw the account's lamports: [5](#0-4) 

Since the attacker set `data.authority` to their own pubkey, they can sign as that authority and drain the full rent-exempt balance (and any extra funding) the legitimate creator placed in the account — a direct, unauthorized fund theft, plus permanent loss of the intended nonce account's usability (denial of service for durable-nonce-based transactions relying on it).

### Likelihood Explanation
Exploitation requires only that `CreateAccount` and `InitializeNonceAccount` be submitted as separate transactions (or otherwise be separately observable/interceptable before both land) — a pattern not prevented by the protocol despite being the non-default path in the reference CLI helper. Any actor with basic mempool/RPC visibility and the ability to submit a competing transaction with higher priority fees can win the race, with no privileged access, leaked keys, or node-level compromise required.

### Recommendation
Require a signer for nonce initialization: either mandate that the nonce account itself sign `InitializeNonceAccount` (matching the invariant implied by its `is_signer: true` usage in test/helper code), or make the check explicit by threading a `signers: &HashSet<Pubkey>` parameter into `initialize_nonce_account` and validating it, consistent with `withdraw_nonce_account` and `authorize_nonce_account`. Document that `CreateAccount` + `InitializeNonceAccount` must be treated as atomic and warn integrators against splitting them across transactions.

### Proof of Concept
1. Alice submits `SystemInstruction::CreateAccount` for a new keypair `N`, sized `nonce::state::State::size()`, owned by `system_program`, funded to at least rent-exemption (`N` signs this tx).
2. Alice separately prepares a second transaction containing only `SystemInstruction::InitializeNonceAccount(alice_authority)` targeting `N`, and broadcasts it.
3. Eve observes account `N` on-chain in `State::Uninitialized` (or sees Alice's pending initialize tx) and submits her own `InitializeNonceAccount(eve_pubkey)` instruction for `N` with a higher priority fee, without needing `N`'s private key or any signature over `N`, per `initialize_nonce_account`'s missing signer check: [1](#0-0) 
4. Eve's transaction lands first; `N.state` becomes `State::Initialized(Data { authority: eve_pubkey, .. })`. Alice's subsequent initialize transaction fails (`InstructionError::InvalidAccountData`, since state is no longer `Uninitialized`).
5. Eve calls `SystemInstruction::WithdrawNonceAccount` on `N`, signing as `eve_pubkey`, and drains all lamports Alice deposited into `N`.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}

pub(crate) fn authorize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Authorize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }
    match account
        .get_state::<Versions>()?
        .authorize(signers, *nonce_authority)
    {
        Ok(versions) => account.set_state(&versions),
        Err(AuthorizeNonceError::Uninitialized) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
        Err(AuthorizeNonceError::MissingRequiredSignature(account_authority)) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} must sign",
                account_authority
            );
            Err(InstructionError::MissingRequiredSignature)
        }
    }
}
