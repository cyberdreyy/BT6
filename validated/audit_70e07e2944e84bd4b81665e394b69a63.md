### Title
Snapshot download timeout can be bypassed by a stalled TCP receiver, keeping the file handle and RPC task open indefinitely - ([File: rpc/src/rpc_service.rs])

### Summary
`TimeoutStream::poll_next` in `rpc/src/rpc_service.rs` only checks `Instant::now() >= self.deadline` when the stream is actually polled, but hyper (and the underlying `jsonrpc_http_server`) only calls `poll_next` on the response body when it has room to write more bytes to the client socket. A client that opens a snapshot download and then stops reading (closes its TCP receive window) prevents `poll_next` from ever being invoked again, so the deadline check never fires and the `tokio::fs::File` plus its serving task stay alive past the intended timeout.

### Finding Description
`process_file_get` in `rpc/src/rpc_service.rs` (lines 255-335) opens the snapshot/genesis file with `Self::open_no_follow` and wraps the resulting `FramedRead` stream in `TimeoutStream::new(stream, timeout)` before handing it to `hyper::Body::wrap_stream`: [1](#0-0) 

`TimeoutStream::poll_next` is the only place the deadline is enforced: [2](#0-1) 

The deadline check `Instant::now() >= self.deadline` executes solely as a side effect of the stream being polled — there is no independent timer/task (e.g., `tokio::time::sleep` armed as a waker) that forces re-polling once the deadline passes. In hyper 0.14 (used transitively via `jsonrpc_http_server`, see Cargo.lock), the server's `Body` is only polled for more data when the connection's write side has capacity to send it to the socket. If the remote peer stops reading (advertises a zero TCP receive window, or simply never calls `recv`), hyper's connection write loop returns `Pending` without touching the body/stream, so `TimeoutStream::poll_next` is never invoked again. Consequently:
- the `tokio::fs::File` opened in `open_no_follow` remains open (FD held),
- the `FramedRead`/`TimeoutStream` future and its associated task stay resident in the `solRpcEl` runtime,
- the deadline value computed from `snapshot_timeout` (up to `FALLBACK_FULL_SNAPSHOT_TIMEOUT_SECS` = 12,000s, or unbounded if `SnapshotInterval::Disabled` combined with a long slot interval) is never actually enforced because the check code path is unreachable while the peer refuses to drain the socket.

No other guard (parameter limit, commitment check, subscription quota) protects this path, since it is a raw HTTP body-streaming endpoint outside the JSON-RPC method dispatch, and reachable via a single unauthenticated HTTP GET to `/snapshot.tar.bz2`, `/incremental-snapshot.tar.bz2`, or the genesis path.

### Impact Explanation
A single HTTP request from one unprivileged client can hold a snapshot file descriptor and an RPC worker task open for far longer than the configured/fallback timeout is meant to allow, by simply not reading the response. This defeats the explicit purpose of `TimeoutStream` (bounding per-request resource cost) and ties up file descriptors on the validator without the attacker needing to repeat requests, matching the "unbounded cost for a single low-rate call" bounty category, since one initial GET (well under the `CLUSTER_SLOT_TIME_TARGET / 2` rate limit) is sufficient to keep the resource open indefinitely.

### Likelihood Explanation
Highly feasible and fully attacker-controlled: any TCP client can advertise a zero receive window or simply stop calling `recv()` after establishing the connection and issuing the GET request; no special privileges, cluster participation, or repeated requests are needed. The behavior is deterministic given hyper's backpressure-driven polling model, and is straightforward to reproduce in an integration test using a mock `Stream` that never completes and a consumer that never polls the wrapping body.

### Recommendation
Enforce the deadline independently of downstream polling pressure, e.g., wrap the stream/file operation with `tokio::time::timeout` driven by an explicit `tokio::time::Sleep` registered against the task's waker (so the deadline fires even when the body isn't being polled), or spawn a companion watchdog task that aborts/drops the file handle when the deadline elapses regardless of whether `poll_next` is called. Alternatively, configure connection/idle-timeouts at the hyper/socket level (e.g., `TcpStream` read/write timeouts or `http1_max_buf_size`/idle timers) so stalled peers are disconnected server-side.

### Proof of Concept
```rust
// integration-style test sketch, added near TimeoutStream in rpc/src/rpc_service.rs tests
#[tokio::test]
async fn test_timeout_stream_not_enforced_without_polling() {
    use futures::stream;
    use std::time::Duration;

    // A stream that would yield data if polled, but we simulate a consumer
    // that never polls it (mirrors hyper not polling body when socket write
    // buffer is full / peer stopped reading).
    let inner = stream::pending::<std::io::Result<Bytes>>();
    let mut timeout_stream = TimeoutStream::new(inner, Duration::from_millis(50));

    // Wait past the deadline WITHOUT polling the stream at all.
    tokio::time::sleep(Duration::from_millis(200)).await;

    // Because nothing polled `timeout_stream`, the deadline check inside
    // poll_next never executed. If we now poll it, in a correct
    // implementation it should immediately report timeout on first poll
    // after resuming — but underlying resources (e.g., the wrapped file)
    // were never reclaimed during the 150ms the deadline was already passed
    // and no external polling occurred, demonstrating the resource stayed
    // "alive" purely because of poll-driven enforcement.
    use futures::StreamExt;
    let first_poll_result = timeout_stream.next().await;
    assert!(matches!(first_poll_result, Some(Err(e)) if e.kind() == std::io::ErrorKind::TimedOut));

    // The assertion that matters for the vulnerability: construct a scenario
    // where poll_next is *never* called again (simulate via hyper body with
    // a client that never reads), and observe (via strace/lsof in an e2e
    // harness) that the underlying tokio::fs::File FD opened in
    // process_file_get remains open past `timeout` with no external
    // cancellation mechanism reclaiming it.
}
```
A full end-to-end PoC would start `JsonRpcService` with a `snapshot_config`, issue a raw TCP `GET /snapshot.tar.bz2` request, read only the HTTP headers, and then stop reading from the socket (or set `SO_RCVBUF` to 0) while polling `/proc/<pid>/fd` (or using `lsof`) to confirm the snapshot file FD remains open well past the configured `snapshot_timeout`.
