### Title
Global `ClientConnectionTracker` concurrent-connection cap can be exhausted by never-completing QUIC handshakes before per-IP/global rate limiters ever consume a token, causing TPU ingest denial - (File: streamer/src/nonblocking/quic.rs)

### Summary
`ClientConnectionTracker::new` gates every incoming QUIC connection against a single global counter (`stats.open_connections` vs `qos.max_concurrent_connections()`), and this gate is consumed *before* either the per-IP `ConnectionRateLimiter` or the global `overall_connection_rate_limiter` actually deduct a token. Because those limiters only consume tokens once the QUIC handshake fully completes (in `setup_connection`), an unprivileged attacker who opens connections but never lets the handshake finish can occupy tracker slots up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` without ever tripping either rate limiter, letting them fill `max_concurrent_connections` and cause legitimate (including high-stake) connections to be refused via `refused_connections_too_many_open_connections`.

### Finding Description
In the accept loop of `run_server` (`streamer/src/nonblocking/quic.rs`), for every incoming connection the following order of operations occurs:
1. `overall_connection_rate_limiter.current_tokens() == 0` is checked [1](#0-0) 
2. `rate_limiter.is_allowed(&incoming.remote_address().ip())` is checked [2](#0-1) 
3. `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` is called, which increments the global `open_connections` atomic and fails (returning `Err`) once `open_connections >= max_concurrent_connections`, triggering `refused_connections_too_many_open_connections` and `incoming.refuse()` [3](#0-2) 

Crucially, steps 1 and 2 are **non-consuming reads**: `TokenBucket::current_tokens()` only reads/refills, it never deducts [4](#0-3) , and `ConnectionRateLimiter::is_allowed()` is documented and implemented to only check without mutating state [5](#0-4) . The actual token consumption for both limiters only happens later, inside `setup_connection`, **after** the QUIC handshake (`connecting.await`) completes successfully: `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` [6](#0-5) .

This means an attacker who initiates a QUIC connection but deliberately never completes the handshake (e.g., sends only an Initial packet, or stalls at any point in the TLS 1.3 handshake) will:
- Pass both non-consuming rate-limiter checks (their bucket is never touched, since `register_connection`/`consume_tokens` are never reached).
- Successfully allocate a `ClientConnectionTracker` slot, incrementing `open_connections`.
- Hold that slot for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (the `timeout()` wrapper around the handshake future in `setup_connection`) before the tracker is dropped and the slot released [7](#0-6) .

`max_concurrent_connections()` for the production `SwQos` controller is `(max_staked_connections + max_unstaked_connections) * 5 / 4` [8](#0-7) , i.e. only a 25% buffer above the sum of the staked and unstaked connection-table capacities, intended to absorb in-flight handshakes — not to be an attacker-controlled resource. This admission check occurs before the peer's stake/pubkey is even known (`ClientConnectionTracker::new` takes no peer-identifying information), so all the stake-aware protections (`prune_random`, `prune_unstaked_connections_and_add_new_connection` in `swqos.rs`) that would otherwise protect high-stake connections from unstaked flooding never get a chance to run — a legitimate staked node's connection attempt is refused at this earlier, stake-blind gate.

By continuously generating fresh incomplete-handshake connection attempts faster than `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` expires them, an attacker keeps `open_connections` pinned at `max_concurrent_connections`, causing every subsequent `ClientConnectionTracker::new` call — for any peer, staked or not — to fail, fully denying TPU QUIC ingest. This can in principle be done from a single IP already (since the per-IP limiter is never actually charged for stalled handshakes); distributing across many source IPs as described in the question makes it trivially easier and defeats any future attempt to add IP-based mitigations at this layer, since none of the existing per-IP/global rate limiters are actually enforced against this specific attack pattern.

### Impact Explanation
This is a remote, non-RPC resource-exhaustion / ingest-starvation vulnerability: an unprivileged network client that can merely open QUIC connections to a validator's TPU port (explicitly an in-scope capability) can deny all legitimate transaction ingest — including from staked/high-priority senders — without needing stake, a valid keypair, or completing any handshake/authentication. This matches the "non-RPC remote resource exhaustion" / ingest starvation bounty category.

### Likelihood Explanation
- Requires only network reachability to the TPU QUIC endpoint — no stake, no valid keypair, no privileged access.
- Requires no non-default configuration; `max_concurrent_connections` is derived directly from default `SwQosConfig`/`QuicStreamerConfig` values.
- The primitive (open, stall the handshake, repeat) is simple to automate at scale and does not require the attacker to complete any expensive cryptographic work relative to the defender.
- Repeatable indefinitely as long as the attacker sustains a connection-attempt rate exceeding `1/QUIC_CONNECTION_HANDSHAKE_TIMEOUT * max_concurrent_connections`.
- One caveat/uncertainty: the exact value of `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, `MAX_CONNECTION_BURST`, and `TOTAL_CONNECTIONS_PER_SECOND` (all referenced in `streamer/src/nonblocking/quic.rs`) could not be retrieved from the indexed excerpts available to me, so the precise attacker throughput required to sustain full occupancy is not confirmed here; a Devin session with full file access would be needed to compute exact feasibility bounds. This does not change the underlying logic flaw (non-consuming rate-limiter checks ahead of the consuming `ClientConnectionTracker` slot allocation), only the exact rate needed to exploit it.

### Recommendation
Reorder or restructure the admission checks so that the global concurrent-connection slot is not consumable by connections that never complete the handshake without also being charged against the rate limiters, e.g.:
- Charge (consume) the per-IP and global rate-limiter tokens at `Incoming` acceptance time (before `ClientConnectionTracker::new`), not only after a successful handshake, and refund/credit them back if the handshake succeeds if burst allowance still needs to be preserved.
- Alternatively, track "handshake-pending" connections separately from `open_connections` used for `max_concurrent_connections`, and apply a stricter, IP-agnostic cap plus faster timeout specifically to unauthenticated/pre-handshake connections so a stalled-handshake flood cannot consume the same budget available to fully-established, stake-classified connections.
- Reduce `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` and/or size `max_concurrent_connections`'s headroom based on measured pending-handshake needs rather than a static 25% multiplier, and add a dedicated, always-consuming rate limit on the number of `Incoming` connections regardless of subsequent completion.
