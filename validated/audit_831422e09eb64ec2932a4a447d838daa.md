## Title
Single-step `ActivationRegistry.setAdmin` can permanently brick feature-activation admin control - (File: `crates/common/precompiles/src/activation/storage.rs`)

### Summary
The Base activation-registry precompile exposes a single-step `setAdmin` function that lets the current admin rotate the state-backed admin address in one transaction. Unlike the `PolicyRegistry` precompile in the same codebase — which implements a `stageUpdateAdmin` / `finalizeUpdateAdmin` two-step transfer — `ActivationRegistryStorage::set_admin` writes the new admin directly after only checking for the zero address, with no confirmation step from the new address.

### Finding Description
`set_admin` validates static-call context, `state_enabled`, and rejects only `Address::ZERO`; it never verifies the new address can act (no acceptance step): [1](#0-0) 

This is dispatched directly off a single ABI call from the current admin: [2](#0-1) 

Once a non-zero value is written to the `admin` storage slot, `admin()` always prefers the stored value over the static chain-config fallback and never falls back again: [3](#0-2) 

Because `require_admin_caller` requires `caller == admin` for every mutating call (including `setAdmin` itself), an incorrect `newAdmin` address (typo, wrong checksum, address with no known private key) makes the admin slot permanently unrecoverable — no other caller, including the original static-config fallback admin, can ever call `setAdmin` again: [4](#0-3) 

This is the same bug class as the reported `changeUberOwner()` issue: a privileged single-step address rotation with only a zero-address check, whose accidental misuse to an uncontrolled address is unrecoverable.

### Impact Explanation
The activation-registry admin is the sole authority able to `activate`/`deactivate` Base-native precompile features (`PolicyRegistry`, `B20Stablecoin`, `B20Asset`) once Cobalt's state-backed admin path is in effect: [5](#0-4) 

If `setAdmin` is called with an incorrect (non-zero) address, feature activation/deactivation is permanently locked at whatever state it was in at that time — no future feature can ever be activated, and if a feature ever needs an emergency deactivation, that emergency control is lost as well. Since the state-backed admin permanently overrides the static fallback, there is no protocol-level recovery path short of a hard fork/chain-spec change. This matches the original report's classification: low probability (requires an operational mistake), but high and irreversible impact on governance-critical control.

### Likelihood Explanation
Low — this requires the legitimate current admin (an operationally privileged actor) to make a mistake by supplying an address it does not control as `newAdmin`. It is not exploitable by an unprivileged attacker directly, but it is a single signed transaction away from a permanent lockout, with no on-chain safety net (unlike `PolicyRegistry`, which already implements the safer two-step pattern in this same repository).

### Recommendation
Adopt the same two-step pattern already implemented for `PolicyRegistry` (`stageUpdateAdmin` / `finalizeUpdateAdmin`, see `crates/common/precompiles/src/policy/logic/v2.rs`) for the activation registry: add a `pendingAdmin` slot, have `setAdmin`/`stageUpdateAdmin` merely stage the candidate, and require the candidate itself to call a `finalizeUpdateAdmin`/`acceptAdmin` from its own address before the rotation takes effect.

### Proof of Concept
1. Deploy/enable the activation registry with Cobalt's state-backed admin (`ActivationAdminConfig::state_backed`).
2. Current admin `A` calls `setAdmin(newAdmin = X)` where `X` is a typo'd/unowned address (non-zero, so it passes the only check in `set_admin`), see `crates/common/precompiles/src/activation/storage.rs:162-169`.
3. `admin()` now returns `X` permanently (state-backed value always wins once non-zero), `crates/common/precompiles/src/activation/storage.rs:105-113`.
4. Any subsequent `setAdmin`, `activate`, or `deactivate` call reverts with `Unauthorized` for every caller except `X`, and `X`'s private key is unknown/unowned — permanently freezing the activation-admin capability, as reproduced by the existing `set_admin_updates_storage_and_authorization` test pattern showing the prior admin loses all authority immediately after rotation (`crates/common/precompiles/src/activation/storage.rs:455-493`).

    pub fn set_admin(
        &mut self,
        new_admin: Address,
        admin_config: ActivationAdminConfig,
    ) -> Result<()> {
        if self.storage.is_static() {
            return Err(BasePrecompileError::revert(IActivationRegistry::StaticCallNotAllowed {}));
        }
        if !admin_config.state_enabled {
            return Err(BasePrecompileError::revert(
                IActivationRegistry::AdminStorageNotEnabled {},
            ));
        }
        if new_admin.is_zero() {
            return Err(BasePrecompileError::revert(IActivationRegistry::ZeroAdminAddress {}));
        }

        let caller = self.require_admin_caller(admin_config)?;

        self.__initialize()?;
        self.admin.write(new_admin)?;
        self.emit_event(IActivationRegistry::AdminChanged {
            previousAdmin: caller,
            newAdmin: new_admin,
            caller,
        })?;

        Ok(())
    }

    /// Reverts unless the current caller is the effective activation admin.
    pub fn require_admin_caller(&self, admin_config: ActivationAdminConfig) -> Result<Address> {
        let caller = self.storage.caller();
        let admin = self.authorized_admin(admin_config)?;
        if caller != admin {
            return Err(BasePrecompileError::revert(IActivationRegistry::Unauthorized { caller }));
        }
        Ok(caller)
    }
