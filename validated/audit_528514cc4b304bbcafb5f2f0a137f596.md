### Title
Builder withdrawal amount honored by the EL is not capped to the builder's actual balance, creating unbacked Gwei - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas (EIP-7732) builder-withdrawal path, the `Withdrawal` object placed into `state.payload_expected_withdrawals` (which the execution layer is spec-required to honor in full) carries the **full requested** `BuilderPendingWithdrawal.amount`, while the corresponding deduction from the builder's own tracked balance in `apply_withdrawals` is explicitly capped with `min(withdrawal.amount, builder_balance)`. If a builder's balance is insufficient at processing time, the EL still pays out the full uncapped amount while the CL only debits what the builder actually had, permanently minting the difference.

### Finding Description
`apply_withdrawals` in `specs/gloas/beacon-chain.md` handles builder withdrawals as: [1](#0-0) 

Here the withdrawal that is queued into `payload_expected_withdrawals` (via `get_builder_withdrawals`/`get_expected_withdrawals`) still carries the original, uncapped `amount` field taken from `BuilderPendingWithdrawal.amount`; only the *bookkeeping* deduction from `state.builders[builder_index].balance` is capped with `min()`. The spec's own commentary on `process_withdrawals` states the invariant that must hold to avoid supply inflation: [2](#0-1) 

That note explains that any silent balance-deduction saturation (i.e., "capping" rather than paying the full committed amount) while "the execution layer mints the full committed amount regardless" creates net supply inflation. This exact scenario is reproduced for builders: the withdrawal committed to (and thus minted by) the EL is the *uncapped* requested amount, while the CL-side balance deduction is explicitly saturated via `min()`.

This is directly confirmed by the test suite, which documents and asserts this exact behavior as the intended output: [3](#0-2) 

i.e. with only 1 ETH backing, a withdrawal committing to pay out 5 ETH is produced (`withdrawal.amount: 5 ETH (requested amount)`), while `builders[0].balance` is merely zeroed rather than the shortfall being rejected, deferred, or otherwise reconciled.

### Impact Explanation
This breaks the fundamental "no Gwei created out of thin air" invariant the spec text itself calls out for validators. Here, a builder (or a party who caused the builder's balance to be depleted before its already-queued `builder_pending_withdrawals` entry is processed, e.g. via an earlier withdrawal or penalty within the same sweep) causes the protocol to commit the beacon block to an execution-layer payment that exceeds what was ever escrowed for that builder. The excess Gwei paid to the `fee_recipient` is unbacked, i.e., Gwei created and paid to a party without any actual staked balance backing it — a Critical-class issue in the given rubric ("Gwei created, destroyed or paid to a non-owner").

### Likelihood Explanation
No coalition, malicious peer, or client bug is required: it only takes the builder's own balance to be lower than the amount it (or governance/protocol logic) previously queued in `builder_pending_withdrawals`, which can occur naturally, e.g., multiple pending withdrawals for the same builder are queued before being swept, and once earlier ones are processed the builder balance is depleted below what a later, still-unprocessed request demands. The behavior is deterministic and spec-following nodes will all agree on the (over-)payment, so this is a specification defect, not a divergence bug, but it results in real value being paid out unbacked by any account.

### Recommendation
Either (a) cap the `Withdrawal.amount` placed into `payload_expected_withdrawals` (and hence honored by the EL) to `min(requested_amount, builder.balance)` at construction time in `get_builder_withdrawals`, mirroring the cap already applied to `builder.balance` in `apply_withdrawals`, or (b) skip/defer builder-pending-withdrawal entries whose requested amount exceeds the builder's current balance instead of silently truncating the balance deduction while still committing the EL to the full amount. Either fix restores the "EL mints exactly what CL committed to, and CL only committed to what was backed" invariant that the spec text already emphasizes for the validator withdrawal path.

### Proof of Concept
1. `state.builders[0].balance = 1_000_000_000` (1 ETH).
2. `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, amount=5_000_000_000, fee_recipient=X)]` (5 ETH requested, queued earlier when balance was sufficient or simply mis-tracked).
3. Block is processed; `get_builder_withdrawals`/`get_expected_withdrawals` produces `Withdrawal(validator_index=<builder 0>, amount=5_000_000_000, address=X)`, which is placed in `state.payload_expected_withdrawals` — the EL is spec-required to honor this in full.
4. `apply_withdrawals` executes `state.builders[0].balance -= min(5_000_000_000, 1_000_000_000)`, leaving `state.builders[0].balance == 0`.
5. Net result: EL mints and pays 5 ETH to `X`, while only 1 ETH was ever tracked/escrowed for builder 0 — 4 ETH created with no corresponding stake, exactly reproducing the test `test_builder_withdrawal_insufficient_balance` at [4](#0-3) .

```markdown
*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
```

```python
def test_builder_withdrawal_insufficient_balance(spec, state):
    """
    Test builder withdrawal with insufficient balance.

    Input State Configured:
        - state.builders[0]: Builder exists with only 1 ETH balance
        - builder_pending_withdrawals: Contains 1 entry requesting 5 ETH
        - builders[0].balance: 1 ETH (insufficient for requested 5 ETH)

    Output State Verified:
        - payload_expected_withdrawals: Contains 1 withdrawal
        - withdrawal.amount: 5 ETH (requested amount)
        - builders[0].balance: 0 (deduction capped to available balance)
        - builder_pending_withdrawals: Reduced by 1 (processed even if capped)
        - next_withdrawal_index: Incremented by 1
    """
    builder_index = 0
    withdrawal_amount = spec.Gwei(5_000_000_000)
    available_balance = spec.Gwei(1_000_000_000)

    prepare_process_withdrawals(
        spec,
        state,
        builder_indices=[builder_index],
        builder_withdrawal_amounts={builder_index: withdrawal_amount},
        builder_balances={builder_index: available_balance},
    )

    pre_state = state.copy()
    yield from run_gloas_withdrawals_processing(spec, state)

        spec,
        state,
        pre_state,
        withdrawal_count=1,
        builder_balances={builder_index: 0},
        builder_pending_delta=-1,
        withdrawal_index_delta=1,
        withdrawal_amounts_builders={builder_index: withdrawal_amount},
    )
```
