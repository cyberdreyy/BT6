### Title
Non-atomic token replacement in `SetAuthToken` allows concurrent `POST /v2/user/token` calls to create two simultaneously valid API tokens for one user - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.SetAuthToken` is meant to enforce "one API token at a time per user" by deleting any existing row before inserting a new one, wrapped in `sqlutil.TransactDataSource`. However the callback ignores the `tx` parameter and issues its `DELETE`/`INSERT`/`SELECT` statements against `l.ds` (the base datasource) instead, so the "transaction" provides no atomicity. Two concurrent `POST /v2/user/token` requests for the same authenticated user can race such that both `DELETE` statements execute (against 0 or the same pre-existing row) before either `INSERT` commits, leaving two valid rows in `ldap_user_api_tokens` for the same `user_email`. `FindUserByAPIToken` itself performs no per-user uniqueness check - it simply looks up by `token_key` and returns whatever row is found - so both tokens remain independently authenticatable.

### Finding Description
`UserController.NewAPIToken` (`core/web/user_controller.go:244-286`) is reachable via the authenticated route `POST /v2/user/token` [1](#0-0) . It validates the user's current password with `TestPassword`, then calls `AuthenticationProvider().SetAuthToken(ctx, &user, newToken)` [2](#0-1) .

In the LDAP authentication provider, `SetAuthToken` wraps its work in `sqlutil.TransactDataSource`, but the callback body queries and mutates using the outer `l.ds` handle rather than the `tx` argument passed into the closure: [3](#0-2) 

Because none of the `SELECT EXISTS`, `DELETE FROM ldap_user_api_tokens`, and `INSERT INTO ldap_user_api_tokens` statements run on `tx`, they are executed as independent, immediately-committed statements against `l.ds`, not as one atomic unit. There is also no unique constraint visible on `user_email` in the table (only `token_key` is looked up as a primary lookup key in `FindUserByAPIToken`) [4](#0-3) , so nothing at the DB layer prevents two rows for the same email.

This produces a classic delete-then-insert TOCTOU race: if two `POST /v2/user/token` requests for the same user execute concurrently, their `DELETE` statements can both run (each seeing 0 or 1 rows, since neither has yet inserted its own row) before either `INSERT` commits. The result is two valid rows in `ldap_user_api_tokens` for one `user_email`, each with its own `token_key`/`token_hashed_secret` and a `user_role` value captured at the time of that specific token creation. `FindUserByAPIToken` performs no per-user single-token invariant check when authenticating incoming requests - it purely looks up by `token_key` and returns the cached `UserEmail`/`UserRole` for that row if not expired [5](#0-4) . Consequently, both tokens continue to authenticate successfully and carry whatever role was cached in their respective row at creation time, until either token individually expires or the periodic upstream sync (`sync.go`) updates/purges rows.

### Impact Explanation
This breaks the documented invariant "user can have only one API token at a time" [6](#0-5) . In the described attack sequence, a user fires two concurrent `POST /v2/user/token` requests while still holding their higher role, both tokens get created with the pre-downgrade role cached, and after the directory role is downgraded, the second (attacker-retained) token continues to authorize actions at the stale, higher role until the next LDAP sync interval elapses. This is authorization confusion / role-based privilege persistence beyond the user's current directory role, matching the "role/authorization bypass" impact class.

### Likelihood Explanation
The attacker only needs a valid, currently-authenticated LDAP session (any role capable of hitting `POST /v2/user/token`, which requires only session/token auth, not admin role) and the ability to send two roughly-simultaneous HTTP requests with their known current password - both are unprivileged/self-service actions. The race window is small but deterministically reproducible with concurrent goroutines/requests in a test harness, since the bug is a genuine non-atomic delete/insert pattern rather than a timing coincidence dependent on external factors.

### Recommendation
Fix `SetAuthToken` to actually use the `tx` parameter for the `SELECT`, `DELETE`, and `INSERT` statements so the replace-token operation is atomic within the transaction. Additionally, add a unique constraint/index on `user_email` in `ldap_user_api_tokens` (or perform an upsert keyed on `user_email`) so the database itself enforces single-token-per-user even under concurrent writers, and consider using `SELECT ... FOR UPDATE` or a serializable transaction to close the TOCTOU window entirely.

### Proof of Concept
Go integration test plan targeting `core/sessions/ldapauth`:
1. Construct an `ldapAuthenticator` backed by a real test Postgres datasource (as done in `ldap_test.go`), with a seeded user having role `Edit`.
2. Launch two goroutines concurrently calling `SetAuthToken(ctx, &user, auth.NewToken())` for the same `user.Email`.
3. After both goroutines complete, query `SELECT count(*) FROM ldap_user_api_tokens WHERE user_email = $1` and assert it is `1` (currently fails, showing `2`).
4. Call `FindUserByAPIToken` with both returned `AccessKey`s and assert both currently succeed (demonstrating two simultaneously valid tokens), then simulate a role downgrade sync and confirm one token still returns the pre-downgrade role until sync runs.

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	return sessions.User{
		Email: foundUserToken.UserEmail,
		Role:  foundUserToken.UserRole,
	}, nil
}
