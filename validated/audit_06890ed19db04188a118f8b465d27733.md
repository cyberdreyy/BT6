## Analysis Result [1](#0-0) 

### Title
Malformed `PRIMARY KEY (signer_addr)` on `block_rejection_signer_addrs` permanently wedges rejection bookkeeping after any signer's second distinct rejection - (File: `stacks-signer/src/signerdb.rs`)

### Summary
The `block_rejection_signer_addrs` table, used by every signer to track which peers rejected which blocks, is defined with `PRIMARY KEY (signer_addr)` instead of a composite key over `(signer_signature_hash, signer_addr)`. Since a signer address is expected to reject many different blocks over its lifetime, this schema silently caps each address to exactly one rejection record, ever, across the entire local database.

### Finding Description
The table is created as: [1](#0-0) 

Note the primary key is `signer_addr` alone — not `(signer_signature_hash, signer_addr)`. Compare this to the sibling `block_signatures` table, which correctly keys on the signature itself, and to the separately-added index `block_rejection_signer_addrs_on_block_signature_hash` on `signer_signature_hash`, which only makes sense if multiple rows for the same address (across different blocks) were intended to coexist — but the primary key forbids exactly that.

`add_block_rejection_signer_addr` writes to this table: [2](#0-1) 

Walking the logic for a signer address `A` that has already rejected block `hash1`:
1. When a *different* block `hash2` is rejected by `A` (either observed via gossip in `handle_block_rejection`, or `A`'s own rejection), the signature-exists check at line 1930-1940 passes through (no signature exists).
2. The lookup at line 1943-1946 filters by the *compound* pair `(hash2, A)`, which does not match the existing row `(hash1, A)`, so `existing_code` is `None`.
3. Control falls into the `None` branch at line 1972-1983, issuing `INSERT INTO block_rejection_signer_addrs (hash2, A, code)`.
4. This insert collides with the `PRIMARY KEY (signer_addr)` constraint, since a row for `A` already exists (with `hash1`), and SQLite (in `STRICT` mode, `INSERT` without `OR IGNORE`/`OR REPLACE`) returns a constraint-violation error from `self.db.execute(...)`, propagated via `?` as `DBError`.

This is directly analogous to the reported bug class: an identifier meant to scope a write operation (`signer_addr` alone standing in for what should be a per-block key, much like an unsanitized path component in the PyMuPDF `_main_.py get` function standing in for a properly-scoped destination) is insufficiently scoped, so a legitimate operation collides with and corrupts unrelated stored state.

### Impact Explanation
Every signer maintains this table for every block it observes rejections on (`handle_block_rejection`, anchored in `docs/signer-flows.md:368`). It is completely ordinary — not requiring a majority, an attacker's key, or auth token — for the *same* signer address to reject two different blocks over the life of a reward cycle (e.g., two different malformed/late proposals from the same miner, as exercised in `stacks-node/src/tests/signer/v0/mod.rs:2683-2708`, which proposes two distinct invalid blocks in sequence). The moment that happens, every other signer's local database attempt to record the second rejection for that address fails with a DB constraint error:
- If the call site unwraps/panics on this error (the surrounding codebase's established pattern for sibling tables, e.g. `add_block_pre_commit`/`add_block_signature` in `stacks-signer/src/v0/signer.rs:1278-1280`, `2454-2457`, both use `.unwrap_or_else(|_| panic!(...))`), the signer process crashes — a liveness wedge, since the signer stops handling all further events, including legitimate block proposals it should sign.
- At minimum, even if the error is only logged, all subsequent rejections from that address are silently dropped from the rejection-weight tally used by `check_block_against_signer_db_state`/`store_and_process_block_rejection` to decide when 30% rejection weight makes 70% acceptance impossible (`docs/signer-flows.md:368-371`). This breaks the aggregated-weight-vs-verified-accepts equality: rejection weight is permanently undercounted for any address that has rejected more than one block, delaying or preventing correct `GloballyRejected` determinations and potentially stalling the tenure.

Both outcomes fall squarely within the accepted impact categories: a liveness wedge, or a miscounted response (rejection weight silently dropped/undercounted).

### Likelihood Explanation
High. Any signer rejecting two different blocks during normal operation (a routine, frequent event — malformed proposals, late proposals, or contested tenure-start blocks) triggers this on first occurrence, for every other signer tracking that address's rejections. No majority, secret key, or special privilege is required — a single miner or gossip participant proposing two rejectable blocks suffices.

### Recommendation
Change the table's primary key to the composite `(signer_signature_hash, signer_addr)` (matching the query patterns already used throughout `add_block_rejection_signer_addr` and `get_block_rejection_signer_addrs`), with a migration to correct any already-deployed schema. Add a regression test inserting rejections for the same `signer_addr` against two distinct `signer_signature_hash` values and asserting both persist independently.

### Proof of Concept
1. Start a fresh `SignerDb` (in-memory is sufficient, as in `stacks-signer/src/signerdb.rs` test helpers).
2. Call `add_block_rejection_signer_addr(&hash1, &addr, RejectReasonPrefix::X)` — succeeds, inserts a row.
3. Call `add_block_rejection_signer_addr(&hash2, &addr, RejectReasonPrefix::Y)` for a different `hash2` — the internal `INSERT` violates `PRIMARY KEY (signer_addr)` and returns `Err(DBError(...))`, whereas the semantics of the API (and its callers, which track per-block reject weight) require this second, independent rejection to be recorded successfully.     /// Record an observed block rejection_signature
    pub fn add_block_rejection_signer_addr(
        &self,
        block_sighash: &Sha512Trunc256Sum,
        addr: &StacksAddress,
        reject_reason: RejectReasonPrefix,
    ) -> Result<bool, DBError> {
        // If this signer/block already has a signature, do not allow a rejection
        let sig_qry = "SELECT EXISTS(SELECT 1 FROM block_signatures WHERE signer_signature_hash = ?1 AND signer_addr = ?2)";
        let sig_args = params![block_sighash, addr.to_string()];
        let exists = self.db.query_row(sig_qry, sig_args, |row| row.get(0))?;
        if exists {
            warn!("Cannot add block rejection because a signature already exists.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %addr,
                "reject_reason" => ?reject_reason
            );
            return Ok(false);
        }

        // Check if a row exists for this sighash/signer combo
        let qry = "SELECT reject_code FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2 LIMIT 1";
        let args = params![block_sighash, addr.to_string()];
        let existing_code: Option<i64> =
            self.db.query_row(qry, args, |row| row.get(0)).optional()?;

        let reject_code = reject_reason as i64;

        match existing_code {
            Some(code) if code == reject_code => {
                // Row exists with same reject_reason, do nothing
                debug!("Duplicate block rejection.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(false)
            }
            Some(_) => {
                // Row exists but with different reject_reason, update it
                let update_qry = "UPDATE block_rejection_signer_addrs SET reject_code = ?1 WHERE signer_signature_hash = ?2 AND signer_addr = ?3";
                let update_args = params![reject_code, block_sighash, addr.to_string()];
                self.db.execute(update_qry, update_args)?;
                debug!("Updated block rejection reason.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(true)
            }
            None => {
                // Row does not exist, insert it
                let insert_qry = "INSERT INTO block_rejection_signer_addrs (signer_signature_hash, signer_addr, reject_code) VALUES (?1, ?2, ?3)";
                let insert_args = params![block_sighash, addr.to_string(), reject_code];
                self.db.execute(insert_qry, insert_args)?;
                debug!("Inserted block rejection.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(true)
            }
        }
    }
