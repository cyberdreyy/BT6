### Title
Destination-escrow fee parameters are unauthenticated, letting any caller of `createDstEscrow` zero out protocol/integrator fees - (File: `contracts/BaseEscrowFactory.sol`)

### Summary
On the source chain, `_postInteraction` computes `protocolFeeAmount`/`integratorFeeAmount` from the order/extension and only *emits* them inside `DstImmutablesComplement.parameters` via `SrcEscrowCreated` — it never commits them into anything enforceable on-chain for the destination side. [1](#0-0) 

`createDstEscrow` is a permissionless, unauthenticated entry point that accepts a full `IBaseEscrow.Immutables` struct — including the `parameters` field that later decodes into `protocolFeeAmount`, `integratorFeeAmount`, and their recipients — directly from `msg.sender`, with no check that it matches the values emitted on the source chain. [2](#0-1) [3](#0-2) 

At withdrawal time, `EscrowDst._withdraw` blindly trusts whatever fee amounts are embedded in the caller-supplied `immutables.parameters`, deducting them from `immutables.amount` before sending the remainder to the maker. [4](#0-3) 

### Finding Description
This mirrors the Peapods M-28 bug-class: fee collection is derived from a value that a party in the flow fully controls and that isn't cross-validated against the "true" computed fee. Here:

1. The maker signs an order and the resolver fills it via the Limit Order Protocol, triggering `_postInteraction`, which computes the correct `protocolFeeAmount`/`integratorFeeAmount` for the fill and only logs them in an event (`SrcEscrowCreated`).
2. Any address (there is no `onlyTaker`/whitelist modifier on `createDstEscrow`) can subsequently call `createDstEscrow`, submitting its own `Immutables.parameters` blob that ABI-encodes `(protocolFeeAmount, integratorFeeAmount, protocolFeeRecipient, integratorFeeRecipient)`.
3. Because `Immutables.hash()` (used for the CREATE2 address/`onlyValidImmutables` check in `Escrow._validateImmutables`) only binds the escrow to whatever `parameters` value the caller supplies — not to the value the factory computed on the source side — a caller can set both fee amounts to `0` (or any smaller value) with no on-chain rejection.
4. When the maker later reveals the secret and `_withdraw` executes, `integratorFeeAmount` and `protocolFeeAmount` are `0`, so `amount = immutables.amount` in full goes to the maker, and the protocol/integrator fee transfer branches are skipped entirely.

The maker still receives the destination amount they expect (in fact more, since none is diverted to fees), so from the maker's perspective the swap looks legitimate — nothing in the on-chain flow forces off-chain verifiers to notice the fee fields were dropped, since the only invariant enforced by `onlyValidImmutables` is CREATE2-address self-consistency, not agreement with the source-chain fee computation.

### Impact Explanation
This is a permanent loss of unclaimed fee-like value: the protocol fee and integrator fee that should have been routed to `protocolFeeRecipient`/`integratorFeeRecipient` on every destination withdrawal can be reduced to zero by whoever deploys the destination escrow, with no economic penalty and no privileged role required to do so (`createDstEscrow` has no access control). This matches the "High: theft or permanent loss of unclaimed fee-like value" bucket in the bounty scope.

### Likelihood Explanation
`createDstEscrow` is a normal, unprivileged, publicly callable function used on every cross-chain swap; nothing about calling it with self-chosen `parameters` requires elevated privileges, a malicious relayer, or a malicious node — it only requires the caller to fund the escrow with the destination tokens/safety deposit, exactly as any legitimate resolver already does. Any actor willing to act as the destination-side funder can trivially omit the fee split.

### Recommendation
Bind the destination fee parameters cryptographically to the source-chain computation, e.g., by including a hash/commitment of `(protocolFeeAmount, integratorFeeAmount, protocolFeeRecipient, integratorFeeRecipient)` in the `orderHash`/extension data validated during `_postInteraction`, and have `createDstEscrow` (or `EscrowDst._withdraw`) verify the supplied `parameters` against that commitment before accepting/using it, rather than trusting caller-supplied fee data outright.

### Proof of Concept
1. Maker signs a Fusion order; resolver fills it, `_postInteraction` computes `protocolFeeAmount = X`, `integratorFeeAmount = Y` and emits them in `SrcEscrowCreated`.
2. Instead of using those values, the destination-side deployer calls `createDstEscrow` with `dstImmutables.parameters = abi.encode(0, 0, protocolFeeRecipient, integratorFeeRecipient)`, funding the escrow with the same `immutables.amount` and safety deposit as expected.
3. `Escrow._validateImmutables` accepts this because CREATE2 address matches the (attacker-chosen) immutables hash — there is no check against the emitted `X`/`Y`.
4. Once the maker reveals the secret (believing the swap is proceeding correctly, since amount/token/hashlock match expectations) and `EscrowDst._withdraw` runs, `integratorFeeAmount == 0` and `protocolFeeAmount == 0`, so no funds are transferred to `protocolFeeRecipient`/`integratorFeeRecipient`; the maker receives the full `immutables.amount`, and 1inch/integrator permanently loses the fee `X + Y` for that swap.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
