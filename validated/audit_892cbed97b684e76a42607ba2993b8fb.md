### Title
Permanent stopEpoch DoS: APR=0 withdrawal bucket bricks the pool when APR is raised - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Like CVE-2016-3139 (missing validation on an attacker-supplied value causing a crash), `IdleCreditVault.prepareStopEpochWithApr0` fails to handle the state combination "non-zero `apr0TotalPrincipal` + non-zero `unscaledApr`" and unconditionally reverts. Any KYC-passing lender can put the vault into this state, after which every `stopEpoch`/`stopEpochWithDuration` call reverts forever — permanently freezing all pool funds and forcing borrower default.

### Finding Description
In `requestWithdraw`, when `unscaledApr == 0` and the pool is not closed, the request principal is added to the APR0 bucket (`_requestWithdrawApr0` increments `apr0TotalPrincipal`) at `IdleCreditVault.sol:285-294` and `IdleCreditVault.sol:567-577`.

At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which contains at `IdleCreditVault.sol:505-508`:

```solidity
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

`apr0TotalPrincipal` is only reset to 0 at the end of this function (`IdleCreditVault.sol:540`) — after the revert. It is never decremented by `_settleApr0` (`IdleCreditVault.sol:545-565`) or by `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:319-350`), which only mutate per-user data. There is no other code path that clears `apr0TotalPrincipal`.

Attack sequence:
1. Pool runs an epoch with `unscaledApr == 0` (a normal, supported mode — tests exercise `setAprs(0, 0)`).
2. Attacker (KYC-passing lender) deposits and calls `cdoEpoch.requestWithdraw(...)` during buffer. `apr0TotalPrincipal > 0`.
3. Before or after the honest `stopEpoch`, the manager calls `setAprs(x, y)` with `x != 0` — a routine, honest APR update for the next epoch.
4. Every subsequent `stopEpoch` reverts at `prepareStopEpochWithApr0`. `apr0TotalPrincipal` can never be cleared, so the revert is permanent — the epoch can never close, repayment can never be accounted, deposits are frozen.

### Impact Explanation
Permanent freezing of all vault funds: NAV, pending withdraw receipts, and borrower repayment are all gated on a successful `stopEpoch`. The entire TVL becomes unrecoverable through normal flows; the only residual path is forced default handling, which itself runs through the same stop machinery in this variant. Quantified loss: full TVL locked at the time of the stuck epoch.

### Likelihood Explanation
Requires only: (a) the pool operating with `unscaledApr == 0`, (b) one lender requesting a withdrawal in that mode, and (c) the manager later setting a non-zero APR — a normal management action, not attacker-controlled manipulation. All actors involved are unprivileged or honest within the threat model. No race or exotic input is needed.

### Recommendation
Make the APR transition safe: instead of reverting, settle the outstanding APR0 bucket using the last stored `apr0RateByEpoch` / realized interest, or allow clearing `apr0TotalPrincipal` when APR changes (e.g., reset the bucket inside `setAprs` with per-request epoch data preserved so users still settle correctly on claim). At minimum, allow `apr0TotalPrincipal` to be decremented when APR0 users claim post-transition.

Note: I could not fully verify whether a privileged recovery path (e.g., `emergencyShutdown`/`restoreOperations` or a default-finalization route that bypasses `prepareStopEpochWithApr0`) exists to unstick the pool — the default-handling functions were not exhaustively traced. If `stopEpoch` is the sole path to accounting finality, the freeze is permanent as described.
