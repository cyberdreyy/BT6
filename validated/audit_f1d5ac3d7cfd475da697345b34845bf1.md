### Title
Stale confirmations from removed multisig members are not purged, allowing a request to execute with fewer live-member confirmations than the configured threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only deletes the pending *requests created by* the removed member and their confirmations; it never scans the `confirmations` map of *other* still-pending requests to strip out a vote the removed member previously cast on them. `confirm` later counts raw entries in that `HashSet<String>` against `num_confirmations` without checking that every entry still belongs to a current member. A stale confirmation from a member who has since been deleted therefore still counts toward the K-of-N threshold, letting the request execute with fewer than K live signers agreeing.

### Finding Description
`confirm` decides whether to execute a request purely by set size: [1](#0-0) 

`delete_member` removes the member from `self.members`, deletes requests *they authored*, and cleans `num_requests_pk`, but does not touch `self.confirmations` entries for requests authored by other members that this member had already confirmed: [2](#0-1) 

The only safety check in `delete_member` is that the remaining member count stays `>= num_confirmations`: [3](#0-2) 

That check protects against making the contract permanently un-executable, but says nothing about the integrity of *already recorded* confirmations. The binding the system is supposed to maintain is:

```
confirmations counted toward execution == confirmations from currently live members
```

but after a `DeleteMember` action, it becomes:

```
confirmations counted toward execution == confirmations from live members ∪ {stale confirmations from removed members on requests they didn't author}
```

The equivalent v1 contract has the same pattern: `DeleteKey` only purges requests authored by that key, not confirmations that key placed on requests authored by others, while `confirm` again just compares raw set size to `num_confirmations`: [4](#0-3) [5](#0-4) 

### Impact Explanation
This breaks the K-of-N authorization guarantee that all consumers of this multisig contract rely on (transfers of NEAR/wNEAR, adding/removing keys, deploying code, function calls). Concretely: a member who confirms a `Transfer` request (e.g. to their own account) and is subsequently removed from the multisig (for being compromised, leaving the organization, etc.) leaves behind a live confirmation that still counts. The remaining live members then only need `num_confirmations - 1` (not `num_confirmations`) of their own approvals to execute that pending request, since the phantom vote of a no-longer-authorized party fills the last slot. This matches the "Critical" category "a multisig request executed below threshold" — funds can be moved, keys added/removed, or contract code deployed with fewer genuinely authorized approvals than the configured threshold.

### Likelihood Explanation
The scenario requires only ordinary multisig operations: a member creates or confirms a normal request (no special privilege beyond being an existing member, which every member already has), and afterwards any other legitimate `DeleteMember` action occurs (a routine event — key rotation, offboarding, suspected compromise). No front-running, redeploy, or foundation/owner privilege is needed beyond standard multisig membership churn, which is an expected and common operation for these contracts over their lifetime.

### Recommendation
In `delete_member` (and `DeleteKey` in `multisig/src/lib.rs`), iterate over all entries in `confirmations` (not just requests authored by the removed member) and remove the removed member's identifier from every confirmation set. Alternatively, have `confirm`/execution-threshold checks filter the confirmation set against `self.members` (or `self.confirmations.get(&member.to_string())` current validity) before comparing its length to `num_confirmations`, so stale confirmations from removed members can never count toward execution.

### Proof of Concept
1. Deploy `multisig2` with members `[Alice, Bob, Carol, Dave]` and `num_confirmations = 3`.
2. Bob calls `add_request_and_confirm` with a `Transfer` request sending funds to Bob's own account — the request now has 1 confirmation (Bob), stored under `confirmations[request_id] = {Bob}` (`multisig2/src/lib.rs:170-207`, `292-315`).
3. Independently, Alice, Carol, and Dave later confirm a separate `DeleteMember { member: Bob }` request (reaching `num_confirmations = 3`), which executes `delete_member` (`multisig2/src/lib.rs:356-379`). This removes Bob from `self.members` and deletes only requests *authored* by Bob — the Transfer request from step 2 was authored by Bob, so in this exact ordering it, too, gets removed. To realize the bug, instead have **Carol** author the Transfer request and Bob merely confirm it (`add_request` by Carol, then `confirm` by Bob) — now the Transfer request is *not* among "requests authored by Bob," so it survives `delete_member` with `confirmations[request_id] = {Bob}` intact even though Bob is no longer a member.
4. After Bob's removal, only Alice and Carol (2 of the 3 remaining live members) need to call `confirm` on the surviving Transfer request. `confirmations.len() as u32 + 1 >= self.num_confirmations` becomes `2 (Bob-stale + Alice) + 1 (Carol) >= 3`, executing the transfer with only 2 live-member approvals instead of the required 3.         self.assert_valid_request(request_id);

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
