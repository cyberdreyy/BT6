### Title
Cross-user response confusion via attacker-chosen `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each user's response callback in `h.savedCallbacks` keyed only by the client-supplied `msg.Body.MessageId`, with no binding to the requesting user's identity (sender). Because `MessageId` is fully attacker-controlled (any signed gateway client picks the string, up to 128 bytes, only constrained by length/null-suffix checks), an unprivileged attacker can register a request with the same `MessageId` as a victim's in-flight request, causing `handleWebAPITriggerMessage` to deliver the DON node's response for the victim's request to the attacker's callback instead.

### Finding Description
`api.Message.Validate` in [1](#0-0)  only checks length/format of `MessageId`; it never verifies uniqueness or ties it to `Sender`. Any two independent, unrelated signed requests from different users can carry an identical `MessageId`.

In `HandleLegacyUserMessage`, the gateway saves the callback purely by `MessageId`: [2](#0-1) 

This is a plain Go map write (`h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}`), so if user B submits a request with the same `MessageId` as user A's still-pending request, B's `savedCallback` silently overwrites A's entry in the map.

When a DON node later responds (echoing the `MessageId` from the original request sent to it), `handleWebAPITriggerMessage` looks the callback up solely by `MessageId` and delivers the response to whichever callback currently occupies that key, deleting the entry right after lookup: [3](#0-2) 

If B's request overwrote A's entry after A's request was already forwarded to the DON (`don.SendToNode` loop at [4](#0-3) ), then when the node's response for A's original trigger arrives with the shared `MessageId`, it is routed to B's callback, delivering A's response data (and never delivering anything correct to A, who instead gets no response / a stale timeout). Conversely, the attacker can also intentionally register first to intercept whatever data a subsequently-triggered legitimate request generates for the same colliding ID.

This is structurally different from `common.requestCache` (used by other gateway handlers), which explicitly guards against exactly this by keying on `globalId{sender, id}` instead of `id` alone: [5](#0-4) [6](#0-5) 
That cache also rejects a request whose key already exists (`"request already exists"`), preventing overwrite — a protection entirely absent from the `capabilities` handler's `savedCallbacks` map.

No authentication/authorization layer prevents this: any client capable of signing a gateway message (i.e., any holder of a valid signing key recognized by the DON's allowlist — not necessarily a privileged operator) can pick an arbitrary `MessageId`, including one equal to another user's concurrently in-flight `MessageId`. Signature verification only proves who sent a given message; it does nothing to prevent `MessageId` collision between two different senders' unrelated messages.

### Impact Explanation
This allows cross-user response confusion: an unprivileged attacker who can submit signed web API trigger requests to the gateway can cause another user's trigger response (which may include arbitrary web-fetched data flowing back through the DON) to be delivered to the attacker's own callback instead of the rightful requester, and can deny/corrupt the response the victim receives. This matches the bounty class "unauthorized action on another user's job/subscription" / "cross-user response confusion" since responses tied to one user's authenticated request session are hijacked by another.

### Likelihood Explanation
Exploitability requires only: (1) the ability to send a signed gateway `web_api_trigger` request as some address recognized by the DON/gateway allowlist (no special role beyond being an allowed API client), and (2) choosing a `MessageId` value that collides with a victim's concurrently pending request. Because `MessageId` is entirely attacker-chosen freeform text (up to 128 bytes) rather than gateway-generated, an attacker does not need to "guess" a random ID — they can pick any string, including short, predictable, or observed values (e.g., if victims use sequential/timestamp-based/naive-random `MessageId` generation client-side), or simply race using a fixed low-entropy value repeatedly to collide against many concurrent victims. This is fully reproducible in a unit test without any network-level or operator access.

### Recommendation
Key `savedCallbacks` by a composite of `(sender, MessageId)` (mirroring `common.requestCache`'s `globalId{sender, id}`), and reject/no-op on collision (return an error rather than silently overwriting an existing entry) in `HandleLegacyUserMessage`. When looking up in `handleWebAPITriggerMessage`, use the same composite key derived from the DON member's `Sender`/node context bound to the original request, ensuring a node's response can only ever match the exact requester's dispatched request.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Call `setupHandler` to construct a `*handler`.
2. Simulate user A: build a signed `api.Message` with `Body.MessageId = "X"`, `Sender = userA`, and invoke `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` where `callbackA` is a mock `handlers.Callback` recording invocations. Confirm `h.savedCallbacks["X"]` now points to `callbackA`.
3. Simulate attacker B: build a second signed `api.Message` with the same `Body.MessageId = "X"` but `Sender = userB`, and invoke `h.HandleLegacyUserMessage(ctx, msgB, callbackB)` with mock `callbackB`. Assert `h.savedCallbacks["X"]` now points to `callbackB` (overwritten), i.e., `callbackA` is orphaned.
4. Simulate the DON node responding to user A's original dispatched trigger request by calling `h.HandleNodeMessage(ctx, resp, nodeAddr)` (or directly `handleWebAPITriggerMessage`) with `resp.Body.MessageId = "X"` and content that should belong to A.
5. Assert `callbackB.SendResponse` was called (receiving A's response payload) and `callbackA.SendResponse` was never called — proving the response intended for user A was delivered to attacker B's callback, demonstrating cross-user response confusion.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
