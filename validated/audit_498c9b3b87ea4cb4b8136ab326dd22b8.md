### Title
Missing `VestingSchedule::assert_valid()` check at lockup initialization allows an owner to self-define a degenerate vesting schedule that bypasses foundation clawback - (File: lockup/src/lib.rs)

### Summary
`VestingSchedule::assert_valid()` enforces `start_timestamp <= cliff_timestamp <= end_timestamp` and `start_timestamp < end_timestamp` [1](#0-0) , but this check is never invoked when a public/explicit `VestingSchedule` is supplied at contract initialization, nor when it is forwarded through the factory.

### Finding Description
`LockupContract::new` accepts `vesting_schedule: Option<VestingScheduleOrHash>`. When the caller supplies the explicit, public variant `VestingScheduleOrHash::VestingSchedule(vs)`, the contract stores it directly into `VestingInformation::VestingSchedule(vs)` without ever calling `vs.assert_valid()`: [2](#0-1) 

The same missing validation exists in `lockup-factory/src/lib.rs::create`, which accepts an unauthenticated `vesting_schedule: Option<VestingScheduleOrHash>` from any caller (no owner/foundation restriction on `create`) and forwards it verbatim into the deployed lockup contract's `new` call: [3](#0-2) .

Because `assert_valid()` is defined but dead code on this path, a caller can set, e.g., `start_timestamp == cliff_timestamp == end_timestamp` at (or before) contract creation time, or otherwise order the three timestamps so the schedule is degenerate/already elapsed. `get_unvested_amount` then evaluates the schedule as already past its end: [4](#0-3) 
returning `0` for the unvested amount from the moment the contract exists, regardless of the (documented) real vesting period the schedule was supposed to represent.

The binding broken is: `releasable_amount == f(schedule)` should always evaluate to "0% vested" until `cliff_timestamp` and pro‑rata thereafter until `end_timestamp`; instead an unchecked schedule lets `unvested_amount` collapse to `0` immediately, i.e. `releasable_amount` no longer tracks the intended schedule at all.

### Impact Explanation
This directly maps to the Critical bucket "locked or unvested tokens released early." `terminate_vesting`, the foundation's only recourse to claw back unvested tokens on early termination, requires `unvested_amount.0 > 0`: [5](#0-4) 
With a degenerate schedule, `unvested_amount` is always `0`, so `terminate_vesting` unconditionally panics with `"The account is fully vested"`, permanently defeating the foundation's ability to reclaim any unvested balance, and the owner's tokens (which are supposed to be under a real, multi-year vesting/cliff schedule) are effectively immediately liquid/unclawable from inception.

### Likelihood Explanation
The `assert_valid()` helper exists and is exercised only in test helper code, never in the production `new` constructor path, so any deployment that uses the explicit `VestingScheduleOrHash::VestingSchedule` variant (rather than the hashed variant) is affected. `lockup-factory`'s `create` entry point places no restriction on which timestamps a caller may submit, and no additional revalidation happens later (the hash-reveal path in `assert_vesting` only checks the hash matches, not that the schedule is well-formed) [6](#0-5) . This makes the missing precondition reachable on every contract creation that uses a public vesting schedule.

### Recommendation
Call `vesting_schedule.assert_valid()` inside `LockupContract::new` (`lockup/src/lib.rs`) whenever `VestingScheduleOrHash::VestingSchedule(vs)` is supplied, and reject schedules that are not comfortably in the future relative to `env::block_timestamp()` if that is also a desired invariant, mirroring the analog report's request to bound both ordering and future-dating of the schedule’s timestamps.

### Proof of Concept
1. Attacker calls `lockup-factory::create` with `owner_account_id = attacker`, and `vesting_schedule = Some(VestingScheduleOrHash::VestingSchedule(VestingSchedule { start_timestamp: T, cliff_timestamp: T, end_timestamp: T }))` where `T` is the current or a past timestamp.
2. The factory forwards this unchanged to the newly deployed lockup contract's `new`, which stores it without calling `assert_valid()` [2](#0-1) .
3. From block one, `get_unvested_amount` sees `block_timestamp >= end_timestamp` and returns `0` [7](#0-6) .
4. If the foundation later attempts `terminate_vesting` to claw back unvested tokens (e.g., on early employment termination), the call always panics with `"The account is fully vested"` [8](#0-7) , permanently freezing the foundation out of its clawback right and leaving the full "unvested" balance releasable to the owner despite the nominal multi-year schedule.

    pub fn get_unvested_amount(&self, vesting_schedule: VestingSchedule) -> WrappedBalance {
        let block_timestamp = env::block_timestamp();
        let lockup_amount = self.lockup_information.lockup_amount;
        match &self.vesting_information {
            VestingInformation::Terminating(termination_information) => {
                termination_information.unvested_amount
            }
            VestingInformation::None => U128::from(0),
            _ => {
                if block_timestamp < vesting_schedule.cliff_timestamp.0 {
                    // Before the cliff, nothing is vested
                    lockup_amount.into()
                } else if block_timestamp >= vesting_schedule.end_timestamp.0 {
                    // After the end, everything is vested
                    0.into()
                } else {
                    // cannot overflow since block_timestamp < vesting_schedule.end_timestamp
                    let time_left = U256::from(vesting_schedule.end_timestamp.0 - block_timestamp);
                    // The total time is positive. Checked at the contract initialization.
                    let total_time = U256::from(
                        vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0,
                    );
                    let unvested_amount = U256::from(lockup_amount) * time_left / total_time;
                    // The unvested amount can't be larger than lockup_amount because the
                    // time_left is smaller than total_time.
                    unvested_amount.as_u128().into()
                }
            }

    pub fn assert_vesting(
        &self,
        vesting_schedule_with_salt: Option<VestingScheduleWithSalt>,
    ) -> VestingSchedule {
        match &self.vesting_information {
            VestingInformation::VestingHash(hash) => {
                if let Some(vesting_schedule_with_salt) = vesting_schedule_with_salt {
                    assert_eq!(
                        &vesting_schedule_with_salt.hash(),
                        &hash.0,
                        "Presented vesting schedule and salt don't match the hash"
                    );
                    vesting_schedule_with_salt.vesting_schedule
                } else {
                    env::panic(b"Expected vesting schedule and salt, but it was not provided")
                }
            }
            VestingInformation::VestingSchedule(vesting_schedule) => {
                assert!(
                    vesting_schedule_with_salt.is_none(),
                    "Explicit vesting schedule exists"
                );
                vesting_schedule.clone()
            }
            VestingInformation::Terminating(_) => env::panic(b"Vesting was terminated"),
            VestingInformation::None => env::panic(b"Vesting is None"),
        }
    }
