### Title
Loss-adjusted withdraw receipts can be re-requested into a later epoch and claimed at par, escaping the stopEpochWithDuration haircut - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`collectWithdrawFunds` stores the pro-rata receipt haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. Because `requestWithdraw` overwrites `lastWithdrawRequest[_user]` on every new request and never blocks re-requesting while an old receipt is unclaimed, a user who makes any later withdraw request permanently loses the pointer to the loss epoch. The stale haircutted basis stays in `withdrawsRequests[_user]` and is then paid at par by `_claimFundedWithdrawRequest`, while the strategy only holds the haircutted amount.

### Finding Description

When `stopEpochWithDuration` realizes a loss with pending receipts, `previewLossAdjustedWithdrawFunds` splits the loss pro rata and `collectWithdrawFunds` records the funded ratio keyed by the current epoch:

- `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (`IdleCreditVault.sol:421`) and `pendingWithdraws = 0`.
- The per-user basis remains in `withdrawsRequestsByEpoch[user][lossEpoch]` and in the aggregate `withdrawsRequests[user]`.

On claim, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which only checks the epoch stored in `lastWithdrawRequest[_user]`:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```
(`IdleCreditVault.sol:789-792`)

`_clearWithdrawClaimForEpoch` is therefore only ever invoked for `lastWithdrawRequest[_user]` (or `defaultRecoveryEpoch`). But `requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` unconditionally on each request (`IdleCreditVault.sol:282`), and nothing in the CDO's `requestWithdraw` prevents a user with an uncleared loss-epoch receipt from requesting again in a later buffer period — the code comments even acknowledge this flow ("if a user does not claim ... and instead requests another withdraw, he will have to wait for another epoch"). Once a second request lands in epoch M > N:

- `lastWithdrawRequest[user] = M`, `lossRecoveryPriceByEpoch[M] == 0`, so the loss-adjusted path returns 0.
- `withdrawsRequestsByEpoch[user][N]` stays non-zero forever; `_claimLossAdjustedWithdrawRequest` can never reach epoch N again.
- `_claimFundedWithdrawRequest` then pays `normalAmount = withdrawsRequests[user]` — which still includes the unhaircutted epoch-N basis — at par, and burns the corresponding receipt tokens the user legitimately holds.

The strategy only received `lossRecoveryPrice * basis` for those epoch-N receipts, so the excess `(basis − funded)` is paid out of funds belonging to other pending/funded claimants or active LPs.

### Impact Explanation

Direct theft / insolvency. The attacker converts a haircutted receipt into a par claim: they recover `receiptBasis` instead of `receiptBasis * lossRecoveryPrice`, stealing the haircut amount from the strategy's funded pool. The theft is bounded by the attacker's pending basis in a loss epoch, but the owner controls `_lossAmount` economically — an attacker can simply hold a large pending request when a loss stop occurs, or be one of several pending redeemers sharing `pendingLoss` pro rata. Every later claimaint is insolvent by the amount overpaid; underflow on `balanceOf` or insufficient strategy balance will make honest users' claims revert (permanent freezing of their funded claims once the pool is drained).

### Likelihood Explanation

The sequence is fully attacker-driven with only honest-privileged calls interleaved:

1. Buffer phase: attacker (a KYC-passing lender) deposits into AA and calls `requestWithdraw`, creating a pending receipt for epoch N.
2. Epoch N runs and ends with an honest `stopEpochWithDuration(..., _lossAmount)` (e.g., a real borrower shortfall); `collectWithdrawFunds` funds receipts at `lossRecoveryPrice < 1`.
3. Buffer phase of epoch N+1: attacker calls `requestWithdraw` again on remaining tranche tokens — `allowAAWithdrawRequest` is true and no check blocks a prior unclaimed receipt. `lastWithdrawRequest` is overwritten to N+1.
4. After epoch N+1's `stopEpoch` funds the new receipts, `claimWithdrawRequest` pays the aggregate `withdrawsRequests[user]` at par.

No default, no flag manipulation, and no privileged misbehavior is required — only a loss-epoch stop, which is a normal operating event the codebase explicitly supports.

### Recommendation

Track the loss-adjusted epoch per user rather than only via `lastWithdrawRequest`. Options:

- In `_claimLossAdjustedWithdrawRequest`, iterate/record all epochs with `lossRecoveryPriceByEpoch[e] != 0` for which `withdrawsRequestsByEpoch[user][e] != 0` (e.g., store a per-user `lastLossEpoch` or a bitmap of pending haircutted epochs when `collectWithdrawFunds` writes the price), and clear those bases before the funded claim path runs.
- Alternatively, in `requestWithdraw`, force settlement of any existing receipt belonging to a loss-adjusted epoch before accepting the new request, so `withdrawsRequests[user]` can never mix haircutted and par basis.

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
// Foundry fork test against deployed IdleCreditVault + IdleCDOEpochVariant
function testLossEpochHaircutEscape() public {
    // --- setup: attacker deposits AA in buffer phase ---
    deal(underlying, attacker, 200_000e6);
    vm.startPrank(attacker);
    IERC20(underlying).approve(address(cdo), type(uint256).max);
    cdo.depositAA(200_000e6);                 // KYC'd attacker wallet
    vm.stopPrank();

    // --- epoch 0: request half out, then epoch runs and ends WITH LOSS ---
    vm.prank(attacker);
    uint256 basisN = cdo.requestWithdraw(
        IERC20(AAtranche).balanceOf(attacker) / 2, address(AAtranche));
    // honest manager: startEpoch, warp past end, stop with loss
    startEpoch();
    vm.warp(cdo.epochEndDate() + 1);
    uint256 loss = basisN / 4;                // e.g. 25% of pending basis lost
    vm.prank(manager);
    cdo.stopEpochWithDuration(newApr, 0, duration, loss);
    // => strategy.collectWithdrawFunds funded only basisN - pendingLoss,
    //    lossRecoveryPriceByEpoch[0] < 1e18

    // --- epoch 1: attacker requests again -> lastWithdrawRequest overwritten ---
    vm.prank(attacker);
    uint256 basisM = cdo.requestWithdraw(0, address(AAtranche)); // rest of tranche bal
    startEpoch();                            // epoch 1
    vm.warp(cdo.epochEndDate() + 1);
    vm.prank(manager);
    cdo.stopEpoch(newApr, expectedInterest); // no loss this epoch

    // --- claim: epoch-0 basis escapes haircut ---
    uint256 balPre = IERC20(underlying).balanceOf(attacker);
    vm.prank(attacker);
    cdo.claimWithdrawRequest();
    uint256 got = IERC20(underlying).balanceOf(attacker) - balPre;

    uint256 priceN = vault.lossRecoveryPriceByEpoch(0);
    uint256 expected = basisN * priceN / 1e18 + basisM;
    // BUG: attacker received basisN + basisM (par), not the haircutted amount
    assertGt(got, expected);
}
```

Note: I verified the claim-path logic and epoch keying in `IdleCreditVault.sol` (`collectWithdrawFunds` line 421, `_claimLossAdjustedWithdrawRequest` lines 789–801, `_claimFundedWithdrawRequest` lines 319–350, `_clearWithdrawClaimForEpoch` lines 811–837). I did not fully trace `IdleCDOEpochVariant.claimWithdrawRequest` / `requestWithdraw` gating edge cases (e.g., whether `whenNotPaused`/flags ever block a second request while a loss receipt is pending); the code comments and tests (`requestWithdraw` called repeatedly across epochs) indicate re-requesting is supported. If a guard elsewhere prevents re-request before claiming, the attack alternates between two attacker wallets is not needed — but I found no such guard in the strategy-level accounting.
