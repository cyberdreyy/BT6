### Title
Reorg-timing permission derived from local, miner-controllable timestamps lets a single miner reorg away its own already-globally-accepted block - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a new sortition's block is allowed to build off something other than the immediately prior sortition (i.e., allowed to reorg away the prior tenure). The "is this OK" test is a locally-computed elapsed time — `sortition_state_received_time - approved_at` — compared against a fixed `first_proposal_burn_block_timing`. Both endpoints of that elapsed-time computation are timestamps that a miner substantially controls (when it broadcasts its block, thus when the signer's `approved_time`/`proposed_time` gets set), analogous to the TWAP bug where the "duration" fed into a freshness check was itself attacker-influenced rather than a fixed, objective window. [1](#0-0) 

### Finding Description
`check_parent_tenure_choice` only forgives a reorg of a tenure that produced at most one globally-accepted block, and only if that block's local timing was "too close" to the next sortition: [2](#0-1) [1](#0-0) 

The timing signal is `proposal_to_sortition = sortition_state_received_time.saturating_sub(approved_at)`, where:
- `approved_at` is `local_block_info.approved_time`, stamped locally when *this* signer pre-committed/accepted the reorged tenure's first block.
- `sortition_state_received_time` is `signer_db.get_burn_block_receive_time(&self.burn_block_hash)`, i.e. when the local signer's node reported the *next* sortition's burn block. [3](#0-2) 

Both numbers are downstream of when the miner chose to broadcast its proposal: a miner who deliberately withholds broadcasting its (otherwise fully-signed and globally-accepted) block until just before the next Bitcoin block arrives compresses `proposal_to_sortition` toward zero, satisfying `< first_proposal_burn_block_timing` regardless of the configured window size. This mirrors the reported TWAP flaw precisely: the "freshness window" is not a fixed, externally-anchored duration but the delta between two locally observed, attacker-timeable events, so an attacker who "controls two consecutive blocks" (its own tenure's block-broadcast timing and the block that follows at the next sortition) can force the window to whatever value it needs.

The test harness `reorg_timing_testing` demonstrates the mechanics precisely: it constructs the "sortition time" as `block_info_1.proposed_time + sortition_timing_secs` and shows that varying this single delta (30 vs 31, 30 vs 29) flips the reorg decision from refused to permitted: [4](#0-3) [5](#0-4) 

When the reorg is judged "permitted," the previously-reorged tenure is marked **superseded**, which specifically voids this signer's own earlier signature over that tenure's block as a future conflict: [6](#0-5) 

so the signer becomes willing to sign a new, conflicting block at the same height/tenure slot that the network (and possibly the node itself, since the block was globally accepted) had already treated as canonical.

### Impact Explanation
If a miner can arrange for its own broadcast timing to make `proposal_to_sortition` small (by delaying propagation of an already-signed, globally-accepted block until immediately before it wins/controls the next sortition), the signer will treat its own previously-canonical tenure as "poorly timed" and permit a follow-on block to reorg it away, superseding the earlier signature. This is a **Critical**-class break: a signer ends up willing to sign a conflicting/non-canonical block over one it had already globally accepted, i.e., the "approved-parent vs canonical" equality is broken by an attacker who does not need a majority of signers — only control over its own block-broadcast timing across the tenure and the following sortition win.

### Likelihood Explanation
This requires the miner to win (or otherwise be the proposer for) two temporally adjacent sortitions/tenures and to control precisely when it broadcasts its proposal relative to bitcoin block arrival — the same "control two consecutive blocks" precondition called out as feasible in the source report (post-merge, and in Stacks, a miner can also simply delay its own broadcast, which is entirely under its control, rather than needing to "control" the Bitcoin block itself). The mechanism is directly exercised by existing unit tests (`check_parent_tenure_choice_reorg_timing_ok`/`_bad`) and integration tests (`allow_reorg_within_first_proposal_burn_block_timing_secs`), confirming the code path is reachable in practice and that its "OK/refused" outcome hinges entirely on this locally-derived delta.

### Recommendation
Anchor the "was this proposal too close to the sortition transition" decision to a value the miner cannot skew by delaying its own broadcast — e.g., use the reorged tenure's own **burn_header_timestamp**/consensus-visible chain data (the point at which the *prior* sortition itself occurred) rather than this signer's locally observed `approved_time`, or require agreement across multiple signers' independently observed `approved_time`s (similar to how `get_burn_block_received_time_from_signers` aggregates weighted timestamps) before treating a globally-accepted tenure as reorg-eligible. At minimum, never allow superseding a tenure whose block has already reached `GloballyAccepted` state purely on the basis of one signer's locally-timed delta.

### Proof of Concept
1. Miner wins sortition A, builds block A1, gets it signed/globally accepted, but withholds broadcasting/finalizing propagation until just before it also wins/controls the next Bitcoin block (sortition B).
2. Signer's local `approved_time` for A1 ends up very close to `sortition_state_received_time` for B, because the miner timed the broadcast that way, not because the network was genuinely racing.
3. Miner then submits a block for sortition B whose commit skips tenure A (`parent_tenure_id != prior_sortition`), triggering `check_parent_tenure_choice`.
4. `proposal_to_sortition = sortition_state_received_time - approved_at` computes small, `< first_proposal_burn_block_timing`, so `check_parent_tenure_choice` returns `Ok(true)` and calls `record_superseded_tenure`, as reproduced by `reorg_timing_testing(name, 30, 29)` in `stacks-signer/src/chainstate/tests/v2.rs:373`.
5. The signer's earlier signature over A1 no longer blocks conflicts, and the signer proceeds to sign a new block for tenure B that reorgs away the previously globally-accepted A1 — a conflicting block being signed over one already treated as canonical.

fn reorg_timing_testing(
    test_name: &str,
    first_proposal_burn_block_timing_secs: u64,
    sortition_timing_secs: u64,
) -> (Result<bool, SignerChainstateError>, bool) {
    let (
        _stacks_client,
        mut signer_db,
        block_sk,
        mut block,
        mut cur_sortition,
        last_sortition,
        mut sortitions_view,
    ) = setup_test_environment(test_name);
    sortitions_view.config.first_proposal_burn_block_timing =
        Duration::from_secs(first_proposal_burn_block_timing_secs);
    cur_sortition.data.parent_tenure_id = last_sortition.data.parent_tenure_id.clone();
    block.header.consensus_hash = cur_sortition.data.consensus_hash.clone();
    let block_pk = StacksPublicKey::from_private(&block_sk);
    cur_sortition.data.miner_pkh = Hash160::from_node_public_key(&block_pk);
    cur_sortition.data.miner_pubkey = Some(block_pk);

    let block_proposal_1 = BlockProposal {
        block: NakamotoBlock::new(
            NakamotoBlockHeader {
                version: 1,
                chain_length: 10,
                burn_spent: 10,
                consensus_hash: last_sortition.data.consensus_hash.clone(),
                parent_block_id: StacksBlockId([0; 32]),
                tx_merkle_root: Sha512Trunc256Sum([0; 32]),
                state_index_root: TrieHash([0; 32]),
                timestamp: 11,
                miner_signature: MessageSignature::empty(),
                signer_signature: vec![],
                pox_treatment: BitVec::ones(1).unwrap(),
                problematic_txs: vec![],
            },
            vec![],
        ),
        burn_height: 2,
        reward_cycle: 1,
        block_proposal_data: BlockProposalData::empty(),
    };
    let mut block_info_1 = BlockInfo::from(block_proposal_1);
    block_info_1.mark_locally_accepted(false).unwrap();
    signer_db.insert_block(&block_info_1).unwrap();

    let sortition_time = SystemTime::UNIX_EPOCH
        + Duration::from_secs(block_info_1.proposed_time + sortition_timing_secs);
    signer_db
        .insert_burn_block(
            &cur_sortition.data.burn_block_hash,
            &cur_sortition.data.consensus_hash,
            3,
            &sortition_time,
            &last_sortition.data.burn_block_hash,
        )
        .unwrap();
