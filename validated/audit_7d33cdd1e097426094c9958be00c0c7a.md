## Analysis

The dst-escrow fee mechanism is a genuine bug. `createDstEscrow` accepts a caller-supplied `Immutables` struct — including the `parameters` field that packs `protocolFeeAmount`, `integratorFeeAmount`, `protocolFeeRecipient`, and `integratorFeeRecipient` — with **no cross-check** against the commitment made in the source-chain `SrcEscrowCreated` event's `immutablesComplement`. [1](#0-0) 

Because the caller of `createDstEscrow` fully controls `dstImmutables.parameters`, an unprivileged taker can set `integratorFeeRecipientCd`/`protocolFeeRecipientCd` to a contract that unconditionally reverts on token receipt, with a non-zero fee amount. `_withdraw` unconditionally attempts these fee transfers before the maker's payout, and `_uniTransfer` reverts on any failure (`safeTransfer` reverting for ERC20, or `revert NativeTokenSendingFailure()` for native): [2](#0-1) [3](#0-2) 

Since both `withdraw` (taker-only) and `publicWithdraw` (any access-token holder) call the same `_withdraw` internal function, every attempt — private or public — reverts identically for the entire withdrawal window. `cancel()` remains blocked by `onlyAfter(DstCancellation)`, and even after that stage, `cancel()` and `rescueFunds()` are restricted to `onlyCaller(immutables.taker.get())` — meaning only the taker (the attacker) can ever recover the funds; the maker has no path to force resolution. [4](#0-3) [5](#0-4) 

Note that because the escrowed capital on the destination side was deposited by the taker themselves, the taker can always reclaim it via `cancel()`/`rescueFunds()` once the relevant timelock passes — so the impact is a **temporary freeze of the maker's expected destination-chain payout for the entire withdrawal window** (private + public), not a genuine permanent loss of third-party funds, since the taker's own capital just returns to the taker. This matches the "temporary freezing of funds during the live swap lifecycle" bucket rather than the "permanent freeze / insolvency" (Critical) bucket claimed in the question.

### Title
Unvalidated fee-recipient/amount parameters in `createDstEscrow` allow a taker to permanently revert `withdraw`/`publicWithdraw`, freezing the maker's destination payout for the entire withdrawal window - (File: contracts/BaseEscrowFactory.sol, contracts/EscrowDst.sol)

### Summary
`createDstEscrow` deploys a destination escrow using an `Immutables` struct supplied entirely by the calling taker, without validating the `parameters` field (protocol/integrator fee recipients and amounts) against what was committed on the source chain during `_postInteraction`. A malicious taker can set a fee recipient to a contract that always reverts on token receipt with a non-zero fee amount, causing `_withdraw` (invoked by both `withdraw` and `publicWithdraw`) to always revert.

### Finding Description
`EscrowDst._withdraw` unconditionally attempts `_uniTransfer` to `integratorFeeRecipientCd()`/`protocolFeeRecipientCd()` before transferring the remaining `amount` to the maker. `_uniTransfer` propagates any revert from the recipient (ERC20 `safeTransfer` revert or a failed native `call`). Because `createDstEscrow` never validates that these recipients/amounts match a trusted, protocol-committed value, an attacking taker can pick a reverting contract as recipient at escrow-creation time. Every subsequent `withdraw`/`publicWithdraw` call — regardless of caller — replays the same fee transfer and reverts, blocking the maker (and any public-withdraw actor) from completing the swap until `DstCancellation`. [6](#0-5) [7](#0-6) 

### Impact Explanation
This is a High-severity "temporary freezing of funds during the live swap lifecycle" issue: the maker cannot receive their destination-side funds for the full private+public withdrawal window. It does not rise to Critical/permanent freeze or insolvency because the escrowed capital belongs to the attacking taker, who can always reclaim it via `cancel()`/`rescueFunds()` (both restricted to the taker) once the relevant timelocks elapse.

### Likelihood Explanation
High likelihood: any unprivileged taker calling `createDstEscrow` (a normal, permissionless entrypoint) fully controls the `parameters` bytes with no protocol-side validation, requiring no special privileges, timing, or governance access.

### Recommendation
Validate `dstImmutables.parameters` in `createDstEscrow` against a protocol-trusted source (e.g., re-derive/verify fee recipients and amounts from the corresponding `SrcEscrowCreated`/`immutablesComplement` commitment, or require the factory to construct/attest this data rather than accept it verbatim from the caller). Additionally, consider making fee transfers best-effort (e.g., via try/catch or a pull-payment pattern) so a reverting fee recipient cannot block the maker's principal payout.

### Proof of Concept
1. Attacker (taker) deploys a mock ERC20/native recipient contract that reverts on any incoming transfer.
2. Attacker calls `createDstEscrow` with `dstImmutables.parameters` encoding `integratorFeeAmount > 0` and `integratorFeeRecipient` = the reverting contract, funding the escrow as required.
3. When `DstWithdrawal` stage begins, attacker (or anyone with the access token) calls `withdraw`/`publicWithdraw` with the valid secret; `_withdraw` reverts at the `_uniTransfer` call to the integrator fee recipient, before the maker's `amount` transfer runs.
4. Every subsequent call before `DstCancellation` reverts identically since the same fee recipient is re-used; `cancel()` is unavailable until `DstCancellation`, and even then only the taker (attacker) can call it, so the maker never receives destination-chain funds for the swap.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
