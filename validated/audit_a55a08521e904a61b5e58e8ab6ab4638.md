### Title
Missing duplicate-MessageId check in `HandleLegacyUserMessage` allows cross-user callback hijack via savedCallbacks map overwrite - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` unconditionally overwrites `h.savedCallbacks[msg.Body.MessageId]` without first checking whether an entry for that `MessageId` already exists. Any unprivileged sender who submits a legacy gateway request reusing an in-flight `MessageId` can silently replace another user's callback binding, causing the eventual node response to be delivered to the wrong caller.

### Finding Description
In `HandleLegacyUserMessage`, after payload/timestamp/method validation and signature verification of the *attacker's own* message, the handler stores the callback keyed purely by the caller-supplied `msg.Body.MessageId`: [1](#0-0) 
There is no `if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists { ... }` guard before the write, unlike the equivalent code paths in sibling handlers. The `confidentialrelay` handler's `newActiveRequest` explicitly rejects duplicate request IDs (`"request ID already exists"`), and the `vault` handler explicitly returns `"request was already authorized previously"` on collision, as shown by their tests: [2](#0-1) [3](#0-2) 
No such invariant exists in `capabilities/handler.go`.

`MessageId` is fully attacker-controlled plaintext in the message body — it is not derived from the sender's identity, and each caller signs their own message including their own chosen `MessageId`: [4](#0-3) 
`msg.Validate()` only checks length/format constraints on `MessageId`, not uniqueness or binding to sender: [5](#0-4) 
The gateway's `ProcessRequest` routes any legacy request straight into `HandleLegacyUserMessage` after only format validation, with no dedup check at that layer either: [6](#0-5) 

When a node eventually responds, `handleWebAPITriggerMessage` looks up and deletes by `MessageId` and delivers the response to whatever callback is currently stored: [7](#0-6) 
If an attacker submits a second request with the same `MessageId` while a victim's request is still outstanding, the map entry is overwritten with the attacker's callback. Whichever DON response (victim's or attacker's) is received first by the gateway will be delivered through the (now attacker-controlled or victim-controlled) stored callback — a cross-user response confusion/hijack, or a denial-of-service against the victim's original request (which will never receive its response and eventually time out).

### Impact Explanation
This is a cross-user response confusion / request hijacking bug: an unprivileged gateway client can hijack or deny another user's outstanding `web_api_trigger` request by resending a colliding `MessageId`, causing either (a) the victim to receive no response (DoS on their request), or (b) the attacker to receive the victim's response payload (potential data exposure depending on what the trigger response contains), or (c) the victim's callback to be fed with data originating from the attacker's own crafted request. This matches the "cross-user response confusion" / unauthorized action-on-another-user's-request bounty class.

### Likelihood Explanation
Exploitability requires only knowledge of a live, in-flight `MessageId` for a legacy `web_api_trigger` request — no credentials beyond the ability to submit signed gateway requests (any unprivileged sender can self-sign their own message). `MessageId` values are chosen by the calling script/client (e.g., generated in `core/scripts/gateway/web_api_trigger/invoke_trigger.go`) and are not required to be unpredictable, random, or bound to the sender, so if an attacker can observe or guess a concurrent `MessageId` (e.g., via shared/predictable ID schemes, or by racing with a known target endpoint), the attack window during the request's outstanding lifetime (up to `CallbackMaxAgeSec`, default 120s) makes this practically repeatable.

### Recommendation
In `HandleLegacyUserMessage`, before inserting into `h.savedCallbacks`, check for an existing entry under the lock and reject the request (returning a `ConflictError`/`HandlerError` response to the caller) instead of overwriting it — mirroring the duplicate-ID handling already implemented in `confidentialrelay.newActiveRequest` and the `vault` handler.

### Proof of Concept
Add a table test to `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build two distinct valid, signed `api.Message`s (from two different keys/nodes list membership) with `Method = MethodWebAPITrigger` and the **same** `MessageId`.
2. Call `handler.HandleLegacyUserMessage(ctx, msg1, cb1)`, assert `savedCallbacks[MessageId]` is bound to `cb1`.
3. While `cb1`'s request is still outstanding (do not deliver a node response yet), call `handler.HandleLegacyUserMessage(ctx, msg2, cb2)` with the same `MessageId`.
4. Expected (fixed) behavior: the second call returns an error/`ConflictError` and `savedCallbacks[MessageId]` still references `cb1`.
5. Current (vulnerable) behavior: no error is returned, and `savedCallbacks[MessageId]` is silently overwritten with `cb2`; simulate a node response via `handler.HandleNodeMessage` and confirm it is delivered to `cb2` instead of `cb1`, demonstrating the hijack.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.

	}
	return nil
