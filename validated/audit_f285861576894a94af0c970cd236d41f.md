This confirms the described flow is real and exploitable in `ziplegacy`, in contrast to the `fastzip` extractor which correctly passes `e.dir` into `fastzip.NewExtractorFromReader(e.r, e.size, e.dir, opts...)` to confine extraction. The `ziplegacy.extractor.Extract` completely discards `e.dir` and calls `archives.ExtractZipArchive(zr)`, which operates on `file.Name` verbatim for `os.MkdirAll`, file creation, `os.Symlink`, `lchmod`, and `os.Lchown` — with no path sanitization, no check against absolute paths, and no `..` traversal guard anywhere in `helpers/archives/zip_extract.go` or `zip_extra_unix.go`.

### Title
Zip extraction ignores confinement directory and allows absolute/`../` path traversal to write and chown arbitrary host files - (File: commands/helpers/archive/ziplegacy/zip_legacy_extractor.go, helpers/archives/zip_extract.go, helpers/archives/zip_extra_unix.go)

### Summary
The legacy zip extractor (`ziplegacy.extractor.Extract`) is constructed with a `dir` field intended to confine extraction, but never uses it — it calls `archives.ExtractZipArchive(zr)` directly. `extractZipFile` and `processZipUIDGidField` then use `file.Name` from the zip archive verbatim in `os.MkdirAll`, file writes, `os.Symlink`, `lchmod`, and `os.Lchown`, with no validation that the path is relative or confined to any directory.

### Finding Description
`ziplegacy.NewExtractor` stores `dir` in the `extractor` struct [1](#0-0) , but `Extract` never joins `dir` with any extracted file path — it simply calls `archives.ExtractZipArchive(zr)` [2](#0-1) .

Inside `ExtractZipArchive`, each `zip.File.Name` is passed straight to `extractZipFile`, `lchmod`, and `processZipExtra` with no path sanitization [3](#0-2) . `extractZipFile` calls `os.MkdirAll(filepath.Dir(file.Name), 0o777)` and then creates the file/symlink/directory using `file.Name` verbatim [4](#0-3) . On Unix, `processZipUIDGidField` performs `os.Lchown(file.Name, uid, gid)` again using the raw name, with UID/GID also taken from attacker-supplied zip extra-field data [5](#0-4) .

There is no check anywhere in this path for absolute paths, `..` segments, or symlink-based escapes (`errorIfGitDirectory` only checks for `.git` directory names, not traversal) [6](#0-5) . By contrast, the `fastzip` extractor correctly forwards `e.dir` into the underlying library, which performs path confinement [7](#0-6) , confirming that `dir`-scoping is the intended invariant that the legacy zip path violates.

An unprivileged job that controls cache/artifact zip contents (e.g., via a custom-built cache archive, or any code path that lets it supply a zip processed by `ziplegacy`) can create a zip entry named `../../../etc/cron.d/x` or an absolute path, causing `extractZipFile` to write outside the intended cache/artifact directory and `Lchown` to change ownership of the resulting file to attacker-chosen UID/GID (bounded by the runner process's privileges).

### Impact Explanation
This allows a job to write attacker-controlled file contents and set arbitrary ownership on files outside the confined extraction directory, on hosts/executors where the runner (or its helper process) has sufficient privileges. Depending on where `ziplegacy` is used (cache/artifact extraction) and the privilege level of the process performing extraction, this can lead to writing files into arbitrary locations on the executor host filesystem and manipulating ownership, which is a workspace/cache escape and matches the scoped impact of "host filesystem write + ownership change outside the workspace/cache directory."

### Likelihood Explanation
Feasible and fully attacker-controlled: any job that can influence the contents of a zip artifact/cache file processed via the `ziplegacy` extractor (a normal `.zip` archive it builds itself before upload, or crafts directly) can set `zip.File.Name` to arbitrary strings including `../` sequences or absolute paths, since the zip format does not restrict file names. No authentication, image, or shell-executor trust boundary blocks this — it is a pure parsing/path-validation gap in the extraction code itself.

### Recommendation
- In `ziplegacy.extractor.Extract` (and centrally in `archives.ExtractZipArchive`), join every `file.Name` with the configured `dir`, and validate with `filepath.Clean`/`filepath.Rel` (or equivalent) that the resulting path stays within `dir`, rejecting archives with absolute paths or resolved paths escaping the root — mirroring the confinement that `fastzip` already provides.
- Apply the same fix to `lchmod`/`processZipExtra` (i.e., `processZipUIDGidField`'s `os.Lchown`) so ownership changes are also confined to validated, resolved paths under `dir`.

### Proof of Concept

func processZipUIDGidField(data []byte, file *zip.FileHeader) error {
	var ugField ZipUIDGidField
	err := binary.Read(bytes.NewReader(data), binary.LittleEndian, &ugField)
	if err != nil {
		return err
	}

	if !(ugField.Version == 1 && ugField.UIDSize == 4 && ugField.GIDSize == 4) {
		return errors.New("uid/gid data not supported")
	}

	return os.Lchown(file.Name, int(ugField.UID), int(ugField.Gid))
}
