### Title
Rate limiter keys solely on client IP with no per-account throttling, enabling distributed credential-stuffing/token-guessing - ([File: core/web/router.go])

### Summary
The `rateLimiter` function in `core/web/router.go` builds an `mgin.NewMiddleware` on top of `github.com/ulule/limiter/v3`, which by default derives the rate-limit key from the client's remote IP address (via `c.ClientIP()`), not from any account/email/token identity. Since `AuthenticateBySession` and `AuthenticateByToken` in `core/web/auth/auth.go` contain no per-account failed-attempt tracking or lockout, an attacker who controls many source IPs can distribute password/token guesses against a single target admin account, with each IP independently staying under its own quota.

### Finding Description
`NewRouter` applies the rate limiter to the entire authenticated API group: [1](#0-0) 

The limiter itself is constructed with the default `mgin` middleware and no custom key function: [2](#0-1) 

`mgin.NewMiddleware(limiter.New(store, rate))` uses `ulule/limiter`'s default `GetIPKey` behavior, keying strictly on `c.ClientIP()`. There is no wrapping key function that mixes in the request path, submitted email, access-key header, or any per-account identifier.

On the authentication side, `AuthenticateBySession` and `AuthenticateByToken` simply attempt to validate the session/token and return `auth.ErrorAuthFailed` on mismatch — there is no counter, cache, or database column tracking failed attempts per user/email that could independently throttle or lock an account regardless of source IP: [3](#0-2) 

A search of the repository for lockout/failed-login-attempt tracking (`FailedLogin`, `lockout`, etc.) in the `core/web` and `core/sessions` areas found no such mechanism tied to authentication failures. The only defense is the IP-scoped `rateLimiter` middleware applied before `sessionRoutes`/`v2Routes` in `NewRouter`.

Because the key is `ClientIP` only, an attacker with access to N distinct source IPs (e.g., via proxy/VPN/botnet rotation) can send up to `rl.Authenticated()` requests per `rl.AuthenticatedPeriod()` from each IP, all targeting the same victim account's `/sessions` login or the same crafted `X-API-KEY`/`X-API-SECRET` pair against a `/v2/*` route, multiplying the effective global throughput against that one account by N with no additional check ever engaging.

### Impact Explanation
This maps to Chainlink's "authentication soundness" impact class — the security control intended to make brute force infeasible (rate limiting) provides no protection when attackers control multiple source IPs, because the limiter enforces per-IP, not per-account, quotas. Successful brute force of a session password or API token secret would grant full node UI/API access at whatever role the compromised account holds (potentially admin), including job management, key export flows gated behind role checks, and other sensitive `/v2/*` endpoints. This is a real, scoped vulnerability in the rate-limiting design rather than a network-layer or infrastructure concern, since it lies entirely within `core/web/router.go`'s `rateLimiter` construction and `core/web/auth/auth.go`'s authentication functions.

### Likelihood Explanation
Preconditions: the attacker needs no credentials or node access — only network reachability to the node's HTTP API and access to multiple source IPs (commonly available via cloud providers, proxy pools, or botnets), which is a very low bar for a determined attacker. The attack is straightforward to script: rotate source IP, send login/token attempt, repeat. It is fully repeatable and requires no timing tricks beyond respecting each IP's own quota window. The strength of an admin password/token is the only remaining defense, which is not itself audited here but is not treated as an independent rate-limiting layer.

### Recommendation
Incorporate an identity-aware component into the rate-limit key (e.g., combine IP with submitted email for `/sessions`, or with the `X-API-KEY` access key for token-based routes), and additionally implement per-account/per-credential lockout or exponential backoff tracked server-side (e.g., in the database or a shared cache) that is independent of source IP. Apply a stricter, dedicated limiter specifically to `/sessions` (login) keyed by the submitted email, on top of the existing IP-based limiter.

### Proof of Concept
Go handler-level integration test plan:
1. Build a `gin.Engine` using `rateLimiter(period, limit)` from `core/web/router.go` mounted in front of a stub `/sessions` handler that always returns 401 with a fixed error (simulating a failed login for target account `admin@example.com`).
2. Configure `limit = 3`, `period = 1s` (mirroring `WebServer.RateLimit.Authenticated`).
3. Simulate 10 distinct "client IPs" by setting `X-Forwarded-For`/`RemoteAddr` per request (with `engine.RemoteIPHeaders` configured to trust the test header, or by directly manipulating `http.Request.RemoteAddr`), each sending 3 login attempts for the same target account within the period.
4. Assert that all 30 requests (10 IPs × 3 attempts) are accepted by the rate limiter (no 429 status) — proving the limiter never engages a per-account quota, only exhausting after each individual IP's own 3rd request.
5. Contrast with a modified limiter keyed on `email + ip` or `email` alone (hypothetical fix) and assert that after cumulative 3 attempts across all IPs for the same account, the 4th request returns 429 — demonstrating the fix closes the gap.

```go
func rateLimiter(period time.Duration, limit int64) gin.HandlerFunc {
	store := memory.NewStore()
	rate := limiter.Rate{
		Period: period,
		Limit:  limit,
	}
	return mgin.NewMiddleware(limiter.New(store, rate))
}
```

```go
func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}

var _ authMethod = AuthenticateBySession

// AuthenticateByToken authenticates a User by their API token.

// Implements authMethod
func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
```
