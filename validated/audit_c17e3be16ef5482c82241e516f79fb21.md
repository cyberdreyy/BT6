## Analysis

The Astaria bug is fundamentally about a **stale authorization remaining valid after the authorizer's revocation mechanism is bypassed** — a nonce that should invalidate old signed approvals is never enforced, so an old commitment keeps being honored. The closest analog in this NEAR repo is in the multisig contracts (`multisig` and `multisig2`), where **confirmations recorded by a member are never purged when that member is removed from the multisig**, other than for requests the removed member itself created.

### Root cause

In `multisig2/src/lib.rs`, `delete_member` only cleans up requests whose **creator** (`r.member`) equals the member being removed: [1](#0-0) 

It never scans the `confirmations` map to strip the removed member's vote from requests **created by someone else that this member merely confirmed**. The same bug exists in the v1 contract's `DeleteKey` handling: [2](#0-1) 

Later, `confirm()` counts confirmations purely by set size, with no re-validation that every entry in the set is still a current member: [3](#0-2) [4](#0-3) 

`assert_valid_request` only checks that the *caller* is currently a member and that the request/confirmation entries exist — it does not re-check the validity of prior confirmers already stored in the set: [5](#0-4) 

### Broken invariant

`num_confirmations` is supposed to mean "at least N **currently valid** members approved this action." Instead the code enforces "at least N approvals were ever recorded, even from members who have since been removed." A stale, revoked member's confirmation still counts toward the threshold on any request created before their removal.

### Title
Stale member confirmations are not purged on removal, allowing multisig requests to execute below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`delete_member` (multisig2) and the `DeleteKey` action (multisig v1) only remove pending requests *created* by the member/key being removed. They do not strip that member's existing confirmations from other pending requests they had merely co-signed. `confirm()` then counts these stale confirmations toward `num_confirmations`, so a request can execute even though fewer than `num_confirmations` *currently valid* members actually approved it.

### Finding Description
Consider `num_confirmations = N` with members that include member `M`.
1. `M` confirms an existing pending request `R` (created by another member), adding `M` to `confirmations[R]`.
2. The multisig later executes a separate, legitimate `DeleteMember { member: M }` (or `DeleteKey` in v1) request, removing `M` from `self.members` and revoking its access key. This path only removes requests whose `request.member == M` (i.e., requests `M` created) — see `delete_member`, `multisig2/src/lib.rs:361-371`, and the equivalent `DeleteKey` block in `multisig/src/lib.rs:198-216`. `R`'s confirmation set still contains `M`.
3. Remaining current members continue to confirm `R`. Once `confirmations[R].len() + 1 >= num_confirmations`, `confirm()` executes the request — but the stale entry for the now-removed `M` is counted in that tally.
4. The request therefore executes with strictly fewer than `num_confirmations` *live* members' consent, e.g. `N-1` live confirmers plus one stale/revoked one.

This breaks the equality the multisig is supposed to guarantee: `count(confirmations that come from live members) == count(confirmations) >= num_confirmations`. After the exploit, `count(live confirmations) < num_confirmations` while the request still executes.

### Impact Explanation
This is a threshold-bypass on an account/multisig that can hold and transfer NEAR, add/delete keys or members, or make arbitrary `FunctionCall`s (see `MultiSigRequestAction::Transfer`/`FunctionCall` in `execute_request`, `multisig2/src/lib.rs:224-290`). A request (e.g., a `Transfer` moving the multisig's NEAR balance, or an `AddKey`/`AddMember` granting new control) can be pushed through with fewer live-member approvals than the configured `num_confirmations`, i.e., "a multisig request executed below threshold" — explicitly a Critical-impact scenario for this program.

### Likelihood Explanation
No privileged access is required beyond being (or having been) a legitimate multisig member at the time of confirming — a completely ordinary, unprivileged multisig workflow. The only precondition is that a member confirms a request before being removed, and the request remains pending afterward, which is a realistic and easily engineered sequence (member confirms, then is later removed for unrelated reasons such as key rotation, compromise response, or offboarding, while other pending requests linger).

### Recommendation
When removing a member/key (`delete_member` in `multisig2/src/lib.rs`, `DeleteKey` in `multisig/src/lib.rs`), iterate over **all** `confirmations` entries (not just `requests` whose creator matches) and remove the departing member/key from every confirmation set. Alternatively, revalidate every entry in `confirmations[request_id]` against `self.members` (or the access-key set) at `confirm()`/execution time, discounting confirmations from accounts/keys no longer part of the multisig before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 3` and members `A, B, C, D`.
2. `A` calls `add_request` to create request `R` (e.g., `Transfer` of the account's NEAR to an attacker-controlled account).
3. `B` calls `confirm(R)` → `confirmations[R] = {B}`.
4. Separately, `A, C, D` push through and execute a `DeleteMember { member: B }` request (this only clears requests where `r.member == B`; `R` was created by `A`, so it is untouched) — `multisig2/src/lib.rs:361-371`. `B` is now removed from `self.members` and its access key revoked.
5. `C` calls `confirm(R)` → `confirmations[R] = {B, C}` (len 2).
6. `D` calls `confirm(R)` → `len(confirmations) + 1 = 3 >= num_confirmations(3)` → `execute_request(R)` fires the `Transfer`, even though only `C` and `D` (2 live members) plus a stale, already-revoked `B` approved it — one fewer live approval than the configured threshold requires.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();

            "Already confirmed this request with this key",
        );

            let request = self.remove_request(request_id);

            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
