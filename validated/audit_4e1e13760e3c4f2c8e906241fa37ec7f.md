### Title
Claimed instant-withdraw receipts stay in `instantWithdrawClaimsByEpoch`, inflating the default-recovery basis and reserve so tail claimants are frozen out — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` accumulates each user's receipt into `instantWithdrawClaimsByEpoch[epochNumber]`, but the normal claim path `claimInstantWithdrawRequest` never decrements that per-epoch counter. Only the post-default path `_claimDefaultedInstantWithdrawRequest` subtracts. If instant receipts are claimed during an epoch and the borrower later defaults in that same epoch, `finalizeDefaultRecovery` reads a stale basis: `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` both count already-paid claims, overstating `totalBasis` (diluting `defaultRecoveryPrice` for everyone) and overstating `defaultRecoveryReserve` by the claimed amount. The last recovery claimants then revert in `safeTransfer` — a permanent freeze of their share of the recovery reserve.

### Finding Description
- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (`IdleCreditVault.sol:371-372`). [1](#0-0) 
- `claimInstantWithdrawRequest` burns the receipt and pays out, but only zeroes `instantWithdrawsRequests[_user]`; it does not touch `instantWithdrawClaimsByEpoch` or `instantWithdrawsRequestsByEpoch` (`IdleCreditVault.sol:387-392`). [2](#0-1) 
- At default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying already held (`IdleCreditVault.sol:644-649, 716-723`). Both quantities are computed from the stale counter. [3](#0-2) [4](#0-3) 
- `finalizeDefaultRecovery` then sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `defaultRecoveryPrice = reserveAmount / totalBasis`, where both terms are inflated by the already-claimed amount `C` (`IdleCreditVault.sol:685-692`). [5](#0-4) 
- `epochNumber` is only bumped inside `deposit()` during a running-epoch (stopEpoch) deposit (`IdleCreditVault.sol:607-614`), so a mid-epoch default keeps the same `epochNumber` as the epoch in which the stale instant receipts were recorded — the lookup `instantWithdrawClaimsByEpoch[epochNumber]` hits the polluted key. [6](#0-5) 

This is the analog of the CVE's off-by-one: a boundary counter that should have been shrunk by one "unit" (each claim) is left oversized, so a later computation reads past the real boundary and corrupts a shared accounting buffer (the recovery reserve/price).

### Impact Explanation
Let `C` be the total instant-withdraw amount claimed before finalization in the defaulted epoch. Then:

- `totalBasis` is overstated by `C`, so `defaultRecoveryPrice` is lower than the true funded ratio — every legitimate claimant (active LPs, pending normal receipts, unfunded instant receipts) is haircut more than warranted.
- `defaultRecoveryReserve` is overstated by `C` tokens that were already transferred out. `_transferDefaultRecovery` decrements the reserve and calls `underlyingToken.safeTransfer(_user, _amount)` (`IdleCreditVault.sol:912-917`); once the real balance is exhausted, the remaining claims totaling up to `C` revert permanently — there is no other funding source and no way to correct the reserve post-finalization (`defaultRecoveryFinalized` is one-way). [7](#0-6) 

Net effect: up to `C` of recovery value is frozen forever (last claimants cannot claim), and all claimants absorb a diluted recovery price. An unprivileged attacker can also shape `C`: any lender eligible for instant withdrawals (APR-drop path) can request, get funded at epoch start, claim, then the borrower defaults mid-epoch — the attacker already extracted full value while honest claimants' receipts are bricked.

### Likelihood Explanation
Requires: (a) an epoch in which instant-withdraw receipts are created, funded via `collectInstantWithdrawFunds`, and claimed while `epochNumber` is unchanged; (b) at least one still-unfunded instant receipt (`pendingInstantWithdraws != 0`) or any normal pending basis coexisting so the polluted branch executes; (c) a borrower default and `finalizeDefault` in the same epoch number. All roles in the sequence (manager startEpoch/stopEpoch, borrower default, owner finalize) are honest per the threat model; the triggering claim is a normal user action. Medium likelihood — it needs a default coinciding with same-epoch claimed instant receipts, but instant withdrawals are specifically enabled during buffer periods and defaults are a designed-for scenario in this code.

### Recommendation
Decrement per-epoch counters on the funded claim path, mirroring the default path:

```solidity
// in claimInstantWithdrawRequest, after reading `amount`
uint256 requestEpoch = lastInstantWithdrawEpoch[_user]; // or track per-user epoch
instantWithdrawsRequestsByEpoch[_user][requestEpoch] -= amount;
instantWithdrawClaimsByEpoch[requestEpoch] -= amount;
```

Since `instantWithdrawsRequestsByEpoch` is keyed by request epoch, either store the user's request epoch (a `lastInstantWithdrawRequest` marker analogous to `lastWithdrawRequest`) or iterate/clear the current-epoch slot. Also consider making `_defaultPrefundedInstantReserve` measure the actual token balance earmarked for instant claims rather than deriving it from `instantBasis - pendingInstant`.

### Proof of Concept
Foundry fork sketch (patterns from `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Setup: pool with instant withdrawals enabled, users A (instant claimer) and B.
// 1. During buffer: A and B call cdoEpoch.requestWithdraw -> instant path
//    (lastEpochApr > unscaledApr + instantWithdrawAprDelta).
//    instantWithdrawClaimsByEpoch[N] = A_amt + B_amt.
// 2. manager: startEpoch(); CDO calls collectInstantWithdrawFunds funding only A_amt
//    (partial funding -> pendingInstantWithdraws = B_amt).
// 3. A: cdoEpoch.claimInstantWithdrawRequest();  // A paid in full.
//    BUG: instantWithdrawClaimsByEpoch[N] still = A_amt + B_amt.
// 4. Borrower defaults mid-epoch N (epochNumber still N):
//    owner: cdoEpoch.stopEpochWithDuration / default flow, then finalizeDefault(recovered, source).
//    Inside finalizeDefaultRecovery:
//      pendingBasis    += A_amt + B_amt          // should be only B_amt
//      prefundedReserve += (A_amt + B_amt) - B_amt = A_amt   // phantom, already paid to A
//    => recoveryPrice diluted; defaultRecoveryReserve overstated by A_amt.
// 5. B and defaulted-epoch normal receipt holders claim via claimWithdrawRequest /
//    claimInstantWithdrawRequest. The last claimant's _transferDefaultRecovery
//    reverts on insufficient balance -> permanent freeze of up to A_amt.
assertTrue(instantWithdrawClaimsByEpoch[N] > pendingInstantWithdraws + strategyUnderlyingBal);
vm.expectRevert(); // safeTransfer insufficient balance on final recovery claim
cdoEpoch.claimInstantWithdrawRequest();
```

Uncertainty note: the exploit requires the CDO's `stopEpoch`/default flow to keep `epochNumber` constant through finalization (verified — only `deposit()` during a running epoch bumps it) and that partial instant funding leaves `pendingInstantWithdraws != 0`, which the prefunded-reserve logic itself documents as possible (`IdleCreditVault.sol:638-640`). Full end-to-end verification of the CDO-side default entry points was not completed within this pass, but the stale-counter defect and its arithmetic impact are directly visible in the strategy code.
