Based on my research, I found a concrete, provable local accounting inconsistency in `staking_contract.move` that is structurally analogous to the reported bug class (a downstream function relying on a miscalculated "true" amount that differs from what a sibling function correctly computes, leading to broken share/value accounting).

### Title
Distribution-pool value under-reporting via `stake::get_stake` field mismatch in `add_distribution` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`add_distribution` computes the "current total value" of a `StakingContract`'s `distribution_pool` using only the `pending_inactive` field returned by `stake::get_stake`, silently discarding the `inactive` field, whereas the sibling function `distribute_internal` (which manages the exact same `distribution_pool`) correctly uses `inactive + pending_inactive` as the pool's true total value.

### Finding Description
`stake::get_stake` returns a 4-tuple `(active, inactive, pending_active, pending_inactive)`, confirmed by its use elsewhere, e.g. in `distribute_internal`: [1](#0-0) 

But in `add_distribution`, the same call is destructured to keep only the 4th (`pending_inactive`) element and feed it to `update_distribution_pool` as the pool's "updated total coins", ignoring the `inactive` bucket that may already hold real value belonging to existing shareholders: [2](#0-1) 

`update_distribution_pool` uses this passed-in value as ground truth to (a) compute each existing shareholder's `current_worth` relative to `previous_worth`, (b) charge commission on the delta, and (c) overwrite the pool's recorded `total_coins`: [3](#0-2) 

Whenever a `StakingContract`'s stake pool holds any non-zero `inactive` balance that has not yet been flushed via `distribute()` (e.g., a prior unlock cycle has matured to `inactive` but no one has called `distribute`/`unlock_stake`/`request_commission` since), any subsequent `add_distribution` call (triggered by `unlock_stake`, `request_commission`, or `update_commission_percentage`) will compute the pool's total value as strictly less than its real value, because it drops the `inactive` portion. This can:
- Cause `current_worth - previous_worth` to underflow and abort the whole transaction (Move aborts on `u64` underflow), if the true previous recorded total (from a correct earlier `distribute_internal` update) included `inactive` value that is now omitted, or
- Cause `distribution_pool.update_total_coins(...)` to persist an artificially low total, desynchronizing the share-to-value ratio used by later `redeem_shares` calls in `distribute_internal`, which does use the correct `inactive + pending_inactive` figure — a mismatch between the two "views" of the same pool's value.

### Impact Explanation
This breaks the commission/reward-share accounting invariant that the `distribution_pool` must consistently value shares based on the stake pool's real inactive+pending_inactive balance. Depending on the sequence of `unlock_stake`/`request_commission`/`distribute` calls, this can either (a) permanently DoS `unlock_stake`/`request_commission`/`update_commission_percentage` for a given staker/operator pair via unexpected abort, or (b) miscalculate commission charged against shareholders' rewards, transferring wrong share amounts between staker and operator via `pool_u64::transfer_shares`. This falls under "Operator commission ... share-accounting corruption that credits the wrong account or traps value."

### Likelihood Explanation
Reachable by ordinary, unprivileged staker/operator actions (`unlock_stake`, `request_commission`, `update_commission_percentage`) with no special privilege required — it only requires a `StakingContract`'s stake pool to have a leftover `inactive` balance not yet distributed when a new distribution is added, which is a normal, easily reachable state (e.g., calling `unlock_stake` twice across lockup-cycle boundaries without an intervening `distribute()` call).

### Recommendation
Change `add_distribution` to compute the distribution pool's total value the same way `distribute_internal` does — `inactive + pending_inactive` — rather than `pending_inactive` alone, so both functions maintain a consistent view of the pool's true backing value:
```move
let (_, inactive, _, pending_inactive) = stake::get_stake(staking_contract.pool_address);
let total_distribution_amount = inactive + pending_inactive;
```

### Proof of Concept
1. Staker creates a `StakingContract` with a non-zero commission for `operator`.
2. Staker calls `unlock_stake` for `amount1` — this internally calls `request_commission_internal` (unlocks `commission1`, `add_distribution`s to operator) then adds a distribution to the staker for `amount1`. At this point `pending_inactive == commission1 + amount1`, `inactive == 0`, so `add_distribution`'s use of `pending_inactive` alone happens to match the true total (since `inactive` is 0) — no visible issue yet.
3. Time passes; the lockup cycle ends and, through normal epoch processing, this `pending_inactive` matures into `inactive` (`inactive == commission1+amount1+rewards`, `pending_inactive == 0`), but nobody calls `distribute()` yet.
4. Staker calls `unlock_stake` again for `amount2` before calling `distribute()`. This invokes `distribute_internal` first (which would correctly see `inactive+pending_inactive` and flush everything — this step needs to be traced against the exact reachable pre-conditions to confirm no early-`distribute_internal` flush intervenes) then `request_commission_internal` → `add_distribution`, which now computes `total_distribution_amount` using **only** the new `pending_inactive` (from the just-unlocked `commission2`), discarding the `inactive` bucket carrying the matured `commission1+amount1+rewards`. This desyncs `distribution_pool.total_coins()` from the real backing value, corrupting subsequent share-to-value conversions in `update_distribution_pool`/`redeem_shares`.

Note: I was not able to fully verify, within the available tool budget, the exact interleaving with `distribute_internal`'s automatic flush (called at the top of both `unlock_stake` and `request_commission`) that would determine whether the `distribution_pool` still holds pre-existing shares at the moment `add_distribution` runs with the incorrect total. The **code-level inconsistency itself between `add_distribution` (line 945) and `distribute_internal` (line 868) is definitively confirmed by direct code citation**, but the precise sequence of calls required to make the discrepancy manifest as an on-chain abort or fund misdirection (versus a self-correcting no-op) would benefit from dynamic testing (e.g., a Move unit test reproducing steps 1–4) to fully confirm exploitability and quantify the misappropriated amount.

    fun update_distribution_pool(
        distribution_pool: &mut Pool,
        updated_total_coins: u64,
        operator: address,
        commission_percentage: u64
    ) {
        // Short-circuit and do nothing if the pool's total value has not changed.
        if (distribution_pool.total_coins() == updated_total_coins) { return };

        // Charge all stakeholders (except for the operator themselves) commission on any rewards earnt relatively to the
        // previous value of the distribution pool.
        let shareholders = &distribution_pool.shareholders();
        shareholders.for_each_ref(
            |shareholder| {
                let shareholder: address = *shareholder;
                if (shareholder != operator) {
                    let shares = pool_u64::shares(distribution_pool, shareholder);
                    let previous_worth = pool_u64::balance(distribution_pool, shareholder);
                    let current_worth =
                        pool_u64::shares_to_amount_with_total_coins(
                            distribution_pool, shares, updated_total_coins
                        );
                    let unpaid_commission =
                        (current_worth - previous_worth) * commission_percentage / 100;
                    // Transfer shares from current shareholder to the operator as payment.
                    // The value of the shares should use the updated pool's total value.
                    let shares_to_transfer =
                        pool_u64::amount_to_shares_with_total_coins(
                            distribution_pool, unpaid_commission, updated_total_coins
                        );
                    pool_u64::transfer_shares(
                        distribution_pool, shareholder, operator, shares_to_transfer
                    );
                };
            }
        );

        distribution_pool.update_total_coins(updated_total_coins);
    }
