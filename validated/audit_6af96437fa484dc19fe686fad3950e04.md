### Title
`depositDuringEpoch` credits the nominal `_amount` instead of the net amount received, so a fee-on-transfer underlying lets a depositor mint unbacked shares and drain other LPs — (`contracts/IdleCDOEpochVariant.sol`)

### Summary
The bug class (fee-on-transfer mismatch between assumed and received amounts, Sherlock bullvbear M) maps to `IdleCDOEpochVariant.depositDuringEpoch`. Unlike `_deposit` in `IdleCDO`/`IdleCDOCreditVault`, which measures `_contractTokenBalance(_token) - _preBal` and mints on the delta, `depositDuringEpoch` pulls `_amount` via `_transferUnderlyingsFrom` and then uses the nominal `_amount` for share minting, interest accounting, strategy-token minting, and the outbound transfer to the borrower.

### Finding Description
In `contracts/IdleCDOEpochVariant.sol` `depositDuringEpoch` (lines ~684-732):

```solidity
_transferUnderlyingsFrom(msg.sender, address(this), _amount);   // no balance delta measured
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
_mintShares(_tranche, msg.sender, _minted, _amount);            // mints on nominal _amount
IdleCreditVault(strategy).mintStrategyTokens(_amount);          // NAV credit on nominal _amount
_transferUnderlyings(_borrower(), _amount);                     // sends full _amount out
```

If `token` is (or becomes, e.g. via upgrade or a fee-enabled stablecoin) a fee-on-transfer token, the vault receives `_amount - fee` but:
1. mints the attacker tranche shares priced on the full `_amount` plus `trancheInterest`,
2. mints `_amount` of strategyTokens (strategyToken balance drives `getContractValue`/NAV),
3. transfers the full `_amount` to the borrower from the contract's balance.

Net effect per call: the vault's raw token balance decreases by `fee` while liabilities (strategyTokens + minted tranche shares) increase by the full `_amount + trancheInterest`. The shortfall is borne by existing AA/BB NAV until the honest borrower repays principal + interest at `stopEpoch`, at which point the missing `fee` is crystallized as a loss against tranche holders (BB first).

Contrast with `IdleCDO.sol:250-253` and `IdleCDOCreditVault.sol:203-206`, which correctly mint on `balanceOf` delta — the epoch-variant path bypassed that protection.

### Impact Explanation
Direct theft/solvency break: each `depositDuringEpoch` call extracts `fee` tokens worth of value from existing LPs (attacker's shares are over-minted relative to value contributed; the residual deficit sits in vault balance). With a large fee parameter or repeated deposits the loss scales linearly; if cumulative fees exceed BB NAV it triggers the BB-wipeout shutdown path in `_updateAccounting`, freezing normal operations. Attacker class fits: any KYC-passed wallet (`isWalletAllowed`) during a running epoch, non-programmable, non-AYS mode — all attacker-reachable.

### Likelihood Explanation
Requires the vault's underlying to charge on transfer. Deployments pin `token` at init, and mainnet underlyings used are typically USDC-class tokens that do not charge fees today; the risk is an upgradeable token gaining a fee (the exact scenario the source report cites) or a deployment choosing an FoT underlying. Medium-low likelihood, but no guard (`_skimDonatedAssets` only sweeps excess; nothing reconciles `received < _amount`) stops it.

### Recommendation
Measure the net received amount in `depositDuringEpoch`:

```solidity
uint256 _preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
_amount = _contractTokenBalance(token) - _preBal;
```

and use the adjusted `_amount` for `trancheInterest`, `_minted`, `mintStrategyTokens`, and the transfer to the borrower. Same for `getFundsFromBorrower`/`stopEpoch`: confirm the received delta when pulling repayments, or use `balanceOf` for fee payouts instead of the assumed `_pendingWithdrawFees`/`_grossInterest`.
