### Title
Stale confirmations from removed multisig members still count toward the execution threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` counts every entry stored in the `confirmations` `HashSet<String>` for a request toward `num_confirmations`, but `delete_member` only purges pending requests that were *created* by the removed member — it never scans other requests' confirmation sets for that member's signature. A member can confirm a request, later be removed from the multisig, and that stale confirmation still counts toward reaching the K‑of‑N threshold, allowing a request to execute with fewer genuinely live approvals than `num_confirmations` requires.

### Finding Description
The binding this contract is supposed to maintain is:
`confirmations counted toward execution == confirmations from accounts that are currently live members`.

In `confirm()`:
```rust

`assert_valid_request`/`current_member()` only validate that the *caller of the current transaction* is a live member; they never re-validate the identities already stored inside `confirmations`. Once a string is inserted into the `HashSet<String>` for a request, it is trusted forever, regardless of subsequent membership changes.

`delete_member()` only cleans up requests *created by* the removed member:
```rust
// multisig2/src/lib.rs:356-379

        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);

``` [2](#0-1) 

`r.member` is the account that *created* the request (`MultiSigRequestWithSigner.member`), set once in `add_request()` [3](#0-2) . If the removed member had only *confirmed* (not created) a still‑pending request created by someone else, that request is not touched by `delete_member`, and the removed member's entry remains inside `self.confirmations[request_id]`.

Concrete flow:
1. Multisig is 3‑of‑4 with members `A, B, C, X`.
2. `A` creates+self-confirms a `Transfer` request `R` (`add_request_and_confirm`) → `confirmations(R) = {A}`.
3. `X` confirms `R` → `confirmations(R) = {A, X}` (2 < 3, not yet executed).
4. `A, B, C` submit and confirm a `DeleteMember{X}` request (3 confirmations from live members) → executes, `X` is removed. `members.len() - 1 = 3 >= num_confirmations (3)` passes the check in `delete_member`, so removal succeeds. `R`'s creator is `A`, not `X`, so `R` and its confirmations are left untouched.
5. `B` confirms `R` → `confirmations(R).len() + 1 = 3 >= num_confirmations (3)` → `R` executes via `execute_request`, transferring funds.

`R` executed with confirmations `{A, X, B}`, but `X` is no longer a member at execution time — only `A` and `B` are live confirmers. The 3‑of‑4 (now 3‑of‑3) guarantee is broken: the request executed on 2 live confirmations instead of the required 3.

The identical pattern exists in the legacy `multisig` contract's `DeleteKey` handler, which also filters removed requests only by `r.signer_pk == pk` [4](#0-3) .

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." A `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` action can be pushed through and executed with fewer live-member approvals than `num_confirmations` mandates, undermining the entire K‑of‑N security model the contract exists to enforce. This can result in unauthorized fund transfers or unauthorized privilege changes (e.g., adding a new full-access key) executed with insufficient authorization.

### Likelihood Explanation
This requires no foundation, owner, redeploy, or external validator — it is achievable by any member set through normal contract usage: a member confirms a pending request, then is later removed (a routine, expected multisig operation, e.g. offboarding a departing member or team key rotation) before that request reaches quorum, and any remaining member(s) confirm afterward. No special timing exploit, race condition, or privileged bypass is needed; it merely requires the ordinary sequence "confirm → member removed → confirm again," which can easily occur unintentionally, and can be intentionally engineered by a malicious member who confirms sensitive requests before arranging their own removal (or a removed key's replacement) to make it look retroactively legitimate.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over `self.confirmations` for **all** pending requests (not just those created by the removed member) and strip the removed member's entry from each confirmation set. Alternatively, revalidate at execution time in `confirm()` that every account/key in the stored `confirmations` set for a request is still a current member before counting it toward `num_confirmations`, discarding stale entries lazily.

### Proof of Concept
Using the existing test harness in `multisig2/src/lib.rs`:
```rust
let mut c = MultiSigContract::new(members(), 3); // members: alice, bob, key1, key2 (X = key2)

// Step 1: alice creates+confirms request R (Transfer)
testing_env!(context_with_account(alice(), amount));
let r = c.add_request_and_confirm(transfer_request.clone()); // confirmations(R) = {alice}

// Step 2: key2 (X) confirms R
testing_env!(context_with_key(key2_pk, amount));
c.confirm(r); // confirmations(R) = {alice, key2}, 2 < 3, not executed

// Step 3: 3 live members confirm DeleteMember{key2} and it executes, removing key2
//   (delete_member only purges requests created by key2 — R was created by alice, untouched)

// Step 4: bob confirms R
testing_env!(context_with_account(bob(), amount));
c.confirm(r); // confirmations(R).len()+1 == 3 >= num_confirmations(3) -> executes
// R executed with only {alice, bob} as live confirmers (2 live), plus a stale, no-longer-valid
// confirmation from the removed member key2.
```
This demonstrates the request executes despite only 2 of the 3 required confirmations coming from currently live members.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
