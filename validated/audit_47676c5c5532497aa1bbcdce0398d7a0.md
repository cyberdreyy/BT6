### Title
Keyring re-check on `requestWithdraw` freezes funds of lenders whose credential lapses after entry - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`isWalletAllowed` is enforced not only on entry (`_deposit`, `depositDuringEpoch`) but also on the exit path `requestWithdraw`, and on `IdleCDOEpochQueue.requestWithdraw`. A lender who passed KYC, deposited, and later loses their Keyring credential (credential expiry, policy change, or removal from `KeyringIdleWhitelist.whitelist`) can no longer initiate a withdrawal. Their tranche tokens remain locked in the vault with no self-service exit, mirroring the "un-whitelisting causes stuck funds" bug class.

### Finding Description
The KYC gate lives in `IdleCDOEpochVariant.requestWithdraw`: [1](#0-0) 

and in `IdleCDOEpochVariant._deposit` / `depositDuringEpoch`: [2](#0-1) [3](#0-2) 

`isWalletAllowed` performs a live external check each call: [4](#0-3) 

so a credential that was valid at deposit time can return `false` later. The same gating exists in the epoch queue's `requestWithdraw` via `_checkAllowed`: [5](#0-4) [6](#0-5) 

The behavior is even codified in tests: `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw` asserts a non-allowed holder's `requestWithdraw` reverts with `NotAllowed`: [7](#0-6) 

Claims already in the system (`claimWithdrawRequest`, `claimInstantWithdrawRequest`, queue `claimWithdrawRequest`) are correctly not gated: [8](#0-7) 

but a holder whose credential lapses *before* requesting can never reach the claim stage. Their only exit is transferring tranche tokens to another credentialed wallet or selling through `WriteOffEscrow` at a negotiated (likely discounted) price — neither is guaranteed, and no privileged action is required: Keyring credentials expire naturally.

### Impact Explanation
Temporary-to-permanent freezing of user funds. All tranche tokens held by a de-credentialed lender become non-withdrawable for an unbounded period; quantified loss equals the holder's full position value (principal + accrued interest) for the freeze duration, or a forced discounted exit via the write-off escrow.

### Likelihood Explanation
Keyring credentials are time-bound attestations; expiry or policy-id rotation (`setKeyringParams` changes `keyringPolicyId`) can revoke `checkCredential` for existing holders without any malicious action. Every epoch cycle (deposit → wait → requestWithdraw → wait → claim) lengthens the window in which a lapse strands funds.

### Recommendation
Enforce `isWalletAllowed` only on entry (deposits, queue `requestDeposit`) and on fresh commitments, not on exits for assets already inside the system. Remove the `!isWalletAllowed(msg.sender)` term from `requestWithdraw` and from `IdleCDOEpochQueue._checkAllowed` when used by `requestWithdraw`, matching the already-ungated claim functions.

    // check if the wallet is allowed to deposit (ie epoch is running and keyring KYC completed)
    _checkAllowed(msg.sender);
    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // withdraw requests will be made in the next buffer period (ie next epoch)
    uint256 nextEpoch = IdleCreditVault(strategy).epochNumber() + 1;
    // updated user queued withdraw amount for the next epoch. Epoch number
    // is considered the epoch when processWithdrawRequests will be called
    userWithdrawalsEpochs[msg.sender][nextEpoch] += amount;
    // update pending withdraw requests
    epochPendingWithdrawals[nextEpoch] += amount;
  }
