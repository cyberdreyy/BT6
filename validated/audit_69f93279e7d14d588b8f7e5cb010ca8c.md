### Title
A dust APR0 withdraw request permanently blocks `stopEpoch` once APR is raised, freezing the running epoch — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Qwik bug class is "an attacker-controlled input reaches a code path whose thrown error is unhandled and takes down the whole service." The credit-vault analog lives in `IdleCreditVault.prepareStopEpochWithApr0`, which is called unconditionally at the top of every `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration`. When `apr0TotalPrincipal != 0` and `unscaledApr != 0`, it reverts with `NotAllowed` — before borrower pull, before `_handleBorrowerDefault`, before any recovery path. Any unprivileged user can create a nonzero `apr0TotalPrincipal` with a dust `requestWithdraw` while APR is 0; the next honest APR change then makes the epoch un-stoppable, freezing all vault funds.

### Finding Description
`requestWithdraw` routes to `_requestWithdrawApr0` whenever `unscaledApr == 0` and the pool is not closed, which does `apr0TotalPrincipal += _amount` (`contracts/strategies/idle/IdleCreditVault.sol:567-577`). A user can request a minimal withdrawal (even 1 wei of principal after fees) during the buffer between epochs while APR is 0.

At the next `stopEpoch`, `IdleCDOEpochVariant` calls `prepareStopEpochWithApr0` before pulling funds or handling borrower default (`contracts/IdleCDOEpochVariant.sol:362`). Inside:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) return (...);
if (unscaledApr != 0) {
  revert NotAllowed();
}
```
`contracts/strategies/idle/IdleCreditVault.sol:499-508`

If the manager has since set a nonzero APR — a routine, honest operation via `setAprsWithBuffer`/`setApr` (`IdleCreditVault.sol:217-235`) — this check reverts. `stopEpoch` therefore always reverts:

- `apr0TotalPrincipal` is only zeroed at line 540, *after* the revert check, so it can never self-clear.
- `_handleBorrowerDefault`/`finalizeDefaultRecovery` are unreachable because they sit downstream of this call in `stopEpoch`; there is no path to default that bypasses `prepareStopEpochWithApr0`.
- Users cannot cancel a pending request (no `deleteWithdrawRequest` on the strategy side; the queue's variant is owner/manager-gated and only touches queue ledgers).

The only recovery is the manager noticing the freeze and setting `unscaledApr` back to 0 — the epoch then remains stuck until the next `stopEpoch` window, and the same user can re-seed `apr0TotalPrincipal` during the following buffer again as long as APR passes through 0 at any point.

### Impact Explanation
While the epoch cannot be stopped, `isEpochRunning` stays true: deposits revert (`Pausable: paused`), `claimWithdrawRequest` reverts (`epochNumber <= lastWithdrawRequest`), and the borrower cannot repay/settle through the normal path. All user principal and accrued yield in the CDO are frozen — a temporary freeze of the entire TVL, recoverable only if the manager diagnoses and reverts the APR change, and re-triggerable by the same attacker whenever APR is 0 during a buffer. This matches the report's "service crashes from an unhandled error on a reachable request path" pattern: a trivially craftable state (dust APR0 receipt) turns a routine admin action into a hard revert on the only epoch-finalization entry point.

### Likelihood Explanation
Requires an epoch phase with `unscaledApr == 0` (explicitly supported: `setAprs(0,0)` and `_forceLastEpochAprToZero` flows are exercised in tests) and a subsequent APR change while an APR0 receipt is open. Both are normal operations; the attacker only needs a KYC-allowed wallet and dust. No privileged misbehavior is needed — the honest manager's own `setAprsWithBuffer` arms the trap.

### Recommendation
In `prepareStopEpochWithApr0`, don't revert on `unscaledApr != 0` when an APR0 bucket is open. Either settle the bucket with zero APR0 interest (set `apr0RateByEpoch[epochNumber] = 0` and zero `apr0TotalPrincipal`), or compute the pro-rata split with the APR that was in effect at request time. Also give users (or the CDO) a way to clear `apr0Users`/`apr0TotalPrincipal` on request cancellation so the bucket cannot be left permanently open.

### Proof of Concept
Foundry-style sequence on the existing `IdleCreditVault.t.sol` harness:

```solidity
// APR == 0 phase
vm.prank(manager);
IdleCreditVault(address(strategy)).setAprs(0, 0);
idleCDO.depositAA(10_000 * ONE_SCALE);
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, 0, expectedInterest); // apr stays 0

// buffer: attacker (any allowed wallet) files a dust APR0 withdraw request
uint256 dustTranche = (ONE_TRANCHE + cdoEpoch.virtualPrice(address(AAtranche)) - 1)
                      / cdoEpoch.virtualPrice(address(AAtranche));
vm.prank(attacker);
cdoEpoch.requestWithdraw(dustTranche, address(AAtranche));
assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

// honest manager raises APR for the next epoch
vm.prank(manager);
IdleCreditVault(address(strategy)).setAprsWithBuffer(10e18, cdoEpoch.epochDuration(), buffer);

_startEpochAndCheckPrices(1);
vm.warp(cdoEpoch.epochEndDate() + 1);

// epoch can never be stopped: every variant hits the same revert
vm.prank(manager);
vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
cdoEpoch.stopEpoch(0, 0);

vm.prank(manager);
vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), 0);

// deposits and withdraw claims remain bricked
vm.expectRevert(bytes("Pausable: paused"));
idleCDO.depositAA(ONE_SCALE);
```

Caveat: this is a temporary freeze, not permanent loss — the honest manager can restore `unscaledApr = 0` to unstick the epoch, so the finding should be judged under the "temporary freezing of funds" category with a quantifiable locked amount (entire vault NAV plus pending claims for the freeze duration).
