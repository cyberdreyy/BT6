### Title
Unauthenticated LOOP plugin pprof symbol resolution via `POST /plugins/:name/debug/pprof/symbol` - ([File: core/web/router.go], [File: core/web/loop_registry.go])

### Summary
The LOOP plugin debug/pprof routes registered by `loopRoutes` are mounted directly on the base `api` router group, which only applies rate limiting and session middleware — no authentication middleware is attached, unlike every other sensitive route group in the router. This lets any unauthenticated client call `pluginPPROFPOSTSymbolHandler` (and the sibling `pluginPPROFHandler`/`pluginMetricHandler`) to proxy pprof requests into a running LOOP plugin's `/debug/pprof/symbol` endpoint and resolve internal function symbol names.

### Finding Description
In `core/web/router.go`, the top-level `api` group is created with only rate limiting and cookie-session middleware attached (no `auth.Authenticate`): [1](#0-0) 

`debugRoutes`, `sessionRoutes`, and the authenticated part of `v2Routes` all explicitly wrap their sub-groups with `auth.Authenticate(app.AuthenticationProvider(), ...)` before registering handlers, e.g. host pprof endpoints under `metricRoutes` are nested inside the `authv2` group: [2](#0-1) [3](#0-2) 

However `loopRoutes` is called directly on `api` with no such wrapping: [4](#0-3) 

`pluginPPROFPOSTSymbolHandler` accepts the plugin name from the URL, reads the raw request body, and forwards it as a POST to the plugin's internal `/debug/pprof/symbol` endpoint, returning the plugin's raw response body to the caller: [5](#0-4) 

Since no authentication middleware guards this route, any unauthenticated client can POST a pprof symbol-resolution payload and receive symbol name responses proxied straight from the plugin process, disclosing internal function/symbol names of the running LOOP plugin binary.

### Impact Explanation
This discloses internal binary/topology information (function symbol names) of a running LOOPP plugin process to an unauthenticated caller, which aids further exploitation (e.g., crafting targeted attacks against known internal functions, understanding plugin internals/version fingerprinting). It matches Chainlink's "sensitive information disclosure" bounty impact class — no fund movement or job hijacking directly, but a genuine authentication-bypass on a debug/introspection endpoint that leaks internals about the running node's plugins.

### Likelihood Explanation
Precondition is simply that the node runs at least one LOOP plugin (common for chain plugins like EVM/Solana/etc., as seen in `testdata/scripts/admin/profile/multi-chain-loopp.txtar`). No credentials, cookies, or tokens are required — a bare HTTP POST to `/plugins/:name/debug/pprof/symbol` suffices, and the plugin name is discoverable via the equally unauthenticated `/discovery` endpoint. This is trivially repeatable.

### Recommendation
Wrap `loopRoutes` (and any plugin `/metrics` and `/debug/pprof/*` handlers) with the same `auth.Authenticate` middleware used for `debugRoutes`/`metricRoutes`, e.g. register them inside an authenticated sub-group of `api` rather than directly on the unauthenticated base group.

### Proof of Concept
Go handler-level integration test plan:
1. Build a `gin.Engine` using `web.NewRouter` (or directly call `loopRoutes`) with an `Application` that has a fake `LoopRegistryServer`/registry containing one plugin entry (e.g., `"evm.1"`) pointing at a local `httptest.Server` that implements `net/http/pprof`'s `/debug/pprof/symbol`.
2. Using `httptest.NewServer(router)` and a plain `http.Client` (no cookie jar, no `Authorization` header, no session), issue:
   `POST /plugins/evm.1/debug/pprof/symbol` with body `b0x<addr>` (pprof symbol lookup format).
3. Assert the response status is `200 OK` (not `401 Unauthorized`), and that the body contains the resolved symbol name proxied from the plugin, confirming the request reached `pluginPPROFPOSTSymbolHandler` without any authentication check.
4. As a control, repeat against `POST /v2/debug/pprof/symbol` (host-level, via `metricRoutes`/`authv2`) and confirm it returns `401 Unauthorized` for the same unauthenticated client, demonstrating the inconsistency/gap specific to `loopRoutes`.

func (l *LoopRegistryServer) pluginPPROFPOSTSymbolHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/symbol", l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	body, err := io.ReadAll(gc.Request.Body)
	if err != nil {
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "error reading plugin pprof request body: %s", err))
		return
	}
	l.doRequest(gc, "POST", pluginURL, bytes.NewReader(body), timeout, pluginName)
}
