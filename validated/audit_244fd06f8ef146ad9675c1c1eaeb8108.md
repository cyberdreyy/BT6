### Title
Missing dot-boundary check in wildcard CORS origin matching allows suffix-collision domains to bypass allowlist - ([File: core/services/gateway/network/httpserver.go])

### Summary
`isAllowedOrigin` implements wildcard matching for entries like `*.remix.com` by stripping the `*.` prefix and then calling `strings.HasSuffix(originHost, allowedHost)`, without verifying that the matched suffix is preceded by a `.` (or is an exact match). This lets an attacker who controls a domain such as `evilremix.com` (or `xremix.com`) satisfy the suffix check against allowed wildcard `*.remix.com`, even though `evilremix.com` is not a subdomain of `remix.com`.

### Finding Description
In `isAllowedOrigin` [1](#0-0) , once the scheme and port match, the code checks:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
```
If `CORSAllowedOrigins` contains `https://*.remix.com`, `allowedHost` becomes `remix.com`. `strings.HasSuffix("evilremix.com", "remix.com")` returns `true` because Go's `HasSuffix` performs pure character-suffix comparison with no boundary check — it does not require that the character preceding the matched suffix be a `.` (or that the strings be equal). Consequently a completely unrelated, attacker-registered domain like `evilremix.com` or `xremix.com` is treated as an authorized subdomain of `remix.com`.

This function is invoked directly from `handleRequest` [2](#0-1)  on every incoming request when `CORSEnabled` is true: the raw `Origin` header is reflected back via `Access-Control-Allow-Origin` if `isAllowedOrigin` returns true, with no additional dot-boundary validation anywhere else in the request path. There is no middleware or later check that re-validates the origin.

### Impact Explanation
An attacker who registers or controls a domain with a suffix collision (e.g., `evilremix.com` when `*.remix.com` is allow-listed) can host a malicious webpage that issues credentialed cross-origin `fetch`/`XHR` requests to the Gateway HTTP endpoint. The browser will permit the malicious page to read the JSON-RPC-style Gateway responses (`ProcessRequest` results, which may include job/DON responses tied to a victim's session/JWT `Authorization` header) because the server reflects the attacker's origin and grants `Access-Control-Allow-Origin`. This is a cross-user/cross-origin response confusion issue — data intended only for the legitimate `*.remix.com` frontend can be read by an unrelated attacker-controlled site, potentially exposing gateway request/response data or enabling request impersonation against the gateway's HTTP interface on behalf of a victim's browser session.

### Likelihood Explanation
Preconditions: `CORSEnabled=true` and `CORSAllowedOrigins` containing a wildcard entry (e.g. `*.remix.com`), which is an explicitly supported code path in `isAllowedOrigin` [1](#0-0) . No credentials or special role are required by the attacker — only a victim's browser visiting the attacker's page, and the attacker registering any domain string ending in the allowed suffix (trivial and cheap, e.g. `evilremix.com`). This is fully reproducible and deterministic given the wildcard config, requiring no race conditions or timing.

### Recommendation
Fix the wildcard suffix check to require a dot boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".remix.com"
    if originHost == allowedHost[2:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
i.e., compare against `.remix.com` (keeping the leading dot) rather than `remix.com`, so that `evilremix.com` no longer satisfies the suffix check while `foo.remix.com` still does.

### Proof of Concept
Add a table-driven Go test for `isAllowedOrigin` in `core/services/gateway/network/httpserver_test.go`:
```go
func TestIsAllowedOrigin_WildcardBoundary(t *testing.T) {
    s := &httpServer{
        config: &HTTPServerConfig{CORSAllowedOrigins: []string{"https://*.remix.com"}},
        lggr:   logger.Test(t),
    }
    cases := map[string]bool{
        "https://sub.remix.com":     true,  // legit subdomain
        "https://remix.com":         false, // wildcard shouldn't match bare apex per current design intent (verify against spec)
        "https://evilremix.com":     false, // should NOT match — currently returns true (bug)
        "https://xremix.com":        false, // should NOT match — currently returns true (bug)
        "https://remix.com.evil.com": false,
    }
    for origin, want := range cases {
        got := s.isAllowedOrigin(origin)
        assert.Equalf(t, want, got, "origin=%s", origin)
    }
}
```
Running this against the current implementation shows `https://evilremix.com` and `https://xremix.com` incorrectly return `true`, confirming the bypass.
