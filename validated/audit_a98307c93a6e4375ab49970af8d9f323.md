### Title
Stale confirmations from removed members count toward `num_confirmations`, letting a `DeployContract` request execute against the multisig with fewer live-member confirmations - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts confirmations by set size only and never re-validates that previously-confirming members are still current members. `DeleteMember` (`delete_member`) only purges requests that the removed member itself *created*, not confirmations the removed member gave on other, still-pending requests. This lets a request (including one that carries `DeployContract` against the multisig's own account) execute once its stale confirmation count reaches `num_confirmations`, even though one of the counted confirmers has since been removed from the multisig.

### Finding Description
The invariant the question targets can be stated as an equality that must hold at execution time:
`confirmations.len() at execution == number of CURRENTLY LIVE members who confirmed >= num_confirmations`.

The code only enforces `confirmations.len() as u32 + 1 >= self.num_confirmations` in `confirm`: [1](#0-0) 

`confirmations` is a `HashSet<String>` of `MultisigMember::to_string()` values, populated at the time each member confirmed: [2](#0-1) 

`assert_valid_request` only re-checks that the *current caller* is a live member; it never re-checks the members already recorded in `confirmations`: [3](#0-2) 

When a member is removed via `DeleteMember`, `delete_member` only prunes requests where `r.member == member`, i.e. requests the removed member *created* as signer - it does not scrub that member's confirmation entries from the `confirmations` set of *other* pending requests it merely confirmed: [4](#0-3) 

Exploit flow (multisig with members {A, B, C, D}, `num_confirmations = 3`):
1. Member A creates request R = `DeployContract { code: malicious }` with `receiver_id == current_account_id()` (the multisig itself), and confirms it (`confirmations = {A}`).
2. Member B confirms R (`confirmations = {A, B}`, count 2 < 3, not yet executed).
3. Separately, members A, C, D fully confirm and execute an unrelated `DeleteMember { member: B }` request (`delete_member`), removing B from `members` and deleting B's access key. R's `confirmations` set still contains B's stale entry because `delete_member` only filters by request-creator identity, not by confirmer membership.
4. Member C now confirms R. `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)`, so `confirm` immediately calls `remove_request` and `execute_request`, deploying `malicious` code onto the multisig account.

At execution time only A and C are still live members who confirmed - B's confirmation is stale/void since B was removed - so the request executed with 2 live confirmations against a 3-confirmation policy. `assert_self_request` is not relevant here since `DeployContract` doesn't call it; regardless, the check that fails is the confirmation-liveness check, which does not exist anywhere in the contract.

### Impact Explanation
The multisig's code can be replaced (or any other action - `Transfer`, `AddKey`, `FunctionCall`, etc. - executed) with fewer live-member confirmations than the configured `num_confirmations`, directly matching the Critical impact category "a multisig request executed below `num_confirmations` live members." Since `DeployContract` lets an attacker-controlled contract be deployed at the multisig's own account address, the attacker (via a compromised-but-legitimately-removed member, or simply by exploiting the timing) can replace the multisig logic entirely and subsequently drain any NEAR held by the multisig account. The bug is repeatable for any multisig instance and any request type each time a confirming member is later removed before the request reaches its threshold.

### Likelihood Explanation
This requires the normal, expected multisig operational sequence: a request partially confirmed, then one of its confirmers removed via a legitimate `DeleteMember`, then the threshold reached by another confirmation. It does not require the removed member to be malicious - simple member turnover (e.g., a key holder leaving the team, key rotation) combined with a pending request creates the exposed window. No special privileges beyond ordinary multisig membership actions are needed to trigger the divergence; a single remaining malicious/colluding member timing their confirmation right after a `DeleteMember` executes is sufficient to complete the exploit.

### Recommendation
When counting confirmations in `confirm` (and when displaying `get_confirmations`), filter the stored confirmation set to only those entries whose `MultisigMember` is still present in `self.members` before comparing against `num_confirmations`. Additionally, `delete_member` should scrub the removed member's entry from the `confirmations` set of every request, not just requests it created, to keep `confirmations` consistent with live membership immediately.

### Proof of Concept
```rust
// cargo test in multisig2/src/lib.rs test module

#[test]
fn test_stale_confirmation_after_member_removed_executes_below_threshold() {
    // Setup: members = [alice (Account), bob (Account), key1 (AccessKey), key2 (AccessKey)]
    // num_confirmations = 3
    let amount = 1_000;
    testing_env!(context_with_key(key1_pk(), amount));
    let mut c = MultiSigContract::new(members(), 3);

    // Step 1: alice creates + confirms DeployContract request R targeting self (current_account_id)
    testing_env!(context_with_account(alice(), amount));
    let deploy_request = MultiSigRequest {
        receiver_id: alice(), // current_account_id in these tests
        actions: vec![MultiSigRequestAction::DeployContract { code: vec![1,2,3].into() }],
    };
    let r_id = c.add_request_and_confirm(deploy_request.clone());
    assert_eq!(c.get_confirmations(r_id).len(), 1);

    // Step 2: bob confirms R -> confirmations = {alice, bob}, count 2 < 3
    testing_env!(context_with_account(bob(), amount));
    c.confirm(r_id);
    assert_eq!(c.get_confirmations(r_id).len(), 2);

    // Step 3: remove bob via a separate fully-confirmed DeleteMember request
    testing_env!(context_with_account(alice(), amount));
    let delete_bob_req_id = c.add_request(MultiSigRequest {
        receiver_id: alice(),
        actions: vec![MultiSigRequestAction::DeleteMember {
            member: MultisigMember::Account { account_id: bob() },
        }],
    });
    c.confirm(delete_bob_req_id); // alice confirms 1
    testing_env!(context_with_key(key1_pk(), amount));
    c.confirm(delete_bob_req_id); // key1 confirms 2
    testing_env!(context_with_key(key2_pk(), amount));
    c.confirm(delete_bob_req_id); // key2 confirms 3 -> executes, bob removed

    // Assert: bob is no longer a member, but R's confirmations still contains bob's entry
    assert!(!c.get_members().contains(&MultisigMember::Account { account_id: bob() }));
    assert_eq!(c.get_confirmations(r_id).len(), 2); // stale {alice, bob} still present

    // Step 4: key1 (live member) confirms R -> count reaches 3 (2 stale/live mixed + 1), executes DeployContract
    testing_env!(context_with_key(key1_pk(), amount));
    let result = c.confirm(r_id);

    // BINDING CHECK: request executed (r_id removed) even though only {alice, key1} are live confirmers (2 < num_confirmations=3)
    assert!(c.requests.get(&r_id).is_none()); // request executed/removed
    // Live confirmer count at execution time was 2, not 3 -> invariant "confirmations >= num_confirmations among LIVE members" is violated
}
```
This demonstrates that a `DeployContract` request against the multisig account executes with confirmations from only 2 currently-live members while `num_confirmations` is configured to 3, confirming the vulnerability.

        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
