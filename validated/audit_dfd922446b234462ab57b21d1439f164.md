### Title
Node-side vote tally double-counts a signer's weight when its response for the same block flips from reject to accept, corrupting `total_weight_rejected`/`total_weight_approved` — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` (the node/miner-side coordinator that tallies signer weight per proposal) uses two independent guards — `responded_signers` for rejections and `gathered_signatures` for acceptances — to prevent double counting a signer's weight. These guards are only safe for the accept-then-reject ordering. For the reject-then-accept ordering (a legitimate, protocol-sanctioned transition — the signer state machine explicitly allows `LocallyRejected → LocallyAccepted` on re-evaluation of the same block), the signer's weight ends up counted in **both** `total_weight_rejected` and `total_weight_approved` for the same `signer_signature_hash`, with no code path decrementing the stale rejection. This inflates the tallied blocking-minority weight and can cause the miner to declare a block globally rejected (and exclude its transactions) even though the true, current rejecting weight never crossed the >30% threshold.

### Finding Description
`stacks-node/src/nakamoto_node/stackerdb_listener.rs` maintains a `BlockStatus` per `block_sighash` with `total_weight_approved`, `total_weight_rejected`, `responded_signers`, and `gathered_signatures`.

Acceptance handling always records the slot into both `gathered_signatures` and `responded_signers`, and adds weight guarded only by `gathered_signatures`: [1](#0-0) 

Rejection handling adds weight guarded only by whether the slot was already in `responded_signers`: [2](#0-1) 

If a signer's message order for this same block is **reject → accept** (permitted by the signer's own local state machine, whose `BlockState` explicitly allows `LocallyRejected → LocallyAccepted : re-evaluated`, per `docs/signer-flows.md`'s state diagram and the corresponding re-evaluation logic in `stacks-signer/src/v0/signer.rs`):
1. The reject message inserts the slot into `responded_signers` (`insert` returns `true`) and adds the signer's weight to `total_weight_rejected`.
2. The later accept message for the *same* `signer_signature_hash` checks only `gathered_signatures.contains_key(&slot_id)`, which is still `false` (only `responded_signers` was touched), so the signer's weight is *also* added to `total_weight_approved`.

Nothing subsequently removes the stale weight from `total_weight_rejected`. The only place `total_weight_rejected` is ever cleared is `reset_rejections`, which is explicitly invoked from the miner's own rejection-timeout retry loop, not in response to a per-signer flip: [3](#0-2) 

`get_block_status` in `stacks-node/src/nakamoto_node/signer_coordinator.rs` checks the rejection-crosses-blocking-minority condition against this uncorrected `total_weight_rejected` *before* checking the approval threshold: [4](#0-3) 

So one signer's now-superseded rejection remains permanently counted alongside its new acceptance, inflating apparent blocking weight for the life of that proposal (until an unrelated timeout retry happens to clear it).

### Impact Explanation
This breaks the equality between the node's aggregated `total_weight_rejected` and the set of signers who currently, validly reject the block ("aggregated-weight vs verified-accepts/rejects"). A stuck double-counted weight can push the tallied rejecting weight over the >30% blocking-minority threshold earlier than the true opinion set warrants, causing the miner to treat a block as globally rejected (`NakamotoNodeError::SignersRejected`), discard/exclude its transactions, and force an unnecessary re-mine cycle — a liveness degradation of the block-production pipeline that does not require a majority of colluding signers, only ordinary asynchronous message delivery from a single honest signer that re-evaluates its own decision (which the protocol explicitly permits).

### Likelihood Explanation
Reject→accept transitions for the *same* block are a normal, documented part of the signer's local re-evaluation logic (state re-checks after validation completes, chainstate re-checks at pre-commit threshold, etc.), and StackerDB message delivery/polling ordering is not guaranteed, so this ordering can occur under ordinary network conditions/gossip delay without any adversarial signer collusion — only timing.

### Recommendation
Track per-slot vote state explicitly (e.g., an enum `{Accepted, Rejected}` per slot rather than two independently-guarded sets/maps) and, when a slot transitions from Rejected to Accepted (or vice versa) for the same block, subtract the stale contribution from the previous bucket before adding it to the new one, keeping `total_weight_approved` and `total_weight_rejected` mutually exclusive and always reflecting the signer's current, live vote.

### Proof of Concept
1. Miner proposes block B; `StackerDBListener::insert_block` initializes `BlockStatus` for `sighash(B)`.
2. Signer S (weight w) rejects B for a transient reason (e.g., fails `check_block_against_signer_db_state` at that moment) — `handle` records `BlockResponse::Rejected`: `responded_signers.insert(S)` succeeds, `total_weight_rejected += w` (`stackerdb_listener.rs:515-518`).
3. S re-evaluates (e.g., on a subsequent pre-commit re-check per the documented `LocallyRejected → LocallyAccepted` transition) and broadcasts `BlockResponse::Accepted` for the *same* `sighash(B)`.
4. The listener's accept handler sees `gathered_signatures` does not yet contain S's slot, so it adds `total_weight_approved += w` and inserts S into both `gathered_signatures` and `responded_signers` (`stackerdb_listener.rs:443-465`).
5. `BlockStatus` for `sighash(B)` now shows S's weight counted in both `total_weight_rejected` and `total_weight_approved`; `get_block_status`'s rejection check (`signer_coordinator.rs:509-520`) uses the inflated `total_weight_rejected`, which — combined with other genuine rejecters near the 30% line — can trip the blocking-minority branch and cause the miner to declare B rejected even though S's current, live vote is acceptance.

    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
