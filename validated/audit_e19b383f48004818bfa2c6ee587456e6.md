### Title
View-role users can read a bridge's cleartext OutgoingToken via GET /v2/bridge_types/:BridgeName - ([File: core/web/bridge_types_controller.go])

### Summary
`BridgeTypesController.Show` returns `presenters.NewBridgeResource(bt)` unconditionally, and `BridgeResource.OutgoingToken` is serialized with a plain `json:"outgoingToken"` tag (no `omitempty`, no role check). Unlike `IncomingTokenHash` (which is never exposed), the `OutgoingToken` field is stored in cleartext on `BridgeType` and is returned in full to any authenticated caller who can hit the view-gated `Show`/`Index`/`Update`/`Destroy` endpoints.

### Finding Description
`core/bridges/bridge_type.go` shows that `BridgeType` persists `OutgoingToken` as cleartext (in contrast to `IncomingTokenHash`, which is a salted hash): [1](#0-0) 

`presenters.NewBridgeResource` copies this cleartext value directly into the response struct with no redaction and no `omitempty`: [2](#0-1) 

`BridgeTypesController.Show` (mapped to `GET /v2/bridge_types/:BridgeName`) fetches the bridge from the ORM and passes it straight into `NewBridgeResource` with no field-level access control or role-based filtering: [3](#0-2) 

The same unredacted resource is also returned by `Index`, `Update`, and `Destroy`: [4](#0-3) [5](#0-4) 

Since read endpoints (`Show`/`Index`) are only gated at the "view" role level in the router (per the audit's stated precondition and typical Chainlink RBAC where GET routes require the lowest privilege tier), a view-role authenticated user can call `GET /v2/bridge_types/:BridgeName` and receive the bridge's `outgoingToken` field in the JSON response body. This token is the credential the node uses to authenticate outbound EA callback requests, so its disclosure breaks the intended secret-confinement boundary between "read-only" and "admin" roles.

### Impact Explanation
Disclosure of the `OutgoingToken` lets a low-privilege (view-role) user impersonate the Chainlink node when it calls back to the external adapter, or replay/forge requests that the EA trusts as coming from the node — a credential/secret exposure impact. This matches the Chainlink bounty program's "unauthorized secret disclosure to a lower-privileged role" impact class.

### Likelihood Explanation
Fully feasible and repeatable: it requires only a valid session/API token with the view role (the lowest authenticated tier) and knowledge of (or ability to enumerate/list via `Index`) a bridge name. No admin, host, or database access needed. Any bridge created with an outgoing token is exposed to every view-role user who can read `/v2/bridge_types`.

### Recommendation
Redact `OutgoingToken` from `BridgeResource` for read paths (`Show`/`Index`), returning it only at creation time (as is already done for `IncomingToken`, which is only populated in `Create`). Consider adding `omitempty` and only populating `OutgoingToken` when serving `Create`, or restrict full-detail bridge reads to admin/edit roles; alternatively hash/encrypt `OutgoingToken` at rest similarly to `IncomingTokenHash` and never re-expose the plaintext after creation.

### Proof of Concept
Go handler-level integration test (in `core/web/bridge_types_controller_test.go` style):
1. Start test app/router with `cltest.NewApplication` and create a session/API token with role `view` (non-admin).
2. As an admin/setup step, create a bridge via `POST /v2/bridge_types` (or directly via `bridges.NewBridgeType` + `orm.CreateBridgeType`) capturing the generated `OutgoingToken`.
3. Using the view-role authenticated `httptest` client, issue `GET /v2/bridge_types/<bridgeName>`.
4. Assert HTTP 200 and parse the JSON body's `data.attributes.outgoingToken` field.
5. Assert that the returned `outgoingToken` equals the cleartext token generated in step 2 — proving disclosure to a view-role principal, and that no role/field redaction occurred despite `IncomingToken` correctly being absent (`omitempty`, only set on create).

// Index lists Bridges, one page at a time.
func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
