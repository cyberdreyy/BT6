### Title
`lending_pool_close_bank` permanently strands outstanding fees and vault balances - ([File: programs/marginfi/src/instructions/marginfi_group/close_bank.rs])

### Summary
The Velodrome report's root cause is that a lock/authority state (`lockedUntil`) is reset to zero *before* the value it gates (accrued swap fees) is transferred out, permanently orphaning the funds because the only claim path (`claimFees`, gated by `onlyLocked`) becomes permanently unreachable. The marginfi analog is `lending_pool_close_bank`, which closes (and deallocates) the `Bank` account without verifying that outstanding collected fees have been swept and without verifying that the `liquidity_vault`, `insurance_vault`, or `fee_vault` token accounts are empty. Since every fee-claiming instruction (`LendingPoolCollectBankFees`, `LendingPoolWithdrawFees`, `LendingPoolWithdrawFeesPermissionless`) requires the live `Bank` account to deserialize (`has_one = group`, Anchor discriminator/owner checks), once the `Bank` account is closed there is no remaining instruction path to reach the tokens still sitting in those vault PDAs.

### Finding Description
`lending_pool_close_bank` validates several invariants before closing the `Bank` account: [1](#0-0) 

It checks `CLOSE_ENABLED_FLAG`, zero position counts, zero total asset/liability shares, and zero `emissions_remaining` — but it never checks that `bank.collected_insurance_fees_outstanding`, `bank.collected_group_fees_outstanding`, or `bank.collected_program_fees_outstanding` are zero, and it never checks that the `liquidity_vault`, `insurance_vault`, or `fee_vault` token account balances are zero. The `bank` account is then closed and its rent returned to `admin`: [2](#0-1) 

As documented in the fee-collection guide, fees accrue into `collected_*_fees_outstanding` on the `Bank` struct and must be moved out via the permissionless `LendingPoolCollectBankFees` (moves accrued amounts from `liquidity_vault` into `insurance_vault`/`fee_vault`/`fee_ata`), followed by `LendingPoolWithdrawFees`/`LendingPoolWithdrawFeesPermissionless` (moves `fee_vault` contents to the destination): [3](#0-2) 

Both of these instructions require a live, correctly-owned `Bank` account: [4](#0-3) 

Once `lending_pool_close_bank` closes the `Bank` account (Anchor zeroes the data and transfers lamports to `admin`, so the account no longer has the Anchor discriminator/owner needed by `AccountLoader<'info, Bank>`), any subsequent `LendingPoolCollectBankFees` or `LendingPoolWithdrawFees(Permissionless)` call for that bank will fail at deserialization. Any tokens already sitting in `liquidity_vault` (uncollected interest/fees, since `total_asset_shares`/`total_liability_shares` are required to be zero but the vault can still hold un-swept fee tokens), any balance already sitting in `insurance_vault`/`fee_vault` that hasn't yet been withdrawn via `LendingPoolWithdrawFees`, or `collected_*_fees_outstanding` amounts recorded in the bank become permanently unreachable — the state (`Bank` account) that authorizes and drives the transfer was reset/removed before the value was swept out, exactly mirroring the `V2Locker.unlock()` bug pattern where `lockedUntil` is zeroed before fees are claimed.

### Impact Explanation
This is a durable financial freeze: SPL tokens legitimately owed to the insurance fund, group, or global fee wallet become permanently stuck in vault PDAs with no on-chain instruction able to move them, since the vault-draining instructions all require the (now-closed) `Bank` account. Depending on how much interest/fees accrued between the last `LendingPoolCollectBankFees`/`LendingPoolWithdrawFees` call and the bank closure, this can range from dust to a materially larger sum, and is unrecoverable without a program upgrade or manual intervention.

### Likelihood Explanation
`lending_pool_close_bank` is a normal, documented admin lifecycle operation (see `tests/specs/basic/13_closebank.spec.ts`) intended to be used once a bank has no more positions. Because interest/fee accrual runs on essentially every user interaction and can leave `collected_*_fees_outstanding` non-zero even after the last balance is withdrawn (interest can accrue up to the very last withdrawal transaction, and there is no requirement to run `LendingPoolCollectBankFees`/`LendingPoolWithdrawFees` before `close_bank`), it is plausible for an admin to close a bank while fees remain uncollected — especially since the instruction imposes no such requirement and gives no error/warning about outstanding balances.

### Recommendation
In `lending_pool_close_bank`, add checks that `collected_insurance_fees_outstanding`, `collected_group_fees_outstanding`, and `collected_program_fees_outstanding` are all zero (within `ZERO_AMOUNT_THRESHOLD`), and require that the `liquidity_vault`, `insurance_vault`, and `fee_vault` token account balances are zero (or automatically sweep/transfer any remaining balances to the appropriate destinations) before allowing the `Bank` account to close.

### Proof of Concept
1. Group admin creates a bank, users deposit and borrow, generating outstanding fees (`collected_insurance_fees_outstanding`, `collected_group_fees_outstanding`, `collected_program_fees_outstanding` > 0), some of which have accrued into `liquidity_vault` but not yet been swept to `insurance_vault`/`fee_vault` (i.e., `LendingPoolCollectBankFees` has not been called since the last interest accrual), or have been swept to `fee_vault`/`insurance_vault` but not yet withdrawn via `LendingPoolWithdrawFees`.
2. All users repay/withdraw fully so `total_asset_shares == 0`, `total_liability_shares == 0`, `lending_position_count == 0`, `borrowing_position_count == 0`, and `emissions_remaining == 0` — satisfying every check in `lending_pool_close_bank`. [5](#0-4) 
3. Admin calls `lending_pool_close_bank`. It succeeds because none of the fee/vault-balance conditions are checked; the `Bank` account is closed and rent returned to `admin`.
4. Any attempt to now call `LendingPoolCollectBankFees` or `LendingPoolWithdrawFees(Permissionless)` for this bank fails because the `bank: AccountLoader<'info, Bank>` account no longer exists/deserializes.
5. The SPL tokens still held in `liquidity_vault`, `insurance_vault`, and/or `fee_vault` PDAs (derived from the now-nonexistent bank's pubkey) remain on-chain but are permanently unreachable by any instruction in the program.

```markdown
## How Fees Are Collected

(1) Interset accrues and increases the number in `fees_outstanding` fields. Optionally, origination
fees are charged and do the same.

(2) Anyone (the ix is permissionless) runs `LendingPoolCollectBankFees`. This moves:
* The amount specified in `collected_insurance_fees_outstanding` from the `liquidity_vault` to the
  `insurance_vault`
* The amount specified in `collected_group_fees_outstanding` from the `liquidity_vault` to the `fee_vault`
* The amount specified in `collected_program_fees_outstanding` from the `liquidity_vault` to the
    `fee_ata`, which is the cannonical ATA of the global fee wallet.

Then the `fees_outstanding` are all reset to zero. The vast majority of the time, we run this ix just before a withdraw.

(3) The group admin runs `LendingPoolWithdrawFees`. This moves:
* The amount in `fee_vault` into any account of the group admin's choosing. 

(3a) If the group admin set a destination of choice with `LendingPoolUpdateFeesDestinationAccount`,
then anyone can run `LendingPoolWithdrawFeesPermissionless`, which does the same thing as
`LendingPoolWithdrawFees` but doesn't require permission, and always sends to the account defined by
the group admin (`bank.fees_destination_account`)
```
