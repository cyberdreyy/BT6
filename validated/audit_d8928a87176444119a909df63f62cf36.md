### Title
`VoteStateView::commission()` truncates basis points instead of rounding up, causing inconsistent/misreported commission percentages via account-decoding paths - ([File: vote/src/vote_state_view/field_frames.rs])

### Summary
`CommissionView::commission_percent()` in `vote/src/vote_state_view/field_frames.rs` converts a vote account's `inflation_rewards_commission_bps` (basis points, 0–10000) into a legacy `u8` percent using floor division (`bps / 100`), while every other place in the codebase that performs this exact conversion — `rpc/src/rpc.rs::get_vote_accounts()` and `account-decoder/src/parse_vote.rs::parse_vote()` — uses `bps.div_ceil(100)`. This mirrors the reported bug class ("wrong divisor/rounding constant used when converting a basis-points value to a legacy scale, causing misreported/incorrect values reachable from an unprivileged read path").

### Finding Description
`inflation_rewards_commission_bps` is a `u16` basis-points value (0–10000, i.e. 100 bps = 1%), introduced by SIMD‑0185/SIMD‑0291 alongside `VoteStateV4`. There are two independent code paths that derive the legacy 0–255 `commission` percent field from this bps value:

- `vote/src/vote_state_view/field_frames.rs::CommissionView::commission_percent()`:
```rust
let percent = (bps / 100).min(u8::MAX as u16);
percent as u8
``` [1](#0-0) 
This is exposed via `VoteStateView::commission()`: [2](#0-1) 

- `rpc/src/rpc.rs::get_vote_accounts()` (RPC `getVoteAccounts` handler) and `account-decoder/src/parse_vote.rs::parse_vote()` (used for `jsonParsed` account decoding, e.g. `getAccountInfo`, `getProgramAccounts`):
```rust
let bps = vote_state_view.inflation_rewards_commission();
bps.div_ceil(100).min(u8::MAX as u16) as u8
``` [3](#0-2) 
```rust
commission: vote_state
    .inflation_rewards_commission_bps
    .div_ceil(100)
    .min(u8::MAX as u16) as u8,
``` [4](#0-3) 

The dedicated unit test for the SIMD‑0185 conversion explicitly documents the expected rounding-up behavior and validates only the setter-side conversion (percent→bps, multiply by 100), not this getter-side truncation path: [5](#0-4) 

Any `inflation_rewards_commission_bps` value that is not an exact multiple of 100 (e.g. any value a validator can legitimately set after SIMD‑0185/0291 activation, such as 1%–99% expressed with finer granularity, or any arbitrary bps set by a malicious/careless validator) will produce a `commission_percent()` result from `VoteStateView::commission()` that is systematically **one lower** than what `getVoteAccounts` and `jsonParsed` `getAccountInfo`/`getProgramAccounts` report for the same account, because one path floors and the other ceils.

### Impact Explanation
`VoteStateView::commission()` is a general-purpose accessor used throughout the runtime/validator (e.g., commission-rate calculation call sites in `programs/vote/src/vote_state/mod.rs`, `programs/vote/src/vote_processor.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`). If any consumer of this legacy `u8` commission (as opposed to the raw bps field) relies on it for display or decision logic while another consumer (RPC/jsonParsed decoding) uses `div_ceil`, unprivileged RPC clients querying the same account state can observe inconsistent/incorrect commission percentages depending on which code path served the value — a decoder misreporting issue in the same class as the referenced report (wrong divisor/rounding when converting basis points to the legacy commission scale). This is a read-only display/decoding discrepancy; it does not directly cause funds loss, a crash, or a consensus-state mutation, so the impact is limited to "wrong data returned" for a percent field, not a critical fee-miscalculation like the original Solidity report (fee calculations in Agave use `inflation_rewards_commission_bps` and `commission_split`/`commission_split_preserve_lamports` directly, which correctly use the 10000 divisor, as verified in `runtime/src/inflation_rewards/mod.rs`).

### Likelihood Explanation
Any vote account with SIMD‑0185/0291 active and a commission_bps value not evenly divisible by 100 will trigger the discrepancy every time `VoteStateView::commission()` is called versus the RPC/`parse_vote` code path. Given `inflation_rewards_commission_bps` is a native `u16` field settable to arbitrary values, this is easily and reliably reproducible without any special privileges — a single unprivileged read/query is enough to observe the mismatch.

### Recommendation
Change `CommissionView::commission_percent()` in `vote/src/vote_state_view/field_frames.rs` to use `bps.div_ceil(100)` (matching `rpc.rs` and `parse_vote.rs`) instead of `bps / 100`, so that all commission-bps-to-percent conversions are consistent across the codebase.

### Proof of Concept
1. Set `inflation_rewards_commission_bps = 150` (1.5%) on a `VoteStateV4` account (achievable via `VoteStateHandler::set_commission`/SIMD-0185 v2 vote instructions once basis-points commission is active).
2. Call `VoteStateView::commission()` on the account → returns `150 / 100 = 1` (1%).
3. Query the same account via RPC `getVoteAccounts` or `getAccountInfo` with `jsonParsed` encoding → returns `150.div_ceil(100) = 2` (2%), per `rpc/src/rpc.rs` and `account-decoder/src/parse_vote.rs`.
4. The two "commission percent" values for the identical on-chain state differ, demonstrating the inconsistent/incorrect derivation from the same divisor bug class as the reported issue.

impl CommissionView<'_> {

            self.buffer[0]
        } else {

            let bps = u16::from_le_bytes(data);
            let percent = (bps / 100).min(u8::MAX as u16);
            percent as u8
        }
