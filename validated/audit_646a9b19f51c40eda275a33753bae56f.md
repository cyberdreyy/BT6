## Finding [1](#0-0) 

### Title
Miscounted signer weight tally lets a stale rejection and a later acceptance from the same signer both count toward `BlockStatus` totals - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` maintains two independent weight accumulators per proposed block, `total_weight_approved` and `total_weight_rejected`, gated by two different, non-synchronized guards (`gathered_signatures` for accepts, `responded_signers` for rejects). When a single signer sends a `Rejected` response before an `Accepted` response for the *same* block (a flow the signer explicitly supports via "reconsider a block proposal that it previously rejected"), the signer's weight is added to `total_weight_rejected` on the reject and then *also* added to `total_weight_approved` on the later accept, because the accept-path guard only checks `gathered_signatures`, not `responded_signers`. The stale rejection weight is never cleared. This is the same class of defect as the reported Deriverse bug: two accumulators meant to reflect a signer's current, mutually-exclusive vote end up double counted/out of sync because one path's update doesn't account for state already recorded by the other.

### Finding Description
`BlockStatus` ( [1](#0-0) ) tracks `responded_signers`, `gathered_signatures`, `total_weight_approved`, and `total_weight_rejected` per `signer_signature_hash`.

- On `BlockResponse::Rejected`, the code adds the signer's weight to `total_weight_rejected` guarded by `block.responded_signers.insert(slot_id)` (returns `true` only the first time this slot responds at all): [2](#0-1) 
- On `BlockResponse::Accepted`, the code adds the signer's weight to `total_weight_approved` guarded by `!block.gathered_signatures.contains_key(&slot_id)` — a *different* map — and then unconditionally inserts into both `gathered_signatures` and `responded_signers`: [3](#0-2) 

If a signer's `Rejected` message arrives first, `responded_signers` gets the slot and `total_weight_rejected` is incremented. If that same signer subsequently sends `Accepted` for the same block hash (legitimate reconsideration is a supported flow, per the signer's own changelog "For some rejection reasons, a signer will reconsider a block proposal that it previously rejected... (#5880)"), the accept branch's guard (`gathered_signatures`) is still false, so `total_weight_approved` is *also* incremented by that signer's weight. `total_weight_rejected` is never decremented to compensate. The two accumulators, which are supposed to reflect disjoint, mutually-exclusive per-signer votes, now both contain the same signer's weight — exactly the "redundant/unsynchronized state update" pattern from the external report, just split into two named accumulators instead of one being overwritten.

Note the asymmetry: if `Accepted` arrives first, `responded_signers` already contains the slot, so a later `Rejected`'s `responded_signers.insert(slot_id)` returns `false` and the reject weight is correctly *not* added — the bug is only present when the order is reject-then-accept.

### Impact Explanation
`SignerCoordinator::get_block_status`'s wait loop checks the rejection condition before the acceptance condition: [4](#0-3)  and [5](#0-4) . With the phantom, never-cleared rejection weight retained after that signer reconsiders and accepts, `total_weight_rejected` can cross the blocking-minority threshold (`total_weight_rejected + weight_threshold > total_weight`) purely due to stale data from one reconsidering signer, causing the coordinator to declare the block globally rejected (`NakamotoNodeError::SignersRejected`) even though the same signer's current, valid acceptance combined with everyone else's real acceptances would otherwise reach the 70% approval threshold. This is a miscounted-response bug that misclassifies signer consensus outcomes and can wedge liveness by forcing rejection/resubmission of blocks that legitimately reached quorum acceptance, triggerable by a single signer's normal reconsideration flow — no majority collusion required.

### Likelihood Explanation
The reject-then-accept ordering for the same block by the same signer is a documented, first-class supported behavior of the signer (reconsideration of prior rejections for certain reject reasons), so this is reachable in ordinary, non-adversarial operation whenever network delays or timing cause a signer's initial verdict to flip, and is trivially reachable by any single equivocating signer's own StackerDB messages (which are cryptographically its own and thus always "valid" to the coordinator).

### Recommendation
Track a single per-signer "current vote" (e.g., a map from slot_id to `Accepted`/`Rejected`), and when a signer's vote changes, subtract the weight from the previous category's accumulator before adding it to the new category's accumulator — mirroring how `signerdb.rs`'s `add_block_signature`/`add_block_rejection_signer_addr` already delete the opposing entry when a signer switches. Alternatively, guard both the accept and reject weight increments with the same `responded_signers`-style state and explicitly move weight between the two totals on a vote flip rather than only incrementing one side.

### Proof of Concept
1. Node proposes block `B`; three of the four signer weight units are needed for a 70% threshold.
2. Signer `S1` sends `BlockResponse::Rejected(B)` (e.g., timing-related rejection reason). `StackerDBListener` records `responded_signers={S1}`, `total_weight_rejected = weight(S1)`.
3. Signer `S1`'s local state re-evaluates and it now sends `BlockResponse::Accepted(B, sig)` (a supported reconsideration). `StackerDBListener`'s accept-path check `!gathered_signatures.contains_key(S1)` is true (S1 never accepted before), so `total_weight_approved += weight(S1)`. `total_weight_rejected` is left unchanged at `weight(S1)`.
4. Other signers `S2`, `S3` accept normally, pushing `total_weight_approved` to/above `weight_threshold`.
5. In `SignerCoordinator::get_block_status`, if any other signer(s) also rejected such that `total_weight_rejected (still including stale weight(S1)) + weight_threshold > total_weight`, the rejection branch fires first and the coordinator returns `NakamotoNodeError::SignersRejected` even though `total_weight_approved >= weight_threshold` was also true — the block is treated as rejected despite having reached real acceptance quorum, due to the uncleared stale rejection weight from `S1`.
