### Title
Builder can drain full balance via exit-triggered sweep withdrawal, leaving already-committed builder payments to proposers unbacked - (File: specs/gloas/beacon-chain.md)

### Summary
In the Gloas builder-payment design, a builder that has already committed to paying a proposer (via a winning `ExecutionPayloadBid`) can subsequently exit and let the automatic "builder sweep" withdraw its **entire** balance to its own `execution_address`, with no check against outstanding `state.builder_pending_withdrawals`/`state.builder_pending_payments` owed to fee recipients. When the previously-queued builder payment is later processed, `get_builder_withdrawals` emits a `Withdrawal` with the **full, unclamped** committed amount into the payload, while `apply_withdrawals` only debits `min(amount, builder.balance)` from the (now zero) builder balance. The execution layer is required to honor the committed withdrawal amount, so ETH is paid to the fee recipient with no corresponding balance ever deducted — a Gwei-creation / unbacked-payment bug, structurally identical to `MysteryBox::ownerWithdrawEarnm()` letting the owner rug the pool while liabilities (unclaimed boxes) remain outstanding.

### Finding Description
Builders are staked, self-registered actors tracked outside `state.validators`, with their own balance field `Builder.balance` [1](#0-0) .

When a builder wins a slot's bid, `process_execution_payload_bid` records a `BuilderPendingPayment` (not yet an actual withdrawal) for later settlement, without touching `builder.balance` immediately: [2](#0-1) 

One slot later, `apply_parent_execution_payload`/`settle_builder_payment` moves this commitment into `state.builder_pending_withdrawals` (a real, queued obligation to pay `fee_recipient`): [3](#0-2) [4](#0-3) 

Separately, a builder can request to exit, which only sets `withdrawable_epoch`: [5](#0-4) 

Once `withdrawable_epoch <= current_epoch`, `get_builders_sweep_withdrawals` automatically withdraws the builder's **entire balance** to `builder.execution_address` — this function performs no check whatsoever against `state.builder_pending_withdrawals` or `state.builder_pending_payments` still owed to third-party fee recipients for that same builder: [6](#0-5) 

Compare this to `get_builder_withdrawals`, which processes the FIFO queue of already-committed payments and emits `Withdrawal.amount = withdrawal.amount` **unclamped** to current balance (unlike every other withdrawal type in this file, which clamps to available balance, e.g. `min(balance - MIN_ACTIVATION_BALANCE, withdrawal.amount)` for validators): [7](#0-6) [8](#0-7) 

Finally, `apply_withdrawals` clamps only the **internal CL balance decrease**, not the amount already placed in the payload's committed withdrawals list: [9](#0-8) 

That same unclamped withdrawal list is what gets published as `state.payload_expected_withdrawals`, which the execution layer is obligated to apply verbatim (i.e., mint/transfer that exact amount to `address`): [10](#0-9) [11](#0-10) 

**The equality broken:** total Gwei paid out on the execution layer for a committed `Withdrawal` should equal the Gwei actually deducted from the paying account on the consensus layer. Because the builder sweep (`get_builders_sweep_withdrawals`) can zero out `builder.balance` with no regard to already-queued `builder_pending_withdrawals` for that builder, and `get_builder_withdrawals` never re-clamps its emitted `amount` to the builder's now-reduced balance, the CL commits to an EL payment that is no longer backed by any balance — Gwei is effectively created/paid to the fee recipient without a matching deduction anywhere in state.

### Impact Explanation
This matches the **Critical** category: "Gwei created, destroyed, or paid to a non-owner." A builder that has committed to a payment can walk away without paying it (or rather, the CL still instructs the EL to pay it despite there being no backing balance), producing an accounting mismatch between the consensus layer's tracked balances and the value the execution layer is required to mint. This directly parallels the original report's impact: the "owner" (the builder, controlling its own exit) can withdraw the pool's backing funds while a "mystery box" (the queued builder payment to the proposer/fee recipient) remains outstanding and is paid out anyway from thin air.

### Likelihood Explanation
This requires only the builder's own unilateral actions — submitting a bid (creating a `BuilderPendingPayment`) and later requesting its own exit — no coalition, no client bug, and no peer misbehavior. The main open question (which I could not fully verify given tool budget) is whether `process_builder_exit_request` itself imposes an additional check against `state.builder_pending_payments`/`state.builder_pending_withdrawals` before allowing the exit to be initiated. However, even if such a check existed at exit-request time, the automatic `get_builders_sweep_withdrawals` sweep executed every block thereafter (whenever `withdrawable_epoch <= current_epoch`) still has **no such check at withdrawal-processing time**, and does not coordinate with the separately-queued `builder_pending_withdrawals`/`builder_pending_payments` for the same builder, based on the retrieved code. The `MIN_BUILDER_WITHDRAWABILITY_DELAY` window gives time for outstanding payments to normally drain first (they are processed with priority ahead of the sweep in `get_expected_withdrawals`), but the FIFO queue (`state.builder_pending_withdrawals`) is shared across *all* builders and capped at `MAX_WITHDRAWALS_PER_PAYLOAD - 1` (15) entries drained per block; a sufficiently deep queue (whether from this builder's own multiple bids or congestion from many builders) can delay a specific builder's queued payment past the point its own sweep has already zeroed its balance.

### Recommendation
- In `get_builders_sweep_withdrawals`, subtract any amount still owed via `state.builder_pending_withdrawals` and non-empty `state.builder_pending_payments` for that builder before computing the sweep amount (i.e., only sweep `builder.balance - total_outstanding_commitments`), analogous to how the mystery box fix requires tracking total liability and only allowing withdrawal of the surplus.
- In `get_builder_withdrawals`, clamp the emitted `Withdrawal.amount` to `min(withdrawal.amount, builder.balance)` at the time it is placed into the payload (mirroring the clamp already applied inside `apply_withdrawals`), so the committed EL payment can never exceed the CL-tracked backing balance.
- Alternatively/additionally, have `initiate_builder_exit`/`process_builder_exit_request` reject or defer the exit while the builder has non-zero pending payments/withdrawals outstanding.

### Proof of Concept
1. Builder `B` submits `SignedExecutionPayloadBid` with `value = V` for slot `S`; `can_builder_cover_bid` passes since `B.balance >= V` at that time [12](#0-11) .
2. Block for slot `S` is processed; `process_execution_payload_bid` records `BuilderPendingPayment(amount=V)` for `B` [13](#0-12) .
3. In the same or a subsequent block, `B` submits a `BuilderExitRequest`, processed by `process_builder_exit_request`, setting `B.withdrawable_epoch = current_epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY` [5](#0-4) .
4. `settle_builder_payment` (called from `apply_parent_execution_payload`) moves the pending payment into `state.builder_pending_withdrawals` for `B` [3](#0-2) . Suppose the FIFO queue is congested with entries ahead of `B`'s (from other builders bidding in the same epochs), so `B`'s entry is not immediately drained.
5. Once `current_epoch >= B.withdrawable_epoch`, `get_builders_sweep_withdrawals` emits a `Withdrawal(amount=B.balance)` for `B`'s own `execution_address`, and `apply_withdrawals` sets `B.balance = 0` [6](#0-5) , [9](#0-8) .
6. When `B`'s queued entry in `state.builder_pending_withdrawals` (amount `V`, owed to the proposer's `fee_recipient`) is finally reached by `get_builder_withdrawals`, it still emits `Withdrawal(amount=V)` unclamped [7](#0-6) . `apply_withdrawals` computes `min(V, 0) = 0` for the CL balance change, but the payload's `Withdrawal(amount=V)` is unchanged and is included in `state.payload_expected_withdrawals`, which the execution layer must honor by paying `V` to `fee_recipient` — Gwei paid with no CL balance ever having backed it.

## Builder Model (PR #4788)

Builders are **separate non-validating staked actors** stored in
`state.builders[]`. They are NOT validators with special credentials.

**Key differences from validators**:

- Builders have their own registry (`state.builders`) separate from
  `state.validators`
- Builder balances are in `Builder.balance`, not `state.balances[]`
- Builders cannot be slashed
- Builders use `BuilderIndex` type, which is converted to/from `ValidatorIndex`
  using `convert_builder_index_to_validator_index()` and
  `convert_validator_index_to_builder_index()`
- In `Withdrawal` output, builder withdrawals use a converted validator index
  (with `BUILDER_INDEX_FLAG` bit set)

##### New `get_builder_withdrawals`

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

##### New `get_builders_sweep_withdrawals`

```python
def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
            withdrawal_index += 1

        builder_index = (builder_index + 1) % len(state.builders)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
