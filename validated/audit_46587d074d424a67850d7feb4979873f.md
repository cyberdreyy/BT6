### Title
Signer weight double-counted into both `total_weight_approved` and `total_weight_rejected` for a single signer's vote flip - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` (the miner-side coordinator tally that `SigningCoordinator`/`signer_coordinator.rs` polls to decide whether a block is approved or rejected) uses two different dedup keys for the same logical "has this signer already voted" question: the `Accepted` branch dedups against `gathered_signatures`, while the `Rejected` branch dedups against `responded_signers`. Because these are two distinct sets, a signer who first rejects a block and later signs an acceptance for the *same* block sighash has its weight added to `total_weight_rejected` **and then again** to `total_weight_approved`, even though `responded_signers` already recorded that slot as having responded.

### Finding Description
In `StackerDBListener::run` (stacks-node/src/nakamoto_node/stackerdb_listener.rs), the `Accepted` branch guards the weight increment with: [1](#0-0) 

```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```

while the `Rejected` branch guards the weight increment with: [2](#0-1) 

```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
```

If a given `slot_id` sends `Rejected` first (real, validly-signed rejection for `block_sighash`), `responded_signers.insert(slot_id)` returns `true` (first insertion) and `total_weight_rejected` is incremented. `gathered_signatures` is untouched by this branch.

If that same signer later reconsiders and sends a validly-signed `Accepted` for the identical `block_sighash` (a scenario the signer protocol explicitly supports via reconsideration of a rejection, i.e. the signer state machine can move from "rejected" to "accepted" for the same block), the `Accepted` branch checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (only `responded_signers` was populated by the prior rejection). The guard therefore passes and `total_weight_approved` is incremented too — while `total_weight_rejected` is never decremented or cleared. The signer's weight now sits in both totals simultaneously, and the stale rejection weight is never retracted.

This breaks the intended equality that `total_weight_approved` and `total_weight_rejected` reflect disjoint, mutually-exclusive weight from the current/latest vote of each signer for a given block. The `BlockStatus` these tallies live in is read directly by `SigningCoordinator::wait_for_signer_signatures_or_timeout` (stacks-node/src/nakamoto_node/signer_coordinator.rs), which checks the reject condition first each poll: [3](#0-2) 

```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ...
    return Err(NakamotoNodeError::SignersRejected { ... });
} else if block_status.total_weight_approved >= self.weight_threshold {
    ...
    return Ok(block_status.gathered_signatures.values().cloned().collect());
}
```

A stale, superseded rejection weight that should have been retracted when the signer later accepted can combine with other genuinely-rejecting signers' weight to cross the >30% blocking-minority threshold and abort the round with `SignersRejected`, even though the "current" vote set (excluding the stale reject) may not actually contain a genuine blocking minority. Conversely, because the check order evaluates rejection first, the same double-counted weight biases the outcome toward rejection rather than toward the (also inflated) approval path — either way, the aggregated weight tallies no longer equal the true, current set of accepting/rejecting signers.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality that the coordinator's threshold decision depends on: `total_weight_approved`/`total_weight_rejected` are supposed to represent disjoint weight contributions from the current position of each responding signer, but the code allows a single signer's weight to be counted in both buckets at once, with the stale rejection weight never retracted. This can cause the miner to declare `SignersRejected` for a block round that, judged by the signers' *current* votes, should not have crossed the blocking minority, degrading liveness for that block-signing round.

### Likelihood Explanation
Only requires one signer (its own StackerDB slot and its own key) to send a `Rejected` message and later a validly-signed `Accepted` message for the same `signer_signature_hash` — a sequence explicitly supported by the signer-side reconsideration logic (rejections can later be superseded by an acceptance for the same block once conditions change). No majority, no other signer's key, and no node/auth-token access is required; it is purely a bookkeeping bug in the miner's own StackerDB listener tally.

### Recommendation
Use a single shared guard (`responded_signers`, or an explicit per-slot "current vote" map keyed by `slot_id`) for both the `Accepted` and `Rejected` branches, and when a signer's vote flips (reject → accept or accept → reject) for the same block, subtract the old contribution from the previous tally before adding the weight to the new one, rather than only ever guarding the `Accepted` path against `gathered_signatures`.

### Proof of Concept
1. Miner proposes block `B` with sighash `H`; `StackerDBListener` tracks `BlockStatus` for `H` with `total_weight_approved = 0`, `total_weight_rejected = 0`, `responded_signers = {}`, `gathered_signatures = {}`.
2. Signer `S` (slot `k`, weight `w`) broadcasts `BlockResponse::Rejected` for `H` (e.g., transient local state mismatch). Listener processes it: `responded_signers.insert(k)` → `true` → `total_weight_rejected += w`.
3. `S` later re-evaluates (per the standard reconsideration path in `stacks-signer/src/v0/signer.rs`) and broadcasts a validly-signed `BlockResponse::Accepted` for the same `H`.
4. Listener processes the `Accepted` message: `gathered_signatures.contains_key(k)` is `false` (never touched by step 2) → weight guard passes → `total_weight_rejected` remains `w` (stale) AND `total_weight_approved += w`.
5. `S`'s weight `w` is now counted in both `total_weight_approved` and `total_weight_rejected` for block `H`, even though `S` has only one current, valid vote (accept). Depending on other signers' weight, this can push `total_weight_rejected` over the >30% blocking-minority threshold in `signer_coordinator.rs`, aborting the round with `SignersRejected`, using weight that should have been retracted once `S` accepted.
