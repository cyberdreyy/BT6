### Title
AP=0 withdraw-request bucket bricks `stopEpoch` permanently when APR later becomes non-zero — unprivileged user can freeze all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. Any unprivileged lender can arm this state for free by calling `requestWithdraw` while the pool runs at APR = 0. If the pool's APR is subsequently set non-zero (honest manager/`setAprsWithBuffer` at `startEpoch`, or `manager.setAprs`), every `stopEpoch` reverts and no epoch can ever be stopped or defaulted until APR is forced back to 0 — freezing every depositor's funds and blocking borrower repayment.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` routes requests to `_requestWithdrawApr0` whenever `unscaledApr == 0`, incrementing the global `apr0TotalPrincipal` and recording `apr0Users[_user].principalEpoch = epochNumber` (lines 285–286, 567–577).
- `prepareStopEpochWithApr0` (only callable by the CDO during `stopEpoch`) reverts if `apr0TotalPrincipal != 0 && unscaledApr != 0` (lines 499–508).
- `apr0TotalPrincipal` is only cleared at the end of that same function (line 540), so a revert leaves the poisoned state intact. The only other clears are `_clearWithdrawClaimForEpoch` (reachable only after a default is finalized — but `stopEpoch`/default handling itself reverts, so this is unreachable) and `_ensureDefaultRecoveryInitialized` (reverts while `pendingWithdraws != 0` unless the pool is already closed, lines 924–935).

There is no self-service path for a user to cancel an APR0 request, and `requestWithdraw` cannot clear `apr0TotalPrincipal`. Once `unscaledApr != 0`, `stopEpoch` → `prepareStopEpochWithApr0` always reverts before `apr0TotalPrincipal` is reset — a persistent state-dependent DoS analogous to the CVE's crafted-input NULL deref: a benign-looking input poisons a structure that a later mandatory code path dereferences unconditionally.

### Impact Explanation
All LP principal (AA and BB) is locked: no `stopEpoch`, no default finalization, no `claimWithdrawRequest` settlement of the armed bucket. Withdraw requesters' receipts cannot be funded because `stopEpoch` never runs. The freeze persists for as long as `unscaledApr != 0`; recovery requires the honest manager to set APR back to 0 and successfully stop the epoch, i.e. the pool cannot operate at any positive APR while the armed bucket exists. In a scenario where the operator needs a positive APR to service the borrower, this is effectively permanent freezing of all vault funds at the mercy of the armed bucket.

### Likelihood Explanation
The attack costs one minimal `requestWithdraw` transaction during any APR0 buffer/running epoch — the attacker only needs to pass the same KYC/allowance checks as any lender. The arming is invisible (`apr0TotalPrincipal` and `pendingWithdraws` both look like ordinary pending requests). The trigger — a non-zero APR while `apr0TotalPrincipal > 0` — arises from normal operations (manager repricing APR, or `setAprsWithBuffer` at the next `startEpoch` with a positive configured APR); the attacker does not need to time anything, the state stays armed indefinitely.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert when `unscaledApr != 0 && apr0TotalPrincipal != 0`. Instead settle the bucket conservatively — e.g. treat APR0 requests as normal requests when the APR changed after request time (`apr0TotalPrincipal = 0; apr0RateByEpoch[epochNumber] = 0`), or track per-request `aprAtRequest` and only apply APR0 settlement when it is still 0. Add a Foundry test covering: APR0 request → `setAprs(nonZero)` → `stopEpoch` must succeed.

### Proof of Concept
```solidity
// Foundry fork test sketch (existing harness: test/foundry/IdleCreditVault.t.sol)
function testApr0RequestBricksStopEpochAfterAprChange() external {
  // 1. Pool runs at APR = 0 (unscaledApr == 0). Attacker deposits AA and requests a withdraw.
  idleCDO.depositAA(1_000 * oneScale);           // attacker, KYC-passed lender
  cdoEpoch.requestWithdraw(smallTrancheAmount, address(aaTranche));
  assertGt(strategy.apr0TotalPrincipal(), 0);    // bucket armed

  // 2. Honest manager reprices to a non-zero APR mid-epoch (allowed: setAprs by manager).
  vm.prank(manager);
  strategy.setAprs(5e18, 5e18);

  // 3. Epoch ends; every stopEpoch reverts before apr0TotalPrincipal can be cleared.
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.expectRevert(NotAllowed.selector);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  // 4. Repeating while APR != 0 keeps reverting; all deposits and pending receipts stay frozen.
}
```

Note: I verified the revert and the absence of a clearing path inside `IdleCreditVault.sol`, but I could not read `IdleCDOEpochVariant.stopEpoch` to confirm `prepareStopEpochWithApr0` is invoked unconditionally on every stop path — the finding assumes it is called whenever the strategy has pending APR0 state, which the `_onlyIdleCDO` gating and function name strongly indicate.
