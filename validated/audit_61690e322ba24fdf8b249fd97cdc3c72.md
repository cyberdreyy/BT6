### Title
Funded instant-withdraw claims never clear the per-epoch receipt counters, enabling a double payout at default finalization - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Like the kernel bug (a refcount taken by `of_parse_phandle()` is never released on one exit path), `requestInstantWithdraw` "acquires" per-epoch receipt accounting — `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` — but the normal funded claim path `claimInstantWithdrawRequest` only clears the aggregate `instantWithdrawsRequests[_user]` and never releases the per-epoch counters. Those counters are later trusted verbatim by default-recovery accounting, so an already-paid claim is counted again as a defaulted receipt.

### Finding Description
`requestInstantWithdraw` records three pieces of state: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

The funded claim path clears only the aggregate: [2](#0-1) 

`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` are left at their full value — the "leaked refcount". They are only ever decremented inside `_claimDefaultedInstantWithdrawRequest` [3](#0-2) .

On borrower default, `finalizeDefaultRecovery` computes the claim basis via `defaultPendingClaimBasis()`, which adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [4](#0-3) . Because the stale entry was never released, the basis includes instant receipts that were already fully paid at par, so `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is depressed and every legitimate claimant's recovery is diluted.

The attacker then converts the leak into an outright second payout: after the funded claim, they place a new `requestInstantWithdraw` for the same amount, which re-mints `_amount` strategy-token receipts to them [5](#0-4) . When `claimInstantWithdrawRequest` runs post-finalization, `_claimDefaultedInstantWithdrawRequest` reads the never-cleared `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, burns the attacker's freshly minted receipt, and pays `claimBasis * defaultRecoveryPrice` from `defaultRecoveryReserve` a second time — one economic claim paid twice.

### Impact Explanation
Direct theft of recovery funds with a quantified loss. Concretely: attacker requests an instant withdraw of `X`, gets funded and claims `X` at par. They re-request `X` (fresh receipt). Borrower defaults and `finalizeDefaultRecovery` runs in the same epoch while some other instant request of `Y` remains unfunded (so `pendingInstantWithdraws != 0` and the instant bucket is included). `instantWithdrawClaimsByEpoch[epoch]` still contains the attacker's stale `X`, inflating the basis to `X + Y + ...` instead of `Y + ...`, so `defaultRecoveryPrice` drops and honest claimants lose up to `X/(X+Y)` of their entitled recovery. The attacker then claims `X * defaultRecoveryPrice` from `defaultRecoveryReserve` for a receipt they already redeemed — value comes directly out of the pool shared with defaulted-epoch withdraw requesters and active LPs.

### Likelihood Explanation
Requires an unprivileged user (only a KYC-allowed tranche holder calling `requestInstantWithdraw` via the CDO) plus a borrower default in the same epoch while at least one instant request stays unfunded — all sequencing is done by the honest manager/borrower (`collectInstantWithdrawFunds`, `stopEpoch`, `finalizeDefaultRecovery`), consistent with the threat model. The missing cleanup is unconditional on the funded claim path; no existing guard (`_onlyIdleCDO`, `defaultRecoveryFinalized` checks, `NotAllowed` reverts) touches the per-epoch counters on this path. The only nuance: the attacker must hold enough fresh receipt tokens to satisfy `_burn(_user, claimBasis)`, which the second `requestInstantWithdraw` provides.

### Recommendation
In `claimInstantWithdrawRequest`, on the funded path, release the per-epoch accounting the same way `_claimDefaultedInstantWithdrawRequest` does: for each epoch with a non-zero `instantWithdrawsRequestsByEpoch[_user][e]` (or at minimum `epochNumber`, since instant claims settle within their request epoch), set it to zero and subtract the claimed amount from `instantWithdrawClaimsByEpoch[e]`. This mirrors the kernel fix — every acquisition of the per-epoch "reference" must be paired with a release on every exit path.

Foundry fork PoC sketch (scaffold exists in `test/foundry/IdleCreditVault.t.sol`, e.g. `testClaimWithdrawRequestWithInstantDefault`):

```solidity
// setup: cdoEpoch + IdleCreditVault strategy, instant withdraws enabled,
// attacker = KYC'd LP holding AA tranches.

// epoch N running:
// 1) attacker: cdoEpoch.requestInstantWithdraw(X, AAtranche)
//    -> strategy.instantWithdrawsRequestsByEpoch(attacker, N) == X
//    -> strategy.instantWithdrawClaimsByEpoch(N) == X (+ victim's Y)
// 2) manager funds instant queue; attacker: cdoEpoch.claimInstantWithdrawRequest()
//    -> attacker paid X at par; instantWithdrawsRequests(attacker) == 0
//    -> BUG: instantWithdrawsRequestsByEpoch(attacker, N) still == X
//            instantWithdrawClaimsByEpoch(N) still == X + Y
// 3) attacker: requestInstantWithdraw(X) again (fresh receipt tokens minted)
// 4) borrower defaults; owner calls finalizeDefault(...) -> strategy.finalizeDefaultRecovery
//    assert: defaultPendingClaimBasis() includes attacker's stale X
//    -> defaultRecoveryPrice lower than honest value; capture pre/post
// 5) attacker: claimInstantWithdrawRequest()
//    -> _claimDefaultedInstantWithdrawRequest burns X receipt, pays
//       X * defaultRecoveryPrice from defaultRecoveryReserve
// assert attacker total received > X (par) + fair share of second request;
// assert victim's recovery < their entitlement (dilution quantified).
```

Key assertions: `instantWithdrawsRequestsByEpoch[attacker][N]` remains non-zero after step 2, `instantWithdrawClaimsByEpoch[N]` over-counts basis at step 4, and `defaultRecoveryReserve` decreases by the double-paid amount at step 5.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
