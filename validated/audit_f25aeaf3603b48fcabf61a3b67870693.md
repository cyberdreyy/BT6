### Title
Cache archive/extract path traversal via unsanitized cache `Key` in `cacheArchivePath` - ([File: functions/concrete/run/stages/cache_archive.go])

### Summary
`cacheArchivePath` builds the local cache archive path with `filepath.Join(e.CacheDir, key, "cache.zip")` and never validates that the resulting path stays under `e.CacheDir`. Both `CacheArchive.Run` and `CacheExtract.extract` (via `CacheSource.Key`) call this helper with the job's cache key, so a key containing `../` segments can make the archiver/extractor read or write outside the intended cache directory.

### Finding Description
`cacheArchivePath` in `functions/concrete/run/stages/cache_archive.go` performs: [1](#0-0) 
`filepath.Join` calls `filepath.Clean`, which lexically resolves `..` segments without any bounds checking against `e.CacheDir`. If `key` is e.g. `../../other-project/cache`, the resulting `absPath` can point completely outside `e.CacheDir`. The function only computes a path relative to `e.WorkingDir` for convenience — it performs no `strings.HasPrefix`/`filepath.Rel`-against-`CacheDir` containment check.

This function is invoked from two places:
- `CacheArchive.archivePath` / `alternateArchivePath`, used to build the `--file` argument passed to the `cache-archiver` helper command: [2](#0-1) 
- `CacheExtract.archivePath`, used identically for `cache-extractor`: [3](#0-2)  and [4](#0-3) 

These `CacheArchive`/`CacheExtract` steps are produced by `stagesToConcreteStep` in `common/build_step_dispatch.go`, which calls `builder.Build(build.Job, build.GetAllVariables(), ...)` to generate the concrete step-runner configuration when `UseConcrete`/step-runner dispatch is active: [5](#0-4) 

The cache `Key` value ultimately originates from the job's `.gitlab-ci.yml` `cache:key` (or per-cache-entry key), which supports variable expansion and is fully controllable by the pipeline author — no special privilege beyond authoring/triggering a pipeline is required. I was unable to fully trace the exact assignment site of `Key`/`AlternateKey` inside `functions/concrete/builder/builder.go` (the tool budget ran out before locating the precise code that copies the cache key from `Job` into `CacheArchive.Key`/`CacheSource.Key`), so I cannot confirm with certainty whether any hashing or character-restriction is applied there (e.g. under `FF_HASH_CACHE_KEYS`) before the key reaches `cacheArchivePath`. This is a real gap in verification.

### Impact Explanation
If the cache key reaches `cacheArchivePath` unsanitized, a job can direct the cache-archiver/extractor helper to write or read a `cache.zip` file at an attacker-chosen filesystem location outside `e.CacheDir`, rather than only within the intended per-project/per-key cache subtree. On setups where `CacheDir` is a shared host path across concurrent jobs from different projects (e.g. shared runner with host-mounted local cache), this could allow reading another project's cached archive or overwriting it. The exact blast radius (whether it crosses actual project/tenant boundaries or stays inside a per-job sandboxed filesystem) depends on executor and cache configuration, which I could not fully confirm from available code.

### Likelihood Explanation
The precondition (attacker controls the cache `Key`) is plausible since `cache:key` in `.gitlab-ci.yml` is author-controlled and supports variable expansion, requiring no elevated privilege. Exploitability depends on whether `builder.Build` applies any key normalization/hashing before populating `CacheArchive.Key`/`CacheSource.Key` — a point this audit could not conclusively verify given the tool budget. If no such normalization exists, the traversal is trivially reproducible.

### Recommendation
Add explicit containment validation in `cacheArchivePath`: after `filepath.Join`, verify the resulting absolute path is still lexically within `e.CacheDir` (e.g. using `filepath.Rel` and rejecting results starting with `..` or being absolute), and reject/sanitize keys containing path traversal sequences before they reach this function — independent of whatever validation may or may not exist upstream in `builder.go`.

### Proof of Concept
```go
func TestCacheArchivePath_RejectsTraversal(t *testing.T) {
    e := &env.Env{CacheDir: "/builds/proj/cache", WorkingDir: "/builds/proj"}
    got := cacheArchivePath(e, "../../other-project/secret")
    rel, err := filepath.Rel(e.CacheDir, filepath.Join(e.WorkingDir, got))
    require.NoError(t, err)
    assert.False(t, strings.HasPrefix(rel, ".."), "archive path escaped CacheDir: %s", got)
}
```
Expected (current) result: assertion fails, demonstrating the archive path resolves outside `CacheDir` when `Key` contains `../` segments.

func cacheArchivePath(e *env.Env, key string) string {
	absPath := filepath.Join(e.CacheDir, key, "cache.zip")
	rel, err := filepath.Rel(e.WorkingDir, absPath)
	if err != nil {
		return absPath
	}
	return rel
}
