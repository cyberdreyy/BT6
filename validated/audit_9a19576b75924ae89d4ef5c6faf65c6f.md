### Title
Unbounded, duplicate-tolerant `topics` array in web-api-trigger's `HandleGatewayMessage`/`processTrigger` enables DoS via gateway-forwarded requests - (File: core/capabilities/webapi/trigger/trigger.go)

### Summary
The web-api-trigger capability's `triggerConnectorHandler.processTrigger` accepts a user/gateway-supplied `payload.Topics` array with no upper bound on length and no duplicate check, then iterates it in a nested loop over all `h.registeredWorkflows`, performing rate-limit checks, execution-ID generation, and event emission for every match. This mirrors the reported liquidity-proxy bug class: an unvalidated, unbounded vector accepted from an unprivileged path drives O(workflows × vector-length) work with no cost accounting.

### Finding Description
`HandleGatewayMessage` unmarshals a gateway-relayed `webapicap.TriggerRequestPayload` (whose JSON schema only requires `topics` be an array of strings, with no `maxItems` or uniqueness constraint) and passes it directly to `processTrigger`: [1](#0-0) 

`processTrigger` only checks that `topics` is non-empty — it does not cap the length or reject duplicate entries — and then iterates every registered workflow against every topic in the request: [2](#0-1) 

The JSON schema backing `TriggerRequestPayload.topics` confirms there is no size or uniqueness constraint enforced at validation time: [3](#0-2) 

For each `(workflow, topic)` match, the handler performs an execution-ID generation, an event emission, and (for fully-matched entries) a blocking channel send with sender-based rate limiting checked per topic occurrence rather than once per request: [4](#0-3) 

Sending the same allowed topic thousands of times in one request multiplies the per-workflow work identically to how the liquidity-proxy bug allowed a single `selected_source_types` vector with duplicate/excess entries to multiply `generic_split` work inside one `swap` call — the cost of the request is not bounded by, or charged for, the size of the attacker-controlled array.

### Impact Explanation
A single external web-api-trigger POST can carry an arbitrarily large `topics` array (bounded only by generic message-size limits elsewhere in the gateway/connector layer, if any — not verified in this handler). Each entry causes an iteration across every registered workflow on the node, each doing map lookups, rate-limiter calls, execution-ID hashing, and event emission calls. Repeated or many such requests can consume disproportionate CPU/goroutine time on the capability node, degrading trigger processing for all workflows registered on that node — a denial-of-service condition analogous to the reported swap-extrinsic spam vector, though scoped to this capability node's trigger-processing loop rather than full network consensus.

### Likelihood Explanation
The `topics` field is fully attacker-controlled JSON input reachable from an unauthenticated/low-trust external actor via the gateway (`HandleGatewayMessage` is registered against the "web_api_trigger" method and invoked for any gateway-relayed message). No authentication step gates the size of this field before `processTrigger` runs; only sender-address / rate-limit checks occur, and those are evaluated per-topic-per-workflow-match rather than up front, so the expensive iteration happens before any check can short-circuit it for unmatched or duplicate topics. This is a low-effort, low-cost trigger available to any client capable of sending gateway messages to the web-api-trigger capability.

### Recommendation
- Enforce a maximum length on `TriggerRequestPayload.topics` (both at the JSON-schema level with `maxItems` and defensively in `processTrigger`) before entering the workflow-matching loop.
- De-duplicate `topics` before iterating so an attacker cannot fan out identical work by repeating the same value.
- Consider capping/accounting for the number of matched-workflow × topic combinations processed per request, and short-circuit once rate limits are exceeded rather than continuing to iterate.
- Add tests that submit an oversized or duplicate-heavy `topics` array and assert the handler rejects it early rather than performing proportional work.

### Proof of Concept
1. Register one or more workflows via `RegisterTrigger` with a config containing at least one entry in `AllowedTopics`.
2. Send a gateway message routed to `triggerConnectorHandler.HandleGatewayMessage` with method `web_api_trigger`, whose `body.Payload` decodes to a `webapicap.TriggerRequestPayload` where `Topics` is a large array (e.g., 100,000 entries) — either all equal to an allowed topic (to also multiply through the rate-limiter/emit path) or a mix of allowed and junk values (to still force the outer/inner loop to iterate fully before returning `no Matching Workflow Topics` in the worst case).
3. Observe the handler performs `len(registeredWorkflows) × len(topics)` map lookups and, for matching entries, per-entry rate-limit checks and `events.EmitTriggerExecutionStarted` calls, all driven by a single unauthenticated request — with no length or duplicate validation rejecting the request beforehand.

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

	switch body.Method {
	case ghcapabilities.MethodWebAPITrigger:
		resp := h.processTrigger(ctx, gatewayID, body, sender, payload)
		var response ghcapabilities.TriggerResponsePayload
		if resp == nil {
			response = ghcapabilities.TriggerResponsePayload{Status: "ACCEPTED"}
		} else {
			response = ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: resp.Error()}
			h.lggr.Errorw("Error processing trigger", "gatewayID", gatewayID, "body", body, "response", resp)
		}
		err = h.sendResponse(ctx, gatewayID, body, response)
		if err != nil {
			h.lggr.Errorw("Error sending response", "body", body, "response", response, "err", err)
		}
		return nil
