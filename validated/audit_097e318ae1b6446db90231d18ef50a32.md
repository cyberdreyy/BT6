### Title
Path-escape via glob pattern segment reattached after project-boundary check bypasses `../` validation - ([File: commands/helpers/file_archiver.go])

### Summary
`fileArchiver.findRelativePathInProject` validates that a path stays inside the working directory only against the *base* portion returned by `doublestar.SplitPattern`, but then re-appends the raw, unvalidated pattern portion (`patt`) via `filepath.Join`, which lexically cleans and can resolve `../` sequences embedded in `patt` to escape the working directory after the check has already passed.

### Finding Description
In `commands/helpers/file_archiver.go` (`findRelativePathInProject`, lines 191-222), when the `--path`/`--exclude` value contains a doublestar meta-character (`*?[{`), the function splits it into `base` (meta-char-free directory prefix) and `patt` (the remainder, which can itself contain `..` segments following the first meta-character) via `doublestar.SplitPattern`. Only `base` is resolved to an absolute path and checked against the working directory with `strings.HasPrefix(rel, ".."+string(filepath.Separator))` (lines 203-216) [1](#0-0) . After that check passes, the function does `rel = filepath.Join(rel, patt)` (line 219) [2](#0-1) . `filepath.Join` calls `Clean`, which lexically resolves any `..` components in `patt` against `rel`, and since `patt` was never subjected to the escape check, a pattern such as `*/../../etc/passwd` splits to `base="."` (validated, resolves to `wd`, passes) and `patt="*/../../etc/passwd"`, and the final `filepath.Join(".", patt)` cleans to `../etc/passwd` — a path outside the working directory that was never checked. This resulting `rel` is then fed straight into `doublestar.FilepathGlob` in `processPath` (lines 152-164), which will glob-expand against the filesystem outside the build directory. The two glob-related meta-character checks (`isExcluded`'s use of the same function, and the boundary check in `process` for the *results* of matches) do not cover this specific construction because the boundary validation only inspects `base`, not the effective final path after `patt` is appended.

### Impact Explanation
An unprivileged pipeline author who controls the `artifacts:paths` or `artifacts:exclude` (both flow into `fileArchiver.Paths`/`Exclude`, ultimately `--path`) can craft a value like `*/../../<sensitive-path>` to make the archiver glob and include files located outside the job's working directory into the artifact archive uploaded to GitLab, or exfiltrate build-host files outside the intended build root. This violates the invariant that "file operations must stay within intended build/cache/artifact roots."

### Likelihood Explanation
Feasible with a normal CI job: the attacker only needs to control the `artifacts:paths` list in `.gitlab-ci.yml`, which is fully within an unprivileged pipeline author's control. No special executor privileges, admin access, or leaked credentials are required — this is directly reachable through documented job configuration fields.

### Recommendation
Re-validate (or re-derive) the escape check *after* `filepath.Join(rel, patt)` is computed, not only against `base`. Concretely, after line 219, re-run the same `strings.HasPrefix`/`rel == ".."` check (or use `filepath.Rel(c.wd, filepath.Join(abs, patt))` and validate that) before returning `rel`, so that `..` segments hidden inside the glob-pattern suffix cannot escape the working-directory boundary.

### Proof of Concept
Go unit test to add to `commands/helpers/file_archiver_test.go`:
```go
func TestFindRelativePathInProject_GlobEscapesWorkingDir(t *testing.T) {
    wd, err := os.Getwd()
    require.NoError(t, err)

    c := &fileArchiver{wd: wd}

    rel, err := c.findRelativePathInProject("*/../../etc/passwd")
    require.NoError(t, err) // currently succeeds - should instead error

    // Assert the bug: rel escapes the working directory despite the check
    // that was supposed to prevent exactly this.
    assert.True(t, strings.HasPrefix(rel, ".."+string(filepath.Separator)),
        "expected escaped path to be rejected, got: %s", rel)
}
```
Expected (fixed) behavior: `findRelativePathInProject` should return an error ("artifact path is not a subpath of project directory") for this input, matching the behavior already enforced for non-glob paths like `../etc/passwd`. Currently (per code review) the function returns `../etc/passwd` without error, confirming the check is bypassed for the glob+`../` combination.

**Note on verification confidence:** I was unable to locate the vendored/go-module source of `bmatcuk/doublestar/v4.SplitPattern` inside this repository (only the import is present in `file_archiver.go`; the dependency's own source is not indexed here), so the exact split boundaries for every meta-character/`../` combination could not be directly inspected in this environment. The exploit logic above is based on the documented/standard `SplitPattern` semantics (splitting at the last separator before the first meta character, leaving any subsequent `..` segments inside `patt`) combined with the observable `filepath.Join`/`Clean` semantics in `findRelativePathInProject`. Confirming this with the actual PoC test run (or reading the vendored `doublestar` source directly) is recommended to fully validate the exact bypass string before treating this as fully confirmed.
