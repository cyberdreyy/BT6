Confirmed: `DstImmutablesComplement` is never read back anywhere except in test files — it is purely an emitted event payload, never used on-chain to validate what actually gets deployed via `createDstEscrow`. That confirms there is no on-chain linkage between the source-committed fee amounts and the destination escrow's actual fee parameters.

### Title
Unvalidated destination fee parameters in `createDstEscrow` allow the depositor to zero out protocol/integrator fees committed on the source chain - (File: contracts/BaseEscrowFactory.sol)

### Summary
`createDstEscrow` accepts `IBaseEscrow.Immutables calldata dstImmutables` directly from an unprivileged caller, including the `parameters` field that encodes `protocolFeeAmount` and `integratorFeeAmount`. There is no on-chain check tying these values to the fee amounts computed and committed on the source chain (via `FeeTaker._getFeeAmounts` in `_postInteraction`, emitted as `DstImmutablesComplement.parameters` in `SrcEscrowCreated`).

### Finding Description
On the source chain, `_postInteraction` computes `integratorFeeAmount`/`protocolFeeAmount` from the maker-signed order via `FeeTaker._getFeeAmounts` and only enforces `integratorFeeAmount + protocolFeeAmount < takingAmount` [1](#0-0) . These amounts are packaged into `DstImmutablesComplement.parameters` and emitted for off-chain reconstruction [2](#0-1) , but that struct is never persisted or referenced again on-chain.

On the destination chain, `createDstEscrow` takes the entire `Immutables` struct — including `parameters` — straight from calldata, and only validates the native-token amount actually sent (`msg.value == safetyDeposit (+ amount if native)`); it never checks that `dstImmutables.parameters` matches the fee amounts committed on the source chain [3](#0-2) .

When `EscrowDst._withdraw` runs, it reads `integratorFeeAmount`/`protocolFeeAmount` straight out of these attacker-supplied `parameters` bytes and only forwards fee payments if they are nonzero, sending the remainder to the maker: [4](#0-3) . Since `parameters` is arbitrary calldata with no cross-chain enforcement, whoever calls `createDstEscrow` can simply encode `protocolFeeAmount = 0` and `integratorFeeAmount = 0`, permanently denying the protocol and integrator the fee revenue that was supposed to be paid on the destination side, regardless of what the maker's signed source order committed to.

### Impact Explanation
This is a permanent loss of unclaimed fee-like value for the protocol and integrator — matching the bounty's High-severity category ("theft or permanent loss of unclaimed fee-like value"). Unlike the source chain, where the maker's signature over the order (validated through `FeeTaker`) protects the committed fee schedule, the destination-chain fee amounts have no cryptographic or on-chain binding to that commitment, so they can be unilaterally zeroed by whoever deploys the destination escrow.

### Likelihood Explanation
`createDstEscrow` is a public, permissionless function (no whitelist gating, unlike some parts of the source-fill path) [5](#0-4) . Any resolver/depositor benefits directly by minimizing the fee they pay out, so there is a direct economic incentive to set these to zero every time, on every destination-chain fill — this requires no privileged role, no governance action, and no race condition; it's a straightforward parameter-crafting attack available on every single swap.

### Recommendation
Bind the destination escrow's fee parameters to the source-chain commitment on-chain rather than trusting caller-supplied `parameters`. Options: (1) have `createDstEscrow` derive/validate `protocolFeeAmount`/`integratorFeeAmount` against a value hashed/stored from `SrcEscrowCreated` (e.g., store the `dstImmutablesComplement.parameters` hash keyed by `orderHash` during `_postInteraction` and require the caller of `createDstEscrow` to supply matching values), or (2) have the factory recompute fee amounts itself from trusted state rather than accepting them as arbitrary calldata.

### Proof of Concept
1. Maker signs a source order via LOP specifying nonzero `protocolFee`/`integratorFee` (as configured in `extraData`).
2. Resolver fills the order; `_postInteraction` computes real `protocolFeeAmount`/`integratorFeeAmount` and deploys `EscrowSrc`, emitting `SrcEscrowCreated` with these amounts in `dstImmutablesComplement.parameters`.
3. Resolver calls `BaseEscrowFactory.createDstEscrow` on the destination chain, but instead constructs `dstImmutables.parameters` with `protocolFeeAmount = 0` and `integratorFeeAmount = 0` (any values are accepted; only `msg.value` matching `safetyDeposit (+amount)` is checked) [6](#0-5) .
4. `EscrowDst` is deployed with these zero-fee immutables; when the maker/taker calls `withdraw`, `_withdraw` skips both fee transfers (`integratorFeeAmount > 0` / `protocolFeeAmount > 0` checks are false) and sends the full `amount` to the maker [7](#0-6) .
5. Protocol and integrator permanently receive zero fee for this swap, despite the source order committing to nonzero fees.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
