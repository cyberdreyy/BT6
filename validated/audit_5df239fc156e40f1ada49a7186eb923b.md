### Title
Stale-epoch instant-withdraw receipts escape the default-recovery haircut and are paid at par, draining the recovery reserve / freezing other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest` only account for instant-withdraw receipts recorded in `instantWithdrawClaimsByEpoch[epochNumber]` / `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, i.e. the single epoch in which the default is finalized. An instant receipt requested in an earlier epoch that remains (partially) unfunded across a `stopEpoch` keeps its basis in the old epoch bucket, is excluded from the haircut basis, and is later paid at par through `_transferFundedClaim` in `claimInstantWithdrawRequest`.

### Finding Description
- `requestInstantWithdraw` records receipts per request epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (`IdleCreditVault.sol:367-374`).
- At default finalization, `defaultPendingClaimBasis` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the current epoch — even though `pendingInstantWithdraws` is a global remainder that may cover receipts from older epochs (`IdleCreditVault.sol:644-649`). `_defaultPrefundedInstantReserve` likewise only nets the current-epoch basis (`IdleCreditVault.sol:716-723`).
- After finalization, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (`IdleCreditVault.sol:842-856`). Any basis the same user holds in an earlier epoch stays in `instantWithdrawsRequests[_user]` and is then paid in full by `_burn(_user, amount)` + `_transferFundedClaim(_user, amount)` (`IdleCreditVault.sol:387-392`).
- `_transferFundedClaim` only protects `defaultRecoveryReserve` (`balance - reserve < amount` reverts, `IdleCreditVault.sol:897-907`). It does not know that the stale-epoch receipt was never funded nor haircut.
- Broken invariant: "one receipt, one payout, uniformly haircut". The recovery reserve and prefunded instant cash are sized for `totalBasis = activeBasis + pendingBasis` where the stale instant basis is missing, so paying it at par either (a) consumes underlyings reserved for defaulted-epoch claimants once the guard's arithmetic is satisfied by prefunded funds, or (b) reverts when `balance - reserve < amount`, permanently freezing the attacker's *and* subsequent claimants' payouts behind the same reserve accounting.

### Impact Explanation
Direct theft / permanent freezing with quantified loss: a stale-epoch instant receipt of `X` is paid `X` instead of `X * defaultRecoveryPrice / 1e18`. Every defaulted-epoch claimant (normal, instant, post-default) is shorted pro-rata because the reserve was computed on a basis that excluded `X`; equivalently, if the funded-claim guard trips, claims revert and recovery funds are stuck. Loss magnitude is bounded by the stale receipt size, which an attacker controls by sizing their instant withdraw.

### Likelihood Explanation
Requires instant withdraws enabled (`allowInstantWithdraw`), an instant request that stays partially unfunded across one `stopEpoch` (occurs whenever `getInstantWithdrawFunds` collects less than `pendingInstantWithdraws`, e.g. borrower liquidity shortfall — no privileged misbehavior needed), and a subsequent borrower default finalized via `finalizeDefault`. All are normal, honest-actor protocol sequences; the attacker is an ordinary KYC'd tranche holder.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, aggregate instant claim basis across all epochs with unfunded receipts (or track a global unfunded instant basis rather than only `instantWithdrawClaimsByEpoch[epochNumber]`). In `_claimDefaultedInstantWithdrawRequest`, haircut the user's *entire* remaining `instantWithdrawsRequests[_user]` basis that was unfunded at default, not only the `defaultRecoveryEpoch` bucket, so stale-epoch receipts cannot bypass the recovery price.

### Proof of Concept
Source-level trace (Foundry fork PoC sketch):
1. Manager enables instant withdraws; attacker deposits AA and calls `cdoEpoch.requestInstantWithdraw` in epoch N → `instantWithdrawsRequestsByEpoch[attacker][N] = X`, `pendingInstantWithdraws = X`.
2. Borrower under-funds: `getInstantWithdrawFunds` collects `< X`; `pendingInstantWithdraws` stays non-zero; `stopEpoch`/`startEpoch` roll to epoch N+1 while `instantWithdrawClaimsByEpoch[N]` still holds `X`.
3. Epoch N+1: borrower defaults → `finalizeDefault(recovered, source)`. `defaultPendingClaimBasis` misses `X`; reserve/price are computed too low.
4. Attacker calls `claimInstantWithdrawRequest`: `_claimDefaultedInstantWithdrawRequest` finds `instantWithdrawsRequestsByEpoch[attacker][N+1] == 0` → no haircut; `instantWithdrawsRequests[attacker] = X` is burned and `X` is transferred at par via `_transferFundedClaim`.
5. Assert other claimants recover `< claimBasis * defaultRecoveryPrice / 1e18` (or their claims revert on the reserve guard), i.e. reserve insolvency equal to `X * (1 - defaultRecoveryPrice/1e18)`.

Uncertainty: confirmed by code analysis of `IdleCreditVault.sol` only; I could not fully read `IdleCDOEpochVariant.sol` to confirm nothing at the CDO layer blocks `claimInstantWithdrawRequest` when a user's basis spans epochs — if the CDO reverts on partial-funding states the impact degrades to the freezing variant, which is still a valid finding.
