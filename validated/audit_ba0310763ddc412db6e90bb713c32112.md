### Title
Stale Confirmations from Removed Multisig Members Still Count Toward Execution Threshold - (File: multisig2/src/lib.rs)

### Summary
In the multisig2 contract, when a member is removed via `DeleteMember`, only the pending *requests that member authored* are purged. Confirmations that member previously cast on *other* still-pending requests are never removed from the `confirmations` map, and `confirm()` never re-validates that the members recorded in a request's confirmation set are still current members. As a result, a removed member's stale confirmation continues to count toward `num_confirmations`, allowing a request to execute with fewer live-member approvals than the configured threshold requires — the same class of bug as the reported RFQ issue, where a state transition (member removal / RFQ confirmation) was not propagated into the check that gates a later privileged action (request execution / RFQ cancellation).

### Finding Description
`delete_member` only cleans up requests whose *author* (`r.member`) matches the removed member: [1](#0-0) 

It does not scan the `confirmations: LookupMap<RequestId, HashSet<String>>` map for entries containing the removed member's identity string on requests authored by *other* members. Those confirmations are left in place.

`confirm()` counts confirmations purely by set size against `self.num_confirmations`, without re-checking that every entry in the set still corresponds to a current member: [2](#0-1) 

`assert_valid_request` (called by both `confirm` and `delete_request`) only validates that the *caller* is a current member and that the request/confirmation entries exist — it never re-validates the historical confirmers: [3](#0-2) 

The binding that should hold is: `confirmations counted toward num_confirmations == confirmations from members who are still live at execution time`. Because stale entries are never purged or re-validated, this equality is silently broken once any confirmer is later removed from membership — mirroring the RFQ bug where `cancel_access_control` failed to re-check the `confirmed` state that had changed since the check was first designed.

The identical pattern exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` only purges requests where `r.signer_pk == pk` (the request author), not confirmations cast by that key on other pending requests: [4](#0-3) 

### Impact Explanation
This is Critical: it allows a multisig request (e.g., `Transfer`, `AddKey`, `FunctionCall`) to execute with fewer than `num_confirmations` live-member approvals, effectively a threshold bypass. Funds or full-access keys can be moved/granted with less real, current consensus than the multisig was configured to require, and the requirement degrades permanently every time a confirming member departs while a request is still outstanding.

### Likelihood Explanation
Reaching this requires only ordinary multisig operation: a member confirms a request, is later removed (a normal governance event — departure, key rotation, compromise handling), and the earlier request remains pending. No attacker privilege escalation, foundation action, or external condition is needed beyond the contract's own designed request lifecycle (`add_request` → partial `confirm` → later `DeleteMember` action → later `confirm` completing execution). Multisig membership changes over the lifetime of a contract are a realistic and expected occurrence, so a window where this discrepancy is exploitable is plausible, especially since the default active-request limit (12) and lack of any expiry on requests means confirmed-but-incomplete requests can remain pending indefinitely.

### Recommendation
When a member is removed, either:
1. Iterate all pending requests and strip the removed member's identity from every `confirmations` set (not just requests they authored), and re-persist the resulting sets, or
2. On every `confirm()` call, re-validate the existing confirmation set against current `self.members` and discard/ignore entries that no longer correspond to a live member before comparing the count to `num_confirmations`.

### Proof of Concept
1. Multisig deployed with members `{A, B, C, D}` and `num_confirmations = 3`.
2. Member `A` calls `add_request` to create request `R` (e.g., `Transfer` to an attacker-controlled account) and `confirm`s it — `confirmations[R] = {A}`.
3. Separately, the group later approves a `DeleteMember { member: A }` request that reaches threshold and executes, removing `A` from `self.members`. `delete_member` only removes requests where `r.member == A`; since `R` was authored by `A`, in this exact scenario it *would* be purged — but if `A` had instead only confirmed a request authored by `B` (not `R` itself, but some other pending request `R2` originally added by `B`), `delete_member` never inspects or purges `confirmations[R2]`, leaving `A`'s stale confirmation in place.
4. `B` and `C` (2 live members) subsequently confirm `R2`. `confirm()` sees `confirmations[R2].len() == 3` (`A`, `B`, `C`) and `3 >= num_confirmations (3)`, so it executes `R2` — even though only 2 of the currently live members actually approved it after `A`'s removal.

This demonstrates the threshold binding `count(confirmations) == count(live-member approvals)` is broken, the direct analog of the reported `rfq` cancel bug where a stale/insufficiently-checked state (`confirmed`) allowed a later action to bypass an intended invariant.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
