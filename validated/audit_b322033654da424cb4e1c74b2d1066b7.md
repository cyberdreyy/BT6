### Title
Frontrunnable `deleteWriteOffRequest()` lets a fulfiller force a stale write-off sale after terms change - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
Analogous to Cooler's `toggleRoll()` frontrun, a lender's write-off request in `IdleCreditVaultWriteOffEscrow` is fulfillable forever once created. The lender's only way to withdraw or reprice it is a separate `deleteWriteOffRequest()` transaction, which any fulfiller can frontrun with `fullfillWriteOffRequest()`, forcing the lender to sell escrowed tranche tokens at the stale ask price even after the information that motivated the cancellation (e.g., full borrower repayment at epoch end) is public.

### Finding Description
`createWriteOffRequest()` escrows the lender's tranche tokens and records an ask price while the epoch is running [1](#0-0) . Two facts create the two-transaction intent window:

1. Requests are additive and immutable in price. A second call to `createWriteOffRequest` only increases `tranches`/`underlyings` [2](#0-1) , so a lender who wants to cancel or lower the ask must submit `deleteWriteOffRequest()`.
2. `fullfillWriteOffRequest()` has no epoch-running check and no expiry — it only verifies the fulfiller pays at least the recorded ask and takes the full tranche amount [3](#0-2) . `deleteWriteOffRequest()` likewise has no epoch gate [4](#0-3) .

Sequence: epoch running, lender escrows 100 BB tranches asking 70 underlying (distressed pricing). Epoch ends, `stopEpoch` succeeds with full repayment; BB tranches are now redeemable near 100. The lender broadcasts `deleteWriteOffRequest()` to reclaim the tokens. An attacker (any EOA acting as a write-off fulfiller, an explicitly allowed attacker role) sees the mempool transaction and frontruns `fullfillWriteOffRequest(lender, 100 tranches, 70 underlyings)`. The lender's delete then reverts (`Is0`), the lender receives `70 - exitFee` instead of tokens worth ~100, and the attacker pockets the ~30% spread. The honest lender's revocation intent is subverted exactly as in the Cooler bug.

`nonReentrant` does not prevent ordering attacks, and no other guard (KYC, pausing, only-CDO) restricts `fullfillWriteOffRequest` or gives the request an expiry.

### Impact Explanation
Direct theft: the attacker extracts the spread between the stale ask and the current tranche redemption value, paid out of the escrowed tranche tokens the lender was trying to recover. Loss is quantified as `trancheValue − (ask − exitFee)` per request and scales with the escrowed amount; realistic spreads are large because write-off asks are priced during epoch uncertainty while fulfillment can occur after `stopEpoch`/`finalizeDefault` reveal true recovery value.

### Likelihood Explanation
High under the report's own model: the attack needs only mempool monitoring and a standard frontrun, the fulfiller role is permissionless, and the trigger condition (lender repricing/cancelling after resolution of epoch uncertainty) is the natural usage pattern of the escrow. The only mitigant is that the ask price is lender-chosen, which is also true in the original Cooler finding (lender-chosen rollability) and did not prevent a High severity rating.

### Recommendation
Bind the request to the context in which it was priced, e.g., have `createWriteOffRequest` record `epochEndDate`/epoch number and have `fullfillWriteOffRequest` revert once that epoch has stopped or the pool is defaulted/finalized, forcing re-confirmation of terms. Alternatively add an explicit lender-signed expiry or a two-step delete (request-cancel then withdraw) so a pending fulfillment cannot outlive the conditions under which the price was set.

### Proof of Concept
Foundry fork-style PoC against a deployed `IdleCreditVaultWriteOffEscrow`:

```solidity
function testFrontrunWriteOffDelete() public {
    // epoch running: lender escrows 100 BB tranches asking 70e18 underlying
    vm.prank(lender);
    escrow.createWriteOffRequest(100e18, 70e18);

    // epoch ends, borrower repays in full; BB tranches now worth ~100e18
    _stopEpochFullyRepaid();

    // lender broadcasts deleteWriteOffRequest(); attacker frontruns it
    uint256 underlyingBefore = underlying.balanceOf(attacker);
    uint256 trancheBefore = bbTranche.balanceOf(attacker);

    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(lender, 100e18, 70e18); // succeeds: no epoch check

    // lender's queued delete now reverts; tokens are gone at stale price
    vm.expectRevert(Is0.selector);
    vm.prank(lender);
    escrow.deleteWriteOffRequest();

    assertEq(bbTranche.balanceOf(attacker) - trancheBefore, 100e18);
    // lender netted 70e18 - exitFee for tokens redeemable at ~100e18
    assertEq(underlyingBefore - underlying.balanceOf(attacker), 70e18);
}
```

Note: I could not run the test suite, so the PoC is written against the deployed contract semantics verified by reading `contracts/IdleCreditVaultWriteOffEscrow.sol` — specifically that `fullfillWriteOffRequest` performs no `isEpochRunning()` check (line 123) while `createWriteOffRequest` does (line 88), and that `deleteWriteOffRequest` reverts once the request is cleared (line 109).

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
  }
```

```text
  function deleteWriteOffRequest() external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[msg.sender];
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, currentRequest.tranches);
  }
```

```text
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];
```
