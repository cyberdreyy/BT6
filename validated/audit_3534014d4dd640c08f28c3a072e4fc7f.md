### Title
`lastWithdrawRequest` used as the only epoch key for loss-adjusted receipts lets a later withdraw request promote a haircutted receipt to a full-par payout — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The orangefs bug is a keyed-lookup bug: `xattr_key()` used the wrong key, so cache entries were hashed into the wrong bucket and never matched (leak), and the loop terminator compared the wrong thing. The direct analog in `IdleCreditVault` is `_claimLossAdjustedWithdrawRequest`, which looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — a single-slot, user-level marker — instead of the epoch in which the loss-adjusted receipt was actually created (`withdrawsRequestsByEpoch[_user][epoch]`). When a user makes a second `requestWithdraw` in a later epoch before claiming, the marker is overwritten, the loss-adjusted receipt "misses its bucket," and it is silently promoted to a full-par payout in `_claimFundedWithdrawRequest`, overpaying the attacker out of reserves funded for other claimants.

### Finding Description
`stopEpochWithDuration` with `_lossAmount > 0` calls `previewLossAdjustedWithdrawFunds` and then `collectWithdrawFunds(pendingToFund)` where `pendingToFund < pendingBasis`. This stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and clears `pendingWithdraws` — i.e. the strategy is funded with strictly less than the aggregate claim basis for that epoch's receipts (<cite> tag: contracts/strategies/idle/IdleCreditVault.sol:411-430).

Claims are dispatched in `claimWithdrawRequest`: first `_claimLossAdjustedWithdrawRequest`, then `_claimFundedWithdrawRequest`. The loss-adjusted path computes `lossEpoch = lastWithdrawRequest[_user]` and uses it as the key:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

`lastWithdrawRequest[_user]` is overwritten on every `requestWithdraw` (`lastWithdrawRequest[_user] = currentEpoch;`). So for a user who holds a haircutted receipt from epoch N and then requests another withdraw in epoch N+1:

- `lossRecoveryPriceByEpoch[N+1] == 0`, so `_claimLossAdjustedWithdrawRequest` returns 0 and `_clearWithdrawClaimForEpoch` is never invoked for epoch N. The epoch-N `withdrawsRequestsByEpoch` entry and its share of `withdrawsRequests[_user]` remain untouched.
- `_claimFundedWithdrawRequest` then pays `normalAmount = withdrawsRequests[_user]` — which still includes the full epoch-N basis — at par (`_transferFundedClaim(_user, amount)`), as soon as `epochNumber > N+1`.

The strategy only ever received `pendingToFund` (< full basis) for the epoch-N receipts, so paying them at par overdraws the funded reserve: the attacker takes underlying earmarked for other users' funded claims, or the transfer reverts and the user's claim is frozen. This is the same defect class as the kernel bug — a single overwritten key causing a per-epoch record to be looked up in the wrong bucket — but with direct fund impact.

Notably the code acknowledges multi-epoch receipts ("he will have to wait for another epoch to claim both requests") and stores `withdrawsRequestsByEpoch` per epoch, but the loss-adjusted claim path ignores that per-epoch mapping entirely and trusts the single-slot marker.

### Impact Explanation
An unprivileged tranche-token holder can steal the haircut portion of their receipt: e.g., with a 50% `lossRecoveryPrice`, a 100k USDC receipt that should pay 50k pays 100k. The extra ~50k comes out of the strategy's underlying balance that was collected to fund *other* epochs'/users' receipts, causing direct insolvency for later claimants (their `claimWithdrawRequest` reverts on insufficient balance or pays less than funded). This breaks the loss-waterfall invariant: pending receipts are supposed to share the stop-loss pro rata via `lossRecoveryPriceByEpoch`, and the attacker escapes that socialized loss entirely.

### Likelihood Explanation
Requirements are all satisfiable by an unprivileged user and honest privileged actors:

1. User holds tranche tokens and calls `requestWithdraw` during epoch N (buffer/running phase, normal fixed-APR mode).
2. Manager/owner calls `stopEpochWithDuration(..., _lossAmount > 0)` — a legitimate, documented flow for realizing partial losses — producing `lossRecoveryPriceByEpoch[N] < 1e18`.
3. Before claiming, the user calls `requestWithdraw` again in epoch N+1 (allowed; re-requesting while unclaimed is explicitly supported).
4. After epoch N+1 ends and its receipts are funded, the user calls `claimWithdrawRequest` and receives the full basis at par.

No malicious privileged role, default freeze, or oracle manipulation is needed; only the honest `stopEpochWithDuration` loss path, which exists precisely for partial-loss events. The attacker's only cost is waiting one extra epoch.

### Recommendation
Key the loss-adjusted claim by the actual receipt epoch, not by `lastWithdrawRequest`. Options:

- In `_claimLossAdjustedWithdrawRequest`, iterate or record the specific epoch: store per-user the epoch whose receipts were loss-adjusted (e.g. a `lossAdjustEpoch[_user]` set when `withdrawsRequestsByEpoch[_user][epoch]` exists at collect time is not enumerable, so instead) apply the recovery check inside `_clearWithdrawClaimForEpoch`/`_withdrawClaimAmountsForEpoch` per epoch, or
- In `requestWithdraw`, force-settle any outstanding loss-adjusted receipt for the user before overwriting `lastWithdrawRequest` (i.e. claim it or revert), so a haircutted receipt can never coexist with a newer `lastWithdrawRequest` value, or
- In `_claimFundedWithdrawRequest`, exclude any `withdrawsRequestsByEpoch[_user][e]` amounts where `lossRecoveryPriceByEpoch[e] != 0` and route them through the haircut — minimally, when `withdrawsRequestsByEpoch` has entries under an epoch with a stored recovery price, apply that price rather than par.

### Proof of Concept
Foundry fork sketch against `IdleCreditVault` / `IdleCDOEpochVariant` (mirroring `test/foundry/IdleCDOEpochQueue.t.sol` helpers `_requestWithdrawWithUser`, `_stopCurrentEpochWithApr`):

```solidity
function testLossAdjustedReceiptPromotedToPar() external {
    // Epoch N: two users deposit and request withdraw (normal APR mode)
    _stopCurrentEpochWithApr(10e18);                  // enter epoch 1
    uint256 t1 = _depositWithUser(attacker, 100e6);
    uint256 t2 = _depositWithUser(victim,   100e6);
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(attacker, t1);
    _requestWithdrawWithUser(victim,   t2);

    // stopEpochWithDuration with a real loss, e.g. pendingToFund = 50% of basis
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 activeBasis  = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 lossAmount   = /* chosen so pendingLoss ≈ 50% of pendingBasis */;
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(address(underlying), strategy.borrower(), repay, true);
    vm.prank(strategy.borrower()); underlying.approve(address(cdoEpoch), repay);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), lossAmount);
    // lossRecoveryPriceByEpoch[N] < 1e18 now; strategy holds only pendingToFund

    uint256 lossEpoch = /* epoch the receipts were requested in */;
    assertLt(strategy.lossRecoveryPriceByEpoch(lossEpoch), 1e18);

    // Epoch N+1: attacker requests another withdraw -> lastWithdrawRequest overwritten
    uint256 t3 = _depositWithUser(attacker, 10e6); // or reuse remaining tranches
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(attacker, t3);

    // Epoch N+2: stop normally so the new receipt is funded at par
    _stopCurrentEpochWithApr(10e18);

    // Attacker claims: loss path misses (key = N+1), funded path pays ALL at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker); // via IdleCDO claim entrypoint used by tests
    cdoEpoch.claimWithdrawRequest(attacker);        // dispatch into strategy
    uint256 got = underlying.balanceOf(attacker) - balPre;

    // got includes the full epoch-N basis, not basis * lossRecoveryPrice
    assertGt(got, /* expected haircutted + new-receipt amounts */);
    // Victim's claim now reverts or is underpaid: strategy underfunded
    vm.expectRevert(); // or assertLt on payout
    cdoEpoch.claimWithdrawRequest(victim);
}
```

Caveats not fully verified within tool limits: the exact `epochNumber` value used as the `lossRecoveryPriceByEpoch` key relative to the request epoch (it depends on whether `epochNumber += 1` in `deposit()` runs before or after `collectWithdrawFunds` inside `_stopEpoch`), and the precise public entrypoint signature for user claims on the CDO (`claimWithdrawRequest(_user)` is called by the CDO/queue). The core defect — `lastWithdrawRequest` being overwritten while `withdrawsRequestsByEpoch[N]` retains the haircutted basis and `_claimFundedWithdrawRequest` paying the aggregate at par — is confirmed by the code at `IdleCreditVault.sol` lines 282, 289–293, 319–349, and 789–800.
