## Analysis

The Shortfall.sol bug is fundamentally a **push-payment griefing pattern**: an auction refunds the loser by pushing tokens directly to their address inside the same state-transition that must succeed for the next bid to be accepted, so if the recipient can make that specific transfer fail, the whole operation reverts and value gets stuck/redirected.

The closest Aptos-native analog is in `staking_contract.move`'s payout path, which pushes coins directly to shareholder addresses inside a loop that must complete atomically before the caller's own funds become available.

### Root cause

`distribute_internal` in `aptos_move/framework/aptos-framework/sources/staking_contract.move` iterates over **every** shareholder currently owed a payout from the shared `distribution_pool` (populated by both `unlock_stake` for the staker and `request_commission_internal` for the operator/beneficiary) and pushes coins to each one in a single atomic `while` loop: [1](#0-0) 

`distribute` is explicitly `public entry`, callable by any unprivileged account ("Allow anyone to distribute already unlocked funds"): [2](#0-1) 

The payout uses `aptos_account::deposit_coins`, which auto-registers `CoinStore<CoinType>` for the recipient **only if** `can_receive_direct_coin_transfers` returns true; otherwise it aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`: [3](#0-2) 

`can_receive_direct_coin_transfers` is controlled per-account and can be flipped to `false` at any time by the account owner via a self-service, unprivileged entry function (`set_allow_direct_coin_transfers`), which is formally specified in the module's own spec: [4](#0-3) [5](#0-4) 

### Title
Unregistered / opted-out payout recipient permanently DoS's `staking_contract::distribute_internal` and strands co-shareholder funds - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`distribute_internal` bundles the payouts owed to *all* current shareholders of a `StakingContract`'s `distribution_pool` (the staker and the operator/beneficiary) into one atomic loop that pushes `AptosCoin` directly via `aptos_account::deposit_coins`. Any one of those parties can unilaterally make their own leg of the push-payment abort by (a) never registering `CoinStore<AptosCoin>` and (b) calling the public `aptos_account::set_allow_direct_coin_transfers(false)`. Because `distribute_internal` has no per-recipient try/skip semantics, this single griefing condition aborts the whole transaction, which blocks payout to *every* other shareholder sharing that pool, including funds the other party has already fully unlocked/inactivated.

### Finding Description
`distribute_internal` is invoked from `distribute`, `request_commission`, `unlock_stake`, `switch_operator`, and `update_commision` — all before any per-caller action is allowed to proceed (each forces a distribution flush first, see the call at `staking_contract.move:624-629` inside `request_commission`, and `staking_contract.move:784-789` inside `switch_operator`). If the pending distribution pool contains a share for an account whose `CoinStore<AptosCoin>` is not yet registered and who has disabled direct coin transfers, `aptos_account::deposit_coins` aborts for that shareholder mid-loop. Since Move aborts unwind the entire transaction, none of the other shareholders' shares are paid either — even though `coin::extract` had already removed part of the withdrawn coins from `coins` for shareholders processed earlier in the loop, none of it commits.

Concretely: after `switch_operator`, an old operator's beneficiary retains an entry in the pool for any not-yet-fully-unlocked commission. If that beneficiary account has never registered for `AptosCoin` and disables direct transfers (a purely self-directed, unprivileged action requiring no special role), every future call to `distribute`/`request_commission`/`unlock_stake` for that staker/operator pair will abort while trying to pay the stale beneficiary entry — permanently blocking the staker (and the new operator) from withdrawing their own already-unlocked stake through this contract, since `distribute_internal` is the only path that releases inactive/pending_inactive funds from the pool.

### Impact Explanation
This breaks the "Accounting across active, pending_active, pending_inactive, inactive, rewards, and commission state must preserve value and withdrawal rights" invariant: a legitimate staker's or operator's already-unlocked stake/commission becomes non-recoverable through the `staking_contract` module as long as one co-shareholder keeps `CoinStore<AptosCoin>` unregistered and direct transfers disabled. Because `distribute` is a public entry function callable by anyone, no privileged bypass path exists to force partial payout to the unaffected party, and Move's aborts-fully-revert semantics guarantee any attempted distribution attempt fails as a whole.

### Likelihood Explanation
The griefing precondition is entirely unprivileged: `aptos_account::set_allow_direct_coin_transfers` is a public entry function anyone can call on their own account, and simply never calling `coin::register<AptosCoin>` leaves the CoinStore unregistered. No governance, admin, or existing role is required — an operator, a beneficiary, or a staker can trigger this on their own account to grief the counterparties they share a `StakingContract` distribution pool with.

### Recommendation
Change `distribute_internal` to a pull-over-push pattern: instead of directly depositing to each shareholder in the same atomic loop, credit each shareholder's owed amount into a per-account claimable balance/resource (or an escrow), and let each shareholder withdraw independently via their own entry function. This isolates one shareholder's inability/unwillingness to receive a push transfer from all other shareholders' withdrawal rights, matching the mitigation recommended in the source report.

### Proof of Concept
1. Staker creates a `staking_contract` with operator O and commission 10% via `create_staking_contract`.
2. O calls `set_beneficiary_for_operator` to point to account B; B never calls `coin::register<AptosCoin>()`.
3. B calls `aptos_account::set_allow_direct_coin_transfers(false)`.
4. O earns rewards; O calls `request_commission`, adding a distribution share for B via `add_distribution` inside `request_commission_internal`. [6](#0-5) 
5. Stake pool lockup expires; commission becomes withdrawable (`inactive`/`pending_inactive` > 0).
6. Staker calls `unlock_stake` to withdraw their own already-vested stake. This first calls `distribute_internal`, which tries to pay B via `aptos_account::deposit_coins(B, ...)`.
7. Because B has no `CoinStore<AptosCoin>` and has opted out of direct transfers, the deposit aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, reverting the whole `unlock_stake` transaction — the staker cannot withdraw their unlocked stake as long as B's state persists, even though the staker has no relationship with or control over B's account settings. [7](#0-6) 

**Note on scope/uncertainty:** I could not fully confirm from the indexed content whether `distribute_internal`/`vesting::distribute` are the only ever-called paths releasing this specific pool's funds, or whether an alternate emergency withdrawal exists elsewhere in `staking_contract.move` that isn't indexed here; if such a path exists it could mitigate the "non-recoverable" severity. I recommend verifying this in a full checkout of the repository, since the index has size limits and some function bodies (e.g. `add_distribution`, and the tail of `withdraw_internal` in `delegation_pool.move`) were not retrievable in full.
