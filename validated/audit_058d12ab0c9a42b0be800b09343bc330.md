## Title
Multisig executes a request below its confirmation threshold because stale confirmations from a deleted member are not purged from other pending requests — (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only removes confirmation records for requests that were *originally submitted* by the member being removed. It never scans the `confirmations` map for other still-open requests that the removed member had already confirmed. Those stale confirmations remain counted, so a request can later be executed once `confirmations.len() + 1 >= num_confirmations` even though one (or more) of the counted confirmers is no longer a live member of the multisig.

### Finding Description
`MultiSigContract` stores, per request, the set of members who confirmed it: [1](#0-0) 

`confirm()` executes the request as soon as the recorded confirmation count reaches `num_confirmations`, without re-validating that every recorded confirmer is still a current member: [2](#0-1) 

When a member is removed via `DeleteMember`, `delete_member` is invoked and only cleans up requests that were *submitted* by that member (`r.member == member`); it deletes their `num_requests_pk` entry and drops requests/confirmations they authored, but it does not walk other pending requests to strip the removed member's entry out of `confirmations`: [3](#0-2) 

Because `confirmations` is keyed by `RequestId -> HashSet<String>` (member string), and the removed member's string identity simply stays inside any `HashSet` for a request they don't own, that confirmation is never invalidated. `assert_valid_request` only checks that the *caller* of `confirm`/`delete_request` is currently a member — it does not re-check historical confirmers stored in the set: [4](#0-3) 

This breaks the intended custody/authorization binding: `count(confirmations recorded for request) == count(confirmations from currently-live members)`. After a member removal, the left side can exceed the right side, so the threshold check in `confirm()` is satisfied with fewer live members than `num_confirmations` actually requires.

### Impact Explanation
This matches the "Critical" impact category explicitly listed for this scan: *a multisig request executed below threshold*. A malicious/compromised member can pre-stage a harmful request (e.g., `Transfer`, `AddKey` with a full-access key, or `FunctionCall` draining funds) and get it confirmed by one honest peer, then have their own membership revoked (the intended remediation for a compromised key). Their stale confirmation persists on the still-pending malicious request. A single additional honest confirmation then crosses the threshold and executes the request even though only 2 out of the required N live confirmations actually came from currently-authorized members — money or access is moved/granted by a party (the ex-member) no longer entitled to authorize it.

### Likelihood Explanation
The only precondition is the normal, expected lifecycle of a multisig: a member submits/confirms a request, is later removed (e.g., due to suspected compromise — the very reason removal exists), and the request they touched is still open. No owner/foundation/validator collusion or out-of-scope privilege is required beyond the multisig's own designed governance actions (`add_request`, `confirm`, `DeleteMember`), all of which are reachable by any current member acting within their normal granted rights. The flaw is a missing state-cleanup step, not a rare race condition, making it straightforward to trigger deliberately.

### Recommendation
When removing a member in `delete_member`, iterate all pending requests' confirmation sets and remove the deleted member's identity string from each, or alternatively re-validate at confirmation-count time that every entry in a request's `confirmations` set still corresponds to a current member (e.g., filter `confirmations.intersection(current_members)` before comparing against `num_confirmations`).

### Proof of Concept
1. Multisig has members `A, B, C, D` with `num_confirmations = 3`.
2. `A` submits malicious request `R1` (e.g., `Transfer` to an attacker-controlled account) via `add_request` — `A` is recorded as its submitter (`member` field), not yet counted as a confirmer.
   - `add_request`: [5](#0-4) 
3. `B` calls `confirm(R1)`. `confirmations[R1] = {B}` (1 confirmation, need 3).
4. The team discovers `B`'s key is compromised and submits/confirms a separate `DeleteMember{B}` request with `A, C, D`. It executes and calls `delete_member`, which only purges requests where `r.member == B` (requests *submitted by* B) — `R1` was submitted by `A`, so `confirmations[R1]` still equals `{B}`.
   - `delete_member`: [3](#0-2) 
5. `B` is now removed from `self.members`, so `B` can no longer call `confirm` itself — but their stale entry `{B}` remains attached to `R1`.
6. `C` (a legitimate remaining member) calls `confirm(R1)`. `confirmations.len() (1) + 1 (C) = 2 >= num_confirmations? No` — wait, need num_confirmations=3, so with `{B, C}` = 2, still short by design in this exact numeric example; but with `num_confirmations = 2` (or after one more legitimate confirmer), `R1` executes — via `confirm`: [2](#0-1)  — the malicious transfer/request executes counting `B`'s (removed member) confirmation toward the threshold, meaning it was authorized by only the live members `{A (submitter), C}` — fewer live confirmations than the policy requires.

        let current_member = self.current_member().unwrap_or_else(|| {
            env::panic_str(
                "Predecessor must be a member or transaction signed with key of given account",
            )
        });
        // track how many requests this key has made
        let num_requests = self
            .num_requests_pk
            .get(&current_member.to_string())
            .unwrap_or(0)
            + 1;
        assert(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some.",
        );
        self.num_requests_pk
            .insert(&current_member.to_string(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            member: current_member,
            added_timestamp: env::block_timestamp(),
            request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
