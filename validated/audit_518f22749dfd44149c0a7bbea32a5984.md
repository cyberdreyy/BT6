### Title
Withdraw ConfidentialTransfer parser mislabels `rangeProofContextStateAccount` as `owner` when account list is minimal-length with both proof offsets zero - (File: `transaction-status/src/parse_token/extension/confidential_transfer.rs`)

### Summary
`parse_confidential_transfer_instruction`'s `Withdraw` branch uses a heuristic boundary check (`offset < account_indexes.len().saturating_sub(1)`) to decide whether to attribute an account index to `equalityProofContextStateAccount` / `rangeProofContextStateAccount` versus reserving it for the owner/signer parsing. When `equality_proof_instruction_offset == 0` and `range_proof_instruction_offset == 0` (i.e., both proofs use context-state accounts, no `instructionsSysvar` needed) and the raw instruction's `account_indexes` list is exactly at the minimum length enforced by `check_num_token_accounts(account_indexes, 4)`, the second context-state-account slot fails the boundary check and is instead consumed by `parse_signers` as the `owner`, producing an incorrect field-to-account mapping in `jsonParsed` output.

### Finding Description
In the `Withdraw` arm [1](#0-0) , the code:
1. Requires only 4 accounts via `check_num_token_accounts(account_indexes, 4)` [2](#0-1) .
2. Computes `has_sysvar` from the two proof offsets; if both are `0`, no sysvar account is consumed, and `offset` starts at `2` [3](#0-2) .
3. Attempts to attribute `equalityProofContextStateAccount` at `offset=2`, guarded by `offset < account_indexes.len().saturating_sub(1)` [4](#0-3) . With `account_indexes.len()==4`, this bound is `3`, so `2 < 3` passes and `offset` becomes `3`.
4. Attempts to attribute `rangeProofContextStateAccount` at `offset=3`, guarded by the same bound (`3`). Since `3 < 3` is false, this insertion is **skipped** even though `range_proof_instruction_offset == 0` explicitly signals that a range-proof context-state account should be present at that position [5](#0-4) .
5. `parse_signers(map, offset, ...)` is then called with `offset` still `3`, so `account_indexes[3]` — which per the encoded offsets is actually the range-proof context-state account — is instead labeled `"owner"` in the output [6](#0-5) .

The parser operates purely on the raw instruction bytes/account indexes taken from the transaction message (via `parse_token`/`parse_confidential_transfer_instruction`), independent of on-chain execution success. Because `getTransaction` (`jsonParsed` encoding) parses instructions from the stored raw message regardless of whether the instruction actually succeeded at runtime, an attacker only needs a transaction containing this crafted `Withdraw` instruction to land in a block (fees paid, valid blockhash, syntactically valid instruction with `spl-token-2022` program id) — execution failure due to real account-count mismatch in the on-chain program does not prevent the RPC's `jsonParsed` decoder from producing this mislabeled output. The `check_num_token_accounts` guard only enforces a coarse minimum count (4) and does not verify consistency between the encoded proof offsets and the number of accounts actually supplied, so the boundary heuristic (`len() - 1`) silently breaks down at this exact minimal-length edge case.

### Impact Explanation
This is a decoder misreporting bug: a client relying on `getTransaction`'s `jsonParsed` output for a Withdraw ConfidentialTransfer instruction can be shown an attacker-controlled account key labeled as `"owner"` when it is actually the `rangeProofContextStateAccount`, and the real `rangeProofContextStateAccount` field is silently omitted. This falls under the "decoder panic and misreporting" acceptance category — it does not crash the validator or mutate consensus state, but it does cause wrong-field/wrong-identity data to be returned from a read RPC endpoint for data that is legitimately on-chain (a submitted transaction, whether it executed successfully or failed).

### Likelihood Explanation
Trivial to trigger: the attacker fully controls the raw instruction's account list and data at transaction-construction time; no privileged validator, leader, or on-chain state is required, and the transaction need not even succeed execution to be indexed and later returned by `getTransaction`. The only precondition is submitting one transaction containing a `ConfidentialTransferExtension::Withdraw` instruction with exactly 4 accounts and `equality_proof_instruction_offset == 0`, `range_proof_instruction_offset == 0`, then querying it back with a single `getTransaction` call (well within the one-call-per-slot budget).

### Recommendation
Do not use the `account_indexes.len().saturating_sub(1)` heuristic to gate context-state-account attribution. Instead, compute the exact expected account count deterministically from the decoded proof-location flags (sysvar-needed + number of context-state accounts needed) before attempting to insert any field, and treat any shortfall as `InstructionNotParsable` rather than silently reassigning the account to `owner`/`multisigOwner`. Apply the same fix to the analogous `Transfer` and `TransferWithFee` arms, which use the identical pattern.

### Proof of Concept
```rust
// transaction-status/src/parse_token/extension/confidential_transfer.rs (new test)
#[test]
fn test_withdraw_minimal_accounts_mislabels_range_ctx_as_owner() {
    let token_account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let range_ctx_actually_owner_slot = Pubkey::new_unique(); // attacker-chosen key

    // Manually build a Withdraw instruction with exactly 4 accounts:
    // [account, mint, equalityProofContextStateAccount(=implicit via data), range_ctx_slot]
    // equality_proof_instruction_offset = 0, range_proof_instruction_offset = 0
    let withdrawal_data = WithdrawInstructionData {
        amount: 42.into(),
        decimals: 9,
        new_decryptable_available_balance: PodAeCiphertext::default(),
        equality_proof_instruction_offset: 0,
        range_proof_instruction_offset: 0,
    };

    let accounts = vec![
        AccountMeta::new(token_account, false),
        AccountMeta::new_readonly(mint, false),
        AccountMeta::new_readonly(Pubkey::new_unique(), false), // equality ctx (correctly attributed)
        AccountMeta::new_readonly(range_ctx_actually_owner_slot, false), // SHOULD be rangeProofContextStateAccount
        // Note: no separate owner account provided - only 4 accounts total.
    ];

    let instruction = encode_confidential_transfer_instruction(
        ConfidentialTransferInstruction::Withdraw,
        &withdrawal_data,
        accounts,
    );

    let message = Message::new(&[instruction], None);
    let parsed = parse_token(
        &message.instructions[0],
        &AccountKeys::new(&message.account_keys, None),
    )
    .unwrap();

    // BUG: rangeProofContextStateAccount is missing
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());

    // BUG: the actual range-proof context account key is mislabeled as "owner"
    assert_eq!(
        parsed.info["owner"],
        json!(range_ctx_actually_owner_slot.to_string())
    );
}
```
Expected result: the test demonstrates that the account intended (per the encoded zero offsets) to be `rangeProofContextStateAccount` is dropped from that field and instead surfaces under `"owner"`, confirming the field-to-account mapping drift described above.
