### Title
Builder payment `fee_recipient` is never validated against the block proposer's committed preference in `process_execution_payload_bid` - ([File: specs/gloas/beacon-chain.md])

### Summary
`process_execution_payload_bid` records a `BuilderPendingPayment`/`BuilderPendingWithdrawal` whose destination address is taken directly and unconditionally from the builder-supplied `bid.fee_recipient` field, with no consensus-level check that this address matches the address the block's actual proposer registered via `SignedProposerPreferences`. The only place such a match is checked is a soft, non-authoritative gossip `IGNORE` rule, not a state-transition validity rule, and it is not even listed among the block-construction "MUST" checks a proposer is instructed to perform.

### Finding Description
`process_execution_payload_bid` [1](#0-0)  accepts a `SignedExecutionPayloadBid` and, if `amount > 0`, stores a `BuilderPendingPayment` whose `withdrawal.fee_recipient` is set verbatim to `bid.fee_recipient`:
```
pending_payment = BuilderPendingPayment(
    weight=Gwei(0),
    withdrawal=BuilderPendingWithdrawal(
        fee_recipient=bid.fee_recipient,
        amount=amount,
        builder_index=builder_index,
    ),
    proposer_index=get_beacon_proposer_index(state),
)
```
This is the only address binding used later when the payment is settled: `settle_builder_payment` moves the whole `payment.withdrawal` (including `fee_recipient`) into `state.builder_pending_withdrawals` [2](#0-1) , and `apply_withdrawals`/`process_withdrawals` later pays that exact address out of the builder's balance [3](#0-2) .

Nowhere in `process_execution_payload_bid` (or in `verify_execution_payload_bid_signature`, which only checks the BLS signature over the bid) is `bid.fee_recipient` cross-checked against the current proposer's own registered fee recipient (`SignedProposerPreferences.fee_recipient`).

The spec text itself documents the intended binding as a pure gossip-layer convenience filter, not a consensus rule:
- `p2p-interface.md` gossip validation for the `execution_payload_bid` topic has an `IGNORE` (not `REJECT`) check: "The bid's fee recipient matches the proposer's preference" [4](#0-3) . `IGNORE` only affects gossip propagation/scoring, it has no bearing on block or state validity.
- The honest-validator block-construction procedure in `validator.md`, which enumerates the "MUST" conditions a proposer must verify before including a bid (signature, balance coverage, slot, parent hash/root, prev_randao), does **not** include a check that `bid.fee_recipient` equals the proposer's own preference [5](#0-4) . The note at line 223-224 merely states, descriptively, that whatever address is in `fee_recipient` "will receive the builder payment" — it is not phrased as a requirement to verify.

Because of this gap, the equality that should hold — "the Gwei a builder pays for winning a slot goes to the proposer of that slot" — is not enforced by the state-transition function at all. A block that a fully spec-following node will accept as valid can commit a builder payment to *any* address the builder chose, regardless of which proposer produced the block or what fee recipient that proposer had registered. Enforcement is delegated entirely to social/off-chain conventions (gossip `IGNORE` and non-mandatory validator guidance), which a malicious or careless builder, or a compromised builder-relay pathway (bids obtained "by other off-protocol means", explicitly permitted by validator.md line 202-203), can simply bypass.

### Impact Explanation
This maps directly to the "builder payment or withdrawal misdirected" High-impact category. The Gwei being moved is real value the builder owes for winning a block-building auction; consensus should guarantee it reaches the correct beneficiary (the proposer who accepted the bid), analogous to how `FCNProduct.sol`'s unchecked `vaultAddress` let an unprivileged caller redirect `safeTransferFrom` funds to an address of their choosing. Here, an unprivileged builder (or a relay standing between builder and proposer) similarly controls the destination of a payment that a spec-following node will settle without any on-chain verification that it matches the intended recipient, so a proposer can lose a promised builder payment to an address they never approved while every spec-following client still considers the resulting chain state fully valid — there is no fork or safety break, but real value is misdirected away from its rightful owner without their authorization.

### Likelihood Explanation
Likelihood is moderate: exploitation requires either (a) a malicious/compromised builder or relay that supplies a bid whose `fee_recipient` does not match the block's actual proposer preference through an off-gossip channel (explicitly allowed by spec: "The block proposer MAY obtain these signed messages by other off-protocol means"), or (b) proposer software that (correctly, per the letter of the spec's "MUST" list) omits the fee-recipient cross-check because it's not a listed requirement. Since the fee-recipient match is enforced only as a gossip `IGNORE`, any bid path that bypasses public gossip (private relays, direct builder-proposer negotiation) is not covered by that filter at all.

### Recommendation
Add an explicit consensus-level assertion to `process_execution_payload_bid` (or to the parent execution payload processing / block validity rules) that ties `bid.fee_recipient` to a value verifiably associated with the proposer of `bid.slot` — e.g., requiring the bid or block to include (and the state transition to verify) a `SignedProposerPreferences` commitment whose `fee_recipient` matches `bid.fee_recipient`, mirroring the checked-equality pattern already used for withdrawal/consolidation/builder-exit requests (`source_address == validator.withdrawal_credentials[12:]` / `builder.execution_address`). At minimum, promote the current gossip `IGNORE` check to a `REJECT` at the gossip layer *and* add the corresponding assertion in `validator.md`'s block-construction "MUST" list and in the state-transition function itself, so that spec-following nodes reject blocks committing to a builder payment for an unverified recipient rather than merely deprioritizing them in gossip.

### Proof of Concept
1. Builder `B` is active with sufficient balance to cover a bid of value `V`.
2. Proposer `P` is scheduled for slot `s` and has published `SignedProposerPreferences` with `fee_recipient = A_p`.
3. `B` crafts and signs a `SignedExecutionPayloadBid` with `bid.slot = s`, `bid.value = V`, and `bid.fee_recipient = A_attacker` (an address of the builder's choosing, not `A_p`), and delivers it to `P` off-gossip (e.g., via a private relay, which the spec explicitly permits: "MAY obtain these signed messages by other off-protocol means").
4. `P` includes this bid in `block.body.signed_execution_payload_bid` without independently re-verifying `fee_recipient == A_p` (not required by validator.md's MUST list).
5. `process_execution_payload_bid(state, signed_bid)` executes successfully — all of its assertions (signature, balance coverage, slot, parent hash/root, prev_randao, blob limits) pass, since none of them constrain `fee_recipient`. `state.builder_pending_payments[...]` is set with `withdrawal.fee_recipient = A_attacker`.
6. At settlement (`settle_builder_payment` → `apply_withdrawals`), `V` Gwei is paid from `B`'s balance to `A_attacker` instead of `A_p`.
7. Every spec-following node accepts this state transition as valid; there is no fork, no invalid-block detection — the builder payment has simply been misdirected away from proposer `P` with no consensus-level recourse. [1](#0-0) [2](#0-1) [3](#0-2) [5](#0-4) [4](#0-3)

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()

##### New `process_execution_payload_bid`

```python
def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid

##### Signed execution payload bid

To obtain `signed_execution_payload_bid`, a block proposer building a block on
top of a `state` MUST take the following actions in order to construct the
`signed_execution_payload_bid` field in `BeaconBlockBody`:

- Listen to the `execution_payload_bid` gossip global topic and save an accepted
  `signed_execution_payload_bid` from a builder. The block proposer MAY obtain
  these signed messages by other off-protocol means.
- The `signed_execution_payload_bid` MUST satisfy the verification conditions
  found in `process_execution_payload_bid` with the alias
  `bid = signed_execution_payload_bid.message`, that is:
  - For external builders, the signature MUST be valid.
  - For self-builds, set `bid.builder_index` to `BUILDER_INDEX_SELF_BUILD`.
  - For self-builds, the signature MUST be `bls.G2_POINT_AT_INFINITY` and the
    `bid.value` MUST be zero.
  - The builder balance can cover the `bid.value`.
  - The `bid.slot` is for the proposal block slot.
  - The `bid.parent_block_hash` equals
    `state.latest_execution_payload_bid.block_hash` if
    `should_build_on_full(store, head, get_current_slot(store))` is true,
    otherwise `state.latest_execution_payload_bid.parent_block_hash`.
  - The `bid.parent_block_root` equals the current block's `parent_root`.
  - The `bid.prev_randao` equals
    `get_randao_mix(state, get_current_epoch(state))`.
- Select one bid and set
  `block.body.signed_execution_payload_bid = signed_execution_payload_bid`.

*Note*: The execution address encoded in the `fee_recipient` field in the
`signed_execution_payload_bid.message` will receive the builder payment.
