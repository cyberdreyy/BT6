### Title
POSIX-mode command echo (`EscapeForPosix`) does not neutralize ANSI/control-character injection, enabling trace-log spoofing of the `$ <command>` line - ([File: functions/script_legacy/internal/escape.go])

### Summary
`CommandFormatter.FormatLogLine` (functions/script_legacy/internal/command_formatter.go:31-39) always wraps the command in `ansiGreen`/`ansiReset` and echoes it verbatim, but the escaping applied to the echoed text differs by shell mode. `EscapeForAnsiC` hex-escapes all control bytes (including `ESC`, `\r`) to stop terminal manipulation, while `EscapeForPosix` does not, so in POSIX mode a job-controlled command string containing raw `ESC`/`\r` sequences is echoed unescaped and can rewrite/clear the rendered `$ ` prompt line in a terminal viewer, without changing the actually executed command line written by `writeNormalCommand`.

### Finding Description
`FormatLogLine` builds the display string as `ansiGreen + "$ " + getDisplayCommand(command) + ansiReset` [1](#0-0) . For single-line commands, `getDisplayCommand` returns the command unmodified [2](#0-1) , and `isMultiline`/`getFirstLine` only special-case `\n`, not `\r` or ANSI escape bytes [3](#0-2) . That means a single job-provided script line containing embedded `\r` and `ESC[...` bytes (no literal `\n`) is passed through untouched to the echo builder.

The escaping applied then depends on shell mode: in bash mode, `EscapeForAnsiC` hex-escapes every control byte < 0x20, 0x7F, and non-ASCII bytes — explicitly including `ESC` (0x1B) and `\r` — which is documented as preventing "jobs from clearing the screen or rewriting logs using ANSI escape sequences" [4](#0-3) . In POSIX mode, `EscapeForPosix` only escapes a fixed set of shell metacharacters (`` ` ``, `"`, `\`, `$`, space, `!`, `#`, `%`, `&`, `(`, `)`, `*`, `<`, `=`, `>`, `?`, `[`, `|`) and leaves every other byte — including `ESC` and `\r` — untouched, passed straight into the `echo "..."` argument [5](#0-4) .

`writeNormalCommand` then writes the formatted echo line, followed on the next line by the literal, unmodified `command` for execution [6](#0-5) . Because the raw command bytes (including any `\r`/`ESC` the attacker embedded) are used both for the echoed "audit" line and for the executed line, a terminal or ANSI-aware log renderer processing the echo output will interpret the embedded `\r` (carriage return) and `ESC[2K`/similar sequences to overwrite or clear the already-rendered portion of the line, letting the attacker present a fabricated, benign-looking `$ <command>` prompt in the rendered trace view while the underlying raw bytes (and the actually executed command) contain the real, different text. The existing safeguard (`EscapeForAnsiC`'s hex-escaping) exists precisely to stop this, but it is not applied when `PosixEscape`/`posixMode` is true, so the protection is inconsistent and bypassable simply by using the POSIX/sh code path.

### Impact Explanation
This is a log/audit-integrity issue: a pipeline author (unprivileged, since they only control their own `.gitlab-ci.yml`/script content) can, when the runner uses POSIX-mode script generation, cause the rendered job trace to visually display a different, innocuous command in place of the actually-run line, undermining any human review of job logs that relies on the terminal-rendered `$ ` echo lines to know what ran. The underlying raw trace bytes still contain the real content (so raw-text search/audit tooling not doing ANSI rendering is unaffected), which somewhat limits severity, but any terminal-based or ANSI-rendering log viewer is fooled.

### Likelihood Explanation
Trivially reachable: any job whose shell config selects POSIX escaping (`config.PosixEscape == true`, used for `/bin/sh`-based shells) and whose script line contains raw `\r`/`ESC` bytes (achievable via CI job script text, e.g. embedding raw control bytes in a YAML string or via `printf`-generated content stored as a script line) will trigger this on every run through `ProcessCommand` → `writeNormalCommand` → `FormatLogLine`. No special privilege or external state is required.

### Recommendation
Make `EscapeForPosix` hex-escape (or otherwise neutralize) control characters (`0x00-0x1F`, `0x7F`, and ideally non-ASCII) the same way `EscapeForAnsiC` does, so POSIX-mode echoes get the same terminal-manipulation protection as bash-mode echoes.

### Proof of Concept
Go unit test in `functions/script_legacy/internal/command_formatter_test.go`:
```go
func TestCommandFormatter_FormatLogLine_PosixMode_ANSIInjectionNotEscaped(t *testing.T) {
    formatter := NewCommandFormatter(true) // POSIX mode
    malicious := "echo real_malicious_command\r\x1b[2K$ innocuous looking command"
    result := formatter.FormatLogLine(malicious)

    // BUG: raw ESC/CR bytes pass through unescaped in POSIX mode,
    // unlike EscapeForAnsiC which hex-escapes them.
    assert.Contains(t, result, "\r", "raw CR should not appear unescaped in echoed line")
    assert.Contains(t, result, "\x1b[2K", "raw ANSI clear-line sequence should not appear unescaped")
}
```
Expected (fixed) behavior: both assertions should fail once `EscapeForPosix` hex-escapes control bytes, i.e. `result` should contain `\r` and `ESC` only as escaped sequences (e.g. `\xNN`), matching `EscapeForAnsiC`'s behavior.

// EscapeForAnsiC escapes a string for use in ANSI-C quoting ($'...').
// Control characters and non-ASCII bytes are hex-escaped to prevent terminal manipulation.
// This prevents jobs from clearing the screen or rewriting logs using ANSI escape sequences.
// Matches GitLab Runner's ShellEscape behavior.
func EscapeForAnsiC(s string) string {
	var buf strings.Builder

	for i := 0; i < len(s); i++ {
		c := s[i]
		switch c {
		case '\\':
			buf.WriteString("\\\\")
		case '\'':
			buf.WriteString("\\'")
		case '\n':
			buf.WriteString("\\n")
		case '\r':
			buf.WriteString("\\r")
		case '\t':
			buf.WriteString("\\t")
		case '\a':
			buf.WriteString("\\a")
		case '\b':
			buf.WriteString("\\b")
		case '\f':
			buf.WriteString("\\f")
		case '\v':
			buf.WriteString("\\v")
		default:
			// Hex-escape control characters (0x00-0x1F, 0x7F) and non-ASCII (>0x7F)
			// This prevents ANSI escape sequences (ESC = 0x1B) from manipulating terminal
			if c < 0x20 || c == 0x7F || c > 0x7F {
				fmt.Fprintf(&buf, "\\x%c%c", hextable[c>>4], hextable[c&0x0f])
			} else {
				buf.WriteByte(c)
			}
		}
	}

	return buf.String()
}

func EscapeForPosix(s string) string {
	if s == "" {
		return "''"
	}

	var buf strings.Builder
	needsQuoting := false

	for _, r := range s {
		switch r {
		case '`', '"', '\\', '$':
			buf.WriteRune('\\')
			buf.WriteRune(r)
			needsQuoting = true
		case ' ', '!', '#', '%', '&', '(', ')', '*', '<', '=', '>', '?', '[', '|':
			buf.WriteRune(r)
			needsQuoting = true
		default:
			buf.WriteRune(r)
		}
	}

	if needsQuoting {
		return `"` + buf.String() + `"`
	}

	return buf.String()
}
