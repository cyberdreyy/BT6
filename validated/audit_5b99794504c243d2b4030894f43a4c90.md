### Title
Cross-job pipeline run disclosure via `PipelineRunsController.Show` ignoring `:ID` path param - ([File: core/web/pipeline_runs_controller.go])

### Summary
`GET /v2/jobs/:ID/runs/:runID` looks up a run solely by `runID` via `prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)` and never verifies that the returned run's `PipelineSpec.JobID` corresponds to the `:ID` path parameter. Any authenticated user with access to this endpoint (no special role wrapper is applied) can supply an arbitrary `runID` under any job's URL and retrieve that run's full data, including task outputs/errors which may embed bridge response bodies or other sensitive data.

### Finding Description
The route is registered without any per-route role guard: `authv2.GET("/jobs/:ID/runs/:runID", prc.Show)` [1](#0-0) , unlike sibling routes that use `auth.RequiresEditRole`/`auth.RequiresRunRole`. It sits under the `authv2` group, which only requires a valid authenticated session or token (`auth.Authenticate(...AuthenticateByToken, AuthenticateBySession)`), i.e. any role (View and above) can reach it [2](#0-1) .

Inside `Show`, the implementation only parses `c.Param("runID")` into a `pipeline.Run` ID and fetches it directly, ignoring `c.Param("ID")` entirely: [3](#0-2) 

There is no subsequent check comparing `pipelineRun.PipelineSpec.JobID` (or `PipelineSpecID`) against the job resolved from `:ID`. Compare this with `Index`, which correctly scopes results to the job ID from the path when present [4](#0-3) . `Show` has no equivalent scoping/ownership check, so the `:ID` segment is purely decorative — any valid `runID` returns its run data no matter what job ID is in the URL, and no matter whether the requester has any relation to that job.

Because the response is generated via `presenters.NewPipelineRunResource(pipelineRun, ...)`, this discloses the run's outputs/errors, which for jobs with bridge/HTTP tasks can include full bridge response bodies (potentially containing sensitive data returned by external adapters).

### Impact Explanation
This is a broken object-level authorization / cross-job data disclosure: a low-privileged authenticated user (View role) can read pipeline run details, including task outputs and errors (which can contain third-party/bridge response bodies), for jobs they should not have access to, simply by guessing or enumerating sequential integer run IDs. This maps to a "sensitive information disclosure via broken authorization" class of bug — while it does not expose private keys or secrets directly, it can leak bridge payloads or business-sensitive data embedded in run outputs across job boundaries, undermining the node's per-job data isolation invariant.

### Likelihood Explanation
Exploitation requires only a valid authenticated session/token with the minimum node role (View), which is the lowest privilege level able to reach any `/v2` job-run endpoints. Run IDs are sequential/enumerable integers, making guessing feasible in a multi-job node. The request is a single unauthenticated-relative-to-target-job `GET` request; the flaw is deterministic and 100% repeatable, not conditioned on any race condition or timing.

### Recommendation
In `PipelineRunsController.Show`, resolve the job from `c.Param("ID")` (as `Index` already does), and after calling `FindRun`, verify that `pipelineRun.PipelineSpec.JobID` matches the resolved job's ID before returning the resource; otherwise return `404 Not Found` (avoid leaking existence via distinguishable error codes).

### Proof of Concept
Go handler-level integration test plan (extending `core/web/pipeline_runs_controller_test.go`):
1. Create two jobs, Job A and Job B, each with a pipeline spec including an HTTP/bridge task that returns distinguishable dummy sensitive output (e.g. `{"secret":"jobB-secret"}`).
2. Trigger a run for Job B (`POST /v2/jobs/{jobB.ID}/runs`) and capture the resulting `runID`.
3. As an authenticated View-role (or any authenticated) session, issue `GET /v2/jobs/{jobA.ID}/runs/{jobB-runID}`.
4. Assert: current behavior returns `200 OK` with the Job B run's data (including the `jobB-secret` output) despite the URL specifying Job A — proving isolation is broken.
5. After the fix, the same request should return `404 Not Found` since `runID` does not belong to `jobA.ID`.

```go
func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
	jsonAPIResponse(c, res, "pipelineRun")
}
```
