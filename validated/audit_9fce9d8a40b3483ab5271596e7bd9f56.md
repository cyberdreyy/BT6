### Title
`FF_USE_LEGACY_BASH_EVAL` legacy `: | eval` pipeline dumps script body (including expanded secrets) to job trace on SIGTERM cancellation - (File: `functions/concrete/run/stages/internal/scriptwriter/scriptwriter.go`)

### Summary
The `UseLegacyBashEval` code path (`b.UseLegacyBashEval`) deliberately reproduces the pre-fix `: | eval ' ...'` pipeline that issue 39005 replaced, and both the code comments and dedicated tests confirm it is "the known vulnerable escape hatch." This flag is read from job/CI variables via `isFeatureFlagOn` → `variables.DefaultBool`, making it attacker-settable by any pipeline author through a `FF_USE_LEGACY_BASH_EVAL: "true"` CI/CD variable, and a job-cancel/SIGTERM race then reproduces the documented script-body/secret leak to the trace.

### Finding Description
`buildBashScript` in `functions/concrete/run/stages/internal/scriptwriter/scriptwriter.go` emits either a fixed form or, when `UseLegacyBashEval` is true, the legacy form: [1](#0-0) 

The default (fixed) path wraps `eval` in an explicit subshell with its own `trap 'exit 1' TERM` and `< /dev/null` stdin redirection, specifically to stop SIGTERM (job cancellation) from causing the shell to dump the full `eval` body — which contains expanded CI variables, including masked secrets — to stderr/trace, per the comment directly above it and issue 39005: [2](#0-1) 

The legacy pipeline form has no such protection: it relies on the outer script's `trap 'exit 1' TERM` (line 123) propagating correctly into the `eval` side of the `:  | eval ...` pipe, which is exactly the historical bug: on affected bash versions (bash >= 5.3 and bash < 4.4, per the repo's own test comments) SIGTERM during execution causes the shell to print the currently-executing command — the whole `eval` argument, i.e. the entire script body with variables/secrets expanded — to the trace before terminating.

The activation path is: `Step.Run` sets `sw.UseLegacyBashEval = s.UseLegacyBashEval` [3](#0-2) , and `Step.UseLegacyBashEval` is populated in `builder.buildSteps`'s `configure` closure and in `buildGetSources` from `b.isFeatureFlagOn(featureflags.UseLegacyBashEval)` [4](#0-3) [5](#0-4) . `isFeatureFlagOn` falls back to reading the flag as a boolean job/CI variable when no runner-level override function is injected: `variables.DefaultBool(b.variables, flag, false)` [6](#0-5) . GitLab feature flags of the `FF_*` form are documented to be settable as ordinary CI/CD variables at the project/job level, so a pipeline author (the unprivileged attacker in scope) can set `FF_USE_LEGACY_BASH_EVAL=true` in their own `.gitlab-ci.yml` or job variables to force this vulnerable path for their own job.

The repository's own test suite explicitly documents and reproduces this exact scenario: `RunBuildWithScriptBodyLeakOnCancel` in `common/buildtest/bash_eval.go` cancels a build mid-script and asserts the canary text (representing script-body/secret content) does **not** appear in the trace — but the comment states this is "only ... asserted [for] the default (fixed) form" and that `FF_USE_LEGACY_BASH_EVAL` "is the known vulnerable escape hatch and is intentionally not exercised here" [7](#0-6) . `scriptwriter_test.go` further confirms structurally that the legacy form omits both the trap-reinstall and the `< /dev/null` isolation present in the default form [8](#0-7) .

Regarding the second half of the question (partially-substituted/double-executed/corrupted quote boundary on cancellation race): no evidence was found in `scriptwriter.go`, `step.go`, or the associated tests of a double-execution or quote-corruption race condition. The script is written once to a fixed temp file (`shell()` in `step.go`) and executed once via `e.Command`; SIGTERM only affects the running process's termination behavior, not re-invocation or re-parsing of the script text. That portion of the question is not substantiated by the code and is not asserted by this finding.

### Impact Explanation
On a runner/executor combination using an affected bash version, cancelling a job that has `FF_USE_LEGACY_BASH_EVAL=true` set (attacker-controlled via job/CI variables) while a `run:`/script step is executing causes the entire script body — with all expanded CI/CD variables, including masked/secret variables — to be written to the public job trace via SIGTERM-induced command echoing. This is a same-project secret disclosure (secrets referenced in that job's own script become visible in the trace, defeating GitLab's variable masking for that job) whenever the attacker/pipeline author can view the job log (which they normally can, since it's their own job).

### Likelihood Explanation
Preconditions are fully attacker-controllable: (1) set `FF_USE_LEGACY_BASH_EVAL: "true"` as a job/pipeline variable, (2) include a script with a masked/secret variable, (3) trigger job cancellation or let a timeout fire mid-execution. Cancellation is a standard, always-available user action (Cancel button / pipeline timeout / `after_script` never needed). The only external dependency is running on a bash version affected by the SIGTERM-dump behavior (bash >= 5.3 or < 4.4, per the repo's own test comments), which is a property of the job's chosen image/executor, itself attacker-selectable in many executor configurations (e.g., docker executor with a custom image pinning an affected bash). This makes the finding highly reproducible and repeatable, and it is explicitly called out as a known/intentional gap in the codebase's own comments and tests.

### Recommendation
- Deprecate/remove `FF_USE_LEGACY_BASH_EVAL` or, if it must be retained for a migration window, disallow it from being enabled via ordinary job/CI variables — require it to be a runner-config-level override only (i.e., always resolved via `opts.isFeatureFlagOn`, not falling back to `variables.DefaultBool` on `b.variables`), so a pipeline author cannot self-select the vulnerable path.
- At minimum, emit a masked-variable-aware warning or hard-block the legacy path when masked variables are present in the script when this flag is active.
- Extend `RunBuildWithScriptBodyLeakOnCancel` to also run against the legacy form (currently explicitly skipped) so CI enforces awareness of the residual exposure, or gate the flag behind a runner-admin-only configuration setting instead of a job-variable-controllable feature flag.

### Proof of Concept
Extend `common/buildtest/bash_eval.go`'s `RunBuildWithScriptBodyLeakOnCancel` (or add a sibling test) to run with `FF_USE_LEGACY_BASH_EVAL=true` explicitly forced on, against a bash image known to be affected (e.g., bash 5.3, as already wired for the docker executor per the existing comment), and assert:
1. `build.Variables` includes a masked variable whose value is embedded/echoed in the script body.
2. Cancel the build mid-`sleep` via `trace.Cancel()` as done in the existing test.
3. Assert `common.JobCanceled` failure reason is returned (cancellation path was exercised).
4. Assert the trace buffer **does** contain the canary/secret value in the legacy-eval configuration (proving the leak) versus **does not** contain it in the default configuration (existing passing assertion), demonstrating the discrepancy introduced specifically by `FF_USE_LEGACY_BASH_EVAL=true`.

// RunBuildWithScriptBodyLeakOnCancel verifies that cancelling a job does not
// dump the generated script body — including expanded variables — into the job
// log. See issue #39005 / !6784.
//
// When a job is cancelled the runner sends SIGTERM to the bash processes
// running the stage script (sendSIGTERMToContainerProcs / the bash.go
// cancellation script). On bash >= 5.3 (and bash < 4.4) the unfixed pipeline
// form caused the shell to print the command it was running — the whole eval
// body — to stderr, which lands in the public log. The trapped-subshell form
// turns the SIGTERM into a clean exit so no dump occurs.
//
// The leak is bash-version-specific, so this test only has teeth on an executor
// pinned to an affected bash (the docker executor wires it with a bash:5.3
// image); on an unaffected bash it still asserts the fix produces no dump. Only
// the default (fixed) form is asserted — FF_USE_LEGACY_BASH_EVAL is the known
// vulnerable escape hatch and is intentionally not exercised here.
//
// The behavior is bash-specific, so the check is skipped for non-bash shells.
func RunBuildWithScriptBodyLeakOnCancel(t *testing.T, config *common.RunnerConfig, setup BuildSetupFn) {
	if config.Shell != "" && config.Shell != "bash" {
		t.Skipf("script-body leak is bash-specific; skipping shell %q", config.Shell)
	}

	// Marker placed on a non-first line of a multi-line command. The shell
	// echoes only the first line of a collapsed multi-line command (see
	// AbstractShell.writeCommands), so the marker never appears in normal
	// output — it can only surface if the entire eval body is dumped to the log.
	const canary = "RUNNER_SCRIPT_BODY_LEAK_CANARY_e3b0c44298fc"
