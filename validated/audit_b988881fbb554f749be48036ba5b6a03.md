### Title
Unbounded recursive `TrieNode::decode` allows stack-overflow DoS via deeply-nested MPT node preimages - (File: crates/proof/mpt/src/node.rs)

### Summary
`TrieNode::decode` (the `Decodable` impl in `crates/proof/mpt/src/node.rs`) recursively decodes RLP-encoded trie nodes with no depth limit, mirroring the seroval issue where deeply-nested payloads exceed the call-stack limit during deserialization.

### Finding Description
`TrieNode::decode` handles a `Branch` node by decoding a `Vec<Self>` of up to 17 children via `Vec::<Self>::decode(buf)`, and each child element recurses back into `TrieNode::decode` [1](#0-0) . There is no depth counter or nesting-depth constant anywhere in the `mpt` crate — a `grep` for `depth` across `crates/proof/mpt/**` returns no matches, in contrast to the CBOR attestation parser in `crates/proof/tee/registrar/src/cbor.rs`, which explicitly threads a `depth` parameter through `CborItem::read_at` and rejects input once `depth > MAX_CBOR_NESTING_DEPTH` [2](#0-1) . That existing pattern shows the codebase is aware of, and elsewhere mitigates, exactly this bug class (CWE-770 via unbounded recursive-descent parsing), but the MPT trie-node decoder was not given the same protection.

Because Ethereum MPT nodes can inline any child encoding to at most 32 bytes before it must be "blinded" to a hash, a single crafted RLP buffer can still contain many nested small list structures (branch/extension/leaf wrappers) that legally decode without ever being blinded, each level consuming further call-stack frames in `TrieNode::decode`. A sufficiently deep chain of such nested, unblinded nodes will overflow the call stack in the process performing trie-node decoding.

### Impact Explanation
`TrieNode`/MPT decoding is core to the fault-proof program's state/account/storage trie traversal, which is explicitly in-scope as an attacker-reachable path (the fault-proof program processes preimages supplied through the untrusted preimage oracle during permissionless dispute-game execution). A stack overflow while decoding a maliciously deep trie-node preimage would crash/panic the process computing the trie root or account/storage proof, which can halt or corrupt fault-proof execution — i.e., prevent production of a correct provable output root or crash the verifier during a dispute game, which the validation rules for this analog explicitly treat as an in-scope, high-impact outcome ("wrong provable output root, node halt").

### Likelihood Explanation
Any dispute-game participant who controls preimage data fed into MPT node resolution (an unprivileged actor reachable path per scope) can construct the malicious nested-node RLP bytes; no special privilege, signature, or protocol-level access is required beyond supplying a preimage/proof that the fault-proof program will decode.

### Recommendation
Add an explicit recursion/nesting-depth bound to `TrieNode::decode` (and any recursive helper it calls), following the same pattern already used in `crates/proof/tee/registrar/src/cbor.rs`'s `MAX_CBOR_NESTING_DEPTH` guard — thread a depth counter into the branch/extension decode path and return a decode error once a maximum trie depth (bounded by the maximum possible real-trie depth, e.g. 64) is exceeded.

### Proof of Concept
Conceptually: construct an RLP buffer representing a chain of nested 2-element list nodes (extension-node shape) each small enough (<32 bytes) to remain un-blinded, nested far beyond typical trie depth (e.g., thousands of levels), and feed it to `TrieNode::decode`. Each nesting level recurses into `TrieNode::decode` again with no depth check, and the recursion will exhaust the call stack. This mirrors the unit test already present for the CBOR parser that explicitly asserts rejection of nesting deeper than `MAX_CBOR_NESTING_DEPTH` [3](#0-2) , which has no equivalent for `TrieNode::decode`.

**Note on uncertainty:** I could not trace the exact call path connecting an untrusted preimage-oracle byte stream to `TrieNode::decode` outside the `mpt` crate (the fault-proof program/host integration code was not found in the indexed portion of this repo), nor confirm whether an outer harness (e.g., a fixed Cannon/MIPS stack size) would turn this into a deterministic halt versus an exploitable divergence. This should be verified against the actual fault-proof program integration before treating the impact as confirmed rather than an analog based on the missing depth guard.
