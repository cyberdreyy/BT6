### Title
Global, caller-unscoped `req.ID` namespace in confidential relay `newActiveRequest` enables predictable-ID pre-registration DoS - (File: `core/services/gateway/handlers/confidentialrelay/handler.go`)

### Summary
`handler.HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty and ≤200 characters before calling `h.newActiveRequest`, which stores the request in a single shared `h.activeRequests` map keyed solely by the raw, attacker-supplied `req.ID` string, with no per-caller/tenant/workflow namespacing or authentication check at all in this handler. Any caller able to reach `HandleJSONRPCUserMessage` for this DON/handler can pre-register a request with an ID that a victim's legitimate job/workflow is about to use, causing the victim's subsequent call to fail immediately with `"request ID already exists"`.

Unlike the vault handler, which runs `h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)` (signature-based authorization) before calling `newActiveRequest` [3](#0-2) , the confidential relay handler performs **no authentication or per-caller binding whatsoever** before registering the ID in the shared map — it goes directly from length/emptiness validation to `newActiveRequest` and `fanOutToNodes`. There is no ownership prefix (e.g., `owner + separator + requestID` as vault uses for its response IDs) applied to the map key. This is confirmed by the existing unit test that demonstrates the exact collision behavior:

```go
func TestConfidentialRelayHandler_DuplicateRequestID(t *testing.T) {
	...
	err := h.HandleJSONRPCUserMessage(t.Context(), req, cb)
	require.NoError(t, err)

	cb2 := common.NewCallback()
	err = h.HandleJSONRPCUserMessage(t.Context(), req, cb2)
	require.ErrorContains(t, err, "request ID already exists")
}
``` [4](#0-3) 

Because `req.ID` is fully client-controlled JSON-RPC request data reaching this handler through `gateway.ProcessRequest` → `h.HandleJSONRPCUserMessage` [5](#0-4) , and the only length gate is applied both at the gateway layer and again inside the handler, any caller who can predict or observe the ID a victim workflow/job run is about to use (e.g. because it is derived from a predictable job run ID, workflow execution ID, or sequential counter) can submit that exact ID first. The victim's subsequent legitimate call then fails at `newActiveRequest` with `"request ID already exists"`, and the error is returned synchronously from `HandleJSONRPCUserMessage` before `fanOutToNodes` ever executes — the victim's relay call never reaches the DON.

### Impact Explanation
This is a targeted denial-of-service: a specific job/workflow relay request is silently blocked from completing because its `req.ID` collides with an ID an attacker deliberately pre-registered. Since the confidential relay handler has no authentication gate before ID registration, this requires no privilege beyond being able to send a message to this gateway handler — matching the stated "run-role credential" precondition. The impact is scoped to individual request/run failures (not global service disruption or fund loss), consistent with a bounded DoS impact class.

### Likelihood Explanation
Exploitability depends entirely on the attacker's ability to predict or observe the victim's future `req.ID` before it is submitted (e.g., sequential counters, deterministic IDs derived from workflow/job identifiers, or IDs leaked via other observable channels). Given that precondition, the attack is trivial and fully repeatable: submit one JSON-RPC message with the guessed ID slightly before the victim's job triggers. No signature forgery, credential theft, or race beyond simple timing is needed once the ID is known.

### Recommendation
Bind `req.ID` to the caller/tenant identity before using it as the map key, e.g., prefix the internal tracking key with an authenticated caller/owner identifier (as vault does for its outbound response IDs) or require request authentication before `newActiveRequest` is called, rejecting requests whose ID collides only when they originate from an already-known distinct caller. At minimum, add authentication and authorize-then-bind logic to the confidential relay handler analogous to `vault/handler.go`'s `ProcessRequest` authorization step, so pre-registration by an unrelated caller cannot block a legitimate caller's namespace.

### Proof of Concept
Extend the existing `TestConfidentialRelayHandler_DuplicateRequestID` test in `core/services/gateway/handlers/confidentialrelay/handler_test.go` to simulate two distinct callers:
1. Caller A (attacker) sends `HandleJSONRPCUserMessage` with `req.ID = "victim-job-42"` and no distinguishing owner/auth context, and it succeeds (`require.NoError`).
2. Caller B (victim), representing a different job/tenant, sends `HandleJSONRPCUserMessage` with the same `req.ID = "victim-job-42"` shortly after.
3. Assert `err` from step 2 contains `"request ID already exists"`, proving the victim's legitimate request is rejected purely due to ID collision with no per-caller namespacing — i.e., confirm there is no code path that distinguishes the two callers before the `h.activeRequests[req.ID]` check in `newActiveRequest`.
