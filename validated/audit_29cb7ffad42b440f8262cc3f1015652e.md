### Title
Vote-flip double-counts a single signer's weight in both accept and reject tallies, corrupting `BlockStatus.total_weight_rejected`/`total_weight_approved` used by the mining coordinator - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`BlockStatus` maintains a single shared `responded_signers: HashSet<u32>` that both the `Accepted` and `Rejected` `BlockResponse` branches are supposed to use to make sure each signer's weight is added exactly once, into exactly one bucket (`total_weight_approved` or `total_weight_rejected`). The two branches guard the weight increment inconsistently: the `Rejected` branch gates on `responded_signers.insert(slot_id)` [1](#0-0) , while the `Accepted` branch gates on a *different* set, `gathered_signatures.contains_key(&slot_id)` [2](#0-1) . A signer that first rejects a block (adding its weight to `total_weight_rejected` and its slot to `responded_signers`) and then re-evaluates and accepts the same block (e.g. after a re-proposal, or simply because it changed its mind) will have its weight added to `total_weight_approved` as well, since `gathered_signatures` never contained its slot. Its stale weight is never removed from `total_weight_rejected`. The aggregated per-signer accounting (`total_weight_approved + total_weight_rejected`) can therefore exceed the true number of distinct current votes, breaking the equality "aggregated rejected weight == weight of signers currently rejecting."

### Finding Description
`BlockStatus` (node-side, mining coordinator) is defined with a single `responded_signers` set intended to prevent a signer's weight from being counted twice across the whole life of a block: [3](#0-2) .

In the `Rejected` handler, the weight increment is correctly gated on the shared `responded_signers` set so a signer can only ever push its weight into `total_weight_rejected` once: [1](#0-0) .

In the `Accepted` handler, however, the weight increment is instead gated on `gathered_signatures.contains_key(&slot_id)` — a *different* map that is populated with signatures, not with vote-processing state: [4](#0-3) . Because `gathered_signatures` is not touched by the rejection path, a signer's earlier rejection has no effect on this check.

Consequence: for slot `S` belonging to signer weight `w`,
1. `S` sends `Rejected` → `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`.
2. `S` later sends `Accepted` for the same block (e.g. `handle_block_pre_commit`/re-evaluation on the signer causes it to reconsider and sign) → `gathered_signatures` does not contain `S` → `total_weight_approved += w` as well, and `S` is added to `gathered_signatures` and (redundantly) to `responded_signers`.

At this point `total_weight_rejected` still includes `w` from step 1 even though signer `S` no longer rejects the block — the reject tally is stale and no longer reflects any currently-rejecting signer. `total_weight_approved + total_weight_rejected` can now exceed `self.total_weight`, an invariant the coordinator implicitly relies on when deciding block fate: [5](#0-4) . (The reverse order — accept then later reject — does not trigger the bug, because the reject branch's `responded_signers.insert` will correctly return `false` the second time and skip the increment; the asymmetry is specific to the reject→accept ordering.)

### Impact Explanation
The coordinator (`signer_coordinator.rs::wait_for_block_signatures`-style loop) treats `total_weight_rejected` crossing the blocking-minority threshold as proof that ≥30% of weight has permanently rejected the block, and reacts by aborting block assembly and excluding transactions the rejectors flagged as failed: [6](#0-5)  (typo aside, same file as above). Because a flipped signer's stale rejection weight is never retracted, a single signer that rejects and then accepts can leave a permanent, phantom contribution in `total_weight_rejected` for the remainder of that block's lifetime in this coordinator instance. In combination with genuine rejections from other signers this phantom weight can push the tally over the 30% blocking-minority threshold earlier than actual signer sentiment warrants, causing the miner to spuriously treat the block as globally rejected (`NakamotoNodeError::SignersRejected`), unnecessarily discard or permanently exclude transactions, and repeatedly retry block assembly — a liveness degradation for block production that does not require a majority of signers to trigger (a single signer flipping its own vote is sufficient). This matches the "aggregated-weight vs verified-accepts equality" class called out in scope: the aggregated weight tracked in `BlockStatus` diverges from the actual set of signers presently holding each stance.

### Likelihood Explanation
Reaching this state requires no cooperation from other signers and no majority: any single honest-but-slow, or simply reconsidering, signer that sends a `Rejected` `BlockResponse` for a signature hash and later sends an `Accepted` `BlockResponse` for the *same* `signer_signature_hash` (which is entirely plausible in the normal re-evaluation flow described in the signer flows: `should_reevaluate_block` / `should_reevaluate_reject_reason` can move a block from `LocallyRejected` back to `LocallyAccepted`) will trip this bug automatically. No malicious majority, no auth token or key compromise is needed — this is a pure node-side counting-logic bug reachable by ordinary signer message traffic during normal operation.

### Recommendation
Use a single, consistent per-slot vote state (e.g. an enum `Accepted(weight)`/`Rejected(weight)`) keyed uniformly by `responded_signers`, and when a signer's vote flips, subtract its weight from the bucket it is leaving before adding it to the bucket it is entering, rather than gating the two branches on two different collections (`responded_signers` vs `gathered_signatures`). At minimum, the `Accepted` branch should check/update `responded_signers` (and, on flip, decrement `total_weight_rejected`) exactly as the `Rejected` branch does, so `total_weight_approved + total_weight_rejected` never exceeds the sum of currently-held distinct votes.

### Proof of Concept
1. Set up a reward set with 3 signers of weights approximately 35/35/30 (matching the existing `verify_signer_signatures` test fixtures) and a `StackerDBListener` tracking a `BlockStatus` for a proposed block's `signer_signature_hash`.
2. Signer A (weight 35) sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for the block → `responded_signers = {A}`, `total_weight_rejected = 35`.
3. Signer A later re-evaluates (e.g. after a pre-commit threshold from peers, mirroring the `should_reevaluate_reject_reason` path in `stacks-signer/src/v0/signer.rs`) and sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the *same* `signer_signature_hash`.
4. In `stackerdb_listener.rs`'s `Accepted` handler, `block.gathered_signatures.contains_key(&A)` is `false` (never populated by the reject path), so `total_weight_approved` is incremented by 35 to `35`, while `total_weight_rejected` remains `35` — unmodified.
5. Assert `block.total_weight_approved + block.total_weight_rejected == 70 > self.total_weight_of_signer_A_alone(35)`, demonstrating the same 35-weight signer is counted in both totals simultaneously, and that a second genuinely-rejecting signer of weight ~0 more than the blocking-minority threshold (`total_weight - weight_threshold`) would now spuriously trip `signer_coordinator.rs`'s `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` check even though signer A no longer rejects the block.
