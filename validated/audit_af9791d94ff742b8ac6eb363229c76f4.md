### Title
`defaultPendingClaimBasis` under-counts pending instant-withdraw receipts from earlier epochs, inflating `defaultRecoveryPrice` and overpaying active LPs and early claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`finalizeDefaultRecovery` computes the aggregate claim basis via `defaultPendingClaimBasis()`, which adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the instant receipts recorded in the *current* epoch — to `pendingWithdraws`. `pendingInstantWithdraws` is a global, cross-epoch aggregate, but instant receipts requested in *earlier* epochs and never fully funded are silently excluded from the recovery basis while remaining claimable. The result is a denominator that is too small, so `defaultRecoveryPrice` (and `activeFinalNAV` minted to the CDO) is inflated — the same bug class as the Xen grant-status translation writing past the declared array capacity: the declared basis is smaller than the actual set of claims written against it.

### Finding Description
- `requestInstantWithdraw` records receipts per-epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]`, while `pendingInstantWithdraws` aggregates all epochs ( [1](#0-0) ).
- `collectInstantWithdrawFunds` only decrements the global `pendingInstantWithdraws`; per-epoch keys are never migrated or cleared ( [2](#0-1) ). An unfunded remainder from epoch N therefore survives into epochs N+1, N+2, … under `instantWithdrawClaimsByEpoch[N]` while the global pending counter includes it.
- On default, `defaultPendingClaimBasis` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — only the *current* epoch key ( [3](#0-2) ). Old-epoch pending instant receipts are omitted from `totalBasis`.
- `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is therefore too large, and `activeFinalNAV = activeBasis * recoveryPrice` mints excess strategy tokens to the CDO, inflating active tranche recovery at the expense of the reserve ( [4](#0-3) ).
- Meanwhile `_defaultPrefundedInstantReserve` computes `instantBasis(current epoch) - pendingInstant(global)`; when old-epoch claims inflate the global pending counter above the current-epoch basis, it returns 0 — yet part of the strategy's held underlying is implicitly backing those old receipts and is simultaneously counted into `reserveAmount` only via other buckets, double-spending the same cash.
- After finalization, omitted old-epoch instant receipts are still payable: `claimInstantWithdrawRequest` only clears the `defaultRecoveryEpoch` key and then pays `instantWithdrawsRequests[_user]` in full ( [5](#0-4) ), drawing on a reserve sized for a smaller basis.

Concrete attack sequence (unprivileged lender):
1. Epoch N (running): borrower repays partially; attacker calls `requestInstantWithdraw` for amount X; CDO collects only part, leaving `pendingInstantWithdraws = X` and `instantWithdrawClaimsByEpoch[N] = X` unfunded.
2. Epoch N+1 starts (honest manager/borrower calls). Attacker (or anyone) makes another instant request Y → `instantWithdrawClaimsByEpoch[N+1] = Y`, `pendingInstantWithdraws = X + Y`.
3. Borrower defaults (honest failure to repay — no malicious privileged action needed); `finalizeDefaultRecovery` runs with `pendingInstantWithdraws != 0`, so basis = `pendingWithdraws + Y` — X is excluded.
4. `recoveryPrice` is inflated by factor `(active + pending + X + Y)/(active + pending + Y)`; the CDO is minted excess active NAV and each recorded claimant is overpaid per unit. The attacker then claims both the defaulted-epoch receipt at the inflated price *and* the still-live epoch-N instant receipt at par via `_transferFundedClaim`, extracting more underlying than the reserve was sized for; later claimants / residual reserve are left short — direct insolvency.

### Impact Explanation
The reserve is divided over a too-small basis, so (a) active tranche holders receive an inflated `activeFinalNAV` (excess `_mint(idleCDO, …)`), and (b) every defaulted-epoch receipt is paid at a price above the true recovery ratio. The omitted old-epoch receipts remain fully claimable at par. Total payouts exceed the recovered funds; the shortfall materializes as permanent loss for whoever claims last and/or as unbacked tranche value — direct theft/insolvency of unclaimed recovery, quantified as `reserveAmount * X / (trueBasis)` of overpay plus X paid at par with no budgeted basis.

### Likelihood Explanation
Requires: (i) an instant-withdraw request left partially unfunded across an epoch boundary (normal whenever borrower cash is tight — the pending bucket is precisely designed for this), and (ii) a subsequent borrower default — a normal credit event the whole `finalizeDefaultRecovery` path exists for. No privileged misbehavior, no oracle manipulation, no timing precision needed; the attacker only needs to hold a pending instant receipt from a prior epoch or simply be an early claimant after finalization.

### Recommendation
In `defaultPendingClaimBasis` (and `_defaultPrefundedInstantReserve`), account for *all* outstanding instant receipts, not just `instantWithdrawClaimsByEpoch[epochNumber]`. Since per-epoch keys cannot be enumerated, track a separate global `totalInstantWithdrawClaims` counter incremented in `requestInstantWithdraw` and decremented in `collectInstantWithdrawFunds`/claims, and use it for both the basis and the prefunded-reserve computation; or clear per-epoch instant keys when funding is collected so stale epochs cannot linger.

      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);

    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
