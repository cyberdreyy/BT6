Confirmed: there is no setter for `staking_pool_whitelist_account_id` after deployment — it's fixed for the life of the lockup contract by the `new()` constructor. [1](#0-0) 

### Title
`create`'s caller-supplied `whitelist_account_id` lets a front-runner deploy a squatted lockup with an attacker-controlled whitelist for the victim's `owner_account_id` - (lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the deployed lockup's account name deterministically from only `owner_account_id` (`sha256(owner_account_id)[..20] + factory_account`), and lets the *caller* — not the future owner — freely choose `staking_pool_whitelist_account_id` via the optional `whitelist_account_id` argument. An attacker can pre-empt a victim's intended `create` call by calling `create` first with `owner_account_id = victim`, funding it themselves and passing their own whitelist contract, permanently squatting the deterministic lockup address with an unvetted whitelist baked in for the contract's whole lifetime.

### Finding Description
Binding claimed: `staking_pool_whitelist_account_id` trusted by the deployed lockup == the account the entitled owner or factory operator actually vetted.

In `lockup-factory/src/lib.rs`, `create()` computes the lockup address purely from `owner_account_id`: [2](#0-1) 

and lets the caller override the whitelist that will be trusted forever by the deployed lockup: [3](#0-2) 

This value is passed straight into the lockup's `new()` and stored as `staking_pool_whitelist_account_id`, with no further validation that it is the factory's own `whitelist_account_id` or any foundation-vetted contract — the lockup constructor only checks the ID is syntactically valid: [4](#0-3) 

There is no setter to change `staking_pool_whitelist_account_id` after deployment — it is fixed for the life of the contract. Because account creation for `lockup_account_id` is a one-time, name-collision-guarded operation (`Promise::new(lockup_account_id).create_account()`), whichever `create` call executes first "wins" that deterministic address; a second `create` call with the same `owner_account_id` will fail at `create_account` and simply refund the caller via `on_lockup_create`'s failure branch: [5](#0-4) 

Exploit flow: the attacker observes (or predicts) that a victim intends to call `create(owner_account_id=victim, ...)` on the factory. The attacker front-runs with their own transaction: `create(owner_account_id=victim, lockup_duration=..., whitelist_account_id=Some(attacker_whitelist), ...)`, attaching the `MIN_ATTACHED_BALANCE` themselves. This deploys the lockup at the deterministic address with `owner_account_id = victim` (so the victim genuinely becomes and stays the entitled owner — `assert_owner` checks still work correctly for them) but `staking_pool_whitelist_account_id = attacker_whitelist`, a contract the attacker deployed and controls. The victim's own later `create` call for the same `owner_account_id` fails (account already exists) and is refunded — they never notice the squat produced a differently-configured contract, since they still successfully "have" a working, owned lockup at that address.

Once deployed, `select_staking_pool` in `lockup/src/owner.rs` always queries `self.staking_pool_whitelist_account_id` — now the attacker's own contract — via `ext_whitelist::is_whitelisted`: [6](#0-5) 

and the callback `on_whitelist_is_whitelisted` trusts whatever `#[callback] is_whitelisted` value comes back from that cross-contract call, with no check that the whitelist contract itself is the legitimate one: [7](#0-6) 

Since the attacker's whitelist contract can be programmed to always return `true`, any `staking_pool_account_id` the victim later selects — including one the attacker controls — passes the check as if it had been vetted by the real NEAR Foundation whitelist. Existing guards (`assert_owner`, `assert_self()`, `is_valid_account_id`, `assert_staking_pool_is_not_selected`, `assert_no_termination`) do not fail here: `assert_owner` correctly passes because the true victim is the owner; the flaw is entirely in which whitelist contract is trusted, a value the entitled owner never chose or approved.

### Impact Explanation
This directly matches the Critical category "a lockup deployed with parameters its rightful creator never chose": the victim's lockup exists with an owner-chosen `owner_account_id` but a whitelist contract they never selected or vetted, silently substituted by an unprivileged front-runner. Downstream, if the victim later stakes via `select_staking_pool`/`deposit_and_stake` (whether by mistake or because the attacker-controlled fake whitelist approves an attacker's pool), the real NEAR held in the lockup can be routed to and retained by an attacker-controlled staking pool, which is unconstrained by the legitimate NEAR Foundation vetting the whitelist is supposed to guarantee. This is repeatable for any `owner_account_id` the attacker can predict or observe being targeted, and does not require compromising the victim's keys — only winning a race on account creation.

### Likelihood Explanation
The attacker needs only: enough NEAR to cover `MIN_ATTACHED_BALANCE` (3.5 NEAR) for the squatted `create` call, knowledge/prediction of the victim's `owner_account_id`, and a self-deployed "whitelist" contract implementing `is_whitelisted` to always return `true`. No privileged role, foundation key, or victim key is required — this is squarely within the unprivileged attacker capabilities described. The main precondition is winning the race against the victim's own (or their operator's) legitimate `create` call, which is feasible when `owner_account_id`s are predictable (e.g., sequential employee onboarding, public allocation lists) or when the victim broadcasts/announces their intended lockup creation before it lands.

### Recommendation
Do not let an arbitrary caller override `whitelist_account_id` in `LockupFactory::create` at all — always use `self.whitelist_account_id` (the factory-vetted one) for `staking_pool_whitelist_account_id`, removing the parameter or restricting it to be settable only by the entitled owner (e.g., require `predecessor_account_id == owner_account_id`, or move whitelist selection to a post-deploy owner-only call). Additionally, consider binding the deterministic lockup address to the actual funding/predecessor account as well as `owner_account_id`, so an unrelated party cannot squat an address derived solely from a victim's intended owner identity.

### Proof of Concept
```rust
// lockup-factory/src/lib.rs test module (near-sdk unit test style, consistent with existing tests)
#[test]
fn test_frontrun_squat_with_malicious_whitelist() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker front-runs with owner_account_id = victim, but their own whitelist.
    context.predecessor_account_id = String::from(attacker_account()); // attacker pays
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // victim's intended owner_account_id
        lockup_duration,
        None,
        None,
        None,
        Some(custom_whitelist_account_id()), // attacker-controlled whitelist, not factory's default
    );

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let created = contract.on_lockup_create(
        lockup_account(), // deterministic address derived only from victim's owner_account_id
        ntoy(30).into(),
        String::from(attacker_account()),
    );
    assert!(created);

    // Assert: the deployed lockup's staking_pool_whitelist_account_id equals the
    // attacker's contract, NOT contract.whitelist_account_id (the factory-vetted one).
    // i.e. LockupArgs.staking_pool_whitelist_account_id (custom_whitelist_account_id())
    //      != contract.get_foundation/whitelist default (whitelist_account_id()).
    // Victim's later legitimate create() call for the same owner_account_id then fails
    // at create_account and is refunded, proving the squat is permanent:
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);
    context.predecessor_account_id = account_factory();
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let victim_create_result = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(account_tokens_owner()),
    );
    assert_eq!(victim_create_result, false); // victim refunded, squatted lockup with attacker whitelist remains live
}
```

```rust
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```

```rust
    /// Called after a given `staking_pool_account_id` was checked in the whitelist.
    pub fn on_whitelist_is_whitelisted(
        &mut self,
        #[callback] is_whitelisted: bool,

    ) -> bool {
```
