### Title
`capabilities.handler.HandleLegacyUserMessage` stores callbacks keyed only by client-supplied `MessageId`, allowing a second sender to silently overwrite another sender's in-flight callback - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`multiHandler.HandleLegacyUserMessage`/`HandleJSONRPCUserMessage` route purely by `Method` and delegate identity separation entirely to the downstream handler [1](#0-0) . The WebAPI capabilities handler (`MethodWebAPITrigger`) saves the user callback in a map keyed solely by `msg.Body.MessageId` — a value fully controlled by the requesting client — with no existence check and no binding to `msg.Body.Sender`, unlike the sibling `common.RequestCache` implementation which correctly composes the key from `{sender, id}`.

### Finding Description
In `handler.HandleLegacyUserMessage`, after validating the payload, the handler unconditionally stores the callback: [2](#0-1) 
The map `savedCallbacks` is declared as `map[string]*savedCallback`, keyed only by `id` (the `MessageId`) [3](#0-2) [4](#0-3) . There is no check for `sender` and no rejection if an entry already exists for that `MessageId` (contrast with `httpTriggerHandler.setupCallback`, `vault.handler.newActiveRequest`, and `confidentialrelay.handler.newActiveRequest`, which all reject with "already exists" errors on ID collision [5](#0-4) [6](#0-5) ). The correct pattern for sender-scoped isolation already exists in the codebase: `common.RequestCache` builds its key from `globalId{sender, id}` specifically to prevent cross-sender collisions [7](#0-6) [8](#0-7) .

Because `multiHandler` never inspects `msg.Body.Sender` and passes the raw message straight through [9](#0-8) , an attacker (Sender B) can submit a `web_api_trigger` request whose `msg.Body.MessageId` collides with a `MessageId` chosen concurrently by a different attacker (Sender A). Since `MessageId` is attacker-chosen and not required to be globally unique or scoped to the sender, `h.savedCallbacks[msg.Body.MessageId] = ...` silently replaces Sender A's saved callback with Sender B's. When the DON node's response correlating to that `MessageId` arrives, it will be delivered to whichever callback is currently in the map — potentially Sender B's callback receiving the result computed for Sender A's original request, and Sender A's request being orphaned until it times out via the pruning logic (`pruneCallbacks`), never receiving a response.

### Impact Explanation
This is a cross-user response confusion / request impersonation issue: an unprivileged attacker can (a) cause denial-of-service against another user's in-flight `web_api_trigger` request by choosing a colliding `MessageId`, and (b) potentially receive the response payload originally destined for the other sender's request if the attacker's overwrite occurs before that node response arrives. This falls under the "cross-user response confusion" / "unauthorized action on another user's request" impact class in scope.

### Likelihood Explanation
The only precondition is the ability to send two `web_api_trigger` gateway messages with a colliding `msg.Body.MessageId` while another sender's identical-ID request is still in-flight (bounded by `CallbackMaxAgeSec`, default 120s [10](#0-9) ). No special credential beyond ordinary gateway client access is required, and `MessageId` values are not validated for cross-sender uniqueness or randomness by the gateway, making exploitation feasible if IDs are ever predictable, sequential, or reused by a client library, or via racing two attacker-controlled identities against each other.

### Recommendation
Change `savedCallbacks` to be keyed by a composite of `(msg.Body.Sender, msg.Body.MessageId)` (mirroring `common.RequestCache`'s `globalId` pattern), and reject (rather than overwrite) any request whose composite key already has an in-flight entry, consistent with the existing-entry checks used in `http_trigger_handler.go`, `vault/handler.go`, and `confidentialrelay/handler.go`.

### Proof of Concept
Go handler-level test plan (`core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` with a mocked `handlers.DON`.
2. Build two `api.Message`s, `msgA` (Sender = "0xAAA...") and `msgB` (Sender = "0xBBB..."), both with identical `MessageId = "collide-1"` and `Method = web_api_trigger`, differing payloads.
3. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` then immediately `h.HandleLegacyUserMessage(ctx, msgB, callbackB)`.
4. Assert `h.savedCallbacks["collide-1"].Callback == callbackB` (i.e., callbackA has been evicted/overwritten) — proving the collision instead of an error being returned for the second call.
5. Simulate a node response for `MessageId = "collide-1"` and assert it is delivered to `callbackB`, while `callbackA` never receives any response (times out via `pruneCallbacks`), demonstrating cross-sender response confusion/DoS.
