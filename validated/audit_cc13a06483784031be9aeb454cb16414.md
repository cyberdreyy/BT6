### Title
`IdleCreditVaultWriteOffEscrow.deleteWriteOffRequest` can be front-run by `fullfillWriteOffRequest`, forcing a stale-priced sale of the lender's tranche tokens - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
A lender who escrowed tranche tokens can revoke the sell order via `deleteWriteOffRequest` at any time (no epoch-phase check), and any wallet can fill the order via `fullfillWriteOffRequest`. A fulfiller can front-run the lender's revocation transaction, paying the stale `underlyings` amount and seizing the escrowed tranche tokens — the same class as `revokeAll` being front-run by `claim`.

### Finding Description
- `createWriteOffRequest` escrows the lender's tranche tokens and stores `userRequests[msg.sender] = {tranches, underlyings}` [1](#0-0) .
- `deleteWriteOffRequest` deletes the request and returns the escrowed tranches. It has **no `isEpochRunning` gate** and no timelock, so revocation is intended to be always available [2](#0-1) .
- `fullfillWriteOffRequest` is explicitly callable by **any wallet**, requires only `_underlyings >= currentRequest.underlyings`, pays the lender `underlyings - fee`, and sends the escrowed tranche tokens to `msg.sender` [3](#0-2) .

Because matching is done against on-chain state at execution time, any fulfiller observing a pending `deleteWriteOffRequest` (or a `createWriteOffRequest` that lowers the ask is impossible — requests only accumulate) can insert `fullfillWriteOffRequest` in front of it. The deletion then reverts on `Is0()` since the request was already consumed. The lender's ability to revoke — the exact asset the external report's `revokeAll` protects — is nullified, and the escrowed tranches are transferred to the front-runner.

The economic loss materializes whenever the tranche tokens' actual redemption/recovery value exceeds the stale `underlyings` ask: after `finalizeDefaultRecovery` sets a recovery price, or when AA tranches are priced below par during a running epoch, a lender trying to cancel a now-underpriced order can be force-filled by any unprivileged EOA. Note `fullfillWriteOffRequest` itself has **no `isEpochRunning` check**, so fills (and thus this front-run) remain possible even in buffer/stopped phases where the lender may most want to exit.

### Impact Explanation
Direct theft of value: the lender permanently loses escrowed tranche tokens worth more than the underlyings received (loss = tranche recovery/market value − `underlyings`). The broken invariant is "one request, one outcome chosen by the owner": revocation and fulfillment race, and the fulfiller — not the asset owner — decides the outcome by ordering.

### Likelihood Explanation
Requires a pending mempool `deleteWriteOffRequest` and a stale underpriced ask. On mainnet, MEV searchers monitor exactly this pattern; whenever tranche value drifts above the ask (default recovery priced in, interest accrual, secondary-market premium), the front-run is profitable and gas-cost only. Medium likelihood, bounded by how often stale orders exist.

### Recommendation
Bind fulfillment to the lender's live consent: e.g., add an `isEpochRunning`/freshness check to `fullfillWriteOffRequest` symmetric to `createWriteOffRequest`, or have the fulfiller specify `maxTranches`/min-price parameters, or require the lender to countersign/refresh the ask (nonce or expiry timestamp) so an order cannot be filled against a stale price after the lender has signaled revocation.

### Proof of Concept
Foundry fork sketch (contracts live at `contracts/IdleCreditVaultWriteOffEscrow.sol`):

```solidity
// setup: epoch running, lender has tranche tokens
vm.startPrank(lender);
tranche.approve(escrow, 100e18);
escrow.createWriteOffRequest(100e18, 50e6); // ask: 50 USDC for 100 tranches
vm.stopPrank();

// time passes; tranche recovery value rises (e.g., finalizeDefaultRecovery) so
// 100 tranches are now worth ~100 USDC. Lender tries to cancel:
vm.prank(lender);
escrow.deleteWriteOffRequest(); // <-- front-run this tx

// attacker (any EOA) front-runs in the same block:
vm.startPrank(attacker);
underlying.approve(escrow, 50e6);
escrow.fullfillWriteOffRequest(lender, 100e18, 50e6);
vm.stopPrank();

assertEq(tranche.balanceOf(attacker), 100e18);        // attacker seized the tranches
assertEq(underlying.balanceOf(lender), 50e6 - fee);   // lender paid out at stale price
vm.prank(lender);
vm.expectRevert(Is0.selector);
escrow.deleteWriteOffRequest(); // revocation is now impossible
```

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

```text
  function deleteWriteOffRequest() external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[msg.sender];
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, currentRequest.tranches);
```

```text
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```
