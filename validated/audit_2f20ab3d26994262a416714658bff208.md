### Title
Re-proposal overwrite of an already-`GloballyAccepted` block silently wipes its signer-DB state, opening a same-height sibling-signing window - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`handle_block_proposal` builds a brand-new `BlockInfo` from every re-received `BlockProposal` and blindly persists it, wiping the previous `BlockState`, `valid`, `signed_self`, `signed_group`, and `approved_time` fields whenever `should_reevaluate_block` decides the block is eligible for re-evaluation. This is the CWE-524-class bug from the report translated into signer terms: instead of an HTTP header being clobbered, the signer's persisted equivocation-guard state (`BlockInfo`/`BlockState` in `signerdb`) is clobbered by a value the caller (the miner) controls, and downstream consumers (`get_tenure_last_block_info`, `get_last_signed_block`, `get_signed_conflicts`) trust that state as ground truth for whether "this signer has already committed to a block at this height."

### Finding Description
`BlockInfo::from(BlockProposal)` always constructs a fresh struct with `state: BlockState::Unprocessed`, `valid: None`, `signed_self: None`, `signed_group: None`, `approved_time: None`, `reject_reason: None`: [1](#0-0) 

`handle_block_proposal` unconditionally uses this constructor whenever `should_reevaluate_block` returns `true`, explicitly noting the overwrite behavior in its own comment: [2](#0-1) 

`should_reevaluate_block` only short-circuits (refuses to overwrite) when `block_info.globally_approved_and_responded()` is true: [3](#0-2) 

and `globally_approved_and_responded` requires `state == GloballyAccepted && (signed_self.is_some() || valid == Some(false))`: [4](#0-3) 

However, a block can reach `GloballyAccepted` **without** this signer ever validating or signing it itself. `mark_globally_accepted` is state-machine-legal from any prior state except `GloballyRejected`, and the `NewBlock` event handler calls it on any tracked block the moment the node's chain tip advances past it — regardless of whether this signer's own `valid`/`signed_self` were ever set (e.g., this signer's own validation request was slow or still pending while the rest of the signer set reached the 70% threshold and the block was already pushed to the node): [5](#0-4) [6](#0-5) 

In that race, `signed_self == None` and `valid == None`, so `globally_approved_and_responded()` returns `false`. Continuing through `should_reevaluate_block`: `reject_reason` is `None` (never rejected) so `should_reevaluate_reject_reason` returns `false`; the state is not `PreCommitted`; `determine_response` returns `None` because `valid` is `None`: [7](#0-6) 

With no pending validation recorded for this already-globally-accepted hash, the function falls through both branches with no early `return false`, and the trailing `true` at the end of `should_reevaluate_block` is returned: [8](#0-7) 

Back in `handle_block_proposal`, this `true` causes the exact same `BlockProposal` (miner simply re-sends/relays the identical, already-signed block it broadcast earlier — no new signature or majority needed) to overwrite the persisted `GloballyAccepted` `BlockInfo` with a fresh `Unprocessed` one, which is then written to `signerdb` via `insert_block` further down the same handler.

The invariant this breaks: downstream chainstate guards trust the DB's `state`/`signed_self`/`signed_group` columns as the durable record of "this signer already has skin in the game at this height." `get_tenure_last_block_info` (which feeds `check_latest_block_in_tenure`, used at proposal time, validate-ok time, and signing time) and the pre-commit "one last look" conflict guard (`get_signed_conflicts`, described in `docs/signer-flows.md` section 5) both depend on `get_last_signed_block`/state filtering to detect an existing committed/accepted block: [9](#0-8) [10](#0-9) 

While the row is reset to `Unprocessed` (during the window it takes to re-validate, or while queued behind `submitted_block_proposal`/`insert_pending_block_validation`), these guards see no committed/accepted block for that tenure/height, exactly like the CorsHandler's `set()` erasing the app's own `Vary: Authorization` value and letting the cache treat the response as if that constraint never existed.

### Impact Explanation
This maps to the Critical impact class defined in scope: "a signer signing an invalid, non-canonical, or conflicting block." During the overwrite window, a genuinely conflicting sibling proposal at the same height (same tenure or a different one) submitted to this specific signer would not be blocked by `check_latest_block_in_tenure`'s early rejection (no signed tip found) nor by the pre-commit conflict guard (`get_signed_conflicts` finds nothing at that height for this signer), because the persisted evidence of the earlier accepted block was wiped. This can lead this signer to sign a second, conflicting block at the same height it already helped finalize, contributing its signature weight toward an equivocating block.

### Likelihood Explanation
- Reachable by a single miner (or anyone relaying a previously observed `BlockProposal` StackerDB message) resending an already-known, already-signed block proposal — no majority, no other signer's key, and no auth_token/local access required.
- The triggering precondition (`signed_self`/`valid` both `None` while `state == GloballyAccepted`) requires this specific signer to have lagged behind the rest of the signer set on validating/pre-committing before the block reached the chain — a plausible, naturally occurring race under load or minor validation latency, not a contrived edge case; it is exactly the "single slow signer" scenario already exercised in `stacks-node/src/tests/signer/v0/signers_wait_for_validation.rs`.
- The overwrite window's duration is bounded by however long re-validation/re-queueing takes (`submit_block_for_validation`, `check_pending_block_validations`), so likelihood scales with node/validation latency and proposal timing by a hostile or careless miner.

### Recommendation
In `handle_block_proposal` (`stacks-signer/src/v0/signer.rs`), do not construct a brand-new `BlockInfo::from(block_proposal)` for a block whose prior `BlockInfo` already has `state == GloballyAccepted` (or, more generally, `is_locally_finalized()`/`has_reached_consensus()` true) — regardless of whether `signed_self`/`valid` happen to be set. Either (a) extend `globally_approved_and_responded()` (or add a new check) so any `GloballyAccepted` state short-circuits `should_reevaluate_block` to `false`, or (b) when re-evaluating is otherwise warranted, preserve the existing `state`/`signed_self`/`signed_group`/`approved_time` fields from the prior `BlockInfo` instead of discarding them, refreshing only fields safe to refresh (e.g. `proposed_time`). This ensures a block that the node/network has already finalized can never be reported to conflict-detection logic as `Unprocessed`.

### Proof of Concept
1. Configure a signer set where signer S is deliberately slow (or its validation RPC is delayed) relative to the rest of the set, as in `signer_waits_for_validation_before_signing`.
2. Miner proposes block A (height h). The other signers reach the 70% pre-commit/signature threshold and the block is pushed to the node before S's own validation for A returns; S receives a `NewBlock` event and, via `handle_event_match`'s `NewBlock` branch, calls `mark_globally_accepted()` on its tracked (still `signed_self=None`, `valid=None`) `BlockInfo` for A, persisting `state=GloballyAccepted` with no local signature evidence.
3. The miner (or any relay) re-sends the *identical* `BlockProposal` message for block A to S. On S, `should_reevaluate_block` returns `true` per the trace above, and `handle_block_proposal` overwrites A's `BlockInfo` in `signerdb` with a fresh `Unprocessed` one via `insert_block`.
4. While S is asynchronously re-validating A (or queued behind another in-flight validation), the miner proposes a conflicting sibling block B at height h (or a competing tenure-start block at height h in a new tenure). Because S's DB no longer reflects any signed/accepted block at height h in A's tenure, `check_latest_block_in_tenure`/`get_tenure_last_block_info` find nothing to reject B on and `get_signed_conflicts` (invoked from `handle_block_pre_commit`) finds no conflict for B, allowing S to proceed toward signing B despite having already helped finalize A at the same height.

    /// Get the last signed block from the given tenure if it has not timed out.
    /// Even globally accepted blocks are allowed to be timed out, as that
    /// triggers the signer to consult the Stacks node for the latest globally
    /// accepted block. This is needed to handle Bitcoin reorgs correctly.
    ///
    /// The timeout window is measured from the last time a signature actually covered the
    /// block: our own (`signed_self`) or the observed group/global acceptance
    /// (`signed_group`), whichever is later, matching how `get_signed_conflicts` measures
    /// endorsement freshness. `approved_time` is deliberately not used: it is stamped at
    /// pre-commit, which carries no signature, so it would close the window early. This also
    /// means a globally accepted block we never signed ourselves gets a full window from the
    /// time its acceptance was observed, rather than timing out instantly for lack of a
    /// timestamp.
    pub fn get_tenure_last_block_info(
        consensus_hash: &ConsensusHash,
        signer_db: &SignerDb,
        tenure_last_block_proposal_timeout: Duration,
    ) -> Result<Option<BlockInfo>, ClientError> {
        // Get the last signed block in the tenure
        let last_signed_block = signer_db
            .get_last_signed_block(consensus_hash)
            .map_err(|e| ClientError::InvalidResponse(e.to_string()))?;

        let Some(block_info) = last_signed_block else {
            return Ok(None);
        };

        // `approved_time` may hold the pre-commit time; use the actual signature time.
        let Some(signed_over_time) = block_info.signed_self.max(block_info.signed_group) else {
            return Ok(None);
        };

        if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
            > get_epoch_time_secs()
        {
            // The last accepted block is not timed out, return it
            Ok(Some(block_info))
        } else {
            // The last accepted block is timed out
            info!(
                "Last accepted block has timed out";
                "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                "signed_over_time" => signed_over_time,
                "state" => %block_info.state,
            );
            Ok(None)
        }
    }
