### Title
Node-side signer tally lets a single signer's rejection be recounted as an acceptance - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::run` tallies `BlockResponse::Accepted`/`BlockResponse::Rejected` messages from signers into `BlockStatus.total_weight_approved` / `total_weight_rejected`, which the miner's `SignerCoordinator` (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) uses to decide whether a block has been signed, rejected, or should be retried. The two branches use different, unsynchronized guards to decide whether to add a signer's weight, so a single signer who first rejects and later accepts the same block has their weight added to both tallies, breaking the "signed vs validated"/"aggregated-weight vs verified-accepts" invariant that the two totals represent mutually exclusive sets of signers. This is the same bug class as the `SpigotedLoan.updateOwnerSplit()` report: a state-mutating call path with an asymmetric/missing guard lets one uninvolved party (here, one signer, no majority needed) skew a tallied value that governs an important protocol decision.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the accept handler only guards weight addition on the `gathered_signatures` map: [1](#0-0) 

```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```

The reject handler guards weight addition on a *different* set, `responded_signers`, via an atomic test-and-insert: [2](#0-1) 

```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
```

Because `responded_signers` is written by *both* branches (line 465 for accept, line 515 for reject) but only *checked* by the reject branch, the sequence matters:

- Reject-then-Accept for the same `slot_id`: reject sets `responded_signers` and adds to `total_weight_rejected`. The later accept only checks `gathered_signatures` (still empty for this slot), so it adds the same signer's weight to `total_weight_approved` too. The signer's weight now counts in *both* tallies simultaneously.
- Accept-then-Reject is correctly protected: accept sets `responded_signers`, so the later reject's `responded_signers.insert(slot_id)` returns `false` and no rejected weight is added.

This is a one-directional guard, not a symmetric mutual-exclusion invariant. The intended invariant — that a signature and a rejection for the same signer/block are mutually exclusive — is implemented correctly elsewhere in the codebase, in the per-signer local DB used by `stacks-signer`: [3](#0-2) 

`add_block_rejection_signer_addr` explicitly checks for an existing signature first and refuses to record a rejection if one exists, and the corresponding tests confirm the intended contract in both orderings: [4](#0-3) 

The `stacks-signer` CHANGELOG documents this exact bug class as previously fixed ("Do not count both a block acceptance and a block rejection for the same signer/block"): [5](#0-4) 

but `stackerdb_listener.rs` — the miner/node-side aggregation path consumed by `signer_coordinator.rs` — does not implement the same guard.

### Impact Explanation
`total_weight_approved` and `total_weight_rejected` are read directly by the mining loop to decide the fate of a proposed block: [6](#0-5) 

These two counters are meant to represent disjoint sets of signer weight (a signer either accepted or rejected a given block, never both). With the bug, one signer's weight can be double-booked into both categories from a single sequence of two legitimately-signed StackerDB messages, corrupting the aggregated-weight vs verified-accepts equality that both the rejection-threshold check and the approval-threshold check rely on for correctness. This falls squarely under the "aggregated-weight vs verified-accepts" equality-break category, achievable by a single signer slot with no majority required.

### Likelihood Explanation
Any signer can publish two conflicting `BlockResponse` messages to their own StackerDB slot in sequence (e.g., due to a race, a bug, or intentional Byzantine behavior) for the same `signer_signature_hash`; the listener processes each StackerDB chunk update as an independent event, so this ordering is trivially reachable without coordinating with any other signer.

### Recommendation
Make weight bookkeeping symmetric: gate the accept branch's weight addition on `responded_signers` (or an equivalent unified "has this signer already been tallied for this block" check) rather than solely on `gathered_signatures`, and if a prior rejection exists for the slot, reverse/void the previously-added rejected weight (and any associated `failed_txids` weight) when a later valid acceptance for the same signer/block arrives — mirroring the mutual-exclusion contract already implemented in `stacks-signer/src/signerdb.rs`.

### Proof of Concept
1. Miner proposes block B; `StackerDBListener` creates a fresh `BlockStatus` for B's `signer_signature_hash`.
2. Signer S (slot `k`, weight `w`) publishes `BlockResponse::Rejected` for B. `handle` processes it: `responded_signers.insert(k)` succeeds, `total_weight_rejected += w`.
3. Signer S then republishes to the same StackerDB slot with `BlockResponse::Accepted` for the same B (e.g., changes its mind, or is byzantine). `handle` processes it: the check is `!gathered_signatures.contains_key(k)`, which is still true (only `responded_signers`, not `gathered_signatures`, was touched by step 2), so `total_weight_approved += w`.
4. Now `total_weight_rejected` and `total_weight_approved` both include `w` for the same signer `k`, even though S is a single signer and should only ever count once, on one side.

    /// Record an observed block rejection_signature
    pub fn add_block_rejection_signer_addr(
        &self,
        block_sighash: &Sha512Trunc256Sum,
        addr: &StacksAddress,
        reject_reason: RejectReasonPrefix,
    ) -> Result<bool, DBError> {
        // If this signer/block already has a signature, do not allow a rejection
        let sig_qry = "SELECT EXISTS(SELECT 1 FROM block_signatures WHERE signer_signature_hash = ?1 AND signer_addr = ?2)";
        let sig_args = params![block_sighash, addr.to_string()];
        let exists = self.db.query_row(sig_qry, sig_args, |row| row.get(0))?;
        if exists {
            warn!("Cannot add block rejection because a signature already exists.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %addr,
                "reject_reason" => ?reject_reason
            );
            return Ok(false);
        }
