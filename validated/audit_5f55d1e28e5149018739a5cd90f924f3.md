### Title
Stale `instantWithdrawClaimsByEpoch` after funded instant-withdraw claim inflates default-recovery reserve and price, draining recovery funds from later claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The curl leak frees the `push_headers` array without freeing each stored header string — per-element resources escape cleanup on a count-based path. `IdleCreditVault` has the same shape: instant-withdraw receipts are tracked both per-user-per-epoch (`instantWithdrawsRequestsByEpoch[_user][epoch]`) and per-epoch (`instantWithdrawClaimsByEpoch[epoch]`), but the funded claim path only clears the per-user aggregate `instantWithdrawsRequests[_user]` and never decrements the per-epoch counters. Those stale counters are later read by `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` during `finalizeDefaultRecovery`, which treats already-paid-out claims as still-backed reserves.

### Finding Description
`requestInstantWithdraw` increments `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . When the CDO funds the request, `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` but leaves `instantWithdrawClaimsByEpoch` untouched [2](#0-1) . The funded claim path then burns the receipt and zeroes only `instantWithdrawsRequests[_user]`, never clearing `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` [3](#0-2) . The claim is not epoch-gated, so a user can request an instant withdraw, have it funded, and claim the underlying all inside one epoch.

If the borrower defaults while `epochNumber` is still that epoch and some other instant request remains unfunded (`pendingInstantWithdraws != 0`), `defaultPendingClaimBasis()` re-adds the already-claimed `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis [4](#0-3) , and `_defaultPrefundedInstantReserve()` counts `instantBasis - pendingInstant` — which includes the paid-out amount — as cash the strategy supposedly still holds [5](#0-4) . `finalizeDefaultRecovery` then sets `defaultRecoveryReserve` and `defaultRecoveryPrice` using this phantom reserve [6](#0-5) . Because `defaultRecoveryEpoch` equals the still-current `epochNumber`, the stale epoch counter is used directly.

### Impact Explanation
The phantom amount X (the attacker's already-claimed instant withdraw) is added to both the claim basis and the reserve, but the underlying was already transferred out. Since `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` and the true reserve is `reserveAmount - X`, every defaulted-epoch claim is paid at an inflated price: early claimants (including the attacker, who can hold a second unfunded instant receipt or a normal withdraw receipt in the same epoch) are overpaid, and the real reserve runs out before the last claimants are served, permanently freezing their recovery. This is a direct theft of unclaimed recovery funds proportional to X, which the attacker controls by choosing the instant-withdraw size.

### Likelihood Explanation
Requires only unprivileged actions: a KYC-passing user calls `requestInstantWithdraw` (via the CDO instant-withdraw flow), the honest CDO funds it, the user claims, another user's instant request stays pending, and the borrower later defaults within the same `epochNumber` (epochs only advance at `stopEpoch` in `deposit()`, so a mid-epoch default keeps the same epoch). No privileged actor misbehaves, and no existing guard clears the stale per-epoch counters — the funded-claim path simply lacks the decrement that `_claimDefaultedInstantWithdrawRequest` performs on the same counters [7](#0-6) .

### Recommendation
In `claimInstantWithdrawRequest`'s funded path, clear the per-epoch accounting at the request's epoch(s): decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount. Since the funded path currently has no per-epoch cursor, track the request epoch for instant receipts (mirroring `lastWithdrawRequest`/`withdrawsRequestsByEpoch` for normal requests) or record the epoch at request time so the funded claim can decrement the correct `instantWithdrawClaimsByEpoch` entry.

### Proof of Concept
Foundry fork PoC sketch on the epoch variant + `IdleCreditVault` strategy:

```solidity
// 1. Pool is running in epoch N with instant-withdraw liquidity.
//    Attacker (allowed wallet) deposits AA, then:
cdo.withdrawAAInstant(X);               // -> requestInstantWithdraw(X, attacker)
// 2. Honest manager/borrower funds instant queue:
//    CDO calls strategy.collectInstantWithdrawFunds(X) -> pendingInstantWithdraws = 0
//    instantWithdrawClaimsByEpoch[N] still == X + victimPending
// 3. Attacker claims at par: CDO calls strategy.claimInstantWithdrawRequest(attacker)
//    -> instantWithdrawsRequests[attacker] = 0, but
//       instantWithdrawsRequestsByEpoch[attacker][N] == X   (stale)
//       instantWithdrawClaimsByEpoch[N]          still includes X   (stale)
// 4. Victim requests instant withdraw V in same epoch, left unfunded:
//    pendingInstantWithdraws = V
// 5. Borrower defaults; CDO calls finalizeDefaultRecovery(R, source):
//    basis   += instantWithdrawClaimsByEpoch[N]  (includes already-paid X)
//    reserve += _defaultPrefundedInstantReserve() = instantBasis - V  (phantom X)
//    -> defaultRecoveryPrice inflated by X / totalBasis
// 6. Assert: strategy token balance < defaultRecoveryReserve (phantom reserve)
//    and final claimant's claimWithdrawRequest/claimInstantWithdrawRequest reverts
//    on insufficient balance -> overpayment to early claimants, frozen remainder.
```

Run with `forge test --fork-url $RPC` targeting `contracts/IdleCDOEpochVariant.sol` + `contracts/strategies/idle/IdleCreditVault.sol`, asserting the mismatch between actual underlying held and `defaultRecoveryReserve` after step 5.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
