## Title
Stale reward-vs-delegation consistency check in partitioned epoch reward distribution can panic (cluster halt) when a stake account is mutated between reward calculation and distribution - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
The Olympus finding is a class of bug where a value computed from a wallet's balance/vote-power at one point in time (`vote()`'s snapshot of `VOTES.balanceOf`) is later compared against a *changed* balance (via `issueVotesTo`/`revokeVotesFrom`), producing an inconsistency that the contract does not reconcile. Agave has a structurally identical pattern in its partitioned epoch-rewards pipeline: stake rewards (and the resulting expected `Delegation::stake`) are computed once, at the epoch boundary "calculation" phase, from a `StakesCache` snapshot of each stake account. The actual crediting of lamports happens later, in `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` → `build_updated_stake_reward`, potentially many blocks after the snapshot was taken. In between, the stake account's owner can freely submit ordinary stake-program transactions (e.g. `Merge`, `Split`, `Withdraw`, `Deactivate`/`Redelegate`) that change `Delegation::stake`, and nothing in the stake program blocks this while an epoch's reward distribution is `Active`.

### Finding Description
`build_updated_stake_reward` fetches the *current* stake account from `stakes_cache_accounts` at distribution time [1](#0-0) , then adds the previously-computed `stake_reward`/`block_reward` lamports to it [2](#0-1) . When `adjust_delegations_for_rent` is `false` (i.e. the `relax_post_exec_min_balance_check` feature is not active), the code enforces that the *current* delegation plus the *stale, previously-computed* `stake_reward` must exactly equal the `new_stake.delegation.stake` value that was computed during the earlier calculation phase: [3](#0-2) 

This is enforced with `assert_eq!`, i.e. a hard panic, not a graceful error path (contrast with the `DistributionError` variants used elsewhere in the same function for recoverable failures) [4](#0-3) .

The reward-computation ("calculation") phase snapshots stake delegations and computes rewards well before distribution: `compute_new_epoch_caches_and_rewards` takes a snapshot of `stakes_cache.stakes()` and calculates activated stake / rewards from it [5](#0-4) , and the resulting per-stake rewards are stored and later replayed, one partition per block, over the following blocks via `distribute_partitioned_epoch_rewards` [6](#0-5) . Nothing in this pipeline re-validates or updates the previously-computed `stake_reward`/`new_stake.delegation.stake` if the underlying stake account is mutated by an ordinary user transaction (Split/Merge/Withdraw/Deactivate) during that window — this is exactly analogous to the Olympus bug: `userVotesForProposal` is fixed at `vote()` time and is later compared against a changed `VOTES` total supply, producing an inconsistent result. Here, the "old vote" is the pre-computed `new_stake.delegation.stake`, and the "changed total supply" is the actual on-chain `Delegation::stake` at distribution time, mutated by the account owner’s subsequent stake-program transaction.

There is already a regression test in the repo (`test_recalculate_stake_rewards_after_partial_distribution` context, `calculation.rs:2770-2799`) demonstrating that a StakesCache update to a larger delegation for the same vote account, applied between calculation and distribution, is a *known* scenario this code must tolerate for `recalculate_stake_rewards`, but the `assert_eq!` in `build_updated_stake_reward` shows the actual *distribution* write path (not the recalculation path) still hard-fails when a stake account's own delegation diverges from what was expected [7](#0-6)  vs [3](#0-2) .

### Impact Explanation
If `adjust_delegations_for_rent` is false on a given cluster (i.e. `relax_post_exec_min_balance_check` not yet activated), any staker can, with an ordinary signed stake-program transaction sent between the reward-calculation block and the block in which their stake account's partition is distributed (a window that can span many blocks depending on `num_partitions`), change their own stake account's `Delegation::stake` (e.g., via `Split`+`Withdraw`, `Merge`, or a deactivate/redelegate cycle) such that `stake.delegation.stake + stake_reward != new_stake.delegation.stake`. This triggers the `assert_eq!` panic inside bank processing on every validator that reaches that block height, i.e. a deterministic, transaction-triggered panic during normal (non-adversarial) bank operation — a cluster-wide halt condition, since all validators execute the same reward-distribution code deterministically at the same block height.

### Likelihood Explanation
Likelihood depends entirely on whether `relax_post_exec_min_balance_check` (which flips `adjust_delegations_for_rent` to `true` and removes the assert-guarded branch) is active on the target cluster/version. If it is inactive, the trigger requires only an ordinary staker performing a normal stake operation on their own account during the multi-block distribution window following the reward calculation for their epoch — no special privileges, no malicious leader, and no cross-account interaction are needed, making this readily reachable by any unprivileged staker. I was not able to fully confirm the current mainnet-beta/testnet activation status of `relax_post_exec_min_balance_check` within the available context, which is the main source of uncertainty in assessing current-day exploitability; if the feature is already active everywhere, this specific assert-guarded panic path is dead code in practice but the underlying design pattern (stale computed reward vs. live account state) remains structurally unchanged from the Olympus vote/vote-supply inconsistency class.

### Recommendation
Mirror the Olympus mitigation: at distribution time, do not assert that the live on-chain state matches the value computed at calculation time. Either (a) recompute the reward relative to the account's *current* delegation instead of asserting equality with the stale value, or (b) restrict the stake program from allowing delegation-changing instructions (`Split`, `Merge`, `Withdraw` below rent-exempt+delegation, `Deactivate`/`Redelegate`) for any stake account with a pending unpaid partitioned reward, analogous to disabling `issueVotesTo`/`revokeVotesFrom` while a vote is active. At minimum, replace the `assert_eq!` with a recoverable `DistributionError` variant so a legitimate user transaction cannot crash bank processing.

### Proof of Concept
Conceptual PoC (not executed, derived from existing test scaffolding in `distribution.rs`/`calculation.rs`):
1. Set up a bank with `relax_post_exec_min_balance_check` inactive, create a stake account, and let it reach an epoch boundary so that `compute_new_epoch_caches_and_rewards` computes a `stake_reward` for it and stores the reward status as `EpochRewardPhase::Calculation`, matching the setup pattern used in the existing test at [8](#0-7) .
2. Before the block corresponding to that stake account's partition index is reached, submit an ordinary stake-program transaction from the stake account owner that changes `Delegation::stake` for that account in the `StakesCache` (e.g. `Merge` with another stake account, mirroring how the existing test forces "StakesCache with a larger delegation for the same vote account" at [9](#0-8) , but applied to the *unpaid* index instead of only the already-paid one).
3. Advance to the block height that triggers `distribute_partitioned_epoch_rewards` → `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` → `build_updated_stake_reward` for that index [10](#0-9) .
4. Observe the `assert_eq!(expected_delegation, new_stake.delegation.stake, ...)` panic at [11](#0-10)  because the on-chain delegation no longer matches what was computed during the earlier calculation phase.

        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),

                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
