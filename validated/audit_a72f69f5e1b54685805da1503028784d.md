### Title
Stale confirmations from revoked multisig keys still count toward the K-of-N execution threshold - ([File: multisig/src/lib.rs])

### Summary
The `MultiSigContract::confirm` function authorizes and executes a request once `confirmations.len() + 1 >= self.num_confirmations`, but the set of confirmations is never revalidated against the multisig's currently live access keys. When a key is revoked via a `DeleteKey` request, only the *requests originally created* by that key are purged; any *confirmations* that key already cast on other still-pending requests remain in the `confirmations` set and continue to count toward the threshold indefinitely.

### Finding Description
`confirm()` reads `self.confirmations.get(&request_id)` and checks the *cardinality* of that set against `self.num_confirmations`, without checking whether each public key in the set is still an authorized key on the contract account: [1](#0-0) 

When a `DeleteKey` action is executed, the cleanup logic only removes requests that were *added* (signed) by the deleted key, plus its `num_requests_pk` counter. It does **not** scan `self.confirmations` to strip that key's stale approvals from other pending requests it merely confirmed: [2](#0-1) 

The intended custody binding for a K-of-N multisig is: *a request executes only once K currently-authorized members have approved it* — i.e. `|confirmations ∩ live_keys| >= num_confirmations`. The implemented check instead enforces `|confirmations| >= num_confirmations`, ignoring whether each confirming key is still live. Because `confirmations` is a plain `HashSet<PublicKey>` persisted per request with no invalidation hook tied to key removal, a confirmation given by a key that is subsequently deleted remains permanently valid for that request.

Concrete sequence (N=3 keys A, B, C; `num_confirmations = 2`):
1. Key A calls `add_request_and_confirm` on a `Transfer` request → `confirmations = {A}`.
2. Governance/owner rotates out key A for a legitimate reason (compromise, offboarding) via a separate `DeleteKey{public_key: A}` request approved by B and C. This purges A's *own* requests and its `num_requests_pk` entry, but the transfer request's `confirmations` set still contains A's now-deleted key.
3. Key B (a single live signer) calls `confirm(request_id)`. `confirmations.len() + 1 == 2 >= num_confirmations(2)` → `execute_request` runs the transfer.

The transfer executes with only one currently-valid signer (B) actively approving it plus a stale approval from a since-revoked key (A), even though the contract's security model requires 2 live keys to authorize any action.

### Impact Explanation
This breaks the multisig's core custody guarantee that funds/actions require confirmation from `num_confirmations` *currently authorized* members. After any legitimate key rotation that removes a signer who had previously confirmed an outstanding request, that request's threshold can be satisfied by combining the stale confirmation with fewer live signers than the configured `K`, allowing NEAR transfers, `AddKey`, `DeployContract`, or `FunctionCall` actions to execute below the intended threshold — a Critical-severity outcome per the stated impact categories ("a multisig request executed below threshold").

### Likelihood Explanation
Likelihood is high in realistic operational flows: key rotation (removing a departing employee, replacing a suspected-compromised key, or resizing the signer set) is a routine multisig operation exercised via the documented `DeleteKey` action. Any request left pending (not yet executed nor deleted, e.g. it is common for `add_request_and_confirm` to leave partially-confirmed multi-step requests open) across a key-rotation event is silently exposed. No privileged bypass, redeploy, or malicious validator is required — only the normal `DeleteKey` workflow and one live signer's subsequent `confirm` call.

### Recommendation
When executing `DeleteKey` (multisig v1) or `DeleteMember` (multisig2), iterate over all pending requests' `confirmations` sets and remove the deleted key/member's entry, not just the requests it originally created. Alternatively, revalidate the confirmation set at `confirm()`/execution time by intersecting it with the current set of live keys/members before comparing against `num_confirmations`.

### Proof of Concept
Rust-style walkthrough against `multisig/src/lib.rs`:
```rust
// num_confirmations = 2, keys = A, B, C
c.add_request_and_confirm(transfer_request);      // confirmations = {A}
// Separate request executed: DeleteKey{public_key: A}, confirmed by B, C
// -> purges only requests SIGNED by A; transfer_request.confirmations still == {A}
c.confirm(transfer_request_id);                    // called with key B
// confirmations.len() (1) + 1 == 2 >= num_confirmations (2) -> executes Transfer
// Result: Transfer executed with only 1 live signer (B) + 1 stale, revoked signer (A)
```
The analogous code path exists in `multisig2/src/lib.rs` (`DeleteMember` at lines 239-242), which likewise removes only requests created by the member without scrubbing stale confirmations from `self.confirmations`, though I was not able to fully trace `delete_member`'s internals within the available context to confirm identical behavior with certainty.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
