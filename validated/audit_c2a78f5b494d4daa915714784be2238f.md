### Title
Loss-adjusted withdraw receipts escape their epoch haircut and are later paid at par, draining other users' funded claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` applies the `stopEpochWithDuration` loss haircut only to the receipt recorded in the user's *latest* request epoch (`lastWithdrawRequest[_user]`). A user who holds a haircut receipt from epoch E can simply file a new `requestWithdraw` in a later epoch, which overwrites `lastWithdrawRequest`. The loss-epoch lookup then misses (`lossRecoveryPriceByEpoch[E+1] == 0`), the E-epoch basis stays in `withdrawsRequests[_user]`, and `_claimFundedWithdrawRequest` pays the entire aggregate at par — even though `collectWithdrawFunds` only funded it at the loss-recovery price.

### Finding Description
Like CVE-2018-18509, where a valid signature covers only part of the displayed message but the whole message is shown as "signed", the par-value "funded claim" attestation in `claimWithdrawRequest` covers receipt amounts that were never fully funded.

Concrete flow (running epoch, loss mode via `stopEpochWithDuration(_lossAmount)`):

1. Attacker calls `requestWithdraw` in epoch E. `requestWithdraw` records `withdrawsRequests[user] += amount`, `withdrawsRequestsByEpoch[user][E] += amount`, `pendingWithdraws += amount`, and `lastWithdrawRequest[user] = E` (contracts/strategies/idle/IdleCreditVault.sol:279-293).
2. Epoch E ends with a partial loss. `collectWithdrawFunds` computes `lossRecoveryPrice = funded * RECOVERY_FULL / pendingBasis` (e.g. 0.5e18), stores it in `lossRecoveryPriceByEpoch[E]`, zeroes `pendingWithdraws`, and pulls only the funded portion into the vault (lines 411-429). The attacker's receipt is now backed by only 50% of face value.
3. Instead of claiming, the attacker calls `requestWithdraw` again in epoch E+1. This sets `lastWithdrawRequest[user] = E+1` and adds a second, fully funded amount.
4. Epoch E+1 stops normally (`epochNumber` becomes E+2). The attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` = `lossRecoveryPriceByEpoch[E+1]` = 0 and returns 0 **without clearing the epoch-E basis** (lines 789-801). The haircut is never applied to the epoch-E receipt.
   - `_claimFundedWithdrawRequest` passes the wait check (`epochNumber > lastWithdrawRequest`), computes `amount = withdrawsRequests[user] + apr0 buckets`, which still includes the full epoch-E `normalAmount`, burns the receipt tokens, and calls `_transferFundedClaim(user, amount)` at par (lines 338-349).

The vault transfers 100% of the epoch-E receipt while only the loss-adjusted 50% was collected. `_transferFundedClaim`'s reserve guard (lines 897-906) only protects `defaultRecoveryReserve`; it does not compare the payout to the loss-adjusted funded amount, so it does not stop this.

### Impact Explanation
Direct theft / insolvency. The attacker is paid the unhaircutted face value of a receipt that was funded at, say, 50 cents on the dollar. The deficit is taken from underlying held in the vault that is earmarked for other users' funded normal/instant claims, so honest claimants' `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on insufficient balance or are paid less. The extractable amount equals `(1 - lossRecoveryPrice) * receiptBasis` — bounded only by the size of the attacker's loss-epoch request, i.e. proportional to their deposit. The epoch-E entry in `withdrawsRequestsByEpoch` is also never cleared, but this provides no recourse because the aggregate was already zeroed and paid.

### Likelihood Explanation
- Attacker requirement: any KYC-passing lender able to call `requestWithdraw`. No privileged role needed.
- Trigger condition: an epoch stopped via `stopEpochWithDuration` with `0 < _lossAmount` while `defaultRecoveryInitialized` is set — a normal, supported "BB-first loss / pending receipt haircut" mode of the vault, not an edge configuration.
- The attack requires only two ordinary `requestWithdraw` calls and one `claimWithdrawRequest`, sequenced around honest manager `stopEpoch`/`collectWithdrawFunds` calls.
- The per-epoch data (`withdrawsRequestsByEpoch`) exists precisely to distinguish epochs, but the loss path indexes `lossRecoveryPriceByEpoch` with a single mutable `lastWithdrawRequest` pointer, so multi-epoch pending receipts are mishandled by construction. There is no guard forcing a user to claim an open loss-adjusted receipt before requesting again (unlike the post-default flow, where `_hasWithdrawRequest` gating exists).

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, do not key the loss lookup solely on `lastWithdrawRequest`. Iterate (or track) all epochs with non-zero `withdrawsRequestsByEpoch[user][epoch]` having a non-zero `lossRecoveryPriceByEpoch[epoch]` and clear each through `_clearWithdrawClaimForEpoch`, or alternatively revert in `requestWithdraw` when the user has an unclaimed receipt in a loss epoch. A minimal fix: before overwriting `lastWithdrawRequest` in `requestWithdraw`, require that any prior request epoch either has `lossRecoveryPriceByEpoch == 0` or has already been cleared.

### Proof of Concept
Foundry fork PoC outline (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossReceiptEscapesHaircutViaSecondRequest() external {
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    address attacker = makeAddr('attacker');
    address victim = makeAddr('victim');
    uint256 amt = 100_000 * ONE_SCALE;

    // attacker and victim deposit AA (KYC'd), epoch 0 runs
    _depositWithUser(attacker, amt, true);
    _depositWithUser(victim, amt, true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // epoch 1 buffer: attacker requests withdraw of full tranche balance
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // epoch 1 runs, then stopEpochWithDuration realizes a loss so that
    // pending receipts are funded at lossRecoveryPrice < 1
    _startEpochAndCheckPrices(1);
    // borrower repays only part; manager stops epoch with _lossAmount
    // such that pendingToFund = 50% of pendingWithdraws
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, epochDuration, lossAmount); // partial loss
    assertLt(vault.lossRecoveryPriceByEpoch(1), vault.RECOVERY_FULL());

    // attacker does NOT claim; instead requests again in epoch 2 buffer
    // (deposits continue so a new epoch exists)
    idleCDO.depositAA(amt);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // lastWithdrawRequest = 2

    // epoch 2 runs and stops fully funded
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, initialProvidedApr, _expectedFundsEndEpoch());

    // attacker claims: epoch-1 loss receipt is paid at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    // paid == full epoch-1 face value + epoch-2 amount,
    // while vault only received 50% funding for the epoch-1 receipt.
    // The excess over funded amount comes out of the victim's funded claim:
    vm.prank(victim);
    vm.expectRevert(); // insufficient vault balance / NotAllowed
    cdoEpoch.claimWithdrawRequest();
}
```

Expected result: `paid` exceeds `receipt1 * lossRecoveryPrice + receipt2` by exactly `(1 - lossRecoveryPrice) * receipt1`, and the victim's claim can no longer be fully honored — demonstrating insolvency of the funded-claims pool.
