### Title
Invariant enforcement for `OverlayPrecompileStorage::checkpoint_revert` is a `debug_assert!` that compiles out in release builds, silently permitting corrupted overlay state during EIP‑8130 txpool admission - (File: crates/execution/txpool/src/validator.rs)

### Summary
The Cosmos SDK `x/crisis` report describes a class of bug where a critical invariant check exists but its *failure path* does not actually halt/protect the system in production — the check is effectively advisory. The Base txpool validator has the same bug-class shape: the safety invariant for `OverlayPrecompileStorage` ("the authorize-and-apply flow never performs a nested checkpoint/revert") is only enforced via `debug_assert!(false, ...)`, which is compiled to a no-op in release builds [1](#0-0) .

### Finding Description
`OverlayPrecompileStorage` is the `PrecompileStorage` backend used for EIP‑8130 (sponsored/authorized-transaction) admission in the txpool: it buffers `sstore`/`sload` writes for the duration of `TransactionAuthorizer::authorize_and_apply` and its `ConfigChangeAuthorizer` / `AccountChangeApplier` steps, and is only meant to be either fully committed on success or fully dropped on error [2](#0-1) . Because it never journals, `checkpoint()` is a no-op returning a default checkpoint [3](#0-2) , and `checkpoint_revert()` is also a no-op that relies solely on a `debug_assert!(false, ...)` to catch a violation of the "no nested revert" invariant [4](#0-3) .

`debug_assert!` is compiled out entirely in release builds. This means the only enforcement of the invariant — the only thing that would "halt" the flow the way an `x/crisis` invariant check is supposed to halt the chain — disappears in production binaries. If any current or future precompile/EVM code path invoked during `authorize_and_apply` (directly or through the `ConfigChangeAuthorizer`/`AccountChangeApplier` steps that this overlay drives) performs an internal `checkpoint`/`checkpoint_revert` cycle (e.g., a nested call that reverts partway through, which is normal EVM/precompile semantics elsewhere in the codebase — see the same `checkpoint`/`checkpoint_revert` contract exercised for ordinary halted calls in `crates/common/evm2/src/registry.rs:333-364`), the overlay would silently "revert" by doing nothing, i.e., it would keep already-buffered partial writes from the failed nested attempt instead of unwinding them. In a debug/test build this trips the assertion and panics; in a release build it silently proceeds with a corrupted overlay state.

This is architecturally the same failure mode as the reported `x/crisis` bug: an invariant that is supposed to stop unsafe execution from proceeding is enforced by a mechanism (`debug_assert!`) that is inert in the exact build configuration (release/production) where it matters, so the "no halt on invariant failure" condition is guaranteed by construction rather than accidentally.

### Impact Explanation
Because the txpool admission path for EIP‑8130 transactions is reachable by any unprivileged transaction sender/RPC client submitting a transaction that triggers `authorize_and_apply` (sponsored-transaction authorization and account/config-change application), a silent invariant violation here would let a transaction be admitted to the pool based on partially-applied, inconsistent authorization/config state rather than being correctly rejected. Depending on which fields leak through (allowances, role/config state used to gate authorization), this could translate into transactions being incorrectly authorized or incorrectly rejected at admission time — a wrong-provable-state / incorrect-authorization condition in a path that gates which transactions enter the pool. It does not, on its own, prove theft of funds; the primary provable, in-scope impact is that the invariant guaranteeing overlay correctness for this authorization path has no enforcement in production, and any future code change that introduces the nested revert this comment warns about would be silently accepted rather than failing loudly, undermining the correctness guarantee of the EIP‑8130 admission gate.

### Likelihood Explanation
Low-to-moderate. Exploitation is not currently demonstrated because it requires an as-yet-unidentified nested checkpoint/revert to actually be triggered from inside `authorize_and_apply`'s current call graph (`ConfigChangeAuthorizer` / `AccountChangeApplier`) by attacker-controlled inputs; the codebase's own comment asserts this "never" happens today. The risk is that this invariant is enforced only by a mechanism absent from release builds, so any future regression (a common occurrence as precompile logic evolves, as seen elsewhere in the codebase using nested calls and halts) would ship silently to production without any test or runtime safeguard catching it, exactly mirroring the reported bug class where the chain does not halt when the invariant check fails.

### Recommendation
Replace the `debug_assert!(false, ...)` in `checkpoint_revert` with an enforcement mechanism that is active in release builds — e.g., return a `BasePrecompileError::Fatal(...)` (which the codebase already classifies as a system error that must propagate and fail the transaction, per `BasePrecompileError::is_system_error` in `crates/common/precompile-storage/src/error.rs:75-79`) or otherwise make `authorize_and_apply` fail closed instead of silently continuing with un-journaled partial writes if a nested revert is ever attempted.

### Proof of Concept
Not independently demonstrated: producing a concrete transaction that forces a nested checkpoint/revert inside `authorize_and_apply`'s current `ConfigChangeAuthorizer`/`AccountChangeApplier` call graph was not verified within the available index/tooling, and the surrounding comments assert this path is not currently reachable. The finding is that the sole guard against this scenario (`debug_assert!`) is inert in release builds, so if such a path is ever introduced (intentionally or via a future precompile change), it would silently corrupt admission state in production rather than being caught, with no test coverage possible against a release-mode build to prove it is *not* reachable today. A Devin session with full repository and build access would be needed to trace every current call path into `authorize_and_apply` and confirm whether any of them can already trigger a nested `checkpoint`/`checkpoint_revert`.
