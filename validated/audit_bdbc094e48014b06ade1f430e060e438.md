### Title
Defaulted-epoch instant-withdraw receipts paid at par when claimed before instant claims are finalized, draining the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` only applies the default-recovery haircut when both `defaultRecoveryFinalized` and `defaultInstantWithdrawsFinalized` are true. If recovery has been finalized but the instant-withdraw bucket has not yet been finalized, the function falls through to paying the entire `instantWithdrawsRequests[_user]` balance — including receipts created in the defaulted epoch — at par from the funded claim path. The receipt tokens are burned and the ledger zeroed, so the haircut can never be applied retroactively. This is the closest analog to the gnutls use-after-free: a receipt whose accounting context (the default haircut) has already been "freed" by finalization is still consumed through a stale full-value path.

### Finding Description
In `claimInstantWithdrawRequest` (`contracts/strategies/idle/IdleCreditVault.sol:380-393`):

```solidity
if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
  _claimDefaultedInstantWithdrawRequest(_user);
}
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

The haircutted path `_claimDefaultedInstantWithdrawRequest` (`:842-856`) is skipped entirely when `defaultInstantWithdrawsFinalized == false`, even though `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` still holds the user's defaulted-epoch basis. That basis was never funded at par — `pendingInstantWithdraws` was decremented per funded amount in `collectInstantWithdrawFunds` (`:398-403`), and during finalization the unfunded remainder is only backed by `defaultRecoveryPrice < RECOVERY_FULL`. Paying it at par via `_transferFundedClaim` spends reserve/strategy underlyings earmarked for other claimants.

### Impact Explanation
An attacker holding a defaulted-epoch instant-withdraw receipt calls `cdoEpoch.claimInstantWithdrawRequest()` during the window between `finalizeDefault` (which sets `defaultRecoveryFinalized` and `defaultRecoveryPrice < 1`) and whatever call sets `defaultInstantWithdrawsFinalized`. They receive `instantWithdrawsRequests` at 100% instead of `defaultRecoveryPrice`, i.e. they steal `(1 - defaultRecoveryPrice) * claimBasis` of underlying from the recovery reserve. Since the strategy's underlying balance is finite and shared, every other defaulted-epoch claimant (normal receipts via `_claimDefaultedWithdrawRequest`, instant receipts via `_claimDefaultedInstantWithdrawRequest`) is paid less or reverts on insufficient balance — direct theft plus insolvency of the recovery reserve. The invariant "one haircutted receipt, one haircutted payout" is broken, and the state zeroing (`instantWithdrawsRequests[_user] = 0`) makes it unrecoverable.

### Likelihood Explanation
The attack requires a borrower default with pending instant-withdraw receipts and a claim executed in the gap before instant finalization. Whether that gap is reachable depends on the CDO-side sequencing (I could not fully trace where `defaultInstantWithdrawsFinalized` is set — it appears in `IdleCDOEpochVariant.sol` but the two matched lines were not sufficient to confirm it is always set atomically inside `finalizeDefault`). If it is set in a separate manager/owner transaction, the window is real and any unprivileged receipt holder can exploit it; severity is bounded by total defaulted-epoch instant claims but can be the full unfunded remainder.

### Recommendation
Revert in `claimInstantWithdrawRequest` when `defaultRecoveryFinalized && !defaultInstantWithdrawsFinalized && instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch] != 0` — i.e., do not let a defaulted-epoch receipt fall through to the par-funded path before its haircut is finalized. Alternatively, finalize the instant bucket atomically within `finalizeDefault`/`finalizeDefaultRecovery` so the two flags can never diverge.

### Proof of Concept
A Foundry fork PoC would: (1) deposit AA tranche, enable instant withdrawals, start epoch; (2) `requestInstantWithdraw` during the epoch so the receipt is booked in `instantWithdrawsRequestsByEpoch[user][epoch]`; (3) warp past `epochEndDate` with borrower unfunded so the pool defaults via `getInstantWithdrawFunds`/`stopEpoch`; (4) `finalizeDefault(recovered < pending)` setting `defaultRecoveryPrice < RECOVERY_FULL`; (5) before the instant-finalization call, invoke `claimInstantWithdrawRequest` and assert the user received the full `claimBasis` rather than `claimBasis * defaultRecoveryPrice / RECOVERY_FULL`, and that `underlying.balanceOf(strategy)` is now short versus `instantWithdrawClaimsByEpoch[defaultEpoch] * defaultRecoveryPrice / RECOVERY_FULL` owed to remaining claimants.

**Caveat:** step (5) depends on confirming a real ordering gap for `defaultInstantWithdrawsFinalized`; if the CDO sets it atomically inside the same finalization call, this path is unreachable and the finding reduces to a defense-in-depth gap.
