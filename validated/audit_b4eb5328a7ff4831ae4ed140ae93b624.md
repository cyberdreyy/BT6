### Title
Bridge `OutgoingToken` secret is disclosed to unprivileged/view-role users via `GET /v2/bridge_types/:BridgeName` - (File: core/web/presenters/bridges.go)

### Summary
`presenters.NewBridgeResource` unconditionally copies `bridges.BridgeType.OutgoingToken` into the JSON-serialized `BridgeResource.OutgoingToken` field, which lacks `omitempty` and is populated on every read path. `BridgeTypesController.Show`, `Index`, `Update`, and `Destroy` all call `NewBridgeResource` on data loaded straight from the ORM, so any authenticated caller allowed to hit these read endpoints receives the bridge's outgoing credential in plaintext, not just the creator at creation time.

### Finding Description
`BridgeType` stores `OutgoingToken` in plaintext (unlike `IncomingTokenHash`, which is hashed with a salt) [1](#0-0) . `NewBridgeResource` maps this plaintext value directly onto the presenter without redaction: [2](#0-1) . The `BridgeResource` struct's `OutgoingToken` JSON tag has no `omitempty`, while the analogous `IncomingToken` field is explicitly commented as "only provided when creating a Bridge" and does carry `omitempty`: [3](#0-2) .

`BridgeTypesController.Show` fetches the bridge from the ORM and passes it straight into `NewBridgeResource` with no field stripping: [4](#0-3) . The same pattern repeats in `Index`, `Update`, and `Destroy` [5](#0-4) [6](#0-5) [7](#0-6) . Only `Create` treats `IncomingToken` specially by attaching it from the ephemeral `BridgeTypeAuthentication` value, but it does nothing to redact `OutgoingToken` on the reused presenter either, and that's a one-time creation response, not the recurring problem — the systemic issue is that every subsequent `GET`/`PATCH`/`DELETE` response re-leaks the same secret indefinitely.

The `/v2/bridge_types/:BridgeName` route is reachable by any session/API-token holder permitted to call bridge-type endpoints (a role-gated but non-owner-scoped route — bridges are node-global resources, not scoped to the caller). Because the outgoing token authenticates node-to-external-adapter callback traffic, any caller who can read bridge metadata (not just edit it) obtains a live credential that can be used to impersonate the node's outgoing bridge requests, unrelated to whether they were the one who created that bridge.

### Impact Explanation
This is a secret/credential disclosure: the outgoing bridge token, meant to authenticate node→external-adapter traffic, is returned in full on every read of a bridge resource to any role permitted to view bridges. This falls under Chainlink's "key/secret disclosure" bounty class — a caller with only read/view access (not edit/admin) can extract long-lived credentials usable to spoof or impersonate legitimate bridge callback traffic.

### Likelihood Explanation
The vulnerability is trivially and repeatably exploitable by any caller authorized to hit `GET /v2/bridge_types/:BridgeName` (or `Index`) — no special privilege beyond whatever minimal role guards that endpoint is required, and it fires every single time the endpoint is called, not just at creation. This makes it highly likely to be found and exploited in any deployment exposing multiple credential tiers of API users to bridge-read endpoints.

### Recommendation
Add `omitempty` to `OutgoingToken` in `BridgeResource` and, more importantly, stop populating it in `NewBridgeResource` for read/list paths — only attach it transiently (like `IncomingToken`) on the `Create` response, or better, never return the raw outgoing token again after creation and instead support a rotate-and-reveal-once flow. Also strip it explicitly on `Index`, `Show`, `Update`, and `Destroy` responses.

### Proof of Concept
1. Unit test on `presenters.NewBridgeResource`: construct a `bridges.BridgeType{OutgoingToken: "secret-outgoing-token"}`, call `NewBridgeResource`, marshal to JSON, and assert the resulting JSON contains `"outgoingToken":"secret-outgoing-token"` — proving no redaction occurs by default.
2. Handler-level integration test extending `core/web/bridge_types_controller_test.go`: create a bridge via `Create` (capturing its `OutgoingToken` from ORM), then issue `GET /v2/bridge_types/:BridgeName` using a session/API key with only view-level permissions (not edit/admin), and assert the JSON response's `data.attributes.outgoingToken` field equals the stored plaintext secret — confirming a non-privileged read exposes the credential.

func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
