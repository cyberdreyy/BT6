## Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing requests to execute below the live-member quorum — (`multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges pending requests that were *authored* by the removed member; it never strips that member's confirmations from other members' pending requests. Because `confirm()` counts entries in the `confirmations: HashSet<String>` without re-validating that each entry still belongs to a current member of `self.members`, a request can be executed using a "phantom" confirmation from an account that has already been removed from the multisig. This breaks the intended equality `confirmations counted == live members who approved`, letting a transfer or other privileged action execute with fewer real approvals than `num_confirmations` requires.

### Finding Description
`add_member`/`delete_member` maintain `self.members: UnorderedSet<MultisigMember>` as the authoritative membership set, and `num_confirmations` is meant to represent a threshold over *live* members: [1](#0-0) 

`delete_member` removes the departing member from `self.members`, deletes their access key, and cleans up only the requests where `r.member == member` (i.e. requests they themselves *added*):

```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```

It never scans `self.confirmations` for entries where the removed member appears as a *confirmer* on a request authored by someone else. Those confirmation sets are left untouched.

`confirm()` then decides whether to execute a request purely by comparing the size of that untouched `HashSet<String>` against `self.num_confirmations`, with no check that every entry in the set is still a current member: [2](#0-1) 

`assert_valid_request` (called from `confirm`) only validates that the *caller* is currently a member and that the request/confirmations map entries exist — it does not re-validate the *existing* confirmers: [3](#0-2) 

Exploit path:
1. Member `M2` (benign) authors request `R` (e.g. a `Transfer`) via `add_request`.
2. Member `A` (about to be removed, e.g. suspected of key compromise) confirms `R` via `confirm(R)`. `confirmations(R) = {A}`.
3. Member `M1` confirms `R`. `confirmations(R) = {A, M1}` — still below the 3-of-4 threshold.
4. The remaining members (`M1`, `M2`, `M3`) submit and confirm a `DeleteMember{A}` request; `delete_member` succeeds because `members.len() - 1 (=3) >= num_confirmations (=3)`. `A` is removed from `self.members`, but since `A` did not author `R`, `R`'s confirmation set `{A, M1}` is left intact.
5. Member `M3` (a genuine, current member) confirms `R`. `confirmations.len() (2) + 1 == num_confirmations (3)`, so `execute_request` fires — even though only 2 of the 3 confirmers (`M1`, `M3`) are actually still members of the multisig; `A`'s stale vote is counted as if it came from a live member.

The `Transfer` (or `AddKey`/`DeployContract`/etc.) action in `R` is executed with only 2 real live confirmations against a nominal 3-of-N threshold.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold": funds can be transferred, or privileged actions (`AddKey`, `DeployContract`, `FunctionCall`) executed, without genuinely obtaining the configured number of live-member approvals. Since multisig custody guarantees rest entirely on the confirmation-count/threshold binding, this undermines the core security property of the contract and can lead to unauthorized movement of NEAR held by the multisig account.

### Likelihood Explanation
Moderate: it requires normal, expected multisig operations — one member's request accumulating partial confirmations, followed by removal of one of the confirmers (a routine security response to a compromised or departing member) — with no attacker action beyond being (at some point) a legitimate member and no reliance on victim keys, redeploys, or external actors. Any organization that rotates/removes multisig members while requests are in flight is exposed.

### Recommendation
In `delete_member`, in addition to purging requests authored by the removed member, iterate over all pending requests and strip the removed member's entry from every `confirmations` set (or lazily filter `confirmations.get(&request_id)` in `confirm`/`assert_valid_request` against `self.members` before counting). Alternatively, when counting confirmations in `confirm()`, intersect the stored confirmation set with the current `self.members` set before comparing against `num_confirmations`.

### Proof of Concept
See exploit path in the Finding Description above; it can be reproduced directly against `MultiSigContract::new`, `add_request`, `confirm`, and `execute_request via DeleteMember` in `multisig2/src/lib.rs` (lines 148-315 and 356-379) with a 4-member/3-confirmation setup as described.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
