Based on the analysis, this is not a valid vulnerability finding.

The `integration_acc_2` account in `LendingPoolAddBankSolend` is declared as a `SystemAccount<'info>` with only PDA seed constraints (no `init`), meaning `lending_pool_add_bank_solend` merely validates that the given address is derived correctly and currently owned by the System Program — it doesn't create or fund the account itself. [1](#0-0) 

The actual initialization happens later in `solend_init_obligation`, where `integration_acc_2` is declared with `#[account(init, payer = fee_payer, space = SOLEND_OBLIGATION_SIZE, owner = SOLEND_PROGRAM_ID, seeds = [...], bump)]`. [2](#0-1) 

An unprivileged attacker can only send lamports to the PDA address via a plain System Program transfer before it's created. Since a bare-lamport transfer to a non-existent address on Solana creates the destination as a zero-data account still owned by the System Program (an attacker's normal wallet cannot call `assign` on an account it doesn't own to reassign ownership to something else), Anchor's `init` constraint handles this pre-funded case gracefully: it recognizes the account as uninitialized (zero-length data, System-Program-owned), tops up any additional lamports needed for rent-exemption, and then performs `allocate`/`assign` via `invoke_signed` using the marginfi-derived PDA seeds to set the final owner (`SOLEND_PROGRAM_ID`) and space. This same pattern (PDA `init` after being merely pre-funded) is already exercised elsewhere in the codebase for other PDAs, e.g. `MarginfiAccountInitializePda`. [3](#0-2) 

Since the attacker cannot become the account's owner and cannot assign arbitrary data/ownership without the PDA's signing authority (which only the marginfi program derives, via `bank_signer!`), there is no path for authority hijack or account takeover — at most, the attacker permanently donates lamports to the account (a benign, one-directional value loss to the attacker, not the protocol). This matches exactly the "Scoped impact" framing in the question itself, and Anchor's own account-init logic already neutralizes this as a griefing vector rather than a security bypass. [4](#0-3) 

#### No Vulnerability found for this question.
