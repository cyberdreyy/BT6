### Title
Quadratic-time longest-common-prefix scan in `find_majority_prefix_replay_set` lets a single signer's `StateMachineUpdate` stall global-state evaluation - ([File: libsigner/src/v0/signer_state.rs])

### Summary
`GlobalStateEvaluator::determine_global_state` (called from `Signer::check_block_against_state` on every block-proposal evaluation pass) falls back to `find_majority_prefix_replay_set` whenever no signer's replay set reaches exact 70% agreement. That function repeatedly truncates a candidate transaction-prefix one element at a time and, for every truncation, re-scans *all* signers' replay sets calling `Vec::starts_with`, which itself is O(prefix length). This mirrors the js-yaml merge-key bug class: work that should be O(N) becomes O(N·L²) where L is the length of the `replay_transactions` list a single signer can put in its `StateMachineUpdateContent::V1`.

### Finding Description
`find_majority_prefix_replay_set` (`libsigner/src/v0/signer_state.rs:196-275`) is invoked from `determine_global_state` (`libsigner/src/v0/signer_state.rs:102-158`) once no exact-agreement replay set is found: [1](#0-0) 

The candidate prefix starts at the length of the most-supported replay set and is shortened one transaction at a time in a `while !candidate_prefix.is_empty()` loop; at every iteration it iterates over the *entire* `tx_replay_sets` map and calls `replay_set.0.starts_with(&candidate_prefix)`, an O(prefix-length) comparison. For a candidate of length L this is O(L) truncation steps × O(N·L) scan work per step = O(N·L²).

`tx_replay_sets` is built directly from each registered signer's own `StateMachineUpdate.content.tx_replay_set()` inside `determine_global_state`: [2](#0-1) 

`tx_replay_set()` reads the `replay_transactions: Vec<StacksTransaction>` field directly out of `StateMachineUpdateContent::V1`, a field that is filled and gossiped by each individual signer over StackerDB (`libsigner/src/v0/messages.rs`), and is inserted into the evaluator unconditionally via `insert_update` as long as the sender is a known signer address: [3](#0-2) 

A single registered signer (which the threat model allows — "gossip" from one signer without needing majority) can therefore broadcast a `StateMachineUpdate` whose `replay_transactions` vector is very long. Every other signer, on receipt, inserts this update via `check_block_against_state` (called once per block-proposal evaluation) and re-runs `determine_global_state`, hitting the quadratic path each time no exact agreement exists (which is guaranteed if the attacker's list disagrees with everyone else's).

### Impact Explanation
This does not break a signature-safety equality directly, but it degrades the pre-proposal evaluation pass that gates every block signature: `check_block_against_state` is on the hot path for every `BlockProposal` and `BlockValidationResponse` a signer processes, and it re-inserts/re-evaluates the global state machine each time. A large, sustained CPU cost injected by one signer's crafted replay-set list would slow or stall this evaluation on every peer signer for every proposal, pushing block-proposal responses past `block_proposal_timeout`/`tenure_last_block_proposal_timeout` and risking the signer failing to sign valid blocks in time — a liveness degradation of the class "signer wedged into never signing valid blocks," though the severity is bounded by the size limits StackerDB and the transaction/message encoding impose on `replay_transactions`, and by the small number of registered signers (N) which caps the fan-out term.

### Likelihood Explanation
The trigger requires only a single signer (or any peer able to place a message on that signer's StackerDB slot) sending one `StateMachineUpdate` with a long `replay_transactions` vector — no majority collusion is required, and it can be repeated on every burn/tenure change to keep re-triggering the expensive fallback. However, I could not verify within the available index whether `replay_transactions` (or the surrounding `StateMachineUpdate`/StackerDB chunk) is capped at a size small enough to make the quadratic blowup practically negligible; `libsigner/src/v0/messages.rs` defines the `StateMachineUpdateContent::V1` structure and its serialization, but I was unable to locate an explicit maximum-length check on `replay_transactions` in the excerpts retrieved. This bounds my confidence in the real-world severity of the CPU cost, and a background agent should confirm the actual size cap before treating this as high-likelihood.

### Recommendation
- Bound the total work in `find_majority_prefix_replay_set`: instead of re-scanning all sets from scratch at every truncation length, build a trie/prefix-count structure once (O(N·L)) or cap the number of truncation steps considered.
- Enforce an explicit maximum length on `replay_transactions` in `StateMachineUpdateContent::V1` (and reject/ignore updates exceeding it) at the point updates are validated/inserted (`GlobalStateEvaluator::insert_update`), independent of any StackerDB chunk-size limit, so the quadratic cost is provably bounded regardless of transport-level limits.
- Consider bailing out of the LCP search early once remaining candidate weight cannot reach the 70% threshold even in the best case, to shorten the truncation loop.

### Proof of Concept
Conceptual PoC (mirrors the js-yaml merge-chain PoC pattern):
1. Signer A broadcasts a `StateMachineUpdate` (`StateMachineUpdateContent::V1`) whose `replay_transactions` is the maximum-length list the wire format allows.
2. All other signers have empty or short/disagreeing replay sets.
3. On the next block proposal, every honest signer calls `check_block_against_state` → `determine_global_state` → `find_majority_prefix_replay_set`, which truncates A's L-length list one element at a time, each time rescanning the N-entry map with an O(L) `starts_with` call, costing O(N·L²) per evaluation, repeated on every subsequent proposal until A's update is superseded.

I was not able to fully confirm the concrete cap on L within the indexed files, so the exact CPU cost achievable in practice remains unverified — a Devin session with full repo access should measure `replay_transactions`'s maximum size (message/StackerDB chunk limits) to quantify real-world severity.
