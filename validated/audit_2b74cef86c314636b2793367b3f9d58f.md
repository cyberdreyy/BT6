### Title
Instant-withdraw claims never clear per-epoch receipt ledgers, causing double-counted default-recovery basis in the same epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a missing lock around the buddy allocator's trim path, letting a concurrent allocation corrupt shared free-list state. The analog in `IdleCreditVault` is a missing ledger update on the instant-withdraw claim path: `claimInstantWithdrawRequest` clears the aggregate receipt counter `instantWithdrawsRequests[_user]` but never clears the per-epoch ledgers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If the epoch in which those receipts were created later defaults at `stopEpoch`, `_claimDefaultedInstantWithdrawRequest` re-reads the already-paid basis and processes it a second time against the default-recovery accounting. [1](#0-0) 

### Finding Description
`requestInstantWithdraw` records a receipt in three places: the per-user aggregate `instantWithdrawsRequests[_user]`, the per-epoch map `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the epoch-wide `instantWithdrawClaimsByEpoch[currentEpoch]`. [2](#0-1) 

The normal funded claim only touches the aggregate: it burns `_user` receipts, sets `instantWithdrawsRequests[_user] = 0`, and pays via `_transferFundedClaim`. Both per-epoch ledgers retain the full claim basis forever. [3](#0-2) 

That is inconsistent with the defaulted-epoch claim path, which treats `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` as the authoritative outstanding basis: it zeroes the per-epoch entry, decrements the aggregate, decrements `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch`, and pays the claimant `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from the recovery reserve. [4](#0-3) 

Concrete trace:

1. Buffer before epoch N: a KYC'd lender calls `IdleCDOEpochVariant.requestWithdraw` while the APR-drop condition holds, creating an instant receipt `X` in epoch N (`instantWithdrawsRequestsByEpoch[user][N] = X`, `instantWithdrawClaimsByEpoch[N] = X`, `pendingInstantWithdraws += X`). [5](#0-4) 
2. `startEpoch` runs: the CDO forwards cash via `collectInstantWithdrawFunds`, decrementing `pendingInstantWithdraws` by `X`; `allowInstantWithdraw` is set. [6](#0-5) 
3. The user calls `claimInstantWithdrawRequest` and is paid `X` at par. Aggregate is zeroed; `instantWithdrawsRequestsByEpoch[user][N]` and `instantWithdrawClaimsByEpoch[N]` still equal `X`. [1](#0-0) 
4. At epoch N's `stopEpoch`, the borrower's transfer fails and `_handleBorrowerDefault` fires. Epoch N becomes `defaultRecoveryEpoch` at finalization. [7](#0-6) 
5. `finalizeDefault` → `finalizeDefaultRecovery` reads the epoch ledgers (`defaultInstantWithdrawsFinalized` marks exactly this step) and now sees `X` of ghost outstanding instant basis in epoch N that was already paid at par. [8](#0-7) 

Two consequences:

- **Ghost recovery claims**: the recovery multiplier is computed over an inflated outstanding basis, so the recovered amount is spread across receipts that no longer exist. The ghost share is never claimable — for the stale user, `instantWithdrawsRequests[_user] -= claimBasis` underflows (aggregate is 0) and reverts — so that portion of `defaultRecoveryReserve` is permanently frozen in the vault instead of accruing to genuinely unpaid claimants. [9](#0-8) 
- **Permanent claim lock for mixed users**: a user who claimed a funded instant receipt in the defaulted epoch and still holds another claim in the same call path (older funded receipts handled by the fallthrough branch, or post-default receipts) has `claimInstantWithdrawRequest`/`claimWithdrawRequest` revert permanently on the underflowing subtraction. [10](#0-9) 

### Impact Explanation
Recovered underlying routed to `defaultRecoveryReserve` in `finalizeDefaultRecovery` is sized against `instantWithdrawClaimsByEpoch[defaultEpoch]`. Because paid receipts are never removed from that counter, a share of the reserve is attributed to already-settled claims and can never be distributed — it sits in the vault with no sweep path after `defaultInstantWithdrawsFinalized`. Legitimate unfunded claimants of the defaulted epoch are diluted pro rata, and the residual is permanently frozen. This is a permanent freezing of funds owed to recovery recipients, scaling linearly with the amount of instant withdrawals that were claimed at par before the epoch defaulted. [11](#0-10) 

### Likelihood Explanation
Requires a specific but plausible sequence: instant withdrawals must be enabled (`disableInstantWithdraw = false`, a sufficient APR drop at `stopEpoch`), instant receipts must be claimed during the epoch, and the borrower must then default at that same epoch's stop. The attacker is only an unprivileged lender exercising documented request/claim orderings; the default trigger is honest manager/borrower behavior. No privileged role misbehavior is needed — the corruption is purely the stale ledger.

### Recommendation
In `claimInstantWithdrawRequest`, mirror the bookkeeping done for defaulted claims: decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` for the receipt's request epoch (tracked via `lastWithdrawRequest`-style per-user epoch pointer, or a dedicated `lastInstantWithdrawRequest` map). This keeps the per-epoch ledgers consistent with the aggregate so finalization only counts genuinely unpaid receipts. [3](#0-2)

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
