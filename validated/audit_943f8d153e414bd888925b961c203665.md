### Title
Unfunded instant-withdraw receipts are paid out of other users' funded claims in `claimInstantWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analog of CVE-2021-47321 (`del_timer()` that does not wait for the still-running handler): `claimInstantWithdrawRequest` "removes" (burns) the user's entire `instantWithdrawsRequests` receipt balance and immediately pays it out, without checking that the asynchronous funding step (`getInstantWithdrawFunds` → `collectInstantWithdrawFunds`) has actually settled the *latest* requests. A user can stack a funded instant receipt with a newly requested, still-unfunded instant receipt and claim both in one call, paying the unfunded portion out of underlyings reserved for other users' funded normal/default receipts.

### Finding Description
`requestInstantWithdraw` burns the CDO's strategy tokens and mints a receipt to the user, increasing `instantWithdrawsRequests[_user]` and the global `pendingInstantWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:356-375). The funds are only pulled from the borrower later, via `collectInstantWithdrawFunds`, which decreases `pendingInstantWithdraws` and transfers underlyings into the vault (lines 398-403).

The claim path, however, pays the *aggregate* user balance with no link between receipt and funding:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`_transferFundedClaim` (lines 897-907) only guards `defaultRecoveryReserve`; it does not reserve the funded balances of other claimants. So if the vault holds underlyings that belong to funded *normal* withdraw receipts (`withdrawsRequests`/`pendingWithdraws` already collected by `collectWithdrawFunds`), a claimant with `instantWithdrawsRequests = funded_old + unfunded_new` receives the full sum — the unfunded part is stolen from the funded normal receipts.

The timer analogy is exact: `del_timer()` = the request bookkeeping is cleared immediately; `del_timer_sync()` would be = wait until the async funding (`collectInstantWithdrawFunds`) has actually run for that receipt. The receipt is "freed" (burned and paid) while the asynchronous funding handler has not run.

### Impact Explanation
An unprivileged KYC-passed lender holding AA/BB tranche tokens can:

1. During epoch N buffer, request an instant withdraw of X (receipt minted, `pendingInstantWithdraws += X`).
2. Wait until the manager calls `getInstantWithdrawFunds`, which funds X into the vault.
3. In epoch N+1, request a second instant withdraw of Y (receipt minted, `pendingInstantWithdraws += Y`, but *not yet funded*).
4. Once the CDO's instant-claim timing gate is satisfied, call `claimInstantWithdrawRequest`, which burns X+Y receipts and transfers X+Y underlyings.

The Y portion is paid out of underlyings that back other users' already-funded normal withdraw claims (or the strategy's residual balance). Loss: up to the full second request amount Y, i.e. direct theft of other users' funded claims; equivalently a permanent insolvency for the last claimants, who will find the vault balance short when they call `claimWithdrawRequest`.

### Likelihood Explanation
Requires the instant-withdraw mode enabled (`setInstantWithdrawParams`, a manager action — but manager is honest and this is a supported mode), two epochs, and sequencing around the honest manager's funding call. No privileged misbehavior is needed; the attacker is just a tranche holder. The only mitigating factor is whatever timing gating `IdleCDOEpochVariant.claimInstantWithdrawRequest` applies to *new* requests in the current epoch — but nothing in the vault ties the claimed amount to per-request/per-epoch funding status, and `instantWithdrawsRequestsByEpoch` is recorded only for default accounting, not for a funded-vs-unfunded check.

### Recommendation
Track funded instant claims separately from pending ones. Either:

- In `claimInstantWithdrawRequest`, cap the payout to a per-user funded amount: `fundedInstantWithdraws[_user]`, incremented inside `collectInstantWithdrawFunds` proportionally (or per-epoch, using the existing `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` ledgers), and burn only that portion; or
- Keep a `fundedInstantWithdraws` global counter mirroring `pendingInstantWithdraws`, and in `_transferFundedClaim` reserve `pendingInstantWithdraws` (unfunded remainder) so claims can never spend underlyings earmarked for still-pending instant receipts — the equivalent of `del_timer_sync`, i.e. do not settle the receipt until its funding handler has completed.

### Proof of Concept
Foundry fork test against `IdleCreditVault` + `IdleCDOEpochVariant` (same harness as `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testUnfundedInstantClaimDrainsFundedReceipts() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);

    // epoch 0 -> 1 with low apr so instant withdraws are enabled
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // victim: normal withdraw request, funded at next stopEpoch
    address victim = makeAddr('victim');
    uint256 victimTranches = _depositWithUser(victim, amount, true);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(victimTranches, address(AAtranche));

    // attacker: instant withdraw X
    uint256 x = mintedAA / 2;
    cdoEpoch.requestWithdraw(x, address(AAtranche)); // routed to instant path per params
    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds();                       // attacker receipt X funded
    _stopEpochAndCheckPrices(1, initialProvidedApr / 2, _expectedFundsEndEpoch()); // victim receipt funded

    // epoch 2: attacker requests a second instant withdraw Y — NOT funded
    uint256 y = mintedAA / 4;
    cdoEpoch.requestWithdraw(y, address(AAtranche));
    _startEpochAndCheckPrices(2);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    // NOTE: no _getInstantFunds() for Y

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimInstantWithdrawRequest();   // burns X+Y receipts
    assertEq(underlying.balanceOf(address(this)) - balPre, x + y,
        'attacker paid for unfunded instant receipt');

    // victim's funded claim now underflows / vault is insolvent
    vm.prank(victim);
    vm.expectRevert(); // insufficient vault balance
    cdoEpoch.claimWithdrawRequest();
}
```

Note: I was unable to read the body of `IdleCDOEpochVariant.claimInstantWithdrawRequest`/`getInstantWithdrawFunds` within the available iterations, so the exact timing gate on the second request may need adjusting in the PoC (e.g., whether the second request must wait one epoch). The vault-side defect — burning and paying `instantWithdrawsRequests` in full regardless of funding state — is confirmed in `IdleCreditVault.sol` lines 380-393 and 398-403.
