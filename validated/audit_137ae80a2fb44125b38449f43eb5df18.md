### Title
Fail-open on node RPC failure lets a signer sign a conflicting block in its own tenure - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`handle_block_pre_commit` in `stacks-signer/src/v0/signer.rs` guards against a signer double-signing at the same block height by querying its own node for the tenure's canonical tip before signing a block that conflicts with one it already signed in that tenure. When that RPC call (`get_tenure_tip`) errors instead of returning a definitive answer, the code treats the unknown state as "unconfirmed" and falls through to sign the conflicting block anyway — the same "unresolvable input defaults to safe/allowed" pattern as the `dssrf` DNS-NXDOMAIN bug, where an inconclusive external answer (NXDOMAIN / RPC error) is silently treated as the permissive outcome instead of the safe one.

### Finding Description
`handle_block_pre_commit` collects `conflicts` — other blocks at the same or higher chain length that this signer already signed or saw signed, possibly in the same tenure — via `get_signed_conflicts` [1](#0-0) .

For a *fresh* conflict (`last_endorsed > freshness_cutoff`) that still blocks per `conflict_still_blocks`, the signer correctly refuses to sign [2](#0-1) .

But for conflicts in the block's **own tenure** whose `reorg_permit_stands` check fails (i.e. not covered by a sanctioned reorg permit — this is the path reached once the earlier signature has gone *stale*), the code asks the node for that tenure's canonical tip:

```
match stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash) {
    Ok(tip) => { ... if tip_height >= proposed height => refuse ... }
    Err(e) => {
        warn!("... Failed to fetch the canonical tip ... Treating the tenure as unconfirmed.");
    }
}
``` [3](#0-2) 

On `Err(e)` the function does **not** return — it falls through to the "no conflict still blocks" branch, logs that it is "signing the replacement," and proceeds to `mark_locally_accepted`, insert the block, and broadcast a signature over the new (conflicting) block: [4](#0-3) 

The project's own design docs confirm this is the intended, but explicitly risk-accepted, fail-open branch: "For the own-tenure question below, an unreachable node is instead treated as unconfirmed and the signature goes out," contrasted with every other branch of the same flow (`conflict_still_blocks`, `reorg_permit_stands`) which explicitly fails **closed** ("Whenever the node cannot be asked, the conflict keeps blocking") [5](#0-4) .

This asymmetry is the same equality-break pattern as the `dssrf` advisory: a query meant to resolve a safety-critical fact (is the tenure already at/above this height?) returns an inconclusive answer (RPC error, analogous to DNS NXDOMAIN), and instead of preserving the conservative default, the code treats the unknown as the permissive case and proceeds to the security-sensitive action (signing).

### Impact Explanation
If the node's tenure tip is actually at or above the proposed block's height — meaning the tenure has already progressed past the point of the earlier signed block, and the previously-signed block is potentially still canonical or already broadcast — but the RPC call transiently errors (timeout, connection reset, node under load, brief restart), the signer will place a fresh signature on a **second, conflicting block in the same tenure**. This breaks the one-signed-block-per-height invariant that the pre-commit conflict guard exists to enforce, one of the explicitly listed Critical outcomes ("a signer signing an invalid, non-canonical, or conflicting block").

### Likelihood Explanation
Triggering requires only: (1) a signer having previously signed a block in a tenure, (2) that signature going stale (past `tenure_last_block_proposal_timeout`), (3) a competing/re-proposed block for the same tenure at the same or higher height crossing the pre-commit threshold, and (4) the signer's `get_tenure_tip` RPC call to its own node failing at that moment. Steps 1–3 are ordinary, miner-triggerable re-proposal scenarios already anticipated by the surrounding logic (see the "async sibling validation" test suite) [6](#0-5) ; step 4 is a naturally occurring RPC failure mode and does not require a majority of signers, another signer's key, or volumetric flooding.

### Recommendation
Change the `Err(e)` arm of the `get_tenure_tip` match at [7](#0-6)  to fail closed — refuse to sign (return) rather than falling through to the "sign the replacement" path — consistent with every other node-query failure mode in this same function (`conflict_still_blocks`, `reorg_permit_stands`), which already fail closed per the documented design rationale.

### Proof of Concept
1. Signer S signs block B1 for tenure T at height H (`signed_self` set, recorded via `get_signed_conflicts`).
2. B1's signature goes stale (`last_endorsed` passes `freshness_cutoff`), and no reorg permit was recorded for T (`reorg_permit_stands` returns false).
3. A re-proposed/competing block B2 for tenure T at height ≥ H reaches the pre-commit threshold and is passed to `handle_block_pre_commit` on S.
4. At the moment S evaluates the same-tenure branch, S's call to `stacks_client.get_tenure_tip(T)` fails (any transient RPC/network error) even though the node's real tenure tip is actually at/above H.
5. The `Err(e)` arm at lines 1449–1455 only logs and does not return; execution falls to the "signing the replacement" branch and S signs B2 [4](#0-3) , producing two signer signatures over conflicting blocks in the same tenure at overlapping heights.
