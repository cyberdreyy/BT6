### Title
Zip cache-extraction leaves symlinks planted by earlier zip entries in place even on later per-entry failure, letting a subsequent fallback cache source write outside the working directory - (File: helpers/archives/zip_extract.go)

### Summary
`ExtractZipArchive` creates each zip entry (including symlinks) immediately and in-place, but never fails or aborts on a per-entry error — it only logs a warning and continues, and always returns `nil` at the end. This means a maliciously crafted zip-format cache archive can plant an escaping symlink and still be treated by the whole helper/extraction pipeline as if it were a legitimate cache miss/failure path is not even triggered normally, but a follow-up fallback cache extraction into the same working directory will silently write through any symlink left by a previous archive's entries.

### Finding Description
`ExtractZipArchive` iterates `archive.File` and calls `extractZipFile` for every entry; any per-entry error is only logged via `tracker.actionable(err)`/`logrus.Warningf`, never returned, and the loop keeps going to the next entry: [4](#0-3) . Symlink entries are materialized immediately, in file order, with `os.Symlink(string(data), file.Name)`, with no check that `file.Name` resolves within the destination root and no deferral like the tar/zstd extractor uses: [5](#0-4) . Contrast this with the tar+zstd extractor, which explicitly validates the resolved path stays under `e.dir` and *defers* symlink creation until the end of a successful pass specifically to avoid this class of issue: [6](#0-5) . The zip extractor has neither protection: no root-containment check on `file.Name`, and immediate (non-deferred) symlink materialization.

Because `ExtractZipArchive` always returns `nil` (line 109), and `Execute()` only calls `logrus.Fatalln` if `extractor.Extract` itself returns a non-nil error [7](#0-6) , a zip cache archive whose entries include `a` (symlink to `/tmp/evil` or another attacker-writable path) followed by `a/payload` (regular file entry) will: (1) create symlink `a` in the job's working directory, (2) `os.MkdirAll(filepath.Dir("a/payload"))` follows the existing symlink `a`, and (3) `extractZipFileEntry` writes `payload` through the symlink into the attacker-chosen target — all inside a single, "successfully" completing extraction attempt (since per-entry symlink escape isn't a returned Go `error` at all — `os.Symlink`/`os.Create` following a symlink into another dir succeeds without error).

This does not even require the "first source fails, second exploits it" retry chain described in the question: a single malicious zip cache archive is enough to escape the working directory in one shot, because there's no root-containment validation at all for zip in `extractZipFile`/`extractZipSymlinkEntry`/`extractZipFileEntry`. The multi-source/TOCTOU angle from the question (residual symlink from a *failed* first source surviving into a *second* source's extraction) is also plausible here specifically because `cmd.Dir = e.WorkingDir` is identical across all `s.Sources` attempts [1](#0-0)  and `CacheExtract.Run`'s loop continues to the next source on any failure of the previous one without cleaning the working directory [3](#0-2) : an attacker-poisoned first-source zip archive can plant a symlink and then deliberately trigger a later per-entry warning-only "failure" (which doesn't stop other entries anyway) or an outright `Extract`-level error from some other code path, and a second source (potentially referencing content the attacker doesn't fully control, e.g. a shared fallback key) that later writes a same-named path will walk through the leftover symlink.

Existing checks reviewed and found insufficient: there is no destination-root prefix check for zip entries (unlike the tar/zstd extractor's `filepath.Abs` + `strings.HasPrefix` check), no `zip.File.Name` path/`..` sanitization visible in `extractZipFile`, and no cleanup of the working directory between fallback-source attempts in `CacheExtract.Run`.

### Impact Explanation
An unprivileged pipeline author who controls the content of a cache archive (a normal `cache:` push from an earlier job in their own pipeline) can cause the runner's built-in cache-extraction helper to write arbitrary files to any path reachable from the job's working directory via a symlink — outside the intended `CI_PROJECT_DIR`/cache root — during automatic cache restoration of a later job. This is a "file write outside cache root" primitive, scoped to whatever filesystem access the job's own executor process already has (e.g., other paths within the executor's writable filesystem, sibling directories, or shared runner state depending on executor type). It does not on its own escape the executor sandbox further than the executor process already permits, but it breaks the invariant that cache extraction confines writes to the designated cache/build root.

### Likelihood Explanation
Fully reachable with only standard, unprivileged pipeline capabilities: a `.gitlab-ci.yml` job can push a `cache:` archive with attacker-chosen paths/content (including symlink entries, since GitLab Runner's own cache archiver supports symlinks) under a key the pipeline author controls, and any later job with a `cache:` restore of that key or a compatible fallback key will run the vulnerable extraction path. No special GitLab permissions, admin access, or executor misconfiguration is required beyond default cache push/pull behavior. This is highly repeatable and deterministic for the "single malicious zip" variant; the "second source through a residual symlink from a failed first source" variant is somewhat probabilistic (depends on how far zip's per-entry warn-and-continue loop got, or the ordering of failure vs. symlink creation) but the primary, always-reachable variant does not need randomness at all.

### Recommendation
Add root-containment validation to `extractZipFile`/`extractZipSymlinkEntry` analogous to the tarzstd extractor's `filepath.Abs` + prefix check on `e.dir`, reject entries whose resolved target escapes the destination directory, and defer symlink creation until after all other entries have validated successfully (or otherwise refuse to let any subsequently-extracted path traverse through an entry-created symlink). Additionally, make `ExtractZipArchive` fail fast (return a real error) on suspicious/escaping entries instead of only logging a warning, and have `CacheExtract.Run` clean/reset the working directory (or extract each fallback source into a fresh scratch directory that is only merged in on full success) between fallback-source attempts so a failed first source cannot leave any filesystem residue for a later source to walk through.

```go
func TestExtractZipArchiveSymlinkEscape(t *testing.T) {
    testInWorkDir(t, func(t *testing.T, _ string) {
        escapeDir := t.TempDir() // simulates a path outside the intended cache/working root

        buf := &bytes.Buffer{}
        zw := zip.NewWriter(buf)

        // 1. symlink entry "a" -> escapeDir
        hdr := &zip.FileHeader{Name: "a"}
        hdr.SetMode(os.ModeSymlink | 0777)
        w, _ := zw.CreateHeader(hdr)
        w.Write([]byte(escapeDir))

        // 2. regular file entry written *through* the symlink
        fw, _ := zw.Create("a/payload.txt")
        fw.Write([]byte("pwned"))

        zw.Close()

        r, _ := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
        err := ExtractZipArchive(r)
        require.NoError(t, err) // currently always nil -- demonstrates no failure signal

        // Assert the payload never landed outside escapeDir via the symlink
        _, statErr := os.Stat(filepath.Join(escapeDir, "payload.txt"))
        assert.True(t, os.IsNotExist(statErr), "file must not be written outside the extraction root via symlink")
    })
}
```

```go
	err = os.Symlink(string(data), file.Name)
	return
```
