### Title
Stale rejection weight is never retracted when a signer switches its vote to acceptance, letting one signer's weight double-count across both tallies - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` tallies `BlockStatus.total_weight_approved` and `BlockStatus.total_weight_rejected` from `BlockResponse` messages relayed over StackerDB. The rejection path gates its weight addition on `responded_signers.insert(slot_id)` (a per-slot, one-shot gate that is never cleared), while the acceptance path independently gates its weight addition on `gathered_signatures.contains_key(&slot_id)`. Because these are two different, non-communicating guards, a signer that first rejects a block and later legitimately reconsiders and accepts the same block (a normal, documented flow) has its weight counted into `total_weight_rejected` *and* into `total_weight_approved`, with the rejected weight never retracted.

### Finding Description
In the `Accepted` branch [1](#0-0) , the weight is added only if `!block.gathered_signatures.contains_key(&slot_id)`. In the `Rejected` branch [2](#0-1) , the weight is added only if `block.responded_signers.insert(slot_id)` returns `true` (first time seen).

These two guards are independent: a rejection inserts the slot into `responded_signers` but not into `gathered_signatures`. If that same signer later sends an `Accepted` message for the same block (e.g. after `should_reevaluate_reject_reason` allows reconsidering a stale/now-resolved rejection reason, as described in `docs/signer-flows.md` section 3), the `Accepted` branch sees `gathered_signatures` does *not* yet contain the slot, so it adds the signer's weight to `total_weight_approved` — while the earlier weight added to `total_weight_rejected` is never removed. The signer's weight is now counted in both buckets simultaneously and permanently.

This breaks the invariant that `total_weight_approved` and `total_weight_rejected` are supposed to represent mutually-exclusive current votes summing to at most `total_weight`. The stacks-signer's own SQLite bookkeeping in `signerdb.rs` (`add_block_rejection_signer_addr`) explicitly guards against a signer having both a stored signature and a rejection recorded at the same time [3](#0-2) , and the CHANGELOG documents this exact class of bug being fixed once already ("Do not count both a block acceptance and a block rejection for the same signer/block") [4](#0-3) . The `StackerDBListener` reimplements this tally independently on the node/miner side and reintroduces the same class of bug via mismatched guard variables.

### Impact Explanation
The miner's decision loop in `SignerCoordinator::get_block_status` checks rejection before acceptance every iteration [5](#0-4) :
```
if total_weight_rejected + weight_threshold > total_weight { reject }
else if total_weight_approved >= weight_threshold { accept }
```
Because `total_weight_rejected` retains stale weight from signers who have since switched to accepting, it can cross the "blocking minority" threshold purely from stale votes, even while `total_weight_approved` simultaneously (and correctly) reaches the acceptance threshold from the very same signers' current, valid signatures. Since the reject branch is checked first, the miner can incorrectly conclude the block was globally rejected (`SignersRejected`), discard the gathered valid signatures, and potentially permanently exclude transactions (`permanently_excluded_txids`) that a real blocking minority never actually rejected. This is a liveness wedge: legitimately signed blocks/transactions can be discarded and mining can stall or repeatedly re-propose based on phantom rejection weight that should have been retracted.

### Likelihood Explanation
This requires no majority collusion or key compromise — it is triggered purely by the normal behavior of a single honest signer reconsidering a rejection (a supported, documented flow: `should_reevaluate_reject_reason` / "signer_can_accept_rejected_block" test scenario). Any block that is rejected and then re-proposed/re-considered by even one signer exercises this path, making it readily reachable in ordinary operation, not just adversarially.

### Recommendation
Use a single, shared per-slot "current vote" state (e.g. an enum `Accepted`/`Rejected` keyed by `slot_id`) to gate both branches, and when a signer's vote changes, retract the weight from the previous bucket before adding it to the new one — mirroring the safeguard already present in `signer_db::add_block_rejection_signer_addr`/`add_block_signature` on the signer side. Alternatively, gate the `Accepted` branch on `!block.responded_signers.contains(&slot_id) || previous_vote_was_rejected`, and subtract `signer_entry.weight` from `total_weight_rejected` whenever a slot transitions from rejected to accepted (and vice versa).

### Proof of Concept
1. Miner proposes block B to signer set with per-signer weight `w`.
2. Signer S (slot `k`) sends `BlockResponse::Rejected` for B (e.g. `ProposalTooOld` or a reason later deemed re-evaluable). `stackerdb_listener.rs` line 515-518 sets `responded_signers.insert(k)` and adds `w` to `total_weight_rejected`.
3. The block is re-proposed (unchanged hash) or S's local state re-evaluates the rejection as resolved; S sends `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. Line 443's check `!gathered_signatures.contains_key(&k)` is `true` (first acceptance), so `total_weight_approved` also gains `w`. `total_weight_rejected` still contains `w` from step 2 — never decremented.
5. Repeat/accumulate with enough other signers so that `total_weight_rejected + weight_threshold > total_weight` becomes true purely due to stale weights like S's, even though `total_weight_approved >= weight_threshold` from current votes. `SignerCoordinator::get_block_status` (lines 509-545) evaluates the reject branch first and returns `NakamotoNodeError::SignersRejected`, discarding the valid signature set gathered in `gathered_signatures`.
