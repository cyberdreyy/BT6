### Title
Unskimmed underlying donations are crystallized into NAV and create unbacked withdraw claims - ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary
An unprivileged sender can transfer underlying tokens directly to `IdleCDOCreditVault`, after which any depositor causes `_updateAccounting()` to include the unsolicited balance in managed NAV. When the epoch manager later calls `startEpoch()` or `stopEpoch()`, `_skimDonatedAssets()` removes that same balance, leaving recorded tranche NAV and potentially pending withdrawal obligations without corresponding strategy-token backing.

### Finding Description
`IdleCDOCreditVault.getContractValue()` counts both the CDO's strategy-token balance and its raw underlying balance. [1](#0-0) 

`_deposit()` calls `_updateAccounting()` before transferring the depositor's assets and before any donation-skimming operation. [2](#0-1) 

Consequently, a direct ERC20 transfer to the CDO is interpreted as protocol gain during the next deposit. `_updateAccounting()` records that gain in `unclaimedFees`, `lastNAVAA`, `lastNAVBB`, `priceAA`, and `priceBB`. [3](#0-2) 

The same raw balance is later treated as an unsolicited donation and removed by `_skimDonatedAssets()` at epoch start. [4](#0-3) 

If the depositor first creates a withdrawal request, the inflated price can be converted into an address-bound strategy-token receipt and added to `pendingWithdraws`. [5](#0-4) 

The donation is therefore counted once as tranche NAV or withdraw-request basis and then physically removed as an unrelated donation, producing two claims on the same tokens.

### Impact Explanation
A KYC-passing tranche holder can make a deposit after an underlying transfer, crystallize the donated amount into tranche NAV, and optionally request withdrawal before the manager calls `startEpoch()`.

For a donation `D`:

1. `D` is included in NAV during `_deposit()`.
2. The donor-controlled tranche position or withdrawal receipt receives up to `D` of additional claim value.
3. `startEpoch()` transfers `D` to `feeReceiver`.
4. The recorded NAV or pending withdrawal obligation remains higher than the managed strategy-token backing by up to `D`.

This is quantifiable insolvency or borrower-claim theft. The attacker can also wait for an unrelated accidental direct transfer, so the attack does not require the attacker to permanently sacrifice the donated amount for the protocol insolvency to occur.

### Likelihood Explanation
The trigger requires only an unprivileged ERC20 transfer plus an ordinary deposit or withdrawal-request transaction during the buffer phase. The subsequent skim is performed by the honest owner or manager as part of normal `startEpoch()` processing.

The issue does not require privileged misconduct, a borrower default, external oracle manipulation, an unbounded loop, or an ERC4626 price move.

### Recommendation
Use one consistent definition of managed NAV:

- Prefer changing `IdleCDOCreditVault.getContractValue()` to return `_managedContractValue()`, so unsolicited raw underlying is never included in tranche accounting.
- Alternatively, call `_skimDonatedAssets()` before `_updateAccounting()` in every accounting entry point, including `_deposit()` and withdrawal-request paths.
- Add a fork regression test proving that a direct underlying transfer changes neither `virtualPrice()` nor the aggregate `lastNAVAA + lastNAVBB` before or after epoch start.

### Proof of Concept
Insert the following regression test into the existing `ProgrammableBorrowerCreditVault.t.sol` fork harness, which already deploys `idleCDO`/`cdoEpoch`, `strategy`, `aaTranche`, `underlying`, and the `owner`/`manager` accounts.

```solidity
function testDirectUnderlyingDonationCannotEnterTrancheNAV() external {
    uint256 amount = 10_000 * oneScale;
    uint256 donation = 1_000 * oneScale;

    // Create an established AA position and complete an ordinary accounting update.
    idleCDO.depositAA(amount);
    uint256 navBefore = idleCDO.getContractValue();

    // Unprivileged direct underlying transfer to the CDO. This is not a deposit.
    deal(address(underlying), attacker, donation);
    vm.prank(attacker);
    underlying.transfer(address(idleCDO), donation);

    // A dust deposit currently calls _updateAccounting() while the donation is still
    // present in getContractValue().
    deal(address(underlying), attacker, oneScale);
    vm.startPrank(attacker);
    underlying.approve(address(idleCDO), oneScale);
    idleCDO.depositAA(oneScale);
    vm.stopPrank();

    uint256 recordedNav =
        idleCDO.lastNAVAA() + idleCDO.lastNAVBB();

    assertEq(
        recordedNav,
        navBefore + oneScale,
        "donation was incorrectly crystallized into tranche NAV"
    );

    // The attacker converts the inflated tranche price into a pending receipt.
    uint256 attackerShares = aaTranche.balanceOf(attacker);
    vm.prank(attacker);
    idleCDO.requestWithdraw(attackerShares, address(aaTranche));

    uint256 pendingBasis = strategy.pendingWithdraws();
    assertGt(pendingBasis, 0, "expected pending withdraw basis");

    // Honest epoch operation now skims the donation after it already entered NAV.
    vm.prank(manager);
    idleCDO.startEpoch();

    assertEq(
        underlying.balanceOf(address(idleCDO)),
        0,
        "donation should have been skimmed"
    );

    // Force accounting to expose the stranded bookkeeping. Managed strategy-token
    // backing is lower than the earlier NAV/receipt basis by approximately `donation`.
    vm.prank(owner);
    idleCDO.updateAccounting();

    uint256 managedBacking = strategy.balanceOf(address(idleCDO));
    assertLe(
        idleCDO.lastNAVAA() + idleCDO.lastNAVBB(),
        managedBacking,
        "recorded NAV must not exceed managed strategy-token backing"
    );
}
```

    _accrueManagementFee();
    uint256 _lastNAVAA = lastNAVAA;
    uint256 _lastNAVBB = lastNAVBB;
    uint256 _lastNAV = _lastNAVAA + _lastNAVBB;

    uint256 _aprSplitRatio = trancheAPRSplitRatio;
