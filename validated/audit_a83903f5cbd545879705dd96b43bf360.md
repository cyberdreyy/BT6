### Title
Nonce Transaction Dedup Slot Squatting Enables Ingest Starvation for Durable-Nonce Transactions - (File: `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs`)

### Summary
The external report describes a low-cost, permissionless state mutation (`addCredit()` with 1 wei) that can be front-run cheaply to invalidate a hash-based validity check (`validateLien()`) used by legitimate transactions, causing them to be rejected/DOSed. The closest reachable analog in Agave is the banking-stage nonce-transaction dedup mechanism, which buffers **only one transaction per nonce account address** at a time, keyed purely by the nonce pubkey referenced in the packet — before nonce authority/signature validity against actual on-chain state is confirmed.

### Finding Description
The receive-and-buffer path tracks a single "nonce transaction priority id" per nonce address to prevent buffering multiple conflicting nonce transactions for the same account [1](#0-0) . Tests confirm this dedup slot is keyed by `nonce_pubkey` alone, and that competing transactions referencing the same nonce account are evicted/dropped based on this dedup logic and relative fee priority, independent of whether the *previous* occupant of the slot will ultimately pass authority/signature checks at execution time [2](#0-1) . Because any user can construct and submit a transaction that names an arbitrary (victim) nonce account as its `advance_nonce_account` target — cheaply, and with an attacker-chosen `compute_unit_price` — an attacker can craft transactions that occupy or repeatedly contest the dedup slot for a victim's nonce account, similar to how `addCredit()` could be called by anyone at trivial cost to perturb state relied upon by another user's transaction validity check.

The actual nonce-authority signature and on-chain state check (`verify_nonce_account`, authority-signer check) only happens later, in `TransactionBatchProcessor::validate_transaction_nonce` [3](#0-2) , i.e., after the ingest-layer dedup/priority decision has already been made and a legitimate competing transaction may have already been dropped.

### Impact Explanation
If the dedup/eviction decision at ingest time can be influenced by cheap, ultimately-invalid transactions referencing a victim's nonce account (e.g., wrong authority, since authority is not checked until SVM validation), an attacker could grief a specific user's durable-nonce transactions by keeping the dedup slot occupied with worthless competing transactions, causing the victim's legitimate high-value transaction to be dropped at `num_dropped_on_nonce_dedup`/`num_evicted_on_nonce_dedup` before ever reaching execution — an ingest-starvation DOS against a targeted durable-nonce user.

### Likelihood Explanation
This requires the attacker to know the victim's nonce pubkey (public, easily observable on-chain) and to pay only the minimum priority fee/compute cost to construct a competing packet; the existing test suite already validates certain non-eviction cases (bad blockhash, bad authority, bad fee payer) do NOT evict the current legit entry [4](#0-3) , which suggests the current implementation applies some protection. However, I was not able to fully trace the exact eviction/insertion logic (`transaction_state_container.rs`) within the tool-call budget to confirm whether *higher-priority-fee* but ultimately-invalid attacker transactions can still occupy/evict the slot before validation, or whether all such cases are guarded. This is a partial/unconfirmed finding.

### Recommendation
Ensure the nonce-dedup slot in the receive/buffer path can only be occupied/evicted by transactions that have been confirmed (via at least a lightweight signature/authority pre-check against current bank state) to reference the nonce account with a plausible-valid authority signature, not merely by referencing the pubkey and offering a higher priority fee. Consider requiring a minimum on-chain-state plausibility check before granting dedup-slot priority to a competing nonce transaction.

### Proof of Concept
Not fully constructible from static analysis alone — this requires exercising `receive_and_buffer.rs`'s dedup/eviction code paths with a targeted low-cost attacker transaction naming a victim's nonce pubkey with an invalid authority, sent with higher priority fee than the victim's genuine transaction, and observing whether it occupies/evicts the dedup slot before SVM-level authority validation runs. Existing unit tests such as `test_receive_and_buffer_nonce_dedup_validation_failure` [5](#0-4)  would be the starting point to adapt for this scenario, but I could not confirm within available context whether all such attacker scenarios are already mitigated.
