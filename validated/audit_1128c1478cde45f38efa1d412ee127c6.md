### Title
Loss-adjusted withdraw receipt misclassified as fully-funded par receipt after a second `requestWithdraw` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks per-epoch withdrawal receipts (`withdrawsRequestsByEpoch`) but routes claims through a single pointer, `lastWithdrawRequest[_user]`. When a stop-epoch loss haircuts pending receipts via `lossRecoveryPriceByEpoch`, the user's aggregate `withdrawsRequests[_user]` keeps the full un-haircutted basis. If the user files any new withdraw request afterward, `lastWithdrawRequest` is overwritten to the new epoch, the loss-adjusted claim path finds `lossRecoveryPriceByEpoch[newEpoch] == 0` and is skipped, and the funded-claim path pays the entire stale aggregate — including the haircutted epoch basis — at par. This is the vault analog of CVE-2022-0457's type confusion: the same receipt object is reinterpreted under the wrong claim "type" (funded-par instead of loss-adjusted), corrupting the payout.

### Finding Description
- `collectWithdrawFunds` at `contracts/strategies/idle/IdleCreditVault.sol:411` stores a haircut `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` when the borrower underfunds, but never reduces `withdrawsRequests[_user]` or `withdrawsRequestsByEpoch[_user][lossEpoch]` [1](#0-0) .
- `requestWithdraw` at line 282 unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` for any new request [2](#0-1) .
- `claimWithdrawRequest` runs `_claimLossAdjustedWithdrawRequest` first, but that function derives the epoch solely from `lastWithdrawRequest[_user]`; after a new request it looks up `lossRecoveryPriceByEpoch[newEpoch] == 0` and returns 0 without clearing the old epoch's basis [3](#0-2) .
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — the aggregate still containing the full pre-haircut loss-epoch basis — at par via `_transferFundedClaim` [4](#0-3) .
- `_clearWithdrawClaimForEpoch` would have subtracted the loss-epoch piece from the aggregate, but it is only reachable through the loss-adjusted path that was skipped [5](#0-4) .

### Impact Explanation
The attacker claims the haircutted epoch's basis twice in value terms: once implicitly at par instead of at `lossRecoveryPrice`. Example: a 50% loss epoch leaves the attacker owed 50 but `withdrawsRequests` holds 100; a dust second request re-keys `lastWithdrawRequest`, and the funded claim pays 100 + new request amount from strategy-held underlying reserved for other users' funded receipts. Direct theft / insolvency of the funded-claim reserve, sized up to the full un-haircutted basis of every user who re-requests after a loss epoch.

### Likelihood Explanation
Requires a `stopEpochWithDuration` partial-loss event (borrower underfunding is an unprivileged-economic condition, not an attacker action) followed by the attacker — any tranche holder / KYC'd lender — submitting a second withdraw request in a later epoch before claiming. No privileged role is the attacker; the sequencing (request → loss epoch → request → claim) is entirely in user space. No existing guard catches it: `epochNumber <= lastWithdrawRequest` only enforces the wait, and `defaulted`/recovery flags are irrelevant for a non-default loss stop.

### Recommendation
Iterate all epochs with non-zero `withdrawsRequestsByEpoch[_user][e]` having `lossRecoveryPriceByEpoch[e] != 0` in `_claimLossAdjustedWithdrawRequest` (or track a per-user list of loss epochs), rather than deriving the epoch from the single `lastWithdrawRequest` pointer; alternatively subtract each epoch's cleared basis from `withdrawsRequests[_user]` at `collectWithdrawFunds` time so the funded aggregate never contains un-haircutted basis.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault` loss-adjusted tests):
1. User deposits AA, epoch runs, `stopEpoch`, then `requestWithdraw(100)` in buffer of epoch N.
2. Epoch N+1 runs; borrower repays short → `stopEpochWithDuration(_lossAmount)` triggers `collectWithdrawFunds(funded < pending)`; `lossRecoveryPriceByEpoch[N] = 0.5e18` (or use the previewed loss path).
3. Epoch N+2 runs/stops; user calls `requestWithdraw(1)` → `lastWithdrawRequest[user] = N+2`.
4. After epoch advances past N+2, `cdo.claimWithdrawRequest()` → strategy `claimWithdrawRequest(user)`:
   - `_claimLossAdjustedWithdrawRequest`: `lossRecoveryPriceByEpoch[N+2] == 0` → returns 0.
   - `_claimFundedWithdrawRequest`: pays `withdrawsRequests[user] = 101` at par instead of `100*0.5 + 1 = 51`.
5. Assert `received == 101` while only `51` + other users' funded reserves back the strategy; a second user's identical claim reverts/strategy is insolvent.

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
