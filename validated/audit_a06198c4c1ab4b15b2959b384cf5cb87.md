### Title
Multisig executes requests counting confirmations from members already removed via `DeleteMember`/`DeleteKey`, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`confirm()` counts entries in the `confirmations` set for a request against `num_confirmations` without verifying that every recorded confirmer is still a current member of the multisig. `delete_member` / `DeleteKey` only purge **requests originated by** the removed member/key, not the removed member's **confirmations left on other members' still-pending requests**. This mirrors the ENS `NameWrapper` bug class: a state value (`confirmations` set) that should stay bound to a live authorization set (current `members`) is allowed to diverge from that set, and the divergence is later trusted as if it were still valid, letting a request execute with fewer than `num_confirmations` currently-authorized signers.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` adds the calling member to the request's confirmation set and executes once the count reaches the threshold: [1](#0-0) 

`assert_valid_request()` only checks that the *current caller* is a member and that the request/confirmations map entries exist — it never re-validates the members already stored inside the `confirmations` set: [2](#0-1) 

`delete_member()` removes the member from `self.members`, deletes the access key if applicable, and cleans up **only the requests that member itself created** (`r.member == member`) plus its `num_requests_pk` entry — it does not scan `self.confirmations` to strip that member's confirmation from *other* pending requests: [3](#0-2) 

The same gap exists in the older `multisig/src/lib.rs`, where `DeleteKey` removes requests signed by that key but likewise does not scrub that key's confirmations recorded on other members' requests: [4](#0-3) 

Concrete flow (analog of the ENS "ownership detached from ENS but ERC1155 token still valid" bug — here "confirmation still valid but member removed"):
1. Multisig is `K`-of-`N`. Member `B` creates request `X` (e.g. `Transfer` of funds to an address `B` controls, or a `FunctionCall`).
2. Member `A` (one of the `N` members) confirms `X`. `A`'s identifier is inserted into `confirmations[X]`, but `X` does not yet reach `K` confirmations, so it stays pending.
3. Members (possibly `A` and `B` colluding, or `A` acting alone before being removed) submit a *separate* request `Y = DeleteMember{member: A}` and get it confirmed/executed, removing `A` from `self.members` and clearing `A`'s **own** requests — but `X`'s stored confirmation from `A` is untouched.
4. Now the multisig has `N-1` live members, and the real security assumption is "K out of the *current* N-1 members must confirm." But `X.confirmations` still contains `A`'s stale entry.
5. Only `K-1` additional *live* members need to confirm `X` for `confirmations.len()+1 >= num_confirmations` to hold (the stale `A` entry from step 2 counts toward the total), so `execute_request(X)` fires with only `K-1` currently-authorized members having actually approved it.

This breaks the equality that should hold: `confirmations_counted(request) == confirmations_from_current_members(request)`. After step 3 the left side keeps a phantom entry the right side no longer has, yet the code treats them as equal.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." An arbitrary `Transfer`, `FunctionCall`, `AddKey`, or `AddMember` action can be pushed through with confirmations from fewer currently-trusted members than `num_confirmations` mandates, because a stale confirmation from a since-removed member is still counted. This can move NEAR out of the account, add an attacker-controlled key/member, or execute privileged calls on behalf of the contract — all while nominally requiring `K` signers, but actually only needing `K-1` live signers plus one previously-recorded (now revoked) approval.

### Likelihood Explanation
Requires no privileged access beyond being one of the existing multisig members (which is the normal, expected class of "unprivileged" party for a multisig relative to full withdrawal authority) and requires a member-removal event to occur — a routine operational action (rotating a compromised or departing member's key). Any time a member is removed while they have outstanding confirmations on other pending requests, this state divergence exists; it does not require any bug in the removal transaction itself, only that the codebase never scrubs cross-request confirmations on removal. Given that `add_request`/`confirm` are ordinary multisig operations and removal of members/keys is a standard maintenance operation, this is readily triggerable, not a purely theoretical corner case.

### Recommendation
When executing `DeleteMember` (or `DeleteKey` in the legacy `multisig`), iterate `self.confirmations` for **all** pending requests (not just ones authored by the removed member) and remove the deleted member's/key's entry from each confirmation set. Alternatively, at `confirm()` time (or execution time), re-validate that every account/public key stored in the request's `confirmations` set is still present in `self.members` before counting it toward `num_confirmations`, discarding stale entries lazily.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 2` and members `{A, B, C}`.
2. As `B`, call `add_request` to create request `X` (e.g., `Transfer{amount}` to an account `B` controls).
3. As `A`, call `confirm(X)` — `confirmations[X] = {A}`, `1 < 2`, request stays pending.
4. As `B` and `C` (2-of-3), submit and confirm `DeleteMember{member: A}` — executes, removing `A` from `self.members`; `self.confirmations` for `X` is untouched (only requests where `r.member == A` are purged, and `X.member == B`).
5. As `C` (now the only other live member besides `B`), call `confirm(X)`. `confirmations[X].len() + 1 == 2 >= num_confirmations (2)` → `execute_request(X)` fires the `Transfer`, even though only `C` and the now-removed `A` "confirmed" it — i.e., only one *current* live member (`C`) plus the request's own author (`B`, who never confirmed) plus a phantom historical confirmation from `A` combined to reach threshold, not two currently-authorized signers acting with intent at the time of execution.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
