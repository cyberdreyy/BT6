### Title
Block-rejection reason/response-data forgery via unauthenticated fields in `BlockRejection` signature - (File: `libsigner/src/v0/messages.rs`)

### Summary
`BlockRejection::hash()` (the message that is actually signed and verified) commits only to the block's `signer_signature_hash`. The `reason`, `reason_code`, and the entire `response_data` (`reject_reason`, `failed_txid`, tenure/read-count extend timestamps) are transmitted alongside the signature but are **not** part of the signed payload. Because `BlockResponse::Rejected` messages are broadcast in the clear over public StackerDB, any network observer can take a genuine rejection signature a signer produced for a given block (for whatever reason it originally rejected) and re-wrap it with an attacker-chosen `reason_code`/`response_data`, and it will still pass `BlockRejection::verify()` / `recover_public_key()` as an authentic message from that signer. This is the same bug class as the frp advisory: the field used for authentication (`signer_signature_hash`) and the fields that downstream logic actually acts on (`reason_code`, `response_data`) diverge, and only the former is checked.

### Finding Description
`BlockRejection::hash()` in `libsigner/src/v0/messages.rs` builds the signed digest as: [1](#0-0) 
Only `self.signer_signature_hash` (wrapped in a Clarity buffer) is fed into `structured_data_message_hash`; `reason`, `reason_code`, and `response_data` never enter the hash. `verify()` and `recover_public_key()` recompute exactly this same restricted hash: [2](#0-1) 

Both consumers of `BlockRejection` trust `reason_code`/`response_data` as if they were authenticated once the signature checks out against `signer_signature_hash`:

- Signer-side, `handle_block_rejection` recovers the pubkey/address purely from the (block-hash-only) signature, then feeds the attacker-controllable `rejection.response_data.reject_reason` into vote accounting: [3](#0-2) 
- `store_and_process_block_rejection` records that reason per signer address and, once ≥30% weight of recorded rejections carry `RejectReasonPrefix::ReorgNotAllowed`, permanently invalidates the miner for the current sortition: [4](#0-3) 
- Miner-side, `stackerdb_listener.rs` performs the identical unauthenticated trust: it validates only that the signature recovers to the expected `signer_pubkey`, then uses `rejected_data.reason_code` / `response_data.failed_txid` to accumulate per-txid "problematic" weight that later bans transactions from block proposals: [5](#0-4) 

Because these fields are not part of the signed material, an attacker who merely observes the public StackerDB gossip (no signer key, no majority, no auth token) can splice a genuine signature for a given `signer_signature_hash` with a forged `reason_code`/`response_data` and rebroadcast it. Slot-level de-duplication (`block.responded_signers.insert(slot_id)` on the miner, and the update-in-place row in `block_rejection_signer_addrs` on signers) means the *first* copy of a given signer's response to arrive for a block wins — so racing a forged message ahead of, or in place of, the authentic one is sufficient to have the forged reason recorded as if it came from that signer.

### Impact Explanation
This breaks the equality that a signer's *stated reason* for a vote must match what it actually attested to. The most severe consequence is on the reorg-protection path: an attacker only needs any ≥30%-weight set of legitimately signed rejections for a block (for any reason — timeout, connectivity issues, stale proposal, etc., which occur routinely without collusion) and can relabel enough of them as `ReorgNotAllowed` to cross the 30% blocking-minority threshold in `store_and_process_block_rejection`, causing each signer that processes them to set `sortition_state.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock`. This wedges the affected signer instance(s) into refusing to sign any further valid block proposals from that miner for the remainder of the sortition — a liveness break matching the "signer wedged into never signing valid blocks" category, achievable by a one-slot participant plus public gossip observation, without a majority of signers, another signer's key, or node access.

On the miner side, the same gap lets an observer forge `ValidateRejectCode::ProblematicTransaction`/`BadTransaction` attribution with an arbitrary `failed_txid`, corrupting the miner's `failed_txids` weight accounting in `signer_coordinator.rs`/`stackerdb_listener.rs` and potentially causing legitimate transactions to be permanently excluded from block templates — an availability/liveness impact on transaction inclusion, though secondary to the reorg-flag wedge.

### Likelihood Explanation
StackerDB chunks carrying `BlockResponse::Rejected` messages are public; any party monitoring the signer set's StackerDB slots (a one-slot miner easily qualifies) can observe valid `(signature, signer_signature_hash)` pairs from real signers as soon as ~30% of them naturally reject a proposal for any reason (common during churn, timeouts, or stale proposals). No cryptographic break is required — only re-serializing the message with a different `reason`/`reason_code`/`response_data` while keeping the original `signature` and `signer_signature_hash`. This makes the attack straightforward to mount opportunistically whenever partial rejection weight accumulates.

### Recommendation
Include `reason`, `reason_code`, and `response_data` (or a hash thereof) in the structured-data digest signed and verified in `BlockRejection::hash()` (and analogously in `BlockAccepted` if its `response_data` is later used for consensus-relevant decisions), so that any modification to these fields invalidates the signature. Apply the same fix pattern anywhere else a "signed field" and a "consumed/acted-upon field" have been allowed to diverge in the v0 message types.

### Proof of Concept
1. Wait for/observe a naturally occurring situation where ≥30% of signer weight rejects a specific block proposal for benign reasons (e.g., `RejectReason::ConnectivityIssues`, `ProposalTooOld`), each producing a `BlockRejection{ signer_signature_hash, signature, reason_code: <benign>, response_data: {...} }` broadcast on the signers' StackerDB slot.
2. For each such message, construct a new `BlockRejection` with the identical `signer_signature_hash` and `signature` fields (copied verbatim) but with `reason_code` set to `RejectCode::ValidationFailed(ValidateRejectCode::ReorgNotAllowed)` (or its `RejectReasonPrefix` equivalent) and `response_data.reject_reason` changed accordingly.
3. Broadcast the forged copies to the signer set's StackerDB slot ahead of (or racing) the legitimate messages.
4. Each receiving signer's `handle_block_rejection` → `rejection.recover_public_key()` in `libsigner/src/v0/messages.rs` succeeds because only `signer_signature_hash` was signed; the forged `reject_reason` is stored via `add_block_rejection_signer_addr`.
5. Once forged `ReorgNotAllowed` weight from distinct signer addresses exceeds the 30% blocking-minority threshold in `stacks-signer/src/v0/signer.rs::store_and_process_block_rejection`, each processing signer sets `sortition_state.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock`, refusing to sign any further valid proposals from the legitimate miner for that sortition — despite no signer actually having flagged a reorg violation.

    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
