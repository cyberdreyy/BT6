## Finding

### Title
`distribute()` griefing DOS via unregistered + opted-out recipient blocks entire staker/shareholder payout loop - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move], [File: aptos-move/framework/aptos-framework/sources/vesting.move])

### Summary
`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` when the recipient exists, is not yet registered for the coin type, and has opted out of unsolicited transfers via `set_allow_direct_coin_transfers(false)`. `staking_contract::distribute_internal` and `vesting::distribute` both iterate over a list of shareholders (staker, operator/beneficiary, or vesting grant shareholders) in a single Move transaction and call `aptos_account::deposit_coins` for each recipient without a try/catch equivalent. Because Move has no partial commit, an abort for any single recipient in the loop reverts the whole transaction, permanently blocking payout to every other shareholder in that pool. This mirrors the reported `fulfillUnstake()` FIFO revert-DOS: one uncooperative recipient in a payout loop can block the release of funds owed to other, unrelated parties. [1](#0-0) 

### Finding Description
`deposit_coins` only auto-registers the recipient for the coin type if the account did not previously exist (`account::exists_at` false triggers `create_account`, which calls `register_apt`). If the account already exists but was never registered for `AptosCoin`, and the account owner previously called `set_allow_direct_coin_transfers(account, false)`, the assert on `can_receive_direct_coin_transfers(to)` aborts the whole call: [2](#0-1) 

`staking_contract::distribute_internal` buys out all shareholders of the `distribution_pool` (which always includes the operator, receiving commission, and normally the staker) in a `while` loop that calls `aptos_account::deposit_coins` for each recipient in turn: [3](#0-2) 

Similarly, `vesting::distribute` iterates over all grant-pool shareholders and calls `aptos_account::deposit_coins` for each: [4](#0-3) 

Because `distribute`/`distribute_internal` is `public entry fun distribute(...)` callable by "anyone" (per its own doc comment: "Allow anyone to distribute already unlocked funds"), any shareholder in the pool who is unregistered for `AptosCoin` and has set `allow_arbitrary_coin_transfers = false` on their own account causes every future call to `distribute()`/`distribute_internal()` for that pool to abort — including calls made by the staker or admin trying to withdraw their own unlocked funds.

The Move framework's own formal spec already flags this design gap without resolving it: `spec distribute(...) { // TODO: Can't handle abort in loop. pragma verify = false; ... }` and the equivalent TODO on `staking_contract`'s specs, confirming the loop-abort hazard is a known, unmitigated property of this code path. [5](#0-4) 

### Impact Explanation
The operator role (in `staking_contract`/`vesting`) is not privileged over the staker's withdrawal rights — the whole point of `distribute` being callable by "anyone" is to guarantee the staker/shareholders can always retrieve their own unlocked stake regardless of operator cooperation. An operator (or any shareholder) who deliberately opts out of direct coin transfers on an unregistered account can permanently block `distribute()` for that pool, trapping the staker's already-unlocked (`inactive`/`pending_inactive`) stake and any accrued rewards indefinitely — a non-recoverable loss of claim rights until/unless the malicious party registers and re-enables transfers (something they have no incentive to do while griefing). This matches the "Permanent lock or non-recoverable loss of claim rights in stake ... vesting flows" impact category.

### Likelihood Explanation
The precondition is narrow but fully within an unprivileged operator/shareholder's own control: create/control an address that has never registered an `AptosCoin` store, call `aptos_account::set_allow_direct_coin_transfers(false)` on it, and use that address as the `operator`/`beneficiary`/shareholder in a `staking_contract` or `vesting_contract`. No cooperation from the staker/admin nor any privileged capability is required — it is entirely self-inflicted account state, similar in spirit to the reverting `receive()` in the external report.

### Recommendation
Adopt a pull-over-push pattern for these distribution loops: instead of pushing coins directly to each shareholder inside the atomic loop, credit each shareholder's share to a per-recipient pending-withdrawal balance (or skip/carry-over a recipient whose deposit fails, e.g., by catching failures with `coin::is_account_registered`/`can_receive_direct_coin_transfers` checks beforehand and routing to an escrow instead of aborting the whole transaction), so a single uncooperative recipient cannot block payouts owed to all others in the pool.

### Proof of Concept
1. Operator `O` creates account `O` via `account::create_account` (or otherwise) without ever calling `coin::register<AptosCoin>` / receiving APT (so `coin::is_account_registered<AptosCoin>(O) == false`).
2. `O` calls `aptos_account::set_allow_direct_coin_transfers(&O_signer, false)`.
3. Staker `S` creates a staking contract with operator `O` via `staking_contract::create_staking_contract`, stakes funds, funds earn rewards/commission, lockup expires making funds `inactive`.
4. Anyone calls `staking_contract::distribute(S, O)`. `distribute_internal` reaches `O` (or `O`'s beneficiary, if unset defaults to `O`) in the shareholder buy-out loop and calls `aptos_account::deposit_coins(O, ...)`, which aborts at the `can_receive_direct_coin_transfers` assert.
5. The entire transaction reverts, meaning neither `O`'s commission nor `S`'s own unlocked stake is distributed — every subsequent call to `distribute` for this staker/operator pair fails the same way, permanently until `O` cooperates.

**Caveat on verification**: I was unable to read the full source of `can_receive_direct_coin_transfers`/`is_account_registered` in this session (the file viewer returned blank content for that range), so I could not directly confirm the exact default value and every corner-case (e.g., whether gas-fee payment auto-registers `AptosCoin` for all active accounts, which would narrow exploitability to accounts that never sign a transaction). This should be independently confirmed by reading `aptos-move/framework/aptos-framework/sources/coin.move` (`is_account_registered`, `can_receive_direct_coin_transfers`) and by running the PoC end-to-end in a Devin session with full repo/tool access before treating this as fully confirmed.
