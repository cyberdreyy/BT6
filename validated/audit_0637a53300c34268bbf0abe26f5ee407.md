### Title
Confirmations from deleted multisig members remain counted toward the confirmation threshold on other pending requests, allowing a request to execute below the live-member threshold - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
The mobile-wallet report's underlying bug class is a mismatch between a trust check and the data actually used to satisfy it (unencrypted payload being trusted as if the encryption invariant held). The closest reachable analog in this repository is in the multisig contracts: `confirm` counts the size of a request's `confirmations` set against `num_confirmations` to decide whether a request should execute, but `delete_member`/`DeleteKey` never purges a removed member's confirmation entries from *other* requests they had already confirmed. This breaks the intended invariant "confirmations counted == confirmations from currently live members".

### Finding Description
`confirm` executes a request once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

When a member is removed via the `DeleteMember` action, `delete_member` only deletes requests that were *originated* by that member; it does not scan or clean the `confirmations` sets of other outstanding requests that the removed member had previously confirmed: [2](#0-1) 

The v1 `multisig` contract has the identical gap in its `DeleteKey` handling, which purges only requests signed by that key, not confirmations the key gave on other requests: [3](#0-2) 

As a result, a stale confirmation from an account/key that is no longer a member is still counted by `confirm`'s length check on any request that member confirmed before being removed. `assert_valid_request` only checks that the *caller* confirming now is a current member; it never re-validates that previously stored confirmations still belong to current members: [4](#0-3) 

### Impact Explanation
This breaks the custody/authorization binding "confirmations counted == confirmations from live members" that backs the K-of-N threshold guarantee. Concretely: with `num_confirmations = K` and `N` members, if a member confirms a pending request and is subsequently removed (member count still `>= num_confirmations`, satisfying the check in `delete_member`), their stale confirmation remains in the set. The request can then be executed with only `K-1` *live*-member confirmations instead of `K`, i.e. a multisig request executes below the documented threshold. Per the given impact taxonomy this is Critical ("a multisig request executed below threshold"), since it can authorize a `Transfer`, `AddKey`, `FunctionCall`, or contract upgrade action that should have required one more currently-authorized signer.

### Likelihood Explanation
Reaching this requires only ordinary multisig operations available to any current member set: (1) a member confirms request X without reaching threshold, (2) the multisig later approves a `DeleteMember`/`DeleteKey` request removing that member (a normal governance action, not requiring any out-of-scope privilege beyond what multisig membership already grants), (3) request X is later confirmed by the remaining members. No cryptographic assumptions, no interception, and no reliance on foundation/owner/redeploy actions are needed — it is a direct consequence of `execute_request`/`delete_member` never re-validating or purging confirmations on unrelated pending requests.

### Recommendation
When removing a member (`delete_member` in `multisig2/src/lib.rs`, `DeleteKey` in `multisig/src/lib.rs`), iterate over all outstanding requests and remove that member's entry from each request's `confirmations` set (not only requests it originated), or alternatively re-validate at `confirm`-time that every counted confirmation still corresponds to a current member before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy multisig2 with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `D` calls `add_request` then `confirm` on request `X` (a `Transfer`) → `confirmations(X) = {D}`, len=1.
3. Members submit and confirm a `DeleteMember{D}` request (requires 3 confirmations from A/B/C/D as usual) → `D` is removed; `self.members.len() == 3 >= num_confirmations(3)` passes the check in `delete_member`; only requests *originated by D* are purged — `X` is untouched, `confirmations(X)` still `= {D}`.
4. `A` calls `confirm(X)` → `confirmations.len()=1`, `+1 = 2 < 3`, stored: `confirmations(X) = {D, A}`.
5. `B` calls `confirm(X)` → `confirmations.len()=2`, `+1 = 3 >= 3` → `execute_request` fires the `Transfer`.
6. The transfer executed with confirmations from only `A`, `B`, and the now-removed `D` — i.e., only 2 of the 3 *current* members (`A, B, C`) approved it, even though the contract requires 3-of-3 live-member confirmations. [1](#0-0) [2](#0-1)
