### Title
Unbounded, low-cost permissionless staked-bank creation allows peer-list-style DoS flooding of a marginfi group - (File: `programs/marginfi/src/instructions/marginfi_group/add_pool_permissionless.rs`)

### Summary
The reported bug class is a networking-layer DoS: an unprivileged peer can register itself into a node's peer list with no validation and no cap, letting an attacker cheaply flood the list and overload honest participants. The closest reachable analog in marginfi is `lending_pool_add_bank_permissionless`, which lets *any* unprivileged caller create new `Bank` entries in a `MarginfiGroup` with no real cap and at minimal cost, incrementing a bank counter that itself never actually enforces a limit.

### Finding Description
`lending_pool_add_bank_permissionless` is explicitly permissionless — the `LendingPoolAddBankPermissionless` account struct has no admin/authority signer check, only a `fee_payer: Signer` who pays rent for the new accounts: [1](#0-0) 

The `bank` PDA is derived from `marginfi_group`, `bank_mint`, and a caller-supplied `bank_seed: u64`, so the same caller/mint/stake-pool combination can be used to mint an effectively unlimited number of distinct `Bank` accounts just by varying `bank_seed`: [2](#0-1) 

Each successful call increments the group's bank counter via `group.add_bank()`, but that function performs no cap enforcement at all — it just saturates once an absurdly large number is reached and otherwise always succeeds: [3](#0-2) 

This mirrors the reported issue precisely: an unprivileged actor can add entries to a group-scoped resource (peer list ↔ bank list) with no real validation of "value" (an arbitrary IP ↔ an arbitrary `bank_seed`) and no hard limit, enabling flooding.

### Impact Explanation
Downstream systems (indexers, off-chain risk engines, clients enumerating banks by `marginfi_group`, and health/liquidation computations that must iterate over a user's bank balances/oracles in a single transaction) are sensitive to the number of banks associated with a group. The repository's own test suite demonstrates that once enough banks/balances are present, transactions begin failing with out-of-memory / compute-unit-exceeded errors during borrow/health checks: [4](#0-3) 
An attacker who can permissionlessly and cheaply create large numbers of banks in a group (unlike the admin-gated `lending_pool_add_bank`, which requires `has_one = admin` and pays a flat SOL fee to the protocol) can degrade off-chain tooling that enumerates per-group banks, pollute group-level bank counts/state, and potentially contribute to resource-exhaustion conditions analogous to the reported peer-list DoS. This is a resource-exhaustion/DoS class issue rather than a direct fund-loss bug.

### Likelihood Explanation
Likelihood is constrained by the fact that `lending_pool_add_bank_permissionless` still requires a real, validator-owned `spl-single-pool` stake pool and vote account to pass PDA/ownership validation (`derive_single_pool_keys_from_vote_and_validate_owner`), and each call costs the caller rent for a `Bank` account plus liquidity/insurance/fee vaults. However, because `bank_seed` is fully attacker-controlled, a single valid validator vote account/stake pool can be reused to mint an arbitrary number of distinct bank PDAs, so the real constraint is only rent cost, not a hard protocol-level cap — the `add_bank()` counter increment is explicitly documented as a no-op safeguard ("If you managed to create 16,000 banks, congrats, does nothing"), confirming no real limit exists.

### Recommendation
Introduce an explicit, enforced cap on the number of banks (in particular permissionlessly-created staked banks) allowed per `marginfi_group`, and reject `lending_pool_add_bank_permissionless` once that cap is reached, rather than relying on a saturating counter that never blocks bank creation. Consider also requiring a per-validator uniqueness constraint (e.g., only one permissionless bank per `stake_pool`/vote account per group, or gating additional `bank_seed` values behind an admin/idempotency check) to prevent the same validator from being used to mint unbounded numbers of banks, similar to the report's recommendation to cap peer-list size while still allowing legitimate/idempotent entries.

### Proof of Concept
Conceptual PoC (not executed, since this is a design/limit gap rather than a memory-safety bug):
1. Attacker selects any validator with a valid `spl-single-pool` stake pool (public information; no permission required — `validator_vote_account` and `stake_pool` are `UncheckedAccount`s in [5](#0-4) ).
2. Attacker repeatedly calls `lending_pool_add_bank_permissionless(bank_seed)` with increasing `bank_seed` values against a target `marginfi_group` that has opted in to `StakedSettings`.
3. Each call succeeds (no admin check, no fee_state flat fee, only rent), creating a new `Bank` PDA and incrementing `group.banks` via `add_bank()`, which never rejects the call.
4. Repeating this thousands of times floods the group with staked banks for the same validator, analogous to flooding a peer list with fake/duplicate entries, degrading enumeration/indexing of the group's banks and potentially contributing to compute/memory exhaustion in aggregate risk computations, as demonstrated by the existing OOM tests in `tests/specs/limits/m01_accountLimits.spec.ts`.
