No vulnerability found for this question.

**Reasoning:** The claimed invariant — "the whitelist only grows with pools a trusted party vetted" — does not match the actual design. The `staking-pool-factory` contract is explicitly designed to let any unprivileged account create and auto-whitelist a staking pool without foundation approval, per its own README: "This allows anyone on the network to be able to create a staking pool contract for themselves without needing approval from the NEAR Foundation" [1](#0-0) . The whitelist's `add_staking_pool` correctly checks that the caller is either the foundation or a whitelisted factory [2](#0-1) , and the factory only calls this after it itself deployed the real, packaged staking-pool WASM binary to the new account via `create_account().transfer(...).deploy_contract(...)` — the attacker cannot substitute arbitrary bytecode [3](#0-2) .

Regarding "repeating the call with identical arguments in the same block": `create_staking_pool` inserts the target account id into `staking_pool_account_ids` and asserts uniqueness, panicking with "The staking pool account ID already exists" on any duplicate attempt before any promise is scheduled [4](#0-3) . Even if that check were bypassed, the underlying NEAR account-creation action for an already-existing account fails at the runtime level, which would cause `is_promise_success()` to return false in `on_staking_pool_create`, triggering a refund instead of whitelisting [5](#0-4) . So repeated identical calls cannot accumulate duplicate or extra whitelist entries beyond the single legitimately created pool.

The attacker does control `owner_id`, `stake_public_key`, and `reward_fee_fraction` for their own newly created pool, but that is the intended permissionless-pool-creation feature, not a bypass — the pool is created for the caller/owner they specify, with their own funds, and no other user's funds are ever routed into it without that user separately choosing to delegate to it. There is no code path shown here that lets an attacker whitelist an arbitrary externally-deployed contract or duplicate/collide an existing whitelisted pool id.
