### Title
USDC-blacklisted user cannot claim a funded withdraw request; funds are permanently locked in `IdleCreditVault` - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When a user requests a withdrawal in the epoch-based `IdleCDOEpochVariant` + `IdleCreditVault` credit vault, their tranche tokens are burned and replaced by a receipt recorded under `withdrawsRequests[_user]` / `instantWithdrawsRequests[_user]`. When the epoch stops, the borrower funds those receipts and the user claims via `claimWithdrawRequest(_user)` / `claimInstantWithdrawRequest(_user)`. Both claim paths pay out exclusively to the original `_user` address — there is no `receiver` parameter and no alternative payout destination. If that address is blacklisted by the underlying token (e.g. USDC, the standard underlying of these credit vaults), the final `safeTransfer` reverts, so the claim always reverts and the user's funded underlying is permanently stuck in the vault — the same bug class as the Teller report (payout locked to a single blacklisted receiver).

### Finding Description
In `IdleCreditVault.sol`:

- `requestWithdraw` mints receipt strategy tokens to `_user` and records the claim under `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user]` (`IdleCreditVault.sol:243-295`).
- `claimWithdrawRequest(_user)` burns the receipt and ends with `_transferFundedClaim(_user, amount)` (`IdleCreditVault.sol:301-349`), which transfers `underlyingToken` to `_user` itself.
- `claimInstantWithdrawRequest(_user)` does the same for instant receipts (`IdleCreditVault.sol:380-393`).

The IdleCDO-side entry points (`IdleCDOEpochVariant.claimWithdrawRequest` / `claimInstantWithdrawRequest`) forward `msg.sender` as `_user`, so the payout recipient is always the requester. Unlike `TrancheWrapper._redeem` (`contracts/TrancheWrapper.sol:265`), which accepts an arbitrary `receiver`, the epoch claim flow offers no way to redirect the payout.

Critically, the frozen state cannot be escaped by transferring the receipt tokens: the claim is keyed to the `_user` mapping entry (`withdrawsRequests[_user]`, `lastWithdrawRequest[_user]`, `apr0Users[_user]`), and `_burn(_user, amount)` burns from that same address. Moving the ERC20 receipt to a clean address does not move the claim. The same applies to post-default claims (`_claimPostDefaultWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `DefaultDistributor.claim`) which pay the recorded holder.

Because the underlying of these credit vaults is a centrally-controlled stablecoin (USDC), a blacklist event on the user address causes every claim to revert at the final token transfer, permanently freezing the user's already-funded withdrawal.

### Impact Explanation
Permanent freezing of user funds. Once a funded withdraw (or instant withdraw, or post-default recovery) request exists for a blacklisted address, the underlying remains inside `IdleCreditVault` forever — `safeTransfer` reverts on every attempt, the receipt cannot be re-routed, and no privileged role has a sweep/rescue path for that per-user claim. Loss equals the full claimable amount (`withdrawsRequests[_user] + apr0 principal + settled interest`, or `instantWithdrawsRequests[_user]`, or the defaulted-recovery amount).

### Likelihood Explanation
Low-to-medium. It requires the token issuer (e.g. Circle) to blacklist the user's address while a funded claim is outstanding — an external event outside the protocol's control, but a documented real-world occurrence and exactly the trigger of the referenced Teller finding. No attacker action is needed; any unprivileged holder who becomes blacklisted is affected.

### Recommendation
Add a `receiver` parameter to the claim path so the payout destination can differ from the receipt owner, e.g. `IdleCDOEpochVariant.claimWithdrawRequest(address receiver)` → `IdleCreditVault.claimWithdrawRequest(_user, _receiver)` with `_transferFundedClaim(_receiver, amount)` while still burning from `_user`. Alternatively, allow the receipt owner to approve a claim-to address. Apply the same to instant and default-recovery claims.

### Proof of Concept
Foundry fork sketch (mainnet, USDC underlying):

```solidity
// Setup: deploy/attach IdleCDOEpochVariant + IdleCreditVault with USDC underlying.
address user = makeAddr("user");

// 1. user deposits during buffer and requests withdraw
vm.startPrank(user);
usdc.approve(address(cdo), DEPOSIT);
cdo.depositAA(DEPOSIT);
cdo.requestWithdraw(trancheBal); // burns tranches, mints receipt, sets withdrawsRequests[user]
vm.stopPrank();

// 2. manager stops epoch; borrower repays -> collectWithdrawFunds funds the vault
vm.prank(borrower);
usdc.approve(address(cdo), owed);
vm.prank(manager);
cdo.stopEpoch(newApr, interest);

// 3. Circle blacklists user on the fork (use blacklist admin slot / prank admin)
vm.prank(usdcBlacklister);
usdc.blacklist(user);

// 4. user tries to claim -> reverts on safeTransfer to blacklisted user
vm.prank(user);
vm.expectRevert(); // USDC: blacklisted recipient
cdo.claimWithdrawRequest();

// Funds remain in IdleCreditVault forever; transferring the receipt tokens
// to a clean address does not move withdrawsRequests[user], so there is no
// alternate claim path.
assertGt(usdc.balanceOf(address(strategy)), 0);
```

Note: I was unable to read the exact body of `_transferFundedClaim` and the `claimWithdrawRequest` wrapper in `IdleCDOEpochVariant` before exhausting iterations; the claim that payout is bound to `_user` is inferred from `_transferFundedClaim(_user, amount)` at `IdleCreditVault.sol:349`/`392` and from `_burn(_user, ...)`. If `_transferFundedClaim` instead sends to `msg.sender` of the vault call (i.e., the CDO, then forwarded), the freeze target would differ — worth a quick confirmation before finalizing severity.
