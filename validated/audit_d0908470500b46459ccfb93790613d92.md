## Title
Multisig confirmations survive key deletion, allowing requests to execute below the live-member threshold - (File: `multisig/src/lib.rs`)

## Summary
The `MultiSigContract::confirm` function counts confirmations recorded in the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map without verifying that every public key in that set is still a currently authorized member of the multisig. When a member's key is revoked via the `DeleteKey` action, the code only purges requests that key *originally created*, but never scrubs that key from the `confirmations` sets of other pending requests it merely *confirmed*. This lets a stale, revoked confirmation combine with confirmations from currently-valid keys to reach `num_confirmations` and execute a request, even though fewer than `num_confirmations` live members actually approved it.

## Finding Description
`add_request` stores the request together with the creator's key as `signer_pk`: [1](#0-0) 

`confirm` simply checks the number of entries in the `confirmations` HashSet for the request, with no re-validation that those keys are still live members: [2](#0-1) 

When a key is removed via `DeleteKey`, the contract removes `num_requests_pk` for that key and deletes only the requests where that key is the *original requester* (`r.signer_pk == pk`). It does **not** remove that key from the `confirmations` sets of other requests where it only added a confirmation (not the request itself): [3](#0-2) 

Because of this gap, the binding "confirmations recorded for a request == approvals from currently live members" is broken: a confirmation from an already-revoked key remains permanently counted toward the threshold for any request it wasn't the creator of.

## Impact Explanation
Concretely, with `num_confirmations = 2` and members `key1`, `key2`, `key3`:
1. `key2` calls `add_request` for a `Transfer` (request's `signer_pk = key2`).
2. `key1` calls `confirm` on it — `confirmations = {key1}` (count 1, below threshold).
3. Separately, `key2` and `key3` confirm a different request that deletes `key1` (a normal, legitimate revocation of a departing/compromised member). This executes `DeleteKey{key1}` — which does not touch the `Transfer` request's confirmations because that request's `signer_pk` is `key2`, not `key1`.
4. `key2` (or `key3`) later calls `confirm` on the original `Transfer` request. `confirmations.len()` is `1` (still containing the now-revoked `key1`) `+1 = 2 >= num_confirmations`, so the request executes.

The transfer executes with only **one** currently-valid signer's real approval, even though the contract is supposed to require two live members to agree. This is exactly "a multisig request executed below threshold," matching the Critical impact category: unauthorized movement of funds held by the multisig account.

## Likelihood Explanation
This requires no privileged/out-of-scope actor: revoking a member's key via `DeleteKey` is a normal, expected multisig operation (e.g., offboarding an employee or rotating a compromised key), and any member can confirm pending requests as part of ordinary usage. No foundation, owner, redeploy, or victim key compromise is needed — only the interleaving of normal operations (a request confirmed by a soon-to-be-revoked key, followed by that key's legitimate removal, followed by a final confirmation).

## Recommendation
When executing `DeleteKey`, iterate over all pending requests' `confirmations` sets and remove the deleted public key from each, not just from requests it created. Alternatively, `confirm`/count logic should validate at confirmation-execution time that every key in the `confirmations` set is still present as a valid access key on the account before counting it toward `num_confirmations`.

## Proof of Concept
Extend `multisig/src/lib.rs` tests analogous to `add_key_delete_key_storage_cleared`:
```rust
let mut c = MultiSigContract::new(2); // num_confirmations = 2
// key2 creates request, key1 confirms it (count=1)
testing_env!(context_with_key(key2.clone(), amount));
let transfer_req_id = c.add_request(MultiSigRequest { receiver_id: bob(), actions: vec![MultiSigRequestAction::Transfer{amount: amount.into()}] });
testing_env!(context_with_key(key1.clone(), amount));
c.confirm(transfer_req_id); // confirmations = {key1}

// key2 + key3 confirm a DeleteKey{key1} request, executing it
testing_env!(context_with_key(key2.clone(), amount));
let del_req_id = c.add_request(MultiSigRequest { receiver_id: alice(), actions: vec![MultiSigRequestAction::DeleteKey{public_key: key1.clone()}] });
testing_env!(context_with_key(key2.clone(), amount));
c.confirm(del_req_id);
testing_env!(context_with_key(key3.clone(), amount));
c.confirm(del_req_id); // key1 is now revoked, but transfer_req_id's confirmations still contain key1

// key2 confirms the original transfer request; it executes with only 1 truly-live approver
testing_env!(context_with_key(key2.clone(), amount));
c.confirm(transfer_req_id); // count = {key1(stale), key2} = 2 >= num_confirmations -> executes
assert_eq!(c.requests.len(), 0); // transfer executed below live-member threshold
```

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
