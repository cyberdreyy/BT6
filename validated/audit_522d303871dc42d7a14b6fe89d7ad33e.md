### Title
Post-default instant withdraw receipts are paid from the finalized default-recovery reserve, stealing defaulted-epoch claimants' funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` has no `defaultRecoveryFinalized` handling (unlike `requestWithdraw`, which routes post-default requests into a separate `postDefaultRequests` bucket). A receipt created **after** `finalizeDefaultRecovery` is recorded in `instantWithdrawsRequestsByEpoch[user][epochNumber]`, where `epochNumber` still equals `defaultRecoveryEpoch` (it is only incremented by `deposit` during `stopEpoch`/`startEpoch`). `claimInstantWithdrawRequest` then treats it as a defaulted-epoch claim and pays it `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` out of `defaultRecoveryReserve`, draining recovery funds reserved for genuine pre-default claimants.

### Finding Description
In `requestWithdraw` (lines 243-258), once `defaultRecoveryFinalized` is set the function rejects users with open receipts and stores new requests in `postDefaultRequests`, which `_claimPostDefaultWithdrawRequest` pays 1:1 — explicitly "already priced after the haircut" so they "must not fall through to the defaulted-epoch receipt logic". `requestInstantWithdraw` (lines 356-375) has no such branch: it always burns the CDO's strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` with `currentEpoch = epochNumber`.

`epochNumber` is not advanced by `finalizeDefaultRecovery` (lines 661-710) — `defaultRecoveryEpoch = epochNumber`. Therefore a post-finalization instant request lands in the same per-epoch bucket as the defaulted-epoch claims. On claim, `claimInstantWithdrawRequest` (lines 380-393) runs `_claimDefaultedInstantWithdrawRequest` whenever `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`; that function reads `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (now containing the attacker's new post-default receipt) and pays it the recovery haircut from `defaultRecoveryReserve` via `_transferDefaultRecovery`.

Because `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` was computed over a fixed `totalBasis` at finalization, every wei paid to a post-default receipt reduces what legitimate defaulted-epoch claimants (normal and instant) can recover — the reserve is drained pro-rata on an inflated claim set. This mirrors the CVE bug class: a "free"/claim executed against an object (the finalized epoch bucket) that should no longer accept new entries, corrupting the recovery accounting.

### Impact Explanation
Direct theft of unclaimed recovery funds. Any unprivileged user able to route an instant-withdraw request through the CDO after default finalization extracts `amount * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve`, up to the full reserve. Legitimate defaulted-epoch receipt holders then find the reserve depleted when calling `claimWithdrawRequest`/`claimInstantWithdrawRequest` — permanent loss of their recovery share, bounded only by reserve size (potentially the entire recovered amount across all claimants).

### Likelihood Explanation
The attack requires (a) a borrower default that reaches `finalizeDefaultRecovery` with `pendingInstantWithdraws != 0` (so `defaultInstantWithdrawsFinalized` is true), and (b) the CDO still permitting `requestInstantWithdraw` post-finalization — plausible in prefunded/instant-enabled configurations where the instant path is kept live for liquidity. Both conditions are configuration-dependent rather than attacker-controlled, so likelihood is medium. No privileged-role misbehavior is needed; the sequencing (default → finalize → new instant request → claim) is executable by any lender.

### Recommendation
Add the same post-default guard to `requestInstantWithdraw` that `requestWithdraw` already implements: if `defaultRecoveryFinalized`, either revert when any open receipt exists, or route the new request into a separate post-default bucket paid at par — never into `instantWithdrawsRequestsByEpoch[epochNumber]` while `epochNumber == defaultRecoveryEpoch`. Alternatively, advance `epochNumber` (or snapshot `defaultRecoveryEpoch` and require `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` entries be created strictly before finalization via a per-epoch `createdBeforeFinalization` flag) so post-default receipts can never enter the defaulted bucket.

### Proof of Concept
Foundry fork test sketch against `IdleCreditVault` + `IdleCDOEpochVariant`:

```solidity
function testPostDefaultInstantRequestDrainsRecovery() external {
    // 1. Lenders deposit; epoch runs; instant withdraws enabled.
    _depositWithUser(victim, 100_000 * ONE_SCALE, true);
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // 2. Victim files an instant withdraw mid-epoch (unfunded -> pendingInstantWithdraws > 0).
    uint256 victimTranche = IERC20(AAtranche).balanceOf(victim) / 2;
    _requestInstantWithdrawWithUser(victim, victimTranche);

    // 3. Borrower defaults; manager/owner drive handleBorrowerDefault + finalizeDefaultRecovery
    //    with recoveredAmount < totalBasis so defaultRecoveryPrice < RECOVERY_FULL.
    _triggerDefaultAndFinalize(recoveredAmount);

    uint256 reserve = strategy.defaultRecoveryReserve();
    uint256 epoch = strategy.epochNumber();
    assertEq(epoch, strategy.defaultRecoveryEpoch());

    // 4. Attacker files a NEW instant withdraw AFTER finalization.
    uint256 attackerTranche = IERC20(AAtranche).balanceOf(attacker);
    _requestInstantWithdrawWithUser(attacker, attackerTranche);

    // It was recorded into the defaulted epoch bucket:
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epoch), attackerTranche);

    // 5. Attacker claims; paid out of defaultRecoveryReserve at recovery price.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 stolen = underlying.balanceOf(attacker) - balPre;
    assertEq(stolen, attackerTranche * strategy.defaultRecoveryPrice() / RECOVERY_FULL);
    assertEq(strategy.defaultRecoveryReserve(), reserve - stolen);

    // 6. Victim's legitimate defaulted-epoch claim now underflows/pays less than entitled.
    //    Sum of all defaulted claims exceeds the reserve -> last claimants lose funds.
}
```

Key assertions for the PoC harness: use the prefunded variant so instant withdrawals stay enabled; drive the default via the existing `_handleBorrowerDefault`/`finalizeDefaultRecovery` test helpers; fund `requestInstantWithdraw` through `IdleCDOEpochVariant`'s instant-withdraw entry point so `_onlyIdleCDO` is satisfied.

Caveat: the validity hinges on step 4 — whether `IdleCDOEpochVariant` still forwards instant-withdraw requests after default finalization (I could not fully trace its gating of `requestInstantWithdraw` within the search budget). If the CDO unconditionally reverts instant requests post-finalization, this vector is blocked and the finding reduces to defense-in-depth.
