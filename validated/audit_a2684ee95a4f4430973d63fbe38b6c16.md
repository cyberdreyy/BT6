### Title
Global connection-slot exhaustion via stalled QUIC handshakes bypasses per-IP and overall connection rate limiters - (File: streamer/src/nonblocking/quic.rs)

### Summary
An unstaked attacker can occupy every slot counted by `ClientConnectionTracker::new`/`qos.max_concurrent_connections()` by opening connections and never completing the QUIC handshake, because both the per-IP `ConnectionRateLimiter` and the global `overall_connection_rate_limiter` only consume tokens on a *successful* handshake, not on an attempt. The server auto-frees each slot after `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s), so the attacker just needs to keep opening new stalled connections at that cadence to keep the global cap saturated, causing legitimate `Connecting` futures to be refused with `refused_connections_too_many_open_connections`.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:304-411`), each incoming connection first passes two "checks" before `ClientConnectionTracker::new` is consulted:
- `overall_connection_rate_limiter.current_tokens() == 0` (peek only) [1](#0-0) 
- `rate_limiter.is_allowed(&incoming.remote_address().ip())` (peek only) [2](#0-1) 

Neither call consumes/decrements the token bucket for the attempt. Consumption only happens later, inside `setup_connection`, and only on the *success* branch after the handshake completes: `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` [3](#0-2) . `ConnectionRateLimiter::is_allowed` explicitly documents this assumption: "we assume that only IPs with actual confirmed connections are stored in it... allow connection request" if unseen [4](#0-3) .

Consequently, an attacker who never completes the handshake never triggers either rate limiter's token consumption, so both remain effectively unthrottled for stalled/incomplete handshakes — from a single IP or many.

The only remaining gate is `ClientConnectionTracker::new`, which enforces the global `max_concurrent_connections` cap by incrementing/checking `stats.open_connections` [5](#0-4) . Once accepted, `setup_connection` bounds the handshake to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (`const QUIC_CONNECTION_HANDSHAKE_TIMEOUT: Duration = Duration::from_secs(2);`) via `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await` [6](#0-5) [7](#0-6) . On timeout/failure, `handle_connection_error` runs and `client_connection_tracker` is dropped at end of scope, decrementing `open_connections` [8](#0-7) [9](#0-8) .

So the attacker cannot literally hold a slot "indefinitely" (the server self-clears it every 2s), but that is exactly the mechanism the question describes: cycle stalled connections at the ~2s boundary. Because neither rate limiter throttles unsuccessful attempts, the attacker can refill the cap as fast as slots free, from one or many source IPs, with no protocol-level cost (a QUIC Initial packet is cheap to send and requires no completed handshake, no stake, no valid certificate exchange).

### Impact Explanation
This is a non-RPC remote resource exhaustion / ingest-path DoS against the TPU QUIC listener: sustained saturation of `max_concurrent_connections` denies `ClientConnectionTracker` allocation (and therefore `incoming.accept()`) to legitimate staked/unstaked peers, which shows up as `refused_connections_too_many_open_connections` in `StreamerStats` [10](#0-9) . This maps to the "ingest starvation" / availability category rather than fund loss or consensus divergence — impact is scoped to connection admission, not to already-established staked traffic (which lives in per-key `ConnectionTable` slots, separately gated by `max_connections_per_peer`).

### Likelihood Explanation
Preconditions are default config: default `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) and no stake requirement to attempt a handshake — exactly as stated in the prompt. The attacker capability required is trivial: ability to open UDP/QUIC connections to the TPU port and simply not respond to complete the handshake (or actively stall it). This is a network-only, unprivileged, repeatable action; the rate-limiter gap (peek-not-consume) means there is no server-side counter-pressure specifically against failed/stalled attempts, only the raw `max_concurrent_connections` cap and 2s timeout, both of which the attacker can race by controlling attempt cadence and/or a modest number of source sockets/IPs.

### Recommendation
- Reserve/consume rate-limiter tokens (both per-IP `ConnectionRateLimiter` and the global `overall_connection_rate_limiter`) at *accept* time (before or concurrently with `ClientConnectionTracker::new`), not only on handshake success, so stalled/incomplete handshake attempts are throttled the same as completed ones.
- Consider reserving a portion of `max_concurrent_connections` exclusively for connections that have passed some lightweight address-ownership signal (e.g., QUIC stateless Retry / address validation) before admitting them into the general pool, rather than counting pre-validated `Connecting` futures at parity with established connections.
- Shrink or make configurable the effective exposure window relative to attacker request rate, and add a stat/alert specifically tracking the ratio of `outstanding_incoming_connection_attempts` to `max_concurrent_connections` sustained over time, to detect this pattern operationally.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
