### Title
Client-controlled `MessageId` allows unprivileged request collision/overwrite in gateway webhook callback map - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The `capabilities` gateway handler stores a pending user callback in a shared, mutex-protected map (`savedCallbacks`) keyed solely by `msg.Body.MessageId`, a value copied verbatim from the untrusted client-supplied JSON-RPC `id` field [1](#0-0) . Any unprivileged caller can choose an arbitrary `MessageId`, so two concurrent, unrelated requests can be made to collide on the same key, or an attacker can pre-emptively call `HandleLegacyUserMessage` with a chosen `MessageId` to overwrite another in-flight request's saved callback entry before the legitimate DON response arrives.

### Finding Description
`HandleLegacyUserMessage` inserts the caller's callback into the shared map without any binding to the caller or verification that the ID is unused: `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` [2](#0-1) . Later, `handleWebAPITriggerMessage` looks up and deletes the entry by the same `MessageId` when a DON node responds, then routes the response to whichever callback is currently stored under that key: [3](#0-2) .

This is directly analogous to the reported bug class: a state-mutating "checkpoint" (`savedCallbacks[id] = ...`) that is publicly/unprivilegedly writable, and a later "ensure/consume" step (`handleWebAPITriggerMessage`) that trusts whatever is currently recorded under that key without re-validating ownership. Because the `MessageId` is entirely attacker-chosen (`msg.Body.MessageId = request.ID` at `jsonrpccodec.go:30`), an unprivileged client can:
1. Submit a request with a `MessageId` equal to another user's in-flight request ID (racing the legitimate request), overwriting the map entry so the legitimate DON response is delivered to the attacker's callback instead of the victim's (cross-user response confusion).
2. Alternatively, cause the victim's callback registration to silently replace the attacker's own dangling entry, or vice versa, corrupting delivery for either party.

### Impact Explanation
If exploited, an unprivileged actor could intercept a webhook-trigger response destined for another user (response hijacking / cross-user data leak), since `savedCallbacks` has no per-request secret binding beyond the attacker-guessable `MessageId`. It could also cause denial of service for the legitimate caller, whose response is swallowed by the wrong (or now-deleted) callback entry.

### Likelihood Explanation
Exploitability requires only unauthenticated/unprivileged access to the gateway's `HandleLegacyUserMessage`-backed HTTP endpoint and the ability to guess or observe another request's `MessageId` while it is still in flight (the callback lives in the map until the DON responds or `pruneCallbacks` runs). No node compromise, privileged role, or malicious peer is required — solely a timing race with an attacker-chosen ID value. This raises likelihood, though successful exploitation depends on winning the race against the real DON response and knowing/guessing the collided `MessageId`, which somewhat limits practical likelihood.

### Recommendation
Do not use a purely client-supplied value as the sole key for a shared mutable map that later drives response delivery. Instead, generate the `MessageId` (or an internal correlation key) server-side per accepted request, or bind the map key to a combination of the client-supplied ID plus a server-generated random/session-specific component, and reject (rather than overwrite) insertions when the key already exists in `savedCallbacks`.

### Proof of Concept
1. Attacker sends a legacy webhook trigger request to the gateway HTTP endpoint with `id = "X"` (a value it expects or can predict another client to also use), which is stored as `savedCallbacks["X"]` via `HandleLegacyUserMessage` [2](#0-1) .
2. Concurrently, a victim sends its own webhook trigger request also using `id = "X"` (e.g., both use a naive/sequential/timestamp-based ID scheme, or the attacker observes/predicts the victim's next ID).
3. Whichever request registers second overwrites `savedCallbacks["X"]`, since there is no existence check.
4. When the DON node responds with `MessageId = "X"`, `handleWebAPITriggerMessage` delivers the response to whatever callback is currently stored at that key [3](#0-2) , potentially delivering the victim's response to the attacker's HTTP connection.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
