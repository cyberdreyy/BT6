Based on my analysis of `stacks-signer/src/runloop.rs`, the described flaw does exist in the code as written, but let me lay out precisely what is confirmed vs. uncertain.

### Title
`refresh_signer_config` overwrites a not-yet-stale-cleaned `ConfiguredSigner` slot without checking `has_unprocessed_blocks`, discarding a still-active cycle's signer state - ([File: stacks-signer/src/runloop.rs])

### Summary
`stacks_signers: HashMap<u64, ConfiguredSigner<...>>` is keyed only by `reward_cycle % 2`, giving just two slots for "current" and "next" cycle signers. `refresh_signer_config` (line 342-362) unconditionally does `self.stacks_signers.insert(reward_index, new_signer_config)`, dropping whatever `ConfiguredSigner` previously occupied that slot, with no check of `has_unprocessed_blocks()`. That guard is only ever consulted inside `cleanup_stale_signers` (lines 471-500), and `refresh_runloop` calls `refresh_signer_config` for the "next" cycle (line 435-439) *before* `cleanup_stale_signers` runs (line 441) [1](#0-0) .

### Finding Description
The equality being violated: the `SignerConfig`/weights returned by `self.stacks_signers.get(&(reward_cycle % 2))` for a given `reward_cycle` should always be `SignerConfig` for exactly that `reward_cycle`, or absent — never silently replaced by a different, non-adjacent cycle's config while the old one still has unresolved work.

The code path:
- `is_configured_for_cycle`/`is_registered_for_cycle` (lines 450-469) only compare `signer.reward_cycle() == reward_cycle`; they say nothing about pending work, and are only used to decide *whether to call* `refresh_signer_config`, not to protect the slot during the call.
- `refresh_signer_config` (line 342) computes `reward_index = reward_cycle % 2` and does an unconditional `insert`, replacing/dropping the previous `ConfiguredSigner` value at that slot regardless of its state [2](#0-1) .
- `cleanup_stale_signers` (line 471) is the *only* place that checks `signer.has_unprocessed_blocks()` before removing a stale entry [3](#0-2) , but it runs *after* the next-cycle refresh in `refresh_runloop` (line 441), so by the time it would check the guard for the old signer, that signer object has already been overwritten/dropped by `insert`.

Because there are only two hashmap slots (parity 0/1), a signer for cycle N and cycle N+2 collide on the same key. In the normal cadence of `refresh_runloop`, when current cycle is `N+1` and the runloop enters the "next reward cycle" prepare phase, it calls `is_configured_for_cycle(next = N+2)` which looks at key `(N+2)%2 == N%2` — the same slot still occupied by the (not-yet-cleaned) cycle-`N` signer. If that check is false (i.e., the slot's `reward_cycle()` is N, not N+2), `refresh_signer_config(N+2)` is invoked and destroys the cycle-N `ConfiguredSigner`, including any of its unresolved/in-flight `BlockProposal` state, without ever consulting `has_unprocessed_blocks()`.

### Impact Explanation
This matches the "High - acting on a stale reward set/threshold" / liveness category: an in-flight cycle-N `BlockProposal` that the signer was still validating/signing against cycle-N's reward set and threshold is lost the moment its `ConfiguredSigner` object is dropped, rather than being finished or safely handed off. This is a liveness defect (the signer can be wedged into never finishing valid signing work for cycle N) rather than a chain-safety break, since the destroyed signer simply stops processing rather than signing under the wrong weights — there is no code path shown where the *new* cycle-N+2 signer re-evaluates the old cycle-N proposal under N+2's weights (the new `ConfiguredSigner::RegisteredSigner` starts fresh via `Signer::new`), so the specific "proposal judged under wrong cycle's threshold" claim in the prompt is not directly substantiated by what I could read — what's confirmed is that in-flight state/proposals for cycle N are dropped/lost, not silently re-scored.

### Likelihood Explanation
The precondition is timing-dependent and not attacker-controlled in the way described: cycle N's slot collides with cycle N+2's slot, and normally the transition to prepare-refresh N+2 happens near the end of cycle N+1 — a full reward cycle (~2 weeks) after cycle N ended. For the bug to bite, cycle N's `ConfiguredSigner` would have to still `has_unprocessed_blocks()` returning true across that entire span, which requires an independent stall/bug in the signer's own processing (not something a single attacker with one miner slot and gossip access can force). I could not fully verify `has_unprocessed_blocks()`'s exact semantics (I did not get to read its implementation in `signerdb.rs`/`v0/signer.rs` before running out of tool calls), so I cannot confirm whether an attacker-controlled stuck-proposal state is realistically achievable within the required window using only unprivileged capabilities (one miner slot + gossiped proposals/StackerDB messages). Given the described attacker model (no majority signers, no privileged access), triggering the multi-week overlap needed is not demonstrated to be reachable by the described attacker actions alone.

### Recommendation
In `refresh_signer_config`, before inserting a new `ConfiguredSigner` into `stacks_signers`, check whether an existing entry occupies that slot and, if it is a `RegisteredSigner` with `has_unprocessed_blocks() == true`, defer the replacement (or route unresolved work to completion) rather than unconditionally overwriting it.

### Proof of Concept
Not provided — I was unable to confirm within the available tool budget whether `has_unprocessed_blocks()`'s semantics allow an unprivileged single-slot attacker to keep a cycle-N signer "busy" long enough (about one full reward-cycle length) to reach the overlap window with cycle N+2's prepare-phase refresh. Without that confirmation, and without evidence that the *new* signer re-evaluates the *old* cycle's proposal under the new cycle's weights (rather than simply dropping it), I can't assert the specific safety/liveness equality break claimed in the prompt with the required rigor.     fn cleanup_stale_signers(&mut self, current_reward_cycle: u64) {
        #[cfg(any(test, feature = "testing"))]
        if TEST_SKIP_SIGNER_CLEANUP.get() {
            warn!("Skipping signer cleanup due to testing directive.");
            return;
        }
        let mut to_delete = Vec::new();
        for (idx, signer) in &mut self.stacks_signers {
            let reward_cycle = signer.reward_cycle();
            if reward_cycle >= current_reward_cycle {
                // We are either the current or a future reward cycle, so we are not stale.
                continue;
            }
            match signer {
                ConfiguredSigner::RegisteredSigner(signer) => {
                    if !signer.has_unprocessed_blocks() {
                        debug!("{signer}: Signer's tenure has completed.");
                        to_delete.push(*idx);
                    }
                }
                ConfiguredSigner::NotRegistered { .. } => {
                    debug!("{signer}: Unregistered signer's tenure has completed.");
                    to_delete.push(*idx);
                }
            }
        }
        for idx in to_delete {
            self.stacks_signers.remove(&idx);
        }
    }
