### Title
Stale instant-withdraw receipts escape the default haircut and are paid at par from other claimants' funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Like HTTP request smuggling (two layers disagreeing on where a request begins/ends), `IdleCreditVault` keeps two interpretations of instant-withdraw requests: a per-epoch view (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) used by default finalization, and an aggregate per-user view (`instantWithdrawsRequests`) used by the claim path. When the borrower defaults while `pendingInstantWithdraws` is non-zero, `defaultPendingClaimBasis()` counts only the current epoch's instant claims, so an unfunded instant receipt recorded in an earlier epoch is never included in the recovery basis and never haircut — yet `claimInstantWithdrawRequest` later pays the user's full aggregate at par via `_transferFundedClaim`. The "smuggled" stale receipt is paid whole while same-epoch receipts take the recovery haircut, draining strategy underlyings owed to funded claimants.

### Finding Description
- `requestInstantWithdraw` records both `instantWithdrawsRequests[_user] += _amount` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` / `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`, and increments `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`). There is no mechanism that forces `pendingInstantWithdraws` to zero at epoch boundaries; it only decreases in `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`), so a receipt the CDO never funded can survive into a later epoch.
- On default, `finalizeDefaultRecovery` computes the claim basis via `defaultPendingClaimBasis()`, which adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — when `pendingInstantWithdraws != 0` (`IdleCreditVault.sol:644-649`). `_defaultPrefundedInstantReserve` likewise only recognizes the current-epoch basis (`IdleCreditVault.sol:716-723`). A receipt requested in epoch N-1 that is still unfunded at default in epoch N contributes to `pendingInstantWithdraws` but is excluded from both the haircut basis and the prefunded-reserve calculation.
- After finalization, `claimInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` through `_claimDefaultedInstantWithdrawRequest` (which also floors `pendingInstantWithdraws` at 0, conflating stale and current-epoch basis at `IdleCreditVault.sol:849-853`), then burns and pays the entire remaining `instantWithdrawsRequests[_user]` at par through `_transferFundedClaim` (`IdleCreditVault.sol:380-392`). The reserve guard in `_transferFundedClaim` (`IdleCreditVault.sol:897-906`) protects `defaultRecoveryReserve` but not other underlyings, so the stale unfunded receipt is paid from the strategy's general balance — funds that back other users' already-funded claims.
- Broken invariant: one receipt, one consistently-priced payout. The finalize path treats the stale receipt as outside the recovery universe, while the claim path treats it as fully funded at par — the same ambiguity that makes request smuggling exploitable.

### Impact Explanation
An unprivileged lender (KYC-passing tranche holder) whose instant-withdraw request was left unfunded across an epoch boundary receives 100% of the receipt while every defaulted-epoch claimant receives only `defaultRecoveryPrice`. The payout consumes strategy underlyings that were collected to satisfy funded withdraw/instant claims, so later claimants' transfers revert or are shortchanged — a direct transfer of value up to the full stale receipt amount, and potentially permanent freezing of remaining claims if the strategy balance is exhausted.

### Likelihood Explanation
Requires: (a) an instant-withdraw request remaining unfunded (nonzero `pendingInstantWithdraws`) across at least one `stopEpoch`/`epochNumber` increment, and (b) a subsequent borrower default finalized via `finalizeDefaultRecovery`. The attacker only needs to have placed the instant request in an earlier epoch; default timing is exogenous. The main uncertainty is how readily the CDO leaves instant requests unfunded across an epoch boundary — `collectInstantWithdrawFunds` is pull-based, so any epoch where the CDO lacks liquid underlying or delays collection leaves pending basis. The bug is structural (aggregate vs. per-epoch accounting desync), not timing-coincidence-dependent beyond the pending state itself. I was unable to fully verify the CDO-side instant-withdraw funding timing in `IdleCDOEpochVariant.sol` within the available search budget; if the CDO guarantees same-transaction funding, the window narrows but `pendingInstantWithdraws` accounting and the epoch-scoped `defaultPendingClaimBasis` clearly anticipate nonzero pending at finalization.

### Recommendation
In `claimInstantWithdrawRequest`, pay receipts epoch-by-epoch rather than by aggregate: for each epoch with nonzero `instantWithdrawsRequestsByEpoch[user][e]`, pay at `defaultRecoveryPrice` if `e == defaultRecoveryEpoch`, at `lossRecoveryPriceByEpoch[e]` if set, and at par only if the receipt was actually funded. Correspondingly, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` should include all unfunded instant basis across epochs (e.g., track `instantWithdrawClaimsByEpoch` cumulatively or iterate/settle stale epochs), not only `epochNumber`. Alternatively, revert `requestInstantWithdraw` or force-claim when `instantWithdrawsRequests[user]` carries basis from an epoch `< epochNumber`.
