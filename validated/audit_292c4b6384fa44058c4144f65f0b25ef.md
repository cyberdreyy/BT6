### Title
Unauthenticated cross-user callback hijack via `savedCallbacks` map keyed only by client-controlled `MessageId` - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
`handler.HandleLegacyUserMessage` stores the caller's response callback in `h.savedCallbacks` keyed **only** by `msg.Body.MessageId`, a field fully chosen by the requesting client and validated only for length/format, not for uniqueness or binding to the sender. `msg.Validate()` computes `Body.Sender` from the signature but the callback map is never scoped by sender. Any external, unauthenticated party can submit a `web_api_trigger` request carrying the same `MessageId` as an in-flight request from a different user; the second call in `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` silently overwrites the first entry. When a node's response for that `MessageId` later arrives, `handleWebAPITriggerMessage` looks the callback up by `MessageId` alone and delivers the (possibly sensitive) response to whichever caller most recently wrote that map key — not necessarily the original requester.

### Finding Description [1](#0-0) 
writes into the shared `savedCallbacks` map without first checking whether an entry for that `MessageId` already exists, unlike the sibling implementations in the same codebase that explicitly guard against this:
- `core/services/gateway/handlers/common/requestcache.go` keys entries by `globalId{sender, id}` and returns an error `"request already exists"` if the key is already present [2](#0-1) .
- `core/services/gateway/handlers/confidentialrelay/handler.go` and `core/services/gateway/handlers/vault/handler.go` both explicitly reject the request with `"request ID already exists"` before creating a new `activeRequest` [3](#0-2) .
- `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go` returns `jsonrpc.ErrConflict` ("in-flight request") for a duplicate `requestID` [4](#0-3) .

The legacy `capabilities.handler` (`web_api_trigger` / `web_api_target` methods) lacks this guard entirely. `MessageId` is attacker-controlled (bounded only to ≤128 bytes, non-null-terminated) [5](#0-4) , and `Validate()` never checks that the ID is unique or previously unseen — it only recovers the signer into `Body.Sender` for later use, which the callback map ignores [6](#0-5) . Consequently:

1. User A sends a `web_api_trigger` request with `MessageId = "X"`. `HandleLegacyUserMessage` stores A's callback at `savedCallbacks["X"]` and forwards the request to DON nodes.
2. Before a node responds, attacker B sends another `web_api_trigger` request re-using `MessageId = "X"` (a value B can choose freely or, in practice, may be predictable/enumerable given the ID is echoed in wire messages). `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with B's callback.
3. When a DON node later responds for `MessageId = "X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, deletes the entry, and delivers A's response payload to B [7](#0-6) .
4. User A's original HTTP call (in `gateway.ProcessRequest`, which just does `callback.Wait(ctx)` [8](#0-7) ) times out with no response, while B receives A's data.

### Impact Explanation
This is a cross-user response confusion / hijack: an unprivileged, unauthenticated caller of the gateway's external HTTP entry point can cause another user's workflow-trigger response (which may embed sensitive computed data or execution results returned by DON nodes) to be redirected to the attacker instead of the legitimate requester, and simultaneously deny the legitimate requester their response. This directly mirrors the Angle `disputeTree()`/`resolveDispute()` bug class: a single mutable slot recording "who is owed the eventual result" can be overwritten by an unrelated party before resolution, causing the result to be delivered to the wrong party.

### Likelihood Explanation
Exploitability depends on the attacker knowing or guessing a victim's in-flight `MessageId` and firing their own request with the same ID before the DON responds. `MessageId` is not a secret by design (it's part of the signed body and observable on the wire in various contexts), and no cryptographic or per-sender binding of the callback map key is enforced, so this only requires a race against the network's round-trip time to DON nodes — a modest but realistic window given the asynchronous fan-out to `donConfig.Members`.

### Recommendation
Scope `savedCallbacks` (and its lookup/deletion) by `(sender, MessageId)` instead of `MessageId` alone, matching the pattern already used in `common.requestCache`'s `globalId{sender, id}`. Additionally, reject a `HandleLegacyUserMessage` call outright if an entry already exists for the computed key, returning a conflict error to the caller (as `http_trigger_handler.go` and the vault/confidentialrelay handlers already do), rather than silently overwriting the previous entry.

### Proof of Concept
1. Start the gateway with the `capabilities` legacy handler enabled for a DON.
2. As "User A", sign and POST a `web_api_trigger` message with `Body.MessageId = "shared-id"`.
3. Before any DON node responds, as "Attacker B" (different signing key), sign and POST another `web_api_trigger` message reusing `Body.MessageId = "shared-id"`. Note `HandleLegacyUserMessage` performs no existence check before `h.savedCallbacks["shared-id"] = &savedCallback{...}` [9](#0-8) , so B's callback now occupies the slot.
4. Simulate a DON node sending back a `web_api_trigger` response for `MessageId = "shared-id"` (containing data intended for User A) via `HandleNodeMessage` → `handleWebAPITriggerMessage`.
5. Observe that Attacker B's HTTP callback receives the response payload, while User A's HTTP request hangs until timeout with no data.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
