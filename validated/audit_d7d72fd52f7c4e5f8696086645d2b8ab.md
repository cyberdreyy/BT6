### Title
Loss-adjusted withdrawal haircut is bypassed when a user holds receipts in multiple epochs — `_claimLossAdjustedWithdrawRequest` only ever checks `lastWithdrawRequest`, so the loss-epoch claim is silently skipped and the full basis is paid at par ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Vim bug: corrupted NFA structure leaves `state->out1` NULL, and `nfa_max_width()` later traverses the graph dereferencing `state->out1->out` with no NULL check. The idle-tranches analog is a lookup keyed on a corrupted/stale epoch reference: `_claimLossAdjustedWithdrawRequest` resolves the loss-epoch haircut solely through `lastWithdrawRequest[_user]` — a single "latest request" pointer — instead of iterating the user's per-epoch receipts. When that pointer is overwritten by a second `requestWithdraw`, the stored `lossRecoveryPriceByEpoch` entry for the earlier epoch becomes unreachable (the NULL-equivalent lookup returns 0), and `_claimFundedWithdrawRequest` then pays the aggregated `withdrawsRequests[_user]` — which still includes the haircutted epoch's basis — at 100% par. The loss socialization invariant is broken and the attacker drains underlyings that belong to other claimants.

### Finding Description
In `requestWithdraw`, each request records `withdrawsRequestsByEpoch[_user][currentEpoch]` and overwrites `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:282-293`). When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` stores the haircut as `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` for the pending-withdraw epoch (`IdleCreditVault.sol:411-421`).

`claimWithdrawRequest` then runs `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:789-801`):

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;   // <-- NULL-deref analog: silent early return
```

If `lastWithdrawRequest[_user]` does not equal the epoch where the loss price was stored, the lookup yields 0 and the function returns without touching `withdrawsRequestsByEpoch[_user][lossEpoch]` — exactly like dereferencing a NULL `out1` and treating it as a valid state.

Execution then falls into `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:319-350`), which computes `amount = withdrawsRequests[_user] + apr0 amounts` — the *aggregate* basis that still contains the haircutted epoch's full principal — burns the receipts and calls `_transferFundedClaim(_user, amount)` at par. The haircut is never applied.

There are two ways the pointer becomes wrong, both reachable by an unprivileged tranche holder:

1. **Two-epoch receipts.** User requests a withdraw in epoch N (it lands in the pending bucket). `stopEpochWithDuration(_lossAmount)` is executed and `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[N']` for that pending bucket, while the user's `withdrawsRequestsByEpoch[N]` is still live. The user then calls `requestWithdraw` again in a subsequent epoch, overwriting `lastWithdrawRequest` to N+1. On claim, `lossRecoveryPriceByEpoch[N+1] == 0` → loss path skipped → funded path pays the aggregate (including epoch-N basis) at par.

2. **Keyed-mismatch at write time.** `collectWithdrawFunds` stores the price under `epochNumber` *at collection time*, while the claim reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the *request* epoch. Since `epochNumber` is incremented inside `deposit()` during `stopEpoch` (`IdleCreditVault.sol:607-611`), any ordering in which the bump happens before `collectWithdrawFunds` permanently orphans the price entry for every user of that epoch.

Either way the receipt is paid as if fully funded. The excess paid is backed by strategy underlyings that belong to honest pending claimants and the `defaultRecoveryReserve`/`_transferFundedClaim` funding pool, causing insolvency for later claimers (later claims revert on insufficient balance, i.e., permanent freezing of unclaimed yield for the victims).

### Impact Explanation
Direct theft + insolvency: the attacker escapes the `stopEpochWithDuration` haircut entirely and withdraws 100% of basis. Since `pendingWithdraws` was cleared at funding time to the haircutted amount (`IdleCreditVault.sol:420`), the strategy only holds `pendingToFund` underlying for that epoch; paying any claimant at par overpays by `claimBasis - pendingToFund_share`, which comes out of funds reserved for other pending/loss-adjusted/APR0 claims. The last claimants' `_transferFundedClaim` reverts on insufficient balance — permanent freezing of their unclaimed yield. Quantified: the attacker profit equals `claimBasis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL`, i.e., the entire haircutted amount the epoch was supposed to absorb.

### Likelihood Explanation
Triggerable by any KYC-passed lender / tranche holder with no privileged role and no timing race: request a withdrawal, let `stopEpochWithDuration(_lossAmount)` realize a loss, submit a second `requestWithdraw`, then call `claimWithdrawRequest`. The protocol's own comments (`IdleCreditVault.sol:323-324`) explicitly support stacking multiple unclaimed requests across epochs, so multi-epoch state is an expected configuration. The guard `_checkNotAllowed(epochNumber <= lastWithdrawRequest)` does not help because it compares epoch numbers, not per-epoch funding status; nothing else validates that the aggregate `withdrawsRequests[_user]` being paid at par contains only fully-funded epochs. Confirmed bypass requires `lossRecoveryPriceByEpoch` to be keyed by the funding epoch while claims index by request epoch — the code stores under `epochNumber` at collection (`:421`) and reads under `lastWithdrawRequest` (`:790`), and these diverge whenever the second-request or stop-time-bump ordering applies.

### Recommendation
Key loss-adjusted claims by the same epoch identifier used at write time, and do not let a single `lastWithdrawRequest` pointer decide whether the loss path runs:

- In `_claimLossAdjustedWithdrawRequest`, iterate/check `withdrawsRequestsByEpoch[_user][e]` for every epoch with a non-zero `lossRecoveryPriceByEpoch[e]` (or store the loss epoch list per user), rather than deriving the epoch from `lastWithdrawRequest`.
- In `_claimFundedWithdrawRequest`, subtract epochs covered by a non-zero `lossRecoveryPriceByEpoch` from the par-funded basis so an unclaimed loss-adjusted receipt can never be paid at par.
- Alternatively, when `collectWithdrawFunds` records a loss, tag each pending epoch explicitly (e.g., a `lossEpochs` set keyed consistently with `withdrawsRequestsByEpoch`) so the claim-time lookup cannot silently miss.

### Proof of Concept
Foundry fork PoC outline (single-user haircut escape; deterministic, no privileged attacker):

```solidity
function testLossHaircutBypassedBySecondRequest() public {
    // 1. Deposit via KYC'd attacker, epoch N
    uint256 tranches = _depositWithUser(attacker, 100e6);
    vm.prank(manager); cdoEpoch.startEpoch();

    // 2. Attacker requests withdraw -> withdrawsRequestsByEpoch[N], lastWithdrawRequest=N
    _requestWithdrawWithUser(attacker, tranches);

    // 3. Honest stopEpochWithDuration with a realized loss; borrower funds pendingToFund
    uint256 lossAmount = /* realized loss */;
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    _fundBorrowerAndApprove(pendingToFund + cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), lossAmount);
    // lossRecoveryPriceByEpoch[fundingEpoch] = funded/pending < RECOVERY_FULL

    // 4. Attacker requests withdraw again -> lastWithdrawRequest overwritten to N+1
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(attacker, 1); // minimal second request bumps the pointer

    // 5. After the wait epoch, attacker claims: loss path looks up
    //    lossRecoveryPriceByEpoch[N+1] == 0 -> skipped;
    //    funded path pays aggregate withdrawsRequests at par.
    _stopCurrentEpoch();
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(/* CDO path or queue */ );
    strategy.claimWithdrawRequest(attacker);

    uint256 parPayout = 100e6; // full basis incl. haircutted epoch
    assertEq(underlying.balanceOf(attacker) - balPre, parPayout,
        "loss-adjusted receipt was paid at par, haircut bypassed");
}
```

Expected result on the current code: the attacker receives the full un-haircutted basis; `withdrawsRequestsByEpoch[attacker][N]` is zeroed by `_clearWithdrawClaimForEpoch`/`_claimFundedWithdrawRequest` without ever applying `lossRecoveryPriceByEpoch`, and a subsequent honest claimant's `_transferFundedClaim` reverts for lack of funds.

*Uncertainty note:* PoC step 3's correctness depends on whether `epochNumber` is bumped inside `stopEpochWithDuration` before `collectWithdrawFunds` is invoked (the bump lives in `deposit()`, `IdleCreditVault.sol:610`). If the bump precedes collection, the bypass occurs even with a single request (path 2 in Finding Description); if it follows, path 1 (second `requestWithdraw`) is required. Either ordering yields the exploit; I could not read the `stopEpochWithDuration` body to pin down which applies within the iteration budget.
