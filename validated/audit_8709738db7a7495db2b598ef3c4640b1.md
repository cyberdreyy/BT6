### Title
Internal error messages (DB errors, wrapped errors) leaked verbatim in HTTP auth error responses - ([File: core/web/auth/helpers.go])

### Summary
`jsonAPIError` serializes `err.Error()` directly into the JSON response body whenever the error is not already a `*models.JSONAPIErrors`. `AuthenticateBySession`, `AuthenticateByToken`, and the session `Create` handler forward any non-`auth.ErrorAuthFailed` error (e.g., a database error surfaced from `AuthorizedUserWithSession` or `FindUserByAPIToken`) straight up the call stack into `jsonAPIError`, without sanitizing or replacing it with a generic message.

### Finding Description
`jsonAPIError` at [1](#0-0)  falls back to `models.NewJSONAPIErrorsWith(err.Error())` for any error that isn't already a `*models.JSONAPIErrors`. This means whatever string is inside `err` is returned verbatim to the client.

In `AuthenticateBySession`, any error from `AuthorizedUserWithSession` other than the sentinel auth-failure case is returned as-is: [2](#0-1) . Likewise, in `AuthenticateByToken`, only `sql.ErrNoRows` and `ErrUserSessionExpired` are converted to the generic `auth.ErrorAuthFailed`; any other error from `FindUserByAPIToken` (e.g., a DB connectivity error, timeout, or driver-level failure) is returned unchanged: [3](#0-2) . The `Authenticate` middleware then passes that raw error straight to `jsonAPIError` with a 401 status: [4](#0-3) .

Similarly, `SessionsController.Create` forwards the error from `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` directly into `jsonAPIError` without wrapping/sanitizing it: [5](#0-4) . Note that the adjacent `GetUserWebAuthn` error path in the same handler is already sanitized to a generic "internal Server Error" message and logged server-side instead [6](#0-5) , showing the developers were aware of this exact leak pattern for one call but did not apply the same treatment to the `CreateSession` and `AuthenticateBySession`/`AuthenticateByToken` paths.

An unauthenticated attacker who can trigger a database-level error during the token/session lookup (e.g., malformed input causing a query error, a transient connectivity failure surfaced as an `error` from the ORM, or any other non-`sql.ErrNoRows` failure) will have that raw `err.Error()` string returned in the HTTP response body, since no auth/role check occurs before this failure — the request is by definition not yet authenticated.

### Impact Explanation
This is an information-disclosure issue: raw internal error text (potentially including DB driver messages, query fragments, or internal state) is returned to an unauthenticated caller. Depending on the underlying driver, these messages could reveal internal schema/table names or infrastructure details useful for further attacks, but they do not by themselves grant authentication bypass, privilege escalation, or key/secret disclosure. It maps to the lower "sensitive information disclosure" bounty class rather than a critical/high node-compromise class.

### Likelihood Explanation
Exploitability depends entirely on being able to reliably trigger a non-`sql.ErrNoRows` error from `AuthorizedUserWithSession` or `FindUserByAPIToken` (e.g., DB connectivity issues, timeouts) — conditions largely outside attacker control under normal operation. No attacker-triggerable path was found in the current context that deterministically forces such a backend error via crafted, unprivileged HTTP input; it typically requires an already-degraded DB/backend state. Likelihood is therefore low without further evidence of an attacker-controllable trigger for these specific internal error branches.

### Recommendation
In `AuthenticateBySession`, `AuthenticateByToken`, and `SessionsController.Create`, treat all internal (non-auth-failure) errors uniformly: log the detailed error server-side and return a generic error message (as already done for the `GetUserWebAuthn` failure) instead of passing `err` directly into `jsonAPIError`.

### Proof of Concept
Go handler-level test plan:
1. Implement a fake `Authenticator` whose `FindUserByAPIToken` returns a custom error, e.g. `errors.New("pq: connection to server at \"10.0.0.5\", port 5432 failed")`.
2. Invoke `auth.Authenticate(fakeAuthr, auth.AuthenticateByToken)` as gin middleware with valid `X-API-KEY`/`X-API-SECRET` headers set.
3. Assert the HTTP response status is 401 and inspect the JSON body via `models.JSONAPIErrors`; assert the returned `Detail`/`Title` field equals the raw injected string (demonstrating the leak) rather than a generic message.
4. Repeat with a fake `AuthorizedUserWithSession` error for `AuthenticateBySession`, and with `AuthenticationProvider().CreateSession` returning a custom DB error for `SessionsController.Create`, asserting the same leak.

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```

```go
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```
