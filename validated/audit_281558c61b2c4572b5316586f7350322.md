### Title
Fee-on-transfer underlyings mint unbacked strategy tokens and overstate NAV, causing insolvency for later withdrawers - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The credit vault stack assumes `transferFrom`/`transfer` move exactly `_amount` of `token`. `IdleCreditVault.deposit` mints strategy tokens to the CDO 1:1 with the requested `_amount` without measuring the balance actually received, and `IdleCDOEpochVariant.depositDuringEpoch` mints tranche shares and forwards `_amount` to the borrower while only `_amount - fee` ever arrives. With a fee-on-transfer (or fee-enabled) underlying such as USDT/USDC, the strategy token supply becomes unbacked, `getContractValue` overstates NAV, and the shortfall is socialized onto the last withdrawers/default claimants.

### Finding Description
The in-scope `IdleCDOCreditVault._deposit` correctly measures received tokens when minting tranche shares (`_contractTokenBalance(_token) - _preBal`), but then pushes the nominal `_amount` into the strategy:

- `contracts/IdleCDOCreditVault.sol:203-211`: `_transferUnderlyingsFrom(msg.sender, address(this), _amount)` followed by `IIdleCDOStrategy(strategy).deposit(_amount)`.
- `contracts/strategies/idle/IdleCreditVault.sol:601-616`: `deposit` does `underlyingToken.safeTransferFrom(msg.sender, address(this), _amount)` and unconditionally `_mint(msg.sender, _amount)` — no before/after balance check.
- `contracts/IdleCDOEpochVariant.sol:724-732`: `depositDuringEpoch` computes `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal`, calls `IdleCreditVault(strategy).mintStrategyTokens(_amount)` (which mints without moving any underlying, `IdleCreditVault.sol:621-624`), and forwards `_amount` to the borrower via `_transferUnderlyings(_borrower(), _amount)` — while the CDO only received `_amount - fee` from the depositor at line 685.
- `contracts/IdleCDOCreditVault.sol:125-128`: `getContractValue` trusts `_contractTokenBalance(strategyToken) + _contractTokenBalance(token) - unclaimedFees`, so every unbacked strategy token is counted as a full underlying of NAV.

The codebase supports generic ERC20 `token`/`underlyingToken` set at initialization; nothing restricts deployment to non-fee tokens, and USDT/USDC (the realistic underlyings for this credit vault) can enable fees by governance action.

### Impact Explanation
Two quantifiable insolvency paths:

1. **Buffer/closed-pool deposits**: a lender deposits `_amount` of a fee-on-transfer token. The CDO mints shares on `received = _amount - fee` (correct), but `IdleCreditVault.deposit(_amount)` pulls `_amount` from the CDO — funded partly by other depositors' idle balance — and mints `_amount` unbacked strategy tokens to the CDO. `getContractValue` reports `_amount` while only `_amount - fee` exists. The overstatement `fee` per deposit accrues to the last withdrawers' claims (`requestWithdraw`/instant-claims/default recovery basis), which become unpayable — permanent loss of `fee` per deposit for honest users, not the attacker.
2. **`depositDuringEpoch`**: an attacker-depositor deposits during a running epoch. The CDO receives `_amount - fee`, mints the attacker shares priced for `_amount + trancheInterest`, mints `_amount` strategy tokens to itself, and transfers `_amount` to the borrower — a transfer that only succeeds by draining other depositors' buffer cash. NAV is instantly overstated by `fee` plus the prorated `trancheInterest` granted against phantom principal; at `stopEpoch`/`_updateAccounting` the realized shortfall is socialized across AA/BB NAV via `_virtualPriceAux`.

The invariant broken is fair mint/burn / solvency: strategy-token supply (the CDO's claim on pool assets) exceeds actual underlying held.

### Likelihood Explanation
Medium. Requires the deployed underlying to charge a transfer fee — not the case for plain USDC today, but USDT already supports a fee switch and the vault is designed for credit stablecoin pools where USDT is a plausible underlying. No privileged action is needed to trigger once such a token is configured; any KYC-passing lender's ordinary `depositAA`/`depositBB`/`depositDuringEpoch` creates the unbacked mint. Existing guards don't help: `_skimDonatedAssets` only sweeps unsolicited transfers, `_guarded`/`isWalletAllowed` gate access not amounts-received, and `_checkDefault` compares `_strategyPrice` which is unaffected by the over-mint (strategy tokens are minted 1:1, not priced by balance).

### Recommendation
Measure actual received amounts everywhere underlying moves:

- In `IdleCreditVault.deposit`, record `balanceBefore`, then `safeTransferFrom`, then `_mint(msg.sender, balanceAfter - balanceBefore)` (and return the received amount so `totEpochDeposits`/`epochNumber` accounting stays consistent).
- In `IdleCDOCreditVault._deposit`, pass the measured received amount (already computed for `_minted`) to `strategy.deposit` instead of the nominal `_amount`, or have the strategy pull/record the received amount itself.
- In `depositDuringEpoch`, compute shares and `mintStrategyTokens` off the balance delta of the `_transferUnderlyingsFrom`, and transfer to the borrower only the amount actually received.
- Alternatively, explicitly document/enforce that only non-fee-on-transfer tokens may be used as `token`.

### Proof of Concept
Foundry fork PoC (buffer-phase deposit path; same structure applies to `depositDuringEpoch` by calling it while `isEpochRunning`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "../contracts/IdleCDOCreditVault.sol";
import "../contracts/strategies/idle/IdleCreditVault.sol";

// Fee-on-transfer ERC20: burns 10% on every transfer/transferFrom
contract FoTToken is ERC20 {
    constructor() ERC20("FoT", "FOT") {}
    function mint(address to, uint256 a) external { _mint(to, a); }
    function _transfer(address s, address r, uint256 a) internal override {
        uint256 fee = a / 10;
        super._transfer(s, r, a - fee);
        _burn(s, fee);
    }
}

contract FeeOnTransferTest is Test {
    IdleCDOCreditVault cdo;
    IdleCreditVault strat;
    FoTToken fot;

    function test_unbackedStrategyMint() public {
        fot = new FoTToken();
        // deploy cdo + strat wired with token = address(fot), borrower, AATranche...
        address victim = address(1);
        address attacker = address(2);

        // victim seeds the pool with a legitimate deposit (assume no fee yet or
        // pre-existing idle liquidity in the CDO covering the strategy pull)
        fot.mint(victim, 1_000e6);
        fot.mint(attacker, 1_000e6);
        // ... victim deposits 900e6 -> CDO holds idle balance / strategy tokens

        uint256 stratBefore = fot.balanceOf(address(strat));
        uint256 navBefore = cdo.getContractValue();

        vm.startPrank(attacker);
        fot.approve(address(cdo), 100e6);
        cdo.depositAA(100e6); // CDO receives 90e6, mints on 90e6
        vm.stopPrank();

        // IdleCreditVault.deposit minted 100 strategy tokens for 90 received
        assertEq(strat.balanceOf(address(cdo)) /* +100 */,
                 stratBefore + /* received */ 90e6 + 10e6 /* unbacked */);

        // NAV counts 100 while real backing grew by only 90
        // -> every withdrawal priced off tranchePrice/getContractValue is
        //    overpaid; the last claimants' requestWithdraw / instant claims
        //    revert or are haircut by ~10% of all FoT deposits.
        assertGt(cdo.getContractValue(),
                 navBefore + 90e6); // NAV overstatement == fee
    }
}
```

Steps:
1. Deploy `IdleCDOCreditVault` + `IdleCreditVault` strategy with a fee-on-transfer `token`.
2. KYC'd depositor calls `depositAA(100)` — CDO receives `90`, mints shares on `90`, then `IdleCreditVault.deposit(100)` mints `100` strategy tokens to the CDO for `90` received (funded from other depositors' idle balance).
3. `getContractValue` reports `+100` NAV against `+90` backing; subsequent withdraw requests and default-recovery basis are denominated in the inflated NAV, leaving the last claimants unpayable.

The identical defect exists in `depositDuringEpoch` (`IdleCDOEpochVariant.sol:724-732`), where shares, `mintStrategyTokens`, and the borrower transfer are all denominated in the nominal `_amount` while only `_amount - fee` arrived.
