### Title
`IdleCreditVault.deposit` mints strategy tokens 1:1 trusting `safeTransferFrom` without verifying received balance - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Ajna M-13 bug class — crediting funds after a `safeTransferFrom` that reports success without checking the actual balance delta — exists in `IdleCreditVault.deposit()` and the funding pull functions `collectWithdrawFunds()` / `collectInstantWithdrawFunds()` / `finalizeDefaultRecovery()`. The vault mints strategy tokens to the IdleCDO (or marks withdraw claims as funded) based on the *requested* `_amount`, not on tokens actually received. If the underlying (e.g. an upgraded USDC/USDT) executes `transferFrom` successfully but withholds the internal accounting update (blacklist-style upgrade), the strategy mints unbacked receipt tokens and inflates `getContractValue()`, diluting all existing lenders and permanently freezing withdrawals.

### Finding Description
`IdleCreditVault` is the strategy behind `IdleCDOEpochVariant` credit vaults. Its `price()` is hardcoded to `oneToken`, so every strategy token in circulation is treated as 1:1 backed by `underlyingToken`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
function deposit(uint256 _amount) external virtual override returns (uint256) {
  _onlyIdleCDO();
  if (_amount > 0) {
    underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
    _mint(msg.sender, _amount);        // mints requested amount, no balance check
  }
  ...
}

Note that `IdleCDOCreditVault._deposit` *does* measure the delta at the CDO level (`_preBal` / `_contractTokenBalance`), so tranche shares minted to the depositor are correct — but the strategy then pulls `_amount` *again* and mints `_amount` strategy tokens to the CDO unconditionally. The strategy-token supply and `getContractValue()` therefore inflate independently of the tokens actually held by the strategy. [5](#0-4) 

### Impact Explanation
With a token that returns `true` on `transferFrom` but does not credit the strategy (the exact "upgraded USDC blacklist" scenario from M-13):

- **Deposit path (running/buffer epoch, unprivileged lender):** `deposit()` mints unbacked strategy tokens to the CDO. NAV/`virtualPrice` count them at `price() == oneToken`, so the vault reports solvency it doesn't have. When the borrower later repays real funds at `stopEpoch`, the inflated strategy-token supply claims them first; the shortfall is socialized across all tranche holders, or withdrawals permanently revert on insufficient balance. Loss: up to the gap between minted supply and real backing.
- **Funding path (stopped epoch, griefing):** `collectWithdrawFunds(_amount)` either zeroes `pendingWithdraws` or writes `lossRecoveryPriceByEpoch`, and `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` — all as if funds arrived. Pending withdraw claimants' receipts become "funded" while the strategy holds nothing; `claimWithdrawRequest` / `claimInstantWithdrawRequest` then revert or pay out of other users' reserved funds. Permanent loss up to the whole `pendingWithdraws`/`pendingInstantWithdraws` bucket.
- **Recovery path:** `finalizeDefaultRecovery` inflates `defaultRecoveryPrice` with phantom recovered funds, letting claimants drain the real reserve faster than their haircut entitles, or reverting all recovery claims.

### Likelihood Explanation
Low probability, matching M-13's medium severity: requires the underlying token to adopt silent-accounting behavior via an upgrade (plausible for USDC/USDT-class proxy tokens used as pool currency) or a token that already behaves this way being whitelisted. No malicious privileged role is needed — any KYC-passing lender's deposit, or the honest manager's `stopEpoch`/`finalizeDefault` calls, trigger the miscrediting; the attacker is just the initiator of a griefing call or even an ordinary depositor.

### Recommendation
Apply the same balance-delta pattern used in `IdleCDOCreditVault._deposit` to every strategy-side pull:

```solidity
uint256 _preBal = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
uint256 _received = underlyingToken.balanceOf(address(this)) - _preBal;
require(_received >= _amount, "transfer shortfall");
_mint(msg.sender, _received);
```

Do the same in `collectWithdrawFunds`, `collectInstantWithdrawFunds`, and `finalizeDefaultRecovery` (revert if received < booked amount, or book only the received amount into `defaultRecoveryReserve`/`lossRecoveryPriceByEpoch`).

### Proof of Concept
Foundry fork test. Deploy a wrapper token that mimics an upgraded USDC: `transferFrom` returns `true` but does not credit the strategy (e.g. `vm.etch` the real USDC code with a modified `transferFrom`, or deploy a `SilentUSDC` mock and point the vault at it in a fork of an existing deployment's storage — simpler: unit-test against the strategy directly).

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";

// Mimics an "upgraded" USDC: reports success, never credits recipient.
contract SilentUSDC is Test {
    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;
    uint8 public constant decimals = 6;
    function mint(address to, uint256 a) external { balanceOf[to] += a; }
    function approve(address s, uint256 a) external { allowance[msg.sender][s] = a; }
    // succeeds, debits nothing / credits nothing
    function transferFrom(address, address, uint256) external pure returns (bool) { return true; }
    function transfer(address, uint256) external pure returns (bool) { return true; }
}

contract SilentTransferPoC is Test {
    IdleCreditVault vault;
    SilentUSDC usdc;
    address cdo = makeAddr("idleCDO");
    address lender = makeAddr("lender");

    function setUp() public {
        usdc = new SilentUSDC();
        vault = new IdleCreditVault();
        vault.initialize(address(usdc), address(this), address(this), makeAddr("borrower"), "Borrower", 5e18);
        // whitelist the mock "CDO" (an EOA acting as IdleCDOEpochVariant is enough for strategy-level PoC)
        vault.setWhitelistedCDO(cdo);
        // lender deposits via the CDO: CDO pulls tokens and calls strategy.deposit
        usdc.mint(cdo, 1_000_000e6);
        vm.prank(cdo);
        usdc.approve(address(vault), type(uint256).max);
    }

    function testDepositMintsUnbackedStrategyTokens() public {
        // Mock epochEndDate()/isEpochRunning() on the fake CDO is not needed:
        // deposit() only calls isEpochRunning on idleCDO; use a contract that returns false.
        // (For a pure-strategy PoC, deploy a tiny stub CDO exposing isEpochRunning()==false.)
        uint256 supplyBefore = vault.totalSupply();
        vm.prank(cdo);
        vault.deposit(1_000_000e6);          // safeTransferFrom "succeeds", credits nothing
        assertEq(vault.totalSupply() - supplyBefore, 1_000_000e6); // minted anyway
        assertEq(usdc.balanceOf(address(vault)), 0);               // nothing received
        // => getContractValue()/price() now count 1M phantom units against real borrower repayments
    }
}
```

The identical test applied to `collectWithdrawFunds(1_000_000e6)` (with `pendingWithdraws` primed via `requestWithdraw`) shows `pendingWithdraws` cleared while `usdc.balanceOf(vault) == 0`, leaving claimants permanently unfunded.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
