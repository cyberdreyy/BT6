### Title
Unbounded `inBuf` growth in `Splitter.Write` allows single-job memory exhaustion - ([File: common/buildlogger/innerstream/innerstream.go])

### Summary
`Splitter.Write` in `common/buildlogger/innerstream/innerstream.go` appends attacker-controlled step-runner stdout bytes to `s.inBuf` with no size cap whenever a chunk lacks a `'\n'`, allowing an unbounded in-memory buffer to grow for the lifetime of a single nested `run:` step's output stream. Unlike other log-handling paths in the runner (trace output limit, container log limit, bufio line-splitting limits), this specific decode buffer has no equivalent cap.

### Finding Description
`Splitter.Write` scans each write for a `'\n'`; when none is found it does `s.inBuf = append(s.inBuf, p...)` and returns, deferring processing until a newline eventually arrives [1](#0-0) . There is no maximum length check on `inBuf` before or after the append, so a malicious inner step-runner process (attacker controls this via a `run:` step, per `functions/concrete/run/run_steps.go`, `runUserSteps`) can stream an arbitrarily large chunk of bytes with no `'\n'` and force `inBuf` to grow to the size of the entire malicious payload [2](#0-1) .

Critically, the runner's existing log-size protections do not apply here: `helpers/trace/buffer.go`'s `limitWriter` enforces `DefaultTraceOutputLimit` (4MB) only on bytes actually written to the trace buffer [3](#0-2) , but that check happens *after* `consumeLine()` extracts a completed line and forwards `body` downstream [4](#0-3) . Since `consumeLine()` is only invoked once a `'\n'` is found, an attacker who never sends `'\n'` never triggers `consumeLine`, and the trace-level cap never engages — the bytes sit indefinitely in `inBuf`. Other similar decode paths in the codebase (e.g. Docker/Kubernetes log demux at `DefaultReaderBufferSize = 16 * 1024`, or `limitwriter.New(&buf, ServiceLogOutputLimit)` for container logs at `executors/docker/docker.go`) impose an explicit cap on unterminated line buffers; `innerstream.Splitter` has no analogous cap.

### Impact Explanation
Each job gets its own `Splitter` instance, created fresh per nested `run:` dispatch in `runUserSteps` [5](#0-4) , so this is not a shared-state corruption across jobs. However, `gitlab-runner` executes concurrent jobs as goroutines within a single OS process (subject to the `concurrent` setting), so heap growth from one job's unbounded `inBuf` consumes memory shared by the whole process. A sufficiently large malicious payload can drive up heap usage and GC pressure to the point of triggering OS-level memory pressure/OOM, which can delay or kill other concurrently running jobs in the same runner process — including their cache/artifact upload goroutines. This matches the scoped impact of resource exhaustion causing delayed handling for other jobs sharing the process, though the causal link is indirect (via general process memory pressure rather than a shared lock or blocking call).

### Likelihood Explanation
Preconditions are met by an ordinary pipeline author: any CI job using a `run:` step (executed through the concrete step-runner integration) fully controls the nested step's stdout/stderr content, and can trivially emit a large byte stream without any `'\n'` character. The attack is deterministic and repeatable — no race conditions or special timing needed, just sustained output without a line terminator.

### Recommendation
Add an explicit maximum size for `Splitter.inBuf` (mirroring `DefaultReaderBufferSize` or a dedicated constant), and once exceeded, either: (a) flush/truncate the accumulated bytes as a synthetic line and emit a "line too long" marker before continuing, or (b) return an error from `Write` that the caller (`runUserSteps`) surfaces as a job failure. This bounds memory usage per nested job stream independent of whether the trace's own `OutputLimit` is ever reached.

### Proof of Concept
```go
func TestSplitterUnboundedInBufGrowth(t *testing.T) {
    var stdout, stderr bytes.Buffer
    s := innerstream.New(&stdout, &stderr)

    // Simulate a malicious step-runner stdout stream: large chunks, no '\n'.
    chunk := bytes.Repeat([]byte("A"), 10*1024*1024) // 10MB, no newline
    for i := 0; i < 50; i++ { // attempt to grow inBuf to ~500MB
        _, err := s.Write(chunk)
        require.NoError(t, err)
    }

    // Assert: this test should fail today because there is no cap;
    // after a fix, Write should either error out or cap growth once a
    // configured max line size is exceeded.
    // e.g. assert.LessOrEqual(t, s.InBufLen(), maxLineSize)
}
```
Run with `go test -run TestSplitterUnboundedInBufGrowth -v` and observe unbounded memory growth (e.g. via `runtime.MemStats`) with no error returned, confirming the missing cap.

func (s *Splitter) Write(p []byte) (int, error) {
	written := 0
	for len(p) > 0 {
		nl := bytes.IndexByte(p, '\n')
		if nl == -1 {
			s.inBuf = append(s.inBuf, p...)
			return written + len(p), nil
		}

func (s *Splitter) consumeLine() error {
	line := s.inBuf
	if len(line) <= headerLen {
		// Malformed (shorter than the prefix). Drop it rather than emit
		// header bytes to the trace.
		return nil
	}

	streamType := line[streamTypeOff]
	lineType := line[lineTypeOff]
	body := line[headerLen:]

	pending, w := &s.pendingStdout, s.stdout
	if streamType == streamStderr {
		pending, w = &s.pendingStderr, s.stderr
	}

	if len(*pending) > 0 {
		out := *pending
		if lineType == linePartial && out[len(out)-1] == '\n' {
			out = out[:len(out)-1]
		}
		if _, err := w.Write(out); err != nil {
			return err
		}
	}

	*pending = append((*pending)[:0], body...)
	return nil
}
