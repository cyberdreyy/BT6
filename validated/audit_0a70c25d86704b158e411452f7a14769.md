Found it. `OrderedListWalker::fetch_leaves` in `crates/proof/mpt/src/list_walker.rs` recurses through every `Branch`/`Extension`/`Blinded` node with no recursion-depth counter, and each `Blinded` child triggers an oracle fetch of an attacker-controlled preimage inside the fault-proof program — this is the direct structural analog of the LWAPP unbounded-encapsulation crash (CVE-2018-9256).

### Title
Unbounded recursive trie traversal in `OrderedListWalker::fetch_leaves` allows stack-overflow DoS of the fault-proof program via attacker-supplied preimages - ([File: crates/proof/mpt/src/list_walker.rs])

### Summary
`OrderedListWalker::fetch_leaves` recursively walks a Merkle Patricia Trie's `Branch`/`Extension`/`Blinded` nodes to collect leaves, calling itself for every non-leaf, non-empty child with no depth limit. `TrieNode::Blinded` children are resolved via `fetcher.trie_node_by_hash`, whose preimages in the fault-proof program come from an untrusted/attacker-influenced preimage oracle (the L1/L2 chain data being proven, or a malicious counterparty in the dispute game). Because the recursion depth is bounded only by the number of nested nodes the attacker can construct and get accepted as valid preimages for a claimed hash, an attacker can build an extremely deep chain of single-child `Extension`/`Branch` nodes (each blinding to the next) and force `fetch_leaves` to recurse until the call stack overflows — the same bug class as the LWAPP dissector's unbounded encapsulation recursion in CVE-2018-9256. [1](#0-0) 

### Finding Description
`fetch_leaves` is called from `hydrate`, which is invoked by `OrderedListWalker::try_new_hydrated` — used throughout the fault-proof program to reconstruct L1 receipts/transactions and L2 transactions from a claimed trie root: [2](#0-1) [3](#0-2) 

Each call into `fetch_leaves` recurses on `TrieNode::Branch { stack }` items, `TrieNode::Extension { node, .. }`, and specifically for `TrieNode::Blinded { commitment }` resolves an oracle preimage and recurses again on the result: [4](#0-3) 

There is no `depth` parameter or maximum-recursion check anywhere in this function or its call sites, unlike the CBOR parser elsewhere in the codebase which explicitly enforces `MAX_CBOR_NESTING_DEPTH`: [5](#0-4) [6](#0-5) 

The `TrieNode::open`/`insert`/`delete` walking functions are self-limiting because each step consumes at least one nibble from a fixed-length key (bounded to ~64 nibbles for a 32-byte hash key). `fetch_leaves`, by contrast, walks the *entire* trie structure to collect every leaf and is not bound by key length at all — an `Extension` node can point to another single-child `Branch`/`Extension` an arbitrary number of times, and each hop is a fresh stack frame plus a new preimage-oracle round trip. Since the preimage oracle in the proof program derives its data from potentially attacker-influenced L1/L2 chain state or a malicious dispute-game counterparty supplying preimages for a claimed hash, this recursion depth is effectively attacker-controlled.

### Impact Explanation
A stack overflow in the fault-proof program's trie walker halts/crashes the program that computes the claimed output root during a dispute game. This can prevent the honest party from producing a valid execution trace/output root for a disputed claim, potentially causing the challenger or defender to be unable to respond correctly within the dispute window — a node-halt / wrong-or-missing-provable-output-root condition reachable purely by crafting malicious L1 data or preimages that a claim's execution must traverse.

### Likelihood Explanation
Reaching this path requires only supplying block data (receipts/transactions trie) whose structure, when derived through the normal proof flow, produces a deeply nested chain of blinded extension/branch nodes — something an attacker controlling L1 transaction/receipt ordering or a bad-faith preimage source in the dispute game can construct. No privileged access is needed beyond being able to get such data included/claimed for proving, which the rules explicitly permit analyzing (fault-proof program and MPT paths).

### Recommendation
Add an explicit, bounded recursion/iteration depth counter to `fetch_leaves` (and thread it through the `Blinded` preimage-fetch path), returning a `TrieNodeError`/`OrderedListWalkerError` once a maximum depth (e.g., matching the theoretical max nibble depth of the trie, ~64, plus a small safety margin) is exceeded — mirroring the `MAX_CBOR_NESTING_DEPTH` pattern already used in `crates/proof/tee/registrar/src/cbor.rs`. Alternatively, convert the traversal to an explicit iterative worklist (e.g., a `VecDeque`/stack of pending nodes) instead of native recursion, eliminating the stack-overflow vector entirely regardless of trie shape.

### Proof of Concept
1. Construct a chain of N nested `TrieNode::Extension`/single-child `TrieNode::Branch` nodes, each blinded (RLP length ≥ 32 bytes) so it resolves via `TrieNode::Blinded { commitment }`.
2. Provide these as preimages through a `TrieProvider`/preimage oracle such that the root hash resolves to node 1, whose child resolves to node 2, and so on down to a terminal `Leaf`.
3. Call `OrderedListWalker::try_new_hydrated(root, &fetcher)` (as done in `OracleL1ChainProvider::receipts_by_hash`/`block_info_and_transactions_by_hash` or `OracleL2ChainProvider::block_by_number`) with a sufficiently large N (a few thousand nested nodes, well within the native call-stack limit of the fault-proof program's execution environment).
4. Observe that `fetch_leaves`'s unbounded recursion exhausts the stack, crashing the proof program instead of returning a decode error.

    /// Traverses a [`TrieNode`], returning all values of child [`TrieNode::Leaf`] variants.
    fn fetch_leaves(
        trie_node: &TrieNode,
        fetcher: &F,
    ) -> OrderedListWalkerResult<VecDeque<(Bytes, Bytes)>> {
        match trie_node {
            TrieNode::Branch { stack } => {
                let mut leaf_values = VecDeque::with_capacity(stack.len());
                for item in stack {
                    match item {
                        TrieNode::Blinded { commitment } => {
                            // If the string is a hash, we need to grab the preimage for it and
                            // continue recursing.
                            let trie_node = Self::get_trie_node(commitment.as_ref(), fetcher)?;
                            leaf_values.append(&mut Self::fetch_leaves(&trie_node, fetcher)?);
                        }
                        TrieNode::Empty => { /* Skip over empty nodes, we're looking for values. */
                        }
                        item => {
                            // If the item is already retrieved, recurse on it.
                            leaf_values.append(&mut Self::fetch_leaves(item, fetcher)?);
                        }
                    }
                }
                Ok(leaf_values)
            }
            TrieNode::Leaf { prefix, value } => {
                Ok(vec![(prefix.to_vec().into(), value.clone())].into())
            }
            TrieNode::Extension { node, .. } => {
                // If the node is a hash, we need to grab the preimage for it and continue
                // recursing. If it is already retrieved, recurse on it.
                match node.as_ref() {
                    TrieNode::Blinded { commitment } => {
                        let trie_node = Self::get_trie_node(commitment.as_ref(), fetcher)?;
                        Ok(Self::fetch_leaves(&trie_node, fetcher)?)
                    }
                    node => Ok(Self::fetch_leaves(node, fetcher)?),
                }
            }
            TrieNode::Empty => Ok(VecDeque::new()),
            _ => Err(TrieNodeError::InvalidNodeType.into()),
        }
    }
