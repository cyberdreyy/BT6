### Title
Limit orders (`Order`) have no deadline/expiry, letting a permissionless keeper delay execution until maximum allowed slippage is extracted from the user - (File: `type-crate/src/types/order.rs`)

### Summary
`marginfi_account_place_order` creates an on-chain `Order` (stop-loss/take-profit) PDA that is designed to be executed later by any permissionless keeper via `start_execute_order`/`end_execute_order`. The `Order` struct explicitly has no creation timestamp or deadline field — the source even carries the comment `// TODO timestamp creation` — and neither `place_order` nor `start_execute_order`/`end_execute_order` check any time bound before allowing execution.

### Finding Description
The `Order` account is defined with no expiry/deadline mechanism at all: [1](#0-0) 

The executor of an order is completely unprivileged — anyone can supply themselves as `executor` in `StartExecuteOrder`: [2](#0-1) 

`start_execute_order` only checks that the trigger condition (`net <= sl` or `net >= tp`) is currently satisfied, with no time-based validation of when the trigger became true or how long the order has been sitting live: [3](#0-2) 

`end_execute_order` bounds the keeper's extractable value only by `order.max_slippage` (capped at `MAX_ORDER_SLIPPAGE`, ~10%) and `fee_state.order_execution_max_fee`, both of which are static, price-independent tolerances rather than time-bound guarantees: [4](#0-3) 

Because the trigger condition merely needs to be true at execution time and the slippage/fee bound is fixed, once an order becomes triggerable a keeper is not compelled to execute promptly. As shown by the test comment describing intended keeper behavior, keepers are expected to maximize their own profit up to the slippage cap: [5](#0-4) 

This is functionally the same root cause as the referenced Stableswap finding: an action intended to be time-bound (execute promptly once the condition is met, within acceptable price movement) has no deadline enforcement, so an unprivileged party (keeper here, "miner" in the original report) can freely withhold execution and choose the moment that is worst for the user and best for themselves, up to the maximum slippage/fee the protocol allows.

### Impact Explanation
A keeper can wait, after a take-profit or stop-loss trigger condition is first met, for price movement that approaches (but stays within) the user's configured `max_slippage`/`order_execution_max_fee` bound before executing, systematically capturing the maximum extractable spread on every order rather than executing near the trigger price. This durably and repeatably redirects value from order-placing users to keepers on every limit order execution, which is a direct financial-effect issue, not merely theoretical, since it's the deterministic outcome of the missing deadline given profit-seeking keepers are permissionless (`executor` has "no checks whatsoever").

### Likelihood Explanation
High likelihood: keeper execution is fully permissionless and economically incentivized to delay (per the codebase's own test naming, "keeper earns the max profit"), and no code path enforces any time bound between trigger and execution. This requires no privileged access, no state corruption, and no admin action — merely patience by any bot watching triggerable orders.

### Recommendation
Add a creation/trigger timestamp to `Order` (the codebase already flags this gap with `// TODO timestamp creation`) and enforce a maximum allowed delay between when the trigger condition first becomes satisfiable and when `end_execute_order` can settle, or alternatively tighten the slippage bound as a function of elapsed time so that delay does not linearly benefit the keeper up to the full slippage cap.

### Proof of Concept
1. User places a take-profit order via `marginfi_account_place_order` with `max_slippage` at or near `MAX_ORDER_SLIPPAGE` (the cap, ~10%).
2. Price reaches the take-profit threshold; the order becomes eligible to execute (`start_execute_order` trigger check passes) as shown in `programs/marginfi/src/instructions/marginfi_account/order.rs` lines 303-321.
3. Rather than executing immediately, the permissionless keeper (see `executor: UncheckedAccount` with no checks, lines 683-695) monitors price and waits.
4. Keeper executes only once price movement lets them withdraw the maximum amount allowed under `slippage_frac`/`max_fee_frac` (`end_execute_order`, lines 411-421), maximizing their own profit at the user's expense, exactly as demonstrated by the existing test `limit_order_take_profit_max_profit_allowed` in `programs/marginfi/tests/user_actions/limit_orders.rs` (lines 357-435), which asserts the keeper nets the maximum allowed profit share.
