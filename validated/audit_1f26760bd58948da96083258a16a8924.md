### Title
Post-default instant-withdraw requests are never funded yet are paid 1:1 from vault balance, draining other users' funded receipts - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` lacks the `defaultRecoveryFinalized` handling that `requestWithdraw` has. After default finalization a user can open a new instant-withdraw request, receive minted receipt tokens, and later claim them at par through `_transferFundedClaim`, which only protects `defaultRecoveryReserve` — not underlyings earmarked for other users' funded receipts. The result is theft of funded-claim liquidity by an unprivileged tranche holder, the analog of the use-after-free/double-spend bug class (a receipt is honored against state that no longer backs it).

### Finding Description
`requestWithdraw` explicitly branches on `defaultRecoveryFinalized`: it reverts if any stale receipt exists (`instantWithdrawsRequests[_user] != 0 || postDefaultRequests[_user] != 0`), burns the CDO's tokens, and books the request into `postDefaultRequests` without increasing `pendingWithdraws` (lines 247-257 of `contracts/strategies/idle/IdleCreditVault.sol`). This isolates post-default claims to the haircut reserve via `_transferDefaultRecovery`.

`requestInstantWithdraw` (lines 356-375) has no such branch. Post-default it still:
- mints `_amount` receipt strategy tokens to `_user`,
- increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `pendingInstantWithdraws`.

After default, no epoch runs, so `collectInstantWithdrawFunds` (lines 398-403) is never invoked and `pendingInstantWithdraws` is never funded.

`claimInstantWithdrawRequest` (lines 380-393) then:
1. calls `_claimDefaultedInstantWithdrawRequest(_user)`, which pays the defaulted-epoch basis at `defaultRecoveryPrice` from the reserve and decrements `instantWithdrawsRequests[_user]` by only that defaulted-epoch basis;
2. pays the entire remaining `instantWithdrawsRequests[_user]` — which now includes the attacker's new unfunded post-default request — via `_transferFundedClaim` (lines 897-907).

`_transferFundedClaim` only guards `balance - reserve < _amount`. Any non-reserve underlyings in the vault (funded amounts collected for other users' normal/instant receipts that haven't been claimed yet, or skimmed/donated balance) are freely spendable. The attacker burns receipt tokens they legitimately hold and drains liquidity belonging to other claimants — one receipt, paid against funds backing a different receipt (broken "one receipt one payout" / solvency invariant). The `requestWithdraw` post-default guard (`instantWithdrawsRequests[_user] != 0 → revert`) confirms the intended invariant that no new request may be opened while stale receipts exist; `requestInstantWithdraw` simply never enforces it.

### Impact Explanation
An unprivileged tranche-token holder can mint a post-default instant receipt of arbitrary size (bounded by their CDO-side tranche balance translated to strategy tokens) and immediately claim it at par, stealing underlyings that back other users' already-funded withdraw receipts. Loss equals the non-reserve vault balance up to the attacker's request size; victims' later claims revert or underflow on `_burn`/insufficient balance — permanent loss plus freezing of their funded receipts.

### Likelihood Explanation
Requires the vault to be in the defaulted/finalized state and to hold non-reserve underlyings (common: `collectWithdrawFunds`/`collectInstantWithdrawFunds` pull funded amounts into the strategy ahead of user claims, so unclaimed funded receipts typically sit in the vault). The attacker needs only to hold tranche tokens and call the CDO's instant-withdraw request path. Note: this assumes `IdleCDOEpochVariant.requestInstantWithdraw`/`claimInstantWithdrawRequest` remain callable when `defaulted()` — the strategy code clearly anticipates post-default instant claims (the `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` branch), but the CDO-side gating should be verified during PoC; if the CDO hard-blocks all instant paths post-default, the request path may be unreachable while the claim path remains, narrowing the finding to pre-default requests made but never funded before default.

### Recommendation
Mirror the `requestWithdraw` post-default logic in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, revert if `_hasWithdrawRequest(_user) || instantWithdrawsRequests[_user] != 0 || postDefaultRequests[_user] != 0`, then book the amount into `postDefaultRequests` (or revert outright if instant withdrawals are not meant to exist post-default), and never increase `pendingInstantWithdraws`. Also consider reverting in `claimInstantWithdrawRequest` if the residual `instantWithdrawsRequests[_user]` exceeds the funded amount tracked for that user.

### Proof of Concept
Foundry sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// Setup: deposit AA, run an epoch, borrower defaults, manager calls
// finalizeDefaultRecovery -> defaultRecoveryFinalized = true,
// defaultRecoveryReserve set, some user B has a funded unclaimed receipt
// (vault holds underlying balance > reserve).

// Attacker A (unprivileged tranche holder):
uint256 t = IERC20(AAtranche).balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(t, address(AAtranche)); // mints receipt, bumps pendingInstantWithdraws

// A claims immediately:
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
// _claimDefaultedInstantWithdrawRequest clears only the default-epoch basis;
// residual instantWithdrawsRequests[A] == new unfunded request, paid via _transferFundedClaim
assertGt(underlying.balanceOf(attacker) - balPre, 0);

// Victim B's funded claim now reverts or pays less:
vm.prank(victim);
vm.expectRevert();
cdoEpoch.claimWithdrawRequest(); // insolvent: vault balance < funded obligation
```
