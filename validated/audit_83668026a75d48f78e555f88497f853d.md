External Initiators bypass the intended int-ID exclusion in job runs and can trigger `RunJobV2` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the int32-ID `RunJobV2` path behind an `isUser` check derived from `auth.GetAuthenticatedUser`, with a comment stating "only users are allowed to run jobs using int IDs - EIs not allowed." However, `AuthenticateExternalInitiator` also populates the same `SessionUserKey` context value with a synthetic `run`-role `User`, so `GetAuthenticatedUser` cannot distinguish a real user from an EI-derived pseudo-user, defeating the intended exclusion.

### Finding Description
In `core/web/pipeline_runs_controller.go`, `Create` does: [1](#0-0) 
It calls `auth.GetAuthenticatedUser(c)` to decide whether the caller may use the int32-ID path that calls `prc.App.RunJobV2`.

The root cause is in `core/web/auth/auth.go`: `AuthenticateExternalInitiator` validates EI credentials and then sets both `SessionExternalInitiatorKey` and `SessionUserKey` (with a synthetic `clsessions.User{Role: clsessions.UserRoleRun}`): [2](#0-1) 

`GetAuthenticatedUser` simply reads `SessionUserKey` from the gin context without any way to know whether it was set by `AuthenticateBySession`/`AuthenticateByToken` (real user) or `AuthenticateExternalInitiator` (EI pseudo-user): [3](#0-2) 

Because the `/v2/jobs/:ID/runs` create route is authenticated via `auth.Authenticate` with multiple `authMethod`s (session/token AND external-initiator methods composed together, consistent with how EIs must reach this same handler to trigger UUID/webhook-style runs), an EI credential holder satisfies `isUser == true` in the same way a real dashboard user would. This directly contradicts the code comment's stated intent and lets an EI supply an int32 job ID and reach `prc.App.RunJobV2(ctx, jobID, nil)`.

### Impact Explanation
An external-initiator credential (a lower-trust, narrowly-scoped credential intended only to post webhook-triggered runs) can trigger arbitrary jobs by their numeric database ID via `RunJobV2`, bypassing the intended restriction that only interactive/dashboard users can do so. This is an authorization-exactness / role-boundary bypass: an EI-scoped credential gains capability equivalent to a `run`-role user for any job ID, not just the job(s) the EI was provisioned for. `RunJobV2` executes the job's pipeline (potentially involving on-chain transmitters and node keys, and is gated only by `build.IsProd()` at the application layer). This matches the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: an attacker only needs valid EI credentials (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret`-style headers) that already grant them "run" capability by design for their own job — no admin/session/token needed. The request is a single unauthenticated (w.r.t. session) `POST /v2/jobs/<int32-id>/runs` call with EI headers. This is trivially repeatable and does not depend on any race condition or timing.

### Recommendation
Distinguish EI-derived pseudo-users from real authenticated users. Options:
- Do not set `SessionUserKey` in `AuthenticateExternalInitiator`; instead check `auth.GetAuthenticatedExternalInitiator(c)` explicitly in `PipelineRunsController.Create` and reject (or route separately) when an EI is present.
- Alternatively, use a distinct context key/type (e.g., `SessionUserKey` value tagged with an "is EI" flag, or a separate `IsExternalInitiator bool` on the context) so `Create` can call `_, isEI := auth.GetAuthenticatedExternalInitiator(c); if isEI { reject int32 path }` independent of `isUser`.

### Proof of Concept
Handler/integration test plan:
1. Set up a `TestApplication` with a job that has an int32 `ID`, and create/persist an `ExternalInitiator` with known access key/secret (`bridges.ExternalInitiator`).
2. Build an HTTP client that sends `POST /v2/jobs/<jobID>/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers set to the EI's credentials, and no session cookie and no `X-API-KEY`/`X-API-SECRET`.
3. Assert the response is `200 OK` and a `PipelineRunResource` is returned (i.e., `RunJobV2` was actually invoked), instead of the expected `422 "bad job ID"` that the comment on `pipeline_runs_controller.go` line 110 implies should occur for EI callers.
4. Optionally use `mocks.Application` with `On("RunJobV2", ...)` to assert the call occurred with the EI-authenticated request, directly proving the exclusion in the comment is not enforced.
