Found a genuine analog to the CVE's bug class: two duplicate-block-tenure checks use inconsistently "tagged" (differently-scoped) queries for the same conceptual predicate — exactly the CVE-2016-9449 pattern of "inconsistent naming of access query tags" causing one code path to under-check what another checks correctly.

### Title
Inconsistent duplicate-block query scope between the v1 tenure-change check (`get_last_globally_accepted_block`) and the v0 recheck (`get_last_signed_block`) can let a v1-protocol signer sign a conflicting tenure-start block - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
The v1 tenure-change duplicate-block guard, `SignerChainState::validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs`, queries only `get_last_globally_accepted_block` [1](#0-0)  to decide whether the signer already committed to a block in the current tenure. The equivalent v2 check instead uses `get_last_signed_block`, which also covers `LocallyAccepted` blocks [2](#0-1) . A regression test explicitly documents that the v2 query was fixed to close this exact gap: "Before the fix, this would have incorrectly passed because `get_last_globally_accepted_block` would not find the locally-accepted block." [3](#0-2)  The v1 path, still used by signers running the older (pre-global-state) protocol version, was left on the narrower, pre-fix query.

### Finding Description
For protocol versions that use the local (non-global) state machine, `check_block_against_state` routes through `check_block_against_local_state` → `SortitionsView::check_proposal`, which for tenure-change blocks calls `validate_tenure_change_payload` in `v1.rs`. That function's duplicate guard is:

```
let last_in_current_tenure = signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)...
``` [4](#0-3) 

`get_last_globally_accepted_block` filters strictly on `state = GloballyAccepted` [5](#0-4) . A block the signer has already `LocallyAccepted` (i.e., already signed with its own key, per the `BlockState` machine [6](#0-5) ) but that has not yet gathered the 70% group signatures to become globally accepted, is invisible to this query. A miner can therefore re-propose a second, conflicting tenure-start block for the same tenure (different transactions/parent), and this v1 check will pass it through as if no prior commitment existed — exactly the scenario the v2 test at `check_tenure_change_rejects_when_locally_accepted_block_exists` was written to prevent, but only for the v2 path [7](#0-6) .

This breaks the "one-per-height / no double-sign" equality the signer is designed to preserve: a signer must never place a second signature on a conflicting block in the same tenure once it has already signed one (as documented for the section-5 pre-commit conflict guard [8](#0-7) ). The pre-commit-time conflict guard (`get_signed_conflicts`) is a backstop for exactly this blind spot in `check_proposal`, but it only re-checks "own tenure" conflicts among *signed* blocks reaching the pre-commit threshold later — it does not prevent the v1 `check_proposal` from initially waving through and queuing validation/pre-commit for the second block, and if the network conditions (freshness/staleness of the first signature) line up, the v1-specific gap plus the freshness-based own-tenure guard could still permit a second signature before the first is considered "fresh" from the signer's own perspective, since the guard's `OWN` branch depends on the *node's* view of tenure tip, not directly on the first block's local-accept status.

### Impact Explanation
If exploitable, this is a Critical-class issue per the rules: a signer signing a conflicting/non-canonical block at the same height/tenure it already locally accepted, which is the direct double-sign/equivocation scenario the signer's whole pre-commit design exists to prevent [9](#0-8) .

### Likelihood Explanation
Requires only a single miner (one slot) proposing two competing tenure-start blocks and does not require colluding signers — it exploits a difference between the v1 and v2 code paths that is otherwise identical in intent. Likelihood is limited to signer fleets still running the local-state (v1/pre-global-state) protocol version rather than the newer global-state (v2) version, since v2 was already patched. I could not fully verify from the indexed code whether v1 is still an actively reachable/default protocol path in the current codebase state, or whether other guards (e.g., `check_block_against_signer_db_state`'s tenure-tip recheck at validate-ok/pre-commit time) fully close this gap before a second signature is produced — this needs verification in a full checkout, since the index does not show the complete call graph deciding which protocol version is active by default.

### Recommendation
Align `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload`'s duplicate check with the v2 fix: use `get_last_signed_block` (covering both `LocallyAccepted` and `GloballyAccepted`) instead of `get_last_globally_accepted_block`, so both protocol versions apply the same "already signed" tag/predicate consistently.

### Proof of Concept
1. Run a signer on the v1 (local-state) protocol path.
2. Miner proposes tenure-start block A; signer validates and locally accepts (signs) A via `mark_locally_accepted`, before A reaches the 70% group threshold.
3. Miner proposes a second, conflicting tenure-start block B for the same tenure (same `consensus_hash`, different contents/parent).
4. `SortitionsView::check_proposal` → `validate_tenure_change_payload` (v1) calls `get_last_globally_accepted_block(consensus_hash)`, which returns `None` because A is only `LocallyAccepted`, not `GloballyAccepted` [1](#0-0) .
5. B is not rejected with `DuplicateBlockFound` and proceeds to validation/pre-commit, unlike the v2 path which is proven by the analogous test to correctly reject in this situation [10](#0-9) .

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
