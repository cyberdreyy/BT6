### Title
View-role authenticated users can read a bridge's plaintext OutgoingToken and credential-bearing URL via GET /v2/bridge_types/:BridgeName - ([File: core/web/bridge_types_controller.go])

### Summary
The route `GET /v2/bridge_types/:BridgeName` is registered without any `Requires*Role` wrapper, unlike `Create`/`Update`/`Destroy`, so any authenticated caller (including view-role sessions/tokens) can call `bt.Show`. The handler serializes the bridge via `presenters.NewBridgeResource`, which unconditionally includes `OutgoingToken` (no `omitempty`, no redaction) and the raw `URL`, both of which are secrets used to authenticate the node's outbound requests to external adapters.

### Finding Description
`v2Routes` wires the bridge routes as: [1](#0-0) 

`bt.Index`, `bt.Create` are gated (`paginatedRequest`, `auth.RequiresEditRole`), and `Update`/`Destroy` require `auth.RequiresEditRole`, but `bt.Show` has no role check at all — only the outer `authv2` group's session/token authentication applies: [2](#0-1) 

`BridgeTypesController.Show` loads the bridge and serializes it directly: [3](#0-2) 

`presenters.NewBridgeResource` copies `OutgoingToken` from the stored `bridges.BridgeType` into the JSON response with no `omitempty` and no masking, and also copies the raw `URL`: [4](#0-3) 

`IncomingToken` is only populated by the `Create` handler from the one-time plaintext returned at creation (`bta.IncomingToken`), and is not re-populated from the persisted `BridgeType` on `Show`/`Update`/`Destroy` (the stored value is a hash), so `IncomingToken` is not leaked here. However `OutgoingToken` is stored and reused as-is and is returned on every `Show`/`Update`/`Destroy`/`Create` response. Since `Show` has no role restriction, a view-role user (who should only be permitted to read non-sensitive info) can retrieve this token, and if the bridge URL was configured with embedded basic-auth credentials (`https://user:pass@host/...`), those are exposed too.

### Impact Explanation
Disclosure of `OutgoingToken` allows a low-privileged (view-role) authenticated caller to obtain a secret used by the node to authenticate itself to the external adapter for that bridge. Depending on how the adapter validates this token, this can enable request forgery/impersonation of the node toward the adapter, or reuse/replay of the secret outside the node's control — a credential/secret disclosure that exceeds the intended privilege boundary between view-role and edit-role users. This matches the "sensitive information disclosure via authenticated node API without adequate role enforcement" bounty class.

### Likelihood Explanation
Preconditions: attacker only needs a valid but low-privileged (view-role) session or API token — no edit/admin role, no operator/host access. The route is reachable directly (`GET /v2/bridge_types/:BridgeName`) with the bridge name known or guessable (bridge names are often visible via job specs or the paginated `Index` endpoint which is also unauthenticated-for-role). This is trivially and repeatably exploitable by any authenticated low-privilege user.

### Recommendation
Wrap `bt.Show` (and consider `Index`, since it also has no role check) with an appropriate role check consistent with the sensitivity of the returned fields, e.g. `auth.RequiresEditRole(bt.Show)`, or redact `OutgoingToken`/credentialed `URL` from the `BridgeResource` for callers without edit role, mirroring how `IncomingToken` is already excluded from persisted-state responses.

### Proof of Concept
Go handler-level test plan:
1. In `core/web/bridge_types_controller_test.go`, create a bridge via `app.BridgeORM().CreateBridgeType` with `URL` containing embedded credentials (e.g. `https://user:pass@testing.com/bridges`) and a known `OutgoingToken`.
2. Create an HTTP client authenticated as a view-role user/token (`app.NewHTTPClient` with view-only session, as used elsewhere in the test suite for role checks, e.g. patterns in `auth_test.go`).
3. Call `client.Get("/v2/bridge_types/" + bt.Name.String())`.
4. Assert `resp.StatusCode == http.StatusOK` (i.e., not `403 Forbidden`), proving no role check is enforced.
5. Parse response into `presenters.BridgeResource` and assert `resource.OutgoingToken == bt.OutgoingToken` and `resource.URL` contains the embedded credentials — proving secret/credential disclosure to a view-role caller.
6. Expected fix behavior: after adding `auth.RequiresEditRole` (or redaction), the same request from a view-role user should return `403` or the response should have `OutgoingToken` empty/redacted.

```go
// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
```
