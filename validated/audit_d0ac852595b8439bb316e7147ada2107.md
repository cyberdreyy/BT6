### Title
`UseGlobalContractAction` is not restricted to `predecessor_id == receiver_id`, allowing an attacker to force a victim account to adopt attacker-chosen contract code - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`use_global_contract` (`runtime/runtime/src/global_contracts.rs:75-108`) rewrites the receiver account's `AccountContract` (via `account.set_contract(...)`) purely based on the receipt's `account_id`/`account`, with no check that the action's `predecessor_id` matches the `receiver_id`. Per the protocol's documented actor-permission model, only `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, and `DeleteAccount` are required to have `predecessor_id == receiver_id`; `UseGlobalContract` (and `DeployGlobalContract`) are conspicuously absent from that list.

### Finding Description
`docs/RuntimeSpec/Actions.md:26-35` states explicitly: "For the following actions, `predecessor_id` and `receiver_id` are required to be equal: `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`." `UseGlobalContract` is not in that list. Neither `validate_use_global_contract_action` in `runtime/runtime/src/action_validation.rs:253-259` (which only validates the identifier format via `validate_global_contract_identifier`) nor `use_global_contract`/`action_use_global_contract` in `runtime/runtime/src/global_contracts.rs:64-108` perform any predecessor/receiver identity check. The function simply looks up the global contract, clears prior contract storage usage, and calls `account.set_contract(contract)` on whatever account the receipt targets.

Because the actor-permission gate for "account management" actions is keyed on action type and `UseGlobalContract` is excluded, an attacker account `A` can craft a receipt whose `receiver_id` is a victim account `V` and whose action list contains `UseGlobalContract`, either:
1. Directly in a signed transaction (`signer_id = A`, `receiver_id = V`, actions = `[UseGlobalContract]`), or
2. Via `promise_batch_action_use_global_contract_by_account_id` (`logic.rs:2776-2809`) inside a `FunctionCall` from `A`'s own contract, creating a new promise batch with `receiver_id = V`.

In both cases the resulting receipt has `predecessor_id = A`, `receiver_id = V`, `A != V`. Since the enforced equality list omits `UseGlobalContract`, this receipt is not rejected by action validation, and `use_global_contract` executes, rewriting `V`'s `AccountContract` to `AccountContract::GlobalByAccount(A)` or `AccountContract::Global(code_hash)` without any signature, access key, or consent from `V`.

### Impact Explanation
This breaks authorization exactness between accounts: an unprivileged attacker can force an arbitrary, unrelated, funded account `V` to run attacker-chosen (or attacker-controlled, if `GlobalContractIdentifier::AccountId`) contract code on `V`'s next `FunctionCall`. Since `AccountContract::GlobalByAccount(A)` dynamically resolves to whatever code `A` deploys under its own account, `A` gains ongoing, mutable control over the logic that will execute against `V`'s balance and storage — a direct path to theft/loss of funds ("Contracts execution flows" / "Stealing or loss of funds" bounty category).

### Likelihood Explanation
The attacker only needs a funded account and the ability to submit ordinary signed transactions (or deploy a trivial wasm contract that issues one host-function call). No validator, node-operator, or privileged access is required, and the exploit is fully repeatable against any account whose identifier is known (all account ids are public on-chain).

### Recommendation
Add `UseGlobalContract` (and audit `DeployGlobalContract`) to the set of actions requiring `predecessor_id == receiver_id` in the action-permission enforcement path (the same gate documented for `DeployContract`/`AddKey`/etc.), so that only an account's own transaction (or an action list where `CreateAccount` establishes permission, per the existing carve-out) can change that account's active contract binding.

### Proof of Concept
Integration/test-loop test:
1. Create two funded accounts `attacker.test.near` and `victim.test.near`, with `victim` never interacting with `attacker`.
2. Deploy a global contract under `attacker.test.near`'s own account id (`DeployGlobalContract` with `AccountId` mode).
3. Submit a transaction signed by `attacker.test.near` with `receiver_id = victim.test.near`, single action `UseGlobalContract { contract_identifier: AccountId(attacker.test.near) }` (or reproduce via a `FunctionCall` on an attacker contract that calls `promise_batch_action_use_global_contract_by_account_id` targeting `victim.test.near`).
4. Assert that the transaction execution outcome is `Success` (or, if the finding is invalid, assert it is rejected with an actor/permission error). 
5. Query `victim.test.near`'s account state and assert whether `AccountContract` was changed to `GlobalByAccount(attacker.test.near)` — if so, this confirms the account-hijack.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}
