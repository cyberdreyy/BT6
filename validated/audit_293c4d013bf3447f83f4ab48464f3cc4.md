### Title
Missing validation allows fulfiller to seize escrowed tranche tokens for zero underlying in write-off escrow - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` accepts any `underlyingsRequested` value, including `0` (or a dust amount far below the tranche tokens' fair value). Because `fullfillWriteOffRequest` only enforces `_underlyings >= currentRequest.underlyings`, any arbitrary fulfiller can satisfy such a request by transferring 0 underlying and receiving the lender's entire escrowed tranche balance. This is the direct analog of the reported "insufficient input validation" bug class: user-supplied parameters are stored and later consumed without a sanity lower bound, enabling theft.

### Finding Description
In `createWriteOffRequest` the only validations are epoch-running and `amount != 0`:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:86-101
function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
  if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
  if (amount == 0) revert NotAllowed();
  IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
  userRequests[msg.sender] = WriteOffRequest({
    tranches: currentRequest.tranches + amount,
    underlyings: currentRequest.underlyings + underlyingsRequested
  });
  pendingUnderlyings += underlyingsRequested;
}
```

There is no check on `underlyingsRequested`. In `fullfillWriteOffRequest` the matching check is:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:129
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
```

With `underlyings == 0` stored, `_underlyings < 0` is impossible, so any caller passes the check, pays nothing, and receives `currentRequest.tranches` at line 151. Additionally, `createWriteOffRequest` overwrites/accumulates requests without requiring a price quote signed at call time, so a lender who mistypes the parameter (e.g., forgets decimals, transposes `amount`/`underlyingsRequested`) permanently exposes the escrowed tranches to a free grab. MEV bots can monitor the mempool and fulfill the malformed request in the same block — `fullfillWriteOffRequest` is explicitly callable "by any wallet" (line 122).

A second related gap: nothing caps `underlyingsRequested` relative to the tranche tokens' virtual price, so a wildly *overpriced* request simply locks the tranches (lender loss via permanent freezing, only recoverable via `deleteWriteOffRequest`), while an underpriced one is instantly stolen. The underpriced case is the theft vector.

### Impact Explanation
Direct theft: the fulfiller receives the victim's escrowed AA or BB tranche tokens while transferring `0` (or dust) underlying. The tokens are real claims on the credit vault (`tranche` is the live `AATranche`/`BBTranche` of `idleCDOEpoch`), redeemable via `requestWithdraw`/`claimWithdrawRequest`. Loss = full escrowed tranche balance of the victim; the check `currentRequest.tranches == _tranches` even forces the fulfiller to take the *entire* position, maximizing extraction.

### Likelihood Explanation
The attack requires a lender to submit a malformed request — plausible given `underlyingsRequested` is a raw integer denominated in underlying decimals while `amount` is in 1e18 tranche units, an easy mistake. Once created, exploitation is permissionless and atomic; any EOA qualifies as fulfiller. No privileged role, no timing dependency beyond the epoch being running at creation. Front-running `createWriteOffRequest` transactions makes the theft effectively guaranteed whenever a bad request hits the mempool.

### Recommendation
- Reject `underlyingsRequested == 0` in `createWriteOffRequest`.
- Optionally enforce a sanity band: `underlyingsRequested <= amount * virtualPrice(tranche) / ONE_TRANCHE` so requests cannot be priced above (or absurdly below, e.g., via a minimum-ratio bound) the current tranche value.
- Allow the fulfiller to partially fill or require exact `_underlyings == currentRequest.underlyings` to prevent dust-satisfaction edge cases.

### Proof of Concept
Foundry fork PoC (requires existing IdleCreditVault deployment with running epoch):

```solidity
function testStealEscrowedTranchesForZero() public {
  // lender is a KYC'd tranche holder, epoch is running
  uint256 trancheAmt = 100e18;
  deal(address(tranche), lender, trancheAmt);

  // victim creates request forgetting the underlying amount
  vm.startPrank(lender);
  tranche.approve(address(escrow), trancheAmt);
  escrow.createWriteOffRequest(trancheAmt, 0);
  vm.stopPrank();

  // attacker: arbitrary fulfiller, no tokens needed
  uint256 balBefore = tranche.balanceOf(attacker);
  vm.prank(attacker);
  escrow.fullfillWriteOffRequest(lender, trancheAmt, 0);

  assertEq(tranche.balanceOf(attacker) - balBefore, trancheAmt);
  assertEq(underlying.balanceOf(lender), 0); // lender received nothing
}
```

Uncertainties: I did not fully trace whether a distinct `underlyingsRequested` upper-bound check exists elsewhere (e.g., an off-chain keeper or the factory validating requests); within `IdleCreditVaultWriteOffEscrow.sol` itself no such check exists, and the fulfiller path is permissionless.
