## Title
V1 SortitionsView duplicate-tenure-start check misses locally-accepted (unsigned-by-quorum) blocks, allowing a signer to sign two conflicting tenure-start blocks - ([File: stacks-signer/src/chainstate/v1.rs])

## Summary
`SortitionsView::validate_tenure_change_payload` in the v1 chainstate module rejects a tenure-start proposal with `DuplicateBlockFound` only if it finds an existing **globally accepted** block in that tenure (`get_last_globally_accepted_block`). The equivalent v2 code path was migrated to `get_last_signed_block`, which also counts `LocallyAccepted` blocks, specifically to close this gap — with an explicit regression test documenting the fix. That fix was never back-ported to v1, leaving v1 signers able to locally-accept (sign) a second, competing tenure-start block for a tenure they already signed a block in, before global consensus is reached.

## Finding Description
`validate_tenure_change_payload` (v1) performs the tenure-start duplicate check as follows: [1](#0-0) 

It queries `get_last_globally_accepted_block`, which by construction only returns blocks in `GloballyAccepted` state, and therefore returns `None` when the signer has merely *locally* accepted (signed with `signed_self`, `BlockState::LocallyAccepted`) a prior tenure-start block for the same tenure but the network has not yet reached the 70% signature threshold.

The v2 equivalent was fixed to close exactly this gap: [2](#0-1) 

using `get_last_signed_block`, which matches on `GloballyAccepted OR LocallyAccepted`: [3](#0-2) 

A dedicated regression test for v2 makes the intent of the fix explicit and confirms the exact scenario that is unguarded in v1: [4](#0-3) 

The documentation for the signer flows independently corroborates the asymmetry between v1 and v2 on this exact check: [5](#0-4) 

Crucially, this `DuplicateBlockFound` check only runs once, at proposal arrival, inside `check_proposal`/`validate_tenure_change_payload` — it is never re-run at validate-ok or at pre-commit time. The re-check that does run repeatedly, `check_block_against_signer_db_state`, only examines the **parent** tenure for a tenure-change block, not its own tenure, so it cannot catch a second tenure-start block for the *same* tenure: [6](#0-5) 

The only remaining backstop is the pre-commit-threshold conflict guard, `get_signed_conflicts`, which looks for any block a signature was placed over (self or group) at or above the proposal's height, across all tenures: [7](#0-6) 

This guard *does* eventually catch same-height conflicts once pre-commit weight reaches 70% (`store_and_process_block_signature`/`handle_block_pre_commit`), but only at that late stage, and only among blocks whose height is `>=` the current proposal's chain length. Between the moment a v1 signer locally accepts the first tenure-start block and the moment the second competing tenure-start block for the same tenure crosses the 70% pre-commit threshold, individual v1 signers can freely validate and pre-commit to (and, if their own pre-commit reaches threshold before the conflict backstop activates as a hard block, sign) the second block, because the only gate designed to reject it at entry (`DuplicateBlockFound`) silently passes due to the `get_last_globally_accepted_block` blind spot.

## Impact Explanation
This breaks the "one signed tenure-start block per tenure" invariant that the `DuplicateBlockFound` gate exists to enforce. A single miner (the tenure's leader, a one-slot actor) can, before the first tenure-start block reaches global acceptance, propose a second tenure-start block for the same tenure with different transactions/coinbase. A v1 signer who already locally-accepted (signed) the first block will not be blocked by `validate_tenure_change_payload` from also validating and pre-committing/signing the second, because the DuplicateBlockFound check sees no globally-accepted block yet. This is a rejection/duplicate-accounting bug that produces a signer signing conflicting blocks at the same height for the same tenure before the sole intended one-shot gate can catch it — matching the "signer signing an invalid/non-canonical/conflicting block" Critical impact class. It also matches the bug-class of the reference report: a security check was migrated to a safe implementation on some code paths (v2) while an identical, still-reachable path (v1) was left on the old, incomplete implementation.

## Likelihood Explanation
Triggering this requires only a single miner (the reward-cycle's currently-selected leader — a one-slot actor) and no signer collusion: propose a tenure-start block, wait for some signers to locally-accept it, then propose a second, different tenure-start block for the same tenure before the first reaches global acceptance. This is entirely within a lone miner's control and requires no majority of signers or leaked keys. The window in which this is exploitable is bounded by how fast the first proposal's pre-commit/signature threshold is reached, but the v1 code path itself contains no time-based mitigation for the specific `DuplicateBlockFound` blind spot — it relies purely on the coincidence that `get_signed_conflicts` runs later, at a different check.

## Recommendation
Back-port the v2 fix to v1: change `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, matching `stacks-signer/src/chainstate/v2.rs`. Add a v1 regression test mirroring `check_tenure_change_rejects_when_locally_accepted_block_exists` in `stacks-signer/src/chainstate/tests/v2.rs` to lock in the fix and prevent future divergence between the v1 and v2 chainstate implementations of this check.

## Proof of Concept
Not directly executable from static review alone, but the exploit scenario is fully reconstructable from existing test infrastructure:
1. Set up a v1 `SortitionsView` test environment (as in `stacks-signer/src/chainstate/tests/v1.rs::setup_test_environment`).
2. Insert a `BlockInfo` for a first tenure-start block in tenure `T`, call `mark_locally_accepted(false)` on it (leaving it `LocallyAccepted`, not `GloballyAccepted`), and `signer_db.insert_block(&existing_block_info)`.
3. Build a second tenure-start block proposal for the same tenure `T` (same `tenure_consensus_hash`/`prev_tenure_consensus_hash`, different transactions), and call `view.check_proposal(...)` on it (v1's `SortitionsView::check_proposal`).
4. Observe that `check_proposal` returns `Ok(())` instead of `Err(RejectReason::DuplicateBlockFound)`, because `validate_tenure_change_payload` (v1) queries `get_last_globally_accepted_block`, which returns `None` for the `LocallyAccepted` first block — the exact scenario the v2 regression test `check_tenure_change_rejects_when_locally_accepted_block_exists` (`stacks-signer/src/chainstate/tests/v2.rs:756-850`) was written to prevent, but which is not covered in v1.

/// Test that a tenure change proposal is rejected when a locally-accepted
/// (but not globally-accepted) block already exists in the same tenure.
///
/// This is a regression test: previously, the check used
/// `get_last_globally_accepted_block`, which would miss blocks in
/// `LocallyAccepted` or `PreCommitted` state and incorrectly allow
/// a duplicate tenure change.
#[test]
fn check_tenure_change_rejects_when_locally_accepted_block_exists() {
    let MockServerClient {
        server,
        client: stacks_client,
        config: _,
    } = MockServerClient::new();
    let rand_int = server.local_addr().unwrap().port();

    let (_stacks_client, mut signer_db, block_sk, mut block, cur_sortition, _, sortitions_view) =
        setup_test_environment(&format!("{}_{rand_int}", function_name!()));

    // Set up the block in the current tenure
    block.header.consensus_hash = cur_sortition.data.consensus_hash.clone();
    let parent_block_header = make_parent_header_meta(&block_sk, &mut block);
    let response = crate::client::tests::build_get_tenure_tip_response(&parent_block_header);

    // Insert a locally-accepted block in the same tenure (same consensus_hash).
    // This simulates a miner's first tenure-start block that the signer has
    // locally accepted but that hasn't yet gathered enough signatures to be
    // globally accepted. In practice this block would contain a tenure-change
    // and coinbase tx, but we omit them here because `get_last_accepted_block`
    // only queries by consensus_hash and block state — the block's transactions
    // are irrelevant to the duplicate check.
    let existing_block_proposal = BlockProposal {
        block: NakamotoBlock::new(
            NakamotoBlockHeader {
                version: 1,
                chain_length: 10,
                burn_spent: 10,
                consensus_hash: cur_sortition.data.consensus_hash.clone(),
                parent_block_id: StacksBlockId([0; 32]),
                tx_merkle_root: Sha512Trunc256Sum([0; 32]),
                state_index_root: TrieHash([0; 32]),
                timestamp: 11,
                miner_signature: MessageSignature::empty(),
                signer_signature: vec![],
                pox_treatment: BitVec::ones(1).unwrap(),
                problematic_txs: vec![],
            },
            vec![],
        ),
        burn_height: 2,
        reward_cycle: 1,
        block_proposal_data: BlockProposalData::empty(),
    };
    let mut existing_block_info = BlockInfo::from(existing_block_proposal);
    existing_block_info.mark_locally_accepted(false).unwrap();
    signer_db.insert_block(&existing_block_info).unwrap();

    // Now build a *second* tenure-start block proposal for the same tenure.
    // This simulates the miner attempting to replace their first block (e.g.,
    // with different transactions). The tenure change tx must have
    // cause=BlockFound with a coinbase to be recognized as a tenure-start block.
    let tenure_change_payload = TenureChangePayload {
        tenure_consensus_hash: cur_sortition.data.consensus_hash.clone(),
        prev_tenure_consensus_hash: cur_sortition.data.parent_tenure_id.clone(),
        burn_view_consensus_hash: cur_sortition.data.consensus_hash.clone(),
        previous_tenure_end: block.header.parent_block_id.clone(),
        previous_tenure_blocks: 1,
        cause: TenureChangeCause::BlockFound,
        pubkey_hash: Hash160::from_node_public_key(&StacksPublicKey::from_private(&block_sk)),
    };
    let tenure_change_tx = make_tenure_change_tx(tenure_change_payload);
    let coinbase_tx = StacksTransaction::new(
        TransactionVersion::Testnet,
        TransactionAuth::Standard(TransactionSpendingCondition::new_initial_sighash()),
        TransactionPayload::Coinbase(CoinbasePayload([0; 32]), None, Some(VRFProof::empty())),
    );
    *block.executed_and_skipped_txs_mut() = vec![tenure_change_tx, coinbase_tx];
    block.header.sign_miner(&block_sk).unwrap();

    let exit_flag = Arc::new(AtomicBool::new(false));
    let moved_exit_flag = exit_flag.clone();

    let serve = std::thread::spawn(move || {
        crate::client::tests::write_response_nonblockinig(
            &server,
            response.as_bytes(),
            moved_exit_flag,
        );
    });

    let result = sortitions_view.check_proposal(&stacks_client, &mut signer_db, &block);

    exit_flag.store(true, Ordering::SeqCst);
    serve.join().unwrap();

    // The proposal should be rejected because there's already a locally-accepted
    // block in this tenure. Before the fix, this would have incorrectly passed
    // because get_last_globally_accepted_block would not find the locally-accepted block.
    assert!(
        matches!(result, Err(RejectReason::DuplicateBlockFound)),
        "Expected DuplicateBlockFound rejection when a locally-accepted block exists in the tenure, got: {result:?}"
    );
}

`check_latest_block_in_tenure` answers "does this block confirm the tip we
expect?" and it runs in three places: at proposal arrival (inside

it is asked about depends on the block: a tenure-change block is checked against
its **parent** tenure, every other block against its **own**. Never both. The
pivotal helper is `get_tenure_last_block_info`, which considers only blocks that
carry a signature (`get_last_signed_block`): a pre-commit never vetoes anything,
it only counts as miner activity.
