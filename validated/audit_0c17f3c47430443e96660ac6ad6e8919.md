### Title
Inflated ERC4626 share price in ProgrammableBorrower vault mints unbacked epoch interest, letting early withdrawers steal principal - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The SSRF report is a "trusted fetch of an unvalidated external resource" bug: the endpoint fetches attacker-influenced remote content and stores it as authoritative data. The idle-tranches analog is `ProgrammableBorrower.totalInterestDueNow()`, which treats the external ERC4626 vault's `convertToAssets` valuation as the authoritative source of epoch interest at `stopEpoch`, with no sanity cap. A tranche holder who is also a user of that ERC4626 vault can inflate the share price (direct asset donation into the vault), causing phantom vault PnL to be minted as real tranche interest in minted-interest mode, then exit at the inflated price while later LPs absorb the shortfall.

### Finding Description
`IdleCDOEpochVariant._stopEpoch` resolves interest in programmable mode via `_resolveStopEpochInterest` → `IProgrammableBorrower(_borrower()).totalInterestDueNow()` [1](#0-0) . That value comes from `_vaultNetInterest()`, which computes `earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault` against the epoch-start baseline [2](#0-1) . `_currentVaultAssets()` is the live `convertToAssets` valuation of the external vault — fully manipulable by anyone who can transfer underlying into the vault contract or hold vault shares.

Two guards that would normally bound this do not apply:
- The `maxApr` cap on overridden interest only fires when `_interest > 1`; in programmable mode `_interest` is `0` or `1` before resolution, so `totalInterestDueNow()` is returned uncapped [3](#0-2) .
- `_skimDonatedAssets()` only sweeps raw underlyings sitting on the CDO contract itself; it cannot see donations made inside the external vault that surface only through the share price [4](#0-3) .

Programmable borrowers force `isInterestMinted = true` [5](#0-4) , so the inflated `expectedEpochInterest` is crystallized into tranche NAV via `mintStrategyTokens` / `_updateAccounting` without any corresponding cash pull (`_amountToPullFromBorrower = 0`) [6](#0-5) . Tranche prices rise, but vault backing does not.

Attack sequence (buffer phase deposit → running epoch):
1. Attacker (KYC'd) deposits into the BB tranche during buffer; honest `startEpoch` runs, funds parked in the external ERC4626 vault.
2. Mid-epoch, the attacker donates `D` underlying directly into the ERC4626 vault (they may also hold vault shares themselves, recovering a pro-rata share of `D`).
3. Honest manager calls `stopEpoch(0,0)` after `epochEndDate`. `_vaultNetInterest` reports `D` as epoch interest; minted accounting raises `lastNAV`/`tranchePrice` by `D` with zero cash pulled.
4. Attacker calls `requestWithdraw`/`claimWithdrawRequest` (or sells) at the inflated price. Real vault assets never increased for the pool proportionally, so remaining LPs' claims are undercollateralized — a BB-first loss is effectively manufactured against honest holders.

Broken invariant: fair mint/burn — NAV grows without backing, so "one receipt one payout" fails for later claimants.

### Impact Explanation
Direct theft of LP principal. The attacker's profit is bounded by `D × (attackerTrancheShare)` while their cost is `D × (1 − attackerVaultShare)`. By pre-positioning as a large vault shareholder, cost approaches zero while the NAV inflation is fully extracted through tranche redemption. Quantified loss: up to `D` of honest LP NAV, crystallized as a BB-first loss when claims exceed real backing.

### Likelihood Explanation
Requires (a) a programmable-borrower deployment, (b) attacker passes Keyring KYC to hold tranche tokens, and (c) an ERC4626 vault whose `totalAssets` is manipulable by donation — true for standard ERC4626 implementations. No privileged role is needed; sequencing rides on the honest manager's routine `stopEpoch` call.

### Recommendation
Cap resolved programmable interest: in `_stopEpoch`, enforce the existing `maxApr` ceiling whenever `isProgrammableBorrower` and `_mintInterest`, not only when `_interest > 1`. Additionally, value the vault sleeve using a manipulation-resistant measure (e.g., clamp `totalInterestDueNow` to `borrowerInterestAccruedNow() + bufferInterest` plus realized withdrawals only), or treat vault contributions as in-kind share transfers rather than minting NAV against an unvalidated `convertToAssets` reading.

### Proof of Concept
Foundry fork sketch (concrete contracts depend on deployment fixtures; see `test/` for programmable-borrower setup):
```solidity
// setup: programmable CDO, attacker KYC'd, deposit BB tranche in buffer
cdo.depositAAorBB(BB, 100e6);           // attacker
cdo.depositAAorBB(BB, 900e6);           // honest LP
vm.prank(manager); cdo.startEpoch();

// inflate vault share price via donation
uint256 D = 50e6;
underlying.transfer(address(externalVault), D);

vm.warp(epochEndDate + 1);
vm.prank(manager); cdo.stopEpoch(0, 0); // mints D as interest, pulls ~0 cash

uint256 before = underlying.balanceOf(attacker);
cdo.requestWithdraw(0, BB);             // priced on inflated NAV
// claim next epoch; assert attackerOut > attackerPrincipal while honest NAV impaired
assertGt(underlying.balanceOf(attacker) - before + attackerOut, 100e6 + shareOf(D));
```

  function _vaultNetInterest() internal view returns (uint256 interest, uint256 loss) {
    if (!epochAccountingActive) return (0, 0);
    uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
    uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
    int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
    if (netDelta > 0) {
      interest = uint256(netDelta);
    } else {
