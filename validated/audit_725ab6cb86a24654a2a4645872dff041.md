This confirms the analysis is complete. `lending_pool_configure_bank` requires `has_one = admin @ MarginfiError::Unauthorized` with `admin: Signer<'info>`, so an unprivileged caller cannot zero `asset_weight_init` via this or any other bank-config path. `start_liquidation` is explicitly marked `(Permissionless)`, but it only sets `ACCOUNT_IN_RECEIVERSHIP` to `true` via `start_receivership`/`marginfi_account.set_flag(ACCOUNT_IN_RECEIVERSHIP, false)` (note: this call sets the flag to `true`, the boolean param controls a different toggle) after verifying `check_pre_liquidation_condition_and_get_account_health` — i.e., the account must actually be unhealthy first. There is no instruction that lets the account authority unilaterally clear this flag except `end_liquidation`, which is validated via transaction instruction introspection (`validate_ix_last`) to be the final instruction of the same atomic liquidation transaction.

Both values checked by the `KaminoWithdraw` bank constraint — `marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP)` and `bank.load()?.config.asset_weight_init` — are read from the same deserialized account states within the single Anchor instruction's constraint evaluation, which happens atomically as part of that one instruction's execution inside one Solana transaction. Solana transactions execute their instructions strictly sequentially and atomically; there is no interleaving of a separate admin's `configure_bank` transaction "mid-instruction" with the withdraw's constraint check. Any such races would require the admin tx and the withdraw tx to be ordered, and ordering is deterministic per the leader's sequencing — the withdraw either sees the pre- or post-update bank state, and in both cases the constraint is evaluated consistently against the actual current on-chain data at the time that instruction runs, not something the unprivileged withdrawer can spoof. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

The premise that an attacker could "forge" `ACCOUNT_IN_RECEIVERSHIP=false` doesn't apply either: when the flag is genuinely `false` (account not under liquidation), the constraint `!(false && weight==0)` is trivially satisfied by design — that's the normal, non-liquidation withdrawal path, which is intentionally unrestricted regardless of asset weight. The restriction exists specifically to stop a liquidator/receiver from extracting zero-weight collateral disproportionately during an active receivership, and that flag can only be set by `start_liquidation`/`start_deleverage` after real health checks, cleared only by the matching `end_liquidation`/`end_deleverage` at the end of the same atomic liquidation transaction. There's no permissionless path to zero `asset_weight_init`, and no reachable mechanism for an unprivileged authority to race or spoof the flag/config pairing across transaction boundaries.
