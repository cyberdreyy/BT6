## Finding: v1 signer accepts a second conflicting tenure-start proposal because `validate_tenure_change_payload` checks only *globally* accepted state, unlike v2 — ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` in the v1 chainstate module uses `SignerDb::get_last_globally_accepted_block` to detect a duplicate tenure-start proposal in the current tenure, while the v2 (`GlobalStateView`) equivalent was patched to use `SignerDb::get_last_signed_block` (locally *or* globally accepted). This is a confirmed, documented v1/v2 asymmetry — v2 carries a regression test for exactly this gap, v1 does not.

### Finding Description
In `stacks-signer/src/chainstate/v1.rs`, `validate_tenure_change_payload` runs the duplicate-block check as: [1](#0-0) 
which only fires once this signer's local record for the tenure reaches `BlockState::GloballyAccepted`.

The v2 path, `GlobalStateView::validate_tenure_change_payload`, was fixed to use the broader `get_last_signed_block` (matches `LocallyAccepted`, `PreCommitted`, or `GloballyAccepted` states carrying a signature): [2](#0-1) 

The v2 fix has a dedicated regression test explaining the exact prior bug: [3](#0-2) 

v1 has no equivalent test, and `get_recent_commits`/`grep_search` show v1.rs still contains the single, un-patched `get_last_globally_accepted_block` call with no counterpart regression test in `stacks-signer/src/chainstate/tests/v1.rs`.

This matters because `check_proposal`'s `DuplicateBlockFound` guard is the *only* place this specific duplicate-tenure-start check runs — it is never re-run at validate-ok or at signing time, as documented: [4](#0-3) 

The remaining backstop is the pre-commit-time "own-tenure conflict" guard in `handle_block_pre_commit`, but that guard is explicitly designed to let a stale conflict be superseded once the node hasn't yet confirmed the tenure at that height: [5](#0-4) 

So the full chain is:
1. A single miner proposes tenure-start block A for tenure T. This v1 signer locally signs it (`mark_locally_accepted` → `signed_self` set, state = `LocallyAccepted`), but A never gathers the full 70% weight needed to become `GloballyAccepted` (plausible any time other signers are slow/offline, or the miner simply stops advertising A to the rest of the set).
2. The same miner proposes a second, conflicting tenure-start block B for the same tenure T (different transactions/timestamp ⇒ different hash). `check_proposal`'s `validate_tenure_change_payload` calls `get_last_globally_accepted_block(&T)`, which returns `None` because A is only `LocallyAccepted`, so `DuplicateBlockFound` is never raised and B's proposal passes.
3. B goes through validation; `check_block_against_signer_db_state` for tenure-change blocks only re-checks the **parent** tenure, not T itself, so it does not catch the sibling either (documented in `docs/signer-flows.md:391-448`).
4. Once A's signature goes stale (past `tenure_last_block_proposal_timeout`) and the node's canonical tip for T has not advanced to/past B's height (true whenever A never reached the network-wide 70% threshold and was never pushed to the node), the pre-commit-time own-tenure guard in `signer.rs:1432-1457` no longer blocks B, and the signer proceeds to sign B.

The result: this single v1 signer ends up producing signatures over two conflicting tenure-start blocks (A and B) at the same height/tenure — a double-sign/equivocation, entirely orchestrated by one miner (plus normal gossip timing), with no need for a majority of signers, another signer's key, or node compromise.

### Impact Explanation
This breaks the core "no conflicting signature" invariant for a single signer: it directly matches the Critical impact class "a signer signing an invalid, non-canonical, or conflicting block." If exploited against enough signers concurrently, this facilitates a chain-reorg/equivocation the signer set is specifically designed to prevent.

### Likelihood Explanation
Likelihood is bounded by protocol version and timing: it requires the reward-cycle signer set to be running the v1 protocol (`SortitionsView`, not the v2 `GlobalStateView`), and requires block A to sit in `LocallyAccepted` long enough to go stale without ever reaching global 70% acceptance or being pushed to the node — a timing condition fully controllable by the proposing miner (e.g., by only sharing A with a minority of signers before abandoning it for B). No majority-signer collusion, secret key material, or auth token is required.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to use `SignerDb::get_last_signed_block` instead of `get_last_globally_accepted_block`, mirroring the v2 fix, so that a proposal conflicting with any block this signer has already signed (locally or globally accepted) in the same tenure is rejected with `DuplicateBlockFound` at proposal time, rather than relying on the staleness-sensitive pre-commit backstop.

### Proof of Concept
1. Configure a signer running the v1 protocol version.
2. Miner proposes tenure-start block A for tenure T; the signer signs it locally (`signed_self` set, `LocallyAccepted`), but withhold further propagation so A never reaches `GloballyAccepted`.
3. Wait past `tenure_last_block_proposal_timeout` so A's signature is no longer "fresh."
4. Miner proposes tenure-start block B for the same tenure T (different timestamp ⇒ different hash), with the node's canonical tip for T still behind B's height (A never pushed to the node).
5. Observe that `check_proposal` (v1) does not reject B with `DuplicateBlockFound` (since `get_last_globally_accepted_block` returns `None`), and that once B reaches the pre-commit threshold, `handle_block_pre_commit`'s own-tenure staleness branch allows the signer to sign B, producing two conflicting signatures (over A and B) from the same signer for the same tenure/height.

```rust
fn check_tenure_change_rejects_when_locally_accepted_block_exists() {

    );
```

```markdown
Two things belong to the proposal path only and are **not** re-run at validate-ok
or at signing:

- `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we
  have already accepted a block in the tenure a tenure-change block is starting.
  v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1
  counts only globally accepted ones (`get_last_globally_accepted_block`).
- the v2 `check_proposal` wrapper checks miner pubkey hash, consensus hash, the
  pox bitvec, and tenure-extend rules before delegating here.

Because the duplicate check never runs again, a block that crosses the pre-commit
threshold long after it was proposed relies on section 5's own-tenure conflict
guard to cover the same ground.
```
