### Title
Removed multisig member's stale confirmation still counts toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` removes a member from `self.members` and cleans up only the requests that member itself created (filtered by `r.member == member`), but does not remove that member's entries from the `confirmations` set of *other* pending requests it had merely confirmed. As a result, a confirmation recorded by an account that is no longer a member of the multisig can still be counted when a later `confirm()` call checks `confirmations.len() as u32 + 1 >= self.num_confirmations`, letting a request execute with fewer *live* signers than `num_confirmations` requires.

### Finding Description
In `MultiSigContract::confirm` (multisig2/src/lib.rs:294-315), the threshold check only inspects the size of the `HashSet<String>` of confirmer identifiers stored for a `request_id`; it never re-validates that every entry in that set corresponds to a member still present in `self.members`.

`delete_member` (multisig2/src/lib.rs:356-379) is the only code path that mutates `self.members`, and its clean-up logic is scoped incorrectly:
```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
This only deletes requests *created* by the removed member (`MultiSigRequestWithSigner.member`). It does not iterate `self.confirmations` to strip the removed member's key/account identifier from confirmation sets belonging to requests created by *other* members. So a pending, not-yet-fully-confirmed request that the soon-to-be-removed member had confirmed retains that confirmation permanently, even after the member is deleted.

This breaks the intended equality: `confirmations recorded == confirmations from currently live members`. After deletion, `confirmations recorded > confirmations from currently live members` for any request the removed member had confirmed but not created.

### Impact Explanation
If `num_confirmations = k` and a pending request already has one confirmation from a member who is subsequently removed, only `k-1` *additional live* confirmations are needed from the remaining members to reach the threshold and trigger `execute_request`. This effectively lowers the real signing threshold below the configured `num_confirmations` for that request, letting the multisig execute a Transfer, AddKey, FunctionCall, etc. with fewer authorized/live signers than intended — an authorization boundary crossing (K-of-N threshold bypass), which falls under the "confirmations counted versus live members" custody binding and the Critical impact category ("a multisig request executed below threshold").

### Likelihood Explanation
Requires no privileged access beyond being (at some point) a legitimate multisig member who confirms a request and is later removed (e.g., through normal key rotation, a compromised-key removal, or an owner leaving the organization) — a realistic and expected multisig lifecycle event, not a contrived edge case. Any pending request that member had confirmed prior to removal remains exploitable indefinitely (there is no expiry other than `delete_request`, which requires an explicit call and REQUEST_COOLDOWN).

### Recommendation
When removing a member in `delete_member`, iterate all pending `requests`/`confirmations` entries and remove the deleted member's identifier from every confirmation set (not just requests it created), or alternatively re-validate at `confirm()` time that all recorded confirmer identifiers are still present in `self.members`, discarding stale ones before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig initialized with members `[A, B, C]`, `num_confirmations = 2`.
2. `B` calls `add_request` (as creator) for a `Transfer` request `R` (receiver arbitrary).
3. `C` calls `confirm(R)` — confirmations set for `R` = `{C}`, size 1 < 2, request stays pending.
4. Separately, members execute a `DeleteMember{member: C}` request (through the normal `AddMember/DeleteMember` multisig flow) to remove `C` — `delete_member` only checks/removes requests where `r.member == C` (i.e., requests *created* by `C`); since `R` was created by `B`, `R`'s confirmation set is untouched and still contains `C`.
5. `C` is now removed from `self.members`, live members are `[A, B]`.
6. `B` later calls `confirm(R)`: `confirmations.len() (1, still containing removed C) + 1 >= 2` → threshold met → `execute_request(R)` runs, executing the Transfer with only `B`'s live confirmation plus the stale confirmation of removed member `C`, i.e., below the actual live-member threshold of 2.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
