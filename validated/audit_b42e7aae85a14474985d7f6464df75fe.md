### Title
Instant-withdraw receipts from epochs before the default epoch are unrecoverable and permanently frozen after `finalizeDefaultRecovery` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`IdleCreditVault` tracks instant-withdraw receipt basis per request epoch via `instantWithdrawsRequestsByEpoch[user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]`, but default recovery accounting only ever looks at `epochNumber` (the single "current" entry). If an unprivileged user's instant receipt is created in epoch N, only partially funded by `collectInstantWithdrawFunds`, and the borrower then defaults after `epochNumber` has advanced to N+1, the old receipt is neither included in the recovery claim basis nor payable at par, because `_transferFundedClaim` forbids spending the recovery reserve. The user's strategy-token receipt can never be redeemed — a permanent freeze of their funds, mirroring the CVE pattern where a table reduced to a single entry causes out-of-bounds handling of older entries.

### Finding Description

Three pieces interact:

1. `requestInstantWithdraw` records basis under the **current** `epochNumber` only [1](#0-0) . `collectInstantWithdrawFunds` may fund only part of `pendingInstantWithdraws`, leaving a remainder [2](#0-1) .

2. On default, `defaultPendingClaimBasis` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch's bucket — when `pendingInstantWithdraws != 0` [3](#0-2) . Likewise `_defaultPrefundedInstantReserve` only counts the current-epoch instant basis [4](#0-3) . An instant receipt created in epoch `epochNumber - 1` (or earlier) that was left partially unfunded when `deposit()` bumped `epochNumber` [5](#0-4)  is invisible to both the claim basis and the prefunded reserve.

3. After `finalizeDefaultRecovery`, `defaultInstantWithdrawsFinalized` is true (`pendingInstantWithdraws != 0`), so `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest`, which only clears `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — zero for a prior-epoch receipt [6](#0-5) . Execution then falls through to `_transferFundedClaim(_user, amount)`, which reverts whenever the remaining balance cannot cover the claim **on top of** `defaultRecoveryReserve` [7](#0-6) . Since finalization sweeps all strategy-held underlying into `defaultRecoveryReserve` [8](#0-7) , the claim always reverts.

### Impact Explanation

An unprivileged holder of an instant-withdraw receipt created one or more epochs before the default epoch permanently loses the entire receipt amount: the claim path reverts forever (the reserve guard has no exception), the receipt is excluded from the recovery basis so it gets no `defaultRecoveryPrice`-haircut payout either, and `transferToken` is owner-only rescue. Worse, the underlying backing those receipts still sits in the strategy and was counted into `reserveAmount` via the normal balance, so other claimants recover at an inflated `recoveryPrice` — the frozen user's funds are effectively redistributed to other claimants. Quantified loss: up to the full unfunded `instantWithdrawsRequests[user]` amount for every affected user.

### Likelihood Explanation

Requires: (a) an instant-withdraw request (`requestInstantWithdraw` via the CDO's APR-drop instant path) that the CDO only partially funded through `collectInstantWithdrawFunds` — i.e. `pendingInstantWithdraws` leftover; (b) `epochNumber` advancing (any subsequent `deposit()` while `isEpochRunning()`); (c) borrower default + `finalizeDefaultRecovery`. Partial instant funding is a designed-for state (the codebase explicitly handles "the already-funded part" of instant claims), and defaulting after an epoch rollover is a normal lifecycle, so the sequence is reachable without privileged collusion. The trigger is not attacker-steering — the loss falls on whichever unprivileged user's receipt straddled the epoch boundary, and the attacker framing is a borrower-default aftermath the rules allow since the borrower is not the attacker.

### Recommendation

Index instant recovery accounting by all request epochs with outstanding basis, not only `epochNumber`: maintain a global unfunded/pending instant basis (or iterate stored epochs) inside `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, and have `_claimDefaultedInstantWithdrawRequest` clear *every* epoch entry for the user (e.g., aggregate `instantWithdrawsRequestsByEpoch` across epochs or track per-user epochs). Alternatively, forbid advancing `epochNumber`/`stopEpoch` while `pendingInstantWithdraws != 0` and older-epoch instant claims remain unfunded, or add a sweep that folds leftover prior-epoch instant basis into the current epoch bucket when an epoch rolls over.

### Proof of Concept

Foundry fork PoC sketch (against the existing `IdleCreditVault.t.sol` harness):

```solidity
// 1. Setup: user deposits AA, epoch 0 runs with APR drop so instant path is enabled.
idleCDO.depositAA(amount);
cdoEpoch.requestInstantWithdraw(reqAmount /* via requestWithdraw APR-drop path */, AA);
// strategy: instantWithdrawsRequestsByEpoch[user][0] = reqAmount, pendingInstantWithdraws = reqAmount

// 2. Honest manager partially collects instant funds, leaving remainder.
uint256 fundedPart = reqAmount / 2;
deal(underlying, address(cdoEpoch), fundedPart);
vm.prank(manager); // or CDO internal path
strategy.collectInstantWithdrawFunds(fundedPart); // pendingInstantWithdraws = reqAmount - fundedPart

// 3. Epoch rolls over: stopEpoch + deposit during running epoch bumps epochNumber to 1.
//    (instantWithdrawClaimsByEpoch[0] still holds reqAmount; [1] == 0)

// 4. Borrower defaults; owner finalizes recovery.
//    defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[1]
//    => user's epoch-0 instant receipt contributes ZERO basis.
cdoEpoch.finalizeDefaultRecovery(recovered, recoverySource);

// 5. User claims: _claimDefaultedInstantWithdrawRequest clears epoch[1] basis (0),
//    then _transferFundedClaim(user, reqAmount) reverts because
//    balance == defaultRecoveryReserve.
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimInstantWithdrawRequest();
// pendingInstantWithdraws and the receipt tokens stay locked forever.
```

Assert `strategy.instantWithdrawsRequests(user) == reqAmount` after the revert and that `defaultRecoveryReserve` was inflated by the user's unfunded share (it was pulled into the reserve even though no basis was assigned).

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
