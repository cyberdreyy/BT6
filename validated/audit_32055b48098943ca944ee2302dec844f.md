### Title
Unauthenticated `/v2/resume/:runID` endpoint allows any unprivileged actor to inject task results into another user's pipeline run - (File: core/web/router.go, core/web/pipeline_runs_controller.go)

### Summary
The `PATCH /v2/resume/:runID` route is registered on a completely unauthenticated router group and forwards attacker-controlled JSON directly into `ResumeJobV2`, with no session, API-token, or external-initiator credential check of any kind.

### Finding Description
In `core/web/router.go`, the route is wired as: [1](#0-0) 

`unauthedv2` is a bare router group with no `auth.Authenticate(...)` middleware applied, unlike every other v2 route which requires session/token auth (`authv2`) or external-initiator/token/session auth (`userOrEI`): [2](#0-1) 

The handler itself, `PipelineRunsController.Resume`, does not perform any additional authorization check — it parses `runID` as a UUID, decodes a `pipeline.ResumeRequest` from the raw request body, and calls `prc.App.ResumeJobV2(ctx, taskID, result)` unconditionally: [3](#0-2) 

This is functionally the same bug class as the reported `addLiquidity` finding: a state-mutating function that should only be reachable by an authorized actor (there, the router; here, the external service/bridge that originally suspended the pipeline task) is instead reachable by anyone who can reach the HTTP endpoint. The code even records the anomaly via a dedicated audit event name, `audit.UnauthedRunResumed`, confirming this is a known "unauthed" surface rather than an oversight in labeling.

### Impact Explanation
Any unauthenticated network client that can guess or otherwise obtain a suspended task's `runID` (a UUID identifying a paused pipeline task, e.g. an `ETHCall`/bridge/webhook "async" task awaiting an external callback) can submit arbitrary result data to resume that run on behalf of the intended external caller. This allows:
- Cross-user/cross-caller response confusion: an attacker can complete someone else's pending job run with attacker-chosen data instead of the legitimate external service's response.
- Front-end/consumer impact analogous to the `addLiquidity` report: dashboards, job-run listeners, or downstream on-chain reporting mechanisms driven by the resumed pipeline's output can be manipulated, since the resumed value is not validated as coming from the original external initiator/bridge.
- Depending on which task type raised the suspend (e.g. VRF, external adapter callbacks), the injected result could ultimately feed into transactions or reports the node submits.

The severity depends on how hard `runID` values are to enumerate/guess (they are UUIDs, but they may leak via other logs/APIs, error messages, or be observable if the external adapter reflects them), but the endpoint itself has zero access control by design, matching the report's "unrestricted state-changing entry point" root cause exactly.

### Likelihood Explanation
Likelihood is moderate: exploitation requires knowledge of a specific pending `runID` UUID, which is not trivially enumerable, but the complete absence of authentication (vs. e.g. requiring the external initiator's `OutgoingToken`/`OutgoingSecret` that the node itself generates for callbacks) means there is no defense-in-depth if a `runID` is ever disclosed (logs, error responses, timing, or a compromised/curious external adapter operator who isn't the legitimate resumer).

### Recommendation
Require the resume request to be authenticated using the outgoing token/secret that Chainlink already generates per external initiator/bridge (`OutgoingToken`, `OutgoingSecret` — see `core/bridges/external_initiator.go`), or otherwise bind the resume credential to the specific task/run so that only the entity that received the original callback request can complete it, rather than leaving `/v2/resume/:runID` fully open to any caller with the UUID.

### Proof of Concept
1. Create a job whose pipeline includes an async/bridge task that suspends pending an external callback (yields a `runID`).
2. Without any authentication, send `PATCH /v2/resume/<runID>` with an attacker-chosen JSON body matching `pipeline.ResumeRequest`.
3. Observe that `ResumeJobV2` executes and completes the run with attacker-supplied data, confirmed by the `audit.UnauthedRunResumed` audit event and no `401/403` response, since the route bypasses `auth.Authenticate` entirely: [1](#0-0) [4](#0-3)

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
