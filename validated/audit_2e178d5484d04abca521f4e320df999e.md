## Finding: Stale Confirmations From Removed Multisig Members Are Still Counted Toward Threshold

### Title
Stale Confirmations From Removed Members Counted Toward `num_confirmations` Threshold in `MultiSigContract::confirm` - (File: `multisig2/src/lib.rs`)

### Summary
`multisig2`'s `confirm()` and `delete_member()` never revalidate that the entries already stored in a request's confirmation set still belong to current members. When a member is removed, only requests *they personally created* have their confirmations purged; any confirmation that removed member previously cast on a request created by someone else is left in place and continues to count toward `self.num_confirmations`. This breaks the K‑of‑N multisig invariant: a request can execute using fewer live‑member confirmations than the configured threshold.

### Finding Description
`confirm()` decides whether to execute a request purely by counting entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set against `self.num_confirmations`, without checking whether each entry is still a current member: [1](#0-0) 

`delete_member()` is the only place that scrubs confirmation data on member removal, and it only removes *requests* (and their confirmation sets) where the deleted member was the original requester (`r.member == member`) — it does not scan or scrub confirmations that member cast on requests created by other members: [2](#0-1) 

`assert_valid_request()`, called from both `confirm()` and `delete_request()`, only validates that the *caller* is currently a member; it performs no validation over the already-accumulated confirmation set: [3](#0-2) 

The binding that should hold is: `confirmations counted == confirmations from accounts that are members at execution time`. Because stale entries from removed members are never purged for requests they didn't create, this equality is violated — `confirmations counted > live-member confirmations`.

### Impact Explanation
This is a Critical-severity issue per the "multisig request executed below threshold" category: a `MultiSigRequestAction::Transfer`, `FunctionCall`, `AddKey`, etc. can be executed by the contract having received fewer confirmations from currently-authorized members than `num_confirmations` requires, because one or more of the counted confirmations belongs to an account that has since been removed from the multisig. Since multisig contracts of this kind are used to gate access to NEAR balances and privileged operations (e.g. `add_full_access_key`, `Transfer`), executing a request below the intended live-member threshold is a direct authorization-boundary violation with potential for fund loss.

### Likelihood Explanation
This requires no unauthorized access beyond the normal multisig flow: (1) a member confirms a pending request created by a different member, (2) that confirming member is later removed via the documented `DeleteMember` action (e.g., key rotation, compromise response, or membership change), and (3) the remaining members confirm the request without realizing a stale, now-invalid confirmation is already counted. All of `add_request`, `confirm`, and `AddMember`/`DeleteMember` are documented, ordinary entry points, so the path is fully reachable through intended contract usage without needing to bypass initialization or exploit a redeploy.

### Recommendation
When executing `delete_member`, iterate all active requests' confirmation sets (not just requests created by the removed member) and remove the removed member's entry from each. Alternatively, when counting confirmations in `confirm()`, filter the confirmation set to only entries that are still present in `self.members` before comparing against `self.num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. Member `A` calls `add_request` to create request `R` (e.g. `Transfer` draining funds); `confirmations(R) = {}`.
3. Member `B` calls `confirm(R)`; `confirmations(R) = {B}` (1 < 2, not executed) — see `confirm()` logic at [1](#0-0) .
4. Members confirm and execute a `DeleteMember { member: B }` request (e.g., because `B`'s key was later found compromised). `delete_member` only clears requests where `r.member == B` (i.e., requests *B* created); since `R` was created by `A`, `R`'s confirmation set is untouched — see [4](#0-3) . Members now = `[A, C]`.
5. Member `C` calls `confirm(R)`. `confirmations(R) = {B, C}`, size 2 ≥ `num_confirmations` (2), so `execute_request` runs — even though `B` is no longer a member and only one currently-live member (`C`) actually confirmed. [5](#0-4)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
