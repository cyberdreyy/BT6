### Title
Loss-adjusted withdraw receipts are paid at par when a newer request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` only inspects the single epoch stored in `lastWithdrawRequest[_user]`. If a user has a receipt from an earlier loss-adjusted epoch and then makes a second `requestWithdraw` in a later epoch, `lastWithdrawRequest` is overwritten, the earlier epoch's haircut is never applied, and the stale receipt remains inside `withdrawsRequests[_user]`, where `_claimFundedWithdrawRequest` pays it at full par.

### Finding Description
This mirrors CVE-2018-7868's out-of-bounds read class: the claim path reads only the latest epoch marker and silently "reads past" older recorded claim data instead of iterating `withdrawsRequestsByEpoch`.

- `requestWithdraw` records both aggregate `withdrawsRequests[_user]` and per-epoch `withdrawsRequestsByEpoch[_user][currentEpoch]`, and sets `lastWithdrawRequest[_user] = currentEpoch` (IdleCreditVault.sol:282-293). [1](#0-0) 
- On a partially-funded `stopEpochWithDuration` loss, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` — the deficit is never funded (IdleCreditVault.sol:411-421). [2](#0-1) 
- On claim, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` only. If that latest epoch has no loss price it returns 0 and leaves earlier per-epoch receipts untouched (IdleCreditVault.sol:789-801). [3](#0-2) 
- `_claimFundedWithdrawRequest` then checks `epochNumber <= lastWithdrawRequest[_user]` — which passes since the marker moved to the new epoch — and pays the entire `withdrawsRequests[_user]` aggregate (including the un-haircut old receipt) at par via `_transferFundedClaim` (IdleCreditVault.sol:319-349). [4](#0-3) 

The `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`, not the loss-epoch deficit, so the overpayment is drawn from other claimants'/LP funds.

### Impact Explanation
Broken invariant: one receipt one payout at its epoch-specific recovery price. The attacker recovers `claimBasis_E * (RECOVERY_FULL - lossRecoveryPrice_E) / RECOVERY_FULL` more than funded — a direct theft from the vault's underlying balance, which either drains funds reserved for other users' claims or renders later claims insolvent. Loss magnitude scales with the epoch-E haircut (up to nearly the full receipt when the borrower funds a tiny fraction).

### Likelihood Explanation
Fully unprivileged: the attacker only calls `depositAA/BB` and `requestWithdraw` twice. It requires two consecutive epochs where the first ends via a loss-adjusted `stopEpochWithDuration` (an honest manager/borrower flow, not attacker-controlled malice). Both requests are ordinary user actions; no privileged misbehavior is needed.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, iterate `lossRecoveryPriceByEpoch` for every epoch in which the user has a nonzero `withdrawsRequestsByEpoch` (or track a per-user list/set of pending loss epochs), rather than keying off the single `lastWithdrawRequest` slot. Alternatively, subtract each loss epoch's funded amount from `withdrawsRequests[_user]` inside `collectWithdrawFunds` so unfunded deficits can never leak into the funded-claim path.

### Proof of Concept
Foundry fork PoC (extend `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testLossReceiptPaidAtParAfterNewerRequest() external {
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    uint256 amount = 10_000 * ONE_SCALE;

    // Epoch E: deposit and request withdraw
    uint256 minted = idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);
    cdoEpoch.requestWithdraw(minted / 2, address(AAtranche));

    // Borrower underpays -> loss-adjusted stopEpochWithDuration at epoch E
    uint256 loss = vault.pendingWithdraws() / 2; // 50% receipt haircut
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() - loss);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, loss, 7 days, 0);
    // lossRecoveryPriceByEpoch[E] now set; the deficit was never funded

    // Epoch E+1: attacker requests the rest -> lastWithdrawRequest overwritten to E+1
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0); // clean full-funding stop

    // Claim: loss path reads epoch E+1 (price 0 -> skipped), funded path pays
    // the epoch-E receipt at PAR despite only 50% being funded
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    // paid includes full basis of epoch-E receipt; expected funded amount was only
    // basis * lossRecoveryPriceByEpoch[E] / RECOVERY_FULL
    assertGt(paid, /* funded-only expectation */, 'unfunded haircut stolen at par');
}
```

Key assertions: `lossRecoveryPriceByEpoch[epoch E] != 0`, `withdrawsRequestsByEpoch[user][E]` survives the claim, and `paid` exceeds the sum of funded amounts by `basis_E * (1 - lossRecoveryPrice_E)`.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
