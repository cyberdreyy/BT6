### Title
JWT Replay Guard Check-Then-Act Race Allows Duplicate Workflow Trigger Authorization - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
The `WorkflowMetadataHandler.Authorize` function used by the internet-facing HTTP Trigger Gateway handler checks JWT replay status and records JWT usage in two separate, non-atomic locking operations, with unrelated authorization work performed in between. This is structurally the same bug class as the reported reentrant-withdrawal pattern: a validity check is performed first, "effects" (signer/workflow lookups usable by an attacker to complete an authorized action) happen next, and the state update that should prevent reuse (`recordUsage`) is deferred until the very end — leaving a window where concurrent requests using the identical JWT can both pass the replay check before either is recorded as used.

### Finding Description
`Authorize` in [1](#0-0)  performs:
1. `h.jwtCache.isReplay(claims.ID)` — a read-locked check (`RLock`) at [2](#0-1) .
2. Workflow lookup and signer-authorization checks (non-trivial work, no locking related to the JWT cache).
3. Only at the end, `h.jwtCache.recordUsage(claims.ID)` — a separate write-locked (`Lock`) call at [3](#0-2) .

Because `isReplay` uses `RWMutex.RLock` (which allows multiple concurrent readers) and the check/record are two independent critical sections rather than one atomic check-and-set, two goroutines processing the same JWT concurrently (e.g., from a replayed/duplicated HTTP trigger request hitting the gateway near-simultaneously) can both observe `isReplay == false` before either calls `recordUsage`. Both then pass the "already used" gate and proceed to be treated as authorized, exactly analogous to the report's core root cause: the check occurs before the state-mutating operation that is supposed to make the check meaningful, and an attacker able to trigger overlapping execution windows can bypass the guard multiple times before the state is updated.

Compare this to the "TOCTOU-safe" `RequestReplayGuard.CheckAndRecord` used elsewhere in the same vault-authorizer subsystem, at [4](#0-3) , which correctly performs the check-and-record as a single atomic operation under one `sync.Mutex.Lock()`. The `jwtReplayCache` in the HTTP Trigger handler does not follow this safe pattern.

This is reachable directly from an unprivileged client: `HandleUserTriggerRequest` → `authorizeRequest` → `WorkflowMetadataHandler.Authorize` is invoked for every inbound HTTP trigger JSON-RPC request hitting the gateway, as seen in [5](#0-4) . No privileged access, node key, or gateway operator role is required — any external caller submitting the trigger request (and a JWT they control/replay) can attempt to race two authorization attempts with the same `jti`.

### Impact Explanation
If the race is won, a single JWT (`jti`) intended to authorize exactly one workflow trigger execution can be accepted twice concurrently, resulting in duplicate/unauthorized workflow executions from a single signed authorization. Depending on the downstream capability (e.g., fund-moving or state-mutating workflow actions), this could cause duplicate job runs or duplicate execution of a workflow action that was meant to be single-use, which is the functional equivalent of "unauthorized job run" cited as an acceptable impact class for this analog.

### Likelihood Explanation
Likelihood is **low-to-moderate**. Exploitation requires: (1) an attacker who already controls a valid signed JWT for a legitimate trigger request (i.e., is themselves the workflow signer/owner or has obtained the token), and (2) precise concurrent timing to land both requests inside the narrow window between the `RLock`-protected read and the later `Lock`-protected write. The window includes real lookups (`authorizedKeys` map access, string comparisons) but no I/O, so the race window is narrow but not impossible over a network with retries/duplicated packets or a client deliberately firing parallel requests. This mirrors the original report's own assessment that likelihood is low but the flaw is real and should be fixed via atomic check-and-record.

### Recommendation
Make the JWT replay check and record operation atomic, following the same pattern already used by `RequestReplayGuard.CheckAndRecord`: acquire a single write lock, check `cache[jti]` for existence, and if absent, insert it — all within one critical section — before returning "not a replay." Do not perform the "record" step at the end of a larger set of operations; combine check-and-set into a single method (e.g., `CheckAndRecord(jti) error`) called at the very start of `Authorize`, consistent with the "perform all state updates atomically with checks" principle described in the reference vulnerability report.

### Proof of Concept
Conceptual PoC (structurally mirrors the reentrant-withdraw race):
1. Attacker crafts one valid signed JWT for a workflow trigger request with `jti = X`.
2. Attacker fires two (or more) HTTP trigger requests to the gateway carrying the identical JWT nearly simultaneously (e.g., two goroutines/threads sending to `handleUserTriggerRequest` concurrently, similar to the existing test `TestRequestReplayGuard_ConcurrentAccess` pattern in [6](#0-5)  but targeted at `WorkflowMetadataHandler.Authorize`/`jwtReplayCache` instead of the safe `RequestReplayGuard`).
3. Both goroutines call `isReplay(X)` under `RLock` before either calls `recordUsage(X)` under `Lock`; both see `exists == false`.
4. Both goroutines pass the "already used" check, proceed through signer authorization, and are both treated as authorized — resulting in duplicate accepted trigger executions from a single JWT that was supposed to be single-use.

Note: I was not able to execute this concurrently in a live environment (no test/runtime execution available in this session); the finding is based on static analysis of the locking pattern in `jwtReplayCache.isReplay`/`recordUsage` versus the atomic `RequestReplayGuard.CheckAndRecord` pattern used elsewhere in the same codebase for the same purpose.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func TestRequestReplayGuard_ConcurrentAccess(t *testing.T) {
	guard := NewRequestReplayGuard()
	futureExpiry := time.Now().UTC().Unix() + 100

	const goroutines = 100
	results := make([]error, goroutines)
	var wg sync.WaitGroup
	wg.Add(goroutines)

	for i := range goroutines {
		go func(idx int) {
			defer wg.Done()
			results[idx] = guard.CheckAndRecord("same-digest", futureExpiry)
		}(i)
	}
	wg.Wait()

	successCount := 0
	duplicateCount := 0
	for _, err := range results {
		if err == nil {
			successCount++
		} else {
			require.ErrorIs(t, err, ErrRequestAlreadySeen)
			duplicateCount++
		}
	}

	assert.Equal(t, 1, successCount, "exactly one goroutine should succeed")
	assert.Equal(t, goroutines-1, duplicateCount, "all others should be rejected as duplicates")
}
