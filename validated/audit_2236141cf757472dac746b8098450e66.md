### Title
Stale cached vote/stake account attribution on owner reassignment - (File: runtime/src/stakes.rs)

### Summary
The Dopex report's bug class is a cached "owner"-style attribute that is set at creation time but never updated or evicted when the underlying ownership actually changes, causing stale trust in derived state. The closest reachable analog in this codebase is `StakesCache::check_and_store` in [1](#0-0) , which contains an explicit acknowledged gap: it does not evict a pubkey from the vote/stake cache when that account's `owner` field changes away from the vote/stake program (unless lamports also drop to zero).

### Finding Description
`check_and_store` is invoked for every stored account on every transaction via `Bank::update_stakes_cache` / `Bank::store_accounts`, keyed only by `account.owner()` at call time: [2](#0-1)  and [3](#0-2) . The routing logic checks `solana_vote_program::check_id(owner)` / `stake_program::check_id(owner)` on the *current* account state to decide whether to `upsert_vote_account` / `upsert_stake_delegation`, or to remove the entry — but only removes an entry in the vote/stake branches themselves, or in the separate zero-lamport branch: [4](#0-3) . The code contains the developer's own acknowledgment of this exact defect class:

```
// TODO: If the account is already cached as a vote or stake account
// but the owner changes, then this needs to evict the account from
// the cache. see:
// https://github.com/solana-labs/solana/pull/24200#discussion_r849935444
``` [5](#0-4) 

This mirrors the RdpxDecayingBonds bug class precisely: a struct that caches a "who this belongs to" attribute is written once on creation/insertion, but the removal/refresh path is not triggered on every state transition that changes true ownership — only on the transitions the code's authors anticipated (owner staying vote/stake program, or lamports hitting zero).

### Impact Explanation
`StakesCache` is not a peripheral read cache — `Stakes<StakeAccount>` backs consensus-relevant queries such as vote-account sets, delegated stake totals, and leader/stake-weighted computations used across the bank (rewards distribution reads `stakes_cache.stakes().stake_delegations()` directly, e.g. [6](#0-5) ). If a pubkey remains attributed to the stake or vote program in this cache after its true `owner()` field has changed to something else, RPC/consensus-facing views derived from `Stakes` (e.g., delegated stake, active vote accounts) can diverge from the authoritative accounts-db state returned to `getVoteAccounts`/`getProgramAccounts`-style queries, which is a wrong-state-returned condition per the accepted impact classes.

### Likelihood Explanation
This is explicitly a known, currently-unmitigated gap (per the inline TODO referencing an already-tracked upstream discussion from solana-labs/solana#24200), not a newly discovered path. However, exploitability by an ordinary unprivileged transaction is constrained by protocol invariants: reassigning an account's owner away from a program that has already initialized non-zero-lamport, non-zeroed data generally requires the `system_program::assign` path, which itself requires the account data to be zeroed first (`assign()` in [7](#0-6) , and the underlying `set_owner` check for zeroed data in [8](#0-7) ). I was unable to fully confirm within the given search budget whether there exists a concrete single-transaction path (e.g., through CPI account reuse/realloc patterns) that leaves a vote/stake-owned account with non-zero lamports but a changed owner without first zeroing lamports (which would already be caught by the zero-lamport removal branch). This uncertainty means the finding should be treated as a **confirmed code defect with acknowledged root cause**, but its practical single-request reachability under current runtime invariants is not fully verified from static review alone.

### Recommendation
In `StakesCache::check_and_store`, always evict any pre-existing vote/stake cache entry for `pubkey` whenever the account's current `owner()` is neither the vote program nor the stake program, rather than relying on the zero-lamport branch as the only unconditional removal path. Concretely, add an `else` branch after the `stake_program::check_id(owner)` check that unconditionally calls `stakes.remove_vote_account(pubkey)` and `stakes.remove_stake_delegation(...)` regardless of prior cache membership, closing the gap the existing TODO documents.

### Proof of Concept
Not independently reproducible from static analysis within this session — reachability depends on confirming a concrete single-transaction sequence that changes a previously-cached vote/stake account's `owner()` field to a non-vote/non-stake program while keeping lamports non-zero, which the tooling available here (code search only, no execution) could not conclusively establish or rule out. This should be validated with a runnable Devin session that can write and execute a bank-level unit test analogous to the existing test at [9](#0-8)  to attempt to force this exact code path.

    /// a bank-level cache of vote accounts and stake delegation info
    fn update_stakes_cache(
        &self,
        txs: &[impl SVMMessage],
        processing_results: &[TransactionProcessingResult],
    ) {
        debug_assert_eq!(txs.len(), processing_results.len());
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let use_fixed_point_stake_math = self.use_fixed_point_stake_math();
        txs.iter()
            .zip(processing_results)
            .filter_map(|(tx, processing_result)| {
                processing_result
                    .processed_transaction()
                    .map(|processed_tx| (tx, processed_tx))
            })
            .filter_map(|(tx, processed_tx)| {
                processed_tx
                    .executed_transaction()
                    .map(|executed_tx| (tx, executed_tx))
            })
            .filter(|(_, executed_tx)| executed_tx.was_successful())
            .flat_map(|(tx, executed_tx)| {
                let num_account_keys = tx.account_keys().len();
                let loaded_tx = &executed_tx.loaded_transaction;
                loaded_tx.accounts.iter().take(num_account_keys)
            })
            .for_each(|(pubkey, account)| {
                // note that this could get timed to: self.rc.accounts.accounts_db.stats.stakes_cache_check_and_store_us,
                //  but this code path is captured separately in ExecuteTimingType::UpdateStakesCacheUs
                self.stakes_cache.check_and_store(
                    pubkey,
                    account,
                    new_warmup_cooldown_rate_epoch,
                    use_fixed_point_stake_math,
                );
            });

fn assign(
    account: &mut BorrowedInstructionAccount,
    address: &Address,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    // no work to do, just return
    if account.get_owner() == owner {
        return Ok(());
    }

    if !address.is_signer(signers) {
        ic_msg!(invoke_context, "Assign: account {:?} must sign", address);
        return Err(InstructionError::MissingRequiredSignature);
    }

    account.set_owner(&owner.to_bytes())
}

    /// Assignes the owner of this account (transaction wide)
    pub fn set_owner(&mut self, pubkey: &[u8]) -> Result<(), InstructionError> {
        // Only the owner can assign a new owner
        if !self.is_owned_by_current_program() {
            return Err(InstructionError::ModifiedProgramId);
        }
        // and only if the account is writable
        if !self.is_writable() {
            return Err(InstructionError::ModifiedProgramId);
        }
        // and only if the data is zero-initialized or empty
        if !is_zeroed(self.get_data()) {
            return Err(InstructionError::ModifiedProgramId);
        }
        // don't touch the account if the owner does not change
        if self.get_owner().to_bytes() == pubkey {
            return Ok(());
        }
        self.touch()?;
        self.account.copy_into_owner_from_slice(pubkey);
        Ok(())
    }
