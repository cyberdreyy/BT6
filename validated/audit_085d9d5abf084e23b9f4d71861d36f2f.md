### Title
Stale per-epoch instant-withdraw receipt basis is never cleared on funded claims, corrupting default recovery accounting - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` pays a funded instant receipt but never clears `instantWithdrawsRequestsByEpoch[user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. Like the upstream bug where `num_widgets` is used for bounds before the array is actually filled, the per-epoch "count" (`instantWithdrawClaimsByEpoch`) retains entries whose receipts were already paid out. If a borrower default is later finalized in the same epoch, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` treat already-paid-out underlyings as still-held recovery backing, inflating `defaultRecoveryPrice`/`defaultRecoveryReserve` beyond real balances and underflow-reverting honest users' defaulted claims.

### Finding Description
- `requestInstantWithdraw` records per-epoch basis: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` [1](#0-0) .
- `claimInstantWithdrawRequest` burns the receipt and pays underlying, but clears only the aggregate `instantWithdrawsRequests[_user]` — the per-epoch mappings stay non-zero forever [2](#0-1) .
- On default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` (stale, includes already-paid claims) whenever `pendingInstantWithdraws != 0` [3](#0-2) .
- `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` as underlyings "already held" for those claims, but paid-out funds are no longer held, so `defaultRecoveryReserve` is credited for tokens the contract does not have [4](#0-3) .
- The victim-side claim path then does `instantWithdrawsRequests[_user] -= claimBasis` with a `claimBasis` larger than the user's remaining balance (it includes already-claimed amounts), causing an underflow revert that permanently blocks `claimInstantWithdrawRequest` for any user who claimed a funded instant withdrawal earlier in the defaulted epoch [5](#0-4) .

### Impact Explanation
Two concrete harms, both quantifiable:

1. Recovery insolvency / permanent freeze of unclaimed recovery. Suppose in epoch N: instant requests total 160 (100 funded via `collectInstantWithdrawFunds` and already claimed, 60 unfunded). At `finalizeDefaultRecovery`, `instantBasis = 160`, `pendingInstant = 60` → `prefundedReserve = 100` is added to `defaultRecoveryReserve` even though those 100 tokens were already transferred out. `recoveryPrice = reserveAmount * 1e18 / totalBasis` is computed against ~100 tokens of phantom backing. Recovery claimants draw down `defaultRecoveryReserve` until the actual `underlyingToken.balanceOf` is exhausted, at which point `safeTransfer` reverts — later claimants' recovery is permanently frozen (the reserve accounting can never reconcile) [6](#0-5) .
2. Permanent claim DoS for prior claimants: any user who claimed a funded instant receipt in the default epoch has `claimBasis > instantWithdrawsRequests[user]`, so the subtraction at line 848 underflows and `claimInstantWithdrawRequest` always reverts for them.

### Likelihood Explanation
Requires only unprivileged actions: an attacker or ordinary lender makes an instant-withdraw request that gets funded mid-epoch (`getInstantWithdrawFunds`/collect path), claims it, then other users' instant requests remain pending when the borrower defaults in the same epoch. No malicious privileged role is needed — the borrower defaulting is an expected adverse event, not attacker collusion. The accounting gap is deterministic once the sequence occurs: `instantWithdrawClaimsByEpoch` is only ever incremented and decremented inside `_claimDefaultedInstantWithdrawRequest`, never on the normal funded-claim path.

### Recommendation
On the funded instant claim path, clear the per-epoch records for the amount paid:

```solidity
// in claimInstantWithdrawRequest, after computing `amount`
uint256 currentEpoch = epochNumber;
uint256 epochBasis = instantWithdrawsRequestsByEpoch[_user][currentEpoch];
uint256 paid = epochBasis < amount ? epochBasis : amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] -= paid;
instantWithdrawClaimsByEpoch[currentEpoch] -= paid;
```

This keeps `instantWithdrawClaimsByEpoch[epochNumber]` equal to the still-outstanding receipt basis so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only count unpaid claims. Optionally also clear entries for older epochs lazily, or key receipts so a claim in epoch N clears only epoch-N basis.

### Proof of Concept
Foundry fork sketch (against `IdleCreditVault` + `IdleCDOEpochVariant` deployment used in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function test_StaleInstantBasisCorruptsRecovery() public {
    // setup: vault running, attacker is a KYC'd lender with tranche tokens

    // 1) Attacker requests instant withdraw of 100
    vm.prank(address(cdo));
    strategy.requestInstantWithdraw(100e18, attacker);

    // 2) CDO collects funds for instant queue and attacker claims
    vm.startPrank(address(cdo));
    deal(address(underlying), address(cdo), 100e18);
    underlying.approve(address(strategy), 100e18);
    strategy.collectInstantWithdrawFunds(100e18);
    strategy.claimInstantWithdrawRequest(attacker);
    vm.stopPrank();
    assertEq(underlying.balanceOf(attacker), 100e18);
    // BUG: per-epoch basis still records the paid claim
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, strategy.epochNumber()), 100e18);
    assertEq(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), 100e18);

    // 3) Victim requests instant withdraw of 60, left unfunded
    vm.prank(address(cdo));
    strategy.requestInstantWithdraw(60e18, victim);

    // 4) Borrower defaults; CDO finalizes default recovery with some external recovery
    //    instantBasis = 160, pendingInstant = 60 -> prefundedReserve counted = 100 (phantom)
    //    defaultRecoveryReserve includes 100 tokens the strategy does not hold.
    // ... drive cdo defaulted + finalizeDefaultRecovery ...

    // 5) Attacker's defaulted claim: claimBasis = 160 > instantWithdrawsRequests = 0
    vm.prank(address(cdo));
    vm.expectRevert(); // underflow on instantWithdrawsRequests[user] -= claimBasis
    strategy.claimInstantWithdrawRequest(attacker);

    // 6) Recovery claimants exhaust real balance; the phantom 100 of reserve can never
    //    be paid -> last claimant's _transferDefaultRecovery reverts on safeTransfer.
}
```

The asserted residual `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` values after step 2 demonstrate the stale-count root cause; steps 5–6 demonstrate the DoS and insolvency consequences.
