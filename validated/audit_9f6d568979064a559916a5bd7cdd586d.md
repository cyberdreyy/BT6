### Title
Operator can permanently DoS a staker's `unlock_stake`/`switch_operator`/`request_commission` by setting an unregistered, transfer-opted-out beneficiary - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`staking_contract::set_beneficiary_for_operator` lets an operator set an arbitrary `new_beneficiary` address with no check that the address is registered to receive `AptosCoin` or accepts direct coin transfers. That beneficiary is later paid via a *push* payment inside `distribute_internal`, which loops over **all** shareholders (staker included) and calls `aptos_account::deposit_coins` for each of them in a single atomic transaction. If the deposit to the beneficiary aborts, the whole transaction — including the staker's own payout — reverts, permanently blocking the staker's ability to withdraw/unlock stake as long as the operator keeps that beneficiary configured this way.

### Finding Description
`set_beneficiary_for_operator` performs no registration/acceptance check on `new_beneficiary`: [1](#0-0) 

Compare this to `vesting::set_beneficiary`, which explicitly requires the new beneficiary to be registered for APT *specifically to prevent this class of DoS*: [2](#0-1) 

`distribute_internal` is the push-payment routine used by `distribute`, `unlock_stake`, `request_commission`, `switch_operator`, and `update_commision`. It iterates over every shareholder (staker and operator/beneficiary) in one atomic loop and calls `aptos_account::deposit_coins` for each, redirecting the operator's share to `beneficiary_for_operator(operator)`: [3](#0-2) 

`aptos_account::deposit_coins` only auto-registers/accepts a coin deposit if the recipient is already registered for the coin type or has not opted out of arbitrary coin transfers; otherwise it aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`: [4](#0-3) 

An address can opt out of unregistered/direct coin transfers at any time via `set_allow_direct_coin_transfers(false)`: [5](#0-4) 

`unlock_stake` (staker-initiated) and `switch_operator` (staker-initiated) both invoke `distribute_internal` before doing their own logic ("Force distribution of any already inactive stake"): [6](#0-5) [7](#0-6) 

**Root cause chain:** operator (unprivileged w.r.t. staker's funds) sets `beneficiary_for_operator` to an address that (a) is not registered for `AptosCoin` and (b) has `allow_arbitrary_coin_transfers = false` → distribute_internal's atomic loop always aborts on the beneficiary's deposit → every function that force-distributes (unlock_stake, request_commission, switch_operator, update_commision, and distribute itself) reverts as long as this configuration persists → the staker cannot unlock/withdraw their own stake, nor switch away from the malicious/uncooperative operator, because `switch_operator` itself calls `distribute_internal` first.

This is the exact Move-level analog of the Solidity report's push-payment DoS: a single non-cooperating recipient in an atomic payout loop blocks funds belonging to unrelated parties.

### Impact Explanation
This traps the staker's principal and voting/withdrawal rights: `unlock_stake` and `switch_operator` (the only staker-initiated exits, aside from waiting on `distribute` which has the same problem) cannot complete while the poisoned beneficiary configuration exists. This is a permanent, non-recoverable-without-operator-cooperation lock on stake belonging to the staker, not the attacker. It matches the required impact "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows." High severity because it can freeze mainnet staker funds behind a validator operator's unilateral, always-available configuration change, with no recovery path exposed in `staking_contract.move` (the operator can flip the beneficiary or its `DirectTransferConfig` back, but a malicious/uncooperative operator is not required to).

### Likelihood Explanation
Reachable by any operator of a staking contract (a role the framework itself expects to sometimes be adversarial to or diverging in interest from the staker — see the module's whole reward-sharing model). No special privilege beyond being the operator of that specific staking contract is needed, and setting `allow_arbitrary_coin_transfers=false` on the beneficiary account and never registering it for `AptosCoin` are both ordinary, permissionless actions. `features::operator_beneficiary_change_enabled()` must be on, which is the intended/enabled path for this feature.

### Recommendation
Mirror the fix already applied in `vesting.move`: require `aptos_account::assert_account_is_registered_for_apt(new_beneficiary)` (or equivalent "can accept APT" check) in `staking_contract::set_beneficiary_for_operator` before accepting the new beneficiary. Additionally, consider making `distribute_internal`'s per-recipient deposit fault-tolerant (e.g., catch/skip a failing recipient and leave their share still redeemable, or use a pull-based claim per recipient) so that one recipient's inability to receive funds can never block payouts to other shareholders.

### Proof of Concept
1. Staker creates a staking contract with `operator` via `create_staking_contract`, contributing `amount` stake. [8](#0-7) 
2. `operator` (or any address) calls `aptos_account::set_allow_direct_coin_transfers(false)` on a fresh address `evil_beneficiary` that has never been registered for `AptosCoin`.
3. `operator` calls `staking_contract::set_beneficiary_for_operator(operator, evil_beneficiary)` — succeeds with no validation. [1](#0-0) 
4. Time passes, the stake pool earns rewards, some stake becomes inactive/pending_inactive.
5. Staker calls `unlock_stake(staker, operator, amount)` to withdraw part of their stake. Internally this calls `distribute_internal`, which tries to pay the operator's commission share to `evil_beneficiary` via `aptos_account::deposit_coins`. [3](#0-2) 
6. Because `evil_beneficiary` is unregistered for `AptosCoin` and has opted out of direct transfers, `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, reverting the entire `unlock_stake` transaction — the staker receives nothing and cannot make progress.
7. Staker tries `switch_operator` to escape — it also calls `distribute_internal` first and reverts for the same reason, so the staker cannot even leave the operator without the operator's cooperation.

Note: this analysis is based on static code review of `staking_contract.move`, `vesting.move`, and `aptos_account.move` in this indexed snapshot; a live Move-VM test run to confirm the exact abort behavior was not performed and is recommended before treating this as fully confirmed.

            );

            SetBeneficiaryForOperator {
                operator: operator_addr,

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
