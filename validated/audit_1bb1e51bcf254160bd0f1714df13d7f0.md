### Title
`skip_deduct` in `promise_batch_action_function_call_weight` reads a live, batch-mutated `current_account_balance`, letting a self-funded account skip 1-yoctoNEAR deduction after draining its own balance mid-execution - (File: `runtime/near-vm-runner/src/logic/logic.rs`)

### Summary
`promise_batch_action_function_call_weight` decides whether to skip deducting the attached `amount` from the account by checking `self.result_state.current_account_balance.is_zero()` at the moment the action is appended [1](#0-0) . Because `current_account_balance` is a single mutable field in `result_state` that is decremented in place by every prior `deduct_balance` call within the same contract execution (e.g. from an earlier `promise_batch_action_transfer` or another function-call deposit in the same batch), a contract with a genuinely nonzero starting balance can spend it down to exactly zero via one action and then have a later 1-yoctoNEAR `FunctionCall` action in the same batch/receipt qualify for `skip_deduct`.

### Finding Description
The relevant check is:
```rust
let skip_deduct = amount == Balance::from_yoctonear(1)
    && self.config.one_yocto_on_promise
    && self.result_state.current_account_balance.is_zero();
if skip_deduct {
    self.result_state.subsidized_amount = self.result_state.subsidized_amount.checked_add(amount)...;
} else {
    self.result_state.deduct_balance(amount)?;
}
``` [2](#0-1) 

`current_account_balance` is not a snapshot taken once per receipt/transaction; it is the live running balance in `VMLogic`'s `result_state`, mutated by every `deduct_balance` invocation triggered by prior actions dispatched in the same contract call (transfers, deposits on other function calls, etc.). This means the zero-balance condition is evaluated **after** any earlier action in the same batch/execution has already drained the account, not against the balance the account held when the receipt started executing.

There is nothing in this function, nor visible in the surrounding code, that restricts `skip_deduct` to a specific account category (e.g., a "deterministic"/keyless account intended by the doc comment) — it is purely a function of the live balance value and the `one_yocto_on_promise` config flag. Consequently, an ordinary contract (deployed by an unprivileged user, funded with real NEAR) can, within a single function-call execution:
1. Issue a `promise_batch_action_transfer`/deposit-bearing action that moves its entire real balance out, driving `current_account_balance` to zero.
2. Issue a subsequent `promise_batch_action_function_call_weight` call with `amount == 1` yoctoNEAR targeting a third-party receiver contract that expects a subsidized 1-yoctoNEAR attached deposit.
3. Because the balance is now (transiently) zero, `skip_deduct` triggers, crediting `subsidized_amount` instead of calling `deduct_balance`, even though the account originally held real funds.

The outgoing action still carries `amount` as its deposit field to `ext.append_action_function_call_weight`, so the receiver-side receipt still specifies the 1 yoctoNEAR deposit regardless of whether it was actually deducted from the sender.

### Impact Explanation
This breaks the intended 1:1 relationship between what is subtracted from the sender's balance and what is recorded as "subsidized" (conjured) value. In the worst case, this is a dust-level token-inflation/accounting-invariant violation: value appears in an outgoing receipt's deposit without a corresponding deduction from the sender's balance, because the "skip" was granted based on a transient zero-balance state induced by the account's own prior action in the same batch rather than a persistent, genuinely-zero-balance account. Per NEAR's bounty categories this falls under token inflation / loss (accounting divergence), though the magnitude per action is bounded to 1 yoctoNEAR and each occurrence costs real gas (`function_call_base`/`function_call_byte` fees), so it is not economically profitable at scale — it is primarily a protocol-invariant correctness issue rather than a direct fund-theft vector.

### Likelihood Explanation
Reachable by any unprivileged account: deploy a contract, fund it with any positive balance, and craft a single function call that (a) drains the account's balance via a transfer/deposit action earlier in the same execution, then (b) attaches exactly 1 yoctoNEAR to a further promise batch action. No validator, RPC operator, or privileged access is required — only standard transaction signing, a deployed wasm contract, and knowledge of the `promise_batch_action_transfer` / `promise_batch_action_function_call_weight` host APIs. It is fully repeatable, limited only by gas/transaction cost per attempt.

### Recommendation
Snapshot `current_account_balance` (or a dedicated "was this account created/funded with zero balance for its entire receipt lifetime" flag) once at the start of receipt/action processing rather than re-checking the live, batch-mutated balance on every `promise_batch_action_function_call_weight` call. Alternatively, restrict `skip_deduct` eligibility explicitly to the account category the feature was designed for (deterministic/keyless accounts that structurally cannot hold balance), rather than inferring it from a value that can be driven to zero by the account's own actions within the same execution.

### Proof of Concept
Integration test plan (runtime-level, e.g. in `runtime/runtime/src/tests/apply.rs` style harness):
1. Create account `A` with a nonzero real balance and deploy a contract exposing a method `drain_then_skip` that, in one execution:
   - Calls `promise_batch_create` for a promise to some receiver `B`, then `promise_batch_action_transfer` moving `A`'s entire balance out.
   - Calls `promise_batch_create` for a second promise to receiver `C` (a third-party contract), then `promise_batch_action_function_call_weight` with `amount = 1` yoctoNEAR.
2. Enable `one_yocto_on_promise` in the runtime config used by the test.
3. Execute the receipt and assert:
   - `result_state.subsidized_amount == 1` (the skip fired) even though `A` started with a nonzero real balance.
   - The outgoing receipt to `C` carries `deposit == 1`.
   - Total value conservation across the chunk (sender debit vs. receiver credit) is checked by the balance checker and does not account for the extra 1 yoctoNEAR, demonstrating the discrepancy described.

Uncertainty: I could not verify, within the available tool budget, how `subsidized_amount` is subsequently consumed in `runtime/runtime/src/lib.rs` or whether the chunk-level balance checker independently catches/reverts this discrepancy, nor whether `one_yocto_on_promise` is actually enabled unconditionally for all accounts on mainnet versus gated to a specific account category elsewhere in the transaction/action validation pipeline. Confirming those two points would be necessary to fully establish end-to-end exploitability and severity.
