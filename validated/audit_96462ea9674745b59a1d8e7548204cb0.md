### Title
ERC4626 liquidity failure prevents `stopEpoch` from reaching the default path - (`contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower.onStopEpoch` translates a covered-but-failed ERC4626 withdrawal into a reverting call, causing `IdleCDOEpochVariant.stopEpoch` to revert before its borrower-transfer `try/catch` can invoke `_handleBorrowerDefault`. A liquidity-constrained external vault can therefore keep the credit epoch running even though the intended failure-handling state already exists.

### Finding Description
`stopEpoch` calls `onStopEpoch` before entering the `try this.getFundsFromBorrower(...)` block that handles borrower default. [1](#0-0) 

Inside `onStopEpoch`, the borrower first checks whether its ERC4626 position economically covers the requested shortfall; if it does, a failed `vault.withdraw` is caught and replaced with `StopEpochVaultLiquidityUnavailable`, which bubbles to `stopEpoch`. [2](#0-1) 

Consequently, neither `getFundsFromBorrower` nor its surrounding `catch` executes, so `_handleBorrowerDefault` is never reached. [3](#0-2) 

This matters when the ERC4626 vault still values the programmable borrower’s shares above the shortfall but lacks immediately withdrawable liquidity, such as after ordinary vault users withdraw available cash while the vault’s remaining assets are lent out. In that state, an external liquidity shortage prevents the honest manager from both stopping the epoch and recording a default. [4](#0-3) 

The ordinary emergency shutdown does not recover the epoch because it only pauses the CDO and disables withdrawal requests; it does not set `defaulted`, stop `isEpochRunning`, or settle pending withdrawals. [5](#0-4) 

### Impact Explanation
All user deposits and pending withdrawal receipts remain locked while `isEpochRunning` remains true and `defaulted` remains false. This is at least a temporary freezing of the affected pool’s full active NAV and pending withdrawal amount, and it becomes indefinite while the ERC4626 position remains nominally valuable but non-withdrawable.

The broken invariant is epoch liveness: once `epochEndDate` has passed, the manager should either complete settlement or transition the pool into default accounting. Instead, a failure in an external integration blocks both outcomes before the existing default transition is reached. [6](#0-5) 

### Likelihood Explanation
No privileged actor is required to create the condition: ordinary users of the underlying ERC4626 vault can consume its immediately available liquidity, while the programmable borrower’s shares can continue to report enough value through `convertToAssets`. The condition is especially plausible for credit or lending-style ERC4626 vaults where assets may be deployed and withdrawals depend on available cash.

The manager cannot route around the failure through `emergencyExitVault` when the vault itself cannot satisfy withdrawals, and `setVault` is unavailable while the programmable borrower still owns vault shares. [7](#0-6) [8](#0-7) 

### Recommendation
Add an explicit manager-controlled settlement mode equivalent to the report’s `needToWithdraw` parameter, such as `stopEpoch(..., bool attemptVaultWithdraw)`.

When `attemptVaultWithdraw` is false, skip the ERC4626 withdrawal and proceed to the borrower pull so its failure is caught by the existing `try/catch` and calls `_handleBorrowerDefault`. Alternatively, allow `onStopEpoch` to return `false` for a covered-but-unavailable vault withdrawal after a manager elects forced-default handling, while retaining the current retryable behavior for normal stops.

### Proof of Concept
The following Foundry test can be added to `test/foundry/ProgrammableBorrowerCreditVault.t.sol`; it uses a mainnet fork for USDC and an ERC4626 stub whose accounting remains solvent while cash liquidity is consumed by an unprivileged external borrower:

```solidity
contract LiquidityConstrained4626 is ERC20 {
  IERC20Detailed public immutable assetToken;
  uint256 public managedAssets;

  constructor(address asset_) ERC20("Liquidity Constrained", "LC") {
    assetToken = IERC20Detailed(asset_);
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    return supply == 0 ? shares : shares * managedAssets / supply;
  }

  function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
    uint256 supply = totalSupply();
    shares = supply == 0 || managedAssets == 0
      ? assets
      : assets * supply / managedAssets;
    assetToken.transferFrom(msg.sender, address(this), assets);
    managedAssets += assets;
    _mint(receiver, shares);
  }

  function withdraw(
    uint256 assets,
    address receiver,
    address owner_
  ) external returns (uint256 shares) {
    // Reverts when reported assets are lent out rather than held as cash.
    require(assetToken.balanceOf(address(this)) >= assets, "no-liquidity");
    uint256 supply = totalSupply();
    shares = (assets * supply + managedAssets - 1) / managedAssets;
    if (msg.sender != owner_) _spendAllowance(owner_, msg.sender, shares);
    managedAssets -= assets;
    _burn(owner_, shares);
    assetToken.transfer(receiver, assets);
  }

  function redeem(uint256 shares, address receiver, address owner_) external returns (uint256 assets) {
    assets = convertToAssets(shares);
    require(assetToken.balanceOf(address(this)) >= assets, "no-liquidity");
    if (msg.sender != owner_) _spendAllowance(owner_, msg.sender, shares);
    managedAssets -= assets;
    _burn(owner_, shares);
    assetToken.transfer(receiver, assets);
  }

  // Represents unprivileged utilization of the ERC4626's underlying liquidity.
  function utilizeLiquidity(uint256 assets) external {
    assetToken.transfer(msg.sender, assets);
  }
}

function testStopEpochCannotDefaultWhenERC4626IsIlliquid() external {
  LiquidityConstrained4626 constrainedVault = new LiquidityConstrained4626(USDC);
  _setUpProgrammableBorrowerCreditVault(FORK_BLOCK, address(constrainedVault));

  uint256 amount = 10_000 * oneScale;
  idleCDO.depositAA(amount);
  _startEpochAndCheckPrices(0);

  // An unprivileged consumer removes immediate liquidity. ProgrammableBorrower's
  // shares still cover the required shortfall because managedAssets is unchanged.
  constrainedVault.utilizeLiquidity(underlying.balanceOf(address(constrainedVault)));
  assertGe(programmableBorrower.vaultSharesBalance(), 0);
  assertGe(programmableBorrower.totalUnderlying(), amount - 1);

  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
  cdoEpoch.stopEpoch(0, 0);

  // The epoch neither settles nor reaches the default transition.
  assertTrue(cdoEpoch.isEpochRunning());
  assertFalse(cdoEpoch.defaulted());
}
```

The critical assertion is that the revert occurs before `getFundsFromBorrower`, so the existing `catch` block cannot mark the borrower as defaulted. [1](#0-0)
