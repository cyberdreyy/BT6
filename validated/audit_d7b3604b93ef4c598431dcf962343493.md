### Title
Attached deposit is permanently stuck in `multisig-factory` when new multisig account creation fails - ([File: multisig-factory/src/lib.rs])

### Summary
`MultisigFactory::create` forwards the caller's entire `attached_deposit` to a newly created multisig sub-account in the same promise batch, but unlike the sibling factory contracts in this codebase (`lockup-factory`, `staking-pool-factory`), it has no callback to detect a failed creation and refund the deposit. If the `create_account`/`deploy_contract`/`transfer`/`function_call` batch fails for any reason (e.g. the sub-account name already exists, or is otherwise invalid), the attached NEAR remains on the factory's own balance with no code path to return it to the caller.

### Finding Description
`create` builds a single promise batch that creates the account, deploys the multisig2 code, transfers `env::attached_deposit()`, and calls `new`, but does not chain any `.then(...)` callback: [1](#0-0) 

Compare this with `lockup-factory::create`, which forwards the same deposit but explicitly chains `on_lockup_create` as a callback: [2](#0-1) 

That callback checks `is_promise_success()` and, on failure, transfers the deposit back to the original predecessor: [3](#0-2) 

The same pattern exists in `staking-pool-factory::create_staking_pool` / `on_staking_pool_create`: [4](#0-3) [5](#0-4) 

`multisig-factory` has no equivalent `on_create`/refund callback anywhere in its source, confirmed by the absence of any `ext_self`, `callback`, or `refund` logic in `multisig-factory/src/lib.rs`. Because all actions targeting the new sub-account (`create_account`, `deploy_contract`, `transfer`, `function_call`) are part of one receipt, if that receipt fails (e.g. the target account name is already taken, contains invalid characters, or `deploy_contract`/`new` fails for any reason), the deposit that was already debited from the factory's own balance to fund that outgoing receipt is not returned to the factory and is never redirected back to the caller by any application-level logic. This breaks the custody binding: deposit attached by the caller == deposit either delivered to the new multisig or refunded to the caller. Here it becomes: deposit attached == deposit stuck on the factory, unrecoverable by any unprivileged call.

### Impact Explanation
This matches the "funds permanently frozen" Critical impact criterion: NEAR sent by an unprivileged caller to create a multisig is not delivered to the intended destination on failure, and is not recoverable through any function exposed by `MultisigFactory` (there is no owner/withdraw/refund method in this contract). The value is permanently locked in the factory's account balance.

### Likelihood Explanation
Likelihood is moderate to high: any collision on the derived sub-account name (`{name}.{factory}` already existing, e.g. due to a front-run or a repeated `create` call with the same `name`) or any other failure in the batched receipt (invalid `name`, insufficient gas for the nested `new` call, `deploy_contract` failure) triggers this, and requires no special privileges — any ordinary user calling `create` with a colliding or otherwise failing `name` triggers the fund loss.

### Recommendation
Add a callback (analogous to `on_lockup_create` / `on_staking_pool_create`) chained via `.then(...)` on the `create` promise that checks `is_promise_success()` and, on failure, transfers `env::attached_deposit()` back to `env::predecessor_account_id()`.

### Proof of Concept
1. Caller A calls `multisig-factory.create({name: "acct", members: [...], num_confirmations: 1})` attaching `X` NEAR — succeeds, creates `acct.factory`.
2. Caller B calls `multisig-factory.create({name: "acct", members: [...], num_confirmations: 1})` attaching `Y` NEAR, targeting the same `name`.
3. The `create_account` action for `acct.factory` fails because the account already exists; the whole receipt (including the `transfer(Y)`) fails.
4. `Y` NEAR, having already been debited from the factory's balance to fund the failed outgoing receipt, is not refunded to Caller B by any code in `multisig-factory/src/lib.rs` (no callback exists), and no other exposed method allows Caller B or anyone else to reclaim it — the funds are permanently stuck in the factory contract.

            )
    }

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
