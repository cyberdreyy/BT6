### Title
Fee-on-transfer / rebasing underlying breaks `IdleCreditVault.deposit` 1:1 strategy-token minting, causing NAV overstatement and stuck funds - ([contracts/strategies/idle/IdleCreditVault.sol:596-617](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCDOCreditVault._deposit` correctly mints tranche shares based on the *actual* balance delta received (`_contractTokenBalance(_token) - _preBal`), but it then calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the nominal `_amount`. Inside `IdleCreditVault.deposit`, the strategy does `underlyingToken.safeTransferFrom(msg.sender, address(this), _amount)` and unconditionally `_mint(msg.sender, _amount)` — minting receipt tokens 1:1 with the *nominal* amount rather than the amount actually received, and also incrementing `totEpochDeposits += _amount`. If `token` charges a transfer fee (or is rebasing), the vault ends up holding fewer underlyings than strategy tokens outstanding, so the CDO's NAV is permanently overstated and later payouts revert for lack of balance.

### Finding Description
Relevant code in `contracts/strategies/idle/IdleCreditVault.sol`:

```solidity
function deposit(uint256 _amount) external virtual override returns (uint256) {
  _onlyIdleCDO();
  if (_amount > 0) {
    underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
    _mint(msg.sender, _amount);              // mints nominal amount, not received amount
  }
  if (IIdleCDOEpochVariant(idleCDO).isEpochRunning()) {
    totEpochDeposits = 0;
    epochNumber += 1;
  } else {
    totEpochDeposits += _amount;             // also uses nominal amount
  }
  return _amount;
}
```

And the caller in `contracts/IdleCDOCreditVault.sol` (lines 201-211):

```solidity
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
_minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
_updateSplitRatio(_getAARatio(true));
IIdleCDOStrategy(strategy).deposit(_amount);  // pushes full _amount to strategy
```

Strategy tokens are explicitly "1:1 with underlyings" (`burnStrategyTokens` docstring, line 588), and `getContractValue`/NAV accounting treats the CDO's strategy-token balance as claimable underlying. With a fee-on-transfer token (e.g. USDT with fees enabled, STA, PAXG):

- The vault receives `_amount - fee`, but mints `_amount` receipt tokens to the CDO and books `totEpochDeposits += _amount`.
- The discrepancy is invisible at deposit time: tranche shares were minted only for the received amount, so the overstatement only surfaces later when the strategy must push real underlyings back — `sendInterestAndDeposits(_amount)` does `safeTransfer(idleCDO, _amount)` (line 584), which reverts once cumulative booked claims exceed the real balance. `stopEpoch`/claim flows then brick.
- A downward-rebasing token produces the same outcome: minted strategy tokens stay fixed while the vault balance shrinks.

The minted-vs-received gap compounds across every deposit (each fee event adds more unbacked receipt supply), so the shortfall grows over time rather than staying at one deposit's fee.

### Impact Explanation
Permanent freezing / insolvency: strategy-token supply exceeds vault underlying balance, so `stopEpoch` settlement via `sendInterestAndDeposits` and any pull of underlyings reverts once the real balance is exhausted. Last-to-claim withdraw-request holders and tranche holders cannot be paid; funds are stuck in the vault. Loss equals the cumulative transfer fees (or rebase deficit) on all deposits, which is unbounded over the pool's lifetime. No guard prevents it: there is no balance-delta check in `deposit`, no `_skimDonatedAssets` analog that would correct it (skimming would only make it worse), and `totEpochDeposits`/`apr0TotalPrincipal` style accounting compounds the bookkeeping error.

### Likelihood Explanation
The credit vaults are designed to be deployed against an arbitrary ERC20 `token` chosen at initialization; nothing restricts the underlying to non-fee tokens. USDT/USDC — the typical credit-vault currencies — can enable transfer fees at any time by issuer decision, and fee-on-transfer tokens are a documented reality for exactly this kind of integration. An unprivileged lender merely needs to call `depositAA`/`depositBB` while a fee is active; no attacker manipulation is required, though a lender could also deliberately deposit a fee-charging token to grief the pool. The inflated claim only needs one fee-charging deposit to create a shortfall.

### Recommendation
In `IdleCreditVault.deposit`, compute the actually-received amount and mint/track that:

```solidity
uint256 balBefore = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
uint256 received = underlyingToken.balanceOf(address(this)) - balBefore;
_mint(msg.sender, received);
... // use `received` for totEpochDeposits and the return value
```

Correspondingly, `IdleCDOCreditVault._deposit` should pass the received delta (already computed as `_contractTokenBalance(_token) - _preBal`) to `strategy.deposit` rather than `_amount`. For rebasing tokens, either disallow them at deployment, or make `getContractValue`/claim paths cap payouts at the vault's real `balanceOf` and socialize deficits through the existing loss waterfall.

### Proof of Concept
Foundry fork-style PoC sketch:

```solidity
// FeeToken: ERC20 mock that burns 1% of `amount` on every transfer/transferFrom.
// Deploy IdleCDOCreditVault + IdleCreditVault with `token = feeToken`.

function testFeeOnTransferShortfall() public {
    feeToken.mint(user, 1_000_000e6);
    vm.startPrank(user);
    feeToken.approve(address(idleCDO), type(uint256).max);

    // Deposit 1,000,000; vault receives 990,000 but mints 1,000,000 strategy tokens
    idleCDO.depositAA(1_000_000e6);
    vm.stopPrank();

    assertEq(feeToken.balanceOf(address(strategy)), 990_000e6);   // real balance
    assertEq(strategy.balanceOf(address(idleCDO)), 1_000_000e6);  // booked claim

    // At stopEpoch the strategy must push back interest + principal.
    // sendInterestAndDeposits(amount > 990_000e6) -> safeTransfer reverts:
    vm.expectRevert(); // ERC20: transfer amount exceeds balance
    idleCDO.stopEpoch(0); // any positive expectedEpochInterest path hits the same wall
}
```

The invariant violated is solvency: strategy tokens are a 1:1 underlying claim, yet total supply can exceed the vault's real token balance, so `stopEpoch`/claim payouts revert and residual funds are permanently frozen.
