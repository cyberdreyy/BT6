### Title
Removed multisig members' stale confirmations still count toward execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges requests *created* by the removed member, but never scans or cleans the `confirmations` map for confirmations the removed member previously cast on *other* members' requests. Because `confirm()` decides whether to execute a request purely by comparing `confirmations.len()` to `self.num_confirmations` (never re-validating that each entry in the confirmation set is still a current member), a request can execute using one or more "confirmations" from an account that is no longer a member of the multisig at execution time.

### Finding Description
The relevant custody binding is: **number of confirmations counted for a request == number of confirmations from currently live members**. This invariant is broken.

- `confirm()` fetches `confirmations = self.confirmations.get(&request_id)` and executes once `confirmations.len() as u32 + 1 >= self.num_confirmations` [1](#0-0) . It never checks that the accounts/keys already present in that `HashSet<String>` are still in `self.members`.
- `delete_member` is the only place that mutates state when a member is removed. It removes access keys, decrements `num_requests_pk`, and removes the member from `self.members`, but the request-cleanup step only targets requests whose `MultiSigRequestWithSigner.member` (the *creator*/original signer) equals the member being deleted: `self.requests.iter().filter_map(|(k, r)| if r.member == member { Some(k) } else { None })` [2](#0-1) .
- If the removed member had instead **confirmed** (not created) some other still-pending request, that confirmation entry in `self.confirmations` for that `request_id` is left untouched, since it is keyed by `request_id` and iterated over from a different collection than the one filtered.

As a result, a confirmation cast by an account that is later removed from `self.members` remains valid indefinitely and keeps counting toward `num_confirmations` for any request it was cast on prior to removal.

### Impact Explanation
This lets a `Transfer`, `FunctionCall`, `AddKey`, or other `MultiSigRequestAction` execute with fewer *live* member approvals than the configured threshold, effectively executing multisig actions below the intended confirmation threshold — moving NEAR (or granting keys/permissions) out of the account without the number of currently-trusted signers the multisig was configured to require. This falls squarely under the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
No special privilege is required beyond being (at some point) a legitimate member who confirms a request, and later being removed through the normal `DeleteMember` governance flow (itself achieved with the required threshold, an entirely ordinary lifecycle event, not an attack on the removal step). Any request left pending across a membership change is silently affected; this can also be intentionally engineered by the remaining signers to reduce the effective threshold, or exploited by a soon-to-be-removed member who pre-confirms requests before being pushed out.

### Recommendation
When a member is removed in `delete_member`, iterate over all entries in `self.confirmations` (not just requests the member created) and strip the removed member's identifier from every confirmation set; alternatively, `confirm()` should validate on read that every account/key in a request's confirmation set is still contained in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy multisig with `members = [A, B, C]`, `num_confirmations = 2`.
2. `A` calls `add_request` creating request `R` (e.g., `Transfer` of contract funds to an external account) — `R.member == A`.
3. `B` calls `confirm(R)` → `confirmations[R] = {B}` (len 1 < 2, not executed yet) [3](#0-2) .
4. Through the normal (correctly-thresholded) multisig flow, `A` and `C` submit/confirm a `DeleteMember { member: B }` request, which succeeds and removes `B` from `self.members`. This only removes requests where `r.member == B`; since `R.member == A`, `R` and its confirmation set `{B}` are left intact [4](#0-3) .
5. Now live members are only `{A, C}`, and `num_confirmations` is still 2.
6. `A` calls `confirm(R)`. `confirmations.len() + 1 == 2 >= num_confirmations(2)` → `R` (the `Transfer`) executes, even though only `A` is a currently-live confirming member and `B`'s stale confirmation is what pushed it over the threshold [5](#0-4) .

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
