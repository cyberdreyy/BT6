### Title
Stale confirmations from deleted multisig members still count toward the confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in the multisig2 contract only removes confirmations belonging to requests that were *originally submitted by* the member being deleted. It does not scrub that member's confirmation entries from other pending requests that were submitted by different members but which the removed member had already confirmed. Consequently, a confirmation cast by a member who is later removed still counts toward reaching `num_confirmations` on `confirm()`, breaking the intended "K distinct current members" custody binding on request execution.

### Finding Description
`delete_member` is implemented as: [1](#0-0) 

It filters `self.requests` for entries where `r.member == member` (i.e., requests the deleted member itself created) and removes the associated `confirmations` and `requests` entries for only those. It never iterates over `self.confirmations` to strip the deleted member's identifier from confirmation sets belonging to requests *submitted by other members*.

The threshold check in `confirm()` counts entries in the request's `confirmations` set without validating that each entry corresponds to a currently active member: [2](#0-1) 

Because `MultisigMember`/signer identifiers are stored as opaque strings in the `confirmations: UnorderedSet<String>` associated with a `request_id`, and `delete_member` never purges these sets for requests it doesn't itself own, a confirmation recorded by a member before their removal remains valid data that is summed against `num_confirmations` even after that member is no longer part of `self.members`.

The equality that should hold is:
```
confirmations counted towards a request == confirmations cast by members who are currently in `self.members`
```
This is violated: confirmations counted can include entries from accounts/keys no longer present in `self.members`.

### Impact Explanation
This breaks the "confirmations counted versus live members" custody-authorization binding explicitly called out as an in-scope impact class. The K-of-N guarantee of the multisig (that at least K *currently authorized* members approved a request before NEAR is moved, a key is added, code is deployed, etc.) can be undermined: a request that only has confirmations from `K-1` current, legitimate members plus one stale confirmation from a removed (e.g., compromised or off-boarded) member will still execute via `execute_request`, which can transfer NEAR (`MultiSigRequestAction::Transfer`), deploy new contract code, add full access keys, or add/delete members — i.e., move funds or grant authority on behalf of the account with fewer than the intended number of currently-trusted approvals. This is a Critical-class custody violation per the rules ("a multisig request executed below threshold").

### Likelihood Explanation
The vulnerable window requires: (1) a request to be created and confirmed by a member (but not yet fully confirmed), and (2) that confirming member subsequently deleted via `DeleteMember`, while the original request is still pending. This is a realistic operational sequence — for example, an organization removes a departing or compromised member while other administrative requests are mid-flight, or an attacker who briefly held key access confirms a malicious/self-serving request just before being detected and removed. Since `delete_member` gives no visible warning that pending cross-member confirmations survive, operators are unlikely to know they must manually `delete_request` every outstanding request before removing a member, making accidental triggering plausible.

### Recommendation
When deleting a member, iterate over `self.requests` (or maintain a reverse index) to also strip the deleted member's identifier from the `confirmations` set of every request, not only requests it authored. Alternatively, validate at `confirm()`-threshold-check time that every entry in a request's confirmation set still corresponds to a member present in `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize multisig2 with members `[A, B, C, D]` and `num_confirmations = 3`.
2. Member `B` calls `add_request` (submits request `X` targeting a `Transfer` action), then a separate call from `A` (or `B` itself via `add_request_and_confirm`) results in `confirmations[X] = {B}` (1 confirmation).
3. Member `C` confirms `X`: `confirmations[X] = {B, C}` (2 confirmations, below threshold of 3, so request stays pending — see the `confirm()` logic at lines 292-315 above).
4. Through a separate fully-confirmed multisig request, `B` is deleted via `DeleteMember`. `delete_member` (lines 355-379) only removes requests where `r.member == B` (requests B itself authored); request `X` was authored by someone else, so `confirmations[X] = {B, C}` is untouched.
5. Member `D` (a legitimate, currently active member) confirms `X`: `confirmations[X].len() + 1 = 3 >= num_confirmations`, so `execute_request` fires the `Transfer` — even though only 2 of the 3 confirming identities (`C`, `D`) are still current members; `B`'s stale confirmation from before removal counted toward the threshold.

Note: I was unable to complete a byte-for-byte comparison against the older `multisig/src/lib.rs` (v1) implementation's `delete_key`/`remove_request` handling before running out of tool iterations, so it is uncertain whether the same defect is present there or was already mitigated; the finding above is confirmed specifically for `multisig2/src/lib.rs`.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
