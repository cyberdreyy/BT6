### Title
Incomplete duplicate-tenure-block inspection in v1 `validate_tenure_change_payload` lets a signer sign two conflicting tenure-start blocks in the same tenure - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The v1 chainstate's guard against duplicate tenure-start blocks inspects only `get_last_globally_accepted_block`, ignoring blocks the signer has already locally accepted (i.e., already signed) but that have not yet reached global (majority) acceptance. This mirrors the CIS advisory's root cause — a validator that checks only one policy "shape" (attached) while missing another equivalent shape (inline) that carries the same admin-equivalent power. Here, the validator checks only the "globally accepted" evidence shape and misses the "locally accepted / signed-by-me" shape that is equally probative of a prior commitment, letting a competing tenure-change block bypass the one-tenure-start guard.

### Finding Description
`validate_tenure_change_payload` in v1 is the sole gate (run only at proposal time, per `docs/signer-flows.md` section 7) that prevents accepting a second, competing tenure-start block for a tenure the signer has already committed to [4](#0-3) . It queries:

```rust
let last_in_current_tenure = signer_db
    .get_last_globally_accepted_block(&block.header.consensus_hash)
```

That helper only returns blocks in `BlockState::GloballyAccepted` — i.e., blocks the *node* has already adopted after a full-weight signature set (per the state machine described in `docs/signer-flows.md` section 2 and section 6, `mark_globally_accepted` fires only on `NewBlock` from the node). It does **not** see blocks in `LocallyAccepted` state, i.e., blocks this very signer has already added its own signature to via `mark_locally_accepted`, but that have not yet reached the node/global threshold.

By contrast, the v2 implementation of the same guard was hardened to close exactly this gap, using `get_last_signed_block` (locally OR globally accepted) instead [5](#0-4) , and a regression test explicitly documents the prior bug and fix:

```
/// This is a regression test: previously, the check used
/// `get_last_globally_accepted_block`, which would miss blocks in
/// `LocallyAccepted` or `PreCommitted` state and incorrectly allow
/// a duplicate tenure change.
``` [6](#0-5) 

The v1 path was never given the equivalent fix; it still contains only the narrower, pre-fix check [4](#0-3) . Since v1 remains the live path whenever the fleet's negotiated protocol version is below 2 [7](#0-6) , this is a reachable, non-theoretical gap in a currently-shipped code path, not a dead branch.

Concretely: once this signer signs (locally accepts) tenure-start block A for consensus hash `CH`, but before block A reaches global acceptance (i.e., before the node has counted a majority and emitted `NewBlock`), a miner can propose a second, conflicting tenure-start block B for the same `CH` (different transactions/parent choice). `validate_tenure_change_payload` calls `get_last_globally_accepted_block(CH)`, which returns `None` (A is only locally accepted), so the `DuplicateBlockFound` rejection never fires, and B passes `check_proposal`. Because this duplicate check is documented as running *only* at proposal time and never again at validate-ok or at signing (`docs/signer-flows.md` section 7: "the duplicate check never runs again") [8](#0-7) , the signer can proceed to also sign block B if B's own pre-commit threshold is separately reached — resulting in the signer having signed two conflicting blocks for the same tenure, breaking the one-tenure-start invariant that the state machine (`docs/signer-flows.md` section 8, `parent_tenure_last_block` equality) relies on for consensus-visible agreement.

### Impact Explanation
This breaks the safety invariant "a signer signs at most one tenure-start block per tenure" — analogous to signing a conflicting/non-canonical block. If both A and B individually cross the 70% pre-commit threshold among different subsets of signers (plausible under normal miner retry behavior described in flows section 3, where the same proposal is resent until rejection weight accumulates), this can produce two divergent, signer-endorsed candidate chains rooted at the same tenure, i.e., a signer-level equivocation qualifying as Critical under "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
No majority collusion or key compromise is required — a single miner (or gossip of a re-proposed block) triggers the code path. The exact preconditions (locally-but-not-globally-accepted state, followed by a competing tenure-change proposal) are a normal, race-prone part of the block lifecycle documented in the flows: `approved_time`/`signed_self` are set well before `signed_group`/node-side global acceptance, giving a real window [9](#0-8) . Likelihood is bounded only by needing the v1 (pre-`GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`) protocol path to be active, which is a real, currently-supported configuration in this codebase.

### Recommendation
Update `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` (matching v2's fixed logic) instead of `get_last_globally_accepted_block`, so both locally- and globally-accepted blocks are treated as a prior commitment that blocks a competing tenure-change proposal.

### Proof of Concept
1. Run a signer set negotiated at protocol version < 2 (V1/local-state path).
2. Miner proposes tenure-start block A for consensus hash `CH`; enough signers (but not the global/node threshold) sign it so that at least this signer's `BlockInfo` for A reaches `LocallyAccepted` (`mark_locally_accepted`) without yet reaching `GloballyAccepted`.
3. Miner proposes a second, conflicting tenure-start block B for the same `CH` (e.g., different tx set/parent choice), with a valid tenure-change payload.
4. `SortitionsView::check_proposal` → `validate_tenure_change_payload` calls `signer_db.get_last_globally_accepted_block(CH)`, which returns `None` because A is only `LocallyAccepted`, so the `RejectReason::DuplicateBlockFound` check is skipped and B passes validation [4](#0-3) .
5. If B independently gathers its own pre-commit threshold, the signer ends up having signed two competing tenure-start blocks (A and B) for the same tenure.
