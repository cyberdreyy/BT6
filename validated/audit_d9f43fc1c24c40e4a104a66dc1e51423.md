### Title
Stale confirmations from removed multisig members are still counted toward the execution threshold - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`delete_member` (in `multisig2`) and the `DeleteKey` action (in `multisig`) only purge pending requests that were *created* by the removed member/key. They never scrub that member's stale confirmations from requests created by *other* members. `confirm()` counts `confirmations.len()` against `num_confirmations` without verifying every stored confirmer is still a current member, so a request can execute even though the number of confirmations from currently-valid members is below the configured threshold.

### Finding Description
When a member `M` confirms a request `R` created by another member (so `M` is not `R.member`/`R.signer_pk`), `M`'s account/key string is inserted into `self.confirmations[R]`. If the multisig later legitimately votes to remove `M` via `DeleteMember`/`DeleteKey`:

- `delete_member` (`multisig2/src/lib.rs:356-379`) filters `self.requests` for entries whose *creator* equals `M` and deletes only those requests plus their confirmation sets. It never inspects or cleans `confirmations` sets belonging to requests created by someone else where `M` was merely a confirmer.
- The equivalent `DeleteKey` handling in `multisig/src/lib.rs:198-216` has the identical gap (`filter(|(_k, r)| r.signer_pk == pk)` only matches the request creator).
- `current_member()` (`multisig2/src/lib.rs:321-339`) and `self.members` correctly reflect that `M` is no longer a member, and `M` can no longer call `confirm` again. But `M`'s previously recorded confirmation on `R` is never invalidated retroactively.
- `confirm()` (`multisig2/src/lib.rs:292-315`, `multisig/src/lib.rs:246-266`) simply does `confirmations.len() as u32 + 1 >= self.num_confirmations`, with no check that every entry in `confirmations` still corresponds to a member in `self.members`.

This breaks the intended custody binding: confirmations counted toward the threshold ≠ approvals from currently-live members. A request can therefore be executed with fewer genuine, currently-authorized approvals than `num_confirmations` requires.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." Any pending request (e.g., a `Transfer` moving NEAR out of the multisig account, an `AddKey`/`AddMember` granting a new signer, or a `DeployContract` upgrade) can be pushed to execution using a phantom confirmation from a member who has since been removed, meaning the multisig's core safety guarantee (`K`-of-`N` live approval) is silently violated. Funds can move, or privileged actions execute, without truly `K` current, authorized approvals.

### Likelihood Explanation
This requires no attacker privilege beyond what any legitimate multisig member already has as part of normal operation: (1) a member confirms a pending request created by another member, (2) the multisig later removes that member through an ordinary, properly-authorized `DeleteMember`/`DeleteKey` governance action (common when rotating signers), and (3) the original request (if still outstanding, e.g. blocked on other slow confirmers) is later pushed over threshold by a remaining member, unaware that one of the recorded confirmations belongs to a party no longer part of the multisig. This is a realistic sequence in normal multisig lifecycle management (member rotation while requests are in flight), not a contrived edge case.

### Recommendation
When deleting a member (`delete_member`/`DeleteKey`), also scan every pending request's confirmation set and strip out the departing member's entry (and re-check whether the request now falls below its previous confirmation progress). Alternatively, at confirm-time, validate that every string/key stored in a request's `confirmations` set is currently present in `self.members` before counting it toward `num_confirmations`, discarding stale entries lazily.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]` and `num_confirmations = 2`.
2. `A` calls `add_request` to create request `R1` (e.g., `Transfer` of NEAR to some receiver).
3. `B` calls `confirm(R1)` → `confirmations[R1] = {B}` (len 1, below threshold 2, so it's queued).
4. Separately, the multisig (via `A` and `C` confirming a `DeleteMember{member: B}` self-request) removes `B`. `delete_member` only deletes requests where `r.member == B` (i.e., requests `B` created) — `R1` was created by `A`, so `R1` and `confirmations[R1] = {B}` remain untouched. Members are now `[A, C]`.
5. `C` calls `confirm(R1)` → `confirmations[R1].len() + 1 == 2 >= num_confirmations(2)` → `R1` executes, transferring funds, even though only `C`'s confirmation (plus the stale `B` entry) exists among current members — effectively only 1 live confirmation (`C`, since `A` created it but didn't confirm) authorized the transfer instead of the required 2.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
