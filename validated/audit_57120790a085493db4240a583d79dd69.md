### Title
Stale message replay bypasses timestamp freshness check enabling repeated job re-triggering - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` only rejects a `webapicap.TriggerRequestPayload` if its `Timestamp` is older than `h.config.MaxAllowedMessageAgeSec`, but it does not track or reject previously-seen `msg.Body.MessageId`/signature/nonce combinations. Any signed trigger payload captured by an attacker can be resubmitted verbatim, repeatedly, as long as it is replayed inside the freshness window, causing the DON to be sent the exact same trigger request each time.

### Finding Description
In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` (lines 341-421) performs the following checks on an incoming legacy user message body decoded into `webapicap.TriggerRequestPayload`:
1. JSON-decodability check.
2. `payload.Timestamp == 0` check.
3. Freshness check: `if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` — rejects only messages *older* than the allowed age. [1](#0-0) 

After these checks pass, it builds a JSON-RPC request from the message and unconditionally stores/overwrites a callback keyed by `msg.Body.MessageId`, then forwards the request to every DON member: [2](#0-1) 

There is no de-duplication structure (no seen-message-ID cache, no nonce table) consulted before this send. The only interaction with `msg.Body.MessageId` is to overwrite any existing entry for that key in `savedCallbacks` — which does not block or detect resubmission, it merely lets the newest resubmission "win" the callback slot. Consequently, replaying the exact same signed payload (same `MessageId`, same `Timestamp`, same signature) at any point before `Timestamp + MaxAllowedMessageAgeSec` passes all three checks again and triggers another round of `don.SendToNode` calls to the DON members, i.e., another job-trigger fan-out to the workflow DON.

The entry point is `gateway.ProcessRequest` in `core/services/gateway/gateway.go`, which for legacy requests only calls `msg.Validate()` (structural/signature validation) before dispatching to `h.HandleLegacyUserMessage` — `msg.Validate()` does not track replay either (it operates only on the single message being validated). [3](#0-2) 

### Impact Explanation
An attacker who captures one valid signed `web_api_trigger` request (e.g., by observing network traffic, a log, or a previously-authorized single-use trigger) can resend it as many times as desired within the configured `MaxAllowedMessageAgeSec` window, causing the target workflow/job to be triggered multiple times without new authorization. This maps to Chainlink's "unauthorized job run" bounty impact class, since the credential holder is only supposed to authorize a single trigger execution per signed payload but can force repeated executions of the DON-side workflow.

### Likelihood Explanation
Exploitation requires only the ability to observe/capture one legitimate signed trigger message (no signing key needed, since it's a pure replay) and resend it to the gateway's user-facing HTTP endpoint within the freshness window (default relevant to `MaxAllowedMessageAgeSec`, e.g., commonly configured in the range of seconds). This is fully repeatable — the exact same message can be resent multiple times back-to-back until the timestamp ages out, and then a fresh capture repeats the cycle. No special privilege beyond capturing a single signed request is needed, matching the "unprivileged client/gateway request sender" threat model.

### Recommendation
Add replay protection in `HandleLegacyUserMessage` (or in `gateway.ProcessRequest` before dispatch) by tracking already-processed `msg.Body.MessageId` values (or a hash of `(Sender, MessageId, Timestamp, Signature)`) in a bounded/expiring cache (similar to the existing `savedCallbacks` pruning mechanism), and reject with a "duplicate message" error if the same MessageId/signature has already been accepted and forwarded within the freshness window, rather than silently overwriting the stored callback.

### Proof of Concept
1. In `core/services/gateway/handlers/capabilities/handler_test.go`, construct a valid signed `api.Message` wrapping a `webapicap.TriggerRequestPayload` with `Timestamp = now - (MaxAllowedMessageAgeSec/2)` (well inside the freshness window) and a fixed `MessageId`.
2. Call `handler.HandleLegacyUserMessage(ctx, msg, callback1)` and assert:
   - `don.SendToNode` is invoked for each DON member (verify via mock `handlers.DON`).
   - No error is returned.
3. Immediately call `handler.HandleLegacyUserMessage(ctx, msg, callback2)` again with the identical payload/signature/timestamp/MessageId (simulating replay before expiry).
4. Assert (current behavior, demonstrating the bug): `don.SendToNode` is invoked a second time with the same trigger payload — i.e., the mock DON records two identical trigger sends — proving the message was reprocessed rather than rejected as a duplicate.
5. Expected behavior after fix: the second call should return an error/duplicate-message response via `callback2.SendResponse`, and `don.SendToNode` should not be called a second time for the same `MessageId`/signature.
