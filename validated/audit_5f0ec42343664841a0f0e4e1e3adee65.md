### Title
Already-claimed instant-withdraw receipts are never removed from `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, so default finalization counts paid-out funds as prefunded reserve and inflates recovery basis — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` zeroes the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch ledgers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. When the same epoch later defaults and `finalizeDefaultRecovery` runs with `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` treat those stale entries as still-outstanding basis backed by strategy-held underlyings — funds that were already transferred to claimants. Recovery is computed over phantom basis, the reserve is diluted/short, and late claimants are underpaid or frozen.

### Finding Description
In `IdleCreditVault`:

- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (IdleCreditVault.sol:371-372).
- `claimInstantWithdrawRequest` burns the aggregate receipt and pays funded underlyings, but leaves both per-epoch mappings untouched (IdleCreditVault.sol:387-392).
- On default, `finalizeDefaultRecovery` computes `pendingBasis = defaultPendingClaimBasis()`, which adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (IdleCreditVault.sol:644-648), and adds `_defaultPrefundedInstantReserve() = instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` as "already-held" reserve (IdleCreditVault.sol:685, 716-722). Both include receipts already claimed and paid out earlier in the same epoch.
- `defaultInstantWithdrawsFinalized` is set true in that case (IdleCreditVault.sol:696), and `_claimDefaultedInstantWithdrawRequest` will also attempt to pay every user's stale per-epoch entry from `defaultRecoveryReserve` (IdleCreditVault.sol:842-855).

The bug class analog: the ClamAV 7z OOB write is "data written/counted outside its valid boundary"; here the protocol writes instant-receipt basis into an epoch ledger with no boundary clearing on the payout path, so later accounting reads outside the set of live claims.

### Impact Explanation
Direct loss with a broken "one receipt one payout" / solvency invariant:

1. Every underlying already paid to claimed instant withdrawers is counted a second time as `prefundedReserve`, inflating `recoveryPrice` over a `totalBasis` that includes dead claims (IdleCreditVault.sol:686-688). The recorded `defaultRecoveryReserve` exceeds actually-held tokens by the claimed amount.
2. Claims proceed at `claimBasis * defaultRecoveryPrice` but the reserve cannot cover all of them: the last claimants hit an underflowing `safeTransfer` in `_transferDefaultRecovery` and are permanently frozen, and/or all claimants receive a diluted haircut.
3. Loss is quantified: phantom basis = sum of instant receipts claimed-and-paid in the defaulted epoch while at least one instant request remained unfunded (`pendingInstantWithdraws != 0`).

Existing guards do not stop this: the funded-claim path simply never updates the per-epoch mappings, and `_defaultPrefundedInstantReserve` has no way to distinguish paid from unpaid epoch claims.

### Likelihood Explanation
Requires a specific sequence but only unprivileged actions plus honest privileged calls:

- Epoch N running with instant withdrawals enabled; attacker (any tranche holder / KYC-passing lender) requests instant withdraw X via `IdleCDOEpochVariant.requestWithdraw` when APR drops (`instantWithdrawAprDelta`), waits `instantWithdrawDelay`, and claims X via `claimInstantWithdrawRequest` once `getInstantWithdrawFunds` funds it. Per-epoch entries for X remain.
- Another user's instant request stays unfunded so `pendingInstantWithdraws != 0`, then the borrower fails to repay (honest default or `stopEpochWithDuration` loss path) and honest manager/owner calls `finalizeDefaultRecovery`. Stale X is counted as reserve automatically.
- No privileged collusion, no oracle, no mock; works in fixed-APR + instant-withdraw mode (the standard epoch variant, not prefunded/programmable).

Likelihood is moderate: it needs a partial instant-queue funding followed by a same-epoch default, which is plausible exactly in stressed conditions where defaults occur.

### Recommendation
Clear the per-epoch instant ledgers on the funded claim path and keep the epoch claim total consistent:

- In `claimInstantWithdrawRequest`, before paying, iterate/derive the user's per-epoch entries (or track the current open epoch) and subtract the claimed amount from `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`.
- Alternatively, make `_defaultPrefundedInstantReserve` and `defaultPendingClaimBasis` rely on a separate "funded-but-unclaimed" counter maintained by `collectInstantWithdrawFunds` rather than deriving it from `instantWithdrawClaimsByEpoch`.
- Reconcile `pendingInstantWithdraws`, `instantWithdrawClaimsByEpoch`, and actual token balance in `finalizeDefaultRecovery` (cap `prefundedReserve` at `underlyingToken.balanceOf(this)` minus other reserves).

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol` style helpers; attacker is a normal lender):

```solidity
function testClaimedInstantReceiptCountedAsDefaultReserve() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18); // epoch 1 buffer
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    // attacker and victim deposit AA
    address attacker = makeAddr('attacker');
    address victim   = makeAddr('victim');
    uint256 ta = _depositWithUser(attacker, 100e6);
    uint256 tv = _depositWithUser(victim, 100e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();            // epoch 1 running
    _stopCurrentEpochWithApr(1e18);   // APR drop -> instant mode in epoch 2 buffer

    // both request instant withdraws during buffer
    vm.prank(attacker); cdoEpoch.requestWithdraw(ta, address(AAtranche));
    vm.prank(victim);   cdoEpoch.requestWithdraw(tv, address(AAtranche));

    vm.prank(manager);
    cdoEpoch.startEpoch();
    skip(101);

    // fund only attacker's instant request partially, attacker claims at par
    uint256 pending = IdleCreditVault(address(strategy)).pendingInstantWithdraws();
    // manager collects only enough for attacker's share
    // (borrower/CDO funds it honestly)
    ...
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest(); // paid X at par

    // stale per-epoch entries remain:
    uint256 e = IdleCreditVault(address(strategy)).epochNumber();
    assertGt(IdleCreditVault(address(strategy)).instantWithdrawsRequestsByEpoch(attacker, e), 0);

    // borrower cannot fully repay -> default, then finalizeDefaultRecovery
    _checkDefault(); // helper: warp past end, stopEpoch triggers default
    // honest owner finalizes recovery
    ...
    // instantWithdrawClaimsByEpoch[e] still includes attacker's paid X,
    // so _defaultPrefundedInstantReserve() over-counts reserve by X
    // and totalBasis includes X -> victim's recovery is diluted / last claims revert.
}
```

Caveat: I could not exhaustively verify whether `_transfer` restrictions on strategy tokens affect a secondary double-claim path (the stale-entry claim in `_claimDefaultedInstantWithdrawRequest` burns `instantWithdrawsRequests[_user] -= claimBasis`, which underflows for an attacker whose aggregate is already zero — so the second payout reverts). The primary insolvency/dilution impact stands regardless, because `finalizeDefaultRecovery` inflates basis and phantom reserve without any second claim being needed.
