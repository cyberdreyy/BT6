### Title
Stale rejection weight from a signer who later accepts is never cleared, permanently inflating `total_weight_rejected` on the miner's `StackerDBListener` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::handle_signer_messages` maintains two independent, additive-only weight counters per proposed block, `total_weight_approved` and `total_weight_rejected`, but never removes a signer's weight from `total_weight_rejected` once that signer subsequently sends an `Accepted` response for the same block. Since a signer legitimately can re-evaluate a rejected block into acceptance (`LocallyRejected -> LocallyAccepted: re-evaluated`, documented in `docs/signer-flows.md:144-145`), the same signer's weight can end up counted in both tallies simultaneously, and the stale rejection weight is never retracted.

### Finding Description
Rejection handling adds weight unconditionally the first time a slot is seen: [1](#0-0) 

Acceptance handling adds weight keyed only on `gathered_signatures`, with no check against (and no adjustment of) `total_weight_rejected`: [2](#0-1) [3](#0-2) 

There is no code path anywhere in the file (confirmed via search) that subtracts from `total_weight_rejected` when the same slot later accepts. `reset_rejections` only zeroes the whole counter on a resend timeout, re-seeding `responded_signers` from `gathered_signatures`—it does not handle the in-place transition from reject to accept on the *same* proposal round: [4](#0-3) 

Sequence that breaks the equality between "weight recorded as rejecting" and "signers currently rejecting":
1. Signer S (weight w) sends `Rejected` for block B → `total_weight_rejected += w`, `responded_signers.insert(S)`.
2. S locally re-evaluates and now signs B, sending `Accepted` → `gathered_signatures` does not yet contain S, so `total_weight_approved += w` is applied. `total_weight_rejected` still includes S's `w` from step 1; it is never decremented.
3. From this point on, `total_weight_rejected` (as tracked by the miner's coordinator) permanently over-counts by `w`, even though S is now an approver, for as long as this `BlockStatus` entry lives (i.e., until the proposal round ends via accept/reject/timeout in `get_block_status`, `signer_coordinator.rs:509-545`).

This breaks the required equality "aggregated-weight vs verified-accepts/rejects": the coordinator's rejection-weight accounting no longer reflects the actual current set of rejecting signers, because a signer's most recent verdict does not retract its earlier, superseded verdict from the opposing counter.

### Impact Explanation
The miner's `SignerCoordinator::get_block_status`/`get_block_status` loop uses `total_weight_rejected` to decide the block is dead: [5](#0-4) 
and `total_weight_approved` to decide it is accepted: [6](#0-5) 

Because `total_weight_rejected` can be inflated by weight belonging to signers who have since switched to accepting, the sum `total_weight_approved + total_weight_rejected` can legitimately exceed `total_weight`, and in the case where enough signers flip from reject to accept without the reset path being triggered, the rejection-count-derived "blocking minority" logic (`> self.total_weight - self.weight_threshold`) can fire on stale data — causing the miner to declare a block `SignersRejected` (via `NakamotoNodeError::SignersRejected`) even though the currently-live rejecting weight is below the blocking-minority threshold and the block is in fact converging toward 70% approval. This is a liveness-affecting mis-accounting reachable purely by miner/signer message flow (a signer legitimately re-evaluating its vote, no majority collusion needed), not a signature-validity or double-sign issue, so severity is best characterized as a liveness/availability defect in the miner's local weight tally rather than a Critical/High per the strict impact list, but it does directly violate the "aggregated-weight vs verified-accepts" equality called out in the validation rules.

### Likelihood Explanation
The trigger condition — a signer rejecting and then, within the same coordinator polling round (before `reset_rejections`/timeout fires), accepting the same block — is explicitly a documented, intended signer behavior (`should_reevaluate_reject_reason`, `LocallyRejected --> LocallyAccepted: re-evaluated` in `docs/signer-flows.md`). It requires no malicious majority, no other signer's key, and no privileged access — a single normally-operating signer that re-evaluates its vote (e.g., because a previously-conflicting sibling went stale, per `stale_sibling_replaced_when_canonical_tip_below` test scenario) is sufficient to produce the stale weight. This makes the condition realistically reachable, though it needs the timing window where the flip happens before any reset/timeout clears the counters.

### Recommendation
When processing a `BlockResponse::Accepted` for a slot that is already present in the rejection accounting (tracked separately, or by keeping a per-slot last-verdict map instead of two independent counters), retract that slot's weight from `total_weight_rejected` before/while adding it to `total_weight_approved` (and symmetrically for an accept-then-reject flip, if that is intended to be honored, though the code comments suggest approvals are meant to be sticky). At minimum, track weight per slot with the *current* verdict rather than accumulating both counters independently and unconditionally, so `total_weight_approved + total_weight_rejected` never double-counts a single signer's weight across a flipped vote.

### Proof of Concept
1. Configure a miner with `SignerCoordinator`/`StackerDBListener` tracking `BlockStatus` for proposal B, with signer S having weight `w`, and total blocking-minority threshold `M = total_weight - weight_threshold`.
2. Have S send `BlockResponse::Rejected` for B. `total_weight_rejected = w`. (Uses the path at `stackerdb_listener.rs:486-518`.)
3. Before any timeout/resend clears rejections, have S re-evaluate and send `BlockResponse::Accepted` for B (a legitimate signer transition per `docs/signer-flows.md` state diagram). `total_weight_approved` increases by `w` per `stackerdb_listener.rs:443-465`; `total_weight_rejected` remains `w`, uncorrected.
4. If enough other signers' rejections bring `total_weight_rejected` (still including S's stale `w`) above `M`, `get_block_status` (`signer_coordinator.rs:509-519`) declares the block rejected via `NakamotoNodeError::SignersRejected`, even though S — counted in both tallies — is a live approver and the true rejecting weight (excluding S) may be below `M`.

This proof of concept could not be run in an actual test harness within this analysis; it is derived directly from tracing the counter-update code paths described above. A background Devin session with repo access could add a unit/integration test in `stacks-node/src/tests/signer/v0/` reproducing steps 1–4 to confirm the double-count empirically.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
