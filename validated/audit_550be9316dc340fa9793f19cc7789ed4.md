### Title
Mid-epoch deposits leave `trancheAPRSplitRatio` stale, letting a depositor mint discounted shares and capture the other tranche's epoch interest - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`depositDuringEpoch` mints tranche tokens at a discounted price and credits the deposit's expected interest to `expectedEpochInterest`, but never calls `_updateSplitRatio`. Every other NAV-changing entry point (`_deposit`, `_depositFees`, fee minting in `_stopEpoch`) refreshes `trancheAPRSplitRatio` via `_updateSplitRatio(_getAARatio(true))`. Because the stale ratio is used twice — once to compute the minter's discounted share count (`trancheInterest`) and again at `stopEpoch` inside `_virtualPriceAux` to split the enlarged epoch interest — an unprivileged KYC'd attacker can deposit into the tranche whose configured interest share exceeds its post-deposit NAV weight and extract yield belonging to the opposing tranche.

### Finding Description
The bug class in the external report is a boundary error on attacker-controlled input: a value is written outside the bounds it was supposed to stay within. The vault analog is `depositDuringEpoch` writing new NAV into `lastNAVAA`/`lastNAVBB` and new obligations into `expectedEpochInterest` while leaving the interest-split boundary (`trancheAPRSplitRatio`) at its pre-deposit value.

In `IdleCDO._deposit`, after minting, the split ratio is refreshed so subsequent yield accounting reflects the new NAV weights: [1](#0-0) 

`depositDuringEpoch` performs the same NAV mutation through `_mintShares` and increases `expectedEpochInterest`, but has no `_updateSplitRatio` call: [2](#0-1) 

The minted amount is itself computed with the stale ratio via `_calcTrancheInterestShare`, so an over-favored tranche both receives too many shares (bigger `trancheInterest` discount) and is allocated too much of the epoch interest at settlement: [3](#0-2) 

At `stopEpoch`, `_updateAccounting` → `_virtualPriceAux` splits `totalGain` by `trancheAPRSplitRatio` — still the pre-deposit value: [4](#0-3) 

Broken invariant: fair mint/burn — shares are minted at a price that does not reflect the depositor's true end-of-epoch entitlement, and epoch interest is allocated by stale weights.

### Impact Explanation
Direct theft of yield between tranche classes. When `trancheAPRSplitRatio` over-weights tranche X relative to its NAV share, an attacker deposits into X mid-epoch and receives (a) more minted shares than warranted, because `trancheInterest` in the numerator is inflated by the stale ratio, and (b) an oversized share of the epoch interest on the now-larger pool at `stopEpoch`. The excess is paid from gross `expectedEpochInterest`, i.e. from the opposing tranche's entitlement. With a stale AA ratio of e.g. 90% while AA is ~50% of NAV, a BB-side attacker captures roughly double their NAV-proportional yield; losses scale with pool TVL and epoch APR and are bounded only by `_guarded` deposit limits and the epoch duration.

### Likelihood Explanation
Requirements are all satisfiable by an unprivileged KYC-passing lender:

- `isDepositDuringEpochDisabled == false` (manager-enabled feature; tested extensively in `test/foundry/IdleCreditVault.t.sol`).
- `isAYSActive == false` and `isProgrammableBorrower == false` (checked at lines 661-665), which is exactly the non-AYS mode where `trancheAPRSplitRatio` tracks NAV ratio.
- A running epoch (`isEpochRunning`, `block.timestamp < epochEndDate`) and nonzero target tranche supply — trivially met in the normal epoch lifecycle.
- A stale ratio favorable to one tranche, which occurs naturally whenever the last ratio checkpoint (a deposit, fee mint, or harvest) left AA/BB weights different from current NAV composition — e.g., after a large withdraw request on one tranche (`requestWithdraw` decreases NAV via `_withdrawOps` without re-syncing the ratio for interest-split purposes).

The attacker sequences around honest manager calls (`startEpoch`, `stopEpoch`); no privileged role is the attacker.

### Recommendation
After `_mintShares` in `depositDuringEpoch`, call `_updateSplitRatio(_getAARatio(true))` so the post-deposit NAV weights govern the remaining epoch's interest split, and recompute the discounted mint using the refreshed ratio (or compute `trancheInterest`/`trancheExpected` against the post-deposit ratio explicitly). Alternatively, include the deposit's pro-rata interest directly in the claim and keep it out of the ratio-based split. Add a regression test that a mid-epoch deposit into the minority-share tranche leaves both tranches' end-of-epoch per-unit yields equal to their configured split.

### Proof of Concept
Foundry-style fork test sketch (extend the existing `TestIdleCreditVault` harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testDepositDuringEpochStaleSplitRatioExtractsYield() external {
    // Non-AYS mode required (depositDuringEpoch reverts when AYS active)
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);

    // Setup: AA-heavy pool so trancheAPRSplitRatio ~ AA NAV fraction
    uint256 aaDeposit = 9_000 * ONE_SCALE;
    uint256 bbDeposit = 1_000 * ONE_SCALE;
    idleCDO.depositAA(aaDeposit);   // ratio -> ~90% AA
    idleCDO.depositBB(bbDeposit);
    _startEpochAndCheckPrices(0);   // 10% apr epoch

    uint256 staleRatio = cdoEpoch.trancheAPRSplitRatio();

    // Victim adds BB normally before epoch start would raise BB share;
    // instead attacker waits until mid-epoch so ratio is NOT refreshed.
    vm.warp(cdoEpoch.epochEndDate() - cdoEpoch.epochDuration() / 2);

    // Now NAV composition has drifted (interest accrual is only in
    // expectedEpochInterest, NAVs unchanged) but any prior BB-heavy
    // checkpoint works symmetrically; here we exploit the fact that
    // the attacker's deposit does not refresh the ratio.
    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    address attacker = makeAddr('attacker');
    uint256 atkAmt = 1_000 * ONE_SCALE;
    deal(defaultUnderlying, attacker, atkAmt);
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), atkAmt);
    uint256 minted = cdoEpoch.depositDuringEpoch(atkAmt, address(BBtranche));
    vm.stopPrank();

    // ratio must not have moved — this is the bug
    assertEq(cdoEpoch.trancheAPRSplitRatio(), staleRatio, "ratio refreshed");

    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Attacker's per-unit BB yield exceeds the configured BB share:
    // BB captured (FULL_ALLOC - staleRatio) of the *enlarged* interest
    // over a small BB NAV, paid by AA holders.
    uint256 bbPrice = cdoEpoch.virtualPrice(address(BBtranche));
    uint256 atkValue = minted * bbPrice / ONE_TRANCHE_TOKEN;
    // Fair entitlement = principal + BB-share of interest on atkAmt/2 epoch
    // computed with the post-deposit (refreshed) weights.
    assertGt(atkValue, _fairBBEntitlement(atkAmt), "attacker overpaid");
}
```

The key assertions are reproducible from code inspection: `depositDuringEpoch` (lines 656-733) contains no `_updateSplitRatio`, while the mint formula at line 724 and the gain split in `_virtualPriceAux` both consume the stale `trancheAPRSplitRatio`. Exact quantification of the stolen amount depends on live ratio/TVL and should be confirmed by running the harness on a fork; the directional yield transfer is guaranteed whenever the depositing tranche's ratio share exceeds its post-deposit NAV weight.

Note: I could not fully verify whether any recently added guard (e.g., inside `_mintShares` overrides or `_getAARatio`) compensates for the missing ratio refresh; the indexed code shows none. If maintainers intentionally keep the epoch's ratio frozen, the `trancheInterest` term in the mint formula still produces an over-mint for the favored tranche and should be corrected regardless.
