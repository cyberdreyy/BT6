### Title
Unbounded per-notification serialization cost in `accountSubscribe` for large attacker-controlled accounts - ([File: rpc/src/rpc_subscriptions.rs, account-decoder/src/lib.rs])

### Finding Description
`accountSubscribe` registers an `AccountSubscriptionParams` with no data-size restriction [1](#0-0) . Every time `RpcSubscriptions::notify_watchers` runs (invoked once per bank/gossip commitment update, i.e. up to once per slot) it iterates all account-commitment watchers and, for each one whose `last_modified_slot` changed, calls `filter_account_result`, which unconditionally calls `encode_ui_account(&params.pubkey, &account, params.encoding, None, None)` on the account's full data [2](#0-1) , driven from the per-slot `notify_watchers` dispatch [3](#0-2) .

`encode_ui_account` has no size cap for `Base64`/`Base64Zstd` encodings: it always slices/copies and base64-encodes (or zstd-compresses + base64-encodes) the entire account data buffer [4](#0-3) . Only the legacy `Binary`/`Base58` paths reject data over 128 bytes (`MAX_BASE58_BYTES`) by returning an error string instead of encoding it [5](#0-4) , but this guard does not exist for base64 encodings, which is the encoding most clients actually use.

An unprivileged attacker can: (1) create one account sized up to `MAX_PERMITTED_DATA_LENGTH` (system/BPF-loader accounts can be extended up to this limit), (2) issue a single `accountSubscribe` websocket call with `encoding: base64` (or `base64+zstd`) for that pubkey, and (3) send one lamport-mutating transaction per slot (well within the `CLUSTER_SLOT_TIME_TARGET / 2` cadence limit) to force `last_modified_slot` to change every notification cycle. Because there is no per-subscription cost/size budget enforced anywhere between `filter_account_result` and `encode_ui_account`, the validator's `notify_watchers` thread pool spends CPU/memory proportional to the attacker-chosen account size on every commitment update, rather than a bounded amount.

### Impact Explanation
This is an "unbounded cost for a single low-rate call" scenario explicitly listed as in-scope: a single websocket subscription combined with normal-cadence transactions causes the validator's notification path (`notify_watchers`, which runs on the shared rayon-parallel notification thread pool used by all other subscriptions) to repeatedly allocate and encode large buffers, increasing CPU and memory pressure and notification latency for the whole pubsub service in proportion to attacker-chosen account size, not a fixed budget.

### Likelihood Explanation
Feasible with a single unprivileged client: creating a large account and one subscription requires no special privileges, and updating lamports once per slot is within the allowed one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` cadence. The behavior is deterministic and repeatable every commitment update as long as the subscription remains open and the account keeps changing.

### Recommendation
Enforce a maximum account-data size (or a data-slice-equivalent hard cap) before calling `encode_ui_account` for `Base64`/`Base64Zstd`/`JsonParsed` in `filter_account_result` and the analogous program/account RPC/pubsub encode paths, mirroring the existing `MAX_BASE58_BYTES` behavior in `encode_bs58`; alternatively require/force a `dataSlice` for large accounts or return an error once account size exceeds a configurable notification threshold.

### Proof of Concept
Rust integration test plan (extending the existing `rpc/src/rpc_subscriptions.rs` account subscription tests, e.g. near [6](#0-5) ):
1. Create accounts of increasing `data_len` (e.g. 1 KiB, 1 MiB, 10 MiB) owned by system program, each subscribed via `account_subscribe` with `encoding: Base64`.
2. For each size, mutate the account's lamports once, call `subscriptions.notify_subscribers(commitment_slots)`, and measure wall-clock time and allocated bytes inside `RpcSubscriptions::notify_watchers` (via `Measure::start("notify_watchers")` already present) per notification.
3. Assert that `notify_watchers` time/memory scales linearly with `data_len` with no upper bound, and that no error/truncation occurs for `Base64` encoding (unlike the `Binary`/`Base58` case which already returns `"error: data too large for bs58 encoding"` per the existing test at line 1351).
4. Confirm the fix caps cost by asserting an error or truncated response is returned once `data_len` exceeds the proposed threshold.

    params: &AccountSubscriptionParams,
    last_notified_slot: Slot,
    bank: Arc<Bank>,
) -> (Option<UiAccount>, Slot) {
    // If the account is not found, `last_modified_slot` will default to zero and
    // we will notify clients that the account no longer exists if we haven't already
    let (account, last_modified_slot) = result.unwrap_or_default();

    // If last_modified_slot < last_notified_slot this means that we last notified for a fork
    // and should notify that the account state has been reverted.
    let account = (last_modified_slot != last_notified_slot).then(|| {
        if is_known_spl_token_id(account.owner())
            && params.encoding == UiAccountEncoding::JsonParsed

            get_parsed_token_account(&bank, &params.pubkey, account, None)
        } else {
            encode_ui_account(&params.pubkey, &account, params.encoding, None, None)
        }
    });
    (account, last_modified_slot)
}

pub const MAX_BASE58_BYTES: usize = 128;

fn encode_bs58<T: ReadableAccount>(
    account: &T,
    data_slice_config: Option<UiDataSliceConfig>,
) -> String {
    let slice = slice_data(account.data(), data_slice_config);
    if slice.len() <= MAX_BASE58_BYTES {
        bs58::encode(slice).into_string()
    } else {
        "error: data too large for bs58 encoding".to_string()
    }
}
