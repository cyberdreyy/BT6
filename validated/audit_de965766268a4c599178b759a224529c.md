### Title
Cache-key collision in `handler.savedCallbacks` allows cross-user response hijacking via attacker-chosen `MessageId` - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The web-API-trigger callback cache in `handler.HandleLegacyUserMessage`/`handleWebAPITriggerMessage` is keyed only by `msg.Body.MessageId`, a value fully controlled by the requesting client (it is copied verbatim from the JSON-RPC request `ID` in `ValidatedMessageFromReq`). Any signed gateway client can choose the same `MessageId` as another (in-flight or predictable) request, overwrite the shared `savedCallbacks` map entry, and cause the DON's verified response meant for one user's request to be delivered through the wrong stored callback.

### Finding Description
`NewHandler` builds a `handler` with `savedCallbacks map[string]*savedCallback` keyed purely by string `MessageId`: [1](#0-0) 

When a user submits a `web_api_trigger` request, `HandleLegacyUserMessage` unconditionally stores/overwrites the entry keyed by `msg.Body.MessageId` with no check for a pre-existing entry and no binding to the request's signer: [2](#0-1) 

`msg.Body.MessageId` is populated directly from the caller-supplied JSON-RPC request `ID` with no uniqueness, randomness, or per-sender scoping enforced: [3](#0-2) 

Later, when a DON node responds, `handleWebAPITriggerMessage` looks the callback up **solely by `MessageId`**, deletes it, and forwards whatever response is found to that callback: [4](#0-3) 

Because the map key has no sender/receiver component, two different callers (a legitimate victim and an attacker) that happen to use the same `MessageId` collide: whichever caller's `HandleLegacyUserMessage` call executes last overwrites the map entry, so the DON response destined for the first caller is instead delivered to whichever `Callback` currently occupies that slot. The codebase's own `RequestCache` (used elsewhere) demonstrates the correct pattern, keying by a composite `globalId{sender, id}` and rejecting duplicate `(sender, id)` pairs: [5](#0-4) 

`handler.go`'s `savedCallbacks` cache does not use this pattern, so the DON-side signature check on the *node* message (`msg.Body.Sender != nodeAddr` in `HandleNodeMessage`) only proves the message came from a legitimate DON node — it does nothing to bind that node response to the correct originating user request, since the lookup key (`MessageId`) was chosen by an untrusted client in the first place.

Exploit flow:
1. Attacker (any address that can sign gateway messages, no privilege required) submits a `web_api_trigger` `HandleLegacyUserMessage` request using a `MessageId` equal to one used (or about to be used, since `MessageId` generation for web API triggers can be deterministic — see `messageID()` in `core/services/workflows/syncer/v2/fetcher_test.go`) by a legitimate victim request.
2. Whichever of the two `HandleLegacyUserMessage` calls executes second overwrites `savedCallbacks[MessageId]`, silently replacing the pending callback.
3. When the DON later returns its (still correctly-signed) response for the *original* request, `handleWebAPITriggerMessage` delivers it to whatever callback currently occupies the slot — the wrong user's HTTP response channel.
4. This produces cross-user response confusion: either a victim receives a response actually generated from the attacker's own attacker-controlled trigger request content, or the attacker receives the victim's response data. Either direction breaks the "only DON-verified responses may populate the cache, keyed to their request" invariant, since the *keying* itself is attacker-influenceable, not the DON verification.

### Impact Explanation
An attacker can cause a legitimate user's HTTP-triggered workflow call to receive a response body that actually originated from a completely different (attacker-authored) trigger request, or cause a victim's DON-verified response to be exfiltrated to the attacker. Where this response data flows into oracle/report logic downstream, this matches the "misreporting of prices and/or data: attacker-controlled oracle job input/output reported on-chain" impact class, since the delivered payload is not guaranteed to correspond to the requester's own submitted request.

### Likelihood Explanation
No special privilege is needed beyond the ability to sign and send a gateway `web_api_trigger` message (any EOA holder). The main precondition is a `MessageId` collision with a legitimate in-flight request; this is more exploitable if `MessageId` values are predictable/deterministic (as seen with the `messageID()` helper pattern used elsewhere in the codebase for similarly-shaped web-API-trigger flows) or if the attacker races many candidate IDs against known workflow trigger windows. The lack of a duplicate/ownership check in `HandleLegacyUserMessage` (unlike the sibling `RequestCache` which explicitly rejects duplicate `(sender, id)` pairs) makes the race trivially repeatable.

### Recommendation
Key `savedCallbacks` by a composite of `(sender, MessageId)` (mirroring `common.RequestCache`'s `globalId`) instead of `MessageId` alone, and reject/skip insertion if an entry for that key already exists rather than silently overwriting it. Additionally, bind the response lookup in `handleWebAPITriggerMessage` to the same composite key so a DON response can only be routed back to the callback registered by the same original sender.

### Proof of Concept
Go handler-level test plan (in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` via `NewHandler` with a mock `handlers.DON`.
2. Craft `victimMsg` with `Body.MessageId = "shared-id"`, signed by `victimKey`, and call `h.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`; assert `savedCallbacks["shared-id"]` is `victimCallback`.
3. Craft `attackerMsg` with the same `Body.MessageId = "shared-id"`, signed by a different `attackerKey`, and call `h.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)`; assert `savedCallbacks["shared-id"]` is now overwritten to `attackerCallback` (no error returned, no duplicate check).
4. Simulate the DON node responding to the victim's original request: build a signed `api.Message` with `Body.MessageId = "shared-id"` and `Body.Method = MethodWebAPITrigger`, and call `h.HandleNodeMessage(ctx, resp, nodeAddr)`.
5. Assert that `attackerCallback.SendResponse` (not `victimCallback.SendResponse`) is invoked, proving the victim's DON-verified response was routed to the attacker's callback due to the `MessageId`-only cache key collision.
6. (Optional) Reverse the order to show the attacker can also receive a response derived from the victim's request, or the victim can be handed the attacker-triggered response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
