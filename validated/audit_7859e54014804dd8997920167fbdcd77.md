### Title
Unauthenticated cross-job pipeline run resumption via unvalidated `runID` - ([File: core/web/pipeline_runs_controller.go])

### Summary
The reported bug class (a mutation endpoint accepts a target identifier from the request but never verifies that identifier actually belongs to the calling principal, letting one actor "update" a record they don't own) has a concrete analog in `PipelineRunsController.Resume`.

### Finding Description
`Resume` is documented as `PATCH <application>/jobs/:ID/runs/:runID`, implying the pipeline run `:runID` should be scoped to job `:ID`. In the implementation, however, `c.Param("ID")` (the job ID) is never read or validated — only `c.Param("runID")` is parsed and passed straight to `prc.App.ResumeJobV2`: [1](#0-0) 

`ResumeJobV2` simply forwards to the pipeline runner's `ResumeRun(ctx, taskID, ...)`, which looks up and resumes whatever task run matches that UUID, with no ownership/ACL check tying the task to the authenticated caller, their external-initiator record, or the job path segment: [2](#0-1) [3](#0-2) 

Authentication for this class of route can be satisfied by `AuthenticateExternalInitiator`, which authenticates a caller against one specific `ExternalInitiator` record (looked up by its own `AccessKey`/`Secret`) but then grants a generic `run`-role `SessionUser`, with no scoping information tying that principal to a specific job or set of runs: [4](#0-3) 

Because the handler ignores the job-ID path parameter and performs no check that the resolved `runID` (task UUID) belongs to a run created for the job/external-initiator identified in the URL or by the caller's own credentials, any principal holding valid `run`-role credentials for *any* webhook job can resume a pending task belonging to a *different* job/owner, provided they know or can obtain that task's UUID (e.g., leaked via logs, shared tooling, or another party's webhook response).

### Impact Explanation
Resuming a task run supplies attacker-controlled `value`/`error` results (`pipeline.ResumeRequest` -> `ToResult()`) that are injected into another user's pipeline execution, potentially causing that pipeline to complete with falsified data, trigger downstream on-chain transactions, or corrupt/finish another owner's run out of band. This is a cross-owner mutation on a resource (a pipeline run) that should be scoped to the specific webhook job / external initiator that created it, matching the pattern of the reported bug class (unauthorized submission update via missing ownership check).

### Likelihood Explanation
Exploitation requires: (1) any valid `run`-role credential (an external initiator token, or an API user/token with at least run role), and (2) knowledge of a target task's UUID. The UUID is not guessable, and the audit event name `UnauthedRunResumed` suggests the team is already aware this action lacks fine-grained per-run authorization: [5](#0-4) 

This mitigates but does not eliminate risk — UUIDs can leak through the calling webhook's own response/callback flow, shared logging, or multi-tenant integrations where several webhooks are configured with a shared external initiator.

### Recommendation
- Validate that the `runID` in `PipelineRunsController.Resume` corresponds to a task run belonging to the job identified by `:ID`, rejecting the request if there is a mismatch.
- When authenticated via `AuthenticateExternalInitiator`, additionally verify that the resolved `ExternalInitiator` is associated with the specific job/run being resumed (not just that some external initiator credential was valid).
- Consider renaming/refactoring the `UnauthedRunResumed` audit path to make explicit that this endpoint intentionally has weaker authorization, and add stronger scoping checks or a per-run resume token instead of relying solely on the UUID's unguessability.

### Proof of Concept
1. Attacker holds valid `run`-role credentials for `externalInitiatorA` (webhook job A).
2. Attacker obtains the task-run UUID for a pending suspended run belonging to job B (e.g., leaked through shared infrastructure/log aggregation).
3. Attacker sends `PATCH /v2/jobs/A/runs/<jobB-taskUUID>` with a crafted `pipeline.ResumeRequest` body, authenticating with `externalInitiatorA`'s access key/secret headers.
4. `Resume` ignores the job ID mismatch and calls `ResumeJobV2` with the supplied UUID, causing job B's suspended pipeline run to complete using attacker-supplied data, as traced in [6](#0-5)  and [3](#0-2) .

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
```

```go
func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
```

```go
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
```
