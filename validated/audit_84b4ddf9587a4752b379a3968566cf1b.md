### Title
Async deposit refund/cancellation permanently reverts for blacklisted-token depositors due to no-op fallback in `_transferWithFallback` - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2` escrows deposit tokens (e.g. USDC) for async deposit requests and only returns them to the user via `cancelRequest`/`refundRequest`, both of which route through `_transferWithFallback`. This helper is meant to protect against a transfer failure by falling back to an alternate recipient, but when `request.receiver == requester` (the default, most common case created by the single-argument `requestDeposit`/`requestRedeem` wrappers), the fallback is skipped entirely and the function calls `token.safeTransfer` directly to the very same (potentially blacklisted) address, guaranteeing a revert. This mirrors the JOJO liquidation bug: escrowed value can only be returned to the affected user's own address, with no alternate recovery path, once that address is blacklisted by the token issuer.

### Finding Description
`_transferWithFallback` is used to protect refund/cancel/solve flows from failing when a receiver cannot accept tokens: [1](#0-0) 

However, its guard is: if `receiver == requester`, it skips the `trySafeTransfer` fallback attempt and immediately calls the (non-try) `token.safeTransfer(requester, amount)`. In the ordinary self-service flow, a user calls `requestDeposit(token, tokensIn, minUnitsOut, solverTip, deadline, maxPriceAge, isFixedPrice)` (the legacy overload), which sets both `request.user` and `request.receiver` to `msg.sender`: [2](#0-1) [3](#0-2) 

Tokens (e.g. USDC) are escrowed in the Provisioner via `token.safeTransferFrom(msg.sender, address(this), tokensIn)`. If the depositor is subsequently blacklisted by the deposit token's issuer (e.g. USDC) before the request is solved:
- `cancelRequest` computes `refundAmount` and calls `_clearHashAndTransferRefund(token, request, msg.sender, refundAmount, token)`, which calls `_transferWithFallback(token, requester, request.receiver, amount)` with `requester == receiver == msg.sender`. Because of the `receiver == requester` short-circuit, it directly calls `token.safeTransfer(requester, amount)`, which reverts against a blacklisted recipient: [4](#0-3) [5](#0-4) 
- `refundRequest` (used after deadline expiry, or by an authorized party) hits the same code path and reverts identically: [6](#0-5) 
- The async-deposit solve paths (`_solveDepositVaultAutoPrice`/`_solveDepositVaultFixedPrice`) also fall back to `_transferWithFallback(token, request.user, request.receiver, request.tokens)` for the "deadline passed" refund branch, with the same `receiver == requester` weakness: [7](#0-6) 

Since `asyncRequestHashes[hash]` is unset as an "Effect" *before* the reverting transfer executes, the whole transaction (including the hash-clearing effect) reverts atomically, so retrying produces the identical failure every time — there is no other function in `ProvisionerV2` that lets a user reclaim the specific escrowed deposit token once both the receiver and fallback-requester addresses collapse to the same blacklisted address.

This is the direct structural analog of the JOJO bug: value is only returned by transferring the underlying token straight to the affected user's wallet, with the codebase's own designed safety net (`_transferWithFallback`) neutralized in exactly the configuration that real users hit by default.

### Impact Explanation
Once a user is blacklisted by the deposit token (USDC is the most realistic bounty-relevant example), any USDC they have already escrowed into `ProvisionerV2` via an async deposit request becomes permanently unrecoverable through any self-service or solver-driven path: `cancelRequest`, `refundRequest`, and the deadline-passed refund branches of `solveRequestsVault`/`solveRequestsDirect` all revert identically. This is a freezing of user funds directly inside a deployed, bounty-listed contract (`ProvisionerV2`), consistent with a "temporary/permanent freeze of funds" bounty category.

### Likelihood Explanation
Requires: (1) a token with issuer-controlled blacklisting used as a deposit token in `ProvisionerV2` (USDC is the standard example and is a realistic supported asset), (2) the user creating an async deposit request via the default self-receiver flow (the common/legacy usage pattern), and (3) becoming blacklisted after escrowing funds but before the request is solved. All of these are ordinary, permissionless user actions requiring no privileged role, oracle manipulation, or MEV — only a compliance action by a third-party token issuer, which is the exact precondition class the referenced report is about.

### Recommendation
Do not special-case `receiver == requester` to skip the safe-fallback attempt; instead, always attempt `trySafeTransfer` to the receiver, and if that fails, either (a) leave the funds recoverable under a separate escrow claim path (e.g. re-set the request hash so it isn't destructively cleared until a successful transfer, or track an internal claimable balance the user can withdraw to a *different* address once un-blacklisted or via an alternate receiver), or (b) allow an authorized/admin path to redirect stuck refunds to a user-specified alternate address after the primary attempt fails, rather than making refund success solely conditional on transferring to the one address that is guaranteed to fail.

### Proof of Concept
1. Deploy `ProvisionerV2` wired to a mock USDC-like token implementing a `blacklist(address)`/`isBlacklisted` check that makes `transfer`/`transferFrom` revert for blacklisted addresses (mirrors real USDC `BlacklistablePausableFiatToken` behavior).
2. As `userA` (not blacklisted), call `requestDeposit(token, tokensIn, minUnitsOut, solverTip, deadline, maxPriceAge, false)` (legacy overload) — this sets `request.user == request.receiver == userA` and escrows `tokensIn` USDC into the Provisioner.
3. Blacklist `userA` on the mock USDC contract.
4. Advance time past `deadline`, then call `refundRequest(token, request)` from any address — assert it reverts (transfer to `userA` fails inside `_transferWithFallback`, and the `receiver == requester` branch means no alternate destination is ever attempted).
5. Alternatively, before `deadline`, have `userA` call `cancelRequest(token, request)` — assert it also reverts for the same reason.
6. Confirm there is no other Provisioner or Sweepable function callable by `userA` (or any non-privileged actor) that returns the escrowed USDC to a non-blacklisted address, demonstrating the funds are stuck as long as the blacklist persists (or permanently, from the ordinary user's perspective, since only privileged token-issuer/admin action could resolve it).

    function cancelRequest(IERC20 token, RequestV2 calldata request) external nonReentrant {
        // Requirements: self-cancel caller must be request user
        require(msg.sender == request.user, Aera__CallerIsNotRequestUser());

        if (_isRequestTypeDeposit(request.requestType)) {
            // Requirements: deposit cancellation toggle must be enabled
            require(_depositCancellationsEnabled, Aera__DepositRequestCancellationDisabled());

            uint256 refundAmount = request.tokens;
            // Requirements: pre-deadline self-cancel applies cancellation fee
            if (block.timestamp < request.deadline) {
                uint256 cancellationFee = _computeDepositCancellationFeeTokens(token);
                // Requirements: cancellation fee cannot exceed escrowed amount
                require(cancellationFee <= refundAmount, Aera__CancellationFeeExceedsRequestAmount());
                if (cancellationFee != 0) {
                    unchecked {
                        // unchecked: safe because cancellationFee <= refundAmount is enforced above
                        refundAmount -= cancellationFee;
                    }
                    // Interactions: transfer cancellation fee to vault
                    token.safeTransfer(MULTI_DEPOSITOR_VAULT, cancellationFee);
                }
            }

            // Effects + interactions: clear hash, emit refund event, and transfer net token amount with fallback
            _clearHashAndTransferRefund(token, request, msg.sender, refundAmount, token);

            minUnitsOut,

    function _clearHashAndTransferRefund(
        IERC20 token,
        RequestV2 calldata request,
        address requester,
        uint256 amount,
        IERC20 transferToken
    ) internal {
        bytes32 requestHash = _getRequestHash(token, request);
        // Requirements: hash has been set

        // Log refund event

            emit DepositRefunded(requestHash);
        } else {
            emit RedeemRefunded(requestHash);
        }
    }

    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
