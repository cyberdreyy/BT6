### Title
Job-controlled stdout can forge the pwsh JSON exit-status marker, desynchronizing Kubernetes stage-completion detection - (File: shells/powershell.go)

### Summary
`pwshJSONInitializationScript`/`pwshJSONTerminationScript` communicate stage lifecycle (`{"script": ...}` / `{"command_exit_code": ..., "script": ...}`) to the runner by writing plain, unauthenticated JSON lines into the same stdout stream that carries the job script's own output. Because the job script runs inside the same outer `& { ... }` block and its stdout/stderr is merged into the identical log stream the runner parses for these markers, a job script can emit a line that is indistinguishable from a real marker.

### Finding Description
`NewPsWriter` enables `useJSONInitializationTermination` whenever the executor is Kubernetes and `FF_USE_LEGACY_KUBERNETES_EXECUTION_STRATEGY` is off [1](#0-0) . `finishPwsh`/`finishPowerShell` then prepend `pwshJSONInitializationScript` inside the same `& { ... }` block that wraps the rest of the generated script (which includes the user's job commands) [2](#0-1) . The initialization script itself is nothing but `echo ""` followed by `echo "$start_json"` [3](#0-2) , and the (separately invoked) termination wrapper likewise just echoes `$out_json` containing `command_exit_code`/`script` [4](#0-3) .

On the Kubernetes executor, `getContainerInfo` pipes both stage script stdout and the termination wrapper's own stdout through `buildRedirectionCmd`, which for PowerShell re-encodes and appends everything to the same `s.logFile()` [5](#0-4) . `processLogs`/`forwardLogLine` then scans that log line-by-line, and any line that successfully unmarshals via `StageCommandStatus.TryUnmarshal` and reports `IsExited()` is treated as the authoritative signal that the running stage has terminated, updating `s.remoteStageStatus` and pushing to `s.remoteProcessTerminated` [6](#0-5) . `runInContainer` blocks on that same channel and treats whatever `CommandExitCode` it receives as ground truth for the stage's exit status [7](#0-6) .

There is no nonce, HMAC, sentinel delimiter, or any check that the JSON line actually originated from the runner's own injected script rather than from the job's own script output. A job author fully controls the "job script" text executed inside the same `& { ... }` block/stream, so they can simply write to stdout a line such as `Write-Output '{"command_exit_code": 0, "script": "<stage-script-basename>"}'` before their actual script finishes.

### Impact Explanation
Because `forwardLogLine`/`processLogs` cannot distinguish a genuine termination marker from one forged by the job's own script, a job can desynchronize the runner's view of stage completion from what is actually happening in the container:
- It can signal early/false completion (with an arbitrary exit code) for the currently running stage while the real script process keeps running in the persistent build-container shell.
- Because Kubernetes stages are executed serially over a persistent attached shell/log tail, the runner will then proceed to send the *next* stage's command into the same container/shell before the previous stage's real process has actually finished, causing the two stages' output to interleave in the same log/JSON stream. This can corrupt or mask the legitimate exit-status marker of a subsequent stage (including predefined/helper stages such as artifact upload or cache handling), leading to incorrect exit-code reporting, spurious script/stage mismatches, or hung/mis-terminated jobs.
- At minimum, a job can spoof its own final exit code, e.g., a script that actually fails can force the runner to record success by racing its forged `"command_exit_code": 0` marker ahead of/instead of the true one.

This is confined to the attacker's own job execution and does not itself cross project or container isolation boundaries, but it undermines the integrity of the runner's own control-channel (job success/failure and stage sequencing correctness) — a Core Invariant ("Job ... state must not let one job impersonate another [stage]"). Full end-to-end confirmation of downstream consequences on multi-stage interleaving (e.g., whether `TryUnmarshal`/`StageCommandStatus` in the (unread) `shells/trap_command_exit_status.go` implementation applies any additional validation, such as matching `script` field to the currently expected stage script path before accepting the marker) could not be verified from the available index; the `script` field naming convention (`(Get-Item $PSCommandPath).BaseName`) does suggest some correlation may occur, which would reduce but not necessarily eliminate exploitability, since the attacker can also supply that expected value if it's predictable/discoverable.

### Likelihood Explanation
High feasibility for the "forge own exit code" variant — it only requires a normal pipeline author to add a single `Write-Output`/`echo` line producing valid JSON text to stdout in a `.gitlab-ci.yml` script; no special executor privileges are needed beyond running a Kubernetes-executor job with the new (non-legacy) execution strategy, which is the default going forward. The stage-desynchronization/interleaving variant is more timing-dependent (the forged marker must race ahead of the real one and land while the next stage's attach begins), so it is feasible but less deterministic.

### Recommendation
Distinguish runner-emitted control markers from user-controlled stdout, e.g., by:
- Writing the JSON status markers to a dedicated stream/file descriptor or separate log file rather than the same combined-output stream as the job script, or
- Prefixing/wrapping markers with an unpredictable per-job/per-stage token (nonce) that is verified before a line is treated as authoritative, so job-script stdout cannot forge it, or
- Having `TryUnmarshal`/the consuming code strictly validate the `script` field against the exact expected in-flight script path and require the marker to appear only after the underlying process (not just the log-scanner) has actually exited, e.g., by using an explicit exec exit code from the Kubernetes attach API rather than solely trusting embedded JSON in the log stream.

### Proof of Concept
Kubernetes-executor integration test outline:
1. Configure a build with `FF_USE_LEGACY_KUBERNETES_EXECUTION_STRATEGY: "false"`, `shell: pwsh`.
2. Script content:
   ```
   Write-Output '{"command_exit_code": 0, "script": "step_script"}'
   Start-Sleep -Seconds 10
   exit 1
   ```
3. Run the job stage via `runInContainer`/`processLogs` against a fake/mock log source feeding these lines.
4. Assert that `s.remoteProcessTerminated` receives `CommandExitCode == 0` immediately after the forged line (well before the real `Start-Sleep`/`exit 1` completes), i.e. `forwardLogLine` accepted the forged marker as `IsExited() == true` and the true exit code (1) is never observed by the runner for that invocation — demonstrating the runner's stage-completion/exit-status channel can be forged by job-controlled stdout.

func (s *executor) buildRedirectionCmd(shell string) string {
	if shell == shells.SNPowershell {
		// powershell outputs utf16, so we re-encode the output to utf8
		// this is important because our json decoder that detects the exit status
		// of a job requires utf8.Converting command output to strings with %{"$_"}
		// prevents a powershell complaint about native command output on stderr.
		return fmt.Sprintf("2>&1 | %%{ \"$_\" } | Out-File -Append -Encoding UTF8 %s", s.logFile())
	}

	return fmt.Sprintf("2>&1 | tee -a %s", s.logFile())
}

func (s *executor) forwardLogLine(w io.Writer, line string) {
	var status shells.StageCommandStatus
	if !status.TryUnmarshal(line) {
		if _, err := w.Write([]byte(line)); err != nil {
			s.BuildLogger.Warningln(fmt.Sprintf("Error writing log line to trace: %v", err))
		}

		return
	}

	s.BuildLogger.Debugln(fmt.Sprintf("Setting remote stage status: %s", status))
	s.remoteStageStatusMutex.Lock()
	s.remoteStageStatus = status
	s.remoteStageStatusMutex.Unlock()

	if status.IsExited() {
		s.remoteProcessTerminated <- status
	}
}
