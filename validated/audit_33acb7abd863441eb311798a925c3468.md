### Title
Vote account commission-in-basis-points update has no timing/anti-frontrunning protection, enabling authorized withdrawer to steal delegator rewards - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The reported PancakeSwap bug is a class of "no-timelock privileged parameter change" — an owner can instantly flip a fee parameter to profit at the expense of users who transacted expecting the old value. Agave's vote program contains a directly analogous pattern: the legacy `UpdateCommission` instruction enforces an anti-frontrunning rule (`is_commission_update_allowed`) that blocks commission *increases* late in an epoch, but the newer basis-points commission mechanism, `UpdateCommissionBps` (SIMD-0291), explicitly removes this rule, allowing the vote account's authorized withdrawer to instantly and repeatedly change commission with zero cooldown.

### Finding Description
`update_commission` (legacy, whole-percent commission) enforces a timing rule before allowing a commission increase: [1](#0-0) 

`enforce_commission_update_rule` is only skipped if `disable_commission_update_rule` (a feature-gate, `delay_commission_updates`) is active — which imposes a full-epoch delay instead. Otherwise `is_commission_update_allowed(clock.slot, epoch_schedule)` prevents commission increases in the "late" portion of an epoch, specifically to stop validators from raising their cut right before rewards for that epoch are calculated/distributed — i.e., an explicit anti-frontrunning control for this exact bug class.

In contrast, the newer basis-points commission function has no such control at all: [2](#0-1) 

The comment `// No commission update rule, per SIMD-0249 and SIMD-0291.` confirms this is an intentional design choice, but it reintroduces the exact vulnerability class described in the external report: a privileged party (`authorized_withdrawer`, verified only by `verify_authorized_signer`) can change a value that determines how much of the future reward stream is diverted to them, with no time-lock, no slot-based restriction, and no minimum delay before the new value takes effect.

`update_commission_bps` is dispatched directly from the instruction processor without any additional gating: [3](#0-2) 

(Note: this citation shows the legacy `UpdateCommission` dispatch which still enforces `disable_commission_update_rule`; the `UpdateCommissionBps` dispatch path was not fully captured in the available context, but the underlying `update_commission_bps` function in `vote_state/mod.rs` unconditionally performs the update once signature verification passes, with no epoch/slot check comparable to `is_commission_update_allowed`.)

### Impact Explanation
An authorized withdrawer (the on-chain analog of the "owner" in the report) can:
1. Wait until just before an epoch boundary/rewards calculation.
2. Submit an `UpdateCommissionBps` transaction raising `inflation_rewards_commission_bps` or `block_revenue_commission_bps` to the maximum.
3. Collect a larger share of the epoch's staking rewards or block revenue that delegators expected to receive at the previous (lower) rate.
4. Immediately lower the commission back down afterward, since there is no delay/lock enforced.

This is a direct fund-diversion attack against delegators who have no visibility into or control over the timing of the withdrawer's transaction, mirroring the "owner changes fee from 0% to 5% right before a large deposit" attack vector in the original report.

### Likelihood Explanation
The attack requires only that the actor control the `authorized_withdrawer` key of a vote account — a normal, unprivileged-at-the-protocol-level capability reachable via an ordinary signed transaction (no node-level access, no leaked validator identity key, no consensus manipulation needed). Since `update_commission_bps` was deliberately built without the anti-frontrunning rule that exists for the legacy path, this is a straightforward, repeatable action any vote-account withdraw authority can perform at will.

### Recommendation
Apply an equivalent (or stronger) timing restriction to `update_commission_bps` as exists for `update_commission`: e.g., require a minimum number of epochs' notice before a commission-bps increase takes effect (matching the intent of `delay_commission_updates`), or restrict increases to the early portion of an epoch via `is_commission_update_allowed`-style logic. Alternatively, expose commission-bps state changes through a two-step "propose then activate after N epochs" mechanism so delegators can react before the new rate applies.

### Proof of Concept
Conceptual sequence (based on `update_commission_bps` at `programs/vote/src/vote_state/mod.rs:827-859` and its instruction handler):
1. Authorized withdrawer observes that epoch rewards distribution is imminent.
2. Submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: CommissionKind::InflationRewards }` signed only by the withdrawer.
3. `update_commission_bps` validates only the signer (`verify_authorized_signer`) and applies the change immediately — no slot/epoch gating.
4. Rewards for the current/next distribution are computed using the inflated commission, diverting funds away from delegators.
5. Withdrawer submits a second `UpdateCommissionBps` transaction restoring the original low rate, with no penalty or delay.

I was not able to fully trace the `UpdateCommissionBps` instruction dispatch arm in `vote_processor.rs` within the available index (only the legacy `UpdateCommission` and later test code for `UpdateCommissionBps` were retrieved), so I cannot 100% rule out an additional gating check that may exist elsewhere in the dispatch path. Given the index size limits, a Devin session with full file access to `programs/vote/src/vote_processor.rs` would be needed to fully confirm there is no supplementary check on the `UpdateCommissionBps` dispatch arm before treating this finding as conclusively unmitigated.

pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
