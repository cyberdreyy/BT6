### Title
`update_policy` lets a token's `DefaultAdmin` unilaterally rewire the `TransferSender`/`TransferReceiver`/`TransferExecutor` policy at any time, permanently freezing holders' funds - (File: `crates/common/precompiles/src/b20_asset/logic/v2.rs`)

### Summary
The B-20 `Asset`/`Stablecoin` precompiles expose `updatePolicy(policyScope, newPolicyId)`, which lets the token's `DefaultAdmin` role rebind a policy scope (e.g. `TransferSender`, `TransferReceiver`, `TransferExecutor`) to *any* existing `PolicyRegistry` policy at *any* time, with no timelock, no migration path, and no restriction preventing the new policy from denying everyone. This is structurally the same bug class as the C4 finding: a privileged single-transaction call can redirect a "critical dependency" that all holders' fund movement relies on, with no safeguard against making existing balances permanently unmovable.

### Finding Description
`update_policy` is implemented once per token type/version and gates every unprivileged `transfer`/`transferFrom` call: [1](#0-0) 

The only guard is a role check (`DefaultAdmin`) and that the target policy id exists in the `PolicyRegistry` — there is no check on what the policy *does*: [2](#0-1) 

The policy is enforced unconditionally on every unprivileged transfer path (`transfer`, `transfer_from`), via `B20Guards::ensure_policy_type` / `ensure_authorized_by_id`, which reverts with `PolicyForbids` when the account is not authorized under the *currently wired* policy: [3](#0-2) [4](#0-3) 

Because `updatePolicy` can be called repeatedly and unrestrictedly (no "once-only" or additive-only semantics, unlike the append-only nature the codebase enforces for its trait interfaces), the admin can swap `TransferSender`/`TransferReceiver`/`TransferExecutor` to a freshly created `ALLOWLIST` policy with zero members, or to a `BLOCKLIST` that blocks everyone, in a single transaction — instantly blocking every current holder's ability to transfer (i.e. "withdraw"/move) their balance. This mirrors the reported bug class exactly: a mutable, unguarded pointer to an external authorization/registry object that existing token holders' fund movement depends on, changeable post-hoc with no migration mechanism.

The stablecoin variant has the identical structure (`crates/common/precompiles/src/b20_stablecoin/logic/v2.rs`), so both B-20 asset and stablecoin tokens are affected.

### Impact Explanation
An admin (or a compromised/malicious admin key, or an admin acting under duress/attack) can, with a single `updatePolicy` transaction, make every current holder's balance permanently untransferable by pointing `TransferSender`/`TransferReceiver` at an always-deny policy. Because `update_policy` has no restriction preventing this and no timelock/migration, this is a direct path to freezing funds for all holders of the affected B-20 token/stablecoin — a permanent freezing-of-funds condition matching the Medium-severity class of the referenced report (funds are recoverable only if the same admin chooses to fix the policy again, exactly as in the original report's mitigation reasoning).

### Likelihood Explanation
This requires the token's `DefaultAdmin` role (a privileged actor), so it is not exploitable by an arbitrary unprivileged sender — the same limitation the original judge used to downgrade severity to Medium in the source report (an admin-key operation, not a permissionless attack). Given `DefaultAdmin` is a role deliberately granted at token creation/via `grantRole`, and given the same admin already controls pause/mint/burn, this doesn't introduce a *new* privilege escalation, but it does introduce a new, unguarded footgun/attack surface via a role that many B-20 deployments may grant to operational keys with lower security bars than "can permanently freeze all user funds."

### Recommendation
- Add a guard rejecting `newPolicyId` selections that would make the policy scope's default/empty-member semantics obviously deny-all in a way that traps existing balances, or at minimum
- Require a timelocked/two-step change for `TransferSender`/`TransferReceiver`/`TransferExecutor` policy scopes (mirroring the pending-admin two-step pattern already used elsewhere in the policy registry, e.g. `pendingPolicyAdmin`), so holders have a window to exit before a hostile/faulty repointing takes effect.
- Alternatively, document this as an explicitly accepted admin-trust assumption (as Biconomy did) — but currently there is no code-level mitigation, note, or event distinguishing a "safe" from "fund-freezing" policy update.

### Proof of Concept
1. Admin deploys a B-20 asset token, wiring `TransferSender`/`TransferReceiver` to a benign `ALLOWLIST` policy with wide membership. Holders accumulate balances via normal `transfer`/`mint`.
2. Admin calls `PolicyRegistry.createPolicy(admin, ALLOWLIST)` to create a new, empty allowlist policy `P2`.
3. Admin calls `updatePolicy(TransferSender.id(), P2)` (and/or `TransferReceiver.id()`), per `AssetV2::update_policy` at `crates/common/precompiles/src/b20_asset/logic/v2.rs:669-696`.
4. Any holder's subsequent unprivileged `transfer`/`transferFrom` now fails `B20Guards::ensure_policy_type`/`ensure_authorized_by_id` with `PolicyForbids`, because nobody is a member of `P2` — this is directly analogous to the `actions/harness/tests/beryl/b20_policy.rs` test `b20_allowlist_sender_policy_blocks_non_members`, which demonstrates the same mechanism being used to legitimately block transfers; the same call path can be pointed at an empty/hostile policy to block *everyone*, including previously-authorized holders, with no way for holders to recover funds except by the same admin reverting the policy.

impl<S: AssetAccounting, A: PolicyAccounting> Asset<S, A> for AssetV2 {
    fn transfer(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        to: Address,
        amount: U256,
        privileged: bool,
    ) -> Result<()> {
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::TRANSFER)?;
        let to = NonZeroAddress::new(to)
            .map_err(|_| BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }))?;
        let from = NonZeroAddress::new(caller)
            .map_err(|_| BasePrecompileError::revert(IB20::InvalidSender { sender: caller }))?;
        if privileged {
            return self.transfer_inner(token, from, to, amount, None);
        }
        let policies = token.accounting().transfer_policy_ids()?;
        self.transfer_inner(token, from, to, amount, Some(&policies))
    }

    fn update_policy(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        policy_scope: B256,
        new_policy_id: u64,
        privileged: bool,
    ) -> Result<()> {
        if !privileged {
            B20Guards::ensure_token_role(token, caller, B20TokenRole::DefaultAdmin)?;
        }
        Self::ensure_supported_policy_type(policy_scope)?;
        if !token.policy().policy_exists(token.policy_storage(), new_policy_id)? {
            return Err(BasePrecompileError::revert(IB20::PolicyNotFound {
                policyId: new_policy_id,
            }));
        }
        let old_policy_id = token.accounting().policy_id(policy_scope)?;
        token.accounting_mut().set_policy_id(policy_scope, new_policy_id)?;
        token.accounting_mut().emit_event(
            IB20::PolicyUpdated {
                policyScope: policy_scope,
                oldPolicyId: old_policy_id,
                newPolicyId: new_policy_id,
            }
            .encode_log_data(),
        )
    }

    ///
    /// Identical to [`Self::ensure_policy`] except the caller supplies the id (already loaded, e.g.
    /// via [`TokenAccounting::transfer_policy_ids`](crate::TokenAccounting::transfer_policy_ids)),
    /// so a batch of checks against ids from the same slot pays a single SLOAD. Reverts the same
    /// `PolicyForbids { policyScope, policyId }` as `ensure_policy`.
    pub fn ensure_authorized_by_id<T: Token + ?Sized>(
        token: &T,
        policy_scope: B256,
        policy_id: u64,
        account: Address,
    ) -> Result<()> {
        if token.policy().is_authorized(token.policy_storage(), policy_id, account)? {
            Ok(())
        } else {
            Err(BasePrecompileError::revert(IB20::PolicyForbids {
                policyScope: policy_scope,
                policyId: policy_id,
            }))
        }
    }
