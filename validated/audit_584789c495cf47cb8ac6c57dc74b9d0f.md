### Title
Unprivileged shareholder can permanently DoS vesting `distribute()` for all other shareholders by opting out of direct coin transfers - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`vesting::distribute()` iterates over **every** shareholder in a `VestingContract` and calls `aptos_account::deposit_coins` for each recipient in a single atomic transaction. `aptos_account::deposit_coins` aborts if the target account is not registered for the coin and has explicitly disabled arbitrary direct coin transfers via `set_allow_direct_coin_transfers(false)`. Since Move transactions are all-or-nothing, one uncooperative/malicious shareholder can permanently block distribution to all co-shareholders of the same vesting contract, and also block `terminate_vesting_contract`/`admin_withdraw`, since `terminate_vesting_contract` first calls `distribute`.

### Finding Description
`distribute_internal`-equivalent loop in vesting: [2](#0-1) 

For each shareholder, `get_beneficiary` resolves the payout address and `aptos_account::deposit_coins` is invoked. That function aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` when the target account exists, is unregistered for the coin, and `can_receive_direct_coin_transfers` returns false: [3](#0-2) 

`can_receive_direct_coin_transfers` is controlled per-account by `set_allow_direct_coin_transfers`, an entirely permissionless, always-available function that any account (including any vesting shareholder) can call on itself at any time: [4](#0-3) 

The framework authors were aware of this exact class of failure and added a guard specifically for `set_beneficiary` (checking `assert_account_is_registered_for_apt(new_beneficiary)` "so `distribute()` wouldn't fail and block all other accounts"), but this guard:
1. Only applies at the moment the admin sets a beneficiary — it does not prevent the shareholder or beneficiary from later becoming unregistered/opted-out (e.g., calling `coin::migrate`/never registering, or toggling `set_allow_direct_coin_transfers(false)` after being registered is fine only if already registered for AptosCoin — but if the shareholder's account is a *shareholder itself* with no beneficiary set, there is no equivalent check at all, since `set_beneficiary` is optional).
2. Does nothing for the default case where a shareholder never gets a beneficiary assigned — `get_beneficiary` simply returns the shareholder address itself, and there is no analogous registration check anywhere in `create_vesting_contract` for the raw shareholder addresses.

Because `distribute()` is a single atomic loop over `grant_pool.shareholders()`, any one shareholder (of up to `MAXIMUM_SHAREHOLDERS`, referenced in the module docs/spec) can render distribution to *all* shareholders impossible by causing their own leg of the loop to abort.

### Impact Explanation
This blocks reward/vesting distribution (`distribute`, `distribute_many`) and — critically — blocks `terminate_vesting_contract`, which calls `distribute` first before flipping state to terminated and unlocking the remaining grant: [5](#0-4) 

If termination is blocked, `admin_withdraw` (which requires `VESTING_POOL_TERMINATED` state) can never run either: [6](#0-5) 

This traps all co-shareholders' vested rewards and, more seriously, can prevent the admin from ever recovering the remaining grant, a permanent non-recoverable loss/lockup of stake and vesting funds for parties who did nothing wrong — squarely within the "Permanent lock or non-recoverable loss of claim rights in stake ... or vesting flows" impact category.

### Likelihood Explanation
Likelihood is high given how trivial the trigger is: any shareholder simply calls `aptos_account::set_allow_direct_coin_transfers(false)` on their own already-registered-then-later-arranged-to-be-unregistered account, or more directly, any account added as a shareholder that was never registered for the coin and set its `DirectTransferConfig.allow_arbitrary_coin_transfers = false` before any distribution ever occurs. No privilege beyond being one of the (potentially many, up to `MAXIMUM_SHAREHOLDERS`) shareholders is required, and the action is a single unprivileged framework call.

### Recommendation
- Make `distribute()` resilient to individual recipient deposit failures by attempting each deposit in a way that cannot abort the whole loop (e.g., catch/skip and accumulate undistributed amounts into a per-shareholder pending balance that can be claimed separately, rather than pushing funds).
- Alternatively/additionally, validate at vesting-contract creation time (`create_vesting_contract`) that every shareholder address satisfies `assert_account_is_registered_for_apt`, mirroring the fix already applied to `set_beneficiary`, and re-validate whenever an account's coin-transfer configuration could affect distribution.
- Decouple `terminate_vesting_contract` from a successful `distribute()` call so termination/admin recovery is not held hostage by a single griefing shareholder.

### Proof of Concept
1. Admin creates a vesting contract with shareholders `[S1, S2]` via `create_vesting_contract`, no beneficiaries set for either.
2. `S1` calls `aptos_account::set_allow_direct_coin_transfers(false)` on their own account (fully permissionless) before ever registering for `AptosCoin` (e.g., account created via `account::create_account_for_test`/exists but never called `coin::register`).
3. Vesting period elapses; anyone calls `vesting::vest(contract_address)` to unlock funds, then `vesting::distribute(contract_address)`.
4. Inside `distribute`, the loop reaches `S1`; `aptos_account::deposit_coins(S1, ...)` hits `coin::is_account_registered<CoinType>(S1) == false` and `can_receive_direct_coin_transfers(S1) == false`, causing `assert!` failure with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, aborting the entire transaction.
5. `S2` (and all other shareholders) can never receive their distribution while `S1` keeps this configuration, and `terminate_vesting_contract`/`admin_withdraw` are likewise permanently blocked since `terminate_vesting_contract` calls `distribute` unconditionally first.

Note: I was not able to fully trace `create_vesting_contract`'s shareholder validation logic (only partial context was retrieved), so it is possible — though not evidenced in the code reviewed — that some existing check on initial shareholder addresses partially mitigates the "never-registered-shareholder" variant. The `set_beneficiary` guard, however, is confirmed by direct code and comment, and provides strong evidence that this exact failure mode is a known-but-incompletely-patched issue in this codebase. A Devin session with fuller repository access could verify `create_vesting_contract`'s shareholder validation to close this residual uncertainty.

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );

                allow_arbitrary_coin_transfers: allow,

                    DirectCoinTransferConfigUpdatedEvent>(account)

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
