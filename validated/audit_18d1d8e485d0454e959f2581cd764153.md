### Title
Nested `run:` dispatch (`runUserSteps`) cancels only the local client context and never issues the step-runner `Cancel(id)` RPC, so a server-side nested job can outlive the outer job's "canceled" status - ([File: functions/concrete/run/run_steps.go])

### Summary
`Runner.Cancel()` cancels `r.scriptCancel`, which for a `run:` step is the context passed into `cli.RunAndFollow(ctx, req, out)` in `runUserSteps`. Unlike the top-level job dispatch path in `steps/execute.go`, which explicitly wires a `RegisterCancel` callback that issues a `c.Cancel(cancelCtx, request.Id)` RPC to the step-runner server, `runUserSteps` never calls the equivalent `Cancel(id)` RPC for the nested job it starts.

### Finding Description
The step-runner protocol treats `Run` as fire-and-forget: `steps/stepstest/server.go`'s `Run` "returns immediately; the job is treated as 'running' until Cancel is invoked" [1](#0-0) , and `FollowLogs` is merely a log-follow stream that unblocks either when the server records an explicit `Cancel` RPC or when the stream's own context is done [2](#0-1) . This models the real step-runner: job execution is tracked server-side by job ID and is not intrinsically tied to a single client's `RunAndFollow` stream context — stopping the actual job requires an explicit `Cancel(id)` call, not just disconnecting/cancelling the follow stream.

The top-level dispatch path in `steps/execute.go` respects this: it registers a callback via `opts.RegisterCancel` that performs a distinct, explicit `c.Cancel(cancelCtx, request.Id)` RPC using its own 5-second context independent of the job's own `ctx` [3](#0-2) .

`runUserSteps`, used for the nested `run:` keyword, has no such mechanism. It only passes `ctx` (the outer `scriptCtx`) into `cli.RunAndFollow(ctx, req, out)` [4](#0-3) , and `Runner.Cancel()` only calls `r.scriptCancel()`, canceling that local context - it never issues a `Cancel(id)` RPC for the nested job's ID (`strconv.FormatInt(r.config.ID, 10) + "-run"`, built in `buildRunRequest`) [5](#0-4) [6](#0-5) .

Canceling the client-side gRPC context tears down the `RunAndFollow` stream/connection from the client's perspective, and `interpretRunResult` classifies the resulting transport error or cancelled status into `ErrJobCanceled`, so the outer job's reported outcome becomes "canceled" [7](#0-6) . But per the protocol semantics shown in the fake server, the server only truly stops/marks a job cancelled upon receiving the `Cancel(id)` RPC, not merely from the client dropping its follow stream. Since that RPC is never sent for `run:` dispatch, the job the server started under `req.Id` can continue running and consuming shared resources on the shared step-runner socket after the client already reports cancellation.

### Impact Explanation
This matches the scoped impact: on a shared step-runner backend (e.g. the shell executor's shared server referenced by `socketPathOverride`'s comment about "long-lived hosts") [8](#0-7) , a canceled outer job whose `run:` steps were dispatched as a nested tenant leaves an orphaned, still-executing job on the server, tying up CPU/goroutines/handles on the socket that other tenants (other jobs multiplexed through the same step-runner) depend on, degrading or starving subsequent job dispatch.

### Likelihood Explanation
Any pipeline author using the `run:` keyword (a normal, unprivileged CI feature) triggers this path unconditionally - no special crafting beyond a job that takes a while to run (or ignores termination signals inside step-runner's builtin/step machinery) is needed; the gap is structural (missing `Cancel(id)` RPC), not input-dependent. It reproduces deterministically: cancel any in-flight `run:`-dispatched job and observe that no `Cancel` RPC is sent to step-runner for the nested job ID, unlike the top-level path.

### Recommendation
In `runUserSteps` (or `runRunSteps`), register a cancel callback analogous to `steps/execute.go`'s `RegisterCancel`: when `Runner.Cancel()` fires, in addition to cancelling `scriptCtx`, explicitly call `cli.Cancel(cancelCtx, req.Id)` (with its own bounded timeout, independent of the already-cancelled `scriptCtx`) so the step-runner server is told to gracefully stop the specific nested job by ID, not merely observe a dropped stream.

### Proof of Concept
Extend `steps/stepstest.Server` (or an equivalent fake) to track jobs by ID and only mark them "stopped" upon an explicit `Cancel` RPC; wire it as the dial target for `functions/concrete/run/run_steps.go`'s `unixSocketDialer`/`extended.New`. Then:
1. Start a `Runner` with `RunSteps` set, dispatching via `runUserSteps` against the fake server.
2. From the fake `Run` handler, block until a test hook fires (simulating a long-running/blocking builtin) and record whether `Cancel(id)` was ever invoked for that job ID.
3. Call `r.Cancel()` externally to cancel `scriptCancel`.
4. Assert: `runUserSteps` returns promptly with `ErrJobCanceled` (client-side view), but assert that `server.Cancels()` (mirroring the existing `TestBuild_executeStepStage_ForwardsRegisterCancel` pattern in `common/build_test.go`) is empty/never receives the nested job's ID — proving the server was never told to stop that job, unlike the equivalent assertion that already passes for the top-level dispatch path via `steps/execute.go`.

func (r *Runner) runUserSteps(ctx context.Context, steps []schema.Step) error {
	req, err := r.buildRunRequest(steps)
	if err != nil {
		return err
	}

	dialer := unixSocketDialer(socketPath())
	cli, err := extended.New(dialer)
	if err != nil {
		return fmt.Errorf("dialing step-runner: %w", err)
	}
	//nolint:errcheck
	defer cli.CloseConn()

	splitter := innerstream.New(r.env.Stdout, r.env.Stderr)
	out := &extended.FollowOutput{Logs: splitter}

	status, err := cli.RunAndFollow(ctx, req, out)
	// Flush any line whose continuation marker we never saw.
	flushErr := splitter.Flush()

	return interpretRunResult(status, err, flushErr)
}
```

func interpretRunResult(status client.Status, runErr, flushErr error) error {
	if runErr == nil {
		runErr = flushErr
	}
	if runErr != nil {
		return fmt.Errorf("running user steps via step-runner: %w", runErr)
	}

	switch status.State {
	case client.StateSuccess:
		return nil
	case client.StateCancelled:
		return fmt.Errorf("%w: %s", ErrJobCanceled, status.Message)
	default:
		msg := status.Message
		if msg == "" {
			msg = status.State.String()
		}
		return errors.New(msg)
	}
}
```
