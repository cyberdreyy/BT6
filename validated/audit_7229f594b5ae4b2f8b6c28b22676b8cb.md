### Title
Stale per-epoch instant-withdraw counters are never cleared on claim, inflating the default recovery basis and recovery price - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. These stale per-epoch entries are later read as authoritative claim basis by `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` during `finalizeDefaultRecovery`, inflating `recoveryPrice` with phantom (already-paid) funds. This is the direct analog of the GART bug: state written at "allocation" (request time) is consumed later as if still valid even though the underlying claim was already settled.

### Finding Description
- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` [1](#0-0) .
- `claimInstantWithdrawRequest` pays the user and zeroes only `instantWithdrawsRequests[_user]`; neither per-epoch mapping is touched [2](#0-1) .
- On default finalization, `defaultPendingClaimBasis` adds the full stale `instantWithdrawClaimsByEpoch[epochNumber]` to the haircut basis whenever `pendingInstantWithdraws != 0` [3](#0-2) , and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as real already-held reserve even though those funds were already paid out [4](#0-3) .
- `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount / totalBasis` where both numerator (phantom prefunded reserve) and basis are inflated [5](#0-4) .

### Impact Explanation
An inflated `recoveryPrice` means every defaulted/post-default claim paid through `_transferDefaultRecovery` or `_claimDefaultedWithdrawRequest` receives more underlying than its pro-rata share of the real reserve [6](#0-5) . An attacker holding a normal withdraw receipt in the defaulted epoch claims first, drains the real `defaultRecoveryReserve` at the inflated price, and later legitimate claimants (other receipt holders, `DefaultDistributor` claimants) find the reserve exhausted — direct theft of recovery funds quantified by the phantom instant basis `X`.

### Likelihood Explanation
Requires an instant-withdraw epoch that subsequently defaults with `pendingInstantWithdraws != 0` (partially unfunded instant queue — explicitly contemplated by the `_defaultPrefundedInstantReserve` comments) and epoch numbering alignment so the stale entries sit under `defaultRecoveryEpoch`. An unprivileged tranche holder controls the request/claim timing; borrower default is an ordinary protocol event. Caveat: I could not fully verify that `epochNumber` at request time equals `defaultRecoveryEpoch` at finalization (it is incremented in `deposit` during `stopEpoch`); if the default epoch always differs, the stale entries instead strand under the old key and the impact reduces to incorrect `instantWithdrawsRequests[_user] -= claimBasis` accounting for users re-requesting post-default.

### Recommendation
In `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (and all prior epoch entries for the user) and decrement `instantWithdrawClaimsByEpoch` by the claimed amount, mirroring the cleanup in `_clearWithdrawClaimForEpoch`. Alternatively, track per-epoch claims so `defaultPendingClaimBasis` only counts still-unpaid receipts.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
