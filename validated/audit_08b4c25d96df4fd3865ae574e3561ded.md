### Title
Unbounded Growth of On-Chain Allowlisted Requests Causes Linear-Scan DoS in Vault Request Authorization - (File: core/capabilities/vault/allow_list_based_auth.go)

### Summary
The Vault gateway's `AuthorizeRequest` path performs a full linear scan over the entire in-memory list of on-chain "allowlisted requests" for every single vault JSON-RPC request (create/update/delete/list secrets). This list is populated from the `WorkflowRegistry` contract's `AllowlistRequest`/`getActiveAllowlistedRequestsReverse` methods, which any linked workflow owner can call with no apparent cap on the number of active (unexpired) entries. This mirrors the reported bug class: an attacker-influenced/unbounded whitelist that is fully iterated on a hot, unprivileged-reachable path, degrading (and potentially blocking) request processing for all users.

### Finding Description
`allowListBasedAuth.fetchAllowlistedItem` linearly scans the full slice of allowlisted requests to find a matching digest: [1](#0-0) 

This scan happens inside `findAllowlistedItemWithRetry`, which itself retries the linear scan up to `allowListBasedAuthRetryCount` (10) times with `allowListBasedAuthRetryInterval` (3s) between retries — i.e., up to 11 full scans per single vault request, spread over up to ~30 seconds: [2](#0-1) 

The in-memory list scanned here (`w.allowListedRequests`) is a shared, DON-wide resource populated from the on-chain `WorkflowRegistry` contract and is not bounded by number of owners or global size — only individual entries are dropped once expired: [3](#0-2) 

Any linked workflow owner can add new allowlist entries via `AllowlistRequest` on the contract with an arbitrary future expiry timestamp — there is no visible on-chain or off-chain cap on the number of *active* entries a single owner (or many colluding/sybil owners) can register, unlike the explicit `MaxSecretsPerOwner`/`MaxBatchSize` limits enforced elsewhere in the Vault plugin (`core/services/ocr2/plugins/vault/plugin.go`): [4](#0-3) 

A test in the codebase itself demonstrates the list growing past 1,000 entries and being fully materialized in memory and returned via `GetAllowlistedRequests`: [5](#0-4) [6](#0-5) 

Since `AuthorizeRequest` is invoked on every incoming `vault.secrets.*` JSON-RPC request received by the internet-facing gateway handler before any secret operation is processed: [7](#0-6) 

...an unbounded (or very large) allowlist directly increases CPU cost and per-request latency for *every* vault user on the DON, analogous to the original Moloch `_ragequit` bug where an unbounded whitelist loop degraded/blocked processing for all participants.

### Impact Explanation
As the number of active allowlisted requests grows (any linked owner can add entries with no visible cap), the per-request authorization cost grows linearly and is repeated up to 11 times per request due to the retry loop. This can significantly increase latency or cause request timeouts for the Vault gateway's authorization path across all owners/workflows sharing the DON, effectively degrading or blocking legitimate secret create/update/delete/list operations — a service-wide availability impact reachable purely from a normal (non-privileged) linked-owner action, not requiring any node-operator or malicious-node capability.

### Likelihood Explanation
Any account that has linked ownership with the `WorkflowRegistry` (a self-service, permissionless action available to any workflow owner) can repeatedly call `AllowlistRequest` with distinct digests and long expiry timestamps. Because there is no apparent limit on the number of active allowlist entries per owner or globally, an adversarial or even organically growing set of workflow owners can inflate this list over time, making the degraded-performance scenario realistically reachable without any privileged access.

### Recommendation
Introduce an explicit cap on the number of *active* allowlisted requests, either per-owner or DON-wide (mirroring the existing `MaxSecretsPerOwner`/`MaxBatchSize` pattern used elsewhere in the vault plugin), and/or replace the linear `fetchAllowlistedItem` scan with a hash-map/index keyed by digest so that lookup cost stays O(1) regardless of list size. Additionally, consider bounding the retry loop's total scanned-entries budget so a large allowlist cannot multiply the cost via retries.

### Proof of Concept
1. As any address, call `LinkOwner` on the `WorkflowRegistry` contract to become a valid workflow owner (self-service, no special privilege required).
2. Repeatedly call `AllowlistRequest(requestDigest, farFutureExpiryTimestamp)` with many distinct digests (as shown feasible in `Test_InitialStateSyncV2`, which adds `MaxResultsPerQuery + 1` = 1001 entries), growing the "active" allowlist to tens or hundreds of thousands of entries over time, since there is no cap enforced.
3. Once the Vault DON's `workflowRegistry.syncAllowlistedRequests` picks up the inflated list (`core/services/workflows/syncer/v2/workflow_registry.go:764-804`), every subsequent `vault.secrets.*` request handled by `GatewayHandler.HandleGatewayMessage` triggers `AuthorizeRequest` → `findAllowlistedItemWithRetry`, which scans the full list up to 11 times.
4. Observe increasing per-request latency for all vault users on the DON as the list grows, potentially exceeding client-side timeouts and effectively blocking legitimate secret operations.

```go
func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}
```

```go
func (w *workflowRegistry) syncAllowlistedRequests(ctx context.Context) {
	ticker := w.getTicker(defaultTickIntervalForAllowlistedRequests)
	w.lggr.Debug("starting syncAllowlistedRequests")
	for {
		select {
		case <-ctx.Done():
			w.lggr.Debug("shutting down syncAllowlistedRequests, %s", ctx.Err())
			return
		case <-ticker:
			newAllowListedRequests, totalAllowlistedRequests, head, err := w.getAllowlistedRequests(ctx, w.contractReader)
			if err != nil {
				w.lggr.Errorw("failed to call getAllowlistedRequests", "err", err)
				continue
			}
			w.allowListedMu.Lock()
			// Prune expired requests
			activeAllowlistedRequests := []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest{}
			expiredRequestsCount := 0
			for _, request := range w.allowListedRequests {
				if int64(request.ExpiryTimestamp) > time.Now().Unix() {
					activeAllowlistedRequests = append(activeAllowlistedRequests, request)
				} else {
					expiredRequestsCount++
				}
			}

			// Add new requests
			activeAllowlistedRequests = append(activeAllowlistedRequests, newAllowListedRequests...)
			w.allowListedRequests = activeAllowlistedRequests
			w.lastSeenAllowlistedRequestsCount = totalAllowlistedRequests
			w.lggr.Debugw("synced allowlisted requests",
				"newRequestsNum", len(newAllowListedRequests),
				"expiredRequestsNum", expiredRequestsCount,
				"activeRequestsNum", len(w.allowListedRequests),
				"lastSeenOnchainRequestsNum", w.lastSeenAllowlistedRequestsCount,
				"blockHeight", head.Height,
			)
			w.allowListedMu.Unlock()
		}
	}
}
```

```go
func (w *workflowRegistry) GetAllowlistedRequests(_ context.Context) []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest {
```

```go
func (h *GatewayHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) (err error) {
	reqLggr := h.requestLogger(req, gatewayID)
	reqLggr.Debugw("received message from gateway", "req", req)

	var response *jsonrpc.Response[json.RawMessage]
	var authResult *AuthResult

	switch req.Method {
	case vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate:
		publicKey, pkErr := h.getMasterPublicKey(ctx)
		if pkErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pkErr)
			break
		}
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, publicKey)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodSecretsDelete, vaulttypes.MethodSecretsList:
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, nil)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodPublicKeyGet:
		response = h.handlePublicKeyGet(ctx, gatewayID, req)
	default:
		response = h.errorResponse(ctx, gatewayID, req, api.UnsupportedMethodError, errors.New("unsupported method: "+req.Method))
	}
```
