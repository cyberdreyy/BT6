### Title
Unbounded, permissionless spam of a victim address's `AddressSignatures` ledger index enables `getSignaturesForAddress` RPC DoS / indexing bloat - (File: `ledger/src/blockstore.rs`)

### Summary
Any ordinary user can craft transactions that reference an arbitrary victim `Pubkey` as a non-signer, read-only account. `TransactionStatusService`/`Blockstore::write_transaction_status` indexes **every** account key present in `message.account_keys()` — not just signers or accounts a program actually validated ownership over — into the `AddressSignatures` column family keyed by `(pubkey, slot, transaction_index, signature)`. This is exactly analogous to the Ajna `memorializePositions` bug: a permissionless call lets an attacker attach arbitrary, low-value records to a third party's "position" (here, their address-indexed transaction history) without their consent, degrading a downstream enumeration path (`getSignaturesForAddress`) for the victim.

### Finding Description
`TransactionStatusService::write_transaction_status_batch` iterates over `message.account_keys()` and calls `blockstore.add_transaction_status_to_batch(...)` for every key in the transaction, marking each with `(writable)` flag [1](#0-0) . This feeds into `Blockstore::write_transaction_status_helper`, which unconditionally writes an `address_signatures_cf` entry for **every** key returned by the iterator, with no check that the key belongs to a signer, a writable account actually mutated by the transaction, or any privileged relationship to the transaction submitter [2](#0-1) .

Because Solana transaction messages allow including arbitrary extra accounts as read-only, non-signer inputs to an instruction (e.g., padding accounts passed to the Memo program or any custom program that ignores unused accounts), any user can construct a cheap transaction (one fee, ~5000 lamports) that includes any victim's `Pubkey` in `account_keys`, with no signature or ownership check on that key. Each such transaction adds one more row keyed by the victim's address to `AddressSignatures` [3](#0-2) .

This index is the sole backing store for `getSignaturesForAddress`. `get_confirmed_signatures_for_address2` iterates the `address_signatures_cf` column in reverse from the requested `(address, slot)` cursor, scanning entries until `limit` matching hits are found or the lower bound slot is passed [4](#0-3) . If an attacker floods a victim's address with irrelevant, low-value junk signatures (analogous to insignificant positions in the Ajna bug), the victim's genuine `getSignaturesForAddress` queries must scan through — and RPC/CLI clients paging via `before`/`until` must traverse — an attacker-inflated volume of entries [5](#0-4) .

### Impact Explanation
- Read-path DoS/degradation: `getSignaturesForAddress` (used broadly by wallets, explorers, and the CLI's `transaction-history` command [6](#0-5) ) becomes slower and can be starved of useful results for a targeted victim address, since the attacker's junk rows interleave with legitimate rows in the reverse-slot iteration.
- Storage growth: every junk transaction permanently grows the ledger's `AddressSignatures` column (until pruned by ledger cleanup), imposing unbounded storage cost on any validator/RPC node maintaining transaction history for the targeted address, without the victim's consent — mirroring the Ajna NFT-position storage-array spam.
- No privilege or victim key is required by the attacker; only ordinary fee-payer capability is needed, matching the "anyone" precondition in the original H-03 report.

### Likelihood Explanation
High for any RPC node running with `--enable-rpc-transaction-history` (gated by `check_if_transaction_history_enabled` [7](#0-6) ). Constructing a valid transaction that references an arbitrary extra read-only pubkey is trivial and requires no special program logic (any instruction that tolerates extra unused accounts, or a minimal custom/no-op program, suffices). The only cost is the standard transaction fee, making sustained spam economically cheap relative to the persistent indexing damage inflicted on the victim address.

### Recommendation
- Restrict `AddressSignatures` indexing to keys that are either signers of the transaction or accounts actually touched/written by the executed instructions (using post-execution "touched accounts" data rather than the raw static `message.account_keys()` list), so an attacker cannot associate a victim's address with a transaction it had no meaningful relationship to.
- Alternatively/additionally, apply per-address rate limiting or a minimum "relevance" bar (e.g., only index an address if it is writable or a signer) before writing `address_signatures_cf` entries in `Blockstore::write_transaction_status_helper`.
- Consider exposing pagination/filtering in `get_confirmed_signatures_for_address2` that can distinguish "self-relevant" entries to mitigate the impact for already-written data.

### Proof of Concept
1. Build a transaction with a fee payer/signer keypair `attacker`, and one instruction (e.g., `spl_memo::build_memo` or the System Program `Transfer` of 0 lamports to self) that includes `AccountMeta::new_readonly(victim_pubkey, false)` as an *extra*, unused account.
2. Submit many such transactions (varying memo/nonce to get distinct signatures) from `attacker`, each embedding a different/same `victim_pubkey`.
3. On a validator/RPC node with transaction history enabled, each submission triggers `TransactionStatusService` → `Blockstore::add_transaction_status_to_batch` → one new `address_signatures_cf` row for `victim_pubkey` [1](#0-0) .
4. Call `getSignaturesForAddress(victim_pubkey)` (or the analogous `Blockstore::get_confirmed_signatures_for_address2` test pattern shown in `test_get_confirmed_signatures_for_address2` [8](#0-7) ) and observe the results are now dominated by attacker-injected junk signatures, with iteration cost growing linearly with attacker spam volume.

    fn write_transaction_status_helper<'a, F>(
        &self,
        slot: Slot,
        signature: Signature,
        keys_with_writable: impl Iterator<Item = (&'a Pubkey, bool)>,
        status: TransactionStatusMeta,
        transaction_index: usize,
        mut write_fn: F,
    ) -> Result<()>
    where
        F: FnMut(&Pubkey, Slot, u32, Signature, bool) -> Result<()>,
    {
        let status = status.into();
        let transaction_index = u32::try_from(transaction_index)
            .map_err(|_| BlockstoreError::TransactionIndexOverflow)?;
        self.transaction_status_cf
            .put_protobuf((signature, slot), &status)?;

        for (address, writeable) in keys_with_writable {
            write_fn(address, slot, transaction_index, signature, writeable)?;
        }

        Ok(())
    }

    pub fn write_transaction_status<'a>(
        &self,
        slot: Slot,
        signature: Signature,
        keys_with_writable: impl Iterator<Item = (&'a Pubkey, bool)>,
        status: TransactionStatusMeta,
        transaction_index: usize,
    ) -> Result<()> {
        self.write_transaction_status_helper(
            slot,
            signature,
            keys_with_writable,
            status,
            transaction_index,
            |address, slot, tx_index, signature, writeable| {
                self.address_signatures_cf.put(
                    (*address, slot, tx_index, signature),
                    &AddressSignatureMeta { writeable },
                )
            },
        )
    }
