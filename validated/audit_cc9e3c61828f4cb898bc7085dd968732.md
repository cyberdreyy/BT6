### Title
Confirmations from removed multisig members remain counted toward execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
The `preLiquidateHook` bug class is about an action being authorized using a stale enrollment/state check instead of the entity's *current* membership status. The direct analog in this NEAR codebase is in `multisig2`: `confirm()` counts confirmations stored in `self.confirmations` toward the `num_confirmations` threshold without verifying that each confirming member is still a current, live member of `self.members`. `delete_member()` only purges requests *originated by* the removed member, not confirmations that member cast on *other* live requests. This breaks the intended equality "confirmations counted == live members who approved."

### Finding Description
The intended invariant is: a request executes only when at least `num_confirmations` **current** members have approved it. Instead, the contract counts raw entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set: [1](#0-0) 

When a member is removed via `delete_member`, the code cleans up only requests that member itself created (`r.member == member`), and removes their `num_requests_pk` entry, but does **not** scan and strip that member's entries from `confirmations` sets of requests created by *other* members: [2](#0-1) 

So if member `C` confirms request `R` (created by `A`), and is later removed from the multisig via a separate `DeleteMember` request, `R`'s confirmation set still contains `C`'s serialized identity. A subsequent confirmation by any remaining live member can push `confirmations.len() + 1 >= num_confirmations`, causing `execute_request` to run — even though the actual number of *live* approving members is one less than `num_confirmations`.

`assert_valid_request` and `current_member()` only check that the *caller* of `confirm` is currently a member; they never re-validate the members recorded in a pre-existing confirmation set: [3](#0-2) [4](#0-3) 

### Impact Explanation
This crosses the threshold/identity boundary explicitly named in scope: "confirmations counted versus live members." A `MultiSigRequestAction::Transfer` (or `DeployContract`, `AddKey`/`AddFullAccessKey`, `FunctionCall`, etc.) can be executed by fewer live signers than `num_confirmations` requires, i.e., "a multisig request executed below threshold" — a Critical impact per the rules, since it moves NEAR (or grants a full access key / deploys code) with fewer real authorizations than configured, effectively lowering the security threshold silently after any member removal.

### Likelihood Explanation
This requires no privileged or out-of-scope actor: any of the (still-legitimate, unprivileged in the "not entitled" sense for the *specific* request) confirming members can exploit it opportunistically. The only precondition is the ordinary, expected lifecycle event of removing a member from the multisig (e.g., an employee leaving, a key rotation) while there exists a pending, partially-confirmed request that the removed member had confirmed. This is a normal operational occurrence for a multisig wallet, not a contrived edge case, making likelihood high whenever membership changes occur with requests in flight.

### Recommendation
When executing `delete_member`, iterate over all pending `requests`/`confirmations` (not just those the removed member created) and strip the removed member's entry from every confirmation set; alternatively, on `confirm()`, filter `confirmations` to only members still present in `self.members` before comparing the count to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R1` (e.g., `Transfer` to an attacker-controlled account).
3. `B` calls `confirm(R1)` → confirmations = `{B}` (1 < 3, not yet executed).
4. `C` calls `confirm(R1)` → confirmations = `{B, C}` (2 < 3, not yet executed).
5. Separately, `D` creates and confirms (with enough live members) a `DeleteMember { member: C }` request, which executes and removes `C` from `self.members`; per `delete_member` (lines 356-379), only requests originated by `C` are cleaned — `R1`'s confirmation set `{B, C}` is untouched.
6. `A` (as request creator, or any remaining live member) calls `confirm(R1)` again is not allowed for the same member, but any other live member, e.g. `D`, calls `confirm(R1)` → `confirmations.len() + 1 = 3 >= num_confirmations (3)` → `execute_request` runs the `Transfer`.
7. The transfer executes with only 2 genuinely live confirmers (`B`, `D`) plus the stale `C` entry counted, i.e., below the configured 3-of-4 threshold — funds move despite an insufficient number of live authorizers.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
