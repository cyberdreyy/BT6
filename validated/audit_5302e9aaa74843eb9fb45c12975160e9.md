### Title
Missing Zero-Address Validation in `send_token` / `send_token_v2` Enables Permanent Fund Loss via Bridge — (`File: crates/sui-framework/packages/bridge/sources/bridge.move`)

---

### Summary

`send_token` and `send_token_v2` in the Sui native bridge validate only the *length* of the caller-supplied EVM `target_address` (must equal 20 bytes) but never check whether those 20 bytes are all zeros. A user who supplies `0x0000000000000000000000000000000000000000` as the recipient passes every on-chain guard, their bridged tokens are burned on Sui, and the resulting bridge message is permanently unclaimable on the EVM side — causing irreversible fund loss.

---

### Finding Description

`send_token` (and its v2 variant) perform exactly two checks on `target_address`:

```move
assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
assert!(token_amount > 0, ETokenValueIsZero);
``` [1](#0-0) 

Neither check rejects the all-zero address. The existing test suite confirms this is accepted silently:

```move
let eth_address = x"0000000000000000000000000000000000000000";
env.send_token(@0xABCD, chain_ids::eth_sepolia(), eth_address, btc);
``` [2](#0-1) 

After the assertion passes, `send_token_internal` immediately and irrevocably burns the coin:

```move
inner.treasury.burn(token);
``` [3](#0-2) 

A bridge message is then stored and awaits committee signatures. Once signed, anyone can submit it to the EVM `SuiBridge` contract via `transferBridgedTokensWithSignatures`, which calls `_transferTokensFromVault`:

```solidity
function _transferTokensFromVault(...) private ... {
    address tokenAddress = committee.config().tokenAddressOf(tokenID);
    require(tokenAddress != address(0), "SuiBridge: Unsupported token");
    if (tokenID == BridgeUtils.ETH) {
        vault.transferETH(payable(recipientAddress), amount);
    } else {
        vault.transferERC20(tokenAddress, recipientAddress, amount);
    }
    ...
}
``` [4](#0-3) 

The only zero-address guard here is for `tokenAddress`, not `recipientAddress`. The same pattern is present in `SuiBridgeV2.sol`: [5](#0-4) 

**ETH path:** `BridgeVault.transferETH` calls `recipientAddress.call{value: amount}("")` on `address(0)`. This low-level call succeeds; ETH is permanently destroyed. [6](#0-5) 

**ERC-20 path:** `BridgeVault.transferERC20` calls `SafeERC20.safeTransfer(token, address(0), amount)`. OpenZeppelin's ERC-20 implementation reverts on transfer to `address(0)`, so the EVM transaction always reverts. `isTransferProcessed[nonce]` is never set, so the message can be retried indefinitely — but every attempt reverts. The Sui tokens are already burned; the EVM tokens are permanently locked in the vault. [7](#0-6) 

---

### Impact Explanation

| Token type | Sui side | EVM side | Net result |
|---|---|---|---|
| ETH | Burned | Sent to `address(0)` (succeeds) | Permanent double-burn |
| ERC-20 | Burned | Vault transfer always reverts; message stuck | Permanent fund lock |

Both outcomes constitute irreversible loss of user funds. The Sui tokens are gone the moment `send_token` executes; there is no recovery path.

---

### Likelihood Explanation

- The function is `public` and callable by any SUI holder with no privilege requirement.
- The zero address is a 20-byte value that trivially satisfies the only existing guard (`length() == 20`).
- The existing test suite uses `x"0000000000000000000000000000000000000000"` as a *passing* test case, confirming the protocol treats it as valid input.
- A user could trigger this accidentally (copy-paste error, uninitialized variable in a script) or a malicious contract could route a victim's tokens through this path.

---

### Recommendation

Add a zero-address check in both `send_token` and `send_token_v2` immediately after the length assertion:

```move
assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
assert!(target_address != vector::tabulate(EVM_ADDRESS_LENGTH, |_| 0u8), EInvalidEvmAddress);
```

Equivalently, add a corresponding guard on the EVM side in `_transferTokensFromVault` (both `SuiBridge.sol` and `SuiBridgeV2.sol`):

```solidity
require(recipientAddress != address(0), "SuiBridge: Invalid recipient address");
```

---

### Proof of Concept

1. Obtain any supported bridged token (e.g., BTC, ETH, USDC) on Sui testnet.
2. Call `bridge::bridge::send_token` with:
   - `target_chain` = `chain_ids::eth_sepolia()`
   - `target_address` = `x"0000000000000000000000000000000000000000"`
   - `token` = any non-zero coin
3. Observe: transaction succeeds, coin is burned, `TokenDepositedEvent` is emitted with `target_address = 0x000...000`.
4. Wait for bridge committee signatures (or simulate with `approve_token_transfer`).
5. Call `SuiBridge.transferBridgedTokensWithSignatures` on Sepolia with the signed message.
   - **ETH token:** transaction succeeds; ETH is sent to `address(0)` and permanently destroyed.
   - **ERC-20 token:** transaction reverts every time due to OpenZeppelin's zero-address guard; bridge message is permanently stuck; vault funds are locked.

The test at `bridge_tests.move:261-268` already demonstrates step 2–3 passing without any revert. [8](#0-7)
