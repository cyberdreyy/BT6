### Title
Unprivileged cross-user DoS via requestID collision in gateway HTTP trigger handler - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The external report describes a DoS pattern where a strict, globally-shared state check (`getTVLByOwnerOfShares(...) > 0`) can be griefed by any unprivileged actor depositing a trivial amount, permanently blocking a legitimate operation for others. The analogous pattern in the gateway's HTTP trigger handler is a strict "must not already exist" check against a single shared, unscoped keyspace (`requestID`) that is fully controlled by the unprivileged caller, letting one user block another user's request.

### Finding Description
`httpTriggerHandler.setupCallback` stores in-flight requests in `h.callbacks`, a single `map[string]savedCallback` keyed only by the client-supplied JSON-RPC `req.ID` (the `requestID`), with no namespacing by workflow ID, workflow owner, or sender/session identity: [1](#0-0) [2](#0-1) 

The only validation performed on `requestID` is that it is non-empty and does not contain `/`; it can otherwise be any short/predictable/attacker-chosen string: [3](#0-2) 

Because the map key does not incorporate the caller's authenticated identity or the target workflow, any unprivileged client that can reach the HTTP trigger endpoint can pre-register (or race) a `savedCallback` entry under a `requestID` that another legitimate caller intends to use (or is expected to use, e.g. a well-known/predictable ID pattern used by an integration). When the legitimate caller later submits their request with that same `requestID`, `setupCallback` rejects it outright: [4](#0-3) 

This mirrors the reported bug class exactly: a strict "must not already be occupied/non-zero" precondition checked against global, attacker-writable state, allowing a trivial unprivileged action (submitting one JSON-RPC request with a chosen ID) to deny service to a legitimate, unrelated request.

### Impact Explanation
A malicious but otherwise unprivileged client (anyone able to reach the gateway's HTTP trigger endpoint, which is the public entry point for workflow execution) can cause targeted denial-of-service against other users' workflow executions by squatting on `requestID` values before the legitimate caller uses them. Since the map is shared globally across all workflows/owners rather than scoped per caller, this is a cross-user DoS, not merely self-inflicted: the attacker doesn't need the target workflow's key material or authorization — the check happens purely on `requestID`, before/independent of the aggregator setup — meaning it can be used to selectively block specific known request IDs used by integrators (e.g., idempotency keys generated by external systems that are guessable or observable).

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to know or guess the victim's intended `requestID` ahead of time (e.g., via observing/predicting an integrator's idempotency-key generation scheme, or via a race condition against retried requests using the same ID). It does not require any authentication bypass, secret knowledge, or privileged access — only the ability to submit a JSON-RPC `workflows.execute` request to the gateway with an attacker-chosen `id`, making it exploitable by any unprivileged actor with network access to the gateway trigger endpoint.

### Recommendation
Scope the `callbacks` map key by a tuple that includes the authenticated/authorized identity (e.g., `workflowID` + authorized key/session identity + `requestID`) rather than `requestID` alone, so that one caller cannot collide with another caller's in-flight request. Alternatively, generate/derive the internal tracking key server-side (e.g., hash of `workflowID + authorizedKey + requestID`) instead of trusting the raw client-supplied `requestID` as a global namespace.

### Proof of Concept
1. Attacker learns or predicts the `requestID` value ("R") that a victim's system will use for its next `workflows.execute` call to a given workflow (e.g., a deterministic idempotency key).
2. Attacker sends a well-formed `workflows.execute` JSON-RPC request with `id = "R"` (using any workflow they are authorized for, or one that passes validation up through `setupCallback`) slightly before the victim's real request arrives.
3. `setupCallback` inserts an entry into `h.callbacks["R"]`.
4. The victim's legitimate request with `id = "R"` arrives and is rejected via the `ErrConflict`/"in-flight request" check at [4](#0-3) , denying the victim's workflow execution until the attacker's entry times out or completes.

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
