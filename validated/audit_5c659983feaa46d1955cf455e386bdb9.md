### Title
Loss-adjusted withdraw receipts become payable at par after a later request overwrites `lastWithdrawRequest` — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` locates a user's loss-adjusted epoch solely via `lastWithdrawRequest[_user]` — the epoch of the *most recent* request. A holder who had a receipt in an epoch stopped via `stopEpochWithDuration(_lossAmount)` (funded only at the haircut `lossRecoveryPriceByEpoch[E]`) can request a new withdrawal in a later epoch `E+1`, overwriting the marker. The epoch-`E` receipt is then never haircut-cleared; it remains in `withdrawsRequestsByEpoch[_user][E]` and in the aggregate `withdrawsRequests[_user]`, and `_claimFundedWithdrawRequest` pays the full aggregate at par. This is the smart-contract analog of the CVE NULL-deref: the code dereferences a single "latest" pointer assuming it identifies the relevant record, while the actual record is stale/misidentified.

### Finding Description
On `requestWithdraw`, the vault records the receipt per-epoch and overwrites the scalar marker: [1](#0-0) 

At claim time the loss-adjusted path only looks at that one marker: [2](#0-1) 

If `lastWithdrawRequest[_user]` was advanced to a healthy epoch `E+1`, `lossRecoveryPriceByEpoch[E+1] == 0` and the function returns early without clearing the epoch-`E` basis. `_clearWithdrawClaimForEpoch` — the only code that deletes `withdrawsRequestsByEpoch[_user][E]` and decrements `withdrawsRequests[_user]` for that epoch — is never reached for `E`: [3](#0-2) 

`_claimFundedWithdrawRequest` then pays the aggregate `withdrawsRequests[_user]` (still containing the full epoch-`E` basis) at par once `epochNumber > lastWithdrawRequest[_user]`: [4](#0-3) 

The borrower only funded `claimBasis * lossRecoveryPrice / RECOVERY_FULL` for epoch `E` (the comment at line 797 confirms `pendingWithdraws` was already cleared at the funded, haircut amount), so the excess `(claimBasis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL)` is drawn from underlying that belongs to the strategy reserve, other pending claimants, or active tranche holders.

### Impact Explanation
Direct theft / insolvency. An attacker holding tranche tokens requests a withdrawal during a running epoch; the epoch is stopped with a loss (`stopEpochWithDuration`, `_lossAmount > 0`). Instead of claiming at the haircut, the attacker requests a second (even dust-sized) withdrawal in the next epoch, waits one more epoch, then calls `claimWithdrawRequest` through the CDO and receives the epoch-`E` basis at 100% plus the epoch-`E+1` receipt at par. Quantified loss: `claimBasis_E × (1 − lossRecoveryPriceByEpoch[E]/RECOVERY_FULL)`, up to the full haircut taken by the pool, paid from funds earmarked for other users.

### Likelihood Explanation
Requires only an unprivileged tranche-token holder and a manager-called `stopEpochWithDuration` with a loss (an honest, expected flow for distressed epochs — analogous to a partial default). No privileged misbehavior, timing race, or external manipulation is needed: the attacker merely makes an ordinary second `requestWithdraw` in the following epoch, which the protocol explicitly supports (the NOTE at line 323-324 even documents that a new request delays both claims). No existing guard stops it: the `epochNumber <= lastWithdrawRequest` gate passes after one more epoch, and the funded path has no check that earlier per-epoch receipts were loss-adjusted.

### Recommendation
In `_claimLossAdjustedWithdrawRequest` (and `_claimDefaultedWithdrawRequest`), iterate or look up the user's actual per-epoch receipts rather than relying on the single `lastWithdrawRequest` marker — e.g., check `lossRecoveryPriceByEpoch` for every epoch present in `withdrawsRequestsByEpoch[_user]`, or store per-epoch markers so a loss-adjusted epoch receipt cannot be absorbed into the aggregate funded claim. Alternatively, in `requestWithdraw`, settle/clear any outstanding loss-adjusted receipt before recording the new request.

### Proof of Concept
Foundry fork PoC (schematic, using the harness style of `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossAdjustedReceiptClaimedAtPar() external {
  // deposit as attacker (KYC'd), start epoch 1
  uint256 amount = 100_000 * ONE_SCALE;
  idleCDO.depositAA(amount);
  _startEpochAndCheckPrices(0);

  // attacker requests withdrawal of half their tranches in epoch E
  uint256 trancheHalf = IERC20(AAtranche).balanceOf(address(this)) / 2;
  uint256 basisE = cdoEpoch.requestWithdraw(trancheHalf, address(AAtranche)); // epoch E

  // borrower funds only the haircut amount; manager stops epoch with a loss
  vm.warp(cdoEpoch.epochEndDate() + 1);
  uint256 lossAmount = cdoEpoch.getContractValue() / 10; // 10% loss
  deal(defaultUnderlying, borrower, /* interest + funded(haircut) */);
  vm.prank(manager);
  cdoEpoch.stopEpochWithDuration(apr, 0, duration, lossAmount);
  // lossRecoveryPriceByEpoch[E] = ~0.9e18; pendingWithdraws cleared at funded amount

  // instead of claiming, attacker requests a dust withdrawal in epoch E+1
  _startEpochAndCheckPrices(1);
  cdoEpoch.requestWithdraw(1, address(AAtranche)); // lastWithdrawRequest := E+1

  // epoch E+1 ends normally, fully funded
  vm.warp(cdoEpoch.epochEndDate() + 1);
  deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws());
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  uint256 balPre = underlying.balanceOf(address(this));
  cdoEpoch.claimWithdrawRequest();
  uint256 claimed = underlying.balanceOf(address(this)) - balPre;

  // attacker was paid basisE at PAR although only ~90% was funded
  assertGt(claimed, basisE * strategy.lossRecoveryPriceByEpoch(E) / 1e18,
           "epoch-E haircut receipt paid at par");
}
```

Caveat: the exact epoch-indexing of `lossRecoveryPriceByEpoch` inside `stopEpochWithDuration` and whether it also zeroes `withdrawsRequestsByEpoch` for the loss epoch could not be fully verified within the search budget; if the loss path clears those per-epoch entries itself, the excess payment would instead surface as the double-counted aggregate (`withdrawsRequests[_user] -= normalAmount` never runs for `E`), which yields the same over-claim through `withdrawsRequests` at line 338.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
