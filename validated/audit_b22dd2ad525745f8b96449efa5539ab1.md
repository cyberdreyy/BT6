No vulnerability found for this question.

**Reasoning:**

The scenario described requires assuming that the receiving contract `R`'s *own* code — not attacker-authored — blindly takes call arguments and issues a `promise_batch_action_transfer_to_gas_key` host call parameterized by those args, sending `R`'s own balance to an attacker-chosen public key. That is a hypothetical vulnerable contract design, not a protocol/runtime bug.

Key facts that rule this out as a nearcore vulnerability:

1. `FunctionCallPermission` (narrow access key) restricts what the **transaction signer** (the caller) may attach — specifically it forbids `deposit > 0` on the outer `FunctionCall` action, per `verify_function_call_permission` at [1](#0-0)  and the delegate-action equivalent path exercised in [2](#0-1) . This restriction is about the caller's contribution to the receipt, not about what the receiving contract subsequently does with its own already-owned balance.

2. `promise_batch_action_transfer_to_gas_key` in `logic.rs` deducts the transfer amount from the *currently executing account's* balance via `self.result_state.deduct_balance(amount)` — i.e., from `R`'s own account balance, since the code is running as `R` — not from any gas/prepaid-gas pool and not from the attacker's account: [3](#0-2) . There's no mechanism here converting "prepaid gas" into spendable value; the amount transferred is ordinary NEAR balance the target contract already held.

3. This host function's job is simply to append a `TransferToGasKey` action to the outgoing receipt based on whatever arguments the executing contract's own wasm code supplies — exactly analogous to `promise_batch_action_transfer`, which likewise lets a contract move its own balance based on internal logic ( [4](#0-3) ). Nothing in the imports/logic layer is meant to authorize *who* the contract should pay; that authorization is entirely the responsibility of the contract's own business logic (e.g., checking `predecessor_account_id`, requiring a signature, requiring deposit, etc.), just as with a normal `transfer` call.

4. The rules explicitly state the attacker is "an ordinary client" with no control over `R`'s deployed bytecode. If `R`'s own contract genuinely forwards attacker-supplied public keys/amounts into a `transfer_to_gas_key` call without authorization checks, that is a bug in that specific dApp's contract, not in `near-vm-runner` or the runtime — the FunctionCallPermission was never designed to (and structurally cannot) constrain what a called contract chooses to do with funds it already owns.

Since the question requires assuming a specific vulnerable pattern in a third-party (victim's own) contract rather than a flaw in nearcore's access-key/runtime enforcement, and the value-conservation/authorization checks that nearcore does own (deposit-zero enforcement on the FunctionCall action itself, balance deduction from the correct account) function correctly, there is no reachable protocol-level vulnerability here.

fn verify_function_call_permission(
    function_call_permission: &FunctionCallPermission,
    tx: &Transaction,
) -> Result<(), InvalidTxError> {
    if tx.actions().len() != 1 {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::RequiresFullAccess,
        ));
    }
    let Some(Action::FunctionCall(function_call)) = tx.actions().get(0) else {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::RequiresFullAccess,
        ));
    };
    if function_call.deposit > Balance::ZERO {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::DepositWithFunctionCall,
        ));
    }

    pub fn promise_batch_action_transfer(
        &mut self,
        promise_idx: u64,
        amount_ptr: u64,
    ) -> Result<()> {
        self.result_state.gas_counter.pay_base(base)?;
        if self.context.is_view() {
            return Err(HostError::ProhibitedInView {
                method_name: "promise_batch_action_transfer".to_string(),
            }
            .into());
        }
        let amount = Balance::from_yoctonear(
            self.memory.get_u128(&mut self.result_state.gas_counter, amount_ptr)?,
        );

        let (receipt_idx, sir) = self.promise_idx_to_receipt_idx_with_sir(promise_idx)?;
        let receiver_id = self.ext.get_receipt_receiver(receipt_idx);
        let send_fee = transfer_send_fee(
            &self.fees_config,
            sir,
            self.config.eth_implicit_accounts,
            receiver_id.get_account_type(),
        );
        let exec_fee = transfer_exec_fee(
            &self.fees_config,
            self.config.eth_implicit_accounts,
            receiver_id.get_account_type(),
        );
        let burn_gas = send_fee.gas;
        let use_gas = burn_gas.checked_add(exec_fee.gas).ok_or(HostError::IntegerOverflow)?;
        self.result_state.gas_counter.pay_action_accumulated(
            send_fee,
            use_gas,
            ActionCosts::transfer,
        )?;
        self.result_state.deduct_balance(amount)?;
        self.ext.append_action_transfer(receipt_idx, amount);
        Ok(())
    }
