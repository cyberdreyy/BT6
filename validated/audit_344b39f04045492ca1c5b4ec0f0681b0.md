### Title
Removed multisig member's prior confirmations remain valid, allowing requests to execute below the effective live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` in `multisig2/src/lib.rs` only purges confirmations/requests that the removed member *originated* (`r.member == member`), but never scrubs that member's confirmation entries from the `confirmations` set of requests originated by *other* members. Because `confirm` simply counts entries in that set against `num_confirmations`, a confirmation cast by a member before removal continues to count toward execution after the member is deleted, letting a request execute with fewer live-member approvals than the configured threshold.

### Finding Description
`confirm` treats the size of `self.confirmations.get(&request_id)` as the number of valid approvals and executes the request once it reaches `num_confirmations`: [1](#0-0) 

When a member is removed via `DeleteMember`, `delete_member` only cleans up requests that member itself submitted, and only removes their `num_requests_pk` bookkeeping and membership entry — it does not scan other requests' `confirmations` sets to strip that member's prior confirmation string: [2](#0-1) 

This breaks the intended binding: `confirmations counted for a request == confirmations from currently-live members`. After a member is removed, a stale confirmation they made on someone else's still-pending request (`r.member != removed_member`) is left untouched in the `confirmations` HashSet and continues to count toward `num_confirmations` in the subsequent `confirm` call.

### Impact Explanation
This is a multisig-request-executed-below-threshold issue: a request (e.g. a `Transfer` of the contract's NEAR balance) can reach the required number of confirmations even though one of those confirmations came from an account that is no longer a member at execution time. The remaining live members believe `num_confirmations` live approvals are required, but the contract effectively only enforces `num_confirmations - 1` (or fewer, if multiple stale confirmations exist) live approvals plus phantom ones from ex-members. This maps to "a multisig request executed below threshold," a Critical-severity impact per the custody-binding rules — funds can move without the intended quorum of currently-authorized signers.

### Likelihood Explanation
The scenario only requires normal multisig operation: a member submits or confirms a request, is later removed (a routine operational event, e.g. offboarding or suspected key compromise — the very reason `DeleteMember` exists), and the pending request is confirmed to threshold afterward by the remaining honest members without realizing one of the counted confirmations originated from someone no longer authorized. No admin/owner exploit or redeploy is needed; it's a straightforward flow through `add_request` → `confirm` (by member A) → `DeleteMember(A)` executed → `confirm` (by remaining members) → execution.

### Recommendation
When executing `DeleteMember`, iterate over all pending requests' `confirmations` sets (not just requests originated by the removed member) and strip the removed member's `to_string()` entry from each, so any not-yet-executed request re-derives its live-confirmation count from only current members.

### Proof of Concept
1. Initialize a 3-of-5 `MultiSigContract` with members A, B, C, D, E.
2. Member D calls `add_request` with a `Transfer` action to an attacker-controlled account (request_id = R).
3. Member E calls `confirm(R)` — 1 confirmation recorded (E's string added to `confirmations[R]`).
4. A second member confirms too if desired, but crucially: the remaining members later legitimately remove E via a separate `DeleteMember { member: E }` request (`execute_request` → `delete_member`), because E's key was compromised or E left the organization.
5. `delete_member` only removes requests where `r.member == E` (i.e., requests E personally submitted); it does **not** touch `confirmations[R]`, so E's earlier confirmation on R (submitted by D) is left intact.
6. Two more live members (say B and C) call `confirm(R)`. `confirmations[R].len()` is now 3 (E's stale one + B + C) ≥ `num_confirmations` (3), so `execute_request` runs and the `Transfer` executes — even though only 2 currently-live members (B, C) plus D (originator, uncounted unless D also confirmed) actually approved it, one fewer live approval than the configured threshold.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
