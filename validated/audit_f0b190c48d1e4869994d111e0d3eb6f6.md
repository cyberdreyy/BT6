### Title
`setTrancheAPRSplitRatio`/`setFeeParams` apply the new split/fee retroactively to unaccrued yield — ([File: contracts/IdleCDO.sol])

### Summary
`IdleCDO.setTrancheAPRSplitRatio` and `IdleCDO.setFeeParams` update `trancheAPRSplitRatio`/`fee` without first running `_updateAccounting()`. All yield (or loss) accrued since the last deposit/withdraw/harvest is then split between AA and BB — and charged the new fee — at the *new* parameters on the next `_updateAccounting()` call, exactly like the JPEG'd `setDebtInterestApr` bug where the new rate was applied retroactively to the unaccrued period. The same pattern exists in `IdleCDOCreditVault`/`IdleCDOEpochVariant`, where accrued gains can persist unbooked for an entire epoch because deposits/withdrawals are paused while `isEpochRunning`.

### Finding Description
`_updateAccounting` reads the stored `trancheAPRSplitRatio` and `fee` and applies them to the whole pending delta `nav - lastNAV`:

```solidity
// contracts/IdleCDOCreditVault.sol:228-234
uint256 _aprSplitRatio = trancheAPRSplitRatio;
if (nav > _lastNAV) {
  unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;
}
(uint256 _priceAA, int256 _totalAAGain) = _virtualPriceAux(AATranche, nav, _lastNAV, _lastNAVAA, _aprSplitRatio);
(uint256 _priceBB, int256 _totalBBGain) = _virtualPriceAux(BBTranche, nav, _lastNAV, _lastNAVBB, _aprSplitRatio);
```

The setters write the parameter directly with no accrual step:

```solidity
// contracts/IdleCDO.sol:899-903
function setTrancheAPRSplitRatio(uint256 _trancheAPRSplitRatio) external virtual {
  _checkOnlyOwner();
  _checkAmountTooHigh((trancheAPRSplitRatio = _trancheAPRSplitRatio) > FULL_ALLOC);
}

// contracts/IdleCDO.sol:860-864
function setFeeParams(address _feeReceiver, uint256 _fee) external {
  _checkOnlyOwner();
  _checkIs0((feeReceiver = _feeReceiver) == address(0));
  _checkAmountTooHigh((fee = _fee) > MAX_FEE);
}
```

Deposits/withdraws correctly sequence `_updateAccounting()` *before* `_updateSplitRatio(...)` (`IdleCDO.sol:247-255`, `IdleCDOCreditVault.sol:200-208`), so the AYS auto-adjustment is not retroactive — but the owner setters bypass that ordering entirely. In `IdleCDOEpochVariant` deposits/requests are paused during a running epoch (`startEpoch` calls `_pause()`, `IdleCDOEpochVariant.sol:246`), so a large NAV delta can sit unbooked for a full `epochDuration` + `bufferPeriod`, and the very next accounting event (stopEpoch, or a `depositDuringEpoch` call) prices all of it at the new ratio/fee.

### Impact Explanation
Accrued-but-unbooked yield is redistributed between AA and BB holders, or to `feeReceiver`, at parameters that did not apply while the yield accrued — a direct violation of fair yield split and a theft of unclaimed yield. Quantified: for pending gain `G = nav - lastNAV`, BB holders lose `G * (newRatio - oldRatio) / FULL_ALLOC` when the ratio is raised (e.g., raising the split from 50% to 90% retroactively hands BB 40% of all accrued gains), and raising `fee` from `f1` to `f2` retroactively skims `G * (f2 - f1) / FULL_ALLOC` from all tranche holders. An unprivileged user can also trigger/sandwich the crystallization: any KYC'd lender calling `depositAA`/`depositBB` (or `depositDuringEpoch`) immediately after the owner tx executes `_updateAccounting` under the new parameters, permanently pricing the misallocation into `priceAA`/`priceBB`.

### Likelihood Explanation
The functions are only-owner, and the roles are assumed honest — but the harm is independent of intent: the bug is that there is no accounting checkpoint before the parameter change, identical in mechanism to the confirmed JPEG'd M-04. It triggers whenever a rate/fee change lands while `nav > lastNAV` (normal operating state for a live epoch), and an unprivileged user's next deposit crystallizes it, so no malicious role is required for the loss to materialize.

### Recommendation
Call an accounting checkpoint before writing the parameter in `setTrancheAPRSplitRatio` and `setFeeParams` (and consider `setMinAprSplitAYS`/`setIsAYSActive`), e.g. `_skimDonatedAssets()` + `_updateAccounting()` in the epoch variant, or a non-reverting variant of the `_forceUpdateAccounting` pattern, so the pending delta is split under the old parameters. This must handle the `Default` revert path in `_updateAccounting` (e.g., only accrue when `nav >= lastNAV` or reuse the skipDefaultCheck flow deliberately).

### Proof of Concept
Foundry-style PoC against `IdleCDO` (or `IdleCDOEpochVariant` mid-epoch):

```solidity
// Setup: AA and BB funded, strategy/token NAV has grown since last accounting
uint256 gain = cdo.getContractValue() - (cdo.lastNAVAA() + cdo.lastNAVBB());
assertGt(gain, 0);

uint256 priceBBBefore = cdo.virtualPrice(cdo.BBTranche());

// Owner raises AA split from e.g. 50% to 90% with no accrual
vm.prank(owner);
cdo.setTrancheAPRSplitRatio(90_000);

// Any unprivileged user crystallizes the retroactive split
vm.prank(attacker);
cdo.depositAA(1e18); // internally runs _updateAccounting at the NEW ratio

// BB lost (90%-50%) * gain worth of already-accrued yield
uint256 bbLoss = gain * (90_000 - 50_000) / 100_000;
assertApproxEqAbs(
  priceBBBefore * cdoBBSupply / 1e18 - cdo.lastNAVBB(), bbLoss, 1e2
);
```

Same pattern for `setFeeParams`: prank owner to raise `fee`, then any deposit crystallizes `gain * feeDelta / FULL_ALLOC` into `unclaimedFees` that was accrued under the old (lower) fee.
