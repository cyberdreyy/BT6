### Title
Race condition in Windows legacy CTRL_C signaling can misdirect termination signals across concurrently-running jobs - (File: helpers/process/killer_windows.go)

### Summary
`taskTerminate` (helpers/process/killer_windows.go, lines 60-111) manipulates process-wide Windows console attachment state (`FreeConsole`/`AttachConsole`/`GenerateConsoleCtrlEvent`) with no synchronization across concurrent invocations. Because console attachment is a property of the entire calling process (the `gitlab-runner` process), not of the individual goroutine handling a given job, two jobs terminating concurrently under `UseWindowsLegacyProcessStrategy=true` can interleave their `FreeConsole`/`AttachConsole(pid)` calls, causing `GenerateConsoleCtrlEvent` to be delivered to the wrong job's console group.

### Finding Description
`windowsKiller.Terminate()` (helpers/process/killer_windows.go, lines 31-42) is invoked per-job via `osKillWait.KillAndWait` (helpers/process/killer.go, lines 66-77), and each job's termination runs on its own goroutine with no shared lock found anywhere in `helpers/process/*.go` (only a `sync.Once` used for per-command job-object cleanup in `job_windows.go`, unrelated to console state).

Inside `taskTerminate`, when `UseWindowsLegacyProcessStrategy` is true, the sequence executed against the *runner process itself* is:
1. `FreeConsole()` — detach the runner process from its current console.
2. `AttachConsole(pid)` — attach the runner process to the console of the job's target process.
3. `SetConsoleCtrlHandler(nil, true)` — ignore Ctrl-C in the runner.
4. `GenerateConsoleCtrlEvent(CTRL_C_EVENT, pid)` — send Ctrl-C to whatever console the runner is currently attached to.
5. `FreeConsole()` / `AttachConsole(MaxUint32)` / `SetConsoleCtrlHandler(nil, false)` — restore state.

All of `FreeConsole`, `AttachConsole`, and the "current console" state are per-process Win32 concepts (the `kernel32.dll` calls act on the calling process, not the calling thread). If Job A's goroutine executes steps 1-2 (attaching the runner to A's console) and, before it reaches step 4, Job B's goroutine concurrently executes its own steps 1-2 (detaching the runner from A's console and attaching it to B's), then when A's goroutine finally calls `GenerateConsoleCtrlEvent`, it is delivered to whichever console the process is attached to at that moment — potentially B's — because there is no lock serializing this global state mutation across goroutines. Errors from the restoring calls are also intentionally swallowed via `multierror.Append`/`ErrorOrNil` and only logged as warnings, so a partially-successful/misdirected sequence does not fail loudly.

Existing checks/mitigations do not address this: there is no mutex, semaphore, or single-threaded dispatcher serializing calls into `taskTerminate`; `SetConsoleCtrlHandler` only affects whether the runner ignores the signal, not which console it is targeting; the job-object mechanism (`UseWindowsJobObject`) is a separate, unrelated kill path used for `ForceKill`, not for graceful `Terminate`.

### Impact Explanation
If misdirected, `CTRL_C_EVENT`/`CTRL_BREAK_EVENT` could interrupt a build/test process belonging to a *different, concurrently running* job than the one the Runner intended to terminate, potentially truncating output files, corrupting artifacts, or causing inconsistent state in that other job's workspace — even though that job was never supposed to be terminated. This matches the scoped impact (cross-job disruption to file I/O consistency), but it is a job-vs-job disruption between two jobs already running as sibling processes under the same Windows service/runner host, not a sandbox escape, credential leak, or unauthorized data access.

### Likelihood Explanation
Preconditions are specific and non-default: `UseWindowsLegacyProcessStrategy=true` must be explicitly configured (this is a legacy, non-default fallback), and it requires two or more jobs executing genuinely concurrently on the *same* Windows runner host/process (e.g. `concurrent` > 1 with the shell/custom executor on Windows), plus one of them being terminated (cancellation, timeout, or manual cancel) while the other is also mid-termination or at least mid-console-attach window. The race window per call is narrow (a handful of syscalls) but real, given the total absence of a mutex around this global mutable state. It is a genuine timing-dependent concurrency bug rather than a purely theoretical one, though reliably reproducing the exact misdirection (rather than just an error) in an automated test may require deliberately interleaving the two `taskTerminate` calls (e.g. via test hooks/instrumentation) since a naturally-timed test would only probabilistically trigger it.

### Recommendation
Serialize all `taskTerminate` console operations with a package-level mutex (e.g. `var consoleMu sync.Mutex` in `killer_windows.go`) so that the entire `FreeConsole → AttachConsole → SetConsoleCtrlHandler → GenerateConsoleCtrlEvent → restore` sequence for one job completes atomically with respect to any other concurrent `taskTerminate` call before another job's sequence can begin. Additionally, stop silently ignoring restoration errors (or at minimum log them at `Error` level and surface them) so operators can detect when this invariant has been violated in production.

### Proof of Concept
Go concurrency test in `helpers/process/killer_windows_test.go` (Windows-only, build-tagged):
```go
func TestConcurrentLegacyTerminateDoesNotCrossSignal(t *testing.T) {
    // Launch two long-running child processes (writer_a, writer_b) that each
    // continuously append timestamped lines to their own file, with
    // UseWindowsLegacyProcessStrategy = true and no CREATE_NEW_PROCESS_GROUP.
    cmdA, fileA := startWriterProcess(t, "a.log")
    cmdB, fileB := startWriterProcess(t, "b.log")

    killerA := newKiller(logger, cmdA)
    killerB := newKiller(logger, cmdB)

    var wg sync.WaitGroup
    wg.Add(1)
    go func() {
        defer wg.Done()
        killerA.Terminate() // should only affect writer_a
    }()
    // Do NOT terminate B; B should keep writing uninterrupted.
    wg.Wait()

    waitForExit(t, cmdA, 5*time.Second)
    // Assert B is still running / still appending new lines after A's Terminate returns.
    sizeBefore := fileSize(fileB)
    time.Sleep(2 * time.Second)
    sizeAfter := fileSize(fileB)
    assert.Greater(t, sizeAfter, sizeBefore, "writer_b must not receive Ctrl-C intended for writer_a")

    // Repeat with both A and B terminated at nearly the same instant to
    // assert each writer's file is truncated/interrupted only once, by its
    // own Terminate call, not the other's.
}
```
This is difficult to make fully deterministic without adding a test hook (e.g. an injectable delay or channel synchronization inside `taskTerminate` between `AttachConsole(pid)` and `GenerateConsoleCtrlEvent`) to force the interleaving; without such a hook the test is probabilistic and should be run with `-race` and repeated iterations to increase the chance of exposing the interleaving.
