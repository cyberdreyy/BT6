### Title
Mid-epoch deposits mint shares and fund borrower using declared rather than received amount - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`depositDuringEpoch` pulls `_amount` underlying from the depositor but mints tranche shares, records expected interest, mints strategy tokens, and sends `_amount` to the borrower without measuring the actual balance delta. [1](#0-0)  If the configured underlying transfers less than `_amount`, the deficit is consumed from vault-held funds while the attacker receives shares and expected-yield accounting for the full declared amount. [2](#0-1) 

### Finding Description
The normal credit-vault deposit path takes a pre-transfer balance, calls `_transferUnderlyingsFrom`, and mints using the observed balance delta. [3](#0-2)  In contrast, `depositDuringEpoch` calls `_transferUnderlyingsFrom` and continues to use the caller-controlled `_amount` throughout pricing and accounting. [4](#0-3) 

A qualifying attacker calls `depositDuringEpoch` while the epoch is running, mid-epoch deposits are enabled, AYS and programmable-borrower mode are disabled, the selected tranche already has supply, and the wallet is KYC-allowed. [5](#0-4)  For an underlying that burns or fees part of the transfer, the attacker can declare `D`, deliver `D - F`, and still receive shares computed from `D + trancheInterest`. [6](#0-5) 

The function then increases `expectedEpochInterest` by interest calculated on `D`, mints strategy-token accounting for `D`, and transfers the full `D` to the honest borrower. [7](#0-6)  Any existing vault balance covers the missing `F`, causing those assets to be lent to the borrower while tranche NAV reflects assets that were never contributed by the attacker. [2](#0-1) 

### Impact Explanation
The broken invariant is fair minting and solvency: one underlying unit contributed should produce only one underlying unit of tranche NAV and borrower funding. [2](#0-1)  For each deposit of declared amount `D` and shortfall `F`, existing participants absorb up to `F` of immediately misallocated borrower funding, while the attacker additionally receives inflated tranche shares and expected-interest accounting. [2](#0-1) 

### Likelihood Explanation
The function is directly callable by any allowed wallet during an active epoch and has no balance-delta check. [8](#0-7)  Exploitation depends on the vault being configured with an underlying whose `transferFrom` can deliver less than the requested amount; standard fixed-supply underlyings without transfer deductions do not expose the discrepancy. [1](#0-0) 

### Recommendation
Measure `received = token.balanceOf(address(this)) - balanceBefore` around the transfer, then use `received` consistently for guarded-limit checks, interest calculation, share minting, tranche NAV, strategy-token minting, and borrower funding. Alternatively, reject non-exact receipt with `if (received != _amount) revert`, matching the assumptions of the surrounding epoch accounting. [9](#0-8) 

### Proof of Concept
A Foundry fork PoC should configure or select a deployment whose `token()` is an ERC20 with an enabled transfer fee, seed an existing tranche supply and vault balance, allow the attacker's wallet, start an epoch in non-programmable/non-AYS mode, and execute:

```solidity
uint256 D = 1_000e6;
uint256 fee = D * feeBps / 10_000;
uint256 received = D - fee;

uint256 vaultBefore = token.balanceOf(address(cdo));
uint256 attackerSharesBefore = tranche.balanceOf(attacker);

vm.prank(attacker);
cdo.depositDuringEpoch(D, tranche);

assertEq(token.balanceOf(address(cdo)), vaultBefore + received);
assertGt(tranche.balanceOf(attacker), attackerSharesBefore);
```

The vault receives only `received`, but `_mintShares` records `D`, `expectedEpochInterest` uses `D`, `mintStrategyTokens` uses `D`, and the borrower is sent `D`. [2](#0-1)  A differential assertion against `received` demonstrates that NAV/share issuance and borrower funding are overstated by the transfer shortfall. [3](#0-2)

```text
  function depositDuringEpoch(uint256 _amount, address _tranche) external virtual returns (uint256 _minted) {
    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == BBTranche && !isBBDepositEnabled) ||
      isDepositDuringEpochDisabled ||
      skipDefaultCheck ||
      // programmable borrowers use APR=0 so mid-epoch deposits would dilute existing depositors
      isProgrammableBorrower ||
      // check if AYS is active as we don't support deposits during epoch in that case
      isAYSActive ||
      // check if epoch is still running even if not manually stopped yet
      !isEpochRunning || block.timestamp >= epochEndDate ||
      !isWalletAllowed(msg.sender)
    );

    if (_amount == 0) {
      return _minted;
    }

    uint256 _trancheTotSupply = _trancheSupply(_tranche);
    // Avoid pricing discontinuities for the first mid-epoch deposit in a tranche
    _checkNotAllowed(_trancheTotSupply == 0);

    _skimDonatedAssets();
    // Check that limit is not exceeded after removing skimmable raw donations.
    _guarded(_amount);
    _updateAccounting();

    // Get underlyings from user
    _transferUnderlyingsFrom(msg.sender, address(this), _amount);

    // interest for the remaining epoch plus the full buffer period
    // NOTE: _calcInterest already gives full‑epoch + full‑buffer interest for the whole epoch
    //   So when a user joins mid‑epoch, we take the fraction of that full‑period interest 
    //   that matches the time they actually remain plus the entire buffer
    uint256 buffer = bufferPeriod;
    uint256 remaining = epochEndDate - block.timestamp;
    uint256 interest = _calcInterest(_amount) *
      // the time the depositor actually participates (remaining epoch + full buffer)
      (remaining + buffer) /
      // the total time baked into the scaled APR (epoch + buffer).
      (epochDuration + buffer);

    uint256 expectedInt = expectedEpochInterest;
    uint256 pendingFees = pendingWithdrawFees;
    uint256 trancheExpected;
    // existing holders' share of net expected interest for the epoch (pre-deposit)
    // (exclude pendingWithdrawFees since they go to fee receivers, not tranche holders)
    if (expectedInt > pendingFees) {
      trancheExpected = _calcTrancheInterestShare(
        _netGainAfterFees(expectedInt - pendingFees, _calculateManagementFee(lastNAVAA + lastNAVBB, remaining)),
        _tranche
      );
    }
    // interest this deposit will earn for the tranche over the remaining time (net of fees)
    uint256 trancheInterest = _calcTrancheInterestShare(
      _netGainAfterFees(interest, _calculateManagementFee(_amount, remaining)),
      _tranche
    );
    // pre-deposit expected final NAV for existing holders.
    // This won't ever be zero as we checked _trancheTotSupply and we seed initial NAV at tranche creation
    uint256 expectedFinal = _lastSavedNAV(_tranche) + trancheExpected;

    // mint at a discounted price so depositor gets principal + its prorated interest at epoch end
    // A mid‑epoch depositor should get _amount + trancheInterest at epoch end.
    // So they need minted = (amount + trancheInterest) / priceEnd.
    // priceEnd = expectedFinal / _trancheTotSupply
    // so minted = (amount + trancheInterest) * _trancheTotSupply / expectedFinal
    _minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
    _mintShares(_tranche, msg.sender, _minted, _amount);

    // update expected epoch interest
    expectedEpochInterest += interest;
    // mint strategy tokens to this contract
    IdleCreditVault(strategy).mintStrategyTokens(_amount);
    // transfer underlyings to the borrower
    _transferUnderlyings(_borrower(), _amount);
```
