### Title
Decoder panic in `parse_confidential_transfer_fee_instruction` from missing account-count validation on `WithdrawWithheldTokensFromAccounts` - (File: `transaction-status/src/parse_token/extension/confidential_transfer_fee.rs`)

### Summary
`ConfidentialTransferFeeInstruction::WithdrawWithheldTokensFromAccounts` in the spl-token-2022 instruction parser indexes `account_keys[account_indexes[0]]` and `account_indexes[1]` before ever validating that `account_indexes` (the instruction's account list, fully attacker-controlled) actually has at least 2 elements — unlike its sibling arm `WithdrawWithheldTokensFromMint`, which calls `check_num_token_accounts(account_indexes, 4)?` first. This mirrors the report's root-cause pattern: trusting untrusted, attacker-supplied input length/shape before using it to index/write state, with no bounds check.

### Finding Description
`parse_confidential_transfer_fee_instruction` is reached through `parse_token` → `TokenInstruction::ConfidentialTransferFeeExtension` in `transaction-status/src/parse_token.rs:624-635`, which is itself invoked from `parse_instruction::parse` (`transaction-status/src/parse_instruction.rs:96-123`) whenever an RPC client requests `jsonParsed` encoding for a transaction/instruction whose program id is `spl_token_2022`.

In `transaction-status/src/parse_token/extension/confidential_transfer_fee.rs:80-127`: [1](#0-0) 
the `WithdrawWithheldTokensFromAccounts` arm decodes `num_token_accounts` from instruction data and computes `first_source_account_index = account_indexes.len().saturating_sub(num_token_accounts as usize)` (safe due to `saturating_sub`), but then unconditionally does: [2](#0-1) 
`account_keys[account_indexes[0] as usize]` and `account_keys[account_indexes[1] as usize]` — with **no prior `check_num_token_accounts` call**. Every other extension-instruction arm in this module and in `parse_token.rs` (e.g. `WithdrawWithheldTokensFromMint` at lines 37-79 of the same file, or `DefaultAccountStateExtension`/`MemoTransferExtension`/etc. in `parse_token.rs:534-691`) validates the minimum account count first via `check_num_token_accounts`. This arm is the outlier.

If `account_indexes.len()` is 0 or 1, `account_indexes[0]` or `account_indexes[1]` indexing panics (Rust out-of-bounds index panic), unwinding through `parse_confidential_transfer_fee_instruction` → `parse_token` → `parse_instruction::parse` → the RPC transaction-encoding path.

Crucially, this instruction-list parsing operates purely on the **raw compiled instruction accounts array and data bytes as authored in the transaction message**, independent of whether the instruction executed successfully on-chain. An attacker can craft and submit (via `sendTransaction`) a transaction whose message contains an instruction:
- `program_id_index` → the `spl_token_2022` program id
- `accounts` → `[]` or a single-element vector
- `data` → `[TokenInstruction::ConfidentialTransferFeeExtension discriminant, ConfidentialTransferFeeInstruction::WithdrawWithheldTokensFromAccounts sub-discriminant, num_token_accounts byte, ...]`

The transaction will fail at runtime (the vote/token program will reject it for insufficient accounts), but Agave still records the transaction and its exact message/instructions in blockstore transaction-status metadata, since failed transactions are stored with their original message. Any unprivileged client can then call `getTransaction` (or `getConfirmedTransaction`/block-fetching RPCs) with `encoding: "jsonParsed"` for that signature, triggering `parse_token` → the panicking arm inside the RPC-handling thread.

### Impact Explanation
This is a decoder panic reachable from a single unprivileged JSON-RPC call (`getTransaction`/`getBlock` with `jsonParsed` encoding) after submitting one attacker-controlled transaction. Per the validation criteria, "decoder panic and misreporting" from account/instruction parsing is an explicitly accepted impact class. Depending on whether the RPC request-handling path wraps encoding in `catch_unwind`, this could crash or poison the RPC processing thread/task, causing denial of service for that RPC node when serving parsed transaction data for the crafted transaction. I could not fully verify from the available index whether jsonrpc-http-server's request dispatch wraps handler execution in `panic::catch_unwind` (which would downgrade this to a caught error rather than a full crash); this is a real limitation of my analysis given the tool constraints in this session.

### Likelihood Explanation
High: The attacker only needs to submit one arbitrarily crafted transaction (which can fail at the SPL Token-2022 program level while still being stored with its original instruction encoding) and then issue a single `getTransaction`/`getBlock` RPC call with `jsonParsed` encoding to reach the vulnerable code path — no elevated privileges, no special timing, and no dependency on transaction success.

### Recommendation
Add an early `check_num_token_accounts(account_indexes, 2)?` (matching the pattern used by the sibling `WithdrawWithheldTokensFromMint` arm and by essentially every other extension parser in this crate) at the top of the `ConfidentialTransferFeeInstruction::WithdrawWithheldTokensFromAccounts` branch in `transaction-status/src/parse_token/extension/confidential_transfer_fee.rs`, before any indexing into `account_indexes` or `account_keys`, and ensure `first_source_account_index` slicing is likewise guarded.

### Proof of Concept
1. Build a `CompiledInstruction` with `program_id_index` pointing at the `spl_token_2022` program id, `accounts: vec![]` (or a single-element vec), and `data` set to:
   - byte 0: the `TokenInstruction::ConfidentialTransferFeeExtension` discriminant
   - byte 1: the `ConfidentialTransferFeeInstruction::WithdrawWithheldTokensFromAccounts` sub-discriminant
   - remaining bytes: a valid `WithdrawWithheldTokensFromAccountsData` payload (any `num_token_accounts` value, e.g. 0 or 1)
2. Call `transaction_status::parse_token::parse_token(&instruction, &account_keys)` directly (unit-test level) or wrap it in a transaction and query via `getTransaction`/`getBlock` with `"encoding": "jsonParsed"`.
3. Observe the panic at `account_keys[account_indexes[0] as usize]` / `account_indexes[1]` in `confidential_transfer_fee.rs:89-107` due to `account_indexes.len() < 2`. [3](#0-2)
