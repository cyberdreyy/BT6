### Title
Job-object breakaway combined with process-tree-based taskkill allows an unprivileged job to spawn a survivor process that keeps writing/deleting inside the reused workspace - ([File: helpers/process/killer_windows.go], [File: helpers/process/job_windows.go])

### Summary
`CreateJobObject` deliberately sets `JOB_OBJECT_LIMIT_BREAKAWAY_OK`, which lets any descendant process created with `CREATE_BREAKAWAY_FROM_JOB` leave the job object entirely. [1](#0-0)  The runner's cleanup path, `windowsKiller.ForceKill`, does not rely on job-object membership at all for the primary kill - it shells out to `taskkill /F /T /PID <pid>`, which kills descendants by walking the live Win32 process-tree (parent PID + creation-time), and only afterwards calls `closeJobObject()` as a secondary safety net. [2](#0-1) [3](#0-2)  A malicious job script can defeat both mechanisms by (1) launching a helper with `CREATE_BREAKAWAY_FROM_JOB` (permitted because of the flag above) and (2) having the immediate breakaway process spawn a grandchild and then exit, severing the Win32 parent-child link that `taskkill /T` depends on. The grandchild is then invisible to both the tree-walk kill and the job-object `KILL_ON_JOB_CLOSE` limit, and can keep an open handle into `CommandOptions.Dir` after the executor reports the job finished and the directory is reused.

### Finding Description
- `AssignPidToJobObject` puts the job's top-level process into a job object created with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_BREAKAWAY_OK`. [4](#0-3) [5](#0-4)  The `BREAKAWAY_OK` flag is a prerequisite that lets any process spawned within the job use `CREATE_BREAKAWAY_FROM_JOB` to leave job-object control - this is opt-in by the child, but the parent job explicitly permits it.
- When the runner wants to stop the job, `Terminate` first tries a console `CTRL_BREAK_EVENT`/`CTRL_C_EVENT`, falling back to `ForceKill`. [6](#0-5)  `ForceKill` calls `taskKill(pid)` (i.e., `taskkill /F /T /PID`) and then `pk.cmd.closeJobObject()`. [2](#0-1) 
- `taskkill /T` recursively kills the process tree by matching parent PID and process creation timestamp in the live Win32 process table - it does **not** consult job-object membership. If an attacker-controlled child breaks away from the job and then also disconnects from the Win32 parent-child chain (e.g., the immediate breakaway process spawns a grandchild and exits, so the grandchild's recorded "parent" is a PID that no longer corresponds to a live ancestor in the target's lineage), `taskkill /T` will not find or kill that grandchild.
- Because the grandchild also isn't a job member (it inherited breakaway eligibility from its immediate parent, which itself used `CREATE_BREAKAWAY_FROM_JOB`), `closeJobObject()`'s `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` will not terminate it either, since `KILL_ON_JOB_CLOSE` only affects processes still assigned to the job.
- Nothing in `osCmd.Start`/`Wait`/`closeJobObject` verifies that all descendants have actually terminated before returning; `Wait()` simply calls `c.internal.Wait()` (which only waits on the direct child) and closes the job handle. [7](#0-6)  There is no post-kill verification that the workspace directory is free of active handles before the executor reuses it for a subsequent job.

### Impact Explanation
A surviving orphaned process retains a live file handle inside the job's `CommandOptions.Dir` (build/cache directory). After `ForceKill` returns and the runner believes the job's process tree is gone, it proceeds to reuse the same working directory (e.g., for a subsequent pipeline job using the same runner/build-dir, or for artifact/cache packaging that happens right after cleanup). The still-running survivor can continue writing or deleting files there, allowing cross-job cache/artifact poisoning or corruption of files being read/packaged by the next job — a concrete break of the "file operations must stay within intended, currently-owned build/cache/artifact roots" invariant, since the writer is no longer an owned/tracked process of that job at all.

### Likelihood Explanation
Preconditions are realistic for a single, well-known configuration option (`UseWindowsJobObject=true`, used by shell/custom executors on Windows). [8](#0-7)  The technique required (spawn with `CREATE_BREAKAWAY_FROM_JOB`, then have that process spawn a grandchild and exit to sever the Win32 tree link) is standard, well-documented Windows process-tree evasion and fully achievable from an unprivileged CI job script (batch/PowerShell/compiled helper) with no special privileges — `CREATE_BREAKAWAY_FROM_JOB` requires only that the job object permit it, which `CreateJobObject` does unconditionally. This is reliably reproducible, not merely theoretical.

### Recommendation
- Do not set `JOB_OBJECT_LIMIT_BREAKAWAY_OK` by default; only enable it for use cases (e.g. specific executors) that explicitly need to launch long-lived detached helpers, and document/gate it behind an opt-in setting rather than always-on.
- If breakaway must be supported, do not rely solely on `taskkill /T`'s process-tree walk for termination. Instead, enumerate all currently-known job-associated PIDs via `QueryInformationJobObject`/`IsProcessInJob` before allowing breakaway, or use `TerminateJobObject` (which handles all *still-assigned* members) plus an explicit post-kill scan (e.g., via a snapshot of handles open under `CommandOptions.Dir`) before signaling directory reuse.
- Add a verification/wait step after `ForceKill`/`closeJobObject` that confirms no process still holds open handles under `CommandOptions.Dir` (e.g., using `RestartManager`/handle enumeration APIs) before the executor marks the workspace as free for reuse.

### Proof of Concept
Integration test (Windows-only), extending `helpers/process/killer_integration_test.go`:
1. Set `UseWindowsJobObject = true`, `CommandOptions.Dir = <tempDir>`.
2. Start a script/binary that:
   - Immediately spawns a child process with `CREATE_BREAKAWAY_FROM_JOB` set in `SysProcAttr.CreationFlags`.
   - That breakaway child spawns a grandchild (also inheriting no job/tree link) which loops writing `time.Now()` into `marker.txt` in `CommandOptions.Dir` every second, then the breakaway child exits immediately (severing the Win32 parent link).
3. Call `windowsKiller.ForceKill()` on the top-level command's pid; assert it returns without error.
4. Wait 3+ seconds and read `marker.txt` - assert its timestamp keeps advancing (proving a live writer still exists after `ForceKill`).
5. Reuse `CommandOptions.Dir` for a "second job" (e.g., write a build artifact into the same dir) and assert its content gets corrupted/overwritten by the still-running grandchild, demonstrating cross-job poisoning.

```go
func CreateJobObject() (windows.Handle, error) {
	jobObj, err := windows.CreateJobObject(nil, nil)
	if err != nil {
		return 0, fmt.Errorf("creating job object: %w", err)
	}

	info := windows.JOBOBJECT_EXTENDED_LIMIT_INFORMATION{
		BasicLimitInformation: windows.JOBOBJECT_BASIC_LIMIT_INFORMATION{
			LimitFlags: windows.JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE |
				windows.JOB_OBJECT_LIMIT_BREAKAWAY_OK, // Allow subprocesses to explicitly avoid termination using CREATE_BREAKAWAY_FROM_JOB
		},
	}

	if _, err = windows.SetInformationJobObject(
		jobObj,
		windows.JobObjectExtendedLimitInformation,
		uintptr(unsafe.Pointer(&info)),
		uint32(unsafe.Sizeof(info))); err != nil {
		return 0, fmt.Errorf("setting job object information: %w", err)
	}

	return jobObj, nil
}
```

```go
func AssignPidToJobObject(pid int, jobObject windows.Handle) error {
	procHandle, err := FindProcessHandleFromPID(pid)
	if err != nil {
		return fmt.Errorf("failed to retrieve handle for process: %w", err)
	}
	defer windows.CloseHandle(procHandle)

	return AssignProcessToJobObject(procHandle, jobObject)
}
```

```go
func (pk *windowsKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := taskKill(pk.cmd.Process().Pid)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}

	pk.cmd.closeJobObject()
}
```
