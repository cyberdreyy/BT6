### Title
Deposits and withdrawals execute at an implicitly trusted price with no expected-price bound — owner parameter changes landing before inclusion reprice the user's fill - (File: contracts/IdleCDOCreditVault.sol)

### Summary
The external finding is a missing "believed price" check: `KnightingRound.buy` executes at whatever `tokenOutPrice` is stored at inclusion time, so a governance `setTokenOutPrice` transaction ordered before the user's `buy` silently reprices the trade. The same structure exists in the credit vaults: `depositAA`/`depositBB` (and the withdraw/request paths) mint or burn tranche tokens at whatever `_tranchePrice` is produced by `_updateAccounting` at inclusion time, and that price is a function of owner/manager-controlled parameters (`fee`, `trancheAPRSplitRatio` / AYS bounds, instant-withdraw APR delta). Neither entry point accepts an expected-price or min-shares parameter, so a privileged parameter update ordered before a user's transaction reprices the fill.

### Finding Description
`_deposit` in `IdleCDOCreditVault` mints tranche tokens at `_tranchePrice(_tranche)` computed inside the same transaction, with no user-supplied bound: [1](#0-0) [2](#0-1) 

The price is recomputed in `_updateAccounting`, which first accrues a management/performance `fee` into `unclaimedFees` and then splits the pending gain between AA and BB using the stored `trancheAPRSplitRatio`: [3](#0-2) [4](#0-3) 

Both `fee` and the split-ratio inputs (`trancheAPRSplitRatio` / `minAprSplitAYS` / `isAYSActive`, applied in `_updateSplitRatio` at line 386+) are owner/manager-settable storage. The same pattern holds in `IdleCDO._deposit`, which mints at current price after `_updateAccounting` with no bound: [5](#0-4) [6](#0-5) 

Scenario:
1. Lender observes `virtualPrice(AATranche)` = P and a favorable pending-gain split, signs `depositAA(amount)`.
2. The manager's `setFee`/split-ratio update (or an epoch transition such as `stopEpochWithDuration` / instant-withdraw APR delta change in the credit vault) is mined first.
3. The lender's deposit executes `_updateAccounting` under the new parameters: more of the pending gain is routed to `unclaimedFees` or to the BB class, the realized mint price is worse than P, and the lender receives fewer tranche tokens for the same `amount` — with no way to express the price they agreed to.

### Impact Explanation
The user pays a price they did not consent to. The loss equals the minted-share shortfall versus the quoted `virtualPrice`, bounded by (pending interest) × (fee/split delta), which can be the full pending gain for large deposits into a vault with accrued interest; the skimmed value accrues to `feeReceiver`/`unclaimedFees` or to the opposite tranche class. This is the identical harm to the reported finding: transacting at a price unknown to the user at signing time, with no revert path.

### Likelihood Explanation
Parameter updates and epoch transitions are routine manager operations, so ordering collisions are plausible whenever deposits are submitted against stale `virtualPrice` quotes. An unprivileged attacker cannot set the parameters, but cannot be required to — the victim's loss materializes purely from transaction ordering around honest privileged calls, matching the original finding's "collision" scenario. Severity is bounded because losses are limited to the pending-gain slice repriced by the parameter delta, not the principal.

### Recommendation
Add a `believedPrice`/`minSharesOut` (and symmetrically `minUnderlyingOut` for withdrawals/claims) parameter to the deposit and withdraw entry points in `IdleCDOCreditVault`/`IdleCDO`, and revert if the realized `_tranchePrice` after `_updateAccounting` deviates beyond the bound — mirroring the upstream fix of checking `believedPrice == tokenOutPrice`. The `TrancheWrapper`/`IdleTokenWrapper` `deposit`/`mint`/`redeem` functions, which also execute at the live `virtualPrice`/`tokenPrice` with no bound (contracts/TrancheWrapper.sol:81-110, contracts/IdleTokenWrapper.sol:98-115), should forward the same check.

### Proof of Concept
A Foundry fork PoC would: (1) seed a credit vault with AA+BB deposits and warp to accrue pending interest; (2) quote `virtualPrice(AATranche)` and the expected minted shares for a victim deposit; (3) in the same block, order a manager `setFee`/split-ratio update before the victim's `depositAA`; (4) assert the minted shares are strictly less than the quoted amount while the user's underlying is fully taken, quantifying the shortfall. I could not fully verify the exact setter names/signatures on `IdleCDOCreditVault` within the available iterations — `setFee`, the split-ratio configuration path and the instant-withdraw APR delta setter should be confirmed directly in the contract before writing the PoC.

```text
  function _updateAccounting() internal virtual returns (bool shutdown) {
    _accrueManagementFee();
    uint256 _lastNAVAA = lastNAVAA;
    uint256 _lastNAVBB = lastNAVBB;
    uint256 _lastNAV = _lastNAVAA + _lastNAVBB;
    uint256 nav = getContractValue();
    uint256 _aprSplitRatio = trancheAPRSplitRatio;
    // If gain is > 0, then collect some fees in `unclaimedFees`
    if (nav > _lastNAV) {
      unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;
    }
    (uint256 _priceAA, int256 _totalAAGain) = _virtualPriceAux(AATranche, nav, _lastNAV, _lastNAVAA, _aprSplitRatio);
    (uint256 _priceBB, int256 _totalBBGain) = _virtualPriceAux(BBTranche, nav, _lastNAV, _lastNAVBB, _aprSplitRatio);
    lastNAVAA = uint256(int256(_lastNAVAA) + _totalAAGain);
    lastNAVBB = uint256(int256(_lastNAVBB) + _totalBBGain);
```

```text
  function _mintSharesAtCurrPrice(uint256 _amount, address _to, address _tranche) internal virtual returns (uint256 _minted) {
    // calculate # of tranche token to mint based on current tranche price: _amount / tranchePrice
    _minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche);
    _mintShares(_tranche, _to, _minted, _amount);
```
