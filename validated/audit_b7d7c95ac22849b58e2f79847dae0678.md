### Title
Post-default instant withdraw requests are untracked and paid at par from the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestInstantWithdraw` lacks the `defaultRecoveryFinalized` guard that `requestWithdraw` has. After borrower default is finalized, an attacker can mint a new instant-withdraw receipt that is never registered as a defaulted claim and is paid out 1:1 by `claimInstantWithdrawRequest` from underlying that backs the `defaultRecoveryReserve`, stealing recovery funds belonging to defaulted-epoch claimants.

### Finding Description
In `requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:247-257), when `defaultRecoveryFinalized` is true the vault routes the request into `postDefaultRequests`, which are explicitly "already priced after the haircut and backed by the reserve". `requestInstantWithdraw` (lines 356-375) has no equivalent branch: it calls `_ensureDefaultRecoveryInitialized()`, mints a strategy-token receipt to the user, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]` and `pendingInstantWithdraws` regardless of `defaultRecoveryFinalized`.

On claim, `claimInstantWithdrawRequest` (lines 380-393) only invokes `_claimDefaultedInstantWithdrawRequest` when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. Even when that branch runs, `_claimDefaultedInstantWithdrawRequest` (lines 842-856) only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — receipts minted in a later epoch have zero basis there, so nothing is haircutted. Execution then falls through to burn `instantWithdrawsRequests[_user]` and call `_transferFundedClaim(_user, amount)` at par.

Post-finalization, the only underlying held by the strategy is `defaultRecoveryReserve`, which is meant to be paid exclusively through `_transferDefaultRecovery` at `defaultRecoveryPrice`. A post-default instant receipt is paid as a "funded" claim even though the borrower never funded it: `collectInstantWithdrawFunds` is only invoked by the CDO during normal epoch flow, and the new `pendingInstantWithdraws` increment happens after `defaultPendingClaimBasis`/`finalizeDefaultRecovery` already ran. This is the analog of XSA-224's "loss of grant trackability": a receipt (grant reference) is created that the accounting layer does not associate with any funded or haircutted claim, so it is honored at par against funds reserved for others.

### Impact Explanation
Any KYC-passing lender holding tranche tokens (or strategy-token receipts) can, after `finalizeDefault`, request an instant withdrawal and immediately claim it 1:1, draining underlying that was reserved to pay defaulted-epoch claimants at `defaultRecoveryPrice`. Each claimed token directly reduces the recovery reserve available to legitimate claimants, so the attacker can extract up to the full remaining `defaultRecoveryReserve` while honest claimants' payouts fall below the finalized recovery ratio — direct theft of reserved funds with quantified loss equal to the amount claimed beyond the haircut.

### Likelihood Explanation
Likelihood hinges on the CDO still forwarding instant-withdraw requests after default. `requestInstantWithdraw` is `_onlyIdleCDO()` and the vault itself imposes no post-default or epoch-phase check (unlike `requestWithdraw`, which explicitly handles the post-default case), so the strategy-side accounting bug is unconditional. I could not fully trace `IdleCDOEpochVariant`/`IdleCDOCreditVault`'s post-default request routing in the available iterations; if the CDO blocks instant requests when `defaulted()` is set, the attack surface narrows to instant requests in flight between default and finalization, which still hit the same untracked-epoch payment path. The asymmetric guarding (present in `requestWithdraw`, absent in `requestInstantWithdraw`) indicates the path was not considered.

### Recommendation
Add the same post-default handling to `requestInstantWithdraw` as `requestWithdraw`: either revert when `defaultRecoveryFinalized` is true, or route the receipt into a haircut-aware bucket (e.g., record it under `postDefaultRequests` semantics paid from reserve at par only if pre-haircut). Additionally, make `claimInstantWithdrawRequest` reject or haircut receipts in `instantWithdrawsRequestsByEpoch` entries for epochs other than funded ones, and ensure `_transferFundedClaim` can never pay from `defaultRecoveryReserve` balances.

// Foundry fork PoC (scaffold; adapt to test/foundry/IdleCreditVault.t.sol helpers)
function testPostDefaultInstantWithdrawDrainsRecovery() external {
    // Setup: deposit, run epoch, stopEpoch, borrower default, finalizeDefault
    // with recoveryRatio < 1 so defaultRecoveryReserve > 0 and
    // defaultRecoveryFinalized == true. (reuse _checkDefault / finalizeDefault helpers)
    uint256 recovered = ...;
    vm.startPrank(manager);
    IERC20Detailed(underlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    uint256 reservePre = IdleCreditVault(address(strategy)).defaultRecoveryReserve();

    // Attacker: a tranche holder post-default requests an instant withdraw
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 100e6); // or transfer tranche tokens to attacker
    uint256 trancheBal = IERC20Detailed(address(AAtranche)).balanceOf(attacker);

    // CDO forwards to strategy.requestInstantWithdraw -> no defaultRecoveryFinalized check
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(trancheBal, address(AAtranche)); // instant path when enabled

    // Claim pays at par via _transferFundedClaim instead of haircutted reserve payout
    uint256 balPre = IERC20Detailed(underlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 paid = IERC20Detailed(underlying).balanceOf(attacker) - balPre;

    assertGt(paid, trancheBal * strategy.defaultRecoveryPrice() / 1e18);
    // reserve invariant broken: funded claim consumed recovery reserve
    assertLt(strategy.defaultRecoveryReserve() + paid, reservePre + paid); // reserve not decremented
}
