### Title
Unfiltered backend error message disclosure via `jsonAPIError` in `AuthenticateByToken` auth failure path - ([File: core/web/auth/auth.go, core/web/auth/helpers.go])

### Summary
When `AuthenticateByToken` encounters a non-`sql.ErrNoRows`/non-`ErrUserSessionExpired` error from `FindUserByAPIToken`, it returns the raw error unchanged, and the `Authenticate` middleware forwards it straight to `jsonAPIError`, which serializes `err.Error()` verbatim into the JSON response body sent to the unauthenticated caller.

### Finding Description
`AuthenticateByToken` in [1](#0-0)  calls `authr.FindUserByAPIToken(ctx, token.AccessKey)`. If the returned error is not `sql.ErrNoRows` or `clsessions.ErrUserSessionExpired`, the function returns the error unmodified (`return err`), instead of wrapping it in `auth.ErrorAuthFailed` as is done for the expected "not found" case.

This error then propagates through `Authenticate` in [2](#0-1) , which calls `jsonAPIError(c, http.StatusUnauthorized, err)`.

`jsonAPIError` in [3](#0-2)  checks whether `err` is a `*models.JSONAPIErrors`; if not (which is the case for a raw DB/driver error), it falls through to `c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))`, placing the full `Error()` string of the internal error directly into the `detail` field of the JSON response body returned to the caller, as shown in [4](#0-3) .

The concrete `FindUserByAPIToken` implementation used for the local-auth provider is a thin wrapper over a raw SQL query using the attacker-supplied `X-API-KEY` header value as a parameter: [5](#0-4) . Any error surfaced by the SQL driver/connection layer other than "no rows" (e.g., driver-level errors, timeouts, connection failures, malformed/oversized input triggering a database-side error) is passed through unfiltered to the HTTP response. No middleware, role check, or presenter sits between this error and the JSON response — `jsonAPIError` performs no redaction of non-`JSONAPIErrors` error types.

### Impact Explanation
This is an information-disclosure primitive reachable by a fully unauthenticated attacker (anyone hitting any API-key protected route with the `X-API-KEY`/`X-API-SECRET` headers). Depending on what error the datastore layer surfaces (driver error strings, connection state, timeout details), the attacker could learn internal implementation details about the datastore layer that aid further reconnaissance/attacks. This matches Chainlink's "information disclosure aiding further exploitation" bounty impact class — it does not directly grant fund movement or auth bypass, but it weakens defense-in-depth by exposing internal error content to unauthenticated requests.

### Likelihood Explanation
Exploitability is constrained: PostgreSQL parameterized queries (`$1`) make it hard to trigger arbitrary driver errors purely by manipulating the header value, since the value is bound as a parameter rather than interpolated into SQL. Realistic triggers are more likely to be transient conditions (DB connection pool exhaustion, context deadline exceeded, network blips) rather than attacker-controlled payloads reliably forcing a specific error. Thus the attacker can observe this behavior opportunistically (any legitimate transient DB error during their request) but cannot reliably force a specific internal string to appear on demand. No privileged access is required to attempt it.

### Recommendation
In `AuthenticateByToken` (and analogously in `AuthenticateExternalInitiator`), do not propagate raw datastore errors to the HTTP layer. Wrap/replace any non-`sql.ErrNoRows` error with a generic, sanitized error (e.g., `auth.ErrorAuthFailed` or a fixed `"internal error"` message) while logging the original error server-side for diagnostics. Additionally, harden `jsonAPIError` to never emit `err.Error()` directly for errors that aren't already `*models.JSONAPIErrors`, and instead map unknown/internal errors to a fixed, non-descriptive message.

### Proof of Concept
Go unit test plan:
1. Create a mock `auth.Authenticator` (using the existing mocks, e.g. `core/sessions/mocks/authentication_provider.go` pattern) whose `FindUserByAPIToken` returns a wrapped error such as `errors.New("pq: connection to server at \"10.0.0.5\", port 5432 failed")` (simulating a non-`sql.ErrNoRows` DB error).
2. Set up a `gin` test router with `auth.Authenticate(mockAuthr, auth.AuthenticateByToken)` middleware wrapping a dummy handler.
3. Send a request with `X-API-KEY` and `X-API-SECRET` headers set to any non-empty values.
4. Assert the response status is `401`.
5. Assert the JSON response body's `errors[0].detail` field does NOT contain the raw error string/sensitive substrings (e.g., does not contain `"10.0.0.5"` or `"connection"`); currently, this assertion FAILS, confirming the raw error text is echoed back, e.g. `{"errors":[{"detail":"pq: connection to server at \"10.0.0.5\", port 5432 failed"}]}`.

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
```

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```

// NewJSONAPIErrorsWith creates an instance of JSONAPIErrors populated with this
// single detail.
func NewJSONAPIErrorsWith(detail string) *JSONAPIErrors {
	fe := NewJSONAPIErrors()
	fe.Errors = append(fe.Errors, JSONAPIError{Detail: detail})
	return fe
}
