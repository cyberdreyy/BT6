### Title
Stale confirmations from removed multisig keys allow a request to execute below the effective live-key threshold - ([File: multisig/src/lib.rs])

### Summary
The `MultiSigContract` counts confirmations for a request from a raw `HashSet<PublicKey>` and only checks `confirmations.len() as u32 + 1 >= self.num_confirmations` in `confirm()`. When a key is removed from the account via a `DeleteKey` action, `execute_request` only purges *requests and confirmations for requests whose `signer_pk` (the creator) equals the deleted key* — it never scrubs the deleted key out of the confirmation sets of *other* pending requests that key had already confirmed as a co-signer. Those stale confirmations continue to count toward the threshold, so a request can later execute with fewer genuinely live/authorized keys than `num_confirmations` requires.

### Finding Description
`confirm()` blindly trusts the stored `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` size: [1](#0-0) 

The only place confirmations/requests get cleaned up in response to key removal is inside the `DeleteKey` arm of `execute_request`, and it filters strictly by request *creator* (`signer_pk`), not by *confirmer*: [2](#0-1) 

So if public key `B` is a co-signer (confirmer, not creator) on a still-pending request `R`, and `B`'s key is later removed from the account through a separate, properly-authorized `DeleteKey` request, `R`'s confirmation `HashSet` still contains `B`. `B` is no longer a valid account key, but its historical confirmation is never invalidated. The binding that should hold — "confirmations counted == currently live/authorized keys" — is broken: `confirmations.len()` can include entries for keys that no longer exist on the account. `assert_valid_request()` only checks that the *caller* is `current_account_id == predecessor_account_id` (i.e., that the caller currently holds a valid access key); it never re-validates the *previously stored* confirmers in the set: [3](#0-2) 

This is directly analogous to the `WithdrawTrieVerifier` bug class described in the report: a value (`confirmations.len()`) is treated as proof of a full, current set of legitimate approvals, but the mechanism doesn't verify that every element of that count is still valid at execution time — an intermediate/stale state (`B`'s earlier confirmation) is silently reused to satisfy the threshold check, just as a shortened/stale proof would be reused to satisfy a Merkle root check.

### Impact Explanation
This crosses the "confirmations counted versus live members" boundary explicitly called out as in-scope. A multisig configured for `k`-of-`n` can end up executing a sensitive request (`Transfer`, `AddKey`, `FunctionCall`, `DeployContract`, etc.) with fewer than `k` genuinely live, currently-authorized confirmations, because one or more counted confirmations belong to keys that have since been removed. This is a Critical-class impact per the rules: "a multisig request executed below threshold." Concretely, funds (`MultiSigRequestAction::Transfer`) can be moved, or a new full-access key can be added (`AddKey`) to seize the account, using an authorization count that no longer reflects the actual live signer set.

### Likelihood Explanation
This requires no privileged access beyond being one of the currently valid multisig keyholders (an "unprivileged" party relative to the removed key) — the baseline attacker profile in scope is "malicious normal user abusing valid product/protocol flows." The sequence — create request, get it partially confirmed by a co-signer, have that co-signer's key legitimately removed later (a normal operational event, e.g. rotating a compromised or departing member's key), then confirm again to cross the stale threshold — is a realistic operational sequence rather than a contrived edge case, and does not require breaking cryptography or any owner/foundation privilege beyond the normal multisig flow itself.

### Recommendation
When a key is removed (`DeleteKey`), iterate over all entries in `self.confirmations` (not just requests created by the deleted key) and remove the deleted public key from every confirmation set, or alternatively re-validate at `confirm()`/execution time that every public key recorded in a request's confirmation set is still present among the account's current access keys before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` with keys `A`, `B`, `C`, `D` as full-access keys on the account (any 3 of the 4 required to approve).
2. Key `A` calls `add_request` to create request `R` (e.g. `Transfer { amount }`) — not auto-confirmed.
3. Key `B` calls `confirm(R)` → `confirmations[R] = {B}`.
4. Separately, keys `A`, `C`, `D` execute a fully-confirmed multisig request containing `MultiSigRequestAction::DeleteKey { public_key: B }`, removing `B` from the account. Per `execute_request`'s `DeleteKey` arm, only requests where `signer_pk == B` are purged; `R` (created by `A`, confirmed by `B`) is untouched because its `signer_pk` is `A`, not `B`. `confirmations[R]` still equals `{B}`.
5. Key `C` calls `confirm(R)` → `confirmations.len() (1) + 1 = 2 < 3` → not yet executed, `confirmations[R] = {B, C}`.
6. Key `D` calls `confirm(R)` → `confirmations.len() (2) + 1 = 3 >= 3` → `R` executes.
7. At execution time the truly live, still-valid keys that approved `R` are only `A` (creator, not counted as confirmer here), `C`, and `D` — `B`'s counted confirmation is stale since `B` no longer exists as an account key. The `Transfer` (or `AddKey`/`FunctionCall`) executes having effectively bypassed the intended 3-live-key threshold, since one of the three counted approvals belongs to a removed key. [4](#0-3)

        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
