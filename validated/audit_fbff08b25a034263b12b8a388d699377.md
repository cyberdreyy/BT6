### Title
Stale Confirmations From Removed Multisig Members Allow Requests To Execute Below The Configured Confirmation Threshold - (File: multisig2/src/lib.rs)

### Summary
Both multisig implementations (`multisig/src/lib.rs` and `multisig2/src/lib.rs`) track per-request approvals in a `confirmations` set keyed by signer/member, and compare `confirmations.len()` against `num_confirmations` to decide whether to execute a request. When a signer/member is removed (`DeleteKey` in v1, `DeleteMember` in v2), the code only purges *requests originated by* that signer/member — it never scans and removes that signer's/member's *confirmations left on other pending requests*. A stale confirmation from a now-removed member therefore continues to count toward the quorum, letting a request execute with fewer currently-authorized approvals than `num_confirmations` requires.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

Membership removal is handled by `delete_member`, which only cleans up requests the removed member *originated* (`r.member == member`), and removes the member's own `num_requests_pk` counter and access key — it does **not** walk `self.confirmations` to strip that member's prior confirmations from requests originated by *other* members: [2](#0-1) 

The invariant the contract intends to enforce is:
`confirmations recorded for request R (§len) == number of currently live members who approved R`

After a member is deleted, this equality breaks: a confirmation cast by the now-removed member is still present in `self.confirmations.get(&request_id)` and is counted by `confirm()`, even though that member is no longer part of `self.members` and can no longer authorize anything.

The same bug class exists in the legacy contract `multisig/src/lib.rs`, where `DeleteKey` only removes requests signed (originated) by the deleted key, not confirmations that key placed on other pending requests: [3](#0-2) 

### Impact Explanation
This is a Critical-impact finding per the custody-binding rules: it results in "a multisig request executed below threshold." A `Transfer`, `FunctionCall`, `DeployContract`, or `AddKey`/`AddMember` action can be executed with the number of *genuinely live* approving members strictly less than `num_confirmations`, effectively letting a minority of current members move funds or change contract state that should have required a majority/quorum of live signers.

### Likelihood Explanation
The precondition is a normal, expected operational event: removing a member (e.g., because their key is lost, compromised, or they're offboarded) while a request they had previously confirmed is still pending. Given `REQUEST_COOLDOWN` and the `active_requests_limit` of 12 pending requests per member, it's plausible for a confirmed-but-not-yet-executed request to remain open across a `DeleteMember`/`DeleteKey` action. No attacker privilege beyond being a remaining member (or simply waiting for this ordinary sequence of events to occur) is required to benefit — the last confirming member effectively pushes through a request that should still require one more live approval.

### Recommendation
When removing a member/key (`delete_member` in `multisig2/src/lib.rs`, `DeleteKey` in `multisig/src/lib.rs`), iterate over `self.confirmations` (or maintain a reverse index from member → confirmed request ids) and remove that member's/key's confirmation entry from every pending request, not just requests they originated. Alternatively, validate at `confirm()`-time / execution-time that every public key or account counted in `confirmations` is still a current member of `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
Using `multisig2::MultiSigContract` with members `[A, B, C]` and `num_confirmations = 2`:
1. `A` calls `add_request(R)` where `R` is e.g. `Transfer { amount }` to an attacker-controlled/receiver account (`request_nonce` assigned, `confirmations[R] = {}`).
2. `B` calls `confirm(R)` → `confirmations[R] = {B}` (1 < 2, not yet executed) — see `confirm()` at [4](#0-3) .
3. Members separately approve and execute a `DeleteMember { member: B }` request (a legitimate governance action, e.g. because B's key was compromised) via `delete_member()` — [5](#0-4) . This removes `B` from `self.members` and deletes `B`'s access key, but leaves `confirmations[R] = {B}` untouched because `R.member == A`, not `B`.
4. `C` calls `confirm(R)`. Inside `confirm()`, `confirmations.len() (1, still containing B) + 1 (C) = 2 >= num_confirmations (2)` → `execute_request(R)` runs the `Transfer`.
5. Result: `R` executed with only `A` (originator) and `C` (confirmer) as genuinely live approving members plus one stale confirmation from removed member `B` — i.e., the request executed while only 1 truly live member (`C`) actually confirmed it beyond origination, below the intended 2-of-N live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
