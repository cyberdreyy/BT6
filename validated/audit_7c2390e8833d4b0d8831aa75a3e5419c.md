### Title
Instant-withdraw claims never clear per-epoch receipt accounting, enabling double-claim of default recovery and reserve insolvency - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` zeroes only the aggregate `instantWithdrawsRequests[_user]` and burns the receipt tokens, but it never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]` (the resource "freed" incompletely — the analog of the usbnet error-path leak where allocated buffers are not released). When the same epoch later defaults with `pendingInstantWithdraws != 0`, the stale entries are treated as live claims: the already-paid user is paid a second time from `defaultRecoveryReserve`, and the already-paid amount is also counted as a "prefunded reserve" that does not actually exist, inflating `defaultRecoveryPrice` and leaving the last claimants unable to withdraw.

### Finding Description
In `claimInstantWithdrawRequest` (lines 380-393):

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Only the aggregate is cleared. `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (written at lines 371-372 in `requestInstantWithdraw`) remain.

Compare with `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which does clean up: zeroes the per-epoch entry, decrements the aggregate, decrements `pendingInstantWithdraws`, and decrements `instantWithdrawClaimsByEpoch`. The normal claim path skips this bookkeeping entirely.

Two consequences when a default is finalized in the same epoch while `pendingInstantWithdraws != 0` (i.e. `defaultInstantWithdrawsFinalized = true`, line 696):

1. **Double claim / theft of recovery reserve.** `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (line 844). A user who already claimed their funded instant receipt still has a non-zero per-epoch entry, so `claimInstantWithdrawRequest` → line 382-385 pays them `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` a second time from `defaultRecoveryReserve`. One receipt pays out twice.

2. **Inflated recovery price / insolvency.** `_defaultPrefundedInstantReserve` (lines 716-723) computes `instantBasis - pendingInstant` as "underlyings already held for instant claims." Because the claimed user's basis was never removed from `instantWithdrawClaimsByEpoch`, their already-paid-out amount is counted as held reserve. `finalizeDefaultRecovery` adds this phantom amount to `reserveAmount` (line 686), raising `defaultRecoveryPrice` for every defaulted claimant. The reserve does not contain those tokens, so claims by later users (`_transferDefaultRecovery` at line 915, and normal defaulted-epoch claims) either underflow the reserve or revert on the token transfer — permanently freezing recovery funds owed to other pending receipt holders.

Attack sequence (instant mode, epoch running): user A and B call `requestInstantWithdraw`. The CDO funds only part (e.g. enough for A) via `collectInstantWithdrawFunds`. A claims, receiving underlying at par; A's per-epoch entries stay non-zero. The epoch ends with the borrower defaulting (`stopEpoch` shortfall). `finalizeDefault` runs: `pendingInstantWithdraws = B` (non-zero) so `defaultInstantWithdrawsFinalized = true`; `instantWithdrawClaimsByEpoch = A + B`, so `prefundedReserve = A` — phantom. Recovery price is inflated by `A`, and A can claim `A * recoveryPrice` again from the reserve.

Guards do not stop this: `requestWithdraw`'s stale-epoch checks (lines 263-271) gate only *new* requests, not claims; `_ensureDefaultRecoveryInitialized` explicitly does not clear instant requests (line 926); the reserve guard in `_transferFundedClaim` (line 904) protects the reserve but nothing protects the reserve *from* stale per-epoch accounting.

### Impact Explanation
Direct theft of default recovery funds by the already-paid user (double payout at `defaultRecoveryPrice`), plus permanent freezing: the inflated `defaultRecoveryPrice` promises more than `defaultRecoveryReserve` holds, so the last claimants' `_transferDefaultRecovery` calls revert or underflow `defaultRecoveryReserve -= _amount`, permanently freezing their recovery. Loss scales with the claimed instant amount that precedes the default in the same epoch.

### Likelihood Explanation
Requires instant withdraws enabled and a borrower default in the same epoch where instant funding was partial and at least one funded receipt was already claimed. The attacker is an unprivileged instant-withdraw requester; sequencing depends only on honest manager/borrower epoch calls. Defaults are a designed-for flow (`stopEpochWithDuration`, `finalizeDefault`), not an edge case.

### Recommendation
In `claimInstantWithdrawRequest`, before zeroing the aggregate, clear the per-epoch entries: iterate/zero `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (and any prior epochs with funded receipts) and subtract the claimed amounts from `instantWithdrawClaimsByEpoch[epochNumber]`, mirroring the cleanup in `_clearWithdrawClaimForEpoch`/`_claimDefaultedInstantWithdrawRequest`. Alternatively, track funded-vs-unfunded per-epoch instant basis so `instantWithdrawClaimsByEpoch` only ever reflects unclaimed basis.

### Proof of Concept
Reproducible Foundry fork PoC sketch (following the harness in `test/foundry/IdleCreditVault.t.sol`, e.g. `testFinalizeDefaultHaircutsPendingInstantRedeems`):

1. Enable instant withdraws via `setInstantWithdrawParams`.
2. Users A and B deposit into AA; both call `requestInstantWithdraw` (amounts `A_amt`, `B_amt`) in epoch 0.
3. Borrower/manager funds only `A_amt` through the instant funding path (`getInstantWithdrawFunds` → `collectInstantWithdrawFunds`), so `pendingInstantWithdraws == B_amt`.
4. A calls `claimInstantWithdrawRequest` and receives `A_amt`. Assert `instantWithdrawsRequestsByEpoch[A][0] == A_amt` still (bug).
5. Warp past `epochEndDate`; manager calls `stopEpoch` with a shortfall so `defaulted()` is true; owner calls `finalizeDefault(recovered, manager)` with `recovered < totalBasis`.
6. Assert `defaultInstantWithdrawsFinalized == true` and that `_defaultPrefundedInstantReserve()` included `A_amt` despite A already being paid.
7. A calls `claimInstantWithdrawRequest` again → receives `A_amt * defaultRecoveryPrice / RECOVERY_FULL` a second time (theft).
8. B's subsequent `claimInstantWithdrawRequest`/defaulted claim reverts or underpays because the reserve is drained/overstated (permanent freezing of B's recovery).
