### Title
Unbounded `operator_fee_scalar`/`operator_fee_constant` accepted from L1 `SystemConfig` update logs, allowing the L1 system-config owner to force L2 transactions to pay an unbounded operator fee - (File: `crates/common/genesis/src/updates/operator_fee.rs`)

### Summary
The `OperatorFeeUpdate::try_from` decoder that turns an L1 `SystemConfigUpdate(OperatorFee)` log into the L2 `SystemConfig.operator_fee_scalar` / `operator_fee_constant` fields performs only generic ABI-shape validation and applies no upper-bound / sanity check on the decoded values, mirroring the reported `setFee` pattern where an admin-controlled fee parameter can be pushed to an extreme value with no cap.

### Finding Description
`OperatorFeeUpdate::try_from` decodes the raw `uint32` scalar and `uint64` constant straight from the log payload and returns them unchecked: [1](#0-0) 

This is applied directly to the L2 `SystemConfig` with no clamping: [2](#0-1) 

Contrast this with the sibling `GasLimitUpdate` decoder, which explicitly guards against unreasonable/overflowing values before accepting them: [3](#0-2) 

No equivalent bound exists for the operator fee fields anywhere in the update/validator pipeline: [4](#0-3) 

The unbounded scalar is then used, per-transaction, to compute a fee that is charged upfront against every L2 sender's balance: [5](#0-4) [6](#0-5) 

Because `SystemConfigUpdate(OperatorFee)` logs are derived from L1 receipts written by whoever controls the L1 `SystemConfig` (the same class of privileged, but bound-less, "admin" role as the reported `setFee` caller), a value at or near `u32::MAX` for `operator_fee_scalar` (and/or a large `operator_fee_constant`) can be committed into the derivation pipeline exactly like the audited `setFee(100%)` case: the code trusts the privileged caller completely and enforces no ceiling.

### Impact Explanation
Once such an update is derived, `operator_fee_charge_inner` multiplies every transaction's gas by the oversized scalar (or, post-Jovian, by `scalar * OPERATOR_FEE_JOVIAN_MULTIPLIER` with no decimal division at all), producing a fee that can dwarf the sender's actual gas/value budget. `ensure_can_pay_fees` then requires `gas_limit*max_fee_per_gas + value + l1_fee + operator_fee` to be covered by the sender's balance, so an extreme operator fee causes ordinary senders to be rejected for insufficient funds, or (if funds are available) has the sender's balance drained almost entirely into the operator fee vault, functionally the same outcome as "the user's entire reward/value is taken as the fee" in the original report — except here it manifests as unauthorized, protocol-level over-charging/DoS of L2 transaction execution rather than a single vault claim.

### Likelihood Explanation
Reaching this path only requires an L1 `SystemConfigUpdate(OperatorFee)` log with an extreme scalar/constant to be included in an L1 receipt at the configured `l1_system_config_address`; the derivation pipeline decodes and applies it without any bound check, matching the class of bug in the report (a privileged fee setter lacking a maximum-value guard) that is explicitly in scope as "derivation of attacker-written L1 ... system-config data."

### Recommendation
Add explicit maximum bounds to `OperatorFeeUpdate::try_from` (and/or to `SystemConfig`/derivation application) analogous to the `GasLimitUpdate` overflow guard, e.g. reject `operator_fee_scalar` values above `OPERATOR_FEE_SCALAR_DECIMAL` (or another sane protocol-defined ceiling) and reject unreasonably large `operator_fee_constant` values, returning a dedicated `OperatorFeeUpdateError` variant instead of silently accepting any `u32`/`u64` value.

### Proof of Concept
1. An L1 `SystemConfigUpdate(OperatorFee)` log is emitted (via `enqueue_operator_fee_update` in the test harness, mirroring the real L1 `SystemConfig.setOperatorFeeScalars` call) with `operator_fee_scalar = u32::MAX`. [7](#0-6) 
2. The derivation pipeline decodes this via `OperatorFeeUpdate::try_from` with no bound check and applies it to `SystemConfig.operator_fee_scalar`. [8](#0-7) 
3. Subsequent L2 transactions compute `operator_fee_charge_inner(gas, upgrade)` using this scalar, producing a fee far exceeding the transaction's intended cost. [9](#0-8) 
4. `ensure_can_pay_fees` requires the sender's balance to cover this inflated `operator_fee` in addition to gas and value, causing legitimate transactions to be rejected or the sender's funds to be almost entirely consumed by the fee, with no code-level ceiling ever having stopped it. [10](#0-9)

    /// Validates the common structure of a `SystemConfig` update log data.
    ///
    /// This function performs the following validations:
    /// 1. Checks that the data length is exactly 96 bytes
    /// 2. Decodes and validates the pointer (must be 32)
    /// 3. Decodes and validates the data length field (must be 32)
    ///
    /// # Returns
    ///
    /// Returns a `ValidatedUpdateData` containing the validated fields and original data,
    /// or a `ValidationError` if any validation fails.
    pub fn validate(
        data: &alloy_primitives::Bytes,
    ) -> Result<ValidatedUpdateData<'_>, ValidationError> {
        // Validate total data length
        if data.len() != Self::STANDARD_UPDATE_DATA_LEN {
            return Err(ValidationError::InvalidDataLen(
                Self::STANDARD_UPDATE_DATA_LEN,
                data.len(),
            ));
        }

        // Decode and validate pointer
        let pointer = <sol!(uint64)>::abi_decode_validate(&data[0..32])
            .map_err(|_| ValidationError::PointerDecodingError)?;
        if pointer != Self::EXPECTED_POINTER {
            return Err(ValidationError::InvalidDataPointer(pointer));
        }

        // Decode and validate length
        let length = <sol!(uint64)>::abi_decode_validate(&data[32..64])
            .map_err(|_| ValidationError::LengthDecodingError)?;
        if length != Self::EXPECTED_DATA_LENGTH {
            return Err(ValidationError::InvalidDataLength(length));
        }

        Ok(ValidatedUpdateData { data })
    }

    /// Calculates the operator fee for a given `gas` amount.
    ///
    /// Missing scalars fall back to zero to match the execution path during the
    /// txpool bootstrap window before the first L1 attributes deposit.
    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }

    fn operator_fee(host: &mut Evm<'_, BaseEvmTypes>, envelope: &BaseTxEnvelope, gas: u64) -> U256 {
        let Some(enveloped) = envelope.enveloped() else {
            return U256::ZERO;
        };
        let upgrade = host.config_spec_id().upgrade();
        if (upgrade as u8) < (BaseUpgrade::Isthmus as u8) {
            return U256::ZERO;
        }
        host.block_env().ext.operator_fee_charge(enveloped, U256::from(gas), upgrade)
    }

    /// Rejects the transaction when `caller` cannot cover the full upfront charge — the maximum
    /// gas cost, the transferred value, and the OP-stack L1 data and operator fees.
    ///
    /// The framework's `validate_sender` already rejects a caller that cannot cover the gas cost
    /// and value, but it is unaware of the L1 and operator fees charged here, and
    /// [`charge_upfront`] deducts with wrapping arithmetic. Without this guard an underfunded
    /// caller would silently wrap to a spurious balance instead of the transaction failing; this
    /// mirrors the revm reference, which rejects such a caller with `LackOfFundForMaxFee`.
    ///
    /// A no-op for deposits (funded on L1 and exempt) and when fee charging or balance checks are
    /// disabled (e.g. `eth_call` simulation), matching the conditions under which `validate_sender`
    /// and `charge_upfront` themselves enforce balances.
    fn ensure_can_pay_fees(
        host: &mut Evm<'_, BaseEvmTypes>,
        envelope: &BaseTxEnvelope,
        caller: Address,
        l1_fee: U256,
        operator_fee: U256,
    ) -> HandlerResult<()> {
        let Some(tx) = envelope.as_standard() else {
            return Ok(());
        };
        if !host.feature(EvmFeatures::FEE_CHARGE) || !host.feature(EvmFeatures::BALANCE_CHECK) {
            return Ok(());
        }
        let required = U256::from(tx.gas_limit())
            .saturating_mul(U256::from(tx.max_fee_per_gas()))
            .saturating_add(tx.value())
            .saturating_add(l1_fee)
            .saturating_add(operator_fee);
        let balance =
            host.state_mut().account(&caller, false).map_err(HandlerError::Fatal)?.balance();
        if balance < required {
            return Err(HandlerError::InsufficientFunds);
        }
        Ok(())
    }
