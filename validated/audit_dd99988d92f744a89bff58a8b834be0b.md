### Title
Single external `submit()` failure in the pull-funds path blocks all synchronous withdrawals/redeems for a token - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.redeem()` and `ProvisionerV2.withdraw()` are ordinary-user, permissionless entry points (`anyoneButVault`) that route through `_syncRedeem()`, which calls `_pullFundsIfNeeded()` whenever the vault's idle balance of the requested token is insufficient. `_pullFundsIfNeeded()` invokes `IBaseVault(MULTI_DEPOSITOR_VAULT).submit(data)` with no failure handling — the code comment explicitly states "reverts on failure" — so any revert inside the guardian-configured pull-funds operation (yield source paused, insufficient liquidity, a reverting hook, or the vault itself being paused) bubbles up and reverts the entire user withdrawal/redeem transaction. This mirrors the reported `PrimeStrategy.withdraw()` pattern: a single external dependency failure in the withdrawal-liquidity-sourcing step causes a full DoS on user withdrawals until a privileged party intervenes.

### Finding Description
`_pullFundsIfNeeded()` is called from `_syncRedeem()`: [1](#0-0) 

It reads pull-funds calldata from an SSTORE2 pointer and calls `submit()` unconditionally: [2](#0-1) 

`_syncRedeem()` is reached by the public, permissionless `redeem()` and `withdraw()` functions (gated only by `anyoneButVault`/`solvingNotPaused`, no manager/guardian role required): [3](#0-2) 

`BaseVault.submit()` reverts as soon as any single embedded operation call fails (`Aera__SubmissionFailed`) or if the vault is paused (`whenNotPaused`): [4](#0-3) [5](#0-4) 

Because there is no try/catch (unlike the explicit swallow-failure pattern the team already applies to `postSolveSubmitData` in `solveRequestsVault`, and unlike the documented behavior that `preSolveSubmitData`/pull-funds "reverts on failure"), a single failing pull-funds operation blocks every subsequent `redeem()`/`withdraw()` call for that token, freezing all users' access to funds until an authorized party updates `pullFundsSubmitDataPointer` via `setTokenDetails` or resolves the underlying issue. [6](#0-5) 

### Impact Explanation
This is a temporary freeze of user funds/withdrawal ability for all users of that token in the vault, not caused by any privileged or malicious actor — it is triggered by ordinary use combined with a failure external to the caller's control (paused/illiquid yield strategy, reverting operation hook, or a paused vault). This matches the Medium-severity "temporary freeze of funds" category recognized by Immunefi, analogous to the referenced `PrimeStrategy.withdraw()` finding.

### Likelihood Explanation
Preconditions: (1) `pullFundsSubmitDataPointer` is configured for the token (a normal operational state for any token backed by a yield source), (2) the vault's idle balance of that token is below the requested `tokensOut` (a routine condition after outflows or before rebalancing), and (3) the configured pull-funds operation reverts (e.g., third-party protocol paused, insufficient liquidity in the underlying strategy, an operation/submit hook revert, or the vault being paused). Any ordinary user calling `redeem()`/`withdraw()` under these conditions triggers the DoS with no special privilege needed, making this reasonably likely in production given dependence on external yield protocols.

### Recommendation
Wrap the `submit()` call in `_pullFundsIfNeeded()` in a swallow-failure (low-level call / try-catch) pattern consistent with how `postSolveSubmitData` is already handled in `solveRequestsVault`, and if the pull fails, either revert with a clear, recoverable error that still allows partial fulfillment from idle balance, or fall back to a smaller/partial withdrawal rather than an unconditional revert of the entire user transaction.

### Proof of Concept
1. On a local fork, deploy/configure `ProvisionerV2` with `MULTI_DEPOSITOR_VAULT` and set `tokensDetails[token].pullFundsSubmitDataPointer` to SSTORE2 data encoding a `submit()` operation that calls into a mock/paused external strategy contract that always reverts.
2. Drain the vault's idle balance of `token` below a target `tokensOut` (e.g., via a prior `redeem`/`withdraw` or direct transfer out) so `idleBalance < tokensOut`.
3. As an ordinary EOA (no special role), call `provisioner.redeem(token, unitsIn, minTokensOut, receiver)` or `provisioner.withdraw(token, tokensOut, maxUnitsIn, receiver)`.
4. Assert the transaction reverts with `Aera__SubmissionFailed` bubbled from `BaseVault.submit()`, and that this revert occurs for every subsequent call from any address attempting `redeem()`/`withdraw()` for that token until `setTokenDetails` is called by an authorized party to fix/disable the pointer — demonstrating a full, non-privileged-triggered freeze of user withdrawals.

    /// @notice Pull funds from yield source if vault idle balance is insufficient
    /// @param token The redeem token
    /// @param tokensOut The amount of tokens needed for the redeem
    function _pullFundsIfNeeded(IERC20 token, uint256 tokensOut) internal {
        // Interactions: check vault's idle balance of the redeem token
        uint256 idleBalance = token.balanceOf(MULTI_DEPOSITOR_VAULT);
        if (idleBalance >= tokensOut) return;

        // Requirements: pull-funds submit data must be configured
        address pointer = tokensDetails[token].pullFundsSubmitDataPointer;
        require(pointer != address(0), Aera__PullFundsSubmitDataNotSet());

        // Effects: compute shortfall and store in transient storage
        uint256 shortfall;
        unchecked {
            // Unchecked: idleBalance < tokensOut checked above
            shortfall = tokensOut - idleBalance;
        }
        _storeAmount(shortfall);

        // Interactions: read submit data from SSTORE2 and call vault.submit (reverts on failure)
        bytes memory data = SSTORE2.read(pointer);
        IBaseVault(MULTI_DEPOSITOR_VAULT).submit(data);
    }
