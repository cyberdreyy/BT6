### Title
Stale Confirmations from Deleted Members Allow a Multisig Request to Execute Below the Live-Member Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`multisig2`'s `delete_member` only purges pending requests and confirmations that were **authored by** the member being removed, but it does not scrub confirmations that member previously cast on requests **authored by someone else**. Because `confirm` simply counts the size of the stored `confirmations` set against `num_confirmations` without verifying that every recorded confirmer is still a current member, a request can be executed with fewer live, currently-authorized confirmations than `num_confirmations` requires — a stale confirmation from an already-removed member is silently counted as valid.

### Finding Description
`confirm` decides whether to execute a request purely by comparing the stored confirmation count to the threshold: [1](#0-0) 
It never re-validates that each account/key present in `self.confirmations.get(&request_id)` is still contained in `self.members`.

`delete_member` removes a departing member's own outstanding requests (and their confirmation sets), but the filter is scoped to `r.member == member`, i.e., requests the deleted member *authored*, not requests they merely *confirmed*: [2](#0-1) 

So the invariant the contract is supposed to maintain — "a request executes only once `num_confirmations` **current** members have approved it" — can be expressed as:
```
count({ m ∈ confirmations(R) : m ∈ members }) >= num_confirmations   (intended)
```
but what is actually checked is:
```
len(confirmations(R)) >= num_confirmations   (actual, includes stale entries)
```
These two are not equal once a confirming member is deleted while their confirmation on some other pending request `R` (authored by a different member) is left behind.

### Impact Explanation
This breaks the authorization/threshold binding explicitly listed as Critical impact: "a multisig request executed below threshold." Any privileged action reachable via `MultiSigRequestAction` (funds `Transfer`, `AddKey`/`AddFullAccessKey`, `AddMember`, `DeployContract`, etc.) inherits this weakness — an action can be pushed through with only `num_confirmations - 1` (or fewer) *live* signers, because one of the counted "confirmations" belongs to an account/key that has already been evicted from the multisig and should have zero standing.

### Likelihood Explanation
This does not require any external compromise, oracle, or malicious relayer — it only requires the ordinary sequence of multisig operations already supported by the contract: request creation, partial confirmation, and a later `DeleteMember` request that removes one of the partial confirmers via a governance-approved action. No special privileges beyond normal multisig member status are needed to trigger the latent request left in the state; the remaining members simply need to add one more confirmation to cross the (now falsely reduced) threshold.

### Recommendation
When executing `delete_member`, iterate over **all** outstanding requests (not just ones authored by the deleted member) and drop the deleted member's entry from every confirmation set (removing the request outright if that drop makes it stall below a resolvable state), or alternatively, have `confirm` re-validate `confirmations(R) ∩ members` live before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig initialized with `num_confirmations = 3` and `members = [A, B, C, D]`. [3](#0-2) 
2. Member `A` calls `add_request` creating `R1` (e.g., `Transfer` to an attacker-controlled account). `R1.member == A`.
3. Member `B` calls `confirm(R1)` → confirmations = `{B}` (1/3).
4. Member `C` calls `confirm(R1)` → confirmations = `{B, C}` (2/3, not yet executed). [1](#0-0) 
5. Separately, the multisig (via a normal 3-of-4 confirmed request) removes member `B` using `DeleteMember`. `delete_member` only deletes requests where `r.member == B`; since `R1.member == A`, `R1` and its confirmation set `{B, C}` are left untouched even though `B` is no longer in `self.members`. [2](#0-1) 
6. Members are now `[A, C, D]` (3 live members), yet `num_confirmations` is still `3`.
7. Member `D` calls `confirm(R1)`: `confirmations.len() + 1 == 3 >= num_confirmations (3)` → `R1` executes. [4](#0-3) 
8. `R1` (the `Transfer`) is executed with confirmations counted from `{B, C, D}`, but `B` was no longer a live member at execution time — only 2 of the 3 counted approvers (`C`, `D`) were actually current members, i.e., the request executed below the intended live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
