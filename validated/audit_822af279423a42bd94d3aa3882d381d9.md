### Title
Stale rejection weight is never decremented when a signer flips its vote to Accept, letting a stale/partial blocking minority wedge the miner into globally rejecting an actually-approved block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tracks two independent running totals per block, `total_weight_approved` and `total_weight_rejected`, on the shared `BlockStatus` struct [1](#0-0) . A signer's weight is added to `total_weight_rejected` the first time its slot is inserted into `responded_signers` from a `Rejected` message, and separately added to `total_weight_approved` the first time its slot is inserted into `gathered_signatures` from an `Accepted` message. There is no code path that subtracts a signer's weight from `total_weight_rejected` when that same signer later sends an `Accepted` response for the same block, or vice versa - the two counters are append-only, exactly like Derby's `totalAllocatedTokens` was append-only and never adjusted when `currentAllocations[_protocolNum]` was zeroed on blacklisting.

### Finding Description
In the `Accepted` branch, weight is only added to `total_weight_approved` guarded by `gathered_signatures.contains_key(&slot_id)` [2](#0-1) . In the `Rejected` branch, weight is only added to `total_weight_rejected` guarded by `responded_signers.insert(slot_id)` [3](#0-2) .

Critically, `responded_signers` is shared and updated by *both* branches (`block.responded_signers.insert(slot_id);` also runs in the `Accepted` branch at line 465). This means:
- If a signer rejects first, then later accepts: the `Accepted` branch's guard (`gathered_signatures.contains_key`) is false, so `total_weight_approved` is bumped by that signer's weight — but `total_weight_rejected` is **never reduced**, because there is no code that inspects or clears a prior rejection when an acceptance for the same slot arrives.
- The single-signer, one-slot-per-vote design of the v0 signer explicitly allows a signer to revise an earlier verdict for the same block once "the reason I rejected has since gone away," per the documented re-evaluation logic (`should_reevaluate_reject_reason`, `should_reevaluate_block`) in `stacks-signer/src/v0/signer.rs`, and as summarized in the flow documentation ("repeat my earlier answer (unless the reason I rejected has since gone away)"). This is a normal, single-signer-triggerable event, not requiring a majority or another party's key.

The result: `total_weight_approved + total_weight_rejected` can exceed `total_weight`, and specifically `total_weight_rejected` becomes a stale/inflated value that misrepresents the *current* rejecting weight — breaking the aggregated-weight-vs-verified-accepts (and verified-rejects) equality the miner relies on.

### Impact Explanation
The miner's polling loop in `signer_coordinator.rs` checks the rejection condition before the acceptance condition:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected ...)
} else if block_status.total_weight_approved >= self.weight_threshold {
    ... return Ok(...)
}
``` [4](#0-3) 

Because `total_weight_rejected` can retain weight from signers who have since switched to accept, a blocking-minority condition can be (falsely) satisfied from stale data even while the *live* set of votes has actually reached the 70% approval threshold. Since the rejected-weight check is evaluated first, the miner can permanently treat a validly-approved block as globally rejected (`SignersRejected`), stalling that tenure/block. This is a liveness wedge at the node/coordinator layer driven purely by ordinary vote-revision behavior of the signer set, matching the "aggregated-weight vs verified-accepts" equality break called out as in-scope, and functionally forces re-proposal/timeouts even when consensus was actually reached.

### Likelihood Explanation
This requires only a single signer (one-slot) to reject a proposal and later legitimately flip to accept the same block hash after conditions change — a scenario the signer's own re-evaluation logic is explicitly designed to support (stale reject reasons "going away"). No majority, no other signer's key, and no auth token are needed; it is a normal single-actor sequence of two StackerDB messages for the same `signer_signature_hash`.

### Recommendation
When processing an `Accepted` message, check whether the sending slot previously contributed weight via `responded_signers`/a rejection path, and if so, subtract that signer's weight from `total_weight_rejected` before/while adding it to `total_weight_approved` (and symmetrically for a rejection following a prior acceptance). Concretely, track each slot's last verdict (accept/reject) in a single map keyed by `slot_id` rather than two independently-accumulated append-only totals, and derive `total_weight_approved`/`total_weight_rejected` from that map so a vote change moves weight between the two buckets instead of duplicating it.

### Proof of Concept
1. Reward set with total weight 100, threshold 70 (`weight_threshold = 70`), so blocking minority is 30.
2. Signer A (weight 35) sends `BlockResponse::Rejected` for block `H` — `total_weight_rejected = 35` [3](#0-2) .
3. The condition that caused A's rejection resolves (e.g., a competing tenure died out), and A's local signer logic re-evaluates and now sends `BlockResponse::Accepted` for the *same* `H` [5](#0-4) .
4. `total_weight_approved` becomes 35 (A's weight), but `total_weight_rejected` remains 35 — never decremented — because the `Accepted` branch has no logic to look at or clear prior rejection weight [2](#0-1) .
5. Two more signers, B and C, each with weight 0 net-new rejection contribution needed: only 30 more weight of *genuine* current rejection is needed to trip `total_weight_rejected + 70 > 100`. Because A's stale 35 is still counted, only −5 more (i.e., signers whose actual live rejection weight sums to ≥ −5, trivially any additional rejecting weight, or even none if other signers already rejected before A flipped) is needed to cross the miner's rejection threshold, even though the *live* votes (A now accepting, plus others accepting) may have already reached 70 real approving weight.
6. The miner's `wait_on_signer_updates`-style loop in `signer_coordinator.rs` sees `total_weight_rejected.saturating_add(weight_threshold) > total_weight` first and returns `Err(SignersRejected { .. })`, permanently discarding the tenure-valid block despite genuine live approval having reached threshold [4](#0-3) .
