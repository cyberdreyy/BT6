### Title
View-role users can read ExternalInitiator `AccessKey` and `OutgoingToken` credentials via GET /v2/external_initiators - ([File: core/web/external_initiators_controller.go])

### Summary
The `GET /v2/external_initiators` route is registered with only generic authentication (`paginatedRequest(eia.Index)`, no `auth.RequiresEditRole`/`RequiresAdminRole` wrapper), so any authenticated user with the lowest `view` role can call it. The handler serializes every stored `ExternalInitiator` into `presenters.ExternalInitiatorResource`, which unconditionally includes the plaintext `AccessKey` and `OutgoingToken` fields with no role-based redaction.

### Finding Description
`v2Routes` registers the route as: [1](#0-0) 
unlike sibling mutating routes on the same controller (`Create`, `Destroy`) which are wrapped in `auth.RequiresEditRole`. The `Index` handler pulls all `ExternalInitiator` rows straight from the DB and maps them to the resource, with no filtering by caller role: [2](#0-1) 

The presenter used includes `AccessKey` and `OutgoingToken` as plain, non-redacted JSON fields: [3](#0-2) 

This is confirmed as the accepted, tested behavior of the route: the RBAC route map in the auth test suite explicitly marks `GET /v2/external_initiators` as `viewOnlyAllowed: true`, and the existing controller test asserts the response includes `AccessKey`/`OutgoingToken` values equal to the stored ones with no admin/edit gating: [4](#0-3) [5](#0-4) 

Root cause: the route/handler/presenter combination treats `AccessKey` and `OutgoingToken` as ordinary metadata rather than secret material, and applies no privilege check beyond "any authenticated user."

Note on real exploitability: `AccessKey` alone is not sufficient to authenticate incoming EI-triggered job runs — that requires the `Secret`, which is only ever returned once at creation time via `ExternalInitiatorAuthentication` (`incomingSecret`) and is never persisted/returned in plaintext afterward (only `HashedSecret`+`Salt` are stored and compared via `AuthenticateExternalInitiator`): [6](#0-5) 
However, `OutgoingToken` is genuine outbound credential material — analogous to `BridgeType.OutgoingToken` — used by the node to authenticate itself when it calls out to the external initiator's webhook. Disclosing it to a low-privilege view-only user lets that user impersonate the node's outbound calls to the EI endpoint, and also fully discloses the `AccessKey` identifier used in the EI's own authentication scheme.

### Impact Explanation
This is a credential/secret disclosure to an under-privileged principal (Chainlink bounty class: "credential/key material disclosure to lower-privileged role"). A `view`-role user — the lowest privilege tier that is only supposed to have read-only observability — can obtain the `OutgoingToken` (and `AccessKey`) for every external initiator configured on the node, enabling impersonation of the node's outbound authenticated calls to third-party EI webhook endpoints. It does not on its own allow forging inbound job-triggering requests to the node (since `Secret`/`HashedSecret` are not exposed), which limits the blast radius but does not eliminate the credential-disclosure impact.

### Likelihood Explanation
Trivial and fully repeatable: any operator who provisions a `view`-role user/API token (a common, intentionally low-trust delegation, e.g. for dashboards/monitoring) automatically gets full read access to all EI `AccessKey`/`OutgoingToken` values with a single unauthenticated-role-check GET request. No special conditions, races, or configuration required beyond having at least one `ExternalInitiator` configured and at least one `view` role credential — both are standard, intended states.

### Recommendation
Either (a) restrict `GET /v2/external_initiators` to `auth.RequiresEditRole` or `auth.RequiresAdminRole` (consistent with `Create`/`Destroy` on the same controller), or (b) keep it view-accessible but redact `AccessKey`/`OutgoingToken` from `presenters.ExternalInitiatorResource` (or based on caller role) similarly to how the one-time `ExternalInitiatorAuthentication` response is the only place secrets should ever be surfaced.

### Proof of Concept
Go handler-level integration test (extending `TestExternalInitiatorsController_Index`):
1. Start app, create an `edit`/`admin` user and a `view`-role user (`cltest.User{Role: sessions.UserRoleView}`, per `TestRBAC_Routemap_ViewOnly` pattern).
2. Insert an `ExternalInitiator` via `cltest.MustInsertExternalInitiatorWithOpts` with known `AccessKey`/`OutgoingToken`.
3. As the `view`-role client, call `GET /v2/external_initiators`; assert `http.StatusOK` (not 401/403).
4. Parse the JSON:API body into `[]presenters.ExternalInitiatorResource`.
5. Assert `resource.AccessKey == eiFoo.AccessKey` and `resource.OutgoingToken == eiFoo.OutgoingToken` are non-empty and match stored values — demonstrating the view-role caller received unredacted credential material.
6. (Optional comparison) Repeat with an `admin` client and show identical fields are returned, proving no role-based redaction distinguishes the two.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

// AuthenticateExternalInitiator compares an auth against an initiator and
// returns true if the password hashes match
func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(ea.HashedSecret)) == 1, nil
}
