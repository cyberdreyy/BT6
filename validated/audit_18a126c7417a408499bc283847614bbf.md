### Title
Replay-guard digest poisoning via failed owner-mismatch requests causes DoS against victim's legitimate retry - (`core/capabilities/vault/authorizer.go`)

### Summary
`authorizer.AuthorizeRequest` calls `a.replayGuard.CheckAndRecord(authResult.Digest(), ...)` before calling `validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner())`. If owner validation subsequently fails, the digest has already been permanently recorded in the `RequestReplayGuard`, and there is no rollback/eviction on the owner-validation failure path. Any later request bearing the same digest — including a legitimate, well-formed retry by the actual secret owner — is rejected with `ErrRequestAlreadySeen`.

### Finding Description
In `core/capabilities/vault/authorizer.go`: [1](#0-0) 

The order of operations is:
1. `authorizeRequest` resolves an `AuthResult` (via `allowListBasedAuth` or `jwtBasedAuth`), which independently validates a signature/token and binds a `digest` and an `AuthorizedOwner()` — for the JWT path the digest is `req.Digest()` verified to equal the JWT's `authorization_details.request_digest` claim (see `core/capabilities/vault/jwt_based_auth.go` lines 252-261).
2. `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` is called and, on success, permanently records the digest in `RequestReplayGuard.seen` (`core/capabilities/vault/request_replay_guard.go` lines 35-47) until natural expiry.
3. Only *after* the digest is recorded does `validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner())` check that the secret owner(s) embedded in `req.Params` (e.g. `EncryptedSecret.Id.Owner`) match the JWT/allowlist-authorized owner.
4. If step 3 fails, `AuthorizeRequest` returns the owner error — but the digest recorded in step 2 is never removed.

Because the JWT auth mechanism only requires that the *caller's own* signed JWT commit to a `request_digest` matching `req.Digest()` (i.e., the caller/attacker fully controls the request content whose digest they get their own JWT signed for, including setting `EncryptedSecret.Id.Owner` to an arbitrary victim address), an attacker can:
- Construct a `SecretsCreate`/`SecretsUpdate`/`SecretsDelete` request whose params reference the victim's owner address.
- Obtain (or already possess) their own valid JWT/allowlist authorization binding to that exact request's digest with `workflow_owner` = the attacker's own address.
- Submit it. `authorizeJWTBasedAuth` succeeds (digest matches JWT claim, JWT itself is validly signed for the attacker). `CheckAndRecord` records the digest as seen. `validateSecretOwnersMatchAuthorized` then fails because `authResult.AuthorizedOwner()` (attacker) != the owner embedded in params (victim), and the request is rejected — but too late, the digest is poisoned.
- If the victim later sends the byte-identical request (same digest) as their own well-formed, correctly-owned request, `CheckAndRecord` immediately returns `ErrRequestAlreadySeen`, and the legitimate request is rejected as a replay.

### Impact Explanation
This is a denial-of-service / cross-user isolation violation: an unprivileged attacker who can only submit malformed cross-owner requests can preemptively "consume" a digest that belongs to another subscriber's legitimate operation, blocking that subscriber's secret create/update/delete/list call for as long as the replay guard entry remains valid (based on `authResult.ExpiresAt()`). This maps to a griefing/DoS bounty class against Vault's per-owner isolation guarantees, since it lets one tenant interfere with another tenant's request processing without any privileged access.

### Likelihood Explanation
Feasibility depends on how much of the request the attacker needs to predict/collide to produce the exact same `req.Digest()` as the victim's future request. `req.Digest()` is computed from request `Method`/`Params` (and possibly `ID`) via the `jsonrpc2` package in `chainlink-common`, which is outside this repo and was not directly inspectable here — so whether the digest includes a per-request random/unique field (e.g., a nonce or unpredictable ID) that would make blind pre-poisoning infeasible is **unconfirmed**. If such content is attacker-predictable or reusable (e.g., deterministic params for a known secret ID), the attack is straightforward and repeatable with only the attacker's own valid credentials. This uncertainty should be resolved by inspecting `jsonrpc2.Request.Digest()` in `chainlink-common`.

### Recommendation
Reorder `authorizer.AuthorizeRequest` so `validateSecretOwnersMatchAuthorized` runs **before** `replayGuard.CheckAndRecord`, ensuring the digest is only recorded once the request is fully authorized (owner match included). Alternatively, if `CheckAndRecord` must run first for other reasons, add an explicit rollback (`replayGuard.Release(digest)` or equivalent) on any subsequent authorization failure so a rejected request cannot poison the replay guard for a legitimately-owned digest.

### Proof of Concept
Go unit test plan (in `core/capabilities/vault/authorizer_test.go`):
1. Construct a fake `jwtBasedAuth`/mock `Authorizer` returning `AuthResult{workflowOwner: "attacker", digest: "D", expiresAt: futureUnix}` for a `SecretsCreate` request whose `EncryptedSecrets[0].Id.Owner == "victim"`.
2. Call `authorizer.AuthorizeRequest(ctx, req)`; assert it returns an owner-mismatch error (via `validateSecretOwnersMatchAuthorized`).
3. Construct a second, well-formed request/mock `Authorizer` returning `AuthResult{workflowOwner: "victim", digest: "D", expiresAt: futureUnix}` with `EncryptedSecrets[0].Id.Owner == "victim"` (matching, legitimate).
4. Call `authorizer.AuthorizeRequest(ctx, req2)`; assert whether it fails with `ErrRequestAlreadySeen` even though the owner matches and this is the legitimate owner's first well-formed attempt — confirming the poisoning.
5. Add a regression assertion that after fixing the ordering, step 4 succeeds (returns a valid `AuthResult`) since the earlier malicious request never should have consumed the digest.

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}
