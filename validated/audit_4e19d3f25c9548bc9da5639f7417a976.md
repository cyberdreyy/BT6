### Title
Peer signatures replayed via `process_pending_responses_for_block` can push a block to `LocallyAccepted`/broadcast before this signer's own node has validated it - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`store_and_process_block_signature`, the function that tallies peer `BlockAccepted` signatures toward the 70% signing threshold, never checks `block_info.valid` before counting a signature and, once the threshold is reached, calling `mark_locally_accepted` and `broadcast_signed_block`. This function is reachable for a brand-new, not-yet-validated proposal through `process_pending_responses_for_block`, which is invoked immediately after `insert_block` in `handle_block_proposal`, before this signer's own node has ever validated the specific block content [1](#0-0) .

### Finding Description
The intended invariant (documented and enforced elsewhere) is: a signer never signs, and never treats a block as locally accepted, until its own node has validated that exact block. This is explicit in `handle_block_pre_commit`, which bails out with "we have not determined to be valid" if `block_info.valid` is not `Some(true)`, before it will count pre-commit weight toward a signature [2](#0-1) . The same gate exists in `handle_block_validate_ok`, which only proceeds to `mark_pre_committed`/signing paths after the node's own validation response and a fresh `check_block_against_signer_db_state` recheck [3](#0-2) .

`store_and_process_block_signature`, however, has no such guard:
```
fn store_and_process_block_signature(...) {
    ...
    if !self.signer_db.add_block_signature(block_hash, signer_address, signature)... { return; }
    if signer_address != &self.stacks_address && !self.signer_db.has_committed(...) {
        self.handle_block_pre_commit(...);   // only gated path
        return;
    }
    if block_info.signed_group.is_some() { return; }
    // tally ALL stored signatures, compare to threshold
    ...
    if let Err(e) = block_info.mark_locally_accepted(true) { ... }
    self.signer_db.insert_block(block_info)...;
    self.broadcast_signed_block(stacks_client, block_info.block.clone(), &addrs_to_sigs);
}
``` [4](#0-3) 

Note that once `has_committed` is true for a signer address (i.e. that signer already appears in `block_pre_commits`), the function skips straight to tallying signatures and, if the aggregated weight of *stored signatures* meets the 70% threshold, marks the block `LocallyAccepted` and broadcasts it to this signer's own node - all without ever consulting `block_info.valid`.

This function is reachable for a block this signer's own node has not yet validated: `handle_block_proposal` builds a fresh `BlockInfo` from the incoming proposal (`valid` unset), does only the cheap `check_block_against_state` "not provably invalid" check, inserts the record, and then immediately calls `process_pending_responses_for_block`, which replays any *pending* signatures that arrived from peers before this proposal did [1](#0-0) [5](#0-4) . Those pending signatures are dispatched straight into `store_and_process_block_signature` [6](#0-5) , which - as shown above - can conclude "signed_group reached" and broadcast the block, all before `submit_block_for_validation`'s result for *this* block has ever come back.

This mirrors the reported bug class: two related state transitions (here, "validated locally" vs "peer signature tally / broadcast decision") are updated out of order, and a message that arrives out-of-order (a pre-commit/signature that raced ahead of the proposal) is replayed into a path that skips the guard the "normal" path enforces. In the C4 report, transferring token B before token A's balance settled let a reentrant call see stale/partial state; here, replaying a *pending* signature into `store_and_process_block_signature` lets the signer conclude group-signed status for a block whose `valid` flag was never checked in that code path.

### Impact Explanation
If exploitable, this breaks the "signed vs validated" equality that Critical-severity findings target: a signer would mark a block `LocallyAccepted` (the state from which `broadcast_signed_block`/`handle_post_block` push the block to the node) purely from a set of pre-existing peer signatures, without this signer's own validation of that block's content ever having completed for the code path in question. Because `broadcast_signed_block` assembles a real quorum signature set and pushes the block toward the node, this could contribute to an invalid or non-canonical block reaching a state where it's propagated as accepted by this signer, at least locally, prior to (or independent of) an actual validation verdict for it.

### Likelihood Explanation
The precondition (having already-`has_committed` peer signers for a fresh, not-yet-validated block, with signatures parked as "pending" and replayed on proposal arrival) is a normal, one-slot-miner/gossip-triggerable scenario documented and exercised elsewhere in the codebase (`process_pending_responses_for_block`, "early votes" parked before the proposal). No majority-signer collusion is required beyond signatures that are already valid, correctly-attributed messages from real signers arriving in a different order than the proposal — an ordering a miner or relay can influence by delaying proposal delivery relative to StackerDB message delivery.

### Recommendation
Add the same `block_info.valid.unwrap_or(false)` guard used in `handle_block_pre_commit` to `store_and_process_block_signature` before it tallies stored signatures toward the 70% threshold or calls `mark_locally_accepted`/`broadcast_signed_block`. If `valid` is not yet `Some(true)`, the signature should be recorded (as it already is) but the threshold/promotion logic should be deferred until validation completes, consistent with the invariant enforced in the pre-commit and validate-response paths.

### Proof of Concept
1. A miner proposes block `X` at height `h`.
2. Before the proposal reaches signer `S`, `S` receives (via StackerDB gossip) `BlockAccepted` messages for `X` from enough peer signers to meet the 70% weight threshold; because `S` has already recorded pre-commits from those same signers for `X` (`has_committed` true), these signatures are parked as pending signature responses (`add_pending_block_signature_response`) rather than being redirected through `handle_block_pre_commit`.
3. The proposal for `X` finally reaches `S`. `handle_block_proposal` builds a fresh `BlockInfo` (valid unset), inserts it, and calls `process_pending_responses_for_block`.
4. `process_pending_responses_for_block` replays the pending signatures into `store_and_process_block_signature`, which (per its code, lines 2442-2538) never checks `block_info.valid`, finds the aggregated signature weight already at/above threshold, calls `mark_locally_accepted(true)`, and calls `broadcast_signed_block` — all before `S`'s own node has returned any validation verdict for `X`.

    /// Store the block acceptance signature and check if we have reached a consensus decision on the block because of it. If we have, update the block state accordingly and broadcast the block if accepted.
    fn store_and_process_block_signature(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &mut BlockInfo,
        signer_address: &StacksAddress,
        signature: &MessageSignature,
    ) {
        let block_hash = &block_info.signer_signature_hash();
        // signature is valid! store it.
        // if this returns false, it means the signature already exists in the DB, so just return.
        if !self
            .signer_db
            .add_block_signature(block_hash, signer_address, signature)
            .unwrap_or_else(|_| panic!("{self}: Failed to save block signature"))
        {
            return;
        }

        // If this isn't our own signature and we haven't seen a pre-commit from this signer yet, try treating it as a pre-commit in case the caller is running an outdated version
        if signer_address != &self.stacks_address && !self.signer_db.has_committed(block_hash, signer_address).inspect_err(|e| warn!("Failed to check if pre-commit message already considered for {signer_address:?} for {block_hash}: {e}")).unwrap_or(false) {
            self.handle_block_pre_commit(stacks_client, sortition_state, signer_address, block_hash);
            return;
        }

        if block_info.signed_group.is_some() {
            // We have already processed this block to the accepted state. Adding more signatures will not change anything so nothing to check.
            return;
        }
        // do we have enough signatures to broadcast?
        // i.e. is the threshold reached?
        let signatures = self
            .signer_db
            .get_block_signatures(block_hash)
            .unwrap_or_else(|_| panic!("{self}: Failed to load block signatures"));

        // put signatures in order by signer address (i.e. reward cycle order)
        let addrs_to_sigs: HashMap<_, _> = signatures
            .into_iter()
            .filter_map(|sig| {
                let Ok(public_key) = Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s(
                    block_hash.bits(),
                    &sig,
                ) else {
                    return None;
                };
                let addr = StacksAddress::p2pkh(self.mainnet, &public_key);
                Some((addr, sig))
            })
            .collect();

        let signature_weight = self.signer_weights.get(signer_address).unwrap_or(&0);
        let total_signature_weight = self.compute_signature_signing_weight(addrs_to_sigs.keys());
        let total_weight = self.compute_signature_total_weight();

        let min_weight = NakamotoBlockHeader::compute_voting_weight_threshold(total_weight)
            .unwrap_or_else(|_| {
                panic!("{self}: Failed to compute threshold weight for {total_weight}")
            });

        if min_weight > total_signature_weight {
            info!("{self}: Received block acceptance, but have not yet reached the acceptance threshold.";
                "signer_signature_hash" => %block_hash,
                "signature_weight" => signature_weight,
                "consensus_hash" => %block_info.block.header.consensus_hash,
                "block_height" => block_info.block.header.chain_length,
                "total_weight_approved" => total_signature_weight,
                "total_weight" => total_weight,
                "percent_approved" => (total_signature_weight as f64 / total_weight as f64 * 100.0),
            );
            return;
        }
        info!("{self}: have reached the block acceptance threshold";
            "signer_signature_hash" => %block_hash,
            "signature_weight" => signature_weight,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "total_weight_approved" => total_signature_weight,
            "total_weight" => total_weight,
            "percent_approved" => (total_signature_weight as f64 / total_weight as f64 * 100.0),
        );

        // have enough signatures to broadcast!
        // move block to LOCALLY accepted state.
        // It is only considered globally accepted IFF we receive a new block event confirming it OR see the chain tip of the node advance to it.
        if let Err(e) = block_info.mark_locally_accepted(true) {
            if !block_info.has_reached_consensus() {
                warn!("{self}: Failed to mark block as locally accepted: {e:?}");
            }
        }
        let _ = self.signer_db.insert_block(block_info).map_err(|e| {
            warn!("Failed to set group threshold signature timestamp for {block_hash}: {e:?}");
            panic!("{self} Failed to write block to signerdb: {e}");
        });
        self.broadcast_signed_block(stacks_client, block_info.block.clone(), &addrs_to_sigs);
    }
