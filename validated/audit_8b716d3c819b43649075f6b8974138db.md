### Title
Unbounded zstd compression of account data allows single-call CPU exhaustion in `encode_ui_account` - (File: `account-decoder/src/lib.rs`)

### Summary
### Finding Description
The external report's bug class is: an unprivileged, attacker-influenced input causes a validator/contract-adjacent process to perform unbounded, expensive work in response to a single call, because the code path assumes cheap/bounded processing of externally supplied data. In agave, the analogous unbounded-cost path is `encode_ui_account` in `account-decoder/src/lib.rs`, which handles the `Base64Zstd` account encoding option used by JSON-RPC handlers such as `getAccountInfo`/`getProgramAccounts` in `rpc/src/rpc.rs`: [1](#0-0) 

When a client requests `encoding: "base64+zstd"`, the handler synchronously runs a zstd `Encoder` over the *entire* account data (`slice_data(account.data(), data_slice_config)`), with no data-size gate or CPU/time budget, before returning the response: [2](#0-1) 

Any account owned by any program can be grown up to the maximum permitted account size (accounts can be resized up to the network's max account data length via `system_processor`/`bpf_loader` realloc paths, referenced across `programs/bpf_loader/src/lib.rs`, `programs/system/src/system_processor.rs`, and `transaction-context/src/lib.rs`), so a single unprivileged, unauthenticated `getAccountInfo` request against such an account with `Base64Zstd` encoding forces the RPC node to compress the full account buffer inline in the RPC-handling code path: [3](#0-2) [4](#0-3) 

This mirrors the Notional `_isWrappedFCash` gas-bomb pattern in spirit: a decode/encode routine that is assumed cheap is instead driven by attacker-controlled input size/content into performing disproportionately expensive work triggered by one request, with no bound analogous to a gas limit.

### Impact Explanation
A single low-rate, unprivileged JSON-RPC call (`getAccountInfo`, `getMultipleAccounts`, or `getProgramAccounts` with `encoding=base64+zstd`) targeting a large account can force the validator's RPC-serving thread to spend significant CPU compressing megabytes of data per request, with no size ceiling or timeout in `encode_ui_account`. Because there is no cap distinguishing this from a normal request, an attacker can repeatedly target large, pre-existing accounts (e.g., large program/data accounts) to degrade RPC responsiveness with minimal request volume. This falls into the "unbounded cost for a single low-rate call" impact category.

### Likelihood Explanation
Likelihood is moderate: it requires (1) an existing (or attacker-created, since account growth up to max size is a normal operation available to any user paying rent) large account, and (2) a single RPC call specifying `Base64Zstd` encoding — no special privileges or multiple round trips needed. The `eth_estimateGas`-style pre-filtering that reduced the original Notional bug's severity does not have a direct analog here, since RPC encoding choice isn't gas-metered.

### Recommendation
Bound the cost of `Base64Zstd` (and, more generally, any encoding) in `encode_ui_account` by:
- Enforcing a maximum data length (or a maximum estimated compression cost) before invoking `zstd::stream::write::Encoder`, falling back to `Base64` (as already done on compressor error) when the slice exceeds a safe threshold.
- Considering a per-request/global CPU or wall-clock budget for RPC-side encoding work, and/or moving expensive encoding off the hot request path.

### Proof of Concept
1. Identify or create an account (any owner) whose data has been grown, via normal system/program operations, to a large size (up to the network's maximum permitted account data length).
2. Issue a single `getAccountInfo` (or `getMultipleAccounts`) JSON-RPC request against that pubkey with `{"encoding": "base64+zstd"}`.
3. Observe that `encode_ui_account`'s `UiAccountEncoding::Base64Zstd` branch synchronously zstd-compresses the full account buffer inline in the RPC request path (`account-decoder/src/lib.rs:67-79`, reached via `rpc/src/rpc.rs` `get_encoded_account`/`encode_account`), consuming CPU proportional to account size with no upper bound, for the cost of one request.

Note: I was unable to fully verify the exact current value of the maximum permitted account data length constant in this indexed snapshot (search for `MAX_PERMITTED_DATA_LENGTH` returned matches in several files, e.g. `programs/bpf_loader/src/lib.rs`, `programs/system/src/system_processor.rs`, `transaction-context/src/lib.rs`, but the constant definition itself was not retrievable in the available index) — a Devin session with full repository access would be needed to confirm the exact ceiling and any existing size-based gating (if present) in `encode_ui_account`'s call sites.

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
