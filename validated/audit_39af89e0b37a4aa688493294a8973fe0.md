### Title
JWT replay check-then-act race allows double-triggering a workflow with a single signed token - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks replay status via `h.jwtCache.isReplay(claims.ID)` and later marks the JWT as used via `h.jwtCache.recordUsage(claims.ID)`, but these are two separate, independently-locked operations rather than one atomic check-and-set. Two concurrent `Authorize` calls carrying the same JWT can both pass the `isReplay` check before either calls `recordUsage`, allowing the same JWT to authorize two workflow trigger executions.

### Finding Description
`Authorize` at [1](#0-0)  calls `h.jwtCache.isReplay(claims.ID)`, which only takes an `RLock`, reads the map, and returns whether the entry exists [2](#0-1) . The write that marks the jti as used, `recordUsage`, happens only after signer/authorization checks succeed, at the very end of the function [3](#0-2) , and is a separate lock acquisition in `recordUsage` [4](#0-3) .

Because `isReplay` and `recordUsage` are not combined into a single atomic "check-and-insert" operation under one lock, two goroutines calling `Authorize(workflowID, token, req)` concurrently with the identical signed JWT can interleave as follows:
1. Goroutine A calls `isReplay(jti)` → false (not yet in cache).
2. Goroutine B calls `isReplay(jti)` → false (A hasn't recorded yet).
3. Both A and B proceed through the authorized-key lookup (which succeeds for both, since it's read-only and keyed by workflowID, not jti).
4. Both A and B call `recordUsage(jti)`, which is idempotent (just overwrites the map entry) — both calls return `nil` error and a valid `*gateway.AuthorizedKey`.

Both callers therefore receive a successful `Authorize` result with the same token, and (per the file being the sole guard for JWT single-use in this code path) both requests proceed to trigger the workflow, defeating REQUEST_BINDING/replay-prevention for the HTTP trigger authorization path.

### Impact Explanation
This allows an attacker who possesses one valid, signed JWT for a workflow trigger to cause the workflow to execute more than once by sending two (or more) concurrent HTTP trigger requests with the same token. This corresponds to Chainlink's "unauthorized job run" / replay-protection bypass impact class — a single authorized signature can be leveraged to double-trigger execution, which may cause duplicate on-chain actions, duplicate fund movement, or resource exhaustion depending on the workflow's semantics.

### Likelihood Explanation
The precondition is only possession of one valid signed JWT (the exact credential the caller already needs to trigger the workflow once) and the ability to send two requests concurrently — no additional privilege beyond what's needed for a single legitimate trigger. This is trivially reproducible by any client capable of firing parallel HTTP requests, and the race window, while narrow, is real because `isReplay` and `recordUsage` are non-atomic operations separated by network-latency-scale work in between (authorized key lookup), making a race win each request cycle. Likelihood is a function of timing, but given typical server concurrency, it's a repeatable race in a fuzz/stress-test scenario, and can be reliably won by synchronizing two goroutines to call `Authorize` at the same time (e.g., via a start barrier), as would be typical in a proof-of-concept test.

### Recommendation
Make the check-and-record operation atomic: acquire the cache's write lock once, check for existing jti and insert to reserve it as a single critical section (e.g., a `checkAndRecord(jti) bool` method that returns false if it was already present, done entirely under the `mu.Lock()`), and return early if replay is detected without waiting until after the signer/authorized-key checks. This closes the TOCTOU window and ensures at most one concurrent `Authorize` call for a given jti can succeed.

### Proof of Concept
Go concurrency test in `workflow_metadata_handler_test.go`:
1. Construct a `WorkflowMetadataHandler` with a registered `workflowID` and one authorized key, matching the signer of a single generated JWT (using the same helper used elsewhere in `workflow_metadata_handler_test.go` for signing tokens with `claims.ID` set).
2. Use a `sync.WaitGroup` and a start-barrier channel to have N (e.g., 20) goroutines call `h.Authorize(workflowID, token, req)` simultaneously with the identical token.
3. Collect results (error/nil) from each call into a shared slice/counter with a mutex or channel.
4. Assert: exactly one goroutine returns `(*gateway.AuthorizedKey, nil)` and all others return the "JWT token has already been used" error — i.e., `successCount == 1`.
5. Run with `go test -race -run TestAuthorize_ConcurrentReplay` repeated multiple times (or with `-count=100`) to demonstrate the race consistently allows `successCount > 1` before the fix, and exactly `1` after applying the atomic check-and-record fix.

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
