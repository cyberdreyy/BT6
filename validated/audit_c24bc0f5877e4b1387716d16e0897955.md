### Title
Unauthenticated `/health` and `/readyz?full` endpoints leak internal dependency status/error details, unlike the intentionally minimal `/public-readyz` - ([File: core/web/health_controller.go])

### Summary
`HealthController.Health` and `HealthController.Readyz` (mounted without `auth.Authenticate` per `healthRoutes` in `core/web/router.go`) return per-check names and raw error output from the internal `HealthChecker`, while `PublicReadyz` was explicitly written to "never return per-check details ... to avoid leaking internal service state on publicly reachable endpoints." An unauthenticated caller can hit `/health` or `/readyz?full=1` and receive the same class of internal diagnostic detail that `PublicReadyz` deliberately withholds.

### Finding Description
`PublicReadyz` in `core/web/health_controller.go` (lines 27-37) is documented as the safe, public-facing readiness probe and intentionally returns only an HTTP status code, no body. In contrast, `Readyz` (lines 43-81) returns a JSON list of `presenters.Check{Name, Status, Output}` for every failing/erroring dependency check when the `full` query parameter is present, and `Health` (lines 83-139) unconditionally returns per-check `Name`/`Status`/`Output` for every registered health check (DB, chains, RPCs, services, etc.), including raw `err.Error()` text (`output = err.Error()`), rendered as JSON, HTML, or plaintext depending on `Accept` header/`NegotiateFormat`. These `Output` fields come directly from internal service error messages (e.g., could include connection strings, chain RPC URLs, internal service names, or stack-trace-like text depending on what individual health checks report), which is exactly the class of information `PublicReadyz`'s comment says must not be exposed publicly. Both `/health` and `/readyz` are unauthenticated (no `auth.Authenticate` wrapper), so any unauthenticated network client can enumerate the node's internal component names and error state, learning internal service topology (list of running chains/relayers/services and which are failing and why) without any credential.

### Impact Explanation
This is an information-disclosure issue (Chainlink bounty class: information disclosure / internal state leak), not remote code execution or fund loss. It allows unauthenticated reconnaissance of a node's internal topology and failure state (which chains/relayers/DB components exist and their error text), which can help an attacker time other attacks (e.g., targeting a known-failing dependency) or infer deployment details. It does not by itself grant privilege escalation, key disclosure, or fund movement.

### Likelihood Explanation
Trivial and fully unauthenticated: any client with network access to the node's API port can `curl /health` or `curl '/readyz?full=1'` with no credentials, and repeat indefinitely. The only "precondition" is network reachability of the endpoint, which is the default posture for these routes (they exist specifically to be reachable by k8s/load balancers, but are not access-restricted to internal-only networks by the code).

### Recommendation
Either (a) restrict `/health` and `/readyz?full=…` to require authentication (or an internal-network-only listener) so detailed check output isn't reachable by arbitrary external clients, or (b) make `/health` and `/readyz` behave like `PublicReadyz` by default — return only aggregate status codes to unauthenticated/public callers — and gate the detailed per-check JSON/HTML/plaintext output (including `Output`/error text) behind authentication or a separate operator-only route, consistent with the stated intent of `PublicReadyz`.

### Proof of Concept
Go handler-level test plan (using `httptest` + `gin`):
1. Construct a `chainlink.Application` mock (or reuse fixtures from `core/web/health_controller_test.go`) with `GetHealthChecker()` returning a checker with at least one failing check whose error contains a distinguishing marker string, e.g. `"internal-rpc-endpoint-xyz failed"`.
2. Register routes as done in `core/web/router.go` (`/health`, `/readyz`, `/public-readyz`) without any auth middleware, matching the actual router wiring.
3. Send `GET /public-readyz` (no headers) → assert response body is empty and only status code (200/503) is set — no leaked strings.
4. Send `GET /readyz?full=1` (no auth headers) → assert HTTP 200/401 is NOT required, and assert response body contains the check `Name` and `Output` text (e.g., contains `"internal-rpc-endpoint-xyz failed"`).
5. Send `GET /health` (no auth headers, `Accept: application/json`) → assert response body contains the same check name/output details.
6. Assert differential: `/public-readyz` body == empty while `/health`/`/readyz?full=1` bodies contain the sensitive marker string, proving `/health` and `/readyz` leak detail that `/public-readyz` explicitly withholds to unauthenticated callers.
