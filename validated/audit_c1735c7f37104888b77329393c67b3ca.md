### Title
Claimed instant-withdraw receipts are never removed from per-epoch ledgers, so default finalization counts already-paid funds as prefunded reserve and mints unbacked recovery value - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out and zeroes only the aggregate `instantWithdrawsRequests[_user]`, but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` intact. If that same epoch later defaults with any other instant receipt still unfunded, `finalizeDefaultRecovery` dereferences this stale basis twice — once as claim basis in `defaultPendingClaimBasis` and again as "already-held prefunded reserve" in `_defaultPrefundedInstantReserve` — crediting the recovery pool with tokens that were already transferred out. The result is an inflated `defaultRecoveryPrice`/`defaultRecoveryReserve` and unbacked strategy tokens minted to the CDO: a solvency break and permanent freezing of honest claimants' recovery.

### Finding Description
The kernel bug class is "a synchronous path treats an in-flight consumer as finished and frees state the async worker still references." Here, `claimInstantWithdrawRequest` (the "free") releases the funds while a deferred consumer — epoch-end default finalization — still reads the stale per-epoch ledgers:

- `claimInstantWithdrawRequest` (lines 380-393) burns the receipt, sets `instantWithdrawsRequests[_user] = 0` and transfers underlying. It never touches `instantWithdrawsRequestsByEpoch` (written at line 371) or `instantWithdrawClaimsByEpoch` (written at line 372). Compare with `_claimDefaultedInstantWithdrawRequest` (lines 847-853), which correctly decrements both.
- `defaultPendingClaimBasis` (lines 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` — including amounts already claimed and paid.
- `_defaultPrefundedInstantReserve` (lines 716-723) returns `instantBasis - pendingInstant`, i.e. it treats the already-claimed portion as underlying still held by the strategy. Those tokens are gone.
- `finalizeDefaultRecovery` (lines 685-704) folds the phantom amount into `reserveAmount` → inflated `recoveryPrice`, inflated `defaultRecoveryReserve`, and `activeFinalNAV = activeBasis * recoveryPrice` mints unbacked strategy tokens to `idleCDO` (line 704).

### Impact Explanation
The phantom reserve `X` (the already-claimed instant amount) is booked into `defaultRecoveryReserve` but does not exist in the contract's balance. Two concrete losses:

1. Insolvency / theft: `recoveryPrice` is inflated (adding `X` to numerator while the basis also grows), so `_mint(idleCDO, activeFinalNAV - activeBalance)` credits the CDO — and every claimant using `_transferDefaultRecovery` — value above real backing. Early claimants (attacker-controlled, e.g. via a defaulted normal withdraw receipt or post-default request) drain the real tokens; the shortfall equals roughly `X × (1 − truePrice)`.
2. Permanent freezing: once the real balance is exhausted, `_transferDefaultRecovery` underflows/reverts (line 915 `defaultRecoveryReserve -= _amount` and the `safeTransfer`), so remaining honest claimants can never claim their recovery.

### Likelihood Explanation
Requires: instant withdrawals enabled, a claimed funded instant receipt and at least one unfunded instant receipt in the epoch that defaults (so `pendingInstantWithdraws != 0` and `defaultInstantWithdrawsFinalized` is true at line 696). Instant-withdraw funding depends on borrower liquidity, and borrower default is an in-scope protocol event, not attacker-controlled timing beyond choosing to hold receipts — a KYC-passing lender/unprivileged user triggers the claim; the inflation then harms all recovery claimants regardless of who exploits it.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers exactly like `_claimDefaultedInstantWithdrawRequest` does:

```solidity
uint256 currentEpoch = epochNumber;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] = 0; // or track claimed portion
instantWithdrawClaimsByEpoch[currentEpoch] -= amount;
```

Because multiple requests accumulate into one epoch entry, store the claimed amount per epoch (e.g. a parallel `instantWithdrawsClaimedByEpoch` map) so that `_claimDefaultedInstantWithdrawRequest` pays only the still-unclaimed remainder.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` / `IdleCDOEpochQueue.t.sol` patterns):

```solidity
// setup: deposit AA/BB, startEpoch, enable instant withdraws (setInstantWithdrawParams)
// epoch E:
uint256 r1 = 100e6;
cdoEpoch.requestInstantWithdraw(r1, userA);          // via CDO requestWithdraw in instant mode
// borrower funds r1 only
getInstantWithdrawFunds(r1);                          // collectInstantWithdrawFunds: pendingInstantWithdraws = 0
cdoEpoch.claimInstantWithdrawRequest();               // userA paid; per-epoch ledgers still hold r1
cdoEpoch.requestInstantWithdraw(r2, userB);           // unfunded -> pendingInstantWithdraws = r2
// borrower defaults on epoch E (stopEpoch with no repayment)
cdoEpoch.finalizeDefault(recovered, manager);
// inside finalizeDefaultRecovery:
//   instantBasis = r1 + r2, pendingInstant = r2  ->  prefundedReserve = r1 (phantom)
//   reserveAmount and recoveryPrice inflated by r1; CDO minted r1-scaled unbacked tokens
assertGt(strategy.defaultRecoveryReserve(), underlying.balanceOf(address(strategy)) - otherObligations);
// honest claimants' _transferDefaultRecovery reverts once real balance is drained:
vm.expectRevert();
cdoEpoch.claimInstantWithdrawRequest();               // userB (or defaulted normal claimant)
```
