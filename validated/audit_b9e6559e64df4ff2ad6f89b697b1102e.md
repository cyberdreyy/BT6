## Analysis: Shared `SortitionsView` state bleeding across reward-cycle contexts

### Title
Next-reward-cycle signer instance can corrupt the current-cycle signer's `SortitionsView.miner_status`, wedging valid block signing - (File: `stacks-signer/src/runloop.rs`)

### Summary
`RunLoop` maintains a single, un-scoped `sortition_state: Option<SortitionsView>` field that is passed by mutable reference into `process_event` for *every* `ConfiguredSigner` instance it holds — including both the current-reward-cycle signer and the "next" reward-cycle signer that runs concurrently during the prepare-phase overlap window. `capitulate_viewpoint`, which is invoked unconditionally on every pass for every signer instance (before any reward-cycle/parity gating), can mutate this shared object's `cur_sortition.miner_status` based on that instance's *own* (different-reward-cycle) `GlobalStateEvaluator`/weight table. Because the object is shared, the next-cycle signer's miner-view judgment silently overwrites the field that the current-cycle signer later reads to decide whether to accept or reject a block proposal.

### Finding Description
`RunLoop` declares one shared field: [1](#0-0) 

In `run_one_pass`, this same field is handed out by mutable reference to *each* configured signer in the loop, regardless of which reward cycle that signer represents: [2](#0-1) 

Two `ConfiguredSigner` instances (current cycle and next cycle) can coexist, since `initialize_runloop`/`refresh_signer_config` registers the next cycle's signer once its prepare phase begins: [3](#0-2) 

Each `Signer::process_event` calls `capitulate_viewpoint` unconditionally, *before* the parity gate and before the "has our reward cycle started" gate — so even the dormant next-cycle instance runs it on every pass, using its own `self.global_state_evaluator` (built from its own, different, reward-cycle's `signer_weights`): [4](#0-3) 

Inside `capitulate_viewpoint`/`capitulate_miner_view`, if that signer's own state-machine consensus disagrees with `sortition_state.cur_sortition.data.miner_pkh`, it mutates the *shared* object's miner status: [5](#0-4) 

The current-cycle signer subsequently reads that same shared field when validating a real block proposal via `check_block_against_local_state` → `SortitionsView::check_proposal`: [6](#0-5) 

And the proposal check enforces the miner status unconditionally: [7](#0-6) 

Since `miner_status` is a per-signer-set consensus judgment (dependent on that instance's own weight table/`GlobalStateEvaluator`), but is stored on a single object shared across two different signer-set contexts (current vs. next reward cycle), the next cycle's — possibly premature or differently-weighted — verdict can silently overwrite the current cycle's live view. This is directly analogous to the reported bug class: state scoped to one context ("channel"/reward-cycle) inherited into another context, breaking the equality between "what this signer set actually validated" and "what is checked."

### Impact Explanation
If the next-cycle signer instance's own state machine disagrees with the current sortition's miner (e.g. because it observed a different/absent miner update, or its differently-weighted signer set reached a different capitulation outcome), it sets `cur_sortition.miner_status = InvalidatedBeforeFirstBlock` on the shared `SortitionsView`. On the very next event the current-cycle signer processes, its `check_proposal` will reject an otherwise valid, canonical block proposal from the legitimate current-tenure miner with `RejectReason::InvalidMiner`, even though nothing in the *current* cycle's own signer-set consensus warranted that. Repeated corruption from the concurrently-running next-cycle instance can wedge the current signer into never signing valid blocks for that tenure — a High-impact liveness wedge matching the accepted impact class ("a signer wedged into never signing valid blocks ... or losing the equivocation guard").

### Likelihood Explanation
This requires no majority collusion and no key compromise: it is triggered purely by the ordinary, permitted overlap of two `ConfiguredSigner` instances sharing one mutable `sortition_state` reference, which occurs on every reward-cycle boundary transition (during the next cycle's prepare phase) as part of normal gossip/StackerDB message processing. Any divergence in miner view between the outgoing and incoming reward-cycle signer sets (a routine occurrence around cycle boundaries and tenure changes) is sufficient to trigger the cross-context write.

### Recommendation
Scope `SortitionsView` (and specifically `cur_sortition.miner_status`) per `ConfiguredSigner`/reward cycle instead of sharing one instance across all signer instances in `RunLoop`. Alternatively, have `capitulate_viewpoint` refuse to mutate `sortition_state.cur_sortition.miner_status` for a signer instance whose own reward cycle has not yet started (`self.reward_cycle > current_reward_cycle`), and audit all other call sites where `&mut Option<SortitionsView>` is passed identically to multiple `ConfiguredSigner`s in the same pass.

### Proof of Concept
1. Approach a reward-cycle boundary so that `RunLoop` has two registered `ConfiguredSigner`s: current cycle `N` and next cycle `N+1` (`stacks-signer/src/runloop.rs:371-377`).
2. Let other signers in reward-set `N+1` (a different weight table) broadcast `StateMachineUpdate` messages that disagree with the actual current sortition's miner (e.g., a stale or forked view still propagating for the next cycle).
3. On a pass in `run_one_pass`, the `N+1` signer's `process_event` runs `capitulate_viewpoint` first (loop over `self.stacks_signers.values_mut()`), and because its own consensus disagrees with `sortition_state.cur_sortition.data.miner_pkh`, it sets `sortition_state.cur_sortition.miner_status = InvalidatedBeforeFirstBlock` (`stacks-signer/src/v0/signer_state.rs:964-977`).
4. Immediately afterward in the same pass, the `N` signer's `process_event` handles an incoming, entirely valid `BlockProposal` from the legitimate current-tenure miner via `handle_block_proposal` → `check_block_against_local_state` → `sortition_state.check_proposal`, which now reads the corrupted `miner_status` and returns `Err(RejectReason::InvalidMiner)` (`stacks-signer/src/chainstate/v1.rs:288-300`), causing this signer to reject a valid block it would otherwise have signed.
