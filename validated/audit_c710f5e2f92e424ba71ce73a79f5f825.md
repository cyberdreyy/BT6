## Title
Secrets-resolution stage runs outside any build context/cancellation, letting a hung `resolver.Resolve()` block the job goroutine forever and evade `job.Cancel()` - (File: common/build.go)

## Summary
`Build.Run` calls `b.resolveSecrets(trace)` (line 1549) *before* the build's cancellable `ctx, cancel := context.WithTimeout(ctx, b.GetBuildTimeout())` is created (line 1560) and before `b.configureTrace(trace, cancel)` wires up the cancel/abort functions (line 1563). The entire secret-resolution call chain (`executeResolveSecretsStage` → `helpers.BuildSection.Execute` → `SecretsResolver.Resolve` → `SecretResolver.Resolve`) is synchronous, untimed, and takes no `context.Context` at all, so neither the job's timeout machinery nor a user/API-triggered cancellation can interrupt a stalled resolver.

## Finding Description
`helpers.BuildSection.Execute` (`helpers/build_section.go:44-49`) is a trivial synchronous wrapper: it just calls `s.Run()` directly with no goroutine, no `select` on a context, and no deadline. [1](#0-0) 

`Build.executeResolveSecretsStage` builds a `BuildSection` whose `Run` closure calls `resolver.Resolve(b.Secrets)` synchronously: [2](#0-1) 

Critically, the `SecretsResolver` and `SecretResolver` interfaces carry no `context.Context` parameter whatsoever: [3](#0-2) 

And in `Build.Run`, secrets resolution happens *before* the job-scoped, cancellable context and the trace cancel/abort wiring exist: [4](#0-3) 

`b.configureTrace(trace, cancel)` — the call that lets an external `job.Cancel()`/UI abort actually interrupt the running job — only happens *after* `resolveSecrets` has already returned. This means that while a secret resolver is blocked, there is no cancel function registered on the trace yet, so a cancellation signal delivered during this window has nothing to act on inside the runner process; the goroutine executing `Build.Run` (one worker slot from the runner's concurrency pool, e.g. as spawned by `mr.processBuildOnRunner` in `commands/multi.go`) simply keeps blocking inside `resolver.Resolve` → `handleSecret` → `sr.Resolve()`. [5](#0-4) 

Individual resolver implementations only inconsistently bound their own network calls. The AWS resolver does impose an explicit 30s `context.WithTimeout`: [6](#0-5) 

But GCP Secret Manager calls its client with a bare `context.Background()` — no deadline at all: [7](#0-6) 

The Azure Key Vault and GitLab/Vault-backed resolvers (`helpers/vault`) build their own HTTP-backed clients (`vault.NewClient`, `service.NewAzureKeyVault`) without threading in any per-request/job deadline; whatever timeout exists is only whatever default the underlying SDK's HTTP client happens to apply, not anything tied to the job's lifecycle. [8](#0-7) [9](#0-8) 

Secret server endpoints (`Server.URL`/similar fields under `secrets:` in `.gitlab-ci.yml`) are configured by the pipeline author and can reference CI/CD variables, so an unprivileged pipeline author can point a secret's backing server at an attacker-controlled host that accepts the TCP/TLS connection but never responds (or stalls mid-handshake), triggering the indefinite hang for whichever resolver lacks its own bounded context (GCP, Azure Key Vault, and the HTTP layers underneath the Vault/GitLab Secrets Manager clients absent an explicit deadline).

The `attemptResolveSecrets` retry wrapper (`common/build.go:1742-1755`) does not change this: it retries `executeResolveSecretsStage` synchronously, so the same unbounded blocking call is simply repeated after the first one returns — it provides no protection against a single call that never returns at all.

## Impact Explanation
Because the resolve-secrets stage executes before the job's build-timeout context and before the trace cancel function are established, a hung resolver call cannot be timed out by `GetBuildTimeout()` and cannot be aborted by a GitLab-side job cancellation. The goroutine running `Build.Run` for that job is permanently pinned blocking inside `sr.Resolve()`. Each job (and each retry of a "cancelled" job that a user or CI system repeatedly re-triggers pointed at the same non-responsive endpoint) consumes one of the runner's limited concurrent worker/goroutine slots indefinitely. Repeating this across many jobs progressively exhausts the runner's available concurrency (and associated open sockets/file descriptors held by the stalled dial/handshake), degrading or denying service to all other jobs/projects sharing that runner instance — a multi-tenant resource-exhaustion condition that survives job cancellation.

## Likelihood Explanation
This requires only that: (1) the runner is configured to resolve `secrets:` from a resolver whose underlying call is not wrapped in its own short deadline (GCP Secret Manager is a clear code-level example; Vault/Azure paths depend on SDK defaults which may be large or absent), and (2) the pipeline author can point the secret's server field at a host under their control (common in self-managed runner setups where `secrets:` server URLs are configurable per-job). No privileged access is needed — a normal pipeline author supplies the secret configuration in `.gitlab-ci.yml`. The bug is deterministic and fully repeatable: every job hitting the non-responsive endpoint hangs the same way, every time, and cancellation has no effect during the affected window.

## Recommendation
- Thread a `context.Context` through `SecretsResolver.Resolve` and `SecretResolver.Resolve`, derived from the job's cancellable context, and call `resolveSecrets` after (or in parallel with correctly ordered) the `context.WithTimeout(ctx, b.GetBuildTimeout())`/`configureTrace` setup in `Build.Run`, so cancellation and the build timeout apply to this stage too.
- Enforce a bounded per-resolver deadline (similar to the AWS resolver's `contextTimeout`) uniformly across all resolvers (GCP, Azure Key Vault, Vault/GitLab Secrets Manager), rather than relying on inconsistent SDK defaults.
- Ensure `helpers.BuildSection.Execute`/`Run` closures used for network-bound stages accept and respect a context so a canceled job cannot leave a goroutine blocked indefinitely.

## Proof of Concept
Go integration test outline:
1. Register a fake `SecretResolver` (or point the GCP/Azure resolver's underlying client at a TCP listener that accepts connections but never writes/reads) simulating a non-responsive secret server.
2. Construct a `Build` with `Secrets` referencing this resolver, invoke `build.Run(ctx, ...)` in a goroutine, and immediately call the job's cancellation path (simulating `job.Cancel()`/UI abort) or cancel the passed-in `ctx`.
3. Assert that `build.Run` returns (or the spawned goroutine terminates) within a bounded time (e.g. `b.GetBuildTimeout()` + slack) instead of hanging past that deadline — currently it will not return until the mock server closes/responds.
4. Repeat with N concurrent "canceled" jobs against the mock non-responsive server and assert via `runtime.NumGoroutine()` / open-FD count that goroutines are not accumulating unbounded once the corresponding contexts are cancelled — currently the count keeps climbing and never returns to baseline for the blocked resolvers.

func (b *Build) executeResolveSecretsStage(trace JobTrace) error {
	b.OnBuildStageStartFn.Call(BuildStageResolveSecrets)
	defer b.OnBuildStageEndFn.Call(BuildStageResolveSecrets)

	section := helpers.BuildSection{
		Name:        string(BuildStageResolveSecrets),
		SkipMetrics: !b.Job.Features.TraceSections,
		Run: func() error {
			logger := b.getNewLogger(trace, b.Log(), false)
			defer logger.Close()

			resolver, err := b.secretsResolver(&logger, GetSecretResolverRegistry(), b.IsFeatureFlagOn)
			if err != nil {
				return fmt.Errorf("creating secrets resolver: %w", err)
			}

			variables, err := resolver.Resolve(b.Secrets)
			if err != nil {
				return fmt.Errorf("resolving secrets: %w", err)
			}

			b.secretsVariables = variables
			b.RefreshAllVariables()

			return nil
		},
	}

	return section.Execute(&b.logger)
}

func (v *azureKeyVaultResolver) Resolve() (string, error) {
	if !v.IsSupported() {
		return "", secrets.NewResolvingUnsupportedSecretError(resolverName)
	}

	secret := v.secret.AzureKeyVault
	s, err := newVaultService(secret.Server)
	if err != nil {
		return "", err
	}

	name := secret.Name
	version := secret.Version

	data, err := s.GetSecret(name, version)

	if err != nil {
		return "", err
	}

	return fmt.Sprintf("%v", data), nil
}
