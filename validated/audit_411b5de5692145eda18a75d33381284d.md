### Title
`check_parent_tenure_choice` treats "we never saw the reorged block's approval" as proof of poor timing, letting a miner reorg a tenure without meeting the timing rule - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` is the sole gate that decides whether a miner is allowed to build off something other than the prior sortition (a tenure reorg). The rule is supposed to be objective: a reorg is only permitted if the reorged tenure's first block was proposed "too close" to the next sortition to count, measured as `sortition_state_received_time - local_block_info.approved_time`. When the signer's own local DB has no `approved_time` for that tenure's first block, the code silently substitutes `0` for the elapsed time instead of refusing to answer, which always satisfies the "too close" condition and unconditionally green-lights the reorg — even when the real proposal-to-sortition gap was large and the reorg should be refused.

### Finding Description [1](#0-0) 

The relevant branch:
```
let Some(local_block_info) = signer_db.get_first_approved_block_in_tenure(&tenure.consensus_hash)? else {
    // no local knowledge at all -> reject the reorg (safe default)
    return Ok(false);
};
let checked_proposal_timing = if let Some(sortition_state_received_time) = sortition_state_received_time {
    let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
        sortition_state_received_time.saturating_sub(approved_at)
    } else {
        info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
        0
    };
    if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
        // treat as poorly timed -> permit and supersede the tenure
        superseded_tenures.push(tenure);
        continue;
    }
    true
} else {
    false
};
``` [2](#0-1) 

Two distinct "we don't fully know" situations are handled very differently:
- If `get_first_approved_block_in_tenure` returns `None` (no local record at all), the function safely returns `Ok(false)` — reorg refused by default.
- If a `local_block_info` record exists but its `approved_time` field is `None`, the code does **not** apply the same safe-refusal default. Instead it substitutes `proposal_to_sortition = 0`, which is always `< first_proposal_burn_block_timing` (a positive duration), so the branch **always** takes the "poorly timed, permit the reorg" path — regardless of what the actual elapsed time was on the rest of the network.

This directly parallels the external report's bug class: a value that is unknown/undefined (a missing timestamp, analogous to a negative/absent PnL/fee component) is substituted with a value (`0`) that happens to make an inequality check trivially pass in the attacker's favor, instead of causing the code to conservatively refuse or query further. `approved_time` is documented elsewhere as being stamped "at pre-commit or local acceptance (first wins)" (see `docs/signer-flows.md` section 2), so a `BlockInfo` row can exist in a signer's DB without `approved_time` being set, e.g., for a block that was only stored/proposed but never itself pre-committed by this particular signer — which is exactly the state a signer can be in after being restarted, resynced, or simply delayed relative to the rest of the fleet.

### Impact Explanation
This lets a malicious miner reorg away an already-produced (and possibly globally-accepted) tenure block without satisfying the real `first_proposal_burn_block_timing` safety window, as long as it can get even one signer into a state where that signer's local record of the reorged tenure's first block lacks `approved_time` (e.g., a signer that only received the proposal after the fact via replay/pending-response, or restarted before it locally pre-committed). That signer will then treat `check_parent_tenure_choice` as passing and go on to sign a block that conflicts with a tenure's already-produced/accepted block, in violation of the exact reorg-timing protection this subsystem exists to enforce (see the extensive `conflict_still_blocks`/`reorg_permit_stands` machinery in `signer.rs`, which is explicitly built to prevent exactly this class of erroneous reorg-sign). Per the scoring rubric this is "a signer signing an invalid/non-canonical/conflicting block" — a Critical-class outcome — achieved purely through miner-controlled tenure/proposal timing and normal gossip propagation delay, without needing another signer's key or a signer majority.

### Likelihood Explanation
Likelihood depends on an attacker being able to reliably put at least one signer into the "record exists, but `approved_time` unset" state for a tenure it intends to reorg. This is plausible without any privileged access: a signer that restarts (losing pending pre-commit progress but retaining a proposal insert from before), or one that receives the reorging proposal through the normal "early votes / pending" replay path before it finishes pre-committing to the original tenure's block, can end up in this exact state through ordinary timing/gossip races the miner can influence (e.g., timing when it broadcasts the reorging proposal relative to signer restarts, or exploiting the tenure_last_block_proposal_timeout window). This does not require majority collusion, since the vulnerability is in each signer's independent, local decision function.

### Recommendation
Do not treat a missing `approved_time` on an existing local block record as proof of "late/poor timing." When `local_block_info.approved_time` is `None`, the signer should either:
- refuse the reorg by default (mirroring the `None`-record branch that already returns `Ok(false)`), or
- fall back to `local_block_info.proposed_time` (or another timestamp that is guaranteed to be set whenever a record exists) instead of substituting `0`, so that `proposal_to_sortition` reflects a real elapsed time rather than an artificial zero that trivially satisfies the timing check.

### Proof of Concept
Conceptual PoC (cannot be executed without a live devnet/testnet cluster):
1. Miner M produces tenure T1's first block; it propagates to the signer set. Assume it becomes globally accepted (only 1 globally-accepted block in T1, satisfying the earlier `globally_accepted_blocks > 1` guard).
2. Before signer S locally reaches `mark_pre_committed`/`mark_locally_accepted` for T1's first block (e.g., S is mid-restart, or the proposal is only replayed into S's DB via `drain_pending_block_responses` without S itself having pre-committed), S's `BlockInfo` for that block exists but `approved_time` is `None`.
3. Miner M immediately mines tenure T2 building off the sortition prior to T1 (a reorg of T1), a long time after T1's first block was actually proposed — i.e., the real world timing violates `first_proposal_burn_block_timing`.
4. S's `check_parent_tenure_choice` computes `proposal_to_sortition = 0` (since `approved_time` is `None`), which is `< first_proposal_burn_block_timing`, so S marks T1 as `superseded` and treats the reorg as permitted, going on to sign T2's block even though it conflicts with T1's already-produced/accepted block and the real timing rule was violated.
5. Other signers that did record `approved_time` for T1 correctly refuse the reorg (`checked_proposal_timing = true` path, `return Ok(false)`), so S's viewpoint diverges from the rest of the honest set — S has signed a conflicting/non-canonical block that violates the invariant the rest of the codebase (`conflict_still_blocks`, `reorg_permit_stands`, section 5 of `docs/signer-flows.md`) is designed to prevent.

Note: I was not able to fully inspect `SignerDb::get_first_approved_block_in_tenure`'s exact query/definition before running out of tool budget, so I cannot 100% confirm every code path that can leave `approved_time` unset on an existing row; this should be verified directly in `stacks-signer/src/signerdb.rs` before treating this as a confirmed, reproducible exploit rather than a substantiated logic defect in `check_parent_tenure_choice`.
