## Analysis

The external report's core theme — a validated parameter is silently invalidated by a later state change, producing a distribution/accounting result that no longer matches the state on which it was validated — has a direct analog in the `multisig` and `multisig2` contracts: a **removed signer's stale confirmation still counts toward the `num_confirmations` threshold** for pending requests it was not the *original* requester of.

### Root cause

In both `multisig/src/lib.rs` and `multisig2/src/lib.rs`, `execute_request`'s `DeleteKey`/`DeleteMember` handler only purges pending requests that the removed key/member originally *created* (`r.signer_pk == pk` in v1, `r.member == member` in v2). It does **not** scan other pending requests' `confirmations` sets to strip out confirmations previously cast by that same key/member as a *co-signer*. [1](#0-0) [2](#0-1) 

Meanwhile, `confirm()` only checks whether the *current* caller already confirmed and then compares `confirmations.len() + 1` against `num_confirmations` — it never re-validates that previously stored confirmations still belong to currently live members/keys: [3](#0-2) [4](#0-3) 

This breaks the equality that should hold: `confirmations_counted(request) == confirmations_from_currently_live_members(request)`.

### Proof of concept (multisig v1, analogous for v2)

1. `num_confirmations = 3`, members with keys `A, B, C, D`.
2. `B` creates request `R` (e.g., `Transfer` to an attacker-controlled account). `R.signer_pk = B`.
3. `A` confirms `R` → `confirmations(R) = {A}`.
4. `C` confirms `R` → `confirmations(R) = {A, C}` (2/3, not yet executed).
5. Members later revoke key `A` (compromised) by executing a separate `DeleteKey{A}` request confirmed by `B, C, D`. The `DeleteKey` handler removes only requests where `signer_pk == A` (not `R`, since `R.signer_pk == B`), so `R`'s confirmation set `{A, C}` is left untouched. `A`'s access key is deleted on-chain.
6. Now only `B, C, D` remain live keys, yet `R` still shows 2 confirmations, one of which (`A`) is from a revoked key.
7. `D` confirms `R` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request(R)` fires the `Transfer`, even though only two currently-live keys (`C`, `D`) actually approved it — below the intended 3-of-n threshold.

### Impact

This allows a request (including fund transfers, key/member management, or contract upgrades) to execute with fewer live confirmations than the configured threshold — a multisig request executed below threshold, matching the Critical impact bucket defined by the prompt ("a multisig request executed below threshold").

### Recommendation

When a key/member is deleted, `DeleteKey`/`DeleteMember` handlers should also strip that key/member's identity from every pending request's `confirmations` set (not just requests it originally authored), or `confirm()` should re-validate that all stored confirmations still belong to current members before comparing against `num_confirmations`.

### Title
Stale confirmations from revoked multisig keys/members are still counted toward the confirmation threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
`DeleteKey` (multisig v1) and `DeleteMember` (multisig v2) only purge pending requests originated by the removed key/member; confirmations cast by that key/member on *other* pending requests remain in storage and are still counted by `confirm()` toward `num_confirmations`, letting a request execute with fewer currently-authorized confirmers than the configured threshold.

### Finding Description
`execute_request`'s `DeleteKey` ( [1](#0-0) ) and `DeleteMember` ( [2](#0-1) ) handlers filter `self.requests` by `signer_pk`/`member` equal to the revoked identity and clear only those. They never inspect `self.confirmations` entries belonging to *other* requests where the revoked identity had already contributed a confirmation as co-signer. `confirm()` ( [3](#0-2)  / [4](#0-3) ) blindly trusts the stored `HashSet` size, so a stale confirmation from a revoked key/member is indistinguishable from a live one.

### Impact Explanation
The intended custody binding of a k-of-n multisig is `confirmations recorded == confirmations by currently authorized signers`. This binding is broken: a request can execute with a threshold count that includes a revoked signer, effectively lowering the real number of live approvers required. Since `execute_request` can perform `Transfer`, `DeployContract`, `AddKey`/`AddMember`, and `FunctionCall` actions, this can lead to unauthorized fund transfers or account takeover with less-than-configured approval, which is a Critical-severity outcome per the given impact classes ("a multisig request executed below threshold").

### Likelihood Explanation
This requires a normal multisig operational sequence: a pending request gets partial confirmations, then one of the confirming keys/members is later revoked (a routine key-rotation/security event), and the request is subsequently completed by other live members. No exploitation trick beyond ordinary usage is needed, and NEAR core-contracts' multisig contracts are used to secure high-value accounts (e.g. by the Foundation and its multisig-factory deployments), making this a realistic and highly consequential operational gap.

### Recommendation
On `DeleteKey`/`DeleteMember`, iterate all entries in `self.confirmations` and remove the revoked key/member's entry from every set, not just requests it authored; alternatively, validate at `confirm()` time that all previously stored confirmers are still members before counting them toward `num_confirmations`.

### Proof of Concept
See the PoC steps above: revoke a key that already confirmed a pending request, then let the remaining live members supply just enough further confirmations to hit the old `num_confirmations` count that includes the stale entry, causing execution with fewer than `num_confirmations` live approvals.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })

            // remove confirmations for this request

            self.requests.remove(&request_id);

        self.num_requests_pk.remove(&member.to_string());

            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
