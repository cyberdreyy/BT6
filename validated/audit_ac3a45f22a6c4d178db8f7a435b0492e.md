### Title
Denial of Service Risk Due to Unvalidated Freeze Authority on `bank_mint` in `LendingPoolAddBank` - ([File: programs/marginfi/src/instructions/marginfi_group/add_pool.rs])

### Summary
`LendingPoolAddBank` accepts an arbitrary `bank_mint: InterfaceAccount<'info, Mint>` without validating whether the mint has a `freeze_authority` set [1](#0-0) . The `liquidity_vault`, `insurance_vault`, and (implicitly) `fee_vault` token accounts are all initialized with `token::mint = bank_mint` [2](#0-1) . If the admin (or, in the `clone_bank`/permissionless-listing style paths that also reuse `source_mint` without freeze checks [3](#0-2) ) initializes a bank with a mint that has a freeze authority, the mint issuer can later freeze the bank's vault token accounts, permanently blocking all deposits/withdrawals for that bank.

### Finding Description
No check for `freeze_authority.is_some()` exists anywhere in the marginfi-v2 program; a repo-wide search for `freeze_authority`/`FreezeAuthority`/`MintHasFreezeAuthority` returns zero matches. This mirrors the root cause of the referenced ONFT `H-01` finding: a mint field is accepted at pool/bank initialization time with no validation of its freeze authority, and the resulting escrow/vault token account can later be frozen by the mint's freeze authority, causing an irrecoverable state for token movements tied to that account.

In marginfi, the equivalent asset is the bank's SPL vaults:
- `liquidity_vault` — used for all deposit/withdraw/borrow/repay transfers [4](#0-3) .
- `insurance_vault` / `fee_vault` — created alongside the liquidity vault at bank-add time [5](#0-4) .

If the bank's underlying SPL mint's freeze authority freezes any of these vault accounts, subsequent SPL token transfers into or out of that account will be rejected by the SPL Token program at the CPI layer, since `deposit_spl_transfer` performs a direct `transfer`/`transfer_checked` CPI with no fallback path [6](#0-5) .

### Impact Explanation
A frozen `liquidity_vault` renders the entire bank for that mint permanently unusable: deposits (`lending_account_deposit`), withdrawals, borrows, and repays that touch the vault will all revert on the underlying SPL CPI. Depositors' funds already in the vault become inaccessible (frozen, not stolen, but a durable denial-of-service with real financial impact — locked user funds). Because `bank_mint` is fully attacker/issuer-controlled at add-bank time and no allowlist or freeze check exists, this is a realistic and durable freeze condition, consistent with "High" severity in the original report.

### Likelihood Explanation
Likelihood depends on group-admin trust and mint selection practices: `LendingPoolAddBank` is restricted to the group `admin` via `has_one = admin` [7](#0-6) , so exploitation ultimately requires either (a) an admin unknowingly listing a mint that has (or later adds, though SPL mints generally fix freeze authority at creation) a freeze authority controlled by a malicious/compromised third party, or (b) a permissionless/less-trusted bank-cloning path (`clone_bank.rs`) reusing an untrusted `source_mint` without validating freeze authority. Since many real-world SPL tokens (including regulated stablecoins) legitimately carry a freeze authority, the risk is non-trivial and matches the "sample implementation" guidance in the original report advocating an explicit check or allowlist policy.

### Recommendation
1. At `LendingPoolAddBank` (and any bank-cloning/reuse path such as `clone_bank.rs`), reject mints where `bank_mint.freeze_authority.is_some()`, unless the mint is on an explicit protocol allowlist (e.g., major regulated stablecoins).
2. If freeze-authority mints must be supported, surface a clear warning/flag on the bank config so downstream UIs and integrators can disclose the risk to depositors.
3. Add a regression test analogous to `tests/specs/basic/15_accountFreeze.spec.ts` (which currently only exercises marginfi's own `ACCOUNT_FROZEN` account flag, not SPL-level mint freeze authority) that attempts to add a bank with a freeze-authority mint and asserts failure.

### Proof of Concept
1. Admin calls `create_initialize_mint2` (or similar) specifying a non-null `freeze_authority`.
2. Admin calls `lending_pool_add_bank` with this mint as `bank_mint`; the instruction succeeds because no freeze-authority check exists [8](#0-7) .
3. Users deposit into the bank, populating `liquidity_vault`.
4. The mint's freeze authority calls the SPL Token `FreezeAccount` instruction on `liquidity_vault`.
5. Any subsequent `lending_account_deposit`/withdraw/borrow/repay CPI touching `liquidity_vault` fails at the SPL Token program level, permanently freezing user funds in that bank.
