### Title
`internal_ping` reverts on any balance decrease (e.g. validator slashing), permanently freezing every delegator's staked and unstaked funds - ([File: staking-pool/src/internal.rs])

### Summary
The staking pool's reward-distribution routine `internal_ping` assumes the contract's total balance (`account_locked_balance() + account_balance()`) can never decrease between epochs. It hard-asserts this with `assert!(total_balance >= self.last_total_balance, ...)`. Because `internal_ping` is invoked unconditionally at the top of every single state-changing method (`ping`, `deposit`, `deposit_and_stake`, `withdraw`, `withdraw_all`, `stake`, `stake_all`, `unstake`, `unstake_all`), if the validator ever suffers a legitimate balance loss — most notably slashing, which is a documented and expected NEAR consensus risk — the very first call to any of these methods in the following epoch will panic and abort, and every subsequent call will do the same forever, since `last_total_balance` is only updated inside the same assertion that fails.

### Finding Description
`internal_ping` in [1](#0-0)  computes the new total balance and asserts it is not less than the previously recorded `last_total_balance`:
```
let total_balance = env::account_locked_balance() + env::account_balance() - env::attached_deposit();
assert!(total_balance >= self.last_total_balance, "The new total balance should not be less than the old total balance");
```
This mirrors exactly the flaw in the External Report: the Sense `Redeemer.redeem()` code assumes "one PT equals at least one underlying" and reverts if `redeemed < amount`, with no path to handle a legitimate loss (e.g. Lido slashing). Here the staking pool assumes the pool's total balance is monotonically non-decreasing, with no path to handle a legitimate loss (validator slashing), which the project's own README acknowledges is out of scope for its guarantees: "Guarantees are based on the no-slashing condition. Once slashing is introduced, the contract will no longer provide some guarantees" [2](#0-1) .

The critical difference from a simple "the guarantee doesn't hold under slashing" caveat is that here the failure mode is not merely "share price incorrectly reported" — it is a hard `assert!` that reverts the entire transaction, and this assert sits in a function called by literally every entry point that touches funds:
- `ping` [3](#0-2) 
- `deposit` / `deposit_and_stake` [4](#0-3) 
- `withdraw` / `withdraw_all` [5](#0-4) 
- `stake` / `stake_all` [6](#0-5) 
- `unstake` / `unstake_all` [7](#0-6) 

Since `last_total_balance` is only ever updated at the end of a successful `internal_ping` call [8](#0-7) , once a slashing event drops the real balance below the recorded `last_total_balance`, every future call to any of the above methods recomputes the same (now-lower) `total_balance`, re-triggers the same failed assertion, and reverts. There is no recovery path in this contract: no owner method exists to reset `last_total_balance` or otherwise acknowledge the loss.

**The binding broken (as an equality):**
- Expected: `last_total_balance_after_epoch == locked_balance + account_balance` should be allowed to move in either direction, since NEAR validators can be slashed, and the contract should adjust total_staked_balance and share price downward.
- Actual: The contract enforces `total_balance >= last_total_balance` as an invariant, so any decrease is treated as an anomaly requiring a full revert rather than a legitimate loss to be distributed (negatively) across "stake" shares.

### Impact Explanation
This is a Critical / permanent-funds-freezing bug: after a slashing event (a known, non-exotic NEAR protocol risk, not requiring any malicious actor within this contract's trust boundary), no delegator — including the pool owner — can ever again `deposit`, `withdraw`, `stake`, `unstake`, or even call `ping` to unfreeze the pool. All staked and unstaked balances held by the contract become permanently inaccessible through the contract's public interface. This matches the report's "Permanent freezing of funds" impact classification and required-outcome category of "funds permanently frozen."

### Likelihood Explanation
Slashing is a documented consensus-level risk for any NEAR validator that this staking pool contract is designed to represent (the contract itself literally calls `Promise::new(...).stake(...)` to become a validator via `internal_restake` [9](#0-8) ). No malicious action inside this repository's contracts is required to trigger it — an unrelated validator-node fault (double-signing, downtime past protocol thresholds, etc.) suffices. The README already flags this as a known unhandled scenario, confirming the maintainers were aware slashing was out of scope for the current invariants but did not add a graceful degradation path.

### Recommendation
Remove the hard `assert!` on total-balance non-decrease in `internal_ping`, and instead handle a decrease as a loss to be applied to `total_staked_balance` (and thus to the "stake" share price) symmetrically to how gains are applied, rather than reverting. At minimum, add an owner-gated recovery method that can re-baseline `last_total_balance` after a confirmed slashing event so the pool does not remain permanently bricked, and ensure the share-price computation in `staked_amount_from_num_shares_rounded_down`/`_up` correctly reflects a reduced `total_staked_balance` for all pending unstake/withdraw operations.

### Proof of Concept
1. Pool has `last_total_balance = X` after a normal epoch of `ping`/`deposit`/`stake` activity.
2. The pool's validator node is slashed by the NEAR protocol, reducing `env::account_locked_balance() + env::account_balance()` to `X' < X`.
3. Any delegator (or the owner) calls any of `ping`, `deposit`, `deposit_and_stake`, `withdraw`, `withdraw_all`, `stake`, `stake_all`, `unstake`, `unstake_all`.
4. `internal_ping` computes `total_balance = X' < self.last_total_balance = X` and hits `assert!(total_balance >= self.last_total_balance, ...)`, which panics and reverts the transaction.
5. Because `last_total_balance` was never updated (the assert fires before the update on line 248), every subsequent call by every account repeats step 4 forever — no state-changing method on the contract can ever succeed again, permanently freezing all staked and unstaked balances of every delegator.

```rust
    /// Distributes rewards after the new epoch. It's automatically called before every action.
    /// Returns true if the current epoch height is different from the last epoch height.
    pub(crate) fn internal_ping(&mut self) -> bool {
        let epoch_height = env::epoch_height();
        if self.last_epoch_height == epoch_height {
            return false;
        }
        self.last_epoch_height = epoch_height;

        // New total amount (both locked and unlocked balances).
        // NOTE: We need to subtract `attached_deposit` in case `ping` called from `deposit` call
        // since the attached deposit gets included in the `account_balance`, and we have not
        // accounted it yet.
        let total_balance =
            env::account_locked_balance() + env::account_balance() - env::attached_deposit();

        assert!(
            total_balance >= self.last_total_balance,
            "The new total balance should not be less than the old total balance"
        );
        let total_reward = total_balance - self.last_total_balance;
```
