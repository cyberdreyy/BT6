## Analysis

Confirmed root cause in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, function `run` (message-processing loop, `BlockResponse::Accepted`/`BlockResponse::Rejected` handlers).

- On `Rejected`: `block.responded_signers.insert(slot_id)` returning `true` (first response) increments `block.total_weight_rejected` [1](#0-0) .
- On a later `Accepted` from the *same* signer (vote flip), the code only checks `!block.gathered_signatures.contains_key(&slot_id)` to gate the `total_weight_approved` increment [2](#0-1) ; it never checks or clears `total_weight_rejected`, so the previously-added rejection weight for that signer is never decremented (the analog of `buyoutLien()` never calling `decreaseEpochLienCount()`).

This is exactly the bug-class in the report: a value is "moved" from one bucket (`total_weight_rejected`) to another (`total_weight_approved`) without decrementing the source, breaking the invariant that `total_weight_approved` and `total_weight_rejected` partition the signer set's weight.

### Title
Signer vote-flip double-counts weight in both `total_weight_approved` and `total_weight_rejected`, breaking the accept/reject weight invariant - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener`'s block-status aggregation increments `total_weight_rejected` when a signer's `Rejected` response is first seen, and separately increments `total_weight_approved` when an `Accepted` response is first seen from that signer — gated independently by `responded_signers` and `gathered_signatures` respectively. Neither branch removes a signer's weight from the other bucket, so a signer that rejects and later accepts (or vice versa) is counted in both totals simultaneously.

### Finding Description
`get_block_status`/the coordinator relies on `BlockStatus.total_weight_approved` and `total_weight_rejected` to decide the miner's next action: approve (broadcast) once `total_weight_approved >= weight_threshold` [3](#0-2) , or abandon the proposal once `total_weight_rejected` makes 70% approval impossible [4](#0-3) . These two checks implicitly assume `total_weight_approved + total_weight_rejected <= total_weight`.

In the listener:
- Rejection path increments `total_weight_rejected` guarded only by `block.responded_signers.insert(slot_id)` [1](#0-0) .
- Acceptance path increments `total_weight_approved` guarded only by `!block.gathered_signatures.contains_key(&slot_id)` [5](#0-4) .

Because `responded_signers` and `gathered_signatures` are two independent sets, a single signer address can trip both increments for the same block by sending Rejected then Accepted (a legitimate scenario: e.g. re-evaluating after a `should_reevaluate_block`/pre-commit re-evaluation flow that can flip a prior rejection to an acceptance, as seen on the signer side in `should_reevaluate_reject_reason`/`should_reevaluate_block` [6](#0-5) ). No code path subtracts the stale weight from `total_weight_rejected` when the same signer later accepts (or from `total_weight_approved` if they later reject).

### Impact Explanation
This breaks the aggregated-weight-vs-verified-accepts equality the miner relies on for a go/no-go decision on block broadcast. Concretely:
- `total_weight_rejected` can remain permanently inflated by weight that has actually flipped to approval, causing the miner to spuriously conclude rejection is inevitable (`NakamotoNodeError::SignersRejected`) and abandon a proposal that in fact has (or could reach) the 70% approval threshold — a liveness wedge on block production for that miner/tenure.
- Conversely, `total_weight_approved` and `total_weight_rejected` can simultaneously appear to satisfy their respective thresholds (sum exceeding `total_weight`), since the code's early "signal notify" checks at each accept/reject event fire independently once each counter alone crosses its own threshold, regardless of the other counter's state.

This matches the "liveness wedge" / miscounted response class called out in the rules, reachable purely by a single signer sending a rejection followed later by an acceptance (or the reverse) for the same block — no majority collusion required.

### Likelihood Explanation
Signers are documented and coded to change their block-response verdict for the same `signer_signature_hash` when circumstances change (`should_reevaluate_block`, pre-commit re-evaluation, and rejection reasons that are re-evaluable) [6](#0-5) . Thus a normal, non-malicious sequence of events (network delay causing a stale rejection followed by a corrected acceptance, or the reverse) reliably triggers this on the node side, since the node-side listener has no logic that reconciles the two counters against a signer's latest verdict.

### Recommendation
Track each signer's current verdict (accepted vs rejected) in a single per-slot map instead of two independent sets/maps, and when a signer's verdict changes, decrement the weight from the previous bucket before adding it to the new one, e.g.:
```rust
match previous_verdict {
    Some(Verdict::Rejected) if new == Accepted => {
        block.total_weight_rejected = block.total_weight_rejected.saturating_sub(signer_entry.weight);
    }
    Some(Verdict::Accepted) if new == Rejected => {
        block.total_weight_approved = block.total_weight_approved.saturating_sub(signer_entry.weight);
    }
    _ => {}
}
```
and only then apply the increment for the new verdict.

### Proof of Concept
1. Miner proposes block `B` and waits via `get_block_status` (`stacks-node/src/nakamoto_node/signer_coordinator.rs`).
2. Signer `S` (weight `w`) initially sends `BlockResponse::Rejected` for `B` (e.g. due to a transient state mismatch). Listener sets `block.responded_signers.insert(slot_id) == true` and `total_weight_rejected += w`.
3. `S` re-evaluates (per `should_reevaluate_block`/pre-commit flow) and later sends `BlockResponse::Accepted` for the same `signer_signature_hash`. Listener checks only `!block.gathered_signatures.contains_key(&slot_id)` (true, since `S` never accepted before) and does `total_weight_approved += w`, without touching `total_weight_rejected`.
4. Now `block.total_weight_rejected` still includes `w` from step 2, and `block.total_weight_approved` also includes `w` from step 3 — `S`'s weight is double counted across the two mutually-exclusive tallies, and `total_weight_rejected` never reflects that `S` in fact currently approves, potentially causing `get_block_status` to return `SignersRejected` erroneously (wedging that tenure's block production) even though sufficient approval weight exists once the stale reject weight is discounted.
