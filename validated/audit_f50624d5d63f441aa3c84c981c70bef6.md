### Title
Post-default withdraw receipts are paid 1:1 from the fixed recovery reserve, draining defaulted claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analogous to the actix-service aliasing bug (two "mutable owners" of the same data), `IdleCreditVault` gives two different claim classes exclusive-looking access to the same `defaultRecoveryReserve`: defaulted-epoch receipts priced at `defaultRecoveryPrice`, and post-default receipts created by `requestWithdraw` that are paid out 1:1. Post-default requests add new claims to a reserve whose size was fixed at finalization, so each post-default claim spends recovery funds that belong to earlier defaulted claimants.

### Finding Description
`finalizeDefaultRecovery` computes `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + old reserve` and `recoveryPrice = reserveAmount / totalBasis`, where `totalBasis` only includes active basis plus pending default-epoch receipts (lines 686–693). The reserve exactly covers `totalBasis * defaultRecoveryPrice`.

After finalization, `requestWithdraw` takes the `defaultRecoveryFinalized` branch (lines 247–257): it burns the CDO's strategy tokens, mints receipt tokens to the user, and records `postDefaultRequests[_user]`. No underlying is added to `defaultRecoveryReserve`. `_claimPostDefaultWithdrawRequest` then pays these receipts 1:1 via `_transferDefaultRecovery` (lines 760–766), which decrements `defaultRecoveryReserve` and transfers the full `amount`.

The CDO strategy tokens burned for the post-default request were only backed at `defaultRecoveryPrice` per unit (finalization adjusted active NAV to `activeBasis * recoveryPrice`, lines 699–705). The receipt therefore converts a claim economically worth `amount * recoveryPrice` into a payout of `amount`. Every post-default claim extracts `(1 - recoveryPrice) * amount` of unbacked value, drawn from the same finite reserve owed to defaulted-epoch receipt holders and active LPs. Late defaulted claimants' `_transferDefaultRecovery` calls will underflow/revert on the depleted reserve — permanent freezing/theft of their recovery.

The `_transferFundedClaim` reserve guard (lines 897–905) does not help: post-default claims deliberately bypass it by using `_transferDefaultRecovery`, and nothing caps cumulative post-default payouts to the reserve's surplus over `totalBasis * defaultRecoveryPrice`.

### Impact Explanation
Any tranche-token holder can, after `finalizeDefaultRecovery`, call `requestWithdraw` and immediately `claimWithdrawRequest`, receiving 1:1 underlying from the recovery reserve while their burned claim was only worth `recoveryPrice`. Loss to other claimants is `(1 - recoveryPrice) * claimedAmount`; e.g., at a 50% recovery price, a post-default claim of 100k USDC steals 50k USDC of recovery owed to defaulted-epoch withdrawers, whose claims then permanently revert on the drained reserve. With recovery price < 1 this is direct theft plus permanent freezing of unclaimed recovery.

### Likelihood Explanation
Requires a borrower default followed by `finalizeDefaultRecovery` — an honest-privileged flow the rules permit sequencing around. The attacker is an ordinary tranche-token holder (explicitly in scope), needs no timing edge beyond acting before other claimants, and the payout path (`claimWithdrawRequest` → `_claimPostDefaultWithdrawRequest` → `_transferDefaultRecovery`) has no guard limiting post-default draws to reserve surplus. Any default with `recoveryPrice < 1` and post-default withdraw demand triggers it deterministically.

### Recommendation
Fund post-default receipts separately instead of spending `defaultRecoveryReserve`: either pull the corresponding underlying from the CDO/borrower when the post-default request is created (minting a reserve-backed claim), or track a `postDefaultReserve` bucket and pay `_claimPostDefaultWithdrawRequest` only from underlying balance above `defaultRecoveryReserve` (the `_transferFundedClaim` guard pattern), reverting if insufficient. Alternatively, apply `defaultRecoveryPrice` to post-default claims too, so a claim can never pay out more than its burned backing.

### Proof of Concept
Foundry fork PoC outline (mirroring `test/foundry/IdleCreditVault.t.sol` default scenarios):

```solidity
function testPostDefaultClaimDrainsRecoveryReserve() external {
    // Setup: userA deposits AA, epoch 0 runs, userA requestWithdraw(X) -> pending receipt.
    // userB holds tranche tokens, no pending request.

    // Borrower defaults; manager/owner finalize:
    //   cdoEpoch._handleBorrowerDefault(); finalizeDefault(recovered < basis);
    // -> strategy.finalizeDefaultRecovery(recovered, source)
    // reserve = R, recoveryPrice = R / totalBasis < 1e18.

    // Attacker (userB, ordinary tranche holder):
    vm.startPrank(userBIdleCdoCaller); // via cdoEpoch
    cdoEpoch.requestWithdraw(trancheBalB, address(AAtranche)); // post-default branch
    strategy.claimWithdrawRequest(userB);                    // pays Y 1:1 from reserve
    vm.stopPrank();

    // userA's defaulted claim owed = basis_A * recoveryPrice
    vm.expectRevert(); // underflow on defaultRecoveryReserve or insufficient balance
    strategy.claimWithdrawRequest(userA); // reserve drained by post-default claim
    // assert userB received Y while contributing backing worth only Y * recoveryPrice
}
```

Key assertions: `userB` balance increases by `postDefaultRequests` at par; subsequent `_claimDefaultedWithdrawRequest`/`_transferDefaultRecovery` for `userA` reverts because `defaultRecoveryReserve` was decremented by claims never included in `totalBasis`.
