### Title
Gateway HTTP-action response cache is scoped only by workflow owner, not by workflow ID, contradicting the documented per-workflow isolation guarantee — ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's `responseCache` for outbound HTTP capability actions is documented to isolate cached responses per workflow ("Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" — same class of bug as the external report: a piece of cached state that the system relies on for correctness/isolation is not actually kept in sync with the identifier it's supposed to be scoped by, so stale/wrong cached data gets handed out to the wrong party.

### Finding Description
`responseCache.Fetch`/`Set` key the cache purely on `req.Hash()`: [1](#0-0) [2](#0-1) 

The project's own unit test explicitly documents and asserts that `WorkflowID` is excluded from the hash computation, while `WorkflowOwner` is included: [3](#0-2) 

Yet the module's README states the opposite guarantee — that the cache key is generated from *workflow ID* and request hash, and that entries are scoped by workflow ID specifically to prevent cross-workflow data leakage: [4](#0-3) 

This is the same bug class as the external report: a cached/derived value (`liquidatedCollateralAmountInWei`) that the system depends on for correctness is not kept properly scoped/updated relative to the entity it's supposed to track (per-user balance vs. per-workflow cache key), so the system serves stale/incorrect state to a party that is not actually entitled to it. Here, any two workflows deployed under the same `WorkflowOwner` that issue HTTP actions with identical method/URL/headers/body (and `CacheSettings.Store=true`) will collide on the same cache entry and one workflow's fetched response is silently served to a different workflow, regardless of the intended workflow-level isolation asserted by the documentation. The gateway's inbound path is reachable via `HandleNodeMessage → makeOutgoingRequest`, which parses the `OutboundHTTPRequest` from a DON node message and drives `Fetch`/`Set`: [5](#0-4) .

### Impact Explanation
This falls under "cross-user response confusion": responses intended for one workflow can be transparently served to another workflow owned by the same account, violating the documented workflow-scoping guarantee. Because `CacheSettings` fields (`Store`, `MaxAgeMs`) themselves are excluded from the hash and are workflow/request-controlled, and only `WorkflowOwner` (not `WorkflowID`) participates in the key, workflows sharing an owner can unintentionally (or an attacker-controlled workflow could deliberately) read cached HTTP responses that were fetched in the context of a different, unrelated workflow under the same owner. This can leak data across workflow boundaries the system is supposed to keep isolated per the documented invariant.

### Likelihood Explanation
Likelihood is moderate: it requires an owner to run multiple workflows that issue HTTP actions to identical URLs/methods/bodies with caching enabled — a realistic scenario for shared upstream integrations reused across a customer's workflows. No special privilege beyond normal workflow-owner capability usage is needed; it is entirely reachable from unprivileged workflow/DON-originated outbound HTTP action requests processed by the gateway handler.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) in the cache key computed by `OutboundHTTPRequest.Hash()`, matching the documented "cache key generated from workflow ID and request hash" behavior, or otherwise partition the `responseCache` map by workflow ID before hashing the remaining request fields. Update/verify the unit test at `response_cache_test.go:139-149` accordingly, since it currently locks in the vulnerable behavior as expected behavior.

### Proof of Concept
1. Workflow A (owner `O`) issues an `OutboundHTTPRequest{Method:"GET", URL:"https://api.example.com/data", CacheSettings:{Store:true, MaxAgeMs:600000}, WorkflowOwner:"O", WorkflowID:"wf-A"}`; gateway fetches and caches the response under `Hash()` (which does not include `WorkflowID`).
2. Workflow B (same owner `O`, different `WorkflowID:"wf-B"`) issues an identical request (same method/URL/headers/body) with caching enabled.
3. Per `TestRequestHash` ("having different workflowID results in same Hash"), `req.Hash()` for A and B are identical, so `responseCache.Fetch` returns A's cached response to workflow B without making a new external call — demonstrated directly by the existing test at `response_cache_test.go:139-149`.

	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
