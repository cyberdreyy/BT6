### Title
User enumeration via distinguishable authentication error messages in `SessionsController.Create` - ([File: core/web/sessions_controller.go])

### Summary
`SessionsController.Create` passes the raw error from `AuthenticationProvider().CreateSession` straight into `jsonAPIError`, which serializes `err.Error()` into the JSON response body. Because the local-auth ORM's `CreateSession` returns a different, distinguishable error for a nonexistent email (`sql.ErrNoRows` from `FindUser`) versus a wrong password (`"Invalid password"`), an unauthenticated attacker can enumerate valid emails by diffing response bodies.

### Finding Description
In `core/web/sessions_controller.go` `Create`, the login flow calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and, on error, does: [1](#0-0) 
`jsonAPIError` writes `err.Error()` verbatim into the JSON body: [2](#0-1) 

The default (local) authentication provider's `CreateSession` (`core/sessions/localauth/orm.go`) first calls `FindUser`, and if that lookup fails, it returns the raw underlying error unmodified: [3](#0-2) 
`FindUser`/`findUser` runs a `SELECT ... WHERE lower(email) = lower($1)` and returns whatever `sqlx.GetContext` yields, which for a nonexistent email is `sql.ErrNoRows` (message: `"sql: no rows in result set"`): [4](#0-3) 

In contrast, when the email exists but the password is wrong, the ORM explicitly returns a different, custom error: [5](#0-4) 

So a POST to `/sessions` with a nonexistent email yields a JSON body containing `"sql: no rows in result set"`, while a POST with a valid email and wrong password yields `"Invalid password"`. These two paths are trivially distinguishable by an unauthenticated client, enabling user enumeration for credential-stuffing campaigns. Neither the auth middleware (this route is intentionally unauthenticated, being the login endpoint) nor any presenter/redaction logic sanitizes this difference before it reaches the HTTP response.

### Impact Explanation
This is an information-disclosure bug leading to user enumeration: an attacker can determine which email addresses have registered node accounts by observing the distinct error text/messages returned by `/sessions`, without needing any credentials. This aids targeted credential-stuffing and brute-force attacks against the node's admin/API login, which is a real, exploitable authentication-adjacent weakness (though it does not by itself grant access, key disclosure, or fund movement).

### Likelihood Explanation
No preconditions are required — the attacker only needs unauthenticated HTTP access to the node's `/sessions` endpoint. The distinguishing behavior is deterministic and repeatable for every request (not a race or timing side-channel), making this a highly reliable and trivially automatable enumeration primitive.

### Recommendation
Return a single generic, constant error/message for all authentication failures in `CreateSession` (email not found, wrong password, MFA errors), and ensure `SessionsController.Create` never forwards raw provider errors verbatim to the client — e.g., log the specific error server-side and return a fixed `"invalid credentials"` message with `http.StatusUnauthorized` for every failure branch. Also normalize timing where feasible (already partially addressed via constant-time email compare) to avoid a timing side channel alongside message differences.

### Proof of Concept
Go handler-level integration test plan (using `httptest` and the existing test router `cltest` helpers used elsewhere, e.g. `core/web/sessions_controller_test.go` patterns):
1. Seed a user via `cltest.MustRandomUser` / `orm.CreateUser`.
2. `POST /sessions` with `{"email": "<existing>", "password": "wrong"}` — capture status code and body.
3. `POST /sessions` with `{"email": "nonexistent@example.com", "password": "wrong"}` — capture status code and body.
4. Assert both return `http.StatusUnauthorized`, but note that body 2 contains `"sql: no rows in result set"` while body 1 contains `"Invalid password"` — demonstrating the invariant ("no information disclosure via errors") is violated.
5. After the fix, assert both bodies are byte-identical (e.g., both `{"errors":[{"detail":"invalid credentials"}]}`).

```go
// jsonAPIError adds an error to the gin context and sets
// the JSON value of errors.
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```
