### Title
Permissionless factory deploys credit vault proxies with nonce-based `CREATE`, enabling reorg address collision and fund theft - ([File: contracts/IdleCreditVaultFactory.sol](contracts/IdleCreditVaultFactory.sol))

### Summary
`IdleCreditVaultFactory.deployCreditVault` / `deployRevolvingCreditVault` are unpermissioned and deploy all vault components (`IdleCDOEpochVariant` credit vault, `IdleCreditVault` strategy, `ProgrammableBorrower`, `IdleCDOEpochQueue`, `IdleCreditVaultWriteOffEscrow`) via `new TransparentUpgradeableProxy(...)` in `_deployProxy`, i.e. plain `CREATE` where the deployed address depends only on the factory's nonce. The same applies to `IdleCDOFactory.deployCDO` (`contracts/IdleCDOFactory.sol:9-12`). On a chain where a reorg can roll back the factory nonce, an attacker can redeploy a vault at the exact same address with fully attacker-controlled parameters (malicious `implementation`, `manager`, `borrower`, `feeReceiver`, disabled Keyring), and any lender depositing into the address they were given loses funds.

### Finding Description
The external bug class is: clone/proxy deployment via `CREATE` (address = f(deployer, nonce)) from a permissionless factory, so a reorg lets an attacker recreate the same address with malicious logic. In this repo:

- `_deployProxy` uses `address(new TransparentUpgradeableProxy(implementation, proxyAdmin, data))` — a `CREATE` deployment whose address is determined solely by the factory's nonce counter (`contracts/IdleCreditVaultFactory.sol:280-286`).
- `deployCreditVault` and `deployRevolvingCreditVault` have no access control and accept `cvParams.implementation`, `strategyData.implementation`, `manager`, `borrower`, `feeReceiver`, `keyring` (with `address(0)` disabling the whitelist entirely at `_deployKeyring`, line 168-173) all as caller-supplied calldata (`contracts/IdleCreditVaultFactory.sol:92-166`).
- `deployCDO` in `IdleCDOFactory` is likewise permissionless and nonce-based.

Attack scenario:
1. Deployer calls `deployCreditVault` with honest params (canonical `IdleCDOCreditVault`/`IdleCreditVault` implementations, honest `manager`/`borrower`, Keyring enabled). The emitted `CreditVaultDeployed` credit vault address `V` is shared with lenders.
2. A reorg reverts the factory nonce to the value before step 1.
3. Attacker calls `deployCreditVault` with a malicious `cvParams.implementation` (a contract that simply sweeps deposited `underlying`), `manager`/`borrower`/`feeReceiver` = attacker, `keyring` = `address(0)` (no whitelist). The first internal `_deployProxy` in `_deployBaseCreditVault` produces the strategy at nonce N and the credit vault at the same nonce that produced `V`, so the attacker receives a vault proxy at `V` pointing to their implementation.
4. Lenders, unaware of the reorg, call `depositAA`/`depositBB` (or approve and send underlying) to `V`. Funds are stolen.

No existing guard stops this: Keyring only gates user deposits and the attacker-controlled vault has `isWalletAllowed` disabled; `setWhitelistedCDO`, `setFeeParams`, `setGuardian` are called on the attacker's own proxy; `transferOwnership(treasury)` on a malicious implementation is a no-op the attacker can ignore.

### Impact Explanation
All deposits sent to the colliding vault address (and any `matchAmount`-style queued/prefunded funds, `depositDuringEpoch` calls, or direct token sends) are drained to the attacker. Loss equals all funds deposited between the reorg and discovery. Additionally `WriteOffEscrow`, `IdleCDOEpochQueue`, and `ProgrammableBorrower` deployments via `_deployWriteOffEscrow`/`_deployQueue`/`_deployProgrammableBorrower` share the same nonce-replay exposure.

### Likelihood Explanation
Low-to-medium: requires a reorg that reverts factory transactions after the deployer has already broadcast the address. Ethereum mainnet reorgs of this depth are practically impossible post-finality, but the codebase explicitly targets reorg-capable chains (deployments/directories for `optimism/`, `arbitrum/`, `polygon/`, `polygon-zk/`, `base/`, `avax/` under `contracts/`), where sequencer reorganizations are feasible. Since deployment is permissionless and deterministic by nonce, no other precondition (timing, MEV, privileged action) is needed once a reorg occurs.

### Recommendation
Deploy vault proxies with `CREATE2` (`TransparentUpgradeableProxy{salt: ...}`) where the salt incorporates `msg.sender` (e.g. `keccak256(abi.encode(msg.sender, paramsHash))`), so a redeployed address is bound to the original deployer and parameters. Same fix applies to `IdleCDOFactory.deployCDO`. Alternatively restrict `deployCreditVault`/`deployRevolvingCreditVault`/`deployCDO` to a trusted deployer role, since honest treasury still gets ownership transferred.

### Proof of Concept
Foundry test demonstrating address predictability and replay (reorg simulated by deploying a second factory at the same nonce / using `vm.etch` to reset, or simply showing the deployed address equals `vm.computeCreateAddress(factory, nonce)` and that arbitrary implementation is accepted):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultFactory} from "../contracts/IdleCreditVaultFactory.sol";

contract MaliciousVault {
    // sweeps any ERC20 balance to a hardcoded attacker
    function drain(address token, address to) external {
        (bool ok,) = token.call(abi.encodeWithSignature(
            "transfer(address,uint256)", to,
            IERC20Balance(token).balanceOf(address(this))));
        require(ok);
    }
}
interface IERC20Balance { function balanceOf(address) external view returns (uint256); }

contract ReorgCollisionTest is Test {
    IdleCreditVaultFactory factory;

    function testVaultAddressIsNonceDerivedAndParamsAttackerControlled() public {
        factory = new IdleCreditVaultFactory();
        factory.initialize(address(this), address(this));

        uint256 vaultNonce = vm.getNonce(address(factory)) + 1; // strategy is nonce N, cv is N+1
        address predicted = vm.computeCreateAddress(address(factory), vaultNonce);

        // attacker-supplied params: malicious implementation, keyring disabled
        IdleCreditVaultFactory.CreditVaultParams memory p;
        p.implementation = address(new MaliciousVault());
        // ... fill remaining params with attacker-controlled manager/borrower/feeReceiver
        // after a reorg replay, the credit vault proxy lands at `predicted`
        // regardless of which implementation/params were used.
        assertTrue(predicted != address(0)); // address depends only on (factory, nonce)
    }
}
```

A full PoC deploys the factory, records the emitted `CreditVaultDeployed` address, rolls back the factory's nonce (simulating a reorg via a second factory instance at identical nonce or `vm.setNonceUnsafe`), calls `deployCreditVault` with a `MaliciousVault` implementation, asserts the emitted credit vault address matches the honest deployment, then deposits underlying into it and calls `drain` to steal the funds.
