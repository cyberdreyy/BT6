### Title
Path traversal via file-type variable `Key` in cleanup file deletion - (File: `shells/abstract.go`)

### Summary
`AbstractShell.writeCleanupScript` builds the cleanup command for `File: true` variables using the raw, attacker-controlled variable `Key` as the filename component passed to `w.TmpFile(variable.Key)`, with no sanitization of path-traversal sequences. Because `TmpFile` implementations (bash/PowerShell `ShellWriter`) join this name onto the job's temporary directory using plain path-join semantics (which normalize `..` segments rather than rejecting them), a `Key` containing `../../` sequences can cause the resulting `RmFile` command to reference a path outside the job's tmp/build directory.

### Finding Description
`writeCleanupScript` in `shells/abstract.go` iterates `info.Build.GetAllVariables()` and, for every variable marked `File: true`, calls `w.RmFile(w.TmpFile(variable.Key))` [1](#0-0)  — this is the analogous prepare-stage pattern shown for fixed filenames (`gitlabEnvFileName`, `masking.db`); the cleanup-stage code follows the same `RmFile(TmpFile(...))` call convention but keys the filename off the variable's `Key` field rather than a constant.

The `TmpFile` implementations for bash and PowerShell (`shells/bash.go`, `shells/powershell.go`) construct the temp path by joining the supplied name onto the shell's configured temporary directory. Standard path-join/clean semantics (Go's `path.Join`/`filepath.Join`) collapse `..` segments arithmetically instead of rejecting them, so a name like `../../etc/passwd` combined with a tmp dir such as `/builds/tmp` normalizes to a path outside that directory (e.g. `/etc/passwd`, depending on the tmp dir depth). Because the `Key` is fully attacker-supplied (a job/pipeline author can define an arbitrary variable name in `.gitlab-ci.yml` or via pipeline/trigger variable input) and is used unsanitized as a path component in a file-deletion command, an unprivileged job can potentially cause the generated cleanup script to run `rm`/`Remove-Item` against a path outside the intended tmp/build root.

Whether this is actually exploitable end-to-end depends on two additional factors that could not be fully confirmed from the available index:
1. Whether GitLab (Rails) enforces a strict variable-key format (e.g., `^[A-Za-z_][A-Za-z0-9_]*$`) before the variable ever reaches the Runner. If enforced upstream for all variable-definition paths (project/group CI variables, `.gitlab-ci.yml` `variables:`, trigger/pipeline API variables), traversal characters like `/` or `..` would never reach Runner's `GetAllVariables()`, closing this path.
2. Whether `TmpFile`/`Absolute` in `shells/bash.go` and `shells/powershell.go` perform any sanitization or containment check on the name before joining (e.g., `filepath.Base`, rejection of `..`, or a "must remain under tmp dir" assertion) — I was not able to retrieve the full body of these functions to confirm one way or the other.

### Impact Explanation
If reachable, the scoped impact is deletion of an arbitrary file outside the job's tmp/build/cache root during the cleanup stage, executed with the privileges of the job's shell process (host user for shell executor, container user for container-based executors). This would violate the invariant that file operations derived from variables must stay confined to the job tmp directory.

### Likelihood Explanation
Feasibility hinges entirely on the two open questions above. If GitLab enforces variable-key format validation server-side for every variable-definition surface, the attack is not reachable and this reduces to defense-in-depth gap only. If `TmpFile` internally sanitizes/rejects traversal in the name argument, it is also not reachable. Without being able to confirm either safeguard is present or absent from the indexed code, likelihood cannot be conclusively established.

### Recommendation
Regardless of upstream enforcement, `TmpFile` (and any function deriving file paths from variable `Key`) should defensively sanitize the input — e.g., apply `filepath.Base()` or a strict allow-list regex to strip path separators and `..` sequences — before joining to the temp directory, and/or verify (via `filepath.Rel`) that the resulting path remains within the tmp directory before emitting `RmFile`/`TmpFile` commands. This closes the gap independent of whatever validation GitLab Rails performs.

### Proof of Concept
```go
// shells/bash_test.go (illustrative)
func TestTmpFile_RejectsPathTraversal(t *testing.T) {
    w := &BashWriter{TemporaryPath: "/builds/tmp"}
    got := w.TmpFile("../../etc/passwd")
    // Expect the resulting path to remain rooted under the temp dir.
    rel, err := filepath.Rel("/builds/tmp", got)
    assert.NoError(t, err)
    assert.False(t, strings.HasPrefix(rel, ".."), "TmpFile escaped tmp dir: %s", got)
}
```
Additionally, an integration-level PoC job would define a `File: true` variable with `Key: "../../../../tmp/canary"` (or similar) and assert that the generated `writeCleanupScript` output's `rm`/`Remove-Item` command line does not reference any path outside the job's configured tmp directory.

**Caveat:** I could not retrieve the full source of `TmpFile` in `shells/bash.go` / `shells/powershell.go` or confirm/deny server-side variable-key validation from the indexed content, so this finding should be treated as a plausible but not fully verified path — a Devin session with full repository/filesystem access should inspect `shells/bash.go` and `shells/powershell.go` `TmpFile`/`Absolute` implementations directly to confirm whether sanitization already exists before treating this as confirmed exploitable.
