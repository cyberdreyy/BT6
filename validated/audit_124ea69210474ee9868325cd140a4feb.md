### Title
Blocked/blacklisted `msg.sender` permanently locks a user's matured withdraw claim in `IdleCreditVault` — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Withdraw and instant-withdraw claims in `IdleCreditVault` can only pay out to the exact address that created the request (`msg.sender` propagated through `IdleCDOEpochVariant`). The receipt strategy tokens minted at request time are deliberately non-transferable (`_transfer` reverts unless the caller is the CDO), and no claim function accepts an alternative receiver. If the underlying token (e.g. USDC/USDT, which `token` represents for these Clearpool-style credit vaults) blocks the requester's address after `requestWithdraw` but before `claimWithdrawRequest`, every claim path reverts inside `safeTransfer`, and the already-funded underlyings remain in the vault forever.

### Finding Description
The flow mirrors the reported SolverVault bug:

1. `IdleCDOEpochVariant._requestWithdraw` calls `creditVault.requestWithdraw(_underlyings, msg.sender, principal)`, binding the claim to `msg.sender` (`IdleCDOEpochVariant.sol:788`, `IdleCreditVault.sol:243-295`). The user receives `_amount` strategy tokens as a receipt.
2. After one epoch, `IdleCDOEpochVariant.claimWithdrawRequest()` calls `IdleCreditVault.claimWithdrawRequest(msg.sender)` (`IdleCDOEpochVariant.sol:967-971`), which reaches `_claimFundedWithdrawRequest` → `_transferFundedClaim(_user, amount)` → `underlyingToken.safeTransfer(_user, _amount)` (`IdleCreditVault.sol:343-349`, `IdleCreditVault.sol:897-907`).
3. Every other payout path has the same hardcoded recipient: `_claimLossAdjustedWithdrawRequest` (line 800), `_claimDefaultedWithdrawRequest`/`_claimPostDefaultWithdrawRequest` via `_transferDefaultRecovery` (lines 766, 783, 912-917), and `claimInstantWithdrawRequest` (line 392).
4. Unlike the original SolverVault report, the receipt cannot even be sold or moved to a clean address: `_transfer` reverts with `NotAllowed` unless `msg.sender == idleCDO` (`IdleCreditVault.sol:939-942`), and `setCanTransfer(true)` is permanently disabled (`IdleCreditVault.sol:948-951`).

If USDC/USDT blocks `_user` between request and claim (e.g., address added to the Circle/Tether blocklist for an unrelated reason), `safeTransfer` reverts and, because the revert is atomic, the user's receipt, `withdrawsRequests[_user]`, `apr0Users[_user]`, and `lastWithdrawRequest[_user]` remain set but unclaimable. There is no user-facing escape: the only alternative withdrawal entry point, `requestWithdraw` for a new request, does not move the stuck funds, and after `defaultRecoveryFinalized` the stuck state additionally blocks new requests via the `_hasWithdrawRequest` check (`IdleCreditVault.sol:249-251`).

### Impact Explanation
Permanent freezing of the affected user's funds. Once a request matures, the underlyings are already sitting in `IdleCreditVault` reserved for that claim (`collectWithdrawFunds` pulled them from the CDO/borrower), yet they can only ever be sent to the blocked address. The user loses the full claim amount (principal + interest, or the loss/default-haircut amount) with no self-service recovery. The only remediation is the owner's `transferToken` rescue (`IdleCreditVault.sol:963-965`), a privileged escape hatch outside the user's control — analogous to the audited report's "no clear mechanism to release them to the rightful owner." The strategy tokens themselves are already burned/`_burn(_user, ...)` is part of the same reverting transaction, so the user can't even re-route via the receipt.

### Likelihood Explanation
Low-to-moderate. It requires the underlying to be a blocklisting token (USDC/USDT — the standard pool currency for these vaults) and the user's address to be blocked in the window between `requestWithdraw` and `claimWithdrawRequest` (or between instant request and `claimInstantWithdrawRequest`, which is a shorter window but still nonzero since `getInstantWithdrawFunds` funding happens at epoch start). The probability of any individual address being sanctioned is small, but the consequence is total loss of that claim, and the Sherlock original was accepted at Medium severity. No attacker action is needed — this is an availability/design flaw, matching the original report's classification.

### Recommendation
Mirror the audited fix: let the receipt owner specify the payout address at claim time. Concretely:

- Add a `receiver` parameter to `IdleCDOEpochVariant.claimWithdrawRequest`/`claimInstantWithdrawRequest` and forward it to `IdleCreditVault.claimWithdrawRequest(_user, _receiver)` / `claimInstantWithdrawRequest(_user, _receiver)`.
- Keep `_user` as the claim owner for accounting/burns (`withdrawsRequests`, `apr0Users`, `instantWithdrawsRequests`, `lastWithdrawRequest`, `_burn(_user, ...)`), but send underlying to `_receiver` in `_transferFundedClaim`/`_transferDefaultRecovery`.
- Apply the same to `IdleCDOEpochQueue.claimWithdrawRequest`/`claimDepositRequest` if the queue variant ships, since they likewise hardcode `msg.sender` (`IdleCDOEpochQueue.sol:388`, `:409`).

### Proof of Concept
Foundry fork sketch (mainnet fork so `token` is real USDC with its blocklist):

```solidity
// Setup: deploy IdleCDOEpochVariant + IdleCreditVault with USDC underlying,
// user passes Keyring, deposits AA.

// 1. User requests withdraw during buffer period.
vm.prank(user);
uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

// 2. Epoch runs; stopEpoch funds the pending request.
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, apr, expectedFunds); // collectWithdrawFunds pulls USDC into vault

// 3. USDC blocklists `user` before they claim (fork cheat: prank the USDC
//    blocklister role or use vm.store on the blocklist mapping slot).
vm.prank(usdcBlocklistAdmin);
IUSDC(usdc).blacklist(user);

// 4. Claim reverts inside safeTransfer — forever.
vm.prank(user);
vm.expectRevert(); // "Blacklistable: account is blacklisted" or OZ revert
cdoEpoch.claimWithdrawRequest();

// 5. No escape: receipt transfer to a clean address is also blocked.
vm.prank(user);
vm.expectRevert(NotAllowed.selector);
IERC20(strategyToken).transfer(cleanAddr, receipt);

// 6. Even after un-blacklisting is impossible/or a default finalizes,
//    the stuck request blocks new requests (post-default path).
assertEq(usdc.balanceOf(user), preClaimBal); // funds remain in IdleCreditVault
```

The same sequence works for `claimInstantWithdrawRequest` (APR-drop path) and for `_transferDefaultRecovery` paths after `finalizeDefaultRecovery`, since all terminate in `safeTransfer(_user, ...)`.
