This confirms the analog: the Vault gateway's `AllowListBasedAuth.AuthorizeRequest` at [1](#0-0)  authorizes any incoming JSON-RPC request whose byte-exact digest matches an on-chain allowlist entry (`WorkflowRegistryOwnerAllowlistedRequest`), and this is exactly the "separate permission step, then separate action step" pattern from the report.

### Title
Front-Running of Vault Gateway Allowlisted Requests Enables Response Hijacking / DoS - ([File: core/capabilities/vault/allow_list_based_auth.go])

### Summary
The Vault capability's gateway-facing request flow mirrors the reported permit-front-running bug class: an owner first authorizes a specific request off-chain by getting its digest allowlisted on-chain (analogous to `permit()`), and then separately submits the actual JSON-RPC request to the internet-facing Gateway HTTP endpoint (analogous to `depositWithPermit2()`/`processWithPermit()`). Because the allowlist entry is public (on-chain) and the digest is derived deterministically from the request's method/params [1](#0-0) , any unprivileged actor watching the chain can reconstruct the exact byte-identical request and race it to the Gateway before the legitimate owner's client does.

### Finding Description
`allowListBasedAuth.AuthorizeRequest` computes `req.Digest()` and checks it against `workflowRegistrySyncer.GetAllowlistedRequests(ctx)`, which is populated from an on-chain contract (`WorkflowRegistryOwnerAllowlistedRequest`) [2](#0-1) . Once an owner's transaction allowlisting a request digest is broadcast/mined, that digest and its parameters are visible to anyone monitoring the chain (or even the gateway's own logs, since digests are logged: `allowedRequestsStrs` at line 84-87). The authorization is single-use, enforced by `RequestReplayGuard.CheckAndRecord`, which returns `ErrRequestAlreadySeen` for a second submission of the same digest [3](#0-2) . `authorizer.AuthorizeRequest` wires the allowlist authorization directly into this single-use replay guard [4](#0-3) .

The Gateway's public, unprivileged HTTP endpoint accepts and forwards any JSON-RPC request matching this scheme (`gateway.ProcessRequest` → `handler.HandleJSONRPCUserMessage` → `GatewayVaultRequestProcessor.ProcessRequest`) [5](#0-4) . Because the digest computation depends only on request content (method, id, params), an attacker who has observed the on-chain allowlist entry can reconstruct byte-identical `params`/`ID`/`method` and submit them to the Gateway first. The DON then processes this attacker-submitted request exactly as if it were the legitimate owner's, and the response (including any `SendResponse` correlation tied to the connection/callback that submitted the HTTP request) is delivered back to the attacker's HTTP connection rather than the legitimate owner's, per the request/response correlation pattern seen in `gateway.ProcessRequest`'s `callback.Wait(ctx)` [6](#0-5) . When the legitimate owner's client then submits the same request, it fails with "request was already authorized previously" (confirmed by system test comments explicitly describing this exact race condition as an accepted/tolerated outcome) [7](#0-6) .

This is the direct root-cause analog to the `permit()`/`permitTransferFrom()` front-running bug: a publicly-observable authorization step (on-chain allowlist tx ≈ `permit()` signature) is decoupled from the action step (Gateway HTTP submission ≈ `depositWithPermit2()`), and the single-use nature of the authorization (the replay guard ≈ nonce consumption) lets an unprivileged attacker consume it first.

### Impact Explanation
An unprivileged actor with no special access, simply monitoring on-chain allowlist transactions to the WorkflowRegistry contract (public data) or the gateway's own debug logs which print allowlisted digests, can:
1. Deny service to the legitimate owner's create/update/delete/list secrets request — a time-sensitive DoS, matching the report's concern about `repayWithPermit2` being "time sensitive."
2. Hijack the response of a request meant for another user/workflow (cross-user response confusion): the attacker's HTTP connection, not the legitimate owner's, receives the JSON-RPC success response for an action that was intended for and executed on behalf of the true owner.

The secret plaintext itself remains protected by TDH2 threshold encryption to the vault's public key, so this is not a full secret-disclosure bug, but it is a legitimate, unprivileged-actor-reachable request impersonation / cross-user response confusion / DoS vulnerability against the internet-facing Gateway.

### Likelihood Explanation
Medium. It requires the attacker to monitor either the on-chain allowlist transactions (public, permissionless to observe) or gateway node logs, and to win a race against the legitimate client's own submission. The window is non-trivial: the allowlist syncer polls every ~12s and the auth retries for up to ~30s (`allowListBasedAuthRetryCount=10`, `allowListBasedAuthRetryInterval=3s`) before rejecting, giving an attacker ample time to front-run [8](#0-7) . The existing system test already documents and "tolerates" this exact race outcome as expected behavior, indicating the maintainers are aware this race can and does occur under normal operation, not just adversarially [7](#0-6) .

### Recommendation
Bind the Gateway-side authorization/response delivery to a client-specific value not observable by third parties (e.g., require the actual request to be signed by the same key that produced the allowlist digest, and verify that signature at the Gateway/handler before forwarding to the DON, rather than trusting digest-equality alone). Additionally, ensure that the response callback/session correlation cannot be satisfied by any submitter other than the one holding proof of the original owner's authorization — e.g., require an owner-signed nonce or client secret bound to the HTTP session distinct from the publicly-visible on-chain digest, similar to adding a `didPrepay`-style check recommended in the original report.

### Proof of Concept
1. Owner submits an on-chain transaction to the WorkflowRegistry contract allowlisting a specific request digest (computed from method + params) for their vault secret creation.
2. An unprivileged attacker monitors the mempool/chain (or Gateway debug logs which print `allowedRequestsStrs` including digests and raw allowlisted entries) and reconstructs the exact `jsonrpc.Request` (method, ID, params) that hashes to that digest.
3. Attacker submits this byte-identical request to the Gateway's public HTTP endpoint before the legitimate owner's own client does.
4. `allowListBasedAuth.AuthorizeRequest` succeeds (digest matches), `RequestReplayGuard.CheckAndRecord` records it as consumed, and the DON processes/responds to the attacker's HTTP connection.
5. When the legitimate owner's client subsequently submits the same request, `AuthorizeRequest`/`CheckAndRecord` returns `ErrRequestAlreadySeen` ("request was already authorized previously"), denying the legitimate request and returning the actual response to the attacker instead [3](#0-2) .

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}

func (r *allowListBasedAuth) fetchAllowlistedItem(allowListedRequests []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, digest [32]byte) *workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest {
	for _, item := range allowListedRequests {
		if item.RequestDigest == digest {
			return &item
		}
	}
	return nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
	if req.Method == vaulttypes.MethodPublicKeyGet {
		// Public key requests don't require authorization,
		// Let's process this request right away.
		// Note we cache this value quite aggressively so don't need to worry about DoS.
		publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
		if cachedPublicKey == nil {
			// Not found in cache. Fetch from nodes.
			ar, err := h.newActiveRequest(req, callback)
			if err != nil {
				h.lggr.Errorw("failed to create new activeRequest", "error", err)
				return err
			}
			return h.handlePublicKeyGet(ctx, ar)
		}
		h.lggr.Debugw("returning cached public key response")
		return h.handlePublicKeyGetSynchronously(ctx, req, publicKeyResponseBytes, callback)
	}

	if !vaulttypes.IsGatewaySecretsMethod(req.Method) {
		return h.sendImmediateUserResponse(ctx, req, callback, api.UnsupportedMethodError, errors.New("this method is unsupported: "+req.Method))
	}

	_, cachedPublicKey := h.getCachedPublicKey()
	authorized, err := h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)
	if err != nil {
		if vaultcap.IsInvalidVaultParamsError(err) {
			return h.sendImmediateUserResponse(ctx, req, callback, api.InvalidParamsError, err)
		}
		h.lggr.Errorw("request not authorized", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "error", err)
		return errors.New("request not authorized: " + err.Error())
	}
	authorizedOwner := authorized.AuthResult.AuthorizedOwner()

	h.lggr.Debugw("handling authorized vault request", "method", req.Method, "requestID", req.ID, "authorizedOwner", authorizedOwner)
	ar, activeRequestErr := h.newActiveRequest(req, callback)
	if activeRequestErr != nil {
		return activeRequestErr
	}
