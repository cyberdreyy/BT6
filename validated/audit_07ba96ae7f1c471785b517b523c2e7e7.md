### Title
Stale-epoch instant-withdraw receipts escape the default-recovery haircut because the scope check is keyed only to `defaultRecoveryEpoch` - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the AWS-LC CRL partitioned-scope check (a revocation entry outside the checked distribution-point partition bypasses the check), `IdleCreditVault` scopes default-loss accounting to *one* epoch partition — `instantWithdrawClaimsByEpoch[epochNumber]` at finalization and `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` at claim. An unfunded instant receipt recorded under an earlier epoch is invisible to that partition, so it bypasses the `defaultRecoveryPrice` haircut and is paid at par via `_transferFundedClaim`.

### Finding Description
When the borrower defaults, `finalizeDefaultRecovery` computes the claim basis with `defaultPendingClaimBasis()`, which adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch partition — when `pendingInstantWithdraws != 0` [1](#0-0) . `defaultRecoveryEpoch` is then set to that same `epochNumber` [2](#0-1) .

Instant receipts are, however, persisted per request epoch: `requestInstantWithdraw` writes `instantWithdrawsRequestsByEpoch[user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` [3](#0-2) , and the aggregate `instantWithdrawsRequests[user]` is only cleared on a successful claim. Since `claimInstantWithdrawRequest` burns and pays the *whole* aggregate, a partially funded instant receipt cannot be claimed and simply rolls forward across epochs [4](#0-3) .

If default is finalized in a later epoch, the stale receipt falls outside both partitions:
- it is excluded from `defaultPendingClaimBasis()` (keyed to `epochNumber` ≠ its request epoch), so it never contributes to `totalBasis` and is never haircut;
- `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, which is 0 for the stale receipt [5](#0-4) .

Execution then falls through to the funded-claim path, which burns the user's full `instantWithdrawsRequests` (including the unfunded stale receipt) and pays it at par through `_transferFundedClaim`, whose only guard is that the payout cannot touch `defaultRecoveryReserve` — it does not verify the receipt was ever funded [6](#0-5) .

### Impact Explanation
Any non-reserve underlying held by the strategy at claim time — prefunded instant amounts collected via `collectInstantWithdrawFunds`, dust, or other users' funded balances — can be drained at par by a holder of an unfunded pre-default instant receipt, while every correctly partitioned claim (normal withdraws, current-epoch instant receipts, active LPs) absorbs the `defaultRecoveryPrice` haircut. Loss = the stale receipt's par payout that should have been paid at `defaultRecoveryPrice` (or not at all, since it was never funded), directly diluting defaulted-epoch claimants.

### Likelihood Explanation
Requires (i) instant withdrawals enabled, (ii) an epoch to end with `pendingInstantWithdraws > 0` attributable to a receipt recorded in an earlier epoch (partial instant funding at `startEpoch`, or the queue/keeper failing to fully service it), and (iii) a subsequent borrower default finalized via `finalizeDefaultRecovery`. The attacker needs only to be the holder (or recipient via CDO-driven claim) of the stale receipt — an ordinary KYC-passing lender. No privileged misbehavior is needed.

### Recommendation
In `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest`, iterate (or track) all epochs with outstanding `instantWithdrawClaimsByEpoch` rather than only `epochNumber`/`defaultRecoveryEpoch`, or normalize stale per-epoch instant receipts into the default epoch during finalization. At minimum, the par-payout path in `claimInstantWithdrawRequest` should only release the portion of `instantWithdrawsRequests[user]` that was actually funded.

### Proof of Concept
Foundry fork sketch (modeled on `test/foundry/IdleCreditVault.t.sol` instant-withdraw setups):

```solidity
// 1. Epoch N: enable instant withdraws; user deposits, requests instant withdraw.
//    Borrower/keeper funds only part of it (collectInstantWithdrawFunds < amount),
//    so pendingInstantWithdraws > 0 and instantWithdrawClaimsByEpoch[N] > 0 persist.
// 2. Epoch N+1 ... N+k: epochs roll; stale receipt stays in instantWithdrawsRequests[user].
// 3. Borrower defaults in epoch M (> N); manager calls finalizeDefaultRecovery.
//    - defaultPendingClaimBasis() includes instantWithdrawClaimsByEpoch[M] only
//    - defaultRecoveryEpoch = M
// 4. Ensure strategy holds non-reserve underlying >= stale receipt amount
//    (e.g., prefunded instant cash for epoch-M claims beyond reserve).
// 5. cdoEpoch.claimInstantWithdrawRequest():
//    - _claimDefaultedInstantWithdrawRequest clears byEpoch[user][M] = 0
//    - funded path burns full instantWithdrawsRequests[user] (incl. epoch-N receipt)
//      and pays it at PAR via _transferFundedClaim.
// Assert: payout == staleAmount, while defaultRecoveryPrice < 1e18 proves it should
// have been haircut; defaulted claimants' reserve/basis is diluted accordingly.
```

The broken invariant is "one receipt, one haircut": the epoch-partitioned scope check misses receipts outside `defaultRecoveryEpoch`, exactly the partition-scope logic error class of the reference advisory.

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
