## Title
Stale confirmations from removed multisig members are still counted toward the execution threshold - (`multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` in the `multisig2` contract executes a pending request once the number of stored confirmations reaches `num_confirmations`, without verifying that every confirmation in the stored set still belongs to a *current* member. `delete_member()` only purges confirmations for requests that the removed member **authored**, not confirmations the removed member cast on requests **authored by other members**. This is the same completeness gap as the reported `CollectionShutdown::execute()` bug: an operation is finalized based on a snapshot/array that is not kept consistent with the current state of the underlying set (locked NFTs / live members), letting stale entries silently count toward the finalizing threshold.

### Finding Description
`confirm()` finalizes and executes a request purely by comparing the size of the `confirmations` set to `num_confirmations`: [1](#0-0) 

`delete_member()` is the only place that prunes confirmation data when membership changes, and it only removes confirmations for requests whose `member` field (the *author*) equals the member being deleted: [2](#0-1) 

If member `A` previously called `confirm()` on a request `R` authored by a different member `B`, that confirmation is stored under `R`'s id in `self.confirmations`, independent of who authored `R`. When `A` is later removed via `DeleteMember`, `delete_member()` only scans requests where `r.member == A` (i.e., requests `A` created) — it never scans `self.confirmations` for entries where `A` confirmed someone else's request. `A`'s confirmation on `R` therefore remains in the set, uncorrelated to `A`'s membership status.

The binding that should hold is:
```
confirmations counted toward threshold == confirmations from accounts that are currently live members
```
Because `delete_member()` doesn't enforce this, the equality is broken: a stale confirmation from a removed member is still counted as if it were a live member's confirmation.

### Impact Explanation
This lets a request execute with fewer live-member confirmations than `num_confirmations` actually requires, i.e., a multisig request can be executed below the intended threshold — a Critical-impact scenario per the custody-binding rules ("a multisig request executed below threshold"). Since `MultiSigRequestAction::Transfer`/`FunctionCall`/`AddKey` are all reachable actions, this can move NEAR out of the multisig account with fewer authorizations than configured, directly undermining the K-of-N security guarantee the contract advertises.

### Likelihood Explanation
This does not require compromising a live key or any out-of-scope privilege beyond being (or having been) a legitimate multisig member — a realistic operational event (offboarding an employee, rotating a compromised key) that the multisig is specifically designed to survive. A member who anticipates their own removal (or colludes with a soon-to-be-removed member) can pre-confirm a malicious request; after removal, only marginally fewer *live* confirmations are needed to push it through. No admin/foundation override, no redeployment, and no violation of any documented initialization is required — this is a straightforward path through `add_request` → `confirm` → `DeleteMember` (executed via a separate, legitimately-confirmed request) → `confirm` again.

### Recommendation
When counting confirmations in `confirm()` (and when computing `get_confirmations`), filter the stored confirmation set to only those entries that are still present in `self.members` before comparing against `num_confirmations`. Additionally, `delete_member()` should scan `self.confirmations` for all requests (not just ones authored by the removed member) and remove any entry belonging to the removed member, so stale confirmations can never be counted after membership changes.

### Proof of Concept
1. Multisig deployed with `members = [A, B, C, D]`, `num_confirmations = 2`.
2. `B` calls `add_request(R)` where `R` is `Transfer { amount }` to an attacker-controlled account, authored by `B` (`r.member == B`).
3. `A` calls `confirm(R)`; `confirmations[R] = {A}` (set len 1, `1 < 2`, no execution yet).
4. Through normal governance, the multisig executes a separate, properly-confirmed `DeleteMember { member: A }` request (e.g., because `A`'s device/key is thought compromised). `delete_member()` only removes requests where `r.member == A`; since `R.member == B`, `R` and its confirmations (`{A}`) are untouched. `A` is removed from `self.members`.
5. `C` (a live member) calls `confirm(R)`. `confirmations[R].len() + 1 == 2 >= num_confirmations (2)` → `execute_request(R)` runs, transferring funds, even though only one truly live member (`C`) ever authorized it — the configured 2-of-N threshold was not actually met by live members.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
