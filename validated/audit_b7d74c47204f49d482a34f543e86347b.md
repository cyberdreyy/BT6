### Title
Local cache archive path is keyed only by cache key, not by project/job, allowing cross-project archive-file collisions on shared runners - ([File: functions/concrete/run/stages/cache_extract.go])

### Summary
`CacheExtract.extract` computes the local on-disk cache archive path solely from `e.CacheDir` and the (attacker-controlled) cache key, with no per-project or per-job component and no locking. Two different jobs (from different projects) sharing the same runner host and the same cache key will resolve to the identical local `cache.zip` path, so concurrent cache-extractor/cache-archiver invocations can interleave on that shared file even though the remote cache storage itself is properly scoped per-project.

### Finding Description
`CacheExtract.extract` calls `s.archivePath(e, src.Key)` which delegates to the shared helper: [1](#0-0) [2](#0-1) 

`cacheArchivePath` builds the file path as `filepath.Join(e.CacheDir, key, "cache.zip")`. `e.CacheDir` is a single, runner-wide directory (configured once per runner, e.g. `/cache`), shared by all concurrent jobs the runner executes — it is not derived per-job or per-project. The only differentiator between jobs is `key`, which is either the user-supplied `cache:key` (expanded via job variables, fully attacker-controlled) or the default `${jobName}/${gitRef}` (also attacker-influenceable by naming a job/branch identically in another project).

By contrast, the *remote* cache object path IS correctly scoped per project via `cache.GetAdapter`, which joins `project/<projectId>` into the object path before the key: [3](#0-2) 

So while the remote object that gets uploaded/downloaded is isolated per project, the **local staging file** that `cache-extractor`/`cache-archiver` read/write to is not. `CacheExtract.extract` invokes `e.RunnerCommand(ctx, ..., "cache-extractor", "--file", archiveFile, ...)`, passing distinct, project-scoped download URLs but an identical local `--file` target if the key collides: [4](#0-3) 

Neither `CacheExtract.Run`/`extract` nor `CacheArchive.Run` implement any per-job subdirectory, unique temp-file naming, or file lock around this path before invoking the helper binary, so two concurrent jobs on the same runner host with a colliding key can race on the same `cache.zip`.

### Impact Explanation
If Job A (Project A) and Job B (Project B) run concurrently on the same runner and both resolve to the same `archiveFile` (e.g., because both set an identical `cache: key:` value, or share job-name/branch defaults), their `cache-extractor`/`cache-archiver` subprocesses write to and read from the same local path. Depending on timing, Job A's extractor could end up extracting content that was concurrently overwritten by Job B's download (or vice versa), producing a cross-project cache content leak/poisoning into the wrong build workspace — a violation of the invariant that a job must not access another project's workload.

### Likelihood Explanation
Requires: (1) both jobs scheduled on the same runner host concurrently (feasible with `concurrent > 1`, especially on shared runners serving multiple projects), and (2) an identical resolved cache key across the two projects, which an attacker fully controls via `.gitlab-ci.yml`'s `cache:key` field (a normal, unprivileged CI-config input). This is deterministic and easily reproducible by an attacker who controls (or colludes with) two different projects on a shared runner; it does not require any admin/privileged action.

### Recommendation
Scope the local cache archive path per project/job (e.g., include project ID and/or job token/ID as a path segment, mirroring what `cache.GetAdapter` already does for remote objects) rather than keying solely off the cache key, and/or write to a unique temp file per invocation before an atomic rename, so concurrent jobs never share the same on-disk path.

### Proof of Concept
Go unit test in `functions/concrete/run/stages` package:
```go
func TestCacheArchivePath_CrossProjectCollision(t *testing.T) {
    eA := &env.Env{WorkingDir: "/builds/projectA", CacheDir: "/cache"}
    eB := &env.Env{WorkingDir: "/builds/projectB", CacheDir: "/cache"}

    pathA := cacheArchivePath(eA, "shared-key")
    pathB := cacheArchivePath(eB, "shared-key")

    // Resolve to absolute paths to compare true on-disk targets.
    absA, _ := filepath.Abs(filepath.Join(eA.WorkingDir, pathA))
    absB, _ := filepath.Abs(filepath.Join(eB.WorkingDir, pathB))

    // BUG: two different projects with the same cache key collide on disk.
    assert.Equal(t, absA, absB, "expected collision demonstrating missing per-project isolation")
}
```

func cacheArchivePath(e *env.Env, key string) string {
	absPath := filepath.Join(e.CacheDir, key, "cache.zip")
	rel, err := filepath.Rel(e.WorkingDir, absPath)
	if err != nil {
		return absPath
	}
	return rel
}

	if config == nil {
		return nopAdapter{}
	}

	if key == "" {
		logrus.Warning("Empty cache key. Skipping adapter selection.")
		return nopAdapter{}
	}

	// generate object path
	// runners get their own namespace, unless they're shared, in which case the
	// namespace is empty.
	namespace := ""
	if !config.GetShared() {
		namespace = path.Join("runner", shortToken)
	}
	basePath := path.Join(config.GetPath(), namespace, "project", projectId)

	// When sharded (i.e. FF_HASH_CACHE_KEYS is enabled), insert the first two
	// hex characters of the key as an intermediate path component. This
	// distributes objects across 256 distinct S3 prefixes per project, avoiding
	// 503 Slow Down responses caused by all cache objects sharing the same
	// prefix and landing on the same partition.
	var fullPath string
	if sharded {
		if len(key) < 2 {
			logrus.WithError(fmt.Errorf("cache key too short to shard (length %d)", len(key))).Error("Error while generating cache bucket.")
			return nopAdapter{}
		}
		fullPath = path.Join(basePath, key[:2], key)
	} else {
		fullPath = path.Join(basePath, key)
	}
