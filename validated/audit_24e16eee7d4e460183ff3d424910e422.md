### Title
CORS wildcard origin allowlist bypass via missing dot-boundary check in `strings.HasSuffix` - (File: `core/services/gateway/network/httpserver.go`)

### Summary
`httpServer.isAllowedOrigin` validates wildcard entries like `*.remix.com` by stripping the `*.` prefix and calling `strings.HasSuffix(originHost, allowedHost)`, without verifying that the matched suffix is preceded by a literal dot (i.e., is a true subdomain boundary). This allows an attacker-registered domain such as `evilremix.com` to satisfy the suffix check for an allowed wildcard `*.remix.com`, causing the gateway to reflect the attacker's `Origin` value in `Access-Control-Allow-Origin`.

### Finding Description
In `core/services/gateway/network/httpserver.go`, `isAllowedOrigin` performs the wildcard match: [1](#0-0) 

`allowedHost` is derived from a config entry like `*.remix.com` by slicing off `*.`, yielding `remix.com`. The check `strings.HasSuffix(originHost, allowedHost)` only verifies that `originHost` ends with the literal string `remix.com` — it does not require a `.` immediately before that suffix. Consequently, an `Origin` header value with host `evilremix.com` (13 chars) ends with the 9-character suffix `remix.com` and satisfies `strings.HasSuffix("evilremix.com", "remix.com") == true`, even though `evilremix.com` is not a subdomain of `remix.com`.

This is reachable directly from `handleRequest`, which calls `isAllowedOrigin(origin)` with the raw `Origin` request header and, if it returns true, reflects the attacker-supplied origin verbatim into the `Access-Control-Allow-Origin` response header: [2](#0-1) 

Any unauthenticated network client can set an arbitrary `Origin` header on a cross-origin request (browsers set it automatically for cross-origin fetch/XHR, and it requires no privilege). Since scheme and port checks pass trivially (`https`/no explicit port) and the host suffix check is spoofable via domain registration (e.g. registering `evilremix.com`), the wildcard allowlist intended to scope trust to genuine subdomains of `remix.com` can be bypassed.

### Impact Explanation
This is a CORS allowlist/origin-validation bypass (matches the "allowlist bypass" impact class in scope). If the gateway ever relies on wildcard entries (`*.<domain>`) in `CORSAllowedOrigins`, an attacker who registers a domain that merely ends with the allowed suffix (no dot boundary, e.g. `evilremix.com`, `notarealsubdomain-remix.com` is not matched since dash differs, but a bare-concatenation domain like `evilremix.com` is) can have their page's cross-origin requests treated as coming from a trusted subdomain. Combined with any credentialed/cross-origin-readable response mode, this enables an attacker-controlled origin to read gateway response data intended only for trusted subdomains of the allowed domain — a cross-user/cross-origin response confusion. Note that the response headers set by this handler do not include `Access-Control-Allow-Credentials`, which limits (but does not eliminate, for non-credentialed reads or future header changes) the practical severity of stealing cookie-authenticated data; the core defect is nonetheless a real origin-allowlist validation bug in security-relevant code.

### Likelihood Explanation
Requires `CORSEnabled: true` and at least one wildcard entry (`*.<domain>`) configured in `CORSAllowedOrigins`. No credentials or privileges are needed by the attacker beyond registering a domain name that has the allowed domain as a literal string suffix and hosting a page there; the browser automatically sends the `Origin` header on cross-origin requests. This is fully attacker-controlled and repeatable.

### Recommendation
Fix the suffix comparison to require a dot boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // keep the leading dot, e.g. ".remix.com"
    if originHost == allowedHost[2:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
This ensures `originHost` must either equal the bare domain or end with `.remix.com` (with the dot), rejecting `evilremix.com` while still accepting `foo.remix.com`.

### Proof of Concept
Add a Go table test for `isAllowedOrigin` in the `network` package:
```go
func TestIsAllowedOrigin_WildcardSuffixBypass(t *testing.T) {
    s := &httpServer{
        config: &HTTPServerConfig{CORSAllowedOrigins: []string{"https://*.remix.com"}},
        lggr:   logger.Test(t),
    }
    cases := []struct{
        origin string
        want   bool
    }{
        {"https://foo.remix.com", true},   // true subdomain
        {"https://remix.com", false},      // bare domain not in list (only wildcard given)
        {"https://evilremix.com", false},  // should be rejected, currently matches due to bug
        {"https://evil.remix.com", true},
    }
    for _, c := range cases {
        got := s.isAllowedOrigin(c.origin)
        assert.Equal(t, c.want, got, "origin=%s", c.origin)
    }
}
```
Running this against the current implementation demonstrates `https://evilremix.com` incorrectly returns `true`, confirming the bypass.
