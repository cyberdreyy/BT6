Confirmed: `delete_member` in `multisig2/src/lib.rs` has exactly the same gap as `delete_key`'s `DeleteKey` handler in `multisig/src/lib.rs` — it only purges requests/confirmations where the **removed member was the original requester** (`r.member == member`), not confirmations the removed member cast on requests **created by other members**. This is the "confirmations counted versus live members" custody-binding break called out in the rules.

### Title
Stale confirmations from removed multisig members still count toward the approval threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
`confirm()` approves and executes a request purely by counting entries in the `confirmations` `HashSet`, without re-validating that each confirming key/member is still a current multisig member. `DeleteKey`/`DeleteMember` only scrub requests and confirmations for requests **signed (created) by** the removed key/member; they never scan other pending requests to strip confirmations previously cast by that key/member. A confirmation from an already-revoked signer therefore remains valid credit toward `num_confirmations` forever.

### Finding Description
In `multisig/src/lib.rs`, `confirm()` (`multisig/src/lib.rs:246-266`) executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations`, with no check that the accumulated public keys in `confirmations` are still access keys on the account. [1](#0-0) 

When a key is revoked via `MultiSigRequestAction::DeleteKey`, the cleanup logic only removes requests whose `signer_pk` (the key that *created* the request) matches the deleted key — it does not touch the `confirmations` set of any *other* pending request that the deleted key had previously confirmed: [2](#0-1) 

The identical pattern exists in `multisig2/src/lib.rs`'s `delete_member`, which filters outstanding requests by `r.member == member` (the creator) and purges only those, leaving stale confirmations by the removed member on requests created by others intact: [3](#0-2) [4](#0-3) 

The binding that should hold is:
```
count(confirmations for request R) == count(distinct members that are still current AND confirmed R)
```
After a `DeleteKey`/`DeleteMember` action executes, this equality is broken for any request R that the removed key/member confirmed but did not create: the confirmation is still counted even though the underlying member is gone.

### Impact Explanation
This allows a request to be executed with a smaller number of currently-authorized signers than `num_confirmations` mandates — a multisig request executed below the intended live-membership threshold, which is explicitly a Critical-class custody-binding break (funds moved/actions authorized without the required quorum of currently trusted members). Concretely: member A creates a legitimate-looking or later-weaponized request R; member B (whose key/access is later revoked, e.g. because it was compromised, an employee left, or is otherwise untrusted) confirms R while still a member; the multisig then removes B via `DeleteKey`/`DeleteMember`; R's confirmation set still contains B's stale approval; the remaining live members only need to supply `num_confirmations - (existing count)` further confirmations to trigger execution, meaning the transaction is signed off by fewer *currently valid* members than the threshold was designed to require. In the limiting case of `num_confirmations == N` (all members must agree), removing one member and having the remaining members confirm can still execute the request using the removed member's stale confirmation, effectively achieving unanimous execution with one fewer live signer than intended.

### Likelihood Explanation
Likelihood is moderate: it requires normal multisig lifecycle operations (member/key rotation via `DeleteKey`/`DeleteMember`) combined with a pending, not-yet-fully-confirmed request that the departing member had already confirmed — a routine and expected sequence of events (e.g., revoking a departing employee's or a suspected-compromised key while requests are in flight) rather than a contrived edge case. No special privilege beyond being (or having been) an ordinary multisig member is needed to create the stale confirmation; the flaw is purely in the cleanup/execution logic.

### Recommendation
When executing `DeleteKey` (`multisig/src/lib.rs`) / `DeleteMember` (`multisig2/src/lib.rs`), iterate over **all** pending requests' `confirmations` sets (not just requests created by the removed key/member) and remove the deleted key/member's entry from each. Alternatively, validate at `confirm()`-time (or immediately before executing) that every public key/member present in the request's `confirmations` set is still contained in the current key/member set, discarding stale ones before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig` with 3 keys (A, B, C) and `num_confirmations: 3`.
2. Key A calls `add_request` to create request `R` (e.g., a `Transfer`).
3. Key B calls `confirm(R)` — `confirmations = {A, B}` is not tracked here since add_request doesn't auto-confirm; assume A confirms via `add_request_and_confirm`, so `confirmations = {A}`, then B confirms: `confirmations = {A, B}` (2/3).
4. Separately, the multisig executes a `DeleteKey` request removing key B's access key (e.g., because B's device was lost). Per `multisig/src/lib.rs:198-216`, this only removes requests where `signer_pk == B`; `R` (signed by A) is untouched and its `confirmations` set still contains B.
5. Key C now calls `confirm(R)`. `confirmations.len() + 1 == 3 >= num_confirmations`, so `R` executes — approved with confirmations nominally from A, B, C, but B's access key no longer exists on the account at execution time. The threshold of 3 *live* confirmations was never actually met; only 2 currently valid keys (A and C) authorized it.

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
