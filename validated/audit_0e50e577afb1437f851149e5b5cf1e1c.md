### Title
Post-default instant-withdraw claims paid at par from funded underlyings, bypassing the recovery haircut — (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
CVE-2016-5598 is an unprivileged remote compromise of a *connector* component — an unauthenticated caller reaching sensitive backend state through a secondary entry path rather than the guarded front door. The on-chain analog lives in `IdleCreditVault.claimInstantWithdrawRequest`/`requestInstantWithdraw`: after a borrower default is finalized, the instant-withdraw path is only haircutted if `defaultInstantWithdrawsFinalized` is already set. Any receipt holder calling before (or when) that flag is unset falls through to `_transferFundedClaim`, which pays the full `instantWithdrawsRequests[_user]` at par whenever the contract holds non-reserve underlyings. Additionally, `requestInstantWithdraw` has none of the post-default gating that `requestWithdraw` enforces, so new instant receipts can be created post-default and claimed the same way.

### Finding Description
Two related paths:

1. `claimInstantWithdrawRequest` only invokes the haircutted recovery path when both flags are set:

```solidity
if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
  _claimDefaultedInstantWithdrawRequest(_user); // pays claimBasis * defaultRecoveryPrice
}
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount); // pays 1:1
```

`_claimDefaultedInstantWithdrawRequest` (lines ~842-856) correctly pays `claimBasis * defaultRecoveryPrice / 1e18` out of `defaultRecoveryReserve`. But when `defaultInstantWithdrawsFinalized` is false — e.g. instant claims are settled through a separate finalization step, or the defaulted-epoch instant bucket was emptied while aggregate `instantWithdrawsRequests[_user]` still carries basis recorded under a different epoch — the entire user aggregate is paid at par. `_transferFundedClaim` (lines ~897-907) only guards `balance - defaultRecoveryReserve >= amount`; any funded balance above the reserve is fair game at 100%.

2. `requestInstantWithdraw` (lines ~356-375) performs no post-default checks at all: it burns CDO-side strategy tokens, mints the receipt to the user, and increases `instantWithdrawsRequests`/`pendingInstantWithdraws`. Compare `requestWithdraw` (lines ~243-258), which under `defaultRecoveryFinalized` reverts if the user has open requests and routes the new receipt into the reserve-backed `postDefaultRequests` bucket. The instant path creates a par-claimable receipt out of the same defaulted pool, and also inflates `pendingInstantWithdraws` — a liability counter the honest manager/borrower uses for funding decisions.

### Impact Explanation
A receipt holder (any user who requested an instant withdraw, or who creates one post-default) receives underlying at 1:1 while other defaulted-epoch claimants are capped at `defaultRecoveryPrice`. This directly steals funded underlyings that honest accounting treats as belonging to pending-claim funding or residual pool liquidity — breaking the "one receipt, haircut-proportional payout" invariant and diluting recovery for everyone else. Because `pendingInstantWithdraws` is also manipulated upward, subsequent honest funding/accounting is skewed (integrity impact), and legitimate claimants can be left unable to withdraw their full reserve share (availability impact) — mirroring the CVE's combined C/I/A impact through a secondary unguarded connector path.

### Likelihood Explanation
Requires a finalized default with a non-zero funded balance above `defaultRecoveryReserve`, which occurs whenever the vault held previously funded underlyings or residual liquidity at default time — a realistic state, since `collectInstantWithdrawFunds`/`collectWithdrawFunds` accumulate underlying before claims drain it. The attacker is an ordinary KYC-passed lender who already holds (or cheaply acquires via a post-default `requestInstantWithdraw`) a receipt; no privileged role is involved. The ordering window (recovery finalized, instant-finalization flag unset) is attacker-observable on-chain.

### Recommendation
- In `claimInstantWithdrawRequest`, when `defaultRecoveryFinalized` is true but `defaultInstantWithdrawsFinalized` is false, either revert or route all remaining defaulted-epoch basis through the reserve haircut; never let `instantWithdrawsRequests[_user]` fall through to `_transferFundedClaim` while it contains defaulted-epoch basis.
- Mirror `requestWithdraw`'s post-default gating in `requestInstantWithdraw`: revert on open requests/instant receipts and record new receipts in a reserve-backed bucket rather than the par-claimable aggregate.
- Preferably, key instant claims per epoch (`instantWithdrawsRequestsByEpoch`) for payout, so defaulted-epoch basis can never be aggregated into a funded par claim regardless of flag ordering.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testPostDefaultInstantClaimPaysPar() external {
    address user = makeAddr("attacker");
    _depositWithUser(user, 10_000 * ONE_SCALE, true);

    // Epoch N: create instant withdraw request, get it funded by stopEpoch
    vm.prank(user);
    uint256 req = cdoEpoch.requestInstantWithdraw(...); // via CDO instant path
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Leave underlying funded but do NOT claim yet.

    // Epoch N+1: borrower defaults; manager finalizes default recovery.
    idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, 0);
    assertTrue(cdoEpoch.defaulted());
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();
    // defaultRecoveryFinalized == true, defaultInstantWithdrawsFinalized == false
    // and strategy still holds funded underlyings above defaultRecoveryReserve.

    uint256 balBefore = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimInstantWithdrawRequest(); // user-facing CDO claim
    // ASSERT BUG: user receives `req` at par instead of req * defaultRecoveryPrice
    assertGt(underlying.balanceOf(user) - balBefore, req * strategy.defaultRecoveryPrice() / 1e18);
}
```

Uncertainty I could not fully resolve within available iterations: the exact CDO-side sequencing that leaves `defaultInstantWithdrawsFinalized` unset while a funded balance exists (that flag is toggled in `IdleCDOEpochVariant` finalization, which I did not read line-by-line), and whether the instant-request surface is exposed directly on `IdleCDOEpochVariant` post-default. If finalization atomically sets both flags in all reachable states, the residual bug is the missing post-default gating in `requestInstantWithdraw`, which still lets new receipts inflate `pendingInstantWithdraws` and claim residual funded balance at par. Either variant warrants the same fix.
