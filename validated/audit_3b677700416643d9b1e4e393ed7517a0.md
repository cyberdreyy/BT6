### Title
Phantom ERC4626 vault yield is minted as real epoch interest via `totalInterestDueNow()` in programmable minted-interest mode — (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
The SSRF bug class — trusting a response from an attacker-influenced external endpoint — maps onto `ProgrammableBorrower`, where `IdleCDOEpochVariant._stopEpoch` treats `IProgrammableBorrower.totalInterestDueNow()` as authoritative epoch interest. That value is derived from `vault.convertToAssets()` on an external ERC4626 vault chosen only for matching `asset()`. Any unprivileged depositor of that vault can inflate `convertToAssets` with a direct underlying donation, producing phantom "vault interest". In `isInterestMinted` mode, `stopEpoch` mints strategy tokens equal to that phantom interest and inflates tranche NAV, letting an attacker who also holds tranches exit at an inflated price before the phantom yield unwinds.

### Finding Description
`_stopEpoch` resolves programmable interest through `_resolveStopEpochInterest`, which returns `IProgrammableBorrower(_borrower()).totalInterestDueNow()` (`contracts/IdleCDOEpochVariant.sol:1004`). That value comes from `_vaultNetInterest`, which computes `earnedAssets - principalAssets` where `earnedAssets` includes `_currentVaultAssets()` — a live `convertToAssets` on the external vault (`ProgrammableBorrower.sol:337-346`, `330-333`). For the common ERC4626 implementation where `totalAssets()` is the vault's raw token balance, a donation of `D` underlying raises `convertToAssets` for every shareholder, so the borrower's sleeve appears to have earned interest it never did.

On the success path, when `isInterestMinted` and not closing, the CDO calls `_strategy.mintStrategyTokens(_grossInterest)` (`IdleCDOEpochVariant.sol:430`) with `_amountToPullFromBorrower = 0` (`line 376`) — i.e., the interest is credited to NAV purely by minting shares, with zero cash backing ever pulled from the borrower. The only sanity check is the `maxApr` bound at `lines 377-380`, which is gated on `_interest > 1`; `_resolveStopEpochInterest` reverts for `_interest > 1` in programmable mode (`line 1003`), so the cap is unreachable and phantom interest is unbounded.

Attack sequence (buffer phase → running → stop):
1. Attacker deposits into the same ERC4626 vault the `ProgrammableBorrower` uses, then into the CDO as an AA tranche holder during the buffer phase.
2. Manager calls `startEpoch` (honest); borrower sleeve is deposited to the vault.
3. Before `epochEndDate`, attacker donates `D` underlying directly to the vault contract. `_currentVaultAssets` rises by ~`D * borrowerShares/totalShares`; `totalInterestDueNow` reports phantom interest `P`.
4. Manager calls `stopEpoch(0, 0)` (honest). `_strategy.mintStrategyTokens(P)` inflates `getContractValue` and all tranche prices by `P` with no cash ever received.
5. Attacker requests withdrawal and claims at the inflated price, receiving real underlying; simultaneously redeems his vault shares, recovering the donation minus the `P` fraction attributed to the borrower.
6. Next epoch, `epochStartVaultAssets` re-baselines at the deflated value; the `P` of minted strategy tokens is unbacked and the shortfall is eventually realized as a loss through the BB-first waterfall or as a default when `getFundsFromBorrower` fails.

`_skimDonatedAssets` (`IdleCDOEpochVariant.sol:355`) only protects tokens donated directly to the CDO, not donations into the external vault, and `setVault` (`ProgrammableBorrower.sol:158-169`) only validates `asset()` — a legitimate, owner-chosen vault with balance-based `totalAssets` is sufficient.

### Impact Explanation
Direct theft / insolvency: `P` underlying-equivalent of unbacked strategy tokens are minted and priced into tranche NAV. The attacker extracts roughly `P * (his tranche share)` in real underlying via a withdrawal request at the inflated price, while the pool retains vault shares worth only their pre-donation value. Residual loss is borne by remaining LPs (BB first). Loss magnitude is bounded only by the attacker's donation size and his share of vault/tranche ownership; with a tranche position larger than his vault share, net profit is positive up to the pool's total NAV.

### Likelihood Explanation
Requires `isInterestMinted` mode and an ERC4626 vault whose `convertToAssets` reflects raw balance donations (OpenZeppelin-default style). Both are realistic configurations — the Foundry suite itself exercises minted mode. Attacker needs only to be a user of the external vault and a KYC'd lender, both explicitly unprivileged. No privileged misbehavior is required; `startEpoch`/`stopEpoch` are called honestly. Capital cost is largely recovered via vault-share redemption, so the attack is cheap relative to the extractable amount.

### Recommendation
Bound programmable-borrower interest against a rate-derived ceiling on every stop, not only on the close path — e.g., apply the existing `maxApr` check (`IdleCDOEpochVariant.sol:377-380`) whenever `_mintInterest` is true, since `totalInterestDueNow` bypasses the `_interest > 1` gate. Additionally or alternatively, have `ProgrammableBorrower` track vault PnL against a share-quantity baseline (assets-per-share at epoch start) rather than absolute `convertToAssets`, or require the configured vault to use internal (donation-immune) asset accounting.

### Proof of Concept
Foundry fork/unit PoC sketch:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
// Setup mirrors test/foundry/ProgrammableBorrowerCreditVault.t.sol:
// cdoEpoch with isInterestMinted = true, programmableBorrower pointing at
// a balance-accounting ERC4626 vault V (asset = USDC). Vault chosen by owner —
// honest config; attacker is merely a user of V and a KYC'd AA lender.

function testPhantomVaultInterestMinted() external {
    // 1. Attacker deposits into V (vault user) and into AA tranche (buffer phase).
    uint256 poolDeposit = 100_000e6;
    uint256 attackerVaultDep = 100_000e6;
    deal(USDC, attacker, attackerVaultDep + poolDeposit + 1_000_000e6);
    vm.prank(attacker); V.deposit(attackerVaultDep, attacker);
    vm.prank(attacker); cdoEpoch.depositAA(poolDeposit);

    // 2. Honest start; borrower sleeve lands in V.
    vm.prank(manager); cdoEpoch.startEpoch();

    // 3. Attacker donates D straight to V, inflating convertToAssets.
    uint256 D = 50_000e6;
    vm.prank(attacker); IERC20(USDC).transfer(address(V), D);

    // Phantom interest visible to the pool.
    uint256 phantom = programmableBorrower.totalInterestDueNow();
    assertGt(phantom, 0);

    // 4. Honest stop mints strategy tokens for phantom interest (maxApr check
    //    unreachable since _interest > 1 reverts for programmable borrowers).
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 navBefore = cdoEpoch.getContractValue();
    vm.prank(manager); cdoEpoch.stopEpoch(0, 0);
    uint256 navAfter = cdoEpoch.getContractValue();
    assertGt(navAfter - navBefore, phantom - 10); // minted, no cash pulled

    // 5. Attacker redeems vault shares (recaptures donation share) and
    //    withdraws tranche position at inflated price, then next epoch NAV
    //    re-baselines -> pool is short ~attacker-share-weighted phantom amount.
}
```

Key assertion: `stopEpoch` succeeds, `mintStrategyTokens` mints `phantom` with `_amountToPullFromBorrower == 0`, and the inflated tranche price is claimable while the vault sleeve holds no corresponding realizable assets.

Uncertainty noted: the exploit is conditional on the configured vault's `totalAssets` counting raw donations (true for the default OZ ERC4626; false for internally-accounted vaults like MetaMorpho used in some fork tests). `setVault` only enforces `asset()` matching, so such a vault is a valid honest configuration.
