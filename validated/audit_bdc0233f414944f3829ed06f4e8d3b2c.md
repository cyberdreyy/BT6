### Title
Raw internal error messages (including DB errors) are leaked to unauthenticated clients via `jsonAPIError` - ([File: core/web/auth/helpers.go])

### Finding Description
`jsonAPIError` in `core/web/auth/helpers.go` falls back to `c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))` whenever the error passed in is not already a `*models.JSONAPIErrors`: [1](#0-0) 

This function is invoked directly by the `Authenticate` middleware in `core/web/auth/auth.go` for every error returned by an `authMethod`, using the *raw* error object, not a sanitized message: [2](#0-1) 

`AuthenticateByToken` only converts to the generic `auth.ErrorAuthFailed` for the specific cases of `sql.ErrNoRows` or `clsessions.ErrUserSessionExpired`. Any other error returned by `authr.FindUserByAPIToken(ctx, token.AccessKey)` (e.g. a database-layer error, timeout, or malformed-query error) is returned unmodified via `return err`, and likewise any error from `clsessions.AuthenticateUserByToken` is returned unmodified: [3](#0-2) 

Because `Authenticate` passes this error straight into `jsonAPIError` without any sanitation, and `jsonAPIError` serializes `err.Error()` directly into the JSON response body, any error string produced deeper in the stack (ORM/driver error text, wrapped context strings, etc.) is returned verbatim to an unauthenticated caller. The attacker only needs to supply an `X-API-KEY` value that causes `FindUserByAPIToken` to fail with something other than `sql.ErrNoRows`/`ErrUserSessionExpired` — for example a value that trips a query-layer error (oversized value, invalid encoding, driver-level constraint) — to have that error text echoed back in the 401 JSON payload.

No middleware, role check, or presenter sits between this error and the HTTP response — `RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole` all use the same unsanitized `jsonAPIError` helper as well.

### Impact Explanation
This maps to Chainlink's "information disclosure aiding further attacks" impact class: verbatim propagation of internal error strings (potentially including query fragments, column/table names, or other backend implementation details) to unauthenticated requesters. It does not directly grant secrets/keys/auth bypass, but it weakens the "secret confinement" invariant and can materially aid a follow-on attack (e.g., DB fingerprinting, error-based enumeration).

### Likelihood Explanation
Requires only unauthenticated network access to any endpoint protected by `Authenticate(..., AuthenticateByToken, ...)` and the ability to make `FindUserByAPIToken` fail with a non-`sql.ErrNoRows` error. This is feasible depending on the underlying store implementation (`core/sessions/localauth/orm.go`, not fully inspected here) — the actual reachability of a query-layer error (as opposed to a clean not-found) depends on how that ORM method builds/executes its query and whether the driver returns descriptive errors for malformed input. I could not fully confirm the exact driver-level error content because `core/sessions/localauth/orm.go`'s `FindUserByAPIToken` implementation was not retrieved before running out of tool calls, so the severity of what actually leaks (e.g., whether it's a generic "context deadline exceeded" versus something containing schema details) is not fully verified.

### Recommendation
In `jsonAPIError` (or in `Authenticate`), never serialize non-`JSONAPIErrors` errors via `err.Error()` for 5xx/db-originated failures — log the raw error server-side and return a generic message (e.g., "Internal Server Error" / "Authentication failed") to the client. Additionally, `AuthenticateByToken` and `AuthenticateExternalInitiator` should collapse all unexpected/internal errors (not just `sql.ErrNoRows`) into a generic error before returning, so `Authenticate` middleware can always respond with `auth.ErrorAuthFailed`-equivalent generic text.

### Proof of Concept
Go handler-level test plan:
1. Construct a fake `Authenticator` implementation whose `FindUserByAPIToken` returns a wrapped error such as `errors.New("pq: syntax error at or near \"$1\" in query SELECT secret FROM users WHERE access_key=...")` (simulating a non-`sql.ErrNoRows` DB failure).
2. Wire up `auth.Authenticate(fakeAuthr, auth.AuthenticateByToken)` as gin middleware in a test router, matching `core/web/auth/auth_test.go` patterns.
3. Send a request with `X-API-KEY`/`X-API-SECRET` headers set.
4. Assert: the response body (via `models.JSONAPIErrors`) does NOT contain the substrings `"pq:"`, `"SELECT"`, or other internal error fragments — only a generic message like `"Authentication failed"`.
5. Currently, this test would fail because `jsonAPIError` echoes `err.Error()` verbatim, proving the leak.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
