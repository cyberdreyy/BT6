### Title
Double-refund of `DeterministicStateInitAction.deposit` when a later action in the same receipt fails - ([File: runtime/runtime/src/deterministic_account_id.rs])

### Finding Description
`action_deterministic_state_init` performs its own inline deposit refund by pushing a `Receipt::new_balance_refund` directly into `result.new_receipts` for any unused portion of `action.deposit` [1](#0-0) . This is unique among action handlers: every other action (`CreateAccount`, `Transfer`, `FunctionCall`, `DeployContract`, etc.) relies exclusively on the single, centralized end-of-receipt refund mechanism, `refund_unspent_gas_and_deposits`, which computes `total_deposit` over *all* actions in the receipt and issues one refund receipt only if the whole receipt's `result.result` is `Err` [2](#0-1) .

Because `total_deposit` sums the *original* deposit of every action in the receipt unconditionally, it does not know that `DeterministicStateInitAction`'s deposit was already partially refunded inline. Sequence of events for a receipt with actions `[DeterministicStateInit, Transfer-to-nonexistent]`:

1. `action_deterministic_state_init` runs first, succeeds, consumes part of `action.deposit` for storage staking, and pushes a refund receipt for the unused remainder into `result.new_receipts`.
2. The second action (`Transfer` to a receiver that fails, e.g. insufficient balance/nonexistent account) fails, setting the overall `result.result = Err`.
3. At the end of receipt processing, `state_update` for the *whole* receipt is rolled back based on `result.result` being `Err` [3](#0-2) , which undoes the account/storage changes from step 1 (e.g., the storage-stake balance increase), but does **not** remove the refund receipt already appended to `result.new_receipts` in memory.
4. `refund_unspent_gas_and_deposits` then computes `deposit_refund = total_deposit` (since the receipt failed), which includes the *full original* `DeterministicStateInitAction.deposit` again, and issues a second refund for it [4](#0-3) .
5. The final receipt-generation loop unconditionally forwards every entry in `result.new_receipts` as an outgoing receipt regardless of `result.result` [5](#0-4) , so both refund receipts (the inline one from step 1 and the generic one from step 4) are sent to the receiver.

There is no check anywhere in `refund_unspent_gas_and_deposits` or in the receipt finalization path that subtracts amounts already refunded by an in-loop action handler. The two refund paths are entirely independent and additive.

### Impact Explanation
This allows an unprivileged attacker who submits an ordinary multi-action receipt (via a normal transaction with actions `[DeterministicStateInit, <any action guaranteed to fail>]`) to receive a refund receipt equal to the unused portion of the `DeterministicStateInit` deposit *twice*: once from the inline refund in `action_deterministic_state_init`, once again from the generic `refund_unspent_gas_and_deposits` totals. Because `state_update` for the deterministic-account's storage-staking balance increase is rolled back on failure while the (now duplicated) refund is still emitted, the attacker collects tokens that were never actually consumed by any persisted state change — a token-inflation bug (funds materialize out of nothing, matching the "token inflation" bounty category). All validators execute this deterministically the same way, so it does not cause a chain split, but it does let an attacker mint/duplicate NEAR balance.

### Likelihood Explanation
Low cost, fully attacker-controlled, and repeatable: the attacker only needs to submit a transaction whose receipt contains a `DeterministicStateInitAction` with a deposit exceeding the storage-staking requirement (so a nonzero partial refund is queued), followed by any action guaranteed to fail (e.g. a `Transfer` to an account with insufficient balance or a reverting `FunctionCall`). No special permissions, validator access, or race conditions are required — this is a pure unprivileged transaction-construction bug, repeatable indefinitely.

### Recommendation
Remove the inline refund push in `action_deterministic_state_init` (lines 87-91 of `deterministic_account_id.rs`) and instead track the "consumed" portion of the deposit (e.g., via `result.new_receipts`/a dedicated `result` field consumed by `refund_unspent_gas_and_deposits`, similar to how other deposit-bearing actions are handled), so that the centralized end-of-receipt refund computation is the single source of truth for deposit refunds and never double-counts an already-issued partial refund. Alternatively, make `total_deposit`/`refund_unspent_gas_and_deposits` aware of amounts already refunded by in-action-loop handlers and subtract them before issuing the final refund.

### Proof of Concept
Runtime/test-loop integration test:
1. Construct an action receipt with two actions: `DeterministicStateInitAction { deposit: D }` (with `D` greater than the storage-staking requirement `S`, so a nonzero `deposit_refund = D - S` is expected to be pushed inline) followed by a `TransferAction` to a receiver guaranteed to fail (e.g., insufficient balance).
2. Apply the receipt through the runtime (`Runtime::process_receipt` / test-loop harness).
3. Collect all outgoing "balance refund" receipts generated from this receipt.
4. Assert: sum of all refund receipt amounts should equal exactly the total attached deposit (`D + transfer_deposit`), per NEAR's balance-conservation invariant.
5. Expected (bug) result: the sum exceeds the attached deposit by the already-refunded `deposit_refund` amount (`D - S`), because it is counted both by the inline push in `action_deterministic_state_init` and by `refund_unspent_gas_and_deposits`'s `total_deposit`-based refund on overall receipt failure — violating the conservation assertion and demonstrating token duplication.
