### Title
Instant-withdraw claims are not gated on epoch funding, allowing unfunded receipts to drain reserves earmarked for other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out the full `instantWithdrawsRequests[_user]` balance with no check that the user's request epoch was actually funded via `collectInstantWithdrawFunds`. This mirrors CVE-2021-37594's bug class: a missing input/state validation on a request lets a caller act on data the protocol never verified. The normal-withdraw path explicitly gates claims on epoch maturity (`epochNumber <= lastWithdrawRequest[_user]` → revert), and the default path tracks funded claims per epoch via `instantWithdrawClaimsByEpoch`, but the funded instant path validates neither the epoch nor the funding state.

### Finding Description
In `IdleCreditVault.sol`:

- `requestInstantWithdraw` burns CDO strategy tokens, mints a receipt to the user, and records `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `pendingInstantWithdraws` (lines 356–375).
- `collectInstantWithdrawFunds` decrements the global `pendingInstantWithdraws` by `_amount` and pulls underlying from the CDO (lines 398–403). Crucially, nothing binds collected funds to a specific epoch — there is no `instantFundedByEpoch` marker, and `pendingInstantWithdraws` is a single aggregate.
- `claimInstantWithdrawRequest` (lines 380–393) does exactly:
  ```solidity
  uint256 amount = instantWithdrawsRequests[_user];
  _burn(_user, amount);
  instantWithdrawsRequests[_user] = 0;
  _transferFundedClaim(_user, amount);
  ```
  There is no check equivalent to the `_claimFundedWithdrawRequest` gate `epochNumber <= lastWithdrawRequest[_user]` (line 326), and no check that the CDO collected enough underlying to cover this request's epoch.

The contrast is precise: normal withdraw receipts cannot be claimed until their epoch ends, and defaulted-epoch instant receipts are cleared through `_claimDefaultedInstantWithdrawRequest`, which also maintains `instantWithdrawClaimsByEpoch` — proof the codebase knows per-epoch funding attribution is required. The funded instant path has no such attribution, so a claim only needs the strategy's underlying balance to be non-empty, not to be *funded for this request*.

Attack sketch (unprivileged lender/tranche holder):
1. Epoch N is running. Victim's normal withdraw request was processed at the previous `stopEpoch`, and the CDO called `collectWithdrawFunds`, moving underlying into the strategy to back victim receipts.
2. Attacker (KYC'd AA holder) calls `cdoEpoch.requestInstantWithdraw` (or the instant-triggered path at `stopEpoch`) to create an instant receipt while `pendingInstantWithdraws` is funded only partially or not yet for the current epoch.
3. Attacker calls `cdoEpoch.claimInstantWithdrawRequest` → `IdleCreditVault.claimInstantWithdrawRequest` → `_transferFundedClaim` sends `amount` underlying from the same strategy balance that was funded for the victim's normal receipt.
4. When the victim later calls `claimWithdrawRequest`, `_transferFundedClaim` reverts on insufficient strategy balance — the attacker converted an unfunded receipt into funded-receipt underlying.

`_transferFundedClaim` only excludes `defaultRecoveryReserve` from the spendable balance (lines 897+); it does not segregate normal-funded vs instant-funded buckets, so the drained funds are indistinguishable to the check.

### Impact Explanation
Direct theft of underlying reserved for other users' funded withdraw receipts. Loss equals `min(attacker receipt, strategy underlying balance net of defaultRecoveryReserve)` — up to the full funded-receipt pool if the attacker's receipt is large enough (receipt size is bounded only by the attacker's tranche position, which is unbounded in size). Victims' claims become permanently unpayable unless governance replenishes the vault: theft plus freezing of unclaimed funded withdrawals.

### Likelihood Explanation
Requires an epoch where instant withdraws are enabled and a strategy balance holding funded-but-unclaimed underlying — a routine state after any `stopEpoch` that collects withdraw funds while claimants have not yet claimed. The attacker needs only a KYC'd wallet and a tranche position (either own deposit or acquired tranche tokens). No privileged action, no default, and no oracle manipulation needed — just sequencing the claim before the per-epoch funding attribution that the code never enforces.

Caveat: whether `IdleCDOEpochVariant` orders `collectInstantWithdrawFunds` strictly before exposing `claimInstantWithdrawRequest` at the CDO layer could not be fully verified in this pass. However, even a correct CDO ordering does not fix the missing attribution: `pendingInstantWithdraws` and the strategy balance are global aggregates, so a partially funded epoch (borrower underpays at `stopEpoch`, or funding is split across transactions) still lets earlier instant claimants draw against other users' funded basis.

### Recommendation
Track funded instant-withdraw amounts per epoch (e.g., `instantFundedByEpoch[epoch]` set in `collectInstantWithdrawFunds` pro-rata or via a funded-price mapping like `lossRecoveryPriceByEpoch`), and gate `claimInstantWithdrawRequest` on the user's request epoch having been fully funded — mirroring the `epochNumber <= lastWithdrawRequest` gate in `_claimFundedWithdrawRequest`. Alternatively, segregate the instant-claim reserve from the normal funded-claim balance in `_transferFundedClaim`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

contract InstantClaimTheftPoC is Test {
    // Uses the repo's existing IdleCreditVault.t.sol harness setup:
    // strategy = IdleCreditVault, cdoEpoch = IdleCDOEpochVariant,
    // underlying = USDC-like token, AAtranche = tranche token.

    function testUnfundedInstantClaimDrainsFundedNormalReceipt() public {
        // --- Setup (reuse harness helpers) ---
        // victim deposits 100_000 USDC into AA, attacker deposits 10_000 USDC into AA.
        // startEpoch(); borrower takes funds.

        // Epoch 0 -> stopEpoch with normal withdraws funded:
        //   victim requests withdraw of all tranches.
        //   manager calls stopEpoch -> CDO calls collectWithdrawFunds(pendingWithdraws),
        //   strategy now holds underlying backing victim's receipt.

        // Epoch 1: instant withdraws enabled
        //   cdoEpoch.setInstantWithdrawParams(delay, minAprDiff, true);
        //   startEpoch();

        // Attacker requests instant withdraw:
        //   cdoEpoch.requestInstantWithdraw(attackerTranches) ->
        //   strategy.requestInstantWithdraw burns CDO tokens, mints receipt,
        //   sets instantWithdrawsRequests[attacker] = amount,
        //   pendingInstantWithdraws += amount.

        // KEY: CDO does NOT call collectInstantWithdrawFunds for the attacker's
        // epoch (e.g., borrower underpaid at stopEpoch, or funding is delayed),
        // OR epoch funding was partial. Strategy balance still holds the
        // victim's funded normal-claim underlying.

        // Attacker claims immediately:
        //   cdoEpoch.claimInstantWithdrawRequest(attacker)
        // No check on epochNumber, no check that collectInstantWithdrawFunds
        // covered this epoch -> _transferFundedClaim pays 'amount' underlying
        // from the balance funded for the victim.

        uint256 strategyBal = underlying.balanceOf(address(strategy));
        vm.prank(attacker);
        cdoEpoch.claimInstantWithdrawRequest();

        assertGt(underlying.balanceOf(attacker), 0, "attacker paid from unfunded receipt");

        // Victim's claim now reverts / underpays:
        vm.prank(victim);
        vm.expectRevert(); // insufficient strategy balance in _transferFundedClaim
        cdoEpoch.claimWithdrawRequest();

        assertLt(underlying.balanceOf(address(strategy)), strategyBal, "funded reserve drained");
    }
}
```
