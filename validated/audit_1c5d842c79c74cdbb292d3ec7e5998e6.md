## Title
Fail-open RPC error handling in `check_latest_block_in_tenure` lets a signer sign a stale/conflicting block when the last-look check should fail closed - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` treats a failed `get_tenure_tip` RPC call as `Ok(true)` ("assume the proposal is higher"), i.e. it fails open rather than closed. This function is reused not only at proposal-arrival time (where the node's own `/v3/block_proposal` validation is a backstop) but also as the final "one last look" re-check performed at the pre-commit-threshold moment, right before a signature is produced — a re-check that exists specifically because chain/signer-db state may have changed since validation. At that specific call site there is no equivalent node-side backstop, so a transient error talking to the local stacks-node collapses the last-look check into an automatic pass.

### Finding Description
`check_latest_block_in_tenure` is documented as safe to fail open because "this proposal ultimately must be passed to the `stacks-node` for proposal processing," relying on the node's own validation as the real backstop: [1](#0-0) 

The actual fail-open branch: [2](#0-1) 

That reasoning holds only when the caller is the proposal-arrival path (`check_proposal`), because a still-pending node validation call will catch any real inconsistency. But the same helper — via `check_tenure_change_confirms_parent` / `confirms_latest_block_in_same_tenure` — is also invoked from `check_block_against_signer_db_state`, which is the *only* place performing the "one last look" re-check right before a signer commits its own signature at the pre-commit threshold: [3](#0-2) [4](#0-3) 

This re-check is explicitly there because "the chain and signer db state may have changed materially since this block passed the proposal-time checks," and it is meant to reject the block instead of signing it if the tenure has moved on. When that check's underlying RPC (`client.get_tenure_tip`) simply errors — a local timeout, a transient node hiccup, a restart, or anything else that momentarily breaks the signer↔node loopback RPC — the function does not propagate the error as "unknown, don't sign"; it returns `Ok(true)`, meaning "assume the proposal is still the highest and continue." `check_block_against_signer_db_state` then reports no rejection, the pre-commit path proceeds to sign, and the signature is broadcast for a block that may in fact no longer be the canonical tip of its tenure.

This breaks the "signed vs validated" equality the last-look check is designed to protect: the signer ends up signing a block whose freshness/height relationship to the tenure tip was never actually confirmed at signing time, purely because of an incidental RPC error rather than any genuine confirmation that the proposal is still valid.

### Impact Explanation
This falls under the Critical impact class: a signer can sign a non-canonical/conflicting block. The pre-commit-threshold last-look check is the sole final safeguard for exactly this class of race (state changed between validation and signature); collapsing it to an automatic pass on RPC error removes that safeguard at the single point designed to catch it, with no other check at that step covering the same ground (per `docs/signer-flows.md`, "Because the duplicate check never runs again, a block that crosses the pre-commit threshold long after it was proposed relies on section 5's own-tenure conflict guard to cover the same ground" — but that own-tenure conflict guard is a separate mechanism from this height check and does not cover cross-tenure sibling conflicts caught only by `check_latest_block_in_tenure`).

### Likelihood Explanation
The trigger condition is any transient failure of the signer's local RPC call to its own stacks-node's tenure-tip endpoint at the exact moment the pre-commit threshold is crossed — a condition that does not require a majority of signers, another signer's key, or privileged access, and can occur from ordinary node load, restarts, or network blips coincident with block timing that a miner (who controls proposal/re-proposal timing) can influence.

### Recommendation
At the `check_block_against_signer_db_state` call site (the signing-time last-look), treat an RPC error from `get_tenure_tip` as "cannot confirm, do not sign" (fail closed / return a `ConnectivityIssues` rejection) rather than defaulting to `Ok(true)`. The current fail-open behavior should be scoped only to the proposal-arrival caller (`check_proposal`), where the node's own validation endpoint remains a backstop, e.g. by parameterizing `check_latest_block_in_tenure` with an explicit "on RPC error" policy per call site instead of a single hard-coded `Ok(true)`.

### Proof of Concept
1. A miner proposes block `B1` in tenure `T`; signers pre-commit toward the 70% threshold.
2. Independently (naturally, or via node restart/timeout, or by the miner's proposal/gossip timing coinciding with node load) a signer's local RPC to `get_tenure_tip(T)` starts erroring right as the pre-commit threshold for `B1` is reached.
3. `handle_block_pre_commit` calls `check_block_against_signer_db_state`, which calls `check_latest_block_in_tenure`; the `get_tenure_tip` call errors, hitting the `Err(e) => { ...; return Ok(true) }` branch at `chainstate/mod.rs:450-461`.
4. No rejection is produced, so the signer proceeds to `mark_locally_accepted` and signs `B1`, even though the actual state of tenure `T`'s tip (which the RPC failure prevented confirming) may no longer support signing `B1` as the canonical next block. [2](#0-1) [4](#0-3)

    fn check_block_against_signer_db_state(
        &mut self,
        stacks_client: &StacksClient,
        proposed_block: &NakamotoBlock,
    ) -> Option<BlockRejection> {
        let signer_signature_hash = proposed_block.header.signer_signature_hash();
        // If this is a tenure change block, ensure that it confirms the correct number of blocks from the parent tenure.
        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {
            // Ensure that the tenure change block confirms the expected parent block
            match SortitionData::check_tenure_change_confirms_parent(
                tenure_change,
                proposed_block,
                &mut self.signer_db,
                stacks_client,
                self.proposal_config.tenure_last_block_proposal_timeout,
                self.proposal_config.reorg_attempts_activity_timeout,
            ) {
                Ok(true) => return None,
                Ok(false) => {
                    return Some(self.create_block_rejection(
                        RejectReason::SortitionViewMismatch,
                        proposed_block,
                    ))
                }
                Err(e) => {
                    warn!("{self}: Error checking block proposal: {e}";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %proposed_block.block_id()
                    );
                    return Some(self.create_block_rejection(
                        RejectReason::ConnectivityIssues(
                            "error checking block proposal".to_string(),
                        ),
                        proposed_block,
                    ));
                }
            }
        }
