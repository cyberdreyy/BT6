### Title
Multi-epoch withdraw receipts bypass the `lossRecoveryPriceByEpoch` haircut — only the epoch stored in `lastWithdrawRequest` is haircutted, older receipts are paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug bounds a peer-controlled `frame_count` to a loose limit (64) that exceeds the fixed `frags[]` capacity (17), so entries overflow the array. The analog in `IdleCreditVault` is the same shape: `requestWithdraw` lets a user accumulate funded-receipt basis across **many** epochs via `withdrawsRequestsByEpoch[_user][epoch]`, but the loss-haircut machinery can only reference **one** epoch — the single slot `lastWithdrawRequest[_user]`. When a `stopEpochWithDuration` loss haircuts the aggregate `pendingWithdraws`, only the latest-epoch portion of a multi-epoch requester is haircutted; the rest is claimed at par from an underfunded strategy, draining the loss-recovery pool owed to other claimants.

### Finding Description
- `requestWithdraw` records receipts per epoch (`withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`) but stores only the latest epoch in `lastWithdrawRequest[_user] = currentEpoch` (lines 282–293). The only guard (lines 263–271) blocks a *new* request if the *previous* `lastWithdrawRequest` epoch already has a `lossRecoveryPrice` — it does not prevent stacking requests across multiple epochs while no loss exists yet.
- On a partial funding, `collectWithdrawFunds` sets `pendingWithdraws = 0` and `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` (lines 411–430). The haircut is meant to apply pro rata to *all* pending receipts, as `previewLossAdjustedWithdrawFunds` states ("all pending receipts share their aggregate portion of the loss pro rata", line 435).
- At claim time, `_claimLossAdjustedWithdrawRequest` (line 789) reads `lossEpoch = lastWithdrawRequest[_user]` and haircuts only `withdrawsRequestsByEpoch[_user][lossEpoch]` — the latest epoch's share. `_clearWithdrawClaimForEpoch` subtracts only that epoch's amount from `withdrawsRequests[_user]` and resets `lastWithdrawRequest` to 0 (lines 815–836).
- `claimWithdrawRequest` then falls through to `_claimFundedWithdrawRequest`, which pays the remaining aggregate `withdrawsRequests[_user]` (the earlier-epoch receipts) **at par** via `_transferFundedClaim` (lines 319–350). The epoch check passes because `lastWithdrawRequest` was zeroed and `epochNumber` advanced.

Net effect: a user holding receipts from epochs N and N+1 gets the haircut applied only to the N+1 share; the epoch-N share is paid 1:1 even though the borrower funded only `pendingBasis * lossRecoveryPrice` total.

### Impact Explanation
Direct theft / insolvency. The attacker escapes the realized loss on all but their latest-epoch receipts, withdrawing underlyings that belong to other haircutted claimants. Each wei of pre-loss earlier-epoch receipt is paid at par instead of `lossRecoveryPrice`, so the strategy's funded balance is exhausted early and subsequent claimants' `_transferFundedClaim` either reverts (permanent freezing of unclaimed recovery) or is silently shortchanged. With a 50% haircut, an attacker who split requests 50/50 across two epochs extracts ~25% more than their fair share.

### Likelihood Explanation
Fully attacker-controlled and cheap: a lender calls `requestWithdraw` once per epoch across two epochs (both requests are permitted — the guard only fires when a loss price already exists). Then they wait for (or merely exploit the next) `stopEpochWithDuration` partial funding, which honest manager/borrower calls routinely. No privileged role, timing race, or donation is required; `claimWithdrawRequest` then executes the theft in one call.

### Recommendation
In `requestWithdraw`, revert if the user has any outstanding receipt in an epoch different from `currentEpoch` (i.e., require `withdrawsRequests[_user] == 0 || lastWithdrawRequest[_user] == currentEpoch`), or make `_claimLossAdjustedWithdrawRequest` apply `lossRecoveryPrice` to the user's **entire** pending `withdrawsRequests[_user]` balance rather than only the `lastWithdrawRequest` epoch slice. Long-term, iterate all epochs with receipts or collapse multi-epoch receipts into a single basis.

### Proof of Concept
Foundry fork sketch (vault with USDC underlying, epoch variant CDO):

```solidity
// Setup: attacker deposits T tranche tokens worth 200 USDC; vault running.
// Epoch N (running):
cdo.requestWithdraw(attackerAAorBB);           // requestWithdraw(100e6, attacker, 100e6)
// epoch advances via manager.startEpoch -> epochNumber = N+1
// Epoch N+1 (running):
cdo.requestWithdraw(attackerAAorBB);           // second request, lastWithdrawRequest = N+1
// pendingWithdraws = 200e6 total (attacker) + other users' receipts

// Borrower repays only half: manager calls stopEpochWithDuration(..., loss)
// -> collectWithdrawFunds(_amount < pendingBasis)
// -> lossRecoveryPriceByEpoch[N+1] = 0.5e18, pendingWithdraws = 0

// Claim:
vm.prank(attacker);
cdo.claimWithdrawRequest(); // IdleCDO -> strategy.claimWithdrawRequest(attacker)
// _claimLossAdjustedWithdrawRequest: haircut only epoch N+1 receipts (100e6 * 0.5 = 50e6)
// _claimFundedWithdrawRequest: pays epoch N receipts 100e6 AT PAR
// attacker receives 150e6 of the ~funded pool instead of fair 100e6.
// Remaining claimants' _transferFundedClaim reverts or is underpaid -> insolvency.
```

Key state assertions: `strategy.lossRecoveryPriceByEpoch(N+1) == 0.5e18`, attacker paid `150e6` while `recoveryPrice`-fair payout is `100e6`, and a later claimant's `claimWithdrawRequest` reverts on insufficient strategy balance.
