### Title
Instruction Parser Trusts Attacker-Supplied `decimals` Field Instead of Verifying Against the Actual Mint, Causing Misreported Token Amounts in RPC Responses - (`transaction-status/src/parse_token.rs`)

### Summary
The `*Checked` SPL Token instruction parser (`TransferChecked`, `ApproveChecked`, `MintToChecked`, `BurnChecked`) builds the human-readable `tokenAmount` field directly from the `decimals` value embedded in the instruction's raw calldata, without cross-checking it against the actual decimals of the referenced mint account. This mirrors the Pear Protocol root cause: a value with an implicit "correct scale" assumption (there `minOut`, here `decimals`) is consumed without validating it matches the real, per-asset scale, producing wrong computed output that is surfaced to unprivileged callers.

### Finding Description
For every `*Checked` token instruction, the parser constructs `SplTokenAdditionalDataV2::with_decimals(decimals)` straight from the parsed instruction data and feeds it into `token_amount_to_ui_amount_v3` to compute `uiAmount`/`uiAmountString`: [1](#0-0) [2](#0-1) [3](#0-2) 

The `decimals` field here is attacker-controlled instruction data (any value 0–255 can be encoded by whoever constructs the transaction) and is never compared to the `decimals` field stored in the actual mint account referenced by `account_keys[instruction.accounts[1]]` (or `[0]` for mint-to/burn). The SPL Token *program* does perform this comparison at execution time and will fail the instruction if `decimals` doesn't match the mint — but the RPC-facing parser in `transaction-status` runs independent of execution success and is not aware of, nor does it query, the real mint state.

By contrast, the correct pattern used elsewhere in the same codebase looks up the mint's real decimals from bank state, e.g. `get_mint_owner_and_additional_data`/`get_additional_mint_data` in `rpc/src/parsed_token_accounts.rs`, which unpack the actual `Mint` account: [4](#0-3) 

The `*Checked` instruction parser bypasses this validated path entirely and blindly trusts the instruction payload.

### Impact Explanation
This is a decoder-misreporting bug reachable by any unprivileged user who crafts and submits (or even just gets included/fails on-chain) a transaction containing a `*Checked` token instruction with a `decimals` value inconsistent with the real mint. Any RPC consumer requesting `jsonParsed` encoding (e.g. `getTransaction`, `getBlock`, `simulateTransaction` with parsed accounts, `getConfirmedSignaturesForAddress2` details) for that transaction will receive a `tokenAmount.uiAmount`/`uiAmountString` computed with the wrong number of decimal places — a multiple-orders-of-magnitude misrepresentation of the actual token amount involved. Downstream tooling, wallets, explorers, and exchanges that trust RPC `jsonParsed` output for accounting or display can be fed grossly incorrect balances/amounts, which is the same "silent, ineffective validation due to reused/untrusted scale parameter" class of bug as the original finding, just manifesting as data misreporting rather than a funds-locking DoS.

### Likelihood Explanation
Trivial to trigger: crafting a `TransferChecked`/`ApproveChecked`/`MintToChecked`/`BurnChecked` instruction with an arbitrary `decimals` byte requires no special privileges, only standard instruction construction. The instruction does not even need to succeed on-chain for it to be parsed and displayed by `jsonParsed`-mode RPC queries against the transaction, since instruction parsing is independent of execution outcome.

### Recommendation
When parsing `*Checked` token instructions for `jsonParsed` display, resolve the actual mint account referenced in the instruction and use its on-chain `decimals` (and any interest-bearing/scaled-UI-amount config) — analogous to `get_mint_owner_and_additional_data` — instead of trusting the `decimals` field taken verbatim from instruction data. If mint state is unavailable in the parsing context, the parser should surface both the raw declared amount and the raw declared decimals without computing a derived `uiAmount`, or otherwise flag it as unverified.

### Proof of Concept
1. Construct a token mint with `decimals = 9`.
2. Construct a `TransferChecked` instruction (`spl_token_interface::instruction::transfer_checked`) referencing that mint, but pass `decimals = 0` instead of `9`, with `amount = 42`.
3. Submit (or merely have processed/failed) the transaction; the on-chain program will reject it if it actually executes, but the transaction is still recorded on the ledger.
4. Call `getTransaction` (or `simulateTransaction`) with `"encoding": "jsonParsed"`.
5. Observe: `transactionStatus/parse_token.rs`'s `TransferChecked` branch computes `tokenAmount` using `SplTokenAdditionalDataV2::with_decimals(0)` (see lines 365–373), yielding `uiAmount: 42` and `uiAmountString: "42"` instead of the mint-correct `uiAmount: 0.000000042`, a >10^9x misrepresentation — matching the existing unit test expectations at [5](#0-4)  that show `decimals` is taken verbatim from the instruction, not from mint state.

```rust
fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}
```
