# No vulnerability found for this question.

**Analysis:**

The claimed exploit describes `NakamotoSigners::pox_5_make_signer_set`'s largest-remainder apportionment, where tied `remainder` values are broken deterministically by ascending `signing_key` comparison [1](#0-0) . This does not constitute a security vulnerability under the stated rules for several reasons:

1. **The tie-break is the canonical rule, not a bypass of one.** The apportionment (including the deterministic tie-break by `signing_key`) is computed identically by every node from the same on-chain `pox-5` stacking state [2](#0-1) . There is no "unbiased" reference weight that this diverges from — the algorithm's output *is* the consensus-agreed weight that `verify_signer_signatures` consumes. The premise that there exists a separate ground-truth allocation "absent adversarial key grinding" is not supported by the code: for exactly-tied remainders, any deterministic tie-break is equally valid, and the comment in the code explicitly states the pubkey-sort tie-break exists "so the apportionment is deterministic (and matches the final sort)" [3](#0-2) .

2. **No safety or liveness property is broken.** Every full node runs the same deterministic computation over the same on-chain `pox-5` data, so all nodes converge on the identical `RewardSet`/`NakamotoSignerEntry.weight` values fed into `verify_signer_signatures`. There is no scenario where an invalid/non-canonical block gets signed, a rejection is recounted as acceptance, a signature crosses cycle/tenure boundaries, or a signer is wedged — the categories required for Critical/High impact are not implicated.

3. **This is a fairness/theoretical question about tie-break selection, not an exploitable equality violation.** The scenario (attacker precisely engineering `stacked_amt` to tie with another signer's remainder, based on `total_ustx_locked` across *all* signers which the attacker does not control, plus trivial key selection) at best shifts which of two tied, equally-deserving parties receives a single leftover weight unit — a fairness nuance in the tie-break specification, not a chain-safety or liveness bug. This falls under "theoretical findings," which is explicitly out of scope per the rules.

No exploitable equality break or wedge state exists in the traced code; the finding does not meet the required Critical/High impact bar.

        // a largest-remainder method:
        //
        // The threshold is `ceil(total / reward_slots)`.
        //
        // Flooring each signer's `stacked / threshold` assigns a base weight where the sum is `<= reward_slots`
        // (the ceil makes `total/threshold <= reward_slots`).
        //
        // This leaves some unassigned ("leftover") slots, which are handed out one-per-signer
        //  in descending fractional-remainder order (ties broken by pubkey-sort order).
        //
        // This avoids degenerate modes of the floor-and-drop scheme: when more than
        // `reward_slots` distinct signers hold roughly equal stake, every base weight floors to
        // 0, and without the leftover round the entire signer set could be dropped.
        let reward_slots = u128::from(pox_constants.reward_slots());
        let threshold = std::cmp::max(1, total_ustx_locked.div_ceil(reward_slots));

        struct Apportionment {
            signing_key: [u8; SIGNERS_PK_LEN],
            stacked_amt: u128,
            weight: u128,
            remainder: u128,
        }

        let mut apportioned: Vec<Apportionment> = signer_set
            .into_iter()
            .map(|(signing_key, stacked_amt)| Apportionment {
                signing_key,
                stacked_amt,
                weight: stacked_amt / threshold,
                remainder: stacked_amt % threshold,
            })
            .collect();

        // Guaranteed `<= reward_slots` by the ceil quota, so leftover does not underflow.
        let assigned: u128 = apportioned.iter().map(|entry| entry.weight).sum();
        let mut leftover = reward_slots.saturating_sub(assigned);

        if leftover > 0 {
            // Largest fractional remainder wins the next slot; ties broken by signing_key
            // ascending so the apportionment is deterministic (and matches the final sort).
            apportioned.sort_by(|a, b| {
                b.remainder
                    .cmp(&a.remainder)
                    .then_with(|| a.signing_key.cmp(&b.signing_key))
            });
            for entry in apportioned.iter_mut() {
                if leftover == 0 {
                    break;
                }
                entry.weight += 1;
                leftover -= 1;
            }
