## Title
Stale Confirmations From Removed Members Allow Multisig Requests To Execute Below The Live-Member Threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` in the multisig2 contract only purges pending requests and `num_requests_pk` counters that were *originated* by the removed member. It never scans the `confirmations` map to strip that member's previously-cast votes from *other* pending requests. `confirm()` later counts those stale votes toward `self.num_confirmations`, so a request can execute with fewer confirmations from members who are still actually part of the multisig than the configured threshold requires — the same class of bug as NFTR-11: a state binding (a confirmation "reserved" by an account) survives the removal of that account's standing, and nothing can later reconcile or purge it.

### Finding Description
The multisig binding that must hold is: `confirmations counted == confirmations from currently-live members`. `add_request` creates an empty confirmation set per request [1](#0-0) . `confirm` adds the caller's `MultisigMember` identity string to that set and executes the request once `confirmations.len() + 1 >= self.num_confirmations` [2](#0-1) .

`delete_member` is the only path that can invalidate a member's standing. It removes the access key (if any), removes `members`, and removes pending requests/`num_requests_pk` — but strictly filtered to requests where `r.member == member`, i.e. requests the removed member itself created: [3](#0-2) 

It does not iterate `self.confirmations` to remove the departing member's string from confirmation sets of requests created by *other* members. Those stale entries remain in the `HashSet<String>` forever, and `confirm()` has no way to distinguish a "live" confirmation from a stale one — it only checks set cardinality.

### Impact Explanation
This is Critical: "a multisig request executed below threshold." An attacker (or colluding minority of members) can get a request partially confirmed, then have the confirming member removed via a separate, unrelated `DeleteMember` request, and the removed member's confirmation still counts toward the total needed to authorize transfers, key additions, or contract calls — i.e. the contract can move funds or grant access with fewer *currently authorized* signers than `num_confirmations` mandates.

### Likelihood Explanation
Reachable by any subset of members with no protocol violation and no reliance on foundation/owner/redeploy assumptions: any member (or two colluding members) can (1) add and partially confirm a sensitive request, (2) separately confirm removal of one of the confirming members, and (3) finish confirming the original request with the remaining live members. Ordering of unrelated requests is entirely within members' control, so this is straightforward to trigger in normal usage, not a contrived edge case.

### Recommendation
When executing `DeleteMember`, iterate all pending requests' confirmation sets (not just those originated by the removed member) and remove the departing member's identity string from each, re-checking whether removal drops any request below a state that should reset counting. Alternatively, when confirming, validate that every entry in the stored confirmation set is still present in `self.members` before counting it (i.e., recompute intersection with live membership rather than trusting historical set length).

### Proof of Concept
1. Initialize multisig with members `A, B, C, D` and `num_confirmations = 3` via `new` [4](#0-3) .
2. `D` calls `add_request` to create request `R` (e.g. `Transfer`) — confirmations for `R` start empty [5](#0-4) .
3. `A` calls `confirm(R)` → `confirmations = {A}` (1 < 3, not yet executed) [2](#0-1) .
4. `B` calls `confirm(R)` → `confirmations = {A, B}` (2 < 3, not yet executed).
5. Separately, members `B, C, D` confirm a `DeleteMember{A}` request to threshold and it executes, removing `A` from `members` and deleting any requests `A` had *originated* — but `R` (originated by `D`) is untouched, so `confirmations` for `R` still contains `A` [3](#0-2) .
6. `C` calls `confirm(R)` → `confirmations.len() + 1 == 3 >= num_confirmations (3)` → `R` executes, even though the only currently-live confirmers were `B`, `C`, and `D` never explicitly confirmed (only `A`'s stale vote plus `B` and `C` count), i.e. the request executed with confirmations attributable to only 2 live members instead of 3.

    /// Add request for multisig.
    pub fn add_request(&mut self, request: MultiSigRequest) -> RequestId {
        let current_member = self.current_member().unwrap_or_else(|| {
            env::panic_str(
                "Predecessor must be a member or transaction signed with key of given account",
            )
        });
        // track how many requests this key has made
        let num_requests = self
            .num_requests_pk
            .get(&current_member.to_string())
            .unwrap_or(0)
            + 1;
        assert(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some.",
        );
        self.num_requests_pk
            .insert(&current_member.to_string(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            member: current_member,
            added_timestamp: env::block_timestamp(),
            request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
