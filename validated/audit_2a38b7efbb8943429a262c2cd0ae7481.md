## Title
Instruction parser trusts attacker-supplied `decimals` in SPL-Token "Checked" instructions without validating against the real mint - ([File: transaction-status/src/parse_token.rs])

### Summary
The external report flags a class of bug where a contract accepts two independently-supplied values that are supposed to represent the same real quantity (`msg.value` vs `amountIn`) but never cross-checks them, so the *reported*/used amount can diverge from the *actual* amount. The equivalent bug class in agave is the transaction/instruction parser used by JSON-RPC methods such as `getTransaction`/`getParsedTransaction`: for SPL-Token "Checked" instructions (`TransferChecked`, `ApproveChecked`, `MintToChecked`, `BurnChecked`, `TransferCheckedWithFee`, permissioned-burn `BurnChecked`, confidential `Deposit`/`Withdraw`), the parser takes the `decimals` field straight out of the attacker-controlled instruction bytes and formats the human-readable `tokenAmount`/`uiAmount` from it, without ever consulting the actual mint account's real `decimals` value.

### Finding Description
In `transaction-status/src/parse_token.rs`, `TransferChecked { amount, decimals }` is decoded and immediately turned into a `SplTokenAdditionalDataV2::with_decimals(decimals)` using the `decimals` value taken verbatim from the instruction data, then formatted via `token_amount_to_ui_amount_v3`: [1](#0-0) 

The same pattern repeats for `ApproveChecked`, `MintToChecked`, `BurnChecked`: [2](#0-1) 

and for the transfer-fee extension's `TransferCheckedWithFee`: [3](#0-2) 

and for confidential-transfer `Deposit`/`Withdraw`: [4](#0-3) 

By contrast, when parsing account *state* (not instructions), `account-decoder/src/parse_token.rs` correctly fetches the real decimals from the mint account via `additional_data` before rendering `UiTokenAmount`: [5](#0-4) 
and the RPC's `get_token_account_balance`/`get_token_supply` handlers likewise resolve decimals from the on-chain mint before formatting: [6](#0-5) 

The instruction parser in `transaction-status/src/parse_token.rs`, however, has no equivalent step — it never loads the mint account referenced by `account_keys[instruction.accounts[1]]` to verify that the caller-supplied `decimals` actually matches the mint's real decimals. This is precisely the "value A vs value B not cross-checked" pattern from the report: the SPL-Token runtime program does enforce `decimals == mint.decimals` for `TransferChecked` to succeed on-chain, but the RPC decoder used for `getTransaction`/`getParsedTransaction` display formats the number purely from the (possibly mismatched) instruction bytes.

### Impact Explanation
Any unprivileged user can submit a transaction containing a `TransferChecked`/`ApproveChecked`/`MintToChecked`/`BurnChecked`/`TransferCheckedWithFee` instruction with a `decimals` value that does not match the real mint. If the instruction fails at runtime (`InvalidNumberOfDecimals`), the transaction is still recorded on-chain and can still be fetched and JSON-parsed via `getTransaction`/`getParsedTransaction`. Any client, indexer, or explorer that renders the parsed `tokenAmount.uiAmount`/`uiAmountString` from this RPC output — without separately re-deriving decimals from the mint — will display a wrong amount for that instruction, i.e., wrong account/instruction data is returned by an unprivileged read RPC call. This matches the "decoder misreporting" acceptance criterion.

### Likelihood Explanation
Low-to-medium. It requires a user (attacker or the transaction's own fee payer) to deliberately construct a "Checked" instruction with a `decimals` argument that differs from the mint's actual decimals, and for consumers of `getTransaction`/`getParsedTransaction` to trust the parsed `tokenAmount` display for failed/malformed instructions without independently checking the mint. No special privilege is required — only submitting an ordinary transaction and querying it back through public RPC.

### Recommendation
When parsing `*Checked` SPL-Token instructions in `transaction-status/src/parse_token.rs` (and the transfer-fee/confidential-transfer extension parsers), resolve the referenced mint account and compare its real `decimals` against the instruction-supplied `decimals` before formatting `tokenAmount`. If they differ, either flag the parsed result (e.g., add a `decimalsMismatch` marker) or fall back to displaying only the raw integer `amount` without a computed `uiAmount`, mirroring the mint-aware resolution already done in `account-decoder/src/parse_token.rs` and `rpc/src/rpc.rs::get_token_account_balance`.

### Proof of Concept
1. Create a token mint with `decimals = 9`.
2. Craft a `TransferChecked` instruction (via `spl_token_2022_interface::instruction::transfer_checked`) specifying `decimals = 2` (mismatched) and `amount = 42`.
3. Submit the transaction; it fails on-chain with `InvalidNumberOfDecimals`, but the transaction and its instructions are still stored/queryable.
4. Call `getTransaction`/`getParsedTransaction` (unprivileged JSON-RPC) on the signature; the parser at `transaction-status/src/parse_token.rs:365-387` decodes `tokenAmount` using the attacker-chosen `decimals = 2` (`ui_amount = 0.42`) instead of the mint's real `decimals = 9` (which would be `0.000000042`), returning a misleading `uiAmount`/`uiAmountString` to any caller relying on the parsed output.

    pub fn get_token_account_balance(
        &self,
        pubkey: &Pubkey,
        commitment: Option<CommitmentConfig>,
    ) -> Result<RpcResponse<UiTokenAmount>> {
        let bank = self.bank(commitment);
        let account = bank.get_account(pubkey).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find account".to_string())
        })?;

        if !is_known_spl_token_id(account.owner()) {
            return Err(Error::invalid_params(
                "Invalid param: not a Token account".to_string(),
            ));
        }
        let token_account = StateWithExtensions::<TokenAccount>::unpack(account.data())
            .map_err(|_| Error::invalid_params("Invalid param: not a Token account".to_string()))?;
        let mint = &Pubkey::from_str(&token_account.base.mint.to_string())
            .expect("Token account mint should be convertible to Pubkey");
        let (_, data) = get_mint_owner_and_additional_data(&bank, mint)?;
        let balance = token_amount_to_ui_amount_v3(token_account.base.amount, &data);
        Ok(new_response(&bank, balance))
    }
