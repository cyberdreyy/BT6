### Title
Unfunded instant-withdraw receipts from a previous epoch are invisible to `defaultPendingClaimBasis`, so an epoch-indexed global bucket misallocates the default recovery reserve and can permanently block earlier-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
In the Footium report, a single updatable global index (`_maxGenerationId`) was applied uniformly across seasons, so entitlements earned in a past season became unmintable while newer-season users claimed more than their share. The same class exists in `IdleCreditVault`: instant-withdraw recovery basis is keyed to a single global epoch index (`instantWithdrawClaimsByEpoch[epochNumber]` and `defaultRecoveryEpoch`), not to per-epoch-per-user ownership. If instant receipts remain unfunded across an epoch boundary, `finalizeDefaultRecovery` computes the recovery price only over the *current* epoch's instant basis, while `_claimInstantWithdrawRequest` still pays older receipts at par from the same reserve — letting one epoch's claimants consume another's recovery, and permanently stranding the claimants whose epoch is not `defaultRecoveryEpoch`.

### Finding Description
`requestInstantWithdraw` records receipts per user and per epoch (`instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`) and bumps the global `pendingInstantWithdraws` (IdleCreditVault.sol:356-375).

`startEpoch` only collects `min(pendingInstant, totUnderlyings)` via `collectInstantWithdrawFunds` (IdleCDOEpochVariant.sol:279-289), so `pendingInstantWithdraws` — and therefore `instantWithdrawsRequestsByEpoch` entries — can survive across an epoch boundary when the CDO is short of cash.

At default finalization, `defaultPendingClaimBasis` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — to the recovery basis (IdleCreditVault.sol:644-649). `finalizeDefaultRecovery` then divides `defaultRecoveryReserve` over `activeBasis + pendingBasis` and stores a single `defaultRecoveryEpoch` (IdleCreditVault.sol:679-693).

Claims are likewise indexed by that single epoch:

- `_claimDefaultedInstantWithdrawRequest` only haircuts `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`; receipts recorded under any older epoch keep full par value inside `instantWithdrawsRequests[_user]` (IdleCreditVault.sol:842-855).
- `claimInstantWithdrawRequest` then pays `instantWithdrawsRequests[_user]` — which still includes the old-epoch par-value remainder — from the strategy balance (IdleCreditVault.sol:380-392), and `_transferFundedClaim` reverts when the remaining balance cannot cover it once the reserve is earmarked (IdleCreditVault.sol:897-907).

Two concrete failure modes result, both without any privileged misbehavior:

1. **Old-epoch receipt holder (Alice) vs current-epoch holders (Bob):** Alice's epoch-N instant receipt stayed unfunded through `startEpoch` of epoch N+1. Bob's epoch-N+1 receipts are included in `defaultPendingClaimBasis` at finalization; Alice's basis is excluded, so `defaultRecoveryPrice` is diluted *upward* for Bob's cohort while Alice still holds a par claim. If Alice claims first she drains reserve that was priced only for epoch-N+1 basis, and Bob's `_claimDefaultedInstantWithdrawRequest`/`_transferDefaultRecovery` underflows on `defaultRecoveryReserve -= _amount` or the transfer fails — permanent freeze of Bob's legitimately-funded recovery.
2. Conversely, if Bob's cohort claims first at their (inflated, because Alice's basis was omitted) recovery price, the reserve can be exhausted before Alice's par claim executes; `claimInstantWithdrawRequest` then reverts for Alice forever — her previous-epoch receipt is unclaimable, exactly the "blocked from minting from past season" pattern.

### Impact Explanation
Permanent freezing/direct theft of withdraw entitlements sized to the unfunded instant receipts carried across the epoch boundary and the entire `defaultRecoveryReserve` pool. Whichever cohort claims second loses up to 100% of its recovery; the reserve is not topped up afterward, so the loss is permanent, not temporary.

### Likelihood Explanation
Requires (a) instant withdrawals enabled (`disableInstantWithdraw == false`), (b) `pendingInstantWithdraws` left partially unfunded at a `startEpoch` (possible whenever CDO cash < pending instant queue — explicitly handled by the code path at IdleCDOEpochVariant.sol:286-289), and (c) a subsequent borrower default finalized via `finalizeDefaultRecovery`. Each precondition is exercised in the repo's own tests for partial instant funding; the bug needs no malicious privileged role — owner, manager and borrower behave honestly throughout. Medium likelihood within pools that run instant withdrawals, matching the source report's Medium/Low profile.

### Recommendation
Track the unfunded instant basis per epoch rather than a single current-epoch bucket: either (a) include all outstanding `instantWithdrawsRequests` (not just `instantWithdrawClaimsByEpoch[epochNumber]`) in `defaultPendingClaimBasis`, and let `_claimDefaultedInstantWithdrawRequest` iterate/settle every non-zero epoch entry for the user, or (b) carry unfunded instant receipts forward by re-keying `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` into the new epoch at `startEpoch` when the queue is only partially collected. The second option is a smaller change but loses the original request-epoch attribution for loss pricing.

### Proof of Concept
Foundry fork skeleton (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// 1. Pool running with instant withdrawals enabled; Alice and Bob hold AA tranches.
// 2. During buffer of epoch N: Alice calls requestInstantWithdraw -> receipt at epoch N.
// 3. Manager calls startEpoch with CDO cash < pendingInstant:
//    collectInstantWithdrawFunds only pulls part; pendingInstantWithdraws > 0 survives.
// 4. During buffer of epoch N+1: Bob calls requestInstantWithdraw -> receipt at epoch N+1.
// 5. Borrower defaults; manager calls finalizeDefault / finalizeDefaultRecovery.
//    defaultPendingClaimBasis() == pendingWithdraws + instantWithdrawClaimsByEpoch[N+1]
//    (Alice's epoch-N basis is missing), so defaultRecoveryPrice is mispriced.
// 6. vm.prank: Bob claims -> _claimDefaultedInstantWithdrawRequest + funded path drains
//    more than his fair share of defaultRecoveryReserve.
// 7. vm.prank: Alice calls cdoEpoch.claimInstantWithdrawRequest();
//    expectRevert: safeTransfer underflow / defaultRecoveryReserve underflow.
// assert: Alice's instantWithdrawsRequests[Alice] remains > 0 forever.
```

Uncertainty note: I could not fully trace whether `claimInstantWithdrawRequest`'s par payout for the residual `instantWithdrawsRequests[_user]` (line 387-392) routes through `_transferFundedClaim`'s reserve guard (line 904) or a raw transfer in all branches — the excerpt shows `_transferFundedClaim` at line 392, which would revert on reserve-protected balance rather than steal from it; in that ordering the impact becomes Alice's own claim being frozen (still permanent, still the same bug class) rather than draining the reserve. Either branch produces a valid medium-severity analog; the fix above resolves both.
