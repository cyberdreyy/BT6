### Title
lchmod follows attacker-crafted symlink when duplicate zip entry names swap a regular file to a symlink, allowing chmod outside the extraction root - (File: helpers/archives/zip_extract.go / helpers/archives/os_unix.go)

### Summary
`ExtractZipArchive` performs a two-pass extraction: the first pass writes all entries to disk, and the second pass calls `lchmod(file.Name, file.Mode())` for every entry using that entry's *own* recorded mode. If an attacker crafts a zip with two entries sharing the same `Name`, where the first is a regular file and the second is a symlink to an attacker-chosen target, the on-disk path ends up as a symlink after pass one, but the second-pass `lchmod` call for the first (regular) entry still uses that entry's non-symlink `Mode()`, so it skips the symlink-skip check in `lchmod` and calls `unix.Fchmodat` with `flags=0`, which follows the symlink and chmods the attacker-chosen target.

### Finding Description
In `helpers/archives/zip_extract.go`, `ExtractZipArchive` iterates `archive.File` twice: [1](#0-0) 

Pass 1 (`extractZipFile`) writes each entry to `file.Name`, removing any existing entry first: [2](#0-1) 

If entry A (`Name="x"`, regular file) is processed, then entry B (`Name="x"`, symlink, target `../../../etc/passwd` or any absolute/relative path outside the workspace) is processed afterward, `extractZipSymlinkEntry` removes the file created by A and creates a symlink at `x` pointing outside the workspace. After pass 1, the filesystem path `x` is a symlink to the attacker's target.

Pass 2 then iterates the same `archive.File` slice again in order and calls `lchmod(file.Name, file.Mode())` for **each entry object**, not for each unique path. When it reaches entry A (index for the regular-file entry), `file.Mode()` is the mode recorded for A (no `os.ModeSymlink` bit), and `file.Name` is `"x"`. In `helpers/archives/os_unix.go`: [3](#0-2) 

On Linux, the `mode&os.ModeSymlink != 0` skip only fires based on the *entry's* recorded mode — not the current filesystem type at that path. Since entry A's mode has no symlink bit, the skip is bypassed, and `flags` remains `0`. `unix.Fchmodat(unix.AT_FDCWD, "x", ..., 0)` with `flags=0` follows symlinks (equivalent to `chmod`, not `lchmod`), so it operates on whatever `x` currently resolves to — which pass 1 has already swapped to the attacker's symlink target outside the extraction root.

No existing check prevents this: `errorIfGitDirectory` only blocks `.git` paths, and there is no duplicate-name detection, no path-traversal/absolute-path validation for zip entry names or symlink targets, and no re-stat of the current filesystem type before calling `lchmod` in the second pass.

### Impact Explanation
An attacker who controls the contents of a cache or artifact zip (both are attacker-controlled inputs: cache keys/paths and artifact paths are configurable by the pipeline author) can cause the Runner process, during cache/artifact restoration, to change file permissions (`chmod`) on an arbitrary file path reachable by symlink target resolution — including files outside the job's working directory, subject to the OS permissions of the Runner process. This is a permission-modification integrity issue outside the intended extraction root, violating the invariant that "file operations must stay within intended build/cache/artifact roots." The severity is bounded by the Runner process's own file permissions (it cannot chmod files it doesn't own/have write-DAC on), but it can still corrupt permissions on shared files/directories writable by the runner user (e.g., other projects' build directories on a shared shell runner, or files under the runner's home directory), causing availability/integrity impact for unrelated jobs or the runner host.

### Likelihood Explanation
Preconditions are modest: the attacker needs the ability to supply a crafted zip as a cache or artifact archive that Runner will extract via `ExtractZipArchive`/`ExtractZipFile` — feasible for any pipeline author uploading/restoring cache or artifacts. Crafting a zip with two entries of identical `Name` (one regular, one symlink) is straightforward with the standard `archive/zip` writer or a manual zip constructor, since the zip format does not forbid duplicate names. The exploit is deterministic and repeatable: for any two-entry-same-name zip of this shape, the result of pass 2 is that `lchmod` runs `Fchmodat` with `flags=0` against a symlink, following it. This is fully reachable on Linux, which is the documented/primary target per the `runtime.GOOS == "linux"` branch in `lchmod`.

### Recommendation
Fix `lchmod`/`ExtractZipArchive` so the symlink-skip decision is based on the current on-disk file type at `file.Name` (e.g., `os.Lstat` immediately before calling `Fchmodat`), not the mode recorded in the (possibly stale/duplicate) zip entry. Additionally, reject or de-duplicate zip archives containing multiple entries with the same `Name` before extraction, and ensure `Fchmodat` is never invoked with `flags=0` unless it has just been verified (via `Lstat`) that the target is not currently a symlink.

### Proof of Concept
Go unit test in `helpers/archives`:
1. Build an in-memory `zip.Writer` with two entries both named `"link_target_alias"` (or a subpath like `"a/b"`): entry 1 a regular file with arbitrary mode (e.g., `0644`), entry 2 a symlink entry whose content (target) is a relative path escaping the extraction directory, e.g., `"../../canary"`.
3. Create a temp extraction directory `extractDir`, and outside it create a canary file `canary` with a known mode (e.g., `0600`).
4. Call `ExtractZipArchive` with CWD set to `extractDir` (or adjust entry names so the symlink resolves to `../canary` relative to `extractDir`).
5. Assert: after extraction, `os.Lstat(filepath.Join(extractDir, "a/b"))` reports a symlink (proving swap happened), and `os.Stat(canaryPath).Mode().Perm()` is unchanged from `0600` — i.e., the symlink-follow-chmod did not alter the canary's permissions.
6. To demonstrate the bug pre-fix, the test should fail (canary mode changed to entry 1's `0644`) before the fix, and pass after re-stat-based fix is applied.

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}

func lchmod(name string, mode os.FileMode) error {
	var flags int

	if runtime.GOOS == "linux" {
		// Linux does not support changing modes on symlinks.
		if mode&os.ModeSymlink != 0 {
			return nil
		}
	} else {
		flags = unix.AT_SYMLINK_NOFOLLOW
	}

	err := unix.Fchmodat(unix.AT_FDCWD, name, uint32(mode.Perm()), flags)
	if err != nil {
		return &os.PathError{Op: "lchmod", Path: name, Err: err}
	}
	return nil
}
