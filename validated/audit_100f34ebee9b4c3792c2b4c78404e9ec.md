### Title
Stale per-epoch instant-withdraw basis is never cleared on funded claims, inflating default recovery and freezing later claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays a funded instant receipt but only clears the aggregate `instantWithdrawsRequests[_user]`; it never clears `instantWithdrawsRequestsByEpoch[_user][epochNumber]` or decrements `instantWithdrawClaimsByEpoch[epochNumber]`. If the same epoch later defaults with any still-unfunded instant request, `defaultPendingClaimBasis` reads that stale per-epoch entry as if it were still outstanding — the direct analog of `nsc_rle_decompress_data` consuming `context->Planes` without verifying the buffer still contains valid data. The inflated basis dilutes `defaultRecoveryPrice` for every recovery claimant, and the affected user's `_claimDefaultedInstantWithdrawRequest` underflows on `instantWithdrawsRequests[_user] -= claimBasis`, permanently reverting their claim.

### Finding Description
In `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393) the funded-claim path does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It does **not** touch `instantWithdrawsRequestsByEpoch[_user][epochNumber]` or `instantWithdrawClaimsByEpoch[epochNumber]`, which `requestInstantWithdraw` (lines 371-372) increments.

Later, on borrower default, `finalizeDefaultRecovery` calls `defaultPendingClaimBasis` (lines 644-649), which adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0`. The already-paid, stale receipt in the current epoch is counted again. Then `_claimDefaultedInstantWithdrawRequest` (lines 842-856) reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — the stale plus new basis — and subtracts it from the aggregate `instantWithdrawsRequests[_user]`, which only holds the *new* request amount. That subtraction underflows and reverts.

### Impact Explanation
Two distinct harms, both reachable by an unprivileged tranche holder:

1. **Recovery dilution (theft from other claimants).** The stale amount `X` inflates `totalBasis` in `finalizeDefaultRecovery`, lowering `defaultRecoveryPrice = reserve / totalBasis` for every defaulted-epoch receipt holder and active LP. The difference is never paid out — it is stranded in `defaultRecoveryReserve`, so honest users permanently recover less than entitled.
2. **Permanent freeze of the repeat-requester's claim.** The attacker's (or victim's) own legitimate new instant receipt becomes unclaimable because `_claimDefaultedInstantWithdrawRequest` always underflows (`claimBasis = X + new > instantWithdrawsRequests[_user] = new`). Since `defaultRecoveryFinalized` is already set, there is no recovery path; the underlying is locked forever.

Broken invariants: "one receipt one payout" (the paid receipt is counted twice in recovery basis) and solvency of the recovery reserve (basis exceeds funded claims).

### Likelihood Explanation
The sequence is short and uses only honest privileged calls:

- Epoch N running. User requests instant withdraw (`requestWithdraw` with `lastEpochApr > currentApr + instantWithdrawAprDelta`). Manager calls `getInstantWithdrawFunds` after `instantWithdrawDeadline`; `collectInstantWithdrawFunds` sets `pendingInstantWithdraws` to 0; user claims — stale `instantWithdrawsRequestsByEpoch[user][N] = X` remains.
- Still in epoch N (epochNumber only bumps at the next `stopEpoch`), the same or another user makes a second instant request of amount `Y`: `pendingInstantWithdraws = Y`, `instantWithdrawClaimsByEpoch[N] = X + Y`.
- Borrower fails to fund the second batch; `getInstantWithdrawFunds` catch-path triggers `_handleBorrowerDefault`. `finalizeDefaultRecovery` computes basis including stale `X`.

All steps use normal user flows plus owner/manager calls that occur in ordinary operation (funding instant queue, then default). No guard prevents a second instant request in the same epoch; the `defaultRecoveryFinalized` re-request guard in `requestWithdraw` only applies post-finalization. The requirement is a default in the same epoch as a previously claimed instant receipt — plausible since instant requests cluster in the same epoch when APR drops.

### Recommendation
In `claimInstantWithdrawRequest` (and in `collectInstantWithdrawFunds` if claims are settled at collection time), clear the per-epoch records when paying funded receipts:

- set `instantWithdrawsRequestsByEpoch[_user][requestEpoch] -= paid` (tracking the request epoch per user, e.g., a `lastInstantWithdrawRequest` mapping), and
- decrement `instantWithdrawClaimsByEpoch[requestEpoch]` and ensure consistency with the pending counter.

Alternatively, in `defaultPendingClaimBasis` / `_claimDefaultedInstantWithdrawRequest`, cap the per-epoch basis by the still-outstanding aggregate (`min(instantWithdrawsRequestsByEpoch[user][epoch], instantWithdrawsRequests[user])`) so already-funded receipts cannot re-enter recovery accounting.

### Proof of Concept
Foundry fork PoC (scaffold consistent with `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopCurrentEpochWithApr`):

```solidity
function testStaleInstantBasisInflatesDefault() external {
  uint256 amount = 100_000 * ONE_SCALE;
  idleCDO.depositAA(amount); idleCDO.depositBB(amount);
  address alice = makeAddr('alice');
  _depositWithUser(alice, 10_000 * ONE_SCALE, true);

  // epoch 0 ends with low apr so instant withdraws trigger in buffer of epoch 1
  _startEpochAndCheckPrices(0);
  _stopCurrentEpochWithApr(1e18); // apr drops -> instant mode enabled

  // alice requests instant withdraw (epochNumber == 1)
  vm.prank(alice);
  cdoEpoch.requestWithdraw(0, address(AAtranche));
  uint256 X = strategy.instantWithdrawsRequestsByEpoch(alice, 1);
  assertGt(X, 0);

  // run epoch 1, borrower funds instant queue after delay
  _startEpochAndCheckPrices(1);
  deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
  vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
  vm.prank(manager);
  cdoEpoch.getInstantWithdrawFunds(); // pendingInstantWithdraws -> 0

  vm.prank(alice);
  cdoEpoch.claimInstantWithdrawRequest(); // paid X, but per-epoch basis stays
  assertEq(strategy.instantWithdrawsRequestsByEpoch(alice, 1), X); // STALE

  // alice requests instant withdraw again in the SAME epoch 1
  vm.prank(alice);
  cdoEpoch.requestWithdraw(0, address(AAtranche)); // second instant request, amount Y
  uint256 Y = strategy.instantWithdrawsRequests(alice);

  // borrower cannot fund -> default, then finalize recovery
  // (manager calls getInstantWithdrawFunds; transfer fails -> _handleBorrowerDefault)
  // owner finalizes via finalizeDefault/ finalizeDefaultRecovery path
  // Assert: basis counted X + Y instead of Y
  assertEq(strategy.instantWithdrawClaimsByEpoch(1), X + Y); // diluted basis

  // alice's claim reverts: instantWithdrawsRequests[alice] (=Y) - claimBasis (=X+Y) underflows
  vm.prank(alice);
  vm.expectRevert(); // arithmetic underflow in _claimDefaultedInstantWithdrawRequest
  cdoEpoch.claimInstantWithdrawRequest();
}
```

Expected: recovery price is lower than `reserve / Y` (other claimants underpaid), and Alice's legitimate `Y` receipt is permanently unclaimable.
