### Title
Instant-withdraw funding decision and payout are not atomic: unfunded/partially funded instant receipts are claimable in full and drain the strategy reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a race between a *decision* (whether to fall back) and the *action* (performing the fallback), both keyed on state that could change in between. The closest analog in this codebase is the instant-withdraw pipeline in `IdleCreditVault`: the *decision* side is the aggregate bucket `pendingInstantWithdraws`, which `collectInstantWithdrawFunds` decrements by whatever amount the CDO actually collected, while the *action* side, `claimInstantWithdrawRequest`, pays each user's full recorded receipt `instantWithdrawsRequests[_user]` without checking that the user's request epoch was actually funded.

### Finding Description
`requestInstantWithdraw` burns CDO-held strategy tokens, mints a 1:1 receipt to the user, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]` and `pendingInstantWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:356-375). Funding is decided later, at epoch stop, when the CDO calls `collectInstantWithdrawFunds(_amount)`, which only decrements the aggregate `pendingInstantWithdraws -= _amount` and pulls `_amount` of underlying from the CDO (contracts/strategies/idle/IdleCreditVault.sol:398-403). There is no per-epoch funded price or per-user funded flag recorded.

`claimInstantWithdrawRequest` then unconditionally pays the full `instantWithdrawsRequests[_user]` and burns the receipt (contracts/strategies/idle/IdleCreditVault.sol:380-393). Outside of the `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` path, no check ties the claim to what was actually collected for that epoch. So if the CDO funds the instant queue only partially (e.g., `getInstantWithdrawFunds` returns less than `pendingInstantWithdraws` because the liquid buffer is smaller than the queued amount, or only part of the requests qualified under the instant-withdraw APR/delay window), the first claimants receive 100% of their receipts while later claimants' transactions revert on the ERC20 transfer — the funded amount is consumed by whoever claims first, not pro-rata. Worse, a user who files an instant request in a new epoch before any funding decision for that epoch can race to `claimInstantWithdrawRequest` against a reserve that belongs to previously funded receipts or to `defaultRecoveryReserve`, because the payout path never verifies funding.

The broken invariant is "one receipt, one funded payout": the funding decision (aggregate `pendingInstantWithdraws` accounting at collect time) and the claim action (per-user full payment) are decoupled and evaluated against different state. Existing guards do not stop this: `nonReentrant` is irrelevant across transactions, `_onlyIdleCDO` only gates the caller, and the default-recovery branch only covers the finalized-default case.

### Impact Explanation
Unprivileged tranche-token holders can extract more underlying than the borrower actually funded for instant withdrawals. In the partial-funding scenario, early claimants steal the underlying that was funded for other users' receipts (direct theft / unfair socialization instead of pro-rata). In the post-default scenario, a fresh instant receipt can drain `defaultRecoveryReserve`, permanently reducing what defaulted-epoch claimants recover via `defaultRecoveryPrice`. Loss is bounded by the strategy's underlying balance at claim time; every underlying token claimed beyond the funded amount is stolen from other receipt holders or from the recovery reserve.

### Likelihood Explanation
Requires the instant-withdraw feature to be enabled (manager-honest assumption holds — the attacker is only a KYC-passed tranche holder) and a state where collected funds are less than the sum of claimable receipts, which occurs whenever the CDO's liquid balance at `stopEpoch` covers only part of `pendingInstantWithdraws`, or when an attacker files an instant request in an epoch whose instant queue is never funded. No privileged cooperation is needed; the attacker only calls `requestInstantWithdraw` and `claimInstantWithdrawRequest` through the CDO.

### Recommendation
Record a per-epoch funded price for instant withdrawals, mirroring `lossRecoveryPriceByEpoch`/`epochWithdrawPrice` in `IdleCDOEpochQueue`: e.g., set `instantFundedPriceByEpoch[epoch] = collectedAmount * 1e18 / instantWithdrawClaimsByEpoch[epoch]` inside `collectInstantWithdrawFunds` (and clear per-epoch totals once fully funded), then make `claimInstantWithdrawRequest` pay `instantWithdrawsRequests[_user]` pro-rata by that price and revert or skip when the request epoch was never funded. This makes the funding decision and the payout action use the same per-epoch record.

### Proof of Concept
Foundry fork sketch (assumes instant withdrawals enabled via `setInstantWithdrawParams` and a caller path through `cdoEpoch`):

```solidity
// Epoch 0 running; users file instant requests.
cdoEpoch.requestInstantWithdraw(amountA, userA); // via AA tranche holder A
cdoEpoch.requestInstantWithdraw(amountB, userB); // holder B
// stopEpoch: CDO has liquidity < pendingInstantWithdraws, so it collects
// only part via collectInstantWithdrawFunds(partial).
// Attacker A claims first: pays amountA in full though funding was partial.
vm.prank(userA); cdoEpoch.claimInstantWithdrawRequest();
// Victim B's claim now reverts on safeTransfer (insufficient strategy balance)
// or, after a new epoch's request, drains reserve meant for other claims.
vm.expectRevert(); vm.prank(userB); cdoEpoch.claimInstantWithdrawRequest();
```

Note: I was not able to fully read `IdleCDOEpochVariant.getInstantWithdrawFunds`/`stopEpoch` to confirm whether partial `collectInstantWithdrawFunds` occurs in practice and whether `requestInstantWithdraw` is gated to the post-start delay window; the finding holds if either partial funding or post-decision request insertion is reachable, which the strategy-side code structure (aggregate `pendingInstantWithdraws` vs per-user full payout) makes possible.
