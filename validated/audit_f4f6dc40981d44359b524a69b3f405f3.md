### Title
Permissionless `lending_pool_emissions_deposit` allows front-run/back-run share dilution attack against honest depositors - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
`lending_pool_emissions_deposit` transfers same-mint "emissions" tokens directly into a bank's `liquidity_vault` and immediately re-prices `asset_share_value` for **all** existing depositors, without minting new shares. Because the call is permissionless, carries no deposit lock-up, and `lending_account_deposit`/`lending_account_withdraw` have no time delay, an attacker can front-run a pending (or self-triggered) emissions deposit with a large `lending_account_deposit`, let the emissions inflate `asset_share_value` over the attacker's newly-minted shares, and immediately back-run with a withdrawal — capturing a disproportionate slice of the emissions that were intended for the bank's long-term depositors. This is the exact bug class described in the NFTX `XTokenUpgradeable`/`distribute` report: instantaneous share-price inflation combined with unrestricted deposit/withdraw timing.

### Finding Description
`lending_pool_emissions_deposit` is declared and documented as permissionless: [1](#0-0) 

It accrues interest, transfers `amount` tokens into the vault, and re-derives `asset_share_value` as `(total_assets + amount) / total_asset_shares` — i.e., it dilutes the reward across whatever shares happen to exist **at the moment the instruction executes**, without minting shares to the funder: [2](#0-1) 

This is confirmed by the test suite, which explicitly checks that `total_asset_shares` is unchanged while `asset_share_value` jumps by the ratio `(1 + emissions_deposit/total_deposited)`: [3](#0-2) [4](#0-3) 

There is no time-lock, minimum holding period, or share-based vesting on `lending_account_deposit` or `lending_account_withdraw` — deposits mint shares immediately at the then-current `asset_share_value`, and withdrawals burn shares immediately at the then-current `asset_share_value`: [5](#0-4) [6](#0-5) 

Combined, this reproduces the NFTX `XTokenUpgradeable`/`NFTXSimpleFeeDistributor.distribute` pattern: (1) a permissionless function injects a lump sum of value into a shared pool, (2) that value is distributed proportionally to whoever holds shares at that exact instant, and (3) there is no delay preventing a large depositor from entering right before the injection and exiting right after.

Note this differs from marginfi's normal interest-accrual mechanism, which is time-based and compounds gradually per `bank.accrue_interest` (see `README.md` "Interest Accumulation" section) — that mechanism is not exploitable this way because the yield accrues continuously over elapsed time rather than as an instantaneous lump-sum injection. `lending_pool_emissions_deposit` is a distinct, newer code path that reintroduces exactly the lump-sum/instant-repricing pattern the interest-accrual design otherwise avoids.

### Impact Explanation
An attacker monitoring the mempool/leader schedule for an upcoming `lending_pool_emissions_deposit` call (which could be sent by the protocol team, a partner, or even the attacker's own bot in coordination with a known rewards schedule) can:
1. Deposit a large amount of the bank's underlying asset via `lending_account_deposit`, minting shares at the pre-emissions `asset_share_value`.
2. Let the `lending_pool_emissions_deposit` transaction land, which raises `asset_share_value` proportionally across all outstanding shares, including the attacker's freshly minted ones.
3. Immediately withdraw via `lending_account_withdraw`/`withdraw_all`, redeeming shares at the new, inflated `asset_share_value`.

The attacker earns a share of the emissions proportional to capital deployed but held for a negligible duration, diluting the return honest, long-term depositors were meant to receive from the same emissions injection. This is a direct value-redirection/financial-loss issue against existing depositors of the affected bank, scaling with the attacker's available capital and the size of the emissions deposit.

### Likelihood Explanation
- The function is explicitly permissionless (`depositor: Signer<'info>`, no admin/role check) and callable by anyone at any time.
- There is no deposit lock-up or minimum staking duration for `lending_account_deposit`/`lending_account_withdraw`.
- The attack requires no flash loan (unlike some frontrunning attacks) — a well-capitalized actor can simply hold funds ready and react to observed `lending_pool_emissions_deposit` transactions, or, in the worst case, learn of them from off-chain communication about scheduled emissions.
- Since this instruction is new/documented in `patch-note-drafts/patch-notes-0.1.9.md` as intended functionality for distributing emissions/rewards, it is reasonable to expect it will be invoked periodically and predictably (e.g., after harvesting Kamino/Drift rewards), giving attackers a target to front-run.
- Mitigating factors: the attacker must have significant capital relative to total bank deposits to meaningfully capture value (similar capital-intensity caveat noted in the original NFTX report), and normal deposit/withdraw slippage/fees (if any) reduce profitability.

### Recommendation
- Require deposits to be present for a minimum bonding period (or apply the emissions increase pro-rata to a snapshot of balances taken before the deposit transaction, rather than to balances current when the CPI executes).
- Alternatively, mint new shares to the emissions depositor rather than diluting `asset_share_value` directly, or restrict `lending_pool_emissions_deposit` to a trusted role (e.g., `admin`/`delegate_emissions_admin`) executed via a delayed/timelocked mechanism so it cannot be front-run by opportunistic depositors.
- Consider a withdrawal cooldown/timelock (as recommended in the original NFTX report) so that deposits cannot be immediately withdrawn after a lump-sum reward injection.

### Proof of Concept
Given the existing test `emissions_same_bank_deposit_updates_asset_share_value` as a template: [7](#0-6) 

Exploit scenario:
1. Two honest depositors A (40 USDC) and B (60 USDC) deposit into `usdc_bank`, minting shares at `asset_share_value = 1.0`. Total assets = 100, total shares = 100.
2. Attacker observes (or triggers) a pending `lending_pool_emissions_deposit(50)` transaction and front-runs it with `lending_account_deposit(1,000,000)` (a much larger deposit), minting `1,000,000` shares at `asset_share_value ≈ 1.0`.
3. The 50-USDC emissions deposit executes: `asset_share_value` is recomputed as `(total_assets + 50) / total_shares`, inflating the attacker's holding (now the vast majority of shares) by nearly the full 50-token benefit intended for A and B.
4. Attacker immediately calls `lending_account_withdraw`/`withdraw_all`, redeeming shares at the new, inflated `asset_share_value`, extracting most of the 50-token emissions while having held the position for effectively zero time — the same mechanic and outcome documented in the report's Bob/Alice example against `XTokenUpgradeable`.

async fn emissions_same_bank_deposit_updates_asset_share_value() -> anyhow::Result<()> {

    let depositor_b = test_f.create_marginfi_account().await;

    let depositor_b_usdc = test_f.usdc_mint.create_token_account_and_mint_to(60).await;

        .try_bank_deposit(

            usdc_bank,

        )

        .try_bank_deposit(
            depositor_b_usdc.key,
            usdc_bank,
            depositor_b_amount as f64,
            None,
        )
        .await?;

    let bank_before = usdc_bank.load().await;
    let shares_before = I80F48::from(bank_before.total_asset_shares);
    let share_value_before = I80F48::from(bank_before.asset_share_value);

    let liquidity_vault_before =
        TokenAccountFixture::fetch(test_f.context.clone(), bank_before.liquidity_vault)
            .await
            .balance()
            .await;

    let emissions_deposit = 50;
    usdc_bank
        .try_emissions_deposit(native!(emissions_deposit, "USDC"), emissions_funding.key)
        .await?;

    let bank_after = usdc_bank.load().await;
    let shares_after = I80F48::from(bank_after.total_asset_shares);
    let share_value_after = I80F48::from(bank_after.asset_share_value);

    let liquidity_vault_after =
        TokenAccountFixture::fetch(test_f.context.clone(), bank_after.liquidity_vault)
            .await
            .balance()
            .await;

    let asset_shares_value_multiplier =
        1.0 + emissions_deposit as f64 / (depositor_a_amount + depositor_b_amount) as f64;

    );
    assert_eq!(I80F48::from(bank_after.emissions_remaining), I80F48::ZERO);
