### Title
Anyone can set `unscaledApr`/`lastApr` while `idleCDO` is unset, corrupting epoch interest accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.setApr` skips its caller check when `idleCDO == address(0)`, the same bug class as the reported `onlyPolicyCenter` bypass in `CoverRightToken.sol`. During the deployment window between `initialize` and `setWhitelistedCDO`, any EOA can call `setApr`, `setAprs`, or `setAprsWithBuffer` and write arbitrary `lastApr`/`unscaledApr` values, which are the inputs the CDO uses for `expectedEpochInterest`, the APR0 withdraw flow, and `prepareStopEpochWithApr0`.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol:225-235`:

```solidity
function setApr(uint256 _apr) public {
  address _cdo = idleCDO;
  // if cdo is not yet set we skip the check (this can happen only during the setup)
  if (_cdo != address(0)) {
    if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
  }
  uint256 _maxApr = maxApr;
  if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
  lastApr = _apr;
}
```

While `idleCDO` is zero, `lastApr` can be set up to `maxApr` (default `DEFAULT_MAX_APR = 20e18`, i.e. a 2000% scaled APR). Worse, `setAprs` and `setAprsWithBuffer` write `unscaledApr` **unconditionally with no cap** before delegating to `setApr`:

```solidity
function setAprs(uint256 _unscaledApr, uint256 _apr) external {
  unscaledApr = _unscaledApr;   // uncapped, set even if setApr reverts? no — reverts propagate
  setApr(_apr);
}
```

`unscaledApr` is security-critical in two places:

1. `requestWithdraw` routes users into the APR0 accounting bucket only when `unscaledApr == 0` (`IdleCreditVault.sol:285`). A wrong nonzero `unscaledApr` on a vault intended to run at APR 0 silently mis-routes requests into normal `withdrawsRequests` accounting.
2. `prepareStopEpochWithApr0` reverts with `NotAllowed` when `apr0TotalPrincipal != 0 && unscaledApr != 0` (`IdleCreditVault.sol:506-508`). If an attacker seeds a mismatched `unscaledApr` during setup before the CDO wires itself, the honest epoch APR setter eventually overwrites it, but any request lifecycle recorded under the wrong flag leaves the per-epoch buckets (`apr0Users`, `withdrawsRequestsByEpoch`, `apr0TotalPrincipal`) inconsistent with the intended mode.

`lastApr` is returned by `getApr()` and consumed by the CDO to compute `expectedEpochInterest` and tranche interest splits. A pre-wiring attacker-set `lastApr` of up to 2000% persists until the first legitimate `setAprsWithBuffer` call, so if `startEpoch` runs before the manager corrects it, the first epoch's interest expectation, AA/BB split, and any loss-vs-interest classification in `stopEpoch`/`stopEpochWithDuration` are computed against an attacker-chosen rate.

### Impact Explanation
An unprivileged attacker can, during the setup window, either (a) inflate `lastApr` to `maxApr` so the first epoch's `expectedEpochInterest` and AA/BB interest attribution are computed on a 2000% rate, causing a fabricated shortfall at `stopEpoch` that is socialized BB-first as a loss to honest tranche holders, or (b) poison `unscaledApr` so APR0-mode request accounting and `prepareStopEpochWithApr0` revert or mis-settle, breaking the "one receipt one payout" invariant for withdraw receipts. The attacker needs no role, no deposit, and no KYC — only a transaction landed between `initialize` and `setWhitelistedCDO`. Loss magnitude is bounded by the first epoch's interest basis but can equal the full realized epoch interest misattributed between tranche classes.

### Likelihood Explanation
Low-to-moderate. The window is short (deployment wiring), but factories/EOA deployers that do not atomically call `setWhitelistedCDO` in the same transaction as `initialize` leave it open to any mempool observer. The pattern is identical to the accepted-risk Degis finding: a "skip check when unset" guard on a function controlling a critical parameter. Once the CDO is wired, the bug is unreachable, matching the low likelihood of the original report.

### Recommendation
Do not silently skip the caller check. Revert when `idleCDO == address(0)` unless the caller is `owner()` or `manager`, e.g.:

```solidity
if (_cdo == address(0)) {
  if (msg.sender != owner() && msg.sender != manager) revert NotAllowed();
} else if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
```

Alternatively, require `setWhitelistedCDO` to be called atomically in the same transaction as `initialize` (e.g. via the factory), eliminating the open window entirely.

### Proof of Concept

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract SetAprUnsetCDOTest is Test {
  IdleCreditVault vault;
  address attacker = makeAddr("attacker");

  function setUp() public {
    // Deploy proxy + implementation, run initialize() but do NOT call setWhitelistedCDO yet
    vault = IdleCreditVault(address(deployProxy()));
    // vault.initialize(underlying, owner, manager, borrower, "Borrower", 5e18);
  }

  function testAnyoneCanSetAprBeforeCDOWired() public {
    assertEq(vault.idleCDO(), address(0));

    vm.prank(attacker);
    // capped only by maxApr (default 20e18): scaled APR set to 2000%
    vault.setApr(20e18);
    assertEq(vault.lastApr(), 20e18);
    assertEq(vault.getApr(), 20e18);
  }

  function testAnyoneCanPoisonUnscaledApr() public {
    vm.prank(attacker);
    // unscaledApr is uncapped; flips vault out of APR0 mode and breaks
    // prepareStopEpochWithApr0 once apr0TotalPrincipal != 0
    vault.setAprs(1, 0);
    assertEq(vault.unscaledApr(), 1);
  }
}
```
