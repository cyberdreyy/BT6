### Title
`secp256k1_recover` syscall leaves the output buffer untouched on invalid-signature errors, enabling stale-memory signature bypass in caller programs - (File: `syscalls/src/lib.rs`)

### Summary
The `SyscallSecp256k1Recover` builtin syscall mirrors the exact bug class described in the Vyper `ecrecover` advisory (CVE-2023-37902): on any input validation failure (bad hash, bad recovery id, bad signature, or a signature that fails to recover a key), the syscall returns a non-zero error code but does **not** write anything into the caller-supplied `result` buffer. Any BPF program that checks only the recovered-key bytes (and not the syscall's u64 return code) can be tricked into accepting an invalid/forged secp256k1 signature if it previously placed attacker- or program-controlled data at that memory location.

### Finding Description
`SyscallSecp256k1Recover` validates the mapping of the output buffer purely for "error compatibility with old code" and then, on each of the four failure branches, returns early with `Ok(Secp256k1RecoverError::…)` without ever touching `result`: [1](#0-0) 

Only the success path calls `translate_mut!` again and performs `result.write_copy_of_slice(&public_key[1..65])`: [2](#0-1) 

This is architecturally identical to the go-ethereum `ecrecover` precompile behavior cited in the report: the precompile output buffer is left unmodified when signature recovery fails, and the caller (compiler-generated code, or here, a BPF program) is responsible for checking the explicit success/failure signal before trusting the buffer contents. The Vyper compiler bug was that the *generated code* forgot to check that signal and instead trusted stale buffer contents (commonly the `PERMIT_TYPEHASH` immutable that happened to sit at that memory address). The exact same hazard exists for any Solana/SBF program author (or any SDK helper) that calls `sol_secp256k1_recover` and only compares the resulting 64-byte "public key" against an expected value without first checking that the syscall's u64 return value is `0` (`SUCCESS`).

Unlike the EVM's fixed memory-location model, on Solana the `result` buffer address is fully caller-chosen (typically stack or heap memory inside the calling BPF program), so it is even easier for a real-world program to reuse a buffer that still contains a previously-computed "known good" public key, an immutable value, or attacker-influenced account data right before invoking `sol_secp256k1_recover` — exactly the pattern flagged in the original advisory ("a contract could have unexpected behavior... if an immutable representing a real address... was read right before the ecrecover operation").

### Impact Explanation
Any onchain program is affected if it uses `sol_secp256k1_recover` (directly, or via a wrapper such as the `solana_program::secp256k1_recover` helper) and does not strictly check the returned error code before comparing/trusting the output buffer. Because the syscall is reachable from any deployed program invoked by an ordinary user transaction, a program with this pattern could be tricked into accepting a forged/invalid signature (e.g., in a permit-style authorization, a bridge/relayer verification, or a custom multisig scheme), leading to unauthorized state mutation or fund movement — matching the "concrete unauthorized fund or state mutation" bar for this scan.

### Likelihood Explanation
This is not a flaw an attacker can trigger purely at the syscall/runtime layer in isolation — it requires a calling program that (a) reuses a buffer with attacker/program-influenced prior contents as the `result` argument and (b) fails to check the syscall's non-zero error return. This is a real, previously-seen anti-pattern in ecrecover-style code (as documented by the very Vyper advisory used as the report source), and Solana's on-chain test/demo code for this syscall does check the return code correctly, showing this is a known but easy-to-miss caller obligation rather than a documented, enforced runtime guarantee. Likelihood is therefore dependent on downstream program correctness rather than the syscall itself, but the runtime provides no mitigation (e.g., zeroing the buffer on failure) the way some other security-sensitive APIs do.

### Recommendation
Have `SyscallSecp256k1Recover` explicitly zero (or otherwise clear to a value that can never validly recover, e.g., all-zero) the `result` buffer on every failure branch before returning the error code, removing any possibility that stale caller memory is misinterpreted as a valid recovered public key. This mirrors the eventual Vyper fix (ensuring the output register/memory cannot silently retain unrelated data across a failed `ecrecover`).

### Proof of Concept
1. A BPF program stores the "expected" 32/64-byte public key or address at a fixed offset on its stack/heap (e.g., loaded from an account or hardcoded), for use immediately after calling `sol_secp256k1_recover` into that same buffer.
2. An attacker submits an instruction with a syntactically valid but cryptographically invalid signature/hash/recovery-id combination.
3. `SyscallSecp256k1Recover` hits one of the `Ok(Secp256k1RecoverError::…)` early-return branches shown in `syscalls/src/lib.rs:952-968`, leaving the `result_addr` buffer unchanged (still containing the pre-populated expected key).
4. If the calling program only does `if recovered_pubkey == expected_pubkey` and does not check that the syscall returned `0`, the check spuriously passes, exactly analogous to the Vyper `assert ecrecover(...) == _owner` bypass.
