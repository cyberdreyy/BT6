## Analog Found

The reported pattern — a per-user mapping of a single "last action" timestamp that gets **overwritten on every new deposit**, forcing earlier deposits to inherit the lock window of the latest one — has a direct analog in `ProvisionerV2`.

### Root cause mapping

In the reported swappool bug, `latestDepositAtBlockNo[msg.sender] = block.number` is overwritten on every deposit, extending the insurance timelock for previously-deposited funds. The same structural flaw exists in `ProvisionerV2._syncDeposit`, which sets a single refund-lock timestamp keyed only by receiver address: [1](#0-0) 

Specifically: [2](#0-1) 

`userUnitsRefundableUntil[receiver]` is a single mapping slot per user, not per-deposit. Every call to `deposit()` or `mint()` overwrites it with `block.timestamp + depositRefundTimeout` — a value monotonically ≥ the previous one — regardless of the receiver's existing (already unlockable) position.

This lock is enforced in two places, mirroring the original report's insurance-period guard:
- Directly in `redeem`/`withdraw`: [3](#0-2) 
- Indirectly via `MultiDepositorVault._update`, which blocks any unit transfer (including the `safeTransferFrom` used inside `requestRedeem`) while locked: [4](#0-3) 

### Critical difference from the original report

Crucially, `deposit()`/`mint()` accept an **arbitrary `receiver`** parameter that is only checked for non-zero via `_requireValidReceiver`, not for caller/receiver equality: [5](#0-4) 

This means any third party (not just the depositor themself) can call `deposit(token, tinyTokensIn, minUnitsOut, victim)` and re-lock the victim's entire unit balance by resetting `userUnitsRefundableUntil[victim]` to a fresh, later timestamp — indefinitely, by repeating this every `depositRefundTimeout` window. Because the lock also blocks `requestRedeem`'s `safeTransferFrom` step (via the vault's `_update` hook), a griefer can perpetually freeze a victim's already-owned, previously-unlockable vault units without their consent, at the cost of only a trivial deposit amount plus gas.

This is a stronger version of the audited swap-pool issue: not merely "serious depositors wait longer," but an **unauthorized third party can indefinitely freeze a victim's redeemable units** by repeatedly depositing tiny amounts on the victim's behalf.

### Title
Arbitrary receiver in `ProvisionerV2.deposit`/`mint` allows griefer to indefinitely re-lock a victim's already-vested vault units via the overwritten `userUnitsRefundableUntil` mapping - (File: v3/src/core/ProvisionerV2.sol)

### Summary
`ProvisionerV2._syncDeposit` stores a single refund-lock expiry per receiver address in `userUnitsRefundableUntil`, overwriting it on every sync deposit regardless of the receiver's existing lock status. Since `deposit`/`mint` allow specifying an arbitrary `receiver`, any account can repeatedly deposit minimal amounts on behalf of a victim to continuously extend the victim's lock, freezing transfers and redemptions of the victim's full unit balance indefinitely.

### Finding Description
`deposit(token, tokensIn, minUnitsOut, receiver)` and `mint(...)` only validate that `receiver != address(0)` via `_requireValidReceiver`, with no check that `msg.sender == receiver` or any receiver consent/approval. Both call `_syncDeposit`, which unconditionally does `userUnitsRefundableUntil[receiver] = block.timestamp + depositRefundTimeout`, clobbering any prior expiry. `redeem`/`withdraw` require `userUnitsRefundableUntil[msg.sender] < block.timestamp`, and `MultiDepositorVault._update` blocks any unit transfer (used by `requestRedeem`'s pull and by plain ERC20 transfers) while `areUserUnitsLocked` is true. An attacker can call `deposit` with a minimal `tokensIn` and `receiver = victim` right before the victim's existing lock expires, resetting the lock to a new future timestamp — repeating this forever fully freezes the victim's unit balance from redemption and transfer.

### Impact Explanation
Freezing of user funds (vault units representing deposited assets) for an indefinite duration at negligible cost to the attacker, matching a Medium "temporary freezing of funds" Immunefi impact, escalatable to indefinite/permanent freezing since the griefer can repeat the attack cheaply forever.

### Likelihood Explanation
High feasibility: the attack requires only that sync deposits are enabled for some token, a small token balance, and knowledge of a victim address holding vault units — no privileged role, oracle manipulation, or governance action needed.

### Recommendation
Track refund-lock windows per deposit (e.g., by hash/id as in the referenced report's recommendation) rather than a single mapping per receiver, and/or restrict `deposit`/`mint`'s `receiver` parameter so a caller cannot arbitrarily extend the lock of a `receiver` that is not `msg.sender` (e.g., require receiver opt-in via `depositReceiverApprovals`, already present for other purposes) so the refund lock only ever extends the depositor's own new funds and never previously-vested balances.

### Proof of Concept
Foundry fork steps:
1. Deploy/attach to `ProvisionerV2` + `MultiDepositorVault` with sync deposits enabled for `token`; set `depositRefundTimeout = T`.
2. `victim` calls `deposit(token, X, minOut, victim)` at `t0`; assert `userUnitsRefundableUntil[victim] == t0 + T`.
3. Warp to `t0 + T - 1` (still locked). `attacker` (unrelated address, holding 1 wei of `token`) calls `deposit(token, 1, 0, victim)`.
4. Assert `userUnitsRefundableUntil[victim]` is now `(t0+T-1) + T`, strictly greater than before, extending the lock.
5. Warp to original expiry `t0 + T`; assert `victim`'s call to `redeem`/transfer of their original units still reverts with `Aera__UnitsLocked`, proving the lock was extended by a third party against the victim's will.
6. Repeat step 3 in a loop to show the freeze can be perpetuated indefinitely.

    /// @notice Handles a synchronous deposit, records the deposit hash, and enters the vault
    /// @dev Reverts if the deposit hash already exists. Sets the refundable period for the user
    /// @param token The ERC20 token to deposit
    /// @param tokenAmount The amount of tokens to deposit
    /// @param unitAmount The amount of vault units to mint for the user
    /// @param receiver The address receiving the minted units
    function _syncDeposit(IERC20 token, uint256 tokenAmount, uint256 unitAmount, address receiver) internal {
        uint256 refundableUntil = block.timestamp + depositRefundTimeout;
        bytes32 depositHash = _getDepositHash(msg.sender, receiver, token, tokenAmount, unitAmount, refundableUntil);

        // Requirements: deposit hash is not set
        require(!syncDepositHashes[depositHash], Aera__HashCollision());
        // Effects: set hash as used
        syncDepositHashes[depositHash] = true;

        // Effects: set receiver's refundable until timestamp
        userUnitsRefundableUntil[receiver] = refundableUntil;

        // Interactions: enter vault
        IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).enter(msg.sender, token, tokenAmount, unitAmount, receiver);

        // Log deposit event
        emit Deposited(msg.sender, receiver, token, tokenAmount, unitAmount, depositHash);
    }
