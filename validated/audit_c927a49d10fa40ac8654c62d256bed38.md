### Title
`get_confirmed_signatures_for_address2` forces full decode of attacker-chosen dense blocks via `before`/`until` resolution - ([File: ledger/src/blockstore.rs])

### Summary
`Blockstore::get_confirmed_signatures_for_address2` resolves the `before` and `until` signature parameters by calling `get_block_signatures_rev`, which fully deserializes the entire target slot's block (`get_complete_block`) and reverses its transaction list just to locate one signature's position. This per-call cost scales with the size of whichever slot the attacker-supplied `before`/`until` signature happens to live in, not with the `limit` parameter or any other request-bounded value, and it is paid up to twice per call (once for `before`, once for `until`).

### Finding Description
In `get_confirmed_signatures_for_address2`, both the `before` and `until` resolution branches call `self.get_block_signatures_rev(slot)` after locating the slot via `get_transaction_status`: [1](#0-0) [2](#0-1) 

`get_block_signatures_rev` itself calls `get_complete_block(slot, false)`, which reads and deserializes every entry/transaction in the block (via `do_get_complete_block_with_components` → `get_slot_components_with_shred_info` → `build_versioned_confirmed_block` → `map_transactions_to_statuses`), then reverses the full transaction list and filters/collects all signatures, purely to find the position of one target signature: [3](#0-2) 

The full block decode path is the same one used for `getBlock`: [4](#0-3) [5](#0-4) 

The entrypoint is the JSON-RPC `getSignaturesForAddress` method, `JsonRpcRequestProcessor::get_signatures_for_address`, which passes `before`/`until` straight through to the blockstore call: [6](#0-5) 

Parameter validation only bounds `limit` (`MAX_GET_CONFIRMED_SIGNATURES_FOR_ADDRESS2_LIMIT`); it performs no validation or cost bound related to the density of the slot containing `before`/`until`: [7](#0-6) 

Because a real Solana slot can contain thousands of transactions (bounded only by block compute-unit/size limits, not by this RPC's own guards), an attacker who knows (or has previously landed) a signature in a maximally packed slot can supply that signature as `before` and/or `until`. The single-call cost of resolving that parameter (full block fetch, deserialization, sanitize of every transaction, and a full reversal) scales with that slot's transaction count — an attacker-chosen or attacker-known quantity completely decoupled from the `limit` parameter that is supposed to bound the cost of the RPC call. Supplying both a `before` signature from one dense slot and an `until` signature from another dense slot doubles this cost within a single request.

### Impact Explanation
This is unbounded per-call CPU/memory cost for a single low-rate RPC call: the actual work done to resolve `before`/`until` is proportional to attacker-chosen or attacker-known block density (potentially thousands of transactions to decode/sanitize/reverse), not to any RPC-level bound such as `limit`. This falls under the "unbounded cost for a single low-rate call" bounty category permitted by the rules, since it requires only one `getSignaturesForAddress` call from a single unprivileged client.

### Likelihood Explanation
Feasibility is high: mainnet blocks routinely contain large numbers of transactions, so an attacker doesn't even need to control block production — they only need to identify (via `getBlock`/`getSignaturesForAddress` results, explorers, or their own densely-packed transaction) a signature located in a heavily populated slot. The attack is trivially repeatable and can be doubled by choosing dense slots for both `before` and `until` in the same call, all within the single-call-per-`CLUSTER_SLOT_TIME_TARGET/2` constraint.

### Recommendation
Avoid full block decode+reverse just to locate a signature's position within a slot. Options:
1. Use the existing transaction-index information (`get_transaction_status` already returns slot; if it can also return the transaction's index within the slot, or if the `AddressSignatures` column family already stores `transaction_index`) to determine the truncation/split point without materializing and reversing the entire block's transaction list.
2. Add a lightweight signatures-only accessor that reads only signature data for a slot rather than fully deserializing/sanitizing each transaction and building a `VersionedConfirmedBlock`, reducing cost from full transaction decode to a cheaper index/signature lookup.

### Proof of Concept
Integration test outline (in `ledger/src/blockstore/tests.rs` or a new benchmark):
1. Populate one slot ("sparse") with a single transaction touching `address`, and another slot ("dense") with the maximum practical number of transactions (e.g., thousands), including one transaction touching `address`, recording its signature as `dense_before_sig` and `dense_until_sig` from a second densely packed slot.
2. Call `blockstore.get_confirmed_signatures_for_address2(address, highest_slot, Some(sparse_sig), None, 1)` and measure wall-clock/CPU time.
3. Call `blockstore.get_confirmed_signatures_for_address2(address, highest_slot, Some(dense_before_sig), Some(dense_until_sig), 1)` and measure wall-clock/CPU time.
4. Assert that case (3)'s cost scales roughly linearly with the transaction count of the dense slots (e.g., is orders of magnitude larger than case (2) despite an identical `limit`), demonstrating the cost is governed by attacker-chosen block density rather than by `limit` or any other request-scoped bound — i.e., no early-exit optimization exists in `get_block_signatures_rev`/`get_complete_block` for this use case.

    fn get_block_signatures_rev(&self, slot: Slot) -> Result<Vec<Signature>> {
        let block = self.get_complete_block(slot, false).map_err(|err| {
            BlockstoreError::Io(IoError::other(format!("Unable to get block: {err}")))
        })?;

        Ok(block
            .transactions
            .into_iter()
            .rev()
            .filter_map(|transaction_with_meta| {
                transaction_with_meta
                    .transaction
                    .signatures
                    .into_iter()
                    .next()
            })
            .collect())
    }

fn verify_and_parse_signatures_for_address_params(
    address: String,
    before: Option<String>,
    until: Option<String>,
    limit: Option<usize>,
) -> Result<(Pubkey, Option<Signature>, Option<Signature>, usize)> {
    let address = verify_pubkey(&address)?;
    let before = before
        .map(|ref before| verify_signature(before))
        .transpose()?;
    let until = until.map(|ref until| verify_signature(until)).transpose()?;
    let limit = limit.unwrap_or(MAX_GET_CONFIRMED_SIGNATURES_FOR_ADDRESS2_LIMIT);

    if limit == 0 || limit > MAX_GET_CONFIRMED_SIGNATURES_FOR_ADDRESS2_LIMIT {
        return Err(Error::invalid_params(format!(
            "Invalid limit; max {MAX_GET_CONFIRMED_SIGNATURES_FOR_ADDRESS2_LIMIT}"
        )));
    }
    Ok((address, before, until, limit))
}
