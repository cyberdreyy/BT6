### Title
Global Bridge Transfer Limiter Can Be Exhausted by Any Large Token Holder, Blocking All Other ETH→Sui Claims for Up to 24 Hours - (File: crates/sui-framework/packages/bridge/sources/limiter.move)

### Summary

The Sui native bridge enforces a global 24-hour rolling USD limit on the ETH→Sui route via `bridge::limiter`. Any ordinary bridge user who holds sufficient ETH (~$5M on mainnet) can exhaust this global limit in a single claim transaction, causing all other users' approved ETH→Sui transfers to fail with `TokenTransferLimitExceed` for the remainder of the 24-hour window. The attacker can then bridge their tokens back to Ethereum (the Sui→ETH direction has no limiter) and repeat the attack every 24 hours at the cost of gas fees only.

### Finding Description

The `TransferLimiter` in `bridge::limiter` tracks a rolling 24-hour USD window per `BridgeRoute`. For mainnet, the only seeded limit is the route `eth_mainnet() → sui_mainnet()` at $5,000,000 USD: [1](#0-0) 

This limit is **global** — it is shared across all users bridging ETH→Sui. There is no per-account tracking. The limit is checked and recorded atomically inside `claim_token_internal` when a user claims their approved transfer on Sui: [2](#0-1) 

When the limit is exceeded, the function emits `TokenTransferLimitExceed` and returns `None` without aborting, leaving the `BridgeRecord` with `claimed = false`. The transfer is silently blocked and must be retried after the window resets.

The Sui→ETH direction has **no limiter at all** — `initial_transfer_limits()` seeds no route for `sui_mainnet() → eth_mainnet()`, and calling `check_and_record_sending_transfer` on that route aborts with `ELimitNotFoundForRoute`: [3](#0-2) 

This asymmetry enables the cycling attack.

**Attack sequence:**

1. Attacker deposits ~$5M worth of ETH on Ethereum via `SuiBridge.bridgeERC20`/`bridgeETH`.
2. Bridge authorities sign and submit `approve_token_transfer` on Sui.
3. Attacker calls `claim_token` or `claim_and_transfer_token` on Sui — this succeeds and records the full $5M against the 24-hour window.
4. All other users' pending approved ETH→Sui transfers now fail with `TokenTransferLimitExceed` for up to 24 hours.
5. Attacker calls `send_token` on Sui to bridge their tokens back to Ethereum — **no limiter is checked on this path** (`send_token_internal` only checks pause state and route validity, not the limiter).
6. After bridge processing, attacker recovers their ETH on Ethereum.
7. Repeat at the next 24-hour window reset.

The outbound path (`send_token` / `send_token_internal`) confirms no limiter is applied: [4](#0-3) 

### Impact Explanation

All legitimate users with approved ETH→Sui bridge transfers are unable to claim their tokens for up to 24 hours per attack cycle. Their funds are not permanently lost — the `BridgeRecord` remains with `claimed = false` and can be retried — but the bridge's claim functionality is rendered unavailable for the entire user base during the window. The attacker recovers their capital with only gas costs, enabling indefinite repetition.

For V1 messages (no timestamp), the block lasts the full 24-hour window. For V2 messages, the 48-hour maturity bypass (`bypass_limiter = clock.timestamp_ms() > timestamp + 48 * 3600000`) provides eventual relief, but only after 48 hours — meaning two full 24-hour windows can be disrupted per deposit: [5](#0-4) 

### Likelihood Explanation

The attack requires holding ~$5M USD worth of ETH, which is a high but not unrealistic capital requirement for a motivated attacker (e.g., a competing bridge, a short-seller, or a protocol adversary). The execution is straightforward: one deposit transaction on Ethereum, one claim on Sui, one return bridge transaction. Gas costs on both chains are the only recurring expense. The attack is repeatable every 24 hours indefinitely.

### Recommendation

1. **Per-account sub-limits**: Track per-sender contribution to the rolling window so no single account can exhaust the global limit alone.
2. **Minimum fee on bridge deposits**: Introduce a small USD-denominated fee on deposits (analogous to Chainlink CCIP's bps fee) to make repeated cycling economically costly.
3. **Raise the limit or make it dynamic**: The current $5M hardcoded limit is reachable by a single large holder. A higher limit or a dynamic limit based on recent bridge volume reduces the attack surface.
4. **Apply the limiter symmetrically**: Consider applying a limit on the Sui→ETH direction as well, so the attacker cannot freely cycle capital back without cost.

public(package) fun check_and_record_sending_transfer<T>(
    self: &mut TransferLimiter,
    treasury: &BridgeTreasury,
    clock: &Clock,
    route: BridgeRoute,
    amount: u64,
): bool {
    // Create record for route if not exists
    if (!self.transfer_records.contains(&route)) {
        self
            .transfer_records
            .insert(
                route,
                TransferRecord {
                    hour_head: 0,
                    hour_tail: 0,
                    per_hour_amounts: vector[],
                    total_amount: 0,
                },
            )
    };
    let record = self.transfer_records.get_mut(&route);
    let current_hour_since_epoch = current_hour_since_epoch(clock);

    record.adjust_transfer_records(current_hour_since_epoch);

    // Get limit for the route
    let route_limit = self.transfer_limits.try_get(&route);
    assert!(route_limit.is_some(), ELimitNotFoundForRoute);
    let route_limit = route_limit.destroy_some();
    let route_limit_adjusted = (route_limit as u128) * (treasury.decimal_multiplier<T>() as u128);

    // Compute notional amount
    // Upcast to u128 to prevent overflow, to not miss out on small amounts.
    let value = (treasury.notional_value<T>() as u128);
    let notional_amount_with_token_multiplier = value * (amount as u128);

    // Check if transfer amount exceed limit
    // Upscale them to the token's decimal.
    if (
        (record.total_amount as u128)
            * (treasury.decimal_multiplier<T>() as u128)
            + notional_amount_with_token_multiplier > route_limit_adjusted
    ) {
        return false
    };

    // Now scale down to notional value
    let notional_amount =
        notional_amount_with_token_multiplier / (treasury.decimal_multiplier<T>() as u128);
    // Should be safe to downcast to u64 after dividing by the decimals
    let notional_amount = (notional_amount as u64);

    // Record transfer value
    let new_amount = record.per_hour_amounts.pop_back() + notional_amount;
    record.per_hour_amounts.push_back(new_amount);
    record.total_amount = record.total_amount + notional_amount;
    true
}

fun send_token_internal<T>(
    inner: &mut BridgeInner,
    target_chain: u8,
    token: Coin<T>,
    message: BridgeMessage,
) {
    assert!(!inner.paused, EBridgeUnavailable);
    assert!(chain_ids::is_valid_route(inner.chain_id, target_chain), EInvalidBridgeRoute);

    // burn / escrow token, unsupported coins will fail in this step
    inner.treasury.burn(token);

    // Store pending bridge request
    inner
        .token_transfer_records
        .push_back(
            message.key(),
            BridgeRecord {
                message,
                verified_signatures: option::none(),
                claimed: false,
            },
        );
}
