### Title
Confirmations from removed multisig members remain counted toward `num_confirmations`, allowing a request to execute with fewer live-member approvals than the threshold - (File: `multisig2/src/lib.rs`)

### Summary
`DeleteMember` (in `multisig`, `DeleteKey`) only purges *requests created by* the removed member, but never scrubs that member's *confirmations* recorded on other still-pending requests. `confirm()` and `assert_valid_request()` never re-validate that the accumulated confirmations still belong to current members, so a confirmation cast by an account/key that is later removed continues to count toward `self.num_confirmations` when the request is eventually finalized.

### Finding Description
`add_request`/`confirm` accumulate a `HashSet` of member identifiers in `self.confirmations[request_id]`, and a request executes once `confirmations.len() + 1 >= self.num_confirmations` [1](#0-0) . When a member is deleted via `MultiSigRequestAction::DeleteMember`, `delete_member` removes only the requests whose *creator* (`r.member`) equals the deleted member, plus that member's own `num_requests_pk` entry and membership record — it does not touch `self.confirmations` entries where the removed member appears merely as a *confirmer* on someone else's still-open request [2](#0-1) . `assert_valid_request`, which gates both `confirm` and `delete_request`, only checks that the *caller* is currently a member and that the request/confirmation entries exist — it never re-checks the membership of the accounts already present in the stored confirmations set [3](#0-2) .

As a result, once enough total confirmations (stale + live) accumulate to reach `num_confirmations`, `confirm()` executes the request regardless of whether some of those confirmations originated from accounts that are no longer members [4](#0-3) . The same structural flaw exists in the legacy `multisig` contract, where `DeleteKey` filters outstanding requests only `where r.signer_pk == pk` (the request creator), not stale entries in the `confirmations` map [5](#0-4) , and `confirm`/`assert_valid_request` have the identical gap [6](#0-5) .

This breaks the equality that should hold: `confirmations counted at execution == confirmations from accounts that are members at execution time`. Instead, `confirmations counted >= confirmations from live members`, so a request can execute with strictly fewer live-member approvals than the configured `num_confirmations` threshold.

### Impact Explanation
This is the Critical-tier impact "a multisig request executed below threshold." A multisig is a custody/authorization boundary controlling `Transfer`, `AddKey`/`AddMember`, `DeleteMember`, `FunctionCall`, etc. If a stale confirmation from a removed member still counts, an attacker who is (or was, together with a colluding still-active member) able to get a confirmation recorded before being removed can later cause an under-threshold execution of arbitrary requests (including fund transfers or granting full-access keys), i.e., NEAR moved / access granted by fewer authorized parties than the contract's own configured security threshold requires.

### Likelihood Explanation
Exploitation requires only sequencing of ordinary member operations that any account entitled to submit/confirm/manage multisig requests can trigger: cast a confirmation, then (via a separate, otherwise-legitimate `DeleteMember`/`DeleteKey` request) remove that confirming member, then obtain the final confirmation from a remaining member. No special privilege beyond normal multisig participation is needed, and no code path currently prevents it — this makes it readily reachable in any deployed instance of `multisig` or `multisig2` where membership ever changes while requests are pending.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over `self.confirmations` (not just `self.requests`) and remove the deleted member's identifier from every pending request's confirmation set (recomputing/dropping-below-threshold as needed), or alternatively re-validate at `confirm()` time that every account.pubkey present in the stored confirmation set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(R1)` → `confirmations[R1] = {A}`.
3. `B` calls `confirm(R1)` → `confirmations[R1] = {A, B}` (2 < 3, not yet executed).
4. Separately, members submit and confirm a `DeleteMember{B}` request (using confirmations from `A, C, D` — unrelated to `R1`); this executes via `delete_member`, which only removes requests *created* by `B` and leaves `confirmations[R1] = {A, B}` untouched [7](#0-6) . Current members are now `{A, C, D}`.
5. `C` calls `confirm(R1)`. `assert_valid_request` passes because `C` is a current member and `R1`/its confirmation set still exist [3](#0-2) . `confirmations.len() + 1 = 3 >= num_confirmations(3)`, so `R1` executes [4](#0-3) , even though only `A` and `C` are live members who actually approved it — one fewer live-member confirmation than the configured threshold of 3.

    // removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .expect("Failed to remove existing element");
        // decrement num_requests for original request signer
        let original_signer_pk = request_with_signer.signer_pk;
        let mut num_requests = self.num_requests_pk.get(&original_signer_pk).unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_signer_pk, &num_requests);
        // return request
        request_with_signer.request
    }
