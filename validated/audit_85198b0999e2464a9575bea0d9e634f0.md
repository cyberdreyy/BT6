## Title
`BlockRejection` signature omits `reason`, `reason_code`, and `response_data` from its signed transcript, allowing a relayer to forge the rejection metadata a valid signer signature attests to - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` and `BlockRejection::sign()`/`verify()`/`recover_public_key()` derive the signed digest only from `signer_signature_hash` (plus a fixed domain separator and `chain_id`). The struct also carries `reason` (free-form `String`), `reason_code: RejectCode`, and `response_data: BlockResponseData` (which includes `reject_reason`, `failed_txid`, and tenure/read-count extend timestamps), none of which are included in the signed transcript. [1](#0-0) 

### Finding Description
`BlockRejection::hash()` builds the SIP-018 message hash from only `self.signer_signature_hash` under domain `("block-rejection", "1.0.0", chain_id)`: [2](#0-1) 

`verify()` and `recover_public_key()` both recompute this same (incomplete) hash and check the signature against it: [3](#0-2) 

But the `BlockRejection` struct that is gossiped, stored, and acted upon carries far more state than the hash covers: `reason`, `reason_code`, and `response_data` (which itself contains `reject_reason`, `failed_txid`, and the tenure/read-count extend timestamps): [4](#0-3) 

Since none of these fields are part of the signed digest, `signature` remains valid for the same `signer_signature_hash` regardless of what `reason`, `reason_code`, or `response_data` are set to. This is exactly the "omitted transcript component" pattern from the report: the verification equation (`ecdsa_verify(pubkey, hash(signer_signature_hash), signature)`) does not bind the auxiliary fields that downstream code treats as authenticated signer output.

Downstream consumers on both the node side and the signer side treat these unauthenticated fields as if they came from the signer's cryptographic attestation:

- Node-side `stackerdb_listener.rs` uses `rejected_data.reason_code` and `rejected_data.response_data.failed_txid` to accumulate per-txid weighted votes (`failed_txids`, `problematic_weight`), which are later used by `signer_coordinator.rs` to compute `temporarily_excluded_txids`/`permanently_excluded_txids` (a blocking-minority-weighted ban list for the next block-building attempt): [5](#0-4) [6](#0-5) 

- The node also authenticates the message purely via `recover_public_key()` matching the StackerDB slot's known pubkey, with no separate binding of `reason_code`/`response_data`: [7](#0-6) 

- Signer-side `handle_block_rejection` recovers the pubkey the same way, then feeds `rejection.response_data.reject_reason` into `store_and_process_block_rejection`, which drives the signer's own state-machine decision of whether/how to treat the rejection (including whether the reason permits reconsideration on a later proposal): [8](#0-7) 

Because a StackerDB chunk carrying this message can be relayed/republished by any party with visibility into the network (a signer's own chunk write is authenticated by the chunk-level secp256k1 signature over the raw bytes, but that only proves *who wrote this exact byte sequence to the slot*, and the "gossip" surface this report is scoped to includes any party that can construct or replay chunks over the same slot before the legitimate signer overwrites it, or a byzantine-adjacent relay/observer path feeding `test_observer`/`get_stackerdb_signer_messages` equivalents). Regardless of the exact relay vector, the core cryptographic defect stands on its own: **the `BlockRejection.signature` field cryptographically proves nothing about `reason`, `reason_code`, or `response_data`.** Any code path that can construct an arbitrary `BlockRejection` value with a *copied* `signature` and `signer_signature_hash` from a genuinely-signed rejection, but altered `reason_code`/`response_data`, will pass `verify()`/`recover_public_key()` unchanged.

### Impact Explanation
This breaks the intended equality "the rejection reason/response metadata attributed to signer S is what S actually signed." Concretely:

- **Miscounted/misattributed vote weight for `failed_txids`.** The node's `permanently_excluded_txids`/`temporarily_excluded_txids` computation (a blocking-minority, i.e., <majority, weighted decision) is driven by `reason_code`/`failed_txid`, both unauthenticated. This lets a party who can replay/rewrite a signer's rejection message change which txid is banned from future block proposals, without needing that signer's key or a majority of signers - satisfying the "rejection recounted"/"miscounted response" class of impact.
- **Signer state-machine wedge risk.** `response_data.reject_reason` (unauthenticated) determines how `store_and_process_block_rejection` treats the vote on the signer side; forging this field can cause a signer's local view of *why* a block was rejected to diverge from what the originating signer intended, potentially causing inconsistent reconsideration behavior across the signer set for the same `signer_signature_hash`.
- **Tenure/read-count extension timestamps are also unauthenticated** (they live in the same `response_data`), so they could similarly be manipulated for a given signature, affecting the node's computed `get_tenure_extend_timestamp`/`get_read_count_extend_timestamp` thresholds.

This maps to the "Critical" bucket's "rejection recounted as acceptance"/"miscounted response" pattern in spirit (a rejection's authenticated payload is smaller than what the protocol treats as authenticated), though the most directly provable consequence is the transaction-banning miscount, which does not require a signer majority.

### Likelihood Explanation
No majority of signers, no private key, and no auth_token are required to exploit the *cryptographic gap* itself - the flaw is that `verify()`/`recover_public_key()` never depend on `reason`, `reason_code`, or `response_data`, so any actor capable of resubmitting/relaying a `BlockRejection` value (same slot chunk under normal StackerDB constraints, or any observer able to feed a crafted message into a code path that only calls `.verify()`) can swap those fields at will while keeping a previously-valid `signature`. The main uncertainty is the exact relay/gossip vector available to a "one-slot miner plus gossip" actor to get a mutated struct accepted into a StackerDB slot in place of/alongside the original (StackerDB chunk-write authentication is a separate, out-of-scope mechanism per the rules), which is why this is flagged as a concrete cryptographic defect with a plausible but not fully traced end-to-end delivery path.

### Recommendation
Include `reason_code` (or the full `reason` string) and the entirety of `response_data` (or at least `reject_reason` and `failed_txid`) inside the SIP-018 structured data hashed in `BlockRejection::hash()`, e.g. add them as additional tuple fields alongside `signer_signature_hash`, mirroring how `BlockAccepted`/`NakamotoBlockHeader` bind every semantically meaningful field into their respective signature hashes. Add negative tests asserting that mutating `reason_code`, `response_data.reject_reason`, or `response_data.failed_txid` after signing invalidates `verify()`.

### Proof of Concept
1. Take any genuinely-signed `BlockRejection` `r` for a given `signer_signature_hash` (e.g., `reason_code = ValidationFailed(BadTransaction)`, `failed_txid = None`).
2. Construct `r2 = r.clone()` and set `r2.reason_code = ValidationFailed(ProblematicTransaction)` and `r2.response_data.failed_txid = Some(<arbitrary_txid>)`, keeping `r2.signature = r.signature` and `r2.signer_signature_hash` unchanged.
3. Call `r2.verify(&signer_pubkey)` / `r2.recover_public_key()` - both succeed because `hash()` only depends on `signer_signature_hash` and `chain_id`: [1](#0-0) 
4. Feed `r2` into the node's `stackerdb_listener.rs` rejection-handling branch; it accumulates `problematic_weight`/`failed_txids` for `<arbitrary_txid>` under `signer_pubkey`'s legitimate weight, exactly as if that signer had truly reported that txid as problematic: [5](#0-4)

    /// The signature hash for the block rejection
    pub fn hash(&self) -> Sha256Sum {
        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
        structured_data_message_hash(data, domain_tuple)
    }

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
}

    /// Handle an observed rejection from another signer
    fn handle_block_rejection(
        &mut self,
        rejection: &BlockRejection,
        sortition_state: &mut Option<SortitionsView>,
    ) {
        debug!("{self}: Received a block-reject signature: {rejection:?}");

        let block_hash = &rejection.signer_signature_hash;
        let signature = &rejection.signature;

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {
            debug!("{self}: Received block rejection with an unrecovarable signature. Will not store.";
               "signer_signature_hash" => %block_hash,
               "signature" => %signature
            );
            return;
        };

        // authenticate the signature -- it must be signed by one of the stacking set
        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }

        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {
            if let Err(e) = self.signer_db.add_pending_block_rejection_response(
                block_hash,
                &signer_address,
                (&rejection.response_data.reject_reason).into(),
            ) {
                warn!("{self}: Failed to add pending block rejection response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block rejection";
            "signer_pubkey" => public_key.to_hex(),
            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "reject_reason" => ?rejection.response_data.reject_reason,
        );

        self.store_and_process_block_rejection(
            sortition_state,
            &mut block_info,
            &signer_address,
            (&rejection.response_data.reject_reason).into(),
        );
