### Title
Missing validation of `hdr.Linkname` allows creation of dangling symlinks that escape the extraction chroot - (File: commands/helpers/archive/tarzstd/tarzstd_extractor.go)

### Summary
`tarzstd.extractor.Extract` validates that the *location* of an extracted entry (`hdr.Name`) stays inside `e.dir`, but never validates the *target* of a symlink entry (`hdr.Linkname`) before calling `os.Symlink`. This lets a job-controlled tar+zstd archive (an artifact or cache produced by an earlier pipeline stage) plant a symlink inside the build/cache root that points anywhere on the host filesystem, e.g. `/etc`, `../../../etc`, or another job's directory. [1](#0-0) [2](#0-1) 

### Finding Description
The chroot check only guards `path`, which is derived from `hdr.Name`:

```go
path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name))
...
if !strings.HasPrefix(path, e.dir+string(filepath.Separator)) && path != e.dir {
    return fmt.Errorf("%s cannot be extracted outside of chroot (%s)", path, e.dir)
}
``` [3](#0-2) 

For symlink entries, `hdr.Linkname` (the symlink target) is used unchecked in the deferred loop:
```go
if fi.Mode()&os.ModeSymlink != 0 {
    if err := os.Symlink(hdr.Linkname, path); err != nil {
        return err
    }
}
``` [2](#0-1) 

`path` (the symlink's own name/location) is confined to `e.dir`, but `hdr.Linkname` can be any string — absolute (`/etc/cron.d/x`) or relative with `..` segments — and is never checked against `e.dir`. `os.Symlink` does not validate or resolve the target either, so the symlink is created successfully and now permanently points outside the intended root.

Regarding the exact mechanism proposed in the question (a same-archive TOCTOU where a symlink is created and then a later entry in the *same* `Extract` call writes through it): this specific ordering does not hold, because all symlink entries are collected into the `deferred` map and are only materialized via `os.Symlink` in the final loop, which runs strictly after the main loop that writes all regular files has already finished. [4](#0-3)  So within one call to `Extract`, a symlink cannot be used to redirect a subsequent regular-file write in that same archive.

However, the underlying root cause — unchecked `hdr.Linkname` — is real and exploitable in the broader job lifecycle rather than within a single `Extract` call: extracted content (cache and artifacts) is written into the shared build directory (`e.dir`, e.g. `CI_PROJECT_DIR`) and that directory persists and is reused across multiple extraction operations in the same job/pipeline (cache restore, then artifact download, then later stage's cache save, or the job's own shell commands writing to job-controlled relative paths). Once the dangling symlink exists on disk, any subsequent write (from a second archive extraction reusing the same tree, or from the job script itself performing `echo x > plantedname/file`) will traverse the symlink and land on the host path chosen by the attacker, outside `e.dir`.

### Impact Explanation
An unprivileged job that controls an artifact/cache archive can create a symlink inside its own build directory whose target is an arbitrary host path. Any later write operation that traverses that symlink path (a subsequent extraction into the same directory, or normal job script execution) results in a file write outside the intended job root. On hosts where build directories or job execution overlap (e.g. shell/custom executors, or a build dir reused across stages of the same job), this is a path-confinement bypass with host file write outside the sandboxed root — matching the scoped impact of a chroot escape via extraction, albeit realized via a persisted dangling symlink rather than a same-call TOCTOU.

### Likelihood Explanation
Feasible and repeatable: an attacker only needs the ability to produce/upload a cache or artifact archive consumed later via `tarzstd`'s extractor (`commands/helpers/cache_extractor.go`, `commands/helpers/artifacts_downloader.go`), which is standard, unprivileged CI job behavior. No secret leakage or admin action is required — only that the runner extracts a job-controlled tar+zstd archive into a directory that is written to again afterward (by a later extraction or by job commands).

### Recommendation
Validate `hdr.Linkname` the same way `hdr.Name` is validated before creating the symlink: resolve `filepath.Join(path_dir, hdr.Linkname)` (or, for absolute targets, reject them outright) and confirm the resulting absolute path still has `e.dir` as a prefix; reject the entry otherwise. Additionally, consider re-validating with `filepath.EvalSymlinks` on parent directories before subsequent writes, or extracting into a directory that is never reused for a second, independently-untrusted extraction without first clearing/verifying it contains no unexpected symlinks.

### Proof of Concept
Go unit test in `tarzstd_extractor_test.go` (package `tarzstd`):
1. Build an in-memory tar+zstd stream containing a single entry: a symlink named `link` with `Linkname` set to `/tmp/outside-marker` (or a relative target with `../../` escaping `e.dir`).
2. Call `NewExtractor(...).Extract(ctx)` with `e.dir` set to a fresh temp dir.
3. Assert that `Extract` either returns an error (desired fix) or, under current code, succeeds and `os.Lstat(filepath.Join(e.dir, "link"))` shows a symlink whose target (`os.Readlink`) is outside `e.dir` — demonstrating the missing validation.
4. Follow-up integration test: extract a second archive containing a regular file entry named `link/pwned.txt` into the same `e.dir`; assert (under current code) that the file is written to `/tmp/outside-marker/pwned.txt` on the host instead of failing, proving the escape; after the fix, assert `Extract` returns a chroot error instead.
