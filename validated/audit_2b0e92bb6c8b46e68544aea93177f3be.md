### Title
Stale per-epoch instant-withdraw basis is double-counted as a default claim — already-paid users dilute the recovery reserve and can block later claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The bug class in the Prysm commit — bookkeeping cleanup that removes leaf/empty entries but leaves the parent aggregate behind, corrupting epoch-end accounting — maps directly onto `IdleCreditVault`'s instant-withdraw receipt ledgers. The funded claim path `claimInstantWithdrawRequest` zeroes only the per-user aggregate `instantWithdrawsRequests[_user]` but never clears `instantWithdrawsRequestsByEpoch[_user][epochNumber]` or decrements `instantWithdrawClaimsByEpoch[epochNumber]`. If the pool defaults in that same epoch while `pendingInstantWithdraws != 0`, `finalizeDefaultRecovery` counts those already-paid receipts again in `totalBasis` and in the prefunded reserve, understating `defaultRecoveryPrice` and over-reserving for ghost claims. Legitimate defaulted claimants are underpaid and the last claimants become permanently unfunded.

### Finding Description
`requestInstantWithdraw` records three ledgers per request: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

`claimInstantWithdrawRequest` pays the user from already-collected funds but clears only the aggregate:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

The per-epoch entries survive. This matters because default recovery reads exactly those per-epoch entries:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [3](#0-2) .
- `_defaultPrefundedInstantReserve` adds `instantBasis - pendingInstant` as "already-held" reserve when the epoch's instant basis exceeds the unfunded remainder — stale basis from paid claims inflates both terms [4](#0-3) .
- `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over the inflated basis [5](#0-4) .
- `_claimDefaultedInstantWithdrawRequest` later clears `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — including the stale ghost basis — and decrements `instantWithdrawsRequests[_user]`, which underflows for a user whose aggregate was already zeroed [6](#0-5) .

The analogous prysm asymmetry is exact: the funded-claim path deletes the "empty" leaf (the zeroed aggregate) while the "full" parent bookkeeping (per-epoch basis and epoch claim totals) is never removed at the epoch boundary.

### Impact Explanation
Direct insolvency/permanent freezing of recovery funds, quantified by the stale amount `S` already paid out:

- `totalBasis` is inflated by `S`, so `defaultRecoveryPrice` is understated by a factor `totalBasis / (totalBasis + S)`. Every legitimate defaulted receipt (normal, APR0, instant) is paid proportionally less than the true recovery ratio.
- `_defaultPrefundedInstantReserve` treats `S` as on-hand backing even though those underlyings already left the strategy, so `defaultRecoveryReserve` is nominally larger than the real cash. When claimants actually withdraw, `defaultRecoveryReserve` hits zero before all claims are paid and `_transferDefaultRecovery` cannot pay the tail — the last claimants are permanently unpaid by `S` (minus rounding).
- Additionally, an already-paid user's own subsequent claim path is broken: `_claimDefaultedInstantWithdrawRequest` reads their stale basis and `instantWithdrawsRequests[_user] -= claimBasis` underflows (aggregate is 0), so any call to `claimInstantWithdrawRequest` reverts for them.

### Likelihood Explanation
Requires, within one epoch: (a) instant withdrawals enabled and at least one request only partially funded (CDO cash < instant queue), leaving `pendingInstantWithdraws > 0`; (b) a user claims the funded portion at par; (c) the borrower fails repayment at that epoch's `stopEpoch`/`stopEpochWithDuration` and `finalizeDefault` runs. Partial instant funding is an explicitly designed mode — `_defaultPrefundedInstantReserve` exists precisely because instant claims can be funded only in part [7](#0-6) . The user actions are all unprivileged (tranche holder request + claim); the default requires no malicious privileged act — it triggers automatically when recalled funds are insufficient. Likelihood is moderate: it needs a default coinciding with an open instant-claims epoch, but no attacker timing control beyond making ordinary requests.

No existing guard stops it: `_ensureDefaultRecoveryInitialized`, the `defaultRecoveryFinalized` flags, and the `pendingInstantWithdraws` clamp (`claimBasis >= pending ? 0 : pending - claimBasis`) [8](#0-7)  all operate on the already-corrupted aggregates.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers alongside the aggregate for the request's epoch(s) — i.e., zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and subtract from `instantWithdrawClaimsByEpoch[epoch]` the amounts paid at par (analogous to what `_claimDefaultedInstantWithdrawRequest` already does for the defaulted epoch). Since a user may hold receipts from multiple epochs, either track the oldest open instant-request epoch per user (like `lastWithdrawRequest`) or iterate/cap the clearing against the user's per-epoch entries so the funded path leaves no residual basis. Add a regression test: partially funded instant claim in epoch E → same-epoch default → `finalizeDefault` → assert `defaultPendingClaimBasis` excludes already-claimed instant receipts and `defaultRecoveryPrice` equals the true ratio.

### Proof of Concept
Foundry fork test sketch (extends the harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleInstantBasisDilutesDefaultRecovery() external {
    _useStandardEpochVariant();               // instant withdrawals path
    _stopCurrentEpochWithApr(10e18);
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address victim  = makeAddr('victim');
    address early   = makeAddr('early-claimer');
    uint256 amt = 100e6;

    _depositWithUser(victim, amt);            // normal position -> will request normal withdraw
    _depositWithUser(early, amt);
    vm.prank(manager); cdoEpoch.startEpoch();
    skip(101);                                // past instant delay

    // early user requests instant withdraw for full balance
    uint256 earlyTr = IERC20(AAtranche).balanceOf(early);
    vm.prank(early); cdoEpoch.requestInstantWithdraw(earlyTr, AAtranche);
    uint256 epoch = strategy.epochNumber();
    uint256 instBasis = strategy.instantWithdrawClaimsByEpoch(epoch);

    // Fund only part of the instant queue via CDO cash, then early claims at par
    // (drive getInstantWithdrawFunds/collectInstantWithdrawFunds as in existing instant tests)
    _fundInstantPartially(instBasis / 2);
    vm.prank(early); cdoEpoch.claimInstantWithdrawRequest();

    // BUG: per-epoch basis still fully recorded although half was paid
    assertEq(strategy.instantWithdrawsRequestsByEpoch(early, epoch), instBasis);
    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), instBasis);

    // Borrower repays insufficiently -> default in same epoch, then finalize
    deal(defaultUnderlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager); cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted());

    uint256 basis = strategy.defaultPendingClaimBasis();
    // stale instant basis still included
    assertEq(basis, strategy.pendingWithdraws() + instBasis);

    // Finalize with the "correct" external recovery for the real basis only
    uint256 realBasis = basis - instBasis;
    uint256 recovered = realBasis * 7e17 / 1e18;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // recoveryPrice < 70% because ghost basis was counted
    assertLt(strategy.defaultRecoveryPrice(), 7e17);

    // victim's defaulted claim is haircut below the true ratio -> residual unpaid,
    // and early's next claimInstantWithdrawRequest reverts on underflow
    vm.prank(early);
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();
}
```

`_fundInstantPartially` should mirror the instant-funding helper used by `testProcessWithdrawalClaimsInstantEpoch` (deal limited cash to the CDO and invoke the instant-fulfil path so `collectInstantWithdrawFunds` runs with `_amount < pendingInstantWithdraws`). The assertions on `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` and `defaultRecoveryPrice < 7e17` demonstrate both the stale-bookkeeping root cause and the quantified haircut/insolvency impact.

  /// @notice Get current-epoch instant-withdraw funds already collected before default finalization.
  /// @dev `pendingInstantWithdraws` is the still-unfunded remainder. If it is lower than the
  /// current-epoch claim basis, the difference is already-held underlying reserved for those claims.
  /// @return prefundedReserve amount of current instant claims already backed by strategy underlyings
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
