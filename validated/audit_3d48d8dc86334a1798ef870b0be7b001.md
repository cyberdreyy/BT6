## Analysis

`BaseEscrow.rescueFunds` is gated by `onlyCaller(immutables.taker.get())`, `onlyValidImmutables`, and `onlyAfter(rescueStart)` [1](#0-0) . Calling it with `token = address(0)` and `amount = immutables.safetyDeposit` is a normal, permitted call once `RESCUE_DELAY` has elapsed — the taker is only reclaiming the exact native deposit it originally posted, and this is the documented last‑resort mechanism, not privileged access. On its own, this framing ("taker sweeps its own posted deposit instead of letting withdraw/cancel decide") is **not theft**, because the safety deposit belongs to the taker until someone earns it via the normal incentive flow, and `RESCUE_DELAY` exists specifically to unlock stuck value when nobody has acted.

However, tracing the consequence of that call reveals a real downstream defect. `EscrowSrc._cancel` (used by both `cancel` and `publicCancel`) unconditionally attempts to pay out the *original* `immutables.safetyDeposit` amount in native currency to the caller, alongside returning the ERC20 principal to the maker: [2](#0-1) . Neither `BaseEscrow`, `Escrow`, nor `EscrowSrc` define a `receive`/`fallback` function, so the contract cannot be topped up with plain ETH after deployment [3](#0-2) .

If the taker calls `rescueFunds(address(0), immutables.safetyDeposit, immutables)` before anyone exercises `cancel`/`publicCancel`, the contract's native balance drops to zero while the ERC20 principal is left untouched. Because `withdraw`/`withdrawTo` are only available `onlyBefore(SrcCancellation)` [4](#0-3) , and the scenario is already past the public-cancellation window, `cancel`/`publicCancel` become the only remaining paths to return the maker's ERC20 principal — but both now permanently revert in `_ethTransfer` because the contract cannot pay the `safetyDeposit` it no longer holds [5](#0-4) . With no way to refund the native balance, the maker's principal tokens become permanently stuck in the `EscrowSrc` clone.

### Title
Partial `rescueFunds` drain of the source safety deposit permanently bricks `cancel`/`publicCancel`, freezing the maker's principal - (File: `contracts/BaseEscrow.sol`, `contracts/EscrowSrc.sol`)

### Summary
`rescueFunds` lets the taker withdraw an arbitrary `(token, amount)` pair from an `EscrowSrc` clone once `RESCUE_DELAY` has passed, independent of whether the swap has actually concluded. If the taker rescues only the native `safetyDeposit` while leaving the ERC20 principal, the escrow's native balance falls below the amount that `_cancel`/`publicCancel` unconditionally attempt to pay to their caller, and since the contract has no `receive`/`fallback` to accept a top-up, every subsequent `cancel`/`publicCancel` call reverts forever.

### Finding Description
`_cancel` hard-codes `_ethTransfer(msg.sender, immutables.safetyDeposit)` with no balance check [2](#0-1) . This design assumes the safety deposit funded at CREATE2 deployment always remains available until consumed by `withdraw`/`withdrawTo`/`cancel`/`publicCancel`. `rescueFunds` breaks that assumption: it is a generic sweep that can move any `(token, amount)` out of the clone independently of the swap's lifecycle state, gated only by caller/immutables/rescueStart checks [1](#0-0) . There is no invariant tying `rescueFunds` withdrawals to the amounts still owed for principal/deposit, and no `receive`/`fallback` exists to allow anyone to restore the drained native balance. Once the safety deposit is drained this way while the ERC20 principal is still present, `cancel`/`publicCancel` become unconditionally unexecutable.

### Impact Explanation
The maker's ERC20 principal becomes permanently locked in the `EscrowSrc` clone with no remaining code path to release it (withdraw window already closed by the time public cancellation/rescue windows are relevant; cancel/publicCancel revert forever). This is a permanent freezing of user funds, matching the Critical/High impact bar in the bounty scope.

### Likelihood Explanation
Requires only an unprivileged taker (a normal swap participant) waiting until `RESCUE_DELAY` and calling `rescueFunds` with `token=address(0)`, before any access-token holder calls `publicCancel`. `RESCUE_DELAY` is typically configured to exceed `SrcPublicCancellation`, so there is a real window where both are simultaneously callable; the outcome depends on which is executed first, making this a timing race rather than a certainty, but fully reachable by an unprivileged actor with no special assumptions.

### Recommendation
Make `_cancel`/`withdraw` resilient to a reduced native balance (e.g., transfer `min(address(this).balance, immutables.safetyDeposit)` instead of the fixed amount), or restrict `rescueFunds` from touching amounts/tokens that are still owed as part of the active swap accounting (e.g., disallow rescuing the native currency while the ERC20 principal is still present, or require the principal to have already been withdrawn/cancelled before rescue is allowed to touch the safety-deposit-denominated asset).

### Proof of Concept
1. Order fills, `EscrowSrc` clone is deployed with `immutables.safetyDeposit = X` funded in native currency.
2. Maker fails to call `cancel`/`publicCancel` during the private/public cancellation windows.
3. Taker waits until `block.timestamp >= immutables.timelocks.rescueStart(RESCUE_DELAY)`.
4. Taker calls `rescueFunds(address(0), X, immutables)`; passes `onlyCaller(taker)`, `onlyValidImmutables`, `onlyAfter(rescueStart)` and transfers the full native balance to the taker.
5. Any later call to `cancel(immutables)` or `publicCancel(immutables)` executes `_ethTransfer(msg.sender, X)` inside `_cancel`, which reverts because the contract's native balance is now `0 < X`.
6. The ERC20 principal remains permanently locked in the clone; no other function can release it.
