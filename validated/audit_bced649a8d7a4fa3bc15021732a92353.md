### Title
Flash-loanable access-token balance gates public escrow execution and safety-deposit theft - (File: contracts/BaseEscrow.sol)

### Summary
The `onlyAccessTokenHolder` modifier in `BaseEscrow` grants the right to call `publicWithdraw` and `publicCancel` based on the caller's current `_ACCESS_TOKEN` balance, which is the same root cause as the reported governance issue where current balance is used as a privileged weight. [1](#0-0)  An unprivileged attacker can flash-loan the access token in the same transaction, satisfy the balance check, execute the public function, receive the escrow's safety deposit, and repay the loan. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`BaseEscrow` defines `onlyAccessTokenHolder` to restrict `publicWithdraw` and `publicCancel` to addresses that currently hold the configured access token. [1](#0-0)  The modifier reads `_ACCESS_TOKEN.balanceOf(msg.sender)` at call time and reverts only if the balance is zero. [1](#0-0)  It does not use a prior-block balance, a time-weighted holding, a delegation snapshot, or any other flash-loan-resistant measure. [1](#0-0)  `EscrowSrc.publicWithdraw`, `EscrowSrc.publicCancel`, and `EscrowDst.publicWithdraw` all rely on this modifier and, on success, transfer `immutables.safetyDeposit` native tokens to `msg.sender`. [2](#0-1) [3](#0-2) [4](#0-3)  This is the same root cause as the reported governance issue: a deterministic, value-transferring action is gated by a token balance that can be borrowed and repaid atomically. [1](#0-0) 

### Impact Explanation
An unprivileged user who can flash-borrow the access token can claim the safety deposit from any source or destination escrow that has entered its public execution window. [2](#0-1) [4](#0-3)  The safety deposit is user-funded native value locked in the escrow: it is supplied by the maker on the source chain and by the taker on the destination chain. [5](#0-4) [6](#0-5)  Its theft is direct loss of user funds at rest and fits the Critical/High bounty scope for theft of native refund-path value. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
The attack is a single-transaction flash loan: borrow the access token, call the public function, receive native safety deposit, repay the loan. [1](#0-0)  It requires no privileged role, no malicious relayer or bridge, and no owner action. [1](#0-0)  For `publicWithdraw` the secret must be known, which is the normal public-execution assumption once the secret is revealed; for `publicCancel` no secret is required. [3](#0-2)  Any liquid access token with an external flash-loan market is sufficient because the contract only checks the current balance. [9](#0-8) 

### Recommendation
Replace the current-balance check with a flash-loan-resistant access control mechanism. Options include requiring the access token to be held for a minimum number of blocks before the call, using a delegated/staked/non-transferable access token, or snapshotting balances at order creation and requiring the caller to prove prior holding. At minimum, cap or separate the safety-deposit reward so that it cannot be captured by a same-block balance.

### Proof of Concept
1. Attacker identifies an `EscrowSrc` or `EscrowDst` that has reached its public withdrawal or public cancellation window. [2](#0-1) [3](#0-2) [4](#0-3) 
2. Attacker takes a flash loan of the `_ACCESS_TOKEN` token. [9](#0-8) 
3. In the flash-loan callback, attacker calls `publicWithdraw(secret, immutables)` (with the revealed secret) or `publicCancel(immutables)`. [2](#0-1) [3](#0-2) [4](#0-3) 
4. `onlyAccessTokenHolder` sees a non-zero access-token balance and allows the call. [1](#0-0) 
5. The escrow transfers `immutables.safetyDeposit` native tokens to the attacker. [7](#0-6) [8](#0-7) 
6. Attacker repays the flash loan and keeps the safety deposit as profit.

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
