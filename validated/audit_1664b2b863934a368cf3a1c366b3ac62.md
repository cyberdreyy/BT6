## Title
Node-side coordinator lets a signer's stale `Rejected` weight persist after it later `Accepted`, inflating `total_weight_rejected` without offset — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tallies per-block `total_weight_approved` and `total_weight_rejected` from `BlockResponse` messages, keyed per `Sha512Trunc256Sum` block hash in a `BlockStatus` struct. The `Accepted` and `Rejected` branches update disjoint bookkeeping sets (`gathered_signatures` vs `responded_signers`) with asymmetric guards, so a signer that first rejects and later legitimately signs/accepts the very same block has its rejection weight counted permanently, with no corresponding decrement — mirroring the Cork Protocol H-10 pattern of "increment without corresponding decrement" breaking an accounting equality.

### Finding Description
In `handle_signer_message` (stackerdb_listener.rs), the two branches are:

Rejected path [1](#0-0) :
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
```

Accepted path [2](#0-1) :
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```

The guard for `total_weight_approved` is keyed on `gathered_signatures` (only touched by the accept path), while the guard for `total_weight_rejected` is keyed on `responded_signers` (touched by both paths). Consequence:

- If signer S first sends `Rejected`: `responded_signers.insert(S)` succeeds → `total_weight_rejected += w(S)`.
- If S later sends a genuinely valid `Accepted` (signature verifies, `signer_pubkey.verify` passes) for the *same* `block_sighash`: the check is `!gathered_signatures.contains_key(S)` — true, since only the reject path ran before — so `total_weight_approved += w(S)` as well. `total_weight_rejected` is **never decremented**.

The reverse order (Accept then Reject) is correctly guarded, since `responded_signers` already contains the slot after Accept, so the Reject branch's `insert` returns `false` and skips the increment. Only the Reject→Accept ordering is asymmetric.

This breaks the implicit equality the coordinator's loop in `signer_coordinator.rs` relies on — that a signer's weight contributes to at most one of the two buckets at a time. After the flip, `total_weight_rejected + total_weight_approved` can exceed `total_weight`, and the stale rejection weight sticks around for the lifetime of that `block_sighash`'s `BlockStatus` entry, since nothing in the coordinator loop clears it once a signer's stance changes.

### Impact Explanation
The coordinator loop checks the reject condition before the accept condition [3](#0-2) :
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { ... });
} else if block_status.total_weight_approved >= self.weight_threshold {
    return Ok(...)
}
```
Because stale rejection weight from signers who have since accepted is never purged, enough such flips can push `total_weight_rejected` over the blocking-minority line even though the same signers' current, valid signatures are also accumulating toward `total_weight_approved`. This can cause the coordinator to spuriously return `SignersRejected` for a proposal that in fact has (or would have) reached the real acceptance threshold, wedging the miner into discarding/retrying a validly-signed block. This is a liveness degradation on the node/coordinator side (a false "rejected" verdict caused by stale accounting), not a signature forgery or invalid-block-signing event, so it maps to a **High**-severity wedge (block confirmation stalls due to double-counted signer weight) rather than Critical.

### Likelihood Explanation
Reachable by a single signer (one slot) that sends a `BlockResponse::Rejected` for a given `signer_signature_hash` and subsequently sends a genuinely-signed `BlockResponse::Accepted` for the same hash — both messages carry real, verifiable signatures from that signer, requiring no key compromise or majority collusion. Signer state-machine flows in this codebase explicitly allow a signer's decision on the same block to change over time (see the pre-commit/threshold re-check logic in `docs/signer-flows.md` describing re-evaluation against chainstate that can flip outcomes), so this is not a purely theoretical signer behavior. Only a single flipping signer, plus normal StackerDB gossip delivery, is needed to plant the stale weight; enough concurrent flips (from otherwise honest signers reconsidering) could tip `total_weight_rejected` past the blocking-minority threshold.

### Recommendation
Make `total_weight_rejected`/`total_weight_approved` bookkeeping mutually exclusive and reversible per signer slot: track a single "current stance" per slot (e.g., `HashMap<u32, Stance>` where `Stance` is `Accepted(weight)` or `Rejected(weight)`), and when a slot's stance changes, subtract the previous contribution from its old bucket before adding to the new one — analogous to the Cork Protocol fix of calling `decLocked` before/alongside any new `lockFrom`. Concretely, in the `Rejected` branch, if `gathered_signatures.contains_key(&slot_id)` is true (i.e., the signer had previously accepted), decide policy (ignore vs. move weight); and in the `Accepted` branch, if `responded_signers.insert(slot_id)` indicates a prior response was a rejection, decrement `total_weight_rejected` by `signer_entry.weight` before adding to `total_weight_approved`.

### Proof of Concept
1. Miner proposes block B; coordinator creates `BlockStatus` for `sighash(B)` with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight `w`) sends `BlockResponse::Rejected` for `sighash(B)` (e.g., due to a transient chainstate check failure). `responded_signers.insert(S)` succeeds → `total_weight_rejected = w`.
3. S re-evaluates (chainstate/sortition view advances) and legitimately signs and sends `BlockResponse::Accepted` for the same `sighash(B)`. `gathered_signatures.contains_key(S)` is `false` → `total_weight_approved = w`; `total_weight_rejected` remains `w`, uncorrected.
4. Repeat for enough signers so that `total_weight_rejected.saturating_add(weight_threshold) > total_weight` becomes true in `signer_coordinator.rs`, even though those same signers' current signatures are simultaneously accumulating in `total_weight_approved`. The coordinator returns `Err(SignersRejected { .. })`, discarding a proposal that legitimate, currently-valid signer weight supports. [4](#0-3) [3](#0-2)
