### Title
Signer weight double-counted across `total_weight_approved` and `total_weight_rejected` when a signer flips its vote — (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` (the miner-side vote tally used by `SignerCoordinator::get_block_status`) tracks two independently-incremented weight counters, `total_weight_approved` and `total_weight_rejected`, guarded by two *different* de-duplication sets. The `Accepted` handler only checks `gathered_signatures` before adding weight, while the `Rejected` handler checks `responded_signers`. Because `Accepted` never checks `responded_signers`, a signer who first rejects and later accepts the same block has its weight added to `total_weight_approved` *without* the stale contribution being removed from `total_weight_rejected`. This breaks the invariant (explicitly called out as fixed elsewhere in this exact codebase, see the CHANGELOG entry "Do not count both a block acceptance and a block rejection for the same signer/block") that a signer's weight should count toward at most one side of the tally.

### Finding Description
In the `Accepted` branch: [1](#0-0) 
the guard is `if !block.gathered_signatures.contains_key(&slot_id)`, then `block.total_weight_approved = ...saturating_add(signer_entry.weight)`, followed unconditionally by `block.responded_signers.insert(slot_id);`.

In the `Rejected` branch: [2](#0-1) 
the guard is `if block.responded_signers.insert(slot_id)`, then `block.total_weight_rejected = ...saturating_add(signer_entry.weight)`.

Sequence for a single signer S with weight `w`:
1. S sends `Rejected` first → `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`.
2. S later sends `Accepted` (permitted by the signer-side re-evaluation flow, e.g. `should_reevaluate_block`/`LocallyRejected --> LocallyAccepted`) → `gathered_signatures.contains_key(S)` is false (S never signed before) → `total_weight_approved += w`. `responded_signers.insert(S)` is a no-op since S is already present, but this doesn't matter because the `Accepted` path never consults `responded_signers` to gate the weight addition.

Result: `total_weight_rejected` still contains `w` from step 1 even though S has since accepted; `total_weight_approved` also now contains `w`. The two totals are no longer mutually exclusive; `total_weight_approved + total_weight_rejected` can exceed `total_weight`, and — critically — `total_weight_rejected` remains permanently polluted with weight from a signer who is no longer rejecting.

Note the reverse order (accept-then-reject) is correctly guarded: `Accepted` unconditionally inserts into `responded_signers`, so a subsequent `Rejected` from the same signer is a no-op via `block.responded_signers.insert(slot_id)` returning `false`. The bug is one-directional: only the accept-side add is missing the `responded_signers` check.

### Impact Explanation
`total_weight_rejected` (and the derived stale value) drives the miner's rejection decision in `SignerCoordinator::get_block_status`: [3](#0-2) 
`block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` triggers `NakamotoNodeError::SignersRejected`, which excludes txids from future proposals and aborts the current one. Because the stale rejection weight from a signer who has since switched to accepting is never removed, the tally can incorrectly cross the blocking-minority threshold (i.e., act on a stale/incorrect aggregated weight), causing the miner to wrongly treat a block as globally rejected and to mark transactions as problematic/excluded even though the real, current rejecting weight is below the 30% blocking minority. This is a liveness wedge on block production driven purely by ordinary vote-flip behavior that the signer protocol itself permits (re-evaluation of previously rejected blocks), not requiring a signer majority or key compromise.

### Likelihood Explanation
Reachable by a single signer (malicious or merely re-evaluating its own decision, which the documented signer state machine explicitly allows: `LocallyRejected --> LocallyAccepted : re-evaluated`) sending a `Rejected` `BlockResponse` followed later by an `Accepted` `BlockResponse` for the same block hash over StackerDB — ordinary gossip traffic the coordinator already processes. No majority or additional privileges are required; only the ordering (reject observed before accept) is needed, which any one-slot participant fully controls for its own message and the coordinator processes both messages as legitimate.

### Recommendation
In the `Accepted` handler, gate the weight addition on `!block.responded_signers.contains(&slot_id)` (or otherwise track state per signer to ensure their weight contributes to exactly one of `total_weight_approved`/`total_weight_rejected`), and when a signer's vote flips, remove any stale weight from the opposite tally rather than only adding to the new one. This mirrors the fix already applied on the signer side (`signerdb.rs`/`signer.rs`, where `add_block_rejection_signer_addr` checks for an existing signature before allowing a rejection to be recorded).

### Proof of Concept
1. Miner submits a block proposal and starts `StackerDBListener` polling for `BlockStatus`.
2. Signer S (weight `w`) initially rejects: send `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` with `signer_signature_hash` = block hash. `total_weight_rejected` increases by `w`; `responded_signers` now contains S's slot id.
3. S changes its mind and later sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same block hash (permitted by the normal signer re-evaluation flow). `gathered_signatures` does not yet contain S's slot id, so `total_weight_approved` increases by `w`, while `total_weight_rejected` is left unchanged (still includes `w`).
4. Repeat for additional signers whose combined weight, once stuck in `total_weight_rejected`, satisfies `total_weight_rejected.saturating_add(weight_threshold) > total_weight` in `SignerCoordinator::get_block_status`, even though the currently-rejecting weight (excluding flipped signers) is below the real 30% blocking minority.
5. The miner incorrectly returns `NakamotoNodeError::SignersRejected`, excluding txids and/or stalling block production despite sufficient real signer support for the block.
