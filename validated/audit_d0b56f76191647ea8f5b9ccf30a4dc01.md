### Title
Unauthenticated pipeline-run resume endpoint allows arbitrary task result injection / job-run nullification - (File: core/web/router.go, core/web/pipeline_runs_controller.go)

### Summary
The external report describes an incomplete DoS/nullification protection: because certain state-mutating actions (withdrawal application, order cancellation) were not gated by the intended timelock/authorization check, an unprivileged trader could nullify a trade that had already been submitted for processing. The analogous condition in this codebase is the `PATCH /v2/resume/:runID` endpoint, which is explicitly registered without any authentication middleware and accepts an attacker-controlled `taskID` and JSON body that is used to directly resolve/complete a pending pipeline task run.

### Finding Description
The route is registered in `unauthedv2`, a router group with no auth middleware, unlike the sibling `authv2` group which requires `auth.Authenticate(...)` with `AuthenticateByToken`/`AuthenticateBySession`: [1](#0-0) 

The handler, `PipelineRunsController.Resume`, parses `runID` from the URL as a UUID (the pipeline task ID), decodes a JSON body into a `pipeline.ResumeRequest`, and calls `App.ResumeJobV2` with the caller-supplied result — with no ownership check tying the requester to the job/run in question: [2](#0-1) 

`ResumeJobV2` forwards directly into the pipeline runner, which updates the task run's `Result` (value/error) via `UpdateTaskRunResult` and, if this was the last outstanding task, resumes execution of the whole pipeline run with that attacker-supplied value: [3](#0-2) [4](#0-3) 

This endpoint exists to let async bridge adapters call back with results once they finish out-of-band processing (the response URL is generated by `BridgeTask` as `.../v2/resume/<task-run-uuid>`): [5](#0-4) 

The only correctness dependency is the unguessability of the `task run UUID`. There is no bearer token, HMAC signature, or per-run secret validated by the endpoint itself — it relies solely on UUID secrecy. If that UUID is ever observable to a party other than the intended bridge/adapter (e.g., logged, leaked via bridge/adapter logs, exposed to a malicious or compromised external adapter, or through timing/replay by an adapter that received the URL for a different purpose), any unauthenticated client can:
- Supply an arbitrary/malicious result for a task, corrupting the pipeline run's output before it reaches on-chain reporting or other downstream consumers (cross-user response confusion / forged responses), or
- Replay/resume the same run repeatedly or with conflicting values to disrupt or nullify runs relying on a single legitimate bridge callback (DoS-style nullification directly analogous to the source report's order-cancellation scenario).

Note: this is the well-documented `X-Chainlink-Pending`/bridge resume mechanism, and the audit log entry is literally named `UnauthedRunResumed`, indicating the team is aware this is intentionally unauthenticated and relies on the UUID as a shared secret: [6](#0-5) 

### Impact Explanation
An attacker who obtains or guesses a pending task-run UUID can inject falsified data into a pipeline run (corrupting oracle/report data before finalization) or repeatedly resume/interfere with runs to prevent legitimate bridge responses from being the ones that finalize the run — directly mirroring the reported bug class of "nullifying a trade/run that was already submitted" via a state-mutating action that bypasses the intended authorization boundary. Since UUIDv4 values are not guessable at scale, the practical severity depends heavily on whether the UUID can leak (e.g., through external adapter logs, network intermediaries, or a malicious/compromised bridge adapter) — this is an architectural reliance on secrecy of an identifier rather than a properly-authenticated callback.

### Likelihood Explanation
Low-to-moderate: exploitation requires the attacker to already know a specific pending task's UUID, which is not enumerable and not otherwise exposed via the API. The design is intentional (UUID-as-capability-token) and is called out as such in the audit constant name, so this may be an accepted risk rather than an oversight. It is included here strictly as a structural analog to the reported bug class — a state-mutating "resume/complete" action reachable without session/API authentication — for further review, not as a confirmed high-likelihood exploit.

### Recommendation
Consider adding a secondary authentication factor for the `/v2/resume/:runID` endpoint beyond the raw UUID — for example, an HMAC of the task ID signed with a per-bridge or per-node secret, checked before calling `ResumeJobV2`, so that leakage or interception of the UUID alone is insufficient to forge or nullify a run's outcome. At minimum, ensure task-run UUIDs are never logged or exposed in a way accessible to third parties, and consider single-use/one-time validation (reject a second resume for the same task ID) to prevent replay-style interference with the pipeline run.

### Proof of Concept
Given a pending async bridge task with `taskID = <uuid>` (as would be sent to the configured bridge adapter's `responseURL`), any unauthenticated client can call:
```
PATCH /v2/resume/<uuid>
Content-Type: application/json

{"data": {"result": "attacker-controlled-value"}}
```
This is routed to `PipelineRunsController.Resume` without any authentication middleware [7](#0-6) , which calls `App.ResumeJobV2` with the attacker's payload and resumes the pipeline run with that value [8](#0-7) , matching the runner_test pattern of resuming a pending async job via this exact path [9](#0-8) .

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
```

```go
func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events

		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
```
