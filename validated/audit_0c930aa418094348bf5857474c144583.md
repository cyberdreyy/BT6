### Title
Private (non-propagated) validity/extension transactions are exposed through standard txpool query RPCs - ([File: crates/execution/txpool/src/pool.rs])

### Summary
Base's transaction pool marks certain transactions with `TransactionOrigin::Private` specifically so they are not gossiped over P2P (`base_sendRawTransactionValidity` and the builder's `insert_validated_transaction` for extension-bearing transactions). The pool's own code enforces this "stay private" intent only in the methods that back P2P propagation (`pooled_transactions`, `pooled_transaction_hashes`), which filter on the `propagate` flag. Other read paths that back standard `eth_*`/`txpool_*` RPC "views" (e.g. `get`, `get_all`, `get_transactions_by_sender`, `pending_transactions`, `get_pending_transactions_with_predicate`) do not filter on `propagate`/origin at all, so the same "private" transaction content is fully readable by any RPC caller through those query paths.

### Finding Description
Two ingress paths intentionally keep a transaction's raw bytes/metadata out of P2P gossip by inserting with `TransactionOrigin::Private`:
- `base_sendRawTransactionValidity` inserts with `TransactionOrigin::Private` so validity predicates/expiry data are not broadcast: [1](#0-0) 
- The builder's `insert_validated_transaction` inserts extension-bearing transactions the same way, with the comment explicitly stating the intent: "Extension-bearing transactions remain private so normal P2P gossip cannot propagate the raw transaction without its extension metadata": [2](#0-1) 

The pool's propagation-facing accessors correctly gate on the `propagate` flag before returning transactions, which is what keeps them out of P2P gossip: [3](#0-2) 

However, other accessors on the same pool — which back generic `eth_*`/`txpool_*` "view" RPCs (lookup by hash, lookup by sender, pending-transaction predicate scans) — do not check `propagate` or `origin` at all: [4](#0-3) 

Because these unfiltered accessors return the full `ValidPoolTransaction` (raw signed transaction, sender, nonce, and — for validity transactions — the validity predicates attached via `with_validity_predicates`), any caller reaching the node's standard read-only pool RPC surface (`eth_getTransactionByHash`, `txpool_content`, `txpool_contentFrom`, or any other query using `get`/`get_all`/`get_transactions_by_sender`/`get_pending_transactions_with_predicate`) can retrieve the full content of a transaction that the ingress code explicitly tried to keep private from third parties, exactly mirroring the GitLab CVE-2020-10085 pattern: a specific "view" bypasses the access restriction that is correctly enforced elsewhere in the same subsystem.

### Impact Explanation
This is an information-disclosure class issue, not a funds-theft or consensus-safety bug: it lets any RPC client see the exact content (sender, destination, calldata, validity predicates, expiry) of a transaction that was purposely kept off the P2P network because its sender/builder wanted to control who sees it before inclusion (e.g., MEV-sensitive validity-gated transactions, or builder extension transactions meant to stay confidential until included). Disclosure via txpool queries defeats that confidentiality guarantee and could let a competing party front-run or copy a "private" transaction, particularly relevant for `base_sendRawTransactionValidity` submissions whose predicates reveal strategic conditions (balance/storage triggers) before execution.

### Likelihood Explanation
High reachability: any client with access to a node's standard read RPC namespace can call `eth_getTransactionByHash` or `txpool_content`/`txpool_contentFrom` — no special privilege is required beyond normal RPC access, which is far less restrictive than the write-side sequencer/gossip guard. Since the `propagate: false`/`origin: Private` transactions still sit in the same nonce pool queried by these unfiltered accessors, exposure is deterministic, not probabilistic — every private transaction submitted this way is visible via these paths for as long as it remains in the pool.

### Recommendation
Filter on `transaction.propagate` (or explicitly on `origin != TransactionOrigin::Private`) in every pool-read path that can be reached by a general RPC caller — at minimum `get`, `get_all`, `get_transactions_by_sender`, and `get_pending_transactions_with_predicate` — or ensure the `txpool_*`/`eth_getTransaction*` RPC handlers themselves suppress non-propagate transactions before returning results to unauthenticated callers, consistent with the filtering already applied in `pooled_transactions`/`pooled_transaction_hashes`.

### Proof of Concept
1. Submit a transaction via `base_sendRawTransactionValidity` (or the builder's `insert_validated_transaction` with extensions) — it is inserted with `TransactionOrigin::Private`/`propagate: false` ( [1](#0-0) ).
2. From any RPC client with access to the node's read RPC surface, call `eth_getTransactionByHash` for that hash, or `txpool_content`/`txpool_contentFrom` for the sender — both resolve through `get`/`get_transactions_by_sender` in the pool implementation, which return the transaction unconditionally regardless of the `propagate` flag ( [5](#0-4) ).
3. The caller receives the full transaction (and, for validity transactions, the attached predicates), even though the transaction was never gossiped and was explicitly intended to "remain private."

**Note on completeness:** I was unable to fully verify, within the remaining tool budget, which exact RPC trait implementation Base uses for the standard `txpool_content`/`txpool_contentFrom` methods (whether it's stock `reth-rpc` `TxPoolApi` calling into these pool trait methods, or a Base-specific override) — the grep for `TxPoolApiServer`/`txpool_content` implementation only surfaced client-side (`basectl`) usages, not the server-side trait impl. The core finding (unfiltered `propagate`-agnostic accessors on the pool alongside a `propagate`-filtered set used for gossip) is confirmed directly in `crates/execution/txpool/src/pool.rs`, but confirming the precise RPC method name(s) that route through the unfiltered accessors would need a further look at the reth `TransactionPool` trait's default RPC bindings.

    fn get(&self, tx_hash: &TxHash) -> Option<Arc<ValidPoolTransaction<Self::Transaction>>> {
        self.protocol_pool.get(tx_hash).or_else(|| self.nonce_pool.read().get(tx_hash))
    }

    fn get_all(&self, txs: Vec<TxHash>) -> Vec<Arc<ValidPoolTransaction<Self::Transaction>>> {
        let nonce_pool = self.nonce_pool.read();
        txs.into_iter()
            .filter_map(|tx| self.protocol_pool.get(&tx).or_else(|| nonce_pool.get(&tx)))
            .collect()
    }

    fn on_propagated(&self, txs: PropagatedTransactions) {
        let nonce_pool = self.nonce_pool.read();
        let protocol_txs = PropagatedTransactions(
            txs.0.into_iter().filter(|(hash, _)| !nonce_pool.contains(hash)).collect(),
        );
        drop(nonce_pool);
        self.protocol_pool.on_propagated(protocol_txs)
    }

    fn get_transactions_by_sender(
        &self,
        sender: Address,
    ) -> Vec<Arc<ValidPoolTransaction<Self::Transaction>>> {
        let mut transactions = self.protocol_pool.get_transactions_by_sender(sender);
        transactions.extend(self.nonce_pool.read().transactions_by_sender(sender));
        transactions
    }

    fn get_pending_transactions_with_predicate(
        &self,
        mut predicate: impl FnMut(&ValidPoolTransaction<Self::Transaction>) -> bool,
    ) -> Vec<Arc<ValidPoolTransaction<Self::Transaction>>> {
        let mut transactions =
            self.protocol_pool.get_pending_transactions_with_predicate(&mut predicate);
        transactions.extend(
            self.nonce_pool
                .read()
                .pending_transactions()
                .into_iter()
                .filter(|transaction| predicate(transaction)),
        );
        transactions
    }
