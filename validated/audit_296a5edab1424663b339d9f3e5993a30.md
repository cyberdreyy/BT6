The `MIMSpell3` bug pattern (a solvency/authorization check that doesn't reflect updated state) maps to a comparable flaw in `multisig`/`multisig2`: **confirmations recorded in the `confirmations` set are never revalidated against the live member/key list**, so a request can execute once the *stale* confirmation count reaches `num_confirmations`, even though a confirming party was subsequently removed.### Title
Multisig executes requests using stale confirmations from removed keys/members, allowing execution below the live-member threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
`confirm()` counts entries in a per-request `confirmations: HashSet<...>` and executes the request once `confirmations.len() + 1 >= num_confirmations` [1](#0-0) , and identically in the legacy contract [2](#0-1) . When a key/member is removed via `DeleteKey`/`DeleteMember`, the contract only purges *requests that member originally created* (`r.signer_pk == pk` / `r.member == member`) — it never scans other pending requests to strip out that member's prior *confirmations* on them [3](#0-2) [4](#0-3) . The stale confirmation therefore continues to count toward `num_confirmations` on any request it was added to, other than the ones the removed member itself authored.

### Finding Description
The binding that should hold is:
`live confirmations on request R at execution time == confirmations recorded on request R`,
where "live" means each confirming principal (public key or account) is still present in `self.members` (multisig2) / still holds an authorized key (multisig).

Sequence showing the binding breaks:
1. `num_confirmations = 3`, members `{A, B, C, D}`.
2. Request `R` (e.g. `Transfer` to an attacker-controlled account, or `FunctionCall`) is added and confirmed by `A` and `B`. `confirmations(R) = {A, B}` (size 2, below threshold) [1](#0-0) .
3. Separately, a legitimate `DeleteMember { member: A }` request reaches threshold and executes, removing `A` from `self.members` and revoking its access key [5](#0-4) . Because the deletion logic only removes requests where `r.member == A` (i.e., requests *A authored*), `R`'s confirmation set `{A, B}` is untouched.
4. Live members are now `{B, C, D}`; only 2 of them (`B` and, if it now confirms, `C`) have ever actually approved `R`, but `A`'s stale confirmation is still stored.
5. `C` calls `confirm(R)`. The check is `confirmations.len() as u32 + 1 >= num_confirmations` → `2 + 1 >= 3` → true, and the promise executes [6](#0-5) .

At no point does `confirm()` or `execute_request()` re-validate that every principal in `confirmations` is still in `self.members` (or holds a valid key in the legacy contract). The recorded-confirmations ledger diverges from the live-membership ledger, and the divergence is never reconciled before the equality is checked, so the request executes with genuinely fewer than `num_confirmations` currently-authorized approvals.

### Impact Explanation
This directly matches the Critical impact class "a multisig request executed below threshold." A `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` action can be pushed through with fewer live approvals than the configured `num_confirmations`, undermining the entire security guarantee of the k-of-n multisig (funds movement, key/permission changes, or code upgrades authorized with insufficient live quorum).

### Likelihood Explanation
This requires normal, expected multisig operations — no compromise of the foundation, no owner privilege beyond being an ordinary member, and no malformed deployment. Any multisig that has ever removed a member/key after that member/key confirmed (but did not originate) a still-pending request is exposed. Membership changes (staff turnover, key rotation, compromised-key removal) are a routine, anticipated operation for these contracts, making the scenario realistic rather than purely theoretical — and it is aggravated in exactly the case operators most want it to help: revoking a compromised key does not retroactively invalidate that key's prior confirmations on other pending requests.

### Recommendation
On `DeleteMember`/`DeleteKey` (and generally in `confirm`/`execute_request`), also scan `confirmations` for every pending request and remove entries belonging to the deleted member/key, or — more robustly — validate at confirm/execution time that every principal in the stored `confirmations` set is still present in `self.members` before counting it toward `num_confirmations`, discarding stale entries first.

Not independently executed in this session (index/tool access does not include a live NEAR runtime), but the trace is directly derivable from the code:

2. `add_request(R)` by any member; `confirm(R)` as `A`; `confirm(R)` as `B` → `confirmations(R) = {A,B}` [7](#0-6) .
3. Separate request `DeleteMember{A}` reaches 3 confirmations and executes via `execute_request` → `delete_member` [8](#0-7) [4](#0-3) ; `R`'s confirmations are untouched because `r.member == A` filter only matches requests A authored.
4. `confirm(R)` as `C`: `confirmations.len() (2) + 1 >= num_confirmations (3)` → true → `execute_request(R)` runs with only `B` and `C` as live confirmers, i.e., below the intended 3-of-4 live threshold [9](#0-8) .

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
