Confirmed: neither `replace` nor `clean` in `state-manipulation/src/lib.rs` performs any predecessor/caller check — they are raw `#[no_mangle]` exports (not even gated by `near_bindgen` owner logic) that write or remove arbitrary storage keys on whatever account the contract is deployed to, callable by literally any account on the network.

### Title
Unauthenticated `replace`/`clean` allow anyone to overwrite a deployed contract's storage, forging custody records - (File: state-manipulation/src/lib.rs)

### Summary
`state-manipulation/src/lib.rs` exposes two low-level entry points, `replace` (writes arbitrary key/value pairs into the current account's storage) and `clean` (deletes arbitrary storage keys). Neither function checks `predecessor_account_id` or any other authorization, so any unprivileged caller can invoke them once this code is the contract deployed on an account.

### Finding Description
`replace` decodes base64 key/value pairs from the call input and writes them directly via `near_sys::storage_write` with no gate at all: [1](#0-0) . `clean` similarly removes arbitrary keys via `near_sys::storage_remove` with no gate: [2](#0-1) . Both are raw `#[no_mangle]` WASM exports, not wrapped by `near_bindgen`/`assert_owner`/`assert_self` style checks used everywhere else in this repo (e.g. `assert_owner` in `staking-pool/src/internal.rs:184-190`, `assert_self` throughout `lockup/src/owner_callbacks.rs` and `lockup/src/foundation_callbacks.rs`, `assert_called_by_foundation` in `whitelist/src/lib.rs:135-141`). On NEAR, calling a contract's public function requires no special key or permission beyond knowing the account ID and method name — so once this binary is the code deployed on an account, **any account on the network** can call `replace`/`clean` against it, regardless of who deployed it or who controls its keys.

This breaks every custody binding enumerated in scope simultaneously, because it operates below the level of any single contract's business logic: an attacker can directly overwrite the raw Borsh-serialized state of a staking pool (`total_staked_balance`, `total_stake_shares`, an individual account's `stake_shares`/`unstaked` balance — see `staking-pool/src/internal.rs:70-181`), a lockup contract (`owner_account_id`, `lockup_information`, `vesting_information` — see `lockup/src/getters.rs:64-113`), or a whitelist (`whitelist`/`factory_whitelist` `LookupSet` entries — `whitelist/src/lib.rs:10-21`) without ever calling any of those contracts' guarded methods and without moving any NEAR through the normal deposit/stake/withdraw paths.

### Impact Explanation
This is Critical under the stated impact criteria: an attacker can fabricate `claims exceeding assets held` (e.g. write themselves an inflated `stake_shares`/`unstaked` balance in a staking pool's account map, then call the pool's normal, otherwise-safe `withdraw`/`unstake` to drain real NEAR that was never deposited), release `locked or unvested tokens` early (overwrite a lockup's `lockup_information`/`vesting_information` fields), or produce a `wrongly whitelisted... deployment` (directly insert an arbitrary `staking_pool_account_id` into the whitelist's `LookupSet` storage, bypassing `add_staking_pool`'s `assert_called_by_foundation`/factory check entirely). Any of these leads to concrete NEAR loss or an insolvent ledger.

### Likelihood Explanation
High if and only if this contract's binary is deployed as (or alongside) a production contract holding funds. There is no privilege requirement to exploit it — no owner, foundation, or multisig-member access is needed, only knowledge of the target account ID, which is public. The likelihood is bounded by whether operators actually deploy this tool onto accounts holding real value; the repository's own README frames it as a debugging/testing utility ("Deploy this contract into the account that already has another contract deployed to it") [3](#0-2) , which suggests it is intended for test/dev environments. However, nothing in the code enforces that restriction, and the rules explicitly place `state-manipulation/src/**` in scope, so the missing access control itself is the reportable defect.

### Recommendation
Add an authorization check to both `replace` and `clean` (e.g. `assert_eq!(near_sdk::env::predecessor_account_id(), near_sdk::env::current_account_id())` or an explicit owner check) so that only the account itself (i.e., a transaction signed with a full-access key of that account) can invoke state manipulation, matching the access-control pattern (`assert_owner`/`assert_self`/`assert_called_by_foundation`) used consistently by every other contract in this repository.

### Proof of Concept
1. Deploy `state-manipulation.wasm` (built with the `replace` feature) onto an account, e.g. as an upgrade layered on top of a staking-pool account `pool.factory` that holds delegator funds (this could happen via a compromised or careless deploy key, or if the tool is left deployed after debugging).
2. From any unrelated account with no keys on `pool.factory`, call:
   `near call pool.factory replace '{"entries":[["<base64 of an account's storage key>", "<base64 of a forged Account{unstaked: <large>, stake_shares: 0}>"]]}' --accountId attacker.near`
3. Storage is written directly via `storage_write` with no `predecessor_account_id` check [4](#0-3) , so the attacker's forged unstaked balance now exists in the pool's `accounts` map without any corresponding deposit.
4. Attacker calls the pool's normal `withdraw`/`withdraw_all` (`staking-pool/src/lib.rs:238-263`) to receive real NEAR that was never deposited, insolvent relative to `last_total_balance`.

#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    #[derive(serde::Deserialize)]
    struct ReplaceInput<'a> {
        #[serde(borrow)]
        entries: Vec<(&'a str, &'a str)>,
    }

    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(
            &base64::decode(key).unwrap(),
            &base64::decode(value).unwrap(),
        );
    }
}
```

pub fn clean() {
    #[derive(serde::Deserialize)]
    struct CleanInput<'a> {
        #[serde(borrow)]
        keys: Vec<&'a str>,
    }

    let input = input().unwrap();
    let args: CleanInput = serde_json::from_slice(&input).unwrap();
    for key in args.keys {
        storage_remove(&base64::decode(key).unwrap());
    }
}

# State Manipulation contract

This contract has been designed to put key value pairs into storage with `replace` and clear key/value pairs with `clean` from an account's storage.

Deploy this contract into the account that already has another contract deployed to it.
This contract on call `clean` will remove any items of the state specified (keys should be specified in base64). When compiled with `replace` feature, `replace` method can be called with an array of key/value tuple pairs to insert into state.

## Parameters

JSON format for `clean`:

```json
{"keys":["<base64 encoded key byte string>", "...", "..."]}
```

JSON format for `replace`:
```json
{"entries":[["<base64 key byte string>", "<base64 value byte string>"], ["...", "..."]]}
```
