### Title
SSH executor cancellation relies on unenforceable SIGKILL channel-request, allowing backgrounded/detached remote processes to survive job cancellation - ([File: helpers/ssh/ssh_command.go])

### Summary
`Client.Run` in `helpers/ssh/ssh_command.go` cancels a running remote command solely by sending an SSH `signal` channel request (`session.Signal(ssh.SIGKILL)`) and then closing the channel, discarding any error from the signal request. Because many `sshd` implementations do not honor `signal` requests for exec channels, and because closing the channel only guarantees the direct child (the shell) is torn down — not any subprocess a job script has detached from that channel's stdio — a job can outlive the cancellation of `Run()` on the remote host.

### Finding Description
`Client.Run` starts the job's command via `session.Start(cmd.Command)` and waits on a `waitCh` fed by `session.Wait()` in a goroutine: [1](#0-0) 

On `ctx.Done()` (build cancellation/timeout), the only termination mechanism sent to the remote host is: [2](#0-1) 

`session.Signal` maps to the SSH `signal` channel request defined in RFC 4254 §6.9. Support for this request on the *exec* channel of a non-interactive session is inconsistent across `sshd` implementations, and its error is explicitly discarded (`_ = session.Signal(...)`), so Runner has no way to detect that the signal was ignored. The only other action taken is `session.Close()`, which tears down the SSH channel but does not guarantee that a grandchild process detached from that channel's stdio (e.g., via `setsid ... &`, `nohup ... &`, or a double-fork) is reaped — the `sshd` server generally only tracks/kills the direct child tied to the channel's PTY/pipes, not descendants that have re-parented and redirected their I/O away from it.

A job script fully controlled by the attacker (an unprivileged CI pipeline author) can therefore do, e.g.:
```
setsid sh -c 'sleep 3600 ...malicious...' < /dev/null > /tmp/out 2>&1 &
disown
```
and then continue or exit normally. When the build is cancelled, `session.Signal` either errors (ignored) or is not delivered to the detached grandchild at all; `session.Close()` closes the channel, which triggers `session.Wait()` to return quickly (once the transport signals channel closure), so `Run()` returns promptly to the caller (`executors/ssh/ssh.go` `Run`) — while the backgrounded process keeps running on the remote host.

This is exploitable specifically through the SSH executor, which is explicitly designed to allow the remote host to be shared: it registers `SharedBuildsDir: true` and `features.Shared = true`: [3](#0-2) 

No code path in `Client.Run`, `executors/ssh/ssh.go`, or `Cleanup` re-verifies remote process termination, enumerates/reaps orphaned processes, or uses a stronger isolation primitive (e.g., a per-job process group/cgroup killed as a unit on the remote host). The existing "check" (the SIGKILL signal request) is not actually enforced against an adversarial script.

### Impact Explanation
On a shared SSH executor host, a cancelled or timed-out job from one project can leave a runaway background process executing on that host after `Run()`/`Cleanup()` report completion. This can interfere with subsequent, unrelated jobs from different projects scheduled on the same shared host (resource exhaustion, port/file contention, persistence across job boundaries), which violates the invariant that a cancelled job must actually terminate and not leak workload into the next job's execution context.

### Likelihood Explanation
This requires only a normal, unprivileged CI job author who can supply arbitrary shell script content executed via the SSH executor (`s.BuildShell.CmdLine`/`cmd.Script`) — a standard capability of any pipeline author. No special sshd/host misconfiguration beyond default SSH executor deployment is needed; the technique (`setsid`/`nohup`/disown detachment) is a well-known, easily repeatable shell idiom. The behavior is deterministic given a `sshd` that does not enforce `signal` requests on detached grandchildren (a common, not "admin-misconfigured" default).

### Recommendation
Do not rely solely on the SSH `signal` channel request for cancellation. On job start, wrap the remote command so it and all descendants belong to a killable group the Runner can reliably terminate on cancellation — e.g., start the command under a fresh process group/session (`setsid`) whose PID or PGID is captured and explicitly `kill -9 -PGID`'d over a follow-up exec channel when `ctx.Done()` fires, rather than trusting `session.Signal`. Additionally, check and surface the error from the signal/kill request instead of discarding it, and consider failing the build loudly (or retrying with a stronger kill mechanism) if remote termination cannot be confirmed.

### Proof of Concept
Using the repo's `helpers/ssh/stub_ssh_server.go` test harness:
1. Configure the stub server's session handler to spawn the requested command via `setsid`/background semantics (or simply ignore incoming `signal` channel requests, as `handleSession` already does not implement a `case "signal":` branch, so any signal request will hit `default: return fmt.Errorf("unknown request type: %s", ...)` and be swallowed by the discarded error in `Client.Run`).
2. In a Go test, call `Client.Run(ctx, cmd)` with a `cmd.Command` that, on the stub server side, keeps the backing `exec.CommandContext`'s child process running (e.g., have the stub spawn a detached shell that itself spawns a long sleep) after the exec channel closes.
3. Cancel `ctx` shortly after start.
4. Assert: `Run()` returns within a short bound (e.g., < 1s), **and** separately assert the stub server still reports the underlying command/process as running (e.g., via a side channel/flag the stub sets before/after the detached command exits), proving Runner-side cancellation did not stop remote execution.
