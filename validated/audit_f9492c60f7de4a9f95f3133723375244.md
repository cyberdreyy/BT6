### Title
Missing authorization in `setApr`/`setAprs`/`setAprsWithBuffer` while `idleCDO` is unset lets any EOA fix the vault APR - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.setApr` skips its caller check entirely when `idleCDO == address(0)`. Between `initialize` and the owner wiring the CDO via `setWhitelistedCDO`, any unprivileged caller can set `lastApr` and `unscaledApr` to arbitrary values bounded only by `maxApr` (default 20e18). This mirrors the Mattermost flaw: a permission check that is silently skipped in a specific state, letting a party that should have no authority configure a privileged parameter. A KYC-passing lender can fix the epoch APR at the cap and harvest excess borrower-funded interest.

### Finding Description
`setApr` gates callers with `msg.sender != _cdo && msg.sender != manager`, but only inside `if (_cdo != address(0))`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:225-235
function setApr(uint256 _apr) public {
  address _cdo = idleCDO;
  // if cdo is not yet set we skip the check (this can happen only during the setup)
  if (_cdo != address(0)) {
    if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
  }
  uint256 _maxApr = maxApr;
  if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
  lastApr = _apr;
}
```

Both `setAprs` (lines 206-210) and `setAprsWithBuffer` (lines 217-220) funnel into `setApr`, so in the same window an attacker also controls `unscaledApr`. In `IdleCDOEpochVariant`, the APR for the next epoch is only updated at `stopEpochWithDuration`/`stopEpoch` time; `startEpoch` does not overwrite `lastApr`. Consequently, whatever `lastApr` exists when the first epoch starts drives `expectedEpochInterest()` for the entire epoch. Owner pre-setting the APR during setup does not help, because the attacker can call `setAprs` again after the owner's call and before `setWhitelistedCDO` — the check is still skipped and ordering favors the attacker (anyone can re-call it; there is no "already set" latch).

A secondary angle: the attacker can set `unscaledApr = 0` while the intended APR is nonzero. `requestWithdraw` routes withdraws into the APR0 bucket (`apr0Users`, `apr0TotalPrincipal`) whenever `unscaledApr == 0` (lines 285-294), corrupting the epoch's withdraw accounting versus the intended fixed-APR flow.

### Impact Explanation
An attacker who is a KYC-passing AA lender:
1. Sets `lastApr = unscaledApr = maxApr` (20e18, i.e. 20%) during the unwired window.
2. Deposits into the AA tranche; owner wires the CDO; manager starts epoch 1.
3. The epoch accrues `expectedEpochInterest` at 20% instead of the intended rate. The honest borrower funds that interest at `stopEpoch`, and the attacker redeems the excess through `requestWithdraw`/`claimWithdrawRequest` or instant withdraw.

Quantified loss: `(maxApr - intendedApr) * epochTvl * epochDuration / YEAR`, paid by the borrower's repayment into the pool and captured pro rata by the attacker. For a $1M TVL vault on a 30-day epoch with an intended 5% APR, the excess is ~$12.3k per epoch until owner intervention. Alternatively, `unscaledApr = 0` misroutes all epoch-1 withdraw requests into APR0 accounting, distorting interest settlement.

### Likelihood Explanation
Medium-low. Exploitation requires the deployment flow to leave a non-atomic gap between `initialize` and `setWhitelistedCDO` on the strategy. If `IdleCreditVaultFactory` wires `idleCDO` in the same transaction as `initialize`, the window does not exist in factory-deployed vaults; manual proxy deployments or upgrades that re-zero `idleCDO` remain exposed. Note that the window cannot be closed by the owner acting first — the attacker can always re-set the values as long as `idleCDO == 0`, so a single non-atomic deployment suffices. Whether the factory deployment is atomic could not be fully confirmed within this review; that is the main uncertainty on likelihood.

### Recommendation
Remove the open window: in `setApr`, revert when `idleCDO == address(0)` unless `msg.sender == owner()` (or `manager`), rather than skipping the check entirely. Alternatively set the APR atomically inside `initialize` and/or `setWhitelistedCDO`, and revert `setApr` before the CDO is configured.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract SetAprAuthPoC is Test {
    IdleCreditVault strategy;
    address owner = makeAddr("owner");
    address manager = makeAddr("manager");
    address borrower = makeAddr("borrower");
    address attacker = makeAddr("attacker"); // unprivileged EOA / KYC lender
    IERC20Detailed constant USDC = IERC20Detailed(0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48);

    function setUp() public {
        vm.createSelectFork(vm.envString("ETH_RPC_URL"));
        // deploy behind proxy in real deployments; direct instance suffices to show the auth gap
        strategy = new IdleCreditVault();
        // simulate uninitialized state by using a fresh proxy-equivalent:
        // call initialize as the deployer would
        strategy.initialize(address(USDC), owner, manager, borrower, "Borrower", 5e18);
        // NOTE: idleCDO is still address(0) — setWhitelistedCDO not yet called
    }

    function testAnyEOACanSetAprBeforeCdoWired() public {
        assertEq(strategy.idleCDO(), address(0));
        assertEq(strategy.lastApr(), 5e18);

        // attacker (unprivileged) sets APR to the default cap — no revert
        vm.prank(attacker);
        strategy.setAprs(20e18, 20e18);

        assertEq(strategy.lastApr(), 20e18);
        assertEq(strategy.unscaledApr(), 20e18);

        // owner can still fix it while unwired, but attacker can overwrite again:
        vm.prank(owner);
        strategy.setAprs(5e18, 5e18);
        vm.prank(attacker);
        strategy.setAprs(20e18, 20e18);
        assertEq(strategy.lastApr(), 20e18);

        // once owner calls setWhitelistedCDO, the attacker is locked out —
        // but only then; epoch 1 runs at the attacker's 20% APR.
    }
}
```
