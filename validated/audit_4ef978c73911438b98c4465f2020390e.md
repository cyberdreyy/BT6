### Title
Confirmations from deleted multisig members remain counted toward quorum on other pending requests - (File: `multisig2/src/lib.rs`)

### Summary
This is a valid structural analog of the reported bug class: a value that should be re-validated against the current authoritative set (live delegate/live member) is instead left stale after that set changes, letting a party who is no longer entitled continue to count toward a binding threshold.

### Finding Description
`MultiSigContract::confirm` counts entries in the `confirmations` map for a given `request_id` against `self.num_confirmations` to decide whether to execute a request: [1](#0-0) 

`delete_member` is the only place member removal is handled. It removes the deleted member's own *created* requests (`r.member == member`) and clears the `num_requests_pk` counter for that member, but it never scans `self.confirmations` to strip that member's confirmation from *other* still-pending requests that the member confirmed before being deleted: [2](#0-1) 

`current_member()` is used only when a live member is *adding* a new confirmation (`confirm`/`add_request`), so a removed member cannot add a *new* confirmation - but their confirmation strings recorded earlier are never invalidated: [3](#0-2) 

This is the same class of bug as the reported issue: a state value (`_delegateBalances` in the report, `confirmations` here) is derived from membership in a set (`delegate`/`multisig member`) at the time it was recorded, but is never corrected when that membership changes (`msg.sender == _delegate` self-delegation vs. `member` being deleted). The binding that should hold is:

`confirmations.len() for request R == number of currently-live members who confirmed R`

After a `DeleteMember` request executes, this equality is broken: a stale confirmation from a now-removed member still counts.

### Impact Explanation
If `num_confirmations` is, say, 3 and a member confirms a pending `Transfer` or `FunctionCall` request, and is later removed via a separate `DeleteMember` request (e.g., due to key compromise or offboarding), that pending request retains the removed member's confirmation. The remaining live members then only need `num_confirmations - 1` *new* confirmations to reach `confirmations.len() + 1 >= num_confirmations` and execute the request - effectively executing a multisig request below the intended threshold of currently-authorized signers. This matches the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
This requires a normal, expected operational sequence (a member confirms a request, then is removed before that request reaches quorum) with no special privilege beyond ordinary multisig membership - the attacker does not need to be the one removed; any remaining member benefits from the stale confirmation. Given that member rotation (key compromise, offboarding) is a routine and even security-motivated multisig operation, and that a partially-confirmed request sitting active during a member removal is plausible in real usage, likelihood is moderate.

### Recommendation
When executing `DeleteMember`, iterate `self.confirmations` for all active `request_id`s and remove any confirmation entry keyed by `member.to_string()`, so that quorum is always computed strictly against the current member set. Alternatively, recompute/validate confirmer membership live inside `confirm`/`execute_request` rather than trusting the persisted `HashSet<String>`.

### Proof of Concept
1. Initialize `MultiSigContract` with 4 members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R` (e.g. `Transfer`).
3. `B` calls `confirm(R)` → `confirmations = {B}` (len 1 < 3, not yet executed).
4. Separately, members create and confirm a `DeleteMember { member: B }` request with 3 confirmations, executing it - `B` is removed from `members`, but `confirmations` for `R` still contains `B` (see `delete_member`, `multisig2/src/lib.rs:355-379`, which only touches requests where `B` is the *creator*, not confirmer).
5. `C` calls `confirm(R)` → `confirmations.len() + 1 = 3 >= num_confirmations(3)` → `R` executes, having received live confirmations only from `A` (creator, implicit) and `C`, plus the stale confirmation from now-removed `B` - i.e., executed with only 2 currently-authorized confirmers instead of the required 3.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

        let member = if env::current_account_id() == env::predecessor_account_id() {

                    .try_into()

            }

                account_id: env::predecessor_account_id(),
            }
        };
        if self.members.contains(&member) {
            Some(member)

            None
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
