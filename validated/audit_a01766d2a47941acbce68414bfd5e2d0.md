### Title
Cross-user response hijacking via unscoped `MessageId` key in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`(*handler).HandleLegacyUserMessage` stores each user's callback in `h.savedCallbacks` keyed solely by the client-supplied `msg.Body.MessageId`, with no binding to the message signer/sender and no collision check. An attacker who submits a `web_api_trigger` request with the same `MessageId` string as a victim's still in-flight request will silently overwrite the victim's saved callback, so the DON's response intended for the victim is delivered to the attacker instead.

### Finding Description
`api.Message.Validate` (`core/services/gateway/api/message.go:54-88`) only checks length/format of `MessageId` (non-empty, ≤128 bytes, no trailing null byte) and verifies the signature belongs to *some* valid signer — it never enforces uniqueness or binds the ID to the signer identity.

The gateway's synchronous request path, `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`), validates the message, then calls `h.HandleLegacyUserMessage(ctx, msg, callback)` and blocks on `callback.Wait(ctx)` until a response arrives or times out.

Inside `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`):
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
```
The map key is the raw `MessageId` with no per-sender namespacing and no existence check (contrast with the newer v2 `httpTriggerHandler.setupCallback`, `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:398-405`, which explicitly rejects a reused `requestID` with `jsonrpc.ErrConflict`). Any two different signers who happen to use the same `MessageId` string collide, and the second write silently clobbers the first.

When the DON node later responds, `handleWebAPITriggerMessage` (`core/services/gateway/handlers/capabilities/handler.go:148-162`) looks the callback up purely by `msg.Body.MessageId`:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
```
It has no way to tell whether `savedCb` still belongs to the original requester — if the attacker's request overwrote the entry, the DON's response (intended for the victim) is delivered to the attacker's blocked HTTP call instead, and the victim's own `callback.Wait` in `gateway.ProcessRequest` eventually times out with `RequestTimeoutError`.

### Impact Explanation
This is cross-user response confusion: an unprivileged attacker can intercept another user's DON response payload by colliding on `MessageId`, and the victim's request silently fails (times out). Since `web_api_trigger` responses can carry sensitive trigger/workflow data returned by the DON, this constitutes attacker-controlled disclosure of another user's response data and denial of service for the victim's request — matching the "cross-user response confusion" / unauthorized access to another user's request bounty class.

### Likelihood Explanation
Exploitation requires the attacker to know or guess the exact `MessageId` value the victim is using and to submit a colliding request while the victim's request is still in-flight (the window between the gateway forwarding the request to DON nodes and receiving the node's response). No credentials beyond the ability to sign and submit a gateway HTTP request are needed (`Validate()` accepts any valid ECDSA signature from any address). If client SDKs use predictable, low-entropy, or sequential `MessageId`s, or if the attacker can enumerate/guess likely IDs, this is fully reproducible and repeatable; the in-flight window can be several hundred milliseconds to seconds depending on DON responsiveness, which is a workable race for an automated attacker.

### Recommendation
Namespace `savedCallbacks` (and equivalent maps in `handler.dummy.go`) by `(sender, MessageId)` instead of `MessageId` alone, or reject new requests whose `MessageId` already has an in-flight entry (mirroring the `setupCallback` collision check already used in the v2 `httpTriggerHandler`). Additionally, `handleWebAPITriggerMessage`/`HandleNodeMessage` should verify that the DON response's echoed sender/request context matches the original requester before dispatching the saved callback.

func (m *Message) Validate() error {
	if m == nil {

		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
