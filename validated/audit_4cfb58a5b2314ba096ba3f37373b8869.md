### Title
Missing lower-bound validation on `num_confirmations` allows the multisig K-of-N threshold to collapse to a single confirmation - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
Neither the `multisig` nor `multisig2` contracts validate that `num_confirmations` is at least `1` (or `>0`), either at initialization (`new`) or when it is later changed via the `SetNumConfirmations` request action. Because the threshold check in `confirm()` is `confirmations.len() as u32 + 1 >= self.num_confirmations`, setting `num_confirmations = 0` makes this comparison always true on the very first confirmation, so any single key/member can execute arbitrary multisig requests (transfers, `DeployContract`, `AddKey`, etc.) without the intended K-of-N approval.

### Finding Description
The binding the multisig contract is supposed to enforce is: `confirmations actually collected ("live" approvals) >= num_confirmations (the configured threshold)` before a request executes.

`MultiSigContract::new` in `multisig/src/lib.rs` accepts `num_confirmations: u32` with no validation at all: [1](#0-0) 

`multisig2::new` adds only a relative check (`members.len() >= num_confirmations`), which is trivially satisfied by `num_confirmations = 0`: [2](#0-1) 

The `SetNumConfirmations` request action, executed via the normal multisig request/confirm flow, likewise applies the new value with no bound check: [3](#0-2) 

The threshold check itself is: [4](#0-3) 
and the identical pattern in `multisig2`: [5](#0-4) 

If `num_confirmations == 0`, then on the *first* `confirm()` call, `confirmations.len()` is `0`, so `0 + 1 >= 0` is always `true`, and `execute_request` runs immediately — before any of the intended "K" approvals have been collected. This is structurally the same bug class as the reported Oval issue: a degenerate/zero parameter value (there, `maxTraversal == 0`; here, `num_confirmations == 0`) causes the code path meant to gate on a threshold/staleness condition to always short-circuit into the "unprotected" branch, silently defeating the mechanism designed to guarantee that only a properly-authorized quorum can act.

### Impact Explanation
This directly breaks the "confirmations counted versus live members/threshold" custody binding called out in scope: a multisig request (including `Transfer` of NEAR held by the account) can be executed with a single confirmation instead of the configured K-of-N. This matches the explicit Critical impact category: "a multisig request executed below threshold." Any one member (holder of one access key, in `multisig`, or one `MultisigMember` in `multisig2`) can unilaterally move all NEAR held by the multisig account, deploy arbitrary code to it, or add full-access keys, defeating the entire purpose of the multisig scheme.

### Likelihood Explanation
The gap exists at both initialization and via ongoing operation:
- If a multisig is deployed with `num_confirmations = 0` due to an input/config error (there is no assertion preventing this), the contract is unprotected from the very start — no privileged action beyond calling `new` with bad arguments is required, which is a normal deployment step, not an "ignore of documented initialization" (there is no documented lower bound to ignore).
- Even for correctly-initialized multisigs, if `SetNumConfirmations { num_confirmations: 0 }` is ever proposed and reaches quorum (e.g., by accident, or by a value substitution bug in client tooling), all subsequent security collapses to 1-of-N with no way to detect it apart from calling `get_num_confirmations`.

### Recommendation
Add an explicit lower-bound assertion (`num_confirmations >= 1`, and ideally `num_confirmations >= 2` for genuine multi-party security) in:
- `MultiSigContract::new` in both `multisig/src/lib.rs` and `multisig2/src/lib.rs`.
- The `SetNumConfirmations` action handler in `execute_request` in both contracts, so it cannot be reduced to `0` (or below a sane minimum) after deployment.

### Proof of Concept
1. Deploy (or reconfigure via `SetNumConfirmations`) a `multisig`/`multisig2` contract with `num_confirmations = 0`.
2. Any single member calls `add_request_and_confirm` with a `Transfer` action to their own account for the full contract balance.
3. In `confirm()`, `confirmations.len() as u32 + 1 (=1) >= self.num_confirmations (=0)` evaluates `true` on the first confirmation, so `execute_request` runs immediately and the transfer promise is scheduled, draining the account with a single signature instead of the configured K-of-N. [4](#0-3)
