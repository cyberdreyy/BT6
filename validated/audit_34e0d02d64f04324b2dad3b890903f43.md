### Title
JWT Replay-Protection Cache Uses a Non-Atomic Check-Then-Record Pattern, Allowing Concurrent Replay of the Same Trigger JWT - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The Gateway's `WorkflowMetadataHandler.Authorize()` function protects HTTP Trigger requests from JWT replay by checking a `jwtReplayCache` before authorizing a request and only recording the JWT ID (`jti`) as "used" *after* the full authorization flow succeeds. Because the check (`isReplay`) and the mark-as-used step (`recordUsage`) are two separate, independently-locked operations rather than a single atomic check-and-set, concurrent requests carrying the identical JWT can all pass the replay check before any of them records usage — mirroring the report's underlying bug class: a cache invalidation/consistency mechanism whose state-defining update is decoupled from (and lags) the operation it is supposed to gate.

### Finding Description
`Authorize()` performs the following sequence for every incoming HTTP Trigger request: [1](#0-0) 

1. Verify the JWT signature/claims (`utils.VerifyRequestJWT`).
2. Call `h.jwtCache.isReplay(claims.ID)` — a read-locked map lookup.
3. Validate the signer against the workflow's `authorizedKeys`.
4. Only on success, call `h.jwtCache.recordUsage(claims.ID)` — a write-locked map insert, executed after all prior checks pass.

`isReplay` and `recordUsage` are implemented as two independent critical sections: [2](#0-1) 

There is no lock held across the "check" and "record" steps, and no synchronization primitive (e.g., a single atomic `LoadOrStore`) enforces that a `jti` can only pass step 2 once. If two (or more) requests bearing the same signed JWT arrive concurrently — trivially reproducible by an unprivileged client replaying a captured/sniffed JWT-signed request in parallel — both requests observe `isReplay == false` in step 2 (since neither has reached step 4 yet), both pass the signer-authorization check in step 3, and both are authorized and forwarded to the workflow DON as legitimate HTTP Trigger invocations. Only after both complete does the map end up holding a single entry, but by then the JWT has already been used more than once.

This is the same root-cause pattern flagged in the external report: a security-relevant cache/state update (`STATE_UPDATE_TIMESTAMP` / `LAST_STATE_PERSIST_TIMESTAMP` there, `jwtReplayCache` entry here) is updated at the wrong point relative to the operation it is meant to gate, and the check against that cache does not correctly reflect all outstanding in-flight uses, breaking the single-use invariant the cache exists to enforce.

### Impact Explanation
JWTs used to authorize HTTP Trigger requests are meant to be single-use (per the code's own comment: "JWT token has already been used. Please generate a new one with new id (jti)"). This anti-replay guarantee is a security boundary: it limits the blast radius of a leaked/intercepted trigger JWT to a single workflow execution. The race described here allows an attacker who obtains (or replays) one valid signed JWT to trigger the same workflow multiple times concurrently, defeating the single-use/anti-replay control. Depending on the workflow's semantics this can cause duplicate/unauthorized job runs, resource exhaustion of the DON via forced concurrent executions, or, if the workflow moves funds/state per trigger, duplicated fund-moving actions.

### Likelihood Explanation
Exploitation requires only the ability to send two (or more) requests with the same previously-obtained valid JWT to the Gateway's HTTP Trigger endpoint within the same authorization window — well within reach of any unprivileged client capable of capturing or being handed one valid signed request (e.g., via network observation, logging, or a legitimate single trigger call replayed by the client itself). No privileged or node-operator access is required; this is purely a race in the internet-facing gateway request path (`http_trigger_handler.go` → `WorkflowMetadataHandler.Authorize`).

### Recommendation
Make the check-and-mark operation atomic under a single lock (or use a concurrency-safe primitive such as `sync.Map`'s `LoadOrStore`) so that a `jti` can be claimed by at most one in-flight request:
```go
func (cache *jwtReplayCache) claim(jti string) bool {
    cache.mu.Lock()
    defer cache.mu.Unlock()
    if _, exists := cache.cache[jti]; exists {
        return false // already used/in-flight
    }
    cache.cache[jti] = time.Now()
    return true
}
```
Call `claim(claims.ID)` immediately after JWT verification (before/instead of the later `recordUsage`), and if it returns `false`, reject the request as a replay before doing any further authorization work. If the request subsequently fails authorization for other reasons, decide explicitly whether the `jti` should remain marked used (to prevent retry abuse) or be released — but the initial claim/check must be atomic to close the race window.

### Proof of Concept
1. Obtain one valid, signed HTTP Trigger JWT for an authorized signer/workflow (e.g., capture a legitimately issued request).
2. Fire two (or more) concurrent HTTP Trigger requests to the Gateway using the identical JWT (same `jti`), e.g. with a simple concurrent HTTP client:
```
for i in 1 2; do
  curl -s -X POST https://gateway/host/trigger -H "Authorization: Bearer $JWT" -d "$PAYLOAD" &
done
wait
```
3. Observe that both requests reach `WorkflowMetadataHandler.Authorize`, both pass `isReplay(claims.ID) == false` before either calls `recordUsage`, and both are authorized — resulting in the workflow being triggered twice from a single JWT, contrary to the intended single-use replay protection.

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```
