### Title
Programmable borrower `onStopEpoch` reverts forever on a persistently illiquid ERC4626 vault, permanently blocking `stopEpoch` and the default path — funds frozen - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
When `isProgrammableBorrower` is enabled, `IdleCDOEpochVariant._stopEpoch` delegates liquidity recall to `ProgrammableBorrower.onStopEpoch`. If the borrower contract's accounting says the vault shares cover the shortfall but the external ERC4626 `vault.withdraw` reverts, `onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable` instead of returning `false`. The revert bubbles through `stopEpoch`, so the transaction fails atomically: the epoch never stops and — critically — `_handleBorrowerDefault` is never reached. This is the same bug class as the f2fs infinite flush loop: an operation whose failure mode is "retry forever" with no terminal/error escape path. An unprivileged attacker can make the ERC4626 withdrawal permanently revert (e.g., drain/borrow all liquidity out of the third-party vault, or occupy its withdrawal queue), permanently freezing the epoch and every tranche holder's and pending receipt's funds.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch` (contracts/IdleCDOEpochVariant.sol:395-404), the flow is:

```solidity
if (!IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)) {
  _handleBorrowerDefault(_amountToPullFromBorrower + _pendingWithdraws);
  return;
}
```

Only a `false` return triggers the default path. But in `ProgrammableBorrower.onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:240-254):

```solidity
if (shortfall > _currentVaultAssets()) return true;
try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) { ... }
catch { revert StopEpochVaultLiquidityUnavailable(); }
```

The guard only distinguishes "shares don't cover the shortfall" (return true → the later `transferFrom` fails → default) from "shares cover it but the withdrawal reverted" (revert → retry). There is no third branch for "covered but the vault can never pay". If `vault.withdraw` deterministically reverts — e.g., an external lending-vault utilization crunch, a permanently paused vault, or a withdrawal-queue vault whose liquidity an attacker keeps draining — every `stopEpoch`/`stopEpochWithDuration` call reverts. The epoch state machine cannot advance past the running phase: `epochNumber` never increments, `pendingWithdraws` are never collected, withdraw requests can never be claimed (`_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest`), and interest/default accounting never runs.

The design even hard-codes the assumption of transience — the code comment at ProgrammableBorrower.sol:243-244 and IdleCDOEpochVariant.sol:397 say "transient ERC4626 liquidity failures can be retried" — but provides no escape if the failure is permanent. `setVault` cannot be used as an escape hatch either, since it requires `vault.balanceOf(address(this)) == 0` (ProgrammableBorrower.sol:165), and unwinding the position requires the very `vault.withdraw`/`redeem` call that is failing.

### Impact Explanation
Permanent freezing of all funds in the CDO: while the epoch is stuck running, lenders cannot claim queued withdraws, new epochs can't start, and the borrower default path (the designed failure valve) is unreachable because `onStopEpoch` reverts before `_handleBorrowerDefault` can execute. The frozen amount equals the entire `pendingWithdraws` + interest + all tranche NAV that can only be recovered through epoch progression or default. An unprivileged attacker profits indirectly (e.g., keeps utilization of the external vault at 100% for their own borrow) while imposing a permanent freeze costing the pool its full TVL until the external vault recovers — which the attacker controls if they keep renewing borrows.

### Likelihood Explanation
The attacker is any EOA interacting with the third-party ERC4626 vault — fully in scope. For a shared liquidity vault (Morpho/Aave-style ERC4626), draining available liquidity so `withdraw` reverts is a standard, repeatable action costing only interest on the attacker's own borrow. The protocol has no way to distinguish transient from permanent failure, and no privileged fallback exists (`setVault` is blocked by the non-zero share balance). The only mitigation is that the honest owner could keep retrying — the exact "infinite loop" the upstream fix eliminated.

### Recommendation
Do not revert in `onStopEpoch` when `vault.withdraw` fails. Return `false` (or introduce a tri-state) so `_stopEpoch` falls through to `_handleBorrowerDefault`, letting the facility enter the defaulted state and activate the loss waterfall / recovery distribution instead of freezing. Alternatively, bound retries: track consecutive `StopEpochVaultLiquidityUnavailable` failures (or a deadline set on first failure) and allow the owner/manager to force the default path after the threshold.

### Proof of Concept
Foundry fork PoC sketch (programmable-borrower deployment):

```solidity
// Setup: epoch running, isProgrammableBorrower = true, all idle cash parked in `vault`.
// Attacker (EOA) drains vault liquidity: borrow/supply-manipulate so vault.withdraw reverts,
// while ProgrammableBorrower still holds shares covering the shortfall
// (convertToAssets(shares) >= shortfall but vault has 0 liquid asset).

// Lender created a pending withdraw in the previous buffer:
cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));

// Warp past epoch end.
vm.warp(cdoEpoch.epochEndDate() + 1);

// Every stopEpoch attempt reverts — the "infinite flush loop":
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(10e18, 0);

// The retry never converges and never falls back to default:
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 1); // even close-pool can't force default

assertFalse(cdoEpoch.defaulted());          // default path unreachable
assertEq(strategy.epochNumber(), epochBefore); // epoch can never advance

// Lender can never claim:
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimWithdrawRequest();
```

Key precondition the PoC must satisfy: `shortfall <= _currentVaultAssets()` (shares cover it) while `vault.withdraw` reverts — exactly the branch at ProgrammableBorrower.sol:245-253 that converts a funding failure into a non-terminal revert instead of a default.
