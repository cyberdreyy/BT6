### Title
Pending APR0 withdraw request permanently reverts `stopEpoch` after any APR change, freezing all vault funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Open5GS CVE is a null-pointer dereference on a crafted request hitting uninitialized state, crashing the AMF. The analog in `IdleCreditVault` is a missing-state-validation DoS: `prepareStopEpochWithApr0` unconditionally reverts whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`, with no path to clear the APR0 bucket. An unprivileged KYC'd lender who deposits while `unscaledApr == 0` and files a dust `requestWithdraw` plants a latent revert that bricks every subsequent `stopEpoch` as soon as the honest manager/CDO sets any non-zero APR — a routine, expected operation.

### Finding Description
`requestWithdraw` routes requests into the APR0 bucket whenever `unscaledApr == 0` at request time, incrementing `apr0TotalPrincipal` via `_requestWithdrawApr0` (`IdleCreditVault.sol:285-286`, `567-577`). `apr0TotalPrincipal` is only ever cleared inside `prepareStopEpochWithApr0` (`line 540`), which is called by `IdleCDOEpochVariant.stopEpoch`. But `prepareStopEpochWithApr0` reverts `NotAllowed` when `_principal != 0 && unscaledApr != 0` (`lines 502-508`).

Sequence:

1. Vault runs an epoch (or buffer) with `unscaledApr == 0` — a supported mode.
2. Attacker (any KYC-passing lender) deposits a dust amount and calls `requestWithdraw` for e.g. 1 wei of underlying through the CDO. `apr0TotalPrincipal = 1`, `apr0Users[attacker].principal = 1`.
3. Manager honestly raises APR via `setAprs`/`setAprsWithBuffer` for the next epoch — a normal operational call.
4. Manager calls `stopEpoch` → `prepareStopEpochWithApr0` reverts `NotAllowed`.
5. Setting APR back to 0 and retrying still reverts permanently if any other epoch transition already ran, and even the APR=0 path only clears the bucket at `stopEpoch` — but the revert check happens *before* `apr0TotalPrincipal = 0`, so the only escape is for the manager to set `unscaledApr` back to exactly 0 and stop the epoch at APR 0 (forfeiting the intended rate for that epoch) or never. There is no admin function to delete `apr0TotalPrincipal` or a user's `apr0Users` entry.

The broken invariant is epoch-liveness/solvency continuity: a single dust receipt written under one APR regime makes the epoch state machine unclosable under any other regime. Existing guards (`_onlyIdleCDO`, `maxApr` cap, loss-recovery gating in `requestWithdraw` lines 262-271) do not cover this — the guard itself is the bug: it validates a stale precondition (`unscaledApr != 0`) at settle time rather than at request time, exactly the "dereferenced null state on a crafted request" shape.

### Impact Explanation
While `apr0TotalPrincipal` is stuck non-zero with `unscaledApr != 0`, `stopEpoch` always reverts, so `epochEndDate` never advances, `epochNumber` never increments, and `_claimFundedWithdrawRequest` reverts at the `epochNumber <= lastWithdrawRequest[_user]` check (`line 326`) for every withdrawer. All borrower-held funds are unreachable and all pending receipts are frozen. Recovery requires the honest manager to roll `unscaledApr` back to 0 and run `stopEpoch` at APR 0 — meaning at minimum one full epoch of frozen funds and forced APR-0 yield loss for all LPs, quantified as `unscaledApr * TVL * epochDuration / YEAR`. If the pool was meant to close at a non-zero APR, the freeze is effectively permanent for that configuration.

### Likelihood Explanation
Attacker cost is a dust deposit plus one `requestWithdraw` while APR is 0 — APR0 epochs are an explicitly supported configuration (`_requestWithdrawApr0`, `apr0RateByEpoch`). The triggering condition (manager changes APR while a withdraw is pending) is routine, not adversarial coordination: managers set APR each epoch via `setAprsWithBuffer`. Likelihood is moderate-to-high whenever APR0 mode is used; the attacker can also keep a standing dust request to catch any future APR transition.

### Recommendation
Settle or migrate pending APR0 principal instead of reverting in `prepareStopEpochWithApr0`: when `unscaledApr != 0`, move each outstanding APR0 principal into the normal `withdrawsRequests`/`withdrawsRequestsByEpoch` path (it already gets no interest anyway) and set `apr0TotalPrincipal = 0`. Alternatively, reject `setApr`/`setAprs` to a non-zero value while `apr0TotalPrincipal != 0`, or sweep `apr0TotalPrincipal` into `pendingWithdraws` at `startEpoch` before the APR change takes effect.
