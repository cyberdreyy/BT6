### Title
Job-controlled cache key suffix `-protected` forces `ManagerConfig.Protected=true` regardless of branch protection - ([File: executors/docker/volume.go])

### Summary
`createVolumesManager` in `executors/docker/volume.go` sets `config.Protected` to `true` if *either* the ref is protected *or* any job-supplied `cache.key` ends in `-protected` (and not `-non_protected`). Because `e.Build.Cache[].Key` is populated from the `.gitlab-ci.yml`/pipeline `cache:key` field, which is fully controlled by the pipeline/job author, an unprivileged author on an unprotected branch can set `protectedKeyIdx >= 0` and force `Protected=true` purely from job-supplied string content.

### Finding Description
`createVolumesManager` computes:
```go
protectedKeyIdx := slices.IndexFunc(e.Build.Cache, func(c spec.Cache) bool {
    return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
})
config := volumes.ManagerConfig{
    ...
    Protected: e.Build.IsProtected() || protectedKeyIdx >= 0,
}
``` [1](#0-0) 

`config.Protected` is then used by `(*manager).withProtected` to append the `-protected` suffix to cache volume names/host-cache directory names, and is stored as the `protected` label on the created Docker volume via `createCacheVolume`: [2](#0-1) [3](#0-2) 

The volume/directory name for reusable cache volumes is derived purely from `UniqueName` (project-level, `ProjectRealUniqueName()`) and the hashed destination path — it does not incorporate the specific cache key that triggered protection, or job/pipeline identity: [4](#0-3) 

So: any unprotected-branch job can add an (unused) `cache:` entry with `key: "foo-protected"`. This flips `Protected=true` for that job's *entire* volume manager, causing every reusable cache volume/host-cache dir created by that job (for cache paths that are unrelated to the crafted key) to be created/reused under the same `-protected`-suffixed name that a genuinely protected-branch job for the same project/path would use. This is confirmed by the existing test comment referencing the deliberate design (`https://gitlab.com/gitlab-org/gitlab/-/work_items/494478`), but the OR-based control flow relies entirely on a string suffix supplied in job configuration, with no server-side/GitLab-verified attestation visible in this code path that the suffix genuinely reflects protected-branch status.

Existing checks reviewed:
- There is no validation in `executors/docker/volume.go` or `executors/docker/internal/volumes/manager.go` that cache keys ending in `-protected` are only accepted when `e.Build.IsProtected()` is true — the OR logic explicitly allows either condition alone to set `Protected=true`.
- No check ties the specific triggering cache key to the specific cache path/volume being created; `protectedKeyIdx` gates the manager-wide `Protected` flag, not a per-volume decision.

### Impact Explanation
An unprivileged author on an unprotected branch can create or overwrite the `-protected`-suffixed project cache volume/host directory that is later reused (Docker volume reuse by name, or host-directory reuse by path) by a genuinely protected-branch job for the same project and cache path. This breaks the protected-branch cache isolation invariant this code was explicitly built to enforce (isolating protected cache storage so untrusted branches cannot write into it), enabling cache-content injection into storage that protected pipelines will subsequently mount and trust, or denial of legitimate protected-cache creation (name/path collision).

### Likelihood Explanation
Fully feasible and repeatable by any pipeline author who can edit `.gitlab-ci.yml` cache configuration on an unprotected branch/MR — no special runner or GitLab privileges are required, and the affected code path (`createVolumesManager` → `NewManager` → `Create`/`addCacheVolume`) executes on every Docker-executor job that defines a cache with a matching key suffix.

### Recommendation
Do not derive `config.Protected` from job-supplied cache key content at all. If GitLab intends to signal per-cache-entry protection state, that signal must be authenticated/derived by GitLab server-side from actual branch protection (e.g., a separate build-payload field verified against `e.Build.IsProtected()`), not from a free-form string suffix an author can put directly into `cache.key`. At minimum, require `e.Build.IsProtected()` to be true before honoring any `-protected` suffix (i.e., `Protected: e.Build.IsProtected() && (trustedProtectedFlag || protectedKeyIdx >= 0)`), or drop the `protectedKeyIdx` OR-condition entirely.

### Proof of Concept
Go unit test in `executors/docker/volume_test.go` (or extend existing test near `createVolumesManager`):
```go
func TestCreateVolumesManager_UserControlledCacheKeyCannotForceProtected(t *testing.T) {
    e := &executor{}
    e.Build = &common.Build{
        JobResponse: common.JobResponse{
            GitInfo: common.GitInfo{Ref: "feature/unprotected-branch"}, // unprotected
        },
        Cache: []spec.Cache{{Key: "attacker-controlled-protected"}}, // crafted suffix
    }
    // e.Build.IsProtected() == false in this scenario

    vm, err := createVolumesManager(e)
    require.NoError(t, err)

    mgr, ok := vm.(*volumes.manager) // or expose config via test hook
    require.True(t, ok)
    assert.False(t, mgr.config.Protected,
        "an unprotected-branch job must not be able to force Protected=true via cache key suffix alone")
}
```
Expected (current) result: the assertion **fails** — `config.Protected` is `true` even though `IsProtected()` is `false`, confirming the bug. A complementary integration-style test can additionally assert that `withProtected(...)` produces the same volume name as a genuinely protected build for the identical cache destination, demonstrating the collision/reuse path.

func (m *manager) createHostBasedCacheVolume(destination string) error {
	destination, err := m.absolutePath(destination)
	if err != nil {
		return fmt.Errorf("defining absolute path: %w", err)
	}

	err = m.managedVolumes.Add(destination)
	if err != nil {
		return fmt.Errorf("updating managed volumes list: %w", err)
	}

	// The leaf directory dir has a name with a length of:
	//	- 42 chars when protected
	//	- 32 chars when not protected (the length of the md5sum only)
	dir := m.withProtected(hashPath(destination))
	hostPath := m.parser.Path().Join(m.config.CacheDir, m.config.UniqueName, dir)

	m.appendVolumeBind(&parser.Volume{
		Source:      hostPath,
		Destination: destination,
	})

	return nil
}

// withProtected returns a string with a specific suffix when the config states, we are running against a protected
// ref, or when any of the cache keys includes the `-protected` suffix.
// See https://gitlab.com/gitlab-org/gitlab/-/work_items/494478.
func (m *manager) withProtected(s string) string {
	if !m.config.Protected {
		return s
	}
	return s + protectedSuffix
}
