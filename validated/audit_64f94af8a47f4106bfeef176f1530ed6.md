### Title
Same-epoch instant-withdraw claims consume funds reserved for earlier receipts — ordering/initialization bypass in `claimInstantWithdrawRequest` — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Zephyr bug is a state-ordering violation: the I2C target handler writes a data byte through a buffer that was only allocated when the length register was written first, so an unauthenticated master skips the "allocate" step and writes through an uninitialized pointer. The credit-vault analog lives in `IdleCreditVault.claimInstantWithdrawRequest` (lines 380–393): a receipt created by `requestInstantWithdraw` (lines 356–375) can be claimed in the *same running epoch*, paying out of the strategy's aggregate underlying balance — the pool that `collectInstantWithdrawFunds` pulled from the borrower at epoch start to cover *previous* epochs' receipts. The claim path never checks that the caller's receipt belongs to an already-funded epoch; it burns whatever `instantWithdrawsRequests[_user]` holds and transfers `_amount`, exactly like writing data bytes before the length register allocated the buffer.

### Finding Description
Relevant code, `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestInstantWithdraw` (lines 356–375) burns the user's strategy tokens via the CDO, mints a 1:1 receipt, and bumps `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`. It records `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` but sets no per-epoch funded/mature marker.
- `claimInstantWithdrawRequest` (lines 380–393) unconditionally does `_burn(_user, amount); instantWithdrawsRequests[_user] = 0; _transferFundedClaim(_user, amount)`. Unlike `_claimFundedWithdrawRequest` (line 326), which reverts unless `epochNumber > lastWithdrawRequest[_user]`, there is **no epoch-maturity check** — no comparison between `instantWithdrawsRequestsByEpoch` and the funded epoch.
- Funding only happens in `collectInstantWithdrawFunds` (lines 398–403), called by the CDO at `startEpoch` to pull borrower cash for the *pending* instant queue built during the prior epoch. The strategy balance during a running epoch is therefore earmarked for receipts requested in earlier epochs.
- `IdleCDOEpochVariant.claimInstantWithdrawRequest` (`IdleCDOEpochVariant.sol:975-979`) only gates on `allowInstantWithdraw`, which is true while the epoch is running — the same window in which new instant requests are accepted (subject to `instantWithdrawDelay`). Nothing prevents a request and a claim in the same epoch.

Broken invariant: "one receipt, one (correctly sourced) payout" — the payout is sourced from funds allocated to a different epoch's receipts, and the attacker's receipt *additionally* remains inside `pendingInstantWithdraws`, so the borrower is charged for it again at the next `startEpoch`.

### Impact Explanation
An unprivileged tranche-token holder (any KYC-passing lender allowed to request instant withdrawals) can:

1. Drain the funded instant-withdraw pool immediately, skipping the intended one-epoch wait and the `instantWithdrawDeadline` repayment window.
2. Cause **temporary freezing** of every honest instant claimant: their `claimInstantWithdrawRequest` reverts on insufficient strategy balance until the next `startEpoch` refills the pool (which happens only because the attacker's already-paid receipt is still counted in `pendingInstantWithdraws`).
3. If the pool is closed (`stopEpoch` with `_interest == 1` sentinel / `epochEndDate = 0`) or a default intervenes before refilling, the freeze becomes effectively permanent for the last claimants; `pendingInstantWithdraws != 0` also blocks `_ensureDefaultRecoveryInitialized` (line 926) and forces `defaultPendingClaimBasis` (lines 644–649) to include unfunded instant basis, distorting `defaultRecoveryPrice` for all recovery claimants.

Loss quantification: up to the entire `pendingInstantWithdraws` collected at epoch start can be paid to receipt holders whose requests have not yet been funded, freezing an equal amount of legitimate claims for at least one full epoch (or permanently on close/default).

### Likelihood Explanation
- Attacker requirements: hold tranche tokens, pass `isWalletAllowed` (KYC), and call `cdoEpoch.requestInstantWithdraw` then `cdoEpoch.claimInstantWithdrawRequest` in one transaction during a running epoch while `allowInstantWithdraw` is true and the strategy holds collected instant funds. No privileged role, no borrower cooperation.
- The window exists whenever instant withdrawals are enabled and earlier receipts are unclaimed — a routine state.
- The one-byte-overflow analog (write-then-check) also appears in spirit: the claim writes (`_burn`, balance transfer) are performed before any check that funding exists; the only backstop is the ERC20 transfer reverting on insufficient balance, which protects nothing when the pool holds other epochs' money.

### Recommendation
- Track a funded marker per instant receipt, e.g., only allow claims for `instantWithdrawsRequestsByEpoch[_user][e]` where `e < epochNumber` (mirroring the `epochNumber <= lastWithdrawRequest` gate used for normal withdrawals), or decrement a funded-vs-unfunded counter in `collectInstantWithdrawFunds` and cap claimable amounts to it.
- Alternatively, disallow new `requestInstantWithdraw` while unfunded claims from the current collection are still outstanding, or net the claim against `pendingInstantWithdraws` so a paid receipt is no longer re-funded at the next epoch start.

### Proof of Concept
Foundry fork test sketch (deploy `IdleCDOEpochVariant` + `IdleCreditVault` per `test/foundry/IdleCreditVault.t.sol` setup, instant withdrawals enabled via `setInstantWithdrawParams(delay, aprDiff, true)`):

```solidity
// --- epoch N: honest user requests instant withdraw ---
uint256 honAmt = 100_000e6;
uint256 honTranches = _depositWithUser(honest, honAmt); // buffer deposit
// epoch running N:
_requestInstantWithdrawWithUser(honest, honTranches);

// stopEpoch N, startEpoch N+1 -> borrower funds pendingInstantWithdraws,
// collectInstantWithdrawFunds pulls honAmt underlying into the strategy.
_stopCurrentEpoch();
deal(underlying, borrower, needed);
vm.prank(borrower); underlying.approve(cdo, needed);
vm.prank(manager); cdoEpoch.startEpoch(); // isEpochRunning, allowInstantWithdraw == true

// --- attacker, same epoch N+1 ---
uint256 atkTranches = _depositAttackerBeforeEpoch(); // attacker holds tranches
vm.startPrank(attacker);
cdoEpoch.requestInstantWithdraw(atkTranches, AAtranche);   // receipt created, pendingInstantWithdraws += amt
// BUG: no funded-epoch check -> claim succeeds immediately, paid from honest user's pool
cdoEpoch.claimInstantWithdrawRequest();
vm.stopPrank();

assertGt(underlying.balanceOf(attacker), 0);               // attacker paid with zero wait
vm.prank(honest);
vm.expectRevert();                                          // ERC20: transfer amount exceeds balance
cdoEpoch.claimInstantWithdrawRequest();                     // honest claim frozen until next funding
assertGt(strategy.pendingInstantWithdraws(), 0);            // attacker's receipt still queued -> funded AGAIN at epoch N+2
```

Note: I verified the missing maturity check by reading `requestInstantWithdraw`, `claimInstantWithdrawRequest`, `collectInstantWithdrawFunds`, `_transferFundedClaim`, and the `allowInstantWithdraw` gate; the exact flag timing of `disableInstantWithdraw`/`allowInstantWithdraw` around `startEpoch` (IdleCDOEpochVariant.sol lines ~211–270) should be confirmed when writing the PoC, but the claim path itself performs no funding-order validation regardless of flag state.
