### Title
Unbounded per-sender cache-slot consumption causes global request-cache exhaustion / DoS - ([File: core/services/gateway/handlers/common/requestcache.go])

### Finding Description
`requestCache.NewRequest` stores every pending request in a single shared map `cache map[globalId]*pendingRequest[T]` guarded only by a global `maxCacheSize` counter [1](#0-0) . The only checks performed are (1) duplicate `(sender, messageId)` rejection and (2) `len(c.cache) >= int(c.maxCacheSize)` returning `"request cache is full"` [2](#0-1) . There is no per-sender quota, allow-list weighting, or fairness mechanism — any signer able to produce distinct `MessageId` values (which is entirely attacker-controlled, since the key is `globalId{sender, messageId}`) can insert entries until `maxCacheSize` is reached. Entries are only removed on `ProcessResponse` aggregation or after `c.timeout` fires via `time.AfterFunc` [3](#0-2) , so a signer can hold slots for up to the full configured timeout simply by never triggering an aggregated response (e.g., letting nodes never answer, or the attacker's own workflow never resolving). Once the map is full, every other sender's `NewRequest` call — including legitimate run/edit-role users' pipeline-triggering requests routed through the same cache instance (e.g. the HTTP/webAPI trigger handler in `core/services/gateway/handlers/capabilities/v2/http_handler.go`) — receives `"request cache is full"` and is rejected, blocking their job runs.

The higher-level per-sender/global rate limiters (`PerSenderRPS`/`PerSenderBurst`, `GlobalRPS`/`GlobalBurst`) described in `core/services/gateway/handlers/capabilities/v2/README.md` throttle the *rate* of accepted messages but do not cap the *number of concurrently outstanding cache entries* per sender [4](#0-3) . A signer within its allowed RPS/burst can still steadily accumulate unique-`MessageId` requests over time (up to the cache timeout window) until the shared cache reaches `maxCacheSize`, since nothing evicts or limits a single sender's share of the map.

### Impact Explanation
This is a denial-of-service against other users sharing the same gateway/DON request cache: once the cache is saturated by one signer, all subsequent legitimate `NewRequest` calls from any other sender fail with `"request cache is full"`, blocking their pipeline/job-triggering requests until the attacker's entries time out or are processed. This matches the "Denial of Service" bounty impact class — it does not compromise keys/funds directly but denies service availability to legitimate users' on-chain-triggering workflows.

### Likelihood Explanation
Preconditions are minimal: any entity capable of sending validly-signed gateway messages (no elevated role or admin access required) can supply unique `MessageId` values and call the endpoint repeatedly, respecting existing per-sender rate limits, until it accumulates `maxCacheSize` outstanding entries. This is fully reproducible and requires no race condition or timing luck — it is a straightforward loop bounded only by `maxCacheSize` and the per-sender rate limit's time-to-fill.

### Recommendation
Add a per-sender quota (e.g., a configurable `maxPerSenderCacheSize` or a reserved-slot allocation) enforced inside `requestCache.NewRequest` alongside the existing `maxCacheSize` check, so a single sender cannot occupy an unbounded share of the shared cache. Alternatively, track per-sender counts in the `requestCache` struct and reject/evict oldest-first when a sender exceeds its fair share, independent of global rate limiting on request ingress rate.

### Proof of Concept
Table-driven Go unit test in `core/services/gateway/handlers/common/requestcache_test.go`:
1. Construct `NewRequestCache[T](timeout, maxCacheSize)` with a small `maxCacheSize` (e.g., 3).
2. Loop `maxCacheSize` times calling `NewRequest` with the *same* attacker `sender` and a freshly generated unique `MessageId` each iteration, a no-op callback, and non-nil `responseData`; assert each call returns `nil` error.
3. Call `NewRequest` once more with a distinct legitimate `sender`/`id` pair; assert the returned error is `"request cache is full"`.
4. This demonstrates that a single sender fully consumes global cache capacity and blocks a different, legitimate sender's request from being admitted.
