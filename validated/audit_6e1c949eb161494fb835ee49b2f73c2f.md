### Title
Division-before-multiplication in Jovian DA-footprint gas estimation causes systematic under-metering of L1 data-availability gas - (File: crates/common/l1-fees/src/params.rs)

### Summary
`L1FeeParams::jovian_da_footprint` computes the Jovian DA-footprint gas by dividing the FastLZ-scaled estimated size by `1e6` *before* multiplying by the DA-footprint gas scalar, instead of multiplying first and dividing last. This is the same bug class as the referenced external report (`AaveLeverageStrategyExtension._calculateMinRepayUnits`): performing division ahead of multiplication truncates the intermediate fractional result, permanently losing precision that the final multiplication can no longer recover.

### Finding Description
`jovian_da_footprint` is documented and implemented as "divide then multiply": [1](#0-0) 

Compare this to the correct multiply-then-divide order used everywhere else in this same file for structurally identical formulas, e.g. `calculate_tx_l1_cost_fjord` and `calculate_tx_l1_cost_ecotone`: [2](#0-1) [3](#0-2) 

`tx_estimated_size_fjord` returns `max(MIN_TX_SIZE_SCALED, intercept + fastlzCoef*fastlzSize)`, a value scaled by `1e6` that is generally *not* an exact multiple of `1e6`: [4](#0-3) 

Because `jovian_da_footprint` computes `(size / 1e6) * scalar` instead of `(size * scalar) / 1e6`, any fractional remainder in `size / 1e6` (up to just under 1 unit) is discarded before the multiplication by `scalar`, whereas the mathematically correct order would retain that fraction through the multiplication and only round down once at the very end. This produces a result that is at least as small as, and in many cases strictly smaller than, the correct floor value — a systematic under-estimate of the DA footprint gas.

The same divide-then-multiply pattern is repeated at the two call sites that actually charge/report this gas:
- `crates/common/evm/src/executor/block_executor.rs::jovian_da_footprint_estimation` (`estimate_tx_compressed_size(...).saturating_div(1_000_000)` then `.saturating_mul(da_footprint_gas_scalar)`), used during block execution/building.
- `crates/execution/rpc/src/eth/receipt.rs` test/usage of the same `estimate_tx_compressed_size(...).saturating_div(1_000_000).saturating_mul(...)` sequence for populating `blob_gas_used` in receipts.

### Impact Explanation
The DA-footprint gas figure feeds directly into block gas/resource metering for L1 data-availability budgeting once the Jovian upgrade is active. Systematically under-counting this figure means:
- Transactions are charged less Jovian DA-footprint gas than the correct formula would produce, so the chain's accounting of L1 data-posting resource consumption is consistently biased low.
- Because a single-byte scaled quantum error is baked in on every transaction (bounded by `scalar - 1` per tx, since `scalar` here is a small configured constant such as `100` in the test fixtures), the aggregate under-metering grows with transaction volume across a block and across the chain's lifetime, permanently skewing the resource-metering ledger relative to the reference algorithm it is meant to faithfully port (per the code's own doc comment referencing `jovian_da_footprint_estimation`).

Unlike the original Solidity report (which could truncate to exactly zero and lose 100% of a computed amount when `borrowPrice < 1`), here the minimum estimated size is floored at `100 * 1e6`, so the division does not collapse to zero. The magnitude of the discrepancy per transaction is small and bounded, and it does not by itself cause direct token theft, double-spend, consensus divergence, or freezing of funds — it does not meet the "concrete unauthorized operation, theft, or permanent freezing of funds" bar required here. I could not confirm within the available exploration that this feeds into any consensus-critical divergence (e.g., between nodes disagreeing on this value) versus being a deterministic, reproducible (if slightly incorrect) computation applied uniformly by all nodes; if it is applied identically everywhere, there is no chain-split risk, just an intentional-looking (but arithmetically suboptimal) resource-accounting bias.

### Likelihood Explanation
This code executes on every transaction once Jovian is active and a `da_footprint_gas_scalar` is configured, making the incorrect order of operations always reachable by any transaction sender — no special privileges required. However, the resulting deviation from the "true" formula is bounded and small per transaction, and the same divide-then-multiply computation is applied deterministically by every node from the same input parameters, so it does not diverge between honest nodes.

### Recommendation
Reorder the arithmetic in `jovian_da_footprint` (and its duplicated forms in `block_executor.rs::jovian_da_footprint_estimation` and the RPC receipt code) to multiply before dividing, matching the pattern already used correctly elsewhere in this file:
```rust
U256::from(tx_estimated_size_fjord(input))
    .saturating_mul(scalar)
    .wrapping_div(U256::from(1_000_000u64))
    .saturating_to::<u64>()
```
This should be reflected consistently across all three call sites so the metered DA footprint gas matches the mathematically correct formula bit-for-bit.

### Proof of Concept
Given `tx_estimated_size_fjord(input) = 100_500_000` (not an exact multiple of `1e6`) and `da_footprint_gas_scalar = 3`:
- Correct (multiply-then-divide): `(100_500_000 * 3) / 1_000_000 = 301_500_000 / 1_000_000 = 301`
- Actual (current divide-then-multiply): `(100_500_000 / 1_000_000) * 3 = 100 * 3 = 300`

The existing unit test only exercises the exact-multiple-of-`1e6` boundary case (`100 * 1_000_000`), which is why the discrepancy is not currently caught: [5](#0-4) 

**Note on severity:** Given the bounded, per-transaction, deterministic nature of this precision loss (no truncation-to-zero scenario, no divergence between nodes observed in the code I could inspect), I assess this analog as a legitimate instance of the reported bug class but of **low/informational** real-world impact rather than a Medium/High/Critical finding with concrete fund theft, freezing, or consensus-divergence impact. I flag it here for completeness since it is the closest structural match to the reported bug class, but per the stated validation bar it likely does not qualify as a valid Medium/High/Critical analog on its own.

```rust
    /// Calculates the Jovian DA-footprint gas for posting the enveloped transaction bytes `input`.
    ///
    /// The footprint is the FastLZ-estimated compressed size (scaled by `1e6`, as
    /// [`tx_estimated_size_fjord`] returns) divided back down by `1e6` and multiplied by the
    /// DA-footprint gas scalar. Returns zero when no scalar is set (pre-Jovian or unconfigured).
    /// Mirrors the reference `jovian_da_footprint_estimation`.
    pub fn jovian_da_footprint(&self, input: &[u8]) -> u64 {
        let Some(scalar) = self.da_footprint_gas_scalar else {
            return 0;
        };
        U256::from(tx_estimated_size_fjord(input))
            .wrapping_div(U256::from(1_000_000u64))
            .saturating_mul(scalar)
            .saturating_to::<u64>()
    }
```

```rust
/// Calculate the estimated compressed transaction size in bytes, scaled by 1e6.
/// This value is computed based on the following formula:
/// max(minTransactionSize, intercept + fastlzCoef*fastlzSize)
pub fn tx_estimated_size_fjord(input: &[u8]) -> u64 {
    let fastlz_size = flz_compress_len(input) as u64;

    fastlz_size
        .saturating_mul(L1_COST_FASTLZ_COEF)
        .saturating_sub(L1_COST_INTERCEPT)
        .max(MIN_TX_SIZE_SCALED)
}
```
