### Title
Keyring wallet lock (`isWalletAllowed`) enforced on deposit/request paths but bypassed on claim paths and via transferable strategy-token receipts - (contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` gates entry points with the Keyring credential check `isWalletAllowed` (lines 645, 668, 743), but the two exit paths — `claimWithdrawRequest()` (line 967) and `claimInstantWithdrawRequest()` (line 975) — perform no wallet check, and the strategy-token receipt minted to users by `IdleCreditVault.requestWithdraw`/`requestInstantWithdraw` (line 275) is a plain ERC20. Likewise `IdleCDOTranche` is an unrestricted ERC20. A user whose credential is revoked, or any non-KYC address that receives receipt tokens, can still withdraw underlying directly — the same "lock covers entry but is bypassed via direct access / child resources" pattern as GHSA-h5v5-8746-g7mm.

### Finding Description
`requestWithdraw` burns the caller's tranche tokens and mints an equal amount of `IdleCreditVault` strategy tokens to `msg.sender` as a claim receipt. `claimWithdrawRequest()` forwards `msg.sender` to `IdleCreditVault.claimWithdrawRequest(_user)`, which burns the caller's strategy-token balance and transfers underlying (`_transferFundedClaim`) without re-checking credentials. `claimInstantWithdrawRequest()` only checks `allowInstantWithdraw`. Neither function calls `isWalletAllowed`, and neither the tranche token nor the strategy-token receipt applies a transfer-time Keyring check.

Consequences:

1. **Revocation bypass ("lock all" gap).** When the admin relies on Keyring revocation to stop a wallet from interacting with the vault, a revoked wallet that already holds withdraw receipts can still call `claimWithdrawRequest()` / `claimInstantWithdrawRequest()` and pull underlying out. The lock only covers new deposits and new requests, not settlement of existing claims.
2. **Secondary-transfer bypass (child-resource gap).** Strategy-token receipts are transferable. A KYC'd lender can request a withdrawal and transfer the receipt tokens to a non-credentialed address, which then claims the underlying directly through `claimWithdrawRequest()` with no `isWalletAllowed` check anywhere in the path (`IdleCDOEpochVariant.claimWithdrawRequest` → `IdleCreditVault.claimWithdrawRequest` → `_claimFundedWithdrawRequest` → `_transferFundedClaim`).

### Impact Explanation
The vault's credential enforcement is intended to restrict which wallets may move value in and out of the credit pool. Because claims and receipt-token transfers are outside the lock, a non-credentialed address can be the ultimate recipient of underlying tokens equal to the receipt face value (principal + accrued interest for normal requests; request-time value for instant requests). In a Keyring-gated deployment, revocation of a lender mid-flight does not prevent them from completing withdrawal of e.g. their full receipt balance, and receipts can be laundered to arbitrary non-KYC wallets, defeating the compliance restriction on fund outflows. Loss to the pool equals the claimed underlying; the broken invariant is the access/lock invariant on fund exits.

### Likelihood Explanation
Requires only: (a) a KYC'd lender makes a withdraw request (normal or instant), then (b) has credentials revoked or transfers the receipt tokens to any address. Claims mature after one epoch (`_claimFundedWithdrawRequest` only requires `epochNumber > lastWithdrawRequest[_user]`), and instant claims require `allowInstantWithdraw` after `getInstantWithdrawFunds`. No privileged cooperation is needed; the bypass is a deterministic function of missing checks, not a race.

### Recommendation
- Add `isWalletAllowed(msg.sender)` checks to `claimWithdrawRequest()` and `claimInstantWithdrawRequest()` in `IdleCDOEpochVariant`.
- Consider gating strategy-token receipt transfers (or re-checking credentials at claim time via the token's `_beforeTokenTransfer`) so that receiving a receipt does not confer an unmediated right to pull underlying.
- Mirror the same checks in `DefaultDistributor.claim`/`_transferDefaultRecovery` paths if those are reachable by non-credentialed holders of defaulted receipts.

### Proof of Concept
Foundry sketch (extend the harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testClaimBypassesKeyringLock() external {
    // keyring configured; user is credentialed
    uint256 mintedAA = idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    uint256 requested = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));

    // admin "locks" the wallet: Keyring credential revoked
    keyringMock.setCredential(keyringPolicyId, address(this), false);
    assertFalse(cdoEpoch.isWalletAllowed(address(this)));

    // new request is correctly blocked
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.requestWithdraw(1, address(AAtranche));

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // bypass: claim still succeeds despite revoked credential
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(address(this)) - balPre, requested);
}

function testClaimByNonKycRecipientOfReceipt() external {
    uint256 mintedAA = idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    uint256 requested = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));

    // transfer claim receipt (strategy tokens) to a non-KYC attacker
    address attacker = makeAddr("nonKyc");
    IERC20Detailed(strategyToken).transfer(attacker, requested);

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest(); // succeeds with no isWalletAllowed check
    assertEq(underlying.balanceOf(attacker), requested);
}
```

**Uncertainty note:** I could not fully verify that `IdleCreditVault` strategy tokens are unrestricted ERC20 transfers (grep returned matches but I could not read the transfer/override section), and I could not confirm whether `DefaultDistributor.claim` or the post-default claim paths perform their own credential checks. If `IdleCreditVault` overrides `_beforeTokenTransfer` to enforce Keyring, the secondary-transfer leg is weaker, but the revocation-bypass leg on `claimWithdrawRequest`/`claimInstantWithdrawRequest` stands on the code shown.
