### Title
Session lifetime bounded only by idle timeout, not absolute age, allowing indefinite session extension - (File: core/sessions/localauth/orm.go)

### Summary
`AuthorizedUserWithSession`/`findValidSession`/`updateSessionLastUsed` in `orm.go` validate and renew a session purely based on `last_used + SessionTimeout >= now()`, with no check on `created_at`. Any holder of a session cookie or replayed session ID can keep the session alive forever by issuing one request per idle window (default 15 minutes), regardless of the 240h `SessionReaperExpiration`, because that reaper only deletes sessions that have gone idle past `SessionTimeout + SessionReaperExpiration`, not sessions that are simply old.

### Finding Description
`findValidSession` in [1](#0-0)  validates a session solely via `last_used + $sessionDuration >= now()` where `sessionDuration` is `WebServer.SessionTimeout` (default 15m, see [2](#0-1) ). On every authenticated request through `AuthorizedUserWithSession`, `updateSessionLastUsed` unconditionally sets `last_used = now()` [3](#0-2) , with no comparison against `created_at`.

The only other cleanup mechanism is the background `sessionReaper`, which computes a single idle-based threshold — `now - SessionTimeout - SessionReaperExpiration` — and deletes rows where `last_used < threshold` [4](#0-3) . It never looks at `created_at`, so a session that is used at least once every `SessionTimeout` interval (15 minutes by default) will never be reaped and never be rejected by `findValidSession`, no matter how old it is.

This is reachable from any request that carries the `clsession` cookie through `AuthenticateBySession`, which reads `SessionIDKey` from the cookie and calls `AuthorizedUserWithSession` [5](#0-4) . There is no admin/role check involved here — it's the base authentication step used by every protected route.

### Impact Explanation
If a session cookie is ever exfiltrated (XSS, log leakage, shared browser/proxy, network capture on a misconfigured deployment, etc.), the holder can keep it valid forever simply by polling any authenticated endpoint faster than every `SessionTimeout` interval (default 15 minutes), which is trivial to automate. This defeats the operator's expectation that `SessionReaperExpiration` (240h) bounds session lifetime, and undermines credential-rotation/forced-logout assumptions, since there is no absolute cap tied to `created_at`. Combined with a leaked admin session cookie, this gives durable admin access — key export, unauthorized transaction submission, node takeover — matching the "Critical - node takeover" impact class from the question, contingent on some other means of obtaining a valid session ID/cookie.

### Likelihood Explanation
Exploiting this requires the attacker to already possess a valid session ID/cookie for some user (this ORM function itself doesn't leak or forge sessions — the "attacker controls password bytes" framing in the question assumes normal authentication, not an unauthenticated bypass). Given a valid cookie, sustaining it forever is trivial: an automated script issuing one GET request per `SessionTimeout` interval is enough, and it's fully repeatable/deterministic. The interesting risk is that operators/incident responders relying on `SessionReaperExpiration` as an absolute session TTL will be wrong — an actively-replayed stolen session is not bounded by it.

### Recommendation
Enforce an absolute session lifetime independent of activity: track `created_at` and reject/require re-authentication once `now() - created_at > MaxAbsoluteSessionLifetime`, in addition to the existing idle-based check in `findValidSession`. Apply the same cap in the reaper's deletion query (`created_at < threshold OR last_used < idle_threshold`) rather than idle time alone.

### Proof of Concept
Go test plan for `core/sessions/localauth/orm_test.go`:
1. Insert a session row directly with `created_at = now() - (SessionReaperExpiration + 1h)` but `last_used = now()` (simulating continuous polling).
2. Call `orm.AuthorizedUserWithSession(ctx, sessionID)` — expect it to currently succeed and refresh `last_used` again (demonstrating the bug).
3. Add/assert a new absolute-lifetime check: after the fix, the same call should return `sessions.ErrUserSessionExpired` because `created_at` exceeds the configured maximum absolute lifetime, even though `last_used` is fresh.
4. Table-test across: idle-expired-but-young, active-but-old (should fail post-fix), and active-and-young (should pass) to confirm the invariant "bounded by absolute age, not only idle time."

func (o *orm) AuthorizedUserWithSession(ctx context.Context, sessionID string) (user sessions.User, err error) {
	if len(sessionID) == 0 {
		return sessions.User{}, sessions.ErrEmptySessionID
	}

	email, err := o.findValidSession(ctx, sessionID)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	user, err = o.findUser(ctx, email)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	if err := o.updateSessionLastUsed(ctx, sessionID); err != nil {
		return sessions.User{}, err
	}

	return user, nil
}
