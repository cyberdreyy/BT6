### Title
Stale confirmations from deleted multisig members count toward execution threshold, allowing requests to execute below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
Both `multisig` and `multisig2` clean up outstanding *requests originally created by* a deleted key/member, but neither cleans up *confirmations cast on other pending requests* by that key/member before it was removed. `confirm()` only compares the confirmation-set size to `num_confirmations`; it never re-validates that every recorded confirmer is still a current member. This breaks the intended custody binding: `confirmations counted == confirmations from currently authorized members`.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member` only purges requests whose *creator* (`r.member`) equals the member being removed: [1](#0-0) 

It does not scan `self.confirmations` (a separate map keyed by `request_id`, holding the set of confirmers) to strip out the departing member's confirmation from requests created by *other* members. `confirm()` then blindly trusts the size of that stale set: [2](#0-1) 

The equivalent v1 contract has the identical gap: `DeleteKey` only removes requests keyed by `r.signer_pk == pk`, not confirmations left by that key on other pending requests: [3](#0-2) [4](#0-3) 

Binding that should hold: `confirmations.get(request_id).len() == |{live members who confirmed request_id}|`. After a member is removed, this becomes `confirmations.get(request_id).len() > |{live members who confirmed request_id}|`, because the removed member's stale confirmation is never purged from requests it didn't create.

### Impact Explanation
This lets a request execute (e.g. a `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` action) with fewer *live* confirmations than `num_confirmations` mandates, because a confirmation from an already-removed member is silently counted. This is a direct violation of the "multisig request executed below threshold" impact class — a K-of-N authorization guarantee is broken, permitting funds to move or contract upgrades to occur with less than K currently-authorized approvals. This is Critical per the stated impact taxonomy (multisig request executed below threshold).

### Likelihood Explanation
No attacker privilege beyond normal, expected multisig usage is required: any account holding legitimate confirming rights combined with normal governance churn (removing a member/key while a request is still pending) reproduces this. It does not require redeploying the contract, foundation intervention, or a compromised key — only ordinary sequencing of `add_request`/`confirm`/`DeleteMember`(or `DeleteKey`) actions, all reachable by unprivileged (but legitimate) multisig members. Because membership changes are a normal operational event and pending requests can persist (bounded only by `active_requests_limit`/no expiry check besides `REQUEST_COOLDOWN` for deletion), this is a realistically reachable state, not a contrived one.

### Recommendation
When removing a member/key (`delete_member` in `multisig2`, `DeleteKey` in `multisig`), iterate over all pending requests' confirmation sets and strip out the removed member's entry (not just requests it created), or alternatively re-validate at `confirm()`/execution time that every entry in the confirmation set still belongs to `self.members` (or corresponds to a still-valid access key) before counting it toward `num_confirmations`.

### Proof of Concept
Using `multisig2` semantics (members = {A, B, C, D}, `num_confirmations = 3`):
1. A calls `add_request_and_confirm(request X)` → `confirmations[X] = {A}`.
2. B calls `confirm(X)` → `confirmations[X] = {A, B}` (2 < 3, not yet executed).
3. Separately, A, C, D confirm a `DeleteMember{B}` request (3 confirmations, legitimately meets threshold) → B is removed from `self.members`; `delete_member` only clears requests where `r.member == B`, but request X was created by A, so `confirmations[X]` still contains `{A, B}`.
4. Members are now {A, C, D}; `assert(self.members.len() - 1 >= num_confirmations)` passed (4-1=3≥3) at removal time, so `num_confirmations` stays 3.
5. C calls `confirm(X)` → `confirmations[X].len() + 1 = 3 >= num_confirmations (3)` → request X executes, even though only 2 currently-live members (A and C) ever confirmed it; B's stale confirmation counted toward the threshold. [2](#0-1) [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
