### Title
Stale per-epoch instant-withdraw basis is never cleared on the funded claim path, enabling a double recovery payout after default - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug frees every `rwi` except the last successfully processed one — a success-path cleanup leak. The direct analog lives in `IdleCreditVault.claimInstantWithdrawRequest`: on the normal (funded) success path the function zeroes the aggregate receipt `instantWithdrawsRequests[_user]` and burns the receipt tokens, but never clears `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` nor decrements `instantWithdrawClaimsByEpoch[currentEpoch]` or `pendingInstantWithdraws`. Only the defaulted-epoch claim path (`_claimDefaultedInstantWithdrawRequest`) clears the per-epoch bucket — mirroring the leaked last `rwi`. If a default is finalized for that same epoch, the stale per-epoch basis is claimed a second time.

### Finding Description
`requestInstantWithdraw` records three ledgers: the aggregate `instantWithdrawsRequests[_user]`, the per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the epoch-global `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 366-374). On a successful funded claim, `claimInstantWithdrawRequest` only resets the aggregate (lines 387-392); the two per-epoch entries are left behind. Later, after `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, the same function first calls `_claimDefaultedInstantWithdrawRequest` (lines 382-385), which reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — still nonzero — subtracts it from the (already zeroed) aggregate, decrements `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch`, burns the user's receipt tokens, and pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from the recovery reserve (lines 842-855).

Attack sequence (unprivileged tranche holder):
1. During epoch N, deposit, request an instant withdraw, wait for borrower funding, claim. Aggregate receipt is cleared; `instantWithdrawsRequestsByEpoch[user][N]` remains.
2. Borrower defaults; owner/manager finalizes the default while `epochNumber` is still N, so `defaultRecoveryEpoch == N` (this alignment assumption could not be fully verified — the assignment site wasn't retrieved — but is the natural indexing used elsewhere in the file).
3. Attacker makes a new instant-withdraw request, receiving fresh receipt tokens, then calls `claimInstantWithdrawRequest`. The defaulted-epoch branch consumes the *stale* epoch-N basis: it burns the attacker's new receipt tokens and transfers `basis * defaultRecoveryPrice` of already-recovered funds a second time.
4. If instead the attacker holds no new receipt, `instantWithdrawsRequests[_user] -= claimBasis` underflows (or `_burn` reverts), permanently bricking `claimInstantWithdrawRequest` for that user — the same "leaked entry blocks later processing" shape as the kernel leak.

`instantWithdrawClaimsByEpoch[N]` is likewise inflated forever, corrupting any global accounting that trusts it.

### Impact Explanation
Double payment from the default-recovery reserve up to the size of the attacker's previously-claimed instant withdrawal, directly diluting other defaulted-epoch claimants' recovery (the reserve is a fixed pool distributed at `defaultRecoveryPrice`). Alternatively, permanent freezing of the victim user's instant-claim path via arithmetic underflow.

### Likelihood Explanation
Requires an instant withdraw claimed in the same epoch that is later finalized as the default epoch — a plausible sequence since defaults are discovered during or right after a running epoch in which instant withdrawals were being serviced. The attacker only needs ordinary user actions; the only privileged step is honest default finalization. Guard analysis: no guard clears the per-epoch entries on the funded path, and `requestWithdraw`'s post-default stale-receipt check (lines 249-251) is absent from `requestInstantWithdraw`, so nothing prevents re-entering with a fresh receipt.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers on the funded path, symmetric with `_claimDefaultedInstantWithdrawRequest`: find the epoch(s) contributing to `instantWithdrawsRequests[_user]` (e.g., track `lastInstantWithdrawRequest` epoch), zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` and `pendingInstantWithdraws` before burning. Alternatively, gate `_claimDefaultedInstantWithdrawRequest` to skip epochs whose aggregate receipt is already zero.

### Proof of Concept
Reproducible Foundry fork PoC sketch (modeled on `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleInstantEpochBasisDoublePays() external {
  // epoch N running
  _startEpochAndCheckPrices(0);
  uint256 amt = 100e6;
  _depositWithUser(attacker, amt, true);
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(amt, address(AAtranche)); // routed to instant path
  // borrower funds instant withdrawals
  _getInstantFunds();
  vm.prank(attacker);
  cdoEpoch.claimInstantWithdrawRequest();
  // aggregate cleared, per-epoch stale
  assertEq(strategy.instantWithdrawsRequests(attacker), 0);
  assertGt(strategy.instantWithdrawsRequestsByEpoch(attacker, strategy.epochNumber()), 0);
  // borrower defaults; finalize in same epoch number
  _finalizeDefault(); // sets defaultRecoveryEpoch == epochNumber
  // attacker re-requests to obtain fresh receipt tokens, then claims again
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(dust, address(AAtranche));
  uint256 balPre = underlying.balanceOf(attacker);
  vm.prank(attacker);
  cdoEpoch.claimInstantWithdrawRequest();
  // stale basis paid a second time at defaultRecoveryPrice
  assertGt(underlying.balanceOf(attacker) - balPre, dustExpected);
}
```

Expected result on current code: the second claim pays `staleBasis * defaultRecoveryPrice / RECOVERY_FULL` from the recovery reserve, or reverts on underflow if no fresh receipt exists — both confirming the missing cleanup.
