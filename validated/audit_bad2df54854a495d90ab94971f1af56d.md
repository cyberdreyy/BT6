### Title
Concrete step-runner path ignores shell executor's configured `User`, running job scripts as the runner process's own identity - ([File: executors/shell/steps.go])

### Summary
The shell executor's `User` setting (`s.Shell().User`, set in `executors/shell/shell.go` `Prepare`) is only consumed by `shells/bash.go`/`shells/powershell.go` `GetConfiguration`, which wraps the classic script command with `su <user> -c ...` for the `shell.Run`/`newCommander` path. The native-steps/concrete path (`executors/shell/steps.go` `Connect` → `steps/localserver.Start` → `functions/concrete/run/stages/step.go` `shell()` → `functions/concrete/run/env/env.go` `Env.Command`) never reads or applies `User` at all, so concrete-dispatched job scripts run under the runner process's ambient uid/gid regardless of the configured `User`.

### Finding Description
`executors/shell/steps.go`'s `stepRunnerServer.ensureStarted` starts `localserver.Start(localserver.Options{OperatorLogger: ...})` [1](#0-0) , and `localserver.serve` registers only the `"concrete"` builtin via `di.WithBuiltinFunc("concrete", concrete.New())`, with no user/identity option in `localserver.Options` [2](#0-1) [3](#0-2) . This server is created once per provider and shared across every build dispatched through the shell executor's `Connect` (`executors/shell/steps.go` lines 44-62), independent of any per-job `User`.

Meanwhile, `executors/shell/shell.go`'s `Prepare` sets `s.Shell().User = options.User` [4](#0-3) , but that field is only read by `shells/bash.go`'s `GetConfiguration`, which builds an `su <User> -c <cmdline>` wrapper consumed by `shell.Run`'s `newCommander` call [5](#0-4) [6](#0-5) . This is the *only* place `User` is honored.

When `FF_CONCRETE`/`UseConcrete` is on and the executor supports `steps.Connector`, `common/build.go`'s `executeScript` dispatches the whole job through `executeConcreteJob` → `executeStepStage(... connector, "concrete", ...)` instead of the classic `executeUserScripts`/`shell.Run` path [7](#0-6) . That path goes over gRPC to the shared `localserver`, into the `concrete` builtin (`functions/concrete/concrete.go`), which builds a `run.Runner` and calls `runner.Run(ctx)`, eventually reaching `functions/concrete/run/stages/step.go`'s `shell()` for each `Step.Script`. That function writes a script file and executes it via `e.Command(ctx, cmd, envVars, args...)` [8](#0-7) , and `Env.Command` in `functions/concrete/run/env/env.go` constructs the process purely with `gracefulexitcmd.New(ctx, e.GracefulExitDelay, name, args...)` plus `Dir`/`Env`/`Stdout`/`Stderr` — there is no `Credential`, `SysProcAttr`, or any uid/gid/user field set anywhere in `Env` or in the call chain [9](#0-8) . The `Env` struct itself (lines 29-69) has no `User` field to carry such a setting even if one were threaded through.

Thus a job's script content, when dispatched via the concrete/native-steps path, spawns subprocesses inheriting the ambient identity of the `gitlab-runner` process — not any configured shell executor `User` — while the classic path correctly drops to `User` via `su`.

### Impact Explanation
On a shell executor host where the operator configured `User` specifically to restrict job scripts to run as a low-privileged local account (a documented shell-executor hardening mechanism), enabling `FF_CONCRETE` (or any config that routes jobs through `UseConcrete`) silently causes job scripts to execute as whatever identity runs the `gitlab-runner` process (frequently `root` for a system-installed service, or a runner service account with broader filesystem/network access than the intended job user). This is a privilege-escalation-by-omission for any attacker-controlled `.gitlab-ci.yml` script content on that shared host, since script/step content is fully attacker-controlled by the pipeline author and the identity check that the operator relies on is bypassed entirely without any error or warning.

### Likelihood Explanation
Preconditions are narrow but realistic: a shell executor configured with `User` for privilege dropping, and `FF_CONCRETE`/native-steps enabled (which GitLab has been rolling out as the future default execution mode). Any pipeline author on that runner can trigger this merely by having a job scheduled, with no special job configuration needed beyond normal CI script content — the divergence happens automatically once concrete dispatch is chosen for the executor. No additional protections in `localserver`, `concrete`, or `env.Command` check or reject a configured `User`; the setting is simply never read on this path, so there is no fallback to safety (e.g., no forced-legacy-path or explicit error when `User` + concrete are both set).

### Recommendation
Thread the shell executor's `User` through to the concrete/native-steps execution path: either (a) reject/force-fallback to the legacy script path when both `Shell().User` and native/concrete dispatch are configured together, or (b) propagate `User` from `Prepare` into `localserver.Options` (or per-request `RunRequest` metadata) and apply an equivalent `su`-style wrapping (or `syscall.Credential`) inside `functions/concrete/run/stages/step.go`'s `shell()` / `env.Command`, so subprocess identity matches the configured `User` in both paths. At minimum, `executors/shell/steps.go`'s `Connect` should fail loudly if `s.Shell().User != ""` while dispatch is routed through `localserver`, rather than silently ignoring it.

### Proof of Concept
Go unit test in `functions/concrete/run/env` (or an integration test spanning `executors/shell`):
1. Configure a shell executor with `Shell().User = "nobody"` (or another low-priv test account) and `FF_CONCRETE`/`UseConcrete` on.
2. Dispatch a job whose script is `id -u` (or `os.Getuid()`-based Go helper) through the concrete path (`Build.executeConcreteJob`).
3. Capture command stdout and assert the reported uid/username equals the configured `User`'s uid, not `os.Getuid()` of the test process.
4. Expected today: test fails — the captured uid equals the runner test process's own uid (ambient identity), proving `User` is not applied through `functions/concrete/run/env/env.go`'s `Env.Command` / `stages/step.go`'s `shell()`.
5. Cross-check: same script dispatched via classic `shell.Run` (`FF_CONCRETE` off) correctly shows the `su`-mapped identity, confirming the divergence is specific to the concrete/localserver path.

func (e *Env) Command(ctx context.Context, name string, env map[string]string, args ...string) error {
	environ := os.Environ()
	for k, v := range e.Env {
		environ = append(environ, k+"="+v)
	}
	for k, v := range e.GitLabEnv {
		environ = append(environ, k+"="+v)
	}
	for k, v := range env {
		environ = append(environ, k+"="+v)
	}

	cmd := gracefulexitcmd.New(ctx, e.GracefulExitDelay, name, args...)
	cmd.Dir = e.WorkingDir
	cmd.Env = environ
	cmd.Stdout = e.Stdout
	cmd.Stderr = e.Stderr

	return normalizeExitError(cmd.Run(), cmd.ProcessState)
}
