### Title
Authorization bypass allowing any non-owner signer to withdraw from a receivership account via `solend_withdraw` - (File: `programs/marginfi/src/instructions/solend/withdraw.rs`)

### Summary
`start_liquidation` is permissionless and lets any caller flip `ACCOUNT_IN_RECEIVERSHIP` on any unhealthy marginfi account while setting an attacker-controlled, unchecked `liquidation_receiver`. Once the flag is set, `is_signer_authorized(&a, g.admin, authority.key(), true, false)` in `solend_withdraw`'s account constraints authorizes *any* signer other than the account's true authority, regardless of whether that signer matches the recorded `liquidation_receiver`, letting an unrelated third party race in and withdraw Solend collateral to an arbitrary `destination_token_account`.

### Finding Description
`StartLiquidation` in [1](#0-0) is explicitly documented as "(Permissionless)" and accepts a `liquidation_receiver: UncheckedAccount` with "CHECK: no checks whatsoever, liquidator decides this without restriction" [2](#0-1) . It calls `start_receivership`, which sets `ACCOUNT_IN_RECEIVERSHIP` to true on the target account [3](#0-2) , gated only on the account being unhealthy (`ignore_healthy=false` for liquidation) — a condition attacker cannot fabricate for a healthy account, but is trivially satisfiable for any account that is genuinely unhealthy/liquidatable, which is a normal, expected state reachable without special privilege.

Once `ACCOUNT_IN_RECEIVERSHIP` is set, `solend_withdraw`'s account validation calls `is_signer_authorized(&a, g.admin, authority.key(), true, false)` [4](#0-3) . The implementation of `is_signer_authorized` shows that when `allow_receivership` is true and the flag is set, it returns `marginfi_account.authority != signer` — i.e., **any signer other than the true owner is authorized**, with no check against `liquidation_record.liquidation_receiver` at all [5](#0-4) .

Combined with `destination_token_account` being fully caller-controlled ("the caller controls the destination") [6](#0-5) , this means: once any unhealthy account enters receivership (which any permissionless caller can trigger via `start_liquidation`), a completely unrelated third-party signer — not the designated `liquidation_receiver`, not an admin — can call `solend_withdraw` and redirect the account's Solend collateral withdrawal to their own token account, racing ahead of the legitimate liquidator/receiver.

### Impact Explanation
This breaks the intended invariant that only the designated `liquidation_receiver` (or the true owner, outside receivership) should be able to manipulate account balances during receivership. An arbitrary unprivileged actor can redirect withdrawn liquidity to an attacker-chosen `destination_token_account`, causing direct value theft/misdirection of funds that belong to the account (and ultimately its owner/depositors), not merely griefing. This is a genuine authorization-bypass with durable financial impact, consistent with the audit's AUTHZ_HOLDS invariant being violated.

### Likelihood Explanation
Highly feasible and repeatable: `start_liquidation` is permissionless and requires only that the target account be unhealthy (a state that occurs naturally under normal market conditions and is observable on-chain by anyone). Any bot monitoring for `ACCOUNT_IN_RECEIVERSHIP` accounts (or one that triggers it themselves) can race a `solend_withdraw` call with itself as `authority` and its own `destination_token_account`, as `is_signer_authorized` places no restriction tying the signer to the actual `liquidation_receiver` recorded in `liquidation_record`.

### Recommendation
`is_signer_authorized`'s receivership branch should validate that `signer` matches the `liquidation_record.liquidation_receiver` for the given account (requiring the `liquidation_record` account to be passed into and checked by every withdraw/repay CPI-integration instruction, as is likely already done elsewhere, e.g. `liquidate_end.rs`), rather than authorizing any non-owner signer. Audit `borrow.rs`, `close_balance.rs`, `deposit.rs`, `repay.rs`, and all other integration deposit/withdraw instructions (`drift`, `juplend`, `kamino`, `solend`) that call `is_signer_authorized(..., true, ...)` for the same gap.

### Proof of Concept
Integration test plan (Rust, using `programs/marginfi/tests` harness):
1. Set up a marginfi group, bank, and a marginfi account owned by `owner`, with a Solend position, and drive it into an unhealthy state.
2. Call `start_liquidation` as `attacker_A`, setting `liquidation_receiver = attacker_A_receiver` (an account attacker_A controls). Assert `ACCOUNT_IN_RECEIVERSHIP` flag is now set on the account.
3. In the same transaction (before `end_liquidation`), invoke `solend_withdraw` with `authority = attacker_B` (a completely different, unrelated signer not equal to `attacker_A_receiver` or `owner`), and `destination_token_account` = attacker_B's own token account.
4. Assert the transaction **succeeds** (demonstrating the bug) and that funds land in attacker_B's token account — i.e., neither `owner` nor the designated `liquidation_receiver` (`attacker_A_receiver`) authorized this withdrawal.
5. Cross-check against `is_signer_authorized`: add a unit test in `marginfi_account.rs` asserting `is_signer_authorized(&account_in_receivership, admin, arbitrary_pubkey, true, false) == true` for any `arbitrary_pubkey != account.authority`, confirming the missing binding to `liquidation_record.liquidation_receiver`.
