### Title
Unauthenticated user enumeration via distinguishable error bodies and bcrypt timing in session login - ([File: core/sessions/localauth/orm.go], [File: core/web/sessions_controller.go])

### Summary
The local-auth `CreateSession` flow returns different, unwrapped error content for "unknown email" vs. "wrong password" cases, and the `SessionsController.Create` HTTP handler forwards the raw internal error message verbatim into the JSON response body. Combined with the fact that only known-email attempts trigger a bcrypt password comparison, an unauthenticated client can enumerate valid operator emails via response-body content and timing differences.

### Finding Description
`orm.CreateSession` in `core/sessions/localauth/orm.go` first calls `o.FindUser(ctx, sr.Email)`, which runs `SELECT * FROM users WHERE lower(email) = lower($1)` [1](#0-0) . If the email does not exist, the function returns immediately with the raw, un-wrapped SQL error (e.g. `sql: no rows in result set`) at line 147 (`return "", err`) [2](#0-1) , without ever calling `utils.CheckPasswordHash`.

If the email does exist, the code proceeds to `utils.CheckPasswordHash(sr.Password, string(user.HashedPassword))`, a bcrypt-based comparison, and on mismatch returns a distinctly different error `"Invalid password"` [3](#0-2) .

Crucially, `SessionsController.Create` in `core/web/sessions_controller.go` forwards this raw `err` object straight into the HTTP response body via `jsonAPIError(c, http.StatusUnauthorized, err)` [4](#0-3) , and `jsonAPIError` serializes `err.Error()` directly into the JSON payload when it isn't already a `*models.JSONAPIErrors` [5](#0-4) . This means the client-visible response body differs by exact database driver error text for unknown emails vs. the fixed `"Invalid password"` string for existing accounts with wrong passwords — a direct content-based user-enumeration oracle at HTTP status 401 for both cases.

Additionally, because the bcrypt hash comparison (`utils.CheckPasswordHash`, backed by `golang.org/x/crypto/bcrypt`) only executes on the "known email" code path, the response latency for known-email/wrong-password attempts is measurably higher (bcrypt cost factor induces tens-to-hundreds of milliseconds) than for unknown-email attempts, which fail fast at the SQL lookup. This constitutes a secondary timing side-channel reinforcing the same enumeration capability, matching the "authentication failures must be uniform in content and timing" invariant violation described in the question.

Existing tests in `core/web/sessions_controller_test.go` (`TestSessionsController_Create`) confirm both "incorrect pwd" and "incorrect email" cases only assert `resp.StatusCode >= 400` without validating the response body is uniform, so this discrepancy is not caught by current tests [6](#0-5) .

Note: the rate limiter on `/sessions` (`unauth.POST("/sessions", sc.Create)` wrapped with `rateLimiter`) throttles brute force volume but does not close the content/timing oracle itself [7](#0-6) .

### Impact Explanation
This is a user-enumeration primitive, not by itself a full node takeover. It allows an unauthenticated attacker reaching the node's API port to precisely determine which operator email addresses are valid accounts before mounting a targeted password-guessing or credential-stuffing attack, reducing the search space and improving the efficiency of subsequent credential attacks. It maps to a lower-severity "authentication weakness/information disclosure" class rather than the "Critical - node takeover" impact claimed in the question; enumeration alone does not grant a session, token, or key access. The escalation to node takeover requires a *further* successful credential attack, which is a distinct precondition not established here.

### Likelihood Explanation
No privileges are required — only network reachability to the node's API port and the ability to send POST requests to `/sessions`. Exploitation is trivial and fully repeatable: sending two requests (one with a known email/wrong password, one with a random/unknown email) and diffing the JSON error body (or measuring response latency) reliably distinguishes account existence. Rate limiting (`rl.UnauthenticatedPeriod()`/`rl.Unauthenticated()`) constrains request throughput but does not prevent a slow, low-volume enumeration campaign.

### Recommendation
- In `core/sessions/localauth/orm.go`, always perform a (dummy) bcrypt comparison against a constant/dummy hash when the user is not found, so both code paths take equivalent time, and return one identical opaque error (e.g., `"invalid email or password"`) for both "user not found" and "password mismatch" cases.
- In `core/web/sessions_controller.go`, stop forwarding the raw ORM error into the HTTP response; replace `jsonAPIError(c, http.StatusUnauthorized, err)` with a fixed, generic error message that does not vary based on which internal validation step failed.
- Apply the same treatment to `FindUserByAPIToken`/API-token authentication paths and the LDAP/OIDC `localLoginFallback` variants, which have analogous `"invalid email"`/`"invalid password"` distinctions [8](#0-7) .

### Proof of Concept
Go handler-level integration test plan (extending `TestSessionsController_Create` in `core/web/sessions_controller_test.go`):
1. Create one real user via `app.AuthenticationProvider().CreateUser`.
2. Send POST `/sessions` with `{email: realUser, password: "wrongpassword"}` — capture status code, full response body, and latency.
3. Send POST `/sessions` with `{email: "doesnotexist@test.com", password: "wrongpassword"}` — capture status code, full response body, and latency.
4. Assert both requests return the same status code (currently true, both 401/`>=400`).
5. Assert both requests return **byte-identical response bodies** — expected to **fail** currently, since body 1 contains `"Invalid password"` while body 2 contains a raw SQL "no rows" style error string.
6. Optionally repeat each request N times and assert the mean latency difference between the two cases is within a small tolerance — expected to show a measurable gap due to the bcrypt-only code path for known emails.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
