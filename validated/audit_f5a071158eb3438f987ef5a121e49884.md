### Title
Unprivileged ERC4626 vault liquidity drain forces `onStopEpoch` revert, freezing all epoch funds indefinitely - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` treats "vault shares economically cover the shortfall" as sufficient, but calls `vault.withdraw(shortfall)` and reverts with `StopEpochVaultLiquidityUnavailable` when the external ERC4626 vault lacks withdrawable liquidity. The revert bubbles into `IdleCDOEpochVariant.stopEpoch`, so the epoch can never be stopped while the vault is illiquid. An unprivileged user of the programmable borrower's ERC4626 vault (e.g., a borrower draining the underlying Morpho market the vault allocates to) can keep the vault illiquid across `epochEndDate` and freeze every LP's funds.

### Finding Description
In `onStopEpoch`, when on-hand cash is below `_amountRequired`, the code compares the shortfall against `_currentVaultAssets()` — the *valuation* of the borrower's share position (`convertToAssets`), not the *liquidity* the vault can actually pay out (`maxWithdraw`): [1](#0-0) 

Two distinct failure modes exist and only one is handled:

- `shortfall > _currentVaultAssets()`: returns `true`, letting IdleCDO's `transferFrom` fail and route to the default path.
- `shortfall <= _currentVaultAssets()` but `shortfall > vault.maxWithdraw(...)`: `vault.withdraw` reverts and the catch reverts the whole `stopEpoch` call.

IdleCDO relies on hook reverts bubbling so the stop can be retried: [2](#0-1) 

There is no partial-withdrawal fallback: the hook does not withdraw what liquidity *is* available and then let the transferFrom pull the remainder later. Because `stopEpoch` is the only path to end an epoch, and `requestWithdraw`/claims and deposits are gated on epoch state (`isEpochRunning`, `allowAAWithdrawRequest`, `_beforeUnpause` blocks unpause while `isEpochRunning`), a sustained revert means permanent-until-resolved freezing of the entire pool NAV — including honest pending withdraw requests that matured in the stopped epoch.

The attacker transaction: in Morpho-style ERC4626 vaults the vault's assets are lent into markets; any market participant can borrow down available liquidity. An attacker (allowed role: "user of the programmable borrower's ERC4626 vault") keeps vault idle liquidity below `shortfall` around `epochEndDate` (either by holding a large borrow or by sandwiching `stopEpoch` calls, since the revert is retryable but the attack is repeatable each block). `totalInterestDueNow()` was already consumed before the hook, so the resolved interest value is unaffected — the freeze is purely mechanical.

### Impact Explanation
Temporary freezing of funds at pool scale: the entire NAV (AA + BB tranche holders plus pending withdraw receipts) cannot be withdrawn while the vault is illiquid, and the attacker can extend the window arbitrarily by keeping vault liquidity drained each time `stopEpoch` is retried. Loss magnitude equals full pool TVL for the duration of the freeze; unlike a normal default, no `defaulted` state is entered, so even the default-recovery flow is unavailable to LPs while this persists.

### Likelihood Explanation
Likelihood is moderate-to-high for deployments on allocated-liquidity vaults. The precondition is only that the vault's withdrawable liquidity be below the stop-epoch shortfall — a normal market state for lending vaults near full utilization, reachable without collusion. The attacker needs no privileged role and no capital loss (borrowing requires collateral but is economically self-serving when the vault offers favorable rates). Note the code comment at lines 243-245 acknowledges the ERC4626-withdrawal-failure case and deliberately makes it retryable, but this design choice converts a recoverable partial-liquidity event into a total stop-epoch DoS vector rather than degrading gracefully.

### Recommendation
In `onStopEpoch`, withdraw up to `vault.maxWithdraw(address(this))` (capped at `shortfall`) instead of requiring the full `shortfall` in one `withdraw` call, tracking the actual redeemed assets in `epochWithdrawnFromVault`. If even the capped withdraw reverts or zero liquidity is available, either (a) return `false`/`true` in a way that routes to `_handleBorrowerDefault` for the unrecoverable remainder, or (b) allow `stopEpoch` to complete with the cash actually recalled and account the missing amount as a vault loss via `bufferedVaultDelta`/loss accounting, so tranche holders bear the shortfall explicitly instead of being frozen. At minimum, bound the retry window: if `stopEpoch` has reverted for a threshold period past `epochEndDate`, permit a forced default/loss-crystallization path so LPs are not held hostage to vault liquidity cycles.

### Proof of Concept
A Foundry fork PoC (extending the existing harness in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`, which already forks a live MetaMorpho vault and demonstrates `vault.setWithdrawLimit`-style liquidity caps via the mock in `test/foundry/ProgrammableBorrowerAccountingInvariant.t.sol:325-328`):

```solidity
function testVaultIlliquidityFreezesStopEpoch() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    // LP requests a withdraw so _pendingWithdraws > 0 at stop
    // (or rely on _expectedInterest being pulled as cash in non-minted mode)

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Attacker (vault market borrower) drains vault liquidity so that
    // maxWithdraw(programmableBorrower) < required shortfall while
    // convertToAssets(shares) still covers it.
    morphoBorrower.borrowUpToLiquidity(); // or vault.setWithdrawLimit(0) on the mock

    // stopEpoch reverts via StopEpochVaultLiquidityUnavailable -> epoch never ends
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Repeat: attacker keeps liquidity drained; every retry reverts.
    // Meanwhile: requestWithdraw reverts (epoch running), unpause reverts
    // via _beforeUnpause(isEpochRunning), claimWithdrawRequest unavailable.
    assertTrue(cdoEpoch.isEpochRunning());
}
```

Key assertion: `_currentVaultAssets()` (share valuation) stays above `shortfall`, so the code enters the `try vault.withdraw` branch and reverts — demonstrating that share coverage, not liquidity coverage, is the flawed gate, mirroring the upstream bug class (trusting an inherited/self-reported descriptor field — here the vault's accounting value — without validating it against the property actually needed).
