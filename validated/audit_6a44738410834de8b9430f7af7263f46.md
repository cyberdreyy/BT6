This confirms a genuine TOCTOU vulnerability. The `isReplay` check and `recordUsage` write are two separate, non-atomic operations under `jwtReplayCache`, each taking its own lock rather than a single atomic "check-and-set."

### Title
JWT Replay Cache TOCTOU Allows Concurrent Double-Use of a Single-Use Workflow Trigger JWT - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` verifies a JWT, checks replay status via `jwtCache.isReplay(claims.ID)`, performs authorized-key lookup, and only then calls `jwtCache.recordUsage(claims.ID)`. Because `isReplay` and `recordUsage` are separate lock acquisitions rather than an atomic check-and-set, two concurrent `Authorize` calls with the same valid, observed JWT can both pass the `isReplay` check before either calls `recordUsage`, resulting in double execution of a workflow trigger that is supposed to be single-use.

### Finding Description
`Authorize` at [1](#0-0)  performs, in order: JWT verification (`utils.VerifyRequestJWT`), a read-only replay check (`h.jwtCache.isReplay(claims.ID)`), authorized-key lookup, and finally `h.jwtCache.recordUsage(claims.ID)`. The underlying cache implements these as two independently-locked operations: [2](#0-1) 

`isReplay` takes an `RLock`, reads, and releases; `recordUsage` separately takes a `Lock`, writes, and releases. There is no single atomic "check-and-mark" operation and no external lock held across the gap between them in `Authorize`. If an attacker has observed one valid signed JWT for someone else's workflow trigger (e.g., via network capture, logs, or a replayed HTTP request body), they can submit two (or more) concurrent gateway requests wrapping that same JWT in fresh outer `jsonrpc.Request` envelopes. Both goroutines can call `isReplay(claims.ID)` and get `false` before either calls `recordUsage`, so both pass the check, both pass the authorized-key lookup (same signer, same workflow), and both proceed to trigger the workflow — violating the intended single-use invariant of the `jti` claim.

This differs materially from the sibling implementation in `core/capabilities/vault/request_replay_guard.go`, where `CheckAndRecord` performs the existence check and the map write atomically under a single mutex acquisition: [3](#0-2) . The vault package's design (and its concurrency test `TestRequestReplayGuard_ConcurrentAccess` asserting exactly one success out of 100 concurrent calls) demonstrates the correct atomic pattern that `jwtReplayCache` fails to follow.

The existing test `duplicate JWT token and request ID` in `http_trigger_handler_test.go` only exercises the sequential (non-concurrent) case and does not catch this race: [4](#0-3) .

### Impact Explanation
This is a request-binding/replay-protection bypass leading to unauthorized double-execution of another user's workflow trigger using only an observed (not forged) JWT. Depending on what the triggered workflow does (e.g., fund movement, state-changing capability actions), this can cause duplicate side effects attributable to the legitimate signer, i.e., unauthorized action performed using another user's credential replayed by an attacker who merely observed the token in transit/logs.

### Likelihood Explanation
Exploitation requires only observation of one valid signed JWT (no forgery or private key access) plus the ability to send two nearly-simultaneous gateway requests carrying that token — both are within reach of an unprivileged network client. The race window is small but real, and is fully client-controlled (attacker chooses submission timing/concurrency), making it repeatable via straightforward concurrent HTTP/gateway request submission in a tight loop.

### Recommendation
Replace the separate `isReplay`/`recordUsage` calls in `jwtCache` with a single atomic check-and-set method (analogous to `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go`), holding the `Lock` for the entire check-then-insert sequence, and call it once inside `Authorize` immediately after the authorized-key check passes (or as the first replay-relevant step under a single critical section spanning existence-check-and-insert).

### Proof of Concept
Go test in `core/services/gateway/handlers/capabilities/v2` package:
1. Construct a `WorkflowMetadataHandler` (via `createTestTriggerHandler`-style helper) and register a workflow/authorized key as in existing tests.
2. Build a single `jsonrpc.Request` with a fixed `claims.ID` (jti) and sign a JWT for it via `createTestJWTToken`.
3. Launch `N` (e.g., 50) goroutines, each calling `handler.Authorize(workflowID, token, req)` (or `HandleUserTriggerRequest` with fresh outer envelopes but the same JWT/jti) concurrently, collecting results into a slice.
4. Assert that exactly one goroutine returns success (`nil` error, non-nil key) and the rest return the "JWT token has already been used" error — mirroring the pattern in `TestRequestReplayGuard_ConcurrentAccess` at [5](#0-4) . With the current `isReplay`/`recordUsage` split, this assertion will fail intermittently (more than one success), demonstrating the TOCTOU race.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func TestRequestReplayGuard_ConcurrentAccess(t *testing.T) {
	guard := NewRequestReplayGuard()
	futureExpiry := time.Now().UTC().Unix() + 100

	const goroutines = 100
	results := make([]error, goroutines)
	var wg sync.WaitGroup
	wg.Add(goroutines)

	for i := range goroutines {
		go func(idx int) {
			defer wg.Done()
			results[idx] = guard.CheckAndRecord("same-digest", futureExpiry)
		}(i)
	}
	wg.Wait()

	successCount := 0
	duplicateCount := 0
	for _, err := range results {
		if err == nil {
			successCount++
		} else {
			require.ErrorIs(t, err, ErrRequestAlreadySeen)
			duplicateCount++
		}
	}

	assert.Equal(t, 1, successCount, "exactly one goroutine should succeed")
	assert.Equal(t, goroutines-1, duplicateCount, "all others should be rejected as duplicates")
}
