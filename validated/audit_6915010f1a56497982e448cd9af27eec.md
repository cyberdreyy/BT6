### Title
Missing mint-account ownership validation allows spoofed decimals/UiTokenAmount fidelity break - ([File: rpc/src/parsed_token_accounts.rs])

### Summary
`get_mint_owner_and_additional_data` and `get_additional_mint_data` unpack any account's bytes as `StateWithExtensions::<Mint>` without verifying that account is owned by an SPL Token program. Several RPC paths (`get_token_account_balance`, `get_parsed_token_account`, `get_parsed_token_accounts`) resolve a token account's "mint" field to an arbitrary pubkey and use whatever data unpacks there for `decimals`, so an attacker can plant a fake "mint" account with spoofed decimals and have it reflected in returned `UiTokenAmount`s.

### Finding Description
`get_token_account_mint` in `account-decoder/src/parse_token.rs` (lines 166-170) extracts the mint field (first 32 bytes) from token account data with no validation that it points to a real, correctly-owned mint. Callers then resolve that pubkey to whatever account currently exists at that address: [1](#0-0) 

`get_mint_owner_and_additional_data` fetches `bank.get_account(mint)` and calls `get_additional_mint_data`, which does `StateWithExtensions::<Mint>::unpack(data)` with zero ownership check [2](#0-1) . The `decimals` field returned is `mint.base.decimals` — fully attacker-controlled if the attacker owns/writes the account at that pubkey.

Concretely:
- `get_token_account_balance` (`rpc/src/rpc.rs` lines 2013-2035) validates that the *token account* is owned by a known SPL token program, but discards the mint's owner (`let (_, data) = get_mint_owner_and_additional_data(&bank, mint)?;`) — it never checks that the mint account itself belongs to a token program before trusting its decimals. [3](#0-2) 
- `get_parsed_token_accounts` (used by jsonParsed `getTokenAccountsByOwner`/`getProgramAccounts`) similarly discards the mint owner: `let (_, data) = get_mint_owner_and_additional_data(&bank, &mint_pubkey).ok()?;` [4](#0-3) 
- `get_parsed_token_account` (used by jsonParsed `getAccountInfo`) calls `get_additional_mint_data` directly, which has no owner-check parameter at all [5](#0-4) 

By contrast, `get_token_supply` and `get_token_program_id_and_mint` do correctly call `is_known_spl_token_id` on the mint owner before trusting the unpacked data [6](#0-5) [7](#0-6) , showing the check is known-necessary but inconsistently applied.

The `decimals` value flows straight into `token_amount_to_ui_amount_v3`, which uses it unconditionally to compute `ui_amount`/`ui_amount_string` [8](#0-7) .

### Attacker Flow
1. Attacker sends a transaction (e.g. via System Program `allocate`/`assign`/`transfer` funding + a program they control, or any account they can write with arbitrary data — a `Mint`-shaped account is only 82 bytes, no signature over "being a mint" is required) to create an account at pubkey `M` containing valid `Mint` layout bytes with `decimals = 255` (or any spoofed value), owned by an arbitrary/unrelated program.
2. Attacker creates a legitimate SPL Token Account (owned by real `spl_token` program) with its `mint` field set to `M`.
3. Attacker calls `getTokenAccountBalance` on that token account, or `getAccountInfo`/`getTokenAccountsByOwner` with `jsonParsed` encoding.
4. The RPC resolves `M` via `bank.get_account`, unpacks it as `Mint` without checking `M`'s owner, and returns a `UiTokenAmount` with the attacker's spoofed `decimals`/`ui_amount`/`ui_amount_string`, misrepresenting the real balance to any client/integrator trusting the RPC response.

### Impact Explanation
This is a decode/parse fidelity bug (PARSE_FIDELITY invariant) reachable from a single unprivileged read-only RPC call after one on-chain write. It causes RPC to return incorrect `UiTokenAmount.decimals`/`ui_amount`/`ui_amount_string` for a real token account, which can mislead downstream integrators (wallets, explorers, exchanges) about the actual value represented by a token balance — a wrong-data-returned class finding under Agave's RPC correctness/security scope.

### Likelihood Explanation
Fully attacker-controlled and repeatable with a single low-cost transaction (write one small account) plus a single subsequent RPC call, no special privileges, no validator/leader control needed. It is deterministic given the missing owner check in `get_additional_mint_data`/`get_mint_owner_and_additional_data`.

### Recommendation
In `get_mint_owner_and_additional_data` and `get_additional_mint_data`, verify the mint account's owner is a known SPL token program id (`is_known_spl_token_id`) before trusting its unpacked `decimals`/extension data, and propagate that check consistently to all callers (`get_token_account_balance`, `get_parsed_token_account`, `get_parsed_token_accounts`) instead of discarding the returned owner with `_`.

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };
    UiTokenAmount {
        ui_amount,
        decimals,
        amount: amount.to_string(),
        ui_amount_string,
    }
