### Title
`instantWithdrawClaimsByEpoch` accumulates forever — claimed instant receipts are never decremented, inflating default-recovery basis and diluting the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2022-2928 (a refcount incremented on every `add_option()` call with no matching `option_dereference()`), `IdleCreditVault.requestInstantWithdraw` increments `instantWithdrawClaimsByEpoch[epochNumber]` on every request, but the normal claim path `claimInstantWithdrawRequest` clears only the per-user aggregate `instantWithdrawsRequests[_user]` and never decrements the per-epoch total. The epoch counter is a monotonically accumulating "refcount" that is only decremented on the defaulted-claim path. When a default is later finalized, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` read this stale, inflated value and treat already-paid-out claims as if they were still backed by strategy-held underlying.

### Finding Description
- `requestInstantWithdraw` adds `_amount` to `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (`IdleCreditVault.sol:367-374`).
- `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]` and pays the user, but never touches `instantWithdrawClaimsByEpoch` or `instantWithdrawsRequestsByEpoch` (`IdleCreditVault.sol:387-393`). Only `_claimDefaultedInstantWithdrawRequest` decrements both (`IdleCreditVault.sol:847-853`).
- At default finalization, `finalizeDefaultRecovery` computes `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` where `prefundedReserve = instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` when positive (`IdleCreditVault.sol:685-722`). Stale claims inflate `prefundedReserve` — counting tokens that were already transferred out as if still held — and inflate `basis` via `defaultPendingClaimBasis` (`IdleCreditVault.sol:644-649`).
- The result is a `defaultRecoveryPrice` computed against phantom reserve: recovery claims pay out `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` against a reserve that does not actually contain those tokens (`IdleCreditVault.sol:855`, `899-910`).

### Impact Explanation
An unprivileged tranche-token holder can repeatedly request and claim instant withdrawals within one epoch (each request mints receipt tokens, claims burn only the user-level aggregate). Each round-trip leaves a permanent, un-decremented residue in `instantWithdrawClaimsByEpoch[epoch]`. If the epoch later defaults with any genuinely unfunded instant receipt outstanding (`pendingInstantWithdraws != 0`), the inflated epoch basis (a) counts phantom prefunded reserve, pushing `defaultRecoveryPrice` above what the real reserve supports — early claimants of defaulted receipts are overpaid and drain the reserve, leaving later claimants (including honest defaulted-epoch withdrawers) with nothing — direct theft/insolvency of the recovery reserve; and (b) inflates `totalBasis`, mispricing the haircut applied to all active AA/BB holders. Loss magnitude scales with the accumulated stale claims the attacker can build up before the epoch ends, bounded by instant-withdraw liquidity the attacker cycles.

### Likelihood Explanation
Requires: instant-withdraw mode enabled, an attacker able to make instant withdraw requests (unprivileged lender flow through the CDO), and a subsequent borrower default in the same epoch while some instant receipt is still unfunded. Attacker setup is cheap (repeat request→claim), but payoff materializes only on default finalization, an honest-party event. Medium likelihood.

### Recommendation
In `claimInstantWithdrawRequest` (and the funded-claim portion of the default path), decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` symmetrically with `instantWithdrawsRequests[_user]`, mirroring the decrement already present in `_claimDefaultedInstantWithdrawRequest`. Alternatively, derive the funded/prefunded instant reserve from actual strategy token balance rather than a cumulative per-epoch counter.

### Proof of Concept
```solidity
// Foundry fork test sketch (contracts/test harness style of test/foundry/IdleCreditVault.t.sol)
function testInstantClaimsEpochCounterLeak() external {
    // Setup: credit vault with instant withdraws allowed, epoch N running/buffer.
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true); // AA tranche deposit via CDO

    uint256 epoch = creditVault.epochNumber();
    uint256 claims0 = creditVault.instantWithdrawClaimsByEpoch(epoch);

    // Attacker cycles: requestInstantWithdraw -> funded -> claimInstantWithdrawRequest, x3.
    for (uint256 i; i < 3; ++i) {
        vm.prank(attacker);
        cdoEpoch.requestInstantWithdraw(10_000 * ONE_SCALE); // _mint receipt, ++counters
        // borrower/CDO funds instant requests (collectInstantWithdrawFunds pulls tokens)
        // then user claims:
        vm.prank(attacker);
        cdoEpoch.claimInstantWithdrawRequest(); // burns user agg, never decrements epoch map
    }
    uint256 leaked = creditVault.instantWithdrawClaimsByEpoch(epoch) - claims0;
    assertEq(leaked, 30_000 * ONE_SCALE); // stale residue remains forever

    // New unfunded instant receipt in same epoch, then borrower defaults.
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(5_000 * ONE_SCALE);
    // ... borrower fails to repay; CDO calls finalizeDefaultRecovery ...
    // _defaultPrefundedInstantReserve() returns (30k+5k) - pendingInstantWithdraws,
    // counting 30k already-paid tokens as held reserve -> inflated recoveryPrice,
    // overpaying early recovery claimants and leaving the reserve insolvent for the rest.
}
```

Note: the exact CDO-side entry points (`cdoEpoch.requestInstantWithdraw`/`claimInstantWithdrawRequest` names and the funding step via `collectInstantWithdrawFunds`) were inferred from `IdleCreditVault.sol`'s `_onlyIdleCDO` interface and repo tests; I could not fully verify the CDO wrapper signatures within the available iterations, but the missing decrement in the strategy contract is confirmed by direct reading of `IdleCreditVault.sol:356-393` and `842-856`.
