### Title
StackerDBListener double-counts a signer's weight in both `total_weight_rejected` and `total_weight_approved` when a signer flips from Reject to Accept for the same block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::handle_message` (miner-side aggregator used by `SignerCoordinator::get_block_status`) tallies per-signer weight for a proposed block into two running counters, `total_weight_approved` and `total_weight_rejected`. The `Accepted` branch only guards against double counting by checking `gathered_signatures.contains_key(&slot_id)` (a prior *acceptance*), while the `Rejected` branch guards with `responded_signers.insert(slot_id)` (any prior response, accept or reject). This makes the de-duplication asymmetric: Accept→Reject is protected, but Reject→Accept is not. Since the signer protocol explicitly allows a signer to reconsider and flip a prior rejection into an acceptance for the same block (`should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`, and the equivalent `SignerDb::add_block_signature`/`add_block_rejection_signer_addr` pairing that correctly deletes the stale rejection row), a single signer's weight ends up counted in *both* tallies at the node/coordinator, breaking the "aggregated weight equals sum of unique verified votes" invariant.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- `Accepted` handling:
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [1](#0-0) 

- `Rejected` handling:
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [2](#0-1) 

If a signer's first message for a block is a `Rejected` response, `responded_signers.insert(slot_id)` succeeds and `total_weight_rejected` is bumped by that signer's weight. If the same signer later legitimately reconsiders and sends an `Accepted` response for the same block (a supported flow — see the reject-reconsideration logic and the changelog entry stating votes must not double count), the `Accepted` branch's only guard is `gathered_signatures.contains_key(&slot_id)`, which is false (the signer never accepted before), so `total_weight_approved` is *also* bumped by the same signer's weight. The signer is now counted in both totals simultaneously, with no code path ever decrementing `total_weight_rejected` for that slot.

This is the mirror-image of the bug class in the external report: a value meant to represent one committed state (a "deposit"/rejection) is not cleared/withdrawn when a conflicting, later, valid operation (the "accept") occurs, so both states are simultaneously counted against the same underlying accounting pool.

By contrast, `stacks-signer/src/signerdb.rs::add_block_signature` correctly deletes any existing `block_rejection_signer_addrs` row for that signer/block before inserting the signature, and `add_block_rejection_signer_addr` refuses to record a rejection if a signature already exists — showing the signer-side DB has the exact protection that is missing in the node-side `StackerDBListener` aggregator. [3](#0-2) [4](#0-3) 

The re-evaluation flow that legitimately produces a reject-then-accept sequence from a single signer is a designed, in-scope feature, not an attack requiring a majority: [5](#0-4) 

### Impact Explanation
`SignerCoordinator::get_block_status` uses these two counters to decide the block's fate:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight { ... return Err(SignersRejected...) }
else if block_status.total_weight_approved >= self.weight_threshold { ... return Ok(gathered_signatures...) }
``` [6](#0-5) 

Because a single signer's weight can be counted in *both* buckets, the sum `total_weight_rejected + total_weight_approved` can exceed `total_weight`, i.e. the aggregated-weight-vs-verified-accepts equality is broken. In near-threshold scenarios this can cause the rejection branch (`total_weight_rejected + weight_threshold > total_weight`) to fire spuriously even though the true (deduplicated) rejecting weight never reached the blocking minority — causing the miner to abandon/repropose a block, or wrongly bump problematic-transaction exclusion counters, purely because of accounting inflation from one signer's legitimate vote change. This is a liveness degradation in the miner/coordinator's view of consensus rather than a signer forging an invalid signature, but it directly corrupts the weight tally the coordinator relies on for its accept/reject decision.

### Likelihood Explanation
This requires only a single signer (with any non-trivial weight) exercising the already-supported "reconsider a prior rejection" flow once for the same block. No majority, no forged signature, and no protocol violation is needed — it is a byproduct of ordinary reject→accept flip-flopping that the codebase already anticipates and protects against on the signer-DB side but not in the miner-side `StackerDBListener`.

### Recommendation
In the `Accepted` branch of `StackerDBListener::handle_message`, check `responded_signers` (not just `gathered_signatures`) before adding weight to `total_weight_approved`, and when a signer transitions from a prior rejection to an acceptance, subtract their weight from `total_weight_rejected` (and vice versa, to keep both directions symmetric), mirroring the delete-then-insert pattern already used in `SignerDb::add_block_signature`/`add_block_rejection_signer_addr`.

### Proof of Concept
1. Node proposes block B; signer S (weight w) sends `BlockResponse::Rejected` for B. `total_weight_rejected += w`, `responded_signers = {S}`.
2. S later reconsiders (a supported flow, e.g. after a reject reason becomes stale/reconsiderable) and sends `BlockResponse::Accepted` with a valid signature for the same B.
3. In the `Accepted` handler, `block.gathered_signatures.contains_key(&slot_id)` is `false` (S never accepted before), so `total_weight_approved += w` is executed even though S is already counted in `total_weight_rejected`.
4. `total_weight_rejected` is never decremented for S, so `total_weight_rejected + total_weight_approved` now exceeds the true number of distinct signer votes, and can exceed `total_weight`, corrupting the threshold checks in `SignerCoordinator::get_block_status`.

    /// Record an observed block signature
    pub fn add_block_signature(
        &self,
        block_sighash: &Sha512Trunc256Sum,
        signer_addr: &StacksAddress,
        signature: &MessageSignature,
    ) -> Result<bool, DBError> {
        // Remove any block rejection entry for this signer and block hash
        let del_qry = "DELETE FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2";
        let del_args = params![block_sighash, signer_addr.to_string()];
        self.db.execute(del_qry, del_args)?;

        // Insert the block signature
        let qry = "INSERT OR IGNORE INTO block_signatures (signer_signature_hash, signer_addr, signature) VALUES (?1, ?2, ?3);";
        let args = params![
            block_sighash,
            signer_addr.to_string(),
            serde_json::to_string(signature).map_err(DBError::SerializationError)?
        ];
        let rows_added = self.db.execute(qry, args)?;

        let is_new_signature = rows_added > 0;
        if is_new_signature {
            debug!("Added block signature.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %signer_addr,
                "signature" => %signature
            );
        } else {
            debug!("Duplicate block signature.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %signer_addr,
                "signature" => %signature
            );
        }
        Ok(is_new_signature)
    }
