### Title
`createDstEscrow` accepts caller-supplied fee amounts/recipients with no on-chain link to the source-chain fee commitment, allowing fee-like value theft/loss - ([File: contracts/BaseEscrowFactory.sol])

### Summary
`BaseEscrowFactory.createDstEscrow()` deploys the destination escrow using an `Immutables.parameters` blob (protocol fee amount, integrator fee amount, protocol/integrator fee recipients) that is supplied directly by the caller in calldata, with zero on-chain validation against the fee values that were computed and emitted on the source chain in `_postInteraction`.

### Finding Description
On the source chain, `_postInteraction` computes `integratorFeeAmount`/`protocolFeeAmount` via `FeeTaker._getFeeAmounts` and packages them into `DstImmutablesComplement.parameters`, which is only **emitted in an event** (`SrcEscrowCreated`), not stored or enforced on-chain: [1](#0-0) 

On the destination chain, `createDstEscrow` takes `dstImmutables` entirely from calldata and uses it as-is to deploy the clone — there is no check that `dstImmutables.parameters` (fee amounts/recipients) matches the complement emitted on the source side: [2](#0-1) 

The fee amounts are later trusted blindly in `EscrowDst._withdraw`, where they are subtracted directly from `immutables.amount` before paying the maker, and routed to whatever recipients were baked into the immutables at creation time: [3](#0-2) 

Because `hash()`/`hashMem()` in `ImmutablesLib` fold the caller-supplied `parameters` bytes into the deterministic address/salt used for `onlyValidImmutables` checks, the contract only verifies **internal self-consistency** (that the same immutables used at deploy time are used at withdraw time) — it never verifies that those immutables' fee fields match the off-chain-agreed / source-chain-committed values: [4](#0-3) 

This is the direct analog of the reported bug class: values computed off-chain (fee split) are handed to a privileged-looking but actually unprivileged-callable function (`createDstEscrow` has no access-control modifier restricting the caller) and used verbatim to determine distribution of value, with no on-chain arithmetic or cross-chain consistency check.

### Impact Explanation
Any caller of `createDstEscrow` (the party funding the destination escrow) can set `protocolFeeAmount` and `integratorFeeAmount` to `0` and set fee recipients to arbitrary/irrelevant addresses. At withdrawal time `EscrowDst._withdraw` will then pay the entire `immutables.amount` to the maker and nothing to the protocol/integrator fee recipients, permanently denying the protocol and integrator their fee revenue for that swap. This matches the bounty's Medium/High category: "theft or permanent loss of unclaimed fee-like value." It does not touch the maker's principal or safety deposit, so it is not a critical fund-theft/insolvency issue, but it does allow bypassing the fee-routing invariant entirely with no on-chain enforcement.

### Likelihood Explanation
High — no special privilege is required to call `createDstEscrow`; the caller simply supplies their own `dstImmutables` including the `parameters` bytes and funds the escrow themselves. Nothing in `BaseEscrowFactory` or `EscrowDst` cross-references the fee fields against the source-chain-committed `DstImmutablesComplement`, so exploitation requires only calling the function with modified fee parameters instead of the ones from the emitted `SrcEscrowCreated` event.

### Recommendation
Bind the destination escrow's fee parameters cryptographically to the source-chain commitment, e.g., by having `_postInteraction` store (or return via a verifiable structure such as a hash) the `DstImmutablesComplement.parameters` hash on-chain (or include it as part of a signed/committed payload validated in `createDstEscrow`), and have `createDstEscrow` revert if the supplied `dstImmutables.parameters` hash does not match the expected commitment from the corresponding source escrow.

### Proof of Concept
1. Resolver/Taker calls `LimitOrderProtocol.fillOrderArgs`, triggering `_postInteraction`, which computes and emits `protocolFeeAmount = X`, `integratorFeeAmount = Y` in `SrcEscrowCreated`'s `immutablesComplement.parameters`.
2. Instead of using those exact values, the same (or any) caller calls `EscrowFactory.createDstEscrow(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.parameters` encoding `protocolFeeAmount = 0`, `integratorFeeAmount = 0`.
3. `createDstEscrow` deploys the clone with these attacker-chosen values — no check compares them to the source commitment (`contracts/BaseEscrowFactory.sol:165-185`).
4. When the maker withdraws via `EscrowDst.withdraw`, `_withdraw` computes `amount = immutables.amount - 0 - 0`, sending the full amount to the maker and zero to protocol/integrator fee recipients (`contracts/EscrowDst.sol:84-93`), permanently losing the fee revenue that should have been collected.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    function hash(IBaseEscrow.Immutables calldata immutables) internal pure returns(bytes32 ret) {
        // Compute the EIP-712 hash for the immutables struct
        bytes calldata parameters = immutables.parameters;
        assembly ("memory-safe") {
            let ptr := mload(0x40)

            // Copy immutables.parameters to memory and compute its hash
            calldatacopy(ptr, parameters.offset, parameters.length)
            let parametersHash := keccak256(ptr, parameters.length)

            // Copy the immutables struct to memory, patch `parameters` and compute its hash
            calldatacopy(ptr, immutables, IMMUTABLES_SIZE)
            mstore(add(ptr, IMMUTABLES_LAST_WORD), parametersHash)
            ret := keccak256(ptr, IMMUTABLES_SIZE)
        }
    }
