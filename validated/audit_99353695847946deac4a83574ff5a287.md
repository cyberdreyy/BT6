### Title
`JOB_OBJECT_LIMIT_BREAKAWAY_OK` lets a CI-spawned Windows child escape the job object and survive `ForceKill`/cancellation - (File: `helpers/process/job_windows.go`)

### Summary
`CreateJobObject` explicitly sets `windows.JOB_OBJECT_LIMIT_BREAKAWAY_OK` in addition to `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Any child process the job script starts with the Win32 `CREATE_BREAKAWAY_FROM_JOB` creation flag is never a member of the job, so neither the normal `closeJobObject()` (kill-on-close) path nor the `ForceKill`/`taskkill /T` path is guaranteed to reach it once the parent process has exited, letting it outlive the CI job's configured lifetime.

### Finding Description
`CreateJobObject` (`helpers/process/job_windows.go:86-108`) builds the job's `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` with: [1](#0-0) 
`JOB_OBJECT_LIMIT_BREAKAWAY_OK` is a Win32 flag that permits any process created as a child of a job member to specify `CREATE_BREAKAWAY_FROM_JOB` and thereby never become a member of the job at all. This behavior is only active when `FF_USE_WINDOWS_JOB_OBJECT` is enabled, wired through the shell and custom executors: [2](#0-1) [3](#0-2) 

Normal termination paths rely on job membership:
- `osCmd.Wait()` calls `closeJobObject()`, which closes the job handle to trigger `KILL_ON_JOB_CLOSE` for remaining members: [4](#0-3) 
- `windowsKiller.ForceKill()` runs `taskkill /F /T /PID <pid>` on the wrapped top-level process, then calls `closeJobObject()`: [5](#0-4) 

`taskkill /T` walks the OS-recorded parent-PID chain rooted at the wrapped process's PID, not job membership, so it can still catch a breakaway grandchild while its direct parent (the CI job's own process, e.g. a shell) is still alive. However, if the breakaway process's parent has already exited (e.g. the job script spawns a detached breakaway process and then finishes normally, or the CI's shell process itself has terminated before `ForceKill`/`closeJobObject` runs), the breakaway process is orphaned from the tracked tree: it is not a job member (so job-handle-close does nothing), and `taskkill /T <old pid>` has nothing to walk since that PID no longer exists. The process then keeps running under the CI job's own OS identity/token indefinitely, decoupled from the job scope the runner believed it fully controlled.

An unprivileged pipeline author fully controls the job script content (shell/custom executor), so they can trivially invoke a small compiled helper, PowerShell `Add-Type` P/Invoke snippet, or a native tool (e.g. `runas`/WMI-style creation, or a purpose-built binary using `CreateProcess` with `CREATE_BREAKAWAY_FROM_JOB`) to spawn a detached long-lived process before the job's script exits. Because `JOB_OBJECT_LIMIT_BREAKAWAY_OK` is unconditionally set for every job-object-wrapped command, there is no configuration or runtime check that could block this — the flag universally allows breakaway for any job-scoped command.

### Impact Explanation
A CI job can leave a detached process running on the runner's Windows host beyond the job's cancellation, timeout, or completion — the exact invariant this feature (`FF_USE_WINDOWS_JOB_OBJECT`) was introduced to guarantee ("all runner subprocesses are terminated"/"no stale CI jobs linger"). The detached process retains whatever OS-level identity/permissions the job process had, and continues consuming host resources or holding open file/network handles after the runner and GitLab believe the job has been terminated — a persistence/scope-escape from the job's enforced lifetime, matching the "surviving cancellation" impact described in the question. It does not grant elevated privileges beyond what the job already had; the impact is specifically the survival of the job-scoped process beyond its configured lifetime/kill scope.

### Likelihood Explanation
- Precondition: `FF_USE_WINDOWS_JOB_OBJECT` must be enabled (default `false`) and the executor must be shell or custom on Windows. [6](#0-5) 
- The attacker only needs the ability to run arbitrary script content in the job, which any pipeline author has.
- Reaching the breakaway API requires spawning a process with the `CREATE_BREAKAWAY_FROM_JOB` flag, which typically requires either a compiled binary using `CreateProcess` directly (via P/Invoke from PowerShell, a small pre-built EXE checked into the repo, or a tool that already uses this flag) — feasible but not a one-liner in default shells, making exploitation straightforward for a moderately capable pipeline author but not accidental.
- Repeatable: deterministic given the explicit and unconditional `JOB_OBJECT_LIMIT_BREAKAWAY_OK` flag in `CreateJobObject`.

### Recommendation
Remove `windows.JOB_OBJECT_LIMIT_BREAKAWAY_OK` from the job's `LimitFlags` in `CreateJobObject` (`helpers/process/job_windows.go:92-97`) so that child processes cannot opt out of job containment; only `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (and ideally `JOB_OBJECT_LIMIT_ACTIVE_PROCESS` limits or `JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION` as needed) should be set, ensuring `CREATE_BREAKAWAY_FROM_JOB` requests from job-scoped children fail, keeping every descendant bound to the job for the entire job lifetime.

### Proof of Concept
Go integration test in `helpers/process` (Windows-only, build tag `windows`):
```go
func TestJobObject_BreakawayChildSurvivesForceKill(t *testing.T) {
    cmdOpts := CommandOptions{
        UseWindowsJobObject: true,
        Logger:              new(MockLogger), // stub
    }
    // parentScript.exe: on start, spawns childBreakaway.exe with
    // CREATE_BREAKAWAY_FROM_JOB via syscall.CreateProcess, then sleeps.
    c := NewOSCmd("parentScript.exe", nil, cmdOpts)
    require.NoError(t, c.Start())

    // give time for parent to spawn the breakaway child and record its PID
    // (test harness has parentScript.exe write child PID to a temp file)
    time.Sleep(500 * time.Millisecond)
    childPID := readChildPIDFromFile(t)

    k := newKiller(logger, c)
    k.ForceKill() // simulates runner cancellation / job timeout

    _ = c.Wait()

    // Assert breakaway child is still alive after ForceKill + job handle close
    proc, err := os.FindProcess(childPID)
    require.NoError(t, err)
    assert.True(t, isProcessAlive(proc), "breakaway child should have been killed but is still running")
}
```
Expected (current, vulnerable) result: the assertion fails as written — i.e., `isProcessAlive(proc)` returns `true`, proving the breakaway child survives `ForceKill` and `closeJobObject`. After removing `JOB_OBJECT_LIMIT_BREAKAWAY_OK`, `CreateProcess` with `CREATE_BREAKAWAY_FROM_JOB` in `childBreakaway.exe`'s creation would fail/be ignored, keeping the child in the job and terminated by `KILL_ON_JOB_CLOSE`, making the assertion pass.

	if pk.cmd.Process() == nil {
		return

	err := taskKill(pk.cmd.Process().Pid)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
