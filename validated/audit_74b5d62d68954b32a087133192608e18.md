### Title
External-Initiator credential misuse for cross-job run triggering via blanket `UserRoleRun` assignment - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` grants every valid EI accesskey/secret holder a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` without binding that role to the specific `ExternalInitiator`/job that owns the credential. [1](#0-0)  However, the practical blast radius is narrower than "any run-role endpoint" because `AuthenticateExternalInitiator` is only wired into a single, distinct route group (`userOrEI`) exposing just `GET /v2/ping` and `POST /v2/jobs/:ID/runs`; all other `RequiresRunRole` endpoints (`/replay_from_block/:number`, `/find_lca`, `/lp_skip_to_block`, `/execute_capability`) live in the separate `authv2` group which only accepts `AuthenticateByToken`/`AuthenticateBySession`. [2](#0-1) [3](#0-2) 

### Finding Description
`AuthenticateExternalInitiator` (core/web/auth/auth.go:119-151) authenticates the EI accesskey/secret against the `external_initiators` table, then unconditionally sets `SessionUserKey` to a `UserRoleRun` user, with no association to which job(s) that EI is permitted to trigger. [1](#0-0)  The EI identity itself is separately stored in `SessionExternalInitiatorKey` and retrievable via `GetAuthenticatedExternalInitiator`, but this binding is never consulted anywhere it matters.

The only real attack surface reachable with this role is `PipelineRunsController.Create`, mounted at `POST /v2/jobs/:ID/runs` under the `userOrEI` group with `auth.RequiresRunRole`. [4](#0-3)  Inside `Create`, the handler checks `isUser, _ := auth.GetAuthenticatedUser(c)` to decide whether to allow running arbitrary integer job IDs — but `GetAuthenticatedUser` simply reads `SessionUserKey`, which is set identically by `AuthenticateByToken`, `AuthenticateBySession`, AND `AuthenticateExternalInitiator`. [5](#0-4)  The comment "only users are allowed to run jobs using int IDs - EIs not allowed" is factually incorrect for the current code: an EI-authenticated request also satisfies `isUser == true`, and the handler then calls `prc.App.RunJobV2(ctx, jobID, nil)` for whatever integer job ID was supplied in the URL, with **no check that the job's `ExternalInitiatorWebhookSpecs` includes the EI identified via `GetAuthenticatedExternalInitiator(c)`**. [6](#0-5) 

So, an attacker holding one valid EI accesskey/secret pair provisioned for job A can send `POST /v2/jobs/<jobB_ID>/runs` with the two EI headers, pass `RequiresRunRole`, and trigger `RunJobV2` for job B — a job unrelated to their EI credential.

Caveat/limitation: `RunJobV2` on `ChainlinkApplication` explicitly returns an error on secure/production builds (`if build.IsProd() { return 0, errors.New("manual job runs not supported on secure builds") }`), and is documented as "Only used for local testing, not supported by the UI." [7](#0-6)  This significantly limits real-world exploitability on production deployments, though the authorization gap in the HTTP layer itself is real and the stale comment/broken `isUser` check remains a genuine logic defect regardless of the build-mode guard.

### Impact Explanation
On non-production/dev builds (or any deployment where `build.IsProd()` is false), an EI credential scoped to trigger one job can be used to trigger execution of an arbitrary job by numeric ID, running its pipeline (which may include ETH transactions, bridge calls, or other side effects) without the resource-owner binding intended by scoping EI credentials per bridge/job. This is a role/authorization-scope-bypass class issue — the role granted (`UserRoleRun`) is not narrowed to the specific external initiator, defeating the principle of least privilege for EI credentials, though the impact is currently gated by the `build.IsProd()` check in `RunJobV2`.

### Likelihood Explanation
Precondition: attacker holds one valid, unrevoked EI accesskey/secret pair (e.g., legitimately provisioned to trigger their own webhook job). No admin/host access needed. Exploitation requires only a single HTTP POST with the EI headers to `/v2/jobs/:ID/runs` targeting a different job's numeric ID. Feasibility is fully gated by the `build.IsProd()` check in `RunJobV2`; in a secure/production build the request fails at that layer regardless of the HTTP-level scope defect.

### Recommendation
1. In `PipelineRunsController.Create`, do not conflate "authenticated user" with "authenticated EI." Distinguish EI-originated requests via `auth.GetAuthenticatedExternalInitiator(c)` and reject them outright for the generic `/jobs/:ID/runs` path, or verify that the target job's `WebhookSpec.ExternalInitiatorWebhookSpecs` contains the calling EI's ID before invoking `RunJobV2`.
2. Fix/remove the misleading `isUser` check and comment, since `GetAuthenticatedUser` returns true even for EI-authenticated sessions.
3. Longer-term, `AuthenticateExternalInitiator` should attach a job/bridge-scoped identity/claim rather than a blanket `UserRoleRun`, so any future run-role route additions do not silently inherit this same unscoped trust.

### Proof of Concept
Handler-level integration test plan (Go, using `httptest` + gin, mirroring existing tests in `core/web/pipeline_runs_controller_test.go` and `core/services/job/runner_integration_test.go`):
1. Start app with `JobPipeline.ExternalInitiatorsEnabled = true` and a non-prod build tag (or stub `build.IsProd()` to false for test).
2. Create External Initiator A via `POST /v2/external_initiators` (as an authenticated user), capturing `AccessKey`/`Secret`.
3. Create Job A (webhook job bound to EI A) and Job B (any other job type, e.g. `offchainreporting` or another webhook bound to a different EI/no EI).
4. Send `POST /v2/jobs/<JobB.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI A's credentials (no session/API token).
5. Assert: expected secure behavior is `401/403` (rejected — EI A is not bound to Job B). Actual current behavior (if `build.IsProd()` is false in test binary): request succeeds with `200 OK` and a `pipelineRun` resource for Job B, demonstrating cross-job impersonation via `isUser` misclassification in `PipelineRunsController.Create`.
6. Add assertion confirming `GetAuthenticatedExternalInitiator(c).ID != Job B's bound EI ID` yet the run still executed, proving the missing binding check.
