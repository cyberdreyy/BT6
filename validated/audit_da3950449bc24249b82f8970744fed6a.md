### Title
Anyone can front-run a grantor's `create` call and permanently squat a victim's deterministic lockup address with attacker-chosen release terms - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the new lockup's account id **solely** from `sha256(owner_account_id)` and accepts `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration` and `whitelist_account_id` from **whoever calls it**, with no check that the caller is the foundation or grantor. Because the target account id does not depend on those parameters, an unprivileged attacker can call `create` first for a victim's `owner_account_id` with attacker-chosen schedule/whitelist parameters, permanently occupying that deterministic address before the legitimate grantor's transaction lands.

### Finding Description
The broken binding: the caller of `create` is implicitly assumed to be the grantor/foundation, i.e. `predecessor_account_id() == foundation_account_id` should hold before schedule parameters are trusted. In the actual code no such check exists: [1](#0-0) 

`create` only requires `env::attached_deposit() >= MIN_ATTACHED_BALANCE`; there is no `assert_called_by_foundation`-style guard on the predecessor. The resulting lockup account id is computed as:

```
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
```

This is a pure function of `owner_account_id` and the factory account — it is completely independent of `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and `whitelist_account_id`. All of those attacker-controlled fields are serialized directly into `LockupArgs` and passed to the newly created contract's `new` constructor: [2](#0-1) 

Since NEAR's `create_account()` fails if the account already exists, whoever's `create` transaction is included first wins the deterministic address. An attacker who front-runs a foundation/grantor's `create(owner_account_id=victim, ...)` transaction (mempool visibility, or simply calling first) with the same `owner_account_id` but attacker-chosen `release_duration` (e.g. 0, i.e. immediate release), `vesting_schedule` (e.g. none/already elapsed), and `whitelist_account_id` (pointed at an attacker-deployed "whitelist" contract that will approve any attacker-controlled staking pool as legitimate) will have their lockup created and the deterministic account permanently occupied.

When the legitimate grantor's transaction subsequently executes for the same `owner_account_id`, `create_account()` fails (account already exists), the whole promise batch fails, and `on_lockup_create` simply refunds the attached deposit to the original predecessor: [3](#0-2) 

No error is raised to indicate the address was squatted; the grant is simply never created at the intended address. The account that now exists at that address is fully attacker-parameterized: its `release_duration`/`vesting_schedule` may release funds far earlier than intended, and its `staking_pool_whitelist_account_id` can point to an attacker-controlled whitelist contract that will approve attacker-controlled staking pools as "whitelisted." Any party (the grantor, an integrator, or later automation) who subsequently sends the real grant's NEAR to this pre-existing address — trusting it as the canonical lockup for that owner — has their funds subjected to attacker-chosen release/whitelist rules, and the victim owner can be steered (via the poisoned whitelist) into staking with an attacker-controlled pool contract that the protocol otherwise treats as vetted.

None of the existing guards (`assert_self`, `is_promise_success`) address this because they only protect the callback's own logic, not the missing caller-authorization check on `create` itself.

### Impact Explanation
This lets an unpriviledged attacker deploy, at the exact deterministic lockup address that a grantor/foundation will use for a specific `owner_account_id`, a contract with:
- a `release_duration`/`vesting_schedule` that unlocks funds on an attacker-chosen timeline (not the grant's intended schedule), and
- a `staking_pool_whitelist_account_id` pointing to an attacker-controlled contract that will approve attacker-controlled staking pools as legitimate.

This matches "an account whitelisted or a lockup deployed with parameters its rightful creator never chose," which is listed as Critical impact. Because the malicious contract also blocks the legitimate lockup from ever being created at that address (the account name is permanently taken), the attack is repeatable against any target `owner_account_id` for a fixed cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) per victim, and the blast radius scales to every future grant recipient whose lockup has not yet been created.

### Likelihood Explanation
The attacker needs only an ordinary account, `MIN_ATTACHED_BALANCE` (~3.5 NEAR), and knowledge/prediction of a target `owner_account_id` that the foundation intends to grant to (these are typically public/predictable, e.g. known team/investor accounts, or observable via mempool front-running of the foundation's own `create` transaction). No special privilege, key, or foundation/owner/multisig role is required, matching the "unprivileged attacker" threat model in scope.

### Recommendation
Restrict `create` to only be callable by the trusted grantor (`assert_eq!(env::predecessor_account_id(), self.foundation_account_id)`), or otherwise bind the deterministic lockup account id to more than just `owner_account_id` (e.g., include a grantor-supplied nonce/salt or require the address to be reserved beforehand), so schedule parameters cannot be raced in by an unrelated third party.

### Proof of Concept
```rust
// cargo test in lockup-factory/src/lib.rs tests module
#[test]
fn test_frontrun_create_squats_victim_lockup() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker (not foundation) calls create() first for victim's owner_account_id
    // with malicious release_duration = 0 and a whitelist account the attacker controls.
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    let malicious_release: WrappedDuration = 0.into();
    contract.create(
        account_tokens_owner(), // victim's intended owner_account_id
        LOCKUP_DURATION.into(),
        None,
        None,
        Some(malicious_release),
        Some(ValidAccountId::try_from("attacker-whitelist.near").unwrap()),
    );
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    assert!(contract.on_lockup_create(
        lockup_account(), // deterministic address = sha256(owner_account_id)
        ntoy(30).into(),
        String::from("attacker.near"),
    ));

    // Foundation now attempts the legitimate create() with correct release_duration/whitelist
    // for the SAME owner_account_id -> same lockup_account_id, but create_account() fails
    // because the account already exists (simulated as PromiseResult::Failed).
    context.predecessor_account_id = String::from(foundation_account_id());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(),
        LOCKUP_DURATION.into(),
        None,
        None,
        Some(CORRECT_RELEASE_DURATION.into()),
        None,
    );
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let result = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        foundation_account_id(),
    );

    // Assert the binding is broken: legitimate creation failed (account squatted),
    // while attacker's malicious parameters (release_duration=0, attacker whitelist)
    // are the ones live at `lockup_account()`.
    assert_eq!(result, false, "legitimate grantor's create must fail: address already squatted");
    // (In a full near-workspaces integration test, additionally assert that the deployed
    // contract's `release_duration`/`vesting_schedule`/`staking_pool_whitelist_account_id`
    // equal the attacker's values, not the foundation's intended values.)
}
```

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
