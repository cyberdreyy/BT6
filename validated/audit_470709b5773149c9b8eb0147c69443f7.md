### Title
Stale confirmations from deleted members count toward multisig execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`multisig2` (and similarly `multisig`) counts a request as approved when `confirmations.len() + 1 >= num_confirmations`, but confirmations recorded earlier from members who are later removed via a `DeleteMember` request are never purged from in-flight requests' `confirmations` set. This lets a request execute even though the number of *live* members who actually approved it is below the configured threshold.

### Finding Description
`add_request`/`confirm` store approvals in `self.confirmations: LookupMap<RequestId, HashSet<String>>` keyed by request, populated by `member.to_string()` [1](#0-0) . `confirm()` only validates that the *current caller* is a member (`current_member()` in `assert_valid_request`), but never re-validates the members already present in the stored `confirmations` set for that request [2](#0-1) . When a `DeleteMember` action executes (via `execute_request`), it removes the member from `self.members`, but there is no sweep over `self.requests`/`self.confirmations` to strip that member's stale approvals from other pending requests [3](#0-2) . Contrast this with `DeleteKey` handling in `multisig/src/lib.rs`, which explicitly purges *all requests signed by* the deleted key (`request_ids` filtered by `r.signer_pk == pk`, then removed) [4](#0-3)  — but this only clears requests *originated* by that key, not confirmations *added* by that key to other members' requests. `multisig2`'s `AddMember`/`DeleteMember` action path has no equivalent cleanup at all for confirmations stored in the `confirmations` map.

This is the same bug class as the `Manager.addToken` finding: a mapping (`vaults[_token]`/`tokens[_vault]` there, `confirmations` here) is mutated without any check against the current ground truth (whether the token is already bound to another vault; whether the confirming account is still a member), letting stale/duplicate state count toward a security-critical decision (double-counted vault value there; below-threshold execution here).

### Impact Explanation
The binding that should hold is: `count(confirmations for request R that are members at time of confirm(R) triggering execution) == count(live members who approved R)`. Because stale confirmations from removed members are never purged, an attacker/insider scenario is: member A confirms request R (leaving it 1 confirmation short of `num_confirmations`), a separate multisig request removes A from `members` (`DeleteMember`), and then any other member C confirms R. `confirmations.len() + 1 >= num_confirmations` becomes true and `execute_request` fires, even though A's approval is no longer valid — the request is executed with fewer than `num_confirmations` currently-live approving members. This is a violation of the multisig's core custody guarantee (funds/actions gated behind k-of-n live signer approval), matching the stated Critical impact "a multisig request executed below threshold."

### Likelihood Explanation
Requires only actions available to normal, unprivileged multisig members through the documented API (`add_request`, `confirm`, `AddMember`/`DeleteMember` actions) — no foundation privilege, no redeploy, no malicious validator. It requires membership changes to occur while other requests are pending, which is a realistic operational sequence for any multisig doing routine key rotation.

### Recommendation
When executing `DeleteMember` (and `AddMember`, to avoid unrelated inflation of member count semantics), sweep all pending `requests`/`confirmations` and remove confirmations attributed to the deleted member, mirroring the `DeleteKey` cleanup already present in `multisig/src/lib.rs`. Alternatively, at `confirm()` time, revalidate every entry in the stored `confirmations` set against the current `members` set before counting toward the threshold, discarding stale entries.

### Proof of Concept
1. Deploy `multisig2` with 3 members `{A, B, C}` and `num_confirmations = 3`.
2. A calls `add_request_and_confirm(request_transfer_funds)` → `confirmations = {A}`.
3. Separately, members confirm and execute a `DeleteMember{member: A}` request (requires 3-of-3 confirmations from current members, achievable by A, B, C acting on that specific request before A is removed) — now `members = {B, C}`.
4. B calls `confirm(request_transfer_funds)` → `confirmations = {A, B}`, size 2, still < 3, no execution yet.
5. C calls `confirm(request_transfer_funds)` → `confirmations.len() + 1 = 3 >= num_confirmations (3)` → `execute_request` fires and transfers funds, even though only B and C are live members who validly approved (2-of-2 effectively, and A's stale approval was counted as one of the 3 required confirmations despite A no longer being a member).

        let mut promise = Promise::new(request.receiver_id.clone());
        let receiver_id = request.receiver_id.clone();
        let num_actions = request.actions.len();

                }

                    self.assert_self_request(receiver_id.clone());

                    self.delete_member(promise, member)

                    permission,

                    method_name,
                    args.into(),
                    deposit.into(),
                    Gas::from(gas.0),

                MultiSigRequestAction::SetNumConfirmations { num_confirmations } => {

                    self.assert_one_action_only(receiver_id, num_actions);
                    self.active_requests_limit = active_requests_limit;
                    return PromiseOrValue::Value(true);
                }
            };
        }

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
