Confirmed: `multisig-factory/src/lib.rs` contains no callback, no `is_promise_success` check, and no refund logic anywhere in the crate, unlike its sibling factories.### Title
`MultisigFactory::create` has no callback to verify deployment success, permanently freezing attached NEAR on failed multisig creation - (File: multisig-factory/src/lib.rs)

### Summary
The external report's core concern is that a fixed-address deployment transaction (Nick's method) has no guaranteed fallback when the underlying deployment fails, and any value sent along with it can be stranded. `MultisigFactory::create` in this repository has exactly that structural gap: it fires a single-shot `Promise` batch (`create_account` → `deploy_contract` → `transfer` → `function_call`) with the user's `attached_deposit`, but — unlike its sibling factories — never chains a `.then()` callback to check whether the batch succeeded, and therefore never refunds the caller if it fails.

### Finding Description
`create` builds the sub-account name from a caller-supplied `name` parameter and issues a promise batch carrying the full `env::attached_deposit()`: [1](#0-0) 

Compare this to `LockupFactory::create` and `StakingPoolFactory::create_staking_pool`, which perform the identical create-account/deploy/transfer/function_call sequence but always chain `ext_self::on_lockup_create` / `ext_self::on_staking_pool_create` as a `.then()` callback. Those callbacks call `is_promise_success()` and, on failure, explicitly `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` to return the funds to the caller: [2](#0-1) [3](#0-2) 

`MultisigFactory::create` has no equivalent. A `grep` across the entire `multisig-factory` crate found no `on_create`, no `callback`, and no `is_promise_success` reference at all — the crate consists solely of the 50-line `lib.rs` shown above. If the deployment receipt fails for any reason — the sub-account `name.factory` already exists (an unprivileged attacker can pre-create/squat any target `name`), the `name` is malformed, the attached gas is insufficient for the `new` call inside `multisig2`, or the `new` constructor itself panics on bad `members`/`num_confirmations` input — the attached NEAR is never routed back to `env::predecessor_account_id()`. It is retained on the `MultisigFactory` contract's own balance with no code path to return it to the depositor.

This is the same root-cause class flagged in the report: a deployment mechanism with no verified-success fallback for returning value when the deployment doesn't land as intended. The report's fix pattern (documented fallback / explicit handling of failure) is precisely what `lockup-factory` and `staking-pool-factory` already implement and what `multisig-factory` is missing.

### Impact Explanation
Any depositor's attached NEAR (the `README.md` example uses 50 NEAR) becomes permanently frozen in the `MultisigFactory` contract if the sub-account creation/deploy/init fails. Because there is no refund path and no way for the depositor to reclaim the deposit through the factory's public interface, this is a solvency-freezing bug: value debited from the caller is never delivered to either the intended multisig account or back to the caller. This matches the "Critical – funds permanently frozen" impact category. An unprivileged attacker can also deliberately front-run/squat a target `name` sub-account to force a victim's `create` call to fail, permanently freezing the victim's attached deposit inside the factory with no recourse.

### Likelihood Explanation
High. No privileged role, owner action, or malicious validator is required. Triggering the bug only requires either (a) a legitimate collision/failure (e.g., someone reusing a `name` already created by anyone else, since `name` is unrestricted user input with no uniqueness check unlike `staking-pool-factory`'s `staking_pool_account_ids.insert` guard), or (b) an attacker pre-creating the target account name before a victim's transaction executes. This is directly analogous to, and simpler to trigger than, the deployment-failure scenarios discussed in the external report.

### Recommendation
Add a `.then()` callback (`on_create`) to `MultisigFactory::create`, mirroring `LockupFactory::on_lockup_create` / `StakingPoolFactory::on_staking_pool_create`: check `is_promise_success()` and, on failure, `Promise::new(predecessor_account_id).transfer(attached_deposit)` to return the caller's funds. Additionally, consider tracking created account IDs (as `staking-pool-factory` does) to reject `name` collisions before spending gas on a doomed deployment.

### Proof of Concept
1. Attacker observes/predicts that a user `alice` intends to call `MultisigFactory::create({"name": "team", "members": [...], "num_confirmations": 2})` with 50 NEAR attached.
2. Attacker front-runs by calling `create` (or directly `create_account` via any means) for `team.<factory_account>` first, or simply any prior caller already used `name = "team"`.
3. Alice's transaction executes: `Promise::new("team.<factory_account>").create_account()` fails because the account already exists; the chained `deploy_contract`/`transfer`/`function_call` in the same receipt also fail as part of the same batch.
4. Because `create()` (`multisig-factory/src/lib.rs:28-49`) has no `.then()` callback, Alice's 50 NEAR remains on the `MultisigFactory` contract account — it is not returned to Alice and no multisig contract was created for her.
5. Alice has no method on `MultisigFactory` to reclaim the deposit; the funds are permanently frozen.

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(

                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids

                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
