I found a promising use-after-free analog: per-epoch receipt entries that survive a claim and get re-read after default finalization. Let me verify the remaining claim paths and fund-transfer helpers.### Title
Stale per-epoch instant-withdraw receipt is re-charged against default recovery reserve after the receipt was already claimed (use-after-free) - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` pays an instant withdrawal and zeroes the aggregate `instantWithdrawsRequests[_user]`, but never clears `instantWithdrawsRequestsByEpoch[_user][requestEpoch]`. If the borrower later defaults and `finalizeDefaultRecovery` runs while `epochNumber` still equals that request epoch, `_claimDefaultedInstantWithdrawRequest` resurrects the already-claimed basis from the stale per-epoch entry and pays it again out of `defaultRecoveryReserve`. The attacker only needs to make a second instant request in the same epoch so the aggregate subtraction does not underflow. This is a textbook use-after-free analog: the receipt is "freed" (paid, aggregate counter zeroed) but the per-epoch record is left live and is re-read by the post-default claim path.

### Finding Description
In `requestInstantWithdraw`, the strategy records both an aggregate and a per-epoch basis [1](#0-0) . On a normal claim, only the aggregate is cleared — `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are left untouched [2](#0-1) .

Unlike normal withdraws, the instant claim has no epoch-maturity gate (`epochNumber > lastWithdrawRequest`), so a user can be fully paid within the same `epochNumber` in which the request was recorded (funds arrive via `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` but not the per-epoch maps) [3](#0-2) .

On default finalization, `defaultRecoveryEpoch = epochNumber` and `defaultInstantWithdrawsFinalized` is true whenever `pendingInstantWithdraws != 0` — i.e., whenever any *other* user's instant receipt in the same epoch is still unfunded [4](#0-3) . The default claim path then reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` with no "was this already paid" check [5](#0-4) .

### Impact Explanation
Direct theft from the isolated `defaultRecoveryReserve`. The reserve is sized at finalization as `reserveAmount / totalBasis` against genuinely outstanding claims [6](#0-5) ; every `_transferDefaultRecovery` call consumes it [7](#0-6) . An attacker who already received 100% of an instant withdrawal claims `staleBasis * defaultRecoveryPrice` a second time, so legitimate defaulted-epoch claimants (the unfunded instant user, pending normal receipts, and active AA/BB holders claiming through the CDO) are shorted by that amount — the reserve becomes insolvent and later claims revert or pay less than the finalized recovery ratio. Loss is quantified: up to the attacker's first instant-withdraw amount times the recovery price, bounded only by the reserve.

### Likelihood Explanation
All attacker steps are unprivileged user actions: deposit (KYC), `requestInstantWithdraw`, `claimInstantWithdrawRequest` after funding, a second `requestInstantWithdraw`, then `claimInstantWithdrawRequest` again after `finalizeDefaultRecovery`. The honest-actor events required are common sequencing: (a) the borrower funds only part of the epoch's instant queue before defaulting, keeping `pendingInstantWithdraws != 0` so `defaultInstantWithdrawsFinalized` is set; (b) default is declared before the next `stopEpoch`/`deposit` bumps `epochNumber` (epochNumber increments only inside `deposit` during `stopEpoch` [8](#0-7) ). `requestInstantWithdraw` has no guard against a pre-existing receipt balance, so sizing the second request ≥ the stale basis avoids the underflow at `instantWithdrawsRequests[_user] -= claimBasis`, and the receipt tokens burned at `_burn(_user, claimBasis)` were freshly minted to the attacker by that second request [9](#0-8) . No existing guard (skim, flags, epoch gating) covers this path — the normal-withdraw analog is protected by the epoch-wait check, but instant claims bypass it by design.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch records when consuming them: iterate/set `instantWithdrawsRequestsByEpoch[_user][requestEpoch] = 0` (and decrement `instantWithdrawClaimsByEpoch[requestEpoch]` accordingly) for every funded instant claim, or track a per-user "claimed basis" that `_claimDefaultedInstantWithdrawRequest` subtracts from the raw epoch basis. At minimum, `_claimDefaultedInstantWithdrawRequest` should cap `claimBasis` at the still-unclaimed portion rather than trusting the per-epoch entry to represent a live claim.

### Proof of Concept
Foundry fork PoC sketch (see `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_stopCurrentEpoch`):

```solidity
// Epoch N running -> stopEpoch -> buffer of epoch N (epochNumber == N)
// 1. Attacker A (KYC'd LP) deposits, then:
cdoEpoch.requestInstantWithdraw(attackerShares, AAtranche);   // instantWithdrawsRequestsByEpoch[A][N] = X
// 2. Victim B also requests instant withdraw of Y (Y stays unfunded).
// 3. CDO collects only A's share: collectInstantWithdrawFunds(X); pendingInstantWithdraws = Y.
// 4. A claims: instantWithdrawsRequests[A] = 0, A receives X at par.
//    BUG: instantWithdrawsRequestsByEpoch[A][N] still == X.
// 5. A requests a second instant withdraw of X again (aggregate = X, per-epoch adds).
// 6. Borrower defaults during epoch N; manager/owner run default + finalizeDefaultRecovery
//    while epochNumber == N  => defaultRecoveryEpoch = N, defaultInstantWithdrawsFinalized = true.
// 7. A calls claimInstantWithdrawRequest:
//      _claimDefaultedInstantWithdrawRequest reads claimBasis = X (stale),
//      instantWithdrawsRequests[A] (X) -= X -> 0, _burn(A, X) burns A's new receipt,
//      _transferDefaultRecovery(A, X * defaultRecoveryPrice / 1e18) drains reserve.
// Result: A paid X at par + X*price from reserve for ONE funded receipt;
// reserve is short by that amount -> B's finalized claim cannot be fully paid.
```

Key assertion: `underlying.balanceOf(A)` after step 7 exceeds `X (first claim) + remaining`, and `defaultRecoveryReserve` is under-consumed for the remaining honest claimants (or B's later claim reverts/underpays). Uncertainty to verify during PoC: whether the CDO's default flow calls `finalizeDefaultRecovery` before `epochNumber` advances — `defaultRecoveryEpoch = epochNumber` at line 693 suggests it must be invoked in the defaulted epoch, which is exactly the window the exploit needs.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
