### Title
Password-change flow does not invalidate the current session token, allowing a hijacked/stolen session to survive password reset - ([File: core/web/user_controller.go])

### Summary
`UserController.UpdatePassword` calls `updateUserPassword`, which invokes `getCurrentSessionID(c)` to read the requesting browser's session ID from its cookie and then calls `ClearNonCurrentSessions(ctx, sessionID)`, which deletes every other session for that user but explicitly excludes the session matching `sessionID`. If an attacker has obtained (e.g., via XSS, log leakage, or cookie theft) the exact same session cookie value the victim is currently using, the attacker's replayed request and the victim's own request are indistinguishable — both carry the identical `sessionID`. As a result, the session the attacker is riding on is treated as "current" and is never revoked by the password change, defeating the security purpose of the password-reset-as-incident-response flow. This is not strictly a timing race (no ordering dependency is needed); it's a deterministic consequence of using raw session-ID equality as the sole criterion for "current session."

### Finding Description
`UserController.UpdatePassword` (`core/web/user_controller.go:202-241`) validates the old password and then calls `u.updateUserPassword(c, &user, request.NewPassword)`.

`updateUserPassword` (`core/web/user_controller.go:341-360`) does:
```go
sessionID, err := getCurrentSessionID(c)
...
orm.ClearNonCurrentSessions(ctx, sessionID)
...
orm.SetPassword(ctx, user, newPassword)
```
`getCurrentSessionID` (`core/web/user_controller.go:332-339`) simply reads `webauth.SessionIDKey` out of the gin session cookie attached to the incoming request — it performs no additional binding to device fingerprint, IP, or a freshly rotated token.

`ClearNonCurrentSessions` in `core/sessions/localauth/orm.go:243-251` runs:
```sql
DELETE FROM sessions WHERE lower(email) = lower($1) AND id != $2
```
using the email looked up from the given `sessionID`. Any session row whose `id` equals the passed `sessionID` is preserved by definition.

Because the cookie's session ID is the literal, un-rotated database session identifier, whichever party (victim or attacker) presents that same cookie value is treated identically as "the current session." If the attacker already holds a copy of that exact cookie (session hijacking via XSS, referrer leakage, shared/compromised terminal, log/proxy exposure, etc.), the attacker's session is structurally the *same* session row as the one the legitimate user is using to submit the password change — `ClearNonCurrentSessions` cannot distinguish "victim's browser" from "attacker's copy of the same cookie" because no session rotation occurs during password change and no other binding factor exists. The password is updated but the compromised session token itself is never invalidated, and the account owner has no way to know that the "current" session that survived the reset is not actually restricted to their own browser.

### Impact Explanation
An attacker who has obtained a valid copy of the victim's session cookie retains full authenticated access to the node's user API after the victim performs a password change intended to lock them out — including sensitive privileged actions gated only by session auth (e.g., API token management, key export flows, job/bridge management depending on role). This matches Chainlink's bounty impact class of "authentication/session bypass leading to retained unauthorized access," since the very purpose of the password-change endpoint (revoke all other access, per the accompanying `audit.PasswordResetSuccess` log entry) is silently defeated for the one session that most needs killing — the compromised one.

### Likelihood Explanation
Requires the attacker to already possess a copy of the victim's raw session cookie value (via XSS, cookie leakage, shared browser/log exposure, etc.) that remains valid (not yet expired via `sessionDuration`/`last_used`). Given that precondition, the failure is fully deterministic — no timing/race precision needed — and is 100% repeatable: any password change performed while the attacker's stolen cookie is unexpired preserves that exact session row.

### Recommendation
On password change, rotate/regenerate the session ID for the legitimate requester (issue a brand-new session record and cookie, migrate `last_used`, and update the `sessions.SessionIDKey` value in the gin session store) instead of reusing the existing `sessionID` as the "current" exemption key. Alternatively/additionally, delete *all* sessions (including current) on password change and force re-authentication, which is the strongest guarantee against any stolen-cookie persistence.

### Proof of Concept
Handler-level integration test plan:
1. Seed a user and create two `sessions` rows with **identical** effective cookie contents is not directly reproducible (IDs are unique per `sessions.NewSession()`), so instead: create session `S` for the user (simulating the victim's browser), then simulate the attacker obtaining a literal copy of the same signed gin-session cookie bytes used by the victim (not a second DB row — the same cookie value).
2. Fire two concurrent HTTP requests to `PATCH /v2/user/password` (or directly call `UserController.UpdatePassword`) both carrying the identical session cookie — one representing the victim's legitimate request, one the attacker's replay.
3. After both requests complete, query the `sessions` table via `orm.Sessions` / `SELECT * FROM sessions WHERE email = ...` and assert that session `S` still exists (it will, per current code) even though the request "intent" was to log out any other holder of that session.
4. Assert (currently failing) that a security-conscious implementation would have rotated the session ID such that the pre-password-change cookie value `S` is no longer valid for `AuthorizedUserWithSession(ctx, S)`, i.e., `AuthorizedUserWithSession` should return `sessions.ErrUserSessionExpired` for the old `S` after a successful password change, demonstrating that reliance on raw session-ID equality in `ClearNonCurrentSessions` fails to protect against a shared/stolen session cookie.

func (u *UserController) updateUserPassword(c *gin.Context, user *clsession.User, newPassword string) error {
	ctx := c.Request.Context()
	sessionID, err := getCurrentSessionID(c)
	if err != nil {
		return err
	}
	orm := u.App.AuthenticationProvider()
	if err := orm.ClearNonCurrentSessions(ctx, sessionID); err != nil {
		u.App.GetLogger().Errorf("failed to clear non current user sessions: %s", err)
		return errors.New("unable to update password")
	}
	if err := orm.SetPassword(ctx, user, newPassword); err != nil {
		if errors.Is(err, clsession.ErrNotSupported) {
			return errUnsupportedForAuth
		}
		u.App.GetLogger().Errorf("failed to update current user password: %s", err)
		return errors.New("unable to update password")
	}
	return nil
}

// ClearNonCurrentSessions removes other sessions for the user tied to sessionID.
func (o *orm) ClearNonCurrentSessions(ctx context.Context, sessionID string) error {
	var email string
	if err := o.ds.GetContext(ctx, &email, "SELECT email FROM sessions WHERE id = $1", sessionID); err != nil {
		return err
	}
	_, err := o.ds.ExecContext(ctx, "DELETE FROM sessions WHERE lower(email) = lower($1) AND id != $2", email, sessionID)
	return err
}
