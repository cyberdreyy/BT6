### Title
Already-claimed instant withdrawals are counted again in default finalization, corrupting the recovery reserve and freezing claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch receipts `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. If the same epoch later defaults, `finalizeDefaultRecovery` re-processes those already-paid receipts as both recovery claim basis and "prefunded" reserve, inflating `defaultRecoveryPrice` above real backing, while the affected user's claim underflows and permanently reverts — the direct analog of LLVM's `!replacements.count(op) && "operation was already replaced"` double-processing assertion.

### Finding Description
The normal instant-claim path (`IdleCreditVault.sol:380-393`) burns and zeroes `instantWithdrawsRequests[_user]` but leaves `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` untouched. The only place these per-epoch entries are decremented is `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:842-856`), which is reachable only after a default.

At default finalization the stale data is consumed twice incorrectly:

1. `defaultPendingClaimBasis` (`IdleCreditVault.sol:644-649`) adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still includes the already-paid amount `X`.
2. `_defaultPrefundedInstantReserve` (`IdleCreditVault.sol:716-723`) computes `instantBasis - pendingInstantWithdraws` and reports `X` as underlying "already held" by the strategy, even though it was transferred out to the claimer.

`finalizeDefaultRecovery` (`IdleCreditVault.sol:661-710`) then computes `recoveryPrice = reserveAmount * 1e18 / totalBasis` with both numerator and denominator corrupted by `X`. Additionally, when the same user later calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` executes `instantWithdrawsRequests[_user] -= claimBasis` where `claimBasis` includes the stale `X`; if the user's current balance is smaller, the subtraction underflows and the claim reverts forever.

### Impact Explanation
- Recovery reserve shortfall: the prefunded component of `defaultRecoveryReserve` includes `X` tokens already paid out, so `defaultRecoveryPrice` is set too high and the last claimants against the reserve (pending receipt holders via `_transferDefaultRecovery`, or AA/BB active LPs via the `defaultBBNav`/forced accounting path) are underpaid or cannot be paid at all — direct insolvency of up to `X` per stale claim.
- Permanent freeze: a user who claimed an instant receipt and opened a smaller one in the same defaulted epoch has `claimBasis > instantWithdrawsRequests[_user]`, so `claimInstantWithdrawRequest` always reverts and their funded receipt is permanently locked.
- No existing guard stops this: nothing clears the per-epoch instant entries on the normal claim path, and `epochNumber` only advances at `stopEpoch`, so a mid-epoch default shares the epoch index of stale entries.

### Likelihood Explanation
Requires a borrower default in the same epoch where at least one instant request was fully funded and claimed while another instant request remained unfunded (`pendingInstantWithdraws != 0` at finalization, enabling `defaultInstantWithdrawsFinalized`). This is a plausible configuration — instant requests are funded from CDO cash at `startEpoch` (`IdleCDOEpochVariant.sol:279-290`), and partial funding is explicitly supported. Attacker needs only a KYC-passed lender wallet making ordinary instant-withdraw requests; the harm falls on other claimants and active LPs.

### Recommendation
In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (or track and clear the appropriate per-epoch entry) and `instantWithdrawClaimsByEpoch[epochNumber]` alongside `instantWithdrawsRequests[_user]`, so already-paid receipts are excluded from `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`. Alternatively, clear the per-epoch entry in `_clearWithdrawClaimForEpoch`-style bookkeeping at claim time.
