### Title
Miner's `StackerDBListener` double-counts a signer's weight into both `total_weight_approved` and `total_weight_rejected` when a signer sends `Rejected` then later `Accepted` for the same block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
In `StackerDBListener::run_loop`'s message handler, the guard used to gate weight-accumulation differs between the `Accepted` and `Rejected` branches. The `Rejected` branch gates on `block.responded_signers.insert(slot_id)` (a single unified "has this signer already responded" set), but the `Accepted` branch gates only on `block.gathered_signatures.contains_key(&slot_id)`. If a signer sends `Rejected` first (recording weight in `total_weight_rejected` and inserting `slot_id` into `responded_signers`) and later sends `Accepted` for the same block hash, the `Accepted` branch does not see `slot_id` in `gathered_signatures` and adds the signer's weight to `total_weight_approved` as well — without removing it from `total_weight_rejected`. The signer's weight is now counted on both sides simultaneously.

### Finding Description
`stacks-node/src/nakamoto_node/stackerdb_listener.rs` maintains a per-block `BlockStatus` with `total_weight_approved`, `total_weight_rejected`, `gathered_signatures`, and a shared `responded_signers` set: [1](#0-0) 

For an `Accepted` message, the code only checks whether the slot already has a stored signature before adding weight: [2](#0-1) 

For a `Rejected` message, the code checks the unified `responded_signers` set before adding weight: [3](#0-2) 

Because `responded_signers.insert(slot_id)` already happened during the earlier `Rejected` processing, and the `Accepted` branch never checks that set (only `gathered_signatures`), a signer that first rejects and later accepts the same block hash gets their weight added to `total_weight_approved` on top of the weight already permanently recorded in `total_weight_rejected`. The per-signer weight is never subtracted from the opposite bucket, so the same weight is simultaneously "aggregated" into both the approval and rejection tallies used by the miner's `SignerCoordinator::get_block_status` loop.

This is directly analogous to the reported class of bug: a value (signer weight) that should be attributed exclusively to one side of a binary outcome is instead applied to both sides, because the code re-uses one side's accounting state (`gathered_signatures`) as the sole gate instead of the shared per-signer response state (`responded_signers`) that the other branch correctly uses.

The docs for this flow describe the intended invariant that acceptances and rejections are tallied against a single 70%/30% split of `total_weight`, with the two outcomes meant to be mutually exclusive once a peer has responded: [4](#0-3) 

Per the same docs, a signer's stance can legitimately be reconsidered after a rejection if the reject reason permits it, so a `Rejected` → `Accepted` sequence for the same block hash from the same signer is a real, reachable path, not a purely theoretical one.

### Impact Explanation
`total_weight_rejected` is used by `SignerCoordinator::get_block_status` (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) to decide when to abandon a block proposal and to determine which failed txids to (permanently) exclude, based on whether rejection weight exceeds the blocking-minority threshold: [5](#0-4) 

Because a signer that ultimately accepted (and validly signed) the block permanently retains its weight in `total_weight_rejected` from its earlier rejection, the miner's coordinator can incorrectly believe the blocking-minority threshold has been crossed for a block that in fact has (or could reach) a valid 70% approval, causing the miner to spuriously abandon a signable block and/or permanently ban a transaction id based on stale rejection weight that no longer reflects that signer's current stance. This is a liveness wedge in the miner/signer coordination path — it can stall block production or cause unwarranted txid exclusion — without requiring a majority of signers, only a single signer legitimately changing its vote.

### Likelihood Explanation
This does not require a majority or malicious collusion — a single signer following the documented "may reconsider a rejection" behavior is sufficient to trigger the double count. It is reachable purely through normal StackerDB gossip message flow (`BlockResponse::Rejected` followed later by `BlockResponse::Accepted` for the same `signer_signature_hash`), which is exactly the kind of single-signer-triggerable, gossip-only path in scope.

### Recommendation
In the `Accepted` branch, gate the weight-accumulation on the same unified `responded_signers` set used by the `Rejected` branch (i.e., check/insert `slot_id` into `responded_signers` before adding to `total_weight_approved`), and treat a stance change consistently — either by disallowing a weight change once a signer has responded, or by explicitly moving the signer's weight from `total_weight_rejected` to `total_weight_approved` (and vice versa) when a later, valid message for the same block hash supersedes the earlier one.

### Proof of Concept
1. Miner proposes block `B` with `signer_signature_hash = H`; `StackerDBListener` tracks `BlockStatus` for `H` with `total_weight_approved = 0`, `total_weight_rejected = 0`, `responded_signers = {}`.
2. Signer `S` (slot `k`, weight `w`) initially rejects `B` for a reconsiderable reason: `BlockResponse::Rejected` is processed at [3](#0-2) , setting `total_weight_rejected = w` and `responded_signers = {k}`.
3. Signer `S` later reconsiders and sends `BlockResponse::Accepted` with a valid signature over `H` for the same block. The handler at [2](#0-1)  checks only `block.gathered_signatures.contains_key(&k)`, which is `false` (never populated by the rejection path), so it adds `w` to `total_weight_approved`, making `total_weight_approved = w` while `total_weight_rejected` remains `w`.
4. Now both `total_weight_approved` and `total_weight_rejected` include `S`'s weight `w` simultaneously; depending on the reward-set weight distribution, this can push `total_weight_rejected` past the blocking-minority threshold in `SignerCoordinator::get_block_status` (`stacks-node/src/nakamoto_node/signer_coordinator.rs` lines 509-540) even though `S`'s current, valid stance is acceptance — causing the miner to abandon the proposal and/or ban txids based on a stale rejection weight that should have been retracted.
