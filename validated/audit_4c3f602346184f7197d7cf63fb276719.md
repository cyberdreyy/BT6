### Title
ERC4626 first-depositor share inflation on `ProgrammableBorrower.onStartEpoch` lets an attacker capture the entire epoch deposit — (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
The Shopware bug is cache poisoning: an attacker-controlled input is written into a shared cache that downstream consumers trust. The analog in idle-tranches is the shared ERC4626 vault whose share price `ProgrammableBorrower` blindly trusts. `onStartEpoch` parks the whole pool balance via `_depositToVault`, which calls `vault.deposit` with no minimum-share check and no sanity check that the vault is non-empty (`setVault` only checks `asset()` and that *this contract* holds no shares). An attacker who seeds an empty configured vault with a dust deposit plus a direct-asset donation inflates the share price so the pool's deposit mints ~0 shares, and the attacker redeems the pool's funds.

### Finding Description
- `setVault` accepts any ERC4626 with the right `asset()`, including a freshly deployed vault with `totalSupply == 0`. It only verifies `vault.balanceOf(address(this)) == 0` (the borrower's own position), not vault-level supply: `ProgrammableBorrower.sol:158-169`.
- `onStartEpoch` deposits the entire on-hand underlying balance: `_depositToVault(underlyingToken.balanceOf(address(this)), 0)` at `ProgrammableBorrower.sol:216`.
- `_depositToVault` issues `vault.deposit(_assetAmount, address(this))` with no min-shares / slippage bound; the minted `shares` are only emitted in an event: `ProgrammableBorrower.sol:378-385`.
- With a standard `totalAssets`/`totalSupply` vault, an attacker deposits 1 wei to mint 1 share, then donates `D` underlying directly to the vault so `1 share ≈ D + 1` assets. When PB deposits `P` (the whole pool), it receives `floor(P / (D+1))` shares — 0 or dust. `epochStartVaultAssets` was snapshotted pre-deposit (`onStartEpoch`, line 214-219), so `_vaultNetInterest()` reports the position as a vault loss, and the attacker, holding ~100% of vault shares, redeems `P + D`.

Broken invariant: fair mint/burn — PB receives shares worth far less than deposited assets, and the loss is then pushed onto tranche holders.

### Impact Explanation
At the next `stopEpoch`, PB holds ~no vault assets and no on-hand cash, so IdleCDO's `transferFrom` pulls nothing and the epoch settles as a loss/default. All LP principal routed through the programmable borrower (up to the full pool TVL) is stolen by the attacker, net of the donation `D`. For `D` chosen just below `P` (e.g. `D = P - 1`), attacker profit ≈ `P - D ≈` nearly the entire deposit.

### Likelihood Explanation
Requirements: the configured vault is empty at first `onStartEpoch` (freshly deployed vault set via `setVault` before any third-party deposits — a realistic configuration sequence for a new facility) and the vault's `convertToShares` uses raw `balanceOf`-style total assets (standard for simple ERC4626 wrappers; MetaMorpho-style vaults with internal accounting mitigate it). The attacker is unprivileged — any vault depositor — satisfying the "user of the programmable borrower's ERC4626 vault" role.

### Recommendation
- In `setVault`, reject vaults with `totalSupply == 0` (or require a minimum existing supply).
- In `_depositToVault`, enforce a slippage bound: compute `previewDeposit(_assetAmount)` (or a minimum expected shares) and revert if minted shares deviate materially, or use `vault.mint(expectedShares, ...)` so any rounding favors PB.
- Optionally seed the vault with a dead-share amount at configuration time.

### Proof of Concept
Foundry test sketch (place under `test/foundry/`, using the repo's mock ERC4626 used by `ProgrammableBorrowerAccountingInvariant.t.sol`):

```solidity
function testVaultInflationCapturesEpochDeposit() external {
    uint256 poolAssets = 1_000_000e18;

    // Attacker seeds the (empty) configured vault: 1 wei deposit + donation
    underlying.mint(attacker, 1 + poolAssets);
    vm.startPrank(attacker);
    underlying.approve(address(vault), type(uint256).max);
    vault.deposit(1, attacker);                       // 1 share
    underlying.transfer(address(vault), poolAssets);  // inflate: 1 share ~= poolAssets
    vm.stopPrank();

    // Fund PB and start epoch -> whole balance deposited, ~0 shares minted
    underlying.mint(address(borrowerContract), poolAssets);
    vm.prank(idleCDO);
    borrowerContract.onStartEpoch(0);

    assertEq(vault.balanceOf(address(borrowerContract)), 0, "PB minted 0 shares");
    assertGt(borrowerContract.vaultLoss(), 0, "loss recognized at epoch level");

    // Attacker redeems everything, capturing the pool deposit
    vm.prank(attacker);
    vault.redeem(1, attacker, attacker);
    assertGt(underlying.balanceOf(attacker), poolAssets, "attacker profited");
}
```

Expected result: PB mints 0 (or dust) shares, `vaultLoss()` ≈ `poolAssets`, the honest `stopEpoch`/`transferFrom` path settles a loss or default, and the attacker exits with the pool's underlying.
