### Title
`BlockRejection`'s EIP-712-style signature omits `reason_code`/`response_data`, letting a relayer forge a signer's rejection metadata - (File: `libsigner/src/v0/messages.rs`)

### Summary
`BlockRejection::hash()` builds the structured-data digest that a signer signs from **only** `self.signer_signature_hash` (plus the domain separator `chain_id`). All the other struct fields that downstream consumers treat as authenticated signer output — `reason`, `reason_code`, and `response_data` (which itself carries `reject_reason`, `failed_txid`, `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`) — are not part of the signed preimage at all. [1](#0-0) 

This is the same defect class as the reported `Permit2OrderLib` bug: the signature's "typestring" (here, the structured-data tuple fed to `structured_data_message_hash`) does not cover every field of the signed struct, so any party who can re-emit the message with the same `signature` bytes and the same `signer_signature_hash` can alter the un-covered fields without invalidating `.verify()`/`.recover_public_key()`.

### Finding Description
`BlockRejection` is defined with 7 semantically meaningful fields, but only one (`signer_signature_hash`) is committed to by the signature: [2](#0-1) 

```rust
pub fn hash(&self) -> Sha256Sum {
    let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
    let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
    structured_data_message_hash(data, domain_tuple)
}
``` [3](#0-2) 

`verify()`/`recover_public_key()` only re-derive this same narrow hash, so a message with the identical `(signer_signature_hash, chain_id, signature)` triple but an arbitrary `reason`, `reason_code`, or `response_data` still verifies successfully against the signer's real public key. [4](#0-3) 

On the node side, `stacks-node/src/nakamoto_node/stackerdb_listener.rs` trusts exactly these un-signed fields once the signature/pubkey check passes:
- It matches `failed_txid` against `reason_code` (`RejectCode::ValidationFailed(BadTransaction|ProblematicTransaction)`) to accumulate per-txid `total_weight`/`problematic_weight`, used to decide whether a transaction is flagged "problematic." [5](#0-4) 
- It feeds `response_data.tenure_extend_timestamp` / `tenure_extend_read_count_timestamp` into `update_idle_timestamp` / `update_read_count_timestamp`, which govern tenure-extend liveness accounting for that signer's weight. [6](#0-5) 

Because `reason_code` and `response_data` are outside the signed preimage, any entity that can re-inject a `BlockRejection` with the signer's captured `(signer_signature_hash, signature)` pair (e.g. by rebroadcasting through a channel that itself is only authenticated on the wire — verification here is on the embedded application-level signature, distinct from the StackerDB slot-write authentication) can pick a different `reason_code`/`response_data`. This is a rejection whose *meaning* is re-mapped after the fact: a “this block is invalid” signature can be relabeled as a “problematic transaction” accusation against an arbitrary `failed_txid`, or its idle/read-count timestamps can be substituted, while still passing `pubkey.verify()`.

### Impact Explanation
This matches the report's "rejection recounted / mis-attributed" class: a validly-signed rejection is reinterpreted with attacker-chosen `reason_code`/`response_data` without the signer's consent, since those fields are unauthenticated. Concretely this can (a) cause a transaction not actually flagged by a signer to accumulate `problematic_weight`/`total_weight` toward the node's problematic-tx tracking, and (b) corrupt idle/read-count timestamp bookkeeping used for tenure-extend liveness decisions — a High-severity liveness/mis-accounting issue per the rules (acting on stale/incorrect signer-reported state).

### Likelihood Explanation
Exploitability is bounded by whether any code path allows delivering a `BlockRejection` payload with a signer's genuine `(signer_signature_hash, signature)` bytes but different `reason_code`/`response_data` to the node/other signers *without* also being blocked by the outer transport authentication (StackerDB chunk signing by the slot owner, or the miner-message HTTP/event-forwarding layer). I could not fully confirm within budget whether any accessible relay/forwarding path in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` or `libsigner/src/events.rs` permits such re-injection without the original signer's private key (the StackerDB chunk-level signature check appears to bind chunk contents to the slot owner independently). Given that uncertainty, this should be treated as a genuine EIP-712-style struct/typestring gap that the field owner should evaluate for reachability, not a fully proven exploit chain.

### Recommendation
Include `reason`, `reason_code`, and all `response_data` sub-fields in the structured-data preimage that is signed/verified for `BlockRejection` (and audit `BlockAccepted`/other structured-data signers for the same gap), so that the signature commits to the entire semantic payload, not just `signer_signature_hash`.

### Proof of Concept
Given a signer's genuine `BlockRejection` `r` for some block `signer_signature_hash = H`:
1. `r.hash()` = `structured_data_message_hash(H, domain("block-rejection","1.0.0", r.chain_id))`, independent of `r.reason`, `r.reason_code`, `r.response_data`.
2. Construct `r2` = clone of `r` but with `reason_code = RejectCode::ValidationFailed(ValidateRejectCode::ProblematicTransaction)` and `response_data.failed_txid = Some(<attacker-chosen txid>)`, keeping `signature`, `signer_signature_hash`, `chain_id` unchanged.
3. `r2.hash() == r.hash()`, so `r2.verify(signer_pubkey)` returns `Ok(true)` — identical to the original — even though `reason_code`/`failed_txid` were forged. [1](#0-0)

    /// The signature hash for the block rejection
    pub fn hash(&self) -> Sha256Sum {
        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
        structured_data_message_hash(data, domain_tuple)
    }

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
