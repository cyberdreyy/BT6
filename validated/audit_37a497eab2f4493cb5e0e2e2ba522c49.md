### Title
Group rate limiter accounting uses Solend collateral (cToken) amount instead of true liquidity outflow, allowing bypass via exchange-rate divergence - ([File: programs/marginfi/src/instructions/solend/withdraw.rs])

### Summary
In `solend_withdraw`, the value fed into `record_withdrawal_outflow` (`rate_limit_amount`) is always the collateral-token (cToken) amount — `collateral_amount` when `withdraw_all=true` or the raw `amount` parameter otherwise — never the actual underlying liquidity amount transferred to the user. Because Solend's collateral-to-liquidity exchange rate diverges from 1:1 as reserve interest accrues, the amount registered against the bank-level and group-level rate limiters does not match the true liquidity value extracted via `cpi_transfer_liquidity_vault_to_destination`.

### Finding Description
`solend_withdraw` computes `collateral_amount` (in cToken units) from `bank_account.withdraw_all()` or from the caller-supplied `amount`, and unconditionally sets: [1](#0-0) 

Both branches (`withdraw_all=true` and `withdraw_all=false`) pass a **collateral-token** amount as both `native_amount` and `balance_amount` to `record_withdrawal_outflow`. Inside that helper, this collateral amount is used both for the bank's native-token rate limiter (`bank.rate_limiter.try_record_outflow`, denominated in native liquidity tokens per the struct doc "For bank-level: denominated in native tokens") and for the group-level USD value via `calc_value(balance_amount, price, bank.get_balance_decimals(), ...)`: [2](#0-1) 

However, the actual liquidity amount transferred to the user is computed later, via Solend's live exchange rate: [3](#0-2) [4](#0-3) 

`collateral_to_liquidity` computes `liquidity = collateral / (collateral_mint_total_supply / total_liquidity)`, i.e., the exchange rate grows above 1 collateral-per-liquidity as reserve interest accrues (`total_liquidity` grows relative to `collateral_mint_total_supply`), meaning `received` (real liquidity extracted) systematically diverges from `collateral_amount` (the value recorded for rate limiting) over the life of a reserve: [5](#0-4) 

This is a genuine unit mismatch, not merely a `withdraw_all` vs. non-`withdraw_all` inconsistency — every solend_withdraw call records cToken units against limiters intended to track native/liquidity outflow and USD value of liquidity, and no code path reconciles `rate_limit_amount` with `received`/`expected_liquidity_amount`. This differs from `lending_account_withdraw` and `drift_withdraw`/`juplend_withdraw`, which record the true native/liquidity amount (`amount_pre_fee` / `token_amount`) for rate-limiting purposes: [6](#0-5) [7](#0-6) 

An unprivileged authority can repeatedly call `solend_withdraw` and always have the rate limiter under-account (or over-account, depending on which direction the exchange rate has drifted) relative to the real liquidity extracted, since the discrepancy is a function of the Solend reserve's accrued interest, not attacker-controlled input manipulation per se — the caller cannot arbitrarily choose the divergence, but it exists deterministically based on reserve state and grows monotonically over time as interest accrues.

### Impact Explanation
If the exchange rate has moved such that `collateral_to_liquidity(collateral_amount) > collateral_amount` (i.e., cTokens are worth more liquidity than their raw count, which is the typical direction as a reserve accrues interest), then the bank-level and group-level rate limiters will under-count the true native/USD outflow. Repeated withdrawals could extract more real liquidity value than the group's hourly/daily rate limits are configured to allow, defeating the purpose of `group_rate_limiter`/`bank.rate_limiter` as a circuit-breaker against rapid fund drainage — this matches the scoped impact of "rate-limit bypass enabling unthrottled Solend fund extraction."

### Likelihood Explanation
Preconditions: group rate limiter (or bank rate limiter) must be enabled, and the target Solend reserve must have accrued enough interest that its exchange rate has diverged meaningfully from 1:1 (this happens naturally over time in any active reserve, not requiring any admin/oracle control). The exploit requires no privileged access — any authorized/unprivileged marginfi account holder calling the public `solend_withdraw` instruction repeatedly will trigger the mismatch, and the mismatch compounds over many small withdrawals from mature reserves.

### Recommendation
Compute the true native liquidity amount to be withdrawn (via `collateral_to_liquidity`) *before* calling `record_withdrawal_outflow`, and pass that liquidity-denominated value (matching `received`/`expected_liquidity_amount`) as `native_amount`/`balance_amount` instead of the raw collateral/cToken amount — consistent with how `lending_account_withdraw` and `drift_withdraw` record native token amounts. Alternatively, move the `record_withdrawal_outflow` call to after the CPI/transfer completes so the exact `received` amount (already verified against `expected_liquidity_amount`) can be used.

### Proof of Concept
Rust integration test plan (extends `programs/marginfi/src/instructions/solend/local_tests.rs`):
1. Set up a Solend mock reserve where `collateral_mint_total_supply < calculate_total_liquidity()` (simulating accrued interest so 1 cToken redeems for >1 liquidity token), and enable both bank-level and group-level rate limiters with a tight `max_outflow`.
2. Deposit and then call `solend_withdraw` with `amount = X` collateral tokens (below the configured limit when measured in cToken units) such that `collateral_to_liquidity(X)` measured in liquidity/USD terms would exceed the configured `max_outflow`/group hourly-daily cap if correctly accounted.
3. Assert the call succeeds (rate limiter does not reject it) even though the true liquidity/USD outflow (computed as `expected_liquidity_amount` and post-transfer `received`) exceeds the configured cap — demonstrating the bypass.
4. As an invariant check, sum `rate_limit_amount` values recorded across repeated `solend_withdraw` calls and compare against the cumulative delta of `liquidity_vault` token balance (or `reserve_liquidity_supply`) across the same calls; assert they diverge, proving the rate limiter accounting doesn't track true net outflow.

```rust
pub fn record_withdrawal_outflow(
    group_rate_limit_enabled: bool,
    native_amount: u64,
    balance_amount: u64,
    price: I80F48,
    bank: &mut Bank,
    group: &MarginfiGroup,
    group_key: Pubkey,
    bank_key: Pubkey,
    marginfi_account: &MarginfiAccount,
    clock: &Clock,
) -> MarginfiResult<()> {
    // Rate limiting tracks net outflow; skip for flashloan/liquidation/deleverage flows.
    if !should_skip_rate_limit(marginfi_account.account_flags) {
        if bank.rate_limiter.is_enabled() {
            bank.rate_limiter
                .try_record_outflow(native_amount, clock.unix_timestamp)?;
        }

        // Group-level rate limiting: read-only validation + event emission.
        // The admin aggregates events off-chain and calls update_group_rate_limiter.
        if group_rate_limit_enabled {
            check!(price > I80F48::ZERO, MarginfiError::InvalidRateLimitPrice);

            let value = calc_value(
                I80F48::from_num(balance_amount),
                price,
                bank.get_balance_decimals(),
                None,
            )?;
```

```rust
    /// Convert collateral to liquidity using this rate
    pub fn collateral_to_liquidity(&self, collateral_amount: u64) -> Result<u64> {
        let collateral: I80F48 = I80F48::from_num(collateral_amount);
        let liquidity: I80F48 = collateral.checked_div(self.0).ok_or_else(math_error!())?;

        liquidity
            .checked_to_num::<u64>()
            .ok_or(SolendMocksError::MathError.into())
    }
```
