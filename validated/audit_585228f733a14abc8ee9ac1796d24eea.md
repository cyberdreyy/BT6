### Title
Epoch-keyed instant-withdraw lookup reads only the current epoch — unfunded instant receipts from prior epochs are excluded from default recovery and permanently frozen - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The ncurses `_nc_find_entry` bug is a hash-table lookup that reads the wrong/stale entry. The analog in `IdleCreditVault` is its epoch-keyed claim lookups: instant-withdraw basis is stored per request epoch (`instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`), but default finalization and defaulted claims only ever read the bucket keyed by the *current* `epochNumber`. An unfunded instant receipt created in an earlier epoch is therefore invisible to the recovery accounting — the same wrong-entry read — leaving the holder's claim permanently unclaimable while the recovery reserve is over-distributed to the claimants that were indexed correctly.

### Finding Description
Instant withdraw requests are recorded under the epoch in which they were made: `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` are incremented at request time in `requestInstantWithdraw`. [1](#0-0)  These per-epoch buckets are never rolled forward or merged when `epochNumber` is incremented in `deposit`. [2](#0-1) 

When the CDO finalizes a default, `defaultPendingClaimBasis` computes the haircut basis as `pendingWithdraws` plus only `instantWithdrawClaimsByEpoch[epochNumber]` — the current epoch's bucket. [3](#0-2)  Symmetrically, `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`. [4](#0-3) 

The trace:
1. Epoch N (running, borrower active, partially prefunded instant queue): a KYC'd lender calls `requestInstantWithdraw` via the CDO. The CDO's `collectInstantWithdrawFunds` only collects part of the queue (the code explicitly contemplates this: `_defaultPrefundedInstantReserve` handles `instantBasis > pendingInstant`), so `pendingInstantWithdraws` remains non-zero and the user's basis sits in `instantWithdrawClaimsByEpoch[N]`.
2. Epoch rolls to N+1 (`deposit` while `isEpochRunning` bumps `epochNumber`).
3. Borrower defaults; manager/keeper calls `finalizeDefault`. `defaultPendingClaimBasis` reads `instantWithdrawClaimsByEpoch[N+1]` — the victim's epoch-N claim contributes **zero** to `totalBasis`, so `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed over a smaller basis and paid out pro-rata only to indexed claimants.
4. Victim calls `claimInstantWithdrawRequest`: `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` is true, so `_claimDefaultedInstantWithdrawRequest` runs but reads `instantWithdrawsRequestsByEpoch[_user][N+1] == 0` and returns early. [5](#0-4)  The funded-claim path then burns the full `instantWithdrawsRequests[_user]` receipt and calls `_transferFundedClaim`, which reverts whenever the strategy balance is fully consumed by `defaultRecoveryReserve` (`balance - reserve < _amount`). [6](#0-5) 

Guards do not stop it: `_ensureDefaultRecoveryInitialized` refuses to run while `pendingInstantWithdraws != 0` precisely because legacy/unfunded instant claims cannot be normalized — the same acknowledgment that unfunded instant receipts can persist across epochs. [7](#0-6) 

### Impact Explanation
Two direct losses: (a) **permanent freezing/theft of unclaimed yield** — the epoch-N receipt holder's claim can never be paid (defaulted path reads the wrong epoch bucket; funded path is blocked by the reserve guard), and their minted receipt tokens become unredeemable; (b) **mispriced reserve distribution** — excluding the victim's basis from `totalBasis` inflates `defaultRecoveryPrice`, so other claimants withdraw more than their fair pro-rata share from `defaultRecoveryReserve`, i.e. the victim's recovery share is transferred to them. Loss equals the victim's full receipt amount up to the reserve.

### Likelihood Explanation
Requires a specific but plausible sequence: an instant withdraw that is only partially funded by the CDO's liquidity sweep, an epoch rollover while `pendingInstantWithdraws` remains non-zero, then a borrower default finalized in a later epoch. Unfunded instant queues across an epoch boundary are realistic whenever the borrower is late on repayment at `stopEpoch`/`startEpoch` (the prefunded-reserve code exists for exactly this partial-funding case). No privileged actor misbehavior is needed; the attacker is simply another claimant who benefits, or no attacker at all — the victim loses regardless.

### Recommendation
Do not key default-epoch instant claim basis to `epochNumber`. Either:
- Track a global aggregate `instantWithdrawClaims` (sum of all unfunded instant basis) used by `defaultPendingClaimBasis`, and per-user store the epoch list or a single aggregate `instantWithdrawsRequests[_user]` as the defaulted claim basis instead of `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`; or
- On epoch rollover (`deposit` bumping `epochNumber`), fold outstanding `instantWithdrawClaimsByEpoch[oldEpoch]` into the new epoch bucket, and document that all unfunded instant claims belong to the newest epoch for recovery purposes.

### Proof of Concept
Foundry fork sketch (test/foundry/IdleCreditVault.t.sol harness):

```solidity
// setup: credit vault CDO + IdleCreditVault strategy, KYC'd alice, active borrower
// EPOCH N running, strategy holds only part of instant liquidity
vm.prank(alice);
cdo.requestInstantWithdraw(100e6);          // strategy mints receipt, epoch N bucket
// CDO collects only 40% of the instant queue
vm.prank(address(cdo));
strategy.collectInstantWithdrawFunds(40e6); // pendingInstantWithdraws = 60e6
// borrower repays epoch, manager stops, epoch N+1 starts -> epochNumber = N+1
manager.stopEpoch(); borrower.startEpoch();

// borrower defaults in epoch N+1; finalizeDefault with partial recovery R
cdo.finalizeDefaultRecovery(R, recoverySource);
// defaultPendingClaimBasis == pendingWithdraws + instantWithdrawClaimsByEpoch[N+1]
// alice's 100e6 basis is NOT included -> recoveryPrice inflated

// alice tries to claim -> _claimDefaultedInstantWithdrawRequest reads epoch N+1 == 0
// then funded path reverts: balance == defaultRecoveryReserve
vm.prank(alice);
vm.expectRevert(NotAllowed.selector);
cdo.claimInstantWithdrawRequest(alice);
// alice's 100e6 receipt is permanently unclaimable; other claimants
// recovered at a price higher than reserveAmount / trueTotalBasis
```

Key uncertainty I could not fully verify in the available iterations: whether the CDO's `stopEpoch`/`startEpoch` path in `IdleCDOEpochVariant` permits advancing the epoch while `pendingInstantWithdraws` remains non-zero. The prefunded-reserve logic (`_defaultPrefundedInstantReserve`) strongly suggests partial funding is supported, but if an earlier guard forces the instant queue to be fully funded before epoch rollover, the cross-epoch window closes and this degrades to a same-epoch-only edge that the current code already handles.

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
