### Title
Stale confirmations from removed multisig members allow request execution below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts a request as approved once `confirmations.len() + 1 >= self.num_confirmations`, where `confirmations` is a `HashSet<String>` keyed by member identity. When a member is removed via `delete_member`, only the *requests that member itself created* are purged; confirmations that member previously cast on requests created by other members are never removed. A stale confirmation from a now-deleted member is therefore still counted toward the `num_confirmations` threshold, letting a request execute with fewer *live* confirming members than the configured threshold requires.

### Finding Description
The invariant the contract is supposed to enforce is: `num_confirmations` == number of distinct **current** members who confirmed a request. The code instead enforces: `num_confirmations` == number of distinct **entries ever inserted** into the `confirmations` set for that request, regardless of whether those entries still correspond to current members.

`delete_member` only cleans up requests keyed by `r.member == member` (i.e., requests the removed member authored), and removes the member's `num_requests_pk` entry: [1](#0-0) 

It never scans `self.confirmations` to strip the removed member's public key/account id from confirmation sets of requests authored by *other* members: [2](#0-1) 

`confirm` then blindly trusts the size of the stored `confirmations` set: [3](#0-2) 

The `current_member` check only gates who is *allowed to add a new confirmation*, not whether previously-recorded confirmations are still valid: [4](#0-3) 

This is structurally the same bug class as the reported `Attestations.addIncompleteAttestations` issue: a counter (`currentIndex` / `confirmations.len()`) is compared against a static threshold without verifying that the underlying set it is drawn from (available validators / live members) still satisfies the assumption made when the threshold was set. Here it manifests as a stale-membership accounting bug rather than a DoS: the equality the contract must hold, `num_confirmations == |{live members who confirmed}|`, is broken to `num_confirmations <= |{confirmations ever recorded, including from removed members}|`.

The identical `remove_request`/`delete_member`/`confirm` pattern exists in the legacy `multisig/src/lib.rs` (there via `DeleteKey`), so both multisig variants in scope share the flaw: [5](#0-4) 

### Impact Explanation
This is Critical: it allows a `MultiSigRequestAction` (e.g., `Transfer`, `AddKey`/`AddMember`, `FunctionCall`) to be **executed below the configured confirmation threshold**, because one or more of the counted confirmations belong to an account that is no longer a member. An outstanding request that was confirmed by a member who is later removed can be pushed to execution by fewer additional *live* members than `num_confirmations` was set to require, moving NEAR (or granting keys/authority) with a weaker authorization set than the multisig's own threshold binding promises.

### Likelihood Explanation
This does not require the foundation, an owner, or a compromised key beyond the normal operation of the multisig members themselves — it only requires the ordinary sequence of: (1) a member confirms a pending request, (2) that member is later removed as part of routine membership rotation (a supported, documented action), and (3) the remaining members continue confirming the still-pending request. No malicious member collusion beyond normal usage is strictly necessary; a legitimate member rotation performed while other requests are outstanding is enough to trigger the mismatch. The `REQUEST_COOLDOWN` and `active_requests_limit` mechanisms do not address this because they govern deletion/rate-limiting, not confirmation-set consistency.

### Recommendation
When removing a member in `delete_member` (and the analogous `DeleteKey` path in `multisig/src/lib.rs`), iterate `self.confirmations` for all outstanding requests and remove the deleted member's entry from every confirmation set, not just from requests the member itself created. Alternatively, revalidate at `confirm` time (and before executing) that every entry in the stored `confirmations` set still corresponds to a current member, discounting stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `B` calls `add_request` to create request `R` (e.g., `Transfer` to an account `B` controls).
3. `A` calls `confirm(R)` → `confirmations(R) = {A}`.
4. Members execute a separate request `DeleteMember { member: A }` (confirmed by `B, C, D`) — this succeeds and removes `A` from `self.members`; per `delete_member`, only requests authored by `A` are purged, so `confirmations(R) = {A}` is untouched.
5. `C` calls `confirm(R)` → `confirmations(R).len() + 1 = 2 >= 3`? No, count is 2 — not yet.
6. `D` calls `confirm(R)` → `confirmations(R).len() + 1 = 3 >= 3` → `execute_request` fires.
7. Result: `R` executes with confirmations nominally from `{A, C, D}`, but `A` is no longer a member. Only `C` and `D` are live confirming members — 2 live confirmations executed a request requiring 3, breaking the `num_confirmations == live confirmers` binding and moving funds/authority below the intended threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
