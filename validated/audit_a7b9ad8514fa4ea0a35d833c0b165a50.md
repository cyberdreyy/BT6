### Title
Dust withdraw request bricks `processWithdrawRequests` via `Is0` revert, permanently freezing an entire epoch's queued withdrawals - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
`IdleCDOEpochQueue.processWithdrawRequests()` computes the epoch withdraw price as `_underlyingsRequested * ONE_TRANCHE / _pending` and reverts with `Is0()` when the result rounds to zero. Any KYC-passing user can submit a 1-wei-tranche withdraw request alongside legitimate requests; when the manager processes the epoch, the aggregated request reverts, and because the dust request cannot be removed by anyone but its (malicious) owner, withdrawal processing for that epoch is permanently blocked.

### Finding Description
In `processWithdrawRequests` (contracts/IdleCDOEpochQueue.sol:298-329), all queued tranche withdrawals for the current epoch are processed in one shot:

```solidity
uint256 _pending = epochPendingWithdrawals[_epoch];
uint256 _underlyingsRequested = _cdo.requestWithdraw(_pending, tranche);
uint256 _epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending;
if (_epochPrice == 0) {
  revert Is0();
}
```

`_underlyingsRequested` is `IdleCreditVault.requestWithdraw`'s return — the post-management-fee underlying amount backing the receipt (contracts/strategies/idle/IdleCreditVault.sol:243-295). When `_pending` is small (a dust tranche amount, e.g. 1 wei, or a dust remainder combined with a management fee that rounds the requested underlyings down), the integer division `underlyings * 1e18 / tranchePending` can yield 0 — specifically whenever `_underlyingsRequested * 1e18 < _pending`, i.e. when implied price per tranche unit is below 1e18/1 wei granularity, or when `_underlyingsRequested` itself rounds to 0 for a dust `_pending`.

The mitigation path does not exist at this stage: `deleteWithdrawRequest` (lines 203-218) lets only `msg.sender` retrieve their own request, and `processWithdrawRequests` reverts before any state is cleared, so `epochPendingWithdrawals[_epoch]` stays non-zero forever. Every honest user's tranche tokens locked in the queue for that epoch are unclaimable: `claimWithdrawRequest` requires `epochWithdrawPrice[_epoch] != 0` (or `isEpochWithdrawZero`), which is only set inside the reverting function.

Note the asymmetry that makes this exploitable: the zero-payout case at *claim* time was handled via `isEpochWithdrawZero` (lines 355-369), but the zero-*price* case at request time still hard-reverts, and there is no skip/refund path for dust requests.

### Impact Explanation
Permanent freezing of funds: all users who queued withdraw requests for the affected epoch lose access to their tranche tokens held by the queue. The loss equals the full `epochPendingWithdrawals[_epoch]` value of co-queued honest users — the attacker risks only a dust amount. The freeze persists across future epochs because `epochPendingWithdrawals` is keyed per epoch and never cleans up.

### Likelihood Explanation
- Attacker needs only KYC (`isWalletAllowed`) plus a tranche token balance — both listed as valid attacker roles.
- During any running epoch they call `requestWithdraw(1)` (or a dust amount sized so `requestWithdraw` returns 0 underlyings after `_calcInterest`/fee rounding).
- The condition triggers deterministically when the honest queued volume is small relative to the dust, or when the pool is post-loss/`virtualPrice` low so that `underlyings * 1e18 / pending` rounds to 0. The only requirement is a manager call to `processWithdrawRequests`, which is routine.
- No privileged misbehavior required; the honest manager is the one who triggers the revert.

### Recommendation
- Skip or isolate dust requests: process withdrawals such that a request whose computed underlyings is 0 is refunded (return tranche tokens, decrement `epochPendingWithdrawals`) instead of reverting.
- Alternatively revert inside `requestWithdraw` when `amount` is below a minimum, mirroring the claim-side `isEpochWithdrawZero` handling, or record a zero price + `isEpochWithdrawZero` and let users reclaim tranche tokens via `deleteWithdrawRequest`.
- A minimum-request check (e.g. require `_pending >= MIN`) also bounds the rounding surface.

### Proof of Concept
Foundry fork test sketch (drop into `test/foundry/IdleCDOEpochQueue.t.sol` style harness):

```solidity
function testDustWithdrawRequestBricksEpochProcessing() external {
  // buffer period: attacker (KYC'd) queues a dust withdraw, honest user queues a real one
  address attacker = makeAddr('attacker');
  address honest = makeAddr('honest');

  uint256 honestTranches = _depositWithUser(honest, 100e6); // 100 USDC worth
  uint256 attackerTranches = _depositWithUser(attacker, 1); // dust deposit -> dust tranches

  vm.prank(manager);
  cdoEpoch.startEpoch();

  _requestWithdrawWithUser(attacker, attackerTranches); // 1-wei scale tranche request
  _requestWithdrawWithUser(honest, honestTranches);

  _stopCurrentEpochWithApr(0); // borrower repays; strategy epochNumber bumps

  vm.prank(manager);
  vm.expectRevert(Is0.selector);
  queue.processWithdrawRequests(); // _underlyingsRequested * 1e18 / _pending rounds to 0

  // no one can fix it: attacker won't delete, manager has no eviction path
  vm.prank(honest);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  queue.claimWithdrawRequest(strategy.epochNumber()); // epochWithdrawPrice never set

  // honest tranche tokens remain locked in the queue
  assertEq(tranche.balanceOf(address(queue)), attackerTranches + honestTranches);
}
```

Caveat: exact dust sizing depends on `IdleCreditVault.requestWithdraw`'s fee/interest path returning 0 underlyings (or < `_pending / 1e18`) for the chosen amount; the PoC should tune `attackerTranches` so `_underlyingsRequested` is 0, which is reachable whenever principal-only burn/mint accounting plus management-fee rounding yields a zero implied price.
