## Finding: Unvalidated zero-address beneficiary in `staking_contract::set_beneficiary_for_operator` permanently blocks distribution of a staker's unlocked/inactive stake

### Title
Operator can set `beneficiary_for_operator` to `0x0`, permanently bricking `distribute()`/`distribute_internal` and freezing the staker's inactive stake and rewards - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::set_beneficiary_for_operator` [1](#0-0)  lets any operator set an arbitrary `new_beneficiary` address with no validation, mirroring the exact bug class from the external report (`CoverageFundAddress.set`/`River.setCoverageFund` failing to reject `address(0)`). Setting the beneficiary to `@0x0` causes every future call to `distribute`/`distribute_internal` for that operator's pool to abort permanently, because `aptos_account::deposit_coins` tries to auto-create an account at `0x0`, which is a reserved address and always aborts.

### Finding Description
`set_beneficiary_for_operator` stores whatever address the operator supplies with no sanity check: [2](#0-1) 

`distribute_internal`, which is invoked by the permissionless `distribute` entry function ("Allow anyone to distribute already unlocked funds"), redirects the operator's commission share to `beneficiary_for_operator(operator)`: [3](#0-2) 

`aptos_account::deposit_coins` auto-creates the destination account if it doesn't exist: [4](#0-3) 

`account::create_account` (invoked transitively through `create_account` in `aptos_account.move`) aborts whenever the target address is a reserved address, including `@vm_reserved` (`0x0`), per the module's own formally-verified spec: [5](#0-4) 

Because `distribute_internal`'s `while` loop processes all distribution-pool shareholders (operator's commission share and the staker's principal/rewards share) within a single atomic transaction, an abort while paying the operator's `0x0` beneficiary reverts the *entire* `distribute` call — including the staker's own withdrawal of already-unlocked (`inactive`/`pending_inactive`) stake, since `stake::withdraw_with_cap` was already executed earlier in the same function and its effects are rolled back along with everything else.

### Impact Explanation
Once an operator calls `set_beneficiary_for_operator(operator, @0x0)`, the `distribute` entry function for that `(staker, operator)` staking contract becomes permanently unusable by anyone (staker or operator), because it will always abort on the operator's `0x0` payout leg. This traps the staker's unlocked stake and accrued rewards for that pool indefinitely (no code path exists to bypass `distribute_internal` and pull funds directly, since the `OwnerCapability` is only held inside the `StakingContract` resource and only accessed via `staking_contract` module functions). This is a permanent lock of stake/commission claim rights that credits no one and traps value, matching "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows."

### Likelihood Explanation
High/likely: this requires only a single unprivileged call by the operator (`set_beneficiary_for_operator`), gated only by the `operator_beneficiary_change_enabled` feature flag being turned on — no special permission beyond already being the assigned operator, and no cooperation or consent from the staker is needed. Any operator (malicious, compromised, or simply careless — e.g., passing a mistyped/zeroed address) can trigger the permanent freeze, and the same mechanism affects any `vesting.move` contract using this operator via `vesting::withdraw_stake` → `staking_contract::distribute`, since vesting relies on the same `distribute_internal` path [6](#0-5) .

### Recommendation
Add a zero-address (and self-referential/sanity) check in `set_beneficiary_for_operator`, rejecting `new_beneficiary == @0x0`, and/or make `distribute_internal` defensively skip/redirect payouts to unregistered or reserved-address beneficiaries instead of aborting the whole distribution loop: [7](#0-6) 

### Proof of Concept
1. Staker creates a staking contract with `operator` O: `staking_contract::create_staking_contract(staker, O, voter, amount, commission_pct, seed)`.
2. Operator O calls `staking_contract::set_beneficiary_for_operator(O, @0x0)` — succeeds, no validation on `new_beneficiary` [1](#0-0) .
3. Time passes; some stake becomes `inactive`/`pending_inactive` (e.g., via `unlock_stake`).
4. Anyone calls `staking_contract::distribute(staker_address, O)`. `distribute_internal` withdraws the inactive stake into a local `coins` value, then in its payout loop attempts `aptos_account::deposit_coins(beneficiary_for_operator(O) == @0x0, commission_coins)`.
5. `deposit_coins` calls `account::create_account(@0x0)`, which aborts because `@0x0 == @vm_reserved` [5](#0-4) .
6. The whole `distribute` transaction reverts — the staker's already-unlocked funds cannot be withdrawn through this pool ever again, since every future call to `distribute` repeats the same abort.

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
