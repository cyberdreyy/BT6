### Title
Default-recovery basis and claim path read instant-withdraw receipts across epoch bounds — earlier-epoch instant claims are excluded from `defaultPendingClaimBasis` yet paid at par (or frozen) - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a heap over-read: `H5T_copy` reads beyond the bounds of the source object. The credit-vault analog is a **claim-basis over-read/under-read across epoch boundaries** in the instant-withdraw recovery path. `defaultPendingClaimBasis()` only counts `instantWithdrawClaimsByEpoch[epochNumber]` (the current epoch) when sizing the default recovery reserve, but `claimInstantWithdrawRequest()` pays the *aggregate* `instantWithdrawsRequests[_user]`, which spans all epochs. An instant receipt opened in an earlier epoch and still unfunded/unclaimed when `finalizeDefault` runs is excluded from the recovery haircut basis, and is then paid at par through `_transferFundedClaim` or blocks all claims through its reserve guard.

### Finding Description
Recovery accounting is keyed per request epoch:

- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (`IdleCreditVault.sol:367-374`).
- `defaultPendingClaimBasis()` computes `basis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — only the *current* epoch bucket (`IdleCreditVault.sol:644-649`).
- `finalizeDefaultRecovery` sizes `defaultRecoveryReserve`/`defaultRecoveryPrice` from that basis (`IdleCreditVault.sol:679-692`).
- On claim, `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (`IdleCreditVault.sol:842-856`), then `claimInstantWithdrawRequest` burns and pays the **entire** `instantWithdrawsRequests[_user]` aggregate via `_transferFundedClaim` (`IdleCreditVault.sol:387-392`).

So a user who requested an instant withdraw in epoch N that was never fully funded (`pendingInstantWithdraws` carries the unfunded remainder) and never claimed, then rolls into epoch N+1 where the borrower defaults:

1. `defaultPendingClaimBasis()` misses their epoch-N receipt — `instantWithdrawClaimsByEpoch[N]` is never added. `totalBasis` is understated, so `recoveryPrice` is set too high and the reserve is under-provisioned relative to real claims.
2. When the user calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` clears only the epoch-(N+1) slice (zero for them), then the full epoch-N receipt is paid **at par** by `_transferFundedClaim`, consuming non-reserve strategy balance that belongs to funded normal-withdraw claimants — or, if the balance is entirely reserve, the `balance - reserve < _amount` guard at `IdleCreditVault.sol:900-905` reverts, permanently freezing the user's claim and potentially every subsequent claim.

The mirror-image case also exists: the same user holding receipts in both epochs gets the epoch-(N+1) slice haircutted but the epoch-N slice paid at par in one call, mixing recovery and funded pools.

### Impact Explanation
Either direct theft or permanent freezing of funds:

- If the strategy holds non-reserve underlying (funded pending withdraws collected via `collectWithdrawFunds`, prefunded instant amounts, post-default deposits), the stale-epoch instant receipt is redeemed at 100% instead of `defaultRecoveryPrice`, draining assets owed to other claimants. Loss equals `(1 - recoveryPrice) * staleClaimBasis` per affected receipt.
- If the strategy holds only the reserve, the `_transferFundedClaim` guard reverts, permanently freezing the stale receipt — and because claims are processed per user, unrelated claimants with funded balances are unaffected only until their own claims exhaust non-reserve funds.
- Additionally, the understated `totalBasis` inflates `defaultRecoveryPrice`, overpaying all defaulted-epoch claimants at the expense of the reserve, which can leave later claimants (including active LPs redeeming via `postDefaultRequests`) unable to withdraw — insolvency of the recovery reserve.

### Likelihood Explanation
Reachable by any KYC-passing lender (unprivileged). Preconditions: the pool uses instant withdrawals (`setInstantWithdrawParams` with a delay — exercised in `testFinalizeDefaultHaircutsPendingInstantRedeems`), the attacker requests an instant withdraw that remains partially or wholly unfunded into the next epoch, and a default is finalized in a later epoch. Partial prefunding is a designed flow (`_defaultPrefundedInstantReserve` exists precisely because `instantWithdrawClaimsByEpoch[epochNumber]` can exceed `pendingInstantWithdraws`), and nothing in `requestInstantWithdraw`, `collectInstantWithdrawFunds`, or the claim path bounds receipt lifetime to one epoch or clears stale per-epoch entries. The existing guards do not stop it: `_transferFundedClaim`'s reserve guard converts theft into a revert (freeze) rather than preventing the mispricing, and the `defaultRecoveryFinalized` path in `claimInstantWithdrawRequest` only engages `defaultInstantWithdrawsFinalized`, which is itself derived from the same current-epoch-only accounting.

One caveat: whether the CDO layer can roll `startEpoch` while `pendingInstantWithdraws > 0` is gated in `IdleCDOEpochVariant` (instant-withdraw delay/funding calls); I could not fully verify that gate in the available iterations, but the strategy explicitly supports multi-epoch instant receipt state (per-epoch mappings, aggregate counters, prefunded-reserve handling), so the under-scoped read is a real inconsistency even if reachability depends on CDO sequencing.

### Recommendation
Make the default-claim basis and the claim path read the same bounds:

- In `defaultPendingClaimBasis()`, account for *all* outstanding instant receipts, not only `instantWithdrawClaimsByEpoch[epochNumber]` — e.g., track a global `totalInstantClaims` counter incremented in `requestInstantWithdraw` and decremented in `claimInstantWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest`, and use `pendingInstantWithdraws` consistency to derive the unfunded share.
- Alternatively, in `claimInstantWithdrawRequest`, iterate/clear all `instantWithdrawsRequestsByEpoch` entries ≤ `defaultRecoveryEpoch` at `defaultRecoveryPrice` instead of paying the residual aggregate at par.
- Ensure `instantWithdrawClaimsByEpoch` entries for old epochs cannot strand unclaimed basis; either fund or expire them before `startEpoch`, or include them in recovery accounting.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
