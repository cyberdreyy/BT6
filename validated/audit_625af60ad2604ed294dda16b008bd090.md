### Title
Unguarded `initializeConfig()` in `BridgeCommittee` Can Be Front-Run to Permanently Lock Bridge Vault Funds — (`bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig()` has no caller restriction. Any Ethereum address can call it before the deployer does. Because the function enforces a one-time-only write (`require(address(config) == address(0))`), a front-runner who wins the race permanently installs a malicious `IBridgeConfig` contract. Every downstream bridge operation that reads `committee.config()` — including the `onlySupportedChain` modifier, token-address lookups, and decimal conversions — then operates against attacker-controlled data, permanently locking all funds held in the `BridgeVault`.

---

### Finding Description

`BridgeCommittee.sol` separates committee member initialization from config initialization into two distinct transactions. The first transaction calls `initialize()` (protected by OpenZeppelin's `initializer` modifier). The second, separate transaction calls `initializeConfig()`:

```solidity
// bridge/evm/contracts/BridgeCommittee.sol L63-66
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

There is no `onlyOwner`, no committee-signature check, and no deployer restriction — the function is `external` with no modifier. The deployment script confirms the gap:

```
// bridge/evm/script/deploy_bridge.s.sol L174-178
BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig));   // ← front-runnable
BridgeCommittee committeeImplementation = BridgeCommittee(Upgrades.getImplementationAddress(bridgeCommittee));
committeeImplementation.initializeConfig(address(bridgeConfig));             // ← also front-runnable
```

Between the deployment of `BridgeConfig` and the call to `initializeConfig`, any observer of the mempool can submit a transaction with higher gas that calls `initializeConfig(maliciousConfigAddress)`. Because the guard only checks `address(config) == address(0)`, the legitimate deployer's subsequent call reverts with `"BridgeCommittee: Config already initialized"`, and the malicious config is permanently cemented.

---

### Impact Explanation

`committee.config()` is called in every critical path of `SuiBridge.sol`:

- **`onlySupportedChain` modifier** (L283-288): calls `committee.config().isChainSupported(targetChainID)`. A malicious config returning `false` for all chains causes every call to `transferBridgedTokensWithSignatures`, `bridgeERC20`, and `bridgeETH` to revert permanently.
- **`transferBridgedTokensWithSignatures`** (L67, L74, L79-80): reads `config.chainID()`, `config.tokenAddressOf()`, and `config.tokenSuiDecimalOf()` to route and convert token transfers out of the vault.
- **`_transferTokensFromVault`** (L250): reads `committee.config().tokenAddressOf(tokenID)` to determine which ERC-20 to release from the vault.

A malicious config that returns `false` from `isChainSupported()` for every chain ID causes all withdrawal paths to revert. All ERC-20 tokens and ETH held in `BridgeVault` become permanently inaccessible — a complete fund lock. The `config` slot can never be overwritten because the one-time guard has already fired.

**Impact class**: Permanent fund lock (High/Medium per the allowed impact gate).

---

### Likelihood Explanation

The attack window is the block interval between the `BridgeConfig` proxy deployment and the `initializeConfig` call. Both transactions are broadcast to the public Ethereum mempool. Any actor monitoring the mempool for `BridgeCommittee` deployment activity can detect the pattern and submit a front-running transaction with a higher gas price. No special privilege, stake, or key material is required — only an ordinary Ethereum account and the ability to read pending transactions.

---

### Recommendation

Add a deployer-only guard to `initializeConfig`. The simplest fix is to record the deployer address during `initialize()` and restrict `initializeConfig` to that address:

```solidity
address private _deployer;

function initialize(...) external initializer {
    __CommitteeUpgradeable_init(address(this));
    __UUPSUpgradeable_init();
    _deployer = msg.sender;
    // ... existing logic
}

function initializeConfig(address _config) external {
    require(msg.sender == _deployer, "BridgeCommittee: Unauthorized");
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

Alternatively, pass `_config` directly into `initialize()` and set it atomically in the same transaction, eliminating the two-step window entirely.

---

### Proof of Concept

1. Deployer broadcasts `BridgeCommittee.initialize(committee, stake, minStake)` — this succeeds; `config` is `address(0)`.
2. Deployer broadcasts `BridgeConfig.initialize(...)` — this succeeds; a legitimate config contract exists at `bridgeConfig`.
3. Deployer broadcasts `BridgeCommittee.initializeConfig(bridgeConfig)`.
4. **Attacker** observes step 3 in the mempool, broadcasts `BridgeCommittee.initializeConfig(maliciousConfig)` with higher gas. Attacker's transaction is mined first.
5. Deployer's transaction from step 3 reverts: `"BridgeCommittee: Config already initialized"`.
6. `committee.config()` now returns `maliciousConfig` permanently.
7. `maliciousConfig.isChainSupported()` returns `false` for all inputs.
8. Every call to `SuiBridge.transferBridgedTokensWithSignatures`, `bridgeERC20`, and `bridgeETH` reverts at the `onlySupportedChain` modifier.
9. All funds in `BridgeVault` are permanently locked with no recovery path.
