### Title
Missing upper-bound (future) timestamp validation in `HandleLegacyUserMessage` staleness check allows expired-window bypass and unauthorized trigger replay - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The staleness check in `handler.HandleLegacyUserMessage` only rejects messages whose `payload.Timestamp` is *older* than `now - MaxAllowedMessageAgeSec`; it never rejects messages whose `Timestamp` is in the future or wraps to a large unsigned value. [1](#0-0)  Because `Timestamp` is an attacker-supplied field inside the user-signed JSON-RPC payload, a caller can set an arbitrarily large (or negative, which wraps via `uint()` cast) `Timestamp` value that will never satisfy the "stale" condition, causing the request to always be forwarded to all DON members regardless of its real age.

### Finding Description
`HandleLegacyUserMessage` unmarshals the user-controlled `TriggerRequestPayload` from `msg.Body.Payload` and only performs two timestamp validations:
1. `payload.Timestamp == 0` is rejected. [2](#0-1) 
2. `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` rejects messages that are too *old*. [1](#0-0) 

There is no corresponding check that rejects `payload.Timestamp` values greater than `now` (or `now + small clock-skew allowance`). Because the inequality is one-sided, any `Timestamp` value at or above `now` (including `math.MaxInt64`, or any far-future date) will make the right-hand side (`uint(payload.Timestamp)`) large enough that the left-hand side is never greater, so the message is never classified "stale" and is forwarded unconditionally past this gate to `common.ValidatedRequestFromMessage` and then to every member of `h.donConfig.Members` via `don.SendToNode`. [3](#0-2) 

Additionally, `payload.Timestamp` is a signed integer (`int64`, confirmed by its use with `strconv.ParseInt` / `int64` assignment in the handler test's `triggerRequest` helper). [4](#0-3)  A negative `Timestamp` cast via `uint(payload.Timestamp)` wraps to a very large unsigned value near `math.MaxUint64` (or `math.MaxUint32` on 32-bit builds), which likewise defeats the "older than" comparison and is never flagged stale.

The attacker precondition is simply the ability to submit a signed gateway trigger message (any holder of a valid signing key able to reach the gateway's user-message path), which the threat model explicitly includes ("any address sending signed gateway requests"). The attacker fully controls the `Timestamp` field inside their own signed payload, so no signature bypass is required — they can just pick a future or negative timestamp when constructing and signing their own request.

### Impact Explanation
This allows an attacker-crafted trigger message with an arbitrary (future or wrapped-negative) `Timestamp` to permanently evade the intended freshness/anti-replay window and be broadcast to every DON node. Because `MethodWebAPITrigger` requests are forwarded verbatim to all workflow DON members and can initiate workflow trigger execution, this weakens the freshness guarantee intended to bound the validity window of trigger requests, and could be used to make a captured/self-crafted signed request remain "fresh" (never rejected as stale) indefinitely, undermining the anti-replay intent of the staleness check. This maps to a limited "logic/validation bypass" impact rather than direct fund loss or credential exposure, since the message must already carry a valid signature.

### Likelihood Explanation
Requires only the ability to submit a validly-signed `web_api_trigger` message to the gateway — no operator/admin access, no misconfiguration, and no reliance on `MaxAllowedMessageAgeSec` being misconfigured. The bug is fully reachable and repeatable at will by the attacker simply setting `Timestamp` to `now + N` or a negative value in the payload before signing, i.e., 100% reproducible.

### Recommendation
Add a symmetric upper-bound check, e.g.:
```go
now := time.Now().Unix()
maxAge := int64(h.config.MaxAllowedMessageAgeSec)
if payload.Timestamp > now || payload.Timestamp < now-maxAge {
    // reject as stale/future-dated
}
```
Perform the comparison using signed `int64` arithmetic (not `uint`) to avoid cast wrap-around for negative or out-of-range values, and validate `payload.Timestamp` is within a sane bound before any subtraction/cast.

### Proof of Concept
Table-driven test in `core/services/gateway/handlers/capabilities/handler_test.go` extending `TestHandlerReceiveHTTPMessageFromClient`:
```go
cases := []struct{
    name      string
    timestamp int64
    wantReject bool
}{
    {"very old", time.Now().Add(-1*time.Hour).Unix(), true},
    {"exactly at lower bound", time.Now().Unix() - int64(handler.config.MaxAllowedMessageAgeSec), false},
    {"future timestamp (1 year ahead)", time.Now().Add(365*24*time.Hour).Unix(), true /* currently fails: passes */},
    {"MaxInt64 timestamp", math.MaxInt64, true /* currently fails: passes */},
    {"negative timestamp", -1, true /* currently fails: passes via uint wraparound */},
}
for _, c := range cases {
    msg := triggerRequest(t, nodes[0].PrivateKey, []string{"t"}, "", strconv.FormatInt(c.timestamp, 10), "")
    cb := hc.NewCallback()
    // don.SendToNode should NOT be called when c.wantReject == true
    err := handler.HandleLegacyUserMessage(ctx, msg, cb)
    require.NoError(t, err)
    r, _ := cb.Wait(ctx)
    if c.wantReject {
        require.Equal(t, api.HandlerError, r.ErrorCode, "expected stale/future rejection for %s", c.name)
    }
}
```
Running this against the current implementation shows the future-timestamp and negative-timestamp cases are forwarded to `don.SendToNode` instead of being rejected, confirming the missing upper-bound check.
