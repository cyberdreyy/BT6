### Title
Signer broadcasts and tallies responses that bypass the `BlockInfo` finality state-guard - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`BlockInfo::check_state`/`move_to` (`stacks-signer/src/signerdb.rs:314-341`) is the object-state limitation meant to make `GloballyAccepted`/`GloballyRejected` terminal: once a block is finalized one way, it must never flip to the other, and never fall back to a bare local verdict. However, every call site that invokes `mark_locally_rejected()`/`mark_locally_accepted()` ignores a failed transition (i.e., a blocked "object state limitation") and proceeds to broadcast and internally process the response anyway.

### Finding Description
`BlockInfo::check_state` ( [1](#0-0) ) enforces that `LocallyAccepted`/`LocallyRejected` cannot be reached from `GloballyRejected`/`GloballyAccepted`. `move_to` ( [2](#0-1) ) returns `Err` when this guard fires, leaving `self.state` untouched (still whatever terminal value it had).

At the pre-commit-threshold re-check site, on a failed chainstate re-check: [3](#0-2) 
the code calls `block_info.mark_locally_rejected()`, and only warns if `!has_reached_consensus()` — i.e. it explicitly anticipates the call failing when the block is already `GloballyAccepted`/`GloballyRejected` — but it does **not** stop there. It falls through to `insert_block`, `handle_block_rejection(&block_rejection, ...)`, and `send_block_response(&block_info.block, block_rejection.into())` unconditionally, broadcasting a `BlockResponse::Rejected` and driving `handle_block_rejection`'s rejection-tally logic even though the object-state guard just refused to record that verdict.

The same pattern exists on the signing side: [4](#0-3) 
`mark_locally_accepted(false)` can fail for the identical reason (block already `GloballyRejected`), yet `handle_block_signature` and `send_block_response` with an `Accepted` response still execute.

And in `handle_block_validate_ok`: [5](#0-4) 
same ignore-and-continue pattern for `mark_locally_rejected`.

So the "object state limitation" that is supposed to prevent a signer from re-litigating a block already finalized has no effect on the signer's outward behavior (network broadcast) or on downstream vote-tallying functions (`handle_block_rejection`, `handle_block_signature`) — only on the persisted `state` enum field, which these downstream functions do not gate on before acting.

### Impact Explanation
This maps to "a rejection recounted as an accept" / miscounted-response class from the rules: a signer can emit a `Reject` for a block it (or the network) already marked `GloballyAccepted`, or emit an `Accepted`/signature for a block already `GloballyRejected`, purely because the in-memory guard's `Err` path is swallowed. Peers receiving a late `Rejected` for an already globally-accepted block feed it into their own `handle_block_rejection`/tally logic (`stacks-signer/src/v0/signer.rs`, "OLD"/"KNOWN" handling documented in `docs/signer-flows.md:349-388`), which is designed to assume any observed response reflects the sender's current, valid state — this assumption is violated here.

### Likelihood Explanation
This is reachable by ordinary races that a single "one-slot" miner + gossip timing can produce without needing a majority of signers or another signer's key: a block reaching global acceptance (via a `NewBlock` event or an observed 70% signature set) concurrently with a late pre-commit-threshold re-evaluation or a delayed `BlockValidateOk` response landing on the same `BlockInfo` — both are ordinary paths already covered by the existing timing-heavy tests in this area (`stacks-signer/src/v0/tests.rs`), showing races here are a normal occurrence, not a contrived edge case.

### Recommendation
At each of the three call sites (`stacks-signer/src/v0/signer.rs:1345-1365`, `1466-1478`, `1946-1959`), the block/return path following a failed `mark_locally_rejected`/`mark_locally_accepted` must be gated on the transition actually succeeding: if `move_to` returns `Err` because the block has already reached consensus, the function should return early without inserting the stale response, without invoking `handle_block_rejection`/`handle_block_signature`, and without sending a `send_block_response` that contradicts the already-finalized `state`.

### Proof of Concept
1. Signer tracks block B, currently `PreCommitted`/`LocallyAccepted`, awaiting pre-commit-threshold evaluation.
2. Before `handle_block_pre_commit`'s post-threshold `check_block_against_signer_db_state` re-check runs, block B is observed to reach `GloballyAccepted` (e.g., via a `NewBlock` node event calling `mark_globally_accepted`, as seen in `stacks-signer/src/chainstate/mod.rs:462-476`).
3. The pending pre-commit evaluation now finds the chainstate re-check fails (e.g., a conflicting sibling shows up) and calls `block_info.mark_locally_rejected()` at `stacks-signer/src/v0/signer.rs:1355`; this returns `Err` since `check_state` blocks `GloballyAccepted -> LocallyRejected`.
4. Because `has_reached_consensus()` is true, no warning is logged, but the function still proceeds to `handle_block_rejection` and `send_block_response(&block_info.block, block_rejection.into())`, broadcasting a `Rejected` for a block that is (and must remain) `GloballyAccepted`.

Given the depth of the surrounding logic (`conflict_still_blocks`, `reorg_permit_stands`, `get_signed_conflicts`) and lack of direct filesystem access to re-run these tests, I was not able to execute a concrete runtime PoC confirming the exact downstream consequence for a receiving peer's tally state; this analysis is based on static code reading of the cited call sites and their control flow.

    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
