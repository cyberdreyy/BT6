### Title
Loss-adjusted withdrawal haircut can be bypassed because `requestWithdraw` only validates the last request epoch - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Django bug class — validating only the last item of a multi-item submission — maps directly onto `IdleCreditVault.requestWithdraw`, which checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` for a pending loss-adjusted receipt. `lastWithdrawRequest` is a single slot that only remembers the most recent request epoch, while `withdrawsRequests`/`withdrawsRequestsByEpoch` can hold receipts across multiple epochs. If a loss is applied to pending receipts under an epoch key different from the user's last request epoch, the guard at `requestWithdraw` reads the wrong key, lets the user file a new request that overwrites `lastWithdrawRequest`, and the haircut receipt is then claimed at par through `_claimFundedWithdrawRequest`.

### Finding Description
In `requestWithdraw` (`IdleCreditVault.sol:243-295`), before opening a new receipt the contract verifies that the user's previous receipt does not carry a pending loss haircut:

```
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (
  lossRecoveryPrice != 0 &&
  (withdrawsRequestsByEpoch[_user][lossEpoch] != 0 ||
  (apr0Users[_user].principal != 0 && apr0Users[_user].principalEpoch == lossEpoch))
) { revert NotAllowed(); }
```

and the same single-epoch lookup drives the claim path in `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:789-801`):

```
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

Meanwhile `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`) stores the haircut under the *current* `epochNumber`, which is the epoch in which the underfunded `stopEpochWithDuration` runs — not necessarily the epoch of any given user's request:

```
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
pendingWithdraws = 0;
```

`pendingWithdraws` is an aggregate across all epochs' receipts, so a loss at epoch N's `collectWithdrawFunds` can cover receipts requested in epochs ≤ N. A user whose `lastWithdrawRequest` is M < N will have `lossRecoveryPriceByEpoch[M] == 0`, so:

1. The `requestWithdraw` guard passes even though their pending receipts were just haircut at key N.
2. Their new request at epoch N (or N+1) overwrites `lastWithdrawRequest`, permanently orphaning the loss key.
3. `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` reads the stale slot → returns 0 → falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` (the full multi-epoch aggregate) at par via `_transferFundedClaim` (`IdleCreditVault.sol:319-350, 897-907`).

The code comments themselves confirm the single-slot design is load-bearing: "A loss-adjusted receipt must be claimed before opening a later request, otherwise `lastWithdrawRequest` would stop pointing to the epoch that stores its haircut" — but the guard only tests the *last* slot, exactly the "only the last uploaded file was validated" shape.

### Impact Explanation
The strategy only received `pendingBasis * lossRecoveryPrice / RECOVERY_FULL` underlying for those receipts. A bypassing user claims at par, draining the funded claim pool so later claimants (who did take the haircut) receive less than their loss-adjusted entitlement or revert on insufficient balance — direct theft of other users' withdrawal proceeds, quantified as `(receipts * (1 - lossRecoveryPrice))` per bypassing request. Under the standard loss-sharing invariant this shortfall is socialized onto remaining claimants.

### Likelihood Explanation
Requires a `stopEpochWithDuration`/`collectWithdrawFunds` underfunding event and an attacker holding pending receipts whose request epoch differs from the epoch key where the loss was recorded. Both are within normal protocol operation (borrower underfunding is an intended loss path), and the attacker only needs to be a tranche holder making ordinary `requestWithdraw`/claim calls. The attacker's marginal step — filing one additional request after the loss instead of claiming — is unprivileged.

### Recommendation
Key the pending-loss check on all of the user's request epochs, not just `lastWithdrawRequest`. Concretely: revert in `requestWithdraw` whenever `pendingWithdraws` was cleared with a loss for any epoch in which the user holds receipts (e.g., iterate or store a per-user loss-epoch bitmap), or record the haircut under every contributing request epoch in `collectWithdrawFunds`. Alternatively, settle/claim existing receipts atomically inside `requestWithdraw` before opening a new one whenever any loss key is non-zero.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Setup: user deposits, epoch running (epochNumber = N-1 boundary)
// 1. user calls CDO.requestWithdraw -> vault.requestWithdraw at epoch N-1
//    -> withdrawsRequestsByEpoch[user][N-1] = amt, lastWithdrawRequest[user] = N-1,
//       pendingWithdraws += amt
// 2. manager calls stopEpochWithDuration with loss; borrower funds only
//    partial amount -> collectWithdrawFunds(partial) at epochNumber = N:
//       lossRecoveryPriceByEpoch[N] = partial*RECOVERY_FULL/pendingBasis
//       pendingWithdraws = 0
// 3. Attacker key step: vault.requestWithdraw for user again (epoch N+1 buffer)
//    guard reads lossRecoveryPriceByEpoch[N-1] == 0 -> no revert
//    lastWithdrawRequest[user] overwritten to N+1
// 4. claimWithdrawRequest:
//    _claimLossAdjustedWithdrawRequest reads key N+1 -> 0 -> skips haircut
//    _claimFundedWithdrawRequest pays withdrawsRequests[user] at par
// Assert: user received full receipt amount while strategy only held
// haircut-funded underlying; second user claiming same epoch is underpaid.
```

Caveat: I could not fully verify the exact `epochNumber` value at `collectWithdrawFunds` time relative to the request epoch (it depends on when `deposit()` increments `epochNumber` inside `IdleCDOEpochVariant._afterStopEpochWithDuration`, which was not fully read). If the loss key always equals the request epoch, the specific path above narrows, but the single-slot guard remains fragile whenever a user's receipts span epochs where any loss key is set on a non-last epoch.
