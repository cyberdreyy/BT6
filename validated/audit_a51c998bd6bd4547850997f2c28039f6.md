### Title
Stale confirmations from removed multisig members allow request execution below the configured signature threshold - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` (and its `multisig` v1 counterpart, `DeleteKey`) only purges pending requests that were *created* by the removed member. It never removes that member's *confirmations* on requests created by other members. Because `confirm()` only compares the raw size of the confirmations set to `num_confirmations`, a stale confirmation from a member who has since been removed still counts toward the threshold. This breaks the intended equality `live confirming members == num_confirmations` and lets a request execute with fewer currently-authorized signers than required.

### Finding Description
`confirm()` accepts a request when `confirmations.len() as u32 + 1 >= self.num_confirmations`, treating every entry stored in the `confirmations: LookupMap<RequestId, HashSet<String>>` map as an equally valid, currently-authorized signature: [1](#0-0) 

When a member is removed via `DeleteMember`, `delete_member` cleans up:
- requests **created by** that member (`r.member == member`)
- that member's `num_requests_pk` entry
- the member's access key (if key-based)

but it does **not** scan `confirmations` for other pending requests (created by different members) where the removed member had already recorded a confirmation: [2](#0-1) 

The same gap exists in the `multisig` v1 contract's `DeleteKey` action, which likewise only removes requests where `r.signer_pk == pk` (the deleted key's own requests), leaving that key's confirmations on other requests intact: [3](#0-2) 

Consequently, a confirmation recorded while an account was a legitimate member remains "live" in the confirmations set forever, even after that account has been formally revoked from the multisig. This is structurally the same class of bug as the reported issue: the contract enforces authorization based on presence in a persisted collection (`confirmations` / `permission_list`) rather than binding that authorization to the *current* live configuration (the `members` set / owner list at execution time).

### Impact Explanation
This breaks the core K-of-N custody invariant of the multisig: `confirmations.len() >= num_confirmations` is supposed to imply "K currently-authorized members approved this," but it can be satisfied with only K-1 live members plus one stale confirmation from a removed member. Since `execute_request` can perform `Transfer`, `AddKey`/`AddMember`, `DeployContract`, or arbitrary `FunctionCall` actions, this allows a coalition smaller than the configured threshold to move funds, add new keys/members, or upgrade the contract — matching the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
This requires no external or unprivileged attacker action beyond normal multisig lifecycle events that are expected to happen routinely: a member confirms a pending request, and later that same member is removed (e.g., because they left, were compromised, or their key was rotated) while other requests they had confirmed are still outstanding. Removing a member and having unconfirmed/outstanding requests coexist is a normal, foreseeable operational sequence, not an edge case requiring privileged escalation — the bug itself, not any additional privilege, is what causes the threshold bypass.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over all outstanding requests' `confirmations` sets and strip any entry belonging to the removed member/key, in addition to removing requests the member authored. Alternatively, recompute the confirmation count at execution time by intersecting the stored confirmations set with the current `members` set (or list of valid keys) before comparing against `num_confirmations`, so stale confirmations from removed signers can never count toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]` and `num_confirmations = 2`.
2. `A` calls `add_request` to create a sensitive request `R` (e.g., `Transfer` or `AddKey`) — `confirmations[R] = {}`.
3. `B` calls `confirm(R)` — since `0 + 1 < 2`, it is stored: `confirmations[R] = {B}` (not yet executed).
4. Members `A` and `C` jointly execute a `DeleteMember { member: B }` request (through the normal 2-of-3 process) because `B`'s key was compromised or `B` left. `delete_member` runs [4](#0-3)  which only removes requests **created by** `B` — it does not touch `confirmations[R]`, which still contains `B`.
5. `A` now calls `confirm(R)`. In `confirm()`, `confirmations.len()` is still `1` (from stale `B`), so `1 + 1 >= 2` is true and `R` executes immediately [5](#0-4) .
6. Result: request `R` executed with only one currently-live member (`A`) actually approving it, even though `num_confirmations = 2` and `B` was already revoked — the K-of-N invariant is violated.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
