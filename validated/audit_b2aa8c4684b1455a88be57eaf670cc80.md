### Title
External-Initiator credential for job A can trigger a pipeline run on any job ID B due to missing job-EI binding check - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` decides whether a caller may trigger a run for an integer job `:ID` solely by checking `auth.GetAuthenticatedUser(c) != nil` (`isUser`). Because `AuthenticateExternalInitiator` injects a synthetic `run`-role `User` into the same session key used by real users, any successfully authenticated External-Initiator (EI) credential satisfies `isUser` and can call `RunJobV2` for an attacker-supplied job ID with no verification that the EI is associated with that specific job.

### Finding Description
The middleware `AuthenticateExternalInitiator` sets **both** `SessionExternalInitiatorKey` and `SessionUserKey` on successful EI authentication, assigning the pseudo-user a `run` role: [1](#0-0) 

`RequiresRunRole` only asserts that *some* authenticated identity with at least `run` privilege exists in the request context — it does not distinguish between a genuine EI/user identity and check any binding to the target job: [2](#0-1) 

In `PipelineRunsController.Create`, the code comments state that "only users are allowed to run jobs using int IDs — EIs not allowed," and gates that behavior on `isUser`: [3](#0-2) 

However, `isUser` is derived from `auth.GetAuthenticatedUser(c)`, which simply reads the `SessionUserKey` context value set by *either* `AuthenticateBySession`/`AuthenticateByToken` for a real user *or* `AuthenticateExternalInitiator` for any valid EI credential: [4](#0-3) 

Because the fake `run`-role user object set for EIs is indistinguishable from a real user session at this call site, an EI credential belonging to job A satisfies the `isUser` branch and can supply an arbitrary integer `:ID` in the path — there is no check that this EI is the one configured on that job's `ExternalInitiatorWebhookSpec`. `RunJobV2` is then invoked directly with the attacker-controlled `jobID`, with no ownership/binding validation performed anywhere in this call chain.

### Impact Explanation
An attacker holding valid EI credentials scoped to one job (job A) can trigger pipeline runs on any other job in the node by integer ID (job B), as long as job B accepts runs via the int32-ID path. This is an authorization/request-binding bypass allowing an attacker to execute another user's/job's pipeline — potentially causing unintended on-chain transactions, VRF fulfillments, or other side effects tied to job B's pipeline, matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Exploitability requires only possession of any valid EI credential (access key/secret) for some job on the node — not admin or edit privileges, and not knowledge of job B's own EI secret. The job ID enumeration space is small (sequential integers), making the attack straightforward and repeatable. The primary caveat is that the webhook/UUID-keyed path is explicitly disabled (`job.ErrJobTypeRemoved`), so exploitability is confined to whatever job types are reachable via the integer-ID branch and depends on this being the same authenticated-route group (`userOrEI`) referenced in the question; I could not directly view the router.go route registration line for the POST route in this session to fully confirm the exact middleware chain (tool access ran out), so this should be verified against the live router registration before treating it as fully confirmed.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject external-initiator-authenticated requests from the integer-ID run path (check `auth.GetAuthenticatedExternalInitiator(c)` presence, not just `GetAuthenticatedUser`), or verify that the job's configured `ExternalInitiatorWebhookSpec` external initiator matches the authenticated EI identity before invoking `RunJobV2`.

### Proof of Concept
1. Create two webhook/EI-triggerable jobs, Job A and Job B, each with a distinct External Initiator (EI A / EI B) via `cltest.CreateExternalInitiatorViaWeb` and job specs referencing them, per pattern in `TestRunner_WebhookJobRemoved`: [5](#0-4) .
2. Send `POST /v2/jobs/<JobB.ID>/runs` (integer ID, not UUID) with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI A's credentials.
3. Assert that `resp.StatusCode` is `401`/`403` (expected secure behavior) vs. observing `200` with a `pipelineRun` resource for Job B's run (actual behavior if unpatched), confirming `isUser` incorrectly accepts the EI session and `RunJobV2(ctx, JobB.ID, nil)` executes without validating EI-to-job binding.

	obj, ok := c.Get(SessionUserKey)

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
