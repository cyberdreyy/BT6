### Title
Missing balance validation in relayer transfer path allows over-balance transaction submission - ([File: core/web/evm_transfer_controller.go])

### Summary
`EVMTransfersController.CreateWithRelayer` sends ETH/native token transfers through `relayer.Transact` without ever calling `ValidateEthBalanceForTransfer`, unlike `CreateEVMLegacy` which enforces this check when `AllowHigherAmounts` is false. Any run/edit-role credential holder that targets a chain resolvable only through `App.GetRelayers().Get()` (i.e., not present in `LegacyEVMChains()`) can submit a transfer with an `Amount` exceeding the source balance and have it forwarded to the relayer without the node-side safety check that exists on the legacy path.

### Finding Description
`Create` chooses the code path based on chain resolution: it first tries `getChain(tc.App.GetRelayers().LegacyEVMChains(), ...)`, and only if that fails does it fall back to `tc.App.GetRelayers().Get(...)` and call `CreateWithRelayer` [1](#0-0) .

`CreateEVMLegacy` conditionally invokes `ValidateEthBalanceForTransfer(c, chain, tr.FromAddress, tr.Amount, tr.DestinationAddress)` whenever `tr.AllowHigherAmounts` is false, returning `422 Unprocessable Entity` if the balance (plus estimated gas) is insufficient [2](#0-1) .

`CreateWithRelayer`, by contrast, only fetches chain info and immediately calls `relayer.Transact(c.Request.Context(), tr.FromAddress.String(), tr.DestinationAddress.String(), tr.Amount.ToInt(), !tr.AllowHigherAmounts)` — there is no call to `ValidateEthBalanceForTransfer` or any equivalent pre-check at the controller layer at all [3](#0-2) . The function's own doc comment acknowledges the asymmetry: "As opposed to CreateEVMLegacy, it just sends the transaction without verifying its success" [4](#0-3) .

The `!tr.AllowHigherAmounts` boolean is passed to `relayer.Transact`, meaning any balance/amount enforcement for the relayer path is delegated entirely to the relayer/LOOP plugin implementation (`loop.Relayer` interface), outside the node's own controller-level validation logic that exists for legacy chains. Whether that check is actually performed depends entirely on the specific relayer plugin's implementation, which is not guaranteed to mirror `ValidateEthBalanceForTransfer`'s logic (gas-inclusive cost estimate via `chain.GasEstimator().GetMaxCost`).

### Impact Explanation
For relayer-only (non-legacy) chains, a request with `Amount` greatly exceeding the actual balance is submitted directly to `relayer.Transact` without the node performing its own balance sufficiency check. This removes a safety net that legacy chains have, and — depending on how strict the specific relayer implementation's own internal checks are — may result in the node broadcasting/attempting a transaction whose failure or side effects (e.g., stuck pending nonce, wasted gas reservation, unexpected txmgr state) were meant to be pre-empted by the API layer. This maps to the "unauthorized/unsafe fund movement" impact class since a financial safety guard that is enforced for one supported chain family is silently absent for another, for what should be functionally equivalent transfer requests.

### Likelihood Explanation
Requires only a valid run-role/edit-role API credential (no admin/operator access) and a target `evmChainID` that resolves via the relayer path rather than `LegacyEVMChains()`. The request is a single `POST /v2/transfers` call with attacker-controlled `Amount` and `AllowHigherAmounts` fields, matching normal API usage patterns and requiring no special timing or race condition — fully repeatable per relayer-backed chain.

### Recommendation
Add an equivalent balance/cost validation step in `CreateWithRelayer` before calling `relayer.Transact` when `!tr.AllowHigherAmounts`, using relayer-exposed balance/gas-estimation APIs (or extend the `loop.Relayer` interface to expose a comparable validation call), so both code paths enforce the same financial safety invariant regardless of legacy vs. relayer chain resolution.

### Proof of Concept
1. Extend `core/web/evm_transfer_controller_test.go`'s relayer-path tests (alongside `TestTransfersController_CreateSuccess_From_WithRelayer`) with a new test `TestTransfersController_CreateWithRelayer_InsufficientBalance`.
2. Configure the mocked relayer (`core/web/testutils/mock_relayer.go` / `core/web/mocks/relayer.go`) to represent an account with balance `0` or far below `Amount`, without configuring the mock to reject the call.
3. Issue `POST /v2/transfers` with a run-role authenticated session, `evmChainID` set to a chain absent from `LegacyEVMChains()` (forcing relayer resolution), and `Amount` set far above any plausible balance, `AllowHigherAmounts=false`.
4. Assert that `relayer.Transact` mock is invoked (`mock.AssertCalled(t, "Transact", ...)`) and that no equivalent of `ValidateEthBalanceForTransfer` was exercised, and that the HTTP response is `200/201` (transaction accepted) rather than `422 Unprocessable Entity`, contrasting with the equivalent legacy-chain test that returns 422 for the same insufficient-balance scenario.

func (tc *EVMTransfersController) CreateWithRelayer(c *gin.Context, relayer loop.Relayer, tr *models.SendEtherRequest) {
	info, err := relayer.GetChainInfo(c)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	cid, ok := new(big.Int).SetString(info.ChainID, 10)
	if !ok {
		jsonAPIError(c, http.StatusInternalServerError, fmt.Errorf("could not parse chain ID: %s", info.ChainID))
		return
	}

	err = relayer.Transact(c.Request.Context(), tr.FromAddress.String(), tr.DestinationAddress.String(), tr.Amount.ToInt(), !tr.AllowHigherAmounts)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}
