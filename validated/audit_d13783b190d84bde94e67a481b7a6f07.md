### Title
Post-default withdraw receipts pay 1:1 from `defaultRecoveryReserve`, draining funds reserved for defaulted-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the ActiveMQ bug where an unvalidated length field causes a payload to be re-interpreted as additional packets, `IdleCreditVault.requestWithdraw` accepts new withdraw receipts **after** `defaultRecoveryFinalized` without adding them to the finalized claim basis, yet `claimWithdrawRequest` later pays them 1:1 out of `defaultRecoveryReserve` — a reserve sized only to cover the pre-default `totalBasis` at `defaultRecoveryPrice`. Every post-default claim is therefore an unbudgeted draw on the recovery reserve.

### Finding Description
In `IdleCreditVault.finalizeDefaultRecovery`, the recovery reserve is fixed as `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and the payout ratio as `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis` covers only active LPs plus pending receipts at finalization [1](#0-0) . After finalization, `requestWithdraw` still lets any tranche holder create a receipt: it burns the CDO's strategy tokens, mints `_amount` receipt tokens to the user, and records `postDefaultRequests[_user] = _amount` — without increasing `pendingWithdraws`, `defaultRecoveryReserve`, or pulling any underlying [2](#0-1) . On claim, `_claimPostDefaultWithdrawRequest` burns the receipt and calls `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` and transfers the full amount [3](#0-2) [4](#0-3) . Since post-default claims were never part of `totalBasis`, their 1:1 payouts consume reserve that belongs to defaulted-epoch claimants.

### Impact Explanation
Direct theft / permanent freezing of unclaimed recovery. The reserve can pay at most `totalBasis * defaultRecoveryPrice` in aggregate. Each post-default claim of `x` leaves `defaultRecoveryReserve` short by `x`, so once the excess draws exceed the rounding slack, subsequent defaulted-epoch claims (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) revert on `defaultRecoveryReserve -= _amount` underflow or insufficient balance — last-in-rightful claimants permanently lose their recovery. An attacker holding tranches post-default extracts recovery value ahead of legitimate claimants. Loss is bounded by total post-default request volume but can equal the whole reserve if enough tranche supply is cycled through requests.

### Likelihood Explanation
Medium. Requirements: pool defaulted and `finalizeDefaultRecovery` executed with a positive reserve; attacker holds tranche tokens (any holder qualifies, no privilege needed); `claimWithdrawRequest` remains callable (no epoch gating on the post-default path, and `_claimFundedWithdrawRequest`'s `epochNumber <= lastWithdrawRequest` check is bypassed because `postDefaultRequests` is paid first and returns early) [5](#0-4) . Post-default tranche prices are haircutted, so the attacker merely converts cheap tranches into full-value reserve claims — economically self-funding. The only mitigating factor is that the CDO passes a haircut-priced `_amount`, so per-request drain equals the receipt's fair value, but it is still pure reserve leakage.

### Recommendation
Either fund post-default claims separately (transfer `_amount` underlying from the CDO/borrower into the strategy at request time or credit them against future repayments), or pay them through `_transferFundedClaim` with the reserve guard instead of `_transferDefaultRecovery`. Alternatively, include post-default requests in a running adjustment of `defaultRecoveryPrice`/`defaultRecoveryReserve` so each new claim re-prices rather than silently overdraws the reserve.

### Proof of Concept
Foundry fork sketch:

```solidity
// Setup: vault with borrower, epoch running, AA + BB deposits.
// 1) Borrower defaults -> cdoEpoch._handleBorrowerDefault() path; manager calls
//    finalizeDefault with recoveredAmount R, so strategy.finalizeDefaultRecovery
//    sets defaultRecoveryReserve = R, defaultRecoveryPrice < 1e18.
// 2) Attacker (KYC'd tranche holder, still holds trancheAmount):
uint256 trancheBal = AAtranche.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.requestWithdraw(trancheBal, address(AAtranche)); // mints postDefault receipt
// 3) Claim pays 1:1 out of the default recovery reserve:
uint256 reservePre = strategy.defaultRecoveryReserve();
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();
// assert attacker received postDefaultRequests amount at par
// assert strategy.defaultRecoveryReserve() == reservePre - claimedAmount
// 4) A defaulted-epoch claimant now reverts (reserve underflow/insufficient balance)
//    or is paid less than claimBasis * defaultRecoveryPrice.
```

Key assertions: `strategy.postDefaultRequests(attacker) > 0` while `defaultRecoveryReserve` was unchanged at request time, and the claim decrements the reserve dollar-for-dollar despite the request never entering `totalBasis`.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.

  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
