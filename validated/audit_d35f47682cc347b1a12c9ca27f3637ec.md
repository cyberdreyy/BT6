### Title
`check_parent_tenure_choice` reorg-timing heuristic is gamed by a miner who delays proposing its own tenure's sole block, letting it self-reorg away that tenure - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a reorg of a prior tenure is permitted by comparing `sortition_state_received_time - local_block_info.approved_time` against `first_proposal_burn_block_timing`, where `approved_time` is stamped locally by each signer the moment it pre-commits/accepts a proposal. Because the miner fully controls when it broadcasts that proposal to signers, a miner who wins two consecutive slots can artificially delay sending the sole block of its own first tenure until just before it wins the next slot, satisfy the timing test, and get signers to sanction (`mark_tenure_superseded`) a reorg of its own, otherwise legitimate, tenure.

### Finding Description
The check lives in `check_parent_tenure_choice` [1](#0-0) . For each reorged tenure with more than one globally accepted block, the reorg is always refused [2](#0-1) . Otherwise, for a tenure with exactly one mined block, the code fetches that block's local record and computes:

```
proposal_to_sortition = sortition_state_received_time - local_block_info.approved_time
if Duration::from_secs(proposal_to_sortition) < first_proposal_burn_block_timing { allow reorg }
``` [3](#0-2) 

`approved_time` is not a chain-observed or miner-chosen timestamp — it is stamped by *this signer* at the moment it pre-commits or locally accepts the proposal (`get_epoch_time_secs()` at receipt time), whichever happens first: `mark_pre_committed` / `mark_locally_accepted` [4](#0-3) . Since the value is set at receipt of the proposal by the signer, and the proposal is only sent when the miner (proposer) decides to broadcast it, the miner directly controls how "late" this timestamp reads relative to `sortition_state_received_time` for the *next* tenure.

The intended semantics (documented in `sample/conf/signer/mainnet-signer-conf.toml`) are: "if the previous tenure's first block arrived shortly before the sortition, forgive a reorg because the incoming miner had no time to RBF an outdated commit." This is designed for a *different, unrelated* incoming miner racing a stale block-commit against a genuinely-late first block from a *different* prior miner. Nothing in `check_parent_tenure_choice` verifies that the reorging tenure's miner differs from the reorged tenure's miner, and nothing anchors the timing measurement to anything the proposer cannot control.

Attack: as a single unprivileged party with normal BTC mining power (able to win a slot), the attacker:
1. Wins tenure T's sortition, mines exactly one block, but deliberately withholds broadcasting its `BlockProposal` to signers until shortly before the burn block that starts the next tenure is expected (or received) — well within the current `first_proposal_burn_block_timing` window. Signers still accept/sign the late-arriving proposal (it is not itself invalid), and it becomes globally accepted.
2. If/when the attacker also wins the next sortition (a legitimate single-slot BTC win, not requiring signer collusion), it crafts a `BlockProposal`/tenure-change whose `parent_tenure_id` skips T, i.e., reorgs T.
3. `check_parent_tenure_choice` computes `proposal_to_sortition` using the deliberately-late `approved_time` from step 1, finds it below `first_proposal_burn_block_timing`, permits the reorg, and calls `mark_tenure_superseded`, which suppresses any of this signer's prior signature on T's block as a future conflict [5](#0-4) .

This is reachable through the exact same code path the tests exercise (`reorg_timing_testing` in `chainstate/tests/v1.rs` and `chainstate/tests/v2.rs`), which only vary the raw `sortition_timing_secs` gap and never model "who proposed" nor "who controls approved_time" [6](#0-5) .

Existing guards do not close this:
- The "more than one globally accepted block" guard only blocks tenures with ≥2 accepted blocks; a single-block tenure remains reachable [2](#0-1) .
- The honest-miner relayer code that avoids self-reorging via a stale commit (`ContinueTenure` instead of `BeginTenure`) is client-side, non-adversarial miner behavior, not a signer-side security control — an attacker's custom miner is not bound by it [7](#0-6) .
- Node-side `check_nakamoto_tenure` only checks structural ordering of consensus hashes/heights for a `BlockFound` tenure change, not whether the same signer set was gamed on timing [8](#0-7) ; this consensus-acceptance layer is explicitly out of scope as "the flaw itself," but note it provides no defense against the signer-side timing manipulation described here.

### Impact Explanation
Signers sign a tenure-change block that reorgs a tenure whose single block had already reached global acceptance — i.e., signers sign a conflicting/non-canonical replacement for a tenure that was not actually poorly timed in any legitimate, race-condition sense, but was made to *appear* poorly timed solely by the same miner's own choice of when to submit its proposal. This breaks the intended safety property that `check_parent_tenure_choice`'s permit reflects a genuine handoff race rather than the reorging party's own manipulation of the metric that grants the permit — a chain-safety violation (signer signing a conflicting block over a tenure it itself controlled and sabotaged the timing of). The attack is repeatable any time the same party wins two consecutive slots, which requires no signer collusion and no majority weight — only ordinary mining participation.

### Likelihood Explanation
Preconditions: the attacker needs to win one sortition (normal for any miner with nonzero BTC hash power), withhold its own proposal broadcast near the boundary (fully under its control, no privilege needed), and then win the immediately following sortition (probability proportional to mining share squared, but nothing stops the attacker from only acting on this play when it happens to occur naturally — cost is zero beyond normal mining, and the play can be attempted every time the attacker wins any tenure). This matches the specified threat model of an attacker who can "win a single miner slot with their own BTC and craft BlockProposals" with at most one signer's weight of "gossip," with no signer collusion. It is repeatable indefinitely.

### Recommendation
Do not use a purely local, proposer-influenced timestamp (`approved_time`) as the sole timing signal in `check_parent_tenure_choice`. At minimum:
- Reject the reorg outright when the reorging tenure's miner (`self.miner_pkh`) is the same as the reorged tenure's miner, since a same-miner "handoff race" is not the scenario the timing exception is meant to excuse.
- If the timing exception must remain for cross-miner races, anchor it to a value the proposer cannot control, e.g., the reorged tenure's own burn-view/sortition timestamp (`burn_header_timestamp`) or the time the reorged sortition's burn block was received by signers, rather than `approved_time`, which is only set once the proposer chooses to broadcast.

### Proof of Concept
Extend `reorg_timing_testing` (in `stacks-signer/src/chainstate/tests/v2.rs`, mirrored in `v1.rs`) to make the reorging and reorged tenures share the same `miner_pkh`, and drive `approved_time` independently of any "genuine" proposal time:

1. Build `last_sortition` (tenure T) and `cur_sortition` (tenure T+1) with identical `miner_pkh`/`miner_pubkey`, as in `setup_test_environment`.
2. Insert T's sole block into `signer_db` via `insert_block`, but set `approved_time` to a value close to `sortition_state_received_time` (simulating the attacker delaying its own proposal) while asserting this is inconsistent with a genuinely long-standing tenure (e.g., set `block.header.timestamp` or a wall-clock marker far earlier to represent the tenure's real age).
3. Call `cur_sortition.data.check_parent_tenure_choice(&mut signer_db, &client, &Duration::from_secs(N))` with the mocked `TenureForkingInfo` response marking T as having exactly one globally accepted block.
4. Assert: with same-miner reorging, the function still returns `Ok(true)` and `signer_db.is_tenure_superseded(&T_consensus_hash)` is `true` — proving the equality is violated: permission was granted based on the attacker-controlled `approved_time` rather than any timing gap the attacker could not have manipulated.
5. As a control, repeat with a genuinely early, non-manipulated `approved_time` (large real gap) and same-miner condition, and show the check *should* deny (per intended design) but currently does not check miner identity at all — both same-miner cases pass whenever `approved_time` is engineered close to the sortition boundary, regardless of the tenure's true age/activity.
