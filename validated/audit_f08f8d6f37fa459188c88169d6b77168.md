### Title
Stale reject weight is never reconciled when a signer later accepts the same block, letting `total_weight_rejected` and `total_weight_approved` double-count the same signer's weight and wedge block finalization - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` maintains two independent running-sum counters, `total_weight_approved` and `total_weight_rejected`, gated by two different guard sets (`gathered_signatures` for accepts, `responded_signers` for rejects) instead of a single per-signer "current vote" ledger. When a signer rejects a block and later legitimately re-evaluates to accept the same `signer_signature_hash` (a supported, miner-triggerable flow), its weight is added to `total_weight_rejected` on the reject and *also* added to `total_weight_approved` on the later accept, because the accept-path guard never checks `responded_signers`/prior reject state. This is the same bug class as the Ammplify `subtreeBorrowedX/Y` issue: an aggregate that is supposed to reflect one consistent state is updated incrementally along two independently-gated paths that never reconcile with each other, so the final totals depend on message order rather than the true current vote set.

### Finding Description
`BlockStatus` tracks weight with two separate accumulators: [1](#0-0) 

On `Accepted`, the weight is added only if the slot isn't already in `gathered_signatures`, and then the slot is inserted into both `gathered_signatures` and `responded_signers`: [2](#0-1) 

On `Rejected`, the weight is added only if the slot isn't already in `responded_signers`: [3](#0-2) 

Tracing the two possible orderings for the same signer and the same block hash:
- Reject → Accept: reject inserts the slot into `responded_signers` and adds weight to `total_weight_rejected`. The later accept checks only `gathered_signatures` (which is still empty for this slot), so it *also* adds the same signer's weight to `total_weight_approved`. The reject weight is never removed. Both counters now include this signer's weight simultaneously.
- Accept → Reject: accept adds weight to `total_weight_approved` and inserts the slot into `responded_signers`. The later reject checks `responded_signers`, which already contains the slot, so no reject weight is added — this direction is (correctly) idempotent.

So only one of the two orderings is safe; the other silently double-counts. This exactly mirrors the root cause pattern from the external report: a running aggregate is only updated/gated along one of its possible update paths, and the outcome is order-dependent rather than reflecting the true current state.

A signer transitioning from a local rejection to a local acceptance for the *same* block is an explicitly supported, common flow — the local signer state machine documents `LocallyRejected --> LocallyAccepted: re-evaluated`, driven by `should_reevaluate_block`/`should_reevaluate_reject_reason` when the miner re-sends or conditions change, entirely under the control of the block's own miner (no other signer's key or majority collusion needed): [4](#0-3) 

### Impact Explanation
`SignerCoordinator::wait_for_signatures` (the consumer of `BlockStatus`) checks the reject-blocking condition *before* the accept-threshold condition: [5](#0-4) 

Because a flipped signer's weight is never removed from `total_weight_rejected`, `total_weight_rejected` can remain permanently inflated by weight that has since moved to acceptance. This lets `total_weight_rejected.saturating_add(weight_threshold) > total_weight` become true even though the same weight is concurrently present in `total_weight_approved`, which may itself have already crossed the real 70% acceptance threshold. Since the rejection branch is checked first, the coordinator returns `SignersRejected` for a block that has, in reality, accumulated sufficient signature weight to be finalized — a liveness wedge on block production caused purely by stale, unreconciled aggregate state, not by any majority of malicious signers. This is directly triggerable by a single miner slot (by causing/observing the natural reject→accept re-evaluation on one or more signers) plus ordinary StackerDB gossip.

### Likelihood Explanation
The reject→accept transition for the same block hash is a normal, documented part of the signer's re-evaluation logic, not a contrived edge case, so this can occur without any signer misbehavior — simply from the natural timing of validation retries, chainstate re-checks, or miner re-proposals that a single miner slot can induce. No majority, no other signer's key, and no auth token is required.

### Recommendation
Track each signer's current vote in a single per-slot ledger (e.g., an enum `Accepted(weight)`/`Rejected(weight)` keyed by `slot_id`) and recompute `total_weight_approved`/`total_weight_rejected` from that ledger (or explicitly subtract the old contribution when a slot's vote changes), analogous to recomputing `subtreeBorrow` from `ownBorrow` plus children rather than incrementally mutating an aggregate that never reconciles across update paths.

### Proof of Concept
1. Signer S (weight w) sends `BlockResponse::Rejected` for hash H → `responded_signers` gains S's slot, `total_weight_rejected += w`.
2. S's local block info later re-evaluates to `LocallyAccepted` for the same H (supported re-evaluation flow) and S sends `BlockResponse::Accepted` for H.
3. In `handle` for `Accepted`, `block.gathered_signatures.contains_key(&slot_id)` is `false` (S never accepted before), so `total_weight_approved += w` is applied on top of the already-recorded `total_weight_rejected += w`.
4. `total_weight_approved + total_weight_rejected` now exceeds `total_weight` by `w`, and `wait_for_signatures`'s reject-first check can trip `SignersRejected` even while `total_weight_approved >= weight_threshold` is independently true, stalling block finalization despite real consensus having been reached.
