### Title
Web terminal session output bypasses buildlogger's mask/urlsanitizer/tokensanitizer chain, unlike job trace - (File: executors/docker/terminal.go, executors/docker/tty.go)

### Summary
`dockerTTY.Read` in `executors/docker/tty.go` reads directly from `hijackedResp.Reader` (the raw Docker exec TTY stream) and this is fed straight into `terminal.ProxyStream`/`terminal.NewStreamProxy` and out to the websocket client, with no pass through `buildlogger.Logger.wrap`'s writer chain (`tokensanitizer` → `urlsanitizer` → `masker`). Job trace output, by contrast, is always written through `buildlogger.Logger`, which applies these sanitizers before bytes reach GitLab's trace storage/UI.

### Finding Description
`terminalConn.Start` (`executors/docker/terminal.go:101-151`) creates a Docker exec session and wraps the resulting `client.HijackedResponse` in `dockerTTY` via `newDockerTTY(&resp)` (`executors/docker/tty.go:5-9`). `dockerTTY.Read`/`Write` (`executors/docker/tty.go:15-21`) operate directly on `hijackedResp.Reader`/`hijackedResp.Conn` — raw bytes from the container's TTY — with zero involvement of `t.logger` (`*buildlogger.Logger`) beyond a couple of `Debugln`/`Errorln` calls for connection-setup diagnostics. The stream is handed to `terminal.ProxyStream(w, r, dockerTTY, proxy)`, which is a bidirectional websocket-to-TTY proxy in the external `gitlab-terminal` package, and that package has no knowledge of or interface to Runner's masking primitives.

By contrast, normal job output flows through `buildlogger.Logger.wrap` (`common/buildlogger/build_logger.go:213-224`), which stacks `tokensanitizer.New` → `urlsanitizer.New` → `masker.New` before any bytes reach the trace sink. This is exactly the mechanism that redacts things like `?private_token=...`, `?x-amz-credential=...`, or `glpat-...`-prefixed tokens from job logs, as demonstrated by `common/buildlogger/internal/urlsanitizer/urlsanitizer_test.go` and `common/buildlogger/internal/tokensanitizer/token_masker_test.go`.

If a user in an interactive web terminal session runs `git remote -v` (exposing a masked `https://gitlab-ci-token:glpat-xxxx@...` remote URL) or dumps environment variables containing masked CI/CD variables, the raw secret value is written straight to the TTY and proxied unmasked to the websocket client. The same command's output, if it appeared in job trace (e.g., via a script step), would have been redacted by the sanitizer chain.

There are no existing checks in this path that stop this: `terminalConn.Start` never calls any of `l.wrap`, `masker.New`, `urlsanitizer.New`, or `tokensanitizer.New`.

### Impact Explanation
An attacker with access to the interactive web terminal (a feature explicitly gated behind project/job permissions in GitLab, but reachable by any user permitted to open a terminal session on their own job) can retrieve masked secrets/URLs (CI/CD job token, predefined masked variables that would otherwise be redacted, or S3/query-string style credentials matched by `urlsanitizer`) simply by causing them to be printed inside the terminal, bypassing the redaction that would apply to the same content in job trace logs. This is a sanitization-parity gap between two output channels for the same job/container.

### Likelihood Explanation
Feasibility is high and fully attacker-controlled: any job with the web terminal enabled (an opt-in runner/job feature) lets its author run arbitrary commands in the build container and read the resulting output over the websocket. No additional privilege beyond normal job/terminal access is required, and the behavior is deterministic and repeatable on every terminal session.

### Recommendation
Route terminal stdout/stderr bytes through the same `buildlogger` sanitizer writer chain (or an equivalent standalone `tokensanitizer`/`urlsanitizer`/`masker` pipeline configured with the job's `MaskPhrases`/`MaskTokenPrefixes`) before they are handed to `terminal.ProxyStream`, e.g. by wrapping `dockerTTY.Read`'s output (or inserting a filtering `io.Reader`/`io.Writer` between `dockerTTY` and the proxy) with the same masking writers used for `StreamWorkLevel`. Note that since terminal output is interactive/streamed byte-by-byte rather than line-buffered, this also requires verifying the sanitizers behave correctly under small/fragmented writes.

### Proof of Concept
Add a Go test in `executors/docker/` mirroring `TestTerminalConn_Start` (`executors/docker/terminal_test.go:237-333`): configure the mocked `ContainerExecAttach` to return a `bufio.Reader` whose content is a string containing a masked pattern (e.g., `http://example.com/?private_token=SECRET123`), have the test dial the websocket per `TestTerminalConn_Start`, and assert:
1. Read raw bytes from the websocket client side.

Assert `strings.Contains(receivedBytes, "SECRET123")` is `true` (proves leak) while a parallel test using `buildlogger.New(...).Stream(...)` on the identical input, asserting `strings.Contains(output, "SECRET123")` is `false` (proves trace sanitization would have redacted it) — the differential establishes the sanitization-parity gap. package docker

import "github.com/moby/moby/client"

func newDockerTTY(hijackedResp *client.HijackedResponse) *dockerTTY {
	return &dockerTTY{
		hijackedResp: hijackedResp,
	}
}

type dockerTTY struct {
	hijackedResp *client.HijackedResponse
}

func (d *dockerTTY) Read(p []byte) (int, error) {
	return d.hijackedResp.Reader.Read(p)
}

func (d *dockerTTY) Write(p []byte) (int, error) {
	return d.hijackedResp.Conn.Write(p)
}

func (d *dockerTTY) Close() error {
	d.hijackedResp.Close()
	_ = d.hijackedResp.CloseWrite()
	return nil
}

func (t terminalConn) Start(w http.ResponseWriter, r *http.Request, timeoutCh, disconnectCh chan error) {
	execConfig := client.ExecCreateOptions{
		TTY:          true,
		AttachStdin:  true,
		AttachStderr: true,
		AttachStdout: true,

	}

	exec, err := t.client.ContainerExecCreate(t.ctx, t.containerID, execConfig)
	if err != nil {
		t.logger.Errorln("Failed to create exec container for terminal:", err)
		http.Error(w, "failed to create exec for build container", http.StatusInternalServerError)
		return
	}

	execStartCfg := client.ExecAttachOptions{TTY: true}

	resp, err := t.client.ContainerExecAttach(t.ctx, exec.ID, execStartCfg)
	if err != nil {
		t.logger.Errorln("Failed to exec attach to container for terminal:", err)
		http.Error(w, "failed to attach tty to build container", http.StatusInternalServerError)
		return
	}

	dockerTTY := newDockerTTY(&resp)
	proxy := terminal.NewStreamProxy(1) // one stopper: terminal exit handler

	// wait for container to exit

	)

// wrap wraps the underlying writer with "filters". Order here somewhat
// matters, and the order they're instantiated in is the reverse order in which
// writes are processed, e.g. last added filter is the first to process data.
//
// order:
// - sync writer to ensure that multiple writes cannot happen concurrently
// - mask phrases (masker.New)
// - mask sensitive URL parameters (urlsanitizer.New)
// - mask secrets with a prefixed token (tokentanitizer.New)
// - split log lines and add timestamps (timestamper.New)
func (l *Logger) wrap(w io.WriteCloser, streamID int, streamType StreamType) io.WriteCloser {
	if l.timestamping {
		w = timestamper.New(w, timestamper.StreamType(streamType), uint8(streamID), true)
	}

	w = tokensanitizer.New(w, l.maskTokenPrefixes)
	w = urlsanitizer.New(w)
	w = masker.New(w, l.maskPhrases)
	w = internal.NewSync(w)

	return w
}
