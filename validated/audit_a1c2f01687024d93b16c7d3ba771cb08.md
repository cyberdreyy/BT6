## Finding: Stale per-txid rejection weight accumulates across rejection-timeout rounds in `StackerDBListenerComms::reset_rejections`

This is a direct structural analog of the reported Fenwick-tree bug: a *partial* reset leaves a subset of the accumulator state untouched, so weight from stale, no-longer-current voting rounds gets combined with weight from fresh rounds, producing an aggregated total that never corresponds to any single, verifiable set of currently-rejecting signers.

### Title
Per-txid rejection weight (`failed_txids`) survives `reset_rejections`, letting minority signer weight accumulate across retries into a false blocking-minority tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`BlockStatus::failed_txids` accumulates per-txid rejection weight guarded only by `responded_signers.insert(slot_id)` returning `true` [1](#0-0) . When the coordinator times out waiting for signatures/rejections, `reset_rejections` clears `responded_signers` and `total_weight_rejected` — but never touches `failed_txids` [2](#0-1) . This is structurally identical to the Fenwick-tree flaw: the "dirty" reset only clears some of the accumulator (here: the block-level rejection tally), leaving another dependent accumulator (`failed_txids`) unreset, so the same signer's weight is added again on every subsequent round.

### Finding Description
`get_block_status` in `signer_coordinator.rs` loops, polling `BlockStatus`, and on each rejection-timeout calls `self.stackerdb_comms.reset_rejections(block_signer_sighash)` before continuing to wait on the *same* block sighash [3](#0-2) . `reset_rejections` is documented as clearing rejections so the block can be "retried" [4](#0-3) , and it does reset `total_weight_rejected` and `responded_signers` — but it does not reset `block.failed_txids`.

Because the rejection-processing code only accumulates weight into `failed_txids[txid]` when `responded_signers.insert(slot_id)` is `true` (i.e., "first time this signer rejected in the current round") [5](#0-4) , clearing `responded_signers` on timeout re-arms that gate for the exact same signers. A minority of signers (with combined weight below the 30% blocking minority) that keeps rejecting the same block/txid across multiple rejection-timeout rounds will have their weight added to `failed_txids[txid].total_weight` again and again, while `total_weight_rejected` itself is correctly bounded per round.

When the block is eventually rejected (for any reason, in any round) via the `SignersRejected` branch, the miner reads the now-inflated `failed_txids` map and can permanently exclude a transaction:
```
if info.total_weight > blocking_minority {
    if info.problematic_weight > blocking_minority {
        permanently_excluded_txids.insert(txid.clone());
    }
    ...
}
``` [6](#0-5) 

The equality broken is "aggregated per-txid rejection weight" vs. "weight of the currently-rejecting, verified signer set": the aggregated number silently includes contributions from prior, already-superseded voting rounds, exactly as the Fenwick tree's un-reset indices 3, 5, 6 kept contributing to later deposits after a full withdrawal.

### Impact Explanation
A signer minority under the 30% blocking threshold — never a majority, and requiring no key compromise — can force a legitimate transaction to be `permanently_excluded_txids` by simply keeping the block proposal round alive across multiple `rejections_timeout` expirations (which the miner's own retry loop does automatically whenever any threshold isn't reached quickly). This lets a minority silently disable transaction inclusion for a specific `Txid` indefinitely, an outcome that should require the genuine 30%+ blocking-minority weight *within a single, current round of votes*, not an accumulation of the same minority's weight replayed round-over-round.

### Likelihood Explanation
High: this requires no majority, no coordination beyond a small minority of already-registered signers voting against the same transaction, and the retry path (`rejections_timeout` expiry -> `reset_rejections` -> resend) is a normal part of every block proposal that doesn't reach consensus quickly, so the accumulation condition is trivially reachable by any node operator running a subset of signer keys.

### Recommendation
`reset_rejections` should clear (or otherwise version/scope) `failed_txids` alongside `total_weight_rejected` and `responded_signers`, or `failed_txids` weight should be computed fresh per-round from the currently responded rejecting signers (mirroring how `compute_signature_signing_weight` in `stacks-signer/src/v0/signer.rs` recomputes weight from the live rejection-address set rather than an incrementally-accumulated counter) [7](#0-6) , so that only weight from the current, live voting round can count toward the blocking-minority threshold used for transaction exclusion.

### Proof of Concept
1. A minority set of signers M (combined weight < 30% of total) is configured/compromised to always reject block proposals citing the same `failed_txid` with `ValidateRejectCode::BadTransaction`/`ProblematicTransaction`.
2. Miner proposes block N containing the target transaction; M's weight is recorded into `block.failed_txids[txid]` (round 1) but is insufficient to reach `SignersRejected` (needs total_weight_rejected + weight_threshold > total_weight for the whole block, and separately blocking_minority for exclusion).
3. The overall block vote stalls (other signers slow/absent) until `rejections_timeout` expires; `reset_rejections` clears `total_weight_rejected` and `responded_signers` but leaves `block.failed_txids[txid].total_weight` at M's accumulated weight.
4. Miner resends the same proposal (same `block_signer_sighash`); M rejects again with the same `failed_txid`; because `responded_signers` was cleared, the `insert(slot_id)` gate is `true` again and M's weight is added a second time into `failed_txids[txid].total_weight`, now roughly 2x M's real weight.
5. Repeat step 3-4 enough times (a small number of timeout cycles) until `failed_txids[txid].total_weight` (and `problematic_weight`) exceeds the real `blocking_minority` (`total_weight - weight_threshold`), even though M's real weight never crossed 30%.
6. Once the block is eventually rejected for any reason in the `SignersRejected` branch, the miner reads the inflated `failed_txids` entry and adds the target `Txid` to `permanently_excluded_txids`, permanently censoring it from all future blocks in the tenure — achieved by a minority that never held real blocking-minority weight in any single round.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
