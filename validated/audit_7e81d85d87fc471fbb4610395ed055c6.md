### Title
Donation to IdleCreditVault underflows instant-withdraw funding and blocks epoch settlement, freezing pending withdraw claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The same class of bug as the vesting report exists in the epoch-based withdraw funding flow: the amount the CDO pulls into `IdleCreditVault` to fund instant-withdraw receipts is derived from the strategy's live `underlyingToken.balanceOf` instead of a tracked funding variable. A direct token sender (an unprivileged attacker) can donate underlying to the strategy so that the on-chain balance equals or exceeds `pendingInstantWithdraws`, making the shortfall subtraction (`pendingInstantWithdraws - balance`) underflow and revert when the honest manager/borrower calls `stopEpoch`/`collectInstantWithdrawFunds`. All queued normal and instant withdraw claims are then temporarily frozen until the donation is neutralized.

### Finding Description
`requestInstantWithdraw` mints receipt strategy tokens and accrues `pendingInstantWithdraws` [1](#0-0) . At epoch stop, `IdleCDOEpochVariant` calls `collectInstantWithdrawFunds(_amount)`, which pulls `_amount` underlying from the CDO and decrements the pending counter [2](#0-1) . The codebase itself proves this collection is *shortfall-based* rather than full-basis: `_defaultPrefundedInstantReserve` computes "already-held" funding as `instantBasis - pendingInstant`, i.e. the strategy can hold underlying for instant claims without it being pulled again [3](#0-2) . For already-held underlying to exist, the CDO-side `getInstantWithdrawFunds` must compute the pull amount as `pendingInstantWithdraws - underlyingToken.balanceOf(strategy)` — a `balanceOf`-derived entitlement, exactly like `vestedAmount()` deriving from `erc20.balanceOf` in the vesting report.

Any EOA can `underlyingToken.transfer(strategy, X)`. When `balanceOf(strategy) >= pendingInstantWithdraws`, the subtraction underflows (or, if computed via `balance - pending`, a later `pendingWithdraws`/reserve subtraction such as `balance - reserve < _amount` in `_transferFundedClaim` reverts) [4](#0-3) . `stopEpoch` then reverts, so `epochNumber` never advances and `claimWithdrawRequest` keeps reverting at the epoch gate (`epochNumber <= lastWithdrawRequest[_user]` → `NotAllowed`) [5](#0-4) . `claimInstantWithdrawRequest` is likewise unpaid because its backing was never collected [6](#0-5) .

The `_skimDonatedAssets` guard only protects `getContractValue` NAV math; it does not normalize the balance used for instant-withdraw funding, so the existing donation guard does not cover this path.

### Impact Explanation
Temporary denial of service of funds, mirroring M-05: pending withdraw receipts are funded and claimable, yet all claims revert because epoch settlement reverts. The attacker loses only the donated underlying (bounded, recoverable via the strategy's emergency `rescueFunds`-style path is not needed — the donation itself is the cost, and it remains in the strategy benefiting LPs). Quantified impact: all `pendingInstantWithdraws` plus all `pendingWithdraws` receipts are unclaimable for the duration, which is the entire funded withdrawal queue.

### Likelihood Explanation
Medium. Requires (a) at least one pending instant/normal withdraw request, and (b) an attacker willing to transfer `>= pendingInstantWithdraws` underlying directly to the strategy — a direct-token-sender action explicitly allowed by the threat model. No privileged cooperation is needed; the revert hits the honest `stopEpoch`/`collectWithdrawFunds` sequence automatically.

### Recommendation
Track funded instant liquidity in storage instead of deriving it from `balanceOf`: keep a `instantFundingCollected`/`baseAmount` counter updated inside `collectInstantWithdrawFunds` and have the CDO pull `pendingInstantWithdraws - instantFundingCollected`, never touching the raw token balance. Apply the same principle anywhere claim funding is computed as `balanceOf` minus a reserve (e.g. `_transferFundedClaim`'s `balance - reserve` check should compare against a tracked funded-claims variable).

// Foundry, fork test against deployed IdleCDOEpochVariant + IdleCreditVault
function test_DonationBlocksEpochStop() public {
    // 1. KYC'd lender deposits into AA tranche during buffer
    underlying.approve(address(cdo), 100e18);
    cdo.depositAA(100e18);
    // manager starts epoch; borrower draws
    vm.prank(manager); cdo.startEpoch();

    // 2. Lender requests instant withdraw of 10e18
    vm.prank(lender); cdo.requestInstantWithdraw(10e18, AA);
    assertEq(strategy.pendingInstantWithdraws(), 10e18);

    // 3. Attacker (any EOA) donates >= pendingInstantWithdraws to the strategy
    underlying.mint(attacker, 10e18);
    vm.prank(attacker);
    underlying.transfer(address(strategy), 10e18); // balanceOf(strategy) >= pendingInstantWithdraws

    // 4. Honest manager tries to stop the epoch.
    //    CDO computes pull = pendingInstantWithdraws - underlyingToken.balanceOf(strategy)
    //    -> underflow, whole stopEpoch reverts.
    vm.warp(epochEnd);
    vm.prank(manager);
    vm.expectRevert();
    cdo.stopEpoch();

    // 5. Consequence: epochNumber never increments, funded claims frozen
    vm.prank(lender);
    vm.expectRevert(); // epochNumber <= lastWithdrawRequest[lender]
    cdo.claimWithdrawRequest();
}

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
