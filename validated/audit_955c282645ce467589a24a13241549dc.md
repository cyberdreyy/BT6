### Title
Node-RPC-failure fallback in the same-tenure conflict check lets a signer sign a conflicting sibling block - (File: `stacks-signer/src/v0/signer.rs`, function `handle_block_pre_commit`)

### Summary
When a signer reaches the pre-commit threshold for a block that shares a `consensus_hash` (i.e. is in the *same tenure*) as a block it has already signed or accepted, it is supposed to ask the node whether that tenure's canonical tip is already at or past the new block's height before signing — this is the guard against signing two conflicting blocks in one tenure. If the RPC call to the node fails, the code does not fail safe: it logs a warning and falls through as if the tenure were "unconfirmed," letting the signature proceed.

### Finding Description
In `handle_block_pre_commit`, after the pre-commit threshold (≥70% weight) is reached, the signer re-derives whether a same-tenure conflict still blocks signing: [1](#0-0) 

If a fresh, unforgiven (`!reorg_permit_stands`) conflict shares the proposed block's `consensus_hash`, the code calls `stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash)` to check whether the node's canonical tip for that tenure is already ≥ the proposed height. On `Ok`, a tip at or above the proposed height correctly refuses to sign. But on `Err(e)` — an RPC failure/timeout/node-unreachable case — the code merely logs "Treating the tenure as unconfirmed" and continues past the `match`, straight into the branch that signs the block (`mark_locally_accepted(false)` and the subsequent broadcast of the signature).

This is inconsistent with the sibling check just above it in the same function (the cross-tenure/any-height conflict path), where an unreachable node in `conflict_still_blocks` explicitly resolves to *refuse to sign* (`HOLD1`), and with `get_sortition_by_burn_hash`'s "could not ask" branch, which also fails closed. Here, the same-tenure check fails open instead: a transient inability to reach the node is treated as evidence the tenure hasn't been built on yet, silently discarding the veto that a real (already-known) same-tenure conflict is supposed to provide. [2](#0-1) 

The documentation confirms this fail-open pattern is intentional elsewhere too ("`node unreachable` --> SIGN"), but applying it to the *same-tenure* stale-conflict check specifically removes the one guard meant to prevent a signer from putting a second, conflicting signature on a sibling block within a tenure it already helped finalize.

### Impact Explanation
This breaks the "one canonical, non-conflicting block per tenure/height" invariant enforced by the signer: the signer can end up producing a valid signature over a block that conflicts with one it already signed/accepted in the same tenure, purely because its `get_tenure_tip` RPC call to its own node errored at the wrong moment. That is a signer signing a conflicting block, which the assignment's rules classify as Critical impact.

### Likelihood Explanation
No majority of signers, no leaked keys, and no auth-token access is required — only a single signer instance experiencing an RPC hiccup on its own node/stacks-client call while already at pre-commit threshold for a same-tenure sibling block. A miner can readily create the conflicting-block precondition simply by proposing two sibling blocks in the same tenure/height in quick succession (normal miner behavior on reorg-adjacent races); the RPC failure window is not miner-controlled directly, but node RPC timeouts/restarts under load are common in production, making this a plausible, low-but-nonzero-probability trigger rather than a purely theoretical one.

### Recommendation
Make the same-tenure conflict check fail closed like its cross-tenure sibling: on `Err` from `get_tenure_tip`, refuse to sign ("hold") instead of treating the tenure as unconfirmed, mirroring the `conflict_still_blocks`/`get_sortition_by_burn_hash` "could not ask" branches that already default to `HOLD1`.

### Proof of Concept
1. Signer set reaches pre-commit threshold on block B, which conflicts (same `consensus_hash`) with a previously signed block A at the same tenure.
2. `reorg_permit_stands` returns false for the conflict (no sanctioned reorg).
3. `handle_block_pre_commit` calls `stacks_client.get_tenure_tip(consensus_hash)`; the call errors (timeout/connection issue with the signer's stacks-node).
4. Instead of refusing, execution falls through the `match`'s `Err` arm (only a warning is logged) and proceeds to `mark_locally_accepted(false)`, producing and broadcasting a signature over B — a block that conflicts with the already-signed A in the same tenure. [3](#0-2)
