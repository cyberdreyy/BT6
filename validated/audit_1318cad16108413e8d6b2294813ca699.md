### Title
Miner-side vote tally double-counts a signer that flips Reject→Accept, letting stale rejection weight combine with fresh acceptance weight past 100% - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener`'s `BlockStatus` tracks `total_weight_approved` and `total_weight_rejected` as separate running counters gated by two different membership sets (`gathered_signatures` and `responded_signers`). Because the Rejected-branch gate (`responded_signers.insert`) is a superset of what the Accepted-branch gate (`gathered_signatures.contains_key`) checks, a signer that first rejects and later legitimately re-evaluates to accept the same block has its weight added to `total_weight_rejected` and *also* added to `total_weight_approved`, with nothing ever subtracted from the rejected tally. This breaks the invariant that a signer's weight is counted toward at most one side of the vote, and the miner's `SignerCoordinator::get_block_status` (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) consumes these inflated, mutually-inconsistent counters directly to decide whether a block is accepted, rejected, or still pending.

### Finding Description
`BlockStatus` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:70-82`) holds:
- `responded_signers: HashSet<u32>` — slot ids that have sent *any* response
- `gathered_signatures: BTreeMap<u32, MessageSignature>` — slot ids that have sent an *acceptance*
- `total_weight_approved` / `total_weight_rejected` — running weight sums

On `BlockResponse::Rejected` (lines 486-591), weight is only added once, guarded by:
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
```
This correctly dedupes repeated rejections and — because `responded_signers.insert` is also called in the Accepted branch — correctly refuses to add rejection weight for a signer who *already accepted* (since their slot id is already in `responded_signers`).

On `BlockResponse::Accepted` (lines 386-485), the guard is different:
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```
This only checks `gathered_signatures`, not `responded_signers`. A signer who previously sent a `Rejected` response for this block populated `responded_signers` but never `gathered_signatures`. When that same signer later sends `Accepted` (a legal transition — the signer state machine explicitly allows `LocallyRejected --> LocallyAccepted : re-evaluated`, per `docs/signer-flows.md` §2/§3, driven by `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`), the Accepted branch's guard passes (slot id absent from `gathered_signatures`) and their weight is added to `total_weight_approved` — with `total_weight_rejected` never decremented for this signer.

The invariant the miner's decision logic implicitly relies on — that at any point `total_weight_rejected` and `total_weight_approved` reflect *current, mutually exclusive* votes and thus `total_weight_rejected + total_weight_approved ≤ total_weight` — is broken. This lets stale rejection weight from a signer who has since flipped to acceptance linger in `total_weight_rejected` indefinitely for that block.

### Impact Explanation
`SignerCoordinator::get_block_status` / the polling loop in `signer_coordinator.rs:509-545` acts directly on these two counters:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { ... })
} else if block_status.total_weight_approved >= self.weight_threshold {
    ... return Ok(...) // block accepted
}
```
Because the stale rejection weight from a since-flipped signer is never cleared, fewer *currently* dissenting signers are needed to cross the `total_weight_rejected + weight_threshold > total_weight` rejection trip-wire than the >30% blocking-minority guarantee assumes. A single signer changing its mind from reject to accept (a normal, protocol-sanctioned re-evaluation, requiring no majority, no key compromise, and no malicious behavior) permanently inflates the rejection side of the ledger for that block, which can cause the miner to treat a block as globally rejected (aborting it, excluding txids, forcing a re-mine) using an artificially inflated `total_weight_rejected` that no longer corresponds to any signer's live vote. This is a liveness wedge on block finalization driven purely by ordinary vote-flip traffic from one signer, matching the "miscounted response" / equality-break class (rejection weight recounted alongside acceptance weight instead of superseding it).

### Likelihood Explanation
Reject→Accept transitions on the same proposal are an explicit, documented, and reachable code path (`should_reevaluate_reject_reason`, `should_reevaluate_block`) — they exist precisely to let a signer recover from a rejection whose cause (e.g., stale parent, temporary node lag) no longer holds. Any single non-malicious signer that rejects then later accepts the identical block triggers this miscount; no coordination with other signers, no majority, and no protocol violation is required.

### Recommendation
Make the Accepted-branch weight-addition guard check `responded_signers` (not `gathered_signatures`) for whether the signer has already contributed weight to *either* side, and if the signer previously contributed to `total_weight_rejected`, subtract that weight before/while adding to `total_weight_approved` (or, simpler, track a single per-slot "current vote" map and always recompute `total_weight_approved`/`total_weight_rejected` from the current vote set rather than accumulating monotonically). This keeps `total_weight_rejected + total_weight_approved ≤ total_weight` as an actual invariant instead of an assumption.

### Proof of Concept
1. Miner proposes block B; `BlockStatus` for B starts with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight w) sends `BlockResponse::Rejected` for B (e.g., due to a transient `check_block_against_signer_db_state` failure). `stackerdb_listener.rs` Rejected-branch: `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`.
3. The condition that caused S's rejection clears (e.g., parent block catches up), and S's local signer, per `should_reevaluate_reject_reason`/`should_reevaluate_block`, re-validates B and now sends `BlockResponse::Accepted` for the same B.
4. Accepted-branch: `gathered_signatures.contains_key(S)` is `false` (S never previously accepted) → guard passes → `total_weight_approved += w`. `total_weight_rejected` is left untouched at its prior value including `w`.
5. Now `total_weight_rejected + total_weight_approved` includes `w` twice, i.e., exceeds what the live vote set actually supports; `total_weight_rejected` retains weight from a signer who no longer rejects the block, moving the rejection tally artificially closer to (or past) `self.total_weight.saturating_sub(self.weight_threshold)` in `signer_coordinator.rs`, independent of any other signer's action.
