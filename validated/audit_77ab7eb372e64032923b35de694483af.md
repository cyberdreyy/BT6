### Title
Multisig executes requests using stale confirmations from deleted members - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` only purges `self.confirmations` for requests that the deleted member *created* (filtered via `r.member == member` on `self.requests`), but never scans other requests' confirmation sets to strip entries matching the deleted member's serialized identity. Consequently, a request created by a still-active member and pre-confirmed by a member who is later deleted keeps that stale confirmation counted toward `num_confirmations`, allowing execution (including a `Transfer`) with fewer live, currently-valid confirming members than required.

### Finding Description
The binding that should hold is: `|{m ∈ self.members : m.to_string() ∈ confirmations[R]}| == num_confirmations` before `execute_request` fires. The code instead checks only `confirmations.len() + 1 >= self.num_confirmations` in [1](#0-0) , where `confirmations` is a raw `HashSet<String>` that is never revalidated against current membership.

Root cause is in `delete_member`: it removes confirmations only for requests whose *creator* (`r.member`) is the member being deleted, at [2](#0-1) , then unconditionally removes the member from `self.members` at line 374 [3](#0-2) . It never inspects `self.confirmations` values for *other* requests to strip out this member's confirmation string.

Exploit flow:
1. Member A creates request `R` (`Transfer{amount}` targeting `attacker_receiver`) via `add_request`.
2. Member B calls `confirm(R)` — since `num_confirmations=2`, this only inserts B into `confirmations[R] = {B}` at [4](#0-3)  (does not yet execute).
3. A separate `DeleteMember{member: B}` request is created and confirmed by A and C, executing `delete_member` and removing B from `self.members`. Because `r.member == member` only matches requests created by B, `R` (created by A) is untouched — `confirmations[R] = {B}` survives.
4. C calls `confirm(R)`. `assert_valid_request` only checks that the *caller* (C) is a current member [5](#0-4) ; it does not validate that existing entries in `confirmations[R]` still belong to `self.members`. `confirmations.len() (1, from B) + 1 >= num_confirmations (2)` is true, so `execute_request` fires, transferring funds to `attacker_receiver` on the strength of only one genuinely live confirmation (C's).

No existing guard (`assert_valid_request`, `assert_self_request`, `assert_one_action_only`) checks confirmer validity against current `self.members`; they only validate the request's existence and the caller's own membership.

### Impact Explanation
This lets an attacker-controlled `Transfer` request (or any other action) execute with only 1 genuinely live confirming member while `num_confirmations = 2`, directly moving NEAR out of the multisig account to a receiver never sufficiently authorized by currently active members — this matches "a multisig request executed below `num_confirmations` live members" under the Critical impact category. It is repeatable for any pre-confirmed-but-not-yet-executed request whenever a confirming (non-creating) member is later removed, and generalizes to any action type (`AddKey`, `FunctionCall`, etc.), not just transfers.

### Likelihood Explanation
Preconditions are realistic and do not require attacker privilege beyond being able to observe on-chain state: any existing multisig with ≥3 members and `num_confirmations` such that a member removal is legitimate (`members.len()-1 >= num_confirmations`) can hit this. The only requirement is ordinary contract-internal member churn (a member being removed, e.g., due to key rotation or offboarding) after that member confirmed but before the confirmed request was fully executed or deleted — a plausible administrative sequence, not an attacker-triggered precondition, but the result benefits whoever set the receiver on the pending request. Cost to trigger is just normal multisig transaction fees; no special access is needed once the stale confirmation exists.

### Recommendation
When deleting a member, iterate all entries in `self.confirmations` (not just requests created by that member) and remove the member's `to_string()` entry from every confirmation set. Alternatively, in `confirm`, filter/count only confirmations whose account/key is still present in `self.members` before comparing against `num_confirmations`.
