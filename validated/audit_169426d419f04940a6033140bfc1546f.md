### Title
Instant withdraw requests let an LPer frontrun a scheduled epoch loss and exit at par, concentrating the loss on remaining LPs — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a privileged settlement action whose effective take shrinks (or whose burden shifts) when unprivileged users redeem against a stale/relative basis before it executes. The idle-tranches analog is the epoch stop flow: `requestInstantWithdraw` crystallizes a user's claim at par (current tranche price) by burning CDO-held strategy tokens mid-epoch, while `_stopEpoch` refuses to run with `pendingInstantWithdraws != 0`. An attacker who anticipates a `stopEpochWithDuration(_lossAmount)` call can queue an instant withdrawal, forcing the honest manager to fund it at par via `getInstantWithdrawFunds` before the loss can be applied — so the full `_lossAmount` lands only on the remaining active LPs and normal pending receipts, and the attacker escapes their pro-rata share entirely.

### Finding Description
`IdleCreditVault.requestInstantWithdraw` burns `_amount` strategy tokens from the IdleCDO and mints a 1:1 receipt to the user, incrementing `pendingInstantWithdraws`, at the pre-loss value (strategy `price()` is fixed at `oneToken`) [1](#0-0) .

`IdleCDOEpochVariant._stopEpoch` (and therefore `stopEpochWithDuration`, the only path that applies `_lossAmount`) reverts with `NotAllowed` while `_pendingInstant() != 0` [2](#0-1) .

The only way to clear that bucket is `getInstantWithdrawFunds`, which pulls the full `pendingInstantWithdraws` amount from the borrower at par and calls `collectInstantWithdrawFunds` [3](#0-2) . `collectInstantWithdrawFunds` decrements the bucket by the full amount with no haircut mechanism — unlike `collectWithdrawFunds`, which records a `lossRecoveryPriceByEpoch` haircut when funded below basis [4](#0-3) .

When the loss is finally applied, `previewLossAdjustedWithdrawFunds` splits `_lossAmount` pro rata between `pendingWithdraws` (normal receipts) and the active basis only — funded instant receipts are excluded [5](#0-4) . The attacker then claims at par via `claimInstantWithdrawRequest` [6](#0-5) .

### Impact Explanation
This mirrors the reported bug exactly: redemptions (instant withdraws) executed before the settlement action shrink the loss-bearing base, so remaining LPs absorb a disproportionately large share of `_lossAmount`. The attacker's avoided loss equals `lossAmount * attackerBasis / (activeBasis + pendingBasis)`; that amount is transferred as excess loss to everyone else. In the extreme, an attacker holding a large fraction of TVL can dodge nearly their entire share. Additionally, the instant request acts as a griefing lever: any `stopEpoch`/`stopEpochWithDuration` reverts until the manager funds the queue, so the attacker can also delay the loss application (and the epoch transition) until repayment liquidity is arranged.

### Likelihood Explanation
Requirements: epoch running, attacker is a KYC'd LP holding tranche tokens, instant withdraws not disabled (`isProgrammableBorrower == false`, `disableInstantWithdraw == false`), and `block.timestamp < instantWithdrawDeadline` so the request is accepted and `getInstantWithdrawFunds` can later clear it. A manager-submitted `stopEpochWithDuration` carrying a loss is publicly visible in the mempool, and any externally observable borrower distress gives advance warning — identical to the "public slashing proposal" frontrun in the source report. The attacker risks nothing: worst case the request is funded at par as designed.

### Recommendation
Include pending instant withdrawals in the loss-bearing basis so they cannot escape at par:

- In `previewLossAdjustedWithdrawFunds`, add `pendingInstantWithdraws` to `pendingBasis` so instant receipts share the haircut, and record a `lossRecoveryPriceByEpoch`-style ratio for instant claims funded in a loss epoch.
- Alternatively, when funding via `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` in an epoch where a loss is pending, apply the same recovery multiplier to instant claims instead of paying par.
- As a partial mitigation, close the instant-request window earlier (e.g., disallow new `requestInstantWithdraw` once the epoch is past a cutoff before `epochEndDate`) to reduce the frontrun surface.

function testInstantWithdrawFrontrunsLoss() external {
    // honest LP and attacker each deposit into AA tranche
    idleCDO.depositAA(10_000 * ONE_SCALE);            // honest
    deal(address(underlying), attacker, attackerAmt);
    vm.startPrank(attacker);
    underlying.approve(address(idleCDO), attackerAmt);
    idleCDO.depositAA(attackerAmt);                    // attacker
    vm.stopPrank();

    _startEpochAndCheckPrices(initialProvidedApr);

    uint256 lossAmount = 5_000 * ONE_SCALE;
    uint256 duration = cdoEpoch.epochDuration();
    uint256 cvPre = cdoEpoch.getContractValue();

    // Attacker sees pending stopEpochWithDuration(loss) and requests instant withdraw
    vm.warp(cdoEpoch.instantWithdrawDeadline() - 1);
    vm.prank(attacker);
    cdoEpoch.instantWithdrawRequest(0, address(AAtranche)); // full balance
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // Manager's loss tx now reverts: pending instant bucket non-zero
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpochWithDuration(0, 0, duration, lossAmount);

    // Manager is forced to fund attacker at par first
    deal(address(underlying), borrower, strategy.pendingInstantWithdraws());
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), strategy.pendingInstantWithdraws());
    vm.warp(cdoEpoch.instantWithdrawDeadline());
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();

    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 attackerOut = underlying.balanceOf(attacker);
    assertEq(attackerOut, attackerAmt, "attacker exited at par, zero loss");

    // Loss now applied only to remaining LPs
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, duration, lossAmount);
    assertEq(cdoEpoch.getContractValue(), cvPre - attackerAmt - lossAmount);
    // Honest LP's per-unit loss exceeds their fair share:
    // fair share = lossAmount * honestAmt / cvPre; actual = lossAmount (whole) on cvPre - attackerAmt
}

  /// @notice collect borrower-funded withdraw receipt funds
  /// @dev Only IdleCDO can call this function. When `_amount` is lower than the
  /// pending basis, the difference is a stopEpochWithDuration loss assigned to
  /// pending receipts and users later claim through `lossRecoveryPriceByEpoch`.
  /// Reverts if the resulting recovery price rounds to zero at `RECOVERY_FULL` precision.
  /// @param _amount number of funded tokens to collect
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
  }
