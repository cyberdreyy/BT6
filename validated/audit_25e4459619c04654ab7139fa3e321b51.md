### Title
Fee-on-transfer deposits can over-credit epoch principal - (`contracts/IdleCDOEpochVariant.sol`)

### Summary
`depositDuringEpoch` measures the requested `_amount`, not the amount actually received or delivered. With a fee-on-transfer underlying, the CDO can mint tranche and strategy-token exposure for the gross amount while the borrower receives only the net amount. Depending on where the token deducts the fee, the call either reverts or leaves the epoch accounting short by the transfer fee.

### Finding Description
Mid-epoch deposits are gated, but can be enabled in fixed-APR, non-programmable vaults while an epoch is running. [1](#0-0) 

The function transfers `_amount` from the depositor but never computes the balance delta. It then uses the gross `_amount` for remaining-epoch interest, the minted-tranche calculation, strategy-token issuance, and the borrower transfer. [2](#0-1) [3](#0-2) 

This differs from the ordinary deposit path, which mints tranche shares using the actual token-balance delta. [4](#0-3) 

The analogous gross-amount assumption also exists in `IdleCreditVault.deposit`: it transfers `_amount` from the CDO and mints `_amount` strategy tokens without measuring the received balance. [5](#0-4) 

For example, with a 1% transfer fee assessed on the CDO-to-borrower leg, a 100-token `depositDuringEpoch` call can mint exposure for 100 tokens plus prorated interest while the borrower receives only 99 tokens. The epoch accounting nevertheless treats the full 100 tokens as deployed principal and later pulls or settles on that gross basis. [6](#0-5) [7](#0-6) 

### Impact Explanation
The broken invariant is fair mint/burn and principal solvency: a depositor is credited for gross principal and expected interest even though less principal reaches the borrower. On a 1% fee, each mid-epoch deposit creates a 1% principal shortfall. If the borrower repays the booked gross obligation, the depositor can extract value corresponding to the fee; if the borrower does not cover the shortfall, the pool can enter the borrower-default path and withdrawals can be frozen or haircut. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
The issue requires the vault underlying to be a fee-on-transfer token and `depositDuringEpoch` to be enabled. That path is disabled by default but is owner/manager-configurable and is intended for fixed-APR, non-programmable vaults. [10](#0-9) [11](#0-10) 

The factory accepts the underlying as a deployment parameter and does not reject fee-on-transfer tokens. [12](#0-11) [13](#0-12) 

### Recommendation
Measure actual balances around every token transfer. In `depositDuringEpoch`, compute `received = token.balanceOf(address(this)) - balanceBefore` after pulling funds, calculate interest and mint shares/strategy tokens from `received`, and forward only `received` to the borrower. Similarly, `IdleCreditVault.deposit` should mint strategy tokens from the actual amount received rather than `_amount`. Alternatively, explicitly reject tokens that do not transfer exactly the requested amount.

### Proof of Concept
A Foundry test can reproduce this with an ERC20 whose `transfer` deducts 1% when the destination is the borrower:

```solidity
contract FeeToken is ERC20 {
    address public feeSink;
    mapping(address => bool) public exemptDestination;

    constructor() ERC20("FeeToken", "FEE") {}

    function setFeeDestination(address account, bool charged) external {
        exemptDestination[account] = charged;
    }

    function _update(address from, address to, uint256 amount) internal override {
        uint256 fee = exemptDestination[to] ? amount / 100 : 0;
        super._update(from, to, amount - fee);
        if (fee != 0) super._update(from, feeSink, fee);
    }
}

function testFeeOnTransferDepositDuringEpoch() external {
    // Fork or deploy:
    // - FeeToken as cvParams.underlying
    // - IdleCreditVault strategy
    // - IdleCDOEpochVariant
    // - a KYC-allowed attacker wallet
    // - depositDuringEpoch enabled and epoch already running

    uint256 amount = 100e6;
    uint256 fee = amount / 100;

    uint256 borrowerBefore = token.balanceOf(borrower);
    uint256 strategySupplyBefore = strategy.balanceOf(address(cdo));

    vm.prank(attacker);
    uint256 minted = cdo.depositDuringEpoch(amount, cdo.AATranche());

    // Only 99 tokens are delivered, while the CDO mints principal accounting
    // and strategy-token exposure for the requested 100 tokens.
    assertEq(token.balanceOf(borrower) - borrowerBefore, amount - fee);
    assertEq(strategy.balanceOf(address(cdo)) - strategySupplyBefore, amount);
    assertGt(minted, 0);

    // At stopEpoch, the CDO requests funding on the gross accounting basis.
    // The 1-token difference is either extracted from the borrower or turns
    // into a default/shortfall even though only 99 tokens were deployed.
}
```
