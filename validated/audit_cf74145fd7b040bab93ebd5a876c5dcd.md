### Title
Cross-user response hijack via MessageId collision in legacy web_api_trigger `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores pending callbacks in `h.savedCallbacks` keyed only by `msg.Body.MessageId`, with no uniqueness check and no binding to `msg.Body.Sender`. Any attacker who submits a legacy `web_api_trigger` request using the same `MessageId` as another in-flight request will silently overwrite the victim's entry, so that when the DON responds to the (colliding) MessageId, the attacker's callback receives the response instead of the original submitter's.

### Finding Description
`HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`) validates the message (timestamp, method, signature via `common.ValidatedRequestFromMessage`) but performs no check for whether `msg.Body.MessageId` already has a pending callback before writing: [1](#0-0) 

This unconditionally overwrites any existing entry in the map, unlike the newer `RequestCache` used elsewhere in the gateway, which keys entries by `(sender, id)` tuple and explicitly rejects duplicates: [2](#0-1) 

When a node later responds with the same `MessageId` for the *original* request, `handleWebAPITriggerMessage` looks up and deletes the entry purely by `MessageId`, and sends the response to whatever callback is currently stored: [3](#0-2) 

Critically, `MessageId` is entirely attacker-chosen: it is not server-generated. It comes directly from the JSON-RPC request ID (`ValidatedMessageFromReq`, `core/services/gateway/handlers/common/message_util.go:36-58`) and is only bounds-checked for length (≤128 bytes) and non-null-terminated suffix in `Message.Validate()` (`core/services/gateway/api/message.go:54-88`). Nothing prevents two different senders from choosing the identical `MessageId` string. Since `MessageId` is often a simple counter, timestamp-based string, or UUID chosen by the calling client/workflow, and there is no per-sender namespacing on the gateway side for this legacy handler, an attacker can trivially construct a request with a MessageId equal to (or matching, if predictable) the victim's, and send it to the gateway while the victim's original request is still pending in `h.savedCallbacks`.

The timestamp staleness check (`payload.Timestamp` vs `h.config.MaxAllowedMessageAgeSec`, lines 372-383) is unrelated to MessageId collision and does not prevent this — it only rejects requests whose *own* payload timestamp is too old; it does not tie the timestamp or MessageId to a particular sender or prevent collisions between two fresh, validly-signed requests from different senders.

### Impact Explanation
This is a cross-user response confusion / hijack: an unprivileged attacker who is any gateway API caller (holding their own valid signing key — not the victim's) can cause the victim's `web_api_trigger` capability execution result (the DON's HTTP/webAPI trigger response payload) to be delivered to the attacker instead of the victim, and simultaneously deny the victim their response (their callback is evicted and dropped from the map, so the victim's request will eventually time out or receive no response). This matches the "cross-user response confusion" / request impersonation impact class in scope.

### Likelihood Explanation
Preconditions: (1) attacker must be able to submit a signed legacy gateway message (attacker only needs their own valid key — any unauthenticated/self-registered signing key that the gateway will validate, since `Message.Validate()` only checks signature format and does not require any allowlisted identity for this handler — see TODO comment "apply allowlist and rate-limiting here" at line 384); (2) attacker must guess/predict/brute-force or otherwise learn the victim's `MessageId` and submit their colliding request while the victim's original request is still pending (within `CallbackMaxAgeSec`, default 120s). Practical feasibility depends heavily on how MessageIds are generated by legitimate clients (sequential/predictable IDs would make this trivial; high-entropy UUIDs make blind guessing infeasible, though the attack remains valid if MessageId leaks via logs/other channels or if the client-side ID generation is predictable). The vulnerability in the code (missing uniqueness/sender-binding check) is concrete and reproducible regardless of that external factor.

### Recommendation
Bind `savedCallbacks` entries to `(Sender, MessageId)` rather than `MessageId` alone (mirroring the `globalId{sender, id}` pattern already used in `common.requestcache.go`), and reject/error on collision with an existing pending entry instead of silently overwriting it, consistent with `requestCache.NewRequest`'s duplicate-detection behavior.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct `handler` with a real `HandlerConfig` and a fake `handlers.DON`/`don.SendToNode` stub that records sent requests.
2. Build two valid, signed `api.Message`s with `Method = MethodWebAPITrigger`, identical `Body.MessageId = "collide-id"`, but different signing keys (different `Sender`), each with distinct `handlers.Callback` (e.g. two `common.NewCallback()` instances) and valid fresh `TriggerRequestPayload.Timestamp`.
3. Call `h.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)` — assert `len(h.savedCallbacks) == 1` and the stored entry's `Callback == victimCallback`.
4. Call `h.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)` with the same `MessageId` — assert `len(h.savedCallbacks) == 1` still, and now the stored entry's `Callback == attackerCallback` (overwrite confirmed, victim's callback reference is lost).
5. Simulate a node response for `MessageId = "collide-id"` via `h.HandleNodeMessage`/`handleWebAPITriggerMessage` with `Body.Sender` set to a DON member address — assert that `attackerCallback.Wait(ctx)` receives the response (`RawResponse` decodable, `ErrorCode == api.NoError`) while `victimCallback.Wait(ctx)` times out / never receives a response, proving the attacker received the victim's intended result.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
