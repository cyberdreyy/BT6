### Title
Node-side `validate()` opens `sort_tip`/`db_handle` from an unverified-canonical `TenureChangeCause::Extend` burn view, letting signers sign on a stale/orphaned burn view - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
`NakamotoBlockProposal::validate()` derives `sort_tip` from `burn_view_consensus_hash` via a plain `SortitionDB::get_block_snapshot_consensus` lookup and then calls `check_block_has_valid_tenure` against a `db_handle` rooted at that (possibly non-canonical) sortition, without ever verifying that `burn_view_consensus_hash` itself is on the currently-canonical burnchain fork. This is different from the canonicity check (`check_valid_consensus_hash`) that consensus-critical block-acceptance code (`check_nakamoto_tenure`) applies to the very same field. A `TenureChangeCause::Extended` proposal naming a stale/orphaned `burn_view_consensus_hash` can therefore receive `BlockValidateOk` from the node while a signer's own canonical view would treat that consensus hash as not canonical.

``` [2](#0-1) 
That connectivity check only requires the named `burn_view_consensus_hash`'s fork to agree with the parent block's stored burn view *at the parent's burn-view height* - it does not require the named hash to still be on the chain tip that is canonical *now*. A Bitcoin fork/orphan that shares history with the canonical chain up to that height and then diverges (a routine occurrence that every full node records in its `sortdb`, not something requiring majority hash power) satisfies this check while pointing at a stale sortition.

`SortitionDB::get_block_snapshot_consensus` merely looks up *any* snapshot matching the consensus hash, canonical or not, so `sort_tip` can legitimately be a real-but-orphaned sortition. `check_block_has_valid_tenure` then only checks `db_handle.has_consensus_hash(tenure_id)`, i.e., ancestry *within the (possibly orphaned) `sort_tip`'s own history* - not against the actual canonical tip:
```

``` [3](#0-2) 
This is a materially weaker check than `NakamotoChainState::check_valid_consensus_hash`, which is applied to the very same field (`burn_view_consensus_hash`) during real block acceptance (`check_nakamoto_tenure`) and explicitly rejects non-canonical snapshots:
```

pub(crate) fn check_valid_consensus_hash<SH: SortitionHandle>(...) {
    let Some(sn) = SortitionDB::get_block_snapshot_consensus(...)? else { return Ok(None) };
    let Some(ancestor_sn) = sort_handle.get_block_snapshot_by_height(sn.block_height)? else { return Ok(None) };
    if ancestor_sn.sortition_id != sn.sortition_id { return Ok(None) } // not canonical
    Ok(Some(sn))
}
``` [4](#0-3) 

Neither `check_nakamoto_tenure` nor `check_valid_consensus_hash` is invoked from `postblock_proposal.rs::validate()` - the proposal-validation path uses only `check_block_has_valid_tenure`/`check_block_has_valid_parent` plus `validate_normal_nakamoto_block_burnchain`, none of which re-derive canonicity of `burn_view_consensus_hash` against the actual current sortition tip. [5](#0-4) 

On the signer side, the only extend-specific gate in `SortitionsView::check_proposal`/`GlobalStateView::check_proposal` (v1.rs/v2.rs) compares `tenure_extend.burn_view_consensus_hash` against `client.get_tenure_tip(...).burn_view` merely to decide whether the extend is *justified* (burn view changed, enough time passed, or replay) - it never checks that the named hash is canonical:
```

A forged hash that merely differs from the reported current burn view satisfies `changed_burn_view == true` and bypasses the timing requirement - the field's actual canonicity is left entirely to the node's `validate()` call, which is the component shown above to be under-checking it. The signer thus trusts the node's `BlockValidateOk` for exactly the property (canonicity of `burn_view_consensus_hash`) that its own `check_proposal` does not independently verify.

### Impact Explanation
If exploitable end-to-end, this breaks the **canonicity** safety property: a signer could sign a `TenureChangeCause::Extended` block whose burn view resolves to an orphaned/non-canonical Bitcoin fork, because the node's `validate()` opens its entire sortition-handle context (`db_handle`, `burn_dbconn`) at that stale fork rather than at the canonical tip, and returns `Ok`. A signature over such a block, once gossiped and aggregated with a threshold of other signers doing the same (each independently fooled the same way, since it is a deterministic node-side gap, not a majority-collusion requirement), finalizes a block anchored to a burn view the network no longer considers canonical - a chain-split/tenure-extend-on-stale-burn-view scenario. This matches the Critical severity category ("a signer signing an invalid, non-canonical, or conflicting block").

### Likelihood Explanation
Preconditions: (1) a Bitcoin fork/orphan must exist whose sortition history agrees with the canonical chain up to the height of the parent block's recorded burn view and then diverges (a naturally occurring, non-adversarial event that every node's `sortdb` retains as historical, non-deleted state); (2) the attacker needs only their own single won miner slot to construct and gossip a `TenureChangeCause::Extended` block proposal naming that stale consensus hash as `burn_view_consensus_hash`, consistent with all the other Extend-specific structural checks (`tenure_consensus_hash == prev_tenure_consensus_hash`, block-builds-on-highest-block, etc.). No majority signer weight, node operator access, other signers' keys, or the validation `auth_token` are required - matching the stated attacker model exactly. The attack is repeatable each time a suitable stale fork exists in the sortdb history relative to the current tenure. The main uncertainty (not fully traced given tool budget) is whether `validate_normal_nakamoto_block_burnchain` or subsequent checks past line 700 of `postblock_proposal.rs` independently re-derive canonicity of `burn_view_consensus_hash` against the live canonical tip before returning `BlockValidateOk`; this should be verified directly against the running node to confirm end-to-end exploitability.

### Recommendation
In `postblock_proposal.rs::validate()`, before using `burn_view_consensus_hash` to open `sort_tip`/`db_handle`, run it through `NakamotoChainState::check_valid_consensus_hash` (or equivalent) against the actual canonical sortition tip, rejecting the proposal if the named consensus hash is not on the currently-canonical fork - mirroring the guard already present in `check_nakamoto_tenure`/`check_valid_consensus_hash`. Additionally, harden the signer-side extend check in `stacks-signer/src/chainstate/v1.rs`/`v2.rs` to independently confirm `tenure_extend.burn_view_consensus_hash` corresponds to a canonical sortition (e.g., via an RPC that itself checks canonicity) rather than relying solely on inequality with `client.get_tenure_tip()` and trusting node-side `Ok`.

```rust
    pub(crate) fn check_valid_consensus_hash<SH: SortitionHandle>(
        sort_handle: &mut SH,
        ch: &ConsensusHash,
    ) -> Result<Option<BlockSnapshot>, ChainstateError> {
        // the target sortition must exist, and it must be on the canonical fork
        let Some(sn) = SortitionDB::get_block_snapshot_consensus(sort_handle.sqlite(), ch)? else {
            // no sortition
            warn!("Invalid consensus hash: no such snapshot"; "consensus_hash" => %ch);
            return Ok(None);
        };
        let Some(ancestor_sn) = sort_handle.get_block_snapshot_by_height(sn.block_height)? else {
            // not canonical
            warn!("Invalid consensus hash: snapshot is not canonical"; "consensus_hash" => %ch);
            return Ok(None);
        };
        if ancestor_sn.sortition_id != sn.sortition_id {
            // not canonical
            return Ok(None);
        }
        Ok(Some(sn))
    }
```
