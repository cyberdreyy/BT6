### Title
Miner-side vote tally lets a signer's stale rejection weight persist after it later accepts, causing a false `SignersRejected` liveness failure - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side `StackerDBListener` tracks per-block signer participation in a `BlockStatus` struct with two independent gates: `gathered_signatures` (checked before crediting `total_weight_approved`) and `responded_signers` (checked before crediting `total_weight_rejected`). These two gates are not kept in sync with each other, so a signer that rejects a block and *later legitimately changes its answer to accept the same block* has its weight added to `total_weight_approved` without ever having its earlier `total_weight_rejected` contribution removed. This produces two independent, additive, never-decremented weight counters that can jointly represent more voting weight than the signer set actually has, and specifically lets a stale rejection persist even after the same signer has switched to accepting. [1](#0-0) 

### Finding Description
The `BlockAccepted` handling path only skips crediting `total_weight_approved` if the signer's slot id is already present in `gathered_signatures`: [2](#0-1) 

The `BlockResponse::Rejected` path instead gates on `responded_signers.insert(slot_id)`, i.e., it treats the signer as having "responded" once, for either an accept or a reject: [3](#0-2) 

Because the accept path never checks `responded_signers`, and the reject path never checks `gathered_signatures`, the two totals are governed by two different (and inconsistent) sets:

- If a signer **accepts first, then rejects** the same block: `responded_signers` was already set to `true` by the accept branch's unconditional `block.responded_signers.insert(slot_id)` (line 465), so the later reject's `responded_signers.insert(slot_id)` returns `false` and `total_weight_rejected` is correctly NOT incremented.
- If a signer **rejects first, then accepts** the same block (a scenario the signer-side state machine explicitly allows — the signer docs describe a signer repeating "my earlier answer... unless the reason I rejected has since gone away", i.e., a legitimate reject→accept flip is an intended protocol behavior), the reject path already set `responded_signers` to contain the slot id, but the accept path's guard is `gathered_signatures.contains_key(&slot_id)`, which is still `false` at that point. The accept branch therefore *does* add the signer's weight to `total_weight_approved` (line 444-446), while the earlier `total_weight_rejected` credit from the reject is never decremented anywhere in the codebase (no code path subtracts from `total_weight_rejected`).

The result: the same one signer's weight is counted simultaneously in `total_weight_rejected` (from its earlier answer) and `total_weight_approved` (from its later, corrected answer), and there is no mechanism to reconcile the two. The invariant the miner's rejection-threshold logic implicitly assumes — that `total_weight_rejected` reflects signers who *currently* reject the block — is broken by a single honest signer's normal vote-flip.

### Impact Explanation
`SignerCoordinator::watch_for_block_signatures` (the consumer of `BlockStatus`) treats `total_weight_rejected` as authoritative for aborting block production: [4](#0-3) 

Since a stale, never-decremented `total_weight_rejected` value can accumulate weight from signers who have since flipped to accepting, the miner can hit `block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` and abort with `NakamotoNodeError::SignersRejected` even though the effective, current rejecting weight is lower than the stored value implies. In borderline cases near the 30% blocking-minority threshold, this can cause the coordinator to prematurely declare a block dead and discard it (and permanently/temporarily ban txids it flags via `failed_txids`) even though, with the signer's corrected vote counted properly, the block would not actually be blocked. This is a liveness defect: it can wedge the miner into rejecting/discarding blocks that a fully reconciled tally would show as viable, consistent with the "signer wedged into never signing valid blocks" / stale-count class of issue. It does not, on its own, cause an invalid or non-canonical block to be signed, since `gathered_signatures` still requires a real, individually-verified signature per accepting signer before `total_weight_approved` counts it.

### Likelihood Explanation
This requires no majority collusion, no compromised keys, and no protocol violation — a single honest signer that rejects a proposal and later accepts the same proposal (an explicitly supported, documented behavior per the signer's own decision flow, "repeat my earlier answer... unless the reason I rejected has since gone away") is enough to place the miner-side tally into the inconsistent state. Any legitimate scenario where a signer's rejection reason resolves (e.g., a transient validation/connectivity issue, or a reorg-related rejection that becomes valid again) before the block dies naturally triggers this code path.

### Recommendation
Make the `responded_signers` set (or an equivalent per-slot "current vote" map) the single source of truth for both credit paths, and reconcile weight when a vote changes:
- Before crediting `total_weight_approved` for an `Accepted` message, check whether the slot id is already present in `responded_signers` as a rejection and, if so, subtract the signer's weight from `total_weight_rejected` (and vice versa for a reject overriding a prior accept).
- Alternatively, track a single per-slot "current decision" (`Accepted`/`Rejected`) and recompute `total_weight_approved`/`total_weight_rejected` as the sum over current decisions rather than as independently-incremented, never-decremented counters.

### Proof of Concept
1. Miner proposes block `B` with `signer_signature_hash = H`.
2. Signer `S` (slot `k`, weight `w`) initially rejects `B` (e.g., due to a transient/soon-to-be-stale reason): `StackerDBListener` runs the `Rejected` branch — `responded_signers.insert(k)` succeeds, `total_weight_rejected += w`.
3. The reason for `S`'s rejection resolves (e.g., its earlier reorg/connectivity concern clears — a case the signer's own logic explicitly re-evaluates), and `S` now sends `Accepted` for the same `H` with a valid signature.
4. `StackerDBListener`'s `Accepted` branch checks only `gathered_signatures.contains_key(&k)`, which is `false` (never touched by the reject branch), so it executes `total_weight_approved += w` and inserts into `gathered_signatures`/`responded_signers`.
5. Now `BlockStatus` for `H` shows `total_weight_rejected = w` (stale, from step 2) and `total_weight_approved = w` (from step 4) — `S`'s weight is counted in both totals, and nothing in the codebase ever decrements `total_weight_rejected`. If other signers' rejections push `total_weight_rejected` close to the 30% blocking minority, this stale contribution from `S` can be the deciding weight that trips `SignersRejected` in `signer_coordinator.rs` (lines 509-518), even though `S` currently accepts the block.
