### Title
Missing per-sender isolation/rate limiting in `HandleLegacyUserMessage` allows attacker-driven eviction of a victim's pending `web_api_trigger` callback via `pruneCallbacks` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores every accepted `web_api_trigger` request into a shared `savedCallbacks` map keyed only by `MessageId`, with no per-sender quota or rate limit, as explicitly flagged by the `// TODO: apply allowlist and rate-limiting here` comment. When the map grows past `MaxSavedCallbacks` (default 20000), `pruneCallbacks` evicts strictly by oldest `createdAt`, with no notion of which sender owns an entry, so an attacker who floods enough distinct signed requests can cause an older, still-pending victim callback to be silently deleted before the node ever responds.

### Finding Description
The reachable path is: gateway HTTP endpoint → `gateway.ProcessRequest` (`core/services/gateway/gateway.go:267-269`) → `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`). This function only requires a syntactically valid, self-signed `api.Message` (any attacker can generate their own ECDSA key and sign a well-formed `TriggerRequestPayload` with a fresh `MessageId`/timestamp) — signature verification only proves the message wasn't tampered with, it does not authorize the sender or throttle them. The explicit TODO at line 384 confirms no allowlist/rate-limit is applied for this legacy path (unlike the v2 handler in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`, which calls `authorizeRequest` and `checkRateLimit`).

Each valid request inserts into the shared map under the global lock: [1](#0-0) 

`pruneCallbacks`, run periodically by a background ticker, first removes expired entries, then—if the map still exceeds `MaxSavedCallbacks`—sorts all remaining entries by `createdAt` and deletes the oldest half, with no per-sender accounting whatsoever: [2](#0-1) 

Because eviction order is purely oldest-first across the whole map, an attacker who submits enough distinct `MessageId`s to push the total count over `MaxSavedCallbacks` can cause an older, legitimately-inserted victim callback (which is not yet expired and whose node response hasn't arrived) to be deleted in the same prune pass, purely because it happens to be one of the globally-oldest entries. Once deleted, the victim's node response — handled in `handleWebAPITriggerMessage` — finds no matching entry (`found == false`) and silently drops the response: [3](#0-2) 

The victim's original HTTP-facing `callback.Wait(ctx)` in `gateway.ProcessRequest` then times out, returning a spurious "handler timeout" error to the victim even though the DON might correctly reply later.

### Impact Explanation
This is a cross-user denial of capability-execution-response delivery: an unauthenticated, unprivileged attacker can cause another user's legitimate, in-flight `web_api_trigger` request to be dropped and time out, without ever touching that victim's credentials or DON. This matches "cross-user response confusion" / availability impact for another user's request, though it does not grant privilege escalation, secret disclosure, or fund movement — the affected primitive is response delivery/isolation, not authorization state.

### Likelihood Explanation
Feasibility is high in principle: no authentication beyond a self-generated signing key is required, and the code has no per-sender rate limiter or allowlist for this path (confirmed by the TODO). Exploitability is time/volume dependent though: the attacker must sustain enough concurrently-outstanding (not-yet-responded, not-yet-expired) requests to push the total above `MaxSavedCallbacks` (20000) within a `CallbackMaxAgeSec` (120s) window, and the eviction only runs every `CallbackPruneIntervalSec` (30s) via a ticker, so the attack requires substantial sustained throughput plus favorable timing (victim's request must be among the globally-oldest fraction at prune time). This is realistic under sustained load/flood conditions rather than a single request, but does not require any privileged token.

### Recommendation
Add per-sender rate limiting/quota enforcement in `HandleLegacyUserMessage` (the TODO already flags this), and change `pruneCallbacks` eviction to be sender-aware (e.g., cap outstanding callbacks per sender address, or weight eviction to prioritize removing entries from senders that most exceed their quota) rather than a purely global oldest-first strategy.

### Proof of Concept
Go test plan (in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` with `MaxSavedCallbacks` set low (e.g., 10) for test speed.
2. Insert one "victim" callback via `handler.HandleLegacyUserMessage` with an early `createdAt` (or manipulate `handler.savedCallbacks` directly to simulate an older timestamp).
3. Simulate the "attacker" by inserting >`MaxSavedCallbacks` distinct signed `web_api_trigger` messages (varying `MessageId`s, all signed with attacker-controlled keys) via repeated `HandleLegacyUserMessage` calls, each with a later `createdAt`.
4. Call `handler.pruneCallbacks()` directly.
5. Assert that the victim's `MessageId` is no longer present in `handler.savedCallbacks` (evicted) while the attacker's newer entries remain, demonstrating the victim's not-yet-responded, not-yet-expired callback was evicted purely due to attacker volume.
6. Optionally simulate the node response for the victim's `MessageId` via `HandleNodeMessage` afterward and assert `handleWebAPITriggerMessage` returns `found == false` / no callback delivered, confirming silent drop.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.

	return nil
}
