### Title
Unsafe Timing Constraint in `createDstEscrow` Allows Fund Theft via Race Condition - (`contracts/BaseEscrowFactory.sol`)

### Summary
The `BaseEscrowFactory.createDstEscrow` function enforces an incorrect timing constraint that requires the destination escrow's cancellation time to be less than or equal to the source chain's cancellation timestamp. This violates the fundamental security requirement of atomic swaps, where the destination cancellation must occur strictly after the source cancellation to allow the maker time to react to a revealed secret. An unprivileged resolver can exploit this to withdraw funds on the source chain and immediately cancel the destination escrow, effectively stealing the maker's funds.

### Finding Description
In `BaseEscrowFactory.createDstEscrow`, the contract validates the `DstCancellation` timelock against the `srcCancellationTimestamp` provided by the caller: [1](#0-0) 

This check ensures that `DstCancellation <= srcCancellationTimestamp`. However, in a cross-chain atomic swap, the destination escrow must remain open for withdrawal until well after the source escrow's withdrawal period has ended. This is because the secret is revealed on the source chain during withdrawal; the maker (or a public caller) must then have sufficient time to observe this secret and submit a withdrawal transaction on the destination chain.

If `DstCancellation` is exactly equal to `srcCancellationTimestamp` (the boundary condition allowed by the check), the resolver can:
1.  Withdraw from the source escrow at `t = srcCancellationTimestamp - 1`, revealing the secret.
2.  Immediately call `cancel` on the destination escrow at `t = srcCancellationTimestamp`.

Due to cross-chain latency and block inclusion times, the maker will be unable to use the revealed secret on the destination chain before the resolver cancels it. The factory not only allows this unsafe state but actually *reverts* if a resolver attempts to set a safe `DstCancellation` (i.e., one that is strictly greater than `srcCancellationTimestamp`).

### Impact Explanation
This is a **Critical** impact. It allows a malicious resolver to perform a "double-spend" attack: they acquire the maker's funds on the source chain by revealing the secret, and then reclaim their own funds (and safety deposit) on the destination chain by cancelling the escrow before the maker can react. The maker loses their source-chain assets and receives nothing on the destination chain.

### Likelihood Explanation
The likelihood is **High**. The vulnerability is built into the core validation logic of the factory. Any swap where the resolver knows the secret (which is the standard case for many settlement models) is susceptible. The attacker only needs to be an unprivileged resolver (taker) of a live order.

### Recommendation
Reverse the logic of the timelock validation in `createDstEscrow`. The destination cancellation should be required to be significantly *later* than the source cancellation to account for cross-chain communication delays and finality.

```solidity
// Suggested fix:
if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) < srcCancellationTimestamp + MIN_SAFETY_MARGIN) revert InvalidCreationTime();
```

### Proof of Concept
1.  **Setup**: A maker creates a Limit Order with a `hashlock` for which the resolver knows the secret `S`.
2.  **Source Fill**: The resolver fills the order. `BaseEscrowFactory._postInteraction` deploys `EscrowSrc` with `SrcCancellation = T`.
3.  **Malicious Dst Deployment**: The resolver calls `createDstEscrow` on the destination chain. They provide `srcCancellationTimestamp = T` and `dstImmutables` with `DstCancellation = T`.
    *   The check `DstCancellation > srcCancellationTimestamp` (T > T) is false, so the call succeeds.
4.  **Theft**:
    *   At `t = T - 1s`, the resolver calls `EscrowSrc.withdraw(S, ...)`. They receive the maker's funds. Secret `S` is now on-chain.
    *   At `t = T`, the resolver calls `EscrowDst.cancel(...)` on the destination chain. They receive their `takingAmount` and `safetyDeposit` back.
5.  **Outcome**: The maker sees `S` at `t = T - 1s`. They attempt to call `EscrowDst.withdraw(S, ...)` or `publicWithdraw`, but the transaction arrives at or after `t = T`. The call reverts because `EscrowDst` is already in the cancellation stage or has been cancelled. The resolver has successfully stolen the maker's source funds.
