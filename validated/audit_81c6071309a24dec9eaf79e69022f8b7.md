### Title
Unbound MessageId key in `savedCallbacks` allows response hijacking/DoS across users - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each incoming user request's callback in `h.savedCallbacks` keyed solely by `msg.Body.MessageId`, with no binding to the sender/signer and no check for an existing in-flight entry with that ID. An attacker who submits a legacy `web_api_trigger` request with a `MessageId` identical to another user's currently pending request can silently overwrite the victim's callback entry, causing the victim's original callback to be dropped and the DON's response instead delivered to the attacker (or vice versa), and/or causing the victim's request to hang until pruning.

### Finding Description
In `HandleLegacyUserMessage`, after validating the payload, the handler unconditionally writes:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [1](#0-0) 

There is no check for `found` before overwrite, and no association between the map key and the sender's identity — the map is `map[string]*savedCallback` keyed purely by `MessageId`. [2](#0-1) 

The `Message.Validate()` function checks signature format, length limits on `MessageId`, `Method`, `DonId`, and `Receiver`, and derives `Sender` from the signature, but it never checks `MessageId` for cross-request uniqueness or ties it to `Sender` — it enforces per-message signature integrity, not per-ID exclusivity. [3](#0-2) 

When the DON later responds via `handleWebAPITriggerMessage`, the response is dispatched purely by looking up `msg.Body.MessageId` in `savedCallbacks` and deleting/using whatever entry is currently there — again with no sender-binding check:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [4](#0-3) 

Exploit flow: Victim sends request A with `MessageId="X"`. Handler stores `savedCallbacks["X"] = victimCallback`. Before nodes respond to A, attacker crafts and signs their own message B with the same `MessageId="X"` (attacker fully controls the `MessageId` field of their own signed message; nothing derives it from a server-side counter or nonce tied to sender identity) and submits it to the same gateway endpoint/DON. Handler overwrites `savedCallbacks["X"] = attackerCallback`. When the DON eventually responds to request A (or B), the response is delivered to whichever callback is currently stored under key `X` — the victim's connection may hang forever (DoS, cleaned up only by `pruneCallbacks` after `CallbackMaxAgeSec`, default 120s) or, if timing allows, the attacker could receive the victim's request/response semantics or the victim could receive the attacker's response, since `handleWebAPITriggerMessage` returns the first node response verbatim without validating which original request it correlates to beyond the (attacker-collidable) `MessageId`.

No existing mitigation intervenes: rate limiting only throttles per-node message volume in `handleWebAPIOutgoingMessage`/`nodeRateLimiter`, not per-`MessageId` uniqueness in `HandleLegacyUserMessage`; the `TODO: apply allowlist and rate-limiting here` comment confirms no such enforcement exists at this call site. [5](#0-4) 

### Impact Explanation
This is a cross-user response confusion / hijacking and denial-of-service vulnerability: an unprivileged, unauthenticated attacker able to reach the gateway's HTTP endpoint can disrupt or hijack another user's in-flight WebAPITrigger request purely by choosing a colliding `MessageId`, with no authentication or special role required. This matches the "cross-user response confusion" impact class explicitly called out as in-scope.

### Likelihood Explanation
Exploitability requires only: (1) knowledge or guessability of a victim's in-flight `MessageId` (which may be attacker-controlled/predictable in some client integrations, or discoverable via race conditions/log leakage in some deployments), and (2) the ability to submit a validly signed message to the gateway, which any keyholder/API caller can do. No operator or admin access is needed. The race window is bounded by the callback's lifetime (`CallbackMaxAgeSec`, default 120s), which is a comfortably large window for an attacker to time a collision. This is straightforward to reproduce and repeat.

### Recommendation
Bind `savedCallbacks` entries to the requesting sender (e.g., key by a hash of `(Sender, MessageId)` or store `Sender` in `savedCallback` and verify it matches on both insertion and lookup/response delivery). Reject or securely handle collisions in `HandleLegacyUserMessage` (e.g., return an error to the second caller if an unexpired entry for a different sender already exists at that `MessageId`), and validate sender consistency in `handleWebAPITriggerMessage` before delivering a response to a saved callback.

### Proof of Concept
Go handler-level integration test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler with a DON config containing at least one member; create two distinct signers (simulate victim and attacker).
2. Victim signs message A with `MessageId = "X"`, method `web_api_trigger`; call `handler.HandleLegacyUserMessage(ctx, msgA, victimCallback)`; assert `h.savedCallbacks["X"]` is bound to `victimCallback` (e.g., via a `Sender` field or callback identity).
3. Attacker signs message B (different signer) also with `MessageId = "X"`; call `handler.HandleLegacyUserMessage(ctx, msgB, attackerCallback)`.
4. Assert: either the call is rejected (error returned, e.g. duplicate/collision error) OR `h.savedCallbacks["X"]` still references `victimCallback` (not silently replaced by `attackerCallback`).
5. Simulate a node response for `MessageId = "X"` via `handler.HandleNodeMessage`, and assert `victimCallback.SendResponse` is invoked (not `attackerCallback.SendResponse`), proving no cross-user hijack occurred.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
