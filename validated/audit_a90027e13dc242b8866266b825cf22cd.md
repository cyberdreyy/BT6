### Title
Instant-withdraw claims pay the full declared receipt even when only partially funded, draining other users' reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the RabbitMQ bug (a declared body size is recorded, then a larger actual frame drives the remaining-bytes counter negative before validation, tearing down the connection), `IdleCreditVault` records a declared instant-withdraw receipt amount, then pays it out in full before validating that the claim was actually funded. `pendingInstantWithdraws` tracks the still-unfunded remainder, but `claimInstantWithdrawRequest` ignores it entirely and transfers the full receipt amount, letting an unprivileged user overdraw the strategy's underlying at the expense of other claimants and depositors.

### Finding Description
- `requestInstantWithdraw` mints a 1:1 receipt and increments both `instantWithdrawsRequests[_user]` and the global `pendingInstantWithdraws`, and records per-epoch basis in `instantWithdrawClaimsByEpoch` (lines 356-375).
- `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` by whatever the CDO actually collected — it accepts partial funding (lines 398-403).
- The contract's own accounting acknowledges the resulting state: `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` as "already-held underlying" for instant claims, i.e., claims can be funded only in part (lines 716-723), and `defaultPendingClaimBasis` documents that `pendingInstantWithdraws != 0` means current-epoch instant receipts were not fully funded (lines 636-649).
- `claimInstantWithdrawRequest` then does the "subtract before validate" step: it burns `instantWithdrawsRequests[_user]` (the declared amount) and calls `_transferFundedClaim(_user, amount)` for the whole amount, with zero reference to `pendingInstantWithdraws` or to how much of this user's claim was funded (lines 380-393).
- `_transferFundedClaim` only protects `defaultRecoveryReserve` when it is non-zero; before default finalization there is no funded-vs-declared check at all (lines 897-907).

Attack sequence (buffer → running epoch, any mode):
1. Attacker (a KYC-passing lender, or the CDO acting on their behalf — `requestInstantWithdraw` is only callable by `idleCDO`, which users reach via the CDO's instant-redeem path) calls `requestInstantWithdraw(amount)`.
2. Honest manager calls `startEpoch`; the CDO's available cash covers only part of the instant queue, so `collectInstantWithdrawFunds` pulls a partial amount. `pendingInstantWithdraws` remains > 0 — the exact state the code documents.
3. Attacker calls `claimInstantWithdrawRequest` via the CDO and receives the full `instantWithdrawsRequests` amount, even though only a fraction was funded.
4. The transfer is paid out of underlying held by the strategy that backs other instant claimants (the "prefunded" portion reserved for them) and/or depositor principal awaiting `sendInterestAndDeposits`. Every subsequent claimant reverts on `safeTransfer` or is shorted — declared receipts now exceed actual funded backing.

Broken invariant: one receipt one payout, and solvency — total claimable instant receipts exceed funded underlying whenever `pendingInstantWithdraws < instantWithdrawClaimsByEpoch` and claims are paid at par.

### Impact Explanation
Direct theft/insolvency: the first claimant (or claimants, racing) withdraw underlying belonging to later instant claimants, who can never be paid; the shortfall can also eat depositor principal held in the strategy. Loss is bounded only by the instant queue size and the strategy's liquid underlying balance — quantified as `(funded portion claimed at par) − (attacker's pro-rata funded share)` stolen, plus permanent freezing of remaining unfunded receipts until default finalization haircuts them.

### Likelihood Explanation
Requires only a partially funded instant queue, which the code explicitly anticipates (`startEpoch` cash covering only part of the queue, per the `defaultPendingClaimBasis` comment). No privileged misbehavior, no oracle, no default needed — any user able to trigger an instant withdraw can be first to claim after partial funding. Caveat I could not fully verify: the exact CDO path (`IdleCDOEpochVariant.getInstantWithdrawFunds` / `startEpoch`) that determines when partial funding occurs; grep results confirm the callsites exist in `IdleCDOEpochVariant.sol` but I ran out of search iterations to read the funding-ordering logic. If the CDO always collects the full pending amount before any claim is claimable, likelihood drops significantly.

### Recommendation
Track funded vs. unfunded instant claims per epoch/user, or gate `claimInstantWithdrawRequest` so a claim can only pay `min(instantWithdrawsRequests[_user], funded share)` — e.g., maintain a funded-price per epoch like `lossRecoveryPriceByEpoch`, or revert when `pendingInstantWithdraws != 0` unless claims are paid pro-rata from the collected amount. At minimum, subtract the unfunded remainder from the claimable amount before burning the receipt.
