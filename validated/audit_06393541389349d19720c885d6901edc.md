### Title
Stale confirmations from removed multisig members allow requests to execute below the live confirmation threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member()` in `multisig2/src/lib.rs` only purges pending requests that were *created* by the removed member, but never scrubs that member's entry from the `confirmations` set of other pending requests they had previously *confirmed*. Because `confirm()` counts raw entries in `confirmations` against `num_confirmations` without verifying each entry still belongs to a current member, a stale confirmation from a member who has since been removed keeps counting toward the threshold. This lets a request execute with fewer live-member confirmations than `num_confirmations` actually requires — the same class of bug as the referenced report (recorded confirmation state diverging from the live signer set and being trusted anyway).

### Finding Description
The relevant state is: [1](#0-0) 

`delete_member()` cleans up requests filtered only by the request's *creator* (`r.member == member`), and removes the member's own `num_requests_pk` counter and its membership entry — but it never touches `confirmations` entries left by that member on *other* pending requests: [2](#0-1) 

`confirm()` trusts the size of the stored `confirmations` set directly against `num_confirmations`, with no check that every recorded confirmer is still a current member: [3](#0-2) 

`assert_valid_request()`, called at the top of `confirm()`, only validates that the *caller* is a current member and that the request/confirmation records exist — it performs no reconciliation of already-stored confirmations against the current member set: [4](#0-3) 

This is the direct structural analog of the report's bug: a piece of recorded "approval" state (`confirmations`) is allowed to diverge from the ground truth it's supposed to represent (the live set of authorized members), and the threshold-comparison logic (`confirmations.len() + 1 >= num_confirmations`) blindly trusts the stale recorded state rather than the corrected live truth — exactly as `reconcileSignerCount()` blindly trusted `validSignerCount`/state comparisons without correctly reconciling against `targetThreshold`.

### Impact Explanation
This breaks the core custody binding of the multisig: *confirmations counted* must equal *confirmations from live members*. When it doesn't, a request can be executed by fewer genuinely-authorized signers than `num_confirmations` requires. Since `execute_request()` can perform `Transfer`, `AddKey`, `FunctionCall`, `AddMember`, etc., an under-threshold execution can move funds or grant access without the intended quorum of currently-authorized members — this is the "a multisig request executed below threshold" Critical impact category.

### Likelihood Explanation
Member removal (`DeleteMember`) is a normal, expected multisig operation (e.g., revoking a compromised or departing member's access). Any time a member is removed while they have an outstanding confirmation on a request created by someone else, the stale confirmation persists indefinitely (there's no expiry tying confirmations to membership). The remaining members do not need to do anything unusual — a normal subsequent `confirm()` call on that pre-existing request silently benefits from the phantom vote. This requires no malicious member, no privileged misuse, and no unusual sequencing beyond ordinary multisig lifecycle operations (create request → some member confirms → that member is later removed → another member confirms and unknowingly triggers execution one confirmation early).

### Recommendation
In `delete_member()`, iterate all pending requests' `confirmations` entries (not just requests created by the removed member) and strip the removed member's `to_string()` key from each `HashSet`. Alternatively, change `confirm()` to filter `confirmations` against `self.members` before counting (`confirmations.iter().filter(|m| self.members.contains(...)).count()`), so the threshold check is always computed against live membership rather than raw stored set size.

### Proof of Concept
1. Initialize `MultiSigContract::new(members: [A, B, C], num_confirmations: 2)`.
2. Member `A` calls `add_request(request_X)` (some `Transfer` request), without confirming.
3. Member `B` calls `confirm(request_X)` → `confirmations[request_X] = {B}` (len 1 < 2, pending, not executed).
4. Through a separate, already-confirmed multisig request, the group executes `DeleteMember { member: B }`. `delete_member()` only removes requests where `r.member == B` (i.e., requests B created) — `request_X` (created by A) is untouched, so `confirmations[request_X]` still contains `B`.
5. Member `C` calls `confirm(request_X)`. `confirmations.len() + 1 = 2 >= num_confirmations (2)` → `execute_request(request_X)` runs and the transfer executes.
6. Result: `request_X` executed with confirmations `{B, C}`, but `B` is no longer a member at execution time — only one live member (`C`) actually authorized it, one short of the required threshold of 2.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
