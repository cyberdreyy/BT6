### Title
Unvalidated fee amounts in `createDstEscrow` allow underflow-triggered permanent DoS of `EscrowDst.withdraw` - (File: `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw` computes `amount = immutables.amount - integratorFeeAmount - protocolFeeAmount` without ever validating that the fee sum is smaller than the escrowed amount. [1](#0-0) 
Unlike the source-chain path, which enforces this invariant in `BaseEscrowFactory._postInteraction`, `createDstEscrow` accepts taker-supplied `Immutables.parameters` (which encode `protocolFeeAmount`/`integratorFeeAmount`) with no equivalent check. [2](#0-1) [3](#0-2) 

### Finding Description
This is the same root-cause class as the reported `RangeFeeGrowth` bug: a subtraction of two independently-derived quantities from a total, performed without a guard that the sum of subtrahends cannot exceed the minuend, producing a guaranteed-revert underflow on the withdrawal path.

In this repository, `integratorFeeAmountCd`/`protocolFeeAmountCd` are decoded directly from the calldata `parameters` bytes of the `Immutables` struct passed by the caller of `createDstEscrow`. [4](#0-3) 
`createDstEscrow` takes `dstImmutables` entirely from `msg.sender` (the taker/resolver), derives the CREATE2 salt from its full hash, deploys the clone, and funds it — but never checks that `protocolFeeAmount + integratorFeeAmount < immutables.amount`. [3](#0-2) 

Contrast this with the source-chain escrow creation path, `_postInteraction`, which explicitly guards against this exact condition:
```solidity
if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();
``` [5](#0-4) 
No analogous `InvalidFeeAmounts` check exists in `createDstEscrow`, so an unprivileged taker can encode `parameters` where `protocolFeeAmount + integratorFeeAmount >= immutables.amount` while still producing a syntactically valid `Immutables` struct (the hash/salt used for `onlyValidImmutables` is self-consistent because it's derived from whatever the taker supplies).

Because `Immutables` (including `parameters`) is fixed forever at deployment (it's baked into the CREATE2 salt and checked via `onlyValidImmutables` on every call), once such an escrow is created there is **no possible calldata** that both (a) passes `onlyValidImmutables` and (b) avoids the underflow in `_withdraw`. Every call to `withdraw`/`publicWithdraw` for that escrow will revert with an arithmetic underflow panic, permanently. [6](#0-5) [7](#0-6) 

`cancel()`, however, is unaffected by the fee fields (it just transfers `immutables.amount` back to the taker plus the safety deposit), so the taker who deployed the broken escrow can always recover their own committed funds after the cancellation timelock, while the maker can never withdraw. [8](#0-7) 

### Impact Explanation
This matches the bounty's Medium bucket: "smart contract unable to operate because required token/native balances can be broken by an unprivileged actor." Any unprivileged taker calling `createDstEscrow` (a live, public entry point in the destination-escrow-creation flow explicitly in scope per the audit pivots) can construct `Immutables.parameters` such that the destination escrow can never be successfully withdrawn from — the maker's expected destination funds are permanently unrecoverable via `withdraw`/`publicWithdraw`, while the taker can reclaim their own deposit via `cancel()` once the cancellation timelock elapses. This is a real broken-balance/broken-accounting invariant reachable without any privileged role.

A more severe secondary consequence is possible but less certain: if the maker submits a `withdraw` transaction with the correct (matching-hash) immutables and it reverts due to the underflow, the `secret` argument is still publicly visible in the failed transaction's calldata. A taker who observes this could use the leaked secret to withdraw the maker's funds from `EscrowSrc` on the source chain while the destination escrow never pays out and is later cancelled back to the taker. This would elevate the impact toward theft/permanent freezing of funds (High/Critical), but this escalation depends on mempool/calldata visibility and timing assumptions relative to the source-side cancellation timelock, so it is flagged with lower confidence than the core Medium finding.

### Likelihood Explanation
High. `createDstEscrow` is a normal, unauthenticated, frequently-invoked function in the live swap lifecycle; no whitelist or governance check restricts who can call it or what `parameters` they encode. Any resolver/taker (an unprivileged actor per the bounty's attacker model) can trigger this by miscalculating or maliciously inflating `protocolFeeAmount`/`integratorFeeAmount` relative to `amount` at deployment time, and the effect is deterministic and permanent for that escrow instance.

### Recommendation
Add the same guard used in `BaseEscrowFactory._postInteraction` to `createDstEscrow`:
```solidity
if (integratorFeeAmount + protocolFeeAmount >= immutables.amount) revert InvalidFeeAmounts();
```
using `ImmutablesLib.integratorFeeAmount`/`protocolFeeAmount` decoded from `dstImmutables.parameters`, before deploying the clone. Alternatively (or additionally), make the subtraction in `EscrowDst._withdraw` `unchecked` with an explicit `require`/custom-error check, so the failure mode is a clear, well-defined revert rather than an unguarded underflow, and consider validating fee consistency between the source-chain `SrcEscrowCreated`/`DstImmutablesComplement` data and the actual `dstImmutables` supplied to `createDstEscrow`.

### Proof of Concept
1. Resolver (taker) computes `dstImmutables` for a swap where `amount = 1000` (destination token units).
2. Taker crafts `dstImmutables.parameters` so that `protocolFeeAmount = 600` and `integratorFeeAmount = 500` (sum `1100 > 1000`), packed per the layout expected by `ImmutablesLib` (`0x20`/`0x40`/`0x60`/`0x80` offsets). [9](#0-8) 
3. Taker calls `createDstEscrow(dstImmutables, srcCancellationTimestamp)`, funding it with the required native/ERC20 amount; no check rejects the fee configuration. [3](#0-2) 
4. Once the withdrawal window opens, the maker calls `EscrowDst.withdraw(secret, immutables)` using the exact `immutables` matching the deployed hash. Execution reaches `_withdraw`, computing `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount = 1000 - 500 - 600`, which underflows and reverts (Solidity 0.8 panic). [1](#0-0) 
5. Every subsequent `withdraw`/`publicWithdraw` call with the same (only valid) immutables reverts identically — the maker can never claim the destination funds from this escrow.
6. After the cancellation timelock, the taker calls `cancel(immutables)` and recovers their full deposited `amount` plus the safety deposit, having paid nothing to the maker. [8](#0-7)

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
