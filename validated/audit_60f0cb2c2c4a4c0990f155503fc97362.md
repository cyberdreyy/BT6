### Title
Miner's StackerDB rejection aggregator drops a signer's re-evaluated rejection if that signer already accepted, letting stale acceptance weight count toward the broadcast threshold - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side `StackerDBListener` (analogous role to a coordinator tallying signer votes) tracks per-slot participation in a single `responded_signers: HashSet<u32>` shared between the `Accepted` and `Rejected` code paths. The `Accepted` branch guards double-counting via `gathered_signatures.contains_key(&slot_id)`, while the `Rejected` branch guards via `responded_signers.insert(slot_id)`. Because both branches write into the same `responded_signers` set, a signer that first accepts and later legitimately re-evaluates and rejects the same block has its rejection silently dropped, leaving the earlier (now-withdrawn) acceptance weight permanently counted toward `total_weight_approved`.

### Finding Description
`stacks-signer`'s own state machine explicitly allows a block to move from `LocallyAccepted` back to `LocallyRejected` on re-evaluation (documented in `docs/signer-flows.md` stateDiagram: `LocallyAccepted --> LocallyRejected : re-evaluated`), and `BlockInfo::check_state` in [1](#0-0)  permits this transition (`LocallyAccepted | LocallyRejected` states are reachable from anything not yet global). This means a single signer, upon seeing a conflicting/higher proposal or a state change, can validly flip from having accepted a block to rejecting it, and will broadcast a new `Rejected` `BlockResponse`.

On the miner side, `StackerDBListener::run` processes `BlockResponse::Accepted` and `BlockResponse::Rejected` messages independently:

- In the `Accepted` branch, weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, then `block.gathered_signatures.insert(slot_id, signature)` and `block.responded_signers.insert(slot_id)` unconditionally run: [2](#0-1) 
- In the `Rejected` branch, weight is added to `total_weight_rejected` only `if block.responded_signers.insert(slot_id)` succeeds (i.e., only if the slot hasn't already responded at all): [3](#0-2) 

Since the same `responded_signers` set is shared and never cleared/updated per-message-type, once a signer's slot is present (from an earlier `Accepted`), a subsequent `Rejected` from that same signer fails the `insert` check and the rejection weight is never recorded — and, critically, `total_weight_approved` is also never decremented for the earlier stale acceptance. The aggregator thus permanently retains "approved" weight from a signer that has since withdrawn support, breaking the equality between "aggregated weight" and "the set of signers currently and validly accepting the block."

### Impact Explanation
This is the "rejection recounted as an accept" class of bug: a signer's legitimate rejection is discarded and its earlier acceptance keeps counting. If enough signers flip from accept to reject on a block that turns out to be non-canonical or conflicting (e.g., a competing block was found to be canonical, or the block's parent context changed), the miner's coordinator can still believe `total_weight_approved >= self.weight_threshold` in [4](#0-3)  is satisfied purely from stale, withdrawn acceptances, causing the miner to broadcast/push a block that a supermajority of signers no longer actually support at the moment of broadcast. This directly threatens the "aggregated-weight vs verified-accepts" equality the scan targets and can lead to the network accepting a block whose live signer support has fallen below threshold — a safety-relevant miscount reachable by ordinary re-evaluation/gossip, not requiring a signer majority or key compromise.

### Likelihood Explanation
This requires no malicious majority — it can be triggered by the normal, single-signer re-evaluation path (`LocallyAccepted -> LocallyRejected`) that the signer software itself performs whenever it sees a conflicting proposal, timeout, or fresh SortitionsView/GlobalStateView result after having already accepted a block, combined with ordinary gossip delivering both messages to the miner's listener. Any one signer flipping its vote after an initial accept is sufficient to create the stale-weight artifact; if this occurs across several signers near the threshold boundary, the miner's tally can diverge materially from the live vote.

### Recommendation
Track accept/reject participation per-slot with a single, overwritable record (e.g., `HashMap<u32, Vote>` instead of separate `gathered_signatures`/`responded_signers` sets) so that a later `Rejected` from a signer who previously `Accepted` removes their weight from `total_weight_approved` and adds it to `total_weight_rejected` (and vice versa), keeping the aggregate weights synchronized with the latest known vote per signer.

### Proof of Concept
1. Reward set with signers A (40% weight), B (35%), C (25%); `weight_threshold` = 70%.
2. A and B send `BlockResponse::Accepted` for block X → `total_weight_approved` = 75% (≥ threshold), `gathered_signatures`/`responded_signers` contain A, B.
3. Before/while the miner processes threshold logic, A re-evaluates (e.g., sees a conflicting higher block) and legitimately transitions `LocallyAccepted -> LocallyRejected`, broadcasting `BlockResponse::Rejected` for X.
4. In `StackerDBListener`, the `Rejected` branch executes `block.responded_signers.insert(slot_id)` for A's slot — this returns `false` because A's slot is already present from step 2, so the `if` body (which would add A's weight to `total_weight_rejected`) never runs.
5. `total_weight_approved` remains 75% (A's now-withdrawn 40% is never removed), so the miner's threshold check in `signer_coordinator.rs` (`total_weight_approved >= weight_threshold`) still reports the block as accepted, even though only B (35%) currently supports it — well below the 70% threshold.

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
