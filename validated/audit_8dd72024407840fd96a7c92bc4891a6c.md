### Title
`parse_confidential_mint_burn_instruction` relabels an untrusted account as `proofContextStateAccount` or `instructionsSysvar` based solely on the attacker-supplied `proof_instruction_offset` field, with no verification of the account's actual role - (File: `transaction-status/src/parse_token/extension/confidential_mint_burn.rs`)

### Summary
In the `RotateSupplyElGamalPubkey` branch of `parse_confidential_mint_burn_instruction`, the label attached to `account_indexes[1]` (`proofContextStateAccount` vs `instructionsSysvar`) is chosen purely from the client-controlled `proof_instruction_offset` field of the decoded `RotateSupplyElGamalPubkeyData`, without any cross-check against the account's real on-chain identity (e.g. comparing it to `sysvar::instructions::id()`) or its actual account data. An attacker can submit an instruction (even one that will fail on-chain) with an arbitrary account at that index and an arbitrary `proof_instruction_offset`, causing the RPC-facing "parsed" JSON to attach a misleading semantic label to that account.

### Finding Description
The relevant code is: [1](#0-0) 

```
let offset = 1;
if offset < account_indexes.len().saturating_sub(1) {
    if rotate_supply_data.proof_instruction_offset == 0 {
        map.insert("proofContextStateAccount", ...account_keys[account_indexes[offset]]...);
    } else {
        map.insert("instructionsSysvar", ...account_keys[account_indexes[offset]]...);
    }
}
```
`rotate_supply_data` is fully attacker-controlled: it comes straight from `decode_instruction_data(instruction_data)` [2](#0-1)  with no further validation of the field value against the actual account passed at `account_indexes[1]`. The parser never checks that the account at that index is actually `sysvar::instructions::id()` (for the "instructionsSysvar" case) or that it is actually a proof context-state account owned by the ZK-ElGamal-proof program (for the "proofContextStateAccount" case). It simply branches on whether the offset field is zero.

This is consistent with the general design of the `transaction-status` "parsed" instruction decoders throughout the crate (e.g., the analogous but runtime-unverified offset-based logic in `confidential_transfer.rs`): they are best-effort explainers of instruction data for RPC consumers (`getTransaction`/`getConfirmedTransaction` "jsonParsed" encoding) and do not consult runtime account state, since the parser only has access to `instruction_data`, `account_indexes`, and `account_keys` — never actual account contents or ownership.

The attack requires no privilege beyond submitting a transaction (which can even fail on-chain, since the instruction is decoded at the transaction-status/history layer regardless of execution outcome) that invokes `RotateSupplyElGamalPubkey` with a crafted `proof_instruction_offset` value and an arbitrary account at `account_indexes[1]`.

### Impact Explanation
Downstream integrators (explorers, indexers, compliance/auditing tools) that trust the `jsonParsed` output for confidential mint/burn instructions will display an incorrect semantic label (`proofContextStateAccount` vs `instructionsSysvar`) for an account that has no relation to that role. This falls under "misreporting" of parsed instruction data ([File: svm/src/transaction_execution_result.rs] scope, "decoder panic and misreporting" being one of the explicitly accepted impact categories) rather than any consensus-affecting or crash-inducing bug — the on-chain execution semantics are unaffected; only the RPC-exposed parsed representation is misleading.

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: any client can construct a `RotateSupplyElGamalPubkey` instruction with an arbitrary account list and an arbitrary `proof_instruction_offset` value, submit it once (it need not even succeed on-chain, since transaction-status parsing runs on any transaction included in a block/returned by RPC), and observe the resulting label flip deterministically based solely on the offset field.

### Recommendation
Do not assert a specific account role in the parsed output based solely on the attacker-supplied offset field. Either (a) omit the specific `proofContextStateAccount`/`instructionsSysvar` key names and instead emit a neutral field name (e.g. `proofAccount`) annotated with the raw offset value, letting consumers interpret it themselves, or (b) where feasible, validate the labeled account against known well-known identifiers (e.g., compare to `solana_sdk_ids::sysvar::instructions::id()` before emitting `instructionsSysvar`) and only apply the `proofContextStateAccount` label when independently corroborated, falling back to a generic label otherwise.

### Proof of Concept
```rust
// transaction-status/src/parse_token/extension/confidential_mint_burn.rs (test)
#[test]
fn test_rotate_label_flip_independent_of_real_role() {
    let mint = Pubkey::new_unique();
    let authority = Pubkey::new_unique();
    let arbitrary_account = Pubkey::new_unique(); // not a real context-state account, not the sysvar

    // Build two otherwise-identical instructions differing only in proof_instruction_offset,
    // but keep account_indexes[1] pointing at the same `arbitrary_account`.
    let instr_offset_zero = build_rotate_instruction_with_account(
        &mint, &authority, &arbitrary_account, /*proof_instruction_offset=*/0,
    );
    let instr_offset_nonzero = build_rotate_instruction_with_account(
        &mint, &authority, &arbitrary_account, /*proof_instruction_offset=*/1,
    );

    let msg0 = Message::new(&[instr_offset_zero], None);
    let msg1 = Message::new(&[instr_offset_nonzero], None);

    let parsed0 = parse_token(&msg0.instructions[0], &AccountKeys::new(&msg0.account_keys, None)).unwrap();
    let parsed1 = parse_token(&msg1.instructions[0], &AccountKeys::new(&msg1.account_keys, None)).unwrap();

    // Same underlying account, but relabeled purely based on attacker-chosen offset:
    assert_eq!(parsed0.info["proofContextStateAccount"], json!(arbitrary_account.to_string()));
    assert!(parsed0.info.get("instructionsSysvar").is_none());

    assert_eq!(parsed1.info["instructionsSysvar"], json!(arbitrary_account.to_string()));
    assert!(parsed1.info.get("proofContextStateAccount").is_none());

    // The account's real role never changed; only the attacker-controlled offset did.
}
```
This demonstrates that the emitted role label for `account_indexes[1]` is a direct, unconditional function of the attacker-controlled `proof_instruction_offset` field, independent of the account's actual identity or role.
