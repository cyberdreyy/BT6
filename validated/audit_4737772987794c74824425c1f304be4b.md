### Title
Unit mismatch in Store.List() length check allows attacker-crafted masking.db entries to panic proxy-exec (masking bypass on crash) - (File: commands/helpers/internal/store/store.go)

### Summary
`Store.List()` compares the raw base64-encoded line length against `s.c.NonceSize()` instead of checking the length of the decoded message (`len(msg)`), and these are not the same units. Because base64 expands 3 bytes into 4 characters, a line whose encoded length satisfies `len(line) >= NonceSize()` can still decode to fewer than `NonceSize()` bytes, causing `msg[:s.c.NonceSize()]` at [1](#0-0)  to panic with a slice-out-of-range error.

### Finding Description
`Store.List()` reads lines from `masking.db`, base64-decodes each into `msg`, then guards against short messages with `if len(line) < s.c.NonceSize()` before slicing `msg[:s.c.NonceSize()]`: [2](#0-1) 

The check uses `len(line)` (the base64 string, including the trailing `\n` from `ReadString('\n')`) rather than `len(msg)` (the decoded byte slice that is actually sliced). Since base64 encodes 3 bytes as 4 characters, `len(msg) ≈ len(line) * 3/4`, and with padding it can be even smaller. `chacha20poly1305.NewX` sets `NonceSize() == 24`. A line whose length is at or slightly above 24 characters can decode to well under 24 bytes (e.g., a 24-character base64 string decodes to at most 18 bytes, and with `=` padding fewer still). The length check therefore does not guarantee `len(msg) >= s.c.NonceSize()`, and `msg[:24]` on a shorter slice panics.

`masking.db` is opened via `store.Open` in `commands/helpers/proxy_exec.go` inside the job's temp/build directory (`RUNNER_TEMP_PROJECT_DIR` or `--temp-dir`): [3](#0-2) [4](#0-3) 

`proxy-exec` is invoked per script step to run the masking proxy (`addmask` package reads previously-masked phrases back via `Store.List()` to persist masking across steps within the same job). Because `masking.db` lives in the job's own workspace/temp directory, and the pipeline author's own script executes with filesystem access to that same directory between/alongside `proxy-exec` invocations, an unprivileged pipeline author can write or append a crafted line to `masking.db` before a later script step's `proxy-exec` call triggers `Store.List()`. There is no existing check anywhere in the read path that validates decoded length against encoded length correctly — the only check present is the flawed `len(line) < NonceSize()` comparison.

### Impact Explanation
A crafted `masking.db` line causes the `gitlab-runner-helper proxy-exec` process to panic (slice bounds out of range) mid-invocation. Since `proxy-exec` wraps the masking pipeline for a script step's stdout/stderr, a crash aborts that masking proxy. Depending on timing (panic occurring before `addmask` finishes wrapping the writers, or during `Close()`), previously-masked or subsequently-written secret values for that step could be emitted to the job log/trace unmasked, since the masking wrapper is no longer intercepting output correctly once the helper process has died. This matches the scoped impact: proxy-exec helper crash aborts masking, and output can be emitted unmasked.

### Likelihood Explanation
- Precondition: the runner must be configured to use `ProxyExec` (the masking-proxy execution mode) — this is opt-in but is exercised in the runner's own masking test suite (`common/buildtest/masking.go`, `TestBuildMaskingProxyExec`), confirming it is a supported, real feature path.
- The attacker only needs pipeline-author-level control (writing arbitrary shell/script commands) to append a crafted base64 line into the `masking.db` file located in the job's own temp/build directory before a subsequent script step invokes `proxy-exec` again.
- Constructing a base64 string with `len(line) >= 24` that decodes to `< 24` bytes is trivial and deterministic (e.g., short payloads padded with `=`), making this a repeatable, always-reproducible parsing bug rather than a probabilistic one.

### Recommendation
Fix the check in `Store.List()` (`commands/helpers/internal/store/store.go`) to validate the decoded byte length instead of the encoded string length:
```go
if len(msg) < s.c.NonceSize() {
    return results, fmt.Errorf("encrypted message length too small")
}
```
This ensures `msg[:s.c.NonceSize()]` and `msg[s.c.NonceSize():]` are always safe regardless of base64 expansion effects, padding, or malformed/short input.

### Proof of Concept
Go unit test in `commands/helpers/internal/store/store_test.go`:
```go
func TestList_ShortDecodedMessage_NoPanic(t *testing.T) {
    dir := t.TempDir()
    db, err := Open(dir)
    require.NoError(t, err)
    defer db.Close()

    // Craft a base64 line whose *encoded* length >= NonceSize() (24)
    // but whose *decoded* length is well under NonceSize().
    // e.g. 8 raw bytes -> 12 base64 chars is too short; pad to
    // reach an encoded length >= 24 while decoded len < 24.
    shortMsg := []byte{0x01, 0x02, 0x03, 0x04, 0x05, 0x06} // 6 bytes decoded
    encoded := base64.StdEncoding.EncodeToString(shortMsg)
    for len(encoded) < 24 {
        // pad encoded string with valid base64 padding chars/newlines
        // to satisfy len(line) >= NonceSize() while len(decoded) stays < 24
        encoded += "AA=="
    }
    line := encoded + "\n"

    require.NoError(t, os.WriteFile(filepath.Join(dir, "masking.db_extra"), nil, 0o644)) // placeholder

    // Append the crafted line directly after the 32-byte key header.
    f, err := os.OpenFile(filepath.Join(dir, "masking.db"), os.O_RDWR, 0o644)
    require.NoError(t, err)
    _, err = f.Seek(0, io.SeekEnd)
    require.NoError(t, err)
    _, err = f.WriteString(line)
    require.NoError(t, err)
    require.NoError(t, f.Close())

    require.NotPanics(t, func() {
        _, err := db.List()
        require.Error(t, err) // must return an error, not panic
    })
}
```
Expected: with the current code, this test panics with `runtime error: slice bounds out of range` when `msg[:s.c.NonceSize()]` is evaluated on a decoded slice shorter than 24 bytes. After applying the recommended fix (checking `len(msg)` instead of `len(line)`), `Store.List()` returns a clean error (`"encrypted message length too small"`) instead of crashing.
