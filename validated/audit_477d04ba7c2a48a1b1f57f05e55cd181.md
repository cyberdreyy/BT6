### Title
Stale confirmations from removed multisig members are still counted toward the approval threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm()` in `multisig2/src/lib.rs` counts entries in the `confirmations` `HashSet<String>` for a request without verifying that each confirming identity is still a current member. `delete_member()` only removes confirmation state for requests *created by* the removed member, not for other pending requests that member had already confirmed. This lets a request execute using a confirmation from an account/key that is no longer part of the multisig, breaking the "confirmations counted versus live members" invariant.

### Finding Description
The relevant binding that must hold is:
`num_confirmations_from_current_members(request) >= self.num_confirmations`

`confirm()` instead checks:
```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
``` [1](#0-0) 

`confirmations` is a raw `HashSet<String>` keyed by `member.to_string()` with no cross-check against the live `self.members` set at execution time [2](#0-1) .

When a member is removed via the `DeleteMember` action, `delete_member()` only cleans up requests that member itself created (`r.member == member`); it does not scan `self.confirmations` to strip that member's confirmation from *other* pending requests they had already confirmed:
```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&member.to_string());
    self.members.remove(&member);
    ...
}
``` [3](#0-2) 

Sequence:
1. Member A creates Request X (`add_request`). Member B (still a valid member) confirms it via `confirm()`, inserting `"B"` into `confirmations[X]`.
2. Separately, a `DeleteMember { member: B }` request is submitted and executed, removing B from `self.members`. Because Request X was created by A (not B), the loop in `delete_member` never touches Request X, so `confirmations[X]` still contains `"B"`.
3. If `num_confirmations` is, say, 2 and originally 3 members existed, X now only needs one more live confirmation because B's stale confirmation still counts — even though B is no longer authorized to approve anything.
4. A single remaining valid member confirms X; `confirm()` sees `confirmations.len() + 1 >= num_confirmations` (stale B + live confirmer) and executes the request — a `Transfer`, `AddKey`, `FunctionCall`, etc. — despite only one *currently valid* member having actually approved it.

The identical structural flaw exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` only purges requests whose `signer_pk` equals the deleted key, leaving that key's confirmations on other requests intact [4](#0-3) [5](#0-4) .

### Impact Explanation
This breaks the multisig's core authorization guarantee: a request can be executed by the contract's own account key/funds (`Transfer`, `AddKey`, `FunctionCall`, `DeployContract`) with fewer genuinely-authorized confirmations than `num_confirmations` mandates, because a removed member's stale approval is silently retained and counted. Per the rules, this matches "Critical - NEAR moved by a party not entitled to it... a multisig request executed below threshold."

### Likelihood Explanation
This requires no privileged action beyond the normal multisig workflow already exposed to members (`add_request`, `confirm`, and a legitimate `DeleteMember`/`DeleteKey` execution) — no foundation, victim key, redeploy, or external actor is needed. The only precondition is that a member confirms a request before being removed and that request remains open, which is an ordinary operational sequence (e.g., legitimate member rotation) rather than a contrived edge case, making likelihood credible whenever membership changes while requests are in flight.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over **all** pending requests' confirmation sets (not just those created by the removed member) and remove the departing member's entry from each; alternatively, when checking the threshold in `confirm()`, filter `confirmations` to only entries whose corresponding member/key is still present in `self.members` before comparing against `self.num_confirmations`.

### Proof of Concept
Using the existing `multisig2` test harness (`MultiSigContract::new(members(), num_confirmations)`), construct:
1. Member A: `add_request(request_X)` (any action, e.g., `Transfer`).
2. Member B: `confirm(request_X)` — inserts B into `confirmations[request_X]`, does not yet execute since `num_confirmations` not reached.
3. Any sufficient set of members: `add_request_and_confirm(DeleteMember{member: B})` to reach threshold and execute B's removal — this only clears requests where `r.member == B` (there are none, since A created request_X), so `confirmations[request_X]` still contains B's entry and `self.members` no longer contains B.
4. A single additional current member confirms `request_X`: `confirm(request_X)` — since `confirmations.len() (1, from stale B) + 1 >= num_confirmations` (e.g., 2), the request executes, even though only one *current* member ever confirmed it.
5. Assert `get_confirmations(request_X)` still lists B (pre-removal) and that `request_X`'s action executed despite B no longer being in `get_members()`.
