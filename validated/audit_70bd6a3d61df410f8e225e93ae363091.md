## Title
Response cache key omits `WorkflowID`, causing cross-workflow HTTP response leakage in the CRE Gateway HTTP handler - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The Gateway's HTTP capability response cache is keyed by `OutboundHTTPRequest.Hash()`, which — like the Panoptic `s_accountLiquidity` update that checked only the right slot and ignored the left slot — validates/derives its identity from only part of the request's state. The hash intentionally omits `WorkflowID` while including `WorkflowOwner`, method, URL, headers, and body. Two different workflows owned by the same owner that issue identical outbound HTTP action requests (same method/URL/headers/body) collide on the same cache key, so one workflow's cached HTTP response can be served to a completely different workflow.

### Finding Description
`responseCache.Fetch`/`Set`/`isExpiredOrNotCached` all key the cache map by `req.Hash()` [1](#0-0)  and the same key is used for both the fast-path check and singleflight-protected slow path [2](#0-1) .

The hashing test explicitly documents and asserts that `WorkflowID` is excluded from the hash while `WorkflowOwner` is included: [3](#0-2) 

This directly contradicts the component's own documented guarantee: "**Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [4](#0-3) .

In practice, the cache is populated and read via `makeOutgoingRequest`, which passes the full `gateway_common.OutboundHTTPRequest` (including `WorkflowID`) straight into `Fetch`/`Set` without any additional per-workflow scoping at the call site: [5](#0-4) . Since the cache key does not include `WorkflowID`, any workflow (potentially belonging to a different DON job, tenant scope, or dataset) that happens to issue byte-identical HTTP action requests (same method, URL, headers, body) will read the other workflow's cached `OutboundHTTPResponse` if `CacheSettings.MaxAgeMs > 0`, or will have its own fresh response silently reused by that other workflow later.

This is a structural analog to the Panoptic issue: the "identity" used to gate/derive shared mutable state (there: `positionKey` intentionally omitting long/short distinction and only checking `rightSlot`; here: cache key intentionally omitting `WorkflowID`) is narrower than the full identity of the logical entities using that state, so one entity's data bleeds into another's.

### Impact Explanation
This falls under "cross-user response confusion," an explicitly accepted analog category. A workflow can receive an HTTP action response that was actually fetched for a different workflow (e.g., stale data, data intended for a different downstream execution, or data fetched under different parameters believed to be workflow-specific). Because `WorkflowOwner` is included but `WorkflowID` is not, this specifically affects multiple workflows deployed by the same owner — a very plausible real-world scenario (an owner running several workflows that call the same external API/URL). Depending on how workflow logic consumes the HTTP action result (e.g., for pricing, oracle-like external data, or business logic gating fund movements), incorrect cross-workflow data could silently corrupt one workflow's execution using another's response.

### Likelihood Explanation
Likelihood is moderate: it requires two workflows from the same owner making outbound HTTP actions with identical method, URL, headers, and body while using `CacheSettings.Store`/`MaxAgeMs`. This is a realistic configuration pattern (e.g., templated workflows or workflows built from the same tool hitting a shared API endpoint), and it is triggered purely through normal, unprivileged workflow authoring — no malicious node or gateway/network-layer compromise is needed.

### Recommendation
Include `WorkflowID` (or another unique workflow identifier) as part of `OutboundHTTPRequest.Hash()`'s digest input alongside method, URL, headers, body, and `WorkflowOwner`, so that cache entries are correctly scoped per-workflow as the design document already claims. Update `TestRequestHash`'s "having different workflowID results in same Hash" test to instead assert different hashes for different `WorkflowID`s.

### Proof of Concept
1. Workflow A (owner `0xabc`, `WorkflowID: "workflow-123"`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", WorkflowOwner: "0xabc"}` with `CacheSettings.Store = true`.
2. The gateway calls `responseCache.Set(reqA, respA)`, storing under key `reqA.Hash()` [6](#0-5) .
3. Workflow B (same owner `0xabc`, but `WorkflowID: "workflow-456"`) issues an identical `OutboundHTTPRequest` (same method/URL/headers/body/owner) with `CacheSettings.MaxAgeMs > 0`.
4. Because `reqA.Hash() == reqB.Hash()` (proven directly by the existing unit test) [7](#0-6) , `responseCache.Fetch(reqB, ...)` returns Workflow A's cached response to Workflow B without ever calling the HTTP client [8](#0-7) .

// isExpiredOrNotCached returns true if the cached response is expired or not cached.
// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
- **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage

func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
