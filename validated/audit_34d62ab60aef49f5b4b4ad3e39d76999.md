### Title
Claimed instant withdrawals are never removed from `instantWithdrawsClaimsByEpoch`/`instantWithdrawsRequestsByEpoch`, corrupting default-recovery accounting and draining the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`claimInstantWithdrawRequest` pays the user at par but only clears the aggregate `instantWithdrawsRequests[_user]`. It never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If the same epoch later ends in a borrower default, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` reuse these stale, already-paid amounts: the already-claimed instant withdrawals are counted both as outstanding recovery claims and as "prefunded" cash reserve. The resulting `defaultRecoveryPrice` is computed over phantom funds, so recovery claimants are overpaid on paper while the actual cash is short — the reserve is drained early and the last claimants' payouts revert permanently (`defaultRecoveryReserve -= _amount` underflow / insufficient balance in `_transferDefaultRecovery`).

### Finding Description

The instant-withdraw lifecycle is:

1. `requestInstantWithdraw` mints receipt tokens and records `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` (`IdleCreditVault.sol:366-374`).
2. When the request is funded and claimed, `claimInstantWithdrawRequest` only does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

(`IdleCreditVault.sol:387-392`) — the per-epoch ledgers `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are left populated.

3. If the borrower defaults in that same epoch (epochNumber is *not* bumped on default — see `IdleCDOEpochQueue.sol:290` `_prefundedEpochToProcess` comment and `finalizeDefaultRecovery` setting `defaultRecoveryEpoch = epochNumber` at `IdleCreditVault.sol:693`), the stale entries re-enter accounting:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];   // includes already-paid claims
}
```

(`IdleCreditVault.sol:644-648`)

and

```solidity
if (instantBasis > pendingInstant) {
  prefundedReserve = instantBasis - pendingInstant;     // treats paid claims as held cash
}
```

(`IdleCreditVault.sol:719-722`)

`prefundedReserve` is supposed to represent underlying already collected for the current epoch's instant queue. Because claimed amounts were never subtracted, money that already left the contract is counted as reserve, inflating `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (`IdleCreditVault.sol:688`).

There is a second, partially self-correcting symptom: a claimant whose instant receipt was paid in the default epoch cannot re-claim through `_claimDefaultedInstantWithdrawRequest` because `instantWithdrawsRequests[_user] -= claimBasis` underflows (`IdleCreditVault.sol:848`). But the stale basis remains in `instantWithdrawClaimsByEpoch` and `prefundedReserve` regardless, so the mispricing and reserve shortfall still occur.

### Impact Explanation

Direct theft plus permanent freezing of unclaimed recovery funds:

- `defaultRecoveryPrice` is inflated by `(paidInstantClaims) / totalBasis` worth of phantom reserve, so genuine default-epoch claimants (normal withdrawers via `_claimDefaultedWithdrawRequest`, unfunded instant claimants via `_claimDefaultedInstantWithdrawRequest`, post-default requesters via `_claimPostDefaultWithdrawRequest`) draw on a reserve that is smaller than accounted.
- The shortfall equals the total instant withdrawals already paid at par during the default epoch (`instantWithdrawClaimsByEpoch[defaultEpoch] - Σ unclaimed`). Whoever claims last hits an underflow in `_transferDefaultRecovery` (`defaultRecoveryReserve -= _amount`, `IdleCreditVault.sol:915`) or an insufficient balance — their recovery claim is permanently frozen.
- Equivalently, earlier claimants extract more than their fair share: the invariant "one receipt, one pro-rata payout" and the loss-waterfall are broken.

Quantified loss: up to the full amount of instant withdrawals claimed at par earlier in the defaulted epoch, redistributed away from other recovery claimants / frozen in the reserve.

### Likelihood Explanation

Requirements:

- Instant withdrawals enabled (`allowInstantWithdraw`), at least one instant request funded and claimed during epoch N (`getInstantWithdrawFunds` → `collectInstantWithdrawFunds` → `claimInstantWithdrawRequest`).
- At least one *unfunded* instant request outstanding in epoch N (`pendingInstantWithdraws != 0` at finalization — e.g., a request submitted after the funding collection, or a partial collection).
- Borrower default in epoch N via `_handleBorrowerDefault`, then `finalizeDefaultRecovery`.

No privileged misbehavior is needed — manager/guardian calls are honest and sequenced normally; only the unprivileged claimant actions and an ordinary borrower default (an in-scope honest-failure event handled by the protocol) are required. The stale-ledger cleanup omission is deterministic once these conditions coincide.

### Recommendation

In `claimInstantWithdrawRequest` (and its internal helpers), clear the per-epoch ledgers exactly like `_claimDefaultedInstantWithdrawRequest` does:

```solidity
function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
        _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    _burn(_user, amount);
    instantWithdrawsRequests[_user] = 0;
    // cleanup: attribute the paid claim to its request epoch(s) so it cannot
    // be re-counted by defaultPendingClaimBasis / _defaultPrefundedInstantReserve
    instantWithdrawClaimsByEpoch[epochOfRequest] -= amount;
    instantWithdrawsRequestsByEpoch[_user][epochOfRequest] = 0;
    _transferFundedClaim(_user, amount);
}
```

Since requests of different epochs can be aggregated, either track the request epoch per instant receipt (e.g., `lastInstantRequestEpoch` analogous to `lastWithdrawRequest`, with a guard preventing mixing epochs) or maintain a per-user running epoch pointer and clear `instantWithdrawsRequestsByEpoch` for each funded epoch before payment.

### Proof of Concept

Foundry fork/ftest scenario (based on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testStaleInstantClaimCorruptsDefaultRecovery() external {
    // Setup: standard epoch variant, instant withdraws enabled, AA deposit of 1000e6
    uint256 amount = 10000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);                    // epoch N running

    // 1) Alice instant-requests 100 and gets funded + claimed at par
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(/* enable, deadline */);
    cdoEpoch.requestInstantWithdraw(100 * ONE_TRANCHE, address(AAtranche)); // via CDO as Alice
    // manager pulls instant liquidity from borrower
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();              // collectInstantWithdrawFunds(100)
    // Alice claims at par after instant deadline
    cdoEpoch.claimInstantWithdrawRequest();
    // stale: instantWithdrawsRequestsByEpoch[alice][N] == 100
    //        instantWithdrawClaimsByEpoch[N] == 100, pendingInstantWithdraws == 0

    // 2) Bob instant-requests 50 in the SAME epoch, left unfunded
    bobRequestInstantWithdraw(50 * ONE_TRANCHE);     // instantWithdrawClaimsByEpoch[N] == 150
    assertEq(strategy.pendingInstantWithdraws(), 50 * ONE_SCALE);

    // 3) Epoch ends; borrower cannot repay -> _handleBorrowerDefault in stopEpoch
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, expectedInterest);         // defaults
    assertTrue(cdoEpoch.defaulted());

    // 4) Finalize default recovery with the real recovered cash only
    uint256 recovered = /* whatever borrower recovered */;
    finalizeDefaultRecovery(recovered);

    // BUG: defaultPendingClaimBasis counted 150 instead of 50,
    // and _defaultPrefundedInstantReserve credited 100 phantom cash.
    // defaultRecoveryPrice is inflated; reserve is short by Alice's paid 100.

    // 5) Bob claims his default-epoch instant receipt at inflated price
    claimInstantAs(bob);                              // pays 50 * inflatedPrice

    // 6) A normal default-epoch withdrawer claims last -> reverts:
    //    _transferDefaultRecovery underflows / balance < amount
    vm.expectRevert();
    claimWithdrawAs(carol);                          // permanent freeze of recovery claim
}
```

Assertions to include:
- `strategy.instantWithdrawsRequestsByEpoch(alice, N)` remains `100 * ONE_SCALE` after Alice's at-par claim (the missing cleanup).
- `strategy.defaultPendingClaimBasis()` includes the stale 100 during finalization.
- Final `defaultRecoveryReserve` is exhausted before all legitimate claims are paid; the last claim reverts.

Caveat: exact helper names (`_startEpochAndCheckPrices`, instant-withdraw CDO entry points, `finalizeDefaultRecovery` call path through the CDO) should be matched to the repo's test suite; the state assertions above are the load-bearing part of the PoC.
