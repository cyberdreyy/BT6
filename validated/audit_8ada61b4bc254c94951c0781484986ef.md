### Title
Withdraw-request receipt tokens (IdleCreditVault strategy tokens) sent back to the IdleCDO by direct `transfer` are double-counted: they inflate tranche NAV via `getContractValue` while the same underlyings remain claimable by the receipt holder - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault.getContractValue()` computes NAV as the CDO's raw `strategyToken` balance plus raw `token` balance minus `unclaimedFees` (`contracts/IdleCDOCreditVault.sol:125-128`). In `IdleCreditVault.requestWithdraw`/`requestInstantWithdraw`, the CDO's strategy tokens are burned and an equal amount is minted to the requesting user as a receipt (`contracts/strategies/idle/IdleCreditVault.sol:272-275`, `356-374`). These receipt tokens are ordinary ERC20s: anyone can `transfer` them back to the CDO address. Because `_skimDonatedAssets` only sweeps `token` — never `strategyToken` (`contracts/IdleCDOEpochVariant.sol:793-796`) — donated receipt tokens permanently inflate `getContractValue` while the underlyings that back them were already moved to the strategy via `collectWithdrawFunds`/`collectInstantWithdrawFunds` and remain payable to the same user on `claimWithdrawRequest`/`claimInstantWithdrawRequest` (`_transferFundedClaim`, `IdleCreditVault.sol:897-907`). This is the direct analog of the PaymentSplitter bug: value entering the contract through a bare `transfer` bypasses all deposit accounting yet is fully reflected in NAV.

### Finding Description
Concrete sequence (fixed-APR mode, buffer phase):

1. Alice (KYC'd lender) deposits AA; the epoch starts and later stops; `collectWithdrawFunds` moves underlyings for pending receipts to `IdleCreditVault`.
2. Bob (any wallet that passed `isWalletAllowed`, or simply a previous depositor) calls `requestWithdraw`. `IdleCreditVault.requestWithdraw` burns `principal` strategy tokens from the CDO and mints `_amount` (principal + interest) receipt tokens to Bob.
3. Bob calls `strategyToken.transfer(address(cdoEpoch), _amount)`. No hook exists — like ink!'s `transfer`, the receipt arrives untracked.
4. The next `_updateAccounting` (triggered by any `depositAA`/`requestWithdraw`, or `stopEpoch`) reads `getContractValue()`, which now counts Bob's receipt as fresh strategy-token backing, and distributes the phantom gain AA/BB via `_virtualPriceAux`, raising `priceAA`/`priceBB` and `lastNAV*`.
5. Bob then calls `claimWithdrawRequest`; `_transferFundedClaim` pays him the full `_amount` from the strategy's funded balance — the reserve guard only applies to `defaultRecoveryReserve`, not to ordinary funded claims.

The same tokens therefore back two claims: once inside CDO NAV (distributed to all tranche holders and to new mints) and once as Bob's still-spendable receipt. The broken invariant is solvency/one-receipt-one-payout: NAV asserts backing that has already been paid out to the strategy's claim reserve.

### Impact Explanation
The inflation is not self-funding for the attacker — Bob loses the receipt face value to the CDO — so it is primarily a griefing/insolvency vector rather than direct profit. However the loss is real and quantified: every subsequent depositor mints shares against an inflated price and every withdrawal is priced on NAV that is not backed by liquid or strategy-held funds (the backing sits in the strategy's claim pool already owed to Bob). The last withdrawers / the borrower-facing `expectedEpochInterest` computed at `startEpoch` (`_calcInterest(getContractValue())`, `IdleCDOEpochVariant.sol:260`) are overstated by the donated amount, causing either an unwarranted borrower default check strain or insolvency equal to the donated receipt value. A BB holder can additionally steer the phantom gain's distribution to erode the AA-first-loss ordering indirectly via fee accrual (`unclaimedFees += gain * fee`).

### Likelihood Explanation
Requires only a funded withdraw receipt and a plain ERC20 transfer — no privileged role. Cost equals the donated amount, so it is a deliberate griefing or a trap for integrations that sweep/stray tokens (exactly the interoperability hazard in the original report). No existing guard stops it: `_skimDonatedAssets` covers `token` only, `requestWithdraw`/claim paths do not check CDO strategy-token provenance, and `_updateAccounting` trusts raw balances.

### Recommendation
Track the CDO's expected strategy-token backing in a dedicated counter (e.g., `cdoStrategyBacking`) updated on mint/burn/deposit paths, and compute NAV as `min(counter, rawBalance)` or skim excess `strategyToken` (to `feeReceiver` or back to the strategy) in `_skimDonatedAssets`. Alternatively have `IdleCreditVault` block transfers of receipt tokens to `idleCDO`/`strategy` addresses.

### Proof of Concept
```solidity
// foundry fork PoC, phase = buffer after a stopped epoch, fixed-APR mode
// Setup: alice deposits AA, epoch 0 starts and stops with funds collected for pending receipts.
address bob = makeAddr("bob");
_depositWithUser(bob, 10_000 * ONE_SCALE, true);   // KYC'd deposit
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

// 1) Bob opens a normal withdraw request -> receipt strategy tokens minted to bob
vm.prank(bob);
uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));
assertEq(strategyToken.balanceOf(bob), receipt);

uint256 pricePre = cdoEpoch.virtualPrice(address(AAtranche));
uint256 navPre   = cdoEpoch.getContractValue();

// 2) Untracked "deposit": bare transfer of the receipt to the CDO
vm.prank(bob);
strategyToken.transfer(address(cdoEpoch), receipt);

// 3) NAV and virtual price inflate without any accounting entry
assertEq(cdoEpoch.getContractValue(), navPre + receipt);
assertGt(cdoEpoch.virtualPrice(address(AAtranche)), pricePre);

// 4) Crystallize: any interaction splits the phantom gain into tranche prices
vm.prank(alice);
idleCDO.depositAA(ONE_SCALE);   // alice mints shares at the inflated price
assertGt(cdoEpoch.priceAA(), pricePre);

// 5) Bob still claims the same underlying from the strategy reserve
uint256 balPre = underlying.balanceOf(bob);
vm.prank(bob);
cdoEpoch.claimWithdrawRequest();
assertEq(underlying.balanceOf(bob) - balPre, receipt); // double-spend: NAV + claim
```
Invariant broken: `getContractValue` counts strategy tokens whose underlying was already escrowed for the same user's receipt claim, so aggregate tranche NAV exceeds real backing by `receipt`.
