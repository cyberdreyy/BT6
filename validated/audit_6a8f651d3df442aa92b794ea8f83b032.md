### Title
Reap/re-registration race lets an attacker's re-used requestID receive another user's in-flight DON trigger response - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`httpTriggerHandler` keys all in-flight callbacks by a single, user-controlled `requestID` string in a global map (`h.callbacks`), and `reapExpiredCallbacks` deletes an entry purely by age (`createdAt` vs `CleanUpPeriodMs`) without any coordination with node responses still in flight for that ID. Because `setupCallback` only checks for an in-use key (not a permanently-retired one), an attacker can immediately re-register the very same `requestID` right after it is reaped, and any subsequently-arriving DON node responses for the original (now-reaped) execution will be routed by `HandleNodeTriggerResponse` into the attacker's freshly-created aggregator/callback.

### Finding Description
`setupCallback` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:398-435`) stores a `savedCallback` keyed only by the caller-supplied `requestID` (validated only for non-empty and no `/`, see `validateRequestID` at lines 183-195) — there is no per-owner/per-workflow namespacing of this key. `reapExpiredCallbacks` (lines 527-544) walks `h.callbacks` and deletes any entry whose `createdAt` is older than `CleanUpPeriodMs`, using the very same duration both as the ticker interval (`Start`, line 502) and as the max-age threshold (line 533) — a request can therefore be aged-out at essentially one tick after creation in the worst case.

Once `cleanupCallback` (lines 439-446) removes the victim's entry, `HandleNodeTriggerResponse` (lines 448-496) resolves the callback purely by `resp.ID == requestID` (line 452) — it never validates that the response's aggregator instance still corresponds to the original workflow/owner. If an attacker immediately re-POSTs a trigger request reusing the same `requestID` string, `setupCallback`'s only guard (`h.callbacks[requestID]` presence check, line 402) passes because the slot was freed by the reaper, and a brand-new `savedCallback` (new `doneCh`, new per-shard `IdenticalNodeResponseAggregator`s) is installed under that key.

Any node responses for the *original* victim execution that arrive late (still addressed with the same `resp.ID`) are then fed into the attacker's aggregator via `agg.CollectAndAggregate` (line 468), keyed by `shard.donID` from `h.nodeAddrToShard[nodeAddr]`. If the victim's and attacker's workflows share a shard/DON (common in practice) and enough delayed identical victim-shard node responses arrive to reach that shard's quorum threshold, `saved.SendResponse` (line 481) delivers the victim's genuine execution result to the attacker's HTTP connection, and `cleanupCallback` closes it out as if it were the attacker's own successful request. No authentication or authorization boundary is crossed here since `requestID` is not tied to the authenticated key/owner at the response-routing layer — it's purely a map key shared across all users of the gateway instance.

### Impact Explanation
This is a cross-user response confusion / data-leak: an attacker with a legitimate (if separate) workflow can receive another user's off-chain workflow execution output — the very payload the victim expected to be its private response — by winning a race on a shared, low-entropy, and freely reusable string identifier. This maps to the "unauthorized access to another user's data / cross-user response confusion" impact class in the Chainlink bounty program.

### Likelihood Explanation
Exploitation requires: (1) the attacker knows or predicts a soon-to-reap victim `requestID` (feasible if the caller/integration uses low-entropy or otherwise guessable IDs, since nothing in the API enforces high-entropy IDs), (2) the attacker's own (otherwise legitimate) workflow shares a shard/DON assignment with the victim's, and (3) the timing race between `reapExpiredCallbacks` firing and slow node responses landing is won — this is inherently probabilistic/racy and depends on operator-configured `CleanUpPeriodMs`/`NodeSendTimeoutMs`/`MaxTriggerRequestDurationMs`, and on multiple stale node responses reaching the shard's quorum threshold after reap. No special privilege is needed beyond normal gateway API access (an authorized key for some workflow), matching the "unprivileged API client" attacker model.

### Recommendation
- Do not use a bare client-chosen string as the sole global correlation key; bind the callback slot to a value that is unguessable and unique per execution (e.g., derive/require use of the already-computed `executionIDWithTriggerIndex`/legacy execution ID, or embed workflowID/owner into the internal map key while keeping `requestID` only as the external JSON-RPC id).
- After reaping, retain a short-lived "tombstone" for the freed `requestID` (or use a monotonically-incrementing generation/nonce stored alongside the callback) so that late node responses referencing a reaped generation are dropped instead of being matched against a newly registered callback, and so `setupCallback` can also reject immediate reuse within a grace window.
- Decouple the reap threshold from the ticker interval (`CleanUpPeriodMs` should not serve both purposes) and make the max-callback-age configurable independently, with a suitable margin over `MaxTriggerRequestDurationMs`/`NodeSendTimeoutMs` so callbacks aren't reaped while legitimate retries/responses can still arrive.

### Proof of Concept
Go handler-level integration test in `http_trigger_handler_test.go`:
1. Configure `httpTriggerHandler` with a very small `CleanUpPeriodMs` (e.g., 50ms) and start it.
2. Register victim callback A via `setupCallback`/`HandleUserTriggerRequest` with `requestID = "shared-id"`, workflow W1 assigned to shard S.
3. Sleep past `CleanUpPeriodMs` so the background ticker's `reapExpiredCallbacks` deletes A's entry (assert via internal state or exposed test hook that `h.callbacks["shared-id"]` no longer exists).
4. Immediately call `setupCallback`/`HandleUserTriggerRequest` again with the same `requestID = "shared-id"` for attacker workflow W2, also assigned to shard S, capturing attacker's callback B (e.g., via a fake `handlers.Callback` implementation that records `SendResponse` calls).
5. Deliver enough delayed `HandleNodeTriggerResponse` calls (from shard S nodes, with `resp.ID = "shared-id"` and payload representing victim A's genuine result) to reach S's quorum threshold.
6. Assert that attacker callback B's `SendResponse` is invoked with the victim's payload, and that victim callback A never received a response (already errored/timed out), proving cross-user delivery of a response into the wrong callback.
