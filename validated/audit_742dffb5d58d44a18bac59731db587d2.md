### Title
Node's per-block signer weight tally double-counts a signer who rejects then later accepts, corrupting `total_weight_approved`/`total_weight_rejected` - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The node-side `StackerDBListener` (used by `SigningCoordinator`/`signer_coordinator.rs` to decide whether a proposed Nakamoto block reaches the 70% signing threshold or the 30% blocking-minority rejection threshold) tallies each signer's weight into two mutually-exclusive buckets, `total_weight_approved` and `total_weight_rejected`. The `Rejected` handler guards the weight addition with `responded_signers.insert(slot_id)` (only adds once per signer), but the `Accepted` handler guards the weight addition with `gathered_signatures.contains_key(&slot_id)` instead of `responded_signers`. This asymmetry lets a signer who first rejects and later legitimately accepts (a normal, documented re-evaluation flow) have its weight counted in **both** `total_weight_rejected` (stale, never removed) and `total_weight_approved` (new), corrupting the aggregate tallies the coordinator relies on to make consensus-affecting decisions — directly analogous to the referenced FairSide bug where the same economic action was charged twice through two independent, unsynchronized code paths.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, `BlockStatus` tracks per-block state: [1](#0-0) 

For `BlockResponse::Accepted`, the weight is added only if the slot isn't already in `gathered_signatures`: [2](#0-1) 

For `BlockResponse::Rejected`, the weight is added only if `responded_signers.insert(slot_id)` returns `true` (i.e., first response ever, not first *rejection*): [3](#0-2) 

Trace a single signer's slot through both branches:
1. Signer sends `Rejected` first → `responded_signers.insert(slot_id)` returns `true` → `total_weight_rejected += weight`; `responded_signers` now contains `slot_id`.
2. Same signer later re-evaluates and sends `Accepted` (a legitimate flow: the signer-side code documents `should_reevaluate_reject_reason` / the `reject_then_accept` transition in `signerdb.rs`, where a signature supersedes a prior rejection) → the `Accepted` branch checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (no signature stored yet) → `total_weight_approved += weight` is executed.

At no point is `total_weight_rejected` decremented when the signer flips to `Accepted`. Compare this to the signer-side `SignerDb::add_block_signature`, which explicitly deletes any prior rejection row for the same signer/block before inserting the signature: [4](#0-3) 

No equivalent cleanup exists in the node's in-memory `BlockStatus`. The result is that a single signer's weight is simultaneously present in both `total_weight_approved` and `total_weight_rejected`, so `total_weight_approved + total_weight_rejected` can exceed `total_weight`, and the rejection tally can retain "phantom" weight from signers who have since switched to supporting the block.

### Impact Explanation
`SignerCoordinator`/`signer_coordinator.rs` uses these exact fields to decide the block's fate every polling iteration: [5](#0-4) 

Because `total_weight_rejected` can retain stale weight from a signer that has already moved to `Accepted`, the miner's coordinator can compute `total_weight_rejected + weight_threshold > total_weight` and return `NakamotoNodeError::SignersRejected`, permanently discarding the block proposal — even though the *current* set of signers opposing the block, excluding the flipped one, may be below the real blocking minority. This is a liveness wedge: a valid block that should reach the 70% approval threshold can instead be treated as globally rejected (or spuriously extend the rejection-timeout escalation logic just above this snippet) due to weight that no longer reflects any signer's actual current position. This requires no majority of colluding signers and no key compromise — it can occur from a single signer's ordinary state transition during a re-proposal/retry cycle, which the signer-side code explicitly supports and expects.

### Likelihood Explanation
The reject→accept transition for a single signer is a normal, expected operational flow, not an attacker-crafted edge case: the signer flow docs and code (`should_reevaluate_reject_reason`, `reject_then_accept`) describe re-evaluating a prior rejection into an acceptance once the invalidating condition clears (e.g., transient `ConnectivityIssues`, a stale sortition view that gets refreshed, or a resubmitted proposal after timeout). Any miner-triggered re-proposal cycle combined with at least one signer experiencing a transient rejection reason resolves this path, making it readily triggerable in ordinary network conditions without requiring a majority of signers or any privileged access.

### Recommendation
Guard the `Accepted` branch's weight addition with the same `responded_signers`-based "first rejection vs first ever response" semantics used elsewhere, or explicitly subtract the signer's weight from `total_weight_rejected` (and remove it from any per-txid `failed_txids` tallies) when that signer's slot transitions from `Rejected` to `Accepted`, mirroring the DELETE-before-INSERT pattern already used in `SignerDb::add_block_signature`. At minimum, track which signers are in each bucket exclusively (e.g., a single `HashMap<u32, Vote>` rather than independent `total_weight_approved`/`total_weight_rejected` counters plus a separate `responded_signers` set) so a signer's weight can never be counted in both tallies simultaneously.

### Proof of Concept
1. Node's `StackerDBListener` is coordinating signatures for block `B` with signer slot `S` (weight `W`) among the tracked signer set.
2. Slot `S` sends `BlockResponse::Rejected` for `B` → `responded_signers.insert(S)` succeeds → `total_weight_rejected += W`.
3. The condition triggering the rejection is resolved (e.g., a stale sortition view is refreshed, or `ConnectivityIssues` clears), and per the documented `should_reevaluate_reject_reason`/re-proposal flow, slot `S`'s signer re-validates `B` and sends `BlockResponse::Accepted` with a valid signature.
4. In `stackerdb_listener.rs`'s handler for `Accepted`, `block.gathered_signatures.contains_key(&S)` is `false` (first signature for `B` from `S`), so `total_weight_approved += W` executes.
5. `total_weight_rejected` is never decremented; `block.total_weight_rejected` still includes `W` from step 2 even though slot `S` now supports the block.
6. Any subsequent independent rejections from other signers are added on top of this stale `W`, so `signer_coordinator.rs`'s check `block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` can become true — and the block is discarded via `NakamotoNodeError::SignersRejected` — using an aggregate rejection weight that double-counts slot `S`'s weight in a bucket it no longer belongs to.
