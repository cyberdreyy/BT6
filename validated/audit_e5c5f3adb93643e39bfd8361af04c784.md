## Finding

### Title
Confirmations from removed multisig members remain counted toward the approval threshold, allowing requests to execute below the configured `num_confirmations` — (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
The multisig contracts track approvals for a request in a `confirmations` set keyed by request ID, and separately track the set of valid signers in `members` (or via valid access keys in the original `multisig`). When a member/key is removed via `DeleteMember`/`DeleteKey`, the contract only purges **requests originated by** that member and that member's own `num_requests_pk` counter — it never scans other pending requests to strip confirmations that member previously cast. `confirm()` then compares `confirmations.len() + 1 >= num_confirmations` without ever revalidating that every entry in the confirmations set still corresponds to a current, live member. This breaks the binding: `confirmations counted == confirmations from live members`.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member` only cleans up requests where the member was the **requester**: [1](#0-0) 

It does not iterate `self.confirmations` to remove the deleted member's approval from other, still-pending requests that member had merely *confirmed* (not authored). The original `multisig` contract has the identical gap in the `DeleteKey` branch of `execute_request`, which only removes requests where `r.signer_pk == pk`: [2](#0-1) 

`confirm()` then blindly trusts the size of the stored confirmation set to decide whether to execute the request, without re-checking that each confirming identity is still a member: [3](#0-2) [4](#0-3) 

This is the same class of bug as the Aave exposure-ceiling report: a control (the K-of-N threshold / LTV=0 restriction) is enforced at creation time but not consistently re-validated at every state-changing entry point that can invalidate it (member removal here, vs. `transfer`/`withdraw`/`setUserUseReserveAsCollateral` in Aave). The equality that should hold — `count(confirmations) == count(confirmations from accounts in self.members)` — is broken the moment a confirming member is removed while their approval is still cached on some other pending request.

### Impact Explanation
This is Critical: it allows a multisig request (e.g., a `Transfer` of the account's NEAR, an `AddKey`, or a `DeployContract`) to execute with fewer live, currently-authorized confirmations than the contract's own `num_confirmations` requires — i.e., "a multisig request executed below threshold." A K-of-N multisig can effectively be reduced to (K-1)-of-(N-1) (or worse, if multiple members who previously confirmed different pending requests are later removed) any time member rotation occurs while requests are outstanding.

### Likelihood Explanation
Member rotation (removing a compromised or departing signer) is a routine multisig operation, and it is very plausible that a departing member has a pending confirmation outstanding on some other request at the time of their removal — there is no requirement to first clear all pending requests before removing a member. No malicious action by the removed member is required; the flaw is purely in `delete_member`/`DeleteKey` failing to sweep the `confirmations` collection.

### Recommendation
When removing a member (`delete_member`/`DeleteKey`), iterate all entries in `self.confirmations` and strip the removed member's/key's identity from every confirmation set, not just from requests they authored. Alternatively, validate at `confirm()` time (and before execution) that every identity in the stored confirmations set is still contained in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request` creating request `R` (e.g., `Transfer` of the account balance to an external address), leaving it unconfirmed.
3. `D` calls `confirm(R)` — `confirmations[R] = {D}` (1/3), request stays pending (`confirm`, `multisig2/src/lib.rs:294-315`).
4. The remaining members submit and confirm a `DeleteMember{D}` request (3-of-4, legitimately reached with A/B/C), which executes `delete_member` (`multisig2/src/lib.rs:355-379`). Because `R` was authored by `A`, not `D`, it is untouched, and `D`'s entry in `confirmations[R]` is never purged.
5. Now only `{A, B, C}` remain as members, with `num_confirmations` still 3.
6. `A` calls `confirm(R)` → `confirmations[R] = {D, A}` (2/3, but `D` is no longer a member).
7. `B` calls `confirm(R)` → count reaches 3/3 and `execute_request(R)` fires, transferring funds — approved by only 2 *live* members (`A`, `B`) plus one stale confirmation from removed member `D`, i.e. executed below the real live-member threshold.

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
