### Title
View-role users can retrieve any bridge's OutgoingToken via GET /v2/bridge_types/:BridgeName (missing role wrapper) - (File: core/web/router.go, core/web/bridge_types_controller.go)

### Summary
The `/v2/bridge_types/:BridgeName` GET route is registered with only session/token authentication (`auth.Authenticate`) but no role-level wrapper, unlike `Create`, `Update`, and `Destroy` which use `auth.RequiresEditRole`. As a result, any authenticated user regardless of role — including the lowest-privilege `view` role — can call `Show` and retrieve the bridge's `OutgoingToken`, a credential secret used to authenticate outbound calls to the external adapter.

### Finding Description
In `core/web/router.go`, the bridge routes are: [1](#0-0) 
Note that `Index`, `Create`, `Update`, and `Destroy` are gated with either `paginatedRequest` alone (Index has no sensitive data) or `auth.RequiresEditRole`, but `Show` is registered bare: `authv2.GET("/bridge_types/:BridgeName", bt.Show)`.

`BridgeTypesController.Show` in `core/web/bridge_types_controller.go` fetches the bridge by name and returns it via `presenters.NewBridgeResource(bt)` with no filtering: [2](#0-1) 

`presenters.NewBridgeResource` copies `OutgoingToken` unconditionally into the JSON response (it lacks `omitempty` and is not redacted), unlike `IncomingToken` which is only set at creation time: [3](#0-2) 

Since the `authv2` group only requires successful `auth.Authenticate` (session or API token) with no minimum role check for `Show`, a user with `UserRoleView` — the lowest role, which `RequiresRunRole` and `RequiresEditRole` explicitly exclude elsewhere — is able to reach `Show` and receive the `OutgoingToken` for any bridge whose name they know, including bridges they did not create. The role-check functions `RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole` in `core/web/auth/auth.go` demonstrate that the app's authorization model treats `view` as a restricted role, but `Show` simply isn't wrapped by any of them.

### Impact Explanation
This is a credential/secret disclosure to a lower-privileged, unrelated user: the `OutgoingToken` is a bearer-token style secret bridges use to authenticate to their external adapter endpoints (see `BridgePresenter`/CLI table rendering treating it as sensitive, and the CLI list view intentionally omitting it: `assert.NotContains(t, output, outgoingToken)` in `core/cmd/bridge_commands_test.go`). A `view`-role account (which by design should only be able to read non-sensitive info) can extract this token for any bridge name it can guess or enumerate, allowing it to potentially call the external adapter with the legitimate outgoing token, impersonating the Chainlink node in requests to that adapter.

### Likelihood Explanation
Exploitation only requires one precondition: attacker possesses valid `view`-role credentials (session cookie or API token) — the minimum privilege level grantable in this system, and any bridge name. No admin, no host or DB access, no misconfiguration required. The request is a single unauthenticated-role-check `GET /v2/bridge_types/<name>` call, fully repeatable for every bridge name known to the attacker.

### Recommendation
Wrap the `Show` route with a role check consistent with the sensitivity of `OutgoingToken`, e.g. `auth.RequiresEditRole(bt.Show)`, or redact `OutgoingToken` in the presenter for non-edit/admin roles (similar to how `IncomingToken` is only surfaced on creation).

### Proof of Concept
Go handler-level integration test (extends existing `TestBridgeController_Show` in `core/web/bridge_types_controller_test.go`):
1. Create an app with an admin user who creates a bridge (`app.BridgeORM().CreateBridgeType`) with a known `OutgoingToken`.
2. Create a second user/session with `sessions.UserRoleView` (using `cltest` helpers for creating a view-role authenticated HTTP client, analogous to existing view-role test patterns in `core/web/auth/auth_test.go`).
3. Using the view-role client, `GET /v2/bridge_types/<bridgeName>`.
4. Assert `http.StatusOK` is returned (not 401/403).
5. Parse the JSON:API response into `presenters.BridgeResource` and assert `resource.OutgoingToken == bt.OutgoingToken`, proving the low-privilege view-role user obtained the bridge's secret outgoing token.

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
