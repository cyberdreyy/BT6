### Title
Funded instant-withdraw claims leave stale per-epoch basis, which is double-counted as prefunded recovery reserve on default finalization - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays a funded instant receipt by clearing only the aggregate `instantWithdrawsRequests[_user]` (line 391). It never clears the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` written in `requestInstantWithdraw` (lines 371-372). If the same epoch later defaults and `finalizeDefaultRecovery` runs while `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis` adds the stale `instantWithdrawClaimsByEpoch[epochNumber]` (including already-paid claims) to the recovery basis, and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying still held by the strategy — even though those tokens were already transferred out to claimants. This is the exact analog of the GatewayRegistry bug: a reset/claim path leaves stale accounting that a later lifecycle transition (default finalization ≈ re-registration) re-reads as fresh claimable balance. ### Finding Description
Sequence, all in epoch N while the epoch is running, instant withdraws enabled:

1. Users A and B call `requestInstantWithdraw` via the CDO. `instantWithdrawsRequestsByEpoch[A][N] = a`, `[B][N] = b`, `instantWithdrawClaimsByEpoch[N] = a+b`, `pendingInstantWithdraws = a+b`.
2. Manager calls `cdoEpoch.getInstantWithdrawFunds()`; the CDO partially funds, calling `collectInstantWithdrawFunds(a)` → `pendingInstantWithdraws = b`, and `a` underlyings now sit in the strategy.
3. A calls `claimInstantWithdrawRequest`, is paid `a` via `_transferFundedClaim`, `instantWithdrawsRequests[A]` is zeroed — but `instantWithdrawsRequestsByEpoch[A][N]` and `instantWithdrawClaimsByEpoch[N]` are left untouched.
4. Borrower honestly fails to repay at `stopEpoch` → `defaulted() = true`. Owner/manager finalizes with `finalizeDefault(recovered, source)`.
5. In `finalizeDefaultRecovery`: `pendingInstantWithdraws = b != 0`, so `defaultInstantWithdrawsFinalized = true`, `defaultPendingClaimBasis()` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[N]` = includes the already-paid `a`, and `_defaultPrefundedInstantReserve()` returns `instantBasis(a+b) - pendingInstant(b) = a` — counting `a` as cash held by the strategy when it was already sent to A.
6. `reserveAmount = recovered + a + defaultRecoveryReserve` and `totalBasis` both include the phantom `a`. `defaultRecoveryPrice` is computed on a balance that does not exist: the strategy's actual token balance is short exactly `a`.

Two consequences, both rooted in the stale entries:

- **Insolvency / over-payment of recovery**: `defaultRecoveryReserve` exceeds real balance by `a`. The first claimants through `_claimDefaultedWithdrawRequest` / `_claimDefaultedInstantWithdrawRequest` (called first in `claimInstantWithdrawRequest`, line 385) are paid an inflated `defaultRecoveryPrice`; the last claimants' `safeTransfer` reverts — permanent freezing of their recovery. An attacker can position as the first claimant (e.g., hold a defaulted-epoch pending withdraw receipt and call `claimWithdrawRequest` immediately after finalization) to extract more than the fair pro-rata share.
- **Inflated basis dilution**: `a` is added to `totalBasis` though no claim exists for it (A's claim would underflow-revert at `instantWithdrawsRequests[_user] -= claimBasis`, line 848), so recovery price does not even map basis→reserve consistently; the extra `a` in the numerator with no extra tokens means every honest recovery claimant's entitlement is paid out of other users' share.

No guard catches this: `_transferFundedClaim`'s reserve check (lines 900-904) only protects the reserve from funded claims, not the reserve itself from being overstated; the `pendingInstantWithdraws != 0` gate in `_ensureDefaultRecoveryInitialized` does not apply post-initialization; and `defaultInstantWithdrawsFinalized` correctly identifies that epoch-N instant claims join recovery but cannot distinguish paid from unpaid ones. ### Impact Explanation
Direct theft plus permanent freezing of unclaimed recovery: the recovery reserve is overstated by the total amount of same-epoch instant withdrawals already paid out before default finalization. Early claimants (attacker-controlled) withdraw more than their fair share; the final `safeTransfer` for honest claimants reverts once the real balance is exhausted, permanently freezing the remainder. Quantified loss ≈ sum of all instant receipts claimed in the defaulted epoch (arbitrarily large fraction of epoch liquidity; e.g., 100k USDC of prefunded-then-claimed instant withdraws makes the reserve short 100k USDC). [7](#0-6) 

### Likelihood Explanation
Requires only an honest sequence of privileged actions: manager funds instant withdraws mid-epoch (a normal operation when `allowInstantWithdraw` is on), a user claims, then the borrower defaults at epoch end and the manager/owner calls `finalizeDefault` — all routine. The attacker is any unprivileged user holding an instant or normal receipt in that epoch who claims first. The condition `instantBasis > pendingInstant` (partial funding) plus at least one pre-default claim is the natural state whenever instant withdraws were partially serviced before a default.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch records for funded claims: delete `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (or iterate the user's request epochs) and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, mirroring how `_claimDefaultedInstantWithdrawRequest` clears them at lines 847-853. Alternatively track a `instantWithdrawClaimedByEpoch[epoch]` counter and subtract it in `_defaultPrefundedInstantReserve`/`defaultPendingClaimBasis` so only unfunded, unclaimed receipts enter the recovery basis and prefunded reserve. [8](#0-7) 

### Proof of Concept
Foundry fork PoC sketch (mirror the helpers in `test/foundry/IdleCreditVault.t.sol`, e.g. `testFinalizeDefaultMixedFundedAndUnfundedInstantReceipts` at line ~4500, which already sets up funded + unfunded instant receipts):

```solidity
function test_StaleInstantBasisInflatesRecoveryReserve() public {
  uint256 amount = 100_000 * ONE_SCALE;
  address early = makeAddr('early-claimer');      // claims pre-default
  address late  = makeAddr('late-claimer');       // claims post-default
  _depositWithUser(early, amount, true);
  _depositWithUser(late,  amount, true);

  // enable instant withdraws
  vm.prank(manager);
  cdoEpoch.setInstantWithdrawParams(1, 0, true);

  // both request instant withdraws in current epoch N
  uint256 half = amount / 2;
  vm.prank(early);
  cdoEpoch.requestInstantWithdraw(half, address(AAtranche));
  vm.prank(late);
  cdoEpoch.requestInstantWithdraw(half, address(AAtranche));

  // borrower partially funds: only `early`'s request is covered
  vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
  deal(defaultUnderlying, borrower, half);
  vm.prank(borrower);
  underlying.approve(address(cdoEpoch), half);
  vm.prank(manager);
  cdoEpoch.getInstantWithdrawFunds();
  assertEq(IdleCreditVault(address(strategy)).pendingInstantWithdraws(), half);

  // early claims; per-epoch records for `early` are NOT cleared
  vm.prank(early);
  cdoEpoch.claimInstantWithdrawRequest();
  assertEq(
    IdleCreditVault(address(strategy)).instantWithdrawsRequestsByEpoch(early, 0),
    half, 'stale per-epoch instant basis remains'
  );

  // borrower defaults honestly at epoch end
  deal(defaultUnderlying, borrower, 0);
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);
  _checkDefault();

  IdleCreditVault cv = IdleCreditVault(address(strategy));
  uint256 realCash = underlying.balanceOf(address(strategy));

  // finalize: prefunded reserve double-counts `half` already paid to `early`
  uint256 recovered = 10_000 * ONE_SCALE;
  deal(defaultUnderlying, manager, recovered);
  vm.startPrank(manager);
  underlying.approve(address(strategy), recovered);
  cdoEpoch.finalizeDefault(recovered, manager);
  vm.stopPrank();

  // reserve was credited `half` that no longer exists as tokens
  assertGt(
    cv.defaultRecoveryReserve(),
    underlying.balanceOf(address(strategy)),
    'recovery reserve exceeds real balance by already-paid instant claim'
  );

  // late claimants overdraw until balance runs out; last claim reverts/frozen
}
```

Key assertions: `instantWithdrawsRequestsByEpoch[early][N]` remains `half` after the funded claim, and after `finalizeDefault` the on-chain `defaultRecoveryReserve` exceeds the strategy's real underlying balance by exactly `half`, proving the reserve was funded on phantom tokens.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```

```text
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;

    defaultRecoveryReserve -= _amount;
```
