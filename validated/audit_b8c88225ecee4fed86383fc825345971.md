This is a real cross-user response-confusion bug, but it is a design gap in the legacy capabilities handler's `savedCallbacks` map, not in the 200-char length check in `gateway.ProcessRequest` itself.

### Title
Legacy `savedCallbacks` map keyed only by attacker-controlled `MessageId` allows cross-user response delivery - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores the pending callback in `h.savedCallbacks[msg.Body.MessageId]`, a map keyed solely by the client-supplied `MessageId`, with no binding to the requester's identity (sender/signer). If two different callers submit legacy requests with the same `MessageId` to the same DON, the second request's insertion silently overwrites the first's callback entry, so whichever node response arrives for that `MessageId` is delivered to the caller who most recently wrote that map key rather than the original requester.

### Finding Description
The 200-character length check in `gateway.ProcessRequest` at [1](#0-0)  only bounds size, it does nothing to prevent collisions and is not the actual control point. The real issue is downstream in `HandleLegacyUserMessage`, which unconditionally overwrites the map entry: [2](#0-1) 
The `MessageId` is fully attacker-controlled (copied from the client-supplied JSON-RPC `ID`/body field) and validated only for length/format, not uniqueness or ownership, in `Message.Validate` at [3](#0-2) . When a node later responds, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageId`, with no cross-check against the original requester's sender/identity: [4](#0-3) 
The only sender check performed, `msg.Body.Sender != nodeAddr` in `HandleNodeMessage`, verifies the *node* that sent the response, not that the response corresponds to the caller who currently owns that map entry: [5](#0-4) . So if Attacker A submits a request with `MessageId = "X"`, and Victim B concurrently (or afterward, before B's response returns) submits a different request with the same `MessageId = "X"` to the same DON, B's map entry replaces A's. When the node's response for either in-flight message arrives keyed on `"X"`, it is delivered to whichever callback currently occupies `savedCallbacks["X"]`, which may not be the original submitter of that particular request/response pair.

Notably, a different subsystem in the same codebase, `RequestCache` used elsewhere, already fixes this exact class of bug by keying on `globalId{sender, id}` instead of `id` alone: [6](#0-5)  — confirming this is a known pattern that the legacy `capabilities` handler's `savedCallbacks` map fails to apply.

### Impact Explanation
This is cross-user response confusion: an attacker who can predict or coordinate a collision on `MessageId` can (a) hijack another caller's callback slot so their own subsequent response is delivered to the victim instead (denial of service to the victim, whose original request effectively receives no reply until its own timeout), or (b) more concerning, if timing allows, receive a response payload intended for another user's request when the victim's request overwrites the attacker's entry and the node's response for the attacker's original request is instead delivered to the victim (and vice versa). This matches the "cross-user response confusion" / unauthorized access to another user's request/response data impact class in scope.

### Likelihood Explanation
Exploitability strictly requires the attacker to know or guess the exact `MessageId` string of a victim's concurrently in-flight legacy request to the same DON, since `MessageId` is chosen by each client independently. If any calling system uses predictable, low-entropy, or externally-observable `MessageId`s (e.g., counters, workflow execution IDs, transaction hashes), an attacker could feasibly cause a collision; if callers always use high-entropy random IDs (e.g., UUIDs), the practical likelihood is low. The code provides no defense-in-depth against collisions regardless of ID entropy (no per-sender scoping, no rejection of duplicate in-flight `MessageId`s), so the vulnerability is real and code-level fixable, but its practical trigger probability depends on external, non-reviewable client ID-generation behavior.

### Recommendation
Scope `savedCallbacks` (and the pruning/eviction logic) by `(sender, MessageId)` rather than `MessageId` alone, mirroring the fix already used in `RequestCache` (`globalId{sender, id}`). Additionally, reject/overwrite-protect insertion when an entry for the same key already exists and is not yet expired, returning an error to the duplicate submitter instead of silently overwriting.

### Proof of Concept
1. Unit test in `core/services/gateway/handlers/capabilities/handler_test.go`: build two `api.Message`s signed by two different private keys (`nodes[0]` acting as "attacker" signer, `nodes[1]` acting as "victim" signer) but both use identical `Body.MessageId = "collide-id"` and `Body.DonId`.
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, cbVictim)` then immediately `handler.HandleLegacyUserMessage(ctx, attackerMsg, cbAttacker)` before either resolves.
3. Assert `handler.savedCallbacks["collide-id"]` now references `cbAttacker`'s callback (verifying the overwrite).
4. Simulate a node response for `"collide-id"` (call `handleWebAPITriggerMessage`/`HandleNodeMessage` with a response message whose `MessageId` is `"collide-id"`).
5. Assert that `cbAttacker.Wait()` receives the response and `cbVictim.Wait()` times out/never resolves — demonstrating cross-delivery/loss instead of each caller receiving only their own response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
