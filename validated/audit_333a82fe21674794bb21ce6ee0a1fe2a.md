## Title
Stale confirmations from removed multisig members/keys are never purged, allowing requests to execute below the configured confirmation threshold — (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` authorizes execution purely by comparing the *size* of the `confirmations` set stored for a request against `num_confirmations`, with no check that every recorded confirmer is still a current member/key. When a member or access key is removed via `DeleteMember` (multisig2) or `DeleteKey` (multisig), the cleanup logic only purges requests **originated** by that member/key — it never scans other pending requests' `confirmations` sets to strip that now-revoked identity out. A confirmation given before removal therefore continues to count toward the threshold forever, letting a request execute with fewer *currently valid* signers than `num_confirmations` requires.

### Finding Description
The binding that must hold is:
`confirmations.len()` (recorded) == number of *live* members who actually approved the request.

In `multisig2/src/lib.rs`, `delete_member` removes a member and cleans up only requests it authored: [1](#0-0) 
It filters `self.requests` by `r.member == member` (the request's *originator*) and clears confirmations only for those requests. It does **not** iterate `self.confirmations` to strip the removed member's entry from requests it merely *confirmed* but did not create.

`confirm` then blindly counts set size to decide whether to execute: [2](#0-1) 

The same pattern exists in the older `multisig` contract's `DeleteKey` handling, which only removes requests where `r.signer_pk == pk` and leaves that key's confirmation on other pending requests intact: [3](#0-2) [4](#0-3) 

This is the same bug class as the reported `CSVerifier` issue: a value trusted at the time it was recorded (a withdrawal-vault address / a confirming member) is never re-validated against the current authoritative set (the current vault address / the current membership list) after that set changes, so stale trust silently persists and is treated as still valid.

### Impact Explanation
This crosses an explicit authorization/threshold boundary: a `Transfer`, `DeployContract`, `AddKey`, `FunctionCall`, etc. can be executed by `execute_request` with fewer *live* approvals than `num_confirmations` mandates, because one or more counted confirmations belong to accounts/keys that are no longer members. Per the rules, "a multisig request executed below threshold" is a Critical impact — funds (NEAR) can move, or a contract can be upgraded/re-deployed, with less real authorization than the multisig was configured to require.

### Likelihood Explanation
No special privilege beyond being an ordinary multisig member is required. Any request that received a confirmation before its confirmer was removed remains exploitable indefinitely (there is no expiry or re-validation), and member turnover (key rotation, personnel changes, compromised-key remediation via `DeleteKey`/`DeleteMember`) is a normal, expected multisig operation, making this reachable in ordinary usage rather than a contrived edge case.

### Recommendation
When removing a member/key (`delete_member` / `DeleteKey`), scan `confirmations` for **all** pending requests (not just ones authored by that member) and remove the departing identity's entry from each. Alternatively, have `confirm`/`execute_request` re-validate, at execution time, that every public key/account in the stored `confirmations` set is still present in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 4 members `{A, B, C, D}` and `num_confirmations = 3`.
2. Member `B` calls `add_request` to create request `R` (e.g. `Transfer` to an attacker-controlled account).
3. Member `A` calls `confirm(R)` → `confirmations[R] = {A}` (1 < 3, not yet executed).
4. Through a separate, legitimately-confirmed `DeleteMember { member: A }` request, `A` is removed from the multisig (e.g., routine key rotation). `delete_member` only purges requests where `r.member == A` (i.e., requests `A` created) — `R` (created by `B`) is untouched, so `confirmations[R]` still contains `A`.
5. Members `C` and `D` now call `confirm(R)` twice, appending themselves: `confirmations[R] = {A, C, D}`, size 3 ≥ `num_confirmations` (3) → `execute_request(R)` fires.
6. The transfer executes, even though only 2 currently-live members (`C`, `D`) actually approved it — one full confirmation "slot" was supplied by `A`, who was no longer a member at execution time. This breaks the `confirmations recorded == live approvals` invariant and lets a request execute below the real threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
