### Title
Loss haircut stored under post-increment `epochNumber` lets pending withdraw receipts bypass `lossRecoveryPriceByEpoch` and claim at par - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Ktor request-smuggling bug class is about two parties disagreeing on request boundaries/framing, so a request is processed under a different interpretation than the one the guard assumed. The analog in `IdleCreditVault` is epoch-number framing for loss-adjusted withdraw receipts: `requestWithdraw` tags a receipt with `lastWithdrawRequest[_user] = epochNumber` (lines 260–282), while `collectWithdrawFunds` writes the haircut under whatever `epochNumber` reads at funding time (`lossRecoveryPriceByEpoch[epochNumber]`, line 421). But `deposit()` increments `epochNumber` mid-`stopEpoch` (lines 607–611), so the haircut is stored under a different epoch index than the receipts it is meant to haircut. The claim path then fails to find the haircut and pays the full request at par.

### Finding Description
- `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (`IdleCreditVault.sol:282-293`).
- On a loss-realizing `stopEpoch` (i.e., `stopEpochWithDuration`/`stopEpoch` funding less than `pendingWithdraws`), the CDO calls `collectWithdrawFunds(_amount)` which stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` (`IdleCreditVault.sol:411-422`).
- `epochNumber` is bumped inside `deposit()` when a deposit lands while the epoch is being stopped ("deposit done on stopEpoch ... epochNumber += 1", `IdleCreditVault.sol:607-611`). Depending on call ordering inside the CDO's stopEpoch flow (borrower funding/`deposit` vs `collectWithdrawFunds`), the haircut can be keyed under the *next* epoch while receipts are keyed under the previous one.
- The claim path `_claimLossAdjustedWithdrawRequest` looks the haircut up exclusively by `lastWithdrawRequest[_user]` (`IdleCreditVault.sol:789-801`). If the price was stored under a different index, `lossRecoveryPrice == 0`, the function returns 0, and execution falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` in full and burns the receipt (`IdleCreditVault.sol:319-350`).
- The guard in `requestWithdraw` (lines 263–271) that forces users to claim a loss-adjusted receipt before a new request is keyed on the same stale index, so it also never triggers.

### Impact Explanation
Pending withdraw receipts that should have been haircut pro rata by a realized epoch loss are instead paid 1:1 from funded strategy underlyings. This violates the loss-socialization invariant: the pending-bucket loss computed by `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` is silently dropped, so the withdrawer is overpaid relative to active LPs (who absorb the full loss through the BB-first waterfall) and relative to other pending withdrawers. The excess payout drains the funded reserve, producing insolvency for the last claimers and for tranche holders — direct, quantified loss equal to `pendingLoss = _lossAmount * pendingBasis / totalBasis` for every unfunded-loss epoch.

### Likelihood Explanation
Triggering requires only an unprivileged withdraw request in a running epoch plus a later `stopEpoch` where the borrower under-funds `pendingWithdraws` — an ordinary (manager/honest-borrower) flow, not an attacker-privileged action. The attacker merely holds a pending receipt and calls `claimWithdrawRequest` after the epoch closes; the framing mismatch does the rest. The main uncertainty is the exact ordering inside the CDO's stopEpoch routine (whether `deposit()`/the `epochNumber` bump executes before `collectWithdrawFunds`); this could not be fully confirmed because `IdleCDOCreditVault.sol` contains no direct `collectWithdrawFunds` call site visible to the index. If the haircut is ever stored under an index that differs from `lastWithdrawRequest` (also reachable when a user requests during a buffer epoch and the loss lands after an epoch boundary), the same escape applies.

### Recommendation
Key the loss haircut by the epoch that the pending receipts actually belong to rather than the mutable `epochNumber` at collection time — e.g., store `lossRecoveryPriceByEpoch` per the request epoch set tracked in `withdrawsRequestsByEpoch`, or snapshot `pendingWithdrawsEpoch` when `pendingWithdraws` is increased and use that index in `collectWithdrawFunds`. Additionally, make `_claimFundedWithdrawRequest` revert (instead of silently paying at par) when a user's request epoch has a non-zero `lossRecoveryPriceByEpoch` under any stored index, and add a regression test asserting that a pending request opened in epoch N is haircut by a loss applied during the stopEpoch that ends epoch N.
