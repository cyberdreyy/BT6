### Title
Beneficiary redirection is bypassed for commission accrued at `switch_operator` time, sending funds to the stale operator address instead of the designated beneficiary - (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
An unprivileged staker calling `switch_operator` on their own staking contract can, as an unintended side effect of normal usage, cause commission that was requested during the switch to permanently bypass the old operator's configured `BeneficiaryForOperator` and instead be paid to the old operator's raw account address once the funds later become withdrawable.

### Finding Description
`switch_operator` removes the `StakingContract` from the map under `old_operator`, calls `distribute_internal` and `request_commission_internal` (both still passed `old_operator`), then calls `stake::set_operator_with_cap` and re-inserts the same `StakingContract` under `new_operator`: [1](#0-0) 

`request_commission_internal` records the newly requested commission as a share in `distribution_pool` keyed by the raw operator address, and merely calls `stake::unlock_with_cap` — the coins are not actually paid out yet, they only move to `pending_inactive` and require the lockup to expire before they are truly withdrawable: [2](#0-1) 

The beneficiary redirection logic lives in `distribute_internal`, and it only redirects a distribution-pool share to `beneficiary_for_operator(operator)` when the shareholder address equals the `operator` **parameter passed into the current call**: [3](#0-2) 

Once `switch_operator` completes, the `StakingContract` only exists under the `new_operator` key, so every subsequent call (`distribute`, `request_commission`, `unlock_stake`, etc.) invokes `distribute_internal(staker, new_operator, staking_contract)`. When the pending commission share (still keyed under `old_operator` from before the switch) finally becomes withdrawable and gets redeemed, the check `recipient == operator` compares `old_operator == new_operator`, which is false. As a result the beneficiary lookup is skipped entirely, and the coins are deposited directly to the raw `old_operator` address instead of to the beneficiary the old operator had configured via `set_beneficiary_for_operator`.

Note: the exploit mechanism is not actually the *ordering* of `request_commission_internal` vs `stake::set_operator_with_cap` (reordering these two calls would not change the outcome, since `request_commission_internal` is always invoked with the literal `old_operator` argument regardless of when the stake pool's operator field is updated). The real root cause is that the beneficiary redirect in `distribute_internal` is keyed off the *current* function parameter rather than a persistent per-shareholder identity, and the staking-contract map key changes on switch while the distribution-pool shareholder key does not get remapped.

### Impact Explanation
Any commission requested by `request_commission_internal` during a `switch_operator` call that has not yet fully unlocked (i.e., the pool's lockup has not expired at switch time — the normal case) will, upon eventual distribution, be paid directly to the old operator's own account rather than to the beneficiary address the operator explicitly configured via `set_beneficiary_for_operator`. This violates the beneficiary-update invariant that beneficiary-designated payouts must not be silently redirected away from the beneficiary. It does not destroy value (the old operator's own account still receives it) and does not benefit the staker who triggered the switch, but it does misroute commission away from the operator's intended recipient without any error or event indicating the redirection failed.

### Likelihood Explanation
This triggers under ordinary, non-adversarial staker behavior (no special privilege beyond being the staker of their own contract) whenever: (1) the operator-beneficiary feature is enabled, (2) the old operator has set a beneficiary, and (3) `switch_operator` is called while there is unpaid commission and the stake pool's lockup has not yet fully expired — which is the typical situation for an active validator, since `unlock_with_cap` only moves stake to `pending_inactive`. This makes the condition fairly easy to hit in practice, though it requires the specific combination of features/beneficiary configuration.

### Recommendation
When calling `distribute_internal` for a contract that has just been reassigned via `switch_operator`, either (a) fully settle any pending distribution shares under `old_operator`'s key before removing the contract from the map (i.e., force-drain the distribution pool for `old_operator`, not just call `request_commission_internal`/`distribute_internal` once), or (b) make the beneficiary lookup in `distribute_internal` independent of the transient `operator` parameter — e.g., always resolve `beneficiary_for_operator(recipient)` whenever `recipient` itself has a stored `BeneficiaryForOperator` entry, rather than only when `recipient == operator`.

### Proof of Concept
1. Staker creates a staking contract with `old_operator`, non-zero commission percentage.
2. `old_operator` calls `set_beneficiary_for_operator` to designate `beneficiary_addr`.
3. Rewards accrue; staker calls `switch_operator(staker, old_operator, new_operator, new_commission_percentage)`. Inside, `request_commission_internal` adds a distribution-pool share keyed by `old_operator` for the newly computed commission, then `unlock_with_cap` moves it to `pending_inactive` (lockup not yet expired). The contract is reinserted under `new_operator`.
4. Time passes until lockup expires (`pending_inactive` becomes `inactive`).
5. Anyone calls `distribute(staker_address, new_operator)`. Inside `distribute_internal`, the `operator` parameter is `new_operator`, but the pending share's shareholder key is `old_operator`; `recipient == operator` is false, so `beneficiary_for_operator` is never consulted, and the coins are deposited directly to `old_operator` instead of `beneficiary_addr`.
6. Assertion that would fail: `beneficiary_addr`'s balance does not increase by the expected commission amount; `old_operator`'s balance increases instead — demonstrating the beneficiary designation was silently bypassed for that commission tranche.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

        // Request to unlock the commission from the stake pool.
        // This won't become fully unlocked until the stake pool's lockup expires.
        stake::unlock_with_cap(commission_amount, &staking_contract.owner_cap);

        let pool_address = staking_contract.pool_address;
        emit(
            RequestCommission {
                operator,
                pool_address,
                accumulated_rewards,
                commission_amount
            }
        );

        commission_amount
    }
