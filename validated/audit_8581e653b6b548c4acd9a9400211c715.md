### Title
Claimed instant-withdraw receipts keep their per-epoch claim basis, corrupting default recovery price - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`claimInstantWithdrawRequest` burns the user's receipt tokens and pays them out, but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If a borrower default is later finalized in that same epoch while `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis()` counts already-claimed-and-paid receipts as outstanding basis, and `_defaultPrefundedInstantReserve()` treats funds that already left the strategy as held reserve. The resulting `defaultRecoveryPrice` is inflated, so early recovery claimants are paid more than the real reserve supports, draining underlying that backs active LP strategy tokens, while late claimants revert on an exhausted reserve.

### Finding Description

When a user requests an instant withdrawal, the vault records both an aggregate and a per-epoch basis:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:366-374
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

But the claim path only clears the aggregate:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:387-392
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are left untouched. Both are only written again inside `_claimDefaultedInstantWithdrawRequest` (lines 847-853), which runs exclusively after default finalization.

On finalization, `defaultPendingClaimBasis()` adds the full current-epoch claim counter when any instant remainder is unfunded:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:644-649
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
    basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

and `_defaultPrefundedInstantReserve()` computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` as underlying already held by the strategy (lines 716-723). A claimed receipt is paid out in full via `underlyingToken.safeTransfer` in `_transferFundedClaim`, so those tokens are no longer held — yet they are counted as prefunded reserve.

The aggregate receipt-token conservation (`_burn` / `instantWithdrawsRequests[_user]`) correctly prevents a literal double claim: a second claim on the same user reverts because `instantWithdrawsRequests[_user] - claimBasis` underflows. The corruption is in the global accounting instead:

- `totalBasis` in `finalizeDefaultRecovery` (line 680) is inflated by ghost claims.
- `prefundedReserve` is inflated by funds that already left the strategy.
- `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` uses a `reserveAmount` containing non-existent tokens, so the stored price does not match real holdings.

Every subsequent `_claimDefaultedInstantWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `_claimPostDefaultWithdrawRequest` and the active-LP path (via post-default `requestWithdraw` → `postDefaultRequests`) pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve` (lines 912-917). Since the reserve was credited with funds that were already paid out, the total payouts exceed real holdings. Once the ERC20 balance is exhausted, `safeTransfer` reverts — but claimants who go first draw underlying that economically belongs to active tranche holders (CDO-held strategy tokens) and to other pending receipt holders. The broken invariant is "one receipt one payout / recovery reserve solvency": the strategy promise value exceeds its balance.

### Impact Explanation

Concrete sequence (attacker = any KYC-passed lender / instant-withdraw requester):

1. Buffer phase of epoch N: attacker requests an instant withdraw of `X`. `instantWithdrawClaimsByEpoch[N] += X`.
2. `startEpoch` fully funds instant requests (`collectInstantWithdrawFunds` sets `pendingInstantWithdraws = 0` and moves `X` underlying into the vault). Attacker claims `X` at par. The per-epoch basis `X` remains recorded.
3. Same epoch N: another user requests an instant withdraw of `Y` late in the buffer (still epoch N tagging, since `epochNumber` only bumps at `stopEpoch`'s `deposit()`). At the next `startEpoch`/`getInstantWithdrawFunds`, only `Z < Y` can be funded, so `pendingInstantWithdraws = Y - Z > 0`. Borrower then fails repayment; `stopEpoch`/`getInstantWithdrawFunds` triggers `_handleBorrowerDefault`.
4. Manager calls `finalizeDefault(R, source)`. `defaultPendingClaimBasis` now includes `X + Y` instead of `Y`, and `_defaultPrefundedInstantReserve` computes `X + Y - (Y - Z) = X + Z` instead of `Z`, crediting `X` tokens that were already paid to the attacker.
5. `defaultRecoveryPrice` is computed against a `reserveAmount` inflated by `X`. The user with the legit `Y` receipt (and defaulted-epoch normal withdrawers and active LPs through `postDefaultRequests`) claim at this price; the vault pays out more underlying than it holds until the balance is exhausted. Whoever claims first steals up to `X` underlying from the remaining claimants; the rest face permanent reverts (`safeTransfer` failure on empty balance), i.e., permanent freezing of their recovery.

The attacker's profit does not come from double-claiming (that reverts) but from the inflation itself: any holder of a real defaulted receipt — which the attacker can also be, e.g., by splitting across two wallets — claims `basis * inflatedPrice`, receiving more than the pro-rata share of actually held funds. Loss is bounded by the total claimed instant receipts of the default epoch (`X`), which is only limited by available liquidity at the time and is fully user-controlled.

### Likelihood Explanation

Requirements are all unprivileged-user reachable and rely only on honest privileged actions:

- Instant withdrawals must be enabled (`disableInstantWithdraw = false`) — a standard supported mode (`setInstantWithdrawParams`).
- The attacker's instant receipt must be claimed in the same epoch number that later defaults. Since `epochNumber` is only incremented inside `deposit()` during a successful `stopEpoch`, a receipt created in the buffer, funded at `startEpoch`, claimed, and then followed by a partially unfunded instant queue plus a borrower funding failure within that same epoch window satisfies the condition. Borrower default is an honest-manager trigger (`_handleBorrowerDefault` fires automatically on failed `getFundsFromBorrower`), not attacker misconduct.
- `finalizeDefault` is called by the honest owner/manager as designed.

Existing guards do not stop it: `_ensureDefaultRecoveryInitialized` does not reconcile `instantWithdrawClaimsByEpoch` with actually outstanding claims; `_transferFundedClaim`'s reserve guard protects the reserve from funded claims, not the reserve computation itself; the `_onlyIdleCDO` gate is irrelevant since the corruption is data, not access.

### Recommendation

In `claimInstantWithdrawRequest`, clear the per-epoch basis for the epoch in which each receipt was recorded. Because a user's aggregate `instantWithdrawsRequests` can span epochs, either:

- Track the oldest unclaimed request epoch per user and decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount on every successful claim, or
- Store instant receipts as a per-user list/stack of `(epoch, amount)` entries consumed FIFO.

Additionally, as defense in depth, `defaultPendingClaimBasis` / `_defaultPrefundedInstantReserve` should derive the instant basis from a counter that is maintained as "still-outstanding claims" (incremented on request, decremented on claim) rather than "ever-requested claims", e.g., by keeping `instantWithdrawClaimsByEpoch` strictly in sync with claimable basis.

### Proof of Concept

```solidity
// SPDX-License-Identifier: UNLICENSED
// test/foundry/PoCInstantReceiptBasis.sol
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../../contracts/interfaces/IERC20Detailed.sol";

contract PoCInstantReceiptBasis is Test {
    // reuse the suite's standard deployment helpers (as in test/foundry/IdleCreditVault.t.sol)
    // idleCDO: IdleCDOEpochVariant, strategy: IdleCreditVault, borrower, AAtranche...
    IdleCDOEpochVariant cdoEpoch;
    IdleCreditVault vault;
    IERC20Detailed underlying;
    address borrower = address(0xB0);
    address attacker = address(0xA77);
    address victim = address(0xV1C);

    function testClaimedInstantReceiptCorruptsRecoveryPrice() public {
        // --- setup: deposits, instant withdrawals enabled, KYC for attacker/victim ---
        uint256 X = 1_000e18;
        uint256 Y = 1_000e18;

        // Buffer of epoch N: attacker requests instant withdraw of X (apr drop path or direct)
        vm.prank(attacker);
        cdoEpoch.requestWithdraw(0, address(AAtranche)); // routes to requestInstantWithdraw
        assertEq(vault.instantWithdrawClaimsByEpoch(vault.epochNumber()), X);

        // startEpoch funds instant queue fully; attacker claims X at par
        _startEpoch(); // owner/manager
        vm.prank(attacker);
        cdoEpoch.claimInstantWithdrawRequest();
        // BUG: per-epoch basis still recorded
        assertEq(vault.instantWithdrawClaimsByEpoch(vault.epochNumber()), X);

        // Same epoch N: victim requests instant withdraw of Y; only partially funded
        vm.prank(victim);
        cdoEpoch.requestWithdraw(0, address(AAtranche)); // adds Y to instantWithdrawClaimsByEpoch[N]
        _partiallyFundInstant(Y / 2); // pendingInstantWithdraws = Y/2 > 0

        // Borrower fails repayment -> _handleBorrowerDefault, then manager finalizes
        _defaultBorrower();
        cdoEpoch.finalizeDefault(recoveredAmount, recoverySource); // owner/manager

        // defaultPendingClaimBasis counted X + Y instead of Y,
        // and _defaultPrefundedInstantReserve credited X as already-held funds.
        uint256 price = vault.defaultRecoveryPrice();
        uint256 realReserve = underlying.balanceOf(address(vault));
        uint256 promisedReserve = vault.defaultRecoveryReserve();
        assertGt(promisedReserve, realReserve); // accounting > holdings by X

        // Victim claims at inflated price; drains underlying beyond its real share
        uint256 balBefore = underlying.balanceOf(victim);
        vm.prank(victim);
        cdoEpoch.claimInstantWithdrawRequest();
        uint256 paid = underlying.balanceOf(victim) - balBefore;
        // payout = claimBasis * inflated price > claimBasis * realReserve/totalRealBasis
        assertGt(paid, expectedFairPayout);

        // Remaining claimants (post-default requests / other receipts) now revert
        // on _transferDefaultRecovery -> safeTransfer with insufficient balance.
        vm.expectRevert();
        vm.prank(otherClaimant);
        cdoEpoch.claimWithdrawRequest();
    }
}
```

Note: the exact helper names follow the existing harness in `test/foundry/IdleCreditVault.t.sol`; the essential assertions are (a) `instantWithdrawClaimsByEpoch` is unchanged after a successful `claimInstantWithdrawRequest`, and (b) after `finalizeDefault`, `defaultRecoveryReserve` exceeds the strategy's actual underlying balance by the previously claimed amount.
