### Title
Missing `return` statements after failed claim/error checks in OIDC token exchange allow session creation to proceed with invalid state - (File: core/sessions/oidcauth/oidc.go)

### Summary
This is a structural analog of the reported "unchecked function result" bug class. Just as the Trading.sol contract checked a boolean flag from `ok`/`transfer()` without properly validating it before continuing, `oidcAuthenticator.handleTokenExchange` in `core/sessions/oidcauth/oidc.go` checks the results of a type assertion and a database call, logs an error/writes an HTTP error response, but fails to `return`, letting execution fall through into the authenticated-session-creation logic anyway.

### Finding Description
In `handleTokenExchange` (`core/sessions/oidcauth/oidc.go`), two checked results are not honored with an early return:

1. Email claim assertion (lines 226-230): [1](#0-0) 
If the verified ID token's claims map lacks an `"email"` string field, the code writes a 500 response but does **not** `return`. Execution continues to role mapping and session creation with `email` left as the zero value (`""`).

2. Session-row insert error (lines 250-260): [2](#0-1) 
If the `INSERT INTO oidc_sessions ...` call fails, the error is only logged and written as a 500 body — again with no `return`. Execution falls through to: [3](#0-2) 
which records an `AuthLoginSuccessNo2FA` audit entry, sets the gin session cookie referencing `clSession.ID`, and finally emits `ExchangeTokenResponse{Success: true}` with an HTTP 200 body appended after the earlier 500 status/body — a corrupted response and a misleading, inaccurate audit trail — regardless of whether the session row was actually persisted.

Both cases mirror the report's root cause: a result (`ok`, `err`) is examined, an error path is logged, but the code does not stop, so processing continues under an invalid or unverified assumption exactly as unchecked `transfer()`/`safeTransfer` results let a caller believe a transfer succeeded when it may not have.

### Impact Explanation
- Missing return #1 causes real, functioning authenticated sessions (`oidc_sessions` rows and gin session cookies) to be created with `user_email = ''` whenever the identity provider's ID token omits the configured `"email"` claim. Because `AuthorizedUserWithSession` (`core/sessions/oidcauth/oidc.go`, `AuthorizedUserWithSession`) looks sessions up by random session ID (not email), the created session is fully functional, but the empty-string email is then used in audit records (`AuthLoginSuccessNo2FA`) and would collide with any other authenticated identity that also lacks an email claim, undermining per-user attribution/audit integrity of an internet-facing login endpoint.
- Missing return #2 causes the handler to report `Success: true` to the client and to write an `AuthLoginSuccessNo2FA` audit record even when the session was never durably created in the database, corrupting both the audit log and the HTTP response (a 500 status/body is written, then a 200 JSON body is appended on top of it), giving an unprivileged client and the audit trail conflicting/incorrect information about authentication state.

Overall this is a data-integrity / audit-trail-confusion class issue in an unauthenticated, internet-facing endpoint (`handleTokenExchange` is invoked before any session exists), not a full authentication bypass, since role/session validity is still gated by a legitimately-verified ID token from the configured OIDC provider.

### Likelihood Explanation
Triggering path 1 only requires completing the standard OIDC authorization code flow with a provider/account whose ID token does not include an `"email"` claim (e.g., account created without an email field, or provider misconfiguration/omitted scope) — this is plausible in real deployments and does not require attacker control over the IdP's signing keys. Triggering path 2 requires a transient database failure during session insertion, which is lower likelihood but still a realistic operational condition.

### Recommendation
Add explicit `return` statements immediately after each error-response branch in `handleTokenExchange`:
- After `c.String(http.StatusInternalServerError, "Failed to get email from claims")` (line 229) — return before falling through to role mapping/session creation.
- After `c.String(http.StatusInternalServerError, "Error creating session")` (line 259) — return before writing the success audit log, setting the session cookie, and sending the `Success: true` response.

Additionally, consider treating a missing/empty `"email"` claim as a hard authentication failure (mirroring the checks already performed for `id_token` and claim parsing), since email is used downstream for audit attribution.

### Proof of Concept
1. Configure OIDC login (`OIDC.Enabled = true`) with an identity provider account/response that returns a verifiable ID token without an `"email"` claim (or a provider that omits the `email` scope claim in the ID token payload).
2. Complete the standard SSO flow (`/oidc/login` → provider auth → `/oidc/token` invoking `handleTokenExchange`).
3. Observe that despite the "Failed to get email from claims" 500 body being written at line 229, execution continues: `IDClaimsToUserRole` still succeeds using the group claims, and a session row is inserted into `oidc_sessions` with `user_email = ''`.
4. The client can now use the returned session cookie to call any endpoint gated by `AuthenticateBySession` and be treated as an authenticated user with `Email: ""`, an audit-trail-breaking identity that is indistinguishable from any other user hitting the same missing-email condition.
