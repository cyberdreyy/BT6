### Title
Unbounded recursive RLP decoding of `TrieNode` allows stack-exhaustion DoS of the fault-proof program - (File: `crates/proof/mpt/src/node.rs`)

### Summary
`TrieNode::decode` (the RLP decoder used everywhere a trie-node preimage is parsed in the Base fault-proof program) recurses into itself with no depth limit, both for extension-node children encoded inline in the same buffer and for branch-node children decoded via `Vec::<Self>::decode`. A crafted preimage supplied to the fault-proof program's preimage oracle can nest thousands of extension/leaf nodes to blow the native stack, mirroring CVE-2017-9763's "excessive stack use and application crash" from a crafted, deeply-structured binary blob (GRUB's `grub_ext2_read_block`).

### Finding Description
`TrieNode::decode` dispatches on the RLP list length: [1](#0-0) 

For a 2-element list (leaf/extension), `try_decode_leaf_or_extension_payload` is called, and for the extension case it recurses directly into `Self::decode(buf)` on the *same buffer*, with no separate preimage lookup or bound check: [2](#0-1) 

Per the Ethereum MPT encoding rule implemented here, only nodes whose RLP encoding exceeds 32 bytes are "blinded" (replaced by a hash requiring a fresh oracle round trip); anything ≤32 bytes is embedded inline and decoded eagerly and recursively: [3](#0-2) 

Because a single extension node's minimal RLP encoding (a 1-nibble path + pointer) is only a handful of bytes, an attacker can nest an arbitrarily large number of extension nodes inside one preimage blob, each nesting driving one more recursive call to `TrieNode::decode` → `try_decode_leaf_or_extension_payload` → `TrieNode::decode`, with no depth guard anywhere in the crate (no `MAX_DEPTH`/recursion-limit construct exists in `crates/proof/mpt`). The branch-node path is equally recursive via `Vec::<Self>::decode(buf)`, which itself calls `TrieNode::decode` per element: [4](#0-3) 

The trie-walking code built on top of this type is likewise unboundedly recursive when unblinding nested nodes, e.g. `fetch_leaves` in the ordered-list walker used for deposit/withdrawal lists: [5](#0-4) 

This `TrieNode::decode` path is the standard entry point used by every `TrieProvider` implementation in the fault-proof program, e.g. the L1 chain provider used during derivation inside the FPVM: [6](#0-5) 

The preimage backing these decodes is attacker-influenced: the preimage oracle/KV store only verifies that `keccak256(value) == key` for hash-typed keys — it does not, and cannot, validate the *shape* of the RLP structure inside: [7](#0-6) 

In the interactive fault-dispute/preimage-oracle model, a dispute-game participant supplies both the data and (by construction) its hash-derived key for any node reachable along their claimed (possibly divergent) execution trace — this is the normal operating mode of the large-preimage oracle, not a bypass of any check. A participant can therefore submit a single trie-node preimage engineered with deep extension-node nesting for a node hash on their own claimed path.

### Impact Explanation
When the fault-proof program (native host/executor or in-enclave/zk witness verifier) decodes such a preimage, unbounded native recursion exhausts the call stack and crashes the process before an output root can be computed. This directly denies the ability to compute/verify the correct provable output root for that dispute step: an honest party racing the dispute clock can be forced to miss it, or the "wrong provable output root" / non-terminating proof outcome required by the Validate criteria is produced. This is a concrete node/process halt inside the fault-proof program logic reachable from a dispute-game participant, which the rules explicitly list as an in-scope path ("the fault-proof program and MPT").

### Likelihood Explanation
Crafting the malicious nested-extension-node blob requires only RLP encoding skill, no cryptographic break, and the participant fully controls the bytes they submit as a preimage for a hash of their own choosing. No privileged access is needed beyond being a dispute-game participant (an attacker-reachable role explicitly in scope). Likelihood is High.

### Recommendation
Add an explicit recursion/depth limit to `TrieNode::decode` (and to `fetch_leaves`/other recursive trie walks), converting to an iterative worklist-based decode or tracking depth and returning a decode error once a maximum plausible trie depth (e.g., 64, bounded by 32-byte keys) is exceeded, regardless of whether nodes are blinded or embedded inline.

### Proof of Concept
1. Build a chain of `TrieNode::Extension` values where each child is another inline (`≤32`-byte encoded) `Extension`/`Leaf`, nested N times (N in the tens of thousands) inside a single RLP buffer, ending in a `Leaf`.
2. Compute `keccak256` of the resulting bytes and submit it as a large-preimage-oracle entry for that hash as part of a dispute-game move / L1 hint response.
3. When the fault-proof program's `TrieProvider` resolves that hash and calls `TrieNode::decode` on the bytes (e.g. via `OracleL1ChainProvider::trie_node_by_hash` at `crates/proof/proof/src/l1/chain_provider.rs:128-141`), the recursive descent through `try_decode_leaf_or_extension_payload` (`crates/proof/mpt/src/node.rs:439-469`) overflows the native stack and crashes the process before it can finish computing the output root.

impl Decodable for TrieNode {
    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.
                    buf.advance(header.length());
                    // Decode the leaf or extension node's raw payload.
                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }

                            // If the item is already retrieved, recurse on it.
                            leaf_values.append(&mut Self::fetch_leaves(item, fetcher)?);
                        }
                    }
                }

    fn check_preimage(key: &PreimageKey, value: &[u8]) -> crate::Result<()> {
        let expected_hash: Option<[u8; 32]> = match key.key_type() {
            PreimageKeyType::Keccak256 => Some(keccak256(value).0),
            PreimageKeyType::Sha256 => Some(sha2::Sha256::digest(value).into()),
            // Blob keys are `keccak256(commitment ++ z)` and precompile keys are
            // `keccak256(address ++ input)` — neither can be re-derived from the
            // stored value alone, so we skip verifying them here and instead verify them
            // during derivation.
            PreimageKeyType::Local
            | PreimageKeyType::GlobalGeneric
            | PreimageKeyType::Blob
            | PreimageKeyType::Precompile => None,
        };

        if let Some(hash) = expected_hash
            && key != &PreimageKey::new(hash, key.key_type())
        {
            return Err(NitroError::InvalidPreimage(*key));
        }
        Ok(())
    }
