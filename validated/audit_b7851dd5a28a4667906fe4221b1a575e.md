### Title
Signer signs a block whose tenure may have been orphaned by a Bitcoin reorg — fail-open on `get_tenure_tip` errors - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
`check_latest_block_in_tenure`, the function that gates both the post-validation re-check and the final pre-signature re-check, treats *any* error from `client.get_tenure_tip(tenure_id)` — including the 404 the node returns when a tenure's blocks are unknown because a Bitcoin reorg orphaned it — as proof the proposal is valid, rather than as an ambiguous result that needs the same conservative treatment the codebase already applies to an analogous 404 elsewhere.

### Finding Description
`check_latest_block_in_tenure` is the sole check the signer performs against the *node's live chain view* for "does this tenure still stand"; it is invoked both from `check_tenure_change_confirms_parent` / `confirms_latest_block_in_same_tenure` (proposal time) and, more importantly, from `check_block_against_signer_db_state`, which is re-run at two later, security-critical points: [1](#0-0) 

At the end of that function, any failure to fetch the tenure tip is treated as an implicit pass: [2](#0-1) 

`get_tenure_tip` hits `/v3/tenures/tip/:consensus_hash`, which returns 404 "No blocks in tenure" whenever `find_highest_known_block_header_in_tenure` finds nothing for that consensus hash — this is indistinguishable between "this tenure's blocks simply haven't propagated to my node yet" and "this tenure was orphaned by a Bitcoin fork and will never have blocks": [3](#0-2) 

`check_block_against_signer_db_state` is the *last* check run before a signer places its group-threshold signature over a block, in `handle_block_pre_commit`: [4](#0-3) 

and the same function is re-run right after node validation succeeds, in `handle_block_validate_ok`: [5](#0-4) 

Note the asymmetry with the *only other* place in this codebase that faces the identical 404-ambiguity problem — the signed-sibling-conflict guard. That code explicitly refuses to trust a bare 404 and instead cross-checks the node's burnchain tip height before treating an orphaned tenure as dead: [6](#0-5) 

`check_latest_block_in_tenure` has no equivalent tip-height cross-check for its own `get_tenure_tip` error path — it just returns `Ok(true)` ("assume higher — node's proposal endpoint is the backstop"): [7](#0-6) 

That "backstop" reasoning is the trust-boundary bug: the strong validation that actually checks canonical-fork membership of the tenure (`check_block_has_valid_tenure`, gated on `db_handle.has_consensus_hash(tenure_id)` against the *canonical* Bitcoin fork) runs exactly once, at the node's `/v3/block_proposal` endpoint, when the proposal first arrives: [8](#0-7) 

That endpoint is never invoked again at pre-commit-threshold time. The signer instead relies on `check_block_against_signer_db_state`'s cheaper `get_tenure_tip` re-check — which, on ambiguous failure, resolves to "trust the earlier validation" instead of re-verifying canonicity or treating the ambiguity conservatively (as the sibling-conflict code correctly does). This is the same pattern as the reported analog: a value validated once (the tenure's canonical status at proposal-submission time) is reused unchecked at a later action (the irreversible act of signing), and the code's fallback for "cannot verify" is "assume still valid" rather than "assume unsafe."

### Impact Explanation
This lets a signer place its individual signature — and, if enough signers race the same window, lets the *signer set* collectively assemble and broadcast a 70%-weight signature — over a block whose tenure has already been orphaned by a Bitcoin reorg. That is a signer signing a non-canonical block, breaking the "signed ⇔ validated-canonical" invariant the whole pre-commit/signature protocol exists to guarantee (per `docs/signer-flows.md`'s own framing: "a signature is never given away cheaply… the one irreversible act"). This matches the Critical impact category: a signer signing a non-canonical or conflicting block.

### Likelihood Explanation
The trigger requires only ordinary network conditions this codebase is explicitly designed to survive — a Bitcoin reorg landing between the moment a block is proposed/pre-committed and the moment the 70% pre-commit threshold is reached (a window the docs themselves describe as "where most of the subtlety lives: time passes, the burn chain can fork"). No majority of signers, no other signer's key, and no node access is needed — a single lagging/never-yet-informed signer node returning a 404 for the now-orphaned tenure is enough to flip this specific check to "pass." The asymmetry with the carefully-guarded sibling-conflict path (which the same author clearly recognized needed a tip-height cross-check) indicates this is a genuine oversight rather than an intentionally accepted risk.

### Recommendation
Apply the same conservative treatment used by `conflict_still_blocks`/`get_sortition_by_burn_hash` to `check_latest_block_in_tenure`'s `get_tenure_tip` error path: only treat a 404/error as "assume proposal still valid" once the node's own burnchain tip (`get_peer_info`) is confirmed to be at or past the burn height associated with `tenure_id`; otherwise treat the check as inconclusive and hold (do not sign) rather than defaulting to pass. Alternatively, re-invoke a lightweight canonical-tenure check (`has_consensus_hash`) against the node immediately before signing, mirroring the once-only `check_block_has_valid_tenure` guard that currently only runs at initial proposal submission.

### Proof of Concept
1. Miner proposes block `B` for tenure `T` (`consensus_hash = CH_T`) atop the currently canonical sortition; `B` passes `GlobalStateView::check_proposal`/`SortitionsView::check_proposal` and the node's `/v3/block_proposal` validation (`check_block_has_valid_tenure` confirms `CH_T` is canonical at that instant).
2. Signers broadcast pre-commits for `B`; suppose the pre-commit weight has not yet crossed 70% on any signer (e.g., due to normal message-propagation delay).
3. A Bitcoin reorg orphans the sortition for `CH_T` before propagation of that fact reaches all signer nodes; the node backing at least one signer now returns 404 ("No blocks in tenure") from `/v3/tenures/tip/CH_T`, because it never received/committed any blocks under `CH_T` (`stackslib/src/net/api/gettenuretip.rs:104-111`).
4. That signer's later-arriving pre-commit crosses the 70% threshold on some node, entering `handle_block_pre_commit` → `check_block_against_signer_db_state` → `check_latest_block_in_tenure(CH_T, …)`.
5. `get_tenure_tip` returns `Err`; the function hits `stacks-signer/src/chainstate/mod.rs:450-461`, logs "Assuming proposal is higher… for now," and returns `Ok(true)`, so `check_block_against_signer_db_state` returns `None` (no rejection).
6. The signer proceeds to `SIGN: mark_locally_accepted, handle_block_signature, broadcast acceptance` over `B` (`stacks-signer/src/v0/signer.rs:1345-1366`, else-branch), placing a valid signature on a block in a tenure that is, at that moment, non-canonical from the perspective of Bitcoin's actual canonical fork.

**Note on completeness:** I could not fully trace how the node-side final block-acceptance path (`NakamotoChainState::accept_block`/`NewBlock` handling) would react to receiving a fully-assembled signature set over such a block, since that is outside the requested signer-side scope; the finding's impact is scoped to the signer incorrectly producing/broadcasting a signature over a non-canonical block, which is itself the safety break this class of report targets, independent of whatever downstream node-side defense may or may not exist.

1. **Is the conflict's tenure still on the canonical burn chain?** The signer
   saved the tenure's burn block when it arrived (section 8), and
   `/v3/sortitions/burn/:hash` resolves it against the node's canonical fork. A
   404 means a burnchain fork orphaned the tenure: everything it built is void,
   and the conflict is dead no matter what state its block is in. But a 404
   alone is not proof — the same endpoint 404s a perfectly canonical burn block
   when the node is still catching up (and on internal data misses), so it is
   only trusted once the node's burnchain tip (`get_peer_info`) is at or past
   the stored burn block's height; below that, the conflict keeps blocking and
   the next evaluation retries. If the burn block was never saved (a restart,
   or the tenure predates us), the question is skipped rather than guessed.

    /// Verify that the block we received builds upon a valid tenure.
    /// Implemented as a static function to facilitate testing.
    pub(crate) fn check_block_has_valid_tenure(
        db_handle: &SortitionHandleConn,
        tenure_id: &ConsensusHash,
    ) -> Result<(), BlockValidateRejectReason> {
        // Verify that the block's tenure is on the canonical sortition history
        if !db_handle.has_consensus_hash(tenure_id)? {
            warn!(
                "Rejected block proposal";
                "reason" => "Block's tenure consensus hash is not on the canonical Bitcoin fork",
                "consensus_hash" => %tenure_id,
            );
            return Err(BlockValidateRejectReason {
                reason_code: ValidateRejectCode::NonCanonicalTenure,
                reason: "Tenure consensus hash is not on the canonical Bitcoin fork".into(),
                failed_txid: None,
            });
        }
        Ok(())
    }
