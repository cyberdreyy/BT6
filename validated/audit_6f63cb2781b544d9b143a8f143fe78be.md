### Title
Unbounded recursive `serde_json::from_str` in `parse_config` causes validator RPC-thread stack overflow on attacker-controlled Config account data - ([File: account-decoder/src/parse_config.rs])

### Summary
`parse_config` bincode-decodes an attacker-writable Config-program account into a `ValidatorInfo{ info: String }` and then feeds the raw `info` string directly into `serde_json::from_str` with no depth limit. `serde_json`'s default parser is recursive-descent and consumes a stack frame per nesting level, so a deeply-nested JSON array/object string (e.g. 100k consecutive `[` characters) can exhaust the thread stack and abort the process when any client requests `jsonParsed` encoding for that account.

### Finding Description
`parse_config` in `account-decoder/src/parse_config.rs` first bincode-deserializes the account bytes into `ConfigKeys`, and if `key_list.keys[0].0 == validator_info::id()`, it calls `parse_config_data::<String>` to bincode-decode the trailing payload into a `String` (`ValidatorInfo::config_data`), then does: [1](#0-0) 

```rust
pub fn parse_config(data: &[u8], _pubkey: &Pubkey) -> Result<ConfigAccountType, ParseAccountError> {
    let parsed_account = deserialize::<ConfigKeys>(data).ok().and_then(|key_list| {
        if !key_list.keys.is_empty() && key_list.keys[0].0 == validator_info::id() {
            parse_config_data::<String>(data, key_list.keys).and_then(|validator_info| {
                Some(ConfigAccountType::ValidatorInfo(UiConfig {
                    keys: validator_info.keys,
                    config_data: serde_json::from_str(&validator_info.config_data).ok()?,
                }))
            })
```

`serde_json::from_str(&validator_info.config_data)` is the culprit: it drives `serde_json`'s recursive-descent `Value` parser, which recurses once per open bracket/brace with no depth ceiling. There is no `MAX_LONG_FIELD_LENGTH`/`MAX_VALIDATOR_INFO` enforcement in this decode path — those constants are only checked client-side by the `solana-cli` publish-validator-info tool (`cli/src/validator_info.rs`), not by the Config on-chain program or by `parse_config` itself. Because the attacker writes the account directly (not through the CLI), those client-side checks never run, and nothing in the Config program or in `parse_config`/`parse_config_data` bounds the depth or length of the JSON contained in `info`.

Exploit flow:
1. Attacker submits a single transaction creating/writing a Config-program account whose `ConfigKeys[0]` is `validator_info::id()` and whose trailing bincode payload is a `String` of, e.g., `"["repeated 100_000 times` (bincode length-prefixed string, well within the ~10MB `MAX_PERMITTED_DATA_LENGTH` account-size cap, so account creation succeeds).
2. Any client calls `getAccountInfo(pubkey, encoding=jsonParsed)`. RPC dispatches into the parsing pipeline that calls `parse_account_data_v3` (`account-decoder/src/parse_account_data.rs:143`, `ParsableAccount::Config => serde_json::to_value(parse_config(data, pubkey)?)?`), which calls `parse_config`, which calls the unbounded `serde_json::from_str`.
3. The recursion depth is proportional to attacker-chosen nesting and can exceed the RPC-handling thread's stack size, causing a stack overflow. In Rust, stack overflow is not a catchable panic — it aborts the process (SIGABRT/SIGSEGV depending on platform), taking down the entire validator process, not just the one RPC connection. [2](#0-1) 

### Impact Explanation
A single unprivileged client, after one prior transaction writing the malicious Config account, can crash the validator process by issuing one `getAccountInfo`/`getProgramAccounts`/`getMultipleAccounts` call with `jsonParsed` encoding on that account (or any code path that reaches `parse_account_data_v3` for a Config-owned account). This matches the "validator process abort (stack overflow) from a single low-rate call" impact category — a genuine crash/DoS from one request against one attacker-controlled account, not requiring multiple clients or elevated privileges.

### Likelihood Explanation
Feasible and repeatable: creating a Config account with an arbitrary `ConfigKeys`/`ValidatorInfo` payload requires only a standard `system_instruction::create_account` + `config_instruction::store`-style transaction that the attacker fully controls (they are the signer for their own account), no special permissions needed. The payload size needed to trigger a stack overflow (tens to low hundreds of KB of `[` characters) is far below Solana's account size limits. Any subsequent `jsonParsed` `getAccountInfo` call by literally any RPC client — including the attacker themselves, or an unwitting victim — triggers the crash deterministically, and the crash reproduces on every validator/RPC node that later parses this same account with `jsonParsed` encoding.

### Recommendation
- Enforce `MAX_LONG_FIELD_LENGTH`/`MAX_VALIDATOR_INFO`-style length bounds (and a reasonable JSON-nesting depth bound) inside `parse_config`/`parse_config_data` itself, not just in the CLI publish path, since the decoder must treat all on-chain data as attacker-controlled.
- Replace the unbounded `serde_json::from_str` call with a depth-limited JSON parser, or pre-scan `validator_info.config_data` for maximum bracket/brace nesting depth before invoking `serde_json`, rejecting (returning `ParseAccountError`) inputs beyond a safe depth (e.g., 128).
- Alternatively, run this parsing on a thread with a bounded/guarded stack or via a wrapper that catches stack-overflow conditions gracefully (e.g., use `serde_json`'s streaming `Deserializer` with an explicit recursion-limit combinator, or `serde_stacker`-style stack growth guards).

### Proof of Concept
```rust
// account-decoder/src/parse_config.rs (new test)
#[test]
fn test_parse_config_deep_nesting_stack_overflow() {
    // Build a pathologically nested JSON string: 100_000 '[' characters.
    let nested_json: String = "[".repeat(100_000);

    let validator_info = crate::validator_info::ValidatorInfo {
        info: nested_json,
    };
    let info_pubkey = solana_pubkey::new_rand();
    let account = create_config_account(
        vec![(validator_info::id(), false), (info_pubkey, true)],
        &validator_info,
        10,
    );

    // Expected (safe) behavior: parse_config should return an Err(ParseAccountError)
    // instead of causing a stack overflow / process abort.
    let result = std::panic::catch_unwind(|| {
        parse_config(account.data(), &info_pubkey)
    });
    assert!(result.is_ok(), "parse_config aborted/crashed on deeply nested JSON input");
}
```
Run this test (and a fuzz target sweeping nesting depth from 1_000 to 1_000_000) under a constrained-stack test harness (e.g., spawn the test on a thread with the default RPC-service stack size) to confirm that beyond some depth, the process aborts with a stack-overflow signal rather than returning `Err`. A depth-limited parser or explicit `AccountNotParsable` error should be returned instead of aborting.

pub fn parse_account_data_v3(
    pubkey: &Pubkey,
    program_id: &Pubkey,
    data: &[u8],
    additional_data: Option<AccountAdditionalDataV3>,
) -> Result<ParsedAccount, ParseAccountError> {
    let program_name = PARSABLE_PROGRAM_IDS
        .get(program_id)
        .ok_or(ParseAccountError::ProgramNotParsable)?;
    let additional_data = additional_data.unwrap_or_default();
    let parsed_json = match program_name {
        ParsableAccount::AddressLookupTable => {
            serde_json::to_value(parse_address_lookup_table(data)?)?
        }
        ParsableAccount::BpfUpgradeableLoader => {
            serde_json::to_value(parse_bpf_upgradeable_loader(data)?)?
        }
        ParsableAccount::Config => serde_json::to_value(parse_config(data, pubkey)?)?,
        ParsableAccount::Nonce => serde_json::to_value(parse_nonce(data)?)?,
        ParsableAccount::SplToken | ParsableAccount::SplToken2022 => serde_json::to_value(
            parse_token_v3(data, additional_data.spl_token_additional_data.as_ref())?,
        )?,
        ParsableAccount::Stake => serde_json::to_value(parse_stake(data)?)?,
        ParsableAccount::Sysvar => serde_json::to_value(parse_sysvar(data, pubkey)?)?,
        ParsableAccount::Vote => serde_json::to_value(parse_vote(data, pubkey)?)?,
    };
