### Title
`requestInstantWithdraw` bypasses post-default gating, letting new receipts drain funded claim underlyings at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The bug class in the report is "validate entries on read so checks cannot be skipped in one path". In `IdleCreditVault`, the normal withdraw path `requestWithdraw` explicitly validates the post-default state (lines 247-257: revert on stale receipts, then route through the haircut `postDefaultRequests` bucket). The instant path `requestInstantWithdraw` (lines 356-375) performs the same receipt creation — burn CDO strategy tokens, mint user receipt, increment `instantWithdrawsRequests`/`pendingInstantWithdraws` — with **no** `defaultRecoveryFinalized` check at all. The symmetric claim path `claimInstantWithdrawRequest` (lines 380-393) then pays the full `instantWithdrawsRequests[_user]` via `_transferFundedClaim`, which only protects `defaultRecoveryReserve` (lines 897-907) and happily spends any other underlying balance held by the strategy.

### Finding Description
After `finalizeDefaultRecovery`, the strategy holds underlying in two buckets: `defaultRecoveryReserve` (for haircut claims) and non-reserve underlying backing funded-but-unclaimed receipts (e.g., loss-adjusted `lossRecoveryPriceByEpoch` claims and funded requests not yet collected). Post-default, a tranche holder can call the CDO's instant-withdraw entry point, which invokes `requestInstantWithdraw`: it burns the attacker's already-haircut-valued strategy tokens and mints a 1:1 receipt recorded only under the *current* `epochNumber`. Because `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` is 0, `_claimDefaultedInstantWithdrawRequest` (lines 842-856) skips it, and `claimInstantWithdrawRequest` pays the full amount at par through `_transferFundedClaim`. The reserve guard at line 904 only checks `balance - defaultRecoveryReserve >= amount`, so the payout is taken from the non-reserve balance that belongs to other users' funded/loss-adjusted claims.

Broken invariant: "one receipt, one funded payout" and reserve isolation — an unfunded, post-haircut receipt is paid at par from other claimants' funded backing.

### Impact Explanation
Direct theft: the attacker converts tranche tokens (worth `defaultRecoveryPrice` per unit after the haircut) into par-valued underlying, drawing down the non-reserve underlying that backs honest users' pending funded and loss-adjusted claims. Those users' subsequent `claimWithdrawRequest`/`_claimLossAdjustedWithdrawRequest` calls either revert on `NotAllowed` (line 904) or receive less, i.e., permanent loss of their funded claims up to the attacker's tranche balance.

### Likelihood Explanation
Requires only an unprivileged tranche holder and a finalized default, which is a normal pool lifecycle state. No privileged actor misbehavior needed; all attacker calls go through the honest CDO. The sequence is two user transactions (`requestInstantWithdraw` then `claimInstantWithdrawRequest`) in the defaulted phase. Caveat I could not fully verify in the remaining scope: whether `IdleCDOEpochVariant.requestInstantWithdraw`/`claimInstantWithdrawRequest` gate these calls once `defaulted()` is true; if the CDO blocks instant requests post-default the surface narrows, but the strategy function itself is the unguarded entry and mirrors `requestWithdraw`'s explicit default branch, strongly suggesting the check belongs here.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, reject new instant requests (or route them through an already-haircut, reserve-backed bucket like `postDefaultRequests`), and revert if the user has unfinalized receipts. Additionally, in `claimInstantWithdrawRequest`, treat receipts whose epoch is not `defaultRecoveryEpoch` and were created after finalization as unfundable rather than paying them from the non-reserve balance.

### Proof of Concept
Foundry fork sketch:

```solidity
// pool in defaulted phase; finalizeDefaultRecovery already called with
// defaultRecoveryPrice < RECOVERY_FULL and non-reserve underlying > 0
// (funded loss-adjusted/funded claims of user B still unclaimed)

uint256 pre = underlying.balanceOf(address(strategy));
uint256 reserve = strategy.defaultRecoveryReserve();
uint256 stealable = pre - reserve; // funded claims of honest user B

// attacker holds tranche tokens worth recoveryPrice per unit
vm.prank(attacker);
cdo.requestInstantWithdraw(amount);          // no default check in strategy
vm.prank(attacker);
cdo.claimInstantWithdrawRequest();           // pays amount at par

assertEq(underlying.balanceOf(attacker) - balPre, amount); // paid at par
// B's claim now reverts NotAllowed or underpays:
vm.prank(userB);
vm.expectRevert(NotAllowed.selector);
cdo.claimWithdrawRequest(userB_tranche);
```

The test asserts the attacker's receipt, created after finalization with zero basis in `defaultRecoveryEpoch`, drains `min(amount, stealable)` of the non-reserve funded underlying at par.
