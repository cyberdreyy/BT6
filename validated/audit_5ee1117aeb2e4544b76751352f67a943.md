## Title
v1 signer's tenure-change duplicate check misses locally-accepted competing tenure-start blocks, allowing equivocation on a single tenure - (File: stacks-signer/src/chainstate/v1.rs)

## Summary
`v1::SortitionState::validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:461-520`) guards against a signer re-signing a competing tenure-start block for the same tenure by looking up `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` (line 505-506). Unlike the v2 path, which was fixed to use `get_last_signed_block` (locally-or-globally accepted, `stacks-signer/src/chainstate/v2.rs:344-345`), the v1 check only catches blocks that already reached global acceptance, so a locally-accepted-but-not-yet-globally-accepted competing tenure-start block for the *same* tenure is invisible to it.

## Finding Description
The relevant equality is: for a given (signer, tenure) pair, once the signer has put a signature over any block in that tenure (`signed_self`/`signed_group` set — tracked by `has_signed_block_in_tenure`, `stacks-signer/src/signerdb.rs:1511-1516`), the signer must never sign a second, conflicting block for that same tenure.

`validate_tenure_change_payload` in v1 is supposed to enforce this for tenure-start (`BlockFound`) blocks by rejecting with `RejectReason::DuplicateBlockFound` when the signer has already accepted a block in the tenure the new tenure-change block is starting (`block.header.consensus_hash`, i.e. the *new* tenure the miner is announcing, not the parent tenure): [1](#0-0) 

That lookup uses `SignerDb::get_last_globally_accepted_block`, which only returns blocks whose state is `GloballyAccepted` (see the corresponding query filtering only on `BlockState::GloballyAccepted` in `signerdb.rs`, exercised by `get_accepted_blocks`): [2](#0-1) 

The v2 equivalent was fixed to close exactly this gap, as documented directly in its regression test: [3](#0-2) 
and implemented with `get_last_signed_block` (locally- or globally-accepted), not `get_last_globally_accepted_block`: [4](#0-3) 

The v1 code path was never updated to match. `docs/signer-flows.md` documents this divergence explicitly: [5](#0-4) 

**Exploit flow (attacker = miner with one BTC slot, running their own signer weight, gossiping BlockProposals):**
1. Attacker wins the sortition slot for tenure `T` and proposes tenure-start block `X` (contains `TenureChange{cause: BlockFound, tenure_consensus_hash: T, ...}` + coinbase).
2. The victim v1 signer accepts `X`, crosses the local signature threshold, and calls `mark_locally_accepted` — `signed_self`/`signed_group` gets set, `state = LocallyAccepted`. Global acceptance (state transition to `GloballyAccepted`, which happens only once the node reports the block via a `NewBlock` event) has not yet happened — e.g. the attacker simply withholds broadcasting `X` to the node, or the node hasn't processed it yet.
3. Attacker crafts a second, conflicting tenure-start proposal `B` for the *same* tenure `T` (same `tenure_consensus_hash`, different transactions/coinbase — the exact pattern used in the v2 regression test `check_tenure_change_rejects_when_locally_accepted_block_exists`, adapted to the v1 code path).
4. `v1::validate_tenure_change_payload` runs `get_last_globally_accepted_block(&B.header.consensus_hash)`; because `X` is only `LocallyAccepted`, this returns `None`, so the `DuplicateBlockFound` branch is skipped and the function returns `Ok(())`.
5. `B` proceeds through the rest of the signer state machine, gets locally accepted and signed by the same v1 signer — despite `has_signed_block_in_tenure(T) == true` from step 2.

This breaks the uniqueness/equivocation guard: the same signer now holds signatures over two conflicting blocks for tenure `T`. Existing guards (`has_signed_block_in_tenure`, used for liveness/timeout decisions in section 8 of `docs/signer-flows.md`, not for duplicate rejection in the proposal path) do not run inside `validate_tenure_change_payload`; the parent-tenure confirmation check (`check_tenure_change_confirms_parent` via `get_tenure_last_block_info`/`get_last_signed_block`, shared in `chainstate/mod.rs`) is a different check about the *parent* tenure and does not cover this same-tenure duplicate scenario.

## Impact Explanation
This is a Critical chain-safety break: a signer signs two conflicting blocks for the same tenure, violating the uniqueness/equivocation guarantee the duplicate check exists to enforce. If enough v1 signers are similarly induced (each independently, needing only one slot plus gossip per attacker instance, but each v1 signer is independently vulnerable), a fork/equivocation at the tenure-start boundary becomes signable rather than being fail-closed. This is repeatable for every tenure the attacker wins while any signer in the set still runs the v1 (pre-`GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`) chainstate, i.e., throughout a rolling upgrade window.

## Likelihood Explanation
- Precondition: at least one signer runs `SortitionState` v1 (protocol version below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`), which is exactly the mixed-fleet-during-upgrade condition called out in `docs/signer-flows.md`.
- Attacker cost: winning a single miner BTC slot (attacker already needs this to propose any block) plus gossiping two competing `BlockProposal`s for the same tenure over StackerDB — well within the unprivileged-attacker model (one slot, no signer majority, no auth_token, no local access).
- Feasibility: entirely mechanical — withhold/delay broadcast of the first proposal to the node (or simply race it) so that global acceptance has not yet been observed when the second, competing proposal is sent.
- Repeatable once per mixed-version tenure won by the attacker, for as long as any v1 signers remain active.

## Recommendation
Change `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, mirroring the fix already applied to `v2.rs`, so the duplicate check also catches `LocallyAccepted` blocks.

## Proof of Concept
Rust test plan (`stacks-signer/src/chainstate/tests/v1.rs`), mirroring `check_tenure_change_rejects_when_locally_accepted_block_exists` from `v2.rs`:
1. Build a `SortitionState` (v1) test environment (`setup_test_environment` analog for v1).
2. Insert `existing_block_info` for tenure `T` (`consensus_hash = cur_sortition.data.consensus_hash`), call `existing_block_info.mark_locally_accepted(false)` (no `mark_globally_accepted`), `signer_db.insert_block(&existing_block_info)`.
3. Assert precondition: `signer_db.has_signed_block_in_tenure(&T).unwrap() == true`.
4. Build a second tenure-start `NakamotoBlock` `B` for the same tenure `T` with a `TenureChangePayload{cause: BlockFound, tenure_consensus_hash: T, prev_tenure_consensus_hash: parent_tenure_id, ...}` plus coinbase, signed by the miner key.
5. Call `sortition_state.validate_tenure_change_payload(&proposed_by, &tenure_change, &B, &mut signer_db, &client)`.
6. Assert the equality break: `result.is_ok()` (bug present), where the expected/fixed behavior is `matches!(result, Err(RejectReason::DuplicateBlockFound))` (as in the v2 regression test).
7. Optionally continue through `signer.rs::handle_block_proposal` to confirm `B` ends up with `signed_self` set in `signer_db`, completing the equivocation demonstration.
