### Title
`allowed_images` bypass via unexpanded-vs-expanded image string mismatch between `common.VerifyAllowedImage` and `createVMTunnel` - ([File: executors/instance/instance.go], [File: executors/internal/autoscaler/acquisition.go])

### Summary
`executor.Prepare` in `executors/instance/instance.go` validates the job-supplied `image:` value against `allowed_images` **before** CI/CD variable expansion, but the value actually used to create the nested VM in `acquisitionRef.createVMTunnel` is the **variable-expanded** string. Because these two are different strings, a pipeline author can put a variable reference (or a variable-populated suffix) into `image:` that satisfies the `doublestar.Match` glob check in its raw form, while the expanded value used to create the VM resolves to an entirely different, non-allowed image.

### Finding Description
In `executors/instance/instance.go`, `Prepare` validates the image name directly off the job definition: [1](#0-0) 

This calls `common.VerifyAllowedImage`, which does a `doublestar.Match(allowedImage, options.Image)` against the **literal** `options.Build.Image.Name` string: [2](#0-1) 

No variable expansion is performed on `options.Build.Image.Name` prior to this check.

After this check passes, `Prepare` calls `environment.Prepare(...)`, which for the instance/autoscaler executor is `acquisitionRef.Prepare` → `createVMTunnel` in `executors/internal/autoscaler/acquisition.go`. There, the image string is taken again from `options.Build.Image.Name` (same field, when `mapJobImageToVMImage` is true, which `NewProvider` sets for the instance executor) and is then **expanded**: [3](#0-2) 

The expanded `image` is passed unchecked to `nc.Create(ctx, image, &slot)`, which creates the nesting VM. There is no second call to `VerifyAllowedImage` after expansion.

The unit test `acquisition_test.go` "variables expansion works for image" confirms that `image:` values containing variable references (e.g. `${TEST_VARIABLE}`) are an intentionally supported feature, expanded from job variables at VM-creation time: [4](#0-3) 

Exploit flow:
1. Attacker (pipeline author) defines a job-level variable, e.g. `MYVAR: "evil-registry.example/backdoor:latest"`, in `.gitlab-ci.yml`, which is fully attacker-controlled (`variables:` block).
2. Attacker sets `image: "alpine:$MYVAR"` (or any prefix matching one of the admin's `allowed_images` glob patterns, e.g. `alpine:*`).
3. `instance.go`'s `Prepare` calls `VerifyAllowedImage` with `Image = "alpine:$MYVAR"`. Since `doublestar.Match("alpine:*", "alpine:$MYVAR")` is `true` (the glob only checks the literal unexpanded text and has no path separator to stop it), the check **passes**.
4. Execution proceeds to `createVMTunnel`, which computes `image = options.Build.GetAllVariables().ExpandValue("alpine:$MYVAR")`, producing e.g. `alpine:evil-registry.example/backdoor:latest` — a string that was never itself validated against `allowed_images` and does not match the intended allowed pattern set once truly resolved as an image reference.
5. This unvalidated string is passed directly to `nc.Create`, which instructs the nesting hypervisor to create a VM using this (now attacker-influenced) image reference.

Existing protections fail because: (a) the allowed-image check operates on the pre-expansion string, (b) expansion is a pure textual substitution with no re-validation, and (c) `doublestar.Match` treats `$VAR`-style placeholders as opaque literal characters that satisfy `*` wildcards, so a crafted job variable can be smuggled through a glob pattern intended to restrict fixed prefixes/suffixes.

### Impact Explanation
A job author can cause the runner to provision a nested/autoscaled VM instance from an image that was never approved by the `allowed_images` restriction, defeating a runner-enforced control whose entire purpose is to prevent unprivileged pipeline authors from selecting arbitrary VM images. This can lead to execution inside a VM image with different (potentially stronger) tooling/credentials/trust characteristics than the operator intended to allow, i.e. exactly the scoped "restriction bypass causing stronger identity/permissions via unauthorized VM image" impact.

### Likelihood Explanation
Preconditions: VM isolation nesting must be enabled (`options.Config.Autoscaler.VMIsolation.Enabled`) and `allowed_images` must be configured with at least one glob pattern that can incidentally match a job-crafted `$VAR`-containing string (a plausible real-world pattern, e.g. `"*"`, `"repo/*"`, `"name:*"`, etc., all common ways admins scope allowed images by prefix/tag while allowing flexible suffix). Given this, the attack requires only standard `.gitlab-ci.yml` `variables:` and `image:` fields — fully within the capability of any unprivileged pipeline author, no special runner/network access needed, and it is fully repeatable per job run.

### Recommendation
Perform the `allowed_images` check on the **fully expanded** image string, at the same point (or later) where the string is actually used to create the VM — i.e., call `options.Build.GetAllVariables().ExpandValue(options.Build.Image.Name)` before calling `common.VerifyAllowedImage` in `executors/instance/instance.go`, or alternatively move/duplicate the `VerifyAllowedImage` call into `createVMTunnel` in `executors/internal/autoscaler/acquisition.go` immediately after the `ExpandValue` call and before `nc.Create` is invoked, failing closed if validation fails post-expansion.

### Proof of Concept
Go unit test extending `TestAcquisitionRef_Prepare` / a new test around `instance.executor.Prepare` + `VerifyAllowedImage`:
```go
func TestAllowedImages_BypassViaVariableExpansion(t *testing.T) {
    allowed := []string{"alpine:*"}
    rawImage := "alpine:$MYVAR" // as it appears in job config, unexpanded

    // Step 1: simulate instance.go's pre-expansion check
    err := common.VerifyAllowedImage(common.VerifyAllowedImageOptions{
        Image:         rawImage,
        AllowedImages: allowed,
    }, noopLogger)
    require.NoError(t, err) // check incorrectly passes

    // Step 2: simulate createVMTunnel's expansion with attacker-controlled MYVAR
    vars := spec.JobVariables{{Key: "MYVAR", Value: "evil-registry.example/backdoor:latest"}}
    expanded := vars.ExpandValue(rawImage)

    // Step 3: assert the expanded (unvalidated) image no longer matches the intended allow-list scope
    ok, _ := doublestar.Match("alpine:*", expanded)
    assert.False(t, ok, "expanded image %q should not have matched allowed pattern, exposing bypass", expanded)
}
```
Expected assertion failure demonstrates that the value validated (`rawImage`) and the value used to create the VM (`expanded`) diverge, and the divergent value is not itself checked against `allowed_images`, confirming the bypass.
