### Title
Stale confirmations from removed multisig members still count toward quorum, allowing execution below threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts the size of the `confirmations` set for a request against `num_confirmations` to decide whether to execute a request [1](#0-0) . `delete_member`, which is invoked when a `DeleteMember` request executes, only purges requests *authored by* the removed member and their `num_requests_pk` entry — it never scans other pending requests to strip that member's prior confirmations from their `confirmations` sets [2](#0-1) . As a result, a confirmation cast by a member who is later removed from `self.members` remains counted toward the quorum of any other still-pending request, letting that request execute with fewer live, currently-authorized members than `num_confirmations` requires.

### Finding Description
The intended custody binding of the multisig is: a request executes only when at least `num_confirmations` **current, live** members have approved it, i.e. `len(confirmations ∩ live_members) >= num_confirmations`.

The actual code enforces only `len(confirmations) >= num_confirmations` [3](#0-2) , where `confirmations` is a `HashSet<String>` of member identifiers accumulated over the lifetime of the request, independent of current membership.

`delete_member` is the only place membership changes are propagated to request/confirmation bookkeeping, and it is narrowly scoped:
- It removes requests where `r.member == member` (requests *created* by the removed member) and clears their confirmation sets.
- It removes the `num_requests_pk` entry for that member.
- It does **not** iterate `self.confirmations` for other requests to remove the departing member's prior approvals [4](#0-3) .

So if member M confirms request R (not authored by M), and M is subsequently removed via a separate `DeleteMember` request, M's entry persists inside `confirmations[R]`. Later confirmations by other, still-live members can now reach `num_confirmations` sooner than intended because the stale M-confirmation is still being counted, breaking the equality between "confirmations counted" and "live members who actually approved."

### Impact Explanation
This crosses the threshold/authorization boundary the report describes by analogy ("confirmations counted versus live members"). A request (e.g., a `Transfer` of NEAR out of the multisig account, or an `AddKey`/`AddMember` action) can be executed with actual live-member approval strictly below the configured `num_confirmations`, i.e. "a multisig request executed below threshold" — one of the explicitly listed Critical impacts. Funds can be moved, or control of the account (new keys/members) can be granted, by a coalition smaller than the wallet's configured security threshold.

### Likelihood Explanation
This requires only ordinary lifecycle events already supported by the contract's own API: a member confirms a pending request, and later that member is removed via `DeleteMember` (e.g., a departing employee, revoked key, or a malicious member deliberately confirming favorable requests before being offboarded). No privileged access beyond normal multisig membership is needed, and the confirmation-leak is triggered automatically by the existing `delete_member` code path — no special exploit primitives are required.

### Recommendation
When a member is deleted, iterate all pending requests' `confirmations` sets and remove the departing member's entry (not just requests they authored). Alternatively, validate at `confirm`-time / execution-time that every entry still counted in `confirmations` corresponds to a value in `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new(members=[A, B, C, D], num_confirmations=3)`.
2. A calls `add_request_and_confirm(R)` where `R` is `Transfer{ amount, receiver_id: <attacker> }`. `confirmations[R] = {A}`.
3. B calls `confirm(R)`. `confirmations[R] = {A, B}` (2 < 3, not yet executed).
4. Separately, A, C, D confirm a `DeleteMember{ member: B }` request (3-of-4, legitimate quorum) which executes `delete_member`, removing B from `self.members`. Per `delete_member`, only requests authored by B are purged; `R` (authored by A) is untouched, so `confirmations[R]` still contains `"B"` [4](#0-3) .
5. C calls `confirm(R)`. `confirmations[R].len() + 1 == 3 >= num_confirmations(3)` [3](#0-2) , so `R` executes and transfers funds to the attacker — even though only A and C are currently live members who ever approved it plus the stale, no-longer-valid confirmation from removed member B, i.e., execution occurred with 2 live-member approvals against a configured threshold of 3.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
