### Analysis

This scenario is not a valid vulnerability under the given rules.

The "bypass" described is not actually a bypass — it's the intended behavior of `SwQos::build_connection_context`. A connection is classified `ConnectionPeerType::Staked(stake)` precisely when `stake_ratio >= min_stake_ratio`, i.e., when the stake is large enough to be entitled to at least one stream per throttling window; this is exactly what the threshold is designed to do, not a defect that lets attackers "bypass" a check.

<cite repo="EzraCole/agave--001" path="streamer/src/nonblocking/swqos.rs" start="315="329" end="329" /> [1](#0-0) 

The `.max(max_unstaked_load_in_throttling_window + 1)` floor in `available_load_capacity_in_throttling_duration` is also explicit, intentional, and documented design: "1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked clients get at least 1 more number of streams than unstaked connections." This exact behavior is covered by an existing unit test, `test_staked_capacity_shares_when_throttled`, confirming it is a known trade-off, not an oversight. [2](#0-1) [3](#0-2) 

Critically, the described attack requires the attacker to actually acquire and hold real, on-chain delegated stake for "dozens of low-stake keypairs" so they appear in `StakedNodes` with nonzero `get_node_stake`. Becoming a staked validator identity is explicitly excluded by the threat model: the rules state the attacker is unprivileged and is "Not a validator, staked node, leader, gossip/turbine/repair peer, operator." Acquiring stake is not something achievable by "funding a keypair" or "submitting transactions" — it requires becoming an actual staked network participant, which is out of scope. [4](#0-3) 

Even setting aside the actor-privilege issue, the aggregate resource consumption remains bounded by existing connection-table caps (`max_staked_connections`, `max_connections_per_staked_peer`) and per-connection QUIC stream limits (`compute_max_allowed_uni_streams_with_rtt`), so the "unbounded aggregation above the intended staked budget" claim overstates the actual bound, which scales with the number of distinct real staked identities the attacker would have to fund with genuine stake — a cost-bearing, capital-intensive precondition rather than a free exploit. fn compute_max_allowed_uni_streams_with_rtt(
    rtt_millis: u32,
    peer_type: ConnectionPeerType,
    total_stake: u64,
) -> u32 {
    let streams = match peer_type {
        ConnectionPeerType::Staked(peer_stake) => {
            // No checked math for f64 type. So let's explicitly check for 0 here
            if total_stake == 0 || peer_stake > total_stake {
                warn!(
                    "Invalid stake values: peer_stake: {peer_stake:?}, total_stake: \
                     {total_stake:?}"
                );

                QUIC_MIN_STAKED_CONCURRENT_STREAMS
            } else {
                let delta = (QUIC_TOTAL_STAKED_CONCURRENT_STREAMS
                    - QUIC_MIN_STAKED_CONCURRENT_STREAMS) as f64;

                (((peer_stake as f64 / total_stake as f64) * delta) as u32
                    + QUIC_MIN_STAKED_CONCURRENT_STREAMS)
                    .clamp(
                        QUIC_MIN_STAKED_CONCURRENT_STREAMS,
                        QUIC_MAX_STAKED_CONCURRENT_STREAMS,
                    )
            }
        }
        ConnectionPeerType::Unstaked => QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
    };
    // scale amount of streams based on RTT if RTT is larger than REFERENCE_RTT_MS
    // multiply first then divide to avoid rounding errors.
    (streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS))) / REFERENCE_RTT_MS
}
