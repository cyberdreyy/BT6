### Title
Password change fails to revoke previously issued API tokens, allowing indefinite continued authentication with a stolen token - ([File: core/web/user_controller.go])

### Summary
`(*UserController).UpdatePassword` only calls `ClearNonCurrentSessions`, which invalidates other browser/cookie sessions but does not touch or revoke the user's API token (`TokenKey`/`TokenHashedSecret`) created via `NewAPIToken`. Because API token authentication (`AuthenticateByToken`) is a completely separate code path from session authentication, an attacker holding a previously issued API token retains full access after the victim "rotates" their credentials by changing the password.

### Finding Description
`UserController.UpdatePassword` (core/web/user_controller.go:202-241) calls `u.updateUserPassword(c, &user, request.NewPassword)`, which in turn calls `orm.ClearNonCurrentSessions(ctx, sessionID)` followed by `orm.SetPassword(ctx, user, newPassword)`: [1](#0-0) 

`ClearNonCurrentSessions` only operates on the session store (cookie-based sessions identified by `SessionIDKey`), as seen from the `AuthenticationProvider` interface, which keeps session management (`CreateSession`, `ClearNonCurrentSessions`, `DeleteUserSession`) entirely separate from API token management (`SetAuthToken`, `CreateAndSetAuthToken`, `DeleteAuthToken`, `FindUserByAPIToken`): [2](#0-1) 

Crucially, API token authentication (`AuthenticateByToken`) never consults the session table at all — it loads the user directly via `FindUserByAPIToken` and validates the token against the user's stored `TokenSalt`/`TokenHashedSecret` via `AuthenticateUserByToken`: [3](#0-2) 

Since `UpdatePassword`/`updateUserPassword` never calls `DeleteAuthToken` (or otherwise rotates the stored `TokenKey`/`TokenHashedSecret`), an API token issued earlier via `NewAPIToken` (core/web/user_controller.go:244-286) remains valid and continues to satisfy `AuthenticateByToken` after a password change. The only way to invalidate the token is to explicitly call `DeleteAPIToken` or `NewAPIToken` again — actions a victim who only "changes password" believing it revokes access will not necessarily take.

### Impact Explanation
An attacker who has stolen a user's API token (e.g., leaked from a script, CI config, or client machine) can continue authenticating to protected endpoints (including key-export/secret-exposing routes) indefinitely after the victim changes their password, because password rotation does not revoke the API token credential. This falls under credential/session revocation failure leading to continued unauthorized access and potential key/secret exfiltration.

### Likelihood Explanation
Requires the attacker to already possess a previously issued, valid API token for the victim account (a precondition explicitly stated in the question). Given that precondition, exploitation is trivial and fully reliable: no additional steps are needed beyond replaying the token after the victim's password change, since the token validation path is entirely independent of the password/session state.

### Recommendation
When a user's password is changed via `UserController.UpdatePassword`, also revoke or rotate the user's existing API token (call `orm.DeleteAuthToken(ctx, &user)` or regenerate it) in `updateUserPassword`, in addition to `ClearNonCurrentSessions`. Alternatively, clearly document to operators/users that password change and API token revocation are independent actions and that `DeleteAPIToken` must be called separately to fully revoke access.

### Proof of Concept
1. Create a user, log in to establish a session, and call `NewAPIToken` to obtain `{AccessKey, Secret}`.
2. Call `PATCH /user/password` with the correct old password to change to a new password — assert 200 OK.
3. Using the previously obtained API token in `X-Chainlink-APIKey` / `X-Chainlink-APISecret` headers, call a protected endpoint (e.g., an export-keys route) that uses `webauth.Authenticate(..., webauth.AuthenticateByToken)`.
4. Assert the request currently succeeds (200), demonstrating the token was not revoked — expected/fixed behavior should return 401.

func (u *UserController) updateUserPassword(c *gin.Context, user *clsession.User, newPassword string) error {
	ctx := c.Request.Context()
	sessionID, err := getCurrentSessionID(c)
	if err != nil {
		return err
	}
	orm := u.App.AuthenticationProvider()
	if err := orm.ClearNonCurrentSessions(ctx, sessionID); err != nil {
		u.App.GetLogger().Errorf("failed to clear non current user sessions: %s", err)
		return errors.New("unable to update password")
	}
	if err := orm.SetPassword(ctx, user, newPassword); err != nil {
		if errors.Is(err, clsession.ErrNotSupported) {
			return errUnsupportedForAuth
		}
		u.App.GetLogger().Errorf("failed to update current user password: %s", err)
		return errors.New("unable to update password")
	}
	return nil

func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
