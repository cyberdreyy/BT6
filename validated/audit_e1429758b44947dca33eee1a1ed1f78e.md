**Analysis:**

`_new_from_parent` itself performs no lt-hash mixing at all — it simply clones the parent's current `accounts_lt_hash` value into the child bank via `accounts_lt_hash: Mutex::new(parent.accounts_lt_hash.lock().unwrap().clone())`. [1](#0-0) 

The actual mixing happens later, during `freeze()`, through `enqueue_on_chain_accounts_lt_hash_updates` and `finish_accounts_lt_hash_updates`, which call `AccountsLtHashAsyncProgress::process` to mix out the previous account state and mix in the current one for every modified account. [2](#0-1) 

The per-account contribution is derived from `AccountsDb::lt_hash_account`, which returns an identity/zero contribution only for zero-lamport (dead) accounts, and otherwise hashes `lamports || data || executable || owner || pubkey` with BLAKE3 and expands the digest via BLAKE3's XOF into the 1024×u16 `LtHash` value. [3](#0-2) 

`LtHash::mix_in`/`mix_out` use `wrapping_add`/`wrapping_sub` per-element by design — this is the standard lattice-hash construction (an additively-homomorphic incremental hash over Z/2^16 per element, 1024 elements ≈ 16Kbit total state), not an unintended overflow bug. [4](#0-3) 

For an attacker to make two distinct account states (different lamports/data/owner) mix into the accounts lt-hash identically, they would need to find a BLAKE3-XOF preimage/second-preimage collision across the full 1024-element output — this requires breaking BLAKE3's cryptographic security, not exploiting an agave code defect. The audit rules explicitly exclude findings that require breaking a dependency's/toolchain's cryptography rather than a bug in agave itself. There is no reachable code path in `_new_from_parent` or the lt-hash mixing logic that lets an unprivileged fee-payer's transaction force a hash collision or cause consensus divergence through normal account writes; the mixing logic is deterministic and identical on every replaying validator, so identical committed account states always produce identical lt-hash contributions.

    pub fn lt_hash_account(account: &impl ReadableAccount, pubkey: &Pubkey) -> AccountLtHash {
        if account.lamports() == 0 {
            return ZERO_LAMPORT_ACCOUNT_LT_HASH;
        }

        let hasher = Self::hash_account_helper(account, pubkey);
        let lt_hash = LtHash::with(&hasher);
        AccountLtHash(lt_hash)
    }

    /// Hashes `account` and returns the underlying Hasher
    fn hash_account_helper(account: &impl ReadableAccount, pubkey: &Pubkey) -> blake3::Hasher {
        let mut hasher = blake3::Hasher::new();

        // allocate a buffer on the stack that's big enough
        // to hold a token account or a stake account
        const META_SIZE: usize = 8 /* lamports */ + 1 /* executable */ + 32 /* owner */ + 32 /* pubkey */;
        const DATA_SIZE: usize = 200; // stake accounts are 200 B and token accounts are 165-182ish B
        const BUFFER_SIZE: usize = META_SIZE + DATA_SIZE;
        let mut buffer = SmallVec::<[u8; BUFFER_SIZE]>::new();

        // collect lamports into buffer to hash
        buffer.extend_from_slice(&account.lamports().to_le_bytes());

        let data = account.data();
        if data.len() > DATA_SIZE {
            // For larger accounts whose data can't fit into the buffer, update the hash now.
            hasher.update(&buffer);
            buffer.clear();

            // hash account's data
            hasher.update(data);
        } else {
            // For small accounts whose data can fit into the buffer, append it to the buffer.
            buffer.extend_from_slice(data);
        }

        // collect executable, owner, and pubkey into buffer to hash
        buffer.push(account.executable().into());
        buffer.extend_from_slice(account.owner().as_ref());
        buffer.extend_from_slice(pubkey.as_ref());
        hasher.update(&buffer);

        hasher
    }

    /// Mixes `other` into `self`
    ///
    /// This can be thought of as akin to 'insert'
    pub fn mix_in(&mut self, other: &Self) {
        for i in 0..self.0.len() {
            self.0[i] = self.0[i].wrapping_add(other.0[i]);
        }
    }

    /// Mixes `other` out of `self`
    ///
    /// This can be thought of as akin to 'remove'
    pub fn mix_out(&mut self, other: &Self) {
        for i in 0..self.0.len() {
            self.0[i] = self.0[i].wrapping_sub(other.0[i]);
        }
    }
