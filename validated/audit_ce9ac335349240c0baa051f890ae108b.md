## Title
Proposer-slashing can erase an already-quorum-confirmed `BuilderPendingPayment`, letting a builder escape a committed payment - (File: `specs/gloas/beacon-chain.md`)

## Summary
In the Gloas (ePBS) fork, `process_proposer_slashing` unconditionally zeroes the `BuilderPendingPayment` entry associated with the slashed proposer's slot, without checking whether that payment has already accumulated enough attester weight to be considered "confirmed" (`payment.weight >= quorum`). This lets a proposer who colludes with (or is) the builder discard a builder's already-earned payment obligation simply by self-inflicting a proposer slashing (equivocating on their own slot), causing the committed `bid.value` to never be withdrawn from the builder's balance nor paid to `fee_recipient`.

## Finding Description
When a builder's bid is accepted for a slot, the state records a `BuilderPendingPayment` with `proposer_index`, `weight`, and a `withdrawal` (amount owed by the builder to `fee_recipient`). As attestations for that slot arrive, `process_attestation` increments `payment.weight`: [1](#0-0) 

Once `payment.weight >= get_builder_payment_quorum_threshold(state)`, the epoch-boundary function `process_builder_pending_payments` moves the payment into `builder_pending_withdrawals`, from which the builder is eventually actually charged (balance decreased) and `fee_recipient` paid: [2](#0-1) 

However, `process_proposer_slashing` (modified for Gloas) clears the pending payment for the equivocating proposer's slot **unconditionally**, regardless of whether `payment.weight` has already reached quorum: [3](#0-2) 

The comment explains the `payment.proposer_index == header_1.proposer_index` guard was added to stop an *unrelated* equivocation from griefing an honest proposer's payment — but it does not check whether the payment is already "earned" (quorum-confirmed). A proposer can trivially equivocate on their own slot (sign two distinct headers with their own key — no cooperation from any other party is required), submit a `ProposerSlashing` against themselves within the 2-epoch window, and thereby erase a `BuilderPendingPayment` that already met quorum, before `process_builder_pending_payments` would have settled it.

This is structurally the same bug class as the reported `perp_statistics_reset` issue: a "reset" path zeroes an accounted amount owed to/by a party without first checking whether that amount is already due, letting the responsible party (here, the builder, aided by a self-sacrificing proposer) skip payment.

## Impact Explanation
This breaks the equality that a payload the network has already attested/confirmed as delivered obligates the builder to pay the committed amount to `fee_recipient`. Instead, the payment silently evaporates: the builder's balance is never decreased and `fee_recipient` never receives the funds — i.e., "a builder payment ... escaped," which is explicitly a High-impact category (builder payment misdirected/escaped). Because the proposer's slashing penalty is bounded (`effective_balance // MIN_SLASHING_PENALTY_QUOTIENT_ELECTRA`, a small fraction of stake) while `bid.value` can be arbitrarily large (e.g., high-MEV blocks), a colluding builder/proposer pair can profit whenever the escaped payment exceeds the slashing cost (plus any side-payment/bribe to the proposer).

## Likelihood Explanation
The equivocation required is entirely self-produced by the proposer (sign two conflicting headers for their own slot), requiring no external validator collusion, network partition, or client bug — only a colluding or vertically-integrated builder/proposer pair. The 2-epoch window during which `builder_pending_payments` entries remain clearable gives ample time to submit the slashing after quorum is reached but before the epoch-boundary settlement runs, making the attack practically executable whenever it is economically worthwhile.

## Recommendation
Before clearing a `BuilderPendingPayment` in `process_proposer_slashing`, check whether `payment.weight` has already reached `get_builder_payment_quorum_threshold(state)`. If quorum has been reached, the payment should be settled normally (appended to `builder_pending_withdrawals`) rather than discarded, since it is already consensus-confirmed; only payments that have not yet reached quorum (i.e., not yet earned/committed) should be eligible for clearing on proposer slashing.

## Proof of Concept
1. Builder `B` wins slot `S` with `bid.value = V`, `fee_recipient = F`; proposer `P` proposes the block. `state.builder_pending_payments[idx] = {proposer_index: P, weight: 0, withdrawal: {amount: V, fee_recipient: F, builder_index: B}}`.
2. Subsequent blocks in the same/adjacent slots include attestations with the correct same-slot payload flag; `process_attestation` increments `payment.weight` (`specs/gloas/beacon-chain.md:2382-2403`) until `payment.weight >= quorum`.
3. Before the epoch boundary runs `process_builder_pending_payments`, `P` (self-signing two distinct headers for slot `S`) submits a `ProposerSlashing` in a later block, still within the current/previous epoch window.
4. `process_proposer_slashing` matches `payment.proposer_index == P` and sets `state.builder_pending_payments[idx] = BuilderPendingPayment.empty()` (`specs/gloas/beacon-chain.md:2461-2462`), discarding the already-quorum-reached withdrawal, then slashes `P`.
5. At the next epoch boundary, `process_builder_pending_payments` sees an empty entry for slot `S` and appends nothing to `builder_pending_withdrawals`.
6. `B`'s balance is never decreased by `V`; `F` never receives `V`. `P` pays only the bounded slashing penalty (and exits), which can be smaller than `V`, making the collusion profitable.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
