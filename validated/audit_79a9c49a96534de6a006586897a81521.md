### Title
Signer weight double-counted in both `total_weight_approved` and `total_weight_rejected` when a signer switches its vote for the same block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side `StackerDBListener` tallies signer `BlockResponse` messages into two independent counters, `total_weight_approved` and `total_weight_rejected`, guarded by two *different* dedup sets (`gathered_signatures` for accept, `responded_signers` shared/used for reject). A signer that first rejects and later accepts the same block (a legitimate, supported reconsideration flow) has its weight added to `total_weight_rejected` and never removed, and then added again to `total_weight_approved` because the accept-side guard only checks `gathered_signatures`, not whether that slot already contributed to the rejection tally. This breaks the "aggregated-weight vs verified-accepts" invariant the coordinator relies on. [1](#0-0) [2](#0-1) 

### Finding Description
`handle_stackerdb_message` (or equivalent dispatch loop) processes `BlockResponse::Accepted` and `BlockResponse::Rejected` for the same `signer_signature_hash` independently:

- On `Accepted`: weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, then the slot is inserted into both `gathered_signatures` and `responded_signers`. [1](#0-0) 
- On `Rejected`: weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` succeeds (i.e., first time this slot responds at all). [2](#0-1) 

Because the guard on the accept path is `gathered_signatures` (populated only by accepts) rather than `responded_signers` (populated by both), a signer that rejects first (weight added to `total_weight_rejected`, `responded_signers` now contains the slot) and later sends an `Accepted` message for the *same block hash* will pass the `!gathered_signatures.contains_key(&slot_id)` check (still empty for that slot) and have its weight added to `total_weight_approved` as well — with no corresponding subtraction from `total_weight_rejected`. The signer's weight is now counted on both sides simultaneously.

This vote-flip path is not theoretical: `stacks-signer/src/v0/signer.rs` explicitly documents that a signer "do[es] not change our votes on rejected blocks unless we receive a new block proposal for it and the reject reason allows us to reconsider" — i.e., reconsideration from reject to accept for the same block is a supported, reachable state transition. [3](#0-2) 

The consumer of this tally, `SignerCoordinator::get_block_status`, treats `total_weight_approved` and `total_weight_rejected` as if they partition the total signer weight (`self.total_weight`), using them to decide both "reject the block" (`total_weight_rejected + weight_threshold > total_weight`) and "accept the block" (`total_weight_approved >= weight_threshold`). [4](#0-3)  Once double-counting occurs, the sum `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, meaning a stale rejection (from a signer who has since switched to accept) inflates the rejection side, or a switched-to-accept signer's weight artificially pads the acceptance side beyond what distinct, currently-rejecting signers actually contributed.

### Impact Explanation
This is a liveness wedge / miscounted-response issue as defined in-scope: the block-status tally (approve vs reject) is the equality the coordinator relies on to decide whether a block has enough distinct signer weight to be broadcast, or enough distinct rejecting weight to be aborted. Double counting a single signer's weight on both sides means:
- The coordinator can conclude "blocking minority reached" (`total_weight_rejected + weight_threshold > total_weight`) using a stale rejection weight from a signer who has already switched to accepting, causing the miner to erroneously abort/exclude a block that in reality has (or would have) sufficient real signer weight — a liveness wedge on block production for that tenure.
- Conversely, a signer's weight lingering in `total_weight_approved` from an earlier acceptance (this direction is symmetric and not fixed either, since `gathered_signatures` is never cleared on reject) can also distort the observed approve/reject balance used for downstream decisions like rejection-timeout stepping and excluded-txid logic (`blocking_minority` computation at lines 521-535). [5](#0-4) 

This does not directly forge a Critical "signing an invalid/non-canonical block" outcome by itself, but it is exactly the reachable analog of "a rejection recounted as an acceptance" called out as a valid Critical class in the rules, occurring purely through a single signer's legitimate vote-flip (no majority collusion required, only one signer plus the miner's own listener state).

### Likelihood Explanation
This requires only a single signer (out of the full signer set) to send a `Rejected` message followed later by an `Accepted` message for the same `signer_signature_hash` — a transition the signer implementation explicitly supports under the documented reconsideration rules. No majority, no other signer's key, and no auth token are needed; the miner's own `StackerDBListener` state machine mismatches the two guards purely due to how it processes ordinary, protocol-compliant StackerDB traffic.

### Recommendation
Use a single shared dedup mechanism per (block, slot_id, vote-kind) that also handles vote transitions correctly: when a slot moves from Rejected to Accepted (or vice versa), subtract the previously counted weight from the old bucket before adding it to the new one, rather than gating the accept-path increment on `gathered_signatures` while the reject-path increment is gated on the shared `responded_signers` set. Concretely, track each slot's last-known vote kind and weight, and only ever have that slot's weight present in exactly one of `total_weight_approved` / `total_weight_rejected` at a time.

### Proof of Concept
1. Signer S (slot_id = k, weight = w) sends `BlockResponse::Rejected` for block hash H.
   - `responded_signers.insert(k)` succeeds → `total_weight_rejected += w`. [2](#0-1) 
2. Later (a supported reconsideration path per `stacks-signer/src/v0/signer.rs`), signer S sends `BlockResponse::Accepted` for the same H.
   - `gathered_signatures.contains_key(&k)` is `false` (only ever populated by the Accepted branch), so the guard passes → `total_weight_approved += w`. [1](#0-0) 
3. Now `total_weight_rejected` still includes S's weight `w` from step 1 (never decremented), and `total_weight_approved` also includes `w`. `total_weight_approved + total_weight_rejected` exceeds the true distinct signer weight and can exceed `self.total_weight` if other signers have also voted, causing `SignerCoordinator::get_block_status` to make an accept/reject decision based on an inflated/incoherent tally. [4](#0-3)
