### Title
Bash-shell file-secret `Variable.Key` is embedded via Go's `%q` (not shell-safe) into a double-quoted path, enabling command-substitution injection - (File: `shells/bash.go`)

### Summary
`BashWriter.Variable` (used to materialize file-type secrets/variables in bash scripts) builds the temp-file path from the raw, unescaped secret key and formats it with Go's `%q` verb, which produces a Go/bash *double*-quoted string. Because Go's `%q` does not treat `$` or backtick as characters requiring escaping, a key containing `$(...)` or backticks survives into a bash double-quoted context, where bash performs command substitution, letting the value execute as a command inside the generated job script.

### Finding Description
`defaultSecretsResolver.handleSecret` (`common/secrets.go:116-146`) builds `spec.Variable{Key: variableKey, ...}` directly from the map key of `spec.Secrets`, which originates from the job payload's `secrets:` configuration (author-controlled in `.gitlab-ci.yml`), with no charset/identifier validation performed anywhere in the runner's own code path (only `common/labels.go` enforces such a regex, and that is for runner *labels*, not for secrets/variable keys) [1](#0-0) .

When this `Variable` reaches the bash shell writer, `BashWriter.Variable` does:
```
variableFile := b.TmpFile(variable.Key)
b.Linef("mkdir -p %q", helpers.ToSlash(b.TemporaryPath))
b.Linef("printf '%%s' %s > %q", b.escape(variable.Value), variableFile)
b.Linef("export %s=%q", b.escape(variable.Key), variableFile)
``` [2](#0-1) 

`TmpFile` (`path.Join(b.TemporaryPath, name)` then `cleanPath`) does not sanitize the key content at all [3](#0-2) ; the raw key characters (including `$`, backticks, parentheses) pass straight through into `variableFile`.

Both the `printf ... > %q` line and the `export ... =%q` line then format `variableFile` with Go's `fmt` `%q` verb. Go's `%q` produces a double-quoted string literal, escaping non-printable characters, backslashes, and the quote character itself — but `$` and `` ` `` are ordinary printable ASCII and are emitted unescaped. In the resulting bash script this becomes a bash **double**-quoted string (`"..."`), and bash performs command/parameter substitution inside double quotes regardless of context (including redirection targets and `export` right-hand sides). So a key such as `` X`touch /tmp/pwned` `` or `X$(id>id.txt)` turns the generated line into e.g.:
```
printf '%s' $'the secret' > "$PWD/foo/bar/X$(touch /tmp/pwned)"
```
which bash executes, running `touch /tmp/pwned` as a side effect of command substitution before `printf` runs.

Note that `variable.Key` is *also* used in `export %s=%q` at line 234 with the *value* (`variableFile`) subject to the same unsafe `%q`, i.e. two independent injection sites share the same root cause. The `b.escape()` function (ANSI-C `$'...'` quoting) is bash-safe and is correctly used for `variable.Value` and for `variable.Key` in the `export` variable name — but it is not used for the `variableFile` path built from the key.

No existing check intercepts this: there is no key-name sanitization in `defaultSecretsResolver.handleSecret`, no regex enforcement analogous to `labelKeyAllowedRx` for secret/variable names, and `TmpFile`/`cleanPath` only perform path-joining and absolute-path normalization, not shell-safety sanitization.

### Impact Explanation
A pipeline author who can define a `secrets:` entry (or, more broadly, an attacker-controlled `spec.Variable` with `File: true`) with an injection-crafted key can achieve arbitrary command execution inside the job's bash-generated build script — i.e., executor-container command execution independent of, and prior to, whatever legitimate script commands were intended to run. This matches the scoped impact ("executor breakout / arbitrary command execution in job container") for the bash shell case.

### Likelihood Explanation
Requires: (1) bash shell executor, (2) a file-type secret/variable whose key contains `$(...)`/backtick sequences, and (3) no upstream (e.g., GitLab Rails) validation rejecting such key names before the job payload reaches the runner. Within the runner's own codebase there is no defense-in-depth check preventing this, so the bug is real from the runner's perspective; whether it is exploitable end-to-end also depends on GitLab Rails-side secret-name validation, which is outside this repository and could not be verified here — this is a genuine unknown that limits certainty about real-world reachability via the GitLab.com/self-managed UI, but does not change the fact that the runner's shell-generation code is not shell-injection-safe for such keys.

### Recommendation
In `shells/bash.go`, stop using Go's `%q` for any value that will end up inside a bash double-quoted context. For the `variableFile` path in `BashWriter.Variable` (and anywhere else `TmpFile`/paths derived from user-controlled keys are interpolated), use the existing bash-safe ANSI-C quoting helper (`b.escape`) instead of `%q`, e.g.:
```go
b.Linef("printf '%%s' %s > %s", b.escape(variable.Value), b.escape(variableFile))
b.Linef("export %s=%s", b.escape(variable.Key), b.escape(variableFile))
```
Additionally, add defense-in-depth validation in `defaultSecretsResolver.handleSecret` (or in `spec.Variable` construction) rejecting/sanitizing keys that are not valid shell/environment identifiers (e.g. `^[A-Za-z_][A-Za-z0-9_]*$`), analogous to `common/labels.go`'s `labelKeyAllowedRx`.

### Proof of Concept
Go unit test extending `Test_BashWriter_Variable` in `shells/bash_test.go`:
```go
func Test_BashWriter_Variable_KeyInjection(t *testing.T) {
    v := spec.Variable{Key: "X$(touch /tmp/pwned)", Value: "secret", File: true}
    w := BashWriter{TemporaryPath: "/foo/bar"}
    w.Variable(v)
    script := w.String()

    // Oracle: actually run the generated line(s) via /bin/bash -c and confirm
    // that the side-effect command executed (e.g. check /tmp/pwned was created),
    // rather than being treated as a literal filename character sequence.
    cmd := exec.Command("bash", "-c", script)
    _ = cmd.Run()
    _, err := os.Stat("/tmp/pwned")
    assert.NoError(t, err, "expected command substitution in secret key to execute touch")
}
```
Expected assertion: `/tmp/pwned` exists after running the generated script, proving that the `$(...)` sequence in `variable.Key` was interpreted by bash as command substitution rather than a literal filename fragment — confirming injection via the `%q`-formatted `variableFile` path.

func (r *defaultSecretsResolver) handleSecret(variableKey string, secret spec.Secret) (*spec.Variable, error) {
	sr, err := r.secretResolverRegistry.GetFor(secret)
	if err != nil {
		r.logger.Warningln(fmt.Sprintf("Not resolved: %v", err))
		return nil, nil
	}

	r.logger.Println(fmt.Sprintf("Using %q secret resolver...", sr.Name()))

	value, err := sr.Resolve()
	if errors.Is(err, ErrSecretNotFound) {
		if !r.featureFlagOn(featureflags.EnableSecretResolvingFailsIfMissing) {
			err = nil
		} else {
			err = fmt.Errorf("%w: %v", err, variableKey)
		}

		return nil, err
	}

	variable := &spec.Variable{
		Key:    variableKey,
		Value:  value,
		File:   secret.IsFile(),
		Masked: true,
		Raw:    true,
	}
