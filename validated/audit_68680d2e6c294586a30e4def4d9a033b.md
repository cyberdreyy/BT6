### Title
`VestingSchedule::assert_valid()` is never invoked, allowing a malformed schedule to permanently brick `get_unvested_amount` via division-by-zero - (File: `lockup/src/lib.rs`, `lockup/src/getters.rs`, `lockup-factory/src/lib.rs`)

### Summary
`VestingSchedule::assert_valid()` exists in both `lockup/src/types.rs` and `lockup-factory/src/types.rs` but is never called from `LockupContract::new()`, `LockupFactory::create()`, or anywhere else in the codebase. This allows a `VestingScheduleOrHash::VestingSchedule` with `start_timestamp == end_timestamp` (or `cliff_timestamp < start_timestamp`) to be deployed, causing `get_unvested_amount` to divide by zero (`total_time = end_timestamp - start_timestamp == 0`) once `block_timestamp` falls into the `[cliff_timestamp, end_timestamp)` window.

### Finding Description
The binding that should hold is: **for every lockup deployed by the factory, `vesting_schedule.assert_valid()` was invoked such that `start_timestamp < end_timestamp` always holds** — i.e. `deployed_schedule.start_timestamp < deployed_schedule.end_timestamp` must equal `true` for every schedule the factory accepts.

Tracing the code:
- `LockupFactory::create()` in [1](#0-0)  accepts `vesting_schedule: Option<VestingScheduleOrHash>` from any caller with no restriction that `predecessor_account_id == owner_account_id`, and forwards it verbatim to the deployed lockup's `new()` via `LockupArgs`, without ever calling `assert_valid()`.
- `LockupContract::new()` in [2](#0-1)  matches on `vesting_schedule` and for the `VestingScheduleOrHash::VestingSchedule(vs)` branch stores `VestingInformation::VestingSchedule(vs)` directly — `vs.assert_valid()` is never called. It is also not called for the `VestingHash` branch (validation there is deferred to termination time via hash-reveal, but that path is equally uncovered).
- `VestingSchedule::assert_valid()` is defined at [3](#0-2)  (and identically in `lockup-factory/src/types.rs`), but a repo-wide search shows no call site outside its own definition in either file.
- `get_unvested_amount` in [4](#0-3)  computes `total_time = U256::from(vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0)` and then `U256::from(lockup_amount) * time_left / total_time` whenever `cliff_timestamp <= block_timestamp < end_timestamp`. If `start_timestamp == end_timestamp` (with `cliff_timestamp < end_timestamp`, itself unchecked since `assert_valid` never runs), this branch is reachable and `total_time == 0`, causing a division-by-zero panic in `U256`.
- `get_unvested_amount` is called internally by `get_locked_amount` ( [5](#0-4) ) which is in turn called by `get_owners_balance`/`get_liquid_owners_balance`, and also by `terminate_vesting` ( [6](#0-5) ) — so even the foundation's termination path, the only mechanism that could otherwise clear a bad vesting state, also panics and cannot fix it.

Existing guards do not prevent this: `is_promise_success()` in `on_lockup_create` only rolls back if `new()` itself panics at deploy time; since `new()` never calls `assert_valid()`, it succeeds and the malformed schedule is durably committed to state. No other assertion (`assert_owner`, `assert_self`, etc.) touches vesting-schedule validity.

### Impact Explanation
Once deployed with `start_timestamp == end_timestamp`, every subsequent call to `get_unvested_amount`, `get_locked_amount`, `get_owners_balance`, `get_liquid_owners_balance` for `block_timestamp` in `[cliff_timestamp, end_timestamp)` panics. `terminate_vesting` — the only path that could otherwise resolve the vesting into a `Terminating`/`None` state — also calls `get_unvested_amount` and panics identically, so there is no recovery method reachable in-contract. The owner's balance becomes permanently unreadable/unspendable for that time window (and since `start_timestamp==end_timestamp` collapses the window boundary, this is essentially the entire pre-`end_timestamp` life of the contract), freezing whatever NEAR is held (and, if a staking pool is later selected, any staking rewards owed to this account) with no way to clear it. Because the factory's `create()` does not restrict `owner_account_id` to the caller, an unprivileged attacker can target this at a third party by choosing `owner_account_id = victim` and funding the lockup themselves, which would qualify as Critical (a third party's funds frozen with no recovery). Absent third-party targeting, this is self-inflicted (attacker griefs only their own funds), matching the High impact bucket ("funds frozen ... recoverable" does not strictly apply here since it's permanent, but per the question's own scoring guidance it is capped at High when self-targeted).

### Likelihood Explanation
Trivial and cheap: the attacker only needs `MIN_ATTACHED_BALANCE` (per `lockup-factory/src/lib.rs::get_min_attached_balance`) and a single `create()` call with `vesting_schedule = Some(VestingScheduleOrHash::VestingSchedule(VestingSchedule { start_timestamp: T, cliff_timestamp: T-1 (or T), end_timestamp: T }))`. No special privileges, no foundation involvement, no timing dependency beyond waiting for `block_timestamp >= cliff_timestamp`. Fully repeatable against any number of lockup deployments.

### Recommendation
Call `vesting_schedule.assert_valid()` inside `LockupContract::new()` for the `VestingScheduleOrHash::VestingSchedule(vs)` branch before storing `VestingInformation::VestingSchedule(vs)`, and additionally call the equivalent check in `lockup-factory`'s `create()` before dispatching the `Promise` (so bad schedules are rejected as early as possible, minimizing wasted attached deposit/gas). For the `VestingHash` branch, since the raw schedule isn't known until termination time, ensure `assert_vesting`/`terminate_vesting` calls `assert_valid()` on the revealed schedule before using it in `get_unvested_amount`.

### Proof of Concept
```rust
// lockup/src/lib.rs tests module (or a new #[cfg(test)] test)
#[test]
#[should_panic] // division by zero in U256
fn test_zero_duration_vesting_schedule_bricks_balance() {
    let mut context = basic_context();
    testing_env!(context.clone());

    let bad_schedule = VestingSchedule {
        start_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into(),
        cliff_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into(),
        end_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into(), // start == end
    };

    // Confirm assert_valid is not invoked: new() succeeds despite invalid schedule.
    let contract = LockupContract::new(
        account_owner(),
        0.into(),
        None,
        TransfersInformation::TransfersEnabled {
            transfers_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into(),
        },
        Some(VestingScheduleOrHash::VestingSchedule(bad_schedule.clone())),
        None,
        AccountId::from("whitelist"),
        Some(account_foundation()),
    );
    // new() did NOT panic -> assert_valid() was skipped (binding broken).

    // Move block_timestamp into [cliff_timestamp, end_timestamp) window.
    // Since start==cliff==end, block_timestamp == end_timestamp hits the
    // ">= end_timestamp" branch (returns 0) -- so instead pick cliff < end
    // to force the vulnerable branch:
    let bad_schedule2 = VestingSchedule {
        start_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into(),
        cliff_timestamp: to_ts(GENESIS_TIME_IN_DAYS - 1).into(), // cliff < start == end
        end_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into(),
    };
    let contract2 = LockupContract::new(
        account_owner(), 0.into(), None,
        TransfersInformation::TransfersEnabled {
            transfers_timestamp: to_ts(GENESIS_TIME_IN_DAYS - 10).into(),
        },
        Some(VestingScheduleOrHash::VestingSchedule(bad_schedule2.clone())),
        None, AccountId::from("whitelist"), Some(account_foundation()),
    );

    context.is_view = true;
    context.block_timestamp = to_ts(GENESIS_TIME_IN_DAYS - 1); // in [cliff, end)
    testing_env!(context.clone());

    // This panics with division-by-zero (U256 total_time == 0).
    let _ = contract2.get_unvested_amount(bad_schedule2.clone());

    // Demonstrate the freeze: get_owners_balance / get_liquid_owners_balance
    // also panic transitively, for any subsequent call at this timestamp.
    let _ = contract2.get_owners_balance();
}
```
Run with `cargo test -p lockup test_zero_duration_vesting_schedule_bricks_balance -- --nocapture` (unit test, no mainnet); the panic confirms `new()` never calls `assert_valid()` and that `get_unvested_amount`/`get_owners_balance` become permanently unreadable for the chosen block-timestamp window.

    pub fn get_unvested_amount(&self, vesting_schedule: VestingSchedule) -> WrappedBalance {
        let block_timestamp = env::block_timestamp();
        let lockup_amount = self.lockup_information.lockup_amount;
        match &self.vesting_information {
            VestingInformation::Terminating(termination_information) => {
                termination_information.unvested_amount
            }
            VestingInformation::None => U128::from(0),
            _ => {
                if block_timestamp < vesting_schedule.cliff_timestamp.0 {
                    // Before the cliff, nothing is vested
                    lockup_amount.into()
                } else if block_timestamp >= vesting_schedule.end_timestamp.0 {
                    // After the end, everything is vested
                    0.into()
                } else {
                    // cannot overflow since block_timestamp < vesting_schedule.end_timestamp
                    let time_left = U256::from(vesting_schedule.end_timestamp.0 - block_timestamp);
                    // The total time is positive. Checked at the contract initialization.
                    let total_time = U256::from(
                        vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0,
                    );
                    let unvested_amount = U256::from(lockup_amount) * time_left / total_time;
                    // The unvested amount can't be larger than lockup_amount because the
                    // time_left is smaller than total_time.
                    unvested_amount.as_u128().into()
                }
            }
        }
