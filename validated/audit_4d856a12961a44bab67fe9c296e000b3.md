### Title
Loss-adjusted withdraw receipts escape their haircut because `collectWithdrawFunds` indexes `lossRecoveryPriceByEpoch` by an `epochNumber` already incremented inside `stopEpoch` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records a realized `stopEpochWithDuration` loss under `lossRecoveryPriceByEpoch[epochNumber]`, but `deposit()` increments `epochNumber` when called while `isEpochRunning()` is still true — i.e. during the same `stopEpoch` call that funds receipts. Receipts were registered under the pre-increment epoch (`lastWithdrawRequest[_user]`), so the haircut price lands one epoch too high and `_claimLossAdjustedWithdrawRequest` finds `lossRecoveryPriceByEpoch[lossEpoch] == 0`, letting claims fall through to the full-par funded path. [1](#0-0) [2](#0-1) 

### Finding Description
The external report concerns an uninitialized type value used as an array index. The analog here is `epochNumber` used as the index for the per-epoch haircut map:

- `requestWithdraw` records receipts per user per epoch: `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `lastWithdrawRequest[_user] = currentEpoch`, where `currentEpoch = epochNumber` (epoch N). [3](#0-2) 
- During `stopEpoch`, the CDO pushes repaid borrower funds via `deposit()`. Because `isEpochRunning()` is still true at that point, `deposit()` executes `epochNumber += 1` (now N+1). [4](#0-3) 
- If the borrower underfunds pending receipts, `collectWithdrawFunds(_amount)` with `_amount < pendingBasis` stores `lossRecoveryPriceByEpoch[epochNumber]` — i.e. at index N+1, not N. [5](#0-4) 
- `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = 0 and returns early. [6](#0-5) 
- Execution continues into `_claimFundedWithdrawRequest`, which burns the full receipt and calls `_transferFundedClaim(_user, amount)` at par, even though only `claimBasis * lossRecoveryPrice / 1e18` was actually funded. The withdrawal-wait gate (`epochNumber <= lastWithdrawRequest[_user]`) is already satisfied because `epochNumber` was bumped to N+1. [7](#0-6) 

The same index also poisons `requestWithdraw`'s griefing guard at lines 261-271: any user whose `lastWithdrawRequest` or APR0 `principalEpoch` equals the polluted index N+1 (i.e. requests made in epoch N+1, before its own stop) sees `lossRecoveryPrice != 0` together with a non-zero receipt and is permanently reverted, blocking even fully-funded claims — a second, independent manifestation.

### Impact Explanation
Two compounding impacts from the wrong index:

1. **Theft / insolvency**: receipt holders of epoch N claim 100% of `claimBasis` while only `lossRecoveryPrice` of it was transferred in via `collectWithdrawFunds`. The first claimants drain underlying belonging to other receipt holders (or `defaultRecoveryReserve` guard at lines 899-905 reverts for later claimants). Loss ≈ `pendingBasis * (1 - lossRecoveryPrice)`, directly quantified by the intended haircut.
2. **Permanent freeze**: receipts created in epoch N+1 (after the misindexed write) hit `lossRecoveryPriceByEpoch[N+1] != 0` but `_claimLossAdjustedWithdrawRequest` clears `withdrawsRequestsByEpoch[N+1]` and computes `claimBasis * price` — mixing a haircut intended for epoch N with N+1 receipts, so N+1 claimants are either underpaid by the stale price or revert in `requestWithdraw`'s guard forever.

### Likelihood Explanation
Requires only an unprivileged lender who made a `requestWithdraw` in the affected epoch, and an honest `stopEpochWithDuration(_lossAmount > 0)` call by the manager — a normal, sanctioned operation, not attacker privilege. The misindexing is deterministic whenever `collectWithdrawFunds` is invoked after the `deposit()` that bumps `epochNumber` inside the same `stopEpoch` transaction (the exact ordering depends on `IdleCDOEpochVariant.stopEpoch` internals; the vault's own comment confirms `deposit` runs "on stopEpoch (before setting the var to false)", so if funding/collection occurs after that deposit the index is already stale — this ordering should be verified in the PoC). No guard prevents it: `NotAllowed` checks, `defaultRecoveryInitialized`, and `_transferFundedClaim`'s reserve guard do not distinguish a missing haircut from a fully-funded epoch.

### Recommendation
Snapshot the request epoch before the bump and use it consistently:

- In `collectWithdrawFunds`, write `lossRecoveryPriceByEpoch[epochNumber - 1]` (or better, pass the receipt epoch explicitly from the CDO) so the haircut is stored under the epoch in which the receipts were created.
- Alternatively, increment `epochNumber` only after all per-epoch writes for the closing epoch (move the bump out of `deposit()` into an explicit `stopEpoch`-finalization hook).
- Add an invariant test: after `stopEpochWithDuration` with a loss, `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` for every pending receipt.

### Proof of Concept
Foundry fork test (scaffold; wire deployment addresses per `test/` fixtures):

```solidity
// test/foundry/LossEpochIndex.t.sol
function test_lossHaircutEscapesViaEpochIndex() public {
    // Epoch N is running; lender already deposited via CDO AA tranche.
    vm.prank(address(cdo));
    vault.requestWithdraw(1000e6, lender, 1000e6);       // receipt recorded at epoch N
    assertEq(vault.lastWithdrawRequest(lender), vault.epochNumber());

    uint256 epochAtRequest = vault.epochNumber();

    // Borrower repays principal minus loss; cdo.stopEpochWithDuration(loss) internally:
    //   1) vault.deposit(repaid)      -> epochNumber++  (isEpochRunning still true)
    //   2) vault.collectWithdrawFunds(funded) where funded < pendingWithdraws
    vm.startPrank(borrower);
    underlying.approve(address(cdo), type(uint256).max);
    vm.stopPrank();
    vm.prank(manager);
    cdo.stopEpochWithDuration(duration, lossAmount);      // loss > 0, partial funding

    // Bug: haircut stored under epoch N+1, not N
    assertEq(vault.lossRecoveryPriceByEpoch(epochAtRequest), 0);
    assertGt(vault.lossRecoveryPriceByEpoch(epochAtRequest + 1), 0);

    // Lender claims at FULL par even though only funded portion exists
    uint256 balBefore = underlying.balanceOf(lender);
    vm.prank(lender);
    cdo.claimWithdrawRequest();                            // routes to _claimFundedWithdrawRequest
    assertEq(underlying.balanceOf(lender) - balBefore, 1000e6); // paid par, haircut skipped

    // A second receipt holder / reserve claimant now reverts in _transferFundedClaim
    // (balance < amount) or drains defaultRecoveryReserve-adjacent funds -> insolvency.
}
```

Note: the PoC's success hinges on `IdleCDOEpochVariant.stopEpoch` calling `collectWithdrawFunds` after the `deposit()` that increments `epochNumber`; that ordering was not fully readable within this session's index and should be confirmed in `contracts/IdleCDOEpochVariant.sol` (the 8 `epochNumber`-adjacent matches located there) before finalizing the finding. If collection precedes the increment, the write lands on the correct epoch and this vector is invalid.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
