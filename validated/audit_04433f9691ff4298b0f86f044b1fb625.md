### Title
`/debug/vars` (expvar) is reachable by any authenticated session role, including `view`, with no admin/edit role gate - ([File: core/web/router.go])

### Summary
`debugRoutes` in `core/web/router.go` registers `GET /debug/vars` protected only by `auth.Authenticate(..., auth.AuthenticateBySession)`, with no role wrapper (`RequiresAdminRole`/`RequiresEditRole`), unlike almost every other sensitive route in `v2Routes` (keys export/import, config, transfers, etc.) which are explicitly wrapped with `auth.RequiresAdminRole` or `auth.RequiresEditRole`. This allows any valid session, even a `view`-role user, to retrieve `expvar.Handler()` output.

### Finding Description
`NewRouter` mounts `debugRoutes(app, api)` at `core/web/router.go:87`, which defines:
```go
func debugRoutes(app chainlink.Application, r *gin.RouterGroup) {
	group := r.Group("/debug", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	group.GET("/vars", expvar.Handler())
}
``` [1](#0-0) 

`auth.Authenticate` with only `AuthenticateBySession` authenticates that a valid session cookie exists and sets `SessionUserKey` on the context, but performs no role check — it will succeed for any `clsessions.UserRoleView`, `UserRoleRun`, `UserRoleEdit`, or `UserRoleAdmin` user. [2](#0-1) 

Compare this to the rest of the router: sensitive/introspective and mutating endpoints under `v2Routes` are consistently wrapped in `auth.RequiresAdminRole` (e.g. key export/import, `/users`) or `auth.RequiresEditRole`/`auth.RequiresRunRole` for less-sensitive mutating actions [3](#0-2) . `debugRoutes` has no equivalent role wrapper at all, so a `view`-role user (the lowest privilege authenticated role, normally restricted to read-only, non-sensitive endpoints) can call `GET /debug/vars` and receive Go's built-in `expvar.Handler()` output, which by default includes `cmdline` and `memstats` (GC stats, heap sizes, goroutine counts) and any additional vars any package in the running process has published via `expvar.Publish`/`NewString`/`NewMap`/`NewInt`. This is process-level introspection data that is not filtered or redacted by any presenter (unlike, e.g., API key/secret responses elsewhere in the codebase that are explicitly redacted).

### Impact Explanation
This is an authorization-exactness gap: a low-privileged, non-admin session (down to `view` role) can access an introspection endpoint intended to require elevated privilege, matching the described invariant violation. The concrete impact is disclosure of internal process telemetry (memory/runtime stats, and any expvar-registered internal counters/paths) to users who should not have access to internal operational details — an information-disclosure class finding under Chainlink's bounty program (not fund loss or credential theft, but unauthorized visibility into internal node state). It does not, by itself, expose private keys or secrets (no code path publishes those specific values into `expvar` in this codebase per available context), so the impact is bounded to metadata/telemetry disclosure rather than direct key/secret compromise.

### Likelihood Explanation
High feasibility and trivially repeatable: precondition is merely possession of any valid authenticated session, including the lowest `view` role, which is routinely granted to many operational/monitoring users. No additional exploitation steps, timing, or race conditions are required — a single `GET /debug/vars` request with a valid session cookie succeeds.

### Recommendation
Wrap the `/debug/vars` route with an explicit role gate consistent with the rest of the router's sensitive/introspective endpoints, e.g.:
```go
group.GET("/vars", auth.RequiresAdminRole(func(c *gin.Context) { expvar.Handler().ServeHTTP(c.Writer, c.Request) }))
```
This aligns `/debug/vars` with the same `RequiresAdminRole` pattern already used for key export/import and other privileged introspection/config endpoints in `v2Routes`.

### Proof of Concept
Handler-level integration test plan (mirroring existing router tests, e.g. `core/web/router_test.go` style):
1. Boot the app/router with a fake `AuthenticationProvider` and create two sessions: one for a user with `Role: clsessions.UserRoleView`, another for `UserRoleAdmin`.
2. Perform `GET /debug/vars` using the `view`-role session cookie.
3. Assert response status is `200 OK` and body contains standard expvar keys (`"cmdline"`, `"memstats"`), proving the view-role session reached `expvar.Handler()` without a role check.
4. Add assertion (currently failing, demonstrating the gap) that a `view` role should instead receive `401`/`403`, matching the behavior of `RequiresAdminRole`-protected routes (e.g., re-use the existing test pattern from `authv2.GET("/users", auth.RequiresAdminRole(uc.Index))` which correctly returns `403 Forbidden` for non-admin sessions) — confirming `/debug/vars` is the outlier lacking this gate.

// Authenticate is middleware which authenticates the request by attempting to
// authenticate using all the provided methods.
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
