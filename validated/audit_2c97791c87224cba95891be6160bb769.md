## Finding

### Title
Missing fee-vs-amount validation in `createDstEscrow` lets an unprivileged caller set `EscrowDst` immutables that underflow on withdrawal, permanently freezing the maker's destination funds - (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw` computes `immutables.amount - integratorFeeAmount - protocolFeeAmount` with no underflow guard, the exact same missing-precision/no-bound-check root cause described in the external report about `PorticoFinish::payOut`. On the source side this exact class of bug is explicitly guarded against (`_postInteraction` reverts if `integratorFeeAmount + protocolFeeAmount >= takingAmount`), but the equivalent check is missing on the destination side, where `createDstEscrow` accepts the entire `Immutables` struct — including the `parameters` blob encoding `protocolFeeAmount`/`integratorFeeAmount` — directly from `msg.sender` with zero validation against `amount`.

### Finding Description
`createDstEscrow` lets any caller (the taker/resolver funding the destination escrow) supply an arbitrary `dstImmutables` struct, which is hashed and used as the CREATE2 salt with no relationship enforced to the corresponding source-chain order fee parameters: [1](#0-0) 

Compare this to `_postInteraction`, which explicitly protects against a bad fee configuration before it can ever reach an escrow: [2](#0-1) 

No such check exists for the destination path. When the maker later reveals the secret to withdraw, `EscrowDst._withdraw` subtracts the two attacker-controlled fee amounts (read straight out of the immutables `parameters` supplied at `createDstEscrow` time) from `immutables.amount` without any bound check: [3](#0-2) 

If `integratorFeeAmount + protocolFeeAmount > immutables.amount`, line 92 underflows and reverts under Solidity 0.8 checked arithmetic. Because `onlyValidImmutables` ties the call to the exact immutables hash used at deployment (the CREATE2 salt), the caller cannot supply different, corrected fee values to work around this at withdrawal time — every `withdraw()`/`publicWithdraw()` call for that escrow will revert forever.

### Impact Explanation
This is not the self-inflicted scenario described in the Wormhole report (there, only the affected user could set their own fee). Here, the taker/resolver — a distinct, unprivileged party from the maker — sets these fee values when calling the public `createDstEscrow` function while funding the escrow with the maker's expected destination tokens. If those fee fields are set (accidentally or maliciously) such that they sum to more than `amount`, the maker who legitimately reveals the secret (thereby also enabling the taker to withdraw the source-chain tokens) can never withdraw the destination tokens: `withdraw`/`publicWithdraw` permanently revert. The only path to resolve the locked destination-side balance is `cancel()` after the cancellation timelock, which returns the entire `amount` back to the taker — not the maker. This is a genuine third-party freezing/loss of the maker's expected proceeds, matching the bounty's "temporary freezing of funds during the live swap lifecycle" / potential "theft of ... unclaimed fee-like value" impact class, entered purely through the permissionless `createDstEscrow` entry point.

### Likelihood Explanation
`createDstEscrow` is a public, permissionless function reachable by any address that funds the escrow; no signature, whitelist, or cross-chain verification ties `dstImmutables.parameters` to the actual order's agreed fee terms. A resolver only needs to pass fee-amount parameters whose sum exceeds `amount` (e.g., by error in off-chain fee computation, decimal mismatch between the order's basis-point fee config and the raw destination-token amount, or intentionally) to trigger the always-revert underflow. This requires no privileged role and no cooperation from the maker.

### Recommendation
Add the same guard used in `_postInteraction` to `createDstEscrow`/`_withdraw`:
- In `createDstEscrow`, revert if `integratorFeeAmount + protocolFeeAmount >= immutables.amount` (mirroring `InvalidFeeAmounts` in `_postInteraction`), computed from the decoded `parameters`.
- Defensively, in `EscrowDst._withdraw`, cap/clamp the fee deductions or explicitly check for underflow before subtracting, rather than relying on immutables set at a completely separate, unchecked entry point.

### Proof of Concept
1. Taker calls `createDstEscrow(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.amount = 100` and `dstImmutables.parameters` encoding `protocolFeeAmount = 60`, `integratorFeeAmount = 50` (sum 110 > 100). No check in `createDstEscrow` rejects this (contracts/BaseEscrowFactory.sol:165-185).
2. Escrow is deployed and funded (token transferred in, safety deposit in native token) per the attacker-chosen immutables.
3. Maker learns the secret via source-chain flow and calls `EscrowDst.withdraw(secret, immutables)` once the withdrawal window opens.
4. `_withdraw` transfers `integratorFeeAmount` and `protocolFeeAmount` out first, then executes `immutables.amount - integratorFeeAmount - protocolFeeAmount` = `100 - 60 - 50`, which underflows and reverts (contracts/EscrowDst.sol:92). Every subsequent `withdraw`/`publicWithdraw` call with the same immutables reverts identically.
5. The maker's destination-chain tokens can never be withdrawn by the maker; after the cancellation timelock, only `cancel()` succeeds, returning the full `amount` to the taker.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
