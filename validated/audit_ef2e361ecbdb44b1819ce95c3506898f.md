Based on the code I was able to examine, I found strong supporting evidence but could not fully trace the router registration and middleware chain for `PipelineRunsController.Create` before running out of iterations to confirm which auth methods are chained to that route (i.e., whether `AuthenticateExternalInitiator` is even included in the middleware for `/v2/jobs/:ID/runs`). I'll present findings based on what's confirmed and flag the remaining uncertainty.

### Title
Missing job/subscription binding check in external-initiator authenticated run-trigger route allows cross-job run triggering - ([File: core/web/pipeline_runs_controller.go], related [File: core/sessions/oidcauth/oidc.go])

### Summary
`FindExternalInitiator` in `core/sessions/oidcauth/oidc.go` (and the equivalent in `core/sessions/ldapauth/ldap.go` / `core/sessions/localauth/orm.go`) authenticates a credential purely by `access_key` lookup, with zero binding to a specific job/subscription ID. Downstream, `AuthenticateExternalInitiator` in `core/web/auth/auth.go` sets the exact same `SessionUserKey` context value for external-initiator credentials as it does for real logged-in users, and `PipelineRunsController.Create` in `core/web/pipeline_runs_controller.go` only checks `isUser` presence (not identity or scope) before calling `prc.App.RunJobV2(ctx, jobID, nil)` for an arbitrary attacker-supplied job ID.

### Finding Description
`FindExternalInitiator` performs: [1](#0-0) 
It looks up the initiator solely by `eia.AccessKey` with no job/bridge identifier supplied in or checked against the request.

In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` calls this lookup, verifies the secret, and then sets `SessionUserKey` to a synthetic `Run`-role user identical in shape to what a normal session/token-authenticated user would have: [2](#0-1) 

`PipelineRunsController.Create`, which triggers job runs by numeric job ID, gates on `auth.GetAuthenticatedUser(c)` — which only checks for the presence of `SessionUserKey` in the gin context, not the *type* of credential (real user vs. external initiator) nor any relationship between the credential and the target job: [3](#0-2) 

The inline comment "only users are allowed to run jobs using int IDs - EIs not allowed" is aspirational but not enforced by the code, since `isUser` is `true` for any request where `SessionUserKey` was set — including by `AuthenticateExternalInitiator`. There is no code path in `FindExternalInitiator`, `AuthenticateExternalInitiator`, or `PipelineRunsController.Create` that cross-checks the external initiator's registered job/bridge against the requested job ID (`idStr`/`ID` param).

### Impact Explanation
If confirmed reachable (see caveat below), this would allow an external-initiator credential holder registered for job A to trigger runs of job B (or any job on the node, since the only check is a numeric parseable ID), which is an unauthorized-action-on-another-user's-job class impact matching Chainlink's "Unauthorized job run" bounty category.

### Likelihood Explanation
Requires possession of a legitimately-issued external initiator access key/secret pair (any restricted, non-admin credential holder qualifies as attacker per the threat model) and knowledge/guessing of another job's integer ID (job IDs are sequential integers, making enumeration trivial). No further privilege is needed. However, I could not verify from the available context whether the route wired to `PipelineRunsController.Create` (`/v2/jobs/:ID/runs`) actually includes `AuthenticateExternalInitiator` in its middleware chain in `core/web/router.go` — I was unable to retrieve that route registration before running out of tool budget. If that route is only reachable via `AuthenticateBySession`/`AuthenticateByToken` (not the EI method), then external initiators cannot reach this handler at all, and the vulnerability would not be exploitable through this specific path.

### Recommendation
- In `PipelineRunsController.Create`, explicitly distinguish external-initiator-authenticated requests from real user sessions (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` and reject, matching the stated intent in the comment), rather than relying solely on `SessionUserKey` presence.
- If external initiators are intended to trigger specific jobs, `FindExternalInitiator`/`AuthenticateExternalInitiator` should bind the credential to the specific job/bridge it was registered against, and the run-trigger handler should verify the requested job ID matches that binding before calling `RunJobV2`.

### Proof of Concept
1. Confirm route wiring in `core/web/router.go` for `/v2/jobs/:ID/runs` (POST) to determine which `authMethod`s are chained via `auth.Authenticate(...)`.
2. If `AuthenticateExternalInitiator` is included:
   - Register external initiator `EI-A` bound to job A via `external_initiators_controller.go`.
   - Create job B (any type, different from A) with a known integer ID.
   - Send `POST /v2/jobs/<jobB-ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI-A's credentials.
   - Assert: request either succeeds (confirming the bug) or is rejected with 401/422 (confirming a mitigating check exists elsewhere not found in this trace).
3. If `AuthenticateExternalInitiator` is NOT included in that route's middleware, this specific PoC does not apply, and the finding should be downgraded/invalidated pending confirmation of an alternate reachable route that does chain EI auth to `PipelineRunsController.Create` or an equivalent run-trigger handler.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
