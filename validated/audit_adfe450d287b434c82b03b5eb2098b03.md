Based on my investigation, I found a confirmed and documented gap that maps to the same bug class as the Gearbox report: an identity/eligibility check performed once at proposal time is not re-verified at the point the irrevocable action (signing) actually happens, and the identity in question can legitimately change in between purely from gossip/node state a single miner (or the passage of time) controls.

### Title
Stale Miner-Validity Re-Check at Pre-Commit Signing Allows a Signature Over a Block From a Miner Invalidated After Proposal - (File: stacks-signer/src/v0/signer.rs)

### Summary
`check_block_against_signer_db_state`, the only re-check run at validate-ok and again right before a signature is produced at the pre-commit threshold, is explicitly documented and coded as an incomplete check: it only re-verifies tenure/parent-confirmation ordering (`check_tenure_change_confirms_parent` / `check_latest_block_in_tenure`). It never re-runs the full `check_proposal` miner-identity checks (current-miner pubkey hash match, `SortitionMinerStatus`/`MinerState::ActiveMiner` validity) that gate a proposal on arrival.

### Finding Description
`check_proposal` (v1: `stacks-signer/src/chainstate/v1.rs:205-318`, v2: `stacks-signer/src/chainstate/v2.rs:111-198`) is the only place that verifies the proposing miner is still the currently valid one: it checks `miner_pkh` against the sortition/`ActiveMiner` state and (v1) `SortitionMinerStatus != Valid` / `InvalidatedAfterFirstBlock` transitions. [1](#0-0) [2](#0-1) 

This full check runs once, at `handle_block_proposal` time. But between then and the moment a signer actually signs — i.e. when the pre-commit weight crosses the 70% threshold in `handle_block_pre_commit` — the only re-validation performed is `check_block_against_signer_db_state`, which is explicitly documented as re-checking only tenure-confirmation ordering, not miner identity/status: [3](#0-2) 
This function's own doc comment states: *"WARNING: This is an incomplete check. Do NOT call this function PRIOR to check_proposal..."* — acknowledging it is not a substitute for `check_proposal`. [4](#0-3) 

The developer-authored flow documentation independently confirms this gap: "the v2 `check_proposal` wrapper checks miner pubkey hash, consensus hash, the pox bitvec, and tenure-extend rules before delegating here" is listed as one of the things that belong *only* to the proposal path and are **not** re-run at validate-ok or at signing. [5](#0-4) 

The miner-validity state this check would have needed is genuinely mutable and time-based, not requiring majority collusion — a single miner missing its `block_proposal_timeout` window causes the signer to unilaterally invalidate it (`SortitionMinerStatus::InvalidatedBeforeFirstBlock`, or `InvalidatedAfterFirstBlock` once a block was signed), and this is a routine, single-actor/local-clock event. [6](#0-5) [7](#0-6) 

Concretely: a miner proposes a valid block B while it is the active/valid miner; `check_proposal` passes and the block is submitted for node validation and stored as `Unprocessed`/pending. The signer set is slow to gossip pre-commits (gossip latency the miner does not need to control — it can simply delay its own network broadcast, an action fully within a "one slot + gossip" actor's power). During that window the `block_proposal_timeout` elapses and each signer's local `SortitionMinerStatus` for that tenure flips to `InvalidatedBeforeFirstBlock` (v1) or the v2 `MinerState` transitions away from `ActiveMiner` for that pubkey hash. Pre-commits nonetheless continue to accumulate (each signer's own earlier "willing to sign" pre-commit, from before the timeout, remains recorded and is never retracted — `handle_block_pre_commit` does not re-check current-miner validity, only tenure-confirmation ordering via `check_block_against_signer_db_state`). Once accumulated pre-commit weight crosses the 70% `compute_voting_weight_threshold`, `handle_block_pre_commit` re-runs only `check_block_against_signer_db_state` — which passes, since B still correctly confirms its tenure/parent — and proceeds straight to `SIGN: mark_locally_accepted`, producing a signature over a block from a miner the signer's own state machine currently considers invalid. [8](#0-7) [9](#0-8) 

This exactly mirrors the Gearbox pattern: an eligibility/identity check ("is this account/miner still valid to act on") is verified once at the start of a flow, the flow is then delayed by an adversary-controllable window, the identity legitimately changes underneath it, and the final irrevocable action (liquidation / block signature) is executed against the *stale* identity because the completion step re-checks only a narrower invariant (collateral math / tenure-confirmation ordering) rather than the full original eligibility check.

### Impact Explanation
This produces a **Critical** outcome per the given rubric: a signer signing a block from a miner it has independently determined is invalid produces a signature that other honest signers, using the same logic but slightly different local timing, may not agree is valid — i.e. a signature is placed on a block that violates the "signer's-own-declared-invalid-miner" invariant that `check_proposal`'s `InvalidMiner`/`NotLatestSortitionWinner`/`PubkeyHashMismatch` rejections exist to enforce. Because the flow only requires ordinary pre-commit gossip and a single miner delaying its own broadcast (well within "a one-slot miner plus gossip"), no majority collusion or another signer's key is needed to trigger the divergence between what `check_proposal` would reject and what `check_block_against_signer_db_state` lets through.

### Likelihood Explanation
The trigger conditions (network/gossip delay exceeding `block_proposal_timeout`, followed by the pre-commit threshold being reached from already-cast pre-commits) are ordinary operating conditions rather than an exotic attack, and the documentation itself flags this incomplete-check design as deliberate but incomplete, indicating the codebase authors are aware only tenure-confirmation is re-verified, not miner eligibility.

### Recommendation
Re-run (or fold into `check_block_against_signer_db_state`) the miner-identity/status checks from `check_proposal` — `PubkeyHashMismatch`, `InvalidMiner`, `NotLatestSortitionWinner` (v1) / `ActiveMiner` pkh match (v2) — immediately before `mark_locally_accepted` in `handle_block_pre_commit`, so that a signature is never placed over a block whose miner the signer's own state machine currently considers invalid, regardless of how much pre-commit weight accumulated earlier while the miner was still considered valid.

### Proof of Concept
1. Miner M wins sortition and is the valid `ActiveMiner`/`SortitionMinerStatus::Valid`. It proposes tenure-start block B.
2. `check_proposal` passes for all signers; B is submitted for node validation, then `handle_block_validate_ok` → `check_block_against_signer_db_state` passes → `mark_pre_committed` → each signer broadcasts its pre-commit for B and stores it via `handle_block_pre_commit` (below threshold at first).
3. M intentionally delays further broadcasting/activity for longer than `block_proposal_timeout` (an action a single miner fully controls).
4. Each signer's local `check_miner_inactivity`/`SortitionState::is_timed_out` (`stacks-signer/src/chainstate/v1.rs:52-94`) fires, flipping `last_sortition.miner_status` to `InvalidatedBeforeFirstBlock` for M's tenure — this happens locally, per signer, with no external input.
5. Gossip eventually delivers enough previously-cast pre-commits (cast in step 2, before invalidation) to a signer to cross the 70% `compute_voting_weight_threshold` in `handle_block_pre_commit`.
6. `handle_block_pre_commit` re-runs only `check_block_against_signer_db_state` (tenure-confirmation check), which still passes since B legitimately confirms its own tenure; it does **not** re-check `SortitionMinerStatus`, so the function proceeds to `mark_locally_accepted`/sign B despite the signer's own state now considering M invalid.

impl SortitionState {
    /// Check if the given sortition identified by its ConsensusHash has timed out based on current signed blocks
    /// and the time at which the burn block for it was first recorded in the provided signerdb
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
