# Title
Stale Confirmations From Removed Multisig Members Count Toward Confirmation Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in [1](#0-0)  counts a request as approved once the size of its stored `confirmations` set reaches `num_confirmations`, without re-validating that every account/key recorded in that set is still a current member. `delete_member` only purges requests *originated by* the removed member, not confirmations that member previously cast on other members' pending requests, so a stale confirmation from a departed member remains permanently counted toward the threshold.

### Finding Description
The intended invariant is: `confirmations from currently-live members >= num_confirmations` before a request executes — analogous to the report's binding that only entitled callers should be able to trigger privileged execution logic.

`confirm()` only validates the *current caller*: [1](#0-0) 

`assert_valid_request` likewise only checks that the caller confirming *right now* is a member; it never revisits the accounts already present in the stored confirmation set: [2](#0-1) 

`delete_member` removes a departing member's own outstanding *requests*, but not their confirmations left on other members' still-pending requests: [3](#0-2) 

Because of this, once a member confirms a pending request and is later removed from the multisig (e.g. compromised key revoked, member leaving), that confirmation is never invalidated. The `confirmations.len()` count used in the threshold check at line 304 therefore no longer represents "how many live members approved," but "how many accounts — live or since-removed — ever confirmed."

### Impact Explanation
This lets a request be executed with fewer truly live, currently-authorized signers than `num_confirmations` requires — a multisig request executed below the intended live-member threshold. Any privileged `MultiSigRequestAction` (e.g. `Transfer`, `AddKey` granting a full-access key, `FunctionCall`) can be pushed through this way, resulting in unauthorized fund transfer or unauthorized key/permission grant on the multisig account. This matches the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
No privileged access is required beyond being a legitimate member at request-creation/confirmation time, which is the normal operating mode of a multisig. The only precondition is ordinary membership churn (removing a member after they confirmed a still-pending request) — a routine, expected multisig lifecycle event, not a rare edge case. Any remaining member can then complete execution of the stale request.

### Recommendation
When counting confirmations toward the threshold in `confirm()`, filter the stored `confirmations` set down to accounts that are still present in `self.members` (or, simpler, scrub/invalidate confirmations belonging to a member in `delete_member` for *all* pending requests, not only requests they authored).

### Proof of Concept
1. Initialize `MultiSigContract::new([A, B, C, D], 3)` (4 members, 3 confirmations required).
2. `A.add_request(Transfer{amount, receiver_id: attacker})` → `request_id`.
3. `B.confirm(request_id)` → confirmations = {B} (1/3, pending).
4. `C.confirm(request_id)` → confirmations = {B, C} (2/3, pending).
5. Separately, members submit and confirm a `DeleteMember{member: B}` request (reaching 3 confirmations legitimately) — `B` is removed via [3](#0-2) ; note only requests *authored by B* are purged, the `{B, C}` confirmation set on the Transfer request is untouched.
6. Members are now `{A, C, D}`, `num_confirmations` is still `3`.
7. `A.confirm(request_id)` → `confirmations.len() (2) + 1 >= 3` → request executes and funds are transferred to `attacker`, even though only `A` and `C` are actually live members who approved it (B's stale confirmation counted as the third).

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
