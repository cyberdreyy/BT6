### Title
Griefing: a single APR0 withdraw receipt permanently/temporarily bricks `stopEpoch` once APR is raised — `prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0 && unscaledApr != 0` ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` is invoked by `IdleCDOEpochVariant` during every epoch stop. It early-returns only when `apr0TotalPrincipal == 0`; otherwise it reverts with `NotAllowed()` if `unscaledApr != 0` (`IdleCreditVault.sol:506-508`). An unprivileged lender can open a withdraw request while the pool APR is 0 (the request is routed to `_requestWithdrawApr0`, which increments `apr0TotalPrincipal` at `IdleCreditVault.sol:567-577`). Because `apr0TotalPrincipal` is only cleared at the end of a *successful* `prepareStopEpochWithApr0` call (`IdleCreditVault.sol:540`), once the honest manager sets a nonzero APR for the next epoch, every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts — freezing all lender funds until the manager remediates by lowering APR back to 0.

### Finding Description
The withdraw-request path in `IdleCDOEpochVariant.requestWithdraw` → `IdleCreditVault.requestWithdraw` buckets receipts by current APR: when `unscaledApr == 0` and the pool is not closed, the principal is recorded via `_requestWithdrawApr0(_amount, _user)`, which adds to the global `apr0TotalPrincipal` counter (`IdleCreditVault.sol:285-286, 567-577`).

At epoch end the CDO calls `prepareStopEpochWithApr0(_interest)`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:499-508
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

The zeroing `apr0TotalPrincipal = 0` (`:540`) is reached only *after* this check, so the revert is self-perpetuating: the counter cannot be cleared by the very function designed to close the bucket. There is no other code path that decrements `apr0TotalPrincipal` for still-open receipts except `_clearWithdrawClaimForEpoch` in the *default* finalization flow (`:822-831`) — i.e., absent a borrower default, the only escape is the manager setting `unscaledApr` back to 0 via `setAprs`/`setAprsWithBuffer` so one stop can succeed.

Epoch lifecycle sequence (normal, non-default mode):

1. Epoch N ends; buffer period begins. Manager has set `unscaledApr = 0` (a legitimate configuration — APR0 mode is a supported feature, see `testApr0WithdrawGetsInterestAtStopEpoch`).
2. Attacker (any KYC-passing lender holding tranche tokens) calls `cdoEpoch.requestWithdraw(amount, tranche)`. Since `unscaledApr == 0`, this creates an APR0 receipt: `apr0Users[attacker].principal += amount`, `apr0TotalPrincipal += amount`. Cost: only tranche tokens they already own; the receipt stays claimable.
3. Manager honestly raises APR for the upcoming epoch (`setAprs(newApr, scaledApr)` — a routine privileged action in every epoch transition where the borrower's rate changes).
4. Epoch N+1 runs and ends. Manager calls `stopEpoch(...)` → `prepareStopEpochWithApr0` sees `apr0TotalPrincipal != 0` and `unscaledApr != 0` → `revert NotAllowed()`.
5. Every `stopEpoch`/`stopEpochWithDuration` attempt reverts identically. The epoch can never close while APR is nonzero, and `epochEndDate` has passed — no deposits, no claims maturing, no interest accounting. Attacker can repeat for free each time APR is 0 again, and can front-run any remediation attempt with a fresh APR0 request the moment APR touches 0.

### Impact Explanation
Temporary freezing of all funds in the vault: as long as `apr0TotalPrincipal != 0 && unscaledApr != 0`, `stopEpoch` is uncallable, so the epoch never ends, `epochNumber` never increments, and all pending withdraw receipts cannot mature (`_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest[_user]`, `IdleCreditVault.sol:326`). Entire TVL is locked. Recovery requires the honest manager to set APR to 0 for a full epoch (forcing an unintended zero-yield epoch on all lenders — a quantifiable yield loss equal to `expectedEpochInterest` for that epoch), and the attacker can re-grief each cycle at negligible cost. Maps to the CVE's availability-impact bug class (hang/DoS of the credit-vault state machine via a single unprivileged transaction sequenced around a routine privileged call).

### Likelihood Explanation
Medium. Requires a specific but plausible configuration window: `unscaledApr == 0` while the pool accepts withdraw requests, followed by a manager APR increase — a normal operational sequence whenever a borrower's rate moves off 0. The attacker needs only tranche tokens (any KYC'd lender) and spends only gas; their principal remains recoverable. Existing guards do not stop it: `requestWithdraw` has no check preventing an APR0 request from outliving the zero-APR regime, and `_ensureDefaultRecoveryInitialized`/`defaultRecoveryFinalized` paths are irrelevant pre-default. Acknowledged uncertainty: this analysis is based on the indexed snippets; it assumes `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` unconditionally route through `prepareStopEpochWithApr0` (its `_onlyIdleCDO` guard and name imply it is the CDO's epoch-stop hook), which should be confirmed when building the PoC.

### Recommendation
In `prepareStopEpochWithApr0`, replace the hard revert with graceful settlement: when `unscaledApr != 0`, treat the APR0 bucket as settled with zero additional interest (skip the pro-rata allocation, still execute `apr0TotalPrincipal = 0`), or settle each receipt's claim basis into the normal funded path so the bucket always closes. Alternatively, prevent new APR0 requests from being created while a nonzero APR transition is pending, or make `requestWithdraw` settle/claim outstanding APR0 receipts instead of stacking them. A Foundry fork test should assert that `stopEpoch` succeeds with a nonzero APR while an open APR0 receipt exists.

### Proof of Concept
```solidity
// test/foundry/Apr0StopEpochDos.t.sol — Foundry, mainnet fork of a live IdleCreditVault deployment
function testApr0ReceiptBlocksStopEpochAfterAprRaise() external {
    // Setup: pool in buffer period, unscaledApr == 0 (manager set APRs to 0 last stopEpoch)
    vm.prank(manager);
    IdleCreditVault(strategy).setAprs(0, 0);

    // Attacker: KYC'd lender holding AA tranches opens a withdraw request while APR == 0
    vm.startPrank(attacker);
    cdoEpoch.requestWithdraw(attackerTrancheBal, address(AAtranche));
    vm.stopPrank();
    assertGt(IdleCreditVault(strategy).apr0TotalPrincipal(), 0);

    // Honest manager raises APR for the next epoch — routine operation
    vm.prank(manager);
    IdleCreditVault(strategy).setAprs(10e18, scaledApr); // within maxApr

    // Epoch runs to its end
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(underlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(borrower);
    IERC20(underlying).approve(address(cdoEpoch), type(uint256).max);

    // stopEpoch bricks: prepareStopEpochWithApr0 reverts NotAllowed()
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Repeatable: still reverts; epochNumber never advances; no receipts mature
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Victim's older funded receipt cannot be claimed while epoch can't close
    vm.prank(victim);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();
}
```
