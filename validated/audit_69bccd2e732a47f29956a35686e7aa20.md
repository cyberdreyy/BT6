## Finding: Stale confirmations from removed multisig members still count toward the execution threshold

This is a solid analog to the "trusted-but-unverified state" bug class in the report: just as the `StabilityPool` trusts `finalizeLiquidation()` without re-verifying the debt was cleared, the multisig contracts trust the `confirmations` set for a request without re-verifying that every entry in it still corresponds to a *current* member. Removing a member only cleans up requests *created* by that member — not confirmations that member left on *other* pending requests.

### Title
Multisig requests can execute below the configured confirmation threshold because removed members' stale confirmations are still counted - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`confirm()` in both `multisig2/src/lib.rs` and `multisig/src/lib.rs` decides whether to execute a request purely by counting entries already present in that request's `confirmations` set, without checking that those confirmers are still valid/live members. `delete_member` (multisig2) / the `DeleteKey` action (multisig) only purges confirmations for requests that the removed member *originated*, leaving that member's confirmations on requests created by *other* members intact. A request can therefore be executed with contributions from a member who has already been removed, i.e. below the number of live-member approvals the `num_confirmations` threshold is supposed to guarantee.

### Finding Description
In `multisig2/src/lib.rs`: [1](#0-0) 

`delete_member` only removes requests where `r.member == member` (requests the removed member created) and their confirmations: [2](#0-1) 

It never scans `self.confirmations` for other requests that contain `member.to_string()` as one of the approving entries.

`confirm()` then decides execution purely on the size of the stored confirmation set plus the new confirmer, with no check that existing entries are still members: [3](#0-2) 

The same pattern exists in the older PK-based `multisig/src/lib.rs`: the `DeleteKey` action only removes requests originated by that key (`r.signer_pk == pk`), not confirmations that key left on other requests, and `confirm()` again just counts set size: [4](#0-3) [5](#0-4) 

**Binding broken:** `confirmations counted == live members who approved`. In reality, after a member removal, `confirmations counted ⊇ live members who approved`, since a removed member's prior confirmation on a still-pending request is never invalidated.

### Impact Explanation
This directly matches the Critical criterion "a multisig request executed below threshold." A request (e.g. a `Transfer` or `FunctionCall` moving NEAR out of the account) can reach `num_confirmations` and execute even though one of the counted approvals came from an account/key that was deliberately removed as a member — for example because its key was compromised, or the group intentionally reduced its trust. The multisig's core security guarantee (K-of-N *live* signers must approve) is broken; funds can move on the say of fewer than K currently-trusted parties.

### Likelihood Explanation
This requires no exploitation of a rare edge case; it is a straightforward ordering of ordinary multisig operations available to any current member with legitimate access:
1. A request is created and partially confirmed by some members (not yet reaching threshold).
2. One of the confirmers is subsequently removed via a normal `DeleteMember`/`DeleteKey` request (a routine security operation, e.g., in response to a suspected key compromise).
3. The pending request's confirmation from the now-removed member is never purged.
4. Remaining live members confirm, and the request executes counting the stale confirmation, resulting in execution with only `K-1` (or fewer) genuinely live approvals.

No attacker-controlled deployment, victim key theft, or social engineering is needed beyond the normal flow of removing a member while a request is in flight — a scenario the contract explicitly supports (member removal alongside pending requests) but fails to reconcile.

### Recommendation
When removing a member/key (`delete_member` in `multisig2/src/lib.rs`, `DeleteKey` in `multisig/src/lib.rs`), iterate over **all** pending requests' confirmation sets (not just requests the member originated) and remove that member's entry from each. Alternatively, when counting confirmations in `confirm()`, filter the stored confirmation set to only those entries still present in `self.members` (multisig2) or still holding a valid access key (multisig) before comparing against `num_confirmations`.

### Proof of Concept
Scenario with members `{A, B, C, D}` and `num_confirmations = 3`:
1. `A` calls `add_request_and_confirm(R)` → `confirmations(R) = {A}`.
2. `B` calls `confirm(R)` → `confirmations(R) = {A, B}` (2 < 3, stays pending) — see `confirm()` logic [6](#0-5) .
3. The group discovers `B`'s key is compromised and submits/confirms a `DeleteMember { member: B }` request, which executes via `delete_member` — this removes `B` from `self.members` and deletes `B`'s *own* requests, but request `R` (created by `A`) is untouched: `confirmations(R)` remains `{A, B}` [2](#0-1) .
4. `C` (a live member) calls `confirm(R)` → `confirmations(R).len() + 1 == 3 >= num_confirmations` → `R` executes [7](#0-6) .

`R` (e.g., a `Transfer` of contract funds) executes with the counted approval of `A`, `B`, `C` — but `B` was removed in step 3 and is no longer a live member. Only two currently-trusted members (`A`, `C`) actually approved, one short of the configured `num_confirmations = 3` threshold of live members.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
