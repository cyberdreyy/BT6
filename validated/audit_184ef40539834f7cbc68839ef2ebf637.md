### Title
Decoder panic via unbounded `Vec<Pubkey>` length prefix in `ExtendLookupTable` bincode deserialization - ([File: transaction-status/src/parse_address_lookup_table.rs])

### Summary
`parse_address_lookup_table` deserializes raw, attacker-controlled `CompiledInstruction.data` bytes with plain `bincode::deserialize::<ProgramInstruction>` with no size/length validation against the actual byte slice length. Because `ProgramInstruction::ExtendLookupTable` contains a `Vec<Pubkey>`, an attacker can craft instruction data whose bincode length prefix claims an enormous element count (e.g., near `u64::MAX`), causing the standard serde `Vec` visitor to call `Vec::with_capacity(len)` based purely on that untrusted prefix before any actual bytes are consumed, which can trigger a `capacity overflow` panic (or a huge allocation attempt) inside the decode path reachable from `getTransaction`.

### Finding Description
`parse_address_lookup_table` in `transaction-status/src/parse_address_lookup_table.rs` decodes instruction bytes like this: [1](#0-0) 

`instruction.data` originates from a `CompiledInstruction` inside a transaction that a client submitted; it is fully attacker-controlled bytes and is only interpreted by this decoder when a client later calls `getTransaction` (jsonParsed encoding), which reaches `parse::parse` → `parse_address_lookup_table`: [2](#0-1) 

`ProgramInstruction::ExtendLookupTable { new_addresses: Vec<Pubkey> }` is deserialized with `bincode::deserialize`, which uses bincode's default (unbounded) options. Serde's generic `Vec<T>` deserialization implementation calls `Vec::with_capacity(seq.size_hint().unwrap_or(0))` before reading any actual elements, and bincode's `SeqAccess::size_hint()` returns the length value taken directly from the untrusted length-prefix in the input bytes — it is not validated against the number of bytes actually remaining in `instruction.data`. An attacker can therefore submit an instruction whose serialized enum variant tag selects `ExtendLookupTable` followed by a `u64` length field set to a huge value (e.g. `u64::MAX`) with few or no trailing address bytes. Because `Pubkey` is 32 bytes, `Vec::with_capacity(len)` for such a length will overflow the internal `len * size_of::<Pubkey>()` capacity check, triggering Rust's `capacity overflow` panic (or, for more moderate but still absurd lengths, attempt an oversized allocation) — this happens inside the decode call before the "insufficient bytes" bincode error path is ever reached, i.e., before any allocation-vs-remaining-bytes check occurs.

This transaction need not execute successfully on-chain against real address-lookup-table state; it only needs to land in the ledger (or be retrievable via blockstore) so that its raw bytes are later fed to `getTransaction`'s jsonParsed parsing path. The existing guard `check_num_address_lookup_table_accounts`/`check_num_accounts` only validates the number of instruction *account* indices, not the instruction *data* length or the plausibility of the decoded `Vec` length, so it does not stop this.

The same unguarded pattern also exists in `ledger/src/transaction_address_lookup_table_scanner.rs`, which deserializes `ProgramInstruction` from instruction data during transaction sanitization (`wincode::deserialize`) — though that path is exercised earlier in the transaction lifecycle and uses a different deserializer (`wincode`) whose bounding behavior was not verified in this investigation.

### Impact Explanation
A single crafted transaction, once landed (or otherwise retrievable), causes any client's subsequent `getTransaction` (jsonParsed) call to trigger a panic (or oversized transient allocation) inside `parse_address_lookup_table`. This matches the explicitly accepted "decoder panic and misreporting" impact category. Whether this escalates to a full validator-process crash depends on whether the JSON-RPC handler thread wraps parsing in `catch_unwind`; this could not be conclusively confirmed from the available index, but at minimum it constitutes a reproducible decoder panic for a single low-rate RPC call, satisfying the "unbounded cost for a single low-rate call" / decoder-panic bounty category.

### Likelihood Explanation
Feasibility is high and preconditions are minimal: the attacker only needs to construct raw `CompiledInstruction.data` bytes for the address-lookup-table program ID with an oversized bincode `Vec` length prefix — the transaction does not need to succeed at runtime, only be included/stored so bytes are retrievable. No special privileges, staked node, or multiple calls are required; a single `getTransaction` call triggers the bug, consistent with the "no more than one call per CLUSTER_SLOT_TIME_TARGET/2" constraint. It is fully repeatable since the same crafted transaction bytes reliably reproduce the panic.

### Recommendation
Do not decode attacker-controlled instruction data with bincode's default (unbounded) `Options`; use `bincode::config::Options::with_limit` (or `bincode::DefaultOptions::new().with_limit(instruction.data.len() as u64)`) so the deserializer bounds any length-prefixed collection allocation by the actual number of bytes available, and reject the instruction gracefully instead of panicking. Additionally, validate that a declared `Vec` length is consistent with the remaining byte count before calling `with_capacity`, or switch to an incremental/streaming deserialization approach that avoids upfront preallocation from untrusted length fields. Apply the same treatment to the `wincode::deserialize` call in `ledger/src/transaction_address_lookup_table_scanner.rs`.

### Proof of Concept
```rust
// transaction-status/src/parse_address_lookup_table.rs (add to existing #[cfg(test)] mod test)
#[test]
fn test_extend_lookup_table_huge_length_prefix_does_not_panic() {
    use solana_message::compiled_instruction::CompiledInstruction;

    // ProgramInstruction::ExtendLookupTable is (per solana_address_lookup_table_interface)
    // encoded as: u32 variant tag (2 = ExtendLookupTable) followed by a bincode Vec<Pubkey>
    // (u64 length prefix + elements). Craft data with a huge length and no element bytes.
    let mut data = Vec::new();
    data.extend_from_slice(&2u32.to_le_bytes()); // ExtendLookupTable variant index
    data.extend_from_slice(&u64::MAX.to_le_bytes()); // claimed Vec<Pubkey> length
    // no trailing address bytes at all

    let instruction = CompiledInstruction {
        program_id_index: 0,
        accounts: vec![1, 2],
        data,
    };

    let account_keys = solana_message::AccountKeys::new(
        &[solana_pubkey::Pubkey::new_unique(); 3],
        None,
    );

    // Expected (fixed) behavior: returns Err(ParseInstructionError::InstructionNotParsable(..))
    // Current (vulnerable) behavior: panics with "capacity overflow" before returning.
    let result = std::panic::catch_unwind(|| {
        super::parse_address_lookup_table(&instruction, &account_keys)
    });
    assert!(
        result.is_ok(),
        "parse_address_lookup_table panicked on attacker-controlled length prefix"
    );
}
```
Expected assertion after the fix: the deserializer returns a bincode error (insufficient bytes) mapped to `ParseInstructionError::InstructionNotParsable`, with no panic and no allocation proportional to the attacker-claimed length. Before the fix, the test is expected to panic (`capacity overflow`), demonstrating the vulnerability.
