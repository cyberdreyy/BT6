### Title
`VaultController.ExportDKGResult` discloses full DKG result package to any edit-role caller without workflow/instance ownership checks - ([File: core/web/vault_controller.go])

### Summary
`ExportDKGResult` (`core/web/vault_controller.go:91-119`) looks up a DKG result solely by attacker-supplied `instanceId` and returns the full hex-encoded `ReportWithResultPackage` to the caller, with no check that the requester's role/session is authorized for that specific workflow's DKG instance. Any account holding the edit role (not just admin) that can reach this route can therefore retrieve another workflow's DKG result package purely by guessing/enumerating `instanceId`.

### Finding Description
`ExportDKGResult` decodes the request body for `instanceId` only, then calls `vault.NewVaultORM(vc.App.GetDB()).ReadResultPackage(ctx, instanceID)`: [1](#0-0) 

`ReadResultPackage` in the vault ORM performs an unscoped lookup keyed only by `instance_id` against the `dkg_results` table, with no owner/workflow/job column to filter by caller identity: [2](#0-1) 

The handler then hex-encodes the raw `ReportWithResultPackage` bytes and returns them directly in the JSON response via `presenters.NewExportDKGResultResource`, which carries `HexDKGResultPackage` as a plain field: [3](#0-2) 

This means `ExportDKGResult` returns data well beyond a verification boolean — the entire OCR report + DKG result package (which embeds the per-recipient encrypted shares) is exposed as long as the caller can supply a valid `instanceId`, regardless of whether that instance belongs to their workflow. There is no per-caller authorization check inside the handler or ORM tying the requester's identity/workflow to the `instanceId` being read; the only "gate" is whatever role check exists at the route-registration layer (edit-role, per the question's precondition), which is not a workflow-ownership check.

By contrast, `VerifyDKGResult` only returns a SHA-256 hash of the report (`presenters.NewVerifyDKGResultResource`), not raw key material, so it does not have the same exposure: [4](#0-3) [5](#0-4) 

Note: I could not directly confirm the exact route-registration lines in `core/web/router.go` binding `/vault/dkg_results/export` and `/vault/dkg_results/verify` to `auth.RequiresEditRole` within the available tool iterations (grep on the exact file path intermittently returned no lines for the vault-specific route strings, though `RequiresEditRole`/`v2Routes` patterns matched 23 times in that file). This detail should be verified directly in the file before finalizing severity, but the described exposure at the controller/ORM layer is confirmed and is independent of which specific role wrapper gates the route — the vulnerability is the lack of instance-to-caller ownership binding, not just the role requirement.

### Impact Explanation
This is a scoped cross-user secret/key-material disclosure: any edit-role user (a lower privilege than admin) can retrieve another workflow's full DKG result package — which contains encrypted DKG shares and OCR report data — by supplying an arbitrary/enumerated `instanceId`. This matches Chainlink's "sensitive information disclosure" / "key material exposure" bounty class, since DKG result packages are exactly the kind of workflow-secret material the vault subsystem is designed to protect from cross-tenant/cross-workflow access.

### Likelihood Explanation
Precondition is only a valid edit-role session/token (not admin) — a low bar relative to full node compromise. `instanceId` values are DKG instance identifiers tied to OCR configs, which may be predictable/enumerable within an operator's own node (e.g., seen via job proposals, logs, or other export/verify calls for their own workflows) and there is no rate limiting or ownership check preventing iteration over the `dkg_results` table via this endpoint. The exploit is a single POST request and is fully repeatable.

### Recommendation
Add an authorization check in `ExportDKGResult` (and `VerifyDKGResult`) that verifies the requesting caller's identity/session is associated with the workflow/job that owns the given `instanceId` before returning the result package, e.g., by joining `dkg_results` against the owning job/workflow's ACL, or restricting export to `admin`-only role rather than `edit`. At minimum, redact/omit `HexDKGResultPackage` from responses to non-owning callers and return `403`/`404` instead.

### Proof of Concept
1. Seed two DKG results in `dkg_results` under distinct `instance_id`s, each conceptually tied to a different workflow/job (`workflowA-instance`, `workflowB-instance`), using `vault.ORM.WriteResultPackage`.
2. Authenticate as an edit-role (non-admin) user scoped/owning only `workflowA`.
3. Call `POST /v2/vault/dkg_results/export` with `{"instanceId": "workflowB-instance"}`.
4. Assert current (vulnerable) behavior: HTTP 200 with `hexDKGResultPackage` populated for `workflowB`'s data — i.e., `VaultController.ExportDKGResult` returns another workflow's DKG package to an edit-role user who does not own it.
5. Expected/fixed behavior: HTTP 403/404, no `hexDKGResultPackage` in the response body, verified via a Go handler-level test (`core/web/vault_controller_test.go` style) asserting response status and absence of `HexDKGResultPackage`.

```go
func (vc *VaultController) ExportDKGResult(c *gin.Context) {
	var req ExportDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId is required"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

	hexPackage := hex.EncodeToString(v.ReportWithResultPackage)
	sha := sha256.Sum256(v.ReportWithResultPackage)
	shaStr := hex.EncodeToString(sha[:])
	jsonAPIResponse(c, presenters.NewExportDKGResultResource(hexPackage, shaStr), "exportDKGResult")
```

```go
func (o *orm) ReadResultPackage(ctx context.Context, iid dkgocrtypes.InstanceID) (*dkgocrtypes.ResultPackageDatabaseValue, error) {
	var configDigest []byte
	var seqNr uint64
	var reportWithResultPackage []byte
	var signatures pq.ByteaArray
	var signerOracleIDs []byte

	query := `SELECT config_digest, seq_nr, report_with_result_package, signatures, signer_oracle_ids FROM dkg_results WHERE instance_id = $1;`
	row := o.ds.QueryRowxContext(ctx, query, iid)
	err := row.Scan(&configDigest, &seqNr, &reportWithResultPackage, &signatures, &signerOracleIDs)
	if errors.Is(err, sql.ErrNoRows) {
		return nil, nil
	}
	if err != nil {
		return nil, errors.Wrap(err, "failed to read dkg result")
	}

	var cd types.ConfigDigest
	copy(cd[:], configDigest)

	attributedSigs := make([]types.AttributedOnchainSignature, len(signatures))
	for i := range signatures {
		attributedSigs[i] = types.AttributedOnchainSignature{
			Signature: signatures[i],
			Signer:    commontypes.OracleID(signerOracleIDs[i]),
		}
	}

	value := &dkgocrtypes.ResultPackageDatabaseValue{
		ConfigDigest:            cd,
		SeqNr:                   seqNr,
		ReportWithResultPackage: reportWithResultPackage,
		Signatures:              attributedSigs,
	}

	return value, nil
}
```
