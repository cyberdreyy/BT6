### Title
EI-authenticated requests satisfy `isUser` check and can trigger arbitrary numeric job IDs via `PipelineRunsController.Create` - ([File: core/web/pipeline_runs_controller.go])

### Summary
The premise in the question (bypassing `isUser` by crafting `idStr` to fail `uuid.Parse` but succeed int32 parsing) does not hold, because `isUser` in `PipelineRunsController.Create` is derived solely from the authenticated identity in the gin context and is completely independent of `idStr` content [1](#0-0) . However, tracing the actual auth flow reveals a related, real issue: `auth.AuthenticateExternalInitiator` populates the exact same context key (`SessionUserKey`) that `GetAuthenticatedUser` reads, using a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` [2](#0-1) . This means an EI-authenticated request can cause `GetAuthenticatedUser(c)` to return `ok=true`, so `isUser` evaluates to `true` for EI credentials on any endpoint reachable through the `AuthenticateExternalInitiator` method, contradicting the code comment "only users are allowed to run jobs using int IDs - EIs not allowed" [3](#0-2) .

### Finding Description
`PipelineRunsController.Create` first rejects UUID-looking `idStr` values with a "job type removed" error, then checks `isUser` via `auth.GetAuthenticatedUser(c)` before allowing an int32 job ID to be passed to `prc.App.RunJobV2` [4](#0-3) . `GetAuthenticatedUser` simply reads the `SessionUserKey` value from the gin context and type-asserts it to `*clsessions.User` [5](#0-4) . Critically, `AuthenticateExternalInitiator` — the auth method used to validate `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers for external initiators — sets both `SessionExternalInitiatorKey` and `SessionUserKey` (to a synthetic run-role user) upon success [2](#0-1) . Because `GetAuthenticatedUser` cannot distinguish "a real logged-in user" from "an EI request that was given a synthetic user object for role-check convenience," the `isUser` gate in `PipelineRunsController.Create` is not a reliable EI-exclusion mechanism wherever the route's authentication middleware stack includes `AuthenticateExternalInitiator`.

The idStr-crafting mechanism described in the question is not itself exploitable: `idStr` only determines which of the `uuid.Parse` / `strconv.ParseInt` branches execute, it has no influence on the value of `isUser`.

### Impact Explanation
If the `/v2/jobs/:ID/runs` route (or any other route using `RequiresRunRole`/similar checks fed by `GetAuthenticatedUser`) is wired with `AuthenticateExternalInitiator` in its middleware chain, an EI credential holder could invoke `RunJobV2` with an arbitrary int32 job ID, i.e., trigger job runs outside the intended EI/webhook binding — a privilege/scope confusion matching "unauthorized job run" impact class.

### Likelihood Explanation
This requires only a valid EI credential (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret`), which is a lower-privileged credential than a full user session/API token. Exploitability is contingent on confirming that `PipelineRunsController.Create`'s route is actually reachable through the `AuthenticateExternalInitiator` middleware in `core/web/router.go` — I was not able to fully confirm this specific route's middleware wiring before running out of tool iterations, so this should be verified against `core/web/router.go`'s registration of the `/v2/jobs/:ID/runs` POST route.

### Recommendation
Distinguish EI-originated "synthetic" users from real authenticated users, e.g., by checking `auth.GetAuthenticatedExternalInitiator(c)` in addition to/instead of `GetAuthenticatedUser(c)` in `PipelineRunsController.Create`, or by using a distinct context key/sentinel for EI-synthesized role objects so `GetAuthenticatedUser` cannot be satisfied by EI authentication.

### Proof of Concept
Go handler-level test plan:
1. Construct a `gin.Context` and call `auth.AuthenticateExternalInitiator`-equivalent setup: set `c.Set(auth.SessionExternalInitiatorKey, ei)` and `c.Set(auth.SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` (mirroring the real middleware behavior).
2. Set `c.Params` with `ID` = a numeric string (e.g., `"5"`).
3. Call `PipelineRunsController.Create(c)` with a mocked `App.RunJobV2`.
4. Assert `RunJobV2` **is** invoked (demonstrating `isUser` is true for EI context) — contradicting the intended "EIs not allowed" comment.
5. Separately verify in `core/web/router.go` whether the `/v2/jobs/:ID/runs` POST route's middleware chain includes `AuthenticateExternalInitiator`, to confirm real-world reachability.

// GetAuthenticatedUser extracts the authentication user from the context.
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
