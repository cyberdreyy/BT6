### Title
Loss-adjusted withdraw claims read `lossRecoveryPriceByEpoch` under the request-epoch key while `collectWithdrawFunds` writes it under the post-bump `epochNumber`, so haircutted receipts can claim at par - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug (CVE-2024-57874) is a "partial SETREGSET" flaw: a setter consumes an uninitialized temporary when the caller supplies a zero-length/partial write, so a stale slot is read as if it were initialized state. The analog in `IdleCreditVault` is the epoch-keyed haircut table for pending withdraw receipts: `requestWithdraw` records the receipt under the pre-stop `epochNumber` (`lastWithdrawRequest` / `withdrawsRequestsByEpoch`), while `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]` during `stopEpoch`, i.e. after `deposit()` has already bumped `epochNumber` (the "deposit done on stopEpoch" path). A claim then looks up the haircut under a key that was never written — reading the equivalent of the uninitialized `ctrl` slot — gets `0` ("no loss-adjusted epoch"), and falls through to the par-funded claim path.

### Finding Description
`requestWithdraw` stores the receipt epoch before the epoch counter advances:

```solidity
uint256 currentEpoch = epochNumber;
...
lastWithdrawRequest[_user] = currentEpoch;
withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
```

`deposit()` increments `epochNumber` when invoked while the epoch is still running, which is exactly the `stopEpoch` funding path ("deposit done on stopEpoch ... so we reset the counter / epochNumber += 1"). `collectWithdrawFunds` then stores the haircut under the already-incremented counter:

```solidity
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
```

On claim, `_claimLossAdjustedWithdrawRequest` indexes the haircut table by `lastWithdrawRequest[_user]` (the old epoch), reads `lossRecoveryPriceByEpoch[oldEpoch] == 0`, and returns `0`. `claimWithdrawRequest` then calls `_claimFundedWithdrawRequest`, whose only gate is `epochNumber <= lastWithdrawRequest[_user]` — which now passes because `epochNumber` was bumped — so the full `claimBasis` is burned and paid at par via `_transferFundedClaim`, even though `collectWithdrawFunds` only pulled `pendingBasis * lossRecoveryPrice` underlying from the CDO. The same stale-slot read in `requestWithdraw` (lines 261–271) also fails to detect the pending loss-adjusted receipt, letting a user stack a second request on top of an unclaimed haircutted one.

### Impact Explanation
The "one receipt, haircut-adjusted payout" invariant is broken. Every pending receipt from the loss epoch is paid 100% while the strategy only received `lossRecoveryPrice`-adjusted funds. The shortfall is socialized onto other claimants/LPs: early claimers drain the strategy balance and later claimants (or the tranche NAV) absorb the deficit, producing direct overpayment theft and partial insolvency equal to `pendingBasis * (1 - lossRecoveryPrice)`. If the deficit exceeds the strategy balance, later claims revert — permanent freezing of honest users' funded receipts.

### Likelihood Explanation
Requires only an unprivileged tranche-token holder who calls `requestWithdraw` during a running epoch, plus an honest-manager `stopEpochWithDuration(_lossAmount > 0)` — a routine loss-realization path the code explicitly supports via `previewLossAdjustedWithdrawFunds`. No malicious privileged action is needed. Note on verification: the finding depends on `collectWithdrawFunds` being invoked after the `deposit()`-driven `epochNumber` bump inside `stopEpoch` in `IdleCDOEpochVariant`/`IdleCDOEpochVariantPrefunded`; I was able to confirm the bump inside `deposit()` and the write/read asymmetry in `IdleCreditVault`, but could not fully trace the call order inside `stopEpoch` within the available iterations. If `collectWithdrawFunds` is invoked before the bump, the keys align and this specific vector closes; the stale-read structure (marker `0` default vs. written slot `0`, plus per-epoch dust never cleared in `_claimFundedWithdrawRequest`) remains fragile either way.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the same epoch identifier stored in `lastWithdrawRequest`/`withdrawsRequestsByEpoch` — e.g. pass the request-epoch into `collectWithdrawFunds` or write it under `epochNumber - 1` semantics matching the receipts being haircutted — rather than the post-bump counter. Additionally, treat `lossRecoveryPriceByEpoch[x] == 0` as "no haircut" only when the corresponding per-epoch basis is also zero, and clear `withdrawsRequestsByEpoch` entries in `_claimFundedWithdrawRequest` so stale per-epoch slots cannot be re-consumed.

### Proof of Concept
Foundry fork sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// 1. user deposits AA, epoch starts (epochNumber = N)
idleCDO.depositAA(10_000 * ONE_SCALE);
_startEpochAndCheckPrices(0);

// 2. user requests withdraw during epoch N -> lastWithdrawRequest=N, byEpoch[N]=amount
cdoEpoch.requestWithdraw(0, address(AAtranche));

// 3. borrower repays principal minus loss; manager stops with _lossAmount > 0.
//    Inside stopEpoch: deposit() bumps epochNumber to N+1, then
//    collectWithdrawFunds writes lossRecoveryPriceByEpoch[N+1] = price < 1e18.
deal(defaultUnderlying, borrower, fundedAmount); // fundedAmount < pendingBasis
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(0, lossAmount);

// 4. user claims: _claimLossAdjustedWithdrawRequest reads
//    lossRecoveryPriceByEpoch[N] == 0 -> falls through to
//    _claimFundedWithdrawRequest which pays the full claimBasis at par.
uint256 balPre = underlying.balanceOf(user);
vm.prank(user);
cdoEpoch.claimWithdrawRequest();
assertEq(underlying.balanceOf(user) - balPre, fullClaimBasis); // haircut bypassed

// 5. second claimant's funded receipt now undercollateralized / reverts on
//    _transferFundedClaim reserve check or transfer.
```
