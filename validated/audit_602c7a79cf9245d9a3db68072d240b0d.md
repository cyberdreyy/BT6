This confirms the bug: `apply_withdrawals` correctly caps the beacon-state-side balance deduction to `min(withdrawal.amount, builder_balance)` [1](#0-0) , but `get_builder_withdrawals` places the *uncapped requested* `withdrawal.amount` into `Withdrawal.amount`, which becomes `state.payload_expected_withdrawals` — the value the execution layer is committed to credit to `fee_recipient` [2](#0-1) . This is exactly analogous to the Wise-Lending bug class ("liquidator receives a substitute/short-changed value instead of the committed real payout"), except inverted in direction: here the execution layer pays out *more* than the CL debits, i.e. Gwei is minted from nothing.

### Title
Builder pending-withdrawal amount is not capped to builder balance before being committed to the execution payload, minting Gwei - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` copies the raw requested `builder_pending_withdrawals[i].amount` into the `Withdrawal` object that is placed in `state.payload_expected_withdrawals` — the binding commitment the execution layer must honor — without capping it to the builder's actual balance. Meanwhile `apply_withdrawals`, which mutates CL state (`state.builders[i].balance`), does cap the deduction to `min(withdrawal.amount, builder_balance)`. When a builder's balance is smaller than its queued pending-withdrawal amount, the execution layer mints/pays the full requested amount to `fee_recipient`, while the CL only ever debited the smaller, capped amount (and once balance hits 0, nothing further is debited at all).

### Finding Description
- `get_builder_withdrawals` (specs/gloas/beacon-chain.md:1805-1834) builds the committed withdrawal list using the pending withdrawal's raw `amount` field unconditionally: `amount=withdrawal.amount`. [3](#0-2) 
- `apply_withdrawals` (specs/gloas/beacon-chain.md:1923-1931) is the function that actually decrements the CL-side `state.builders[builder_index].balance`, and it explicitly saturates the deduction at the available balance: `state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)`. [4](#0-3) 
- `state.payload_expected_withdrawals` (set from the exact same `withdrawal.amount` value) is the field the execution layer is required to honor as a real ETH credit to `fee_recipient` — the spec's own comment states withdrawal amounts "must" be honored by any execution payload building on this block. [5](#0-4) 
- The associated (AI-generated, non-normative) report explicitly documents this exact discrepancy as intended test behavior: "Actual = `min(amount, builder.balance)`" is claimed for the *balance side*, while the withdrawal object itself carries the full "Requested amount." [6](#0-5) 
- Test `test_builder_withdrawal_insufficient_balance` codifies this as expected: builder has 1 ETH, pending withdrawal requests 5 ETH; the resulting `Withdrawal.amount` is asserted to be the full 5 ETH (`withdrawal_amounts_builders={builder_index: withdrawal_amount}` where `withdrawal_amount = 5 ETH`), while `builders[0].balance` only drops to 0 (i.e., only 1 ETH was ever debited on the CL side). [7](#0-6) 

Concretely: before attack, `builder.balance = 1 ETH`, pending withdrawal `amount = 5 ETH`. After `process_withdrawals`, `payload_expected_withdrawals[0].amount = 5 ETH` (execution layer mints/pays 5 ETH to `fee_recipient`), but `state.builders[0].balance` only decreases by 1 ETH to 0. The other 4 ETH is paid by the execution layer without any corresponding CL-side debit anywhere in the state — it is created from nothing and paid to `fee_recipient`, breaking the balance-conservation equality between CL debits and EL credits.

### Impact Explanation
This breaks the "Gwei created ... paid to a non-owner" equality explicitly called out in scope: a `fee_recipient` who is not entitled to more than the builder's real balance receives the excess as newly-minted Gwei, sourced from nowhere in `state.builders[*].balance`, `state.balances[*]`, or any other tracked account. This is a critical/high severity totalsupply-inflation bug reachable purely by a builder (or anyone who can queue a `BuilderPendingWithdrawal`, e.g., via the builder payment/withdrawal-request mechanism) requesting a withdrawal amount exceeding its remaining balance.

### Likelihood Explanation
High likelihood of occurrence given normal builder economics: builder balances fluctuate (payments made, slashable? no, but consumed by other pending withdrawals or payment obligations) and multiple `BuilderPendingWithdrawal` entries can be queued against the same builder before being processed, so `sum(pending amounts) > current balance` is a completely ordinary state, not a contrived edge case — the repo's own test suite specifically constructs and asserts this scenario as expected/passing behavior rather than treating it as an invalid input to reject.

### Recommendation
`get_builder_withdrawals` must cap the committed `Withdrawal.amount` to the *actual* available builder balance at the time it is computed (accounting for prior withdrawals already queued in the same block, similar to how `get_pending_partial_withdrawals`/`get_validators_sweep_withdrawals` use `get_balance_after_withdrawals`), so that the amount placed into `payload_expected_withdrawals` exactly matches what `apply_withdrawals` will actually deduct from `state.builders[*].balance`. The cap should be `min(withdrawal.amount, balance_after_prior_withdrawals_in_this_block)`, and `apply_withdrawals`'s `min()` saturation should become unreachable/redundant once this is fixed, not a silent inflation path.

### Proof of Concept
1. Register a builder with `balance = 1_000_000_000` Gwei (1 ETH) and `execution_address`/associated `fee_recipient`.
2. Queue a `BuilderPendingWithdrawal(builder_index=B, fee_recipient=F, amount=5_000_000_000)` (5 ETH) in `state.builder_pending_withdrawals`.
3. Call `process_withdrawals(state)` (with `state.latest_block_hash == state.latest_execution_payload_bid.block_hash` so the early-return doesn't trigger).
4. Observe: `state.payload_expected_withdrawals[0].amount == 5_000_000_000` (the commitment forwarded to the execution layer, which will credit address `F` with 5 ETH), while `state.builders[B].balance == 0` (only 1 ETH was ever debited anywhere in consensus state) — exactly reproduced by the existing repo test `test_builder_withdrawal_insufficient_balance`. [7](#0-6)  The 4 ETH difference is minted on the execution layer with no corresponding consensus-layer source, violating Gwei conservation.

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,

    processed_count = Uint64(0)

        )

        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

*Note*: This is modified to only take the `state` as parameter. Withdrawals are
deterministic given the beacon state, any execution payload that has the
corresponding block as parent beacon block is required to honor these
withdrawals in the execution layer. `process_withdrawals` must be called after
`process_parent_execution_payload` (which updates `state.latest_block_hash`) and
before `process_execution_payload_bid` as the latter function affects validator
balances.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
