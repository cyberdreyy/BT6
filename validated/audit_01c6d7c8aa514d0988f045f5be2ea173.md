### Title
Rejection votes for a signer address are silently dropped after their first rejection due to an incorrect single-column primary key - ([File: stacks-signer/src/signerdb.rs])

### Summary
`block_rejection_signer_addrs` is keyed only by `signer_addr`, not by `(signer_signature_hash, signer_addr)`. Because a signer can legitimately reject many *different* blocks (retries, forks, competing tenures) over the life of a reward cycle, the second time any peer signer's rejection is recorded for a *different* block hash, the `INSERT` collides with the stale row left over from the peer's first-ever rejection and fails. The caller does not treat this failure as fatal, so the new rejection's weight is silently never tallied for the new block — an analog of the reward-token bug's stale, un-cleared per-key state leaking into a new context.

### Finding Description
The table is declared with a primary key on `signer_addr` alone: [1](#0-0) 

But every read/write path treats `(signer_signature_hash, signer_addr)` as the logical key: the "does a rejection already exist" check and the duplicate-detection logic both filter by `signer_signature_hash = ?1 AND signer_addr = ?2`: [2](#0-1) 

When no row matches for *this* `(signer_signature_hash, signer_addr)` pair, the code falls into the `None` branch and does a plain `INSERT` (no `OR REPLACE`/`OR IGNORE`): [3](#0-2) 

Because the real table constraint is `PRIMARY KEY (signer_addr)`, this `INSERT` violates the SQLite `STRICT` table's uniqueness constraint as soon as that `signer_addr` already has *any* row for a *previous, different* block — i.e. after the very first time this peer's rejection was recorded for some block, its rejection for every subsequent distinct block silently fails to persist.

The call site does not fail closed on this error — it only logs and continues, rather than returning: [4](#0-3) 

`store_and_process_block_rejection` then proceeds to recompute the rejection tally from `get_block_rejection_signer_addrs(block_hash)`, which is missing the just-attempted (and silently dropped) rejection row, so that peer's weight is permanently excluded from the tally for the current — and every future — distinct block it tries to reject: [5](#0-4) 

This is the direct analog of the `_marketWeightsByToken` bug: a per-entity association (`signer_addr` → its rejection record) that should be scoped per-context (`signer_signature_hash`) is instead treated as global, so stale/previous-context state silently blocks or corrupts accounting in the new context.

### Impact Explanation
Each local signer independently tallies peer rejection weight from `block_rejection_signer_addrs` to decide when a blocking minority (>30% weight) has been reached and to call `mark_globally_rejected`. Once this bug triggers for a peer (after their first ever rejection of any block), that peer's weight is permanently un-countable in this signer's local view for every subsequent competing/retried block. In an active reward cycle with reorgs, retried proposals, or forked tenures — all of which are routine — this degrades every signer's ability to correctly reach the rejection threshold on bad/conflicting blocks going forward, which can leave the signer unable to formally reject a block that the network is actually rejecting, i.e. a liveness wedge in the rejection-consensus path (`RewardDistributor`-analog: unauthorized weight retention/loss across contexts due to unscoped state).

### Likelihood Explanation
High reachability: no majority collusion or privileged access is required — it triggers naturally whenever the miner reproposes or forks and any signer previously rejected a different block. I could not find, within the reviewed portion of `signerdb.rs`, a later migration (`ALTER TABLE`) that fixes the primary key on `block_rejection_signer_addrs` to include `signer_signature_hash`; if such a migration exists elsewhere in the file (not captured in the snippets reviewed), this finding could be invalidated. This uncertainty should be resolved by inspecting the full migration list in `stacks-signer/src/signerdb.rs` for `block_rejection_signer_addrs`.

### Recommendation
Change the schema (via a proper migration) so the primary key is the composite `(signer_signature_hash, signer_addr)`, matching how every query already treats it, and add an index on `signer_addr` alone if lookups by peer are needed. Additionally, `store_and_process_block_rejection` should treat a `DBError` from `add_block_rejection_signer_addr` as fatal to processing that rejection (return early) rather than continuing to compute a tally against an incomplete rejection set.

### Proof of Concept
1. Peer signer `S` rejects block `A` (`signer_signature_hash = H_A`) → row `(H_A, S)` inserted into `block_rejection_signer_addrs`.
2. The miner reproposes a different block `B` (`H_B != H_A`, e.g. after a reorg or retry) at the same or a later height.
3. Peer `S` also rejects `B`. `add_block_rejection_signer_addr(H_B, S, ...)` looks up `existing_code` filtered by `(H_B, S)` → finds nothing → attempts `INSERT (H_B, S, code)`.
4. Because the actual table constraint is `PRIMARY KEY(signer_addr)`, this insert collides with the existing `(H_A, S)` row and fails with a uniqueness violation.
5. `store_and_process_block_rejection` logs a warning but does not return, then calls `get_block_rejection_signer_addrs(H_B)`, which does not include `S`'s rejection — `S`'s weight is permanently excluded from `B`'s (and every future distinct block's) rejection tally in this signer's local accounting.
