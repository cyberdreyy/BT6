### Title
`DeleteKey` fails to purge stale confirmations recorded by the deleted key on requests it did not create - (File: `multisig/src/lib.rs`)

### Summary
The `MultiSigRequestAction::DeleteKey` branch in `execute_request` only removes *requests* whose `signer_pk` equals the deleted key, and only resets that key's `num_requests_pk` counter. It never scans `self.confirmations` for entries where the deleted key appears as a **confirming** party on a request created by a different key. As a result, a confirmation contributed by a key can outlive the key's deletion and still count toward `num_confirmations`, letting a request execute with fewer than `num_confirmations` *currently valid* keys.

### Finding Description
The invariant that should hold is: `confirmations(request_id)` should only ever contain public keys that are currently valid access keys on the account, i.e. `∀ pk ∈ confirmations(request_id): pk ∈ live_keys` must hold after every state transition, in particular after a `DeleteKey` execution.

The `DeleteKey` handling is: [1](#0-0) 

This only removes requests where `r.signer_pk == pk` (requests *created* by the deleted key) and resets `num_requests_pk` for that key. It does **not** iterate `self.confirmations` to strip the deleted key's public key from the confirmation sets of *other* requests (created by a different signer) that it had already confirmed via `confirm`: [2](#0-1) 

Exploit flow (with `num_confirmations = N`, keys `K1..Kn` on the account, one of which, `Kv`, is later revoked):
1. `K1` calls `add_request` to create request `R` (e.g. a large `Transfer` to an attacker-controlled account). `R.signer_pk = K1`.
2. `Kv` and other keys call `confirm(R)` until `confirmations(R)` has exactly `N-1` entries, one short of execution, one of which is `Kv`.
3. Later, the legitimate members detect `Kv` is compromised/malicious and submit+confirm a separate `DeleteKey{public_key: Kv}` request. `execute_request` deletes only requests whose `signer_pk == Kv` and resets `num_requests_pk[Kv]`; it does not touch `confirmations(R)`, so `confirmations(R)` still contains `Kv`.
4. Any remaining valid key now calls `confirm(R)`. `confirmations(R).len() + 1 >= N` becomes true (using the stale `Kv` entry as one of the counted confirmations), so `execute_request(R)` runs and the `Transfer` promise is scheduled — even though `Kv`'s access key no longer exists on-chain.

`assert_valid_request` only checks that the request/confirmation entries exist and that predecessor == current account; it never re-validates that each public key recorded in `confirmations` is still a live key, so this guard does not catch the stale entry.

### Impact Explanation
The request executes with only `N-1` *currently authorized* keys' real consent — the `Nth` "confirmation" is a residual artifact of a key that has since been deleted, whose authority was supposed to be fully revoked. This directly moves NEAR (or triggers `AddKey`/`FunctionCall`/other privileged actions) out of the multisig account without the entitled quorum of live members, matching the Critical category "a multisig request executed below `num_confirmations` live members." It is repeatable for any request pattern where a soon-to-be-revoked key confirms a request before its own deletion is processed, and the blast radius is the full balance/authority of the multisig account.

### Likelihood Explanation
This requires no special access beyond what any keyholder already legitimately has: any key added to the multisig (including narrowly-scoped `FunctionCall` keys authorized only to call `add_request`/`confirm`) can contribute a confirmation. The only extra requirement is timing — the malicious/soon-to-be-revoked key confirms a damaging request before the group processes its removal, and the removal request happens to target a different request (or the removal is unrelated to the pending malicious request). Since key deletions are a normal, expected multisig operation (e.g., rotating out a compromised device), this scenario is realistic and cheap to trigger: it costs only ordinary transaction fees and requires no privileged foundation/owner role beyond membership already assumed by the question's premise.

### Recommendation
In the `DeleteKey` branch of `execute_request`, in addition to purging requests created by the deleted key, iterate all remaining requests' `confirmations` sets and remove the deleted public key from each, e.g.:
```rust
for (request_id, mut confs) in self.confirmations.iter() {
    if confs.remove(&pk) {
        self.confirmations.insert(&request_id, &confs);
    }
}
```
This ensures a deleted key's prior confirmations no longer count toward `num_confirmations` for any pending request.

### Proof of Concept
`cargo test` in `multisig`, using the existing `VMContextBuilder`/`testing_env!` harness:
```rust
#[test]
fn test_stale_confirmation_survives_delete_key() {
    let amount = 1_000;
    // 3 keys, num_confirmations = 3
    let k1 = /* Base58PublicKey #1 */;
    let k2 = /* Base58PublicKey #2 */; // will be "deleted"
    let k3 = /* Base58PublicKey #3 */;

    testing_env!(context_with_key(k1.clone().into(), amount));
    let mut c = MultiSigContract::new(3);

    // k1 creates request R (Transfer)
    let r = MultiSigRequest { receiver_id: bob(), actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }] };
    let r_id = c.add_request(r.clone());

    // k2 confirms R
    testing_env!(context_with_key(k2.clone().into(), amount));
    c.confirm(r_id);

    // k3 confirms R -> now 2 confirmations, one short of 3
    testing_env!(context_with_key(k3.clone().into(), amount));
    c.confirm(r_id);
    assert_eq!(c.get_confirmations(r_id).len(), 2);

    // Group deletes k2 via a separate self-request (bundle enough confirmations to reach 3)
    testing_env!(context_with_key(k1.clone().into(), amount));
    let del = MultiSigRequest { receiver_id: alice(), actions: vec![MultiSigRequestAction::DeleteKey { public_key: k2.clone() }] };
    let del_id = c.add_request(del);
    testing_env!(context_with_key(k2.clone().into(), amount));
    c.confirm(del_id);
    testing_env!(context_with_key(k3.clone().into(), amount));
    c.confirm(del_id); // executes DeleteKey{k2}

    // BINDING CHECK: confirmations(R) should no longer contain k2 (k2 has no authority)
    // but the bug means it still does:
    assert!(c.get_confirmations(r_id).contains(&k2)); // demonstrates stale confirmation

    // k1 supplies the final confirmation -> R executes despite k2 being deleted
    testing_env!(context_with_key(k1.clone().into(), amount));
    c.confirm(r_id);
    assert_eq!(c.requests.len(), 0); // R was executed with only 2 live keys' true consent (k1, k3)
}
```
The middle assertion (`confirmations(R)` still contains `k2` after `k2` is deleted) is the direct proof that the equality `confirmations(request_id) ⊆ live_keys` is broken, and the final `confirm` call shows the request executes using that stale confirmation.
