### Title
Unauthorized Fee and Recipient Manipulation in Destination Escrow Deployment - (`contracts/BaseEscrowFactory.sol`)

### Summary
The `createDstEscrow` function in `BaseEscrowFactory` allows any user to deploy a destination escrow by providing an `Immutables` struct. The factory fails to validate that the provided `dstImmutables` (specifically the `parameters` containing fee amounts/recipients and the `maker` address) match the intent of the original swap initiated on the source chain. A malicious actor can front-run a legitimate resolver to deploy a destination escrow with manipulated fee recipients or a different maker address, leading to the theft of protocol fees or user funds.

### Finding Description
In the 1inch cross-chain swap protocol, a swap is initiated via `_postInteraction` on the source chain, which emits a `SrcEscrowCreated` event containing the `srcImmutables` and a `DstImmutablesComplement`. The destination escrow is then deployed using `createDstEscrow`.

The `createDstEscrow` function [1](#0-0)  is external and takes an `IBaseEscrow.Immutables` struct as input. This struct includes `parameters` [2](#0-1) , which `EscrowDst` uses to determine fee amounts and recipients during withdrawal [3](#0-2) .

The factory does not store the expected hash of the destination immutables or verify them against the source chain's state. It only checks that the destination cancellation timelock is not later than the source cancellation timestamp [4](#0-3) . 

Because the escrow address is deterministic based on the hash of the `Immutables` [5](#0-4) , an attacker can:
1. Observe a `SrcEscrowCreated` event.
2. Call `createDstEscrow` with the same `orderHash` and `hashlock` but modified `parameters` (e.g., setting themselves as the `integratorFeeRecipient` or `protocolFeeRecipient`).
3. If the attacker uses the correct `maker` address, the resulting contract address will differ from the one the user expects. However, if the off-chain secret distribution mechanism only checks the `orderHash` and `hashlock`, the resolver might inadvertently fulfill a "malicious" escrow where fees are redirected.

### Impact Explanation
This is a **High** impact vulnerability. An unprivileged actor can steal "unclaimed fee-like value" (protocol and integrator fees) by deploying a destination escrow with altered fee recipients. Furthermore, if the off-chain verification is weak, an attacker could set the `maker` address to themselves, leading to the direct theft of the swap amount once the secret is revealed.

### Likelihood Explanation
The likelihood is **Medium**. It requires the attacker to front-run the legitimate resolver's deployment on the destination chain. Since the `SrcEscrowCreated` event is public on the source chain, an attacker has sufficient information to construct the malicious `createDstEscrow` call on the destination chain before the resolver.

### Recommendation
The `BaseEscrowFactory` should implement a mechanism to verify that the `dstImmutables` provided to `createDstEscrow` are authorized. This can be achieved by:
1. Storing a mapping of `keccak256(orderHash, hashlock) => dstImmutablesHash` in `_postInteraction` and verifying it in `createDstEscrow`.
2. Requiring a signature from a trusted authority (e.g., the factory owner or a 1inch backend) that commits to the valid `dstImmutables` for a given swap.

### Proof of Concept
The following scenario demonstrates the fee theft:
1. A user signs an order for a cross-chain swap.
2. A resolver fills the order, triggering `_postInteraction` on the source chain.
3. The event `SrcEscrowCreated` is emitted, showing `protocolFeeRecipient = 0xProtocol` and `integratorFeeRecipient = 0xIntegrator`.
4. An attacker sees this and calls `createDstEscrow` on the destination chain. They provide the same `orderHash`, `hashlock`, `maker`, `token`, and `amount`, but set `parameters` such that `integratorFeeRecipient = 0xAttacker`.
5. The `EscrowDst` is deployed at `Address_A`.
6. The resolver (or the user) sees an escrow deployed for the `orderHash`. If they only verify the `orderHash` and `amount` at `Address_A` without re-hashing the full `Immutables` and checking the fee recipients, the swap proceeds.
7. Upon `withdraw(secret, immutables)`, the `EscrowDst` contract reads the `parameters` provided in the `withdraw` call (which must match the deployment ones to pass `_validateImmutables`) and sends the integrator fee to `0xAttacker`. [6](#0-5)
