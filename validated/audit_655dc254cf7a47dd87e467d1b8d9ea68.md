### Title
CORS wildcard origin allowlist bypass via naive suffix matching in `isAllowedOrigin` - ([File: core/services/gateway/network/httpserver.go])

### Summary
`isAllowedOrigin` implements wildcard matching for entries like `*.remix.com` by stripping the `*.` prefix and doing a plain `strings.HasSuffix(originHost, allowedHost)` check, with no domain-boundary (dot) verification. This lets an attacker-registered domain such as `evilremix.com` satisfy an allowlist entry of `*.remix.com`, causing `handleRequest` to reflect the attacker's `Origin` in `Access-Control-Allow-Origin` even though it is not actually a subdomain of the intended host.

### Finding Description
In `isAllowedOrigin` [1](#0-0) , once the `*.` prefix is stripped, the remaining check is a bare suffix comparison with no requirement that the character preceding the suffix be a `.`. Consequently `strings.HasSuffix("evilremix.com", "remix.com")` returns `true`, so an origin like `https://evilremix.com` is treated as matching an allowlist entry `https://*.remix.com`, even though `evilremix.com` is a completely unrelated, attacker-controlled domain rather than a subdomain of `remix.com`.

`handleRequest` [2](#0-1)  calls `isAllowedOrigin(origin)` directly against the `Origin` request header and, if it returns true, reflects that origin back verbatim in `Access-Control-Allow-Origin`, plus sets permissive `Access-Control-Allow-Methods`/`Access-Control-Allow-Headers`. This means any page hosted on a domain that merely ends with the configured suffix (not a genuine subdomain) can have its cross-origin `fetch`/`XMLHttpRequest` responses read by client-side JavaScript, defeating the intent of the origin allowlist.

However, the broader "cache poisoning of the CORS header across users" and "automatic browser credentials" framing in the question is not supported by this code: `handleRequest` never sets `Access-Control-Allow-Credentials`, and gateway authentication is via a `Bearer` JWT extracted from the `Authorization` header [3](#0-2) , not cookies. Browsers do not automatically attach `Authorization` headers to cross-origin requests, and without `Access-Control-Allow-Credentials: true`, browsers block script access to credentialed cross-origin responses regardless of `Access-Control-Allow-Origin`. There is also no evidence in this codebase of a shared HTTP cache sitting in front of this server, so the "Vary: Origin cache poisoning across users" mechanism is speculative/infrastructure-dependent and not substantiated by the reachable code path.

### Impact Explanation
The concrete, code-level defect is an origin-allowlist bypass: a disallowed, attacker-controlled origin can be misclassified as allowed due to the missing domain-boundary check, letting that origin's page make cross-origin, CORS-permitted calls to the gateway path (using its own credentials/tokens supplied in JS, since none are auto-attached). This weakens the operator's intended origin restriction (an authorization/allowlist bypass on the CORS control) but does not, by itself, expose another user's session or secret, since no cookie-based credential is auto-forwarded and no `Access-Control-Allow-Credentials` header is issued.

### Likelihood Explanation
Exploitability of the suffix-match bug itself is high and requires no special access — merely registering or controlling a domain such as `evilremix.com` whenever an operator configures `*.remix.com` as an allowed origin. It is deterministic and reproducible via a simple unit test. The additional "credential theft via cache poisoning" scenario described in the question is not reachable from this code path given the absence of cookie-based auth and `Access-Control-Allow-Credentials`.

### Recommendation
Fix the wildcard suffix check in `isAllowedOrigin` to require a domain boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".remix.com"
    if strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
(matching on `.remix.com` instead of `remix.com`) so `evilremix.com` no longer satisfies `*.remix.com`. Additionally, consider adding `Vary: Origin` when the CORS header is conditionally set, to avoid any future caching layer from serving one origin's CORS headers to another, even though no such caching layer is evident in this codebase today.

### Proof of Concept
Add to `core/services/gateway/network/httpserver_test.go` (or a new unit test directly against `isAllowedOrigin` if exported/testable):
```go
func TestHTTPServer_IsAllowedOrigin_WildcardSuffixBypass(t *testing.T) {
    _, handler, url := startNewServer(t, 100_000, 100_000, true,
        []string{"https://*.remix.com"})
    handler.On("ProcessRequest", mock.Anything, mock.Anything, mock.Anything).Return([]byte("response"), 200)

    origin := "https://evilremix.com" // NOT a subdomain of remix.com
    resp, _ := sendRequest(t, url, []byte("{}"), http.MethodPost, &origin)
    // Expected (secure) behavior: header should be empty
    require.Empty(t, resp.Header.Get("Access-Control-Allow-Origin"))
    // Current (buggy) behavior: header incorrectly reflects the attacker origin
}
```
Run against current code to confirm `Access-Control-Allow-Origin: https://evilremix.com` is returned, demonstrating the bypass; after applying the boundary-check fix, the header should be empty.

	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}
