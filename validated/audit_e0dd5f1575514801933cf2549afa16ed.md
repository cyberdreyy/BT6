### Title
Unfunded instant-withdraw receipts can be claimed immediately, draining underlying reserved for other users' funded claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug (CVE-2023-23915) is a shared-cache overwrite: parallel transfers race on one HSTS cache slot, so the most recent transfer wins and an earlier host silently loses its upgrade protection. The analog in `IdleCreditVault` is the inverse asymmetry of the same class: instant-withdraw receipts are tracked per request epoch (`instantWithdrawsRequestsByEpoch`) but are *paid* from a single aggregate slot (`instantWithdrawsRequests`) with no check that the epoch's receipts were actually funded. A request recorded in the current (unfunded) epoch inherits the funding status of the aggregate, exactly like the earlier HSTS entry inheriting/losing state because per-transfer context was collapsed into one slot.

### Finding Description
`requestInstantWithdraw` burns CDO-held strategy tokens, mints a receipt to the user, and accrues the request into `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, and `pendingInstantWithdraws`. The underlying is only delivered later, when the CDO calls `collectInstantWithdrawFunds`, which pulls tokens from the CDO and decrements `pendingInstantWithdraws`.

`claimInstantWithdrawRequest` then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

There is no check that:
- the request's epoch was funded (`collectInstantWithdrawFunds` ran and covered it), or
- `pendingInstantWithdraws` corresponding to this user's claim reached zero.

By contrast, normal withdraws enforce a maturity gate (`epochNumber <= lastWithdrawRequest[_user]` reverts) and loss-adjusted/defaulted receipts route through per-epoch recovery prices. Instant receipts skip all of that: the per-epoch bookkeeping exists only for post-default accounting, while the live claim path pays the aggregate balance from whatever underlying the strategy happens to hold. `_transferFundedClaim` only refuses to spend `defaultRecoveryReserve`; it happily spends underlying that belongs to other users' already-funded `withdrawsRequests`/instant claims or freshly deposited funds awaiting `sendInterestAndDeposits`.

Sequence: epoch N is running (or in buffer with `allowInstantWithdraw`/`allowInstantWithdrawRequest` enabled). The strategy holds underlying backing earlier funded withdraw/instant claims. An unprivileged KYC-passing attacker deposits, calls `requestInstantWithdraw` (receipt minted 1:1, `pendingInstantWithdraws += amount`, nothing funded yet), then calls `claimInstantWithdrawRequest` in the same or next transaction. The claim burns the receipt and transfers `amount` of underlying that was never collected for that request — paid out of other users' funded claim balances. When the honest users later claim, the strategy is undercollateralized and their claims revert or underpay; `pendingInstantWithdraws` still reflects a borrower obligation that was already spent.

### Impact Explanation
Direct theft of funded withdraw/instant claim balances held by the strategy. The stolen amount is bounded only by the strategy's liquid underlying (other users' funded claims plus pending deposits), and the attacker only needs deposit capital equal to the receipt size, which is recovered in the same claim — so the effective cost is gas plus transient capital. This breaks the "one receipt, one funded payout" invariant.

### Likelihood Explanation
Requires `allowInstantWithdraw` mode to be enabled and the strategy to hold underlying (funded claims awaiting user collection, or deposits not yet sent to the borrower). Both are normal operating states. The attack is a two-call sequence executable by any KYC-passing lender with no privileged cooperation and no timing dependence beyond claiming before `collectInstantWithdrawFunds` covers the new request. One caveat I could not fully verify within iteration limits: the exact gating in `IdleCDOEpochVariant.requestInstantWithdraw`/`getInstantWithdrawFunds` (e.g., whether requests are restricted to the buffer phase). Even if requests are buffer-only, a request-then-claim before `startEpoch` funding still exercises the same unfunded-claim path whenever the strategy holds underlying, since `claimInstantWithdrawRequest` has no epoch or funding gate at all.

### Recommendation
Mirror the funded-accounting used for normal withdraws: track funded vs unfunded instant receipts per epoch, e.g., gate `claimInstantWithdrawRequest` on the user's request epochs being fully collected (`instantWithdrawClaimsByEpoch[epoch] == collected` or a per-epoch funded flag set in `collectInstantWithdrawFunds`), or decrement a per-user funded counter at collection time and only pay the funded portion. Alternatively, revert in `claimInstantWithdrawRequest` when `pendingInstantWithdraws` indicates the aggregate instant queue is not yet funded.

### Proof of Concept
A reproducible Foundry PoC (fork or in-repo harness in `test/foundry/IdleCreditVault.t.sol` style): enable instant withdrawals; user A requests a normal/instant withdraw, epoch stop funds it via `collectWithdrawFunds`/`collectInstantWithdrawFunds` so the strategy holds underlying; attacker B deposits, calls `requestInstantWithdraw(amount)`, then immediately calls `claimInstantWithdrawRequest` before any `collectInstantWithdrawFunds` for that request; assert B received underlying while `pendingInstantWithdraws` still includes B's basis and A's subsequent claim fails or is underpaid.
