### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing requests to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary

### Finding Description
The intended invariant of the multisig contract is that a request executes only once at least `num_confirmations` **currently valid** members have approved it — i.e. `confirmations.len() >= num_confirmations` should imply that all of those confirmations came from accounts/keys that are still members at execution time.

`confirm()` only validates that the *calling* member is currently valid via `current_member()` [1](#0-0) , and simply counts the size of the `confirmations` `HashSet` stored for the request:

```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
}
``` [2](#0-1) 

When a member is removed via `delete_member`, only the requests **originated by that member** have their confirmations purged (`filter_map(|(k, r)| if r.member == member { Some(k) } else { None })`); confirmations that member previously cast on requests originated by *other* members are never removed:

```
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&member.to_string());
    self.members.remove(&member);
    ...
}
``` [3](#0-2) 

So the equality that should hold — `confirmations counted == confirmations from accounts that are still members` — is broken: a stale confirmation entry (member string) from an account that is no longer in `self.members` remains in the `confirmations` map for any request it did not itself originate, and is still counted by `confirm()`'s threshold check.

The same pattern exists in the older, key-based `multisig/src/lib.rs`: `DeleteKey` only purges requests where `r.signer_pk == pk` [4](#0-3) , leaving that key's confirmations on other members' requests intact, and `confirm()` there likewise only checks set size [5](#0-4) .

### Impact Explanation
This lets a multisig request be executed with fewer live/current confirmers than `num_confirmations` requires. For example, with 3 members and `num_confirmations = 2`: member A adds a `Transfer` request; member B (not the originator) confirms it (1 confirmation, from B). Before a second live confirmation is added, B is removed from the multisig via a separate governance action (B is not the request's originator, so B's confirmation on A's request is never cleared). A remaining live member, C, then confirms the still-pending request: `confirmations.len() + 1 = 2 >= 2`, and the request (e.g. a `Transfer` of NEAR) executes — authorized in substance by only one currently valid member (C) plus a stale confirmation from a now-removed member (B). This is exactly the "a multisig request executed below threshold" scenario, and can move NEAR (or execute privileged actions such as `AddKey`/`AddMember`) with insufficient live authorization — a Critical impact per the custody-binding definition (confirmations counted vs. live members).

### Likelihood Explanation
Membership changes (`DeleteMember`/`DeleteKey`) are an expected, normal multisig operation (e.g. rotating out a compromised or departing signer). Any request that has received at least one confirmation from a member who is *not* its originator, and that member is later removed before the request is deleted/executed, will silently retain that stale confirmation. No special privilege beyond normal multisig member actions is required to trigger the condition; it can also be exploited intentionally by a member who anticipates their own removal by pre-confirming pending requests they didn't originate.

### Recommendation
When removing a member (`delete_member`/`DeleteKey`), iterate over **all** requests (not just those originated by the removed member) and strip that member's/key's entry from each request's `confirmations` set (or track confirmations by member and re-validate membership at confirm/execute time), so that only confirmations from currently valid members are ever counted toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 3 members `A, B, C` and `num_confirmations = 2` via `new`.
2. `A` calls `add_request` with a `Transfer` action (request not confirmed yet).
3. `B` calls `confirm(request_id)` → `confirmations = {B}`, request not yet executed (1 < 2).
4. Via a separate, properly-confirmed request, execute `DeleteMember { member: B }` — `delete_member` only clears requests where `r.member == B`; since the transfer request was authored by `A`, its `confirmations = {B}` entry is left untouched, and `B` is removed from `self.members`.
5. `C` (a live member) calls `confirm(request_id)` → `confirmations.len() + 1 = 2 >= num_confirmations (2)` → `execute_request` runs the `Transfer`, even though only one currently valid member (`C`) actually approved it at execution time (`B`'s stale confirmation from before removal is what made up the count).

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
