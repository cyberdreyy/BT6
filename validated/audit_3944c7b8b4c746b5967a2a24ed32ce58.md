### Title
Failed `new` call leaves attacker's deposit both refunded and stranded in an uninitialized lockup account - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` bundles `create_account`, `deploy_contract`, `transfer`, and `function_call("new", …)` into a single Promise/receipt sent to the derived lockup account, then schedules `on_lockup_create` to refund `attached_deposit` if the receipt fails. Because a NEAR receipt's actions are applied sequentially and are not rolled back as a unit when a later action in the same receipt fails, an attacker can craft `create()` arguments so that `create_account`/`transfer` succeed (funding the new account) while the trailing `function_call("new", …)` fails, causing `on_lockup_create` to additionally refund the same `attached_deposit` to the caller from the factory's own balance.

### Finding Description
The invariant claimed is: `refunded_amount + NEAR_left_in_created_account == attached_deposit`. The code path is: [1](#0-0) 

`Promise::new(lockup_account_id).create_account().deploy_contract(CODE).transfer(attached_deposit).function_call(b"new", ...).then(on_lockup_create(...))`. All four actions (`create_account`, `deploy_contract`, `transfer`, `function_call`) are batched into one receipt targeting the newly derived `lockup_account_id`. `on_lockup_create` only checks `is_promise_success()` on the aggregate receipt outcome: [2](#0-1) 

If the receipt is reported as failed (`is_promise_success() == false`), `on_lockup_create` unconditionally transfers the *entire* `attached_deposit` back to `predecessor_account_id` — paid out of the factory contract's own balance, not recovered from the failed receipt. The code assumes that a failed receipt means none of its actions took effect, i.e., that the `transfer` action was also undone. That assumption does not hold: actions within one receipt execute in order and commit their effects progressively; when a later action (the `function_call` to `new`) fails (e.g., due to insufficient attached gas relative to `gas::LOCKUP_NEW = 25 TGas`, or a panic in `LockupContract::new`'s asserts such as the account-ID validity checks or the vesting/foundation-account consistency checks visible in `lockup/src/lib.rs` lines 191-233), the preceding `create_account`, `deploy_contract`, and `transfer` actions are not reverted. The result: the newly created account keeps the transferred NEAR, but `on_lockup_create` still refunds the full `attached_deposit` to the caller — doubling the payout instead of preserving the invariant.

Because the `new` call never completes, `LockupContract::new`'s `#[init]` guard never sets `state_exists()`, so any account (including the attacker) can subsequently call `new` on that funded, empty-state lockup account and claim ownership of the NEAR that is already sitting there, since no access key was ever added to that account and `new` is a public, unauthenticated `#[init]` method. None of the existing guards (`assert_self()`, `is_promise_success()`) address this because they only check whether the aggregate receipt succeeded, not whether the deposit-carrying action within that receipt was independently applied.

### Impact Explanation
The factory contract's NEAR balance is drained by `attached_deposit` per failed attempt (the improperly issued refund), while an equivalent amount of NEAR is simultaneously stranded in (and later claimable from) an attacker-controlled, uninitialized lockup account. This matches the Critical category: "NEAR moved out of a … lockup … by a party not entitled to it" and "a lockup deployed with parameters its rightful creator never chose" — here the factory's treasury pays out funds it should not have paid, and separately the abandoned account can be re-initialized and drained by anyone, including the attacker. This is repeatable per call to `create()` with a large `attached_deposit`, limited only by the attacker's available NEAR and the factory contract's balance to refund from, and can be repeated across multiple crafted `owner_account_id`s to derive multiple distinct target accounts.

### Likelihood Explanation
The attacker only needs to be an unprivileged NEAR account that can call the public, `#[payable]` `create()` method with `attached_deposit >= MIN_ATTACHED_BALANCE`, and choose parameters that make `LockupContract::new` fail deterministically after account creation/funding (invalid `staking_pool_whitelist_account_id`, or a vesting/foundation-account mismatch such as supplying `vesting_schedule` with no reachable `foundation_account_id`, or simply relying on gas exhaustion since `gas::LOCKUP_NEW` is fixed at 25 TGas). No special privileges, keys, or foundation/owner/multisig role are required, matching the attacker model in scope.

### Recommendation
Do not batch the funding `transfer` and account creation with the `function_call("new", …)` in a way that assumes atomic rollback. Instead: (1) verify after failure whether the account/contract was actually created and funded (e.g., via `Promise::new(lockup_account_id).delete_account(...)` recovery, or splitting the deposit transfer into a second receipt sent only after the `new` call succeeds), or (2) have `on_lockup_create` check the actual account balance of `lockup_account_id` before refunding, refunding only the amount not already stranded, or (3) restructure so the `transfer` of the bulk deposit happens only in a follow-up receipt gated on the success of `create_account + deploy_contract + function_call("new")`.

```rust
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```
