## Finding: Push-based token transfer to receiver in `_solveRequestDirect` lacks blacklist fallback, unlike the refund path

### Title
Permissionless redeem solve in `ProvisionerV2.solveRequestsDirect` reverts and temporarily freezes redemption when `request.receiver` is a blacklisted address for the redeem token - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2._solveRequestDirect` pushes the redeem token directly to `request.receiver` via `token.safeTransferFrom(msg.sender, request.receiver, request.tokens)` with no fallback, while the parallel refund/cancel paths (`_transferWithFallback`) explicitly guard against a non-cooperative or blacklisted receiver by falling back to the requester. This is the exact "push without pull-fallback to a possibly-blacklisted receiver" pattern from the reported liquidation bug, reproduced in a bounty-scoped, ordinary-user-reachable function.

### Finding Description
`solveRequestsDirect` is a fully permissionless entry point (no `requiresAuth`) intended for anyone to solve deposit/redeem requests peer-to-peer [1](#0-0) . It delegates to `_solveRequestDirect`, and for an unexpired redeem request it directly transfers the redeem token from the solver to `request.receiver`: [2](#0-1) 

This is a raw `safeTransferFrom`/`safeTransfer` with no try/catch or fallback recipient, in contrast to the expired/refund branch of the very same function, which uses `_transferWithFallback` to fall back to the original requester if the receiver-side transfer fails: [3](#0-2) [4](#0-3) 

An identical asymmetry exists in the guardian-only `solveRequestsVault` path (`_solveRedeemVaultAutoPrice` / `_solveRedeemVaultFixedPrice`), which use a bare `token.safeTransfer(request.receiver, tokenOutAfterTip)` in the active branch but `_transferWithFallback` in the expired branch: [5](#0-4) [6](#0-5) . That path is privileged and out of scope per the prompt's exclusions, but it confirms the systemic root cause: the "in-progress" solve branches never use the fallback helper, only the "expired" branches do.

Root cause: any ordinary user can call `requestRedeem(token, ..., receiver)` specifying a `receiver` different from (or the same as) themselves [7](#0-6) . If the redeem `token` is USDC (or another asset with an address-level transfer restriction such as blacklisting/freezing) and that `receiver` address becomes blacklisted at any point before the request's `deadline`, every attempt by any solver to call `solveRequestsDirect` for that request will revert at the `token.safeTransferFrom(msg.sender, request.receiver, request.tokens)` line, because the underlying ERC20 blocks transfers to/from a blacklisted address. The failed guard is the absence of the same `_transferWithFallback` pattern used elsewhere in the contract for exactly this scenario.

### Impact Explanation
The user's escrowed vault units (locked in the Provisioner since `requestRedeem` transferred them in) cannot be redeemed for tokens via the direct-solve path while the request is unexpired and the receiver remains blacklisted. This is a temporary freeze of the pending redeem, not a permanent loss: once `request.deadline` passes, `cancelRequest`/`refundRequest` correctly use `_transferWithFallback` and would return the vault units to the fallback address (`msg.sender`/`request.user`). The impact therefore maps to a bounded/temporary denial-of-service on redemption liquidity for the affected receiver, consistent with a Medium-severity temporary freeze of user funds.

### Likelihood Explanation
Requires: (1) the redeem token supports address-level blocking (USDC does), (2) the `receiver` of a `requestRedeem` call becomes blacklisted before the `deadline`. No privileged role is needed to trigger the revert — any user can create the request, and any third-party solver attempting `solveRequestsDirect` will simply fail until the deadline passes. This mirrors the low-likelihood/high-impact profile of the original report.

### Recommendation
Route the active-branch transfer in `_solveRequestDirect` (and analogously in the vault solve paths) through the same `_transferWithFallback` helper already used in the refund branches, or adopt a pull-based claim pattern for the redeem token so a blacklisted receiver cannot block settlement of an otherwise-valid solve.

### Proof of Concept
1. Deploy `ProvisionerV2` wired to a mock USDC-like token implementing a `blacklist(address)` function that reverts on transfers to/from blacklisted addresses.
2. User calls `requestRedeem(token, unitsIn, minTokensOut, solverTip, deadline, maxPriceAge, false /*isFixedPrice*/, receiver)` with `receiver` set to an address the token issuer will later blacklist.
3. Blacklist `receiver` on the mock token.
4. As a solver, call `solveRequestsDirect(token, [request])` before `deadline`; assert the call reverts inside `_solveRequestDirect`'s `token.safeTransferFrom(msg.sender, request.receiver, request.tokens)`.
5. Assert the request hash remains active (`asyncRequestHashes[hash] == true`) and the user's units remain escrowed in the Provisioner, confirming the redeem is stuck until `deadline` — demonstrating the freeze — then show `cancelRequest`/`refundRequest` after expiry succeeds via `_transferWithFallback` to the fallback address, confirming the asymmetry versus the active-branch push.

    /// @inheritdoc IProvisionerV2
    function solveRequestsDirect(IERC20 token, RequestV2[] calldata requests) external nonReentrant {
        // Requirements: vault is not paused in the priceAndFeeCalculator
        require(!PRICE_FEE_CALCULATOR.isVaultPaused(MULTI_DEPOSITOR_VAULT), Aera__PriceAndFeeCalculatorVaultPaused());

        uint256 length = requests.length;
        TokenDetailsV2 storage tokenDetails = tokensDetails[token];
        for (uint256 i = 0; i < length; i++) {
            RequestV2 calldata request = requests[i];
            RequestType requestType = request.requestType;

            // Requirements: direct solves can only solve fixed price requests
            require(!_isRequestTypeAutoPrice(requestType), Aera__AutoPriceSolveNotAllowed());

            if (_isRequestTypeDeposit(requestType)) {
                // Requirements: async deposit is enabled
                require(tokenDetails.asyncDepositEnabled, Aera__AsyncDepositDisabled());
            } else {
                // Requirements: async redeem is enabled
                require(tokenDetails.asyncRedeemEnabled, Aera__AsyncRedeemDisabled());
            }

            // Requirements + Effects + Interactions: solve direct request
            _solveRequestDirect(token, request);
        }
    }

    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
