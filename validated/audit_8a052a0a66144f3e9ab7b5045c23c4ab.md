### Title
Multisig `confirm()` counts confirmations from members already removed by `DeleteKey`/`DeleteMember`, allowing a request to execute below the live-member threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
In both `multisig/src/lib.rs` and `multisig2/src/lib.rs`, when a key/member is removed via `MultiSigRequestAction::DeleteKey` (`multisig`) or `DeleteMember` (`multisig2`), the contract only purges confirmations for requests that the removed member itself *created* (`r.signer_pk == pk` / `r.member == member`). It never scans the `confirmations` map to strip the removed member's entry from *other* pending requests they had already confirmed. `confirm()` then counts `confirmations.len() + 1 >= num_confirmations` without re-validating that every entry in the confirmation set still corresponds to a live member. This is structurally the same bug class as the reported LayerZero issue: a piece of state produced under a previously-valid trust relationship (a confirmation from a member / a queued message from a trusted remote) is not invalidated when that trust is revoked, and can later be “replayed” to help satisfy an authorization check.

### Finding Description
- `multisig/src/lib.rs` `execute_request()`, `DeleteKey` branch (lines 198-216): filters and removes only requests where `r.signer_pk == pk` (requests *created by* the deleted key), and clears confirmations only for those specific request IDs. `multisig2/src/lib.rs` `delete_member()` (lines 356-379) does the analogous filtering by `r.member == member`. [1](#0-0) [2](#0-1) 
- Confirmations are stored independently, keyed by `request_id`, as a `HashSet` of the confirming member's identity (`PublicKey` in `multisig`, stringified `MultisigMember` in `multisig2`): [3](#0-2) [4](#0-3) 
- `confirm()` never re-checks that the accumulated confirming identities are still current members; it only compares the size of the set against `num_confirmations`: [5](#0-4) 

Binding broken: `confirmations counted == live members who authorized` should hold at execution time. Instead, `confirmations counted ⊇ {stale entries from removed members} ∪ {live members}`, so a request can be executed with fewer *currently authorized* confirmations than `num_confirmations` requires.

### Impact Explanation
This falls under the “Critical” bucket explicitly called out in scope: *a multisig request executed below threshold*. If a member key is compromised, used to confirm a malicious `Transfer`/`FunctionCall`/`AddKey` request, and is subsequently revoked by the remaining honest members (the natural incident-response action, analogous to removing a compromised LayerZero remote), the malicious request's confirmation from that now-revoked key is **not removed**. A single additional honest confirmation (which the honest signers believe is only the 2nd-of-3, say) is enough to push the stale set over `num_confirmations` and execute the request — including moving funds — even though only one currently-authorized member actually confirmed it "live" at execution time.

### Likelihood Explanation
The precondition (a member key becomes compromised, confirms a request, and is then removed) mirrors the exact scenario described in the report (“Contract X … set up as a trusted remote … several messages … stored … owner removes Contract X as trusted remote … malicious actor can still call `retryMessage()`”). No redeploy, foundation action, or out-of-scope privilege is required beyond the multisig's own documented remediation workflow (removing a suspected-compromised key), which is a foreseeable, expected use of `DeleteKey`/`DeleteMember`. The remaining honest signers have no visibility that a stale confirmation from a revoked key is still "counted" unless they inspect `get_confirmations` and manually correlate it against `get_members`/live keys.

### Recommendation
When removing a key/member (`DeleteKey` / `DeleteMember`), iterate over all pending requests' confirmation sets (not just requests created by that member) and strip the removed identity from each. Alternatively, at `confirm()`/execution time, filter the confirmation set to only those confirmers still present in `members` (or the current valid-access-key set for `multisig`) before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 3 members `A`, `B`, `C` and `num_confirmations = 2`.
2. `A`'s key is compromised by an attacker. Attacker calls `add_request` (as `A`) to create a malicious `Transfer` request `R`, then `confirm(R)` — `confirmations[R] = {A}` (1/2).
3. Honest members `B`/`C` detect the compromise and submit+confirm a `DeleteMember { member: A }` request — this reaches threshold (2 confirmations from `B`,`C`) and executes, removing `A` from `members` and revoking `A`'s access key. Per `delete_member()` (`multisig2/src/lib.rs:356-379`), only requests *created by* `A` are purged; `R` (created and confirmed by `A`, but here assume created by `B` and merely confirmed by `A`) is untouched, and `confirmations[R]` still contains `A`.
4. Later, `B` (unaware `A`'s confirmation is stale) confirms `R` as the "2nd of 2" needed. `confirm()` computes `confirmations.len() + 1 >= num_confirmations` → `1 + 1 >= 2` → true, and `execute_request(R)` fires the `Transfer`, moving funds out of the multisig account with only one currently-live member's confirmation actually contributing legitimate authorization at execution time.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
