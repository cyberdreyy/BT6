### Title
EI-role bypass of "no EI job runs by int ID" check via shared `SessionUserKey` role forgery in `AuthenticateExternalInitiator` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets `SessionUserKey` to a synthetic `&clsessions.User{Role: UserRoleRun}` for external-initiator (EI) credentials, causing `auth.GetAuthenticatedUser` to return `isUser == true` for EIs exactly as it does for real users. This makes the `isUser` check in `PipelineRunsController.Create` (intended to exclude EIs from int-ID job runs) a no-op, allowing any EI credential holder to trigger `RunJobV2` on arbitrary integer job IDs.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered in the `userOrEI` group with `auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` and wrapped in `auth.RequiresRunRole(prc.Create)`. [1](#0-0) 

Inside `AuthenticateExternalInitiator`, after validating the EI's access key/secret, the code explicitly injects a fake user object under the same session key used for real authenticated users: [2](#0-1) 

`GetAuthenticatedUser` simply reads that key and type-asserts to `*clsessions.User`, with no way to distinguish an EI-derived user from a genuinely authenticated user: [3](#0-2) 

`RequiresRunRole` already requires `GetAuthenticatedUser` to succeed with role ≥ `run` before invoking the handler at all: [4](#0-3) 

In `PipelineRunsController.Create`, the comment states "only users are allowed to run jobs using int IDs - EIs not allowed," and the code re-checks `isUser` from `GetAuthenticatedUser` as if it could still distinguish EIs: [5](#0-4) 

Because `RequiresRunRole` already guarantees `isUser == true` (with `Role: UserRoleRun` for EIs) before `Create` runs, this second check can never actually be false for any request that reaches the handler — it does not differentiate EI-derived pseudo-users from real users. The only surviving restriction in the function is the UUID/webhook-job rejection (lines 103-107); once that's bypassed by using an int job ID, any authenticated EI can call `RunJobV2` on any job ID, not just a job legitimately tied to that EI. There is no additional check anywhere in this path that ties the specific EI identity (`bridges.ExternalInitiator`, retrievable via `GetAuthenticatedExternalInitiator`) to the target job ID.

### Impact Explanation
An external-initiator credential — intended to be scoped to triggering the specific webhook job it was created for — can now trigger execution of any job in the node by integer ID via `RunJobV2`, bypassing the intended access-control boundary documented in the code comment. Depending on job types configured on the node (e.g. jobs with on-chain transaction/write tasks, VRF, OCR, DirectRequest-adjacent, ETH tx tasks), this can lead to unauthorized job execution and potential unauthorized fund movement or unintended on-chain transactions, which maps to Chainlink's "unauthorized job run" / authorization-bypass bounty impact class.

### Likelihood Explanation
Exploitation requires only possession of any valid External Initiator access key/secret (`EI-ACCESSKEY`/`EI-SECRET` headers) — the lowest-privileged credential class supported by the node's V2 API, not an admin/user session or API token. The attack is a single HTTP `POST /v2/jobs/:intID/runs` request with no additional preconditions, and is fully repeatable/scriptable.

### Recommendation
In `PipelineRunsController.Create`, do not rely on `auth.GetAuthenticatedUser` alone to distinguish EIs from real users, since `AuthenticateExternalInitiator` writes to the same `SessionUserKey`. Instead check `auth.GetAuthenticatedExternalInitiator(c)` and explicitly reject the request (or restrict it to jobs tied to that EI) when an EI identity is present, regardless of the synthetic user object. Alternatively, introduce a distinct session key/type for EI-derived pseudo-users (e.g. do not set `SessionUserKey` in `AuthenticateExternalInitiator`, and instead have `RequiresRunRole` accept either a real user with run role or a validated EI-to-job association).

### Proof of Concept
Handler-level integration test plan (Go, in `core/web/pipeline_runs_controller_test.go` style):
1. Set up an app with `cltest.NewApplicationWithConfig`, create a non-webhook job (e.g. OCR or DirectRequest) with integer `jb.ID`, as in `setupPipelineRunsControllerTests`.
2. Register an `ExternalInitiator` via `bridges.NewExternalInitiator`/DB insertion (see `core/bridges/external_initiator_test.go` helpers) unrelated to `jb.ID`.
3. Build an HTTP client (not using `app.NewHTTPClient`, which uses session/token auth) that sets `EI-ACCESSKEY` / `EI-SECRET` headers matching the created EI's credentials.
4. Send `POST /v2/jobs/{jb.ID}/runs` with this EI-authenticated client.
5. Assert the response is `http.StatusOK` (or `StatusCreated`) with a `pipelineRun` resource returned, and that `prc.App.PipelineORM().FindRun` shows a genuinely created run for `jb.ID` — proving the EI triggered `RunJobV2` despite the comment's intent to disallow EIs from running jobs by int ID.
6. Compare against expected behavior: the assertion should fail (i.e., expect `StatusUnauthorized`/`StatusForbidden`) if the fix described above is applied.

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)

	}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
