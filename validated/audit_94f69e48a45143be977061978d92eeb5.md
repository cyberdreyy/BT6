### Title
Stale cross-tenure conflicts skip `conflict_still_blocks`/`reorg_permit_stands` entirely, letting a signer sign a sibling block the node still serves as canonical - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`handle_block_pre_commit` only asks the node whether a conflicting, previously-signed block is still live (`conflict_still_blocks`) or reorg-sanctioned (`reorg_permit_stands`) when that conflict is still "fresh" (`last_endorsed > freshness_cutoff`). The moment a conflict crosses the staleness cutoff, it is dropped from the `find()` guard with **no** node query at all, and the only remaining check (`conflicts.iter().any(...)` at the tenure-tip lookup) is restricted to conflicts sharing the *proposed block's own tenure*. A conflict recorded in a third, unrelated tenure at the same/higher height is therefore released purely by the passage of `tenure_last_block_proposal_timeout`, independent of whether the node still serves that older block as canonical.

### Finding Description
`get_signed_conflicts` returns every previously signed/accepted block at the same or higher height "in ANY tenure" [1](#0-0) . The equivocation guard evaluates these conflicts in two disjoint stages:

1. Fresh-conflict stage: only conflicts with `last_endorsed > freshness_cutoff` are passed through `reorg_permit_stands` and `conflict_still_blocks` (which query the node for sortition/tenure-tip liveness) — a conflict is refused only if it is fresh *and* unsanctioned *and* still live: [2](#0-1) 

2. Own-tenure stale stage: after the fresh check, the code separately looks only at conflicts whose `consensus_hash == block_info.block.header.consensus_hash` (i.e., the *same* tenure as the block being signed) and, if any exist and are unsanctioned, asks the node for that tenure's tip height: [3](#0-2) 

A conflict that is (a) stale (`last_endorsed <= freshness_cutoff`) and (b) recorded against a *third* tenure — neither the block's own tenure nor its parent tenure — is excluded from stage 1 (not fresh) and invisible to stage 2 (different `consensus_hash`). No call to `conflict_still_blocks`, `reorg_permit_stands`, or any node lookup occurs for it; it simply stops blocking as soon as the clock passes `tenure_last_block_proposal_timeout`. The design docs explicitly acknowledge that the earlier chainstate re-check (`check_block_against_signer_db_state`, run immediately before this code) also only ever inspects one tenure (the block's own or its parent's), so "a signed sibling at the same height in a third tenure is invisible to it" [4](#0-3) , and staleness for cross-tenure conflicts is intentionally treated as sufficient without a node re-check [5](#0-4) . That reasoning silently assumes the earlier chainstate check already "settled" whether the block may replace what the third tenure built — but it did not, by the doc's own admission.

Exploit flow: a party that wins one sortition slot (T1) gets a normal block A signed at height H by the honest signer set. Later a second sortition (T3, at the same effective height due to a burn-chain fork the attacker can trigger by winning one more slot with their own BTC) proposes a competing block C at height H whose tenure is neither T1 (A's tenure) nor the parent tenure the node currently associates with C. The attacker (a single miner/slot) simply re-broadcasts/re-times C's `BlockProposal` until after `tenure_last_block_proposal_timeout` has elapsed since A's `signed_self`/`signed_group` timestamp. Once that window passes, the per-signer guard for the A/C conflict is bypassed with zero verification that T1's sortition is orphaned or that A is dead — it is bypassed purely by elapsed wall-clock time, not by any node-derived proof, unlike every other conflict-clearing path in this guard.

### Impact Explanation
This breaks the equivocation guard's core safety property: a signer producing two conflicting signatures at the same chain height, in different tenures — the "signer signing a conflicting block (chain safety)" case called out as Critical. Because staleness is a purely local timestamp comparison (each signer's own clock/`tenure_last_block_proposal_timeout`), different signers can cross the cutoff at different times, so the population of signers that end up signing A versus C can diverge, creating the potential for two blocks at the same height to independently accumulate weight toward the 70% threshold — a chain split / conflicting-canonical-block scenario. The vulnerability is repeatable on every occurrence of a stale, third-tenure sibling.

### Likelihood Explanation
Preconditions: (1) an existing signed conflict in a tenure that is neither the parent nor own tenure of the newly-proposed block, (2) enough elapsed time for that conflict to cross `tenure_last_block_proposal_timeout` (a config value, default on the order of minutes/hours), and (3) the node's validation endpoint accepting the new block as valid (implying some fork/tenure transition has genuinely occurred at the node level, which a single-slot attacker with the ability to win a BTC block can trigger). The attacker's cost is exactly what the threat model allows: one miner slot plus gossiped `BlockProposal`s and normal StackerDB traffic — no privileged key, no majority weight, and no local access. The condition is naturally reachable any time a slow-forming reorg outlasts `tenure_last_block_proposal_timeout`, and an attacker can deliberately widen this window by delaying/holding their proposal until after the cutoff.

### Recommendation
Remove the tenure-scoped restriction on the post-staleness node check: for *every* stale conflict (own-tenure or cross-tenure) that is not reorg-permitted, still call `conflict_still_blocks` (or an equivalent node-derived liveness check) before allowing the signature, instead of only doing this for same-tenure stale conflicts. Staleness (a local timestamp) should never, by itself, substitute for the node-derived proof that a conflicting tenure is actually dead.

### Proof of Concept
Extend the existing sibling-scenario test harness (`stacks-signer/src/v0/tests.rs`, see `run_sibling_scenario`/`run_cross_tenure_scenario`, and `stale_sibling_replaced_when_canonical_tip_below` / `conflict_whose_sortition_is_canonical_still_blocks_signing` at [6](#0-5)  and [7](#0-6) ) with a new scenario:

1. Sign block A in tenure T1 at height H (`assert_a_signed`).
2. Advance the mock clock past `tenure_last_block_proposal_timeout` so A's conflict record is stale.
3. Construct block C in tenure T3 (`consensus_hash` different from both T1 and C's own designated parent tenure — i.e., a genuine third tenure relative to A), at height H, and drive it through `handle_block_pre_commit` with the pre-commit threshold met.
4. Mock the stacks client such that `get_sortition_by_burn_hash`/`get_tenure_tip` for T1 (A's tenure) report A's tenure as **still canonical and reaching height H** (i.e., `conflict_still_blocks` would return `true` if it were called).
5. Assert that despite T1/A being fully live per the mocked node, `info_c.signed_self.is_some()` becomes true — proving the signer signed C without ever consulting `conflict_still_blocks` for the cross-tenure stale conflict, in contrast to the fresh-conflict case (`conflict_whose_sortition_is_canonical_still_blocks_signing`) where the identical node state correctly blocks the signature.

This demonstrates the equality that should hold — "a conflict that the node reports as still live must block signing regardless of its `last_endorsed` freshness, unless it lies in the block's own tenure and is covered by the tip check, or is reorg-permitted" — is violated once the conflict is both stale and cross-tenure.

```markdown
Order matters here: the chainstate re-check runs first and produces an explicit
(sticky) rejection when the block now conflicts with a signed one. The conflict
guard behind it is the silent backstop for what that re-check cannot see, and
silence keeps the door open to sign later once the conflict goes stale. Two
blind spots make the guard necessary:

- the re-check only ever looks at _one_ tenure (a tenure-change block's parent,
  or any other block's own), so a signed sibling at the same height in a third
  tenure is invisible to it;
- the `DuplicateBlockFound` check that would catch a second block in the same
  tenure lives in `check_proposal` and runs only at proposal arrival, never
  again. A block that crosses the pre-commit threshold minutes later has no
  other guard, which is what the own-tenure branch above covers.
```

```markdown
A conflict is any block a signature was ever put over — ours, or a group
threshold we observed — whatever its state now. In particular rejection, even
_global_ rejection, does not clear one: a rejection is a revocable opinion,
while a signature is a bearer instrument that can still be aggregated toward
the 70% threshold if rejecting signers change their minds. Only staleness or
node-derived death (the two questions above) clears a conflict.

Whenever the node cannot be asked, the conflict keeps blocking: that only delays
the replacement until the signature goes stale, whereas wrongly signing cannot be
taken back. The one recorded exception is a tenure whose reorg we sanctioned
under the reorg-timing rules (section 8): there the node still serves the
conflict as fully live — replacing it is only legitimate because we permitted it
— so no question asked of the node about the _conflict_ could clear it. Instead
the record carries the permitting tenure's sortition, and `reorg_permit_stands`
asks the node whether that sortition is still canonical: while it is, the
conflict is excluded outright; if a burnchain fork orphaned it, the reorg we
sanctioned can no longer happen and the conflict gets its voice back. A false
404 there needs no tip-height guard — it merely restores a conflict, which at
worst delays the replacement. For the own-tenure question below, an unreachable
node is instead treated as unconfirmed and the signature goes out.
```
