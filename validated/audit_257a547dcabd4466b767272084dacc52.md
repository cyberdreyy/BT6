### Title
Inconsistent rounding between block-approval threshold and global-state agreement threshold - ([File: libsigner/src/v0/signer_state.rs])

### Summary
The signer network computes the "70% supermajority" threshold in two places that are supposed to represent the same constant, `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD = 7` (i.e. 70%), but with different rounding: `NakamotoBlockHeader::compute_voting_weight_threshold` (used for actual block-signature/pre-commit consensus) rounds **up** (ceiling), while `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` (used for the signer set's shared "global state machine" — current miner, burn view, tx-replay-set, protocol version) rounds **down** (floor). This is structurally the same class of bug as the TokenSoft `tokensToVotes` issue: the same nominal fraction is computed via two code paths that disagree by rounding, producing an equality break between "global state agreed" and "block approved."

### Finding Description
`compute_voting_weight_threshold` computes a *ceiling*-rounded threshold: [1](#0-0) 

This function is the one used both by consensus-critical `verify_signer_signatures` (node/chainstate side) and by `stacks-signer/src/v0/signer.rs` when deciding whether the pre-commit or signature weight is sufficient to sign/broadcast a block: [2](#0-1) [3](#0-2) 

In contrast, `GlobalStateEvaluator::reached_agreement` / `reached_disagreement` — used to decide the signer set's "global state" (which miner is current, which burn view is canonical, which tx-replay-set/protocol version is agreed) — use plain integer division (*floor*), with no ceiling adjustment: [4](#0-3) 

`determine_global_state`, `determine_latest_supported_signer_protocol_version`, and `determine_global_burn_view` all gate on `reached_agreement`, and this global state is what `check_block_against_global_state` uses to decide whether a proposal is valid: [5](#0-4) [6](#0-5) 

For any `total_weight` such that `total_weight * 7` is not a multiple of 10 (the common case), `floor(total_weight*7/10) < ceil(total_weight*7/10)`. E.g. for `total_weight = 11`: `compute_voting_weight_threshold` requires **8** (72.7%), while `reached_agreement` is satisfied at **7** (63.6%). This is confirmed by the existing test suite, which explicitly pins the floor-based partition of `reached_agreement`/`reached_disagreement` as `[0,30%]`, `(30%,70%)`, `[70%,total]` using strict `>=`/`>` on the *floor*-divided values, with no ceiling correction: [7](#0-6) 

The rounding asymmetry means a coalition of signers whose weight sits in the gap between the floor threshold and the ceiling threshold can cause the signer set's shared global-state consensus (which miner/burn view/tx-replay-set/protocol version is "agreed") to converge, even though that same weight would be **insufficient** to actually get a block signed under `compute_voting_weight_threshold`/`verify_signer_signatures`. This breaks the intended equality "global state agreed weight == block-approval-eligible weight" that the protocol implicitly assumes when it treats reaching global-state agreement as reflecting the same 70% supermajority used for block approval.

### Impact Explanation
This is analogous to the referenced report's core defect: two functions meant to encode the *same* fractional constant diverge due to rounding, and downstream logic (here, `check_block_against_global_state`, protocol-version selection, tx-replay-set determination, and "current miner" agreement) treats the weaker (floor) threshold as if it were the canonical 70% supermajority used elsewhere in the protocol for block signature acceptance (`verify_signer_signatures`). This narrows — for specific integer `total_weight` values — the effective safety margin of the "70%" agreement used to steer the global state machine (miner view, burn view, tx replay set), which other signers then rely on to decide how to validate/react to block proposals. In the worst case this could let a sub-70% (but still substantial) set of signers steer the network's shared view of the canonical miner/tenure or transaction-replay set, weakening (though not majority-breaking) the supermajority guarantee the design intends to provide for state-machine consensus.

### Likelihood Explanation
The magnitude of the gap is small (at most 1 unit of signer weight out of `total_weight`), and it only manifests when `total_weight * 7 mod 10 != 0`, which is common for arbitrary reward-set weight sums. Exploiting it meaningfully requires a coalition landing precisely in that narrow gap, which is a fairly constrained condition and does not by itself grant an attacker capability beyond what near-70% weight already implies. This limits the practical severity compared to the referenced report, though the inconsistency itself is a genuine, currently-untested-against-each-other divergence between two "70%" implementations.

### Recommendation
Use a single, shared threshold-computation function (the ceiling-rounded `compute_voting_weight_threshold`, or an equivalent) for both the block-approval path (`verify_signer_signatures`, `stacks-signer/src/v0/signer.rs`) and the global-state-agreement path (`GlobalStateEvaluator::reached_agreement`/`reached_disagreement` in `libsigner/src/v0/signer_state.rs`), so that "70% supermajority" always means the same weight cutoff everywhere in the protocol. If the floor-based partition in `reached_agreement`/`reached_disagreement` is intentional (e.g., to guarantee the two thresholds are complementary and non-overlapping), this should be explicitly documented as a deliberately different (weaker) threshold from `compute_voting_weight_threshold`, and any code path that relies on global-state agreement as a proxy for "the same 70% used for block signing" should be audited.

### Proof of Concept
For `total_weight = 11`:
- `NakamotoBlockHeader::compute_voting_weight_threshold(11)` = `ceil(11*7/10)` = `ceil(7.7)` = **8** — this is the weight required for a block to actually be signed/approved (see `stackslib/src/chainstate/nakamoto/mod.rs:1194-1207`, and its use in `stacks-signer/src/v0/signer.rs:1295-1301` / `2494-2501`).
- `GlobalStateEvaluator::reached_agreement(7)` with `total_weight = 11` evaluates `7 >= floor(11*7/10) = 7` → **true** (see `libsigner/src/v0/signer_state.rs:169-175`).

So a set of signers totaling weight 7 (63.6% of 11) is treated as having reached "global agreement" on a `SignerStateMachine` (current miner / burn view / tx replay set) via `determine_global_state`, even though that same weight of 7 would be rejected by `compute_voting_weight_threshold`/`verify_signer_signatures` as insufficient to approve an actual block (which requires 8). This directly demonstrates the equality break between the two "70%" thresholds used in the same signer stack.

    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

    /// Determine what the maximum signer protocol version that a majority of signers can support
    pub fn determine_latest_supported_signer_protocol_version(&self) -> Option<u64> {
        let mut protocol_versions = HashMap::new();
        for (address, update) in &self.address_updates {
            let Some(weight) = self.address_weights.get(address) else {
                continue;
            };
            let entry = protocol_versions
                .entry(update.local_supported_signer_protocol_version)
                .or_insert_with(|| 0);
            *entry += weight;
        }
        // find the highest version number supported by a threshold number of signers
        let mut protocol_versions: Vec<_> = protocol_versions.into_iter().collect();
        protocol_versions.sort_by_key(|(version, _)| *version);
        let mut total_weight_support: u32 = 0;
        for (version, weight_support) in protocol_versions.into_iter().rev() {
            total_weight_support += weight_support;
            if self.reached_agreement(total_weight_support) {
                return Some(version);
            }
        }
        None
    }

    /// Check if the supplied vote weight crosses the global agreement threshold.
    /// Returns true if it has, false otherwise.
    pub fn reached_agreement(&self, vote_weight: u32) -> bool {
        u64::from(vote_weight)
            >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
                / 10
    }

    /// Check if the supplied vote weight crosses the blocking minority threshold.
    /// Returns true if it has, false otherwise.
    pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
        u64::from(vote_weight)
            > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
                / 10
    }

#[test]
/// Locks the joint behavior of `reached_agreement` and `reached_disagreement`
/// at a single `total_weight`:
///   - agreement: `>=` 70% (inclusive)
///   - disagreement: `>` 30% (strict)
///   - three regions: [0, 30%] neither, (30%, 70%) disagreement only,
///     [70%, total] both
///
/// Walking 0, 30%, 30%+1, 70%-1, 70% catches a flipped inequality on either
/// side and any drift between the two threshold constants. Also pins the
/// "agreement implies disagreement" relation, which holds as long as the
/// agreement threshold sits above the disagreement one.
fn thresholds_partition_weight_space() {
    let evaluator = evaluator_with_total_weight(1_000_000_000);

    // 0%: neither.
    assert!(!evaluator.reached_agreement(0));
    assert!(!evaluator.reached_disagreement(0));

    // Exactly 30%: strict `>`, so not yet disagreement.
    assert!(!evaluator.reached_agreement(300_000_000));
    assert!(!evaluator.reached_disagreement(300_000_000));

    // One unit past 30%: gap region, disagreement only.
    assert!(!evaluator.reached_agreement(300_000_001));
    assert!(evaluator.reached_disagreement(300_000_001));

    // One unit below 70%: still in the gap.
    assert!(!evaluator.reached_agreement(699_999_999));
    assert!(evaluator.reached_disagreement(699_999_999));

    // Exactly 70%: agreement (`>=`), and disagreement still holds since 70% > 30%.
    assert!(evaluator.reached_agreement(700_000_000));
    assert!(evaluator.reached_disagreement(700_000_000));
}
