### Title
Unauthenticated vote-account spoofing via account-index confusion in `parse_vote_transaction` - (File: vote/src/vote_parser.rs)

### Summary
`parse_vote_transaction` derives the "vote account" identity solely from `first_instruction.accounts[0]` without verifying that the corresponding pubkey is cryptographically tied to the transaction's signer(s). Because the vote program's own account-meta layout places the vote account as a **non-signer** and only the "authorized voter" slot as signer, an attacker who controls just their own keypair can construct a syntactically valid, fully self-signed vote instruction that names an arbitrary (e.g., a real, staked, victim) vote-account pubkey in position 0, causing the parser to bind that unrelated pubkey to the vote payload.

### Finding Description
`parse_vote_transaction` (vote/src/vote_parser.rs:50-64) does: [1](#0-0) 
It only checks that `program_id` is the vote program, then blindly resolves `message.account_keys[first_instruction.accounts[0]]` as the vote pubkey and returns it in `ParsedVote`.

The vote program's real instruction encoding (used both here and by the on-chain program) places the vote account as a **writable non-signer** and the authorized voter as the (only) required signer, e.g. as built by `vote_instruction::vote`/`tower_sync` and exercised in the existing test at vote/src/vote_parser.rs:125-155. Because signatures in a `Transaction` only prove that the declared signer pubkeys signed the message — they do not cryptographically assert any relationship between the non-signer "vote account" slot and the signer — an attacker can build the raw `Message`/`CompiledInstruction` (bypassing the `vote_instruction::vote()` helper) so that `instruction.accounts[0]` indexes into any pubkey present in `account_keys`, including a real, staked victim vote account, while the only actual signature is the attacker's own keypair occupying the "authorized voter" slot. Sig-verification of the transaction succeeds (attacker signed for a pubkey they control), yet `parse_vote_transaction` will report the victim's pubkey as the vote key.

This parser is the gossip-vote fast path (used ahead of full bank replay/execution, per its doc comment "Used for parsing gossip vote transactions") and its output feeds `ClusterInfoVoteListener` vote-tracking logic used for optimistic-confirmation accounting, which is exactly the caller referenced in the question. Full on-chain execution of the *same* malformed instruction would later fail the vote program's internal authorized-voter check against the real `VoteState`, but that check happens only during bank replay — the gossip fast-path consumes the parsed (mismatched) key before/independently of that validation.

### Impact Explanation
An unprivileged attacker, using only their own keys, can cause `parse_vote_transaction` to attribute a forged vote payload to an unrelated vote-account pubkey (e.g., a real, actively-staked validator's vote account). If downstream optimistic-confirmation accounting in `ClusterInfoVoteListener` weights this vote by the named pubkey's stake without validating actual voter authority at this stage, it corrupts stake-weighted OC bookkeeping and can surface a false/misattributed confirmation signal via `getSignatureStatuses`/`voteSubscribe`, matching the "wrong-slot/fork/account data returned" and "consensus-state mutation from a query" impact categories in scope.

### Likelihood Explanation
Feasible and fully repeatable with a single crafted, self-signed transaction — no leaked keys, no validator/leader control, and no more than one submission required. The only precondition is manually constructing the `Message`/`CompiledInstruction` (rather than using the `vote_instruction` helper functions) so the account index order deviates from the conventional layout while remaining self-signed and syntactically valid for the vote program ID check.

### Recommendation
In `parse_vote_transaction` (and `parse_sanitized_vote_transaction`), validate that the pubkey extracted from `accounts[0]` corresponds to the actual signer designated as authorized voter per the specific `VoteInstruction` variant's expected account layout (i.e., cross-check against the *known* account-meta schema per instruction type rather than trusting positional index blindly), or reject/downweight gossip votes whose extracted vote-account key has no verifiable relationship to the transaction's signers until confirmed by full bank replay.

### Proof of Concept
```rust
// vote/src/vote_parser.rs (test)
#[test]
fn test_parse_vote_transaction_account_confusion() {
    use solana_message::{CompiledInstruction, Message};

    let attacker_payer = Keypair::new();
    let attacker_authorized_voter = Keypair::new();
    let victim_vote_pubkey = Pubkey::new_unique(); // real/staked vote account, not controlled by attacker

    // Manually build account_keys so index 0 (post-signers) is the victim's vote pubkey,
    // NOT constructed via vote_instruction::vote() helper.
    let account_keys = vec![
        attacker_payer.pubkey(),             // signer 0 (fee payer)
        attacker_authorized_voter.pubkey(),  // signer 1 (claims to be "authorized voter")
        victim_vote_pubkey,                  // non-signer, placed as accounts[0] of instruction
        solana_sdk_ids::sysvar::clock::id(),
        solana_sdk_ids::vote::id(),
    ];

    let vote = Vote::new(vec![42], Hash::default());
    let data = bincode::serialize(&VoteInstruction::Vote(vote.clone())).unwrap();

    let ix = CompiledInstruction {
        program_id_index: 4,
        accounts: vec![2, 3, 1], // vote_pubkey slot = index 2 = victim's key
        data,
    };

    let message = Message::new_with_compiled_instructions(
        2, 0, 0, account_keys, Hash::default(), vec![ix],
    );
    let mut tx = Transaction::new_unsigned(message);
    tx.sign(&[&attacker_payer, &attacker_authorized_voter], Hash::default());

    let (key, parsed_vote, _, _) = parse_vote_transaction(&tx).unwrap();

    // Attacker never controlled victim_vote_pubkey, yet it is bound as the vote key.
    assert_eq!(key, victim_vote_pubkey);
    assert_eq!(parsed_vote, VoteTransaction::from(vote));
}
```
Expected result: the assertion passes, demonstrating `parse_vote_transaction` returns a pubkey (`victim_vote_pubkey`) that the attacker does not control and that is not cryptographically authorized by any signature in the transaction — violating the invariant that returned data belongs to the account cryptographically tied to the request.
