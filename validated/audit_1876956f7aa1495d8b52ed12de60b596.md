### Title
`getLargestAccounts` cache write is not monotonic on slot, allowing a stale/lower-slot result to overwrite a fresher cached result - (File: rpc/src/rpc_cache.rs)

### Summary
`LargestAccountsCache::set_largest_accounts` unconditionally overwrites the cached entry for a given filter key with whatever `(slot, accounts)` is passed in, without ever comparing the new `slot` against the slot of the value currently stored. This mirrors the CidNFT bug class of "blind overwrite of previously stored state without checking whether the existing value should be preserved."

### Finding Description
The cache is a simple `HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>`, and the write path is: [1](#0-0) 

`set_largest_accounts` performs `self.cache.insert(filter.clone(), LargestAccountsCacheValue { .. slot, .. })` unconditionally — there is no check of `value.slot` against the slot of any entry already present for that filter key.

The read/write accessors are exposed on the RPC handler struct: [2](#0-1) 

`getLargestAccounts` is served by the multi-threaded JSON-RPC server, so two concurrent, unprivileged client requests for the same filter can each select/compute against a different (recent) bank/slot and then race to call `set_cached_largest_accounts`. If the request that resolved an *older* bank happens to complete and write to the cache *after* the request that resolved a *newer* bank, the newer, correct entry is silently overwritten by the stale, lower-slot entry — exactly the "insert without checking for a prior value that should not be clobbered" pattern described in the CidNFT report (writing directly into a keyed store without any ordering/overwrite check).

### Impact Explanation
Any subsequent `getLargestAccounts` caller within the cache TTL (`duration`, configured via `--rpc-largest-accounts-cache-duration` or default) for that same filter receives the stale, lower-slot snapshot returned as if it were current, i.e., wrong-slot data returned from a plain read-only RPC query — this matches the "wrong-slot/fork/account data returned" impact category. It does not require privileged access, only ordinary concurrent `getLargestAccounts` traffic against the same node.

### Likelihood Explanation
This requires two (or more) concurrent `getLargestAccounts` calls with the same `filter` racing across two different bank snapshots, which is a realistic condition on any node serving normal RPC concurrency, not an artificial multi-call-per-slot DoS pattern. However, the actual computation and bank-selection code path inside the full `getLargestAccounts` handler (the piece that determines which bank slot is used before calling `set_cached_largest_accounts`) was not directly inspected in this session — I only confirmed the two thin accessor methods `get_cached_largest_accounts` / `set_cached_largest_accounts` and the underlying cache struct. The precise timing window (how much wall-clock skew is required between the two racing requests to reorder their cache writes) is therefore not fully verified and should be validated by reading the full handler body (likely `rpc/src/rpc.rs::get_largest_accounts`) before treating this as confirmed.

### Recommendation
In `LargestAccountsCache::set_largest_accounts`, compare the incoming `slot` against any existing entry's `slot` for the same filter and only overwrite if the new slot is greater than or equal to the stored one (i.e., make the cache write monotonic per filter key), analogous to the CidNFT fix of rejecting/guarding an overwrite instead of applying it unconditionally.

### Proof of Concept
Conceptual PoC (not run, since I only have read access):
1. Client A issues `getLargestAccounts` while the node's `working_bank()` is at slot `N`.
2. A new bank is rooted; Client B issues `getLargestAccounts` (same filter) and computes against slot `N+1`.
3. Client B's request finishes first and calls `set_cached_largest_accounts(filter, N+1, ...)`.
4. Client A's request (started earlier, slower to compute) finishes after B and calls `set_cached_largest_accounts(filter, N, ...)`, unconditionally overwriting B's fresher entry.
5. Any subsequent `getLargestAccounts` call within the cache TTL returns the stale slot-`N` data, misreporting current state.
