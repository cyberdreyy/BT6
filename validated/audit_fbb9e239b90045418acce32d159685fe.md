Found a valid analog: the HTTP trigger handler's `setupCallback` registers pending requests keyed only by the client-supplied JSON-RPC `req.ID`, and the request-ID uniqueness check happens **before** the caller is bound to any per-owner/per-workflow namespace at the storage-key level, allowing one unprivileged caller to grief another caller's in-flight request by ID collision, mirroring the "grief a legitimate actor's pending state via a colliding/racing external call" pattern in the report.

### Title
Unprivileged request-ID griefing of another user's in-flight HTTP trigger request - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
`httpTriggerHandler.setupCallback` stores pending trigger requests in a single global map keyed only by the caller-supplied JSON-RPC `req.ID` string [1](#0-0) . Any unprivileged external client submitting an `HTTPTrigger` request can pick this ID before another legitimate workflow owner does, causing the legitimate request to be rejected with a conflict error.

### Finding Description
`HandleUserTriggerRequest` validates the JWT/auth for a given workflow and then calls `setupCallback`, which checks for an existing entry under `h.callbacks[requestID]` and returns `ErrConflict` if a request with the same ID is already in flight [1](#0-0) . The map is a single global namespace (`h.callbacks map[string]savedCallback`), not scoped per workflow-owner or per workflow, so `requestID` collisions across *different, unrelated* workflow owners are possible: an attacker who can predict or guess another user's request ID (e.g. via a leaked webhook/trigger URL, replay of a public request, or by racing many client-chosen IDs) can pre-register that same ID first. When the legitimate user's request then arrives, `setupCallback` will find the ID already present and reject the legitimate request with `jsonrpc.ErrConflict`, denying that request's execution [2](#0-1) . This is directly analogous to the NFT-withdrawal-grief pattern: a low-cost, unprivileged action from one party (claiming a shared identifier/slot) causes a legitimate, unrelated party's subsequent otherwise-valid call to fail. The unit test `TestHttpTriggerHandler_HandleUserTriggerRequest/"duplicate request ID"` demonstrates the exact mechanic (second caller's request errors with "in-flight request", and a `jsonrpc.ErrConflict` is sent back to them) [3](#0-2) . Authentication (JWT auth per workflow) happens before the ID-collision check but does not bind the requestID namespace to the workflow/owner — the map key is purely `req.ID`, so a valid JWT for workflow A does not protect against an attacker who authenticates as workflow B and reuses the same literal ID string first.

### Impact Explanation
This is a griefing / availability issue: it enables a low-cost DoS against a specific, targeted request (denial of a specific workflow execution trigger) by any external, unauthenticated-relative-to-the-victim party who can guess/observe the victim's chosen request ID and race to submit it first. It does not grant unauthorized fund movement or secret disclosure, but it is a concrete availability/griefing vector reachable directly from an unprivileged client request to the gateway's internet-facing trigger endpoint, matching the DoS/grief classification of the source report.

### Likelihood Explanation
Likelihood depends on whether request IDs are unpredictable (e.g., high-entropy UUIDs chosen by legitimate callers) or predictable/observable (e.g., sequential IDs, IDs echoed in logs/URLs, or IDs reused by automated systems). Where callers use low-entropy or externally-observable IDs, likelihood is moderate; where IDs are cryptographically random and kept secret, likelihood is low. The relevant validation only checks format constraints (no "/" character) per documentation, not entropy/uniqueness guarantees [4](#0-3) .

### Recommendation
Scope the in-flight request map key by workflow/owner in addition to the caller-supplied `requestID` (e.g., key on `(workflowID, requestID)` or `(workflowOwner, requestID)`) so that ID collisions can only occur within the same workflow/owner's own request stream, not across unrelated callers, and document/enforce minimum entropy or server-assigned uniqueness for request IDs.

### Proof of Concept
1. Attacker learns or guesses a request ID `X` that a victim workflow-owner intends to use for a legitimate HTTP trigger call (e.g., through a shared/observable webhook convention).
2. Attacker sends a valid signed `HTTPTrigger` request for their own (attacker-owned) workflow, using `req.ID = X`; `setupCallback` inserts `h.callbacks["X"] = ...` [5](#0-4) .
3. Victim then sends their legitimate, correctly authenticated request also using `req.ID = X` for their own workflow.
4. `setupCallback` finds `h.callbacks["X"]` already present and calls `h.handleUserError(..., jsonrpc.ErrConflict, ...)`, returning `"in-flight request ID: X"` and denying the victim's execution [2](#0-1) , exactly as reproduced in `TestHttpTriggerHandler_HandleUserTriggerRequest/"duplicate request ID"` [3](#0-2) .

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
