This confirms the mechanism: `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` when the recipient exists, is not registered for `AptosCoin`, and has explicitly called `set_allow_direct_coin_transfers(false)`. Since `staking_contract::set_beneficiary_for_operator` performs no validation of `new_beneficiary` (unlike `vesting::set_beneficiary`, which calls `assert_account_is_registered_for_apt`), an operator can weaponize this to permanently block a staker's unlock/withdraw path.

### Title
Operator-controlled beneficiary can permanently DoS staker unlock/withdraw by pointing commission payout at a non-accepting address - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
`staking_contract::set_beneficiary_for_operator` lets an operator set any address, without validating it can actually receive `AptosCoin`, unlike `vesting::set_beneficiary` which enforces `assert_account_is_registered_for_apt` for the exact same class of payout redirection. [1](#0-0) [2](#0-1) 

### Finding Description
`distribute_internal` pays commission owed to the operator to `beneficiary_for_operator(operator)` via `aptos_account::deposit_coins`, inside the shareholder payout loop. [3](#0-2) 

`aptos_account::deposit_coins` aborts if the target account exists, is not registered for the coin type, and has disabled arbitrary direct transfers via `set_allow_direct_coin_transfers(false)`. [4](#0-3) [5](#0-4) 

Critically, `distribute_internal` is not merely called from the permissionless `distribute` entry point — it is called first, unconditionally, inside `unlock_stake` and `switch_operator`, the staker's own withdrawal/exit paths: [6](#0-5) [7](#0-6) 

`set_beneficiary_for_operator` has no check whatsoever on `new_beneficiary`, and this same unchecked pattern is duplicated in `delegation_pool::set_beneficiary_for_operator`. [8](#0-7) [9](#0-8) 

By contrast, the vesting module's `set_beneficiary` (which redirects shareholder distributions, the analogous flow) explicitly validates the target with `assert_account_is_registered_for_apt` before accepting the update, precisely to prevent a bad beneficiary from bricking `distribute()`. [2](#0-1) 

The attack: an operator (who need not hold the staker/owner role and does not need to be malicious toward themselves — they only need to be uncooperative toward the staker) calls `set_allow_direct_coin_transfers(false)` on an address they control (or any address they know is so configured) without registering it for `AptosCoin`, then calls `set_beneficiary_for_operator(operator, that_address)`. From that point forward, any call to `distribute`, `unlock_stake`, or `switch_operator` for that staker/operator pair that has non-zero unpaid commission will abort inside `distribute_internal` when trying to pay the poisoned beneficiary, because the loop has no error handling and iterates over all pending shares including the operator's before completing.

### Impact Explanation
This traps the staker's principal and rewards: `unlock_stake` cannot proceed (it always forces a `distribute_internal` first), and `switch_operator` — the staker's designated escape hatch from a bad operator — likewise force-distributes and force-requests commission before switching, so it also reverts. The staker has no other way to move their stake to `pending_inactive`/`withdraw` while commission is outstanding and the beneficiary is poisoned, because there is no owner-side override to skip or forcibly redirect a stuck distribution. This meets the "permanent lock or non-recoverable loss of claim rights in stake ... flows" and "operator commission ... corruption that credits the wrong account or traps value" criteria, since it is the staker's balance, not just the operator's commission, that becomes unrecoverable.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires no special privilege beyond being the current operator of a `staking_contract` (a role any account can be assigned to by a staker) and requires only two ordinary transactions (`aptos_account::set_allow_direct_coin_transfers(false)` on a controlled address, then `staking_contract::set_beneficiary_for_operator`). No governance or elevated role is needed, and the resulting griefing is durable across epochs since `unlock_stake`/`switch_operator` will keep hitting the same abort every time they are retried.

### Recommendation
Add the same guard used in `vesting::set_beneficiary` to `staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator`: require `aptos_account::assert_account_is_registered_for_apt(new_beneficiary)` (or otherwise verify the address can accept a direct `AptosCoin` deposit) before accepting the update. Additionally, consider hardening `distribute_internal` so that a payout failure to one recipient (particularly the beneficiary) cannot revert the entire distribution loop and block the staker's independent principal — e.g., by isolating the beneficiary payout so its failure only skips/holds that one leg instead of the whole transaction.

### Proof of Concept
1. Staker `S` creates a staking contract with operator `O` via `staking_contract::create_staking_contract` (stake pool earns rewards, so commission accrues over epochs).
2. `O` controls (or nominates) address `B`. `B` (or `O` acting through a resource account it fully controls as `B`) calls `aptos_account::set_allow_direct_coin_transfers(false)` and never registers `AptosCoin` for `B`.
3. `O` calls `staking_contract::set_beneficiary_for_operator(O, B)` — succeeds with no validation. [1](#0-0) 
4. Time passes; stake earns rewards, `O`'s commission share becomes non-zero and some funds move to `inactive`/`pending_inactive`.
5. `S` calls `staking_contract::unlock_stake(S, O, amount)`. This calls `distribute_internal`, which iterates the distribution pool; when `recipient == O`, it substitutes `recipient = beneficiary_for_operator(O) = B` and calls `aptos_account::deposit_coins(B, ...)`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` because `B` is not registered and does not accept arbitrary transfers. [10](#0-9) [11](#0-10) 
6. `S`'s `unlock_stake` transaction reverts. `S` attempts `switch_operator` to move away from `O` — it also force-calls `distribute_internal` before removing the old contract, and reverts for the same reason. [7](#0-6) 
7. `S`'s stake is now stuck: neither unlock nor operator-switch can succeed while `B` remains unregistered/non-accepting, and `S` has no on-chain mechanism to force or bypass this.

**Note on verification limits:** I was not able to execute this scenario in a live Move test environment within this session; the trace is derived entirely from reading the cited source (control flow of `distribute_internal`, `unlock_stake`, `switch_operator`, `set_beneficiary_for_operator`, and `aptos_account::deposit_coins`/`set_allow_direct_coin_transfers`). I recommend a background Devin session write and run a Move unit test analogous to `test_operator_can_set_beneficiary` in `staking_contract.move` but with the beneficiary configured via `set_allow_direct_coin_transfers(false)` and unregistered for `AptosCoin`, then asserting that `unlock_stake` and `switch_operator` abort, to fully confirm exploitability before treating this as fully proven.
