### Title
`claimInstantWithdrawRequest` never decrements per-epoch receipt counters, inflating default-recovery price and insolventing the reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2021-47173 is a missing refcount decrement: `uss720_probe` acquires a `usbdev` reference and never releases it, leaking the object. The analog in `IdleCreditVault` is the same class of bug — `requestInstantWithdraw` records the request in three places (`instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`), but the normal, non-default claim path `claimInstantWithdrawRequest` only clears the first one and burns the receipt. The two per-epoch counters are never decremented, so they leak a stale claim basis that is later consumed by default-recovery accounting as if the funds were still held and still owed.

### Finding Description
`requestInstantWithdraw` increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . Funding is collected via `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` but leaves the per-epoch claim buckets untouched [2](#0-1) . The normal claim then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It never touches `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` — only the defaulted-epoch path `_claimDefaultedInstantWithdrawRequest` clears them [3](#0-2) [4](#0-3) .

These stale counters matter because `finalizeDefaultRecovery` trusts them:

- `defaultPendingClaimBasis()` adds the full `instantWithdrawClaimsByEpoch[epochNumber]` — including already-claimed receipts — into the recovery basis [5](#0-4) .
- `_defaultPrefundedInstantReserve()` computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` and treats that as underlying already held by the strategy [6](#0-5) . But funds backing already-claimed receipts were paid out; they are no longer held. The "prefunded reserve" is therefore overstated by exactly the claimed amount.
- `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` both consume the phantom funds [7](#0-6) .

Additionally, because `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` is never zeroed on a normal claim, a user who claimed a funded instant receipt pre-default and then opens a new `requestInstantWithdraw` post-default (which has no `defaultRecoveryFinalized` guard [8](#0-7) ) can pass through `_claimDefaultedInstantWithdrawRequest` again on the stale per-epoch basis, receiving a second recovery payout for the same receipt.

### Impact Explanation
- `defaultRecoveryPrice` is set above what the reserve actually contains. Early defaulted-epoch claimants (normal and instant) are paid at the inflated price; the reserve is drained prematurely and later claimants receive nothing. This is a direct redistribution loss borne by honest withdraw-request holders.
- `defaultBBNav` / `activeFinalNAV` are computed off the same inflated price, mispricing the residual tranche NAV after default [9](#0-8) .
- The double-claim path lets the attacker mint a real second payout of size `staleBasis * defaultRecoveryPrice / RECOVERY_FULL`, up to their whole instant receipt value.

### Likelihood Explanation
Requires: (1) instant-withdraw requests created in the epoch that ends in default, (2) the CDO partially funding them via `collectInstantWithdrawFunds` so `pendingInstantWithdraws != 0` at `finalizeDefaultRecovery`, and (3) at least one funded receipt claimed before finalization. This is a normal configuration when the pool has idle liquidity mid-epoch; no privileged misbehavior is needed — the borrower defaulting is in-scope per rules (borrower is honest but can default via insufficient repayment). The attacker is any tranche-token holder requesting an instant withdraw, an explicitly allowed unprivileged role. The stale-counter inflation is deterministic, not dependent on oracle data or rounding.

### Recommendation
Mirror the missing-refcount fix: in `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` for the claimed amount, tracking the request epoch (e.g., a `lastInstantWithdrawRequest[_user]` marker, or a per-epoch cursor). Alternatively, fold already-claimed amounts out of `instantWithdrawClaimsByEpoch` when `collectInstantWithdrawFunds`/claims move funds out, so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only see genuinely outstanding, still-held receipts. Also add a `defaultRecoveryFinalized` guard or per-epoch clearing in `requestInstantWithdraw` to prevent post-default reuse of stale per-epoch basis.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` style helpers; requires an instant-withdraw-enabled vault):

```solidity
function testInstantClaimLeakInflatesRecoveryPrice() external {
    address alice = makeAddr("alice");
    address bob   = makeAddr("bob");

    // buffer phase: both deposit
    _depositWithUser(alice, 10_000 * ONE_SCALE, true);
    _depositWithUser(bob,   10_000 * ONE_SCALE, true);

    // epoch 0 running, instant withdraws enabled
    _startEpochAndCheckPrices(0);

    // alice requests instant withdraw of 5_000
    vm.prank(alice);
    uint256 req = cdoEpoch.requestInstantWithdraw(5_000 * ONE_SCALE, address(AAtranche));

    // CDO collects only alice's amount -> pendingInstantWithdraws becomes 0 only if
    // bob also requests; craft partial funding:
    vm.prank(bob);
    cdoEpoch.requestInstantWithdraw(5_000 * ONE_SCALE, address(BBtranche));
    // collect only alice's funded half
    vm.prank(manager); // or whoever triggers collectInstantWithdrawFunds
    strategy.collectInstantWithdrawFunds(req); // pendingInstantWithdraws = 5_000 remains

    // alice claims her funded receipt BEFORE default
    vm.prank(alice);
    cdoEpoch.claimInstantWithdrawRequest();
    // BUG: instantWithdrawClaimsByEpoch[epochNumber] still == 10_000
    //      instantWithdrawsRequestsByEpoch[alice][epochNumber] still == 5_000

    // borrower underfunds -> default, then finalize
    _stopEpochAndCheckPrices(0, initialProvidedApr, /*shortfall*/);
    vm.prank(manager);
    cdoEpoch.finalizeDefault(recoveredAmount, manager);

    // prefundedReserve counted alice's already-paid 5_000 -> recoveryPrice inflated
    // bob's defaulted claim drains reserve; later claimants get nothing / alice can
    // reclaim after posting a new requestInstantWithdraw.
    assertGt(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), 0,
        "stale per-epoch claim basis leaked");
}
```

Key assertions: `instantWithdrawClaimsByEpoch[epochNumber]` and `instantWithdrawsRequestsByEpoch[alice][epochNumber]` remain non-zero after `claimInstantWithdrawRequest`, and `defaultRecoveryPrice * totalBasis` exceeds `defaultRecoveryReserve` actually held, proving the leaked "refcount" directly inflates the recovery price and leaves the reserve insolvent for the last claimants.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
