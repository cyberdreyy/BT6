### Title
Admin whitelist in `KeyringIdleWhitelist.checkCredential` bypasses `policyId` scoping, granting cross-policy access to all gated vaults — (File: contracts/KeyringIdleWhitelist.sol)

### Summary
`KeyringIdleWhitelist.checkCredential` returns `whitelist[entity] || Keyring(keyring).checkCredential(policyId, entity)`. The admin-managed `whitelist` mapping is keyed only by `entity` and ignores `policyId` entirely, so an entity whitelisted by the admin for one intended context is treated as credentialed for every policy that routes through this contract — the direct analog of a whitelisted selector not being bound to the specific revenue contract it was approved for.

### Finding Description
In `KeyringIdleWhitelist.sol`, `checkCredential(uint256 policyId, address entity)` is the gate used by the credit-vault stack (`IdleCDOEpochVariant`, `IdleCreditVaultFactory`, `IdleCDOEpochQueue` all reference `checkCredential`/`isWalletAllowed`/`keyring`) to decide whether a wallet is allowed to interact with a KYC-restricted pool. The intent is twofold: pass a Keyring credential check for a specific `policyId`, or be on the admin whitelist. However, the whitelist short-circuit ignores `policyId`:

```solidity
// contracts/KeyringIdleWhitelist.sol:78-80
function checkCredential(uint256 policyId, address entity) external view returns(bool) {
  return whitelist[entity] || Keyring(keyring).checkCredential(policyId, entity);
}
```

`setWhitelistStatus` (lines 102-112) stores `whitelist[entity]` with no association to a policy or vault. Therefore, once the admin whitelists an entity — e.g., an operational contract, a market maker, or a partner approved under a low-tier policy — that entity satisfies `checkCredential` for *any* `policyId`, including policies it was never vetted for.

This mirrors the Spigot bug class exactly: a permission record (`whitelist[entity]` / `whitelistedFunc[selector]`) is stored without binding it to the resource it was granted for (`policyId` / revenue contract address), so the approval "clashes" and silently authorizes unintended targets.

### Impact Explanation
Access-control bypass. Any address placed on the admin whitelist gains lender access to every `IdleCreditVault`/`IdleCDOEpochVariant` instance that shares this `KeyringIdleWhitelist` deployment, regardless of that vault's `policyId`. An attacker who is legitimately whitelisted for one pool (a KYC-passing lender is an allowed attacker class) can deposit into pools gated by stricter or unrelated policies — e.g., a pool requiring institutional-tier credentials — minting tranche shares and participating in epoch deposits, withdraw requests, and claims without ever satisfying that pool's Keyring policy. Beyond the compliance violation, this lets an unvetted wallet acquire tranche positions and withdraw pool liquidity it was never authorized to touch.

### Likelihood Explanation
Likelihood depends on deployment topology: if every vault shares one `KeyringIdleWhitelist` and one `keyring` contract but uses distinct `policyId`s (the interface is explicitly designed around per-policy checks), a single whitelist entry is a global key. The admin only needs to whitelist one address (e.g., a service/queue contract that itself must be credentialed) for the gap to exist; any compromise or abuse of that whitelisted entity's address then bypasses all policy checks. There is no per-policy mapping, so no guard currently stops it — the honest admin's own `setWhitelistStatus` call is the trigger, which the threat model permits (we sequence around honest admin calls, we don't require admin malice).

### Recommendation
Scope the whitelist to the resource it approves, the same fix pattern as the Spigot report (`mapping(address => mapping(bytes4 => bool))`): change `whitelist` to `mapping(uint256 policyId => mapping(address entity => bool))`, add a `policyId` parameter to `setWhitelistStatus`, and have `checkCredential` evaluate `whitelist[policyId][entity] || Keyring(keyring).checkCredential(policyId, entity)`. If an entity must be globally trusted, add an explicit `globalWhitelist` flag that admins opt into separately, rather than making every grant global by default.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {KeyringIdleWhitelist} from "../contracts/KeyringIdleWhitelist.sol";

contract MockKeyring {
  // Returns false for everything: credential is only reachable via whitelist
  function checkCredential(uint256, address) external pure returns (bool) {
    return false;
  }
}

contract PolicyClashTest is Test {
  KeyringIdleWhitelist whitelist;
  address admin = address(0xAD);
  address partner = address(0xBEEF);

  uint256 constant POLICY_RETAIL = 1;       // vault A policy
  uint256 constant POLICY_INSTITUTION = 42; // vault B (strict) policy

  function setUp() public {
    whitelist = new KeyringIdleWhitelist(address(new MockKeyring()), admin);
  }

  function test_WhitelistBypassesPolicyScoping() public {
    // Admin whitelists `partner` intending it only for the retail policy
    vm.prank(admin);
    whitelist.setWhitelistStatus(partner, true);

    // BUG: partner is credentialed for the unrelated institutional policy too,
    // without ever passing Keyring's check for policyId 42.
    assertTrue(whitelist.checkCredential(POLICY_INSTITUTION, partner));

    // Non-whitelisted attacker is correctly rejected for the same policy
    assertFalse(whitelist.checkCredential(POLICY_INSTITUTION, address(0xCAFE)));
  }
}
```

Running this against `contracts/KeyringIdleWhitelist.sol` shows `checkCredential` returns `true` for `partner` under `POLICY_INSTITUTION` solely because of the policy-agnostic `whitelist[entity]` flag — the same selector-clash primitive: an approval granted for one resource silently authorizes a different, untargeted resource.
