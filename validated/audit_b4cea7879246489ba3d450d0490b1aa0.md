### Title
Signer vote-flip (Reject→Accept) causes double-counted weight in `BlockStatus`, breaking the weighted-tally invariant - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The node-side StackerDB listener tallies `total_weight_approved` and `total_weight_rejected` for a proposed block using two different, mutually-inconsistent de-duplication keys. A single signer that first rejects a block and later flips to accepting it (a legitimate, permitted state transition on the signer side) gets its weight counted in **both** totals, breaking the invariant that a signer's weight is counted at most once across the aggregate tallies.

### Finding Description
`BlockStatus` tracks per-block weight in two counters plus two sets: [1](#0-0) 

On an `Accepted` message, the de-duplication check is against `gathered_signatures` only: [2](#0-1) 

On a `Rejected` message, the de-duplication check is against `responded_signers`, which the accept path also populates: [3](#0-2) 

Because the two branches use different sets for their "have I already counted this signer" check, the order of messages from the *same* signer matters:

- Accept-then-reject: `responded_signers` already contains the slot from the accept step, so the later `insert` on reject returns `false` and `total_weight_rejected` is correctly **not** incremented — no double count.
- Reject-then-accept: on the first (reject) message, only `responded_signers` gets the slot; `gathered_signatures` remains empty for that slot. When the same signer later sends an `Accepted` message (a normal, permitted event — e.g. a rival block died out and the signer's local state machine now allows signing, see the signer-side "capitulation"/"OWN tenure" logic), the accept-path check `!gathered_signatures.contains_key(&slot_id)` is `true`, so `total_weight_approved` is incremented **again** for the same signer whose weight is already baked into `total_weight_rejected`.

The result: `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, and a single signer's weight is simultaneously represented in the rejected tally and the approved tally. This is consumed verbatim by the mining coordinator, which never re-derives distinctness itself: [4](#0-3) 

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality that the >30%/≥70% weight thresholds are built on: each signer's weight is supposed to count exactly once toward whichever side (accept or reject) it currently holds. With the double count, a signer that legitimately changes its answer from reject to accept leaves a "ghost" copy of its weight sitting in `total_weight_rejected` forever (that counter is never decremented). This lets the *rejected* weight cross the `> self.total_weight - weight_threshold` blocking-minority line with fewer genuinely-rejecting distinct signers than the protocol intends, causing `NakamotoNodeError::SignersRejected` to be raised on a block that a real (undiluted) tally would still allow to reach acceptance — a liveness degradation of the mining/coordination path that lets less real weight than 30% force a block's rejection.

### Likelihood Explanation
This requires only one signer (its own key, its own decision) to send a `Rejected` message followed later by an `Accepted` message for the same `signer_signature_hash` — a completely ordinary occurrence documented in the signer's own flow (a signer may reject due to a transient chainstate check failing, then legitimately sign later once conditions change, cf. `handle_block_pre_commit`'s conflict-freshness/capitulation logic). No majority, no other signer's key, and no auth token are required, matching the in-scope threat model.

### Recommendation
Use a single, consistent per-slot ledger to decide whether a signer's weight has already been counted, and if a signer switches from reject to accept (or vice versa), move the counted weight between `total_weight_approved` and `total_weight_rejected` instead of adding it independently under two different key sets. E.g., gate both branches on `responded_signers` membership (only increment on first response) and encode the accept/reject outcome as a value tied to `responded_signers` rather than deriving "already accepted" solely from `gathered_signatures`.

### Proof of Concept
1. Node proposes a block; signer S (weight w) sends `Rejected`. `stackerdb_listener` runs the reject branch: `responded_signers.insert(S)` succeeds, `total_weight_rejected += w`.
2. S's local chainstate view changes (e.g., a conflicting block it was waiting on goes stale) and S legitimately signs and broadcasts `Accepted` for the same block.
3. `stackerdb_listener` runs the accept branch: `gathered_signatures.contains_key(S)` is `false` (S is only in `responded_signers`), so `total_weight_approved += w` as well.
4. Now `total_weight_approved + total_weight_rejected` includes `w` twice; `signer_coordinator::get_block_status` sees an inflated `total_weight_rejected` that can cross the blocking-minority threshold with less real distinct weight than 30%, returning `SignersRejected` for a block that should still be votable to acceptance.
