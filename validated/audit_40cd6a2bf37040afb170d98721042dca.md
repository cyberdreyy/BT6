### Title
Unprivileged front-running of `<name>.<factory>` multisig creation lets an attacker seize a chosen sub-account with attacker-controlled members - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` lets **any** caller pick an arbitrary `name`, `members`, and `num_confirmations` and immediately schedules `create_account()` + `deploy_contract()` + `new(...)` on `<name>.<factory>` with no check that the caller is entitled to that name and no check that the account doesn't already exist. Because NEAR account IDs are globally unique and first-come-first-served, an attacker can pre-emptively claim a name the intended owner was going to use, permanently binding that address to attacker-chosen multisig members.

### Finding Description
The invariant the question asks to validate is:

`members(<name>.<factory>) == members_intended_by_rightful_owner_of(<name>)`

`create` performs no authorization or reservation check at all: [1](#0-0) 

- `name`, `members`, and `num_confirmations` are fully attacker-controlled parameters of a `#[payable]` method callable by any account.
- The derived account id is simply `format!("{}.{}", name, env::current_account_id())` with no `is_valid_account_id` check on `name` and no lookup of whether `<name>.<factory>` already exists or is reserved for someone else.
- The `Promise::new(account_id).create_account()...` chain is fired unconditionally; NEAR's runtime enforces global account-id uniqueness, so whichever transaction reaches the network first "wins" the name permanently — `create_account` on an already-existing account fails, but there is no application-level reservation, so the race is purely who submits first.

Exploit flow:
1. Attacker observes/anticipates that a victim (protocol, DAO, or user) intends to create a multisig at `treasury.multisig-factory.near` (or any recognizable/expected name).
2. Attacker calls `create("treasury", [attacker_key_or_account], 1)` first, attaching whatever deposit/gas they choose.
3. `treasury.multisig-factory.near` is created and deployed with the attacker's own member set and `num_confirmations`, fully under attacker control.
4. When the intended owner later calls `create("treasury", ...)`, `create_account()` fails on the runtime because the account id already exists — the rightful owner can never obtain that address.
5. Any downstream party (users, other contracts, front-ends) that trusts `treasury.<factory>` as "the treasury multisig" is actually depositing funds/trust into a contract whose members and confirmation threshold were chosen entirely by the attacker.

No existing guard in the contract (`assert_owner`, ownership checks, name reservation, or `is_valid_account_id` validation) prevents this, because `MultisigFactory` has no owner concept and performs no pre-check before firing the account-creation promise.

### Impact Explanation
This is a Critical-severity issue matching "an account whitelisted or a lockup deployed with parameters its rightful creator never chose": the deployed multisig at the squatted sub-account has member keys/accounts and a confirmation threshold chosen entirely by the attacker, not the intended owner. Any NEAR subsequently sent to that address by users, integrators, or other contracts who trust the naming convention is effectively under sole attacker control — the attacker (as sole/majority member) can withdraw or misuse it via multisig requests that meet their own self-chosen `num_confirmations`. This is repeatable against any predictable or guessable name and any number of victims, giving a broad blast radius across all users of the factory.

### Likelihood Explanation
The attack requires no privilege beyond being able to submit a NEAR transaction — exactly the "unprivileged attacker" capability set defined in scope. It only requires the attacker to submit their `create` call before the legitimate owner's transaction is included, which is trivial for well-known or predictable names (e.g., project names, "treasury", "dao", "team") announced in advance, or can be done opportunistically by monitoring the network for the intended creation and front-running it (same account nonce fees only). Cost is a single NEAR transaction plus minimal storage deposit; the attack is fully repeatable against any name not yet claimed.

### Recommendation
Add an authorization/reservation mechanism to `MultisigFactory::create`, e.g.: require a whitelist/allow-list of names tied to specific predecessor accounts, require the caller to prove ownership of a reserved `name` (e.g., via a mapping populated by a trusted registrar), or check `env::predecessor_account_id() == name`-derived account ownership before deploying. At minimum, validate that `name` is not already associated with a pending/expected claim and reject creation if `<name>.<factory>` is not explicitly reserved for `predecessor_account_id`.

### Proof of Concept
Using `near-workspaces` (async Rust or JS bindings), or `near-sdk-sim`:
```rust
// 1. Deploy multisig-factory contract to `factory` account.
// 2. Attacker account calls:
//    factory.create("treasury", vec![MultisigMember::Account{account_id: "attacker".into()}], 1)
//    with sufficient deposit/gas.
// 3. Assert `treasury.factory` now exists and its multisig2 state (`get_members` or storage)
//    shows exactly [attacker] as member with num_confirmations == 1.
// 4. Intended owner (a different account) then calls:
//    factory.create("treasury", vec![MultisigMember::Account{account_id: "owner".into()}], 2)
// 5. Assert this second call's outer promise fails (create_account fails because the
//    "treasury.factory" account already exists), and re-query `treasury.factory` members —
//    they are STILL [attacker]/num_confirmations=1, not [owner]/2.
//
// Binding checked:
//   LHS (expected):  members(treasury.factory) == [owner]
//   RHS (actual):    members(treasury.factory) == [attacker]
//   LHS != RHS  =>  vulnerability confirmed.
```

    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
