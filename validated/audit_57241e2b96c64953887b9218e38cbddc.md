### Title
Write-off requests with zero/dust `underlyingsRequested` can be fulfilled by anyone, letting an attacker buy a victim's escrowed tranche tokens for nothing - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`createWriteOffRequest` only rejects `amount == 0`; it performs no sanity check on the caller-supplied `underlyingsRequested`. `fullfillWriteOffRequest` is permissionless and only requires `_underlyings >= currentRequest.underlyings` plus an exact tranche-amount match. A user who mistakenly sets `underlyingsRequested` to `0` (or dust) while depositing real tranche tokens allows any EOA to fulfill the request by transferring nothing (or dust) and receiving the full tranche balance — the direct analog of Perennial's unvalidated `liquidationFee` sign/amount that let a caller's mistaken input move funds the wrong way.

### Finding Description
In `IdleCreditVaultWriteOffEscrow.createWriteOffRequest` the only validation is `amount == 0`:

```solidity
if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
if (amount == 0) revert NotAllowed();
IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
pendingUnderlyings += underlyingsRequested;
``` [1](#0-0) 

`fullfillWriteOffRequest` is explicitly callable by any wallet and only checks `_underlyings < currentRequest.underlyings` — with `underlyingsRequested == 0` the check passes for `_underlyings == 0`:

```solidity
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
...
underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
...
IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
``` [2](#0-1) 

A zero-value `safeTransferFrom`/`safeTransfer` succeeds on standard ERC20s, so the attacker pays nothing and receives all escrowed tranche tokens, which carry a claim on pool NAV redeemable through `requestWithdraw`/`claimWithdrawRequest` (subject to KYC wallet allowlisting — the attacker can be a KYC-passing lender, which is in the unprivileged threat model). The exit fee path is bypassed entirely since `_totFee` on a zero amount is zero.

### Impact Explanation
Direct theft of the victim's escrowed tranche tokens (worth `virtualPrice(tranche)` per token, i.e., their pro-rata claim on pool NAV), quantified as `amount * virtualPrice / 1e18` underlying tokens, in exchange for zero or dust payment. The victim's only recourse is `deleteWriteOffRequest`, but the attacker can fulfill in the same block (or front-run) before the victim corrects the request.

### Likelihood Explanation
Requires user error (entering `0` or an abnormally low `underlyingsRequested`) during a running epoch, mirroring the source report's "mistakenly input a positive liquidation fee" scenario — rated Medium there for the same reason. The permissionless fulfiller role and zero lower bound make exploitation trivial once the mistaken request exists; escrowed requests are publicly visible on-chain so attackers can monitor for underpriced requests. No privileged role, oracle, or timing dependence beyond the victim's own input.

### Recommendation
Enforce a sanity bound on `underlyingsRequested` in `createWriteOffRequest`, e.g., require `underlyingsRequested > 0` and additionally a minimum implied price such as `underlyingsRequested * ONE_TRANCHE >= amount * minPrice`, or derive the requested underlyings internally from `amount * IdleCDOEpochVariant(idleCDOEpoch).virtualPrice(tranche) / ONE_TRANCHE` instead of trusting user input.

### Proof of Concept
Foundry PoC (extend `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`, run while `isEpochRunning()` is true):

```solidity
function testUnderpricedWriteOffRequestStealsTranches() external {
    uint256 trancheAmount = 10_000e18;

    // victim mistakenly requests 0 underlyings for real tranche tokens
    vm.prank(LP);
    escrow.createWriteOffRequest(trancheAmount, 0);

    // attacker is any EOA (here a KYC-passing wallet); no underlying needed
    address attacker = makeAddr("attacker");
    uint256 attackerTranchePre = tranche.balanceOf(attacker);

    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, trancheAmount, 0);

    // attacker received all tranche tokens for 0 underlying
    assertEq(tranche.balanceOf(attacker) - attackerTranchePre, trancheAmount);
    (uint256 tranches, uint256 underlyings) = escrow.userRequests(LP);
    assertEq(tranches, 0);
    assertEq(underlyings, 0);
}
```

The existing test suite confirms `fullfillWriteOffRequest` accepts third-party fulfillers and that a `_underlyings` equal to the requested amount succeeds — the only difference here is the requested amount being zero, which the contract never rejects.

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });

  }

  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
