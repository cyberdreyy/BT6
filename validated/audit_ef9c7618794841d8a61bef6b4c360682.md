### Title
Attacker-owned dust withdraw request permanently bricks `processWithdrawRequests` via `Is0()` revert - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
CVE-2020-8620 is a reachable-assertion crash: an unprivileged client sends crafted input that trips an assertion and halts the server. The analog in this codebase is a user-controlled dust withdrawal request in `IdleCDOEpochQueue` that makes `processWithdrawRequests()` hit `revert Is0()` on every call, so the epoch's queued withdrawals can never be processed while the dust request remains.

### Finding Description
In `processWithdrawRequests()` the queue aggregates `epochPendingWithdrawals[_epoch]` (tranche tokens) and calls `IdleCDOEpochVariant.requestWithdraw(_pending, tranche)`, which returns `_underlyingsRequested`. The implied epoch price is then computed as:

```solidity
uint256 _epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending;
if (_epochPrice == 0) {
  revert Is0();
}
epochWithdrawPrice[_epoch] = _epochPrice;
``` [1](#0-0) 

`_underlyings` in the CDO is `_amount * tranchePrice / ONE_TRANCHE_TOKEN` (`_trancheToUnderlyings`), so when the tranche trades below par (e.g., AA price < `ONE_TRANCHE` after a loss epoch, which is routine in this design) a tiny `_pending` can satisfy `_underlyingsRequested * ONE_TRANCHE < _pending`, i.e. `_underlyingsRequested == 0` or rounds to a zero implied price. An unprivileged, KYC-passing queue user only needs to deposit once and call the queue's `requestWithdraw` with a dust tranche amount (down to a few wei of tranche tokens) during the buffer phase of an epoch where honest users have pending requests — or even alone. Because `epochPendingWithdrawals[_epoch]` is never reset on revert and `deleteWithdrawRequest` can only remove the caller's own entry, the dust entry cannot be removed by the manager or by other users:

```solidity
function deleteWithdrawRequest(uint256 _requestEpoch) external {
  _checkNotAllowed(epochWithdrawPrice[_requestEpoch] != 0 || isEpochWithdrawZero[_requestEpoch]);
  uint256 amount = userWithdrawalsEpochs[msg.sender][_requestEpoch];
  ...
  epochPendingWithdrawals[_requestEpoch] -= amount;
  IERC20Detailed(tranche).safeTransfer(msg.sender, amount);
}
``` [2](#0-1) 

Every subsequent `processWithdrawRequests()` for that epoch re-aggregates `_pending` including the dust and reverts at the same `Is0()` check — a permanent revert exactly mirroring the CVE's "assertion failure kills the process" semantics. The zero-price claim path added for `processWithdrawalClaims` (`isEpochWithdrawZero`) proves the codebase already treats a zeroed epoch price as a terminal condition that must not block users, but no equivalent escape exists on the request side.

### Impact Explanation
All tranche tokens queued for withdrawal in the poisoned epoch remain locked in the queue until every honest user individually calls `deleteWithdrawRequest` and abandons the batched claim flow; the epoch can never transition to the claimable state (`epochWithdrawPrice[_epoch]` stays 0, `epochPendingClaims` is never set). Attacker cost is a dust deposit and two transactions; the freeze is indefinite if the attacker never deletes, and the attack is repeatable every epoch. The analogous `Is0` guard was added specifically to protect this path, which confirms a zero implied price is a reachable, unhandled attacker-controlled state rather than an impossibility.

### Likelihood Explanation
Requirements: tranche price below par so that a dust request yields `_underlyingsRequested == 0` (common after any loss epoch, or immediately for BB tranches priced below 1), and a queue-using deployment. The attacker is any KYC-passed queue user; no privileged role needed. Since `epochPendingWithdrawals` is a sum, even a large honest `_pending` does not prevent the attack if `price < ONE_TRANCHE` strongly enough that the whole sum still rounds to a zero implied price — otherwise the attacker waits for/forces an epoch where the aggregate pending amount is small (e.g., first-requester front-run).

### Recommendation
Replace the hard `revert Is0()` in `processWithdrawRequests()` with the same terminal-zero bookkeeping used in `processWithdrawalClaims()`: set `epochWithdrawPrice[_epoch] = 0`, set `isEpochWithdrawZero[_epoch] = true`, still forward the (zero) request, clear `epochPendingWithdrawals[_epoch]`, and let users exit via `claimWithdrawRequest`/`deleteWithdrawRequest`. Alternatively, skip zero-value forwarding and mark the epoch zero-priced without calling `requestWithdraw`.

### Proof of Concept
```solidity
// Foundry fork-style PoC against test/foundry/IdleCDOEpochQueue.t.sol setup
function testDustRequestBlocksProcessWithdrawRequests() external {
    // Depreciate the tranche below par so dust requests convert to 0 underlyings
    _startEpochAndCheckPrices(0);
    _createLoss(50_000); // 50% loss -> AA/BB price < ONE_TRANCHE
    vm.prank(owner);
    cdoEpoch.updateAccounting();
    _stopEpochAndCheckPrices(0, initialProvidedApr, 0);

    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 10 * ONE_SCALE, true);

    uint256 dust = 1; // 1 wei of tranche tokens; price<1 => _underlyingsRequested == 0
    vm.prank(attacker);
    queue.requestWithdraw(dust); // queue-level request into epochPendingWithdrawals

    // Every processing attempt for this epoch reverts identically, forever
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(Is0.selector));
    queue.processWithdrawRequests();

    // Manager retries after honest users' requests accumulate: still reverts
    _requestWithdrawWithUser(FASA, ONE_TRANCHE);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(Is0.selector));
    queue.processWithdrawRequests();

    // Manager cannot remove attacker's entry; attacker never deletes => epoch
    // stays unprocessed, epochWithdrawPrice==0, no claims possible for the epoch.
    assertEq(queue.epochWithdrawPrice(strategy.epochNumber()), 0);
    assertEq(queue.epochPendingWithdrawals(strategy.epochNumber()) != 0, true);
}
```
Reproduction notes: run against the existing `IdleCDOEpochQueue.t.sol` harness; the exact dust bound is `amount < ONE_TRANCHE / tranchePrice` tranche wei where `tranchePrice = cdoEpoch.virtualPrice(tranche)`. If the honest aggregate is large enough that `_underlyingsRequested` stays nonzero, the attacker instead submits the request while `epochPendingWithdrawals` is still below the threshold (first in the buffer window, or in a low-activity epoch), which is sufficient since the revert blocks that epoch's processing regardless of later additions.
