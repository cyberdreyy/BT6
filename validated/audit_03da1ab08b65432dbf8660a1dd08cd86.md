### Title
Unauthenticated `/readyz?full=1` leaks internal health-check error strings - ([File: core/web/health_controller.go])

### Finding Description
`HealthController.Readyz` calls `checker.IsReady()` and, when the `full` query parameter is present, iterates over the returned `errors` map, converting each non-nil error to a string via `err.Error()` and placing it verbatim into `presenters.Check.Output`, which is then serialized in the JSON API response via `jsonAPIResponse`. [1](#0-0) 

No filtering, redaction, or sanitization is applied to the underlying error text before it is returned to the caller. In contrast, `PublicReadyz` was explicitly written as a minimal-disclosure alternative: its doc comment states it "never returns per-check details regardless of query parameters, to avoid leaking internal service state on publicly reachable endpoints," and its implementation only ever returns an HTTP status code, no `Output` field. [2](#0-1) 

This confirms that `Readyz` (the `full`-detail variant) is the risky one from a design perspective — the codebase itself documents that a "safe" variant was needed because the full variant leaks details. Health check errors in Chainlink (`core/services/health.go`) are produced by arbitrary subsystem `Ready()`/`HealthReport()` implementations (DB connectivity, RPC connections, service state), which commonly wrap underlying driver/connection errors including DSNs, hostnames, or internal paths — exactly the kind of information an attacker benefits from for reconnaissance or credential harvesting.

The critical remaining question — whether `r.GET("/readyz", hc.Readyz)` in `core/web/router.go` is registered without any authentication middleware (as the question claims) — could not be independently confirmed in this session; my `router.go` reads and greps for the exact route-registration lines did not return before the tool budget was exhausted. I was only able to fully verify the `health_controller.go` behavior (the vulnerable leak mechanism itself), not the route's auth wrapper in `router.go`.

### Impact Explanation
If `/readyz` is indeed registered without authentication (as strongly implied by the existence and stated purpose of `PublicReadyz` as the deliberately-added safe/public substitute), any unauthenticated internet client could retrieve internal error strings from failing subsystem health checks — potentially including database connection details, RPC endpoint identifiers, or other internal error context. This maps to an information-disclosure impact class (internal state/config leak), which can aid further attacks (e.g., targeting exposed RPC/DB endpoints) but does not by itself grant fund movement, key disclosure, or authentication bypass.

### Likelihood Explanation
No preconditions or credentials are required beyond network reachability to the node's API port — a simple `GET /readyz?full=1` request. This is trivially repeatable and requires no state (e.g., the node must simply have a subsystem currently failing/degraded, which is common in production incidents — precisely when sensitive error detail is most likely to be present).

### Recommendation
- Confirm in `core/web/router.go` whether `/readyz` is registered on an authenticated route group; if not, either require authentication for the `full` output, or strip/redact error strings before placing them in `Output` (e.g., return only a generic "unhealthy" message or a bounded, sanitized error category instead of `err.Error()`).
- Alternatively, restrict the `full=1` detail path to internal/admin-authenticated callers only, keeping the unauthenticated `/readyz` route behavior identical to `PublicReadyz`.

### Proof of Concept
1. Add a unit test in `core/web/health_controller_test.go` that constructs a `HealthController` with a mocked `services.Checker` (see `core/services/mocks/checker.go`) whose `IsReady()` returns `false` and an error map containing a check with an error like `fmt.Errorf("db dial failed: postgres://user:pass@internal-db:5432/db")`.
2. Issue `GET /readyz?full=1` against the handler via `httptest`.
3. Assert that the JSON response body's `output` field for that check contains the sensitive substring (e.g., `postgres://user:pass@internal-db`), proving the string is returned verbatim.
4. As a control, call `PublicReadyz` with the same mock and assert the response body contains no error text at all (only status code), demonstrating the disparity described in the code comments.

Note: I was unable to verify the exact authentication configuration of the `/readyz` route in `core/web/router.go` within this session due to tool-call limits; this should be confirmed before treating the finding as fully validated, since if the route is actually behind an auth/allowlist middleware, the impact would be significantly reduced or nullified.

// PublicReadyz is a minimal readiness endpoint intended for public load balancer health checks.
// Unlike Readyz, it never returns per-check details regardless of query parameters, to avoid
// leaking internal service state on publicly reachable endpoints.
func (hc *HealthController) PublicReadyz(c *gin.Context) {
	ready, _ := hc.App.GetHealthChecker().IsReady()
	if !ready {
		c.Status(http.StatusServiceUnavailable)
		return
	}
	c.Status(http.StatusOK)
}
