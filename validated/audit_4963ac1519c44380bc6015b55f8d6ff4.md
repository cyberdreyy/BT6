### Title
Shared `maxCacheSize` in `requestCache[T].NewRequest` allows single-sender DoS against other senders' requests - ([File: core/services/gateway/handlers/common/requestcache.go])

### Finding Description
`NewRequest` keys pending entries by `globalId{sender, id}` [1](#0-0) , but the capacity check is a single global counter that applies to `len(c.cache)` across all senders combined, with no per-sender/per-token quota: `if len(c.cache) >= int(c.maxCacheSize) { return errors.New("request cache is full") }` [2](#0-1) . Any caller able to submit distinct `(sender, MessageId)` pairs that never receive a matching `ProcessResponse` can occupy slots for up to `c.timeout` (a single fixed duration for the whole cache, set once in `NewRequestCache`) [3](#0-2) [4](#0-3) . Once `len(c.cache) >= maxCacheSize`, every other sender's `NewRequest` call is rejected with "request cache is full" regardless of who they are, so there is no quota isolation across authorization scopes at this layer.

### Impact Explanation
If reachable by an unprivileged/low-trust caller, this is a shared-resource exhaustion (DoS) against other legitimate senders' job/run requests processed through this gateway handler cache, matching a node-availability/DoS bounty class rather than a data-confidentiality or fund-movement issue.

### Likelihood Explanation
I was unable to confirm, within this session, that `requestCache`/`NewRequestCache` is actually wired into a production gateway handler reachable by attacker-controlled input in this repository snapshot — the only call sites for `NewRequestCache` found are in `requestcache_test.go`; I did not find a production handler invoking it with attacker-supplied `sender`/`MessageId` values, nor could I verify whether an upstream allowlist/rate-limiter (e.g., gateway connector per-sender rate limiting) already caps the number of concurrent unresolved requests per sender before they reach this cache. Without confirming (a) a live production call path from an unauthenticated/low-privileged gateway message into `NewRequest`, and (b) absence of an upstream per-sender request-rate cap, I cannot confirm this is currently exploitable end-to-end. This is a genuine architectural gap in `requestCache` itself (no per-sender partitioning of `maxCacheSize`), but confirming exploitability requires tracing the concrete handler wiring, which I could not complete with the tools/searches available in this session.

### Recommendation
Partition capacity per sender (e.g., track counts per `sender` and enforce a per-sender sub-limit in addition to the global `maxCacheSize`), or require any handler wiring `requestCache` into an attacker-reachable path to enforce its own per-sender/per-token rate limiting before calling `NewRequest`.

### Proof of Concept
1. In `requestcache_test.go`, construct `NewRequestCache[T](timeout, maxCacheSize)` with a small `maxCacheSize` (e.g., 2).
2. From sender A, call `NewRequest` `maxCacheSize` times with unique `MessageId`s and no corresponding `ProcessResponse` calls.
3. From sender B, call `NewRequest` once and assert it returns `"request cache is full"` even though sender B has zero pending entries — demonstrating no per-sender isolation.
4. Additionally confirm (or refute, if found later) whether a production handler exposes `NewRequest` to attacker-controlled `sender`/`MessageId` without an upstream per-sender cap, since that determines real-world exploitability beyond this unit-level demonstration.
