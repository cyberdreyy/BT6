### Title
Cross-user response hijacking via unkeyed `savedCallbacks[msg.Body.MessageId]` overwrite - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each pending callback in `h.savedCallbacks` keyed **only** by the attacker/client-supplied `msg.Body.MessageId`, with no uniqueness check and no binding to the requester's identity (sender). A second request using the same `MessageId` silently overwrites the first entry, so the DON's eventual response gets delivered to the second requester's `Callback` instead of the original one, and the original requester never receives the correct response.

### Finding Description
`HandleLegacyUserMessage` is reached from `gateway.ProcessRequest` [1](#0-0)  for every legacy JSON-RPC request, using a fresh `handlerscommon.NewCallback()` per HTTP call and `msg.Body.MessageId` derived directly from the client-supplied JSON-RPC request `ID` [2](#0-1) . The `MessageId` is attacker-controlled: it is only bounds-checked for length in `Message.Validate` [3](#0-2)  and is not tied to the sender's signer address for uniqueness purposes.

There is no check for an existing entry at that key before overwriting, and the map key is the bare `MessageId` string — it does not incorporate `msg.Body.Sender` (which is validated via signature in `Validate`/`ExtractSigner`). When the DON node responds, `handleWebAPITriggerMessage` looks the callback up purely by `MessageId` and delivers the response to whatever `Callback` is currently stored: [5](#0-4) 

Notably, a sibling component, `RequestCache`, already fixes this exact class of bug by keying pending requests on `{sender, id}` rather than `id` alone: [6](#0-5) 
This confirms the intended invariant (uniqueness scoped per-sender) that `capabilities/handler.go`'s `savedCallbacks` map fails to enforce.

Exploit flow: Attacker A sends a `web_api_trigger` message with `MessageId = X` signed with their own key. While it is still pending (up to `CallbackMaxAgeSec`, default 120s), attacker/second requester B sends another `web_api_trigger` message with the same `MessageId = X` (a different, independently valid signature is fine — `Validate()` only checks signature validity, not ID exclusivity). B's `Callback` overwrites A's entry in `h.savedCallbacks[X]`. When the DON node responds to A's original request with the same `MessageId` (mirrored back by the node), `handleWebAPITriggerMessage` delivers that response to B's callback, i.e., B receives data destined for A, while A's original HTTP call from the gateway hangs until its own request context/`callback.Wait` times out.

### Impact Explanation
This is a cross-user response confusion / request-impersonation issue: an unprivileged, unauthenticated-by-role client can cause another in-flight user's DON response (potentially containing that user's requested data/results) to be delivered to the attacker instead, and can deny/garble the legitimate requester's response. This matches the bounty's "cross-user response confusion" and "request impersonation" impact classes.

### Likelihood Explanation
The only precondition is knowledge or a successful guess of the victim's `MessageId` while their request is still pending (within the callback TTL, default 120s). No privileged access is needed — the gateway processes signed requests from any address per the code path shown; a valid ECDSA signature over attacker-controlled data is all that's required by `Validate()`. If client `MessageId`s are predictable, sequential, reused, or observable (e.g., via shared client libraries, low entropy, or race conditions on shared IDs), this is trivially and repeatably exploitable; even without prediction, it's a straightforward reliability/security invariant violation that a background test can deterministically reproduce by choosing the same ID for two different callbacks.

### Recommendation
Key `savedCallbacks` (and the analogous map in `handler.dummy.go`) by a composite of `{Sender, MessageId}` rather than `MessageId` alone, mirroring the `RequestCache` pattern, and reject/ignore a `HandleLegacyUserMessage` call that would collide with an existing pending entry for a *different* sender (return an error to the caller instead of silently overwriting).

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler via `NewHandler`, backed by a mock `handlers.DON`.
2. Build two valid `api.Message`s with identical `Body.MessageId` and `Body.Method = MethodWebAPITrigger`, but signed by two different private keys (two different `Body.Sender`), each with a distinct mock `handlers.Callback` (`callbackA`, `callbackB`) that records `SendResponse` invocations.
3. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` then `h.HandleLegacyUserMessage(ctx, msgB, callbackB)`.
4. Assert: either the second call returns an error (desired fixed behavior) OR — demonstrating the current bug — inspect `h.savedCallbacks[MessageId]` and show it now points to `callbackB`, not `callbackA`.
5. Simulate a node response via `h.HandleNodeMessage` (or directly call `handleWebAPITriggerMessage`) with the shared `MessageId`; assert that `callbackB.SendResponse` was invoked (hijack) while `callbackA.SendResponse` was never called — proving cross-user response delivery instead of rejection/isolation.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
