### Title
Prior-epoch unfunded instant-withdraw receipts are excluded from the default recovery basis and prefunded reserve, inflating `defaultRecoveryPrice` and leaving excluded claimants unpayable - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug class — expired/historical positions silently dropped from an entitlement calculation — maps to `IdleCreditVault.finalizeDefaultRecovery`. `defaultPendingClaimBasis()` counts pending normal withdraws globally (`pendingWithdraws`) but counts instant-withdraw receipts only for the current epoch (`instantWithdrawClaimsByEpoch[epochNumber]`). Symmetrically, `_defaultPrefundedInstantReserve()` only counts prefunded backing for the current epoch. Instant receipts requested in an earlier epoch that remain unfunded (`pendingInstantWithdraws != 0`) or partially prefunded are therefore invisible to finalization, even though they are still valid claims on `instantWithdrawsRequests` that are later paid at par by `claimInstantWithdrawRequest`/`_transferFundedClaim`. [1](#0-0) [2](#0-1) 

### Finding Description
`requestInstantWithdraw` records receipts under `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and aggregates `instantWithdrawClaimsByEpoch[currentEpoch]`, while `pendingInstantWithdraws` is a cross-epoch unfunded remainder decremented only by `collectInstantWithdrawFunds`. [3](#0-2)  If the CDO only partially funds the instant bucket in epoch E1, a nonzero remainder survives into E2. When a default is finalized in E2:

1. `defaultPendingClaimBasis` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[E2]` — the E1 unfunded instant basis is missing from `totalBasis`. [1](#0-0) 
2. `_defaultPrefundedInstantReserve` computes `instantWithdrawClaimsByEpoch[E2] - pendingInstantWithdraws`, which can understate (or even wrongly attribute) already-held backing, because `pendingInstant` includes E1's remainder while `instantBasis` is E2-only. [2](#0-1) 
3. `recoveryPrice = reserveAmount / totalBasis` is then computed over a denominator that omits legitimate claimants. [4](#0-3) 

After finalization, E1 instant receipts are still paid at par through `claimInstantWithdrawRequest` → `_transferFundedClaim`, which draws against `defaultRecoveryReserve` without those claims ever having been provisioned. [5](#0-4) [6](#0-5) 

### Impact Explanation
The recovery reserve is under-provisioned: `defaultRecoveryPrice` is overstated because the basis excludes prior-epoch instant claims, so included claimants (defaulted-epoch withdraw/instant receipts and active LPs via the NAV adjustment) are paid above the fair ratio. The uncounted instant claimants, who must be paid at par, find the reserve drained — a direct loss of funds for whoever claims last, i.e. insolvency/permanent unpayability of valid receipts. Loss magnitude equals up to the full value of the excluded instant basis (unbounded by the reserve, limited only by `instantWithdrawClaimsByEpoch` of earlier epochs minus their funded portion).

### Likelihood Explanation
Requires: instant withdrawals enabled (`setInstantWithdrawParams`), an instant request that is only partially funded by the CDO so `pendingInstantWithdraws` stays nonzero into a subsequent epoch, and then a borrower default finalized via `finalizeDefault`/`finalizeDefaultRecovery`. Partial funding is an expected state (prefunded instant flow is explicitly supported), and the attacker path is unprivileged — a KYC'd lender requests an instant withdraw that happens to remain unfunded, then defaults make every excluded receipt holder a victim; no attacker can force the default, so likelihood is moderate-low, matching the "severity via mispriced recovery" class rather than active theft.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, aggregate `instantWithdrawClaimsByEpoch` across all epochs with outstanding claims (or track a global `totalInstantClaimBasis` incremented at `requestInstantWithdraw` and decremented at claim/finalization), so prior-epoch unfunded and prefunded instant receipts enter `totalBasis`/`reserveAmount` symmetrically. Also revisit `pendingInstantWithdraws -= claimBasis` clamping in `_claimDefaultedInstantWithdrawRequest`, which already assumes epoch attribution is lossy. [7](#0-6)

```solidity
// 1. Deposit with userA (AA), enable instant withdraws via manager.
// 2. Epoch E1 running: userA requestInstantWithdraw(amountA).
//    Borrower/CDO funds only part -> pendingInstantWithdraws = unfunded remainder > 0.
// 3. stopEpoch / startEpoch into E2 WITHOUT fully collecting instant funds.
//    instantWithdrawClaimsByEpoch[E1] retains userA's residual basis.
// 4. In E2, userB requestWithdraw (normal) -> pendingWithdraws = basisB.

//    finalizeDefaultRecovery computes
//      totalBasis = activeBasis + pendingWithdraws + instantWithdrawClaimsByEpoch[E2]
//    userA's E1 remainder is absent -> recoveryPrice overstated.
// 6. userB claims defaulted receipt at inflated price, draining reserve.
// 7. userA claimInstantWithdrawRequest -> _transferFundedClaim pays at par
//    but reserve is exhausted -> transfer underpays/reverts.
//    assertLt(userAReceived, amountA) // lost funds
```

Caveat: I verified the exclusion logic statically; I did not fully trace every call site of `collectInstantWithdrawFunds`/`claimInstantWithdrawRequest` in `IdleCDOEpochVariant` to confirm a cross-epoch unfunded remainder is reachable in production configurations (it is clearly supported by the prefunded-instant code paths), so the PoC should confirm step 3 reachability first.
