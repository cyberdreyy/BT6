## Title
Unbounded cost for `getTokenAccountsByOwner`/`getTokenAccountsByDelegate` via unauthenticated SPL token account owner/delegate field, no default scan byte limit - ([File: rpc/src/rpc.rs], [File: accounts-db/src/accounts_index/secondary.rs], [File: accounts-db/src/accounts_db.rs])

### Summary
The external report describes a pattern where an unprivileged actor can permissionlessly append entries into a data structure keyed by a victim's address (bypassing any factory/authorization check), causing a single legitimate query that must iterate "all entries for that key" to become unbounded and effectively unusable. Agave has a structurally identical pattern in its SPL-token secondary index (`SplTokenOwner`/`SplTokenMint`): anyone can create an arbitrary number of SPL Token accounts whose `owner` (or `mint`) field points at any victim pubkey, with no signature or authorization from that pubkey required. Each such account is indexed under the victim's pubkey in `spl_token_owner_index`/`spl_token_mint_index`. When the victim (or anyone) later calls `getTokenAccountsByOwner`/`getTokenAccountsByDelegate`, the RPC/accounts-db layer must load every indexed pubkey for that key in a single request. The size-based abort protection (`scan_results_limit_bytes`) is **not enabled by default**, so the scan is effectively unbounded unless the operator explicitly sets `--accounts-index-scan-results-limit-mb`.

### Finding Description
`SecondaryIndex::insert` unconditionally appends the created account's pubkey to the `index` map keyed by the account's `owner`/`mint` field, with no restriction on who can trigger this or how many entries a single key can accumulate: [1](#0-0) 

This is populated for every stored account whenever `AccountIndex::SplTokenOwner`/`SplTokenMint` is enabled, via `update_secondary_indexes`, which unpacks the token account's `owner_key`/`mint_key` directly from account data — fields fully controlled by whoever creates the token account, not requiring any signature from the referenced owner: [2](#0-1) 

When a client calls `getTokenAccountsByOwner`, the request processor uses this secondary index and passes `byte_limit_for_scan = self.config.scan_results_limit_bytes` down to the scan: [3](#0-2) [4](#0-3) 

The actual scan (`index_scan_accounts`) iterates over **every** pubkey returned for the index key and performs a full `do_load` (account fetch) for each one before any abort check can trigger, since the abort is only ever set from inside the accumulate/filter callback: [5](#0-4) 

The byte-accumulation guard that is supposed to bound this cost is a no-op when `byte_limit_for_scan` is `None`: [6](#0-5) 

Critically, the corresponding CLI flag `--accounts-index-scan-results-limit-mb` has **no `default_value`**, so `scan_results_limit_bytes` is `None` unless the operator explicitly configures it: [7](#0-6) [8](#0-7) 

This mirrors the reported bug exactly: an unprivileged actor "deploys" (creates) many cheap objects (SPL token accounts) that are pushed into an index keyed by an arbitrary target ("owner") they do not control and did not need permission from, with no access control on registration. A single subsequent query against that key must iterate the full, attacker-inflatable list.

### Impact Explanation
On any RPC node that has enabled the `spl-token-owner` (or `spl-token-mint`) secondary index without also setting `--accounts-index-scan-results-limit-mb`, an attacker can create an unbounded number of low-cost SPL Token accounts (each merely rent-exempt-minimum lamports, ~0.002 SOL) with the `owner` field set to any victim pubkey. A single subsequent `getTokenAccountsByOwner` call for that victim then forces the RPC thread to load every one of those accounts from accounts-db in one request — unbounded CPU/IO cost for a single low-rate call, and a persistent denial of service against that specific RPC method for the targeted address (the legitimate owner can no longer successfully enumerate their own token accounts via this call without the operator tuning the limit or the spam accounts being closed).

### Likelihood Explanation
Requires the operator to have enabled `--account-index spl-token-owner` (or `spl-token-mint`) — a documented, non-default but commonly used feature for RPC/API nodes that need `getTokenAccountsByOwner`/`getTokenAccountsByDelegate` support. Given that flag is set, the attack requires no special privilege, only paying rent for account creation, which is cheap and can be automated to create very large numbers of victim-targeted accounts over time.

### Recommendation
Apply a sane non-`None` default for `scan_results_limit_bytes` (i.e., give `accounts_index_scan_results_limit_mb` a `default_value`) so the byte-based abort is always active unless explicitly disabled, and/or bound the number of raw pubkeys pulled from `get_index_key_pubkeys` per request (independent of the loaded account size) before doing any `do_load` calls.

### Proof of Concept
1. Start a node with `--account-index spl-token-owner` and do **not** pass `--accounts-index-scan-results-limit-mb`.
2. As an unprivileged attacker, repeatedly submit `InitializeAccount`/`InitializeAccount3` instructions for the SPL Token program creating new token accounts, setting the `owner` field to a victim pubkey `V` (no signature from `V` is required for this field).
3. Repeat until a very large number (e.g. hundreds of thousands) of token accounts are indexed under `V` in `spl_token_owner_index`.
4. Call `getTokenAccountsByOwner(V, {"programId": TOKEN_PROGRAM_ID})` from any client: `index_scan_accounts` (`accounts-db/src/accounts_db.rs:3398-3410`) iterates and `do_load`s every one of the injected pubkeys in that single RPC call, with no abort triggered because `byte_limit_for_scan` is `None`, causing excessive latency/resource consumption for that single request and effectively denying the legitimate use of the RPC method for `V`.

        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.

            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because

        // a map created, so optimize for the common case and only take a read lock.

            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

    /// Accumulate size of (pubkey + account) into sum.
    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }
