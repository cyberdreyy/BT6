### Title
User enumeration via distinguishable authentication error content/timing in local `AuthenticationProvider.CreateSession` - (File: core/sessions/localauth/orm.go)

### Summary
`POST /sessions` (`SessionsController.Create`) forwards the raw error returned by `AuthenticationProvider.CreateSession` directly into the HTTP response body, and the local-auth ORM implementation returns a different, unwrapped error ("Invalid password" vs. the raw `sql: no rows in result set` from `FindUser`) depending on whether the submitted email exists, with the latter path additionally requiring a bcrypt comparison that the former path skips entirely. This produces both a content-based and a timing-based side channel that lets an unauthenticated caller distinguish valid emails from invalid ones.

### Finding Description
`SessionsController.Create` binds the request and calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)`, then returns any error verbatim via `jsonAPIError(c, http.StatusUnauthorized, err)`: [1](#0-0) 

`jsonAPIError` writes `err.Error()` directly into the JSON response body when the error is not a `*models.JSONAPIErrors`: [2](#0-1) 

The local ORM's `CreateSession` first calls `FindUser`, and on failure (unknown email → `sql.ErrNoRows`) returns immediately with that raw driver error, without ever touching password hashing: [3](#0-2) 

For an existing email, it proceeds to a constant-time email compare and then `utils.CheckPasswordHash` (bcrypt comparison), returning the distinct string `"Invalid password"` on mismatch: [4](#0-3) 

Both paths return HTTP 401, so status code alone does not leak information, but:
1. **Response body content differs**: unknown email yields `sql: no rows in result set` (or similar raw SQL driver text) in the JSON error body, while a known email with a wrong password yields the distinct string `"Invalid password"`.
2. **Timing differs**: only the known-email path executes a bcrypt comparison in `utils.CheckPasswordHash`, which is deliberately CPU-expensive (typically tens of milliseconds), whereas the unknown-email path returns after a single indexed DB lookup that immediately errors.

Neither `sessions_controller.go` nor the ORM normalizes these error paths to a uniform message/timing before returning to the client, so both signals are observable to an unauthenticated HTTP client reaching `/sessions`.

### Impact Explanation
This allows an unauthenticated attacker to enumerate valid operator/admin email addresses on the node by observing response body text and/or response timing for `POST /sessions`. This is an information-disclosure / reconnaissance primitive: it narrows subsequent credential-stuffing or brute-force attacks to confirmed accounts, but does not by itself grant session creation, privilege escalation, or key export. Contrary to the "Critical" impact suggested in the question, on its own this maps more accurately to a **Low/Informational** classification (username/account enumeration) under typical bounty impact taxonomies — it is a precondition that assists a follow-on credential attack, not a direct authentication bypass or node takeover. Node takeover would require an additional, separate weakness (e.g., a guessable or weak/default operator password), which is outside the scope of this specific code path.

### Likelihood Explanation
Trivial to exploit: no privileges are required beyond network reachability to the node API port. An attacker sends `POST /sessions` with a candidate email/password pair and inspects the JSON error text and/or measures response latency; repeating this across a wordlist of candidate emails reliably classifies each as "exists" or "does not exist" with no rate-limiting bypass needed beyond the existing unauthenticated rate limiter (`rl.UnauthenticatedPeriod()`), which does not prevent enumeration, only throttles its speed: [5](#0-4) 

### Recommendation
- In `core/sessions/localauth/orm.go` `CreateSession`, return a single generic, constant error message (e.g., `"invalid email or password"`) for both the "user not found" and "wrong password" cases, rather than propagating the raw `FindUser` error or a distinct `"Invalid password"` string.
- Ensure a dummy/constant-cost bcrypt comparison (e.g., against a fixed dummy hash) is always performed on the unknown-email path so response timing is equalized between known and unknown accounts.
- In `core/web/helpers.go`/`sessions_controller.go`, avoid forwarding raw internal errors (e.g., SQL driver errors) into `err.Error()` for auth-related responses; wrap them in a fixed, generic auth-failure message before calling `jsonAPIError`.
- Apply the same normalization to `ldapauth` and `oidcauth` implementations of `CreateSession`, which show similar patterns of distinguishing "user not in upstream"/"no local user" from bind/credential failures.

### Proof of Concept
Go handler-level integration test (extending existing `TestSessionsController_Create` at `core/web/sessions_controller_test.go`):
1. Create one known user via `app.AuthenticationProvider().CreateUser`.
2. Table-drive requests to `POST /sessions`:
   - `{knownEmail, wrongPassword}`
   - `{unknownEmail, anyPassword}`
3. For each case, capture: HTTP status code, full response body, and wall-clock duration of the request (using `time.Now()`/`time.Since()` around `client.Do(request)`).
4. Assertions:
   - `require.NotEqual(t, bodyKnownWrongPw, bodyUnknownEmail)` — currently fails to be equal, proving content-based enumeration (expected: they should be equal/generic).
   - Compare mean latency over N repeated trials for each case; assert `durationKnownWrongPw` is statistically distinguishable (e.g., >2x) from `durationUnknownEmail` due to bcrypt cost — proving timing-based enumeration (expected: comparable timing after fix, e.g., via dummy-hash comparison on the unknown path).

**Uncertainty note**: I could not fully verify the exact wrapped/unwrapped text of the `sql.ErrNoRows` as it propagates through `sqlx.GetContext` in this codebase version (whether it's returned as literal `"sql: no rows in result set"` or a wrapped variant), nor could I inspect the exact bcrypt cost factor configured via `utils.CheckPasswordHash`/`GenerateHashFromPassword` due to iteration limits. These details would need to be confirmed by running the described PoC against a live node instance.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
