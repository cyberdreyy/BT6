### Title
Post-default instant-withdraw receipts escape the 1:1 post-default path and are double-haircut or frozen - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` contains an explicit `defaultRecoveryFinalized` branch that prices new receipts at the already-haircut `virtualPrice` and pays them 1:1 from the recovery reserve via `postDefaultRequests`. `requestInstantWithdraw` has no equivalent branch: post-default instant receipts are recorded into `instantWithdrawsRequestsByEpoch[user][epochNumber]`, where `epochNumber == defaultRecoveryEpoch`, so `claimInstantWithdrawRequest` routes them through `_claimDefaultedInstantWithdrawRequest` and applies `defaultRecoveryPrice` a second time. When `defaultInstantWithdrawsFinalized` is false, the claim instead falls through to `_transferFundedClaim`, whose reserve guard makes it permanently revert. Like the SSHFS `transform_symlinks` early return that lets relative targets escape containment, the post-default mitigation covers the normal-request path but not the instant-request variant.

### Finding Description
After `finalizeDefaultRecovery`, `epochNumber` no longer advances, so `defaultRecoveryEpoch == epochNumber` forever.

- `requestWithdraw` (lines 247-257) detects `defaultRecoveryFinalized`, blocks users with open receipts, and stores the haircut-priced amount in `postDefaultRequests`, later paid 1:1 by `_claimPostDefaultWithdrawRequest` (lines 760-767). This is the intended post-default semantics: the haircut is applied once, at request time, through `virtualPrice`.
- `requestInstantWithdraw` (lines 356-375) has no `defaultRecoveryFinalized` check. It burns the CDO's strategy tokens, mints the same amount to the user, and adds `_amount` to `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`.

On claim, `claimInstantWithdrawRequest` (lines 380-393) behaves differently depending on `defaultInstantWithdrawsFinalized`:

1. If `defaultInstantWithdrawsFinalized == true` (there was an unfunded instant queue at finalization), `_claimDefaultedInstantWithdrawRequest` (lines 842-856) reads `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — which now includes the post-default request — and pays only `claimBasis * defaultRecoveryPrice / 1e18`. The receipt was already priced at the post-haircut `virtualPrice` when the CDO burned the tranche tokens, so the user is haircut twice, losing `(1 - defaultRecoveryPrice)` of a claim that the normal-request path would have paid in full.
2. If `defaultInstantWithdrawsFinalized == false` (instant queue was fully funded at finalization, `pendingInstantWithdraws == 0`), the defaulted-epoch clearing is skipped entirely. The new post-default receipt is paid via `_transferFundedClaim`, which reverts whenever `balance - defaultRecoveryReserve < amount` (line 904). Since after finalization essentially all strategy cash is the reserve, the claim reverts and the receipt is permanently unclaimable — the minted receipt tokens can never be redeemed (no other path burns them or pays out).

`requestInstantWithdraw` also skips the `_hasWithdrawRequest`/`instantWithdrawsRequests`/`postDefaultRequests` guard that `requestWithdraw` enforces post-default, so the two receipt systems can be interleaved in ways the finalized accounting was not designed for.

### Impact Explanation
Any tranche holder (unprivileged, KYC-passed lender) who requests an instant withdraw after default finalization either:

- loses `(1 - defaultRecoveryPrice) × amount` of a claim that should be paid at par (double haircut, paid from `defaultRecoveryReserve`, indirectly diluting/subsidizing other claimants), or
- has the receipt permanently frozen: `_transferFundedClaim` reverts with `NotAllowed` on every claim because there is no non-reserve balance to fund it, and `instantWithdrawsRequests`/`instantWithdrawsRequestsByEpoch` are never cleared, so the underlying is stranded in the strategy forever.

Quantified example: recovery price 0.7e18, user redeems tranche tokens worth 10,000 underlying post-haircut via instant withdraw → receives 7,000 (loses 3,000) in case 1, or 0 and a permanently stuck 10,000 receipt in case 2.

### Likelihood Explanation
Triggering requires only that a lender calls `requestInstantWithdraw` (via `IdleCDOEpochVariant.requestWithdraw` when instant withdrawals are enabled) after `finalizeDefaultRecovery`. No privileged cooperation is needed; manager/owner/borrower behave honestly. The protocol explicitly keeps request/claim UX alive post-default (`postDefaultRequests`), so users are expected to keep redeeming — instant requests are reachable whenever `allowedInstantWithdraw` is on. Likelihood is moderate: it needs the instant-withdraw feature enabled and a user choosing that path post-default, but the loss/freeze is deterministic once taken.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`:

- After `defaultRecoveryFinalized`, require the user has no open receipts (`_hasWithdrawRequest`, `instantWithdrawsRequests`, `postDefaultRequests` all zero), then record the receipt in `postDefaultRequests[_user]` instead of `instantWithdrawsRequestsByEpoch`/`pendingInstantWithdraws`, so `claimWithdrawRequest`'s `_claimPostDefaultWithdrawRequest` pays it 1:1 from the reserve.
- Alternatively (or additionally), revert post-default instant requests outright, and guard `claimInstantWithdrawRequest` so post-default entries in `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` cannot be mixed into `claimBasis` that predates finalization.

### Proof of Concept
Foundry test (pattern follows `test/foundry/IdleCreditVault.t.sol`, e.g. `testFinalizeDefaultHaircutsPendingInstantRedeems`):

```solidity
function testPostDefaultInstantWithdrawDoubleHaircut() external {
    address instantUser = makeAddr('postdefault-instant-user');
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 recoveryRatio = 7e17;

    // lender deposits AA before default
    _depositWithUser(instantUser, amount, true);

    // epoch 0 runs and defaults
    _startEpochAndCheckPrices(0);
    deal(defaultUnderlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _checkDefault();

    // honest manager finalizes recovery at 70%
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    uint256 totalBasis =
        cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest()
        - cdoEpoch.pendingWithdrawFees() + creditVault.defaultPendingClaimBasis();
    uint256 recovered = totalBasis * recoveryRatio / ONE_TRANCHE;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();
    assertTrue(creditVault.defaultRecoveryFinalized());

    // user requests an INSTANT withdraw post-default; receipt priced at post-haircut virtualPrice
    vm.prank(instantUser);
    uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche)); // instant path enabled
    // receipt == haircut-priced amount, same bucket a normal request would pay 1:1

    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(instantUser);
    vm.prank(instantUser);
    cdoEpoch.claimInstantWithdrawRequest();

    uint256 payout = IERC20Detailed(defaultUnderlying).balanceOf(instantUser) - balPre;
    // BUG: payout == receipt * defaultRecoveryPrice / 1e18, i.e. haircut applied twice,
    // while a normal requestWithdraw post-default would pay `receipt` in full via
    // postDefaultRequests/_claimPostDefaultWithdrawRequest.
    assertEq(payout, receipt * creditVault.defaultRecoveryPrice() / 1e18);
    assertLt(payout, receipt);

    // Variant (defaultInstantWithdrawsFinalized == false): swap claim for
    //   vm.expectRevert(NotAllowed.selector); cdoEpoch.claimInstantWithdrawRequest();
    // showing the receipt is permanently frozen behind the _transferFundedClaim reserve guard.
}
```

Root cause lines: `requestInstantWithdraw` missing the `defaultRecoveryFinalized` branch at `contracts/strategies/idle/IdleCreditVault.sol:356-375`, vs the handled branch at `:247-257`; misrouting through `_claimDefaultedInstantWithdrawRequest` (`:842-856`) or the reverting `_transferFundedClaim` guard (`:897-907`).
