### Title
Missing storage gap in `GuardedLaunchUpgradable` and `IdleCDOEpochVariant` corrupts child storage on upgrade - ([File: contracts/GuardedLaunchUpgradable.sol](contracts/GuardedLaunchUpgradable.sol))

### Summary
The credit-vault contracts are deployed behind `TransparentUpgradeableProxy` via `IdleCreditVaultFactory._deployProxy` [1](#0-0) . The deployed implementation chain is `IdleCDOEpochVariantPrefunded → IdleCDOEpochVariant → IdleCDOCreditVault → GuardedLaunchUpgradable / IdleCDOStorage`. While `IdleCDOStorage` correctly reserves `uint256[43] private __gap` [2](#0-1) , two inherited base contracts in the same layout reserve no gap at all:

- `GuardedLaunchUpgradable` declares `limit` and `governanceRecoveryFund` and ends without a `__gap` [3](#0-2) .
- `IdleCDOEpochVariant` declares ~20 new state variables (`isEpochRunning` … `isInterestMinted`) after the `IdleCDOStorage.__gap` block and is itself inherited by `IdleCDOEpochVariantPrefunded`, which appends its own storage [4](#0-3) .

### Finding Description
In `IdleCDOCreditVault is PausableUpgradeable, GuardedLaunchUpgradable, IdleCDOStorage` [5](#0-4) , `GuardedLaunchUpgradable`'s two slots sit directly before `IdleCDOStorage._lastCallerBlock` (confirmed in the recorded proxy layout, where `limit`/`governanceRecoveryFund` immediately precede `IdleCDOStorage` variables) [6](#0-5) . Because `GuardedLaunchUpgradable` has no `__gap`, adding even one state variable to it in a future implementation pushes every `IdleCDOStorage` variable down one slot: `token`, `guardian`, `strategy`, `AATranche`, `BBTranche`, `priceAA`, `priceBB`, `lastNAVAA`, `lastNAVBB`, `unclaimedFees`, `fee`, `feeReceiver`, `isProgrammableBorrower`, `managementFee` all decode from the wrong slots [7](#0-6) . The `// Add new variables here … reduce the __gap length` convention in `IdleCDOStorage` only protects variables added *inside* `IdleCDOStorage`; it cannot protect a sibling base contract.

The same defect exists one level down: `IdleCDOEpochVariant` defines storage after `IdleCDOStorage.__gap` with no gap of its own, yet `IdleCDOEpochVariantPrefunded` inherits it and adds variables. Any new variable in `IdleCDOEpochVariant` overwrites the prefunded child's first slots. Note `IdleCDOStorage` explicitly warns "IMPORTANT: Do not add any variables below `__gap`" [8](#0-7) , but `IdleCDOEpochVariant` does exactly that by design, making a gap at its end mandatory.

### Impact Explanation
An upgrade that adds a variable to `GuardedLaunchUpgradable` (e.g., a new guard flag) or to `IdleCDOEpochVariant` (a new epoch parameter) silently misaligns all descendant storage. Concretely, `strategy` would be read from the old `AATranche` slot, `defaulted`/`isEpochRunning` flags from unrelated slots, and `priceAA`/`priceBB`/`lastNAVAA` from shifted values. Deposits/withdrawals would then compute NAV and tranche minting from corrupted prices, withdrawals could route funds to an address read as `strategy`/`feeReceiver`, and `_updateAccounting` would socialize phantom losses — direct theft or permanent freezing of all vault TVL. This matches the "storage corruption during upgrade" bug class: a one-variable oversight produces total fund loss across every live credit-vault proxy.

### Likelihood Explanation
Likelihood is moderate: it requires a future upgrade performed by the honest owner/treasury that adds storage to a non-`IdleCDOStorage` base. The codebase shows active evolution in exactly these contracts (`isProgrammableBorrower`, `isBBDepositEnabled`, `managementFee` were recently appended to `IdleCDOStorage`, consuming its gap) [9](#0-8) , and epoch variants (`Prefunded`) already layer storage on `IdleCDOEpochVariant`. As the gap shrinks and features grow, adding fields to `IdleCDOEpochVariant` — the natural place for epoch parameters — is a realistic upgrade path that currently corrupts every `IdleCDOEpochVariantPrefunded` deployment.

### Recommendation
Append a storage gap at the end of every upgradeable contract that is (or may be) inherited:

```solidity
// contracts/GuardedLaunchUpgradable.sol
uint256[48] private __gap; // 50 - limit - governanceRecoveryFund

// contracts/IdleCDOEpochVariant.sol (and Prefunded, IdleCreditVault, ProgrammableBorrower, factory, escrow)
uint256[50] private __gap;
```

Place the gap after all existing variables, and shrink it by one slot per variable added in future upgrades. Additionally run `openzeppelin-upgrades` storage-layout validation (`validateUpgrade`/`upgrades-core`) in CI so a layout shift is caught before `upgradeTo` is executed on mainnet proxies.

### Proof of Concept
A Foundry fork PoC demonstrating the corruption:

```solidity
// Deploy V1: IdleCDOEpochVariantPrefunded behind TransparentUpgradeableProxy via factory.
// Record slot of `token` (in IdleCDOStorage) e.g. via vm.load / token().

// V2: GuardedLaunchUpgradableV2 adds `uint256 public newGuardVar;`
// Recompile with V2 in the inheritance chain, deploy implementation V2.

// proxyAdmin.upgrade(proxy, implV2)
// assert: IdleCDOEpochVariantPrefunded(proxy).token() != originalToken
// i.e. `token()` now returns the value that was in the adjacent slot
// (`weth`/`latestHarvestBlock`), and `strategy()` returns the old `strategyToken`.
// priceAA() now reads lastStrategyPrice's old slot -> deposits mint tranches
// at a corrupted price, draining NAV on the first depositAA call.
```

The layout shift is deterministic from Solidity linearization: adding one variable to `GuardedLaunchUpgradable` moves `IdleCDOStorage._lastCallerBlock` and all 40+ downstream variables (`token`, `guardian`, `strategy`, `priceAA`, `lastNAVAA`, `unclaimedFees`, `defaulted`-adjacent epoch flags) by exactly one slot, which the recorded manifest layout in `.openzeppelin/optimism.json` confirms by showing `GuardedLaunchUpgradable` slots immediately preceding `IdleCDOStorage` slots with no reserved buffer [6](#0-5) .
