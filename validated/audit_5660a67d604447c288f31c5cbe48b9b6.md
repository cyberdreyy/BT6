### Title
v1 signer accepts a competing tenure-start block that v2 correctly rejects as `DuplicateBlockFound`, because v1's duplicate-in-tenure check only looks at globally-accepted blocks while v2 also looks at locally-accepted (signed) blocks - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` (v1) guards against equivocation by calling `signer_db.get_last_globally_accepted_block(...)`, while `GlobalStateView::validate_tenure_change_payload` (v2) calls `signer_db.get_last_signed_block(...)`, which per its own code comment additionally covers locally-accepted (signed but not yet globally-accepted) blocks. In the window where a signer has locally accepted a block for a tenure but that block has not yet reached the global-accept threshold, a v1 signer will pass this check and continue evaluating a second, competing tenure-change proposal for the same tenure, whereas a v2 signer will correctly reject it with `RejectReason::DuplicateBlockFound`.

### Finding Description
The relevant code: [1](#0-0) [2](#0-1) 

v2's own inline comment makes the semantic gap explicit: *"Only blocks we have signed (locally or globally accepted) count here: a block we have merely pre-committed to carries no signature from us, so it is safe to accept a competing tenure-start block in its place if it failed to reach consensus."* This means `get_last_signed_block` (v2) returns a match for any block this signer has already put a signature on — `LocallyAccepted` or `GloballyAccepted` — while `get_last_globally_accepted_block` (v1) only returns a match once the block has actually reached the global-accept threshold recorded in `signer_db`.

Consequently, for the identical `BlockInfo`/tenure fixture where a block is `LocallyAccepted`-but-not-yet-`GloballyAccepted`:
- A **v1** signer's `validate_tenure_change_payload` finds `last_in_current_tenure == None` (not yet globally accepted) and does **not** short-circuit with `RejectReason::DuplicateBlockFound`; it falls through to `Ok(())` if the remaining checks in `check_proposal` also pass, meaning the v1 signer can go on to **sign a second, competing tenure-start block for a tenure it already signed a block in**.
- A **v2** signer's `validate_tenure_change_payload` finds `last_in_current_tenure == Some(locally_accepted_block)` and correctly returns `Err(RejectReason::DuplicateBlockFound)`.

This is a genuine divergence in the `check_proposal` accept/reject verdict for the identical `BlockProposal` and identical underlying `signerdb` tip state, keyed purely on which chainstate module (`v1` vs `v2`) is active for a given signer — i.e., on `active_signer_protocol_version`. Note: the specific reject-reason pairing named in the question (`SortitionViewMismatch` vs `InvalidParentBlock`) does not correspond to this code path — that outer mismatch check in v1 (`RejectReason::SortitionViewMismatch`, v1.rs line 273) fires only when the proposal's consensus hash matches neither the current nor last sortition, and v2 has no directly analogous branch using the same error. The actual, verifiable divergence is the one documented above, manifesting as `DuplicateBlockFound` in v2 vs. no rejection in v1 for the same duplicate-in-tenure condition.

### Impact Explanation
This breaks the signer's equivocation guard: an honest signer running v1 chainstate logic can be induced to place its signature on two different, competing blocks for the same tenure when one of them has only been locally accepted and not yet globally accepted. Because signature accumulation for `BlockResponse`s is keyed by `signer_signature_hash`, a v1 signer's signature on the second/competing block contributes real weight toward finalizing a conflicting block that a properly-updated (v2) signer in the exact same reward cycle correctly refuses — this is the "signer signing a conflicting block (chain safety)" Critical category, since it can help accumulate partial signatures toward a fork.

### Likelihood Explanation
Preconditions: a mixed-cycle rollout where some signers still run v1 chainstate logic (`SortitionsView`) while others run v2 (`GlobalStateView`); a tenure where the v1 signer has already `LocallyAccepted` a block but it has not yet crossed the global-accept threshold recorded in `signer_db`. The attacker needs only their own miner slot (to produce a tenure-change block commit/proposal building a competing tenure-start block for the same tenure) plus the ability to gossip the `BlockProposal` to signers — both within the stated unprivileged-attacker capability. This is repeatable in any tenure where the timing window (locally-accepted-but-not-yet-globally-accepted) exists, which is a normal, frequently-occurring transient state during block signing, not a rare edge case.

### Recommendation
Make the duplicate-in-tenure check in `SortitionsView::validate_tenure_change_payload` (v1) use the same broader semantics as v2's `get_last_signed_block` (i.e., also treat locally-accepted/signed-but-not-yet-globally-accepted blocks as a match), or otherwise ensure both code paths query an identical, version-independent notion of "has this signer already signed a block in this tenure" before allowing a competing tenure-start proposal. Since v1 is present only to support the mixed-version rollout window, backport the v2 semantics into `v1.rs`'s duplicate check.
