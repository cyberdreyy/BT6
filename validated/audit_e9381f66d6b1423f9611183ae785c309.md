### Title
Off-by-one rounding in `GlobalStateEvaluator::reached_agreement` lets the signer-side global state machine (current miner / burn view / protocol version / tx-replay-set) "reach consensus" below the true 70% supermajority - ([File: libsigner/src/v0/signer_state.rs])

### Summary
`GlobalStateEvaluator::reached_agreement` computes the 70% supermajority bar with truncating (floor) integer division, while the node/chainstate side that actually enforces the "70% of signer weight" rule (`NakamotoBlockHeader::compute_voting_weight_threshold`) uses ceiling division. This mirrors the M-2 analog exactly: a threshold that must be rounded up (to require *at least* 70%) is instead rounded down, so a lower amount of weight than the intended 70% can satisfy the check whenever `total_weight * 7` is not a multiple of 10.

### Finding Description
`reached_agreement` is defined as: [1](#0-0) 

`u64::from(vote_weight) >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10` truncates towards zero, i.e. it computes `floor(total_weight * 7 / 10)` as the bar. Contrast this with the chainstate-side threshold used to actually validate a Nakamoto block's aggregated signature weight: [2](#0-1) 

`compute_voting_weight_threshold` explicitly adds a `ceil` term so the true required weight is `ceil(total_weight * 7 / 10)`. The signer-side pre-commit and post-vote tallying paths (`handle_block_pre_commit`, `store_and_process_block_rejection`) correctly reuse this ceiling-based `compute_voting_weight_threshold`: [3](#0-2) [4](#0-3) 

However, `GlobalStateEvaluator::reached_agreement` is used exclusively (not the ceiling helper) to decide the **global signer state machine's** consensus view: the active signer protocol version, the agreed burn-block view, the agreed `current_miner`, and the agreed transaction-replay set: [5](#0-4) [6](#0-5) 

Whenever `total_weight` is such that `total_weight * 7 % 10 != 0` (i.e. most values of `total_weight`), the floor bar is exactly one weight unit lower than the true ceiling-based 70% bar. This is a systemic off-by-one, not something requiring a majority of malicious signers to trigger: it happens automatically any time honest signer weight distribution crosses the floor value but not the ceiling value, because the code computes the wrong (lower) bar.

The regression tests added in `libsigner/src/tests/signer_state.rs` document and pin exactly this floor-vs-ceiling behavior (`>=` 70% floor, not ceiling), confirming this is the actual implemented (and now locked-in) behavior rather than a hypothetical: [7](#0-6) 

### Impact Explanation
The `SignerStateMachine` produced by `determine_global_state()` (built on `reached_agreement`) determines, among other things, the agreed `current_miner` and the agreed `tx_replay_set`/burn view that other signer logic (chainstate v1/v2 proposal checks, miner-timeout/capitulation logic) treats as ground truth for whether a miner/tenure is legitimate. Because the "consensus" bar is silently lower than the genuine 70% supermajority, it is possible for a "current miner" or replay-set/burn-view state to be adopted with less than the true 70% of signer weight behind it. This weakens the guarantee that miner/tenure legitimacy and transaction-replay decisions require a genuine supermajority, which can let a signer act on (and ultimately sign on top of) a state that a strict 70% count would not have supported — an aggregated-weight vs. verified-threshold equality break of exactly the kind called out in scope (aggregated-weight vs verified-accepts).

Unlike the actual block-signature verification path in `stackslib`, which correctly rounds up and thus cannot be fooled this way, the signer-side global-state consensus mechanism is inconsistent with it, creating a genuine two-tier standard: the node requires ceil(70%) to accept a block's signatures, but the signer network can converge on a "global state" (miner/replay-set/burn view) with only floor(70%). This does not require a malicious majority to trigger — it is a plain arithmetic bug that fires under normal weight distributions.

### Likelihood Explanation
This is not a probabilistic/attacker-triggered edge case; it is a deterministic function of `total_weight` (the sum of all registered signer weights for the reward cycle). Any reward-cycle weight total where `total_weight * 7` is not divisible by 10 (the overwhelming majority of possible weight totals) reduces the true 70% bar by one unit, so the bug is live in essentially every reward cycle, without requiring any adversarial signer collusion or a supermajority of malicious participants — it is purely a rounding-direction defect analogous to the reported oracle tick-rounding issue.

### Recommendation
Change `reached_agreement` to use ceiling division consistent with `NakamotoBlockHeader::compute_voting_weight_threshold`, e.g. compute `threshold = (total_weight * NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD).div_ceil(10)` and compare `vote_weight >= threshold`, so the signer-side global consensus bar matches the node's enforced 70% supermajority bar exactly (round up, never down), eliminating the asymmetry between the two components that are meant to represent the same "70% of signer weight" invariant.

### Proof of Concept
Using `total_weight = 13` (a value not evenly divisible when multiplied by 7 and divided by 10):
- True 70% (ceiling, matching `compute_voting_weight_threshold`): `ceil(13*7/10) = ceil(9.1) = 10`.
- `reached_agreement`'s floor computation: `floor(13*7/10) = floor(9.1) = 9`.

With `vote_weight = 9`, `reached_agreement(9)` returns `true` (9 >= 9), declaring "agreement" reached on a `current_miner`/burn-view/replay-set/protocol-version state with only 9/13 ≈ 69.2% of signer weight — below the intended 70% supermajority — while the analogous chainstate-side `compute_voting_weight_threshold(13)` would correctly require 10/13 (≈76.9%) before accepting equivalent weight as sufficient for a block signature. This divergence is fully reproducible deterministically from any `evaluator_with_total_weight(13)` and `evaluator.reached_agreement(9)` call as shown in the existing test harness pattern at `libsigner/src/tests/signer_state.rs:723-729`.

        protocol_versions.sort_by_key(|(version, _)| *version);
        let mut total_weight_support: u32 = 0;
        for (version, weight_support) in protocol_versions.into_iter().rev() {
            total_weight_support += weight_support;
            if self.reached_agreement(total_weight_support) {
                return Some(version);
            }
        }
        None
    }

    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

#[test]
/// Locks the joint behavior of `reached_agreement` and `reached_disagreement`
/// at a single `total_weight`:
///   - agreement: `>=` 70% (inclusive)
///   - disagreement: `>` 30% (strict)
///   - three regions: [0, 30%] neither, (30%, 70%) disagreement only,
///     [70%, total] both
///
/// Walking 0, 30%, 30%+1, 70%-1, 70% catches a flipped inequality on either
/// side and any drift between the two threshold constants. Also pins the
/// "agreement implies disagreement" relation, which holds as long as the
/// agreement threshold sits above the disagreement one.
fn thresholds_partition_weight_space() {
    let evaluator = evaluator_with_total_weight(1_000_000_000);

    // 0%: neither.
    assert!(!evaluator.reached_agreement(0));
    assert!(!evaluator.reached_disagreement(0));

    // Exactly 30%: strict `>`, so not yet disagreement.
    assert!(!evaluator.reached_agreement(300_000_000));
    assert!(!evaluator.reached_disagreement(300_000_000));

    // One unit past 30%: gap region, disagreement only.
    assert!(!evaluator.reached_agreement(300_000_001));
    assert!(evaluator.reached_disagreement(300_000_001));

    // One unit below 70%: still in the gap.
    assert!(!evaluator.reached_agreement(699_999_999));
    assert!(evaluator.reached_disagreement(699_999_999));

    // Exactly 70%: agreement (`>=`), and disagreement still holds since 70% > 30%.
    assert!(evaluator.reached_agreement(700_000_000));
    assert!(evaluator.reached_disagreement(700_000_000));
}
