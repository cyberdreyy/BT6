### Title
Claimed instant-withdraw receipts are never removed from `instantWithdrawClaimsByEpoch`, so a same-epoch default finalization reuses already-paid claims and permanently dilutes `defaultRecoveryPrice` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
A use-after-free analog: `claimInstantWithdrawRequest` pays a user and zeroes the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` or the epoch-level counter `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults in that same epoch while other instant receipts remain unfunded, `finalizeDefaultRecovery` counts the already-claimed ("freed") receipts again via `defaultPendingClaimBasis`, inflating the total recovery basis and lowering `defaultRecoveryPrice` for every legitimate claimant. The corresponding share of `defaultRecoveryReserve` is stranded forever.

### Finding Description
`requestInstantWithdraw` records three pieces of per-epoch state: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` [1](#0-0) .

When the CDO funds and the user claims an instant withdrawal, `claimInstantWithdrawRequest` only zeroes `instantWithdrawsRequests[_user]` and burns the receipt — the per-epoch entries remain populated [2](#0-1) . The only place these per-epoch entries are cleared is `_claimDefaultedInstantWithdrawRequest`, which runs exclusively on the defaulted-claim path [3](#0-2) .

`defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0` [4](#0-3) . `pendingInstantWithdraws` is decremented in `collectInstantWithdrawFunds` when funds are collected [5](#0-4) , not when the user claims — so an epoch can legitimately contain (a) instant receipts already collected and claimed at par, and (b) instant receipts still pending, when default finalization runs.

In `finalizeDefaultRecovery`, `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` where `totalBasis` includes the stale ghost basis [6](#0-5) . The already-paid user's claim in `_claimDefaultedInstantWithdrawRequest` reverts on `instantWithdrawsRequests[_user] -= claimBasis` (underflow, since the aggregate is already 0), so there is no direct double-payout — but the inflated `totalBasis` is already baked into `defaultRecoveryPrice`, and the excess reserve proportional to the ghost claims can never be distributed.

### Impact Explanation
Every defaulted-epoch receipt holder (pending withdraw receipts via `_claimDefaultedWithdrawRequest`, post-default receipts, and unfunded instant receipts) receives `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` — a strictly lower payout than entitled. The recovery reserve fraction corresponding to already-claimed instant receipts (`claimedInstant * recoveryPrice / RECOVERY_FULL`) is permanently locked in the strategy: no function can release it, and `defaultRecoveryReserve` accounting treats it as earmarked. This is permanent freezing of recovery funds plus systematic underpayment of defaulted claimants, scaling linearly with the amount of same-epoch instant claims processed before finalization.

### Likelihood Explanation
Requires a specific but reachable sequence: (1) epoch running with instant withdrawals enabled; (2) at least one instant-withdraw request funded via `collectInstantWithdrawFunds` and claimed; (3) at least one instant-withdraw request still pending (`pendingInstantWithdraws != 0`); (4) borrower default and `finalizeDefaultRecovery` executed before `epochNumber` increments. All steps use only unprivileged roles (any lender can request/claim instant withdrawals; default and finalization are honest manager/keeper flows). No privileged misbehavior, timing manipulation, or external oracle dependency is needed — only a partial-funding state at default time, which is exactly the scenario the `pendingInstantWithdraws` machinery was built to handle.

### Recommendation
In `claimInstantWithdrawRequest` (or in the CDO's instant-claim path), clear the per-epoch records alongside the aggregate: set `instantWithdrawsRequestsByEpoch[_user][epochNumber] = 0` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount, mirroring what `_claimDefaultedInstantWithdrawRequest` does. Alternatively, make `defaultPendingClaimBasis` derive the instant basis from unfunded claims only, so already-paid receipts cannot re-enter the recovery denominator.

### Proof of Concept
```solidity
// Foundry fork PoC — contracts/strategies/idle/IdleCreditVault.sol
// Setup: epoch running, instant withdrawals enabled (delay elapsed).

// 1. Attacker (any lender) requests instant withdraw of X.
vm.prank(address(cdoEpoch));
strategy.requestInstantWithdraw(X, attacker);

// 2. Honest user requests instant withdraw of Y (unfunded remainder).
vm.prank(address(cdoEpoch));
strategy.requestInstantWithdraw(Y, victim);

// 3. CDO funds only X (partial funding is the normal instant path).
vm.prank(address(cdoEpoch));
strategy.collectInstantWithdrawFunds(X);       // pendingInstantWithdraws = Y

// 4. Attacker claims X at par. Per-epoch records are NOT cleared.
vm.prank(address(cdoEpoch));
strategy.claimInstantWithdrawRequest(attacker);
// BUG: instantWithdrawsRequestsByEpoch[attacker][epoch] == X still
//      instantWithdrawClaimsByEpoch[epoch] == X + Y still

// 5. Borrower defaults in the same epoch; CDO finalizes recovery with R.
vm.prank(address(cdoEpoch));
strategy.finalizeDefaultRecovery(R, recoverySource);

// 6. defaultPendingClaimBasis() = pendingWithdraws + (X + Y) instead of Y.
uint256 price = strategy.defaultRecoveryPrice();
// price == R * RECOVERY_FULL / (activeBasis + pendingWithdraws + X + Y)
// instead of R * RECOVERY_FULL / (activeBasis + pendingWithdraws + Y)

// 7. Victim's defaulted instant claim is diluted:
//    victimPayout = Y * price / RECOVERY_FULL  <  Y * fairPrice / RECOVERY_FULL
// 8. Stranded reserve ~= X * price / RECOVERY_FULL can never be claimed:
//    _claimDefaultedInstantWithdrawRequest(attacker) reverts on underflow
//    of instantWithdrawsRequests[attacker] -= X (already zero).
```

Uncertainty note: I did not fully trace the CDO-side call ordering in `IdleCDOEpochVariant` (e.g., whether `claimInstantWithdrawRequest` and `finalizeDefaultRecovery` can both occur within the same `epochNumber` in every mode), but the strategy-side state evidence — per-epoch records never cleared on the normal claim path while `defaultPendingClaimBasis` reads them — is direct and sufficient to establish the stale-record (use-after-free) reuse.
