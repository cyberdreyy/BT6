### Title
Stale rejection weight is never cleared when a signer later accepts the same block, causing a miscounted rejection quorum on the miner node - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side vote tally in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` tracks `total_weight_approved` via the `gathered_signatures` map and `total_weight_rejected` via the `responded_signers` set. These are two independent data structures, so a signer that first rejects and later accepts the same block has its weight added to `total_weight_rejected` **and then also** added to `total_weight_approved`, with no code path that removes the earlier rejection weight. The rejection tally is therefore stale but permanently counted, unlike the equivalent case already fixed at the signer-side DB layer (`stacks-signer/src/signerdb.rs`, `add_block_signature` clears prior rejection rows, confirmed by the `reject_then_accept` test and the CHANGELOG entry "Do not count both a block acceptance and a block rejection for the same signer/block").

### Finding Description
In `handle_event` on `stackerdb_listener.rs`:

- `BlockResponse::Accepted` branch: weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`: [1](#0-0) 

- `BlockResponse::Rejected` branch: weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot answers at all): [2](#0-1) 

Sequence: signer S first sends `Rejected` → `responded_signers.insert(slot_id)` is `true` → `total_weight_rejected += weight(S)`. S then reconsiders (a supported, tested behavior — `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs` explicitly allows re-evaluating and accepting a previously rejected block, e.g. `RejectReason::NotFoundError`, `NoSortitionView`, `ConnectivityIssues`) and sends `Accepted` for the same block. In the `Accepted` branch, the check is against `gathered_signatures`, a *different* map that was never touched by the Rejected branch, so `!gathered_signatures.contains_key(&slot_id)` is still `true` → `total_weight_approved += weight(S)` as well.

At no point is S's earlier contribution to `total_weight_rejected` removed. The consumer of these two counters, `signer_coordinator.rs`, treats them as if they partition the signer set: [3](#0-2) 

so `total_weight_rejected` no longer reflects the signer set's live view; it contains phantom weight from signers who have since moved to acceptance.

### Impact Explanation
This breaks the aggregated-weight-vs-verified-current-votes equality: `total_weight_rejected` can retain weight from a signer who no longer opposes the block. If other signers independently reject the same block (e.g. a slow/flaky signer, or one temporarily missing the burn view, as covered by the very same reconsider path), the stale rejection weight from S combines with their live rejections to cross the `total_weight_rejected.saturating_add(weight_threshold) > total_weight` (>30% blocking-minority) condition, causing the miner to declare the block `SignersRejected` and abandon it — even though S itself has already switched to accepting and the block may in fact be on track to reach the 70% acceptance threshold. This is a liveness wedge on a specific, correctly-signed/accepted block: a valid block can be discarded based on a rejection count that is stale/miscounted, matching the report's "aggregated weight vs verified accepts" class of bug.

### Likelihood Explanation
The reject → reconsider → accept path is not a hypothetical edge case; it is an explicitly supported and tested signer behavior (`should_reevaluate_reject_reason`, and node test scenarios like `signer_can_accept_rejected_block`, `signers_reprocess_bitcoin_block_not_found_proposals`, `signers_respond_to_unprocessed_globally_rejected_block_proposals`). Any single signer that legitimately rejects once (e.g. due to a transient `NotFoundError`/`NoSortitionView`/connectivity issue) and later accepts triggers the double-counted, unreconciled state on the miner's `StackerDBListener`. No majority collusion, key access, or malicious behavior is required — a single honest signer's normal retry flow is sufficient.

### Recommendation
When processing a `BlockResponse::Accepted` for a `slot_id` that is already present in `responded_signers` as a rejection, subtract that signer's weight from `total_weight_rejected` (and vice versa for a late rejection following a prior acceptance), mirroring the reconciliation already performed in `stacks-signer/src/signerdb.rs::add_block_signature`. Alternatively, unify tracking into a single per-slot "current vote" map from which both `total_weight_approved` and `total_weight_rejected` are recomputed, so a signer's weight can never be counted toward both totals at once.

### Proof of Concept
1. Node configured with signer S having weight `w`; total weight `T`; `weight_threshold` = 70% of `T`.
2. S sends `BlockResponse::Rejected` for block `B` (e.g. `RejectCode::ValidationFailed(NotFoundError)`). `stackerdb_listener.rs` line 515-518 runs: `responded_signers.insert(slot_id)` → true, `total_weight_rejected += w`.
3. S's local chainstate condition clears (matches `should_reevaluate_reject_reason` true-cases in `stacks-signer/src/v0/signer.rs` lines 2705-2739); S re-evaluates the same proposal and now sends `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. `stackerdb_listener.rs` lines 443-465 run: `gathered_signatures.contains_key(&slot_id)` is `false` (this map was never touched for S) → `total_weight_approved += w` as well. `total_weight_rejected` still includes `w` from step 2, unreduced.
5. If other signers accumulate additional rejections whose weight, together with S's stale `w`, exceeds `T - weight_threshold`, `signer_coordinator.rs` (lines 509-519) declares `SignersRejected` and the miner abandons block `B`, even though S currently accepts it and the true live rejection weight (excluding S) may be below the blocking-minority threshold.
