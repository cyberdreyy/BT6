## Title
Builder-withdrawal amount desynchronization creates Gwei — `apply_withdrawals` deducts a capped amount while the committed `Withdrawal.amount` (paid out on the EL) is the uncapped requested amount - (File: `specs/gloas/beacon-chain.md`)

## Summary
`get_builder_withdrawals` builds `Withdrawal` records for a builder using the *requested* amount stored in `state.builder_pending_withdrawals[i].amount`, with no capping to the builder's current balance. That same, uncapped amount is placed into `state.payload_expected_withdrawals`, which is the value the execution layer is required to credit to `fee_recipient`. However, `apply_withdrawals` only deducts `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance`. If a builder's balance is lower than the sum of amount(s) committed to be withdrawn, the execution layer pays out the full requested amount while the consensus layer only debits the smaller, balance-capped amount — creating Gwei that is not backed by any decrease elsewhere in the system.

## Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md, "New `get_builder_withdrawals`") emits, for every entry in `state.builder_pending_withdrawals`: [1](#0-0) 
i.e. `amount=withdrawal.amount` — the raw, previously-queued request amount, never re-checked or capped against `state.builders[builder_index].balance` at the time the withdrawal is finally emitted.

That withdrawal is placed into `state.payload_expected_withdrawals`, the field the execution layer must honor (crediting `fee_recipient` with the specified `amount`), per the design note in `process_withdrawals`: [2](#0-1) 

Meanwhile, `apply_withdrawals` deducts only the balance-capped amount from the builder's CL-side balance: [3](#0-2) 

The test suite explicitly documents and accepts this asymmetry as expected behavior for insufficient-balance builder withdrawals: [4](#0-3) 
— note the comment: `withdrawal.amount: 5 ETH (requested amount)` while `builders[0].balance: 0 (deduction capped to available balance)`. The `Withdrawal` object that reaches the execution layer still carries the full 5 ETH figure, even though the builder's consensus-layer collateral only covered 1 ETH.

This breaks the equality that every Gwei paid out on the execution layer must correspond to an equal decrease somewhere in consensus-layer state. Here, `EL credit (5 ETH) != CL debit (1 ETH)`, i.e. 4 ETH of value is minted with no offsetting decrease — a pure Gwei-creation bug, not an attacker's own stake being lost.

The root cause is that `can_builder_cover_bid`, which is meant to prevent this, is only checked at bid-acceptance time (`process_execution_payload_bid`): [5](#0-4) 
There is no re-verification at settlement/withdrawal time (`settle_builder_payment`, `process_builder_pending_payments`, `get_builder_withdrawals`) that the builder's balance is still sufficient to cover everything now queued in `builder_pending_withdrawals`. Between bid acceptance and eventual withdrawal processing, several independently-valid, unprivileged builder actions can each pass their own `can_builder_cover_bid` check (which only accounts for *currently pending* commitments at the moment of the check) yet, once queued together and drained by `get_builder_withdrawals`/`get_builders_sweep_withdrawals` (full-balance sweep withdrawal on top of pending payment withdrawals), can end up exceeding the actual balance by the time `apply_withdrawals` executes. The cap-at-settlement design silently absorbs the shortfall on the CL side while the EL-facing `Withdrawal.amount` remains uncapped, so the discrepancy is paid out anyway.

## Impact Explanation
This is Critical severity under the stated rules: it is a case of "Gwei created ... paid to a non-owner" — the execution layer will credit `fee_recipient` more ETH than the builder actually has backing for, effectively minting ETH with no consensus-layer collateral removed to match it. All that's needed is an unprivileged builder queuing withdrawal/payment commitments whose amounts, once settled together, exceed available balance — no malicious peer, coalition, or client bug required, only ordinary (even honest) builder participation combined with the sweep/settlement timing already built into the spec.

## Likelihood Explanation
Likelihood is non-trivial but requires a specific balance/ordering condition: multiple pending payments/withdrawals for the same builder (from bid settlement, quorum-based payment settlement, and/or the withdrawable-epoch full-balance sweep) accumulating to more than the builder's current balance by the time `get_builder_withdrawals`/`apply_withdrawals` runs. Because `can_builder_cover_bid` is re-derived from `get_pending_balance_to_withdraw_for_builder` independently at each bid, and the full sweep withdrawal (`get_builders_sweep_withdrawals`, which withdraws the *entire* current balance) can be queued/settled concurrently with pending-payment withdrawals still in the queue, the two withdrawal paths are not mutually exclusive against a single balance, making an accidental (or intentionally engineered by the builder itself, at no loss to anyone but the protocol) overdraft plausible.

## Recommendation
At the point `get_builder_withdrawals` (and `get_builders_sweep_withdrawals`) constructs each `Withdrawal`, cap `amount` to the builder's *currently remaining* balance after accounting for all prior withdrawals already queued in the same call (mirroring how validator partial withdrawals are capped via `min(balance - MIN_ACTIVATION_BALANCE, amount)` in `get_pending_partial_withdrawals`). The `Withdrawal.amount` value handed to the execution layer must always be provably ≤ the amount actually deducted in `apply_withdrawals`; the two must never diverge.

## Proof of Concept
1. Builder `B` has balance `X`.
2. `B` submits Bid 1 with value `V1` such that `can_builder_cover_bid` passes (`X - (MIN_DEPOSIT_AMOUNT + existing pending) >= V1`); this queues a `BuilderPendingPayment`.
3. Before Bid 1 settles, `B`'s `withdrawable_epoch` is reached (or another payment queues), triggering `get_builders_sweep_withdrawals` which schedules a withdrawal of `B`'s *entire remaining balance* `X` (per `specs/gloas/beacon-chain.md:1858-1867`).
4. Both the pending-payment withdrawal (amount `V1`, from `builder_pending_withdrawals`) and the sweep withdrawal (amount `X`) are drained in the same or nearby `process_withdrawals` call via `get_builder_withdrawals` + `get_builders_sweep_withdrawals`, producing committed `Withdrawal` entries totalling `V1 + X > X`.
5. `apply_withdrawals` processes them in order: the first withdrawal decreases `state.builders[B].balance` by `min(V1, X)`; the second decreases it by `min(X, remaining)`, capping total real deduction at `X`. But `state.payload_expected_withdrawals` (and thus what the execution layer pays out) still totals `V1 + X`.
6. The execution layer credits `fee_recipient`s a combined `V1 + X`, while the builder's consensus-layer collateral only ever held `X` — `V1` in Gwei has been created out of nothing and paid to the fee recipient(s), with no corresponding stake ever removed from anyone.

(Note: the exact scheduling interplay between `process_builder_pending_payments`, `settle_builder_payment`, and `get_builders_sweep_withdrawals` across epoch boundaries needs live-spec simulation to confirm concretely with the current queue-slicing/withdrawal-limit logic; I could not run the pyspec test harness in this environment to execute this scenario end-to-end, so this should be validated by a background Devin session with test-execution capability before filing formally.)

##### Modified `process_withdrawals`

*Note*: This is modified to only take the `state` as parameter. Withdrawals are
deterministic given the beacon state, any execution payload that has the
corresponding block as parent beacon block is required to honor these
withdrawals in the execution layer. `process_withdrawals` must be called after
`process_parent_execution_payload` (which updates `state.latest_block_hash`) and
before `process_execution_payload_bid` as the latter function affects validator
balances.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
