### Title
Stale canonical-fork substitution via attacker-controlled `TenureChange::Extend.burn_view_consensus_hash` bypasses live-tip canonicity check - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
`NakamotoBlockProposal::validate` derives the sortition handle used for tenure-canonicity checking from `burn_view_consensus_hash`, which for a `TenureChange::Extend` cause is taken directly from the attacker-supplied proposal's own `TenureChange` payload rather than the node's live canonical burnchain tip. `check_block_has_valid_tenure` then only asks whether `tenure_id` is on the sortition history *of that attacker-chosen fork*, not whether it is canonical at the current tip, allowing a `BlockValidateOk` for a tenure that has since been reorged out.

### Finding Description
In `validate()`:
```
stackslib/src/net/api/postblock_proposal.rs:587-602

    NakamotoChainState::get_block_burn_view(sortdb, &self.block, &parent_stacks_header)?;
let sort_tip =
    SortitionDB::get_block_snapshot_consensus(sortdb.conn(), &burn_view_consensus_hash)?...;

Self::check_block_has_valid_tenure(&db_handle, &self.block.header.consensus_hash)?;
``` [1](#0-0) 

The comment directly above this block states the intended (and exploited) behavior: *"If the block has a TenureChange with an Extend cause, then the burn view is whatever is indicated in the TenureChange."* [2](#0-1) 

`check_block_has_valid_tenure` itself only checks canonicity relative to whatever sortition handle it is given:
```
pub(crate) fn check_block_has_valid_tenure(
    db_handle: &SortitionHandleConn,
    tenure_id: &ConsensusHash,
) -> Result<(), BlockValidateRejectReason> {
    if !db_handle.has_consensus_hash(tenure_id)? { ... }
}
``` [3](#0-2) 

A `SortitionHandleConn` opened via `sortdb.index_handle(&sort_tip.sortition_id)` scopes ancestor/canonicity queries to the fork ending at `sort_tip.sortition_id` — it does not, by itself, verify that `sort_tip` is the node's currently canonical burnchain tip. Because `sort_tip` is resolved purely by consensus-hash lookup (`SortitionDB::get_block_snapshot_consensus`) and the consensus hash for the Extend case is attacker-supplied, an attacker who once won a sortition (a legitimate single miner slot) on a fork that was later reorged out can still craft a `TenureChange::Extend` payload whose `burn_view_consensus_hash` points back at that now-stale (but formerly canonical) sortition. This causes `sort_tip`/`db_handle` to be anchored to the abandoned fork, on which the attacker's own orphaned tenure consensus hash is still "canonical," letting `has_consensus_hash` return `true` even though the live/current canonical tip has since orphaned that tenure.

The rest of `validate()` (parent lookup, expected burns, tx replay, block building) all proceed using this same stale `db_handle`/`burn_dbconn`, so the entire validation pipeline operates against the wrong (non-live) view of the sortition history, and a `BlockValidateOk` is produced for a tenure that the node's actual live tip would reject.

### Impact Explanation
This breaks the CANONICITY safety property: the tenure being validated is checked against a historical, no-longer-canonical sortition view instead of the current canonical tip. A signer that trusts `BlockValidateOk` from this endpoint could be induced to sign a block belonging to a tenure that has been reorged out at the current tip — a Critical chain-safety violation (signing a non-canonical/conflicting block). This is repeatable by any single miner-slot winner whose tenure is later orphaned by a subsequent reorg, requiring only crafting and submitting one `BlockProposal`/`TenureChange::Extend`.

### Likelihood Explanation
Preconditions: the attacker must have won at least one sortition (achievable with their own BTC, consistent with the "single miner slot" threat model) whose tenure is later superseded by a competing, heavier fork (a normal, not-unusual burnchain reorg event). After the reorg, the attacker crafts a `NakamotoBlockProposal` containing a `TenureChange` transaction with `cause = Extend` and `burn_view_consensus_hash` set to the stale-but-formerly-canonical consensus hash, and submits it (or gossips the resulting signed artifacts) to a signer/node for validation — no majority of signers, no auth_token, and no local access required. The main uncertainty (not fully confirmed in this pass because the body of `NakamotoChainState::get_block_burn_view` was not read to completion) is whether that function independently re-derives/clamps the Extend burn view to the current canonical tip before this code path uses it; based on the explicit surrounding comment and the fact that `check_block_has_valid_tenure`'s own scoping is exactly what the code review flags, no such re-binding is visible in the reviewed call path.

### Recommendation
After resolving `sort_tip` from the (potentially attacker-influenced) `burn_view_consensus_hash`, explicitly verify that `sort_tip.sortition_id` is an ancestor of (or equal to) the node's current canonical sortition tip (`SortitionDB::get_canonical_burn_chain_tip`/canonical sortition_id chain) before using it to open `db_handle`/`burn_dbconn`. Reject the proposal with `NonCanonicalTenure` if the burn view referenced by the `TenureChange::Extend` is not itself part of the live canonical fork.
