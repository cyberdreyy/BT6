### Title
Instant-withdraw receipts can be claimed at par before their epoch's funds are collected, draining reserves funded for earlier claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The netfs bug skipped the flush-and-wait on a partially-written region at EOF, letting a second writer consume writeback state still owned by an in-flight operation. The analog in `IdleCreditVault` is the instant-withdraw path: `requestInstantWithdraw` mints a receipt and increments `instantWithdrawsRequests`/`pendingInstantWithdraws`, while `claimInstantWithdrawRequest` pays the full aggregate receipt balance at par with no check that the funds for that receipt's epoch were actually collected via `collectInstantWithdrawFunds`. A receipt created after the manager already funded the pending bucket is "written" over a region whose settlement was already consumed — the equivalent of the skipped wait — and is paid out of reserves that belong to earlier claimants.

### Finding Description
In `requestInstantWithdraw` the strategy burns CDO strategy tokens, mints a user receipt, and increases `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and the global `pendingInstantWithdraws` — but pulls no underlying. Funding happens separately through `getInstantWithdrawFunds` → `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and transfers exactly `_pendingInstant()` at that moment [1](#0-0) [2](#0-1) .

`claimInstantWithdrawRequest` then burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)` for the entire aggregate, unconditionally, as long as `defaultRecoveryFinalized`/`defaultInstantWithdrawsFinalized` is not set [3](#0-2) . There is no per-epoch or per-receipt funding check in the non-default path — the code assumes every outstanding receipt was included in the last `collectInstantWithdrawFunds` call, the same broken assumption as the skipped flush.

Attack sequence (running epoch, non-programmable borrower, `allowInstantWithdraw` enabled):
1. Victims request instant withdraws; `pendingInstantWithdraws = X`.
2. Honest manager calls `getInstantWithdrawFunds`, which pulls `X` from the borrower and calls `collectInstantWithdrawFunds(X)`, leaving `pendingInstantWithdraws = 0` and `X` underlying sitting in the strategy reserved for the victims [4](#0-3) .
3. While the epoch is still running and instant requests remain routable, the attacker calls `requestWithdraw` on the CDO, which routes to `requestInstantWithdraw`; `instantWithdrawsRequests[attacker] += amount`, `pendingInstantWithdraws += amount`, but no new underlying is pulled.
4. `allowInstantWithdraw` is already `true`, so the attacker immediately calls `claimInstantWithdrawRequest` and is paid `amount` at par from the strategy's underlying balance — i.e., from the `X` funded for victims [5](#0-4) .
5. The attacker's receipt is settled without ever being funded, and the leftover `pendingInstantWithdraws != 0` either blocks the next `stopEpoch` (`_pendingInstant() != 0` check) or forces the borrower to fund the same liability a second time [6](#0-5) .

The broken invariant is one-receipt-one-funded-payout: a receipt minted after the funding snapshot is indistinguishable from funded receipts. No existing guard stops it — `_onlyIdleCDO` only authenticates the caller, `defaultRecoveryFinalized` is false pre-default, and `allowInstantWithdraw` is already true by design after funding.

### Impact Explanation
Direct theft: the attacker redeems underlying at par without their request ever being funded, up to the full instant-withdraw reserve `X` held in the strategy. Loss equals `min(attackAmount, strategy underlying balance)` and is born by earlier instant-withdraw claimants whose funded claims are drained, and/or by LPs if the borrower is forced to re-fund. A secondary effect is temporary freezing of epoch settlement, since `pendingInstantWithdraws` must return to zero before `stopEpoch` can run.

### Likelihood Explanation
Requires a non-programmable-borrower pool with instant withdrawals enabled and a running epoch in the window between `getInstantWithdrawFunds` and `stopEpoch`. The attacker only needs to be a KYC-passing tranche holder able to route a withdraw request into the instant bucket during that window — no privileged role. The caveat is that exploitability depends on the CDO still accepting instant-routed requests after the funding call; if `requestWithdraw` hard-blocks instant routing after `instantWithdrawDeadline`/funding, the window closes and the finding degrades to a defense-in-depth gap. The strategy code itself performs no funding check, so the invariant rests entirely on that external ordering assumption — precisely the class of the kernel bug.

### Recommendation
Track funded vs. unfunded instant receipts. Either (a) in `claimInstantWithdrawRequest`, only pay `instantWithdrawsRequests[_user]` amounts whose request epoch was already collected — e.g., snapshot `pendingInstantWithdraws` growth and gate claims on a per-epoch `instantWithdrawsFundedByEpoch` marker set in `collectInstantWithdrawFunds`; or (b) disallow new `requestInstantWithdraw` once `allowInstantWithdraw` is true / after collection for the current epoch, reverting until the next `startEpoch` resets the bucket.

```solidity
// 1. victim requests instant withdraw -> pendingInstantWithdraws = X
// 2. manager calls getInstantWithdrawFunds() -> strategy holds X, pending = 0, allowInstantWithdraw = true
// 3. attacker (KYC'd tranche holder) requests instant withdraw of amount <= X
//    strategy.requestInstantWithdraw mints receipt, pendingInstantWithdraws = amount, no funds pulled
// 4. attacker calls cdoEpoch.claimInstantWithdrawRequest()
//    -> claimInstantWithdrawRequest burns receipt, _transferFundedClaim pays `amount` at par
// assert attacker underlying gain == amount while pendingInstantWithdraws == amount (unfunded)
// assert victim claims now underpay / stopEpoch reverts on _pendingInstant() != 0
```

Note: I was unable to fully verify the CDO-side gating of `requestInstantWithdraw` relative to `instantWithdrawDeadline` within the available search iterations; the finding assumes (as the strategy's own accounting implies) that instant requests remain accepted while the epoch is running. If that routing is closed after funding, the residual issue is the absence of any on-chain funding check on the claim path.

```text
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```
