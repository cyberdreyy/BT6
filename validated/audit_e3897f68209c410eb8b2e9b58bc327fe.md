### Title
`account_is_implicit` guard omits `NearDeterministic` account IDs, allowing `CreateAccount` to squat/hijack a NEP-616 deterministic-account address - ([File: runtime/runtime/src/actions.rs])

### Summary
`check_account_existence` blocks plain `CreateAccount` only for account IDs classified as implicit by `account_is_implicit`, which tests only `NearImplicitAccount`/`EthImplicitAccount` [1](#0-0) . `NearDeterministic` ("0s" + 40 hex, 42 chars) is a third, distinct account-type class per `get_account_type` [2](#0-1)  that is not covered by this guard, so an ordinary `CreateAccount` action against a syntactically valid deterministic-account ID passes `check_account_existence` and reaches `action_create_account`, which happily creates an empty, attacker-controlled `Account::new(..., AccountContract::None, ...)` there [3](#0-2) .

### Finding Description
`check_account_existence` rejects `Action::CreateAccount` when `account_is_implicit(account_id, ...)` is true, returning `OnlyImplicitAccountCreationAllowed` [4](#0-3) . `account_is_implicit` only classifies `NearImplicitAccount` and (if enabled) `EthImplicitAccount` as implicit [5](#0-4) , while `get_account_type` treats `NearDeterministic` ("0s" + 40 lowercase hex) as a fully separate type, distinct from `NearImplicit`/`EthImplicit`/`Named` [2](#0-1) . Since a `NearDeterministic`-shaped ID contains no `.`, it satisfies `is_top_level()` in `action_create_account`, and because its length (42 chars) is greater than the historically-configured `min_allowed_top_level_account_length` threshold used to gate short top-level names to the registrar, any ordinary predecessor account can submit a plain `CreateAccount` for that ID without registrar permission [6](#0-5) . This creates the account with zero balance, `AccountContract::None`, and sets `actor_id` to the new account itself, letting the same transaction chain further actions (e.g. `AddKey`) against the account it just squatted.

The doc for `action_implicit_account_creation_transfer` notes `NearDeterministic` accounts are meant to be created only via the transfer-implicit path or the dedicated `DeterministicStateInit` action (`create_deterministic_account`, `deterministic_account_id.rs:94`) [7](#0-6) , and `check_account_existence`'s handling of `DeterministicStateInit` explicitly tolerates both existing and non-existing accounts, deferring to the state-init logic [8](#0-7) . Because plain `CreateAccount` is not blocked for this class, the rightful deployer's `DeterministicStateInit` receipt will land on an already-existing account that the attacker controls (having just added a full-access key to it via the follow-up `AddKey` action in the same receipt), rather than on a fresh, uninitialized deterministic account.

### Impact Explanation
This is authorization escalation over deterministic-account addresses (NEP-616): an unprivileged attacker can pre-empt/squat a to-be-deployed deterministic account ID, add a full-access key to it, and thereby seize control of the address (and any funds later sent to it or dependent on that fixed address) before the rightful `DeterministicStateInitAction` deployer arrives, permanently freezing or diverting the account.

### Likelihood Explanation
The only precondition is that the attacker knows or can predict a `NearDeterministic`-formatted account ID ("0s" + 40 hex) that a legitimate party intends to later initialize via `DeterministicStateInit` — deterministic addresses are by design computable/predictable ahead of deployment, which is the entire point of NEP-616, making this fully feasible and repeatable at low cost (one ordinary transaction with `CreateAccount` + `AddKey`, no special privileges, no leaked keys).

### Recommendation
Extend `account_is_implicit` (or add a parallel check in `check_account_existence`) to also reject `Action::CreateAccount` when `account_id.get_account_type() == AccountType::NearDeterministicAccount`, mirroring the existing protection for `NearImplicitAccount`/`EthImplicitAccount`.

### Proof of Concept
Unit test in `runtime/runtime/src/actions.rs` test module:
1. Construct an `AccountId` of the form `"0s" + "a".repeat(40)` (or valid hex) and assert `account_id.get_account_type() == AccountType::NearDeterministicAccount`.
2. Call `check_account_existence(&Action::CreateAccount(CreateAccountAction {}), &None, &account_id, &config, true)` and observe it returns `Ok(())` instead of `Err(OnlyImplicitAccountCreationAllowed)`.
3. Call `action_create_account` with a valid top-level/sub-account predecessor for that same ID and assert it succeeds, producing `account = Some(Account { contract: AccountContract::None, amount: 0, .. })`.
4. Follow up with an integration/test-loop scenario: attacker submits `CreateAccount` + `AddKey(full_access)` for the deterministic ID; then simulate the rightful owner's `DeterministicStateInitAction` targeting the same ID and confirm the account is not re-initialized as a fresh deterministic account (already exists with attacker's key installed).

pub(crate) fn action_create_account(
    fee_config: &RuntimeFeesConfig,
    account_creation_config: &AccountCreationConfig,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    account_id: &AccountId,
    predecessor_id: &AccountId,
    result: &mut ActionResult,
) {
    if account_id.is_top_level() {
        if account_id.len() < account_creation_config.min_allowed_top_level_account_length as usize
            && predecessor_id != &account_creation_config.registrar_account_id
        {
            // A short top-level account ID can only be created registrar account.
            result.result = Err(ActionErrorKind::CreateAccountOnlyByRegistrar {
                account_id: account_id.clone(),
                registrar_account_id: account_creation_config.registrar_account_id.clone(),
                predecessor_id: predecessor_id.clone(),
            }
            .into());
            return;
        } else {
            // OK: Valid top-level Account ID
        }
    } else if !account_id.is_sub_account_of(predecessor_id) {
        // The sub-account can only be created by its root account. E.g. `alice.near` only by `near`
        result.result = Err(ActionErrorKind::CreateAccountNotAllowed {
            account_id: account_id.clone(),
            predecessor_id: predecessor_id.clone(),
        }
        .into());
        return;
    } else {
        // OK: Valid sub-account ID by proper predecessor.
    }

    *actor_id = account_id.clone();
    *account = Some(Account::new(
        Balance::ZERO,
        Balance::ZERO,
        AccountContract::None,
        fee_config.storage_usage_config.num_bytes_account,
    ));
}
