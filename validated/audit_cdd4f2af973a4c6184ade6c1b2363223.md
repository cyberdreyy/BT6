## Title
`vesting::withdraw_stake` sweeps the vesting contract account's entire AptosCoin balance instead of only the distributed amount — ([File: aptos-move/framework/aptos-framework/sources/vesting.move])

### Summary
`vesting::withdraw_stake` mirrors the exact bug pattern from the external report: instead of tracking the amount actually produced by the operation it just triggered (`staking_contract::distribute`), it reads the *entire* current balance of the vesting contract's resource account and withdraws all of it: [1](#0-0) 

```move
fun withdraw_stake(vesting_contract: &VestingContract, contract_address: address): Coin<AptosCoin> {
    // Claim any withdrawable distribution from the staking contract. The withdrawn coins will be sent directly to
    // the vesting contract's account.
    staking_contract::distribute(contract_address, vesting_contract.staking.operator);
    let withdrawn_coins = coin::balance<AptosCoin>(contract_address);
    let contract_signer = &get_vesting_account_signer_internal(vesting_contract);
    coin::withdraw<AptosCoin>(contract_signer, withdrawn_coins)
}
```

`contract_address` here is the vesting contract's resource account — a normal, publicly known Aptos account address (derivable/queryable via the `#[view] stake_pool_address` and the vesting contract's own address) that anyone can `aptos_account::transfer` AptosCoin to. `staking_contract::distribute` is itself a permissionless entry function (comment: "Allow anyone to distribute already unlocked funds... does not need to be restricted to just the staker or operator") [2](#0-1) , so nothing prevents an accidental-transfer scenario followed immediately by a distribute-triggering call.

### Finding Description
`withdraw_stake` is the shared helper invoked by `distribute` (pool-wide distribution to all shareholders), `terminate_vesting_contract`, and `admin_withdraw` (funds sent solely to the admin's `withdrawal_address`) [3](#0-2) . In every one of these flows, `withdraw_stake` is used to determine "how much was just unlocked/distributed from staking" — but it computes that amount as `coin::balance<AptosCoin>(contract_address)`, i.e., the account's total balance, not a before/after delta or the actual return value of the distribution.

If any AptosCoin is present in the vesting contract's resource account for any reason other than the just-triggered `staking_contract::distribute` call (e.g., a user error transferring APT directly to the vesting contract address, or coins left over from a partial/previous flow), that entire balance is swept up and disbursed by whichever caller next triggers `vest`/`distribute`/`admin_withdraw`. Because `admin_withdraw` sends 100% of `withdraw_stake`'s result to `vesting_contract.withdrawal_address` [4](#0-3) , an admin (or, via `distribute`, unrelated shareholders) can capture value that was never part of the vesting grant.

This is structurally identical to the TreehouseRouter `_stethToWsteth` bug: return-value substitution with `balanceOf(this)` after an external interaction, allowing accidentally-transferred assets to be misappropriated by whoever calls the sweep-triggering function next.

### Impact Explanation
Impact is stake/vesting-scoped fund misdirection: coins not owned by the vesting contract's rightful shareholders (accidentally sent APT) get merged into and distributed with the vesting pool's proceeds, crediting the wrong accounts (shareholders' `distribution_pool` shares, or worse, the admin's arbitrary `withdrawal_address` via `admin_withdraw`). This matches the required impact class "Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account or traps value."

### Likelihood Explanation
This requires an accidental transfer of AptosCoin to a vesting contract's resource account, which is a genuine but not attacker-controlled precondition (same precondition class as the original report, which was still rated High). Given vesting contract addresses are public and predictable/visible on-chain, and `distribute`/`vest`/`admin_withdraw` are commonly and permissionlessly (for `distribute`) or admin-routinely (for `admin_withdraw`) called, any stray transfer is very likely to be swept in during normal operation rather than being recoverable by the original sender.

### Recommendation
Change `withdraw_stake` to track only the amount actually produced by `staking_contract::distribute` (e.g., record balance before the call and compute the delta, or have `staking_contract::distribute`/`distribute_internal` return the exact amount deposited to `contract_address`), rather than reading the full account balance. Any coins unrelated to the distribution should be recoverable through an explicit, separate "rescue" path that returns them to the original sender, not silently merged into vesting distributions.

### Proof of Concept
1. Locate a live vesting contract's resource account address `V` via `vesting::stake_pool_address`/contract address (public view functions).
2. Any third party calls `aptos_account::transfer(attacker_or_alice, V, X)` — accidentally or otherwise — depositing `X` AptosCoin directly into the vesting contract's account.
3. Anyone calls `vesting::distribute(V)` (or the admin calls `admin_withdraw`), which internally invokes `withdraw_stake`.
4. `withdraw_stake` computes `withdrawn_coins = coin::balance<AptosCoin>(V)`, which now includes the legitimately-unlocked staking distribution **plus** the `X` coins transferred in step 2.
5. The full amount, including `X`, is withdrawn and distributed to the vesting pool's shareholders (via `distribute`) or entirely to `withdrawal_address` (via `admin_withdraw`) — funds belonging to whoever sent them in step 2 are now irrecoverably distributed to unrelated accounts.

Note: I was unable to fully confirm the exact call sites of `vest`/`distribute`/`admin_withdraw` public entry function bodies due to index truncation/formatting issues in this session (`read_file` returned mostly blank lines for that range); the causal chain through `withdraw_stake` and its balance-based accounting, however, is directly confirmed from source. A Devin session with full file access is recommended to verify the exact public entry-point wiring before remediation.
