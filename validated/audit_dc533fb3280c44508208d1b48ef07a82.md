### Title
Stale confirmations from deleted multisig members allow request execution below the configured confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts confirmations recorded in a `HashSet<String>` keyed by member identity, but `delete_member` only purges outstanding *requests originated by* the removed member — it never scrubs that member's confirmations recorded on *other* still-open requests. A member who confirmed a request and is later removed from the multisig still counts toward that request's `num_confirmations` threshold, letting the request execute with fewer live, authorized signers than `num_confirmations` requires.

### Finding Description
`confirm()` reads the stored `HashSet<String>` of confirmations for a request and compares its length + 1 against `self.num_confirmations`: [1](#0-0) 

`delete_member()` is the only place membership removal touches the `confirmations` map, and it removes confirmations only for requests whose *original signer* (`r.member`) equals the member being deleted: [2](#0-1) 

It does not iterate over `confirmations` to strip the deleted member's entry from HashSets belonging to *other* requests that member merely confirmed (but did not create). Those stale string entries remain valid, uncounted-for-removal votes.

**Binding broken:** `live_confirmations(request) == num_confirmations` is the invariant the contract is supposed to enforce before executing a request. In reality the contract enforces `stored_confirmations(request).len() + 1 >= num_confirmations`, where `stored_confirmations` can contain members no longer in `self.members`. After a member is deleted, `live_confirmations(request) < stored_confirmations(request).len()`, so a request can execute while `live_confirmations(request) < num_confirmations`.

### Impact Explanation
This is a threshold-bypass on a multisig, one of the explicitly listed Critical impacts: "a multisig request executed below threshold." A K-of-N multisig is a custody/authorization mechanism guarding transfers, key changes, contract deployment, etc.; if it can be forced to execute with fewer than K currently-authorized confirmations, arbitrary `Transfer`, `AddKey`/`DeleteMember`, or `FunctionCall` actions can be pushed through by a shrinking or compromised set of members, up to and including draining the account or seizing full control via `AddKey`.

### Likelihood Explanation
Exploitation requires only actions available to existing multisig members through the contract's own public methods (`add_request`, `confirm`, and a `DeleteMember` request) — no foundation, owner, or out-of-scope privileged actor is needed:
1. Member A confirms request R (adds a partial confirmation, R not yet at threshold).
2. Members (any quorum, potentially just remaining honest/compromised members acting on a separate, unrelated request) execute a `DeleteMember { member: A }` request, removing A from `self.members`. `delete_member` only clears requests A itself created, not R.
3. R still shows A's confirmation in its `confirmations` set. Remaining live members only need `num_confirmations - (already stored confirmations, including A's stale one)` further confirmations — one fewer live confirmer than `num_confirmations` actually requires — to trigger `execute_request`.

This is a plausible sequence in normal multisig lifecycle usage (member rotation is a supported, documented feature), not a contrived edge case.

### Recommendation
When removing a member in `delete_member`, iterate all entries in `self.confirmations` and remove the deleted member's identity string from every request's confirmation set (not just requests it originated), or alternatively re-validate at `confirm()` time that every entry in a request's stored confirmation set still corresponds to a current member of `self.members` before counting it toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. A calls `add_request` to create request `R` (e.g. `Transfer` to an attacker-controlled account), then `confirm(R)` — confirmations = `{A}`.
3. Separately, `B`, `C`, `D` create and confirm a `DeleteMember{member: A}` request — this passes (3-of-4) and executes `delete_member`, which only clears requests where `r.member == A` (i.e., requests A created, such as R's own creation record is *not* cleared because deletion logic only removes A's own authored request entries, not confirmation entries on other requests — verified from `delete_member` code, lines 356-379). Confirmations on `R` (which contain `"A"`) are untouched since R was not authored solely-matching removal filter tied to signer, but critically even if `R` happens to be authored by A itself and gets deleted here, the vulnerability generalizes to any request A merely *confirmed* rather than authored — pick R2 authored by B and confirmed by A instead.
4. Reconstruct: B authors `R2` (a `Transfer`), A confirms `R2` (confirmations = `{A}`), then A is removed via step 3. `self.members` = `{B, C, D}`, `num_confirmations` still 3.
5. Only two more live confirmations (say B, C) are now needed on `R2`: `confirmations.len() (=1, "A") + 1 >= 3` triggers execution after just one additional live confirm from B or C — the transfer executes with only 2 truly-current members having confirmed, against a configured 3-of-N policy.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
