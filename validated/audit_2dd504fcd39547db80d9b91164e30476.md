### Title
VerifyDKGResult / ExportDKGResult perform no Functions-subscription ownership check, allowing any authenticated node API caller to probe/retrieve DKG results for instances they are not associated with - ([File: core/web/vault_controller.go])

### Finding Description
Both `VaultController.VerifyDKGResult` and `VaultController.ExportDKGResult` accept only an `InstanceID` (and, for verify, a `MasterPublicKey`) in the request body, then directly look up the stored DKG result package via `vault.NewVaultORM(vc.App.GetDB()).ReadResultPackage(ctx, dkgocrtypes.InstanceID(req.InstanceID))` [1](#0-0) [2](#0-1) . Neither handler validates that the caller (or the node session/API token used) is entitled to the Functions subscription tied to that `InstanceID`; there is no lookup against a subscription-to-caller mapping, no allowlist check, and no scoping of the ORM query beyond the raw instance identifier supplied by the request body. The only "authorization" enforced is whatever role-based route middleware is applied when these handlers are wired into the router; the code itself contains zero subscription-ownership logic. `VerifyDKGResult` further discloses whether an instance's result matches a given `MasterPublicKey` and returns a SHA-256 digest of the on-disk `ReportWithResultPackage`, and `ExportDKGResult` returns the full hex-encoded result package plus its digest to any caller who supplies a valid `InstanceID`, enabling enumeration/confirmation of DKG ceremony state without any proof of association to that ceremony's subscription. [3](#0-2) [4](#0-3) 

I was unable to confirm from the available index which exact role-level gin middleware (`view`/`run`/`admin`) is applied to the `/vault/dkg_results/verify` and `/vault/dkg_results/export` routes in `core/web/router.go` — the route registration lines matched but their content (including any `authorization.RequiresAuth`/role-group wrapper) was not retrievable within the available searches. This is a material gap: whether this issue is exploitable by a genuinely low-privilege ("view"-role) authenticated user, versus only by any node-run-role user, depends on that route wiring, which I could not verify with certainty.

### Impact Explanation
Assuming route-level RBAC does not itself gate access per-subscription (which is consistent with the handler code having no such check), any authenticated node API credential holder can enumerate `InstanceID`s and retrieve/verify DKG result packages for Functions subscriptions not associated with their credential, since the on-chain subscription/allowlist boundary is never re-validated at the node API layer. This matches the "unauthorized action on another user's job/subscription/secret" / information-disclosure impact class rather than direct fund movement, because the disclosed material is an encrypted result package validated against the node's own DKG recipient key — but it still degrades defense-in-depth to a purely on-chain control.

### Likelihood Explanation
Exploitability strictly depends on the role required by the route wiring in `core/web/router.go`, which could not be confirmed here. If the routes are reachable by any session/API-token role weaker than the intended subscription-scoped access, exploitation requires only a valid `InstanceID` guess/enumeration and a single authenticated HTTP POST — trivially repeatable. If the routes in fact require an elevated role equivalent to full node-admin API access, this finding reduces to defense-in-depth degradation without a genuine escalation path.

### Recommendation
Given the unresolved uncertainty about the actual route-level role requirement, this cannot be conclusively confirmed as a role/authorization bypass without inspecting the exact `core/web/router.go` route group for `/vault/dkg_results/verify` and `/vault/dkg_results/export`. Recommend a Devin session with full repo/filesystem access to inspect `router.go`'s route-group role assignment for these two endpoints and, if confirmed reachable by low/view-role credentials, add an explicit subscription-ownership/allowlist check inside `VerifyDKGResult`/`ExportDKGResult` before returning result data.

### Proof of Concept
Cannot be finalized without confirming route role requirements in `core/web/router.go`; a handler-level integration test (`core/web/vault_controller_test.go`) should be extended to assert: (1) a view-role session token receives 200 (not 403) from both endpoints given a valid `InstanceID` belonging to another subscription, and (2) no ORM/service call in the handler chain references caller identity or subscription ownership — confirming the boundary is enforced only downstream, on-chain.

type VerifyDKGResultRequest struct {
	InstanceID      string `json:"instanceId"`
	MasterPublicKey string `json:"masterPublicKey"`
}

// VerifyDKGResult verifies that the DKGResult corresponds to the given public key
// and contains a share that can be decrypted by the node's DKG recipient key.
// Example:
// "POST <application>/vault/dkg_results/verify"
func (vc *VaultController) VerifyDKGResult(c *gin.Context) {
	var req VerifyDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" || req.MasterPublicKey == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId and masterPublicKey are required"))
		return
	}

	keys, err := vc.App.GetKeyStore().DKGRecipient().GetAll()
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}
	if len(keys) == 0 {
		jsonAPIError(c, http.StatusBadRequest, errors.New("no DKG recipient key found"))
		return
	}
	if len(keys) > 1 {
		jsonAPIError(c, http.StatusBadRequest, errors.New("multiple DKG recipient keys found"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

	err = vaultcap.VerifyDKGResult(v.ReportWithResultPackage, req.MasterPublicKey, keys[0])
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("DKG result verification failed: %w", err))
		return
	}

	sha := sha256.Sum256(v.ReportWithResultPackage)
	shaStr := hex.EncodeToString(sha[:])
	jsonAPIResponse(c, presenters.NewVerifyDKGResultResource(shaStr), "verifyDKGResult")
}

// ExportDKGResult returns the DKGResult corresponding to the given instance ID
// "POST <application>/vault/dkg_results/export"
func (vc *VaultController) ExportDKGResult(c *gin.Context) {
	var req ExportDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId is required"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

	hexPackage := hex.EncodeToString(v.ReportWithResultPackage)
	sha := sha256.Sum256(v.ReportWithResultPackage)
	shaStr := hex.EncodeToString(sha[:])
	jsonAPIResponse(c, presenters.NewExportDKGResultResource(hexPackage, shaStr), "exportDKGResult")
