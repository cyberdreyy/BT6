### Title
Confirmations from removed multisig members are not purged, allowing requests to execute with fewer live-member approvals than `num_confirmations` - (File: multisig2/src/lib.rs)

### Summary
`DeleteMember` removes an access key/account from `self.members`, but it only strips confirmations/requests that the removed member *originated* — it never scans the `confirmations` map for votes the removed member cast on *other* still-pending requests. Those stale confirmations remain counted toward the `num_confirmations` threshold, so a request can later execute with fewer live, currently-authorized members than the configured threshold requires.

### Finding Description
`MultiSigContract::confirm` tallies approvals purely from the `confirmations: LookupMap<RequestId, HashSet<String>>` set and compares its length to `self.num_confirmations`: [1](#0-0) 

It does not re-validate that every entry in that `HashSet` still corresponds to a current member of `self.members` — membership is only checked for the *current* caller via `current_member()`, not for previously-recorded confirmers.

`delete_member` (invoked through `execute_request`'s `DeleteMember` branch) only cleans up:
- requests where the removed member was the **original requester** (`r.member == member`), and
- the removed member's `num_requests_pk` entry. [2](#0-1) 

It never iterates `self.confirmations` to remove the departing member's identifier from confirmation sets on requests created by *other* members. Because `MultisigMember::to_string()` serializes the member's public key/account id deterministically, that stale string remains a permanent, uncleared vote in any `HashSet<String>` it was inserted into.

**Broken invariant:** the protocol's implicit binding is `live confirmations on a request == confirmations by members currently in self.members`, and execution should only occur once `live confirmations >= num_confirmations`. This is violated: `confirmations.len()` can include confirmations cast by accounts/keys no longer in `self.members`, so a request can be executed with `live confirmations < num_confirmations`.

### Impact Explanation
This falls under "a multisig request executed below threshold" (Critical). A multisig configured for `k`-of-`n` approval can have an arbitrary `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc. request executed with fewer than `k` currently-authorized approvers, because a stale confirmation from a member who was later removed still counts. This breaks the core security guarantee of the multisig (that `k` *live* members must agree), enabling unauthorized fund transfers or contract upgrades to be pushed through with insufficient live consensus.

### Likelihood Explanation
Membership changes over time are an expected, routine operation for any long-lived multisig (member rotation, key compromise cleanup, onboarding/offboarding). Any sequence where:
1. Member A confirms request R (created by member B, not yet at threshold),
2. Member A is later removed via a separate `DeleteMember` request,
3. R is still pending,
4. Remaining live members confirm R until `confirmations.len() + 1 >= num_confirmations`,

...triggers the bug. No attacker needs special privilege beyond being a normal remaining multisig member/confirmer completing an otherwise-ordinary confirmation; the flaw is triggered by ordinary contract flows rather than requiring a malicious actor to break access control directly.

### Recommendation
When executing `DeleteMember`, iterate all entries in `self.confirmations` (or maintain an index of confirmations-by-member) and remove the departing member's identifier from every request's confirmation set, not just requests it authored. Alternatively, when tallying confirmations in `confirm()`, filter the stored confirmation set to only members still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `B` calls `add_request` to create request `R` (a `Transfer`), then `A` calls `confirm(R)` → `confirmations(R) = {A}` (len 1, `1+1 < 3`, so stays pending).
3. Separately, members reach quorum on a `DeleteMember { member: A }` request and it executes: `delete_member` removes `A` from `self.members` and cleans `num_requests_pk`, but since `A` did not *author* `R`, `A`'s confirmation on `R` is left untouched in `self.confirmations`.
4. `C` calls `confirm(R)` → `confirmations(R) = {A, C}`, len 2, `2 + 1 >= 3` → `execute_request(R)` fires the `Transfer`.
5. Only `B` (author) and `C` are currently live members who acted on `R`; `A`'s stale confirmation, from a member removed in step 3, was required to reach the threshold of 3. The transfer executes with 2 live approvals against a configured 3-of-4 policy — the `num_confirmations` binding is broken.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
