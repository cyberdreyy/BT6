### Title
Stale confirmations from removed multisig members are still counted toward the approval threshold - (File: `multisig2/src/lib.rs`)

### Summary
When a multisig member is removed via `DeleteMember`, only the requests *originated* by that member have their confirmations purged. Any confirmation that the removed member previously cast on a request *originated by a different member* is never cleared. Because `confirm()` only compares the raw size of the `confirmations` set against `num_confirmations`, without re-validating that every entry in that set still belongs to `self.members`, a request can later be executed using a mix of stale (removed-member) and live-member confirmations — letting it execute with fewer *live* approvals than the configured threshold.

### Finding Description
`confirm()` decides to execute a request purely based on `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

The confirmations set is a plain `HashSet<String>` keyed by the confirming member's serialized identity, and nothing in `confirm()` checks that every prior entry is still `self.members.contains(...)`.

`delete_member()` cleans up state for the removed member, but the cleanup is scoped to requests whose *original signer* (`r.member`) equals the removed member — it does not scan `confirmations` sets of other requests to strip out the removed member's prior votes: [2](#0-1) 

So the invariant the contract is supposed to enforce — "a request executes only once `num_confirmations` *current* members have approved it" — is broken. The actual state after a member removal is:
`confirmations set size == (live-member confirmations) + (stale confirmations from removed members)`,
while the code treats it as if `confirmations set size == live-member confirmations`.

This is the exact "confirmations counted versus live members" binding called out as in-scope: the contract's bookkeeping of *approvals* diverges from the true set of members entitled to approve.

The equivalent v1 `multisig/src/lib.rs` contract has the identical pattern in its `DeleteKey` handler — it also only purges requests keyed by the deleted `signer_pk`, not confirmations left by that key on other requests: [3](#0-2) 

### Impact Explanation
This is a Critical-class impact: a multisig request (e.g., a `Transfer` moving NEAR out of the multisig account, or an `AddKey`/`FunctionCall` action) can be **executed below the intended threshold** of live signers. An account previously trusted with `num_confirmations`-of-N security can effectively be drained or have privileged actions taken with fewer than `num_confirmations` currently-authorized approvers, because a removed member's leftover vote silently still counts.

### Likelihood Explanation
No special privilege beyond ordinary multisig membership is required — this is triggerable by the normal, expected admin workflow of the contract (removing a member) combined with any pending request that a soon-to-be-removed member had already confirmed. No malicious deployment, redeploy, or off-chain trust is needed; it's a pure sequencing issue within intended contract usage:
1. A request `R` is created by member A (not yet enough confirmations).
2. Member B confirms `R`.
3. Members legitimately vote to remove B (e.g., because B's key was compromised, or B is leaving) via `DeleteMember` — this executes normally.
4. `R` is untouched by the cleanup (since `r.member == A`, not B), and its `confirmations` set still contains B.
5. Remaining live members confirm `R` further; the stale count from B lets `R` cross the `num_confirmations` threshold with one fewer *live* approval than intended.

### Recommendation
When executing `DeleteMember` (and `DeleteKey` in the v1 contract), iterate over **all** outstanding requests' `confirmations` sets (not just those originated by the removed member) and remove the deleted member's entry from each. Alternatively, when `confirm()` computes whether to execute, first filter the stored confirmations set to only those entries still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
Given a 4-member multisig `{A, B, C, D}` with `num_confirmations = 3`:
1. `add_request(R)` by A → `confirmations[R] = {}`.
2. `confirm(R)` by B → `confirmations[R] = {B}` (len 1 < 3, not executed).
3. Separately, members confirm and execute `DeleteMember { member: B }` (a valid, properly-threshold-confirmed admin action) — `self.members` becomes `{A, C, D}`, but `confirmations[R]` is left as `{B}` because `delete_member` only purges requests where `r.member == B`, and `R.member == A`.
4. `confirm(R)` by C → `confirmations[R] = {B, C}` (len 2 < 3, not executed).
5. `confirm(R)` by D → `confirmations[R] = {B, C, D}` → `len() as u32 + 1 = 4 >= 3` → `execute_request(R)` runs.

`R` executes with only 2 confirmations from *current* live members (C and D) plus 1 stale confirmation from removed member B, despite the contract requiring 3-of-current-members. This directly reproduces the analog "confirmations counted versus live members" binding break, with the transfer/action in `R` executed below the configured threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
