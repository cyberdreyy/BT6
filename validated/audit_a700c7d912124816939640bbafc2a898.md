### Title
Outgoing receipts generated by a failed FunctionCall action receipt are forwarded even after `check_storage_stake` fails and the receipt is rolled back - ([File: runtime/runtime/src/lib.rs])

### Summary
`apply_action_receipt` executes the action loop and accumulates any outgoing promises into `result.new_receipts` before checking whether the receiver account still satisfies its storage-stake requirement. When the storage-stake check fails, the code sets `result.result` to `Err(LackBalanceForState)` and rolls back all trie writes made during the receipt (including balance debits caused by any `Transfer`-type promise actions), but the outgoing-receipt generation/forwarding code that runs afterward operates unconditionally on `result.new_receipts` rather than being gated on `result.result.is_ok()`.

### Finding Description
The action loop in `apply_action_receipt` executes each action of a `FunctionCall` receipt and merges any promises the contract issued (e.g. via `promise_batch_action_transfer`) into `result.new_receipts` [1](#0-0) . Only after the loop completes does the runtime check whether the receiver account can still cover its storage stake; if not, `result.set_error(... LackBalanceForState ...)` is called, which flips `result.result` to `Err` [2](#0-1) . Based on `result.result`, the code either commits or rolls back `state_update` [3](#0-2) , which correctly undoes trie-level writes such as the balance debit performed by the `Transfer` action that funded the attacker's outgoing promise.

However, the subsequent code that assigns receipt IDs and forwards `result.new_receipts` to `receipt_sink` (or `instant_receipts`) runs unconditionally on the `new_receipts` vector collected earlier in the function; the only place that gate is checked is the narrower `ReturnData::ReceiptIndex` branch used for data receivers, not the general forwarding path [4](#0-3) [5](#0-4) . This means a receipt that ultimately fails due to `check_storage_stake` (verifier logic at [6](#0-5) ) still has its already-generated outgoing receipts (e.g. a crafted `Transfer` to an attacker account) sent out, while the trie-level balance change that was supposed to pay for that transfer is rolled back.

Attack flow: an attacker deploys a contract that, within a single `FunctionCall` action, (a) issues `promise_batch_action_transfer` sending funds to an attacker-controlled account, and (b) writes enough state (or otherwise inflates `storage_usage`) that the account fails `check_storage_stake` after the action loop finishes successfully. The `FunctionCall` action itself succeeds (`result.result` starts `Ok`), so its transfer promise is merged into `result.new_receipts`. Only afterward does the storage-stake check flip `result.result` to `Err`, triggering `state_update.rollback()` — undoing the sender's balance debit and storage writes — while the outgoing `Transfer` receipt already captured in `result.new_receipts` proceeds to `receipt_sink`. When that receipt later executes on the receiver, it credits the receiver without any corresponding debit ever having been committed on the sender side, i.e., token inflation / fund duplication.

### Impact Explanation
If confirmed by a runtime-level integration test, this maps to the "token inflation or loss" and "theft of user funds" bounty categories: an attacker can mint value by having a receipt debit-then-rollback while its spawned outgoing transfer still executes, crediting an attacker account with tokens that were never actually removed from the paying account's committed state.

### Likelihood Explanation
The precondition is fully attacker-controlled and requires no privileged access: any account can deploy a WASM contract, call it via a normal signed transaction, and craft the contract logic to (1) issue an outgoing transfer promise and (2) grow its own storage usage enough to trigger `LackBalanceForState` in the same receipt. This is deterministic and repeatable — the attacker fully controls storage usage growth (e.g. writing large keys) and gas/deposit amounts, so the "receiver storage-stake shortfall after a promise is queued" scenario is reliably reproducible. The cost is only the gas/deposit for one function call.

### Recommendation
Gate the receipt-ID generation/forwarding block (`runtime/runtime/src/lib.rs` lines ~1092-1180) on `result.result.is_ok()` (or otherwise clear `result.new_receipts` when `check_storage_stake` fails), so that a receipt failing the post-execution storage-stake check discards all of its generated outgoing receipts symmetrically with the `state_update.rollback()` it already performs.

### Proof of Concept
Add a `runtime/runtime/tests/apply.rs` (or `runtime/runtime/src/tests/apply.rs`) integration test:
1. Deploy a test contract whose exported function calls `promise_batch_action_transfer` to send a fixed amount to `attacker.test`, then writes a large amount of contract state (e.g., via `storage_write`) sized so that, given the account's balance after the transfer, it falls below the storage-stake requirement.
2. Submit a `FunctionCall` action receipt invoking this function with enough attached deposit/gas to succeed the action execution itself.
3. Run `apply_action_receipt` (or the higher-level `Runtime::apply`) and inspect:
   - The `ExecutionOutcome` for this receipt has status `Failure(LackBalanceForState)`.
   - Assert the account's committed balance/storage in the resulting `TrieUpdate`/state root is unchanged from before the receipt (confirming rollback occurred).
   - Assert that **no** outgoing `Transfer` receipt to `attacker.test` appears in `receipt_sink`'s outgoing receipts / the chunk's produced outgoing receipts list.

If the outgoing `Transfer` receipt to `attacker.test` **is** present in the outgoing receipts despite the account rollback and `LackBalanceForState` failure, the vulnerability is confirmed.
