I need to confirm the claim dependency on a successful `stopEpoch` and check emergency escape paths before finalizing.### Title
Unprivileged ERC4626 vault liquidity drain makes `stopEpoch` permanently re-vertible, freezing all tranche LP funds and pending withdraw receipts - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
In the programmable-borrower mode, `IdleCDOEpochVariant._stopEpoch` calls `ProgrammableBorrower.onStopEpoch` **outside** the `try/catch` that protects the borrower pull. The hook's coverage check uses `vault.convertToAssets` (total assets), but then calls `vault.withdraw`, which reverts when the ERC4626 vault has insufficient *liquid* assets. Because `StopEpochVaultLiquidityUnavailable` propagates, the entire `stopEpoch` reverts. Any unprivileged user of the configured ERC4626 vault (e.g., a Morpho-style market) can keep draining its liquidity each time it refills, indefinitely blocking epoch close. While `isEpochRunning` stays true the CDO remains `_pause()`d, `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are false, and no pending withdraw receipt can be claimed — a temporary freezing of the entire pool NAV caused by an unprivileged attacker.

### Finding Description
The upstream bug class (JLSEC-2026-468): the SAX parser emits external-entity events even when the application set a flag intended to suppress them — a guard that checks the wrong condition lets an externally controlled behavior through. The analog here is precise:

1. `_stopEpoch` calls the external hook `IProgrammableBorrower(_borrower()).onStopEpoch(...)` at `IdleCDOEpochVariant.sol:398`, *before* the `try this.getFundsFromBorrower(...)` block at line 408, so hook reverts are not caught — the comment even documents this as intentional ("Hook reverts bubble so transient ERC4626 liquidity failures can be retried"). [1](#0-0) 
2. Inside `onStopEpoch`, the "checked" equivalent is `if (shortfall > _currentVaultAssets()) return true;` — it verifies coverage via `convertToAssets`, i.e., *total* vault assets. [2](#0-1) 
3. But `vault.withdraw(shortfall, ...)` requires *liquid, withdrawable* assets. In interest-bearing ERC4626 vaults (Morpho, Euler, Aave-wrapped, etc.) `convertToAssets` includes lent-out or otherwise illiquid funds, so the check passes while `withdraw` reverts, hitting `catch { revert StopEpochVaultLiquidityUnavailable(); }`. [3](#0-2) 
4. The revert unwinds the whole `stopEpoch`: `_updateAccounting`, `isEpochRunning = false`, `_unpause()`, `allowAA/BBWithdrawRequest = true` never execute (`IdleCDOEpochVariant.sol:474-483`), so the pool stays in the stopped-but-unclosable running state where deposits and withdraw requests remain blocked and no `claimWithdrawRequest` can succeed for the maturing epoch.

An unprivileged vault user (explicitly in scope) executes this by borrowing or withdrawing the vault's free liquidity just after `epochEndDate` passes, and repeating whenever liquidity returns — the same way an XXE attacker controls the external entity. The manager is honest and keeps retrying `stopEpoch`; it reverts every time while the vault is drained.

There is no unprivileged-free recovery: `emergencyExitVault` also calls `vault.redeem`, which reverts under the same liquidity shortage, and `setVault` requires `vault.balanceOf(address(this)) == 0`. [4](#0-3) 

### Impact Explanation
Temporary freezing of 100% of pool NAV plus all pending withdraw receipts. During a running epoch the CDO is paused: `depositAA/BB` revert, `requestWithdraw` reverts (`allowAAWithdrawRequest == false`), and `claimWithdrawRequest` for the maturing epoch can never succeed because the epoch never stops. The attacker controls duration: they only need to keep the ERC4626 vault's `maxWithdraw` below the shortfall whenever the manager retries. In borrowable-liquidity vaults this is cheap and repeatable (borrow all available liquidity, repay later), so the freeze is effectively unbounded, spanning `contracts/IdleCDOEpochVariant.sol` stop flow and `contracts/strategies/idle/IdleCreditVault.sol` claim path.

### Likelihood Explanation
Likelihood is moderate: it requires the programmable-borrower variant wired to an ERC4626 vault whose total assets can exceed liquid assets — the standard case for Morpho/Euler-style markets this contract is designed for (the foundry suite uses a Morpho vault). The attacker needs only to be a user of that external vault — no role, no KYC, no tranche position. The cost is the transient funding cost of draining vault liquidity around `epochEndDate`, which is a publicly visible timestamp. The design explicitly treats this revert as "retryable," but retryability does not bound the freeze because the attacker re-triggers it at will.

### Recommendation
Make the coverage guard check the same condition the withdraw will hit, and don't let a liquidity revert block the honest close path:

- In `onStopEpoch`, compare the shortfall against `vault.maxWithdraw(address(this))` instead of `_currentVaultAssets()`; if `shortfall > maxWithdraw`, return `true` (or `false` to route through the default/recovery path) rather than attempting a withdraw that will revert. This aligns the guard with the actual external-entity behavior — the analog of honoring the "checked" flag.
- Alternatively, move the `onStopEpoch` call inside the `try` in `IdleCDOEpochVariant._stopEpoch` so a liquidity revert falls through to `_handleBorrowerDefault`/recovery accounting instead of reverting epoch close.

```solidity
  uint256 amount = 10_000 * oneScale;
  idleCDO.depositAA(amount);                    // attacker needs no position
  _startEpochAndCheckPrices(0);

  // LP files a normal withdraw request for next epoch (prior epoch flow) so
  // pendingWithdraws > 0, forcing onStopEpoch to pull from the vault.
  // ... requestWithdraw via strategy ...

  vm.warp(cdoEpoch.epochEndDate() + 1);

  // Unprivileged vault user borrows/withdraws all liquid assets from the
  // ERC4626 vault so maxWithdraw(programmableBorrower) < shortfall while
  // convertToAssets still covers it.
  vm.prank(attacker); // arbitrary EOA, no role
  morphoBorrowAllLiquidity(vaultAddress);       // or vault.withdraw(maxWithdraw)

  // Honest manager cannot close the epoch: hook revert propagates.
  vm.prank(manager);
  vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
  cdoEpoch.stopEpoch(0, 0);

  assertTrue(cdoEpoch.isEpochRunning());        // still running, still paused
  assertFalse(cdoEpoch.allowAAWithdrawRequest());
  vm.expectRevert();
  cdoEpoch.claimWithdrawRequest();              // receipts frozen

  // Manager retries whenever liquidity reappears; attacker re-drains each
  // time => unbounded temporary freeze. emergencyExitVault/setVault also
  // revert (redeem illiquid / shares != 0).
}
```

Key assertion: `convertToAssets(shares) >= shortfall` while `vault.withdraw(shortfall)` reverts — the coverage check passes, the external-entity event (revert) still fires, and epoch close is blocked.
