## Analog Found

### Title
Signer unilaterally drops its own equivocation guard on a canonical tenure when it lacks a local `approved_time`, permitting a fork/conflict to be signed - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
The Mattermost bug lets a remote actor, via a mechanism meant for a narrow, well-scoped purpose (shared-channel sync), mutate protection state (read-only) on an object it should have no authority over. The stacks-signer analog is `SortitionData::check_parent_tenure_choice`, which is meant to sanction a reorg only when the replaced tenure's first block was *objectively* proposed too close to the next sortition to matter. Instead, when the evaluating signer simply has no local `approved_time` for that tenure's first block, the code substitutes a hard-coded value of `0` for the elapsed time, which always satisfies the "poorly timed" test and unconditionally sanctions the reorg — even when the replaced block was globally accepted well in advance. Sanctioning immediately calls `mark_tenure_superseded`, which permanently voids that signer's own conflict guard over the tenure it is discarding.

### Finding Description
`check_parent_tenure_choice` is invoked whenever a miner's proposal reorgs off something other than the prior sortition, from both `chainstate/v1.rs::check_proposal` and `validate_tenure_change_payload`: [1](#0-0) [2](#0-1) 

For each reorged tenure, the function:
1. Refuses the reorg if the tenure has more than one globally accepted block [3](#0-2) .
2. Unconditionally treats a tenure the node never mined a block in as supersedable [4](#0-3) .
3. Otherwise looks up `local_block_info = signer_db.get_first_approved_block_in_tenure(...)`; if there is no local record at all, the reorg is refused [5](#0-4) .
4. Otherwise computes the elapsed time between when *this signer* received the new burn block and when *this signer* locally approved the reorged tenure's first block. But if that local record exists yet carries no `approved_time`, the code substitutes `0` and logs "We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal" — which then always passes the `< first_proposal_burn_block_timing` test (config default 60s, sample config comment default 60s) and the tenure is pushed onto `superseded_tenures` and sanctioned regardless of the block's actual, objective timing: [6](#0-5) .

Once every reorged tenure clears these per-tenure checks, `record_superseded_tenure`/`mark_tenure_superseded` is called, which is explicitly documented to remove this signer's own signature over that tenure as a future conflict for as long as the superseding sortition remains canonical: [7](#0-6) [8](#0-7) . This guard removal directly feeds `get_signed_conflicts`, which is what stops a signer from signing two competing blocks at the same height: [9](#0-8) .

The design intent (per `docs/signer-flows.md`) is that a reorg is only sanctioned when the replaced tenure's block "produced its first block too close to the next sortition to count," an objective, network-level timing fact: [10](#0-9) . The `0`-substitution branch replaces that objective criterion with a purely local, subjective one: *whether this particular signer happens to have an `approved_time` recorded for that block* — which depends on this signer's own StackerDB/gossip delivery timing, not on when the block was actually proposed relative to the sortition. A single miner (the "one-slot" actor named in scope) that delays, withholds, or otherwise causes a target signer to never locally pre-commit/accept a tenure's first block (e.g. by manipulating delivery timing, exploiting the signer's own validation backlog, or the signer simply restarting/catching up) can cause that signer's `local_block_info.approved_time` to remain `None` even though `local_block_info` itself (a DB row) exists — landing exactly in the `0`-substitution branch — and thereby force an incorrect "poorly timed, sanction the reorg" verdict on a tenure whose block was, in objective reality, perfectly well-timed and already globally accepted by everyone else.

I was not able to fully verify, from the index alone, the exact SQL predicate behind `get_first_approved_block_in_tenure` (i.e., whether it is possible for that call to return `Some(BlockInfo)` with `approved_time == None`, as opposed to only ever returning rows where `approved_time IS NOT NULL`). The explicit `else` branch and its accompanying log message in `check_parent_tenure_choice` (lines 255-258) strongly imply the authors considered this a reachable state, but this single point should be confirmed against `stacks-signer/src/signerdb.rs`'s definition of `get_first_approved_block_in_tenure` before treating this as fully proven.

### Impact Explanation
If reachable, this breaks the "approved-parent vs canonical" / equivocation-guard equality directly: the signer voids its own conflict record over a canonical, already globally-accepted block based on a fact about its own message-delivery history rather than the block's actual timing. Once voided, `conflict_still_blocks`/`get_signed_conflicts` will no longer prevent the signer from signing a second, conflicting block proposed on the new (reorging) fork at the same height, which is the "Critical" bucket outcome: a signer signing a conflicting/non-canonical block.

### Likelihood Explanation
The mechanism requires only a single miner (block proposer for one slot) plus normal gossip/relay timing — no majority of signers and no other signer's key are needed. It depends on the attacker being able to arrange that one target signer lacks a locally recorded `approved_time` for the tenure's first block at the moment it evaluates the *next* tenure's reorg — a condition that can plausibly arise from ordinary asynchronous delivery, a signer restart, or deliberate selective withholding of the proposal to that one signer, all of which are within a miner/gossip actor's control. The main open question affecting likelihood is the exact reachability of "`local_block_info` is `Some` but `approved_time` is `None`," which requires confirming `get_first_approved_block_in_tenure`'s implementation.

### Recommendation
Do not substitute `0` for missing `approved_time`. If the local signer cannot establish the objective proposal-to-sortition timing for a reorged tenure (i.e., it never locally observed/approved that tenure's first block), the reorg decision should fail closed the same way the "no local knowledge at all" branch does (return `Ok(false)`), rather than defaulting to "assume it was late." Alternatively, derive the timing fact from node/consensus-visible data (e.g., the tenure's actual burn-block timestamps) rather than from this signer's own local approval timestamp, so the sanction decision is objective and not contingent on this signer's own message-delivery history.

### Proof of Concept
1. Miner mines tenure A; it is signed and globally accepted by the network (satisfying the `globally_accepted_blocks <= 1` check).
2. Miner ensures target signer S never locally pre-commits/accepts tenure A's first block before the next sortition (e.g., delayed/selective delivery, or S restarts and has not yet replayed/reprocessed the block), so S's stored `BlockInfo` for that block has `approved_time == None` while still being returned by `get_first_approved_block_in_tenure`.
3. Miner immediately wins the next sortition and proposes tenure B, with a parent-tenure choice that reorgs past tenure A (back to A's prior sortition).
4. S evaluates `check_parent_tenure_choice` for B; tenure A hits the `local_block_info.approved_time == None` branch, `proposal_to_sortition` is forced to `0`, `0 < first_proposal_burn_block_timing` is true, and A is unconditionally pushed to `superseded_tenures` and marked superseded via `mark_tenure_superseded`, despite A's block being neither late nor uncontested.
5. S's `get_signed_conflicts` no longer reports A's block as a conflict while B's sortition is canonical; the miner (or a colluding actor) proposes a new block on B's fork at A's height, and S signs it — S has now signed two conflicting blocks at the same height, one of which the network already treats as canonical.

```rust
                "superseded_tenure_id" => %tenure.consensus_hash,
                "superseded_by" => %self.consensus_hash,
            );
        }
    }
```

```rust
    /// Blocks in tenures whose reorg we sanctioned under the reorg-timing rules (see

    /// sortition is canonical, which the caller derives from the node per evaluation (see
    /// `Signer::reorg_permit_stands`) -- like every other question about whether a conflict is

    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,

                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
```

```rust
    /// Record that we permitted the tenure identified by `superseded_by_*` to reorg this one
    /// under the reorg-timing rules (`first_proposal_burn_block_timing`).
    ///
    /// Having sanctioned the replacement, our own signature over what this tenure built must not
    /// then block it: its blocks stop counting as conflicts (see
    /// [`SignerDb::get_signed_conflicts`]). Recorded when the reorg is permitted rather than
    /// derived at signing time, because by the time a replacement reaches the pre-commit
    /// threshold the sortition view that sanctioned the reorg may be long gone.
    ///
    /// The permit is only honored while the permitting tenure's sortition is still canonical
    /// (checked against the node when the record is applied): if a burnchain fork orphans it,
    /// the reorg we sanctioned can no longer happen, so the record must not keep suppressing
    /// this tenure's conflicts. A re-permit by a different tenure replaces the record, so the
    /// latest permitting sortition is the one checked. Records age out via
    /// [`SignerDb::prune_superseded_tenures`].
    pub fn mark_tenure_superseded(
        &mut self,
        consensus_hash: &ConsensusHash,
        burn_block_height: u64,
        superseded_by_consensus_hash: &ConsensusHash,
        superseded_by_burn_block_hash: &BurnchainHeaderHash,
    ) -> Result<(), DBError> {
        self.db.execute(
            "INSERT OR REPLACE INTO superseded_tenures (consensus_hash, burn_block_height, superseded_by_consensus_hash, superseded_by_burn_block_hash, superseded_at) VALUES (?1, ?2, ?3, ?4, ?5)",
            params![
                consensus_hash,
                u64_to_sql(burn_block_height)?,
                superseded_by_consensus_hash,
                superseded_by_burn_block_hash,
                u64_to_sql(get_epoch_time_secs())?
            ],
        )?;
        Ok(())
    }
```

```markdown
One decision does have to be recorded, because it is ours rather than the
node's. When a miner builds off something other than the prior sortition,
`check_parent_tenure_choice` decides whether the reorg is allowed: it is, if
every tenure being reorged has at most one globally accepted block and produced
its first block too close to the next sortition to count
(`first_proposal_burn_block_timing`). Having sanctioned that replacement, the
signer records those tenures as **superseded** (`mark_tenure_superseded`), so its
own signature over what they built does not then block the replacement it just
permitted — the node cannot answer this one at signing time, since it still
serves the reorged tenure as fully live until the replacement lands. What _is_
still derived from the node is the permit's own validity: the record carries the
permitting tenure's sortition, and it only excludes conflicts while that
sortition remains canonical (section 5, `reorg_permit_stands`), so a burnchain
fork that orphans the permitting tenure automatically voids the permit. A record
more than `MAX_FORK_DEPTH` (100) burn blocks below the tip is dropped; a fork
that deep would cause far bigger problems than a stale conflict.
```
