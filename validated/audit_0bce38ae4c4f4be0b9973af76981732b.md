### Title
Signature message silently reclassified as a pre-commit, bypassing the pre-commit validity gate - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`store_and_process_block_signature` contains a backward-compatibility fallback that, on receiving a `BlockAccepted` signature from a peer for which no prior `BlockPreCommit` was recorded, re-dispatches the message into `handle_block_pre_commit` and returns, treating a *signature* message as if it were a *pre-commit* message.

### Finding Description
In the normal flow, a pre-commit (`BlockPreCommit`) is a promise with no signature attached, gated by `handle_block_pre_commit` on `valid = true` (i.e., the receiver's own validation of the block) before it is allowed to count toward the 70% pre-commit threshold that unlocks signing (see the pre-commit flowchart in `docs/signer-flows.md` section 5, anchored at `handle_block_pre_commit`). A `BlockAccepted` signature, by contrast, is only supposed to be produced *after* a signer has itself gone through validation and the pre-commit/re-check gauntlet.

However, `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:2443-2466`) contains:
```rust
if signer_address != &self.stacks_address && !self.signer_db.has_committed(block_hash, signer_address)...unwrap_or(false) {
    self.handle_block_pre_commit(stacks_client, sortition_state, signer_address, block_hash);
    return;
}
```
This means: any time this signer receives a valid-looking `BlockAccepted` signature from a peer it hasn't already recorded a pre-commit from, it forwards that peer's address/block-hash pair into the pre-commit-counting path — `add_block_pre_commit` and the associated weight tally — as if that peer had broadcast a pre-commit. This conflates two different message types under the tally used to gate this signer's own decision to sign (`self.handle_block_pre_commit`, `stacks-signer/src/v0/signer.rs` section around 1345-1466, gated by `check_block_against_signer_db_state` and the sibling-conflict guard).

Because this path is reachable simply by broadcasting a `SignerMessage::BlockResponse(BlockAccepted{..})` over StackerDB — the same gossip channel any single signer already legitimately writes to — a signer can inject a "phantom pre-commit" for another already-active-but-different-value case (its own crafted BlockAccepted signature) that this receiver will count toward the pre-commit weight tally for a hash, contributing to `TH >= 70%` in the pre-commit flow, all without the peer having gone through the freshness/asynchronous-validation ordering that legitimate `BlockPreCommit` messages are subject to before being counted (note: pre-commit messages are also validated via `KNOWN`/`STORE` paths, but this fallback skips the "did this signer actually validate=true / pre-commit" state and instead trusts the presence of a recoverable signature alone as proof of willingness).

### Impact Explanation
This does not on its own let a single miner or signer force a false pre-commit threshold, because `is_valid_signer` still authenticates that the signature/pre-commit is from a legitimate reward-cycle signer, and weight is still bounded by that signer's own configured weight — so it does not break the equality by itself under a minority signer. However, it collapses a two-round protocol (pre-commit round to gauge willingness pre-signature, then signature round) into effectively accepting a raw signature as authoritative proof of a pre-commit for weight-tally purposes, meaning **the freshness and gating semantics that `handle_block_pre_commit`'s "known/store/validated" flow provide for pre-commits are bypassed for any peer who skips straight to broadcasting a signature.** This is a genuine analog of the ZeroLend flaw (a state normally reached only through a controlled/gated path being reachable directly, unsupervised, from an unprivileged message), but I could not fully trace whether `handle_block_pre_commit`'s internal state checks (e.g. `valid = true`) would independently reject this re-dispatch when called with only a signature and no recorded validation state for that block — this needs verification against `handle_block_pre_commit`'s full body, which I was unable to read within the given iterations.

### Likelihood Explanation
Reachable by any single participating signer (or gossip relay of an intercepted signature) sending a `BlockAccepted` message before ever broadcasting a `BlockPreCommit` for the same hash — no majority, no other signer's key, and no special access required. However, given the incomplete verification of `handle_block_pre_commit`'s internal validity gate under this path, likelihood of an actual safety-break (vs. a merely confusing but harmless code path) is uncertain.

### Recommendation
Verify (and, if needed, restrict) whether `handle_block_pre_commit`, when invoked from this fallback path with only a signature and no independent local `valid=true` state for the block, can be tallied toward the 70% pre-commit weight threshold. If so, require that this reclassification path only accept the value as a "willingness" signal contingent on the receiving signer's own validation state of the block (not purely on signature recoverability), or remove the automatic re-dispatch and instead require an explicit, distinctly-typed backward-compatible pre-commit equivalent.
