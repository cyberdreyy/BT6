### Title
Unauthorized disclosure of bridge `OutgoingToken` secrets to any authenticated user via `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` - ([File: core/web/bridge_types_controller.go])

### Summary
The `BridgeTypesController.Index` and `Show` handlers are wired in `core/web/router.go` without any role-restricting middleware (only generic session/token authentication), while `presenters.NewBridgeResource` always populates `OutgoingToken` in the JSON response with no redaction. This lets any authenticated user or API-token holder — regardless of assigned role — read every bridge's `outgoingToken` secret.

### Finding Description
In `core/web/router.go`, most mutating bridge routes are role-gated (`auth.RequiresEditRole(bt.Create)`, `auth.RequiresEditRole(bt.Update)`, `auth.RequiresEditRole(bt.Destroy)`), but the read routes are not: [1](#0-0) 
Both are only wrapped by the generic `authv2` group middleware (`auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)`), with no `auth.RequiresEditRole`/`RequiresAdminRole` check, meaning any successfully authenticated session or API token — including a low-privilege "view" role — can call them.

`BridgeTypesController.Index` fetches all bridges (paginated) and converts each to a `presenters.BridgeResource` without stripping the outgoing token: [2](#0-1) 

`BridgeTypesController.Show` does the same for a single named bridge: [3](#0-2) 

The presenter itself always serializes `OutgoingToken` (no `omitempty`, unlike `IncomingToken` which is explicitly commented as "only provided when creating a Bridge"): [4](#0-3) 

The `OutgoingToken` is the secret bearer credential the Chainlink node sends to the external adapter (bridge) in the `Authorization` header on outbound HTTP requests, so its disclosure lets an attacker impersonate the node to that bridge/adapter (potential SECRET_CONFINEMENT violation and lateral compromise of connected external adapters).

Note: unlike `Create`, where `IncomingToken` is intentionally attached only in the response for that single call (`resource.IncomingToken = bta.IncomingToken` at `core/web/bridge_types_controller.go:98-99`), there is no equivalent guard around `OutgoingToken` for `Index`/`Show`.

### Impact Explanation
This matches Chainlink's "secret/key disclosure" bounty impact class: a minimally-privileged authenticated user (e.g., view-only role, or a restricted API token intended only for read access) can enumerate and exfiltrate the `OutgoingToken` for every configured bridge on the node via a single paginated GET request. Since `OutgoingToken` authenticates the node to the external adapter, leaking it lets a low-privileged internal user impersonate the node to that adapter, potentially triggering unauthorized bridge/adapter actions or further compromising connected job-pipeline components.

### Likelihood Explanation
Trivial and fully repeatable: it requires only a valid authenticated session or API token (no elevated role) — the same precondition the audit scenario describes ("minimal view-role session or API token"). A simple `GET /v2/bridge_types?size=25&page=1` or `GET /v2/bridge_types/:BridgeName` returns the tokens in plaintext JSON, with no additional exploitation steps needed.

### Recommendation
- Strip `OutgoingToken` from `BridgeResource` for list/show responses (e.g., add a separate "list" presenter without the field, or only populate it for the `Create`/`Update` response paths analogous to how `IncomingToken` is handled), and/or
- Gate `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` behind `auth.RequiresEditRole` (or a new minimum role appropriate for viewing secrets) in `core/web/router.go`, consistent with how the mutating bridge routes are already protected.

### Proof of Concept
Go handler-level integration test plan (extending `core/web/bridge_types_controller_test.go`):
1. Create a bridge via `app.BridgeORM().CreateBridgeType` with a known `OutgoingToken`.
2. Build an HTTP client authenticated with a session/API token assigned the lowest privilege role (view-only), similar to how `cltest` builds role-scoped clients in other role-boundary tests (e.g., `core/web/auth/auth_test.go`).
3. Call `GET /v2/bridge_types?size=25&page=1` and `GET /v2/bridge_types/:BridgeName` with that client.
4. Assert the response status is `200 OK` (proving no role check blocks the low-privilege user).
5. Parse the JSON:API response into `[]presenters.BridgeResource` / `presenters.BridgeResource` and assert `resource.OutgoingToken` is non-empty and matches the value set at creation — proving the secret is disclosed to a low-privileged account.
6. As a regression guard for the fix, add an assertion that either the route requires `edit`/`admin` role (expect `403`) or that `OutgoingToken` is always empty/omitted in `Index`/`Show` responses.

```go
func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}
```

```go
// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
```
