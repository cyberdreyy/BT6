## Analysis

The external salsa.js report is only usable as a bug-class hint: **an authorizer used to satisfy a threshold check that is not validated against the current set of trusted signers**. Mapped onto this repository's in-scope contracts, the strongest analog is in `multisig2/src/lib.rs` — the confirmation-count vs. live-member binding is broken when a member is removed.

`delete_member` only purges confirmations for requests that were *created* by the removed member (`r.member == member`); it never scans the `confirmations` map to strip the removed member's identifier from *other* pending requests that member had already confirmed: [1](#0-0) 

The confirmation state is keyed only by `member.to_string()` and stored per-request in a `LookupMap<RequestId, HashSet<String>>`, entirely decoupled from the live `members: UnorderedSet<MultisigMember>` set: [2](#0-1) 

`assert_valid_request`, used by both `delete_request` and `confirm`, only checks that the *caller* is currently a member — it never re-validates the members already recorded inside a request's stale confirmation set: [3](#0-2) 

`remove_request`/`add_request` similarly track per-member state via the string identifier without reconciling it against `self.members` at execution time: [4](#0-3) 

### Title
Stale confirmations from removed multisig members count toward the execution threshold - (File: multisig2/src/lib.rs)

### Summary
When a multisig member is removed via `DeleteMember`, only requests *created* by that member are cleaned up. Any confirmation that member previously cast on requests created by *other* members remains in the `confirmations` `HashSet<String>` for those requests. Because `confirm()`'s threshold check counts the size of that stale set rather than re-validating each entry against the current `members` set, a request can reach `num_confirmations` using a signature/account that is no longer part of the multisig.

### Finding Description
The multisig's core security invariant is: a request executes only once at least `num_confirmations` *live* members have approved it. The contract tracks confirmations as a `HashSet<String>` per `RequestId` ( [5](#0-4) ), and members as a separate `UnorderedSet<MultisigMember>` ( [6](#0-5) ).

`delete_member` removes requests *authored* by the deleted member and clears the `num_requests_pk` counter for that member, but it filters on `r.member == member` (the request's *creator*), not on membership inside other requests' `confirmations` sets: [7](#0-6) 

Consequently, if member `B` confirmed request `R1` (created by `A`) before being removed, `R1.confirmations` still contains `B`'s identifier after `B` is deleted. The threshold check in `confirm()` (invoked through `add_request_and_confirm`/`confirm`, gated only by `assert_valid_request`) counts set membership, not live membership, so a subsequent live confirmation from `C` can push the set size to `num_confirmations` and trigger `execute_request`, even though only `A` and `C` are actually live, authorized members at execution time.

This breaks the binding: **confirmations counted == live members who approved**, which the rules identify explicitly as an in-scope custody boundary.

### Impact Explanation
This allows a `MultiSigRequest` — including `Transfer`, `AddKey`/full-access-key grants, `DeployContract`, or arbitrary `FunctionCall` — to execute with fewer live, currently-authorized confirmations than `num_confirmations` requires. This is a "multisig request executed below threshold" condition, rated Critical per the scope's impact categories, and can directly enable unauthorized NEAR transfers or account takeover via `AddKey`.

### Likelihood Explanation
Exploitation requires no privileged access beyond being (or having been) a legitimate multisig member at some point and then being removed through the normal `DeleteMember` governance flow — a routine operational event (e.g., rotating out a departing signer). Any request left pending across a membership change is exposed. No redeploy, foundation action, or victim key compromise is needed; it is triggered purely by the intended `DeleteMember` action interacting with pre-existing pending confirmations.

### Recommendation
When removing a member, iterate all pending requests' `confirmations` sets and strip the removed member's identifier (not just requests they authored), or re-validate every entry in a request's `confirmations` set against the live `members` set at the time `confirm()` checks the threshold (e.g., filter `confirmations.get(&request_id)` through `self.members.contains(...)` before comparing its length to `num_confirmations`).

### Proof of Concept
1. Deploy `MultiSigContract::new([A, B, C, D], 3)`.
2. `A` calls `add_request` to create `R1` (e.g., `Transfer` to an attacker-controlled account).
3. `A` confirms `R1` (`confirmations = {A}`).
4. `B` confirms `R1` (`confirmations = {A, B}`).
5. Members execute a separate confirmed `DeleteMember { member: B }` request (legitimate offboarding) — per `delete_member`, only requests created by `B` are cleaned; `R1.confirmations` still contains `B`.
6. `C` (still live) confirms `R1` → `confirmations.len() == 3 == num_confirmations`, and `execute_request` fires the `Transfer`, even though only `A` and `C` are currently authorized members — `B`'s stale confirmation counted toward the threshold after removal.

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
