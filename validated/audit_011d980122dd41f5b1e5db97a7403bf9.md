### Title
Second withdraw request in a later epoch erases the loss-adjusted price of an earlier receipt, paying a haircutted claim at par - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` looks up the loss recovery price only via `lastWithdrawRequest[_user]`, which stores only the *latest* request epoch (an incorrect "alias" for the full set of outstanding request epochs). When a user has a loss-adjusted receipt from epoch N and then files a new request in epoch M > N, `lastWithdrawRequest` is overwritten to M. Since `lossRecoveryPriceByEpoch[M] == 0`, the loss-adjusted path is skipped, and `_claimFundedWithdrawRequest` pays the aggregate `withdrawsRequests[_user]` — which still includes the haircutted epoch-N basis — at full par. This mirrors CVE-2022-28285: a stale/wrong-slot read (latest-epoch marker instead of per-epoch data) yields an out-of-bounds payout beyond what the receipt is entitled to.

### Finding Description
In `requestWithdraw`, every request adds to both the aggregate `withdrawsRequests[_user]` and per-epoch `withdrawsRequestsByEpoch[_user][currentEpoch]`, and unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` (lines 282–293). When `stopEpoch` funds less than `pendingWithdraws`, `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws`, but does **not** reduce `withdrawsRequests[_user]` (lines 411–430). On claim, `_claimLossAdjustedWithdrawRequest` computes `lossEpoch = lastWithdrawRequest[_user]` and returns early if `lossRecoveryPriceByEpoch[lossEpoch] == 0` (lines 789–795). It never iterates or checks other epochs that may have a haircut. If the user's *latest* request epoch was fully funded, the loss path is skipped entirely; then `_claimFundedWithdrawRequest` (lines 319–349) waits one epoch and pays `amount = withdrawsRequests[_user] + apr0...` at par via `_transferFundedClaim`. Because the epoch-N claimBasis is still inside `withdrawsRequests[_user]`, the user redeems the haircutted portion at 100%.

### Impact Explanation
Direct theft / insolvency. A user whose epoch-N receipt was haircut by `stopEpochWithDuration(_lossAmount)` (recovery price < `RECOVERY_FULL`) recovers the haircut portion `(1 - lossRecoveryPrice) * claimBasis` from the strategy's funded-claim underlyings. Those underlyings back *other* claimants' funded receipts and post-default reserves, so the last claimants are left undercollateralized — the vault pays out more than it collected from the borrower for that epoch, breaking the "one receipt, one loss-adjusted payout" invariant. `_transferFundedClaim`'s reserve guard (lines 899–905) only protects `defaultRecoveryReserve`, not ordinary funded underlyings, so it does not stop this.

### Likelihood Explanation
Fully attacker-driven with only unprivileged actions: deposit AA/BB, `requestWithdraw` in epoch N (honest manager stops with `_lossAmount > 0`, which happens whenever the borrower underpays), then `requestWithdraw` again in epoch M, wait one epoch, and call `claimWithdrawRequest`. The only external precondition is a loss-adjusted epoch, which is an intended protocol path. No privileged misbehavior required.

### Recommendation
Track loss-adjusted claim basis per epoch instead of keying off `lastWithdrawRequest`. Either (a) iterate/record the set of epochs with `lossRecoveryPriceByEpoch` entries per user (e.g., store `lossEpochByUser` or move haircutted basis into a separate `lossAdjustedRequests[_user]` bucket with its price), or (b) subtract the haircutted basis from `withdrawsRequests[_user]` inside `collectWithdrawFunds` and pay epoch-N claims strictly through `_claimLossAdjustedWithdrawRequest`. At minimum, `_claimLossAdjustedWithdrawRequest` should check `withdrawsRequestsByEpoch[_user][e]` for every epoch `e` with a nonzero `lossRecoveryPriceByEpoch`, not just `lastWithdrawRequest[_user]`.

### Proof of Concept
Foundry fork test (pattern follows `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossAdjustedReceiptPaidAtPar() external {
    // Epoch N: user deposits and requests withdraw of 1000e6 AA
    uint256 amount = 1000 * ONE_SCALE;
    _depositWithUser(user, amount, true);
    _startEpochAndCheckPrices(0);
    vm.prank(user);
    uint256 req = cdoEpoch.requestWithdraw(0, address(AAtranche)); // epoch N request

    // Honest manager stops epoch N with a 20% loss via stopEpochWithDuration
    // borrower repays only 80% of pendingWithdraws -> lossRecoveryPriceByEpoch[N] = 0.8e18
    deal(defaultUnderlying, borrower, partialFunds);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, epochDuration, lossAmount);

    // Epoch M: user files a second (dust) withdraw request -> lastWithdrawRequest = M
    vm.prank(manager);
    cdoEpoch.startEpoch();
    _depositWithUser(user, 1 * ONE_SCALE, true);   // fresh tranche tokens
    vm.prank(user);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // epoch M = N+1 request

    // Epoch M ends fully funded (no loss): lossRecoveryPriceByEpoch[M] == 0
    deal(defaultUnderlying, borrower, fullFunds);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(apr, 0);

    // Claim: loss path skipped (price[M]==0), funded path pays aggregate at par
    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(user) - balPre;

    // Epoch-N receipt should have paid req * 0.8; assert it paid req * 1.0
    assertGt(paid, req * 8 / 10);          // got more than haircutted value
    assertEq(paid, req + dustReq);         // full par payout incl. haircutted basis
}
```

Expected: `paid` equals the unhaircutted aggregate, i.e., the user extracts the ~20% haircut that should have been socialized, draining underlyings reserved for other claimants.
