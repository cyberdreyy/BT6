### Title
Unprivileged dust instant-withdraw requests repeatedly block `stopEpoch`, indefinitely delaying epoch close and all LP withdrawals - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`_stopEpoch` reverts whenever `_pendingInstant() != 0` (contracts/IdleCDOEpochVariant.sol:345). Any unprivileged tranche holder can submit an instant-withdraw request for a dust amount, forcing the honest owner/manager's `stopEpoch`/`stopEpochWithDuration` transaction to revert. Because the request can be re-submitted (mempool frontrunning) after each `getInstantWithdrawFunds` cleanup, the epoch cannot be closed and every queued withdraw request, tranche redemption and interest settlement is frozen for as long as the attacker keeps griefing — the smart-contract analog of the kernel's uninterruptible, user-extended wait.

### Finding Description
The epoch-close path enforces a strict "no pending instant withdraws" precondition:

- `_stopEpoch` (contracts/IdleCDOEpochVariant.sol:330-351) reverts via `_checkNotAllowed` when `_pendingInstant() != 0`, alongside the checks that the epoch is running and `block.timestamp >= epochEndDate`.
- Pending instant requests can only be drained by the manager calling `getInstantWithdrawFunds` (contracts/IdleCDOEpochVariant.sol:558-570), which is allowed once `block.timestamp >= instantWithdrawDeadline`, pulls the pending amount from the borrower and calls `IdleCreditVault.collectInstantWithdrawFunds`.

Between `getInstantWithdrawFunds` and the subsequent `stopEpoch`, an attacker can insert a new instant-withdraw request (`requestInstantWithdraw` on the vault/CDO, whose fulfillment is later claimed via `claimInstantWithdrawRequest`, exercised in test/foundry/IdleCreditVault.t.sol:5456). `pendingInstantWithdraws` becomes non-zero again and `stopEpoch` reverts. There is no minimum-request size or per-epoch request cutoff after `instantWithdrawDeadline` visible in the CDO gating — the deadline only gates when the *manager* may fund pending requests, not when users may *create* them — so the loop is repeatable each time the manager retries:

1. Epoch running, `epochEndDate` reached.
2. Manager calls `getInstantWithdrawFunds` → pending drained, `allowInstantWithdraw = true`.
3. Attacker (any KYC'd lender holding tranche tokens) submits a 1-wei instant-withdraw request → `_pendingInstant() > 0`.
4. Manager's `stopEpoch`/`stopEpochWithDuration` reverts (`NotAllowed`).
5. Repeat from step 2 each retry; each cycle costs the attacker only gas plus dust temporarily locked, while the whole pool stays open.

`stopEpochWithDuration` (contracts/IdleCDOEpochVariant.sol:520-530) and the orchestrator batch path `IdleCreditVaultManagerOrchestrator.stopEpochWithDuration` (contracts/IdleCreditVaultManagerOrchestrator.sol:96) hit the same revert. No existing guard stops this: the skim, default handling, and `_checkOnlyOwnerOrManager` gates are orthogonal; the attacker is unprivileged and needs no role.

### Impact Explanation
Temporary freezing of all pool funds with quantified impact: while the epoch cannot be stopped, `isEpochRunning` stays true, `epochEndDate`/duration are never reset, and no withdraw request can be claimed (claims are only processed for stopped epochs), no interest is accrued into tranche prices, and `depositAA/BB` during the buffer period cannot proceed. The freeze lasts as long as the attacker repeats step 3 — arbitrarily extensible at near-zero marginal cost, locking 100% of pool TVL for the griefed duration. This matches the accepted "temporary freezing with quantified loss" class (denial of withdrawal is a direct fund-availability impact, not a gas-DoS-only issue).

### Likelihood Explanation
Requires only an unprivileged tranche-token holder (a KYC-passing lender qualifies) willing to spend gas and a dust-sized request per griefing cycle. No privileged misbehavior, no oracle dependency, no timing race beyond ordinary mempool ordering of two manager calls that are already separate transactions. The protocol mitigations (manager can bundle funding + stop, or close-pool via `_interest == 1` which sets `disableInstantWithdraw`) are operational workarounds, not code-level preventions: close-pool recalls all principal and is a heavy action, and atomic bundling still loses to a persistent frontrunner inside the same block window.

### Recommendation
Cap or gate instant-withdraw requests so they cannot be created after `instantWithdrawDeadline` (or after the manager has called `getInstantWithdrawFunds` for the epoch), e.g. set a flag such as `instantRequestsClosed` inside `getInstantWithdrawFunds` and reject new requests while it is set. Alternatively, introduce a minimum instant-withdraw amount and/or let `stopEpoch` treat dust pending amounts below the minimum as zero, so griefing cost scales with real capital.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.17;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

/// Attacker keeps _pendingInstant() != 0 so stopEpoch always reverts.
contract StopEpochGriefPoC is Test {
    IdleCDOEpochVariant cdo;
    IdleCreditVault strategy;
    IERC20Detailed underlying;
    IERC20Detailed aaTranche;
    address manager = address(0xMGR);
    address borrower = address(0xBRW);
    address attacker = address(0xBAD);

    function test_dustInstantRequestBlocksStopEpoch() public {
        // --- setup: attacker deposits into AA tranche, epoch is started ---
        deal(address(underlying), attacker, 1e6);
        vm.startPrank(attacker);
        underlying.approve(address(cdo), 1e6);
        cdo.depositAA(1e6);
        vm.stopPrank();

        vm.prank(manager);
        cdo.startEpoch();

        // warp past epoch end
        vm.warp(cdo.epochEndDate() + 1);

        // --- griefing loop ---
        for (uint256 i; i < 3; ++i) {
            // attacker submits a dust instant-withdraw request
            vm.prank(attacker);
            cdo.requestInstantWithdraw(1, address(aaTranche)); // 1 wei tranche
            assertGt(strategy.pendingInstantWithdraws(), 0);

            // manager drains pending instant requests (borrower funded)
            deal(address(underlying), borrower, 1);
            vm.prank(borrower);
            underlying.approve(address(cdo), 1);
            vm.prank(manager);
            cdo.getInstantWithdrawFunds();
            assertEq(strategy.pendingInstantWithdraws(), 0);

            // attacker frontruns stopEpoch with another dust request
            vm.prank(attacker);
            cdo.requestInstantWithdraw(1, address(aaTranche));

            // stopEpoch reverts: epoch cannot close
            vm.expectRevert(); // NotAllowed
            vm.prank(manager);
            cdo.stopEpoch(0, 0);

            assertTrue(cdo.isEpochRunning(), "epoch still open");
        }

        // attacker repeats indefinitely; all LP withdrawals remain frozen
        // while attacker spent only ~3 wei of tranche + gas.
    }
}
```
