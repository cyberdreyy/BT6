### Title
Durable-nonce transactions lack any chain/fork-binding domain separator, enabling cross-fork replay of fund transfers - (File: `programs/system/src/system_instruction.rs`, `svm/src/transaction_processor.rs`, `runtime/src/bank/check_transactions.rs`)

### Summary
The bug class in the report is "no domain separator (EIP-712/chain-id) in a signed payload whose relay is permissionless, so the same signed message can be replayed on a second, forked chain and misdirect funds." Agave's durable-nonce transaction mechanism has the same structural weakness: a nonce transaction's signed message commits only to a `nonce_address`/`durable_nonce` hash value and instruction data — never to a genesis hash, cluster identifier, or fork epoch. Since transaction submission and forwarding is permissionless (RPC `sendTransaction`, gossip/TPU relay), any observer can rebroadcast a captured, still-valid nonce transaction onto a different persistent chain instance (e.g., a minority fork that continues independently, or a network that is restarted/rolled back from a shared snapshot) as long as that instance's copy of the referenced nonce account still shows the pre-advance `durable_nonce` value.

### Finding Description
Nonce validity is checked purely by matching the account's stored `durable_nonce` (itself just `hash(blockhash)`) against the transaction's `recent_blockhash` field — with no chain identity mixed in: [1](#0-0) [2](#0-1) 

The bank-level nonce validity check (`check_nonce_transaction_validity` / `load_message_nonce_data`) similarly only compares `message.recent_blockhash()` against the account's stored nonce hash, again with nothing binding the message to a specific ledger/fork/genesis instance: [3](#0-2) 

The blockhash queue (and therefore the whole "recent blockhash" replay-protection design) is seeded once from `genesis_config.hash()` at bank creation, but that genesis hash is never incorporated into the bytes a user signs — it only gates which values the *validator* accepts as fresh, not what the *signer* committed to: [4](#0-3) 

Because a Solana transaction's signed message is `(recent_blockhash/nonce_hash, instructions, accounts)` with no chain-id/genesis-hash/fork-epoch analog to EIP-155's chain ID, and because durable-nonce transactions are explicitly designed to remain valid indefinitely (that's the whole point of the "durable" nonce, mirroring the long-lived merkle-tree distributions in the original report), a transaction signed once is valid on *any* ledger instance that happens to (a) share the same nonce account state and (b) accept the referenced nonce value. Both conditions are trivially satisfied across a chain fork or a network restart from a common snapshot, since both branches start from bit-identical account state, including the nonce account's `durable_nonce`.

### Impact Explanation
If a network experiences a fork that persists (minority fork continuing to produce blocks, or an operational restart from a shared snapshot creating two live instances of the same ledger state, both of which have occurred historically on Solana-family networks), an attacker who observes a durable-nonce transaction being submitted/confirmed on one instance can immediately resubmit the identical signed transaction bytes to the other instance via RPC `sendTransaction`, since:
- Anyone may submit/relay any validly signed transaction (msg.sender-independent, same as `withdraw()` in the original report),
- The nonce account state (and thus its accepted `durable_nonce`) is identical on both instances until one of them independently advances it,
- No signed field commits the transaction to one specific chain instance.

This results in the same fund transfer / instruction executing twice — once on each fork/instance — which is a concrete unauthorized state mutation (double-spend/double-execution) analogous to the original "funds go to destination regardless" cross-chain replay.

### Likelihood Explanation
Requires an actual, persistent chain fork or snapshot-based restart producing two independently live ledgers sharing prior state — this is an operational/consensus-level event rather than something an attacker can trigger unilaterally, so likelihood is low-to-moderate and tied to how often such fork/restart events occur. When they do occur, exploitation is trivial (simple RPC replay, no privileged access needed), which is exactly the risk profile flagged as "acknowledged, disagreed with severity" in the original report for the same reason (key/txn portability across chain splits is an inherent property of chains without domain separation).

### Recommendation
Add an explicit chain-binding field into the transaction message hash — akin to EIP-155/EIP-712 domain separation — such as mixing the immutable genesis hash (or a monotonically-increasing hard-fork/restart epoch) into `DurableNonce::from_blockhash`/`verify_nonce_account`, and rejecting nonce/blockhash validity checks in `svm/src/transaction_processor.rs::validate_transaction_nonce` and `runtime/src/bank/check_transactions.rs::check_nonce_transaction_validity` whenever the embedded chain identifier doesn't match the executing bank's genesis hash.

### Proof of Concept
1. Network state `S` forks into instance `A` and instance `B`, both sharing identical account state including a durable-nonce account `N` with `durable_nonce = h0`.
2. A user signs a durable-nonce transaction `T` referencing `N` and `recent_blockhash = h0`, intending it for instance `A` only, and submits it there; it executes and advances `N.durable_nonce` on `A`.
3. Before `T` is observed to also have (or before it can) land on `B`, an attacker who watched `A`'s mempool/ledger resubmits the identical signed bytes of `T` to instance `B`'s RPC `sendTransaction`.
4. Because `B`'s copy of `N` still has `durable_nonce = h0` (unchanged, since `B` diverged before `T` landed), `validate_transaction_nonce` (`svm/src/transaction_processor.rs:833-892`) and `verify_nonce_account` accept `T` as valid on `B` too, executing the same instructions and moving the same funds a second time on the other chain instance — with no signature or message field having ever bound `T` to instance `A` specifically.

    pub(super) fn check_nonce_transaction_validity(
        &self,
        message: &impl SVMMessage,
        next_durable_nonce: &DurableNonce,
        strict_nonce_size_check: bool,
        strict_nonce_authority_check: bool,
    ) -> Option<(Pubkey, u64)> {
        let nonce_is_advanceable = message.recent_blockhash() != next_durable_nonce.as_hash();
        if !nonce_is_advanceable {
            return None;
        }

        let (nonce_address, nonce_data) =
            self.load_message_nonce_data(message, strict_nonce_size_check)?;

        if strict_nonce_authority_check

                .any(|signer| signer == &nonce_data.authority)
        {
            return None;
        }

        let previous_lamports_per_signature = nonce_data.get_lamports_per_signature();

        Some((nonce_address, previous_lamports_per_signature))
    }

    pub(super) fn load_message_nonce_data(
        &self,
        message: &impl SVMMessage,
        strict_nonce_size_check: bool,
    ) -> Option<(Pubkey, NonceData)> {
        let nonce_address = message.get_durable_nonce()?;
        let nonce_account = self.get_account_with_fixed_root(nonce_address)?;
        if strict_nonce_size_check && nonce_account.data().len() != NonceState::size() {
            return None;
        }
        let nonce_data =
            nonce_account::verify_nonce_account(&nonce_account, message.recent_blockhash())?;

        Some((*nonce_address, nonce_data))
    }
