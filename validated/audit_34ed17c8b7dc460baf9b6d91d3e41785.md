### Title
Attacker-controlled `messageId` in `HandleLegacyUserMessage`/`sendHTTPMessageToClient` correlation map allows cross-user response hijacking - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The gateway's capabilities handler correlates DON-node responses back to the originating user solely by the client-supplied `messageId` (JSON-RPC `id`), stored in the shared `h.savedCallbacks` map with no per-sender scoping or server-side uniqueness enforcement. Any unprivileged signer can submit a request reusing a victim's in-flight `messageId`, overwriting the map entry so that the victim's DON response is delivered to the attacker's callback instead.

### Finding Description
`gateway.ProcessRequest` decodes the JSON-RPC request and, for legacy requests, sets `msg.Body.MessageId` directly from the caller-supplied `id` field [1](#0-0) , and no code path re-derives or namespaces this id by sender before it reaches the handler.

In `handler.HandleLegacyUserMessage`, the callback used to deliver the eventual response to the HTTP caller is stored keyed purely by this attacker-controlled id: [2](#0-1) 
This is a plain map assignment — if a second, unrelated request arrives with the same `messageId` (e.g. from a different signer/sender), it silently overwrites the first entry.

When a DON node later responds with `MethodWebAPITrigger`, the response is matched back to a saved callback using only the `messageId`, with no sender/session binding to the original requester: [3](#0-2) 
The response payload (`msg`) is whatever the DON node returned for the *original* (victim) request, but it is delivered via `savedCb.SendResponse`, where `savedCb` is now whichever callback last wrote to that map key.

Exploit flow:
1. Victim signs and submits a `web_api_trigger` request with `messageId = "X"`. It's saved as `savedCallbacks["X"] -> victimCallback` and fanned out to all DON members.
2. Before the DON responds, attacker (any address with a valid EOA key, no special privilege) submits their own signed request also using `messageId = "X"`. Because the store is a bare map write, `savedCallbacks["X"]` is overwritten to `attackerCallback`.
3. When a DON node responds to the *victim's* original request (still tagged `messageId = "X"`), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds the attacker's callback, deletes the entry, and sends the victim's response body to the attacker's HTTP connection.
4. The message signature checks (`common.ValidatedMessageFromResp`/`Message.Validate`) only verify that the *node* response is properly signed by a DON member — they do not verify that the response is being routed to the sender who actually issued the original request. Signature checks on the inbound user message likewise only bind `Sender` to that individual request; they never gate the `savedCallbacks` map key uniqueness or ownership.

Thus the "invariant that request ids must be server-generated or sender-scoped" is violated: the id is fully attacker-chosen and globally scoped across all users hitting the same DON handler instance.

### Impact Explanation
This is cross-user response confusion: an attacker can hijack another user's in-flight `web_api_trigger`/`web_api_target`/`compute_action`/`workflow_syncer` response by colliding on `messageId`. Whatever data the DON node returns for the victim's request (headers, body, potentially secrets or authorization-bearing data returned by the target endpoint/capability) is redirected to the attacker instead of the victim. Depending on which capability/workflow is being triggered, this could disclose sensitive response data intended only for the victim, matching the "cross-user response confusion" / unauthorized disclosure impact class called out in the rules. Note: this specific file (`capabilities/handler.go`) does not itself handle vault/DKG secret material — that claim in the prompt's "Expected Immunefi impact" is not substantiated by this code; the concretely provable impact here is response-hijacking/cross-user data disclosure on the web-API capabilities gateway path, not vault key disclosure.

### Likelihood Explanation
Preconditions: attacker needs only the ability to sign gateway requests with any ECDSA key (no operator/admin/DON privilege) and needs to win a race — submitting a colliding `messageId` after the victim's request is saved but before the DON node's response is processed. Since `CallbackMaxAgeSec` defaults to 120 seconds [4](#0-3) , there is a multi-second-to-minutes window in which collision is feasible, especially if the attacker can predict or observe likely `messageId` values (e.g., sequential/predictable IDs, or by targeting a known workflow that reuses deterministic ids). This is repeatable and requires no special network position, just correctly timed HTTP calls to the public gateway endpoint.

### Recommendation
Do not use the raw client-supplied `messageId` as the sole map key for callback correlation. Either:
- Generate a server-side unique correlation id at message-intake time and map it 1:1 to the client's id + sender address, or
- Key `savedCallbacks` by a composite of `(sender, messageId)` and reject/queue (rather than silently overwrite) collisions on the same key, or
- Detect an existing entry in `h.savedCallbacks` for the same key before insertion and return an error to the second submitter instead of overwriting.

### Proof of Concept
Go handler-level test plan (in `core/services/gateway/handlers/capabilities`):
1. Construct `handler` via `NewHandler` with a mock `don` and `httpClient`.
2. Create two distinct `handlers.Callback` mocks/fakes, `victimCB` and `attackerCB`, each recording the `UserCallbackPayload` it receives.
3. Call `h.HandleLegacyUserMessage(ctx, victimMsg, victimCB)` where `victimMsg.Body.MessageId = "X"`, signed by victim's key. Assert `h.savedCallbacks["X"].Callback == victimCB`.
4. Before simulating the DON's response, call `h.HandleLegacyUserMessage(ctx, attackerMsg, attackerCB)` with `attackerMsg.Body.MessageId = "X"` (same id), signed by attacker's key. Assert `h.savedCallbacks["X"].Callback` is now `attackerCB` (overwritten).
5. Simulate DON node response to the *victim's* request: build a JSON-RPC response with `ID = "X"`, method `MethodWebAPITrigger`, and a payload containing victim-specific sensitive content; call `h.HandleNodeMessage(ctx, resp, nodeAddr)`.
6. Assert `attackerCB` received the victim's response payload (`RawResponse` contains victim's data) and `victimCB` received nothing — demonstrating the response was misdirected to the attacker.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
