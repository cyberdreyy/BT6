### Title
`solveRequestsDirect` omits the `solvingNotPaused` token gate enforced on all other user-facing paths, letting any caller solve async deposit/redeem requests while solving is paused for a token - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`deposit`, `mint`, `redeem`, `withdraw`, and the authorized `solveRequestsVault` all carry the `solvingNotPaused(token)` modifier, which queries the external `ISolvingGate.paused(provisioner, token)` to determine whether solving should be blocked for a given token <cite repo="Thankgod67Ikhide/aera-contracts-public--015" path="v3/src/core/ProvisionerV2.sol" start="141="146" /><cite repo="Thankgod67Ikhide/aera-contracts-public--015" path="v3/src/core/ProvisionerV2.sol" start="170="176" /><cite repo="Thankgod67Ikhide/aera-contracts-public--015" path="v3/src/core/ProvisionerV2.sol" start="386="391" />. The permissionless `solveRequestsDirect` function, callable by "anyone willing to pay units/tokens" per its own docstring, checks only `PRICE_FEE_CALCULATOR.isVaultPaused(...)` and never calls `_checkSolvingNotPaused`/carries the `solvingNotPaused` modifier <cite repo="Thankgod67Ikhide/aera-contracts-public--015" path="v3/src/core/ProvisionerV2.sol" start="411="435" />. This is structurally the same "guard applied to the admin/managed entry point but missing on an alternate, publicly reachable entry point" pattern as CVE-2017-18870 (Mattermost's `EnableOnlyAdminIntegrations` restriction being mishandled for one integration-creation code path but not another).

### Finding Description
`ProvisionerV2` defines the `solvingNotPaused(IERC20 token)` modifier specifically to let an `ISolvingGate` implementation pause deposit/redeem solving per-token for compliance, risk, or oracle-integrity reasons <cite repo="Thankgod67Ikhide/aera-contracts-public--015" path="v3/src/core/interfaces/ISolvingGate.sol" start="6="16" />. This modifier is applied to every synchronous entry point (`deposit`, `mint`, `redeem`, `withdraw`) and to the guardian/solver-gated `solveRequestsVault` <cite repo="Thankgod67Ikhide/aera-contracts-public--015" path="v3/src/core/ProvisionerV2.sol" start="386="391" />. However `solveRequestsDirect`, which is fully permissionless (only `nonReentrant`, no `requiresAuth`, no `solvingNotPaused`) and is explicitly documented as usable by "anyone willing to pay units (for deposits) or tokens (for redeems), pocketing the solver tip" <cite repo="Thankgod67Ikhide/aera-contracts-public--015" path="v3/src/core/ProvisionerV2.sol" start="31="37" />, replaces the token-specific solving-gate check with an unrelated, coarser check — whether the whole vault is paused in the `PriceAndFeeCalculator` <cite repo="Thankgod67Ikhide/aera-contracts-public--015" path="v3/src/core/ProvisionerV2.sol" start="411="415" />. Any ordinary user can therefore continue directly solving outstanding async deposit/redeem requests for a token that has been explicitly paused via the solving gate, as long as the vault itself is not globally paused.

### Impact Explanation
If the solving gate is used to pause solving for a specific token (e.g., due to a suspected bad price feed, sanctioned counterparty, or an in-flight incident requiring a freeze on conversions for that token), `solveRequestsDirect` provides an unguarded bypass that lets any user still force through fixed-price async deposit/redeem solves for that token, continuing to mint/burn vault units and move tokens at the (now-untrusted or restricted) fixed price. This can result in real value extraction/mispricing for the vault and its depositors during the exact window the gate was meant to freeze — matching the "temporary freeze that can be bypassed" class of Medium severity issues.

### Likelihood Explanation
No privileged or colluding role is required; the trigger is simply having the solving gate configured to pause a token (a normal, expected operational action by the owner/guardian) and then any ordinary user calling the already-public `solveRequestsDirect` with a valid, previously-submitted fixed-price request hash. This is a straightforward call sequence with standard user inputs (`token`, `requests[]`), with no special preconditions beyond an outstanding async request and an active gate pause.

### Recommendation
Add the `solvingNotPaused(token)` modifier (or an equivalent internal `_checkSolvingNotPaused(token)` call) to `solveRequestsDirect`, mirroring `solveRequestsVault`, so the solving-gate pause is enforced consistently across all paths that can execute a solve.

### Proof of Concept
1. Deploy `ProvisionerV2` with `solvingGateEnabled = true` and set an `ISolvingGate` implementation whose `paused(provisioner, token)` returns `true` for a target token.
2. As an ordinary user, call `requestDeposit`/`requestRedeem` for that token to create a valid fixed-price async request hash (unaffected by the gate, since request creation isn't gated).
3. Assert that calling `deposit`/`mint`/`redeem`/`withdraw` for that token reverts (gate enforced), and that `solveRequestsVault` also reverts when attempted by an authorized solver.
4. As the same ordinary user (no special role), call `solveRequestsDirect(token, [request])`.
5. Assert the call succeeds — units are minted/burned and tokens move — despite the gate reporting `paused == true`, demonstrating the bypass of the intended freeze.
