### Title
Unredacted `RelayConfig`/`OnchainSigningStrategy` passthrough in job presenters discloses embedded RPC API keys to any authenticated view-role user - ([File: core/web/presenters/job.go])

### Summary
`NewOffChainReporting2Spec` copies `spec.RelayConfig` (`job.JSONConfig`, a `map[string]any`) verbatim into the JSON-serialized `OffChainReporting2Spec.RelayConfig` field with no redaction, and `GET /v2/jobs/:ID` (`JobsController.Show`) is reachable by any authenticated user regardless of role (only `auth.Authenticate` with `AuthenticateByToken`/`AuthenticateBySession`, no `RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole` wrapper). Because `relayConfig` is a free-form TOML/JSON blob commonly containing `nodeURL`/`chainID` and other chain-adapter-specific fields, any node URL with an embedded API key that an admin/edit-role user placed in the job's `relayConfig` will be echoed back unredacted to a low-privileged view-role caller.

### Finding Description
- `OCR2OracleSpec.RelayConfig` is declared as `JSONConfig` (`map[string]any`) at [1](#0-0)  and is chain-specific config that legitimately contains `nodeURL`/RPC connection strings for relayers (see EVM relay config usage patterns), not vetted or scrubbed by the ORM at creation time beyond specific known keys (`sendingKeys`, `chainID`) as seen in [2](#0-1) .
- `NewOffChainReporting2Spec` passes `spec.RelayConfig` straight through into the presenter struct with no filtering/redaction: [3](#0-2) .
- The presenter's `RelayConfig` field is tagged for direct JSON serialization: [4](#0-3) .
- `JobsController.Show` builds this presenter from the DB-loaded job and returns it as-is: [5](#0-4) .
- The route is registered with only generic session/token authentication, no role check: `authv2.GET("/jobs/:ID", jc.Show)` at [6](#0-5) , in contrast to sibling routes like `POST /jobs` and `PUT/DELETE /jobs/:ID` which are wrapped in `auth.RequiresEditRole`. The GraphQL `OCR2Spec.relayConfig` resolver exhibits the identical unredacted passthrough, confirmed by the test fixture at [7](#0-6)  and [8](#0-7) , which returns the raw `relayConfig` map contents to any authenticated GraphQL caller.
- No redaction logic (e.g., scrubbing keys named `nodeURL`, stripping query-string credentials) exists anywhere in `presenters/job.go` or the resolver for `RelayConfig`/`OnchainSigningStrategy`, unlike secret fields elsewhere in the codebase that are explicitly marked (e.g., `EncryptedOCRKeyBundleID`).

### Impact Explanation
An unprivileged/"view"-role authenticated node API user (holding only a read-only session or API token, with no edit/run/admin capability) can `GET /v2/jobs/:ID` for any OCR2 job on the node and retrieve the full `relayConfig` object exactly as an operator configured it. If the operator's relayer configuration embeds an RPC URL with an API key/secret query parameter (a common real-world pattern for dedicated RPC providers), that credential is disclosed to a party who should have no access to node secrets. The disclosed key could be reused externally to query the operator's dedicated RPC endpoint, consuming quota or incurring cost outside the node — a credential/secret disclosure matching Chainlink's "sensitive data exposure" bounty class, scoped to configuration-embedded credentials rather than node keys.

### Likelihood Explanation
Feasibility is high and requires only a valid view-role (or any authenticated) session/API token and knowledge of an existing OCR2 job ID — no admin/edit privilege is needed. Whether this is exploitable in practice on a given node depends entirely on whether the operator chose to embed a raw secret directly inside `relayConfig` (as opposed to using a keystore/config-file-only mechanism); the code enables it but does not require operators to put secrets there. This is a repeatable, deterministic disclosure once such a job exists — every `Show`/GraphQL query returns the same unredacted data.

### Recommendation
Add explicit redaction in `NewOffChainReporting2Spec` (and the equivalent GraphQL `OCR2Spec` resolver path) before serializing `RelayConfig`/`OnchainSigningStrategy`: strip or mask values for well-known sensitive keys (e.g., `nodeURL`, any key containing `url`, `apiKey`, `token`, `secret`) and strip query-string credentials from any URL-shaped string values. Alternatively/additionally, gate `GET /v2/jobs/:ID` and the job list/spec GraphQL fields behind a minimum role higher than view-only, or move RPC credentials out of `relayConfig` entirely into a secrets store never surfaced by presenters.

### Proof of Concept
Go handler-level integration test plan (extending `core/web/jobs_controller_test.go` patterns):
1. Create an OCR2 job with `job.OCR2OracleSpec.RelayConfig = job.JSONConfig{"chainID": "1", "nodeURL": "https://rpc.example.com/v3/?apiKey=SUPERSECRET123"}`.
2. Authenticate as a session/token user assigned only the view role (lowest privilege that can still hit `GET /jobs/:ID`, since the route has no role check).
3. Call `GET /v2/jobs/:ID` against the test app.
4. Assert HTTP 200 and that the response body's `data.attributes.offChainReporting2OracleSpec.relayConfig.nodeURL` equals the raw unredacted string containing `SUPERSECRET123` — demonstrating the leak (test should currently pass, proving the vulnerability; after the fix, assert the substring `SUPERSECRET123` is absent/masked).
5. Repeat via the GraphQL `job(id) { spec { ... on OCR2Spec { relayConfig } } }` query to confirm the same passthrough in `core/web/resolver/spec.go`.
