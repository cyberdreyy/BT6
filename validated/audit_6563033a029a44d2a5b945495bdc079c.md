The `MessageId` (`req.ID`) is taken directly from the JSON-RPC request submitted by the client and is not enforced to be unique or generated server-side [1](#0-0) . `HandleLegacyUserMessage` blindly stores `callback` under `h.savedCallbacks[msg.Body.MessageId]` without checking for an existing entry, so a duplicate `MessageId` silently overwrites the prior saved callback under the same mutex [2](#0-1) . When a node responds, `handleWebAPITriggerMessage` looks up and deletes by `MessageId` and delivers the response to whichever callback is currently stored — the second (overwriting) request's callback — while the first caller's callback is silently dropped and never invoked [3](#0-2) .

### Title
Duplicate `MessageId` in legacy webapi trigger requests causes callback overwrite and cross-user response misdelivery - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` stores each incoming legacy trigger request's callback keyed only by the client-supplied `msg.Body.MessageId`, with no uniqueness check. An unprivileged client that submits two HTTP requests with the same `MessageId` in quick succession causes the second call to overwrite the first's saved callback, so the first request's caller never gets a response, and the eventual node response is delivered to the second caller's callback — potentially returning the wrong original request's response context (a cross-request/cross-caller response confusion).

### Finding Description
`HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go:341-421) parses an incoming `api.Message` whose `Body.MessageId` originates unmodified from the untrusted JSON-RPC request ID set in `ValidatedMessageFromReq` (core/services/gateway/handlers/common/message_util.go:46-53) — there is no server-side generation or uniqueness enforcement of this ID. After validating payload/timestamp/method, the handler does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
```
(core/services/gateway/handlers/capabilities/handler.go:411-414). There is no check for `_, exists := h.savedCallbacks[id]` before writing, so a second request with the same `MessageId` unconditionally replaces the map entry — losing the reference to the first caller's `handlers.Callback`.

Later, when any DON member responds, `handleWebAPITriggerMessage` (handler.go:148-161) looks up and deletes by `MessageId` and sends the response to whatever `savedCallback` is currently stored — which is now the second requester's callback, not the first's. The first caller's HTTP request will simply hang/timeout with no response ever delivered to it, while the second caller receives a node response that was actually triggered by (and addressed to) the first caller's original request/payload (since DON nodes were sent the first request's `req` to all `donConfig.Members`, and any subsequent responses tied to that message ID get routed to the second, overwriting caller).

No authentication, uniqueness, or ownership check exists to prevent this: the only preconditions are the ability to send two HTTP webapi trigger requests with an attacker-chosen `MessageId`, which is available to any unprivileged/unauthenticated caller of the gateway's legacy webapi trigger endpoint.

### Impact Explanation
This causes cross-request/cross-user response confusion: one caller's request never receives a response (denial of service against that specific caller) while another caller silently receives node response payload that was not the result of their own request. This matches the "cross-user response confusion" bounty impact class, and can be a source of information leakage or state corruption if the trigger payload/params differ meaningfully between the two colliding requests (e.g., different topics/workflows), since the second caller ends up correlated with the first's triggered execution.

### Likelihood Explanation
Trivial and fully attacker-controlled: an unauthenticated/unprivileged HTTP caller of the legacy webapi trigger endpoint chooses their own `MessageId` value (it is simply the JSON-RPC request `ID`), and can send two requests with an identical ID back-to-back. No signature exception, allowlist, or rate limit currently guards against ID collision (the `// TODO: apply allowlist and rate-limiting here` comment at handler.go:384 confirms rate-limiting/allowlisting isn't yet applied here). This is fully reproducible with a simple unit test.

### Recommendation
In `HandleLegacyUserMessage`, before storing the callback, check whether `msg.Body.MessageId` already exists in `h.savedCallbacks` under the lock; if it does, reject the new request with an appropriate JSON-RPC error (e.g., a "duplicate message ID" error response) instead of silently overwriting the existing entry.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` via `NewHandler` with a mock `handlers.DON`.
2. Create two mock `handlers.Callback` instances, `callback1` and `callback2`, each recording whether `SendResponse` was called and with what payload.
3. Build two valid signed `api.Message` values with identical `Body.MessageId` (e.g., `"dup-id"`) but distinguishable payload content (e.g., different `Topics`/`TriggerEventId`), and identical `Method: MethodWebAPITrigger`.
4. Call `h.HandleLegacyUserMessage(ctx, msg1, callback1)` then `h.HandleLegacyUserMessage(ctx, msg2, callback2)`.
5. Assert `h.savedCallbacks["dup-id"]` now references `callback2`, not `callback1`.
6. Simulate a node response for `MessageId: "dup-id"` by calling `h.handleWebAPITriggerMessage(ctx, nodeRespMsg, nodeAddr)`.
7. Assert `callback2.SendResponse` was called (receiving a response that logically belongs to `msg1`'s triggered execution) and `callback1.SendResponse` was never called — proving the first caller's callback is starved and the second caller silently receives a mismatched response.
