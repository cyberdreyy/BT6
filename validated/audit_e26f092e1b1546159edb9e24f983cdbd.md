### Title
`osKillWait.KillAndWait` / `unixKiller.Terminate`/`ForceKill` cannot terminate children that escape the process group via `setsid`, letting job-spawned daemons survive both graceful and forced kill - ([File: helpers/process/killer_unix.go])

### Summary
`unixKiller.Terminate` and `unixKiller.ForceKill` both send signals to the negative PID of the job process, i.e. to the process *group* rooted at the job's leader process, rather than to a cgroup/PID-namespace-scoped subtree. A job script that traps `SIGTERM`, forks, and calls `setsid()` in the child creates a new session/process group before it dies, so the forked descendant is no longer a member of the group being signaled and is never delivered `SIGTERM` or the subsequent `SIGKILL`.

### Finding Description
`osKillWait.KillAndWait` sends `Terminate()`, waits up to `GracefulTimeout`, then sends `ForceKill()` and waits up to `KillTimeout` before giving up: [1](#0-0) 

Both `Terminate` and `ForceKill` in the unix implementation compute the target PID via `getPID()`, which negates the PID to target the process *group*: [2](#0-1) 

`kill(2)` semantics for a negative pid ("signal every process whose *process group ID* equals `-pid`") only reach processes that remain members of the job's original process group. A process that calls `setsid()` after `fork()` detaches into a new session and becomes the leader of a brand-new process group; it is then outside the scope of any `-pgid` signal, including `SIGKILL` from `ForceKill`. This is unprivileged: `setsid(2)` requires no special permission, only that the calling process is not already a process-group leader, which is trivially true for a freshly forked child.

Attacker-controlled input: the job's CI script (`before_script`/`script`) can `trap SIGTERM` and daemonize a background process (e.g. via a small helper binary or shell built-ins like `setsid nohup ... &` combined with disowning), which is a normal operation available to any pipeline author, no admin privileges required.

Existing checks: there is no cgroup, PID-namespace, or subtree-tracking mechanism in this code path that would independently enumerate and kill descendants outside the process group; `KillAndWait`'s only fallback after both timeouts is to return `KillProcessError`, it does not attempt any broader reap (e.g. walking `/proc` for children, or killing a cgroup).

### Impact Explanation
On a shell/custom/ssh-based executor where jobs run directly as OS processes managed by this killer (not inside a container runtime providing its own PID-namespace/cgroup teardown), a canceled or timed-out job can leave an attacker-controlled daemon process running on the shared host indefinitely after the job is reported as killed/failed. This process can continue consuming resources, holding open sockets/files, or acting as a persistence mechanism on a multi-tenant runner host, outliving the job's cancellation and the Runner's own kill guarantees.

### Likelihood Explanation
Fully attacker-controlled and requires no special access beyond running an ordinary CI job script. It is deterministic and repeatable: trap `SIGTERM`, fork, `setsid`, sleep/loop, exit parent (or just let parent die from the eventual `SIGKILL`, which won't reach the detached child anyway). The technique is standard Unix daemonizing and works whenever the executor executes job scripts as plain OS processes killed via this process-group-based killer.

### Recommendation
Do not rely solely on process-group signaling for guaranteed subtree termination. Options:
- Place job processes in a dedicated cgroup (v1/v2) at spawn time and kill via the cgroup's `cgroup.kill`/freezer+SIGKILL-all mechanism, which catches processes regardless of session/process-group changes.
- Alternatively, walk `/proc` (or use `prctl(PR_SET_CHILD_SUBREAPER)`) to enumerate all live descendants by PPID chain before/after `setsid` escapes and signal each directly in `ForceKill`.
- At minimum, document this as a known limitation and prefer cgroup-based process management for executors handling untrusted job scripts on shared hosts.

### Proof of Concept
Go integration test (unix) added under `helpers/process`:
```go
func TestKillAndWait_EscapesViaSetsidSurvivesForceKill(t *testing.T) {
    script := `
trap 'exit 0' SIGTERM
( setsid sh -c 'while true; do sleep 1; done' & )
wait
`
    cmd := exec.Command("sh", "-c", script)
    require.NoError(t, cmd.Start())

    waitCh := make(chan error, 1)
    go func() { waitCh <- cmd.Wait() }()

    kw := process.NewOSKillWait(logger, 100*time.Millisecond, 100*time.Millisecond)
    err := kw.KillAndWait(process.NewOSCmd(cmd), waitCh)
    // KillAndWait returns after both timeouts elapse
    require.Error(t, err)

    // Assert the daemon child (found via pgrep for the sleep loop) is still alive
    out, _ := exec.Command("pgrep", "-f", "while true; do sleep 1; done").Output()
    require.NotEmpty(t, out, "expected escaped daemon child to still be running after ForceKill")
}
```
Expected assertions: `KillAndWait` returns `*KillProcessError` after consuming `gracefulKillTimeout + forceKillTimeout`, and the detached grandchild process (found via `pgrep`) is still running, proving `ForceKill`'s `SIGKILL` to `-pgid` did not reach the escaped daemon.

func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}

// getPID will return the negative PID (-PID) which is the process group. The
// negative symbol comes from kill(2) https://linux.die.net/man/2/kill `If pid
// is less than -1, then sig is sent to every process in the process group whose
// ID is -pid.`
func (pk *unixKiller) getPID() int {
	return pk.cmd.Process().Pid * -1
}
