### Title
Keyring credential loss prevents lenders from creating withdrawal requests - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.requestWithdraw` reuses the lender-admission check required for deposits. If a lender’s Keyring credential expires or is removed after they acquire tranche tokens, the sole epoch-withdrawal entrypoint reverts, freezing that address’s tranche position until the credential is restored. [1](#0-0) 

### Finding Description
Ordinary deposits correctly call `isWalletAllowed(msg.sender)` inside `_deposit`. [2](#0-1)  However, `requestWithdraw` applies the same admission predicate even though it does not add principal to the pool; it merely burns tranche tokens and creates a withdrawal receipt. [3](#0-2) 

`isWalletAllowed` is backed by the configured Keyring contract and policy, which can be changed through `setKeyringParams`. [4](#0-3)  Therefore, a credential status valid at deposit time can become invalid before withdrawal time. When the withdrawal window opens, `requestWithdraw` reverts with `NotAllowed`, before the CDO can create the strategy receipt and burn the tranche tokens. [5](#0-4) 

This is analogous to the suspended-collateral bug: a predicate intended to control entry is also applied to exit, causing funds already committed to the system to become unavailable.

### Impact Explanation
The affected lender cannot initiate a withdrawal for its full tranche balance while `isWalletAllowed(msg.sender)` is false. The freeze is temporary if Keyring access is later restored, and permanent for that address if it can never satisfy the policy again. Because withdrawal requests are the epoch vault’s exit mechanism, the blocked amount is the lender’s entire unrealized tranche value, not merely newly deposited funds.

This does not create pool insolvency or let an attacker take the funds; the impact is denial of exit to an existing token holder caused by an incorrect access predicate.

### Likelihood Explanation
Likelihood is moderate. The trigger requires a legitimate Keyring credential expiration, revocation, policy change, or Keyring configuration change after tokens are acquired. These are ordinary administrative or credential-lifecycle events and do not require malicious privileged behavior.

The issue affects every AA or BB holder whose credential becomes false before requesting withdrawal.

### Recommendation
Remove `!isWalletAllowed(msg.sender)` from `requestWithdraw`, while retaining the check in `_deposit`, `depositDuringEpoch`, and queue deposit intake. Withdrawal requests do not introduce new principal and should remain available to existing tranche holders after their admission status changes.

```diff
 function requestWithdraw(uint256 _amount, address _tranche) external returns (uint256 _underlyings) {
     _checkTranche(_tranche);
     _checkNotAllowed(
-      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
-      !isWalletAllowed(msg.sender)
+      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest)
     );
```

### Proof of Concept
Add this to the existing Foundry harness in `test/foundry/IdleCreditVault.t.sol`, where `owner`, `cdoEpoch`, `idleCDO`, `AAtranche`, `_startEpochAndCheckPrices`, and `_stopCurrentEpochWithApr` are initialized:

```solidity
contract MockKeyring {
    mapping(address => bool) public allowed;

    function setAllowed(address user, bool status) external {
        allowed[user] = status;
    }

    function checkCredential(uint256, address user) external view returns (bool) {
        return allowed[user];
    }
}

function testRequestWithdrawAfterKeyringCredentialExpires() external {
    uint256 amount = 10_000 * ONE_SCALE;
    MockKeyring checker = new MockKeyring();

    vm.prank(owner);
    cdoEpoch.setKeyringParams(address(checker), 1);

    // The test contract is admitted and deposits.
    checker.setAllowed(address(this), true);
    idleCDO.depositAA(amount);

    // Run and successfully stop an epoch so AA withdrawal requests reopen.
    _startEpochAndCheckPrices(0);
    _stopCurrentEpochWithApr(10e18);

    assertFalse(cdoEpoch.isEpochRunning());
    assertTrue(cdoEpoch.allowAAWithdrawRequest());

    // The honest credential lifecycle removes access after funds were committed.
    checker.setAllowed(address(this), false);

    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Restoring the credential makes the same withdrawal request succeed.
    checker.setAllowed(address(this), true);
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(requested, 0);
}
```

The first `requestWithdraw` reverting demonstrates that the deposit-admission condition freezes an existing tranche position; the successful request after reapproval confirms that the withdrawal path itself is otherwise valid.

```text
  function requestWithdraw(uint256 _amount, address _tranche) external returns (uint256 _underlyings) {
    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
      !isWalletAllowed(msg.sender)
    );
  
    // we check if there are donated assets to the pool and transfer them to the feeReceiver if any
    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;
    // add expected fees to pending withdraw fees counter
    pendingWithdrawFees += totalFees;

    /// if there is an AA withdrawal the overperformance that the amount withdrawed would have generated for BB tranches
    /// is saved in interestForOverUnderPerformance. This is used to calculate the interest that should be added to the
    /// expectedEpochInterest at the startEpoch.
    /// If there is a BB withdrawal this amount is subtracted from the expectedEpochInterest
    interestForOverUnderPerformance += diff;

    // The receipt is fixed now and leaves live NAV. Charge management fees upfront
    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
    creditVault.requestWithdraw(_underlyings, msg.sender, principal);
    // burn tranche tokens and decrease NAV without interest for the next epoch as it was not yet counted in NAV
    _withdrawOps(_amount, principal, _tranche);
```
