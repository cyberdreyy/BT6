### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
This is a valid analog to the reported bug class: a value that is *recorded* (confirmations counted) diverges from the value that actually exists (live, current multisig members). In `multisig2/src/lib.rs`, `DeleteMember` only purges confirmation state for requests that the removed member *originated*, not confirmations that member *cast* on other members' requests. Those stale confirmations remain in the `confirmations` set and are counted toward `num_confirmations`, letting a request execute with fewer live-member approvals than the configured threshold.

### Finding Description
`confirm()` decides whether to execute a request purely by comparing the size of the `confirmations: HashSet<String>` for that request against `num_confirmations`: [1](#0-0) 

When a member is removed via `DeleteMember`, `delete_member` only cleans up requests whose *original requester* (`r.member`) equals the removed member; confirmations that the removed member had already cast on requests created by *other* members are left untouched in the `confirmations` map: [2](#0-1) 

`assert_valid_request`, called at the top of `confirm`, only checks that the *caller* is currently a member and that the request/confirmations entries exist — it never re-validates that the *previously recorded* confirmers in the `HashSet<String>` are still members: [3](#0-2) 

The custody binding that should hold is: `count(confirmations for request R) == count(distinct live members who confirmed R)`. Because stale confirmations from removed members are never purged, this binding is broken — the recorded confirmation count can exceed the number of *live* members who actually approved.

### Impact Explanation
This maps to the Critical impact category "a multisig request executed below threshold." A multisig request (which can transfer NEAR, deploy code, add/remove keys, etc., via `execute_request`) can be authorized and executed with fewer live/current-member approvals than `num_confirmations` requires, because a phantom confirmation from a since-removed member still counts toward the quorum.

### Likelihood Explanation
This requires no attacker privilege beyond being (or having been) a legitimate multisig member — no owner, foundation, redeploy, or social engineering is needed. It occurs naturally any time membership rotation happens after a partial confirmation has been collected: (1) member A creates request R, (2) member B (a legitimate signer at the time) confirms R, (3) B is later removed from the multisig via a normal `DeleteMember` request (e.g., key rotation, employee offboarding, compromised key remediation), (4) R's confirmations still contain B, so it only needs `num_confirmations - 1` more approvals from currently-live members to execute. Member rotation is an expected, routine multisig operation, so the likelihood of this state occurring is high, not merely theoretical.

### Recommendation
When a member is deleted, iterate over **all** outstanding requests' confirmation sets (not just requests originated by that member) and remove any confirmation entry matching the removed member's identity string. Alternatively, when counting confirmations in `confirm()`, filter the stored confirmation set against `self.members` before comparing to `num_confirmations`, so removed members' stale confirmations never count toward the threshold.

### Proof of Concept
1. Initialize `MultiSigContract` with `members = {A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request(R)` — `R.member = A`, `confirmations[R] = {}`.
3. `B` calls `confirm(R)` → `confirmations[R].len()+1 = 1 < 3` → `confirmations[R] = {B}`.
4. Members submit and confirm a `DeleteMember { member: B }` request (a routine, legitimate rotation) which reaches threshold and executes via `delete_member`. Per `delete_member`, only requests where `r.member == B` (i.e. requests *B* created) have their confirmations wiped; `R` was created by `A`, so `confirmations[R]` still equals `{B}` — unchanged. `B` is now removed from `self.members` and its access key deleted.
5. `C` calls `confirm(R)` → `confirmations[R].len()+1 = 2 < 3` → `confirmations[R] = {B, C}`.
6. `D` calls `confirm(R)` → `confirmations[R].len()+1 = 3 >= 3` → `execute_request(R)` runs.

`R` executes with only 2 live-member confirmations (`C`, `D`) plus one phantom, already-removed member (`B`), even though the contract's stated guarantee is that 3 *current* members must approve. This directly violates the multisig-threshold custody binding.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
