#No Vulnerability found for this question.

**Analysis summary supporting this conclusion:**

The described "parity collision" is not a novel flaw but an inherent, intentional property of the StackerDB contract naming scheme: signer message contracts are named `signer-{reward_cycle % 2}-{message_id}` [1](#0-0) , meaning only two physical contract instances exist and are reused every other cycle by design — this is not something `is_active`'s prefix-only forwarding [2](#0-1)  or the listener's `signer_set != self.signer_set` gate [3](#0-2)  introduces as a bug.

Even granting the claimed parity collision between cycle N and N-2, the attack fails for two independent reasons already enforced in the code:

1. **Signature/weight binding is per-current-cycle, not attacker-controlled.** `signer_entries` and `signer_set` used for verification are derived fresh at `StackerDBListener::new` from the reward set active for the *current* burn tip's cycle [4](#0-3) . Any replayed chunk is checked with `signer_pubkey.verify(block_sighash.bits(), &signature)` against the pubkey mapped to that `slot_id` in the *current* signer set [5](#0-4) . An attacker holding only their own slot's key cannot forge another signer's signature to "bleed" extra weight; at most they can replay their own weight, which grants no advantage over voting normally.

2. **Block-hash exact-match gating.** Both `Accepted` and `Rejected` paths require `blocks.get_mut(&block_sighash)` to find a currently-tracked block header hash [6](#0-5) [7](#0-6) . A stale cycle N-2 chunk references a distinct old block header hash that will not collide with the hash of the block currently being voted on in cycle N, so it is silently dropped ("Received signature/rejection for block that we did not request. Ignoring.") regardless of the `signer_set` parity check.

Additionally, the scenario fundamentally depends on StackerDB chunk versioning/replay behavior at the P2P/sync layer, which is explicitly out of scope for this audit ("P2P/RPC transport and StackerDB sync mechanics ... reject on sight").

Since the attacker (one signer slot, gossip-only, no other signers' keys) cannot make the weight-tallying logic credit any weight beyond their own single slot through this path, no safety or liveness property listed in scope is broken.

pub fn get_signers_db_signer_set_message_id(name: &str) -> Option<(u32, u32)> {
    // Splitting the string by '-'
    let parts: Vec<&str> = name.split('-').collect();
    if parts.len() != 3 {
        return None;
    }
    // Extracting message ID and slot ID
    let signer_set = parts[1].parse::<u32>().ok()?;
    let message_id = parts[2].parse::<u32>().ok()?;
    Some((signer_set, message_id))
}
