### Title
EI-authenticated requests bypass the `isUser` int-ID restriction in `PipelineRunsController.Create` and can reach `RunJobV2` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the int-ID run path with `_, isUser := auth.GetAuthenticatedUser(c)`, with a comment stating "only users are allowed to run jobs using int IDs - EIs not allowed." However, `auth.AuthenticateExternalInitiator` explicitly sets the same `SessionUserKey` context value used by `GetAuthenticatedUser` to a synthetic `clsessions.User{Role: clsessions.UserRoleRun}`, so `isUser` evaluates `true` for EI-authenticated requests too, defeating the intended restriction and letting EI credentials trigger `RunJobV2` by integer job ID.

### Finding Description
The route `userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))` accepts both session/token users and external initiators via `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, `auth.AuthenticateBySession` [1](#0-0) .

Inside `Create`, the code path meant to exclude EIs relies on `auth.GetAuthenticatedUser(c)`:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
``` [2](#0-1) 

`GetAuthenticatedUser` only checks for presence/type of the `SessionUserKey` context value:
```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	...
}
``` [3](#0-2) 

But `AuthenticateExternalInitiator` — the middleware used specifically to authenticate EIs — sets exactly this key to a fabricated `run`-role user:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [4](#0-3) 

Consequently, when an EI authenticates and calls `POST /v2/jobs/:ID/runs` with an integer job ID, `isUser` is `true`, and `Create` proceeds to call `prc.App.RunJobV2(ctx, jobID, nil)` — the exact code path the inline comment claims is unreachable for EIs. This contradicts the code's own stated intent (`AUTHORIZATION_EXACTNESS` violation): the comment/design intends EIs be restricted to (removed) webhook/UUID job runs only, but the shared `SessionUserKey` mechanism makes that restriction ineffective.

Mitigating factor: `RunJobV2` itself unconditionally rejects execution in secure/production builds:
```go
func (app *ChainlinkApplication) RunJobV2(...) (int64, error) {
	if build.IsProd() {
		return 0, errors.New("manual job runs not supported on secure builds")
	}
	...
}
``` [5](#0-4) 
I was not able to locate the definition of `build.IsProd()`/`build.IsDev()` in the indexed codebase to confirm whether this is a compile-time build tag or a runtime-configurable flag; this materially affects exploitability and could not be fully verified with available tools.

### Impact Explanation
If `build.IsProd()` evaluates false at runtime (e.g., dev/test builds, or any deployment not compiled with the production build tag), a holder of valid EI credentials — normally scoped only to triggering webhook-type job runs by UUID (a job type that has since been removed) — can instead trigger arbitrary job runs on **any** job by integer ID via `RunJobV2`, including VRF and other pipeline jobs, without job ownership/EI-association checks in `Create` or `RunJobV2`. This is an authorization-scope bypass: EI credentials gain capability equivalent to an edit/run-role user for job execution, potentially causing unauthorized pipeline execution, resource consumption, or unintended on-chain side effects depending on job type. In production builds, the `build.IsProd()` guard in `RunJobV2` fully blocks this specific execution path, limiting real-world impact to non-production deployments.

### Likelihood Explanation
Preconditions: attacker only needs valid EI access-key/secret headers (`static.ExternalInitiatorAccessKeyHeader`/`static.ExternalInitiatorSecretHeader`) for any registered external initiator — no admin/edit/run user credentials required, matching the "restricted external-initiator credential holder" threat model. The request is a simple `POST /v2/jobs/:ID/runs` with an integer path ID. Feasibility depends entirely on whether the deployed binary is built as "prod" (blocked) or not (exploitable); this could not be confirmed from the available code index.

### Recommendation
Do not overload `SessionUserKey` for EI authentication. Distinguish EI-authenticated requests from real user sessions in `Create` by checking `auth.GetAuthenticatedExternalInitiator(c)` (which uses a distinct `SessionExternalInitiatorKey`) and explicitly reject int-ID run requests when that key is present, regardless of the synthetic `SessionUserKey`. Alternatively, avoid setting `SessionUserKey` at all in `AuthenticateExternalInitiator` and have `RequiresRunRole`/other role checks operate on a unified principal type that preserves the EI/user distinction.

### Proof of Concept
Go handler-level integration test plan (extending `TestRunner_WebhookJobRemoved`-style setup):
1. Create a normal (non-webhook) job (e.g., a simple HTTP/bridge pipeline job) via an authenticated user session.
2. Create an external initiator via `cltest.CreateExternalInitiatorViaWeb`, obtaining `AccessKey`/`Secret`.
3. Send `POST /v2/jobs/<int_job_id>/runs` with headers `static.ExternalInitiatorAccessKeyHeader`/`static.ExternalInitiatorSecretHeader` set to the EI credentials, and no session/API-token headers.
4. Assert the response: if `build.IsProd()` is false, expect `RunJobV2` to be invoked and a pipeline run created (200 with `pipelineRun` resource, `pipeline_runs` row count incremented) — proving EI reached `RunJobV2` despite the "EIs not allowed" comment. If `build.IsProd()` is true, expect `500` with "manual job runs not supported on secure builds", confirming the build-tag mitigation is the only barrier.
5. Contrast with a UUID-based request from the same EI, which should return `422 Unprocessable Entity` with `job.ErrJobTypeRemoved`, per the existing early check.
6. Repeat step 3 with a genuine unauthenticated/anonymous caller (no EI, no user) to confirm `401 Unauthorized` from `RequiresRunRole`, establishing that only EI-specific credentials (not fully unauthenticated) trigger the bypass.
