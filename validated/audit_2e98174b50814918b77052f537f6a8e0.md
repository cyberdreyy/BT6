### Title
Revoked/deleted workflow authorization remains valid at the gateway until the next metadata pull/aggregation cycle - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
The v2 gateway HTTP trigger path (`HandleJSONRPCUserMessage` → `httpTriggerHandler.HandleUserTriggerRequest` → `WorkflowMetadataHandler.Authorize`) authorizes a signed trigger request purely against a locally cached map of `authorizedKeys` per `workflowID`, which is only refreshed by a periodic pull/aggregation loop. A workflow that is deleted, paused, or has a key de-authorized on the workflow-node/DON side is not actively pushed as "revoked" to the gateway; the gateway only drops it from its cache the next time `syncMetadata` runs and the nodes stop reporting it. Until then, any holder of a previously-authorized private key can keep sending signed `MethodWorkflowExecute` JSON-RPC requests that pass `Authorize` and are dispatched to the DON via `sendWithRetries`, and ultimately drive outbound requests through `makeOutgoingRequest`.

### Finding Description
`HandleJSONRPCUserMessage` (`core/services/gateway/handlers/capabilities/v2/http_handler.go:391-401`) forwards all user-submitted trigger requests to `httpTriggerHandler.HandleUserTriggerRequest` [1](#0-0) . That handler resolves the workflow and calls `authorizeRequest`, which delegates entirely to `WorkflowMetadataHandler.Authorize` [2](#0-1) .

`Authorize` verifies the JWT signature/replay (`jwtCache`) and then checks the signer's public key against the in-memory `h.authorizedKeys[workflowID]` map [3](#0-2) . There is no check against the DON/workflow node in real time — no live query, no revocation callback, no cache invalidation trigger tied to workflow deletion/pause/de-authorization events.

The only mechanism that updates `authorizedKeys` is the periodic loop:
- `sendMetadataPullRequest` is invoked every `MetadataPullIntervalMs` (default 60,000 ms) to ask nodes for their current metadata [4](#0-3) .
- `syncMetadata` runs every `MetadataAggregationIntervalMs` (default 60,000 ms) and rebuilds `authorizedKeys`, `workflowIDToRef`, `workflowRefToID` entirely from the currently reported per-shard aggregator state [5](#0-4) .

There is no explicit "workflow revoked" push message type; de-authorization is only implicitly reflected once the workflow node(s) stop reporting the workflow in subsequent pull responses and the F+1 aggregator threshold ages out the old observation. Until both the next pull cycle and the next aggregation cycle complete (up to `MetadataPullIntervalMs + MetadataAggregationIntervalMs`, ~2 minutes with defaults, more under load or if MetadataPullRequestTimeoutMs is hit), the stale `authorizedKeys[workflowID]` entry persists in memory and `Authorize` continues to accept freshly-signed JWTs (new `jti`, so JWT replay protection does not block it) from the previously authorized key. Each accepted request proceeds through `sendWithRetries` to the DON, and any resulting HTTP Action responses flow through `makeOutgoingRequest` in `http_handler.go`, which performs the actual outbound HTTP request with the attacker-controlled `req.URL`/`Headers`/`Body`.

### Impact Explanation
An externally-owned key that was previously authorized for a workflow (e.g., a departing team member's key, or a key an owner explicitly revokes/rotates after a workflow is paused or deleted) can continue to trigger DON execution and outbound HTTP actions for up to the metadata sync window after revocation. Because DON work triggered this way is billed/attributed to the original workflow owner/subscription, this matches "theft of protocol revenue: DON work charged to another owner/subscriber than the attacker" — the attacker consumes DON compute/outbound-request budget on behalf of a workflow owner who believes access has been cut off.

### Likelihood Explanation
Requires the attacker to have held (or still hold) a private key that was at some point registered as an `AuthorizedKey` for the target workflow — this is a realistic scenario for key rotation, employee offboarding, or de-authorization following a security incident, not merely a hypothetical. No operator/admin/DB privileges are needed; the attacker only needs to keep signing new JSON-RPC gateway requests with the old key, which trivially bypasses the JWT replay cache (new `jti` each time). The window is deterministic and bounded by `MetadataPullIntervalMs + MetadataAggregationIntervalMs`, making it fully reproducible in a unit/integration test by populating `authorizedKeys` and then calling `syncMetadata` with data that omits the workflow.

### Recommendation
- Add an explicit revocation/removal signal from workflow nodes (e.g., a "workflow deleted" or "key revoked" push message) that is applied immediately rather than waiting for the next aggregation cycle to silently drop the entry.
- Shorten `MetadataPullIntervalMs`/`MetadataAggregationIntervalMs` for security-sensitive changes, or support an out-of-band immediate re-authorization check (e.g., verifying the key against a freshly pulled per-request state, or invalidating cached authorization eagerly on node-reported deregistration events) so revocation takes effect before the next accepted trigger, matching the required invariant.
- Consider embedding a monotonically increasing version/nonce in workflow metadata so that stale cached entries can be distinguished from current ones and force a synchronous re-check on suspicious/old versions.

### Proof of Concept
Handler-level Go test in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go` or `http_trigger_handler_test.go`:
1. Construct a `WorkflowMetadataHandler`/`httpTriggerHandler` as in existing tests (see `createTestTriggerHandler`).
2. Seed `handler.workflowMetadataHandler.authorizedKeys[workflowID]` with a key derived from `privateKey`, and `workflowIDToRef`/`workflowRefToID` as in `TestHttpTriggerHandler_HandleUserTriggerRequest_JWTAuthorization`.
3. Call `HandleUserTriggerRequest` with a JWT signed by `privateKey` and assert success (request forwarded to DON nodes via `mockDon.SendToNode`).
4. Simulate revocation: call `syncMetadata(ctx)` with aggregator state that no longer reports `workflowID` (i.e., don't feed it any `Collect` observations for that workflow this cycle), confirming `authorizedKeys` before the call still contains the key.
5. Immediately (without advancing beyond the sync call) issue a second signed JWT (new `jti`) for the same workflow/key and assert whether `HandleUserTriggerRequest` still succeeds — expected (vulnerable) result: it succeeds until `syncMetadata` is invoked; expected (fixed) result: it should fail immediately once revocation is known to the gateway, not only after the next scheduled aggregation tick.

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (h *WorkflowMetadataHandler) syncMetadata(ctx context.Context) {
	authorizedKeys := make(map[string]map[gateway.AuthorizedKey]struct{})
	workflowRefToID := make(map[workflowReference]string)
	workflowIDToRef := make(map[string]workflowReference)
	workflowShards := make(map[string][]*shardEndpoint)

	for _, shard := range h.shards {
		agg := h.aggs[shard.donID]
		metadata := agg.Aggregate()
		for _, data := range metadata {
			workflowID := data.WorkflowSelector.WorkflowID
			workflowRef := workflowReference{
				workflowOwner: data.WorkflowSelector.WorkflowOwner,
				workflowName:  data.WorkflowSelector.WorkflowName,
				workflowTag:   data.WorkflowSelector.WorkflowTag,
			}

			// Case 1: this workflow ID was already registered. If the reference
			// matches, this is the same workflow reported by another shard —
			// append the shard to its fan-out list. If the reference differs,
			// it's a conflicting observation; drop it.
			if existingRef, idExists := workflowIDToRef[workflowID]; idExists {
				if existingRef == workflowRef {
					workflowShards[workflowID] = append(workflowShards[workflowID], shard)
				} else {
					h.lggr.Debugw("Duplicate workflow ID with conflicting reference, dropping",
						"workflowID", workflowID, "existingRef", existingRef, "conflictingRef", workflowRef)
				}
				continue
			}

			// Case 2: this workflow reference was already registered under a
			// different workflow ID. First-wins by reference; drop the duplicate.
			if _, refExists := workflowRefToID[workflowRef]; refExists {
				h.lggr.Debugw("Duplicate workflow reference found, dropping",
					"workflowRef", workflowRef, "workflowID", workflowID)
				continue
			}

			// Case 3: new workflow ID and reference — register it.
			workflowIDToRef[workflowID] = workflowRef
			workflowRefToID[workflowRef] = workflowID
			authorizedKeys[workflowID] = make(map[gateway.AuthorizedKey]struct{})
			for _, key := range data.AuthorizedKeys {
				authorizedKeys[workflowID][key] = struct{}{}
			}
			workflowShards[workflowID] = append(workflowShards[workflowID], shard)
		}
	}

	h.mu.Lock()
	defer h.mu.Unlock()

	if len(h.workflowIDToRef) == 0 && len(workflowIDToRef) > 0 {
		latencyMs := time.Since(h.startTime).Milliseconds()
		h.metrics.RecordMetadataSyncStartupLatency(ctx, latencyMs, h.lggr)
	}
	// Log all registered workflow IDs
	workflowIDs := make([]string, 0, len(workflowIDToRef))
	for workflowID := range workflowIDToRef {
		workflowIDs = append(workflowIDs, workflowID)
	}
	h.lggr.Debugw("Synced workflow metadata", "workflowIDs", workflowIDs, "count", len(workflowIDs))

	h.authorizedKeys = authorizedKeys
	h.workflowRefToID = workflowRefToID
	h.workflowIDToRef = workflowIDToRef
	h.workflowShards = workflowShards
	h.metrics.RecordLoadedMetadataSize(ctx, int64(len(h.workflowIDToRef)), h.lggr)
}
