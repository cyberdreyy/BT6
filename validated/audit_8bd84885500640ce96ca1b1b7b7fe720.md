### Title
Factory-deployed credit vaults can bind attacker-controlled strategy implementations and drain lender deposits - (File: contracts/IdleCreditVaultFactory.sol)

### Summary
`IdleCreditVaultFactory.deployCreditVault()` and `deployRevolvingCreditVault()` are permissionless and accept arbitrary contract addresses as strategy and CDO implementations. The factory passes `strategyData.implementation` directly into `_deployProxy()` without checking an approved implementation registry or bytecode hash. [1](#0-0) [2](#0-1) [3](#0-2) 

An attacker can deploy a factory-issued vault whose strategy impersonates the expected `IdleCreditVault` interface but contains an unrestricted withdrawal function. Because the legitimate CDO approves the strategy and transfers every deposit into it, all subsequent lender deposits can be moved directly to the attacker. [4](#0-3) [5](#0-4) 

### Finding Description
The deployment trust boundary is broken. Users and integrations can reasonably treat addresses emitted in `CreditVaultDeployed` as factory-created vaults, but the factory does not verify that the supplied implementation is the audited `IdleCreditVault` or `IdleCDOEpochVariant` code. [6](#0-5) [7](#0-6) 

For a malicious strategy implementation, the attacker only needs to implement the small interface exercised during deployment:

- `initialize(address,address,address,address,string,uint256)`
- `strategyToken()`
- `symbol()`
- `decimals()`
- `setAprs()`
- `setWhitelistedCDO()`
- `transferOwnership()`
- `deposit(uint256)`

The factory then completes deployment, configures the legitimate CDO to use the malicious strategy, and emits the vault in `CreditVaultDeployed`. When a KYC-passing lender deposits, the legitimate CDO transfers underlying to itself, mints tranche tokens, and calls `strategy.deposit(_amount)`. The malicious strategy can pull the CDO’s underlying through the unlimited approval granted during CDO initialization and mint strategy tokens normally, while retaining an unrestricted backdoor to transfer those underlying tokens to the attacker. [4](#0-3) [8](#0-7) [9](#0-8) 

### Impact Explanation
Every underlying deposit routed through the malicious factory-created strategy can be stolen. The attacker controls the deployed strategy code without needing to be the CDO owner, treasury, guardian, manager, borrower, Keyring administrator, fee receiver, or queue operator.

For example, if one lender deposits 1,000,000 USDC, the attacker can call the malicious strategy’s drain function and receive the entire 1,000,000 USDC held by the strategy. The lender is left with tranche tokens backed by uncollectible strategy tokens, producing direct theft and vault insolvency.

### Likelihood Explanation
The attack requires an unprivileged factory call and no privileged-role compromise. Its main prerequisite is convincing lenders or an integration to use the attacker-deployed vault address. The official factory event and shared `proxyAdmin` make the malicious deployment materially more convincing than an unrelated standalone contract. [6](#0-5) [3](#0-2) 

### Recommendation
Do not accept arbitrary implementation addresses in production factory deployments. Maintain an on-chain registry of treasury-approved implementation addresses or bytecode hashes for each component and require:

```solidity
if (!approvedStrategyImplementations[strategyData.implementation]) revert InvalidImplementation();
if (!approvedCdoImplementations[cvParams.implementation]) revert InvalidImplementation();
```

Apply equivalent validation to the programmable borrower, queue, and write-off escrow implementations. Emit the implementation addresses in `CreditVaultDeployed`, and preferably derive deployments from versioned factory configuration rather than caller-supplied implementation parameters.

        uint256 depositAmount = 1_000_000e6;
        underlying.mint(lender, depositAmount);
