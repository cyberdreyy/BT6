### Title
`Message.Validate` performs no freshness or replay check, allowing a captured signed legacy gateway `Message` to be resubmitted and re-trigger the WebAPI DON action multiple times - (File: core/services/gateway/api/message.go)

### Summary
`(*Message).Validate` in `core/services/gateway/api/message.go` only checks field lengths/format and recovers the signer from the signature; it never binds the message to a timestamp window, nonce, or a "used-once" store. The only consumer of legacy messages, `handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go`, adds a coarse payload-timestamp staleness check but never rejects a `MessageId`/signature it has already processed, so any valid captured `Message` can be replayed to `ProcessRequest` any number of times inside the staleness window and each replay re-forwards the trigger to every DON member.

### Finding Description
The legacy gateway path is: `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-262`) decodes the request, and for legacy (DON-ID) requests calls `msg.Validate()` [1](#0-0)  then dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)` [2](#0-1) .

`Validate()` checks only signature length, ID/method/DON-ID length and null-byte suffixes, and recovers the sender from the ECDSA signature - there is no message-id uniqueness tracking, nonce, or timestamp field checked at all: [3](#0-2) .

The only place any freshness is enforced is inside the capabilities handler's `HandleLegacyUserMessage`, which reads a `payload.Timestamp` from the trigger payload and rejects it only if it's older than `MaxAllowedMessageAgeSec`: [4](#0-3) . This is a coarse age check, not a uniqueness/replay check - a message minted "now" remains valid for the entire configured window and can be replayed any number of times inside it.

Crucially, after the staleness check, the handler unconditionally stores/overwrites the callback keyed by `msg.Body.MessageId` and re-forwards the identical request to every DON member on every call, with no check for a previously-seen `MessageId` or signature: [5](#0-4) 

This is in contrast to every other (newer, JSON-RPC v2) handler in the same package tree, which explicitly implement replay/duplicate protection - e.g. `confidentialrelay` rejects with `"request ID already exists"`, the `vault` handler uses `RequestReplayGuard`/`"request was already authorized previously"`, and `v2/http_trigger_handler` rejects in-flight duplicates and JWT replays via `jwtReplayCache`. The legacy `api.Message` + `capabilities.handler` path has no equivalent guard.

Because `Validate()` is stateless and per-message, and the handler that consumes it has no message-id/signature dedup, an attacker who captures one valid signed `Message` JSON body (e.g., by observing network traffic to `/` gateway HTTP endpoint, since TLS termination or logging could expose it, or simply via a client-side leak) can POST the identical bytes multiple times to the gateway. Each POST passes `Validate()` (signature/lengths unchanged), passes the staleness check (still within `MaxAllowedMessageAgeSec`), and is forwarded again via `don.SendToNode` to all DON members, re-triggering `MethodWebAPITrigger` handling on every node in the DON.

### Impact Explanation
This allows unauthorized re-execution of a privileged gateway-to-DON action (duplicate `web_api_trigger` invocation) under the original sender's identity, without needing to forge a new signature. Depending on what the DON's WebAPI trigger capability does with a re-delivered trigger (e.g., re-running a workflow), this can cause duplicate workflow executions / duplicate side effects attributable to the original signer, which matches Chainlink's "unauthorized job run" bounty impact class - a replayed, unprivileged submission causes privileged, non-idempotent gateway/DON actions to fire again.

### Likelihood Explanation
Preconditions are low: the attacker only needs to obtain one previously valid signed `Message` (e.g., via observing an HTTP request, a proxy log, or a compromised client-side channel) — no operator/admin access or key material is needed, since the signature and message bytes are replayed verbatim. The replay is trivially repeatable (simple HTTP POST of identical bytes) for the full duration of `MaxAllowedMessageAgeSec`, and nothing in `Validate()` or `HandleLegacyUserMessage` invalidates a message after first use.

### Recommendation
Add message-id/nonce-based replay protection to the legacy gateway pipeline, mirroring the pattern already used by the JSON-RPC v2 handlers:
- In `HandleLegacyUserMessage`, before storing the callback and forwarding to nodes, check a bounded "seen `MessageId`" (or seen-signature) store and reject with a duplicate/replay error if already present, instead of unconditionally overwriting `h.savedCallbacks[msg.Body.MessageId]`.
- Alternatively/additionally, require a monotonically increasing or single-use nonce per sender that is validated and recorded (e.g. similar to `core/capabilities/vault/request_replay_guard.go`'s `RequestReplayGuard`) at the point `Validate()`/`HandleLegacyUserMessage` processes the message, so a second submission of the same signed payload is rejected regardless of its age.

### Proof of Concept
Go handler-level test (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Build a signed `api.Message` with `Method: MethodWebAPITrigger`, a valid `TriggerRequestPayload` with `Timestamp: time.Now().Unix()`, and a fresh `MessageId`.
2. Call `handler.HandleLegacyUserMessage(ctx, msg, callback1)`; assert `don.SendToNode` was invoked once per DON member and the request succeeded.
3. Call `handler.HandleLegacyUserMessage(ctx, msg, callback2)` again with the identical `msg` (same signature, same `MessageId`, unchanged timestamp, still within `MaxAllowedMessageAgeSec`).
4. Assert (expected to fail today): the second call is rejected as duplicate/stale (e.g., an error like `"message already processed"`), and `don.SendToNode` mock is NOT invoked a second time.
5. Current behavior: the second call succeeds identically to the first, `don.SendToNode` is invoked again for every DON member, and `h.savedCallbacks[msg.Body.MessageId]` is silently overwritten with `callback2` — demonstrating the replay.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
