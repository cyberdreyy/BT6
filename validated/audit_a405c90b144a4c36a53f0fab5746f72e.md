### Title
Kubernetes `terminalConn.Close()` is a no-op, letting a cancelled/completed job's exec proxy goroutine and shared session-server socket leak indefinitely - ([File: executors/kubernetes/terminal.go])

### Summary
For the Kubernetes executor, `terminalConn.Close()` at `executors/kubernetes/terminal.go:41-43` does nothing, so when a job is cancelled the runner's `Session.Kill()` call has no effect on the goroutine blocked inside `terminal.ProxyWebSocket` (invoked from `terminalConn.Start`). Because `waitForTerminal` (`common/build.go:1371-1411`) returns immediately after calling `Session.Kill()` without waiting for that goroutine to actually exit, and the shared `session.Server`'s `http.Server` (`session/server.go:50-90`) has no read/write/idle timeouts, an attacker who keeps their WebSocket open can keep the proxying goroutine and its socket/fd alive on the single shared session listener well past job cancellation.

### Finding Description
`session.Session.execHandler` (`session/session.go:146-191`) synchronously calls `terminalConn.Start(w, r, s.TimeoutCh, s.DisconnectCh)` inside the HTTP handler goroutine spawned by the shared `session.Server`'s `http.Server` (`session/server.go:87,147-152`, wired up once in `commands/multi.go:950-992` as `mr.sessionServer`, a single global TLS listener for the whole runner process).

For Kubernetes, `Start` blocks inside the external `terminal.ProxyWebSocket(w, r, t.settings, wsProxy)` call [1](#0-0) , and `Close()` is a literal no-op: [2](#0-1) 

`common.Build.waitForTerminal` handles job cancellation via `ctx.Done()`, calling only `b.Session.Kill()` and returning immediately — it never signals `TimeoutCh`, and never waits for the `Start()` goroutine to finish: [3](#0-2) 

`Session.Kill()` simply invokes `conn.Close()` and nils out the reference; it does not join the goroutine running `Start()`: [4](#0-3) 

The generic `ProxyTerminal` helper's cancellation mechanism only fires on `timeoutCh` (sent solely by the terminal-session-timeout branch of `waitForTerminal`, not the cancellation branch) or on the proxy function itself returning: [5](#0-4) 

Since `Kill()`→`Close()` is a no-op for Kubernetes, and `TimeoutCh` is never sent on cancellation, nothing internal to the runner unblocks `ProxyWebSocket`. It only stops when the client (attacker) closes its side, or when the backing pod's exec stream is severed — which happens later, via `executor.Cleanup()` (deleting the pod), asynchronously and with no bound guaranteeing prompt termination of the already-blocked HTTP goroutine. The shared `session.Server`'s underlying `http.Server` has no `ReadTimeout`/`WriteTimeout`/`IdleTimeout` set [6](#0-5) , so nothing at the transport layer bounds how long a stalled/held-open WebSocket can keep the handler goroutine and its socket fd alive.

### Impact Explanation
An attacker with legitimate web-terminal access to their own job (a pipeline author/authorized project member) can open the exec WebSocket, then have the job cancelled/timed-out while keeping their client connection open (or a client that stops reading/writing after cancellation but doesn't send a close frame). The `Start()`/`ProxyWebSocket` goroutine and its TCP+TLS socket remain attached to the **shared** `session.Server` — one global listener serving every job/project on that runner — well past job completion. Repeating this across multiple jobs accumulates leaked goroutines and file descriptors on that single shared listener, which is a real, concrete, scoped resource-exhaustion risk that can degrade or deny terminal access for other projects' jobs sharing the same runner process, matching the described scope.

### Likelihood Explanation
Preconditions are modest and attacker-controlled: the Kubernetes executor with the interactive web terminal feature enabled, and the ability to (a) open a terminal on one's own job and (b) get that job cancelled or timed out (trivially triggerable by the same user via pipeline cancellation or job timeout) while not closing the WebSocket cleanly. No admin privileges, no cluster compromise, and no reliance on malicious peers are required — only ordinary GitLab project permissions to view a job's terminal. This is repeatable per job, so the leak accumulates linearly with the number of times the attacker repeats it.

### Recommendation
- Implement a real `Close()` for the Kubernetes `terminalConn` that actively tears down the exec stream/WebSocket dial to the Kubernetes API (e.g., store and cancel the context/dialer used by `ProxyWebSocket`, or close the underlying connection), mirroring the Docker executor's `cancelFn` approach.
- Have `waitForTerminal`'s cancellation branch (`common/build.go:1385-1391`) also signal `s.Session.TimeoutCh` (or an equivalent stop signal) so `ProxyTerminal`'s watcher goroutine reliably triggers `proxyStopCh` on job cancellation, not only on the dedicated terminal-timeout path.
- Add `ReadTimeout`/`WriteTimeout`/`IdleTimeout` (or per-connection deadlines) to the shared `session.Server`'s `http.Server` in `session/server.go` to bound worst-case goroutine/fd lifetime regardless of executor-specific cleanup behavior.
- Optionally have `Session.Kill()`/`closeTerminalConn` wait (with a bounded timeout) for the `Start()` goroutine to actually return before considering the session's resources reclaimed, and log/metric when it doesn't.

### Proof of Concept
Go unit test in `session` (or `executors/kubernetes`) package:
1. Implement a fake `terminal.Conn` mimicking the Kubernetes `terminalConn`: `Start` blocks on a channel that is only closed when the fake's `Close()` is called (to model a "real" fix) vs. never closed (to model the current no-op `Close()`).
2. Use `session.NewSession`, `SetInteractiveTerminal` with a mock returning this fake conn, start an `httptest.Server` with `session.Handler()`, dial a WebSocket to `<endpoint>/exec`.
3. Call `session.Kill()` (simulating `waitForTerminal`'s cancellation branch) and assert:
   - With the current no-op `Close()`: the `Start()` goroutine is still running/blocked after `Kill()` returns (e.g., via a `sync.WaitGroup`/channel that's never signaled within a short deadline) — demonstrating the leak.
   - Track `runtime.NumGoroutine()` before/after `Kill()` plus a grace period, asserting it does **not** return to baseline, reproducing the resource-exhaustion condition.
4. As a regression test for the fix, assert that after implementing a real `Close()` for the Kubernetes `terminalConn`, `Start()` unblocks within the `session_timeout`/a bounded interval and goroutine/fd counts return to baseline.

func (s *Session) Kill() error {
	s.lock.Lock()
	defer s.lock.Unlock()

	if s.terminalConn == nil {
		return nil
	}

	err := s.terminalConn.Close()
	s.terminalConn = nil

	return err
}

func ProxyTerminal(timeoutCh, disconnectCh, proxyStopCh chan error, proxyFunc func()) {
	disconnected := make(chan bool, 1)
	// terminal exit handler
	go func() {
		// wait for either session timeout or disconnection from the client
		select {
		case err := <-timeoutCh:
			proxyStopCh <- err
		case <-disconnected:
			// forward the disconnection event if there is any waiting receiver
			nonBlockingSend(
				disconnectCh,
				errors.New("finished proxying (client disconnected?)"),
			)
		}
	}()

	proxyFunc()
	disconnected <- true
}
