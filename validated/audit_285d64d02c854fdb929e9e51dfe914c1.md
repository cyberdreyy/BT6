The external report's bug class (delivering value via a callback before payment is validated, enabling a free flash loan) requires a hook that executes arbitrary receiver code while holding already-transferred value, before the sender's debit is confirmed. I checked the closest analogs in this repo:

- `w-near/src/w_near.rs` `near_withdraw` performs `self.ft.internal_withdraw(&account_id, amount)` (debit) strictly before `Promise::new(account_id).transfer(amount + 1)` (payout), so there's no window where NEAR is delivered before the wNEAR debit is recorded [1](#0-0) .
- `ft_transfer_call`/`ft_on_transfer` (the actual NEP-141 flow where a receiver contract's callback runs after tokens are already credited to it) is implemented entirely via `near_contract_standards::impl_fungible_token_core!(Contract, ft)` [2](#0-1) , i.e., it's a `near-contract-standards` library behavior with no custom logic path through this repository, which is explicitly out of scope.
- The staking-pool, lockup, and multisig cross-contract call patterns all follow the standard "set busy status → schedule promise → apply state change only in the callback keyed on `is_promise_success()`" pattern (e.g. [3](#0-2) , [4](#0-3) ), which does not expose a window where a counterparty gets custody of funds/NFT-equivalent assets and can execute arbitrary code before the corresponding debit is settled.

No reachable path in the in-scope repository breaks a custody-binding equality in the way described by the report.
