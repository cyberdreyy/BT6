### Title
Global RequestCache admission check allows a single unprivileged sender to exhaust `maxCacheSize` and deny service to all other senders - (File: core/services/gateway/handlers/common/requestcache.go)

### Summary
`(c *requestCache[T]).NewRequest` enforces only a single global capacity check (`len(c.cache) >= int(c.maxCacheSize)`) with no per-sender quota, so any caller able to submit `maxCacheSize` distinct `(sender, id)` pairs can fill the entire shared cache and cause `NewRequest` to reject every subsequent legitimate request with `"request cache is full"`, regardless of who submitted it.

### Finding Description
`NewRequest` computes `key := globalId{request.Body.Sender, request.Body.MessageId}` and admits the request as long as the key is unique and `len(c.cache) < maxCacheSize` [1](#0-0) . There is no bound on how many distinct `sender` values a single map may hold and no per-sender reservation of slots — capacity is a purely global counter shared across all tenants. Because `request.Body.Sender` is derived from `ExtractSigner()` over an attacker-supplied signature [2](#0-1) , an attacker can trivially mint a fresh ECDSA keypair per request to produce arbitrarily many distinct `sender` identities at negligible cost, defeating any notion that "sender" acts as an identity-based quota boundary within this component. The repository's own unit test demonstrates this exact behavior: filling the cache to its max size makes a subsequent unrelated `NewRequest` call fail [3](#0-2) .

Note on reachability: I was not able to confirm, within this investigation, that the specific vault, confidentialrelay, or capabilities/v1 handlers currently route through this particular `common.RequestCache` implementation — the vault handler (`core/services/gateway/handlers/vault/handler.go`) and confidentialrelay handler instead track requests in their own `activeRequests`/`responses` maps keyed by request ID with a separate node-facing rate limiter [4](#0-3) , and I could not locate a call site importing `common.NewRequestCache` in those files. `common.NewRequestCache` is a generic, exported, reusable component intended for exactly this per-request/per-response aggregation pattern, and any handler that does wire it up (as its doc comment implies is expected) inherits this flaw as-is.

### Impact Explanation
If a handler backed by this cache is reachable without a per-sender admission/rate-limit check performed strictly *before* calling `NewRequest`, a single unprivileged client can starve the shared slot pool, denying other tenants the ability to have their requests tracked and ultimately timed-out/rejected — a cross-tenant availability/DoS impact. This matches the "Denial of Service" bounty class rather than any authentication/authorization bypass, since no secrets, keys, or unauthorized actions on another user's data are involved — only availability of the request-tracking mechanism itself.

### Likelihood Explanation
The precondition ("gateway endpoint routed to a handler backed by NewRequestCache, with no additional per-sender capacity reservation upstream") is required and not confirmed to hold for the currently-inspected vault/confidentialrelay/capabilities handlers in this codebase snapshot, since those use separate unbounded/independent maps rather than this shared-capacity cache. Absent that confirmation, exploitability is conditional on the specific handler wiring rather than proven end-to-end for a live, unauthenticated gateway route in this repo version.

### Recommendation
If/when a handler is wired to `common.RequestCache`, enforce a per-sender quota in addition to the global `maxCacheSize` (e.g., track counts per `sender` and cap concurrently pending entries per sender), or require an authenticated/rate-limited admission check (allowlist, JWT-based auth, or per-sender token bucket) upstream of `NewRequest` so identity cannot be freely re-minted to bypass isolation.

### Proof of Concept
Extend `core/services/gateway/handlers/common/requestcache_test.go`:
1. Create `cache := common.NewRequestCache[requestState](time.Hour, N)`.
2. Loop `N` times, each iteration generating a new random `sender` string and unique `MessageId`, calling `cache.NewRequest(...)`; assert all succeed.
3. Attempt one more `cache.NewRequest(...)` with a distinct, previously-unused `sender`/`MessageId` (representing a legitimate victim); assert it returns `"request cache is full"`.
4. This reproduces the existing `TestRequestCache_MaxSize` pattern but explicitly varying `sender` to show cross-tenant slot exhaustion rather than same-sender exhaustion.

func TestRequestCache_MaxSize(t *testing.T) {
	t.Parallel()

	cache := common.NewRequestCache[requestState](time.Hour, 2)
	callback := common.NewCallback()
	lggr := logger.Test(t)
	initialState := &requestState{}

	req := &api.Message{Body: api.MessageBody{MessageId: "aa", Sender: "0x1234"}}
	require.NoError(t, cache.NewRequest(lggr, req, callback, initialState))

	req.Body.MessageId = "bb"
	require.NoError(t, cache.NewRequest(lggr, req, callback, initialState))

	req.Body.MessageId = "cc"
	require.Error(t, cache.NewRequest(lggr, req, callback, initialState))
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
