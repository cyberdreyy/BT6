### Title
Permissionless `lending_pool_emissions_deposit` enables share-price inflation attack against first bank depositors - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
`lending_pool_emissions_deposit` lets **any signer** (not just a rewards distributor or admin) directly inflate a bank's `asset_share_value` by transferring extra tokens into the liquidity vault and recomputing `asset_share_value = (total_assets + amount) / total_asset_shares`. This is the same class of bug as the reported `updateTotalAssets()`/`payManagementFees()` inflation attack in Node.sol: any function that lets an outside caller push extra assets into the pool and recompute the share price based on the *current* (attacker-controlled, tiny) share supply enables a classic first-depositor inflation attack.

### Finding Description
`lending_pool_emissions_deposit` is guarded only by `depositor: Signer<'info>` with no ownership/admin constraint [1](#0-0) . Its only precondition is `total_asset_shares > 0` [2](#0-1) , and it directly manipulates the bank's `asset_share_value` global exchange rate:

```
let total_assets = bank.get_asset_amount(total_asset_shares)?;
let updated_total_assets = total_assets.checked_add(I80F48::from_num(amount))?;
bank.asset_share_value = updated_total_assets.checked_div(total_asset_shares)?.into();
``` [3](#0-2) 

Because `asset_share_value` is a single global scalar shared by every depositor in the bank (not a per-user preview), and because `get_asset_shares` divides the deposited value by this share value with no protection against rounding to zero [4](#0-3) , an attacker can:

1. Deposit a minimal amount into a freshly created (or currently empty) bank via `lending_account_deposit`, becoming (essentially) the sole depositor with `total_asset_shares ≈ 1` [5](#0-4) .
2. Call `lending_pool_emissions_deposit` with a large `amount` of the bank's own mint, which is permitted as long as the mint has no transfer fee/hook [6](#0-5) . This inflates `asset_share_value` by orders of magnitude relative to `total_asset_shares`.
3. When a legitimate depositor then calls `lending_account_deposit`, `bank_account.deposit()` converts their deposited value to shares via `get_asset_shares = value / asset_share_value` [7](#0-6) . Since `deposit.rs` never checks or rejects a zero (or near-zero) `share_amount`, a normal-sized deposit can round down to 0 shares, silently confiscating the depositor's principal into the attacker's inflated position.

This mirrors the report's root cause exactly: a function reachable by an unprivileged caller that recomputes a global share-price/`totalAssets` cache using attacker-supplied direct token transfers, with the share-supply small enough (attacker-controlled) to make the price manipulation cheap.

### Impact Explanation
A malicious actor can steal the first legitimate depositor's funds in a newly-created (or freshly-emptied/low-TVL) bank by manipulating `asset_share_value` through a nominally "permissionless emissions" instruction, redirecting value to themselves — a direct financial loss for victims and a durable corruption of the bank's share accounting (asset_share_value is a monotonically-tracked global rate used everywhere for health/liquidation calculations).

### Likelihood Explanation
The attack requires only: (1) being first/near-first depositor in a bank (trivial to front-run at bank creation, or applicable any time a bank's `total_asset_shares` becomes very small, e.g., after most depositors withdraw), and (2) holding/acquiring enough of the underlying mint to fund a large "emissions deposit," which is refunded to the attacker as inflated share value. No special permissions or admin role are needed to call `lending_pool_emissions_deposit`.

### Recommendation
- Require a minimum non-trivial `total_asset_shares`/`total_assets` threshold before allowing `lending_pool_emissions_deposit` to move the exchange rate (analogous to OZ's ERC4626 virtual-shares/dead-shares mitigation), or restrict the instruction to an authorized emissions/rewards distributor rather than any signer.
- Enforce a minimum-shares-minted check in `lending_account_deposit`/`increase_balance_internal` so that a deposit reverts (or is rejected) if it would mint zero shares for a non-zero token amount, preventing silent value loss regardless of how `asset_share_value` got inflated.
- Consider seeding new banks with locked "dead" shares at creation, as in the standard ERC4626 first-depositor mitigation.

### Proof of Concept
1. Group admin creates a new bank (or an existing bank empties out to near-zero `total_asset_shares`).
2. Attacker calls `lending_account_deposit(bank, amount=1)`, becoming sole depositor with `total_asset_shares ≈ 1`, `asset_share_value = 1`.
3. Attacker mints/holds a large amount of the bank's mint and calls `lending_pool_emissions_deposit(bank, amount=large_amount)` — no ownership check blocks this since `depositor` is any `Signer`. `asset_share_value` becomes `(1 + large_amount) / 1`.
4. Victim calls `lending_account_deposit(bank, amount=normal_deposit)`. `get_asset_shares(normal_deposit) = normal_deposit / asset_share_value` rounds to 0 (or near 0) because `asset_share_value` is now huge, so the victim's deposit accrues (near) no shares while their tokens remain in the vault, which the attacker can withdraw against their own inflated share.
