## Finding Assessment

Based on the evidence gathered, I have strong but not 100%-confirmed evidence of a critical gap. I could not retrieve the full body of `check_actor_permissions` (ran out of tool iterations), so I flag that specific point as needing final confirmation, but multiple independent sources in the codebase converge on the same conclusion.

### Title
Unauthorized rebind of a victim account's `AccountContract` to an attacker-chosen global contract via `Delegate`/`DelegateV2` targeting an arbitrary `receiver_id` — ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`action_use_global_contract` [1](#0-0)  mutates whatever account is passed to it as `account_id`/`account`, which `apply_action` sets to `receipt.receiver_id()` [2](#0-1) . Per the project's own action-semantics documentation, only `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount` are restricted to require `predecessor_id == receiver_id` (enforced via `check_actor_permissions`/`ActorNoPermission`); `UseGlobalContract` is not in that list [3](#0-2) , and the `ActorNoPermission` error kind's own comment repeats the same restricted set without `UseGlobalContract` [4](#0-3) .

### Finding Description
`apply_action` computes `account_id := receipt.receiver_id()` and `actor_id` (initially `predecessor_id`, only promoted to `receiver_id` after a preceding `CreateAccount`), then calls `check_account_existence` and `check_actor_permissions(action, account, actor_id, account_id)` before dispatching to `action_use_global_contract` [5](#0-4) . `action_use_global_contract`/`use_global_contract` itself performs no predecessor/receiver equality check at all — it simply looks up the `GlobalContractCode` trie key and rewrites `account.set_contract(...)` for whatever `account_id` it is given [6](#0-5) . `validate_use_global_contract_action`, invoked from `validate_action_with_mode`, only validates the identifier's own format, not any relationship between predecessor/receiver [7](#0-6) .

For `Delegate`/`DelegateV2`, `apply_delegate_action` builds the inner receipt with `predecessor_id: sender_id` (the `DelegateAction.sender_id`, whose access key was verified) and `receiver_id: delegate_action.receiver_id()` — an attacker-controlled field that is not required to equal `sender_id` [8](#0-7) . The only receiver-related checks performed are: the *outer* transaction's `receiver_id` must equal `delegate_action.sender_id` (`DelegateActionSenderDoesNotMatchTxReceiver`) [9](#0-8) , and (for function-call-permission keys only) the inner receiver must match the access key's allowed receiver. None of these checks constrain `delegate_action.receiver_id()` to equal `delegate_action.sender_id()` when a full-access key is used.

Consequently, an attacker who owns account `attacker.near` can:
1. Sign a `DelegateAction { sender_id: attacker.near, receiver_id: victim.near, actions: [UseGlobalContract{contract_identifier: <attacker's malicious global contract>}], ... }` with their own full-access key.
2. Wrap it in an outer transaction with `signer_id = attacker.near`, `receiver_id = attacker.near` (satisfying the sender/tx-receiver check), and submit/relay it themselves.
3. `apply_delegate_action` spawns a new receipt with `predecessor_id = attacker.near`, `receiver_id = victim.near`, containing the `UseGlobalContract` action.
4. This receipt passes `validate_receipt`/`validate_actions_with_mode` (receiver = `victim.near`, but no actor/predecessor check is performed for `UseGlobalContract`) [10](#0-9) .
5. On `victim.near`'s shard, `apply_action` runs with `account_id = victim.near`, `actor_id = attacker.near` (no preceding `CreateAccount` to promote actor_id), and if `check_actor_permissions` does not gate `UseGlobalContract` (consistent with the documented restricted-action list, which excludes it), the action executes and rebinds `victim.near`'s `AccountContract` to the attacker's chosen `GlobalContractIdentifier`, without any signature from `victim.near`'s keys.

This is corroborated by the codebase's own test, `test_use_global_contract_delegate`, which demonstrates `UseGlobalContract` being delivered via a `Delegate` action to a *different* account than the relayer, confirming the receiver of the inner receipt is attacker/sender-controlled and independent of who owns the account being rebound [11](#0-10) .

**Caveat on confirmation**: I was unable to retrieve the full body of `check_actor_permissions` in `runtime/runtime/src/actions.rs` before this analysis had to conclude. The conclusion that `UseGlobalContract` is *not* gated by this function rests on: (a) the explicit enumeration in `docs/RuntimeSpec/Actions.md` of the five actions requiring `predecessor_id == receiver_id`, which omits `UseGlobalContract`; and (b) the `ActorNoPermission` error's doc-comment in `errors.rs` listing the same five actions. If `check_actor_permissions` has since been silently extended to also cover `UseGlobalContract` without updating either of these two independent sources, the vulnerability would not be exploitable. This should be verified directly against `check_actor_permissions`'s match arms before treating this as fully confirmed.

### Impact Explanation
If confirmed, this allows any unprivileged account to overwrite the deployed-contract binding of **any other existing account** on the network to point at attacker-controlled global contract code (by `CodeHash` or `AccountId`), without ever touching the victim's access keys. This is a full authorization-escalation/account-takeover primitive: the victim's account would subsequently execute attacker-chosen WASM for all `FunctionCall`s, enabling theft of any funds/state the victim contract controls, arbitrary manipulation of its persistent storage, and drainage of user deposits held by that contract — squarely within "authorization escalation across accounts" and "theft of user funds."

### Likelihood Explanation
Preconditions are minimal for an unprivileged attacker: only an account with a full-access key and enough balance to cover the transaction/gas cost of a `Delegate` + `UseGlobalContract` receipt (no elevated permissions, no target-account cooperation, and no reliance on validator/node privilege). The attack is fully repeatable against any victim account and costs only ordinary gas/storage fees, assuming (subject to the caveat above) that `check_actor_permissions` truly does not restrict `UseGlobalContract` to `predecessor_id == receiver_id`.

### Recommendation
Add `UseGlobalContract` (and, if not already covered, verify `DeterministicStateInit`/other contract-rebinding actions) to the restricted-action set enforced in `check_actor_permissions`, requiring `actor_id == account_id` (or a preceding successful `CreateAccount` in the same receipt) before `action_use_global_contract` is allowed to mutate an account's `AccountContract`. Additionally, add a defensive check inside `action_use_global_contract`/`use_global_contract` itself so the invariant does not depend solely on the caller.

### Proof of Concept
Extend `test_use_global_contract_delegate` in `test-loop-tests/src/tests/global_contracts.rs` [11](#0-10) :
1. Deploy a global contract A (benign) and global contract B (attacker-controlled, distinguishable behavior/log).
2. Create `victim` account (unrelated to attacker), and have `victim` legitimately `UseGlobalContract(A)` via its own signed transaction, verifying via `view_call_global_contract`/`view_code` that it currently runs contract A.
3. As `attacker` (a separate, unprivileged account), sign a `DelegateAction { sender_id: attacker, receiver_id: victim, actions: [UseGlobalContract(B)] }` with attacker's own full-access key; wrap in an outer transaction `signer_id = attacker, receiver_id = attacker`; submit/relay it.
4. Run the test loop, then call `view_code`/`view_call_global_contract` on `victim` and assert its bound contract now resolves to `B` (attacker's), and that no action/receipt was rejected with `ActorNoPermission`.
5. Expected (fixed) behavior: the receipt fails with `ActorNoPermission { account_id: victim, actor_id: attacker }`, and `victim`'s contract binding remains `A`.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())

fn validate_delegate_action(
    limit_config: &LimitConfig,
    delegate_action: VersionedDelegateActionRef<'_>,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ActionsValidationError> {
    // Check the count before `get_actions()` clones the list, so a huge
    // nested-action list can't force the allocation before being rejected.
    // Consensus-neutral: same `TotalNumberOfActionsExceeded` as the check in
    // `validate_actions_with_mode` below.
    let num_actions = delegate_action.actions().len() as u64;
    if num_actions > limit_config.max_actions_per_receipt {
        return Err(ActionsValidationError::TotalNumberOfActionsExceeded {
            total_number_of_actions: num_actions,
            limit: limit_config.max_actions_per_receipt,
        });
    }
    let actions = delegate_action.get_actions();
    let inner_receiver =
        if ProtocolFeature::FixDelegatedDeterministicStateInit.enabled(current_protocol_version) {
            // This is the correct receiver id to use for the check.
            delegate_action.receiver_id()
        } else {
            // This is a bug fixed with `FixDelegatedDeterministicStateInit` that
            // validated against the wrong id. This makes it impossible to
            // initialize deterministic accounts from meta transactions.
            // The bug cannot be abused, if someone crafts a state init that passes
            // validation here, it will fail when it is checked as incoming receipt.
            receiver
        };
    validate_actions_with_mode(
        limit_config,
        &actions,
        inner_receiver,
        current_protocol_version,
        mode,
    )?;
    Ok(())
