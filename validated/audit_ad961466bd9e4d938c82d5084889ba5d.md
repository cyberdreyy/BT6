### Title
Cross-epoch instant-withdraw receipts escape the default haircut and drain funded claims - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The dnsmasq bug class is a missing bounds check: the attacker makes the parser read past the allocated packet buffer. The vault analog is an epoch-keyed lookup with an implicit bound of "current epoch only": `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest` only consult `instantWithdrawClaimsByEpoch[epochNumber]` / `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`. Instant receipts recorded in an earlier epoch are "out of bounds" — they are excluded from the recovery basis, never haircut, and later paid at par by `claimInstantWithdrawRequest` out of underlyings that fund other users.

### Finding Description
`requestInstantWithdraw` records receipts per epoch (`instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`) but `pendingInstantWithdraws` is a global aggregate [1](#0-0) . If the borrower underfunds an epoch, `pendingInstantWithdraws` survives `stopEpoch` and carries receipts from epoch E1 into E2.

At default finalization, `defaultPendingClaimBasis` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the current epoch's bucket — so epoch-E1 instant claims are missing from `totalBasis` [2](#0-1) . Likewise `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` [3](#0-2) . After finalization, `claimInstantWithdrawRequest` burns and pays the *aggregate* `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim` [4](#0-3) .

`_transferFundedClaim`'s guard only protects `defaultRecoveryReserve`; it does not prevent an unfunded receipt from consuming underlyings collected for other users' funded claims [5](#0-4) . The same under-accounting applies in `_defaultPrefundedInstantReserve`, which compares `instantBasis` of only the current epoch against the global `pendingInstantWithdraws` [6](#0-5) .

### Impact Explanation
A user holding an instant-withdraw receipt from epoch E1 (never funded by the borrower) waits for default to be finalized in epoch E2. Their receipt was excluded from `totalBasis`, so `defaultRecoveryPrice` is higher than it should be — other claimants' recovery ratio is diluted — and the attacker then calls `claimInstantWithdrawRequest` (through the CDO) and is paid 1:1 from strategy-held underlyings backing other users' funded receipts. Direct theft up to the attacker's stale instant-receipt amount, bounded by the non-reserve balance. Alternatively, if no excess balance exists, the claim permanently reverts (`balance - reserve < _amount`), permanently freezing the receipt — both are accepted impact classes.

### Likelihood Explanation
Requires: instant-withdraw enabled vault, an unprivileged user requesting an instant withdraw in E1, honest borrower underfunding instant claims at that stopEpoch (pendingInstantWithdraws stays >0 across the boundary), and a subsequent borrower default finalized in E2 ≥ E1+1. All privileged actors remain honest; only ordinary sequencing of `stopEpoch`/`_handleBorrowerDefault`/`finalizeDefaultRecovery` is needed. The attacker is just an epoch-tranche-token holder requesting an instant withdraw.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, account for all outstanding instant claims, not only `instantWithdrawClaimsByEpoch[epochNumber]` — e.g. track a global `instantWithdrawClaims` aggregate (or iterate/accumulate per-epoch buckets) so that `pendingInstantWithdraws != 0` always implies the full claim set joins `totalBasis`. In `_claimDefaultedInstantWithdrawRequest`, haircut the user's entire `instantWithdrawsRequests[_user]` balance (or every epoch bucket), not only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// 1. Enable instant withdraws: cdoEpoch.setInstantWithdrawParams(delay, min, true)
// 2. Attacker deposits AA, calls requestInstantWithdraw in epoch E1.
//    pendingInstantWithdraws = X, instantWithdrawsRequestsByEpoch[attacker][E1] = X.
// 3. Honest borrower underfunds: stopEpoch runs but collectInstantWithdrawFunds
//    pulls < X (or 0), so pendingInstantWithdraws == X persists into E2.
// 4. Epoch E2 runs; borrower defaults -> cdoEpoch defaulted; owner/manager calls
//    finalizeDefault -> strategy.finalizeDefaultRecovery(recovered, source).
//    defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[E2]
//    which omits attacker's E1 receipt X -> defaultRecoveryPrice is overstated.
// 5. defaultInstantWithdrawsFinalized == true, but
//    _claimDefaultedInstantWithdrawRequest clears only epoch-E2 receipts
//    (instantWithdrawsRequestsByEpoch[attacker][E2] == 0), leaving
//    instantWithdrawsRequests[attacker] == X intact.
// 6. Attacker calls cdoEpoch.claimInstantWithdrawRequest -> burns X and
//    _transferFundedClaim pays X at par from strategy balance belonging to
//    other users' funded claims (guard only excludes defaultRecoveryReserve).
// assert: attacker received X underlying despite defaultRecoveryPrice < 1e18,
//         while honest claimants' reserve/funded balance is short by X.
```

Uncertainty note: this hinges on `IdleCDOEpochVariant` allowing `pendingInstantWithdraws` to remain nonzero across a `stopEpoch` (borrower underfunding instant claims rather than reverting the stop). I could not fully verify the CDO-side instant-funding path within the available search budget; if `stopEpoch` hard-reverts on unfunded instant withdrawals, the precondition collapses and no valid analog stands.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
