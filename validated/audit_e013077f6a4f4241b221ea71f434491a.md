### Title
Pending-validator stake dilutes active-validator voting power before admission, causing unfair ejection — (`File: crates/sui-framework/packages/sui-system/sources/validator_set.move`)

---

### Summary

In `update_validator_positions_and_calculate_total_stake`, the `initial_total_stake` denominator used to evaluate whether **existing active validators** should be kicked out includes the stake of **pending validators who have not yet been admitted**. If those pending validators subsequently fail the epoch-end re-admission check, their stake is subtracted from the final total, but the active validators that were already ejected are not reinstated. This is the Sui analog of the SEDA M-11 root cause: a new participant's stake is counted in the total before it is confirmed that the participant will actually join, causing existing participants to be penalized against an inflated denominator.

---

### Finding Description

`advance_epoch` calls `update_validator_positions_and_calculate_total_stake` after processing pending stake deposits. Inside that function:

```move
// Note: we count the total stake of pending validators as well!
let pending_total_stake = calculate_total_stakes(&pending_active_validators);
let initial_total_stake = calculate_total_stakes(&self.active_validators) + pending_total_stake;
``` [1](#0-0) 

`initial_total_stake` is then used to compute the voting power of every **active** validator for the purpose of the SIP-39 low-stake ejection check:

```move
let voting_power = voting_power::derive_raw_voting_power(
    validator_stake,
    initial_total_stake,   // inflated by pending validators
);
``` [2](#0-1) 

The same `initial_total_stake` is later used to re-check whether each pending validator still qualifies to join:

```move
let voting_power = voting_power::derive_raw_voting_power(
    validator_stake,
    initial_total_stake,
);
if (voting_power >= min_joining_voting_power_threshold) {
    validator.activate(ctx.epoch()); ...
} else {
    self.validator_candidates.add(validator.sui_address(), validator.wrap_v1(ctx));
    total_removed_stake = total_removed_stake + validator_stake;
}
``` [3](#0-2) 

The ordering is critical: **active validators are ejected first, then pending validators are admitted or rejected**. If a pending validator fails the re-check, its stake is subtracted from `total_removed_stake` and the final `new_total_stake` is corrected — but the active validators that were already ejected are not restored.

The admission gate `can_join`, called at `request_add_validator` time, uses only `self.total_stake` (the previous epoch's total, not including other pending validators):

```move
let future_total_stake = self.total_stake + stake;
let future_validator_voting_power = voting_power::derive_raw_voting_power(
    stake,
    future_total_stake,
);
future_validator_voting_power >= min_joining_voting_power
``` [4](#0-3) 

Because `can_join` ignores other pending validators, N candidates can each individually pass the gate while their combined stake at epoch end inflates `initial_total_stake` enough to push active validators below `very_low_voting_power_threshold`, even if all N pending validators subsequently fail the epoch-end re-check.

---

### Impact Explanation

An active validator whose raw voting power is near `very_low_voting_power_threshold` (1 bp in phase 3) is ejected immediately and involuntarily. Its staking pool is moved to `inactive_validators`; delegators lose one epoch of staking rewards and must wait until the next epoch to withdraw or re-delegate. If the pending validators that caused the dilution all fail the re-check, the ejection was entirely spurious — the final `new_total_stake` is the same as if the pending validators had never existed, yet the active validator is gone. This constitutes harmful smart-contract behavior reachable from public input.

---

### Likelihood Explanation

Any SUI holder can call `request_add_validator_candidate`, stake, and call `request_add_validator`. In phase 3 (the steady-state phase), `min_joining_voting_power = 3 bp`, so each pending validator needs roughly `0.03 %` of the current total stake. The attacker's stake is returned to the candidate pool if the re-check fails, so the only cost is gas and one epoch of opportunity cost. The attack is most effective against validators whose voting power is exactly at `very_low_voting_power_threshold` (1 bp), because integer truncation in `derive_raw_voting_power` drops them to 0 with any increase in the denominator.

---

### Recommendation

Evaluate active validators against a denominator that excludes pending validators whose admission is not yet confirmed. One approach is a two-pass algorithm: first determine which pending validators will be admitted (using only `calculate_total_stakes(&self.active_validators) + pending_total_stake` for the pending-validator check), then re-compute `initial_total_stake` using only the admitted pending validators before running the active-validator ejection loop. Alternatively, `can_join` should account for already-queued pending validators so that the gate and the epoch-end re-check use consistent denominators.

---

### Proof of Concept

Setup (phase 3, `very_low_voting_power_threshold = 1`, `min_joining_voting_power_threshold = 3`):

- 10 active validators each with stake `1 000 SUI` → `self.total_stake = 10 000 SUI`
- Active validator A has stake `1 SUI` → raw VP = `1 * 10000 / 10001 = 0`... actually let's use a cleaner example.

Let `self.total_stake = 10 000 000 SUI`. Active validator A has stake `1 001 SUI` → raw VP = `floor(1001 * 10000 / 10 001 001) = 1` (exactly at `very_low_voting_power_threshold`).

Attacker creates 100 pending validators each with stake `3 001 SUI`:
- `can_join` check per candidate: `floor(3001 * 10000 / (10 000 000 + 3001)) = floor(30 010 000 / 10 003 001) = 3` ✓ each passes.

At epoch end, `initial_total_stake = 10 001 001 + 100 * 3001 = 10 301 101 SUI`.

Active validator A's VP: `floor(1001 * 10000 / 10 301 101) = floor(10 010 000 / 10 301 101) = 0` → **ejected immediately**.

Each pending validator's VP: `floor(3001 * 10000 / 10 301 101) = floor(30 010 000 / 10 301 101) = 2` < 3 → **all 100 fail the re-check and are returned to the candidate pool**.

Final `new_total_stake = 10 301 101 − 100 * 3001 − 1001 = 10 000 000 − 1001 = 9 998 999 SUI`. The network ends up without validator A, even though A would have survived if no pending validators had been queued. [5](#0-4)

```text
fun update_validator_positions_and_calculate_total_stake(
    self: &mut ValidatorSet,
    low_stake_grace_period: u64,
    validator_report_records: &mut VecMap<address, VecSet<address>>,
    ctx: &mut TxContext,
): u64 {
    // take all pending validators out of the tablevec and put them in a local vector
    let pending_active_validators = vector::tabulate!(
        self.pending_active_validators.length(),
        |_| self.pending_active_validators.pop_back(),
    );

    // Note: we count the total stake of pending validators as well!
    let pending_total_stake = calculate_total_stakes(&pending_active_validators);
    let initial_total_stake = calculate_total_stakes(&self.active_validators) + pending_total_stake;
    let (
        min_joining_voting_power_threshold,
        low_voting_power_threshold,
        very_low_voting_power_threshold,
    ) = self.get_voting_power_thresholds(ctx);
    // Iterate through all the active validators, record their low stake status, and kick them out if the condition is met.
    let mut total_removed_stake = 0; // amount of stake to remove due to departed_validators
    let mut i = self.active_validators.length();
    while (i > 0) {
        i = i - 1;
        let validator_ref = &self.active_validators[i];
        let validator_address = validator_ref.sui_address();
        let validator_stake = validator_ref.total_stake();

        // calculate the voting power for this validator in the next epoch if no validators are removed
        // if one of more low stake validators are removed, it's possible this validator will have higher voting power--that's ok.
        let voting_power = voting_power::derive_raw_voting_power(
            validator_stake,
            initial_total_stake,
        );

        // SIP-39: a validator can remain indefinitely with a voting power ≥ LOW_VOTING_POWER_THRESHOLD
        if (voting_power >= low_voting_power_threshold) {
            // The validator is safe. We remove their entry from the at_risk map if there exists one.
            if (self.at_risk_validators.contains(&validator_address)) {
                self.at_risk_validators.remove(&validator_address);
            }
            // SIP-39: as soon as the validator’s voting power falls to VERY_LOW_VOTING_POWER_THRESHOLD,
            //      they are on probation and must acquire sufficient stake to recover to voting power
        } else if (voting_power >= very_low_voting_power_threshold) {
            // The stake is a bit below the threshold so we increment the entry of the validator in the map.
            let new_low_stake_period = if (self.at_risk_validators.contains(&validator_address)) {
                let num_epochs = &mut self.at_risk_validators[&validator_address];
                *num_epochs = *num_epochs + 1;
                *num_epochs
            } else {
                self.at_risk_validators.insert(validator_address, 1);
                1
            };

            // If the grace period has passed, the validator has to leave us.
            if (new_low_stake_period > low_stake_grace_period) {
                let validator = self.active_validators.remove(i);
                let removed_stake = self.process_validator_departure(
                    validator,
                    validator_report_records,
                    false, // the validator is kicked out involuntarily
                    ctx,
                );
                total_removed_stake = total_removed_stake + removed_stake;
            }
            // SIP-39: at the end of an epoch when new voting powers are computed based on stake changes,
            //      any validator with VOTING_POWER < VERY_LOW_VOTING_POWER_THRESHOLD will be removed
        } else {
            // The validator's stake is lower than the very low threshold so we kick them out immediately.
            let validator = self.active_validators.remove(i);
            let removed_stake = self.process_validator_departure(
                validator,
                validator_report_records,
                false, // the validator is kicked out involuntarily
                ctx,
            );
            total_removed_stake = total_removed_stake + removed_stake;
        }
    };
    // check that pending validators still have sufficient stake to be added. this was checked at
    // the time of request_add_validator, but stake may have been withdrawn, or stakes of other
    // validators may have increased significantly
    pending_active_validators.do!(|mut validator| {
        let validator_stake = validator.total_stake();
        let voting_power = voting_power::derive_raw_voting_power(
            validator_stake,
            initial_total_stake,
        );
        if (voting_power >= min_joining_voting_power_threshold) {
            validator.activate(ctx.epoch());
            event::emit(ValidatorJoinEvent {
                epoch: ctx.epoch(),
                validator_address: validator.sui_address(),
                staking_pool_id: validator.staking_pool_id(),
            });
            self.active_validators.push_back(validator);
        } else {
            // return validator object to the candidate pool. want to do this directly instead of
            // calling request_add_validator_candidate because staking_pool_mappings already has an
            // entry for this validator, and the duplicate checks are redundant
            self.validator_candidates.add(validator.sui_address(), validator.wrap_v1(ctx));
            total_removed_stake = total_removed_stake + validator_stake;
        }
    });

    // new total stake is the initial total minus the amount removed via validators we kicked out
    initial_total_stake - total_removed_stake
}
