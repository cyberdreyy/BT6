### Title
actor_id escalation to a `0s` deterministic account via implicit-transfer creation path bypasses actor-permission checks - ([File: runtime/runtime/src/actions.rs])

### Summary
`action_implicit_account_creation_transfer` unconditionally sets `*actor_id = account_id.clone()` at line 224 before branching on `account_id.get_account_type()`, so this reassignment also applies to `AccountType::NearDeterministicAccount` at line 262 [1](#0-0) . This directly contradicts the security invariant documented in `create_deterministic_account`, which states the actor_id must remain the predecessor to prevent hijacking a code-only deterministic account [2](#0-1) .

### Finding Description
`create_deterministic_account` (called both from `action_deterministic_state_init` for the canonical `DeterministicStateInitAction` path, and from `action_implicit_account_creation_transfer` for the implicit-transfer path) is documented as never changing `actor_id`, explicitly to prevent `AddKey`/`DeployContract` from being authorized against the newly created account rather than the true predecessor [3](#0-2) .

However, in `action_implicit_account_creation_transfer`, the line `*actor_id = account_id.clone();` executes unconditionally before the `match account_id.get_account_type()` branch, affecting all three implicit account types (`NearImplicitAccount`, `EthImplicitAccount`, and `NearDeterministicAccount`) [4](#0-3) . For `NearImplicitAccount` and `EthImplicitAccount`, setting `actor_id = account_id` is correct/expected since those accounts get a full-access key or a global contract that is meant to represent an owned account. But for `AccountType::NearDeterministicAccount`, the resulting account has `AccountContract::None` and no access keys at all — it is meant to be strictly code-controlled via the separate `DeterministicStateInitAction` mechanism, which deliberately never elevates `actor_id`.

If a receipt's action list is `[Transfer(receiver=0s_id, deposit), AddKey(0s_id, pk, FullAccess)]`, the `Transfer` action (which triggers `action_implicit_account_creation_transfer` on first-touch of an implicit/deterministic account) sets `actor_id = 0s_id` as a side effect. Any subsequent action in the same receipt's action list evaluated against `check_actor_permissions` would then see `actor_id == account_id == 0s_id`, i.e., the actor appears to be the account owner rather than the predecessor.

### Impact Explanation
This is a genuine logic inconsistency between two code paths that are supposed to enforce the same invariant (actor_id must remain predecessor for deterministic accounts). If exploitable, it would allow an unprivileged predecessor to self-authorize `AddKey`/`DeployContract` actions against a `0s` deterministic account it does not otherwise own, installing a `FullAccess` key on an account meant to be code-only — an authorization-escalation bug matching the "Unauthorized transaction" bounty category.

### Likelihood Explanation
I could not fully verify within the available exploration whether `check_actor_permissions` for the batched `AddKey` action actually reads the `actor_id` value produced after the preceding `Transfer` action within the same receipt/action loop (I was not able to inspect the full `apply_action`/`apply_action_result` loop in `runtime/runtime/src/lib.rs` before the tool budget ran out), nor whether other validation (e.g., `check_account_existence`, action-batch ordering, or a check specific to deterministic accounts) prevents an `AddKey` from targeting a `0s` account at all. The code at `actions.rs:224-267` is unambiguous, and it does contradict the invariant documented for deterministic accounts, but I cannot confirm without seeing the sequential action-application loop and `check_actor_permissions` implementation whether the escalated `actor_id` is actually consumed by a later action in the same receipt, or whether it is reset/re-derived per action from the receipt's predecessor rather than carried as mutable state across actions.

### Recommendation
In `action_implicit_account_creation_transfer`, move the `*actor_id = account_id.clone();` assignment so it only executes for `AccountType::NearImplicitAccount` and `AccountType::EthImplicitAccount`, excluding `AccountType::NearDeterministicAccount`, to match the documented invariant in `create_deterministic_account`.

### Proof of Concept
Add a runtime/apply integration test (e.g. in `runtime/runtime/src/tests/apply.rs`) submitting a single receipt with actions `[Transfer(receiver=0s_id, deposit), AddKey(0s_id, attacker_pubkey, FullAccess)]` where `0s_id` is a valid deterministic account id derived from some code hash, sent from an ordinary funded predecessor account. Assert:
1. Before the fix, the `AddKey` action succeeds (no `ActionErrorKind::AddKeyAlreadyExists`/`NotAllowed`-type error) and a `FullAccess` key is persisted under `0s_id`.
2. Confirm this key is never produced by the `DeterministicStateInitAction` path (`action_deterministic_state_init` / `deploy_deterministic_account`), which only sets contract code and data, never access keys.
3. After the fix (scoping the `actor_id` assignment away from `NearDeterministicAccount`), assert `AddKey` fails with an actor-permission error since `actor_id` remains the original predecessor.

pub(crate) fn action_implicit_account_creation_transfer(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    fee_config: &RuntimeFeesConfig,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    account_id: &AccountId,
    deposit: Balance,
    block_height: BlockHeight,
    epoch_info_provider: &dyn EpochInfoProvider,
) {
    *actor_id = account_id.clone();
    match account_id.get_account_type() {
        AccountType::NearImplicitAccount => {
            let mut access_key = AccessKey::full_access();
            access_key.nonce = initial_nonce_value(block_height);

            // unwrap: here it's safe because the `account_id` has already been determined to be implicit by `get_account_type`
            let public_key = PublicKey::from_near_implicit_account(account_id).unwrap();

            *account = Some(Account::new(
                deposit,
                Balance::ZERO,
                AccountContract::None,
                fee_config.storage_usage_config.num_bytes_account
                    + public_key.trie_id_len() as u64
                    + borsh::object_length(&access_key).unwrap() as u64
                    + fee_config.storage_usage_config.num_extra_bytes_record,
            ));

            set_access_key(state_update, account_id.clone(), public_key, &access_key);
        }
        // Invariant: The `account_id` is implicit.
        // It holds because in the only calling site, we've checked the permissions before.
        AccountType::EthImplicitAccount => {
            let chain_id = epoch_info_provider.chain_id();

            // Use a deployed global contract for ETH implicit accounts.
            let global_contract_hash = eth_wallet_global_contract_hash(&chain_id);
            let storage_usage = fee_config.storage_usage_config.num_bytes_account

            *account = Some(Account::new(
                deposit,
                Balance::ZERO,

pub(crate) fn create_deterministic_account(
    initial_balance: Balance,
    storage_usage_config: &StorageUsageConfig,
) -> Account {
    // Unlike `CreateAccount`, this account creation does not change
    // actor_id. This is important to prevent hijacking the account.
    // Actor id remains the predecessor, so any actions following will
    // be checked against that for actor permissions, preventing
    // `AddKey`, `DeployContract`, or any other actions that only the
    // account owner is permitted to do.
    Account::new(
        initial_balance,
        Balance::ZERO,
        AccountContract::None,
        storage_usage_config.num_bytes_account,
    )
}
