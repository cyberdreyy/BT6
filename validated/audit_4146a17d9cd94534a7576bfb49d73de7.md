### Title
Missing rate limiting/allowlist check on legacy `web_api_trigger` user messages allows unprivileged flooding of an entire DON - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The SEDA bug allowed an unprivileged actor to flood validators with free, unmetered `CommitDataResult`/`RevealDataResult` messages because the AnteHandler exempted them from gas checks without any anti-duplication or throughput safeguard. The Chainlink Gateway has an analogous unmetered fan-out path: legacy `web_api_trigger` messages processed by `handler.HandleLegacyUserMessage` are broadcast to every member of a DON with **no rate limiting and no allowlist check**, a gap the code itself flags with an unaddressed `TODO`.

### Finding Description
Gateway user requests reach the handler in two ways: modern JSON-RPC (`HandleJSONRPCUserMessage`) and legacy (`HandleLegacyUserMessage`). For legacy requests, `gateway.ProcessRequest` only validates the JSON-RPC envelope and structural message fields (`msg.Validate()`) before invoking the handler [1](#0-0) . It performs no per-sender or global rate limiting for this path, unlike other request flows in the same package that use `globalNodeRateLimiter`/`perNodeRateLimiters`/`incomingRateLimiter` [2](#0-1) [3](#0-2) .

Inside `HandleLegacyUserMessage`, the code explicitly documents the missing control:
```go
// TODO: apply allowlist and rate-limiting here
if msg.Body.Method != MethodWebAPITrigger {
``` [4](#0-3) 

After this check, every valid `web_api_trigger` message is stored in `savedCallbacks` and forwarded to **every member of the DON** via `don.SendToNode`, regardless of how many identical or near-identical messages a single unauthenticated caller has already sent: [5](#0-4) 

`msg.Validate()`/`ValidatedMessageFromReq` only checks structural correctness (JSON-RPC version, method presence, params presence) — it does not authenticate the sender or enforce any per-sender quota [6](#0-5) . This mirrors the SEDA root cause: a check exists (`checkFreeGas`/`msg.Validate`) that lets a message class bypass metering, but nothing prevents repeated submission of the same unmetered request by an unprivileged actor.

By contrast, the newer JSON-RPC/v2 gateway path (`http_handler.go`, `outgoing_connector_handler.go`) and even the confidential-relay handler (`TestConfidentialRelayHandler_DuplicateRequestID`) do enforce global/per-node rate limits and duplicate-request-ID rejection [7](#0-6) , showing the legacy web-API trigger path is an outlier that was never hardened, as also called out in the still-pending test TODO: "Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated" [8](#0-7) .

### Impact Explanation
An unprivileged external caller can repeatedly submit legacy `web_api_trigger` gateway messages (each with a unique message ID to avoid `savedCallbacks` de-duplication, or even identical bodies since the map keys on message ID, not sender). Each request is fanned out to every node in the DON, consuming node processing time, HTTP client resources on each node, and gateway memory (`savedCallbacks` entries pruned only periodically). Under sustained flooding this degrades or denies availability of the Gateway/DON message-handling path to legitimate workflow triggers, analogous to the SEDA validator DOS caused by unmetered commit/reveal flooding.

### Likelihood Explanation
The `HandleLegacyUserMessage` path is reachable directly from any external client capable of sending a JSON-RPC request to the Gateway's HTTP endpoint with the legacy `DonId` field set — no signature-based authorization of the caller (only of DON-to-gateway node responses) is enforced before broadcast. The missing rate limiting is explicitly acknowledged as an unresolved `TODO` in production code, indicating high likelihood of exploitability given no additional network-layer or operator-only precondition is required.

### Recommendation
Add sender-based and/or global rate limiting (reusing the existing `ratelimit.RateLimiter`/`limits.RateLimiter` infrastructure already used elsewhere in the gateway package) and an allowlist check to `HandleLegacyUserMessage` before messages are saved to `savedCallbacks` and fanned out to DON members, matching the protections already present in the v2 JSON-RPC handlers and confidential-relay handler.

### Proof of Concept
Not applicable — no PoC was executed; this analysis is based on static code review of the reachable, unauthenticated legacy trigger path and its explicit absence of rate limiting/allowlist enforcement.

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}
