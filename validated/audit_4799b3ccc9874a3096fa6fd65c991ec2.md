This confirms the vulnerability pattern in `multisig/src/lib.rs`. The `DeleteKey` action (lines 198-216) only purges requests where `r.signer_pk == pk` (i.e., requests that the deleted key itself *submitted*), but the `confirmations` `HashSet<PublicKey>` for *other* outstanding requests (submitted by different keys but confirmed by the now-deleted key) is never cleaned up. ### Title
Stale confirmations from revoked/deleted multisig keys still count toward `num_confirmations`, allowing execution below threshold - (File: multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm` (multisig/src/lib.rs:248-266) authorizes execution of a request purely by counting the size of the `confirmations: HashSet<PublicKey>` stored for that `request_id`, without re-validating that each public key in that set is still an active/authorized key on the contract at confirmation time. When a key is removed via the `DeleteKey` request action (multisig/src/lib.rs:198-216), the code only purges requests that the *deleted key itself created* (`r.signer_pk == pk`), never removing that key's confirmations from *other* pending requests it had confirmed. The identical logic is duplicated in `multisig2/src/lib.rs` (`delete_member`, lines 356-379), which filters solely on `r.member == member`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The binding this contract is supposed to maintain is:
`num_confirmations_counted == num_confirmations_by_currently_authorized_keys`

Scenario:
1. Contract initialized with `num_confirmations = 3` and keys `{K1, K2, K3, K4}`.
2. K1 calls `add_request` to create request `R` (`R.signer_pk = K1`).
3. K2 calls `confirm(R)` — since `1 < 3`, K2's public key is added to `confirmations[R]` (now `{K2}`), and the promise is not yet executed. `confirmations.len() == 1`.
4. Separately, the multisig legitimately revokes K2 (e.g., compromised key) by executing a `DeleteKey{ public_key: K2 }` request. The `execute_request` handler for `DeleteKey` (lines 198-216) removes K2's access key and cleans up any requests *where `r.signer_pk == K2`* — but request `R` was created by K1, not K2, so `R` and its `confirmations` set (still containing K2) are left untouched.
5. Now only K1, K3, K4 are valid keys. K1 calls `confirm(R)`: `confirmations.len() (1, from stale K2) + 1 >= 3` is true, so `R` executes with only 2 genuinely live-key confirmations (K1 and the ghost K2), one short of the intended 3-of-n threshold.

This breaks the equality between "confirmations counted" and "confirmations from live members," exactly the class of accounting error described in the report (where a filled/removed portion of state is not properly propagated to a dependent counter).

### Impact Explanation
This allows a `MultiSigRequest` — which can include `Transfer`, `FunctionCall`, `AddKey`/`DeleteKey`, `DeployContract`, etc. — to execute having received fewer authorizations from currently-live keys than `num_confirmations` requires. This is a direct violation of the "multisig request executed below threshold" Critical impact category: funds can be transferred, or the multisig's own access/config can be altered, without the intended quorum of live signers.

### Likelihood Explanation
The trigger conditions are entirely within the ordinary key-rotation/security-hygiene workflow of a multisig: revoking a compromised or departing key while other requests are pending confirmation from it. No attacker exploit beyond normal operational sequencing (existing outstanding request + confirm-then-revoke ordering) is required; the compromised/departing keyholder needs no special privilege beyond having previously confirmed a request that is still open when they are removed.

### Recommendation
When removing a key/member (`DeleteKey` in `multisig/src/lib.rs`, `delete_member`/`DeleteKey` in `multisig2/src/lib.rs`), also strip that key from every outstanding request's `confirmations` set (not just requests it originally submitted), e.g., iterate `self.confirmations` and call `.remove(&pk)` on each set, or re-derive `confirmations.len()` in `confirm()` by intersecting against the currently valid key/member set instead of trusting the raw stored `HashSet` size.

### Proof of Concept
1. `new(num_confirmations: 3)` with keys `K1..K4` (assume `AddKey` already used to add K2-K4).
2. `K1: add_request(request=R)` → `R.signer_pk = K1`, `confirmations[R] = {}`.
3. `K2: confirm(request_id=R)` → `confirmations[R] = {K2}` (size 1 < 3, not yet executed).
4. `K1 (with confirmations from others): add_request_and_confirm({DeleteKey{public_key: K2}})` executes (assuming this reaches threshold through separate confirmations not involving K2) → K2's access key deleted; only requests with `signer_pk == K2` are purged; `R` (signer_pk = K1) and its `confirmations[R] = {K2}` remain in state.
5. `K1: confirm(request_id=R)` → `confirmations.len()=1 + 1 = 2 >= 3`? False here with example numbers — demonstrate with `num_confirmations=2` instead: after step 3, `confirmations[R]={K2}` size 1; `1+1=2>=2` true even with only K1 as a live confirmer plus the ghost K2's stale entry → `execute_request(R)` runs, moving funds/actions with only one genuinely live confirming key instead of two.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
