### Title
Unbounded `Vec<u8>` allocation via unmodified `bincode::deserialize` in `parse_bpf_upgradeable_loader` / `parse_bpf_loader` - (File: `transaction-status/src/parse_bpf_loader.rs`)

### Summary
`parse_bpf_upgradeable_loader` and `parse_bpf_loader` deserialize `instruction.data` with raw `bincode::deserialize`, which has no size limit configured, unlike the on-chain execution path that uses `limited_deserialize` bounded by `PACKET_DATA_SIZE`. An attacker can craft a `Write { offset, bytes: Vec<u8> }` instruction whose encoded length prefix for `bytes` claims an enormous size (up to `u64::MAX`) while the actual instruction bytes are tiny; when this transaction is later fetched via `getTransaction`/`getBlock` with `jsonParsed` encoding, the parser attempts to allocate a `Vec<u8>` sized to the claimed (attacker-controlled) length before any bounds check against the real remaining buffer occurs.

### Finding Description

and for the legacy loader: [2](#0-1) 

Both use the bare `bincode::deserialize` function imported at the top of the file (`use bincode::deserialize;`) with no `Bounded`/size-limit `Options` configured: [3](#0-2) 

This contrasts with the actual on-chain instruction processor, which deliberately bounds the same deserialization to `PACKET_DATA_SIZE` via `solana_bincode::limited_deserialize`: [4](#0-3) 

When `serde`'s `Vec<T>::deserialize` runs against a bincode deserializer, the visitor calls `Vec::with_capacity(seq.size_hint().unwrap_or(0))` before consuming any elements; bincode's `size_hint`/element-count comes directly from the untrusted 8-byte little-endian length prefix encoded in the instruction data, not from the actual number of bytes remaining in the buffer. Because `bincode::deserialize` (unlike `limited_deserialize`) has no configured byte-length limit, this pre-allocation attempt is not rejected before the allocation is requested — it is only after the (attempted) allocation that bincode would notice there isn't enough remaining data and return an `Err`.

An attacker builds a transaction whose compiled instruction is addressed to `bpf_loader_upgradeable::id()` (or `bpf_loader::id()`) with data crafted to look like a serialized `UpgradeableLoaderInstruction::Write { offset, bytes }`, where the serialized `bytes` length prefix is set to `u64::MAX` (or another astronomically large value) while the actual trailing byte payload is empty/small. The transaction does not need to succeed at runtime — the runtime's own bounded `limited_deserialize` in `programs/bpf_loader/src/lib.rs` would reject or safely error on such data, but that only affects execution result, not storage: the transaction (with its raw instruction bytes) is still recorded in the blockstore/transaction-status store regardless of execution outcome. Later, any unprivileged client can call `getTransaction` or `getBlock` with `encoding: jsonParsed`, which routes through `transaction_status::parse_instruction::parse` to `parse_bpf_upgradeable_loader`/`parse_bpf_loader`, reproducing the oversized allocation attempt purely from stored data, at RPC-request cost bounded only by the attacker's chosen length value rather than actual data size.

No length-prefix vs. remaining-buffer sanity check, no `Bounded` bincode config, and no pre-validation of `instruction.data.len()` against the encoded `bytes` length exists in this parsing path before the allocation attempt.

### Impact Explanation
A single unprivileged RPC call (`getTransaction`/`getBlock` with `jsonParsed`) against a previously-submitted transaction can trigger a `Vec<u8>` capacity request unbounded by the actual instruction size, potentially causing a very large or failing allocation. Rust's default global allocator aborts the process on allocation failure, so this can crash the RPC-serving validator process — an unbounded-cost-per-request / decoder-crash issue matching the "unbounded cost for a single low-rate call" and "decoder panic" bounty categories in scope.

### Likelihood Explanation
This requires only the ability to submit one ordinary transaction (any account can craft a compiled instruction addressed to `bpf_loader_upgradeable::id()`; it need not pass BPF loader authority/signer checks to be included and stored, since transaction-status recording happens regardless of instruction execution success) followed by one JSON-RPC call at normal rate. This is fully within the unprivileged, one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` threat model and requires no special permissions, staking, or leader control.

### Recommendation
Replace `bincode::deserialize` in `transaction-status/src/parse_bpf_loader.rs` (both `parse_bpf_loader` and `parse_bpf_upgradeable_loader`) with a length-bounded deserialization equivalent to `solana_bincode::limited_deserialize`, using `instruction.data.len()` (or `PACKET_DATA_SIZE`) as the limit, mirroring the guard already used in `programs/bpf_loader/src/lib.rs`.

### Proof of Concept
```rust
// transaction-status/src/parse_bpf_loader.rs (new test)
#[test]
fn test_parse_bpf_upgradeable_loader_write_oversized_length_prefix_is_bounded() {
    use solana_message::compiled_instruction::CompiledInstruction;

    // Craft data mimicking UpgradeableLoaderInstruction::Write { offset: u32, bytes: Vec<u8> }
    // bincode encodes: [enum_variant_index: u32][offset: u32][bytes_len: u64][bytes...]
    let mut data = Vec::new();
    data.extend_from_slice(&1u32.to_le_bytes()); // Write is variant index 1
    data.extend_from_slice(&0u32.to_le_bytes()); // offset
    data.extend_from_slice(&u64::MAX.to_le_bytes()); // claimed bytes length
    // no actual trailing bytes present

    let instruction = CompiledInstruction {
        program_id_index: 0,
        accounts: vec![1, 2],
        data,
    };
    let account_keys = AccountKeys::new(&[Pubkey::new_unique(); 3], None);

    // Expect a bounded-time Err, not an attempted allocation of ~u64::MAX bytes.
    let result = parse_bpf_upgradeable_loader(&instruction, &account_keys);
    assert!(result.is_err());
}
```
Expected: with the current unbounded `bincode::deserialize`, running this under a memory-limited sandbox (e.g., `ulimit -v`) or with an allocation-tracking fuzz harness demonstrates an attempted `Vec::with_capacity(u64::MAX)` allocation before the error is returned, whereas after applying the recommended `limited_deserialize` fix, the function should return `Err` immediately without attempting the oversized allocation (verifiable via a fuzz corpus of crafted length-prefix values compared against `instruction.data.len()`).
