### Title
Gateway `ProcessRequest` legacy path validates signature format but never enforces sender allow-listing before invoking `HandleLegacyUserMessage` - ([File: core/services/gateway/gateway.go])

### Summary
In the legacy request branch of `gateway.ProcessRequest`, `msg.Validate()` only checks structural well-formedness and recovers `msg.Body.Sender` from the ECDSA signature via `ExtractSigner` - it never checks whether that sender is allow-listed for `msg.Body.DonId`. The gateway then unconditionally routes to `h.HandleLegacyUserMessage`, and at least one concrete handler (`capabilities.handler.HandleLegacyUserMessage`) has no allow-list check at all, only a `// TODO: apply allowlist and rate-limiting here` comment.

### Finding Description
`gateway.ProcessRequest` in `core/services/gateway/gateway.go` handles the legacy path (`msg.Body.DonId != ""`) as follows: [1](#0-0) . `msg.Validate()` (in `core/services/gateway/api/message.go`) checks field lengths/format and calls `ExtractSigner()` to populate `m.Body.Sender` from the recovered signer address, but performs no comparison of that address against any per-DON allow-list [2](#0-1) . After validation, the gateway looks up the handler purely by `msg.Body.DonId` and invokes `h.HandleLegacyUserMessage(ctx, msg, callback)` with no additional check of `msg.Body.Sender` against a DON member/allow-list [3](#0-2) .

The `Handler` interface documents `HandleLegacyUserMessage` as taking `*api.Message` with no stated contract that implementers must perform sender authorization [4](#0-3) . Concretely, the `capabilities` package's implementation forwards any well-signed message with method `web_api_trigger` straight to all DON nodes without checking `msg.Body.Sender` against any allow-list, explicitly flagged by its own TODO comment: [5](#0-4)  and [6](#0-5) .

Thus, any attacker holding an arbitrary (unregistered) ECDSA keypair can produce a validly-formatted signature over a message body, causing `msg.Validate()` to succeed and `Sender` to be set to their own address, and reach handler business logic (forwarding requests to DON nodes) purely because their signature is cryptographically valid - not because they are authorized for that DON.

### Impact Explanation
This conflates "signature is well-formed and verifies" with "sender is authorized," matching the described invariant violation. For handlers like `capabilities.handler` that defer allow-list enforcement (currently unimplemented, per the TODO), an unauthorized/unregistered sender can trigger `web_api_trigger` messages that get relayed to all DON nodes, potentially triggering webhook/workflow executions or wasting DON node resources/rate-limit budget under an attacker-controlled but unauthorized identity - an authorization bypass / unauthorized job-run-triggering class impact, since a party never granted allow-list membership can nonetheless drive DON-side external HTTP interactions.

### Likelihood Explanation
Preconditions are minimal: an attacker needs only to generate any ECDSA keypair and sign an arbitrary message body (`MessageId`, `Method`, `DonId`, `Receiver`, `Payload`) per the documented signing scheme, then submit it against a real, configured DON ID [7](#0-6) . No allow-listed key, credential, or prior authorization is required to pass `gateway.go`'s gating logic; the exploit is fully repeatable and requires no privileged access.

### Recommendation
Add an explicit allow-list/authorization check in `gateway.ProcessRequest` (or as a shared pre-handler step) immediately after `msg.Validate()` succeeds in the legacy branch, verifying `msg.Body.Sender` against the DON's configured member/allow-list before calling `h.HandleLegacyUserMessage`, so authorization is enforced uniformly regardless of handler implementation. Additionally, implement the allow-list check inside `capabilities.handler.HandleLegacyUserMessage` (removing the TODO) as defense in depth.

### Proof of Concept
Go handler-level integration test plan:
1. Configure a `capabilities.handler` (or a minimal stub implementing `handlers.Handler`) with a `donConfig` that has a defined member/allow-list not including the attacker's address.
2. Generate an arbitrary `ecdsa.PrivateKey` unrelated to any configured DON member.
3. Build an `api.Message` with a valid `DonId` matching the handler's DON, arbitrary `MessageId`/`Method` (`web_api_trigger`)/`Payload`, and call `msg.Sign(attackerKey)`.
4. Call `gateway.ProcessRequest` (via the `gateway` struct constructed with `NewGateway`) with the JSON-RPC-wrapped raw request.
5. Assert: `msg.Validate()` succeeds (no error returned to caller), `HandleLegacyUserMessage` is invoked (e.g., via a mock `handlers.Handler` from `core/services/gateway/handlers/mocks/handler.go` asserting `HandleLegacyUserMessage` call count == 1) despite the attacker's address never being in the DON's allow-list, and no rejection/error response referencing sender authorization is produced by `gateway.go` itself.
6. Optionally extend to `capabilities.handler.HandleLegacyUserMessage` directly, asserting it proceeds to call `don.SendToNode` for all `donConfig.Members` regardless of `msg.Body.Sender` value, confirming the missing allow-list gate.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

// Message signatures are over the following data:
//  1. MessageId aligned to 128 bytes
//  2. Method aligned to 64 bytes
//  3. DonId aligned to 64 bytes
//  4. Receiver (in hex) aligned to 42 bytes
//  5. Payload (raw bytes before parsing)
func (m *Message) Sign(privateKey *ecdsa.PrivateKey) error {
	if m == nil {
		return errors.New("nil message")
	}
	rawData := GetRawMessageBody(&m.Body)
	signature, err := gw_common.SignData(privateKey, rawData...)
	if err != nil {
		return err
	}
	m.Signature = utils.StringToHex(string(signature))
	m.Body.Sender = strings.ToLower(crypto.PubkeyToAddress(privateKey.PublicKey).Hex())
	return nil
}

type Handler interface {

	//   1. calls HandleUserMessage
	//   2. waits on callbackCh with a timeout
	HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback Callback) error

	// Each user request is processed by a separate goroutine, which:
	//   1. calls HandleUserMessage
	//   2. waits on callbackCh with a timeout
	HandleJSONRPCUserMessage(ctx context.Context, jsonRequest jsonrpc.Request[json.RawMessage], callback Callback) error

	// Handlers should not make any assumptions about goroutines calling HandleNodeMessage.
	// should be non-blocking

	HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error

	// The methods support by this Handler.

}
