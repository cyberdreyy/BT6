### Title
Post-default instant withdraw requests bypass the recovery haircut and are paid at par from other users' funded-claim backing - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The kernel bug is a missing validity check: `f2fs_submit_merged_ipu_write()` flushed a cached bio that belonged to a *different* IO context after `cp_error` was set, causing a use-after-free. The closest credit-vault analog is in `IdleCreditVault`: after `finalizeDefaultRecovery` crystallizes a haircut (`defaultRecoveryFinalized`, `defaultRecoveryPrice`, `defaultRecoveryEpoch`), `requestWithdraw` correctly detects the changed context and routes new receipts through a separate `postDefaultRequests` path (lines 247-257), but `requestInstantWithdraw` performs **no equivalent context check**. It keeps writing into the *default-epoch* ledgers (`instantWithdrawsRequestsByEpoch[defaultEpoch]`, `instantWithdrawClaimsByEpoch[defaultEpoch]`, `pendingInstantWithdraws`) as if the pre-default IO context were still valid — the "stale cached bio submitted into a new context" pattern.

### Finding Description
- `requestWithdraw` (lines 243-258) reverts unless old receipts are claimed and then mints post-default receipts tracked separately in `postDefaultRequests`, paid from the isolated `defaultRecoveryReserve`.
- `requestInstantWithdraw` (lines 356-375) has no `defaultRecoveryFinalized` branch at all. Post-default it still mints the user a receipt and increments `instantWithdrawsRequests[_user]` and the *stale* `instantWithdrawsRequestsByEpoch[epochNumber]` / `instantWithdrawClaimsByEpoch[epochNumber]` buckets, where `epochNumber == defaultRecoveryEpoch` is frozen forever (no further `stopEpoch` after default).
- `claimInstantWithdrawRequest` (lines 380-393) only routes through `_claimDefaultedInstantWithdrawRequest` when `defaultInstantWithdrawsFinalized` was true **at finalization time** (set on line 696 from the then-current `pendingInstantWithdraws`). A receipt created *after* finalization in a finalization where `pendingInstantWithdraws == 0` (or where the flag is stale relative to the new request) is never haircut.
- The fallback then pays the full `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim` (lines 897-907), whose only guard is `balance - defaultRecoveryReserve >= _amount` — i.e., it may freely spend the non-reserve balance that backs **other users' already-funded withdraw receipts**.

Broken invariant: one receipt one payout at the correct (haircut) basis, and isolation of funded-receipt backing. A post-default instant receipt is priced at par while every other claim in the same context is priced at `defaultRecoveryPrice`, and its payout is drawn from a pool that does not belong to it — the direct analog of submitting a cached bio from the wrong IO context.

### Impact Explanation
Direct theft: a tranche holder requests an instant withdrawal after default finalization, receives a par-valued receipt against a haircut basis, and `claimInstantWithdrawRequest` transfers underlying at par out of the strategy balance that is earmarked for other users' funded (pre-default) claims. The loss is bounded by the non-reserve strategy balance but is realized entirely at the expense of honest claimants, whose later funded claims then revert on the reserve guard or underflow — permanent loss of unclaimed funded receipts plus insolvency of the funded-claim bucket.

### Likelihood Explanation
Requires (a) borrower default finalized via `finalizeDefaultRecovery`, and (b) the IdleCDO to still route `requestInstantWithdraw`/`claimInstantWithdrawRequest` post-default for a user holding tranche tokens. Both are attacker-reachable with only unprivileged actions (any tranche-token holder), assuming the CDO's instant-withdraw entry points remain callable in the defaulted state (the strategy itself imposes no such gate — the asymmetry with `requestWithdraw`'s explicit post-default branch suggests the path was simply not handled). Honest-privileged calls are only sequenced, not abused.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, revert if the user has any pending request, then record the receipt in a dedicated post-default bucket paid via `_transferDefaultRecovery` rather than `_transferFundedClaim`. In `claimInstantWithdrawRequest`, do not key the defaulted-receipt branch solely on the `defaultInstantWithdrawsFinalized` flag captured at finalization; check whether `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` is non-zero, and never create new entries under `defaultRecoveryEpoch` after finalization.

### Proof of Concept
Foundry fork PoC (scaffold): in `test/foundry/IdleCreditVault.t.sol` style — deposit AA for attacker and a second user; run epoch; second user requests a normal withdraw that gets fully funded at `stopEpoch`; then `stopEpoch` with zero borrower repayment to trigger default; call `finalizeDefaultRecovery` with partial recovery so `defaultRecoveryPrice < RECOVERY_FULL` and `pendingInstantWithdraws == 0` (hence `defaultInstantWithdrawsFinalized == false`); attacker calls `cdoEpoch.requestInstantWithdraw`-equivalent entry, then `claimInstantWithdrawRequest`; assert attacker received par underlying while `defaultRecoveryPrice < 1e18`-scale haircut applied to user2's claim, and that the strategy's non-reserve balance dropped below the sum of outstanding funded receipts.

*Caveat: I could not fully verify within the iteration budget whether `IdleCDOEpochVariant` gates instant-withdraw calls after `defaulted()`; if the CDO hard-blocks that entry point post-default, the exploitability collapses to an accounting-corruption issue only. The stale-context write into `instantWithdrawsRequestsByEpoch[defaultRecoveryEpoch]` is nonetheless present in the strategy code regardless.*
