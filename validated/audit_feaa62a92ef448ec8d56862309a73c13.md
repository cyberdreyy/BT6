### Title
Multi-epoch withdraw receipts escape the stopEpoch loss haircut and claim at par, draining funded claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` records a single `lossRecoveryPriceByEpoch[epochNumber]` for the whole aggregate `pendingWithdraws` bucket, but `_claimLossAdjustedWithdrawRequest` applies that haircut only to the receipt portion stored under `lastWithdrawRequest[_user]`'s epoch. A user holding receipts from multiple epochs gets only one epoch's portion haircut; all older-epoch portions remain in `withdrawsRequests[_user]` and are paid at par through `_claimFundedWithdrawRequest`, even though the strategy only received the partially-funded amount. This is the same bug class as the Abracadabra exploit: a "liquidation" (loss socialization) wipes part of the debt but forgets to scrub the rest of the receipt, leaving a phantom claim that is still payable in full.

### Finding Description
- `requestWithdraw` lets a user accumulate `withdrawsRequestsByEpoch` across multiple epochs without claiming in between; `pendingWithdraws` grows by every `_amount` (IdleCreditVault.sol:279-294).
- On a `stopEpochWithDuration` loss, `collectWithdrawFunds` compares the funded `_amount` against the *aggregate* `pendingWithdraws`, stores `lossRecoveryPriceByEpoch[epochNumber]`, and zeroes `pendingWithdraws` (IdleCreditVault.sol:411-425). Only `_amount` of underlying is transferred in.
- In `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and `_clearWithdrawClaimForEpoch` clears **only** `withdrawsRequestsByEpoch[_user][lossEpoch]` plus the matching APR0 bucket, subtracting just that epoch's `normalAmount` from `withdrawsRequests[_user]` (IdleCreditVault.sol:789-837).
- Control then reaches `_claimFundedWithdrawRequest`, which pays the entire remaining `withdrawsRequests[_user]` (all older-epoch receipts) at par via `_transferFundedClaim` (IdleCreditVault.sol:319-349), even though those receipts were part of the `pendingBasis` that was only fractionally funded.
- The only sequencing guard (IdleCreditVault.sol:263-270) blocks a *new* request after a loss epoch; it does nothing for receipts already spread across earlier epochs before the loss.

### Impact Explanation
Direct theft / insolvency. Older-epoch receipt portions are paid 1:1 from a strategy that received only `pendingToFund` (< `pendingBasis`). Each such claim over-pays by `olderReceipt * (1 - lossRecoveryPrice/RECOVERY_FULL)`, draining underlying reserved for other users' funded claims or instant-withdraw claims; later claimers' transactions revert. Quantified loss is bounded by the un-funded fraction of multi-epoch pending receipts.

### Likelihood Explanation
Requires a realized loss epoch (`stopEpochWithDuration` / partial `collectWithdrawFunds`) plus at least one user with unclaimed receipts spanning ≥2 epochs — both achievable by an unprivileged tranche holder who simply requests withdraws in consecutive epochs and waits for the loss. The honest borrower/manager only need to process a loss epoch normally. One caveat I could not fully verify in this pass: the exact ordering of `epochNumber` increment inside `deposit()` (line 610) relative to `collectWithdrawFunds` during the CDO's stopEpoch flow determines which key the haircut is stored under; the finding holds in either ordering because `lastWithdrawRequest` points at the *request* epoch, not necessarily the stored one.

### Recommendation
Track the haircut per pending-receipt basis rather than per request epoch: either store the loss price under every epoch that contributed to `pendingBasis`, or snapshot a single aggregate recovery basis (e.g., `lossRecoveryBasisByEpoch`) that `_claimLossAdjustedWithdrawRequest` applies to the user's entire outstanding `withdrawsRequests[_user]` + open APR0 principal at claim time, instead of clearing only `withdrawsRequestsByEpoch[_user][lossEpoch]`.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol`):
1. Deposit AA for `attacker` and `victim` in epoch N buffer; both `requestWithdraw` their full tranches.
2. `startEpoch`/`stopEpoch` honestly so `epochNumber` = N+1; `attacker` requests a second withdraw in the N+1 buffer without claiming (allowed — `lastWithdrawRequest` loss price is 0).
3. Run `stopEpochWithDuration` with `_lossAmount` so `collectWithdrawFunds` funds `< pendingWithdraws`; `lossRecoveryPriceByEpoch[N+1] = p < RECOVERY_FULL`.
4. `attacker.claimWithdrawRequest()`: epoch-N+1 portion pays `p`, but epoch-N portion in `withdrawsRequests[attacker]` pays at par.
5. Assert `attacker` received `r_{N+1}*p + r_N*1` while the strategy only holds `(r_N + r_{N+1})*p`-ish funding; assert `victim`'s subsequent claim reverts on insufficient balance.

Note: I was unable to execute or fully trace the CDO-side `stopEpoch`/`collectWithdrawFunds` ordering within the available iterations, so the PoC ordering in step 3 should be validated against `IdleCDOEpochVariant.stopEpochWithDuration`; if the haircut key and `lastWithdrawRequest` are guaranteed identical by construction, the residual exploit reduces to the multi-epoch receipt case described above.
