### Title
Closed-pool withdraw receipts are minted and paid at par without ever being funded (`pendingWithdraws` skipped when `epochEndDate == 0`) - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a use-after-free: `blk_mq_get_sq_hctx` dereferenced `->tagset` after the queue's cleanup path had freed it, i.e. state was consumed after its lifetime ended. The analog in `IdleCreditVault` is the withdraw-receipt pipeline consuming epoch-lifetime bookkeeping after the epoch machinery has permanently ended. Once the CDO is closed (`epochEndDate() == 0`), no `stopEpoch` will ever run again, so `pendingWithdraws` — the global counter that `stopEpoch` uses to source funds from the borrower for pending receipts — is deliberately not incremented at `contracts/strategies/idle/IdleCreditVault.sol:277-280`. However, the same call still mints a redeemable receipt and records it in `withdrawsRequests`/`withdrawsRequestsByEpoch`/`lastWithdrawRequest` (`lines 273-293`). The claim side then treats that receipt as a *funded* receipt: `_claimFundedWithdrawRequest`'s epoch-delay gate `epochEndDate() != 0 && epochNumber <= lastWithdrawRequest[_user]` is bypassed precisely because `epochEndDate() == 0` (`line 326`), so the unfunded receipt is paid out immediately at par via `_transferFundedClaim` (`line 349`) — dereferencing "freed" epoch state, the same class as touching `->tagset` after `blk_cleanup_queue`.

### Finding Description
In `requestWithdraw` (`contracts/strategies/idle/IdleCreditVault.sol:243`):

```solidity
bool isClosed = IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0;
...
_mint(_user, _amount);
if (!isClosed) {
  pendingWithdraws += _amount;   // skipped forever once closed
}
lastWithdrawRequest[_user] = currentEpoch;
withdrawsRequests[_user] += _amount;
withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
```

On a closed pool the receipt is created but excluded from `pendingWithdraws`. Then in `claimWithdrawRequest` → `_claimFundedWithdrawRequest` (`lines 319-350`), the only guard separating "fresh request" from "funded request" is the epoch-delay check, which evaluates to false for a closed pool. The receipt therefore reaches `_transferFundedClaim` immediately and is paid out of the vault's underlying balance, even though no accounting bucket was ever reserved for it. The invariant broken is "one receipt one funded payout": receipts are supposed to be claimable only after a `stopEpoch` moved the corresponding amount from the borrower/strategy into the vault; the closed-pool branch fabricates a funded claim out of a request that no funding step can ever cover.

### Impact Explanation
The payout is sourced from the vault's aggregate underlying balance, which backs *all* outstanding funded receipts, unclaimed epoch yields, and (after default finalization) `defaultRecoveryReserve`. An attacker can deposit tranche tokens into the CDO, call `requestWithdraw` while the pool is closed, and call `claimWithdrawRequest` in the same block, receiving underlying at par for a receipt that was never provisioned. If the `_amount` quoted by the CDO embeds interest the pool no longer accrues (e.g. minted-interest flows), or if the vault's free balance is lower than the sum of legitimate claims (loss-adjusted epochs, partially repaid borrower), the attacker's withdrawal directly consumes funds earmarked for other users' `withdrawsRequests`/default-recovery claims — theft of other claimants' funds and insolvency for the last claimers. Loss is bounded by the attacker's tranche holdings but is realized instantly with no epoch wait.

### Likelihood Explanation
Reachable by any unprivileged tranche-token holder (the receipt is minted to `_user` from `msg.sender`'s burned principal via `_onlyIdleCDO`). Trigger conditions are: pool closed (`epochEndDate == 0`, a normal lifecycle end state) or, equivalently, any residual underlying sitting in the vault that is not 1:1 backed against live receipts. No privileged role is required for the request or the claim; only honest manager calls (`stopEpoch` that closes the pool) are needed in the sequence. I was not able to read `_transferFundedClaim` and the CDO close path within the iteration budget, so whether the CDO already blocks `requestWithdraw` when closed, and whether the vault's closed-pool balance always exceeds outstanding claims, could not be fully confirmed — but the vault itself performs no such check, and the asymmetric bookkeeping (receipt recorded, `pendingWithdraws` not) is present in code.

### Recommendation
On a closed pool, either revert `requestWithdraw` (route users through a direct redeem path whose payout is verifiably backed), or treat the request as a normal redemption that immediately burns the receipt against a provably-covered balance rather than enqueuing it into `withdrawsRequests`. At minimum, `_claimFundedWithdrawRequest` should not treat a receipt whose epoch can never be funded as funded — e.g. require `epochEndDate() != 0` for the funded path, or track closed-pool requests in a separate bucket paid from a dedicated reserve, mirroring how `postDefaultRequests` is segregated after default finalization.

### Proof of Concept
```solidity
// Foundry fork test sketch against an IdleCreditVault-backed CDO whose pool
// has been closed by stopEpoch (epochEndDate() == 0).
function testClosedPoolUnfundedReceipt() public {
    // 1. Honest manager closes the pool: borrower repaid, epochEndDate == 0.
    vm.prank(manager);
    cdoEpoch.stopEpoch(/* closes pool */); // pool close mode: epochEndDate = 0
    assertEq(cdoEpoch.epochEndDate(), 0);

    // 2. Vault holds underlying backing other users' still-unclaimed receipts.
    uint256 vaultBal = underlying.balanceOf(address(strategy));
    uint256 attackerTranches = tranche.balanceOf(attacker); // > 0

    // 3. Attacker requests withdraw on the closed pool.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attackerTranches, address(tranche));
    // pendingWithdraws was NOT incremented (isClosed branch skipped it)
    // but withdrawsRequests[attacker] > 0 and lastWithdrawRequest is set.

    // 4. Same block: claim succeeds because the epochDelay gate is skipped
    //    when epochEndDate() == 0.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(address(cdoEpoch)); // via cdoEpoch.claimWithdrawRequest(attacker)
    strategy.claimWithdrawRequest(attacker);

    // 5. Attacker is paid at par from the shared vault balance even though no
    //    stopEpoch ever funded this receipt; other claimants are diluted.
    assertGt(underlying.balanceOf(attacker) - balPre, 0);
}
```
