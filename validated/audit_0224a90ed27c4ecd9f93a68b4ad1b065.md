### Title
User-created APR0 withdraw request permanently bricks `stopEpoch` once APR is raised — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The external finding is a teardown path (`_exitSafe`) that unconditionally reverts when a user-removable prerequisite (`prevModule`) is absent, DoS-ing `removeWholeTree`/`disconnectSafe`. The closest idle-tranches analog is the epoch-teardown path: `prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`, and only the CDO can call it during `stopEpoch`. An unprivileged KYC'd lender creates the poisonous state (`apr0TotalPrincipal > 0`) simply by calling `requestWithdraw` during a zero-APR epoch; there is no other code path that can clear `apr0TotalPrincipal`, so every subsequent `stopEpoch` reverts while the APR stays non-zero.

### Finding Description
`requestWithdraw` routes into `_requestWithdrawApr0` whenever `unscaledApr == 0` and the pool is not closed, incrementing the global `apr0TotalPrincipal` bucket (`IdleCreditVault.sol:285-286, 567-577`). `apr0TotalPrincipal` is only ever reset to zero at the end of `prepareStopEpochWithApr0` (`:540`), which is invoked by `IdleCDOEpochVariant.stopEpoch`. But before reaching that reset, the function hard-reverts:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
``` [1](#0-0) 

Unlike the claimable-receipt gates (e.g. the `lossRecoveryPriceByEpoch` check in `requestWithdraw` at `:263-271`, which the user can unblock by claiming), an APR0 requester has **no self-service way to cancel or settle** their pending principal — `_settleApr0` only runs inside a claim and only after `epochNumber` has advanced, which requires `stopEpoch` to succeed first. The attacker is not even DoS-ing themselves: their own receipt stays claimable in principle, but the revert traps the entire epoch, freezing every lender's funds, instant-withdraw payouts, and borrower repayment accounting.

### Impact Explanation
While `unscaledApr != 0` and `apr0TotalPrincipal != 0`, `stopEpoch` always reverts. The epoch can never close, so:
- no `epochNumber` increment → all pending `withdrawsRequests` revert in `_claimFundedWithdrawRequest` (`epochNumber <= lastWithdrawRequest`), and APR0 principal can never settle;
- borrower repayment/default accounting is stuck mid-epoch;
- funds are frozen for as long as the APR stays non-zero — effectively permanent unless the manager restores `unscaledApr = 0` purely to unbrick the vault.

This is the same structure as the Palmera bug: a user-attainable state (pending APR0 principal ≙ already-disabled module) meets a hard `revert` in a teardown function (≙ `prevModule == address(0)` check) instead of a graceful skip.

### Likelihood Explanation
Requires the pool to run an APR0 epoch (a legitimate mode — `unscaledApr == 0` is set via `setAprs`/`setAprsWithBuffer` by the honest manager/CDO) and a lender to request withdrawal during it. If the borrower/manager then renegotiates the rate upward mid-lifecycle (a normal operation — the manager may set APR through `setApr`/`setAprsWithBuffer` at any time), the very next `stopEpoch` wedges. No malicious privileged action is needed; the lender's single `requestWithdraw` is the unprivileged trigger.

### Recommendation
Mirror the external mitigation: treat the missing/invalid precondition as a skip rather than a revert. In `prepareStopEpochWithApr0`, when `unscaledApr != 0` but `apr0TotalPrincipal != 0`, settle the APR0 bucket at zero interest (or migrate `apr0TotalPrincipal` principal into the normal `pendingWithdraws`/per-epoch receipt basis) and always reset `apr0TotalPrincipal = 0`, instead of reverting. Alternatively, forbid APR increases while `apr0TotalPrincipal != 0` inside `setAprs*` — but the skip is safer since it cannot be weaponized to block rate updates either.

### Proof of Concept
Foundry-style sequence (against `IdleCreditVault` + `IdleCDOEpochVariant`):

```solidity
// 1. Manager configures a zero-APR epoch: setAprsWithBuffer(0, duration, buffer)
// 2. Epoch runs (isEpochRunning == true)
// 3. Attacker (KYC'd AA or BB lender) calls IdleCDO.requestWithdraw
//    -> strategy.requestWithdraw -> _requestWithdrawApr0
//    assertGt(vault.apr0TotalPrincipal(), 0);
// 4. Manager legitimately raises APR: setAprs(newApr, scaledApr) // unscaledApr != 0
// 5. Anyone calls IdleCDO.stopEpoch(...)
vm.expectRevert(); // NotAllowed from prepareStopEpochWithApr0
cdo.stopEpoch(0);
// 6. Repeat: every subsequent stopEpoch reverts while unscaledApr != 0,
//    and no user action can reduce apr0TotalPrincipal.
```

Caveat: I verified the strategy-side revert and the absence of any other `apr0TotalPrincipal` reset, but did not fully trace `IdleCDOEpochVariant.stopEpoch` to confirm the call is unconditional on every stop path (e.g., loss-bearing `stopEpochWithDuration`, pool-close). If any stop path bypasses `prepareStopEpochWithApr0`, the freeze reduces to those paths that invoke it.
