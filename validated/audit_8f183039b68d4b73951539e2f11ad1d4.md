## Analysis

The Union `debtWriteOff` bug is a class of "mutate shared state before a check that depends on it, permanently corrupting an aggregate used for a threshold decision." The strongest reachable analog in this repo is in the node-side signer-response tally kept by `StackerDBListener`, in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`.

`BlockStatus` keeps two independent weight accumulators, `total_weight_approved` and `total_weight_rejected`, each keyed only by "have we already counted this slot_id in *this* accumulator", not by "what is this signer's *current* vote." [1](#0-0) 

When a `BlockResponse::Accepted` arrives, weight is added to `total_weight_approved` only if the slot isn't already in `gathered_signatures`: [2](#0-1) 

When a `BlockResponse::Rejected` arrives, weight is added to `total_weight_rejected` only if the slot isn't already in `responded_signers`: [3](#0-2) 

Neither branch ever subtracts from the *other* accumulator, and the signer-side state machine explicitly allows a block to move `LocallyRejected -> LocallyAccepted` on re-evaluation: [4](#0-3) 

So a signer that first rejects a proposal (e.g. `handle_block_validate_reject`, or a `RECHECK` failure in `handle_block_pre_commit`) and later, on re-proposal/re-evaluation, signs the same block (`mark_locally_accepted`) will have its weight counted in **both** `total_weight_rejected` and `total_weight_approved` on the node side, and the reject weight is never removed.

The coordinator (`signer_coordinator.rs`) treats `total_weight_rejected` crossing the blocking-minority threshold as fatal and returns `SignersRejected`, permanently aborting that block regardless of later accepts: [5](#0-4) 

This breaks the "aggregated-weight vs verified-accepts" equality: the node's rejection tally is not the set of signers who *currently* reject, it is the set who *ever* rejected, which can exceed the true blocking minority. This is purely a bookkeeping/ordering defect (mutate-then-never-revisit, exactly like `totalFrozen` being updated before `withdrawRewards` reads it) reachable by any single signer that changes its vote after an honest re-evaluation — no majority collusion required, and no key/auth-token access needed.

However, before finalizing this as a reportable finding I want to flag the caveat: this requires deeper confirmation that (a) the node-side `BlockStatus` map is never reset/recreated per-proposal-attempt (which would clear stale weight), and (b) that a single miner can actually drive a signer through reject-then-accept for the *same* `signer_signature_hash` twice within a single coordinator's lifetime. Given the iteration budget for this pass, I was not able to fully trace `BlockStatus` lifecycle (creation/removal keyed by `signer_signature_hash`) across `signer_coordinator.rs` to confirm this hasn't already been mitigated by discarding old block entries on retry.

### Title
Node-side signer response tally never removes stale rejection weight after a signer switches to acceptance - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tracks `total_weight_approved` and `total_weight_rejected` as two independent monotonically-increasing counters keyed by slot-id-seen-once, rather than by current vote. Because the signer state machine legitimately allows `LocallyRejected -> LocallyAccepted` transitions on re-evaluation, a single signer's earlier rejection weight is never retracted from `total_weight_rejected` even after that signer later signs the same block, permanently poisoning the coordinator's blocking-minority check.

### Finding Description
`BlockStatus::total_weight_rejected` is incremented in the `Rejected` branch, guarded only by `responded_signers.insert(slot_id)` (first-time-seen, not current-state) at `stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-518`. `BlockStatus::total_weight_approved` is incremented in the `Accepted` branch, guarded by `!gathered_signatures.contains_key(&slot_id)` at lines 443-446. Neither branch ever decrements the counter incremented by the other. Since `docs/signer-flows.md` (and the block-state diagram) documents that a proposal can legitimately move from `LocallyRejected` back to `LocallyAccepted` on re-evaluation (e.g. after `should_reevaluate_reject_reason`/`should_reevaluate_block` in `stacks-signer/src/v0/signer.rs`), a real signer can validly emit `Rejected` and later `Accepted` for the exact same `signer_signature_hash`. The node then double-counts that signer's weight into both tallies, with the rejection weight sticking forever.

### Impact Explanation
`signer_coordinator.rs` treats `total_weight_rejected` crossing the blocking-minority (`total_weight - weight_threshold`) as a terminal `SignersRejected` outcome (lines 509-522), aborting the block/txids regardless of the true, current signer opinions. This can wedge a miner/tenure into never being able to gather a valid block for txids that a stale, retracted rejection still "blocks," a liveness impact matching "a signer wedged into never signing valid blocks" / "acting on stale ... aggregated weight."

### Likelihood Explanation
Requires no majority collusion, no key access — only that a single signer's local view causes one reject followed by one later accept for the same block hash, which the documented state machine explicitly permits as a normal re-evaluation path (`LocallyRejected -> LocallyAccepted`).

### Recommendation
Track a single "current vote per slot_id" map instead of two independent monotonic counters, and recompute `total_weight_approved`/`total_weight_rejected` from the current vote set whenever a signer's vote changes, mirroring how the fix for the Union bug reordered the mutation to happen only after the dependent computation was correctly evaluated.

### Proof of Concept
Not independently verified with a runnable reproduction in this pass — recommend a Devin session tracing `BlockStatus` lifecycle end-to-end (creation, per-attempt reset, and the full `signer_coordinator.rs` polling loop) to confirm no existing reset-on-retry logic already prevents this, before treating this as confirmed.
