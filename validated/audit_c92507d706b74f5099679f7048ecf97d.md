### Title
Buffer-period deposits mint at a stale tranche price that excludes already-accrued programmable-borrower vault yield, letting a new depositor capture yield earned before their deposit - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The analog of the Derby bug (rewards tied to epoch boundaries rather than actual deposit time) exists in `IdleCDOEpochVariant` in programmable-borrower mode, in the exploitable direction. Yield accrued by the programmable borrower's ERC4626 vault during the buffer period between epochs is not included in `getContractValue()` / tranche prices — it is only carried as `bufferedVaultDelta` inside `ProgrammableBorrower` and realized into NAV at the *next* `stopEpoch`. A lender who deposits during the buffer mints tranche tokens at the stale, pre-yield price and then receives a pro-rata share of that pre-accrued yield when it is finally crystallized, diluting existing depositors.

### Finding Description
- In programmable-borrower mode (`isProgrammableBorrower = true`, forced `isInterestMinted`), epoch interest is computed at `stopEpoch` from `IProgrammableBorrower.totalInterestDueNow()` ( [1](#0-0) ), which includes `bufferedVaultDelta` — vault PnL accrued while the pool was in the buffer ( [2](#0-1) , [3](#0-2) ).
- That buffered yield is only pushed into the CDO NAV at the next `stopEpoch` via `mintStrategyTokens(_grossInterest)` followed by `_updateAccounting()` ( [4](#0-3) ).
- Meanwhile `getContractValue()` counts only strategy-token balance plus raw underlying minus `unclaimedFees` — pending vault yield is invisible ( [5](#0-4) ). The test `testProgrammableBorrowerBufferVaultYieldIsRealizedAtNextStop` confirms that `virtualPrice` does *not* move when the next epoch starts and that buffer yield stays "pending" until the next stop.
- Deposits are open during the buffer: `stopEpoch` calls `_unpause()` and `_beforeUnpause` only blocks unpause while `isEpochRunning` ( [6](#0-5) , [7](#0-6) ). `_deposit` calls `_updateAccounting()`, but since pending vault yield is not in `getContractValue()`, the mint price stays stale ( [8](#0-7) ).
- `depositDuringEpoch` is explicitly blocked for programmable borrowers precisely because "mid-epoch deposits would dilute existing depositors" ( [9](#0-8) ), but the identical dilution via ordinary buffer deposits was not closed.

Broken invariant: fair mint/burn — shares must be minted at a price reflecting all yield accrued to date.

### Impact Explanation
An attacker deposits a large amount at the end of the buffer period (e.g., via a flash-loan-sized position), minting AA tranche tokens at a price that excludes `bufferedVaultDelta`. When the subsequent epoch stops, that pre-accrued yield is minted as strategy tokens and split across the now-larger tranche supply. The attacker captures roughly `bufferedVaultDelta * D / (NAV + D)` of yield that accrued entirely before they deposited — direct theft of unclaimed yield from existing tranche holders. With `D >> NAV`, nearly the entire buffered yield is captured. The attacker can then `requestWithdraw`/`claimWithdrawRequest` to exit with the stolen yield.

### Likelihood Explanation
- Only requires being a KYC-passing lender (or no KYC if `keyring == address(0)`) — explicitly in-scope as an unprivileged actor.
- Requires programmable-borrower mode and a vault that actually accrues positive yield during the buffer — a normal, intended configuration (the dedicated test demonstrates nonzero `bufferVaultYield` on a real Morpho vault fork).
- No privileged misbehavior needed; manager's routine `startEpoch`/`stopEpoch` sequencing is the honest flow.

### Recommendation
- Include pending programmable-borrower yield in the NAV used for minting: either add `IProgrammableBorrower(borrower).totalInterestDueNow()` (or `vaultInterestAccrued` + `bufferedVaultDelta`) into `getContractValue()`/`_managedContractValue()` in programmable mode, or force a yield-crystallizing accounting step (mint strategy tokens for pending interest) inside `_deposit`/`startEpoch` before shares are minted.
- Alternatively, block ordinary deposits during the buffer in programmable mode, mirroring the `depositDuringEpoch` guard that already acknowledges this dilution vector.

### Proof of Concept
Reproducible Foundry fork PoC sketch (extending `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
// setup: programmable borrower + MetaMorpho vault, isInterestMinted = true
vm.prank(owner);
cdoEpoch.setIsInterestMinted(true);

// honest LP seeds the pool and epoch 0 runs
idleCDO.depositAA(10_000 * oneScale);
_startEpochAndCheckPrices(0);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);

// vault accrues yield during the buffer (not yet in NAV)
vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);
_accrueMorphoVaultInterest();
uint256 bufferedYield = _programmableVaultAssets() - vaultAssetsAtStop;
assertGt(bufferedYield, 0);

// attacker deposits at the stale price just before startEpoch
address attacker = makeAddr("attacker");
deal(USDC, attacker, 1_000_000 * oneScale);
uint256 priceBefore = cdoEpoch.virtualPrice(address(aaTranche)); // excludes bufferedYield
vm.startPrank(attacker);
underlying.approve(address(idleCDO), type(uint256).max);
uint256 minted = idleCDO.depositAA(1_000_000 * oneScale);
vm.stopPrank();

// epoch 1 runs; buffered yield is realized at its stop
_startEpochAndCheckPrices(1);
vm.warp(cdoEpoch.epochEndDate() + 1);
_accrueMorphoVaultInterest();
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);

// attacker's tranche value now includes a share of pre-deposit buffered yield
uint256 attackerValue = minted * cdoEpoch.virtualPrice(address(aaTranche)) / ONE_TRANCHE_TOKEN;
// attackerValue > deposit + only the yield on their own funds for epoch 1
// honest LP's claim is reduced by ~= bufferedYield * minted * priceBefore / (NAV + deposit)
```

Uncertainty: the exact magnitude depends on `IdleCreditVault.deposit`/`totEpochDeposits` internals and how `startEpoch` forwards buffer deposits to the programmable borrower (`sendInterestAndDeposits`), which I did not fully trace; the stale-mint mechanism itself is confirmed by `getContractValue` excluding pending `vaultInterestAccrued`/`bufferedVaultDelta` and by the test asserting `virtualPrice` is unchanged at epoch start while buffer yield remains pending.
