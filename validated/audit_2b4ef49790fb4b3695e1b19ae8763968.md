### Title
Signer weight double-counted in both accept and reject tallies when a signer flips its vote - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary

### Finding Description
`StackerDBListener` tracks two independent, monotonically-increasing weight tallies per proposed block in `BlockStatus`: `total_weight_approved` and `total_weight_rejected` [1](#0-0) . These are meant to represent mutually exclusive views of the current, up-to-date response of each signer for a given block, and the coordinator relies on them being consistent to decide whether a block is dead (blocking-minority rejected) or accepted (threshold approved) [2](#0-1) .

The two branches gate their weight accounting on different keys:
- `BlockResponse::Rejected` only adds weight the first time a slot_id is inserted into the shared `responded_signers` set: `if block.responded_signers.insert(slot_id) { block.total_weight_rejected = ... }` [3](#0-2) .
- `BlockResponse::Accepted` adds weight based on a *different* key, `gathered_signatures`, not `responded_signers`: `if !block.gathered_signatures.contains_key(&slot_id) { block.total_weight_approved = ... }`, followed unconditionally by `block.gathered_signatures.insert(slot_id, signature); block.responded_signers.insert(slot_id);` [4](#0-3) .

Because a signer is legitimately allowed to reconsider and move from `LocallyRejected` to `LocallyAccepted` for the *same* block hash after re-evaluation (e.g. the reject reason becomes stale and the signer re-signs on re-proposal, per `should_reevaluate_reject_reason` / `should_reevaluate_block`) [5](#0-4) , the node can legitimately observe first a `Rejected` message (weight added to `total_weight_rejected`, slot inserted into `responded_signers`) and later an `Accepted` message for the same `signer_signature_hash` from the same signer. On the Accept path, the check is `!gathered_signatures.contains_key(&slot_id)`, which is still true (the slot was never in `gathered_signatures`), so the signer's weight is *also* added to `total_weight_approved` — nothing ever removes or reconciles the earlier reject weight. The same signer's weight now counts simultaneously toward both `total_weight_rejected` and `total_weight_approved`.

The coordinator's decision loop checks the "dead" condition first: `if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight { ... reject ... } else if block_status.total_weight_approved >= self.weight_threshold { ... accept ... }` [2](#0-1) . Because `total_weight_rejected` is never decremented when a signer later switches to accept, stale/superseded rejection weight can remain permanently counted, inflating `total_weight_rejected` beyond what current signer state actually reflects. This breaks the equality that `total_weight_approved` + non-flipped rejections should represent the *current, verified* set of accepts/rejects — the aggregated weight tracked by the coordinator no longer matches the verified/current signer votes.

### Impact Explanation
This is the "aggregated-weight vs verified-accepts" equality break called out as in-scope. Practically, once enough signers have (at any point) rejected a block and then later reconsidered and accepted it, the stale `total_weight_rejected` can independently cross the blocking-minority mark even though the *current* set of votes has enough weight to approve the block. Since the coordinator evaluates the rejection-dominant branch first, a block that is actually currently signable (real, current `>=70%` approving signatures) can be treated as globally rejected by the miner/coordinator due to leftover rejection weight from signers who have since switched their vote. This is a liveness wedge on block production (miner spuriously treats valid, sufficiently-supported blocks as dead), matching the "signer wedged into never signing valid blocks" / equivalent coordinator-side liveness class. It does not, by itself, cause a signer to sign an invalid/conflicting block (the underlying signatures are still real and validly recovered), so it should be classified as a liveness issue rather than an outright safety break.

### Likelihood Explanation
The trigger does not require a malicious majority or attacker key control: it can occur under normal operation whenever a miner re-proposes the same block (a legitimate, expected flow per `should_reevaluate_block`) after signers initially rejected it for a reason that later becomes stale, causing them to flip to Accept for the identical `signer_signature_hash`. The only asymmetry is a missing re-check between the two weight tallies (`gathered_signatures` vs `responded_signers`), which is a straightforward code-path condition, not something requiring privileged access.

### Recommendation
Make the accept/reject weight-tally bookkeeping share one consistent per-signer "current vote" state rather than two independently-gated data structures. When a signer's vote flips from Rejected to Accepted (or vice versa) for the same block, the previous tally should be reversed/reconciled (subtract stale weight) before adding the new one, so `total_weight_approved` and `total_weight_rejected` always reflect only the *current* vote of each responding signer.

### Proof of Concept
Not independently executed; reasoning is based on static code-path analysis of `stackerdb_listener.rs`'s `Accepted`/`Rejected` handlers (lines 386–465 and 486–591) and `signer_coordinator.rs`'s decision loop (lines 509–545), combined with the documented signer flow permitting `LocallyRejected -> LocallyAccepted` transitions on re-evaluation (`docs/signer-flows.md` section 3, `stacks-signer/src/v0/signer.rs:1592-1604`). A concrete runtime PoC (spinning up a signer set, forcing an initial rejection, then a re-proposal causing acceptance, and observing `BlockStatus.total_weight_rejected`/`total_weight_approved` in `StackerDBListener`) was not run in this session; this would need to be validated with an integration test harness to confirm the exact numeric outcome and whether the "reject" branch in `signer_coordinator.rs` actually fires ahead of a legitimate acceptance in a real timing scenario.
