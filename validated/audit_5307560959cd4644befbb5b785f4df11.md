Analysis of the `multisig` contract confirms a genuine, in-scope custody-boundary bug: stale confirmations from removed access keys are never purged when a key is deleted, breaking the equality that "confirmations counted == live keyholders who approved." [1](#0-0) [2](#0-1) 

### Title
Multisig requests can execute below the effective live-key threshold because `DeleteKey` never purges stale confirmations left by the removed key on other requests - (File: `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts confirmations solely by looking at the size of the `HashSet<PublicKey>` stored for a request and comparing it to `num_confirmations`. When a key is later removed via a `DeleteKey` request, `execute_request`'s `DeleteKey` branch only deletes *requests originally created by* that key and clears its `num_requests_pk` entry; it never scans `self.confirmations` to strip that public key from confirmation sets of *other* still-pending requests it had previously confirmed. As a result, a confirmation cast by a key that has since been revoked keeps counting toward the approval threshold of any request it confirmed before removal.

### Finding Description
The binding that should hold is: `confirmations.len() == number of currently-live access keys that approved the request`, and a request should only execute once that count reaches `num_confirmations` live approvals.

`execute_request`'s `DeleteKey` action:
```rust
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)   // only requests AUTHORED by pk
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [1](#0-0) 

This only cleans up requests where `r.signer_pk == pk` (i.e., requests the removed key itself created). It does not iterate `self.confirmations` to remove `pk` from the confirmation sets of requests created by *other* keys that `pk` had already confirmed. Those stale entries persist and continue to be counted in:
```rust
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    ...
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else { ... }
}
``` [2](#0-1) 

The check `confirmations.len() + 1 >= self.num_confirmations` treats every entry in the set as a live approval, but nothing guarantees the key is still an access key on the account after a `DeleteKey` action has run.

### Impact Explanation
Concrete scenario with `num_confirmations = 3` and keys `A, B, C, D` on the multisig account:
1. `B` creates request `R` (e.g., `Transfer` to an attacker-controlled account). `confirmations[R] = {}`.
2. `A` confirms `R` → `confirmations[R] = {A}` (1/3).
3. Separately, the group legitimately rotates out `A` (e.g., compromised device) via a `DeleteKey{A}` request that reaches threshold and executes. `execute_request` removes only requests where `signer_pk == A`; `R` was authored by `B`, so `confirmations[R]` still contains `A` even though `A`'s access key is now deleted on-chain.
4. `C` confirms `R` → `confirmations[R] = {A, C}` (2/3, but only `C` is a live signer contributing here beyond the stale `A`).
5. `D` confirms `R` → `confirmations[R] = {A, C, D}`, size 3, reaches `num_confirmations = 3`, and `R` executes.

Only `C` and `D` are actually live, currently-authorized signers who approved `R`; `A`'s revoked-key approval is still counted, so the transfer executes with only 2 live confirmations against a nominal 3-of-4 policy. This directly breaks the "multisig request executed below threshold" custody binding and can move NEAR (or trigger `AddKey`/`FunctionCall` actions) out of the account with fewer genuine approvals than the configured security policy requires.

### Likelihood Explanation
This requires no privileged foundation/admin access — it only requires the normal, expected multisig lifecycle event of rotating out one keyholder (a routine operational action any multisig group performs) combined with a pending request that the rotated-out key had already confirmed before removal. No malicious deployment, redeploy, or off-chain component is needed; the flaw is purely in `execute_request`'s incomplete cleanup logic in this repository.

### Recommendation
When executing `MultiSigRequestAction::DeleteKey`, iterate over `self.confirmations` (all pending requests) and remove the deleted `pk` from every confirmation set, not just from requests it authored. Alternatively, re-validate at `confirm()` time (or at threshold-check time) that every public key in a request's confirmation set still corresponds to a live access key on the account before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` with 4 full-access keys `A, B, C, D`.
2. As `B`, call `add_request` with a `Transfer` action to an external/attacker account → `request_id`.
3. As `A`, call `confirm(request_id)` → confirmations = `{A}`.
4. As a quorum (any 3 of the 4 keys), submit and confirm a `DeleteKey{A}` request → executes, deletes `A`'s access key on-chain, but `confirmations[request_id]` (owned by `B`, not `A`) is untouched and still contains `A`.
5. As `C`, call `confirm(request_id)` → confirmations = `{A, C}` (size 2).
6. As `D`, call `confirm(request_id)` → confirmations = `{A, C, D}` (size 3) ≥ `num_confirmations` (3) → `execute_request` runs the `Transfer`, moving funds even though only `C` and `D` are live signers who approved it.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
