### Title
`solveRequestsDirect` omits the `solvingNotPaused` guard enforced on all other Provisioner entry points, allowing async requests to be executed after the token's solving is paused - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2` gates every other user/solver-facing entry point (`deposit`, `mint`, `redeem`, `withdraw`, `solveRequestsVault`) with the `solvingNotPaused(token)` modifier, which queries the optional `ISolvingGate` to determine if solving/trading for a token has been paused. `solveRequestsDirect`, the only *unauthenticated* solve path (callable by "anyone" per the contract's own NatSpec), is missing this modifier entirely, so a pause enacted through the solving gate has no effect on already-placed fixed-price async requests being executed via this path.

Compare its modifier list to every other request-affecting entry point, all of which include `solvingNotPaused(token)`: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

The modifier itself: [7](#0-6) 

`ISolvingGate` is explicitly documented as an emergency/authorization-style circuit-breaker per token: "Returns true if solving is currently paused for the given Provisioner and token" and implementations "MUST return true when solving is paused." [8](#0-7) 

`solveRequestsDirect` only re-validates that the *vault* is not globally paused via `PRICE_FEE_CALCULATOR.isVaultPaused`, and re-checks the per-token `asyncDepositEnabled`/`asyncRedeemEnabled` flags at execution time, but never queries `solvingGate`: [9](#0-8) 

This mirrors the report's root-cause pattern exactly: a revocation/authorization-state check (the solving-gate pause) is enforced consistently across the "normal" entry points (`deposit`, `mint`, `redeem`, `withdraw`, `solveRequestsVault`) but a second, alternate, publicly-reachable path (`solveRequestsDirect`) that operates on the same underlying state (pre-existing `asyncRequestHashes` entries) never re-validates that guard before acting. Just as the OIDC refresh path let a revoked/disabled/group-restricted principal keep transacting because it skipped the authorization re-check that the primary session path enforced, `solveRequestsDirect` lets any address (deposit requester, redeem requester, or unrelated third-party solver collecting the `solverTip`) keep completing pre-existing fixed-price requests after governance has paused solving for that token via the gate.

### Impact Explanation
When `SOLVING_GATE_ENABLED` is true and governance sets a `solvingGate` to halt solving for a token (e.g., because of a stale/incorrect price feed, a compromised token, or a compliance freeze), all legitimate entry points correctly reject further activity. However, any pending `asyncRequestHashes` entries created before the pause (fixed-price deposit/redeem requests) can still be pushed through `solveRequestsDirect` by anyone — including the original requester or an unrelated party collecting the `solverTip` — completely undermining the intended kill switch. Because this bypasses a protocol-level freeze control while still moving real vault assets/units, it constitutes at minimum a Medium-severity "protection bypass enabling continued fund movement during an intended freeze" per Immunefi's temporary-freeze severity bucket; depending on why the gate was engaged (e.g., a known-bad price baked into the fixed-price request), it can translate directly into fund loss for the vault or other depositors.

### Likelihood Explanation
Exploitation requires no privileged role: the attacker only needs (1) a pre-existing fixed-price async deposit or redeem request (which any ordinary depositor can create via `requestDeposit`/`requestRedeem` before the pause), and (2) governance to have engaged the `solvingGate` pause for that token afterward. `solveRequestsDirect` has no `requiresAuth`, no `solvingNotPaused` modifier, and is reentrancy-guarded only against reentrancy — not against the gate check. This makes the bypass trivially reachable by an ordinary user the moment a pause is enacted while their (or anyone else's) fixed-price request is outstanding.

### Recommendation
Add the `solvingNotPaused(token)` modifier to `solveRequestsDirect`, matching every other entry point that touches per-token solving/trading state, so that a solving-gate pause uniformly blocks all execution paths (vault-mediated and direct) for outstanding requests on that token.

### Proof of Concept
1. Deploy `ProvisionerV2` with `solvingGateEnabled = true` and set a mock `ISolvingGate` via `setSolvingGate`.
2. As user A, call `requestDeposit(token, tokensIn, minUnitsOut, solverTip, deadline, maxPriceAge, isFixedPrice=true)` to create a fixed-price async deposit request; capture `depositHash`/request struct.
3. As governance, configure the mock `ISolvingGate.paused(provisioner, token)` to return `true`, simulating an emergency halt of solving for `token`.
4. Assert `deposit(token, ...)` and `solveRequestsVault(token, [request], ...)` now revert due to `solvingNotPaused`.
5. Call `solveRequestsDirect(token, [request])` from any unrelated address — assert it succeeds, minting units to the receiver and paying `solverTip`, despite the gate reporting `paused == true`, proving the missing guard allows continued execution during an active protocol freeze.

    /// @inheritdoc IProvisionerV2
    function solveRequestsDirect(IERC20 token, RequestV2[] calldata requests) external nonReentrant {
        // Requirements: vault is not paused in the priceAndFeeCalculator
        require(!PRICE_FEE_CALCULATOR.isVaultPaused(MULTI_DEPOSITOR_VAULT), Aera__PriceAndFeeCalculatorVaultPaused());

        uint256 length = requests.length;
        TokenDetailsV2 storage tokenDetails = tokensDetails[token];
        for (uint256 i = 0; i < length; i++) {
            RequestV2 calldata request = requests[i];
            RequestType requestType = request.requestType;

            // Requirements: direct solves can only solve fixed price requests
            require(!_isRequestTypeAutoPrice(requestType), Aera__AutoPriceSolveNotAllowed());

            if (_isRequestTypeDeposit(requestType)) {
                // Requirements: async deposit is enabled
                require(tokenDetails.asyncDepositEnabled, Aera__AsyncDepositDisabled());
            } else {
                // Requirements: async redeem is enabled
                require(tokenDetails.asyncRedeemEnabled, Aera__AsyncRedeemDisabled());
            }

            // Requirements + Effects + Interactions: solve direct request
            _solveRequestDirect(token, request);
        }
    }

/// @title ISolvingGate
/// @notice External gate queried by Provisioner to determine whether solving is allowed
/// @dev When the gate address is zero the Provisioner treats solving as always open
///      Implementations MUST return `true` when solving is paused and `false` otherwise
interface ISolvingGate {
    /// @notice Returns true if solving is currently paused for the given Provisioner and token
    /// @param provisioner The address of the Provisioner querying the gate
    /// @param token The token for which the solve is being attempted
    /// @return True if solving is currently paused, false otherwise
    function paused(address provisioner, IERC20 token) external view returns (bool);
}
