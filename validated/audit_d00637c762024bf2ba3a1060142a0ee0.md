Based on my investigation, this finding does not hold up as a valid vulnerability.

Key points from the codebase:

1. `SecretKey::from_str` for `KeyType::SECP256K1` (`core/crypto/src/signature.rs:887-891`) parses a **private** key using `secp256k1::SecretKey::from_slice`, which validates the scalar is a valid nonzero value less than the curve order. This function is not involved in deriving or storing an `AccessKey.public_key` on-chain — it is a client-side utility for constructing a signer from a private key string, not something an attacker controls when submitting an `AddKey` action to a victim account. [1](#0-0) 

2. The actual `AddKeyAction.public_key` that ends up stored via `action_add_key`/`add_regular_key` is a `PublicKey`, populated from the transaction the **victim signs**, not from a string an attacker feeds into `SecretKey::from_str`. The premise that a "third party" can inject a corrupted point into a victim-signed `AddKey` transaction is not supported — the victim controls transaction construction and signs the whole transaction, including the `public_key` field being added. There's no code path shown where an attacker-controlled string is parsed via `PublicKey::from_str`/`SecretKey::from_str` and lands unchecked into a stored `AccessKey` without the account owner's consent to that exact value. [2](#0-1) 

3. Critically, `DeleteKeyAction` processing (`action_delete_key` in `runtime/runtime/src/access_keys.rs:52-91`) looks up the key to delete by its `public_key` field and removes it directly — it does not require that the *signer's* access key be the same key being deleted. Permission/signature checks for who is allowed to submit the transaction are handled separately in `verifier.rs`/`action_validation.rs`, which (per NEAR's access-key model) permit any `FullAccess` key on the account to sign a `DeleteKey` action targeting *any* other key on that same account, including a broken/unusable one. [3](#0-2) 

4. Storage usage accounting for a deleted key is refunded in `delete_regular_key`, based on the key's own key type/size, regardless of whether that key is cryptographically "valid" or ever used — deletion doesn't require verifying a signature made *by* that key. [4](#0-3) 

Given these facts, even if a broken/unverifiable public key were somehow added to an account, it could be removed by any other full-access key already present via a normal `DeleteKey` action, reclaiming the storage deposit. The proof-idea described in the prompt itself (DeleteKey by another full-access key works) is consistent with what I found in `action_delete_key`, and no administrative path requiring signature verification specifically by the broken key was found in the reachable code.

### No Vulnerability found for this question.

impl FromStr for SecretKey {
    type Err = crate::errors::ParseKeyError;

    fn from_str(s: &str) -> Result<Self, Self::Err> {
        let (key_type, key_data) = split_key_type_data(s)?;
        Ok(match key_type {
            KeyType::ED25519 => Self::ED25519(ED25519SecretKey(decode_bs58(key_data)?)),
            KeyType::SECP256K1 => {
                let data = decode_bs58::<{ secp256k1::constants::SECRET_KEY_SIZE }>(key_data)?;
                let sk = secp256k1::SecretKey::from_slice(&data)
                    .map_err(|err| Self::Err::InvalidData { error_message: err.to_string() })?;
                Self::SECP256K1(sk)
            }
            KeyType::MLDSA65 => {
                let data = decode_bs58::<ML_DSA_65_SECRET_KEY_LENGTH>(key_data)?;
                // Mirror SECP256K1: validate the bytes form a valid
                // private key by handing them to the library. Catches
                // malformed-but-correct-length blobs at parse time
                // rather than blowing up later in `sign()`.
                PqdsaKeyPair::from_raw_private_key(&ML_DSA_65_SIGNING, &data[..])
                    .map_err(|err| Self::Err::InvalidData { error_message: err.to_string() })?;
                Self::MLDSA65(MlDsa65SecretKey(Box::new(data)))
            }
        })
    }
}

pub(crate) fn action_delete_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,

    delete_key: &DeleteKeyAction,
) -> Result<(), RuntimeError> {
    let access_key = get_access_key(state_update, account_id, &delete_key.public_key)?;
    if let Some(access_key) = access_key {

                result,

                account_id,

            public_key: delete_key.public_key.clone().into(),
            account_id: account_id.clone(),

    Ok(())
