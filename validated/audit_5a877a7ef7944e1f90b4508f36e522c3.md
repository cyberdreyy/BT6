### Title
Unvalidated ERC4626 share price lets any vault depositor mint unbacked epoch interest and drain the pool in minted/APR0 mode - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` derives epoch interest (`totalInterestDueNow`) from the live `convertToAssets` valuation of an external ERC4626 `vault` it does not control (`_vaultNetInterest`, lines 337-347). `IdleCDOEpochVariant.stopEpoch` consumes that value as `_expectedInterest` and, when `isInterestMinted` is set and `_interest` is not the close-pool sentinel, mints strategy tokens for the full reported gain via `_strategy.mintStrategyTokens(_grossInterest)` (IdleCDOEpochVariant.sol:428-430). The only sanity cap — comparing the gain against `maxApr()` — is bypassed whenever `maxApr() == 0` (line 379: the revert predicate requires `_maxApr != 0`), which is exactly the APR0 operating mode exercised throughout the programmable-borrower tests (`strategy.setAprs(0, 0)`). A depositor in the shared ERC4626 vault can therefore inflate the measured "vault interest" without depositing anything into the credit facility, get fake yield baked into tranche `virtualPrice`, and redeem tranche tokens against real pooled underlyings that the minted shares do not represent.

### Finding Description
During an active epoch, `_vaultNetInterest` computes `interest = _currentVaultAssets() + epochWithdrawnFromVault - (epochStartVaultAssets + epochDepositedToVault) + bufferedVaultDelta`. `_currentVaultAssets()` is a live `vault.convertToAssets(vault.balanceOf(this))` — a valuation fully controlled by the external vault's accounting. Any party able to move that vault's share price (a vault depositor injecting yield/donating into a balanceOf-based vault, or pushing exchange-rate changes on vaults where that is permissionless) raises `totalInterestDueNow` without transferring a single token to the `IdleCDO`.

At `stopEpoch` in minted mode (`isInterestMinted == true`, `_isRequestingAllFunds == false`), `_amountToPullFromBorrower = 0` (line 376) — the CDO pulls no cash for interest — and instead calls `mintStrategyTokens(_grossInterest)`, increasing strategy-token supply and, through `_updateAccounting()`, every tranche's `virtualPrice`. The guard on lines 377-380 only fires when `maxApr() != 0`; in the APR0 configuration (`setAprs(0,0)`) there is no upper bound on the fabricated interest. The attacker sequence:

1. Epoch running, `epochAccountingActive == true`, pool capital parked in the ERC4626 vault.
2. Attacker (a plain depositor/user of that vault) inflates the vault's price-per-share by amount `X` (donation or forced yield realization attributed to the borrower's share balance).
3. After `epochEndDate`, `stopEpoch(0, 0)` is called by the honest manager. `totalInterestDueNow` returns real interest + `X`; `expectedEpochInterest` is set to that inflated value; `mintStrategyTokens(X)` credits unbacked value; AA tranche `virtualPrice` rises as if `X` real underlyings were received.
4. Attacker, holding tranche tokens (acquired via `depositAA`/`depositBB` beforehand — KYC'd lender is an allowed attacker class), redeems at the inflated price. Because the minted interest has no underlying backing, the contract pays the attacker real pool principal belonging to other depositors; remaining holders/withdraw-request receipts are left undercollateralized, i.e. insolvency plus direct theft.

The skim mechanism (`_skimDonatedAssets`) only addresses stray tokens on the IdleCDO itself; it does not exist for the borrower-side vault valuation, and no guard re-verifies that the reported interest corresponds to assets actually transferred into the facility (`_amountToPullFromBorrower` is zero by design in minted mode, so there is nothing to reconcile against). The Default path is not triggered — `onStopEpoch` returns `true` and the subsequent `getFundsFromBorrower` succeeds because it pulls only `_pendingWithdraws`.

### Impact Explanation
Direct theft and insolvency: the attacker converts a purely accounting-side inflation of `totalInterestDueNow` into a higher tranche redemption price, extracting real underlyings up to the minted fake interest (bounded by the pool's liquid balance and the degree of share-price manipulation the chosen vault permits). Loss is pro-rata against all honest tranche holders and pending withdraw-request holders, who are left holding claims against unbacked minted strategy tokens.

### Likelihood Explanation
Requires a pool configured with `isProgrammableBorrower`, `isInterestMinted`, and `maxApr == 0` (the tested/expected APR0 configuration), plus a programmable-borrower vault whose `convertToAssets` can be moved by an unprivileged depositor — true for `balanceOf`-style ERC4626s and for vaults where interest realization or exchange-rate updates are permissionless. The attacker needs only tranche tokens (any KYC-passing lender) and vault-depositor status; both are explicitly allowed unprivileged roles. Where the configured vault uses fully internal `totalAssets` accounting that ignores donations (e.g., some Morpho-style vaults), the attacker must instead induce an actual rate move or realized-interest event, which narrows but does not eliminate the surface — the core defect is that a third-party valuation is trusted to mint unbacked pool value with no cap in APR0 mode.

### Recommendation
- Never let minted-mode `stopEpoch` credit interest that was not pulled as cash without an upper bound. Enforce the `maxApr` check even when `maxApr() == 0` by deriving the cap from configured APRs or a stored `expectedEpochInterest`, and revert when `maxApr == 0 && _grossInterest > 0` unless an explicit expected-interest value was set at `startEpoch`.
- In `ProgrammableBorrower._vaultNetInterest`, value the position conservatively (e.g., `min(convertToAssets, maxWithdraw)` or a smoothed/capped delta per epoch), or require vault gains above a threshold to be realized (redeemed to cash on-hand) before they count as epoch interest in minted mode.
- Treat direct underlying transfers to the borrower contract and vault share-price jumps symmetrically: snapshot and bound epoch vault delta to `maxApr`-derived expectations.

### Proof of Concept
Foundry fork (mainnet, e.g. the existing `ProgrammableBorrowerCreditVault.t.sol` harness with a `balanceOf`-accounting ERC4626 vault such as an sUSDS-style or donation-sensitive vault):

```solidity
function testVaultPriceInflationMintsUnbackedInterest() external {
    // setup identical to testProgrammableBorrowerStopEpochAutoRealizesInterestWithRealVault
    vm.prank(owner); cdoEpoch.setIsInterestMinted(true);      // minted mode
    // strategy.setAprs(0,0) already in setUp -> maxApr() == 0, cap check disabled

    uint256 amount = 100_000 * oneScale;
    idleCDO.depositAA(amount);                                 // attacker+honest depositors hold AA
    _startEpochAndCheckPrices(0);                              // funds parked in ERC4626 vault

    // ATTACK: attacker is a vault depositor and inflates convertToAssets for the
    // borrower's share balance by X, e.g. underlying.transfer(vault, X) on a
    // balanceOf-based vault (or forcing realized yield attributed to PB's shares).
    uint256 fakeGain = 20_000 * oneScale;
    underlying.mint(address(vault), fakeGain);                 // or vault-specific injection
    assertGt(programmableBorrower.totalInterestDueNow(), 0);   // now includes fakeGain

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                                  // honest keeper call

    // mintStrategyTokens credited fakeGain to the pool; AA price inflated with no cash
    uint256 inflatedPrice = cdoEpoch.virtualPrice(address(aaTranche));
    // attacker redeems AA at inflated price and receives REAL underlyings
    uint256 balBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    idleCDO.withdrawAA(aaTranche.balanceOf(attacker));
    assertGt(underlying.balanceOf(attacker) - balBefore,
             attackerPrincipal, "attacker extracted more than deposited");

    // residual: pool NAV (cash + vault + borrower debt) < tranche claims -> insolvency
    assertLt(cdoEpoch.getContractValue(), totalTrancheClaims());
}
```

Caveats: the exact injection primitive depends on the configured vault — for vaults with internally tracked `totalAssets` (e.g., MetaMorpho), a pure donation does not move `convertToAssets`, so the PoC should instead use whatever permissionless rate-move the vault exposes (realized interest, market reallocation, or a vault where donations do count). The vulnerable invariant — uncapped trust in an external share price minting unbacked pool value in APR0/minted mode — is independent of the injection mechanism.
