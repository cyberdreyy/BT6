### Title
`getInflationReward` Silently Converts Negative Reward Amounts to Positive via `unsigned_abs()`, Misreporting Slashed/Deactivated-Stake Rewards as Gains - ([File: rpc/src/rpc.rs])

### Summary
This is the closest reachable analog to the GMToken price-cast bug in an unprivileged, JSON-RPC-reachable path. In `JsonRpcRequestProcessor::get_inflation_reward`, the signed `lamports: i64` field of a `Reward` (which can legitimately be negative, e.g. for `RewardType::DeactivatedStake`) is converted into the RPC response's `amount` field using `.unsigned_abs()` instead of being checked for sign and either preserved as a signed value or zeroed/flagged as the GMX report recommends.

### Finding Description
`Bank`/blockstore reward records use a signed `lamports: i64` field precisely because rewards are not always positive — deactivated/loss cases can carry negative values. [1](#0-0) [2](#0-1) 

`JsonRpcRequestProcessor::get_inflation_reward` builds the client-facing `RpcInflationReward` by taking the absolute value of the signed `lamports` field with `.unsigned_abs()`, discarding the sign entirely: [3](#0-2) 

This mirrors the reported GMX pattern almost exactly: a value that is naturally signed (and can validly be negative) is coerced into an unsigned representation without any check for negativity, and the recommended fix ("if negative, return 0") is not applied here either — instead the negative case is mapped to a *positive* magnitude, which is arguably worse because it actively asserts a reward occurred when in fact stake was lost/deactivated.

Other places in the codebase that also transform signed `lamports` for display are more careful and preserve the sign for the user (e.g., CLI output explicitly checks `reward.lamports < 0` and prints a `-` sign before using `unsigned_abs()` purely for magnitude formatting): [4](#0-3) 
This shows the codebase is aware that `Reward.lamports` can be negative and needs sign-aware handling — but the RPC-facing `get_inflation_reward` path does not carry that same care into the wire-format `RpcInflationReward.amount`, which has no sign field to recover the original semantics.

### Impact Explanation
Any unprivileged caller of the `getInflationReward` JSON-RPC method can retrieve reward data for arbitrary addresses. For any epoch/address combination where the underlying `Reward.lamports` was negative (deactivated/penalized stake), the RPC response reports a positive `amount`, i.e., wrong data is returned for a read-only query — this falls in the "wrong-slot/fork/account data returned" acceptance bucket, since it's effectively data misreporting to any wallet, exchange, or accounting tool that consumes this endpoint to reconcile stake rewards. This can cause downstream financial miscalculations (double counting, incorrect reward accounting) without any way for the caller to detect the discrepancy, since the sign information is irrecoverably lost.

### Likelihood Explanation
Reachable via a single, unauthenticated `getInflationReward` RPC call — no special role or privilege required. It is not a crash or DoS, but a deterministic data-correctness bug: whenever a queried address's reward for the requested epoch was negative, this exact miscast occurs unconditionally as part of standard, low-rate RPC usage.

### Recommendation
Do not use `unsigned_abs()` to build `RpcInflationReward.amount`. Preserve the sign, e.g. by:
- Adding a signed `amount`/`i64` (or an explicit `is_negative`/`reward_type == DeactivatedStake` disambiguator) field to `RpcInflationReward`, mirroring how `cli-output` retains sign information for display, or
- At minimum, returning `None`/omitting the entry rather than reporting a spurious positive `amount` when `lamports < 0`.

### Proof of Concept
1. Construct/observe an epoch in which a queried stake account has `RewardType::DeactivatedStake` and a negative `lamports` value in the epoch-boundary or partition reward block (this is a legitimate, already-supported code path per `runtime/src/reward_info.rs` and `accounts-db/src/stake_rewards.rs`, which model `lamports` as signed specifically to support this case).
2. Call `getInflationReward` for that address/epoch via a standard unauthenticated JSON-RPC request.
3. Observe in `rpc/src/rpc.rs` lines 880-895 that `amount: reward.lamports.unsigned_abs()` converts the negative loss into a positive value in the response, indistinguishable from a legitimate reward gain — no client-recoverable indicator of the sign is provided.

Note: I could not fully confirm from the indexed code whether current mainnet reward-generation logic (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs`) can currently produce a negative `lamports` for `DeactivatedStake` in practice (the struct/type clearly supports it), since deep tracing of that file's negative-value-producing logic was not completed within the available searches — a Devin session with full file access would be needed to confirm the exact conditions that generate a negative `Reward.lamports` today.
