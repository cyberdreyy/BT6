# #Funds Redirected to New Operator Beneficiary After `set_beneficiary_for_operator()` — Retroactively Steals Already-Requested Commission - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::request_commission` records a pending commission distribution keyed by the **operator's address**, not the beneficiary that was active when the commission was requested. The actual payout recipient is resolved lazily, at `distribute()` time, via `beneficiary_for_operator(operator)`. Because unlocking commission requires waiting for the stake pool's lockup to expire (a multi-day/multi-week window), an operator can call `set_beneficiary_for_operator` after commission has already been requested but before it becomes withdrawable, redirecting the entire pending distribution — including amounts that accrued while the previous beneficiary was set — to the new beneficiary.

### Finding Description
In `request_commission_internal`, the pending commission is recorded with the operator's address as the distribution key: [1](#0-0) 

```
// Add a distribution for the operator.
add_distribution(
    operator,
    staking_contract,
    operator,
    commission_amount
);

// Request to unlock the commission from the stake pool.
// This won't become fully unlocked until the stake pool's lockup expires.
stake::unlock_with_cap(commission_amount, &staking_contract.owner_cap);
```

`stake::unlock_with_cap` only moves the commission into `pending_inactive` state; it does not become withdrawable (`inactive`) until the stake pool's lockup cycle ends, which can be a substantial delay.

When `distribute_internal` is eventually called (by anyone, permissionlessly), it resolves the actual payout address at that moment, not at request time: [2](#0-1) 

```
while (distribution_pool.shareholders_count() > 0) {
    let recipients = distribution_pool.shareholders();
    let recipient = recipients[0];
    let current_shares = distribution_pool.shares(recipient);
    let amount_to_distribute =
        distribution_pool.redeem_shares(recipient, current_shares);
    // If the recipient is the operator, send the commission to the beneficiary instead.
    if (recipient == operator) {
        recipient = beneficiary_for_operator(operator);
    };
    aptos_account::deposit_coins(
        recipient, coin::extract(&mut coins, amount_to_distribute)
    );
```

The beneficiary is looked up via `beneficiary_for_operator`, which simply returns whatever is currently stored: [3](#0-2) 

Because the distribution pool never snapshots "beneficiary at request time," any change to the beneficiary mapping — via `set_beneficiary_for_operator` — before `distribute()` executes retroactively redirects the entire pending commission, including any portion that accrued while a different beneficiary was configured: [4](#0-3) 

This mirrors the external report's root cause exactly: an in-flight withdrawal/settlement is initiated against one recipient context, an intervening privileged state change occurs, and the final settlement pays out to the new context instead of the one active when the request was made — resulting in the original claimant (the prior beneficiary) losing funds it was already entitled to.

### Impact Explanation
This directly falls under "Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account or traps value." A prior beneficiary (who may be a separate legal/economic entity relying on the operator's commission-sharing arrangement) can have their already-requested, already-unlocking commission fully diverted to a newly designated beneficiary simply because `distribute()` had not yet been called when the switch occurred. Given lockup periods that can last weeks, this window is large and easily exploitable by any operator wishing to short-change a beneficiary they've already agreed to share commission with.

### Likelihood Explanation
Medium-to-High: no special preconditions are required beyond the ordinary flow of `request_commission` → wait for lockup → `distribute`. Any operator who controls `set_beneficiary_for_operator` (gated only by the `operator_beneficiary_change_enabled` feature flag, not by any additional restriction preventing changes on in-flight distributions) can trigger this at any time before `distribute()` runs, and `distribute()` can be delayed indefinitely since it's a separate permissionless call.

### Recommendation
Snapshot the resolved beneficiary address at the time `add_distribution` is called for a commission request (i.e., use `beneficiary_for_operator(operator)` as the distribution key instead of `operator`), or otherwise disallow beneficiary changes while there is an outstanding unresolved commission distribution for that operator.

### Proof of Concept
1. Staker creates a staking contract with `operator`, commission 10%. Operator sets beneficiary to `A` via `set_beneficiary_for_operator`.
2. Time passes, rewards accrue. `A` (or the operator) calls `request_commission`, which calls `add_distribution(operator, staking_contract, operator, commission_amount)` and `stake::unlock_with_cap` — commission enters `pending_inactive`.
3. Before the stake pool's lockup expires, operator calls `set_beneficiary_for_operator(operator, B)`, changing the beneficiary mapping to `B`.
4. Once the lockup cycle ends, anyone calls `distribute(staker, operator)`. In `distribute_internal`, the recipient for the `operator` share is resolved as `beneficiary_for_operator(operator)`, which now returns `B`.
5. `B` receives the entire commission amount that had already been earned/requested while `A` was the beneficiary; `A` receives nothing.
