### Title
Signer switching a vote from Rejected to Accepted causes its weight to be double-counted across both tallies, spuriously triggering `SignersRejected` on a legitimately-approvable block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
In the miner-side StackerDB listener that tallies signer `BlockResponse`s for the coordinator, a signer who first rejects a block and later accepts the same block (a flow the signer client explicitly supports, per the accompanying `signerdb.rs` "reject_then_accept" behavior) has its weight added to `total_weight_approved` on the accept, but its earlier weight in `total_weight_rejected` is never removed. The two tallies are guarded independently (`gathered_signatures` for accepts, `responded_signers` for the first-ever response), so a vote flip is never reconciled, and `total_weight_approved + total_weight_rejected` can exceed `total_weight`.

### Finding Description
The `BlockResponse::Accepted` handler only guards double counting on `block.gathered_signatures.contains_key(&slot_id)`: [1](#0-0) 

If this same signer has previously sent a `BlockResponse::Rejected` for the same `block_sighash`, that rejection already incremented `total_weight_rejected` and inserted the slot into `responded_signers`: [2](#0-1) 

Because the accept path checks `gathered_signatures` (a different set than `responded_signers`), the later accept is *not* recognized as a flip: `total_weight_approved` is incremented by the signer's weight as if it were a fresh, unique approving signer, while `total_weight_rejected` still contains that same signer's weight from the earlier rejection — it is never subtracted. This is the direct analog of the reported ETH-emitter bug: a value/weight quantity that should move (or be reconciled) between two accounting buckets when a state changes is instead left counted in the old bucket while also being added to the new one.

Note the asymmetric case (accept-then-reject) is correctly guarded: `responded_signers.insert(slot_id)` returns `false` on the second response, so the reject-after-accept path skips incrementing `total_weight_rejected` entirely. Only the reject→accept direction leaks weight into both counters.

The CHANGELOG documents that this exact accept/reject double counting class was fixed for the signer's own local bookkeeping (`signerdb.rs`, tests `reject_then_accept`/`accept_then_reject`): [3](#0-2) 

but the same fix was not applied to the miner-node-side StackerDB listener that the block-signing coordinator relies on for `total_weight_approved`/`total_weight_rejected`.

### Impact Explanation
`signer_coordinator.rs`'s polling loop uses these tallies to decide the fate of a block proposal: [4](#0-3) 

Because a rejection is checked and acted upon *before* the approval branch, a stale/duplicated rejection weight from a signer who has since legitimately switched to Accepted can push `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight`, causing the miner to treat an otherwise validly-approvable block as `SignersRejected` — discarding it and permanently/temporarily excluding transactions based on a rejection reason that the issuing signer has already retracted. This is a liveness wedge: a single signer's normal, protocol-sanctioned vote-flip (reject→accept, e.g. after `should_reevaluate_reject_reason` lets it reconsider) can cause the miner to spuriously fail to build a block that in fact has enough real accepting weight, and to incorrectly ban/queue-out transactions based on a withdrawn objection. It also generally corrupts the invariant that `total_weight_approved + total_weight_rejected <= total_weight`, which downstream logging/threshold percentages and blocking-minority txid exclusion calculations rely on.

This does not directly cause a signer to sign an invalid/non-canonical block (the approval axis is still guarded per-slot via `gathered_signatures`), so it falls under the liveness-wedge impact category rather than a Critical safety break.

### Likelihood Explanation
This requires only a single signer (one slot) to send a `Rejected` response followed later by an `Accepted` response for the same `signer_signature_hash` — a sequence explicitly anticipated and supported by the signer's own reconsideration logic (`should_reevaluate_reject_reason`, and the `reject_then_accept` unit test in `signerdb.rs`). No majority, no other signer's key, and no StackerDB-sync trickery is needed — a normal, honest signer that initially rejects for a transient reason and later re-evaluates to accept is sufficient to trigger the double count on the miner/coordinator side.

### Recommendation
In the `BlockResponse::Accepted` handler, before adding to `total_weight_approved`, check whether the slot is already present in a rejection-tracking set (or explicitly remove the signer's weight from `total_weight_rejected`/`failed_txids` bookkeeping) when a signer transitions from rejected to accepted, mirroring the reconciliation already implemented in `stacks-signer/src/signerdb.rs`. Track vote state per-slot (e.g., an enum `Accepted`/`Rejected`) rather than two independently-guarded weight counters, so a flip in either direction correctly moves weight from one bucket to the other instead of allowing it to accumulate in both.

### Proof of Concept
1. Configure a reward set with signers `A` (weight `wA`) and others, with `weight_threshold` computed via `NakamotoBlockHeader::compute_voting_weight_threshold`.
2. Have signer `A` send `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for block `B` — `total_weight_rejected` becomes `wA`, `A`'s slot is added to `responded_signers`.
3. Have signer `A` (legitimately, e.g. after reconsidering) send `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same block `B` — since `gathered_signatures` does not yet contain `A`'s slot, `total_weight_approved` becomes `wA` as well.
4.
