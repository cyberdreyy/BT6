### Title
Stale rejection weight is never retracted when a signer flips Rejected→Accepted, letting one signer's phantom rejection push the miner coordinator into a false "block doomed" abort - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The mining-side `StackerDBListener` tallies per-block approval and rejection weight incrementally in `BlockStatus.total_weight_approved` / `total_weight_rejected`, deduplicating each vote type with a different guard. The guard used for rejections is not symmetric with the guard used for acceptances, so a signer that first rejects and later accepts the *same* block (an explicitly supported, ordinary state transition in the signer state machine: `LocallyRejected --> LocallyAccepted : re-evaluated`, per `docs/signer-flows.md:144`) gets counted in **both** tallies simultaneously. The stale rejection weight is never removed, so `total_weight_rejected` can remain permanently inflated by a signer who no longer rejects the block, biasing the coordinator's accept/reject decision.

### Finding Description
`StackerDBListener` processes `BlockResponse::Accepted` and `BlockResponse::Rejected` messages independently: [1](#0-0) 

The accept path guards weight-addition with `!block.gathered_signatures.contains_key(&slot_id)`, then unconditionally inserts the slot into both `gathered_signatures` and `responded_signers`. [2](#0-1) 

The reject path guards weight-addition with `block.responded_signers.insert(slot_id)` (true only if this is the slot's first-ever response).

Because both branches write into the *same* `responded_signers` set but only the accept branch also writes into a separate `gathered_signatures` map that the accept path itself checks:

- **Accept → Reject** (signer signs, then somehow tries to reject the same hash): protected. `responded_signers` already contains the slot from the earlier accept, so the reject branch's `insert()` returns `false` and `total_weight_rejected` is *not* incremented.
- **Reject → Accept** (signer rejects, then later reconsiders and signs the same block hash): **not protected**. The reject branch has already added the signer's weight to `total_weight_rejected` and inserted the slot into `responded_signers`, but the accept branch only checks `gathered_signatures` (which is still empty for this slot) — so it unconditionally adds the same signer's weight to `total_weight_approved` as well. The earlier rejection weight is never subtracted.

The result: `total_weight_approved + total_weight_rejected` can exceed the signer's true, single, current vote weight — the invariant "each signer's weight counted at most once across the two tallies" is broken. This is a direct analog of the FTC bug class: an action taken on one side of a state pair (reject) is not undone/reconciled when the actor's state changes (accept), so a bookkeeping total intended to represent a distinct set of current voters instead retains stale contributions.

This matters because the miner's decision loop in `SignerCoordinator::gather_signatures` checks the rejection condition *first, every iteration*: [3](#0-2) 

```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { ... });
} else if block_status.total_weight_approved >= self.weight_threshold {
    ... return Ok(...)
}
```

If the phantom, never-retracted rejection weight (from a signer who has since switched to accepting) combines with genuine rejections/timeouts from other signers to cross the blocking-minority threshold (`total_weight - weight_threshold`, i.e. >30%), the coordinator will conclude the block is globally doomed and abort it via `SignersRejected`, even though the *true* current distinct-signer weight (recomputed from each signer's latest, real vote) might already satisfy the 70% approval threshold. Nothing in the codebase re-derives these totals from a per-signer "latest vote" map; they are pure running sums that are only ever incremented (aside from an explicit `reset_rejections` called on a *timeout*, not on a vote flip).

### Impact Explanation
This is a liveness wedge on the node/coordinator side: a single signer performing an ordinary, protocol-sanctioned reject→accept re-evaluation (Section 2/5 of `docs/signer-flows.md`, `LocallyRejected --> LocallyAccepted`) permanently inflates the rejection tally for that block hash in the miner's local `BlockStatus`. Combined with any other legitimate reject/timeout weight from the rest of the signer set, this stale, double-counted weight can push the miner into erroneously declaring the block globally rejected (`SignersRejected`) and abandoning it, even when the *current* signer vote distribution would actually clear the 70% approval threshold. This wastes the round, forces a new proposal, and — in adversarial conditions — lets one signer amplify their weight's effect on the rejection side without needing majority collusion, degrading block production liveness. It maps to the "wedge the state machine" / "aggregated-weight vs verified-accepts" class explicitly in scope.

### Likelihood Explanation
No majority or malicious collusion is required. The triggering transition (`LocallyRejected -> LocallyAccepted`, driven by `should_reevaluate_reject_reason` / `should_reevaluate_block` in `stacks-signer/src/v0/signer.rs`) is a normal, documented part of the signer's re-evaluation logic (e.g., a signer initially rejects because a conflicting block was fresh, then later signs once that conflict goes stale). Any single signer exhibiting this ordinary behavior for a block that other signers are also slow to approve (network delay, near-threshold rejections) is sufficient to trip the false-doom path. This requires no exploit beyond normal signer/network timing, making it a plausible, low-effort occurrence rather than a purely theoretical one.

### Recommendation
Track each signer's *current* vote in a single per-slot map (e.g., `HashMap<u32, Vote>` where `Vote = Accepted(sig) | Rejected`) instead of two independently-incremented running totals guarded by different sets. Recompute `total_weight_approved` / `total_weight_rejected` by summing weights from that map on each update (or explicitly subtract the old contribution before adding the new one when a slot's vote changes), so a signer's weight is always counted exactly once, on the side of their most recent vote. Symmetrically apply the same guard logic to both the accept and reject branches (e.g., both should check/update one canonical "current vote" record per slot rather than the asymmetric `gathered_signatures` vs `responded_signers` combination).

### Proof of Concept
Conceptual sequence (mirrors the FTC "open-then-close instantly" pattern of exploiting an unretracted running total):
1. Miner proposes block B; `StackerDBListener::insert_block` initializes `BlockStatus { total_weight_approved: 0, total_weight_rejected: 0, responded_signers: {} , gathered_signatures: {} }` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:693-700`).
2. Signer S (slot k, weight w) initially sends `BlockResponse::Rejected` for B (e.g., because a competing block was fresh at proposal time). Handler at lines 515-519 does `responded_signers.insert(k) == true` ⇒ `total_weight_rejected += w`.
3. Signer S later re-evaluates (per `should_reevaluate_reject_reason` / the `LocallyRejected -> LocallyAccepted` transition documented in `docs/signer-flows.md:144`) and sends `BlockResponse::Accepted` for the *same* B. Handler at lines 443-446 checks `gathered_signatures.contains_key(k)` — false, since S never accepted before — so `total_weight_approved += w` as well.
4. Now `BlockStatus` for B simultaneously carries `w` inside `total_weight_rejected` (stale) and `w` inside `total_weight_approved` (current, correct). No code path ever subtracts `w` back out of `total_weight_rejected`.
5. If enough other signers are also slow/rejecting such that `total_weight_rejected(stale-inclusive).saturating_add(weight_threshold) > total_weight`, the coordinator's loop (`signer_coordinator.rs:509-519`) returns `Err(SignersRejected{...})` on its very next poll — before ever reaching the `total_weight_approved >= weight_threshold` branch — even though S's true current vote (and possibly enough others') should have let the block reach acceptance.

I was not able to execute this against a live test harness (no filesystem/terminal access here); the sequence above is derived directly from reading the exact guard logic in `stackerdb_listener.rs` and the documented signer re-evaluation transitions in `docs/signer-flows.md`, and would need to be exercised with an integration test (e.g., extending the existing `stacks-node/src/tests/signer/v0/mod.rs` harness) to obtain a concrete runtime trace.
