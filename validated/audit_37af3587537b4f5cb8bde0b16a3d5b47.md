### Title
Preregistration Withdrawal-Credential Binding Lets the Validator's Own Key-Holder Grief and Destroy a Legitimate Depositor's Deposit - (File: `specs/_features/eip8205/beacon-chain.md`)

### Summary
EIP-8205's `process_preregistration_request` and `process_deposit_request` implement a pubkey→withdrawal-credentials binding intended to protect delegated-staking depositors from front-running [1](#0-0) . In practice, whoever controls the BLS private key for a not-yet-deposited pubkey — e.g. a key-generation party in a delegated/staking-as-a-service setup, analogous to the "owner of the LaunchEvent token" in the referenced report — can unilaterally record a binding to arbitrary withdrawal credentials before the true depositor's deposit lands. Any subsequent legitimate `DepositRequest` whose credentials don't match that binding is silently discarded rather than queued, permanently losing the depositor's already-locked execution-layer ETH with no recovery path.

### Finding Description
`process_preregistration_request` accepts a `PreregistrationRequest` and stores a binding as long as the signature verifies against the pubkey (`is_valid_preregistration_signature`) and no validator/pending deposit for that pubkey exists yet [2](#0-1) . The signature check only proves possession of the pubkey's private key — it does not require that the signer be the intended depositor, nor that `withdrawal_credentials` refer to anything the signer controls [3](#0-2) .

Once an active binding exists, `process_deposit_request` enforces it against every subsequent deposit for that pubkey:

```python
preregistration = get_active_preregistration(state, deposit_request.pubkey)
if preregistration is not None:
    if deposit_request.withdrawal_credentials != preregistration.withdrawal_credentials:
        return
    ...
``` [4](#0-3) 

If credentials don't match, the function simply `return`s — the deposit request is dropped, no `PendingDeposit` is appended, and there is no way to recover the funds. The binding stays enforceable for the entirety of `PREREGISTRATION_EXPIRY_SLOTS` (2**18 slots) [5](#0-4) [6](#0-5) .

This mirrors the report's bug class exactly: a party with a narrow privileged capability (owning the LaunchEvent token / here, owning the pubkey's private key) can pre-empt a check ("pair doesn't exist yet" / "no active preregistration binding yet") that a legitimate participant's later, honest transaction depends on, permanently blocking that participant's intended state transition and — unlike the pure DOS in the report — actually destroying already-committed Gwei, since the execution-layer deposit contract has already irrevocably locked the depositor's ETH by the time the beacon chain drops the corresponding `DepositRequest`.

### Impact Explanation
This breaks the equality between execution-layer deposited Gwei and the corresponding beacon-chain accounting: ETH is locked in the deposit contract on the EL side, but the CL-side `PendingDeposit`/validator credit that should represent it is never created. This is a "Gwei destroyed" outcome, matching the Critical impact bar. The griefing party (key holder) loses nothing — no stake is put at risk on their side — so this is not merely "the attacker's own stake" being lost; it's the depositor's already-spent funds.

### Likelihood Explanation
The attack requires only that some party other than the ultimate fund-depositor holds the validator's BLS private key at deposit time — a normal, common arrangement in delegated/custodial or staking-as-a-service deployments (which is precisely the use case EIP-8205's introduction text cites as the feature's target audience) [7](#0-6) . No coalition, foreign key compromise, or client bug is needed: it's simply the key-generation party using its ordinary signing capability adversarially, exactly as "owner of LaunchEvent token" used its ordinary token-ownership capability adversarially in the referenced report. The window to act is generous (deposit request must be preceded in slot order, and the binding covers ~2^18 slots).

### Recommendation
Do not let a preregistration silently swallow deposits whose credentials mismatch. Options: (1) require any binding-registrant to also prove control of the withdrawal credentials being bound (e.g., signature from the credential's key/address) so a pure pubkey-holder cannot bind arbitrary credentials on someone else's behalf; (2) instead of dropping a mismatched deposit outright, refund/queue it for withdrawal via a mechanism symmetrical to other rejected EL-triggered requests so no Gwei is destroyed; (3) restrict who may submit a `PreregistrationRequest` for a given pubkey to the same execution-layer address that will submit the corresponding deposit (binding registration and deposit tied to the same EL sender), removing the ability of a separate key-holder to preempt the depositor.

### Proof of Concept
1. Party K (key generator for a delegated-staking pubkey `P`, not the ultimate depositor D) submits a `PreregistrationRequest{pubkey=P, withdrawal_credentials=C_k, signature=Sign(P_priv, P, C_k)}`. `process_preregistration_request` accepts it since no validator/pending-deposit exists yet for `P`, storing `StoredPreregistration(P, C_k, expiry_slot=slot+PREREGISTRATION_EXPIRY_SLOTS)` [2](#0-1) .
2. Depositor D, unaware of the binding, sends a normal 32 ETH deposit transaction on the execution layer with `withdrawal_credentials=C_d != C_k`, correctly signed. The EL deposit contract locks D's ETH.
3. When the resulting `DepositRequest` is processed by `process_deposit_request`, `get_active_preregistration` returns K's still-active binding; since `C_d != C_k`, the function returns immediately without appending a `PendingDeposit` [4](#0-3) .
4. D's 32 ETH remains locked in the EL deposit contract permanently, with no corresponding beacon-chain credit and no defined recovery path — Gwei destroyed, at zero cost to K.

def process_preregistration_request(state: BeaconState, request: PreregistrationRequest) -> None:
    pubkey = request.pubkey

    # An active binding for this pubkey makes the new request a no-op,
    # whether the duplicate is exact or conflicting
    if get_active_preregistration(state, pubkey) is not None:
        return

    # A pubkey with an existing validator cannot be preregistered
    if pubkey in [validator.pubkey for validator in state.validators]:
        return

    # A pubkey with a valid pending deposit cannot be preregistered
    if is_pending_validator(state.pending_deposits, pubkey):
        return

    # The capacity check counts only active records, so the timing of the
    # garbage-collection sweep does not affect admission. It applies to
    # appends and to replacements alike, since both create an active binding
    active_preregistrations = [
        preregistration
        for preregistration in state.validator_preregistrations
        if is_active_preregistration(state, preregistration)
    ]
    if len(active_preregistrations) >= PREREGISTRATIONS_LIMIT:
        return

    if not is_valid_preregistration_signature(state, request):
        return

    preregistration = StoredPreregistration(
        pubkey=pubkey,
        withdrawal_credentials=request.withdrawal_credentials,
        expiry_slot=state.slot + PREREGISTRATION_EXPIRY_SLOTS,
    )
    index = get_stored_preregistration_index(state, pubkey)
    if index is not None:
        # Replace the expired record in place
        state.validator_preregistrations[index] = preregistration
    else:
        state.validator_preregistrations.append(preregistration)
```

def process_deposit_request(state: BeaconState, deposit_request: DepositRequest) -> None:
    # [New in EIP8205]
    preregistration = get_active_preregistration(state, deposit_request.pubkey)
    if preregistration is not None:
        if deposit_request.withdrawal_credentials != preregistration.withdrawal_credentials:
            return

        if not is_valid_deposit_signature(
            deposit_request.pubkey,
            deposit_request.withdrawal_credentials,
            deposit_request.amount,
            deposit_request.signature,
        ):
            return

        remove_stored_preregistration(state, deposit_request.pubkey)

    state.pending_deposits.append(
        PendingDeposit(
            pubkey=deposit_request.pubkey,
            withdrawal_credentials=deposit_request.withdrawal_credentials,
            amount=deposit_request.amount,
            signature=deposit_request.signature,
            slot=state.slot,
        )
    )
