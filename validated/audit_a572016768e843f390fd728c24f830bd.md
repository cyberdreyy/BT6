### Title
Buffer-period deposits mint tranche shares at a stale price that excludes accrued ProgrammableBorrower vault PnL, letting a new lender capture yield earned before their deposit - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external report describes minting at a fresh asset rate against a stale pool valuation, over-valuing the incoming deposit relative to existing holders. In the idle-tranches credit vault, the analog is the buffer phase of a programmable-borrower pool: vault-sleeve PnL accrues inside `ProgrammableBorrower` and is tracked only in `bufferedVaultDelta`/`bufferInterest`, which is not reflected in `getContractValue()`/`_managedContractValue()` until the next `stopEpoch` realizes it via `totalInterestDueNow()`. A lender depositing during the buffer therefore mints AA/BB shares at a pre-PnL price and immediately shares in yield that accrued entirely before their deposit.

### Finding Description
`ProgrammableBorrower` parks idle capital in an external ERC4626 vault. Vault PnL generated while the pool is in the buffer is snapshotted into `bufferedVaultDelta` at `onStartEpoch` and paid borrower interest accumulates in `bufferInterest`, but neither value enters the CDO NAV while the buffer is running. [1](#0-0) [2](#0-1) 

`totalInterestDueNow()` — the only channel through which this PnL reaches tranche prices — is read by `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration`, where `_updateAccounting()` then distributes the gain across all current tranche holders via `trancheAPRSplitRatio`. [3](#0-2) 

Meanwhile, ordinary `depositAA`/`depositBB` remain enabled during the buffer (`restoreOperations` only re-pauses while `isEpochRunning`, and after a clean stop the pool is unpaused). `_deposit` calls `_updateAccounting()`, which computes NAV from `getContractValue()` — the strategy-token value — and mints shares at that price via `_mintSharesAtCurrPrice`. Because the programmable sleeve's `bufferedVaultDelta`/`bufferInterest` is held off-contract in `ProgrammableBorrower`, the mint price excludes yield already accrued to the pool. [4](#0-3) [5](#0-4) 

Broken invariant: fair mint/burn. The depositor's shares are priced against a NAV that omits accrued-but-unrealized pool yield, so at the next `stopEpoch` the newly minted shares dilute the pre-existing holders' claim on `totalInterestDueNow()`. This mirrors the report: `depositTby` pulling `pool.getRate` (fresh) while the pool's own valuation is only synced once per 24h via `poke`; here the deposit is valued at the CDO price (stale) while the pool's true claim on `ProgrammableBorrower` (fresh) is higher.

### Impact Explanation
A KYC-passed lender deposits `D` underlying during the buffer at price `P_stale = (NAV - bufferedPnL)/supply`. When the next epoch stops, `totalInterestDueNow()` injects the buffered vault gain `G` into `_updateAccounting`, raising the tranche price for all supply including the attacker's shares. The attacker captures `minted * (G / totalSupply)` of yield produced before they entered; existing holders lose the identical amount. The loss scales with buffer length, vault yield, and deposit size — a bounded but direct transfer of yield, matching the severity class of the original report.

### Likelihood Explanation
Requires a programmable-borrower deployment (`isProgrammableBorrower`) with the ERC4626 sleeve earning non-zero yield during the buffer, plus an enabled deposit path (`isWalletAllowed` KYC for the attacker, pool unpaused between epochs). Any unprivileged whitelisted lender can execute it; no privileged action needed. Likelihood is moderate: buffer windows are typically short and the extractable amount is the attacker's pro-rata share of buffer PnL only, so the theft is small per execution but repeatable every buffer period.

### Recommendation
Include the accrued buffer PnL in the deposit-time valuation. Concretely, either (a) have `getContractValue`/`_managedContractValue` add `ProgrammableBorrower`'s pending buffer delta (e.g., expose `bufferedVaultDelta + bufferInterest` or a `pendingBufferYield()` view and fold it into NAV), or (b) checkpoint/settle buffered PnL into strategy tokens at `onStartEpoch` before reopening deposits, so `_updateAccounting` on the first buffer deposit prices it in. Both approaches mirror the report's fix of excluding un-poked yield from the mint rate — here it is the inverse direction (un-credited yield excluded from NAV), but the same invariant: no participant should receive shares whose value embeds yield accrued before their deposit.

### Proof of Concept
Sketch of a Foundry fork test (modeled on `test/foundry/IdleCreditVault.t.sol` mid-epoch tests):

```solidity
function testBufferDepositCapturesAccruedVaultPnL() external {
    // setup: programmable borrower pool, vault = ERC4626 earning yield
    idleCDO.depositAA(1000 * ONE_SCALE);          // existing lender
    _startEpochAndCheckPrices(0);

    // stop epoch cleanly -> buffer begins; ProgrammableBorrower funds stay in vault
    _toggleEpoch(false, apr, expectedFunds);
    // warp through buffer; external vault share price rises by G
    vm.warp(block.timestamp + bufferPeriod);
    _increaseExternalVaultPrice(G);               // simulate accrued vault yield

    // attacker deposits during buffer at stale price (no bufferedVaultDelta in NAV)
    address attacker = _kycLender();
    deal(underlying, attacker, DEPOSIT);
    vm.startPrank(attacker);
    IERC20(underlying).approve(cdo, DEPOSIT);
    uint256 minted = IdleCDOEpochVariant(cdo).depositAA(DEPOSIT);
    vm.stopPrank();

    // next epoch runs and stops; bufferedVaultDelta is realized into tranche price
    _startEpochAndCheckPrices(0);
    _toggleEpoch(false, apr, expectedFunds2);

    // attacker's shares now redeem for more than DEPOSIT + their own prorated yield:
    // they captured minted * G / totalSupply of pre-deposit yield
    uint256 attackerValue = minted * cdo.virtualPrice(AA) / 1e18;
    assertGt(attackerValue, DEPOSIT + _ownYieldShare(DEPOSIT));
}
```

Uncertainty: the exact magnitude depends on whether the IdleCreditVault strategy `price()` partially reflects `ProgrammableBorrower`'s vault position; from the code reviewed, buffer PnL is only realized into NAV through `totalInterestDueNow()` at `stopEpoch`, which is the basis for this finding. A confirming PoC should assert `getContractValue()` is unchanged by external-vault price movement during the buffer.
