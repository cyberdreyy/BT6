### Title
Job script output can forge the JSON exit-status marker and spoof stage completion on Kubernetes executor - ([File: executors/kubernetes/kubernetes.go], [File: shells/bash.go])

### Summary
When `useJSONInitializationTermination` is forced on for the Kubernetes executor, the completion signal for a build stage is a plain JSON line (`{"command_exit_code": N, "script": "..."}`) written to the same log stream/file that carries the user's own build stdout. `forwardLogLine` treats any line that satisfies `StageCommandStatus.TryUnmarshal` as an authoritative "the stage command has exited" signal, with no check that the marker actually originated from the `runner_script_trap` in `bashJSONTerminationScript` rather than from user-printed output.

### Finding Description
`NewBashWriter` forces `useJSONInitializationTermination` for the Kubernetes executor (non-legacy execution strategy) [1](#0-0) . When enabled, `Finish` prepends `bashJSONInitializationScript` and appends the `runner_script_trap` from `bashJSONTerminationScript`, which prints `{"command_exit_code": $exit_code, "script": "$0"}` on shell exit [2](#0-1) [3](#0-2) .

The generated container command pipes both stdout and stderr of the stage script through `tee -a` into the executor's log file: `2>&1 | tee -a <logfile>` [4](#0-3) . That log file is read line-by-line by `processLogs`, and each line is passed to `forwardLogLine`, which unconditionally attempts `status.TryUnmarshal(line)`; if it succeeds and `status.IsExited()` is true, the executor immediately signals `s.remoteProcessTerminated <- status`, treating it as the real end of the current stage [5](#0-4) .

Because the same pipe carries the raw stdout of the user's own build commands (the `script:` lines from `.gitlab-ci.yml`), an attacker-controlled job step that simply does `echo '{"command_exit_code": 0, "script": "anything"}'` produces a line indistinguishable, from the parser's point of view, from the genuine trap-generated marker. There is no reserved prefix, HMAC, sequence number, or "only trust the last line before EOF" check tying the marker to the real trap invocation — `forwardLogLine`/`TryUnmarshal` validate only JSON shape, not provenance.

### Impact Explanation
A normal pipeline author can inject a forged completion marker into their own job's stdout to make the Kubernetes executor believe the currently running stage script has already exited (with an attacker-chosen exit code), while the actual script keeps running in the container. This can be used to: force a stage to be reported as succeeded (exit code 0) even though the real script later fails, causing CI status forgery/bypass of build-gate logic that depends on the job's real exit code; or desynchronize the runner's stage tracking from the container's actual execution state, since the runner proceeds to the next stage/log-forwarding-resume logic while the previous script is still executing and its later output/exit code is no longer looked at. This is a job self-manipulation bug (a job forging its own success status), not a cross-project escape, so the blast radius is limited to the job's own reported outcome and any external gating logic that trusts it.

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: Kubernetes executor with the new (default, non-legacy) execution strategy, and any `script:`/`after_script:` line able to `echo` arbitrary text to stdout — something every GitLab CI author can do. No special CI config, image, or admin cooperation is required, and the injected line does not need to be exact except for matching the JSON keys the unmarshaler checks, which is easily discoverable from the shipped `bashJSONTerminationScript` constant in the runner's own open-source code.

### Recommendation
Do not trust bare JSON shape as proof that a line is the trap's own marker. Options: (1) emit the marker with an unforgeable/unique-per-invocation token (e.g., a per-stage random nonce known only to the runner and injected into the trap script, then required in `TryUnmarshal` validation) so user-printed JSON cannot collide; (2) emit the marker on a distinct, out-of-band channel instead of interleaving it with the container's regular stdout/stderr (e.g., a separate control fifo/file not exposed to user script output); (3) only accept the marker after confirming it is the last line and that the underlying kube exec stream has actually closed/reported completion, rather than treating any well-formed line mid-stream as authoritative.

### Proof of Concept
Go test plan (extend `TestProcessLogs`/`forwardLogLine` tests in `executors/kubernetes/kubernetes_test.go`):
1. Construct a fake log file where line 1 is ordinary build output, line 2 is an attacker-forged marker `{"command_exit_code": 0, "script": "/fake"}`, and line 3 is more build output that would represent the real (still-running) command's later, differing output/exit code.
2. Feed this synthetic stream through the executor's log processor / `forwardLogLine` exactly as `processLogs` does.
3. Assert that `s.remoteProcessTerminated` receives a `StageCommandStatus{CommandExitCode: 0}` immediately after line 2, before the "real" script output/exit in line 3 is processed — proving the executor commits to a stage result based purely on attacker-controlled stdout content, with no correlation to the genuine trap invocation.

Note: I was not able to load the source defining `shells.StageCommandStatus`/`TryUnmarshal` (only its test file was found) within tool call limits, so the exact leniency of the unmarshal validation (e.g., whether extra/missing fields are tolerated) is inferred from the JSON produced by `bashJSONTerminationScript` and the test helper `getCommandExitStatus`, not directly confirmed from that source file.

	if shell == shells.SNPowershell {
		// powershell outputs utf16, so we re-encode the output to utf8
		// this is important because our json decoder that detects the exit status
		// of a job requires utf8.Converting command output to strings with %{"$_"}
		// prevents a powershell complaint about native command output on stderr.
		return fmt.Sprintf("2>&1 | %%{ \"$_\" } | Out-File -Append -Encoding UTF8 %s", s.logFile())
	}

	return fmt.Sprintf("2>&1 | tee -a %s", s.logFile())
}

func (s *executor) forwardLogLine(w io.Writer, line string) {
	var status shells.StageCommandStatus
	if !status.TryUnmarshal(line) {
		if _, err := w.Write([]byte(line)); err != nil {
			s.BuildLogger.Warningln(fmt.Sprintf("Error writing log line to trace: %v", err))
		}

		return
	}

	s.BuildLogger.Debugln(fmt.Sprintf("Setting remote stage status: %s", status))
	s.remoteStageStatusMutex.Lock()
	s.remoteStageStatus = status
	s.remoteStageStatusMutex.Unlock()

	if status.IsExited() {
		s.remoteProcessTerminated <- status
	}
}
