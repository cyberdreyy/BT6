### Title
Anyone can un-exit a builder via a permissionless top-up deposit, resetting `withdrawable_epoch` without the builder's authority - (File: `specs/gloas/beacon-chain.md`)

### Summary
`process_builder_deposit_request` handles execution-layer deposit requests that top up an *existing* builder's balance. When the target builder has already exited and been swept (`withdrawable_epoch != FAR_FUTURE_EPOCH` and `balance == 0`), the function resets `builder.withdrawable_epoch` to `epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY` before crediting the deposit — even though the spec's own documentation states "Exited builders cannot be reactivated." No signature or ownership check is performed on this path, since `is_valid_builder_deposit_signature` is only invoked in the "new builder" branch, not the top-up branch.

### Finding Description [1](#0-0) 

```python
def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:
    # Ignore deposits with unexpected withdrawal credential prefixes
    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
        return

    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        if is_valid_builder_deposit_signature(request):
            add_builder_to_registry(...)
    else:
        builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
        builder = state.builders[builder_index]

        # If exited and swept, reset the withdrawable epoch
        if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
            epoch = get_current_epoch(state)
            builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY

        # Increase balance by deposit amount
        builder.balance += request.amount
```

The condition `request.pubkey not in builder_pubkeys` is `False` when the pubkey belongs to an already-registered (and possibly exited) builder, so execution falls into the `else` branch. That branch:
1. Requires only that `request.pubkey` match an existing entry in `state.builders` — the pubkey is public information, visible on-chain.
2. Never calls `is_valid_builder_deposit_signature`, and never checks `request.withdrawal_credentials` (or any execution address) against `builder.execution_address`, unlike the sibling function `process_builder_exit_request`, which explicitly enforces `builder.execution_address != request.source_address` before allowing any mutation.
3. Unconditionally overwrites `builder.withdrawable_epoch` whenever the swept-and-exited condition holds, discarding the value that `initiate_builder_exit`/the sweep mechanism previously set.

This is the same bug shape as the reported `Vesting.vest()` issue: a function reachable by *any* caller (here, any account able to trigger an execution-layer deposit request naming an existing builder's pubkey and depositing the minimal required amount) unconditionally overwrites a piece of protected per-entity state (`withdrawable_epoch`) that is documented to be immutable once an exit has been swept, and that should only change through the builder's own authorized exit flow. The spec's own prose ("Exited builders cannot be reactivated") states the invariant that the code violates.

### Impact Explanation
Resetting `withdrawable_epoch` un-exits the builder's slot: the "exited and swept" builder no longer satisfies the swept condition (`balance == 0`) after the deposit, and its withdrawability is pushed `MIN_BUILDER_WITHDRAWABILITY_DELAY` epochs into the future again. Depending on how `is_active_builder` and downstream payment/participation logic key off `withdrawable_epoch`/`exit_epoch`, this allows a third party — without holding the builder's signing key or execution address — to mutate a builder's lifecycle state that only the builder (via `process_builder_exit_request`, itself authenticated by `execution_address`) is supposed to control. This matches the in-scope class "a validator or builder mutated without its authority," which is rated High.

### Likelihood Explanation
Likelihood is high given the small friction to trigger it: builder pubkeys are public, deposit requests are permissionless (only requiring `is_builder_withdrawal_credential` on the prefix of `request.withdrawal_credentials`, unrelated to the target builder's identity), and only a minimal deposit amount is needed to enter the top-up branch. No coalition, malicious peer, or economic majority is required — any single unprivileged account issuing an EL deposit request can trigger the mutation once the target builder is in the swept state.

### Recommendation
In `process_builder_deposit_request`, only reset/extend `builder.withdrawable_epoch` for a top-up when the request is authenticated as coming from the builder's own `execution_address` (mirroring the check already present in `process_builder_exit_request`), or better, disallow top-ups on already-exited (`withdrawable_epoch != FAR_FUTURE_EPOCH`) builder slots entirely and instead route the deposited amount to be immediately withdrawn to `builder.execution_address`, consistent with the documented intent that "Any deposit sent to an exited builder will be withdrawn to the builder's execution address."

### Proof of Concept
1. Builder `B` with pubkey `P` and `execution_address = A` registers via `process_builder_deposit_request` (new-builder branch, signature-checked).
2. `B` calls `process_builder_exit_request` (or is otherwise exited); eventually the sweep sets `state.builders[idx].balance == 0` while `withdrawable_epoch` is set to some finite epoch `E` (no longer `FAR_FUTURE_EPOCH`).
3. Attacker `M` (unrelated to `A`, no signature or key for `P`) submits a `BuilderDepositRequest` with `pubkey = P` and `withdrawal_credentials` merely satisfying `is_builder_withdrawal_credential` (arbitrary execution address of `M`'s choosing, e.g. `M`'s own address) and `amount = MIN_DEPOSIT_AMOUNT`.
4. `process_builder_deposit_request` takes the `else` branch (pubkey already registered), finds `builder.withdrawable_epoch (E) != FAR_FUTURE_EPOCH` and `balance == 0`, and sets `builder.withdrawable_epoch = current_epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY`, then adds the deposit to `builder.balance` — all without any check that `M` controls `A` or `P`.
5. Builder `B`'s exited slot is thereby reactivated (its withdrawability pushed into the future) purely by an unrelated third party's minimal deposit, contradicting the documented "Exited builders cannot be reactivated" invariant and mutating builder state without the builder's authorization. def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
