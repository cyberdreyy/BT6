### Title
Malicious operator beneficiary permanently blocks `staking_contract::distribute` for both operator and staker - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`staking_contract::distribute_internal` pays out **all** unlocked stake in a single atomic loop that calls `aptos_account::deposit_coins` for every shareholder in the contract's `distribution_pool`, including the staker and the operator's beneficiary. Since Move transactions are all-or-nothing, if the deposit to *any single* recipient aborts, the entire distribution reverts — including the legitimate staker's own already-unlocked funds. An operator fully controls `set_beneficiary_for_operator`, and can set the beneficiary to an address it configures to permanently reject direct coin transfers, which makes every future `distribute()`/`distribute_internal()` call abort forever. This is the same bug class as the reNFT report: an externally-controlled "reject" condition on one counterparty causes a shared settlement function to revert, freezing funds belonging to *other*, non-malicious parties.

### Finding Description
`distribute_internal` withdraws the pool's total unlocked/inactive stake and then loops over every shareholder in `distribution_pool`, redeeming shares and calling `aptos_account::deposit_coins`, substituting the operator's beneficiary for the operator recipient: [1](#0-0) 

`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient is not yet registered for the coin and has explicitly disabled direct transfers via `can_receive_direct_coin_transfers`: [2](#0-1) 

An operator can create an address, from that address call `set_allow_direct_coin_transfers(false)` (an entirely permissionless, self-serve entry function), never register that account for `AptosCoin`, and then set it as the beneficiary via `set_beneficiary_for_operator`, which is unrestricted to any `new_beneficiary` address: [3](#0-2) 

Because `distribute_internal` redeems shares for *all* shareholders — staker, operator/beneficiary — in one atomic loop before any deposits are finalized, one poisoned recipient makes the whole function abort every time it's called, for as long as that shareholder still has a nonzero share balance in `distribution_pool`. There is no alternate withdrawal path for the staker in `staking_contract.move`: `unlock_stake`, `unlock_rewards`, and `request_commission` all merely add entries to the same `distribution_pool`; `distribute`/`distribute_internal` is the only function that actually pays out inactive/unlocked stake. This same pattern is duplicated in `vesting::distribute`, which loops over all shareholders identically: [4](#0-3) 

### Impact Explanation
Once the operator sets a poisoned beneficiary, the entire staking contract's unlocked/inactive stake (belonging to the staker, not the operator) becomes permanently un-withdrawable through the documented flow — a non-recoverable loss of claim rights for the staker, triggered purely by operator misbehavior with a role they legitimately hold (operator), but which harms a different, non-consenting party (the staker) who cannot fix or bypass the operator's beneficiary setting. This matches the "Permanent lock or non-recoverable loss of claim rights in stake ... commission, beneficiary ... flows" impact bucket.

### Likelihood Explanation
The attack requires no special privileges beyond the operator role, which is obtainable by anyone a staker chooses to appoint (or which an attacker could convince a staker to appoint, e.g. through a seemingly normal staking-as-a-service offer). All primitives used (`set_allow_direct_coin_transfers`, `set_beneficiary_for_operator`) are ordinary, permissionless entry functions with no guardrails preventing this configuration.

### Recommendation
- Decouple recipients in `distribute_internal`/`vesting::distribute`: catch/skip failures for individual recipients (e.g. via `move` error-handling patterns, or by depositing into a per-recipient claimable/pull-based escrow) instead of aborting the whole batch.
- Alternatively, validate that a beneficiary can actually receive `AptosCoin` (already registered or `can_receive_direct_coin_transfers` true) at the time `set_beneficiary_for_operator` is called, and re-validate on every `distribute` — falling back to depositing into the beneficiary's *unmodifiable* fallback (e.g. the operator address itself) if the configured beneficiary cannot currently accept funds, so honest stakers are never blocked by another party's account configuration.

### Proof of Concept
1. Staker creates a staking contract with `operator` O via `create_staking_contract`.
2. O creates a fresh account `B`, funds it minimally to exist, and calls `aptos_account::set_allow_direct_coin_transfers(B, false)` — `B` never registers a CoinStore/primary store for `AptosCoin`.
3. O calls `staking_contract::set_beneficiary_for_operator(O, B)`.
4. Time passes, rewards accrue; staker calls `unlock_stake`/`unlock_rewards`, which succeed (they only manipulate `distribution_pool` and call `stake::unlock_with_cap`).
5. Once the stake pool's lockup ends, any call to `staking_contract::distribute(staker, O)` reaches `distribute_internal`, redeems shares, and attempts `aptos_account::deposit_coins(B, ...)` for the operator's commission share — this aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, reverting the whole transaction and undoing the staker's redemption as well.
6. `distribute` can never succeed again while `B` remains beneficiary with shares outstanding; the staker's unlocked stake is permanently stuck in the stake pool with no way to reach their `CoinStore`.

**Caveat:** I was not able to fully confirm within the indexed code whether `coin::is_account_registered<AptosCoin>` interacts identically for freshly created accounts under the current fungible-asset migration (some `deposit`/`primary_fungible_store` internals were only partially visible via the index). If `AptosCoin`'s primary store is now lazily and unconditionally created regardless of `DirectTransferConfig` (bypassing the `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` check entirely for the native coin), then this specific PoC vector would not apply, and it should be validated with an actual Move test / Devin session before treating this as confirmed-exploitable in production. I recommend starting a Devin session to write and run a Move unit test simulating this exact sequence in `staking_contract.move`'s test module to confirm whether `distribute` actually aborts as described.

    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }

    /// Distribute any withdrawable stake from the stake pool.
    public entry fun distribute(contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        let coins = withdraw_stake(vesting_contract, contract_address);
        let total_distribution_amount = coin::value(&coins);
        if (total_distribution_amount == 0) {
            coin::destroy_zero(coins);
            return
        };

        // Distribute coins to all shareholders in the vesting contract.
        let grant_pool = &vesting_contract.grant_pool;
        let shareholders = &grant_pool.shareholders();
        shareholders.for_each_ref(|shareholder| {
            let shareholder = *shareholder;
            let shares = pool_u64::shares(grant_pool, shareholder);
            let amount = pool_u64::shares_to_amount_with_total_coins(grant_pool, shares, total_distribution_amount);
            let share_of_coins = coin::extract(&mut coins, amount);
            let recipient_address = get_beneficiary(vesting_contract, shareholder);
            aptos_account::deposit_coins(recipient_address, share_of_coins);
        });

        // Send any remaining "dust" (leftover due to rounding error) to the withdrawal address.
        if (coin::value(&coins) > 0) {
            aptos_account::deposit_coins(vesting_contract.withdrawal_address, coins);
        } else {
            coin::destroy_zero(coins);
        };
