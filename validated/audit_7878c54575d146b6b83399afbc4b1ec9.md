### Title
Bash `%q` quoting in `RmFilesRecursive`/`RmDirsRecursive` does not escape `$`, backticks, or `!`, allowing shell command substitution injection via job-controlled `name`/`path` - (File: shells/bash.go)

### Summary
`BashWriter.RmFilesRecursive` and `RmDirsRecursive` build the `find` command line using Go's `fmt`/`%q` verb, which performs Go-string quoting (escaping only `"`, `\`, and control characters), not shell quoting. Because the generated line is later executed via `eval` inside a bash double-quoted context, a `name` or `path` value containing `$(...)` or backticks is not neutralized and undergoes command substitution when the script is evaluated, resulting in arbitrary command execution — not merely an injected `find` primitive.

### Finding Description
`RmFilesRecursive` and `RmDirsRecursive` construct their command via: [1](#0-0) [2](#0-1) 

`Linef` simply does `fmt.Sprintf` and appends the line to the buffer: [3](#0-2) 

The resulting script buffer is later executed via `eval` (or the legacy `: | eval` form) inside `Finish`: [4](#0-3) 

The `%q` verb for a Go string invokes `strconv.Quote` semantics: it wraps the value in double quotes and escapes only the quote character, backslash, and non-printable characters. It does **not** escape `$`, backtick, or `!`, which are all special inside bash double-quoted strings. When the emitted line (e.g. `find "path" -name "$(payload)" -type f -exec rm -f {} "+"`) is fed into `eval`, bash performs command substitution on `$(payload)` (or backtick equivalents) **before** `find` ever runs — so the attacker doesn't need to break out of the `%q` quotes with an escape sequence; the quoting itself is insufficient for the shell context it's used in.

This differs from the safe pattern used elsewhere in the same file, e.g. `SetupGitCredHelper` explicitly calls a dedicated `doubleQuote()` helper for shell-safe quoting rather than relying on raw `%q`: [5](#0-4) 

`RmFilesRecursive`/`RmDirsRecursive` bypass that vetted helper and use the format verb directly, which is the root cause.

Preconditions per the question: an attacker (unprivileged pipeline author) controls a cache key fragment, artifact glob/exclude pattern, or similar value that is threaded as the `name` (or `path`) argument into `ShellWriter.RmFilesRecursive`/`RmDirsRecursive` through `AbstractShell`'s cache/artifact cleanup logic. Given that precondition, no existing check in `bash.go` sanitizes `$()`/backtick sequences before they reach `Linef`, and no shell-escaping function (`escape`/`doubleQuote`) is applied to these two arguments.

### Impact Explanation
If a job-controlled value reaches these calls, the attacker can achieve arbitrary command execution in the job's shell context at cleanup time (via bash command substitution), rather than merely appending a `find` action such as `-exec`. This exceeds the file-deletion boundary the `find` invocation was meant to enforce and can be used to read/write/delete files outside the intended cache/artifact/workspace roots, within the privileges of the job's shell (same privilege level as normal job script execution, but at an unexpected script-generation point, potentially bypassing job-script-specific safeguards).

### Likelihood Explanation
Feasibility depends entirely on whether `AbstractShell`'s cache/artifact cleanup logic passes a raw, attacker-influenced string (e.g., derived from `cache:key`, `cache:paths`, `artifacts:exclude`, or similar `.gitlab-ci.yml` fields) directly as the `name`/`path` parameter without prior sanitization or shell-escaping. This repository's `shells/abstract.go` contains the caller-side logic that would need to be inspected to confirm exactly which fields flow into these two arguments unescaped; that verification was not completed within the available tool budget. If such an unsanitized flow exists, the exploit is trivially repeatable (a single crafted CI value, e.g. a cache key of `` $(touch /tmp/pwned) ``, triggers it every time the cleanup stage runs).

### Recommendation
Replace the raw `%q` usage in `RmFilesRecursive`/`RmDirsRecursive` with the same vetted shell-escaping function (`b.escape` or `doubleQuote`, whichever is confirmed safe against `$`, backticks, and `!`) used elsewhere for values that end up in bash double-quoted contexts under `eval`. At the `AbstractShell` call sites, validate/sanitize `name`/`path` values derived from job configuration (cache keys, artifact patterns) before passing them to `ShellWriter` methods, rejecting or escaping shell metacharacters.

### Proof of Concept
Go unit test in `shells/bash_test.go` (pattern already established by existing `RmFilesRecursive`/`RmDirsRecursive` tests):
```go
func TestBashWriter_RmFilesRecursive_CommandSubstitutionInjection(t *testing.T) {
    w := &BashWriter{}
    w.RmFilesRecursive("/build", "$(touch /tmp/pwned)")
    script := w.String()
    // Assert the raw, unescaped command substitution sequence is present
    // in the generated script that will be fed to `eval`.
    assert.Contains(t, script, `-name "$(touch /tmp/pwned)"`)
}
```
Combined with an integration-style test that runs the generated script through `bash -c` (mirroring `Finish`'s `eval` wrapping) and asserts that `/tmp/pwned` is created — demonstrating command execution beyond the intended `find`/`rm` action.

```go
func (b *BashWriter) RmFilesRecursive(path string, name string) {
	b.IfDirectory(path)
	// `find -delete` is not portable; https://unix.stackexchange.com/a/194348
	// The '+' `find -exec` terminator is the default as it performs less invocations on supported systems.
	//   Other systems (e.g. z/OS) will use the ';' terminator when the initial 'test find' command fails, causing `$et` to be updated.
	//   The intitial `test find` command is used to prevent undesirable stderr output from a failed execution using the `+` terminator.
	b.Linef(`et='+' ; find /dev/null -exec true {} + 2>/dev/null || et=';' ; find %q -name %q -type f -exec rm -f {} "${et}"`, path, name)
	b.EndIf()
}
```
