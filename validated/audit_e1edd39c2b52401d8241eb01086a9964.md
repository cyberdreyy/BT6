### Title
Multisig `confirm` executes requests using stale confirmations from removed members, bypassing the K-of-N threshold - (File: `multisig2/src/lib.rs`)

### Summary
The Velodrome report describes a case where a downstream custody-check (`VotingEscrow.depositFor`'s expiry check) is not accounted for by the upstream accounting logic (`RewardsDistributor.claim`), leading to a state where recorded entitlement no longer matches what can actually be redeemed. The analogous bug class here is a binding that is supposed to hold — "confirmations counted == confirmations from currently live members" — but is not maintained when membership changes, in `MultiSigContract`.

### Finding Description
`MultiSigContract::confirm` decides whether to execute a request purely by counting entries in the `confirmations` `HashSet<String>` for that `request_id` against `self.num_confirmations`: [1](#0-0) 

Confirmations are added by member identity string in `confirm`, and `add_request` initializes an empty confirmation set per request: [2](#0-1) 

When a member is removed via `DeleteMember`, `delete_member` only purges requests and confirmation sets for requests where the *removed member is the original request author* (`r.member == member`): [3](#0-2) 

It does **not** scan `self.confirmations` to strip the removed member's identity from confirmation sets of *other* requests it merely confirmed (but did not author). The equality that should hold is:

`num_confirmations_needed == count(confirmations from currently-live members)`

but after a `DeleteMember` action, a pending request authored by someone else that the now-removed member had previously confirmed still carries that stale confirmation, so the actual invariant becomes:

`recorded confirmation count >= live-member confirmation count`

i.e., the tally can include confirmations from accounts that are no longer part of the multisig's trust set.

### Impact Explanation
This falls under "a multisig request executed below threshold" (Critical), an explicitly listed impact category. If `num_confirmations` is, say, 2 of 3 members (A, B, C):
1. A calls `add_request` for a sensitive action (e.g., `Transfer`, `AddKey`, `FunctionCall`).
2. B calls `confirm` on it — confirmations = `{B}`, count 1, below threshold of 2, so it is queued, not executed.
3. Separately, the members approve removing B (`DeleteMember{member: B}`) through its own request/confirm flow. `delete_member` runs, removing B from `members`, and only cleans up requests *authored* by B — A's pending request (with B's confirmation still in the set) is untouched.
4. Now only A and C are legitimate members, and the "true" threshold is 2-of-2 live members.
5. C confirms A's earlier request: `confirmations.len() (1, containing stale "B") + 1 >= num_confirmations (2)` evaluates true, and the request executes using a live confirmation from C plus a stale confirmation from the now-removed B.

The net effect: the request is authorized and executed with only one currently-authorized member (C) actively approving it in real time, even though the documented security model of the contract is that `num_confirmations` distinct *current* members must approve. Depending on the request's actions (`Transfer`, `FunctionCall`, `AddKey`), this can move funds or grant access with fewer live approvals than intended — a broken authorization/threshold binding, not merely a griefing/DoS issue.

### Likelihood Explanation
This requires no special privilege beyond being one of the remaining legitimate members (which is expected multisig operation) and simply relies on ordinary usage sequencing: a request pending confirmation at the time another member is removed. Multisig membership changes (onboarding/offboarding signers) are a normal operational event, and pending, not-yet-fully-confirmed requests are common in practice (e.g., waiting on other signers, or the `REQUEST_COOLDOWN` window), so the precondition is realistic rather than contrived.

### Recommendation
When removing a member in `delete_member`, iterate over all entries in `self.confirmations` (not just requests authored by the removed member) and strip the removed member's identity from every confirmation set; alternatively, validate at `confirm`-time that every entry counted in a request's confirmation set still belongs to a current member of `self.members`, discarding stale ones before comparing against `self.num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new([A, B, C], 2)`.
2. `A` calls `add_request({receiver_id: X, actions: [Transfer{amount}]})` → `request_id = 0`.
3. `B` calls `confirm(0)` → confirmations for request 0 = `{B}` (count 1, below threshold, not executed): [4](#0-3) 
4. Separately confirm and execute a `DeleteMember{member: B}` request (via the normal 2-of-3 flow using A and C) → `delete_member` runs: [3](#0-2)  — note it only removes requests where `r.member == B` (requests B authored); request 0 (authored by A) is untouched, and its confirmation set `{B}` remains stored.
5. `C` calls `confirm(0)`. In `confirm`, `confirmations.len() (1) + 1 >= num_confirmations (2)` → true, so `execute_request` runs the `Transfer`, even though B is no longer a member and only C actually confirmed in real time.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
