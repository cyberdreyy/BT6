### Title
Malicious/uncooperative operator can permanently freeze a staker's unlock, distribute, and switch-operator paths in `staking_contract` by disabling direct coin transfers - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`staking_contract::distribute_internal` pays out every pending recipient (staker and, when commission is owed, the operator/former-operator) from a single shared `distribution_pool` in one loop, using `aptos_account::deposit_coins`. That helper only auto-registers a `CoinStore` for a not-yet-registered recipient if that recipient's `can_receive_direct_coin_transfers` flag is `true`; otherwise it aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. Because `distribute_internal` is invoked as a mandatory first step inside `unlock_stake`, `switch_operator`, and `distribute`, an operator who has never registered a `CoinStore<AptosCoin>` for themselves can call the fully permissionless `aptos_account::set_allow_direct_coin_transfers(false)` on their own account and thereby make every subsequent call that must pay them commission permanently abort - exactly mirroring the TOFT bug where a single un-payable recipient (`address(0)`/`approve` revert) makes a shared batch operation fail forever on retry.

### Finding Description
`distribute_internal` iterates the shared `distribution_pool` and pays every shareholder in it (staker's own withdrawal amount and the operator's un-paid commission share) in a single atomic loop: [1](#0-0) 

`aptos_account::deposit_coins` will abort instead of silently succeeding when the recipient is not yet registered for the coin **and** has opted out of unsolicited transfers: [2](#0-1) 

`set_allow_direct_coin_transfers` is a fully permissionless, self-directed entry function - any account, including the operator of a `staking_contract`, can flip this flag on itself at any time: [3](#0-2) 

`distribute_internal` is unconditionally called (before any real work) by:
- `unlock_stake` (staker-initiated withdrawal request) — [4](#0-3) 
- `switch_operator` (staker-initiated operator replacement) — [5](#0-4) 
- `distribute` (permissionless distribution trigger) — [6](#0-5) 

Once the operator's outstanding commission share exists in `distribution_pool` (which happens as soon as there is any inactive/pending_inactive stake to distribute and `commission_percentage > 0`), every one of these entry points will attempt to pay the operator via `aptos_account::deposit_coins`. If the operator has disabled direct transfers and has no pre-existing `CoinStore<AptosCoin>`, that call reverts, and because the abort happens inside a loop that also extracts/deposits the staker's own share in the same coin object, the **entire transaction** reverts — including the staker's own withdrawal. The operator's `distribution_pool` entry and flag persist unchanged across retries, so any retry of `unlock_stake`, `switch_operator`, or `distribute` fails identically forever, precisely matching the reported bug class ("the failed message if retried will always fail... permanent loss").

### Impact Explanation
This is a **stake/vesting withdrawal-and-switch lockup**: an operator (who no longer needs to hold any special privilege beyond having been assigned as operator earlier — e.g. a former operator the staker is actively trying to fire) can trap a staker's active/inactive/pending_inactive stake in the contract indefinitely. The staker can neither `unlock_stake` (withdraw), nor `switch_operator` away from the uncooperative operator, nor trigger `distribute`, because all three unconditionally attempt to flush the shared `distribution_pool` first. This satisfies the "Permanent lock or non-recoverable loss of claim rights in stake ... flows" and "Unlock, reactivate, withdraw ... paths must not ... strand it permanently" impact categories — value legitimately owned by the staker becomes unreachable purely due to another party's benign-looking, unprivileged self-configuration.

### Likelihood Explanation
Requires only two unprivileged preconditions on the operator's side: (1) never having registered a `CoinStore<AptosCoin>` (plausible for an account primarily using the newer fungible-asset/primary-store path or a fresh account created solely to serve as operator), and (2) calling the permissionless `set_allow_direct_coin_transfers(false)`. Both are fully within a normal, non-privileged account's control and require no interaction with the staker. This is realistically triggerable by any operator who wants to hold a staker's funds hostage or simply grief them, at negligible cost.

### Recommendation
`distribute_internal` should not let one recipient's coin-acceptance preference or missing `CoinStore` block payouts to unrelated parties. Recommended mitigations:
- Isolate each recipient's payout so a failure for one shareholder does not roll back the others (e.g., wrap each `aptos_account::deposit_coins` call so failures are captured and the specific recipient's owed amount is preserved/re-queued rather than aborting the whole transaction), or
- Use a deposit path that cannot abort due to `DirectTransferConfig` (e.g., always force-register the coin store for the recipient irrespective of their opt-out flag, since this is a contractual payout the recipient is legally owed and not an unsolicited transfer), or
- Allow the staker to unilaterally unlock/withdraw their own principal independent of whether the operator's commission payout succeeds (decouple staker withdrawal from operator commission distribution).

### Proof of Concept
1. Staker `S` calls `staking_contract::create_staking_contract(operator = O, commission_percentage = 10, ...)`.
2. `O` never calls `coin::register<AptosCoin>` for their own account (no pre-existing `CoinStore<AptosCoin>`).
3. `O` calls `aptos_account::set_allow_direct_coin_transfers(&O_signer, false)` — a fully permissionless self-call.
4. Stake pool accrues rewards; `S` calls `staking_contract::unlock_stake(S, O, amount)` (or any call that triggers `distribute_internal`, e.g., after time passes and stake becomes inactive).
5. Inside `distribute_internal`, `update_distribution_pool` grants `O` shares for their commission cut; the payout loop reaches `O` and calls `aptos_account::deposit_coins(O, ...)`.
6. Since `O` has no `CoinStore<AptosCoin>` and `can_receive_direct_coin_transfers(O) == false`, `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
7. The whole `unlock_stake` transaction reverts — `S`'s own withdrawal never happens.
8. `S` retries `unlock_stake`, `switch_operator`, or `distribute` — every one calls `distribute_internal` first and hits the same abort, since `O`'s flag and pending distribution-pool entry are unchanged. `S`'s stake remains permanently stuck as long as `O` keeps the flag disabled.

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
