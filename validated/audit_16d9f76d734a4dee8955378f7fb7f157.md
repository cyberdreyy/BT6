### Title
Permissionless `lending_pool_collect_bank_fees` performs unconditional zero-amount SPL transfers, allowing a Token-2022 transfer-hook mint to permanently DoS fee collection - (File: `programs/marginfi/src/instructions/marginfi_group/collect_bank_fees.rs`)

### Summary
The `LendingPoolCollectBankFees` instruction is permissionless and moves outstanding insurance, group, and program fees from a bank's `liquidity_vault` to their respective destination vaults. It computes each transfer amount as `min(outstanding, available_liquidity)` but never checks whether that amount is greater than zero before calling `bank.withdraw_spl_transfer`, exactly mirroring the Aave Lens `[M-09]` bug class where zero-value fee transfers are attempted unconditionally.

### Finding Description
`lending_pool_collect_bank_fees` computes three transfer amounts and unconditionally calls `bank.withdraw_spl_transfer` for each, with no `if amount > 0` guard: [1](#0-0) [2](#0-1) 

`withdraw_spl_transfer` performs a raw `transfer`/`transfer_checked` CPI regardless of the amount, including `0`: [3](#0-2) 

The instruction itself is permissionless (any caller can invoke it) and is only gated on the group not being paused, with no admin/`has_one` authorization on the caller: [4](#0-3) 
This permissionless design is confirmed by the project's own documentation, describing `LendingPoolCollectBankFees` as callable by "Anyone": [5](#0-4) 

Marginfi explicitly supports Token-2022 mints with the `TransferHook` extension, as demonstrated by a dedicated `test_transfer_hook` program and test coverage for `SupportedExtension::TransferHook` banks: [6](#0-5) 

If a bank's underlying mint uses a transfer-hook program (or any Token-2022/weird-token behavior) that reverts on zero-amount transfers — a documented, real-world SPL/ERC20 pattern — then any time `collected_insurance_fees_outstanding`, `collected_group_fees_outstanding`, or `collected_program_fees_outstanding` is zero for that bank (a very common steady state, e.g., a freshly created bank or a bank that was just fully collected), the entire `LendingPoolCollectBankFees` instruction reverts. Because all three transfers happen in one instruction/transaction and any one revert aborts the whole call, this is far more fragile than the original Aave Lens report (which only had a single fee transfer per collect call).

### Impact Explanation
This is not a hypothetical: because collection of the three fee categories is bundled into a single instruction, and it is common for one or two of the three `outstanding` fee balances to be legitimately zero at any given time (e.g., a bank with no insurance fee configured, or one collected slightly earlier than another), a transfer-hook-based mint that rejects zero-value transfers would make `LendingPoolCollectBankFees` permanently revert for that bank. Since `LendingPoolWithdrawFees`/`LendingPoolWithdrawFeesPermissionless` pull from the `fee_vault`/`insurance_vault` that only get funded via a successful `LendingPoolCollectBankFees` call, this durably freezes fee collection and downstream withdrawal for that bank — a durable freeze/DoS with financial effect (protocol/group/insurance fees become permanently uncollectable for banks using such a mint), matching the "durable freeze/inconsistency with financial effect" bar.

### Likelihood Explanation
Likelihood depends on a group admin whitelisting a bank whose mint uses a Token-2022 transfer hook (or other transfer-hook/weird-token behavior) that reverts on 0-amount transfers. This is a supported, tested configuration in the codebase (not a theoretical/mocked-only scenario), and does not require any privileged or malicious actor — it triggers automatically the moment any of the three fee categories has zero balance outstanding, which is a normal, unprivileged, permissionless code path (`LendingPoolCollectBankFees` is callable by anyone). It requires no attacker action beyond calling the already-permissionless instruction; a normal user's routine "collect fees" call fails as an unavoidable side effect of a benign zero-fee state.

### Recommendation
Guard each of the three `bank.withdraw_spl_transfer` calls in `lending_pool_collect_bank_fees` with a check that the computed transfer amount is greater than zero before invoking the transfer, e.g.:
```rust
if group_fee_transfer_amount > I80F48::ZERO {
    bank.withdraw_spl_transfer(...)?;
}
```
Apply the same guard to the insurance and program fee transfers.

### Proof of Concept
1. Group admin creates a bank whose mint is a Token-2022 mint with a `TransferHook` extension pointing to a hook program that reverts when the transferred `amount == 0` (analogous to `programs/test_transfer_hook` already present in the repo for testing this extension: [6](#0-5) ).
2. Normal lending activity accrues, e.g., only `collected_group_fees_outstanding` becomes non-zero while `collected_insurance_fees_outstanding` and `collected_program_fees_outstanding` remain `0` (a common state, since insurance/program fee rates can be zero or simply haven't accrued yet).
3. Any unprivileged user calls `LendingPoolCollectBankFees` (it is permissionless, per [7](#0-6) ).
4. Inside the handler, `insurance_fee_transfer_amount` computes to `0` and is passed unconditionally into `bank.withdraw_spl_transfer` at [8](#0-7) , which performs a `transfer_checked` CPI with `amount = 0` via [9](#0-8) .
5. The transfer-hook program rejects the zero-amount transfer, causing the whole `LendingPoolCollectBankFees` transaction to revert.
6. Because the fee vaults are never funded, `LendingPoolWithdrawFees`/`LendingPoolWithdrawFeesPermissionless` ( [10](#0-9)  and [11](#0-10) ) have nothing to withdraw for that bank, permanently blocking fee collection for as long as any one of the three fee categories remains at zero.

pub fn lending_pool_withdraw_fees_permissionless<'info>(
    mut ctx: Context<'info, LendingPoolWithdrawFeesPermissionless<'info>>,
    amount: u64,

    let LendingPoolWithdrawFeesPermissionless {
        bank: bank_loader,

        fee_vault_authority,
        fees_destination_account,
        token_program,
        ..
    } = ctx.accounts;

    let bank = bank_loader.load()?;

            BankVaultType::Fee,
            bank_loader.key(),

    fn withdraw_spl_transfer<'info>(
        &self,
        amount: u64,
        from: AccountInfo<'info>,
        to: AccountInfo<'info>,
        authority: AccountInfo<'info>,
        maybe_mint: Option<&InterfaceAccount<'info, Mint>>,
        program: AccountInfo<'info>,
        signer_seeds: &[&[&[u8]]],
        remaining_accounts: &[AccountInfo<'info>],
    ) -> MarginfiResult {
        debug!(
            "withdraw_spl_transfer: amount: {} from {} to {}, auth {}",
            amount, from.key, to.key, authority.key
        );

        #[cfg(feature = "client")]
        if let Some(mint) = maybe_mint {
            invoke_client_token_transfer(
                program.key,
                amount,
                from,
                Some(mint.to_account_info()),
                to,
                authority,
                Some(mint.decimals),
                remaining_accounts,
                signer_seeds,
            )?;
        } else {
            // `transfer_checked` and `transfer` does the same thing, the additional `_checked` logic
            // is only to assert the expected attributes by the user (mint, decimal scaling),
            //
            // Security of `transfer` is equal to `transfer_checked`.
            invoke_client_token_transfer(
                program.key,
                amount,
                from,
                None,
                to,
                authority,
                None,
                remaining_accounts,
                signer_seeds,
            )?;
        }

        #[cfg(not(feature = "client"))]
        if let Some(mint) = maybe_mint {
            spl_token_2022::onchain::invoke_transfer_checked(
                program.key,
                from,
                mint.to_account_info(),
                to,
                authority,
                remaining_accounts,
                amount,
                mint.decimals,
                signer_seeds,
            )?;
        } else {
            // `transfer_checked` and `transfer` does the same thing, the additional `_checked` logic
            // is only to assert the expected attributes by the user (mint, decimal scaling),
            //
            // Security of `transfer` is equal to `transfer_checked`.
            #[allow(deprecated)]
            transfer(
                CpiContext::new_with_signer(
                    program.key(),
                    Transfer {
                        from,
                        to,
                        authority,
                    },
                    signer_seeds,
                ),
                amount,
            )?;
        }

(2) Anyone (the ix is permissionless) runs `LendingPoolCollectBankFees`. This moves:
* The amount specified in `collected_insurance_fees_outstanding` from the `liquidity_vault` to the
  `insurance_vault`
* The amount specified in `collected_group_fees_outstanding` from the `liquidity_vault` to the `fee_vault`
* The amount specified in `collected_program_fees_outstanding` from the `liquidity_vault` to the
    `fee_ata`, which is the cannonical ATA of the global fee wallet.

Then the `fees_outstanding` are all reset to zero. The vast majority of the time, we run this ix just before a withdraw.
