### Title
Missing initiator-to-job binding check allows any external-initiator credential to trigger runs on any integer-ID job - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` grants a blanket `UserRoleRun` session user for any successfully authenticated external initiator (EI), with no linkage to the specific job being acted on. `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser(c)` to decide whether to run the requested job by integer ID, but that check returns `true` for EI-authenticated requests too, defeating the code's own comment that "EIs not allowed" for int-ID runs, and letting EI credential holder A trigger `RunJobV2` for a job never bound to initiator A.

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) verifies the EI access key/secret against `store.FindExternalInitiator`, but after success it unconditionally does: [1](#0-0) 
This sets `SessionUserKey` to a fresh `&clsessions.User{Role: clsessions.UserRoleRun}` for *every* successfully authenticated EI, regardless of which job or bridge the EI is actually registered against.

The route `POST /v2/jobs/:ID/runs` is wired with all three auth methods and `RequiresRunRole`: [2](#0-1) 

Inside `PipelineRunsController.Create`: [3](#0-2) 
The code comment states "only users are allowed to run jobs using int IDs - EIs not allowed," relying on `isUser, _ := auth.GetAuthenticatedUser(c)` to distinguish EI sessions from real user sessions. But `GetAuthenticatedUser` (`core/web/auth/auth.go:178-187`) only checks whether `SessionUserKey` is present in the gin context — and as shown above, `AuthenticateExternalInitiator` always sets that key too. Therefore `isUser` is `true` for EI-authenticated requests as well, and the intended EI-exclusion is a no-op. The handler proceeds to parse `idStr` as an `int32` job ID and call `prc.App.RunJobV2(ctx, jobID, nil)` with no check that the authenticated `ei` (available via `auth.GetAuthenticatedExternalInitiator(c)`) is bound to, or was ever associated with, that job ID.

As a result, any EI credential (initiator A) can supply an arbitrary numeric job ID — including one that belongs to a different initiator (B) or has no EI binding at all — and still successfully trigger `prc.App.RunJobV2`.

### Impact Explanation
This is an authorization/binding bypass: an external-initiator credential scoped to one job/bridge can trigger pipeline runs on arbitrary jobs by ID, violating the intended "requests are bound to their initiator" invariant. Depending on the job's pipeline (e.g., jobs performing on-chain transactions, VRF fulfillment, or other side effects), this can cause unauthorized job execution and downstream unauthorized actions/fund movement, corresponding to Chainlink's "unauthorized job run" / authorization-bypass bounty class.

### Likelihood Explanation
The precondition is minimal: possession of any valid EI access key/secret pair (the lowest-privilege node credential, `UserRoleRun`-equivalent). No admin/edit access, no knowledge of which jobs the initiator is bound to, and no additional social engineering is required — the attacker only needs to know or guess a numeric job ID (job IDs are sequential and often enumerable via `GET /v2/jobs`, which many low-privileged sessions can read). The exploit is directly reachable through the public HTTP route and is fully repeatable.

### Recommendation
In `PipelineRunsController.Create`, when the authenticated principal is an external initiator (check via `auth.GetAuthenticatedExternalInitiator(c)` rather than solely `GetAuthenticatedUser`), look up the job's webhook/EI spec and verify the requesting EI is actually bound to that job ID before calling `RunJobV2`; reject with 401/403 otherwise. Additionally, `AuthenticateExternalInitiator` should not set an unconditional generic `UserRoleRun` session user without also recording/propagating the specific EI identity so downstream handlers can enforce per-job binding, and the `isUser` check in `Create` should be corrected to actually exclude (or properly scope) EI-authenticated principals as the comment intends.

### Proof of Concept
Go handler-integration test plan (in `core/web/pipeline_runs_controller_test.go` style):
1. Create external initiator B (`ExternalInitiator` with unique access key/secret), and create a webhook/job bound to initiator B with a known integer job ID.
2. Create a second, unrelated external initiator A with its own valid access key/secret, not associated with job B's ID.
3. Send `POST /v2/jobs/<jobB.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to initiator A's credentials.
4. Assert current (vulnerable) behavior: response is `200 OK` with a `pipelineRun` resource returned, and `prc.App.RunJobV2` was invoked for job B — i.e., initiator A triggered a run on a job it was never bound to.
5. Expected (fixed) behavior: response should be `401 Unauthorized`/`403 Forbidden`, and `RunJobV2` should not be invoked, since initiator A has no binding to job B.
