### Title
Prior-epoch unfunded instant-withdraw receipts are excluded from default recovery accounting, permanently freezing user claims - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug is a reused single-slot buffer reset at a batch boundary while prior-generation work still references it — state keyed to the "current generation" silently orphaned in-flight data from an older generation. The direct analog in `IdleCreditVault` is instant-withdraw accounting: `pendingInstantWithdraws` and `instantWithdrawsRequests[_user]` are aggregate counters spanning all epochs, but `instantWithdrawClaimsByEpoch` is keyed per epoch and only the *current* epoch's bucket is consulted during default finalization. An unfunded instant receipt created in an earlier epoch survives the epoch boundary (its "generation") yet is invisible to `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` when `finalizeDefaultRecovery` runs, permanently freezing that user's claim.

### Finding Description
`requestInstantWithdraw` records receipts in three places: the per-user aggregate `instantWithdrawsRequests[_user]`, the per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the global per-epoch `instantWithdrawClaimsByEpoch[currentEpoch]`, plus the aggregate `pendingInstantWithdraws` (IdleCreditVault.sol:356-375).

At default finalization, `defaultPendingClaimBasis` only adds `instantWithdrawClaimsByEpoch[epochNumber]` — the epoch in which the default is finalized (IdleCreditVault.sol:644-649). Likewise `_defaultPrefundedInstantReserve` compares `pendingInstantWithdraws` (all unfunded instant receipts, any epoch) against only `instantWithdrawClaimsByEpoch[epochNumber]` (IdleCreditVault.sol:716-723).

If an instant request was made in epoch E, was only partially funded at the epoch boundary (borrower shortfall is an expected case — the comment at line 694-696 acknowledges `pendingInstantWithdraws` can be non-zero), and the default finalizes in epoch E+1, then:

- The old receipt contributes nothing to `pendingBasis`, so `recoveryPrice` is computed without it — other claimants get a slightly inflated price, and no reserve is allocated for this receipt.
- `defaultInstantWithdrawsFinalized` is set true, but `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` = epoch E+1 entries (IdleCreditVault.sol:843-845). The epoch-E entry remains.
- The leftover amount stays in `instantWithdrawsRequests[_user]` and falls through `claimInstantWithdrawRequest` to `_transferFundedClaim`, which reverts whenever `balance - defaultRecoveryReserve < amount` (IdleCreditVault.sol:900-905). Since the reserve was fully allocated to other claims and the contract holds no free balance for this receipt, every `claimInstantWithdrawRequest` by the affected user reverts forever.

Invariant broken: one receipt, one payout — a receipt created and accepted by the protocol must be either funded at par or haircutted into the recovery reserve; it cannot be left unfunded and unclaimable.

### Impact Explanation
Any user whose instant-withdraw request was only partially funded before an epoch transition, followed by a borrower default in a later epoch, has their entire receipt permanently frozen. Loss equals the full unfunded amount of the stale receipt; the funds are not stolen but are unrecoverable — they remain locked because the reserve guard correctly prevents spending other claimants' recovery funds, and no code path ever pays or clears the stale receipt.

### Likelihood Explanation
Requires a specific but plausible sequence: (1) instant withdrawals requested and only partially funded at an epoch boundary so `pendingInstantWithdraws > 0` carries into the next epoch; (2) borrower default and `finalizeDefaultRecovery` in a subsequent epoch. Instant underfunding and defaults are both designed-for failure modes in this vault, and no guard blocks an instant request from spanning epoch boundaries. The attacker needs no special action beyond holding a stale instant receipt — an ordinary user triggers the freeze.

### Recommendation
Track unfunded instant claims across all epochs, not just the finalization epoch. Either:
- maintain a cumulative `instantWithdrawClaimsTotal` alongside `pendingInstantWithdraws` and use it in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`, or
- roll forward each epoch's `instantWithdrawClaimsByEpoch` bucket (e.g., re-key the unfunded remainder into the new epoch at `stopEpoch`/`startEpoch` in `IdleCDOEpochVariant`), analogous to how the fix in the external report tags every item with its generation and drains a slot before reuse.

Claims after finalization should also iterate or aggregate all per-epoch entries in `_claimDefaultedInstantWithdrawRequest`, not only `defaultRecoveryEpoch`.

### Proof of Concept
Proposed Foundry fork test (not executed — source-level reasoning only). In `test/foundry/IdleCreditVault.t.sol` harness style:

```solidity
function testStaleEpochInstantReceiptFrozenOnDefault() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    address user = makeAddr('staleInstantUser');

    // Epoch E: user deposits AA and requests an instant withdraw
    _depositWithUser(user, 10_000 * ONE_SCALE, true);
    vm.prank(user);
    cdoEpoch.requestInstantWithdraw(/* amount */, address(AAtranche));

    // Partial funding: CDO collects only part of the instant queue at epoch end,
    // leaving pendingInstantWithdraws > 0 (borrower underfunds via deal() shortfall).
    // ... warp, stopEpoch with insufficient instant funds ...

    // Epoch E+1: borrower defaults; manager/orchestrator finalizes recovery.
    // finalizeDefaultRecovery computes basis = pendingWithdraws +
    // instantWithdrawClaimsByEpoch[epochNumber(E+1)] -> user's epoch-E basis excluded.

    // User's claim: _claimDefaultedInstantWithdrawRequest clears only epoch E+1 entry (0),
    // then _transferFundedClaim reverts: balance - reserve < amount.
    vm.prank(user);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Uncertainty: I did not fully trace `IdleCDOEpochVariant`'s instant-funding path (`getInstantWithdrawFunds`) to confirm a partial-collection path that leaves `pendingInstantWithdraws > 0` across an epoch boundary; the grep matched the file but returned no line detail. If the CDO always fully funds or sweeps instant receipts at every boundary, the stale-generation precondition cannot occur and this finding reduces to not-applicable.
