### Title
Withdraw instruction parser can mislabel a context-state-account as `owner`/omit the expected proof-context field due to under-constrained account-count checks - (File: transaction-status/src/parse_token/extension/confidential_transfer.rs)

### Finding Description
The `ConfidentialTransferInstruction::Withdraw` arm decodes `equality_proof_instruction_offset` and `range_proof_instruction_offset` from fully attacker-controlled instruction data, then walks `account_indexes` sequentially, conditionally inserting `instructionsSysvar`, `equalityProofContextStateAccount`, and `rangeProofContextStateAccount`, before finally handing the remaining `offset` to `parse_signers` for the `owner`/`multisigOwner` field [1](#0-0) .

The only account-count guard for this arm is `check_num_token_accounts(account_indexes, 4)`, which enforces just the minimal case (account, mint, sysvar-or-nothing, owner) [2](#0-1) . It does not scale with the actual number of context accounts implied by the offsets. Each conditional insertion is gated only by `offset < account_indexes.len().saturating_sub(1)` [3](#0-2) , which merely prevents an out-of-bounds index/array-panic and reserves the last slot for the owner — it does not verify that enough slots exist for every ctx-account implied by the offsets being zero.

Consequently, an attacker can encode data where, e.g., `equality_proof_instruction_offset != 0` (so a sysvar is expected) and `range_proof_instruction_offset == 0` (so a `rangeProofContextStateAccount` is structurally expected), but supply only the minimal 4 accounts. In that case: offset starts at 2, the sysvar branch consumes index 2 and increments offset to 3, then the range-context branch check (`offset(3) < len.saturating_sub(1)=3`) is `false` and is skipped — silently dropping the `rangeProofContextStateAccount` field — after which `parse_signers` treats `account_indexes[3]` (which per the encoded semantics should have been the range-proof context account) as the `owner` field.

Because `account_indexes` and instruction data are entirely attacker-controlled in a client-submitted transaction, and `getParsedTransaction`/`getTransaction` (jsonParsed encoding) parses instruction data independent of whether the instruction actually succeeds at runtime, an attacker can submit such a malformed/failing Withdraw instruction, have it land in a block (even as a failed transaction, since the fee payer/blockhash checks are separate from instruction semantics), and then query the RPC to obtain a JSON-parsed instruction where an account never intended as a signer/owner is reported under the `"owner"` key while the expected `"rangeProofContextStateAccount"` key is missing entirely.

### Impact Explanation
This is a PARSE_FIDELITY / decoder-misreporting bug in `getParsedTransaction`/`getTransaction` (jsonParsed) responses: an unrelated `account_keys` entry can be mislabeled as `owner` (implying signer authority) while the true intended field (`rangeProofContextStateAccount`/`equalityProofContextStateAccount`) is silently dropped. No consensus state, execution outcome, or account data is affected — only the RPC's human-readable JSON representation is wrong. This matches the "decoder panic and misreporting" bounty category rather than a crash or consensus issue.

### Likelihood Explanation
Fully reachable by an unprivileged single client: craft one `ConfidentialTransferInstruction::Withdraw` instruction with `account_indexes.len()` at the minimal boundary (4) while setting `equality_proof_instruction_offset != 0` and `range_proof_instruction_offset == 0` (or other offset/account-count combinations at the `saturating_sub(1)` boundary), submit via `sendTransaction`, and query `getParsedTransaction`/`getTransaction` once the transaction (even if it fails on-chain) is included in a block. No special privileges, staking, or multiple calls are required, satisfying the single-call threshold.

### Recommendation
Compute the exact number of trailing accounts required from the decoded offsets (sysvar presence, equality-ctx presence, range-ctx presence, plus owner/multisig) before calling `check_num_token_accounts`, and validate `account_indexes.len()` against that computed minimum instead of the fixed constant `4`. Only proceed with the offset-walking/field-insertion logic once sufficient accounts are confirmed present for the specific offset combination encoded in the instruction data.

### Proof of Concept
Rust unit test (extending the existing `test_withdraw` table in `transaction-status/src/parse_token/extension/confidential_transfer.rs`):
```rust
#[test]
fn test_withdraw_boundary_misattribution() {
    // Build a Withdraw instruction data buffer manually with:
    //   equality_proof_instruction_offset = 1 (needs sysvar)
    //   range_proof_instruction_offset = 0 (needs rangeProofContextStateAccount)
    // but supply only 4 accounts: [token_account, mint, sysvar, some_unrelated_account]
    let unrelated_account = Pubkey::new_unique();
    let instruction = build_raw_withdraw_instruction(
        token_account, mint, /*eq_offset=*/1, /*range_offset=*/0,
        vec![token_account, mint, sysvar::instructions::id(), unrelated_account],
    );
    let message = Message::new(&[instruction], None);
    let parsed = parse_token(
        &message.instructions[0],
        &AccountKeys::new(&message.account_keys, None),
    ).unwrap();

    // BUG: unrelated_account gets reported as "owner" instead of
    // "rangeProofContextStateAccount", and the range field is missing.
    assert_eq!(parsed.info["owner"], json!(unrelated_account.to_string()));
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());
}
```
Expected (fixed) behavior: parsing should either reject the instruction as malformed (insufficient accounts for the encoded offsets) or correctly attribute `unrelated_account` to `rangeProofContextStateAccount`, never silently promoting it to `owner`.
