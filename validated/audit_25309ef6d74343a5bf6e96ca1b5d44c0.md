### Title
Claimed same-epoch instant withdrawals remain in `instantWithdrawClaimsByEpoch`, inflating the default-recovery reserve and diluting/DoSing recovery claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` burns the user's receipt and pays out funded instant withdrawals, but it never decrements `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch`. If a default is finalized in the same epoch while `pendingInstantWithdraws` is still non-zero (partial funding), `finalizeDefaultRecovery` counts already-paid claims as "prefunded reserve" and as pending claim basis, crediting `defaultRecoveryReserve` with tokens that already left the contract. Later recovery claims are then overpriced and the last claimants' transfers revert — a permanent freeze / shortfall of recovery funds. This mirrors the ext4 bug: a stale flag/accounting entry (claimed-but-recorded receipts) lets the release path free more than was ever reserved.

### Finding Description
In `requestInstantWithdraw`, each request is recorded in three places: `instantWithdrawsRequests[user]`, `instantWithdrawsRequestsByEpoch[user][epoch]`, and the aggregate `instantWithdrawClaimsByEpoch[epoch]` (`IdleCreditVault.sol:356-375`). `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` (`:398-403`).

`claimInstantWithdrawRequest` then burns the full `instantWithdrawsRequests[_user]` and pays out, but clears neither `instantWithdrawsRequestsByEpoch` nor `instantWithdrawClaimsByEpoch` (`:380-393`). Those per-epoch counters are only ever decremented inside `_claimDefaultedInstantWithdrawRequest` (`:842-856`).

At default finalization (`finalizeDefaultRecovery`, `:661-710`):
- `defaultPendingClaimBasis()` adds the full `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (`:644-649`) — including amounts already claimed.
- `_defaultPrefundedInstantReserve()` credits `instantBasis - pendingInstant` as already-held underlying (`:716-723`) — but part of that "held" amount was already transferred out to claimants.

So `reserveAmount` (line 686) and `totalBasis` (line 680) are both inflated by the already-claimed amount `X`, and `defaultRecoveryReserve` records tokens the strategy does not hold.

### Impact Explanation
Any later defaulted/post-default claim drains `defaultRecoveryReserve` via `_transferDefaultRecovery` (`:912-917`). Because the reserve is overstated by `X` (the sum of same-epoch instant claims already paid), either (a) claimants receive a diluted-but-still-positive `recoveryPrice` and the final claimants' `underlyingToken.safeTransfer` reverts due to insufficient balance, permanently freezing their recovery, or (b) recovery above par is computed on phantom funds. Quantified loss: up to the total same-epoch instant-withdraw claims paid before finalization — a direct shortfall borne by defaulted-epoch receipt holders and active LPs. No existing guard stops this: `_transferFundedClaim`'s reserve check only protects the reserve from funded claims, not the reserve from being overcredited.

### Likelihood Explanation
Requires: an epoch where instant withdrawals are requested, the CDO collects only part of them at `startEpoch`/`collectInstantWithdrawFunds` (partial funding — happens whenever CDO cash is less than the queue), at least one claimant redeems, and the borrower defaults with `finalizeDefaultRecovery` executed in the same epoch. All attacker steps (request + claim instant withdrawals) are unprivileged lender actions; the default path is driven by honest manager/borrower. Partial instant funding plus a same-epoch default is an unusual but reachable state.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch accounting the same way `_claimDefaultedInstantWithdrawRequest` does: set `instantWithdrawsRequestsByEpoch[_user][<requestEpoch>] = 0` and decrement `instantWithdrawClaimsByEpoch[<requestEpoch>]` by the claimed amount. Since a user may have requests across epochs, iterate or track the pending epoch per user (e.g., reuse `lastWithdrawRequest`-style bookkeeping for instant requests) so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only ever count unclaimed receipts.

### Proof of Concept
```solidity
// Foundry fork PoC sketch against IdleCreditVault + IdleCDOEpochVariant
function test_claimedInstantInflatesRecoveryReserve() public {
    // 1. Epoch N running. Lender A deposits via CDO; vault is live.
    // 2. A calls requestInstantWithdraw(100e6) through the CDO.
    //    -> instantWithdrawsRequestsByEpoch[A][N] = 100e6
    //    -> instantWithdrawClaimsByEpoch[N]      = 100e6
    //    -> pendingInstantWithdraws              = 100e6
    // 3. startEpoch: CDO only has 60e6 cash, calls
    //    collectInstantWithdrawFunds(60e6)
    //    -> pendingInstantWithdraws = 40e6, strategy holds 60e6
    // 4. A claims: claimInstantWithdrawRequest(A) pays 60e6 balance
    //    (claim pays full instantWithdrawsRequests[A] bounded by balance;
    //     assume A received the funded portion).
    //    BUG: instantWithdrawClaimsByEpoch[N] is still 100e6.
    // 5. Borrower defaults; CDO calls finalizeDefaultRecovery(R, src).
    //    defaultPendingClaimBasis() = pendingWithdraws + 100e6
    //    _defaultPrefundedInstantReserve() = 100e6 - 40e6 = 60e6
    //    -> reserve credited with 60e6 "held" funds, but 60e6 was
    //       already paid to A in step 4.
    // 6. Recovery claims now draw on a reserve overstated by 60e6;
    //    the last claimant's safeTransfer reverts -> funds frozen.
    assertEq(
      vault.underlyingTokenBalance(),
      vault.defaultRecoveryReserve() - 60e6 // phantom X = 60e6
    );
}
```

Note: the exact claim payout in step 4 depends on how `instantWithdrawsRequests` interacts with partial funding (the function pays the full recorded amount from whatever balance the strategy holds); the accounting flaw — claimed receipts never leaving `instantWithdrawClaimsByEpoch`/`instantWithdrawsRequestsByEpoch` — holds regardless, and the overstated reserve equals the total claimed amount `X`. I was unable to fully trace `IdleCDOEpochVariant`'s `startEpoch`/`collectInstantWithdrawFunds` call sequence within the available iterations, so the precise partial-funding trigger should be confirmed against that contract, but the missing per-epoch decrement in `claimInstantWithdrawRequest` is directly verifiable in `IdleCreditVault.sol:380-393`.
