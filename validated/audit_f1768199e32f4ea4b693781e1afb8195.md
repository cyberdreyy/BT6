**Analysis:** The proposed exploit path is already prevented by an explicit guard and is directly disproven by an existing test in the codebase.

In `vest`, before any `remaining_grant` mutation occurs, the function checks whether the next vesting period has actually elapsed: [1](#0-0) 

Specifically, `last_vested_period` is tracked in `vesting_schedule.last_vested_period`, and `next_period_to_vest = last_vested_period + 1`. Before touching `remaining_grant`, the function short-circuits with `if (last_completed_period < next_period_to_vest) { return }`. After a successful vest, `vesting_schedule.last_vested_period` is immediately advanced to `next_period_to_vest`, so a second call to `vest` within the same epoch/period boundary (no new period elapsed) hits the short-circuit and returns before reaching the `vesting_contract.remaining_grant -= vested_amount` line. There is no window in which `remaining_grant` can be decremented twice for the same period, and `vested_amount` is additionally capped via `min(vested_amount, vesting_contract.remaining_grant)`, so no more than the intended grant can ever be unlocked.

This exact scenario — calling `vest` twice within the same vesting period — is already covered by the framework's own test, `test_vest_twice_should_not_double_count`, which asserts that `remaining_grant` and the stake pool's pending distribution do **not** change on the second call: [2](#0-1) 

The `remaining_grant`/`vested_amount` computation also does not depend on stake-pool reward state that could be "stale" relative to epoch transitions — it is computed from `vesting_contract.grant_pool.total_coins()` (a fixed grant total) and the schedule fraction, not from the underlying stake pool's active/pending_active/pending_inactive/inactive balances. Reward synchronization is handled separately via `unlock_rewards`/`total_accumulated_rewards`, which is called first and is idempotent per-call (it simply unlocks whatever `stake::get_pending_inactive` etc. show as accumulated, not tied to `remaining_grant`). [3](#0-2) 

Because the `last_vested_period` guard blocks re-entry into the grant-decrementing logic within the same period, and this is verified by an existing regression test, the accounting invariant already holds and no unprivileged shareholder can cause `remaining_grant` to be double-decremented or cause more than the intended grant to be unlocked by repeatedly calling `vest`.
