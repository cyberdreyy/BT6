### Title
Unauthenticated `tenure_extend_timestamp`/`tenure_extend_read_count_timestamp` fields in signed `BlockAccepted`/`BlockRejection` messages allow a rogue signer to forge tenure-extend timing without invalidating the signature - (File: `libsigner/src/v0/messages.rs`)

### Summary
`BlockAccepted` and `BlockRejection` carry a `response_data: BlockResponseData` payload (`tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`, reject reason, failed txid) alongside a cryptographic `signature`. The signature, however, only covers `signer_signature_hash` (for `BlockAccepted`) or a structured hash of `signer_signature_hash` + `chain_id` (for `BlockRejection`) — never `response_data`. Any party that can place a message into a signer's own reply channel (including a rogue/compromised signer replaying another signer's already-broadcast, validly-signed acceptance/rejection with a doctored `response_data`) produces a message that still passes `verify()`/`recover_public_key()` because those checks never touch `response_data`.

### Finding Description
`create_block_acceptance` signs only the raw block sighash: [1](#0-0) 

`BlockAccepted`'s signature is verified purely against `signer_signature_hash`, with `response_data` never included in the signed bytes: [2](#0-1) 

Contrast with `BlockRejection`, which does domain-separate its hash by `chain_id` but still excludes `response_data` from what is signed: [3](#0-2) 

Both the node's `StackerDBListener` and other signers extract `tenure_extend_timestamp`/`tenure_extend_read_count_timestamp` straight out of `response_data` after only checking the signature over `block_sighash`: [4](#0-3) 

Other signers do the same in `handle_block_signature`, which recovers the public key solely from `(block_hash, signature)`, confirms it belongs to a registered signer, and then trusts the *unauthenticated* `response_data` fields for weighted-timestamp aggregation: [5](#0-4) 

These forged fields feed directly into consensus-adjacent decisions: the node aggregates per-signer idle timestamps by weight to compute the group's tenure-extend timestamp, and the miner decides whether to time-based tenure-extend based on that aggregate: [6](#0-5) [7](#0-6) 
and other signers independently gate acceptance of a proposed tenure-extend block on the *same* `calculate_full_extend_timestamp`/`calculate_read_count_extend_timestamp` value: [8](#0-7) 

Because `response_data` is not covered by the signature, its per-signer contribution can be forged by anyone able to inject a message attributed to that signer's public key (the recovered key, not the message transport identity, is what's trusted) while re-using a real, unmodified `signature`/`signer_signature_hash` pair. This is structurally the same bug class as CVE-2023-24425: the verified credential (signature) does not bind to the full scope of the data it is meant to authorize (the tenure-timing context), so a party outside that context can supply/replay values as if they belonged to the properly-scoped principal.

### Impact Explanation
A forged/skewed `tenure_extend_timestamp` can push the node's threshold-weighted extend timestamp earlier or later than what the legitimate signer actually approved, causing:
- A miner to time-based tenure-extend earlier than 70% of signers actually authorized, or
- Signers to disagree on `calculate_full_extend_timestamp`/`calculate_read_count_extend_timestamp` inputs used by `check_proposal` (`stacks-signer/src/chainstate/v1.rs`/`v2.rs`) to accept or reject a tenure-extend block, creating divergent local views (`InvalidTenureExtend` for some, accept for others) that can wedge consensus on a valid tenure-extend block or open a window for a stale/aggressive extend to be signed. This falls under the "High" impact tier: a liveness wedge / signer acting on a corrupted (non-canonical) aggregated threshold.

### Likelihood Explanation
No majority collusion is required — the flaw is purely a missing-binding issue in the signed payload, exploitable via message-transport control (e.g., replaying a legitimately observed signature with a modified `response_data`, since StackerDB messages are broadcast and publicly observable). It requires the ability to publish into the signer's reply channel, which is the same low bar ("one-slot miner plus gossip") anticipated by the report's scope.

### Recommendation
Include `response_data` (or its consensus-relevant fields) inside the signed hash for both `BlockAccepted` and `BlockRejection`, using the same domain-separated structured-data hashing already used for `BlockRejection`'s `chain_id` binding, so `signature` cryptographically commits to the full tuple `(signer_signature_hash, chain_id, tenure_extend_timestamp, tenure_extend_read_count_timestamp, reject_reason)`.

### Proof of Concept
Conceptual (no code execution performed — index limits prevented tracing exact StackerDB write-authorization internals, noted below):
1. Observe a genuine `SignerMessage::BlockResponse(BlockResponse::Accepted(accepted))` on StackerDB, where `accepted.signature` validly recovers to signer S's key over `accepted.signer_signature_hash`.
2. Construct a new `BlockAccepted` with the same `signer_signature_hash` and `signature`, but replace `response_data.tenure_extend_timestamp` with an attacker-chosen value.
3. `BlockAccepted::consensus_serialize`/`verify` still succeed because they never hash `response_data`; downstream consumers (`stackerdb_listener.rs`, `handle_block_signature`) accept the forged timestamp attributed to signer S.

Caveat: I could not fully verify, from the indexed code alone, whether the outer StackerDB chunk write-authorization (`StackerDBChunkData::sign`) would prevent an attacker without signer S's key from actually getting a *forged* message accepted into signer S's own StackerDB slot; that layer's exact resign/relay path would need to be checked directly with the full repository to confirm the concrete transport by which a non-owning party could publish this doctored message under S's attribution. Regardless, the core defect — `response_data` unauthenticated by the signature — is independently a proof-verifiable code weakness.

pub struct BlockAccepted {
    /// The signer signature hash of the block that was accepted
    pub signer_signature_hash: Sha512Trunc256Sum,
    /// The signer's signature across the acceptance
    pub signature: MessageSignature,
    /// Signer message metadata
    pub metadata: SignerMessageMetadata,
    /// Extra versioned block response data
    pub response_data: BlockResponseData,
}

impl StacksMessageCodec for BlockAccepted {
    fn consensus_serialize<W: Write>(&self, fd: &mut W) -> Result<(), CodecError> {
        write_next(fd, &self.signer_signature_hash)?;
        write_next(fd, &self.signature)?;
        write_next(fd, &self.metadata)?;
        write_next(fd, &self.response_data)?;
        Ok(())
    }

    fn consensus_deserialize<R: Read>(fd: &mut R) -> Result<Self, CodecError> {
        let signer_signature_hash = read_next::<Sha512Trunc256Sum, _>(fd)?;
        let signature = read_next::<MessageSignature, _>(fd)?;
        let metadata = read_next::<SignerMessageMetadata, _>(fd)?;
        let response_data = read_next::<BlockResponseData, _>(fd)?;
        Ok(Self {
            signer_signature_hash,
            signature,
            metadata,
            response_data,
        })
    }
}

impl BlockAccepted {
    /// Create a new BlockAccepted for the provided block signer signature hash and signature

            response_data: BlockResponseData::new(

    pub fn hash(&self) -> Sha256Sum {

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    fn should_full_tenure_extend(
        &self,
        coordinator: &mut SignerCoordinator,
    ) -> Result<bool, NakamotoNodeError> {
        if self.last_block_mined.is_none() {
            // if we haven't mined blocks yet, no tenure extends needed
            return Ok(false);
        }
        let is_replay = self.config.miner.replay_transactions
            && coordinator
                .get_signer_global_state()
                .map(|state| state.tx_replay_set.is_some())
                .unwrap_or(false);
        if is_replay {
            // we're in replay, we should always TenureExtend
            info!("Tenure extend: In replay, always extending tenure");
            return Ok(true);
        }

        // Do not extend if we have spent a threshold amount of the
        // budget, since it is not necessary.
        let usage = self
            .tenure_budget
            .proportion_largest_dimension(&self.tenure_cost);
        if usage < self.config.miner.tenure_extend_cost_threshold {
            return Ok(false);
        }

        let tenure_extend_timestamp = coordinator.get_tenure_extend_timestamp();
        if get_epoch_time_secs() <= tenure_extend_timestamp
            && self.tenure_change_time.elapsed() <= self.config.miner.tenure_timeout
        {
            return Ok(false);
        }

        info!("Miner: Time-based tenure extend";
              "current_timestamp" => get_epoch_time_secs(),
              "tenure_extend_timestamp" => tenure_extend_timestamp,
              "tenure_change_time_elapsed" => self.tenure_change_time.elapsed().as_secs(),
              "tenure_timeout_secs" => self.config.miner.tenure_timeout.as_secs(),
        );
        Ok(true)
    }
