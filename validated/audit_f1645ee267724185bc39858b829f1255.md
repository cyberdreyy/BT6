### Title
Signer weight double-counted across accept/reject tallies when a signer flips its vote - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side `StackerDBListener` aggregates each signer's block-response weight into two independent running totals, `total_weight_approved` and `total_weight_rejected`, which are later compared against `weight_threshold`/`total_weight` to decide whether a block has enough signer support to be pushed, or enough rejection weight to be abandoned. The de-duplication guard used on the *accept* path checks a different set (`gathered_signatures`) than the one used on the *reject* path (`responded_signers`), even though both paths also write into the shared `responded_signers` set. A signer that rejects a proposal first and later accepts the same proposal (a state transition the signer is explicitly allowed to make, e.g. via `should_reevaluate_block`/pre-commit re-evaluation) gets its weight counted into `total_weight_rejected` *and* later also into `total_weight_approved`, because the accept-path guard never looks at `responded_signers`. This is structurally the same bug class as the AddressWhitelist report: a guard that is correct in isolation (checking "have I already added this to gathered_signatures/whitelist") is bypassed because a different, permitted operation (an owner transfer / a vote flip) changes the relevant state without being visible to that specific guard.

### Finding Description
In `stackerdb_listener.rs`:

- On `BlockResponse::Accepted`, weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, and then the code unconditionally does `block.gathered_signatures.insert(slot_id, signature); block.responded_signers.insert(slot_id);` [1](#0-0) 
- On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot is seen in `responded_signers`) [2](#0-1) 

Because `responded_signers` is written by *both* branches but `gathered_signatures` is written only by the accept branch, the two de-duplication checks are not consistent with each other:

- Reject-then-Accept: signer rejects first → `responded_signers` now contains `slot_id`, `total_weight_rejected += weight`. Same signer later accepts the same block (a legitimate re-evaluation path, e.g. after `should_reevaluate_block`/pre-commit re-evaluation on the signer side) → the accept branch checks `gathered_signatures`, which does **not** contain `slot_id` yet, so it proceeds to add `weight` to `total_weight_approved` as well. The signer's weight now counts in both totals simultaneously.
- Accept-then-Reject is correctly guarded (the reject branch's `responded_signers.insert` returns `false` since the accept branch already inserted it), so only the asymmetric ordering is exploitable.

This breaks the invariant the threshold logic depends on: `total_weight_approved` and `total_weight_rejected` are supposed to be disjoint partitions of `total_weight` (each signer's weight should be reflected by, at most, its current/latest vote). With the bug, `total_weight_approved + total_weight_rejected` can exceed what a correct, deduplicated tally would show, and stale rejection weight lingers in `total_weight_rejected` at the same time fresh acceptance weight from the same signer is (correctly, from that signer's own current view) added to `total_weight_approved`.

### Impact Explanation
`propose_block`/`get_block_status` in the miner's `SignerCoordinator` uses these two totals to decide whether a block proposal has crossed the 70% approval threshold (push the block) or the 30%+ rejection threshold (treat as `SignersRejected`) [3](#0-2) . Inflated/duplicated weight in these node-local tallies corrupts the miner's accounting of the signer set's actual current opinion: a single signer's weight can simultaneously be counted against the block (via its earlier rejection) and for the block (via its later acceptance). In borderline situations this can distort whether the miner's local view crosses the approval or rejection threshold relative to the true, deduplicated state of signer opinion, i.e. a rejection/acceptance is effectively "recounted" using stale weight from the opposite category rather than being fully superseded — matching the "rejection recounted as acceptance" (or vice versa) class of finding.

Note that the node-local tally itself is only used to decide the *miner's local retry/push behavior* (`get_block_status`); it is not the canonical signature the network verifies — `verify_signer_signatures` still checks the actual `gathered_signatures` set for real cryptographic signatures before a block is treated as validly signed on-chain [4](#0-3) . So the direct, provable consequence is corruption of the miner-side weight bookkeeping (a safety-adjacent accounting bug reachable by a single signer's own vote-flip, no majority required), rather than a proven case of an invalid block being finally, cryptographically accepted by the network.

### Likelihood Explanation
Triggering this requires only one signer (not a majority) to send a `Rejected` response for a block and then later a valid `Accepted` response for the same block — a sequence explicitly permitted by the signer's own re-evaluation logic (`should_reevaluate_reject_reason`/pre-commit re-evaluation flows described in the signer docs) and by ordinary miner re-proposal behavior after a signature timeout. It requires no cryptographic forgery, no access to other signers' keys, and no auth token — it is purely a message-ordering issue in the node's local aggregation, matching the "one-slot miner (plus gossip)" reachability bar.

### Recommendation
Use a single, consistent de-duplication key for both accept and reject branches (e.g., always check/update `responded_signers`, and when a signer's category changes, actively remove or renormalize its weight from the opposite total rather than only guarding on insertion). Concretely, on `Accepted`, check whether `slot_id` was previously counted in `total_weight_rejected` and subtract that weight before adding to `total_weight_approved` (and symmetrically for `Rejected`), so a signer's weight is always attributed to exactly one category at a time.

### Proof of Concept
1. Node has a live block proposal being tallied in `StackerDBListener::run` for `signer_signature_hash = H`.
2. Signer S (weight `w`) sends `BlockResponse::Rejected` for `H`. Handler: `block.responded_signers.insert(slot_id)` → `true`; `block.total_weight_rejected += w`.
3. Signer S later (permitted by its own re-evaluation logic) sends `BlockResponse::Accepted` for the same `H` with a valid signature. Handler checks `!block.gathered_signatures.contains_key(&slot_id)` → `true` (S's slot was never inserted into `gathered_signatures`), so `block.total_weight_approved += w`.
4. Now `block.total_weight_approved + block.total_weight_rejected` includes `w` twice, once in each category, for the single signer S — violating the intended invariant that each signer's weight is reflected once, under its current vote, in the tally that `propose_block`/`get_block_status` uses to decide whether to push or abandon the block.
