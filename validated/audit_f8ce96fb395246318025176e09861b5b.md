### Title
Settled APR0 withdraw receipts escape the default haircut and are paid at par after `finalizeDefaultRecovery`, draining the recovery reserve from other claimants - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When a borrower default is finalized, all pending withdraw basis is haircut by `defaultRecoveryPrice`. However, an APR0 (`unscaledApr == 0`) withdraw request that was created in an epoch *before* the defaulted epoch and settled (but never claimed) is stored in `apr0Users[_user].settledPrincipal/settledInterest`. The defaulted-claim path `_claimDefaultedWithdrawRequest` only clears `apr0User.principal` keyed to `principalEpoch == defaultRecoveryEpoch`; it never touches `settledPrincipal`/`settledInterest`. Execution then falls through to `_claimFundedWithdrawRequest`, which pays the settled principal plus interest **at par** via `_transferFundedClaim`, while that same basis was already counted inside `pendingWithdraws`/`defaultPendingClaimBasis` when the recovery price was computed. One claim basis is therefore covered twice by the same reserve math — once inside the haircutted `totalBasis`, and once again at 100% — the same "count one asset to satisfy two obligations" bug class as the Opyn `exercise()` double-spend.

### Finding Description
- `requestWithdraw` mints the user a strategy-token receipt and, when `unscaledApr == 0`, records the claim only in `apr0Users[_user]` via `_requestWithdrawApr0`; `pendingWithdraws` is still increased by `_amount` (contracts/strategies/idle/IdleCreditVault.sol:271-295, 567-577).
- `_settleApr0` lazily moves `principal` into `settledPrincipal`/`settledInterest` once `epochNumber` passes the request epoch (lines 545-565). From then on `apr0User.principal == 0` and `principalEpoch == 0`.
- On default, `finalizeDefaultRecovery` includes all of `pendingWithdraws` in `totalBasis` via `defaultPendingClaimBasis` and sets `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (lines 644-699).
- `claimWithdrawRequest` first calls `_claimDefaultedWithdrawRequest`, which calls `_clearWithdrawClaimForEpoch(_user, defaultEpoch, true)`. That helper only zeroes `withdrawsRequestsByEpoch[user][defaultEpoch]` and `apr0User.principal` when `principalEpoch == defaultEpoch` (lines 811-837). A previously *settled* APR0 position has `principalEpoch == 0` and non-zero `settledPrincipal`, so it survives untouched and contributes `claimBasis == 0` for the default epoch.
- The same call then reaches `_claimFundedWithdrawRequest`, which computes `apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal` and pays `normalAmount + apr0PrincipalAmount + apr0InterestAmount` in full through `_transferFundedClaim` (lines 319-349). The epoch-wait check is bypassed once the pool is defaulted/closed (`epochEndDate == 0`), and `lastWithdrawRequest[_user]` was reset to 0 by `_clearWithdrawClaimForEpoch`.

Broken invariant: every unit of claim basis counted in `totalBasis` at finalization must be paid exactly once, at `defaultRecoveryPrice`. The settled-APR0 basis is priced at `recoveryPrice` but paid at `RECOVERY_FULL`, so the reserve is short by `settledBasis * (RECOVERY_FULL - defaultRecoveryPrice) / RECOVERY_FULL` for each such claim.

### Impact Explanation
The attacker (any KYC-passing lender who held an APR0 withdraw receipt from an earlier epoch) receives more underlying than their haircutted share. The overpayment is drawn from the same vault underlying that backs other pending receipts' recovery claims, so later claimants (normal defaulted receipts via `_claimDefaultedWithdrawRequest`, instant receipts via `_claimDefaultedInstantWithdrawRequest`, or post-default requests) find the reserve depleted — direct theft of unclaimed recovery funds and, for the last claimers, effective freezing of their claims. The theft size is deterministic: `settledPrincipal + settledInterest` times `(1 - defaultRecoveryPrice/1e18)`. With, e.g., a 70% recovery price and a 100,000 USDC settled APR0 receipt, the attacker extracts ~30,000 USDC beyond their fair share.

### Likelihood Explanation
Requires the pool to run with `unscaledApr == 0` at request time (a supported mode), a borrower default in a later epoch, and a user who requested but did not claim before finalization — a normal usage pattern since claims are intentionally permissionless and delayed by one epoch. No privileged misbehavior is needed; `isWalletAllowed`/`_onlyIdleCDO` gating does not distinguish this path, and the skim/donation isolation is irrelevant because the payout uses accounted ledger state. The only trigger is ordinary sequencer of honest manager/borrower calls (stopEpoch epochs passing, then `_handleBorrowerDefault`/`finalizeDefaultRecovery`).

### Recommendation
In `_claimDefaultedWithdrawRequest` (or `_clearWithdrawClaimForEpoch`), also clear `apr0User.settledPrincipal` and `apr0User.settledInterest` that belonged to already-finalized epochs, route them through the `defaultRecoveryPrice` haircut, and subtract their principal+interest from `pendingWithdraws`. Equivalently, treat any APR0 basis outstanding at `defaultRecoveryEpoch` — open or settled — as defaulted-epoch claim basis, so no settled bucket can fall through to `_claimFundedWithdrawRequest` after `defaultRecoveryFinalized`.

### Proof of Concept
Foundry fork PoC outline (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// setup: creditVault with unscaledApr == 0, allowInstantWithdraw off
// 1. user deposits AA, epochs run so APR0 request is possible
cdoEpoch.depositAA? // via idleCDO.depositAA(amountWei) after KYC
// 2. epoch 0..1: user calls cdoEpoch.requestWithdraw(trancheBal, AAtranche)
//    -> strategy.requestWithdraw records apr0Users[user].principal (epoch E), pendingWithdraws += amt
// 3. run another honest epoch (start/stop) so epochNumber > E
//    (settledPrincipal is populated lazily; it is enough that reqEpoch < epochNumber)
// 4. borrower defaults: manager triggers _handleBorrowerDefault path,
//    then owner/manager calls cdoEpoch.finalizeDefaultRecovery(recovered, recoverySource)
//    defaultRecoveryPrice < RECOVERY_FULL (e.g. 70%)
// 5. user calls cdoEpoch.claimWithdrawRequest()
//    expected (fixed): payout == settledBasis * defaultRecoveryPrice / 1e18
//    actual (buggy):   payout == settledBasis (par) via _claimFundedWithdrawRequest,
//    while pendingWithdraws was already haircut inside totalBasis
// 6. assert vault underlying balance < sum of remaining haircutted claims
//    -> second defaulted claimant's claimWithdrawRequest reverts/underpays (OOG on balance or shortfall)
```

Key assertion showing the double-count: after step 5, `strategy.pendingWithdraws()` still contains the settled basis (it is only decremented in `_claimDefaultedWithdrawRequest` for `claimBasis` cleared in the default epoch), yet the underlying backing it was already consumed by the par payout, leaving fewer tokens in the vault than `defaultRecoveryReserve` obligations require.
