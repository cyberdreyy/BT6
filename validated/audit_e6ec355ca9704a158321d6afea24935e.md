Unprivileged front-running of lockup creation via deterministic `owner_account_id`-derived account name - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the lockup contract's account id solely from `sha256(owner_account_id)[..20]` with no restriction on who the caller (`predecessor_account_id`) is, other than attaching `MIN_ATTACHED_BALANCE`. Any unprivileged attacker can call `create` for a victim's `owner_account_id` with weak/no vesting parameters, permanently occupying the deterministic account name before the legitimate grantor (e.g. the foundation) creates the intended vesting lockup.

### Finding Description
The broken binding: for a given `owner_account_id = V`, the intended invariant is `lockup_account_id(V).vesting_schedule == the vesting terms the rightful grantor for V chose`. Instead, the actual binding realized on-chain is `lockup_account_id(V) == first successful caller's chosen parameters`, because the account name is `hex(sha256(V)[..20]).factory` [1](#0-0) , independent of `env::predecessor_account_id()`.

`create` is `#[payable]` and public, gated only by `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)` [2](#0-1)  — there is no `assert_called_by_foundation` or owner check anywhere in `LockupFactory`; the only privileged-style checks in `utils.rs` are `assert_self()` (used in the callback, checking the promise came from the contract itself) and `is_promise_success()`, neither of which restrict who may call `create` [3](#0-2) .

Exploit flow:
1. Attacker calls `create(owner_account_id = victim, lockup_duration, lockup_timestamp=None, vesting_schedule=None, release_duration=None, whitelist_account_id=None)` attaching exactly `MIN_ATTACHED_BALANCE` from their own funds.
2. Because `vesting_schedule` is `None`, `foundation_account` stays `None` [4](#0-3) , so the created lockup has no foundation-controlled termination/vesting.
3. `Promise::new(lockup_account_id).create_account().deploy_contract(...).transfer(...).function_call("new", ...)` executes and succeeds, creating the account at the deterministic name [5](#0-4) .
4. When the legitimate grantor later calls `create` with the same victim `owner_account_id` and a real `vesting_schedule`, the resulting `lockup_account_id` is identical (same sha256 hash), so `Promise::new(lockup_account_id).create_account()` fails on a live network because the account already exists — permanently blocking the intended vesting lockup for that victim.

No existing guard (`assert_self`, `is_promise_success`, deposit check) prevents an arbitrary caller from choosing the `owner_account_id` and pre-creating the account; the callback `on_lockup_create` only handles refund-on-failure for the *attacker's own* creation, not protection for a subsequent legitimate creator.

### Impact Explanation
This matches the Critical category: "a lockup deployed with parameters its rightful creator never chose." The victim's intended grantor is permanently denied the ability to establish the intended vesting terms at the canonical lockup address for that owner, freezing/denying the intended grant terms indefinitely (no redeploy possible without foundation/owner action to migrate, which is out of scope). The attack is repeatable across any victim account name the attacker wants to squat on, at a cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) per victim, which the attacker's own funds cover (recoverable by the attacker afterward since they own the created lockup with weak parameters, or they can even leave it under their own economic control since `owner_account_id` only encodes identity/withdrawal rights inside the lockup contract terms, not creation rights).

### Likelihood Explanation
Feasibility is high: the attacker only needs a NEAR account and `MIN_ATTACHED_BALANCE` (~3.5 NEAR), both within the stated unprivileged attacker capabilities. No special permissions, keys, or foundation access are required — this is a direct, low-cost, deterministic front-run of the `create` entrypoint, executable by anyone at any time.

### Recommendation
Restrict `create` (or at minimum, restrict the ability to set `vesting_schedule`/foundation-controlled parameters, and/or gate lockup creation for accounts intended to receive vesting) to `assert_called_by_foundation` or an equivalent allow-list check, similar to guarding sensitive operations elsewhere in the codebase. Alternatively, derive the lockup account name from a caller/grantor-specific salt (not purely from `owner_account_id`), so an attacker cannot squat the exact deterministic address intended for a victim's legitimate grant.

```rust
// lockup-factory/src/lib.rs tests module (near-workspaces / near-sdk-sim style)
#[test]
fn test_frontrun_lockup_creation_blocks_legit_grant() {
    // Setup factory as in existing tests.
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Step 1: ATTACKER (unrelated to victim) creates lockup for victim's owner_account_id
    // with no vesting schedule, using their own funds.
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(35); // >= MIN_ATTACHED_BALANCE
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    contract.on_lockup_create(
        lockup_account(), // deterministic id = sha256(account_tokens_owner())[..20].factory
        ntoy(30).into(),
        String::from("attacker.near"),
    );
    // Assert: lockup_account() now exists on chain with vesting_schedule = None.

    // Step 2: LEGITIMATE GRANTOR (e.g. foundation) later tries to create the real
    // vesting lockup for the SAME owner_account_id.
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    let vesting_schedule = Some(/* real VestingScheduleOrHash */);
    contract.create(account_tokens_owner(), lockup_duration, None, vesting_schedule, None, None);

    // On a real network, Promise::new(lockup_account_id).create_account() would now
    // FAIL because lockup_account() already exists from Step 1 — asserting that the
    // second creation's deterministic account id equals the first (same sha256 hash)
    // and that create_account on an existing account errors, proving the legitimate
    // vesting grant is permanently blocked.
    assert_eq!(
        format!("{}.{}", hex::encode(&env::sha256(account_tokens_owner().as_bytes())[..20]), account_factory()),
        lockup_account()
    );
}
```
