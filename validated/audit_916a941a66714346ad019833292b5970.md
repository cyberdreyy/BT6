### Title
`lossRecoveryPriceByEpoch` is keyed by the post-increment `epochNumber`, but claims look it up by the pre-increment request epoch — loss-adjusted receipts are paid at par, causing insolvency - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The CVE bug class is an out-of-bounds/mis-indexed access driven by a stale pointer. In `IdleCreditVault`, the loss-recovery haircut recorded at `stopEpochWithDuration` time is stored under the *already-incremented* `epochNumber`, while both the write-side guard and the claim-side lookup index `lossRecoveryPriceByEpoch` with `lastWithdrawRequest[_user]`, which holds the *pre-increment* request epoch. The two indexes never coincide for the receipts they are meant to describe, so the haircut is silently skipped and pending withdraw receipts are paid at par from underfunded reserves — and, as a collision side-effect, receipts requested in the next epoch are incorrectly haircut and then permanently frozen by the re-request guard.

### Finding Description
`requestWithdraw` snapshots `currentEpoch = epochNumber` (the epoch the request was made in), stores the receipt in `withdrawsRequestsByEpoch[_user][currentEpoch]`, and sets `lastWithdrawRequest[_user] = currentEpoch` (lines 260–293). [1](#0-0) 

`epochNumber` is incremented inside `deposit()` when `isEpochRunning()` is still true — i.e., during the same `stopEpoch` transaction that funds pending withdrawals (lines 607–614). [2](#0-1) 

`collectWithdrawFunds` then records the underfunding haircut under the *new* `epochNumber` (line 421), not under the request epoch of the receipts being haircut. [3](#0-2) 

Both readers use the stale pre-increment index:

- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the request epoch — and finds `0`, so it returns 0 and the claim falls through to `_claimFundedWithdrawRequest` (lines 789–801, 312–313). [4](#0-3) 
- `_claimFundedWithdrawRequest` only checks `epochNumber <= lastWithdrawRequest[_user]`, which is now false because `epochNumber` was incremented, and pays the full `withdrawsRequests[_user]` basis at par via `_transferFundedClaim` (lines 326–349). [5](#0-4) 

The mirror-image collision: the haircut stored at key `epochNumber` (new) is exactly the key under which a *fresh* request made in the following epoch records its receipt (`currentEpoch` after increment). That user's `_claimLossAdjustedWithdrawRequest` then finds a nonzero price for their request epoch and applies a haircut meant for the previous epoch's receipts; after clearing, `lastWithdrawRequest[_user]` is reset but the stale `lossRecoveryPriceByEpoch` entry remains and the re-request guard at lines 263–271 (`lossRecoveryPrice != 0 && withdrawsRequestsByEpoch[_user][lossEpoch] != 0`) makes any subsequent `requestWithdraw` revert. [6](#0-5) 

No existing guard stops this: `collectWithdrawFunds` happily accepts partial funding (`_amount < pendingBasis`), `_transferFundedClaim` only enforces the `defaultRecoveryReserve` isolation (irrelevant pre-default), and solvency is enforced nowhere at claim time — whoever claims first takes the funded cash, leaving later claimants and active LPs to absorb the shortfall.

### Impact Explanation
Direct insolvency / theft of unclaimed yield. If a `stopEpoch` with loss funds `pendingWithdraws` at price `p < 1`, the first pending redeemer(s) to call `claimWithdrawRequest` receive `claimBasis` at par instead of `claimBasis * p`, draining the strategy's funded cash. Once the funded amount is exhausted, remaining receipts (and, transitively, tranche holders whose NAV was already reduced by the BB-first loss waterfall) can never be paid — a permanent freeze/shortfall equal to `pendingBasis * (1 - p)`. Symmetrically, users requesting in the next epoch have fully-funded receipts paid at the stale haircut `p` (underpayment frozen as dust in the strategy) and are then permanently blocked from re-requesting by the guard.

### Likelihood Explanation
Requires only an honest `stopEpochWithDuration(_lossAmount > 0)` or any underfunded `collectWithdrawFunds` — a routine borrower-loss path explicitly supported by `previewLossAdjustedWithdrawFunds`. The attacker is an ordinary withdraw requester (KYC'd tranche holder): request in epoch N, wait for the lossy stop, claim at par before other requesters. The mis-indexing is deterministic on every loss-adjusted epoch; no privileged misbehavior needed.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the epoch the receipts belong to, not the counter at collection time. Concretely, in `collectWithdrawFunds` store the haircut under `epochNumber - 1` (the just-ended request epoch), or capture the request epoch explicitly. Alternatively, snapshot `epochNumber` before `deposit()` increments it and pass it through. Add an invariant test asserting `lossRecoveryPriceByEpoch` is only ever read at keys equal to a receipt's `lastWithdrawRequest`/`principalEpoch`, and a fork test where `collectWithdrawFunds` receives `pendingBasis * 90%` and verifies claims pay exactly 90%.

**Uncertainty:** the exact ordering of `deposit()` (the `epochNumber += 1` site) versus `collectWithdrawFunds` inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` was not fully traced in this iteration — if `collectWithdrawFunds` is invoked strictly before the deposit that increments `epochNumber`, the stored key equals the request epoch and the primary path is correct, leaving only the stale-entry re-request freeze and the cross-epoch collision (a fresh request's `lastWithdrawRequest` equals a previously-written loss key only if epochs are reused, which they are not — so that half of the finding depends on the same ordering question). The PoC assertion ordering above pins down which regime the code is in.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
