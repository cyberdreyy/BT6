## Analysis

Based on `docs/signer-flows.md:425-437` and `stacks-signer/src/chainstate/v1.rs:461-520` / `stacks-signer/src/chainstate/v2.rs:306-359`, the "duplicate tenure-start block" (`DuplicateBlockFound`) admission check runs **only at proposal time**, inside `validate_tenure_change_payload`, and is explicitly documented as never re-run at validate-ok or at signing:

> "Because the duplicate check never runs again, a block that crosses the pre-commit threshold long after it was proposed relies on section 5's own-tenure conflict guard to cover the same ground." [1](#0-0) 

Critically, the fallback safety net at signing time (`handle_block_signature`, `stacks-signer/src/v0/signer.rs:1368-1457`) explicitly states it does **not** cover this case for tenure-change blocks:

> "The chainstate checks don't cover this for tenure-change blocks: those check the parent tenure instead of their own." [2](#0-1) 

That fallback only fires when a *fresh, still-live* conflict exists (`get_signed_conflicts`, freshness cutoff via `tenure_last_block_proposal_timeout`, `conflict_still_blocks`) [3](#0-2) , or when the conflict is stale but the node's tenure tip is already at/above the proposed height [4](#0-3) . A conflict that is stale **and** the node has not yet advanced its view of that tenure (e.g., the node is momentarily behind, unreachable, or the conflicting block hasn't propagated to this signer's own node) passes through untouched, and `handle_block_signature` proceeds straight to `mark_locally_accepted` and produces a signature [5](#0-4) .

Additionally, v1's proposal-time duplicate check is strictly narrower than v2's: v1 only consults `get_last_globally_accepted_block` (a block with enough signatures to be canonical), whereas v2 consults `get_last_signed_block` (locally **or** globally accepted — i.e., anything this signer itself has already put a signature on): [6](#0-5) [7](#0-6) 

A dedicated regression test confirms this exact gap existed and was fixed for v2's own-tenure duplicate check via `get_last_signed_block`, explicitly noting the prior bug: "Before the fix, this would have incorrectly passed because `get_last_globally_accepted_block` would not find the locally-accepted block." [8](#0-7) . The v1 path (`chainstate/v1.rs`) still uses `get_last_globally_accepted_block` for this same check, so a v1-mode signer's proposal-time duplicate guard does not see a block *it itself has already locally accepted* in the same tenure — only the signing-time-only, freshness/liveness-gated `get_signed_conflicts` fallback stands between the signer and double-signing two competing tenure-start blocks in the same tenure.

### Title
Signer can be induced to sign two conflicting tenure-start blocks in the same tenure — `DuplicateBlockFound` guard is proposal-time-only and, under v1, blind to locally-accepted blocks - (File: `stacks-signer/src/chainstate/v1.rs`, `stacks-signer/src/v0/signer.rs`)

### Summary
The one check that prevents a signer from putting a *second* signature on a competing tenure-start block within the same tenure (`validate_tenure_change_payload` → `DuplicateBlockFound`) runs exclusively at proposal-arrival time and is never re-verified at validate-ok or at the moment the pre-commit threshold triggers a signature. The only re-check at signing time (`handle_block_signature`'s `get_signed_conflicts` walk) is explicitly documented and coded to be a liveness-gated, node-view-dependent fallback that does not reproduce the tenure-scoped duplicate check for tenure-change blocks. Under the v1 chainstate path, the proposal-time check itself is also narrower than v2's, using `get_last_globally_accepted_block` instead of `get_last_signed_block`, so it misses conflicts the signer itself has already locally accepted (i.e., already signed) but that have not yet reached global acceptance.

### Finding Description
`check_block_against_signer_db_state` (invoked at validate-ok, `stacks-signer/src/v0/signer.rs:1946`, and again just before signing, `stacks-signer/src/v0/signer.rs:1345`) re-runs `check_latest_block_in_tenure` — but for a tenure-change block this checks the **parent** tenure, not the block's own tenure, by design [9](#0-8) . The only mechanism that ever inspects same-tenure duplication for a tenure-start block is `validate_tenure_change_payload`, called solely from `check_proposal` at proposal time [10](#0-9) .

Two independent windows let a miner get a signature on a second/conflicting tenure-start block for the same tenure past this guard:

1. **Timing window (both v1 and v2).** A miner proposes block A (tenure-start), which passes `validate_tenure_change_payload` because no block in this tenure has yet been accepted. The signer validates A, pre-commits. Before A crosses the 70% pre-commit threshold, the miner proposes a competing tenure-start block B for the *same tenure* (different transactions/timestamp ⇒ different `signer_signature_hash`, so `validate_tenure_change_payload` on B also sees "no accepted block yet" and passes). Both A and B now sit in `PreCommitted` state. Whichever block first reaches 70% pre-commit weight triggers `handle_block_signature`, whose only re-check is `get_signed_conflicts` at chain_length granularity plus liveness gating [11](#0-10) . If the other block hasn't yet been signed by *this* signer (still pre-committed, not locally accepted) or the local node hasn't yet observed the competing tenure's tip, this signer can sign both A and B in turn once each reaches threshold — the tenure-scoped `DuplicateBlockFound` guard that exists specifically to prevent this is never invoked again.
2. **v1-specific coverage gap.** Even outside the timing window, v1's `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:505-518`) only queries `get_last_globally_accepted_block`. If this very signer has already locally accepted (signed) a tenure-start block for the tenure but it hasn't yet reached global acceptance, a second competing tenure-start proposal for the same tenure will not be rejected by the proposal-time check, exactly the scenario the `check_tenure_change_rejects_when_locally_accepted_block_exists` regression test (`stacks-signer/src/chainstate/tests/v2.rs:755-850`) was written to close — but only for v2's `get_last_signed_block`, not v1's `get_last_globally_accepted_block`.

This breaks the "one-per-height / one-per-tenure" equality the signer is supposed to enforce: a single signer's signature is expected to be exclusive per tenure-start, but the guard enforcing that exclusivity is asymmetric across code paths (proposal-time only, and version-dependent in scope).

### Impact Explanation
This is a Critical-class outcome per the rubric: a signer being induced to sign two conflicting (non-canonical relative to each other) tenure-start blocks for the same tenure is exactly the "signer signing an invalid/non-canonical/conflicting block" case. Two conflicting signer-endorsed tenure-start blocks for one tenure can contribute weight toward two different candidate chains simultaneously, undermining the single-slot/one-per-tenure guarantee the pre-commit/threshold design is built to provide, and can be leveraged by a single malicious (or simply fast-repropoosing) miner without needing any other signer's key or a majority of signers.

### Likelihood Explanation
Triggering the timing window requires only that the same one-slot miner propose two competing tenure-start blocks in quick succession (well within existing `block_proposal_max_age_secs` bounds) and race pre-commit gossip so that neither block is yet locally accepted by a given signer when the other crosses threshold for that signer — plausible under normal network jitter, no majority-signer collusion needed. The v1-only gap is deterministic whenever a signer is still running the v1 chainstate path and has locally-but-not-globally accepted a tenure-start block, which is an ordinary, non-adversarial intermediate state on the way to global acceptance.

### Recommendation
- Re-run a same-tenure duplicate/conflict check (equivalent in scope to `validate_tenure_change_payload`'s `DuplicateBlockFound` logic) at validate-ok and immediately before signing, not just at proposal time, mirroring how `check_latest_block_in_tenure` is already re-run for the parent-tenure case.
- In `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload`, replace `get_last_globally_accepted_block` with `get_last_signed_block` (as already done in v2) so the proposal-time check also sees locally-accepted (self-signed) blocks in the same tenure.
- Ensure `handle_block_signature`'s `get_signed_conflicts` fallback treats same-tenure tenure-start conflicts as a hard block regardless of freshness/node-liveness gating, since freshness gating is appropriate for cross-tenure reorg conflicts but not for literal same-tenure double-signing.

### Proof of Concept
1. Boot a signer set with the v1 chainstate path (or, for the timing-window variant, either v1 or v2).
2. As the tenure's sole miner, propose tenure-start block A with a tenure-change tx (`cause: BlockFound`) for consensus_hash `CH`. Let signers validate and pre-commit A, but do not let A reach the 70% pre-commit/signature threshold yet (delay gossip from a subset of signers, as done in the existing test harness's `TEST_BROADCAST_PROPOSAL_STALL`/pause-commit mechanisms, e.g. `stacks-node/src/tests/signer/v0/signers_wait_for_validation.rs`).
3. Before any signer locally accepts A, propose a second tenure-start block B for the same consensus_hash `CH` with different transactions/timestamp (different `signer_signature_hash`). `validate_tenure_change_payload` for B on a given signer sees no globally accepted (v1) / no signed (race-window) block yet for `CH`, so B also gets validated and pre-committed.
4. Release gossip so that B's pre-commits reach threshold first on some signer S while A is still only pre-committed for S; S signs B via `handle_block_signature`.
5. Then release the remaining pre-commits for A; once A also reaches threshold for S, `get_signed_conflicts` is queried — if the conflict (B) is stale per `tenure_last_block_proposal_timeout` or the node hasn't yet observed B's tenure tip, S signs A as well, producing two valid signer-endorsed but mutually conflicting tenure-start blocks for tenure `CH` from the same signer, reproduced analogously to the existing `check_tenure_change_rejects_when_locally_accepted_block_exists` / `check_tenure_change_accepts_when_only_pre_committed_block_exists` test scaffolding in `stacks-signer/src/chainstate/tests/v2.rs:755-952`, but exploiting the v1 `get_last_globally_accepted_block` gap and/or the "duplicate check never runs again" window explicitly called out in `docs/signer-flows.md:425-437`.

        // freshness first: it is a local timestamp comparison, while `reorg_permit_stands`
        // and `conflict_still_blocks` each query the node, so stale conflicts cost no
        // round-trips.

            conflict.last_endorsed > freshness_cutoff
