## Title
Front-running the multisig-factory `create` call causes permanent loss of the victim's attached deposit and hijack of the intended multisig account name - (File: `multisig-factory/src/lib.rs`)

## Summary
`MultisigFactory::create` derives the new multisig's account ID deterministically from a user-supplied `name` and creates it via a single `Promise::new(account_id).create_account().deploy_contract(...).transfer(...).function_call("new", ...)` batch, with **no `.then()` callback** to handle failure of that promise. [1](#0-0)  Because a subaccount name can only be created once, an unprivileged attacker can observe a pending `create` transaction in the mempool and front-run it by calling `create` first with the same `name` (and members/threshold of the attacker's own choosing). The victim's transaction then executes against an account ID that already exists, the `create_account` action fails, and — unlike the sibling `lockup-factory` and `staking-pool-factory` contracts — there is no callback to detect the failure and refund the attached deposit to the original caller.

## Finding Description
Compare this to `lockup-factory` and `staking-pool-factory`, which both attach an `on_*_create` callback that checks `is_promise_success()` and, on failure, explicitly returns the attached deposit to `predecessor_account_id`: [2](#0-1) [3](#0-2) 

`MultisigFactory::create` has no equivalent safeguard: [4](#0-3) 

The account ID is fully determined by attacker-visible input (`name`) plus the fixed factory account ID: `format!("{}.{}", name, env::current_account_id())`. [5](#0-4)  If an attacker submits their own `create(name, attacker_members, attacker_num_confirmations)` call for the same `name` and it lands first, the account `name.<factory>` is created and controlled by the attacker. When the victim's original `create` transaction then executes, the `create_account` action inside the promise batch fails because the account already exists, which also prevents the subsequent `transfer` action in the same batch from executing. Per NEAR's receipt semantics, the un-executed attached deposit is refunded to the *predecessor of the failed receipt* — the `MultisigFactory` contract account itself, not the original caller — because there is no callback to forward it onward. `MultisigFactory` exposes no method to view or withdraw this balance, so the victim's NEAR becomes permanently stuck in the factory contract's own balance.

This breaks the binding: *attached_deposit paid by the caller of `create`* should equal *NEAR ultimately held by the multisig account the caller intended to control, or refunded to the caller on failure*. Instead the deposit is diverted to the factory account with no code path to recover it, while the account name the victim expected to control is now the attacker's multisig.

## Impact Explanation
This matches the "Critical" bucket: funds permanently frozen (the victim's deposit lands in the factory contract with no withdrawal mechanism) and a wrongly-parameterised deployment (the account name the victim expected is instead owned/controlled by attacker-chosen members and threshold). Unlike the referenced report, this is not mere transaction reversion/DoS — the victim's deposit is not returned to them at all, it is silently absorbed by the factory contract.

## Likelihood Explanation
Requires only an unprivileged attacker able to observe a pending `create` call (public mempool) and submit their own transaction with the same `name` and sufficient gas/deposit ahead of it — no owner, multisig member, or special privilege is needed. The `name` value is a plain function argument, fully visible before execution.

## Recommendation
Add a `.then()` callback to `MultisigFactory::create` (mirroring `on_staking_pool_create` / `on_lockup_create`) that checks `is_promise_success()` and refunds `env::attached_deposit()` to `env::predecessor_account_id()` if account creation/deployment failed, rather than allowing the deposit to be silently absorbed by the factory contract.

## Proof of Concept
1. Victim submits `create(name="team", members=[...], num_confirmations=2)` with an attached deposit, intending to deploy their multisig at `team.<factory>`.
2. Attacker observes this pending transaction and submits `create(name="team", members=[attacker_key], num_confirmations=1)` with a minimal valid deposit, with higher gas price/priority so it lands first.
3. Attacker's transaction succeeds: `team.<factory>` is created and deployed as a multisig controlled solely by the attacker.
4. Victim's transaction executes: `Promise::new("team.<factory>").create_account()...` fails because the account already exists; the batch's `transfer` action never executes.
5. Because `create` has no `.then()` callback (contrast with `lockup-factory`/`staking-pool-factory`), the victim's attached deposit is refunded only to the `MultisigFactory` contract account itself (the predecessor of the failed receipt) and is never returned to the victim or delivered to any multisig — it is permanently stuck, since `MultisigFactory` has no function to spend or withdraw its own balance. impl MultisigFactory {
    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
