### Title
Defaulted instant-withdraw receipts are paid at par if claimed before instant default finalization - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Tokensoft M-6 bug class is: an entitlement stored for a user is later *adjusted* by the protocol, but the claim path re-derives the payout from a stale, pre-adjustment value, so the adjustment is silently discarded. The same class exists in `IdleCreditVault.claimInstantWithdrawRequest`: once `defaultRecoveryFinalized` is set, defaulted-epoch instant receipts are supposed to be paid at the haircut price `defaultRecoveryPrice`. However, the haircut path only executes when `defaultInstantWithdrawsFinalized` is also true. In the window between default finalization and instant-withdraw default finalization, a claim pays the full stale `instantWithdrawsRequests[_user]` amount at par via `_transferFundedClaim`, ignoring the pending haircut.

### Finding Description
`claimInstantWithdrawRequest` branches on both flags:

```solidity
if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
  _claimDefaultedInstantWithdrawRequest(_user);
}
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [1](#0-0) 

The haircut path `_claimDefaultedInstantWithdrawRequest` is the only place that applies `defaultRecoveryPrice` to defaulted-epoch receipts (lines 842-856). Before `defaultInstantWithdrawsFinalized` is set, that branch is skipped and the full aggregate `instantWithdrawsRequests[_user]` — which still includes the defaulted-epoch receipt (`instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` was added into it at request time, lines 366-372) — is burned and paid 1:1.

This mirrors M-6 exactly: the stored receipt (`records[beneficiary].total` / `instantWithdrawsRequestsByEpoch`) was repriced downward by a later protocol action (`adjust` / default finalization), but the claim uses the stale pre-adjustment aggregate.

### Impact Explanation
A user whose instant withdrawal was pending in the defaulted epoch receives 100% instead of `claimBasis * defaultRecoveryPrice / RECOVERY_FULL`. The excess is drawn from the strategy's funded underlying balance, which is meant to back other users' funded claims and the default recovery reserve. This is direct theft/insolvency: early claimers in the gap window extract more than their haircut entitlement at the expense of later claimers and the recovery reserve.

### Likelihood Explanation
Requires a specific sequencing: borrower default → `defaultRecoveryFinalized` set → user calls `claimInstantWithdrawRequest` through the CDO before the manager/owner finalizes the instant-withdraw default bucket. The privileged actors remain honest; the attacker is only an unprivileged withdraw requester timing their claim. Reachability depends on whether `defaultRecoveryFinalized` and `defaultInstantWithdrawsFinalized` are set in separate calls — I could not fully verify the exact finalization ordering in `IdleCDOEpochVariant`/`finalizeDefaultRecovery` within the available iterations, so this ordering assumption should be confirmed against those functions before treating the finding as conclusive.

### Recommendation
Gate the par-claim path so it cannot run while defaulted-epoch instant receipts exist but the instant default bucket is not finalized — e.g., revert or skip when `defaultRecoveryFinalized && !defaultInstantWithdrawsFinalized`, or finalize instant defaults atomically with `defaultRecoveryFinalized`.

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```
