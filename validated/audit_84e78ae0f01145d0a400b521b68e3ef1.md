### Title
Already-claimed instant withdraw receipts are counted again in the default-recovery basis and prefunded reserve, diluting recovery and leaving late claimants unpayable - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The reported bug is a double-free: a global cleanup routine frees the same memory twice because stale shared state is not scoped/cleared. The analog in `IdleCreditVault` is a double-counted claim: instant-withdraw receipts claimed at par are never removed from `instantWithdrawClaimsByEpoch`/`instantWithdrawsRequestsByEpoch`, so the same underlying is counted twice — once as paid cash and again as recovery basis/reserve — during `finalizeDefaultRecovery`.

### Finding Description
When a user requests an instant withdrawal, `requestInstantWithdraw` records the amount in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, and `instantWithdrawClaimsByEpoch[epoch]` [1](#0-0) .

When the CDO funds the request (`collectInstantWithdrawFunds`), only `pendingInstantWithdraws` is decremented [2](#0-1) . When the user then claims via `claimInstantWithdrawRequest`, only `instantWithdrawsRequests[_user]` is zeroed — the per-epoch ledgers and `instantWithdrawClaimsByEpoch` keep the stale (already-paid) amounts [3](#0-2) . Those stale per-epoch entries are only cleared inside `_claimDefaultedInstantWithdrawRequest` [4](#0-3) .

If, later in the same epoch, other instant requests remain unfunded (`pendingInstantWithdraws != 0`) and the borrower defaults, `finalizeDefaultRecovery` computes `defaultPendingClaimBasis()` which re-adds the full `instantWithdrawClaimsByEpoch[epochNumber]` — including receipts already paid out at par [5](#0-4) . Worse, `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying still held by the strategy, even though part of it was already transferred to claimers [6](#0-5) . The stale entries become part of `reserveAmount` and `totalBasis` [7](#0-6)  — the same tokens are "freed" twice: once paid to the early claimer, once promised to recovery claimants.

### Impact Explanation
Two consequences:

1. **Diluted recovery.** `totalBasis` is inflated by already-paid claims, lowering `recoveryPrice` for every genuine defaulted receipt holder and for active LPs' crystallized NAV.
2. **Insolvency / permanent freezing of unclaimed recovery.** `defaultRecoveryReserve` is set to a value larger than the strategy's actual balance (the phantom prefunded part was already paid out). Each `_transferDefaultRecovery` decrements the reserve but the token balance runs out first [8](#0-7) . Late claimants' `safeTransfer` reverts, permanently freezing their recovery proceeds.

Loss is bounded by the instant-withdraw amount claimed at par before default finalization within the defaulting epoch.

### Likelihood Explanation
Requires: instant withdrawals enabled; a partially funded instant queue (CDO collects only part via `getInstantWithdrawFunds`, which the codebase explicitly supports — the test at `IdleCreditVault.t.sol:4516-4524` shows mixed funded/unfunded instant claims); an early unprivileged claimer; then a borrower default with finalization in the same epoch. None of the guards stop it: `_transferFundedClaim`'s reserve check only protects a *set* reserve, `_ensureDefaultRecoveryInitialized` explicitly never clears pending instant state, and the underflow on `instantWithdrawsRequests[_user] -= claimBasis` (line 848) blocks the early claimer's second payout but not the basis/reserve inflation harming everyone else.

### Recommendation
Decrement `instantWithdrawClaimsByEpoch[epoch]` (and clear `instantWithdrawsRequestsByEpoch[_user][epoch]`) whenever an instant receipt is paid at par in `claimInstantWithdrawRequest`, so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only count claims whose funds are still held. Alternatively, track a separate per-epoch "funded but unclaimed" counter instead of deriving it as `instantBasis - pendingInstant`.

### Proof of Concept
Foundry fork scenario (mirroring `testFinalizeDefaultHaircutsPendingInstantRedeems` in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Epoch N running, instant withdrawals enabled via setInstantWithdrawParams.
// 1. userA and userB each requestInstantWithdraw(X). 
//    instantWithdrawClaimsByEpoch[N] = 2X, pendingInstantWithdraws = 2X.
// 2. Manager calls getInstantWithdrawFunds(); CDO only collects X
//    (partial funding) -> pendingInstantWithdraws = X.
// 3. userA calls claimInstantWithdrawRequest() -> receives X at par.
//    instantWithdrawsRequestsByEpoch[userA][N] stays = X (stale);
//    instantWithdrawClaimsByEpoch[N] stays = 2X.
// 4. Borrower defaults at stopEpoch; finalizeDefault(recovered, src).
//    basis counts 2X instant claims; prefunded reserve counts X that
//    was already paid to userA.
// 5. Assert: defaultRecoveryReserve > underlyingToken.balanceOf(strategy)
//    by the claimed amount, and recoveryPrice is deflated by X/(totalBasis).
// 6. userB.claimInstantWithdrawRequest() -> recovery payout is haircut
//    more than intended; last claimant's transfer reverts (insufficient
//    balance), permanently freezing the residual reserve.
```

Uncertainty: I could not fully trace `getInstantWithdrawFunds`/`allowInstantWithdraw` gating inside `IdleCDOEpochVariant.sol` within the available iterations to confirm the CDO permits a funded claim while other epoch-N instant requests remain unfunded, though the existing test (`claimData[1] - pendingInstant`) strongly indicates partial funding is a supported state.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
