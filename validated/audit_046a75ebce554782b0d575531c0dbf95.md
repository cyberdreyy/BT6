`LockupContract::new` is annotated with `#[init]` on the `#[near_bindgen]` impl block, using `near-sdk = "3.1.0"`.### Title
Missing `state_exists` guard in `LockupContract::new` allows unprivileged re-initialization/takeover of an existing lockup - (`lockup/src/lib.rs`)

### Summary
`LockupContract::new` in `lockup/src/lib.rs` is marked `#[init]` but never asserts `!env::state_exists()` before constructing and persisting a fresh `Self`, unlike every sibling contract in this repo (`whitelist`, `multisig`, `voting`, `staking-pool-factory`), which all explicitly guard their `new` with `assert!(!env::state_exists(), ...)`. Any unprivileged party can send a `FunctionCall` with method `"new"` to an already-initialized lockup account and completely overwrite its state, including `owner_account_id`, `vesting_information`, `lockup_information`, `staking_information`, and `foundation_account_id`.

### Finding Description
The invariant that should hold is: `env::state_exists() == false` must be true immediately before `LockupContract::new` persists state, exactly once per account. Comparing the code: [1](#0-0) 

shows `new` performs only input-validity asserts (`is_valid_account_id`, vesting/foundation consistency) and then unconditionally returns a freshly constructed `Self { owner_account_id, lockup_information, vesting_information, staking_information: None, staking_pool_whitelist_account_id, foundation_account_id }`. There is no `assert!(!env::state_exists(), ...)` anywhere in this function.

By contrast, every other `#[init]` constructor in this same codebase explicitly performs that check: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

This confirms that in the `near-sdk = "3.1.0"` version used here ( [7](#0-6) ), the `#[init]` attribute macro does not automatically enforce single-initialization — it is purely a convention each contract must implement manually, and `lockup/src/lib.rs` omits it.

Exploit flow: since a `FunctionCall` transaction only needs `receiver_id` = the victim lockup account and does not require any access key on that account, an attacker (unprivileged, no keys, not owner/foundation) can directly call:
```
victim_lockup.new(
  owner_account_id = <attacker_account>,
  lockup_duration = 0,
  lockup_timestamp = None,
  transfers_information = TransfersEnabled { transfers_timestamp: <past> },
  vesting_schedule = None,
  release_duration = None,
  staking_pool_whitelist_account_id = <anything valid>,
  foundation_account_id = None,
)
```
This overwrites the contract's stored `LockupContract` state, setting `owner_account_id` to the attacker's own account, `lockup_amount` to the current account balance (`env::account_balance()` at call time), no vesting, and transfers already enabled. The attacker can then call the owner-only `transfer` method (guarded only by `predecessor_account_id == owner_account_id`) to move the full balance out, since they are now the recorded owner. None of the existing guards (`assert_owner`, `assert_called_by_foundation`, `assert_self()`, `assert_transfers_enabled`, etc.) protect the `new` entrypoint itself, because those guards only run inside already-initialized owner/foundation methods — they never gate re-entry into `new`.

The "cliff timestamp" framing in the question is a red herring for the underlying flaw here: the missing guard is unconditional and works at any `block_timestamp`, not merely at the cliff nanosecond; the cliff-timing detail matters for related vesting-hash-reveal races but is not required to exploit this specific missing-check bug.

### Impact Explanation
This allows any unprivileged actor to seize full control of any deployed lockup contract account and move all NEAR held by that account to themselves, deleting the rightful owner's and NEAR Foundation's ability to enforce vesting/lockup/termination — a full loss of funds for the legitimate lockup beneficiary. This is repeatable against every existing lockup account and matches the Critical category: "NEAR ... moved out of a ... lockup ... by a party not entitled to it" and "locked or unvested tokens released early."

### Likelihood Explanation
No special preconditions are needed beyond knowing a target lockup account ID (these are deterministic and public via the lockup factory, or discoverable on-chain) and paying ordinary transaction gas. No deposit, no owner/foundation privilege, no key compromise required. This is trivially and repeatably exploitable against any live lockup account deployed from this codebase.

### Recommendation
Add `assert!(!env::state_exists(), "The contract is already initialized");` as the first statement in `LockupContract::new` in `lockup/src/lib.rs`, mirroring the guard present in `whitelist/src/lib.rs`, `multisig/src/lib.rs`, `voting/src/lib.rs`, `staking-pool-factory/src/lib.rs`, and `lockup-factory/src/lib.rs`.

### Proof of Concept
```rust
// lockup/src/lib.rs tests module
#[test]
#[should_panic(expected = "already initialized")]
fn test_reinit_blocked() {
    let context = basic_context();
    testing_env!(context.clone());
    let _contract = new_contract(true, None, None, false);

    // Attacker attempts to re-init the same account state.
    testing_env!(context.clone());
    let _attacker_contract = LockupContract::new(
        non_owner(),                     // attacker sets themselves as owner
        0.into(),
        None,
        TransfersInformation::TransfersEnabled {
            transfers_timestamp: to_ts(0).into(),
        },
        None,
        None,
        AccountId::from("whitelist"),
        None,
    );
    // Currently this SUCCEEDS (no panic), proving the missing guard;
    // after the fix, it must panic with "already initialized".
}
```
Before the fix: this test does not panic, `_attacker_contract.owner_account_id == non_owner()`, demonstrating full state overwrite despite prior initialization — violating the binding `state_exists() == false` before persisting new state. After adding the recommended guard, the test panics as expected.

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
