### Title
Donated `token` balance is counted in `getContractValue()` and crystallized as NAV gain, enabling phantom-fee theft and forced loss/default via `_skimDonatedAssets` - ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary
The external report's bug class — trusting `token.balanceOf()` in accounting — maps directly onto `IdleCDOCreditVault.getContractValue()`, which adds the raw underlying balance (`_contractTokenBalance(token)`) to NAV. Unsolicited transfers are only removed by `_skimDonatedAssets()` inside `startEpoch`, `stopEpochWithDuration`, `finalizeDefault` and guardian `updateAccounting`, but **not** inside `_deposit`/`_updateAccounting`. An unprivileged direct token sender can therefore inject a donation that gets crystallized as a real gain (fees accrued on it, prices inflated), is later skimmed to `feeReceiver`, and is then booked as a real loss borne BB-first — potentially triggering `Default`/`_emergencyShutdown`.

### Finding Description
`getContractValue()` returns `strategyToken balance + token balance - unclaimedFees` (`IdleCDOCreditVault.sol:125-128`). `_deposit` calls `_updateAccounting()` *before* transferring the depositor's funds and never skims, so any dust/donation sitting in the contract is treated as performance:

- `nav > _lastNAV` → `unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC` (`IdleCDOCreditVault.sol:230-231`) — phantom performance fees are accrued on donated tokens.
- `_virtualPriceAux` distributes the fake gain into `lastNAVAA`/`lastNAVBB` and `priceAA`/`priceBB`.
- The donation is *not* pushed to the strategy: `IIdleCDOStrategy(strategy).deposit(_amount)` only forwards `_amount` (`IdleCDOCreditVault.sol:211`). The donated tokens stay raw on the CDO.
- At the next `startEpoch`/`stopEpoch`, `_skimDonatedAssets()` sweeps the entire raw `token` balance to `feeReceiver` (`IdleCDOEpochVariant.sol:794-796`, `:242`, `:355`), so `getContractValue()` drops by the donation amount `D`.
- The following `_updateAccounting` computes `totalGain = -D`, applied BB-first via `_virtualPriceAux` (`IdleCDOCreditVault.sol:329-333`). If `D >= lastNAVBB` the vault reverts `Default()` or calls `_emergencyShutdown(true)` (`IdleCDOCreditVault.sol:240-245`).

### Impact Explanation
Two concrete losses, both triggered by an unprivileged "direct token sender" (explicitly in-scope):

1. **Phantom-fee theft**: `unclaimedFees` grows by `D * fee / FULL_ALLOC` and is later paid out of real strategy-token backing via `_transferFeeUnderlyings`, i.e. LPs fund fees on money that was never theirs.
2. **Socialized loss / forced shutdown**: the skim converts the phantom gain into a real `-D` loss absorbed by BB NAV first. With `D >= lastNAVBB` the next interaction reverts `Default` or enters `_emergencyShutdown`, crystallizing a fake loss on tranche prices and freezing normal deposits/withdrawals. Attacker cost is `D` (donated); LP loss is up to `D` plus the phantom fees — a griefing vector that scales with the attacker's budget, not with any privileged action.

### Likelihood Explanation
Requires only an ERC20 transfer to the CDO during the buffer phase plus one tiny `depositAA(1)` to crystallize the gain — no privileged role, no oracle dependence. The cost (`D`) must exceed `lastNAVBB` for the shutdown variant, but the phantom-fee skim works at any `D`. The existence of `_skimDonatedAssets` shows donations were considered, but the accounting path still consumes `balanceOf` before the skim runs, so the guard is incomplete rather than a fix.

### Recommendation
Mirror the "managed NAV" approach used by `virtualPrice`/`_managedContractValue()` inside `getContractValue()` itself (exclude raw `token` balance), or call `_skimDonatedAssets()` at the top of `_updateAccounting`/`_deposit` before NAV is read. Alternatively track deposited principal internally instead of deriving NAV from `balanceOf`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.17;

// Fork test against a live IdleCDOEpochVariant vault during buffer phase.
function test_DonationPhantomFeeAndForcedLoss() public {
    // vault: running IdleCDOCreditVault/IdleCDOEpochVariant, token = underlying (e.g. USDC)
    uint256 bbNavBefore = vault.lastNAVBB();

    // 1. Attacker (any EOA) directly transfers D underlying to the CDO
    uint256 D = bbNavBefore + 1; // for shutdown variant; any D>0 for fee theft
    deal(address(token), attacker, D);
    vm.prank(attacker);
    token.transfer(address(vault), D);

    // 2. Attacker crystallizes the phantom gain with a dust deposit
    deal(address(token), attacker, 1);
    vm.startPrank(attacker);
    token.approve(address(vault), 1);
    vault.depositAA(1); // _updateAccounting counts D: unclaimedFees += D*fee/FULL_ALLOC
    vm.stopPrank();

    uint256 phantomFees = vault.unclaimedFees();
    assertGt(phantomFees, 0); // fees accrued on donated funds

    // 3. Honest manager starts epoch -> _skimDonatedAssets sends D to feeReceiver
    vm.prank(manager);
    vault.startEpoch();

    // 4. Epoch ends; stopEpoch (or any accounting) now books -D loss, BB-first.
    vm.warp(vault.epochEndDate() + 1);
    vm.prank(manager);
    vault.stopEpoch(0, 0); // reverts Default() or triggers _emergencyShutdown
    // BB NAV wiped by phantom loss; remaining LPs' claims reduced by D,
    // feeReceiver holds D + phantomFees paid from real backing.
}
```
Note: I verified the skim call sites and accounting flow in `IdleCDOCreditVault.sol`/`IdleCDOEpochVariant.sol`; I did not exhaustively check `IdleCDOEpochVariantPrefunded`/other subclasses for an overriding `_deposit` that skims first — if one exists, the finding scope narrows to the base credit-vault variant.
