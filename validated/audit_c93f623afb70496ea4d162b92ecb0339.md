### Title
Already-claimed instant-withdraw receipts stay counted in `instantWithdrawClaimsByEpoch`, inflating the default-recovery reserve and basis — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The external bug (CVE-2020-26959) is a use-after-free: a reference is decremented on an object that was already freed. The analog in `IdleCreditVault` is stale per-epoch receipt accounting: when a user claims a funded instant withdrawal, `claimInstantWithdrawRequest` zeroes `instantWithdrawsRequests[_user]` but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]`. The "freed" receipt keeps being referenced by default-finalization accounting (`defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`), which treats already-paid-out underlyings as reserve still held by the strategy. The result is an overstated `defaultRecoveryReserve` and inflated `defaultRecoveryPrice`, causing theft of other claimants' funded receipts and permanent freezing of later recovery claims.

### Finding Description
In `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393), a funded instant claim pays out `instantWithdrawsRequests[_user]` and zeroes it, but leaves two aggregates untouched:

- `instantWithdrawsRequestsByEpoch[_user][epoch]` (set in `requestInstantWithdraw`, line 371)
- `instantWithdrawClaimsByEpoch[epoch]` (line 372)

These stale entries are only consumed in the default path. At finalization:

- `defaultPendingClaimBasis` (line 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0`, so basis includes receipts that were already paid in full.
- `_defaultPrefundedInstantReserve` (line 716-723) computes `prefundedReserve = instantBasis - pendingInstant`, i.e. it assumes every instant receipt not in the still-unfunded `pendingInstantWithdraws` bucket is cash sitting in the strategy. But `_transferFundedClaim` already sent those underlyings to claimants. `finalizeDefaultRecovery` (line 686) then folds this phantom amount into `defaultRecoveryReserve` and computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688).

Additionally, the stale per-user entry makes `_claimDefaultedInstantWithdrawRequest` (line 842-856) compute `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, which includes the already-claimed amount. If the same user re-requested in the same epoch, `instantWithdrawsRequests[_user] -= claimBasis` underflows on the old portion, permanently reverting their claim path; if they did not, `_burn(_user, claimBasis)` exceeds their minted receipt and reverts too.

Concrete sequence (instant mode, epoch N):

1. Attacker calls `requestInstantWithdraw(A)` — `instantWithdrawClaimsByEpoch[N] += A`, `pendingInstantWithdraws += A`.
2. CDO funds it via `collectInstantWithdrawFunds(A)` — `pendingInstantWithdraws -= A`; underlying now sits in the strategy.
3. Attacker calls `claimInstantWithdrawRequest` — receives `A` underlyings. `instantWithdrawsRequestsByEpoch[attacker][N]` stays `A`; `instantWithdrawClaimsByEpoch[N]` still includes `A`.
4. Another user requests instant withdraw `B` in the same epoch, still unfunded (`pendingInstantWithdraws = B`, `instantWithdrawClaimsByEpoch[N] = A + B`).
5. Borrower defaults at end of epoch N; `finalizeDefaultRecovery` runs:
   - `pendingBasis += instantWithdrawClaimsByEpoch[N] = A + B` (A double-counted)
   - `prefundedReserve = (A + B) - B = A` — but `A` was already transferred to the attacker; the strategy does not hold it.
6. `defaultRecoveryReserve = recovered + A + ...` is recorded, and `recoveryPrice` is computed against a reserve that does not exist.

### Impact Explanation
The phantom `A` is counted both as extra claim basis and as extra reserve. Because `defaultRecoveryReserve` is just a counter decremented by `_transferDefaultRecovery` (line 915), early claimants are paid `claimBasis * recoveryPrice / RECOVERY_FULL` from the strategy's real balance — which includes underlyings held for other users' funded normal/instant receipts and legitimate recovery funds. Legitimate recovery claimants and holders of funded receipts (e.g. `_claimFundedWithdrawRequest` paying via `_transferFundedClaim`) are left with an empty contract: their claims revert permanently. Quantified loss equals the total value of instant-withdraw receipts claimed during the defaulted epoch — bounded by epoch volume but a direct, attacker-influenced inflation of recovery payouts. The attacker profits by being an early recovery claimant (or by simply having extracted `A` pre-default while `A` still dilutes/drains the pool).

### Likelihood Explanation
Requires a borrower default in the same epoch in which at least one instant withdrawal was both funded and claimed, plus one still-pending instant request so `pendingInstantWithdraws != 0` at finalization (otherwise `defaultInstantWithdrawsFinalized` stays false and the stale entries are never consulted). Instant withdrawals are an intended user-facing flow and defaults are a designed-for state; no privileged misbehavior is needed — the attacker is an ordinary KYC'd instant-withdraw requester. The stale accounting is unconditional: no guard reconciles `instantWithdrawClaimsByEpoch` at claim time.

### Recommendation
When an instant claim is paid in `claimInstantWithdrawRequest`, clear the per-epoch aggregates the same way `_claimDefaultedInstantWithdrawRequest` does: for the request's epoch (tracked per user), set `instantWithdrawsRequestsByEpoch[_user][epoch] = 0` and decrease `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, so already-paid receipts are never counted again in `defaultPendingClaimBasis` or `_defaultPrefundedInstantReserve`. This requires recording the epoch of open instant requests per user (the aggregate-only `instantWithdrawsRequests` currently loses that information once multiple epochs are involved; a per-user epoch pointer like `lastWithdrawRequest` or a small list suffices since instant receipts are only outstanding within their request epoch).

### Proof of Concept
Foundry fork test (modeled on `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `testClaimInstantWithdrawRequest` in `IdleCDOEpochQueue.t.sol`):

```solidity
function testStaleInstantClaimInflatesDefaultRecovery() public {
    // --- setup: deposits so the vault has funds; instant withdraws enabled ---
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");
    _depositWithUser(attacker, amount, true);
    _depositWithUser(victim,   amount, true);
    _startEpochAndCheckPrices(0);

    uint256 epochN = IdleCreditVault(address(strategy)).epochNumber();

    // 1) attacker requests instant withdraw A in epoch N
    uint256 A = IERC20(AAtranche).balanceOf(attacker) / 2;
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(A, address(AAtranche));

    // 2) borrower/CDO funds it and the delay passes; attacker claims A in full
    skip(instantDelay + 1); // whatever helper the suite uses for the instant delay
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest(); // paid A underlyings
    // stale: instantWithdrawsRequestsByEpoch[attacker][N] == A
    // stale: instantWithdrawClaimsByEpoch[N] still contains A
    assertEq(
        IdleCreditVault(address(strategy)).instantWithdrawsRequestsByEpoch(attacker, epochN),
        A,
        "freed receipt still referenced"
    );

    // 3) victim requests instant withdraw B in same epoch, left unfunded
    uint256 B = IERC20(AAtranche).balanceOf(victim);
    vm.prank(victim);
    cdoEpoch.requestInstantWithdraw(B, address(AAtranche));

    // 4) borrower defaults at end of epoch N
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, 0);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0); // triggers default

    // 5) finalize recovery: basis includes A+B, prefunded reserve counts A twice-free
    uint256 recovered = cdoEpoch.getContractValue() * 7e17 / ONE_TRANCHE;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // 6) phantom reserve A was booked: real balance < defaultRecoveryReserve
    uint256 reserve = IdleCreditVault(address(strategy)).defaultRecoveryReserve();
    uint256 realBal = IERC20Detailed(defaultUnderlying).balanceOf(address(strategy));
    assertGt(reserve, realBal, "recovery reserve exceeds real holdings by claimed amount A");

    // attacker, claiming early via a fresh defaulted-epoch receipt path, drains
    // underlyings that belong to victim's funded receipts / recovery share;
    // the victim's later _transferDefaultRecovery / _transferFundedClaim reverts
    // once the balance is exhausted -> permanent freezing of remaining claims.
}
```

Note: exact helper names (`instantDelay`, `requestInstantWithdraw` signature on `IdleCDOEpochVariant`) should be matched to the suite; the assertions on `instantWithdrawsRequestsByEpoch` residual value and `defaultRecoveryReserve > balanceOf(strategy)` are the core invariants demonstrating the stale-reference double count.
