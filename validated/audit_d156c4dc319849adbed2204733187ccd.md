Confirmed: `AccountLoader::do_load` explicitly treats zero-lamport accounts as `None` (non-existent) via `self.loaded_accounts` cache lookup, and `load_program_with_pubkey` relies on this same account-loading path. Given the confirmed mechanics, I can now assess the analog claim.

### Title
Panic-inducing account-existence race in cooperative program-cache loading can hang concurrent transaction batches - (File: svm/src/transaction_processor.rs)

### Summary
`TransactionBatchProcessor::replenish_program_cache` calls `load_program_with_pubkey(...).expect("called load_program_with_pubkey() with nonexistent account")` [1](#0-0)  after a program key has already been reserved as a `cooperative_loading_task` in the shared `loading_entries` map by `ProgramCache::extract` [2](#0-1) . The `.expect()` is a hard panic path, and the existing test suite documents it fires whenever the account has become non-existent (zero-lamport / absent) by the time of the actual load [3](#0-2) .

### Finding Description
This mirrors the Sherlock report's bug class ("a rogue/mutating dependency can permanently block a shared critical-path operation that other participants rely on") but manifests differently here: instead of a `require()` gating removal on an untrusted callback, Agave has a shared, mutex-protected "loading in progress" registry (`loading_entries: Mutex<HashMap<Pubkey, (Slot, ThreadId)>>`) that other concurrent transaction-processing threads consult and wait on via `LoadingTaskWaiter` [4](#0-3) . A program key is marked "reserved for loading" by one thread in `extract()`, and only removed by that same thread calling `finish_cooperative_loading_task()` after a successful load [5](#0-4) . If the actual load between reservation and completion instead panics via the `.expect()` on `load_program_with_pubkey`, the entry is **never removed** from `loading_entries`, and `loading_task_waiter.notify()` is never called for that key. Any other thread that is concurrently processing a transaction batch requiring the same program will be stuck in the `else` branch calling `task_waiter.wait(task_cookie)` indefinitely for that program [6](#0-5) , since `extract()` will keep reporting the key as already "loading" via the `Entry::Vacant` check [2](#0-1) , and the mutex-guarded map entry is now permanently stale (and if the panic occurs while the `Mutex` guard is held, the mutex itself becomes poisoned, causing every subsequent `.lock().unwrap()` call in `extract()`/`finish_cooperative_loading_task()` across *all* programs to panic as well).

The underlying trigger the test explicitly exercises is `load_program_with_pubkey` returning `None` (mapped straight into the `.expect()` panic) when the program account is reported non-existent by the account loader at load time [7](#0-6) . Critically, `AccountLoader::do_load`/`load_account` treats any account whose cached lamports are `0` as `None` ("Not allocated"/non-existent), even though it was `Some` (existent, executable) moments earlier when `filter_executable_program_accounts`/`extract()` decided the program needed (re)loading [8](#0-7) . This creates a TOCTOU-style race: a legitimate, ordinary transaction (e.g. closing a Loader-v3/v4 program account, or any account manipulation that zeroes its lamports) executing concurrently in a sibling batch/thread between the "decide to load" step and the "actually load" step can flip the account to zero-lamports and trigger the panic in a *different* thread's `replenish_program_cache` call for that same program id.

### Impact Explanation
A panic inside `replenish_program_cache` while holding (or having just released) the `loading_entries` mutex is a validator-thread-level DoS: it can crash the executing thread/pool worker, poison the shared mutex for all future program-cache loads, and leave sibling threads deadlocked waiting on a `LoadingTaskWaiter` cookie that will never be signaled for the affected program key. Because `global_program_cache` is validator-global and shared across all transaction-processing threads, this can escalate from "one bad transaction" to "loss of liveness for an entire class of program loads," which is a legitimate ingest/processing-starvation concern reachable purely by ordinary users deploying/closing programs and submitting normal transactions — no privileged or node-level access required.

### Likelihood Explanation
This requires a specific interleaving: two transaction batches processed concurrently by different threads, where one references a program whose backing account is closed/zeroed by another transaction exactly between that program's cooperative-loading reservation and its actual load. The window is narrow but real given the documented "multiple transaction processor threads running concurrently" design comment [9](#0-8) , and the codebase itself already has a dedicated regression test proving the `.expect()` panics under exactly this "nonexistent account" condition [3](#0-2) . I could not fully verify from the index whether higher-level scheduling (e.g., write-lock/account-conflict scheduling that serializes writers of the same account across batches) prevents this race in practice for the exact "program account, closed concurrently with another batch's load" case — this would require deeper tracing through the banking-stage/scheduler code, which is outside what the index surfaced.

### Recommendation
Replace the `.expect("called load_program_with_pubkey() with nonexistent account")` panic in `replenish_program_cache` (and the analogous one in `prepare_one_program_for_upcoming_feature_set`) with graceful handling that still calls `finish_cooperative_loading_task` (inserting a `Closed`/tombstone entry and notifying waiters) so that `loading_entries` is always cleared and other threads are unblocked, regardless of whether the account is found to be missing at load time.

### Proof of Concept
Not independently reproduced in this analysis; existing unit test `test_replenish_program_cache_with_nonexistent_accounts` [3](#0-2)  already demonstrates the panic trigger in isolation (single-threaded, pre-seeded missing account). Demonstrating the full concurrent-thread livelock/poisoned-mutex consequence would require a multi-threaded SVM integration test that (1) starts loading program P in thread A (reserving it in `loading_entries`), (2) concurrently commits a transaction in thread B that zeroes P's backing account's lamports before thread A's `load_program_with_pubkey` call resolves, and (3) observes thread A panic and thread B (or any other thread awaiting P) hang on `LoadingTaskWaiter::wait`.

/// Suspends the thread in case no cooprative loading task was assigned
#[derive(Debug, Default)]
pub struct LoadingTaskWaiter {
    cookie: Mutex<LoadingTaskCookie>,
    cond: Condvar,
}

impl LoadingTaskWaiter {
    pub fn new() -> Self {
        Self {
            cookie: Mutex::new(LoadingTaskCookie::new()),
            cond: Condvar::new(),
        }
    }

    pub fn cookie(&self) -> LoadingTaskCookie {
        *self.cookie.lock().unwrap()
    }

    pub fn notify(&self) {
        let mut cookie = self.cookie.lock().unwrap();
        cookie.update();
        self.cond.notify_all();
    }

    pub fn wait(&self, cookie: LoadingTaskCookie) -> LoadingTaskCookie {
        let cookie_guard = self.cookie.lock().unwrap();
        *self
            .cond
            .wait_while(cookie_guard, |current_cookie| *current_cookie == cookie)
            .unwrap()
    }
}
