The `Authorize` function performs a check-then-act sequence that is not atomic: `isReplay` takes an `RLock`, releases it, and only later `recordUsage` takes a separate `Lock`. Between those two steps there is no mutual exclusion tying them together, so two concurrent calls to `Authorize` with the same `claims.ID` (jti) can both observe `isReplay == false` before either calls `recordUsage`.

### Title
JWT replay-cache TOCTOU allows single-use trigger JWT to authorize workflow execution twice - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks `h.jwtCache.isReplay(claims.ID)` and later calls `h.jwtCache.recordUsage(claims.ID)`, but these are two independent lock-protected operations rather than one atomic check-and-set. Two concurrent `HandleUserTriggerRequest` calls carrying the identical JWT can both pass the replay check before either records usage, allowing the same single-use JWT to authorize the workflow trigger twice.

### Finding Description
`Authorize` is reached from `httpTriggerHandler.authorizeRequest` → `HandleUserTriggerRequest`, which is the gateway's entry point for user-submitted HTTP trigger requests carrying a bearer JWT (`req.Auth`) [1](#0-0) . Inside `Authorize`, the JWT is verified, then the replay check and the authorized-key check and usage-recording happen in sequence with no combined lock spanning the whole operation [2](#0-1) . The cache primitives themselves take separate, independent locks: `isReplay` acquires and releases an `RLock` purely to check map membership, and `recordUsage` acquires and releases a `Lock` purely to insert into the map [3](#0-2) . There is no atomic "check-and-insert" operation (e.g., a single critical section, or a `sync.Map.LoadOrStore`-style call) guarding the whole check-then-record sequence. If two goroutines call `Authorize` concurrently with the same `claims.ID`, both can execute `isReplay` before either executes `recordUsage`, so both see `exists == false` and both proceed to pass the authorization check and call `recordUsage` (the second call simply overwrites the same map entry harmlessly, but by then both requests have already been authorized).

### Impact Explanation
This breaks the intended isolation invariant that a single-use JWT authorizes exactly one workflow trigger execution. An attacker who captures/replays a single valid JWT (their own, or one intercepted/leaked for another party) can race two nearly-simultaneous `HandleUserTriggerRequest` calls to get the workflow triggered twice under one authorization, causing duplicate workflow executions and consuming another party's rate-limit/resource budget for two triggers using only one authorized JWT. This corresponds to an unauthorized/duplicated job execution and quota-bypass class of impact.

### Likelihood Explanation
Exploitation requires only possession of one valid, unexpired, unused JWT for the target workflow (the same credential level normally needed for a single legitimate trigger) and the ability to fire two nearly-simultaneous HTTP requests to the gateway — no elevated privileges, and it is trivially repeatable each time a fresh JWT is obtained. The race window is real but narrow (bounded by two independent lock acquisitions plus the authorized-key map lookup in between), so success is probabilistic rather than guaranteed on every attempt, though attackers can retry with fresh JWTs until the race lands.

### Recommendation
Merge `isReplay` and `recordUsage` into one atomic check-and-set operation performed under a single lock (or use `sync.Map.LoadOrStore` semantics) so that only one caller can ever transition a given `jti` from "unused" to "used," and reject all other concurrent callers with the same `jti` immediately.

### Proof of Concept
Add a Go test in `workflow_metadata_handler_test.go` that:
1. Constructs a `WorkflowMetadataHandler` with one workflow ID registered and one authorized signer key.
2. Generates a single valid JWT (fixed `jti`) signed by that authorized key, targeting that workflow's `jsonrpc.Request`.
3. Spawns two goroutines that both call `h.Authorize(workflowID, token, req)` concurrently with a `sync.WaitGroup`, collecting each result into a slice.
4. Asserts that exactly one call returns `(key, nil)` and the other returns the "JWT token has already been used" error — under the current implementation, run the test with `-race` and repeated iterations (e.g., `for i := 0; i < 1000; i++`) to demonstrate that occasionally both calls succeed, violating the single-use invariant.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
