### Title
Loss-adjusted withdraw receipts are keyed to the wrong epoch, so the haircut is never applied and pending receipts are paid at par on a first-come-first-served basis — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` records the pro-rata recovery price for haircutted pending withdraw receipts under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is incremented inside `deposit()` during the same `stopEpoch` flow (the `isEpochRunning()` branch). Users' receipts are indexed by the request epoch stored in `lastWithdrawRequest[_user]` / `withdrawsRequestsByEpoch[_user][reqEpoch]`, which is always the pre-increment epoch. The stored haircut is therefore never reachable: `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest]` at the old index, finds 0, and silently falls through to `_claimFundedWithdrawRequest`, which pays the full unhaircutted `withdrawsRequests[_user]` basis. This mirrors CVE-2016-6223's mis-indexed buffer read: an index shifted relative to where the data was written returns "no entry," and the missing-entry path produces a wrong payout instead of a revert.

### Finding Description
- At request time, `requestWithdraw` records the receipt under the current epoch: `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (`IdleCreditVault.sol:282-293`).
- `deposit()` increments `epochNumber` whenever it is called while the epoch is still flagged running — i.e., when the CDO pushes the borrower repayment into the strategy during `stopEpoch` (`IdleCreditVault.sol:607-614`).
- `collectWithdrawFunds` then stores the haircut under the already-incremented counter: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (`IdleCreditVault.sol:411-421`). All receipts created during the ending epoch carry the previous epoch index, so the entry at the new index can never be matched to a `lastWithdrawRequest`.
- On claim, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, gets 0, and returns early (`IdleCreditVault.sol:789-795`). `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` in full once `epochNumber > lastWithdrawRequest` (`IdleCreditVault.sol:326-349`), burning the full receipt and transferring the unhaircutted amount.
- The loss intended for pending receipts (`pendingLoss` computed in `previewLossAdjustedWithdrawFunds`, `IdleCreditVault.sol:457-459`) is thus never enforced: the strategy only holds `pendingBasis - pendingLoss` of funded underlying, while claimants draw `pendingBasis`. Early claimants are overpaid; once the funded balance is exhausted, later claimants' `safeTransfer` in `_transferFundedClaim` reverts, permanently freezing the remainder. The same off-by-one also defeats the `requestWithdraw` guard at `IdleCreditVault.sol:261-271`, which relies on the same lookup to force claiming a haircutted receipt before re-requesting.

### Impact Explanation
Direct theft and permanent freezing. With pending withdraw basis `P` and a realized epoch loss `L`, the borrower funds only `P - pendingLoss` (`previewLossAdjustedWithdrawFunds`). Because the recovery price is written at `epochNumber` after `deposit()` bumped it, every claimant redeems at par: the first claimants collectively extract `pendingLoss` more than was funded (paid out of strategy-held underlying that economically belongs to active tranche holders' funded claims), and the tail claimants' transfers revert with insufficient balance — their receipts can never be claimed. Quantified: user-level loss up to `pendingLoss = L * pendingWithdraws / (activeBasis + pendingWithdraws)`, and active LPs absorb up to the full loss instead of their `activeLoss` share, breaking the loss-waterfall invariant.

### Likelihood Explanation
Requires only ordinary unprivileged flows: users request withdraws during an epoch (`requestWithdraw`), and the honest manager calls `stopEpochWithDuration(_lossAmount)` with a partial repayment such that `_amount < pendingWithdraws` in `collectWithdrawFunds`. No privileged attacker, no oracle manipulation, no default needed — any epoch ending with both pending receipts and a realized loss below the total basis triggers it, and `previewLossAdjustedWithdrawFunds` explicitly supports this mode (`_lossAmount > 0`, `pendingBasis > 0`, `defaultRecoveryInitialized`). The mis-indexing is deterministic: `deposit()` runs while `isEpochRunning()` is still true inside the same stop sequence, so the write index is always request-epoch + 1. Note: I could not fully re-verify the exact call ordering inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` within this session; the bug exists if `collectWithdrawFunds` executes after the funding `deposit()` (the natural ordering, since funds must arrive before they are collected). If the integration intentionally collects before the bump, the finding does not apply and should be closed.

### Recommendation
Store the recovery price under the epoch the pending receipts belong to. Either (a) in `collectWithdrawFunds`, write `lossRecoveryPriceByEpoch[epochNumber - 1]` when the bump already occurred, or more robustly (b) have `IdleCDOEpochVariant` pass the request epoch explicitly, or (c) record a dedicated `pendingReceiptsEpoch`/`currentRequestEpoch` at the time receipts are opened and key `lossRecoveryPriceByEpoch` on that value rather than on the mutable global counter. Add a regression test: request withdraws in epoch N, call `stopEpochWithDuration` with `0 < loss < totalBasis`, then claim — the payout must equal `basis * lossRecoveryPrice / 1e18`.

### Proof of Concept
Foundry fork scenario (against `IdleCDOEpochVariant` + `IdleCreditVault` on mainnet USDC fork, mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// 1. Setup: KYC'd user deposits AA during buffer, manager calls startEpoch.
uint256 dep = 100_000e6;
_depositWithUser(attacker, dep, true);          // AA tranche
_startEpochAndCheckPrices(0);                   // epoch 0 running

// 2. Attacker (and a second user victim) request withdraws during epoch 0.
cdoEpoch.requestWithdraw(0, address(AAtranche)); // attacker
cdoEpoch.requestWithdraw(0, address(AAtranche)); // victim
// strategy.lastWithdrawRequest(attacker) == strategy.lastWithdrawRequest(victim) == 0
// strategy.withdrawsRequestsByEpoch(u)[0] > 0

// 3. Honest manager ends the epoch with a realized partial loss.
deal(defaultUnderlying, borrower, expectedFundsEndEpoch - LOSS);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(0, LOSS);        // funds < pendingWithdraws

// Inside stopEpoch: strategy.deposit() bumps epochNumber 0 -> 1 (isEpochRunning branch),
// then strategy.collectWithdrawFunds(funded < pendingBasis) stores
// lossRecoveryPriceByEpoch[1] = funded * 1e18 / pendingBasis.

// 4. Attacker claims. _claimLossAdjustedWithdrawRequest reads
// lossRecoveryPriceByEpoch[lastWithdrawRequest == 0] == 0 and returns 0.
// _claimFundedWithdrawRequest passes since epochNumber(1) > lastWithdrawRequest(0)
// and pays the FULL unhaircutted basis.
uint256 balBefore = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(attacker) - balBefore;

// Attacker received basis instead of basis * lossRecoveryPrice / 1e18.
assertGt(paid, basis * strategy.lossRecoveryPriceByEpoch(1) / 1e18);

// 5. Victim's claim reverts: funded underlying already drained by the par payout.
vm.prank(victim);
vm.expectRevert(); // ERC20 transfer of insufficient balance
cdoEpoch.claimWithdrawRequest();
```
