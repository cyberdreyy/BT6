### Title
Funded instant-withdraw claims do not clear `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, inflating the default recovery basis and reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The reported bug class — value deducted from an escrow/balance while the internal accounting of that balance is not decremented — has a direct analog in `IdleCreditVault.claimInstantWithdrawRequest`. The funded claim path zeroes the aggregate `instantWithdrawsRequests[_user]` and pays out underlying, but never clears the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. Those per-epoch counters are exactly what `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` use to compute the recovery basis and the already-held reserve at default finalization. Already-paid-out claims are therefore counted as still-owed basis and as still-held reserve collateral, corrupting `defaultRecoveryPrice` and leaving the recovery reserve under-collateralized.

### Finding Description
In `claimInstantWithdrawRequest`, after the (correct) defaulted-receipt branch, the funded path executes: [1](#0-0) 

It burns the user's receipt tokens, sets `instantWithdrawsRequests[_user] = 0`, and transfers `_amount` underlyings via `_transferFundedClaim`. Unlike `_claimDefaultedInstantWithdrawRequest` — which correctly clears `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrements `instantWithdrawClaimsByEpoch[epoch]` (lines 847-853) — the funded path leaves both untouched: [2](#0-1) 

At default finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the haircut basis whenever `pendingInstantWithdraws != 0`: [3](#0-2) 

and `_defaultPrefundedInstantReserve()` treats `instantBasis - pendingInstant` as underlying already held by the strategy to back those claims: [4](#0-3) 

A funded claim that was already paid out (G) thus remains in `instantBasis`: it is double-counted as claimable basis and simultaneously treated as reserve collateral even though those tokens left the contract. In `finalizeDefaultRecovery`, `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed with both `reserveAmount` and `totalBasis` inflated by the same ghost amount G: [5](#0-4) 

Since actual recovery is below par (R < B), adding G to numerator and denominator pushes `defaultRecoveryPrice` toward `RECOVERY_FULL`, i.e., above the economically correct haircut price.

### Impact Explanation
Broken invariant: one receipt one payout / solvency of the isolated recovery reserve. Every defaulted or post-default claim consumes `defaultRecoveryReserve` at the inflated `defaultRecoveryPrice` via `_transferDefaultRecovery` (lines 912-917). Early claimants — including the attacker who caused the ghost basis by claiming their funded instant receipt — are overpaid relative to the fair haircut. The reserve is therefore exhausted before all claims are paid: the last claimants' `defaultRecoveryReserve -= _amount` either underflows (revert) or the transfer fails on insufficient balance. The result is theft of unclaimed recovery funds by earlier claimants and permanent freezing of the remaining claimants' recovery, quantified by the inflation: `Δprice ≈ G·(B − R)·RECOVERY_FULL / (B·(B+G))` applied over the entire `totalBasis`, i.e., up to the full ghost amount G being redistributed to earlier claimers.

### Likelihood Explanation
Requires: (1) instant withdrawals enabled (`allowInstantWithdraw`, set when `instantWithdrawDelay` elapsed or the borrower repays all funds in close-pool mode), (2) an unprivileged user requesting and successfully claiming a funded instant withdrawal within an epoch, (3) another instant receipt in the same epoch remaining unfunded (`pendingInstantWithdraws != 0` — happens whenever startEpoch liquidity covered only part of the instant queue, a documented scenario in the `defaultPendingClaimBasis` comments), and (4) a subsequent borrower default in that epoch finalized via `finalizeDefault`. None of the existing guards stop it: `_transferFundedClaim`'s balance-vs-reserve check only protects a non-zero `defaultRecoveryReserve` that does not yet exist at claim time; the epoch gating in `claimWithdrawRequest` does not apply to instant claims; and no privileged role is involved — the attacker is an ordinary tranche-token holder whose only action is a legitimate `claimInstantWithdrawRequest` plus an early defaulted-epoch claim. The accounting gap is deterministic once the sequence occurs.

### Recommendation
Mirror the per-epoch cleanup done in `_claimDefaultedInstantWithdrawRequest` in the funded path of `claimInstantWithdrawRequest`: for each epoch entry being paid, zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount (clamping at zero for safety), so that `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` only ever observe still-unpaid instant claims. Equivalently, iterate and clear the user's per-epoch instant entries before `_transferFundedClaim` pays out.

### Proof of Concept
Reproducible Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
function testFundedInstantClaimGhostBasis() external {
    // 1. Configure instant withdraws: setInstantWithdrawParams(delay, delta, enabled).
    // 2. userA (attacker) and userB deposit AA; APR is lowered so
    //    requestWithdraw takes the requestInstantWithdraw path for both.
    // 3. Fund only userA's instant receipt via startEpoch/collectInstantWithdrawFunds
    //    so pendingInstantWithdraws still holds userB's amount.
    // 4. userA calls claimInstantWithdrawRequest -> paid in full, but
    //    instantWithdrawClaimsByEpoch[epoch] still includes userA's amount G.
    assertEq(vault.instantWithdrawClaimsByEpoch(epoch), G + userBReceipt); // ghost
    // 5. Borrower repays only partial interest -> stopEpoch default path,
    //    manager calls finalizeDefault(recovered, manager).
    // 6. Observe: defaultPendingClaimBasis() and the computed
    //    defaultRecoveryReserve both include ghost G.
    uint256 price = vault.defaultRecoveryPrice();
    // price > R * RECOVERY_FULL / B  (correct price without ghost)
    // 7. Attacker/userB claim: sum of payouts = totalBasis * price / RECOVERY_FULL
    //    > reserveAmount. Last claimant's _transferDefaultRecovery underflows/reverts
    //    while earlier claimants were overpaid vs the fair haircut.
}
```

The key assertion is step 4: after a fully paid funded claim, `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are non-zero even though the corresponding underlyings have left the strategy — the exact "deducted from escrow but not subtracted from internal balance" discrepancy from the external report.
