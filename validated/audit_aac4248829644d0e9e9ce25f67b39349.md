### Title
Stale-epoch instant-withdraw receipts escape the default haircut and are paid at par from the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The bug class in the advisory — path/key lookups that reach state the guard was supposed to block — maps directly to `IdleCreditVault`'s epoch-keyed receipt accounting. Instant-withdraw receipts are recorded per request epoch in `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (`IdleCreditVault.sol:371`), but default finalization only counts the *current* epoch's instant basis via `instantWithdrawClaimsByEpoch[epochNumber]` (`defaultPendingClaimBasis`, line 644-649), and `_claimDefaultedInstantWithdrawRequest` only clears the `defaultRecoveryEpoch` key (line 842-856). Any instant receipt still pending from an *earlier* epoch is invisible to both, yet `claimInstantWithdrawRequest` then pays the full `instantWithdrawsRequests[_user]` aggregate at par through `_transferFundedClaim` (line 387-392) — out of the same underlying balance that backs `defaultRecoveryReserve`.

### Finding Description
- Attacker (a KYC-passed lender) calls `requestInstantWithdraw` during epoch N. The CDO fails to collect the full instant amount (borrower shortfall), so `pendingInstantWithdraws` remains non-zero and the receipt stays keyed under epoch N in `instantWithdrawsRequestsByEpoch`.
- `stopEpoch` runs, `epochNumber` increments to N+1, and the pool is declared `defaulted`.
- `finalizeDefaultRecovery` computes `basis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — i.e., only epoch N+1 instant claims. The attacker's epoch-N receipt contributes to `pendingInstantWithdraws != 0` (setting `defaultInstantWithdrawsFinalized = true`, line 696) but its basis is *not* included in `instantWithdrawClaimsByEpoch[N+1]`, so the recovery price is computed for a smaller basis.
- After finalization, the attacker calls `claimInstantWithdrawRequest`. `_claimDefaultedInstantWithdrawRequest` looks up `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` = `...[N+1]` = 0, clears nothing, and the function then burns the full `instantWithdrawsRequests[_user]` and pays it 1:1 from `_transferFundedClaim` — funded by strategy-held underlying that includes `defaultRecoveryReserve`.

The intended distinction "defaulted-epoch receipts get the haircut; older funded receipts get par" relies on the epoch key uniquely identifying funding status, but an unfunded receipt can carry a stale epoch key, exactly like a prototype-polluting path that bypasses the guard's intended key set.

### Impact Explanation
The stale-epoch receipt is paid at 100% while every other defaulted claimant (active AA/BB holders via the burned/minted CDO balance, normal withdraw receipts via `_claimDefaultedWithdrawRequest`, same-epoch instant receipts) is paid `defaultRecoveryPrice < 1`. The payout draws on `defaultRecoveryReserve`, so subsequent legitimate claims underflow/insolvent the reserve: direct theft of other users' recovery funds, up to the full stale-receipt amount, in the defaulted/finalized phase.

### Likelihood Explanation
Requires an instant-withdraw request to remain unfunded through a `stopEpoch` — precisely what happens when the epoch ends in borrower default (the scenario `defaultInstantWithdrawsFinalized` exists to cover). No privileged misbehavior needed; the attacker only needs one instant request in the epoch preceding the default epoch. The gap exists because receipt funding status is inferred from the epoch key rather than tracked explicitly.

### Recommendation
In `finalizeDefaultRecovery`/`defaultPendingClaimBasis`, include all outstanding instant receipt basis in the recovery basis (e.g., track a global `totalInstantClaimsBasis` rather than `instantWithdrawClaimsByEpoch[epochNumber]` only). Alternatively, in `claimInstantWithdrawRequest`, pay the par portion only for receipts verifiably funded before default — e.g., cap the par payment at the funded remainder (`instantWithdrawsRequests[_user]` minus unfunded basis) and route the unfunded remainder through `defaultRecoveryPrice` regardless of which epoch key it was recorded under.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// epoch N: user deposits AA, enables instant withdrawals, requests instant withdraw
cdoEpoch.setInstantWithdrawParams(delay, minAprDiff, true); // manager
uint256 tr = _depositWithUser(attacker, 100e6);
cdoEpoch.requestInstantWithdraw(tr, address(AAtranche));    // attacker
assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epochN), amt);

// do NOT fund the instant request; borrower defaults at stopEpoch
deal(underlying, borrower, 0);
vm.warp(cdoEpoch.epochEndDate() + 1);
cdoEpoch.stopEpoch(0, 0);                                    // owner -> defaulted
uint256 epochN1 = strategy.epochNumber();                    // epochNumber incremented

// finalize recovery with partial recovery funds
uint256 recovered = strategy.balanceOf(address(cdoEpoch)) + activeInterest;
deal(underlying, manager, recovered);
underlying.approve(address(strategy), recovered);
cdoEpoch.finalizeDefault(recovered, manager);

// attacker receipt is keyed under epochN, not defaultRecoveryEpoch (epochN1)
// -> skipped by _claimDefaultedInstantWithdrawRequest, paid at par instead
uint256 balPre = underlying.balanceOf(attacker);
cdoEpoch.claimInstantWithdrawRequest();                      // via CDO as attacker
assertEq(underlying.balanceOf(attacker) - balPre, amt);      // full amount, not haircutted
// meanwhile strategy.defaultRecoveryReserve() is drained for other claimants
```

The assertion that the attacker received `amt` at par (rather than `amt * defaultRecoveryPrice / 1e18`) demonstrates the reserve drain.
