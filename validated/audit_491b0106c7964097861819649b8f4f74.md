### Title
`DeployWithMaxDataLen` program deployment can be frontrun by pre-funding the deterministic ProgramData PDA, causing deployment DoS - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `UpgradeableLoaderInstruction::DeployWithMaxDataLen` handler in the `bpf_loader_upgradeable` builtin program derives the `ProgramData` account address deterministically via `Pubkey::find_program_address(&[new_program_id.as_ref()], program_id)` and then performs a CPI to the System Program's `create_account` to create that account [1](#0-0) . Because the target program's pubkey is known ahead of time (it must be pre-generated/signed for deployment), the resulting ProgramData PDA is fully predictable by any observer before the deploy transaction lands, exactly mirroring the `initializeMarket` frontrunning scenario where a deterministic identifier can be raced by an outside party.

### Finding Description
The System Program's `create_account` instruction processor rejects account creation if the destination account already holds any lamports, returning `SystemError::AccountAlreadyInUse` [2](#0-1) . In the deploy path, an attacker who knows the not-yet-deployed program's pubkey can compute the same PDA `programdata_key` off-chain and send it a trivial System Program transfer (even 1 lamport) before the legitimate `DeployWithMaxDataLen` transaction is included. When the loader later attempts `invoke_context.native_invoke_signed(instruction, ...)` to create that same account via CPI [3](#0-2) , the CPI will fail with `AccountAlreadyInUse`, and the whole `DeployWithMaxDataLen` instruction aborts. Unlike the Morpho case, there is no retry/try-catch fallback here — the loader errors out unconditionally rather than treating the already-funded account as an acceptable pre-existing state.

This directly matches the reported bug class: a first-mover/front-running attack on a deterministic account/identifier used for initialization, where the createAccount-style guard (“fail if already in use”) becomes an attacker-controlled DoS primitive rather than a safety check.

### Impact Explanation
An attacker can indefinitely block a specific program from ever completing its initial upgradeable deployment at a chosen program-id address, since the buffer (already drained of lamports for the failed create) and payer both incur wasted fees, and the deploy must be retried — but the attacker can repeat the griefing by re-funding the PDA with a fresh lamport transfer each time before the deploy transaction lands. This is a state-mutation-prevention / denial-of-service impact reachable purely from an ordinary user's System Program transfer transaction, requiring no privileges, no key compromise, and no consensus-level access.

### Likelihood Explanation
The precondition is only that the attacker knows the target program pubkey before the `DeployWithMaxDataLen` transaction confirms, which is normal in CLI deployment flows (the program keypair is generated and its pubkey is visible/predictable, and mempool-adjacent visibility of the pending deploy transaction further exposes it). The griefing transaction itself is a single cheap System Program transfer to a deterministically-derivable PDA, making the attack trivial and repeatable at negligible cost.

### Recommendation
Before invoking the CPI to create the `ProgramData` account, check whether the target address already has a positive lamport balance but empty/system-owned data (i.e., was pre-funded rather than legitimately created), and if so, use `Allocate`+`Assign`+`Transfer` (or an allow-prefund creation path, as already implemented elsewhere via `create_account_allow_prefund` [4](#0-3) ) instead of the strict `create_account` that fails on any positive balance. This mirrors the suggested mitigation of tolerating "already exists" style states instead of hard-failing.

### Proof of Concept
1. Attacker observes/derives the future `program_keypair.pubkey()` intended for deployment (e.g., from a pending `DeployWithMaxDataLen`-preparing transaction or a publicly announced program id).
2. Attacker computes `programdata_address = Pubkey::find_program_address(&[program_id.as_ref()], &bpf_loader_upgradeable::id())`, matching the derivation used in the loader [5](#0-4) .
3. Attacker submits an ordinary System Program transfer sending 1 lamport to `programdata_address` before the legitimate deploy transaction lands.
4. When `DeployWithMaxDataLen` executes, the CPI's `create_account` call sees `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse` [6](#0-5) , aborting the entire deploy instruction and leaving the target program unable to be deployed at that address.
