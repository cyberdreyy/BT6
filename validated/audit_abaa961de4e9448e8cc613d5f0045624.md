### Title
Cross-workflow response injection via unauthenticated MessageId matching in `HandleGatewayMessage` - ([File: core/capabilities/webapi/outgoing_connector_handler.go])

### Summary
`OutgoingConnectorHandler.HandleGatewayMessage` only looks up the pending response channel by `body.MessageId` via `c.responses.get(body.MessageId)` and, aside from a rate limit, does not verify that the signer/sender of the incoming message is the gateway/DON that the original `HandleSingleNodeRequest` call was addressed to [1](#0-0) . Any validly-signed `api.Message` (signed by any private key) whose `MessageId` collides with a currently-pending request's `messageID` will be delivered into that pending request's response channel [2](#0-1) .

### Finding Description
`handleSingleNodeRequest` creates a response channel keyed only by the caller-supplied `messageID` string via `c.responses.new(messageID)` [3](#0-2) , sends the signed request to a selected gateway, and then blocks reading from that channel [4](#0-3) .

When a message arrives back through the gateway connector's read loop, it is dispatched purely by JSON-RPC `Method` to the registered handler [5](#0-4) , and `HandleGatewayMessage` validates the message's *signature format* via `hc.ValidatedMessageFromReq` → `Message.Validate()` — this only checks field lengths and successfully extracts *a* valid ECDSA signer, storing it as `body.Sender` [6](#0-5) . Crucially, `Validate()` does **not** check that `Sender`/`Receiver`/`DonId` match anything related to the original outgoing request — any keypair can produce a validly-formed, validly-signed message.

Back in `HandleGatewayMessage`, the only binding to a specific pending call is `c.responses.get(body.MessageId)` [7](#0-6) . After a per-sender/global rate-limit check (which limits volume, not identity/authorization), the payload is unmarshalled and pushed directly into the channel for methods `MethodWebAPITarget`, `MethodComputeAction`, `MethodWorkflowSyncer` [8](#0-7) . There is no check that `body.Sender`, `body.DonId`, or `body.Receiver` correspond to the gateway/DON that `handleSingleNodeRequest` actually contacted, nor any correlation to the `selectedGateway` used for the outbound send (`gatewayID` argument to `HandleGatewayMessage` is not even compared against `selectedGateway`).

However, `messageID` values in this codebase are generated/supplied by callers (e.g., fetcher/compute-action/webAPI-target call sites) — the security of the design implicitly assumes `messageID` uniqueness is sufficient because it is treated as a shared secret/nonce known only to gateway participants relaying the original request back. The vulnerability described requires the attacker to *guess or collide* a `messageID` for a currently in-flight, unresolved request — `messageID` generation is not shown in this file, so whether IDs are cryptographically random (making collision infeasible) or predictable (e.g., sequential or derived from public data) determines actual exploitability. This file provides no evidence of messageID randomness/entropy, and no receiver/sender binding check exists in the reachable code path, which is the concrete root cause matching the audit question.

### Impact Explanation
If message IDs are guessable or the attacker can otherwise learn a pending, unresolved `messageID` for another workflow's request, they can inject an arbitrary attacker-signed `Response` payload into that workflow's fetch/computeAction/webAPITarget channel, since the delivered `*api.Message` is returned directly to the calling workflow as the "real" gateway response in `handleSingleNodeRequest`'s `select` block [9](#0-8) . This corresponds to cross-user/cross-workflow response spoofing — an attacker-controlled result being returned to another user's workflow execution, matching a "request impersonation / cross-user response confusion" impact class.

### Likelihood Explanation
Exploitability hinges entirely on `messageID` predictability/collision, which is not determined by this file. The audit question's precondition ("messageID collision with a real pending request") is non-trivial to satisfy in practice — the attacker would need to guess an in-flight, cryptographically-generated identifier during its live window (bounded by the request's `TimeoutMs`, default 20s). Without evidence in this file (or code shown) that `messageID` is short, sequential, or otherwise attacker-predictable, this is a **defense-in-depth gap** (missing sender/receiver binding) rather than a directly demonstrated, reproducible cross-workflow compromise. The rate limiter (`incomingRateLimiter.AllowVerbose(body.Sender)`) does not mitigate this, since it limits request *volume* per sender, not response *authorization*.

### Recommendation
Bind the response channel lookup to more than `MessageId`: also verify `body.Sender` and/or `body.DonId`/`body.Receiver` in the incoming message against the expected gateway/DON recorded at the time `handleSingleNodeRequest` sent the original request (e.g., store `selectedGateway`/expected DON alongside the channel in the `responses` map and reject/log-and-drop responses whose `gatewayID`, `DonId`, or `Sender` don't match the expected value). Additionally, consider using cryptographically random, sufficiently long `messageID`s (already partially enforced by `MessageIdMaxLen`, but generation is outside this file) to make collision guessing infeasible.

### Proof of Concept
Extend `TestHandleSingleNodeRequest` (`core/capabilities/webapi/outgoing_connector_handler_test.go`):
1. Start `HandleSingleNodeRequest` for workflow A with `messageID = "shared-id"`, mocking `SendToGateway` to *not* immediately respond (simulate in-flight request).
2. Concurrently, call `connectorHandler.HandleGatewayMessage(ctx, "attacker-gateway", gatewayResponse(t, "shared-id", attackerPrivateKey))` with a `Method: MethodWebAPITarget` payload containing attacker-controlled data, signed with a different, unrelated private key.
3. Assert that `HandleSingleNodeRequest` returns successfully with the attacker-supplied payload as if it were the legitimate gateway response, i.e., `resp.Body.Sender == attackerAddress` and `resp.Body.Payload == attackerPayload`, proving no sender/DON binding check exists.
4. Contrast with expected secure behavior: the response should be rejected/dropped unless `body.Sender`/`DonId` matches metadata recorded when the request was dispatched.

```go
func (c *OutgoingConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		c.lggr.Errorw("failed to validate request", "err", err, "gatewayID", gatewayID)
		return nil
	}
	body := &msg.Body
	l := logger.With(c.lggr, "gatewayID", gatewayID, "method", body.Method, "messageID", msg.Body.MessageId)

	ch, ok := c.responses.get(body.MessageId)
	if !ok {
		l.Warnw("no response channel found; this may indicate that the node timed out the request")
		return nil
	}
```

```go
func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
```
