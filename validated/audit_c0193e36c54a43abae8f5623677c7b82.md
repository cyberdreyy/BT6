### Title
Globally-rejected block can still be broadcast as accepted via `store_and_process_block_signature` skipping the `has_reached_consensus()` guard - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`store_and_process_block_signature` (the accept-path counterpart of `store_and_process_block_rejection`) never checks `block_info.has_reached_consensus()` before tallying signature weight and calling `broadcast_signed_block`. Its sibling function, `store_and_process_block_rejection`, explicitly bails out early once the block has reached consensus: [1](#0-0) 

But the accept path only gates on `block_info.signed_group.is_some()`, not on `has_reached_consensus()`: [2](#0-1) 

If enough signature weight (≥70%) accumulates after the local `BlockInfo` was already moved to `GloballyRejected` (via the reject path's own threshold check), the accept path still computes `total_signature_weight`, unconditionally attempts `mark_locally_accepted(true)`, silently swallows the resulting state-transition error because `has_reached_consensus()` is true, and then unconditionally calls `broadcast_signed_block` → `handle_post_block`, pushing the block to the node as if accepted: [3](#0-2) 

### Finding Description
`BlockInfo::check_state` forbids a `GloballyRejected` block from transitioning to `LocallyAccepted`: [4](#0-3) 

`mark_locally_accepted` (called from `store_and_process_block_signature`) will therefore return an `Err`, but the caller only warns "if `!block_info.has_reached_consensus()`" — i.e. it deliberately does nothing when the block already reached a global state, treating the failed transition as a harmless no-op: [5](#0-4) 

Crucially, the code does not `return` here — execution falls through to `insert_block` and then unconditionally to `broadcast_signed_block`, which assembles the accumulated signatures and calls `handle_post_block` to POST the block to the stacks-node as accepted: [6](#0-5) 

This is possible because signatures and rejections are tallied independently and are not mutually exclusive once persisted: the signerdb test suite documents that a global rejection does **not** clear previously stored signatures, precisely because a signature is "public and can still be aggregated toward the 70% threshold if enough rejecting signers change their minds": [7](#0-6) 

Because `min_weight` (≈70%) and the rejection-blocking threshold (>30%) are complementary over the same total weight, it is mathematically possible under normal asynchronous message delivery for a signer to first observe ≥30% reject weight (marking the block `GloballyRejected` via `store_and_process_block_rejection`) and later observe accept weight crossing ≥70% as remaining honest signers' votes/pre-commit-derived signatures arrive out of order (the "outdated peer" pre-commit-to-signature reinterpretation path, documented in `docs/signer-flows.md` section 6, also feeds signatures into this same tally). A miner that reproposes a block, forks the burn view, or times a competing tenure-start block (as covered by the conflict/timeout logic in `chainstate/v1.rs`/`v2.rs` and `signer.rs`'s pre-commit conflict checks) can widen the timing gap between different signers' local views of the same block, increasing the odds that some signers reject early while others' acceptances still arrive and cross the local accept tally after the local `GloballyRejected` state was already set. No cooperation or majority-key control by the attacker is required — the split arises from honest signers acting on divergent, individually-valid views caused by network/timing conditions the miner (plus normal gossip propagation) can influence.

### Impact Explanation
This breaks the required equality "aggregated-weight vs verified-accepts": a signer's local ground truth (`GloballyRejected`) is bypassed and the same signer still broadcasts the block to its node as accepted with an assembled signature set, effectively re-counting a locally-rejected block as an accept and attempting to push it into the chain. This matches the in-scope Critical impact category: "a rejection recounted as an accept." It also corrupts the signer's own audit state (`BlockInfo` says rejected while the node was handed an accepted block), and if the node accepts the POST, it could canonicalize a block that this signer's own state machine says should not exist.

### Likelihood Explanation
The bug requires no majority collusion, no compromised keys, and no auth token — only ordinary asynchronous delivery of independently-valid signer votes around the ~70%/30% threshold boundary, which the referenced pre-commit/conflict/timeout machinery in `chainstate/v1.rs`, `chainstate/v2.rs`, and `signer.rs` shows is a realistic and already-anticipated occurrence (siblings, reorg timing, stale conflicts). A miner controlling block proposal/reproposal timing (a "one-slot miner plus gossip") can plausibly widen this race window. The missing `has_reached_consensus()` guard is a straightforward control-flow omission relative to its sibling function, making the code path easy to trigger whenever the race condition occurs.

### Recommendation
Add the same early-return guard used in `store_and_process_block_rejection` to `store_and_process_block_signature`: check `block_info.has_reached_consensus()` immediately after `add_block_signature` succeeds (or immediately before computing `total_signature_weight`) and return without calling `mark_locally_accepted` or `broadcast_signed_block` if the block has already reached a terminal global state. Additionally, `broadcast_signed_block` should not be invoked when `mark_locally_accepted` returns an `Err`, regardless of whether the error is swallowed for logging purposes.

### Proof of Concept
Deterministic unit-test scenario (mirrors the pattern of existing tests such as `state_machine` and `has_signed_block` in `stacks-signer/src/signerdb.rs`):

1. Construct a `BlockInfo` for block `B`.
2. Have several signer addresses call `add_block_signature` for `B` (below the 70% threshold) — these are stored and survive rejection per the `has_signed_block_in_tenure` test semantics.
3. Have other signer addresses call `add_block_rejection_signer_addr` for `B` until `store_and_process_block_rejection`'s threshold check fires, calling `block_info.mark_globally_rejected()` (state becomes `GloballyRejected`).
4. Deliver one or more additional, independently valid `BlockResponse::Accepted` signatures for `B` (simulating slow/delayed honest signers) via `handle_block_response` → `store_and_process_block_signature`, until the newly totaled `total_signature_weight` crosses `min_weight`.
5. Observe: `mark_locally_accepted(true)` fails (swallowed because `has_reached_consensus()` is true), but `broadcast_signed_block` is still invoked and `handle_post_block` still POSTs the assembled block/signatures to the stacks-node — despite the signer's own DB recording `state == GloballyRejected` for that block.

Because the actual sequencing depends on message-delivery order across the signer set, exact reproduction requires either a targeted integration test injecting artificial delays on specific signer messages (similar to existing fault-injection tests like `TEST_SIGNERS_IGNORE_PRE_COMMITS`/`TEST_IGNORE_ALL_BLOCK_PROPOSALS` used in `stacks-node/src/tests/signer/v0/signers_consider_late_proposals.rs`) or direct unit-level manipulation of `SignerDb`/`Signer` state as outlined above.

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
