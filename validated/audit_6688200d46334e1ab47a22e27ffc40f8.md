## Title
`getSignatureStatuses` computes each signature's confirmation status against a freshly re-fetched "confirmed" bank and commitment cache per iteration, letting a single RPC call mix results from different underlying ledger states - ([File: rpc/src/rpc.rs])

### Summary
The Pyth bug allows two different price snapshots to be read within one atomic transaction because each price lookup queries live, mutable state instead of a state fixed for the whole call. The `JsonRpcRequestProcessor::get_signature_statuses` handler has the same structural flaw: it fixes one "processed" bank for the outer call, but for every signature it iterates over, it re-derives a brand-new "optimistically confirmed" bank and a brand-new snapshot of `block_commitment_cache` via `get_transaction_status`, both of which can advance mid-loop as the validator keeps processing/rooting new banks concurrently.

### Finding Description
`get_signature_statuses` fetches a single `bank` once, at the "processed" commitment level, and reuses it for the raw signature lookup and for the outer `RpcResponse` context slot: [1](#0-0) 

But for every signature in the loop it calls `get_transaction_status(signature, &bank)`, which internally does **not** reuse any fixed confirmed/root state — it independently re-reads `self.bank(Some(CommitmentConfig::confirmed()))` and re-locks `self.block_commitment_cache` on every call: [2](#0-1) 

`self.bank(commitment)` for `Confirmed`/`Finalized` re-derives the bank from `optimistically_confirmed_bank` or `block_commitment_cache` fresh each time it's invoked: [3](#0-2) 

Because these are independent, unsynchronized reads taken at different wall-clock instants during the same request, and the loop over `signatures` interleaves with `.await` points in other branches (e.g. the `search_transaction_history`/bigtable branch) which yield to the executor, the validator's background threads (`OptimisticallyConfirmedBankTracker`, `ReplayStage` rooting) can advance the "confirmed" bank and `block_commitment_cache` between iterations. Consequently, a single `getSignatureStatuses` call can compute `confirmation_status`/`confirmations` for different signatures in the same batch against *different* confirmed/root snapshots, while the response's outer context (`new_response(&bank, statuses)`) still reports the single, earlier "processed" slot fixed at the top of the function.

This mirrors the oracle bug class: a single client-facing call is supposed to represent one consistent point-in-time view, but internally re-fetches the same "current state" pointer multiple times, allowing state drift to leak into one response.

### Impact Explanation
The result is wrong/fork-inconsistent status data returned within a single RPC response: some signatures in a batch may be reported `Finalized`/`Confirmed` based on a later root/optimistic-confirmation snapshot than others, and the `confirmation_status` values become internally inconsistent with the context slot returned to the caller. Any unprivileged client issuing `getSignatureStatuses` with multiple signatures can observe this, and consumers that rely on the batch being a single consistent point-in-time view (e.g., wallets/bridges gating on finality) can be misled about transaction finality ordering.

### Likelihood Explanation
This requires no special conditions beyond calling the standard, unprivileged `getSignatureStatuses` JSON-RPC endpoint with several signatures during periods of active block production/confirmation (i.e., essentially always on a live cluster). The race window is naturally present anytime the validator's background confirmation/rooting threads run concurrently with RPC request handling, which is continuous.

### Recommendation
Fix the confirmed bank and `block_commitment_cache` snapshot once per `get_signature_statuses` call (mirroring the single "processed" `bank` fetch already done at the top), and thread that fixed snapshot into `get_transaction_status` instead of having it independently re-fetch `self.bank(Some(CommitmentConfig::confirmed()))` and re-lock `block_commitment_cache` on every iteration.

### Proof of Concept
1. Submit two transactions, `sig_a` (submitted/rooted earlier) and `sig_b` (submitted just before the call, not yet optimistically confirmed).
2. Call `getSignatureStatuses` with `[sig_a, sig_b]`.
3. During the loop, before `get_transaction_status(sig_b, &bank)` executes, let a background thread advance `optimistically_confirmed_bank`/`block_commitment_cache` root (this happens continuously on a live validator).
4. Observe that `sig_a` and `sig_b` in the same response can be evaluated against different confirmed-bank/root snapshots, producing a `confirmation_status` set that is not attributable to any single consistent slot, even though the response's single context slot implies one.

    fn bank(&self, commitment: Option<CommitmentConfig>) -> Arc<Bank> {
        debug!("RPC commitment_config: {commitment:?}");

        let commitment = commitment.unwrap_or_default();
        if commitment.is_confirmed() {
            let bank = self
                .optimistically_confirmed_bank
                .read()
                .unwrap()
                .bank
                .clone();
            debug!("RPC using optimistically confirmed slot: {:?}", bank.slot());
            return bank;
        }

        let slot = self
            .block_commitment_cache
            .read()
            .unwrap()
            .slot_with_commitment(commitment.commitment);

        match commitment.commitment {
            CommitmentLevel::Processed => {
                debug!("RPC using the heaviest slot: {slot:?}");
            }
            CommitmentLevel::Finalized => {
                debug!("RPC using block: {slot:?}");
            }
            CommitmentLevel::Confirmed => unreachable!(), // SingleGossip variant is deprecated
        };

        let r_bank_forks = self.bank_forks.read().unwrap();
        r_bank_forks.get(slot).unwrap_or_else(|| {
            // We log a warning instead of returning an error, because all known error cases
