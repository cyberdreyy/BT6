### Title
Unprivileged lockup-factory caller can plant a malicious `staking_pool_whitelist_account_id`, defeating the staking-pool trust check - (File: `lockup-factory/src/lib.rs`)

### Summary
This mirrors the "trusting an unverified account as a pool" bug class from the report: instead of a Router trusting an arbitrary pool address, the NEAR lockup-factory lets any unprivileged funder pin an arbitrary "whitelist" account into a lockup contract deployed for a third-party owner, silently replacing the canonical NEAR Foundation whitelist that `select_staking_pool` is supposed to check against.

### Finding Description
`LockupFactory::create` is `#[payable]` with no caller restriction, callable by anyone who attaches `MIN_ATTACHED_BALANCE` [1](#0-0) . It takes an optional `whitelist_account_id` parameter fully controlled by the caller, and if supplied, uses it verbatim instead of the factory's own `self.whitelist_account_id` (set once at `new()` by whoever deployed the factory) as the `staking_pool_whitelist_account_id` baked into the new lockup contract's init args [2](#0-1) .

The deployed `LockupContract` stores this attacker-chosen value as `staking_pool_whitelist_account_id` [3](#0-2) . The owner's only protection when delegating funds is `select_staking_pool`, which cross-checks the target pool against that stored whitelist account via a cross-contract call [4](#0-3) , and the callback unconditionally trusts whatever boolean the "whitelist" contract returns: `assert!(is_whitelisted, ...)` [5](#0-4) .

Equality that should hold: `lockup.staking_pool_whitelist_account_id == <canonical NEAR-Foundation-controlled whitelist>`. Because the factory lets any funder override this at creation time, the equality can instead become `lockup.staking_pool_whitelist_account_id == <attacker-deployed contract>`, breaking the "account trusted as a whitelist versus the code/arguments that trust was granted for" binding.

### Impact Explanation
An attacker (any unprivileged account) can:
1. Deploy their own mock "whitelist" contract that unconditionally returns `true` from `is_whitelisted`.
2. Call `lockup-factory`'s `create()`, setting `owner_account_id` to the intended victim and `whitelist_account_id` to their mock contract.
3. Once transfers are enabled and the victim (owner) later calls `select_staking_pool` with what they believe is a legitimate, foundation-approved pool ID (or is socially engineered/front-end-tricked into supplying an attacker's pool ID), the call is "verified" against the attacker's mock whitelist, which always returns `true`.
4. The victim's `deposit_and_stake` / `stake` calls then transfer the locked NEAR to the attacker-controlled "staking pool" contract, which can simply keep the funds (never honoring `unstake`/`withdraw`).

This crosses the Critical bar: NEAR moved by a party not entitled to it via a wrongly-parameterised deployment (the lockup is deployed with a subverted trust anchor instead of the documented Foundation whitelist).

### Likelihood Explanation
The `create()` function has no caller restriction and the malicious parameter is a normal, documented optional input (`whitelist_account_id`), not a code bug requiring an edge case — it is directly reachable in one transaction. The remaining condition (victim eventually calling `select_staking_pool` with a pool the attacker also controls or has tricked them into using) parallels exactly the disputed/accepted Medium-severity trust boundary in the original report — a compromised or careless front-end/counterparty picking the "pool"/"whitelist" is the same reliance the whitelist mechanism exists to remove for legitimate factories, but this factory-provided override defeats it for any lockup it deploys.

### Recommendation
Do not let unprivileged callers override the staking-pool whitelist. `lockup-factory::create` should always use `self.whitelist_account_id` (the value pinned at factory initialization by the NEAR Foundation) and drop the caller-suppliable `whitelist_account_id` parameter entirely, or, if per-lockup customization is genuinely required, restrict `create()`/the whitelist override to a foundation-controlled caller and validate the supplied account against a foundation-approved list of whitelist contracts before using it.

### Proof of Concept
1. Attacker deploys `EvilWhitelist` contract exposing `is_whitelisted(staking_pool_account_id) -> bool { true }`.
2. Attacker deploys `EvilPool` contract mimicking the staking-pool interface (`deposit_and_stake`, `stake`) that accepts deposits but reverts/no-ops on `unstake`/`withdraw`.
3. Attacker calls:
```
near call lockup-factory create '{
  "owner_account_id": "victim.near",
  "lockup_duration": "...",
  "whitelist_account_id": "evil-whitelist.attacker.near"
}' --accountId attacker.near --amount 35
```
4. `victim.near` later calls `select_staking_pool({"staking_pool_account_id": "evil-pool.attacker.near"})` — the whitelist check against `evil-whitelist.attacker.near` returns `true`, so `on_whitelist_is_whitelisted` accepts it [5](#0-4) .
5. `victim.near` calls `deposit_and_stake`, transferring locked NEAR to `evil-pool.attacker.near` [6](#0-5) .
6. `evil-pool.attacker.near` retains the funds; `unstake`/`withdraw_from_staking_pool` never succeed against it, permanently freezing/stealing the victim's locked NEAR.
