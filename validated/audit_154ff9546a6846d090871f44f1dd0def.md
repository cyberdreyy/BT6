### Title
LDAP unauthenticated ("empty password") bind bypasses authentication in `CreateSession` - (File: core/sessions/ldapauth/ldap.go)

### Summary
`ldapAuthenticator.CreateSession` passes the attacker-supplied `sr.Password` directly to `conn.Bind(searchBaseDN, sr.Password)` without rejecting an empty password. Per RFC 4513, an LDAP bind with a non-empty DN and an empty password is an "unauthenticated bind" that many LDAP servers accept as successful without verifying any credential, so an attacker who only knows a valid user's email can authenticate as that user and receive a fully privileged session.

### Finding Description
In `CreateSession` [1](#0-0)  the code builds `searchBaseDN` from the attacker-controlled `sr.Email` and calls `conn.Bind(searchBaseDN, sr.Password)`. There is no check anywhere in the request path that `sr.Password` is non-empty: the HTTP handler `SessionsController.Create` binds `clsessions.SessionRequest` straight from JSON and forwards it to `CreateSession` with no password-length/non-empty validation [2](#0-1) , and `SessionRequest` itself has no validation tags [3](#0-2) .

If the LDAP server treats a bind with an empty password as an anonymous/unauthenticated bind and returns success (the RFC-4513-compliant default behavior for many directory servers unless `LDAP_OPT_X_TLS_REQUIRE_CERT`/`disallowUnauthBind`-style hardening is configured on the server), `conn.Bind` returns `nil` error even though no real credential was checked. The code then proceeds: it calls `l.FindUser(ctx, escapedEmail)` to fetch the real role for that email, creates a valid `ldap_sessions` row, and calls `l.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, map[string]any{"email": sr.Email})` [4](#0-3) , returning a legitimate session ID to the attacker. The audit log records a normal successful login, masking the fact that no password was actually verified.

An unauthenticated attacker who knows (or guesses/enumerates) any valid user email registered in the LDAP directory can send `{"email": "<victim>@org.com", "password": ""}` to the session-creation endpoint and, if the upstream LDAP server has not explicitly disabled unauthenticated binds, obtain a valid authenticated session with that victim's full role (potentially Admin).

### Impact Explanation
This is a full authentication bypass leading to account takeover of any known LDAP user, including admin accounts, without knowing their password. This maps to Chainlink's highest bounty impact class (node compromise / authentication bypass) since the attacker gains a legitimate session cookie/ID with the victim's role and can perform all actions that role permits (job management, key/secret access depending on role, fund-affecting operations).

### Likelihood Explanation
Exploitability depends on the upstream LDAP server's configuration for unauthenticated binds, which is outside this application's control — RFC 4513 unauthenticated binds are common default behavior and this Go code performs no defensive check to reject them at the application layer. No credentials, network position, or special role are needed by the attacker beyond knowing a target's email address, which is often guessable/enumerable. The missing check is squarely in `core/sessions/ldapauth/ldap.go`, not merely an LDAP-server misconfiguration issue, since the fix is a one-line guard in application code that any consumer of this library should apply regardless of server config.

### Recommendation
In `CreateSession` (and `TestPassword`), reject empty/whitespace-only passwords before calling `conn.Bind`, e.g.:
```go
if strings.TrimSpace(sr.Password) == "" {
    return "", errors.New("unable to log in with LDAP server. Check credentials")
}
```
This prevents unauthenticated binds from ever reaching the LDAP server regardless of server-side configuration.

### Proof of Concept
Handler-level Go test plan (extending `core/sessions/ldapauth/ldap_test.go`):
1. Build a fake `LDAPClient`/`LDAPConn` mock whose `Bind(dn, password string) error` implementation mimics RFC 4513 semantics: return `nil` (success) when `password == ""` and a non-empty `dn`, and return an error for any non-matching non-empty password.
2. Instantiate `ldapAuthenticator` with this mock client and a stub `ds` that returns a valid `FindUser` result (e.g., an entry that maps the target email to `sessions.UserRoleAdmin`).
3. Call `CreateSession(ctx, sessions.SessionRequest{Email: "victim@example.com", Password: ""})`.
4. Assert: no error is returned, a non-empty session ID string is returned, a row is inserted into `ldap_sessions` for `victim@example.com` with role Admin, and `auditLogger.Audit` was called with `audit.AuthLoginSuccessNo2FA`.
5. This demonstrates that with an empty password the function completes the full "successful login" path without verifying any real credential, confirming the authentication bypass.
