### Title
Griefing shareholder can permanently DoS `vesting::distribute`/`distribute_many` and lock all co-shareholders' vested stake by disabling direct-coin-transfer acceptance - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`vesting::distribute` loops over every shareholder of a vesting pool and calls `aptos_account::deposit_coins` for each one atomically [1](#0-0) . `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient account exists, is not yet registered for `AptosCoin`, and has explicitly opted out of unregistered direct transfers via `aptos_account::set_allow_direct_coin_transfers` [2](#0-1) . Because any account can call `set_allow_direct_coin_transfers(false)` on itself at any time — a fully unprivileged action [3](#0-2)  — a single shareholder (or an address the admin set as someone's beneficiary before that address later opts out) can permanently make `distribute()` for the entire vesting contract revert, which is the direct analog of the reported `OracleManager::generatePerformance`/`deactivateValidator` pattern: one entity's failure blocks a batched operation for everyone else.

### Finding Description
`vesting.move` explicitly acknowledges this exact failure mode for the beneficiary-update path, and defends against it there only:
```
// Verify that the beneficiary account is set up to receive APT. This is a requirement so distribute() wouldn't
// fail and block all other accounts from receiving APT if one beneficiary is not registered.
assert_account_is_registered_for_apt(new_beneficiary);
``` [4](#0-3) 

However, this check is only performed once, at the moment `set_beneficiary` is called, and only for `new_beneficiary`. It does not:
- Verify the default recipient (the shareholder address itself, used whenever no beneficiary is set) at any point, nor at vesting-contract creation.
- Prevent an already-registered/checked beneficiary from later disabling direct-coin-transfer acceptance and de-registering, since registration state and the opt-out flag are both fully controlled by the recipient after the check passes.

`distribute()` then unconditionally calls `aptos_account::deposit_coins(recipient_address, share_of_coins)` for every shareholder inside a `for_each_ref` loop with no error handling or skip-on-failure logic [1](#0-0) . `deposit_coins` aborts whenever the recipient exists, is unregistered for the coin type, and `can_receive_direct_coin_transfers` returns false [5](#0-4) . Since the whole entry function reverts atomically (including the prior `withdraw_stake` that pulled coins out of the underlying stake pool), no shareholder in that vesting pool — not just the offending one — can ever receive their vested/reward distribution again through this path. `terminate_vesting_contract` also calls `distribute` internally before admin_withdraw can proceed [6](#0-5) , so this same poisoned-recipient condition also blocks contract termination/admin_withdraw, compounding the lock. The batch helper `distribute_many` amplifies blast radius across contracts sharing this iteration pattern [7](#0-6) , though the per-contract revert is already sufficient to demonstrate the invariant break.

The same root cause (`deposit_coins` used inside an unskippable distribution loop) also exists in `staking_contract::distribute_internal`, which pays the operator's beneficiary via `aptos_account::deposit_coins` inside its `while (distribution_pool.shareholders_count() > 0)` loop [8](#0-7) , but that path is lower impact because it typically involves fewer parties (staker/operator) rather than an arbitrary set of co-shareholders in a shared vesting pool.

### Impact Explanation
This is a **permanent lock of claim rights** for all shareholders (and their intended beneficiaries) who share a `VestingContract` with a griefing/inactive shareholder. Once one shareholder's designated recipient (shareholder address itself, or a beneficiary that deregisters after being set) opts out of unregistered direct transfers without registering for `AptosCoin`, every future call to `distribute()` for that entire vesting pool reverts — permanently trapping already-unlocked/vested stake for every other, non-malicious shareholder, and also blocking `terminate_vesting_contract`/`admin_withdraw`. This satisfies the "Permanent lock or non-recoverable loss of claim rights in ... vesting flows" impact category, since no other participant nor the admin has any on-chain mechanism to skip or bypass the poisoned recipient in the `distribute` loop.

### Likelihood Explanation
Likelihood is high: `set_allow_direct_coin_transfers` is a fully permissionless, unprivileged public entry function callable by any account holder on itself [3](#0-2) , requiring no special role, stake, or timing condition — any shareholder of a multi-shareholder vesting contract can trigger this at will (or simply never register for `AptosCoin` while defaulting to opted-out semantics), and it can also occur unintentionally (e.g., an inactive/lost-key account that never registered for APT).

### Recommendation
- In `vesting::distribute` (and `staking_contract::distribute_internal`), do not let one recipient's failure abort the whole loop: wrap each `deposit_coins` call so failures are isolated per-shareholder (e.g., check `coin::is_account_registered` / `can_receive_direct_coin_transfers` before attempting deposit and, on failure, escrow that shareholder's share for later individual claim instead of aborting the batch).
- Alternatively, enforce `assert_account_is_registered_for_apt` on the default shareholder address at `create_vesting_contract` time (not only for `set_beneficiary`), and re-validate registration status transactionally (or use a coin-agnostic escrow/claim-based pull pattern) so that the state of one recipient can never block others' entitled distributions.

### Proof of Concept
1. Admin creates a vesting contract with shareholders `A` and `B` via `create_vesting_contract`; neither sets a beneficiary, so distributions default to `A` and `B` directly.
2. `A` calls `aptos_account::set_allow_direct_coin_transfers(A_signer, false)` on their own account, without ever calling `coin::register<AptosCoin>()` (no assertion in the vesting module prevents this — it is entirely independent of vesting logic).
3. Vesting period elapses; `vest()`/`unlock_rewards()` schedule stake to become withdrawable.
4. Anyone calls `distribute(contract_address)`. Inside the shareholder loop, `aptos_account::deposit_coins(A, share_of_coins)` hits `!coin::is_account_registered<AptosCoin>(A)` and `can_receive_direct_coin_transfers(A) == false`, aborting with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The entire `distribute` transaction reverts, so `B`'s legitimately vested/rewarded stake is never paid out, and this remains true for every future call to `distribute` (and `terminate_vesting_contract`) on this contract as long as `A` keeps this state — a state fully controlled by `A`, not by `B` or the admin.

    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
