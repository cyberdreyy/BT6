### Title
Loss-adjusted withdraw receipts are keyed to the wrong epoch, letting them claim at par and freeze later claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.collectWithdrawFunds` stores the pro-rata loss haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is incremented inside `deposit()` whenever it is called while `isEpochRunning` — which per the inline comment is exactly the stopEpoch funding path (`"deposit done on stopEpoch (before setting the var to false) so we reset the counter"`). Withdraw receipts and `lastWithdrawRequest` are keyed to the *pre-increment* epoch. As a result, receipts that were only partially funded via `stopEpochWithDuration` look up `lossRecoveryPriceByEpoch` under the wrong key, skip the haircut entirely, and are paid at par through `_claimFundedWithdrawRequest`, draining more underlying than was ever collected and permanently freezing the remaining claimants.

### Finding Description
- In `requestWithdraw`, a receipt is recorded as `withdrawsRequestsByEpoch[_user][currentEpoch]` and `lastWithdrawRequest[_user] = currentEpoch`, where `currentEpoch = epochNumber` read before the epoch ends (`IdleCreditVault.sol:260-294`).
- During `stopEpoch`, the CDO pushes repaid funds into the strategy via `deposit()`. Because `isEpochRunning` is still true at that moment, `deposit()` executes `epochNumber += 1` (`IdleCreditVault.sol:607-610`).
- Later in the same stop flow, `collectWithdrawFunds(_amount)` is called with `_amount < pendingWithdraws` (a realized loss). It computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` and stores it under `lossRecoveryPriceByEpoch[epochNumber]` — now the *incremented* epoch (`IdleCreditVault.sol:411-421`).
- On claim, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the pre-increment epoch — finds `0`, and returns without applying the haircut (`IdleCreditVault.sol:789-800`).
- The request-side guard at `IdleCreditVault.sol:263-271`, which is meant to force users to claim a loss-adjusted receipt before opening a new one, reads the same wrong key and never triggers.
- The receipt then falls through to `_claimFundedWithdrawRequest`, which only checks `epochNumber <= lastWithdrawRequest[_user]` (now false after the increment) and pays `withdrawsRequests[_user]` in full via `_transferFundedClaim` (`IdleCreditVault.sol:319-350`).

### Impact Explanation
Only `R * pendingBasis` underlying was transferred to the strategy (`collectWithdrawFunds` line 428), but every pending receipt claims 100% of face value. Early claimants drain the funded pool at par — an effective theft of `(1 - R) * pendingBasis` beyond what was funded — and once the balance is exhausted, every subsequent `claimWithdrawRequest` reverts in `safeTransfer`, permanently freezing the remaining users' already-funded withdraw claims. This is a direct insolvency/permanent-freeze of funds, matching the availability-impact class of the reference report.

### Likelihood Explanation
- Attacker is a normal KYC'd tranche holder: they only need to call `IdleCDOEpochVariant.requestWithdraw` during an epoch, then `claimWithdrawRequest` after a lossy stop.
- The triggering condition (`stopEpochWithDuration` with `0 < _lossAmount < pendingBasis`, i.e. partial funding of pending receipts) is a routine manager/borrower action — honest roles, not attacker-controlled.
- No guard stops it: the epoch-gating check passes (epochNumber > lastWithdrawRequest), the loss-haircut lookup misses due to the key mismatch, and `_transferFundedClaim` only protects `defaultRecoveryReserve`, which is 0 absent a default.

### Recommendation
Store the loss recovery price under the epoch in which the receipts were created, not the incremented counter. Either capture `epochNumber` before the incrementing `deposit()` call and pass it to `collectWithdrawFunds`, or change `collectWithdrawFunds` to accept the request epoch as a parameter. Additionally, have `_claimLossAdjustedWithdrawRequest` and the `requestWithdraw` guard iterate or otherwise resolve the correct receipt epoch instead of relying solely on `lastWithdrawRequest`.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (setup mirrors test/foundry/IdleCreditVault.t.sol)
function testLossReceiptClaimedAtPar() external {
    // 1. Attacker deposits into AA during buffer and requests withdraw in epoch K
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    // attacker receipt: withdrawsRequestsByEpoch[attacker][K] = amount
    // lastWithdrawRequest[attacker] = K

    // 2. Borrower (honest) partially repays; manager stops epoch with a loss.
    //    Inside stopEpoch: strategy.deposit() runs while isEpochRunning == true,
    //    so epochNumber becomes K+1 BEFORE collectWithdrawFunds stores
    //    lossRecoveryPriceByEpoch[K+1] = R < 1e18.
    deal(defaultUnderlying, borrower, fundedAmount); // fundedAmount < pendingBasis
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, lossAmount);

    // 3. Attacker claims: lossRecoveryPriceByEpoch[K] == 0 -> haircut skipped,
    //    epochNumber (K+1) > lastWithdrawRequest (K) -> funded path pays FULL amount.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, fullReceiptBasis); // par, not R * basis

    // 4. A second claimant whose receipt was funded only at R now reverts:
    //    strategy balance exhausted -> safeTransfer fails -> permanent freeze.
    vm.prank(victim);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

**Caveat:** this finding depends on the intra-`stopEpoch` ordering — that the `epochNumber += 1` inside `deposit()` executes before `collectWithdrawFunds` reads `epochNumber`. I was unable to trace `stopEpoch`/`stopEpochWithDuration` in `IdleCDOEpochVariant.sol` within the available search iterations, so the exact call ordering (and thus whether `lossRecoveryPriceByEpoch` is keyed pre- or post-increment) should be confirmed before finalizing the PoC. If `collectWithdrawFunds` runs strictly before the incrementing `deposit()`, the keys align and this specific issue does not hold.
