### Title
Missing state-transition check on `bid.execution_payment` allows a proposer to accept an invalid/self-dealing bid uncommitted by gossip validation - ([File: specs/gloas/beacon-chain.md])

### Summary
`process_execution_payload_bid` (the block-processing / state-transition function) never validates `bid.execution_payment`, even though the spec explicitly defines it as a privileged, trust-gated field that "**MUST NOT** be broadcast to the `execution_payload_bid` gossip topic" when non-zero, and gossip validation (`validate_execution_payload_bid_gossip`) rejects any bid with `bid.execution_payment != 0`. This mirrors the LiFi bug class: one code path (NXTP's completion function / here, gossip validation) checks a value-type field, while the authoritative path that actually mutates state (the bridging start function / here, `process_execution_payload_bid`) omits the check entirely.

### Finding Description
`ExecutionPayloadBid` contains an `execution_payment: Gwei` field defined as a "trusted execution-layer payment" indicator (`specs/gloas/beacon-chain.md:760`, `specs/gloas/builder.md:151-153`). The builder-construction guidance says this field must be zero for gossip-sourced bids, and the p2p layer enforces this with a `[REJECT]` check: [1](#0-0) 

However, the beacon-chain state-transition function that actually processes a bid included in a block, `process_execution_payload_bid`, reads only `bid.value` (aliased `amount`) and never inspects or asserts anything about `bid.execution_payment`: [2](#0-1) 

Because a proposer builds/accepts a block directly (not necessarily via the gossip `execution_payload_bid` topic — e.g. via local block production, a local/self-build path, or a private relay/side-channel bid never broadcast on gossip), the gossip-only `[REJECT]` on `execution_payment != 0` provides no guarantee at the consensus state-transition boundary. `process_execution_payload_bid` will happily accept, sign-verify, and record a `BuilderPendingPayment`/cache `state.latest_execution_payload_bid` for a bid carrying an arbitrary non-zero `execution_payment`, with no equality enforced between what the field claims (a "trusted EL payment") and what the CL state actually processes.

This breaks the intended equality that "a payload or payment applied [must be] what the block did commit to, and only through the channels the spec defines to authorize it." The `execution_payment` field is defined as carrying special semantic weight (a trust flag bypassing the normal `value`/pending-payment accounting), yet the state transition treats it as inert data — it is stored in `state.latest_execution_payload_bid` unchecked and is not reconciled against `bid.value`, `can_builder_cover_bid`, or any invariant that a "trusted" payment must correspond to an actual balance movement recorded in `builder_pending_payments`/`builder_pending_withdrawals`.

### Impact Explanation
Any consumer of `state.latest_execution_payload_bid.execution_payment` (either off-chain infrastructure, future spec logic that keys off this field, or client implementations that treat a non-zero `execution_payment` as an authorization signal for EL-side minting/payment) can be fed a value that was never validated by the canonical state transition. Since the field is explicitly called a "trusted execution-layer payment" marker, an unchecked non-zero value reaching finalized state without any accompanying balance-consistency assertion is exactly the kind of "payment applied that the block did not commit to / was not authorized to commit to" scenario flagged as Critical/High in the rules (payload or payment executed/paid that the canonical validation path did not enforce). At minimum, it represents divergence between what gossip nodes would reject and what the state transition silently accepts, i.e., two spec-defined validation layers disagreeing on the validity of the same object, with only one of them (the weaker, block-inclusion path) being authoritative for chain finality.

### Likelihood Explanation
Likelihood is constrained by the fact that only a block proposer/builder controls the bid embedded in a block (this requires no external attacker, no client bug, and no coalition — a single proposer can construct such a block locally, bypassing gossip entirely, since gossip is only a broadcast-time filter, not a state-transition-time filter). Given that block production has an explicit alternate path (self-build / private relay) that never touches the `execution_payload_bid` gossip topic, the missing check in `process_execution_payload_bid` is trivially reachable by any single proposer without needing majority stake or peer cooperation.

### Recommendation
Add an explicit assertion in `process_execution_payload_bid` (mirroring the gossip-layer `[REJECT]`) that `bid.execution_payment == 0`, or, if a legitimate trusted-payment pathway is intended for future functionality, define and enforce the exact state-transition semantics (source of funds, recipient, and balance equality) for a non-zero `execution_payment` directly in the state transition rather than relying solely on gossip-time filtering.

### Proof of Concept
1. A validator acting as its own block proposer (or a builder with a private/non-gossiped bid channel) constructs a `SignedExecutionPayloadBid` with `bid.execution_payment = X` for some `X > 0`, and otherwise-valid fields (`bid.value` set normally, correct `parent_block_hash`, `slot`, `prev_randao`, valid signature, etc.).
2. This bid is never broadcast on the `execution_payload_bid` gossip topic, so `validate_execution_payload_bid_gossip`'s `[REJECT] bid's execution payment must be zero` check is never invoked: [1](#0-0) 
3. The proposer includes this bid in a `BeaconBlock` and the block is processed through normal state transition, calling `process_execution_payload_bid(state, block.body.signed_execution_payload_bid)`.
4. `process_execution_payload_bid` performs its full set of assertions (self-build/value checks, blob count, slot/parent/hash checks) — none of which reference `execution_payment` — and successfully caches `state.latest_execution_payload_bid = bid` with `execution_payment = X` intact: [3](#0-2) 
5. All spec-following nodes accept this block as valid (since `process_execution_payload_bid` never rejects on `execution_payment`), even though the same object would have been rejected had it been propagated via gossip — demonstrating the equality break between the two validation surfaces for the same logical invariant.

```python
def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid
