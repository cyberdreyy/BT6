### Title
Operator can permanently trap a staker's own inactive stake by setting an unregistered/non-accepting beneficiary in `staking_contract::set_beneficiary_for_operator` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::distribute_internal` pays out every shareholder recorded in a staking contract's `distribution_pool` (the staker and the operator/beneficiary) in a single loop within one transaction. Any single failed payout aborts the whole transaction, blocking payout to *every* other shareholder in that loop, including the staker's own unlocked stake. `set_beneficiary_for_operator` lets the operator redirect their commission payouts to an arbitrary `new_beneficiary` address with no check that the address can actually receive APT, unlike the equivalent function in `vesting.move`, which explicitly guards against this exact failure mode.

### Finding Description
`distribute_internal` withdraws all unlocked/pending-inactive stake, buys everyone into a `distribution_pool`, then iterates and pays out each recipient via `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` will abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient exists but is not registered for the coin and has opted out of direct transfers: [2](#0-1) 

The operator controls this loop's second recipient by calling `set_beneficiary_for_operator`, which stores `new_beneficiary` with **no validation** that the address can actually receive APT: [3](#0-2) 

Compare this to the equivalent function in `vesting.move`, `set_beneficiary`, which explicitly performs `assert_account_is_registered_for_apt(new_beneficiary)` with a comment stating this exact rationale — to prevent `distribute()` from failing and blocking all other accounts from receiving APT if one beneficiary is unregistered: [4](#0-3) 

Because `staking_contract.move` never applies this same guard, an operator can set their beneficiary to an address that has called `aptos_account::set_allow_direct_coin_transfers(false)` (or any account that will otherwise reject the deposit) and never registered a `CoinStore<AptosCoin>`. From that point on, any call into `distribute_internal` — which is also invoked internally by `request_commission`, `unlock_stake`, `switch_operator`, and `distribute` itself — will abort while trying to pay the operator/beneficiary, reverting the entire transaction and preventing the staker's own unlocked/inactive stake in the same `distribution_pool` from being paid out in that call.

### Impact Explanation
This traps a party's (the staker's) legitimate claim on their own withdrawn/inactive stake because it shares the same atomic payout loop as the operator's commission. It matches the "Permanent lock or non-recoverable loss of claim rights in stake ... commission, beneficiary ... flows" impact category: the staker cannot withdraw already-unlocked funds through `distribute`/`unlock_stake`/`request_commission` as long as the poisoned beneficiary remains set, and there is no framework function that lets the staker unilaterally reset the operator's beneficiary (only the operator can call `set_beneficiary_for_operator` again). This is a direct analog of the RED-mint-pause bug: a single participant's action against a shared payout resource (the harvest call / the distribution loop) blocks value that rightfully belongs to another, uninvolved party.

### Likelihood Explanation
Low-to-medium. It requires the operator to intentionally (or accidentally, e.g. by using a beneficiary address that had `allow_arbitrary_coin_transfers` disabled) set an unregistered/opted-out beneficiary. This is entirely operator-controlled and does not require the staker's cooperation, so a malicious or careless operator can trigger it at will — but it depends on the operator being incentivized to grief a staker who trusts them with the stake pool.

### Recommendation
Mirror the fix already applied in `vesting.move`: add an `assert_account_is_registered_for_apt(new_beneficiary)` (or equivalent "can receive APT" check) inside `staking_contract::set_beneficiary_for_operator` before storing the new beneficiary, so a bad beneficiary address can never enter the shared distribution loop. Additionally, consider decoupling the operator/beneficiary payout from the staker's own payout in `distribute_internal` (e.g., try/skip failed recipients rather than aborting the whole loop) so one broken recipient cannot block payouts owed to others.

### Proof of Concept
1. Staker creates a staking contract with `operator` via `staking_contract::create_staking_contract`.
2. `operator` calls `aptos_account::set_allow_direct_coin_transfers(false)` from a fresh account `B` that has never registered a `CoinStore<AptosCoin>`.
3. `operator` calls `staking_contract::set_beneficiary_for_operator(operator, B)` — this succeeds because no registration check exists (see `staking_contract.move#L810-838`).
4. Time passes, rewards accrue, and the staker calls `unlock_stake`/`request_commission`/`distribute` to withdraw their unlocked stake. `distribute_internal` builds a `distribution_pool` containing both the staker and `B` (as `beneficiary_for_operator(operator)`), then in the payout loop attempts `aptos_account::deposit_coins(B, ...)`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The whole transaction reverts, so the staker's already-unlocked stake remains stuck in the `distribution_pool`/stake pool with no way to withdraw it until the operator changes the beneficiary back (something only the operator controls) — the exact same "single unresponsive recipient blocks the whole shared distribution" pattern as the RED-token-pause report, but here the trapped value belongs to an unprivileged staker rather than the party who caused the block.

*Note: I was unable to fully verify within available searches whether `delegation_pool.move`'s `set_beneficiary_for_operator`/commission-distribution path has an equivalent registration check or the same atomic-loop structure; this report is limited to the `staking_contract.move` path where the code and its contrast with `vesting.move`'s explicit fix were directly confirmed.*

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
