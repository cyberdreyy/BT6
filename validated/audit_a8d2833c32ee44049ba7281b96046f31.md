### Title
Withdraw instruction parser drops `rangeProofContextStateAccount`/`equalityProofContextStateAccount` and mislabels a context-state account as `owner` when `account_indexes` length sits at the `saturating_sub(1)` boundary - ([File: transaction-status/src/parse_token/extension/confidential_transfer.rs])

### Summary
In `parse_confidential_transfer_instruction`'s `ConfidentialTransferInstruction::Withdraw` arm, the sequential `offset < account_indexes.len().saturating_sub(1)` guards are meant to reserve the final account slot for the signer/owner, but they only reserve one slot regardless of how many context-state fields (`instructionsSysvar`, `equalityProofContextStateAccount`, `rangeProofContextStateAccount`) still need to be emitted. When `account_indexes.len()` is crafted to the minimum accepted by `check_num_token_accounts` (4) while both proof offsets are `0`, the `rangeProofContextStateAccount` check fails its bound test and is skipped, and the account index that should have represented that context-state account is instead consumed by `parse_signers` and labeled `"owner"`. [1](#0-0) 

### Finding Description
The Withdraw handling path is:
```
check_num_token_accounts(account_indexes, 4)?;
...
let mut offset = 2;
let has_sysvar = eq_offset != 0 || range_offset != 0;
if has_sysvar && offset < account_indexes.len().saturating_sub(1) { ... offset += 1 }
if eq_offset == 0 && offset < account_indexes.len().saturating_sub(1) { ... offset += 1 }
if range_offset == 0 && offset < account_indexes.len().saturating_sub(1) { ... offset += 1 }
parse_signers(map, offset, account_keys, account_indexes, "owner", "multisigOwner");
``` [2](#0-1) 

With `equality_proof_instruction_offset == 0` and `range_proof_instruction_offset == 0` (both proofs use dedicated context-state accounts, the spec-correct layout being `[account, mint, equalityCtx, rangeCtx, owner, ...]`, i.e. minimum 5 accounts), if the attacker instead supplies exactly the `check_num_token_accounts`-mandated minimum of 4 account indexes:
- `offset=2`: `eq_offset==0 && 2 < (4-1)=3` → true → `equalityProofContextStateAccount = account_indexes[2]`, `offset=3`
- `offset=3`: `range_offset==0 && 3 < 3` → false → `rangeProofContextStateAccount` is **not emitted at all**
- `parse_signers(map, 3, ...)` → the account at `account_indexes[3]` (which, per the intended 5-account layout, would be the range-proof context-state account) is instead labeled `"owner"`.

The guard was designed to keep the *last* index reserved for the signer, but it doesn't account for the fact that multiple context-account fields may still be pending; it only checks the boundary independently for each field against the same fixed length, so the last remaining slot silently absorbs whatever field is still outstanding and reassigns it the generic `"owner"` role. This produces a JSON-RPC `parsedInstruction` in which a context-state account pubkey is reported under the `"owner"`/`"multisigOwner"` key instead of `"rangeProofContextStateAccount"`, which does not faithfully represent the raw instruction's account roles. Because `parse_token` is purely used to format `getTransaction`/`getConfirmedTransaction` results from raw message data — it runs regardless of whether the on-chain SPL-Token-2022 program would actually accept/execute such a truncated account list — the transaction can be submitted, land on-chain (fee-paying, likely failing on-chain with `NotEnoughAccountKeys`), and still be returned with this misleading parsed instruction to any RPC client. [3](#0-2) 

### Impact Explanation
Scoped impact is limited to RPC output correctness: `getTransaction` (or subscription equivalents) can display a fabricated `"owner"`/`"multisigOwner"` value that is actually a `rangeProofContextStateAccount` pubkey, and omit the true context-state-account field entirely. This falls under the audit's accepted "decoder panic and misreporting" category — it is a display/attribution bug in `transaction-status`, not a consensus or execution vulnerability. There is no state mutation, no crash, and no unbounded cost; the effect is confined to a single misparsed instruction in the JSON response for one transaction. [4](#0-3) 

### Likelihood Explanation
This is trivially reproducible by any unprivileged client: craft and submit a single transaction whose Withdraw instruction (`SplToken2022` program id) has `account_indexes.len() == 4` and both `equality_proof_instruction_offset` and `range_proof_instruction_offset` equal to `0`, satisfying only the minimum `check_num_token_accounts(account_indexes, 4)` bound. No special privileges, staking, or leader control is required — a single `sendTransaction` followed by one `getTransaction` call reproduces the misreporting deterministically. The underlying on-chain execution will likely fail (insufficient accounts for the real program logic), but the transaction still gets included and its parsed representation returned.

### Recommendation
Rework the Withdraw (and similarly structured Transfer/TransferWithFee) offset-tracking logic to reserve enough trailing slots for *all* pending context-account fields before consuming any of them, e.g. compute the number of expected trailing context/sysvar fields up front and only start `parse_signers` after confirming `account_indexes.len()` is sufficient for all of them; otherwise mark the whole parse as unparsable/fallback to raw display rather than silently reassigning a context-state account index to `"owner"`.

### Proof of Concept
```rust
// transaction-status/src/parse_token/extension/confidential_transfer.rs (test module)
#[test]
fn test_withdraw_boundary_misattribution() {
    let account_indexes: Vec<u8> = vec![0, 1, 2, 3]; // len == 4, the check_num_token_accounts minimum
    let account_keys_vec: Vec<Pubkey> = (0..4).map(|_| Pubkey::new_unique()).collect();
    let account_keys = AccountKeys::new(&account_keys_vec, None);

    // WithdrawInstructionData with both offsets == 0 (spec expects 5 accounts:
    // account, mint, equalityCtx, rangeCtx, owner)
    let withdrawal_data = WithdrawInstructionData {
        amount: 42.into(),
        decimals: 9,
        new_decryptable_available_balance: Default::default(),
        equality_proof_instruction_offset: 0,
        range_proof_instruction_offset: 0,
    };
    let instruction_data = encode_instruction(
        ConfidentialTransferInstruction::Withdraw,
        &withdrawal_data,
    );

    let parsed = parse_confidential_transfer_instruction(
        &instruction_data,
        &account_indexes,
        &account_keys,
    )
    .unwrap();

    // BUG: rangeProofContextStateAccount is silently dropped
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());
    // BUG: account_keys[3] (intended as rangeCtx per 5-account spec) is mislabeled "owner"
    assert_eq!(
        parsed.info["owner"],
        json!(account_keys_vec[3].to_string())
    );
}
```
Expected assertions: with `account_indexes.len()==4` and both offsets `0`, `rangeProofContextStateAccount` is missing from the parsed JSON and `owner` incorrectly reports `account_keys[3]`, demonstrating the misattribution described.
