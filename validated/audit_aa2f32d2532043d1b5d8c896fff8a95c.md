### Title
EI credentials bypass "EIs not allowed" restriction to trigger arbitrary jobs by numeric ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates numeric-ID job runs with `_, isUser := auth.GetAuthenticatedUser(c)`, intending (per the inline comment) to block External Initiator (EI) credentials from running jobs by int32 ID. However, `AuthenticateExternalInitiator` in `core/web/auth/auth.go` also calls `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})`, so `GetAuthenticatedUser` returns `ok=true` for EI-only authenticated requests, making `isUser` true and defeating the intended restriction.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered in `core/web/router.go` under the `userOrEI` group, which accepts `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession`, wrapped with `auth.RequiresRunRole`: [1](#0-0) 

Inside `PipelineRunsController.Create`, the code explicitly comments that "only users are allowed to run jobs using int IDs - EIs not allowed" and gates on `isUser`: [2](#0-1) 

But `AuthenticateExternalInitiator` sets the same `SessionUserKey` used by `GetAuthenticatedUser` to a synthetic `User{Role: UserRoleRun}`: [3](#0-2) 

And `GetAuthenticatedUser` simply checks for the presence of that key/type, with no way to distinguish a real session/token user from an EI-synthesized user: [4](#0-3) 

As a result, a request authenticated purely via `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers will have `isUser == true`, entering the numeric-ID branch and calling `prc.App.RunJobV2(ctx, jobID, nil)` for **any** job ID, with no check that the EI is associated with, or authorized for, that specific job. This is a real logic contradiction between the comment's intended invariant and the actual code behavior — `isUser` does not, and cannot, distinguish "true user" from "EI masquerading as run-role user," because both populate the identical context key with the identical concrete type.

### Impact Explanation
This corresponds to Chainlink's **authorization bypass / unauthorized job run** impact class. Normally, External Initiator credentials are scoped to trigger a specific webhook job (validated by EI-specific secrets tied to that job's spec). Here, any valid EI credential — even one issued for an unrelated job — can invoke `RunJobV2` for an arbitrary job by iterating/guessing int32 job IDs, since no job-EI binding check exists in this code path. This allows an EI credential holder to trigger runs of OCR/other non-webhook jobs they have no legitimate relationship to, going beyond the intended scope of their credential.

### Likelihood Explanation
Preconditions are minimal: possession of any valid EI access key/secret pair (issued for any job) is sufficient — no user session, API token, or admin access needed. The attack requires only knowledge or guessing of a target job's int32 ID (job IDs are small sequential integers, easily enumerable). The request is a single unauthenticated-relative-to-the-target-job POST, fully repeatable.

### Recommendation
Distinguish EI-authenticated requests from genuine user requests. Options: (1) use a separate context key/sentinel for EI-synthesized users (or check `GetAuthenticatedExternalInitiator(c)` is absent) rather than relying solely on `GetAuthenticatedUser`; (2) explicitly check `if _, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI { reject }` before checking `isUser`; (3) restore per-job EI authorization scoping for the numeric-ID run path.

### Proof of Concept
Handler/integration test plan (Go, using `cltest` app harness similar to `core/web/pipeline_runs_controller_test.go`):
1. Create an application, insert an `ExternalInitiator` record with known access key/secret via `bridges.ExternalInitiator` fixtures.
2. Create an unrelated OCR (or any non-webhook) job via `app.AddJobV2`, capturing its int32 `jb.ID`.
3. Issue `POST /v2/jobs/{jb.ID}/runs` setting only `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers (no session cookie, no API token).
4. Assert the response is `200 OK` with a `pipelineRun` resource (bug present) instead of the expected `422 Unprocessable Entity` ("bad job ID") that the "EIs not allowed" comment implies should occur.
5. As a white-box unit check, add a `TestPipelineRunsController_Create_EICanRunByNumericID` verifying `RunJobV2` was invoked (e.g., via a run-count/side-effect check) after EI-only authentication.

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
