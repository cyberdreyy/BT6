### Title
Instant-withdraw receipt bookkeeping is never cleared on funded claims, permanently inflating default-epoch claim basis and freezing recovery funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug class is "accounting updated in the wrong place / storage bookkeeping not committed," producing a mismatch between recorded balances and actual ownership. The analog in idle-tranches is `IdleCreditVault`: per-epoch instant-withdraw receipt accounting (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) is incremented on every `requestInstantWithdraw` but is **never decremented** when the receipt is funded and successfully claimed. This stale basis is later counted in `defaultPendingClaimBasis()` during `finalizeDefaultRecovery`, diluting the recovery price, permanently freezing part of `defaultRecoveryReserve`, and causing `_claimDefaultedInstantWithdrawRequest` to revert for users whose receipts were already paid.

### Finding Description
`requestInstantWithdraw` records three pieces of state: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]` [1](#0-0) .

`collectInstantWithdrawFunds` decrements only `pendingInstantWithdraws` [2](#0-1) . `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]`, zeroes that mapping, and pays the user — but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` untouched [3](#0-2) .

At default finalization, `defaultPendingClaimBasis()` adds the **entire** `instantWithdrawClaimsByEpoch[epochNumber]` — including already-claimed-and-paid receipts — whenever `pendingInstantWithdraws != 0` [4](#0-3) . `finalizeDefaultRecovery` then computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over this inflated basis [5](#0-4) . The phantom entries can never be claimed: `_claimDefaultedInstantWithdrawRequest` subtracts `claimBasis` from an already-zeroed `instantWithdrawsRequests[_user]` (underflow revert) [6](#0-5) .

### Impact Explanation
Two direct fund impacts:

1. **Dilution of honest claimants**: `recoveryPrice` is computed over an inflated `totalBasis`, so every genuine defaulted-epoch receipt (normal, APR0, and unfunded instant claims) and active LP basis receives a smaller pro-rata share of the recovered funds than it should.
2. **Permanent freezing of recovery reserve**: the phantom basis has no claimant (claims for already-paid receipts revert on the `instantWithdrawsRequests[_user] -= claimBasis` underflow). The portion of `defaultRecoveryReserve` allocated to phantom claims can never leave via `_transferDefaultRecovery` [7](#0-6)  and stays locked in the strategy forever.

The frozen amount equals `staleClaimedBasis * defaultRecoveryPrice / 1e18`, i.e., proportional to the total instant withdrawals claimed and paid earlier in the defaulted epoch.

### Likelihood Explanation
Requires a specific but plausible sequence: during epoch N at least one instant-withdraw receipt is funded via `collectInstantWithdrawFunds` and claimed via `claimInstantWithdrawRequest`, while at epoch end some instant receipts remain unfunded (`pendingInstantWithdraws != 0` — explicitly contemplated by the code comments: "startEpoch moved the CDO's available cash to the strategy but that cash covered only part of the instant queue"), then the borrower defaults and `finalizeDefaultRecovery` is called. An unprivileged attacker can deliberately create the stale entry by requesting and claiming an instant withdrawal in the epoch that subsequently defaults — no privileged action needed for the inflation itself; the honest borrower/default and unfunded remainder are environmental conditions outside the attacker's control but not required to be malicious.

### Recommendation
- In `claimInstantWithdrawRequest`, decrement `instantWithdrawClaimsByEpoch[epoch]` for each receipt being paid (this requires tracking per-epoch breakdown or iterating/clearing `instantWithdrawsRequestsByEpoch` entries as they are claimed).
- Alternatively, in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`, subtract already-claimed receipts so only unfunded or funded-but-unclaimed receipts form the recovery basis.
- In `_claimDefaultedInstantWithdrawRequest`, use saturating subtraction (`claimBasis >= instantWithdrawsRequests[_user] ? 0 : ...`) consistent with the existing `pendingInstantWithdraws` clamp, so stale entries cannot brick the claim path.

### Proof of Concept
Foundry fork PoC sketch against `IdleCDOEpochVariant` + `IdleCreditVault`:

```solidity
function test_staleInstantReceiptInflatesDefaultBasis() external {
    // 1. Deposit AA so the CDO holds strategy tokens.
    idleCDO.depositAA(100_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);               // epoch N running

    // 2. Attacker (KYC'd user A) and victim (user B) request instant withdraws.
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    _depositWithUser(victim,   10_000 * ONE_SCALE, true);
    vm.prank(attacker); cdoEpoch.requestInstantWithdraw(0, address(AAtranche)); // or user tranche
    vm.prank(victim);   cdoEpoch.requestInstantWithdraw(0, address(AAtranche));

    uint256 epochN = creditVault.epochNumber();

    // 3. Only the attacker's receipt is funded and claimed in-epoch.
    uint256 attackerReq = creditVault.instantWithdrawsRequests(attacker);
    // borrower/CDO provides funds for attacker's receipt only
    vm.prank(address(cdoEpoch)); // via CDO flow
    creditVault.collectInstantWithdrawFunds(attackerReq);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    // attacker's receipt PAID, but:
    assertGt(creditVault.instantWithdrawsRequestsByEpoch(attacker, epochN), 0); // stale
    assertGt(creditVault.instantWithdrawClaimsByEpoch(epochN), attackerReq);     // stale
    // pendingInstantWithdraws still > 0 because victim's receipt is unfunded
    assertGt(creditVault.pendingInstantWithdraws(), 0);

    // 4. Borrower defaults in epoch N; owner finalizes recovery.
    _startEpochAndCheckPrices(0);
    // borrower repays less / defaults -> manager calls stopEpochWithDuration/_handleBorrowerDefault
    // owner then calls finalizeDefaultRecovery with recoveredAmount
    uint256 basis = creditVault.defaultPendingClaimBasis();
    // basis includes attacker's already-paid attackerReq -> inflated
    assertGt(basis, victimUnfundedReceipt + activeBasis);

    // 5. Victim claims recovery -> receives less than fair share
    //    (recoveryPrice diluted by attackerReq).
    // 6. Anyone calling claimInstantWithdrawRequest for attacker post-finalization
    //    reverts (underflow on instantWithdrawsRequests[attacker] -= claimBasis).
    // 7. defaultRecoveryReserve retains attackerReq * defaultRecoveryPrice / 1e18
    //    forever — permanent freezing of recovered funds.
}
```

The broken invariant is "one receipt one payout": the paid receipt remains counted as outstanding claim basis, which both steals recovery value from honest claimants (dilution) and permanently locks the corresponding slice of `defaultRecoveryReserve`. Existing guards (`_onlyIdleCDO`, `defaultRecoveryFinalized` checks, `pendingInstantWithdraws != 0` gate) do not prevent it, because the stale entries are written by the contract's own claim path.
