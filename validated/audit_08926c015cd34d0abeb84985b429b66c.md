### Title
Unbounded acceptance of stale `StateMachineUpdate` gossip lets a single signer overwrite its own fresher miner/burn-view vote in every peer's global-state tally - ([File: libsigner/src/v0/signer_state.rs])

### Summary
The Chainlink report's root cause is generic: a value obtained from an external/peer source is consumed and trusted without checking that it is the *most recent, valid* value (`roundId`/`answeredInRound`/`updateTime` are never compared). The direct analog in this repo is `GlobalStateEvaluator::insert_update`, which is the only gate applied to a peer signer's `StateMachineUpdate` before it is folded into the weighted "global state" that other signers rely on to accept or reject a miner's block proposal (v2 `GlobalStateView::check_proposal`). That function performs no freshness/ordering check whatsoever on the incoming content.

### Finding Description
`GlobalStateEvaluator::insert_update` unconditionally replaces whatever update is currently stored for a signer's address as soon as any weight-carrying entry exists for that address: [1](#0-0) 

There is no comparison against the previously stored update for that address — no burn-block-height monotonicity check, no sequence/nonce, no timestamp comparison. The caller, `handle_state_machine_update`, simply persists and forwards whatever content arrives on the wire for that signer's slot: [2](#0-1) 

The persistence layer (`SignerDb::insert_state_machine_update`) is the same story — `INSERT OR REPLACE` keyed only by `(signer_addr, reward_cycle)`, again with no ordering guard on the *content* of the update, only the wall-clock time the local receiver happened to observe it: [3](#0-2) 

This aggregated, unchecked state feeds `determine_global_state()`, which is the sole input to the v2 consensus-critical check that decides whether a proposed block's miner/tenure is legitimate: [4](#0-3) [5](#0-4) [6](#0-5) 

Because `StateMachineUpdate::new` only enforces that the *content version* matches the negotiated protocol version — never that the *content itself* (burn block, burn height, current miner) is newer than a previously-broadcast value from the same signer — a signer is free to publish (with a perfectly valid, freshly incremented StackerDB slot version and a valid signature) a `StateMachineUpdateContent` describing an **older** burn view or an **older/incorrect current miner** than what it previously broadcast: [7](#0-6) 

Every peer that receives this message overwrites its tally entry for that signer with the stale content, exactly as the Chainlink oracle consumer overwrote its cached price with unstale-checked `latestRoundData()` output. This directly breaks the "aggregated-weight vs verified" equality: the weighted tally used to determine `determine_global_state()` no longer reflects each signer's most recently *verified* (freshest) view, only their most recently *received* one.

### Impact Explanation
This does not require a majority of signers — only the sender of the stale update needs to control their own signer identity/slot (in-scope: "a one-slot miner (plus gossip) can trigger"). While a single stale vote alone cannot flip an already-settled 70%/30% threshold outright, it can:
- Prevent a burn-view / miner-agreement threshold from being reached at all when the tally is near the boundary (since the stale vote no longer matches the honest majority's fresh view), stalling `determine_global_state()` into `None` and causing `check_block_against_global_state` to reject with `NoSignerConsensus` — a liveness wedge (signer wedged into never validating/signing a currently-valid block while waiting on a state that will never resolve, matching the "High" impact class: "wedged into never signing valid blocks... acting on a stale reward set/threshold").
- Feed a stale `current_miner`/`tenure_id` back into the tally that other signers use for `GlobalStateView::check_proposal`'s consensus-hash/pubkey-hash gate, increasing the chance that the aggregate view diverges from the canonical burn chain during a fast-moving burn-block transition, which is exactly the class of “equality broken” (aggregated-weight vs verified-accepts) called out in scope.

### Likelihood Explanation
High reachability, since the only requirement is possession of one registered signer identity and the ability to publish a `StateMachineUpdate` to one's own StackerDB slot — a routine, expected message type that every signer sends regularly. No cryptographic bypass or majority collusion is needed; the flaw is that `insert_update`/`insert_state_machine_update` trust content freshness implicitly rather than verifying it, precisely the missing-staleness-check pattern from the source report.

### Recommendation
Add a monotonicity/freshness check before accepting a peer's `StateMachineUpdate` into the tally, analogous to the Chainlink fix's `answeredInRound >= roundId` check:
- Reject (or ignore for tallying purposes) any incoming update whose `burn_block_height` is lower than the previously accepted `burn_block_height` for that same signer address, unless the local receiver can independently confirm a legitimate bitcoin-fork rationale (mirroring the fork-descendency check already used in `LocalStateMachine::handle_possible_bitcoin_fork` for one's own local state).
- Alternatively, carry an explicit monotonic sequence number or wall-clock timestamp inside `StateMachineUpdateContent` itself (rather than relying only on the StackerDB slot version, which the sender controls) and enforce it in `GlobalStateEvaluator::insert_update`.

### Proof of Concept
1. Signer `S` (a normal registered signer, one slot) observes the canonical burn tip at height `H` and, per normal operation, broadcasts `StateMachineUpdate{ burn_block_height: H, current_miner: A }` — peers store this via `handle_state_machine_update` → `insert_update` (`libsigner/src/v0/signer_state.rs:161`).
2. `S` (buggy, compromised, or malicious) subsequently constructs and signs a new, higher-slot-version `StateMachineUpdate{ burn_block_height: H-1, current_miner: B }` (a state it validly held earlier, or fabricated data referencing a still-existent past sortition) and republishes it.
3. Every peer signer's `handle_state_machine_update` (`stacks-signer/src/v0/signer.rs:1082`) accepts this newer-slot-version but older-content message with no check, and `insert_update` overwrites `S`'s entry in `address_updates` with the stale `H-1`/`B` view.
4. `determine_global_state()` (`libsigner/src/v0/signer_state.rs:102`) now tallies `S`'s vote against the stale view rather than the honest, current view, which can suppress reaching the 70% agreement threshold on burn height/current-miner right when the network needs to converge — causing `check_block_against_global_state` (`stacks-signer/src/v0/signer.rs:944`) to reject valid, canonical proposals with `NoSignerConsensus`, or pollute the aggregated tally used to gate proposal validity in `GlobalStateView::check_proposal` (`stacks-signer/src/chainstate/v2.rs:113`).

impl StateMachineUpdate {
    /// Create a `StateMachineUpdate` for **outbound** messages.
    ///
    /// The content version **must exactly match** the negotiated protocol version:
    /// `min(active_signer_protocol_version, local_supported_signer_protocol_version)`.
    ///
    /// This ensures the message we send conforms strictly to what both sides have agreed upon.
    pub fn new(
        active_signer_protocol_version: u64,
        local_supported_signer_protocol_version: u64,
        content: StateMachineUpdateContent,
    ) -> Result<Self, CodecError> {
        let negotiated =
            active_signer_protocol_version.min(local_supported_signer_protocol_version);
        let version = content.version();

        if version != negotiated {
            return Err(CodecError::DeserializeError(format!(
                "Outbound content version {version} does not match negotiated protocol version {negotiated} \
                 (active={active_signer_protocol_version}, local_supported={local_supported_signer_protocol_version})"
            )));
        }

        Ok(Self {
            active_signer_protocol_version,
            local_supported_signer_protocol_version,
            content,
            no_manual_construct: PhantomData,
        })
    }
