### Title
No vulnerability found: nil-publicKey ciphertext label check on MethodSecretsUpdate is independently enforced downstream - (File: core/capabilities/vault/gateway_vault_request_processor.go)

### Summary
When `publicKey` is `nil` (before `MethodPublicKeyGet` has cached a key), `processUpdateSecretsRequest` does pass `nil` into `ValidateUpdateSecretsRequest`, and label/ciphertext-ownership verification is skipped at that specific validation layer. However, this is a documented, intentional design choice, and the ciphertext-to-owner binding is independently re-verified at two other, unrelated layers before any actual mutation can occur, so the described exploit chain does not achieve a scoped impact.

### Finding Description
`GatewayVaultRequestProcessor.ProcessRequest` dispatches `MethodSecretsUpdate` to `processUpdateSecretsRequest`, which computes `skipLabelValidation := publicKey == nil` and calls `ValidateUpdateSecretsRequest(ctx, publicKey, &updateReq, skipLabelValidation)`. [1](#0-0)  Inside `validateWriteRequest`, when `skipLabelValidation` is true, `verifyEncryptedSecret(publicKey, ...)` is called, and `verifyEncryptedSecret` explicitly returns `nil, nil` (no error) when `publicKey == nil`, with the comment: "Public key can be nil if gateway cache isn't populated yet ... Ok to not validate in such cases, since this validation also runs on Vault Nodes." [2](#0-1)  `EnsureRightLabelOnSecret` has the identical nil-safe skip behavior with a matching doc comment. [3](#0-2) 

Critically, this skip is not the only checkpoint. Before the request even reaches the validator, `AuthorizeRequest` (called from `authorizeAndStamp`, which every gateway-vault request goes through) independently enforces `validateSecretOwnersMatchAuthorized`, which parses the raw params and rejects the request if `EncryptedSecrets[i].Id.Owner` doesn't match the authenticated caller's `workflowOwner` derived from either the allowlist or JWT auth layer. [4](#0-3) [5](#0-4)  This check is unrelated to `publicKey` and independently binds the claimed `Owner` field to the authenticated caller, regardless of whether the ciphertext-label check ran.

Additionally, the actual TDH2 ciphertext-to-label verification (`EnsureRightLabelOnSecret`) is re-executed by the OCR reporting plugin (`ReportingPlugin.validateEncryptedSecretLabel`) using the vault DON's own `r.cfg.PublicKey` — not the gateway's cached copy — during `Observation`/`ValidateObservation`, before any secret is actually written or updated in the vault KV store. [6](#0-5)  This is confirmed by tests showing label mismatches are rejected at the plugin/observation layer even when the gateway forwarded the request. [7](#0-6) 

So while `publicKey=nil` does momentarily bypass the gateway-side ciphertext-label check, (1) the owner-binding check in `AuthorizeRequest` is unaffected and always enforced, and (2) the actual DON-side node consensus process re-verifies the ciphertext label against the real, non-attacker-influenced master public key before persisting anything.

### Impact Explanation
No exploitable impact. Even in the race window before the gateway public key cache populates, the request cannot forward with unverifiable ciphertext ownership to a scoped/impactful outcome: owner mismatch is rejected by `AuthorizeRequest` regardless of `publicKey`, and any label/ciphertext forgery is independently caught by DON nodes at the OCR plugin observation stage, which use their own key material, before secret mutation occurs.

### Likelihood Explanation
Not applicable — there is no exploitable outcome. The precondition (gateway cache not yet populated) is real and unauthenticated-reachable, but the described bypass does not translate into unauthorized secret mutation because of the independent, defense-in-depth checks described above.

### Recommendation
No fix required for this specific claim. If desired for defense-in-depth clarity, the gateway could reject `MethodSecretsUpdate`/`MethodSecretsCreate` outright (rather than skip label validation) when `publicKey` is `nil`, forcing a retry after the key is cached — but this is a hardening/UX improvement, not a required security fix, since the DON-side validation already provides the actual security guarantee.

### Proof of Concept
Existing tests already cover the relevant boundary and confirm no unauthorized secret ends up processed: `TestAuthorizer_AllowListPath_RejectsUpdateOwnerMismatch` / `TestAuthorizer_JWTPath_RejectsOwnerMismatch` show owner-binding rejection independent of `publicKey`. [8](#0-7)  `TestPlugin_Observation_UpdateSecretsRequest_SecretLabelIsInvalid` shows the OCR plugin independently rejects a label mismatch at the DON layer regardless of what the gateway forwarded. [7](#0-6)  A supplementary unit test could call `ProcessRequest` for `MethodSecretsUpdate` with `publicKey=nil` and an `Owner` mismatching the authorized workflow owner, asserting rejection via `AuthorizeRequest`'s owner-binding check — this already passes today per `TestAuthorizer_AllowListPath_RejectsUpdateOwnerMismatch`.

// EnsureRightLabelOnSecret verifies that the TDH2 ciphertext label matches the workflow
// owner label (Ethereum address, left-padded to 32 bytes). owner must be non-empty;

func EnsureRightLabelOnSecret(publicKey *tdh2easy.PublicKey, secret, owner string) error {
	cipherText, err := verifyEncryptedSecret(publicKey, secret)
	if err != nil {
		return err
	}
	if cipherText == nil {
		return nil

func validateEncryptedSecretOwnerMismatch(encryptedSecrets []*vaultcommon.EncryptedSecret, workflowOwner string) error {
	if len(encryptedSecrets) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}
	for idx, encryptedSecret := range encryptedSecrets {
		if encryptedSecret == nil {
			return fmt.Errorf("encrypted secret must not be nil at index %d", idx)
		}
		if encryptedSecret.Id == nil {
			return fmt.Errorf("secret ID must not be nil at index %d", idx)
		}
		if vaultutils.NormalizeOwner(encryptedSecret.Id.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("encrypted secret owner at index %d %q does not match authorized workflow owner %q", idx, encryptedSecret.Id.Owner, workflowOwner)
		}
	}
	return nil
}
