### Title
Post-default instant withdraw requests are not handled by recovery accounting and drain (or corrupt) the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` has a dedicated post-default branch: once `defaultRecoveryFinalized` is set, new requests are haircut at request time and tracked in `postDefaultRequests`, paid 1:1 from `defaultRecoveryReserve`. `requestInstantWithdraw` has no equivalent branch. It unconditionally mints a receipt and records it under the *current* `epochNumber` — which still equals `defaultRecoveryEpoch` after finalization — and increments `pendingInstantWithdraws`. On claim, `claimInstantWithdrawRequest` routes that fresh, fully-funded post-default receipt through `_claimDefaultedInstantWithdrawRequest`, which (a) pays it at the defaulted recovery haircut from `defaultRecoveryReserve` (stealing reserve earmarked for defaulted-epoch claimants) and (b) mutates `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch[defaultEpoch]` for an epoch whose accounting was already closed, which can underflow and permanently brick all remaining default claims.

### Finding Description
The asymmetry is the analog of the reported "missing instruction handling" bug: one request type (`requestWithdraw`) handles the `defaultRecoveryFinalized` state, the other (`requestInstantWithdraw`) silently falls through.

- `requestWithdraw` checks `defaultRecoveryFinalized` and routes to `postDefaultRequests` [1](#0-0) 
- `requestInstantWithdraw` has no `defaultRecoveryFinalized` check; it records the receipt into `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and bumps `pendingInstantWithdraws` [2](#0-1) 
- `epochNumber` is only incremented inside `deposit()` when `isEpochRunning()` is true [3](#0-2) . After default finalization no epoch is running, so `epochNumber == defaultRecoveryEpoch` and the new receipt lands in the already-finalized default-epoch bucket.
- `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest` whenever `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` [4](#0-3) , which clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`, pays `claimBasis * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve`, and clamps `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch[defaultEpoch]` [5](#0-4) .

Two failure modes follow:

1. **Recovery reserve theft / haircut of funded receipt.** If the CDO prefunds the post-default instant request via `collectInstantWithdrawFunds`, the strategy holds the underlying, but the claim path pays only `recoveryPrice` of it out of `defaultRecoveryReserve` — consuming reserve that belongs to defaulted-epoch claimants, while the funded remainder stays stuck in the strategy.
2. **Accounting underflow / permanent freeze.** `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` underflows once all genuine defaulted-epoch instant receipts have been claimed (the bucket reaches 0, but a later post-default receipt is still recorded under `defaultEpoch`), reverting every subsequent defaulted instant claim. Similarly `pendingInstantWithdraws` is clamped to 0, desynchronizing `defaultPendingClaimBasis()` for any later accounting.

### Impact Explanation
Broken invariant: **one receipt one payout** and **donation/reserve isolation**. Either post-default instant claimants are paid the wrong amount from the wrong source (direct loss of `1 - defaultRecoveryPrice` of their funded claim, plus theft of other users' recovery reserve), or `instantWithdrawClaimsByEpoch` underflows and permanently freezes all remaining default recovery claims. Quantified loss: up to the full `defaultRecoveryReserve` drained by post-default claimants, or 100% of residual defaulted-epoch claims frozen.

### Likelihood Explanation
Requires (i) the vault to be in `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` state (borrower default finalized with unfunded instant receipts — an intended, supported state per `defaultInstantWithdrawsFinalized`) and (ii) the CDO to still permit `requestInstantWithdraw` after operations are restored (`restoreOperations` / post-default pool activity is an in-scope flow). No privileged misbehavior is needed: any KYC'd tranche holder requesting an instant withdraw post-finalization triggers it. Uncertainty: whether `IdleCDOEpochVariant`/`Prefunded` gates instant withdraw requests off entirely once `defaulted()` is set — if it does, the bug is latent rather than live; this could not be fully verified in the available context.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert the request or record it under a distinct post-default bucket (e.g., `postDefaultRequests`-style accounting) so it is never mixed into `instantWithdrawsRequestsByEpoch[defaultRecoveryEpoch]`. In `claimInstantWithdrawRequest`, skip `_claimDefaultedInstantWithdrawRequest` for receipts created after `defaultRecoveryEpoch` (or key defaulted claims by `epoch <= defaultRecoveryEpoch` at finalization time). As defense-in-depth, revert on any unhandled combination rather than silently defaulting to the default-epoch bucket.

// borrower defaults; owner/manager finalize default recovery.
// defaultRecoveryFinalized = true, defaultInstantWithdrawsFinalized = true,

// 1) Honest defaulted claimants partially claim; instantWithdrawClaimsByEpoch[defaultEpoch] -> 0.

strategy.claimInstantWithdrawRequest(userA);

// 2) Operations restored. Attacker/user B (KYC'd LP) requests instant withdraw post-default.
vm.prank(cdo);
strategy.requestInstantWithdraw(100e18, userB);

// 3) CDO prefunds it (collectInstantWithdrawFunds pulls 100e18 into strategy).

vm.prank(cdo);
strategy.claimInstantWithdrawRequest(userB);
// BUG A: userB receives 100e18 * 0.5e18/1e18 = 50e18 paid out of defaultRecoveryReserve
//        (stealing defaulted claimants' reserve; the prefunded 100e18 stays stranded).
// BUG B: instantWithdrawClaimsByEpoch[defaultEpoch] underflows (0 - 100e18) -> revert,

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user

    _burn(_user, amount);

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
