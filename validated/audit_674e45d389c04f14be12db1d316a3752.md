### Title
Stale Rejection Weight From a Flip-Flopping Signer Corrupts the Approve/Reject Weight Partition - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` tracks each block's aggregated signer weight in two separate accumulators, `total_weight_approved` and `total_weight_rejected`, which the mining coordinator treats as a strict partition of the signer set (each signer's weight should count toward at most one side). The de-duplication guards for the two branches are inconsistent: the accept path dedups against `gathered_signatures`, while the reject path dedups against `responded_signers` — and only the accept branch unconditionally marks the signer as "responded." A single signer that sends `Reject` and later `Accept` for the same block gets its weight added to `total_weight_rejected` and (independently) to `total_weight_approved`, permanently corrupting the invariant that the two weight totals are mutually exclusive.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- Accept branch (`BlockResponse::Accepted`): [1](#0-0) 
adds weight to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, then unconditionally does `block.responded_signers.insert(slot_id)`.

- Reject branch (`BlockResponse::Rejected`): [2](#0-1) 
adds weight to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot is seen in `responded_signers`).

Because the accept branch checks `gathered_signatures` (a different collection from `responded_signers`) before crediting weight, the following sequence from a single, honest-looking signer (one StackerDB slot, no other signer's key needed) corrupts the accounting:

1. Signer sends `Reject` first → `responded_signers.insert(slot_id)` succeeds → `total_weight_rejected += weight`.
2. The same signer later sends `Accept` for the same block (e.g., after re-evaluating pre-commit/validation state, as the signer-side state machine explicitly allows late signing once earlier conflicts go stale — see `docs/signer-flows.md` section 5 and the sibling-conflict tests in `stacks-signer/src/v0/tests.rs`) → the check is against `gathered_signatures`, which does *not* contain the slot yet → `total_weight_approved += weight` is applied a second time using the same signer's weight.

The reverse order (`Accept` then `Reject`) is correctly guarded, because the accept branch also inserts into `responded_signers`, so the later reject's `insert` returns `false` and no weight is added — but the `Reject`-then-`Accept` order is not guarded at all. `total_weight_rejected` never gets decremented or cleared, so it permanently retains weight from a signer who has since accepted.

### Impact Explanation
`signer_coordinator.rs` uses `total_weight_rejected` directly to decide whether the block is dead: `block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` triggers `NakamotoNodeError::SignersRejected`, which aborts the current block-building attempt and permanently/temporarily excludes transactions based on `info.total_weight`/`info.problematic_weight` accumulated the same stale way. [3](#0-2) 
Because `total_weight_rejected` can hold weight from a signer who has already flipped to `Accept`, the coordinator can wrongly conclude a supermajority rejects a block (and exclude transactions as "problematic") even though the live signer sentiment supports it. This is a liveness impact on block production (spurious `SignersRejected` aborts and incorrect, possibly permanent, txid exclusion) driven purely by a single signer's own message ordering — no majority collusion, no other signer's key, and no special access is required.

### Likelihood Explanation
This requires only one misbehaving/flip-flopping signer sending its own two StackerDB messages (`Reject` then `Accept`) for the same block signature hash — well within the signer-side logic's own documented behavior of refusing to sign and later signing once conflicting state times out (as shown by tests in `stacks-signer/src/v0/tests.rs` such as `stale_sibling_replaced_when_canonical_tip_below`). No StackerDB sync exploitation or transport trickery is needed beyond normal message posting; both messages are legitimately signed by the actual signer key and pass signature verification in the listener.

### Recommendation
Make the two branches dedup against the same tracking set, and make the reset symmetric: gate the accept branch's weight increment on `block.responded_signers.insert(slot_id)` (or check both `gathered_signatures` and `responded_signers`) so a signer's weight can only ever be counted once, in the state matching its most recent (or first, per chosen policy) response, and never simultaneously in both `total_weight_approved` and `total_weight_rejected`.

### Proof of Concept
1. Node proposes a block; signer S (single StackerDB slot, weight W) sends `BlockResponse::Rejected` for `signer_signature_hash = H`. `stackerdb_listener.rs` line 515-518 adds `W` to `total_weight_rejected` and inserts S's slot into `responded_signers`.
2. Same signer S later sends `BlockResponse::Accepted` for the same `H` (its own local state machine allowed this, e.g., after a competing sibling's signature went stale per `stacks-signer/src/v0/signer.rs` conflict-resolution logic).
3. In the listener, `block.gathered_signatures.contains_key(&slot_id)` is `false` (never populated by the earlier reject), so lines 443-465 add `W` again, this time to `total_weight_approved`.
4. Now `total_weight_approved + total_weight_rejected` exceeds the real distinct signer weight that has taken a position, and `total_weight_rejected` retains `W` indefinitely even though S currently accepts — causing `signer_coordinator.rs` (lines 509-540) to potentially fire `SignersRejected` using stale/inflated rejection weight.
