### Title
Unprivileged Front-Running of `BridgeCommittee.initializeConfig` Allows Attacker to Inject Malicious Bridge Config - (`bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig` is an `external` function with no caller restriction. Its only guard is a one-time check that `config == address(0)`. Because the deployment script sends `BridgeCommittee.initialize` and `initializeConfig` as separate on-chain transactions, any unprivileged EOA can front-run the second call and permanently bind the committee to an attacker-controlled `IBridgeConfig` contract, redirecting all bridge token-address lookups, chain-ID checks, and price queries through attacker-controlled logic.

---

### Finding Description

`BridgeCommittee` is deployed in two distinct on-chain steps:

**Step 1** — proxy deployment with `initialize()`, which is protected by OpenZeppelin's `initializer` modifier and cannot be replayed: [1](#0-0) 

**Step 2** — a separate transaction calling `initializeConfig()` to wire in the `BridgeConfig` address: [2](#0-1) 

The function is `external` with no `onlyOwner`, no `msg.sender` check, and no role guard — only the one-time `config == address(0)` check. The deployment script confirms these are two separate broadcast transactions: [3](#0-2) 

Between the two transactions there is an open window. Any observer of the mempool can submit `initializeConfig(maliciousConfig)` with higher gas and have it mined first. The deployer's subsequent call then reverts with `"BridgeCommittee: Config already initialized"`, leaving the committee permanently bound to the attacker's contract.

The `config` object is the root of trust for every bridge operation in `SuiBridge`: [4](#0-3) 

`committee.config()` is called to resolve token addresses, chain IDs, and decimal conversions on every `transferBridgedTokensWithSignatures`, `bridgeERC20`, and `bridgeETH` call.

---

### Impact Explanation

A malicious `IBridgeConfig` can:

1. **Return attacker-controlled token addresses** from `tokenAddressOf()` — causing `vault.transferERC20` to transfer vault-held assets to an address the attacker controls, draining the vault on every legitimate committee-signed transfer message.
2. **Return `true` from `isChainSupported`** for arbitrary chain IDs — bypassing the `onlySupportedChain` modifier and allowing replay of messages from unsupported chains.
3. **Return a wrong `chainID()`** — breaking the target-chain verification inside `transferBridgedTokensWithSignatures`, allowing cross-chain message confusion.
4. **Return manipulated `tokenSuiDecimalOf`** — corrupting decimal conversion so that amounts transferred from the vault are inflated or deflated.

The net effect is that every committee-signed bridge message — which the real validators sign in good faith — executes against attacker-controlled routing logic, enabling direct theft of all ERC-20 and ETH assets held in `BridgeVault`. This matches the Critical impact class: **bridge governance bypass that enables illegitimate unlock of bridged assets**.

---

### Likelihood Explanation

- The vulnerability window exists on every mainnet deployment and every future upgrade that re-deploys `BridgeCommittee`.
- The attack requires only a standard EOA and knowledge of the pending deployment transaction (visible in the public mempool).
- MEV infrastructure makes front-running of known deployment sequences routine.
- No special privilege, stake, or committee membership is required.

---

### Recommendation

Remove the two-step initialization pattern. Pass the `BridgeConfig` address directly into `initialize()` and set `config` there, under the protection of the `initializer` modifier:

```solidity
function initialize(
    address[] memory committee,
    uint16[] memory stake,
    uint16 minStakeRequired,
    address _config          // add this
) external initializer {
    __CommitteeUpgradeable_init(address(this));
    __UUPSUpgradeable_init();
    // ... existing committee setup ...
    require(_config != address(0), "BridgeCommittee: Invalid config");
    config = IBridgeConfig(_config);
}
```

If a two-step flow is unavoidable (e.g., circular dependency between `BridgeCommittee` and `BridgeConfig`), restrict `initializeConfig` to the deployer:

```solidity
address private immutable _deployer;
constructor() { _deployer = msg.sender; }

function initializeConfig(address _config) external {
    require(msg.sender == _deployer, "BridgeCommittee: Not deployer");
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

### Proof of Concept

1. Deployer broadcasts `BridgeCommittee.initialize(committee, stake, minStake)` — transaction is visible in the mempool.
2. Attacker deploys `MaliciousConfig` implementing `IBridgeConfig`, where `tokenAddressOf(tokenID)` returns an attacker-controlled ERC-20 wrapper that re-routes vault withdrawals.
3. Attacker broadcasts `BridgeCommittee(proxy).initializeConfig(address(maliciousConfig))` with higher gas — front-runs the deployer's `initializeConfig` call.
4. Deployer's `initializeConfig` reverts: `"BridgeCommittee: Config already initialized"`.
5. `SuiBridge` is deployed pointing to the now-poisoned `BridgeCommittee`.
6. Real validators sign a legitimate `TOKEN_TRANSFER` message for a user bridging ETH from Sui.
7. Anyone calls `transferBridgedTokensWithSignatures` with the valid signatures; `committee.config().tokenAddressOf(ETH)` returns the attacker's contract address; `vault.transferERC20(attackerAddress, recipient, amount)` drains vault funds to the attacker. [2](#0-1) [5](#0-4) [4](#0-3)
