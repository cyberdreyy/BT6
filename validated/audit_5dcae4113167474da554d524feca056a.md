## Finding

The clearest analog to the "acts on an unverified precondition, assuming success rather than confirming it" bug class from the HOPR report is in the signer's own-tenure conflict guard in `handle_block_pre_commit`, at the exact point where it asks the node whether a conflicting tenure has already been confirmed at or above the proposed block's height. [1](#0-0) 

### Title
Signer fail-opens into signing a same-tenure conflicting block when the tenure-tip RPC check errors - (File: stacks-signer/src/v0/signer.rs)

### Summary
When the pre-commit threshold is reached for a block that conflicts (same `consensus_hash`, i.e. same tenure) with a block the signer already signed/accepted, the signer must first confirm that tenure hasn't already been canonically confirmed at or above the proposed height before signing the replacement. That confirmation is done via `stacks_client.get_tenure_tip`. If that RPC call errors, the code does not refuse to sign or treat the check as inconclusive — it logs a warning ("Treating the tenure as unconfirmed") and falls through to sign the block anyway. [2](#0-1) 

### Finding Description
The relevant guard is documented in `docs/signer-flows.md` section 5 as: "own tenure confirmed at ≥ this height? `get_tenure_tip(own tenure)`" with branches `TIP -- yes --> HOLD2["refuse to sign"]` but `TIP -- "node unreachable" --> SIGN`. [3](#0-2) 

The actual implementation:
```rust
match stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash) {
    Ok(tip) => {
        let tip_height = tip.anchored_header.height();
        if tip_height >= block_info.block.header.chain_length {
            warn!("... Refusing to sign.");
            return;
        }
    }
    Err(e) => {
        warn!("... Treating the tenure as unconfirmed."); // falls through, does NOT return
    }
}
```
This is the direct structural analog of `gimmeToken`: `gimmeToken` proceeds with the reward transfer without verifying the precondition (that the contract actually holds pre-funded tokens) — it assumes the precondition holds and only discovers otherwise when the transfer itself fails. Here, the signer proceeds to sign a conflicting block without verifying the precondition (that the tenure isn't already confirmed at/above this height) — on any RPC failure it *assumes* the tenure is unconfirmed, rather than treating "unknown" as "possibly confirmed" and holding back the signature the way `HOLD1`/`HOLD2` do everywhere else in this same function for the general-conflict path.

Contrast this with the sibling check three call sites earlier in the same function, which is careful to fail closed: when `get_sortition_by_burn_hash` or `get_tenure_tip` cannot be reached, the code paths land on `HOLD1`/`HOLD2` ("refuse to sign") rather than `SIGN`. [4](#0-3) 

Only this one specific same-tenure/`reorg_permit`-denied branch fails open on RPC error, breaking the intended invariant that "a stale conflict in this block's own tenure still blocks if the node already has that tenure at or above the proposed height." [5](#0-4) 

### Impact Explanation
If the node's tenure-tip RPC transiently fails (timeout, connectivity hiccup, node restart mid-request — none of which require an adversary) at the moment the pre-commit threshold is reached for a same-tenure conflicting block, the signer will sign it even though the tenure it conflicts with was already confirmed at or above that height. This is exactly the "signer signing a conflicting block" case called out as Critical: it breaks the invariant that a signer never re-signs/duplicates state the node has already canonically built past in the same tenure, undermining the equality between "validated/confirmed" and "signed."

### Likelihood Explanation
No majority of signers, no attacker key, and no auth-token access is required. It only needs (a) the ordinary appearance of a same-tenure conflicting proposal reaching the pre-commit threshold — a normal occurrence during miner re-proposals/timeouts — combined with (b) any transient failure of the signer's local RPC call to its own node, which is a routine operational condition rather than an exotic attack. The rest of the same function treats RPC failure as "hold, don't sign" for every other conflict category, making this the one branch where an ordinary node hiccup silently converts into a fail-open signature.

### Recommendation
Change the `Err(e)` branch at `stacks-signer/src/v0/signer.rs:1449-1456` to refuse to sign (return without signing) rather than falling through, mirroring the fail-closed behavior of the sibling conflict-check branches (`HOLD1`/`HOLD2`) earlier in the same function. At minimum, treat an RPC error here the same way `conflict_still_blocks`'s "could not ask" branches are treated — as inconclusive, and therefore blocking — rather than as proof of non-confirmation.

### Proof of Concept
1. Signer previously signed/accepted block `A` in tenure `T` at height `h`.
2. Node's canonical tip for `T` in fact reaches height `h` (i.e., `A`, or something at/above it, is confirmed).
3. A new conflicting proposal `B` in the same tenure `T` at height `h` (or lower) reaches the pre-commit threshold; `reorg_permit_stands` returns false (no sanctioned reorg).
4. The signer calls `stacks_client.get_tenure_tip(T)`; the call errors (e.g., timeout).
5. Per `stacks-signer/src/v0/signer.rs:1449-1456`, the signer logs "Treating the tenure as unconfirmed" and proceeds to `mark_locally_accepted` and sign/broadcast `B`, producing a signature over a block that conflicts with the tenure's already-confirmed state — despite the code path existing specifically to prevent this.
