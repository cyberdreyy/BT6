### Title
Unfunded instant-withdraw receipts can be claimed at par, draining underlying reserved for funded withdraw receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out the full `instantWithdrawsRequests[_user]` balance without verifying that the request was ever funded via `collectInstantWithdrawFunds`. The only isolation guard, `_transferFundedClaim`, protects solely `defaultRecoveryReserve`, so an unfunded instant receipt can spend underlying that the strategy holds to back other users' already-funded normal withdraw receipts (`collectWithdrawFunds`) or funded instant receipts. This maps the "memory corruption / use of wrong state" bug class onto receipt accounting: the claim path reads a receipt balance that has no corresponding funded backing.

### Finding Description
- `requestInstantWithdraw` mints the user a receipt and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (IdleCreditVault.sol:356-375). Funding is a separate step: `collectInstantWithdrawFunds` decreases `pendingInstantWithdraws` and pulls tokens from the CDO (IdleCreditVault.sol:398-403).
- `claimInstantWithdrawRequest` then burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)` with no check that this user's receipt was funded — `pendingInstantWithdraws` is never consulted on the claim path (IdleCreditVault.sol:380-393).
- `_transferFundedClaim` only enforces `balance - defaultRecoveryReserve >= _amount` when `defaultRecoveryReserve != 0` (IdleCreditVault.sol:897-907). Before any default, `defaultRecoveryReserve == 0`, so the check is a no-op and any underlying sitting in the strategy is spendable by an instant claimant.
- Attack sequence (buffer/stopped phase, normal mode): victim's epoch-N withdraw request is funded — the CDO calls `collectWithdrawFunds`, so the strategy now holds underlying earmarked for `claimWithdrawRequest`. An unprivileged attacker (any tranche-token holder routing through the honest CDO) calls `requestInstantWithdraw` for amount X, then triggers `claimInstantWithdrawRequest` (or a later claim once the CDO retries). Since no funding check exists, the attacker receives X from the pool holding the victim's funded withdrawal; the victim's subsequent `claimWithdrawRequest` reverts on insufficient balance.
- Even post-default the guard is incomplete: it protects only `defaultRecoveryReserve`, not the separately-funded normal receipt pool.

### Impact Explanation
Direct theft of funded withdraw receipts: an attacker with an unfunded instant receipt can claim underlying collected for other users' funded normal/instant withdrawals. Loss is bounded by the strategy's underlying balance, i.e., the full amount funded-but-unclaimed at the time of the claim, and permanently freezes honest users' claims (their receipts can never be paid once the balance is drained).

### Likelihood Explanation
Requires the strategy to hold a positive underlying balance (funded receipts pending claim, or prefunded instant funds) while the attacker holds or creates an instant receipt. Instant-withdraw liquidity shortfalls are exactly the scenario `pendingInstantWithdraws` models, so unfunded receipts coexisting with funded pools is a normal operating state, not an edge case. No privileged action is needed.

### Recommendation
Track per-user (or per-epoch) funded instant claim basis and pay claims only against it. Concretely: in `collectInstantWithdrawFunds`, credit a `fundedInstantClaims` bucket; in `claimInstantWithdrawRequest`, cap the payout at `min(instantWithdrawsRequests[_user], fundedInstantClaims)` and decrement the bucket. Extend `_transferFundedClaim` (or add an analogous guard) so that instant claims cannot consume underlying reserved for pending funded normal receipts, e.g. by tracking an aggregate `fundedWithdrawsReserve` similar to `defaultRecoveryReserve`.

### Proof of Concept
Conceptual Foundry fork PoC (requires the standard `IdleCreditVault.t.sol` setup with a live CDO, borrower, and USDC-like underlying):

```solidity
// Setup: epoch running, victim deposits, epoch ends
// 1. Victim requests withdraw of 1000 USDC via CDO -> requestWithdraw
// 2. Borrower repays -> CDO calls strategy.collectWithdrawFunds(1000e6)
//    strategy now holds 1000e6 USDC earmarked for victim
// 3. Attacker (holds tranche tokens) requests instant withdraw of 500 USDC
//    via CDO -> strategy.requestInstantWithdraw(500e6, attacker)
//    pendingInstantWithdraws = 500e6, NO funds collected for attacker
// 4. CDO calls strategy.claimInstantWithdrawRequest(attacker)
//    -> _transferFundedClaim sees defaultRecoveryReserve == 0, no check
//    -> attacker receives 500e6 USDC
// 5. Victim calls CDO claimWithdrawRequest -> reverts:
//    strategy balance (500e6) < victim's claim (1000e6)
assertEq(underlying.balanceOf(attacker), attackerBefore + 500e6);
assertEq(underlying.balanceOf(address(strategy)), 500e6); // victim shortfall
```

Uncertainty note: I could not fully verify how `IdleCDOEpochVariant` sequences `requestInstantWithdraw`/`collectInstantWithdrawFunds`/`claimInstantWithdrawRequest` calls (only match locations were returned before the iteration limit). If the CDO funds and claims atomically per user, exploitation requires a prior unfunded instant request persisting while the strategy later accumulates funded-receipt underlying — which `pendingInstantWithdraws` explicitly models, but the exact CDO call gating should be confirmed in `IdleCDOEpochVariant.sol`.
