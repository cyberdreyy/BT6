The premise doesn't hold. `GET /v2/log` is registered only in the `authv2` route group, whose authentication middleware chain is `auth.AuthenticateByToken` and `auth.AuthenticateBySession` — `auth.AuthenticateExternalInitiator` is not included [1](#0-0) . The `LogController.Get` route is added to that same `authv2` group with no additional role wrapper at all: `authv2.GET("/log", lgc.Get)` [2](#0-1) .

The EI-derived identity (auto-assigned `UserRoleRun` via `AuthenticateExternalInitiator`) is only usable on the separate `userOrEI` route group, which exposes exclusively `GET /v2/ping` and `POST /v2/jobs/:ID/runs` [3](#0-2) . Since `/v2/log` is not part of that group and its own `authv2` group's `Authenticate` middleware never invokes `AuthenticateExternalInitiator`, a request bearing only EI credentials (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers) has no `authMethod` in that chain that will succeed — it fails `AuthenticateByToken` (no API key/secret headers) and `AuthenticateBySession` (no session cookie), and `Authenticate` returns `auth.ErrorAuthFailed`, aborting with `401 Unauthorized` before `LogController.Get` is ever invoked [4](#0-3) .

Therefore an EI credential holder cannot reach `GET /v2/log` at all — there is no reachable path from the attacker's stated request to the target function, so the "role scoping" invariant described in the question is not actually violated by any code in this repo.

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
