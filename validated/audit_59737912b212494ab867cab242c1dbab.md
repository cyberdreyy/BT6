### Title
LargestAccountsCache keyed only by filter (not commitment) allows cross-commitment stale data serving in `getLargestAccounts` - ([File: rpc/src/rpc_cache.rs])

### Summary
`LargestAccountsCache` stores entries in a `HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>`, keyed solely by the `filter` parameter and never by `CommitmentConfig`. Because `JsonRpcService::new` instantiates a single shared `largest_accounts_cache` used across all commitment levels, a `getLargestAccounts` call at one commitment level populates a cache slot that is then served back verbatim to a subsequent `getLargestAccounts` call at a different commitment level within `LARGEST_ACCOUNTS_CACHE_DURATION`, even though the underlying bank/slot differs.

### Finding Description
In `rpc/src/rpc.rs`, `get_largest_accounts` computes the bank for the request's commitment (`let bank = self.bank(config.commitment);`), but the cache lookup that happens next only depends on `config.filter`: [1](#0-0) 

`get_cached_largest_accounts`/`set_cached_largest_accounts` forward directly to `LargestAccountsCache::get_largest_accounts`/`set_largest_accounts`, which key the `HashMap` by `Option<RpcLargestAccountsFilter>` alone: [2](#0-1) 

There is exactly one `largest_accounts_cache` instance shared by the whole `JsonRpcService`/`JsonRpcRequestProcessor`, created once in `JsonRpcService::new`: [3](#0-2) 

Exploit flow:
1. Attacker calls `getLargestAccounts(commitment=processed, filter=None)`. This misses the cache, computes `bank.get_largest_accounts(...)` against the processed bank/slot, and calls `set_cached_largest_accounts(&None, slot_processed, accounts_processed)`, populating the `None` filter cache slot with processed-commitment data.
2. Immediately (within `LARGEST_ACCOUNTS_CACHE_DURATION`), attacker calls `getLargestAccounts(commitment=finalized, filter=None)`. `get_cached_largest_accounts(&None)` hits the same cache entry (key is only the filter, `None == None`), and the handler returns the previously cached processed-slot data/accounts wrapped in a response context claiming `slot_processed` — data that was never confirmed/finalized at the time it is being reported for a `finalized` request.
3. Because the attacker controls their own account's lamport balance (churning it up/down across processed/confirmed/finalized windows), they can arrange for the top-N list computed at `processed` to differ from what would actually be computed at `finalized`, and have that unconfirmed/rolled-back ordering served to any client (including themselves or third parties) requesting `finalized` data, for up to the cache TTL.

This violates the RPC invariant that "returned data belongs to the requested commitment level," since the cache has no notion of commitment and blindly serves whatever was last computed under any commitment for that filter value. The check `self.bank(config.commitment)` correctly selects the right bank object, but its result is discarded whenever there is a cache hit — the commitment-based bank selection guard is completely bypassed by the cache-hit path.

### Impact Explanation
This is a wrong-data-returned bug: `getLargestAccounts` at `finalized`/`confirmed` commitment can return account-balance snapshots that were only ever `processed` (i.e., potentially not finalized, or from a rolled-back fork), misreporting slot/commitment-scoped state to any RPC client. This matches the "wrong-slot/fork/account data returned" category in scope. It does not require any privileged access — a single unprivileged client alternating two ordinary RPC calls at different commitment levels triggers it, well within the one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` constraint.

### Likelihood Explanation
- Preconditions: attacker needs any account (their own) whose lamport balance is large enough to plausibly appear near the top-N cutoff, and the ability to churn its balance across confirmation levels. No special stake/leader access required.
- Feasibility: trivially reproducible — two sequential JSON-RPC `getLargestAccounts` calls with the same `filter` value but different `commitment`, issued within `LARGEST_ACCOUNTS_CACHE_DURATION`, deterministically reuse the same cache slot regardless of commitment. This requires no timing races beyond normal request sequencing, and is 100% repeatable.
- The bug is a straightforward missing-cache-key defect (no commitment discriminator), not a race condition, so likelihood of triggering is high whenever any two `getLargestAccounts` calls at different commitments with the same filter occur inside the TTL window (this can even happen accidentally between two different unrelated legitimate clients, amplifying real-world impact beyond the single attacker scenario).

### Recommendation
Include the effective commitment (or at minimum the bank slot actually used, `bank.slot()`, combined with `CommitmentConfig`/`CommitmentLevel`) as part of the `LargestAccountsCache` key, e.g. change the `HashMap` key to `(CommitmentLevel, Option<RpcLargestAccountsFilter>)` or `(Slot, Option<RpcLargestAccountsFilter>)`, and pass `config.commitment` (or the resolved commitment level) through `get_cached_largest_accounts`/`set_cached_largest_accounts` calls in `rpc/src/rpc.rs`.

```rust
        cached,
        Some((100, processed_accounts)),
        "cache served processed-commitment data for a finalized-commitment request"
    );
```

Integration-level PoC (conceptual, for `rpc/src/rpc.rs`):
1. Build a `JsonRpcRequestProcessor` test harness with two banks at different commitment states where the top account list differs (e.g. attacker account balance changed between processed and finalized bank state).
2. Call `meta.get_largest_accounts(Some(RpcLargestAccountsConfig{ commitment: Some(CommitmentConfig::processed()), filter: None, .. }))`.
3. Immediately call `meta.get_largest_accounts(Some(RpcLargestAccountsConfig{ commitment: Some(CommitmentConfig::finalized()), filter: None, .. }))`.
4. Assert that the second call's returned `slot`/`accounts` match the finalized bank's actual `get_largest_accounts` output, not the processed bank's cached output — this assertion fails on current code, confirming the vulnerability.

```rust
#[derive(Debug, Clone)]
pub struct LargestAccountsCache {
    duration: u64,
    cache: HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>,
}

#[derive(Debug, Clone)]
struct LargestAccountsCacheValue {
    accounts: Vec<RpcAccountBalance>,
    slot: u64,
    cached_time: SystemTime,
}

impl LargestAccountsCache {
    pub(crate) fn new(duration: u64) -> Self {
        Self {
            duration,
            cache: HashMap::new(),
        }
    }

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }

    pub(crate) fn set_largest_accounts(
        &mut self,
        filter: &Option<RpcLargestAccountsFilter>,
        slot: u64,
        accounts: &[RpcAccountBalance],
    ) {
        self.cache.insert(
            filter.clone(),
            LargestAccountsCacheValue {
                accounts: accounts.to_owned(),
                slot,
                cached_time: SystemTime::now(),
            },
        );
    }
```
