### Title
Stale `instantWithdrawClaimsByEpoch` on funded instant-withdraw claims inflates default recovery basis and reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` increments the per-epoch receipt counter `instantWithdrawClaimsByEpoch[currentEpoch]` (the "refcount"), but the normal funded-claim path `claimInstantWithdrawRequest` never decrements it — only the defaulted path `_claimDefaultedInstantWithdrawRequest` does. If a user requests an instant withdrawal, gets funded, claims, and the pool later defaults in the **same epoch** while other instant receipts remain unfunded, the already-paid amount is counted twice at finalization: once as an outstanding claim basis and once as "prefunded reserve" that no longer exists. This inflates `defaultRecoveryPrice` and lets later claimants draw more than the real reserve holds, leaving honest claimants unpayable.

### Finding Description
`requestInstantWithdraw` bumps three counters per request epoch: `instantWithdrawsRequestsByEpoch[_user]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, and `pendingInstantWithdraws` [1](#0-0) .

`collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` when the borrower funds [2](#0-1) , and `claimInstantWithdrawRequest` then pays the user but clears **only** `instantWithdrawsRequests[_user]` — it leaks both `instantWithdrawsRequestsByEpoch` and the aggregate `instantWithdrawClaimsByEpoch` [3](#0-2) . The only cleanup path is `_claimDefaultedInstantWithdrawRequest` [4](#0-3) .

Both leaked counters feed default finalization:
- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the haircut basis whenever `pendingInstantWithdraws != 0` [5](#0-4) .
- `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying already held by the strategy [6](#0-5) , but for a claimed user that cash was already paid out — the "reserve" is phantom.
- Both are folded into `recoveryPrice = reserveAmount / totalBasis` in `finalizeDefaultRecovery` [7](#0-6) .

This is the exact analog of CVE-2022-49373: a counter incremented at acquisition is missing its decrement on the non-error (funded-claim) path, leaking a resource reference into later accounting.

### Impact Explanation
Sequence (running epoch N, instant-withdraw mode active): A requests instant withdraw; borrower partially funds via `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`; A claims and receives full payout; B (or A again) requests another instant withdraw that stays unfunded (`pendingInstantWithdraws > 0`); borrower defaults before funding; `finalizeDefaultRecovery` runs. The basis now includes A's already-paid amount, and the prefunded-reserve term counts tokens the strategy no longer holds. `recoveryPrice` is therefore set too high relative to actual holdings: earlier claimants (attacker-controlled) receive more than their fair share of the reserve, and the last honest defaulted claimants (and post-default requests paid 1:1 from `defaultRecoveryReserve`) find the reserve drained — direct theft / insolvency with loss equal to the leaked claimed amount (unbounded, proportional to instant-withdraw volume).

### Likelihood Explanation
Requires an epoch that ends in borrower default *while* some same-epoch instant receipts are unfunded and at least one funded instant claim already occurred — a plausible sequence since instant withdrawals are designed to be requested and claimed mid-epoch and defaults are a first-class, handled state. The attacker needs only to be a KYC'd tranche holder using normal flows; ordering (claim before default, then leave a residual unfunded request) is fully under unprivileged control. No existing guard detects it: `_ensureDefaultRecoveryInitialized`, `defaulted()` checks, and epoch gating all pass.

### Recommendation
Mirror the normal withdraw accounting: in `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][relevantEpoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount (tracking the request epoch per user, e.g. a `lastInstantWithdrawRequest` marker), so funded-and-claimed receipts are never re-counted by `defaultPendingClaimBasis` / `_defaultPrefundedInstantReserve`. Also burn/zero the per-epoch user entry to prevent it being re-claimed through `_claimDefaultedInstantWithdrawRequest` after finalization.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
