## Analysis Result

### Title
Uncapped `BuilderPendingWithdrawal.amount` committed to `Withdrawal.amount` allows builder withdrawal to pay out more ETH on the execution layer than is deducted from the builder's consensus-layer balance - ([File: specs/gloas/beacon-chain.md])

### Summary
The reported bug pattern ("check before/after balance instead of trusting a caller-supplied amount") maps directly onto `get_builder_withdrawals` in `specs/gloas/beacon-chain.md`. This function builds the `Withdrawal` object that the execution layer is contractually required to honor, using the raw, uncapped `BuilderPendingWithdrawal.amount` instead of `min(amount, builder.balance)`. Meanwhile, the companion state-mutation function `apply_withdrawals` *does* cap the balance deduction to `min(withdrawal.amount, builder_balance)`. This asymmetry means the committed payment amount (paid on the EL) can exceed the amount actually subtracted from the builder's balance on the CL, creating Gwei that is not backed by any deducted balance.

### Finding Description
`get_builder_withdrawals` constructs `Withdrawal` entries directly from `state.builder_pending_withdrawals`: [1](#0-0) 

```
    for withdrawal in state.builder_pending_withdrawals:
        ...
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
```

`withdrawal.amount` here is the raw, previously-queued `BuilderPendingWithdrawal.amount` value (set when the bid was accepted in `process_execution_payload_bid` / `settle_builder_payment`), not checked against the builder's *current* balance. This becomes part of `state.payload_expected_withdrawals`, which — per the spec note on `process_withdrawals` — **the execution layer is required to honor** (i.e., the EL must actually credit `fee_recipient` with exactly `withdrawal.amount`): [2](#0-1) 

In contrast, the consensus-layer balance deduction in `apply_withdrawals` is explicitly capped to the builder's actual balance: [3](#0-2) 

```
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)
```

This is precisely the pattern flagged in the external report: a transfer/payout amount is trusted at face value instead of being reconciled against the actual available balance before being committed as the authoritative amount. Here, the "committed amount" is not merely an internal accounting value — it is the literal value the execution layer is bound to pay out, so failing to cap it breaks the invariant that `sum(EL payouts) == sum(CL balance decreases)`.

The existing spec test suite (`tests/core/pyspec/eth_consensus_specs/test/gloas/block_processing/test_process_withdrawals.py::test_builder_withdrawal_insufficient_balance` and `test_builder_withdrawal_insufficient_balance_realistic_bounds`) explicitly documents and asserts this exact scenario as expected behavior: [4](#0-3) 

The test comments state: "withdrawal.amount: 5 ETH (requested amount)" while "builders[0].balance: 0 (deduction capped to available balance)" — i.e., the spec/test authors are aware that the CL only deducts what's available, but the committed `Withdrawal.amount` sent to the EL remains the full, uncapped requested amount.

Whether a builder's balance can actually fall short of a previously-queued `builder_pending_withdrawals` entry depends on `can_builder_cover_bid`, which gates new bid acceptance: [5](#0-4) 
```
def can_builder_cover_bid(state, builder_index, bid_amount):
    builder_balance = state.builders[builder_index].balance
    pending_withdrawals_amount = get_pending_balance_to_withdraw_for_builder(state, builder_index)
    min_balance = MIN_DEPOSIT_AMOUNT + pending_withdrawals_amount
    ...
```
I was unable to fully verify, within the remaining tool budget, whether `get_pending_balance_to_withdraw_for_builder` accounts for *unsettled* `state.builder_pending_payments` (bids accepted in the same epoch but not yet moved into `builder_pending_withdrawals`) in addition to already-queued `builder_pending_withdrawals`. If it only sums the latter, a builder could have multiple bids accepted within the same epoch (each individually re-checked against the same balance before any of them settle), over-committing total pending withdrawal amount relative to actual balance — which is exactly the scenario the test suite exercises and for which `apply_withdrawals` silently caps the balance deduction while the EL is still told to pay the full uncapped amount.

### Impact Explanation
If a builder's balance is (or becomes) insufficient to cover the sum of its queued `builder_pending_withdrawals` at the time of `process_withdrawals`, the execution layer is bound by consensus rules to pay the `fee_recipient` the full, uncapped `Withdrawal.amount`, while the beacon state only decreases the builder's balance by the available (capped) amount. This creates ETH on the execution layer that was never actually backed by a corresponding balance decrease on the consensus layer — a direct violation of the "Gwei created" invariant, which the rules classify as Critical impact.

### Likelihood Explanation
Likelihood is Low: this requires a scenario where a builder's `builder_pending_withdrawals` queue commits more value than the builder's current balance can cover at settlement time, which is guarded against at bid-acceptance by `can_builder_cover_bid`. Whether that guard is airtight against concurrent/overlapping bids within a single epoch (before earlier payments settle into `builder_pending_withdrawals`) could not be conclusively confirmed with the available tool budget. The spec authors' own test names ("insufficient balance") suggest they consider this a reachable edge case worth testing, but the tests validate the (arguably incorrect) current behavior rather than flag it as a bug.

### Recommendation
Cap the `amount` field written into the `Withdrawal` object in `get_builder_withdrawals` to `min(withdrawal.amount, state.builders[builder_index].balance)` at the point the withdrawal is computed (mirroring what `get_builders_sweep_withdrawals` already does by using `builder.balance` directly), so that the amount committed to the execution layer always matches the amount that will actually be deducted from the builder's balance in `apply_withdrawals`. Alternatively, remove the `min()` capping in `apply_withdrawals` and instead make `can_builder_cover_bid` (and any other balance-reservation logic) a hard invariant that guarantees `builder.balance` can never fall below the sum of its pending withdrawal commitments, and treat a violation as an unhandled/invalid state transition rather than silently capping.

### Proof of Concept
Conceptual sequence (subject to the caveat above about `get_pending_balance_to_withdraw_for_builder`'s completeness):
1. A builder is registered with balance `B`.
2. Bid(s) are accepted such that `state.builder_pending_withdrawals` (or payments about to settle into it) for the builder sum to `A`, where `A > B - MIN_DEPOSIT_AMOUNT` is not caught because the check at bid-acceptance time considered a smaller already-settled pending amount.
3. At the next `process_withdrawals`, `get_builder_withdrawals` emits `Withdrawal(amount=A, address=fee_recipient)`.
4. `apply_withdrawals` deducts only `min(A, B) = B` from the builder's balance (capped to zero), per [6](#0-5) .
5. The execution layer, bound by `state.payload_expected_withdrawals`, still pays `fee_recipient` the full `A`, exceeding the `B` that was actually removed from the builder's balance — net ETH creation of `A - B`.

This exact "insufficient balance / capped deduction, uncapped committed amount" scenario is already reproduced (as expected, non-failing behavior) in [7](#0-6) .
