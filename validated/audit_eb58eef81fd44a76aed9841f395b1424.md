### Title
Mid-epoch depositor captures full-epoch withdraw interest via `depositDuringEpoch` + `requestWithdraw` - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`depositDuringEpoch` prices a mid-epoch entry so the depositor only earns interest for the remaining time (`trancheInterest` pro-rated by `(remaining + buffer) / (epochDuration + buffer)`). However, `requestWithdraw` computes withdraw interest as a flat pro-rata share of the *entire* epoch interest over tranche NAV (`_amount * totTrancheInterest / _trancheBal`), with no accounting of when the principal was actually committed. A KYC-passed attacker can therefore deposit near the end of an epoch, immediately file a withdraw request once requests are allowed, and receive a receipt that includes full-epoch interest on capital committed for a fraction of the epoch — the exact analog of staking/unstaking to harvest `cumulativeRewardPerToken` without streaming deposits.

### Finding Description
- `depositDuringEpoch` mints shares at a discounted end-of-epoch price so the depositor is owed `amount + trancheInterest` only for the time actually remaining (`IdleCDOEpochVariant.sol:687-724`). `trancheInterest` shrinks as `remaining` shrinks, so a depositor entering one block before `epochEndDate` pays for essentially zero epoch interest.
- `requestWithdraw` then computes `_interest = _amount * totTrancheInterest / _trancheBal` (`IdleCDOEpochVariant.sol:856-878`), where `totTrancheInterest` is the tranche's share of the *whole* epoch's interest (`_calcInterest(_managedContractValue()) * _duration / (_duration + _buffer)`). There is no per-user deposit timestamp or time-weighted basis — identical to the Streaming bug where `ts.rewards = earned(...)` credited elapsed rewards while `ts.tokens -= acctTimeDelta * ts.tokens / (endStream - lastUpdate)` could be gamed to subtract ~0.
- `requestWithdraw` is gated only by `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and `isWalletAllowed` (`IdleCDOEpochVariant.sol:739-744`); it does not check `isEpochRunning` or `block.timestamp < epochEndDate`. So a mid-epoch depositor can request immediately while their full-epoch interest share is still computable, or at the start of the buffer.
- The credited interest is minted into the user's strategy-token receipt and added to `pendingWithdraws` (`IdleCreditVault.sol:243-295`). `stopEpoch` funds `pendingWithdraws` from the borrower's repayment, which is sized by `expectedEpochInterest` — and `expectedEpochInterest` only grew by the attacker's *prorated* `interest` at deposit time (`IdleCDOEpochVariant.sol:728`). The delta between full-epoch and prorated interest credited to the attacker is therefore under-collateralized by the repayment and is carved out of the fixed interest pool owed to honest LPs.

Broken invariant: fair mint/burn — interest must accrue linearly with capital commitment time. The deposit path enforces time-weighting, the withdraw path ignores it.

### Impact Explanation
The attacker mints a withdraw receipt worth `principal + fullEpochInterestShare` after committing capital for only `remaining` seconds. At claim time the receipt is paid 1:1 from strategy underlyings funded by borrower repayment (`collectWithdrawFunds`, `_transferFundedClaim`). Since the repayment only includes the prorated interest the attacker actually generated, honest LPs' virtual price / pending claims absorb the shortfall — direct theft of yield from other tranche holders, scaling with `attackerDeposit / trancheNAV` and repeatable every epoch. With a large deposit relative to NAV (e.g. depositing an amount comparable to TVL just before epoch end), the attacker can extract a material fraction of the epoch's tranche interest.

### Likelihood Explanation
- Requires `isDepositDuringEpochDisabled == false` (owner-enabled feature), non-AYS, non-programmable, non-APR0 pool — a documented supported mode.
- Attacker needs only a KYC-passed wallet (`isWalletAllowed`) — explicitly an unprivileged role.
- `depositDuringEpoch` has no minimum-remaining-time check and `requestWithdraw` has no holding-period or deposit-time check; nothing in `_skimDonatedAssets`, `_updateAccounting`, or the default-recovery guards prevents it.
- Cost is one epoch-length capital commitment for the principal plus gas; the exploit is most profitable entering close to `epochEndDate` where `trancheInterest ≈ 0` but the withdraw share is still over the full epoch.

### Recommendation
Time-weight the withdraw interest, mirroring the deposit path: in `_calcInterestWithdrawRequest`, scale `_interest` for positions opened via `depositDuringEpoch` (or track a per-user NAV-weighted deposit epoch timestamp) so withdraw interest reflects actual time in the epoch — i.e. multiply the tranche interest share by `(epochEndDate - depositTimestamp + buffer) / (epochDuration + buffer)`, or store the `trancheInterest` already credited at mid-epoch deposit and subtract it from the withdraw interest. Alternatively, disallow `requestWithdraw` for tranche tokens minted in the current epoch.

### Proof of Concept
Foundry fork test sketch (repo: `ThankGod76/idle-tranches--012`, contracts under test: `IdleCDOEpochVariant`, `IdleCreditVault`):

```solidity
function testMidEpochDepositFullEpochWithdrawInterest() public {
    // SETUP: 10% apr, 365-day epoch, buffer = 0, deposits-during-epoch enabled
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(365 days, 0);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);
    vm.stopPrank();

    uint256 initialDeposit = 1000 * ONE_SCALE;
    idleCDO.depositAA(initialDeposit);          // honest LP, in since epoch start
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    _startEpochAndCheckPrices(0);               // expectedEpochInterest = 100

    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    // ATTACK: attacker deposits 1000 right before epoch end
    address attacker = makeAddr("attacker");
    uint256 depositAmount = 1000 * ONE_SCALE;
    deal(defaultUnderlying, attacker, depositAmount);

    vm.warp(cdoEpoch.epochEndDate() - 1);       // remaining = 1s
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), depositAmount);
    cdoEpoch.depositDuringEpoch(depositAmount, address(AAtranche));
    // attacker paid for ~0 interest: trancheInterest ~ 0, minted ~ 1000/1100 supply

    // request withdraw immediately (allowAAWithdrawRequest == true)
    uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.stopPrank();

    // interest credited = receipt - principal(underlyings burned)
    // ~= depositAmount * totTrancheInterest / trancheNAV  -> ~half of 100+ full-epoch interest
    // assert attacker captured ~full-epoch interest on ~0 commitment:
    //   receipt ≈ principal + share_of_full_epoch_interest >> depositAmount
    // while expectedEpochInterest only grew by ~0, so honest LP claims are diluted
    // after stopEpoch funds pendingWithdraws.
}
```

Expected outcome: `receipt - principal` approximates the attacker's NAV share of the entire epoch's AA interest rather than ~0, and post-`stopEpoch` the funded `pendingWithdraws` exceed the interest actually generated, leaving honest LPs' claims under-collateralized.
