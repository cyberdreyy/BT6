### Title
Defaulted-epoch instant-withdraw double counting inflates `defaultRecoveryPrice`, leaving the recovery reserve insolvent and permanently freezing later claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external bug is a negative-index heap write: accounting is updated at a slot "before" where the buffer logically begins. The vault analog is per-epoch instant-withdraw basis that is never cleared when the receipt is claimed, so it is counted twice — once as already-paid cash and once again as a pending defaulted claim — which writes the recovery price above what the reserve actually holds.

`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]`; it leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` populated. At default finalization, `defaultPendingClaimBasis` re-adds the full current-epoch instant claim basis, and `_defaultPrefundedInstantReserve` treats the difference between that stale basis and `pendingInstantWithdraws` as underlying still held by the strategy — even though those tokens were already transferred out to the claimant. `finalizeDefaultRecovery` then computes `recoveryPrice = reserveAmount * 1e18 / totalBasis` on this inflated reserve/basis pair. Claims are paid at the inflated price while `_transferDefaultRecovery` decrements `defaultRecoveryReserve` until it underflows, so the last claimant(s) can never be paid: a permanent freeze/shortfall of unclaimed recovery funds.

### Finding Description
Relevant code paths in `contracts/strategies/idle/IdleCreditVault.sol`:

- Request: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (lines 367–374).
- Funding: `collectInstantWithdrawFunds` decrements only `pendingInstantWithdraws` (line 401).
- Claim: `claimInstantWithdrawRequest` burns the receipt and zeroes `instantWithdrawsRequests[_user]`, but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` (lines 387–392).
- Finalization: `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (lines 644–649), and `_defaultPrefundedInstantReserve` adds `instantBasis - pendingInstant` as supposedly held funds (lines 716–723). Both feed `reserveAmount`/`totalBasis` for `recoveryPrice` (lines 685–688).
- Payout: `_transferDefaultRecovery` does `defaultRecoveryReserve -= _amount`, which underflows once over-issued claims exhaust the real balance (lines 912–916).

### Impact Explanation
Insolvency and permanent freezing of unclaimed yield. Every already-claimed instant receipt in the defaulted epoch is counted once more in `totalBasis` and once more in `prefundedReserve`, so `recoveryPrice` is computed as if paid-out tokens were still on the strategy balance sheet. Early claimants are overpaid pro-rata and the final claimants' transfers revert (either via `defaultRecoveryReserve` underflow or insufficient token balance), permanently locking their recovery. The shortfall equals the sum of instant receipts claimed after partial funding but before default finalization, unbounded by any privileged action.

### Likelihood Explanation
Requires the epoch instant-withdraw mode to be partially funded inside one epoch (a normal, intended flow: the CDO calls `collectInstantWithdrawFunds` as cash arrives), at least one user claiming before epoch end, and the borrower then defaulting in that same epoch. The attacker is an ordinary KYC'd lender performing only legitimate calls (`requestInstantWithdraw`, `claimInstantWithdrawRequest`); borrower default is a credit event, not malicious behavior. No guard stops it: `_onlyIdleCDO`, the `pendingInstantWithdraws != 0` check, and `_transferFundedClaim`'s reserve guard all pass because the stale per-epoch basis looks legitimate.

### Recommendation
When `claimInstantWithdrawRequest` pays a funded receipt, also clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount, so claimed basis can never re-enter default accounting. Alternatively, track a per-epoch funded counter and subtract it in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`.

### Proof of Concept
Foundry fork test sketch (epoch running, instant-withdraw mode):

```solidity
// assume vault/cdo deployed, epoch E running, borrower drawn funds
// attacker and victim are KYC'd lenders with strategy-token balances

// 1) both request instant withdraws in epoch E
cdo.requestInstantWithdraw(attacker, 100e6); // instantWithdrawClaimsByEpoch[E] = 100
cdo.requestInstantWithdraw(victim,   100e6); // instantWithdrawClaimsByEpoch[E] = 200
// pendingInstantWithdraws = 200

// 2) borrower returns only enough to fund the attacker; CDO collects partially
vault.collectInstantWithdrawFunds(100e6);    // pendingInstantWithdraws = 100
cdo.claimInstantWithdrawRequest(attacker);   // attacker paid 100
// BUG: instantWithdrawsRequestsByEpoch[attacker][E] still = 100,
//      instantWithdrawClaimsByEpoch[E] still = 200

// 3) borrower defaults in epoch E; owner/manager finalize recovery
cdo.finalizeDefaultRecovery(recovered, source);
// defaultPendingClaimBasis = pendingWithdraws + 200 (stale 100 included)
// _defaultPrefundedInstantReserve = 200 - 100 = 100 counted as held,
// but those 100 tokens were already sent to the attacker
// => recoveryPrice computed on phantom 100; reserve is short by exactly 100

// 4) claims
cdo.claimWithdrawRequest(otherPendingUser);   // paid at inflated price
vm.expectRevert();                            // reserve underflows / insufficient balance
cdo.claimInstantWithdrawRequest(victim);      // last claimant permanently frozen
```

The assertable invariant: `underlyingToken.balanceOf(vault) >= defaultRecoveryReserve` holds at finalization in code but the reserve accounting double-counts outflowed funds, so the final claim's `defaultRecoveryReserve -= _amount`/transfer reverts, stranding the victim's recovery share equal to the attacker's already-claimed amount.
