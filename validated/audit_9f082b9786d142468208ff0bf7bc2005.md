### Title
A de-whitelisted (KYC-revoked) lender keeps accruing yield and can still exit — KYC revocation is unenforceable on existing tranche positions - (contracts/IdleCDOEpochVariant.sol)

### Summary
`isWalletAllowed` is only enforced at the *entry points* (`_deposit`, `depositDuringEpoch`, `requestWithdraw`, queue `requestDeposit`/`requestWithdraw`). Once a KYC-approved wallet holds tranche tokens, removing its Keyring credential does nothing: the tokens keep appreciating via `virtualPrice`, pending withdraw claims pay out with no credential check, and the holder can exit into underlyings through the unpermissioned `WriteOffEscrow.fullfillWriteOffRequest`. Tranche tokens are also unrestricted ERC20s, so a KYC'd wallet can pass the earning position to a non-KYC wallet. This is the same class as the MToken M-1: revocation of the "earner" privilege cannot be enforced after the position exists, and no function lets anyone force the revoked wallet out.

### Finding Description
KYC gating lives in `IdleCDOEpochVariant.isWalletAllowed`, which delegates to `IKeyring.checkCredential`:

- `contracts/IdleCDOEpochVariant.sol:984-987` — `isWalletAllowed` returns `keyring == 0 || checkCredential(...)`.
- `contracts/IdleCDOEpochVariant.sol:644-645` — `_deposit` checks `isWalletAllowed(msg.sender)`.
- `contracts/IdleCDOEpochVariant.sol:739-744` — `requestWithdraw` checks `isWalletAllowed(msg.sender)`.
- `contracts/IdleCDOEpochVariant.sol:967-979` — `claimWithdrawRequest` and `claimInstantWithdrawRequest` forward to the strategy **without** any `isWalletAllowed` check.
- `contracts/strategies/idle/IdleCreditVault.sol:301-314, 380-393` — `claimWithdrawRequest`/`claimInstantWithdrawRequest` only enforce `_onlyIdleCDO()`; the receipt is burned and underlyings are sent to `_user` unconditionally.
- `contracts/IdleCDOEpochQueue.sol:373-411` — `claimDepositRequest`/`claimWithdrawRequest` likewise have no credential check.
- `contracts/IdleCDOTranche.sol:7-41` — the tranche token is a plain `ERC20`; `transfer`/`transferFrom` are unrestricted, so positions move freely to non-KYC wallets.
- `contracts/WriteOffEscrow.sol` (`fullfillWriteOffRequest`) lets any buyer — explicitly tested as a non-Keyring buyer in `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol:247-294` — swap underlyings for tranches or vice versa with no `isWalletAllowed` check.

So the sequence: Alice passes KYC, calls `depositAA`, epoch runs. Keyring revokes Alice's credential (or admin removes her from `KeyringIdleWhitelist.whitelist`). Alice's tranche tokens keep accruing their share of `expectedEpochInterest` — there is no `stopEarning` equivalent, no forced redemption, and nothing in `stopEpoch`/`_updateAccounting` discriminates by holder. She can still claim any pending withdraw request, and can convert tranches to underlyings through a third-party `WriteOffEscrow` request fulfillment, bypassing `requestWithdraw` entirely. Conversely, a non-KYC wallet can receive tranches by transfer or escrow fulfill and keep earning.

### Impact Explanation
KYC revocation — the compliance lever for removing a sanctioned or non-compliant lender — is ineffective. A revoked wallet continues to earn the full tranche APR and can fully exit at fair value via claims or the escrow. If revocation is meant to cut off yield (the reason such lists exist), each revoked wallet captures the same yield it was entitled to while approved, indefinitely, and the protocol cannot force-exit it. This mirrors the M-1 "earner keeps earning after disapproval" impact: the privileged yield stream is not actually revocable.

### Likelihood Explanation
Requires only a normal sequence of honest-role actions (admin removes a credential — a routine compliance event) plus an unprivileged user who simply holds. Tranche transfers being unrestricted means the "attacker" doesn't even need a prior KYC'd account. No timing or economic assumptions are needed.

### Recommendation
Mirror the M-1 fix: add a permissionless force-exit, e.g. a `forcedWithdraw(user, tranche)` callable by anyone when `!isWalletAllowed(user)`, which routes through the standard `requestWithdraw` path on their behalf (and/or lets the owner burn-and-compensate at `virtualPrice`). Additionally, gate `claimWithdrawRequest`/`claimInstantWithdrawRequest`/queue claims and `WriteOffEscrow.fullfillWriteOffRequest` on `isWalletAllowed`, and add a transfer hook on `IdleCDOTranche` requiring `isWalletAllowed(to)` if revocation is meant to be binding.

### Proof of Concept
Foundry fork test extending `test/foundry/IdleCreditVault.t.sol` helpers:

```solidity
function test_revokedUserKeepsEarningAndExits() external {
    // Alice is KYC'd (keyring == 0 or mocked true)
    uint256 mintedAA = _depositWithUser(alice, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // admin/compliance revokes alice's credential
    address keyring = address(1);
    vm.prank(owner);
    cdoEpoch.setKeyringParams(keyring, 1);
    vm.mockCall(keyring, abi.encodeWithSelector(IKeyring.checkCredential.selector, 1, alice), abi.encode(false));
    vm.mockCall(keyring, abi.encodeWithSelector(IKeyring.checkCredential.selector, 1, address(this)), abi.encode(true));
    assertFalse(cdoEpoch.isWalletAllowed(alice));

    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // alice cannot requestWithdraw (entry point is gated)
    vm.prank(alice);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));

    // but her tranche tokens already accrued yield: virtualPrice > 1
    assertGt(cdoEpoch.virtualPrice(address(AAtranche)), ONE_TRANCHE);

    // exit path 1: an exit made before revocation is still claimable with no KYC check
    // (repeat requestWithdraw pre-revocation, then claimWithdrawRequest post-revocation succeeds)

    // exit path 2: alice sells tranches into a write-off request she created before revocation
    // or a third party's; fullfillWriteOffRequest has no isWalletAllowed check
    escrow.createWriteOffRequest(mintedAA / 2, uint256(underlyingOut));
    deal(address(underlying), buyer, underlyingOut);
    vm.startPrank(buyer); // buyer is also non-KYC
    underlying.approve(address(escrow), underlyingOut);
    escrow.fullfillWriteOffRequest(alice, mintedAA / 2, underlyingOut); // succeeds
    vm.stopPrank();
    // alice received underlyings; non-KYC buyer now holds yield-bearing tranches
}
```

The assertions mirror the M-1 PoC: post-revocation balance keeps growing, the revoked wallet cannot be forced to stop, and both claim and escrow exits pay out full accrued value.
