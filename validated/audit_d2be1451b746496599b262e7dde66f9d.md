### Title
Unauthenticated Pipeline Run Resume Endpoint Allows Unprivileged Actors to Complete/Resume Any Async Job Run - ([File: core/web/router.go])

### Summary
The `/v2/resume/:runID` endpoint is registered in an unauthenticated route group and forwards attacker-controlled resume data directly into `Application.ResumeJobV2`, allowing any unauthenticated network client who obtains or guesses a task UUID to finish/resume that pipeline task with arbitrary result data — no session, API token, or external-initiator credential is checked.

### Finding Description
In `core/web/router.go`, the pipeline-run resume route is explicitly mounted on the unauthenticated `unauthedv2` group, separate from `authv2`/`userOrEI` groups that require session, API token, or external-initiator auth: [1](#0-0) 

The handler, `PipelineRunsController.Resume`, performs no authentication or authorization check at all. It parses the `runID` path parameter as a UUID, decodes an attacker-supplied JSON body into a `pipeline.ResumeRequest`, converts it to a task result, and immediately calls `prc.App.ResumeJobV2` with that result: [2](#0-1) 

By contrast, the sibling `Create` endpoint (job run triggering) is gated behind `auth.RequiresRunRole` and only usable by authenticated users through the `authv2`/`userOrEI` groups: [3](#0-2) 

The only "secret" protecting this endpoint is the unguessability of the UUID `taskID`, which is not a credential, cannot be rotated/redacted, and is not validated against any session/role. The code even acknowledges this design via the audit event name `UnauthedRunResumed`: [4](#0-3) [5](#0-4) 

This is the closest analog in this codebase to the reported "unprotected public function" bug class (a state-mutating function reachable by any caller without an authorization check), mapped to the node's internet-facing HTTP API rather than a smart contract.

### Impact Explanation
An unprivileged network client that can reach the node's HTTP API (which, per the intended design of this endpoint, is meant to be reachable without any Chainlink session/API-key/EI credentials for callback purposes) can submit arbitrary resume payloads for any pipeline task whose UUID it discovers (e.g., via logs, error messages, timing, or brute force over the 128-bit space is impractical but log/response leakage is not). If successful, the attacker can force completion of a suspended pipeline task (e.g., a bridge/external adapter async callback task) with attacker-chosen result data, potentially corrupting downstream job pipeline execution, causing an OCR/VRF/Keeper job to proceed with falsified externally-supplied values, or triggering unintended fund-moving transaction pipeline continuations depending on job type. The severity depends heavily on operational exposure (whether `runID`s are ever disclosed to untrusted parties) and job configuration, which cannot be fully confirmed from static code alone.

### Likelihood Explanation
Likelihood is limited by the practical unguessability of UUIDv4 task IDs; there is no other authorization gate. Exploitation requires the attacker to first learn a valid, still-pending `runID`, which is plausible in setups where the ID is echoed back by an external adapter/bridge response, logged, or otherwise exposed to a partially-trusted or malicious external adapter operator. Without further evidence that `runID` values leak to unprivileged parties in this deployment's usage pattern, likelihood is moderate rather than high, but the endpoint remains completely unauthenticated by design, which is itself the “unprotected public function” condition being evaluated.

### Recommendation
Require the caller to present the resuming external adapter's/bridge's outgoing token/secret (already generated per external initiator/bridge, see `bridges.ExternalInitiator.OutgoingToken`/`OutgoingSecret`) or another bound credential when calling Resume, rather than relying solely on UUID secrecy. At minimum, validate that the resume request is scoped/rate-limited and audit-log failed attempts distinctly from successful ones to detect probing.

### Proof of Concept
1. Identify or intercept a pending pipeline task's `runID` (UUID) associated with a bridge/external-adapter callback (e.g., leaked via a compromised or malicious external adapter, verbose logging, or timing side channel).
2. Without any session cookie, API key, or EI header, send:
   `PATCH /v2/resume/<runID>` with body `{"error": null, "value": "<attacker-controlled>"}` (per `pipeline.ResumeRequest` shape referenced in `core/services/pipeline/models.go`).
3. The request is routed via the `unauthedv2` group directly to `PipelineRunsController.Resume`, which calls `App.ResumeJobV2` with the attacker-supplied result, completing the task with no authentication check. [6](#0-5) [7](#0-6)

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
```
