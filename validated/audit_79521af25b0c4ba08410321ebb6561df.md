### Title
`lastWithdrawRequest` used as the loss-epoch key lets a later withdraw request skip loss adjustment and claim the earlier loss-adjusted receipt at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the Coinbase `removeOwnerAtIndex` bug — where a positional/index parameter resolved to a different entity than the signer intended after state drifted — `IdleCreditVault._claimLossAdjustedWithdrawRequest` does not identify which epoch a user's withdrawal receipt belongs to. It derives the "loss epoch" from the scalar marker `lastWithdrawRequest[_user]`, which is overwritten on every new `requestWithdraw`. A user with a loss-adjusted receipt from epoch E1 who submits any new request in epoch E2 silently re-targets the lookup to E2, skips the haircut, and the leftover E1 basis is then paid at par by `_claimFundedWithdrawRequest`, even though only the reduced, loss-adjusted amount was ever funded by the borrower.

### Finding Description
In `requestWithdraw`, the strategy stores the user's request in two places: an epoch-keyed entry `withdrawsRequestsByEpoch[_user][currentEpoch]`, an aggregate `withdrawsRequests[_user]`, and a single scalar marker `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:282-294`).

On claim, `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`IdleCreditVault.sol:789-801`). This is the index-resolution flaw: the scalar marker is assumed to name the epoch whose receipt carries a loss, but it actually names the user's *most recent* request epoch. If the user requested a withdraw in an epoch that later ended via `stopEpochWithDuration(_lossAmount)` (setting `lossRecoveryPriceByEpoch[E1]`), and then requests again during epoch E2 before claiming, `lastWithdrawRequest` becomes E2. Since `lossRecoveryPriceByEpoch[E2] == 0`, the function returns early and never calls `_clearWithdrawClaimForEpoch(_user, E1, false)`, so `withdrawsRequestsByEpoch[_user][E1]` and the E1 contribution to `withdrawsRequests[_user]` remain intact.

Execution then falls through to `_claimFundedWithdrawRequest`, which, once `epochNumber > lastWithdrawRequest[_user]` (i.e., after E2's epoch has stopped), pays the full aggregate `withdrawsRequests[_user]` at par and burns the receipt (`IdleCreditVault.sol:319-350`). However, per the comment at `IdleCreditVault.sol:797`, the borrower only funded the *loss-reduced* amount for the E1 receipt (`pendingWithdraws` was cleared at funding time at the reduced basis). The user therefore withdraws `claimBasis_E1` at par from the funded reserve while only `claimBasis_E1 * lossRecoveryPrice / RECOVERY_FULL` was deposited, draining `(1 - recovery) * basis` of underlying that belongs to other LPs/receipts — and symmetrically, if E1 was a healthy funded epoch and a *later* epoch E2 takes the loss, the reverse ordering can instead lock the user's E2 loss-adjusted receipt permanently (no path re-derives E2 after `lastWithdrawRequest` is reset to 0 in `_clearWithdrawClaimForEpoch`/`_claimFundedWithdrawRequest`).

### Impact Explanation
Direct theft / insolvency: an unprivileged tranche holder recovers their full pre-loss basis on a haircut receipt, paid out of `fundedClaims`/strategy underlying reserves that were only topped up with the reduced amount. The shortfall is socialized onto other claimants and active LPs (loss waterfall violation: loss is not applied to the receipt that incurred it). Magnitude is bounded by the user's request size and the haircut: loss = `basis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL`. The second ordering yields permanent freezing of a user's loss-adjusted claim.

### Likelihood Explanation
Requires a pool epoch stopped via `stopEpochWithDuration(_lossAmount)` (partial loss, not full default — `lossRecoveryPriceByEpoch` is distinct from the `defaultRecoveryPrice` path) and a user holding an unclaimed loss-adjusted receipt who submits any further `requestWithdraw` in a later epoch, then claims after that epoch ends. Requesting again instead of claiming is explicitly contemplated by the code (`IdleCreditVault.sol:323-324` comment: a new request makes the user "wait for another epoch to claim both requests"), so the trigger is normal user behavior, not exotic sequencing. No privileged misbehavior is needed; owner/manager calls (`stopEpochWithDuration`, `stopEpoch`) occur in the ordinary honest sequence.

### Recommendation
Resolve the claim epoch per receipt rather than via the mutable `lastWithdrawRequest` marker. Concretely: in `_claimLossAdjustedWithdrawRequest`, iterate or track the set of epochs with nonzero `withdrawsRequestsByEpoch[_user][epoch]` that have `lossRecoveryPriceByEpoch[epoch] != 0` (or store the loss epoch on the receipt itself at request time), and clear/apply the haircut to *each* such epoch-keyed entry before falling through to the funded path. Alternatively, block new `requestWithdraw` while an unclaimed receipt exists in an epoch with a pending loss price, mirroring Coinbase's fix of binding the identifier to the entity actually being acted on.

### Proof of Concept
Foundry fork-style sequence, using the same harness primitives as `test/foundry/IdleCDOEpochQueue.t.sol` (`_stopCurrentEpochWithApr`, `stopEpochWithDuration`, `deal`/`prank` on the borrower):

```solidity
function testLossReceiptClaimedAtParAfterLaterRequest() external {
    // buffer period: deposit as ATTACKER (KYC'd lender), epoch E1 runs
    uint256 tranches = _depositWithUser(ATTACKER, 100e6);
    vm.prank(manager); cdoEpoch.startEpoch();

    // attacker requests withdraw during epoch E1 -> lastWithdrawRequest[A] = E1
    _requestWithdrawWithUser(ATTACKER, tranches);

    // epoch E1 ends with a partial loss via stopEpochWithDuration
    vm.warp(cdoEpoch.epochEndDate() + 1);
    // borrower repays only interest + loss-adjusted pendingWithdraws
    uint256 lossAmount = ...; // e.g. 20% haircut on pendingWithdraws
    dealAndApproveBorrowerRepay(expectedInterest + pendingToFund);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, duration, lossAmount);
    // strategy.lossRecoveryPriceByEpoch[E1] is now set (< RECOVERY_FULL)

    // new epoch E2 runs; attacker files ANOTHER withdraw request
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(ATTACKER, smallTrancheAmount);
    // lastWithdrawRequest[A] is now E2, which has no lossRecoveryPrice

    // epoch E2 ends normally (borrower repays in full)
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager); cdoEpoch.stopEpoch(0, 0);

    // attacker claims: loss-adjusted path keyed on E2 returns 0 and is skipped;
    // _claimFundedWithdrawRequest pays withdrawsRequests[A] (E1 + E2 basis) at par
    uint256 balPre = underlying.balanceOf(ATTACKER);
    vm.prank(ATTACKER_EOA_which_is_CDO_entrypoint /* via cdoEpoch.claimWithdrawRequest() */);
    cdoEpoch.claimWithdrawRequest();

    // attacker received full par value for the E1 receipt although only
    // E1_basis * lossRecoveryPrice / RECOVERY_FULL was funded by the borrower
    assertGt(underlying.balanceOf(ATTACKER) - balPre,
             fundedAmountForE1 + e2Basis); // over-claim == E1_basis * (1 - recovery)
}
```

Notes/uncertainty: this PoC sketch assumes `lossRecoveryPriceByEpoch` is written inside `stopEpochWithDuration` keyed by the strategy epoch in which the loss occurred and that per-user `withdrawsRequests` is not reduced at funding time (consistent with the `IdleCreditVault.sol:797` comment that only `pendingWithdraws` is cleared). The precise epoch key used for `lossRecoveryPriceByEpoch` and whether `stopEpochWithDuration` mutates per-user receipt storage were not fully traced within the available context; if per-user basis is reduced at funding, the residual over-claim disappears but the reverse-ordering permanent-freeze variant (loss epoch unreachable once `lastWithdrawRequest` is reset to 0) still stands, since no code path enumerates a user's per-epoch receipts independently of the scalar marker.
