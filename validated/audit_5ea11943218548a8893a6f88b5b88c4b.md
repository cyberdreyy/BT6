## Title
Multisig `confirm()` counts confirmations from access keys that have since been removed, allowing a request to execute below the real `num_confirmations` threshold — (`multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig/src/lib.rs` decides whether to execute a pending request purely by comparing the size of the stored `confirmations` set for that `request_id` against `self.num_confirmations`. This binding assumes every entry in that set corresponds to a currently-live access key. However, the `DeleteKey` execution path only purges confirmations/requests that were *added* by the deleted key — it never scrubs the deleted key out of `confirmations` sets belonging to *other* requests that the key merely *confirmed*. The same asymmetric cleanup pattern exists in `multisig2/src/lib.rs` for `DeleteMember`.

### Finding Description
In `confirm()`:
```rust
// multisig/src/lib.rs:248-266
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert!(!confirmations.contains(&env::signer_account_pk()), ...);
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(env::signer_account_pk());
        self.confirmations.insert(&request_id, &confirmations);
        PromiseOrValue::Value(true)
    }
}
``` [1](#0-0) 

The binding this is supposed to enforce is: `count(confirmations for request_id) == count(distinct still-live signer keys who confirmed)`. That equality can be broken via `DeleteKey`:
```rust
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [2](#0-1) 

This only filters `self.requests` by `r.signer_pk == pk`, i.e., requests that the deleted key itself *created*. It does nothing to scan `self.confirmations` for entries where the deleted key appears as a *confirmer* of a request created by a different key. Those stale confirmations remain counted forever.

Concretely: with `num_confirmations = 3` and keys A, B, C, D:
1. A creates request X (`add_request`).
2. B confirms X → `confirmations[X] = {B}` (1/3).
3. C confirms X → `confirmations[X] = {B, C}` (2/3, not yet executed).
4. Separately, a quorum of keys later approves a `DeleteKey{B}` request (e.g., because B's device was compromised or B left the organization) and it executes, removing B's access key from the account.
5. D confirms X → `confirmations.len() + 1 = 3 >= num_confirmations`, so X executes — using B's stale confirmation even though B is no longer a valid signer of the account.

Effectively the request executed with only 2 live confirmers (C, D) plus a phantom one (B), i.e., below the intended 3-of-N live-signer threshold. `multisig2/src/lib.rs`'s `DeleteMember` action follows the identical pattern (`confirmations` keyed by `member.to_string()`), so the same gap is reachable there as well.

### Impact Explanation
This breaks the multisig custody guarantee directly: `Multisig request executed below threshold` is explicitly listed as a Critical impact. An attacker who is an unprivileged party with respect to the *current* member set (a removed/former key holder) can have contributed a confirmation that persists and is later combined with fewer live confirmations to authorize arbitrary `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc. actions — moving NEAR or granting access with fewer real approvals than the configured security threshold requires.

### Likelihood Explanation
This requires no special privilege beyond being a legitimate signer at the time of confirming (which is the normal usage pattern), and key/member removal is an explicitly supported, documented operation (`DeleteKey` / `DeleteMember`). Any organization that reacts to a compromised or departing signer by removing their key — while a request that signer had previously confirmed is still pending — will trigger this. The multisig README itself documents a related gotcha about falling below `num_confirmations` after key removal, but does not address this specific "stale confirmation counted" issue, indicating it was not previously identified/fixed. [3](#0-2) 

### Recommendation
When executing `DeleteKey` (or `DeleteMember` in `multisig2`), scan all outstanding `self.confirmations` entries (not just `self.requests` filtered by `signer_pk`) and remove the deleted key/member from every confirmation set, not only from requests it originally created. Alternatively, validate at `confirm()` time that every public key/member currently present in a request's confirmation set still corresponds to a live access key/member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig` with keys `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request(X)` where `X = Transfer{...}`.
3. `B` calls `confirm(X)` → `confirmations[X] = {B}`.
4. `C` calls `confirm(X)` → `confirmations[X] = {B, C}` (2/3, request not executed).
5. Using a separate, properly-quorate request, delete key `B`'s access key via `DeleteKey{public_key: B}` — this only removes requests created *by* B (none exist here) and clears `num_requests_pk[B]`, but leaves `confirmations[X] = {B, C}` untouched.
6. `D` calls `confirm(X)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request(X)` runs, transferring funds, even though only `C` and `D` are live confirmers plus `A` as creator — `B`'s confirmation is phantom.

This reproduces the equality violation `count(confirmations) != count(live confirmers)` and results in `X` executing with the same nominal count but a lower real threshold of live signers, matching the "multisig request executed below threshold" Critical impact category.
