### Title
Unchecked ERC20 `transfer` in `MerkleClaim.claim` marks the claim as used even when the transfer silently fails, permanently locking the claimant's allocation - (File: contracts/MerkleClaim.sol)

### Summary
`MerkleClaim.claim` sets `hasClaimed[to] = true` and then calls a raw `IERC20Upgradeable(token).transfer(to, amount)` without checking the boolean return value. ERC20 tokens that return `false` instead of reverting on failure (the "no-revert-on-failure" class) cause the function to complete successfully while no tokens move. Because `hasClaimed` is already set, the claimee can never retry — the allocation is permanently locked. This is the same bug class as the Footium `claimERC20Prize` finding: state is committed before an unchecked token transfer.

### Finding Description
In `claim` at `contracts/MerkleClaim.sol:52-67`:

```solidity
// Set address to claimed
hasClaimed[to] = true;
// Transfer tokens to claimee
IERC20Upgradeable(token).transfer(to, amount);
```

- `token` is an arbitrary ERC20 set once via `initialize` (`MerkleClaim.sol:37-44`), so the contract does not constrain which token is distributed.
- With a no-revert-on-failure token (e.g., tokens in the `weird-erc20` "returns false" class, or a token paused for the recipient that returns `false`), `transfer` returns `false`, the call succeeds, and `hasClaimed[to]` is already `true`.
- Any subsequent `claim` call reverts with `AlreadyClaimed()` at line 54, so the user cannot retry.
- The only escape is `sweep` (line 69), which is gated to `TL_MULTISIG` and only after 60 days — an honest privileged role, not a guaranteed recovery path for the claimant.

The rest of the codebase consistently uses `SafeERC20.safeTransfer` (e.g., `IdleCDOEpochQueue.claimWithdrawRequest`, `DefaultDistributor.claim`, `IdleCreditVault._transferFundedClaim`), which would revert on a `false` return. `MerkleClaim` is the lone production path using the raw `transfer` after committing claim state, and its checks-effects pattern makes the bug exploitable rather than self-correcting.

### Impact Explanation
Permanent loss of the claimant's allocated tokens. If `transfer` returns `false`, the user receives nothing, the merkle allocation is consumed, and the tokens remain in the `MerkleClaim` contract until the timelocked multisig `sweep` (≥ 60 days) — which sends them to an address of the multisig's choosing, not to the claimant. One receipt, zero payout: the "one claim one payout" invariant is broken.

### Likelihood Explanation
Requires the distributed `token` to exhibit no-revert-on-failure behavior and the transfer to fail for the claimant (insufficient contract balance is the most common trigger — e.g., the contract was funded for less than the merkle total, or a prior partial `sweep`). No attacker action is needed; the victim is an unprivileged claimee calling `claim` on their own allocation. Failure is deterministic once the conditions hold, and the loss is irreversible from the user's perspective.

### Recommendation
Use `SafeERC20Upgradeable.safeTransfer` (the contract already imports OZ upgradeable libs) or check the return value, and/or move `hasClaimed[to] = true` after a verified successful transfer:

```solidity
IERC20Upgradeable(token).safeTransfer(to, amount);
hasClaimed[to] = true;
```

Apply the same fix to `sweep` (line 74), which also ignores the return value.

### Proof of Concept
Foundry PoC sketch (a `FalseOnTransfer` mock whose `transfer` returns `false` when its own balance is insufficient or for a flagged recipient):

```solidity
function test_claim_silentTransferFailure_locksClaim() public {
    // Deploy mock token that returns false instead of reverting on failure
    FalseERC20 tok = new FalseERC20();
    MerkleClaim mc = new MerkleClaim();

    bytes32 leaf = keccak256(bytes.concat(keccak256(abi.encode(user, AMOUNT))));
    mc.initialize(leaf /* single-leaf root */, address(tok));

    // Fund contract with less than AMOUNT (or flag `user` so transfer returns false)
    tok.mint(address(mc), AMOUNT - 1);
    tok.setReturnFalse(true);

    bytes32[] memory proof = new bytes32[](0);
    mc.claim(user, AMOUNT, proof);          // succeeds; transfer returns false

    assertEq(tok.balanceOf(user), 0);        // user got nothing
    assertTrue(mc.hasClaimed(user));         // claim consumed
    vm.expectRevert(MerkleClaim.AlreadyClaimed.selector);
    mc.claim(user, AMOUNT, proof);          // retry impossible
}
```

Expected result: `claim` completes without reverting, the user receives zero tokens, and `hasClaimed` permanently blocks retry — demonstrating the locked-funds outcome with a standard no-revert-on-failure ERC20 mock.
