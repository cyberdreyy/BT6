## Title
Reorg-permit authorization not bound to the requesting tenure allows a signer to sign a conflicting/non-canonical block — (File: `stacks-signer/src/v0/signer.rs`)

## Summary
The signer's "reorg permit" mechanism records a one-time authorization ("tenure X may replace tenure Y") when `check_parent_tenure_choice` sanctions a specific miner-tenure transition. That authorization is persisted keyed only to the **victim** tenure (`Y`) and is later "redeemed" by checking only whether the **original permit-holder's** sortition (`X`) is still canonical — never verifying that the block *currently* being considered for a signature is actually built by `X`. Any later, unrelated tenure `Z` whose block conflicts (same/overlapping height) with `Y`'s previously-signed block inherits `Y`'s standing permit "for free," letting the signer place a fresh signature over `Z`'s block even though the reorg-timing rules were only ever evaluated for `X`, not `Z`.

## Finding Description
The permit is created in `check_parent_tenure_choice` / `record_superseded_tenure`: [1](#0-0) 

and persisted with `mark_tenure_superseded`, keyed by the **victim** tenure's `consensus_hash` and carrying the permitting tenure's identity (`superseded_by_consensus_hash` / `superseded_by_burn_block_hash`): [2](#0-1) 

`get_signed_conflicts` joins every previously-signed block with any standing permit on its own tenure: [3](#0-2) 

`reorg_permit_stands` then validates the permit purely by asking whether the **recorded permit-holder's** sortition is still canonical: [4](#0-3) 

Crucially, the consumer of this check — the fresh cross-tenure conflict guard inside `handle_block_pre_commit` — never compares the permit's `superseded_by_consensus_hash` to the tenure of the block *actually being signed right now*: [5](#0-4) 

Contrast this with the *stale, own-tenure* branch a few lines later, which does bind the conflict to the current candidate's own tenure (`conflict.consensus_hash == block_info.block.header.consensus_hash`): [6](#0-5) 

No equivalent binding exists in the first (fresh-conflict) branch. As a result, once tenure `X` is granted a permit to replace tenure `Y`, that permit's exclusion of `Y`'s conflicts is honored for *any* subsequent candidate block at a qualifying height — not only for blocks that are actually part of `X`'s tenure. The signature is an "equality" between (block actually authorized to reorg) and (block currently receiving a signature); the code instead checks only (permit-holder's sortition canonical?) and silently drops the "is the current candidate that permit-holder?" clause. This is directly analogous to the Keycloak flaw: an authorization artifact minted for one specific privileged action (`ExecuteActionsActionToken` for enrolling a specific credential / here, tenure `X` reorging `Y`) is accepted as valid for a different action it was never issued for (tenure `Z` reorging `Y`), because the validator checks only "is this token/permit still alive" and not "is this the actor/action it was issued to."

## Impact Explanation
This is a Critical-class break: it lets a signer place a valid signature on a block that has not passed the reorg-timing safety rules (`check_parent_tenure_choice`) for the tenure actually proposing it — i.e., a signer signing a conflicting/non-canonical block. Because a signer's signature is a "bearer instrument" that counts toward the 70% threshold and cannot be revoked, this can contribute to an illegitimate reorg being finalized without every signer's independent evaluation of the rules that are supposed to gate that specific reorg.

## Likelihood Explanation
Reachable by a single miner/tenure sequence plus normal gossip, no majority of signers or additional keys required:
1. A tenure `X` legitimately earns a reorg permit over tenure `Y` (per `check_parent_tenure_choice`), while `Y` already has a signer-signed block `A`.
2. `X`'s sortition remains canonical afterward (the permit stays "standing").
3. A later, distinct tenure `Z` (its own sortition win, e.g., after a further Bitcoin fork or a natural continuation) proposes a block `B` at a height that conflicts with `A`, with no other fresher conflicting sibling present at that height.
4. When `B` reaches the pre-commit threshold, `handle_block_pre_commit`'s conflict loop finds `A` as the only fresh conflict, calls `reorg_permit_stands`, which returns `true` merely because `X`'s sortition is canonical — with no check that `B` belongs to `X`. `B` gets signed.

The main uncertainty is how frequently a second, unrelated tenure conflicting at the exact right height with a still-permitted victim block occurs in practice; this depends on burnchain fork timing that is out of the signer's control but achievable by an adversarial/faulty miner sequence.

## Recommendation
Bind the permit check to the actual requester: `reorg_permit_stands` (or its caller) must additionally verify that the block currently being evaluated (`block_info.block.header.consensus_hash`, and/or its ancestry) matches `conflict.superseded_by.consensus_hash` before excluding the conflict — i.e., only the tenure that was actually granted the permit may benefit from it. Any other candidate tenure hitting the same conflict must go through the full `conflict_still_blocks` freshness/liveness check unmodified.

## Proof of Concept
Conceptual reproduction (matches existing integration test scaffolding for reorg permits, e.g. `standing_reorg_permit_clears_conflict` in `stacks-signer/src/v0/tests.rs`):
1. Sign block `A` in tenure `Y` (height `h`).
2. Trigger `check_parent_tenure_choice` sanctioning tenure `X` to replace `Y` (single globally-accepted block in `Y`, produced too close to the next sortition) → `mark_tenure_superseded(Y, superseded_by=X)`. Keep `X`'s sortition canonical.
3. Instead of proposing through `X`, have a *different* tenure `Z` (a fresh sortition winner not derived from `X`) propose block `B` at height `h`, conflicting with `A`, without itself ever passing `check_parent_tenure_choice`'s rules against `Y`.
4. Drive `B` to the pre-commit threshold. Observe that `handle_block_pre_commit` signs `B` because `reorg_permit_stands` returns `true` for `Y`'s permit (still keyed to `X`), even though `B` is `Z`'s block, not `X`'s — demonstrating the missing binding described above.

    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";

                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";

                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
