### Title
`check_submitted_block_proposal` broadcasts a rejection before persisting the rejection, breaking the equivocation guard on restart/DB-write failure - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`check_submitted_block_proposal` in `stacks-signer/src/v0/signer.rs` reverses the checks-effects-interactions ordering that every other decision path in the signer uses: it calls `send_block_response` (the network broadcast) *before* calling `self.signer_db.insert_block(&block_info)` (the durable persistence of the just-made `mark_locally_rejected` decision).

### Finding Description
Every other place the signer makes a binding local decision persists it to `signer_db` first and only then broadcasts it, with an explicit comment marking this as a deliberate invariant:

- Accept path: `mark_locally_accepted` → `insert_block` → broadcast (`send_block_response`) [1](#0-0) 
- Validate-ok pre-commit path: `mark_pre_committed` → `insert_block` → `send_block_pre_commit` [2](#0-1) 
- Validate-reject path: `mark_locally_rejected` → `insert_block` → `handle_block_rejection` → `send_block_response` [3](#0-2) 

But in `check_submitted_block_proposal`, the timeout-driven rejection path is inverted: `mark_locally_rejected` is applied to the in-memory `block_info`, then `send_block_response` broadcasts the rejection to the network immediately, and only afterward is `insert_block` called to persist it to `signer_db`: [4](#0-3) 

This is the direct structural analog of the reported bug class: an externally-observable action (the callback/broadcast) is emitted while a state update that should logically precede it (durable persistence of the local rejection decision) is deferred to after that action. `insert_block`'s failure path does not abort or roll back the broadcast — it only logs via `self.handle_insert_block_error(e)` — so a DB write failure, or a process crash/restart occurring in the narrow window between the broadcast and the persist call, leaves the network having received a public rejection for this block while the signer's own durable state (`signer_db`) has no record that this block was ever rejected.

### Impact Explanation
This breaks the equivocation guard the signer relies on for safety across restarts. On restart, or after this insert silently fails, `signer_db` no longer shows this block as `LocallyRejected`; the block's `valid`/state fields are effectively back to unset for the purposes of future re-evaluation. If the block (or a re-proposal referencing the same tenure/height) is subsequently re-evaluated — e.g., via `handle_block_proposal`'s `should_reevaluate_block`/fresh-evaluation path, or through pre-commit replay (`process_pending_responses_for_block`) — the signer can now reach `mark_locally_accepted`/`mark_pre_committed` and sign a block it had already told the rest of the signer set it rejected, since there is no persisted record blocking that outcome. This is exactly the "losing the equivocation guard on restart" failure mode.

### Likelihood Explanation
The triggering condition — a stacks-node validation response failing to arrive within `block_proposal_validation_timeout` — is a normal, one-signer-triggerable condition (no majority or other signer's key needed; slow node RPC, restart, or node hiccup is sufficient). Any single signer instance hitting this timeout path, followed by a DB write hiccup or a process restart in that narrow window, reaches the divergent state.

### Recommendation
Move `self.signer_db.insert_block(&block_info)` before `self.send_block_response(...)` in `check_submitted_block_proposal`, matching the ordering used in every other decision path (`handle_block_validate_ok`, `handle_block_validate_reject`, `store_and_process_block_signature`), and treat an `insert_block` failure here as fatal to persist the rejection before it is ever broadcast to the network, rather than logging-and-continuing.

### Proof of Concept
1. A signer submits a block for validation via `submit_block_for_validation`; the stacks-node's response is delayed beyond `block_proposal_validation_timeout`.
2. `check_submitted_block_proposal` fires each pass through `process_event` [5](#0-4) , and after the timeout elapses it builds a `rejection`, calls `block_info.mark_locally_rejected()`, then `self.send_block_response(&block_info.block, rejection.into())` — broadcasting the rejection over StackerDB — and only then calls `self.signer_db.insert_block(&block_info)`.
3. If that `insert_block` call fails (or the process is killed/restarted immediately after the broadcast and before the write completes), `signer_db` retains no record of the rejection for this block.
4. On restart or on a later fresh evaluation of a re-proposal for the same block/height, the signer treats the block as unseen/undecided, and can proceed to `mark_pre_committed`/`mark_locally_accepted` and issue a signature for a block it already publicly rejected.
