### Title
Multisig executes requests using confirmations from members already deleted, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` removes a departing member from `self.members` and purges only the requests that member itself created, but never prunes that member's confirmation entries from `self.confirmations` on requests created by other members. `confirm()` counts `confirmations.len()` against `num_confirmations` without checking whether every entry in the confirmation set still corresponds to a current member. As a result, a request can execute with fewer than `num_confirmations` *currently authorized* signers.

### Finding Description
The binding that must hold is: `confirmations counted for a request` ⊆ `currently live members`. `confirm()` at [3](#0-2)  only checks `confirmations.len() as u32 + 1 >= self.num_confirmations` — it never re-validates that each string stored in the `HashSet<String>` still corresponds to an account in `self.members`.

`delete_member` at [4](#0-3)  removes the member from `self.members`, and cleans up only requests where `r.member == member`, i.e., requests the removed member *originated*:
```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
It does not iterate `self.confirmations` to strip the removed member's entry from confirmation sets belonging to requests originated by *other* members. Any pending request that the soon-to-be-removed member had already confirmed retains that confirmation permanently. The same gap exists in the older `multisig/src/lib.rs` `DeleteKey` handling at [5](#0-4) , which is scoped by public key equality in the same limited way.

Before: `num_confirmations = 3`, members = {A, B, C, D}. A creates request R, B confirms R (`confirmations(R) = {B}`), C confirms R (`confirmations(R) = {B, C}`, still below 3, not yet executed).
Attack path: A separate multisig request removes member B (`DeleteMember{B}`) — `self.members = {A, C, D}`, but `confirmations(R)` still contains `B`.
After: D confirms R. `confirmations.len() + 1 = 3 >= num_confirmations (3)` → request executes, counting B's stale confirmation as one of the three, even though only A/C/D (and D is confirming) — effectively 2 live confirmations (C, D) plus a phantom one from removed B satisfy a 3-of-4 threshold that should require 3 of the *current* 3 remaining members.

### Impact Explanation
This breaks the multisig's core custody guarantee: a `Transfer`, `AddKey`, or other privileged `MultiSigRequestAction` can be executed with fewer live-member confirmations than `num_confirmations` mandates, i.e., "a multisig request executed below threshold" — a Critical-severity impact per the given classification, since it permits movement of NEAR funds or contract-controlling key changes without the intended quorum of currently-trusted signers.

### Likelihood Explanation
Requires no privileged access beyond being an existing multisig member who requests removal of another member (a normal governance action) while a pending, partially-confirmed request from a third member is outstanding — a plausible, low-friction sequence of ordinary multisig operations, not requiring any redeploy, victim key compromise, or off-chain assistance.

### Recommendation
On `delete_member`, iterate over `self.confirmations` for all outstanding requests (not only ones originated by the removed member) and remove the deleted member's entry from each confirmation set; alternatively, re-validate at `confirm()` time that every stored confirming identity is still present in `self.members` before counting it toward the threshold.

### Proof of Concept
1. Initialize `MultiSigContract::new(members: [A, B, C, D], num_confirmations: 3)`.
2. As A: `add_request_and_confirm(Transfer{...})` → request R, `confirmations(R) = {A}`.
3. As B: `confirm(R)` → `confirmations(R) = {A, B}` (2 < 3, pending).
4. As A/C/D (2 of remaining 3, satisfying quorum for a `DeleteMember` request): submit and confirm `DeleteMember{member: B}` — executes, `self.members = {A, C, D}`.
5. As C: `confirm(R)` → `confirmations(R).len() + 1 = 3 >= 3` → `execute_request` fires the `Transfer`, even though B (whose confirmation is counted) is no longer a member and only A and C among *current* members actually confirmed. [4](#0-3) [3](#0-2)
