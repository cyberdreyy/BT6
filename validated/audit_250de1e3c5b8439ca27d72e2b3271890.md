### Title
`accountSubscribe` silently discards `minContextSlot`, allowing subscribers to receive notifications built from stale bank state - (File: rpc/src/rpc_pubsub.rs)

### Summary
The `RpcSolPubSubImpl::account_subscribe` handler destructures `RpcAccountInfoConfig` but explicitly drops the caller-supplied `min_context_slot` field instead of honoring it, so a subscriber's freshness requirement is silently ignored, mirroring the reported bug class where a user-configurable parameter is accepted by the API but never actually used in the resulting behavior.

### Finding Description
`RpcAccountInfoConfig` includes a `min_context_slot` field that is meant to let a caller require that only data at or above a certain slot be used. In the JSON-RPC HTTP `getAccountInfo`/`getMultipleAccounts`/`getProgramAccounts` handlers, `min_context_slot` is correctly forwarded into `RpcContextConfig` and used by `get_bank_with_config` to select an appropriately fresh bank [1](#0-0) . However, in the pubsub `account_subscribe` implementation, the field is destructured and explicitly discarded with a comment marking it as ignored:

```rust
let RpcAccountInfoConfig {
    encoding,
    data_slice,
    commitment,
    min_context_slot: _, // ignored
} = config.unwrap_or_default();
``` [2](#0-1) 

The resulting `AccountSubscriptionParams` struct used by the subscription tracker/notifier has no field for `min_context_slot` at all [3](#0-2) , and the notification path (`notify_watchers`/`check_commitment_and_notify`) only ever considers `commitment`-derived slots (`highest_super_majority_root`, `highest_confirmed_slot`, or `commitment_slots.slot`) when deciding what bank to read the account from and what slot to report [4](#0-3) . There is no code path anywhere in `rpc_subscriptions.rs` that consults a minimum context slot for account subscriptions—confirmed by the fact that `min_context_slot` appears only in `rpc_pubsub.rs` (where it is read from the request and dropped) and nowhere in the subscription plumbing.

This exactly matches the reported bug class: a configuration value the client is allowed to set (`provider` in the analog report, `min_context_slot` here) is accepted at the API boundary but never propagated to the code that actually performs the underlying operation, so setting it has zero effect on behavior.

### Impact Explanation
An RPC subscriber who explicitly requests `minContextSlot` on `accountSubscribe` to avoid acting on data from a bank/fork that hasn't caught up to a known slot (e.g., after submitting a transaction and needing account state confirmed to be built from a sufficiently advanced bank) will silently receive notifications derived from an older bank/slot than requested, with no error or warning. This is a case of "wrong-slot/fork data returned" to an unprivileged caller via a single API call, since the guarantee the parameter is documented to provide is not enforced.

### Likelihood Explanation
Likelihood is high: any client (unprivileged) issuing `accountSubscribe` with `minContextSlot` set will trigger this every time, deterministically, with a single subscription request—no adversarial conditions or races needed.

### Recommendation
Add a `min_context_slot` field to `AccountSubscriptionParams` (and analogous program-account subscription params), pass it through from `account_subscribe`/`program_subscribe` instead of discarding it, and check it in `notify_watchers`/`check_commitment_and_notify` before selecting the slot/bank used to build a notification—skipping (or delaying) notification until the bank's slot satisfies the requested minimum, consistent with how `min_context_slot` is honored in the HTTP `getAccountInfo` path.

### Proof of Concept
1. Client calls `accountSubscribe` with `{"encoding": "base64", "minContextSlot": 1000}` while the node's current confirmed/processed slot used for account watchers is below 1000.
2. Because `min_context_slot: _, // ignored` drops the value at [5](#0-4) , the subscription is registered as `AccountSubscriptionParams { pubkey, commitment, data_slice, encoding }` with no slot floor.
3. `notify_watchers` computes the slot purely from `commitment` (e.g. `commitment_slots.slot` for `processed`) [6](#0-5)  and immediately notifies using account state from that (potentially < 1000) slot, even though the client explicitly asked to not receive data below slot 1000.
