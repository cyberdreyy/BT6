### Title
Stale cross-tenure sibling conflict bypasses the `conflict_still_blocks` liveness check, letting a signer sign two conflicting blocks at the same height - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`Signer::handle_block_pre_commit`'s conflict-resolution logic only re-verifies a conflicting signed block's liveness against the node (`conflict_still_blocks`/`reorg_permit_stands`) while that conflict is still "fresh" (`last_endorsed > freshness_cutoff`). Once a same-height, different-tenure sibling conflict goes stale, the code falls through to a second guard that only matches conflicts sharing the *proposed block's own* `consensus_hash`, silently skipping any node liveness check for a genuinely different-tenure sibling and proceeding straight to `SIGN`.

### Finding Description
`get_signed_conflicts` correctly returns every signed block at or above the proposed height in *any* tenure [1](#0-0) . In `handle_block_pre_commit`, the only branch that asks the node whether a conflict `conflict_still_blocks`/whether a reorg permit still stands is gated on freshness: [2](#0-1) 

If `A`'s `last_endorsed` timestamp has fallen behind `freshness_cutoff` (computed from this signer's own clock and its own `tenure_last_block_proposal_timeout`), this predicate is `false` for `A`, and no node lookup happens for it at all. The next block only re-derives liveness for conflicts whose `consensus_hash` equals the block being signed's own tenure: [3](#0-2) 

Since `A` is in tenure `CH1` and `B` is in tenure `CH2`, `conflict.consensus_hash == block_info.block.header.consensus_hash` is false for `A`, so this branch is also skipped, and the code proceeds directly to `SIGN` at line 1458 onward, logging only "none of those conflicts still blocks it" [4](#0-3) .

The comment justifying this ("A stale conflict in another tenure ... is settled by the chainstate checks above") relies on `check_block_against_signer_db_state`, run earlier at line 1345 [5](#0-4) . For a tenure-change block that check walks only the block's *parent* tenure via `check_tenure_change_confirms_parent`/`check_latest_block_in_tenure` [6](#0-5) , per the documented blind spot: "the re-check only ever looks at _one_ tenure ... so a signed sibling at the same height in a third tenure is invisible to it." When `A` (`CH1`) and `B` (`CH2`) are true siblings built on the *same* parent tenure, `A` is neither `B`'s own tenure nor `B`'s parent tenure, so neither the chainstate re-check nor the own-tenure conflict guard ever consults the node about `A`'s liveness once `A`'s signature has gone stale locally.

### Impact Explanation
This breaks the intended UNIQUENESS invariant that a signer never signs two conflicting blocks at the same height while the first could still be canonical — the signer's own comments describe `conflict_still_blocks`/`reorg_permit_stands` as the mandatory backstop for exactly this case, yet the stale/cross-tenure path bypasses it entirely. This matches the Critical category ("a signer signing an invalid, non-canonical, or conflicting block") for the affected signer's own weight.

However, to turn this into the claimed "chain split" (both A and B independently reaching aggregate 70% signature weight), a supermajority of signers would need to independently race through the identical stale-conflict window — i.e., most of the signer set would need to have already signed `A` and then experience their individual `tenure_last_block_proposal_timeout` elapse before `B` reaches pre-commit threshold. That requires majority-signer synchronization/clock-skew across most of the network, which the rules explicitly disallow as an attacker capability (the attacker holds only one miner slot and gossip, not a majority of signers). A single miner slot can at best induce this double-sign in whichever subset of signers happen to race into the stale window on their own — a real per-signer safety violation, but not a demonstrated, reliable mechanism for causing the two-fully-signed-conflicting-blocks chain-split scoped in the question.

### Likelihood Explanation
Preconditions are narrow: two literal sibling tenure-start blocks from the same parent, in different tenures, where a given signer already has `signed_self` set on the first and then crosses pre-commit threshold on the second only after its own freshness window elapses. This is plausible for isolated signers when proposals are timed close to the `tenure_last_block_proposal_timeout` boundary, but reliably reproducing it across enough signer weight to matter for consensus safety (rather than just one signer's local state) is not shown to be achievable with one miner slot; it depends on independent per-signer timing that the attacker does not control precisely, and is closer to a race condition than a deterministic exploit.

### Recommendation
For a stale conflict in a tenure that is neither the proposed block's own tenure nor its parent tenure, still invoke `conflict_still_blocks`/`reorg_permit_stands` (or an equivalent node-derived liveness check) before signing, rather than assuming the chainstate re-check already covers it — since that re-check is proven not to see genuine sibling-tenure conflicts.

### Proof of Concept
Extend `run_sibling_scenario` in `stacks-signer/src/v0/tests.rs` to construct `block_a` and `block_b` with *different* `consensus_hash` values (`CH1`/`CH2`) but the same parent and chain_length, so they are true cross-tenure siblings rather than the existing same-tenure variant. Drive the state machine to `signed_self` on `A`, advance the local clock past `tenure_last_block_proposal_timeout` (making `A` stale per `freshness_cutoff`), configure the mock node's `/v3/tenures/tip_metadata` for `A`'s tenure to still report `A` as the live tip (simulating peers/node still treating `A` as canonical), then drive `B` to the pre-commit threshold. Assert that the signer nonetheless signs `B` (`mark_locally_accepted` called, `BlockAccepted` broadcast) despite the node's tip for `A`'s tenure still reporting `A` as canonical — i.e., assert `conflict_still_blocks`/`reorg_permit_stands` were never invoked for the `A` conflict, evidencing the missing liveness check on both sides of the equality (`A` still canonical per node vs. signer nonetheless signing `B`).

                    "Miner's block proposal does not confirm as many blocks as we expect";
