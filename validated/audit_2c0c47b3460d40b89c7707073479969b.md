### Title
APR0 withdraw receipt + mid-epoch APR change permanently reverts `stopEpoch`, freezing the epoch - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` hard-reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. An unprivileged KYC-passed lender can create a non-zero `apr0TotalPrincipal` simply by calling `IdleCDOEpochVariant.requestWithdraw` during a zero-APR epoch. If the honest manager then raises the APR mid-epoch via `setAprsWithBuffer`/`setApr` (an unrestricted manager action allowed during a running epoch), every subsequent `stopEpoch` / `stopEpochWithDuration` call reverts before `epochNumber` is bumped. This is the analog of CVE-2023-30570: an unauthenticated message (a user withdraw request) leaves responder-side state (`apr0TotalPrincipal`) that a later legitimate state transition (APR update) mishandles into a persistent crash of the epoch state machine.

### Finding Description
In `requestWithdraw` (IdleCDOEpochVariant.sol:739), when `unscaledApr == 0` the strategy records the request in the APR0 bucket via `_requestWithdrawApr0`, which increments `apr0TotalPrincipal` (IdleCreditVault.sol:567-577). The bucket is only cleared inside `prepareStopEpochWithApr0` at line 540 (`apr0TotalPrincipal = 0`), but that line is unreachable when the earlier guard at lines 506-508 reverts:

```solidity
// IdleCreditVault.sol:502-508
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

`prepareStopEpochWithApr0` is invoked at `IdleCDOEpochVariant.sol:362`, *outside* the `try this.getFundsFromBorrower(...)` block (lines 408-505), so the `NotAllowed` revert propagates and aborts the whole stop. `isEpochRunning` stays `true`, `epochNumber` is never incremented, deposits remain paused (`_pause()` at startEpoch), and all pending withdraw receipts stay unclaimable because `_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest[user]` (IdleCreditVault.sol:326). The revert condition is self-perpetuating: since `apr0TotalPrincipal` is never zeroed, the revert fires on every retry while `unscaledApr != 0`.

Sequence (attacker = ordinary KYC'd lender; manager remains honest):

1. Manager configures an epoch whose scaled APR resolves to `unscaledApr == 0` (an explicitly supported mode — `_requestWithdrawApr0` exists precisely for it).
2. Attacker deposits AA tranches (or uses an existing tranche balance) and calls `cdoEpoch.requestWithdraw(0, AATranche)` during the buffer/epoch-wait window. `apr0TotalPrincipal > 0`, `apr0Users[attacker].principalEpoch = epochNumber`.
3. Manager performs a routine mid-epoch APR correction: `IdleCreditVault.setAprsWithBuffer(10e18, ...)` or `setApr(_apr)` — permitted at any time by `manager` (IdleCreditVault.sol:217-235, no epoch-running guard).
4. Manager calls `stopEpoch` at `epochEndDate`. `prepareStopEpochWithApr0` sees `apr0TotalPrincipal != 0 && unscaledApr != 0` and reverts `NotAllowed`. Every retry reverts identically.

### Impact Explanation
Temporary/permanent freezing of all vault funds with quantifiable scope: every pending withdraw request (the entire `pendingWithdraws` bucket plus instant receipts) cannot be funded, because only a successful `stopEpoch` pulls borrower repayment via `getFundsFromBorrower`/`collectWithdrawFunds` and bumps `epochNumber`. All LP principal sits with the borrower while `isEpochRunning` blocks deposits (`paused()`) and blocks new withdraw requests (`allowAAWithdrawRequest == false`). The freeze lasts until the manager notices and manually reverts `unscaledApr` to 0 via `setApr`/`setAprsWithBuffer` — a recovery action the code gives no hint about — and any missed window means the borrower retains principal and epoch interest indefinitely. For a pool with TVL `T` and pending receipts `P`, `T + P` underlying is frozen for the duration of the outage.

### Likelihood Explanation
Likelihood is moderate. The trigger requires (a) a zero-APR epoch — a first-class supported configuration used by the APR0 flow and programmable-borrower-style setups, and (b) an honest manager APR adjustment mid-epoch, which `setApr` explicitly permits with no epoch-phase restriction. The attacker's only cost is a normal withdraw request on their own deposit (KYC + tranche tokens), and a single request of any size keeps `apr0TotalPrincipal` non-zero. No existing guard stops it: `requestWithdraw` has no APR-stability check, `setApr` has no `isEpochRunning`/`apr0TotalPrincipal` guard, and the revert in `prepareStopEpochWithApr0` cannot be bypassed by any stopEpoch parameter because it fires before interest resolution completes.

### Recommendation
Do not revert on a stale APR0 bucket. Options:

- In `prepareStopEpochWithApr0`, when `unscaledApr != 0`, settle the APR0 bucket at zero interest (`apr0RateByEpoch[epochNumber] = 0`, `apr0TotalPrincipal = 0`) instead of reverting — requesters still get their principal back via `settledPrincipal` in `_settleApr0`.
- Alternatively, snapshot the APR at request time (store it in `Apr0UserData`/`apr0RateByEpoch` context) and treat a later APR change as simply "APR0 accrues 0 interest for that epoch".
- Optionally also block `setApr`/`setAprsWithBuffer` while `apr0TotalPrincipal != 0`, forcing APR changes to go through `stopEpoch` where the bucket can be closed atomically.

### Proof of Concept
Foundry fork PoC (modeled on `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `_depositWithUser`):

```solidity
function testPocApr0StopEpochDos() external {
    // Configure a zero-APR epoch (APR0 mode is supported natively)
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprsWithBuffer(0, cdoEpoch.epochDuration(), cdoEpoch.bufferPeriod());

    // Attacker: ordinary KYC'd lender deposits and requests withdraw
    uint256 amountWei = 10000 * ONE_SCALE;
    _depositWithUser(attacker, amountWei, true); // tranche tokens + strategy tokens held
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // APR0 bucket: apr0TotalPrincipal > 0
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // Epoch runs with APR 0
    _startEpochAndCheckPrices(0);

    // Honest manager adjusts APR mid-epoch (allowed: no epoch-running guard on setApr)
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setApr(10e18); // unscaledApr != 0 while apr0TotalPrincipal != 0

    // stopEpoch now reverts forever
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Retry also reverts — state is self-perpetuating
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Consequences: epochNumber never bumps, claims revert, deposits stay paused
    assertTrue(cdoEpoch.isEpochRunning());
    vm.prank(attacker);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest(); // epochNumber <= lastWithdrawRequest[attacker]

    // Only recovery: manager manually zeroes APR again, then stop succeeds
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setApr(0);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
}
```
