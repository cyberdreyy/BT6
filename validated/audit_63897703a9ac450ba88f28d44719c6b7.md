## Analysis

The Gateway bug is a classic **signature-replay** bug class: a signed authorization message has no binding to a nonce/state, so once consumed and later "revoked", the same signature can be resubmitted to re-create the authorized state. Searching the consensus-specs, the closest analog is EIP-8205's `PreregistrationRequest` / withdrawal-credentials pre-registration mechanism.

### Root cause

`is_valid_preregistration_signature` verifies a signature over just `(pubkey, withdrawal_credentials)` with a domain that intentionally omits any nonce, slot, or replacement counter: [1](#0-0) 

The design note even states this is deliberately "fork-agnostic ... like a deposit signature," but unlike deposits (which are idempotent — reapplying one only tops up a balance harmlessly), a preregistration binding is **mutable state that can be created, consumed, and expire**, then be resurrected verbatim: [2](#0-1) 

`process_preregistration_request` only rejects a request if there is currently an *active* binding, if the pubkey already has a validator, or if it has a pending deposit — it never checks whether this exact signed request has been used/expired/replaced before: [3](#0-2) 

Once a binding expires (`is_active_preregistration` returns false after `PREREGISTRATION_EXPIRY_SLOTS`) or is consumed by a matching deposit (`remove_stored_preregistration`), the *exact same on-chain, publicly-visible* `PreregistrationRequest` (pubkey, old withdrawal_credentials, signature) can be resubmitted by anyone to recreate the old, stale binding: [4](#0-3) [5](#0-4) 

`process_deposit_request` then silently discards any deposit whose withdrawal credentials don't match the active (attacker-resurrected, stale) binding: [6](#0-5) 

### Concrete attack

1. Validator owner of pubkey `P` preregisters withdrawal credentials `WC_A` (signature `S1` over `(P, WC_A)`), then decides against it and lets it expire (or it's superseded), so no active binding remains.
2. Owner intends to actually deposit `P` with the correct, current credentials `WC_B`.
3. Any unprivileged actor observes the old `S1` (already public on-chain history) and resubmits `PreregistrationRequest(P, WC_A, S1)` right before the owner's deposit lands. `process_preregistration_request` re-admits it because there is no currently active binding for `P`.
4. The owner's legitimate deposit with `WC_B` now fails the credential check in `process_deposit_request` (`WC_B != WC_A`) and is silently discarded — the deposited Gwei is not applied to any pending deposit/validator, i.e., effectively destroyed with no recourse, without the owner's authority.

This mirrors the reported bug exactly: a signature that was implicitly "revoked" (superseded/expired) is replayed by an unrelated party to reinstate state the legitimate signer no longer authorized, causing funds loss.

### Title
Preregistration signature replay allows resurrecting expired/stale withdrawal-credential bindings and causing silent deposit loss — (`specs/_features/eip8205/beacon-chain.md`)

### Summary
`PreregistrationRequest` signatures in EIP-8205 are not bound to any nonce, counter, or one-time-use marker. After a preregistration binding expires or is otherwise no longer the signer's intent, the identical previously-broadcast signature can be resubmitted by any party to recreate the stale binding, causing a subsequent legitimate deposit with different (correct) withdrawal credentials to be silently discarded by `process_deposit_request`.

### Finding Description
`is_valid_preregistration_signature` only checks that `signature` is valid over `ValidatorPreregistration(pubkey, withdrawal_credentials)` under a fixed, nonce-less domain [7](#0-6) . `process_preregistration_request` admits any request whenever there is currently no *active* binding for the pubkey (i.e., expired via `is_active_preregistration`, or never consumed) [3](#0-2) , with no check that the specific `(pubkey, withdrawal_credentials, signature)` tuple was already used and should stay retired. Because the signature never changes and there is no replay-protection state analogous to a used-signature set, anyone who has observed the historical request (public in execution-payload history) can resubmit it verbatim once the binding it created lapses.

### Impact Explanation
A resurrected stale binding causes `process_deposit_request` to reject (silently discard) any subsequent deposit whose `withdrawal_credentials` doesn't match the resurrected binding [8](#0-7) . Since deposit-triggering ETH is transferred at the execution layer before this beacon-chain-level admission check runs, a discarded deposit request results in Gwei that is not credited to any validator — effectively destroyed — with no error surfaced and no path to reapply it, all triggered by a party with no authority over the target pubkey.

### Likelihood Explanation
The attack requires only public information (a previously broadcast, now-expired `PreregistrationRequest`) and the ability to submit an ordinary execution-layer request — no validator keys, no coalition, no client bug. It is timing-sensitive (the attacker must resubmit before the legitimate depositor's request lands) but is fully within the unprivileged threat model the report describes: "any user can reuse [a] signature."

### Recommendation
Bind preregistration signatures to a use-once/replacement-safe context, e.g., include a monotonically increasing nonce or the previous binding's identifier/expiry in the signed `ValidatorPreregistration` payload, and/or retain a marker (e.g., a hash of consumed/expired requests) so that `process_preregistration_request` rejects a `(pubkey, withdrawal_credentials, signature)` tuple that has already been admitted once, mirroring the fix applied to `Gateway.updateKeys()` (track used signature hashes and reject reuse).

### Proof of Concept
Conceptual state-transition trace using existing spec functions:
1. `state.validator_preregistrations` empty for pubkey `P`.
2. Apply `PreregistrationRequest(P, WC_A, S1)` via `process_preregistration_request` → stored with `expiry_slot = slot0 + PREREGISTRATION_EXPIRY_SLOTS`.
3. Advance `state.slot` past `expiry_slot` (or the record is otherwise removed by `remove_stored_preregistration` during an unrelated flow) → `get_active_preregistration(state, P)` returns `None`.
4. Attacker resubmits the identical `PreregistrationRequest(P, WC_A, S1)` → `process_preregistration_request` re-admits it because no active binding exists and `is_valid_preregistration_signature` still verifies (same signature, same message).
5. Legitimate owner submits `DepositRequest(P, WC_B, amount, sig_B)` intending to activate with new credentials `WC_B` → `process_deposit_request` finds active (attacker-resurrected) preregistration with `withdrawal_credentials == WC_A != WC_B` and returns early, discarding the deposit without crediting any pending deposit — funds lost, without the pubkey owner's authorization.

def is_valid_preregistration_signature(state: BeaconState, request: PreregistrationRequest) -> bool:

        pubkey=request.pubkey,

```markdown
def process_preregistration_request(state: BeaconState, request: PreregistrationRequest) -> None:
    pubkey = request.pubkey

    # An active binding for this pubkey makes the new request a no-op,
    # whether the duplicate is exact or conflicting
    if get_active_preregistration(state, pubkey) is not None:
        return

    # A pubkey with an existing validator cannot be preregistered
    if pubkey in [validator.pubkey for validator in state.validators]:
        return

    # A pubkey with a valid pending deposit cannot be preregistered
    if is_pending_validator(state.pending_deposits, pubkey):
        return

    # The capacity check counts only active records, so the timing of the
    # garbage-collection sweep does not affect admission. It applies to
    # appends and to replacements alike, since both create an active binding
    active_preregistrations = [
        preregistration
        for preregistration in state.validator_preregistrations
        if is_active_preregistration(state, preregistration)
    ]
    if len(active_preregistrations) >= PREREGISTRATIONS_LIMIT:
        return

    if not is_valid_preregistration_signature(state, request):
        return

    preregistration = StoredPreregistration(
        pubkey=pubkey,
        withdrawal_credentials=request.withdrawal_credentials,
        expiry_slot=state.slot + PREREGISTRATION_EXPIRY_SLOTS,
    )
    index = get_stored_preregistration_index(state, pubkey)
    if index is not None:
        # Replace the expired record in place
        state.validator_preregistrations[index] = preregistration
    else:
        state.validator_preregistrations.append(preregistration)
```

```markdown
def process_deposit_request(state: BeaconState, deposit_request: DepositRequest) -> None:
    # [New in EIP8205]
    preregistration = get_active_preregistration(state, deposit_request.pubkey)
    if preregistration is not None:
        if deposit_request.withdrawal_credentials != preregistration.withdrawal_credentials:
            return

        if not is_valid_deposit_signature(
            deposit_request.pubkey,
            deposit_request.withdrawal_credentials,
            deposit_request.amount,
            deposit_request.signature,
        ):
            return

        remove_stored_preregistration(state, deposit_request.pubkey)
```
