### Title
Mid-epoch deposits over-credit interest by charging for a buffer period the borrower never holds the funds - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`depositDuringEpoch` computes the extra expected interest for a mid-epoch deposit as `_calcInterest(_amount) * (remaining + bufferPeriod) / (epochDuration + bufferPeriod)`. The base `_calcInterest` only covers `epochDuration` of interest, while the numerator silently adds the full buffer period — a period during which the deposited funds are no longer lent out. The result is an over-credited interest claim that is added to `expectedEpochInterest` and used to over-mint tranche shares to the depositor.

`_calcInterestWithApr` returns `_amount * apr * epochDuration / year` — interest for a *full epoch only*. It contains no buffer-period component. The scaling comment claims "_calcInterest already gives full-epoch + full-buffer interest", but the code does not include `bufferPeriod` in the base.

The deposited underlyings are transferred to the borrower at line 732 and are owed back at `stopEpoch` — i.e. the borrower holds them for `remaining = epochEndDate - block.timestamp`, not `remaining + bufferPeriod`. During the buffer the funds sit in the vault for claim settlement and earn nothing for the depositor. Therefore the correct pro-rata claim is `fullInterest * remaining / epochDuration`. The implementation instead credits `fullInterest * (remaining + buffer) / (epochDuration + buffer)`, which is strictly larger whenever `bufferPeriod > 0` and `remaining < epochDuration`.

The overstated `interest` is then both (a) added to `expectedEpochInterest` (line 728), increasing the amount pulled from the borrower at `stopEpoch`, and (b) fed into the mint formula (line 724), minting the depositor `(amount + trancheInterest) * supply / expectedFinal` shares — a claim on principal plus an inflated yield.

### Impact Explanation
An attacker who is a KYC-passing lender calls `depositDuringEpoch` (requires `isDepositDuringEpochDisabled == false`, epoch running, non-AYS, non-programmable mode) and receives tranche shares representing principal plus interest for `remaining + bufferPeriod`, while the funds they supplied only generate interest for `remaining`. The excess is quantifiable:

`excess = amount * apr/yr * epochDuration * bufferPeriod / (epochDuration + bufferPeriod)` approximately (exact: `amount * apr/yr * bufferPeriod * (epochDuration - remaining) / (epochDuration + bufferPeriod)`).

Concrete numbers: 365-day epoch, 30-day buffer, 10% APR, deposit of 10,000,000 USDC one second before `epochEndDate` (`remaining ≈ 0`):
`excess ≈ 10M * 0.10 * 30/365 * 365/395 ≈ 75,900 USDC` — about 0.76% of the deposit minted as unearned yield.

This excess is funded either by the borrower (who is asked to repay `expectedEpochInterest` inflated by the phantom buffer interest — a transfer from an honest party to the attacker) or, if the borrower repays only the contractual amount, by triggering a shortfall/default that is socialized across tranche holders. Either way it breaks the fair mint/burn and solvency invariants: one unit of deposited principal yields more than the time-proportional interest it earned.

### Likelihood Explanation
Requires `bufferPeriod > 0` (a supported configuration — the buffer exists specifically to space claims), the epoch running, `isDepositDuringEpochDisabled == false`, non-AYS and non-programmable mode, and the attacker passing `isWalletAllowed`. All of these are normal operating conditions; no privileged misbehavior is needed. The closer to `epochEndDate` the deposit, the larger the relative over-credit (the numerator retains `bufferPeriod` while real participation shrinks to zero). No existing guard catches it: `_guarded`, `_skimDonatedAssets`, and `_updateAccounting` run before the mint and do not bound the interest fraction.

### Recommendation
Align the prorating base with the actual interest-bearing period. If mid-epoch deposits earn interest only while funds are with the borrower, compute `interest = _calcInterest(_amount) * remaining / epochDuration`. If the intended design is that the borrower owes interest over `remaining + bufferPeriod`, then the base must be `_amount * (apr/100) * (epochDuration + bufferPeriod) / (365 days * ONE_TRANCHE_TOKEN)` so the ratio correctly scales a full-period interest. Add a unit test depositing at `epochEndDate - 1` asserting credited interest approaches zero (or the buffer-only amount, per the chosen design).

### Proof of Concept
```solidity
// Fork test against an IdleCDOEpochVariant deployment with bufferPeriod = 30 days,
// epochDuration = 365 days, strategy APR = 10e18 (10%), non-AYS, depositDuringEpoch enabled.
function testMidEpochDepositBufferOvercredit() external {
    // setup: existing AA liquidity so _trancheTotSupply > 0
    idleCDO.depositAA(1_000_000e6);
    _startEpoch(); // epochDuration = 365 days, bufferPeriod = 30 days

    // warp to 1 second before epoch end: remaining = 1
    vm.warp(cdoEpoch.epochEndDate() - 1);
    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    uint256 expectedIntPre = cdoEpoch.expectedEpochInterest();
    uint256 D = 10_000_000e6;
    deal(underlying, attacker, D);
    vm.startPrank(attacker);
    IERC20(underlying).approve(address(cdoEpoch), D);
    cdoEpoch.depositDuringEpoch(D, address(AAtranche));
    vm.stopPrank();

    uint256 credited = cdoEpoch.expectedEpochInterest() - expectedIntPre;
    // borrower only owes interest for ~1 second: ~0
    // credited = D * 0.10 * 365d/yr * (1 + 30d) / (365d + 30d)  ~=  D * 0.10 * 30d/yr
    assertGt(credited, 75_000e6); // attacker books ~76k of interest on funds held 1 second

    // attacker minted shares worth D + trancheShare(credited); at stopEpoch the
    // pool demands expectedEpochInterest from borrower, socializing/pulling the excess.
}
```
