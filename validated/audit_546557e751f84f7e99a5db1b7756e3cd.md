### Title
Stale rejection weight is never retracted when a signer flips its vote, permanently wedging block acceptance - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tallies per-block signer weight into `total_weight_approved` and `total_weight_rejected` using a single shared `responded_signers` set to gate idempotency. The `Accepted` branch unconditionally records the slot in `responded_signers` (its own idempotency check is `gathered_signatures.contains_key`), while the `Rejected` branch only adds rejection weight the *first* time `responded_signers.insert(slot_id)` returns `true`. Because a signer can legitimately re-evaluate and switch from Rejected to Accepted for the same `block_sighash` (per the comment in `handle_block_pre_commit` about reconsidering rejected blocks), its earlier rejection weight is never subtracted from `total_weight_rejected` even after it later accepts the block, causing `total_weight_approved + total_weight_rejected` to exceed `total_weight` and letting a stale reject tally alone cross the blocking-minority threshold.

### Finding Description
In `stackerdb_listener.rs`, the `Accepted` handler does: [1](#0-0) 
which increments `total_weight_approved` guarded only by `gathered_signatures.contains_key`, and unconditionally inserts `slot_id` into `responded_signers`.

The `Rejected` handler does: [2](#0-1) 
which increments `total_weight_rejected` only if `responded_signers.insert(slot_id)` returns `true` (i.e., first time responding at all, in either direction).

`responded_signers` is a single set shared across both accept and reject codepaths — it does not distinguish "responded with accept" from "responded with reject." Sequence that breaks the invariant:

1. Signer S (weight w) sends `Rejected` for block B first. `responded_signers.insert(slot_id)` → `true`; `total_weight_rejected += w`.
2. Later S changes its mind and sends `Accepted` for the same B (this is an explicitly anticipated scenario — see the comment in `stacks-signer/src/v0/signer.rs::handle_block_pre_commit`, "we do not change our votes on rejected blocks unless ... the reject reason allows us to reconsider," implying some reject reasons do permit a later Accept for the same block hash).
3. In the `Accepted` handler, `gathered_signatures.contains_key(&slot_id)` is `false` (S never accepted before), so `total_weight_approved += w` — correctly recording the new accept.
4. But `total_weight_rejected` is **never decremented**; S's weight is now counted in *both* tallies simultaneously.

`signer_coordinator.rs` consumes these tallies with rejection checked first and given priority over acceptance: [3](#0-2) 
Once `total_weight_rejected.saturating_add(weight_threshold) > total_weight` is true, the coordinator unconditionally returns `NakamotoNodeError::SignersRejected`, regardless of how high `total_weight_approved` climbs afterward — the `else if total_weight_approved >= weight_threshold` branch is never reached in that case.

This is directly analogous to the reported bug class: a value that should be re-derived/kept in sync with reality (the fee vs. amount relationship in the original report; here the rejected-weight tally vs. actual current votes) is instead a one-way accumulator that is allowed to grow stale, and the resulting mis-tally is used to make a binding decision (rejecting the block) without validating that the underlying assumption ("this weight of signers currently rejects the block") still holds.

### Impact Explanation
This is a liveness wedge (High): a single signer (or any small subset whose combined rejected weight crosses the `> 30%` blocking-minority line before flipping to accept) can cause the miner's `SignCoordinator` to permanently treat an otherwise-valid, sufficiently-approved block as rejected. The coordinator gives priority to the (now-stale) rejected tally over the accurate approved tally, so a block that legitimately reaches the 70% acceptance threshold can still be discarded as `SignersRejected`, stalling tenure/block production for that block hash. No majority of signers or extra keys are needed — this is triggerable by ordinary vote-flip behavior from a minority of signers combined with normal miner/gossip message flow.

### Likelihood Explanation
Vote flips from Reject to Accept on the same block hash are an anticipated, protocol-supported behavior per the code comments in `handle_block_pre_commit` regarding reconsideration of rejected blocks under certain reject reasons, so the preconditions are reachable through ordinary signer/miner interaction rather than a contrived edge case. However, I could not fully trace every reject-reason code path in `stacks-signer/src/v0/signer.rs` that permits a subsequent Accept for the same `block_sighash` within this session — the exact set of `RejectReason`s that allow reconsideration deserves direct confirmation.

### Recommendation
Track accept/reject responses per-slot with the specific direction (e.g., `HashMap<slot_id, ResponseKind>` instead of a single `responded_signers: HashSet`), and when a signer's response changes direction, retract its weight from the old tally before adding it to the new one, so `total_weight_approved` and `total_weight_rejected` always reflect the *current* set of votes rather than an append-only history.

### Proof of Concept
1. Configure a reward set where signer S has weight `w` such that `w + weight_threshold > total_weight` is not yet true alone, but combined with other genuine rejecters it can cross the blocking minority (`total_weight_rejected + weight_threshold > total_weight`).
2. Have S (and other signers as needed) send `BlockResponse::Rejected` for block B first, pushing `total_weight_rejected` across the blocking-minority line — this alone does not yet trigger `SignersRejected` because signer_coordinator only checks after status updates arrive.
3. Have S subsequently send `BlockResponse::Accepted` for the same B (representing a legitimate reconsideration). `total_weight_approved` increases by `w`, but `total_weight_rejected` is not decreased.
4. Have enough remaining signers accept so that `total_weight_approved` reaches `weight_threshold` (≥70%) — a legitimately signable block.
5. Observe that `signer_coordinator.rs`'s poll loop still hits `total_weight_rejected.saturating_add(weight_threshold) > total_weight` first (since it was never decremented) and returns `NakamotoNodeError::SignersRejected`, even though the block has actually reached the real acceptance supermajority.
