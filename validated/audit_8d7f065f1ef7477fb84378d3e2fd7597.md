### Title
Unprotected `initializeConfig()` Allows Any Caller to Set Malicious `BridgeConfig` in `BridgeCommittee` — (`File: bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig()` is an `external` function with no access-control modifier. Any caller can invoke it before the legitimate deployer and point the committee's `config` slot to an attacker-controlled `IBridgeConfig` implementation. Every downstream bridge operation in `SuiBridge` that resolves token addresses, chain IDs, and decimal conversions through `committee.config()` will then use the attacker-supplied values, enabling fund misdirection and permanent vault lock.

---

### Finding Description

`BridgeCommittee.sol` exposes two initializers. The first, `initialize()`, is correctly guarded by OpenZeppelin's `initializer` modifier. The second, `initializeConfig()`, carries **no access-control guard at all**:

```solidity
// bridge/evm/contracts/BridgeCommittee.sol  lines 63-66
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
``` [1](#0-0) 

The sole guard is a one-time check (`config == address(0)`). Because the function is `external` with no `onlyOwner`, `initializer`, or committee-signature requirement, any EOA or contract can race the deployer and call it first with an arbitrary `_config` address.

The `config` state variable is then consumed by every critical path in `SuiBridge` via `committee.config()`:

```solidity
// SuiBridge.sol  line 67
IBridgeConfig config = committee.config();
``` [2](#0-1) 

Affected operations include:
- `transferBridgedTokensWithSignatures` — resolves `tokenAddressOf`, `tokenSuiDecimalOf`, `chainID`, `isChainSupported`
- `bridgeERC20` / `bridgeETH` — resolves `isTokenSupported`, `tokenAddressOf`, `tokenSuiDecimalOf`, `chainID`
- `_transferTokensFromVault` — resolves `tokenAddressOf` to decide which asset to release from the vault [3](#0-2) 

---

### Impact Explanation

A malicious `IBridgeConfig` can return:

| Manipulated return value | Consequence |
|---|---|
| `tokenAddressOf(id) → attacker_token` | Vault releases the wrong ERC-20 on every committee-signed transfer |
| `tokenSuiDecimalOf(id) → 0 or 255` | Amount conversion overflows or underflows, corrupting transfer amounts |
| `isTokenSupported(id) → false` for all IDs | All `bridgeERC20` calls revert; user funds deposited to vault become permanently locked |
| `isChainSupported(id) → false` for all IDs | All outbound and inbound transfers revert; bridge is bricked |
| `chainID() → wrong value` | Target-chain validation in `transferBridgedTokensWithSignatures` always fails |

The most severe reachable outcome without committee collusion is **permanent fund lock**: a malicious config that returns `false` for every `isTokenSupported` / `isChainSupported` call makes the vault inaccessible to all users. This matches the High/Medium allowed impact class ("permanent fund lock, harmful smart-contract behavior").

---

### Likelihood Explanation

- The vulnerability window is the block interval between proxy deployment and the deployer's `initializeConfig` call.
- Any mempool observer (ordinary ETH holder, MEV bot) can front-run the transaction.
- No special privilege, stake, or committee membership is required.
- The attack is a single, cheap `external` call.

---

### Recommendation

Add an `initializer` modifier (so it can only be called once, atomically with `initialize`) **or** restrict it to the committee-signed upgrade path:

```solidity
// Option A – merge into the existing initializer
function initialize(
    address[] memory committee,
    uint16[]  memory stake,
    uint16    minStakeRequired,
    address   _config          // add this
) external initializer {
    // ... existing logic ...
    config = IBridgeConfig(_config);
}

// Option B – add onlyOwner / committee-signature guard
function initializeConfig(address _config)
    external
    verifyMessageAndSignatures(...)   // committee-signed
{
    require(address(config) == address(0), "already initialized");
    config = IBridgeConfig(_config);
}
```

The simplest safe fix is to pass `_config` directly into the existing `initialize()` call so both are covered by the `initializer` modifier in a single atomic transaction.

### Proof of Concept

```
Deployment sequence (normal):
  T0: deployer → proxy.initialize(committee[], stake[], minStake)
  T1: deployer → proxy.initializeConfig(legitimateConfig)   ← UNPROTECTED

Attack:
  T0: deployer → proxy.initialize(...)                      ← succeeds
  T1: attacker watches mempool, sees deployer's initializeConfig tx
  T1: attacker front-runs with proxy.initializeConfig(MaliciousConfig)
      MaliciousConfig.isTokenSupported() always returns false
  T1: deployer's tx reverts ("Config already initialized")

Result:
  - committee.config() → MaliciousConfig
  - SuiBridge.bridgeERC20() reverts for every tokenID
  - SuiBridge.transferBridgedTokensWithSignatures() reverts on chain/token checks
  - All assets already in BridgeVault are permanently inaccessible
``` [4](#0-3) [5](#0-4) [6](#0-5)
