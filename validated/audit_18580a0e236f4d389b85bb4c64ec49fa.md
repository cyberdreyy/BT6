### Title
Unbounded retry loop on `PipelineErrorKind::Temporary` in the fault-proof driver's `produce_payload` can hang the derivation pipeline forever - (File: crates/proof/driver/src/pipeline.rs)

### Summary
The `DriverPipeline::produce_payload` trait method used by the fault-proof/derivation client (`client_derivation_driver`) retries **any** `PipelineErrorKind::Temporary` error unconditionally via `continue`, with no attempt cap and no state-changing action taken between retries. If the underlying L1 data source repeatedly returns the same `Temporary(Provider(_))` error for the same requested block (state does not advance on failure), the loop spins forever instead of terminating. This mirrors CVE-2017-14058's bug class: a stage does not restrict "reload" attempts for data that can never become available, producing an infinite loop.

### Finding Description
`produce_payload` steps the pipeline in a loop and, on failure, dispatches by `PipelineErrorKind`: [1](#0-0) 

Unlike the online-node derivation actor, which only retries the specific `NotEnoughData` variant and yields on any other `Temporary` error ( [2](#0-1) ), and unlike the test harness which caps consecutive no-progress retries at 1000 ( [3](#0-2) ), `produce_payload` treats **every** `Temporary(_)` variant identically and retries with no bound.

The pipeline's `step()` only special-cases `Temporary(Eof)` (by calling `advance_origin()`); any other `Temporary` (e.g. `Provider(_)`) is surfaced directly as `StepFailed`: [4](#0-3) 

`advance_origin()` in the L1 traversal stage fetches `block.number + 1` from the data source and only updates internal state (`self.block`) on success; on failure the origin `block` is left unchanged, so a repeated call after a `continue` issues the exact same request and can fail with the exact same error indefinitely: [5](#0-4) 

A test in the same file confirms that a data-source gap surfaces as `PipelineErrorKind::Temporary(PipelineError::Provider(_))` rather than `Eof`: [6](#0-5) 

Since `Provider(_)` is a `Temporary` variant, `produce_payload`'s catch-all `Temporary(_) => continue` will retry it forever with no forward progress — the fault-proof-program analog of "does not restrict reload attempts for an insufficient [data] list," causing an infinite loop.

### Impact Explanation
`DriverPipeline::produce_payload` is used by `advance_to_target` in the fault-proof / zk client to derive and execute L2 blocks against a fixed preimage-oracle-backed L1/L2 data set ( [7](#0-6) ). Unlike a live node, this execution has no external mechanism to "wait for more data" — the oracle's backing data set is fixed for the duration of program execution. If the requested L1 block is genuinely and permanently unavailable from the oracle (e.g., a malformed or adversarial dispute-game claim/hint set, or a data window edge case), the pipeline enters a tight infinite loop with no timeout, consuming CPU/gas-metered execution resources forever and preventing the fault-proof program from ever producing an output root. This directly falls under the in-scope "fault-proof program" category and can result in a stuck dispute-game resolution / inability to produce a provable output root — a concrete node-halt-class impact on the specific proof execution.

### Likelihood Explanation
Reaching this requires only that `advance_origin`'s underlying provider fetch persistently fails for the requested L1 block during a fault-proof program run — a condition an adversarial dispute-game participant could attempt to engineer by proposing/disputing a claim whose derivation path requires L1 data outside what is hinted/available to the oracle, or by other data-availability edge cases in the fixed-window offline derivation context. The loop itself requires no special code path beyond entering `Temporary(Provider(_))`, which is a normal, reachable error class in the traversal stage.

### Recommendation
Add a bounded retry counter (or map persistent `Provider` errors from the offline/oracle-backed context to a `Critical`/`EndOfSource` error) in `DriverPipeline::produce_payload` for the `Temporary(_)` branch, mirroring the `no_progress > 1_000` guard already used in the test harness (`act_l2_pipeline_until`), so that non-recoverable temporary errors during fault-proof execution terminate deterministically instead of looping forever.

### Proof of Concept
1. Run the fault-proof/zk client (`advance_to_target`) against a preimage oracle whose L1 data window does not include the block that `PollingTraversal::advance_origin` requests (`block.number + 1`) for the disputed derivation range.
2. `advance_origin` returns `PipelineErrorKind::Temporary(PipelineError::Provider(_))` because `block_info_by_number` fails and `self.block` is left unchanged.
3. `step()` returns `StepResult::OriginAdvanceErr(Temporary(Provider(_)))`.
4. `produce_payload`'s `PipelineErrorKind::Temporary(_) => continue` re-enters the loop, re-issuing the exact same failing request forever, since no field influencing the query result changed — an unbounded infinite loop with no timeout in the fault-proof execution context.
