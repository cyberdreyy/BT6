Based on my research, the strongest analog in this codebase is in the Vault gateway handler, where a single "write methods enabled" gate blocks secret deletion the same way the pool's `enabled` flag blocked liquidity removal.

### Title
Vault gateway blocks secret deletion when write methods are disabled, preventing users from removing secrets during an incident - (File: core/services/gateway/handlers/vault/handler.go)

### Summary
The Vault gateway handler gates `Create`, `Update`, and `Delete` secret requests behind the same `writeMethodsEnabled` limiter. If an operator disables vault write methods (e.g., in response to an incident), users lose the ability to delete their own secrets, not just create/update them — mirroring the reported pattern where a single "disabled" flag improperly blocks a withdrawal/removal action that should remain available for user protection.

### Finding Description
`handleSecretsCreate`, `handleSecretsUpdate`, and `handleSecretsDelete` all call the identical check before forwarding the request to vault nodes: [1](#0-0) [2](#0-1) 

Each handler runs `h.writeMethodsEnabled.AllowErr(ctx)` and, if the gate is closed, rejects the request with `UnsupportedMethodError` and the message "vault write methods(create/update/delete) are disabled". This is the same architectural pattern the report criticizes: a single kill-switch gates both "risky" write operations (create/update secrets, i.e., adding new data) and the "safety" removal operation (delete secrets), instead of only gating the operations that pose write risk.

Unlike the Seawater pool case, I could not locate the `writeMethodsEnabled` limiter's settings definition (e.g., a `cresettings` key such as `VaultWriteMethodsEnabled`) or any doc/comment stating deletion should remain available while writes are otherwise disabled — the grep for such a setting key returned no matches, so I cannot confirm whether blocking deletes here is intentional operational policy (e.g., a full incident freeze) or an unintended side effect of reusing one gate for three semantically different operations.

### Impact Explanation
If an operator disables vault writes during an incident (e.g., suspected compromise, corrupted secret material, or overload), users are also unable to delete secrets they own. If the motivation for disabling writes is to let users get their own secrets to safety (analogous to withdrawing liquidity during a pool problem), this gate would prevent exactly that self-remediation action. This is a medium-impact availability/access-control issue only if `DeleteSecrets` is intended to remain available during a write freeze — which is unverified from the code and settings visible in this repo.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires (a) an operator to actually flip the `writeMethodsEnabled` gate off, which is presumably a deliberate, privileged administrative action, and (b) a scenario where users specifically need to delete secrets during that window. This is not remotely triggerable by an unprivileged actor on its own — it only manifests as a problem once the write-disable gate is engaged by an operator.

### Recommendation
Clarify the intended semantics of `writeMethodsEnabled`. If the intent (per the analog bug class) is that "disable" should only block operations that add or change data, split the gate so `handleSecretsDelete` uses a separate, more permissive check (or no check) that still allows secret removal while `handleSecretsCreate`/`handleSecretsUpdate` remain blocked. If the intent is a full write freeze covering deletes too, add documentation/comments clarifying that this is intentional so it isn't mistaken for the same class of bug as the reported liquidity-removal issue.

func (h *handler) handleSecretsCreate(ctx context.Context, ar *activeRequest) error {
	l := logger.With(h.lggr, "method", ar.req.Method, "requestID", ar.req.ID)

	err := h.writeMethodsEnabled.AllowErr(ctx)
	if errors.Is(err, limits.ErrorNotAllowed{}) {
		l.Warnw("secrets write method called but write methods are disabled", "error", err)
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.UnsupportedMethodError, errors.New("vault write methods(create/update/delete) are disabled: "+err.Error()), nil))
	} else if err != nil {
		l.Errorw("error checking if write methods are enabled", "error", err)
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("error checking if write methods are enabled: "+err.Error()), nil))
	}

	return h.fanOutToVaultNodes(ctx, l, ar)
}
