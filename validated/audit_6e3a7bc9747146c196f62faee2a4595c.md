## Title
`JsonRpcRequestProcessor::bank()` silently substitutes the root bank when the commitment-selected slot is missing from `BankForks`, returning wrong-slot data to unprivileged RPC callers - (File: `rpc/src/rpc.rs`)

## Summary
Every commitment-aware JSON-RPC handler (`getBalance`, `getAccountInfo`, `getVoteAccounts`, `getTokenAccountBalance`, `getSignatureStatuses`, etc.) resolves the `Bank` to query through `JsonRpcRequestProcessor::bank()`. This function looks up `BlockCommitmentCache` for the slot matching the caller's requested `commitment`, then fetches that slot from `bank_forks`. If the slot is not present in `bank_forks`, instead of returning an error to the caller, the code logs a warning and silently falls back to `r_bank_forks.root_bank()` — a different (older) bank than the one that was actually resolved for the requested commitment. [1](#0-0) 

This mirrors the analog bug class in the external report: an unvalidated/insufficiently-validated data source (there, a stale Chainlink round; here, a stale/missing `BankForks` entry) is consumed without a completeness or freshness check, and the function returns to the caller as if the data were correct for the requested parameters.

## Finding Description
`bank()` computes the target `slot` from `BlockCommitmentCache::slot_with_commitment` based on the caller-supplied `CommitmentConfig`, then does:
```rust
let r_bank_forks = self.bank_forks.read().unwrap();
r_bank_forks.get(slot).unwrap_or_else(|| {
    warn!("Bank with {:?} not found at slot: {:?}", commitment.commitment, slot);
    r_bank_forks.root_bank()
})
``` [2](#0-1) 

If `bank_forks.get(slot)` returns `None` — e.g., because the bank at that slot has already been pruned/purged from `BankForks`, or because `BlockCommitmentCache` and `BankForks` are momentarily out of sync (the surrounding comment explicitly acknowledges this race with `set_root`) — the function returns `root_bank()` instead of surfacing an error. All downstream RPC methods (`get_vote_accounts` at `rpc/src/rpc.rs:1155-1246`, `get_token_account_balance`/`get_token_supply` at `rpc/src/rpc.rs:2013-2074`, `get_signature_status`/`get_signature_confirmation_status` at `rpc/src/rpc.rs:1642-1670`, etc.) call `self.bank(commitment)` and proceed to compute and serialize results using whatever bank was returned, including embedding `bank.slot()` into the `RpcResponseContext` via `new_response()`. [3](#0-2) 

Because the substitution is silent, the response context's `slot` field and all values in the payload correspond to `root_bank()`'s state, not the state at the commitment level (or minimum slot) the client asked for — exactly analogous to the reported issue where an unchecked/stale oracle read is trusted and propagated into the return value (`quoteAmount`) without any indication to the caller that the underlying read was invalid or stale.

## Impact Explanation
An unprivileged RPC client that requests a specific commitment level can silently receive account/vote/token/signature data from an unrelated, older slot without any error or warning, while the response claims a slot value taken from that fallback bank. This can cause client-side wrong-slot/fork data consumption (e.g., a wallet or exchange integrator reading balances or transaction confirmation status that reflects stale chain state rather than the state the request contractually required). This falls into the accepted "wrong-slot/fork/account data returned" impact category from the Validate section.

## Likelihood Explanation
The fallback path is reachable through a normal single RPC request without any special privileges — the only requirement is a `commitment` selecting a slot that has been pruned from `BankForks` or a race between `BlockCommitmentCache` updates and `BankForks` root advancement, both of which the code's own comment identifies as a real, known condition ("it may occur after an old bank has been purged from BankForks and a new BlockCommitmentCache has not yet arrived").

## Recommendation
Do not silently substitute `root_bank()`. When `bank_forks.get(slot)` returns `None`, return an explicit RPC error (e.g., a `BlockNotAvailable`/`SlotNotFound`-style `RpcCustomError`) so callers cannot mistake stale/incorrect-slot data for the state they requested, mirroring how the oracle mitigation added explicit `require`/error checks rather than allowing an unvalidated fallback to be used as if it were valid.

## Proof of Concept
1. A client issues any commitment-aware RPC call (e.g., `getBalance`) with `commitment: "confirmed"` (or `finalized`).
2. `bank()` computes `slot` from `BlockCommitmentCache::slot_with_commitment`.
3. Before `bank_forks.get(slot)` executes, the corresponding bank is purged from `BankForks` (a normal, timing-dependent condition acknowledged in the code comments) or `BlockCommitmentCache` briefly lags behind `BankForks`'s root update.
4. `r_bank_forks.get(slot)` returns `None`; the code falls back to `r_bank_forks.root_bank()` and only logs a `warn!` — no error is returned to the RPC client.
5. The RPC method proceeds, and the client receives a normal, successful JSON-RPC response whose `context.slot` and account/vote/token data correspond to the root bank rather than the slot it actually requested, with no indication of the substitution. [4](#0-3)

```rust
    fn bank(&self, commitment: Option<CommitmentConfig>) -> Arc<Bank> {
        debug!("RPC commitment_config: {commitment:?}");

        let commitment = commitment.unwrap_or_default();
        if commitment.is_confirmed() {
            let bank = self
                .optimistically_confirmed_bank
                .read()
                .unwrap()
                .bank
                .clone();
            debug!("RPC using optimistically confirmed slot: {:?}", bank.slot());
            return bank;
        }

        let slot = self
            .block_commitment_cache
            .read()
            .unwrap()
            .slot_with_commitment(commitment.commitment);

        match commitment.commitment {
            CommitmentLevel::Processed => {
                debug!("RPC using the heaviest slot: {slot:?}");
            }
            CommitmentLevel::Finalized => {
                debug!("RPC using block: {slot:?}");
            }
            CommitmentLevel::Confirmed => unreachable!(), // SingleGossip variant is deprecated
        };

        let r_bank_forks = self.bank_forks.read().unwrap();
        r_bank_forks.get(slot).unwrap_or_else(|| {
            // We log a warning instead of returning an error, because all known error cases
            // are due to known bugs that should be fixed instead.
            //
            // The slot may not be found as a result of a known bug in snapshot creation, where
            // the bank at the given slot was not included in the snapshot.
            // Also, it may occur after an old bank has been purged from BankForks and a new
            // BlockCommitmentCache has not yet arrived. To make this case impossible,
            // BlockCommitmentCache should hold an `Arc<Bank>` everywhere it currently holds
            // a slot.
            //
            // For more information, see https://github.com/solana-labs/solana/issues/11078
            warn!(
                "Bank with {:?} not found at slot: {:?}",
                commitment.commitment, slot
            );
            r_bank_forks.root_bank()
        })
```
