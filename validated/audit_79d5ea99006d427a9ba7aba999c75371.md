### Title
Peer-signature aggregation path skips the chainstate/conflict re-check that the pre-commit path enforces before signing/broadcasting - (File: stacks-signer/src/v0/signer.rs)

### Summary
`handle_block_pre_commit` re-runs `check_block_against_signer_db_state` and the fresh signed-conflict guard (`get_signed_conflicts` / `conflict_still_blocks` / `reorg_permit_stands`) immediately before a signer signs a block [2](#0-1) . Its sibling function `store_and_process_block_signature`, which counts peer `BlockResponse::Accepted` signatures toward the same 70% threshold and then moves the block to `LocallyAccepted` and broadcasts it to the node, contains none of these checks [3](#0-2) .

### Finding Description
Two code paths converge on the same outcome — a signer certifying and pushing a block to its node — but only one of them re-validates state before doing so:

- **Path A (own signing decision):** `handle_block_pre_commit` tallies pre-commit weight and, on crossing threshold, calls `check_block_against_signer_db_state` and then checks `get_signed_conflicts` against any block this signer has *already signed* at the same or higher height in *any* tenure, honoring freshness and `reorg_permit_stands` before finally calling `mark_locally_accepted`/`handle_block_signature` [4](#0-3) .
- **Path B (peer-signature aggregation):** `store_and_process_block_signature` is invoked from `handle_block_signature` for any `BlockResponse::Accepted` peer message where a pre-commit was already recorded for that signer (`has_committed` is true) [5](#0-4) . It tallies `total_signature_weight` from `get_block_signatures`, and once ≥70% is reached calls `block_info.mark_locally_accepted(true)` and `broadcast_signed_block` directly [6](#0-5)  — with no call to `check_block_against_signer_db_state`, `get_signed_conflicts`, or `reorg_permit_stands`.

The doc comment for the pre-commit path is explicit about why this re-check is needed: *"The chain and signer db state may have changed materially since this block passed the proposal-time checks (e.g. between validation and reaching the pre-commit threshold we may have signed a block that this one would reorg). Re-run the chainstate checks before putting a signature over the block..."* [7](#0-6) . That same time gap exists identically for Path B: the interval between when this signer sent its own pre-commit for a block and when peers' `Accepted` messages accumulate to threshold. During that gap this signer may have already signed a conflicting sibling block (same height, different tenure) via Path A's own conflict-free evaluation at an earlier moment — the exact condition Path A's conflict guard exists to catch. This mirrors the Fenix `reset()`/`vote()` pattern: one function in the "vote-tallying" family carries the guard, its sibling omits it.

### Impact Explanation
This lets a signer that already holds a fresh, valid signature over one block (block B, its own tenure) become the aggregator that also marks a conflicting sibling block (block A, from a competing/alternate tenure at the same height) as `LocallyAccepted` and pushes it to its node via `broadcast_signed_block`, purely because enough *other* signers' `Accepted` messages for A arrived and crossed 70% weight — without re-checking that A still conflicts with this signer's own signed B. This is a signer endorsing/broadcasting a conflicting block, i.e., the "signer signing... a conflicting block" critical-impact category, breaking the double-sign guard that the codebase documents and enforces on the sibling path.

### Likelihood Explanation
Reachable via a single miner (plus ordinary signer gossip): the miner proposes two sibling tenure-start (or otherwise conflicting) blocks at the same height in a timing window (the documented "async sibling validation" gap, see `stacks-signer/src/v0/tests.rs` `async_sibling_validation` module), causing different signers to sign different siblings through their independent, individually conflict-checked Path A evaluations. Any signer that has already signed one sibling but also recorded a pre-commit for the other (a normal outcome of the proposal-time flow, since both siblings can pass `check_proposal` before either is signed) reaches Path B for the other sibling once peer acceptances accumulate — the check gap is executed via ordinary network message processing (`handle_block_response` → `handle_block_signature` → `store_and_process_block_signature`) with no majority-collusion or privileged access required.

### Recommendation
Add the same re-check that `handle_block_pre_commit` performs — `check_block_against_signer_db_state` plus the signed-conflict/freshness/`reorg_permit_stands` guard — inside `store_and_process_block_signature` immediately before calling `mark_locally_accepted(true)` and `broadcast_signed_block`, so both paths that promote a block to `LocallyAccepted`/broadcast enforce an identical invariant.

### Proof of Concept
1. Miner proposes tenure-start block A and, within the async-validation window, re-proposes/proposes sibling block B at the same height in a different tenure (as exercised by `run_sibling_scenario` in `stacks-signer/src/v0/tests.rs`) [8](#0-7) .
2. Signer S validates and pre-commits to both A and B (both pass `check_proposal`/`check_block_against_signer_db_state` at their respective validation times, since neither is yet signed).
3. S's own Path A evaluation for block B (`handle_block_pre_commit` reaching threshold for B) passes the conflict guard (no fresh conflicting signature yet exists) and S signs B via `mark_locally_accepted`/`handle_block_signature` [9](#0-8) .
4. Before B's conflict becomes visible/stale, enough peer `BlockResponse::Accepted` messages for A arrive at S (from signers who committed to A earlier). Since S already has a recorded pre-commit for A, `store_and_process_block_signature` is invoked directly [5](#0-4) .
5. `store_and_process_block_signature` tallies signature weight for A, crosses the 70% threshold, and calls `block_info.mark_locally_accepted(true)` and `broadcast_signed_block` for A with no re-check against S's now-fresh signature over conflicting block B [10](#0-9)  — S ends up endorsing and pushing both conflicting siblings A and B.

    fn store_and_process_block_signature(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &mut BlockInfo,
        signer_address: &StacksAddress,
        signature: &MessageSignature,
    ) {
        let block_hash = &block_info.signer_signature_hash();
        // signature is valid! store it.
        // if this returns false, it means the signature already exists in the DB, so just return.
        if !self
            .signer_db
            .add_block_signature(block_hash, signer_address, signature)
            .unwrap_or_else(|_| panic!("{self}: Failed to save block signature"))
        {
            return;
        }

        // If this isn't our own signature and we haven't seen a pre-commit from this signer yet, try treating it as a pre-commit in case the caller is running an outdated version
        if signer_address != &self.stacks_address && !self.signer_db.has_committed(block_hash, signer_address).inspect_err(|e| warn!("Failed to check if pre-commit message already considered for {signer_address:?} for {block_hash}: {e}")).unwrap_or(false) {
            self.handle_block_pre_commit(stacks_client, sortition_state, signer_address, block_hash);
            return;
        }

        if block_info.signed_group.is_some() {
            // We have already processed this block to the accepted state. Adding more signatures will not change anything so nothing to check.
            return;
        }
        // do we have enough signatures to broadcast?
        // i.e. is the threshold reached?
        let signatures = self
            .signer_db
            .get_block_signatures(block_hash)
            .unwrap_or_else(|_| panic!("{self}: Failed to load block signatures"));

                    block_hash.bits(),
                    &sig,

                    return None;

                let addr = StacksAddress::p2pkh(self.mainnet, &public_key);
                Some((addr, sig))

            .collect();

                "consensus_hash" => %block_info.block.header.consensus_hash,

            );
            return;
        }

            "signer_signature_hash" => %block_hash,
            "signature_weight" => signature_weight,

            "total_weight" => total_weight,
