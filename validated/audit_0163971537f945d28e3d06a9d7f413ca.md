### Title
ERC4626 liquidity exhaustion can indefinitely block `stopEpoch` and freeze lender funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
`ProgrammableBorrower.onStopEpoch` determines solvency using `convertToAssets`, but then requires the configured ERC4626 vault to honor the needed withdrawal immediately. If an unprivileged vault user drains available vault liquidity, `vault.withdraw` reverts even though the programmable borrower’s shares still represent enough economic value. `onStopEpoch` converts that liquidity failure into `StopEpochVaultLiquidityUnavailable`, which propagates out of `IdleCDOEpochVariant._stopEpoch` before its borrower-default handling can run. Repeating the liquidity drain keeps the epoch running and freezes withdrawals and pool settlement until liquidity returns.

### Finding Description
During `onStopEpoch`, the borrower checks whether `shortfall > _currentVaultAssets()` before calling `vault.withdraw(shortfall, ...)`. `convertToAssets` measures economic coverage, not presently withdrawable liquidity. If the vault’s shares are backed by lent or otherwise illiquid assets, the check can pass while the withdrawal itself fails. The catch block then reverts with `StopEpochVaultLiquidityUnavailable` instead of returning an unsuccessful result. [1](#0-0) 

`IdleCDOEpochVariant._stopEpoch` calls the hook before entering its own `try` around `getFundsFromBorrower`. Consequently, a vault withdrawal revert aborts the entire stop transaction without changing `isEpochRunning` or invoking `_handleBorrowerDefault`. [2](#0-1) 

The analogous “never writable” condition is therefore the ERC4626 vault: it remains economically solvent and reports enough convertible assets, but remains operationally unwritable/illiquid at each stop attempt. An attacker who can consume the vault’s available liquidity can force that state around every manager-initiated `stopEpoch`.

### Impact Explanation
Temporary freezing of lender funds. While the condition is maintained:

- `stopEpoch` cannot complete, so `epochNumber` does not advance and `isEpochRunning` remains true.
- Pending withdrawal receipts cannot be funded through the normal epoch settlement path.
- New withdrawal requests remain disabled because `startEpoch` cleared `allowAAWithdrawRequest` and `allowBBWithdrawRequest`.
- For a pool with `P` pending withdrawals and a vault-side shortfall `S`, at least `P` remains unsettled; the broader active NAV also cannot be recalled or settled through `stopEpoch`.

This is not merely a gas or availability issue: the invariant that an economically funded epoch can terminate is broken by an external liquidity state that an unprivileged ERC4626 vault participant can create.

### Likelihood Explanation
The attack requires the programmable-borrower vault to have an illiquid asset base and enough attacker-controlled borrowing or redemption capacity to make `maxWithdraw`/`withdraw` unavailable for the epoch-end shortfall. The attacker needs capital or borrowing collateral, but no privileged role in the credit vault. Success depends on the configured ERC4626 vault permitting users to consume liquidity while the programmable borrower’s remaining shares still represent the required amount.

The code explicitly distinguishes economic coverage from withdrawal failure, but chooses a reverting retry path for the latter. [3](#0-2) 

### Recommendation
Add a bounded settlement path for solvent-but-illiquid ERC4626 positions:

1. Before calling `vault.withdraw`, compare the shortfall with `vault.maxWithdraw(address(this))` and record an explicit `pendingStop` state when liquidity is unavailable.
2. Allow repeated settlement attempts during a fixed grace period without leaving the ordinary epoch live indefinitely.
3. After the grace period, either invoke a governed partial-default/recovery path or permit the manager to settle using the currently withdrawable amount and account for the unfunded remainder as a pending vault claim.
4. Avoid treating a retryable withdrawal failure as indistinguishable from an ordinary transaction revert, because the current behavior gives external vault liquidity veto power over epoch completion.

### Proof of Concept
The following Foundry fork test demonstrates the vulnerable state transition. `drainUnderlyingVaultLiquidity` should call the configured ERC4626 deployment’s legitimate liquidity-consuming path, such as borrowing from its underlying lending market or redeeming sufficiently large attacker-held shares.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";
import {IERC4626} from "../contracts/interfaces/IERC4626.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {ProgrammableBorrower, StopEpochVaultLiquidityUnavailable} from
  "../contracts/strategies/idle/ProgrammableBorrower.sol";

contract ProgrammableBorrowerLiquidityFreezePoC is Test {
  // Fork configuration for the deployed vault under test.
  address constant CDO = address(0);       // deployed IdleCDOEpochVariant
  address constant PB = address(0);        // deployed ProgrammableBorrower
  address constant MANAGER = address(0);   // honest strategy manager
  address constant ATTACKER = address(0);  // ordinary ERC4626 vault user

  function testVaultIlliquidityBlocksStopEpoch() external {
    vm.createSelectFork(vm.envString("MAINNET_RPC_URL"), vm.envUint("FORK_BLOCK"));

    IdleCDOEpochVariant cdo = IdleCDOEpochVariant(CDO);
    ProgrammableBorrower borrower = ProgrammableBorrower(PB);
    IdleCreditVault strategy = IdleCreditVault(cdo.strategy());
    IERC4626 vault = borrower.vault();
    IERC20Detailed asset = borrower.underlyingToken();

    require(cdo.isEpochRunning(), "epoch must be running");
    vm.warp(cdo.epochEndDate());

    uint256 required = strategy.pendingWithdraws();
    uint256 shortfall = required - asset.balanceOf(PB);

    // The programmable borrower is economically covered...
    assertGe(
      vault.convertToAssets(vault.balanceOf(PB)),
      shortfall,
      "PB shares must economically cover the shortfall"
    );

    // ...but the attacker drains the ERC4626 vault's currently available liquidity.
    drainUnderlyingVaultLiquidity(vault, asset, shortfall);

    assertLt(
      vault.maxWithdraw(PB),
      shortfall,
      "attacker failed to make the needed withdrawal unavailable"
    );

    // Hook reverts before IdleCDO reaches getFundsFromBorrower/default handling.
    vm.prank(MANAGER);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdo.stopEpoch(0, 0);

    // No epoch settlement occurred; the pool remains live and lender funds stay locked.
    assertTrue(cdo.isEpochRunning(), "epoch unexpectedly stopped");
    assertEq(strategy.pendingWithdraws(), required, "pending receipt basis changed");

    // Repeating while liquidity remains exhausted produces the same result.
    vm.prank(MANAGER);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdo.stopEpoch(0, 0);
  }

  function drainUnderlyingVaultLiquidity(
    IERC4626 vault,
    IERC20Detailed asset,
    uint256 shortfall
  ) internal {
    // Deployment-specific: as ATTACKER, consume the vault's available liquidity
    // through its public lending-market borrow or large LP redemption path until
    // vault.maxWithdraw(PB) < shortfall.
    vm.startPrank(ATTACKER);
    // e.g. underlyingMarket.borrow(vaultLiquidity()) or vault.redeem(attackerShares, ...)
    vm.stopPrank();
  }
}
```
