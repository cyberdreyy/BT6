### Title
Unvalidated operator beneficiary in `staking_contract::set_beneficiary_for_operator` can permanently lock a shared distribution pool — (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract.move` lets an operator redirect their commission to a `beneficiary_for_operator` address with no validation that the address can actually receive `AptosCoin`. The shared payout path `distribute_internal` — invoked by `distribute`, `unlock_stake`, `request_commission`, and `update_commision` — pays out every recorded distribution (staker withdrawals + operator/beneficiary commission) from the same `StakingContract` in one call. `vesting.move`'s analogous `set_beneficiary` function explicitly guards against this exact failure mode with `assert_account_is_registered_for_apt`, and its own comment states the reason: to prevent `distribute()` from reverting and blocking *all other* recipients if one beneficiary isn't registered. `staking_contract::set_beneficiary_for_operator` has no equivalent check.

### Finding Description
`set_beneficiary_for_operator` sets `BeneficiaryForOperator.beneficiary_for_operator` to any address supplied by the operator, with zero registration/validity checks: [1](#0-0) 

By contrast, `vesting::set_beneficiary` explicitly requires the new beneficiary to be registered for `AptosCoin` before it is stored, precisely because the shared `distribute()` function would otherwise abort for every shareholder if the deposit to one unregistered beneficiary fails: [2](#0-1) 

In `staking_contract.move`, `distribute_internal` is the single shared payout path for the whole `StakingContract` (staker's principal/withdrawal distribution and operator's commission distribution are recorded together and paid out from the same pool in one call): [3](#0-2) 

It is reached from `distribute` (callable by anyone), and from `unlock_stake` and `request_commission`/`update_commision`, all of which call `distribute_internal` before doing their own work: [4](#0-3) [5](#0-4) 

`request_commission_internal` records the operator's commission as a distribution paid to `operator` (i.e., ultimately the beneficiary) inside the same pool that also holds the staker's distribution: [6](#0-5) 

If the actual coin transfer inside `distribute_internal` uses a deposit primitive that aborts on an unregistered/incompatible recipient (as `vesting.move`'s own design comment implies is the risk this exact pattern creates), then an operator who sets (even accidentally) an unregistered `beneficiary_for_operator` would cause every subsequent call to `distribute_internal` for that `StakingContract` to abort — trapping the staker's already-requested, otherwise-withdrawable stake alongside the operator's own commission, with no recovery path (unlike `vesting.move`, `staking_contract.move` has no admin/resetter role that can reset a stuck beneficiary).

### Impact Explanation
If confirmed, this would permanently lock a staker's unlocked/withdrawable stake (and the operator's own commission) in a `StakingContract` pool whenever the operator's beneficiary address cannot receive `AptosCoin`, with no owner-level recovery mechanism analogous to `vesting::reset_beneficiary`. This matches "Permanent lock or non-recoverable loss of claim rights in stake ... flows" from the required impact set.

### Likelihood Explanation
Requires the operator (a standard, unprivileged role in the `staking_contract` flow, not a governance/admin role) to set an unregistered address as their beneficiary — via oversight or malicious operator wanting to hold the staker's funds hostage. No special privileges beyond the operator role are needed to trigger it, though I could not directly confirm from the exact deposit call whether an unregistered address always causes an abort versus some other conditionally-safe path.

### Recommendation
Add the same registration validation that `vesting::set_beneficiary` already performs before storing a new beneficiary in `staking_contract::set_beneficiary_for_operator`:
```move
public entry fun set_beneficiary_for_operator(
    operator: &signer, new_beneficiary: address
) acquires BeneficiaryForOperator {
    assert!(features::operator_beneficiary_change_enabled(), ...);
+   assert_account_is_registered_for_apt(new_beneficiary);
    ...
}
```
Additionally, consider isolating the operator/beneficiary commission payout from the staker's principal distribution so a failure in one does not block the other, and/or add an owner/admin-level reset mechanism analogous to `vesting::reset_beneficiary`.

### Proof of Concept
Could not be fully constructed — I was unable to view the exact coin-transfer statement inside `distribute_internal` (lines ~870-960) due to tool/index truncation, so I cannot confirm with certainty that an unregistered beneficiary causes a hard abort there versus being handled gracefully. **This is the critical fact that must be verified before treating this as a confirmed vulnerability** — recommend a full read of `distribute_internal`'s body in a Devin session with filesystem access to trace the exact deposit call and any fallback/registration-check logic before filing.
