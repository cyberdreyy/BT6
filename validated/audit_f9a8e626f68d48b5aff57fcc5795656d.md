### Title
`depositDuringEpoch` mints shares for the stated `_amount` instead of the net tokens received — fee-on-transfer upgrade over-mints tranche shares - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external report's bug class — crediting the nominal transfer amount without measuring the actual balance delta — is already mitigated in the base deposit path (`IdleCDO._deposit` / `IdleCDOCreditVault._deposit` both compute `_contractTokenBalance(_token) - _preBal`). However, the mid-epoch deposit path `IdleCDOEpochVariant.depositDuringEpoch` reintroduces the same flaw: it pulls `_amount` via `_transferUnderlyingsFrom` and then prices/mints shares purely on the stated `_amount`, never measuring what actually arrived.

### Finding Description
In `depositDuringEpoch` (contracts/IdleCDOEpochVariant.sol:685), the vault executes:

```solidity
_transferUnderlyingsFrom(msg.sender, address(this), _amount);   // line 685
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;  // line 724
_mintShares(_tranche, msg.sender, _minted, _amount);            // line 725
expectedEpochInterest += interest;                              // line 728
IdleCreditVault(strategy).mintStrategyTokens(_amount);          // line 730
```

The minted tranche shares, the prorated `trancheInterest`, `expectedEpochInterest`, and the strategy-token mint are all computed on the declared `_amount`, not on `balanceAfter - balanceBefore`. The credit vault's underlying is a pool currency such as USDC — an upgradeable token that can introduce fee-on-transfer. If it does (or if a new vault is deployed on an already-fee-bearing stablecoin), a deposit of `_amount` delivers only `_amount * (1 - fee)` to the vault while the depositor is minted shares for the full `_amount + trancheInterest`, and `mintStrategyTokens(_amount)` records the full principal against less collateral.

### Impact Explanation
- **Over-mint / dilution:** the attacker receives tranche shares redeemable for more underlying than they contributed; at epoch end their shares claim `_amount + trancheInterest` while only `_amount - fee` entered the pool. The shortfall is socialized across all other tranche holders — direct theft of up to the transfer fee percentage of each deposit.
- **Inflated `expectedEpochInterest` and strategy tokens:** `interest` and `mintStrategyTokens` are computed on `_amount`, so the vault commits to borrower interest/principal it never received, compounding the insolvency gap at `stopEpoch` accounting.

### Likelihood Explanation
Conditional but realistic: it requires the vault's underlying to be (or become) fee-on-transfer — exactly the scenario the report describes for USDC, which is a proxy-upgradeable token. Once true, any KYC-passing lender (an allowed unprivileged attacker) can trigger it on every `depositDuringEpoch` call while an epoch is running and `isDepositDuringEpochDisabled`/`isProgrammableBorrower`/`isAYSActive` are false. The fee skim is bounded by the token's fee rate, so this is a medium-severity conditional-dilution bug, not a full drain.

### Recommendation
Measure the balance delta like the base `_deposit` does:

```solidity
uint256 _preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
_amount = _contractTokenBalance(token) - _preBal;
```

before computing `interest`, `_minted`, `expectedEpochInterest`, and calling `mintStrategyTokens(_amount)`. Alternatively, explicitly reject tokens with fee-on-transfer semantics and document the assumption.

Assert: vault balance increased by only `990_000e6`, but `balanceOf(attacker)` tranche shares correspond to `(_amount + trancheInterest)` on the full `1_000_000e6`, `expectedEpochInterest` grew by interest on `1_000_000e6`, and `IdleCreditVault` minted strategy tokens for `1_000_000e6` — a `10_000e6` + interest hole borne by existing depositors at epoch end.

Note: `IdleCDOEpochQueue.requestDeposit` has the identical stated-amount flaw (contracts/IdleCDOEpochQueue.sol:121-126), but the queue contract is excluded from scope per the rules. `WriteOffEscrow.fullfillWriteOffRequest` also trusts the stated `_underlyings`, but a shortfall just reverts the fulfiller's own call (they can overpay), so it is not exploitable by an unprivileged attacker.
