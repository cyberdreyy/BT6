### Title
Stale rejection weight is never retracted when a signer flips Reject→Accept, letting a sub-quorum of rejections block a block that already has quorum approval - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener`'s per-block tally (`BlockStatus`) adds a signer's weight to `total_weight_rejected` the first time it sees a `Rejected` message from that signer's slot, and separately adds weight to `total_weight_approved` the first time it sees an `Accepted` message from that slot. The two counters are gated by two *different* membership tests (`responded_signers` for rejections, `gathered_signatures` for acceptances), so a signer that rejects and later reconsiders and accepts the same block gets its weight counted in **both** buckets, and the stale rejection weight is never removed. This is the same class of bug as the Sherlock `Stream.balanceOf` finding: a derived accounting value (`remainingBalance - recipientBalance`, here `total_weight_rejected` vs. `total_weight_approved`) is computed under an implicit invariant ("each signer's weight lives in exactly one bucket") that untracked/late-arriving state (a reconsidered vote) can silently violate.

### Finding Description
`BlockStatus` tracks, per proposed block, `responded_signers`, `gathered_signatures`, `total_weight_approved`, and `total_weight_rejected`: [1](#0-0) 

On `BlockResponse::Accepted`, the code only checks whether the slot already has a *gathered signature* before crediting `total_weight_approved`; it never checks `responded_signers`: [2](#0-1) 

On `BlockResponse::Rejected`, the code checks/inserts into `responded_signers` before crediting `total_weight_rejected`: [3](#0-2) 

Sequence that breaks the invariant:
1. Signer S (slot k, weight w) sends `Rejected` for block B first. `responded_signers.insert(k)` succeeds → `total_weight_rejected += w`.
2. The signer-side state machine explicitly supports later reconsidering a rejection and switching to acceptance for the same block (`should_reevaluate_reject_reason`, `PreCommitted`→`LocallyAccepted` transitions documented in `docs/signer-flows.md` §2–3), so S legitimately later sends `Accepted` for the same B.
3. In the listener, the `Accepted` branch tests `!block.gathered_signatures.contains_key(&slot_id)` — true, because S never sent an acceptance before — so `total_weight_approved += w` as well.
4. `total_weight_rejected` is **never decremented**; there is no code path anywhere in `stackerdb_listener.rs` that removes a slot's weight from `total_weight_rejected` once added (confirmed: no decrement/reset logic exists besides the timeout-only `reset_rejections`, which only fires on `SignatureTimeout`, not on a flip).

The consuming coordinator (`SignerCoordinator::wait_for_signer_signatures` in `signer_coordinator.rs`) evaluates the rejection condition *before* the acceptance condition on every poll: [4](#0-3) 

Because `total_weight_rejected` is monotonically non-decreasing and includes stale weight from signers who have since accepted, the miner can observe `total_weight_rejected + weight_threshold > total_weight` and abort with `NakamotoNodeError::SignersRejected` even though the *current* set of dissenting signers is smaller than the blocking minority (30% of weight) and the block may already have (or would soon reach) the 70% approval quorum from `total_weight_approved`. This breaks the equality the protocol relies on — "rejection weight accurately reflects signers currently opposing the block" — via a rejection being permanently recounted alongside a later, valid acceptance.

### Impact Explanation
This is a liveness wedge on the miner/coordinator side: a canonical, otherwise-quorum-approved block can be treated as globally rejected (`SignersRejected`) due to stale weight left behind by signers who reconsidered, even though no majority or collusion is required — a single signer's honest reconsideration (Reject→Accept), which the signer-side protocol explicitly permits, is enough to inflate `total_weight_rejected` permanently. If several signers independently flip near the same time (a normal occurrence around chain-tip races/reorg checks, not collusion), their stale rejected weight can accumulate past the 30% blocking-minority line purely from *retracted* votes, causing the miner to reject/give up on a valid block and also to permanently/temporarily exclude transactions it flagged (`temporarily_excluded_txids`/`permanently_excluded_txids`), degrading throughput and potentially causing repeated mining stalls.

### Likelihood Explanation
Reachable by any single signer (or small number of signers) performing the ordinary, protocol-sanctioned "reject, then reconsider and accept" sequence described in the signer-flow docs. No majority, no forged keys, and no access beyond normal StackerDB gossip is required — only two ordinary messages (`Rejected` then `Accepted`) from the same signer for the same `signer_signature_hash`.

### Recommendation
Make the two counters mutually exclusive and reconciled on reconsideration:
- In the `Accepted` branch, if the slot is already present in `responded_signers` as a rejection, retract the previously credited weight from `total_weight_rejected` before adding it to `total_weight_approved` (and vice-versa for a hypothetical accept→reject transition, if ever allowed).
- Alternatively, track a single `HashMap<slot_id, Vote>` (Approve/Reject) and recompute `total_weight_approved`/`total_weight_rejected` as sums over the current vote map rather than via incremental, one-directional accumulation, so a flipped vote is naturally reflected in both totals.

### Proof of Concept
1. Node proposes block B; signer S (slot `k`, weight `w`) initially rejects B (e.g., due to a transient `check_block_against_signer_db_state` failure) → `stackerdb_listener` sets `responded_signers = {k}`, `total_weight_rejected = w`.
2. S subsequently re-evaluates (chain state changes, `should_reevaluate_reject_reason` allows it) and signs/accepts B, broadcasting `BlockResponse::Accepted`.
3. `stackerdb_listener` receives the acceptance; `gathered_signatures` does not contain `k`, so it adds `w` to `total_weight_approved`, while `total_weight_rejected` still equals `w` from step 1 — S's weight is now counted in both totals.
4. Repeat for enough signers such that stale `total_weight_rejected` (sum of weights of signers who *used to* reject but have since accepted) exceeds the blocking-minority threshold (`total_weight - weight_threshold`), while the currently-live set of rejecting signers is actually below that threshold.
5. On the next poll in `SignerCoordinator::wait_for_signer_signatures`, the rejection branch fires first (`total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight`), causing the miner to abort mining/accepting block B via `NakamotoNodeError::SignersRejected`, even though the live signer set actually supports the block above the 70% approval threshold.
