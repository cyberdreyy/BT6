## Title
Stale confirmations from deleted multisig members are still counted toward the confirmation threshold, allowing requests to execute below the required number of live signers - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges the confirmations for requests that were *originally created* by the member being removed. It does not purge confirmations that the removed member previously cast on requests created by *other* members. Because `confirm()` simply compares the size of the stored confirmation `HashSet<String>` against `num_confirmations`, a confirmation entry left behind by a now-deleted member still counts toward the threshold. This breaks the intended custody binding "confirmations counted == currently-authorized live members" and lets a request (e.g. a `Transfer` of NEAR) execute with fewer than `num_confirmations` *live* member approvals.

### Finding Description
The relevant state is: [1](#0-0) 

Confirmations are stored per-request as a `HashSet<String>` of member identifiers, independent of the current members set: [2](#0-1) 

`confirm()` executes the request purely based on the cardinality of that per-request confirmation set — `confirmations.len() as u32 + 1 >= self.num_confirmations` — with no revalidation that every entry in `confirmations` still refers to a member currently in `self.members`.

When a member is removed via `DeleteMember`, the cleanup logic only removes *requests whose creator (`r.member`) equals the deleted member*, and the deleted member's own `num_requests_pk` counter. It does **not** scan `self.confirmations` for entries where the deleted member had confirmed a request created by someone else: [3](#0-2) 

So any *other* pending request that the removed member had already confirmed retains that confirmation in its `HashSet<String>` forever, even though the member is no longer part of `self.members` and can no longer act on the contract's behalf.

### Impact Explanation
This breaks the equality the multisig is supposed to guarantee: *number of confirmations counted toward execution == number of currently-authorized (live) members who approved the request*. Concretely:

1. Members `A, B, C, D`, `num_confirmations = 3`.
2. `C` creates request `R` (e.g. `Transfer` of the contract's NEAR balance to an attacker-controlled account) via `add_request`.
3. `B` confirms `R` → `confirmations(R) = {B}`.
4. Separately, `A`, `C`, `D` execute a `DeleteMember{B}` request (3 confirmations, satisfying the current threshold) to remove `B`. `delete_member` only removes requests *created* by `B`; `R` was created by `C`, so it survives untouched with `confirmations(R) = {B}` — a confirmation from an account that is no longer a member.
5. Members are now `{A, C, D}`, still `num_confirmations = 3` (>= new member count check only prevents `num_confirmations` from exceeding remaining members, it doesn't revalidate outstanding confirmations).
6. `A` confirms `R`: before insertion, `len({B}) + 1 = 2 < 3` → not yet executed; `confirmations(R) = {B, A}`.
7. `D` confirms `R`: before insertion, `len({B,A}) + 1 = 3 >= 3` → `execute_request` runs `Transfer` immediately.

The transfer executes with only **2 live-member approvals (`A`, `D`)** even though `num_confirmations = 3` is supposed to require 3 live signers. This is a Critical-impact analog to "a multisig request executed below threshold" — NEAR (or any action: `DeployContract`, `AddKey`, `FunctionCall`) can be moved/executed by a coalition smaller than the configured threshold, as long as one confirmer was later removed from the multisig while their stale confirmation remains attached to an unrelated pending request.

### Likelihood Explanation
No privileged role is required beyond normal multisig membership that any of the K-of-N signers already possess. The only precondition is ordinary churn in membership (a legitimate `DeleteMember` action, which multisig owners routinely perform when rotating keys or offboarding a signer) combined with an existing pending request that the departing member had confirmed. A colluding or compromised member can deliberately engineer this: confirm a malicious request, then arrange (or wait) for themselves/an accomplice to be removed, banking on the stale confirmation to reduce the effective threshold needed from the remaining members. This requires only normal multisig operations already exposed by the contract's public API (`add_request`, `confirm`, and a legitimate `DeleteMember` execution) — no redeploy, no foundation, no external interception.

### Recommendation
When a member is deleted (`delete_member`), scan `self.confirmations` for **every** pending request (not just those the deleted member created) and remove the deleted member's entry from each request's confirmation set. Alternatively, when checking the threshold in `confirm()`, intersect the stored confirmation set with `self.members` before comparing its length to `num_confirmations`, ensuring only confirmations from currently-live members are ever counted.

### Proof of Concept
```
// members: A, B, C, D ; num_confirmations = 3

// 1. C creates a Transfer request R (not auto-confirmed)
let r_id = contract.add_request(MultiSigRequest {
    receiver_id: attacker,
    actions: vec![MultiSigRequestAction::Transfer { amount: X }],
}); // creator = C

// 2. B confirms R -> confirmations(R) = {B}
contract.confirm(r_id); // signed as B

// 3. A, C, D remove B via a separate DeleteMember request (3 live confirmations)
let del_id = contract.add_request(MultiSigRequest {
    receiver_id: current_account_id,
    actions: vec![MultiSigRequestAction::DeleteMember { member: B }],
});
contract.confirm(del_id); // A
contract.confirm(del_id); // C
contract.confirm(del_id); // D -> executes delete_member(B)
// delete_member only purges requests created by B; R (created by C) is untouched,
// confirmations(R) still contains B's stale entry.

// 4. Members are now {A, C, D}; num_confirmations unchanged at 3.
contract.confirm(r_id); // A -> confirmations(R) = {B, A}, len 2 < 3, not executed
contract.confirm(r_id); // D -> len({B,A})+1 = 3 >= 3 -> execute_request(R) runs Transfer

// Result: Transfer executed with only A and D as live approvers (2 live confirmations),
// even though num_confirmations = 3 was configured.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
