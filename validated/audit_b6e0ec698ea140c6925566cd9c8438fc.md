### Title

Fee-on-transfer deposits overfund the strategy and can permanently block deposits - (File: `contracts/IdleCDOCreditVault.sol`)

### Summary

`IdleCDOCreditVault._deposit()` correctly measures the actual underlying received and mints tranche tokens for that net amount, but then calls `IdleCreditVault.deposit()` with the original gross `_amount`. For a fee-on-transfer underlying, the CDO receives less than `_amount`, while the strategy attempts to pull and mint `_amount`. If the CDO does not already hold enough underlying to cover the fee, the deposit reverts; if it does, protocol-owned idle underlying is consumed to subsidize the deposit.

### Finding Description

The deposit flow first snapshots the CDO token balance and transfers `_amount` from the depositor: [1](#0-0) 

For a normal ERC20, `postBalance - _preBal == _amount`, so minting shares based on the balance delta is equivalent to minting based on `_amount`.

For a fee-on-transfer token, the CDO receives only `_amount - transferFee`. Tranche shares are therefore minted for the net received amount, which is correct in isolation. However, `_deposit()` then passes the original gross `_amount` to the strategy: [2](#0-1) 

`IdleCreditVault.deposit()` pulls the full `_amount` from the CDO and mints the same number of strategy tokens: [3](#0-2) 

The broken invariant is:

```text
CDO underlying received == underlying transferred to strategy == strategy tokens minted
```

With a fee-on-transfer underlying this becomes:

```text
underlying received = _amount - fee
underlying demanded by strategy = _amount
strategy tokens minted = _amount
```

Consequently, either:

1. the CDO does not hold enough underlying and every deposit reverts, or
2. the missing fee is paid out of pre-existing CDO underlying, causing that balance to be transferred into the strategy and counted as managed backing.

The underlying asset is arbitrary deployment configuration rather than a hard-coded non-fee token: [4](#0-3) [5](#0-4) 

### Impact Explanation

For a vault configured with a fee-on-transfer underlying, unprivileged depositors cannot successfully deposit unless the CDO already owns enough underlying to cover the token fee. This can permanently prevent deposits into that vault because `token` is fixed during initialization.

If the CDO does hold underlying during a buffer period, the deposit can succeed by spending protocol-held underlying to cover the depositor's transfer fee. The strategy mints `_amount` of strategy tokens even though the depositor only supplied `_amount - fee`, so the fee difference is socialized into the vault's managed assets. Repeated deposits can consume previously returned or otherwise idle underlying held by the CDO.

The direct accounting mismatch is bounded per deposit to the token's transfer fee, but the aggregate loss is unbounded across repeated deposits while idle CDO liquidity exists. When that liquidity is absent, the issue manifests as deposit failure rather than loss.

### Likelihood Explanation

Likelihood depends on deploying a credit vault whose underlying charges a transfer fee. The factory accepts an arbitrary `underlying` and does not reject fee-on-transfer tokens. A depositor does not need a privileged role beyond any normal deposit eligibility required by the configured vault.

The issue is easiest to reproduce in the buffer phase, before `startEpoch()` pauses deposits. During an active epoch, deposits are normally paused, so this is primarily a pre-epoch/closed-pool deposit-path issue rather than a mid-epoch borrower action.

### Recommendation

Use the measured amount received throughout the deposit path:

```solidity
uint256 preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 received = _contractTokenBalance(token) - preBal;
require(received != 0, "...");
uint256 minted = _mintSharesAtCurrPrice(received, msg.sender, _tranche);
IIdleCDOStrategy(strategy).deposit(received);
```

Alternatively, explicitly reject fee-on-transfer underlying tokens at deployment/configuration time and enforce that `balanceAfter - balanceBefore == _amount`. Measuring the received amount and passing `received` to `IdleCreditVault.deposit()` is the safer invariant-preserving fix.

### Proof of Concept

A Foundry PoC can deploy the production `IdleCDOEpochVariant` and `IdleCreditVault`, then configure a local ERC20 that burns or diverts 1% of every `transferFrom` amount:

```solidity
contract FeeToken is ERC20 {
    constructor() ERC20("FeeToken", "FEE") {
        _mint(msg.sender, 1_000_000e18);
    }

    function _transfer(address from, address to, uint256 amount) internal override {
        uint256 fee = amount / 100;
        super._transfer(from, to, amount - fee);
        super._burn(from, fee);
    }
}
```

Test sequence:

```solidity
function testFeeOnTransferDepositReverts() public {
    // Deploy/initialize IdleCreditVault and IdleCDOEpochVariant with FeeToken.
    feeToken.approve(address(cdo), 100e18);

    uint256 cdoBefore = feeToken.balanceOf(address(cdo));

    vm.expectRevert(); // ERC20: transfer amount exceeds balance / insufficient funds
    cdo.depositAA(100e18);

    assertEq(feeToken.balanceOf(address(cdo)), cdoBefore);
}
```

The failure occurs because the CDO receives `99e18` but `IdleCreditVault.deposit()` tries to pull `100e18`.

The subsidy path can be demonstrated by donating or otherwise seeding the CDO with `1e18` before the same deposit:

```solidity
feeToken.transfer(address(cdo), 1e18);
cdo.depositAA(100e18);

// User tranche basis is 99e18, while the strategy received and minted 100e18.
// The missing 1e18 came from the CDO's pre-existing balance.
assertEq(feeToken.balanceOf(address(cdo)), 0);
assertEq(strategy.balanceOf(address(cdo)), 100e18);
```
