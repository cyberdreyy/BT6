### Title
Confirmations from deleted multisig members remain counted toward `num_confirmations`, allowing a request to execute below the live-member threshold - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`confirm()` decides whether to execute a pending request purely by comparing the *size* of the stored `confirmations` set to `num_confirmations`, without verifying that every account/key in that set is still a current member. `delete_member`/`DeleteKey` only purge requests that were *added by* the removed member — they never scan and clean up confirmations that removed member left on *other* still‑pending requests. A request can therefore be executed with fewer live-member confirmations than `num_confirmations` requires.

### Finding Description
In `confirm()`: [1](#0-0) 
the check is `confirmations.len() as u32 + 1 >= self.num_confirmations`, where `confirmations` is a `HashSet<String>` of member identifiers previously stored for that `request_id`. Nothing here re-validates that the members in that set are still members of `self.members`.

`delete_member` is the only place stale confirmations could be cleaned up, but it only removes requests *originated* by the removed member: [2](#0-1) 
The `request_ids` filter matches `r.member == member` (the member who called `add_request`), not membership inside `self.confirmations`. Any other pending request that the removed member had previously *confirmed* (but did not create) keeps that member's entry in its `confirmations` set untouched.

The analogous logic exists in the original `multisig` contract's `DeleteKey` action: [3](#0-2) 
which likewise only removes requests whose `signer_pk == pk`, not confirmations that key left on other requests, and `confirm()` there has the identical count-only check: [4](#0-3) 

**Binding broken:** `confirmations_counted(request) == live_members_who_confirmed(request)` is assumed but not enforced; after a member removal, `confirmations_counted(request) > live_members_who_confirmed(request)`, so a request can be executed while only `num_confirmations - 1` (or fewer) *live* members actually approved it.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." A previously-approved but still-pending transfer, `FunctionCall`, `AddKey`/`AddMember`, or `DeleteKey`/`DeleteMember` action can be pushed through execution using a stale confirmation from an account that has since been removed as a member (e.g., because it was compromised, off-boarded, or malicious and deliberately purged). The multisig's core security property — that `K` *current* members must agree — is broken.

### Likelihood Explanation
This requires no privileged attacker action beyond the normal, expected multisig workflow: members confirming requests and later removing a member is a routine operational sequence (e.g., removing a compromised/departing member). No redeploy, foundation, or out-of-scope actor is needed — only ordinary use of `add_request`, `confirm`, and `DeleteKey`/`DeleteMember`, which are the intended participants of the multisig itself. Any pending request that a soon-to-be-removed member had confirmed is silently left in an inflated state.

### Recommendation
When counting confirmations in `confirm()`, filter `confirmations` to only those entries still present in `self.members` before comparing against `num_confirmations`. Additionally, in `delete_member`/`DeleteKey`, iterate all pending requests' confirmation sets (not just requests added by the removed member) and strip the removed member's/key's confirmation from them.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C}` and `num_confirmations = 2`, mirroring the setup in the existing test `test_multi_3_of_n`: [5](#0-4) 
2. `B` calls `add_request` to create request `X` (e.g. a `Transfer`). `A` calls `confirm(X)` → `confirmations(X) = {A}`, count = 1 (< 2, not executed).
3. Separately, `B` and `C` create and confirm a `DeleteMember { member: A }` request, which executes and removes `A` from `self.members` — but per `delete_member`'s logic it only deletes requests where `r.member == A` (i.e., requests A originated), leaving `confirmations(X) = {A}` untouched.
4. `B` calls `confirm(X)` again. `confirmations.len() + 1 = 2 >= num_confirmations (2)` → request `X` executes, even though only one live member (`B`) ever confirmed it after `A`'s removal.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
