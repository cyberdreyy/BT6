### Title
`/debug/vars` (expvar) exposed to any authenticated session regardless of role - ([File: core/web/router.go])

### Summary
The `debugRoutes` function registers `GET /debug/vars` behind only `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)`, with no `Requires*Role` gate, unlike virtually every other sensitive endpoint in `v2Routes`. Any user with a valid session cookie — including the lowest-privilege "view" role — can therefore hit the standard library `expvar.Handler()` and retrieve internal Go runtime state.

Compare this to the pattern used everywhere else in `v2Routes`, where sensitive read/write endpoints are wrapped in `auth.RequiresEditRole`, `auth.RequiresAdminRole`, or `auth.RequiresRunRole` in addition to `auth.Authenticate`, e.g.: [2](#0-1) 

`auth.Authenticate(..., auth.AuthenticateBySession)` only validates that a session cookie exists and is valid; it does not check the user's role. Because `/debug/vars` has no role wrapper, a session belonging to a "view"-role user (the lowest privilege tier used elsewhere to gate read-only access, e.g. `RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole` calls throughout the file) can reach `expvar.Handler()`, which serves Go's built-in `expvar` registry: `cmdline` (process arguments), `memstats` (heap/GC internals), and any other variables published via `expvar.Publish`/`expvar.NewString`/`expvar.NewMap` by the process or its dependencies. A search of the repository for `expvar.Publish`/`expvar.NewString`/`expvar.NewMap` calls in application code found no results, meaning the current codebase does not appear to publish custom secrets through `expvar` itself — the exposure is limited to the standard `cmdline` and `memstats` vars (and anything a linked dependency registers via `init()`).

### Impact Explanation
This is an information-disclosure issue, not an authentication/authorization bypass or secret-key leak: it does not grant privilege escalation, does not expose credentials, and does not allow unauthorized job execution or fund movement. The disclosed data (heap/GC statistics, process command-line) is of low sensitivity in this codebase since no application secrets are registered via `expvar`. It does, however, represent an inconsistency with the rest of the router's least-privilege model — every other authenticated endpoint enforces a role, this one does not — and could leak internal state (e.g., binary invocation flags, paths) to the lowest-privilege authenticated principal. This does not meet the bar of the listed high-impact bounty classes (auth bypass, secret disclosure, fund movement, unauthorized job run, cross-user data return), so it should be treated as low-severity/informational rather than a critical finding.

### Likelihood Explanation
Trivial to trigger: any valid session (lowest "view" role) can `GET /debug/vars` with no additional preconditions. Fully repeatable via a simple authenticated HTTP request.

### Recommendation
Wrap the `/debug/vars` route with an appropriate role check (e.g., `auth.RequiresAdminRole`) consistent with the rest of the authenticated routes in `debugRoutes`/`v2Routes`, or remove/disable the endpoint in production builds if it is only intended for local debugging.

### Proof of Concept
1. In a handler-level integration test (similar to existing tests in `core/web/router_test.go`), create a session for a user with role `view`.
2. Perform `GET /debug/vars` with that session's cookie.
3. Assert the response is `200 OK` and contains standard expvar keys (`cmdline`, `memstats`), demonstrating that a view-role session can access data intended to require a higher role, and that no role-check middleware (unlike other authv2 routes) rejects it with `403`.
