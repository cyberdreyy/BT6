### Title
`depositDuringEpoch` mints tranche tokens, accrues NAV and forwards funds to the borrower based on the nominal `_amount` instead of the actual tokens received, breaking accounting for fee-on-transfer underlyings - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The vault's buffer-period deposit path (`_deposit` in `IdleCDO.sol`/`IdleCDOCreditVault.sol`) correctly mints shares from the *measured* balance delta (`_contractTokenBalance(_token) - _preBal`). The mid-epoch deposit path `depositDuringEpoch` does not: it pulls `_amount` via `_transferUnderlyingsFrom` and then mints shares, bumps `lastNAV`, accrues `expectedEpochInterest`, mints strategy tokens and forwards the full `_amount` to the borrower — all priced off the pre-fee nominal amount. With a fee-on-transfer (FoT) underlying, the vault receives `_amount - fee` but behaves as if it received `_amount`.

### Finding Description
In `IdleCDOEpochVariant.depositDuringEpoch` (contracts/IdleCDOEpochVariant.sol:656-733):

```solidity
_transferUnderlyingsFrom(msg.sender, address(this), _amount);          // vault gets _amount - fee
uint256 interest = _calcInterest(_amount) * ...;                       // interest on nominal amount
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal; // shares on nominal amount
_mintShares(_tranche, msg.sender, _minted, _amount);                   // lastNAV += _amount
expectedEpochInterest += interest;
IdleCreditVault(strategy).mintStrategyTokens(_amount);
_transferUnderlyings(_borrower(), _amount);                            // sends _amount out
```

Compare with `IdleCDOCreditVault._deposit` (contracts/IdleCDOCreditVault.sol:203-206), which mints on `_contractTokenBalance(_token) - _preBal`. `depositDuringEpoch` has no equivalent received-amount measurement.

Concretely, with a 10% FoT token during a running epoch (fixed-APR mode, `isDepositDuringEpochDisabled == false`, caller KYC'd via `isWalletAllowed`):

1. Depositor approves and calls `depositDuringEpoch(1000, AATranche)`. The vault receives 900.
2. The depositor is minted tranche tokens worth ~`1000 + trancheInterest` of underlying at epoch end, `lastNAV` increases by 1000, `expectedEpochInterest` is inflated.
3. The vault then transfers the full 1000 to the borrower (line 732). The 100-token gap is paid out of *other* depositors' principal sitting in the vault, because the borrower pull is unconditioned on what was actually received.

The same class of defect exists secondarily in `IdleCDOCreditVault._deposit` (contracts/IdleCDOCreditVault.sol:211): shares are minted on the received amount, but `IIdleCDOStrategy(strategy).deposit(_amount)` pulls the full nominal `_amount` from the CDO, silently draining the `fee` difference from the vault's balance into the strategy and registering it as a NAV loss borne by existing tranche holders. Similarly, `IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` (contracts/IdleCreditVaultWriteOffEscrow.sol:139-149) forwards `_underlyings - _totFee` assuming it received `_underlyings`, so a FoT fulfillment either short-pays or reverts.

### Impact Explanation
Broken invariant: fair mint/burn plus solvency. Each mid-epoch deposit with a FoT underlying mints shares backed by less collateral than accounted, inflates `lastNAV`/`expectedEpochInterest`, and sends the borrower more than was deposited — the `fee` shortfall is taken directly from existing lenders' principal. The depositor's tranche tokens are redeemable for more than they contributed, so at epoch stop/withdraw the missing funds socialize across honest AA/BB holders, or the borrower transfer itself can revert if the vault lacks the extra `fee` in balance, temporarily freezing deposits. Loss is quantified as `fee% × _amount` per deposit, plus the over-accrued `expectedEpochInterest`.

### Likelihood Explanation
Requires the pool's `token` to be fee-on-transfer (e.g., USDT if a fee is ever enabled, or any future FoT stable/credit asset). Deployments using plain USDC/DAI are unaffected, so likelihood depends on underlying selection; the code path itself is fully exposed — the deposit is permissionless modulo `isWalletAllowed` KYC and the `isDepositDuringEpochDisabled` flag, and no received-amount guard, skim, or Default check intervenes. This is a code defect, not an attacker-privilege issue.

### Recommendation
Measure the actual received amount and use it everywhere downstream, mirroring `_deposit`:

```solidity
address _token = token;
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 _received = _contractTokenBalance(_token) - _preBal;
// use _received (not _amount) for interest calc, _minted, _mintShares, expectedEpochInterest,
// mintStrategyTokens and the borrower transfer
```

Apply the same received-amount pattern in `IdleCDOCreditVault._deposit` (pass the measured delta to `strategy.deposit`) and in `IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` (pay out `received - fee`, not `_underlyings - fee`). Alternatively, revert unless `received == _amount` if FoT tokens are not intended to be supported.

### Proof of Concept
Foundry-style sketch (fork `test/foundry/IdleCreditVault.t.sol` setup; swap `defaultUnderlying` for a fee-on-transfer mock):

```solidity
// MockFoT burns `feeBps` on every transferFrom
function testDepositDuringEpochFoTDrainsVault() external {
    // buffer phase: seed vault with 1000 tokens from existing lender
    idleCDO.depositAA(1000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);            // epoch running, 10% APR
    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    address attacker = makeAddr('fotDepositor');
    uint256 amount = 1000 * ONE_SCALE;
    fot.mint(attacker, amount);               // 10% fee on transfer
    _whitelist(attacker);

    uint256 vaultBalBefore = fot.balanceOf(address(cdoEpoch));
    uint256 borrowerBefore  = fot.balanceOf(borrower);
    uint256 navBefore       = cdoEpoch.lastNAVAA();

    vm.startPrank(attacker);
    fot.approve(address(cdoEpoch), amount);
    uint256 minted = cdoEpoch.depositDuringEpoch(amount, address(AAtranche));
    vm.stopPrank();

    // vault netted only 900, but borrower received the full 1000
    assertEq(fot.balanceOf(address(cdoEpoch)) - vaultBalBefore, 900 * ONE_SCALE);
    assertEq(fot.balanceOf(borrower) - borrowerBefore, amount); // 100 extra taken from prior NAV
    // NAV/shares credited for the full 1000 -> minted shares over-claim existing collateral
    assertEq(cdoEpoch.lastNAVAA() - navBefore, amount);
    assertGt(minted * cdoEpoch.virtualPrice(address(AAtranche)) / 1e18, 900 * ONE_SCALE);
}
```

Expected result: the borrower's balance increases by `_amount` while the vault's increases only by `_amount - fee`, and `lastNAVAA`/minted shares are booked at `_amount` — i.e., `fee` units of pre-existing lender principal are silently transferred to the borrower while the depositor holds tranche tokens claiming the full amount plus prorated interest.
