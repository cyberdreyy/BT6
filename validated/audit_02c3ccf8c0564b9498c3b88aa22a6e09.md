### Title
Unauthenticated `/v2/resume/:runID` endpoint lets any actor inject arbitrary results into a pending pipeline run - (File: `core/web/router.go`)

### Summary
The Splitter bug class is "a function meant to be called only by a trusted party accepts a call from any unprivileged actor because there is no real authorization check, only a self-supplied or guessable identifier." The Chainlink node has a direct analog: the `/v2/resume/:runID` HTTP route is registered in the **unauthenticated** router group and lets any network caller supply an arbitrary result/error for a suspended pipeline task, identified only by a UUID.

### Finding Description
In `core/web/router.go`, the resume endpoint is deliberately placed outside the authenticated router group: [1](#0-0) 

```go

	prc := PipelineRunsController{app}
	psec := PipelineJobSpecErrorsController{app}
	unauthedv2.PATCH("/resume/:runID", prc.Resume)

	authv2 := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(), ...))
```

`ResumeJobV2` funnels straight into `pipeline.Runner.ResumeRun`, which calls `orm.UpdateTaskRunResult` — a query that matches **any** `pipeline_task_runs` row by its UUID, across all jobs/owners, and unconditionally writes the caller-supplied `output`/`error` into it, then restarts the suspended run: [3](#0-2) [4](#0-3) 

This is structurally identical to the Splitter vulnerability: the system relies on the caller possessing a single "self-supplied" token (a task-run UUID) with no cryptographic binding to a trusted originator (the external adapter/EA that legitimately owns that pending async task), instead of validating the caller's identity/role against a registry the way `AuthenticateExternalInitiator`/`AuthenticateByToken` do for other endpoints. The audit event name itself, `UnauthedRunResumed`, confirms this route is explicitly unauthenticated by design.

### Impact Explanation
If an attacker learns or brute-forces a pending task-run UUID (e.g., via log leakage, timing side-channels, or a job with predictable/low-entropy IDs), they can:
- Overwrite the result of an in-flight async task (e.g., a bridge/external-adapter or `ETHTxTask` callback awaiting confirmation) with attacker-chosen data, similar to how the Splitter incrementWindow attacker corrupts `balanceForWindow` accounting with attacker-chosen values.
- Force premature/incorrect resumption of a pipeline run, which can feed falsified data into downstream tasks that ultimately submit values on-chain (e.g., OCR reports, VRF fulfillment), representing a cross-user/cross-job response-confusion and potential fund-movement or oracle-manipulation vector.
- Because there's no ownership check tying `taskID` to a specific external initiator/bridge credential, this is a pure "guess-the-identifier" authorization bypass, not something mitigated by any role check.

### Likelihood Explanation
This requires the UUID to be known to the attacker; standard `uuid.New()` v4 values are not practically brute-forceable. However, likelihood is elevated by: (a) task-run IDs can appear in application/HTTP logs, error messages, external-adapter request bodies, or third-party systems that receive callback URLs containing this ID; (b) the endpoint is unauthenticated by design specifically so that external adapters can call back without full node API credentials, meaning the UUID is the *sole* security boundary and is routinely transmitted over the network to third-party bridge/EA endpoints outside chainlink's control — exactly the same trust-inversion pattern as the Splitter's reliance on `msg.sender`'s self-reported identity.

### Recommendation
Bind the resume-callback authorization to something the node controls rather than only a value transmitted to potentially exposed third parties: e.g., require the external adapter's existing bridge/EI credentials (`AuthenticateExternalInitiator`/bridge access key+secret) on this route the same way other run-triggering endpoints do, and/or record which external initiator/bridge originated the async task so `UpdateTaskRunResult` can verify the caller matches the task's registered owner before applying attacker-controlled output.

### Proof of Concept
Not independently reproducible from static analysis alone (would require a live node with a suspended async task and knowledge/leak of its `runID`), but the code path is unambiguous:
1. Create any job with an async/bridge task (task marked `IsPending: true`, e.g. `ETHTxTask` at [5](#0-4)  or a bridge async task), producing a suspended run with a known `pipeline_task_runs.id`.
2. From any unauthenticated client, send `PATCH /v2/resume/<taskID>` with an arbitrary JSON body decodable by `pipeline.ResumeRequest`.
3. The request is routed by the `unauthedv2` group directly to `PipelineRunsController.Resume` with zero authentication, and `orm.UpdateTaskRunResult` applies the attacker-supplied result to that task run, resuming the pipeline.

Due to indexing limits, the exact `pipeline.ResumeRequest.ToResult()` schema in `core/services/pipeline/models.go` was not retrieved in full; a Devin session with full repo access can confirm the precise accepted payload shape.

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
```

```go
func (o *orm) UpdateTaskRunResult(ctx context.Context, taskID uuid.UUID, result Result) (run Run, start bool, err error) {
	if result.OutputDB().Valid && result.ErrorDB().Valid {
		panic("run result must specify either output or error, not both")
	}
	err = o.transact(ctx, func(tx *orm) error {
		sql := `
		SELECT pipeline_runs.*, pipeline_specs.dot_dag_source "pipeline_spec.dot_dag_source", job_pipeline_specs.job_id "job_id"
		FROM pipeline_runs
		JOIN pipeline_task_runs ON (pipeline_task_runs.pipeline_run_id = pipeline_runs.id)
		JOIN pipeline_specs ON (pipeline_specs.id = pipeline_runs.pipeline_spec_id)
		JOIN job_pipeline_specs ON (job_pipeline_specs.pipeline_spec_id = pipeline_specs.id)
		WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')
		FOR UPDATE`
		if err = tx.ds.GetContext(ctx, &run, sql, taskID); err != nil {
			return fmt.Errorf("failed to find pipeline run for task ID %s: %w", taskID.String(), err)
		}

		// Update the task with result
		sql = `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1`
		if _, err = tx.ds.ExecContext(ctx, sql, taskID, result.OutputDB(), result.ErrorDB(), time.Now()); err != nil {
			return fmt.Errorf("failed to update pipeline task run: %w", err)
		}

		if run.State == RunStatusSuspended {
			start = true
			run.State = RunStatusRunning

			sql = `UPDATE pipeline_runs SET state = $2 WHERE id = $1`
			if _, err = tx.ds.ExecContext(ctx, sql, run.ID, run.State); err != nil {
				return fmt.Errorf("failed to update pipeline run state: %w", err)
			}
		}

		return loadAssociations(ctx, tx.ds, []*Run{&run})
```
