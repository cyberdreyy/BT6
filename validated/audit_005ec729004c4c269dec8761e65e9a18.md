### Title
`getSupply` RPC computes circulating supply via non-atomic snapshot causing integer-underflow panic / bogus supply data - (File: rpc/src/rpc.rs)

### Summary
The BakerFi bug used a `totalSupply()` value read *before* a state-mutating mint to compute a fee ratio, so the value became stale by the time it was actually applied, producing an inconsistent result. The equivalent pattern exists in Agave's `getSupply` JSON-RPC handler: two related quantities (`total_supply` and `non_circulating_supply.lamports`) are captured at two different points in time from a bank that can be actively mutating between those reads, and they are then combined with a non-saturating subtraction.

### Finding Description
`JsonRpcRequestProcessor::get_supply` first performs a full scan to compute `non_circulating_supply` (which internally walks all stake-program accounts and, for each candidate pubkey, calls `bank.get_balance(pubkey)` one at a time) and only *after* that scan completes reads `total_supply = bank.capitalization()`: [1](#0-0) 

`calculate_non_circulating_supply` sums balances lazily, one lookup per tracked pubkey, while the target `bank` can still be an actively-processing (unfrozen) bank obtained via `self.bank(config.commitment)`: [2](#0-1) 

Because `capitalization()` is read strictly *after* the (potentially slow, multi-account) scan finishes, and both quantities are supposed to represent the same logical bank state, any concurrent transaction processing that changes account balances or bank capitalization between the start of the scan and the final `bank.capitalization()` read will desynchronize the two numbers — exactly analogous to the BakerFi report where `totalSupply()` was read before a subsequent mutation (`_mint`) instead of accounting for it, producing a mismatched ratio.

The final computation uses a plain (non-saturating) subtraction:
```rust
circulating: total_supply - non_circulating_supply.lamports,
```
If the scan observes `non_circulating_supply.lamports` that (due to the race) ends up larger than the `total_supply` value read afterward, this subtraction underflows a `u64`.

### Impact Explanation
This is reachable via a single unprivileged `getSupply` JSON-RPC call. Depending on build configuration:
- If overflow checks are enabled for the validator build, the underflow triggers a `panic!`, crashing the RPC-serving thread/validator process from a single client request.
- If overflow checks are not enabled, the subtraction silently wraps to a value near `u64::MAX`, causing wildly incorrect "circulating supply" to be reported to RPC clients (misreporting of on-chain economic data).

Either outcome matches the accepted impact classes ("concrete validator-process crash ... from one request" or "wrong ... data returned"). I was not able to verify from the indexed files whether the workspace `Cargo.toml` release profile enables `overflow-checks` (the search for this setting returned no results, likely because the top-level `Cargo.toml` is outside indexed content), so the crash-vs-misreporting outcome could not be conclusively confirmed from the available index.

### Likelihood Explanation
Triggering the race requires the target bank to still be actively mutating (i.e., a non-frozen/working bank, which is the default when no/`processed` commitment is supplied) and requires enough concurrent transaction volume changing balances/capitalization during the scan window. On a busy validator, `getSupply` scans a fixed but non-trivial set of stake/non-circulating accounts (dozens to potentially many stake accounts), giving a real window for concurrent mutation. This is a plausible but timing-dependent condition, not deterministic on every call, and it hits the low-rate RPC call restriction (no flooding needed — a single call during high tx throughput is enough to encounter divergence).

### Recommendation
Compute `total_supply` and `non_circulating_supply` from the exact same, single logical view: either read `bank.capitalization()` before performing the scan (and, ideally, freeze/borrow a consistent view for both computations), or use `total_supply.saturating_sub(non_circulating_supply.lamports)` to eliminate the panic/wraparound while a more thorough fix (making the whole quantity consistent, e.g. by having `calculate_non_circulating_supply` also return the total capitalization sampled at scan start) is implemented.

### Proof of Concept
1. Run a validator/RPC node with an unfrozen bank exposed to `getSupply` (default commitment, i.e. no commitment or `processed`).
2. Concurrently drive transaction load that mutates the balances of accounts tracked as "non-circulating" (e.g., transfer lamports into locked/non-circulating stake accounts) while repeatedly calling `getSupply`.
3. Because `calculate_non_circulating_supply` sums balances account-by-account and `bank.capitalization()` is read only after the scan finishes, a sufficiently large concurrent increase to the tracked non-circulating balances (or decrease to overall capitalization) between the start of the scan and the final capitalization read can make `non_circulating_supply.lamports > total_supply`, causing the non-saturating subtraction at rpc/src/rpc.rs:1148 to underflow.

    async fn get_supply(
        &self,
        config: Option<RpcSupplyConfig>,
    ) -> RpcCustomResult<RpcResponse<RpcSupply>> {
        let config = config.unwrap_or_default();
        let bank = self.bank(config.commitment);
        let non_circulating_supply =
            self.calculate_non_circulating_supply(&bank)
                .await
                .map_err(|e| RpcCustomError::ScanError {
                    message: e.to_string(),
                })?;
        let total_supply = bank.capitalization();
        let non_circulating_accounts = if config.exclude_non_circulating_accounts_list {
            vec![]
        } else {
            non_circulating_supply
                .accounts
                .iter()
                .map(|pubkey| pubkey.to_string())
                .collect()
        };

        Ok(new_response(
            &bank,
            RpcSupply {
                total: total_supply,
                circulating: total_supply - non_circulating_supply.lamports,
                non_circulating: non_circulating_supply.lamports,
                non_circulating_accounts,
            },
        ))
    }

pub fn calculate_non_circulating_supply(bank: &Bank) -> ScanResult<NonCirculatingSupply> {
    debug!("Updating Bank supply, epoch: {}", bank.epoch());
    let mut non_circulating_accounts_set: HashSet<Pubkey> = HashSet::new();

    for key in non_circulating_accounts() {
        non_circulating_accounts_set.insert(key);
    }
    let withdraw_authority_list = withdraw_authority();

    let clock = bank.clock();
    let stake_accounts = if bank
        .rc
        .accounts
        .accounts_db
        .account_indexes
        .contains(&AccountIndex::ProgramId)
    {
        bank.get_filtered_indexed_accounts(
            &IndexKey::ProgramId(stake::program::id()),
            // The program-id account index checks for Account owner on inclusion. However, due to
            // the current AccountsDb implementation, an account may remain in storage as a
            // zero-lamport Account::Default() after being wiped and reinitialized in later
            // updates. We include the redundant filter here to avoid returning these accounts.
            |account| account.owner() == &stake::program::id(),
            None,
        )?
    } else {
        bank.get_program_accounts(&stake::program::id())?
    };

    for (pubkey, account) in stake_accounts.iter() {
        let stake_account = account
            .deserialize_data::<StakeStateV2>()
            .unwrap_or_default();
        match stake_account {
            StakeStateV2::Initialized(meta)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            StakeStateV2::Stake(meta, _stake, _stake_flags)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            _ => {}
        }
    }

    let lamports = non_circulating_accounts_set
        .iter()
        .map(|pubkey| bank.get_balance(pubkey))
        .sum();

    Ok(NonCirculatingSupply {
        lamports,
        accounts: non_circulating_accounts_set.into_iter().collect(),
    })
}
