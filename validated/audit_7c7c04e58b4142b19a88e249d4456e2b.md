### Title
Windows Job Object cleanup does not terminate `CREATE_BREAKAWAY_FROM_JOB` child processes on normal job completion - ([File: helpers/process/job_windows.go])

### Summary
On Windows, `CreateJobObject()` sets `JOB_OBJECT_LIMIT_BREAKAWAY_OK` alongside `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, which lets any child process created with `CREATE_BREAKAWAY_FROM_JOB` escape job-object membership entirely. The normal (non-cancelled) completion path in `executors/shell/shell.go` `Run()` only calls `osCmd.Wait()` → `closeJobObject()`, which relies solely on `KILL_ON_JOB_CLOSE` semantics and therefore never touches breakaway children, while the cancellation path (`KillAndWait`) at least has a chance to run `taskkill /F /T` (process-tree-based, not job-membership-based) via `ForceKill()`.

### Finding Description
`CreateJobObject()` in `helpers/process/job_windows.go` explicitly configures: [1](#0-0) 
`JOB_OBJECT_LIMIT_BREAKAWAY_OK` allows any process spawned with the Win32 `CREATE_BREAKAWAY_FROM_JOB` creation flag to leave the job object's process set. Once a process breaks away, it is no longer tracked by the job, so `KILL_ON_JOB_CLOSE` — the only cleanup mechanism used on the normal completion path — cannot terminate it.

The normal completion path is: [2](#0-1) 
`Wait()` just calls `internal.Wait()` (which returns as soon as the immediate child/shell process exits, not when all its descendants exit) and then `closeJobObject()`, which does `windows.CloseHandle(c.jobObject)` and nothing else — no enumeration of job processes, no `taskkill /T` sweep.

In `executors/shell/shell.go` `Run()`, the fast/normal exit takes the `case err = <-waitCh: return err` branch: [3](#0-2) 
This branch never constructs a `killer`/`KillWaiter`, so `Terminate()`/`ForceKill()` (which calls `taskkill /F /T /PID`, a process-ancestry-based kill that is not restricted by job-object membership) are never invoked. Only the cancellation branch (`<-cmd.Context.Done()`) can reach `ForceKill()`, and only after `gracefulKillTimeout` elapses without the CTRL_BREAK/CTRL_C signal (`Terminate()`) causing exit.

An unprivileged pipeline author who controls the job script (any CI job running on a shell executor with `FF_USE_WINDOWS_JOB_OBJECT` enabled) can spawn a detached long-running process using `CREATE_BREAKAWAY_FROM_JOB` (trivially reachable from PowerShell via P/Invoke to `CreateProcess`, or via a small compiled helper committed to the repo/cache and executed by the job) and then let the job script exit normally. Because:
1. The child process breaks away from the job object (allowed by `JOB_OBJECT_LIMIT_BREAKAWAY_OK`),
2. `internal.Wait()` returns once the top-level shell process itself exits, independent of the breakaway grandchild,
3. `closeJobObject()` only closes the handle — it has no process left in the job to kill, since the breakaway child is no longer a job member,

the breakaway process survives indefinitely on the runner host after the job is marked finished, with no `ForceKill`/`taskkill /T` sweep ever executing. This is deterministic and reliable — no timing race is needed, unlike attempting the same trick via the cancellation path (where `Terminate()`'s CTRL_BREAK could still hit the still-running parent shell process, and if the shell process delays exit, `ForceKill()`'s `taskkill /T` could still catch the breakaway child via process ancestry before the parent disappears).

### Impact Explanation
An unprivileged CI job author can leave an arbitrary, indefinitely-running, unmonitored process on a shared Windows runner host after their job is reported as completed successfully. This breaks the intended isolation/cleanup invariant that Runner's own Job Object mechanism is designed to guarantee ("When the last handle on the job is closed, all associated processes will be terminated" — see the comment in `AssignPidToJobObject`, `helpers/process/job_windows.go` lines 118-119). Concrete impact: persistent unauthorized code execution/resource consumption on a shared runner beyond the job's lifetime, potential interference with subsequent jobs sharing the same host/build directory, and a reliable process-leak/DoS vector, all without requiring the cancellation timing race the question hypothesizes.

### Likelihood Explanation
Requires: (1) Windows shell/custom executor, (2) `FF_USE_WINDOWS_JOB_OBJECT` enabled (an opt-in but user-configurable feature flag, not admin-only), (3) job script capable of invoking Win32 `CreateProcess` with `CREATE_BREAKAWAY_FROM_JOB` (trivial via PowerShell/.NET reflection or a bundled binary). No race condition is needed — the normal-exit path deterministically skips any process-tree kill, making this fully reproducible on every run, which is a stronger and cheaper technique than relying on the cancellation-path race.

### Recommendation
Do not rely exclusively on `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` for cleanup when `JOB_OBJECT_LIMIT_BREAKAWAY_OK` is also set. Either (a) drop `JOB_OBJECT_LIMIT_BREAKAWAY_OK` unless a specific compatibility need is documented and gated, or (b) after `internal.Wait()` in `osCmd.Wait()`, always perform an explicit process-tree termination (equivalent to `taskkill /F /T /PID <root pid>`) for the whole process tree rooted at the launched process before returning, regardless of whether the job was cancelled — closing the parity gap between the normal-completion path and `KillAndWait`'s `ForceKill()`.

### Proof of Concept
Go integration test (Windows-only, modeled on `helpers/process/killer_integration_test.go`):
1. Build a small helper test binary/script that, when run, spawns a grandchild process via `CreateProcess` with `CREATE_BREAKAWAY_FROM_JOB` set, then immediately exits itself (simulating a fast-completing job).
2. Run it through `newOSCmd`/`osCmd.Start()` with `CommandOptions{UseWindowsJobObject: true}`, matching `executors/shell/shell.go` `Run()`'s normal-exit branch (call `Wait()` directly, not via `KillAndWait`).
3. After `Wait()` returns, assert the breakaway grandchild PID is still alive (e.g., via `OpenProcess`/`GetExitCodeProcess` returning `STILL_ACTIVE`), proving `closeJobObject()` did not terminate it.
4. As a comparison case, repeat with a `cmd.Context` that is cancelled instead, driving the `KillAndWait` path, and assert whether/when the grandchild dies — showing that even the cancellation path's outcome is timing-dependent while the normal-exit path is deterministic in leaving the process alive.
5. Both assertions failing the "must fully terminate everything the job process tree spawned" invariant confirms the bug for both paths, with the normal path being the more reliable exploit technique.
