### Title
Permissionless donation to the programmable borrower's ERC4626 vault inflates `totalInterestDueNow` past the `maxApr` cap and permanently bricks `stopEpoch` - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant._stopEpoch` trusts a pool-facing interest value derived from an external ERC4626 vault's `convertToAssets` (`ProgrammableBorrower.totalInterestDueNow` → `_vaultNetInterest`). Any unprivileged user of that vault (or any EOA) can transfer underlying directly into the vault contract, inflating every holder's `convertToAssets` — including the `ProgrammableBorrower`'s position. In minted-interest mode (required for programmable borrowers), `_stopEpoch` reverts whenever resolved gross interest exceeds `maxApr`-capped interest (`IdleCDOEpochVariant.sol:377-380`). Because the donation is permanent, every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts, freezing the running epoch, all pending withdraw requests, and LP redemptions until governance forces an emergency shutdown/default.

### Finding Description
`ProgrammableBorrower` parks all undrawn lender capital in a single external ERC4626 `vault` (`ProgrammableBorrower.sol:38`, `216`) and prices each epoch from the live share value: `_vaultNetInterest` computes `currentVaultAssets + epochWithdrawnFromVault - epochStartVaultAssets - epochDepositedToVault` plus `bufferedVaultDelta` (`ProgrammableBorrower.sol:337-347`), and `totalInterestDueNow` adds borrower interest and `bufferInterest` (`ProgrammableBorrower.sol:330-334`). This is the exact analog of the Plate SSRF: a privileged consumer fetches a value from an attacker-writable external resource and embeds the response verbatim into its own accounting/output.

`_currentVaultAssets` is `vault.convertToAssets(vault.balanceOf(this))`. For any ERC4626 whose `convertToAssets` is proportional to `totalAssets/totalSupply` (Morpho vaults, standard vaults — the test mock behaves this way, `ProgrammableBorrowerCreditVault.t.sol:36-39`), a direct `underlying.transfer(vault, X)` inflates the ProgrammableBorrower's share valuation by `X * pbShares / totalSupply`. An attacker needs no role: they can be a vault user or just a direct token sender.

In `_stopEpoch` (`IdleCDOEpochVariant.sol:330-506`):
- `_interest = _resolveStopEpochInterest(_interest)` pulls `totalInterestDueNow()` for programmable borrowers, so the inflated value lands in `_expectedInterest`/`_grossInterest` (lines 357-373).
- `isInterestMinted` must be true for programmable borrowers (see `testProgrammableBorrowerRequiresMintedInterest`, `ProgrammableBorrowerCreditVault.t.sol:869`), so `_mintInterest` is true and the guard fires:

```solidity
// IdleCDOEpochVariant.sol:377-380
if (_mintInterest && _interest > 1) {
  uint256 _maxApr = _strategy.maxApr();
  _checkNotAllowed(_maxApr != 0 && _grossInterest > _calcInterestWithApr(getContractValue(), _maxApr) + _pendingWithdrawFees);
}
```

If attacker donation `D > maxAprInterest + pendingWithdrawFees - realInterest`, `_checkNotAllowed` reverts — and it reverts on every retry, forever, since donations cannot be clawed back and `bufferedVaultDelta`/epoch baselines keep the phantom "profit" in `totalInterestDueNow`.

Notably, the donation is even sticky across epochs: a donation landing while the pool is in the buffer is captured as `bufferedVaultDelta = currentVaultAssets - bufferStartVaultAssets` at the next `onStartEpoch` (`ProgrammableBorrower.sol:206-211`), so the attack also works pre-emptively.

Existing guards do not stop it: `_skimDonatedAssets` (line 355) only skims tokens donated to the CDO itself, not to the external vault; `onStopEpoch`'s `try/catch` (lines 246-253) only covers withdrawal reverts; the maxApr check itself is the revert. The only recovery is owner `emergencyShutdown`/`finalizeDefault`, i.e. the entire credit facility is forced into a terminal default flow.

### Impact Explanation
Permanent freezing of all tranche-holder funds in the pool (AA/BB deposits, pending withdraw requests) for a donation cost bounded by `maxApr * NAV * epochDuration / YEAR` — with typical single-digit maxApr this is a small fraction of pool NAV, while 100% of pool NAV is frozen. The protocol's only escape is emergency shutdown + `finalizeDefault`, which kills the facility and crystallizes a "default" on what was actually a solvent borrower. This matches the accepted impact classes (permanent freezing / forced bad-debt socialization path). Unquantified residual risk: recovery of the vault shares post-default requires owner/manager `emergencyExitVault`, adding further delay.

### Likelihood Explanation
Requires only a programmable-borrower deployment (the flagship `IdleCreditVault` configuration in this codebase) whose ERC4626 vault's `convertToAssets` rises on direct donations — true for the MetaMorpho-style vault used in tests (`ProgrammableBorrowerCreditVault.t.sol`). Any EOA or vault user can execute it atomically the block before `stopEpoch` after `epochEndDate`, or even during the buffer. No privileged role, no timing luck beyond the public epoch schedule. I could not fully read `_resolveStopEpochInterest`'s body before finalizing, but the stored tests (`stopEpoch(0,0)` reading `totalInterestDueNow` into `lastEpochInterest`, `ProgrammableBorrowerCreditVault.t.sol:219-222`) confirm the resolved value flows into `_interest`/`_grossInterest`.

### Recommendation
Cap the vault-PnL component of `totalInterestDueNow` at a realized, donation-resistant measure — e.g., track `epochStartVaultShares` and use `previewRedeem`-safe bounds, or clamp `_vaultNetInterest`'s positive leg by `maxApr` interest instead of reverting. Alternatively, treat interest above the cap as skimmed donation (credit it to `feeReceiver`/a recovery bucket) rather than reverting, mirroring how `_skimDonatedAssets` handles direct donations to the CDO.

### Proof of Concept
```solidity
// Foundry test sketch (extends test/foundry/ProgrammableBorrowerCreditVault.t.sol setup)
function testVaultDonationPermanentlyBricksStopEpoch() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);            // ProgrammableBorrower deposits into Morpho vault

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Attacker: any EOA / vault user donates underlying straight to the ERC4626 vault.
    // Inflates convertToAssets(ProgrammableBorrower's shares) => totalInterestDueNow()
    // exceeds _calcInterestWithApr(getContractValue(), maxApr) + pendingWithdrawFees.
    uint256 donation = amount / 10;          // > maxApr-capped epoch interest
    deal(USDC, attacker, donation);
    vm.prank(attacker);
    IERC20Detailed(USDC).transfer(address(morphoVault), donation);

    // Every stopEpoch attempt reverts; epoch can never close.
    vm.prank(manager);
    vm.expectRevert();                       // NotAllowed from _checkNotAllowed at line 379
    cdoEpoch.stopEpoch(0, 0);

    vm.warp(block.timestamp + 365 days);     // donation persists; still bricked
    vm.prank(manager);
    vm.expectRevert();
    cdoEpoch.stopEpoch(0, 0);

    // LP funds (deposits + pending withdraw requests) are frozen; only
    // emergencyShutdown/finalizeDefault can unwind, forcing a fake default.
    assertEq(cdoEpoch.isEpochRunning(), true);
}
```
