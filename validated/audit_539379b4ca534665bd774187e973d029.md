### Title
Missing Zero-Address Validation for `recipientAddress` in Bridge Token Unlock — (File: `bridge/evm/contracts/SuiBridge.sol`)

### Summary
`_transferTokensFromVault` in `SuiBridge.sol` and `SuiBridgeV2.sol` validates that the ERC20 token contract address is not zero but never validates that `recipientAddress != address(0)`. A bridge user who specifies `0x0000000000000000000000000000000000000000` as the EVM recipient causes bridged ETH or ERC20 tokens to be permanently burned on Ethereum while the corresponding assets are already locked or burned on the Sui side.

### Finding Description
In `SuiBridge._transferTokensFromVault`, the only zero-address check guards the token contract address, not the recipient:

```solidity
require(tokenAddress != address(0), "SuiBridge: Unsupported token");
// No check: require(recipientAddress != address(0), ...)
if (tokenID == BridgeUtils.ETH) {
    vault.transferETH(payable(recipientAddress), amount);   // burns ETH if recipientAddress == address(0)
} else {
    vault.transferERC20(tokenAddress, recipientAddress, amount); // burns ERC20 if recipientAddress == address(0)
}
``` [1](#0-0) 

The `recipientAddress` is decoded from the bridge message payload by `BridgeUtils.decodeTokenTransferPayload`, which only validates that the address field is exactly 20 bytes — it does not check that the decoded address is non-zero:

```solidity
uint8 recipientAddressLength = uint8(_payload[offset++]);
require(
    recipientAddressLength == 20,
    "BridgeUtils: Invalid target address length, EVM address must be 20 bytes"
);
// address(0) passes this check — 20 zero bytes is a valid 20-byte value
assembly {
    recipientAddress := mload(add(_payload, add(recipientAddressLength, offset)))
}
``` [2](#0-1) 

The identical gap exists in `SuiBridgeV2._transferTokensFromVault` and `BridgeUtilsV2.decodeTokenTransferPayloadV2`: [3](#0-2) [4](#0-3) 

When `recipientAddress == address(0)`:
- **ETH path:** `vault.transferETH(payable(address(0)), amount)` unwraps WETH then executes `address(0).call{value: amount}("")`, which succeeds in Solidity and permanently burns the ETH.
- **ERC20 path:** `vault.transferERC20(tokenAddress, address(0), amount)` calls `SafeERC20.safeTransfer(token, address(0), amount)`. For WETH, USDC, and USDT — the tokens supported by this bridge — none revert on a zero-address recipient, so the tokens are permanently burned. [5](#0-4) 

### Impact Explanation
Bridged ETH or ERC20 tokens (WETH, USDC, USDT, wBTC) are permanently burned on Ethereum. Because the corresponding assets are already locked or burned on the Sui side at the time the bridge message is created, the user's funds are irrecoverably lost. The nonce is marked processed (`isTransferProcessed[message.nonce] = true`), so the message cannot be replayed to recover the funds. This constitutes unintended permanent burning of bridged assets, matching the "permanent fund lock / unintended permanent burning below the 10B cap" allowed impact class. [6](#0-5) 

### Likelihood Explanation
Low. A bridge user must specify `0x0000000000000000000000000000000000000000` as the EVM recipient, which can occur accidentally through a UI bug, an encoding error, or a copy-paste mistake when constructing the Sui-side bridge call. Validators sign the message because the payload format is valid (20-byte address field). No privileged actor is required.

### Recommendation
Add a zero-address guard in `_transferTokensFromVault` in both `SuiBridge.sol` and `SuiBridgeV2.sol`:

```solidity
require(recipientAddress != address(0), "SuiBridge: Invalid recipient address");
```

Additionally, add the same check inside `BridgeUtils.decodeTokenTransferPayload` and `BridgeUtilsV2.decodeTokenTransferPayloadV2` immediately after the assembly block that extracts `recipientAddress`, so the invariant is enforced at the earliest possible point in the decode path. [7](#0-6) [8](#0-7) 

### Proof of Concept
1. On Sui, call the bridge's token-send entry function with `target_address` set to 20 zero bytes (`0x0000000000000000000000000000000000000000`). The Sui-side bridge locks or burns the tokens and emits a bridge event.
2. Validators observe the event and sign the bridge message. The payload passes all format checks: sender address length = 32, recipient address length = 20.
3. Call `transferBridgedTokensWithSignatures(signatures, message)` on Ethereum (callable by anyone).
4. `BridgeUtils.decodeTokenTransferPayload` decodes `recipientAddress = address(0)` — the length check (`== 20`) passes.
5. `_transferTokensFromVault` is entered. `tokenAddress != address(0)` passes (it checks the ERC20 contract address, not the recipient).
6. For ETH: `vault.transferETH(payable(address(0)), 1 ether)` → WETH unwrapped → `address(0).call{value: 1 ether}("")` returns `(true, "")` → 1 ETH permanently burned.
7. For USDC: `vault.transferERC20(USDC, address(0), amount)` → `SafeERC20.safeTransfer(USDC, address(0), amount)` → USDC `transfer(address(0), amount)` succeeds → tokens permanently burned.
8. `isTransferProcessed[nonce] = true` — the message is consumed; no recovery is possible. [9](#0-8)

        // extract target address from payload (35-54)
        address recipientAddress;

        // why `add(recipientAddressLength, offset)`?
        // At this point, offset = 35, recipientAddressLength = 20. `mload(add(payload, 55))`
        // reads the next 32 bytes from bytes 23 in paylod, because the first 32 bytes

        // casting to address (20 bytes), the least sigificiant bytes are retained, namely
        // `recipientAddress` is bytes 35-54

        }

        // move offset past the target address length
        offset += recipientAddressLength;
