### Title
Symlink-target validation bypass in tar/zstd extraction allows writes/metadata changes outside the job's build directory into sibling project directories on a shared persistent builds root - ([File: commands/helpers/archive/tarzstd/tarzstd_extractor.go])

### Summary
The tarzstd extractor's containment check only validates the *location* of each tar entry against the extraction root (`e.dir`); it never validates a symlink entry's *target* (`hdr.Linkname`), and it never re-resolves the filesystem path after a symlink has actually been placed on disk. Because the same working directory (`wd = os.Getwd()`) is reused by successive `cache-extractor`/`artifacts-downloader` invocations within one job, and is a *sibling* of other projects' directories under the shared `builds_dir` layout, a two-stage archive (symlink in one extraction, then a matching path in a later extraction in the same job) lets subsequent `os.Create`/`os.MkdirAll`/`lchmod`/`lchtimes` calls operate on a path that is lexically inside `e.dir` but is actually resolved by the OS through the planted symlink to a location outside `e.dir`, including another project's build directory.

### Finding Description
`Extract()` computes the destination for a tar entry purely lexically: [1](#0-0) 

This check bounds `path` (i.e., the *location where the entry itself will be written*) but does nothing to validate `hdr.Linkname` — the target a symlink entry will point to: [2](#0-1) 

So an archive built by an unprivileged pipeline author can contain a symlink entry located inside `e.dir` (passes the containment check) whose target is an arbitrary relative path such as `../../otherns/otherproject` (reachable because the default builds layout nests all projects under a shared root, e.g. `{builds_dir}/$RUNNER_TOKEN_KEY/$CONCURRENT_PROJECT_ID/...`, as documented). This planted symlink is created and persists on disk after `Extract()` returns.

The extraction dir `e.dir` is simply the process's current working directory at invocation time, and this is reused across multiple sequential extraction invocations in the same job (multiple cache paths, fallback cache keys, or cache+artifacts): [3](#0-2) [4](#0-3) [5](#0-4) 

In a *second* extraction (a fallback cache, or artifacts) run afterward in the same job/working directory, a regular file entry whose name traverses through the now-existing symlink component (e.g. `shared/evil.txt` where `shared` is the previously planted symlink) is processed: [6](#0-5) 

`filepath.Abs(filepath.Join(e.dir, hdr.Name))` and the `strings.HasPrefix` check operate on the *lexical* string, so they pass. But `os.MkdirAll` and `os.Create` are normal syscalls that follow symlinks in intermediate path components — the actual file lands wherever the pre-existing symlink points, i.e. potentially inside a sibling project's directory. Immediately afterward, `updateFileMetadata` calls `lchtimes`/`lchmod` on that same lexical `path`: [7](#0-6) 

On Windows, `lchmod`/`lchtimes` only special-case the entry itself being a symlink (`mode&os.ModeSymlink`); they do not protect against an intermediate directory component being a symlink, and delegate straight to `os.Chmod`/`os.Chtimes`, which follow symlinks during path resolution: [8](#0-7) 

So the metadata (mode bits, atime/mtime) — and, more severely, the file content itself via the preceding `os.Create`/`io.Copy` — end up modified on a path outside `e.dir`, inside whatever directory the earlier symlink's `Linkname` pointed to. No admin misconfiguration is required: default `builds_dir` nesting, default cache/fallback-cache/artifacts flows, and normal job authoring are sufficient.

### Impact Explanation
On a runner where multiple projects' build directories persist as siblings under the shared `builds_dir` (normal for `shell`/`custom` and for `docker-windows` with host-mounted persistent build paths, concurrent jobs, or non-cleaned checkouts), an unprivileged pipeline author in project A can plant a symlink via a cache/artifact archive and, through a second extraction step in the same job, cause file writes and `lchmod`/`lchtimes` metadata mutation to land inside project B's on-disk build directory. This is metadata corruption and potential file-content tampering across tenant boundaries — a violation of the "file operations must stay within intended build/cache/artifact roots" invariant, and it bypasses the Runner's own explicit "cannot be extracted outside of chroot" protection rather than merely relying on a documented insecure admin choice.

### Likelihood Explanation
Preconditions are all things Runner supports by default: multiple projects sharing a `builds_dir` root, jobs that use cache with multiple paths/fallback keys or cache+artifacts (both are ordinary, non-exotic pipeline configurations), and a build directory that is not fully wiped between the two extraction invocations within a single job (guaranteed within one job execution regardless of `GIT_STRATEGY`). The only environment-dependent factor is whether the process performing extraction has privilege to create the initial symlink (`os.Symlink`) — on Windows this needs `SeCreateSymbolicLinkPrivilege`, commonly available to the runner service account (e.g., `LocalSystem`) but not guaranteed for every account; on Unix this is unrestricted for normal users. This makes the bug fully reachable on Unix-based shell/custom/docker executors with shared builds roots, and reachable on Windows wherever the runner process has symlink-creation rights.

### Recommendation
- Validate `hdr.Linkname` for symlink entries against the extraction root the same way entry locations are validated (reject or clamp targets that resolve outside `e.dir`).
- Before writing any entry, resolve the parent directory chain with `filepath.EvalSymlinks` (or equivalent) and re-verify containment against `e.dir`, rejecting extraction if any existing path component is a symlink that escapes the root.
- Alternatively, extract using an `os.Root`/openat-based chroot-style API (Go 1.24 `os.Root`) that refuses to traverse symlinks outside the sandboxed root, for both file creation and metadata updates (`lchmod`/`lchtimes`/`lchown`).

### Proof of Concept
Go integration test in `commands/helpers/archive/tarzstd`:
1. Create `dirA` and `dirB` as sibling directories (simulating two projects' build dirs under a shared builds root).
2. Build archive #1 containing only a symlink entry `link` -> `../dirB` (relative target escaping `dirA`); extract it with `dir = dirA`. Assert extraction succeeds (no error), and `dirA/link` exists as a symlink pointing to `../dirB`.
3. Build archive #2 containing a regular file entry `link/evil.txt` with distinct content, mode, and mtime; extract it with `dir = dirA` (same extraction root, simulating a fallback-cache/artifacts step in the same job).
4. Assert `dirB/evil.txt` now exists with the attacker-supplied content, mode, and mtime (proving the write/metadata update escaped `dirA` into `dirB`), and that no error was returned from `Extract()` (proving the "cannot be extracted outside of chroot" guard did not catch it).
5. Repeat step 3-4 after a simulated job-A cancellation (i.e., only running extraction #1, then killing the job, then starting a fresh job-A run that performs extraction #2) to show the corruption of `dirB` persists independent of job A's lifecycle.

func (e *extractor) updateFileMetadata(path string, hdr *tar.Header) error {
	fi := hdr.FileInfo()

	if err := lchtimes(path, fi.Mode(), time.Now(), fi.ModTime()); err != nil {
		return err
	}

	if err := lchmod(path, fi.Mode()); err != nil {
		return err
	}

	_ = lchown(path, hdr.Uid, hdr.Gid)
	return nil

func (c *ArtifactsDownloaderCommand) Execute(cliContext *cli.Context) {
	log.SetRunnerFormatter()

	wd, err := os.Getwd()
	if err != nil {
		logrus.Fatalln("Unable to get working directory")
	}

	if c.URL == "" {
		logrus.Warningln("Missing URL (--url)")
	}
	if c.Token == "" {
		logrus.Warningln("Missing runner credentials (--token)")
	}
	if c.ID <= 0 {
		logrus.Warningln("Missing build ID (--id)")
	}
	if c.ID <= 0 || c.Token == "" || c.URL == "" {
		logrus.Fatalln("Incomplete arguments")
	}

	// Create temporary file
	file, err := os.CreateTemp(c.StagingDir, "artifacts")
	if err != nil {
		logrus.Fatalln(err)
	}
	_ = file.Close()
	defer func() { _ = os.Remove(file.Name()) }()

	// Download artifacts file
	err = c.doRetry(func(retry int) error {
		return c.download(file.Name(), retry)
	})
	if err != nil {
		logrus.Fatalln(err)
	}

	f, size, format, err := openArchive(file.Name())
	if err != nil {
		logrus.Fatalln(err)
	}
	defer f.Close()

	extractor, err := archive.NewExtractor(format, f, size, wd)
	if err != nil {
		logrus.Fatalln(err)
	}

	// Extract artifacts file
	err = extractor.Extract(context.Background())
	if err != nil {
		logrus.Fatalln(err)
	}

func (b *AbstractShell) addExtractCacheCommand(
	ctx context.Context,
	w ShellWriter,
	info common.ShellScriptInfo,
	cacheConfigs []cacheConfig,
	cachePaths []string,
) {
	cacheConfig := cacheConfigs[0]

	args := []string{
		"cache-extractor",
		"--file", cacheConfig.ArchiveFile,
		"--timeout", strconv.Itoa(info.Build.GetCacheRequestTimeout()),
	}

	w.Noticef("Checking cache for %s...", cacheConfig.HumanKey)

	extraArgs, env, err := getCacheDownloadURLAndEnv(ctx, info.Build, cacheConfig.HashedKey)
	args = append(args, extraArgs...)
	if err != nil {
		w.Warningf("Failed to obtain environment for cache %s: %v", cacheConfig.HumanKey, err)
	}
	if env != nil {
		cacheEnvFilename := b.writeCacheExports(w, env)
		args = append(args, "--env-file", cacheEnvFilename)
		defer w.RmFile(cacheEnvFilename)
	}

	alternateURLArgs, alternateErr := getAlternateCacheDownloadURL(ctx, info.Build, cacheConfig.AlternateKey)
	if alternateErr != nil {
		w.Warningf("Failed to obtain alternate URL for cache %s: %v", cacheConfig.HumanKey, alternateErr)
	} else {
		args = append(args, alternateURLArgs...)
	}

	w.IfCmdWithOutput(info.RunnerCommand, args...)
	w.Noticef("Successfully extracted cache")
	w.Else()
	w.Warningf("Failed to extract cache")

	// When extraction fails, remove the cache directories to avoid problems in cases
	// where archives may have been partially extracted, leaving the cache in an inconsistent
	// state. If we attempt to extract from fallback caches below, we'll remove the same set
	// of directories if that fails.
	if info.Build.IsFeatureFlagOn(featureflags.CleanUpFailedCacheExtract) {
		for _, cachePath := range cachePaths {
			w.Printf("Removing %s", cachePath)
			w.RmDir(cachePath)
		}
	}

	// We check that there is another key than the one we just used
	if len(cacheConfigs) > 1 {
		b.addExtractCacheCommand(ctx, w, info, cacheConfigs[1:], cachePaths)
	}
	w.EndIf()

func lchmod(name string, mode os.FileMode) error {
	if mode&os.ModeSymlink != 0 {
		return nil
	}

	return os.Chmod(name, mode)
}

func lchtimes(name string, mode os.FileMode, atime, mtime time.Time) error {
	if mode&os.ModeSymlink != 0 {
		return nil
	}

	return os.Chtimes(name, atime, mtime)
}
