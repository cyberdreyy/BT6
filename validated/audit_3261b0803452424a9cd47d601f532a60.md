### Title
`check_latest_block_in_tenure` fails open (assumes the proposal is higher) when the signer's own node RPC for the tenure tip errors - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
The reported CVE is a bypass of a security check caused by trusting an unreliable, OS/environment-dependent oracle (`Resolv.getaddresses`) instead of treating an ambiguous answer conservatively. The analogous pattern in this repo is `SortitionData::check_latest_block_in_tenure`, which asks the signer's own stacks-node for the tenure's current tip via `client.get_tenure_tip(tenure_id)` to decide whether a proposed block actually confirms as much of the parent/own tenure as it must. When that RPC call fails for any reason, the function does not treat the answer as unknown/inconclusive — it explicitly assumes success and returns `Ok(true)`, i.e., "the proposal is higher than the tenure tip; passes." [1](#0-0) 

### Finding Description
`check_latest_block_in_tenure` is the mechanism that answers "does this block confirm the tip I expect from a given tenure?" and is documented to run in three separate places on the critical signing path: at proposal arrival (`check_proposal`), after node validation succeeds (`handle_block_validate_ok` → `check_block_against_signer_db_state`), and again immediately before the signature is emitted at the pre-commit threshold (`handle_block_pre_commit` → `check_block_against_signer_db_state`). [2](#0-1) 

The first stage of the check (comparing against the last *signed* block already recorded in `signerdb`) is a reliable, locally-verified fact. But once that stage passes (no signed block known locally at or above the proposed height), the function falls back to asking the node's `get_tenure_tip` endpoint for ground truth:

```rust
let tip = match client.get_tenure_tip(tenure_id) {
    Ok(tip) => tip.anchored_header,
    Err(e) => {
        warn!(
            "Failed to fetch the tenure tip for the parent tenure: {e:?}. Assuming proposal is higher than the parent tenure for now.";
            ...
        );
        return Ok(true);
    }
};
...
Ok(tip.height() < block.header.chain_length)
``` [3](#0-2) 

This is a fail-open design: any transient failure of the node's own RPC (timeout, connection reset, node busy processing another block, node mid-restart, node syncing) silently converts an "I don't know" into "yes, it confirms enough." Because `Ok(true)` is exactly the value returned when the RPC *succeeds* and genuinely reports the tip below the proposed chain length, callers cannot distinguish "verified higher" from "could not verify, assumed higher." This mirrors the CVE's root cause precisely: a security-relevant equality check (does the proposal's chain length exceed the last confirmed tip in this tenure — the "approved-parent vs canonical" equality) is delegated to a local, non-authoritative, environment-dependent oracle (the node's HTTP/RPC stack), and a negative/ambiguous result from that oracle is silently treated as an affirmative pass rather than surfaced as inconclusive.

Because the check runs again at the moment of signing (`check_block_against_signer_db_state` inside `handle_block_pre_commit`), a node hiccup exactly at that instant is sufficient to let a signature over a chain-length-deficient block through even if the earlier proposal-time check happened to succeed honestly, since each of the three call sites independently re-queries `get_tenure_tip` and each independently fails open. [4](#0-3) 

### Impact Explanation
If the check silently fails open at the pre-commit/signing call site, a signer can place a signature on a block whose chain length does not actually confirm the tenure tip the network already knows about — i.e., the signer signs a non-canonical/conflicting block relative to the true state of the parent tenure. This directly breaks the "approved-parent vs canonical" equality that `check_latest_block_in_tenure` exists to enforce, which the task rules classify as a Critical-tier impact (a signer signing a non-canonical or conflicting block).

### Likelihood Explanation
No majority of signers, no other signer's key, and no auth token are required — the condition depends entirely on the querying signer's own RPC round-trip to its own node timing out or erroring at the moment a proposal is checked, which is an ordinary operational condition (node under IO/CPU load from concurrent block-validation work, brief restart, or network blip) rather than a crafted flood. The severity is bounded to the individual signer's contribution (it does not by itself forge network consensus), which is why it is best framed as a per-signer safety-check bypass rather than a network-wide guarantee break.

### Recommendation
Do not treat an RPC error from `get_tenure_tip` as a pass. Instead:
- Return a distinguishable error/`Unknown` result from `check_latest_block_in_tenure` on RPC failure, and have callers treat "unknown" the same as "not yet verified" (i.e., hold/retry) rather than "confirmed."
- Only fall back to `Ok(true)` after bounded retries plus a policy decision (e.g., only assume-pass if the local signerdb's last known state independently corroborates no conflicting signed block exists), so a single transient RPC failure cannot silently authorize a signature.

### Proof of Concept
1. A miner proposes a tenure-change or ordinary block `B` whose `chain_length` does not actually exceed the true tenure tip already confirmed by the network for `tenure_id` (e.g., another block at or above that height was already globally accepted, but this signer has not yet recorded it locally via `signerdb`).
2. The signer's local `signerdb` has no matching signed block cached (e.g., freshly restarted signer, or the confirming block is only known to other signers/the node, not yet reflected in `get_tenure_last_block_info`), so the first stage of `check_latest_block_in_tenure` passes through.
3. At the pre-commit-threshold signing step, the signer calls `client.get_tenure_tip(tenure_id)` (`check_block_against_signer_db_state` → `check_latest_block_in_tenure`) and the node's HTTP call errors out (timeout because the node is busy validating a concurrent proposal, or a transient connection reset).
4. `check_latest_block_in_tenure` returns `Ok(true)` per [1](#0-0) , `check_block_against_signer_db_state` returns `None` (no rejection), and `handle_block_pre_commit` proceeds to `mark_locally_accepted` / broadcast the signer's signature over `B`, even though `B` does not confirm the tenure tip the network has already moved past.
