### Title
Queued dust deposit permanently blocks `stopEpochWithDuration` on the prefunded variant, freezing all pool funds - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The external bug is a two-phase flow where a condition valid at request time is re-checked at settlement and reverts, bricking the operation. The direct analog lives in the prefunded epoch-queue path: `requestDeposit` accepts any KYC-passing lender's deposit while the subscription window is open, but `IdleCDOEpochVariantPrefunded._afterStopEpochWithDuration` re-checks at `stopEpoch` time that no raw pending deposits remain via `IdleCDOEpochQueue.prefundedDepositsToProcess`. Once the prefunding cutoff has passed, `processDepositsToBorrower` can never run again, so a single un-forwarded dust request makes every subsequent `stopEpochWithDuration` revert permanently.

### Finding Description
In the prefunded flow:

1. `requestDeposit` accepts deposits while `block.timestamp + prefundedDepositWindow < epochEndDate`, gated only by `checkPrefunding` (guarded-launch limit, `defaulted`, `priceAA == 0`) — a dust amount such as 1 wei of underlying trivially passes.
2. `processDepositsToBorrower` (which converts `epochPendingDeposits` into `epochPrefundedDeposits`) is owner/manager-only and reverts unless the same cutoff check holds: `_checkNotAllowed(_prefundedWindow == 0 || block.timestamp + _prefundedWindow < _cdo.epochEndDate())`.
3. `deleteRequest` can only remove the caller's own `userDepositsEpochs` entry; no privileged path can clear another user's pending deposit.
4. At epoch end, `stopEpochWithDuration` reaches `_afterStopEpochWithDuration`, which unconditionally calls `prefundedDepositsToProcess`, which reverts whenever `epochPendingDeposits[_epoch] != 0`. The direct `stopEpoch` selector is separately blocked in `_beforeStopEpoch` when a queue is configured.

Attack path (running epoch, prefunded mode, AA queue enabled): a KYC-passing attacker calls `queue.requestDeposit(1)` just before the deposit window closes, too late (or deliberately timed) for the manager to forward it. After the cutoff, `processDepositsToBorrower` always reverts, the attacker never calls `deleteRequest`, and `stopEpochWithDuration` reverts on `prefundedDepositsToProcess` forever. This is already demonstrated by `testStopEpochWithDurationRevertsIfPrefundedQueueWasNotPrefunded`, which shows the stop reverting with `NotAllowed` whenever pending deposits exist — in the test the pending deposit is benign, but the code cannot distinguish it from a malicious dust deposit that arrived inside the window.

### Impact Explanation
Permanent freezing of the entire pool: while `isEpochRunning` stays true, withdraw-request processing (`processWithdrawRequests` runs only in buffer), deposit processing, and borrower repayment/recall are all blocked. All lender principal and accrued interest are locked behind a single wei of the attacker's queued deposit. The only escape is a privileged intervention such as unsetting `epochQueue` (if allowed mid-epoch — not verified here) or `emergencyShutdown`, i.e. the system degrades to rescue-mode behavior due to an unprivileged griefing action.

### Likelihood Explanation
Requires only a KYC-approved wallet and a dust deposit timed inside the prefunded window — no capital at risk since the deposit stays queued. The cost to the attacker is essentially zero while the freeze affects all pool funds. The condition `epochPendingDeposits[_epoch] != 0` is symmetric: any late-window deposit the manager fails to forward before the cutoff (even non-malicious, due to timing) produces the same deadlock, so it can also arise organically.

### Recommendation
Either let `stopEpochWithDuration` settle residual pending deposits (mint them into the epoch at the post-stop price, as `processPrefundedDeposits` already does for prefunded amounts), or auto-refund un-forwarded `epochPendingDeposits` during the stop flow instead of reverting. Alternatively, make `requestDeposit` for the next epoch close strictly before the last moment `processDepositsToBorrower` is still callable, or give the manager a forced-cancel path for stale pending deposits.

### Proof of Concept
A Foundry fork PoC on the prefunded variant, mirroring `test/foundry/IdleCDOEpochVariantPrefunded.t.sol` helpers:

```solidity
function testDustDepositBlocksStopEpoch() external {
    // setup: prefunded queue enabled, window set
    vm.prank(manager);
    cdoEpoch.setEpochQueue(address(queue));
    vm.prank(manager);
    queue.setPrefundedDepositWindow(PREFUNDED_DEPOSIT_WINDOW);

    // attacker (KYC'd) queues 1 wei right before the cutoff
    address attacker = makeAddr("attacker");
    deal(address(underlying), attacker, 1);
    _enterJustBeforeCutoff(PREFUNDED_DEPOSIT_WINDOW); // warp so deposit still allowed
    vm.startPrank(attacker);
    underlying.approve(address(queue), 1);
    queue.requestDeposit(1);
    vm.stopPrank();

    // cutoff passes; processDepositsToBorrower can no longer run
    _enterPrefundedWindow(PREFUNDED_DEPOSIT_WINDOW);
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    queue.processDepositsToBorrower();

    // epoch end: borrower repays, but every stopEpochWithDuration reverts
    uint256 interest = 1000e6;
    uint256 toRepay = interest + strategy.pendingWithdraws();
    deal(address(underlying), strategy.borrower(), toRepay);
    vm.prank(strategy.borrower());
    underlying.approve(address(cdoEpoch), toRepay);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector); // epochPendingDeposits != 0 in prefundedDepositsToProcess
    cdoEpoch.stopEpochWithDuration(0, interest, cdoEpoch.epochDuration(), 0);

    assertTrue(cdoEpoch.isEpochRunning()); // epoch permanently stuck
}
```

Caveat: this analysis is based on the indexed code; I could not verify whether `setEpochQueue` can be invoked mid-epoch to detach the queue as a privileged recovery path, which would downgrade the impact from permanent to temporary freezing.
