### Title
Stale instant-withdraw receipts escape default haircut and drain the recovery reserve at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug is a failure-path resource leak: state allocated during `dwc3_pci_probe()` is never released when a later step fails. The analog in `IdleCreditVault` is instant-withdraw receipt accounting: `requestInstantWithdraw` mints receipt tokens and records per-epoch basis in `instantWithdrawsRequestsByEpoch[_user][epochNumber]` / `instantWithdrawClaimsByEpoch[epochNumber]` (lines 371-374), but on a borrower default only the *current* epoch's instant bucket is haircut via `defaultPendingClaimBasis`/`_claimDefaultedInstantWithdrawRequest`, which both key strictly on `epochNumber` / `defaultRecoveryEpoch`. Instant receipts opened in an earlier epoch that were never collected survive as stale, unreleased claims and are later paid **at par** through `claimInstantWithdrawRequest` → `_transferFundedClaim`, directly out of the post-default strategy balance that is supposed to back haircutted recovery claims.

### Finding Description
- `requestInstantWithdraw` burns CDO strategy tokens and mints the user a receipt, incrementing `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, and `pendingInstantWithdraws` (lines 356-375).
- Funding arrives via `collectInstantWithdrawFunds`, which only decreases `pendingInstantWithdraws`; the per-epoch claim basis is never cleared on the funded path (lines 398-403).
- On `stopEpoch` failure, `_handleBorrowerDefault` runs and `finalizeDefaultRecovery` computes `totalBasis = activeBasis + defaultPendingClaimBasis()`. `defaultPendingClaimBasis` adds **only** `instantWithdrawClaimsByEpoch[epochNumber]` — the default epoch's bucket (lines 644-649). Receipts recorded under an earlier epoch are absent from the recovery basis.
- After `defaultRecoveryFinalized`, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest(_user)`, which only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (lines 842-856). It then reads `amount = instantWithdrawsRequests[_user]`, which still contains the stale earlier-epoch receipt, burns it, and pays it in full via `_transferFundedClaim` (lines 380-393).
- The paying source after default is the same strategy-held underlying that forms `defaultRecoveryReserve` (set in `finalizeDefaultRecovery`, lines 686-692 and `_transferDefaultRecovery`), so stale receipts are paid 1:1 from funds priced for `defaultRecoveryPrice < RECOVERY_FULL` claimants.

The broken invariant is the loss-waterfall/donation-isolation invariant: every claim on post-default strategy assets is supposed to be scaled by `defaultRecoveryPrice`, but stale instant receipts bypass it — the "leaked" accounting that was never released on the partial-funding/epoch-boundary path.

### Impact Explanation
An unprivileged tranche holder who made an instant-withdraw request in epoch N that was never collected (pendingInstantWithdraws > 0 carried across the boundary) receives a 100% payout after a default in epoch M > N, while all default-epoch claimants and active tranche holders are paid `defaultRecoveryPrice` (e.g. 60%). The overpayment comes out of `defaultRecoveryReserve`/strategy cash, directly reducing what legitimate claimants and active AA/BB holders can recover. With a reserve of R and a stale claim C, up to `C * (1 - defaultRecoveryPrice)` is effectively stolen relative to the intended haircut — quantified theft of recovery funds, not merely a DoS.

### Likelihood Explanation
The preconditions are reachable by an unprivileged lender:
1. Attacker calls `requestInstantWithdraw` during epoch N (allowed whenever `allowInstantWithdraw` is set at epoch start).
2. Epoch N ends with the instant queue only partially funded (borrower repays interest but not the full instant queue; `pendingInstantWithdraws` remains non-zero through `collectInstantWithdrawFunds`/stop). No privileged misbehavior is required — the borrower simply underfunds, which is precisely the scenario the default-recovery machinery is built for.
3. In a later epoch M the borrower truly defaults; `finalizeDefaultRecovery` runs with `totalBasis` excluding the stale epoch-N bucket.
4. Attacker calls `claimInstantWithdrawRequest` and receives the full stale amount at par from the reserve.

No existing guard stops it: `_claimDefaultedInstantWithdrawRequest` is keyed only on `defaultRecoveryEpoch`, `instantWithdrawsRequests[_user]` is an aggregate that retains the stale basis, and `claimInstantWithdrawRequest` performs no `defaultRecoveryFinalized` haircut on the fall-through amount. The main uncertainty I could not fully resolve is whether every non-default `stopEpoch` path guarantees `pendingInstantWithdraws` reaches zero (via `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`); if stopEpoch reverts whenever the instant queue is underfunded, the stale-epoch precondition narrows but the default-epoch partial-funding path described in `_defaultPrefundedInstantReserve` (lines 712-722) shows the unfunded-remainder state is reachable by design.

### Recommendation
- In `finalizeDefaultRecovery`, include **all** outstanding instant receipts in `defaultPendingClaimBasis` (e.g. `instantWithdrawsRequests` aggregate or tracked unfunded basis), not only `instantWithdrawClaimsByEpoch[epochNumber]`; alternatively, make `defaultInstantWithdrawsFinalized` cover every epoch's bucket.
- In `claimInstantWithdrawRequest`, once `defaultRecoveryFinalized`, apply `defaultRecoveryPrice` and `_transferDefaultRecovery` to any residual `instantWithdrawsRequests[_user]` not attributable to `defaultRecoveryEpoch`, instead of paying it at par via `_transferFundedClaim`.
- Alternatively, force `stopEpoch` to revert unless `pendingInstantWithdraws == 0`, so stale instant claims can never cross an epoch boundary unfunded.

### Proof of Concept
Foundry fork PoC outline (against the credit-vault fixture used in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleInstantReceiptDrainsRecoveryReserve() external {
    // Epoch N: attacker deposits AA and requests instant withdraw
    uint256 amount = 10_000 * ONE_SCALE;
    deal(address(underlying), attacker, amount);
    vm.startPrank(attacker);
    underlying.approve(address(idleCDO), amount);
    idleCDO.depositAA(amount);
    vm.stopPrank();

    _startEpoch();                       // allowInstantWithdraw set
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(5_000 * ONE_SCALE, address(AAtranche));
    // strategy now: pendingInstantWithdraws = 5_000, claimsByEpoch[N] = 5_000

    // Epoch N stops WITHOUT fully funding the instant queue (borrower underfunds),
    // epochNumber -> N+1, pendingInstantWithdraws remains > 0
    _stopEpochPartialInstantFunding();

    // Epoch M: borrower defaults; finalizeDefaultRecovery runs
    _stopEpochWithDefaultAndFinalize(0, recoveryAvailable);

    // Attacker's epoch-N receipt was excluded from defaultPendingClaimBasis
    // (only instantWithdrawClaimsByEpoch[M] was counted), so it pays out at par:
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;

    uint256 fair = 5_000 * ONE_SCALE * strategy.defaultRecoveryPrice() / 1e18;
    assertGt(got, fair);              // paid ~1:1 instead of haircut
    // honest claimant now underfunded: reserve drained by got - fair
}
```

The assertion `got > basis * defaultRecoveryPrice / RECOVERY_FULL` demonstrates theft of unclaimed recovery yield from the reserve.
