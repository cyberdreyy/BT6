### Title
Unauthenticated `/v2/resume/:runID` endpoint allows repeated, unrestricted overwrite of a pending async task result before it is consumed - (File: core/web/pipeline_runs_controller.go)

### Summary
The Switchboard report describes a commit-reveal randomness flow where the `RandomnessCommit` instruction can be called by anyone, repeatedly, between a legitimate commit and its reveal — letting an attacker disrupt or manipulate the value a genuine user ultimately consumes. The Chainlink node has a structurally analogous flow: an async pipeline task (e.g. a `bridge` task) suspends the job run and waits for an external party to `PATCH` its result back to the node via `/v2/resume/:runID`. This endpoint is completely unauthenticated and the underlying `UpdateTaskRunResult` query does not enforce single-use semantics, so the "commit" (writing the task result) can be repeated and can race the legitimate reveal.

### Finding Description
The resume endpoint is registered outside any authentication middleware: [1](#0-0) 

`Resume` parses only a `taskID` UUID from the URL and a JSON body, then calls `App.ResumeJobV2` with no authentication, no external-initiator check, and no session/token check: [2](#0-1) 

That flows into `runner.ResumeRun`, which calls the ORM's `UpdateTaskRunResult`: [3](#0-2) 

Crucially, the ORM update is not idempotent/single-use — it matches on `pipeline_task_runs.id` and only requires the owning pipeline run to be in `running` or `suspended` state; it does not check whether the specific task row was already finished (`finished_at`, `output`, `error` already populated) before overwriting them: [4](#0-3) 

Because the run stays in `running` state for the duration of downstream task execution after the first resume call, a second (or Nth) call with the *same* `taskID` but a *different* body can still match the `WHERE ... state in ('running','suspended')` predicate and silently overwrite the previously stored `output`/`error` for that task before the pipeline has consumed/finalized it — mirroring the report's "may be called multiple times" and "generate a favorable value before finalizing" bug classes. This is the same class of bug as `RandomnessCommit`: a state-mutating, unauthenticated callback that can be invoked repeatedly with attacker-controlled data before the "reveal"/consumption step locks it in.

### Impact Explanation
If an attacker learns or intercepts a pending task's UUID (e.g., via network capture of the bridge's outbound `responseURL`, a misconfigured/compromised external adapter, logs, or a race against a slow legitimate responder), they can:
- Overwrite a job run's task output/error with attacker-chosen data before the legitimate external adapter's response arrives or is processed, directly corrupting job pipeline results (e.g., price data, on-chain transaction payloads) — a direct analog to injecting a "favorable random value" before settle.
- Repeatedly hit the endpoint to disrupt a genuine external adapter's callback (denial/griefing of the intended flow), analogous to disrupting the genuine user's commit before their reveal.

This can propagate to `ethtx`/downstream tasks that consume the manipulated value, resulting in incorrect on-chain submissions.

### Likelihood Explanation
Requires knowledge of a task's UUID, which is not exposed to arbitrary internet clients by default, so exploitation likelihood depends on how the UUID could leak (compromised/malicious bridge endpoint, logging, network interception of the outbound bridge request containing the `responseURL`). However, the endpoint enforces no authentication at all and no single-write guarantee once a UUID is known — this is a design gap identical in kind to the reported bug (unrestricted repeat calls to a stateful commit-like instruction).

### Recommendation
- Enforce single-use / idempotent semantics on `UpdateTaskRunResult`: only allow the update when the target task row's `finished_at`/`output`/`error` are still unset (`WHERE ... AND finished_at IS NULL`), rejecting subsequent resume calls for an already-resolved task — mirroring the audit's fix of restricting repeated `RandomnessCommit` calls once committed and not yet revealed.
- Consider binding the resume callback to a per-task secret/nonce (in addition to the UUID) so knowledge of the task ID alone is insufficient to resume/overwrite it.

### Proof of Concept
1. A `bridge async=true` task suspends a pipeline run and sends the external adapter a `responseURL` of `http://node/v2/resume/<taskID>` (see test showing this format): [5](#0-4) 
2. An attacker who obtains `<taskID>` sends `PATCH /v2/resume/<taskID>` with a crafted body before (or instead of) the legitimate adapter — no credentials required since the route sits in `unauthedv2`: [1](#0-0) 
3. `UpdateTaskRunResult` accepts the write as long as the run is `running`/`suspended`, regardless of whether the task was already resolved, letting the attacker's value be stored and consumed by the pipeline: [6](#0-5)

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}

		Error: err,
	})

		// start the runner again

			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}

func (o *orm) UpdateTaskRunResult(ctx context.Context, taskID uuid.UUID, result Result) (run Run, start bool, err error) {
	if result.OutputDB().Valid && result.ErrorDB().Valid {
		panic("run result must specify either output or error, not both")
	}
	err = o.transact(ctx, func(tx *orm) error {
		sql := `
		SELECT pipeline_runs.*, pipeline_specs.dot_dag_source "pipeline_spec.dot_dag_source", job_pipeline_specs.job_id "job_id"
		FROM pipeline_runs
		JOIN pipeline_task_runs ON (pipeline_task_runs.pipeline_run_id = pipeline_runs.id)
		JOIN pipeline_specs ON (pipeline_specs.id = pipeline_runs.pipeline_spec_id)
		JOIN job_pipeline_specs ON (job_pipeline_specs.pipeline_spec_id = pipeline_specs.id)
		WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')
		FOR UPDATE`
		if err = tx.ds.GetContext(ctx, &run, sql, taskID); err != nil {
			return fmt.Errorf("failed to find pipeline run for task ID %s: %w", taskID.String(), err)
		}

		// Update the task with result
		sql = `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1`
		if _, err = tx.ds.ExecContext(ctx, sql, taskID, result.OutputDB(), result.ErrorDB(), time.Now()); err != nil {
			return fmt.Errorf("failed to update pipeline task run: %w", err)
		}

		if run.State == RunStatusSuspended {
			start = true
			run.State = RunStatusRunning

			sql = `UPDATE pipeline_runs SET state = $2 WHERE id = $1`
			if _, err = tx.ds.ExecContext(ctx, sql, run.ID, run.State); err != nil {
				return fmt.Errorf("failed to update pipeline run state: %w", err)
			}
		}

		return loadAssociations(ctx, tx.ds, []*Run{&run})
	})

	return run, start, err
}
