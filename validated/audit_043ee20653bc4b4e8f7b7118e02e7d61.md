### Title
`getLargestAccounts` cache in `LargestAccountsCache` is keyed only by filter, not by commitment/slot, allowing processed-derived data to be served to finalized clients - (File: `rpc/src/rpc_cache.rs`, `rpc/src/rpc.rs`)

### Summary
The `LargestAccountsCache` used by `get_largest_accounts` in `rpc/src/rpc.rs` is a single shared cache keyed only by `Option<RpcLargestAccountsFilter>`, with no dimension for the requested `CommitmentConfig` or the slot's rooted status. A call with `commitment=processed` that populates the cache from an unrooted bank can cause a subsequent `commitment=finalized` call (with the same filter) to receive the cached, potentially unrooted data for up to the full 2-hour cache TTL.

`get_cached_largest_accounts`/`set_cached_largest_accounts` delegate to `LargestAccountsCache`, whose internal `HashMap` key is `Option<RpcLargestAccountsFilter>` only: [2](#0-1) 

There is no `commitment` or bank slot in the key, and `set_largest_accounts` stores whatever slot the populating call happened to use: [3](#0-2) 

The cache TTL is 2 hours: [4](#0-3) 

Exploit flow (single unprivileged client, two sequential JSON-RPC calls, well within the one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` limit):
1. Call `getLargestAccounts({commitment: "processed", filter: X})`. `self.bank(processed)` resolves to the latest (possibly unrooted/soon-to-be-dropped) bank; cache miss populates `LargestAccountsCache` under key `X` with `(slot_unrooted, accounts_from_unrooted_bank)`.
2. Immediately call `getLargestAccounts({commitment: "finalized", filter: X})`. `self.bank(finalized)` correctly resolves to the rooted bank, but `get_cached_largest_accounts(&X)` returns the still-fresh cache entry from step 1 without checking that it was computed from a rooted/finalized-compatible slot. The response's `context.slot` (from `RpcResponseContext::new(slot)`) and the account balances both reflect the unrooted processed-bank snapshot, not the finalized bank that was actually fetched and discarded.

This violates the invariant that a `finalized` response must only reflect rooted-bank data: the returned `slot` and lamport balances can belong to a bank that never became a root (e.g., in the case of a fork that later got pruned), so a finalized-commitment client is silently given data equivalent to a processed/unconfirmed view for up to 2 hours.

### Impact Explanation
This is a wrong-slot/fork data correctness bug reachable via two ordinary RPC calls from a single unprivileged client. It corresponds to the "incorrect data returned by validator" bounty category — a finalized-commitment API silently returns a response tagged with (and derived from) a bank/slot that does not satisfy the finalized commitment guarantee, which can mislead any downstream client/exchange logic relying on `getLargestAccounts(commitment=finalized)` for balance verification.

### Likelihood Explanation
Highly feasible and fully reproducible: it requires no special privileges, no timing race beyond issuing two ordinary RPC calls back-to-back (both within the allowed rate), and works whenever the processed bank at call time can diverge from the currently rooted/finalized bank (a routine, frequent situation during normal cluster operation with forks). The 2-hour cache duration makes the window for a stale/cross-commitment answer very wide.

### Recommendation
Include the resolved commitment (or bank slot together with a rootedness check) as part of the `LargestAccountsCache` key, e.g. key by `(Option<RpcLargestAccountsFilter>, CommitmentConfig)`, or at minimum invalidate/bypass the cache entry when the requested commitment differs from the commitment level used to populate it, and validate that a cached entry's slot is still consistent with (rooted for) the currently requested commitment before returning it.

#[derive(Debug, Clone)]
pub struct LargestAccountsCache {
    duration: u64,
    cache: HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>,
}

#[derive(Debug, Clone)]
struct LargestAccountsCacheValue {
    accounts: Vec<RpcAccountBalance>,
    slot: u64,
    cached_time: SystemTime,
}

impl LargestAccountsCache {
    pub(crate) fn new(duration: u64) -> Self {
        Self {
            duration,
            cache: HashMap::new(),
        }
    }

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }
