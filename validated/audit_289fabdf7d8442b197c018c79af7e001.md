### Title
Stale instant-withdraw receipt basis inflates default recovery price and lets an attacker drain the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch receipt basis `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements the per-epoch total `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults in the same epoch after a funded instant receipt was claimed, `finalizeDefaultRecovery` counts the already-paid-out receipt again: as claim basis (`defaultPendingClaimBasis`) and as phantom "prefunded" reserve (`_defaultPrefundedInstantReserve`). The resulting `defaultRecoveryPrice` is inflated, so an attacker claiming early extracts more underlying than the real reserve supports, leaving later default-recovery claimants permanently underpaid or unable to claim.

### Finding Description
The use-after-free analog: an instant-withdraw receipt is "freed" (paid out at par) but its epoch-scoped storage records are never destroyed, so the default-recovery path later reuses the dead receipt as if funds were still held for it.

Normal claim path, `IdleCreditVault.sol:380-393`:
```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```
Neither `instantWithdrawsRequestsByEpoch[_user][epochNumber]` nor `instantWithdrawClaimsByEpoch[epochNumber]` is touched.

At default finalization (`finalizeDefaultRecovery`, lines 685-696, `defaultPendingClaimBasis` lines 644-649, `_defaultPrefundedInstantReserve` lines 716-723):
- `pendingBasis` includes `instantWithdrawClaimsByEpoch[epochNumber]` — which still contains the claimed amount `X`.
- `prefundedReserve = instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` treats `X` as underlying already held by the strategy, but those tokens were transferred to the claimant in step 3. `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + ...` therefore overstates the real balance by `X`.
- `recoveryPrice = reserveAmount * 1e18 / totalBasis` is computed with a numerator inflated by phantom funds, so every claimant's payout `claimBasis * recoveryPrice / 1e18` is too large relative to actual held tokens. The first claimants are paid from the real balance until `defaultRecoveryReserve` is exhausted; subsequent claims revert in `_transferDefaultRecovery` (`defaultRecoveryReserve -= _amount` underflow) or pay dust.

The attacker's own re-claim of the stale per-epoch entry reverts (`instantWithdrawsRequests[_user] -= claimBasis` underflows at line 848), so profit comes from the inflated price on a second receipt the attacker still holds, claimed before honest users.

### Impact Explanation
Broken invariant: one receipt one payout + reserve solvency. An unprivileged lender (KYC'd, holding tranche tokens) with two accounts, or one account making two instant requests, can inflate `defaultRecoveryPrice`. The attacker claims their still-open defaulted receipt at the inflated price and extracts underlying that belongs to other defaulted-epoch claimants (normal withdraw requesters, other instant requesters) and indirectly distorts the active-LP haircut (`activeFinalNAV = activeBasis * recoveryPrice` mints/burns CDO strategy tokens at the wrong ratio). Quantified loss: up to `X * recoveryPrice` of real reserve tokens stolen, and permanent freezing of other users' recovery claims once the reserve underflows. Requires a borrower default — but the borrower defaulting is a protocol condition, not the attacker being the borrower; sequencing around honest manager calls (`getInstantWithdrawFunds`) is sufficient.

### Likelihood Explanation
- Preconditions: instant-withdraw mode enabled (non-programmable borrower), one funded+claimed instant receipt and one unfunded instant receipt in the same epoch, then a borrower default in that epoch. All are ordinary protocol flows.
- Attacker cost: one instant request claimed at par, one left pending at default; no privileged role needed.
- No existing guard stops it: `_ensureDefaultRecoveryInitialized` only checks `pendingInstantWithdraws != 0` at init; nothing validates that `instantWithdrawClaimsByEpoch` reflects unclaimed receipts only.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch accounting the same way `_clearWithdrawClaimForEpoch` does for normal requests: iterate/record the request epoch (e.g., store `lastInstantWithdrawRequestEpoch` or track per-epoch entries), set `instantWithdrawsRequestsByEpoch[_user][epoch] = 0` and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount. Alternatively, reconcile at finalization by subtracting already-claimed basis from `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` and from `_defaultPrefundedInstantReserve`.

### Proof of Concept
Foundry fork sketch (against an `IdleCDOEpochVariant` + `IdleCreditVault` deployment with instant withdraws enabled):

```solidity
// Epoch N running; attacker controls userA and userB (two KYC'd wallets).
// 1) userA deposits AA, requests instant withdraw of X via IdleCDO.requestInstantWithdraw.
//    -> instantWithdrawsRequestsByEpoch[A][N] = X; instantWithdrawClaimsByEpoch[N] = X;
//       pendingInstantWithdraws = X
// 2) warp past instantWithdrawDeadline; manager (honest) calls getInstantWithdrawFunds().
//    Borrower pays X -> pendingInstantWithdraws = 0; strategy holds X.
// 3) userA calls claimInstantWithdrawRequest -> receives X.
//    BUG: instantWithdrawsRequestsByEpoch[A][N] == X and instantWithdrawClaimsByEpoch[N] == X remain.
// 4) userB (attacker) deposits and requests instant withdraw of Y in same epoch N.
//    -> instantWithdrawClaimsByEpoch[N] = X + Y; pendingInstantWithdraws = Y.
// 5) manager calls getInstantWithdrawFunds(); borrower does not pay -> catch -> _handleBorrowerDefault(Y).
// 6) owner/guardian finalizes: strategy.finalizeDefaultRecovery(recovered, source).
//    defaultPendingClaimBasis() includes X + Y (should be Y);
//    _defaultPrefundedInstantReserve() = (X + Y) - Y = X phantom tokens;
//    defaultRecoveryPrice uses reserveAmount inflated by X.
// 7) userB claims via claimInstantWithdrawRequest:
//    _claimDefaultedInstantWithdrawRequest(B) pays Y * inflatedPrice.
//    Assert: userB received > fair share; an honest defaulted withdraw requester's
//    subsequent claim reverts or pays less because defaultRecoveryReserve is drained.
assertGt(token.balanceOf(userB), Y * fairPrice / 1e18);
vm.expectRevert(); // honest claimant's recovery claim
cdo.claimWithdrawRequest(honestUser);
```

Key assertions: after step 3, `vault.instantWithdrawsRequestsByEpoch(A, N) == X` and `vault.instantWithdrawClaimsByEpoch(N) == X` even though `vault.instantWithdrawsRequests(A) == 0` and A's tokens were paid out — the "freed" receipt is reused by recovery accounting.
