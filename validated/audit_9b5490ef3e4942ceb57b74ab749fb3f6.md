### Title
Zip-slip path traversal in legacy zip extractor allows cache archive entries to be written outside the job workspace - ([File: helpers/archives/zip_extract.go])

### Summary
`helpers/archives/zip_extract.go`'s `extractZipFile`/`ExtractZipArchive` writes each zip entry using `file.Name` verbatim (`os.Mkdir(file.Name, ...)`, `os.OpenFile(file.Name, ...)`, `os.Symlink(...)`) with no path-cleaning, no chroot/prefix check, and no rejection of entries containing `../`. This is unlike the sibling `tarzstd` extractor (`commands/helpers/archive/tarzstd/tarzstd_extractor.go:57-64`), which explicitly resolves each entry against the target directory and rejects paths that escape it ("cannot be extracted outside of chroot"). The `ziplegacy` extractor (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`) discards its `dir` parameter entirely and delegates straight to `archives.ExtractZipArchive(zr)`, so extraction happens relative to the process's current working directory with no containment check at all.

### Finding Description
`cache-extractor` (`commands/helpers/cache_extractor.go:618-664`) downloads a cache archive via a legitimately project-scoped, credentialed URL obtained through `cache.GetAdapter`/`shells/abstract.go` (`addExtractCacheCommand` → `getCacheDownloadURLAndEnv` → `cache.GetAdapter`), then calls `archive.NewExtractor(format, f, size, wd)` and `extractor.Extract(ctx)`. The reachable Go path for the `zip` format when the `ziplegacy` extractor is selected is:

`CacheExtractorCommand.Execute` → `archive.NewExtractor(Zip, ...)` → `ziplegacy.extractor.Extract` (discards `e.dir`) → `archives.ExtractZipArchive` → `extractZipFile` → `os.OpenFile(file.Name, ...)` / `os.Mkdir(file.Name, ...)` / `os.Symlink(data, file.Name)`.

Because `file.Name` comes straight from the attacker-controlled zip's central directory entries and is never validated against the intended cache/job root, a project member who uploads a cache (an unprivileged, legitimately-scoped action — cache upload for their own project) can craft entry names like `../../../etc/whatever` or `../../workspace-sibling/x`. On download+extraction — performed within the *same* project by that legitimate credentialed request — the file is written wherever the traversal resolves relative to the extractor's current working directory, not confined to `wd`/job root. `errorIfGitDirectory` in `helpers/archives/path_check_helper.go` only blocks `.git` paths, not `../` traversal, and provides no containment guarantee. The credentials-adapter/`cache.GetAdapter` project-scoping logic (`cache/cache.go`) is correct and irrelevant to this bug — it only prevents fetching the *wrong project's* object; it says nothing about where the fetched object's *contents* land on disk.

Whether this legacy path is reachable in current production builds depends on which zip extractor implementation (`fastzip` vs `ziplegacy`) is registered as the default for the `Zip` format at runtime; that registration/init wiring was not found within the indexed context (no `archive.Register` call site for production defaults was located, only test helpers `commands/helpers/helpers_archiver_test.go` that register both `fastzip` and `ziplegacy` for testing). `fastzip` (`github.com/saracen/fastzip`) is a well-maintained third-party library that performs its own path-traversal (zip-slip) validation internally, so if `fastzip.NewExtractor` is the sole production path, the missing check in `helpers/archives/zip_extract.go` may be dead/legacy code, exposed only via `ExtractZipFile` (used by other commands, e.g. artifact extraction) or via feature-flag/fallback selection. This is the key uncertainty for exploitability in the shipped binary.

### Impact Explanation
If `helpers/archives/zip_extract.go` (via `ziplegacy.NewExtractor` or any other caller of `archives.ExtractZipArchive`/`ExtractZipFile`) is reachable for cache or artifact extraction in a real job, a project member can overwrite arbitrary files reachable from the extraction process's working directory/permissions (host or container filesystem, depending on executor), using only their own project's cache — no credential/adapter bypass needed. This matches the scoped impact: "host/workspace file overwrite from a legitimately-owned but maliciously crafted cache archive," confined to whatever the runner process user can write (shell executor: potentially host files; container/kubernetes executors: files inside the helper/build container's writable paths).

### Likelihood Explanation
Preconditions are minimal and entirely within an unprivileged pipeline author's control: create a zip with a crafted entry name containing `../` segments (trivial with Go's `archive/zip` package, since it does not sanitize `Name`), upload it as that project's cache via a normal `cache: paths:` job, then run a second job in the same project that restores the cache. The only open question is whether the vulnerable `ziplegacy`/`archives.ExtractZipArchive` code path is actually selected for zip cache archives in the shipped default configuration, or is legacy/fallback-only code superseded by `fastzip`'s safer implementation. This could not be conclusively confirmed from the indexed context (no production `archive.Register(archive.Zip, ...)` call site was found, only test-only registrations), so likelihood is rated with that specific caveat.

### Recommendation
Add the same containment check used in `tarzstd_extractor.go` to `helpers/archives/zip_extract.go`: resolve each `file.Name` against the target extraction directory with `filepath.Join(dir, file.Name)`, take `filepath.Abs`, and reject (or skip with a loud warning) any entry whose resolved path does not have `dir+string(filepath.Separator)` as prefix (and isn't equal to `dir`). Ensure `ziplegacy.extractor.Extract` actually passes and uses `e.dir` instead of discarding it. Apply the same fix to `extractZipSymlinkEntry`'s target path and to `ExtractZipFile`'s callers. Add a unit test analogous to `tarzstd`'s chroot test asserting that a zip entry named `../evil` returns an error and is not written to disk. Additionally, verify and document which extractor is the actual production default for the `Zip` format so the fix (or its absence) can be assessed for real-world exploitability.

### Proof of Concept
Go unit test in `helpers/archives/zip_extract_test.go`:
```go
func TestExtractZipArchive_RejectsPathTraversal(t *testing.T) {
    dir := t.TempDir()
    cwd, _ := os.Getwd()
    require.NoError(t, os.Chdir(dir))
    defer os.Chdir(cwd)

    buf := new(bytes.Buffer)
    zw := zip.NewWriter(buf)
    f, _ := zw.Create("../evil.txt")
    f.Write([]byte("pwned"))
    require.NoError(t, zw.Close())

    zr, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)

    err = ExtractZipArchive(zr)
    // Expected (after fix): err != nil, and the file must NOT exist outside dir.
    _, statErr := os.Stat(filepath.Join(dir, "..", "evil.txt"))
    assert.True(t, os.IsNotExist(statErr), "traversal entry must not be written outside target dir")
}
```
Integration-level PoC job plan: project A uploads a cache with a zip entry `../../../tmp/pwned_by_projectA` via a job step producing that archive as its cache, then a subsequent job in project A restores the cache (`cache-extractor` invoked with a correctly project-A-scoped URL from `cache.GetAdapter`); assert that no file appears at `/tmp/pwned_by_projectA` and that extraction is confined to the job's cache/build directory, regardless of the (correct) per-project credentials/URL scoping.
