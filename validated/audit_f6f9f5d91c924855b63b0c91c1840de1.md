### Title
Builder pending withdrawal commits the full requested amount to the execution payload while only debiting `min(amount, balance)` from the builder's CL balance, minting Gwei — (`specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` builds the `Withdrawal` object that becomes part of `state.payload_expected_withdrawals` — the exact list the execution layer is contractually required to pay out — using the **raw requested** `withdrawal.amount` from `state.builder_pending_withdrawals`, without capping it to the builder's actual balance. [1](#0-0) 

`apply_withdrawals`, however, deducts only `min(withdrawal.amount, builder_balance)` from the builder's actual balance: [2](#0-1) 

The committed amount (paid by the EL to `fee_recipient`) and the amount actually deducted from CL state diverge whenever a builder's balance is insufficient to cover its own queued withdrawal request.

### Finding Description
This is directly analogous to the Tapioca bug: a function's return/output value representing the "requested" amount is used downstream as if it were the *actual* transferable amount, without reconciling it against what could actually be deducted from the underlying balance (the `mtOFT.wrap()` return value vs. the raw input amount).

In `get_builder_withdrawals`, each queued `BuilderPendingWithdrawal.amount` is copied verbatim into the `Withdrawal.amount` field that ends up in `state.payload_expected_withdrawals` (via `get_expected_withdrawals` → `process_withdrawals`). Per the note in `process_withdrawals`, this withdrawals list is the exact set of withdrawals "any execution payload that has the corresponding block as parent beacon block is required to honor" — i.e., the execution layer mints/pays this exact `amount` to `withdrawal.address` unconditionally. [3](#0-2) 

But when the CL applies the very same withdrawal to consensus state via `apply_withdrawals`, the deduction from `state.builders[builder_index].balance` is capped: `balance -= min(withdrawal.amount, builder_balance)`. If `builder_balance < withdrawal.amount`, the builder's balance simply saturates to `0`, while the committed `Withdrawal.amount` sent to the EL is still the full, uncapped requested amount. [4](#0-3) 

This is confirmed by the repository's own spec test, which explicitly documents the mismatch as expected behavior:
- Builder balance = 1 ETH, pending-withdrawal request = 5 ETH.
- Output: `withdrawal.amount` in the payload = 5 ETH (full requested amount), but `builders[0].balance` only decreases by 1 ETH (capped). [5](#0-4) 

The difference of 4 ETH is Gwei that the execution layer pays to `fee_recipient` without any corresponding debit anywhere in consensus state — it is minted out of thin air and paid to a party (the withdrawal's `fee_recipient`, which is attacker-controlled address data on the `BuilderPendingWithdrawal`) that did not have that balance backing it.

### Impact Explanation
This breaks the core Gwei-conservation equality: a payment can be executed by the execution layer that the consensus-layer block did not actually debit anywhere in state. Concretely, Gwei is created and paid to a non-owner (the withdrawal's `fee_recipient`) beyond what the builder's own account ever held, i.e. inflation of total issued/paid ETH not backed by any deposited/staked balance. This matches the "Critical" bucket ("Gwei created, destroyed or paid to a non-owner").

### Likelihood Explanation
Any builder can trigger this by first depositing/registering with a small balance, later voluntarily queuing a `BuilderPendingWithdrawal` (or having balance reduced by e.g. fee/slashing-equivalent debits between queuing and processing, if such mechanisms interact) for an amount larger than its remaining balance, and letting the block proposer include the pending-withdrawal-processing block. No coalition, no malicious peer, and no execution-layer bug is needed — it is a pure spec-following consensus-state defect, exercised purely by a single builder's own (unprivileged) input (`BuilderPendingWithdrawal.amount`).

### Recommendation
`get_builder_withdrawals` should cap the committed `Withdrawal.amount` to `min(withdrawal.amount, state.builders[builder_index].balance)` at the time the withdrawal is built (mirroring what `get_pending_partial_withdrawals` already does for validators via `min(balance - MIN_ACTIVATION_BALANCE, withdrawal.amount)`), so the amount promised to the execution layer always matches the amount actually deductible from consensus state.

### Proof of Concept
1. Register builder `B` with balance `1 ETH`.
2. Queue `state.builder_pending_withdrawals` with `BuilderPendingWithdrawal(builder_index=B, amount=5 ETH, fee_recipient=attacker_address)`.
3. Call `process_withdrawals(state)`.
4. `get_builder_withdrawals` emits `Withdrawal(validator_index=convert(B), address=attacker_address, amount=5 ETH)` into `state.payload_expected_withdrawals`.
5. `apply_withdrawals` sets `state.builders[B].balance = 0` (deducting only 1 ETH).
6. The execution layer processes the block's withdrawals list and pays `attacker_address` the full `5 ETH`, of which `4 ETH` was never backed by any consensus-layer balance — Gwei minted and paid to a non-owner, exactly as demonstrated by `test_builder_withdrawal_insufficient_balance`. [6](#0-5)

```markdown
##### Modified `process_withdrawals`

*Note*: This is modified to only take the `state` as parameter. Withdrawals are
deterministic given the beacon state, any execution payload that has the
corresponding block as parent beacon block is required to honor these
withdrawals in the execution layer. `process_withdrawals` must be called after
`process_parent_execution_payload` (which updates `state.latest_block_hash`) and
before `process_execution_payload_bid` as the latter function affects validator
balances.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.

```

```python
    Test builder withdrawal with insufficient balance.

    Input State Configured:
        - state.builders[0]: Builder exists with only 1 ETH balance
        - builder_pending_withdrawals: Contains 1 entry requesting 5 ETH
        - builders[0].balance: 1 ETH (insufficient for requested 5 ETH)

    Output State Verified:
        - payload_expected_withdrawals: Contains 1 withdrawal
        - withdrawal.amount: 5 ETH (requested amount)
        - builders[0].balance: 0 (deduction capped to available balance)
        - builder_pending_withdrawals: Reduced by 1 (processed even if capped)
```
