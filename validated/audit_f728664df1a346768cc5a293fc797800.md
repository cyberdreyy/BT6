### Title
APR0 pending withdraw principal permanently reverts `stopEpoch` after any APR change, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed()` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged KYC-passed lender can plant a nonzero `apr0TotalPrincipal` simply by calling `requestWithdraw` while the vault is in an APR=0 epoch. If the honest manager later raises the APR (a routine, legitimate action) before the next `stopEpoch`, every subsequent `stopEpoch` call reverts in the strategy hook, so the epoch can never close and all borrower-held and vault-held funds are frozen.

### Finding Description
`requestWithdraw` routes requests made while `unscaledApr == 0` into `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` (IdleCreditVault.sol:285-286, 567-577). That global bucket is only ever cleared inside `prepareStopEpochWithApr0` (line 540) or via the default-claim path in `_clearWithdrawClaimForEpoch` (line 827). Per-user settlement in `_settleApr0` (lines 545-565) never decrements `apr0TotalPrincipal`, so users cannot clear the bucket by claiming.

Inside `prepareStopEpochWithApr0`, the guard at lines 505-508 makes any stop with `unscaledApr != 0` revert while the bucket is nonzero:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

Since `prepareStopEpochWithApr0` is `_onlyIdleCDO` and is invoked by `IdleCDOEpochVariant` during `stopEpoch`, the revert propagates and bricks the epoch state machine. The attacker only needs to call `cdoEpoch.requestWithdraw(0, tranche)` with any positive tranche balance during an APR=0 window — no privileged role required. The broken invariant is liveness of the epoch state machine: an unprivileged user can make the honest manager's next `stopEpoch` unconditionally revert.

### Impact Explanation
Temporary freezing of the entire pool TVL: borrower repayments cannot be booked, no withdraw claims or deposit claims can be processed, and queued withdrawals in `IdleCDOEpochQueue.processWithdrawRequests` stall, because all of them depend on `stopEpoch` completing. The freeze persists until the manager either (a) sets `unscaledApr` back to 0 and completes one `stopEpoch` to flush `apr0TotalPrincipal`, or (b) the vault enters default finalization. If the freeze spans an epoch boundary where the borrower owes interest, lenders' yield realization and withdrawal scheduling are delayed by a full epoch cycle; loss equals foreseen interest/time-value on 100% of NAV for the freeze duration. Note: this analysis assumes `IdleCDOEpochVariant.stopEpoch` calls `prepareStopEpochWithApr0` (grep confirms the hook exists and is `_onlyIdleCDO`-gated, but the exact call site in `stopEpoch`/`stopEpochWithDuration` was not directly read; if the hook is only wired in `stopEpoch`, the loss path may still cover `stopEpochWithDuration`).

### Likelihood Explanation
Low-to-medium. Requires a legitimately configured APR=0 epoch and a manager APR change while an APR0 request bucket is open — both are plausible operational events, and the attacker transaction (a dust `requestWithdraw` during the APR0 window) costs almost nothing and can be done with a self-funded KYC'd deposit. No malicious privileged action is needed; the manager's APR raise is a normal operation.

### Recommendation
Do not gate `stopEpoch` on `unscaledApr == 0` when an APR0 bucket is open. Either (a) settle the open bucket at the stored per-epoch rate semantics regardless of current APR — e.g., treat `apr0RateByEpoch[epochNumber] = 0` and just zero `apr0TotalPrincipal` — or (b) snapshot the APR at request time per epoch and settle against that, so a later APR change cannot retroactively invalidate pending requests. Alternatively allow `_settleApr0`/claim paths to decrement `apr0TotalPrincipal` so users can unwind the bucket without requiring an APR=0 stopEpoch.
