### Title
Unvalidated `decimals` field in SPL Token `*Checked` instructions causes JSON-RPC misreporting of token amounts - (File: `transaction-status/src/parse_token.rs`)

### Summary
The transaction-status JSON parser (`parse_token`) renders human-readable `tokenAmount` fields (`uiAmount`, `uiAmountString`) for `TransferChecked`, `ApproveChecked`, `MintToChecked`, `BurnChecked`, `TransferCheckedWithFee`, and `BurnChecked` (permissioned-burn extension) instructions using the `decimals` value taken directly and unvalidated from the raw instruction data submitted in the transaction, rather than the canonical decimals recorded on the mint account itself. This mirrors the root cause of the external report: an amount/decimal pairing is trusted at face value from an unvalidated source rather than being checked against (or normalized to) the canonical decimal representation, resulting in a value that is treated as equivalent to a real balance when it is not.

### Finding Description
For every `*Checked` SPL Token instruction, `parse_token` extracts `amount` and `decimals` straight from the attacker/user-supplied `instruction.data` and immediately calls `token_amount_to_ui_amount_v3(amount, &SplTokenAdditionalDataV2::with_decimals(decimals))`, e.g.: [1](#0-0) 

The same pattern repeats for `ApproveChecked`, `MintToChecked`, `BurnChecked`: [2](#0-1) 

and in the transfer-fee and permissioned-burn extensions: [3](#0-2) [4](#0-3) 

`token_amount_to_ui_amount_v3` unconditionally trusts the passed-in `decimals` to compute `ui_amount`/`ui_amount_string`: [5](#0-4) 

Nowhere in `parse_token` (or its callers in the JSON-RPC/transaction-status path used by `getTransaction`, `getConfirmedTransaction`, log/pubsub instruction decoding, etc.) is the instruction-supplied `decimals` cross-checked against the actual decimals stored on the referenced mint account. On-chain, the SPL Token program enforces that `decimals` matches the mint for the transaction to *succeed*, but that enforcement happens inside the (out-of-scope) BPF token program, not in agave. Crucially, **agave parses and serves the JSON representation of every instruction regardless of whether the transaction ultimately succeeded or failed on-chain** — the parsing occurs purely off the compiled instruction bytes taken from the block/ledger.

This is a direct analog to the H-01 report: just as the rollup's `process_deposit`/`execute_intent_auth` treated tokens with mismatched decimals as equivalent because no canonical-decimals check or normalization was enforced, agave's instruction parser treats an attacker-chosen `decimals` byte as authoritative for rendering an amount, with no validation against ground truth (the mint's `decimals` field, which is available on-chain and already fetched elsewhere in this same codebase, e.g. `rpc/src/rpc.rs::get_token_account_balance`).

### Impact Explanation
Any unprivileged user can submit a transaction containing a `TransferChecked` (or `ApproveChecked`/`MintToChecked`/`BurnChecked`/`TransferCheckedWithFee`) instruction whose `decimals` field is deliberately wrong relative to the real mint (e.g., `decimals = 0` for a 6-decimal USDC-like mint, or vice versa). The instruction, and thus the transaction, will fail on-chain execution (SPL Token program rejects the mismatch), but the transaction is still recorded in the ledger with an "err" status. Any client calling `getTransaction`/`getConfirmedTransaction` with `jsonParsed` encoding, or subscribing via logs/pubsub that decodes instructions, receives a `tokenAmount` object whose `uiAmount`/`uiAmountString` is off by orders of magnitude (`10^|Δdecimals|`) from the true value — this is exactly the "decoder ... misreporting" class explicitly accepted by scope rules. Downstream consumers (block explorers, indexers, wallets, compliance/monitoring tooling) that trust this RPC-reported amount for display or bookkeeping can be misled about the token value involved in a transaction.

### Likelihood Explanation
Likelihood is high for triggering the misreporting: no privileged role or special conditions are needed — any wallet can construct and submit (or even just have a client submit without landing) such a `*Checked` instruction with any `decimals` byte, and any observer using `jsonParsed` encoding via JSON-RPC will see the corrupted value. It does not require the transaction to succeed, only to be included in the ledger.

### Recommendation
Before formatting `tokenAmount` for any `*Checked` instruction, resolve the referenced mint's canonical `decimals` (already available via `get_token_account_mint`/`get_mint_owner_and_additional_data` in this codebase) and either use that canonical value for display, or flag/annotate a mismatch between the instruction-declared `decimals` and the mint's actual decimals so RPC consumers are not silently given a misleading amount.

### Proof of Concept
1. Create/obtain a mint with `decimals = 6` (e.g., a USDC-like mint).
2. Construct a `TransferChecked` instruction via `spl_token_2022_interface::instruction::transfer_checked` targeting that mint but pass `decimals = 0` and `amount = 1_000_000` (intended to represent `1.0` token, but rendered as `1000000` whole units).
3. Submit the transaction (it will fail on-chain because the SPL Token program's decimals check rejects the mismatch, but it is still included in the block with an error status).
4. Call `getTransaction`/`getConfirmedTransaction` with `{"encoding": "jsonParsed"}` on the resulting signature (this exercises `parse_token` at [1](#0-0) ).
5. Observe that the returned `tokenAmount.uiAmount`/`uiAmountString` reports `1000000` (as if 1,000,000 whole tokens) instead of the true `1.0` token intended, purely because the JSON parser trusted the attacker-supplied `decimals = 0` rather than the mint's real `decimals = 6`.

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };
    UiTokenAmount {
        ui_amount,
        decimals,
        amount: amount.to_string(),
        ui_amount_string,
    }
