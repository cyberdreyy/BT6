### Title
Missing proof-length check in `FecSetRoot` block-id repair verification permits substitution of an internal Merkle node as a forged FEC-set root, enabling repair-path DoS/state poisoning - (File: `core/src/repair/serve_repair.rs`)

### Summary
`BlockIdRepairType::verify_response` in `core/src/repair/serve_repair.rs` implements the same bug class described in the external report: a Merkle-proof verifier that accepts a proof of arbitrary length instead of strictly requiring the proof length to match the tree's known depth. For the `ParentAndFecSetCount` variant this was already fixed by checking `parent_proof.len() != proof_size * SIZE_OF_MERKLE_PROOF_ENTRY` [1](#0-0) , but the sibling `FecSetRoot` variant only checks that the proof is non-empty, never that its length matches the depth required for the actual double-Merkle tree [2](#0-1) .

### Finding Description
`get_merkle_root`/`verify_merkle_proof` in `ledger/src/shred/merkle_tree.rs` terminate as soon as the (repeatedly right-shifted) `index` reaches zero, regardless of how many proof entries were consumed [3](#0-2) . This means the function itself does not enforce a fixed proof depth — any proof, of any length, that folds down to the expected root at index `0` is accepted.

For `BlockIdRepairType::ParentAndFecSetCount`, the code derives the required depth from `fec_set_count` (which is part of the response) and rejects proofs whose length doesn't match exactly [4](#0-3) . This exact check was added specifically to prevent proof/leaf-length malleability, as shown by the accompanying regression test `test_verify_fec_set_count_non_malleable` [5](#0-4) .

For `BlockIdRepairType::FecSetRoot`, however, the request/response pair contains no `fec_set_count`, so the verifier has no way to compute the expected depth, and the code only checks `fec_set_proof.is_empty()` [2](#0-1) . This is confirmed by the existing test `test_verify_fec_set_root_rejects_empty_proof`, which only exercises the empty-proof case and not any depth/length constraint [6](#0-5) .

Because the double-Merkle tree leaves are raw per-FEC-set Merkle roots with no index binding (unlike the parent-info leaf, which explicitly binds `fec_set_count` into its hash specifically to prevent this class of attack) [7](#0-6) , a malicious repair-serving peer — who, by definition of serving repair, already possesses the full slot's real FEC-set roots — can trivially compute any internal node of the real tree (e.g. `hashv(NODE_PREFIX, real_root[i], real_root[i+1])`) and submit it as the "leaf" `fec_set_root` for a chosen `fec_set_index`, together with only the *remaining* (shorter) real sibling path up to the already-pinned, trusted `block_id`. Because the verifier never checks the proof length against the expected depth, `verify_merkle_proof` folds this shorter, internal-node-rooted path back up to the real `block_id` and succeeds, even though the returned "fec_set_root" is not the genuine root for that FEC set.

This forged value is not merely rejected as invalid data — it is propagated directly into subsequent protocol state: the caller in `core/src/repair/block_id_repair_service.rs` treats the "verified" `fec_set_root` as authentic and uses it verbatim as the expected Merkle root (`fec_set_merkle_root`) for all follow-up `ShredForBlockId` repair requests covering that FEC set [8](#0-7) . Since no legitimate shred payload in that FEC set will ever hash/prove correctly against this forged internal-node value (real per-shred Merkle proofs are built against the true, per-erasure-batch root, stored separately as `MerkleRootMeta` and served via `run_fec_set_root` [9](#0-8) ), the requester will permanently fail to verify any subsequent shred for that FEC set.

### Impact Explanation
A single Byzantine (but otherwise unprivileged) validator peer that responds to `BlockIdRepairType::FecSetRoot` repair requests can poison the requester's `fec_set_merkle_root` expectation for an arbitrary FEC set of an arbitrary block, without needing any preimage attack — only knowledge of the real, adjacent FEC-set roots, which any repair-serving peer already has. This makes it impossible for the victim node to ever validate real shreds for that FEC set via this path, effectively starving that block's repair/replay progress. This is a repair-path/ingest starvation impact reachable purely from ordinary (unprivileged) network peers over the repair UDP protocol, matching the "ingest starvation" and "replay-path exhaustion" categories.

### Likelihood Explanation
High for any validator that is willing to run a Byzantine/malicious repair responder: the exploit requires no cryptographic breakthrough, only that the attacker already serve legitimate repair traffic (which is the normal role of any peer answering `FecSetRoot` requests) and can compute one extra hash (`join_nodes`) using data it already possesses. No special privileges, keys, or race conditions are needed; only that the verifier's `FecSetRoot` arm omits a length check that its sibling `ParentAndFecSetCount` arm already applies.

### Recommendation
Bind the number of FEC-set leaves (or equivalently, the exact expected proof length) into the `FecSetRoot` verification path, mirroring the fix already applied to `ParentAndFecSetCount`:
- Either include `fec_set_count` (or the tree size) in the `BlockIdRepairType::FecSetRoot` request/response so the verifier can compute `get_proof_size(...)` and reject any `fec_set_proof` whose length doesn't exactly match, or
- Bind the leaf's own index/position into the fec-set-root leaf hash itself (analogous to how the parent-info leaf binds `fec_set_count`), so that no internal node of the tree can be substituted as a valid leaf for a different index/shorter path.

### Proof of Concept
Not independently executed against a live cluster; based on static code analysis:
1. A malicious node holds the real FEC-set roots `R0, R1, …` for a slot and the trusted `block_id` for that slot (already known/pinned by the victim from a prior `ParentAndFecSetCount` exchange).
2. It computes `H01 = hashv(MERKLE_HASH_PREFIX_NODE, R0, R1)` (an internal tree node) and constructs the *shortened* remaining proof entries needed to fold `H01` up to `block_id`.
3. On receiving a `FecSetRoot` request for `fec_set_index` corresponding to leaf 0, it replies with `fec_set_root = H01` and `fec_set_proof` = the shortened remaining path.
4. `verify_response` (`core/src/repair/serve_repair.rs:327-353`) accepts this because it only checks `fec_set_proof.is_empty()`, and `verify_merkle_proof`/`get_merkle_root` (`ledger/src/shred/merkle_tree.rs:115-152`) fold successfully to `block_id` since `leaf_index >> k == 0` after the shortened proof.
5. `block_id_repair_service.rs` then propagates the forged `H01` as `fec_set_merkle_root` for all `ShredForBlockId` requests in that FEC set, permanently blocking legitimate shred verification for it.

pub fn get_merkle_root<'a, I>(index: usize, node: Hash, proof: I) -> Result<Hash, Error>
where
    I: IntoIterator<Item = &'a MerkleProofEntry>,
{
    let (index, root) = proof
        .into_iter()
        .fold((index, node), |(index, node), other| {
            let parent = if index % 2 == 0 {
                join_nodes(node, other)
            } else {
                join_nodes(other, node)
            };
            (index >> 1, parent)
        });
    (index == 0)
        .then_some(root)
        .ok_or(Error::InvalidMerkleProof)
}

/// Given a flattened merkle `proof` for `node` at `index`,
/// verify the proof against merkle root `root`
pub fn verify_merkle_proof(
    node: Hash,
    index: usize,
    proof: &[u8],
    expected_root: Hash,
) -> Result<(), Error> {
    let proof = proof
        .chunks(SIZE_OF_MERKLE_PROOF_ENTRY)
        .map(<&MerkleProofEntry>::try_from)
        .map(|entry| entry.map_err(|_| Error::InvalidMerkleProof))
        .collect::<Result<Vec<_>, Error>>()?;
    let merkle_root = get_merkle_root(index, node, proof)?;

    (merkle_root == expected_root)
        .then_some(())
        .ok_or(Error::InvalidMerkleProof)
}
