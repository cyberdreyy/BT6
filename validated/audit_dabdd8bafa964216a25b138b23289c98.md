### Title
Stale confirmations from removed multisig members still count toward the execution threshold - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
The multisig contracts store per-request confirmations as a set keyed by member identity, but when a member is removed (`DeleteMember`/`DeleteKey`), the contract only purges requests that member *originated*, not confirmations that member cast on requests originated by someone else. As a result, a stale confirmation from an already-removed member is still counted toward `num_confirmations` when a later `confirm()` call is evaluated, letting a request execute with fewer *currently valid* member approvals than the configured threshold.

### Finding Description
`confirm()` in both `multisig/src/lib.rs` and `multisig2/src/lib.rs` decides execution purely by set size: [1](#0-0) 

The size check (`confirmations.len() as u32 + 1 >= self.num_confirmations`) never re-validates whether each entry in `confirmations` still belongs to `self.members` — it only checks that the *current caller* is a member via `self.current_member()`.

When a member is removed, `delete_member` only cleans up requests where that member is recorded as the *original requester* (`r.member == member`), not confirmations the member cast on other requests: [2](#0-1) 

The equivalent v1 logic (`DeleteKey`) has the same shape — it filters by `r.signer_pk == pk` (the original requester), not by confirmer: [3](#0-2) 

So the binding that should hold is:
`countedConfirmations(request) == liveMemberConfirmations(request)`

but after a member is removed, `countedConfirmations(request)` can still include that now-removed member's stale entry, i.e. `countedConfirmations(request) > liveMemberConfirmations(request)`.

### Impact Explanation
This breaks the multisig's core authorization guarantee: a `K`-of-`N` scheme is supposed to require `K` signatures from *current* members. With this flaw, a request can execute with only `K-1` (or fewer) live-member approvals plus one or more stale approvals from removed members, letting funds be transferred (`MultiSigRequestAction::Transfer`), keys/members added, or contract code deployed with below-threshold live authorization. This matches the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
This requires no attacker-controlled privilege beyond the normal multisig workflow that already exists in production: a partially-confirmed request pending, followed by removal of one of its confirmers (a routine operational action — e.g., rotating out a member, revoking a compromised key). No special timing manipulation, redeploy, or trusted role abuse beyond the existing DeleteMember/DeleteKey action is needed; it can occur incidentally in normal multisig operation.

### Recommendation
When removing a member (`delete_member`/`DeleteKey` handling), iterate over *all* pending requests and strip the removed member's entry from each request's `confirmations` set (not just requests they originated), or alternatively re-validate every entry in `confirmations` against `self.members` at `confirm()`-time before counting toward `num_confirmations`.

### Proof of Concept
Scenario using a 4-member, 3-of-4 `multisig2` contract (members A, B, C, D):
1. Member A calls `add_request` to create request `R` (e.g., `Transfer` to an attacker-controlled account). `confirmations[R] = {}`.
2. Member A confirms: `confirmations[R] = {A}` (via `add_request_and_confirm`).
3. Member B confirms: `confirmations[R] = {A, B}` (2 of 3 needed).
4. Separately, members A, C, D confirm and execute a `DeleteMember{B}` request (`R2`, unrelated to `R`) — e.g. because B's key is being rotated out. `delete_member` only clears requests where `r.member == B` (i.e., requests B originated); `R` was originated by A, so it is untouched. `B` is removed from `self.members`, but `confirmations[R]` still equals `{A, B}`.
5. Member C now calls `confirm(R)`: `confirmations[R].len() + 1 == 3 >= num_confirmations (3)` → passes, and `execute_request` fires the `Transfer`.

Result: `R` executed with confirmations from A, B (removed), and C — i.e., only 2 currently-valid members (A, C) actually authorized it, one short of the configured 3-of-4 threshold. [1](#0-0) [2](#0-1) [3](#0-2)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
