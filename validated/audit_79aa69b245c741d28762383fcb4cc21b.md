### Title
Builder withdrawal amount is paid to the fee recipient in full while the builder's on-chain balance is debited only by a truncated `min()` amount - ([File: specs/gloas/beacon-chain.md])

### Summary
`apply_withdrawals` in Gloas debits a builder's balance by `min(withdrawal.amount, builder_balance)`, but the `Withdrawal` object queued for the execution layer still carries the full, uncapped `withdrawal.amount`. Since the execution layer is required to unconditionally honor every withdrawal in `state.payload_expected_withdrawals`, any situation where `withdrawal.amount > builder_balance` at settlement time results in the fee recipient (or the builder's own withdrawal address, for sweeps) being paid more than was ever actually debited from the builder — Gwei paid without a matching debit. This is structurally identical to the ERC721Pool `take()` bug: one side of the transaction uses the full/untruncated committed value while the other side uses a `min()`-capped value, and the shortfall is never reconciled.

### Finding Description
`apply_withdrawals` (Gloas): [1](#0-0) 

```python
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)
```

The `Withdrawal.amount` field used here is the *same* value that was placed into `state.payload_expected_withdrawals` and that the execution layer is contractually bound to pay out in full: [2](#0-1) 

For builder-payment withdrawals, that amount originates from the bid value recorded at `process_execution_payload_bid` time and is carried unchanged through `settle_builder_payment` into `builder_pending_withdrawals`: [3](#0-2) [4](#0-3) 

The invariant that a builder's balance can always cover its outstanding pending obligations is enforced only at *bid-submission* time via `can_builder_cover_bid`, which nets out `MIN_DEPOSIT_AMOUNT` plus all currently recorded pending withdrawals/payments for that builder: [5](#0-4) 

However, `process_builder_exit_request` only checks that pending balance is zero *at the moment the exit is requested*: [6](#0-5) 

Nothing prevents the builder from being (still) active and submitting a *new* bid after `initiate_builder_exit` has already fixed `withdrawable_epoch`, creating a new `BuilderPendingPayment`/`BuilderPendingWithdrawal` obligation for a builder that is already scheduled to be fully swept. When the builder's `withdrawable_epoch <= current_epoch`, the builder-sweep path pays out the raw current `builder.balance` field to the builder's own `execution_address`: [7](#0-6) 

If that sweep is applied (via `apply_withdrawals`) before, or in a different block from, the still-outstanding pending payment withdrawal, the builder's balance can be driven to (or toward) zero while a separate `BuilderPendingWithdrawal` for the earlier bid is still queued. When that pending withdrawal is later processed, `apply_withdrawals` deducts only `min(withdrawal.amount, builder_balance)` — which may now be `0` or far less than `withdrawal.amount` — yet the `Withdrawal` object placed in `payload_expected_withdrawals` for that entry still carries the full, uncapped `amount`, which the execution layer is required to pay to `fee_recipient` in full.

This breaks the equality "a Gwei may only be paid to a non-owner if it was actually debited from a real balance": the fee recipient receives the committed amount while the builder's ledger absorbs only the truncated remainder (or nothing).

### Impact Explanation
This is a Critical-severity class of bug per the rules ("Gwei created, destroyed or paid to a non-owner") because the execution-layer withdrawal is unconditionally honored regardless of what the beacon state's internal accounting actually subtracted. A gap between the committed `Withdrawal.amount` (paid in full to `fee_recipient`, typically the block proposer) and the amount actually deducted from `state.builders[i].balance` (capped by `min()`) means value is paid out that was never backed by an equivalent debit anywhere in the system — effectively minting Gwei for the fee recipient at the expense of the total-supply invariant the spec is supposed to preserve across state transitions.

### Likelihood Explanation
Reaching the exact underflow requires a specific interleaving: a builder must (a) initiate an exit while having zero pending balance (satisfying the `process_builder_exit_request` check), (b) submit an additional bid afterward while still considered active (creating a new pending payment), and (c) have its full-balance sweep applied before or without conflict-checking against that still-outstanding pending withdrawal. I was not able to fully verify, within the available index, whether `get_builders_sweep_withdrawals` (only its tail was visible) applies any `get_balance_after_withdrawals`-style adjustment analogous to the one used for validator sweeps, nor could I fully confirm the exact definition of `is_active_builder` (whether it permits bidding after exit initiation but before `withdrawable_epoch`). These are the key preconditions that determine whether the underflow/mismatch window is actually reachable in practice, and I could not conclusively establish this given index limitations — a background engineer with full repo access should verify `get_builders_sweep_withdrawals`'s complete body and `is_active_builder`'s definition before treating this as confirmed-exploitable, though the root-cause truncation in `apply_withdrawals` itself (full committed amount vs. `min()`-capped debit) is directly verifiable in the cited code.

### Recommendation
Make the committed `Withdrawal.amount` and the actual balance debit consistent, e.g., by computing withdrawal amounts for builders using a balance-after-prior-withdrawals accounting (as already done for validator partial withdrawals via `get_balance_after_withdrawals`) so that no builder withdrawal can ever be constructed with `amount > builder.balance` at construction time, and/or by having `get_builders_sweep_withdrawals` subtract any already-committed-but-unprocessed pending withdrawal amounts for that builder before sweeping the "remaining" balance, ensuring the sum of all withdrawals for a builder in flight never exceeds its actual balance.

### Proof of Concept
Conceptual sequence (exact reachability depends on unverified details noted above):
1. Builder B has balance `X`, no pending payments/withdrawals. B calls `process_builder_exit_request`; check passes (`get_pending_balance_to_withdraw_for_builder == 0`), `withdrawable_epoch` is set.
2. Before `withdrawable_epoch` is reached, B is still accepted as bidder and submits a bid of value `V` with `can_builder_cover_bid` passing against current balance `X`. A `BuilderPendingPayment` for `V` is recorded, later settled into `builder_pending_withdrawals`.
3. `withdrawable_epoch <= current_epoch` is reached; `get_builders_sweep_withdrawals` emits a sweep `Withdrawal(amount=X, address=B.execution_address)` (full nominal balance), processed via `apply_withdrawals`, setting `B.balance = 0`.
4. In a later (or same) block, the pending `BuilderPendingWithdrawal(amount=V, fee_recipient=...)` from step 2 is drained: `apply_withdrawals` computes `B.balance -= min(V, 0) = 0` (no-op), but the `Withdrawal(amount=V)` object is still included in `payload_expected_withdrawals`.
5. The execution layer pays `V` to `fee_recipient` per the committed withdrawal list, even though no balance anywhere was debited by `V` in step 4 — `V` Gwei effectively created and paid to a non-owner.

#### New `get_pending_balance_to_withdraw_for_builder`

```python
def get_pending_balance_to_withdraw_for_builder(
    state: BeaconState, builder_index: BuilderIndex
) -> Gwei:
    balance = Gwei(0)
    for withdrawal in state.builder_pending_withdrawals:
        if withdrawal.builder_index == builder_index:
            balance += withdrawal.amount
    for payment in state.builder_pending_payments:
        if payment.withdrawal.builder_index == builder_index:
            balance += payment.withdrawal.amount
    return balance
```

#### New `can_builder_cover_bid`

```python
def can_builder_cover_bid(
    state: BeaconState, builder_index: BuilderIndex, bid_amount: Gwei
) -> bool:
    builder_balance = state.builders[builder_index].balance
    pending_withdrawals_amount = get_pending_balance_to_withdraw_for_builder(state, builder_index)
    min_balance = MIN_DEPOSIT_AMOUNT + pending_withdrawals_amount
    if builder_balance < min_balance:
        return False
    return builder_balance - min_balance >= bid_amount
```

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)

    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)

def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
