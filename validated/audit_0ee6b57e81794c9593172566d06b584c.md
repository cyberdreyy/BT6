## Analog Vulnerability Found

### Title
Faucet TCP server signs transactions with no per-connection/IP rate limiting and its per-request-cap path fully bypasses the time/IP rate limiter, enabling unrestricted signing DOS - (File: `faucet/src/faucet.rs`)

### Summary
The `solana-faucet` TCP service (`run_faucet`/`process`/`Faucet::build_airdrop_transaction`) is structurally analogous to the reported `DisperseBlobAuthenticated` flaw: an unauthenticated network peer can trigger repeated, non-negligible cryptographic work (transaction construction + Ed25519 signing with the faucet's private key) with no connection-level or origin-based rate limiting applied before that work is performed. Worse, one code path — requests whose `lamports` exceeds `per_request_cap` — signs a transaction and returns *before* the time/IP rate limiter is ever consulted, meaning the only rate-limiting mechanism present in the codebase can be trivially and permanently bypassed.

### Finding Description
`run_faucet` accepts every incoming TCP connection unconditionally and spawns a task per connection with no cap on concurrent connections and no per-IP throttle at accept time: [1](#0-0) 

Each connection's `process` loop reads a fixed-size request and immediately calls into `Faucet::process_faucet_request` → `build_airdrop_transaction`: [2](#0-1) 

`build_airdrop_transaction` checks `per_request_cap` first. If the requested `lamports` exceeds it, the faucet builds a memo instruction and **signs a full transaction with `self.faucet_keypair`**, then returns immediately — the per-IP/per-address `check_time_request_limit` calls that implement the *only* rate limiting in this module are located strictly after this early-return branch and are therefore never reached for over-cap requests: [3](#0-2) 

This mirrors the reported bug class exactly: a request that ultimately fails/short-circuits still performs the "expensive" step (signature generation) with the rate-limiting check either absent (at the TCP-accept level, unlike the streamer's `ConnectionRateLimiter` used for QUIC, see `streamer/src/nonblocking/connection_rate_limiter.rs`) or trivially bypassable (the memo/over-cap branch in `build_airdrop_transaction`).

### Impact Explanation
An attacker who can reach the faucet TCP port (used behind `requestAirdrop` on test-validator/devnet deployments) can:
- Open unlimited concurrent TCP connections (no accept-time IP throttle, no connection cap), each spawning a tokio task, exhausting file descriptors/threads.
- Send a stream of `GetAirdrop` requests with `lamports` set above `per_request_cap`; each such request forces the faucet to construct and Ed25519-sign a transaction with the faucet's keypair on every single request, with zero rate limiting applied, since the check-limit calls are skipped entirely on this path.

This is a Denial-of-Service vector against the faucet process (CPU/socket/thread exhaustion), directly analogous to the reported medium-severity finding: the only mitigation (rate limiting) is applied too late/incorrectly relative to the expensive operation, and no origin-based limiting exists on the ingestion surface itself.

### Likelihood Explanation
High for any deployment exposing the faucet TCP port (common on devnet/testnet faucets and `solana-test-validator`). The bypass requires no authentication, no valid signatures, and no special privileges — just a TCP connection and a request with `lamports > per_request_cap`.

### Recommendation
- Add an accept-time, per-IP connection rate limiter to `run_faucet` (mirroring `streamer::nonblocking::connection_rate_limiter::ConnectionRateLimiter` used for the QUIC TPU) before spawning the `process` task.
- In `Faucet::build_airdrop_transaction`, move/duplicate the `check_time_request_limit` (IP-based) check to run before the per-request-cap memo-signing branch, so that IP-based limiting cannot be bypassed by simply requesting more lamports than the per-request cap.
- Consider tracking and capping repeated cap-violation attempts per IP (scoring/timeout for bad clients), consistent with the original report's recommendation.

### Proof of Concept
1. Start a faucet with `--faucet-per-request-sol-cap` set to a small value (e.g., 1 SOL).
2. From an attacker host, repeatedly open TCP connections to the faucet port and send `FaucetRequest::GetAirdrop { lamports: <very large>, to: <any pubkey>, blockhash: <any> }`.
3. Observe that `build_airdrop_transaction` takes the `per_request_cap` branch every time, signs a memo transaction with the faucet keypair, and returns — `check_time_request_limit` is never invoked, so the IP is never throttled and no connection-level limit stops further connections, allowing unbounded repeated signing operations and thread/socket usage.
