### Title
Loss-adjusted withdraw receipt escapes its haircut when the user submits a new withdraw request, paying the pre-loss amount at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When a `stopEpochWithDuration` loss leaves pending withdraw receipts only partially funded, `IdleCreditVault.collectWithdrawFunds` stores a per-epoch haircut in `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws`, but leaves each user's `withdrawsRequests`/`withdrawsRequestsByEpoch` basis intact for a later haircutted claim. The claim path locates that haircut exclusively through `lastWithdrawRequest[_user]`. A user who submits a second `requestWithdraw` (or instant request) after the loss epoch overwrites `lastWithdrawRequest[_user]` with the new epoch, so `_claimLossAdjustedWithdrawRequest` finds `lossRecoveryPriceByEpoch[newEpoch] == 0` and returns 0, and `_claimFundedWithdrawRequest` then pays the aggregate `withdrawsRequests[_user]` — which still includes the loss-epoch receipt — at par. The user redeems 100% of a receipt that was only funded at `lossRecoveryPrice`, draining funded underlyings/reserve that belong to other claimants.

### Finding Description
- `collectWithdrawFunds` records a shortfall as `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and sets `pendingWithdraws = 0` (contracts/strategies/idle/IdleCreditVault.sol:411-421). The user-level accounting in `withdrawsRequests` and `withdrawsRequestsByEpoch` is untouched — the haircut is only realized at claim time.
- `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest` then `_claimFundedWithdrawRequest` (lines 301-314).
- `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and early-returns when `lossRecoveryPriceByEpoch[lossEpoch] == 0` (lines 789-792). It only ever checks that single epoch; there is no iteration over `withdrawsRequestsByEpoch` keys.
- `requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` on every request (line 282) and adds to `withdrawsRequests[_user]`/`withdrawsRequestsByEpoch[_user][currentEpoch]` (lines 292-293). Nothing prevents a user with a pending loss-adjusted receipt from requesting again in a later epoch (the code comments even acknowledge multiple pending requests).
- `_claimFundedWithdrawRequest` then computes `normalAmount = withdrawsRequests[_user]` — still containing the loss-epoch basis — and pays it fully via `_transferFundedClaim` (lines 338-349).
- The funded side only holds `_amount = pendingToFund` underlying (the post-haircut figure collected in `collectWithdrawFunds`), plus whatever later epochs funded. Paying the old receipt at par therefore spends other users' funded claims or recovery reserve, or reverts once the strategy is drained — converting a designed loss socialization into a first-come theft and potential permanent freeze of remaining claims.

Net effect: the "one receipt, haircut-adjusted payout" invariant breaks whenever a second request rewrites the epoch marker between the loss epoch and the claim.

### Impact Explanation
Direct theft / insolvency. An attacker holding a loss-adjusted receipt of size `B` with recovery price `p < RECOVERY_FULL` extracts `B` instead of `B * p / RECOVERY_FULL`, stealing `B * (RECOVERY_FULL - p) / RECOVERY_FULL` underlying that was never funded by the borrower. This either drains underlyings reserved for other funded claimants/recovery reserve or leaves the strategy unable to pay later claims (permanent freezing of unclaimed payouts). Quantified: for a 50% haircut on a 100k receipt, the attacker doubles their claim to 100k, taking 50k from other users' funded claims.

### Likelihood Explanation
Requires a realized `stopEpochWithDuration` loss with pending receipts (a path the code explicitly supports), after which any affected receipt holder — an ordinary KYC-passed lender/tranche-token holder — only needs to call `requestWithdraw` once more in a subsequent epoch and wait one epoch boundary before claiming. No privileged cooperation is needed, and the claiming-window check (`epochNumber <= lastWithdrawRequest[_user]`) still passes once the new epoch ends. The economic incentive is direct: skipping the haircut is strictly profitable whenever `p < 1`.

### Recommendation
Track loss-adjusted receipts per epoch rather than via a single `lastWithdrawRequest` marker: in `_claimLossAdjustedWithdrawRequest`, iterate (or maintain a per-user list of) epochs with `lossRecoveryPriceByEpoch[e] != 0` where `withdrawsRequestsByEpoch[_user][e] != 0`, or store a per-user `lossEpoch` flag that survives later requests. Alternatively, eagerly haircut `withdrawsRequests[_user]`/`withdrawsRequestsByEpoch` inside `collectWithdrawFunds` (pro-rata is not possible aggregate-wide, so record the price and force the claim path to consult per-epoch data), or block new `requestWithdraw`/`requestInstantWithdraw` while `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` until the user claims.

### Proof of Concept
Foundry fork PoC (schematic, matching existing test helpers in test/foundry/IdleCreditVault.t.sol):

```solidity
function testLossAdjustedReceiptEscapesHaircut() external {
  // user deposits, epoch 0 starts
  uint256 amount = 10000 * ONE_SCALE;
  idleCDO.depositAA(amount);
  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

  // user requests withdraw of half; becomes pending receipt
  uint256 req = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));
  uint256 lossEpoch = IdleCreditVault(address(strategy)).epochNumber();
  _startEpochAndCheckPrices(1);

  // borrower returns only 50% of pendingWithdraws + active interest
  // -> collectWithdrawFunds stores lossRecoveryPriceByEpoch[lossEpoch] = 0.5e18
  uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
  uint256 funded = pending / 2;
  vm.warp(cdoEpoch.epochEndDate() + 1);
  // borrower funds only `funded` for receipts
  deal(defaultUnderlying, borrower, funded + <active interest>);
  vm.prank(manager);
  cdoEpoch.stopEpoch(funded, <active interest>); // loss-adjusted path

  // ATTACK: instead of claiming at 50%, submit a new request
  uint256 req2 = cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));
  // lastWithdrawRequest[user] = current epoch; lossRecoveryPriceByEpoch[newEpoch] == 0

  _startEpochAndCheckPrices(2);
  _stopEpochAndCheckPrices(2, initialProvidedApr, _expectedFundsEndEpoch());

  uint256 balPre = underlying.balanceOf(address(this));
  cdoEpoch.claimWithdrawRequest();
  uint256 claimed = underlying.balanceOf(address(this)) - balPre;

  // BUG: loss-epoch receipt paid at par instead of req * 0.5
  assertEq(claimed, req + req2);          // actual (par)
  // expected honest payout: req/2 + req2
  assertGt(claimed, req / 2 + req2);      // stolen = req/2
}
```

Key assertion: `claimed == req + req2` (par payout) versus the correct `req * lossRecoveryPrice / RECOVERY_FULL + req2`, with the excess drawn from the strategy's funded balance at other claimants' expense.
