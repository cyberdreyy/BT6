### Title
Unfunded instant-withdraw receipts are paid from shared vault liquidity, double-spending funds reserved for normal withdraw claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a missing refcount: `mremap` created a second mapping over the same arena, but the code tracked only one mapping, so `arena_vm_close` freed shared state while it was still referenced — a use-after-free caused by an unaccounted second claim on the same resource. `IdleCreditVault.claimInstantWithdrawRequest` has the same shape: instant-withdraw receipts are minted at request time, but the claim path pays the full receipt balance at par without checking how much underlying was actually collected for instant claims. When only part of the instant queue is funded (`pendingInstantWithdraws != 0`), a claimant's payout is drawn from the same strategy balance that backs normal pending withdraw receipts — two claim classes holding independent references to the same underlying, with no per-class accounting of what each is entitled to.

### Finding Description
`requestInstantWithdraw` burns the CDO's strategy tokens, mints receipt tokens to the user, and records both `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:356-375). Funding is a separate step: `collectInstantWithdrawFunds` pulls underlying from the CDO and decrements `pendingInstantWithdraws` (lines 398-403). The claim path, however, pays `instantWithdrawsRequests[_user]` in full with no check on how much was funded:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:387-392
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`_transferFundedClaim` only guards `defaultRecoveryReserve` (lines 897-907); it does not compare the payout against funded instant liquidity. The strategy's underlying balance also backs normal funded withdraw receipts (collected via `collectWithdrawFunds`, lines 411-430) and buffered deposits awaiting `sendInterestAndDeposits`. So when the instant queue is only partially funded — the exact state tracked by `pendingInstantWithdraws != 0` — an attacker's claim burns one receipt but consumes underlying that is simultaneously earmarked for other claimants: a double-spend/use-after-free of the same liquidity, directly mirroring the missing-remap-refcount bug.

Attack path (running epoch, any KYC'd lender or tranche holder):
1. Attacker deposits and later calls the CDO instant-withdraw flow; the CDO collects only partial instant liquidity (or the queue is partially funded across epochs), leaving `pendingInstantWithdraws > 0` while `instantWithdrawsRequests[attacker]` holds the full amount.
2. Attacker triggers `claimInstantWithdrawRequest(attacker)` via the CDO. The full receipt amount is burned and paid at par from the strategy balance.
3. The paid amount includes underlying that `collectWithdrawFunds` had reserved for normal pending withdraw claimants (or buffered deposits). Subsequent `claimWithdrawRequest` calls underflow the balance or revert, permanently freezing those claimants' funds.

The broken invariant is "one receipt, one payout": receipts of two different classes reference the same underlying balance with no funded-vs-unfunded accounting on the claim side — precisely the uncounted second mapping from the CVE.

### Impact Explanation
High. The attacker extracts underlying they are not entitled to, directly stealing funds earmarked for normal withdraw claimants and buffered deposits. Loss equals `min(instantWithdrawsRequests[attacker] - fundedShare, strategyBalance - defaultRecoveryReserve)`, up to the full unfunded instant backlog; the flip side is permanent freezing of honest users' funded claims when the balance is drained. No privileged misbehavior is required — the attacker is an ordinary lender timing a claim while `pendingInstantWithdraws` is non-zero.

### Likelihood Explanation
Medium. It requires the instant-withdraw queue to be only partially funded at claim time (partial `collectInstantWithdrawFunds`, or borrower funding shortfall before default finalization), and strategy-held underlying exceeding the funded instant amount — both reachable in normal buffer/running-epoch operation, especially while deposits sit in the strategy before `sendInterestAndDeposits`. Existing guards do not stop it: `_onlyIdleCDO` is satisfied via the normal CDO withdraw flow, `_ensureDefaultRecoveryInitialized` does not gate claims, and `_transferFundedClaim` ignores everything except `defaultRecoveryReserve`.

### Recommendation
Track funded instant liquidity explicitly, e.g. a `fundedInstantWithdraws` counter incremented in `collectInstantWithdrawFunds`, and cap `claimInstantWithdrawRequest` payouts at the funded portion (or decrement per-claim funded basis). Alternatively, record a per-epoch funded price for instant receipts symmetric to `lossRecoveryPriceByEpoch`, so unfunded instant receipts cannot spend underlying owned by other claim classes.

### Proof of Concept
A reproducible Foundry fork PoC would: (1) deploy the vault and CDO on a mainnet fork, (2) seed two KYC'd lenders — attacker requests an instant withdraw while honest user B has a normal `requestWithdraw` funded via `collectWithdrawFunds`, (3) fund only part of the instant queue so `pendingInstantWithdraws > 0`, (4) call `claimInstantWithdrawRequest(attacker)` and show the strategy balance drops below `B`'s funded claim, then `claimWithdrawRequest(B)` reverts on underflow — demonstrating the double-spend of one underlying pool by two receipt classes.
