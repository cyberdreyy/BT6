### Title
Signer weight double-counted when a signer's `BlockResponse` flips from Rejected to Accepted — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tallies per-block signer weight into two independent counters, `total_weight_approved` and `total_weight_rejected`, using two separate dedup keys (`gathered_signatures` for accept, `responded_signers` for both). A signer that first rejects and later accepts the same block has its weight added to `total_weight_rejected` (guarded by `responded_signers`) and then, because `gathered_signatures` does not yet contain its slot, also added to `total_weight_approved`. The same signer's weight is thus recounted across both tallies, breaking the invariant that `total_weight_approved + total_weight_rejected <= total_weight`. This mirrors the bonding-curve report's bug class: an externally-driven update (a peer's second, differently-typed message) mutates one side of an accounting pair without the code re-synchronizing the other side, corrupting values that downstream logic treats as mutually exclusive/bounded.

### Finding Description
`BlockStatus` (stacks-node/src/nakamoto_node/stackerdb_listener.rs:70-82) holds `responded_signers`, `gathered_signatures`, `total_weight_approved`, and `total_weight_rejected` as independent fields with no cross-consistency enforcement. [1](#0-0) 

On `BlockResponse::Accepted`, the dedup check is against `gathered_signatures`:
```rust
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [2](#0-1) 

On `BlockResponse::Rejected`, the dedup check is against `responded_signers`:
```rust
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [3](#0-2) 

Sequence for a single signer at `slot_id`:
1. Signer sends `Rejected` first → `responded_signers.insert(slot_id)` returns `true` (first insertion) → `total_weight_rejected += weight`. `gathered_signatures` is untouched.
2. The same signer later sends `Accepted` for the same block (e.g. it re-evaluates and signs, or a malicious/misbehaving signer deliberately flips) → the accept branch checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (only the reject path touched `responded_signers`, not `gathered_signatures`) → `total_weight_approved += weight` is applied *again*, using the same signer's weight that is already baked into `total_weight_rejected`.

Before the crafted sequence: `total_weight_approved = A`, `total_weight_rejected = R`, with `A + R <= total_weight` for all previously distinct responders.
After the sequence: `total_weight_rejected = R + w`, `total_weight_approved = A + w`, so `A + R + 2w` is now attributed to the block, while only one signer of weight `w` has actually spoken. This is the "rejection recounted as an accept" class: a rejection is not withdrawn, yet the same weight is separately recorded as an acceptance.

### Impact Explanation
`signer_coordinator.rs`'s wait loop treats these two counters as if they partition the signer weight and checks the rejection bound before the acceptance bound:
```rust
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(SignersRejected ...)
} else if block_status.total_weight_approved >= self.weight_threshold {
    ... return Ok(signatures)
}
``` [4](#0-3) 

Because a single flipped signer's weight can now inflate both `total_weight_rejected` and `total_weight_approved` simultaneously, the coordinator's decision no longer reflects the true set of distinct signer weights that voted each way:
- It can reach `total_weight_approved >= weight_threshold` (70%) using phantom weight that also still sits in `total_weight_rejected`, i.e., a block can be treated as having crossed the honest signing threshold when the true, currently-standing vote of that signer is a rejection (or vice versa depending on arrival order), letting a single signer's weight count toward acceptance beyond what it should.
- Symmetrically it inflates `total_weight_rejected`, which can cause `SignersRejected` (with `permanently_excluded_txids`/`temporarily_excluded_txids`) to fire based on double-counted weight rather than a genuine blocking-minority of distinct signers.

This is a genuine miscount of aggregated weight vs. verified per-signer votes — one signer's weight is effectively spent twice across mutually-exclusive outcome buckets, which is exactly the "aggregated-weight vs verified-accepts" equality the task calls out as a Critical-class break (a rejection recounted as an acceptance). It requires no majority collusion: a single existing signer flipping its vote (reject then accept) on the same block is sufficient to trigger the double count, and it is reachable from ordinary gossip traffic the `StackerDBListener` already processes.

### Likelihood Explanation
Likelihood is Medium-High: any single signer can legitimately re-evaluate a block (the signer-side state machine explicitly supports transitioning out of `LocallyRejected` back to `LocallyAccepted` on re-evaluation, per `BlockInfo::check_state` in `stacks-signer/src/signerdb.rs:314-329`), so this is not merely a byzantine action — it's a natural consequence of the documented reject→accept re-evaluation path combined with the coordinator's independent dedup keys. [5](#0-4) 
No special privileges, keys, or majority coordination are required — only that the miner's `StackerDBListener` observe two responses from the same signer for the same block, which is ordinary StackerDB traffic already handled by the loop at stacks-node/src/nakamoto_node/stackerdb_listener.rs:372-560. [6](#0-5) 

### Recommendation
Use a single dedup/authority mechanism for both branches: track one "current response" per `slot_id` (e.g. a `HashMap<u32, ResponseKind>` instead of separate `responded_signers`/`gathered_signatures` sets) so that a later message from the same signer first reverses the effect of the earlier one (`total_weight_rejected -= old_weight` if switching away from reject, or vice versa) before applying the new tally. Alternatively, gate any transition with an explicit check: if `slot_id` is already present in the *other* tally, subtract it there before adding it to the new one, guaranteeing `total_weight_approved + total_weight_rejected` always equals the sum of the most-recent, distinct per-signer weight.

### Proof of Concept
1. Signer S (slot `k`, weight `w`) sends `BlockResponse::Rejected` for block `B`. `StackerDBListener` executes stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-518: `responded_signers.insert(k)` succeeds, `total_weight_rejected += w`.
2. Signer S later sends `BlockResponse::Accepted` for the same block `B` (a valid signature over `B`, as permitted by the signer's own re-evaluation logic in `stacks-signer/src/signerdb.rs`'s `check_state`). `StackerDBListener` executes stacks-node/src/nakamoto_node/stackerdb_listener.rs:443-465: `gathered_signatures.contains_key(k)` is `false`, so `total_weight_approved += w` runs.
3. Now `total_weight_rejected` and `total_weight_approved` both include `w`, so `total_weight_approved + total_weight_rejected` exceeds the true total distinct weight that has responded by `w`. If `w` is large relative to `weight_threshold`/blocking-minority margins, this can independently push `total_weight_approved >= weight_threshold` in `signer_coordinator.rs` (stacks-node/src/nakamoto_node/signer_coordinator.rs:541-545) or push `total_weight_rejected` past the blocking-minority bound (stacks-node/src/nakamoto_node/signer_coordinator.rs:509-519), using the weight of a single signer counted twice.
