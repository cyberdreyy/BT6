### Title
Unbounded extra trailing accounts allow attacker-crafted single-owner Transfer/TransferChecked/Approve/etc. instructions to be misreported as multisig authority transfers - ([File: transaction-status/src/parse_token.rs])

### Summary
`parse_signers` in `transaction-status/src/parse_token.rs` decides whether a token instruction's authority is a plain owner or a multisig purely by comparing `accounts.len()` to `last_nonsigner_index + 1`, with no verification that the trailing accounts are actually used by the on-chain program or that the authority account is really a multisig account. Because `check_num_token_accounts` only enforces a lower bound on account count, an attacker can append arbitrary unused account keys to their own instruction's account list to flip this heuristic and cause `getTransaction`/`getParsedTransaction` (jsonParsed) to report a normal single-authority transfer as a `multisigAuthority` transfer with a fabricated `signers` list.

### Finding Description
For instructions like `TransferChecked`, `ApproveChecked`, `Burn`, `MintTo`, etc., the code calls: [1](#0-0) 
`check_num_token_accounts` only validates a minimum account count (lower bound), it does not cap the maximum, so the compiled instruction's `accounts` array may legally contain more entries than the program actually consumes.

`parse_signers` then branches purely on account-count arithmetic: [2](#0-1) 
If `accounts.len() > last_nonsigner_index + 1`, it labels `accounts[last_nonsigner_index]` as the `multisig_field_name` (e.g. `multisigAuthority`) and treats everything after it as `signers`, regardless of whether:
1. The account at `last_nonsigner_index` is actually a `Multisig`-typed account owned by the token program, and
2. The trailing accounts are truly consumed as multisig co-signers by spl-token-2022's runtime processor.

At the runtime level, spl-token-2022 determines multisig-vs-owner semantics by deserializing the account's on-chain data (its `AccountState`/`Multisig` discriminator), not by counting how many accounts were passed in the instruction. A Solana program that doesn't need extra accounts simply ignores unconsumed entries in `account_info_iter`. Consequently, an attacker fully controlling their own transaction can append an arbitrary, otherwise-unused pubkey to the end of a `TransferChecked` (or similar) instruction's `accounts` list. The transaction still executes as a normal single-owner transfer on-chain, but the transaction-status parser used by `getParsedTransaction`/`getTransaction` RPC endpoints will mislabel the real owner as `multisigAuthority` and list the padding account as a `signers` entry, even though it never signed anything nor is part of any multisig.

This is a `PARSE_FIDELITY` violation: the parsed JSON representation returned by RPC does not match the actual signer/authority semantics enforced by the token program.

### Impact Explanation
This falls under the "decoder ... misreporting" category explicitly accepted in scope. The impact is scoped to metadata/labeling correctness of RPC-served parsed transaction data: any downstream integrator, indexer, exchange compliance tool, or explorer that branches on the presence of the `authority` vs `multisigAuthority` key (or trusts the `signers` array) to determine whether a transfer was multisig-authorized will receive incorrect information for an attacker's own transaction. It does not cause a validator crash, consensus mutation, unbounded cost, or wrong-slot/fork data — it is a display/parsing-fidelity bug confined to the jsonParsed instruction decoding path.

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: the attacker only needs to build their own transaction (using their own token account and authority key) with one extra, non-required account key appended to the relevant instruction's account list, submit it via a single `sendTransaction` call, and later query it via a single `getTransaction`/`getParsedTransaction` call with `jsonParsed` encoding. No special privileges, no interaction with other validators, and no more than the allowed one-call-per-slot-window rate are required.

### Recommendation
`parse_signers` should not infer multisig status from account count alone. Where feasible, the parser should verify against actual account data (if available to the encoding pipeline) whether the referenced account is a `Multisig`-owned account before labeling it `multisigAuthority`, or otherwise clearly document this as a heuristic-based, best-effort label rather than an authoritative signer/authority claim in the RPC docs. At minimum, an upper bound consistent with the instruction's expected accounts (base accounts + up to spl-token-2022's max multisig signer count, i.e., 11) should be enforced so that only account-count patterns that are actually possible for a legitimate multisig invocation trigger the `multisigAuthority` label instead of an unbounded/attacker-chosen number of trailing accounts.

### Proof of Concept
Rust integration test outline for `transaction-status`:
1. Build a `TransferChecked` instruction for `spl_token_2022_interface` with a normal (non-multisig) `authority` pubkey as the single required signer, using `spl_token_2022_interface::instruction::transfer_checked`.
2. Manually push one extra arbitrary `Pubkey::new_unique()` into the resulting `Instruction.accounts` (as a non-signer, non-writable meta) before compiling the message, simulating what an attacker can freely do since they construct their own instruction/message.
3. Compile via `Message::new(&[ix], Some(&payer))` and call `parse_token(&compiled_instruction, &account_keys)`.
4. Assert that the returned JSON contains `"multisigAuthority"` (not `"authority"`) and a non-empty `"signers"` array containing the padding pubkey, even though on real spl-token-2022 runtime execution (verifiable by comparing against spl-token-2022's own `Instruction`/`AccountMeta` construction, where this extra account is never marked as an expected multisig signer) the authority is a direct, non-multisig owner — demonstrating the mismatch between parsed fields and real program semantics.

```rust
fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}
```
