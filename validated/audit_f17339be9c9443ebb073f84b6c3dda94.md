### Title
Boundary-dependent account misattribution in `parse_permissioned_burn_instruction` (ConfidentialBurn arm) causes `permissionedBurnAuthority`/proof-context fields to be mislabeled - ([File: transaction-status/src/parse_token/extension/permissioned_burn.rs])

### Summary
The `ConfidentialBurn` branch of `parse_permissioned_burn_instruction` walks `account_indexes` using a hand-rolled `offset` counter gated by `saturating_sub(2)`/`saturating_sub(1)` bound checks combined with the three proof-offset flags from attacker-controlled instruction data. When `account_indexes.len()` sits at the minimum allowed value (4, the floor enforced by `check_num_token_accounts`) while `has_sysvar` is true, the sysvar-slot check `offset < account_indexes.len().saturating_sub(2)` (`2 < 2`) is false, so the loop never advances past `offset = 2` for the sysvar/proof-context insertions, and the account meant to represent the instructions sysvar (or a proof context account) instead falls straight into the `"permissionedBurnAuthority"` slot at the bottom of the function.

### Finding Description
`parse_permissioned_burn_instruction` is reached from `getTransaction`/`getConfirmedTransaction` with the `jsonParsed` encoding via `parse_token`, operating purely on raw, attacker-supplied instruction bytes and account index lists — it does not validate that the instruction would actually succeed on-chain [1](#0-0) .

For `PermissionedBurnInstruction::ConfidentialBurn`, only `check_num_token_accounts(account_indexes, 4)` is enforced, i.e. a minimum of 4 accounts, with no upper-bound or exact-shape validation tied to the offset flags [2](#0-1) . The subsequent manual walk uses `offset = 2` as a base and four sequential `if` guards keyed off `has_sysvar` and the three `*_proof_instruction_offset == 0` conditions, each protected by `offset < account_indexes.len().saturating_sub(2)` before advancing, followed by a final unconditional-looking `permissionedBurnAuthority` assignment guarded only by `offset < account_indexes.len().saturating_sub(1)` [3](#0-2) .

With `account_indexes.len() == 4` (the minimum allowed) and `has_sysvar == true` (attacker sets any of the three `*_proof_instruction_offset` fields non-zero in the raw instruction data), `account_indexes.len().saturating_sub(2) == 2`, so `offset < 2` is `false` at `offset = 2` and the `instructionsSysvar` insertion is skipped entirely — no `offset` advancement occurs. The code then falls through the equality/validity/range checks (also gated at the same bound, also false), and finally reaches the `permissionedBurnAuthority` check where `offset(2) < len.saturating_sub(1) == 3` is true, so `account_keys[account_indexes[2]]` is labeled `"permissionedBurnAuthority"` even though, per the same code's own comment and the layout implied by `has_sysvar`, that account slot is meant to hold the instructions-sysvar account, not the authority. The attacker fully controls both the instruction data (discriminator + the three `u8`/offset fields) and the account-index list length/content of an arbitrary transaction sent to the SPL Token 2022 program id, requiring no elevated privilege — only a single transaction submission, whether or not it succeeds during execution, since `parse_token` runs on raw instruction bytes independent of execution outcome.

### Impact Explanation
This is a decoder/parser misreporting bug: `getTransaction(jsonParsed)` returns a `"permissionedBurnAuthority"` value that does not correspond to the intended semantic role of that account (it is actually the sysvar or proof-context slot), while `"instructionsSysvar"`/proof-context fields are silently omitted. This falls under the allowed "decoder panic and misreporting" bounty category — it does not affect consensus or validator liveness, but produces wrong-account-role data returned by a public RPC API. [4](#0-3) 

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: any single transaction (need not succeed on-chain) targeting the SPL Token 2022 program with a `ConfidentialBurn` instruction, exactly 4 accounts, and any non-zero proof-instruction offset triggers the mislabeling deterministically. No special account state, signature validity beyond fee-payer, or multiple RPC calls are required — one `getTransaction` call against a block containing such a transaction exposes the bug.

### Recommendation
Replace the manual `offset`/`saturating_sub` walk with an explicit, exact account-layout computation derived from `has_sysvar` and the three proof-offset flags (i.e., compute the expected total account count up front and validate it against `account_indexes.len()` before assigning any field), or fall back to a documented/verified reference implementation matching `spl_token_2022_interface`'s actual account ordering, so that insufficiently-sized account lists produce a hard parse error (`InstructionNotParsable`) rather than a shifted/mislabeled field.

### Proof of Concept
```rust
// transaction-status/src/parse_token/extension/permissioned_burn.rs (test module)
#[test]
fn test_confidential_burn_min_accounts_with_sysvar_offset_mislabels_authority() {
    use spl_token_2022_interface::extension::confidential_mint_burn::instruction::BurnInstructionData;

    // Craft raw ConfidentialBurn instruction data with a non-zero equality offset
    // (has_sysvar == true) but supply the *minimum* allowed 4 accounts.
    let account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let slot2 = Pubkey::new_unique(); // intended to be "instructionsSysvar"
    let slot3 = Pubkey::new_unique(); // intended to be authority/owner region

    // Build instruction data: discriminator for ConfidentialBurn + BurnInstructionData
    // with equality_proof_instruction_offset = 1 (non-zero), others = 0.
    let burn_data = BurnInstructionData {
        new_decryptable_available_balance: Default::default(),
        equality_proof_instruction_offset: 1,
        ciphertext_validity_proof_instruction_offset: 0,
        range_proof_instruction_offset: 0,
    };
    let instruction_data = encode_confidential_burn_instruction(&burn_data); // helper composing discriminator + data

    let account_keys = AccountKeys::new(&[account, mint, slot2, slot3], None);
    let account_indexes: [u8; 4] = [0, 1, 2, 3];

    let parsed = parse_permissioned_burn_instruction(
        &instruction_data,
        &account_indexes,
        &account_keys,
    )
    .unwrap();

    // BUG: instructionsSysvar is never inserted despite has_sysvar == true.
    assert!(parsed.info.get("instructionsSysvar").is_none());

    // BUG: slot2 (meant to be the instructions sysvar account) is mislabeled
    // as permissionedBurnAuthority instead.
    assert_eq!(
        parsed.info["permissionedBurnAuthority"],
        json!(slot2.to_string())
    );
}
```
A full table-driven version should enumerate `account_indexes.len()` in `2..8` crossed with all 8 combinations of the three offset flags, asserting for each combination which raw account index each named field (`instructionsSysvar`, `equalityProofContextStateAccount`, `ciphertextValidityProofContextStateAccount`, `rangeProofContextStateAccount`, `permissionedBurnAuthority`) maps to, and flagging any case where the mapped index does not match the layout implied by the offset flags (as demonstrated at `len == 4`, `has_sysvar == true` above).
