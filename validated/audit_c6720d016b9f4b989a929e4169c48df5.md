### Title
Stale confirmations from removed multisig members are not purged, allowing requests to execute below the required confirmation threshold — (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
Both multisig contracts track per-request confirmations in a set (`confirmations: LookupMap<RequestId, HashSet<String>>` in `multisig2`, `HashSet<PublicKey>` in `multisig`) that is completely independent of the set of currently active members/keys (`members: UnorderedSet<MultisigMember>` / access keys on the account). When a member (or access key) is removed via `DeleteMember`/`DeleteKey`, the code only cleans up requests and confirmations for requests *originated* by that member, but never scans other still-open requests to strip out confirmations that member had already cast on them. The stale confirmation entries remain counted toward `num_confirmations` forever, exactly analogous to the reported bug where a removed operator's `bytes32` slot is left as a stale, uncleaned entry in an array/mapping that downstream logic still trusts.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member` only purges requests whose `member` (the request creator) equals the member being deleted: [1](#0-0) 

It never inspects the `confirmations` map for *other* requests where the removed member merely cast a confirmation (added via `confirm`, which stores `member.to_string()` into the request's `HashSet<String>`): [2](#0-1) 

`confirm()` decides execution purely by counting set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`), with no re-validation that every entry in the set still corresponds to a live member. Once a member is removed, their earlier confirmation on any other still-pending request is never invalidated or removed, so it silently continues to count toward the threshold.

The same pattern exists in the older `multisig/src/lib.rs` contract, where `DeleteKey` only removes requests whose `signer_pk` equals the deleted key: [3](#0-2) 

and `confirm()` similarly just checks set length against `num_confirmations` without revalidating members: [4](#0-3) 

### Impact Explanation
This breaks the binding "confirmations counted == confirmations from live members." A request can reach and pass `num_confirmations` using a mix of stale confirmations from already-removed members plus fewer live-member confirmations than the configured threshold, resulting in a multisig request (including arbitrary `Transfer`, `FunctionCall`, `AddKey`, or further `DeleteMember`/`AddMember` requests) being executed with fewer than `K` currently-authorized approvals. This is a Critical-class issue per the custody model of the contract: a multisig request executed below threshold, directly enabling unauthorized fund transfers or privilege changes signed off by fewer live members than intended.

### Likelihood Explanation
The scenario requires no owner/foundation privilege beyond normal multisig member actions that are part of the contract's own design (any member can create and confirm requests, and member removal is a standard, expected multisig operation). Any deployment that ever removes a member (e.g., key rotation, offboarding) while other requests are concurrently pending confirmation from that member is exposed. Given that active-request limits (`ACTIVE_REQUESTS_LIMIT`) and the 15-minute request cooldown are meant to support long-lived open requests, and member removal is an explicitly supported action, this is realistically reachable, not purely theoretical.

### Recommendation
When a member/key is deleted, iterate over all outstanding requests and remove the deleted member's identifier from every request's confirmations set (not just requests they authored), decrementing effective confirmation counts as needed. Alternatively, validate at `confirm()`-time (or execution time) that every entry in a request's confirmation set still refers to a currently active member, filtering out stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `B` calls `add_request_and_confirm(R)` — confirmations for `R` become `{B}`.
3. `A` calls `confirm(R)` — confirmations for `R` become `{A, B}` (2 < 3, not yet executed).
4. Separately, members confirm and execute a `DeleteMember { member: A }` request, removing `A` from `self.members`. Since `R.member == B` (not `A`), `delete_member` does not touch `R`'s confirmations — `{A, B}` remains untouched.
5. `C` calls `confirm(R)` — confirmations length becomes `2 + 1 = 3 >= num_confirmations (3)`, so `R` executes, even though only `B` and `C` are actually live members that confirmed; `A`'s stale confirmation counted toward the threshold, effectively letting `R` execute with only 2 out of 3 required live-member approvals.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
