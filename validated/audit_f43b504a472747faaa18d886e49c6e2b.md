### Title
`LockupFactory::create` lets the caller override the foundation whitelist, bypassing the staking-pool vetting the deployment was supposed to enforce - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` accepts an optional `whitelist_account_id` argument that, when supplied by the caller, replaces the factory's own configured, foundation-approved `staking_pool_whitelist_account_id` in the `LockupArgs` used to initialize the new lockup contract. [1](#0-0) 

### Finding Description
The `LockupFactory` is initialized once with a trusted `whitelist_account_id` pointing at the NEAR-Foundation-approved whitelist contract, whose entire purpose is to guarantee that any staking pool a lockup owner selects "can not be lost, locked, or stolen" per the documented invariant of the staking system. [2](#0-1) [3](#0-2) 

However, `create()` is an unprivileged, `#[payable]` method callable by any account, and it takes `whitelist_account_id: Option<ValidAccountId>` as a parameter. If supplied, this value — not `self.whitelist_account_id` — is embedded as `staking_pool_whitelist_account_id` in the `LockupArgs` sent to the newly deployed lockup contract's `new` constructor: [4](#0-3) 

The intended binding is:
`deployed_lockup.staking_pool_whitelist_account_id == LockupFactory.whitelist_account_id` (the single foundation-vetted whitelist).

The actual binding after an attacker's call is:
`deployed_lockup.staking_pool_whitelist_account_id == attacker_supplied_account_id`

Because the lockup contract's `select_staking_pool` trusts whichever whitelist account ID it was initialized with unconditionally (`ext_whitelist::is_whitelisted(...)` is called against `self.staking_pool_whitelist_account_id`, with no restriction to a specific known-good contract): [5](#0-4) 

An attacker who deploys (or has someone else deploy) a lockup via the factory can point `staking_pool_whitelist_account_id` at a contract they control (a fake whitelist that always returns `true` for `is_whitelisted`). This breaks the trust binding the whitelist contract is supposed to enforce, exactly analogous to the referenced report's pattern of an entitlement check ("is this staking pool actually vetted?") being satisfiable by data the caller controls rather than the ground truth the system depends on (there: subscription status; here: whitelist membership). The test suite even demonstrates this override path (`test_create_lockup_with_custom_whitelist_success`), confirming the parameter is reachable and effective. [6](#0-5) 

### Impact Explanation
Once a lockup contract is deployed with an attacker-controlled whitelist, `select_staking_pool` on that lockup will accept any `staking_pool_account_id`, including a malicious "staking pool" contract that never intends to return delegated tokens. This is a "wrongly parameterised deployment" of a lockup that no longer carries the safety guarantee (funds cannot be lost/locked/stolen) that the whole staking + whitelist subsystem is designed to provide — the explicit invariant documented in `lockup/README.md`. Locked/unvested NEAR delegated through such a lockup can be permanently frozen or stolen by a malicious staking pool, since the "real" vetting process (which enforces that a whitelisted pool must let the lockup recover its tokens) never happens.

### Likelihood Explanation
`create()` requires no special privilege — any account with the minimum attached deposit can call it and supply an arbitrary `whitelist_account_id`. No foundation or owner permission is checked on this parameter, and the deployed lockup subsequently relies solely on it for pool vetting.

### Recommendation
Remove the caller-supplied `whitelist_account_id` override, or restrict it to values from a foundation-controlled allow-list (e.g., only accept an override if it itself is whitelisted by the master whitelist contract). At minimum, `create()` should always use `self.whitelist_account_id` (the value fixed at factory initialization) unless the override is separately authorized by the foundation.

### Proof of Concept
1. Deploy a minimal "fake whitelist" contract exposing `is_whitelisted(staking_pool_account_id) -> bool` that always returns `true`.
2. Call `lockup_factory.create(owner_account_id, lockup_duration, None, None, None, Some(fake_whitelist_account_id))` with the minimum attached deposit. [1](#0-0) 
3. The new lockup contract is initialized with `staking_pool_whitelist_account_id = fake_whitelist_account_id` instead of the factory's trusted whitelist. [7](#0-6) 
4. As the lockup owner, call `select_staking_pool(malicious_pool_account_id)`; the lockup calls `is_whitelisted` on the fake whitelist, which returns `true`, so the malicious pool is accepted. [5](#0-4) 
5. `deposit_and_stake` can now be used to send locked/unvested tokens to the malicious pool, which is under no obligation (and was never vetted) to allow recovery of the funds.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )

In order for the lockup contracts to be able delegate to a staking pool, the staking pool should faithfully implement the spec.

    pub fn select_staking_pool(&mut self, staking_pool_account_id: AccountId) -> Promise {
        self.assert_owner();
        assert!(
            env::is_valid_account_id(staking_pool_account_id.as_bytes()),
            "The staking pool account ID is invalid"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();

        env::log(
            format!(
                "Selecting staking pool @{}. Going to check whitelist first.",
                staking_pool_account_id
            )
            .as_bytes(),
        );

        ext_whitelist::is_whitelisted(
            staking_pool_account_id.clone(),
            &self.staking_pool_whitelist_account_id,
            NO_DEPOSIT,
            gas::whitelist::IS_WHITELISTED,
        )
        .then(ext_self_owner::on_whitelist_is_whitelisted(
            staking_pool_account_id,
            &env::current_account_id(),
            NO_DEPOSIT,
            gas::owner_callbacks::ON_WHITELIST_IS_WHITELISTED,
        ))
    }
