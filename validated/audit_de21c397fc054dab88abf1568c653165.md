## Analog Vulnerability Found

The reported CVE describes session IDs generated from a source an attacker can predict/steer because the value's origin is not properly unpredictable. The closest analog in this repository is in the **EIP-8321 hash-chain RANDAO** feature, where a validator's future RANDAO contributions are entirely fixed, chosen, and known by the validator itself at chain-generation time — with no on-chain enforcement that the underlying secret is actually unpredictable — unlike the legacy BLS-signature RANDAO reveal, whose value a signer cannot freely choose.

### Title
Ungrindable RANDAO guarantee is broken by attacker-chosen hash-chain commitments enabling steerable proposer/committee selection - (File: `specs/_features/eip8321/beacon-chain.md`)

### Summary
`process_randao_commitment_registration` accepts any 32-byte `commitment` value signed by the validator, with no proof or constraint that it was derived from an unpredictable source. Because the entire hash chain (and thus every future RANDAO contribution this validator will ever make) is generated fully offline before registration, a validator can grind over arbitrarily many candidate chains and register the one whose resulting sequence of RANDAO mixes is most favorable to its own future proposer/committee selection, breaking the "unpredictable until published" grinding-resistance property the design claims to preserve.

### Finding Description
The introduction to EIP-8321 states the design goal explicitly: "RANDAO's resistance to grinding currently relies on BLS signatures being *unique*, so that a proposer cannot bias its contribution... preimage resistance keeps each reveal unpredictable until it is published" [1](#0-0) .

In the legacy phase0 scheme, `process_randao` mixes in `sha256(body.randao_reveal)` where `randao_reveal` is a BLS signature over `(epoch, DOMAIN_RANDAO)` [2](#0-1) . For a given validator/epoch pair this value is unique and unforgeable — the proposer cannot choose among multiple valid reveals for the same epoch; the only lever available is skipping the slot entirely.

The EIP-8321 hash chain replaces this with `compute_hash_chain`, which a validator computes **entirely offline** from a self-chosen `chain_secret`, generating the full sequence of future reveal values (`c_0 ... c_length`) before ever touching the chain [3](#0-2) . The only guidance that this secret be unpredictable is a validator-side recommendation ("draws a uniformly random 32-byte chain secret") [4](#0-3) ; it is **not enforced by the state transition**.

`process_randao_commitment_registration` only checks that the commitment is non-zero, unused, and signed by the validator's key — it performs no check on how the commitment/chain was derived:
```python
assert registration.commitment != UNSET_RANDAO_COMMITMENT
assert state.randao_commitments[index] == UNSET_RANDAO_COMMITMENT
assert all(pending.validator_index != index for pending in state.pending_randao_commitments)
...
assert bls.Verify(validator.pubkey, signing_root, signed_registration.signature)
``` [5](#0-4) 

Once activated, every reveal simply proves the walked hash-chain step and folds the raw preimage into the mix with a hash accumulator, with no additional entropy check:
```python
verify_hash_chain_reveal(state, body, proposer_index)
mix = blake3(get_randao_mix(state, epoch) + body.hash_chain_reveal)
``` [6](#0-5) , with `verify_hash_chain_reveal` only checking the preimage relationship [7](#0-6) .

This RANDAO mix directly feeds `get_seed`, and from there `get_beacon_proposer_index`/`compute_proposer_index` and `get_beacon_committee`/`compute_committee` [8](#0-7) , [9](#0-8) .

Because the validator selects its `chain_secret` — and hence every future reveal value it will ever contribute — entirely offline and before registering, it can generate many candidate chains, simulate the resulting sequence of RANDAO mixes it will contribute at its own future assigned slots, and register only the chain that biases future proposer/committee selection in its favor (e.g., toward slots where it or a colluding validator is more likely to be chosen). This is a materially larger grinding surface than the legacy scheme, where the sole grinding lever per assigned slot is "reveal or skip" and the reveal value itself cannot be chosen.

### Impact Explanation
This breaks the equality that duty selection (`get_beacon_proposer_index`, `compute_committee`, sync-committee selection) should be equally unpredictable/unsteerable by any single participant. A validator that grinds a favorable chain can steer its own (or an accomplice's) probability of proposer/committee selection across many future epochs, a "duty selection one participant can steer" — explicitly listed as a High-impact class in scope.

### Likelihood Explanation
The attack requires only local offline computation (generating and simulating many hash chains before registering) — it needs no majority stake, no client bug, and no cooperation from any other party. It is bounded only by the attacker's own compute budget for generating and searching candidate chains, which is realistic given the low cost of `blake3` hashing and the chain being generated entirely client-side with no on-chain randomness attestation.

### Recommendation
Bind chain generation to unpredictable, protocol-derived entropy that is not known to the validator until close to registration time (e.g., require the registration/commitment to also incorporate a beacon-chain-derived seed the validator cannot control, or add a verifiable-unpredictability proof), or otherwise constrain the registration so the committed chain cannot be freely selected from many self-generated candidates without cost proportional to the grinding advantage gained.

### Proof of Concept
1. Off-chain, a validator generates `N` candidate `chain_secret` values and computes `compute_hash_chain(chain_secret, length)` for each, per `specs/_features/eip8321/validator.md` lines 64-77.
2. For each candidate chain, the validator simulates the sequence of `blake3(mix + reveal)` mixes it would contribute at its own future proposer-assigned slots (which it can predict via `MIN_SEED_LOOKAHEAD` lookahead using `get_beacon_proposer_index_and_threshold`-style simulation, as already exercised by `simulate_lookahead_with_thresholds` in the test helpers) [10](#0-9) .
3. The validator selects the candidate chain whose tip, once registered via `process_randao_commitment_registration`, yields future mixes that bias `get_seed`/`compute_proposer_index` toward re-selecting itself (or a colluding validator) more often than the honest-random baseline.
4. Register that chain's tip as `commitment`; `process_randao_commitment_registration` accepts it unconditionally as long as it is properly signed, with no check that it was derived from unpredictable entropy.

def process_randao_commitment_registration(
    state: BeaconState, signed_registration: SignedRandaoCommitmentRegistration
) -> None:
    registration = signed_registration.message
    index = registration.validator_index

    assert index < len(state.validators)
    assert registration.commitment != UNSET_RANDAO_COMMITMENT
    assert state.randao_commitments[index] == UNSET_RANDAO_COMMITMENT
    assert all(pending.validator_index != index for pending in state.pending_randao_commitments)

    # Fork-agnostic domain since registrations are valid across forks

        PendingRandaoCommitment(
            validator_index=index,
            commitment=registration.commitment,
            activation_epoch=get_current_epoch(state) + COMMITMENT_REGISTRATION_DELAY,

def compute_proposer_index(
    state: BeaconState, indices: Sequence[ValidatorIndex], seed: Bytes32
) -> ValidatorIndex:
    """
    Return from ``indices`` a random index sampled by effective balance.
    """
    assert len(indices) > 0
    MAX_RANDOM_BYTE = 2**8 - 1
    i = Uint64(0)
    total = Uint64(len(indices))
    while True:
        candidate_index = indices[compute_shuffled_index(i % total, total, seed)]
        random_byte = sha256(seed + uint_to_bytes(Uint64(i // 32)))[i % 32]
        effective_balance = state.validators[candidate_index].effective_balance
        if effective_balance * MAX_RANDOM_BYTE >= MAX_EFFECTIVE_BALANCE * random_byte:
            return candidate_index
        i += 1

```python
def compute_hash_chain(chain_secret: Bytes32, length: Uint64) -> Sequence[Bytes32]:
    """
    Return the hash chain ``[c_0, ..., c_length]`` generated from
    ``chain_secret``, where ``c_0`` is the secret itself.
    """
    chain = [chain_secret]
    for _ in range(length):
        chain.append(blake3(HASH_CHAIN_RANDAO_DST + chain[-1]))
    # A link equal to UNSET_RANDAO_COMMITMENT cannot be revealed, so the chain
    # must be regenerated from a fresh secret if one occurs
    assert all(value != UNSET_RANDAO_COMMITMENT for value in chain)
    return chain
```

def simulate_lookahead_with_thresholds(spec, state) -> Sequence[tuple[Uint64, Uint64]]:
    """
    Simulate the lookahead by advancing the state forward with empty slots and

    lookahead = []
    simulation_state = state.copy()
    for _ in range(spec.SLOTS_PER_EPOCH * spec.Uint64(spec.MIN_SEED_LOOKAHEAD + 1)):
        proposer_index = get_beacon_proposer_index_and_threshold(spec, simulation_state)
        lookahead.append(proposer_index)
        next_slot(spec, simulation_state)
    return lookahead
