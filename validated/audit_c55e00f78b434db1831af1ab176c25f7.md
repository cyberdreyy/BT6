### Title
External ERC4626 liquidity drain reverts `stopEpoch` and freezes pending withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
A programmable-borrower epoch cannot be stopped while the configured ERC4626 vault lacks withdrawable liquidity. Even when the borrower’s vault shares economically cover the required amount, `ProgrammableBorrower.onStopEpoch` converts an external `vault.withdraw` failure into a reverting `stopEpoch`. A user of that ERC4626 vault can therefore temporarily freeze settlement of `IdleCreditVault.pendingWithdraws`.

### Finding Description
In a programmable-borrower deployment, epoch interest is minted and `stopEpoch` only needs cash for pending withdrawal receipts. `IdleCDOEpochVariant._stopEpoch` calls `ProgrammableBorrower.onStopEpoch` for `_amountToPullFromBorrower + _pendingWithdraws`, so minted mode normally requires `pendingWithdraws` cash. [1](#0-0) 

When the borrower has insufficient underlying on hand, `onStopEpoch` compares the shortfall with the value of its vault shares. If the shares cover the amount but the vault has insufficient immediately withdrawable assets, the attempted `vault.withdraw` reverts and `onStopEpoch` deliberately reverts with `StopEpochVaultLiquidityUnavailable`. [2](#0-1) 

That revert is not caught by `IdleCDOEpochVariant`: the `onStopEpoch` call is a direct boolean call, not a `try`/`catch`. Consequently, the whole `stopEpoch` transaction reverts, `pendingWithdraws` remains unfunded, and `isEpochRunning` remains true. [3](#0-2) 

An attacker only needs to be a shareholder/user of the configured ERC4626 vault. They can redeem enough vault liquidity around the honest manager’s `stopEpoch` call so that the borrower’s shares still cover `pendingWithdraws`, but the vault cannot supply the cash. This can be repeated whenever liquidity becomes available.

### Impact Explanation
This causes temporary freezing of withdrawal funds. The quantified affected amount is the strategy’s `pendingWithdraws` at the attempted stop; active tranche holders also remain locked because the epoch stays running and normal settlement does not occur. The existing regression test demonstrates that the failed stop leaves `defaulted == false`, `isEpochRunning == true`, borrower accounting active, and the pending withdrawal unchanged. [4](#0-3) 

### Likelihood Explanation
Likelihood is configuration-dependent but does not require a privileged role or malicious borrower. Ordinary ERC4626 liquidity can be depleted by shareholder redemptions or underlying borrowing. The attacker must remove enough liquidity during the interval between `epochEndDate` and the manager’s `stopEpoch` transaction, and the attack is limited to periods of vault illiquidity.

### Recommendation
Do not park assets reserved for already-matured `pendingWithdraws` in the external ERC4626 vault. In `ProgrammableBorrower.onStartEpoch`, retain `epochPendingWithdraws` as on-hand underlying and deposit only the excess into the vault. Alternatively, introduce a distinct retryable-liquidity result that `IdleCDOEpochVariant` can handle without reverting or incorrectly treating the condition as borrower default.

### Proof of Concept
Add this test to `test/foundry/ProgrammableBorrowerCreditVault.t.sol`. It uses the existing liquidity-limited ERC4626 mock to deterministically reproduce the state after a vault user drains withdrawable liquidity:

```solidity
function testExternalVaultLiquidityDrainBlocksStopEpoch() external {
    MockStopEpochLiquidityVault limitedVault =
        new MockStopEpochLiquidityVault(USDC);
    uint256 amount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    vm.prank(manager);
    programmableBorrower.setVault(address(limitedVault));

    idleCDO.depositAA(amount);
    cdoEpoch.requestWithdraw(
        aaTranche.balanceOf(address(this)) / 2,
        address(aaTranche)
    );
    _startEpochAndCheckPrices(0);

    uint256 pendingWithdraws = strategy.pendingWithdraws();
    assertGt(pendingWithdraws, 1);

    // Equivalent state after an external ERC4626 user redeems the
    // vault's idle liquidity: borrower shares still cover the request,
    // but withdrawable underlying is one unit short.
    limitedVault.setWithdrawLimit(pendingWithdraws - 1);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertFalse(cdoEpoch.defaulted());
    assertTrue(cdoEpoch.isEpochRunning());
    assertEq(strategy.pendingWithdraws(), pendingWithdraws);
}
```
