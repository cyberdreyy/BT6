### Title
Missing duplicate-check when registering webapicap callbacks allows cross-user response hijacking - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The `handler.HandleLegacyUserMessage` function in the gateway's WebAPI capabilities handler stores a per-request callback keyed only by the client-supplied `MessageId`, without ever checking whether an entry with that key already exists. This mirrors the analog-report bug class: a registration step that is not paired with a verification/consistency check, allowing a later "registration" to silently clobber an earlier one whose corresponding "callback" (here, a DON node's response) has not yet arrived.

### Finding Description
`HandleLegacyUserMessage` unconditionally overwrites the `savedCallbacks` map entry for a given `MessageId`: [1](#0-0) 

Unlike the newer v2 HTTP trigger handler in the same codebase, which explicitly guards against ID reuse: [2](#0-1) 

the legacy `capabilities/handler.go` path has no such check. `MessageId` is a client-controlled field (`json:"message_id"`), validated only for length/format, not uniqueness or ownership: [3](#0-2) 

Node responses are later routed back purely by this same `MessageId` key: [4](#0-3) 

Because `HandleLegacyUserMessage` is triggered by any unprivileged client hitting the gateway HTTP endpoint (`ProcessRequest` → `h.HandleLegacyUserMessage`), an attacker can:
1. Observe or guess an in-flight `MessageId` for another user's legitimate request that has been sent to DON nodes but not yet answered (window bounded by `CallbackMaxAgeSec`, default 120s).
2. Submit their own signed legacy request using that same `MessageId` (a signature and DON membership are required, but any authorized DON member/onboarded user can pick their own `MessageId`, and the value has no per-sender namespacing—the map key is simply `msg.Body.MessageId`, not `(sender, MessageId)`).
3. The attacker's callback silently replaces the original one in `h.savedCallbacks`.
4. When the DON node eventually responds to the original request (same `MessageId`), `handleWebAPITriggerMessage` looks the entry up by `MessageId` only and delivers the *original* payload to the *attacker's* HTTP callback, while the legitimate original caller never receives a response and is left to time out.

This is the same root-cause shape as the reference report: a callback/registration slot that is asserted to be free/consistent, but the code never validates that assumption before allowing a new registration, letting stale or conflicting state silently coexist and later be dispatched to the wrong (or no) recipient.

### Impact Explanation
This is a cross-user response confusion / information disclosure vulnerability: an unprivileged actor can receive another user's response payload (which may contain HTTP callback data, private endpoint responses, or execution results not authorized for their view) simply by colliding on `MessageId`. It also causes a denial-of-service for the original requester, whose request silently vanishes without any error being returned to them (their `callback.Wait` will eventually time out with a generic timeout error, masking that a hijack occurred). Rated Medium/High depending on payload sensitivity, since it grants a form of unauthorized read access to responses not belonging to the requester—analogous to the original report's "important operations may be skipped/misdirected."

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to know or predict a legitimate in-flight `MessageId` within the callback window (up to 120s by default, or up to `MaxAllowedMessageAgeSec`), and to be a party capable of sending signed legacy requests to the same DON handler (this is reachable by any client/EOA that can produce a valid signed request accepted by `Validate()`—there is no server-side generation or randomization enforcement of `MessageId` uniqueness across senders). Since IDs are entirely client-chosen with no uniqueness enforcement, an attacker controlling their own client can trivially trigger the race by re-using IDs they've previously observed (e.g., via shared tooling, logs, or by initiating requests concurrently with another known user in a shared workflow context).

### Recommendation
1. Reject registration if a `savedCallback` already exists for the given `MessageId` (mirroring the v2 `httpTriggerHandler.setupCallback` pattern which returns a `jsonrpc.ErrConflict`/"already been used" error), instead of silently overwriting it.
2. Namespace the `savedCallbacks` map key by `(Sender, MessageId)` rather than `MessageId` alone, ensuring cross-user collisions are structurally impossible.
3. After the callback map entry is consumed/found in `handleWebAPITriggerMessage`, verify that the responding node's identity/sender matches the DON member the original request was actually dispatched to, adding defense-in-depth similar to the recommendation of checking that expected callback state has been reset before treating it as fulfilled.

### Proof of Concept
1. User A sends a signed legacy `web_api_trigger` request with `message_id = "shared-id-123"` to the gateway; the gateway registers a callback for `"shared-id-123"` and forwards the request to all DON members. `HandleLegacyUserMessage` accepts and stores it: [1](#0-0) 
2. Before any DON node responds, attacker B sends their own signed legacy request also using `message_id = "shared-id-123"` (a value B has learned, e.g. via logging, shared infra, or coordination with A's client). B's request passes `Validate()` since only length/format is checked, and overwrites the map entry for `"shared-id-123"` in `h.savedCallbacks`.
3. A DON node responds to `"shared-id-123"` intending to answer A's original request. `handleWebAPITriggerMessage` looks up `h.savedCallbacks["shared-id-123"]`, finds B's callback instead, and delivers A's response payload to B: [4](#0-3) 
4. A's original callback is never invoked and A's request eventually times out without explanation, while B has received a response payload belonging to A's request.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
