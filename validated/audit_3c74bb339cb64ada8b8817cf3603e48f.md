## Analysis: Double-settlement of builder payments after a missed-slot gap in `apply_parent_execution_payload` [1](#0-0) 

### Title
Builder payment settled twice (epoch-quorum eviction *and* fallback branch) after 2+ missed epochs - (File: specs/gloas/beacon-chain.md)

### Summary
`apply_parent_execution_payload` settles a builder's pending payment through three mutually-exclusive branches keyed only on how many epochs have elapsed since the parent slot, not on whether the payment entry was already resolved. When 2+ epochs elapse before the parent's payload gets acknowledged by a descendant block, the fallback branch unconditionally re-creates a withdrawal from the *cached* `latest_execution_payload_bid.value`, without checking whether `process_builder_pending_payments` (run at every intervening epoch boundary regardless of whether blocks are produced) has already turned that same payment into a withdrawal via the PTC/attestation-weight quorum path.

### Finding Description
The payment lifecycle has two independent, non-communicating settlement paths for the same `BuilderPendingPayment` entry:

1. **Epoch-boundary quorum path** — `process_builder_pending_payments`, called every epoch as part of `process_epoch` (which runs even across empty/missed slots), checks `payment.weight >= quorum` for the first-half slots and appends a `BuilderPendingWithdrawal` if so, then unconditionally shifts/clears the array: [2](#0-1) 

2. **Block-processing settle path** — `apply_parent_execution_payload`, called from `process_parent_execution_payload` when a block acknowledges its parent as FULL, branches purely on `parent_epoch` vs. `get_current_epoch`/`get_previous_epoch`:
```
if parent_epoch == get_current_epoch(state):
    settle_builder_payment(state, payment_index)
elif parent_epoch == get_previous_epoch(state):
    settle_builder_payment(state, payment_index)
elif parent_bid.value > 0:
    # Parent is older than the previous epoch, its payment entry has been
    # evicted from builder_pending_payments. Append the withdrawal directly.
    state.builder_pending_withdrawals.append(BuilderPendingWithdrawal(...))
``` [3](#0-2) 

The comment "its payment entry has been evicted" assumes the entry was *discarded* (quorum not met). But `process_builder_pending_payments` evicts the slot **regardless of the quorum outcome** — the array is overwritten unconditionally (`state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments`), whether or not a withdrawal was appended. Nothing in `apply_parent_execution_payload`'s fallback branch checks `builder_pending_withdrawals` (or any other state) to see if the payment for `parent_bid` was *already* turned into a withdrawal by the epoch-boundary quorum check that necessarily ran while the intervening slots were being advanced (`process_epoch` runs on every epoch boundary independent of block production).

Weight can legitimately reach quorum before the 2-epoch eviction window closes: attesters signal payload availability via `data.index` in `process_attestation`, independent of whether any later proposer's own bid claims the parent as FULL: [4](#0-3) 

Consequently, if enough weight accumulates to clear quorum before block production resumes, the same committed bid value is paid out twice: once via the quorum-triggered `builder_pending_withdrawals.append` in `process_builder_pending_payments`, and again via the unconditional fallback `append` in `apply_parent_execution_payload` when the delayed child block finally arrives.

The existing test only exercises the “weight never reached quorum” branch (`test_builder_payment_after_missed_epochs` sets `weight=0`), so it never observes/detects the double-append case where quorum *was* reached before eviction: [5](#0-4) 

### Impact Explanation
This breaks the equality "a Gwei paid to a non-owner beyond what the block committed to." A single bid `value` (committed once by the builder in its `SignedExecutionPayloadBid`) results in **two** `BuilderPendingWithdrawal` entries of the same amount being queued, both of which are later processed by `apply_withdrawals`/`get_builder_withdrawals`, deducting the amount from the builder's balance twice (up to the builder's balance) and paying the `fee_recipient` twice. This matches the explicitly listed High-severity criterion: "a builder payment or withdrawal misdirected, doubled, or escaped," achieved without any malicious peer/coalition — simply through a naturally occurring missed-slot gap combined with sufficient PTC/attester participation.

### Likelihood Explanation
Requires: (a) a builder bid with non-zero value that accumulates attestation weight ≥ quorum before the second epoch boundary after the bid's slot, and (b) no descendant block acknowledging that parent within the following ~2 epochs (network already has to tolerate multi-slot/epoch gaps as a first-class case, evidenced by the dedicated fallback branch and test). Both conditions are plausible under normal network conditions with occasional multi-slot outages (client bugs, proposer unavailability, network partitions are explicitly out of scope per the rules, but ordinary missed slots without any adversarial party are sufficient here) — no coalition or malicious client is required, only the ordinary skip-slot handling paths of the protocol.

### Recommendation
`apply_parent_execution_payload`'s fallback branch must check whether the payment for `parent_bid`/`parent_slot` was already settled by `process_builder_pending_payments` before appending a new withdrawal — e.g., by tracking a "settled" bit/epoch keyed by slot that persists across the eviction, or by having `process_builder_pending_payments` always append a withdrawal (even when weight < quorum, with amount adjusted) so that a single, unconditional source of truth exists for whether a given slot's builder payment has been settled, and removing the redundant unconditional append in `apply_parent_execution_payload`.

### Proof of Concept
1. Builder B bids value `V` for slot `N`; block `N` is included, creating `builder_pending_payments[SLOTS_PER_EPOCH + N % SLOTS_PER_EPOCH]` with `weight=0`, `withdrawal.amount=V`.
2. Enough attesters submit same-slot attestations for slot `N` in the following blocks (independent of whether later blocks claim N as a "full" parent) so `payment.weight` reaches `get_builder_payment_quorum_threshold(state)` before the second epoch boundary after N.
3. No block acknowledges `N` as its immediate FULL parent for 2+ epochs (i.e., subsequent slots pass with `state` advancing via `process_slots`, which still runs `process_epoch`/`process_builder_pending_payments` at each boundary).
4. At the second epoch boundary, `process_builder_pending_payments` sees `weight >= quorum` and appends `BuilderPendingWithdrawal(amount=V, builder_index=B, ...)` to `state.builder_pending_withdrawals` (withdrawal #1), then unconditionally clears/evicts the entry.
5. A later block (slot `N+k`, k spanning 2+ epochs) is finally produced whose own bid still references `N`'s block hash as parent (`bid.parent_block_hash == parent_bid.block_hash`, since all intervening slots were empty). `process_parent_execution_payload` → `apply_parent_execution_payload` computes `parent_epoch` as 2+ epochs stale, hits the `elif parent_bid.value > 0` branch, and appends a **second** `BuilderPendingWithdrawal(amount=V, builder_index=B, ...)` (withdrawal #2).
6. Both withdrawals are later drained via `apply_withdrawals`, deducting `2V` total from builder B's balance and crediting `fee_recipient` twice for a single committed bid of `V`.

#### New `process_builder_pending_payments`

```python
def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

*Note*: This function processes the parent's execution requests, queues the
builder payment, updates payload availability, and updates the latest block
hash. It is called by `process_parent_execution_payload` during block processing
and by the validator during block production before computing withdrawals.

```python
def apply_parent_execution_payload(
    state: BeaconState,
    requests: ExecutionRequests,
) -> None:
    parent_bid = state.latest_execution_payload_bid
    parent_slot = state.latest_block_header.slot
    parent_epoch = compute_epoch_at_slot(parent_slot)

    assert len(requests.withdrawals) <= MAX_WITHDRAWAL_REQUESTS_PER_PAYLOAD
    assert len(requests.consolidations) <= MAX_CONSOLIDATION_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_deposits) <= MAX_BUILDER_DEPOSIT_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_exits) <= MAX_BUILDER_EXIT_REQUESTS_PER_PAYLOAD

    # Process execution requests from parent's payload. The execution
    # requests are processed at state.slot (child's slot), not the parent's slot.
    def for_ops(operations: Sequence[Any], fn: Callable[[BeaconState, Any], None]) -> None:
        for operation in operations:
            fn(state, operation)

    for_ops(requests.deposits, process_deposit_request)
    for_ops(requests.withdrawals, process_withdrawal_request)
    for_ops(requests.consolidations, process_consolidation_request)
    for_ops(requests.builder_deposits, process_builder_deposit_request)
    for_ops(requests.builder_exits, process_builder_exit_request)

    # Settle the builder payment
    if parent_epoch == get_current_epoch(state):
        payment_index = SLOTS_PER_EPOCH + parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_epoch == get_previous_epoch(state):
        payment_index = parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_bid.value > 0:
        # Parent is older than the previous epoch, its payment entry has been
        # evicted from builder_pending_payments. Append the withdrawal directly.
        state.builder_pending_withdrawals.append(
            BuilderPendingWithdrawal(
                fee_recipient=parent_bid.fee_recipient,
                amount=parent_bid.value,
                builder_index=parent_bid.builder_index,
            )
        )

    # Update parent payload availability and latest block hash
    state.execution_payload_availability[parent_slot % SLOTS_PER_HISTORICAL_ROOT] = Boolean(True)
    state.latest_block_hash = parent_bid.block_hash
