### Title
External Initiator credentials bypass "EI not allowed" restriction and can trigger job runs on arbitrary integer job IDs - ([File: core/web/pipeline_runs_controller.go])

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered in the `userOrEI` group with `auth.RequiresRunRole(prc.Create)`, reachable by users authenticated via session/token AND by external-initiator (EI) credentials via `auth.AuthenticateExternalInitiator` [1](#0-0) .

`AuthenticateExternalInitiator` does not merely mark the request as an EI request — it also injects a synthetic `*clsessions.User{Role: clsessions.UserRoleRun}` into the gin context under the same `SessionUserKey` that real user auth methods use: `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` [2](#0-1) .

Inside `PipelineRunsController.Create`, the code explicitly comments that "only users are allowed to run jobs using int IDs - EIs not allowed," and gates that branch with `isUser, _ := auth.GetAuthenticatedUser(c)` [3](#0-2) . However `auth.GetAuthenticatedUser` simply reads whatever object is stored at `SessionUserKey` — it cannot distinguish a genuine session/token user from the fake "Run"-role user object that `AuthenticateExternalInitiator` sets for EI requests [4](#0-3) . As a result, `isUser` evaluates to `true` for EI-authenticated requests too, and the int32-ID branch — which calls `prc.App.RunJobV2(ctx, jobID, nil)` with **no ownership/association check whatsoever between the EI and job ID** — executes for EI callers exactly as it would for real users.

Since there is no code anywhere in `Create` (or in `RunJobV2`) that verifies the job's `ExternalInitiatorWebhookSpec` matches the authenticated EI's identity, an EI credential holder can supply any integer job ID belonging to any job in the node (not just a webhook job tied to their own EI credential) and trigger a run on it.

### Impact Explanation
This is an authorization-bypass / unauthorized-action vulnerability: a low-privilege credential (external-initiator key/secret, intended only to trigger the specific webhook job it was created for) can be used to trigger pipeline runs on arbitrary jobs on the node, including jobs unrelated to any webhook/EI binding (e.g., OCR, direct-request, flux-monitor jobs identified by integer ID). This maps to Chainlink's "unauthorized job run" impact class — an attacker with a narrow, job-scoped credential gains the ability to invoke node compute/pipeline execution outside its intended scope, potentially causing unwanted external HTTP calls, resource consumption, spurious task/bridge invocations, or interference with legitimate job operations.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs any valid, currently-active external-initiator credential pair (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers), which is the lowest tier of API credential in the system and explicitly meant to be scoped to a single webhook integration. No admin/edit/run-user role, no bridge secret, and no knowledge of internal job UUIDs is required — only an integer job ID, which is often incrementing/sequential and can be brute-forced or discovered via other job listing/pagination behavior. The bug is 100% deterministic and repeatable given valid EI creds.

### Recommendation
In `PipelineRunsController.Create`, explicitly detect and reject EI-authenticated requests before entering the int32-ID branch, e.g. check `if _, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI { reject }`, rather than relying on `GetAuthenticatedUser`, since `AuthenticateExternalInitiator` populates the same context key used by real user sessions. Alternatively, stop injecting a fake `SessionUserKey` user for EI requests in `auth.AuthenticateExternalInitiator` and instead have `RequiresRunRole` and any run-triggering handler check the EI's own identity (`GetAuthenticatedExternalInitiator`) directly, restoring a real binding check between the EI and its associated webhook job before allowing `RunJobV2`.

### Proof of Concept
Handler-level integration test plan:
1. Create the node application, create an external initiator "EI-A" via `ExternalInitiatorsController.Create` (or `cltest` helper), obtaining EI-A's `AccessKey`/`Secret`.
2. Create a second job (e.g. an OCR job or any job with an int32 `ID`, using `setupPipelineRunsControllerTests` helper pattern) that is not associated with EI-A in any way.
3. Build an HTTP client that sends `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers set to EI-A's credentials (no session cookie, no user API token).
4. `POST /v2/jobs/<jobB.ID>/runs` using that client.
5. Assert: the current code returns `200 OK` with a `PipelineRunResource` (proving the run was triggered) — expected/fixed behavior should return `401/403` since EI-A has no relationship to `jobB`.
6. Additionally assert via `RunJobV2` mock/spy that it was invoked with `jobB.ID`, confirming an EI unrelated to that job successfully triggered its execution.
