### Title
Stale epoch index on unfunded instant-withdraw receipts breaks default recovery accounting - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug is an index that is modified after being captured and then reused to index an array, producing an out-of-bounds/wrong-slot access. The analog in `IdleCreditVault` is the *epoch index* used for instant-withdraw receipts: `requestInstantWithdraw` writes `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` using the `epochNumber` value at request time, but the default-recovery path reads those mappings at `epochNumber` / `defaultRecoveryEpoch` — the *current* epoch at finalization. Any unfunded instant receipt that survives an epoch boundary is indexed under a stale epoch and is invisible to recovery accounting, yet remains payable at par afterward.

### Finding Description
1. `requestInstantWithdraw` records the receipt under the request-time epoch (`instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, lines 367–374). `pendingInstantWithdraws` is only decremented in `collectInstantWithdrawFunds` (line 401), so an instant request that the CDO never funds stays pending forever, across `stopEpoch`/`epochNumber` increments.
2. `defaultPendingClaimBasis` (lines 644–649) adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — to the recovery basis. A receipt recorded in an earlier epoch contributes nothing to `totalBasis` in `finalizeDefaultRecovery`, so `defaultRecoveryReserve` and `defaultRecoveryPrice` are computed as if that claim did not exist.
3. `_claimDefaultedInstantWithdrawRequest` (lines 842–856) clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — again the current epoch. The stale-epoch entry is never cleared and `instantWithdrawsRequests[_user]` retains its full amount.
4. `claimInstantWithdrawRequest` (lines 380–393) then burns `instantWithdrawsRequests[_user]` and pays the *entire* residual at par through `_transferFundedClaim`. That claim was never part of the default-recovery `totalBasis`, so it is paid either out of underlyings belonging to active holders/funded claimants, or `_transferFundedClaim`'s reserve guard (lines 899–905) reverts and the receipt is permanently frozen.

### Impact Explanation
- **Theft / reserve drain:** if the strategy holds sufficient non-reserve underlying, the stale-epoch instant claimant redeems at par even though defaulted-epoch claimants receive only `defaultRecoveryPrice` — un-funded claim dilutes and drains funds that other users' funded receipts rely on, breaking the "one receipt, one haircutted payout" and loss-waterfall invariants.
- **Permanent freezing:** if the only underlying left is the recovery reserve, the `balance - reserve < _amount` guard reverts, permanently freezing the user's unfunded instant receipt (which is real, attacker-created claim basis).
- Loss quantification: the full unfunded instant amount requested before the epoch boundary, payable at 100% while every other claimant takes the recovery haircut, or 100% of that receipt frozen.

### Likelihood Explanation
An unprivileged lender only needs to call `requestInstantWithdraw` when the CDO lacks free liquidity to fund it (normal during a running epoch), then wait: `epochNumber` increments at `stopEpoch`, and once the borrower defaults and `finalizeDefaultRecovery` runs, the index mismatch is already baked in. The path requires no privileged cooperation beyond the ordinary epoch cycle and an eventual default, and no existing guard (per-epoch checks, reserve guard, `_onlyIdleCDO`) detects the stale-epoch receipt — the guard that does fire just converts the theft into a freeze, which is still an accepted impact.

### Recommendation
Key instant-withdraw claims by a marker that survives epoch increments, or fold `pendingInstantWithdraws` into `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest` across all epochs rather than only `epochNumber`/`defaultRecoveryEpoch`. For example, iterate/aggregate outstanding instant claims (or keep a single global unfunded-instant basis bucket) so receipts requested in epoch *N* are included in recovery when finalization happens in epoch *N+k*, and clear `instantWithdrawsRequests[_user]` fully during default claims.

### Proof of Concept
```solidity
// Foundry fork-style PoC against IdleCreditVault + IdleCDOEpochVariant
// 1. user deposits, startEpoch runs.
// 2. user calls cdo.requestInstantWithdraw(amount) while CDO has no idle
//    liquidity -> instantWithdrawsRequestsByEpoch[user][E]=amount,
//    pendingInstantWithdraws=amount, never collected.
// 3. manager runs stopEpoch (epochNumber -> E+1), startEpoch, etc.
// 4. borrower defaults; owner calls _handleBorrowerDefault/finalizeDefault ->
//    finalizeDefaultRecovery reads instantWithdrawClaimsByEpoch[E+1] == 0.
//    totalBasis excludes user's instant claim; reserve sized for others only.
// 5. user calls cdo.claimInstantWithdrawRequest():
//    - _claimDefaultedInstantWithdrawRequest finds
//      instantWithdrawsRequestsByEpoch[user][E+1] == 0 -> clears nothing.
//    - _burn(user, amount) + _transferFundedClaim(user, amount) pays at par
//      (theft from funded claimants) or reverts on the reserve guard
//      (permanent freeze of the receipt).
assertEq(strategy.instantWithdrawsRequestsByEpoch(user, requestEpoch), amount);
assertEq(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), 0); // stale index
```

**Caveat:** I could not fully verify whether `IdleCDOEpochVariant.stopEpoch`/`getInstantWithdrawFunds` forcibly settles all `pendingInstantWithdraws` at epoch end — the grep returned no excerpt lines. If instant withdrawals are guaranteed funded within their request epoch, the stale-index window closes and the finding reduces to the freeze/edge case rather than guaranteed theft.
