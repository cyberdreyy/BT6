### Title
ProgrammableBorrower deposits pool assets into the ERC4626 vault with no share floor — first-depositor share inflation steals pool principal - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The external bug class is unsanitized user-controlled input reaching a privileged sink (attacker-supplied video options injected into a shell command). The analog in idle-tranches is unsanitized externally-controlled input — the ERC4626 vault's share price — reaching the pool's capital-deployment sink: `ProgrammableBorrower._depositToVault` calls `vault.deposit(_assetAmount, address(this))` and accepts whatever shares the vault returns, with no `previewDeposit` comparison and no minimum-shares floor [1](#0-0) . A vault user who is first to deposit can inflate the share price via donation before the pool's deposit lands, so the pool mints near-zero shares while the attacker later redeems the donated+deposited assets.

### Finding Description
`onStartEpoch` deposits the entire idle underlying balance into the configured ERC4626 vault: `_depositToVault(underlyingToken.balanceOf(address(this)), 0)` [2](#0-1) . `_depositToVault` performs a bare `vault.deposit` and never validates `shares` [3](#0-2) . The same unchecked pattern exists on `vault.withdraw`/`vault.redeem` paths (`_borrow`, `onStopEpoch`, `emergencyExitVault`), none of which bound the exchange rate [4](#0-3) [5](#0-4) .

The stolen amount is not silently neutralized. `onStartEpoch` snapshots `epochStartVaultAssets = startAssets` measured *before* the deposit [6](#0-5) , so `_vaultNetInterest()` later computes `earnedAssets` (post-inflation share value) well below `principalAssets`, producing a real `vaultLoss` [7](#0-6) . That loss flows into `totalInterestDueNow()` [8](#0-7) , which `IdleCDOEpochVariant._resolveStopEpochInterest` treats as the source of truth for epoch interest [9](#0-8)  — forcing negative/absent epoch interest and, at close, crystallizing the loss on tranche holders via `_updateAccounting`/default paths.

Broken invariant: fair mint of external vault shares on pool deposit (deposit-integrity/solvency). No guard stops it: `nonReentrant` doesn't help (the inflation is done in a prior transaction), `setVault` only enforces `asset()` match and zero existing shares [10](#0-9)  — which is exactly the precondition for the inflation attack.

### Impact Explanation
Direct theft of pool principal with quantified bound: for a vault inflation factor `k = donatedAssets`, a pool deposit of `P` assets mints `P/(1+k)` shares; the attacker redeems its seed share for ≈ `P·k/(1+k)` of pool assets net of donation. With `k ≥ P` the pool's minted shares round to ~0 and the attacker captures ≈ `P − ε` of the deposit. The loss is socialized to AA/BB tranche holders as `vaultLoss` at `stopEpoch`/`stopEpochWithDuration`, or triggers `_handleBorrowerDefault` when the recall fails — either way LPs bear it.

### Likelihood Explanation
Requires a permissionless ERC4626 vault with low/zero liquidity at the moment `onStartEpoch` (or a `repay` redeploy, `_repay` → `_depositToVault`) executes. Vault users are an in-scope attacker class, and any ERC4626 vault without virtual-share inflation protection (e.g., freshly deployed or fully redeemed vaults) is exploitable. `setVault` mandates zero existing shares, meaning a vault swap always begins in the most vulnerable state. Attacker cost is the seed deposit plus donated assets, recovered on redeem.

### Recommendation
In `ProgrammableBorrower._depositToVault` (and the withdraw/redeem call sites), bound the exchange rate: compute `expected = vault.previewDeposit(_assetAmount)` and require `shares >= expected` (or an operator-set minShares), and revert on violation. Equivalently for withdrawals, require `vault.previewWithdraw(shortfall)` coverage. Additionally, prefer vaults with built-in virtual-asset/share inflation protection and document that requirement in `setVault`.

### Proof of Concept
Reproducible Foundry fork PoC sketch (attacker = ordinary vault depositor, epoch phase = buffer→running transition):

```solidity
// Setup: revolving credit vault deployed with ProgrammableBorrower PB, vault V (fresh ERC4626)
// 1. Lender deposits P into CDO (buffer). PB holds P underlying idle.
// 2. Attacker (any EOA), before manager calls startEpoch:
//    a. vault.deposit(1 wei) -> 1 share (first depositor)
//    b. underlying.transfer(address(vault), P)  // donate P -> price = (P+1)/1 share
// 3. manager.startEpoch() -> PB.onStartEpoch -> _depositToVault(P, 0)
//    vault.deposit(P, PB) mints P*1/(P+1) = 0 shares (rounds down)
//    epochStartVaultAssets = P (snapshot taken pre-deposit)
// 4. Attacker: vault.redeem(1 share) -> receives ~2P assets; profit ~P
// 5. Warp past epochEndDate; manager.stopEpoch(0, 0):
//    totalInterestDueNow() sees vaultLoss ~= P; pool NAV impaired / default path.
// Assertions:
assertEq(vault.balanceOf(address(PB)), 0);               // pool minted zero shares
assertGt(programmableBorrower.vaultLoss(), P - dust);    // loss recorded
assertGt(attackerProfit, P - seedCost);                  // quantified theft
```

Notes/uncertainty: exploitability presumes the configured vault lacks inflation protection (a vault-config property, not idle-tranches code); the idle-tranches-side defect — unconditional acceptance of the vault's returned share amount — is confirmed in `ProgrammableBorrower.sol`.

  function _vaultNetInterest() internal view returns (uint256 interest, uint256 loss) {
    if (!epochAccountingActive) return (0, 0);
    uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
    uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
    int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
    if (netDelta > 0) {
      interest = uint256(netDelta);
    } else {
      loss = uint256(-netDelta);
    }
  }
