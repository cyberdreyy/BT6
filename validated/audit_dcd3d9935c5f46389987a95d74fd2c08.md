### Title
Unconditional `savedCallbacks` overwrite in `HandleLegacyUserMessage` enables cross-user response hijacking via MessageId collision, worsened by uncleaned entries on partial DON fan-out failure - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores the caller's `callback` in `h.savedCallbacks[msg.Body.MessageId]` unconditionally, without checking whether an entry for that `MessageId` already exists, unlike sibling handlers (`confidentialrelay`, `http_trigger_handler`, `vault`) which explicitly reject duplicate/in-flight request IDs. When `don.SendToNode` fails for some DON members, the error is joined and returned to the gateway, which short-circuits and never calls `callback.Wait()` for that request, yet the stale `savedCallbacks` entry is never removed — leaving it live until a node eventually responds or `pruneCallbacks` evicts it after `CallbackMaxAgeSec`. This widens the window during which a later request reusing the same `MessageId` can overwrite the entry, causing a DON node's asynchronous response (delivered via `handleWebAPITriggerMessage`) to be routed to the wrong caller's callback.

### Finding Description
`HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go:341-421) saves the callback before fan-out completes: [1](#0-0) 
No lookup/rejection of an existing entry occurs (contrast with `confidentialrelay/handler.go`'s "request ID already exists" check and `http_trigger_handler.go`'s "in-flight request" check). The response is later delivered by matching solely on `msg.Body.MessageId`: [2](#0-1) 

`MessageId` is fully attacker-controlled client input, only length/format-validated (not uniqueness-checked) in `Message.Validate()`: [3](#0-2) 

The gateway entry point calls `HandleLegacyUserMessage` and, if it returns a non-nil error (which happens whenever any `don.SendToNode` call fails, due to `errors.Join`), skips `callback.Wait()` entirely and returns an immediate error response to that caller — but the `savedCallbacks[MessageId]` entry set moments earlier is never cleaned up: [4](#0-3) 

Exploit flow: Attacker A sends request with `MessageId = X`. If one or more DON members fail to accept the send (rate limiting, transient connection drop, etc. — a normal operational condition, not requiring node compromise), `HandleLegacyUserMessage` returns an error; A's HTTP call gets an immediate error response, but `savedCallbacks[X]` (pointing to A's now-discarded callback) remains in the map, since delivery/cleanup only happens on `handleWebAPITriggerMessage` for a successful node response or via periodic `pruneCallbacks`. If a differently-timed request (from another user/session, or the same attacker probing a predictable/colliding ID scheme) later reuses `MessageId = X` before expiry, the map entry is silently overwritten, and whichever caller's callback is currently registered under `X` receives whatever node response next arrives tagged with that ID — including a response destined for another party's original request. Because `savedCallbacks` is a bare map keyed only by the caller-supplied string with no sender binding, a `MessageId` collision (whether accidental among legitimate clients or intentionally crafted by an attacker who can predict/replay another party's ID) causes a genuine cross-caller response confusion: an attacker's registered callback would receive the DON's response payload intended for a different request.

### Impact Explanation
This matches the "cross-user response confusion" bounty class: an unauthorized party can receive response data (including trigger/webapi payloads) generated for another user's request, purely by causing/timing a `MessageId` collision. The uncleaned entry from a failed fan-out extends the exploitable time window relative to the normal fast-path (where a successful single-node reply deletes the entry almost immediately), materially increasing collision feasibility. It does not, on its own, disclose credentials or grant admin privileges, and requires the attacker to guess or otherwise cause reuse of another party's `MessageId`, which is a significant precondition.

### Likelihood Explanation
Requires: (1) ability to trigger or observe a partial `SendToNode` failure (achievable by any unauthenticated/low-privileged caller via normal request volume, since node connection drops/timeouts are a realistic operational occurrence and are not attacker-privileged actions); (2) the ability to predict or reuse another caller's `MessageId` within the stale-entry lifetime (bounded by `CallbackMaxAgeSec`/`MaxSavedCallbacks` pruning). Because `MessageId` is entirely client-chosen with no server-side randomness or uniqueness enforcement, and clients often use predictable schemes (sequence numbers, workflow-derived IDs, timestamps), collision is plausible in specific deployments, though not universally trivial to force against a truly random UUID-choosing victim. This lowers overall likelihood to moderate but the underlying missing-duplicate-check is a code-level defect regardless of the specific attack precondition.

### Recommendation
In `HandleLegacyUserMessage`, check for an existing `savedCallbacks[msg.Body.MessageId]` entry under the lock and reject the request (mirroring the "request ID already exists"/"in-flight request" pattern used in `confidentialrelay/handler.go` and `http_trigger_handler.go`) instead of overwriting silently. Additionally, on fan-out failure (all-or-partial), proactively delete the just-inserted `savedCallbacks` entry before returning the error, so a failed request never leaves a stale, hijackable callback registration.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build handler with `donConfig.Members` = 3 nodes; mock `don.SendToNode` to return `nil` for node1/node2 and an error for node3.
2. Call `handler.HandleLegacyUserMessage(ctx, msgWithID("X"), callbackA)`; assert returned `err != nil` (joined error).
3. Lock `handler.mu`, assert `handler.savedCallbacks["X"]` still exists and its `Callback == callbackA`, proving the entry survives despite the caller never awaiting a response (no matching call to `callback.Wait` reachable from the gateway path when `err != nil`).
4. Call `handler.HandleLegacyUserMessage(ctx, msgWithID("X"), callbackB)` (simulating a second, differently-timed request reusing the same MessageId) with all `SendToNode` mocks returning `nil`; assert no "duplicate"/"already exists" error is returned.
5. Simulate a node response for MessageId "X" via `handler.handleWebAPITriggerMessage(...)` and assert it is delivered to `callbackB` (`callbackB.Wait` returns the payload) — demonstrating that whichever caller currently occupies the map slot receives the DON response, regardless of which caller's request the response was actually destined for.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
