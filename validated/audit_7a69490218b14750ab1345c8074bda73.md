### Title
Unfunded pre-default instant-withdraw receipts escape the recovery haircut through the aggregate `instantWithdrawsRequests` claim path - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The `unearth` bug class is "identity/containment checks done on an unnormalized representation": a path with `../` segments bypasses `is_within_directory` because the check runs on the raw string instead of the canonical path. The credit-vault analog lives in `IdleCreditVault`: instant-withdraw receipts have two representations — a normalized per-epoch ledger (`instantWithdrawsRequestsByEpoch`) and an unnormalized aggregate (`instantWithdrawsRequests`). Default finalization only pulls the *current* epoch's instant claims into the haircut basis, while `claimInstantWithdrawRequest` pays the aggregate remainder at par. An unfunded instant receipt keyed to an older epoch slips past the recovery containment check and is paid 100% from funds belonging to funded claimants — direct theft / insolvency.

### Finding Description
Instant withdraw requests are recorded twice: per user aggregate `instantWithdrawsRequests[_user]` and per user per request-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, plus a per-epoch global `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

`defaultPendingClaimBasis` — the "containment check" deciding what is inside the haircut — only includes `instantWithdrawClaimsByEpoch[epochNumber]`, i.e., claims made in the *defaulted* epoch [2](#0-1) . Instant receipts requested in an earlier epoch and never funded (borrower never called `collectInstantWithdrawFunds`, so `pendingInstantWithdraws` still holds them) are outside that basis, because their `instantWithdrawsRequestsByEpoch` key is a stale epoch number that is never re-keyed [3](#0-2) .

At claim time, `claimInstantWithdrawRequest` first clears only the default-epoch slice (`_claimDefaultedInstantWithdrawRequest` decrements the aggregate by exactly `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`), then pays *whatever remains* of `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim` [4](#0-3) . The stale-epoch unfunded receipt was never haircut and never funded — the aggregate path treats it as "already funded" because only the default epoch's entry was normalized.

`_transferFundedClaim` only protects `defaultRecoveryReserve`; it pays from any non-reserve balance [5](#0-4) . That non-reserve balance is exactly the underlyings collected for *other* users' funded withdraw receipts. So the stale receipt drains funded claimants' backing at 100¢ while every defaulted claimant receives `defaultRecoveryPrice < 1` [6](#0-5) .

Existing guards do not stop it: `requestWithdraw`/`requestInstantWithdraw` don't require prior instant claims to be cleared (only post-default requests do, via `_hasWithdrawRequest`) [7](#0-6) , and `pendingInstantWithdraws != 0` merely enables `defaultInstantWithdrawsFinalized`, which keys claims to the *current* epoch only [8](#0-7) .

### Impact Explanation
Attacker (any KYC'd tranche holder) requests an instant withdraw, the honest borrower/manager simply never funds it, epochs roll over, the borrower later defaults, and recovery is finalized. The attacker's stale unfunded receipt is paid at par, stealing underlyings reserved for other users' funded withdraw/instant claims. Loss = attacker's unfunded instant amount, capped by available non-reserve funded balance. If no non-reserve balance exists, `_transferFundedClaim` reverts `NotAllowed`, permanently freezing the attacker's receipt and blocking their defaulted-epoch claim settlement order — still a permanent-freeze impact on users behind them in claim order who share the same funded pool.

### Likelihood Explanation
Requires (a) an instant withdraw request that stays unfunded across at least one epoch boundary — plausible whenever the instant queue is only partially funded or the borrower is distressed (precisely the pre-default environment), and (b) an eventual default with `pendingInstantWithdraws != 0`. Both are honest-actor sequences; the attacker only needs to hold the unclaimed receipt and be among the first to claim after `finalizeDefaultRecovery`, since the attacker's par payout wins the race against funded claimants for the same non-reserve balance.

### Recommendation
Normalize before validation, like the upstream fix: include *all* outstanding instant claims in the default basis. Either (1) aggregate `instantWithdrawsRequests` globally (add a `totalInstantWithdrawsRequests` counter) and use it in `defaultPendingClaimBasis` instead of `instantWithdrawClaimsByEpoch[epochNumber]`, tracking the prefunded portion across all epochs in `_defaultPrefundedInstantReserve`; or (2) in `_claimDefaultedInstantWithdrawRequest`, iterate/close *all* per-epoch entries for the user — e.g., re-key stale entries to the default epoch at finalization — so `claimInstantWithdrawRequest` cannot pay a defaulted-but-unfunded remainder through the funded path. Additionally reject new claims paying unfunded remainder: require `instantWithdrawsRequests[_user] == 0` after the defaulted-epoch clear unless the remainder was provably funded.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
function testStaleEpochInstantReceiptEscapesHaircut() external {
    // epoch 0 buffer: attacker deposits AA, honest user2 deposits AA
    uint256 amount = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                    // attacker (this)
    _depositWithUser(user2, amount);              // honest funded claimant

    // attacker requests instant withdraw during buffer; borrower never funds it
    uint256 instant = 50_000 * ONE_SCALE;
    cdoEpoch.requestInstantWithdraw(instant, address(AAtranche));
    // pendingInstantWithdraws == instant; instantWithdrawsRequestsByEpoch[attacker][0] == instant

    // epoch rolls over unfunded (stopEpoch without collectInstantWithdrawFunds)
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _stopCurrentEpochWithApr(10e18);              // epochNumber -> 1, receipt stays keyed at 0

    // user2 files a normal withdraw that *is* funded at a later stop
    cdoEpoch.requestWithdraw(tranche2Bal, address(AAtranche));
    // ... run epoch, borrower funds pendingWithdraws + user2's instant funding ...
    // strategy now holds non-reserve balance backing user2's funded claim

    // a tiny current-epoch instant request keeps pendingInstantWithdraws != 0
    // borrower defaults; owner finalizes
    vm.prank(owner);
    cdoEpoch.finalizeDefault(recovered, source);  // basis misses epoch-0 instant claim

    // attacker claims: epoch-1 slice cleared, then epoch-0 `instant` paid AT PAR
    uint256 balPre = underlying.balanceOf(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - balPre, instant * defaultRecoveryPrice / 1e18);
    // attacker received ~`instant` at 100% while defaultRecoveryPrice << 1e18,
    // draining funded backing that user2's claim was entitled to
}
```

Caveat: I did not trace `IdleCDOEpochVariant.finalizeDefault`/`collectInstantWithdrawFunds` call ordering exhaustively; the PoC hinges on `pendingInstantWithdraws` surviving an epoch rollover unfunded (which `collectInstantWithdrawFunds` being optional implies) and on non-reserve strategy balance existing to absorb the par payout — verify both on the fork harness.

    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
