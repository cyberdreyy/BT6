### Title
EI-authenticated caller can trigger job runs on an arbitrary job (not just the job its EI credential is bound to) via `POST /v2/jobs/:ID/runs` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets the same `SessionUserKey` context value used for regular users (`clsessions.User{Role: clsessions.UserRoleRun}`), so `auth.GetAuthenticatedUser(c)` returns `ok == true` for EI-authenticated requests. `PipelineRunsController.Create` uses this `isUser` flag — intended to gate the "int job ID" run path to real users only — but it is satisfied by EI callers too, and the handler never checks that the EI credential is associated with the specific job ID in the path. Any valid EI access key/secret can therefore trigger a run on any job by integer ID, not just the job it was registered for.

### Finding Description
The route is registered as:
```go
userOrEI := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(),
    auth.AuthenticateExternalInitiator,
    auth.AuthenticateByToken,
    auth.AuthenticateBySession,
))
userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))
``` [1](#0-0) 

`auth.RequiresRunRole` only checks `user.Role != UserRoleView`, i.e. it accepts any authenticated principal with run-or-higher role, with no notion of which job that principal is scoped to: [2](#0-1) 

`AuthenticateExternalInitiator` looks up the EI by access key, verifies the secret, but then sets the *same* session key used by the user-based auth methods:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [3](#0-2) 

`GetAuthenticatedUser` simply reads that same key: [4](#0-3) 

In `PipelineRunsController.Create`, the "EI vs user" distinction is made solely via `isUser := auth.GetAuthenticatedUser(c)`, with a comment stating "only users are allowed to run jobs using int IDs - EIs not allowed":
```go
_, isUser := auth.GetAuthenticatedUser(c)
if isUser {
    var jobID int32
    jobID64, err := strconv.ParseInt(idStr, 10, 32)
    if err == nil {
        jobID = int32(jobID64)
        jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
        ...
    }
}
``` [5](#0-4) 

Because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` is `true` for EI-authenticated requests as well, defeating the intended EI-vs-user gate. There is no code anywhere in `Create` that reads `auth.GetAuthenticatedExternalInitiator(c)` and cross-checks the EI's associated job against `c.Param("ID")`. `prc.App.RunJobV2(ctx, jobID, nil)` is called with whatever integer job ID is in the path, regardless of which job the EI credential was registered for.

### Impact Explanation
An external initiator credential registered for job A can be used to trigger pipeline runs on any other job B in the node (by integer job ID) via `POST /v2/jobs/<jobB_ID>/runs`. This is an authorization/request-binding bypass allowing unauthorized triggering of arbitrary job runs — potentially causing unwanted on-chain transactions, unintended fund movement, or resource abuse on jobs the EI was never authorized to run. This corresponds to Chainlink's "unauthorized job run" / authorization bypass impact class.

### Likelihood Explanation
Preconditions are minimal: attacker only needs one valid EI access key/secret pair for any job (job A) — no admin, edit, or elevated privileges are required, since EI credentials are inherently run-role scoped. The exploit is a single unauthenticated-from-user-role-perspective HTTP POST with the EI headers and an arbitrary job ID in the path; it is fully repeatable and requires no timing or race conditions.

### Recommendation
In `PipelineRunsController.Create`, distinguish EI-authenticated callers from real users explicitly (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` first / use a dedicated context flag set only by `AuthenticateBySession`/`AuthenticateByToken`), and when the caller is an EI, verify that the EI record returned by `FindExternalInitiator` is bound to the job identified by `c.Param("ID")` before calling `RunJobV2`. Alternatively, avoid overloading `SessionUserKey` for EI identities and require a distinct check in `Create`/`RequiresRunRole`-derived logic that never treats an EI as a generic user for arbitrary integer-ID job runs.

### Proof of Concept
Handler-level integration test plan (Go, using `httptest`/`gin` similar to existing `pipeline_runs_controller_test.go` and `auth_test.go` patterns):
1. Set up two jobs, Job A and Job B, with distinct integer IDs.
2. Register an `ExternalInitiator` (access key/secret) associated only with Job A in the test fixtures (via `bridges.ExternalInitiator`/`FindExternalInitiator` mocks or DB fixture).
3. Build a router with `v2Routes` wired to a test `chainlink.Application` (mocked `RunJobV2`, `JobORM`, `PipelineORM`).
4. Send `POST /v2/jobs/<jobB.ID>/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to Job A's EI credentials (see `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`).
5. Assert current (buggy) behavior: response is `200`/success and `App.RunJobV2` was invoked with Job B's ID — demonstrating the bypass.
6. Expected/fixed behavior: response should be `403 Forbidden` (or `404`), and `RunJobV2` must not be called, because the EI credential is not bound to Job B.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func (prc *PipelineRunsController) Create(c *gin.Context) {
	ctx := c.Request.Context()
	respondWithPipelineRun := func(jobRunID int64) {
		pipelineRun, err := prc.App.PipelineORM().FindRun(ctx, jobRunID)
		if err != nil {
			jsonAPIError(c, http.StatusInternalServerError, err)
			return
		}
		res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
		jsonAPIResponse(c, res, "pipelineRun")
	}

	idStr := c.Param("ID")

	// Webhook runs used external job UUIDs; that job type has been removed.
	if _, err := uuid.Parse(idStr); err == nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, fmt.Errorf("cannot run job of type %q: %w", job.Webhook, job.ErrJobTypeRemoved))
		return
	}

	_, isUser := auth.GetAuthenticatedUser(c)
	// only users are allowed to run jobs using int IDs - EIs not allowed
	if isUser {
		// Is it an int32? Then process it regardless of type
		var jobID int32
		jobID64, err := strconv.ParseInt(idStr, 10, 32)
		if err == nil {
			jobID = int32(jobID64)
			jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
			if err != nil {
				jsonAPIError(c, http.StatusInternalServerError, err)
				return
			}
			respondWithPipelineRun(jobRunID)
			return
		}
	}

	jsonAPIError(c, http.StatusUnprocessableEntity, errors.New("bad job ID"))
