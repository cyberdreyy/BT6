### Title
Dust withdraw request permanently reverts `processWithdrawRequests`, freezing the epoch's queued withdrawals - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The external advisory describes an uncaught exception on a malformed packet that crashes the whole service. The closest analog in idle-tranches is `IdleCDOEpochQueue.processWithdrawRequests()`: a single malformed (dust-sized) withdraw request makes the aggregate processing call revert at the `Is0` check, aborting settlement for every honest withdrawal queued in that epoch. Because the revert happens before any state is written, and only each request's owner can remove it via `deleteWithdrawRequest`, the attacker can keep the epoch unprocessable indefinitely — and repeat the attack each epoch for negligible cost.

### Finding Description
`requestWithdraw(uint256 amount)` accepts any amount of tranche tokens from any allowed (KYC'd) wallet and adds it to `epochPendingWithdrawals[nextEpoch]`. There is no minimum amount check. [1](#0-0) 

During the buffer period the manager calls `processWithdrawRequests()`, which converts the entire pending tranche amount to underlyings via `_cdo.requestWithdraw(_pending, tranche)` and derives the epoch price: [2](#0-1) 

Tranche tokens have 18 decimals while underlying (e.g. USDC) has 6, and `_trancheToUnderlyings` divides by `ONE_TRANCHE`. An attacker deposits a normal amount, receives tranche tokens, and queues a withdraw request of a few wei of tranche tokens (`_pending` small enough that `_underlyingsRequested` rounds to 0, or that `price = underlyings * 1e18 / _pending` rounds to 0). `_epochPrice == 0` triggers `revert Is0()`. The test suite confirms this revert path exists (`testProcessWithdrawRequestsWith0Price` in `test/foundry/IdleCDOEpochQueue.t.sol:1431-1456`).

The revert rolls back everything, so `epochPendingWithdrawals[_epoch]` still contains the dust. `pendingClaims` is never set, so the epoch is not locked by the claims guard — it simply can never be processed while the dust sits there. `deleteWithdrawRequest` can only remove `msg.sender`'s own request (`userWithdrawalsEpochs[msg.sender][_requestEpoch]`), so the honest manager cannot evict the malicious dust. `isEpochWithdrawZero` cannot rescue the epoch either: it is only set later, inside `processWithdrawalClaims`, which is unreachable until `processWithdrawRequests` succeeds. [3](#0-2) 

### Impact Explanation
Temporary freezing of funds with a griefing amplifier:

- All honest tranche tokens queued for withdrawal in the poisoned epoch are stuck in the queue contract; `processWithdrawRequests` reverts on every call. Honest users must each discover the failure and call `deleteWithdrawRequest` to recover their tranche tokens, then re-queue in a later epoch — losing the epoch's settlement slot and paying extra gas.
- The attack costs the attacker only dust (a few wei of tranche tokens) and can be repeated every epoch, so the queue's withdrawal-processing path can be kept unusable indefinitely while `allowAAWithdrawRequest`/`allowBBWithdrawRequest` routes through the queue.
- The mitigation is partial: affected users retain a self-rescue path (`deleteWithdrawRequest` works even while the epoch is running, and direct `IdleCDOEpochVariant.requestWithdraw` remains available to allowed wallets), so this is temporary freezing / forced-UX-degradation rather than permanent loss of principal. Quantified worst case: the full `epochPendingWithdrawals[_epoch]` tranche balance is frozen for the duration between the manager's first failed processing attempt and each user's manual deletion, repeatable per epoch.

### Likelihood Explanation
Requires only a KYC-passing wallet (`_checkAllowed(msg.sender)`), a deposit to obtain tranche tokens, and a single `requestWithdraw(1)`-scale call — all unprivileged actions explicitly in scope. No privileged cooperation is needed; the manager's routine `processWithdrawRequests` call is the trigger, and it always reverts. The only reason this is not higher severity is the existence of the per-user `deleteWithdrawRequest` escape hatch.

### Recommendation
Handle dust/malformed pending amounts gracefully instead of reverting on the aggregate price:

- In `processWithdrawRequests`, when `_epochPrice == 0`, record the epoch as a terminal zero-price epoch (set `isEpochWithdrawZero[_epoch] = true`, zero out `epochPendingWithdrawals`, and refund the queued tranche tokens pro-rata or leave them claimable) — mirroring the handling already added for zero-price outcomes in `processWithdrawalClaims` — rather than reverting with `Is0`.
- Alternatively, enforce a minimum request size in `requestWithdraw` (e.g. `amount` must convert to ≥ 1 unit of underlying at the current virtual price) so a sub-underlying-wei request can never enter `epochPendingWithdrawals`.

### Proof of Concept
Foundry fork PoC sketch (same setup as `testProcessWithdrawRequestsWith0Price`, but with a real honest request alongside the dust one):

```solidity
function testDustWithdrawRequestBlocksEpochProcessing() external {
    _stopCurrentEpoch();                        // enter epoch #1 buffer

    // honest user deposits and queues a normal withdraw
    address user1 = makeAddr('user1');
    uint256 tranches1 = _depositWithUser(user1, 100e6);
    vm.prank(manager);
    cdoEpoch.startEpoch();                      // epoch #1 running
    _requestWithdrawWithUser(user1, tranches1); // honest request for epoch #2

    // attacker queues a malformed dust request in the same epoch
    address attacker = makeAddr('attacker');
    uint256 atkTranches = _depositWithUser(attacker, 1e6);
    vm.prank(attacker);
    queue.requestWithdraw(1);                   // 1 wei of tranche tokens

    _stopCurrentEpoch();                        // epoch #2 buffer

    // manager tries to settle all pending withdrawals: reverts every time
    vm.expectRevert(abi.encodeWithSelector(Is0.selector));
    vm.prank(manager);
    queue.processWithdrawRequests();

    // manager cannot delete the attacker's request; only attacker can
    // honest user1's tranche tokens stay frozen in the queue until user1
    // manually calls deleteWithdrawRequest(2) and re-queues next epoch.
}
```

Note: the exact dust threshold depends on the current tranche virtual price and decimals; `requestWithdraw(1)` is the extreme case, and any `_pending` for which `_underlyingsRequested * ONE_TRANCHE / _pending == 0` suffices.

```text
  function deleteWithdrawRequest(uint256 _requestEpoch) external {
    // if the epoch withdraw price is already set, withdrawal requests were already processed so
    // the withdraw request can't be deleted. Withdraw requests can be deleted even if the epoch is running
    _checkNotAllowed(epochWithdrawPrice[_requestEpoch] != 0 || isEpochWithdrawZero[_requestEpoch]);

    uint256 amount = userWithdrawalsEpochs[msg.sender][_requestEpoch];
    if (amount == 0) {
      return;
    }
    // reset user withdraw request for the epoch
    userWithdrawalsEpochs[msg.sender][_requestEpoch] = 0;
    // update pending withdraw requests
    epochPendingWithdrawals[_requestEpoch] -= amount;
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, amount);
  }
```
