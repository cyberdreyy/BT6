### Title
`get_mint_owner_and_additional_data` trusts `Mint` data from an unverified account owner, letting a stale/foreign account poison `getTokenAccountBalance` decimals - ([File: rpc/src/parsed_token_accounts.rs])

### Summary
`get_mint_owner_and_additional_data` and its helper `get_additional_mint_data` parse whatever account lives at a token account's `mint` pubkey as `StateWithExtensions::<Mint>` without ever checking that this account is owned by a known SPL Token program, unlike the sibling function `get_token_supply` which explicitly performs that owner check. Because a token account's embedded `mint` field is just a `Pubkey` that keeps pointing at an address even after that address is closed and reused for unrelated, attacker-controlled data, `getTokenAccountBalance` (and the other RPC callers of this helper) can end up trusting fabricated `decimals`/extension metadata from a completely unrelated program-owned account.

### Finding Description
`get_token_account_balance` in `rpc/src/rpc.rs` unpacks the caller-specified account as a `TokenAccount` and extracts its `mint` field directly from account bytes without any additional validation of that pubkey: [1](#0-0) 
It then calls `get_mint_owner_and_additional_data(&bank, mint)` and discards the returned owner (`let (_, data) = ...`): [2](#0-1) 

`get_mint_owner_and_additional_data` fetches whatever account currently resides at that pubkey and passes its raw bytes straight into `get_additional_mint_data`, again with no owner check: [3](#0-2) 
`get_additional_mint_data` only checks that `StateWithExtensions::<Mint>::unpack(data)` succeeds and then reads `decimals` (and any `InterestBearingConfig`/`ScaledUiAmountConfig` extensions) straight out of that buffer: [4](#0-3) 

This is inconsistent with `get_token_supply`, which explicitly verifies `is_known_spl_token_id(mint_account.owner())` before trusting the mint bytes: [5](#0-4) 

Because `Mint::unpack` only requires the fixed-length byte layout (82 bytes base, `is_initialized` flag set) to succeed — it does not verify the account's owner — any account of the right length whose bytes satisfy that shape will be accepted as "the mint," regardless of which program actually owns it. A `mint` pubkey field, once written into a `TokenAccount` at creation time, is never revalidated afterward, so if that address is later closed (e.g. via the real SPL-Token-2022 `MintCloseAuthority` extension, which requires `supply == 0`, i.e. all token accounts referencing it must already show zero balance) and the address is reused for an arbitrary program-owned account with attacker-chosen bytes, the stale, still-live `TokenAccount` that never got closed keeps pointing at that address. A subsequent `getTokenAccountBalance` call on that stale account will unpack the attacker-controlled bytes as a `Mint` and report fabricated `decimals` (and any fabricated `interest_bearing_config`/`scaled_ui_amount_config`), all without checking that the data actually still comes from a real SPL Token program-owned mint.

### Impact Explanation
This is a "wrong account data returned" issue: `getTokenAccountBalance`, `getTokenLargestAccounts`, and the `jsonParsed` encoding path in `get_parsed_token_accounts`/`get_parsed_token_account` (which reuses the same unchecked helper) can report decimals/extension metadata sourced from a non-Mint, unrelated program-owned account rather than a validated Mint. Given the SPL-Token supply-zero invariant needed to close and reuse a mint address, the raw token `amount` on the affected account is necessarily 0 at the point the stale reference becomes exploitable, so the numeric magnitude misreport is limited; the concretely reproducible impact is corrupted/fabricated `decimals` and extension-derived UI-amount formatting metadata returned for a real, still-live token account.

### Likelihood Explanation
Reaching this state requires only unprivileged, standard SPL-Token-2022 usage: creating a mint with the `MintCloseAuthority` extension, initializing a token account against it, driving its balance and the mint's supply to zero, closing the mint (freeing the address), and then creating any new account (owned by any program, including one the attacker deploys) at that address with a buffer matching `Mint::LEN`-shaped data (`is_initialized = true`, arbitrary `decimals`). All of this is achievable with a single unprivileged client issuing normal transactions and does not require validator/operator control or direct store mutation.

### Recommendation
In `get_additional_mint_data`/`get_mint_owner_and_additional_data` (`rpc/src/parsed_token_accounts.rs`), validate the mint account's owner against `is_known_spl_token_id` (as already done in `get_token_supply`) before unpacking it as `Mint` and before trusting its decimals/extension data; propagate an `invalid_params` error otherwise. Ensure all call sites (`get_token_account_balance`, `get_token_largest_accounts`, `get_token_program_id_and_mint`, `get_parsed_token_accounts`) rely on this validated owner rather than discarding it.

### Proof of Concept
Add a unit test in `rpc/src/parsed_token_accounts.rs` (or an integration test in `rpc/src/rpc.rs`) that:
1. Stores an account at pubkey `M` owned by an arbitrary non-token program id, containing exactly `Mint::LEN` bytes crafted with `is_initialized = 1` and `decimals = 250` (any bytes satisfying `StateWithExtensions::<Mint>::unpack`).
2. Stores a `TokenAccount` at pubkey `A`, owned by `spl_token_2022_interface::id()`, with `mint = M` and `amount = 0`.
3. Calls `get_mint_owner_and_additional_data(&bank, &M)` (or `JsonRpcRequestProcessor::get_token_account_balance(&A, None)`).
4. Asserts the call returns an error (or that decimals only ever originate from an account whose owner passes `is_known_spl_token_id`), rather than succeeding and returning `SplTokenAdditionalDataV2 { decimals: 250, .. }` derived from the foreign-owned account.

Fuzz variant: generate random `Mint::LEN`-sized buffers (forcing the `is_initialized` byte to `1`) and assert `get_additional_mint_data` always errors unless the underlying account owner is `spl_token_interface::id()` or `spl_token_2022_interface::id()`.

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}
