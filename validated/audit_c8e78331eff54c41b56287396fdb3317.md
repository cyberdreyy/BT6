### Title
Cross-user response hijacking via unauthenticated `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The `handler.savedCallbacks` map used to correlate a legacy `web_api_trigger` user request with its DON response is keyed solely by the caller-supplied, unauthenticated `MessageId` string, with no ownership binding and no existence/uniqueness check on write. An attacker who can predict or learn a victim's still-pending `MessageId` (whether freed by `pruneCallbacks` or simply overwritten while still pending) can register their own callback under that same ID and receive the victim's DON response instead of the victim.

### Finding Description
`HandleLegacyUserMessage` stores the caller's callback keyed purely by `msg.Body.MessageId`, an attacker-chosen field with no uniqueness enforcement: [1](#0-0) 

`api.Message.Validate()` only checks the ID's length/format, never its uniqueness or entropy, so any caller can pick any string as `MessageId`: [2](#0-1) 

When a DON node's trigger response arrives, `handleWebAPITriggerMessage` looks the callback up and delivers the response purely by `MessageId`, with no check that the response belongs to the same sender/request that registered the callback: [3](#0-2) 

`pruneCallbacks` deletes entries strictly by age/count under a mutex, with no mechanism (e.g., tombstoning, per-sender binding) to prevent a freed ID from being immediately reused by an unrelated caller: [4](#0-3) 

Because insertion at line 412 unconditionally overwrites `h.savedCallbacks[msg.Body.MessageId]`, the same class of bug is exploitable even without waiting for `pruneCallbacks`: if the attacker submits a request with the exact same `MessageId` as a victim's in-flight request, the attacker's callback silently replaces the victim's in the map. The `pruneCallbacks` timing in the question is one path to a freed slot, but it is not required — reuse works as soon as the ID string collides, whether the slot was freed by expiry/eviction (`pruneCallbacks`), by an already-arrived (matched-and-deleted) response, or simply overwritten while still pending. In all cases, the eventual DON response — which is only correlated via `msg.Body.MessageId` and is authenticated only as "sent by a legitimate DON node" (`HandleNodeMessage` checks `msg.Body.Sender != nodeAddr`, not which user it belongs to) — gets delivered to whichever caller currently owns that map slot: [5](#0-4) 

The exploit requires the attacker to know/predict a victim's `MessageId`, which the question grants as a precondition. Nothing in the map/response-matching design would prevent exploitation if that precondition holds, since there is no per-sender scoping of the callback map key.

### Impact Explanation
An attacker who collides `MessageId` with a legitimate victim can have the victim's `web_api_trigger` DON response (potentially containing sensitive trigger/workflow acknowledgment data) delivered to the attacker's own HTTP callback instead of the victim's, i.e., cross-user response interception / confused-deputy delivery of another user's data — matching the "cross-user response confusion" impact class called out in scope.

### Likelihood Explanation
Exploitability is entirely conditioned on the attacker's ability to predict/observe a victim's `MessageId` before the corresponding DON response arrives — the map has no per-sender partitioning and no uniqueness enforcement to prevent this regardless of that precondition being met. If callers use unpredictable/random IDs (as is typical for well-behaved SDKs, e.g. UUIDs), the practical likelihood is low; if a caller uses sequential/predictable/observable IDs (as in the reference scripts, e.g. `core/scripts/gateway/web_api_trigger/invoke_trigger.go`, which defaults `MessageId` to `"12345"`), collision is trivial. No authentication beyond a valid signature over the attacker's own arbitrary message is required, and the technique is repeatable.

### Recommendation
Scope `savedCallbacks` keys to `(Sender, MessageId)` rather than `MessageId` alone, or otherwise bind the callback to the caller's authenticated identity so a colliding/reused ID from a different sender cannot overwrite or intercept another user's pending callback. Additionally, reject `HandleLegacyUserMessage` calls that reuse a `MessageId` already present in `savedCallbacks` (return an explicit "duplicate/ID in use" error) instead of silently overwriting the map entry.

### Proof of Concept
Go handler-level test:
1. Call `handler.HandleLegacyUserMessage` for "victim" with `MessageId = "collide-1"` and callback `victimCb`; assert `savedCallbacks["collide-1"].Callback == victimCb`.
2. Before the DON responds, call `handler.HandleLegacyUserMessage` again with the same `MessageId = "collide-1"` but a different signer ("attacker") and callback `attackerCb`; assert (current buggy behavior) that `savedCallbacks["collide-1"].Callback` is now `attackerCb`.
3. Simulate the victim's DON response via `handler.HandleNodeMessage` with `resp.ID = "collide-1"`; assert (buggy) that `attackerCb.Wait()` receives the response payload originally destined for the victim, while `victimCb.Wait()` never fires.
4. After applying the fix (sender-scoped keys or duplicate-ID rejection), re-run the same steps and assert that step 2 either fails with a duplicate-ID error or stores the entry under a distinct key, and that the DON response in step 3 is delivered only to `victimCb`.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.

	return nil
}

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
