### Title
Reward-commission accounting fails to re-validate collector account type between calculation and distribution, allowing misdirected/burned validator rewards - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The custom-commission-collector feature (SIMD-0232) lets a vote account designate an arbitrary system-owned account as its `inflation_rewards_collector` / `block_revenue_collector` pubkey. Reward calculation records the collector's role via a boolean `is_vote_account` flag on `RewardCommission`, computed once during `redeem_delegation_rewards`. The distribution path (`load_and_reward_commission_accounts`, invoked later in `distribute_reward_commissions`) is a separate stage that re-derives the account's real on-chain type at a later point. Because the "role" flag captured at calculation time is not re-validated as authoritative — and is instead merged/accumulated across multiple stake delegations via `accumulate_lamports` based on `is_vote_account` mismatches — this is structurally the same bug class as the CodedEstate rental-type flaw: a shared record (the `RewardCommission`) carries a type discriminant (`is_vote_account`) that differentiates two categories of collector (system account vs. vote account) with different payout/burn rules, and the discriminant can become stale or attacker-influenced between when it is set and when it is consumed for fund movement.

### Finding Description
`RewardCommission.is_vote_account` is the discriminant analogous to `rental_type` in the C4 report. It is set once per stake-delegation reward record inside `redeem_delegation_rewards`: [1](#0-0) 

Many stake delegations that share the same `commission_pubkey` are merged together via `RewardsAccumulator::add_reward` / `accumulate_into_larger`, which calls `accumulate_lamports`: [2](#0-1) 

The code's own comment documents the exact "shared record, ambiguous type" scenario: [3](#0-2) 

Specifically: vote account A designates system account B as its collector. Later, B is allocated/initialized as vote account B and B sets itself as its own collector. At merge time, `accumulate_lamports` decides — purely from the `is_vote_account` booleans captured at redemption time for each delegation — whether A's commission gets burned or B's gets burned, and mutates the *shared* destination entry's `is_vote_account` flag. This mirrors the rental report's core defect: the same storage slot / discriminant is written by two different "types" of operations without an authoritative, single point of truth, and the actual payout instructions (`store_commission_accounts_partitioned`, later validated in `load_and_reward_commission_accounts`) trust the accumulated commission entry rather than re-deriving account type from current on-chain state at the moment of use.

The comment explicitly acknowledges that this can result in one validator's commission being silently burned instead of paid, and that the only backstop is a *second, independent* check inside `load_and_reward_commission_accounts` — meaning correctness depends on two disjoint code paths (accumulation-time flag and distribution-time validation) staying in sync, exactly the "two functions operating on a shared record without enforcing the discriminant consistently" pattern flagged in the external report.

### Impact Explanation
If the two validation stages (`accumulate_lamports` at calculation time vs. `load_and_reward_commission_accounts` at distribution time) diverge for any edge case — e.g. race between epoch-boundary account reallocation, VAT burns, or additional collector-eligibility rules added in future SIMDs that are not mirrored in `accumulate_lamports` — inflation/block-revenue rewards belonging to one validator's stake delegators could be silently redirected to burn or to the wrong collector account. This is a fund-misdirection bug class (validator/stakers do not receive rewards they are entitled to, or a collector receives rewards it should not), which matches the "loss of funds due to unenforced type discriminant" class in the source report. I could not fully verify `load_and_reward_commission_accounts` in the time available (search matched 33 occurrences in the file but I was unable to read its full body before running out of iterations), so I cannot confirm whether it fully closes every gap `accumulate_lamports` leaves open — this is an area requiring further review.

### Likelihood Explanation
Likelihood is moderate-low: the scenario requires an adversary to (a) get a vote account to designate a system account as collector, (b) subsequently initialize that same address as a new vote account with itself as collector, and (c) have both accounts accrue stake-delegation rewards within the same epoch merge window. This is a narrow, multi-step, deliberately-crafted setup rather than a single-transaction exploit, and the developers were clearly aware of it (hence the defensive comment and the "NOTE" about the secondary burn check). It is not an unprivileged, single-shot exploit path in the way the CodedEstate PoC was, but the underlying pattern (shared mutable record + type flag not authoritatively enforced) is present in production reward-accounting logic that runs every epoch for every validator.

### Recommendation
- Ensure `load_and_reward_commission_accounts` re-derives collector account type (system vs. vote account, and vote-account self-consistency) strictly from current bank state at distribution time, and treats that as the sole source of truth, ignoring/overriding the `is_vote_account` flag accumulated during calculation.
- Avoid merging `RewardCommission` entries across different stake delegations under a shared address before the collector's authoritative type has been finally validated; alternatively, key the accumulation by `(commission_pubkey, is_vote_account)` so mismatched roles cannot silently overwrite each other's burn/pay outcome.
- Add regression tests that simulate the "system account later becomes a vote account with itself as collector" sequence explicitly at the distribution boundary, not just at calculation time, to guarantee the two stages cannot diverge for future protocol changes.

### Proof of Concept
No standalone PoC was constructed for the agave repo; the analysis is based on static code inspection of the comment-documented edge case and the `accumulate_lamports`/`redeem_delegation_rewards` implementation cited above. Confirming exploitability would require simulating: (1) vote account A epoch rewards accrued with collector = system account B, (2) B being closed/reallocated and reinitialized as vote account B with `inflation_rewards_collector = B` in the same epoch, and (3) inspecting whether `load_and_reward_commission_accounts` prevents payout divergence from what `accumulate_lamports` computed. This step was not completed due to running out of tool-call iterations before reading the full `load_and_reward_commission_accounts` implementation.

fn accumulate_lamports(src: &RewardCommission, dst: &mut RewardCommission) {
    match (src.is_vote_account, dst.is_vote_account) {
        (false, true) => {
            // Don't accumulate, burn everything in the source
            // reward commission entry.
            //
            // NOTE: There shouldn't be any burned lamports in the
            // source entry, but we're defensive
            dst.burned_lamports = dst
                .burned_lamports
                .saturating_add(src.commission_lamports)
                .saturating_add(src.burned_lamports);
        }
        (true, false) => {
            // The commission lamports on the source are the only
            // ones that get distributed, all others get burned.
            //
            // NOTE: There shouldn't be any burned lamports in the
            // destination entry, but we're defensive
            dst.is_vote_account = true;
            dst.burned_lamports = dst
                .burned_lamports
                .saturating_add(dst.commission_lamports)
                .saturating_add(src.burned_lamports);
            dst.commission_lamports = src.commission_lamports;
        }
        _ => {
            // Normal case, just accumulate both
            dst.commission_lamports = dst
                .commission_lamports
                .saturating_add(src.commission_lamports);
            dst.burned_lamports = dst.burned_lamports.saturating_add(src.burned_lamports);
        }
    }
}
