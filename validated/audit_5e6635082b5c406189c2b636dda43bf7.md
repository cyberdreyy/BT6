### Title
Claimed instant-withdraw receipts stay in `instantWithdrawClaimsByEpoch`/`instantWithdrawsRequestsByEpoch`, inflating default-recovery basis and reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When a user claims a funded instant-withdraw request, `claimInstantWithdrawRequest` burns the receipt tokens and clears `instantWithdrawsRequests[_user]`, but it never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults and `finalizeDefaultRecovery` runs in the same epoch while other instant requests remain unfunded, those stale entries are counted twice: once as claim basis in `defaultPendingClaimBasis` and again as "already-held" reserve in `_defaultPrefundedInstantReserve`. The recovery price is computed over phantom tokens that were already paid out, so the reserve is insolvent and the stale user's later claim path reverts on underflow.

### Finding Description
The analog of CVE-2016-4077 (truncated data structure handled by a special case that frees memory twice) is the stale per-epoch receipt left behind by the funded-claim path, which is then re-consumed by the default-recovery special case.

1. `requestInstantWithdraw` records the request three ways: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]` [1](#0-0) .
2. `collectInstantWithdrawFunds` reduces `pendingInstantWithdraws` when the CDO funds the queue [2](#0-1) .
3. `claimInstantWithdrawRequest` pays the user and zeroes `instantWithdrawsRequests[_user]` only. The two per-epoch mappings are left intact [3](#0-2) . The only place those mappings are ever cleared is `_claimDefaultedInstantWithdrawRequest` [4](#0-3) .
4. On default, `defaultPendingClaimBasis` adds the full `instantWithdrawClaimsByEpoch[epochNumber]` — including receipts already claimed — to the recovery basis [5](#0-4) .
5. `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` and treats it as underlying already held by the strategy [6](#0-5) . For an already-claimed request those tokens left the contract, so `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` counts non-existent funds [7](#0-6) .
6. `defaultRecoveryPrice = reserveAmount / totalBasis` is therefore inflated, while the actual token balance is short by the claimed amount. `_transferDefaultRecovery` decrements `defaultRecoveryReserve` blindly [8](#0-7) , so earlier claimants (including the attacker re-claiming through `_claimDefaultedInstantWithdrawRequest`, whose stale `instantWithdrawsRequestsByEpoch` still reports the old basis as long as `instantWithdrawsRequests[_user]` still covers it) drain more than their fair share; the last claimants' transfers revert for lack of balance.

There is no guard preventing this: `_ensureDefaultRecoveryInitialized` only blocks when `pendingInstantWithdraws != 0`, which is exactly the precondition for the bug rather than a mitigation [9](#0-8) .

### Impact Explanation
Direct insolvency of the default-recovery reserve. Every underlying claimed through `claimInstantWithdrawRequest` in the default epoch is double-counted: it stays in the claim basis (diluting the recovery price less) while also being counted as held reserve (inflating the recovery price). Early recovery claimants are paid from funds owed to later claimants; once the balance is exhausted, remaining `_transferDefaultRecovery` calls revert, permanently freezing part of the recovery. Quantitatively the shortfall equals the total funded-and-claimed instant withdrawals of the default epoch — unbounded relative to recovered amount.

### Likelihood Explanation
Requires an instant-withdraw mode vault where (a) a user requests, is funded, and claims an instant withdrawal, and (b) the borrower defaults in the same epoch while `pendingInstantWithdraws != 0` (i.e., at least one other instant request was unfunded — the normal partial-liquidity case that makes instant withdrawals relevant). The attacker is an unprivileged KYC-passing lender performing only `requestInstantWithdraw` + `claimInstantWithdrawRequest`, then optionally re-claiming via `claimInstantWithdrawRequest` after finalization since the stale per-epoch basis still attributes the old amount to them. All privileged roles (manager, borrower, CDO) act honestly.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch accounting alongside the aggregate: set `instantWithdrawsRequestsByEpoch[_user][epoch]` to 0 for the request epoch (or track and iterate the user's request epochs) and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, mirroring what `_claimDefaultedInstantWithdrawRequest` does for the defaulted path. Alternatively, recompute `_defaultPrefundedInstantReserve`/`defaultPendingClaimBasis` from actually-unclaimed receipts.

### Proof of Concept
Foundry fork test sketch against `IdleCreditVault` (modeled on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testStaleInstantBasisInflatesRecovery() external {
    // epoch N running, instant withdraws enabled
    _stopCurrentEpochWithApr(10e18);
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);
    address user1 = makeAddr('user1');
    address user2 = makeAddr('user2');
    uint256 t1 = _depositWithUser(user1, 50e6);
    uint256 t2 = _depositWithUser(user2, 50e6);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // both request instant withdraws in epoch N
    _requestInstantWithdraw(user1, t1);
    _requestInstantWithdraw(user2, t2);
    // epoch stops; only user1's request gets funded via collectInstantWithdrawFunds
    _stopCurrentEpochWithApr(1e18); // triggers instant funding path partially

    // user1 claims funded instant receipt: mappings stay stale
    vm.prank(user1);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(strategy.instantWithdrawsRequests(user1), 0);
    assertGt(strategy.instantWithdrawsRequestsByEpoch(user1, strategy.epochNumber()), 0); // stale

    // borrower defaults before instant queue fully funded -> pendingInstantWithdraws != 0
    _triggerBorrowerDefault(); // honest borrower default, CDO calls _handleBorrowerDefault
    vm.prank(manager);
    cdoEpoch.finalizeDefaultRecovery(recovered, recoverySource);

    // reserve counted user1's already-paid tokens -> recoveryPrice inflated
    uint256 bal = underlying.balanceOf(address(strategy));
    uint256 owed = /* sum of defaulted claims at defaultRecoveryPrice */;
    assertLt(bal, owed); // insolvency: last claimant's _transferDefaultRecovery reverts
}
```

Key assertions: after step "user1 claims", `instantWithdrawClaimsByEpoch[epochNumber]` still contains `t1`'s basis; after `finalizeDefaultRecovery`, `defaultRecoveryReserve` exceeds `underlying.balanceOf(strategy)` by exactly the claimed amount, and the final recovery claim reverts.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
