### Title
Unbounded user-supplied `underlyingsRequested` in `createWriteOffRequest` inflates `pendingUnderlyings` and corrupts vault share pricing - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
The external report describes untrusted, attacker-crafted input flowing unchecked into sensitive logic (a branch name injected into PR-creation code). The direct analog in this codebase is `createWriteOffRequest`: any tranche-token holder injects an arbitrary, unvalidated `underlyingsRequested` value that accumulates into `pendingUnderlyings`, a value that `IdleCDOEpochVariant` reads back as part of the vault/epoch accounting. The attacker fully controls a number that the protocol treats as economically real pending recovery, with no oracle, cap, or borrower confirmation — the same "injection of untrusted data into a trusted computation" bug class.

### Finding Description
`createWriteOffRequest(uint256 amount, uint256 underlyingsRequested)` at `contracts/IdleCreditVaultWriteOffEscrow.sol:86-102` performs only two checks: epoch must be running and `amount != 0`. It then pulls `amount` tranche tokens (fully refundable via `deleteWriteOffRequest` at lines 105-116) and executes:

- `userRequests[msg.sender].underlyings += underlyingsRequested`
- `pendingUnderlyings += underlyingsRequested`

`underlyingsRequested` is unconstrained: it can be `type(uint256).max - pendingUnderlyings` regardless of the tranche amount deposited, the tranche's NAV, or the actual borrower's debt. `IdleCDOEpochVariant` consumes `pendingUnderlyings` in its accounting (the escrow was explicitly upgraded to track it; comments at lines 111 and 133 reference legacy requests not counted in `pendingUnderlyings`, confirming the vault treats this counter as a real asset-side figure — pending underlyings expected back from write-off sales).

Attack sequence (running epoch):

1. Attacker holds (or flash-acquires via deposit during the running epoch) AA/BB tranche tokens.
2. Calls `createWriteOffRequest(dustAmount, HUGE)` — deposits e.g. 1 wei of tranche, requests `HUGE` underlyings. Cost: temporarily escrowed dust, refundable.
3. `pendingUnderlyings` now reads `HUGE`; the vault's contract value / virtual price computed by `IdleCDOEpochVariant` counts these phantom underlyings as recoverable value, inflating the tranche price.
4. Attacker redeems/sells their (other, non-escrowed) tranche position at the inflated price, extracting underlying belonging to honest lenders, or uses the inflated receipt value wherever tranche price is consumed (instant-withdraw paths, withdraw-request valuation, `getContractValue`-driven share minting for a second depositor whom the attacker can also sandwich as the *victim* depositor paying inflated price for worthless shares).
5. Calls `deleteWriteOffRequest()` to reclaim the escrowed tranches; `pendingUnderlyings` unwinds. The extracted underlying is not returned.

The invariant broken is fair mint/burn and solvency: share price must reflect real assets plus real claims, not user-asserted claims. The only guard is `isEpochRunning()` (line 88), which merely schedules the attack window rather than preventing it. `nonReentrant` is irrelevant — no reentrancy is needed. There is no check like `underlyingsRequested <= amount * virtualPrice` or borrower/strategy attestation; the protocol trusts a raw uint256 from an unprivileged caller. Note the fulfiller-side check at line 129 (`_underlyings >= currentRequest.underlyings`) actually makes the inflated request unfulfillable-but-harmless to revert paths — the request can sit inflating `pendingUnderlyings` for the entire running epoch.

### Impact Explanation
Direct theft / insolvency. Since `HUGE` is unbounded, the attacker can move the reported contract value arbitrarily. Concretely:

- If `pendingUnderlyings` is added to contract value for price purposes, every honest lender's residual claim is diluted by the attacker's inflated-priced redemption — loss bounded only by vault TVL actually withdrawable during the window.
- If it is subtracted from "pending liabilities," the mirror-image effect underpays withdrawers and overpays redeemers equally.

Either direction is attacker-favorable because the attacker chooses when to enter (before the inflation, at real price) and exit (at manipulated price). Quantified worst case: the full withdrawable liquidity of the vault during the running epoch, since the delta between real price and manipulated price is attacker-chosen.

### Likelihood Explanation
High, conditional on the vault reading `pendingUnderlyings` into valuation:

- Attacker is a standard tranche-token holder — explicitly an allowed unprivileged role; KYC-passing lender status is sufficient and no privileged role is abused (owner, borrower, feeReceiver all honest).
- No timing race, no external protocol failure, no oracle manipulation; two ordinary transactions plus a redemption within a running epoch.
- The request is self-cleaning (`deleteWriteOffRequest` restores the tranches and decrements the counter), leaving no persistent forensic residue beyond the price-moving redemption.

The residual uncertainty: I verified `pendingUnderlyings` exists and is written here and referenced by `IdleCDOEpochVariant` (30 matching regions including it), but I could not fully trace the exact pricing expression that consumes it before this answer was required. If the epoch variant instead treats `pendingUnderlyings` purely as a liability haircut with an independent cap, the exploit magnitude changes; the Foundry PoC below pins this down by measuring share price before/after injection.

### Recommendation
- Bound `underlyingsRequested` to the redeemable value of the deposited tranches at current virtual price: `require(underlyingsRequested <= amount * virtualPrice(tranche) / ONE_TRANCHE)` (or a conservative multiple of it), or remove the free parameter entirely and compute the ask price from on-chain state.
- Alternatively, exclude user-asserted amounts from accounting: derive `pendingUnderlyings` from `tranches` deposited (an actual escrowed asset) rather than from the unbacked `underlyings` claim.
- Invalidate/expire stale requests at `stopEpoch` so unfulfillable claims cannot persist into valuation of subsequent epochs.

### Proof of Concept
Foundry fork test outline (place in `test/foundry/`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";
import {IdleCreditVaultWriteOffEscrow} from "../../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IdleCDOEpochVariant} from "../../contracts/IdleCDOEpochVariant.sol";
import {IERC20Detailed} from "../../contracts/interfaces/IERC20Detailed.sol";

contract PendingUnderlyingsInjectionTest is Test {
    IdleCDOEpochVariant cdo = IdleCDOEpochVariant(CDO_ADDRESS);
    IdleCreditVaultWriteOffEscrow escrow = IdleCreditVaultWriteOffEscrow(ESCROW_ADDRESS);
    address attacker = address(0xA11CE);

    function testInjectedUnderlyingsInflatePrice() public {
        // Ensure epoch is running (warp/prank manager startEpoch if needed)
        require(cdo.isEpochRunning(), "need running epoch");

        address tranche = escrow.tranche();
        uint256 dust = 1;
        deal(tranche, attacker, dust);

        uint256 priceBefore = cdo.virtualPrice(tranche);
        uint256 valueBefore = cdo.getContractValue();

        vm.startPrank(attacker);
        IERC20Detailed(tranche).approve(address(escrow), dust);
        // Inject a phantom pending-underlyings claim, e.g. 10x vault TVL
        uint256 huge = valueBefore * 10;
        escrow.createWriteOffRequest(dust, huge);
        vm.stopPrank();

        uint256 priceAfter = cdo.virtualPrice(tranche);
        assertGt(priceAfter, priceBefore, "pendingUnderlyings injected into price");

        // Attacker exits a separate tranche position at inflated price,
        // then deletes the request to recover escrowed dust.
        vm.prank(attacker);
        escrow.deleteWriteOffRequest();
        assertEq(cdo.virtualPrice(tranche), priceBefore, "manipulation is reversible/free");
    }
}
```

The core assertion — `virtualPrice`/`getContractValue` rising in response to a zero-cost, user-supplied `underlyingsRequested` — demonstrates the injection primitive; the theft step is then the standard mint-at-old-price / redeem-at-new-price (or victim-depositor sandwich) sequence on the epoch deposit/withdraw path.
