## Analog Found: Cheap zero‑lamport account writes inflate AccountsDb's `clean_accounts` candidate set at disproportionate validator cost

### Title
Unprivileged users can cheaply spam zero-lamport account writes to bloat AccountsDb's clean-candidate set, forcing disproportionate index-scan work on every validator's background cleaner - ([File: accounts-db/src/accounts_db.rs])

### Summary
The reported Noya bug lets an attacker call a cheap, side-effect-free `withdraw(0, ...)` to append entries to an on-chain queue that a privileged "keeper" must later process at much higher cost per entry (`calculateWithdrawShares` re-derives TVL for every queued item). The same cost asymmetry exists in Agave: any ordinary transaction that drives an account's rooted balance to zero is trivially cheap (it only pays the network's flat transaction fee, and can even *recover* lamports), yet each such zero-lamport write is unconditionally queued into `uncleaned_pubkeys`/`dirty_stores` for `AccountsDb::clean_accounts`, which every validator's background service must scan and reconcile against the accounts index.

### Finding Description
When the write cache is flushed for a rooted slot, every account touched in that slot (or specifically every zero-lamport account, depending on the reclaim path) is unconditionally added to `uncleaned_pubkeys`: [1](#0-0) 

There is no gating on how many distinct pubkeys/slots a given transaction stream can inject into this set — a user can, in successive slots, transfer an account's entire balance out (zeroing it) and then re-fund/re-zero it again, generating a fresh "dirty" entry each time at minimal cost (a system `Transfer` instruction is cheap, and unlike locking funds in a stake/nonce account, zeroing an already-funded account costs nothing beyond the transaction fee).

Every one of these queued pubkeys is later consumed by `construct_candidate_clean_keys`, which builds per-bin candidate maps from `dirty_stores` and `uncleaned_pubkeys`: [2](#0-1) 

`clean_accounts` then performs an `accounts_index.scan()` for *every* candidate pubkey, including calls to `latest_slot`, `get_entries_up_to_inclusive`, and potentially `collect_reclaims`, all of which are asymptotically more expensive than the cost the attacker paid to enqueue the entry: [3](#0-2) 

This mirrors the Noya `withdrawQueue` pattern precisely: a cheap, unprivileged write operation (`withdraw(0, ...)` / zero-lamport transfer) appends to an internal queue (`withdrawQueue` / `uncleaned_pubkeys`+`dirty_stores`) that a privileged/background actor (the keeper / `AccountsBackgroundService::clean_accounts`) must later process with cost proportional to queue length, not to the cost paid to grow it.

### Impact Explanation
`clean_accounts` runs continuously in the background on **every validator**, not a single "keeper," so a sustained stream of low-cost zero-lamport account churn increases the size of `candidates`/`dirty_stores` that must be scanned every clean cycle on the entire cluster simultaneously. This degrades clean-cycle throughput cluster-wide, increases index memory/CPU pressure, and can delay the reclamation of storage entries, amplifying resource consumption asymmetrically relative to the attacker's transaction fee cost. This is a resource-exhaustion / compute-metering-bypass class issue rather than a fund-theft issue.

### Likelihood Explanation
Reachable via ordinary, unprivileged system-program transactions (no special account, no elevated stake, no privileged CPI): any signer can repeatedly transfer an account's balance to zero and back in successive rooted slots, using only the base per-signature fee. No feature gate or minimum-balance restriction prevents this specific pattern from generating new `uncleaned_pubkeys`/`dirty_stores` entries per slot.

### Recommendation
- Rate-limit or dedupe how many times the same pubkey can re-enter `uncleaned_pubkeys`/`dirty_stores` within a bounded window relative to actual account state churn.
- Consider charging additional compute/fee cost proportional to the expected downstream index-scan cost for zero-lamport account writes (similar to rent-exempt minimum enforcement preventing cheap account creation spam).
- Bound the total size of the candidate set processed per `clean_accounts` invocation and defer overflow to subsequent cycles, so a burst of cheap zero-lamport writes cannot inflate a single cleaning pass disproportionately.

### Proof of Concept
1. Fund account `A` (owned by System Program) with a small balance.
2. In slot `N`, submit a `Transfer` instruction moving `A`'s entire balance to another account, zeroing `A` — cost: one base fee.
3. Root slot `N`; on cache flush, `A`'s pubkey (zero-lamport) is inserted into `uncleaned_pubkeys` per `accounts-db/src/accounts_db.rs:4559-4574`.
4. Re-fund `A` in slot `N+1` with a minimal transfer, then zero it again in slot `N+2`; repeat across many slots/accounts.
5. Each iteration costs only network fees, yet each contributes a new candidate entry that `clean_accounts` (`accounts-db/src/accounts_db.rs:1564-1590`, `1927-2004`) must scan on the next cleaning pass across all validators, demonstrating the cost asymmetry between the cheap write and the expensive background reconciliation it forces.
