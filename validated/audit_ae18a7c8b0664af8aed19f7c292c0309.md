## Finding

Based on my investigation, this describes a real, but narrow, accounting inconsistency in `delegation_pool.move`. I was not able to fully trace `stake.move`'s exact epoch-renewal timing logic before running out of iterations, so I flag that specific detail as unverified, but the core code path is confirmed.

### Title
Commission-rate flip in `synchronize_delegation_pool` is gated on wall-clock time, not on actual stake-pool lockup rollover, letting an unprivileged caller apply the new commission percentage before its lockup cycle has truly ended - (File: `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary
`synchronize_delegation_pool` is a permissionless `public entry fun` callable by anyone, including any delegator, with no ownership/operator check [1](#0-0) . At the end of the call, it swaps `pool.operator_commission_percentage` to the scheduled new value purely based on `is_next_commission_percentage_effective`, which is a wall-clock timestamp comparison unrelated to whether the underlying stake pool's lockup cycle has actually rolled over: [2](#0-1) 

```
if (is_next_commission_percentage_effective(pool_address)) {
    pool.operator_commission_percentage = borrow_global<NextCommissionPercentage>(
        pool_address
    ).commission_percentage_next_lockup_cycle;
}
```

and `is_next_commission_percentage_effective` itself is defined purely by comparing `timestamp::now_seconds()` to a stored `effective_after_secs`: [3](#0-2) 

`effective_after_secs` is set once, at schedule time, to `stake::get_lockup_secs(pool_address)` — the *current* lockup's expiration timestamp, not the actual future rollover event: [4](#0-3) 

Whether the lockup cycle has *actually* ended on the stake pool (i.e., pending_inactive stake has been inactivated) is instead determined inside `calculate_stake_pool_drift` by comparing `stake::get_stake`'s live `inactive` amount to `pool.total_coins_inactive` (`lockup_cycle_ended = inactive > pool.total_coins_inactive`), which only becomes true after an epoch/reconfiguration event actually processes the lockup renewal on the stake pool: [5](#0-4) 

### Finding Description
The two gates — "is the new commission percentage effective" (time-based, `effective_after_secs`) and "has the lockup cycle actually ended" (state-based, `lockup_cycle_ended`) — are computed independently and are not required to be equal at the moment `synchronize_delegation_pool` executes. `calculate_stake_pool_drift` (called first) correctly still uses `pool.operator_commission_percentage` (the *old* rate) to commission whatever reward drift has accrued so far, whether or not the lockup has ended yet [6](#0-5) . But immediately after, the function unconditionally swaps in the new percentage as long as wall-clock time has passed `effective_after_secs`, regardless of whether `lockup_cycle_ended` was true in this same call.

Because `synchronize_delegation_pool` has no permission check, any unprivileged delegator can call it exactly at (or right after) the timestamp when `effective_after_secs` is reached but before the stake pool's own lockup has actually rolled over (which only happens once an epoch/reconfiguration event processes the pool). Doing so flips `pool.operator_commission_percentage` to the new value while the delegation pool is still in the *same*, not-yet-ended observed lockup cycle (`pool.observed_lockup_cycle` unchanged, `lockup_cycle_ended == false` in that call). Any further reward drift accrued in the remaining tail of that still-active lockup cycle — before the real lockup rollover eventually happens — will then be commissioned at the *new* rate instead of the rate that was supposed to govern the entirety of that lockup cycle.

### Impact Explanation
This corrupts the commission split (`commission_active`/`commission_pending_inactive`) computed by later `calculate_stake_pool_drift` calls for the tail of the still-ongoing lockup cycle: value is shifted between the operator/beneficiary and delegators using a rate that does not match the intended "next lockup cycle" semantics baked into `update_commission_percentage`'s design and its `ETOO_LATE_COMMISSION_CHANGE`/buffer checks [7](#0-6) . This affects the "earn/commission" value-preservation invariant across active/pending_inactive accounting called out in scope, since stake earned within the same, not-yet-closed lockup cycle can end up split under two different commission percentages depending purely on when an arbitrary, unprivileged address chooses to call `synchronize_delegation_pool`.

### Likelihood Explanation
Triggering the early flip requires only a permissionless call to `synchronize_delegation_pool(pool_address)` timed between `effective_after_secs` and the actual on-chain lockup rollover (next epoch/reconfiguration touching that pool). Any address can attempt this by monitoring `is_next_commission_percentage_effective` (a `#[view]` function) and firing the call as soon as it turns true. The size of the exploitable window (bounded by epoch duration relative to lockup duration) and its practical magnitude of value shifted depend on `stake.move`'s epoch/lockup-renewal cadence, which I could not fully verify within available tool calls — this should be independently confirmed by tracing `stake::on_new_epoch`/lockup renewal against `staking_config`'s epoch duration before treating this as high severity.

### Recommendation
Gate the `pool.operator_commission_percentage` swap in `synchronize_delegation_pool` on `lockup_cycle_ended` (the state-based signal already computed by `calculate_stake_pool_drift`) rather than, or in addition to, the purely time-based `is_next_commission_percentage_effective` check, so the new commission rate only takes effect once the delegation pool's observed lockup cycle has actually advanced.

### Proof of Concept
1. Owner calls `update_commission_percentage` to schedule a new commission percentage; `effective_after_secs` is set to the current `stake::get_lockup_secs(pool_address)` [8](#0-7) .
2. Advance the chain clock (via test/`timestamp`) to exactly `effective_after_secs` without triggering the epoch/reconfiguration event that actually rolls over the stake pool's lockup (so `stake::get_stake`'s `inactive` has not yet increased).
3. Any unprivileged address calls `synchronize_delegation_pool(pool_address)`. Observe: `calculate_stake_pool_drift` returns `lockup_cycle_ended == false` (correct, old cycle still active) but the trailing check flips `pool.operator_commission_percentage` to the new value [2](#0-1) .
4. Accrue more rewards within the same, still-not-rolled-over lockup cycle and call `synchronize_delegation_pool` again; assert that `commission_active`/`commission_pending_inactive` for this still-open cycle were computed using the *new* percentage, not the old one that should have applied to the entirety of the not-yet-ended lockup cycle.

    fun calculate_stake_pool_drift(pool: &DelegationPool): (bool, u64, u64, u64, u64) {
        let (active, inactive, pending_active, pending_inactive) = stake::get_stake(get_pool_address(pool));
        assert!(
            inactive >= pool.total_coins_inactive,
            error::invalid_state(ESLASHED_INACTIVE_STAKE_ON_PAST_OLC)
        );
        // determine whether a new lockup cycle has been ended on the stake pool and
        // inactivated SOME `pending_inactive` stake which should stop earning rewards now,
        // thus requiring separation of the `pending_inactive` stake on current observed lockup
        // and the future one on the newly started lockup
        let lockup_cycle_ended = inactive > pool.total_coins_inactive;

        // actual coins on stake pool belonging to the active shares pool
        active += pending_active;
        // actual coins on stake pool belonging to the shares pool hosting `pending_inactive` stake
        // at current observed lockup cycle, either pending: `pending_inactive` or already inactivated:
        if (lockup_cycle_ended) {
            // `inactive` on stake pool = any previous `inactive` stake +
            // any previous `pending_inactive` stake and its rewards (both inactivated)
            pending_inactive = inactive - pool.total_coins_inactive
        };
