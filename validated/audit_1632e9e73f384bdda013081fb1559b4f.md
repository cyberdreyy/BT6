### Title
Unfunded instant-withdraw receipts keyed to an earlier epoch are unclaimable and excluded from recovery after default finalization - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` stores a user's instant receipt basis under `instantWithdrawsRequestsByEpoch[user][epochNumber]` using the epoch number at request time, but `_claimDefaultedInstantWithdrawRequest` only clears the entry keyed at `defaultRecoveryEpoch` (the epoch number at finalization, which is incremented by `deposit()` during a running epoch). If an instant receipt stays unfunded across an epoch boundary, the defaulted claim reads the wrong key, finds zero, and the aggregate `instantWithdrawsRequests[user]` balance can never be haircut-claimed or cleared — the user's claim is permanently frozen, mirroring the Nouns `updateFounders` stale-key bug.

### Finding Description
In `requestInstantWithdraw`, receipt basis is written to `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` where `currentEpoch = epochNumber` (IdleCreditVault.sol lines 367–372). `epochNumber` is incremented inside `deposit()` whenever the CDO deposits while an epoch is running (line 610). At default finalization, `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` (line 693) — one epoch later than when the receipt was created.

Later, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (line 844). For a receipt created in the previous epoch, this returns 0, so nothing is cleared: `instantWithdrawsRequests[_user]` retains the basis and the minted receipt tokens. The fallback in `claimInstantWithdrawRequest` then pays `instantWithdrawsRequests[_user]` at par through `_transferFundedClaim`, but the underlying was lent to the borrower — the `balance - reserve < amount` guard (lines 900–905) reverts, and the `defaultRecoveryReserve` cannot legally be spent via that path anyway.

Additionally, `defaultPendingClaimBasis` only adds `instantWithdrawClaimsByEpoch[epochNumber]` (current epoch, line 647), so the stale receipt was never included in the recovery basis: the user receives neither a haircut recovery payout nor a par claim. Worse, post-default `requestWithdraw` reverts whenever `instantWithdrawsRequests[_user] != 0` (line 249), so the user cannot even open a post-default request — a permanent freeze of their position.

### Impact Explanation
Any holder whose instant-withdraw receipt is created in epoch N but remains unfunded (`pendingInstantWithdraws != 0`) when a later epoch N+1 defaults is permanently unable to claim: the funded path reverts on the reserve check, the defaulted path reads a zero basis under the wrong epoch key, and new requests are blocked. Loss is the full receipt amount for affected users, plus permanently stranded `instantWithdrawClaimsByEpoch[N]` accounting.

### Likelihood Explanation
Requires an instant withdrawal request that is not fully funded by `collectInstantWithdrawFunds` before the next epoch starts (the code explicitly anticipates this at line 696 and in `_defaultPrefundedInstantReserve` for the *current* epoch, but provides no handling for *older* epochs), followed by a borrower default and `finalizeDefaultRecovery`. Attacker-facing impact requires only being a normal tranche-token holder who requests an instant withdrawal during an underfunded epoch transition.

### Recommendation
In `_claimDefaultedInstantWithdrawRequest`, iterate or track all epochs with non-zero `instantWithdrawsRequestsByEpoch[user]` (or store a per-user `lastInstantWithdrawRequest` epoch marker analogous to `lastWithdrawRequest`), and include all unfunded instant receipt epochs in `defaultPendingClaimBasis`. At minimum, do not rely on `defaultRecoveryEpoch` as the sole lookup key — the write key (`epochNumber` at request time) and the read key must match, exactly as the Nouns `baseTokenId`/`reservedUntilTokenId` divergence illustrates.

### Proof of Concept
A Foundry PoC would: (1) deposit via `depositAA`; (2) `requestInstantWithdraw` during epoch N buffer so `instantWithdrawsRequestsByEpoch[user][N]` is set; (3) `startEpoch`/`stopEpoch` such that `collectInstantWithdrawFunds` funds less than requested, leaving `pendingInstantWithdraws > 0` while `epochNumber` increments to N+1 via the stop-time `deposit`; (4) trigger borrower default in epoch N+1 and call `finalizeDefault`; (5) show `claimInstantWithdrawRequest` reverts in `_transferFundedClaim` while `_claimDefaultedInstantWithdrawRequest` returns 0 basis, permanently freezing the receipt. Note: I did not fully verify in `IdleCDOEpochVariant` that `pendingInstantWithdraws` can remain non-zero across a `stopEpoch`; if instant withdrawals are always fully funded or revert at epoch boundary, this scenario may be unreachable and the finding would not stand.
