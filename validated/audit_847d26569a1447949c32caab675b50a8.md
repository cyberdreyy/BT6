### Title
Instant-withdraw claims are not gated on the funding event — a requester can drain underlying held for buffer deposits and already-funded normal receipts — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
CVE-2017-2619 is a TOCTOU symlink race: a check validates one filesystem object, then the actor dereferences a *different* object that was swapped in between check and use. The credit-vault analog lives in the instant-withdraw path of `IdleCreditVault`. `requestInstantWithdraw` mints the user a 1:1 strategy-token receipt and records `instantWithdrawsRequests[_user]`, while `claimInstantWithdrawRequest` pays out `instantWithdrawsRequests[_user]` in underlying with **no check that the matching borrower funding has actually arrived** — no epoch gate, no per-request funding marker, no comparison against `pendingInstantWithdraws`. The payout is simply `_transferFundedClaim(_user, amount)`, which only protects `defaultRecoveryReserve` (post-default) and otherwise spends whatever underlying the strategy currently holds. The intended funding source is `collectInstantWithdrawFunds`, which pulls the covered amount from the CDO after the borrower returns funds at `startEpoch` — but nothing binds a claim to that funding, so the claim dereferences *other* underlying in the vault (the "swapped symlink"): buffer-period deposits sitting in the strategy before `startEpoch` forwards them to the borrower, and underlying already collected for other users' funded-but-unclaimed normal withdraw requests.

### Finding Description [1](#0-0)  `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]` and immediately calls `_transferFundedClaim`. [2](#0-1)  `_transferFundedClaim` only guards `defaultRecoveryReserve`; outside a finalized default it transfers any vault-held underlying. [3](#0-2)  `requestInstantWithdraw` likewise has no phase gate — it burns CDO strategy tokens, mints the receipt, and bumps `pendingInstantWithdraws`, which is only decremented later by `collectInstantWithdrawFunds` when the CDO actually delivers the funded underlying. Between request and funding, the receipt is a naked claim on the vault's balance. On the CDO side, `claimInstantWithdrawRequest` checks only `allowInstantWithdraw` and forwards the call; there is no `isEpochRunning` or per-epoch funding check in the vault path shown at [4](#0-3) .

Concretely, during the buffer phase the strategy holds underlying deposited via `deposit()` (line 603 transfers tokens into the strategy) that has not yet been sent to the borrower, plus underlying collected via `collectWithdrawFunds`/`collectInstantWithdrawFunds` backing other users' matured receipts. An attacker holding tranche tokens calls `requestInstantWithdraw` (receipt minted), then `claimInstantWithdrawRequest` in the same phase: the vault pays the attacker's claim out of those unrelated funds. The attacker's own share remains lent to the borrower, so when `startEpoch` runs, `pendingInstantWithdraws` still must be funded for *other* pending instant receipts while the vault is now short — the equivalent of reading the symlink target twice and getting a different file.

Broken invariant: one funded receipt, one payout, from the earmarked funding source. The gap between "receipt recorded" (check) and "underlying source" (use) is exactly the symlink-race shape.

### Impact Explanation
The attacker is paid instantly in underlying that belongs to (a) users whose matured normal/instant receipts are funded but unclaimed, or (b) buffer deposits awaiting `startEpoch`. Since `pendingInstantWithdraws` and `pendingWithdraws` still demand borrower funding at the next `startEpoch`, the strategy becomes insolvent by the drained amount: later claimants' `claimWithdrawRequest`/`claimInstantWithdrawRequest` revert on insufficient balance — direct theft plus permanent freezing of honest funded claims, quantified as `min(instantWithdrawsRequests[attacker], vault underlying balance available above defaultRecoveryReserve)`.

### Likelihood Explanation
Requires only `allowInstantWithdraw == true` (a supported mode, exercised in tests) and a tranche position. The attacker is an ordinary KYC'd lender; no privileged role needed. The window exists whenever the vault holds underlying not yet claimed or not yet forwarded — every buffer phase and any matured-but-unclaimed funded receipts. Caveat: `setInstantWithdrawParams` exposes an `instantDelay` parameter enforced on the CDO request side (not visible in the vault code indexed), so the exploit window depends on how that delay interacts with the funding event; the vault-side claim itself has no funding gate regardless.

### Recommendation
Bind each instant receipt to a funded epoch/source: record `instantWithdrawsRequestsByEpoch` (already tracked) against the epoch in which `collectInstantWithdrawFunds` delivered the underlying, and in `claimInstantWithdrawRequest` pay only receipts whose epoch was funded, or gate the claim on `pendingInstantWithdraws` having been reduced to cover this user's basis. Alternatively, escrow funded instant amounts into a per-epoch reserve analogous to `defaultRecoveryReserve` so unfunded receipts cannot consume it.

### Proof of Concept
Foundry fork sketch (`test/foundry/` harness style used in `IdleCreditVault.t.sol`):

```solidity
// Setup: enable allowInstantWithdraw via setInstantWithdrawParams; pool has
// victim deposits in buffer (strategy holds underlying pre-startEpoch), or a
// matured funded normal withdraw request of `victim` still unclaimed.

// Attacker holds AA tranche tokens.
uint256 atk = attackerTrancheBalance;

// 1) Buffer phase: attacker requests instant withdraw.
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(atk, address(AAtranche)); // receipt minted, pendingInstantWithdraws += atk

// 2) Same phase, before startEpoch/borrower funding: claim immediately.
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest(); // no funding/epoch gate -> _transferFundedClaim pays from vault-held deposits

assertEq(underlying.balanceOf(attacker) - balPre, atk);

// 3) startEpoch: borrower funds pendingInstantWithdraws again (double spend),
// or victim.claimWithdrawRequest() reverts on insufficient vault balance.
```

The assertion that the attacker's balance increased by the full request before any `collectInstantWithdrawFunds` funding for that request demonstrates the funding-source swap; the subsequent insolvency is verified by the victim's claim reverting.

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
