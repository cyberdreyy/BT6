### Title
Builder deposits can reactivate an already-exited builder, contradicting the spec's own invariant that "exited builders cannot be reactivated" - ([File: specs/gloas/beacon-chain.md])

### Summary
`process_builder_deposit_request` in the Gloas fork of the spec allows a `BuilderDepositRequest` sent for a builder that has already exited and been fully swept (`withdrawable_epoch != FAR_FUTURE_EPOCH` and `balance == 0`) to push that builder's `withdrawable_epoch` back into the future and top up its balance, effectively un-exiting it. This is the direct spec analog of the reported bug class: an operation ("add collateral") being permitted on an entity whose lifecycle should already be "closed" (exited/withdrawn), silently reopening/mutating state that a correct implementation should treat as final.

### Finding Description
`process_builder_deposit_request` is documented with an explicit invariant: [1](#0-0) 

Right below that comment, the function body does the opposite of what the comment promises whenever the deposit targets a pubkey that is still present in `state.builders` (i.e., the builder index has not yet been reused by `get_index_for_new_builder`): [2](#0-1) 

Concretely:
- A builder that has been exited (`initiate_builder_exit` sets `withdrawable_epoch`) and fully swept to zero balance is in the terminal "closed" state described by the doc comment ("Any deposit sent to an exited builder will be withdrawn ... Exited builders cannot be reactivated").
- But the `else` branch is reached whenever `request.pubkey` is still `in builder_pubkeys` — this is true both for *active* builders (normal top-up path) and for *exited-but-not-yet-reused* builder slots, since `get_index_for_new_builder` only reuses a slot for a *different* pubkey once it's past `withdrawable_epoch` and zero balance; the original pubkey entry in `state.builders` is not removed or reset on exit/sweep.
- For that already-exited/swept builder, the code explicitly resets `builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY` and adds `request.amount` to `builder.balance`, which is exactly "reactivation": the builder becomes able to receive/hold funds and be swept again in the future, despite having already completed its exit lifecycle.

This breaks the equality that the spec's own comment asserts should hold: "exited builder state is final; only new/never-before-exited pubkeys or entirely reused indices can hold live balance." Instead, sending an `EXECUTION_LAYER` builder deposit request (which requires no authorization beyond knowledge of the exited builder's own pubkey/withdrawal credentials — the same key that already exited) can resurrect a builder record that downstream logic (and the prose spec) assumes is inert.

### Impact Explanation
This falls into the "validator or builder mutated without its authority" / state-consistency class called out in scope. Concretely:
- It contradicts the explicit spec invariant ("Exited builders cannot be reactivated"), meaning implementations that rely on that invariant (e.g., caching, index reuse logic, external explorers/relays tracking "the builder at index N is retired") can diverge from the literal code behavior — a spec-prose vs spec-code inconsistency that different client teams could implement differently, risking a consensus split between spec-following implementations that interpret "cannot be reactivated" as a MUST (and thus reject/ignore such deposits) versus those that implement the literal `process_builder_deposit_request` code (which allows it).
- It also potentially interacts with `get_index_for_new_builder`, which scans for a slot with `withdrawable_epoch <= current_epoch and balance == 0` to assign to a brand-new pubkey. If a deposit resets the withdrawable_epoch of an old, sweepable slot back to the future, it prevents that slot from being reclaimed for new builder registrations, and continues carrying a stale execution/fee-recipient association that observers assumed dead.

I could not, in the remaining budget, fully trace `get_builders_sweep_withdrawals`/`is_active_builder` to confirm whether a "reactivated" builder can then also win/serve payload bids (which would elevate this to funds/payment misdirection). That downstream interaction is the main remaining uncertainty.

### Likelihood Explanation
Triggering requires only submitting a valid `BuilderDepositRequest` (a signed deposit-message, using `DOMAIN_BUILDER_DEPOSIT`) referencing a pubkey that previously registered as a builder, exited, and was swept to zero balance — no special privilege, coalition, or client bug needed, and it is fully reachable through normal execution-layer request processing (`process_builder_deposit_request` is called for every request in `requests.builder_deposits`, per `specs/_features/eip8205/beacon-chain.md:493` in this snapshot, and equivalently in `specs/gloas/beacon-chain.md`). This makes it a straightforward, deterministic, spec-text-reachable divergence rather than a probabilistic or resource-exhaustion issue.

### Recommendation
Align the code with the documented invariant: `process_builder_deposit_request` should check whether the target builder is already exited/swept (i.e., `builder.withdrawable_epoch != FAR_FUTURE_EPOCH`) and, if so, either (a) route the deposit directly to a withdrawal to `builder.execution_address` (matching the doc's "any deposit sent to an exited builder will be withdrawn to the builder's execution address"), instead of resetting `withdrawable_epoch` and crediting `builder.balance`; or (b) update the doc comment if reactivation is in fact the intended behavior, and clearly define how index-reuse (`get_index_for_new_builder`) interacts with a "reactivated" but not fully-reset builder record. Either way, the code and the prose need to be made consistent so all spec-following implementations converge on the same state transition.

### Proof of Concept
1. Register builder `B` via `process_builder_deposit_request` (new pubkey path) — `add_builder_to_registry` sets `withdrawable_epoch = FAR_FUTURE_EPOCH`, `balance = amount`.
2. Exit `B` via `process_builder_exit_request` → `initiate_builder_exit` sets `builder.withdrawable_epoch` to some finite future epoch.
3. Advance epochs until the builder is swept (via `get_builders_sweep_withdrawals`/`apply_withdrawals`), driving `balance` to 0 while `withdrawable_epoch` remains the finite exit epoch (`!= FAR_FUTURE_EPOCH`).
4. Submit a new `BuilderDepositRequest` for the same pubkey `B` with a valid signature (`is_valid_builder_deposit_signature`).
5. `process_builder_deposit_request` takes the `else` branch (pubkey still in `builder_pubkeys`), sees `withdrawable_epoch != FAR_FUTURE_EPOCH and balance == 0`, and sets `builder.withdrawable_epoch = current_epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY`, then `builder.balance += request.amount`.
6. Result: builder `B`, which had fully exited and been swept ("closed"), now again holds a non-zero balance and a fresh future `withdrawable_epoch` — contradicting the spec's stated guarantee that "Exited builders cannot be reactivated." [3](#0-2)

*Note*: Builder indices are reusable. When a builder exits, its index may later

an exited builder will be withdrawn to the builder’s execution address. Exited
builders cannot be reactivated, although a newly registered builder’s public key
may have previously appeared in the builder set. Implementations that rely on
caching should account for this behavior.

def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:
    # Ignore deposits with unexpected withdrawal credential prefixes
    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
        return

    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        if is_valid_builder_deposit_signature(request):
            add_builder_to_registry(
                state,
                request.pubkey,
                PAYLOAD_BUILDER_VERSION,
                ExecutionAddress(request.withdrawal_credentials[12:]),
                request.amount,
                state.slot,
            )
    else:
        builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
        builder = state.builders[builder_index]

        # If exited and swept, reset the withdrawable epoch
        if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
            epoch = get_current_epoch(state)
            builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY

        # Increase balance by deposit amount
        builder.balance += request.amount
