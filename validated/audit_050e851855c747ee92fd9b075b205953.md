### Title
Floor-division threshold in `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` lets signer state-machine "supermajority" agreement be reached below the true 70% consensus threshold - ([File: libsigner/src/v0/signer_state.rs])

### Summary
`GlobalStateEvaluator::reached_agreement` and `reached_disagreement` compute the 70%/30% weight thresholds with a floor division (`total_weight * 7 / 10`), whereas the consensus-critical `NakamotoBlockHeader::compute_voting_weight_threshold` used to actually verify on-chain block signatures rounds the same computation *up* (adds a `ceil` correction). Because the signer-side check floors instead of ceilings, a coalition can be judged to have reached "global agreement" (deciding the active miner, burn view, tx-replay set, or protocol version) with strictly less than the mathematically-required 70% of weight whenever `total_weight * 7` is not a multiple of 10 - the same class of precision loss described in the referenced Paladin `_pledge` report, where a check compares against an intended target while the actual accumulated value is allowed to fall short of it by the rounding error.

### Finding Description
`reached_agreement` and `reached_disagreement` are defined as: [1](#0-0) 

Both divide `total_weight * threshold` by 10 and floor the result, i.e. the number of votes required to "reach agreement" is `floor(total_weight * 7 / 10)` rather than `ceil(total_weight * 7 / 10)`. Whenever `(total_weight * 7) % 10 != 0`, this required vote count is one weight-unit lower than the true 70% supermajority, exactly analogous to the Paladin `_pledge` bug where `bias = slope * boostDuration` rounds down from the intended `amount`, but the guard still checks against the un-rounded `amount`.

By contrast, the consensus-critical threshold used for real block-signature verification correctly rounds *up*: [2](#0-1) 

`GlobalStateEvaluator::determine_global_state`/`determine_latest_supported_signer_protocol_version`/`find_majority_prefix_replay_set` all gate their decisions on `reached_agreement`: [3](#0-2) 

These results feed directly into each signer's `LocalStateMachine`, in particular `capitulate_miner_view`/`capitulate_viewpoint`, which changes which miner/tenure a signer treats as canonical based on `eval` (the same `GlobalStateEvaluator`): [4](#0-3) 

Because the "who is the current miner" / "what burn view is agreed" decision uses a strictly weaker threshold than the one that will later be enforced when counting actual block-approval signatures (`compute_voting_weight_threshold`, used both in `verify_signer_signatures` for consensus and in `stacks-signer/src/v0/signer.rs`'s pre-commit/signature tallying), a signer can capitulate its local view of the "current miner" or accepted burn view/tx-replay-set to a value that only ~69.x% (not 70%) of weight actually endorses. This breaks the intended equality between "aggregated global-state weight" and "verified 70% threshold" that the rest of the signer/consensus pipeline assumes holds identically everywhere the 70% supermajority is checked.

### Impact Explanation
This falls under the High-severity bucket: a signer can be induced to act on a stale/incorrect view of the reward set/threshold (miner state, burn view, or tx-replay set) because the "global agreement" check it relies on is looser than the actual consensus threshold used for signing. In practice this can cause a subset of signers to capitulate to (or fail to capitulate from) a miner viewpoint that lacks true 70% support, producing viewpoint divergence across the signer set and stalling or misdirecting subsequent block pre-commit/signature flows (`handle_block_pre_commit`, `store_and_process_block_signature`) which are keyed off `check_block_against_signer_db_state`/`current_miner`. It does not directly forge a consensus-accepted block signature (the on-chain `compute_voting_weight_threshold` ceil check still gates that), so it is not Critical, but it can wedge/skew signer liveness and agreement, matching the High-impact category "acting on a stale reward set/threshold."

### Likelihood Explanation
This is not an edge case requiring adversarial crafting - it triggers any time `total_weight * 7` is not a multiple of 10, which is the common case for real-world weight distributions (reward-slot weights are rarely multiples of 10/7). No majority collusion, secret keys, or special node access is required; it is a routine arithmetic property of the existing signer weight distribution and fires automatically inside `determine_global_state`/`capitulate_miner_view`.

### Recommendation
Make `reached_agreement`/`reached_disagreement` use the same ceiling-rounded threshold formula as `NakamotoBlockHeader::compute_voting_weight_threshold`, e.g.:
```rust
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    let total = u64::from(self.total_weight);
    let numerator = total.strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD);
    let threshold = numerator.div_ceil(10);
    u64::from(vote_weight) >= threshold
}
```
and the symmetric fix for `reached_disagreement`, so the signer-side "global agreement" notion is never more lenient than the consensus-critical 70% threshold it is meant to approximate.

### Proof of Concept
For `total_weight = 99` (a routine, non-adversarial weight distribution, e.g. produced by `pox_5_make_signer_set`'s Hare apportionment):
- True 70% supermajority requires `ceil(99 * 7 / 10) = 70` weight units, matching `NakamotoBlockHeader::compute_voting_weight_threshold(99) == 70` (per the existing unit tests at [5](#0-4) , which show the ceiling behavior, e.g. `compute_voting_weight_threshold(511) == 358`, not `357 = floor`).
- `GlobalStateEvaluator::reached_agreement(69)` on the same `total_weight = 99` returns `true` because `u64::from(69) >= 99u64.strict_mul(7)/10 == 69`, even though `69/99 = 69.7% < 70%`.
- Any signer coalition naturally holding 69 out of 99 total weight (no majority collusion needed - this is just under true 70%) will cause `determine_global_state`/`capitulate_miner_view` to treat "agreement" as reached on a miner/burn-view/replay-set that lacks the actual 70% support the protocol intends, while the same weight total would correctly fail the consensus-critical `compute_voting_weight_threshold` check used for real block-signature approval.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
