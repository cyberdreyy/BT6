### Title
Stale per-epoch instant-withdraw receipts inflate default recovery basis and freeze claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays a funded instant withdrawal but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` (contracts/strategies/idle/IdleCreditVault.sol:380-393). These stale per-epoch records — the "freed" receipt still referenced — are later read by `defaultPendingClaimBasis` (line 647) and `_claimDefaultedInstantWithdrawRequest` (line 844) when a default is finalized in the same epoch, corrupting recovery accounting. This is the vault analog of CVE-2022-1280's use-after-free: a logically consumed object is dereferenced again because its bookkeeping was not invalidated.

### Finding Description
When a user claims a funded instant withdrawal, the code only does:

- `amount = instantWithdrawsRequests[_user]; _burn(_user, amount);`
- `instantWithdrawsRequests[_user] = 0; _transferFundedClaim(_user, amount);`

It never touches `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch`. Contrast with `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which does clear them — but only runs after `defaultRecoveryFinalized`.

Sequence (running epoch, instant withdraws enabled):

1. Attacker calls `requestInstantWithdraw(X1)`: `instantWithdrawsRequestsByEpoch[attacker][E] = X1`, `instantWithdrawClaimsByEpoch[E] = X1`, `pendingInstantWithdraws = X1`.
2. IdleCDO funds it via `collectInstantWithdrawFunds(X1)` → `pendingInstantWithdraws = 0`, underlyings sit in the strategy.
3. Attacker claims: paid X1, `instantWithdrawsRequests = 0`, but `instantWithdrawClaimsByEpoch[E]` still equals X1.
4. Attacker (or anyone) requests X2; borrower defaults before it is funded → `pendingInstantWithdraws = X2 != 0`.
5. `finalizeDefaultRecovery` computes `defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[E]` = `... + (X1 + X2)` — including the already-paid X1 (line 644-648). `defaultRecoveryPrice = reserve / totalBasis` is permanently diluted.
6. Attacker's `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = X1 + X2` (or X1 for the stale-only case), then executes `instantWithdrawsRequests[user] -= claimBasis` with balance `X2` → underflow revert → their legitimate X2 claim is permanently frozen; `pendingInstantWithdraws` is also driven to 0 spuriously (line 852), and recovery dust is stranded.

### Impact Explanation
Two concrete harms, both quantifiable:

- **Recovery dilution / theft-by-haircut**: every previously-claimed instant amount inflates `totalBasis`, lowering `defaultRecoveryPrice` for all genuine defaulted-epoch and active claimants. The unclaimed reserve difference is locked as dust (line 656-657 notes dust is "isolated"), i.e., permanently frozen funds.
- **Permanent freezing**: `instantWithdrawsRequests[_user] -= claimBasis` underflows whenever the user claimed any same-epoch instant receipt before default, reverting every subsequent claim and trapping the reserve.

### Likelihood Explanation
Requires instant withdrawals enabled (`setInstantWithdrawParams`), an attacker able to get one instant request funded and claimed inside the same epoch, a second unfunded instant request outstanding, and an honest borrower default in that epoch — a supported flow (`_defaultPrefundedInstantReserve` explicitly contemplates partial instant funding at finalization, lines 716-723). No privileged misbehavior needed; any unprivileged tranche holder can do steps 1-3. Likelihood is moderate because it needs the default to land in the same epoch as the claimed receipt.

### Recommendation
In the funded claim path of `claimInstantWithdrawRequest`, clear per-epoch records symmetrically with the defaulted path: subtract the claimed amount from `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (or track each request's epoch) and `instantWithdrawClaimsByEpoch[currentEpoch]`, so a consumed receipt can never re-enter `defaultPendingClaimBasis` or `_claimDefaultedInstantWithdrawRequest`. Alternatively, settle per-epoch instant claims at `stopEpoch`/claim time and store the request epoch per user.

### Proof of Concept
Foundry fork PoC (sketch, modeled on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testStaleInstantReceiptPoisonsDefaultRecovery() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);           // epoch #1 buffer
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    uint256 amount1 = 100e6;
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, amount1);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // 1) attacker requests instant withdraw X1
    vm.warp(block.timestamp + 100);
    _requestInstantWithdrawWithUser(attacker, amount1); // instantWithdrawClaimsByEpoch[E] = X1

    // 2) CDO funds it; attacker claims (funded path, no per-epoch clearing)
    _fundInstantWithdraw(amount1);                      // collectInstantWithdrawFunds
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();             // paid; stale records remain
    assertEq(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), amount1); // BUG: stale

    // 3) second instant request left unfunded
    _requestInstantWithdrawWithUser(attacker, amount1);

    // 4) borrower defaults mid-epoch; finalize recovery
    _borrowerDefaultAndFinalize();                      // uses defaultPendingClaimBasis()

    // recovery basis includes already-paid X1 -> defaultRecoveryPrice diluted
    // attacker's claim now reverts on instantWithdrawsRequests underflow
    vm.expectRevert();
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Note on verification limits: I confirmed the non-clearing claim path (lines 380-393), the epoch-scoped reads (lines 644-648, 842-856), and that `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` (lines 398-403). I did not fully trace `IdleCDOEpochVariant`'s instant-funding/default-finalization call flow, so the exact transaction wiring for step 4 should be confirmed, but the stale-reference accounting flaw in the vault is directly visible in `IdleCreditVault.sol`.
