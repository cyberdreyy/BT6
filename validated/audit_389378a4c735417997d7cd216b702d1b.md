### Title
Claimed instant-withdraw receipts are never cleared from the per-epoch ledger, inflating `defaultPendingClaimBasis` and permanently freezing `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out a funded instant-withdraw receipt at par but only clears the aggregate `instantWithdrawsRequests[_user]` counter. It never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. The stale epoch-level entry is the analog of the Nova bug: the resource was consumed but its accounting record was never transitioned. If the borrower defaults in the same strategy epoch while `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis()` counts the already-paid receipt again, `defaultRecoveryPrice` is diluted for every claimant, and the user who already claimed hits an arithmetic underflow in `_claimDefaultedInstantWithdrawRequest`, permanently bricking their claim and locking the corresponding reserve as unreachable dust.

### Finding Description
In `IdleCreditVault.sol:380-393`, a funded instant claim executes:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Compare with `requestInstantWithdraw` (`IdleCreditVault.sol:366-374`), which sets three ledgers: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]`. Only the first is cleared on claim; the two per-epoch records remain forever.

Those records are only consumed by `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:842-856`), which runs when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` (i.e. `pendingInstantWithdraws != 0` at finalization, `IdleCreditVault.sol:696`). The default basis at `IdleCreditVault.sol:644-649`:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

includes the stale, already-paid amount. Two consequences:

1. **Dilution**: `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (`IdleCreditVault.sol:688`) is computed against an inflated `totalBasis`, so every legitimate defaulted and active claimant receives less than the reserve justifies.
2. **Permanent freeze**: for the user who already claimed, `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` still holds the old basis. If they open any new instant request in the same epoch (no post-default guard exists in `requestInstantWithdraw`), the stale entry makes `claimBasis > instantWithdrawsRequests[user]` and `instantWithdrawsRequests[_user] -= claimBasis` (line 848) underflows, reverting every future `claimInstantWithdrawRequest`. The slice of `defaultRecoveryReserve` earmarked for that phantom claim can never be paid out, since `_transferDefaultRecovery` only moves via claims (line 915).

Existing guards do not stop this: the `lossRecoveryPriceByEpoch` guard in `requestWithdraw` (lines 263-271) only covers normal withdraws, the funded-claim reserve guard in `_transferFundedClaim` (lines 900-904) fires before finalization, and nothing elsewhere clears the per-epoch instant ledgers except the defaulted-claim path that the stale entry itself breaks.

### Impact Explanation
Permanent freezing of unclaimed recovery yield plus recovery dilution. The stuck portion of `defaultRecoveryReserve` equals `staleBasis * defaultRecoveryPrice / 1e18` and remains locked in the strategy contract forever (no sweep function touches the reserve). Honest claimants lose `staleBasis / totalBasis` of the recovery price. With e.g. 100k USDC of already-claimed instant receipts stale in the default epoch and a 1M USDC total basis, all claimants lose ~9% of their recovery payout and ~`100k * recoveryPrice` is permanently locked.

### Likelihood Explanation
The trigger requires an instant-withdraw epoch where the queue is only partially funded (`pendingInstantWithdraws != 0`), one user claiming their funded portion, and the borrower then being finalized as defaulted before `epochNumber` increments (e.g. the prefunded/`_handleBorrowerDefault` flow where no `deposit()` bump occurs). The attacker is any tranche holder — instant withdraw and claim are unprivileged. No privileged or malicious action is needed; it is a state-cleanup gap reachable through ordinary user sequencing. Likelihood is moderate: it needs the partial-instant-funding plus same-epoch default combination, but the accounting error is deterministic once reached.

### Recommendation
In `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`), also clear the per-epoch records: zero `instantWithdrawsRequestsByEpoch[_user][requestEpoch]` and decrement `instantWithdrawClaimsByEpoch[requestEpoch]` for the request's epoch. This requires tracking the instant request epoch per user (analogous to `lastWithdrawRequest`), or clearing the current `epochNumber` entry consistently with how `requestInstantWithdraw` records it.

### Proof of Concept
```solidity
// Foundry fork test sketch on IdleCreditVault + IdleCDOEpochVariantPrefunded
// Setup: standard epoch vault, instant withdraws enabled, users A (attacker) and B.
// 1. Epoch N running. A and B call cdo.requestInstantWithdraw / requestInstantWithdraw
//    so instantWithdrawsRequestsByEpoch[A][N] and instantWithdrawClaimsByEpoch[N] are set.
// 2. startEpoch funds only A's instant request; CDO calls
//    collectInstantWithdrawFunds(amountA). pendingInstantWithdraws = amountB > 0.
// 3. A calls cdo.claimInstantWithdrawRequest -> paid at par via _transferFundedClaim.
//    BUG: instantWithdrawsRequestsByEpoch[A][N] and instantWithdrawClaimsByEpoch[N]
//    still contain amountA.
// 4. Borrower defaults in the same strategy epoch (epochNumber unchanged,
//    e.g. prefunded _handleBorrowerDefault path with no deposit() bump).
//    finalizeDefaultRecovery computes:
//      basis = pendingWithdraws + instantWithdrawClaimsByEpoch[N]   // includes paid amountA
//      defaultRecoveryPrice = reserve / basis                       // diluted
//      defaultInstantWithdrawsFinalized = true
// 5. Assert: recoveryPrice < reserve / (basis - amountA)   // dilution confirmed.
// 6. A calls requestInstantWithdraw again (same epoch, no guard) then
//    claimInstantWithdrawRequest -> _claimDefaultedInstantWithdrawRequest computes
//    claimBasis = amountA + newAmount > instantWithdrawsRequests[A] = newAmount
//    -> instantWithdrawsRequests[A] -= claimBasis underflows -> revert.
// 7. Assert: underlyingToken.balanceOf(strategy) - defaultRecoveryReserve dust ==
//    amountA * defaultRecoveryPrice / 1e18 permanently locked.
```

Confidence note: step 4 depends on a default finalization path that does not increment `epochNumber` (which is bumped only inside `deposit()` when the epoch is running, `IdleCreditVault.sol:610`); the prefunded borrower's `_handleBorrowerDefault`/hook path is the likely trigger but I could not fully trace the CDO-side default sequencing in this review to confirm `epochNumber` stays aligned with the stale entry's epoch.
