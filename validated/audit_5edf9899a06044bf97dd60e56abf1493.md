## Title
Stale confirmations from removed multisig members are not purged from *other* requests, allowing a request to execute below the intended live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

## Summary
`delete_member` (multisig2) / the `DeleteKey` handler (multisig) only remove the *requests originally submitted by* the departing member, and drop that member's `num_requests_pk` counter. Neither implementation walks `self.confirmations` to strip the departing member's confirmation entries from *other, still-pending* requests that this member had already confirmed. `confirm()` later counts confirmations purely by set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) with no re-validation that every entry in the set corresponds to a currently live member. This breaks the binding "confirmations counted == live members who actually confirmed," which the task rules explicitly recognize as a valid custody boundary, and directly mirrors the reported bug class: a state-mutating admin action (member removal, analogous to `updateArtSettings`'s forced `endTime` bump) silently reopens/weakens a guard (mint window / confirmation threshold) that a third party can then exploit.

## Impact Explanation
The equality that should hold is:
`num confirmations in set at execution time == num of currently-live, actually-agreeing members`

After a member removal that doesn't scrub stale confirmations on unrelated requests, the invariant becomes:
`confirmations.len() >= num_confirmations` even though one or more of those confirming identities is no longer a member.

This means a pending `Transfer`, `FunctionCall`, `AddKey`, or `DeployContract` request can be executed with fewer *currently authorized* signers than the configured `num_confirmations` threshold — the exact "multisig request executed below threshold" scenario called out as Critical impact. Since `Transfer` and `FunctionCall` actions move NEAR / invoke arbitrary calls on behalf of the multisig account, this can result in unauthorized fund movement approved by a quorum that, at the time of execution, no longer meets the security assumption the K-of-N scheme is supposed to guarantee.

## Likelihood Explanation
Requires no attacker privilege beyond being one of the existing (still current) members, or simply requires that in the ordinary operational flow a member is removed (e.g., off-boarding, key rotation, compromise response) while other requests are in flight. This is a normal, expected multisig-admin action (`DeleteMember`/`DeleteKey`), not an edge-case misconfiguration — any team that rotates members while multiple requests are open is exposed. The `REQUEST_COOLDOWN` (15 min) and `active_requests_limit` (12) mean the window realistically exists in practice whenever confirmations accumulate slowly across separate requests.

## Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over `self.confirmations` for **all** pending requests (not only those the member authored) and strip the departing member's entry. Alternatively, validate at `confirm()` time (and at execution) that every account/key present in the confirmations set is still contained in `self.members` before counting it toward `num_confirmations`, discarding stale entries lazily.

## Proof of Concept
Multisig2 contract, members = {A, B, C, D}, `num_confirmations = 3`.

1. `C` calls `add_request` creating request `R1` (e.g. `Transfer` to an attacker-controlled account). `confirmations[R1] = {}`.
2. `A` calls `confirm(R1)` → `confirmations[R1] = {A}` (1 < 3, no execution).
3. `B` calls `confirm(R1)` → `confirmations[R1] = {A, B}` (2 < 3, no execution).
4. Separately, members submit and confirm a `DeleteMember { member: A }` request (needs 3 confirmations from B, C, D — unrelated to `R1`). It executes: `A` is removed from `self.members`. Because the filter in `delete_member` only removes requests where `r.member == A` (i.e., requests A itself created), `R1` (created by `C`) is untouched, and `confirmations[R1]` still equals `{A, B}` even though `A` is no longer a member.
5. `C` calls `confirm(R1)`: `confirmations.len() + 1 = 3 >= num_confirmations(3)` → `R1` executes the `Transfer`, even though only `B` and `C` are truly current members who agreed — one of the three "confirmations" belongs to a party that has since been removed from the multisig, effectively executing below the real live-member threshold.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key

            .requests
