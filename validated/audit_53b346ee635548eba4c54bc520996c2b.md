### Title
Stale rejection weight is never cleared when a signer later accepts the same block, letting a single reconsidering signer inflate `total_weight_rejected` past its real value in the miner's `StackerDBListener` - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tracks per-block accept/reject weight in `BlockStatus` so the miner's coordinator (`SignerCoordinator::get_block_status`) can decide whether a proposed block has reached the 70% approval or blocking-minority rejection threshold. The bug is a mirror of the Astaria H-16 pattern: when a signer's vote transitions between two mutually exclusive accounting buckets (rejected → approved), only one side of the transition is updated. The `total_weight_rejected` accumulator is never decremented when the same signer later sends an `Accepted` response, so its weight is permanently double-counted across `total_weight_rejected` and `total_weight_approved`.

### Finding Description
`BlockStatus` maintains two independent weight accumulators guarded by two different sets: [1](#0-0) 

For an `Accepted` message, the guard that decides whether to add weight is `gathered_signatures.contains_key(&slot_id)`, and `responded_signers.insert(slot_id)` is performed unconditionally afterward: [2](#0-1) 

For a `Rejected` message, the guard is `responded_signers.insert(&slot_id)` — i.e. "have we ever seen a response (accept or reject) from this signer before": [3](#0-2) 

Sequence that breaks the accounting:
1. Signer S rejects the proposal (e.g. transient `ConnectivityIssues`/`NoSortitionView`/`NoSignerConsensus` — reasons the signer itself is designed to reconsider, per `should_reevaluate_reject_reason`): [4](#0-3)  — `responded_signers = {S}`, `total_weight_rejected += weight(S)`.
2. The miner re-proposes (or the same proposal is re-evaluated); S's reject reason is re-evaluable, so S re-checks and now signs (`Accepted`): [5](#0-4) .
3. Back at the miner, `handle` for `Accepted` checks `gathered_signatures.contains_key(&slot_id)` — false, since S never accepted before — so `total_weight_approved += weight(S)` is applied (correctly). But nothing in this branch subtracts `weight(S)` from `total_weight_rejected`, and the reject branch's own guard (`responded_signers.insert`) will never fire again for S because `responded_signers` already contains S from step 1.

Result: `weight(S)` is now counted in **both** `total_weight_approved` and `total_weight_rejected` simultaneously, forever, for that block hash. The two accumulators are supposed to represent disjoint partitions of `total_weight` (an approving signer's weight and a rejecting signer's weight for the same block should be mutually exclusive), but the code allows their sum to exceed `total_weight`.

### Impact Explanation
This directly corrupts the equality the miner's coordinator relies on to decide block fate. `SignerCoordinator::get_block_status` treats `total_weight_rejected` as authoritative to declare a block as rejected by a blocking minority: [6](#0-5) 

and to unlock a valid signature set once `total_weight_approved >= weight_threshold`: [7](#0-6) 

Because the stale rejection weight from step 1 is never retracted, a block that is genuinely signed by a real supermajority can still simultaneously appear to carry stale rejection weight from signers who have since accepted it. If enough signers go through this reject→accept flip (weight collectively exceeding the blocking-minority threshold, `total_weight - weight_threshold`), the miner's coordinator will incorrectly conclude `SignersRejected` for a block that in reality has (or is converging toward) a valid supermajority of *current* acceptances, permanently wedging that proposal/tenure cycle even though no majority of signers is truly opposing it. This is a liveness wedge triggered by ordinary, individually-honest signers reconsidering earlier transient rejections (a behavior the protocol explicitly encourages via `should_reevaluate_reject_reason`), not requiring a majority of colluding signers — it only requires signers whose combined weight crosses the 30%-blocking-minority line to have rejected-then-accepted at some point in the block's history.

### Likelihood Explanation
This is readily reachable without any signer misbehavior: `should_reevaluate_reject_reason` marks common transient failure modes (`ConnectivityIssues`, `NoSortitionView`, `NoSignerConsensus`, `ValidationFailed(UnknownParent/NotFoundError)`, etc.) as reconsiderable, and the miner's proposal-resend/re-evaluation loop (`should_reevaluate_block`) is a normal part of the protocol flow (block proposals are frequently retried after node hiccups). Any signer that rejects for one of these reasons and later accepts on re-evaluation triggers the double-count. No special timing, malicious signer, or majority coordination is needed — only ordinary transient conditions on a subset of signers whose combined weight is large enough to reach the blocking-minority threshold.

### Recommendation
When processing an `Accepted` message for a signer previously recorded in `responded_signers` due to an earlier rejection (i.e., `block.total_weight_rejected` includes this signer), subtract that signer's weight from `total_weight_rejected` before/while adding it to `total_weight_approved` (and vice versa for `Rejected` overriding a prior `Accepted`, if that transition is ever intended to be honored). Concretely, track per-slot vote type (accept/reject) instead of a single `responded_signers` set plus two independent saturating accumulators, and recompute `total_weight_approved`/`total_weight_rejected` from that per-slot map so each signer's weight can only ever contribute to exactly one bucket at a time.

### Proof of Concept
1. Reward set with signers A (40% weight), B (35% weight), C (25% weight); `weight_threshold` = 70% of total.
2. Miner proposes block X. B rejects X with `RejectReason::ConnectivityIssues` (a reconsiderable reason). `stackerdb_listener` records `total_weight_rejected = 35`.
3. Miner re-proposes/re-broadcasts X (e.g., after resubmission on timeout, per `check_submitted_block_proposal`). B's local state re-evaluates the rejection (`should_reevaluate_reject_reason` returns true for `ConnectivityIssues`) and B now signs/accepts X.
4. `stackerdb_listener` processes B's `Accepted` message: since B's slot id is not yet in `gathered_signatures`, `total_weight_approved += 35` → `total_weight_approved = 35`. `total_weight_rejected` remains `35` (never decremented).
5. A also accepts: `total_weight_approved = 75 ≥ weight_threshold(70)` → block would normally be considered approved. But `total_weight_rejected` still shows `35`, i.e., together with C rejecting (`total_weight_rejected` could reach `35(B, stale) + 25(C) = 60`, close to the `total_weight - weight_threshold = 30` blocking-minority bound) the coordinator's rejection branch (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`, i.e. `60 + 70 > 100`) fires and returns `SignersRejected`, even though B has already accepted and the real current rejecting weight is only C's 25%, well under the blocking minority. The miner discards a proposal that in reality has adequate live support, wedging tenure progress.

/// Determine if a block should be re-evaluated based on its rejection reason˝
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
    }
}
