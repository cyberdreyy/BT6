Confirmed: `_validateRequest` only requires `receiver != address(0)` — it never requires `receiver == msg.sender` or any approval, so any caller of `requestRedeem`/`requestDeposit` can freely set `receiver` to an arbitrary, unrelated address, including one that is USDC-blocklisted. [1](#0-0) 

### Title
Unbounded `receiver` in async requests lets a griefer force `token.safeTransfer` reverts that DoS batch solving of other users' deposit/redeem requests - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`requestDeposit`/`requestRedeem` let any caller set an arbitrary `receiver` address with no ownership check. [2](#0-1) [1](#0-0) 
When these requests are solved before their deadline, `_solveRedeemVaultFixedPrice`/`_solveRedeemVaultAutoPrice` and `_solveRequestDirect` push funds directly to `request.receiver` via a bare `token.safeTransfer`/`safeTransferFrom`, with no try/fallback, unlike the expired-refund paths which use `_transferWithFallback`. [3](#0-2) [4](#0-3) 
If `request.receiver` is an address blocklisted by the settlement token (e.g. USDC), that transfer unconditionally reverts, and because these are looped over batches, this reverts processing of every other request bundled in the same `solveRequestsVault`/`solveRequestsDirect` call. [5](#0-4) 

### Finding Description
An ordinary user calls `requestRedeem(token, unitsIn, minTokensOut, solverTip, deadline, maxPriceAge, isFixedPrice, receiver)`, escrowing their own vault units and freely choosing `receiver` to be a USDC-blocklisted address (their own sanctioned address, or any known blocklisted address) — the only guard is `receiver != address(0)`. [2](#0-1) 
When a solver later batches this request together with legitimate ones and calls `solveRequestsVault` (or the permissionless `solveRequestsDirect`), `_solveRequestsVault` loops through the batch and calls `_solveRedeemVaultFixedPrice`/`AutoPrice`, which (for unexpired requests) does `token.safeTransfer(request.receiver, ...)` directly — no try/catch, no fallback to the requester. [3](#0-2) 
Because USDC's `transfer` reverts (returns false, which `safeTransfer` bubbles up as revert) for blocklisted recipients, this single malicious request causes the entire batched transaction — and thus every other user's request in that same call — to revert. This mirrors the reported root cause: an unconditional push-transfer to an attacker-influenced address in a batched/all-or-nothing operation, which the reported issue calls out for liquidation and which here applies to redeem/deposit solving. The `_transferWithFallback` mitigation that the protocol clearly designed for the expired/refund branch (falling back to `requester` on failed push) is conspicuously absent in the "solve" happy-path branches (lines 1286, 1231, 1327, 1335), so the guard that would have prevented this class of issue was not applied consistently. [6](#0-5) 

### Impact Explanation
Legitimate users' pending deposit/redeem requests batched alongside the malicious one cannot be solved in that transaction — a temporary freeze of unclaimed yield/withdrawal proceeds until solvers identify and exclude the poisoned request. For `solveRequestsVault` (authorized-only), this degrades the solver's ability to service the queue; for `solveRequestsDirect` (permissionless, peer-to-peer), any user's batch that happens to include the malicious request also reverts, wasting gas and delaying settlement for all bundled counterparties. This matches Immunefi Medium-severity "temporary freeze of funds" criteria.

### Likelihood Explanation
Low cost, no privileged role needed: attacker only needs vault units (or tokens, for a deposit request) and a single call to the public `requestRedeem`/`requestDeposit` function with a chosen blocklisted `receiver`. The attack is repeatable each time the attacker (or anyone) creates a new request with a blocklisted receiver, since nothing prevents resubmission after refund/cancel. The main uncertainty is whether solvers manually filter out known-bad receivers before batching, which would reduce but not eliminate the risk (new blocklisted addresses can appear, and `solveRequestsDirect` is fully permissionless so any third party can trigger the revert by including the request in their own batch).

### Recommendation
Apply the same `_transferWithFallback` pattern already used in refund/cancel paths to the "solve" happy-path pushes in `_solveRedeemVaultFixedPrice`, `_solveRedeemVaultAutoPrice`, and `_solveRequestDirect` (both deposit and redeem branches), so a failed push to `request.receiver` falls back to `request.user` instead of reverting the whole batch.

### Proof of Concept
1. Deploy `ProvisionerV2`/`MultiDepositorVault` on a fork with real USDC as the settlement token; get vault units for two users, Alice (legit) and Mallory (attacker).
2. Mallory calls `requestRedeem(USDC, units, minTokensOut, 0, deadline, maxPriceAge, true, blocklistedAddr)` where `blocklistedAddr` is a real USDC-blocklisted address (or simulate via a mock USDC that reverts `transfer` to `address(1)`, as in the original report's PoC).
3. Alice independently calls `requestRedeem(USDC, ..., receiver: alice)`.
4. An authorized solver batches both requests and calls `solveRequestsVault(USDC, [malloryRequest, aliceRequest], "", "")`.
5. Assert the whole transaction reverts (bubbling the USDC transfer failure from Mallory's leg via `token.safeTransfer(request.receiver, ...)`), even though Alice's request is entirely valid — demonstrating that Alice's redeem cannot be processed while bundled with Mallory's, and must wait for the solver to detect and exclude it, or for Mallory's request to expire/be refunded.

    /// @notice Transfers amount to receiver and falls back to requester if receiver transfer fails
    /// @param token The ERC20 token being transferred
    /// @param requester The original requester address used as fallback receiver
    /// @param receiver The intended receiver from the request
    /// @param amount The amount of tokens to transfer
    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }

    /// @notice Validates common request parameters shared by requestDeposit and requestRedeem
    /// @param receiver The address receiving funds when request is solved
    /// @param solverTip The tip offered to the solver
    /// @param deadline Timestamp until which the request is valid
    /// @param isFixedPrice Whether the request is a fixed price request
    function _validateRequest(address receiver, uint256 solverTip, uint256 deadline, bool isFixedPrice) internal view {
        // Requirements: receiver is not zero address
        require(receiver != address(0), Aera__ZeroAddressReceiver());
        // Requirements: deadline is in the future and not too far in the future
        require(deadline > block.timestamp, Aera__DeadlineInPast());
        unchecked {
            require(deadline - block.timestamp <= MAX_SECONDS_TO_DEADLINE, Aera__DeadlineTooFarInFuture());
        }

        require(!PRICE_FEE_CALCULATOR.isVaultPaused(MULTI_DEPOSITOR_VAULT), Aera__PriceAndFeeCalculatorVaultPaused());
        // Requirements: fixed price requests cannot have a solver tip
        require(solverTip == 0 || !isFixedPrice, Aera__FixedPriceSolverTipNotAllowed());
    }
