### Title
User/MFA enumeration via distinguishable error bodies in `SessionsController.Create` / `orm.CreateSession` - ([File: core/web/sessions_controller.go], [File: core/sessions/localauth/orm.go])

### Summary
The `/sessions` login endpoint returns HTTP 401 for every failure case, but the JSON error body differs depending on whether the email is unregistered ("Invalid email"), the email is valid but the password is wrong ("Invalid password"), or the account has WebAuthn/MFA enabled (a serialized WebAuthn challenge JSON, or "MFA Error"). An unauthenticated attacker can use these distinct response bodies to enumerate valid accounts and determine whether MFA is enrolled.

### Finding Description
`SessionsController.Create` at [1](#0-0)  calls `GetUserWebAuthn` and then `CreateSession`, forwarding whatever error `CreateSession` returns directly into the response via `jsonAPIError(c, http.StatusUnauthorized, err)`. The status code is uniformly 401, but the error text is not normalized.

Inside `orm.CreateSession` at [2](#0-1) , the function returns four distinguishable error payloads:
- `"Invalid email"` when the requested email does not match a user record (comment claims this ordering is to prevent MFA leakage, but the string itself already discloses that the email is unregistered).
- `"Invalid password"` when the email is valid but the password is wrong — this alone confirms the email is registered.
- A serialized WebAuthn challenge JSON (returned as the error string itself) when email+password are correct and the account has MFA enrolled but no `WebAuthnData` was submitted — this directly discloses that MFA is enrolled on the account and leaks challenge/credential data.
- `"MFA Error"` for various MFA-related failures.

Because `jsonAPIError` will serialize `err.Error()` into the JSON response body, an attacker probing `POST /sessions` with arbitrary emails/passwords can trivially distinguish:
1. Non-existent email → `"Invalid email"`
2. Existing email, wrong password, no MFA → `"Invalid password"`
3. Existing email, correct/wrong password combined with MFA-enabled account → WebAuthn challenge JSON returned even before password success is confirdmed in some paths, or `"MFA Error"`

This confirms the account's existence and MFA enrollment status without needing to authenticate, purely from response body content — no timing analysis needed.

### Impact Explanation
This enables account enumeration and MFA-enrollment fingerprinting for the Chainlink node's admin UI login endpoint. Combined with credential stuffing lists, an attacker can identify which node-operator emails exist and which of them lack MFA, allowing them to prioritize weaker-defended accounts for brute-force/credential-stuffing attacks, which if successful grants full node admin API access (job management, key export triggers, bridge configuration, fund-moving transactions). This maps to Chainlink's "authentication weaknesses enabling account compromise" bounty class, though it stops short of a full authentication bypass by itself — it is an enabling/reconnaissance vulnerability rather than a direct compromise.

### Likelihood Explanation
Fully unauthenticated and requires no special privileges — a bare `POST /sessions` request. Response differences are entirely deterministic (not merely a timing side channel), making exploitation trivial and perfectly repeatable via scripted email lists.

### Recommendation
Normalize error handling so that `CreateSession` (or the controller) returns a single generic error message/body (e.g. `"invalid credentials"`) for the "invalid email," "invalid password," and "MFA error" cases, with identical status code and body shape. The WebAuthn challenge flow (needed for real MFA UX) should only be returned after credentials have already been verified in a way that does not leak account existence for wrong-email/wrong-password cases (i.e., perform a dummy password hash comparison for nonexistent emails to keep timing/response uniform, and avoid emitting different message strings for `Invalid email` vs `Invalid password`).

### Proof of Concept
Handler-level Go test plan:
1. Seed one user with no MFA and one user with WebAuthn registered.
2. Table-test `POST /sessions` with:
   - Random nonexistent email + random password → expect body `{"errors":[{"detail":"Invalid email"}]}`, status 401.
   - Existing no-MFA email + wrong password → expect body `{"errors":[{"detail":"Invalid password"}]}`, status 401.
   - Existing MFA-enabled email + correct password + no `WebAuthnData` → expect body containing serialized WebAuthn challenge JSON, status 401.
3. Assert all three cases return HTTP 401 but with textually distinct bodies, proving enumeration is possible purely from response content (`assert.NotEqual` on response bytes across cases, `assert.Equal` on status codes).
4. Optionally assert current behavior matches `orm.CreateSession` return values at [3](#0-2)  to confirm root cause.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

	// Load all valid MFA tokens associated with user's email
	uwas, err := o.GetUserWebAuthn(ctx, user.Email)
	if err != nil {
		// There was an error with the database query
		lggr.Errorf("Could not fetch user's MFA data: %v", err)
		return "", pkgerrors.New("MFA Error")
	}

	// No webauthn tokens registered for the current user, so normal authentication is now complete
	if len(uwas) == 0 {
		lggr.Infof("No MFA for user. Creating Session")
		session := sessions.NewSession()
		_, err = o.ds.ExecContext(ctx, "INSERT INTO sessions (id, email, last_used, created_at) VALUES ($1, $2, now(), now())", session.ID, user.Email)
		o.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, map[string]any{"email": sr.Email})
		return session.ID, err
	}

	// Next check if this session request includes the required WebAuthn challenge data
	// if not, return a 401 error for the frontend to prompt the user to provide this
	// data in the next round trip request (tap key to include webauthn data on the login page)
	if sr.WebAuthnData == "" {
		lggr.Warnf("Attempted login to MFA user. Generating challenge for user.")
		options, webauthnError := sessions.BeginWebAuthnLogin(user, uwas, sr)
		if webauthnError != nil {
			lggr.Errorf("Could not begin WebAuthn verification: %v", webauthnError)
			return "", pkgerrors.New("MFA Error")
		}

		j, jsonError := json.Marshal(options)
		if jsonError != nil {
			lggr.Errorf("Could not serialize WebAuthn challenge: %v", jsonError)
			return "", pkgerrors.New("MFA Error")
		}

		return "", pkgerrors.New(string(j))
	}
