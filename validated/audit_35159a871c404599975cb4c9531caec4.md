### Title
Blacklisted `protocolFeeRecipient` permanently blocks fee recipient's own fee claim - `FeeVault.claimFees()` ([File: v3/src/core/FeeVault.sol])

### Summary
`FeeVault.claimFees()` bundles two unconditional token transfers in a single atomic call: the caller's own earned fees and, if non-zero, the protocol's fees to `protocolFeeRecipient`. Because both transfers are executed with `SafeERC20.safeTransfer` (which reverts on failure) inside one transaction, if `FEE_TOKEN` (e.g. a compliance-blacklisting stablecoin like USDC) blacklists `protocolFeeRecipient`, the entire `claimFees()` call reverts every time it is invoked, permanently blocking the ordinary fee recipient from claiming fees they are legitimately entitled to. [1](#0-0) 

### Finding Description
`claimFees()` is called by the vault's `feeRecipient` (an ordinary, non-privileged entitled party, gated only by `onlyFeeRecipient`) to withdraw their accrued share of `FEE_TOKEN`. The function first calls `feeCalculator.claimFees(...)` which computes and *commits* (via storage mutation) both `feeRecipientFees` and `protocolFees`, then unconditionally transfers `feeRecipientFees` to `msg.sender` and, when `protocolFees != 0`, transfers `protocolFees` to `protocolFeeRecipient` in the same transaction: [2](#0-1) 

Because `BaseFeeCalculator.claimFees` already deducts the claimed amounts from `vaultAccruals` state as soon as it is invoked (effects happen before the second transfer reverts, but the whole external transaction — including this state mutation — is rolled back on revert since it's all one call frame): [3](#0-2) 

If `FEE_TOKEN.transfer(protocolFeeRecipient, protocolFees)` reverts — which happens whenever `protocolFeeRecipient` is blacklisted by the fee token issuer (a normal, expected compliance feature of tokens like USDC/USDT, not "faulty" third-party behavior) — the entire `claimFees()` transaction reverts. Since `protocolFees` accrues automatically over time via TVL/performance fee accrual and can rarely be exactly zero, the ordinary `feeRecipient` has **no way to skip or work around the bundled protocol-fee transfer**: there is no fallback-transfer mechanism (unlike `ProvisionerV2._transferWithFallback`, which explicitly guards against exactly this failure mode for request refunds via `trySafeTransfer` + fallback) and no alternate public function that claims only `feeRecipientFees` while excluding the protocol-fee leg. `claimProtocolFees()` is a separate function but does not help — it still requires the caller to be `protocolFeeRecipient` and does not decouple the fee recipient's own claim. [4](#0-3) 

This is the exact structural analog of the reported OpenQ bug: a single-caller transaction bundles a transfer to the caller together with an unconditional transfer to a *different* address; if that other address is blacklisted, the caller's own otherwise-legitimate withdrawal is blocked, because the "all transfers must succeed" invariant is broken by one non-caller-controlled recipient.

### Impact Explanation
Every legitimate fee recipient of an Aera V3 vault loses the ability to claim any accrued fees (`feeRecipientFees`) — freezing unclaimed yield — for as long as `protocolFeeRecipient` remains blacklisted for the vault's fee token and `protocolFees > 0` (which will almost always be true given continuous TVL/performance fee accrual). This is a freeze of user (fee-recipient) funds/unclaimed yield caused by ordinary, expected third-party token behavior, matching Immunefi's "temporary/permanent freezing of funds" severity bands.

### Likelihood Explanation
Preconditions are minimal and require no privileged action by Aera itself: the fee token must support a compliance blacklist (common for regulated stablecoins used as fee/numeraire tokens), and `protocolFeeRecipient` must become blacklisted (e.g., via regulatory/compliance action, address compromise reported to issuer, or sanctions listing) — an ordinary external event outside Aera's admin control at the time of the claim. Any fee recipient calling the standard, permissionless `claimFees()` entry point is affected; no attacker action is even required, only routine claim usage.

### Recommendation
Decouple the two transfers so a failure in one does not block the other:
- Use a fallback-transfer pattern for the protocol-fee leg (similar to `ProvisionerV2._transferWithFallback`/`trySafeTransfer`), or
- Wrap the protocol-fee transfer in `try/catch` (or a low-level call check) so a revert only leaves `protocolFees` in escrow/re-accrued rather than reverting the fee recipient's own transfer, or
- Split `claimFees()` into two independently callable transfers so the fee recipient's claim never depends on the protocol fee recipient's transfer succeeding.

### Proof of Concept
1. Deploy `FeeVault`/`DelayedFeeCalculator` (or fork mainnet with an existing Aera V3 vault) with `FEE_TOKEN = USDC` and a `protocolFeeRecipient` address `P`.
2. Advance time / submit snapshots so both `accruedFees` (vault/fee recipient) and `accruedProtocolFees` (protocol) are non-zero for the vault, per `BaseFeeCalculator._accrueFees` / `DelayedFeeCalculator._accrueFees`. [5](#0-4) 
3. As the real USDC blacklister (`impersonateAccount` on the USDC `owner`/`blacklister` role in the fork), call `blacklist(P)` on the USDC contract.
4. Call `feeVault.claimFees()` from `feeRecipient`.
5. Assert the call reverts (USDC `transfer` to blacklisted `P` reverts), and assert that `feeRecipient`'s USDC balance is unchanged and `vaultAccruals.accruedFees` for the vault remains non-zero and unclaimed — demonstrating the fee recipient's own entitled, non-blacklisted funds are permanently frozen by the unrelated blacklisted `protocolFeeRecipient`.

    function claimFees() external onlyFeeRecipient returns (uint256 feeRecipientFees, uint256 protocolFees) {
        address protocolFeeRecipient;

        // Interactions: claim the fees
        (feeRecipientFees, protocolFees, protocolFeeRecipient) =
            feeCalculator.claimFees(FEE_TOKEN.balanceOf(address(this)));

        // Requirements: check that the fee recipient has earned fees
        require(feeRecipientFees != 0, Aera__NoFeesToClaim());

        // Interactions: transfer the fees to the fee recipient
        FEE_TOKEN.safeTransfer(msg.sender, feeRecipientFees);
        // Log the fees claimed event
        emit FeesClaimed(msg.sender, feeRecipientFees);

        if (protocolFees != 0) {
            // Interactions: transfer the protocol fees to the protocol fee recipient
            FEE_TOKEN.safeTransfer(protocolFeeRecipient, protocolFees);
            // Log the protocol fees claimed event
            emit ProtocolFeesClaimed(protocolFeeRecipient, protocolFees);
        }
    }

    /// @inheritdoc IFeeCalculator
    function claimFees(uint256 feeTokenBalance) external virtual returns (uint256, uint256, address) {
        // Effects: hook called before claiming fees
        _beforeClaimFees();

        VaultAccruals storage vaultAccruals = _vaultAccruals[msg.sender];

        uint256 vaultEarnedFees = vaultAccruals.accruedFees;
        uint256 protocolEarnedFees = vaultAccruals.accruedProtocolFees;
        uint256 claimableProtocolFee = Math.min(feeTokenBalance, protocolEarnedFees);
        uint256 claimableVaultFee;
        unchecked {
            claimableVaultFee = Math.min(feeTokenBalance - claimableProtocolFee, vaultEarnedFees);
        }

        // Effects: update accrued fees
        unchecked {
            vaultAccruals.accruedProtocolFees = uint112(protocolEarnedFees - claimableProtocolFee);
            vaultAccruals.accruedFees = uint112(vaultEarnedFees - claimableVaultFee);
        }

        return (claimableVaultFee, claimableProtocolFee, protocolFeeRecipient);
    }

    function _accrueFees(
        VaultSnapshot storage vaultSnapshot,
        VaultAccruals storage vaultAccruals,
        uint256 lastFeeAccrualCached
    ) internal returns (uint256 protocolFeesEarned, uint256 vaultFeesEarned) {
        uint256 snapshotTimestamp = vaultSnapshot.timestamp;
        if (lastFeeAccrualCached >= snapshotTimestamp || vaultSnapshot.finalizedAt > block.timestamp) {
            // nothing to accrue
            return (0, 0);
        }

        // pending snapshot has become active, accrue fees
        (uint256 vaultPerformanceFeeEarned, uint256 protocolPerformanceFeeEarned) = _calculatePerformanceFees(
            vaultAccruals.fees.performance, vaultSnapshot.highestProfit, vaultSnapshot.lastHighestProfit
        );

        (uint256 vaultTvlFeeEarned, uint256 protocolTvlFeeEarned) = _calculateTvlFees(
            vaultAccruals.fees.tvl, vaultSnapshot.averageValue, snapshotTimestamp, lastFeeAccrualCached
        );

        // Effects: update the vault's state
        vaultSnapshot.lastHighestProfit = vaultSnapshot.highestProfit;
        vaultSnapshot.lastFeeAccrual = uint32(snapshotTimestamp);
        vaultAccruals.accruedFees += (vaultPerformanceFeeEarned + vaultTvlFeeEarned).toUint112();
        vaultAccruals.accruedProtocolFees += (protocolPerformanceFeeEarned + protocolTvlFeeEarned).toUint112();

        // Effects: delete the pending snapshot
        vaultSnapshot.averageValue = 0;
        vaultSnapshot.highestProfit = 0;
        vaultSnapshot.timestamp = 0;
        vaultSnapshot.finalizedAt = 0;

        protocolFeesEarned = protocolPerformanceFeeEarned + protocolTvlFeeEarned;
        vaultFeesEarned = vaultPerformanceFeeEarned + vaultTvlFeeEarned;
    }
