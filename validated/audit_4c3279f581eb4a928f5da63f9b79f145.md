### Title
Cross-user response hijacking via attacker-controlled `MessageId` collision in Gateway `WebAPIHandler.savedCallbacks` map - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The `WebAPIHandler` used by the internet-facing Gateway to service `web_api_trigger` requests stores pending user callbacks in a map keyed **solely by the client-supplied `MessageId`**, with no binding to the sender/requester identity. Because `MessageId` is fully attacker-controlled (it is the JSON-RPC request `ID` echoed straight from an unauthenticated HTTP client into the message body), an unprivileged actor can submit a request whose ID collides with another in-flight legitimate request. This overwrites the stored callback, so the node's later response — matched only by `MessageId` — is delivered to the attacker's callback instead of the legitimate requester's, causing response hijacking and denial of service for the victim's request.

### Finding Description
`HandleLegacyUserMessage` stores the caller's callback keyed purely by `msg.Body.MessageId`: [1](#0-0) 

`MessageId` is populated directly from the untrusted, attacker-controlled JSON-RPC request `ID` with no uniqueness/ownership check: [2](#0-1) 

When a node later replies with the `web_api_trigger` method, the Gateway looks the callback up **again only by `MessageId`**, deletes it, and forwards whatever payload it finds to that callback — it never verifies the response actually belongs to the same sender who registered it: [3](#0-2) 

This is in clear contrast to `RequestCache`, used elsewhere in the same package, which explicitly composes the cache key from `(sender, id)` to prevent exactly this kind of cross-tenant collision: [4](#0-3) 

The `savedCallbacks` map has no such sender binding, so any unprivileged client that can guess or observe another in-flight request's `MessageId` (message IDs are frequently short-lived, sequential, or otherwise low-entropy in client SDKs, and are visible to the requester and any intermediary) can:
1. Send a competing `web_api_trigger` request using the same `MessageId` before the legitimate DON response arrives.
2. Overwrite `h.savedCallbacks[msg.Body.MessageId]` with its own callback.
3. Receive the DON node's response payload intended for the victim (`sendHTTPMessageToClient`/trigger response data), i.e., cross-user response confusion / potential data exposure.
4. Cause the victim's original HTTP request to hang until timeout with no response delivered, i.e., denial of service targeted at a specific victim request — conceptually analogous to the reported bug, where an unprivileged caller mutates a shared keyed resource using a value it fully controls, corrupting state for another legitimate flow.

### Impact Explanation
An unauthenticated/unprivileged client reaching the Gateway's public endpoint can hijack another user's in-flight trigger response (confidentiality impact — response payload disclosure to the wrong party) and deny that user's request (availability impact), without needing any credentials beyond making an HTTP call to the same Gateway/DON endpoint. This falls squarely within the allowed "cross-user response confusion" and "internet-facing gateway (message envelopes, ... handlers, caches)" categories.

### Likelihood Explanation
Exploitability depends on the attacker's ability to predict or observe the victim's `MessageId` before its response returns. Many client implementations generate short, sequential, or otherwise predictable IDs, and the ID is not treated as a secret (it is present in plaintext, unsigned message bodies sent over the request path). Given the narrow race window (must land inside the pending-request lifetime, up to `defaultCallbackMaxAgeSec` = 120s) but the completely unauthenticated nature of the collision, likelihood is assessed as low-to-medium but concretely reachable with no special privileges.

### Recommendation
Bind the `savedCallbacks` key (and its lookup) to sender identity in the same way `RequestCache` already does — e.g., key on `(sender, MessageId)` instead of `MessageId` alone — or verify sender identity before overwriting/consuming an entry in `HandleLegacyUserMessage` / `handleWebAPITriggerMessage`. Reject/replace-safely on ID collision rather than silently overwriting the prior callback.

### Proof of Concept
1. Victim submits a legitimate `web_api_trigger` HTTP request to the Gateway with JSON-RPC `id = "X"`. This causes `h.savedCallbacks["X"] = victimCallback` (core/services/gateway/handlers/capabilities/handler.go:411-414).
2. Before the DON node responds, attacker submits their own `web_api_trigger` request also using `id = "X"`. This causes `h.savedCallbacks["X"] = attackerCallback`, silently overwriting the victim's entry (no uniqueness check exists in this map, unlike `RequestCache.NewRequest`, requestcache.go:60-63).
3. The DON node eventually responds with `Method == MethodWebAPITrigger` and `MessageId == "X"`. `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, finds `attackerCallback`, deletes the entry, and sends the victim's response data to the attacker (handler.go:148-162).
4. The victim's original HTTP request never receives a response and times out — denial of service — while the attacker receives data intended for the victim — cross-user response confusion.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
