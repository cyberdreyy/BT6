### Title
Global-only Primary Key on `block_rejection_signer_addrs` Collapses Per-Block Rejection Tracking Across Different Blocks - ([File: stacks-signer/src/signerdb.rs])

### Summary
The `block_rejection_signer_addrs` table is designed to record which blocks a given signer has rejected, but its schema keys rows by `signer_addr` alone instead of the `(signer_signature_hash, signer_addr)` pair. This is the same root-cause pattern as the reported "Retry Payload Channel Collision": a logically two-dimensional relationship (which signer rejected which specific block) is collapsed into a one-dimensional storage key (signer only), so a rejection recorded for one block is silently lost or overwritten the moment the same signer records a rejection for a *different* block.

### Finding Description
The table is created as:
```sql
CREATE TABLE IF NOT EXISTS block_rejection_signer_addrs (
    signer_signature_hash TEXT NOT NULL,
    signer_addr TEXT NOT NULL,
    PRIMARY KEY (signer_addr)
) STRICT;
``` [1](#0-0) 

The comment directly above this definition explicitly states the design intent — that `signer_signature_hash` alone uniquely identifies a block across all forks — yet the `PRIMARY KEY` constraint is placed on `signer_addr` only, not on the compound `(signer_signature_hash, signer_addr)` pair that the accompanying index (`block_rejection_signer_addrs_on_block_signature_hash`) is built to query against: [2](#0-1) 

Consequently a single signer address can hold, at any moment, at most one row in this table — associated with whatever block it most recently rejected. If signer `S` rejects block `A` (inserting `(hash_A, S)`), and later rejects an unrelated/different block `B` at a different height or tenure (inserting `(hash_B, S)`), the primary-key constraint on `signer_addr` forces the second insert to either overwrite the first row (turning it into `(hash_B, S)`, erasing `S`'s recorded rejection of `A`) or be ignored (silently dropping the fact that `S` rejected `B`), depending on the conflict-resolution clause used at the call site. Either way, the true set of signers who rejected block `A` no longer matches what the table reports.

This is corroborated by the intended read/write pattern elsewhere in the file: `add_block_signature` explicitly deletes rows scoped to *both* columns —
```sql
DELETE FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2
``` [3](#0-2) 
confirming the intended key is the pair `(signer_signature_hash, signer_addr)`, while the table's actual primary key enforces uniqueness on `signer_addr` alone — an exact structural analog of the Toki bridge bug where `revertReceive[chainId][sequence]` was keyed only on the coarser `chainId` component instead of the true per-channel identity.

### Impact Explanation
This breaks the equality between the *aggregated per-block rejection tally* (what this table is meant to report for a given `signer_signature_hash`) and the *actual set of signers who verifiably rejected that specific block*. Any signer who rejects more than one distinct block over the life of the signer process will have earlier rejection records silently dropped or reattributed to a later block. Code paths that rely on this table to determine whether a block has accumulated enough distinct-signer rejections (to transition it, e.g., to a globally-rejected state) will undercount rejections for the affected block, potentially leaving a block that should be recognized as rejected in an indeterminate state — a liveness-affecting miscount of the aggregated rejection weight versus the true verified set of rejecting signers.

### Likelihood Explanation
Triggering this requires no majority of signers, no other signer's key, and no privileged access — a single signer naturally rejecting two different block proposals during normal operation (e.g., across different tenures/forks, which is routine given block proposals happen continuously) is enough to hit the collision. This makes it a high-likelihood latent defect rather than an exotic edge case.

### Recommendation
Change the primary key of `block_rejection_signer_addrs` to the composite `(signer_signature_hash, signer_addr)`, matching the index already built for signature-hash lookups and the delete pattern already used in `add_block_signature`, so that rejections recorded for distinct blocks by the same signer cannot collide or overwrite one another.

### Proof of Concept
1. Signer `S` receives block proposal `A` (`signer_signature_hash = hash_A`) and rejects it; the code inserts/records `(hash_A, S)` into `block_rejection_signer_addrs`.
2. Later, in a different tenure/fork, signer `S` receives block proposal `B` (`signer_signature_hash = hash_B`) and also rejects it; the insert for `(hash_B, S)` conflicts with the existing row on the `signer_addr` primary key.
3. Depending on the conflict-resolution mode used at the call site, either the row is overwritten to `(hash_B, S)` (losing `S`'s rejection of `A`) or the new insert is silently ignored (losing `S`'s rejection of `B`).
4. Any subsequent query that counts distinct rejecting signers for `hash_A` (via the `block_rejection_signer_addrs_on_block_signature_hash` index) undercounts, since `S`'s rejection of `A` is no longer present in the table — breaking the aggregated-rejection-weight vs. verified-rejecting-signers equality for block `A`.
