### Title
Confirmations from removed multisig members are not purged from other pending requests, allowing execution below the live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` in the multisig2 contract only removes pending requests whose *original signer* matches the removed member, but does not scrub that member's `confirm` votes recorded on *other* still-pending requests. Once the member is deleted, its stale confirmation remains counted in `confirmations` sets, so a later `confirm` from a live member can push the total recorded count to `num_confirmations` even though fewer than `num_confirmations` *currently live* members actually approved the request.

### Finding Description
`confirm` counts confirmations purely from the `confirmations: LookupMap<RequestId, HashSet<String>>` map and executes once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

Membership removal is handled by `delete_member`, which only cleans up requests *originated* by the removed member (`r.member == member`) and removes `num_requests_pk` bookkeeping for that member — it does **not** scan other requests' `confirmations` sets to strip votes cast by the removed member: [2](#0-1) 

Because `confirm` never re-validates that every string in the stored `confirmations` set still corresponds to a current member (`current_member()` is only used to identify *the caller*, not to re-verify prior confirmers), a vote cast by a member who is later removed remains "live" for threshold-counting purposes on any request that member confirmed but did not create.

This breaks the intended custody/authorization binding of a K-of-N multisig: `live confirming members == recorded confirmations counted toward num_confirmations`. After a member is removed, `recorded confirmations > live confirming members` for any request that removed member had confirmed earlier, letting a request execute (including `Transfer`, `FunctionCall`, `AddKey`, etc.) with fewer than `num_confirmations` currently-live approvals.

### Impact Explanation
This is Critical impact per the rubric: "a multisig request executed below threshold." An attacker/participant scenario:
- num_confirmations = 3, members = {A, B, C, D}.
- A adds a `Transfer` request (not yet confirmed).
- B confirms it (confirmations = {B}).
- Separately, members later vote to `DeleteMember { member: B }` (a legitimate governance action unrelated to the pending transfer request). This succeeds and B is removed from `members`, but the transfer request above is untouched because `r.member` (A) ≠ B.
- Now only A, C, D are live members. C confirms the transfer (confirmations = {B, C} → len 2). D confirms (confirmations = {B, C, D} → len 3) → `3 >= num_confirmations` → request executes.
- The transfer executed with only 2 *live* member confirmations (C, D) plus one from a removed, no-longer-trusted member (B), even though the contract's guarantee is that 3 currently-authorized members must approve.

This directly undermines the multisig's core security property (K distinct *current* signers required) and can move NEAR out of the account with fewer live approvals than configured, or push through `AddKey`/`FunctionCall` actions that should have required a full quorum of current members.

### Likelihood Explanation
Likelihood is realistic in normal multisig lifecycle usage: membership changes (e.g., rotating a compromised or departing member) are an expected, routine multisig operation, and any request left pending (even briefly) while some members already confirmed it is a common occurrence — there is no explicit requirement to drain all pending requests before rotating membership. No `panic`/assert enforces that confirmers are still current members before counting them in `confirm`.

### Recommendation
When counting confirmations for the threshold check in `confirm`, filter the stored confirmation set to only those entries whose `MultisigMember` (parsed back from the string) is still contained in `self.members`, or alternatively make `delete_member` scrub the removed member's entry from every request's `confirmations` set (not just requests it originated), and update stored `HashSet<String>` sizes accordingly. Re-validate membership of every confirmer at the moment a request is about to execute.

### Proof of Concept
Using the existing test scaffolding in `multisig2/src/lib.rs`:
1. `MultiSigContract::new(members(), 3)` with members {A, B, C, D}.
2. `add_request` a `Transfer` request as A (unconfirmed).
3. `confirm` as B → confirmations = {B}.
4. Execute a separate `add_request_and_confirm`/`confirm` sequence (with A, C, D) for `DeleteMember { member: B }` (self-request), which succeeds since `members.len() - 1 (=3) >= num_confirmations (=3)`; B's access key/account is removed from `self.members`. The earlier transfer request is untouched since its `r.member == A`.
5. `confirm` the transfer request as C → confirmations = {B, C} (len 2).
6. `confirm` the transfer request as D → confirmations = {B, C, D} (len 3) → `3 >= 3` → `execute_request` fires the `Transfer`.

Result: the transfer executed with confirmations from only 2 live members (C, D) plus 1 from a member (B) already removed from `self.members`, violating the "3 live members must approve" guarantee. [2](#0-1) [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
