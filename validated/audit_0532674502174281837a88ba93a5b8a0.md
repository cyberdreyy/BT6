### Title
Unfunded instant-withdraw receipts are claimable at par, draining funded claims and default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays out the full `instantWithdrawsRequests[_user]` balance and burns the receipt tokens without checking that the corresponding underlying was ever collected via `collectInstantWithdrawFunds`. This is the stale-object analog of CVE-2022-4191 (use-after-free): a receipt whose funding was never performed — i.e., the underlying "object" backing it was never materialized — is still treated as a live, fully-backed claim and redeemed against unrelated strategy balances.

### Finding Description
The instant-withdraw flow has two phases:

1. `requestInstantWithdraw` burns the CDO's strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws` [1](#0-0) .
2. Funding only happens when the CDO later calls `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls underlying into the strategy [2](#0-1) .

`claimInstantWithdrawRequest` burns the user's receipt balance and calls `_transferFundedClaim` unconditionally:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

There is no check that this user's receipt was actually funded — `pendingInstantWithdraws` can be non-zero (unfunded remainder) and the claim still succeeds [3](#0-2) . The code itself acknowledges this gap: `defaultPendingClaimBasis` treats a non-zero `pendingInstantWithdraws` as "the still-unfunded remainder" and `_defaultPrefundedInstantReserve` computes the already-funded portion as `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` [4](#0-3) [5](#0-4) .

The strategy's underlying balance is a shared pool containing:
- underlying collected for *other* users' funded normal withdraws (`collectWithdrawFunds`),
- underlying collected for other users' funded instant withdraws,
- `defaultRecoveryReserve` backing finalized default-recovery claims.

An attacker holding an unfunded instant receipt calls `claimInstantWithdrawRequest` (through the CDO, which is the `onlyIdleCDO` entry point) and is paid at par from this shared pool, stealing other users' funded claims.

### Impact Explanation
Direct theft: the attacker redeems a receipt for which no underlying was ever deposited into the strategy, consuming balances reserved for honest users' funded withdraw claims or the `defaultRecoveryReserve`. Quantified loss equals the attacker's `instantWithdrawsRequests` balance, bounded above by the strategy's free underlying balance (funded claims + reserve). Honest claimants later hit failed transfers or receive nothing — permanent loss of their funded claims.

### Likelihood Explanation
Reachable whenever an instant receipt exists but `collectInstantWithdrawFunds` was not (or only partially) called for the full amount — e.g., the epoch stops on the normal path, borrower funding partially fails, or a mid-epoch default interrupts collection. The attacker needs only to be a tranche holder able to call `requestInstantWithdraw` and later `claimInstantWithdrawRequest`; no privileged role is required. The sequence is: deposit → request instant withdraw → epoch stops without instant funding → claim at par against other users' reserves.

Caveat: I could not fully read `IdleCDOEpochVariant`'s `claimInstantWithdrawRequest`/instant-queue path in the iterations available. If the CDO gates claims on full collection of instant funds or routes all instant claims through `IdleCDOEpochQueue` (which does price funded epochs, per `claimWithdrawRequest`'s `epochWithdrawPrice`/`epochPendingClaims` checks [6](#0-5) ), exploitability depends on that gating being absent for the direct-claim path. The strategy-level function itself contains no such guard.

### Recommendation
In `claimInstantWithdrawRequest`, only pay the funded portion: track per-epoch funded vs. unfunded instant basis and revert or pay zero while `pendingInstantWithdraws` still covers the user's receipt, or require the CDO to assert funding completion (e.g., pass a funded flag or verify `instantWithdrawsRequestsByEpoch[_user][epoch]` is backed by collected funds) before `_transferFundedClaim`.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testUnfundedInstantWithdrawClaim() external {
    // setup: user1 deposits, user2 deposits
    uint256 tranches1 = _depositWithUser(user1, 100e6);
    _depositWithUser(user2, 100e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // user1 requests instant withdraw; receipt minted, pendingInstantWithdraws += amt
    _requestInstantWithdrawWithUser(user1, tranches1);

    // epoch stops on normal path: borrower repays normal basis only,
    // collectInstantWithdrawFunds never called for user1's receipt
    _stopCurrentEpoch();

    // user2 requests normal withdraw; borrower funds it via collectWithdrawFunds
    // -> strategy now holds underlying backing user2's claim
    _requestWithdrawWithUser(user2, /*...*/);
    _startEpochAndFund(); // collectWithdrawFunds pulls user2's funding

    // user1 claims unfunded instant receipt at par
    vm.prank(user1);
    cdoEpoch.claimInstantWithdrawRequest(); // succeeds, drains user2's funded balance

    // user2's funded claim now undercollateralized -> revert/shortfall
    vm.prank(user2);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertion: `strategy.pendingInstantWithdraws() > 0` at the moment `claimInstantWithdrawRequest` succeeds, proving the payout was unfunded.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];

  function claimWithdrawRequest(uint256 _epoch) external {
    // check if withdraw requests were processed and claimed for the epoch
    uint256 _withdrawPrice = epochWithdrawPrice[_epoch];
    _checkNotAllowed(
      (_withdrawPrice == 0 && !isEpochWithdrawZero[_epoch]) ||
      epochPendingClaims[_epoch] != 0
    );
    // amount is in tranche tokens
    uint256 amount = userWithdrawalsEpochs[msg.sender][_epoch];
    if (amount == 0) {
      return;
    }
    // reset user withdraw request counter for the epoch
    userWithdrawalsEpochs[msg.sender][_epoch] = 0;
    // transfer underlyings to user based on the withdraw price of that epoch
    if (_withdrawPrice != 0) {
      IERC20Detailed(underlying).safeTransfer(msg.sender, amount * _withdrawPrice / ONE_TRANCHE);
    }
  }
