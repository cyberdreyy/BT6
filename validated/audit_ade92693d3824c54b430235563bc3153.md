### Title
Unbounded per-conflict node round-trips in `get_signed_conflicts`/`conflict_still_blocks` let a single miner wedge the signer's single-threaded event loop - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The KeyTrap-class bug is "cheap attacker input forces the validator to perform disproportionate, serially-chained expensive work before it can conclude a verdict." The analog here is in the pre-commit-threshold signing path: `handle_block_pre_commit` calls `SignerDb::get_signed_conflicts(height, hash)`, which returns *every* signed block (any state, any tenure) at or above the given height [1](#0-0) , and then, for each fresh conflict, sequentially performs up to two blocking HTTP calls to the local node (`reorg_permit_stands` → `get_sortition_by_burn_hash`, and `conflict_still_blocks` → `get_sortition_by_burn_hash` + `get_tenure_tip`) inside a synchronous `.find()`/`.any()` [2](#0-1) . `conflict_still_blocks` and `reorg_permit_stands` are shown in full at [3](#0-2) .

### Finding Description
A single miner controls how many distinct blocks it proposes per tenure and can cause the signer set to locally-sign (`signed_self`) or globally-sign several of them over the course of a reward cycle, e.g. by repeatedly winning sortition, building a tenure-start block, having it locally accepted, then abandoning it for a new tenure-start block on a fresh (attacker-timed, but legitimate) sortition before the old one reaches 70%. Each such block remains a row in the `blocks` table with `signed_self`/`signed_group` set; nothing in `get_signed_conflicts` bounds the count of rows returned, and the `blocks` table itself is not pruned by height/count (only `superseded_tenures` bookkeeping is pruned via `MAX_FORK_DEPTH`, per `docs/signer-flows.md:461`). Every time a *new* proposal at or above one of those historical heights crosses the pre-commit threshold, `handle_block_pre_commit` re-walks the full conflict list and, for each fresh one, blocks the single signer runloop thread on network I/O to the local stacks-node (`reorg_permit_stands`, `conflict_still_blocks`). Because `process_event` (`stacks-signer/src/v0/signer.rs:333-416`) and the outer `RunLoop::run_one_pass` (`stacks-signer/src/runloop.rs:514-616`) run this on a single thread with no concurrency and no per-conflict budget/timeout beyond the underlying `reqwest::blocking` client's timeout, a large-enough conflict set turns one incoming pre-commit-threshold event into O(n) sequential blocking RPCs — the "closest-encloser proof" analog: iterative, chained validation work whose cost scales with attacker-influenced history rather than being amortized/cached/capped.

### Impact Explanation
While this stalls, the signer thread cannot process other events (new proposals, validation responses, other pre-commits) queued behind it, delaying its own signature on the *currently valid* block past `block_proposal_timeout`/`tenure_last_block_proposal_timeout`. This matches the "High" bar: a signer wedged (temporarily but repeatedly, tenure after tenure) into not signing valid blocks in time due to self-inflicted, attacker-triggerable synchronous I/O cost — a liveness degradation rather than a majority-requiring safety break.

### Likelihood Explanation
Requires only the single active miner's ordinary ability to propose/abandon competing tenure-start blocks across a reward cycle to grow the historical `blocks` table with signed rows, then trigger reprocessing at a shared height — no cooperation from other signers or majority control is needed. However, this is bounded by real economic/timing costs to the miner (each signed conflict requires actually winning sortition and getting local/global signatures), and the per-call cost is a local RPC (not attacker-controlled network latency), which limits how severe the wedge is in practice compared to KeyTrap's remote CPU exhaustion.

### Recommendation
Bound `get_signed_conflicts` (e.g., cap row count or restrict to a bounded lookback window/height distance), cache `reorg_permit_stands`/`conflict_still_blocks` results per conflict for a short interval so repeated evaluations don't re-issue RPCs, and/or move the node round-trips off the critical single-threaded event-processing path (e.g., async prefetch or a background worker) so a growing conflict set cannot block new-proposal handling.

### Proof of Concept
1. As the sole active miner for several tenures within a reward cycle, alternate: win sortition, propose a tenure-start block B_i, let the signer set locally/globally sign it, then abandon it (never confirming it on-chain) and immediately win the next sortition with a competing tenure-start block B_{i+1} at the same or higher height.
2. Repeat enough times that `blocks` accumulates many rows with `signed_self`/`signed_group` set at/above a given height (no pruning removes them).
3. Propose a new block at that height; once it crosses the 70% pre-commit threshold, `handle_block_pre_commit` calls `get_signed_conflicts` and iterates the full list, issuing sequential blocking RPCs to the local node for each fresh conflict via `reorg_permit_stands`/`conflict_still_blocks`, delaying the signer's own signature and its ability to process concurrently-arriving proposals/validations.

Note: I could not execute this in the codebase to measure actual timing impact or confirm the practical size of `n` achievable within realistic reward-cycle constraints — this assessment is based on static code-path analysis only.
