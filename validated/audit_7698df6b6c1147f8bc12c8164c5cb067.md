### Title
Hardcoded universal `MAX_CONF_INTERVAL` (5%) confidence-interval clamp applied uniformly across all bank oracles regardless of asset volatility, silently understating price uncertainty for volatile assets - (File: `programs/marginfi/src/state/price.rs`)

### Summary
Marginfi clamps every oracle's confidence interval to a single hardcoded constant, `MAX_CONF_INTERVAL = 5%`, before it is used to bias asset/liability prices in health calculations, irrespective of each bank's own `oracle_max_confidence` setting and irrespective of the underlying asset's real volatility. This is the same bug class as the referenced Basin `MultiFlowPump` finding: a single, non-asset-specific hard cap is applied indiscriminately to reserves/prices of assets with very different volatility profiles, causing distortion for some assets while having no effect on others.

### Finding Description
`type-crate/src/constants.rs` defines a single global constant used for every bank/oracle: [1](#0-0) 

This constant is applied identically to Pyth push oracles in `get_confidence_interval` (`PythPushOraclePriceFeed`): [2](#0-1) 

and identically to Switchboard pull oracles (`SwitchboardPullPriceFeed::get_confidence_interval`): [3](#0-2) 

In both cases, the oracle's reported confidence is first checked against the bank-configurable `oracle_max_confidence` (which can be set per-bank up to reflect an asset's real volatility), but the value actually consumed by health/pricing math is `min(reported_confidence, 5%_of_price)` - the hardcoded 5% ceiling always wins regardless of what `oracle_max_confidence` was configured to. The documentation itself confirms this is a blanket, non-per-asset limit: [4](#0-3) 

This clamped confidence value then directly biases asset and liability prices used for every health/borrow/liquidation calculation: [5](#0-4) [6](#0-5) [7](#0-6) 

Exactly like the Basin `MultiFlowPump` cap (`LOG_MAX_INCREASE`/`LOG_MAX_DECREASE`), this constant is a single one-size-fits-all bound applied to every bank the pool manages - from stablecoins (USDC/USDT, whose real oracle confidence is typically well under 5%, so the cap never engages) to genuinely volatile or thin-liquidity tokens whose Pyth/Switchboard-reported confidence can legitimately exceed 5% during real volatility/liquidity events. For those volatile assets, the true reported uncertainty is silently truncated to 5%, making the "conservative" low/high bias calculation less conservative than the oracle itself says is warranted.

### Impact Explanation
For volatile or thinly-traded bank assets, when the oracle's real confidence interval genuinely exceeds 5% of the price (a normal condition for smaller/volatile tokens during a fast market move), the protocol still only reduces asset value by 5% (instead of the true, larger, confidence-implied haircut) and only increases liability value by 5% (instead of the true, larger, confidence-implied markup). This directly inflates a user's computed collateral value and understates their computed debt value relative to what the oracle's own uncertainty indicates, at exactly the moments (high volatility) when the safety margin matters most. This can let accounts pass Initial-health borrow checks and avoid Maintenance-health liquidation triggers that should have failed/triggered under the oracle's true reported confidence, i.e., an exploitable misvaluation with direct financial effect (excess borrowing power / delayed liquidation against real risk). Meanwhile, for stable assets the cap is inert, exactly mirroring the C4 report's "no effect on stable assets, but distorts volatile ones" pattern.

### Likelihood Explanation
This triggers under fully permissionless, unprivileged conditions: any user performing a borrow, withdrawal, or health check on a bank whose oracle happens to report >5% confidence (which does occur for real Pyth/Switchboard feeds on volatile or low-liquidity assets during market stress) will automatically get the clamped, less-conservative valuation - no admin action or oracle manipulation is required, only normal market conditions on an asset the group has legitimately listed. Every `health_pulse`/borrow/withdraw/liquidate path that calls `get_price_and_confidence_of_type` / `get_confidence_interval` is affected identically.

### Recommendation
Do not apply a single hardcoded ceiling (`MAX_CONF_INTERVAL`) to the confidence interval used for pricing. Instead, rely solely on the already per-bank-configurable `oracle_max_confidence` as an outright rejection threshold (fail the price fetch if confidence exceeds it), and use the oracle's actual reported confidence (up to that per-bank threshold) for the price-bias calculation rather than additionally clamping it to a global 5%. If a ceiling is still desired as a sanity backstop, make it a per-bank configurable value set at bank-creation time (mirroring `oracle_max_confidence`) rather than a protocol-wide constant, so volatile and stable assets are each governed by parameters appropriate to their own risk profile.

### Proof of Concept
1. Configure a bank for a volatile/low-liquidity token with `oracle_max_confidence` set high (e.g. 20%) to explicitly allow wider confidence during volatility, per `guides/RISK_AND_LIQUIDATORS/RISK_PARAMETERS.md`.
2. Have the Pyth/Switchboard feed report a genuine confidence interval of, say, 12% of price (a realistic scenario for a volatile asset during a fast move) - below the bank's configured 20% rejection threshold, so `get_confidence_interval` does not error out.
3. In `PythPushOraclePriceFeed::get_confidence_interval` / `SwitchboardPullPriceFeed::get_confidence_interval`, observe that `capped_conf_interval = price * MAX_CONF_INTERVAL (5%)` and the function returns `min(conf_interval, capped_conf_interval)` = 5%, not the true 12% reported by the oracle. [2](#0-1) 
4. Depositing this asset as collateral, `calc_weighted_asset_value_standalone` biases the price down by only 5% (`PriceBias::Low`) instead of the true 12% the oracle reported, inflating the asset's counted collateral value versus what the oracle's own confidence data implies is safe, letting the account borrow more or avoid liquidation compared to a correct 12% haircut. [6](#0-5)

```rust
#[inline]
fn apply_price_bias(price: OraclePriceWithConfidence, bias: PriceBias) -> MarginfiResult<I80F48> {
    let price = match bias {
        PriceBias::Low => price
            .price
            .checked_sub(price.confidence)
            .ok_or_else(math_error!()),
        PriceBias::High => price
            .price
            .checked_add(price.confidence)
            .ok_or_else(math_error!()),
    }?;
    Ok(price)
}
```
