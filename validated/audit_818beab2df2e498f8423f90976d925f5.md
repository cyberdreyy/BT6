### Title
Stale per-epoch instant-withdraw basis double-counts already-claimed receipts, corrupting default recovery pricing and permanently freezing later claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. An unprivileged tranche holder who requests an instant withdrawal, lets it be funded, claims it, and then requests a second instant withdrawal in the same epoch permanently poisons the epoch's claim basis. If that epoch then defaults, `defaultPendingClaimBasis` counts the already-paid amount again, `finalizeDefaultRecovery` misprices `defaultRecoveryPrice`/`defaultRecoveryReserve`, and the user's own defaulted claim reverts on arithmetic underflow, permanently freezing their receipt and leaving residual recovery funds stranded.

### Finding Description
The analog of CVE-2018-14471 (a crafted input reaching a code path that dereferences state that was never populated/never invalidated, causing a crash) maps to `IdleCreditVault` reading stale per-epoch receipt records that are never cleared on the normal claim path.

In `requestInstantWithdraw`, each request writes three buckets: the aggregate `instantWithdrawsRequests[_user]`, the per-user-per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the per-epoch total `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . The normal claim path only zeroes the aggregate and burns the minted receipt tokens — the two per-epoch mappings are left permanently nonzero [2](#0-1) .

Attack sequence (running epoch N, buffered instant-withdraw mode):

1. Attacker calls `requestInstantWithdraw(x)`. The CDO funds it via `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` but does not touch `instantWithdrawClaimsByEpoch[N]` [3](#0-2) .
2. Attacker calls `claimInstantWithdrawRequest`, is paid `x` at par; `instantWithdrawsRequestsByEpoch[attacker][N]` and `instantWithdrawClaimsByEpoch[N]` still hold `x`.
3. Attacker calls `requestInstantWithdraw(y)` in the same epoch N. Both mappings now hold `x + y`, while the attacker's actual receipt balance and the unfunded `pendingInstantWithdraws` equal only `y`.
4. The epoch ends with the borrower defaulting. During `finalizeDefaultRecovery`, `defaultPendingClaimBasis()` reads `instantWithdrawClaimsByEpoch[epochNumber]` and includes the already-paid `x` in the recovery basis [4](#0-3) . `_defaultPrefundedInstantReserve()` then treats the phantom `x` as already-held reserve (`instantBasis - pendingInstant`), inflating `defaultRecoveryReserve` and `defaultRecoveryPrice` with funds that were already paid out and no longer exist [5](#0-4) [6](#0-5) .
5. When the attacker (or any user in the same position) later calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = x + y` and executes `instantWithdrawsRequests[_user] -= claimBasis`, which underflows because the aggregate is only `y` — the claim reverts forever [7](#0-6) .

### Impact Explanation
Two distinct losses:

- **Mispriced recovery (theft/socialized loss):** `defaultRecoveryReserve` is credited with `x` tokens that were already paid out in step 2, so `recoveryPrice` is set as if the strategy holds `reserveAmount` underlyings it does not actually hold. Earlier claimants are over-paid at the inflated `defaultRecoveryPrice` while the true balance is short by `x`; the final defaulted-epoch claimants' `_transferDefaultRecovery`/`safeTransfer` calls revert on insufficient balance, permanently stranding their share of the recovery [8](#0-7) .
- **Permanent freezing of a valid claim:** the attacker's own second receipt `y` can never be claimed because the defaulted-epoch claim path always underflows on the stale `x`. The `y` underlyings collected for that receipt remain locked in the strategy with no viable claim path.

No existing guard prevents this: the skim/reserve check in `_transferFundedClaim` only protects against spending below the (already corrupted) reserve [9](#0-8) , and `defaultInstantWithdrawsFinalized` gating only decides which path runs, not whether the per-epoch basis is internally consistent [10](#0-9) . The attacker is a KYC-passing lender holding tranche tokens; no privileged role misbehavior is required — the default only needs an honest borrower failing to repay, which the invariant allows.

### Likelihood Explanation
Requires the instant-withdraw flow to be enabled and an epoch to default while a same-epoch re-request exists. Funding/claiming/re-requesting within one epoch is ordinary user behavior (the feature exists precisely for fast liquidity), so the state that triggers the corruption is cheap to create and persists indefinitely once written. The loss is bounded by the claimed-then-re-requested instant amounts, but the underflow freeze is deterministic once the epoch defaults.

### Recommendation
Keep per-epoch receipt records consistent with the aggregate on every exit path:

- In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` for the epoch(s) being claimed, or store the request epoch alongside the aggregate so the per-epoch basis can be cleared exactly.
- Alternatively, prevent re-requesting while stale per-epoch basis exists (mirroring the `requestWithdraw` guard at lines 263–271 that blocks a new request when a loss-adjusted receipt is pending [11](#0-10) ), and have `collectInstantWithdrawFunds` clear `instantWithdrawClaimsByEpoch` for funded receipts.
- Add an invariant test: after any successful instant claim, `instantWithdrawClaimsByEpoch` must equal the sum of outstanding (unclaimed, unfunded-or-funded) per-user per-epoch receipts only.

### Proof of Concept
Foundry fork test against the deployed-style `IdleCDOEpochVariant`/`IdleCreditVault` pair (instant withdraws enabled, e.g. prefunded or buffered instant mode):

```solidity
function testStaleInstantEpochBasisBreaksDefaultRecovery() external {
    // setup: attacker deposits into AA tranche, epoch N starts, instant withdraws enabled
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    uint256 x = 1_000 * ONE_SCALE;
    uint256 y = 2_000 * ONE_SCALE;

    // 1) request + fund + claim first instant withdraw in epoch N
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(x, AA);
    vm.prank(manager); // or whoever triggers collection
    // cdoEpoch routes funds via strategy.collectInstantWithdrawFunds(x)
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest(); // paid x at par

    // per-epoch basis still holds x (the bug)
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, strategy.epochNumber()), x);
    assertEq(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), x);

    // 2) second instant request in the same epoch
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(y, AA);
    // basis now x + y, real unfunded pendingInstantWithdraws == y
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, strategy.epochNumber()), x + y);
    assertEq(strategy.pendingInstantWithdraws(), y);

    // 3) borrower defaults at stopEpoch, owner finalizes with partial recovery
    _stopEpochToDefault();
    uint256 recovered = /* partial recovery */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // inflated basis: phantom x counted as prefunded reserve
    // => defaultRecoveryPrice and defaultRecoveryReserve are overstated by x

    // 4) attacker's legitimate receipt y can never be claimed
    vm.prank(attacker);
    vm.expectRevert(); // arithmetic underflow in instantWithdrawsRequests[_user] -= (x + y)
    cdoEpoch.claimInstantWithdrawRequest();

    // 5) another defaulted-epoch claimant is over/under-paid relative to true reserve
    // and the last claimant's transfer reverts for insufficient balance,
    // stranding recovery dust in the strategy.
}
```

Expected results: `defaultPendingClaimBasis()` exceeds the true outstanding receipt value by `x`; `claimInstantWithdrawRequest` reverts for the re-requesting user; total payouts exceed actual held underlyings by `x`, leaving the last claimant frozen.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
