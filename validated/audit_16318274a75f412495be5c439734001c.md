### Title
Signer weight double-counted across `total_weight_approved` and `total_weight_rejected` when a signer's Accept follows a Reject for the same block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
In `StackerDBListener`'s handling of `SignerMessageV0::BlockResponse`, the guard that prevents re-counting a signer's weight is scoped per-response-kind instead of per-block. A signer's weight can be added to `total_weight_rejected` on a `Rejected` message and later also added to `total_weight_approved` on an `Accepted` message for the *same* `block_sighash`, because the `Accepted` branch only checks `block.gathered_signatures.contains_key(&slot_id)` (never `responded_signers`), while `responded_signers` was already populated by the earlier rejection. This mirrors the BOLD-reported bug class where one contribution is folded into two different tallies that are supposed to be mutually exclusive/summed correctly.

### Finding Description
`BlockStatus` tracks two independent weight tallies plus a `responded_signers` set meant to make a signer's vote final/one-shot: [1](#0-0) 

For an `Accepted` response, the code adds to `total_weight_approved` only if the slot is *not already in* `gathered_signatures`, then unconditionally records the slot into both `gathered_signatures` and `responded_signers`: [2](#0-1) 

For a `Rejected` response, the code adds to `total_weight_rejected` only if `responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot has responded at all): [3](#0-2) 

The asymmetry is the bug: 
- If Accept arrives first, `gathered_signatures` gets the slot, so a later Reject is correctly blocked (`responded_signers.insert` returns false because Accept already inserted it into `responded_signers`).
- If **Reject arrives first**, only `responded_signers` gets the slot (not `gathered_signatures`). A later Accept for the same block checks `!gathered_signatures.contains_key(&slot_id)`, which is still `true`, so the Accept branch adds the signer's weight to `total_weight_approved` as well — even though that same signer's weight is already counted in `total_weight_rejected`.

The net effect: the same signer weight is counted in both `total_weight_approved` and `total_weight_rejected` simultaneously, so `total_weight_approved + total_weight_rejected` can exceed the true sum of distinct signer weights, breaking the "aggregated-weight vs verified accepts" invariant the coordinator relies on in `wait_for_signer_signatures_effective` in `signer_coordinator.rs` (`block_status.total_weight_approved >= self.weight_threshold` / `total_weight_rejected.saturating_add(weight_threshold) > total_weight`): [4](#0-3) 

Because message ordering across a signer's StackerDB slot is not guaranteed relative to processing order at the miner (gossip/relay can reorder, and a signer can legitimately post a Reject and then an Accept for the same sighash after re-validating), a single misbehaving or simply out-of-order signer (one slot) can cause its weight to be double-booked into both totals for one block.

### Impact Explanation
This inflates `total_weight_approved` beyond the true weight of signers currently standing behind acceptance, letting the block-acceptance threshold be reached with fewer *genuinely* accepting signers than required, while — because `total_weight_rejected` is unaffected by the fix path — it can also simultaneously look closer to the rejection threshold. In the acceptance direction this is the more dangerous outcome: the miner coordinator could believe 70% weight has approved a block (and assemble/broadcast it) when the honestly-summed accepting weight is actually lower, undermining the safety guarantee that `assemble_signature` / `wait_for_signer_signatures_effective` are supposed to enforce before pushing a block to the node. This is analogous to the "aggregated-weight vs verified-accepts" equality violation called out in scope.

### Likelihood Explanation
Triggerable by a single signer slot: any signer (or gossip that redelivers/reorders its own two legitimate-looking messages) that sends a `Rejected` then later an `Accepted` BlockResponse for the same `signer_signature_hash` reaches this code path without needing any other signer's cooperation, majority, or key material. This satisfies the "one-slot miner/signer plus gossip" reachability bar.

### Recommendation
- **Short term**: In the `Accepted` branch, additionally check that the slot is not present with a rejection weight already counted (e.g., track a single `HashMap<u32, ResponseKind>` per slot, or check `responded_signers` combined with a way to know whether the prior response was a rejection) before adding to `total_weight_approved`. Symmetrically, decide the intended semantics up front — either responses are final (first response wins, later ones ignored) or the last response overwrites the previous one and both counters are updated coherently (subtract from the old counter before adding to the new one).
- **Long term**: Add unit tests exercising Reject-then-Accept and Accept-then-Reject orderings from the same slot for the same block hash, asserting that the signer's weight is counted in exactly one of `total_weight_approved` / `total_weight_rejected` at any time.

### Proof of Concept
1. Miner's `StackerDBListener` is tracking a `BlockStatus` for `block_sighash`.
2. Signer slot `S` (weight `w`) sends `BlockResponse::Rejected` for `block_sighash`. The listener sets `block.responded_signers.insert(S)` → `true`; `block.total_weight_rejected += w`.
3. Signer slot `S` later sends `BlockResponse::Accepted` for the same `block_sighash` (e.g., after re-evaluating a re-broadcast/duplicate proposal, or via gossip redelivering a stale message after a local flip). The listener checks `!block.gathered_signatures.contains_key(&S)` → `true` (this map was never touched by the Reject path), so `block.total_weight_approved += w` executes.
4. Now `block.total_weight_rejected` and `block.total_weight_approved` both include `w` for the same signer `S`, inflating the sum used by `signer_coordinator.rs`'s threshold checks (`total_weight_approved >= weight_threshold`, `total_weight_rejected.saturating_add(weight_threshold) > total_weight`) beyond what an honest weight partition would allow.
