### Title
Token-2022 transfer hook callback executes mid-instruction before origination-fee, rate-limiter, and health-check state updates finalize — cross-function/cross-program reentrancy surface in `lending_account_borrow`/`lending_account_withdraw` - ([File: programs/marginfi/src/instructions/marginfi_account/borrow.rs])

### Summary
The reported Timeswap `mint()` bug is that an external callback executes in the middle of the function, before several important pieces of state (reserve, collateral, debt totals) are finalized, violating Checks-Effects-Interactions and opening cross-function reentrancy. The analogous pattern exists in marginfi's core lending instructions (`lending_account_borrow`, `lending_account_withdraw`, and the integration deposit/withdraw flows for Drift/Kamino/Solend/JupLend): when a bank's mint is a Token-2022 mint with an active `TransferHook` extension, the SPL token transfer performed mid-instruction via `bank.withdraw_spl_transfer`/`deposit_spl_transfer` triggers a CPI into an arbitrary, attacker-controllable hook program — a genuine external callback — while marginfi's own instruction still has unfinished state updates (origination fee bookkeeping, rate-limiter outflow recording, bank cache update, health-cache/health-check) pending after that call.

### Finding Description
In `lending_account_borrow` ( [1](#0-0) ), the sequence is:
1. `bank_account.borrow(...)` records the liability increase (state effect).
2. `bank.withdraw_spl_transfer(...)` performs the SPL transfer of borrowed funds to the user — for Token-2022 mints, this uses `spl_token_2022::onchain::invoke_transfer_checked`, which invokes the mint's registered `TransferHook` program as a CPI callback if one is set [2](#0-1) .
3. Only *after* that external CPI does the instruction go on to update origination fee accounting for the group/program fee vaults [3](#0-2) , run `check_account_init_health`, call `record_withdrawal_outflow` (rate-limiter state), and finally `bank.update_bank_cache` / `bank.update_cache_price` [4](#0-3) .

The same ordering pattern (state update → external CPI mid-function → more state updates/health-check afterward) recurs in `lending_account_withdraw` (transfer then `bank.update_bank_cache` and event emission) [5](#0-4) , and in the venue-integration withdraw flows for Solend/Kamino/Drift/JupLend, where the CPI to the external venue and the SPL transfer occur, and only afterward is `check_account_init_health` and `bank.update_bank_cache`/`update_cache_price` executed [6](#0-5) .

The protocol does have a `has_transfer_hook` check, but it is only enforced in the unrelated `lending_pool_emissions_deposit` instruction [7](#0-6)  and in `utils/general.rs` [8](#0-7) . There is no equivalent check preventing banks with Token-2022 transfer-hook mints from being used in `lending_account_borrow`, `lending_account_withdraw`, `lending_account_deposit`, or `lending_account_repay`. The test suite explicitly exercises deposit/borrow/liquidate flows with a transfer-hook mint via `#[cfg(feature = "transfer-hook")]` test helpers, confirming this is a supported (not rejected) configuration for core lending operations [9](#0-8) [10](#0-9) .

Unlike Solana's own program-reentrancy restriction (a program cannot directly call back into itself while already executing on the call stack under normal CPI depth rules), this is not a same-program reentrancy but a genuine cross-program callback: the transfer-hook program is invoked by the SPL Token-2022 program as part of `TransferChecked`, and that hook program is fully attacker-controlled if the attacker can get a hook-enabled mint whitelisted as a bank mint (group admin action) or if an existing bank's mint has its hook program/authority mutated post-listing (Token-2022 transfer hooks can be updated by the mint's transfer-hook authority unless explicitly immutable). During this window, the hook program executes with full CPI capability while marginfi's account (still holding the `marginfi_account` and `bank` AccountLoader mutable borrows dropped mid function, per the block scoping) is in a transient/intermediate accounting state — the liability/balance updates from step 1 have been applied, but origination fees, rate-limiter counters, and the final health check have not.

### Impact Explanation
If a bank is configured (or reconfigured) with a Token-2022 mint carrying an active `TransferHook`, that hook can execute arbitrary CPI logic mid-borrow/mid-withdraw before the risk/health check and before fee/rate-limiter bookkeeping finalize. This could be leveraged to:
- Re-enter other marginfi instructions or other integrated protocols while account state is only partially updated, potentially bypassing invariants that assume atomic, fully-updated state at CPI boundaries (e.g., interacting with the same or other banks' vaults, or with other users' accounts, before this transaction's outflow/health effects are recorded).
- Manipulate or observe intermediate state to compute more favorable borrow/withdraw amounts before the final risk-engine check runs, since `check_account_init_health` runs after the transfer/hook callback in `borrow.rs`.
This is a lower-severity variant of the H-04 class relative to the original Timeswap finding because Solana CPI/account model limits some reentrancy vectors (borrow-checker style account write locks prevent double mutable borrow of the same account within one transaction), but the mid-function external callback before finalized fee/rate-limiter/health state is a real CEI violation and increases the attack surface for any bank onboarded with an unvetted Token-2022 mint.

### Likelihood Explanation
Likelihood is dependent on privileged action: a bank must be configured with a Token-2022 mint that has an active transfer hook, which normally requires group-admin action (`lending_pool_add_bank`) or a permissionless-pool listing path if any transfer-hook mints are not filtered out there. The `has_transfer_hook` check exists in the codebase specifically to block hook mints for emissions deposits, showing hook-mint mints are anticipated to reach the bank/mint set, yet the equivalent guard is missing from the core borrow/withdraw/repay/deposit code paths. If any permissionless bank-listing path (e.g., `add_pool_permissionless`) allows arbitrary Token-2022 mints without filtering transfer hooks, likelihood rises to unprivileged/attacker-reachable.

### Recommendation
- Apply the same `has_transfer_hook` (and `nonzero_fee`) checks used in `lending_pool_emissions_deposit` to bank creation/configuration (`lending_pool_add_bank`, `configure_bank`, and any permissionless pool-add paths) so that banks backed by Token-2022 mints with active transfer hooks cannot be listed, or reject the corresponding instructions at execution time when a hook is detected.
- Where transfer-hook mints must be supported, restructure `lending_account_borrow`, `lending_account_withdraw`, and equivalent venue-integration deposit/withdraw instructions so that all internal state updates (origination fee accounting, rate-limiter recording, `update_bank_cache`, and the risk-engine health check) are finalized *before* the token transfer/CPI is invoked, consistent with Checks-Effects-Interactions.
- Add a reentrancy/lock flag (similar to `ACCOUNT_IN_FLASHLOAN`) guarding these instructions for the duration of the external CPI, or explicit re-validation immediately after the transfer completes.

### Proof of Concept
Not independently exploited in this analysis (would require constructing a Token-2022 mint with an active `TransferHook` registered against a marginfi bank and observing during `lending_account_borrow` that the hook program can execute state-dependent logic before `check_account_init_health`/`record_withdrawal_outflow`/fee accounting complete). The repository's own test harness demonstrates the supported code path for exercising transfer-hook mints in deposit/borrow/liquidate flows: [10](#0-9)  and [9](#0-8) , while the `has_transfer_hook` guard that should generalize this protection is confined to `lending_pool_emissions_deposit` [7](#0-6) . Whether a bank-listing path currently permits an attacker (non-admin) to register a transfer-hook mint was not conclusively verified within the available tool budget; this should be confirmed via `lending_pool_add_bank`/`add_pool_permissionless` review in a follow-up session.

/// Returns `true` if the given mint has an active transfer hook program.
/// If the hook is present but no program is active it would return false.
pub fn has_transfer_hook(mint_ai: AccountInfo) -> MarginfiResult<bool> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(false);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    if let Ok(hook) = mint.get_extension::<TransferHook>() {
        let program_id: Option<Pubkey> = Option::from(hook.program_id);
        return Ok(program_id.is_some());
    }

    Ok(false)
}
