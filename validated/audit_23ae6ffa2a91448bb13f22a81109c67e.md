### Title
Loss-adjusted withdraw claims only haircut the latest request epoch, letting earlier unfunded receipts escape the loss and drain funded reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The upstream bug skips a mode check (`TT`) before dereferencing a pointer (`SSPTPTR`) that is only valid in specific modes. The analog in `IdleCreditVault` is identical in shape: `_claimLossAdjustedWithdrawRequest` dereferences a single "latest request" pointer (`lastWithdrawRequest[_user]`) to locate a user's loss-adjusted receipt, but `pendingWithdraws` — the basis over which `lossRecoveryPriceByEpoch` is computed — aggregates receipts from *all* unclaimed epochs. When a user holds receipts spanning multiple epochs and the latest epoch is stopped with a loss, only the latest-epoch portion is haircut; the older portion falls through to `_claimFundedWithdrawRequest` and is paid at par, even though the funded amount assumed the loss was applied to the whole aggregate.

### Finding Description
- `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * 1e18 / pendingWithdraws` over the *entire* `pendingWithdraws` aggregate and stores it under `lossRecoveryPriceByEpoch[epochNumber]` [1](#0-0) 
- `requestWithdraw` adds each request to `withdrawsRequestsByEpoch[_user][currentEpoch]` and moves the `lastWithdrawRequest[_user]` pointer to the newest epoch, without requiring the user to claim older epochs [2](#0-1) 
- On claim, `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and only clears the basis stored under that single epoch [3](#0-2) 
- `_clearWithdrawClaimForEpoch` subtracts only `withdrawsRequestsByEpoch[_user][_claimEpoch]` from `withdrawsRequests[_user]`, so the older-epoch remainder is then paid at par by `_claimFundedWithdrawRequest` [4](#0-3) [5](#0-4) 

The `requestWithdraw` guard (revert if `lossRecoveryPriceByEpoch[lastWithdrawRequest] != 0` with an existing receipt) only blocks *new* requests after a loss epoch is recorded; it does not prevent a user from holding receipts in two different epochs *before* any loss occurs.

### Impact Explanation
Insolvency / direct theft from other receipt holders. The strategy collects `funded = Σbasis × price` underlying for the loss epoch, but a multi-epoch user withdraws `basis_old + basis_new × price`, i.e., `basis_old × (1 − price)` more than their fair share. Either later claimants' `_transferFundedClaim` transfers revert (permanent freezing of their unclaimed withdrawals) or earlier/faster claimants extract the shortfall. The stolen amount equals the attacker's older-epoch basis times the haircut (`1 − lossRecoveryPrice`), directly quantifiable per epoch.

### Likelihood Explanation
Requires only unprivileged actions in a normal epoch lifecycle: a KYC'd lender (or any tranche holder routed through `IdleCDOEpochVariant.requestWithdraw`) who (1) requests a withdraw in epoch N, (2) declines to claim after it matures, (3) requests again in epoch N+1, then waits for an honest `stopEpochWithDuration(_lossAmount)` by the borrower/manager. No privileged collusion is needed — loss epochs are a normal protocol event. The attacker's extra payout is automatic on their next `claimWithdrawRequest`.

### Recommendation
Apply the loss price to the user's *entire* `pendingWithdraws` contribution, not just the `lastWithdrawRequest` slice. Options: track per-epoch funded receipts and iterate/clear all epochs with nonzero `withdrawsRequestsByEpoch` (or store cumulative requested basis per user), or disallow a new `requestWithdraw` while the user has any unclaimed matured receipt. At minimum, `_claimLossAdjustedWithdrawRequest` should compute `claimBasis` over `withdrawsRequests[_user] + apr0 principal` for the loss epoch rather than the per-epoch mapping slice.

### Proof of Concept
Foundry fork PoC (sketch, run against the repo's harness):

```solidity
// Setup: honest deposits from lpAA, attacker deposits into AA tranche, KYC'd.
// Epoch N (running):
cdoEpoch.requestWithdraw(attackerTrancheBal1, address(AAtranche)); // basis B1, epoch N
// stop epoch N honestly (full funding) -> epochNumber becomes N+1, B1 claimable
// Epoch N+1 (buffer/running):
cdoEpoch.requestWithdraw(attackerTrancheBal2, address(AAtranche)); // basis B2, lastWithdrawRequest = N+1
// Epoch N+1 ends with a loss: borrower funds only (B1+B2)*p
strategy.collectWithdrawFunds((B1 + B2) * p / 1e18); // lossRecoveryPriceByEpoch[N+1] = p

// Attacker claims:
cdoEpoch.claimWithdrawRequest();
// _claimLossAdjustedWithdrawRequest pays  B2 * p
// _claimFundedWithdrawRequest     pays  B1 at par   <-- escapes the haircut
// attackerReceived = B1 + B2*p  >  funded share (B1+B2)*p
// Shortfall = B1*(1-p) is taken from strategy balance that backs other receipts;
// a subsequent honest claimant's _transferFundedClaim reverts/underpays.
assertGt(attackerReceived, (B1 + B2) * p / 1e18);
```

Key assertion: with `p < 1e18`, the attacker's payout exceeds the loss-adjusted pro-rata share by `B1 * (1 - p)`, and the residual strategy balance is insufficient to satisfy remaining `withdrawsRequests` — demonstrating theft/freezing of other users' unclaimed withdrawals.

Note: I could not fully trace the exact ordering of `epochNumber` increments relative to `collectWithdrawFunds` inside `stopEpochWithDuration` within `IdleCDOEpochVariant` (the snippet range I read didn't include that function body), so the PoC assumes `lossRecoveryPriceByEpoch` is keyed to the request epoch `N+1` consistent with `lastWithdrawRequest`. If the key lands on `N` instead, the same flaw applies symmetrically (the `N+1` receipt escapes instead).

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
