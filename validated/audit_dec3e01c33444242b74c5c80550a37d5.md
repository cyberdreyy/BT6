## Analysis

Mapping the report's bug class — a state/validity check enforced in one function but silently dropped in a sibling function that later mutates the same protected state — onto the signer's block-approval pipeline surfaces a real gap between the proposal-time miner-validity check and the checks re-run before a signature is actually produced.

### Where the full check lives (proposal time only)

`GlobalStateView::check_proposal` (v2) validates, against the *current* active-miner view (`MinerState::ActiveMiner`), that:
- the block's `consensus_hash` matches the active miner's `tenure_id`,
- the block's recovered miner pubkey hash matches `current_miner_pkh`,
- the PoX bitvec is all-1s. [1](#0-0) 

The equivalent v1 path (`SortitionsView::check_proposal`) does the analogous work against the local sortition view. This is invoked only from `handle_block_proposal` → `check_block_against_state` → `check_block_against_global_state`/`check_block_against_local_state`, i.e. exclusively at proposal arrival. [2](#0-1) 

### Where the check is missing (validate-ok and signing time)

Both later points where the signer can still commit to a signature — `handle_block_validate_ok` and the pre-commit-threshold crossing in `handle_block_pre_commit` — re-verify the block only via `check_block_against_signer_db_state`, which is explicitly documented as an *incomplete* re-check: [3](#0-2) 

That function only reruns `check_tenure_change_confirms_parent` / `check_latest_block_in_tenure` (tip/height confirmation) — it never re-derives the current `GlobalStateView`/`SortitionsView` and never re-checks `current_miner_pkh`, `consensus_hash` vs. active `tenure_id`, or the PoX bitvec. Both call sites rely on it exclusively: [4](#0-3) [5](#0-4) 

The project's own documentation confirms this design gap exists and is *only* mitigated for one specific sub-case (the `DuplicateBlockFound` dedup check), leaving the miner-pubkey/consensus-hash/bitvec checks with no equivalent mitigation at all: [6](#0-5) 

### The window

Between a block's proposal-time `check_proposal` pass and the moment a signature is actually produced (`mark_pre_committed` at validate-ok, `mark_locally_accepted` at pre-commit threshold), the signer's view of the *active miner* can change — e.g., a new sortition arrives and updates `local_state_machine.current_miner`/`global_state_evaluator`, or the tenure the block belongs to becomes stale/superseded. Section 5 of the docs explicitly acknowledges this general risk ("we may have signed a _different_ block at the same height... before the signature leaves the box") but the mitigation implemented there (`get_signed_conflicts`/`conflict_still_blocks`/`reorg_permit_stands`) only guards against *sibling-height signature conflicts*, not against the specific case where the *same* previously-valid block's miner/consensus-hash pairing has gone stale relative to the newly active miner.

## Verdict

### Title
Signer can pre-commit/sign a block whose miner validity was only checked at proposal time, not re-verified before signing — (File: stacks-signer/src/v0/signer.rs)

### Summary
`GlobalStateView::check_proposal`/`SortitionsView::check_proposal` verify a proposed block's `consensus_hash`, miner pubkey hash, and PoX bitvec against the signer's *current* active-miner view, but this verification runs only once, at proposal arrival. The two later points that actually produce a pre-commit/signature — `handle_block_validate_ok` and the pre-commit-threshold branch of `handle_block_pre_commit` — re-check the block exclusively through `check_block_against_signer_db_state`, a function explicitly documented as incomplete, which only re-validates tenure-tip confirmation and never re-derives the active miner or re-checks pubkey/consensus-hash/bitvec.

### Finding Description
1. A block proposal `B` from miner `A` (currently active per the signer's `SignerStateMachine`/`SortitionsView`) arrives; `check_proposal` passes and `B` is submitted to the node for validation and stored (`insert_block`).
2. Before the node's validation response returns (or before the pre-commit threshold is reached), the signer's view of the active miner changes — e.g., a new burn block/sortition arrives and `local_state_machine`/`global_state_evaluator` now reflect miner `C` as active, or `B`'s tenure becomes superseded — without `B`'s stored `BlockInfo` being invalidated.
3. When the validation response for `B` arrives, `handle_block_validate_ok` calls only `check_block_against_signer_db_state`, which checks tenure/tip confirmation but not miner pubkey hash / consensus-hash / bitvec against the now-current active-miner view; if it passes, `B` is marked `PreCommitted` and a pre-commit is broadcast.
4. Once the pre-commit threshold is reached, `handle_block_pre_commit` again calls only `check_block_against_signer_db_state` before calling `mark_locally_accepted` and broadcasting a signature — again without re-running the miner-validity checks from `check_proposal`.
5. The signer thereby signs a block whose miner/consensus-hash pairing was validated against a stale snapshot of "who is canonical," not the view held at signing time.

### Impact Explanation
This can result in a signer producing a valid signature over a block associated with a miner that is no longer the active/canonical miner in the signer's own state — a signature over a non-canonical block. This falls under the Critical impact category ("a signer signing an invalid, non-canonical, or conflicting block").

### Likelihood Explanation
Requires only ordinary gossip/timing conditions a single miner (plus normal signer-set gossip) can trigger: a validation response or pre-commit threshold crossing arriving after the active-miner view has moved on, which is a routine occurrence around tenure changes/sortition arrivals and does not require control of a majority of signers or any keys beyond the proposing miner's own.

### Recommendation
Re-run the same miner-pubkey-hash, consensus-hash-vs-active-tenure, and bitvec checks performed in `check_proposal` inside `check_block_against_signer_db_state` (or an equivalent freshly-derived `GlobalStateView`/`SortitionsView` check), so that every code path leading to `mark_pre_committed`/`mark_locally_accepted` re-validates against the signer's current active-miner view, not just the tenure-tip confirmation subset.

### Proof of Concept
Conceptual reproduction (no external tooling required, purely a signer-logic race already acknowledged in the docs' section 5 discussion of "the world... re-checked before the signature leaves the box"):
1. Miner A proposes block B for tenure T; signer validates and stores B (`Unprocessed`→pending validation).
2. A new sortition arrives, and the signer's `local_state_machine` switches active miner to C (e.g., A's tenure is deemed inactive/reorg-eligible) — `global_state_evaluator`/`SortitionsView` are updated accordingly for future *proposals*, but B's already-stored `BlockInfo` is untouched.
3. The stacks-node's validation response for B (submitted before the switch) arrives; `handle_block_validate_ok` → `check_block_against_signer_db_state(stacks_client, &B)` — this only checks `check_latest_block_in_tenure`/`check_tenure_change_confirms_parent`, which can still pass for B's own tenure T. B is marked `PreCommitted` and a pre-commit is broadcast.
4. If ≥70% weighted pre-commits accumulate (from peers whose views haven't caught up either), `handle_block_pre_commit`'s threshold branch again calls only `check_block_against_signer_db_state`, which passes for the same reason, and the signer signs B via `mark_locally_accepted`.
5. B is now signed even though, per the signer's own current active-miner view, A is no longer the canonical miner — the exact miner-pubkey/consensus-hash check from `check_proposal` (step 1's gate) was never re-applied at the point the signature was actually produced.
