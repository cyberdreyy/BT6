### Title
Permissionless `KeeperCloseOrder` allows arbitrary redirection of rent and unauthorized deletion of a user's protective order - ([File: programs/marginfi/src/instructions/marginfi_account/order.rs])

### Summary
The `KeeperCloseOrder` instruction accounts struct requires no signer at all and lets the caller supply an arbitrary `fee_recipient` account with, per the code's own comment, "no checks whatsoever." This mirrors the reported bug class of a dispatch/handler path that executes a state-changing, value-moving action without verifying the caller's authorization.

### Finding Description
`KeeperCloseOrder` is defined with only two `UncheckedAccount`s and no `Signer<'info>` field whatsoever: [1](#0-0) 

The `order` account is closed with `close = fee_recipient`, meaning the order's rent lamports are transferred to whatever `fee_recipient` account the transaction supplies — validated only by the comment "no checks whatsoever, keeper decides this without restriction." Unlike `CloseOrder`, which requires the account `authority` to sign and be authorized via `is_signer_authorized`, `KeeperCloseOrder` has no equivalent authorization gate in the `Accounts` struct: [2](#0-1) 

The only stated intent, per the doc comment on `marginfi_account`, is to allow this instruction "to be called even when the marginfi account was closed," with "ownership check ... in the handler." I was unable to locate/verify the `keeper_close_order` handler function body itself within the indexed content (it is referenced in tests, `lib.rs`, and events, but its implementation was not found in the search), so I cannot confirm what runtime gating (if any) restricts this to only "abandoned" orders whose parent account is truly gone, versus allowing closure of live, still-relevant orders (e.g., an active stop-loss/take-profit that has not yet triggered).

### Impact Explanation
If the handler does not strictly verify that the parent `marginfi_account` is closed/defunct before permitting `KeeperCloseOrder` to fire, any unauthorized caller could:
- Delete a live user-created protective order (`Order`, containing stop-loss/take-profit parameters) without the account authority's consent, causing the user to lose their intended risk protection.
- Redirect the reclaimed rent lamports to an arbitrary `fee_recipient` of the caller's choosing instead of the legitimate order owner, since `fee_recipient` has no `has_one`/ownership constraint tying it to the account authority.

Even in the best case (handler does correctly gate on the parent account being closed), the missing signer and unconstrained `fee_recipient` remain a permissionless value-redirection primitive: whoever races to call this after account closure captures the rent regardless of who originally paid it, since the `Accounts` validation performs no ownership check to protect that value stream.

### Likelihood Explanation
The instruction is exposed via the public program IDL/instruction set and requires no privileged role — any signer can construct and submit this transaction (per marginfi's own access-control matrix, permissionless instructions are explicitly a known pattern, but they are all designed to be self-limiting, e.g. "Collect bank fees" only *moves funds between the protocol's own vaults*, not to attacker-chosen destinations). `KeeperCloseOrder` is the one place found where the destination of a closed-account's lamports is unconstrained by any `has_one`/PDA relationship to the legitimate order owner.

### Recommendation
- Constrain `fee_recipient` in `KeeperCloseOrder` to be validated against the order's rightful destination (e.g., derive/require it match the `marginfi_account.authority`, or a group-designated fee wallet), instead of leaving it as a fully unconstrained `UncheckedAccount`.
- In the handler, explicitly and unconditionally enforce (not just in a doc comment) that `marginfi_account` is provably closed/uninitialized (e.g., check `data_is_empty()` or owner != program) before allowing the close to proceed, so this permissionless path cannot be used to grief live orders.
- Add integration tests asserting `KeeperCloseOrder` fails against a still-open, still-valid `marginfi_account`/order pair, and that `fee_recipient` cannot diverge from the legitimate owner/destination.

### Proof of Concept
1. Attacker observes an `Order` PDA (stop-loss/take-profit) belonging to a victim's `MarginfiAccount`.
2. Attacker submits a `KeeperCloseOrder` transaction supplying the victim's `order` PDA, the victim's `marginfi_account`, and an attacker-controlled `fee_recipient` account — no signature from the account authority or any admin is required by the `Accounts` struct.
3. If the handler's gating on "account already closed" is incomplete or bypassable, the order is closed and its rent lamports are transferred to the attacker's `fee_recipient`, deleting the victim's protective order and redirecting the reclaimed rent away from the legitimate owner.

Note: Due to indexing limits, the body of `keeper_close_order` (the handler function enforcing whatever runtime gating exists) could not be located/confirmed in this session. A Devin session with full repository access should verify the exact handler logic in `programs/marginfi/src/instructions/marginfi_account/order.rs` to confirm whether this is fully exploitable as described or only a minor rent-capture griefing vector.

#[derive(Accounts)]
pub struct CloseOrder<'info> {
    pub group: AccountLoader<'info, MarginfiGroup>,

    #[account(
        mut,
        has_one = group @ MarginfiError::InvalidGroup,
        constraint = {
            let a = marginfi_account.load()?;
            account_not_frozen_for_authority(&a, authority.key())
        } @ MarginfiError::AccountFrozen,
        constraint = {
            let a = marginfi_account.load()?;
            let g = group.load()?;
            is_signer_authorized(&a, g.admin, authority.key(), false, false)
        } @ MarginfiError::Unauthorized
    )]
    pub marginfi_account: AccountLoader<'info, MarginfiAccount>,

    pub authority: Signer<'info>,

    #[account(
