## Title
Stale confirmations from removed multisig members still count toward execution threshold - ([File: multisig/src/lib.rs], [File: multisig2/src/lib.rs])

## Summary
Both `multisig` and `multisig2` contracts allow a pending `MultiSigRequest` to be executed once enough confirmations accumulate for a `request_id`. When a member/key is removed (`DeleteKey` in `multisig`, `DeleteMember` in `multisig2`), the code only purges requests that the removed member *originated*, but never purges confirmations the removed member gave on requests originated by *other* members. This is the same class of bug as the reported `Forwarder` issue: an approval, once given, remains valid forever with no invalidation mechanism tied to the current state of trust (there, signer key state; here, live membership), letting a request execute with fewer *live* approvals than the configured threshold.

## Finding Description
In `multisig/src/lib.rs`, `execute_request`'s `DeleteKey` branch only removes requests whose `signer_pk` (the member who *created* the request) equals the deleted key: [1](#0-0) 

It never inspects the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map for entries where the deleted key appears as a *confirmer* on requests created by someone else. `confirm()` simply counts set size: [2](#0-1) 

`multisig2/src/lib.rs` has the identical pattern. `delete_member` only cleans requests where `r.member == member` (the request originator), not confirmations given by that member on other requests: [3](#0-2) 

`confirm()` again just counts the stored confirmation set against `num_confirmations`: [4](#0-3) 

Because a member's historical confirmation on a still-pending request is never invalidated when that member is later removed, the binding "confirmations counted == confirmations from currently live members" is broken: `confirmations.len()` can include identities that are no longer in `self.members` (v2) or no longer hold an access key (v1).

## Impact Explanation
This lets a `MultiSigRequest` execute (e.g., a `Transfer`, `AddKey`/`AddMember` granting new access, or a `FunctionCall`) using a mix of stale and live confirmations that together satisfy `num_confirmations`, even though the number of members who are *live and trusted at the time of execution* is below that threshold. This is exactly the Critical impact "a multisig request executed below threshold" from the rules: the contract's core custody guarantee (k distinct current signers must approve before funds move or privileges change) is violated using only unprivileged, ordinary member/key-removal governance actions plus normal confirm calls — no owner/foundation intervention beyond legitimate multisig operations is required to trigger the divergence.

## Likelihood Explanation
The scenario requires only:
1. A request pending confirmation (normal operation).
2. A member who confirmed it is later removed (a routine, expected lifecycle event — e.g., rotating out a compromised or departing signer), itself an ordinary multisig action.
3. Remaining members continue confirming the pre-existing request past the point of removal.

None of these steps require a malicious validator, redeploy, or social engineering — they are standard multisig usage patterns (member rotation is explicitly a supported feature via `DeleteKey`/`DeleteMember`), making this readily reachable in practice whenever member rotation occurs while requests are outstanding.

## Recommendation
When removing a key/member, also purge that identity from every `confirmations` entry across all pending `requests`, not only the requests it originated (mirroring how `assert_valid_request`/`current_member` checks live membership at confirmation time, apply the same liveness check when *counting* confirmations, or actively strip departed members' confirmations at removal time). Alternatively, validate at `confirm()` time / execution time that every recorded confirming identity is still a current member/key before counting it toward `num_confirmations`.

## Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]`, `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(Transfer{amount: X, receiver_id: attacker})` → request `R` has confirmations `{A}`.
3. `B` calls `confirm(R)` → confirmations `{A, B}` (2/3, not yet executed).
4. Members legitimately remove `A` (e.g., key rotation) via a separate `DeleteMember{member: A}` request that gathers its own 3 confirmations from `B`, `C`, and whichever signer is still valid, and executes — see `delete_member` at [5](#0-4) , which only cleans requests `A` *originated*, not `R` (originated by `A`... note: to avoid ambiguity, have `A` add the transfer request but have `add_request` be called instead by member `D`/another party so `R.member != A`, or simply note `A` is filtered only from requests where `r.member == A`; any request added by someone else that `A` merely confirmed is untouched).
5. `A` is now removed from `self.members`; `A` can no longer call any multisig method.
6. `C` calls `confirm(R)` → `confirmations.len() (2, including stale `A`) + 1 >= num_confirmations (3)` → `execute_request` fires the `Transfer` to the attacker, even though only `B` and `C` are currently live, trusted members — one fewer live approval than the configured `num_confirmations` threshold.

        self.assert_valid_request(request_id);

        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);

        } else {

            self.confirmations.insert(&request_id, &confirmations);

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
