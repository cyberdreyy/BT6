### Title
Stale confirmations from deleted multisig members still count toward the approval threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` in the `multisig2` contract removes a departing member's own pending requests but never removes that member's confirmations recorded on requests created by other members. Because `confirm()` simply counts entries in the `confirmations` `HashSet<String>` against `num_confirmations`, a request can later be executed using a mix of live and phantom (deleted-member) confirmations, letting it pass with fewer live-member approvals than the configured threshold.

### Finding Description
`add_request` creates an empty `HashSet<String>` in `confirmations` for the new request [1](#0-0) . Each subsequent `confirm()` call adds the caller's member identity string to that set until the size reaches `num_confirmations`, at which point the request executes [2](#0-1) .

`delete_member` is supposed to purge multisig state tied to a removed member. It removes the member from `self.members`, deletes the member's access key, and clears **requests originally added by that member** along with their confirmations sets — but it filters only on `r.member == member` (i.e., the request's *creator*), not on whether the member appears inside the confirmations of *other* requests: [3](#0-2) 

If member `X` had already called `confirm()` on a request created by member `Y` (adding `X.to_string()` into that request's `confirmations` set) and is later removed via `DeleteMember`, `X`'s confirmation entry remains in that request's `confirmations` set untouched, because that request's ID is not in the `request_ids` filtered by creator.

The binding that should hold is: `count(confirmations for request) == count(distinct LIVE members who confirmed)`. After a `DeleteMember` action, this becomes `count(confirmations) > count(live members who confirmed)`, since a phantom entry from the removed member persists.

### Impact Explanation
This breaks the confirmation-threshold authorization boundary: `execute_request` can run — moving NEAR, deploying code, adding/deleting keys, or making arbitrary `FunctionCall`s on behalf of the multisig account — with fewer than `num_confirmations` *live* members actually having approved it. For example, with `num_confirmations = 3` and a request already having 2 confirmations (one from a member who is later removed, one from a live member), a single additional live confirmation completes the count to 3, even though only 2 currently-authorized members ever approved it. This is a threshold/authorization violation matching the Critical impact category ("a multisig request executed below threshold").

### Likelihood Explanation
The precondition is realistic in normal multisig operation: a pending request receives a partial confirmation, then (before the request is deleted, confirmed to completion, or naturally expires) the confirming member is removed via a `DeleteMember` request (e.g., during routine key rotation or offboarding). No malicious cooperation beyond that ordinary sequence of legitimate multisig actions is required, and the remaining live members confirming the request have no visibility that one of the counted confirmations belongs to a member who is no longer authorized, since `get_confirmations` returns the raw string list without cross-checking current membership [4](#0-3) .

### Recommendation
When counting confirmations in `confirm()`, filter the stored confirmation strings against current `self.members` (or actively prune confirmations for a removed member across *all* pending requests, not just the ones they created) before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig deployed with `num_confirmations = 3` and members `{A, B, C, D}` (4 members).
2. Member `Y` (e.g., `D`) creates request `R` targeting a `Transfer` action (`add_request`), so `R.member == D`.
3. Member `A` calls `confirm(R)` — `confirmations[R] = {A}` (1/3).
4. Member `B` calls `confirm(R)` — `confirmations[R] = {A, B}` (2/3). Request still pending.
5. Members `A, B, C, D` execute a separate multisig request with action `DeleteMember { member: B }`, reaching threshold and removing `B` from `self.members` (and revoking B's key). Because `R.member == D` (not `B`), `delete_member`'s cleanup loop does not touch `R`'s confirmations; `confirmations[R]` still contains `B`.
6. Member `C` (a live, still-authorized member) calls `confirm(R)`. `confirmations[R].len() + 1 = 3 >= num_confirmations (3)`, so `execute_request` runs the `Transfer` action.
7. Result: the transfer executed with only 2 currently-live-member approvals (`A` and `C`), while `B`'s stale confirmation counted toward the 3-of-4 threshold — a multisig request executed below the intended live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
