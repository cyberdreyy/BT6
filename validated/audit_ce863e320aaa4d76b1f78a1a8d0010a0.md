### Title
Final one-shot pubsub subscriptions are torn down before confirming notification delivery, permanently losing signature/log notifications - (File: rpc/src/rpc_pubsub_service.rs)

### Summary
`BroadcastHandler::handle` removes a subscription entry from `current_subscriptions` as soon as it observes `notification.is_final == true`, and only afterwards attempts to upgrade the `Weak<String>` pointer to the actual JSON payload. If the upgrade fails, the function returns `Err(Error::NotificationIsGone)`, but by that point the subscription has already been permanently deleted, so the client has no way to ever receive (or be renotified of) that terminal event. This mirrors the reported "destroy resource on chain A before confirming delivery on chain B" pattern: the local, permanent side effect (removing the subscription) happens before the delivery of its paired result is confirmed, and once it fails, the client-visible outcome (payload) is unrecoverable.

### Finding Description
`RpcNotifier::notify` builds the JSON payload for a notification, wraps it as `Arc<String>`, pushes it into a bounded `recent_items` buffer for later inspection, and sends only a `Weak` reference through the broadcast channel: [1](#0-0) 

Downstream, `BroadcastHandler::handle` is the function each websocket connection task calls per broadcast message to decide whether/what to forward to the client: [2](#0-1) 

The critical ordering flaw is at lines 257–264: when `notification.is_final` (used for one-shot subscriptions such as `signatureSubscribe` with the automatic-unsubscribe semantics seen in `check_commitment_and_notify(..., true /* Unsubscribe */)`), the code calls `entry.remove()` unconditionally — deleting the client's only registered subscription for that id — and only *then* attempts `notification.json.upgrade()`. If the `Weak` has already been invalidated (the `Arc<String>` was dropped, e.g. evicted from the bounded `recent_items` ring buffer under concurrent broadcast load, or dropped by a slow/lagging receiver task), the upgrade fails and `Error::NotificationIsGone` propagates — but the subscription is already gone from `current_subscriptions`.

This is structurally identical to the `BurnUnlock` bug: the permanent, irreversible action (`entry.remove()` ~ burning tokens on the source chain) is performed before the corresponding delivery is confirmed to succeed (`notification.json.upgrade()` ~ unlocking on destination chain). Once the "confirmation" step fails, there is no path back — the subscriber cannot get the final result and cannot re-subscribe to recover the already-consumed one-shot notification, because the underlying event (e.g., the transaction reaching the target commitment) will not fire again.

### Impact Explanation
An unprivileged RPC client using `signatureSubscribe` (with default auto-unsubscribe-on-final behavior) can have its final confirmation notification silently and permanently dropped even though the transaction did reach the expected commitment level on-chain. The client is left in `commitment_watchers`-cleared state with no further way to learn the transaction's outcome via that subscription; it must fall back to polling `getSignatureStatuses`, but the core guarantee of the pubsub API ("finality notification will always eventually be delivered if reached") is broken for the affected connection. This is a correctness bug of the subscription protocol (wrong/no data returned for a one-shot subscription) rather than a memory-safety/crash issue, so it does not rise to a full node compromise.

### Likelihood Explanation
The race requires the `Weak<String>` in a queued `RpcNotification` to become unresolvable (`recent_items` slot evicted, or the payload otherwise dropped) between the time it's enqueued to the per-connection broadcast receiver and the time that connection's task processes it — plausible under high-notification-rate load (busy validator, many broadcasted `Bank`/`Gossip`/`SignaturesReceived` events) or when an individual pubsub connection's task is scheduled late. It is a normal, unprivileged client-triggerable condition (no special role needed), but is timing/load dependent rather than deterministic on every call.

### Recommendation
Reorder the logic in `BroadcastHandler::handle` so `entry.remove()` only happens after a successful `upgrade()` of `notification.json` (or, if it must be removed regardless to prevent leaks, re-insert/requeue the final notification for at-least-once delivery, or keep the strong `Arc` alive until the final notification for that subscription id has actually been delivered to the client).

### Proof of Concept
1. Client calls `signatureSubscribe` for a transaction signature (default `enable_received_notification=false`, so this subscription is a `commitment_watcher` slated to auto-unsubscribe on the confirming notification per `check_commitment_and_notify(..., true)`). [3](#0-2) 
2. When the transaction reaches the configured commitment, `notifier.notify(..., is_final=true)` is called, pushing an `Arc<String>` into the bounded `recent_items` buffer and broadcasting a `Weak` reference.
3. Under sufficient concurrent notification volume (many other subscriptions/events being notified in the same window), the `recent_items` buffer evicts the `Arc` for this particular payload before this client's connection task processes the broadcast message.
4. `BroadcastHandler::handle` executes `entry.remove()` first (line 258), permanently deleting the subscription, then calls `notification.json.upgrade()` which returns `None`, yielding `Err(Error::NotificationIsGone)`.
5. The client never receives the final signature-confirmation notification and the subscription is already gone, so it cannot be notified again for that transaction via this subscription.

    fn handle(&self, notification: RpcNotification) -> Result<Option<Arc<String>>, Error> {
        if let Entry::Occupied(entry) = self
            .current_subscriptions
            .entry(notification.subscription_id)
        {
            increment_sent_notification_stats(
                entry.get().params(),
                &notification,
                &self.sent_stats,
            );

            if notification.is_final {
                entry.remove();
            }
            notification
                .json
                .upgrade()
                .ok_or(Error::NotificationIsGone)
                .map(Some)
        } else {
            Ok(None)
        }
    }
