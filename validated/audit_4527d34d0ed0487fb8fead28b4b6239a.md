## Finding: Unsynchronized `AtomicU64::fetch_sub` in `CostTracker::sub_transaction_execution_cost` can wrap on underflow

### Title
Unsigned underflow in cost-tracker's shared block-cost accounting via raw `fetch_sub` - (File: cost-model/src/cost_tracker.rs)

### Summary
`CostTracker` tracks per-account costs in a `HashMap<Pubkey, u64>` and a shared block cost in `SharedBlockCost` (an `AtomicU64`). When removing/adjusting a transaction's cost, the per-account map is decremented with `saturating_sub` [1](#0-0) , but the shared block cost is decremented with a plain, non-saturating `AtomicU64::fetch_sub` [2](#0-1) . This is the same class of bug the Bitcoin `TrySub` commit addresses: an unsigned integer accounting decrement performed without an underflow guard, which silently wraps instead of failing loudly.

### Finding Description
`sub_transaction_execution_cost` is invoked from `remove_transaction_cost` (called via the public `CostTracker::remove`) [3](#0-2) . It deliberately uses `saturating_sub` for the per-writable-account map entries, but calls `self.block_cost.fetch_sub(adjustment)` for the aggregate block cost [4](#0-3) . `SharedBlockCost::fetch_sub` is a thin wrapper around `AtomicU64::fetch_sub` with no saturation or underflow check [5](#0-4) . If `remove()`/`sub_transaction_execution_cost()` is ever called with an `adjustment` larger than the currently accumulated `block_cost`, the atomic wraps around to a value near `u64::MAX` rather than saturating at zero — inconsistent with the safe pattern used one line above it for the per-account map.

`remove()` is called from banking-stage rollback paths, e.g. `remove_added_transaction_costs` and the all-or-nothing rollback branch of `try_add_processed_transaction_costs`, which iterate previously-added `transaction_costs` and call `cost_tracker.remove(transaction_cost)` for each [6](#0-5) [7](#0-6) . These call sites are designed to only remove costs that were previously and exactly added via `try_add`, so under intended, single-threaded, correctly-paired add/remove sequences the value being subtracted should never exceed the accumulated block cost.

### Impact Explanation
If reached, an underflow of `block_cost` from near-zero to near-`u64::MAX` would cause `would_fit()`'s block-limit check (`self.block_cost().saturating_add(cost) > self.limits.block_cost`) [8](#0-7)  to permanently reject virtually all subsequent transactions for the remainder of the bank/slot, effectively halting block production (an ingest/scheduling denial-of-service) until the cost tracker resets for a new bank via `new_from_parent_limits` [9](#0-8) .

### Likelihood Explanation
Low/unproven. I could not identify a concrete, reachable code path where `remove()`/`sub_transaction_execution_cost()` is invoked with a mismatched or double-counted `adjustment` that exceeds the currently tracked `block_cost` for a given transaction — every call site I found (`remove_added_transaction_costs`, the all-or-nothing rollback loop) removes exactly the same `TransactionCost` object that was previously added via `try_add`, and `CostTracker` is exclusively accessed under `bank.write_cost_tracker()` (a single writer lock), which rules out a race between adders and removers. Whether there exists a code path in the scheduler that could call `remove()` twice for the same transaction, or with a stale/adjusted cost that doesn't match what was added, was not confirmed within the scope of this investigation — this would need to be validated against the full scheduling/rollback logic (e.g., `core/src/banking_stage/`, unified scheduler) which I was not able to fully trace before running out of iterations.

### Recommendation
Regardless of current reachability, harden `sub_transaction_execution_cost`/`SharedBlockCost::fetch_sub` to use a saturating (or `Assume`/checked-and-panic) subtraction consistent with the per-account map's `saturating_sub`, so that any future or currently-unproven mismatched add/remove pairing fails safely (saturates at 0) instead of wrapping to a near-`u64::MAX` value that could stall block production.

### Proof of Concept
Not established. I was unable to construct or confirm a concrete transaction/instruction sequence that drives `remove()`/`sub_transaction_execution_cost()` with an `adjustment` exceeding the tracked `block_cost`; all discovered call sites appear to be exact-pair add/remove operations under a single writer lock. This should be treated as a defense-in-depth/robustness gap rather than a proven exploitable vulnerability at this time.

        &mut self,

        adjustment: u64,
    ) {
        for account_key in tx_cost.writable_accounts() {
            let account_cost = self
                .cost_by_writable_accounts
                .entry(*account_key)
                .or_insert(0);
            *account_cost = account_cost.saturating_sub(adjustment);
        }
        self.block_cost.fetch_sub(adjustment);
    }

/// Wrapper around blockcost to allow fast sharing of the value without locking.
/// Value is read-only outside of cost-tracker.
#[derive(Debug, Clone)]
pub struct SharedBlockCost(Arc<AtomicU64>);

impl SharedBlockCost {
    pub fn new(value: u64) -> Self {
        Self(Arc::new(AtomicU64::new(value)))
    }

    fn fetch_add(&self, value: u64) -> u64 {
        self.0.fetch_add(value, Ordering::Release)
    }

    fn fetch_sub(&self, value: u64) -> u64 {
        self.0.fetch_sub(value, Ordering::Release)
    }

    pub fn load(&self) -> u64 {
        self.0.load(Ordering::Acquire)
    }
}
