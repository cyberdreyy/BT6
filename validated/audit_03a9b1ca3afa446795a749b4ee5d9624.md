### Title
`accountSubscribe`/`programSubscribe` silently ignore `minContextSlot`, allowing stale/pre-target-slot data to be delivered - ([File: rpc/src/rpc_pubsub.rs])

### Summary
The `minContextSlot` parameter that `getAccountInfo`/`getProgramAccounts` enforce via `MinContextSlotNotReached` is accepted by the pubsub `accountSubscribe`/`programSubscribe` endpoints but is discarded before it can affect subscription behavior, exactly mirroring the reported bug class: a caller-supplied guard value that is supposed to gate an operation is parsed but never wired into the enforcement path, so the check silently defaults to "no minimum," and unprivileged callers get no protection even though they explicitly asked for one.

### Finding Description
`JsonRpcRequestProcessor::get_bank_with_config` enforces `min_context_slot` for request/response RPC calls such as `get_account_info`, returning `RpcCustomError::MinContextSlotNotReached` when the bank slot hasn't caught up: [1](#0-0) [2](#0-1) 

However, in the WebSocket pubsub path, `RpcSolPubSubImpl::account_subscribe` explicitly discards this same field with a comment acknowledging the omission: [3](#0-2) 

`program_subscribe` similarly builds `ProgramSubscriptionParams` from only `encoding`, `data_slice`, and `commitment` out of the embedded `RpcAccountInfoConfig`, never reading its `min_context_slot` field: [4](#0-3) 

The subscription tracking type that stores per-subscription state has no `min_context_slot` field at all — only `commitment`: [5](#0-4) 

So there is no path anywhere in the pubsub subscribe/notify pipeline where `min_context_slot` is consulted once a subscription is registered — the parameter is accepted syntactically (`RpcAccountInfoConfig` has the field, per `rpc-client-types/src/config.rs`) but is a complete no-op for `accountSubscribe`/`programSubscribe`, unlike its `getAccountInfo`/`getProgramAccounts` counterparts.

### Impact Explanation
`minContextSlot` exists specifically so that unprivileged RPC/pubsub clients (e.g., those following a specific fork/slot after a known transaction landed) can be sure they never observe account state from before that point — important for read-after-write consistency in dApps. Because the pubsub layer silently drops the parameter, a client subscribing with `minContextSlot` set can receive notifications with account data from before that context slot, i.e., wrong-slot/stale account data returned to a query, contrary to the documented API guarantee. This is a purely client-facing/JSON-RPC/pubsub-triggerable issue with no need for elevated privileges — any RPC consumer using `accountSubscribe`/`programSubscribe` with `minContextSlot` is silently unprotected.

### Likelihood Explanation
High and trivially reachable: any external client can call `accountSubscribe` or `programSubscribe` with `minContextSlot` set (a documented, supported parameter) over an open pubsub endpoint. No special configuration, timing races, or multiple calls are required to trigger the missing enforcement — it fails by default on every such subscription, which is a single low-rate call, so it is in-scope per the rules (unlike RPC DoS analogs that need repeated queries).

### Recommendation
- Short term: Thread `min_context_slot` through `AccountSubscriptionParams`/`ProgramSubscriptionParams` and `SubscriptionInfo`, and gate notification delivery (or at minimum the initial subscription acknowledgment/first notification) on the subscribing bank/slot meeting the requested `min_context_slot`, returning an error or deferring delivery analogous to `MinContextSlotNotReached` used by the synchronous RPC methods.
- Long term: Add an integration test asserting parity between `getAccountInfo`/`getProgramAccounts` and `accountSubscribe`/`programSubscribe` for `minContextSlot` handling, so any future desync between the two enforcement paths is caught automatically.

### Proof of Concept
1. Start a validator/local-cluster and note the current slot `S0`.
2. Have an unprivileged client submit accountSubscribe with `{"minContextSlot": S0 + 1000}` for some account, then also update the account.
3. Because the pubsub layer ignores `minContextSlot` (per `rpc/src/rpc_pubsub.rs:424-443`), the client immediately begins receiving notifications for the account's current state at slot `S0`, well before slot `S0 + 1000` is reached — in contrast, calling `getAccountInfo` with the same `minContextSlot` at slot `S0` correctly returns `MinContextSlotNotReached` (per `rpc/src/rpc.rs:273-289`). This demonstrates the pubsub API silently violates the guarantee that the synchronous API enforces.

impl JsonRpcRequestProcessor {
    fn get_bank_with_config(&self, config: RpcContextConfig) -> Result<Arc<Bank>> {
        let RpcContextConfig {
            commitment,
            min_context_slot,
        } = config;
        let bank = self.bank(commitment);
        if let Some(min_context_slot) = min_context_slot
            && bank.slot() < min_context_slot
        {
            return Err(RpcCustomError::MinContextSlotNotReached {
                context_slot: bank.slot(),
            }
            .into());
        }
        Ok(bank)
    }
