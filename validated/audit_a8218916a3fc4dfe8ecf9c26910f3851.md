### Title
Raw ORM error message leaked to caller via jsonAPIError in ExternalInitiatorsController.Create - ([File: core/web/external_initiators_controller.go])

### Summary
When `ValidateExternalInitiator` hits a non-`sql.ErrNoRows` error from `orm.FindExternalInitiatorByName`, it returns `errors.Wrap(err, "validating external initiator")`, and `Create` passes this directly to `jsonAPIError`, which serializes `err.Error()` (including the wrapped underlying driver/ORM error text) into the JSON:API response body sent to the caller.

### Finding Description
In `ValidateExternalInitiator`, if the ORM lookup fails with anything other than `sql.ErrNoRows`, the raw error is wrapped and returned unmodified: [1](#0-0) . `Create` then forwards this error straight to `jsonAPIError` with a 400 status: [2](#0-1) . `jsonAPIError` checks whether the error is a `*models.JSONAPIErrors` (a "safe" pre-sanitized error type); since a wrapped generic ORM error is not, it falls through to `models.NewJSONAPIErrorsWith(err.Error())`, which places the full `err.Error()` string — including whatever the original DB/driver error said — into the `detail` field of the JSON:API response: [3](#0-2) . Because `errors.Wrap` from `github.com/pkg/errors` concatenates the wrap message with the original error's message, any driver-level detail (e.g., pq/sqlx error text, which can include column/constraint/table names or connection-related details) is preserved and returned verbatim to the caller in the HTTP response body.

### Impact Explanation
This is an information-disclosure issue: it can leak internal database implementation details (table/column/constraint names, driver-specific error text) to whichever caller can reach `POST /v2/external_initiators`. This matches Chainlink's "information disclosure aiding further attack planning" bounty class, but its severity is capped by the fact that (a) this endpoint is behind the admin/authenticated web API (not the unauthenticated gateway), and (b) it requires triggering a real backend ORM failure that is not attacker-controlled through normal input (the described attacker precondition — "an injected ORM failure condition" — is an artificial/test-only condition, not something an unprivileged caller can normally induce on demand).

### Likelihood Explanation
Exploitability is low in practice: triggering `FindExternalInitiatorByName` to fail with a non-`ErrNoRows` error (e.g., a real DB connectivity blip or constraint violation on a `SELECT`) is not something a remote low-privilege caller can reliably induce via crafted input to this specific query — it typically requires actual infrastructure failure (DB outage, connection pool exhaustion) rather than a payload in the request body. This makes the scenario largely dependent on incidental operational failures rather than an attacker-triggerable condition, reducing repeatability/likelihood for a pure external attacker. That said, this endpoint does require an authenticated session (this is not a route reachable by a fully unauthenticated or view-only caller — it is under the admin-authenticated API surface per `core/web/router.go`/`routes.go` group for admin-only endpoints), further limiting the attacker set consistent with the stated "edit-role" precondition.

### Recommendation
Do not propagate raw wrapped ORM/DB errors to the HTTP client. In `ExternalInitiatorsController.Create`, when `ValidateExternalInitiator` returns an error that is not a `*models.JSONAPIErrors`, log the detailed error server-side and return a generic `models.NewJSONAPIErrorsWith("internal error validating external initiator")` (or similar sanitized message) to the caller instead of `err.Error()`. More generally, `jsonAPIError`'s fallback branch (`c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))`) should not be used for errors originating from ORM/DB layers; only errors explicitly constructed as user-facing (`*models.JSONAPIErrors`) should be surfaced with full detail.

### Proof of Concept
1. Create a mock `bridges.ORM` whose `FindExternalInitiatorByName` returns a generic error, e.g. `errors.New("pq: connection to server at \"10.0.0.5\", port 5432 failed")` (or any non-`sql.ErrNoRows` error).
2. Call `ValidateExternalInitiator(ctx, exi, mockORM)` directly and assert the returned error's `Error()` string contains `"validating external initiator: pq: connection to server..."` — confirming the raw text is retained.
3. At the handler level, spin up `ExternalInitiatorsController` with the mocked `BridgeORM()` returning the same error, issue `POST /v2/external_initiators` with a valid authenticated edit-role session and valid body, and assert on the HTTP response JSON that the `errors[0].detail` field contains the raw injected string (e.g. contains `"10.0.0.5"` or `"pq:"`), demonstrating the leak into the client-visible payload versus an expected generic message.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
