### Title
Replay-from-block endpoint gated by low-privilege `RequiresRunRole` allows external-initiator/run-role callers to force re-execution of arbitrary historical job pipelines - ([File: core/web/replay_controller.go])

### Summary
`ReplayController.ReplayFromBlock`, mounted at `POST /v2/replay_from_block/:number`, is wrapped only by `auth.RequiresRunRole`, which admits any authenticated principal whose role is not `UserRoleView` — including credentials belonging to an External Initiator, which are automatically upgraded to `UserRoleRun` by `auth.AuthenticateExternalInitiator`. This lets a caller who should only be able to trigger a single, pre-registered webhook job instead force the node to replay an arbitrary historical block range with `force=true` for any chain, re-triggering all matching job pipeline runs including ones with on-chain side effects.

### Finding Description
`ReplayFromBlock` accepts `number`, `force`, `family`, and `ChainID` from the request and calls `App.ReplayFromBlock` directly with no additional scoping or ownership check: [1](#0-0) 

The role check applied to this route is `auth.RequiresRunRole`, which only rejects `UserRoleView` and otherwise allows any role (`run`, `edit`, `admin`) through: [2](#0-1) 

Compare this to `RequiresEditRole` and `RequiresAdminRole`, which are used elsewhere in the router to gate configuration/administrative actions and correctly exclude the `run` role: [3](#0-2) 

Critically, `AuthenticateExternalInitiator` — the authentication method used for external-initiator webhook callers — unconditionally sets the authenticated principal's role to `UserRoleRun` upon successful EI credential validation, with an explicit comment that this role is intended only "to trigger job runs": [4](#0-3) 

Because `RequiresRunRole` treats `UserRoleRun` as sufficient, any external initiator credential (scoped, by design, to triggering a single associated job run) or any run-role user/API token can call the replay endpoint and cause the node to re-scan and re-execute *all* job pipelines matching the given block range/chain — not just the EI's own job. This is a role-scope mismatch: the endpoint's blast radius (chain-wide re-execution of pipelines, including on-chain transactions) far exceeds what the `run` role is intended to authorize (triggering one's own job).

### Impact Explanation
An attacker holding only run-level credentials (a scoped API token, or an external-initiator credential meant to invoke one specific webhook job) can force the node to replay arbitrary historical blocks with `force=true`, causing unauthorized re-execution of every job pipeline whose target address/topics fall in that range for the specified chain. This can result in duplicate or unintended on-chain transactions, unintended oracle responses, and unauthorized re-processing of logs across jobs the attacker does not own or administer — this matches the "unauthorized job run / fund movement" impact class.

### Likelihood Explanation
The precondition is minimal: any valid run-role session, API token, or external-initiator credential (the lowest tier of API/webhook access chainlink issues) is sufficient. No edit or admin role is required. The request is a single unauthenticated-relative-to-role HTTP call (`POST /v2/replay_from_block/1?force=true&family=evm&ChainID=<id>`), fully repeatable, and requires no race condition or timing dependency.

### Recommendation
Change the route registration for `/v2/replay_from_block/:number` to use `auth.RequiresEditRole` (or `RequiresAdminRole`, given the chain-wide/on-chain impact) instead of `auth.RequiresRunRole`, so that external-initiator and run-only credentials cannot invoke it. Alternatively, introduce a dedicated permission distinct from the general "run" role for chain-replay operations.

### Proof of Concept
1. Handler/integration test in `core/web` (alongside existing router tests):
   - Set up a test app with a mocked `chainlink.Application` whose `ReplayFromBlock` method is asserted to be called.
   - Authenticate as an external initiator (via `auth.AuthenticateExternalInitiator` test helper / valid EI access key + secret headers) with no other role.
   - Issue `POST /v2/replay_from_block/1?force=true&family=evm&ChainID=1`.
   - Assert HTTP 200 and that `mockApp.ReplayFromBlock` was invoked with `chainID="1"`, `blockNumber=1`, `force=true`.
2. Repeat with a session/API-token user whose `sessions.User.Role == UserRoleRun` (not edit/admin), asserting the same successful invocation, demonstrating that role scoping does not distinguish "trigger my own job" from "replay arbitrary chain history."
3. Contrast with a call to an edit/admin-gated endpoint (e.g., job creation) using the same run-role/EI credential and assert it is rejected with 401/403, confirming the inconsistency in role-gating strictness.

func (bdc *ReplayController) ReplayFromBlock(c *gin.Context) {
	if c.Param("number") == "" {
		jsonAPIError(c, http.StatusUnprocessableEntity, errors.New("missing 'number' parameter"))
		return
	}

	// check if "force" query string parameter provided
	var force bool
	var err error
	if fb := c.Query("force"); fb != "" {
		force, err = strconv.ParseBool(fb)
		if err != nil {
			jsonAPIError(c, http.StatusUnprocessableEntity, errors.Wrap(err, "boolean value required for 'force' query string param"))
			return
		}
	}

	blockNumber, err := strconv.ParseInt(c.Param("number"), 10, 0)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	if blockNumber < 0 {
		jsonAPIError(c, http.StatusUnprocessableEntity, errors.Errorf("block number cannot be negative: %v", blockNumber))
		return
	}

	chainFamily := c.Query("family")
	if chainFamily == "" {
		jsonAPIError(c, http.StatusUnprocessableEntity, errors.New("chain family was not provided"))
		return
	}

	chainID := c.Query("ChainID")
	if strings.TrimSpace(chainID) == "" {
		jsonAPIError(c, http.StatusUnprocessableEntity, errors.New("chain-id was not provided"))
		return
	}

	ctx := c.Request.Context()
	if err := bdc.App.ReplayFromBlock(ctx, chainFamily, chainID, uint64(blockNumber), force); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

			c.Abort()

			return
		}
		handler(c)
	}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
