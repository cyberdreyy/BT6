I'll investigate whether Agave has an analogous pattern: a privileged/permissionless party able to mutate a fee rate parameter that retroactively affects funds already committed by another party (mirroring the Cally `setFee` issue where the fee is applied at exercise time using the *current* fee rate rather than a rate fixed at vault creation).### Title
Vote program `UpdateCommissionBps` for `BlockRevenue` commission omits the anti-rug delay protection applied to inflation-reward commission, allowing a validator to instantly change its self-declared revenue-share rate around block-reward events - (File: programs/vote/src/vote_state/mod.rs)

### Summary
The Cally bug allowed the contract owner to change `feeRate` at will and apply the new rate at exercise time, diverting value that should have gone to another party. Agave has an analogous "commission" concept in the vote program: a validator-controlled percentage (`inflation_rewards_commission_bps` / `block_revenue_commission_bps`) that determines how rewards earned by delegated stake are split between the validator and its delegators. Agave already recognized and fixed this exact bug class for inflation rewards (SIMD-0249, `delay_commission_updates`), but the newer `BlockRevenue` commission path added by SIMD-0123/SIMD-0291 is explicitly documented in code as having no such delay.

### Finding Description
`VoteInstruction::UpdateCommissionBps` is processed without any signer restriction beyond the authorized withdrawer, and for the legacy `UpdateCommission` instruction the runtime enforces `is_commission_update_allowed` (an epoch-boundary rate-increase restriction) plus the `delay_commission_updates` feature, which forces the runtime to use the commission rate recorded 1–2 epochs earlier when computing inflation-reward splits [1](#0-0) , [2](#0-1) .

In contrast, `update_commission_bps`, which sets `inflation_rewards_commission_bps` or `block_revenue_commission_bps`, contains the explicit comment "No commission update rule, per SIMD-0249 and SIMD-0291" and applies the new value immediately with only a withdrawer-signature check: [3](#0-2) . The instruction handler in the processor gates this only on feature activation (`commission_rate_in_basis_points` and `delay_commission_updates`), not on any per-kind delay logic for `BlockRevenue`: [4](#0-3) .

While the `delay_commission_updates` feature does defer the *inflation-reward* commission used in `redeem_delegation_rewards` (fetching commission from a snapshot epoch when the feature is active) [2](#0-1) , there is no equivalent snapshot/delay mechanism applied to `block_revenue_commission_bps` in the code reachable from my search of the reward-calculation and fee-distribution paths (`calculate_block_reward`, `distribute_transaction_fee_details`, `deposit_delegator_rewards`) [5](#0-4) , [6](#0-5) .

### Impact Explanation
If/when the `block_revenue_sharing` (SIMD-0123) mechanism is used to automatically split block revenue (transaction/priority fees) between a validator and its delegators based on `block_revenue_commission_bps`, a validator can raise its own commission to 100% (10,000 bps) immediately before an anticipated high-value revenue event and drop it back down afterward, capturing revenue that should have been shared with delegators who staked under the expectation of the previously-published rate — mirroring the owner's ability in the Cally report to set `feeRate` opportunistically and steal value intended for another party.

### Likelihood Explanation
This is difficult to fully confirm as currently exploitable in this codebase snapshot: `deposit_delegator_rewards`/`DepositDelegatorRewards` (the mechanism that populates `pending_delegator_rewards`, which is later split among delegators in `calculate_block_reward`) appears to require a voluntary, signer-initiated deposit of a caller-chosen amount, rather than the runtime automatically pulling a `block_revenue_commission_bps`-driven share out of collected transaction fees at the point of collection [7](#0-6) . I was not able to locate, within available search results, the exact runtime code path that automatically applies `block_revenue_commission_bps` to split real fee revenue at the moment it is earned. This limits confidence that the missing-delay condition is presently reachable as a concrete fund-theft primitive versus being a currently inert/future-facing field guarded by other, unexamined logic.

### Recommendation
Apply the same commission-update delay/snapshot protection used for `inflation_rewards_commission_bps` (SIMD-0249) to `block_revenue_commission_bps` before or as part of enabling `block_revenue_sharing` in production, so that any change to the block-revenue commission rate only takes effect at least one full epoch later, preventing last-minute "commission rug" behavior around block-revenue distribution.

### Proof of Concept
1. As the vote account's authorized withdrawer, submit `VoteInstruction::UpdateCommissionBps { commission_bps: 10_000, kind: CommissionKind::BlockRevenue }` — this succeeds immediately with no epoch/delay restriction [8](#0-7) .
2. If/when the block-revenue-sharing distribution path automatically applies `block_revenue_commission_bps` to newly-earned block revenue (unverified in the explored code), the validator captures 100% of that revenue instead of the delegator-expected share.
3. Immediately after, submit another `UpdateCommissionBps` to restore the original low rate, since no rate-limiting rule applies to this instruction [4](#0-3) .

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

impl Bank {
    // Distribute collected transaction fees for this slot to the block revenue collector
    // id for the current leader.
    //
    // Each validator is incentivized to process more transactions to earn more transaction fees.
    // Transaction fees are rewarded for the computing resource utilization cost, directly
    // proportional to their actual processing power.
    //
    // The leader is rotated according to stake-weighted leader schedule. So the opportunity of
    // earning transaction fees are fairly distributed by stake. And missing the opportunity
    // (not producing a block as a leader) earns nothing. So, being online is incentivized as a
    // form of transaction fees as well.
    pub(super) fn distribute_transaction_fee_details(&self) {
        let fee_details = self.collector_fee_details.read().unwrap();

        let FeeDistribution { deposit, burn } =
            self.calculate_reward_and_burn_fee_details(&fee_details);

        let total_burn = self.deposit_or_burn_fee(deposit).saturating_add(burn);
        self.capitalization.fetch_sub(total_burn, Relaxed);
    }

    pub fn calculate_reward_for_transaction(
        &self,
        transaction: &impl TransactionWithMeta,
        transaction_configuration: &TransactionConfiguration,
    ) -> u64 {
        let fee_details = solana_fee::calculate_fee_details(
            transaction,
            self.fee_structure().lamports_per_signature,
            transaction_configuration.priority_fee_lamports,
            self.fee_features(),
        );
        let FeeDistribution {
            deposit: reward,
            burn: _,
        } = self.calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details));
        reward
    }

    pub fn calculate_reward_and_burn_fee_details(
        &self,
        fee_details: &CollectorFeeDetails,
    ) -> FeeDistribution {
        let burn = fee_details.transaction_fee * self.burn_percent() / 100;
        let deposit = fee_details
            .priority_fee
            .saturating_add(fee_details.transaction_fee.saturating_sub(burn));
        FeeDistribution { deposit, burn }
    }
