### Title
Disabled instant-withdrawal policy bypassed on request path locks user funds — `requestWithdraw` routes into `requestInstantWithdraw` without checking `allowInstantWithdraw` - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The credit vault has two distinct switches for instant withdrawals: `disableInstantWithdraw`/`isProgrammableBorrower` (hard off) checked in `_isInstantWithdrawEnabled()`, and `allowInstantWithdraw` (operational off) checked only in `claimInstantWithdrawRequest()`. Analogous to the Zitadel advisory — where a disabled login method remained reachable via direct requests because enforcement lived only in one layer — the `allowInstantWithdraw` policy is enforced only at claim time, not at request time. `requestWithdraw()` silently diverts a user into the instant-withdraw path whenever the APR dropped, burning their tranche tokens and minting an instant receipt that can never be claimed while the flag is off.

### Finding Description
In `requestWithdraw`, the instant path is taken when `_isInstantWithdrawEnabled()` is true and `lastEpochApr > unscaledApr + instantWithdrawAprDelta` (IdleCDOEpochVariant.sol:761-770). That path calls `IdleCreditVault(strategy).requestInstantWithdraw(_underlyings, msg.sender)` and burns the user's tranche tokens via `_withdrawOps`, removing principal from NAV — with no queued `withdrawsRequestsByEpoch` receipt created.

Claiming the resulting instant receipt requires `allowInstantWithdraw == true` (IdleCDOEpochVariant.sol:975-978: `_checkNotAllowed(!allowInstantWithdraw)`). So when the owner/manager has set `allowInstantWithdraw = false` (e.g., because the borrower will not prefund instant liquidity), any user calling `requestWithdraw` during an APR drop is forced into the disabled feature: tranche tokens are burned, NAV is reduced, and the receipt is unclaimable for as long as the flag stays false. The user cannot choose the queued path — the branch is deterministic — and there is no cancel/revert of the instant request, so the position is frozen with no fallback.

This is a flag/policy bypass: the "disabled" instant-withdrawal feature remains reachable through `requestWithdraw` because the operational disable flag is only enforced on the claim surface, not the request surface.

### Impact Explanation
Direct loss of access to user funds: an unprivileged tranche holder requesting a normal withdrawal has their entire requested principal + interest converted into an unclaimable receipt. If `allowInstantWithdraw` remains false (e.g., permanently disabled operationally or left off until pool close), the freeze is permanent — the user's tranche tokens are already burned and lastNAV reduced, so even restoring `allowAAWithdrawRequest`/`requestWithdraw` cannot recover the position. Quantified loss: the full `_underlyings` amount of every withdrawal request made while the APR-delta condition holds and the flag is off.

### Likelihood Explanation
Requires (a) `allowInstantWithdraw == false` while `disableInstantWithdraw == false` — a plausible configuration when the manager wants to stop new instant liquidity outflows but hasn't permanently disabled the feature — and (b) an APR decrease exceeding `instantWithdrawAprDelta`, which is the designed trigger. Any user-requested withdrawal in that window hits the bug; the user takes no unusual action.

### Recommendation
Enforce the disabled policy at the request surface: in `requestWithdraw`, skip the instant branch when `!allowInstantWithdraw` (fold it into the `_isInstantWithdrawEnabled()` check or add `&& allowInstantWithdraw`), so requests fall through to the normal queued withdrawal path instead of minting unclaimable receipts.

### Proof of Concept
```solidity
// Foundry fork test — assumes an IdleCDOEpochVariant + IdleCreditVault deployment
// with instant withdrawals operationally disabled but not permanently disabled.
function test_InstantWithdrawFlagBypassLocksFunds() external {
    // Setup: AA holder `alice` deposited and KYC'd; epoch is running.
    // Owner disables instant withdrawals operationally (honest action).
    vm.prank(owner);
    cdo.setAllowInstantWithdraw(false); // allowInstantWithdraw = false
    assertTrue(cdo.isEpochRunning());

    // Manager lowers APR so that lastEpochApr > unscaledApr + instantWithdrawAprDelta
    // (honest manager action at a boundary, or via stopEpoch/startEpoch with lower apr).

    // Alice requests a normal queued withdrawal.
    uint256 bal = AATranche(cdo.AATranche()).balanceOf(alice);
    vm.prank(alice);
    cdo.requestWithdraw(bal, cdo.AATranche());

    // Tranche tokens were burned and an instant receipt was minted instead of
    // a queued withdrawsRequestsByEpoch entry.
    assertEq(AATranche(cdo.AATranche()).balanceOf(alice), 0);

    // Claim is impossible while the flag is off: policy enforced only here.
    vm.prank(alice);
    vm.expectRevert(); // NotAllowed
    cdo.claimInstantWithdrawRequest();

    // Alice's underlyings are frozen; no queued claim path exists either.
    vm.prank(alice);
    cdo.claimWithdrawRequest(); // no receipt registered for alice -> no payout
}
```
