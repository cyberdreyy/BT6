### Title
Stale rejection weight is never retracted when a signer flips to Accept, letting `total_weight_rejected` phantom-inflate past the global-reject threshold - (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The node-side StackerDB message aggregator (`StackerDBListener`'s event loop) tracks per-block weight in two buckets, `total_weight_approved` and `total_weight_rejected`, gated by two *different* dedup guards. The Accept path is guarded by `block.gathered_signatures.contains_key(&slot_id)` while the Reject path is guarded by `block.responded_signers.insert(slot_id)`. This asymmetry means a signer that first rejects a block and later legitimately re-evaluates and accepts the same block (a normal, expected flow per `should_reevaluate_reject_reason`/`should_reevaluate_block` in `stacks-signer/src/v0/signer.rs`) has its weight added to `total_weight_rejected` *and never removed*, while also being correctly added once to `total_weight_approved` when it accepts. The reverse order (accept-then-reject) is correctly guarded and does not double count, exposing the asymmetry as unintentional.

### Finding Description
In the message-processing loop of `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- `BlockResponse::Accepted` handling (around line 443): [1](#0-0) 
adds weight to `total_weight_approved` only `if !block.gathered_signatures.contains_key(&slot_id)`, then unconditionally does `block.gathered_signatures.insert(slot_id, signature)` and `block.responded_signers.insert(slot_id)`.

- `BlockResponse::Rejected` handling (around line 515): [2](#0-1) 
adds weight to `total_weight_rejected` only `if block.responded_signers.insert(slot_id)` — i.e. gated on "have we ever recorded any response from this slot."

Trace both orderings:
- Accept → Reject: Accept sets `gathered_signatures[slot]` and `responded_signers.insert(slot)==true`. A later Reject calls `responded_signers.insert(slot)` which now returns `false` (already present), so `total_weight_rejected` is *not* incremented. Correct — no double count.
- Reject → Accept: Reject calls `responded_signers.insert(slot)==true` (first response ever) and adds weight to `total_weight_rejected`. A later Accept checks `gathered_signatures.contains_key(slot)` — still `false` (this is the first *signature*) — so it adds weight to `total_weight_approved` as well. `responded_signers.insert(slot)` is a no-op since it was already true.

Result: after Reject→Accept, the same signer's weight is counted in **both** `total_weight_rejected` and `total_weight_approved` simultaneously, and the rejected-side weight is never retracted. This breaks the intended invariant that `total_weight_approved` + `total_weight_rejected` reflects the *current* distinct votes of signers (an equality/consistency guarantee the aggregator relies on to decide global accept/reject).

This directly affects the global-reject decision: [3](#0-2) 
`if block.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight { cvar.notify_all(); }` — this wakes up the miner/coordinator logic that treats the block as globally rejected once >30% of weight has rejected. Because stale rejection weight from signers who have since re-evaluated and accepted is never subtracted, this check can fire (or be pushed closer to firing) using phantom weight that no longer reflects any signer's live intent.

This scenario is fully reachable without a majority of signers or any privileged access: the documented re-evaluation flow (`docs/signer-flows.md` section 3, `should_reevaluate_reject_reason`) explicitly allows a signer to reject a proposal (e.g., transient `NotFoundError`/stale burn view) and later accept a re-proposed/re-evaluated version of the *same* `signer_signature_hash`. A one-slot miner can trigger this by re-proposing a block that a signer initially rejected for a re-evaluable reason and then having conditions catch up so the signer accepts on re-evaluation — or a colluding/faulty signer can send Reject then Accept directly over StackerDB (gossip), which is exactly the class of actor permitted by the rules.

### Impact Explanation
This is a liveness wedge on the node/coordinator side: phantom, un-retracted rejection weight can cause the miner to conclude a block has been globally rejected (>30% weight) even though the signers whose weight is counted have already moved on to accepting it. A miner that treats this signal as authoritative may abandon a valid block and produce a replacement/conflicting proposal, wasting a tenure round or creating unnecessary forks/reproposals — a liveness impact consistent with "a signer [system] wedged into never [settling on] a valid block," which the rules classify as High impact. It does not require a majority of the signer set to reach — only one signer's weight following the natural reject→accept sequence is enough to permanently corrupt the `total_weight_rejected` tally for that specific block hash, and repeated occurrences across a churny tenure could compound the effect toward the 30% threshold.

### Likelihood Explanation
The reject→accept sequence for the same block hash is not an edge case requiring an attacker; it's an explicitly supported and expected re-evaluation flow (`should_reevaluate_reject_reason`, `should_reevaluate_block` in `stacks-signer/src/v0/signer.rs`, documented in `docs/signer-flows.md` §3). Any signer whose initial rejection is for a re-evaluable reason (e.g., a burn-view race, as seen in `stacks-node/src/tests/signer/v0/missing_burn_block_proposal.rs`) and who later accepts the same proposal will trigger the asymmetric accounting. A malicious or buggy single signer can also trivially force this by broadcasting a Reject followed by a valid Accept for the same `signer_signature_hash` over StackerDB, with no cryptographic or majority requirement.

### Recommendation
Make the dedup/accounting symmetric: track a per-slot "current vote" (Accept/Reject) rather than independent one-way guards, and when a slot's vote changes, retract the weight from the old bucket before adding it to the new one. Concretely, gate the Accept-side weight addition on the same "already responded before" check used in Reject (or better, unify into a single `slot_id -> current_vote` map), and when transitioning from Reject to Accept (or vice versa) for the same block, subtract the previously counted weight from `total_weight_rejected` (or `total_weight_approved`) before adding it to the other bucket.

### Proof of Concept
1. Node receives `BlockResponse::Rejected` for `signer_signature_hash = H` from `slot_id = S` (weight `w`) — re-evaluable reason (e.g., transient `NotFoundError`, per `missing_burn_block_proposal.rs`).
   - `responded_signers.insert(S)` → `true` → `total_weight_rejected += w`.
2. The same signer re-evaluates the (re-proposed) block for the same `H` and legitimately signs/accepts it, sending `BlockResponse::Accepted`.
   - `gathered_signatures.contains_key(S)` → `false` → `total_weight_approved += w`; `gathered_signatures.insert(S, sig)`; `responded_signers.insert(S)` is a no-op.
3. Final state: `total_weight_rejected` still includes `w` from step 1, and `total_weight_approved` also includes `w` from step 2 — the same signer's weight counted in both, and the rejected weight is never retracted.
4. If cumulative stale-rejected weight from such flips (across multiple signers over a tenure) reaches `>30%` of `total_weight`, the check at lines 567-574 fires the "globally rejected" `cvar.notify_all()` signal even though the true current sentiment of those signers is Accept, potentially causing the miner to abandon a block that in fact has (or will have) sufficient live approval weight.
