### Title
Unfunded instant-withdraw receipts are paid at par from pooled strategy funds - (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`requestInstantWithdraw` mints the user a full strategy-token receipt and records it in `instantWithdrawsRequests[_user]`, but actual funding only arrives later via `collectInstantWithdrawFunds`, which merely decrements the global `pendingInstantWithdraws` counter. `claimInstantWithdrawRequest` then pays the *entire* `instantWithdrawsRequests[_user]` balance at par through `_transferFundedClaim` without checking whether that user's receipt was ever funded. Analogous to CVE-2021-3345 — where a finalize path set a `count` larger than the data actually written — the claimable count is fixed at request time while the funded amount is tracked only in aggregate, so an unfunded or partially funded receipt can still be cashed out in full.

### Finding Description
- `requestInstantWithdraw` (lines 356-375) burns the CDO's tokens, mints the user a receipt equal to `_amount`, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws`. No underlying moves yet.
- `collectInstantWithdrawFunds` (lines 398-403) is the only funding path: the CDO pushes underlyings and `pendingInstantWithdraws -= _amount`. The per-user receipt is never marked funded/unfunded.
- `claimInstantWithdrawRequest` (lines 380-393) burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)`, i.e. pays from whatever underlying the strategy holds. There is no check that the caller's request epoch was funded, no per-user/per-epoch funding flag, and no comparison against `pendingInstantWithdraws`.
- `_transferFundedClaim` (lines 897-907) only guards the `defaultRecoveryReserve`; any other underlying balance — other users' funded instant payouts sitting in the contract, or not-yet-forwarded buffer deposits — is spendable.
- The codebase itself confirms unfunded receipts exist: `_defaultPrefundedInstantReserve` describes `pendingInstantWithdraws` as "the still-unfunded remainder" versus `instantWithdrawClaimsByEpoch[epochNumber]` (lines 712-723), and `defaultPendingClaimBasis` treats current-epoch instant claims as borrower-owed when `pendingInstantWithdraws != 0` (lines 644-649).

Attack path (running epoch, instant withdrawals enabled via `setInstantWithdrawParams`): an attacker deposits, requests an instant withdrawal of the full amount, then calls `IdleCDOEpochVariant.claimInstantWithdrawRequest` — which only checks `allowInstantWithdraw` (lines 975-979) — before `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` runs for that request (e.g., the APR-delta condition wasn't met, or the manager funded only a subset of pending requests). The claim transfers underlying that was collected for *other* users' instant requests or that belongs to other depositors, because the funded pool is fungible and the receipt is honored regardless of its own funding status. This breaks the one-receipt-one-funded-payout invariant.

### Impact Explanation
Direct theft: the attacker converts an unfunded receipt into underlying at par, consuming funds reserved for honest instant-withdraw claimants or idle vault liquidity. Loss is bounded by the strategy's transferable underlying balance (up to the attacker's deposit size per receipt, repeatable each epoch while instant withdrawals are enabled). Honest users' matured instant claims then revert or are haircutted at finalization despite having been "funded."

### Likelihood Explanation
Requires instant withdrawals enabled (`allowInstantWithdraw`) and a window where a request exists before the corresponding `collectInstantWithdrawFunds` — a normal sequence since funding and claiming are separate transactions driven by manager/keeper timing and APR conditions. Any KYC'd lender can execute it with only their own deposit as capital.

### Recommendation
Track funded instant basis per epoch (e.g., `instantWithdrawFundedByEpoch`) and gate `claimInstantWithdrawRequest` so a user can only claim against receipts whose epoch funding was collected; alternatively have `collectInstantWithdrawFunds` mark which receipts are funded and revert claims on unfunded balances instead of paying from pooled funds.
