### Title
APR0 withdraw receipts carry a stale `principalEpoch` tag, letting users escape the `stopEpochWithDuration` loss haircut applied to pending receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
In APR0 mode, `IdleCreditVault._requestWithdrawApr0` records `apr0Users[user].principalEpoch` only when the user's principal bucket is empty, so a second APR0 withdraw request made in a later epoch is still tagged with the earlier epoch. When a `stopEpochWithDuration` loss haircut is recorded in `lossRecoveryPriceByEpoch[epochNumber]`, both the re-request guard in `requestWithdraw` and `_clearWithdrawClaimForEpoch` look the receipt up under `principalEpoch`, find nothing at the loss epoch, and the user is paid the full principal at par even though the borrower only funded the haircutted amount. This is the same bug class as the Linux `split_large_buddy()` fix: a lookup key is used to resolve an accounting record in an epoch where that record does not actually live, so the safety check silently misses it.

### Finding Description
`requestWithdraw` routes APR0 requests to `_requestWithdrawApr0`:

```solidity
// IdleCreditVault.sol:567-577
function _requestWithdrawApr0(uint256 _amount, address _user) internal {
  _settleApr0(_user);
  Apr0UserData storage _apr0User = apr0Users[_user];
  if (_apr0User.principal == 0) {
    _apr0User.principalEpoch = epochNumber;
  }
  _apr0User.principal += _amount;
  apr0TotalPrincipal += _amount;
}
```

`principalEpoch` is set only once, on the first open request. If the user requests again in a later epoch while `principal != 0`, the new amount is merged into the old epoch's tag.

When the honest manager stops an epoch with a realized loss via `stopEpochWithDuration`, the CDO calls `collectWithdrawFunds`, which stores the haircut under the *current* `epochNumber` (`lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice`, `IdleCreditVault.sol:421`). APR0 principal is part of `pendingWithdraws` when that loss is distributed, so every pending receipt's claim is only funded at `lossRecoveryPrice`.

Both protective lookups then miss the mislabeled receipt:

1. The re-request guard (`IdleCreditVault.sol:261-271`) checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` but only treats the receipt as present if `withdrawsRequestsByEpoch[user][lossEpoch] != 0` (APR0 never writes this map) or `apr0Users[user].principalEpoch == lossEpoch`. With `principalEpoch` stuck at the earlier epoch, the guard passes.
2. `_claimLossAdjustedWithdrawRequest` → `_clearWithdrawClaimForEpoch` → `_withdrawClaimAmountsForEpoch` (`IdleCreditVault.sol:865-880`) only counts APR0 principal when `principalEpoch == _claimEpoch`, so `claimBasis` for the loss epoch is 0 and no haircut is applied.
3. `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:319-350`) then pays `settledPrincipal + principal + settledInterest` at par via `_transferFundedClaim`, burning the receipt tokens.

### Impact Explanation
The loss-adjusted epoch was underfunded by design: `collectWithdrawFunds` only pulled `pendingBasis * lossRecoveryPrice` of underlying into the strategy and zeroed `pendingWithdraws`. An APR0 user whose receipt escaped the haircut can withdraw 100% of principal from a pool that was only funded for e.g. `lossRecoveryPrice` of it. The shortfall is paid out of underlyings belonging to other claimants (funded normal/instant receipts and remaining strategy holders), i.e. direct theft/pro-rata insolvency equal to `(1 - lossRecoveryPrice) * escapedPrincipal`, or a revert that freezes later honest claims once the balance is drained.

### Likelihood Explanation
Requires APR0 mode (`unscaledApr == 0`), which is a supported configuration handled by `prepareStopEpochWithApr0` and `_requestWithdrawApr0`. The attacker is an ordinary KYC'd tranche holder who must (a) hold an open APR0 receipt across one epoch boundary and (b) request again in a second epoch that is later stopped with a loss. Losses via `stopEpochWithDuration` are a normal, non-privileged-abuse code path (borrower underfunds; honest manager calls it). No special timing or privileged collusion is needed; the attacker just places two withdraw requests in different epochs before the loss epoch ends.

### Recommendation
Update `principalEpoch` per request, or track APR0 principal per epoch like normal receipts. Minimal fix: in `_requestWithdrawApr0`, revert (or force settle-and-close) when `principal != 0 && principalEpoch != epochNumber`, so an open APR0 bucket can never span two epochs; alternatively store APR0 principal in a per-epoch mapping (`apr0PrincipalByEpoch[user][epoch]`) and make `_withdrawClaimAmountsForEpoch`/`requestWithdraw`'s guard iterate the same key that `collectWithdrawFunds` used (`epochNumber` at loss time). Add a test where two APR0 requests in different epochs are followed by `stopEpochWithDuration` loss and assert the second receipt is haircutted.

### Proof of Concept
Foundry fork test sketch (based on `test/foundry/IdleCDOEpochQueue.t.sol` helpers):

```solidity
// Mode: APR0 (unscaledApr == 0), fixed-APR epoch variant with stopEpochWithDuration loss.
function testApr0ReceiptEscapesLossHaircut() external {
  // 1. set unscaledApr = 0 (manager/CDO path as in existing APR0 tests).
  // 2. user deposits, epoch E1 starts; user calls requestWithdraw -> apr0Users.principalEpoch = E1.
  // 3. stop E1 with NO loss (collectWithdrawFunds funds pending fully) -> epochNumber = E2.
  //    user does NOT claim; principal stays open, principalEpoch still E1.
  // 4. epoch E2 starts; user calls requestWithdraw again.
  //    _requestWithdrawApr0 keeps principalEpoch == E1 but pendingWithdraws now includes
  //    principal tagged as E1 while it will be haircut under epochNumber == E2.
  // 5. borrower underfunds; manager calls stopEpochWithDuration(apr, 0, dur, lossAmount).
  //    collectWithdrawFunds sets lossRecoveryPriceByEpoch[E2] < RECOVERY_FULL, pendingWithdraws = 0.
  // 6. user calls cdoEpoch.claimWithdrawRequest():
  //    - _claimLossAdjustedWithdrawRequest: lastWithdrawRequest = E2, but
  //      _withdrawClaimAmountsForEpoch(E2) sees apr0Users.principalEpoch == E1 -> claimBasis = 0.
  //    - _claimFundedWithdrawRequest pays settledPrincipal + principal + interest AT PAR.
  // assert: user received full principal while the strategy was only funded
  //         lossRecoveryPrice * pendingBasis -> balance shortfall for remaining claimants.
}
```

Expected assertion: `underlying.balanceOf(user)` after claim equals the full un-haircutted principal plus settled interest, while `lossRecoveryPriceByEpoch[E2] < 1e18` and the strategy's transferable balance (`balanceOf(this) - defaultRecoveryReserve`) is insufficient to pay remaining funded claims at par — demonstrating the haircut escape and insolvency.
