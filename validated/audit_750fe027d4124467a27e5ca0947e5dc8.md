### Title
Stale per-epoch instant-withdraw receipt data is not cleared on claim, corrupting default-recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` burns the user's strategy-token receipt and zeroes `instantWithdrawsRequests[_user]`, but never clears the per-epoch bookkeeping written at request time: `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (set at lines 371-372, cleared only in the defaulted-epoch path at lines 847-853). This is the same bug class as the external report: data registered at "mint" (receipt creation) is not removed when the receipt is "burned" (claimed). The stale entries are later consumed by `defaultPendingClaimBasis` (line 647), `_defaultPrefundedInstantReserve` (line 719) and `_claimDefaultedInstantWithdrawRequest` (line 844), so an already-paid receipt is counted again if the borrower defaults in the same epoch.

### Finding Description
In `requestInstantWithdraw` the vault records three pieces of state for the current epoch:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:366-374
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

The normal claim path clears only the aggregate:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:387-392
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Unlike `_claimFundedWithdrawRequest` (line 326), this path has no "wait one epoch" gate, so a user can claim within the same epoch once the CDO has funded instant liquidity (prefunded mode / `getInstantWithdrawFunds`). The stale `instantWithdrawsRequestsByEpoch[_user][N]` and `instantWithdrawClaimsByEpoch[N]` then survive. If the borrower defaults while `epochNumber == N` and `finalizeDefaultRecovery` runs:

- `defaultPendingClaimBasis` adds the already-claimed amount via `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, inflating `totalBasis` and diluting `defaultRecoveryPrice` for every recovery claimant (lines 644-649, 688).
- `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` using the inflated `instantBasis`, over-reserving already-held funds (lines 719-721).
- When the same user claims again, `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (line 844). Two outcomes:
  - `instantWithdrawsRequests[_user] -= claimBasis` underflows if the user has no new request → their `claimInstantWithdrawRequest` permanently reverts while the stale entry persists (their legitimately funded receipt path is reachable only after this call, so recovery claims for any co-mingled new request are blocked).
  - If the user has since opened a new instant request of at least the stale amount, the subtraction succeeds, the vault burns their *new* receipt tokens and pays `claimBasis * defaultRecoveryPrice` from `defaultRecoveryReserve` for a receipt that was already paid at par — a direct double payout draining the isolated reserve owed to defaulted-epoch claimants.

### Impact Explanation
Direct theft of the default-recovery reserve (a user is paid twice for one receipt, funded by other claimants' recovery), plus systematic dilution of `defaultRecoveryPrice` for all AA/BB claimants and instant redeemers because the claim basis is overstated by every same-epoch already-claimed instant receipt. If the stale entry exceeds the user's new aggregate, their claim path reverts, permanently freezing any new funded instant receipt while `defaultRecoveryFinalized` holds. Broken invariants: one receipt one payout, and loss/recovery distribution integrity.

### Likelihood Explanation
Medium. Requires (a) an instant-withdraw request funded and claimed inside the same epoch — achievable in prefunded/liquid configurations since `claimInstantWithdrawRequest` has no epoch-wait check, and (b) a borrower default finalized in that same epoch with `pendingInstantWithdraws != 0` or with the attacker re-requesting. Borrower default is a designed-for flow (`finalizeDefaultRecovery`, `DefaultDistributor`), and the attacker needs only a KYC-passed lender position; no privileged misbehavior is required. The stale-write itself is unconditional — every instant claim leaves it behind.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch records for the epoch(s) the receipt belongs to, mirroring the normal path's cleanup (`withdrawsRequestsByEpoch`, `lastWithdrawRequest`, `apr0Users` deletion at lines 343-348). Concretely, track the request epoch for instant receipts (or clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount) so a paid receipt can never re-enter `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, or `_claimDefaultedInstantWithdrawRequest`.

### Proof of Concept
Foundry fork scenario against `IdleCreditVault` + `IdleCDOEpochVariant` (prefunded or liquid borrower so instant claims are servable mid-epoch):

```solidity
// Epoch N running, attacker is a KYC'd LP holding strategy tokens via the CDO.
// 1. Attacker requests instant withdraw of X.
vm.prank(attacker);
cdo.requestInstantWithdraw(X); // -> strategy.requestInstantWithdraw(X, attacker)

// 2. CDO funds the instant request mid-epoch (getInstantWithdrawFunds /
//    collectInstantWithdrawFunds moves X to the strategy).
vm.prank(manager);
cdo.getInstantWithdrawFunds(X); // strategy.collectInstantWithdrawFunds(X)

// 3. Same epoch: attacker claims at par. Stale entries remain:
//    instantWithdrawsRequestsByEpoch[attacker][N] == X
//    instantWithdrawClaimsByEpoch[N]            == X
vm.prank(attacker);
cdo.claimInstantWithdrawRequest();
assertEq(underlying.balanceOf(attacker), balBefore + X);

// 4. Attacker opens a second instant request of X (or more) in epoch N.
vm.prank(attacker);
cdo.requestInstantWithdraw(X);

// 5. Borrower defaults in epoch N; manager finalizes recovery.
//    defaultPendingClaimBasis() now includes the stale X from step 3,
//    so defaultRecoveryPrice is diluted for all claimants.
vm.prank(manager);
cdo.finalizeDefault(recovered, recoverySource); // -> finalizeDefaultRecovery

// 6. Attacker claims: _claimDefaultedInstantWithdrawRequest pays
//    staleX * defaultRecoveryPrice from the reserve AND the funded path
//    then pays the new X again -> double payout on one live receipt.
vm.prank(attacker);
cdo.claimInstantWithdrawRequest();
// Assert reserve drained beyond the attacker's true basis:
// defaultRecoveryReserve decreased by staleX * price + X.
```

Note: the exact funding path in step 2 depends on the deployed CDO variant (prefunded vs. stop-epoch collection); I could not fully verify `getInstantWithdrawFunds`'s timing within this iteration. If instant funding is only possible at `stopEpoch` (which increments `epochNumber`), the stale entries would land in epoch N-1 while `defaultRecoveryEpoch` is N, neutralizing the double-claim — but the `instantWithdrawClaimsByEpoch` inflation still applies if the claim is made after partial prefunding within the same epoch. The invariant violation (per-epoch receipt data surviving burn) is unconditional and worth fixing regardless.
