### Title
Multisig executes requests below the live-member confirmation threshold because `delete_member`/`DeleteKey` do not purge a removed member's existing confirmations on other pending requests - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts confirmations stored in `self.confirmations` against `self.num_confirmations` without verifying that every confirming entry still corresponds to a current member. `delete_member` (multisig2) and the `DeleteKey` action (multisig) only clean up requests *created* by the removed member; they leave that member's confirmations on requests created by other members untouched. As a result, a request can reach and cross the confirmation threshold using approvals from members who have since been removed, letting it execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
`confirm()` compares `confirmations.len() as u32 + 1` to `self.num_confirmations` and executes the request once that threshold is met: [2](#0-1) 

`delete_member` removes the member and deletes only requests where `r.member == member` (i.e., requests that member originated), then removes the member's `num_requests_pk` entry and their access key/entry from `self.members`: [1](#0-0) 

Nothing in `delete_member` scans `self.confirmations` to strip entries where the removed member had confirmed a request originated by someone else. `assert_valid_request`, called from `confirm`, only checks that the *caller* is a current member — it never re-validates the members already recorded in the request's confirmation set: [3](#0-2) 

The same pattern exists in the original `multisig` contract's `DeleteKey` action, which likewise only removes requests signed by the deleted key, not that key's confirmations elsewhere: [4](#0-3) [5](#0-4) 

The invariant that should hold is: `confirmations counted for a request == confirmations from members who are still current members`. Once a member is removed, their prior confirmation should either be discarded or excluded from the count. Instead the equality breaks: the stored count can exceed the number of confirmations actually given by live members, because stale confirmations persist and are counted as if still valid.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." Concretely:
- Members M1..M5 with `num_confirmations = 3`.
- M1 (an insider planning to leave/be removed) creates request R = `Transfer` funds to an attacker-controlled account, and confirms it (1/3).
- M2 (colluding member also departing) confirms R (2/3).
- Later, M1 and M2 are legitimately removed via `DeleteMember` requests (e.g., normal offboarding), unrelated to R. `delete_member` does not touch R's confirmations because R was not created by M1 or M2's own `num_requests_pk`/request bookkeeping filter (`r.member == member` only matches requests *they created*, not ones they merely confirmed).
- Now only M3, M4, M5 remain as live members, yet R already has 2 stale confirmations recorded. A single additional confirmation from any remaining member (e.g., M3) satisfies `confirmations.len() + 1 >= 3` and executes R — a fund transfer approved by only 1 out of 3 current live members, despite the contract's stated 3-of-N guarantee.

This breaks custody/authorization guarantees of the multisig without requiring any privileged action beyond normal member behavior (creating/confirming requests and later legitimate member removal), and results in NEAR being moved by parties not entitled to authorize that move at the required threshold.

### Likelihood Explanation
Multisig contracts are explicitly designed for membership churn (`AddMember`/`DeleteMember`, `AddKey`/`DeleteKey`), so member turnover is an expected, routine operation rather than an edge case. Any scenario where a member departs (voluntarily or by removal) while having previously confirmed a still-pending request from another member triggers this condition. Because pending requests can be added and left unconfirmed for extended periods before being confirmed or deleted, and `REQUEST_COOLDOWN` only limits deletion timing rather than confirmation staleness, the window in which a stale confirmation can be exploited is realistic in normal contract usage.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over all requests' confirmation sets and strip the removed member's entry from every request's confirmations, not just requests they created. Alternatively, when counting confirmations in `confirm()`, filter `confirmations` to only those entries that are still `self.members.contains(...)` before comparing against `self.num_confirmations`.

### Proof of Concept
1. Deploy multisig2 with members `[M1, M2, M3, M4, M5]` and `num_confirmations = 3`.
2. As `M1`, call `add_request_and_confirm` with a `Transfer` action to attacker's account → confirmations = `{M1}` (1).
3. As `M2`, call `confirm(request_id)` → confirmations = `{M1, M2}` (2), request not yet executed.
4. Via legitimate multisig process, execute a `DeleteMember { member: M1 }` request and a `DeleteMember { member: M2 }` request (unrelated administrative action) — `delete_member` removes M1/M2 from `self.members` and clears only requests they created; the Transfer request's confirmation set `{M1, M2}` is untouched.
5. As `M3` (now one of only 3 remaining members: M3, M4, M5), call `confirm(request_id)` on the Transfer request. `confirmations.len() as u32 + 1 == 3 >= num_confirmations (3)` → request executes, transferring funds, despite only 1 of the 3 current live members ever approving it.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
