I found the analogous binding-breaking vulnerability: in `multisig2` (and `multisig`), the deletion of a member/key only purges confirmations from requests that member *originated*, not confirmations that member *contributed* to other members' requests. A stale confirmation from a removed member counts toward the `num_confirmations` threshold check in `confirm()`.

### Title
Stale confirmations from removed members count toward execution threshold, allowing requests to execute below live-member quorum - (File: multisig2/src/lib.rs)

### Summary
`delete_member()` in `multisig2/src/lib.rs` only removes requests **originated** by the deleted member (`r.member == member`), and only clears the `confirmations` set wholesale for those requests. It never scans other still-open requests to strip the deleted member's confirmation entry out of their `confirmations: HashSet<String>`. Since `confirm()` decides execution purely by comparing `confirmations.len()` against `self.num_confirmations`, a confirmation cast by a member who is later removed keeps counting toward the threshold for any request they confirmed but did not originate.

### Finding Description
`delete_member` at [1](#0-0)  filters `self.requests` for `r.member == member` (the request's *originator*) and clears confirmations only for those matched request IDs:
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
It does not iterate `self.confirmations` to remove the deleted member's key from confirmation sets of requests originated by *other* members. `confirm()` at [2](#0-1)  only checks `confirmations.len() as u32 + 1 >= self.num_confirmations`, treating every entry in the set as a valid, live confirmer. This is the exact structural analog of the VotingEscrow `_burn()` bug: a "membership/vote" record (`confirmations` entry vs. `dstRep` delegate entry) is not cleaned up when the underlying identity (multisig member vs. token owner) is removed, so a stale entry is later counted as if it were still live. Here the broken binding is: `confirmations counted == live members who actually approved`. After removal, `confirmations counted > live members`, so the equality is violated.

The same defect exists in the legacy `multisig/src/lib.rs` `DeleteKey` handler at [3](#0-2) , which likewise only purges requests where `r.signer_pk == pk` and never scrubs that key from confirmations on requests signed by others.

### Impact Explanation
This crosses an authorisation/threshold boundary explicitly listed as in-scope Critical impact: "a multisig request executed below threshold." A request can be confirmed and executed (moving NEAR, deploying code, adding/removing keys) with fewer *live* approvals than `num_confirmations` mandates, because one or more of the counted confirmations belong to members who have since been removed from the multisig (e.g., for being compromised or malicious). This directly undermines the K-of-N security guarantee the contract is supposed to enforce and can let a minority of live members (plus stale confirmations from removed/compromised keys) push through a transfer or upgrade.

### Likelihood Explanation
This requires no special privilege beyond being (or having been) a legitimate multisig member/key holder — an unprivileged-relative-to-the-final-outcome attacker scenario, matching the pattern in the report where a normal participant's leftover approval becomes exploitable. It is a realistic operational sequence: a member confirms an open request, is later removed (e.g., a compromised key is deleted via `DeleteMember`/`DeleteKey`), and the pending request they confirmed is executed afterward by the remaining live confirmations reaching only `num_confirmations - 1` new approvals, since the stale one is still counted. No malicious deployment or special setup deviation is required; it is reachable through documented flows (`add_request` → `confirm` → `DeleteMember` → `confirm`).

### Recommendation
When removing a member (`delete_member` in `multisig2/src/lib.rs`, and the `DeleteKey` action in `multisig/src/lib.rs`), iterate over **all** open requests' `confirmations` sets (not just requests originated by that member) and remove the deleted member's entry from each. Re-persist the updated confirmation sets, and if removing the entry would still leave enough live confirmations to trigger execution, only that should stand — otherwise the request should simply lose that stale vote and require an additional live confirmation.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]`, `num_confirmations = 3`.
2. Member `A` calls `add_request` to create request `R` (e.g., `Transfer`).
3. Member `B` calls `confirm(R)` → confirmations = `{A, B}` (len 2), not yet `>= 3`, so it stays pending — [4](#0-3) .
4. The multisig (via a separate fully-confirmed `DeleteMember` request) removes member `B` — `delete_member` only clears requests **originated** by `B`; `R` was originated by `A`, so `R`'s confirmations set still contains `B` — [5](#0-4) .
5. Member `C` calls `confirm(R)`. `confirmations.len()` (2, including stale `B`) `+ 1 = 3 >= num_confirmations (3)` → `R` executes, even though only `A` and `C` are live members who actually approved it — one fewer live approval than the configured 3-of-N threshold requires.
