### Title
Stale `get_last_globally_accepted_block` check in v1 tenure-change duplicate detection re-opens a fixed double-tenure-start gap - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionData::validate_tenure_change_payload` in the v1 chainstate module still guards against a duplicate tenure-start block using `signer_db.get_last_globally_accepted_block`, which only recognizes blocks that have reached full network consensus. The v2 implementation of the identical check was fixed to use `get_last_signed_block` (which also matches `LocallyAccepted` blocks) after a documented mainnet-relevant regression was found. v1 was never given the same fix.

### Finding Description
`validate_tenure_change_payload` is the only place `DuplicateBlockFound` is raised for a competing tenure-start proposal, and it runs solely at proposal arrival inside `check_proposal` — it is "not re-run at validate-ok or at signing" [6](#0-5) . In v1 (`stacks-signer/src/chainstate/v1.rs`, lines 505-518), the check calls `get_last_globally_accepted_block`, so a block this signer has already locally accepted (i.e., signed with `signed_self`) but that has not yet reached the 70%+ group threshold is invisible to this gate, letting a second, competing `BlockFound` tenure-change proposal for the same tenure pass `check_proposal` [7](#0-6) . The v2 code path fixes exactly this by using `get_last_signed_block`, which matches `LocallyAccepted` or `GloballyAccepted` [8](#0-7) , and a dedicated regression test documents the prior, now-reintroduced-in-v1 behavior as a bug: "Before the fix, this would have incorrectly passed because get_last_globally_accepted_block would not find the locally-accepted block" [9](#0-8) .

### Impact Explanation
If reachable, this reproduces the ERC1155-style class of bug: an "exists"/"already signed" check that should gate a one-time state transition (first tenure-start block per tenure) uses a stale/narrower predicate, letting a second competing proposal through the gate a version too early. This maps to the rule's "one-per-height/tenure equality" break: a signer could be asked to place a second signature over a conflicting tenure-start block in the same tenure. Whether this rises to Critical (an actual conflicting/duplicate signature) depends on whether the section-5 own-tenure conflict re-check (`get_signed_conflicts` in `v0/signer.rs`) independently blocks the second proposal from ever being signed, since two competing `BlockFound` blocks for one tenure share the same `chain_length` and so should be caught by that later, tenure-agnostic guard.

### Likelihood Explanation
Requires only a single miner (or the same miner re-proposing) submitting two competing tenure-start proposals for one tenure within the window between the signer's local acceptance of the first and its global acceptance — a normal, frequently-occurring race already covered by an equivalent regression test for v2. No majority-signer collusion or key compromise is needed to trigger the *code path*; only the ultimate depth of impact (does it produce a second signature) is unconfirmed.

### Recommendation
Align `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload`'s duplicate-block check with v2 by replacing `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` with `signer_db.get_last_signed_block(&block.header.consensus_hash)`, and add the equivalent regression test (`check_tenure_change_rejects_when_locally_accepted_block_exists`) to the v1 test suite to prevent this asymmetry from silently reappearing.

### Proof of Concept
1. Signer locally accepts (signs) tenure-start block B1 for tenure T (state `LocallyAccepted`, `signed_self` set), but B1 has not yet reached group/global acceptance.
2. A miner proposes a second, competing tenure-start block B2 for the same tenure T (same `consensus_hash`, same `chain_length`, different transactions/timestamp).
3. Under the v1 chainstate path, `validate_tenure_change_payload` calls `get_last_globally_accepted_block(T)`, which returns `None` (B1 is only `LocallyAccepted`), so the `DuplicateBlockFound` rejection is skipped and B2 passes `check_proposal`.
4. Compare against v2, where the equivalent test `check_tenure_change_rejects_when_locally_accepted_block_exists` explicitly asserts this exact scenario must be rejected [10](#0-9) ; no such assertion exists for the v1 path.
