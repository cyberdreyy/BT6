### Title
Stale confirmations from removed multisig members are counted toward quorum, allowing execution below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` in `multisig2/src/lib.rs` only purges pending requests and confirmation sets for requests that the removed member *originated*; it does not scan other pending requests' `confirmations` sets to strip out that member's prior confirmation. Since `confirm()` grants execution purely by comparing `confirmations.len()` to `num_confirmations`, a stale confirmation entry left behind by a since-removed member still counts toward quorum, letting a request execute (e.g. a `Transfer`) with fewer *currently active* members approving than `num_confirmations` requires.

### Finding Description
`MultiSigContract::confirm` at [1](#0-0)  checks quorum solely via `confirmations.len() as u32 + 1 >= self.num_confirmations`, where `confirmations: LookupMap<RequestId, HashSet<String>>` stores member-string identifiers per request, as declared at [2](#0-1) .

When a member is removed via `DeleteMember` / `delete_member`, the cleanup logic at [3](#0-2)  only iterates `self.requests` to find and purge requests where `r.member == member` (i.e., requests that member *created*). It removes that member from `self.members` and (if key-based) deletes their access key, but it never inspects or updates `self.confirmations` for *other* pending requests where the removed member had already called `confirm()` and left their identifier in the `HashSet<String>`.

Consequently, if member M confirms request R (created by someone else) and is later removed from the multisig via a separate `DeleteMember` request, R's `confirmations` set still contains M's identifier. The binding that should hold — `confirmations.len()` reflects only votes from members in the *current* `self.members` set — is broken: `confirmations ⊄ current_members` after removal, yet `confirm()` treats `confirmations.len()` as if it always represents live-member approvals.

### Impact Explanation
This crosses the "confirmations counted versus live members" custody boundary: a `Transfer`, `AddKey`, `FunctionCall`, or other privileged `MultiSigRequestAction` can be executed by fewer *currently trusted* members than `num_confirmations` mandates, because one "confirmation" is a ghost vote from someone no longer authorized. For a k-of-n multisig controlling contract funds or upgrade authority, this can allow a NEAR transfer or privileged action to execute below the intended authorization threshold — matching the Critical impact category ("a multisig request executed below threshold").

### Likelihood Explanation
This requires no attacker privilege beyond being a legitimate multisig member at the time of confirming, and requires only that the multisig separately decide to remove a member who had previously confirmed a still-pending request — a normal operational sequence (member confirms request A, is later removed for unrelated reasons, request A is still open). No malicious deployment, redeploy, or foundation/owner-only action is needed beyond the multisig's own ordinary `DeleteMember` governance action, which any member set can trigger without foreseeing the interaction.

### Recommendation
In `delete_member`, iterate all pending requests (not just those created by the removed member) and strip the removed member's entry from each `confirmations: HashSet<String>`, mirroring how the audited `TrustedGuardiansPlugin` fix "automatically cleared removed guardians from `guardiansVoted`." Alternatively, change `confirm()` to validate at execution time that every recorded confirmation still corresponds to a member present in `self.members` before comparing against `num_confirmations`, and have `get_confirmations` filter out stale entries similarly.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. B creates request R (`add_request`) for a `Transfer` action; B does not confirm.
3. A calls `confirm(R)` → `confirmations = {A}`.
4. C calls `confirm(R)` → `confirmations = {A, C}` (2 confirmations, below quorum of 3, so `remove_request`/execute is not yet triggered).
5. Separately, the multisig executes a `DeleteMember { member: C }` request (via `A`, `D`, and one more confirming a `DeleteMember` request) — see `delete_member` at [3](#0-2) ; since C did not originate R, R's confirmations are untouched and still contain `{A, C}`.
6. D now calls `confirm(R)`. `confirmations.len()` is `2` (`{A, C}`), so `2 + 1 >= 3` is true and `execute_request` runs the `Transfer` — even though only `A` and `D` are current live members who approved (C's vote is stale), i.e. only 2 live confirmations authorized a request that required 3.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
