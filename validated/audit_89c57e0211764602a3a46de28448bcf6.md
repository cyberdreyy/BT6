### Title
Instant-withdraw receipts can be claimed before their epoch funding arrives, draining underlyings reserved for other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays the full `instantWithdrawsRequests[_user]` balance with no epoch gating, unlike `_claimFundedWithdrawRequest` which enforces `epochNumber > lastWithdrawRequest[_user]`. A request created in the current epoch — after `collectInstantWithdrawFunds` already moved that epoch's instant liquidity — can be burned immediately for vault-held underlyings that belong to other users' matured, funded receipts. This is the closest analog to the upstream bug: a handle (the instant receipt) remains dereferenceable before/after the funding lifecycle that was supposed to bound it.

### Finding Description
In `IdleCreditVault.requestInstantWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:356-375), the vault burns the CDO's strategy tokens, mints the user a 1:1 strategy-token receipt, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]` and `pendingInstantWithdraws`. There is no check that the request is only claimable once funded.

`claimInstantWithdrawRequest` (lines 380-393) then does:

- `amount = instantWithdrawsRequests[_user]` — the aggregate across all epochs, including a receipt created moments ago in the current epoch.
- `_burn(_user, amount)` — burns the freshly minted receipt.
- `_transferFundedClaim(_user, amount)` — pays underlying already held by the vault.

Instant-epoch liquidity is collected once via `collectInstantWithdrawFunds` (lines 398-403), which decrements `pendingInstantWithdraws` and pulls only the amount funded at that point. A request made after collection (or during a running epoch) is therefore unfunded, yet the claim path treats it identically to a funded one. Any underlying the vault holds — matured normal withdraw receipts awaiting `claimWithdrawRequest`, reserved default recovery, or previously collected instant funds for other users — is used to satisfy the premature claim. In contrast, the normal withdraw path explicitly reverts while `epochNumber <= lastWithdrawRequest[_user]` (lines 326-328); the instant path has no equivalent marker or gate.

### Impact Explanation
Unprivileged theft and insolvency: an attacker holding tranche tokens requests an instant withdraw in an epoch whose instant funding was already collected (or while the pool has funded pending claims), immediately calls `claimInstantWithdrawRequest`, and receives underlying funded for other users. Those users' later claims revert on insufficient balance — permanent freezing/theft of their matured receipts equal to the attacker's claimed amount. No privileged role, default, or oracle manipulation is required; the attacker only needs tranche tokens.

### Likelihood Explanation
Likelihood depends on the IdleCDOEpochVariant side allowing `claimInstantWithdrawRequest` during a running epoch or before collection; the vault itself performs no gating, so any epoch phase in which the vault holds funded underlying and the CDO forwards a claim enables it. The asymmetry between the instant path (no epoch check) and the normal path (explicit `epochNumber <= lastWithdrawRequest` revert) indicates the missing guard is not intentional defense-in-depth elsewhere in this contract.

### Recommendation
Record the request epoch per user (e.g., `lastInstantWithdrawRequest[_user] = currentEpoch`) or reuse `instantWithdrawsRequestsByEpoch`, and in `claimInstantWithdrawRequest` only pay receipts whose epoch has been funded — i.e., exclude entries for `epochNumber` when `pendingInstantWithdraws` still covers them, mirroring the `epochNumber <= lastWithdrawRequest[_user]` gate used for normal receipts. Alternatively, track a per-epoch funded amount and cap claims to funded portions.

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// Phase: epoch running, instant liquidity for this epoch already collected;
// vault holds underlying backing victim's matured (funded) withdraw request.
function testInstantWithdrawClaimsUnfundedReceipt() external {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    // victim: deposit and request normal withdraw in epoch N
    _depositWithUser(victim, 10_000 * ONE_SCALE, true);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // epoch N stops: borrower funds pending receipts -> vault now holds underlyings
    _startEpochAndCheckPrices(0);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0); // pendingWithdraws funded into vault

    // attacker: deposit fresh and request INSTANT withdraw in epoch N+1 (buffer)
    _depositWithUser(attacker, 5_000 * ONE_SCALE, true);
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(5_000 * ONE_TRANCHE, address(AAtranche));

    // attacker claims instantly, before any funding of this epoch's instant bucket
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, 5_000 * ONE_SCALE);

    // victim's matured claim now fails: vault underlying was drained
    vm.prank(victim);
    vm.expectRevert(); // ERC20 transfer exceeds vault balance
    cdoEpoch.claimWithdrawRequest();
}
```

Note: I could not fully verify within this iteration whether `IdleCDOEpochVariant.claimInstantWithdrawRequest` applies an epoch-phase check that would block the claim; if such a gate exists, the finding reduces to premature payout only within the funding window and the "no vault-side epoch marker" remains a latent invariant violation.
