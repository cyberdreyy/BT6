### Title
`batchMint` on the B-20 asset/stablecoin precompiles is all-or-nothing, so one policy-blocked recipient DOSes mint issuance to every other recipient in the batch - ([File: crates/common/precompiles/src/b20_asset/logic/v1.rs])

### Summary
The B-20 asset (and stablecoin) precompile's `batchMint` operation mints to a list of recipients in a single call and is documented as "All-or-nothing." Internally it loops over `(recipient, amount)` pairs and calls the version's `mint` logic with `?`, so any single recipient's mint failure aborts the whole batch and discards all prior mints in that call. Because `mint` enforces the `MintReceiver` policy (which can be wired to a `BLOCKLIST`/`ALLOWLIST` policy in the `PolicyRegistry`), an issuer that queues several beneficiaries' mints together will have the entire batch reverted if even one recipient becomes policy-blocked, permanently denying issuance to the other, non-blocked recipients in that same transaction until the caller manually detects and removes the offending entry.

### Finding Description
`batch_mint` is implemented identically in `AssetV1`/`AssetV2` and their `StablecoinV1`/`StablecoinV2` counterparts: [1](#0-0) 

The loop uses `self.mint(token, caller, recipient, amount, true)?`, so the `?` operator propagates any error from a single recipient's mint straight out of `batch_mint`, aborting the entire batch (all state changes from earlier iterations of the same call are rolled back by the storage-provider's checkpoint/journal semantics used throughout the precompile suite). The interface doc explicitly states the intended (but risky) all-or-nothing semantics: [2](#0-1) 

`mint` itself gates the destination through the `MintReceiver` policy slot, one of the built-in B-20 policy types that can be wired to `BLOCKLIST`/`ALLOWLIST`/composite policies via the `PolicyRegistry` precompile: [3](#0-2) 

Any account holder authorized to update that policy's registry membership (or the token's own admin acting through `updateAllowlist`/`updateBlocklist`) can add a target recipient to a blocking policy at any time between when an issuer decides on a batch and when the batch transaction lands. The `mint` implementation checks this policy and reverts with `PolicyForbids`/`AccountNotSeizable`-style typed errors when the receiver isn't authorized, exactly mirroring the `seize_with_memo` receiver-policy gate whose failure behavior is exercised in the test suite: [4](#0-3) 

Because `batch_mint`'s inner `?` bubbles up the very first failing recipient's error and unwinds the whole call, one policy-blocked (or otherwise disqualified, e.g. zero-address) entry in a `recipients`/`amounts` array is enough to prevent minting to every other, perfectly valid recipient in that same transaction.

### Impact Explanation
This is a direct precompile-dispatch-reachable DoS: `batchMint` is dispatched from ordinary user transactions (`C::batchMint` in the ABI dispatcher) requiring only `MINT_ROLE`, and its failure mode is entirely dependent on third-party-controllable state (policy membership) that the caller does not control at construction time. Legitimate issuance workflows that batch payroll, airdrops, or compliance-driven distributions can be permanently stalled for an entire batch whenever any single beneficiary is (or becomes) blocked, forcing the batch to be re-split/re-submitted — a griefing/DoS vector against the token issuer's batch-mint transactions, and by extension against the timely delivery of funds to unrelated, non-blocked recipients. Given the audit precedent (BendDAO M-03) explicitly established that ERC-20-style blocklist interactions are in-scope viable risk even though "informative" in isolation, the same class here is a genuine functional DoS on a reachable, unprivileged-adjacent operation (any `MINT_ROLE` holder, and blockability is controlled by policy admins, not the mint caller).

### Likelihood Explanation
Moderate. It requires (a) an issuer using `batchMint` with more than one recipient, and (b) any recipient in that batch being (or becoming) blocked under the wired `MintReceiver` policy before/at the time of execution. Given that Base's B-20 precompile suite explicitly supports policy-gated compliance tokens (allowlist/blocklist/composite policies), and `batchMint` is advertised as a compliance-oriented "batched issuance" primitive, this scenario is a foreseeable and easily triggerable operational condition rather than a purely theoretical one.

### Recommendation
Change `batch_mint` from strict all-or-nothing propagation to either: (1) explicit pre-validation of every recipient against the `MintReceiver` policy before performing any state mutation, returning a single aggregated error identifying the offending indices (still atomic, but fails fast and cheaply without requiring rebuilding the batch by trial-and-error), and/or (2) provide a best-effort mode that skips/queues policy-blocked recipients and emits a `MintSkipped`-type event while still minting to the remaining authorized recipients, mirroring the "try/catch"-style mitigation recommended in the original BendDAO finding. At minimum, document this all-or-nothing footgun prominently and ensure `batchMint` callers deduplicate/pre-check policy membership off-chain before submission to reduce accidental DoS from stale membership data.

### Proof of Concept
1. Token admin/`MINT_ROLE` holder wires `MintReceiver` to a `BLOCKLIST` policy via `PolicyRegistry` and leaves address `X` unblocked initially.
2. A policy admin (who may be a different, less trusted party than the mint caller) calls `updateBlocklist` to add `X` to the blocklist (this can legitimately happen for compliance reasons, unrelated to the pending mint batch).
3. The issuer submits `batchMint(recipients = [A, X, B], amounts = [amtA, amtX, amtB])`.
4. `batch_mint`'s loop calls `mint(..., X, amtX, true)`, which fails `B20Guards::ensure_policy_type(token, B20PolicyType::MintReceiver, X)` and returns `PolicyForbids`.
5. The `?` operator propagates this error out of `batch_mint`, reverting the whole precompile call — `A` and `B` receive nothing even though they were never blocked, until the issuer manually removes `X` and resubmits.

    fn batch_mint(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        recipients: Vec<Address>,
        amounts: Vec<U256>,
        privileged: bool,
    ) -> Result<()> {
        // The pause and role guards below are the sole authorization gate for the batch: the inner
        // mints run privileged to avoid re-checking per recipient. Do not remove or conditionalize
        // these guards. Check order: PAUSE -> ROLE -> INPUT -> BUSINESS.
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::MINT)?;
        if !privileged {
            B20Guards::ensure_token_role(token, caller, B20TokenRole::Mint)?;
        }
        if recipients.len() != amounts.len() {
            return Err(BasePrecompileError::revert(IB20Asset::LengthMismatch {
                leftLen: U256::from(recipients.len()),
                rightLen: U256::from(amounts.len()),
            }));
        }
        if recipients.is_empty() {
            return Err(BasePrecompileError::revert(IB20Asset::EmptyBatch {}));
        }
        for (recipient, amount) in recipients.into_iter().zip(amounts) {
            self.mint(token, caller, recipient, amount, true)?;
        }
        Ok(())
    }

    fn seize_with_memo(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        from: Address,
        to: Address,
        amount: U256,
        memo: B256,
    ) -> Result<()> {
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::SEIZE)?;
        B20Guards::ensure_token_role(token, caller, B20TokenRole::Seize)?;
        // `to != 0` guards against a disguised burn; `from != 0` guards against a disguised mint
        // (`Transfer(0x0, to, ...)`), matching `transfer_inner`.
        if to == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }));
        }
        if from == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidSender { sender: from }));
        }
        if from == to {
            return Err(BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }));
        }
        B20Guards::ensure_seizable(token, from)?;
        // Gate the destination like `mint` gates `MintReceiver`: an unset scope is always-allow, so a
        // treasury need not be allowlisted by default.
        B20Guards::ensure_policy_type(token, B20PolicyType::SeizeReceiver, to)?;
        self.move_balance(token, from, to, amount)?;
        // `Memo` must immediately follow the `Transfer` (from `move_balance`), before `Seized`.
        self.emit_memo(token, caller, memo)?;
        token
            .accounting_mut()
            .emit_event(IB20::Seized { caller, from, to, amount }.encode_log_data())
    }
