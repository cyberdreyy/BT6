### Title
Job-controlled ESC (0x1B) bytes are not neutralized by `EscapeForPosix`, allowing forged ANSI sequences in the trace-log echo line - (`functions/script_legacy/internal/command_formatter.go`)

### Summary
`FormatLogLine` wraps the job-supplied command text with the literal `ansiGreen`/`ansiReset` control sequences and then escapes the whole string before embedding it in an `echo` statement. In POSIX mode this escaping is done by `EscapeForPosix`, which — contrary to the stated precondition — does not hex-escape or strip control bytes below `0x20` at all, so a job-controlled `command` string containing a raw `0x1B` byte passes straight through into the emitted shell script and, ultimately, the executed trace-log line.

### Finding Description
`FormatLogLine` builds the display string as `ansiGreen + commandPrefix + f.getDisplayCommand(command) + ansiReset` [1](#0-0) . `getDisplayCommand` returns the job's command text verbatim for single-line commands, and unmodified except for truncation on multi-line ones [2](#0-1) , so the raw bytes of the job's script line flow directly into the wrapped string.

For POSIX mode, the wrapped string is passed to `EscapeForPosix`, whose switch statement only special-cases the characters `` ` " \ $ `` and a fixed shell metacharacter set (space, `!`, `#`, `%`, `&`, `(`, `)`, `*`, `<`, `=`, `>`, `?`, `[`, `|`); every other rune, including `0x1B` (ESC), falls through to the `default` branch and is written unchanged [3](#0-2) . This directly contradicts the audit's stated precondition that "EscapeForAnsiC/EscapeForPosix ... hex-escape control chars <0x20 by rule" — `EscapeForPosix` performs no such hex-escaping for any control byte. Therefore any literal ESC byte a job author embeds in a `script:` line (trivially achievable via YAML double-quoted scalar escapes such as `"\e[0mFAKE\e[1;32m"`, which YAML decodes to raw `0x1B` bytes) is echoed to the trace verbatim, interleaved with the real `ansiGreen`/`ansiReset` wrapper bytes.

The ANSI-C path (`EscapeForAnsiC`, used when `posixMode` is false) does hex-escape bytes `< 0x20` [4](#0-3) , but the escaped string is emitted as `echo $'%s'` [5](#0-4) . Bash's `$'...'` (ANSI-C quoting) itself decodes `\xHH` sequences back into raw bytes at shell-evaluation time, so the hex-escaping only protects against breaking out of the shell quoting — it does not stop the ESC byte from being reconstituted and written to the terminal/trace by `echo`. This makes the "prevents ANSI escape sequences" comment in `escape.go` inaccurate as a terminal-injection defense, though it is a secondary point compared to the outright missing escaping in the POSIX path.

### Impact Explanation
A pipeline author (unprivileged CI job author) can craft a `script:` line whose bytes include forged `\033[0m ... \033[1;32m` sequences. Once rendered by `FormatLogLine`/`echo`, the trace can visually present a fabricated "command" line (e.g., one that looks like a legitimate `CI_JOB_TOKEN` rotation or an innocuous command) distinct from the command actually executed. Any downstream consumer of the trace (a human reviewer, or an automated log-scraper/gate that inspects trace text to make job-state decisions) can be misled by this forged content — matching the scoped impact of trace spoofing feeding job-state decisions.

### Likelihood Explanation
- Preconditions: the runner must be configured/detected to use POSIX-mode script generation (`PosixEscape`/`posixMode = true`), which is a supported, non-privileged configuration path, not an admin-only choice.
- The attacker only needs control over a `script:` line (or any command string reaching `CommandProcessor.ProcessCommand` → `FormatLogLine`) — ordinary pipeline-author capability [6](#0-5) .
- Embedding a raw ESC byte in a YAML script string is trivial (double-quoted scalar `\e` escape, or a literal control character), so the exploit is fully repeatable and requires no special privilege.

### Recommendation
Update `EscapeForPosix` to hex-escape (or otherwise neutralize, e.g. strip) all control bytes `< 0x20` and `0x7F`, mirroring `EscapeForAnsiC`'s control-character handling, so ESC and other control bytes originating from job-controlled command text cannot survive into the emitted `echo` line unescaped. Additionally, since ANSI-C `$'...'` quoting reconstitutes `\xHH` sequences at shell-evaluation time, consider stripping/rejecting ESC bytes from the *job-controlled* portion of the string before wrapping with the trusted `ansiGreen`/`ansiReset` constants, rather than relying on hex-escaping the already-concatenated string for terminal-injection protection.

### Proof of Concept
```go
func TestEscapeForPosix_DoesNotNeutralizeEsc(t *testing.T) {
    s := "\x1b[0mFAKE_JOB_TOKEN_ROTATED\x1b[1;32m"
    escaped := EscapeForPosix(s)
    // Currently fails: raw ESC (0x1B) bytes pass through untouched.
    assert.NotContains(t, escaped, "\x1b", "raw ESC byte must not appear in POSIX-escaped output")
}

func TestFormatLogLine_PosixMode_EscInjection(t *testing.T) {
    formatter := NewCommandFormatter(true) // POSIX mode
    malicious := "\x1b[0mFAKE_JOB_TOKEN_ROTATED\x1b[1;32m"
    result := formatter.FormatLogLine(malicious)

    // Byte-scan for any literal, non-hex-escaped ESC in the final echoed string.
    assert.NotContains(t, result, "\x1b",
        "job-controlled ESC bytes must be neutralized before being embedded in the ansiGreen/ansiReset wrapper")
}
```
Both assertions fail against the current implementation, confirming raw `0x1B` bytes from job-controlled input reach the final `echo` statement in POSIX mode.

```go
	command = ansiGreen + commandPrefix + f.getDisplayCommand(command) + ansiReset

	if f.posixMode {
```

```go
func EscapeForPosix(s string) string {
	if s == "" {
		return "''"
	}

	var buf strings.Builder
	needsQuoting := false

	for _, r := range s {
		switch r {
		case '`', '"', '\\', '$':
			buf.WriteRune('\\')
			buf.WriteRune(r)
			needsQuoting = true
		case ' ', '!', '#', '%', '&', '(', ')', '*', '<', '=', '>', '?', '[', '|':
			buf.WriteRune(r)
			needsQuoting = true
		default:
			buf.WriteRune(r)
		}
	}

	if needsQuoting {
		return `"` + buf.String() + `"`
	}

	return buf.String()
```
