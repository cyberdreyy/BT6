### Title
Message ID collision causes cross-user response delivery in WebAPI trigger callback map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`api.Message.Validate` in [1](#0-0)  correctly derives `Body.Sender` from the cryptographic signature via `ExtractSigner`, so the attacker cannot forge another user's sender address. However, the downstream consumer of validated messages for the legacy WebAPI trigger path, `handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go`, indexes pending callbacks solely by the caller-supplied `MessageId`, with no sender component and no existence/uniqueness check before overwrite, allowing message-ID collisions across different senders to cross-deliver responses.

### Finding Description
`HandleLegacyUserMessage` stores the pending callback keyed only by `msg.Body.MessageId`: [2](#0-1) 

This is a plain map assignment with no check for an existing entry with that key (unlike the sibling `common/requestcache.go`, which explicitly composes the lookup key from both sender and id): [3](#0-2) 

When a DON node later responds with the same `MessageId`, `handleWebAPITriggerMessage` looks up and deletes the entry purely by `MessageId` and forwards the response to whatever callback is currently registered under that key: [4](#0-3) 

Exploit flow:
1. Victim submits a signed gateway message with `method = web_api_trigger` and `message_id = "X"`. `Validate` accepts it and correctly binds `Body.Sender = victim`. The handler stores `savedCallbacks["X"] = victimCallback` and forwards the request to DON nodes.
2. Before the node responds, the attacker (any EOA, using their own private key) submits their own signed message reusing `message_id = "X"`. `Validate` accepts it too — signature verification only proves the attacker legitimately signed their own message; it never checks whether `"X"` is already in use by another sender. `Body.Sender = attacker` is correctly set, but this field is not used as part of the callback map key.
3. `HandleLegacyUserMessage` unconditionally overwrites `savedCallbacks["X"]` with the attacker's callback, silently discarding the victim's pending callback registration.
4. When a DON node responds to the victim's original request (still carrying `message_id = "X"`), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds the attacker's callback, and delivers the victim's response payload to the attacker.

This confirms the exploit idea in the question ("submit signature bytes reusing a victim's id") and the stated invariant violation: request identity used for response routing does not include the authenticated sender, even though the sender is available and cryptographically verified at the `Validate` step.

### Impact Explanation
If the response payload routed through this webapi_trigger path can carry sensitive data destined for the original caller (e.g., workflow trigger results, compute action outputs), an attacker can hijack it by ID-squatting, resulting in cross-user response disclosure. This matches "cross-user response confusion" in-scope impact; the concrete severity depends on the sensitivity of payloads carried over this particular handler (compute_action/web_api_trigger), which is generally lower sensitivity than direct vault/DKG secret disclosure, so the practical impact here is best characterized as a High-severity cross-tenant response leak rather than the Critical vault-secret-theft scenario described in the question (the vault and confidential-relay handlers separately use per-request `activeRequests` maps keyed by request ID under their own auth-processing flow, not by this savedCallbacks map).

### Likelihood Explanation
No special privilege is required beyond the ability to send a signed gateway request with an arbitrary EOA key, which is exactly the baseline capability of any gateway client. The attacker needs to guess or observe a victim's `message_id` (client-generated, often predictable or observable via side channels/logs/timing) and race the request before the DON responds; this is a plausible but time-sensitive precondition, making exploitation feasible but not trivially guaranteed on every attempt.

### Recommendation
Change the `savedCallbacks` map key (and any other message-routing map that currently keys only by `MessageId`, such as `handler.dummy.go`'s equivalent map) to a composite of `(Body.Sender, Body.MessageId)`, mirroring the pattern already used in `common/requestcache.go`. Additionally, reject (rather than silently overwrite) inserts into these maps when a key is already in use.

### Proof of Concept
Go handler-level integration test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two signed `api.Message`s with `method = web_api_trigger`, identical `Body.MessageId = "dup-id"`, but signed by two distinct ECDSA keys (`victimKey`, `attackerKey`), producing `Body.Sender = victim` and `Body.Sender = attacker` respectively after `Validate()`.
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`, then call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)` on the same handler instance.
3. Simulate a DON node response for `message_id = "dup-id"` by invoking `handler.handleWebAPITriggerMessage(ctx, nodeRespMsg, nodeAddr)`.
4. Assert that `attackerCallback.SendResponse` was invoked with the response payload (not `victimCallback.SendResponse`), proving cross-user delivery, and assert `victimCallback` never receives a response (silent drop) — demonstrating both the confusion and the DoS on the victim's original request.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.

	}
	return nil

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
