### Title
Attacker can abort an orchestrated `stopEpochWithDuration` batch via instant withdraw, delaying epoch settlement for all cluster vaults — (File: contracts/IdleCreditVaultManagerOrchestrator.sol)

### Summary
`IdleCreditVaultManagerOrchestrator.stopEpochWithDuration` stops multiple credit-vault epochs atomically in a single loop [1](#0-0) . If the `stopEpochWithDuration` call on any one vault reverts, the entire transaction rolls back and none of the other vaults get stopped. A precondition checked inside `IdleCDOEpochVariant.stopEpochWithDuration` — that there are no pending instant withdrawals (`_pendingInstant() != 0`) [2](#0-1)  — can be flipped between the operator's simulation and execution by any tranche holder submitting an instant-withdraw request. This is the same bug class as the Notional finding: a batched maintenance action reverts because one item's precondition went stale, delaying processing of all items.

### Finding Description
The orchestrator iterates over `StopEpochWithDurationAction[]` and calls `cdo.stopEpochWithDuration(op.newApr, op.interest, op.duration, op.loss)` followed by `_finalizeStopEpoch` for each vault, with no per-item try/catch or skip [3](#0-2) . Inside the CDO, `stopEpochWithDuration` calls `_checkNotAllowed` which reverts when `_pendingInstant() != 0`, i.e., when unfunded instant-withdraw requests exist [2](#0-1) .

Attack path (running epoch, instant-withdraw mode enabled — an operator-configured mode where `instantWithdrawDelay` is set and `disableInstantWithdraw == false`):

1. Epoch end passes on vaults A, B, C in the cluster. The operator builds a `stopEpochWithDuration` batch for all three and checks (simulation/off-chain) that none has pending instant withdrawals.
2. Before or while the batch tx is in the mempool, an unprivileged tranche holder (attacker) on vault A calls `cdoA.requestWithdraw(...)`, which registers an instant-withdraw request in `IdleCreditVault.instantWithdrawsRequests`, making `_pendingInstant() != 0`.
3. The batch tx executes: vault A's `stopEpochWithDuration` reverts via `_checkNotAllowed`; the revert propagates, rolling back vaults B and C's stops as well.
4. Every resubmission can be griefed the same way at trivial cost (a minimal tranche balance plus a request), repeatedly delaying epoch closure for the whole cluster.

Note also that `startEpoch` has the same atomicity shape [4](#0-3) , though the exploitability there is weaker since start preconditions are less user-influenceable.

### Impact Explanation
Temporary freezing of funds: epoch stop is the gate for processing pending withdrawal requests and claims (`processWithdrawRequests`, `processWithdrawalClaims`, `claimWithdrawRequest`). Each successful grief delays settlement for every vault in the batch, so withdrawers across the cluster cannot claim until the batch finally lands. The attacker costs only gas plus a small tranche position on one vault to delay the entire batch. This mirrors the Notional report's impact (delayed rebalancing of still-unhealthy currencies) transposed to delayed epoch stopping of still-functional vaults.

### Likelihood Explanation
Requires a vault cluster operated through the orchestrator (its stated purpose), instant withdrawals enabled on at least one vault, and a mempool-observable or predictable batch call — all realistic conditions. The attacker needs only a tranche position, which any KYC-passed lender can hold. Repetition makes sustained delay feasible, though the operator can eventually split the batch per-vault as mitigation, capping the delay.

### Recommendation
Make the loop per-item fault-tolerant, matching the external report's fix pattern ("skip the healthy/failed item and continue"):

```solidity
// contracts/IdleCreditVaultManagerOrchestrator.sol
try cdo.stopEpochWithDuration(op.newApr, op.interest, op.duration, op.loss) {
  _finalizeStopEpoch(cdo, op.allowDefault);
} catch {
  emit EpochStopSkipped(op.cdo); // new event; operator retries individually
}
```

Alternatively, keep atomicity but document that callers must submit per-vault transactions, or pre-check `pendingInstant == 0` on-chain and skip rather than revert.

### Proof of Concept
Foundry fork PoC (skeleton, along the lines of `test/foundry/IdleCreditVaultManagerOrchestrator.t.sol` setup [5](#0-4) ):

```solidity
// Setup: register cdoA, cdoB with orchestrator; enable instant withdraws on cdoA
// (manager: cdoA.setInstantWithdrawParams(delay, aprDelta, false)); start epochs.

// 1. Warp past epochEndDate on both vaults.
vm.warp(cdoA.epochEndDate() + 1);

// 2. Attacker (any tranche holder on cdoA) submits instant-withdraw request
//    front-running the operator's batch tx.
vm.startPrank(attacker);
cdoA.requestWithdraw(attackerTrancheBal, address(aaTrancheA));
vm.stopPrank();
assertGt(strategyA.pendingInstantWithdraws(), 0);

// 3. Operator submits batch stop for both vaults.
IdleCreditVaultManagerOrchestrator.StopEpochWithDurationAction[] memory actions =
  new IdleCreditVaultManagerOrchestrator.StopEpochWithDurationAction[](2);
actions[0] = ...({cdo: address(cdoA), ..., allowDefault: false});
actions[1] = ...({cdo: address(cdoB), ..., allowDefault: false});

vm.prank(operator);
vm.expectRevert(); // NotAllowed inside cdoA.stopEpochWithDuration
orchestrator.stopEpochWithDuration(actions);

// 4. cdoB (healthy, no pending instant withdraws) is also still running.
assertTrue(cdoA.isEpochRunning());
assertTrue(cdoB.isEpochRunning()); // griefed: B's stop was rolled back
```

Uncertainty: the grep confirmed instant-withdraw request plumbing exists in `IdleCreditVault`/`IdleCDOEpochVariant` (`instantWithdrawsRequests`, `pendingInstantWithdraws`, `_pendingInstant()`), but I did not fully trace `requestWithdraw`'s gating (e.g., whether a small request reliably increments `pendingInstant` before `getInstantWithdrawFunds` is called). If requests are only counted instant after `getInstantWithdrawFunds`, the griefing vector narrows to racing that call, though the stale-precondition atomic-batch issue still stands with other stop preconditions (e.g., `_interest < _pendingWithdrawFees` bounds).
