### Title
Use-after-clear receipt: older-epoch withdraw receipts escape the `stopEpochWithDuration` haircut and are paid at par from the underfunded strategy - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` applies a single `lossRecoveryPriceByEpoch[epochNumber]` haircut to the **entire** `pendingWithdraws` basis when the borrower under-funds a stop, but `_claimLossAdjustedWithdrawRequest` only clears the per-epoch receipt stored at `lastWithdrawRequest[_user]`. Any receipt the same user opened in an earlier, still-unclaimed epoch remains in `withdrawsRequests[_user]` and is subsequently paid **at par** by `_claimFundedWithdrawRequest` from the same underfunded pot — a stale-state/double-counting analog of a use-after-free: the aggregate basis was "freed" (zeroed) while a per-epoch sub-record still points at claimable value.

### Finding Description
- `requestWithdraw` records each receipt twice: in the aggregate `withdrawsRequests[_user] += _amount` and per-epoch `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, and updates `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:281-294`). It only blocks a new request when the *latest* epoch has a nonzero `lossRecoveryPriceByEpoch` (`IdleCreditVault.sol:261-271`).
- At `stopEpochWithDuration`, `collectWithdrawFunds(_amount < pendingBasis)` zeroes the global `pendingWithdraws` and stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` (`IdleCreditVault.sol:411-421`). The haircut therefore applies to **all** pending receipts, regardless of the epoch they were created in.
- On claim, `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` via `_clearWithdrawClaimForEpoch`, paying `claimBasis * lossRecoveryPrice / 1e18` (`IdleCreditVault.sol:789-801`, `811-837`).
- Execution then falls through to `_claimFundedWithdrawRequest`, which pays the remaining `withdrawsRequests[_user]` — i.e., the older-epoch receipt — **at par** via `_transferFundedClaim` (`IdleCreditVault.sol:338-349`).

So a user holding receipts from two epochs where only the newer one is keyed by `lastWithdrawRequest` gets `Y * price + X * 1.0` out of a pot that was funded with `(X + Y) * price`.

### Impact Explanation
Direct theft / insolvency. The attacker extracts `X * (1 - lossRecoveryPrice)` more than the funded reserve covers, where `X` is the older-epoch receipt. Because the strategy's funded balance is exactly `pendingBasis * price`, every extra wei paid to the attacker is a wei missing for other claimants: later `claimWithdrawRequest` calls either under-pay or revert on `ERC20: transfer amount exceeds balance`, permanently freezing part of honest users' already-haircut claims. The `_transferFundedClaim` reserve guard (`IdleCreditVault.sol:897-907`) does not help pre-default (reserve == 0), and `requestWithdraw`'s loss-epoch guard only inspects `lastWithdrawRequest`, not older per-epoch entries.

Quantified example: attacker requests X = 100,000 at epoch N and Y = 100,000 at epoch N+1; borrower funds only 50% at the next stop (`lossRecoveryPrice = 0.5e18`, funded = 100,000). Attacker claims `100,000*0.5 + 100,000` = 150,000 from a 100,000 balance shared with other pending receipts — a 50,000 overpayment stolen from the pool.

### Likelihood Explanation
Requires an unprivileged KYC'd lender to hold unclaimed withdraw receipts across two request epochs (normal usage; comments explicitly allow delaying claims across epochs) and a `stopEpochWithDuration`-style partial loss (`_amount < pendingWithdraws`), which is a designed-for code path, not an edge case. No privileged misbehavior needed; the manager/owner calls `stopEpoch` honestly. The bug triggers deterministically whenever these conditions coincide.

### Recommendation
Track every pending receipt's loss exposure per epoch, not via the single `lastWithdrawRequest` pointer. Options:
- Iterate/accumulate all `withdrawsRequestsByEpoch[_user]` epochs whose receipts were pending at the loss stop, or store a per-user bitmap/set of loss epochs to clear at claim time.
- Alternatively, when `collectWithdrawFunds` records a loss epoch, require that each user's entire `withdrawsRequests[_user]` aggregate be attributable to that epoch, or apply the haircut pro rata inside `_claimFundedWithdrawRequest` for receipts predating the loss.
- Simplest containment: in `requestWithdraw`, revert if `withdrawsRequests[_user] != 0` (or `apr0Users[_user]` non-empty), forcing users to claim all outstanding receipts before opening a new one, mirroring the post-default guard at `IdleCreditVault.sol:249`.

### Proof of Concept
```solidity
// Foundry fork test, based on test/foundry/IdleCreditVault.t.sol harness
function testLossAdjustedReceiptOlderEpochPaidAtPar() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    uint256 amount = 100_000 * ONE_SCALE;
    address attacker = makeAddr('attacker');
    uint256 mintedAA = _depositWithUser(attacker, amount);

    // epoch N buffer: attacker requests half -> receipt X
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));

    // honest start/stop, request NOT funded yet (borrower keeps cash)
    _startEpochAndCheckPrices(0);

    // epoch N+1 buffer: attacker requests remaining half -> receipt Y
    // (no lossRecoveryPrice set yet, guard passes)
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();

    // borrower under-funds the stop: only 50% of pendingWithdraws collected
    // -> collectWithdrawFunds stores lossRecoveryPriceByEpoch[epochNumber] = 0.5e18
    deal(defaultUnderlying, borrower, pending / 2);
    vm.startPrank(borrower);
    underlying.approve(address(cdoEpoch), pending / 2);
    vm.stopPrank();
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // duration variant calls stopEpochWithDuration internally

    // attacker claims: loss-adjusted Y*0.5 + funded X*1.0
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;

    // funded pot held pending/2; attacker alone pulls > pending/2 * (his share)
    // assert he received X + Y/2, i.e. the older receipt at par:
    assertGt(got, pending / 2); // overpaid relative to funded reserve
}
```
The assertion demonstrates the invariant break: total claims exceed total funded underlyings for the same receipt basis.
