### Title
Loss haircut from `collectWithdrawFunds` only applies to the epoch stored in `lastWithdrawRequest`, letting older unclaimed receipts claim at par and drain the funded reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
When `stopEpochWithDuration` realizes a loss, `IdleCreditVault.collectWithdrawFunds` haircuts the *aggregate* `pendingWithdraws` bucket pro rata and stores the recovery price under a single epoch key (`lossRecoveryPriceByEpoch[epochNumber]`). However, the claim-side lookup `_claimLossAdjustedWithdrawRequest` resolves the loss epoch exclusively through the single-slot `lastWithdrawRequest[_user]`, and `_clearWithdrawClaimForEpoch` clears only that one epoch's entry in `withdrawsRequestsByEpoch`. A user who holds withdraw receipts recorded in *earlier* epochs — a legitimate state since `withdrawsRequestsByEpoch` is a per-epoch mapping and requests can accumulate across multiple buffer periods — escapes the haircut entirely: after the loss-adjusted claim clears only the latest epoch's basis, `_claimFundedWithdrawRequest` pays the remaining `withdrawsRequests[_user]` (including the under-funded older basis) at par from the strategy's funded balance. Early claimers over-collect and later claimers' transfers revert, permanently freezing the remainder. This mirrors CVE-2017-9077: state (the loss haircut) is applied to an aggregate but "inherited" only by the most recent per-epoch record.

### Finding Description
Relevant code in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` records receipts per epoch: `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and overwrites `lastWithdrawRequest[_user] = currentEpoch` (lines 282-293). It is called on every request while the epoch is not running, so a user who requests in epoch E1, does not claim, and requests again in epoch E2 holds basis in both `withdrawsRequestsByEpoch[E1]` and `[E2]`, with `lastWithdrawRequest = E2`. The only guard (lines 263-270) blocks a *new* request when the *current* `lastWithdrawRequest` epoch already has a nonzero `lossRecoveryPriceByEpoch` — it does not prevent receipts from spanning multiple epochs before any loss occurs.
- `collectWithdrawFunds` (lines 411-430): when `_amount < pendingBasis`, it sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`. The loss is computed against the whole pending bucket — including receipts booked under earlier epochs — but recorded under a single epoch key.
- `_claimLossAdjustedWithdrawRequest` (lines 789-801) reads `lossEpoch = lastWithdrawRequest[_user]`; if that single epoch has no loss price it returns 0. It calls `_clearWithdrawClaimForEpoch(_user, lossEpoch, false)` which zeroes only `withdrawsRequestsByEpoch[_user][lossEpoch]` and decrements `withdrawsRequests[_user]` by that epoch's piece only (lines 815-820).
- `_claimFundedWithdrawRequest` (lines 319-350) then pays whatever remains in `withdrawsRequests[_user]` at par via `_transferFundedClaim`, since the epoch-wait check `epochNumber <= lastWithdrawRequest[_user]` passes after `lastWithdrawRequest` was reset to 0 (line 832-836 clears it when it equals the cleared epoch).

Attack sequence (buffer phases, honest manager/borrower):

1. Epoch E1 buffer: attacker (KYC'd lender) deposits AA and calls `requestWithdraw` → basis `X` recorded in `withdrawsRequestsByEpoch[attacker][E1]`, `lastWithdrawRequest = E1`. Attacker intentionally does not claim after stopEpoch.
2. Epoch E2 buffer: attacker calls `requestWithdraw` again → basis `Y` in `[E2]`, `lastWithdrawRequest = E2`. Other honest users also have pending basis in E2.
3. Epoch E2 runs; manager calls `stopEpochWithDuration` with `_lossAmount > 0`. `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` computes the pending share of the loss over the aggregate `pendingBasis` (which includes the attacker's E1 basis `X`) and funds only `pendingToFund < pendingBasis`; `lossRecoveryPriceByEpoch[E2]` is set, `pendingWithdraws = 0`.
4. Attacker calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` haircuts and clears only the E2 basis `Y`; `lastWithdrawRequest` resets to 0. Then `_claimFundedWithdrawRequest` pays the still-recorded E1 basis `X` at par from the strategy's underlying balance — even though `X` was included in the haircut computation and only `X * lossRecoveryPrice` was ever funded for it.

### Impact Explanation
Broken invariant: loss waterfall / one-receipt-one-payout. The funded reserve equals `pendingBasis * lossRecoveryPrice` total, but claimers whose receipts sit under epochs other than `lastWithdrawRequest` redeem at `RECOVERY_FULL`. Each such claim over-draws by `basis * (1 - lossRecoveryPrice)`. First claimers (the attacker) extract more than their haircut share; the strategy balance is exhausted before later honest claimers withdraw, so their claims revert on the ERC20 transfer — i.e., direct theft plus permanent freezing of the remainder (the funds were burned from active NAV and never re-funded). Quantified loss to honest receipt holders equals `X * (1 - lossRecoveryPrice)` per exploiting user, bounded by the aggregate pending basis; with e.g. a 50% loss price an attacker controlling half the pending basis via a stale-epoch receipt claims ~25% of the reserve above their entitlement.

### Likelihood Explanation
Requires: (a) `stopEpochWithDuration` with `_lossAmount > 0` — an honest-manager action used for realized partial losses, explicitly supported by `previewLossAdjustedWithdrawFunds`; (b) an attacker holding a pending receipt from an epoch earlier than the loss epoch — achievable by simply not claiming for one epoch and requesting again, which the code permits and even documents ("if a user does not claim... he will have to wait for another epoch to claim both requests"); (c) `defaultRecoveryInitialized` true (lazy-init on any request after upgrade). No privileged collusion needed. The claim race favors whoever claims first after funding.

### Recommendation
Apply the loss haircut to the aggregate basis, not to one epoch key. Options: store the loss epoch(s) and iterate all of a user's `withdrawsRequestsByEpoch` entries (bounded by request count) when claiming, or better — since the haircut is applied to the aggregate `pendingBasis` anyway — record a single `lossRecoveryPrice` that applies to *all* receipts pending at collection time (e.g., a checkpoint index: receipts created before the loss checkpoint claim at `lossRecoveryPrice`, receipts after claim at par). At minimum, `requestWithdraw` must revert whenever *any* of the user's recorded per-epoch bases sits in an epoch with a nonzero `lossRecoveryPriceByEpoch`, not only the `lastWithdrawRequest` epoch; and `_claimFundedWithdrawRequest` must re-check that no residual basis belongs to a loss epoch before paying at par. Alternatively, force-claim or fold older receipts into the current epoch's basis at request time so per-user basis can never span a loss boundary.

### Proof of Concept
Foundry fork sketch against the epoch CDO + `IdleCreditVault` (structure follows `test/foundry/IdleCreditVault.t.sol` withdraw-request tests):

```solidity
function testLossHaircutBypassViaStaleEpochReceipt() public {
    // --- Epoch E1 buffer: attacker requests and never claims ---
    uint256 amt = 100_000e6;
    deal(underlying, attacker, amt);
    vm.startPrank(attacker);
    idleCDO.depositAA(amt);
    uint256 req1 = cdoEpoch.requestWithdraw(0, address(AAtranche)); // basis X @ E1
    vm.stopPrank();

    // stop E1 honestly funded so req1 becomes claimable but stay unclaimed
    _stopEpochFullyFunded();
    // attacker does NOT claim; request epoch marker stays E1
    assertEq(strategy.lastWithdrawRequest(attacker), strategy.epochNumber() - 1);

    // --- Epoch E2 buffer: attacker requests again (allowed, no loss yet) ---
    deal(underlying, attacker, amt);
    vm.startPrank(attacker);
    idleCDO.depositAA(amt);
    uint256 req2 = cdoEpoch.requestWithdraw(0, address(AAtranche)); // basis Y @ E2
    vm.stopPrank();
    assertEq(strategy.lastWithdrawRequest(attacker), strategy.epochNumber()); // E2

    // honest user also has pending basis in E2
    _requestAsUser(honest, amt);

    // --- Epoch E2 runs; manager stops with realized loss ---
    uint256 loss = strategy.pendingWithdraws() / 2; // 50% loss on pending bucket
    _stopEpochWithLoss(loss); // collectWithdrawFunds(pendingToFund < pendingBasis)
    assertGt(strategy.lossRecoveryPriceByEpoch(strategy.lastWithdrawRequest(attacker)), 0);

    // --- Attacker claims ---
    uint256 balBefore = IERC20(underlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = IERC20(underlying).balanceOf(attacker) - balBefore;

    // Attacker received Y*price + X at PAR instead of (X+Y)*price
    uint256 price = strategy.lossRecoveryPriceByEpoch(strategy.epochNumber() - 1);
    assertGt(got, (req1 + req2) * price / 1e18);
    assertApproxEqAbs(got, req1 + req2 * price / 1e18, 1); // X paid at par

    // --- Honest user's claim now underfunded / reverts ---
    vm.prank(honest);
    vm.expectRevert(); // strategy balance drained
    cdoEpoch.claimWithdrawRequest();
}
```

Uncertainty to verify in the PoC: the exact epoch index used as the `lossRecoveryPriceByEpoch` key depends on whether `collectWithdrawFunds` executes inside `_stopEpoch` before `IdleCreditVault.deposit` increments `epochNumber` (IdleCDOEpochVariant.sol:466 vs 474); either way the key is a single epoch and cannot cover receipts recorded under multiple `withdrawsRequestsByEpoch` slots. Also note `lastWithdrawRequest` resetting to 0 in `_clearWithdrawClaimForEpoch` (line 832-836) is what unlocks the subsequent par claim via `_claimFundedWithdrawRequest` without waiting another epoch.
