### Title
Aggregate `instantWithdrawsRequests` balance is paid at par while funding is tracked per-epoch, letting a multi-epoch instant receipt overdraw the strategy - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the OBI `writev` bug — where `iov[0]` (first segment) was resolved but `iov_iter.count` (total across all segments) was used as the copy length — `IdleCreditVault.claimInstantWithdrawRequest` resolves funding per epoch (`instantWithdrawsRequestsByEpoch` / `pendingInstantWithdraws` / `collectInstantWithdrawFunds`) but pays out the aggregate `instantWithdrawsRequests[_user]` in a single `_transferFundedClaim`. A holder who accumulates instant-withdraw receipts across epochs where only part of the basis has been funded can claim the total immediately, spending underlying that belongs to other claimants.

### Finding Description
Instant withdraw requests are funded lazily and per epoch:

- `requestInstantWithdraw` records `instantWithdrawsRequests[_user] += _amount`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, and increments the global unfunded remainder `pendingInstantWithdraws` (lines 356–375).
- The borrower/CDO later funds the queue through `collectInstantWithdrawFunds`, which only decrements `pendingInstantWithdraws` and pulls underlying into the strategy (lines 398–403). There is no per-epoch "funded up to" marker paid out at claim time.
- `claimInstantWithdrawRequest` then does `uint256 amount = instantWithdrawsRequests[_user]` and pays the full aggregate at par via `_transferFundedClaim` (lines 387–392). Outside of default finalization there is no check that the user's receipts — across all epochs — were actually funded. `_transferFundedClaim` only protects `defaultRecoveryReserve` (lines 897–907); any other underlying sitting in the strategy (funded claims of other users, prefunded instant reserves, recovery-prefund balances) is spendable.

So the "pointer" (funded per-epoch basis) describes only the first segment, while the "length" (aggregate `instantWithdrawsRequests[_user]`) covers all segments. A second, still-unfunded request is paid out of other users' money — the same overread/overwrite shape as reading `iov_iter.count` bytes from `iov[0].iov_base`.

Concrete sequence:

1. Epoch N is running with instant withdrawals enabled. Attacker (any KYC'd tranche holder) calls `requestInstantWithdraw(A)`; `instantWithdrawsRequests[attacker] = A`, `pendingInstantWithdraws = A`.
2. Attacker does not claim. Epoch rolls to N+1; the borrower/CDO funds epoch N's instant claims via `collectInstantWithdrawFunds(A)`, so the strategy now holds `A` underlying earmarked for instant claimants and `pendingInstantWithdraws = 0`.
3. Attacker calls `requestInstantWithdraw(B)` again in epoch N+1 (no per-user gating prevents a second request; unlike `requestWithdraw` there is no "claim old receipts first" check). Now `instantWithdrawsRequests[attacker] = A + B` and `pendingInstantWithdraws = B` (unfunded).
4. Attacker calls `claimInstantWithdrawRequest` (via the CDO). The function burns `A + B` receipt tokens and transfers `A + B` underlying, while only `A` was ever funded. The extra `B` is paid from underlying held for other users' funded claims or instant reserves.

The guard that exists for normal withdraws — `epochNumber <= lastWithdrawRequest` revert and per-epoch claim gating in `_claimFundedWithdrawRequest` — has no counterpart on the instant path, and `pendingInstantWithdraws != 0` does not block `claimInstantWithdrawRequest`.

### Impact Explanation
Direct theft / insolvency: the attacker redeems `B` underlying that was never funded by the borrower. That `B` is taken from underlying reserved for other instant-withdraw claimants or funded normal-withdraw claims, so honest users' later claims revert on insufficient balance — a permanent loss up to the size of the attacker's second request (bounded only by their tranche holdings and available strategy liquidity).

### Likelihood Explanation
Requires instant withdrawals to be enabled and the attacker to hold tranche tokens across one epoch boundary. No privileged cooperation is needed; all attacker actions (`requestInstantWithdraw`, `claimInstantWithdrawRequest`) are permissionless user flows routed through the CDO. The window exists whenever a new instant request can be recorded before the prior one is claimed.

### Recommendation
Track funded vs unfunded instant basis separately and cap the claim at the funded portion, e.g. pay only `instantWithdrawsRequests[_user]` up to the amount funded for the epochs the user requested in (mirror the per-epoch accounting already used by `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`), or revert the claim while any of the user's instant receipts sit in `pendingInstantWithdraws`. Alternatively, gate `requestInstantWithdraw` so a user cannot open a new request while `instantWithdrawsRequests[_user] != 0`, matching the `requestWithdraw` guard pattern.

### Proof of Concept
A Foundry fork PoC (Solidity sketch) against `IdleCreditVault` + `IdleCDOEpochVariant` with instant withdrawals enabled:

```solidity
// test/foundry/InstantWithdrawOverclaim.t.sol
function testInstantWithdrawOverclaim() external {
    // enable instant withdrawals
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(delay, 1e18, false);

    // attacker deposits and receives tranches
    uint256 tranches = _depositWithUser(attacker, 100e6);

    // epoch running: request instant withdraw of A
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(tranches / 2, address(AAtranche)); // A

    // borrower/CDO funds epoch-N instant claims
    // -> strategy.collectInstantWithdrawFunds(A) via CDO startEpoch funding path
    _fundInstantClaims(); // pendingInstantWithdraws == 0, strategy holds A

    // attacker does NOT claim; requests B in the next epoch
    _rollToNextEpoch();
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(tranches / 2, address(AAtranche)); // B, unfunded

    // claim pays A + B though only A was funded
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, A + B); // B stolen from reserves
}
```

Uncertainty note: I verified the strategy-side accounting and the absence of a funding guard in `claimInstantWithdrawRequest`/`_transferFundedClaim`, but the `IdleCDOEpochVariant.claimInstantWithdrawRequest` wrapper (which may impose its own timing/funding gating before calling the strategy) could not be fully inspected in this session; if it does not check `pendingInstantWithdraws` coverage per user, the finding stands as described.
