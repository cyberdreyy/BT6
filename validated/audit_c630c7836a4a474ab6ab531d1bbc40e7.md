### Title
External-initiator credentials for any bridge can trigger runs on arbitrary jobs by numeric ID, bypassing the "EIs not allowed" restriction - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` grants any request presenting a *valid* EI-ACCESSKEY/EI-SECRET pair the exact same `*clsessions.User{Role: UserRoleRun}` object that real session/token-authenticated users get, with no binding to the originating `bridges.ExternalInitiator` record. `PipelineRunsController.Create` then decides whether to allow triggering a job run by numeric ID using `auth.GetAuthenticatedUser(c)` ("isUser"), which is true for both real users and EI-authenticated requests, so the comment's intended restriction ("only users are allowed to run jobs using int IDs - EIs not allowed") does not actually hold, and there is never a check comparing the authenticated EI to the target job.

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) authenticates the caller's `EI-ACCESSKEY`/`EI-SECRET` header pair against `store.FindExternalInitiator` and `bridges.AuthenticateExternalInitiator`, both scoped to a specific `bridges.ExternalInitiator` row. On success it stores that EI object under `SessionExternalInitiatorKey`, but also unconditionally sets: [1](#0-0) 
a *generic* `User{Role: UserRoleRun}` under `SessionUserKey` — indistinguishable from what `AuthenticateBySession`/`AuthenticateByToken` set for a genuine user.

This middleware is installed for the run-triggering route: [2](#0-1) 

`PipelineRunsController.Create` is the handler behind `POST /v2/jobs/:ID/runs`. It rejects UUID-style job IDs outright (webhook job type has been removed), then gates the remaining numeric-ID path on `isUser`: [3](#0-2) 

Because `auth.GetAuthenticatedUser(c)` (`core/web/auth/auth.go:178-187`) simply reads whatever object is stored at `SessionUserKey` — and `AuthenticateExternalInitiator` stores an identical `User` object there — `isUser` evaluates to `true` for EI-authenticated requests exactly as it does for genuine session/token users. The handler never calls `auth.GetAuthenticatedExternalInitiator(c)` to check which EI authenticated, nor does it correlate that identity with the target job's bridge/external-initiator binding at all. `GetAuthenticatedExternalInitiator` is defined but is not referenced anywhere else in the codebase that could enforce such a binding.

As a result, any holder of a valid EI-ACCESSKEY/EI-SECRET pair — issued for any bridge/job — can call `POST /v2/jobs/:ID/runs` with an arbitrary numeric job ID and successfully invoke `prc.App.RunJobV2(ctx, jobID, nil)`, triggering a run on a job it was never provisioned for.

### Impact Explanation
This is an authorization bypass allowing an attacker holding one external-initiator credential (a low-privilege, narrowly-scoped credential type) to trigger pipeline runs on any job in the node by numeric ID, not just the job/bridge that credential was issued for. Depending on job task graphs, this can cause unauthorized on-chain transactions, unwanted resource consumption, or unintended fund-moving/reporting actions — matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Requires only one valid EI-ACCESSKEY/EI-SECRET pair for any bridge configured on the node (the lowest privilege credential intentionally scoped to a single bridge). No admin/host access is needed. The bypass is deterministic and repeatable: same headers work against any job ID reachable through `/v2/jobs/:ID/runs`.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests authenticated via `AuthenticateExternalInitiator` (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` and reject if present, matching the code's own comment "EIs not allowed"), or if EI-triggered runs must be supported, verify the authenticated `bridges.ExternalInitiator` is authorized for the specific job/bridge referenced by `:ID` before calling `RunJobV2`. Additionally, avoid storing an indistinguishable generic `User` object for EI auth — use a distinct type/marker so `GetAuthenticatedUser`-based checks can't conflate EI and real-user sessions.

### Proof of Concept
Handler-level integration test plan (Go, using existing `internal/cltest` fixtures similar to `core/web/pipeline_runs_controller_test.go` and `core/web/external_initiators_controller_test.go`):
1. Start a test app/router via `cltest.NewApplicationWithConfig`/`web.NewRouter`.
2. Create Bridge A and Job A (numeric ID `jobAID`), and Bridge B and Job B (numeric ID `jobBID`).
3. Create External Initiator EI-A tied to Bridge A via `POST /v2/external_initiators`, capturing its `AccessKey`/`Secret`.
4. Send `POST /v2/jobs/{jobBID}/runs` with headers `X-Chainlink-EA-AccessKey: EI-A.AccessKey`, `X-Chainlink-EA-Secret: EI-A.Secret`.
5. Assert the response is **not** `401 Unauthorized` — instead it returns `200`/`201` with a created `pipelineRun` resource for Job B, proving EI-A (issued for Bridge A) successfully triggered a run on Job B.
6. Add a regression assertion for the fix: after applying the recommended check, the same request should return `401`/`403` since EI-A is not authorized for Job B (or EI auth is disallowed entirely on this route).
