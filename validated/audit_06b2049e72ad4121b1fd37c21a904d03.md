### Title
Rejected-then-accepted signer weight is double-counted in the node's block-status tally, corrupting the aggregated-weight vs. verified-accepts equality - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
In `StackerDBListener`'s StackerDB message loop, `BlockResponse::Accepted` and `BlockResponse::Rejected` messages for the same block use two *different* de-duplication sets (`gathered_signatures` vs. `responded_signers`) to decide whether a signer's weight should be added to `total_weight_approved` / `total_weight_rejected`. Because the accepted-path guard checks `gathered_signatures` (not `responded_signers`), a signer whose weight was already added to `total_weight_rejected` can later have the *same* weight added to `total_weight_approved` as well, with no corresponding removal from the rejected tally. This is the exact bug class from the external report: an amount that should be mutually exclusive with another bucket (there: fee vs. bad debt; here: rejected weight vs. approved weight) leaks across the accounting boundary due to inconsistent bookkeeping, inflating a value that a downstream threshold check treats as authoritative.

### Finding Description
`handle` in `StackerDBListener` processes `SignerMessageV0::BlockResponse` variants for a given `signer_signature_hash` and slot:

- Accepted path [1](#0-0) : weight is added to `block.total_weight_approved` guarded by `if !block.gathered_signatures.contains_key(&slot_id)`, then `slot_id` is inserted into *both* `gathered_signatures` and `responded_signers`.
- Rejected path [2](#0-1) : weight is added to `block.total_weight_rejected` guarded by `if block.responded_signers.insert(slot_id)`.

Both paths share the single `responded_signers` set, but only the rejected path relies on it for its own de-dup; the accepted path checks the unrelated `gathered_signatures` map. Consequence:

- Reject → later Accept (same block hash, same signer): the reject call inserts `slot_id` into `responded_signers` and adds weight to `total_weight_rejected`. The later accept call checks `gathered_signatures` (still empty for this slot) and unconditionally adds the same signer's weight to `total_weight_approved`, while `total_weight_rejected` is never decremented.
- Accept → later Reject (same block, same signer): correctly suppressed, because the reject path's guard (`responded_signers.insert`) already contains the slot from the earlier accept, so no extra reject weight is added.

The asymmetry means only the "reject-then-accept" ordering leaks weight into both buckets simultaneously and permanently. This breaks the invariant the coordinator relies on — that `total_weight_approved` and `total_weight_rejected` are mutually exclusive partitions of signer weight for a given block — i.e., the "aggregated-weight vs. verified-accepts" equality is corrupted: the recorded rejected weight for a signer survives even after that signer's real, current state is "accepted."

`SigningCoordinator::wait_for_signatures` in `stacks-node/src/nakamoto_node/signer_coordinator.rs` consumes exactly these two counters to decide the block's fate: [3](#0-2) 
It rejects the block as soon as `total_weight_rejected + weight_threshold > total_weight`, and accepts once `total_weight_approved >= weight_threshold`. Because a signer's weight can remain stuck in `total_weight_rejected` even after that signer has switched to accepting the very same block, a later, unrelated rejection from a different signer can push the *stale* `total_weight_rejected` sum over the 30%-blocking threshold and cause the coordinator to declare the block globally rejected (`NakamotoNodeError::SignersRejected`) even though the true, current rejecting weight is below 30% — because part of the tally is "borrowed" from a signer who has already moved to accept.

### Impact Explanation
This corrupts the "aggregated-weight vs. verified-accepts" equality the coordinator's threshold logic depends on to make an accept/reject determination for a block. A signer's weight ends up simultaneously and permanently represented in both the approve and reject running totals, so neither total is a faithful representation of the *current* set of distinct signer verdicts. This can cause the node to wrongly determine block rejection (or, depending on race/order, wrongly reach the accept threshold sooner than the true distinct approving weight warrants), i.e. a wedge/miscount in the aggregated-weight bookkeeping the block-acceptance decision is built on.

### Likelihood Explanation
A miner does not need to compromise a signer's key or gather a majority. The `docs/signer-flows.md` flow (section 3) documents that a signer's rejection can be re-evaluated on re-proposal (`should_reevaluate_reject_reason`), and separate tests (`stacks-node/src/tests/nakamoto_integrations.rs`, `signers_consider_late_proposals.rs`) confirm signers legitimately transition a *specific* block hash from Rejected to Accepted after a reproposal or timing change. A single miner controlling proposal timing (submit-then-resubmit the same block near a timeout/staleness boundary) can reliably induce at least one honest signer to send Rejected then, later, Accepted for the identical `signer_signature_hash` — exactly the sequence that triggers the double count in `StackerDBListener`.

### Recommendation
Use a single, consistent per-slot "final verdict" bookkeeping structure (or unify the guard) so that transitioning a slot from rejected to accepted (or vice versa) atomically removes/adjusts the previous verdict's weight contribution before adding the new one. Concretely, gate the accepted-path weight addition on the same `responded_signers` set used by the rejected path (or maintain an explicit `HashMap<slot_id, Verdict>` and recompute both totals from it), ensuring `total_weight_approved + total_weight_rejected` can never double-count a single signer's weight.

### Proof of Concept
1. Reward set with signers A (weight 40), B (weight 35), C (weight 25); `weight_threshold` = 70 (per `compute_voting_weight_threshold`).
2. Miner proposes block X. Due to timing, signer A initially rejects X (e.g., `ProposalTooOld`), incrementing `total_weight_rejected` to 40 and inserting A's slot into `responded_signers` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-519`).
3. Miner re-proposes the identical block X (same `signer_signature_hash`); per the documented reject-reevaluation flow, A now legitimately accepts X. The accepted-path check `!block.gathered_signatures.contains_key(&slot_id)` is true for A (A's slot was never added to `gathered_signatures`), so `total_weight_approved` becomes 40 (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:443-446`). `total_weight_rejected` is still 40 (never decremented).
4. Signer B, independently and honestly, rejects X for an unrelated reason, adding 35 to `total_weight_rejected`, making it 75.
5. `SigningCoordinator::wait_for_signatures` sees `total_weight_rejected (75) + weight_threshold (70) > total_weight (100)` and returns `NakamotoNodeError::SignersRejected`, globally rejecting block X — even though the *true* current rejecting weight is only B's 35 (35% < 30%-blocking threshold is actually still ≥30%, so pick numbers where true reject weight alone would not have blocked, e.g. B weight 20): with B=20 the true reject weight is 20 (<30 blocking threshold), yet the stale A=40 contribution pushes the sum to 60, still under 70+... adjust weights so the stale contribution is what tips the sum past the `> total_weight - weight_threshold` line while the genuine current reject weight alone would not have.
