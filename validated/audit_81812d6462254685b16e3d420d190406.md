### Title
Borrow cap is checked against nominal `convertToAssets` value, not actual withdrawable liquidity — a max borrow can leave reserved epoch-end withdraws uncovered - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
`ProgrammableBorrower._borrow` caps the borrow at `availableToBorrow()`, which is computed as `onHand + vault.convertToAssets(shares) - epochPendingWithdraws` (line 350-355). This is the same bug class as the Unstoppable report: the pre-check uses a *nominal/quoted* value, while the actual liquidity freed is produced by `vault.withdraw(shortfall, ...)` (line 452), whose real asset yield can be strictly lower than the `convertToAssets` quote (withdrawal fees, slippage, or quote-vs-redeemable mismatch in the ERC4626 vault). There is no post-borrow check that the remaining vault position still covers `epochPendingWithdraws`, so an honest max borrow can leave the epoch-end reserve undercollateralized — the analog of opening a "max leverage" position that is already over the line once the real swap output lands.

### Finding Description
- `availableToBorrow()` (ProgrammableBorrower.sol:350-355) treats `convertToAssets(shares)` as 1:1 withdrawable underlying and subtracts only `epochPendingWithdraws` as the reserve.
- `_borrow` (lines 435-463) then withdraws `shortfall = assets - onHand` via `vault.withdraw` and sends `assets` to the borrower. ERC4626 `withdraw(assets)` is guaranteed to deliver `assets`, but the shares burned are priced by `previewWithdraw`/`redeem`, which can exceed `convertToShares(assets)` — i.e., the remaining share position's `convertToAssets` value can fall by *more* than `assets` when the vault charges exit fees or its quote overstates redeemable value.
- Result: after `borrow(0)` (full draw), `onHand + convertToAssets(remainingShares) < epochPendingWithdraws` even though the pre-check `assets <= borrowable` passed. At `onStopEpoch` (lines 231-268) IdleCDO pulls `_amountRequired`; the facility cannot cover the reserved pending withdrawals, and the borrower's ledger makes it look like a borrower shortfall, pushing the epoch into the default path even though the borrower is honest and stayed within the enforced cap.
- Analogous pre-check/post-outcome gap also exists in `onStopEpoch` itself (line 245): it only compares `shortfall > _currentVaultAssets()` (a quote) before attempting the withdraw, not the actually-freed amount.

### Impact Explanation
Lenders' pending withdrawal requests are undercollateralized at epoch stop. The honest borrower keeps drawn funds while the epoch is forced into the default/failed-settlement path, so pending withdrawers either cannot be paid at the loss-adjusted price they were promised or the pool records a spurious default loss. Loss magnitude: up to the gap between the `convertToAssets` quote and the vault's real redeemable value on the full reserved amount (e.g., a 1% exit fee on a fully-reserved pool leaves 1% of `epochPendingWithdraws` unpayable).

### Likelihood Explanation
Requires an epoch active (`epochAccountingActive`), nonzero `epochPendingWithdraws`, and a vault whose `withdraw` consumes more economic value than the `convertToAssets` quote implies (fee/slippage ERC4626 vaults are common). The trigger is a fully legitimate max `borrow(0)`/`borrow(borrowable)` by the honest borrower or an authorized executor — no privileged action needed by the attacker; a lender with a pending withdraw request is the victim.

### Recommendation
After the `vault.withdraw` in `_borrow`, verify the post-condition directly: `underlyingToken.balanceOf(address(this)) - assets + _currentVaultAssets() >= epochPendingWithdraws` (i.e., remaining coverage still meets the reserve), and revert otherwise. Alternatively, compute `borrowable` from the vault's real redeemable capacity (`maxRedeem`/`previewRedeem` of the share balance minus fees) rather than `convertToAssets`, and apply the same actual-vs-quoted check in `onStopEpoch` after the withdraw attempt.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Setup: pool with deposits, lender calls requestWithdraw -> epochPendingWithdraws > 0,
// ProgrammableBorrower vault = ERC4626 with withdrawal fee (e.g. 1%) so
// convertToAssets(shares) > actual redeemable value.
cdoEpoch.requestWithdraw(lenderShares, address(aaTranche));
_startEpochAndCheckPrices(0);

uint256 borrowable = programmableBorrower.availableToBorrow();
// borrowable = convertToAssets quote - epochPendingWithdraws

vm.prank(revolvingBorrower);
programmableBorrower.borrow(borrowable); // passes the pre-check

// Assert the reserve is now actually uncovered:
uint256 remaining = underlying.balanceOf(address(programmableBorrower))
    + vault.convertToAssets(vault.balanceOf(address(programmableBorrower)));
assertLt(remaining, programmableBorrower.epochPendingWithdraws());

// stopEpoch -> onStopEpoch cannot free _amountRequired -> default path,
// pending withdrawers' claims unpayable despite a fully-compliant borrower.
```
