### Title
Malicious operator/beneficiary can permanently block `staking_contract` distributions and trap staker's unlockable stake - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::distribute_internal` atomically pays out **all** pending recipients (staker principal + operator/beneficiary commission) from a single shared `distribution_pool` in one loop, using `aptos_account::deposit_coins`. That helper aborts if the recipient has opted out of unregistered direct coin transfers via `aptos_account::set_allow_direct_coin_transfers(false)` and has no `CoinStore<AptosCoin>` registered. Because Move transactions are all-or-nothing, one uncooperative recipient in the loop (typically the operator, who is an unprivileged counterparty chosen by the staker, not someone who already controls the staker's funds) can make `distribute_internal` abort every time it runs. Since `distribute_internal` is invoked from `unlock_stake`, `switch_operator`, `update_commision`, and `distribute`, this permanently blocks the staker from ever unlocking, withdrawing, or reorganizing their `staking_contract`, trapping stake indefinitely. This is the direct Aptos analog of the ERC777-hook griefing pattern in the report: an unprivileged party embedded in a shared payout path can unilaterally and repeatedly revert operations that legitimate, unrelated parties depend on.

### Finding Description
`distribute_internal` extracts withdrawable coins once, then loops over every shareholder in `staking_contract.distribution_pool` and pays each one via `aptos_account::deposit_coins`, all within the same atomic call: [1](#0-0) 

`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient is not registered for the coin type and has disabled direct transfers: [2](#0-1) 

Any account can permissionlessly disable direct-coin-transfer acceptance for itself: [3](#0-2) 

Because Move aborts revert the entire transaction, if the recipient at `recipients[0]` (which per the accounting design can be the operator, the operator's beneficiary, or a previous operator still owed a distribution — see `EDISTRIBUTIONS` design comment about switch_operator) cannot accept the payout, the loop aborts before any other shareholder (including the staker) is paid, and the `coin::extract` already performed on the shared `coins` object is rolled back along with everything else: [4](#0-3) 

`distribute_internal` is invoked as a mandatory prerequisite step from `unlock_stake`, `switch_operator`, and `update_commision` before those functions can proceed, and is also directly callable by anyone via `distribute`: [5](#0-4) [6](#0-5) [7](#0-6) 

The same `aptos_account::deposit_coins`-in-a-loop pattern also exists in `vesting::distribute`, where a shareholder or their configured beneficiary can block distribution to all other shareholders of the same vesting contract in one call: [8](#0-7) 

### Impact Explanation
An operator (an unprivileged counterparty relative to the staker's principal) can permanently prevent the staker from calling `unlock_stake`, `switch_operator`, or `update_commision` on the affected `staking_contract` by never registering their account for `AptosCoin` and calling `set_allow_direct_coin_transfers(false)`. Every future `distribute_internal` call — which is a mandatory step before the staker can reorganize or withdraw — will revert as long as the operator (or its beneficiary) is still owed any commission share in the same `distribution_pool`. This traps the staker's principal and rewards with no code-level recovery path (the staker cannot bypass `distribute_internal`), satisfying "permanent lock or non-recoverable loss of claim rights in stake/commission flows" from the impact gate. The analogous pattern in `vesting::distribute` can strand vested rewards owed to other, cooperative shareholders in a multi-shareholder vesting contract.

### Likelihood Explanation
Both preconditions are fully unprivileged and cheap: (1) never register for `AptosCoin` (default state for a fresh account before any AptosCoin is ever deposited to it through the standard `coin::register`/`CoinStore` path), and (2) call `aptos_account::set_allow_direct_coin_transfers(false)`, a public entry function callable by any signer on their own account with no cost beyond gas. An operator role is commonly assigned to a separate, potentially adversarial address chosen by the staker (e.g. a third-party validator operator), making this a realistic griefing/ransom vector rather than a purely theoretical self-harm scenario.

### Recommendation
Do not let a single recipient's inability/unwillingness to accept a payout block payouts to other, unrelated recipients in the same distribution loop. Options: (a) isolate each recipient's payout in a way that failures don't roll back others' payouts (not straightforward in Move's atomic model, so consider a pull-based claim per recipient instead of push-based batch distribution), or (b) if a recipient's deposit fails, skip them and retain/escrow their share for later claim rather than aborting the whole `distribute_internal` call, so other shareholders/stakers are not blocked. Apply the same fix to `vesting::distribute`.

### Proof of Concept
1. Staker creates a `staking_contract` with `operator` O and some commission percentage via `staking_contract::create_staking_contract`.
2. Before ever receiving `AptosCoin` (so `coin::is_account_registered<AptosCoin>(O) == false`), O calls `aptos_account::set_allow_direct_coin_transfers(false)`.
3. Stake pool earns rewards. Staker calls `staking_contract::unlock_stake(staker, O, amount)`.
4. Inside `unlock_stake`, `distribute_internal` is invoked; it eventually reaches O's commission distribution and calls `aptos_account::deposit_coins(O, ...)`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` because O is unregistered and opted out.
5. The entire `unlock_stake` transaction reverts. This repeats for every future call to `unlock_stake`, `switch_operator`, `update_commision`, and `distribute` on this `staking_contract`, permanently trapping the staker's principal and rewards as long as O keeps this configuration.

**Note on verification limits:** I was unable to fully verify, within the available tool budget, whether `coin::is_account_registered<AptosCoin>` and `coin::deposit<AptosCoin>` are special-cased anywhere by the Fungible-Asset migration logic in `coin.move` in a way that would force-register or bypass this check specifically for `AptosCoin` (as opposed to the `fungible_transfer_only` path used only by `aptos_account::transfer`, which `staking_contract.move`/`vesting.move` do **not** use — they use the generic `deposit_coins`). If `coin.move` transparently auto-registers `AptosCoin` for every account regardless of `DirectTransferConfig`, this specific griefing path would not trigger. I recommend a Devin session with full file access to `aptos-move/framework/aptos-framework/sources/coin.move` to confirm whether `is_account_registered<AptosCoin>` can actually be `false` for a live, funded mainnet account and whether the `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` abort path is truly reachable for `AptosCoin` before treating this as a confirmed critical/high-severity finding.

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
