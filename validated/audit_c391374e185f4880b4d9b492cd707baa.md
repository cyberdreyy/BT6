### Title
Funded instant-withdraw claims never decrement `instantWithdrawClaimsByEpoch`, so default finalization overstates the prefunded reserve and inflates `defaultRecoveryPrice` beyond actual backing - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a heap buffer overflow in `excluded_channels()` — memory is written past the end of the allocated buffer because a trusted count is not reconciled with the actual buffer size. The credit-vault analog is paying/reserving past the funded boundary: `IdleCreditVault` tracks the total instant-withdraw claim basis per epoch in `instantWithdrawClaimsByEpoch`, but the map is only decremented on the defaulted-epoch claim path (`_claimDefaultedInstantWithdrawRequest`). When an instant receipt is claimed normally through `claimInstantWithdrawRequest` → `_transferFundedClaim`, the per-epoch counter is never reduced, so `defaultPendingClaimBasis()` / `_defaultPrefundedInstantReserve()` treat already-paid-out underlying as still-reserved. If a borrower default is later finalized while `pendingInstantWithdraws != 0`, `finalizeDefaultRecovery` counts phantom reserve, computes an inflated `defaultRecoveryPrice`, and pays recovery claims with funds that do not exist — earlier claimants over-claim and later claimants (or the reserve itself) are left short.

### Finding Description
- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (lines ~367-374).
- `claimInstantWithdrawRequest` clears `instantWithdrawsRequests[_user]` and `instantWithdrawsRequestsByEpoch` is untouched, and crucially `instantWithdrawClaimsByEpoch` is never decremented (lines ~380-393). The only place `instantWithdrawClaimsByEpoch` decreases is `_claimDefaultedInstantWithdrawRequest` (line ~853).
- At default finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (lines ~644-649), and `_defaultPrefundedInstantReserve()` adds `instantBasis - pendingInstant` to the reserve without pulling any tokens (lines ~716-723).
- `finalizeDefaultRecovery` then sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (lines ~685-692) — but the prefunded portion corresponding to already-claimed receipts was already transferred out, so the reserve exists only on paper.

The invariant "one receipt one payout" / solvency of `defaultRecoveryReserve` is broken: claims on the reserve are satisfied via `_transferDefaultRecovery` up to a reserve amount that exceeds the strategy's real underlying balance, so the last claimants' transfers revert or earlier claimants receive funds belonging to others.

### Impact Explanation
A user who claimed a funded instant withdrawal earlier in the epoch leaves behind a stale `instantWithdrawClaimsByEpoch` entry. If the borrower then defaults in the same epoch and `pendingInstantWithdraws` is non-zero at finalization, `defaultRecoveryPrice` is scaled up by `staleBasis / totalBasis`. Every defaulted-epoch receipt (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`, post-default requests) is paid at the inflated price until the real underlying runs out; subsequent claims permanently revert (theft-by-dilution / permanent freezing of unclaimed recovery for the remaining claimants). Loss is quantified by the stale basis amount — up to the full current-epoch instant claim volume.

### Likelihood Explanation
Requires: (a) an instant withdrawal requested and successfully claimed while other instant requests remain unfunded (`pendingInstantWithdraws > 0`), and (b) a borrower default finalized in that same epoch. Both are reachable by an unprivileged tranche-token holder exercising the normal instant-withdraw flow; the default trigger is an honest-manager event, consistent with the threat model. No privileged or malicious role is needed, and no existing guard (`_onlyIdleCDO`, `defaultRecoveryFinalized`, KYC) reconciles the stale counter.

### Recommendation
Decrement `instantWithdrawClaimsByEpoch[requestEpoch]` (and `instantWithdrawsRequestsByEpoch`) when a funded instant claim is paid in `claimInstantWithdrawRequest`, so the per-epoch claim basis only reflects receipts that still need funding. Track the request epoch per user (or iterate the user's nonzero epoch entries) so the correct bucket is reduced.

### Proof of Concept
```solidity
// Foundry fork test sketch
function test_InstantClaimInflatesDefaultRecovery() public {
    // Setup: running epoch E on an IdleCreditVault/IdleCDOEpochVariant pair.
    // 1. Alice requests instant withdraw of 100 tokens.
    vm.prank(cdo); vault.requestInstantWithdraw(100e18, alice);
    // 2. Bob requests instant withdraw of 100 tokens; CDO only collects/funds 100.
    vm.prank(cdo); vault.requestInstantWithdraw(100e18, bob);
    vm.prank(cdo); vault.collectInstantWithdrawFunds(100e18); // pendingInstantWithdraws = 100
    // 3. Alice claims her funded 100 (instantWithdrawClaimsByEpoch[E] still = 200).
    vm.prank(cdo); vault.claimInstantWithdrawRequest(alice);
    // 4. Borrower defaults; CDO finalizes with recoveredAmount R.
    //    prefundedReserve = instantWithdrawClaimsByEpoch[E] - pendingInstant = 100
    //    but Alice's 100 already left the contract -> reserve overstated by 100.
    // 5. defaultRecoveryPrice = (R + 100 + dust) / totalBasis > true backing.
    // 6. Bob's defaulted claim pays claimBasis * inflatedPrice; assert strategy
    //    underlying balance goes to zero before all claims -> later claim reverts.
}
```
The assertion: `vault.instantWithdrawClaimsByEpoch(epoch)` remains `200` after step 3 while real backing is only `100`, and post-finalization `defaultRecoveryPrice * defaultedBasis / 1e18` exceeds `underlyingToken.balanceOf(vault)`.
