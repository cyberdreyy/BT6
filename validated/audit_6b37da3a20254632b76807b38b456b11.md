### Title
Cross-user callback hijacking via attacker-chosen `MessageId` in `HandleLegacyUserMessage` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores the caller's callback in `h.savedCallbacks[msg.Body.MessageId]` without checking whether that key is already in use, and `msg.Body.MessageId` is fully attacker-controlled (it is the raw JSON-RPC request `ID` sent by the client). A second signed request using the same `MessageId` as a victim's in-flight request overwrites the stored callback, so the DON's later trigger response for that `MessageId` is delivered to the attacker's HTTP connection instead of the victim's.

### Finding Description
`ProcessRequest` in `core/services/gateway/gateway.go` decodes the incoming JSON-RPC request and, for legacy requests, sets `msg.Body.MessageId` from `jsonRequest.ID` (only length-bounded to 200 chars) before calling `msg.Validate()` and `h.HandleLegacyUserMessage(ctx, msg, callback)`. [1](#0-0) 

`api.Message.Validate()` only checks length/format/null-suffix constraints on `MessageId` and validates the signature over the message body — it does not verify that `MessageId` is unique or otherwise tied to the sender in a way that prevents reuse of another sender's chosen ID. [2](#0-1) 

In `handler.HandleLegacyUserMessage`, after passing validation, the handler unconditionally stores (overwrites) the local callback under the attacker-controlled key:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [3](#0-2) 

There is no existence check (`if _, exists := h.savedCallbacks[id]; exists { reject }`) before the map write, so an attacker who submits a second, independently-signed message with `MessageId` identical to a victim's still-pending request simply replaces the victim's `savedCallback` entry with their own.

When the DON node later responds with `MethodWebAPITrigger` for that `MessageId`, `handleWebAPITriggerMessage` looks up and deletes `h.savedCallbacks[msg.Body.MessageId]` and sends the response through whichever `Callback` is currently stored:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [4](#0-3) 

Because the callback was overwritten by the attacker's request, the victim's trigger response (which may contain the victim's HTTP response body/headers/data returned from the external endpoint) is delivered to the attacker's connection, and the victim's original HTTP request to the gateway hangs/times out.

Exploit flow:
1. Victim sends a validly signed `web_api_trigger` legacy message with `MessageId = "X"` — gateway stores `victimCallback` under key `"X"` and forwards the request to all DON members.
2. Before the DON responds, attacker (any address capable of self-signing a message — `Message.Sign`/`SignKS` require only an EOA private key, not any special role) sends their own validly signed message reusing `MessageId = "X"`. `Validate()` passes because it only checks format/signature-self-consistency, not ID uniqueness.
3. `HandleLegacyUserMessage` overwrites `h.savedCallbacks["X"]` with the attacker's callback.
4. When the DON's response for `"X"` arrives, `handleWebAPITriggerMessage` sends it to the attacker's `Callback`, not the victim's.

No allowlist or rate limiting currently guards this path — the code even has a `// TODO: apply allowlist and rate-limiting here` comment right before request dispatch, confirming no additional gating exists at this stage. [5](#0-4) 

### Impact Explanation
This is a cross-user response/data confusion vulnerability: an unprivileged, unauthenticated attacker (any address able to self-sign a gateway message) can hijack another user's pending trigger callback and receive data intended for the victim (the HTTP response payload retrieved by the DON on the victim's behalf), while simultaneously causing a denial of service for the victim (their request never completes and eventually times out). This matches the "request impersonation / cross-user response confusion / unauthorized access to another user's job data" bounty impact class.

### Likelihood Explanation
Exploitability requires only: (a) generating an EOA keypair and signing a well-formed `api.Message` (trivial, no special permission), and (b) guessing or learning the victim's `MessageId` (which is client-supplied and often predictable/sequential/attacker-observable depending on client implementation) and winning a race to submit before the DON's trigger response returns. There is no server-side uniqueness enforcement, so the race window is the only limiting factor — this is a purely single-node, network/API-level race rather than requiring privileged access, DON collusion, or misconfiguration.

### Recommendation
In `HandleLegacyUserMessage`, reject the request (or generate a gateway-side unique key) if `msg.Body.MessageId` already exists in `h.savedCallbacks`, e.g.:
```go
h.mu.Lock()
if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists {
    h.mu.Unlock()
    return callback.SendResponse(handlers.UserCallbackPayload{... duplicate message ID error ...})
}
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}
h.mu.Unlock()
```
Additionally consider keying `savedCallbacks` by a gateway-generated identifier (e.g., `sender+MessageId` or a server-side UUID) rather than trusting the raw client-supplied `MessageId` alone, to eliminate any possibility of cross-sender collisions.

### Proof of Concept
Handler-level integration test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct `handler` with a mock `handlers.DON` (`don.SendToNode` no-op returning nil) and two mock `handlers.Callback` instances: `victimCallback`, `attackerCallback` (mocked `SendResponse`).
2. Build `victimMsg` with `Body.MessageId = "dup-id"`, `Method: MethodWebAPITrigger`, valid `Timestamp`, signed with victim's key; call `h.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`. Assert `h.savedCallbacks["dup-id"].Callback == victimCallback`.
3. Build `attackerMsg` with the same `Body.MessageId = "dup-id"`, signed with a different attacker key; call `h.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)`.
4. Assert `h.savedCallbacks["dup-id"].Callback == attackerCallback` (i.e., victim's callback was overwritten) — this demonstrates the bug (test should currently fail to assert `victimCallback` is preserved, or explicitly assert the overwrite occurs).
5. Simulate DON response: call `h.HandleNodeMessage(ctx, respWithMessageId("dup-id"), nodeAddr)` and assert `attackerCallback.SendResponse` was invoked (not `victimCallback.SendResponse`), proving the victim's response was misdelivered to the attacker.
6. After the fix, step 3 should instead cause `HandleLegacyUserMessage` to return a duplicate-ID error via `attackerCallback.SendResponse`, and `h.savedCallbacks["dup-id"].Callback` should remain `victimCallback`.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
