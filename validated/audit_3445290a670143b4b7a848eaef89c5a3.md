### Title
Signer `BlockRejection` signature does not authenticate `reason_code`/`response_data.reject_reason`, allowing a MITM-free but pubkey-recovery-abusable reason substitution - (File: libsigner/src/v0/messages.rs)

### Summary
`BlockRejection::hash()` builds the SIP-018 structured-data digest over only `self.signer_signature_hash` (the block hash being rejected) and `chain_id`; it never includes `reason_code` or `response_data.reject_reason`. `sign()`/`verify()`/`recover_public_key()` all operate over this same narrow digest. Because the StackerDB chunk layer (`StackerDBChunkData::sign`) commits only to slot_id/slot_version/data-hash of the *whole serialized chunk*, and the chunk carries the entire `BlockRejection` struct, the *chunk* signature does bind the full byte content while it is in flight over StackerDB. However, once a signer or the node's `StackerDBListener` extracts the `BlockRejection` payload and re-derives authenticity purely via `BlockRejection::recover_public_key()` (as the consuming logic does, e.g. `handle_block_rejection` at signer.rs:2220 and the node's `rejected_data.recover_public_key()` at stackerdb_listener.rs:501), the *content-level* signature that is being trusted for that step never actually covers `reason_code`/`response_data`. Any code path that re-serializes/re-signs, forwards, or persists a `BlockRejection` independent of its original StackerDB chunk (e.g. `add_pending_block_rejection_response`, replay of pending rejections, or any relay/coordinator logic that re-verifies just the embedded `BlockRejection.signature`) will accept a tampered `reason_code`/`reject_reason` as validly signed by the original signer, because `verify()` only checks the untouched `signer_signature_hash`.

### Finding Description
`BlockRejection::hash()`:
```

    let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
    let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
    structured_data_message_hash(data, domain_tuple)
}
``` [2](#0-1) 

This is the *only* thing `sign()` (1809-1814), `verify()` (1816-1825), and `recover_public_key()` (1827-1837) operate on. The rest of the struct — `reason`, `reason_code: RejectCode`, `chain_id`, `metadata`, and critically `response_data: BlockResponseData` (which carries `reject_reason: RejectReason`, `failed_txid`, tenure-extend timestamps) — is unauthenticated at the `BlockRejection` level.

`response_data.reject_reason` is exactly the field that downstream logic keys off of for security-relevant decisions:
- `store_and_process_block_rejection` passes `(&rejection.response_data.reject_reason).into()` as the "reject_code" used to decide global rejection and to flag a miner invalid for a disallowed reorg (`RejectReasonPrefix::ReorgNotAllowed`) — see `stacks-signer/src/v0/signer.rs` 2263, 2354-2367 [3](#0-2) [4](#0-3) 
- The node's `StackerDBListener` also inspects `rejected_data.reason_code`/`response_data.failed_txid` to update `failed_txids`/problematic-tx weight tallies used to decide miner behavior [5](#0-4) 

Because none of that payload is bound into the cryptographic digest that `verify()`/`recover_public_key()` checks, any consumer that authenticates a `BlockRejection` purely by calling `recover_public_key()`/`verify()` on the struct (rather than re-verifying the original StackerDB chunk signature over the full serialized bytes) is authenticating only "signer X rejected block H", not "signer X rejected block H for reason R". A rejection with reason `ConnectivityIssues` can be relabeled `ReorgNotAllowed` (or any other reason) and will still `recover_public_key()` to the original signer and pass `verify()`, because the digest is identical regardless of `reason_code`/`response_data`.

This is the direct analog of CardGate's flaw: the IPN endpoint validated a signature but the signature did not actually bind the security-critical fields (merchant ID/secret) that were then trusted, letting an attacker replay a validly-signed envelope with substituted critical content. Here, the `BlockRejection` signature validates origin ("this pubkey signed something about hash H") but not the content that state-machine logic treats as authoritative ("this pubkey rejected H *for this specific reason*").

### Impact Explanation
This breaks the "rejection recounted as an acceptance/altered-verdict" equality class named in the rules: a rejection whose *reason* has been substituted still verifies as validly signed by the original signer, so any logic keyed on `reason_code`/`reject_reason` (miner-invalidation-on-reorg logic, `failed_txid` accounting, or any future logic gating signature counting by reason) can be fed an attacker-crafted reason while still passing signer-authenticity checks. In the current code, the only path that stores rejections (`handle_block_rejection`/`store_and_process_block_rejection`) reads `rejection.response_data.reject_reason` — obtained straight from the (unauthenticated-for-content) struct — to decide whether to mark the current miner invalid for an unauthorized reorg (`RejectReasonPrefix::ReorgNotAllowed`). An attacker who can produce/relay a `BlockRejection` object with the original signature intact but a swapped `reason_code`/`response_data.reject_reason` (e.g., by re-embedding a legitimately-observed `BlockRejection` payload with a modified reason field into a new StackerDB chunk they control the slot signature for, or via any relay path that reconstructs the struct from parts) can cause other signers to incorrectly mark a valid miner invalid, or suppress the ReorgNotAllowed miner-invalidation signal that would otherwise protect the chain — a liveness/safety wedge on the miner-status equality.

### Likelihood Explanation
Exploitation requires an attacker (or malicious/compromised signer) able to independently construct or modify a `BlockRejection` value and route it through logic that authenticates it via `BlockRejection::verify()`/`recover_public_key()` alone rather than through the outer StackerDB chunk signature (which does bind the full bytes). The current in-repo consumer, `handle_block_rejection`, is fed messages that arrived via the StackerDB chunk path, so today the outer chunk signature happens to cover the tampered content too — this narrows practical exploitability to any code path (existing tests already construct `BlockRejection`s directly and re-sign only the narrow digest, e.g. `BlockRejection::new`) that trusts `BlockRejection.signature` in isolation, such as inter-process forwarding, pending-response replay, or future relay/coordinator code that revalidates a detached `BlockRejection`. Given the domain-separated hash is a clear, isolated design choice (mirrors the equally narrow `MockSignature`/`hash()` pattern seen elsewhere in the file), this is a structural weakness rather than a hypothetical one, but does not currently have a fully wired one-slot-miner-triggerable exploit path visible in the reviewed code — it is a latent authentication gap rather than a confirmed exploitable equivocation today.

### Recommendation
Include `reason_code` and the full `response_data` (or at minimum `response_data.reject_reason`) in the `BlockRejection::hash()` domain-separated digest, so that `sign()`/`verify()`/`recover_public_key()` authenticate the entire security-relevant payload, not just the rejected block hash. Apply the same audit to `BlockAccepted`/`MockSignature`/any other message type whose `hash()` excludes fields later trusted by consumers.

### Proof of Concept
1. Take a legitimately observed `BlockRejection` `R1` from signer S with `reason_code = ConnectivityIssues`, `response_data.reject_reason = RejectReason::ConnectivityIssues(..)`.
2. Construct `R2` = `R1` with `reason_code`/`response_data.reject_reason` replaced by `RejectReason::ReorgNotAllowed`, keeping `signer_signature_hash`, `chain_id`, and `signature` unchanged.
3. Call `R2.verify(&S_pubkey)` / `R2.recover_public_key()` — both succeed and return `S`'s pubkey, identical to `R1`, because `hash()` only covers `signer_signature_hash`+`chain_id`.
4. Feed `R2` into any consumer that authenticates via `BlockRejection::recover_public_key()` alone (e.g., a hypothetical relay, or `signer_db.insert_state_machine_update`/pending-rejection replay path) — it is accepted as "signer S rejected block H due to ReorgNotAllowed" even though S never signed that specific claim, potentially triggering `sortition_state.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock` in `store_and_process_block_rejection`.

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
