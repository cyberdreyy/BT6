### Title
`send_token_v2` Deposits Permanently Lock Tokens When EVM Contract Is Still V1 — (`File: crates/sui-framework/packages/bridge/sources/bridge.move`)

---

### Summary

`bridge::send_token_v2` is a public, permissionless function on Sui that burns the caller's tokens and records a V2 bridge message (72-byte payload, `message_version = 2`). The EVM V1 contract (`SuiBridge.sol`) can only process V1 messages (64-byte payload). It has no `transferBridgedTokensWithSignaturesV2` function and its `decodeTokenTransferPayload` hard-reverts on any payload that is not exactly 64 bytes. There is no guard on the Sui side that prevents `send_token_v2` from being called while the EVM contract is still V1. The result is an exact structural analog to the Starknet bug: the deposit side accepts an option that makes the corresponding withdrawal permanently impossible, locking the user's tokens forever.

---

### Finding Description

**Deposit side — no version guard (`bridge.move`)**

`send_token_v2` is `public fun`, callable by any ordinary SUI holder:

```move
public fun send_token_v2<T>(
    bridge: &mut Bridge,
    target_chain: u8,
    target_address: vector<u8>,
    token: Coin<T>,
    clock: &Clock,
    ctx: &mut TxContext,
) {
    ...
    let message = message::create_token_bridge_message_v2(   // version = 2, payload = 72 bytes
        inner.chain_id, bridge_seq_num, ..., clock.timestamp_ms(),
    );
    inner.send_token_internal(target_chain, token, message); // burns token, stores record
    ...
}
``` [1](#0-0) 

`send_token_internal` immediately burns the coin and stores the pending record. There is no check that the destination EVM contract supports V2 messages. [2](#0-1) 

**V2 message format — 72-byte payload**

`create_token_bridge_message_v2` appends an 8-byte timestamp to the standard 64-byte V1 payload, producing a 72-byte payload with `message_version = 2`: [3](#0-2) 

**EVM V1 withdrawal side — hard revert on 72-byte payload**

`SuiBridge.transferBridgedTokensWithSignatures` calls `BridgeUtils.decodeTokenTransferPayload`, which unconditionally reverts if the payload is not exactly 64 bytes:

```solidity
require(_payload.length == 64, "BridgeUtils: TokenTransferPayload must be 64 bytes");
``` [4](#0-3) 

`transferBridgedTokensWithSignaturesV2` only exists in `SuiBridgeV2`, not in the V1 `SuiBridge`: [5](#0-4) 

**E2E test explicitly confirms the lock**

The repository's own integration test documents the exact failure path:

```
// Now try to claim on EVM using V2 function - this should fail because EVM is still on V1
// The V1 EVM contract doesn't have transferBridgedTokensWithSignaturesV2,
// so calling it will fail.
assert!(result.is_err(), "V2 claim on V1 EVM contract should fail, but succeeded");
``` [6](#0-5) 

The test confirms: V2 deposit on Sui succeeds (tokens burned), V2 claim on V1 EVM fails. The test treats this as "expected" but provides no recovery path for the user's burned tokens.

---

### Impact Explanation

Tokens burned by `send_token_v2` while the EVM contract is V1 are permanently lost:

- They cannot be claimed via `transferBridgedTokensWithSignatures` (V1) — payload length check reverts.
- They cannot be claimed via `transferBridgedTokensWithSignaturesV2` — function does not exist on V1.
- There is no refund or unlock mechanism on the Sui side once `send_token_internal` burns the coin.

This is a **permanent fund lock**, matching the High/Medium impact class in the bounty scope.

---

### Likelihood Explanation

`send_token_v2` is a `public fun` in the published API (`0xb::bridge`), callable by any SUI holder with no special permissions. The bridge CLI already routes users to `send_token_v2` when `BridgeVersion::V2` is selected: [7](#0-6) 

Any user who calls `send_token_v2` (directly or via the CLI with `--version v2`) while the EVM proxy still points to the V1 implementation will permanently lose their tokens. The upgrade window between Sui-side V2 deployment and EVM-side V2 upgrade is the exact exposure window.

---

### Recommendation

Add a version guard on the Sui deposit side. `send_token_v2` should assert that the bridge's stored `message_version` (field `inner.message_version` in `BridgeInner`) is at least 2 before accepting a V2 deposit. Alternatively, `send_token_v2` should be gated behind a protocol-config flag that is only enabled after the EVM upgrade is confirmed on-chain. This mirrors the correct fix for the Starknet analog: reject the deposit if the option is not yet supported on the withdrawal side. [8](#0-7) 

---

### Proof of Concept

1. EVM proxy is still pointing to `SuiBridge` (V1 implementation).
2. User calls `bridge::send_token_v2<ETH>(bridge, eth_chain_id, eth_address, coin, clock, ctx)` on Sui.
3. Transaction succeeds: coin is burned, `TokenDepositedEventV2` is emitted, `BridgeRecord` stored with a 72-byte V2 message.
4. Bridge authorities sign the V2 message and call `transferBridgedTokensWithSignatures(signatures, message)` on EVM V1.
5. EVM reverts: `"BridgeUtils: TokenTransferPayload must be 64 bytes"` — because the V2 payload is 72 bytes.
6. Calling `transferBridgedTokensWithSignaturesV2` also fails — the function selector does not exist on the V1 proxy.
7. User's tokens are permanently locked: burned on Sui, unclaimable on EVM.

The repository's own e2e test at `crates/sui-bridge/src/e2e_tests/complex.rs` lines 238–270 reproduces steps 2–6 exactly and asserts the failure. [9](#0-8)

public fun create_token_bridge_message_v2(
    source_chain: u8,
    seq_num: u64,
    sender_address: vector<u8>,
    target_chain: u8,
    target_address: vector<u8>,
    token_type: u8,
    amount: u64,
    timestamp: u64,
): BridgeMessage {
    chain_ids::assert_valid_chain_id(source_chain);
    chain_ids::assert_valid_chain_id(target_chain);

    let mut payload = vector[];

    // sender address should be less than 255 bytes so can fit into u8
    payload.push_back((vector::length(&sender_address) as u8));
    payload.append(sender_address);
    payload.push_back(target_chain);
    // target address should be less than 255 bytes so can fit into u8
    payload.push_back((vector::length(&target_address) as u8));
    payload.append(target_address);
    payload.push_back(token_type);
    // bcs serialzies u64 as 8 bytes
    payload.append(reverse_bytes(bcs::to_bytes(&amount)));
    payload.append(reverse_bytes(bcs::to_bytes(&timestamp)));

    assert!(vector::length(&payload) == 72, EInvalidPayloadLength);

    BridgeMessage {
        message_type: message_types::token(),
        message_version: TOKEN_TRANSFER_MESSAGE_VERSION_V2,
        seq_num,
        source_chain,
        payload,
    }
}
