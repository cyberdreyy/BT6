## Title
`getLargestAccounts` cache does not track requested commitment level, allowing wrong-slot/stale data to be returned - (File: rpc/src/rpc_cache.rs, rpc/src/rpc.rs)

### Summary
`LargestAccountsCache` caches `getLargestAccounts` results keyed only by the `filter` (`Circulating`/`NonCirculating`/`None`), but the RPC's `commitment` parameter — which selects a completely different `Bank` (and thus a different slot/fork state) — is not part of the cache key at all. This mirrors the `NestedFactory` bug class: a stale/incompletely-tracked cache is consulted by a hot-path read function without verifying that the parameters that determine correctness (here, the commitment/slot) still match what was cached.

### Finding Description

The cache itself, `LargestAccountsCache` in `rpc/src/rpc_cache.rs`, stores entries in a `HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>` — the map key is only the filter, with a TTL (`duration`) but no notion of commitment level or bank slot correctness: [3](#0-2) 

The bank resolved via `self.bank(config.commitment)` at line 1072 is fetched (potentially expensively, and correctly reflecting the caller's requested commitment), but then discarded in favor of whatever was last cached under that filter — regardless of which commitment level produced that cached entry. `self.bank()` itself resolves completely different banks (and slots) depending on commitment: [4](#0-3) 

So a request with `commitment: "finalized"` can populate the cache with a `finalized`-slot result. A subsequent request with `commitment: "processed"` (or `"confirmed"`) using the same `filter`, arriving within the cache TTL, will hit the cache and be served the finalized-bank's data/slot, mislabeled with the semantics implied by "processed" commitment — i.e., data that is stale/from the wrong fork relative to what the caller asked for. The reverse is also true: a `"processed"` bank's result (from a potentially non-canonical, since-rolled-back fork) can be served later to a `"finalized"` request within the TTL window, returning non-finalized data as if it were finalized.

### Impact Explanation
This causes an unprivileged JSON-RPC caller to receive **wrong-slot/fork data** for a single, ordinary `getLargestAccounts` call — the response's `context.slot` and account balances can reflect a different commitment level/fork than what was explicitly requested in `RpcLargestAccountsConfig.commitment`. This falls squarely in the "wrong-slot/fork/account data returned" impact bucket for a single low-rate JSON-RPC call, analogous to the NestedFactory bug where a stale cache (not tracking a relevant dimension of state — there "removed" operators, here "commitment level") was consulted by hot-path logic (`create()`/`swapTokenForTokens()` there, `get_largest_accounts` here) without verifying the cache actually reflects the currently-requested state.

### Likelihood Explanation
Any client issuing two consecutive `getLargestAccounts` calls with different `commitment` values (e.g., first `finalized`, then `processed`) using the same `filter` parameter, within the cache's TTL window, will observe the mismatch. This requires no privileged access, no multiple clients, and is well within the "no more than one call per `CLUSTER_SLOT_TIME_TARGET / 2`" bound described in scope, since the second call can be a normal, single low-rate request.

### Recommendation
Include the effective commitment level (or the resolved bank's slot together with commitment) in the `LargestAccountsCache` key, e.g. `HashMap<(Option<RpcLargestAccountsFilter>, CommitmentLevel), LargestAccountsCacheValue>`, so that cached results are only reused for requests at the same commitment level, and invalidate/bypass the cache entry if the resolved bank's slot is behind the cache's stored slot for that commitment.

### Proof of Concept
1. Call `getLargestAccounts` with `{"filter": "circulating", "commitment": "finalized"}`. This populates `LargestAccountsCache` under key `Some(Circulating)` with the finalized bank's slot/results (see `set_cached_largest_accounts` call at `rpc/src/rpc.rs` line 1116).
2. Immediately (within the cache `duration`, default TTL window) call `getLargestAccounts` with `{"filter": "circulating", "commitment": "processed"}`.
3. Because `get_cached_largest_accounts` only looks up by `filter` (`rpc/src/rpc.rs` lines 1049-1055, `rpc_cache.rs` lines 30-42), the second call returns the exact same cached `(slot, accounts)` from step 1 — the finalized bank's data — despite the caller asking for the `processed` (most recent, potentially different-fork) view. The returned `context.slot` in the response corresponds to the finalized bank, not the processed one, demonstrating wrong-slot data returned to a single low-rate RPC call.

#[derive(Debug, Clone)]
pub struct LargestAccountsCache {
    duration: u64,
    cache: HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>,
}

#[derive(Debug, Clone)]
struct LargestAccountsCacheValue {
    accounts: Vec<RpcAccountBalance>,
    slot: u64,
    cached_time: SystemTime,
}

impl LargestAccountsCache {
    pub(crate) fn new(duration: u64) -> Self {
        Self {
            duration,
            cache: HashMap::new(),
        }
    }

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }

    pub(crate) fn set_largest_accounts(
        &mut self,
        filter: &Option<RpcLargestAccountsFilter>,
        slot: u64,
        accounts: &[RpcAccountBalance],
    ) {
        self.cache.insert(
            filter.clone(),
            LargestAccountsCacheValue {
                accounts: accounts.to_owned(),
                slot,
                cached_time: SystemTime::now(),
            },
        );
    }
