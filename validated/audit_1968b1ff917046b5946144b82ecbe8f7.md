### Title
Loss-adjusted withdraw haircut is written to the post-bump `epochNumber`, so loss-bearing receipts are paid at par and drain the vault - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is incremented inside `deposit()` while the epoch is still running — i.e., during the same `stopEpoch` flow — so the haircut is keyed to the *new* epoch while every pending receipt is indexed by the *request* epoch via `lastWithdrawRequest`. The claim path therefore looks up an empty frame (`lossRecoveryPriceByEpoch[lastWithdrawRequest] == 0`), the loss-adjusted branch is skipped, and the receipt falls through to the fully-funded claim path, paying the pre-haircut basis from a strategy that only received the reduced amount — a direct analog of `RPCParseCommandLine` reaching the execute branch on an empty argument frame.

### Finding Description
- Receipts are recorded per request epoch: `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `lastWithdrawRequest[_user] = currentEpoch` (`requestWithdraw`, lines 282–293).
- `epochNumber` is bumped inside `deposit()` whenever `isEpochRunning()` is still true, which the code comments explicitly describe as the `stopEpoch` deposit: lines 607–610.
- On a lossy stop, `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (line 421) and zeroes `pendingWithdraws`, but pulls only the reduced `_amount` of underlying (lines 411–429).
- `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 790–792). Because the price was stored under `epochNumber = requestEpoch + 1` while `lastWithdrawRequest = requestEpoch`, the lookup returns 0 and the loss-adjusted branch returns 0.
- Execution then reaches `_claimFundedWithdrawRequest`, whose epoch gate `epochNumber <= lastWithdrawRequest[_user]` now passes (the bump already happened), and which pays `withdrawsRequests[_user]` — the full pre-loss basis — via `_transferFundedClaim` (lines 319–349).
- Symmetrically, the re-request guard in `requestWithdraw` (lines 261–271) checks `lossRecoveryPriceByEpoch[lastWithdrawRequest]`, which is always 0, so users can freely stack new requests after a lossy stop without being forced to claim the haircutted receipt first.

### Impact Explanation
Broken invariant: loss waterfall / one receipt one payout. The strategy is funded with only `pendingBasis * lossRecoveryPrice / 1e18` underlying but honors receipts at `pendingBasis` par value. The first claimer(s) extract more underlying than was funded; once the strategy balance is exhausted, later receipt holders' claims revert (`safeTransfer` on an empty balance), so part of the pending-receipt queue is permanently unpaid. Concretely, with pendingWithdraws = 1,000,000 USDC and a 20% loss (`_amount = 800,000`), claimants are owed 1,000,000 at par: the first 800,000 of claims succeed, the remaining 200,000 of receipt holders can never claim — a 20% insolvency borne by the tail of the queue, exactly the loss that was supposed to be socialized pro-rata across all receipts. An unprivileged lender holding receipts can also deliberately claim first to shift the entire haircut onto other claimants.

### Likelihood Explanation
- Requires only a lossy `stopEpochWithDuration` (`_amount < pendingBasis`) — an honest manager/borrower action — plus at least one pending withdraw request from any lender. No malicious privileged role is needed.
- The trigger ordering (deposit inside stopEpoch increments `epochNumber` before `collectWithdrawFunds` runs) is the documented behavior at lines 607–610 and is exercised every epoch; the only precondition is a non-zero loss with pending receipts.
- No existing guard stops it: the `lossRecoveryPrice != 0` checks all key off `lastWithdrawRequest` (lines 262, 791), which never matches the epoch the price was stored under, and `collectWithdrawFunds` has already set `pendingWithdraws = 0`, so no residual accounting trips.

### Recommendation
- Store the haircut under the epoch that owns the receipts: either write `lossRecoveryPriceByEpoch[epochNumber - 1]` (or the request epoch tracked explicitly) in `collectWithdrawFunds`, or move the `epochNumber` increment so it occurs strictly after loss funding, or key the claim lookup off `epochNumber` at claim time consistently with the write. The write and the read must use the same epoch domain.
- Additionally, have `_claimFundedWithdrawRequest` verify that the user's request epoch has no entry in `lossRecoveryPriceByEpoch` before paying at par, as a defense-in-depth check.
- Add a Foundry test covering: request in epoch N → lossy `stopEpochWithDuration` → assert `lossRecoveryPriceByEpoch[N]` is set and `claimWithdrawRequest` pays `amount * price / 1e18`, not `amount`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "contracts/strategies/idle/IdleCreditVault.sol";
// assume helpers deploy vault + IdleCDOEpochVariant harness + ERC20 underlying

contract LossEpochMismatchPoC is Test {
    // users: alice, bob each request 500k USDC withdraw in epoch N
    // epoch N ends with a lossy stopEpochWithDuration: collectWithdrawFunds(800k) for pendingBasis 1M
    function test_ReceiptsPaidAtParAfterLossyStop() public {
        // --- epoch N running ---
        // alice and bob deposit 1M total through the CDO, then requestWithdraw(500k each)
        // lastWithdrawRequest[alice] = lastWithdrawRequest[bob] = N
        // withdrawsRequestsByEpoch[*][N] = 500k; pendingWithdraws = 1M

        // --- stopEpoch: borrower repays TVL - loss; CDO calls strategy.deposit(...)
        // while isEpochRunning() == true  -> epochNumber becomes N+1  (line 610)
        // then IdleCDO calls collectWithdrawFunds(800_000e6):
        //   lossRecoveryPriceByEpoch[N+1] = 0.8e18   // line 421: keyed on NEW epoch
        //   pendingWithdraws = 0                     // line 420

        // --- alice claims ---
        // _claimLossAdjustedWithdrawRequest reads lossRecoveryPriceByEpoch[N] == 0 -> skips
        // _claimFundedWithdrawRequest: epochNumber(N+1) > lastWithdrawRequest(N) -> pays 500k at par
        vm.prank(cdo);
        uint256 got = vault.claimWithdrawRequest(alice);
        assertEq(got, 500_000e6);            // expected payout: 500k * 0.8 = 400k
        // strategy now holds 300k for bob's 500k receipt

        // --- bob can never claim the remaining funded loss ---
        vm.prank(cdo);
        vm.expectRevert();                   // ERC20: transfer amount exceeds balance
        vault.claimWithdrawRequest(bob);
    }
}
```

The critical asymmetry to assert directly: after the lossy stop, `vault.lossRecoveryPriceByEpoch(N)` returns `0` while `vault.lossRecoveryPriceByEpoch(N+1)` returns `0.8e18`, proving the haircut was recorded under a frame that contains no receipts — the empty-frame execution analog.
