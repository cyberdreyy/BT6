### Title
Historical `getBlock`/`getTransaction` (jsonParsed) permanently misreports account `writable` status for reserved keys, ignoring the slot's actual per-slot reserved-key/feature-activation state - (File: `transaction-status/src/lib.rs`, `transaction-status/src/parse_accounts.rs`)

### Summary
`EncodableWithMeta::encode_with_meta` for `v0::Message` and the `VersionedTransactionWithStatusMeta::build_json_accounts` path always build the `LoadedMessage` used for `jsonParsed` account-writability calculation with `ReservedAccountKeys::new_all_activated()`, not with the bank's actual `feature_set`/`get_reserved_account_keys()` at the transaction's slot. Because `RESERVED_ACCOUNTS` only grows and is a process-global static list, any account key that becomes reserved via a later feature activation will retroactively be reported as `writable: false` in `jsonParsed` output for historical blocks/transactions where it was, in fact, treated as writable by the runtime at execution time.

### Finding Description
`transaction-status/src/lib.rs` implements `EncodableWithMeta for v0::Message::encode_with_meta`: [1](#0-0) 
which unconditionally calls `ReservedAccountKeys::new_all_activated()` and feeds `.active` (the set of *every* reserved key defined in the codebase, active or not) into `LoadedMessage::new_borrowed`. The same pattern appears in `VersionedTransactionWithStatusMeta::build_json_accounts`: [2](#0-1) 
and in `transaction-status/src/parse_accounts.rs::parse_v0_message_accounts`, which derives `writable` purely from `message.is_writable(i)` on that `LoadedMessage`: [3](#0-2) 

Contrast this with `ReservedAccountKeys::new_all_activated()`'s own doc comment: "This is not to be used by the runtime," and with the actual runtime path in `runtime/src/bank.rs`, which maintains a per-bank `reserved_account_keys` that is updated incrementally as features activate at epoch boundaries via `update_active_set(&self.feature_set)`: [4](#0-3)  and used for the actual write-lock/consensus check in `check_reserved_keys`: [5](#0-4) 

`ReservedAccountKeys::update_active_set` only ever moves a key from `inactive` to `active` once its feature id is active; it can never move a key from active back to inactive: [6](#0-5) 
Combined with `RESERVED_ACCOUNTS` being a static list that historically only grows (comment: "Reserved accounts cannot be removed from this list without breaking consensus"): [7](#0-6) 
`ReservedAccountKeys::new_all_activated()` at any point in time is a superset of what was actually active at any earlier slot.

Exploit/observation flow:
1. Before a feature-gated reserved-account entry (e.g. a future sysvar/program id with a `feature_id` in `RESERVED_ACCOUNTS`) is activated, a legitimate transaction lands in a block that legally write-locks that pubkey (the runtime at that slot did not consider it reserved, since the feature wasn't active, so `bank.check_reserved_keys` and SVM lock resolution treated it as writable and `meta.loaded_addresses.writable`/static writable index correctly recorded it as writable).
2. After the feature activates (which, for any historically finalized block, is guaranteed to eventually be true once the feature has been shipped and activated, i.e., essentially "always" for old blocks queried today), an unprivileged client issues a single `getBlock`/`getTransaction` call with `encoding: "jsonParsed"` for that historical slot.
3. `encode_with_meta`/`build_json_accounts` computes `ReservedAccountKeys::new_all_activated()`, which unconditionally includes this key as reserved regardless of the transaction's slot, and `parse_v0_message_accounts` reports `writable: false` for that account — even though the account really was write-locked, executed as writable, and its state actually mutated at that slot.
4. No commitment/param/subscription guard intervenes: the encoding path has no per-slot feature-set awareness at all; it is not a rate-limit or authorization issue but a straightforward logic bug in reproducing execution-time state.

This differs from the literal framing in the question (which posited a `true`-when-should-be-`false` direction); the actual and provable direction of the bug is the reverse: `jsonParsed` will under-report writability (`false`) for slots where the account was truly writable, because the "all activated" reserved set is time-invariant and always reflects the *latest* code's reserved-key list, not the queried slot's actual protocol state.

### Impact Explanation
This is a wrong-data-returned / consensus-state-misreporting bug scoped to RPC's `jsonParsed` account metadata (`ParsedAccount.writable`). It causes a single, low-rate, unprivileged `getBlock`/`getTransaction` call to return account writability flags that do not correspond to the actual per-slot protocol state used by the bank during execution (`bank.get_reserved_account_keys()`/`check_reserved_keys`). Any downstream consumer relying on `jsonParsed` writable flags to interpret which accounts were touched/write-locked in a historical transaction can be permanently misled for transactions predating a reserved-key feature activation. This matches the "wrong-slot/fork/account data returned" / consensus-state-misreporting category in scope.

### Likelihood Explanation
Fully reachable by an unprivileged client with a single `getBlock`/`getTransaction(jsonParsed)` RPC call; no special commitment, staking, or leader control is required. Preconditions are: (a) a legacy/v0 transaction that write-locked a to-be-reserved pubkey before its gating feature activated, landing on-chain, and (b) any later point in time (which is essentially guaranteed once the feature is shipped and activated on any running cluster) where a client queries that historical block/transaction with `jsonParsed`. This is highly repeatable — it applies to every historical transaction that wrote to any key later added to `RESERVED_ACCOUNTS`, and it is deterministic (not a race), so it can be reproduced reliably in an integration test without needing to hit an exact slot boundary.

### Recommendation
Thread the transaction's actual slot-scoped `ReservedAccountKeys` (or the bank's `feature_set` at that slot) through `encode_with_meta`/`build_json_accounts`/`parse_v0_message_accounts`/`parse_legacy_message_accounts`/`parse_v1_message_accounts`, rather than calling `ReservedAccountKeys::new_all_activated()`. Where the caller (e.g., blockstore-based RPC handlers that no longer have bank access for older slots) cannot recover the slot's exact feature-activation state, the persisted `TransactionStatusMeta`/`loaded_addresses` should carry (or the accounts should be resolved using) the writable/readonly partition that was computed at execution time by the runtime, instead of recomputing writability from a global, ever-growing reserved-key snapshot.

### Proof of Concept
Integration test plan (runtime + transaction-status crates):
1. Pick a `ReservedAccount::new_pending(key, feature_id)` entry (or add a test-only one) not yet activated in a fresh `Bank`.
2. Build and land a `v0::Message` transaction at slot N-1 that write-locks `key` via a lookup table (`loaded_addresses.writable` contains `key`), asserting via `bank.check_reserved_keys` / SVM execution that this succeeds (key is truly writable pre-activation) and capture the resulting `TransactionStatusMeta`.
3. Activate `feature_id` (simulate epoch boundary via `compute_and_apply_new_feature_activations`), producing bank state at slot N where `bank.get_reserved_account_keys().is_reserved(&key)` is `true`.
4. Call `VersionedTransactionWithStatusMeta::encode(UiTransactionEncoding::JsonParsed, ...)` (which invokes `encode_with_meta` → `parse_v0_message_accounts`) on the transaction captured at step 2 (still representing slot N-1's transaction).
5. Assert (expected to fail today, demonstrating the bug):
   - `parsed.account_keys` entry for `key` has `writable == true` (correct, matching execution-time/`bank.check_reserved_keys` state at slot N-1).
   - Actual observed behavior: `writable == false`, because `encode_with_meta` used `ReservedAccountKeys::new_all_activated()` which includes `key` as reserved regardless of the transaction's actual slot/feature state.
6. Add a second assertion comparing against `bank.get_reserved_account_keys()` snapshotted at slot N-1 (before activation) to make the invariant explicit: `parsed_writable == !bank_at_slot.get_reserved_account_keys().is_reserved(&key)` for write-locked indices, which fails under current code.

pub fn parse_v0_message_accounts(message: &LoadedMessage) -> Vec<ParsedAccount> {
    let mut accounts: Vec<ParsedAccount> = vec![];
    for (i, account_key) in message.account_keys().iter().enumerate() {
        let source = if i < message.static_account_keys().len() {
            ParsedAccountSource::Transaction
        } else {
            ParsedAccountSource::LookupTable
        };
        accounts.push(ParsedAccount {
            pubkey: account_key.to_string(),
            writable: message.is_writable(i),
            signer: message.is_signer(i),
            source: Some(source),
        });
    }
    accounts
}

    /// This needs to be checked upon epoch boundary crosses because the

    pub fn check_reserved_keys(&self, tx: &impl SVMMessage) -> Result<()> {
        // Check keys against the reserved set - these failures simply require us
        // to re-sanitize the transaction. We do not need to drop the transaction.
        let reserved_keys = self.get_reserved_account_keys();
        for (index, key) in tx.account_keys().iter().enumerate() {
            if tx.is_writable(index) && reserved_keys.contains(key) {
                return Err(TransactionError::ResanitizationNeeded);
            }
        }

        Ok(())
    }
