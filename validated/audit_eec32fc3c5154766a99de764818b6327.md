### Title
ETH sent along with `withdrawAA`/`withdrawBB` is permanently locked in the ephemeral cooldown-request clone — (`contracts/IdleCDOEthenaVariant.sol`)

### Summary
`IdleCDOEthenaVariant._withdraw` is reachable through the payable `withdrawAA`/`withdrawBB` entrypoints in `IdleCDO`. It forwards the entire `msg.value` into a freshly deployed `EthenaCooldownRequest` clone, but nothing in the clone ever uses or returns that ETH. The clone only exposes an ERC20 `rescue()` gated to `TL_MULTISIG`, so any native ETH balance is unrecoverable — a direct analog of the Footium "excess ETH not returned" issue, except here *all* of the forwarded ETH is excess. [1](#0-0) [2](#0-1) 

### Finding Description
In `IdleCDOEthenaVariant._withdraw`, after burning the user's tranche tokens and computing `SUSDeRedeemed`, the contract deploys a minimal-proxy clone via `cooldownImpl.clone(abi.encodePacked(address(this), msg.sender), msg.value)`. The second argument to `ClonesWithImmutableArgs.clone` is the ETH value forwarded to the clone's address at creation. [1](#0-0) 

The clone (`EthenaCooldownRequest`) has exactly three external functions:
- `startCooldown()` — calls `SUSDE.cooldownShares`, no ETH use. [3](#0-2) 
- `unstake()` — calls `SUSDE.unstake(_getUser())`, paying out in USDe to the user, no ETH use. [4](#0-3) 
- `rescue(address _token)` — callable only by `TL_MULTISIG`, and it does `IERC20Detailed(_token).transfer(...)`, i.e. it sweeps ERC20 balances only; there is no path to move the native ETH balance out. [2](#0-1) 

The clone has no `receive`/`fallback` logic that forwards ETH and no function performing a `call{value:}`. Consequently, whatever ETH the user attached to the withdraw call is locked in a single-use, per-request clone forever. The withdraw itself still succeeds — tranche tokens are burned, sUSDe is cooldowned, and the user gets USDe after `unstake()` — so the loss is silent: the tx does not revert, it just strands the ETH. [5](#0-4) 

### Impact Explanation
Permanent freezing / loss of user funds. Any EOA calling `withdrawAA{value: X}` or `withdrawBB{value: X}` loses the full `X` ETH; it is neither refunded nor used by the protocol, and no role (including the honest `TL_MULTISIG` rescuer) can recover it because `rescue` only handles ERC20. The loss is quantifiable 1:1 as `msg.value` per withdraw call, and the clone address is deterministic per (CDO, user) pair so losses accumulate in dust-clones. Broken invariant: funds entering the system must either be accounted for or returned — here they vanish into an unrecoverable address.

### Likelihood Explanation
Likelihood is driven by user/frontend error rather than an active attacker, matching the original Footium report's class (Medium there as well). The payable entrypoints exist on the base `IdleCDO` interface, so integrators may reasonably attach ETH (e.g., assuming it's needed for the cooldown, or reusing payable wrappers). There is no `msg.value` upper bound, no `require(msg.value == 0)`, and no refund, so a single misconfigured call locks arbitrary ETH. Since `withdrawAA/BB` remain functional and the user's USDe still arrives, the mistake is not flagged by a revert.

### Recommendation
- In `IdleCDOEthenaVariant._withdraw`, either `require(msg.value == 0)` and pass `0` to `clone(...)`, or refund any ETH: keep `clone(..., 0)` and add `if (msg.value > 0) msg.sender.call{value: msg.value}("")` (respecting `nonReentrant` already present).
- Alternatively, if ETH is intended to pre-fund something in the clone, add an ETH sweep path (e.g., extend `EthenaCooldownRequest.rescue`/`unstake` to also return `address(this).balance` to `_getUser()`).

### Proof of Concept
Foundry fork test (mainnet, block where `IdleCDOEthenaVariant` is live and sUSDe `cooldownDuration != 0`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";

contract LockedEthPoC is Test {
    IdleCDOEthenaVariant cdo = IdleCDOEthenaVariant(payable(CDO_ADDRESS));
    IERC20Detailed usde = IERC20Detailed(USDE);
    IERC20Detailed susde = IERC20Detailed(SUSDE);

    function testEthLockedInCooldownClone() public {
        address user = makeAddr("user");
        uint256 depositAmt = 100e18;
        deal(USDE, user, depositAmt);
        vm.deal(user, 1 ether);

        // deposit to get AA tranche tokens
        vm.startPrank(user);
        usde.approve(address(cdo), depositAmt);
        cdo.depositAA(depositAmt);

        // withdraw with stray ETH attached
        cdo.withdrawAA{value: 1 ether}(0);
        vm.stopPrank();

        // predict the clone address (clones-with-immutable-args, CREATE2 by CDO)
        // or capture it from the NewCooldownRequestContract event
        // assert: clone holds the ETH and it is unrecoverable
        address clone = /* clone address from event logs */;
        assertEq(clone.balance, 1 ether);

        // rescue() only sweeps ERC20 and is TL_MULTISIG-gated:
        vm.expectRevert(); // '6' — not multisig
        EthenaCooldownRequest(clone).rescue(address(0));

        // even as multisig, rescue(address(0)) would transfer 0 tokens; ETH stays
        vm.prank(TL_MULTISIG);
        EthenaCooldownRequest(clone).rescue(USDE); // moves USDe, not ETH
        assertEq(clone.balance, 1 ether); // still locked after cooldown/unstake
    }
}
```

Steps: fork mainnet, deposit USDe via `depositAA`, call `withdrawAA{value: 1 ether}(0)`, read the clone address from `NewCooldownRequestContract`, and show `clone.balance == 1 ether` with no code path able to move it.
