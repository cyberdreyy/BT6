### Title
Reward front-running via `deposit_and_stake()` before epoch boundary dilutes existing delegators - (File: staking-pool/src/internal.rs)

### Summary
Because `internal_ping` only realizes/distributes validator rewards lazily (on the next contract call after `env::epoch_height()` changes) and distributes the entire accrued `total_reward` pro-rata over whatever `total_stake_shares` exist at that moment, an attacker who calls `deposit_and_stake()` in the final block of the current epoch mints shares at the pre-reward price without contributing to the reward that is about to be realized. When the epoch subsequently rolls over and any account (attacker or an unrelated user) triggers `internal_ping`, the attacker's freshly minted shares participate fully in the reward split even though the reward was earned entirely by the stake that existed before the deposit.

### Finding Description
The broken binding: `attacker_shares_at_deposit_price == attacker_entitlement_to_R`, where `R` is reward earned solely by pre-existing stake `S`. In reality, `attacker_reward_share = R * new_shares / total_stake_shares' > 0`, even though the attacker contributed `0` to the stake that earned `R`.

Code path:
- `deposit_and_stake()` in [1](#0-0)  calls `internal_ping()` first. If `env::epoch_height() == self.last_epoch_height`, `internal_ping` returns `false` immediately without touching `last_total_balance` or distributing any reward: [2](#0-1) .
- `internal_deposit()` then increments `self.last_total_balance += amount` for the attacker's deposit [3](#0-2) , and `internal_stake()` mints `num_shares` at the *current* (pre-reward) share price via `num_shares_from_staked_amount_rounded_down` [4](#0-3) [5](#0-4) .
- `internal_restake()` issues a `Promise::new(...).stake(...)` to activate the new total on-chain [6](#0-5) ; NEAR protocol semantics mean this newly-staked balance does not earn validator rewards until subsequent epochs, but the balance immediately becomes part of `account_locked_balance()`.
- After the epoch rolls, any account's next call re-enters `internal_ping`. It computes `total_reward = total_balance - self.last_total_balance` (which correctly excludes the attacker's principal since it was already folded into `last_total_balance`), but then distributes `remaining_reward` by simply increasing `self.total_staked_balance` uniformly, which raises the share price for every currently outstanding share — including the attacker's just-minted ones: [7](#0-6) .

None of the existing guards prevent this: the epoch-equality short-circuit in `internal_ping` (line 196) is precisely what allows the deposit to land "for free" in the pre-reward epoch; the balance monotonicity assert (line 208-211) only guards against balance decreases, not fairness of distribution; and the U256 rounding pair in `num_shares_from_staked_amount_rounded_down`/`staked_amount_from_num_shares_rounded_up` (lines 261-321) only prevents rounding-based share-price manipulation, not time-of-entry unfairness.

### Impact Explanation
Existing delegators' accrued-but-undistributed reward `R` is partially reassigned to the attacker's newly minted shares, diluting the staked balance every other delegator is entitled to. No NEAR leaves the contract, but the internal accounting value (`get_account_staked_balance`) that other parties (delegators withdrawing, the owner computing fees) settle on is measurably wrong — matching the "rewards ... attributed to the wrong party" High-severity category. The magnitude scales with the attacker's deposit size relative to the pool (`R * D / (S + D)`), and it is repeatable every epoch against every staking pool instance in this codebase, since the flaw is structural to `internal_ping`/`internal_stake`, not tied to one deployment.

### Likelihood Explanation
Preconditions are modest: the attacker only needs enough NEAR to make a `deposit_and_stake()` call and reasonably predict/observe the upcoming epoch boundary (epoch height and boundary timing are public/deterministic on NEAR). No privileged role, owner, multisig, or foundation account is required — any unprivileged caller can invoke `deposit_and_stake()`. The attacker bears normal staking/unstaking delay (`NUM_EPOCHS_TO_UNLOCK` = 4 epochs) before withdrawing the diluted gain, but that only delays realization, it does not prevent it.

### Recommendation
Realize/settle pending rewards (call `internal_ping`) unconditionally based on wall-clock/epoch state before minting any new shares in `deposit_and_stake`/`stake`, and separately, avoid relying solely on the `last_epoch_height == epoch_height` check to skip distribution — instead track and settle any reward that has already been earned by `account_locked_balance()` prior to processing a same-epoch deposit that could still benefit from a reward realized at the next `ping`. Alternatively, weight new deposits' entitlement to reward by time held (e.g., stake activation snapshots) rather than by static share count at ping time.

### Proof of Concept
```rust
// staking-pool/src/lib.rs (add to #[cfg(test)] mod tests)
#[test]
fn test_frontrun_reward_via_deposit_and_stake() {
    let mut emulator = Emulator::new(
        owner(),
        "KuTCtARNzxZQ3YvXDeLjx83FDqxv2SdQTSbiq876zR7".to_string(),
        zero_fee(),
    );
    // Victim stakes early, establishing S
    let victim_deposit = ntoy(1_000_000);
    emulator.update_context(alice(), victim_deposit);
    emulator.contract.deposit_and_stake();
    emulator.amount += victim_deposit;
    emulator.simulate_stake_call();

    let s_before = emulator.contract.total_staked_balance;

    // Same epoch: attacker deposits & stakes large amount D right before boundary
    // (epoch_height unchanged -> internal_ping is a no-op, per internal.rs:194-199)
    let attacker_deposit = ntoy(9_000_000);
    emulator.update_context(bob(), attacker_deposit);
    emulator.contract.deposit_and_stake();
    emulator.amount += attacker_deposit;
    emulator.simulate_stake_call();

    // Epoch boundary: locked_amount increases due to reward R earned only by s_before
    let reward = ntoy(100_000); // R, purportedly earned only by s_before (alice's stake)
    emulator.skip_epochs(1);
    emulator.locked_amount += reward;
    emulator.update_context(alice(), 0);
    emulator.contract.ping(); // internal_ping distributes R across ALL current shares

    let bob_staked = emulator.contract.get_account_staked_balance(bob()).0;
    // Assert: attacker (bob) receives a nonzero share of R despite contributing
    // nothing to the stake `s_before` that earned it.
    let bob_reward_share = bob_staked as i128 - attacker_deposit as i128;
    assert!(
        bob_reward_share > 0,
        "attacker should not be entitled to reward earned before their stake existed, got {}",
        bob_reward_share
    );
}
```
This test demonstrates that `bob` (attacker), who deposited in the same epoch immediately before the reward-bearing epoch transition, ends up with `staked_balance > attacker_deposit`, i.e., receives a slice of `reward` that was accrued entirely by `alice`'s pre-existing stake, confirming `shares_charged_at_deposit != shares' entitled portion of R`.

        let mut account = self.internal_get_account(&account_id);
        let amount = env::attached_deposit();

    pub(crate) fn internal_stake(&mut self, amount: Balance) {
        assert!(amount > 0, "Staking amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);

        // Calculate the number of "stake" shares that the account will receive for staking the
        // given amount.
        let num_shares = self.num_shares_from_staked_amount_rounded_down(amount);
        assert!(
            num_shares > 0,
            "The calculated number of \"stake\" shares received for staking should be positive"
        );
        // The amount of tokens the account will be charged from the unstaked balance.
        // Rounded down to avoid overcharging the account to guarantee that the account can always
        // unstake at least the same amount as staked.
        let charge_amount = self.staked_amount_from_num_shares_rounded_down(num_shares);
        assert!(
            charge_amount > 0,
            "Invariant violation. Calculated staked amount must be positive, because \"stake\" share price should be at least 1"
        );

        assert!(
            account.unstaked >= charge_amount,
            "Not enough unstaked balance to stake"
        );
        account.unstaked -= charge_amount;
        account.stake_shares += num_shares;
        self.internal_save_account(&account_id, &account);

        // The staked amount that will be added to the total to guarantee the "stake" share price
        // never decreases. The difference between `stake_amount` and `charge_amount` is paid
        // from the allocated STAKE_SHARE_PRICE_GUARANTEE_FUND.
        let stake_amount = self.staked_amount_from_num_shares_rounded_up(num_shares);

        self.total_staked_balance += stake_amount;
        self.total_stake_shares += num_shares;

    pub(crate) fn num_shares_from_staked_amount_rounded_down(
        &self,
        amount: Balance,
    ) -> NumStakeShares {
        assert!(
            self.total_staked_balance > 0,
            "The total staked balance can't be 0"
        );
        (U256::from(self.total_stake_shares) * U256::from(amount)
            / U256::from(self.total_staked_balance))
