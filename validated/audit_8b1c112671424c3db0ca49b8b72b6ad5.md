### Title
ERC4626 vault depositor can front-run `stopEpoch` and force a spurious borrower default - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.stopEpoch` delegates the stop-epoch funding check to `IProgrammableBorrower(_borrower()).onStopEpoch(...)`. When the programmable borrower sources liquidity from an ERC4626 vault, any vault depositor (an unprivileged user) can front-run `stopEpoch` by redeeming/withdrawing vault liquidity so `onStopEpoch` returns `false`. The CDO then treats the borrower as defaulted via `_handleBorrowerDefault`, socializing a loss on a solvent borrower and freezing the epoch state machine.

### Finding Description
The external bug class is "front-run a transaction and change validated parameters so execution fails." In `IdleCDOEpochVariant._stopEpoch`, the critical externally-mutable parameter is the liquidity available in the programmable borrower's ERC4626 vault:

- `stopEpoch`/`_stopEpoch` is callable by owner/manager once `block.timestamp >= epochEndDate` [1](#0-0) .
- In programmable-borrower mode the CDO asks the borrower to recall ERC4626 liquidity via `onStopEpoch(amountNeeded, isRequestingAllFunds)`; a `false` return immediately routes into `_handleBorrowerDefault(amountToPullFromBorrower + _pendingWithdraws)` [2](#0-1) .
- The comment acknowledges reverts bubble and "can be retried," but a `false` return is not retryable — it is treated as default [3](#0-2) .

An attacker who is an ordinary depositor in the borrower's ERC4626 vault watches the mempool (or simply acts after `epochEndDate` passes but before the manager's `stopEpoch` lands) and withdraws/redeems enough of the vault's idle liquidity that `onStopEpoch` cannot source `_amountToPullFromBorrower + _pendingWithdraws`. `onStopEpoch` returns `false`, and the CDO executes the borrower-default path — reserving underlying, invoking `_strategy.reserveDefaultRecovery`, and marking a loss — even though the borrower is solvent and would have repaid moments later [4](#0-3) .

Unlike the Teller case (pure gas griefing), here the induced revert path is not harmless: the false default triggers the loss-waterfall / default-accounting machinery (`vaultLoss`, `defaultPendingClaimBasis`, haircut on pending receipts and active tranches), so tranche holders suffer an immediate haircut and withdraw-request receipts are loss-adjusted while the underlying borrower position is actually healthy.

### Impact Explanation
- Premature loss socialization: BB-first (or pro-rata on pending receipts) loss is booked against a solvent borrower, permanently impairing tranche prices until/unless recovery flow fully unwinds it — and pending withdraw receipts are haircutted via `lossRecoveryPriceByEpoch` / `previewLossAdjustedWithdrawFunds` paths.
- Epoch state machine freezing: after `_handleBorrowerDefault` the normal `stopEpoch` completion is skipped, so `epochNumber` does not advance and deposits/withdrawals/claims gated on epoch progress are blocked until the default is finalized.
- The attack costs the attacker nothing beyond ordinary vault redemption (they keep their funds), and can be repeated at each epoch boundary on low-gas chains — the exact harassment economics described in the external report, upgraded here to real fund impact.

### Likelihood Explanation
- Trigger condition is easy: `stopEpoch` is permissioned to manager/owner but its success depends on *publicly mutable* ERC4626 vault liquidity. Any vault depositor qualifies under the allowed attacker set ("a user of the programmable borrower's ERC4626 vault").
- A large vault LP (or several coordinated LPs) can transiently pull liquidity exactly in the window between `epochEndDate` and the manager's `stopEpoch` transaction, then re-deposit after default is declared.
- Existing guards do not stop it: `_skimDonatedAssets` only handles donations, the `NotAllowed` checks at the top of `_stopEpoch` validate timing/interest inputs, and nothing distinguishes "borrower insolvent" from "borrower vault transiently drained by a third-party LP."

### Recommendation
- Make `onStopEpoch` failure distinguishable: revert on transient liquidity shortfall (retryable) rather than returning `false`, or have the borrower contract only return `false` when the borrower itself cannot repay, not when vault idle liquidity is low.
- Alternatively, add a grace/retry window: record a failed-stop timestamp and only escalate to `_handleBorrowerDefault` if funding is still unavailable after N blocks, so third-party liquidity swings cannot unilaterally trigger default accounting.
- In `ProgrammableBorrower.onStopEpoch`, prefer pulling from borrower-held reserves before trusting ERC4626 idle liquidity.

### Proof of Concept
```solidity
// test/foundry/StopEpochFrontrunDefault.t.sol
// Setup: prefunded/programmable IdleCDOEpochVariant + ProgrammableBorrower
// backed by an ERC4626 vault where `attacker` is a large depositor.
function testFrontrunStopEpochForcesDefault() external {
    // 1. LPs deposit, epoch 0 runs, borrower draws funds as usual.
    _depositWithUser(lp1, 1_000_000e6);
    _startEpochAndCheckPrices(0);

    // 2. Warp past epochEndDate; manager's stopEpoch is expected.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 interest = cdoEpoch.expectedEpochInterest();
    deal(defaultUnderlying, borrower, interest); // borrower IS solvent

    // 3. Attacker (ERC4626 vault depositor) front-runs stopEpoch by
    //    redeeming enough vault shares that onStopEpoch can't recall
    //    amountToPullFromBorrower + pendingWithdraws.
    uint256 needed = interest; // + strategy.pendingWithdraws()
    vm.prank(attacker);
    vault.redeem(vaultLiquidityLeavingShortfall(needed), attacker, attacker);

    // 4. Manager calls stopEpoch; onStopEpoch returns false and the CDO
    //    takes the borrower-default path instead of normal settlement.
    vm.prank(manager);
    cdoEpoch.stopEpoch(newApr, 0);

    // 5. Assert spurious default state and loss socialization:
    assertTrue(strategy.borrowerDefaulted() /* or equivalent flag */);
    uint256 priceAA = cdoEpoch.virtualPrice(address(AAtranche));
    assertLt(priceAA, ONE_TRANCHE, "LP haircut booked on solvent borrower");
    // 6. Attacker redeposits; borrower's actual position was healthy.
}
```

Uncertainty note: I was unable to read `ProgrammableBorrower.onStopEpoch`'s internals within the available index budget, so the exact condition under which it returns `false` versus reverting could not be fully verified. The `try`/`false`→`_handleBorrowerDefault` wiring in `IdleCDOEpochVariant.sol` is confirmed; if `onStopEpoch` reverts (rather than returning `false`) on liquidity shortfall, the same front-running still produces repeated `stopEpoch` failures (temporary epoch freeze), which would reduce the finding to DoS and fall under the rejection criteria — verification of `onStopEpoch`/`vaultLoss` behavior in `contracts/strategies/idle/ProgrammableBorrower.sol` is required before submission.

  function stopEpoch(uint256 _newApr, uint256 _interest) public {
    _stopEpoch(_newApr, _interest, 0);
  }

  /// @notice Internal stop-epoch implementation with optional proportional pending-receipt loss.
  /// @param _newApr New apr to set for the next epoch
  /// @param _interest Interest gained in the epoch
  /// @param _lossAmount Loss amount to split between active LPs and pending receipts
  function _stopEpoch(uint256 _newApr, uint256 _interest, uint256 _lossAmount) private {
    _checkOnlyOwnerOrManager();
    bool _isRequestingAllFunds = _interest == 1;
    _checkProgrammableBorrowerMode();

    IdleCreditVault _strategy = IdleCreditVault(strategy);
    uint256 _pendingWithdrawFees = pendingWithdrawFees;

    _checkNotAllowed(
      // Check that epoch is running
      !isEpochRunning || 
      // Check that end date is passed
      block.timestamp < epochEndDate || 
      // Check that there are no pending instant withdraws, ie `getInstantWithdrawFunds` was called
      // before closing the epoch
      _pendingInstant() != 0 ||
      // Check that overridden interest, if passed (ie > 1), is greater than pending withdraw fees and the apr is 0 
      // otherwise withdrawal requests may not be fullfilled as they consider also the interest gained in the next epoch 
      (_interest > 1 && (_interest < _pendingWithdrawFees || _newApr != 0)) ||
      // Closing already recalls all principal, so applying a separate loss burn would strand returned cash.
      (_isRequestingAllFunds && _lossAmount != 0)
    );
