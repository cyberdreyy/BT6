### Title
Signer weight double-counted when a signer flips from Rejected to Accepted for the same block, corrupting `total_weight_approved`/`total_weight_rejected` accounting - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary

### Finding Description
`StackerDBListener::run` maintains a `BlockStatus` per proposed block with two independent tallies, `total_weight_approved` and `total_weight_rejected`, plus a `responded_signers: HashSet<u32>` that is supposed to represent "this slot has already contributed its weight." [1](#0-0) 

On a `BlockResponse::Rejected` message, the code adds the signer's weight to `total_weight_rejected` gated only by `block.responded_signers.insert(slot_id)` returning `true` (i.e., first response wins the gate): [2](#0-1) 

On a `BlockResponse::Accepted` message, however, the weight is added to `total_weight_approved` based on a *different* condition — `!block.gathered_signatures.contains_key(&slot_id)` — which has nothing to do with `responded_signers`: [3](#0-2) 

Because the "already counted" gate for the reject path (`responded_signers`) is disjoint from the gate for the accept path (`gathered_signatures`), a single signer who first sends a `Rejected` response (weight added to `total_weight_rejected`, slot added to `responded_signers`) and later sends an `Accepted` response for the *same* block hash (allowed — the block is not removed from `blocks` and `gathered_signatures` does not yet contain this slot) will have its weight added to `total_weight_approved` as well. The signer's weight is now counted in both buckets simultaneously, and there is no code path that decrements `total_weight_rejected` when a signer flips to Accepted.

This exactly matches the reported bug class: a missing duplicate/already-counted check (analogous to `IncentiveManager::addIncentiveLogic` not checking for an existing index before overwriting `incentiveSystemIndex`) allows one actor to be recorded into two places that a correct accounting model assumes are mutually exclusive, breaking the invariant that `total_weight_approved + total_weight_rejected` reflects the *disjoint* set of currently-standing votes.

The only defense that exists, `reset_rejections`, clears `responded_signers`/`total_weight_rejected` but is invoked by the *miner's coordinator* only after a timeout — it does not run on every Accept, and does not run at all in the normal (non-timeout) path where a signer rejects then quickly re-sends an acceptance. [4](#0-3) 

### Impact Explanation
`total_weight_rejected` is used by the miner (`SignerCoordinator::get_block_status`) to decide whether the block proposal has been rejected by a blocking minority, to drive the rejection timeout back-off schedule, and to determine which failed transactions to permanently/temporarily exclude from the next block-building attempt: [5](#0-4) 

Because a flipped signer's weight is never removed from `total_weight_rejected`, the miner can perceive stale/duplicated rejection weight that overstates real opposition to the block, potentially:
- Prematurely declaring `SignersRejected` and abandoning a block proposal that would otherwise have reached (or already reached) the real 70% approval threshold, i.e. the aggregated-weight tally the miner trusts no longer matches the true count of currently-standing accepts, a liveness/accounting break called out explicitly as in-scope ("aggregated-weight vs verified-accepts").
- Incorrectly attributing weight toward the `blocking_minority > 30%` bar for excluding transactions (`permanently_excluded_txids`/`temporarily_excluded_txids`), causing transactions to be excluded from future blocks based on inflated/stale rejection weight that no longer corresponds to that signer's current (accepted) position.

This is triggerable by a single signer (no majority required), satisfying the impact criteria of "aggregated-weight vs verified-accepted" mismatch/broken equality.

### Likelihood Explanation
Any signer that is buggy, restarted, or simply reprocesses a proposal (e.g. a signer initially rejects due to a transient local validation issue and later — after further processing/pre-commit handling in `stacks-signer/src/v0/signer.rs` — arrives at acceptance for the same block hash) can trigger this without coordination with other signers. Because the two code branches gate on different maps (`responded_signers` vs `gathered_signatures`), the double count happens automatically the first time any single slot transitions Reject → Accept for the same `signer_signature_hash` while the block status entry is still live in the `blocks` map (i.e., before a proposal timeout triggers `reset_rejections`, or for any slot whose rejection was never reset).

### Recommendation
Gate the Accept-path weight addition on the same "already contributed weight" state used for rejections (i.e., on `responded_signers`, or a unified per-slot vote status), and when a slot transitions from Rejected to Accepted, explicitly subtract its weight from `total_weight_rejected` before adding it to `total_weight_approved` (or vice versa), so that a slot's weight is always counted in exactly one bucket:

```diff
 if !block.gathered_signatures.contains_key(&slot_id) {
+    // If this slot had previously rejected, remove its weight from the reject tally
+    // before counting it toward acceptance, so weight is never double counted.
+    if block.responded_signers.contains(&slot_id) && !block.gathered_signatures.contains_key(&slot_id) {
+        block.total_weight_rejected = block.total_weight_rejected.saturating_sub(signer_entry.weight);
+    }
     block.total_weight_approved = block
         .total_weight_approved
         .saturating_add(signer_entry.weight);
     ...
 }
```

### Proof of Concept
1. Miner proposes block `B`; `StackerDBListenerComms::insert_block` creates a fresh `BlockStatus` with `total_weight_approved = 0`, `total_weight_rejected = 0`, empty `responded_signers`/`gathered_signatures`. [6](#0-5) 
2. Signer at `slot_id = 5` (weight `W`) sends `BlockResponse::Rejected` for `B`. In `StackerDBListener::run`, `block.responded_signers.insert(5)` returns `true`, so `total_weight_rejected += W`. [2](#0-1) 
3. Before any timeout/`reset_rejections` occurs, the same signer at `slot_id = 5` sends `BlockResponse::Accepted` for the same `B` (e.g. after re-evaluating and pre-committing). `block.gathered_signatures.contains_key(&5)` is `false` (never inserted for accept before), so `total_weight_approved += W` executes unconditionally. [3](#0-2) 
4. Now `total_weight_approved = W` and `total_weight_rejected = W` for the *same single signer's weight* — the sum of the two tallies exceeds what a single, currently-standing vote should contribute, and `total_weight_rejected` never reflects that slot 5 has actually moved to Accept.
5. In `SignerCoordinator::get_block_status`, this stale `total_weight_rejected` continues to be added toward the `> self.total_weight - self.weight_threshold` rejection-declaration check and toward `blocking_minority` transaction-exclusion logic, even though the signer in question currently supports the block. [7](#0-6) 

Note: I was not able to fully trace whether `stacks-signer/src/v0/signer.rs` has a legitimate flow where a single signer emits Reject then later Accept for the identical `signer_signature_hash` without an intervening proposal change (e.g., via pre-commit retry logic in `handle_block_pre_commit`/`store_and_process_block_signature`); confirming the exact signer-side trigger sequence would benefit from a full Devin session with the ability to run the existing signer test harnesses in `stacks-signer/src/v0/tests.rs` and `stacks-node` integration tests.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
