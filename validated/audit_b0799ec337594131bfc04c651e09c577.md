### Title
Unbounded `underlyingsRequested` injection lets any tranche holder permanently saturate `pendingUnderlyings` and block write-off fulfillment - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`createWriteOffRequest` accepts a fully attacker-controlled `underlyingsRequested` parameter and adds it verbatim to both the per-user request and the global `pendingUnderlyings` counter, with no bound, sanity check, or relationship to the tranche tokens actually escrowed [1](#0-0) . This is the closest analog to the reported bug class (improper neutralization of attacker-supplied input flowing into a privileged sink): an unvalidated numeric "special element" is injected into protocol-level accounting that the rest of the system trusts.

### Finding Description
In `createWriteOffRequest`, a caller deposits `amount` tranche tokens and declares `underlyingsRequested`. The function performs only two checks: the epoch must be running and `amount != 0` [2](#0-1) . `underlyingsRequested` itself is never validated — it can be `type(uint256).max` regardless of how many tranche tokens are deposited (the minimum viable cost is 1 wei of tranche token). Both `userRequests[msg.sender].underlyings` and `pendingUnderlyings` are incremented by this arbitrary value [3](#0-2) .

Two consequences follow:

1. **Unfulfillable request lock-in.** `fullfillWriteOffRequest` requires `currentRequest.tranches == _tranches` (exact match) and `_underlyings >= currentRequest.underlyings` [4](#0-3) . A request with `underlyingsRequested = type(uint256).max` can never be fulfilled, yet it remains counted in `pendingUnderlyings` until the attacker voluntarily calls `deleteWriteOffRequest`.

2. **Global counter poisoning.** `pendingUnderlyings` is a vault-wide aggregate of all outstanding write-off demand. If this value is consumed elsewhere (e.g., by the vault's `writeOffDeposit` flow in `IdleCDOEpochVariant` or off-chain fulfilment logic that sizes reserves against it), a single attacker inflates it to saturation for the cost of 1 tranche-token wei held in escrow — recoverable at any time via `deleteWriteOffRequest`, making the attack costless and repeatable.

Additionally, `createWriteOffRequest` *accumulates* into an existing request (`currentRequest.tranches + amount`, `currentRequest.underlyings + underlyingsRequested`) rather than overwriting, so repeated calls keep raising `pendingUnderlyings` without bound (subject only to Solidity 0.8 overflow revert, which the attacker avoids by using values just below the ceiling).

### Impact Explanation
Broken invariant: escrow accounting integrity — a user-supplied field that is meant to represent a *bona fide* ask price is instead arbitrary attacker-controlled input injected into a global solvency/liquidity aggregate. The result is denial of the write-off mechanism: the borrower's ability to settle discounted debt via `writeOffDeposit`, and honest fulfillers' ability to clear requests, can be gated by a poisoned `pendingUnderlyings` and by permanently unfulfillable phantom requests. Because the attacker can create and delete at will during any running epoch, they can selectively freeze the write-off path at the moments it matters most (e.g., when a distressed borrower attempts to write off debt), prolonging the freeze of lender funds in the vault.

### Likelihood Explanation
- Attacker requirements: any KYC-passing lender holding ≥1 wei of tranche tokens during a running epoch (`isEpochRunning()` is the only gate) [5](#0-4) . No privileged role needed.
- Cost: gas only; escrowed tranche tokens are fully recoverable via `deleteWriteOffRequest` [6](#0-5) .
- Caveat: the severity hinges on how `pendingUnderlyings` is consumed by the vault/borrower write-off path; I could not fully trace every consumer of this counter in the available iterations. If it is purely informational, the impact reduces to unfulfillable phantom requests (griefing of honest fulfillers' UX), which weakens the finding toward the rejected "DoS without fund impact" class.

### Recommendation
- Validate `underlyingsRequested` in `createWriteOffRequest`: enforce a nonzero floor, and cap it at a sensible bound relative to the escrowed tranches (e.g., `amount * maxWriteOffPrice / ONE_TRANCHE`).
- Alternatively, make fulfillment *partial-friendly*: store `underlyings` as a price-per-tranche rather than a lump sum, so a poisoned lump sum cannot create an unmatchable request.
- Ensure `pendingUnderlyings` cannot be influenced by requests that have no realistic fulfillment path; consider computing it lazily or bounding it by total escrowed tranche value.

```solidity
        escrow.fullfillWriteOffRequest(attacker, 1, type(uint256).max / 2);

        vm.prank(attacker);
        escrow.deleteWriteOffRequest();
```

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

```text
  function deleteWriteOffRequest() external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[msg.sender];
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, currentRequest.tranches);
  }
```

```text
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)

    }
```
