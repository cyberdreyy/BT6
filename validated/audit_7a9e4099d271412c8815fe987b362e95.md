### Title
Stale per-epoch instant-withdraw accounting enables double-claim of default recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Like the kernel bug (one dequeue path decrements `qlen` but not `backlog`, so a later aggregate `qdisc_tree_reduce_backlog` underflows), `claimInstantWithdrawRequest` clears the aggregate receipt counters (`instantWithdrawsRequests[_user]`, balance burn, funded payout) but never clears the paired per-epoch counters `instantWithdrawsRequestsByEpoch[_user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]`. A user who already claimed an instant withdraw at par can be paid a second time from the default recovery reserve if the same `epochNumber` later defaults while `pendingInstantWithdraws` is still non-zero.

### Finding Description
`requestInstantWithdraw` records three coupled counters: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 366-374). The normal claim path `claimInstantWithdrawRequest` only zeroes `instantWithdrawsRequests[_user]` and burns the receipt (lines 387-392) — the per-epoch entries remain stale forever.

Later, if a borrower default is finalized in that same `epochNumber`:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` (lines 644-649), which still includes the already-paid claim, inflating `totalBasis`.
- `_defaultPrefundedInstantReserve()` (lines 716-723) treats `instantBasis - pendingInstant` as cash already held for those claims — including funds already paid out to the user — inflating the reserve.
- In `claimInstantWithdrawRequest`, when `defaultInstantWithdrawsFinalized` is set, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844). Because the stale value was never cleared, the previously-fully-paid user is paid *again* at `defaultRecoveryPrice` from `defaultRecoveryReserve` (lines 847-855).

### Impact Explanation
The attacker receives their instant withdrawal twice: once at par through the funded path, and once more through the defaulted-epoch claim, paid out of the recovery reserve that belongs to genuinely defaulted claimants. This directly steals recovery funds from other users (the reserve is finite; every double-paid wei dilutes or drains honest claims). It also permanently corrupts solvency accounting: `totalBasis` and `prefundedReserve` are both inflated by already-spent funds.

### Likelihood Explanation
Requires: instant-withdraw mode active (APR decreased by more than `instantWithdrawAprDelta`), the user requests and claims an instant receipt, `pendingInstantWithdraws` remains non-zero at default finalization (the code explicitly supports partial instant-queue funding — see comments at lines 636-640 and 713-714), and `defaultRecoveryEpoch == epochNumber` of the stale request (the common case when the borrower's `stopEpoch` fails in the same epoch the instant requests were made). All steps use only unprivileged user calls and honest-manager epoch sequencing.

### Recommendation
In `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` for the request's epoch, mirroring how `_clearWithdrawClaimForEpoch` maintains `withdrawsRequestsByEpoch`/`withdrawsRequests` symmetrically (lines 815-820). This likely requires storing the request epoch per user (e.g., a `lastInstantWithdrawRequest` marker) since it is not currently tracked.
