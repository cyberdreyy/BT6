The gateway's Vault handler contains an unbounded, unauthenticated request-map growth issue that closely mirrors the Ronin vote-pool DOS bug class ("no bound on pending records tracked from untrusted input, no pruning threshold").

### Title
Unauthenticated Vault Gateway `GetPublicKey` requests cause unbounded `activeRequests` map growth (memory-exhaustion DOS) - (File: core/services/gateway/handlers/vault/handler.go)

### Summary
`handler.HandleJSONRPCUserMessage` in the Vault gateway handler explicitly skips authorization for `MethodPublicKeyGet` requests, and `newActiveRequest` inserts every request into `h.activeRequests` keyed by the client-supplied `req.ID` with no cap on the number of entries, unlike the sibling `common.requestCache`, which enforces `maxCacheSize`. An unauthenticated caller can flood the gateway HTTP endpoint with `vault_getPublicKey` requests using unique IDs, each one allocating a new `*activeRequest` that only gets pruned every 5 seconds (`defaultCleanUpPeriod`) after sitting for up to `requestTimeout` (default 30s).

### Finding Description
In `core/services/gateway/handlers/vault/handler.go`: [1](#0-0) 

The comment "Public key requests don't require authorization" confirms this path is reachable pre-auth. Each call that misses the small cache goes through: [2](#0-1) 

`newActiveRequest` only rejects a duplicate `req.ID`; it never checks `len(h.activeRequests)` against any maximum, unlike the analogous `requestCache.NewRequest` used elsewhere in the gateway, which enforces `maxCacheSize` and rejects new entries once the cache is full: [3](#0-2) 

Cleanup only happens on a 5-second ticker and only removes entries older than `requestTimeout` (default 30s): [4](#0-3) 

There is no rate limiter applied to inbound user JSON-RPC requests in this path — `h.nodeRateLimiter` is only checked in `HandleNodeMessage`, i.e., on responses from DON nodes, not on the initial unauthenticated user request: [5](#0-4) 

This is directly analogous to the Ronin vote-pool DOS: the fix there was to (a) only track state for validated input and (b) enforce a pruning/size threshold on the tracked-peer map to stop unbounded growth. Here, an entirely unauthenticated request type is allowed to grow an unbounded in-memory map, with each entry also holding an active goroutine and pending `Callback`/`sync.Mutex` state fanned out to every DON member (`fanOutToVaultNodes`), amplifying resource cost server- and DON-side.

### Impact Explanation
Sustained flooding with unique-ID `vault_getPublicKey` requests can grow `h.activeRequests` without bound between cleanup ticks, exhausting gateway memory and causing goroutine/connection pressure, and amplifying load onto every Vault DON node via `fanOutToVaultNodes`. This can degrade or crash the gateway process serving legitimate users, i.e., a genuine availability DOS reachable from an unauthenticated/unprivileged client.

### Likelihood Explanation
High: the endpoint requires no authentication or allowlisting, request IDs are attacker-controlled and only need to be unique, and there is no per-request-count cap or user-facing rate limiter on this code path (only a rate limiter for node-originated responses exists). An attacker only needs basic HTTP access to the gateway.

### Recommendation
- Enforce a maximum size on `h.activeRequests` (mirroring `requestCache.maxCacheSize`), rejecting new requests once the limit is reached.
- Apply a request-level (per-IP or global) rate limiter to unauthenticated `MethodPublicKeyGet` requests before calling `newActiveRequest`.
- Consider shortening the cleanup interval or using per-entry timers (as `common.requestCache` does with `time.AfterFunc`) rather than a fixed 5-second sweep, to bound worst-case outstanding entries more tightly.

### Proof of Concept
1. Send a high-rate stream of `vault_getPublicKey` JSON-RPC requests to the gateway's HTTP endpoint, each with a fresh, unique `id` field, and no `Auth` header.
2. Each request bypasses authorization (`req.Method == vaulttypes.MethodPublicKeyGet` branch) and, since the public key is not yet cached, calls `h.newActiveRequest`, adding an entry to `h.activeRequests`.
3. Because there is no cap on `len(h.activeRequests)` and cleanup only runs every 5 seconds for entries older than 30 seconds, sustained request rates exceeding the cleanup rate cause the map (and associated per-request goroutines/state) to grow unbounded, exhausting gateway memory/resources.

func (h *handler) removeExpiredRequests(ctx context.Context) {
	h.mu.RLock()
	var expiredRequests []*activeRequest
	now := h.clock.Now()

		if now.Sub(userRequest.createdAt) > h.requestTimeout {

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
