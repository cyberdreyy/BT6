### Title
Stale loss-adjusted withdraw receipt is later paid at par via `lastWithdrawRequest` overwrite — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
A use-after-free style analog: a withdraw receipt from a loss-adjusted epoch (`lossRecoveryPriceByEpoch`) is "freed" logically at `collectWithdrawFunds` (its `pendingWithdraws` basis is cleared and only the haircut amount is collected), but the per-user epoch ledger entry `withdrawsRequestsByEpoch[user][lossEpoch]` survives. If the user makes a *new* withdraw request instead of claiming, `lastWithdrawRequest[user]` is overwritten to the new epoch, so `_claimLossAdjustedWithdrawRequest` never looks up the old loss epoch again. The stale receipt is then paid in full at par through `_claimFundedWithdrawRequest`, spending other claimants' funded underlyings.

### Finding Description
At `collectWithdrawFunds`, when the borrower funds less than `pendingWithdraws`, the strategy stores `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` — the unfunded remainder is a realized loss assigned to all pending receipts of that epoch (`contracts/strategies/idle/IdleCreditVault.sol:411-430`).

The only bridge between a user and that stored price is `lastWithdrawRequest[_user]`, read at `IdleCreditVault.sol:790`:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

`requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` (line 282). So the sequence is:

1. Epoch N: attacker requests withdraw (e.g. all AA tranches). `withdrawsRequestsByEpoch[attacker][N] = amt`, `lastWithdrawRequest[attacker] = N`.
2. `stopEpochWithDuration` realizes a loss → `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL` and collects only `amt * p` (pro-rata share) into the strategy.
3. Attacker does **not** claim. In epoch N+1 buffer, attacker deposits again (or keeps dust tranches) and calls `requestWithdraw` → `lastWithdrawRequest[attacker] = N+1`, `withdrawsRequests[attacker] += amt2`.
4. Epoch N+1 stops normally; `epochNumber` becomes N+2.
5. Attacker calls `claimWithdrawRequest`:
   - `lossRecoveryPriceByEpoch[N+1] == 0` → loss-adjusted path skipped; `withdrawsRequestsByEpoch[attacker][N]` never cleared.
   - `_claimFundedWithdrawRequest` passes the gate (`epochNumber > lastWithdrawRequest`) and pays `withdrawsRequests[attacker]` — which still includes the full epoch-N basis — **at par**.

The attacker receives `amt_N` in full although only `amt_N * p / RECOVERY_FULL` was ever funded for that receipt. The overpayment `amt_N * (1 - p)` comes out of the strategy's underlying balance, which is reserved for other users' funded claims (guarded only against the default-recovery reserve by `_transferFundedClaim`, not against each other).

Broken invariant: one receipt, one payout — the loss-adjusted payout obligation is "freed" (basis cleared at collection) yet the receipt is reused once at full value.

### Impact Explanation
Direct theft / insolvency: the attacker extracts `receiptAmount * (1 - lossRecoveryPrice)` of underlying that belongs to other funded withdraw claimants. The last claimant(s) to call `claimWithdrawRequest` find the strategy under-collateralized and are permanently unable to withdraw. Loss is quantified: e.g., a 100k USDC receipt at a 50% loss-recovery price yields a 50k USDC overpayment.

### Likelihood Explanation
Requires a `stopEpochWithDuration` with `_lossAmount > 0` (honest manager call during a real loss event), plus the attacker keeping re-deposit/re-request rights (any KYC-passing lender). No privileged role is attacker-controlled; the attacker merely times ordinary `requestWithdraw`/`claimWithdrawRequest` calls around honest epoch transitions. Each subsequent loss epoch can be similarly laundered, so the primitive repeats.

### Recommendation
Track loss-adjusted epochs per user, not via the single `lastWithdrawRequest` slot. Concretely: in `_claimLossAdjustedWithdrawRequest`, iterate (or store) all epochs in `withdrawsRequestsByEpoch[_user]` that have a non-zero `lossRecoveryPriceByEpoch`, or record per-user per-epoch haircuts and check `lossRecoveryPriceByEpoch` for *every* epoch with an outstanding entry before paying the remainder at par. At minimum, when a new `requestWithdraw` overwrites `lastWithdrawRequest`, either force-claim/queue the old receipt at its recorded recovery price or refuse the new request while a loss-adjusted receipt is unclaimed.

### Proof of Concept
Foundry sketch against `test/foundry/IdleCreditVault.t.sol` harness (AA tranche, standard epoch variant):

```solidity
function testStaleLossReceiptPaidAtPar() external {
    uint256 amt = 10_000 * ONE_SCALE;
    address attacker = makeAddr('attacker');
    address victim   = makeAddr('victim');

    _depositWithUser(attacker, amt, true);
    _depositWithUser(victim,   amt, true);

    // Epoch N: both request full withdraw
    vm.prank(attacker);
    uint256 aReq = cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(victim);
    uint256 vReq = cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(0);

    // Lossy stop: borrower funds only 50% of pendingWithdraws
    IdleCreditVault cv = IdleCreditVault(address(strategy));
    uint256 pending = cv.pendingWithdraws();
    uint256 loss    = pending / 2;
    (uint256 pendingToFund, uint256 activeLoss) = cv.previewLossAdjustedWithdrawFunds(loss);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(defaultUnderlying, strategy.borrower(), repay);
    vm.prank(strategy.borrower());
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), repay);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), loss);

    // Victim claims haircut amount now; attacker waits
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest();

    // Epoch N+1: attacker redeposits proceeds and requests again, overwriting lastWithdrawRequest
    _depositWithUser(attacker, amt / 10, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Attacker claims: stale epoch-N receipt is paid at PAR, not at 50% recovery price
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre;

    // got includes aReq in full instead of aReq * 0.5 -> strategy insolvent vs remaining claimants
    assertGt(got, aReq / 2 + (amt / 10), 'loss-adjusted receipt was overpaid at par');
}
```

`withdrawsRequestsByEpoch[attacker][N]` is never cleared because `_claimLossAdjustedWithdrawRequest` only inspects `lastWithdrawRequest[attacker]` (now N+1), while `_claimFundedWithdrawRequest` at `IdleCreditVault.sol:338-349` pays the aggregate `withdrawsRequests[attacker]` at par.
