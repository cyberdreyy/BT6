### Title
`depositDuringEpoch` credits and forwards the nominal `_amount` instead of the received amount, breaking solvency with fee-on-transfer underlyings - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`IdleCDOEpochVariant.depositDuringEpoch` pulls `_amount` of underlying from the depositor, but mints tranche shares, updates `lastNAVAA/BB` via `_mintShares`, mints strategy tokens, and forwards funds to the borrower all using the nominal `_amount` — never the balance actually received. With a fee-on-transfer or deflationary underlying (e.g., USDT with fee enabled, or any rebasing/deflationary stable the vault is deployed on), the CDO receives `_amount - fee` while accounting and outflows assume `_amount`, creating an immediate shortfall that is paid out of other depositors' principal.

### Finding Description
The base `IdleCDO._deposit` is fee-on-transfer safe: it snapshots `_preBal` and mints shares on the balance delta (`_contractTokenBalance(_token) - _preBal`) [1](#0-0) . The mid-epoch path does not inherit this protection. In `depositDuringEpoch`: [2](#0-1) 

- `_transferUnderlyingsFrom(msg.sender, address(this), _amount)` pulls the tokens; received amount is never measured.
- `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal` mints shares priced on the full `_amount`.
- `_mintShares(_tranche, msg.sender, _minted, _amount)` bumps `lastNAVAA/BB` by `_amount`.
- `IdleCreditVault(strategy).mintStrategyTokens(_amount)` mints `_amount` claim tokens to the CDO.
- `_transferUnderlyings(_borrower(), _amount)` sends the full `_amount` to the borrower.

Two compounding defects result: (1) the CDO only received `_amount - fee`, so the transfer to the borrower either reverts (DoS) or, if the CDO holds a residual buffer from skimmable donations/instant-withdraw prefunding, drains `fee` worth of other users' assets; (2) even setting the outgoing leg aside, `lastNAV`, `expectedEpochInterest`, minted tranche shares, and minted strategy tokens are all inflated by the fee portion that never arrived — the depositor is credited principal they never paid.

The same pattern exists one level down in `IdleCreditVault.deposit`, which `safeTransferFrom`s `_amount` and then `_mint(msg.sender, _amount)` unconditionally — minting 1:1 strategy tokens for the shortfall amount [3](#0-2) .

### Impact Explanation
Direct insolvency/theft of principal. An unprivileged KYC-passed lender deposits `_amount` of a token charging fee `f`. The CDO forwards `_amount` to the borrower (or credits `_amount` of strategy tokens/NAV) while only `_amount - f` arrived. The deficit `f` per deposit is covered by existing tranche holders' NAV and withdrawable liquidity. With a 1% transfer fee and repeated deposits, an attacker can mint claim shares for value never delivered and socialize the missing `f` onto AA/BB holders at epoch stop or withdrawal — quantified loss equals the aggregate fee skimmed on every deposit.

### Likelihood Explanation
Requires only (a) the vault deployed on a fee-on-transfer underlying — `token` is a free initializer parameter, and USDT-style tokens support optional transfer fees — and (b) `isDepositDuringEpochDisabled == false` with an honest manager running a normal epoch. The attacker is an ordinary whitelisted lender; no privileged collusion is needed. The guards that exist (`_skimDonatedAssets`, `_guarded`, KYC check, `isEpochRunning` gating) do not measure the received balance, so none of them stop it.

### Recommendation
Measure the actual received amount and use it for all downstream accounting:

```solidity
uint256 _preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 _received = _contractTokenBalance(token) - _preBal;
```

Then compute `interest`, `trancheInterest`, `_minted`, `mintStrategyTokens`, and the borrower transfer on `_received` (or revert if `_received != _amount` for a fixed-principal borrower model). Apply the same delta-based minting inside `IdleCreditVault.deposit` (mint `balanceOf - preBal` instead of `_amount`) so the strategy token supply stays backed 1:1.

### Proof of Concept
```solidity
// Foundry fork test sketch (fee-on-transfer mock or USDT-with-fee mainnet fork)
function testFeeOnTransferMidEpochDeposits() external {
    // underlying = FoT token with 1% fee on transfer
    idleCDO.depositAA(10_000e6);            // normal seed deposit
    _startEpochAndCheckPrices(0);
    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);
    vm.warp(cdoEpoch.epochEndDate() - cdoEpoch.epochDuration() / 2);

    address attacker = makeAddr('attacker');
    deal(fotToken, attacker, 1_000e6);
    vm.startPrank(attacker);
    IERC20(fotToken).approve(address(cdoEpoch), 1_000e6);
    uint256 minted = cdoEpoch.depositDuringEpoch(1_000e6, address(AAtranche));
    vm.stopPrank();

    // CDO only received 990e6 but:
    // - minted shares are priced on 1_000e6 (+ interest share)
    // - lastNAVAA increased by 1_000e6
    // - borrower received 1_000e6 pulled from vault liquidity (10e6 of other users' funds)
    // - strategy minted 1_000e6 claim tokens
    assertEq(underlying.balanceOf(address(cdoEpoch)), 0);
    assertGt(minted * cdoEpoch.virtualPrice(address(AAtranche)) / 1e18, 990e6);
}
```
