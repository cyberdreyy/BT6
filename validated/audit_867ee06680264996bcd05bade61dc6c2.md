### Title
Unauthenticated MessageId collision allows cross-user callback overwrite in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each incoming legacy user request in `h.savedCallbacks[msg.Body.MessageId]` without checking whether an entry for that `MessageId` already exists, and `MessageId` is entirely attacker-chosen client input. Because the map key is not namespaced by sender, two different unprivileged senders can pick the same `MessageId`, and the second request silently clobbers the first request's saved `Callback`, causing the DON's eventual response to be delivered to the wrong caller.

### Finding Description
`h.savedCallbacks` is a `map[string]*savedCallback` keyed only by `msg.Body.MessageId`: [1](#0-0) 

In `HandleLegacyUserMessage`, after validation, the handler unconditionally assigns into the map with no existence check: [2](#0-1) 

`MessageId` is fully client-supplied and validated only for length/format, not uniqueness or binding to sender identity: [3](#0-2) 

The signature in `Message.Sign`/`SignKS` covers `MessageId`, `Method`, `DonId`, `Receiver`, and `Payload`, but it authenticates that *the sender chose this MessageId*, not that the `MessageId` is unique across all senders: [4](#0-3) 

When the DON node eventually responds with `MethodWebAPITrigger`, `handleWebAPITriggerMessage` looks up and deletes the entry purely by `MessageId`, then forwards the response to whichever `Callback` currently occupies that slot: [5](#0-4) 

`pruneCallbacks` runs periodically (every `CallbackPruneIntervalSec`) and only prunes by age/count, providing no defense against an attacker deliberately reusing a live `MessageId`: [6](#0-5) 

Exploit flow:
1. Victim A sends a legitimate `web_api_trigger` request with `MessageId = X`; `HandleLegacyUserMessage` stores `savedCallbacks[X] = victimCallback` and forwards the request to all DON members.
2. Before the DON responds (a window that can be seconds, since responses come from real HTTP calls with attacker/victim-controlled timeouts), attacker B sends their own signed request also using `MessageId = X` (attacker fully controls `MessageId` in their own signed message body).
3. `HandleLegacyUserMessage` for B's request overwrites `savedCallbacks[X]` with `attackerCallback`, with no check that a live entry already exists.
4. When the DON eventually responds for `MessageId = X` (originally for victim A's request, or for either request, since both were forwarded to the DON under the same ID), `handleWebAPITriggerMessage` delivers that response to whichever callback is currently stored — i.e., the attacker's callback — leaking the victim's DON response (which may include the victim's request/response data) to the attacker, or vice versa.

No layer of the gateway enforces per-sender namespacing of `MessageId`, and no check rejects a second `HandleLegacyUserMessage` call reusing an ID with a still-pending callback.

### Impact Explanation
This is a cross-user response confusion within the gateway's legacy capabilities handler: an unprivileged, unauthenticated-relative-to-other-users client can hijack another user's callback slot to receive the DON's execution result intended for a different sender, or cause its own response to be silently dropped/misrouted. This matches Chainlink's bounty impact class for unauthorized access to another user's data/response and broken request isolation, since the invariant "one user's callback state cannot be overwritten by another" is violated by design (map keyed solely on attacker-controlled `MessageId`).

### Likelihood Explanation
- Precondition: attacker only needs the ability to sign and submit gateway messages with an arbitrary `MessageId` of their choosing — any legitimate/unprivileged sender can do this since `MessageId` is user-supplied and only constrained by length (`MessageIdMaxLen`) and null-byte-suffix checks.
- The attacker needs to guess or observe another user's in-flight `MessageId` to specifically target them, which requires some visibility into concurrent MessageIds (e.g. via shared client conventions, sequential/guessable IDs, or observing gateway traffic/logs); this lowers but does not eliminate feasibility for a fully blind attacker, though it is trivially reproducible in a controlled test/PoC or against any deterministic/incrementing MessageId generator used by real clients.
- No rate limiting, allowlist, or authorization check on `HandleLegacyUserMessage` prevents ID reuse before the previous entry is delivered/pruned.

### Recommendation
Reject or namespace duplicate `MessageId`s in `HandleLegacyUserMessage`: before writing to `h.savedCallbacks`, check `if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists { return error/no-op }`, or key the map by a tuple of `(Sender, MessageId)` (or a gateway-generated unique correlation ID) instead of raw client-supplied `MessageId` alone, ensuring one sender cannot ever collide with another's live callback entry.

### Proof of Concept
Go unit test in `handler_test.go`:
1. Construct handler with a mocked `handlers.DON` and mocked `handlers.Callback` (using existing test mocks in the package).
2. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` where `msgA.Body.MessageId = "X"`, signed by sender A. Assert `h.savedCallbacks["X"].Callback == callbackA`.
3. Without triggering `handleWebAPITriggerMessage` (simulating DON response not yet arrived), call `h.HandleLegacyUserMessage(ctx, msgB, callbackB)` with `msgB.Body.MessageId = "X"`, signed by a different sender B.
4. Assert (expected fix behavior) that the second call is rejected and `h.savedCallbacks["X"].Callback` still equals `callbackA` — currently this assertion fails because `callbackB` overwrites `callbackA`.
5. Simulate DON node response for `MessageId = "X"` via `HandleNodeMessage`/`handleWebAPITriggerMessage`, and assert that `callbackA.SendResponse` (not `callbackB.SendResponse`) receives the DON's payload — currently `callbackB` receives it, demonstrating cross-user leakage.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

// Message signatures are over the following data:
//  1. MessageId aligned to 128 bytes
//  2. Method aligned to 64 bytes
//  3. DonId aligned to 64 bytes
//  4. Receiver (in hex) aligned to 42 bytes
//  5. Payload (raw bytes before parsing)
func (m *Message) Sign(privateKey *ecdsa.PrivateKey) error {
	if m == nil {
		return errors.New("nil message")
	}
	rawData := GetRawMessageBody(&m.Body)
	signature, err := gw_common.SignData(privateKey, rawData...)
	if err != nil {
		return err
	}
	m.Signature = utils.StringToHex(string(signature))
	m.Body.Sender = strings.ToLower(crypto.PubkeyToAddress(privateKey.PublicKey).Hex())
	return nil
}

func (m *Message) SignKS(ctx context.Context, ks keys.MessageSigner, signer common.Address) error {
	if m == nil {
		return errors.New("nil message")
	}
	rawData := GetRawMessageBody(&m.Body)
	signature, err := ks.SignMessage(ctx, signer, gw_common.Flatten(rawData...))
	if err != nil {
		return err
	}
	m.Signature = utils.StringToHex(string(signature))
	m.Body.Sender = strings.ToLower(signer.Hex())
	return nil
}
