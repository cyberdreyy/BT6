### Title
Stale single-slot `lastWithdrawRequest` epoch pointer skips `lossRecoveryPriceByEpoch` haircut, letting older pending receipts drain the loss-adjusted funded pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Zebra bug was a wrong-key lookup: code read the tree at tip height instead of the most recent valid height, panicking on stale state. The vault analog is in `IdleCreditVault.requestWithdraw` / `claimWithdrawRequest`: a user's loss-epoch membership is recovered through the single-slot `lastWithdrawRequest[_user]` pointer, and the loss haircut is looked up only via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. Any path that lets a user hold an unclaimed loss-epoch receipt while `lastWithdrawRequest` no longer points at that epoch silently skips the haircut in `_claimLossAdjustedWithdrawRequest` and pays the receipt at par through `_claimFundedWithdrawRequest` — from a funded pool that already had the aggregate `pendingWithdraws` loss deducted in `collectWithdrawFunds`. Early claimants are overpaid; the funded balance runs out and later claimants' `safeTransfer` reverts permanently.

### Finding Description
`collectWithdrawFunds` haircuts the *aggregate* `pendingWithdraws` and stores the ratio under `lossRecoveryPriceByEpoch[epochNumber]` (lines 411-421). Recovery of which epoch a user belongs to is entirely via `lastWithdrawRequest[_user]`:

- `requestWithdraw` (lines 261-271) only blocks a new request when `lossRecoveryPriceByEpoch[lastWithdrawRequest]` is non-zero *and* the user still has `withdrawsRequestsByEpoch[user][lossEpoch] != 0` or a live `apr0Users[user].principal` with `principalEpoch == lossEpoch`.
- `_claimLossAdjustedWithdrawRequest` (lines 789-801) likewise computes the haircut only for `lastWithdrawRequest[_user]`; everything else falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user] + settledPrincipal + principal + settledInterest` at full par (lines 319-349).

Two ways the pointer escapes the loss epoch:

1. **Settled-APR0 receipts evade the guard.** In APR0 mode, when the epoch's stop path settles the APR0 bucket (`prepareStopEpochWithApr0` / `_settleApr0` moving `principal` into `settledPrincipal`/`settledInterest` and clearing `principal`/`principalEpoch`), the guard condition `apr0Users[user].principal != 0 && apr0Users[user].principalEpoch == lossEpoch` is false even though the user's claim basis at the loss epoch is still unclaimed. The user then calls `requestWithdraw` in the next epoch, `lastWithdrawRequest` is overwritten to the new epoch, and the loss-epoch haircut is unreachable.

2. **Cross-epoch receipts lose their epoch identity on claim.** `_clearWithdrawClaimForEpoch` clears only the single `_claimEpoch` resolved from `lastWithdrawRequest`; a user holding receipts in more than one pending epoch has no per-epoch iteration — the mapping key is derived from one stale slot, exactly the "latest key vs. tip key" mistake of the Zebra fix.

Once the haircut is skipped, `_claimFundedWithdrawRequest` burns the receipt and transfers the full basis, while `collectWithdrawFunds` only collected `pendingBasis * lossRecoveryPrice / 1e18`. Since claims are FCFS over one strategy balance, earlier claimants (or the same user) extract more than their haircut share and the pool goes insolvent for the remaining claimants.

### Impact Explanation
Direct insolvency/permanent freezing of unclaimed withdraw yield. After a `stopEpochWithDuration(_lossAmount)` stop, the strategy holds `pendingBasis - pendingLoss` to cover all pending receipts. Each claim that escapes the haircut receives `claimBasis` instead of `claimBasis * lossRecoveryPrice`, so the last claimants' `_transferFundedClaim` → `underlyingToken.safeTransfer` reverts on insufficient balance with no recovery path (their receipts remain burnable but unfunded). Quantified worst case: with pendingBasis P and loss L, up to `L`'s worth of pending receipts can be paid at par, leaving a deficit of `L` shared by whoever claims last.

### Likelihood Explanation
Requires a loss-carrying `stopEpochWithDuration` (honest manager call, within rules — the loss itself is protocol operation, the bug is the distribution afterward) combined with either (a) an APR0-mode user whose principal was settled into `settledPrincipal` at the loss epoch, or (b) any user whose `lastWithdrawRequest` no longer indexes the epoch actually holding their unfunded basis. No privileged misbehavior is needed; the attacker is an ordinary KYC'd lender sequencing `requestWithdraw`/`claimWithdrawRequest` before other claimants.

### Recommendation
Do not recover loss-epoch membership from a single mutable pointer. Either iterate/store the set of a user's unfunded request epochs, or record the haircut directly per receipt: store `lossRecoveryPriceByEpoch` alongside each user's request epoch list (e.g., a per-user array or a `user => epochs` enumerable set) and have `requestWithdraw` revert if *any* unfunded request epoch has a non-zero loss price, and `claimWithdrawRequest` apply the haircut per stored epoch rather than only `lastWithdrawRequest[_user]`.

### Proof of Concept
Foundry fork sketch against `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
function testLossEpochEscapeViaStalePointer() external {
    // APR0 mode vault (unscaledApr == 0) or normal mode with settled receipts.
    // 1. userA deposits, then requestWithdraw in epoch N -> lastWithdrawRequest[A] = N,
    //    withdrawsRequestsByEpoch[A][N] = basis.
    // 2. Run epoch N, then manager calls stopEpochWithDuration with _lossAmount > 0
    //    (or stopEpoch path calling collectWithdrawFunds with _amount < pendingBasis).
    //    -> lossRecoveryPriceByEpoch[N] = p < 1e18; strategy funded with basis*p/1e18.
    // 3. Settle A's apr0 position (claim path or stop-path settlement) so that
    //    apr0Users[A].principal == 0 while settledPrincipal/settledInterest remain.
    // 4. After buffer, startEpoch(); A calls requestWithdraw again:
    //    guard at L263-271 sees principal == 0 -> passes; lastWithdrawRequest[A] = N+1.
    // 5. A calls claimWithdrawRequest:
    //    _claimLossAdjustedWithdrawRequest reads lossRecoveryPriceByEpoch[N+1] == 0 -> skips;
    //    _claimFundedWithdrawRequest pays A's full basis at par.
    // 6. userB with an identical loss-epoch N receipt claims later:
    //    strategy balance is exhausted -> safeTransfer reverts; B's funds frozen.
    assertApproxEqAbs(payoutA, basisA, 5);            // A paid at par, not basisA*p/1e18
    vm.expectRevert();                              // B's claim permanently fails
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertions: `lossRecoveryPriceByEpoch[N] != 0` while `lastWithdrawRequest[A] == N+1`, and the strategy's underlying balance after A's claim is less than `sum(remaining claimBasis * p / 1e18)`, demonstrating the broken one-receipt-one-haircut invariant and insolvency for later claimants.
