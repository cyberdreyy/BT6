Confirmed: the `create` function in `lockup-factory/src/lib.rs` lets any unprivileged caller supply an arbitrary `whitelist_account_id` that becomes the deployed lockup's permanent `staking_pool_whitelist_account_id`, with no validation that it matches the factory's trusted `self.whitelist_account_id`. This is baked into the lockup contract at `new()` and used later by `select_staking_pool`/`is_whitelisted` checks to decide which staking pools are safe to delegate to — an exact analog of the report's "unvalidated data trusted by a later step, unable to be corrected."

### Title
Lockup Factory allows caller-supplied whitelist contract to be baked into a deployed lockup, bypassing NEAR Foundation's staking-pool whitelist - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` accepts an optional `whitelist_account_id` parameter supplied entirely by the (unprivileged) caller who funds the lockup creation. If provided, that value—not the factory's own `whitelist_account_id` set at `init`—is written into the new lockup contract's `staking_pool_whitelist_account_id` field, which is then trusted for the lifetime of the lockup contract.

### Finding Description
`create()` computes `staking_pool_whitelist_account_id` as either the caller-provided `whitelist_account_id` or the factory's own trusted field, defaulting to caller input if present: [1](#0-0) 
This value is serialized straight into `LockupArgs` and passed to the newly created lockup's `new()` constructor: [2](#0-1) 
The lockup contract's `new()` only checks that the value is a syntactically valid account ID — it never checks that it equals any canonical/foundation-approved whitelist: [3](#0-2) 
Once deployed, this `staking_pool_whitelist_account_id` is immutable and is the sole authority the owner's `select_staking_pool` method consults (via `ext_whitelist::is_whitelisted`) to decide whether a staking pool is safe to delegate to — this is the exact custody binding the whitelist contract's own documentation describes as the guarantee that "the lockup contract should be able to recover delegated tokens back to the lockup from a staking pool": [4](#0-3) 

The binding that should hold is:
`lockup.staking_pool_whitelist_account_id == factory.whitelist_account_id` (the NEAR Foundation-controlled whitelist).

Because `create()` lets the funder override this with any account, that equality is broken by construction: `lockup.staking_pool_whitelist_account_id` can be an attacker-deployed contract whose `is_whitelisted` always returns `true`.

### Impact Explanation
This is a "wrongly parameterised deployment" (Critical per the impact classes) — the funding party (who need not be the lockup owner, the foundation, or any privileged role) permanently fixes which whitelist governs staking-pool selection for the lockup's owner. If a funder deploys a lockup for a victim owner (or an owner unknowingly reuses a malicious "helper" front-end) with a spoofed whitelist account, the owner's subsequent `select_staking_pool` + `deposit_and_stake` calls will pass validation against the attacker's fake whitelist and allow delegation of the locked/vested NEAR to an attacker-controlled "staking pool" contract that never returns the funds — a direct path to loss of the locked NEAR, violating the lockup's own documented guarantee ("owner can not lose tokens ... by using methods under the staking section").

### Likelihood Explanation
`create` is a public, `#[payable]` entry point on the lockup factory intended to be callable "by any user" (per `lockup-factory/README.md`), and the vulnerable parameter (`whitelist_account_id`) is an ordinary optional argument with no permission check tying it to the factory's trusted whitelist. No compromise of keys, no owner/foundation privilege, and no unusual conditions are required — only that a funder (attacker, or a compromised/careless front-end used by a legitimate funder) supplies a non-default `whitelist_account_id` when creating the lockup for a given owner.

### Recommendation
Remove the caller-suppliable `whitelist_account_id` override entirely, or if flexibility is required, restrict acceptable values to a fixed set known and approved by the foundation (e.g., only allow `self.whitelist_account_id`, or require this parameter be settable only by the foundation account, not the funder).

### Proof of Concept
1. Foundation deploys `lockup-factory` with `whitelist_account_id = "whitelist.near"` (trusted) via `new()`. [5](#0-4) 
2. Attacker deploys their own contract `evil-whitelist.near` whose `is_whitelisted` always returns `true`.
3. Attacker (as funder) calls:
```
near call lockup.factory create '{"owner_account_id":"victim.near","lockup_duration":"...","whitelist_account_id":"evil-whitelist.near"}' --accountId attacker.near --amount 50000
```
4. The new lockup contract for `victim.near` is deployed with `staking_pool_whitelist_account_id = "evil-whitelist.near"` baked in permanently (verified via `create()`/`new()` code paths cited above).
5. Victim owner later calls `select_staking_pool` pointing at an attacker-controlled "staking pool" account; the lockup queries `evil-whitelist.near.is_whitelisted(...)`, which returns `true`, allowing the owner to `deposit_and_stake` locked/vested NEAR into the attacker's pool, from which it can never be recovered.
