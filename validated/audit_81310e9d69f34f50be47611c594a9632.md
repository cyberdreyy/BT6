### Title
Zip extraction uses raw `file.Name` with no path sanitization or sandbox check, allowing Windows reserved-device-name and long-path/UNC-prefixed entries to hit unexpected or out-of-sandbox paths - (File: helpers/archives/zip_extract.go)

### Summary
`extractZipFile`, `extractZipDirectoryEntry`, `extractZipFileEntry`, and the final `lchmod` pass in `ExtractZipArchive` all call `os.MkdirAll`/`os.Mkdir`/`os.OpenFile`/`os.Chmod` directly on `file.Name` taken from the zip header, with zero validation, joining, or chroot-style prefix check. Unlike the sibling `tarzstd` extractor, which resolves each entry with `filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects results outside `e.dir` (see `commands/helpers/archive/tarzstd/tarzstd_extractor.go:58-64`), the legacy zip path (`ziplegacy` -> `archives.ExtractZipArchive`) has no equivalent containment check.

### Finding Description
The exploitable path is: `ExtractZipFile`/`ExtractZipArchive` in `helpers/archives/zip_extract.go:85-110` iterates `archive.File` and calls `extractZipFile(file)` (line 93), which does: [1](#0-0) 

followed by `extractZipDirectoryEntry`/`extractZipFileEntry`, both of which call `os.Mkdir`/`os.OpenFile` with the raw `file.Name` [2](#0-1) [3](#0-2) . The final loop then calls `lchmod(file.Name, ...)` again on the same raw name [4](#0-3) , and on Windows `lchmod` is a thin wrapper around `os.Chmod(name, ...)` with no path checks at all [5](#0-4) .

The only pre-existing check is `errorIfGitDirectory`, which only rejects paths whose first cleaned component is `.git` [6](#0-5) . There is no check for absolute paths, `..` traversal, reserved Windows device names, or `\\?\`-prefixed long paths. The `pathErrorTracker` (`helpers/archives/path_error_tracker.go`) only exists to deduplicate repeated log lines for the same `os.PathError.Op` — it does not validate or block anything; it can only suppress *logging* of repeated errors, which matters for the "error swallowed" half of the question (see below).

Callers reach this path via `ziplegacy.extractor.Extract`, which ignores its own `e.dir` field entirely and simply calls `archives.ExtractZipArchive(zr)` [7](#0-6) , relying on the process's current working directory instead of resolving/validating paths against a target root — unlike `tarzstd`'s extractor, which explicitly joins to `e.dir` and enforces containment [8](#0-7) . This legacy zip extractor is used for artifact/cache download extraction (`commands/helpers/artifacts_downloader.go`, `commands/helpers/cache_extractor.go`), both of which extract into the job's working directory based on attacker-influenced archive contents (artifacts/cache produced by the job itself, or a crafted cache/artifact uploaded and later downloaded in the same or another stage).

Regarding the specific attacker inputs asked about:
- Windows reserved device names (`CON`, `NUL`, `AUX`, `COM1`, etc.) as `file.Name`: on Windows these are special I/O device names reserved at the filesystem-driver level. `os.Mkdir("CON", ...)` / `os.OpenFile("CON", ...)` will generally fail (return an `os.PathError`, typically "The system cannot find the file specified" or "the parameter is incorrect", not "success"), because they are DOS device names intercepted before reaching the actual filesystem. This produces an error, which is swallowed only in terms of *repeated log noise* (`pathErrorTracker`), not silently "successful" — I could not find any code path where this becomes an actual out-of-sandbox write; it's an error-handling/DoS-adjacent nuisance, not a containment breach.
- `\\?\C:\Windows\System32\evil`-style long-path/UNC-prefixed absolute names: Go's `os` package on Windows passes such strings through largely verbatim to the Win32 API when they already carry the `\\?\` prefix, bypassing `MAX_PATH` and relative-path resolution. Because `zip_extract.go` never checks `filepath.IsAbs(file.Name)` or strips/validates a base directory (contrast with `tarzstd_extractor.go`'s explicit `filepath.Join(e.dir, hdr.Name)` + prefix check), an absolute or `\\?\`-prefixed entry name in the zip **would be used as-is** by `os.MkdirAll`, `os.OpenFile`, and `os.Chmod`. This is a real containment gap, not merely a theoretical one — it is the classic "zip slip" pattern applied to legacy zip extraction, and it is not mitigated by anything else in this file or `path_check_helper.go`.

### Impact Explanation
An attacker who can control the contents of an artifact or cache zip that will later be extracted by the runner's legacy zip extractor (e.g., a job that produces its own cache/artifacts, later restored in a subsequent job/stage on the same runner host or shell/custom executor) can craft entries with absolute or `\\?\`-prefixed Windows paths. Because no root/containment check exists, `os.MkdirAll`/`os.OpenFile`/`os.Chmod` will operate on that literal path rather than a path confined to the build/cache directory — enabling writes/chmods to attacker-chosen filesystem locations reachable by the runner process's privileges (shell executor on a shared host, or any executor where the helper process's OS user has write access outside the job directory). Windows reserved-device-name entries are more likely to just generate (deduplicated) error logs rather than a successful out-of-sandbox write, so that specific sub-claim is largely a nuisance/error-log issue rather than a security bypass.

### Likelihood Explanation
Preconditions: the target must use the legacy zip extractor path for cache/artifact extraction on Windows (or, for the traversal-only variant, any OS), and the archive contents must be attacker-influenced (self-produced artifact/cache, or unrestricted archive re-upload/download flow). This is reachable purely with job-level control over generated cache/artifact contents — no admin privileges needed. It is a real, reachable, unauthenticated-from-Runner's-perspective code path with no test coverage enforcing containment for the zip extractor (`zip_extract_test.go` covers `.git` warnings and basic extraction, not absolute-path or reserved-name entries).

### Recommendation
In `helpers/archives/zip_extract.go`, thread a base extraction directory through `ExtractZipArchive`/`ExtractZipFile` (mirroring `tarzstd_extractor.go`), reject/clean each `file.Name` via `filepath.Join(baseDir, file.Name)` + `filepath.Abs` + prefix/`filepath.Rel` containment check before any `os.Mkdir*`/`os.OpenFile`/`lchmod` call, and explicitly reject or sanitize Windows reserved device names and `\\?\`/UNC-prefixed segments so they cannot resolve to device or system paths.

### Proof of Concept
```go
func TestExtractZipFile_RejectsAbsoluteAndDevicePaths(t *testing.T) {
    sandbox := t.TempDir()
    orig, _ := os.Getwd()
    _ = os.Chdir(sandbox)
    defer os.Chdir(orig)

    buf := new(bytes.Buffer)
    zw := zip.NewWriter(buf)
    for _, name := range []string{
        `\\?\C:\Windows\Temp\evil.txt`, // absolute long-path prefixed
        "CON",                          // Windows reserved device name
    } {
        w, _ := zw.Create(name)
        _, _ = w.Write([]byte("x"))
    }
    _ = zw.Close()

    zr, _ := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    _ = ExtractZipArchive(zr)

    // Assert nothing was written outside sandbox.
    _, err := os.Stat(`C:\Windows\Temp\evil.txt`)
    assert.True(t, os.IsNotExist(err), "file must not exist outside sandbox root")
}
```
Expected (current, buggy) behavior: for the `\\?\C:\Windows\Temp\evil.txt` case, if run with sufficient Windows permissions, `os.MkdirAll`/`os.OpenFile` will attempt to write at that literal absolute path instead of failing/containing it inside `sandbox`, since no join/containment check exists in `extractZipFile`. This confirms the missing sandboxing; the `CON` case is expected to fail with an `os.PathError` (logged once via `pathErrorTracker`), not to succeed, so it does not by itself demonstrate an escape.

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}
