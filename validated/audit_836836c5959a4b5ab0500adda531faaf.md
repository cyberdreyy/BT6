### Title
Stale "current miner" validation not re-checked at pre-commit/signing time allows signing a block from a miner the signer's own state machine has already abandoned - (File: stacks-signer/src/v0/signer.rs)

### Summary
`handle_block_proposal` gates a block against "is this proposal from the active/canonical miner" exactly once, via `check_block_against_state` → `GlobalStateView::check_proposal` (v2) / `SortitionsView::check_proposal` (v1). That gate checks `current_miner_pkh`, `tenure_id` (consensus hash), the pox bitvec, and miner validity (`InvalidMiner`, `ConsensusHashMismatch`, `PubkeyHashMismatch`, `NotLatestSortitionWinner`, `InvalidBitvec`). None of this is re-verified later: both `handle_block_validate_ok` (validate-ok path) and `handle_block_pre_commit` (the pre-commit-threshold path that actually produces the signature) only call `check_block_against_signer_db_state`, which checks tenure-tip/parent-confirmation and signed conflicts — not whether the block's tenure/miner is still the signer's currently active one. Because a block proposal can sit in validation and pre-commit accumulation for an extended period, and the signer's own miner-activity timeout logic can move `current_miner` away from that tenure in the meantime, a signer can end up producing a valid group signature for a block whose miner it has itself already deemed inactive/stale — an order-dependent bypass exactly analogous to the LeXscrow report: a condition that must hold is only checked at one point in an ordered sequence and is silently skipped on the path that leads to the actual irreversible action (signing).

### Finding Description
The proposal-arrival path is:
`handle_block_proposal` → `check_block_against_state` → (v2) `GlobalStateView::check_proposal`, which requires `MinerState::ActiveMiner` and matches the block's consensus hash / miner pubkey hash against the signer's *current* view of the active miner [2](#0-1) . This is the only place these identity/liveness checks are performed.

Later re-checks use a different, narrower function. Both the validate-ok path and the pre-commit-threshold-to-signature path call `check_block_against_signer_db_state`, which only checks tenure-change parent confirmation or own-tenure tip confirmation via `SortitionData::check_tenure_change_confirms_parent` / `check_latest_block_in_tenure` [4](#0-3) . It never re-derives or re-checks `MinerState::ActiveMiner`/`current_miner_pkh`/`tenure_id`, so it cannot detect that the signer's own state machine has since moved its active-miner view elsewhere.

`handle_block_pre_commit`, the function that actually crosses the 70% weight threshold and puts a signature on the block, re-runs exactly this same narrower `check_block_against_signer_db_state`, plus a same/any-tenure signed-conflict scan, immediately before signing [5](#0-4) . It does not consult `self.local_state_machine`/`current_miner` at all.

Independently, the signer's local state machine can move `current_miner` away from a tenure whose proposal is still pending pre-commit accumulation: `check_miner_inactivity` (housekeeping run every `process_event` pass) falls back to the prior tenure once a tenure has gone `block_proposal_timeout` without the signer itself having signed a block in it (`has_signed_block_in_tenure`) [6](#0-5) , and `capitulate_viewpoint` can also adopt a different threshold-weighted miner view from peers [7](#0-6) . Neither of these state transitions revisits or invalidates block proposals already stored as `Unprocessed`/pre-committed for the now-abandoned tenure; those proposals keep accumulating pre-commits from other (possibly slower or partitioned) signers, and once they cross the weight threshold, `handle_block_pre_commit`'s recheck — which never asks "is this still my active miner" — lets the signature through.

The documentation itself confirms the asymmetry as an intentional design gap for a related check (`DuplicateBlockFound`), explicitly noting it is proposal-only and "never runs again," relying on a narrower own-tenure conflict guard to "cover the same ground" [3](#0-2) . That compensating guard, however, only covers same/any-tenure height conflicts against *already-signed* blocks — it says nothing about whether the tenure/miner being signed for is the one the signer's own state machine currently endorses. The active-miner identity checks (`InvalidMiner`, `ConsensusHashMismatch`, `PubkeyHashMismatch`, `NotLatestSortitionWinner`, `InvalidBitvec`) have no compensating re-check anywhere in the validate-ok or pre-commit/signing paths.

### Impact Explanation
This breaks the intended equality "a signature is only produced for a block from the miner/tenure the signer currently considers active and canonical." A signer can be made to sign a block for a tenure it has itself already fallen back away from (via `check_miner_inactivity`) or moved past (via `capitulate_viewpoint`), because the only gate for that fact is evaluated once, long before the signature is actually produced, and is never re-verified on the signing path. This matches the report's "Critical" bucket: a signer signing a non-canonical/stale block due to the conditions check being order/timing-dependent rather than re-verified at the point of the irreversible action.

### Likelihood Explanation
No majority of signers or any other signer's key is required. A single one-slot miner naturally creates the conditions: propose a block early in its tenure, let node validation and cross-signer pre-commit gossip take their course (this can legitimately take a while, especially with a partially slow/partitioned signer subset), while the tenure's own `block_proposal_timeout`/`tenure_last_block_proposal_timeout` elapses for signers that haven't yet signed anything in that tenure. Once enough delayed pre-commits arrive after other signers have already moved `current_miner` on, `handle_block_pre_commit`'s threshold-crossing recheck has no code path that would catch the mismatch.

### Recommendation
Re-derive and re-check the active-miner identity conditions (`MinerState::ActiveMiner` match, `tenure_id`/consensus-hash match, `current_miner_pkh` match, bitvec, sortition-winner validity) inside `check_block_against_signer_db_state` (or an equivalent check invoked from both `handle_block_validate_ok` and `handle_block_pre_commit`), rather than gating on them only once at proposal-arrival time in `check_proposal`. The checks that decide whether a signature is safe to produce should be independent of *when* in the proposal/pre-commit/signing sequence they are evaluated, not split across a one-time proposal-time gate and a narrower recheck used everywhere else.

### Proof of Concept
1. Sortition elects miner `M` for tenure `T` (consensus hash `CH`); all signers' `current_miner` becomes `ActiveMiner{tenure_id: CH, current_miner_pkh: M}`.
2. `M` proposes tenure-start block `B` for `T`. `check_block_against_state`/`check_proposal` passes (pubkey hash, consensus hash, bitvec all match) [8](#0-7) . Node validation succeeds; `handle_block_validate_ok`'s recheck (`check_block_against_signer_db_state`) also passes (no conflicting signed tip yet), so the local signer sends a pre-commit.
3. A subset of signers is slow (network delay/partition) to relay pre-commits, so `B` sits below the 70% weight threshold past `block_proposal_timeout`. Signers that have not signed anything in `T` (`has_signed_block_in_tenure` false) run `check_miner_inactivity` and fall back their `current_miner` to the prior tenure [6](#0-5) .
4. The delayed pre-commits eventually arrive and push `B`'s weight over threshold at some signer. `handle_block_pre_commit` reruns only `check_block_against_signer_db_state` (tenure-tip/conflict checks) [5](#0-4)  — it does not check whether `B`'s tenure `T`/miner `M` still matches that signer's (now-reverted) `current_miner`. The check passes and the signer signs `B`, even though its own state machine no longer endorses `T`/`M` as active.
