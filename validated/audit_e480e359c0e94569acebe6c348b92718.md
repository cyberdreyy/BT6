### Title
Strict-equality "full withdrawal" fast-path in `withdraw_nonce_account` can be griefed by donating dust lamports - (File: `programs/system/src/system_instruction.rs`)

### Summary
`withdraw_nonce_account()` decides whether a withdrawal is a "full drain" of an `Initialized` nonce account using strict equality (`lamports == from.get_lamports()`). An attacker can front-run/grief a legitimate full-withdraw transaction by transferring a small amount of lamports into the target nonce account beforehand, which changes `from.get_lamports()` and forces the withdrawal into the "partial withdrawal" code path that additionally enforces a rent-exemption floor — causing the intended, previously-valid full withdrawal to fail with `InsufficientFunds`.

### Finding Description
`withdraw_nonce_account` branches on whether the requested withdrawal amount exactly equals the current account balance: [1](#0-0) 

```rust
State::Initialized(data) => {
    if lamports == from.get_lamports() {
        // full-drain fast path: no rent-exemption floor enforced,
        // account is de-initialized
        ...
        from.set_state(&Versions::new(State::Uninitialized))?;
    } else {
        // partial withdrawal: must leave at least rent-exempt minimum
        let min_balance = rent.minimum_balance(from.get_data().len());
        let amount = checked_add(lamports, min_balance)?;
        if amount > from.get_lamports() {
            return Err(InstructionError::InsufficientFunds);
        }
        check_signer(&data.authority)?;
    }
}
```

Because a nonce account is a System-Program-owned account, it is reachable by an ordinary `system_instruction::transfer` from any unprivileged account (transfers do not require ownership of the destination account). If the nonce authority builds and signs a transaction that withdraws the *entire current balance* `B` (`lamports == B`), an attacker can, prior to that transaction landing, transfer even 1 lamport to the nonce account. The account's balance becomes `B+1`, so `lamports (== B) != from.get_lamports() (== B+1)`, forcing the "else" branch. There, `amount = B + min_balance`, which is greater than `B+1` for any nonzero `min_balance` (nonce accounts have `NonceState::size()` data and thus a non-trivial rent-exempt minimum), so the instruction now fails with `InstructionError::InsufficientFunds` even though the authorized withdrawer legitimately owns and is entitled to the funds.

This is a direct code-level analog of the CEToken `_removeChain`/`_removeToken` bug pattern: a strict `==` check that models "the balance is exactly X" is defeated by an attacker griefing the account with an unsolicited transfer, causing the code to fall into a path whose invariants ("leave rent-exempt reserve") were never intended for the caller's actual (full-drain) intent.

### Impact Explanation
This is a griefing/denial-of-service vector, not a fund-theft vector: the fee payer's legitimate transaction fails, the transaction fee is still consumed, and the nonce account cannot be closed/drained as intended in that attempt (the caller must retry, e.g., withdraw `B+1` instead once observing the new balance, or attacker can repeat the griefing). It can be used to repeatedly block a specific nonce-account close/withdraw flow (e.g., wallets or programs that pre-compute an exact "withdraw all" amount from a stale read of the account), forcing failed transactions and wasted fees. This matches the "Medium/Acknowledged, no direct fund loss" characterization of the original report.

### Likelihood Explanation
High feasibility, low cost: any unprivileged actor can send 1 lamport via a standard System Program transfer to a publicly-known nonce account address, and does not need any special privilege or timing beyond ordinary transaction ordering/front-running (already common on Solana via priority fees / same-slot ordering). The only precondition is that some client withdraws the *exact current balance* rather than an amount computed at execution time — a common pattern for "close/drain the nonce account" flows.

### Recommendation
Avoid relying on strict equality to detect "full withdrawal" intent. Instead:
- Require callers to explicitly request full withdrawal (e.g., a distinguished sentinel value or explicit close instruction) rather than inferring it by matching the current balance, or
- Recompute "full balance" at execution time from `from.get_lamports()` rather than trusting a caller-supplied literal that can go stale due to griefing, or
- When `lamports != from.get_lamports()`, tolerate donated dust by allowing the withdrawal to still fully close the account (deinitialize state) once remaining balance would be below the rent-exempt minimum, sweeping any low remainder to the recipient rather than failing outright.

### Proof of Concept
1. Nonce account `N` is `Initialized`, authority `A`, balance `B`, holding a durable nonce not yet advanced this slot.
2. `A` submits `withdraw_nonce_account(N, A, B)` intending a full drain (this normally succeeds and skips the rent-exemption floor via the `lamports == from.get_lamports()` branch).
3. Attacker `E` submits an earlier-ordered `system_instruction::transfer(E, N, 1)`, landing before `A`'s withdrawal in the same slot/block.
4. When `A`'s withdrawal executes, `N`'s balance is now `B+1`, so `lamports (B) != from.get_lamports() (B+1)`; the code takes the `else` branch: `amount = B + min_balance > B+1`, so the instruction fails with `InstructionError::InsufficientFunds`, and `A`'s transaction fails despite being a valid, previously-correct full-drain request.
