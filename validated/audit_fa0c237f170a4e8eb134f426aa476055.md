### Title
Unauthenticated `/v2/resume/:runID` endpoint allows any unprivileged actor to resume arbitrary pipeline task runs - (File: core/web/router.go, core/web/pipeline_runs_controller.go)

### Summary
The Chainlink node exposes `PATCH /v2/resume/:runID` on an explicitly unauthenticated router group. Any unprivileged network client who can guess or observe a `taskID` (UUID) can call this endpoint to complete/resume a suspended pipeline task with attacker-controlled result data, without any authentication or ownership check tying the caller to the job/task run being resumed.

### Finding Description
In `core/web/router.go`, the pipeline-runs "resume" route is registered on the `unauthedv2` group, bypassing all of the `auth.Authenticate(...)` middleware (session, API-token, or external-initiator auth) applied to every other `/v2/*` route: [1](#0-0) 

The handler itself, `PipelineRunsController.Resume`, only validates that `runID` parses as a UUID and that the JSON body decodes into a `pipeline.ResumeRequest`; it performs no check that the caller is authorized to act on that particular task/job: [2](#0-1) 

Notably, the audit event fired for this action is literally named `audit.UnauthedRunResumed`, confirming this was consciously designed as an unauthenticated action rather than a hardening gap — but the design still lacks any secondary authorization such as a per-run secret/callback token check, correlating the caller to the specific suspended task (e.g., an `EthCall`/webhook/HTTP fetch task awaiting external callback). This mirrors the Maple `closeLoan()` finding: a state-changing function meant to be triggered only by the legitimate initiator of a paused workflow is instead callable by "anyone," enabling a caller who is not the intended party to force completion of the run with attacker-supplied result data.

### Impact Explanation
An unprivileged network attacker who learns or brute-forces a `runID` (task run UUID) can:
- Force resumption/completion of a job's pipeline task with attacker-supplied JSON `result`/`error` values via `pipeline.ResumeRequest`, corrupting the outcome of the pipeline run (analogous to griefing/state-corruption from unauthorized `closeLoan()`).
- Potentially bypass expected external callback flows (e.g., bridge task callbacks) since the resume payload is attacker-controlled and only "ownership" of a matching UUID gates access — and UUIDs, while hard to guess, may leak via logs, webhooks, or other side channels.
- Since this maps to fund-movement-relevant pipeline tasks (e.g., ETH transaction pipelines depending on resumed data), incorrect/malicious resume data could steer downstream job logic incorrectly, similar to how the Maple bug allowed an unauthorized party to disrupt fund-related contract state.

### Likelihood Explanation
Moderate to Low: exploitation requires knowledge of a valid `runID`, which is a UUID and not guessable by brute force in practice. However, likelihood increases in any scenario where `runID` values are exposed to third parties (e.g., returned in webhook payloads to external services, logged, or otherwise observable), which is a documented use case for suspended/resumable pipeline tasks. The route being fully unauthenticated by design (`unauthedv2`) means the barrier to exploitation is solely "knowledge of the UUID," with zero additional authentication factor required, unlike bridge/task-specific approaches elsewhere in the code that require API tokens or external-initiator secrets.

### Recommendation
- Require the resumer to present a secret/token bound to the specific suspended task at creation time (e.g., a per-run HMAC or resume token issued when the task was suspended), and validate it in `PipelineRunsController.Resume` before calling `prc.App.ResumeJobV2`.
- Alternatively, scope authorization to the External Initiator or user that owns the underlying job (similar to `AuthenticateExternalInitiator` gating job "run" role), rejecting resume requests that don't present a token tied to that job/initiator.
- Rate-limit and audit failed/successful resume attempts by `runID` to detect enumeration/guessing attempts.

### Proof of Concept
1. Identify or intercept a `runID` (UUID) tied to a suspended pipeline task in a Chainlink node (e.g., from a webhook payload sent to an external system awaiting callback).
2. Without any authentication headers, send:
```
PATCH /v2/resume/<runID>
Content-Type: application/json

{"value": {"result": "attacker-controlled-value"}}
```
3. The node accepts and processes the resume immediately via `PipelineRunsController.Resume` → `prc.App.ResumeJobV2`, with no verification that the caller is the legitimate party expected to supply that task's result, as shown in [3](#0-2)  and the unauthenticated route registration in [4](#0-3) .

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
