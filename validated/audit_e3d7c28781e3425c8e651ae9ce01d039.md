### Title
Per-sender rate limit bypass via case/format variation of `body.Sender` string key - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
`triggerConnectorHandler.processTrigger` calls `trigger.rateLimiter.Allow(body.Sender)` using the raw, attacker-supplied `body.Sender` string as the rate-limit bucket key, instead of the normalized `sender` (`ethCommon.Address`) that is already computed and used for the `allowedSenders` authorization check. Because Ethereum hex addresses are case-insensitive at the byte level, a single signer can produce many textually distinct but cryptographically valid `body.Sender` strings (different casing/checksum variants) that all pass signature/authorization checks yet map to independent rate-limit buckets.

### Finding Description
In `HandleGatewayMessage`, the sender is normalized once: `sender := ethCommon.HexToAddress(body.Sender)` [1](#0-0) . This normalized `sender` is what gets passed into `processTrigger` and is used for the authorization check `trigger.allowedSenders[sender.String()]` [2](#0-1) , guaranteeing that the allowlist check is case-insensitive/canonical.

However, immediately after, the rate limiter check uses the raw, unnormalized string instead: `if !trigger.rateLimiter.Allow(body.Sender)` [3](#0-2) . `body.Sender` comes directly from the JSON-RPC gateway request body (`api.MessageBody`) as decoded by `hc.ValidatedMessageFromReq` [4](#0-3) , and is fully attacker-controlled text (whatever string the client places in the signed message body).

Since `ethCommon.HexToAddress` parses hex case-insensitively, a legitimate signer for address `0x853d...39bc5` can submit requests where `body.Sender` is written in different casings (all lowercase, all uppercase, or a non-canonical mixed-case variant) — each of these decodes to the identical 20-byte `common.Address` for authorization purposes, so `allowedSenders[sender.String()]` still succeeds for all variants, and (assuming message validation/signature checks operate on the parsed address rather than exact string equality) the signature check does not reject the differently-cased string either. Because `ratelimit.RateLimiter.Allow` keys its per-sender bucket off the raw string argument, each distinct casing of the same address creates a brand-new, independent token bucket, allowing the attacker to multiply their effective per-sender quota (`PerSenderRPS`/`PerSenderBurst`) by the number of distinct string variants they use.

### Impact Explanation
This is a quota/allowlist rate-limit bypass: a single unprivileged, unauthenticated-but-signed sender can defeat the intended per-sender throttling on the web API trigger gateway path, amplifying load on `trigger.ch` and downstream workflow execution far beyond the configured `PerSenderRPS`/`PerSenderBurst`, while the global rate limiter (if configured with a high enough ceiling) would not catch this. This matches the "allowlist/quota bypass" impact class.

### Likelihood Explanation
Exploitability requires only that the attacker control a private key already present in a workflow's `AllowedSenders` list (i.e., they are already permitted to send trigger requests) — no additional privilege is needed. The attack is trivial to repeat: simply vary the string casing of the sender's hex address field in each signed request payload while keeping the underlying key/signature identical.

### Recommendation
Normalize the sender key before using it for rate limiting — call `trigger.rateLimiter.Allow(sender.String())` (or `sender.Hex()`) using the already-normalized `common.Address` value, consistent with the `allowedSenders` check, instead of the raw `body.Sender` string.

### Proof of Concept
Go unit test plan (extending `core/capabilities/webapi/trigger/trigger_test.go`):
1. Register a trigger with `PerSenderBurst: 1` and `PerSenderRPS` set very low, with `AllowedSenders` containing the canonical address for `privateKey1`.
2. Build two `gatewayRequest`s signed with `privateKey1`, but manually override `msg.Body.Sender` in each to a different case variant of the same address (e.g., lowercase vs. uppercase vs. checksummed) before computing/attaching the signature over the intended fields (or verify the signature validation path tolerates the differing casing).
3. Call `th.trigger.HandleGatewayMessage` for both requests in quick succession.
4. Assert: with the fix, the second request should be rate-limited (`Status: "ERROR"`, rate-limited message) because it shares the same bucket as the first; without the fix, both requests are `Status: "ACCEPTED"` because they land in different rate-limit buckets keyed by the differing `body.Sender` strings.

func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}
