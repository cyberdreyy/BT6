## Title
Account pre-funding griefing causes permanent `CreateAccount` DoS in System Program - (`programs/system/src/system_processor.rs`)

### Summary
The System Program's `create_account` instruction handler rejects account creation whenever the destination account already holds a nonzero lamport balance, treating any positive balance as proof the account is "already in use." Because any unprivileged party can send lamports to an arbitrary pubkey via a normal `Transfer` instruction without the recipient's signature, an attacker can pre-fund a target address with as little as 1 lamport before its legitimate owner attempts to create it, permanently blocking `CreateAccount` at that address and denying service to programs/users who rely on deterministic account creation (e.g. PDAs, escrow accounts, associated accounts).

### Finding Description
`create_account` in `programs/system/src/system_processor.rs` uses the destination account's raw lamport balance as a proxy for "does this account already exist," instead of relying on the account's owner/data state alone: [1](#0-0) 

```
fn create_account(...) -> Result<(), InstructionError> {
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ic_msg!(..., "Create Account: account {:?} already in use", to_address);
            return Err(SystemError::AccountAlreadyInUse.into());
        }
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    transfer(...)
}
```

This is exactly analogous to the reported `LiquidityManager.moveLiquidity()` bug: rather than checking internally tracked/authoritative state (whether the account is actually owned and initialized by a program), the code infers "already in use" purely from an externally-manipulable raw balance (`get_lamports()`), which is the Solana equivalent of `balanceOf(address(this))`.

Any account can receive lamports from a `system_instruction::transfer` without the recipient needing to sign — this is enforced in `transfer_verified`/`transfer`, which only requires the `from` account to sign: [2](#0-1) 

So an attacker can:
1. Compute (or observe) a not-yet-created target address (e.g., a PDA, an associated account, an escrow/vault account whose address is deterministic or publicly known before creation).
2. Submit an ordinary `Transfer` instruction sending 1 lamport to that address.
3. Any subsequent legitimate `CreateAccount` instruction targeting that address (via `system_processor::create_account`) will now see `to.get_lamports() > 0` and fail with `SystemError::AccountAlreadyInUse`, even though the account has no owner or data and was never legitimately initialized.

Because this failure occurs inside `create_account` — not `create_account_allow_prefund` — any protocol or client code path that calls the vanilla `CreateAccount` system instruction (rather than the "allow prefund" variant used e.g. by the BPF upgradeable loader for its own account creation) is vulnerable.

### Impact Explanation
This is a griefing/denial-of-service vector reachable by any unprivileged user via ordinary transaction submission (a `Transfer` instruction), with no special privileges required. It can permanently block account creation at a specific, predictable address, disrupting any protocol logic that depends on deterministic account creation (PDAs, vault/escrow initialization flows, first-time account setup), which mirrors the "liquidity migration DoS" impact in the original report: legitimate state-changing operations revert due to attacker-inflated balance checks.

### Likelihood Explanation
Likelihood is high relative to the original EVM finding: the attack costs only 1 lamport (versus millions of dollars in the original PoC) and requires no special access — just knowledge of the target address before it is created, which is common for PDAs and other deterministically-derived accounts.

### Recommendation
Do not use raw lamport balance as the sole "already exists" signal in `create_account`. Instead, follow the same pattern already implemented in `create_account_allow_prefund` (which skips the zero-lamport check and only validates via `allocate_and_assign`, i.e., checks that account data is empty and owner is the system program) for all account-creation call sites, or require callers who need pre-funding protection to explicitly account for and consume any pre-existing balance instead of treating it as fatal.

### Proof of Concept
1. Derive a target pubkey `T` (e.g., a PDA that a program intends to create later, or any keypair whose public key is known in advance).
2. Attacker submits `system_instruction::transfer(attacker, T, 1)` — no signature from `T` is required.
3. Legitimate party submits `system_instruction::create_account(payer, T, lamports, space, owner)`.
4. `create_account` ( [3](#0-2) ) sees `to.get_lamports() > 0` and returns `InstructionError` wrapping `SystemError::AccountAlreadyInUse`, permanently blocking creation at `T` unless the legitimate party reroutes through a "prefund-aware" creation path.

fn transfer_verified(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.get_data().is_empty() {
        ic_msg!(invoke_context, "Transfer: `from` must not carry data");
        return Err(InstructionError::InvalidArgument);
    }
    if lamports > from.get_lamports() {
        ic_msg!(
            invoke_context,
            "Transfer: insufficient lamports {}, need {}",
            from.get_lamports(),
            lamports
        );
        return Err(SystemError::ResultWithNegativeLamports.into());
    }

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;
    Ok(())
}
