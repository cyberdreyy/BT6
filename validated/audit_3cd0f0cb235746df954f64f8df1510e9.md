### Title
Expensive EIP-8130 authenticator crypto (ecrecover / P-256 / WebAuthn) runs for every account-change entry before fee-cap/balance affordability is checked - ([File: crates/execution/eip8130/src/transaction.rs])

### Summary
`TransactionAuthorizer::authorize_and_apply` performs full cryptographic authentication (secp256k1 `ecrecover`, RIP-7212 P-256 verify, or WebAuthn SHA-256 + P-256 verify, optionally with one level of delegate indirection) for the sender **and** for every `ConfigChange`/`Delegation` entry in an EIP-8130 transaction's `account_changes`, and this all happens *before* `FeeCheck::validate_fees` / `FeeCheck::validate_balance` are run, both on the mempool-admission path (`validate_eip8130_full` in `crates/execution/txpool/src/validator.rs`) and on the block-inclusion path (`crates/common/evm/src/eip8130.rs`).

### Finding Description
`TransactionAuthorizer::authorize_and_apply` ( [1](#0-0) ) recovers the sender (ecrecover) and then walks every `AccountChange` entry, calling `ConfigChangeAuthorizer::authorize_with_account_state` for each `ConfigChange` ( [2](#0-1) ), which in turn dispatches to `ActorAuthorizer::authenticate_actor_with_account_state` → `AuthenticatorDispatch::authenticate` ( [3](#0-2) , [4](#0-3) ). Depending on the wire-supplied authenticator address this runs `ecrecover` (~3,000 gas equivalent), P-256 `verify_prehash` (~6,900), or a full WebAuthn flow (`SHA-256` twice plus P-256 verify) ( [5](#0-4) ) — and one level of "delegate" indirection re-enters the whole authentication path against a second account ( [6](#0-5) ).

None of this authentication work is gated behind an affordability check first. On both call sites:

- Mempool admission: `validate_eip8130_full` calls `TransactionAuthorizer::authorize_and_apply` (line ~1017-1026) and only reaches `FeeCheck::validate_balance` afterward, at line 1125 ( [7](#0-6) ).
- Block execution: the equivalent orchestration in `crates/common/evm/src/eip8130.rs` runs `TransactionAuthorizer::authorize_and_apply` (step 1) before the fee-cap/balance check (step 6) ( [8](#0-7) , [9](#0-8) ).

The only checks that run *before* this expensive authentication step are cheap structural checks (`validate_eip8130_structural`: size limits, call-phase count, static/timestamp validation, and one ecrecover for the wire-level sender signature) ( [10](#0-9) ) — none of which bound the number of P-256/WebAuthn config-change authentications a transaction can force, nor check whether the payer can even afford `gas_limit`. `Eip8130Constants::MAX_ACTORS_PER_ENTRY` bounds actors *within* a single `Create` entry ( [11](#0-10) ), but each `ConfigChange`/`Delegation` batch entry in `account_changes` still forces one full authenticator dispatch, and the transaction can carry multiple such entries, each independently priced only *after* the crypto work has already run.

This mirrors the reported bug class exactly: like WASM decompression running before gas is charged for Stylus activation, here the expensive cryptographic verification (potentially several P-256/WebAuthn verifications plus a nested delegate re-authentication) runs unconditionally before the node confirms the payer can even afford the transaction's `gas_limit` and fee caps.

### Impact Explanation
An attacker can craft EIP-8130 transactions with a payer/sender that cannot actually cover the fee (or is deliberately underfunded), but with several `ConfigChange` entries using the most expensive canonical authenticators (P-256/WebAuthn, optionally through the delegate authenticator to double the work), each with plausible-looking (but ultimately-rejected) signatures. Because `authorize_and_apply` runs to completion — attempting ecrecover/P-256/WebAuthn verification for the sender and for each account-change entry, plus a nested-account state lookup for the delegate path — before `FeeCheck::validate_balance` is ever consulted, every submission burns real CPU cycles on cryptographic verification that the node will discard once the (cheap) balance check finally runs. Submitted at volume (repeated resubmission with different nonces/salts to defeat pool de-duplication, or targeting builders/sequencer nodes directly), this is a computational resource-exhaustion vector against mempool-admission and block-building nodes, consistent with a node-halt/degraded-availability impact class. This is a Medium-severity finding: it is a real, currently-reachable DoS amplification via unprivileged transaction submission, but it does not directly cause fund loss, wrong output, or state corruption.

### Likelihood Explanation
Likelihood is Medium: any anonymous RPC client / txpool submitter can construct such a transaction (EIP-8130 is fork-gated on Zenith but otherwise open to any submitter), and the cost asymmetry (cheap-to-generate garbage signatures that still force full authenticator dispatch vs. relatively expensive P-256/WebAuthn verification) makes this attractive for a griefing campaign. It is somewhat mitigated by pool-level rate limiting/anti-spam elsewhere in the stack and by the fact that the structural pre-check already filters out many malformed transactions, but none of those pre-checks bound authenticator cost or check affordability first.

### Recommendation
- **Short term:** Reorder `validate_eip8130_full` (and the equivalent execution-side orchestration in `crates/common/evm/src/eip8130.rs`) so that `FeeCheck::validate_fees` / `FeeCheck::validate_balance` (or at minimum a cheap worst-case affordability check against `gas_limit * max_fee_per_gas`) runs *before* `TransactionAuthorizer::authorize_and_apply` performs any cryptographic authentication. If per-actor authentication must run before the full intrinsic-gas total is known, use `IntrinsicGasInput::worst_case` to compute a conservative ceiling and reject unaffordable transactions before dispatching to `AuthenticatorDispatch::authenticate`.
- **Long term:** Audit every other computationally expensive, attacker-triggerable native routine in the EIP-8130 pipeline (nested delegate authentication, WebAuthn JSON parsing, multi-entry `account_changes` batches) to ensure a cheap affordability/structural gate always runs first, and add an explicit cap on the number of `ConfigChange`/`Delegation` entries (and thus authenticator dispatches) a single transaction may carry, independent of intrinsic-gas accounting.

### Proof of Concept
1. Construct a `TxEip8130` with a `payer` whose balance is below `(gas_limit + payer_auth_cost) * max_fee_per_gas` (or omit funding entirely).
2. Populate `account_changes` with several `AccountChange::ConfigChange` entries, each with a `signature` blob prefixed by the WebAuthn or P-256 canonical authenticator address and a syntactically valid but ultimately-failing signature/`clientDataJSON` payload (forcing `AuthenticatorDispatch::webauthn`/`p256` to run SHA-256 + P-256 `verify_prehash` before failing).
3. Submit this transaction (structurally valid, so it passes `validate_eip8130_structural`) to `BaseTransactionValidator::validate_one_with_state` / to a builder's block-building loop.
4. Observe that `TransactionAuthorizer::authorize_and_apply` executes every configured authenticator's full verification path for each entry before `FeeCheck::validate_balance` is reached and the transaction is finally rejected — i.e., CPU cost is paid regardless of the (already-known-unaffordable) payer balance.
5. Repeat at volume with fresh nonces/salts to amplify CPU cost imposed on validating nodes/builders without ever paying real gas.

    fn p256(hash: B256, data: &[u8]) -> Result<B256, AuthError> {
        if data.len() != 129 {
            return Err(AuthError::MalformedAuth);
        }
        let (r, s, x, y) = (&data[0..32], &data[32..64], &data[64..96], &data[96..128]);
        Self::p256_verify(hash.as_slice(), r, s, x, y)?;
        Ok(keccak256([x, y].concat()))
    }

    /// Verify a P-256 signature `(r, s)` over `prehash` for public key `(x, y)`.
    /// Enforces low-`s` to match `OpenZeppelin` `P256.verify` (malleability check).
    fn p256_verify(
        prehash: &[u8],
        r: &[u8],
        s: &[u8],
        x: &[u8],
        y: &[u8],
    ) -> Result<(), AuthError> {
        let mut sec1 = [0u8; 65];
        sec1[0] = 0x04;
        sec1[1..33].copy_from_slice(x);
        sec1[33..65].copy_from_slice(y);
        let key =
            P256VerifyingKey::from_sec1_bytes(&sec1).map_err(|_| AuthError::InvalidPublicKey)?;

        let mut rs = [0u8; 64];
        rs[..32].copy_from_slice(r);
        rs[32..].copy_from_slice(s);
        let signature = P256Signature::from_slice(&rs).map_err(|_| AuthError::InvalidSignature)?;
        if signature.normalize_s().is_some() {
            return Err(AuthError::InvalidSignature);
        }
        key.verify_prehash(prehash, &signature).map_err(|_| AuthError::InvalidSignature)
    }

    /// `WebAuthn` authenticator. `data = abi.encode(WebAuthnAuth, x, y)`.
    /// `actorId = keccak256(x || y)`. Mirrors `OpenZeppelin` `WebAuthn.verify`
    /// with `requireUV = false` (as the deployed `WebAuthnAuthenticator`).
    fn webauthn(hash: B256, data: &[u8]) -> Result<B256, AuthError> {
        let decoded = <(WebAuthnAuth, B256, B256)>::abi_decode_params(data)
            .map_err(|_| AuthError::MalformedAuth)?;

        // Canonical-encoding guard. `data` is un-signed, relay-mutable material —
        // the WebAuthn signature commits to the challenge and `clientDataJSON`,
        // not to this outer ABI framing — yet every byte is billed as EIP-2028
        // payload gas. A non-canonical re-encoding (trailing padding or
        // non-minimal dynamic offsets) decodes to the same value and still passes
        // the P-256 check, but changes the transaction hash and inflates
        // sender-intrinsic gas, letting a relayer shrink the execution-gas budget
        // without the key. Requiring the input to equal its canonical ABI
        // re-encoding makes any such mutation invalidate the transaction. Honest
        // producers (Solidity `abi.encode` / `alloy` `abi_encode_params`) always
        // emit this canonical form, so this rejects only malleated blobs.
        if decoded.abi_encode_params() != data {
            return Err(AuthError::MalformedAuth);
        }
        let (auth, x, y) = decoded;

        let auth_data = auth.authenticatorData.as_ref();
        let client_json = auth.clientDataJSON.as_bytes();

        // 37-byte minimum authenticator data (32 rpIdHash + 1 flags + 4 counter).
        if auth_data.len() <= 36 {
            return Err(AuthError::InvalidSignature);
        }
        // Step 11: `"type":"webauthn.get"` at typeIndex.
        Self::contains_at(client_json, &auth.typeIndex, WEBAUTHN_TYPE)?;
        // Step 12: `"challenge":"<base64url(hash)>"` at challengeIndex.
        let mut expected = Vec::with_capacity(WEBAUTHN_CHALLENGE_PREFIX.len() + 44);
        expected.extend_from_slice(WEBAUTHN_CHALLENGE_PREFIX);
        expected.extend_from_slice(URL_SAFE_NO_PAD.encode(hash.as_slice()).as_bytes());
        expected.push(b'"');
        Self::contains_at(client_json, &auth.challengeIndex, &expected)?;
        // Step 16: User Present bit must be set. Step 17 (UV) skipped (requireUV = false).
        let flags = auth_data[32];
        if flags & FLAG_USER_PRESENT != FLAG_USER_PRESENT {
            return Err(AuthError::InvalidSignature);
        }
        // Backup state consistency: BS=1 requires BE=1.
        if flags & FLAG_BACKUP_ELIGIBLE != FLAG_BACKUP_ELIGIBLE && flags & FLAG_BACKUP_STATE != 0 {
            return Err(AuthError::InvalidSignature);
        }
        // Step 19-20: P-256 verify over sha256(authenticatorData || sha256(clientDataJSON)).
        let client_hash = Sha256::digest(client_json);
        let mut signed = Sha256::new();
        signed.update(auth_data);
        signed.update(client_hash);
        let signed = signed.finalize();

        Self::p256_verify(
            signed.as_slice(),
            auth.r.as_slice(),
            auth.s.as_slice(),
            x.as_slice(),
            y.as_slice(),
        )?;
        Ok(keccak256([x.as_slice(), y.as_slice()].concat()))
    }

    fn validate_eip8130_structural(
        &self,
        signed: &Eip8130Signed,
    ) -> Result<(), InvalidPoolTransactionError> {
        let size = signed.encode_2718_len();
        let limit = self.inner.max_tx_input_bytes();
        if size > limit {
            return Err(InvalidPoolTransactionError::OversizedData { size, limit });
        }
        if signed.tx().calls.len() > Eip8130Constants::MAX_CALL_PHASES_PER_TX {
            return Err(Self::eip8130_error("call phase count exceeds maximum"));
        }

        // Single read of the head-block timestamp so the fork gate and the
        // expiry check see the same value even when `on_new_head_block` updates
        // the atomic concurrently.
        let now = self.block_timestamp();
        // Fork gate: EIP-8130 (account abstraction) transactions are only
        // admissible to the pool once the Zenith upgrade is active.
        if !self.chain_spec().is_zenith_active_at_timestamp(now) {
            return Err(InvalidTransactionError::TxTypeNotSupported.into());
        }
        let local_chain_id = self.inner.chain_spec().chain().id();
        signed.validate_static(local_chain_id).map_err(InvalidPoolTransactionError::from)?;
        // The validity window is evaluated in milliseconds against
        // `block.timestamp * 1000`; the fork gate above uses seconds.
        let now_ms = now.saturating_mul(1_000);

            .validate_timestamp(now_ms)
            .map_err(|error| Self::map_timestamp_error(error, signed, now_ms))?;
        Self::validate_eoa_sender_signature(signed)?;
        Self::validate_sender_auth(signed)?;
        Self::validate_payer_auth(signed)?;
        Self::validate_account_changes(signed, local_chain_id)?;
        Ok(())
