### Title
User receives fewer strategy-token receipts than quoted when `trancheAPRSplitRatio` changes before `requestWithdraw` is mined — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCDOEpochVariant.requestWithdraw` / `IdleCDOEpochQueue.requestWithdraw` take only a tranche amount — there is no `minAmountOut`, expected-price, or expected-APR parameter. The amount of underlying-denominated strategy tokens minted to the user as a receipt (`_mint(_user, _amount)` in `IdleCreditVault.requestWithdraw`, lines 243–295) is computed at execution time from the current `trancheAPRSplitRatio` and APR state. An owner/strategy-manager `setTrancheAPRSplitRatio` (or a `stopEpoch`/`startEpoch` that rebalances the ratio, or `setInstantWithdrawParams` flipping the instant-withdraw path) mined between the user's transaction submission and inclusion changes the quantity/type of the receipt the user receives, with no revert.

### Finding Description
In `IdleCreditVault.requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:243–295) the CDO burns `_principal` strategy tokens and mints `_amount` to the user. `_amount` is produced by `IdleCDOEpochVariant.requestWithdraw` using the *current* interest calculation, which depends on `trancheAPRSplitRatio` (AYS mechanism) and management-fee state. The codebase's own test acknowledges this mutability: `test/foundry/IdleCreditVault.t.sol:2889–2896` notes that "between first and second request the AA tranche apr split ratio changes so we need to refetch it" and recalculates `netInterest` because `trancheAPRSplitRatio` changed.

Sequence (running epoch, fixed-APR mode):
1. User simulates `requestWithdraw(X, AATranche)` at the current split ratio → expects receipt amount `R` (principal + net interest).
2. User broadcasts the tx.
3. Manager's routine `setTrancheAPRSplitRatio` (or `setFeeParams`, or `stopEpoch`+`startEpoch` reordering via `epochNumber`) is mined first.
4. User's tx mints a receipt of `R' < R` strategy tokens; there is no slippage check and no revert.

A second variant: during a buffer period with instant withdrawals enabled, the manager's `setInstantWithdrawParams(..., disableInstantWithdraw=true)` mined first silently converts the user's instant request into a normal pending withdraw (`test/foundry/IdleCDOEpochQueue.t.sol:1170–1178` shows exactly this conversion for the queue path), locking funds an extra epoch instead of paying out at `instantWithdrawDeadline` — temporary freezing rather than the instant payout the user saw when signing.

### Impact Explanation
- Yield theft class: the user's receipt is minted at a worse effective price than the quoted one; the delta accrues to the opposing tranche class / feeReceiver accounting. Loss is bounded to the interest portion shifted by the ratio change plus fee delta (e.g., a split move from 90%→10% AA share erases most of the AA interest minted into the receipt).
- Temporary freezing class: instant→normal conversion locks principal for a full `epochDuration`.
- The broken invariant is fair burn: "one receipt, one payout" minted at the price the user agreed to. No `minOut` or expected-epoch parameter lets the user bound it.

### Likelihood Explanation
Medium. The privileged caller is honest — the attack surface is pure transaction-ordering around routine manager calls (`setTrancheAPRSplitRatio`, `setFeeParams`, `setInstantWithdrawParams`, `stopEpoch`/`startEpoch`), which are exactly the calls the threat model says to sequence around. `requestWithdraw` succeeds rather than reverting under all these orderings, so the user has no signal at signing time. Guard analysis: `_checkAllowed`/epoch gating, `nonReentrant`, `_onlyIdleCDO`, and the loss-recovery claim check (lines 261–271) do not prevent a parameter change between submission and mining.

### Recommendation
Add a user-supplied bound: `requestWithdraw(uint256 _amount, address _tranche, uint256 _minStrategyTokensOut)` reverting if the computed receipt is below `_minStrategyTokensOut`, and an `expectedEpoch`/`expectedInstant` flag so a request cannot silently switch between instant and normal settlement. For the queue, record the epoch the user signed for and revert if `epochNumber` or instant-withdraw eligibility changed.

### Proof of Concept
Foundry sketch (extends the harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testRequestWithdrawFrontrunBySplitRatioChange() external {
    // deposits + epoch start as in testClaimWithdrawRequest
    uint256 mintedAA = idleCDO.depositAA(10000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // user previews receipt at current ratio
    uint256 expected = cdoEpoch.maxWithdrawable(address(this), idleCDO.AATranche());

    // manager call mined before user's requestWithdraw
    vm.prank(manager);
    cdoEpoch.setTrancheAPRSplitRatio(newRatioFavoringBB); // shifts interest away from AA

    uint256 actual = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));
    assertLt(actual, expected); // silent under-mint, no revert, user cannot bound loss
}
```

Confidence note: I verified the mutability of the receipt amount via the test-suite acknowledgement (`IdleCreditVault.t.sol:2889–2896`) and the instant→normal conversion (`IdleCDOEpochQueue.t.sol:1170–1178`), but could not re-read the exact `_calcInterest`/`_updateSplitRatio` internals to confirm the manager-callable setter name and precise rounding bounds — the PoC setter call may need adjustment to the actual ratio-update entry point in `IdleCDO.sol`/`IdleCDOEpochVariant.sol`.
