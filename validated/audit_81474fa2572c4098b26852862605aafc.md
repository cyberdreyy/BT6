### Title
Instruction data length truncation to `u16` before summation causes leader/validator cost-model divergence and compute-budget bypass - ([File: runtime-transaction/src/instruction_data_len.rs])

### Summary
`InstructionDataLenBuilder::process_instruction` truncates each instruction's `usize` data length down to `u16` *before* accumulating the running total, rather than summing in a wide type and clamping/saturating only the final result. This mirrors the CVE-2021-43537 bug class (incorrect narrowing of a size value from a wide integer to a narrow one before it is used), and it produces an incorrect (and attacker-influenceable) `instruction_data_len` that feeds directly into the cost-model's `data_bytes_cost` calculation used for block-level cost accounting and per-transaction cost enforcement.

### Finding Description
`InstructionDataLenBuilder` accumulates the total instruction-data length across all instructions in a transaction: [1](#0-0) 

Each instruction's `instruction.data.len()` (a `usize`, since a single instruction can carry up to `solana_instruction::MAX_INSTRUCTION_DATA_LEN`-sized data, ~10KB per instruction per-CPI limits, and the full transaction can be up to `PACKET_DATA_SIZE`, 1232 bytes for legacy packet-based transactions but transaction data can be considerably larger via v1 messages / multiple instructions) is cast to `u16` **before** the saturating add:
```rust
self.value = self.value.saturating_add(instruction.data.len() as u16);
```
Casting `instruction.data.len()` to `u16` first means any individual instruction data length ≥ 65536, or any case where `as u16` truncation causes a wraparound to a small value, silently discards the high bits rather than being clamped to `u16::MAX`. This differs qualitatively from a correct pattern (sum in `u64`/`usize`, then saturate to `u16` once at the end), and is the same "narrow before use" mistake that the CVE bug class describes.

This `u16` value, `TransactionMeta::instruction_data_len`, feeds the cost model's `data_bytes_cost` field: [2](#0-1) [3](#0-2) 

`data_bytes_cost` is one of the components summed into the total transaction cost used for leader-side block-cost-limit enforcement (`TransactionCost::sum()`), and it is derived by dividing `instruction_data_len` by `INSTRUCTION_DATA_BYTES_COST`.

### Impact Explanation
If an attacker can construct a transaction where the truncation causes `instruction_data_len` to wrap to a value smaller than the true total instruction-data size, the cost model under-accounts the transaction's true "data bytes cost," letting the transaction consume more block-cost budget than it is charged for. Since this is used purely for cost accounting/estimation (not consensus-critical fund movement), the practical impact is a leader-side cost-limit/block-packing miscalculation (potential for stuffing more actual instruction bytes into a block than the cost model believes, a resource-accounting bypass) rather than a memory-safety corruption as in the original Firefox bug. This is a legitimate reachable defect but its blast radius is limited to cost-model accuracy, not fund movement, consensus divergence, or CPI privilege escalation.

### Likelihood Explanation
Reaching a truncation requires either (a) a single instruction whose serialized data length exceeds 65536 bytes, or (b) an aggregate of instruction data across many instructions that overflows a `u16` before the `saturating_add` — but because the cast happens per-instruction (each `data.len() as u16`) rather than on the running sum, only individual instructions ≥ 65536 bytes trigger real truncation (the sum itself is protected by `saturating_add` afterward, so instructions of legal size accumulating over 65535 would legitimately saturate to `u16::MAX`, which is the intended/safe behavior). Given that per-instruction data length in Solana is already bounded well below 65536 bytes in normal transaction construction paths (packet size limits, `MAX_INSTRUCTION_DATA_LEN` constraints enforced elsewhere), triggering the truncation specifically (as opposed to the intended saturation) requires an instruction data length that itself must be at least 65536 bytes, which is unlikely to pass earlier transaction-size/packet-size sanitization checks before this code executes. I was not able to fully verify from the available index whether any code path allows constructing an `SVMInstruction` with `data.len() >= 65536` before `InstructionDataLenBuilder` runs (e.g., via `TransactionMeta`/`RuntimeTransaction` construction), so likelihood is uncertain and depends on upstream instruction-data-size sanitization that I could not fully trace with the available tools.

### Recommendation
Change `InstructionDataLenBuilder::process_instruction` to accumulate in a wide integer type (`u64`/`usize`) and only saturate to `u16` once, at `build()` time, e.g.:
```rust
pub struct InstructionDataLenBuilder { value: u64 }
fn process_instruction(&mut self, ...) {
    self.value = self.value.saturating_add(instruction.data.len() as u64);
}
fn build(self) -> u16 {
    self.value.min(u16::MAX as u64) as u16
}
```

#[derive(Default)]

    }

    pub fn build(self) -> u16 {
        self.value
    }
}
