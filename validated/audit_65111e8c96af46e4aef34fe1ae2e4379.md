### Title
Write-off fulfiller can overpay underlying while receiving only the fixed requested tranche amount - ([File: `contracts/IdleCreditVaultWriteOffEscrow.sol`])

### Summary
`IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` permits `_underlyings` to exceed the seller's requested amount, while requiring `_tranches` to equal the full escrowed tranche balance. The fulfiller therefore pays the entire submitted amount but receives only the fixed tranche amount; the excess is distributed to the seller and fee receiver. This matches the external liquidation bug class: a repayment-like caller can transfer more assets than the value of the fixed claim received. [1](#0-0) 

### Finding Description
A write-off request stores two values: the seller's deposited `tranches` and the `underlyings` demanded for those tranches. [2](#0-1) 

During fulfillment, the contract enforces:

```solidity
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
```

This rejects underpayment but deliberately accepts any `_underlyings >= currentRequest.underlyings`. [3](#0-2) 

The contract then pulls the full caller-supplied `_underlyings`, calculates the exit fee on that full amount, sends the remainder to the seller, and returns only `currentRequest.tranches`/`_tranches` to the fulfiller. No additional tranches or other consideration are minted or transferred for the excess payment. [4](#0-3) 

For example, if a request specifies `10,000e18` tranches for `10,000e6` underlying and the fulfiller submits `12,000e6`, the fulfiller still receives only `10,000e18` tranches. With a `0.1%` fee, the seller receives `11,988e6`, the fee receiver receives `12e6`, and the fulfiller permanently loses `2,000e6` relative to the advertised exchange price. The repository's own Foundry test verifies this exact outcome. [5](#0-4) 

### Impact Explanation
An unprivileged fulfiller can transfer an arbitrarily larger amount of underlying than the request price while receiving only the fixed tranche amount. The excess is not refundable because it is immediately sent to the seller and fee receiver. [4](#0-3) 

The loss is directly quantified as:

```text
loss = _underlyings - currentRequest.underlyings
```

The fulfiller's received tranche amount remains unchanged. For the demonstrated `12,000e6` payment against a `10,000e6` request, the excess loss is `2,000e6` underlying before considering the fee distribution. [6](#0-5) 

### Likelihood Explanation
The function is callable by any wallet during a running epoch, including borrowers and third-party buyers. [7](#0-6) 

The vulnerable input is fully caller-controlled and no upper-bound check, expected-price parameter, deadline, or slippage protection prevents an excessive payment. Existing validation only rejects a tranche mismatch or underlying underpayment. [3](#0-2) 

Although the caller supplies the excessive amount, transaction construction errors, stale request assumptions, or malformed integrations can produce the same loss. The code explicitly documents that overpayment is accepted rather than capping the transfer to the request price. [8](#0-7) 

### Recommendation
Require an exact underlying payment:

```solidity
if (
  currentRequest.tranches != _tranches ||
  _underlyings != currentRequest.underlyings
) {
  revert WrongRequest();
}
```

Alternatively, keep the current interface but cap the transfer and fee calculation to `currentRequest.underlyings`, ignoring any larger caller-supplied value. This preserves underpayment protection while eliminating irreversible excess payment. [9](#0-8) 

### Proof of Concept
The following Foundry PoC reproduces the issue within the existing `IdleCreditVaultWriteOffEscrow` test environment:

```solidity
function testFullfillWriteOffRequestOverpayLoss() external {
    uint256 requestedTranches = 10_000e18;
    uint256 requestedUnderlyings = 10_000e6;
    uint256 overpaidUnderlyings = 12_000e6;

    vm.prank(LP);
    escrow.createWriteOffRequest(requestedTranches, requestedUnderlyings);

    deal(address(underlying), borrower, overpaidUnderlyings);

    uint256 borrowerBefore = underlying.balanceOf(borrower);
    uint256 borrowerTranchesBefore = tranche.balanceOf(borrower);
    uint256 lpBefore = underlying.balanceOf(LP);
    uint256 feeReceiverBefore = underlying.balanceOf(TL_MULTISIG);

    vm.startPrank(borrower);
    underlying.approve(address(escrow), overpaidUnderlyings);
    escrow.fullfillWriteOffRequest(
        LP,
        requestedTranches,
        overpaidUnderlyings
    );
    vm.stopPrank();

    uint256 fee = overpaidUnderlyings * escrow.exitFee() / escrow.FULL_VALUE();

    // The borrower paid the full 12,000e6.
    assertEq(borrowerBefore - underlying.balanceOf(borrower), overpaidUnderlyings);

    // The borrower still receives only the fixed 10,000e18 tranche amount.
    assertEq(
        tranche.balanceOf(borrower) - borrowerTranchesBefore,
        requestedTranches
    );

    // The LP and fee receiver absorb the full overpayment.
    assertEq(underlying.balanceOf(LP) - lpBefore, overpaidUnderlyings - fee);
    assertEq(underlying.balanceOf(TL_MULTISIG) - feeReceiverBefore, fee);
}
```

This behavior is already demonstrated by the repository test using `10,000e6` requested underlying and `12,000e6` paid underlying, where the borrower receives only the original `10,000e18` tranches. [5](#0-4)

```text
  /// @notice fulfill the write-off request by buying the escrowed tranche tokens
  /// @param _user address of the user that made the write-off request
  /// @param _tranches amount of tranche tokens to transfer
  /// @param _underlyings amount of underlyings to transfer
  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```

```text
  function testFullfillWriteOffRequestWithUnderlyingOverpay() external {
    uint256 requestedUnderlyings = 10000e6;
    uint256 overpayUnderlyings = 12000e6;
    uint256 requestedTranches = 10000e18;

    vm.prank(LP);
    escrow.createWriteOffRequest(requestedTranches, requestedUnderlyings);
    assertEq(escrow.pendingUnderlyings(), requestedUnderlyings, 'pending underlyings is wrong after overpay request');

    deal(address(underlying), borrower, overpayUnderlyings);

    uint256 balPreBorrower = underlying.balanceOf(borrower);
    uint256 balPreBorrowerTranche = tranche.balanceOf(borrower);
    uint256 balPreLP = underlying.balanceOf(LP);
    uint256 balPreFeeReceiver = underlying.balanceOf(TL_MULTISIG);

    vm.startPrank(borrower);
    underlying.approve(address(escrow), overpayUnderlyings);
    escrow.fullfillWriteOffRequest(LP, requestedTranches, overpayUnderlyings);
    vm.stopPrank();

    (uint256 tranches, uint256 underlyings) = escrow.userRequests(LP);
    assertEq(tranches, 0, 'write-off request tranches is not 0 after overpay fulfill');
    assertEq(underlyings, 0, 'write-off request underlyings is not 0 after overpay fulfill');
    assertEq(escrow.pendingUnderlyings(), 0, 'pending underlyings is not 0 after overpay fulfill');

    uint256 fee = overpayUnderlyings * escrow.exitFee() / escrow.FULL_VALUE();
    assertEq(balPreBorrower - underlying.balanceOf(borrower), overpayUnderlyings, 'borrower balance is wrong after overpay fulfill');
    assertEq(underlying.balanceOf(LP) - balPreLP, overpayUnderlyings - fee, 'LP balance is wrong after overpay fulfill');
    assertEq(tranche.balanceOf(borrower) - balPreBorrowerTranche, requestedTranches, 'borrower tranche balance is wrong after overpay fulfill');
    assertEq(underlying.balanceOf(TL_MULTISIG) - balPreFeeReceiver, fee, 'fee receiver balance is wrong after overpay fulfill');
  }
```
