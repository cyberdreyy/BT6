### Title
Stale confirmations from removed multisig members allow requests to execute below the configured threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
In both `multisig` and `multisig2`, when a member's key/account is removed via the `DeleteKey`/`DeleteMember` action, the contract only purges pending requests that were *originally created* by that key. It does not scan and strip that key's confirmation from *other* pending requests it had merely confirmed. A confirmation recorded by a since-removed member therefore remains permanently counted toward `num_confirmations`, letting a single remaining member "complete" a K-of-N request with fewer live signers than the configured threshold — the same class of bug as the reported liquidation issue: a stale/self-serving state (borrower acting as liquidator; here, a ghost confirmation from a departed signer) is trusted as if it were still a valid, live authorization.

### Finding Description
The intended custody binding is: `confirmations.len() (that execute a request) == number of confirmations from currently valid/live members`. This binding is violated because:

- `confirm()` only checks that the request/confirmations exist and that the caller hasn't already confirmed; it never re-validates that *previously stored* confirmations in the set still belong to members that are currently part of the multisig [1](#0-0) , and the threshold check simply compares `confirmations.len() + 1 >= self.num_confirmations` [2](#0-1) .
- When a key is removed via `DeleteKey`, the cleanup logic filters `requests` by `r.signer_pk == pk` (i.e., only requests *authored* by that key) and removes their confirmations sets — it never removes the deleted key's public key from the `confirmations` HashSet of *other* pending requests it had confirmed: [3](#0-2) .
- The identical pattern exists in `multisig2`'s `delete_member`, which filters outstanding requests by `r.member == member` and clears confirmations only for those, leaving stale confirmations from the removed member on any other requests they had confirmed but not created: [4](#0-3) .

As a result, once a member is removed, any confirmation they left on a still-pending, unrelated request continues to count as a legitimate vote forever, even though that member is no longer a real signer on the account.

### Impact Explanation
This directly matches the Critical impact bullet "a multisig request executed below threshold." A K-of-N multisig is supposed to require K *currently authorized* signers to authorize sensitive actions (transfers, key/member changes, function calls). With the stale-confirmation bug, an action can be executed with as few as `K-1` (or fewer) live signers, because one or more "votes" are ghost confirmations from removed members. This weakens the security guarantee the multisig was deployed to provide and can let a minority of current signers move funds or otherwise act on behalf of the account without reaching the real quorum of live members.

### Likelihood Explanation
This requires no attacker outside the existing membership set and no protocol-level access-key exploitation — it only requires the normal, expected operational sequence of (a) a member confirming a pending request, and (b) that member later being removed via a legitimately-confirmed `DeleteKey`/`DeleteMember` request (a routine event, e.g., offboarding an employee or replacing a compromised key) while other requests remain pending. Because member turnover and pending-but-not-yet-fully-confirmed requests are ordinary occurrences, likelihood of the stale confirmation state arising is high; whether it is then exploited depends on remaining members' behavior, but the vulnerable state itself is easy to reach.

### Recommendation
When executing `DeleteKey` (`multisig`) or `DeleteMember` (`multisig2`), iterate over *all* pending requests' confirmation sets (not just the ones authored by the removed key/member) and remove the deleted signer's entry from each. Alternatively, validate at `confirm()`/execution time that every public key/member present in a request's `confirmations` set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig` with `num_confirmations = 2` and three access keys `K1, K2, K3`.
2. `K2` calls `add_request_and_confirm` for a sensitive `Transfer` request `R` (`confirmations(R) = {K2}`, 1/2).
3. Separately, `K1` and `K3` jointly confirm and execute a `DeleteKey { public_key: K2 }` request, removing `K2` from the account (per `execute_request`'s `DeleteKey` handling, only requests where `signer_pk == K2` are purged; `R` is untouched) [3](#0-2) .
4. `K1` alone calls `confirm(R)`. `confirmations(R)` now has 2 entries (`K2`'s stale one plus `K1`'s new one), satisfying `confirmations.len() + 1 >= num_confirmations` and causing `R` to execute [5](#0-4) .
5. The `Transfer` in `R` is executed with only one currently-valid signer (`K1`) actively confirming, even though the contract requires 2-of-N live signers — the request executed below the configured threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })

            self.requests.remove(&request_id);

        self.members.remove(&member);

        }
