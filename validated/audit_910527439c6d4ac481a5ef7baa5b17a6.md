### Title
Unauthenticated resource-exhaustion of `savedCallbacks` / DON fan-out via unrate-limited `web_api_trigger` messages - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` accepts `web_api_trigger` messages from any external caller of the gateway HTTP endpoint and, aside from a stale-timestamp check, applies no allowlist or rate limiting before storing a `savedCallback` and fanning the request out to every DON member. The code explicitly marks this gap with `// TODO: apply allowlist and rate-limiting here` (line 384), unlike the sibling `handleWebAPIOutgoingMessage` path which calls `h.nodeRateLimiter.Allow(nodeAddr)`.

### Finding Description
The attacker request path is: `network.httpserver.handleRequest` (`core/services/gateway/network/httpserver.go:180-229`) → `gateway.ProcessRequest` (`core/services/gateway/gateway.go:264-276`), which for any legacy-style JSON-RPC request with a valid `DonId`/method calls `h.HandleLegacyUserMessage(ctx, msg, callback)` [1](#0-0)  without any per-sender quota check. `msg.Validate()` only validates message structure/signature format for a legacy request, not identity-based rate limiting [2](#0-1) .

Inside `HandleLegacyUserMessage`, after payload decoding and a staleness check, the code proceeds straight to storing the callback and broadcasting to all DON members, with the rate-limiting/allowlist step explicitly deferred via a TODO comment [3](#0-2) . The message is then saved into the shared `h.savedCallbacks` map keyed only by `msg.Body.MessageId` (attacker-controlled) and fanned out to every DON member [4](#0-3) . `savedCallbacks` capacity is only bounded indirectly by `pruneCallbacks`, which runs on a periodic timer (`CallbackPruneIntervalSec`) and evicts down to `MaxSavedCallbacks/2` by oldest `createdAt` once the map exceeds `MaxSavedCallbacks` [5](#0-4) . This confirms that a flood of unique `MessageId`s can grow the map unbounded between prune ticks and, once pruning kicks in, cause legitimate earlier-submitted (older) callbacks to be evicted before their DON responses arrive — i.e., other users' pending triggers are starved/evicted due to age-based sorting.

By contrast, `handleWebAPIOutgoingMessage`, which handles DON-originated outgoing messages, explicitly rate-limits by `nodeAddr` via `h.nodeRateLimiter.Allow(nodeAddr)` [6](#0-5) , showing the asymmetry the question highlights. Tests in the repo corroborate this is a known, unresolved gap: `handler_test.go` contains the comment "TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated" at the end of the trigger test suite [7](#0-6) . At the HTTP transport layer, only a global request-body-size limiter exists (`MaxRequestBytesLimiter`); no per-caller/per-IP/per-signer throttling is applied before dispatch to `ProcessRequest` [8](#0-7) .

### Impact Explanation
An unprivileged, unauthenticated caller of the gateway's public HTTP endpoint can flood `web_api_trigger` messages with unique message IDs, growing `savedCallbacks` unbounded between prune cycles and forcing every DON member to receive and process each forwarded request via `don.SendToNode` — consuming DON bandwidth/compute. Once `pruneCallbacks` triggers, it evicts the oldest half of `savedCallbacks` by `createdAt`, which can evict legitimate, still-pending callbacks belonging to other (victim) callers whose DON responses have not yet arrived, causing those users' requests to silently fail/time out. This is a resource-exhaustion / availability-degradation impact (denial-of-service against the gateway's callback bookkeeping and DON request bandwidth), not a direct fund-loss or credential-disclosure issue, matching a "Denial of Service" class bounty impact scoped to gateway/DON availability degradation caused by an unprivileged actor.

### Likelihood Explanation
No privileged role, credential, or prior authorization is needed — only reachability to the gateway's public HTTP endpoint, which is the endpoint's designed entry point for external users submitting workflow triggers. The flood is trivially repeatable: an attacker only needs to vary `MessageId` per request to bypass the map's dedup-by-key behavior, and no signature-based identity throttle exists to slow this down. Given the explicit TODO and the confirmed absence of any per-sender limiter in this code path, likelihood is high assuming the deployment doesn't compensate with a network-level (e.g. reverse-proxy) rate limiter — which is a configuration/operational mitigation outside this code.

### Recommendation
Implement the deferred allowlist/rate-limiting check in `HandleLegacyUserMessage` before storing the callback and fanning out to DON members — e.g., reuse or adapt `h.nodeRateLimiter`-style limiting keyed by sender/message signer (as already done in `handleWebAPIOutgoingMessage`), and/or bound `savedCallbacks` insertion by rejecting new entries once at `MaxSavedCallbacks` rather than relying solely on periodic `pruneCallbacks` eviction of the oldest entries.

### Proof of Concept
Go handler-level integration test plan (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` with a small `MaxSavedCallbacks` (e.g., 10) and a long `CallbackPruneIntervalSec` so pruning doesn't run mid-test.
2. Loop-call `handler.HandleLegacyUserMessage(ctx, msg, cb)` in a tight loop (e.g., 10,000 times) from a single unauthenticated context, each with a unique `MessageId` and a valid signature/payload (reusing `triggerRequest` helper), without ever calling any rate-limit-bypassing mechanism.
3. Assert: (a) all calls return `nil` error (no rejection due to rate limiting/allowlist), (b) `len(handler.savedCallbacks)` grows well beyond `MaxSavedCallbacks` before any prune tick fires, (c) after manually invoking `handler.pruneCallbacks()`, verify that early-submitted (oldest) callbacks — simulating legitimate victim requests — are evicted from `savedCallbacks` without ever receiving a DON response, demonstrating starvation of legitimate callers.

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
