### Title
Client-controlled `MessageId` used as sole `savedCallbacks` cache key allows cross-user request/response hijacking - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The specific premise in the question is incorrect: `api.Message.Validate` (core/services/gateway/api/message.go:54-88) does bind `msg.Body.Sender` from the recovered signer before returning success. However, a related and real vulnerability exists downstream: `handler.HandleLegacyUserMessage` stores pending callbacks in `h.savedCallbacks` keyed **only** by the attacker/user-supplied `msg.Body.MessageId`, with no binding to `msg.Body.Sender`, and unconditionally overwrites any existing entry for that ID.

### Finding Description
`Message.Validate` correctly recovers the signer and sets `m.Body.Sender = utils.StringToHex(string(signerBytes))` at [1](#0-0)  before returning `nil`, so the hypothesis that Sender-binding happens too late relative to cache-key use is false.

The real isolation gap is in `HandleLegacyUserMessage`: the pending callback is saved with [2](#0-1) 
which unconditionally writes `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` regardless of whether an entry for that ID already exists, and without ever recording or checking `msg.Body.Sender`. `MessageId` is fully attacker-controlled input (bounded only to ≤128 bytes and no trailing NUL, per `MessageIdMaxLen`/`Validate` checks at [3](#0-2) ), and each message is independently, validly signed by its own sender, so `Validate()`/`ExtractSigner()` succeed for both a victim's message and an attacker's message that reuses the same `MessageId`.

If an attacker submits a second `HandleLegacyUserMessage` request with a `MessageId` matching one already in-flight for another user (same DON/handler instance), the map entry is silently overwritten with the attacker's `handlers.Callback`. When a DON node later responds with that `MessageId`, `handleWebAPITriggerMessage` at [4](#0-3)  looks up and deletes the single map entry and delivers the response to whichever callback currently occupies that slot — potentially the attacker's, even though the DON request was the victim's, or vice versa. There is no per-sender partitioning of the cache and no check-then-set atomicity guarding against overwrite of an existing entry belonging to a different sender.

### Impact Explanation
This breaks request/response isolation between independent web API trigger requests handled by the same capabilities gateway handler/DON: an unauthenticated attacker who can predict or otherwise supply a colliding `MessageId` can cause the victim's job trigger response (which may include job-run output data or execution status) to be delivered to the attacker's registered callback, or cause the victim's callback to receive the attacker's response, creating cross-user response confusion. This maps to a request impersonation / cross-user response disclosure impact class.

### Likelihood Explanation
Exploitability depends entirely on the attacker being able to submit a request with the identical `MessageId` while the victim's request is still pending (default callback lifetime up to `defaultCallbackMaxAgeSec` = 120s, or configured `CallbackMaxAgeSec`). No credentials beyond the ability to send a signed gateway message are required (any address can self-sign). The main constraint is discovering/guessing a live `MessageId`; if client applications generate `MessageId`s in a predictable or low-entropy fashion (sequential counters, timestamps, fixed values), collision is trivial and repeatable. Even with random IDs, the underlying isolation defect (no sender-scoped keying, unconditional overwrite) is a genuine architectural gap independent of ID predictability.

### Recommendation
Scope the `savedCallbacks` cache key to include the sender (e.g., key by `(Sender, MessageId)` or a hash combining both) so that only the original sender's subsequent messages/responses can reference their own callback slot. Additionally, reject or log an error when attempting to insert a callback for a `MessageId` that already has an unexpired entry, instead of silently overwriting it in [2](#0-1) .

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build the `handler` via `NewHandler` with a short `CallbackMaxAgeSec`.
2. Craft `msgVictim := &api.Message{...}` with `Body.MessageId = "X"`, sign with `victimKey`, call `Validate()`, then call `handler.HandleLegacyUserMessage(ctx, msgVictim, victimCallbackMock)`.
3. Craft `msgAttacker := &api.Message{...}` with the same `Body.MessageId = "X"`, sign with a different `attackerKey`, call `Validate()` (assert `msgVictim.Body.Sender != msgAttacker.Body.Sender`), then call `handler.HandleLegacyUserMessage(ctx, msgAttacker, attackerCallbackMock)`.
4. Simulate a DON node response for `MessageId "X"` via `handler.HandleNodeMessage`.
5. Assert that `victimCallbackMock.SendResponse` is never invoked (its entry was silently overwritten) while `attackerCallbackMock.SendResponse` receives the response — demonstrating the victim's registered callback was lost/clobbered by the colliding attacker request.
