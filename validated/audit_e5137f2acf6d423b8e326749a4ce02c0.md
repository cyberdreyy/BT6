This confirms the analog vulnerability. In `multisig2/src/lib.rs`, `delete_member()` only purges outstanding requests **submitted by** the removed member (`r.member == member`), and only removes `num_requests_pk` for that member. It does **not** scan `self.confirmations` for entries where the removed member had confirmed a request **submitted by someone else**. Since `confirmations` is stored as a `HashSet<String>` keyed by the member's serialized identity [1](#0-0) , and `confirm()` only checks membership of the *current* signer via `current_member()` before adding a *new* confirmation [2](#0-1) , previously recorded confirmations from a member who has since been deleted are never invalidated or removed [3](#0-2) . When the confirmation count reaches `num_confirmations`, `execute_request` runs regardless of whether all contributing confirmers are still live members [4](#0-3) .

### Title
Stale confirmations from removed multisig members count toward execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member()` in the `multisig2` contract removes a member and deletes only the requests *they submitted*, but leaves intact any confirmations they previously cast on requests submitted by other members. Those stale confirmations continue to count toward `num_confirmations`, allowing a request to execute with fewer currently-authorized signers than the configured threshold requires.

### Finding Description
The multisig's core custody guarantee is: a request executes only once `num_confirmations` distinct **current** members have confirmed it — i.e. `confirmations counted == live members who confirmed`. The implementation breaks this equality.

`confirm()` increments a `HashSet<String>` of confirmer identities and compares its length to `num_confirmations` [5](#0-4) . `delete_member()` is the only place membership changes are propagated to outstanding state, and it explicitly scopes cleanup to `r.member == member` (i.e. requests the removed member *added*), not requests they merely confirmed [6](#0-5) :
```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
```
Consequently, if member `B` confirms request `R` (submitted by member `A`) before `B` is removed via `DeleteMember`, `B`'s entry remains in `self.confirmations[R]` after removal. A later confirmation by a still-current member `C` can push the count to `num_confirmations` and trigger `execute_request`, even though only one still-authorized member (`C`, plus the already-executed removal action) actually endorsed `R` at execution time.

The equality broken: **confirmations counted (2: B+C) ≠ live members who confirmed (1: C)**, letting a transfer/function-call/key-add action execute below the real live-member threshold.

### Impact Explanation
This maps to the Critical impact category "a multisig request executed below threshold." An attacker (or any dishonest former co-signer) can pre-position a stale confirmation on a pending high-value request, get themselves removed (or wait to be removed for unrelated reasons), and have an accomplice or unwitting remaining member supply the final confirmation — resulting in the multisig moving NEAR/executing privileged actions (`Transfer`, `FunctionCall`, `AddKey`) without truly reaching the configured `k`-of-`n` threshold of live signers.

### Likelihood Explanation
Requires a normal sequence of on-chain calls only (`add_request`, `confirm`, a `DeleteMember` request, another `confirm`) — no privileged access beyond being a current multisig member, which is the expected operating mode of this contract. No redeploy, foundation action, or key compromise needed beyond the multisig's own designed workflow. The original `multisig/src/lib.rs` has a related but narrower gotcha (documented as a "Gotcha" about deleting keys below the confirmation threshold) [7](#0-6) , but `multisig2` additionally never scrubs a removed member's confirmations from requests they did not submit, which is undocumented and more directly exploitable.

### Recommendation
When removing a member in `delete_member()`, iterate all `self.confirmations` entries (not just requests the member submitted) and remove the deleted member's confirmation from every pending request; re-check whether the remaining confirmation count for each affected request still satisfies staleness invariants. Alternatively, re-validate at `confirm()`/`execute_request()` time that every confirming identity stored in `confirmations` is still present in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 2` and members `{A, B, C}`.
2. `A` calls `add_request` to create request `R1` (e.g. `Transfer` of funds to an external account), then `confirm`s it — 1 confirmation (`A`).
3. `B` calls `confirm(R1)` — 2 confirmations recorded (`A`, `B`), but suppose `num_confirmations` was actually 3 at this point (adjust scenario: use 3 members with `num_confirmations=3`, confirmed by `A` and `B`, count = 2, not yet executed).
4. A separate request `R2` = `DeleteMember { member: B }` is submitted and confirmed by the required threshold using still-current members, executing and removing `B` from `self.members` and deleting only requests `B` had *submitted* — `R1` (submitted by `A`) is untouched, and `B`'s confirmation entry inside `self.confirmations[R1]` remains.
5. `C` (still current) calls `confirm(R1)` — count becomes 3 (`A`, `B`, `C`) which meets `num_confirmations = 3`, and `execute_request` fires the `Transfer`, even though `B` is no longer a member and only two live members (`A`, `C`) actually authorized it at execution time.
