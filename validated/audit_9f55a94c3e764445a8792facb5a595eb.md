Confirmed: in both `multisig/src/lib.rs` and `multisig2/src/lib.rs`, `delete_member`/`DeleteKey` only purges requests that were *originated* by the removed member (`r.member == member` / `r.signer_pk == pk`), but does not scrub that member's *confirmations* recorded on requests originated by other members. This is a direct analog of the OpenQ bug: a bookkeeping record (confirmation) survives after the entitlement backing it (live membership) is revoked, and a later privileged operation (`confirm` → `execute_request`) trusts the stale count instead of re-validating against current membership.

### Title
Stale confirmations from removed multisig members can be counted toward the approval threshold, allowing requests to execute below the live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`DeleteMember`/`DeleteKey` removes a member from `self.members` and deletes only the requests *they personally created*, but never removes their entries from `self.confirmations` on other outstanding requests they had previously confirmed. `confirm()` counts `confirmations.len() + 1 >= num_confirmations` without checking that every counted signer/account is still a current member. This lets a request execute with fewer than `num_confirmations` *live* approvals.

### Finding Description
`delete_member` in [1](#0-0)  filters and purges only requests whose original signer (`r.member`) equals the member being removed, then removes the member from `self.members`. It never iterates `self.confirmations` to strip that member's approval from requests created by *other* members. The same pattern exists in the legacy `multisig` contract's `DeleteKey` handler at [2](#0-1) .

`confirm()` then treats the raw size of the stored confirmation set as proof of live approval: [3](#0-2)  — `confirmations.len() as u32 + 1 >= self.num_confirmations` triggers `execute_request` with no re-check that every public key/account in `confirmations` is still in `self.members`.

Binding broken: `confirmations counted == confirmations from currently-live members`. Before a `DeleteMember` action, the invariant `confirmations.get(id).len() <= |members|` holds and every entry corresponds to a still-valid signer. After a member who had confirmed some *other* request is removed, that request's confirmation set still contains the stale entry, so the equality no longer holds — the recorded approval count exceeds the number of members who could still legitimately approve.

### Impact Explanation
This is a Critical-class impact per the given rubric: "a multisig request executed below threshold." Concretely: with `num_confirmations = 3` and 4 members, request R (created by member A) is confirmed by B and C (2/3). Separately, a `DeleteMember{C}` request is created and approved (C is not the requester of R, so R is untouched by the purge in `delete_member`). C is now removed from `self.members` and no longer has multisig authority. The remaining live members are A, B, D. When any one of A/D confirms R, `confirmations.len()==2 (B,C) + 1 == 3 >= num_confirmations`, and `execute_request` fires the transfer/action — even though only 2 of the currently 3 live members (B and the new confirmer) actually approved it, with C's stale confirmation making up the difference.

### Likelihood Explanation
This does not require the foundation, an owner, or any privileged party beyond the multisig's own normal operation: it only requires the ordinary sequence of (1) a member confirming a request, (2) a legitimate `DeleteMember` action removing that member later, and (3) confirming the older pending request. No malicious code, no redeploy, and no cooperation from the removed member is needed — any remaining member (or even an attacker who is a member) can drive the sequence to push a request past threshold using the phantom confirmation.

### Recommendation
When removing a member (`delete_member`/`DeleteKey`), iterate all outstanding requests' confirmation sets and strip the removed member's entry (not just requests they originated), or re-validate at execution time that every entry in `confirmations` still exists in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 4 members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request` for `Transfer{amount}` to `bob()` → `request_id = R`.
3. `B` calls `confirm(R)` → confirmations = `{B}`.
4. `C` calls `confirm(R)` → confirmations = `{B, C}` (2/3, not yet executed) — see the counting logic at [4](#0-3) .
5. Separately, `A` creates and the group approves a `DeleteMember{C}` request; `delete_member` runs and only removes requests where `r.member == C`, i.e. requests C personally created — `R` (created by A) is left untouched, and C's confirmation entry on `R` survives, per [5](#0-4) .
6. `D` (a live member) calls `confirm(R)`. `confirmations.len() (2) + 1 == 3 >= num_confirmations (3)` → `execute_request(R)` runs and the transfer executes, even though C — one of the two confirmations counted — is no longer a member.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
