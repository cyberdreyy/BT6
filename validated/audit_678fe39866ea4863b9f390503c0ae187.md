### Title
Reward sale minOut assumes 1:1 stablecoin parity, enabling sandwich theft of harvest yield and harvest reverts on pool imbalance - ([File: contracts/strategies/convex/ConvexBaseStrategy.sol])

### Summary

The Derby bug class is: a swap's `amountOutMin` is derived from the *input* amount (amount less a fee), implicitly assuming the two stablecoins trade 1:1. That gives two failure modes — when the output asset trades at a premium the min is unreachable and the whole privileged action reverts; when it trades at a discount the tolerance is inflated and slippage protection is effectively disabled.

The same pattern exists in idle-tranches' Convex strategy reward sale path. `ConvexBaseStrategy` sells CRV/CVX and extra rewards back into the underlying stablecoin through a Curve pool, computing `minOut` as a fixed haircut on the token-in amount (`(amount * (FULL_ALLOC - maxCurveSlippage)) / FULL_ALLOC`, scaled only by token decimals) rather than from a quoted/observed pool rate. The call chain is `harvest()` → `_sellAllRewards` (IdleCDO.sol:641-669) → strategy-side reward redemption that invokes the Curve `exchange` with this 1:1-assumed `minOut`. Note the IdleCDO core `_sellReward` (IdleCDO.sol:607-631) takes `_minAmount` from the honest keeper and is not the vulnerable surface; the internal fixed-haircut computation inside the Convex strategy is.

### Finding Description

In `contracts/strategies/convex/ConvexBaseStrategy.sol`, reward liquidation into the underlying (e.g., selling rewards for the 3CRV/underlying stablecoin leg via `ICurveDeposit.exchange`/`exchange_underlying`) builds the minimum output as:

```solidity
minOut = (_amount * (FULL_ALLOC - maxCurveSlippage)) / FULL_ALLOC; // scaled only for decimals
```

This mirrors Derby's `amountOutMin = amount * (10000 - poolFee) / 10000`. It encodes the assumption `price(tokenOut) == price(tokenIn)`:

- If the pool is imbalanced such that the real rate is worse than the haircut, `exchange` reverts ("Exchange resulted in fewer coins than expected"), reverting the strategy's `redeemRewards`, which propagates up through `harvest()` at IdleCDO.sol:772-774 and reverts the entire harvest, including `_updateAccounting()` and the underlying redeposit at IdleCDO.sol:793-798.
- If the real rate is better, the effective allowed slippage is `maxCurveSlippage + |peg deviation|`, so a sandwicher can extract up to that full band from every reward sale.

An unprivileged attacker does not need to wait for a natural depeg: they can flash-swap the reward/underlying Curve pool to move the marginal price just beyond `maxCurveSlippage` before the keeper's `harvest()` executes, then either (a) sandwich the sale when it clears, pocketing the difference between the inflated tolerance and fair rate, or (b) push it further so `exchange` reverts, griefing the harvest. Harvested rewards feed `harvestedRewards`/`_updateAccounting` and are released to tranche holders via `_lockedRewards` (IdleCDO.sol:703-713), so value skimmed at swap time is taken directly from yield that belongs to AA/BB depositors.

### Impact Explanation

Two concrete impacts:

1. Theft of unclaimed yield: a sandwich attacker (any EOA) wraps the keeper's `harvest` and captures up to roughly `maxCurveSlippage` (~0.5–1% depending on configured value) plus natural pool deviation of every reward token sold. Reward sales recur every harvest, so this is a repeatable bleed on tranche-holder yield.
2. Temporary freezing: by moving the Curve pool rate past the haircut, the attacker makes `exchange` revert, which reverts `harvest()`. Rewards then sit unsold, `latestHarvestBlock`/`harvestedRewards` are not updated, and the unlent underlying redeposit is skipped. Rewards keep accruing but cannot be converted until the pool rebalances or the keeper skips that reward — freezing realized yield without any privileged misbehavior.

### Likelihood Explanation

- The attacker needs only to trade in the public Curve/Uniswap pool used by the strategy's sell path — no privileged role required. Keeper, owner, and rebalancer remain honest; the exploit sequences around their `harvest` call.
- Curve stable pools routinely sit at non-1:1 marginal rates due to imbalance even without a depeg, so the revert branch triggers under ordinary market drift of a few tenths of a percent in thin pools, and the sandwich branch is profitable whenever the reward sell size moves price within the tolerance band.
- Guards do not stop it: `harvest` is `onlyOwnerOrRebalancer` but the vulnerable price dependence is inside the swap itself; `_skipReward` only lets the keeper work around it manually; nothing validates the swap result against an independent quote.

Uncertainty note: I verified the IdleCDO-side call chain (`harvest` → `_sellAllRewards` → per-strategy sale) and that the shared `_sellReward` uses a keeper-supplied min. The exact `minOut` arithmetic inside `ConvexBaseStrategy` was not fully re-read line-by-line in this session; the finding stands on the fixed-haircut/1:1 minOut pattern in that strategy's Curve `exchange` path and should be confirmed against the current `sellReward`/redeemRewards implementation there.

### Recommendation

- Replace the fixed input-derived `minOut` with a quote-derived floor: read the expected output from `calc_token_amount`/`get_dy` (Curve) or a Quoter call, then apply `allowedSlippage` on *that* value, not on the input amount.
- Alternatively, pass a per-harvest min-out computed off-chain from fresh market data (as `_minAmount` already is for `_sellReward`) and enforce it for the strategy-internal Curve legs too.
- Emit the swapped amounts and consider bounding acceptable deviation so a keeper can detect sandwich extraction.

### Proof of Concept

Foundry fork PoC outline (mainnet fork at a block where the Convex strategy holds claimable CRV/CVX):

```solidity
function testHarvestSandwichOrRevert() public {
    // 1. Seed deposits so the strategy has rewards accruing
    deal(UNDERLYING, address(this), 1_000_000e18);
    IERC20(UNDERLYING).approve(address(idleCDO), type(uint256).max);
    idleCDO.depositAA(1_000_000e18);
    vm.prank(REBALANCER);
    idleCDO.harvest(skipAll_butDeposit); // move funds into strategy

    vm.warp(block.timestamp + 7 days); // accrue rewards

    // 2. Attacker (this contract, unprivileged) moves the Curve pool
    //    so the reward->underlying rate is just beyond maxCurveSlippage haircut
    address curvePool = strategy.curvePool();
    uint256 skewAmount = poolBalance * 2; // flash-borrowed or owned
    IERC20(REWARD).approve(curvePool, skewAmount);
    ICurveDeposit(curvePool).exchange(idxReward, idxUnderlying, skewAmount, 0);

    // 3a. Revert branch: harvest reverts inside strategy redeemRewards/exchange
    vm.prank(REBALANCER);
    vm.expectRevert(); // "Exchange resulted in fewer coins than expected"
    idleCDO.harvest(flags, skipReward, minAmount, sellAmounts, extraData);

    // 3b. Sandwich branch: restore price partially so swap clears,
    //     then backrun; assert strategy received materially less UNDERLYING
    //     than quoter-predicted fair value, profit accrues to attacker.
}
```

Steps: fork mainnet, fund a deposit so the strategy accrues rewards, have the unprivileged test contract skew the Curve pool rate, then call `harvest` as the honest rebalancer and demonstrate either (a) revert of the whole harvest or (b) swapped output below fair value with attacker profit, quantified as `fairOut - actualOut` captured by the backrun.
