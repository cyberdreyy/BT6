### Title
`getServicesDefinitions` bypasses `AllowedServices` for job-declared services whose `Name` collides with an admin-configured internal service - ([File: executors/docker/services.go])

### Summary
`getServicesDefinitions` builds `internalServiceImages` purely from the *string* `Name` field of admin-configured `[[runners.docker.services]]` entries, then passes that list to `e.verifyAllowedImage` as a short-circuit allowlist for job-declared `Build.Services`. Because the match is done by name equality only, with no provenance/identity check, a job that declares a service whose `Name` is identical to an internal service name is treated as "already trusted" and skips the `AllowedServices` pattern check entirely, even though the object actually appended to `serviceDefinitions` is the raw, attacker-controlled `spec.Image` from `e.Build.Services` — not the admin's own definition.

### Finding Description [1](#0-0) 

The flow is:
1. `internalServiceImages` is populated from `e.Config.Docker.GetExpandedServices(...)`, i.e. admin `config.toml` `[[runners.docker.services]]` entries — trusted, admin-only input.
2. For every job-declared service in `e.Build.Services` (fully attacker-controlled via `.gitlab-ci.yml` `services:` keyword, including `name`, `alias`, `entrypoint`, `command`, `variables`, `pull_policy`), `e.verifyAllowedImage(service.Name, "services", AllowedServices, internalServiceImages)` is called.
3. If `service.Name` string-matches any entry in `internalServiceImages`, the internal-image short-circuit in `verifyAllowedImage` accepts it regardless of whether it matches any pattern in `AllowedServices`.
4. Critically, on success the code does **not** substitute the admin's trusted service definition — it appends the job's own `service` struct (`serviceDefinitions = append(serviceDefinitions, service)`, line 95) to the list that is later passed to `createFromServiceDefinition`.

This conflates "image name equals an admin-configured internal service name" with "this is the admin's trusted service instance." An unprivileged pipeline author who knows or guesses the exact `Name` string used in an admin's `[[runners.docker.services]]` block (these are often predictable, e.g. `postgres:14`, `redis:7`, or an internal registry path referenced in shared CI templates/docs) can declare a service with that same `Name` but with attacker-controlled `entrypoint`, `command`, `variables`, and `alias`. Because the name matches `internalServiceImages`, `verifyAllowedImage` accepts it even if that same image is deliberately excluded from `AllowedServices` (i.e., the admin never intended users to be able to request that image as a job-controlled service with custom command/entrypoint).

`AllowedServices` is the intended enforcement boundary for "what service images/commands a job may request"; the internal-image bypass in `verifyAllowedImage` was not designed to grant job authors full control over an internal service's runtime parameters — only to avoid double-restricting images the admin already runs — but the implementation performs no distinction between "this is literally the admin's configured instance" and "a job merely typed a matching string."

### Impact Explanation
An unprivileged job can obtain execution of a container using an image the admin never listed in `AllowedServices`, with job-controlled `Command`/`Entrypoint`/`Variables`/`Alias` fields, purely by matching an internal service's `Name` string. This is a concrete `allowed_services` restriction bypass, letting an attacker run arbitrary commands inside a trusted image the runner operator did not intend to expose to arbitrary job configuration control.

### Likelihood Explanation
Requires the runner's `config.toml` to define `[[runners.docker.services]]` (common in shared-runner setups for standard DB/cache services) and requires the attacker to know or guess the exact `Name` string used there. Since these names are frequently standard/well-known image tags (`postgres:14`, `mysql:8`, etc.) or leak via documentation/templates, this is feasible and deterministically repeatable once the name is known.

### Recommendation
Do not use bare `Name` string equality to grant a bypass of `AllowedServices`. Either:
- Only allow the internal-image bypass when the job-declared service definition is structurally identical to the admin's configured entry (no attacker-supplied `Command`/`Entrypoint`/`Variables` overrides), or
- Track internal services by index/identity rather than by name, and merge only the permitted overridable fields (e.g., `alias`) into the trusted definition instead of substituting the entire job-supplied `spec.Image`.

```go
func TestGetServicesDefinitions_InternalNameCollisionBypassesAllowedServices(t *testing.T) {
    e := &executor{
        AbstractExecutor: executors.AbstractExecutor{
            Build: &common.Build{
                JobResponse: common.JobResponse{
                    Services: common.Services{
                        {Name: "postgres:14", Command: []string{"sh", "-c", "attacker-payload"}},
                    },
                },
            },
            Config: common.RunnerConfig{
                RunnerSettings: common.RunnerSettings{
                    Docker: &common.DockerConfig{
                        Services:       common.Services{{Name: "postgres:14"}}, // admin-configured internal service
                        AllowedServices: []string{"redis:*"},                   // postgres NOT allowed
                    },
                },
            },
        },
    }

    defs, err := e.getServicesDefinitions()

    // Expected (secure) behavior: reject, since "postgres:14" is not in AllowedServices
    // and the job-declared entry is not actually the admin's trusted instance.
    assert.Error(t, err)
    assert.Empty(t, defs)

    // Actual behavior observed: err is nil and defs contains the attacker-controlled
    // Command override for "postgres:14", proving the bypass.
}
```

```go
func (e *executor) getServicesDefinitions() (spec.Services, error) {
	var internalServiceImages []string
	serviceDefinitions := spec.Services{}

	for _, service := range e.Config.Docker.GetExpandedServices(e.Build.GetAllVariables()) {
		internalServiceImages = append(internalServiceImages, service.Name)
		serviceDefinitions = append(serviceDefinitions, service.ToImageDefinition())
	}

	for _, service := range e.Build.Services {
		err := e.verifyAllowedImage(service.Name, "services", e.Config.Docker.AllowedServices, internalServiceImages)
		if err != nil {
			return nil, err
		}

		serviceDefinitions = append(serviceDefinitions, service)
	}

	servicesLimit := e.Config.Docker.GetServicesLimit()
	if servicesLimit >= 0 && len(serviceDefinitions) > servicesLimit {
		return nil, &tooManyServicesRequestedError{requested: len(serviceDefinitions), allowed: servicesLimit}
	}

	return serviceDefinitions, nil
}
```
