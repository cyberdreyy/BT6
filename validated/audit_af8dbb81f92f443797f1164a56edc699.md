### Title
Deny-List v2 Signing Check Blocks Withdrawal of Already-Accumulated Regulated-Coin Balance — (`crates/sui-types/src/deny_list_v2.rs`)

---

### Summary

`check_coin_deny_list_v2_during_signing` applies the same deny-list gate to both (a) regulated-coin objects used as transaction inputs and (b) `FundsWithdrawalArg` inputs that withdraw a sender's own already-accumulated address-balance. Once an address is added to the deny list, it cannot submit any transaction that carries a `FundsWithdrawalArg` for that coin type, even to reclaim funds that were deposited before the denial. The accumulated balance is locked for as long as the deny-list entry persists.

---

### Finding Description

**Step 1 – Withdrawal types are collected and fed into the signing check.**

In `handle_coin_deny_list_checks` (`crates/sui-core/src/authority.rs` lines 1191–1202), every `FundsWithdrawalArg` in the transaction is resolved and its inner `Balance<T>` type parameter is extracted into `funds_withdraw_types`:

```rust

    .values()

            .map(|ty| ty.to_canonical_string(false))
    })
    .collect::<BTreeSet<_>>();

That set is then forwarded to `check_coin_deny_list_v2_during_signing`.

**Step 2 – The signing check merges withdrawal types with input-object coin types and denies the sender.**

Line 126 (`coin_types.extend(funds_withdraw_types)`) is the root cause: it causes the sender's address to be checked against the deny list for every coin type it is trying to *withdraw from its own accumulator*, not just for coin types it is receiving or spending as objects.

**Step 3 – Confirmed by the framework's own transactional test.**

The test `coin_deny_and_undeny_address_balance_receiver.move` deposits regulated coins into address B's accumulator, then denies B. After the epoch boundary, B attempts to withdraw its own accumulated balance:

```
//# programmable --sender B
//   --inputs withdraw<sui::balance::Balance<test::regulated_coin::REGULATED_COIN>>(1) @A
//> 0: sui::balance::redeem_funds(Input(0));
//> 1: sui::balance::send_funds<...>(Result(0), Input(1));
```

The snapshot records the result:

```
Error: Error checking transaction input objects:
  Address @B is denied for coin object(1,0)::regulated_coin::REGULATED_COIN
``` [3](#0-2) 

The rejection happens at signing, before execution, so no gas is consumed and no state changes occur — the funds simply remain inaccessible.

---

### Impact Explanation

Any address that holds a non-zero `Balance<T>` in the address-balance accumulator for a regulated coin type, and is subsequently added to that coin's deny list, cannot submit a transaction containing a `FundsWithdrawalArg` for that type. Because `redeem_funds` / `balance::send_funds` are the only public paths to move accumulator-held regulated-coin balances, the funds are locked for the entire duration of the deny-list entry. If the coin issuer never removes the entry, the lock is permanent. This satisfies the **permanent fund lock** impact class in the allowed-impact gate.

---

### Likelihood Explanation

The scenario requires:
1. A regulated coin whose issuer uses `deny_list_v2_add` — a standard, documented feature.
2. The target address having previously received that coin via `balance::send_funds` into the accumulator.

Both conditions are ordinary usage paths. The accumulator-based transfer flow (`send_funds` / `redeem_funds`) is the primary mechanism for address-balance regulated-coin transfers, so any issuer who denies an active user will trigger this lock without any special exploit.

---

### Recommendation

Separate the deny-list gate for *withdrawal* from the gate for *input objects and receiving*. Specifically, `funds_withdraw_types` should **not** be merged into the signing-time deny-list check for the sender's own address. The rationale is that a `FundsWithdrawalArg` represents the sender reclaiming funds already credited to their own accumulator — an operation semantically distinct from spending or receiving a regulated coin object. If regulatory policy requires freezing accumulated balances as well, a dedicated, explicitly documented flag or a separate check path should be used so that the two concerns do not share a single gate.

Concretely, remove or condition line 126 in `crates/sui-types/src/deny_list_v2.rs`:

```rust
// Before (locks accumulated balance of denied sender):
coin_types.extend(funds_withdraw_types);

// After (only check withdrawal recipient, not the withdrawing sender):
// Do not extend coin_types with funds_withdraw_types here.
// Apply a separate, opt-in check if the issuer explicitly wants to freeze accumulator balances.
``` [4](#0-3) 

---

### Proof of Concept

The framework's own transactional test already demonstrates the issue end-to-end:

1. **Publish** a regulated coin; mint 10 000 units to address A.
2. **Deposit** 2 units into address B's accumulator via `balance::send_funds` (tasks 2 and 4 in the snap).
3. **Deny** address B with `coin::deny_list_v2_add` (task 3).
4. **Advance epoch** so the deny-list entry takes effect for receiving (task 6).
5. **Attempt withdrawal** from B's accumulator (task 8):
   ```
   programmable --sender B
     --inputs withdraw<sui::balance::Balance<REGULATED_COIN>>(1) @A
   > 0: sui::balance::redeem_funds(Input(0));
   > 1: sui::balance::send_funds<REGULATED_COIN>(Result(0), Input(1));
   ```
6. **Observed result**: signing-time rejection — `Address @B is denied for coin REGULATED_COIN` — even though B is the rightful owner of the accumulated balance and is not receiving any new coins. [5](#0-4) [3](#0-2) 

The accumulated balance (2 units of `REGULATED_COIN`) remains locked in B's accumulator with no available withdrawal path for the duration of the deny-list entry.

pub fn check_coin_deny_list_v2_during_signing(
    address: SuiAddress,
    input_objects: &CheckedInputObjects,
    receiving_objects: &ReceivingObjects,
    funds_withdraw_types: BTreeSet<String>,
    object_store: &dyn ObjectStore,
) -> UserInputResult {
    let mut coin_types =
        input_object_coin_types_for_denylist_check(input_objects, receiving_objects);
    coin_types.extend(funds_withdraw_types);

    for coin_type in coin_types {
        let Some(deny_list) = get_per_type_coin_deny_list_v2(&coin_type, object_store) else {
            continue;
        };
        if check_global_pause(&deny_list, object_store, None) {
            return Err(UserInputError::CoinTypeGlobalPause { coin_type });
        }
        if check_address_denied_by_config(&deny_list, address, object_store, None) {
            return Err(UserInputError::AddressDeniedForCoin { address, coin_type });
        }
    }
    Ok(())
}
