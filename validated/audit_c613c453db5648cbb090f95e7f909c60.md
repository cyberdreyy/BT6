### Title
GraphQL `createCSAKey` mutation lacks role-based authorization, allowing view/run-role users to create a new CSA key - ([File: core/web/resolver/mutation.go], [File: core/web/router.go])

### Summary
The `/query` GraphQL route is protected only by `auth.AuthenticateGQL`, which authenticates the caller but performs no role check, and the `CreateCSAKey` resolver / `CSAKeyResolver` types in `core/web/resolver/csa_keys.go` contain no authorization logic before invoking the keystore. This contrasts with the equivalent REST endpoint `POST /v2/keys/csa`, which is explicitly wrapped with `auth.RequiresEditRole`.

### Finding Description
`core/web/router.go` registers the GraphQL endpoint with only authentication middleware and no role gate: [1](#0-0) 

Compare this to the REST CSA-key creation route, which explicitly enforces edit role before allowing key creation: [2](#0-1) 

The GraphQL resolver types backing `createCSAKey` (`CreateCSAKeyPayloadResolver`, `CreateCSAKeySuccessResolver`, etc.) contain no role/authorization checks — they only wrap the key/error for presentation: [3](#0-2) 

A search for authorization-related identifiers (`authenticated`, `hasRole`, `requireEditOrAdmin`, `Authorize`) across `core/web/resolver/*.go` matches only in `_test.go` files (i.e., only in test assertions), not in any production resolver source file such as `mutation.go` or `csa_keys.go`. This indicates that role enforcement is not implemented at the GraphQL resolver layer at all — only session/token *authentication* (via `auth.AuthenticateGQL`) gates the `/query` endpoint, not *authorization* by role. Since GraphQL mutations are dispatched generically through the single `/query` route and `graphqlHandler`, there is no per-operation role wrapper analogous to `auth.RequiresEditRole`/`auth.RequiresAdminRole` used throughout the REST v2 routes.

As a result, any authenticated session or API token — regardless of assigned role (view or run) — that can reach `/query` can execute `mutation { createCSAKey { ... } }`, and the resolver will call through to `App.GetKeyStore().CSA().Create()` without an intervening role check.

### Impact Explanation
A view-role or run-role credential holder (the lowest privileged authenticated actor) can create a brand-new CSA (oracle identity) key on the node. This is an unauthorized-key-generation / privilege-escalation impact: CSA keys are used to identify/authenticate the node as an oracle to feeds managers and could be swapped into node configuration, enabling identity confusion or unauthorized participation as an oracle if the newly created key is later adopted. This matches the "unauthorized creation of a sensitive key/credential due to authorization bypass" bounty class.

### Likelihood Explanation
Precondition is minimal: any valid authenticated session or API token with view or run role (the least-privileged roles) is sufficient — no admin/edit privileges required. The attack is a single POST to `/query` with the `createCSAKey` mutation, fully repeatable, and requires no race conditions, timing, or special network position.

### Recommendation
Add explicit role checks inside GraphQL mutation resolvers that modify state (especially key management mutations like `CreateCSAKey`, `DeleteCSAKey`, and other key-creation/import/export mutations) by inspecting the authenticated user/role from context (as already done for REST equivalents via `auth.RequiresEditRole`/`auth.RequiresAdminRole`), returning an authorization error for insufficient roles before calling into `App.GetKeyStore()`.

### Proof of Concept
1. In `core/web/resolver/csa_keys_test.go` (or a new test), construct a GraphQL test client authenticated with a user/session whose role is `view` (or `run`) only.
2. Execute the mutation:
```graphql
mutation {
  createCSAKey {
    ... on CreateCSAKeySuccess {
      csaKey { id publicKey }
    }
  }
}
```
3. Assert that `App.GetKeyStore().CSA().Create()` is NOT invoked, and that the GraphQL response contains an authorization error (e.g., `"Unauthorized"`), matching the pattern already used for admin-only REST routes in `resolver_test.go` (`authenticated`/role assertions).
4. Currently, with the code as-is, this call succeeds and returns a `CreateCSAKeySuccess` payload with a newly generated CSA key — demonstrating the missing role check.

// -- CreateCSAKey Mutation --

type CreateCSAKeyPayloadResolver struct {
	key *csakey.KeyV2
	err error
}

func NewCreateCSAKeyPayload(key *csakey.KeyV2, err error) *CreateCSAKeyPayloadResolver {
	return &CreateCSAKeyPayloadResolver{key: key, err: err}
}

func (r *CreateCSAKeyPayloadResolver) ToCreateCSAKeySuccess() (*CreateCSAKeySuccessResolver, bool) {
	if r.key != nil {
		return NewCreateCSAKeySuccessResolver(r.key), true
	}

	return nil, false
}

func (r *CreateCSAKeyPayloadResolver) ToCSAKeyExistsError() (*CSAKeyExistsErrorResolver, bool) {
	if r.err != nil && errors.Is(r.err, keystore.ErrCSAKeyExists) {
		return NewCSAKeyExistsError(r.err.Error()), true
	}

	return nil, false
}
