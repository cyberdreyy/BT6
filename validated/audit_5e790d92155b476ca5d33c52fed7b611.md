### Title
Stale per-epoch instant-withdraw receipt is double-paid from the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` records the receipt in three ledgers: the aggregate `instantWithdrawsRequests[user]`, the per-epoch `instantWithdrawsRequestsByEpoch[user][epoch]`, and `instantWithdrawClaimsByEpoch[epoch]`. The normal claim path `claimInstantWithdrawRequest` clears only the aggregate counter (the "folio" reference) but never clears the per-epoch entries (the "page" references). If the borrower defaults and `finalizeDefaultRecovery` runs while `epochNumber` is still the request epoch, `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch entry and pays the user a second time out of `defaultRecoveryReserve` — the exact analog of the kernel's mismatched `get_page()`/`page_ref_inc()` vs single `put_page()` over-release.

### Finding Description
- Request: `requestInstantWithdraw` increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, and `pendingInstantWithdraws` [1](#0-0) .
- Normal claim: `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]`, zeroes it, and pays via `_transferFundedClaim`, but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` untouched [2](#0-1) .
- Default path: when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, `_claimDefaultedInstantWithdrawRequest` re-reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, decrements the aggregate (which is already 0 → underflow or, worse, deducts a *different* user's later receipt), burns `claimBasis` receipt tokens the user no longer holds, and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve` [3](#0-2) .
- `defaultRecoveryEpoch` is set to the *current* `epochNumber` at finalization [4](#0-3) , and `epochNumber` only advances on `deposit()` during a running epoch [5](#0-4) . A mid-epoch default therefore lands `defaultRecoveryEpoch` on the same epoch where the stale entry lives.
- The stale entry is also counted twice in the recovery denominator: `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` (which still includes the already-paid claim) whenever `pendingInstantWithdraws != 0` [6](#0-5) , and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as reserve even though part of that basis was already claimed [7](#0-6) .

Broken invariant: one receipt, one payout. The receipt was "released" once via the aggregate counter but remains releasable again via the per-epoch counter — a refcounting mismatch identical in structure to CVE-2024-53138.

### Impact Explanation
An unprivileged KYC'd lender double-claims an instant withdrawal: once at par pre-default, and again at `defaultRecoveryPrice` post-default from the recovery reserve. Each double payout directly steals `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` underlying reserved for other defaulted claimants, and the inflated `instantWithdrawClaimsByEpoch` basis simultaneously dilutes `defaultRecoveryPrice` for every legitimate claimant. Net effect: direct theft from the isolated default-recovery reserve plus mispriced recovery for all tranche holders.

### Likelihood Explanation
Requires: instant withdrawals enabled, an attacker instant request funded and claimed, and a borrower default finalized before `epochNumber` advances (no intervening `stopEpoch`/deposit-while-running). `defaultInstantWithdrawsFinalized` additionally needs `pendingInstantWithdraws != 0` at finalization — the attacker can guarantee this with a second, deliberately unclaimed instant request, since `pendingInstantWithdraws` is only reduced by `collectInstantWithdrawFunds` [8](#0-7) . All steps are ordinary user/CDO calls in a running epoch; the honest-actor constraint holds (manager/CDO only performs the routine default flow). Note `_claimDefaultedInstantWithdrawRequest` underflows `instantWithdrawsRequests[_user] -= claimBasis` when it is 0 — on Solidity ≥0.8 this reverts, so the double-pay only lands when the attacker also holds a fresh aggregate balance (e.g., the second unclaimed request), which the attack already requires.

### Recommendation
In `claimInstantWithdrawRequest`'s funded path, clear the per-epoch ledgers alongside the aggregate: zero `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` (guarding the epoch key — e.g., store the request epoch per user or iterate via `lastWithdrawRequest`-style tracking). Alternatively, make `_claimDefaultedInstantWithdrawRequest` skip entries whose `instantWithdrawsRequests[_user]` basis was already consumed. Add an invariant test: after a funded instant claim, `instantWithdrawsRequestsByEpoch[user][epoch]` must be 0.

// Setup: epoch variant CDO + IdleCreditVault strategy, instant withdrawals enabled.

// 1. Epoch N running. Attacker (KYC'd AA holder) requests instant withdraw of X.
cdoEpoch.requestInstantWithdraw(xAmount, address(AAtranche));
//    instantWithdrawsRequests[atk]=X, ByEpoch[atk][N]=X, claimsByEpoch[N]+=X

// 2. CDO funds the request (collectInstantWithdrawFunds pulls X from idleCDO,
//    pendingInstantWithdraws -= X). Attacker claims at par:
cdoEpoch.claimInstantWithdrawRequest();   // pays X via _transferFundedClaim
//    instantWithdrawsRequests[atk]=0  but ByEpoch[atk][N] still == X   <-- stale ref

// 3. Attacker files a second instant request Y that stays unfunded
//    (CDO never calls collectInstantWithdrawFunds for it) so pendingInstantWithdraws > 0.
cdoEpoch.requestInstantWithdraw(yAmount, address(AAtranche));

// 4. Borrower defaults mid-epoch; CDO calls finalizeDefaultRecovery.
//    defaultRecoveryEpoch == N; defaultInstantWithdrawsFinalized == true.
//    instantWithdrawClaimsByEpoch[N] (still includes X+Y) inflates totalBasis.

// 5. Attacker claims again:
cdoEpoch.claimInstantWithdrawRequest();
//    _claimDefaultedInstantWithdrawRequest reads ByEpoch[atk][N]=X  (stale)
//    instantWithdrawsRequests[atk] = Y - X accounting mixes the two receipts;
//    attacker walks away with X funded + (X+Y)*recoveryPrice instead of Y*recoveryPrice.
//
// assertEq(underlying.balanceOf(attacker), X + (X + Y) * defaultRecoveryPrice / 1e18);
// Honest defaulted claimants' reserve is short by X * defaultRecoveryPrice / 1e18.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
