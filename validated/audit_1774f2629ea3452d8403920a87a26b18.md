### Title
Distinguishable "Invalid email" vs "Invalid password" responses in `CreateSession` enable account enumeration - (core/sessions/localauth/orm.go)

### Summary
`CreateSession` returns different, attacker-visible error strings depending on whether the submitted email exists in the `users` table, and these errors are passed unmodified to the HTTP client by `SessionsController.Create`. An unauthenticated caller can therefore enumerate valid node-admin emails and observe timing differences (bcrypt only runs for valid emails), without ever supplying a correct password.

### Finding Description
`CreateSession` first looks up the user by email via `FindUser`/`findUser` (`core/sessions/localauth/orm.go:144-148`); if the SQL query returns no row, the raw DB error is returned immediately, before any bcrypt work is performed [1](#0-0) . If the email does exist, the code proceeds to a `constantTimeEmailCompare` check (always true since the SQL lookup was already case-insensitive) and, on password mismatch, explicitly returns `pkgerrors.New("Invalid password")` only after running `utils.CheckPasswordHash` (a bcrypt comparison) [2](#0-1) . These two code paths produce (a) different error text ("no matching user"/DB error vs. "Invalid password") and (b) measurably different latency (bcrypt vs. no bcrypt).

The HTTP handler `SessionsController.Create` forwards the `err` from `CreateSession` verbatim to the client via `jsonAPIError(c, http.StatusUnauthorized, err)` with no normalization [3](#0-2) . There is no rate limiting, generic error normalization, or artificial delay equalization in this path, so nothing in the auth middleware or presenter layer stops the leak.

Regarding the MFA-challenge concern in the question: `SessionsController.Create` does call `GetUserWebAuthn(ctx, sr.Email)` unconditionally before invoking `CreateSession` [4](#0-3) , but that result is only used internally to populate `sr.SessionStore`/`sr.WebAuthnConfig` and is not returned to the caller. Inside `CreateSession`, the WebAuthn-challenge JSON response is only reachable after the password check succeeds (`CheckPasswordHash` must pass) [5](#0-4) , so an attacker who does not know the password cannot use this path to detect MFA status. The exploitable leak is limited to the email-existence signal from "Invalid email"/DB-not-found vs. "Invalid password", plus the associated timing side-channel.

### Impact Explanation
This is an account/email enumeration vulnerability, not a direct authentication bypass. An attacker can determine which email addresses correspond to real node-admin/API users, which is a reconnaissance step for credential-stuffing or targeted phishing/social-engineering against those confirmed accounts. It does not by itself grant session forgery, MFA bypass, or credential disclosure, and does not satisfy the stricter bounty impact classes (auth bypass, role bypass, secret disclosure, fund movement). Under the stated rules ("Reject ... without exploitable impact"), enumeration alone is a low-severity information-disclosure issue rather than a qualifying critical/high finding, since it requires an additional, independent step (obtaining a valid password or leveraging phishing) to produce concrete impact.

### Likelihood Explanation
No preconditions or credentials are needed — this is reachable by any unauthenticated caller of `POST /sessions`, and is trivially repeatable (send arbitrary emails, diff response body/timing). Feasibility is high; however, actual damage requires further out-of-scope attacker action (password guessing/credential stuffing or social engineering), so the standalone severity remains limited to information disclosure.

### Recommendation
Return a single, generic "invalid email or password" error for both the "email not found" and "password mismatch" branches in `CreateSession`, and perform a constant-time dummy bcrypt comparison when the email is not found so response timing is equalized between the two cases. Ensure `SessionsController.Create` does not forward internal error text verbatim to the client.

### Proof of Concept
Table-driven test in `core/sessions/localauth/orm_test.go` (or handler-level test in `core/web/sessions_controller_test.go`):
1. Seed one known user with a hashed password.
2. Call `CreateSession` with (a) a non-existent email + any password, and (b) the known email + wrong password.
3. Assert both calls currently return distinguishable error strings ("no matching user"/DB error vs. "Invalid password") — this demonstrates the enumeration primitive.
4. Optionally measure wall-clock time for both calls over N iterations and assert there is a statistically significant difference (bcrypt cost) confirming the timing side-channel.
5. After the fix, assert both paths return an identical generic error string and comparable timing (within a small tolerance).
