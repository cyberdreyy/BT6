### Title
Unregistered/arbitrary `req.Method` is fanned out to all DON nodes before any method validation - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`handler.HandleJSONRPCUserMessage` performs no check of `req.Method` against `h.Methods()` (`MethodSecretsGet`, `MethodCapabilityExec`) before calling `newActiveRequest` and `fanOutToNodes`. Any JSON-RPC request that reaches this handler — including one with an attacker-chosen, unregistered method string — is registered as an active request and broadcast via `h.don.SendToNode` to every DON member, with method validation only happening implicitly and much later inside `bundler.Bundle`.

### Finding Description
`HandleJSONRPCUserMessage` only validates `req.ID` (non-empty, ≤200 chars) before immediately calling `h.newActiveRequest(req, callback)` followed by `h.fanOutToNodes(ctx, l, ar)`: [1](#0-0) 

`h.Methods()` returns the registered method list, but it is never referenced anywhere in `HandleJSONRPCUserMessage`, `newActiveRequest`, or `fanOutToNodes`: [2](#0-1) [3](#0-2) 

`fanOutToNodes` unconditionally sends `&ar.req` (attacker-supplied body, with an arbitrary `Method` field) to every member of `h.donConfig.Members` via `h.don.SendToNode`, with only per-node send timeouts and a failure-count threshold — no method check.

The only place method routing to a handler is gated is in `multiHandler.getHandler` (`core/services/gateway/multihandler.go`), which looks up `methodToHandler[method]` built from each handler's `Methods()`. Critically, that lookup is bypassed entirely when only one handler type is configured: [4](#0-3) 

So in any DON configuration where the confidential-relay handler is the sole registered handler (a supported, non-misconfiguration setup used "for cases where only one handler is registered"), `getHandler` returns the handler directly for *any* method string, with zero validation against the registered `Methods()` list. Control then reaches `HandleJSONRPCUserMessage` with a completely attacker-controlled `req.Method`, which is neither checked there nor anywhere before fan-out. The request is only rejected later, inside `h.bundler.Bundle`'s method-specific switch (not shown in this file but referenced via the `relayBundler` interface at line 152-154), which triggers only after DON members have already been sent the raw request and have already begun processing/responding to it.

This means an unauthenticated/unprivileged gateway client can submit `req.Method = "unregistered.method"` (or any junk method) with an arbitrary JSON body, and the gateway will: (1) accept and track it as an active request, (2) broadcast it to every DON node, and (3) only discover it's invalid after the DON has already spent resources on it (each node must parse/route/reject the message itself) and only fails locally in the gateway once `Bundle`'s default case runs on collected responses.

### Impact Explanation
This is a resource-exhaustion / DoS amplification vector against gateway and DON nodes: an attacker can force the gateway to fan out arbitrary bogus requests to every member of a DON without any pre-validation, multiplying a single attacker request into N node-directed messages and consuming per-node send slots, rate-limiter tokens (`globalNodeRateLimiter`/`perNodeRateLimiters`), and `activeRequests` map entries (bounded only by request timeout expiry) before any rejection occurs. It also exposes DON members to attacker-chosen, completely unvalidated method/payload combinations. This does not, on its own, break confidentiality/integrity or lead to fund loss or credential exposure — it maps to a resource-exhaustion / availability-degradation impact class rather than a compromise-severity one.

### Likelihood Explanation
Reachability requires (a) attacker access to submit a JSON-RPC user message to the gateway for this DON (this is the normal unauthenticated/whatever-auth-tier client entry point for gateway JSON-RPC requests) and (b) the confidential-relay handler being the only handler registered for that DON — a legitimate, documented configuration path (`multiHandler.getHandler`'s single-handler shortcut), not a misconfiguration. Given that, the exploit is trivial and fully repeatable: any request with a fresh `req.ID` and an arbitrary `Method` will pass straight through to `fanOutToNodes`.

### Recommendation
Add an explicit method-allowlist check at the top of `HandleJSONRPCUserMessage` (e.g., `if !slices.Contains(h.Methods(), req.Method) { return h.sendResponseAndClearRequest(ctx, ..., h.constructErrorResponse(req, api.UnsupportedMethodError, ...)) }`) before `newActiveRequest`/`fanOutToNodes` are invoked, so invalid methods are rejected immediately without registering active-request state or contacting any DON node. Additionally, consider removing or gating the single-handler bypass in `multiHandler.getHandler` so it still validates against the registered method set rather than unconditionally routing all traffic.

### Proof of Concept
Go handler-level unit test in `core/services/gateway/handlers/confidentialrelay/handler_test.go`:
1. Construct a `handler` with a mock `gwhandlers.DON` (asserting `SendToNode` is never called) and a mock `relayBundler`.
2. Call `h.HandleJSONRPCUserMessage(ctx, jsonrpc.Request[json.RawMessage]{ID: "test-id", Method: "unregistered.method"}, callback)`.
3. Assert:
   - `don.SendToNode` was never invoked (fails today because it's invoked once per DON member).
   - `h.activeRequests` does not contain `"test-id"` after the call (fails today because `newActiveRequest` inserts it unconditionally).
   - The callback received an `UnsupportedMethodError`/equivalent response immediately, without any node round trip.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) fanOutToNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var (
		group      errgroup.Group
		nodeErrors atomic.Uint32
	)

	// Each send is bounded independently. A node whose websocket accepts no writes blocks
	// until its context is cancelled, and because the caller only reads the response callback
	// after this function returns, an unbounded send would hold the request open until the
	// client gives up, discarding a bundle that already reached quorum.
	sendCtx, cancel := context.WithTimeout(ctx, h.nodeSendTimeout)
	defer cancel()

	for _, node := range h.donConfig.Members {
		group.Go(func() error {
			err := h.don.SendToNode(sendCtx, node.Address, &ar.req)
			if err != nil {
				nodeErrors.Add(1)
				l.Errorw("error sending request to node", "node", node.Address, "error", err)
			}
			return nil
		})
	}

	_ = group.Wait()

	numNodeErrors := nodeErrors.Load()
	remainingPossibleResponses := len(h.donConfig.Members) - int(numNodeErrors)
	if remainingPossibleResponses < h.donConfig.F+1 && numNodeErrors > 0 {
		return h.sendResponseAndClearRequest(ctx, ar, h.constructErrorResponse(ar.req, api.FatalError, errors.New("failed to forward user request to nodes")))
	}

	l.Debugw("successfully forwarded request to relay nodes")
	return nil
}

func (m *multiHandler) getHandler(method string) (handlers.Handler, error) {
	// If there's only one handler, return it directly.
	// This preserves backwards compatibility for cases where the method
	// isn't specified on responses (and for cases where only one handler is registered more generally).
	if len(m.typeToHandler) == 1 {
		for _, handler := range m.typeToHandler {
			return handler, nil
		}
	}

	handler, ok := m.methodToHandler[method]
	if !ok {
		return nil, errors.New("no handler found for method " + method)
	}

	return handler, nil
}
