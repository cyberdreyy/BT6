### Title
External Initiator credentials can trigger job runs on any job (no EI-to-job binding check) via synthetic run-role user - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` sets both `SessionExternalInitiatorKey` and a generic `SessionUserKey` (`&clsessions.User{Role: clsessions.UserRoleRun}`) on every successful EI authentication. Because `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser(c)` (which reads `SessionUserKey`) to decide whether to treat the caller as a "user" and run the int-ID job-run path, an EI-authenticated request is indistinguishable from a real user and is allowed to trigger a run for *any* numeric job ID, not just a job bound to that EI.

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) authenticates the EI access key/secret and, in addition to setting `SessionExternalInitiatorKey`, unconditionally sets: [1](#0-0) 
a bare `User{Role: UserRoleRun}` with no `Email`/`ID`, intended only to satisfy `RequiresRunRole` gating on the route.

The route `POST /v2/jobs/:ID/runs` is registered in the `userOrEI` group with all three auth methods (EI, token, session) and gated only by `auth.RequiresRunRole`: [2](#0-1) 

`RequiresRunRole` only checks `user.Role != UserRoleView`; it has no notion of *which* job the caller is entitled to run, and it operates purely on the synthetic user object set by `AuthenticateExternalInitiator`: [3](#0-2) 

Inside `PipelineRunsController.Create`, the handler branches on `isUser := auth.GetAuthenticatedUser(c)` with the comment "only users are allowed to run jobs using int IDs - EIs not allowed": [4](#0-3) 
However, because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `GetAuthenticatedUser` returns `ok=true` for EI-authenticated requests too — the code's own intent ("EIs not allowed" for int-ID job runs) is defeated by the synthetic user injection at `auth.go:148`. As a result, any valid EI credential can call `RunJobV2(ctx, jobID, nil)` for an arbitrary job ID, with no check that the job is the one the EI is registered/bound to.

### Impact Explanation
An external-initiator credential holder (a low-privilege, narrowly-scoped credential meant to trigger runs only for the webhook job it was created for) can trigger job runs for *any* job on the node by ID, including jobs belonging to other bridges/initiators. This is an authorization-bypass / cross-tenant unauthorized action: unauthorized triggering of another job's execution using a credential not scoped to that job, matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: possession of any single valid EI access key/secret pair (which by design is a narrowly-scoped, lower-trust credential distributed to external initiator services). The attack is a single unauthenticated-in-effect HTTP call: authenticate with EI headers and `POST /v2/jobs/{anyJobID}/runs`. It is deterministic and repeatable for any job ID that exists, requiring no race conditions, timing, or privileged access.

### Recommendation
In `PipelineRunsController.Create`, distinguish real users from EI-authenticated callers by checking `auth.GetAuthenticatedExternalInitiator(c)` first (or checking that `SessionExternalInitiatorKey` is absent) rather than relying solely on `GetAuthenticatedUser`. Alternatively/additionally, stop `AuthenticateExternalInitiator` from populating `SessionUserKey` with a full "run" user, and instead have `RequiresRunRole`/downstream handlers explicitly authorize EI callers against the specific job's registered external initiator (verify the job's webhook/EI spec references the authenticated `ei.Name`/ID before invoking `RunJobV2`).

### Proof of Concept
Handler-level integration test plan (Go, using existing `cltest` helpers similar to `core/web/pipeline_runs_controller_test.go`):
1. Create two webhook jobs, Job A and Job B, each with a distinct external initiator webhook spec; register External Initiator `EI-A` bound conceptually to Job A only.
2. Authenticate an HTTP client using `EI-A`'s access key/secret via the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`).
3. Send `POST /v2/jobs/{JobB.ID}/runs` with `EI-A`'s headers.
4. Assert current (buggy) behavior: response is `200`/`201` and a pipeline run is created for Job B (`prc.App.PipelineORM().FindRun` returns a run tied to Job B), proving cross-job run triggering.
5. Assert expected/fixed behavior: response should be `401`/`403` (or the run should only be permitted for the job bound to `EI-A`), i.e. `isUser` should be `false` for `GetAuthenticatedUser(c)` when only an EI context is set, or the handler should validate the job's EI matches the authenticated initiator before calling `RunJobV2`.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
