## Title
Stale confirmations from a removed multisig key/member are still counted toward `num_confirmations`, letting a request execute below the current live-signer threshold - (`File: multisig/src/lib.rs`, `multisig2/src/lib.rs`)

## Summary
The reported Aries Markets bug is a class where an action commits to using a value (the minted LP tokens) as if an earlier-checked precondition still held, without re-validating that assumption at the point the value is actually consumed. The same bug class exists in this repository's multisig contracts: a confirmation recorded by a public key/member is trusted forever once stored, even after that key/member is removed from the multisig via `DeleteKey`/`DeleteMember`. `DeleteKey`/`DeleteMember` only purges *requests originated by* the removed signer, not *confirmations cast by* that signer on other still-pending requests. When threshold is later reached, `confirm()` only counts `confirmations.len()`, without checking whether those confirming keys/members are still valid, so a request can execute with fewer live confirmations than `num_confirmations` requires.

## Finding Description
In `multisig/src/lib.rs`, `confirm()` decides to execute purely from confirmation-set size: [1](#0-0) 

When a key is removed via the `DeleteKey` action, only pending requests *authored* by that key are cleaned up (`r.signer_pk == pk`); confirmations that the removed key placed on requests authored by *other* keys are left untouched in the `confirmations` map: [2](#0-1) 

The same gap exists in `multisig2/src/lib.rs`. `delete_member` only removes requests whose creator (`r.member`) equals the removed member, not requests the removed member merely confirmed: [3](#0-2) 

and `confirm()` there likewise trusts the raw confirmation count: [4](#0-3) 

The binding that should hold is:
```
count(confirmations on request R from currently-valid members) >= num_confirmations
```
But because stale confirmations aren't purged when a signer is removed, what is actually checked is:
```
count(confirmations on request R, including from removed members) >= num_confirmations
```
These two values diverge as soon as any confirming key is removed from the multisig while its confirmation on an unrelated pending request is still outstanding.

## Impact Explanation
This lets a `MultiSigRequest` (e.g., a `Transfer` of NEAR, an `AddKey`, or a `FunctionCall`) execute with fewer currently-authorized signers than `num_confirmations` mandates — i.e., "a multisig request executed below threshold," which is explicitly called out as a Critical impact. Funds can move, or new keys/members can be added/removed, based on approval from a party no longer entitled to approve anything for the account.

## Likelihood Explanation
This requires no attacker-controlled deployment, foundation, or victim key — it only requires the multisig's own documented, unprivileged member workflow: any member requests removal of another member's key (a routine security/operational action, e.g., off-boarding), while an older unrelated pending request already carries that member's confirmation. This is a realistic sequence in any long-lived multisig with several outstanding requests and periodic membership rotation, and is achievable purely by the normal legitimate members interacting with the contract's public API (`add_request`, `confirm`, `DeleteKey`/`DeleteMember`) — no external compromise needed.

## Recommendation
When executing `DeleteKey` (`multisig/src/lib.rs`) or `DeleteMember` (`multisig2/src/lib.rs`), also scrub the removed key/member's confirmation from every other pending request's confirmation set (not just requests it authored), or alternatively re-validate at `confirm()`/execution time that every entry in the confirmation set still corresponds to a current member/key before comparing the count to `num_confirmations`.

## Proof of Concept
1. Multisig initialized with `num_confirmations = 3` and members `K1, K2, K3, K4`.
2. `K4` calls `add_request` creating Transfer request `R` (confirmations = {}).
3. `K1` calls `confirm(R)` → confirmations = `{K1}` (1 < 3, no execution).
4. `K2` calls `confirm(R)` → confirmations = `{K1, K2}` (2 < 3, no execution).
5. Separately, `K1, K3, K4` create and confirm a `DeleteKey{K2}` request, which reaches 3 confirmations and executes, revoking `K2`'s access key. Per `multisig/src/lib.rs` lines 198-216, only requests *authored* by `K2` are purged — `R` (authored by `K4`) is untouched, so its confirmation set still contains `K2`.
6. `K3` calls `confirm(R)`. `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` per `multisig/src/lib.rs` line 255, so `R` executes — even though only `K1` and `K3` are currently valid signers who approved it (2 of 3 live confirmations), because `K2`'s stale confirmation was counted.     pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
