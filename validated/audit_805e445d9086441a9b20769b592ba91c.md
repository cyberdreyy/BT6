### Title
Front-runnable multisig deployment via unrestricted `name` parameter in `MultisigFactory::create` - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` lets any caller pick an arbitrary `name`, `members` list, and `num_confirmations`, then deploys a multisig contract at `<name>.<factory>` with those attacker-chosen parameters. Because NEAR sub-account creation is first-come-first-served and the method performs no check that the caller is entitled to that `name`, an attacker can pre-emptively squat any not-yet-created `<name>.<factory>` id with a multisig whose member set (and confirmation threshold) they fully control.

### Finding Description
The invariant the question asks about is: for a given sub-account id `S = <name>.<factory>`, `members(S) == members_chosen_by(intended_owner_of(name))`. `MultisigFactory::create` breaks this binding because it is `#[payable]` and callable by any predecessor with no authorization check tying `name` to `env::predecessor_account_id()`: [1](#0-0) 

The method builds `account_id = format!("{}.{}", name, env::current_account_id())` and immediately issues `create_account().deploy_contract(CODE).transfer(...).function_call("new", {members, num_confirmations}, ...)` with no restriction on `name`, `members`, or `num_confirmations` beyond what the caller supplies. NEAR account creation semantics mean whoever's promise executes first for a given `account_id` wins; there is no reservation, allowlist, or ownership check on `name` at the factory level. An attacker observes (or predicts, e.g. via a company/protocol convention like `treasury.multisig-factory.near`) an id that a victim organization intends to use, and calls `create(name, [attacker_key_or_account], 1)` first. The resulting multisig contract at that id is fully attacker-controlled: attacker sets themselves as sole member with `num_confirmations = 1`, giving unilateral control over any funds later sent to that account by users/integrations trusting the name.

Existing guards do not help: there is no `assert_owner`, no `assert_self()`, no foundation check, and NEAR itself has no concept of "name reservation" for sub-accounts prior to creation — the first successful `CreateAccount` action for that id wins. Once created, the id cannot be recreated by the legitimate owner (NEAR disallows re-creating an existing account), so the squat is permanent absent a new name.

### Impact Explanation
Any party that later sends NEAR (or relies on the multisig at `<name>.<factory>` as a trusted contract, e.g. depositing funds, granting permissions, or routing protocol funds) is sending value to an account whose members were never chosen by the intended owner. Funds transferred to the squatted multisig can be immediately withdrawn by the attacker (as sole member with `num_confirmations = 1`), constituting NEAR moved out of a contract by a party not entitled to it — this matches the Critical impact category ("an account whitelisted or a lockup deployed with parameters its rightful creator never chose"), generalized here to a multisig deployed with parameters (members) its rightful creator never chose. The attack is repeatable across every not-yet-created `<name>.<factory>` id, i.e. across arbitrarily many organizations/users that plan to use this factory, with no per-attempt cost beyond gas and the tiny storage deposit for account creation.

### Likelihood Explanation
The only precondition is that the attacker learns or guesses the intended `name` before the legitimate party calls `create`. This is highly feasible: predictable naming conventions (org name, product name), public announcements of intended multisig names, or simply mempool-watching a pending `create` transaction and front-running it with higher gas/priority are all available to an unprivileged NEAR account holder. Cost is minimal (one transaction plus small account-creation storage deposit), and the exploit is trivially repeatable against many targets.

### Recommendation
Require the caller to prove entitlement to `name` before creating the sub-account — e.g., require `env::predecessor_account_id() == name` (self-registration only) or require the `name` account to sign/co-sign the creation, similar to patterns used by other NEAR factories that tie sub-account creation to a full-access key controlled by the predecessor. Alternatively, have the factory only create accounts under a namespace derived from `predecessor_account_id()` so squatting is impossible.

```rust
    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
```
