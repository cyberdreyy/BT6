### Title
Stale-epoch instant-withdraw receipts escape default haircut and are paid at par, draining recovery funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` tracks instant-withdraw receipt basis per epoch (`instantWithdrawsRequestsByEpoch[user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`), but `pendingInstantWithdraws` is a global aggregate that survives across epochs. When a default is finalized, `defaultPendingClaimBasis()` only folds `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — into the recovery basis. Instant receipts requested in an earlier epoch and still unfunded are "out-of-bounds" of the haircut calculation: they keep a full par claim against the strategy while the recovery price is computed on an understated basis. After finalization, `claimInstantWithdrawRequest` pays the leftover `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim`, breaking the fair loss-distribution invariant and letting earlier claimants overdraw funds that economically belong to the default-epoch recovery pool.

### Finding Description
The analog of the OOB write is an out-of-scope epoch-bucket write: `requestInstantWithdraw` records basis under `currentEpoch` while `pendingInstantWithdraws` aggregates all epochs, so `finalizeDefaultRecovery` reads only the current-epoch slice.

Attack flow (programmable/fixed-APR vault, unprivileged KYC'd lender):

1. Epoch N running, APR drops → attacker calls `IdleCDOEpochVariant.requestWithdraw`, which routes to `IdleCreditVault.requestInstantWithdraw(_amount, user)`, minting a receipt and recording `instantWithdrawsRequestsByEpoch[user][N] += amount`, `instantWithdrawClaimsByEpoch[N] += amount`, `pendingInstantWithdraws += amount` [1](#0-0) 
2. Manager calls `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` but the borrower only partially returns funds; `pendingInstantWithdraws -= collected` leaves a nonzero remainder that is *not* tied to any epoch [2](#0-1) 
3. Epoch N+1 starts and runs; borrower defaults. `finalizeDefault` → `finalizeDefaultRecovery` computes `pendingBasis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — only epoch N+1 instant claims are included; the epoch-N basis is silently dropped from the denominator [3](#0-2) 
4. `_defaultPrefundedInstantReserve` computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`; with the stale global remainder, `pendingInstant >= instantBasis` so prefunded reserve is recorded as 0 even when real collected cash sits in the strategy [4](#0-3) 
5. `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` is true, but `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` — the epoch-N portion of `instantWithdrawsRequests[user]` survives [5](#0-4) 
6. Attacker calls `claimInstantWithdrawRequest`; the residual `instantWithdrawsRequests[user]` (full original amount, including the never-funded part) is paid at par through `_transferFundedClaim` as long as `balance - reserve >= amount` [6](#0-5) 

The existing guards do not stop this: `_transferFundedClaim` only protects `defaultRecoveryReserve`, and the reserve was understated precisely because the stale-epoch basis was excluded. The `requestWithdraw` stale-receipt guard added for normal withdrawals (`lossRecoveryPriceByEpoch` check) has no equivalent for instant receipts.

### Impact Explanation
An unprivileged lender whose instant receipt spans an epoch boundary before a default receives 100% of their receipt at par — including the portion the borrower never returned — paid from strategy-held underlyings (prefunded instant cash, failed-send funds, or any non-reserve balance) that should have been shared pro-rata at `defaultRecoveryPrice`. Conversely, funded cash excluded from `reserveAmount` by the `pendingInstant > instantBasis` underflow in `_defaultPrefundedInstantReserve` permanently depresses the recovery price for all default-epoch claimants and can strand tokens in the contract (recoverable only by privileged `transferToken`). Quantified loss: up to the full stale-epoch `instantWithdrawsRequests` balance stolen/overpaid, plus the prefunded amount that never enters the recovery pool.

### Likelihood Explanation
Requires a specific but ordinary sequence: an APR drop triggering instant withdrawals, partial borrower repayment leaving `pendingInstantWithdraws > 0` across a `stopEpoch`/`startEpoch` boundary, then a borrower default. Nothing in the code forces `pendingInstantWithdraws` to zero before a new epoch, and partial funding is explicitly contemplated by the prefunded-reserve logic. The attacker needs no privilege — only a KYC'd wallet and timing.

### Recommendation
Track the unfunded instant remainder per epoch (or a single global `pendingInstantBasis` that is decremented on funding) and include *all* unfunded instant receipt basis in `defaultPendingClaimBasis`, not just `instantWithdrawClaimsByEpoch[epochNumber]`. In `claimInstantWithdrawRequest`, route every epoch's outstanding instant receipt through the recovery price when `defaultRecoveryFinalized`, rather than clearing only `defaultRecoveryEpoch` and paying the rest at par.

    _onlyIdleCDO();

    // burn strategy tokens from cdo

    // mint equal amount of strategy tokens to the user as receipt, useful in case of default

    // we record both per-user (old, kept for compatibility) and per-epoch so on

    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
