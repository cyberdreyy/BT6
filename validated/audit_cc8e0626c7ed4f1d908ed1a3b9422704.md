### Title
Builder Payment Settlement Bypasses PTC Quorum Requirement, Paying Builders Without Timeliness Attestation Authorization - (File: specs/gloas/beacon-chain.md)

### Summary
`settle_builder_payment`, invoked from `apply_parent_execution_payload` on every block that follows a "full" parent, releases the builder's pending payment into `state.builder_pending_withdrawals` based solely on `payment.withdrawal.amount > 0`. It never checks `payment.weight` against the Payload Timeliness Committee (PTC) quorum threshold. The only code path that does enforce this quorum — `process_builder_pending_payments`, run at epoch boundaries — is starved of any entries to check, because `settle_builder_payment` has already zeroed out (`BuilderPendingPayment.empty()`) every settled slot on the very next block. This mirrors the report's root cause: two divergent code paths handle the "same" payment/reward release, and the path that actually executes bypasses the authorization gate the other path was designed to enforce, so funds are paid out without the intended condition being satisfied.

### Finding Description
`process_builder_pending_payments` (epoch processing) is written to gate builder payment release on quorum: [1](#0-0) 

```python
def process_builder_pending_payments(state: BeaconState) -> None:
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)
    ...
```

However, `settle_builder_payment` — the function that actually fires on every subsequent block for a full parent — contains no such check: [2](#0-1) 

```python
def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()
```

`settle_builder_payment` is called from `apply_parent_execution_payload`, which runs during `process_parent_execution_payload` for essentially every block whose parent was "full" (i.e. the builder's payload envelope matched the bid and was revealed): [3](#0-2) 

```python
    # Settle the builder payment
    if parent_epoch == get_current_epoch(state):
        payment_index = SLOTS_PER_EPOCH + parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_epoch == get_previous_epoch(state):
        payment_index = parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_bid.value > 0:
        ...
```

Because this settlement fires on the very next block (or at worst before the epoch boundary), the `state.builder_pending_payments[payment_index]` slot is cleared to `BuilderPendingPayment.empty()` long before `process_builder_pending_payments` ever inspects it at end of epoch. The quorum-gated code path therefore only ever sees empty, already-processed slots (weight 0, already paid) for every full-parent case — it is effectively dead code for the exact case it was written to protect (payments for revealed/full payloads). The unconditional-amount check in `settle_builder_payment` is the only path that actually executes, so the builder is paid in full regardless of whether the PTC committee ever attested to the payload's timeliness/availability at quorum strength.

### Impact Explanation
This breaks the equality that a builder payment should only be released once the PTC committee's attested weight reaches quorum — i.e. once the network has confirmed the builder delivered its payload on time. Instead, the builder is paid unconditionally for any full parent, which is exactly the "a payload executed or paid that the block did not commit to" / "Gwei ... paid to a non-owner [without required authorization]" class of Critical impact: a builder can receive its full bid value even when the PTC committee overwhelmingly failed to attest that the payload was timely/available, undermining the entire purpose of the PTC quorum mechanism that Gloas (EIP-7732) introduces to police builder payments.

### Likelihood Explanation
This triggers on the ordinary, spec-following code path for every full-parent block — no adversarial input, coalition, or malicious peer is required. It is a deterministic consequence of the state-transition ordering (`settle_builder_payment` always runs before `process_builder_pending_payments` gets a chance to see a non-empty, non-quorate payment slot for any full parent), so it would manifest on mainnet under normal operation, not merely in a contrived edge case.

### Recommendation
Add the same `payment.weight >= quorum` gate inside `settle_builder_payment` that `process_builder_pending_payments` uses, so that a builder payment is only appended to `state.builder_pending_withdrawals` once PTC quorum weight has been reached; if quorum has not yet been reached at settlement time (i.e., attestations for the parent slot are still outstanding), the payment entry should remain in `state.builder_pending_payments` until it can be adjudicated by the epoch-level quorum check rather than being unconditionally paid and cleared.

### Proof of Concept
1. Builder B submits an execution payload bid for slot S with `value = V`, `builder_index = B`; the payload envelope is revealed and matches the bid, so the parent is "full" (`bid.parent_block_hash == parent_bid.block_hash` in the next block).
2. Attesters at slot S largely do NOT confirm the payload was delivered on time (e.g., it arrived late), so PTC attestations accumulate `payment.weight < quorum = get_builder_payment_quorum_threshold(state)` for `state.builder_pending_payments[payment_index]`.
3. Block at slot S+1 is processed. `process_parent_execution_payload` → `apply_parent_execution_payload` computes `payment_index` and calls `settle_builder_payment(state, payment_index)`.
4. `settle_builder_payment` only checks `payment.withdrawal.amount > 0` (true, since `value = V > 0`), appends the full withdrawal of `V` to `state.builder_pending_withdrawals`, and clears the payment slot to `BuilderPendingPayment.empty()` — the `weight < quorum` condition is never evaluated.
5. At the next epoch boundary, `process_builder_pending_payments` scans `state.builder_pending_payments[:SLOTS_PER_EPOCH]` and finds the slot already empty (weight 0) — it has nothing to gate, since the payment was already unconditionally settled in step 4.
6. Builder B receives the full payment `V` via the withdrawal sweep despite the PTC committee never reaching quorum that the payload was timely — the payment was authorized/paid without the commitment (quorum attestation) the protocol design requires.

```python
def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
```
