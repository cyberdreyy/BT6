### Title
Funded instant-withdraw claims never clear `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, enabling a double payout and corrupted default-recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` settles the user's withdrawable receipt (`instantWithdrawsRequests[_user]`) and burns the receipt tokens, but never decrements the paired per-epoch trackers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` — the same class of bug as the reference report, where `balance_amount` was updated but `total_amount` was not. When a borrower default is later finalized in that same epoch, the stale per-epoch entries are re-read by `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve` and `_claimDefaultedInstantWithdrawRequest`, letting a user be paid twice for one receipt and inflating the recovery basis with already-paid funds.

### Finding Description
`requestInstantWithdraw` keeps three counters in sync: per-user `instantWithdrawsRequests[_user]`, per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the epoch aggregate `instantWithdrawClaimsByEpoch[currentEpoch]` (plus global `pendingInstantWithdraws`). [1](#0-0) 

On a funded claim, only the per-user aggregate is cleared; the two per-epoch trackers are left permanently set: [2](#0-1) 

The stale entries are then consumed on the default path:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, so already-claimed receipts still count toward the haircut basis. [3](#0-2) 
- `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` as "cash already held for those claims", but funds paid out through `_transferFundedClaim` are no longer held — the reserve is credited with phantom underlying. [4](#0-3) 
- `_claimDefaultedInstantWithdrawRequest` pays `instantWithdrawsRequestsByEpoch[_user][defaultEpoch] * defaultRecoveryPrice`, so a user whose epoch-N receipt was already paid can claim the full stale basis again. [5](#0-4) 

Attack sequence (running epoch, non-prefunded mode, unprivileged KYC'd lender):

1. Epoch N is running. Attacker calls `requestInstantWithdraw(A1)` — `byEpoch[N] = A1`, `instantWithdrawsRequests = A1`, `pendingInstantWithdraws = A1`.
2. Borrower returns liquidity mid-epoch; CDO calls `collectInstantWithdrawFunds(A1)` → `pendingInstantWithdraws = 0`, strategy now holds A1 underlying.
3. Attacker calls `claimInstantWithdrawRequest` → receives A1; `instantWithdrawsRequests = 0`, but `instantWithdrawsRequestsByEpoch[N]` and `instantWithdrawClaimsByEpoch[N]` still equal A1.
4. Attacker calls `requestInstantWithdraw(A2)` → `pendingInstantWithdraws = A2`, `instantWithdrawsRequests = A2`, `byEpoch[N] = A1 + A2`.
5. Borrower defaults before A2 is funded; owner/manager calls `IdleCDOEpochVariant.finalizeDefault` → `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber = N` and, since `pendingInstantWithdraws = A2 != 0`, `defaultInstantWithdrawsFinalized = true`. `defaultPendingClaimBasis` counts `A1 + A2` (should be A2), and `_defaultPrefundedInstantReserve` adds `A1` of phantom reserve that was already paid out — so `defaultRecoveryReserve` and `totalBasis` are both overstated by A1. [6](#0-5) 
6. Attacker calls `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` reads stale `byEpoch[N] = A1 + A2` and pays `(A1 + A2) * defaultRecoveryPrice` — recovering A1 a second time. The phantom reserve entry means later honest claimants' `_transferDefaultRecovery` calls underflow/fail once the real balance is exhausted.

The broken invariant is "one receipt, one payout" plus recovery-reserve solvency: the settled receipt still exists in the per-epoch claim tables. No existing guard stops it — `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` [7](#0-6) , the funded-claim path never touches per-epoch state, and `_onlyIdleCDO` is satisfied because claims route through the CDO.

### Impact Explanation
Direct theft plus freezing of recovery funds. The attacker is paid `A1 * recoveryPrice` a second time (double payout for a single receipt). Simultaneously, `defaultRecoveryReserve` is booked A1 higher than the actual token balance, so once the real funds are drained, remaining defaulted-epoch claimants (and normal receipt holders sharing the same reserve) cannot claim — a permanent loss for them and stranded dust. Loss magnitude: up to the full prefunded-and-claimed instant amount per attacker per defaulted epoch; scalable by repeating steps 1–4 with more claimed-then-re-requested volume.

### Likelihood Explanation
Requires a borrower default/hard-loss to be finalized via `finalizeDefault` in the same epoch where the attacker both claimed a funded instant withdrawal and left an unfunded one — i.e., a partially funded instant queue at default time, a scenario the code comments explicitly anticipate ("cash covered only part of the instant queue"). The attacker controls steps 1–4 and can keep stale basis outstanding across epochs opportunistically; the trigger (borrower default) is an honest-party event outside attacker control, which lowers likelihood but does not require any privileged misbehavior. All attacker calls are ordinary lender-facing CDO functions available to any KYC-passing wallet.

### Recommendation
Mirror the paired-counter invariant: when a funded instant claim is settled in `claimInstantWithdrawRequest`, also clear `instantWithdrawsRequestsByEpoch[_user][<requestEpoch>]` and decrement `instantWithdrawClaimsByEpoch[<requestEpoch>]` by the claimed amount (the user's request epoch needs to be tracked, e.g., a `lastInstantWithdrawRequest` marker analogous to `lastWithdrawRequest`). Alternatively, subtract claimed amounts from the per-epoch tables at claim time so `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve` and `_claimDefaultedInstantWithdrawRequest` only ever see unsettled receipts.

### Proof of Concept
Foundry fork PoC outline (target `contracts/strategies/idle/IdleCreditVault.sol` + `IdleCDOEpochVariant`):

```solidity
// setup: deploy IdleCDOEpochVariant + IdleCreditVault, KYC attacker + honestLender,
// epoch running, instant withdraws enabled, fixed APR mode.

// 1. Attacker requests instant withdraw A1 during epoch N
cdo.requestInstantWithdraw(A1);                       // byEpoch[N] = A1

// 2. Honest borrower returns A1; manager funds the instant queue
vm.prank(manager);
cdo.getInstantWithdrawFunds(A1);                      // -> collectInstantWithdrawFunds(A1)
assertEq(vault.pendingInstantWithdraws(), 0);

// 3. Attacker claims funded receipt
cdo.claimInstantWithdrawRequest();                    // attacker paid A1
// BUG: instantWithdrawsRequestsByEpoch[attacker][N] still == A1
//      instantWithdrawClaimsByEpoch[N] still == A1

// 4. Attacker opens second, unfunded instant request A2
cdo.requestInstantWithdraw(A2);                       // byEpoch[N] = A1+A2

// 5. Borrower defaults; manager finalizes with recoveredAmount R
vm.prank(manager);
cdo.finalizeDefault(R, recoverySource);
// defaultPendingClaimBasis() = pendingWithdraws + (A1 + A2)  // inflated by A1
// _defaultPrefundedInstantReserve() = A1               // phantom reserve

// 6. Attacker claims defaulted receipt: pays on basis A1+A2
cdo.claimInstantWithdrawRequest();
// received ~= (A1 + A2) * defaultRecoveryPrice / 1e18
// => A1 recovered twice; strategy real balance < defaultRecoveryReserve by A1

// 7. Honest claimant's _transferDefaultRecovery reverts/underpays once reserve exhausted
```

Expected: `instantWithdrawsRequestsByEpoch[attacker][N] == A1 + A2` after the funded claim (should be 0 before A2), the attacker receives ~`A1 * recoveryPrice` of unentitled recovery, and the strategy's actual underlying balance is `A1` below `defaultRecoveryReserve`, causing the last recovery claim(s) to fail.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
