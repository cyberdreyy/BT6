### Title
Permissionless griefing shareholder in `vesting::distribute()` permanently locks vested stake, rewards, and commission for all other shareholders - ([File: aptos-move/framework/aptos-framework/sources/vesting.move])

### Summary
`vesting::distribute()` withdraws all currently-withdrawable stake for a vesting contract and pays it out to *every* shareholder in a single loop, using `aptos_account::deposit_coins` for each recipient. `aptos_account::deposit_coins` can abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient already has an `Account` resource, is not yet registered for `AptosCoin`, and has opted out of unsolicited coin transfers via `set_allow_direct_coin_transfers(false)`. Because Move aborts unwind the entire transaction and the loop has no way to skip a failing shareholder, a single such shareholder permanently blocks `distribute()` for the whole vesting contract — including all other, unrelated shareholders' vested tokens, rewards, and even the operator's commission, since `distribute()` is the sole payout mechanism and is also invoked at the start of `terminate_vesting_contract()`.

### Finding Description
`distribute()` iterates over all shareholders and unconditionally calls `aptos_account::deposit_coins` for each: [1](#0-0) 

`aptos_account::deposit_coins` only bypasses the opt-out check when the recipient is *already* registered for the given coin type; otherwise it enforces `can_receive_direct_coin_transfers`: [2](#0-1) 

`can_receive_direct_coin_transfers` returns `false` once an account has called `set_allow_direct_coin_transfers(false)`, and this opt-out requires no coin registration at all: [3](#0-2) 

Only the *beneficiary* path is protected: `set_beneficiary()` explicitly requires the new beneficiary to already be registered for APT, with a comment acknowledging exactly this failure mode ("so distribute() wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered"): [4](#0-3) 

However, the default recipient — the shareholder address itself, used whenever no beneficiary is set — receives no equivalent registration check anywhere in `create_vesting_contract` or `distribute()`. A shareholder address that (a) already has an on-chain `Account` (e.g., created via any means other than `aptos_account::create_account`, which is the only path that auto-registers APT) and (b) calls `aptos_account::set_allow_direct_coin_transfers(false)` before ever being paid by `distribute()`, will cause every future `distribute()` call for that vesting contract to abort inside the `shareholders.for_each_ref` loop.

Because the loop has no per-recipient try/catch or skip-and-continue logic — the exact bug class from the external Axelar report, where a failed sub-call has no fallback/recovery path — the abort unwinds the whole transaction:
- All other shareholders' vested/reward distributions revert every time.
- `terminate_vesting_contract()` calls `distribute()` first and thus can never complete, so the vesting contract can never be wound down or have `admin_withdraw()` reach the `VESTING_POOL_TERMINATED` state: [5](#0-4) 

- Operator commission bundled into the same distribution pool (paid via the shared `distribution_pool` in `staking_contract::distribute_internal`, invoked from `vesting::withdraw_stake`) is similarly stuck alongside shareholder funds.

### Impact Explanation
This breaks the "unlock/distribute/withdraw paths must not strand value permanently" invariant for vesting: a single unprivileged shareholder (who need not even be malicious toward themselves, or a griefer targeting the fund) can permanently lock the principal, rewards, and operator commission of an entire vesting contract shared by multiple shareholders, with no admin recovery function that bypasses the shareholder loop. This is a permanent, non-recoverable loss of claim rights for all co-shareholders of that vesting contract, matching the "Permanent lock or non-recoverable loss of claim rights in stake ... vesting flows" impact category.

### Likelihood Explanation
The precondition (an account existing without APT registration, plus calling the permissionless `set_allow_direct_coin_transfers(false)`) is fully within the control of any account holder and requires no privileged role — any shareholder added to a multi-shareholder vesting grant can trigger this unilaterally at any time before their first payout, and it need not even be intentional griefing (a shareholder could set this for unrelated reasons, e.g. spam-transfer protection, without realizing it will freeze the whole pool's future distributions).

### Recommendation
In `distribute()`, isolate per-shareholder payout failures so one recipient cannot block payment to others — e.g., wrap each `aptos_account::deposit_coins` call so failures fall back to crediting an internal claimable balance (pull-payment pattern) or are diverted to the `withdrawal_address`/a recovery escrow, similar to the Connext Executor recovery-address pattern cited in the source report, rather than aborting the entire loop.

### Proof of Concept
1. Account `S` calls `account::create_account` indirectly (e.g. by being the target of any module that creates an `Account` resource without registering AptosCoin, such as receiving an object or being set up as a multisig/resource-account owner), so `account::exists_at(S) == true` but `coin::is_account_registered<AptosCoin>(S) == false`.
2. `S` calls `aptos_account::set_allow_direct_coin_transfers(S, false)` — permissionless, no registration required (`aptos_account.move:187-231`).
3. Admin creates a vesting contract via `create_vesting_contract` with shareholders `[S, A, B]` and no beneficiary set for any of them.
4. Time passes; rewards/vested tokens accumulate and unlock.
5. Anyone calls `vesting::distribute(contract_address)`. The loop reaches `S`, calls `aptos_account::deposit_coins(S, ...)`, which hits the `!coin::is_account_registered<AptosCoin>(S)` branch, checks `can_receive_direct_coin_transfers(S)` → `false`, and aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. The entire `distribute()` transaction reverts. `A` and `B` never receive their share; `terminate_vesting_contract()` (which calls `distribute()` first) also always reverts, permanently freezing the contract.

Note: I could not find any code path (in the reachable sources) that filters out or skips a non-receiving shareholder before or during the `for_each_ref` loop in `distribute()`, confirming there is no existing mitigation for the default (non-beneficiary) recipient case.

    public entry fun terminate_vesting_contract(admin: &signer, contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        // Distribute all withdrawable coins, which should have been from previous rewards withdrawal or vest.
        distribute(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        verify_admin(admin, vesting_contract);
        let (active_stake, _, pending_active_stake, _) = stake::get_stake(vesting_contract.staking.pool_address);
        assert!(pending_active_stake == 0, error::invalid_state(EPENDING_STAKE_FOUND));

        // Unlock all remaining active stake.
        vesting_contract.state = VESTING_POOL_TERMINATED;
        vesting_contract.remaining_grant = 0;
        unlock_stake(vesting_contract, active_stake);

        emit(
            Terminate {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
            },
        );
    }

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }

    #[view]
    /// Return true if `account` can receive direct transfers of coins that they have not explicitly registered to
    /// receive.
    ///
    /// By default, this returns true if an account has not explicitly set whether the can receive direct transfers.
    public fun can_receive_direct_coin_transfers(
        account: address
    ): bool acquires DirectTransferConfig {
        !exists<DirectTransferConfig>(account)
            || borrow_global<DirectTransferConfig>(account).allow_arbitrary_coin_transfers
    }
