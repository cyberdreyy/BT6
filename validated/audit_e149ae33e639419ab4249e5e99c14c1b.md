## Analog Found: v1 signer chainstate skips the same-tenure duplicate-block guard for locally-signed (not yet globally accepted) blocks, widening the window for the stale-signature "reorg escape hatch" to double-sign a tenure

### Title
Signer can be induced to sign two conflicting blocks in the same tenure — v1 protocol's tenure-change duplicate check uses `get_last_globally_accepted_block` instead of `get_last_signed_block` (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` gates its `DuplicateBlockFound` rejection on `signer_db.get_last_globally_accepted_block(...)`, while the newer `stacks-signer/src/chainstate/v2.rs::validate_tenure_change_payload` gates the identical check on `signer_db.get_last_signed_block(...)`, which also covers `LocallyAccepted` blocks. [1](#0-0) [2](#0-1) 

### Finding Description
The `DuplicateBlockFound` check exists specifically to reject a second tenure-start block proposal for a tenure the signer has already signed, and by design it runs only once, at proposal arrival, never again: [3](#0-2) 

In v2, this check correctly treats a block the signer has only **locally** accepted (`signed_self` set, not yet globally accepted) as "already signed," using `get_last_signed_block`, which explicitly includes `GloballyAccepted` and `LocallyAccepted` states: [4](#0-3) 

In v1, the equivalent check instead calls `get_last_globally_accepted_block`, which only matches `GloballyAccepted`: [5](#0-4) 

Consequence: for a v1 (legacy, non-global-state) signer, if it has already signed block A (tenure-start, `signed_self` set) but A has not yet been globally accepted by the node (still waiting on other signers, or network-delayed), a miner can re-propose a second, different tenure-start block B for the *same* tenure. `check_proposal` → `validate_tenure_change_payload` does not detect the duplicate (because `get_last_globally_accepted_block` returns `None`), so B is not rejected at proposal time and proceeds to node validation and pre-commit.

The only remaining guard is the cross-tenure conflict check that runs later, at the pre-commit→signature boundary: [6](#0-5) 

That check (`get_signed_conflicts`) does catch A as a conflict, but it contains a deliberate "stale signature" escape hatch: once A's signature ages past `tenure_last_block_proposal_timeout`, the signer falls into the "own tenure" branch and will sign the *replacement* B if the node's chain tip has not yet confirmed A at that height: [7](#0-6) 

This escape hatch was designed for the case where A is genuinely dead (its tenure was orphaned or its signature can never reach threshold), which is exactly what the async-sibling-validation tests exercise — but those tests only cover the case where A and B are proposed within the *same async validation window*, before A is signed: [8](#0-7) 

The v1 gap described here is different and stronger: a miner can re-propose a genuinely competing tenure-start block *after* the signer has already locally signed the first one, purely because v1's proposal-time duplicate check ignores locally-signed (not-yet-global) blocks. If different subsets of signers observe the node's tip at different times relative to A's broadcast, a fraction of the signer set can end up putting a fresh signature on A while another fraction — having seen A's signature go stale and the node's tip not yet reflect it — signs B instead. That breaks the "one signed block per tenure/height" equality that the pre-commit/conflict machinery is designed to preserve for a single winning miner, and instead of being a pure liveness fallback, it becomes a legitimate signing path for a genuinely live/competing block that the same miner (not a majority of signers, not another signer's key) can trigger simply by re-proposing after the timeout.

### Impact Explanation
If enough weight lands on each of A and B independently (each requiring only the same static configured 70% threshold, but drawn from disjoint or overlapping views of the network), the signer set could produce valid ≥70%-weight signature sets over two different Nakamoto blocks for the same tenure — a conflicting/duplicate signed block, which is exactly the "signer signing a conflicting block" class this scan targets (Critical).

### Likelihood Explanation
This requires only a single winning miner (no majority of signers, no other signer's key, no auth token) to re-propose a competing tenure-start block after `tenure_last_block_proposal_timeout` has elapsed on some signers, and applies only to signers running the legacy v1 (non-global-state) chainstate protocol. Likelihood is bounded by the fact that v1 is a legacy code path (v2 uses the correct `get_last_signed_block` check), and requires the node's tip to lag behind the locally-signed block A across some but not all signers.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, matching the v2 implementation, so a block this signer has locally signed for a tenure is treated as "already signed" and a competing tenure-start proposal is rejected as `DuplicateBlockFound` at proposal time regardless of protocol version.

### Proof of Concept
1. Signer S runs v1 (legacy) chainstate protocol.
2. Miner wins sortition, proposes tenure-start block A; S validates and signs A (`signed_self` set), but A has not yet reached global acceptance (e.g., other signers slow/offline).
3. Before A becomes globally accepted, but after `tenure_last_block_proposal_timeout` elapses, the same miner proposes a different tenure-start block B for the identical `consensus_hash`/tenure.
4. `check_proposal` → `validate_tenure_change_payload` calls `get_last_globally_accepted_block`, which returns `None` (A is only locally accepted) — no `DuplicateBlockFound`, so B is accepted for validation.
5. B reaches the pre-commit threshold; `handle_block_pre_commit`'s conflict check finds A as a signed conflict, but treats it as stale (past `tenure_last_block_proposal_timeout`) and, seeing the node's tenure tip not yet at A's height, signs B.
6. S has now signed two different blocks (A and B) for the same tenure/height — the same defect verifiable directly by unit-testing `SortitionData::validate_tenure_change_payload` (v1) with a `BlockInfo` that is `LocallyAccepted` but not `GloballyAccepted` in the same tenure, and observing it does not return `RejectReason::DuplicateBlockFound`, contrasted with v2's `validate_tenure_change_payload` under the same setup which does.
