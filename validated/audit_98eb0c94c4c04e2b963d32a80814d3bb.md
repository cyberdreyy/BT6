### Title
Stale write-off requests can be force-executed by any third party, selling a lender's escrowed tranche tokens at a below-market fixed price - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
The phpMyFAQ bug class is "an unintended action triggered on a victim's behalf without interaction or consent" (a forced download via an embedded frame). The on-chain analog is `fullfillWriteOffRequest` in `IdleCreditVaultWriteOffEscrow`: once a lender posts a write-off request, any unprivileged address can execute it at any later time, forcing the sale of the lender's escrowed tranche tokens at a stale, lender-quoted fixed price. The lender cannot revoke consent retroactively — `deleteWriteOffRequest` races with fulfillment and can be front-run.

### Finding Description
`createWriteOffRequest` escrows a lender's tranche tokens and records a fixed `underlyings` ask with no expiry and no per-fulfillment consent check (IdleCreditVaultWriteOffEscrow.sol:86-102). `fullfillWriteOffRequest` is permissionless ("this function can be called by any wallet") and only requires `_underlyings >= currentRequest.underlyings` (lines 123-131). It then:

- deletes the request (line 135),
- pulls the stale ask amount from the fulfiller (line 139),
- sends `underlyings - fee` to the lender (line 149),
- transfers the full `currentRequest.tranches` to the fulfiller (line 151).

The ask is a fixed nominal amount, but tranche tokens are claim-like claims on the CDO whose value tracks `virtualPrice`/recovery outcomes. Between `createWriteOffRequest` and fulfillment, conditions that raise the tranche's realizable value — a successful `stopEpoch` crediting interest, a `finalizeDefaultRecovery` recovery distribution, or a pool state change making withdrawals more favorable — leave the ask stale. An attacker monitors the mempool/state and fulfills the moment the escrowed tranches are worth more than the ask, or front-runs the lender's `deleteWriteOffRequest` (which the lender would submit precisely to reprice/cancel). No guard in `fullfillWriteOffRequest` re-validates the price against `virtualPrice`, enforces a deadline, or requires fresh consent — the only "consent" is the still-existing request, exactly like the iframe that triggers the download merely because the resource still exists.

Note: the docstring and `testFullfillWriteOffRequestAllowsThirdPartyBuyer` explicitly bless arbitrary third-party fulfillers, so permissionless fulfillment per se is intended. The weakness is the absence of an expiry/re-priced consent, which lets an attacker execute an order the lender economically no longer wants.

### Impact Explanation
Broken invariant: fair exchange / consent. The lender receives `underlyings - exitFee` for tranche tokens whose realizable value has risen above the ask. Loss to the lender = `tranche_value_at_fulfill - underlyings_requested`, captured entirely by the fulfiller, plus the 0.1% exit fee leakage. Quantitatively, if a lender escrows 10,000 tranches asking 10,000 underlying, and a recovery event or accrued interest raises tranche value to 12,000, the attacker profits ~2,000 underlying stolen from the lender in a single transaction. This qualifies as direct value extraction from a user.

### Likelihood Explanation
Requires a lender to leave a request open while the tranche value appreciates above the ask — plausible because lenders post these requests during distress and ask prices are commonly set below par expecting negotiation, while epochs, stopEpoch interest accrual, and default-recovery finalizations routinely move tranche value. The attacker needs only ERC20 approval and a mempool/state watcher; no privileged role. Front-running `deleteWriteOffRequest` is straightforward since fulfillment is atomic. Likelihood is moderate: it depends on stale asks existing, but the attack is cheap and repeatable across every appreciation event while a request is open.

### Recommendation
Add a liveness/consent bound to requests: store an expiry (block.timestamp deadline) set at `createWriteOffRequest` and revert fulfillment after it, and/or a nonce/`requestVersion` bumped on any user action so a front-run deletion invalidates fulfillment. Alternatively, price the exchange at fulfillment time against `IdleCDOEpochVariant.virtualPrice(tranche)` (or require `_underlyings` to match a freshly re-signed ask), so an attacker cannot arbitrage stale quotes against lenders.

### Proof of Concept
Conceptual Foundry fork scenario (standard `IdleCreditVault` + escrow deployment as in `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`):

```solidity
// setup: deposit as LP, epoch running
escrow.createWriteOffRequest(10_000e18 /* tranches */, 10_000e6 /* ask */); // LP asks below expected value

// attacker waits: epoch progresses, stopEpoch credits interest / recovery is finalized,
// tranche realizable value rises to ~12,000 underlying while ask stays 10,000

// optional: LP tries to cancel
// vm.prank(LP); escrow.deleteWriteOffRequest();  // attacker front-runs this tx

vm.startPrank(attacker);
underlying.approve(address(escrow), 10_000e6);
escrow.fullfillWriteOffRequest(LP, 10_000e18, 10_000e6);
vm.stopPrank();

// attacker holds 10,000 tranches worth ~12,000 underlying; LP received only ~9,990 (0.1% fee)
assertGt(realizableValueOf(tranche.balanceOf(attacker)), 10_000e6);
```

I was unable to fully verify with a running fork PoC in this session, and the finding rests on the stale-price/forced-execution interpretation — reviewers may weigh the explicitly documented "any wallet" fulfillment as intended design, in which case this is an accepted risk rather than a bug.
