### Title
Cheap, repeated invalid reorg-attempt proposals let a single miner indefinitely refresh `last_activity_time` and suppress the inactivity fallback - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_latest_block_in_tenure` counts a *rejected*, non-advancing block proposal (one that reorgs/duplicates a height it should not) as valid "miner activity" and refreshes `last_activity_time` for that miner's tenure, as long as it arrives within `reorg_attempts_activity_timeout` of the conflicting block's signature time. `SortitionState::is_timed_out` (v2) / the v1 analogue use exactly this timestamp to decide whether to fall back to the prior miner. A single sortition winner can therefore keep "activity" alive — and block the liveness fallback — by repeatedly sending cheap, doomed proposals instead of ever producing a valid block, mirroring the external report's pattern: a resource/liveness safeguard (there: EIP-1559 fee scaling; here: the inactivity timeout) can be kept from firing by an action that is intentionally rejected/low-cost, because the check that "counts as activity" does not require the action to make real progress.

### Finding Description
`check_latest_block_in_tenure` (stacks-signer/src/chainstate/mod.rs, lines 376-478) is invoked from both `check_proposal` (at proposal arrival) and `check_block_against_signer_db_state` (at validate-ok / pre-commit-threshold time). When a proposed block does **not** confirm more blocks than the signer already knows about (`block.header.chain_length <= info.block.header.chain_length`), the function returns `Ok(false)` — i.e. rejects the proposal — but before doing so it explicitly calls:

```
if info.signed_group.is_none_or(|signed_time| {
    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
}) {
    ...
    signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())
    ...
}
return Ok(false);
``` [1](#0-0) 

This `last_activity_time` is exactly the timestamp `SortitionState::is_timed_out` reads to decide whether the current sortition's miner has gone inactive and should be abandoned in favor of a fallback to the prior tenure:

```
let last_activity = signer_db
    .get_last_activity_time(sortition)?
    .map(|time| UNIX_EPOCH + Duration::from_secs(time))
    .unwrap_or(received_time);
...
Ok(elapsed > timeout)
``` [2](#0-1) 

and per `docs/signer-flows.md`, this feeds `check_miner_inactivity`, which is the sole mechanism that falls back to the prior miner when the current one stalls:

```
TO -- "no signed block, and inactive past block_proposal_timeout" --> FALL["fall back to prior tenure: make_miner_state(prior sortition)"]
``` [3](#0-2) 

The equality/liveness invariant being broken: the inactivity fallback is supposed to fire when the current miner produces **no progress** within `block_proposal_timeout`. But "activity" as measured by the signer is satisfied by *any* proposal that merely fails to advance the chain, provided it arrives before the tenure's last signed block goes stale (`reorg_attempts_activity_timeout`). A sortition winner (one-slot miner, no majority of signers or other keys needed) can broadcast a stream of trivially rejectable proposals — e.g., re-proposing at or below the currently confirmed height — at negligible cost (a `BlockProposal` gossip message; it never even needs to pass node validation to reach this code path in the proposal-arrival case, and is cheap to construct even at validate-ok time) to repeatedly call `update_last_activity_time`, resetting the clock that `is_timed_out` measures against. As long as each subsequent doomed proposal arrives before the timeout elapses, `elapsed > timeout` never becomes true, and `check_miner_inactivity`/`is_timed_out` never triggers the fallback to the prior tenure.

This is structurally analogous to the Morph L2 finding: there, a size-based capacity limit (blob size) could be hit cheaply by an attacker without incurring proportional cost, defeating the fee-based liveness/DoS protection (EIP-1559 base-fee escalation) that the system relied on. Here, a "liveness/DoS protection" (the inactivity-based fallback that exists specifically to un-stick the chain when a miner misbehaves or stalls) can be defeated cheaply by an attacker (the current miner) sending repeated invalid/no-progress proposals that are nonetheless credited as "activity," at a cost far below what a real block requires.

### Impact Explanation
This is a liveness wedge: signers can be kept from ever falling back to a working miner while the current miner (or an adversary who won the current sortition slot) refuses to produce a valid, progressing block, using only cheap, disposable proposals. This matches the "High" impact bucket: a signer wedged into never signing valid blocks / never triggering the liveness fallback it relies on to recover from a stalled or malicious miner. No majority of signers or additional key material is required — a single sortition winner (one-slot) plus ordinary StackerDB/miner gossip is sufficient to exploit the mechanism.

### Likelihood Explanation
The action needed — sending a `BlockProposal` (or a proposal that reaches validate-ok / pre-commit re-check) whose `chain_length` does not exceed the already-known tip in its own tenure — is trivial for the current sortition winner to construct repeatedly, and the check that credits it as "activity" runs unconditionally in that branch, gated only by the freshness of `signed_group`/`reorg_attempts_activity_timeout`, which the miner already controls the timing of. This requires no cooperation from other signers or the node beyond normal proposal delivery.

### Recommendation
`check_latest_block_in_tenure` should not credit a proposal that fails the height/progress check as "miner activity" merely because it arrived within the reorg-activity window; activity credit should require either a proposal that actually clears validation (or otherwise represents genuine, distinguishable progress) or should be rate-limited/capped so a burst of rejected re-proposals cannot indefinitely extend `last_activity_time`. Consider decoupling the "still counts as legitimate reorg-timing activity" concept from "resets the inactivity fallback timer," e.g., by tracking a monotonic bound on how far `last_activity_time` can be pushed forward without an actual accepted/pre-committed block, or by making the fallback timeout measured from `received_time` regardless of subsequent rejected proposals once a threshold number of doomed proposals has been seen.

### Proof of Concept
1. Miner A wins the current sortition slot for tenure T, becoming the `ActiveMiner` in the signer state machine.
2. Miner A proposes a first (real or trivial) block that gets signed, establishing `info.signed_group` in `signerdb` for T.
3. Before `block_proposal_timeout` elapses, and while the signed block in T is still "fresh" (within `reorg_attempts_activity_timeout` of `signed_group`), miner A repeatedly broadcasts additional `BlockProposal`s for T whose `chain_length` does not exceed the already-signed block's height (e.g., re-proposing the same height, or a lower height, "reorg attempts").
4. Each such proposal is routed through `check_latest_block_in_tenure`/`check_block_against_signer_db_state`, is rejected (`Ok(false)`), but before returning triggers `signer_db.update_last_activity_time(&block.header.consensus_hash, ...)` [4](#0-3) .
5. `SortitionState::is_timed_out` recomputes `elapsed = now - last_activity`, which keeps resetting to near-zero, so `elapsed > timeout` never holds [5](#0-4) .
6. `check_miner_inactivity` therefore never falls back to the prior tenure's miner, and the chain stalls behind miner A indefinitely as long as A keeps sending cheap, doomed proposals faster than the timeout windows expire.

Note: I was unable to fully trace the equivalent v1 `is_timed_out` implementation's exact wiring of `last_activity_time` within the tool budget available, and could not confirm any additional rate-limiting on repeated `BlockProposal` gossip at the libsigner/transport layer that might mitigate the frequency of this refresh (out-of-scope per the rules, but relevant to real-world exploitability). A Devin session with fuller repo access could verify the v1 code path and any StackerDB slot/gossip rate limits that bound how often this refresh can occur in practice.
