### Title
Missing user-controlled deadline / min-shares in `depositDuringEpoch` lets a delayed inclusion mint fewer tranche tokens for the same underlying - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`depositDuringEpoch` prices minted shares using `block.timestamp` at inclusion time (`remaining = epochEndDate - block.timestamp`). There is no `deadline` or `minShares` parameter, so a transaction is valid whenever a validator includes it. A validator that holds a user's mid-epoch deposit until late in the epoch causes the depositor to receive fewer tranche tokens for the same `_amount` of underlying, while the unminted value remains in the pool for other tranche holders. This is the same bug class as the reported Uniswap `block.timestamp`-deadline issue: ordering/timing of inclusion silently changes the economic outcome against the sender's intent.

### Finding Description
In `IdleCDOEpochVariant.depositDuringEpoch` the minted amount is: [1](#0-0) [2](#0-1) 

`trancheInterest` is proportional to `remaining + buffer`. As `remaining` shrinks toward 0, the depositor pays the full `_amount` of underlying but is credited only the buffer-period fraction of interest, so `_minted` decreases monotonically with inclusion delay. The only upper bound is the global `block.timestamp >= epochEndDate` check at [3](#0-2) , which the depositor cannot tighten. There is no `minShares`/`deadline` argument, mirroring the external report's missing deadline on `MintParams`/`IncreaseLiquidityParams`/`DecreaseLiquidityParams`.

The protocol even enshrines a timing cutoff for the privileged `processDepositsToBorrower` path (`block.timestamp + prefundedDepositWindow < epochEndDate`) [4](#0-3) , but ordinary users of `depositDuringEpoch` get no equivalent protection.

### Impact Explanation
A KYC-passed lender submits `depositDuringEpoch` mid-epoch. A validator (or any actor able to delay inclusion, e.g. via censorship/MEV) holds the tx until just before `epochEndDate`. The depositor still transfers `_amount` underlying to the borrower [5](#0-4) , but mints shares priced on a near-zero `remaining`, forfeiting up to the full prorated epoch interest. The forgone interest stays in `expectedEpochInterest`/NAV, benefiting remaining tranche holders (unprivileged third parties). The loss is quantified by `trancheInterest` at submit time minus the buffer-only interest at inclusion; for a 365-day, 10% APR epoch a deposit held from day 1 to the last block loses essentially the whole ~10% APR accrual on `_amount` — direct, quantified loss of user funds (not a DoS/gas issue).

### Likelihood Explanation
Requires the pool to be in `depositDuringEpoch`-enabled mode (fixed-APR, not AYS, not programmable, not APR0) and an epoch in the running phase. Inclusion-delay attacks require validator/MEV capability; on Ethereum mainnet with MEV infrastructure this is a realistic, well-documented vector — exactly the threat model Cyfrin accepted in the reference report. Existing guards (KYC, skim, `_guarded` limit, `isEpochRunning` check, supply-nonzero check) do not bound *when* within the epoch the tx lands, so none of them mitigate it.

### Recommendation
Add a `minShares` (and optionally a `deadline`) parameter to `depositDuringEpoch`, reverting if the computed `_minted < minShares` or `block.timestamp > deadline`, so users can bound the inclusion-time-dependent pricing. Optionally also enforce a global `lastDepositCutoff` before `epochEndDate`, analogous to `prefundedDepositWindow`.

### Proof of Concept
Foundry fork test sketch (setup mirrors `testDepositDuringEpochNumericalAA` at `test/foundry/IdleCreditVault.t.sol:1591`):

```solidity
// contracts/IdleCDOEpochVariant.sol depositDuringEpoch PoC
function testDepositDuringEpochDelayedInclusionLoss() external {
    // 10% apr, 365-day epoch, no buffer
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(365 days, 0);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);
    vm.stopPrank();

    idleCDO.depositAA(1000 * ONE_SCALE);
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    _startEpochAndCheckPrices(0);
    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    address user = makeAddr('victim');
    uint256 depositAmount = 1000 * ONE_SCALE;
    deal(defaultUnderlying, user, depositAmount);
    vm.startPrank(user);
    underlying.approve(address(cdoEpoch), depositAmount);

    // User submits tx at epoch start, intending ~10% interest over the epoch.
    // A validator holds the tx; it is included 1 second before epochEndDate.
    vm.warp(cdoEpoch.epochEndDate() - 1);
    uint256 minted = cdoEpoch.depositDuringEpoch(depositAmount, address(AAtranche));
    vm.stopPrank();

    // Honest inclusion at epoch start would mint ~ (1000 + ~100 interest) * supply / expectedFinal.
    // With remaining ~0 the interest term is ~0, so minted is strictly lower:
    // user paid 1000 underlying but receives shares redeemable for ~1000 at epoch end,
    // i.e. loses essentially the entire prorated epoch interest (~up to 10% of principal),
    // which remains in expectedEpochInterest/NAV for other tranche holders.
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    uint256 userValue = minted * cdoEpoch.virtualPrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;
    assertLt(userValue, 1001 * ONE_SCALE); // ~0 interest despite full-epoch deposit intent
}
```
