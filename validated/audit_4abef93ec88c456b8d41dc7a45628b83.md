### Title
Multisig `confirm` counts stale confirmations from deleted members, allowing execution below the live-member threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
`MultiSigContract::confirm` decides whether a request has reached quorum by comparing the size of the `confirmations` set stored for that request against `num_confirmations`. When a member/key is removed via `DeleteMember` (multisig2) or `DeleteKey` (multisig), the contract only purges **requests originated by** the removed member; it never scans other still-open requests to strip that member's already-recorded confirmation. A request that was partially confirmed by a member who is later removed keeps "counting" that removed member's vote, so fewer than `num_confirmations` *currently valid* members are needed to reach and execute the quorum threshold.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` executes once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

`assert_valid_request()` only checks that the caller (current confirmer) is a member and that the request/confirmations entries exist — it never re-validates that the *other* public keys/accounts already present in the stored `confirmations` set are still members: [2](#0-1) 

`delete_member()` removes outstanding requests **created by** the deleted member (`r.member == member`) and clears `num_requests_pk`, but does nothing to any *other* request's `confirmations` set that may already contain this member's confirmation: [3](#0-2) 

The legacy `multisig` contract has the identical pattern: `DeleteKey` only removes requests signed (created) by that key, not confirmations left by that key on other pending requests: [4](#0-3) [5](#0-4) 

This breaks the intended equality: `confirmations recorded for a request == confirmations from currently live members`. Once a member is removed, that equality no longer holds for any request they had confirmed before removal — their stale confirmation is still summed toward quorum.

### Impact Explanation
This lets a multisig request (e.g. `Transfer`, `AddKey` granting a full-access key, `FunctionCall`) execute with fewer live, authorized confirmations than `num_confirmations` requires. This is a direct case of "a multisig request executed below threshold," moving funds or granting access with less authorization than the deployment's security model guarantees — a Critical-impact custody-binding violation (recorded confirmations vs. live membership diverge, and the divergent side is trusted to authorize fund movement).

### Likelihood Explanation
The precondition (a member gets removed while they have an outstanding unconfirmed vote on some other pending request) is a routine operational scenario for any multisig that rotates its members/keys — no privileged action beyond ordinary `DeleteMember`/`DeleteKey` requests (which any legitimate quorum can already trigger) is required, and no attacker-only privilege is needed beyond being one of the remaining members who exploits the timing.

### Recommendation
When removing a member (`delete_member`/`DeleteKey`), iterate over **all** pending requests' `confirmations` sets (not just those the member created) and remove the member's entry from each, re-checking whether any request that still meets or exceeds `num_confirmations` should now be blocked from further confirmation until it's re-confirmed by currently valid members. Alternatively, revalidate every entry in a request's `confirmations` set against current `members` at the moment `confirm()` computes quorum, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 3` and members `[A, B, C, D]`.
2. `A` calls `add_request` creating request `R` (e.g. `Transfer` of contract funds).
3. `B` calls `confirm(R)` → `confirmations(R) = {B}` (1 of 3).
4. Separately, `A`, `C`, `D` fully confirm a different request that executes `DeleteMember { member: B }`. `B` is removed from `self.members`; per `delete_member`, only requests where `r.member == B` are purged — `R` (created by `A`) is untouched, and `confirmations(R)` still contains `B`.
5. `A` calls `confirm(R)` → `confirmations(R).len()+1 == 2+1 >= 3` is false at this step but only one more live-member confirmation is needed. `C` calls `confirm(R)` → `confirmations(R).len()+1 == 2+1 = 3 >= 3`, so `execute_request` runs `R`.
6. `R` executed with confirmations from only `A` and `C` as currently live members plus a stale confirmation from removed member `B` — i.e., below the actual `3`-live-member threshold the contract is supposed to enforce.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

        assert(
            self.current_member().is_some(),

        // request must have
        assert(
            self.confirmations.get(&request_id).is_some(),
            "Internal error: confirmations mismatch requests",
        );
    }
