### Title
Signer reorg-permit scope confusion allows signing a conflicting block via an unrelated tenure's stale permit - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`SignerDb::mark_tenure_superseded` records a reorg permit keyed only by the *superseded* tenure's `consensus_hash`, and `Signer::reorg_permit_stands` validates that permit purely by asking whether the *permitting* tenure's sortition is still canonical — it never checks that the permit was granted in relation to the block currently being evaluated. Because `get_signed_conflicts` matches conflicting blocks to permits solely by the conflicting block's own tenure hash (independent of which tenure is presently trying to sign), a reorg permit legitimately earned by tenure `A` (replacing tenure `X`) can be silently consumed to excuse an unrelated tenure `D`'s conflicting block from the double-sign guard, even though `D` never passed `check_parent_tenure_choice`/the reorg-timing rules itself.

### Finding Description
The pre-commit conflict guard is designed so a signer never signs two conflicting blocks at the same height unless a specific, freshly-validated reorg was sanctioned. The sanctioning logic lives in `SortitionData::check_parent_tenure_choice`, which validates the *reorging* tenure's own commit and, only once satisfied, calls `record_superseded_tenure` → `SignerDb::mark_tenure_superseded` to persist that this specific superseding tenure may safely bypass the conflict from the tenures it reorged: [1](#0-0) 

The persisted row associates the superseded tenure's `consensus_hash` with `superseded_by_consensus_hash`/`superseded_by_burn_block_hash`: [2](#0-1) 

When a new block reaches the pre-commit threshold, `get_signed_conflicts` looks up every previously-signed conflicting block and LEFT JOINs the permit table purely by the *conflict's own* tenure hash — with no reference at all to the tenure of the block currently being evaluated: [3](#0-2) 

`reorg_permit_stands` then decides whether that permit still excludes the conflict, but it only asks the node whether the *recorded permitting sortition* is canonical — it takes no parameter identifying the block/tenure that is currently trying to get signed, so it cannot verify the permit actually pertains to that attempt: [4](#0-3) 

This function is invoked from `handle_block_pre_commit` purely as `self.reorg_permit_stands(stacks_client, conflict)`, again with no linkage to `block_info`'s own tenure: [5](#0-4) 

Consequence: once tenure `A` legitimately earns a permit to reorg tenure `X` (because `X` produced ≤1 globally-accepted block near the sortition boundary), that permit remains recorded against `X`'s `consensus_hash` and stays "standing" for as long as `A`'s sortition is canonical. Any later, *unrelated* tenure `D` whose block happens to conflict in height with a block previously signed in `X` — regardless of whether `D` is actually built on `A`, is a sibling of `A`, or has nothing to do with the sanctioned reorg at all — will have that conflict silently excluded by `reorg_permit_stands`, because the check only asks "is `A`'s sortition canonical?" and never "is `D` the tenure this permit was granted for?" `D`'s own tenure-choice/reorg-timing validation (`check_parent_tenure_choice`) is never consulted for this exclusion, so `D` can bypass the double-sign guard even if `D` itself would fail the reorg-timing rules or is not a tenure-change block at all.

### Impact Explanation
This breaks the safety invariant documented in `docs/signer-flows.md` (section 5) that the conflict guard "must not stand in the way of a replacement we sanctioned" — i.e., it must stand in the way of one we did *not* sanction. A signer can be tricked into placing a signature on a block `D` that conflicts with a block `X` it already signed, purely because an unrelated tenure `A` once earned a permit over `X`. This is a signer signing a conflicting block — the exact "Critical" class defined by the task rules (breaking the "one-per-height"/no-double-sign equality). If `A` never becomes canonical (or `D` is not actually descended from the sanctioned replacement), the signer set may end up with valid signatures over two competing chains at the same height/tenure, which is precisely the equivocation the pre-commit conflict guard exists to prevent.

### Likelihood Explanation
Triggering this requires only: (1) one prior legitimate reorg permit ever being granted (a normal, unprivileged occurrence whenever a short-lived tenure is reorged near a sortition boundary — no majority-signer collusion needed), and (2) a later, ordinary miner-controlled tenure producing a block that happens to conflict in height with the earlier superseded tenure's signed block while the permitting sortition is still canonical. Both are single-miner/gossip-controlled conditions (block proposal content and timing), matching the "one-slot miner plus gossip" threat model — no majority of signers or additional keys are required.

### Recommendation
Scope the permit check to the block actually being evaluated: `mark_tenure_superseded`/`get_signed_conflicts`/`reorg_permit_stands` should verify that the currently pre-committing block's own tenure is the recorded `superseded_by` tenure (or a descendant of it) before excluding the conflict — not merely that the permitting sortition remains canonical in isolation. Concretely, thread `block_info`'s tenure/consensus_hash into `reorg_permit_stands` and require it to match (or descend from) `conflict.superseded_by.consensus_hash` before returning `true`.

### Proof of Concept
1. Tenure `X` produces one block that the signer signs (via `mark_locally_accepted`).
2. Tenure `A` proposes a tenure-change reorging `X`; `X`'s single block satisfies the `first_proposal_burn_block_timing` window, so `check_parent_tenure_choice` returns `Ok(true)` and calls `mark_tenure_superseded(X, superseded_by=A)` (`stacks-signer/src/chainstate/mod.rs:290-294`).
3. While `A`'s sortition is still canonical, a separate/competing tenure `D` (which never itself passed `check_parent_tenure_choice` against `X`, e.g. because it is a plain block extending some other fork, or a sibling of `A` that fails the timing rule on its own) proposes a block whose `chain_length` conflicts with `X`'s signed block.
4. When `D`'s block reaches the 70% pre-commit weight threshold, `handle_block_pre_commit` calls `get_signed_conflicts`, which returns `X` annotated with `superseded_by = A` purely by `consensus_hash` join (`stacks-signer/src/signerdb.rs:1606-1625`).
5. `reorg_permit_stands(stacks_client, conflict)` queries only whether `A`'s sortition is canonical (`stacks-signer/src/v0/signer.rs:1222-1248`) — true — so the conflict is excluded and the signer signs `D`, despite `D` having no sanctioned relationship to the permit that excused it.

    /// Whether a reorg permit recorded for this conflict's tenure still stands.
    ///
    /// `check_parent_tenure_choice` records a permit when the reorg-timing rules sanction a
    /// later tenure replacing what the conflict's tenure built (see
    /// [`SignerDb::mark_tenure_superseded`]). A standing permit excludes the conflict entirely:
    /// our signature must not stand in the way of a replacement we sanctioned. But the permit
    /// is only as alive as the sortition it was granted to: if a burnchain fork orphaned the
    /// permitting sortition, the reorg we sanctioned can no longer happen, and the record must
    /// not keep suppressing the conflict.
    ///
    /// A false 404 here (e.g. from a node still catching up) only restores a conflict the
    /// permit could have excluded, which at worst delays the replacement, so unlike
    /// `conflict_still_blocks` no tip-height guard is needed. A node error voids the permit for
    /// the same reason: blocking is the direction that can be taken back.
    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }
    }
