### Title
External ERC4626 liquidity failures can indefinitely block epoch settlement - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower.onStopEpoch` converts any ERC4626 `withdraw` failure into a reverting `StopEpochVaultLiquidityUnavailable` error, even when the borrower position is solvent. `IdleCDOEpochVariant._stopEpoch` calls this hook before pulling funds and does not catch hook reverts, so an unprivileged participant who can temporarily exhaust or disable liquidity in the configured shared ERC4626 vault can repeatedly prevent `stopEpoch` from completing.

### Finding Description
`IdleCDOEpochVariant._stopEpoch` invokes `IProgrammableBorrower.onStopEpoch` before calling `getFundsFromBorrower`; a false return enters the default path, while a revert bubbles out of the entire stop transaction [1](#0-0) .

When the programmable borrower does not have enough underlying on hand, `onStopEpoch` calculates the shortfall and withdraws exactly that amount from its ERC4626 vault [2](#0-1) . The economic-solvency check only verifies that the shortfall is not larger than `convertToAssets(shares)`, but it does not verify that the vault currently has withdrawable liquidity [3](#0-2) . Any failure in `vault.withdraw` is caught locally and replaced with `StopEpochVaultLiquidityUnavailable`, which then reverts the CDO stop [4](#0-3) .

An unprivileged user of a shared lending-style ERC4626 vault can front-run each manager `stopEpoch` call and occupy the vault’s available liquidity, for example by borrowing or redeeming enough assets to make the programmable borrower’s withdrawal fail. The position remains solvent, so the attacker cannot directly seize it, but every `stopEpoch` call reverts while this condition is maintained.

The broken invariant is epoch liveness for solvent positions: `stopEpoch` should distinguish an economically insolvent borrower from a temporarily illiquid external vault and allow a recoverable settlement path. Instead, the current path conflates liquidity failure with a hard revert at the CDO boundary [5](#0-4) .

Existing guards do not prevent this. `_checkProgrammableBorrowerMode` only checks minted-interest mode and pending instant withdrawals [6](#0-5) . The surrounding `try` only covers the subsequent `getFundsFromBorrower` call, not the earlier hook call [7](#0-6) .

### Impact Explanation
The attacker can repeatedly freeze the programmable credit vault in the running-epoch state. Deposits are paused during an epoch and withdrawal-request flags are disabled when `startEpoch` executes [8](#0-7) . Because `stopEpoch` cannot complete, depositor principal and pending withdrawal claims remain inaccessible while the attacker maintains external-vault illiquidity.

The frozen amount is the pool’s full programmable-borrower exposure, represented by idle cash plus `vault.convertToAssets(vaultSharesBalance())` [9](#0-8) [10](#0-9) . For example, if the vault holds 10,000,000 USDC of pool assets and stop requires 1,000,000 USDC of pending withdrawals, leaving less than that amount withdrawable in the ERC4626 vault freezes all 10,000,000 USDC of epoch settlement even though only the withdrawal amount is needed at the stop boundary.

The freeze is temporary rather than permanent because the transaction is retryable and the borrower can potentially repay enough cash to make `onHand >= amountRequired`. The impact is therefore temporary freezing of user funds, which is an accepted impact class.

### Likelihood Explanation
Likelihood is moderate where the configured ERC4626 vault shares liquidity with unprivileged borrowers or has utilization-sensitive withdrawals. The attack does not require a privileged role, forged accounting, or control of the CDO, borrower, manager, or owner. It requires only the ability to make `vault.withdraw(shortfall, address(this), address(this))` revert at the stop block and to repeat that condition whenever settlement is retried [11](#0-10) .

Likelihood is lower for a private ERC4626 vault with guaranteed full-liquidity redemption. The issue is still implementation-dependent rather than hypothetical arithmetic speculation because `ProgrammableBorrower` accepts any owner-configured ERC4626 whose asset matches the CDO token [12](#0-11)  and relies on synchronous `withdraw` succeeding inside the epoch-state transition.

### Recommendation
Do not let a liquidity-only ERC4626 failure abort the entire `stopEpoch` transaction. Consider one of the following:

- Return a distinct retryable status from `onStopEpoch` instead of reverting, so `IdleCDOEpochVariant` can preserve the running epoch or enter an explicit liquidity-pending state without rolling back unrelated accounting.
- Pull the maximum currently withdrawable amount and expose the unfunded remainder separately, allowing partial receipt funding or pro-rata loss accounting where intended.
- Add a dedicated settlement/finalization path that permits later completion after vault liquidity returns, without requiring the original `stopEpoch` call to succeed atomically.
- Require the configured vault to provide reliable redemption guarantees, or maintain enough idle liquidity outside the vault to cover `epochPendingWithdraws`.

If partial funding is introduced, ensure the accounting remains aligned with `previewLossAdjustedWithdrawFunds`, `pendingWithdraws`, and each receipt’s epoch-level claim basis [13](#0-12) .

### Proof of Concept
The following Foundry regression isolates the production path: a public vault actor makes liquidity unavailable, the solvent programmable borrower still owns enough shares, and the CDO-facing hook reverts instead of returning a recoverable result. In the full deployment this revert bubbles out of `IdleCDOEpochVariant.stopEpoch` before `getFundsFromBorrower` is attempted.

import "forge-std/Test.sol";

contract LiquidityGriefedVault is IERC4626, IERC20Detailed {
    IERC20Detailed public immutable override asset;
    mapping(address => uint256) public override balanceOf;
    uint256 public override totalSupply;
    bool public liquidityBlocked;

    constructor(IERC20Detailed _asset) {
        asset = _asset;
    }

    function decimals() external pure override returns (uint8) { return 6; }
    function name() external pure override returns (string memory) { return "griefed vault"; }
    function symbol() external pure override returns (string memory) { return "gv"; }
    function allowance(address, address) external pure override returns (uint256) { return 0; }
    function approve(address, uint256) external pure override returns (bool) { return true; }
    function transfer(address, uint256) external pure override returns (bool) { return true; }
    function transferFrom(address, address, uint256) external pure override returns (bool) { return true; }

    function seedShares(address owner, uint256 shares) external {
        balanceOf[owner] += shares;
        totalSupply += shares;
    }

    /// @notice Public liquidity consumer used by the attacker.
    function consumeLiquidity() external {
        liquidityBlocked = true;
    }

    function releaseLiquidity() external {
        liquidityBlocked = false;
    }

    function convertToAssets(uint256 shares) external view override returns (uint256) {
        return shares;
    }

    function deposit(uint256 assets, address receiver) external override returns (uint256) {
        balanceOf[receiver] += assets;
        totalSupply += assets;
        return assets;
    }

    function withdraw(uint256 assets, address, address owner) external override returns (uint256) {
        require(!liquidityBlocked, "no shared-vault liquidity");
        require(balanceOf[owner] >= assets, "shares");
        balanceOf[owner] -= assets;
        totalSupply -= assets;
        return assets;
    }

    function redeem(uint256 shares, address receiver, address owner) external override returns (uint256) {
        return withdraw(shares, receiver, owner);
    }

    function maxWithdraw(address owner) external view override returns (uint256) {
        return liquidityBlocked ? 0 : balanceOf[owner];
    }
}

contract ProgrammableBorrowerStopLiquidityTest is Test {
    ProgrammableBorrower borrowerAdapter;
    LiquidityGriefedVault vault;
    IERC20Detailed underlying;

    address owner = makeAddr("owner");
    address manager = makeAddr("manager");
    address realBorrower = makeAddr("realBorrower");
    address idleCDO = makeAddr("idleCDO");
    address vaultUser = makeAddr("vaultUser");

    function setUp() external {
        underlying = IERC20Detailed(makeAddr("underlying"));
        vault = new LiquidityGriefedVault(underlying);
        borrowerAdapter = new ProgrammableBorrower();

        borrowerAdapter.initialize(
            address(vault),
            idleCDO,
            owner,
            manager,
            realBorrower,
            5e18
        );

        // Solvency is not in question: all 10m USDC of shares are backed 1:1.
        vault.seedShares(address(borrowerAdapter), 10_000_000e6);
    }

    function testStopEpochRevertsOnTransientVaultLiquidity() external {
        // An unprivileged participant in the shared ERC4626 liquidity pool
        // consumes/blocks the liquidity immediately before manager settlement.
        vm.prank(vaultUser);
        vault.consumeLiquidity();

        // The CDO only needs 1m USDC for pending withdrawals, much less than
        // the borrower's 10m USDC share value, but the synchronous vault
        // withdrawal fails and the entire stop path reverts.
        vm.prank(idleCDO);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        borrowerAdapter.onStopEpoch(1_000_000e6, false);

        // Retrying while the vault user maintains the liquidity condition
        // keeps the running epoch unsettled.
        vm.prank(idleCDO);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        borrowerAdapter.onStopEpoch(1_000_000e6, false);
    }
}

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
