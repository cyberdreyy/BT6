### Title
Fee-on-transfer / rebasing `token` breaks share minting and vault solvency — minted shares and strategy tokens assume nominal `_amount`, not actual received (`contracts/IdleCDOEpochVariant.sol`, `contracts/strategies/idle/IdleCreditVault.sol`, `contracts/IdleCDOCreditVault.sol`)

### Summary
The external bug class — caching the nominal `amount` instead of the balance delta for fee-on-transfer (FoT) or rebasing tokens — has a direct analog in the credit vault flow. While `IdleCDO._deposit` and `IdleCDOCreditVault._deposit` correctly measure the received amount for *share minting* via a balance delta, the downstream calls still use the nominal `_amount`: `IIdleCDOStrategy(strategy).deposit(_amount)` pulls the full nominal amount out of the CDO and `IdleCreditVault.deposit` mints `_amount` strategy tokens 1:1 regardless of what actually arrived. `depositDuringEpoch` is worse: it never measures a balance delta at all — it mints tranche shares from `_amount`, calls `mintStrategyTokens(_amount)`, and forwards the full `_amount` to the borrower.

### Finding Description
Three concrete mismatches with a FoT `token` (e.g. USDT/USDC if fees are enabled, PAXG, STA) or a rebasing token:

1. `IdleCDOCreditVault._deposit` (`contracts/IdleCDOCreditVault.sol:202-211`): shares are minted on the balance delta (`_contractTokenBalance(_token) - _preBal`), but `IIdleCDOStrategy(strategy).deposit(_amount)` then pulls the *nominal* `_amount` via `underlyingToken.safeTransferFrom(msg.sender, address(this), _amount)` in `IdleCreditVault.deposit` (`contracts/strategies/idle/IdleCreditVault.sol:601-604`). The CDO received only `_amount - fee`, so the shortfall is taken from existing vault liquidity belonging to other depositors.

2. `IdleCreditVault.deposit` (`contracts/strategies/idle/IdleCreditVault.sol:603-605`): `_mint(msg.sender, _amount)` mints strategy tokens 1:1 with the nominal amount, not the received amount. Strategy tokens are the vault's internal claim on underlying — supply is inflated by the fee relative to actual holdings, permanently decoupling strategy-token redemption value from real liquidity.

3. `IdleCDOEpochVariant.depositDuringEpoch` (`contracts/IdleCDOEpochVariant.sol:684-732`): `_transferUnderlyingsFrom(msg.sender, address(this), _amount)` is followed by share minting `(_amount + trancheInterest) * _trancheTotSupply / expectedFinal`, `mintStrategyTokens(_amount)`, and `_transferUnderlyings(_borrower(), _amount)` — all using the nominal `_amount`. For a FoT token the contract received `_amount - fee` but still sends the full `_amount` to the borrower; the fee shortfall is extracted from pooled tranche-holder liquidity, and the depositor is additionally credited as if they supplied the full amount.

For rebasing tokens, `getContractValue()` is computed from live `balanceOf`, so a positive rebase is booked as yield (inflating `unclaimedFees` and NAV) and a negative rebase is socialized as a loss that can trigger the default path in `_updateAccounting`, even though no real gain/loss occurred.

### Impact Explanation
Broken invariant: solvency / fair mint/burn. Every FoT deposit mints strategy tokens and forwards funds in excess of what was received, so aggregate claims exceed real underlying. The loss is socialized across tranche holders; the last withdrawers/claimants (via `requestWithdraw` / `claimWithdrawRequest` or normal `withdrawAA/BB`) revert on insufficient liquidity — the same "last users can't withdraw" outcome as the external report. The loss is quantifiable: `sum(fees taken on each deposit)` becomes permanently unbacked strategy-token supply and claims.

### Likelihood Explanation
The underlying is fixed at deployment, so the issue activates only if the configured token takes a transfer fee or rebases. The protocol targets stablecoin credit vaults; USDC/USDT are upgradeable and USDT already supports fee hooks — the same argument the original report used for a High severity. No attacker action is needed beyond an ordinary deposit; any unprivileged KYC'd wallet calling `depositAA`/`depositBB`/`depositDuringEpoch` triggers the leakage.

### Recommendation
- In `IdleCDOCreditVault._deposit` / `IdleCDOEpochVariant.depositDuringEpoch`, compute `received = _contractTokenBalance(token) - _preBal` after the pull and use `received` (not `_amount`) for `strategy.deposit`, `mintStrategyTokens`, share minting, and the borrower forwarding.
- In `IdleCreditVault.deposit`, measure `balanceOf` before/after `safeTransferFrom` and `_mint(msg.sender, received)`.
- Alternatively, enforce a token allowlist at vault deployment and document that FoT/rebasing underlyings are unsupported.

### Proof of Concept
Foundry fork test sketch:

```solidity
// 1. Deploy/configure the vault with a FoT token mock (e.g. 1% burn-on-transfer USDT variant).
// 2. Seed the vault: honest user A deposits 10_000e6 via depositAA.
// 3. Attacker/user B (KYC'd wallet) calls cdoEpoch.depositAA(10_000e6):
//    - CDO receives 9_900e6, mints shares for 9_900e6 (balance-delta is correct here),
//      but IdleCreditVault.deposit transfers 10_000e6 out and mints 10_000e6 strategy tokens.
//    - assertEq(strategyToken.balanceOf(cdo), 10_000e6) while only 9_900e6 of B's deposit
//      backs it; 100e6 of user A's principal is consumed.
// 4. Repeat: each deposit leaks `fee` from existing NAV.
// 5. On withdraw: user A requestWithdraw/withdrawAA for full tranche value reverts or returns
//    less than pro-rata once cumulative fees exceed spare liquidity.
// 6. Mid-epoch variant: enable depositDuringEpoch, startEpoch, warp mid-epoch; B deposits
//    10_000e6 FoT -> borrower receives 10_000e6 while only 9_900e6 arrived; the deficit is
//    borrowed against the pool's buffer, and expectedEpochInterest overcounts by `fee` too.
```

Asserts: `underlying.balanceOf(strategy) + outstandingDebt < totalStrategyTokenSupply` grows with every deposit, and the final `claimWithdrawRequest`/`withdrawAA` for an earlier depositor reverts with insufficient balance.
