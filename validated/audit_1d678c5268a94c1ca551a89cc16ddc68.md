### Title
External Initiator authenticates as a fabricated zero-value User, defeating identity checks that rely on `GetAuthenticatedUser` - (File: core/web/auth/auth.go)

### Finding Description
`AuthenticateExternalInitiator` does not merely grant "run" privileges to an EI — it injects a synthetic `*clsessions.User{Role: clsessions.UserRoleRun}` into the gin context under the same `SessionUserKey` used for real, DB-backed users: [1](#0-0) .

`GetAuthenticatedUser` simply type-asserts the context value to `*clsessions.User` and returns `ok=true` if that assertion succeeds, with no way to tell a real `AuthenticateBySession`/`AuthenticateByToken` user apart from the EI's fabricated placeholder: [2](#0-1) . `RequiresRunRole` (lines 202-217) only checks `user.Role != UserRoleView`, which the EI's forced `UserRoleRun` value trivially satisfies: [3](#0-2) .

This directly breaks the explicit intent encoded in `PipelineRunsController.Create`, the only `RequiresRunRole` handler reachable by EI credentials via `POST /v2/jobs/:ID/runs` (registered on the `userOrEI` route group together with `AuthenticateExternalInitiator`): [4](#0-3) . The handler's own comment says "only users are allowed to run jobs using int IDs - EIs not allowed", and gates on `_, isUser := auth.GetAuthenticatedUser(c)`: [5](#0-4) . Because the EI-forced pseudo-user is a real `*clsessions.User` value (zero-value `Email`, `ID`, etc.), `isUser` evaluates to `true` for an EI caller exactly as it would for a genuine user — the intended EI restriction is a no-op due to identity-type confusion at the auth layer, not a policy enforced by data.

The other `RequiresRunRole` endpoints (`/replay_from_block/:number`, `/find_lca`, `/lp_skip_to_block`, dev-only `/execute_capability`) are registered only on `authv2` (session/token-only group), so they are not reachable by EI credentials alone: [6](#0-5) . I found no `Audit(...)` call inside `PipelineRunsController.Create` that logs `user.Email`, so the specific "audit log falsely attributes a job run to a named user via `user.Email`" scenario is not concretely demonstrated in the reachable code path — that part of the hypothesis is unproven. What is concretely proven is that the same root cause (an EI is indistinguishable from a real `*clsessions.User` once past `GetAuthenticatedUser`) defeats an explicit, code-documented authorization boundary ("EIs not allowed" for int-ID job runs).

### Impact Explanation
An EI-credential holder (a lower-privilege, narrowly-scoped credential intended only to trigger runs on jobs specifically wired to that EI) can trigger runs of **any** job by integer ID via `POST /v2/jobs/:ID/runs`, bypassing the code's explicit "EIs not allowed" restriction for this call path, because the identity-confusion in `GetAuthenticatedUser`/`AuthenticateExternalInitiator` makes an EI indistinguishable from a real user for any code that trusts `GetAuthenticatedUser`'s boolean result as a proxy for "is a genuine authenticated user." This is an authorization-bypass class issue: unauthorized action (triggering an arbitrary job run) using a credential that was not supposed to be able to perform it via that route. It also creates latent risk for any future/other code that assumes `GetAuthenticatedUser` returning `ok=true` implies a real, attributable `User` record (e.g., for logging, auditing, or per-user resource scoping) — such code would silently attribute the actor as a blank/zero-value user rather than correctly identifying it as an EI.

### Likelihood Explanation
Only a valid EI `AccessKey`/`Secret` pair is required — no admin, session, or API-token credential needed. This is fully reachable over the standard public/API-facing HTTP router without any host or operator access. It is trivially repeatable and deterministic (same fabricated user object is set on every EI-authenticated request).

### Recommendation
Do not represent an External Initiator's implicit run privilege using the same `*clsessions.User` type/context key as real users. Introduce a distinct context flag/type (e.g., a boolean "isExternalInitiator" or a dedicated `Actor`/`Identity` interface with an explicit kind) so that:
- `GetAuthenticatedUser` only returns `ok=true` for genuine, DB-backed users.
- `PipelineRunsController.Create`'s `isUser` check (and any other code relying on `GetAuthenticatedUser` to gate "real user only" logic) correctly excludes EI-authenticated requests.
- Role-checking middleware (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`) can still authorize EIs for endpoints that intentionally allow them, without conflating them with real users for identity-sensitive logic (audit logging, per-user resource ownership, etc.).

### Proof of Concept
Handler-level integration test in `core/web`:
1. Set up a test app with an `ExternalInitiator` record (valid AccessKey/Secret) and no `User` record correlated to it.
2. Create a job with a known integer ID not associated with that EI.
3. Send `POST /v2/jobs/:ID/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (per `static.ExternalInitiatorAccessKeyHeader/SecretHeader`) and no session cookie or API token.
4. Assert current (buggy) behavior: response is `200 OK` with a `pipelineRun` resource (i.e., `RunJobV2` was invoked) — demonstrating that despite the `// EIs not allowed` comment in `PipelineRunsController.Create`, the run succeeds because `isUser` (from `auth.GetAuthenticatedUser`) is `true`.
5. Add a unit test on `auth.GetAuthenticatedUser` directly: call `AuthenticateExternalInitiator` against a `gin.Context`, then call `GetAuthenticatedUser(c)` and assert it returns `ok=true` with a `User{Email: "", ID: ""}` — proving the type confusion at the source.
6. Expected fixed behavior: `GetAuthenticatedUser` returns `ok=false` for EI-only authenticated contexts, and `PipelineRunsController.Create` responds `422 Unprocessable Entity` ("bad job ID"/EI not allowed) for EI credentials, matching the documented intent.

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
