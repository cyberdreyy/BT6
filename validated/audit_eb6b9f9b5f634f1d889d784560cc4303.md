### Title
Withdrawal receipts retain a stale epoch APR after mid-buffer APR updates - ([contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`requestWithdraw` permanently prices a withdrawal receipt using the strategy APR stored at request time, but the manager can still replace that next-epoch APR during the buffer before `startEpoch` freezes the epoch. An unprivileged lender can front-run an APR reduction with a withdrawal request and receive a receipt containing yield calculated under the old APR, forcing the borrower to fund excess principal at epoch settlement or triggering a borrower default.

### Finding Description
A withdrawal request converts tranche tokens to a fixed underlying receipt by valuing principal at the current tranche price, projecting the next epoch’s interest, subtracting fees, recording the resulting `_underlyings`, and burning the user’s tranche tokens. [1](#0-0)  The projected interest is derived from `_getStrategyApr()`, `epochDuration`, and `bufferPeriod` at request time. [2](#0-1) [3](#0-2) 

`IdleCreditVault` nevertheless lets the CDO or manager replace both the unscaled APR and scaled APR through `setAprsWithBuffer` or `setAprs` while withdrawal requests are already outstanding. [4](#0-3)  The existing receipt remains minted for the stale amount because `requestWithdraw` stores the exact claim amount in `withdrawsRequests` and `pendingWithdraws`. [5](#0-4) 

At `startEpoch`, borrower interest expectations are recalculated using the newly installed APR, but the stale receipt remains separately payable as pending withdrawal principal. [6](#0-5)  At `stopEpoch`, the CDO pulls the new expected interest plus the full stale `pendingWithdraws` amount from the borrower and transfers the latter to the strategy. [7](#0-6) 

For example, a lender can request a withdrawal while the next-epoch APR is 10%, after which the manager legitimately lowers it to 1%. The receipt retains yield projected at 10%, while new accounting uses 1%; the lender still claims the original 10%-based amount after the epoch. [8](#0-7)  The APR-dependent instant-withdrawal branch only affects subsequent requests and does not correct already created receipts. [9](#0-8) 

### Impact Explanation
When APR decreases after a request, the attacker receives interest for an epoch rate that no longer exists, and the excess is funded by the borrower when `pendingWithdraws` is collected. [10](#0-9)  If the borrower cannot or does not provide the stale excess amount, `getFundsFromBorrower` fails and `_handleBorrowerDefault` marks the pool defaulted. [11](#0-10) [12](#0-11) 

When APR increases after a request, the inverse occurs: the requester’s already-burned tranche position is fixed to the lower APR quote and cannot receive the higher final epoch rate. [1](#0-0) 

### Likelihood Explanation
APR updates during the buffer are an explicitly supported manager action rather than privileged misbehavior. [4](#0-3)  A lender can monitor a pending APR-reduction transaction or otherwise request withdrawal before a scheduled rate adjustment, with no privileged access required. No existing guard blocks APR changes while requests are outstanding, and the stale receipt survives both `startEpoch` and `stopEpoch`. [13](#0-12) 

### Recommendation
Make next-epoch parameters immutable once withdrawal requests open, or reprice all pending receipts from a frozen parameter snapshot selected at `stopEpoch`/`startEpoch`. At minimum, prevent `setApr`, `setAprs`, `setAprsWithBuffer`, and `setEpochParams` from changing APR or timing parameters while `pendingWithdraws != 0`; alternatively, store the APR used by each request and settle the epoch consistently against that frozen value. [4](#0-3) [14](#0-13) 

### Proof of Concept

```solidity
function testWithdrawReceiptUsesStaleAprAfterMidBufferAprUpdate() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);

    uint256 highApr = 10e18;
    uint256 lowApr = 1e18;
    uint256 depositAmount = 10_000 * ONE_SCALE;

    address staleRequester = makeAddr("staleRequester");
    address fairRequester = makeAddr("fairRequester");

    _depositWithUser(staleRequester, depositAmount, false);
    _depositWithUser(fairRequester, depositAmount, false);

    uint256 requesterTranches =
        IERC20Detailed(address(AAtranche)).balanceOf(staleRequester);
    assertEq(
        requesterTranches,
        IERC20Detailed(address(AAtranche)).balanceOf(fairRequester),
        "different quote bases"
    );

    // Finish epoch 0 and publish a 10% APR for the next epoch.
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, highApr, _expectedFundsEndEpoch());

    // The lender fixes a normal withdrawal receipt while the published APR is 10%.
    vm.prank(staleRequester);
    uint256 staleReceipt =
        cdoEpoch.requestWithdraw(requesterTranches, address(AAtranche));

    // A later honest manager operation reduces the next epoch's APR to 1%.
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprsWithBuffer(
        lowApr,
        cdoEpoch.epochDuration(),
        cdoEpoch.bufferPeriod()
    );

    // An identical position quoted under the final APR receives materially less.
    uint256 fairReceipt =
        cdoEpoch.maxWithdrawable(fairRequester, address(AAtranche));

    assertGt(
        staleReceipt,
        fairReceipt,
        "receipt did not retain stale high-APR yield"
    );

    uint256 borrowerBefore =
        IERC20Detailed(defaultUnderlying).balanceOf(
            IdleCreditVault(address(strategy)).borrower()
        );

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, lowApr, _expectedFundsEndEpoch());

    uint256 requesterBefore =
        IERC20Detailed(defaultUnderlying).balanceOf(staleRequester);

    vm.prank(staleRequester);
    cdoEpoch.claimWithdrawRequest();

    uint256 requesterAfter =
        IERC20Detailed(defaultUnderlying).balanceOf(staleRequester);
    uint256 borrowerAfter =
        IERC20Detailed(defaultUnderlying).balanceOf(
            IdleCreditVault(address(strategy)).borrower()
        );

    assertEq(
        requesterAfter - requesterBefore,
        staleReceipt,
        "stale receipt was not paid at its original amount"
    );
    assertGt(
        staleReceipt - fairReceipt,
        0,
        "borrower funded excess withdrawal yield"
    );
    assertGe(
        borrowerBefore + staleReceipt - fairReceipt,
        borrowerAfter,
        "borrower balance did not cover the withdrawal settlement"
    );
}
```

The assertion `staleReceipt > fairReceipt` demonstrates that the receipt contains yield priced under the superseded APR, while the successful claim proves that the borrower still funds that obsolete quote. [5](#0-4) [10](#0-9)

  function _handleBorrowerDefault(uint256 funds) internal {

  function requestWithdraw(uint256 _amount, address _tranche) external returns (uint256 _underlyings) {
    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
      !isWalletAllowed(msg.sender)
    );
  
    // we check if there are donated assets to the pool and transfer them to the feeReceiver if any
    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;

    pendingWithdrawFees += totalFees;

    /// if there is an AA withdrawal the overperformance that the amount withdrawed would have generated for BB tranches
    /// is saved in interestForOverUnderPerformance. This is used to calculate the interest that should be added to the
    /// expectedEpochInterest at the startEpoch.
    /// If there is a BB withdrawal this amount is subtracted from the expectedEpochInterest
    interestForOverUnderPerformance += diff;

    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
    creditVault.requestWithdraw(_underlyings, msg.sender, principal);
    // burn tranche tokens and decrease NAV without interest for the next epoch as it was not yet counted in NAV
    _withdrawOps(_amount, principal, _tranche);

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
