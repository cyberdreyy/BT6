### Title
Contract depositors cannot withdraw because `_withdraw` force-sends a PoLido ERC-721 via `safeTransferFrom`, requiring `IERC721Receiver` support - (File: contracts/IdleCDOPoLidoVariant.sol)

### Summary
Analogous to forcing a draft receiver interface (EIP-4524) on transfer recipients, `IdleCDOPoLidoVariant._withdraw` unconditionally delivers the redemption as a PoLido NFT via `safeTransferFrom` to `msg.sender` at `contracts/IdleCDOPoLidoVariant.sol:78`. Any contract LP that does not implement `IERC721Receiver.onERC721Received` can deposit and mint tranche tokens normally but can never complete a withdrawal: the final `safeTransferFrom` always reverts, permanently freezing their entire position.

### Finding Description
`_withdraw` in `IdleCDOPoLidoVariant.sol:40-79` performs the full withdrawal path (same-block check, `_checkDefault`, `_updateAccounting`, pricing, `_liquidate`, `IdleCDOTranche.burn`, NAV updates) and then finishes with:

```solidity
uint256 tokenId = tokenIds[tokenIds.length - 1];
stMatic.poLidoNFT().safeTransferFrom(address(this), msg.sender, tokenId);
```

`safeTransferFrom` on an ERC-721 invokes `onERC721Received` on `msg.sender` whenever it is a contract and reverts if the return value is not the selector. The deposit path (`_deposit`, lines 26-33) imposes no such requirement — a contract can deposit underlying, receive fungible tranche tokens, but the exit path demands a callback interface. Since the revert happens at the end of the transaction, the `burn` and NAV updates roll back too, so the user simply cannot withdraw at all; there is no alternative redemption path that pays out ERC-20 underlying instead of the NFT.

Note also that the design is strictly stronger than a composability annoyance: the withdrawal always delivers exactly one NFT (`tokenIds[tokenIds.length - 1]`), so the receiver check is unavoidable for any non-EOA holder.

### Impact Explanation
Any contract-based LP (vault, strategy contract, DAO treasury, smart account without an ERC-721 handler) that deposits into the AA or BB tranche has its funds permanently frozen: every `_withdraw` call reverts at the `safeTransferFrom`. The loss equals the full value of the contract's tranche position (principal plus accrued interest). This is a permanent-freezing impact with a quantified loss equal to the affected position, matching the "cannot be used by receiver contracts" bug class.

### Likelihood Explanation
Likelihood is moderate: unprivileged depositors are routinely contracts (aggregators, smart wallets, yield vaults), and many ERC-20-only contracts do not implement `onERC721Received`. The only trigger is a normal user-initiated withdraw after a deposit — no privileged action, oracle manipulation, or exotic epoch phase is required; it works in any epoch state where withdraws are enabled and PoLido NFTs have been minted by `_liquidate`. The guard set (`_checkSameBlock`, `_checkDefault`, `nonReentrant`) does not mitigate it. Caveat: this is specific to the PoLido variant of the CDO; the standard `IdleCDO`/`IdleCreditVault` withdrawal paths pay ERC-20 underlying via `safeTransfer` and are not affected. If this variant is considered a legacy strategy, the finding may be out of scope.

### Recommendation
Deliver a fungible asset on withdrawal (e.g., sell/claim the NFT redemption and pay underlying, or transfer the NFT with `transferFrom` instead of `safeTransferFrom`), or offer a fallback claim path so contract LPs that cannot receive ERC-721 are not permanently locked. At minimum, document the ERC-721 receiver requirement at deposit time and revert early in `_deposit` for contracts lacking `IERC721Receiver` support.

### Proof of Concept
Foundry fork test against Polygon mainnet with `stMatic`/PoLidoNFT deployed at their constants:

```solidity
contract NonReceiver {
    IdleCDOPoLidoVariant cdo;
    function deposit(uint256 amt) external {
        IERC20(matic).approve(address(cdo), amt);
        cdo.depositAA(amt);
    }
    function withdraw(uint256 amt) external {
        cdo.withdrawAA(amt); // reverts: onERC721Received missing
    }
    // note: no onERC721Received implemented
}

function testContractDepositorFrozen() public {
    NonReceiver lp = new NonReceiver();
    deal(matic, address(lp), 1000e18);
    lp.deposit(1000e18);             // succeeds, tranche tokens minted to lp
    vm.warp(block.timestamp + 1 days);
    vm.expectRevert();               // ERC721: transfer to non ERC721Receiver
    lp.withdraw(0);                  // withdraw always reverts at safeTransferFrom
}
```

The same revert occurs after unstaking matures; the tranche tokens and their claim on NAV remain locked indefinitely for that depositor.
