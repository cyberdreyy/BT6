### Title
`getProgramAccounts`/`getMultipleAccounts` fail entirely when a single matched account cannot be Base58-encoded - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_program_accounts` collects the encoded result of every account returned by a program scan using `.collect::<Result<Vec<_>>>()?` [1](#0-0) . Because `encode_account` for `UiAccountEncoding::Base58`/`Binary` can fail when an account's data (after any `dataSlice`) exceeds `MAX_BASE58_BYTES` (128 bytes) [2](#0-1) , a *single* oversized account among the (possibly thousands of) accounts owned by `program_id` causes the entire RPC call to return an error instead of the accounts that could be encoded successfully. The same iterate-and-`?`-per-item pattern exists in `get_multiple_accounts`, where each per-pubkey lookup uses `?` inside the loop over `pubkeys` [3](#0-2) .

### Finding Description
This is directly analogous to the Sherlock `payOffDebtAll` bug: iterating over a collection of independent items (protocols/accounts) where one item's failure (insufficient debt-payment balance / oversized account data) aborts processing for *all* items, rather than being isolated to just that item.

In `get_program_accounts`, when `encoding` is `Base58`/`Binary` (the default for `getProgramAccounts`, see `encoding.unwrap_or(UiAccountEncoding::Binary)` at line 621) and no (or an insufficiently small) `dataSlice` is supplied, any single returned account whose data slice is larger than 128 bytes causes `encode_account` to return an `Err`, which is then propagated with `?` out of the `.collect::<Result<Vec<_>>>()?` and aborts the whole `getProgramAccounts` response — even if the vast majority of the program's accounts would have encoded fine. Because any unprivileged client can deploy a program and create one account owned by it with >128 bytes of data, this failure mode is fully attacker-controlled: any client can make `getProgramAccounts` for that `program_id` permanently fail for every caller (not just the attacker) by simply owning one oversized account under that program, unless callers pass `Base64`/`jsonParsed` encoding or an appropriate `dataSlice`.

### Impact Explanation
This causes wrong behavior for a legitimate, unprivileged, single-call RPC request: `getProgramAccounts` returns an error for the entire account set instead of the requested/available account data, denying correct data to all callers querying that program id with default/Base58 encoding — the same "single bad item blocks work for everyone" failure class as the original finding. It does not crash the validator process and requires no elevated privileges to trigger (just funding one small account owned by any program with >128 bytes of data).

### Likelihood Explanation
High: any user can deploy a program (or use any existing program) and create/own a data account exceeding 128 bytes, then simply querying `getProgramAccounts` with default encoding will trip this. No special timing, cost, or multiple calls needed — a single `getProgramAccounts` call to an affected program id is sufficient to observe the failure.

### Recommendation
In `get_program_accounts` (and similarly `get_multiple_accounts`), do not fail the whole response when one account cannot be encoded in the requested format. Encode accounts fallibly per-item, and either 1) return the encode error inline for just that account (similar to how `encode_bs58` already degrades gracefully to an `"error: data too large..."` string rather than propagating an `Err`) [4](#0-3) , or 2) skip/mark that entry rather than aborting the `collect` for the entire batch [1](#0-0) .

### Proof of Concept
1. Deploy or pick any `program_id`.
2. Create one account owned by `program_id` with account data length > 128 bytes (trivial with the System Program's `createAccount`/`allocate` + reassign to `program_id`, or any custom program).
3. Also create additional normal (small) accounts owned by the same `program_id`.
4. Call `getProgramAccounts(program_id)` with default configuration (no `encoding`, no `dataSlice`).
5. Observe the RPC call returns an error (from the failed Base58 encode of the oversized account) instead of the list of all accounts owned by `program_id`, even though the smaller accounts could have been encoded successfully — matching the exact `rpc/src/rpc.rs:656-666` `.collect::<Result<Vec<_>>>()?` code path.

pub const MAX_BASE58_BYTES: usize = 128;

fn encode_bs58<T: ReadableAccount>(
    account: &T,
    data_slice_config: Option<UiDataSliceConfig>,
) -> String {
    let slice = slice_data(account.data(), data_slice_config);
    if slice.len() <= MAX_BASE58_BYTES {
        bs58::encode(slice).into_string()
    } else {
        "error: data too large for bs58 encoding".to_string()
    }
}
