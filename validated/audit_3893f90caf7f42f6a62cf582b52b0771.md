### Title
Signer weight double-counted across accept/reject buckets when a signer flips from `Rejected` to `Accepted` for the same block — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tallies signer weight for a proposed block into two independent counters, `total_weight_approved` and `total_weight_rejected`, using two different de-duplication keys (`gathered_signatures` for accepts, `responded_signers` for both). If a signer first sends `BlockResponse::Rejected` and later sends `BlockResponse::Accepted` for the *same* `signer_signature_hash`, the reject weight is never removed and the accept weight is additionally added, so a single signer's weight is counted in both buckets simultaneously. This breaks the "aggregated weight equals current verified opinions" invariant that `SignCoordinator::wait_on_block_signatures` relies on to decide whether a block is globally rejected or accepted.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the `BlockResponse::Rejected` arm records the vote like this: [1](#0-0) 

`responded_signers.insert(slot_id)` is the *only* gate for the rejection weight; once inserted, it stays in `responded_signers` for the life of the `BlockStatus`.

The `BlockResponse::Accepted` arm, however, uses a completely different set to decide whether to add weight: [2](#0-1) 

The check is `!block.gathered_signatures.contains_key(&slot_id)`, not `!block.responded_signers.contains(&slot_id)`. Since `gathered_signatures` is only ever populated by the `Accepted` arm, a signer that previously sent `Rejected` (so `slot_id` is in `responded_signers` but not in `gathered_signatures`) will have their weight added to `total_weight_approved` on the follow-up `Accepted` message — while their earlier weight contribution to `total_weight_rejected` is never removed or corrected.

Note the reverse direction is actually guarded: if a signer sends `Accepted` first, `responded_signers.insert(slot_id)` already happened in that arm, so a later `Rejected` message from the same signer is a no-op (`if block.responded_signers.insert(slot_id) { … }` returns `false`). Only the `Rejected → Accepted` ordering is exploitable.

The consumer of this tally, `SignCoordinator::wait_on_block_signatures` in `signer_coordinator.rs`, evaluates the reject condition *before* the accept condition each loop iteration: [3](#0-2) [4](#0-3) 

Because `total_weight_rejected` can retain stale weight from a signer who has already switched to `Accepted`, the miner can incorrectly conclude the block is globally rejected (crossing the `blocking_minority` threshold) even though the true, current set of opinions would legitimately clear the acceptance threshold. This is exactly the "aggregated-weight vs verified-accepts" equality called out as a target class: the aggregated counters diverge from what a re-derivation from current, per-signer votes would show.

### Impact Explanation
This is a liveness/equality break in the miner-side vote tally, not requiring a majority of signers — only one equivocating (or simply slow-then-reconsidering) signer needs to send `Rejected` then `Accepted` for the same block. The consequence:
- `total_weight_rejected` is permanently inflated with weight that no longer reflects that signer's actual vote.
- The reject branch is checked first in `wait_on_block_signatures`, so a block that has legitimately reached (or would reach) the ≥70% approval threshold can instead be treated as rejected, causing the miner to abort with `NakamotoNodeError::SignersRejected`, discard the block, and even permanently/temporarily exclude transactions based on `failed_txids` weight computed against this corrupted denominator.
- This can repeatedly stall block production for a single miner/tenure attempt, a concrete liveness wedge triggerable by a single non-colluding signer flipping their vote (which is a legitimate, permitted sequence — e.g., a signer that rejects on stale info then re-validates and accepts).

### Likelihood Explanation
Any signer can trigger this simply by sending a `Rejected` message and later a valid `Accepted` message for the same `signer_signature_hash` — both are normal, permitted signer behaviors (e.g., re-evaluating a block after a rejection due to timing/state, then validating and signing). No StackerDB replay, majority collusion, or malformed message is required; only ordinary message ordering over the wire, which the local listener does not protect against.

### Recommendation
Use a single per-signer response state (or the existing `responded_signers` set) to gate weight additions in *both* the `Accepted` and `Rejected` arms, and when a signer's vote changes, subtract their weight from the previous bucket before adding it to the new one (or, simpler, only allow a signer's first response to count and ignore/log subsequent conflicting responses, consistent with the existing `Rejected`-then-`Accepted` guard already present in the `Rejected` arm).

### Proof of Concept
1. Miner proposes block `B` with `signer_signature_hash = H`; `BlockStatus` for `H` starts with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected(H)`. In `stackerdb_listener.rs` lines 486-591, `responded_signers.insert(S)` succeeds, so `total_weight_rejected += w`.
3. Signer `S` reconsiders (e.g., after a chainstate recheck) and sends `BlockResponse::Accepted(H)` with a valid signature. In lines 386-465, the guard `!gathered_signatures.contains_key(&S)` is true (since `gathered_signatures` was never touched for `S`), so `total_weight_approved += w` as well; `total_weight_rejected` is left at its stale value.
4. Now `total_weight_approved + total_weight_rejected` exceeds the true total signer weight tied to distinct opinions, and `total_weight_rejected` no longer reflects `S`'s current vote.
5. If other signers' genuine rejects plus this stale `w` push `total_weight_rejected.saturating_add(weight_threshold) > total_weight` in `signer_coordinator.rs` (lines 509-520) before `total_weight_approved` is checked (line 541), the miner errors out with `SignersRejected` and discards the block, even though the real, current opinion set (excluding `S`'s stale reject) may have already reached the acceptance threshold.
