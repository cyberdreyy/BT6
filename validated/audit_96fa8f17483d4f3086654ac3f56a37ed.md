### Title
Miner-side signer response aggregation double-counts a signer's weight into both `total_weight_approved` and `total_weight_rejected` on reject→accept flip - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The mining node's `StackerDBListener` tallies `BlockResponse::Accepted`/`BlockResponse::Rejected` messages into two independent weight counters, `total_weight_approved` and `total_weight_rejected`, which drive `SignerCoordinator`'s decision to push a block or abandon it. Unlike the actual signer-side consensus bookkeeping in `stacks-signer/src/signerdb.rs`, which explicitly clears a signer's prior rejection record when that signer later signs (confirmed by the `reject_then_accept` test), the miner-side listener never clears or reconciles the opposite bucket. A signer that legitimately reconsiders a rejected block and later accepts it (a state transition explicitly permitted by the signer state machine, `LocallyRejected -> LocallyAccepted`) ends up contributing its weight to *both* totals simultaneously, permanently inflating `total_weight_rejected` with a stale, withdrawn opinion.

### Finding Description
In `handle_block_proposal`/`store_and_process_block_signature` (signer side, `stacks-signer/src/v0/signer.rs` + `stacks-signer/src/signerdb.rs`), signature storage explicitly removes a signer's earlier rejection record so `total_reject_weight` and `total_signature_weight` remain mutually exclusive per signer — verified directly by the unit test `reject_then_accept`: [1](#0-0) 

The CHANGELOG documents this as an intentional fix: "Do not count both a block acceptance and a block rejection for the same signer/block." [2](#0-1) 

However, the mining node's independent aggregation path in `stackerdb_listener.rs` does not implement this invariant. The `Accepted` branch only checks `gathered_signatures` (a map populated exclusively by prior `Accepted` messages) before adding weight to `total_weight_approved`: [3](#0-2) 

The `Rejected` branch, by contrast, dedups against the shared `responded_signers` set (which the `Accepted` branch also populates): [4](#0-3) 

Because the two branches use different dedup sets (`gathered_signatures` vs. `responded_signers`) and neither branch removes the signer's entry from the *other* bucket, the two orderings are asymmetric:
- Accept → Reject: the later Reject is suppressed (since `responded_signers` already contains the slot from the earlier Accept), so no double count occurs in this direction.
- Reject → Accept: the earlier Reject adds the signer's weight to `total_weight_rejected` and marks `responded_signers`. The later Accept checks `gathered_signatures` (still empty for this slot) so it unconditionally adds the *same* signer's weight to `total_weight_approved` as well, while `total_weight_rejected` is never decremented.

This aggregation directly feeds `SignerCoordinator::get_block_status`'s rejection/acceptance decision loop, which compares `total_weight_rejected` against a blocking-minority threshold and `total_weight_approved` against the approval threshold to decide whether to push the block or fail the mining attempt and exclude flagged transactions: [5](#0-4) 

### Impact Explanation
The reject→accept flip is not a hypothetical attacker action requiring extra privilege — it is an explicitly supported protocol behavior: signers are documented to "reconsider a block proposal that it previously rejected" for some rejection reasons, and the `BlockState` diagram explicitly allows `LocallyRejected -> LocallyAccepted` transitions. Any single ordinary signer that rejects and then reconsiders (or a network delay that reorders delivery of a signer's own two responses) will leave permanently stale weight in `total_weight_rejected` on the miner's aggregation. If enough signers independently reconsider, the miner can compute `total_weight_rejected` as exceeding the true blocking minority even though every one of those signers currently supports the block, causing the miner to wrongly treat a block that has real ≥70% current support as globally rejected, aborting the mining attempt (`NakamotoNodeError::SignersRejected`) and possibly excluding transactions based on inflated "problematic weight." This is a liveness degradation matching the "acting on a stale... threshold" analog class (High impact): the miner acts on a stale, no-longer-valid rejection weight rather than a currently accurate one, unnecessarily stalling block production and forcing re-mining even when the signer set genuinely supports the block.

### Likelihood Explanation
This requires no majority collusion or key compromise — it is triggered by the ordinary, protocol-sanctioned behavior of a single signer changing its mind about a block (reject, then later accept for the same `signer_signature_hash`), which the codebase's own tests and CHANGELOG confirm is expected and already specifically guarded against on the signer's own consensus bookkeeping path. The bug is that the guard was implemented once (in `signerdb.rs`) but the independently-implemented, structurally similar aggregation in the miner's `stackerdb_listener.rs` was never given the equivalent fix, making it a real, reachable divergence rather than a theoretical one.

### Recommendation
In `stackerdb_listener.rs`, make the `Accepted` and `Rejected` handlers mutually exclusive per signer by deduping both branches against the same set (`responded_signers`), and when an accept follows an earlier reject for the same slot, subtract that signer's weight back out of `total_weight_rejected` (and vice versa if backing out a reject-after-accept is ever allowed), mirroring the invariant already implemented in `stacks-signer/src/signerdb.rs`'s `add_block_signature`/`add_block_rejection_signer_addr` pair.

### Proof of Concept
1. Miner proposes block B; `SignerCoordinator`/`StackerDBListener` starts tracking `BlockStatus` for B with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight w) initially rejects B due to a reconsiderable reason (e.g. a transient chainstate mismatch): `stackerdb_listener.rs` records `total_weight_rejected += w`, `responded_signers.insert(slot_S)`.
3. S re-evaluates (per the documented reconsideration feature) and later signs/accepts B, broadcasting `BlockResponse::Accepted`.
4. In the `Accepted` handler, `block.gathered_signatures.contains_key(&slot_S)` is `false` (only `Accepted` messages populate this map), so the handler adds `total_weight_approved += w` and inserts into `gathered_signatures`/`responded_signers`.
5. Result: `total_weight_rejected` still includes `w` from step 2 (never removed) while `total_weight_approved` also includes `w` from step 4 — the same signer's weight is now counted on both sides of the tally used by `SignerCoordinator::get_block_status`, permanently inflating the stale rejection total even though S currently supports B.
