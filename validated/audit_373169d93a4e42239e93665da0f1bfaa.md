### Title
External Initiator credentials are not bound to any specific job/bridge and can trigger runs of *any* job via `/v2/jobs/:ID/runs` - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
The `bridges.ExternalInitiator` model has no field associating it with a specific job or bridge, so authenticating with any valid EI access key/secret proves nothing more than "this is *some* external initiator". `AuthenticateExternalInitiator` compounds this by also setting the generic `SessionUserKey` to a fabricated `User{Role: UserRoleRun}`, which causes `PipelineRunsController.Create`'s `isUser` check (intended to block EIs from triggering int-ID job runs) to pass for EI-authenticated requests as well.

### Finding Description
`AuthenticateExternalInitiator` in [1](#0-0)  looks up the `ExternalInitiator` purely by access key/secret via `store.FindExternalInitiator` and `bridges.AuthenticateExternalInitiator`, with no job or bridge ID involved in the lookup or comparison. The `ExternalInitiator` struct itself, defined in [2](#0-1) , contains only `Name`, `URL`, `AccessKey`, and secret/salt fields — there is no `JobID`/`BridgeID` binding at all.

After successful EI authentication, the handler sets both the EI context key and, critically, also sets `SessionUserKey` to a synthetic run-role user: [3](#0-2) 

In `PipelineRunsController.Create`, the code that is supposed to restrict integer-ID job runs to real users (excluding EIs) only checks whether `SessionUserKey` is present: [4](#0-3) 

Because `AuthenticateExternalInitiator` populates `SessionUserKey` too, `auth.GetAuthenticatedUser(c)` returns `ok=true` for EI-authenticated requests exactly the same as for real users. The comment "only users are allowed to run jobs using int IDs - EIs not allowed" is therefore not enforced by the code — `isUser` is true in both cases, and the handler proceeds to call `prc.App.RunJobV2(ctx, jobID, nil)` for whatever `:ID` is in the URL, with no check that the authenticated EI has any relationship to that job.

Consequently, any valid EI access key/secret pair (for any EI record in the DB) can be used to POST to `/v2/jobs/<any-job-id>/runs` and trigger a run of an arbitrary job, not just a job associated with that EI (since no such association exists in the schema/model to begin with).

### Impact Explanation
This allows an attacker holding a low-privilege EI credential (bound conceptually to one webhook/bridge integration) to trigger execution of unrelated jobs on the node, including jobs that move funds or interact with sensitive external adapters, without possessing a real user session or API token. This matches the "unauthorized job run / fund movement" impact class.

### Likelihood Explanation
Precondition is simply possession of one valid EI access key + secret (the minimal EI credential level). No other authentication material, admin access, or knowledge of the target job's association is required — the attacker just needs to know or brute-force/enumerate a target job ID. This is fully reproducible via a handler-level HTTP request and requires no special timing or race condition.

### Recommendation
- Add a job/bridge binding to `ExternalInitiator` (e.g., a `JobID` or set of authorized job IDs) and enforce it in `PipelineRunsController.Create` by checking the EI's authorized job set against the requested `:ID`.
- Do not set `SessionUserKey` from `AuthenticateExternalInitiator`; use `GetAuthenticatedExternalInitiator` explicitly wherever code needs to distinguish EI-originated requests from genuine user sessions, and fix `isUser` checks (e.g., in `PipelineRunsController.Create`) to actually exclude EI-authenticated context instead of relying on the shared `SessionUserKey`.

### Proof of Concept
1. Create two jobs, Job A and Job B, and one `ExternalInitiator` record (or two, each nominally "associated" with a bridge for Job A and Job B respectively, since no real binding exists).
2. Authenticate an HTTP request to `POST /v2/jobs/<JobB-ID>/runs` using EI headers (`static.ExternalInitiatorAccessKeyHeader` / `static.ExternalInitiatorSecretHeader`) corresponding to the EI nominally tied to Job A.
3. Assert current behavior: response is `200`/success and a pipeline run for Job B is created (`prc.App.RunJobV2` invoked with Job B's ID) — demonstrating no job/bridge scoping is enforced.
4. Expected secure behavior: response should be `401`/`403` because the EI is not authorized for Job B.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
