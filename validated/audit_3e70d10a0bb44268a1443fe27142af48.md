### Title
Front-runnable EIP-8130 CREATE2 account address lets an attacker seize a victim's counterfactual account with attacker-controlled initial actors - (File: crates/execution/eip8130/src/apply.rs)

### Summary
The external report's bug class is: a deterministic, non-caller-bound `CREATE2` address lets an attacker pre-create the destination contract with attacker-chosen parameters before the legitimate party's transaction lands, corrupting whatever "pairing"/"delegation" state gets bound to that address. I checked whether Base's B-20 token factory precompile is exposed to the same class and it is not, because its address derivation binds `msg.sender` into the salt: `let address_hash = keccak256((caller, call.salt).abi_encode())` [1](#0-0) , so an attacker cannot compute another user's future token address without also being that user, and the factory additionally rejects collisions only by code presence (not balance) via `already_deployed` in `FactoryV1::create_b20` [2](#0-1) .

The same class of risk does reappear, however, in the EIP-8130 account-creation path. `ApplyAccountConfiguration::apply_create` derives the deployed account address purely from `(user_salt, code, initial_actors)` — it does not bind `msg.sender`/the transaction sender at all:
- `compute_address` hashes `0xff || ACCOUNT_CONFIG || effective_salt || code_hash` [3](#0-2) .
- `effective_salt` is `keccak256(user_salt || actors_commitment)`, where `actors_commitment` is a hash over the caller-supplied `initial_actors` list [4](#0-3) .
- `apply_create` rejects the create only if the target address is `already_deployed`/initialized, returning `AlreadyInitialized` [5](#0-4) .

Because `user_salt` and `code` (the account implementation bytecode, e.g. a well-known wallet factory) are both public/predictable — analogous to the NFT-collection address in the original report being publicly known — and neither the address nor the create-guard is bound to a specific caller identity, an attacker who learns a soon-to-be-used `(user_salt, code)` pair can submit `apply_create` first with a *different* `initial_actors` set (e.g. an attacker-controlled authenticator instead of the victim's), permanently occupying that address before the victim's transaction lands.

### Finding Description
`apply_create`'s address derivation and initialization guard are content-addressed by `(user_salt, code, initial_actors)` but never incorporate the transaction sender. This mirrors the root cause in the external report: the vulnerable `UniswapV2Factory` allowed `createPair` to be called with a precomputed wrapper address before the legitimate `createWrapper` call, permanently binding attacker-chosen delegation state to that address. Here, the equivalent "delegation pairing" is the account's `initial_actors` (the authenticators/keys authorized to control the account): whichever transaction reaches `apply_create` first for a given `(user_salt, code)` combination wins the address and installs its own actor set; `storage.get_account_state(address)?.is_initialized()` then permanently blocks any subsequent legitimate `apply_create` call for that same address [5](#0-4) .

### Impact Explanation
If a victim's wallet-creation flow uses a predictable `user_salt` (e.g., derived from a known EOA, an app-assigned counter, or a documented default) together with a canonical, publicly known account implementation (`code`), an attacker can front-run the victim's `createAccount`-equivalent transaction, deploying the same address first with attacker-controlled `initial_actors`. The victim's own creation transaction then reverts (`AlreadyInitialized`), permanently denying them their intended counterfactual account address and — worse — leaving that address initialized under attacker authority, which the victim may have already been counting on (e.g., counterfactual funding, EIP-7702 delegation target, or a precomputed address shared out-of-band). This is a concrete denial-of-service / account-hijack-by-squatting on the EIP-8130 account-creation path, reachable from a single unauthorized signed transaction, matching the required "unauthorized operation" / permanent loss-of-intended-control impact bar.

### Likelihood Explanation
Exploitability depends entirely on whether `user_salt` values used by wallets/dapps in practice are attacker-predictable ahead of the legitimate creation transaction (e.g., deterministic salts derived from an EOA address, a counter, or off-chain-shared values prior to submission) — this is analogous to the original report, where the collection address (and hence the wrapper address) is public before `createWrapper` is called. Given `code` is generally a canonical, publicly known implementation (`DEFAULT_ACCOUNT`, etc., per `Eip8130Contracts` [6](#0-5) ), the only secret an attacker needs is the salt, which is likely observable in mempool/off-chain coordination before inclusion, making this a plausible medium-likelihood front-run.

### Recommendation
Bind the transaction sender (or another value only the legitimate initiator controls, verified via signature/authorization) into `effective_salt`/`compute_address`, so no other account can compute or claim the same deterministic address. Alternatively, require `apply_create` to verify that the caller is authorized for the requested `initial_actors` set (e.g., via a signature check on the actors commitment) before allowing first-come-first-served address claiming.

### Proof of Concept
Conceptual PoC mirroring the report's `test_createCompulsoryDelegate`:
1. Observe/derive `user_salt` and `code` a victim intends to use for `apply_create` (e.g., a documented default account salt scheme).
2. Compute `address = compute_address(user_salt, code, victim_actors)` off-chain using the same formula as `Self::compute_address` [7](#0-6) .
3. Submit an `apply_create` transaction with the same `(user_salt, code)` but attacker-controlled `initial_actors`, ahead of the victim's transaction.
4. The victim's later `apply_create` call for the identical address fails with `ApplyError::AlreadyInitialized` [5](#0-4) , while the address is now permanently controlled by the attacker's actor set.

Note: I was not able to fully trace, within the available indexed context, how/where `user_salt` is generated or whether upstream tooling always randomizes it unpredictably before broadcast — that determination would require deeper inspection of the wallet/SDK code that constructs `CreateEntry` values, which is not fully covered by the current index. If salts are always attacker-unpredictable at broadcast time in the intended usage pattern, this finding's likelihood is lower than stated.

    /// Computes the counterfactual CREATE2 address for a created account. Mirrors
    /// `computeAddress`.
    pub fn compute_address(
        user_salt: B256,
        code: &[u8],
        initial_actors: &[InitialActor],
    ) -> Result<Address, ApplyError> {
        let effective_salt = Self::effective_salt(user_salt, initial_actors);
        let code_hash = keccak256(Self::build_deployment_code(code)?);
        let mut buf = Vec::with_capacity(1 + 20 + 32 + 32);
        buf.push(0xff);
        buf.extend_from_slice(Eip8130Contracts::ACCOUNT_CONFIG.as_slice());
        buf.extend_from_slice(effective_salt.as_slice());
        buf.extend_from_slice(code_hash.as_slice());
        Ok(Address::from_word(keccak256(buf)))
    }

    /// The CREATE2 salt: `keccak256(user_salt || actors_commitment)`. Mirrors
    /// `_computeEffectiveSalt`.
    fn effective_salt(user_salt: B256, initial_actors: &[InitialActor]) -> B256 {
        // Exactly 64 bytes: `user_salt` (32) || `actors_commitment` hash (32).
        let mut packed = Vec::with_capacity(64);
        packed.extend_from_slice(user_salt.as_slice());
        packed.extend_from_slice(Self::actors_commitment(initial_actors).as_slice());
        keccak256(packed)
    }
