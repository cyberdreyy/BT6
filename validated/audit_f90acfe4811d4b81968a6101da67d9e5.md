## Analysis: Missing beneficiary-registration check lets an operator trap a staker's stake in `staking_contract`

### Bug-class reduction
The external report's invariant is: **before routing funds to a newly-configured address, verify that address can actually receive them — otherwise the sender becomes permanently unable to move funds through that path.** In `BaseBridgeReceiver`/`Timelock`, the unchecked address was `localTimelock`. The Aptos-native analog I traced is the **operator beneficiary address** in `staking_contract.move`, which is written into state with no validation and is later used as the mandatory recipient of `aptos_account::deposit_coins` inside the *single, shared* `distribute_internal` routine that also pays out the staker's own unlocked stake.

### Finding Description
`staking_contract::set_beneficiary_for_operator` lets an operator set an arbitrary `new_beneficiary` address with **no check that the address can accept a coin deposit**: [1](#0-0) 

Contrast this with `vesting::set_beneficiary`, which explicitly guards against exactly this failure mode: [2](#0-1) 

`distribute_internal` is the **only** code path that moves already-inactive/pending-inactive coins for a `(staker, operator)` pair out of the stake pool. It iterates the shared `distribution_pool` (which holds both the staker's own withdrawable stake and the operator's commission) and unconditionally calls `aptos_account::deposit_coins` for every recipient, redirecting the operator's share to `beneficiary_for_operator(operator)`: [3](#0-2) 

`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the target account has not registered a `CoinStore<AptosCoin>` **and** has disabled `allow_arbitrary_coin_transfers` via `DirectTransferConfig`: [4](#0-3) 

Because the loop processes all shareholders of the *same* `distribution_pool` inside one Move transaction, if the deposit to the poisoned beneficiary aborts, the **entire transaction reverts**, including the staker's own portion. `switch_operator` (the staker's only way to leave a malicious operator) and `update_commision` both call `distribute_internal` first, before any other state change: [5](#0-4) 

So a malicious operator can:
1. Create/control a fresh account, leave it unregistered for `AptosCoin`, and call `account::set_allow_direct_coin_transfers` (via `aptos_account`) to disable arbitrary direct transfers on that account.
2. Call `set_beneficiary_for_operator(operator, poisoned_address)`.
3. Any subsequent call to `distribute`, `switch_operator`, or `update_commision` for that `(staker, operator)` pair will abort permanently — trapping the staker's own already-unlocked stake with no way for the staker to force a resolution, since only the operator can change the beneficiary back.

### Impact Explanation
This is an unprivileged-role (operator) action that strands funds and blocks the exit/withdrawal rights of a *different* party (the staker), matching "Permanent lock or non-recoverable loss of claim rights in stake ... beneficiary ... flows" and "withdrawal of stake ... balances not owned by the attacker." The staker has no self-service remedy: `switch_operator` (meant to let a staker leave without a lengthy unstake) is itself blocked by the same `distribute_internal` call, so the staker cannot even escape to a new operator.

### Likelihood Explanation
Requires only entry-function calls available to any operator (`set_beneficiary_for_operator`, and standard `aptos_account`/`coin` calls to configure the poisoned recipient) — no privileged access, no race condition, and it is deterministic and repeatable. `features::operator_beneficiary_change_enabled()` must be on, but that's a standard mainnet feature flag governing this functionality, not a special admin precondition.

### Recommendation
Add the same guard already used in `vesting::set_beneficiary` — validate that `new_beneficiary` is registered/able to receive `AptosCoin` (or, more robustly, use a fungible-asset primary-store deposit path that cannot be opted out of) in `staking_contract::set_beneficiary_for_operator` (and the equivalent `delegation_pool::set_beneficiary_for_operator`) before persisting the new beneficiary. Additionally, consider decoupling the staker's own payout from the operator/beneficiary payout in `distribute_internal` so that a failure delivering commission cannot block the staker's independent withdrawal.

### Proof of Concept (conceptual)
1. Staker creates a `staking_contract` with `operator`.
2. `operator` creates address `B`, does not register `CoinStore<AptosCoin>` for `B`, and calls `aptos_account::set_allow_direct_coin_transfers(B_signer, false)`.
3. `operator` calls `staking_contract::set_beneficiary_for_operator(operator, B)`.
4. Stake pool accrues rewards/unlocks; staker calls `staking_contract::distribute(staker, operator)` — the transaction aborts every time at the `aptos_account::deposit_coins` call for the operator's commission recipient `B`.
5. Staker attempts `staking_contract::switch_operator` to escape — also aborts, because it invokes `distribute_internal` first.
6. Staker's already-unlocked stake, and their ability to switch operator, remain permanently blocked until `operator` voluntarily calls `set_beneficiary_for_operator` again with a valid address.

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };
