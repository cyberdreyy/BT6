### Title
Unverified external ERC4626 deposits allow share-price inflation theft of parked lender funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
The external advisory describes software that downloads and executes a binary over an unauthenticated channel with no integrity check. The on-chain analog is `ProgrammableBorrower`, which "downloads" value into an opaque external component — an operator-selected ERC4626 `vault` — and trusts its responses (`deposit` share count, `withdraw`/`redeem` asset count, `convertToAssets` valuation) with zero integrity checks: no minimum-shares bound, no max-shares bound, no slippage check, and no verification that the vault protects against share-price manipulation.

### Finding Description
`setVault` only verifies `_vault.asset() == underlyingToken`; the vault's share-inflation resistance is never checked [1](#0-0) . `onStartEpoch` then parks **all** lender capital into that vault via `_depositToVault(underlyingToken.balanceOf(address(this)), 0)`, which calls `vault.deposit` and accepts whatever share amount is returned without a `minSharesOut` guard [2](#0-1) [3](#0-2) . The same unchecked trust applies to `vault.withdraw` inside `_borrow` and `onStopEpoch` [4](#0-3) .

The accounting is then built on `vault.convertToAssets` via `_currentVaultAssets()`, so a manipulated share price directly corrupts `epochStartVaultAssets`, `totalInterestDueNow`, and `availableToBorrow` [5](#0-4) .

Attack path (any unprivileged EOA acting as a user of the configured ERC4626 vault):
1. Operator configures (honestly, but mistakenly) a vault without inflation protection — e.g., a fresh ERC4626 with no virtual shares and no existing depositors.
2. Attacker front-runs the first `startEpoch`/`onStartEpoch` flow: deposits 1 wei into the empty vault, then donates a large amount of underlying directly to the vault, inflating the share price to ~1 unit = huge asset value.
3. `onStartEpoch` calls `_depositToVault` with the pool's entire idle balance. Rounding causes the pool to receive 0 or near-0 shares; the bulk of the deposit accrues to the attacker's majority share position.
4. Attacker redeems their shares and withdraws roughly half (up to nearly all, depending on rounding) of the pool's parked capital.
5. `ProgrammableBorrower` records the lost assets as a vault loss in `_vaultNetInterest`, socializing it to tranche holders; `totalInterestDueNow` silently absorbs it [6](#0-5) .

A milder variant works even on a non-empty vault: attacker sandwiches a `borrow()`/`onStopEpoch` `vault.withdraw` call to force a bad share burn rate (e.g., on vaults with dynamic fees or manipulable totalAssets), since no `maxShares`/`minAssets` bound is enforced.

### Impact Explanation
Direct theft of lender principal: the pool's idle funds parked in the vault can be partially or almost fully siphoned via first-deposit share inflation. The loss then flows through `totalInterestDueNow()`/`vaultLoss()` into the tranche waterfall as a real pool loss, so AA/BB depositors bear it at the next `stopEpoch`. Because `epochStartVaultAssets` is snapshotted *before* the deposit [7](#0-6) , the theft is recorded as vault PnL rather than caught by any accounting guard.

### Likelihood Explanation
Medium. It requires the honest operator to point `setVault` at a vault that is empty or lacks share-inflation defenses — plausible during facility onboarding or vault rotation (a supported operation). No privileged misbehavior is needed; the attacker is any third-party depositor in that vault. Existing guards (`_checkOnlyOwnerOrManager`, `epochAccountingActive` checks, `nonReentrant`, `setVault`'s zero-balance requirement) do not validate the vault's resilience or bound the exchange rate on deposits/withdrawals, so they do not stop it.

### Recommendation
- Enforce slippage bounds on all vault interactions: check `shares >= convertToShares(assetAmount) - tolerance` after `vault.deposit`, and bound `maxShares` on `vault.withdraw`/`redeem`.
- In `setVault`, reject vaults with `totalSupply() == 0` and below a minimum liquidity/decimals offset, or require the integrator to seed the vault before enabling the facility.
- Consider treating an anomalous `epochDepositedToVault` vs. share delta (deposit returning far fewer shares than the exchange rate implies) as a hard revert in `onStartEpoch`/`_depositToVault` so losses surface immediately instead of being socialized as vault PnL.

### Proof of Concept
```solidity
// forge test — conceptual PoC; requires a VulnerableVault ERC4626 without
// inflation protection (raw totalAssets/totalSupply pricing) deployed and set
// via programmableBorrower.setVault(vulnerableVault) by owner.

function testVaultShareInflationStealsParkedFunds() external {
    // Setup: owner configures an empty, unprotected ERC4626 vault on ProgrammableBorrower
    vm.prank(owner);
    programmableBorrower.setVault(address(vulnerableVault));

    uint256 amount = 10_000 * oneScale;
    idleCDO.depositAA(amount);            // pool funds land in ProgrammableBorrower

    // Attacker (any EOA) front-runs startEpoch:
    // 1) deposit 1 wei -> receives 1 share
    deal(USDC, attacker, 1 + amount);
    vm.startPrank(attacker);
    underlying.approve(address(vulnerableVault), type(uint256).max);
    vulnerableVault.deposit(1, attacker);          // 1 share, price = 1:1
    // 2) donate to inflate price: 1 share now worth ~`amount` assets
    underlying.transfer(address(vulnerableVault), amount);
    vm.stopPrank();

    // Honest manager starts the epoch; _depositToVault mints ~1 share for `amount` assets
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Attacker redeems, extracting roughly half of the pool's parked funds
    vm.prank(attacker);
    uint256 stolen = vulnerableVault.redeem(1, attacker, attacker);
    assertGt(stolen, amount / 2 - 1);

    // The theft is recorded as vault loss and socialized to tranche holders
    assertApproxEqAbs(programmableBorrower.vaultLoss(), amount - _programmableVaultAssets(), 2);
}
```

The same unchecked-trust pattern exists on the withdrawal side (`_borrow`, `onStopEpoch`), so a fix must bound both deposit shares and withdrawal rates rather than only hardening the epoch-start deposit.
