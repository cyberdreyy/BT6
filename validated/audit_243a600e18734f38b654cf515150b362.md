### Title
Loss-adjusted withdrawal receipts stored under the wrong epoch after `deposit()` increments `epochNumber`, letting pending claimants withdraw at par — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The out-of-bounds read class of CVE-2018-5811 maps onto epoch-indexed accounting: state keyed by epoch is written or read one slot past the epoch it logically belongs to. In `IdleCreditVault`, `collectWithdrawFunds` records `lossRecoveryPriceByEpoch[epochNumber]`, but `deposit()` — the fund-return call made inside `stopEpoch` while `isEpochRunning` is still true — increments `epochNumber` first. When the CDO calls `collectWithdrawFunds` after the deposit inside the same `stopEpoch`, the haircut price is stored under epoch N+1 while every pending receipt's `lastWithdrawRequest` still points to epoch N. The haircut is then never found, and claimants are paid at par from a strategy that only received the reduced amount.

### Finding Description
- `deposit()` increments `epochNumber` when called while the epoch is running (the stopEpoch path), per the comment "deposit done on stopEpoch (before setting the var to false) so we reset the counter" [1](#0-0) .
- `collectWithdrawFunds` writes the loss ratio under the *current* `epochNumber`: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` and zeroes `pendingWithdraws` [2](#0-1) .
- On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. the request epoch N [3](#0-2) . The price stored under N+1 is invisible — a one-past-the-end index, the exact analog of the OOB read.
- With price == 0 the claim falls through to `_claimFundedWithdrawRequest`, whose gate `epochNumber <= lastWithdrawRequest` now passes (N+1 > N), paying `withdrawsRequests` in full at par [4](#0-3) .
- The `requestWithdraw` guard that would catch an unclaimed loss receipt also reads `lossRecoveryPriceByEpoch[lastWithdrawRequest]` (epoch N) and sees 0, so it does not stop new requests either [5](#0-4) .

Broken invariant: the loss waterfall / fair-burn invariant. Borrower funds only `_amount < pendingBasis`, but claimants burn receipts for the full `claimBasis` and drain the strategy balance (including funds backing active LP strategy tokens and any future reserve).

### Impact Explanation
Direct insolvency/theft. After `stopEpochWithDuration` with a realized loss, the first pending-withdraw claimants redeem at par and consume more underlying than the borrower repaid for the pending bucket; the shortfall is paid out of the strategy's remaining underlying, and later claimants or the CDO's active-NAV redemptions are left unbacked or revert permanently. Loss that should have been socialized across pending receipts is instead borne by other users.

### Likelihood Explanation
Requires a `stopEpochWithDuration`/`stopEpoch` flow that calls `strategy.deposit` (fund return) before `collectWithdrawFunds` in the same transaction — the natural ordering, since the repayment deposit precedes splitting proceeds between pending receipts and active NAV — plus a non-zero loss and at least one pending withdraw request. No privileged attacker is needed; any pending receipt holder triggers the overpayment by calling `claimWithdrawRequest` normally.

Caveat: I could not read `IdleCDOEpochVariant.stopEpoch` to confirm the deposit→collect ordering (search returned match counts only). If `collectWithdrawFunds` is invoked strictly before `deposit`/`epochNumber` increments, the store lands on the correct epoch and this issue does not exist; the PoC below verifies this ordering on a fork.

### Recommendation
Store the loss price under the epoch the requests were made in, not the post-increment counter — e.g. use `epochNumber - 1` semantics consistent with `deposit()`'s increment, or record the haircut keyed by the epoch captured at `stopEpoch` entry. Alternatively, make `collectWithdrawFunds` take the target epoch as a parameter from the CDO, or apply pending-receipt haircuts before incrementing `epochNumber`.

    // 2. Lender calls requestWithdraw during buffer of epoch N:
    //    lastWithdrawRequest[user] = N, withdrawsRequestsByEpoch[user][N] = amount,
    //    pendingWithdraws = amount.
    // 3. Borrower repays principal + partial interest with a realized loss L.
    // 4. Manager calls cdo.stopEpochWithDuration(epochDuration, L):
    //    - internally strategy.deposit(...) runs while isEpochRunning -> epochNumber becomes N+1
    //    - then strategy.collectWithdrawFunds(funded < pendingWithdraws)
    //      -> lossRecoveryPriceByEpoch[N+1] = funded * 1e18 / pendingBasis; pendingWithdraws = 0
    // 5. Lender calls cdo.claimWithdrawRequest():
    //    - _claimLossAdjustedWithdrawRequest: lossRecoveryPriceByEpoch[N] == 0 -> skipped
    //    - _claimFundedWithdrawRequest: epochNumber (N+1) > lastWithdrawRequest (N)
    //      -> pays full `amount` at par from strategy balance
    uint256 paid = strategy.underlyingBalanceBefore();
    vm.prank(address(cdo));
    strategy.claimWithdrawRequest(user);
    // assert: user received `amount` even though only `funded < amount` was collected
    assertGt(strategy.underlyingSpent(), funded);

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
