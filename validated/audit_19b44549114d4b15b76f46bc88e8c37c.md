### Title
Unbounded decompression in `extractZipFileEntry` allows zip-bomb disk exhaustion during artifact/cache extraction - ([File: helpers/archives/zip_extract.go])

### Summary
`extractZipFileEntry` opens a ZIP entry's compressed stream and copies it directly to disk with `io.Copy(out, in)` without ever comparing the number of bytes written against the entry's declared `UncompressedSize64` or any absolute ceiling. Because a ZIP `File` header's declared uncompressed size is untrusted metadata and `io.Copy` will happily read from the DEFLATE decompressor until EOF regardless of what the header claims, an attacker-supplied artifact/cache archive with a small compressed payload but a huge (or falsely-small) actual decompressed stream can make Runner write unbounded data to the job's workspace.

### Finding Description
`extractZipFileEntry` at [1](#0-0)  opens the per-entry reader via `file.Open()` and streams it straight to the destination file with a single `io.Copy(out, in)` call, with no size accounting, no `io.LimitReader`, and no post-copy validation against `file.UncompressedSize64`. This function is reached by `extractZipFile` → `ExtractZipArchive` → `ExtractZipFile`, which is used by the legacy zip extractor at [2](#0-1) , itself wired into artifact/cache extraction (`commands/helpers/artifacts_downloader.go`, `archive.NewExtractor`). The archive content (file names, compression method, and payload) is fully attacker-controlled — a pipeline author can produce a job whose artifacts/cache archive gets downloaded and extracted by the Runner using this code path. Because `archive/zip`'s DEFLATE reader will decompress as many bytes as the compressed stream encodes regardless of the (attacker-set) `UncompressedSize64` field in the header, and `extractZipFileEntry` never limits or checks output size, a small compressed file (e.g., a few KB of highly compressible repeated data) can expand to gigabytes/terabytes written to `file.Name` on disk. There is no size-limit check, disk-quota check, or `LimitReader` anywhere in this code path or in the callers found (`ExtractZipArchive`, `ExtractZipFile`, `ziplegacy` extractor); the fastzip-based extractor (`fastzip.NewExtractorFromReader`) is a separate implementation not reviewable here, but the legacy path unconditionally exists and is reachable.

### Impact Explanation
Exploiting this causes the Runner process to write unbounded bytes into the job workspace/staging directory during artifact or cache extraction, which can exhaust local disk space on the host running the job. Depending on executor type (e.g., shell executor or any executor sharing a host filesystem/volume with other jobs' cache or build directories), disk exhaustion can degrade or fail unrelated concurrent jobs sharing that filesystem, and can crash or hang the Runner extraction step for the attacker's own job. This is a resource-exhaustion / availability impact, not a sandbox escape or data leak.

### Likelihood Explanation
Preconditions are minimal: any pipeline author who can upload a custom artifact or cache archive (a routine, unprivileged CI capability) can craft a ZIP with a single entry containing a highly compressible large payload (a "zip bomb"), which is trivial to construct (e.g., repeating zero bytes, achieving compression ratios well over 1000:1). No special runner configuration or admin misconfiguration is required beyond the default artifact/cache extraction flow existing, and the extraction path (`ExtractZipArchive`/`extractZipFileEntry`) is unconditionally used by the legacy zip extractor. This makes the issue highly feasible and repeatable.

### Recommendation
Enforce a hard ceiling on decompressed bytes per entry (and/or total archive) in `extractZipFileEntry`, e.g., wrap `in` with `io.LimitReader(in, maxAllowedSize)` and treat hitting the limit as an error, or track bytes written via `io.Copy` in a loop/counter and abort once a configurable maximum (or a sane multiple of `file.UncompressedSize64`) is exceeded. This should be applied consistently to all ZIP/TAR extraction code paths in `helpers/archives`, not just the file-entry copy.

### Proof of Concept
Go unit test outline:
```go
func TestExtractZipFileEntry_ZipBombSizeLimit(t *testing.T) {
    // Build an in-memory zip with one entry of declared small size
    // but whose compressed stream expands to, e.g., 500MB when read
    // (many repeated bytes with maximal compression ratio).
    buf := buildZipBombEntry(t, "bomb.txt", 500*1024*1024)
    r, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)

    dir := t.TempDir()
    wd, _ := os.Getwd()
    os.Chdir(dir)
    defer os.Chdir(wd)

    err = archives.ExtractZipArchive(r)
    // Expected (after fix): error indicating size limit exceeded, and
    // written file size <= configured ceiling.
    require.Error(t, err)

    info, statErr := os.Stat(filepath.Join(dir, "bomb.txt"))
    require.NoError(t, statErr)
    assert.LessOrEqual(t, info.Size(), int64(maxAllowedEntrySize))
}
```
Current behavior (pre-fix): the test would show `ExtractZipArchive` returns `nil` and the resulting file size equals the full decompressed bomb size, demonstrating unbounded write with no size enforcement.

```go
func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}
```
