### Title
Missing Zero-Value Guard in `TokensDepositedV2` Arm Allows Zero-Amount Bridge Action to Reach WAL — (`crates/sui-bridge/src/abi.rs`)

### Summary

The V1 `TokensDeposited` arm in `try_into_bridge_action` explicitly rejects events where `sui_adjusted_amount == 0` with `BridgeError::ZeroValueBridgeTransfer`. The V2 `TokensDepositedV2` arm, added later, omits this guard entirely. A `TokensDepositedV2` log carrying `suiAdjustedAmount=0` passes through `EthToSuiTokenBridgeV2::try_from` and is wrapped into a `BridgeAction::EthToSuiTokenTransferV2` with a zero amount, which is then persisted to the WAL and signed by bridge authorities. The EVM vault retains the deposited tokens while Sui mints nothing, permanently locking user funds.

### Finding Description

In `crates/sui-bridge/src/abi.rs`, `try_into_bridge_action` handles two deposit event variants:

**V1 arm (lines 117–145)** — has the guard:

```rust
EthSuiBridgeEvents::TokensDeposited(event) => {
    let bridge_event = match EthToSuiTokenBridgeV1::try_from(&event) {
        Ok(bridge_event) => {
            if bridge_event.sui_adjusted_amount == 0 {          // ← guard present
                return Err(BridgeError::ZeroValueBridgeTransfer(...));
            }
            bridge_event
        }
        ...
    };
    ...
}
``` [1](#0-0) 

**V2 arm (lines 146–154)** — guard is absent:

```rust
EthSuiBridgeEvents::TokensDepositedV2(event) => {
    let eth_bridge_event = EthToSuiTokenBridgeV2::try_from(&event)?;  // no zero check
    Some(BridgeAction::EthToSuiTokenTransferV2(
        EthToSuiTokenTransferV2 { eth_tx_hash, eth_event_index, eth_bridge_event },
    ))
}
``` [2](#0-1) 

`EthToSuiTokenBridgeV2::try_from` simply copies `event.suiAdjustedAmount` verbatim with no validation: [3](#0-2) 

`ZeroValueBridgeTransfer` is never raised anywhere in the V2 code path — confirmed by the grep results showing it only appears in the V1 arm and the error definition.

### Impact Explanation

If a `TokensDepositedV2` event is emitted with `suiAdjustedAmount=0` (possible when a user deposits a token amount that rounds to zero under `convertERC20ToSuiDecimal`):

1. The zero-amount `EthToSuiTokenTransferV2` action is created and WAL-persisted.
2. Bridge authorities sign and submit it.
3. Sui mints **0 tokens** to the recipient.
4. The EVM vault retains the deposited tokens with no corresponding Sui-side release.
5. The user's funds are **permanently locked** — the backing guarantee is broken (EVM vault holds non-zero tokens; Sui side holds nothing).

This meets the **permanent fund lock** impact class listed as High/Medium in the active bounty scope.

### Likelihood Explanation

The V1 arm's comment — *"This only happens when solidity code does not align with rust code"* — confirms the developers treat this as a real edge case requiring a defensive Rust-side guard. The V2 arm was added without porting that guard. Any token whose EVM-to-Sui decimal conversion can produce zero for a non-zero input amount (e.g., a token with many more EVM decimals than Sui decimals, deposited in a dust amount) creates the triggering condition via a normal public bridge call (`bridgeERC20V2`).

### Recommendation

Add the same zero-value guard to the V2 arm immediately after `EthToSuiTokenBridgeV2::try_from`:

```rust
EthSuiBridgeEvents::TokensDepositedV2(event) => {
    let eth_bridge_event = EthToSuiTokenBridgeV2::try_from(&event)?;
    if eth_bridge_event.sui_adjusted_amount == 0 {
        return Err(BridgeError::ZeroValueBridgeTransfer(format!(
            "Manual intervention is required: {}",
            eth_tx_hash
        )));
    }
    Some(BridgeAction::EthToSuiTokenTransferV2(
        EthToSuiTokenTransferV2 { eth_tx_hash, eth_event_index, eth_bridge_event },
    ))
}
```
