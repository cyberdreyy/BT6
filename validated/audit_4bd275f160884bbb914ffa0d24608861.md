### Title
Permissionless `accrue_interest` applies the *current spot* interest rate to the *entire elapsed backlog period*, allowing utilization-rate manipulation to retroactively overcharge stale borrowers — (File: `programs/marginfi/src/state/bank.rs`)

### Summary
Marginfi's interest model computes a single "spot" interest rate from the current `total_liabilities/total_assets` ratio and multiplies it by the entire time elapsed since `last_update`, exactly the bug class described in the Derive report (peak-rate applied to a stale period). Because `utilization_rate` in marginfi is derived directly from on-chain shares that a user can move within a single transaction (unlike Derive's price/impact-fee oracle), and because the accrual instruction is fully permissionless, an attacker can spike the rate immediately before triggering accrual on a rarely-touched bank, causing the entire backlog window to be charged at the manipulated rate.

### Finding Description
`Bank::accrue_interest` computes `time_delta = current_timestamp - self.last_update` and applies the interest rate calculated from the *current* utilization to that whole `time_delta`: [1](#0-0) 

The utilization rate used to derive that rate is `total_liabilities / total_assets`, computed from live share balances at the moment of the call: [2](#0-1) 

The rate is then compounded onto share values with `calc_accrued_interest_payment_per_period`, which multiplies principal by `(1 + apr * time_delta / SECONDS_PER_YEAR)` — i.e. the whole backlog period gets one flat rate: [3](#0-2) 

Accrual is triggered by the fully permissionless `lending_pool_accrue_bank_interest` instruction — no signer authorization beyond the group not being paused: [4](#0-3) 

The protocol's own documentation acknowledges that interest realizes closer to an APY only "for Banks that have meaningful borrows"; "Banks that have meaningful borrows typically end up yielding within 1% of the continuously compounded APY. The exceptions are rare cases where an asset has a high APR, but not a lot of activity" — i.e. it explicitly flags less-active banks (long `time_delta`) as the vulnerable case, mirroring the report's "less frequently traded asset" caveat: [5](#0-4) 

Because utilization is derived from shares the attacker directly controls (borrow/repay), rather than requiring an external price shock as in Derive's funding-rate case, this is a *stronger* and more directly triggerable analog: an attacker can atomically (1) borrow a large amount against the same bank to spike `utilization_rate` toward the top of the interest curve (which "grows rapidly" beyond the optimal point per the README's curve description), (2) call the permissionless `lending_pool_accrue_bank_interest` in the same transaction, applying that spiked APR to the full stale `time_delta` for all existing liability/asset shares in the bank, and (3) repay the borrow, restoring `utilization_rate` — all within one atomic transaction, so no genuine collateral/interest risk is borne for more than an instant.

### Impact Explanation
This retroactively imposes an inflated interest charge across the *entire* elapsed period on every existing borrower/depositor of that bank, based on a rate that existed for only a single instant engineered by the attacker. Since `asset_share_value` and `liability_share_value` both move together, the manipulation redistributes value between the bank's existing lenders and borrowers (lenders gain accrued yield, existing borrowers' debt balloons) proportional to `time_delta`, which can be large for illiquid/rarely-used banks. This is a durable state change (share values are persisted) with direct financial effect on third parties who never opted into a transaction. The protocol's own SECURITY.md explicitly does **not** exclude oracle/utilization manipulation or flash-loan-style attacks from scope. [6](#0-5) 

### Likelihood Explanation
Likelihood is higher than in the original Derive report because:
- `utilization_rate` is derived from state (shares) the attacker fully controls in the same transaction, not an external oracle that only occasionally spikes.
- `lending_pool_accrue_bank_interest` is explicitly permissionless and composable within any transaction.
- Illiquid/low-activity banks (long `time_delta` since `last_update`) are common in a multi-asset lending protocol and are exactly the case the team's own documentation calls out as producing outlier results.
- The attacker needs sufficient liquidity/collateral to execute a large temporary borrow (or can use the built-in flash-loan feature, which defers health checks until `end_flashloan`), lowering the capital requirement.

Mitigating factors: the attacker's own newly-created liability/asset also accrues the same inflated rate for that instant, and borrow/deposit limits (`borrow_limit`/`deposit_limit`) and available bank liquidity bound how far utilization can be pushed; the net extractable value depends on the size of pre-existing liabilities/assets relative to the attacker's temporary position and the shape of the specific bank's interest curve.

### Recommendation
- Avoid using an instantaneous spot rate multiplied by an unbounded elapsed `time_delta`; instead, use a time-weighted/twap utilization rate, or checkpoint accrual more frequently (e.g., via a keeper/settler that accrues on a fixed cadence as Derive's team committed to), or cap the maximum `time_delta` that can be charged at a single, freshly-computed spot rate.
- Consider disallowing borrow+accrue+repay (or utilization-changing operations immediately followed by permissionless accrual) within the same transaction, or snapshot utilization prior to the instruction that triggered a large backlog accrual.

### Proof of Concept
Conceptual (bankrun/litesvm) PoC, analogous to the existing `z01_compoundInterest.spec.ts` test harness which already demonstrates how `accrueInterest` is permissionless and rate-sensitive to `time_delta` and utilization:
1. Set up a bank with modest deposits/liabilities and let a long period elapse without any `accrue_interest` call (simulating a low-activity bank), as shown by the "no touch" bank scenarios in `z01_compoundInterest.spec.ts`. [7](#0-6) 
2. In a single transaction: (a) attacker borrows a large amount from the same bank to push `utilization_rate` toward the high end of the curve, (b) attacker (or anyone) calls `lending_pool_accrue_bank_interest` for that bank, (c) attacker repays the borrow in full.
3. Compare `bank.asset_share_value` / `bank.liability_share_value` before and after: the entire stale `time_delta` will have been charged at the manipulated peak rate rather than the rate that prevailed for most of that period, confirmed by inspecting `bank.cache.interest_accumulated_for` and `bank.cache.accumulated_since_last_update`, which report the full elapsed seconds and the associated share-value delta. [8](#0-7)

fn calc_accrued_interest_payment_per_period(
    apr: I80F48,
    time_delta: u64,
    value: I80F48,
) -> Option<I80F48> {
    let ir_per_period: I80F48 = apr
        .checked_mul(time_delta.into())?
        .checked_div(SECONDS_PER_YEAR)?;

    let new_value: I80F48 = value.checked_mul(I80F48::ONE.checked_add(ir_per_period)?)?;

    Some(new_value)
}

/// Calculates the interest payment for a given period `time_delta` in a principal value `value` for interest rate (in APR) `arp`.
/// Result is the interest payment.
fn calc_interest_payment_for_period(apr: I80F48, time_delta: u64, value: I80F48) -> Option<I80F48> {
    if apr.is_zero() {
        return Some(I80F48::ZERO);
    }

    let interest_payment: I80F48 = value
        .checked_mul(apr)?
        .checked_mul(time_delta.into())?
        .checked_div(SECONDS_PER_YEAR)?;

    Some(interest_payment)
}

pub fn lending_pool_accrue_bank_interest(
    ctx: Context<LendingPoolAccrueBankInterest>,
) -> MarginfiResult {
    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = &ctx.accounts.group.load()?;

    bank.accrue_interest(
        clock.unix_timestamp,
        group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    // TODO see if we can recycle some things like the InterestRateCalc from accrue to save some CU
    bank.update_bank_cache(group)?;

    Ok(())
}

#[derive(Accounts)]
pub struct LendingPoolAccrueBankInterest<'info> {
    #[account(
        constraint = (
            !group.load()?.is_protocol_paused()
        ) @ MarginfiError::ProtocolPaused
    )]
    pub group: AccountLoader<'info, MarginfiGroup>,

    #[account(
        mut,
        has_one = group @ MarginfiError::InvalidGroup
    )]
    pub bank: AccountLoader<'info, Bank>,
}

Realized rates on our banks are actually closer to the APY. Interest is computed just before any
balance change, so the rate at which different Banks compound actually varies. More popular Banks,
like SOL, compound every few minutes, or even every few seconds on more active days. Less popular
Banks might compound just a few times per week, but these Banks typically have very few borrows (and
thus a low APR to compound). Since interest compounds based on usage, the more popular our platform,
the more often interest compounds. Remember that interest accrues for all of a Bank's users at the
same time: that means if anyone transacts with a bank, the interest for *every* user compounds!

In practice, Banks that have meaningful borrows typically end up yielding within 1% of the
continuously compounded APY. The exceptions are rare cases where an asset has a high APR, but not a
lot of activity.
