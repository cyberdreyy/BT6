### Title
JWT single-use replay guard is not atomic (check-then-act TOCTOU allows double execution of workflow trigger) - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` calls `h.jwtCache.isReplay(claims.ID)` and, several steps later, `h.jwtCache.recordUsage(claims.ID)`, using two independent lock acquisitions instead of one atomic check-and-set. Two concurrent `Authorize` calls with the identical JWT can both observe `isReplay == false` before either calls `recordUsage`, allowing the same single-use JWT to authorize the workflow trigger twice.

### Finding Description
`Authorize` is reachable from the gateway's public JSON-RPC entrypoint: `gatewayHandler.HandleJSONRPCUserMessage` → `triggerHandler.HandleUserTriggerRequest` → `WorkflowMetadataHandler.Authorize` [1](#0-0) [2](#0-1) . Nothing upstream of `Authorize` deduplicates or serializes concurrent requests carrying the same JWT — no per-request-ID lock, no queueing by `jti`.

Inside `Authorize`:
```
if h.jwtCache.isReplay(claims.ID) { ... reject ... }   // read-lock, released immediately
...  // signature check, workflow lookup, key lookup
h.jwtCache.recordUsage(claims.ID)                       // write-lock, separate acquisition
```
`isReplay` takes `cache.mu.RLock()` and returns whether `claims.ID` exists in the map, releasing the lock immediately [3](#0-2) . `recordUsage` separately takes `cache.mu.Lock()` and inserts the entry [4](#0-3) . Between these two calls, JWT signature verification, workflow ID lookup, and authorized-signer lookup are performed [5](#0-4) , none of which touch the replay cache or block concurrent identical requests. Because the check (`isReplay`) and the act (`recordUsage`) are not combined into a single atomic critical section, two goroutines processing the same valid, not-yet-used JWT concurrently can both pass the `isReplay` check before either executes `recordUsage`, resulting in both proceeding to key authorization and both succeeding in returning an `*AuthorizedKey`, i.e., both authorizing the trigger.

This directly contrasts with `vault.RequestReplayGuard.CheckAndRecord`, which correctly combines check-and-record under a single mutex acquisition in the same repo, showing that the atomic pattern is known and used elsewhere but not applied here [6](#0-5) . That guard's own concurrency test demonstrates the pattern is testable and expected to yield exactly one success under N concurrent identical requests [7](#0-6) ; `jwtReplayCache` has no equivalent test for concurrent identical JWTs, only a sequential replay test [8](#0-7) .

### Impact Explanation
An unprivileged attacker holding one valid, signed, single-use JWT (issued for a specific workflow trigger request) can race two simultaneous gateway requests with the identical token and have both authorized, causing the workflow trigger to execute twice from a single-use credential. This violates the single-use guarantee (`AUTHENTICATION_SOUNDNESS`) documented by the error message "JWT token has already been used" and could cause duplicate/unintended workflow executions, which can translate into duplicate on-chain actions or duplicate fund-moving triggers depending on what the workflow does — matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Exploitation only requires possession of one legitimately obtained, still-valid JWT (which the attacker is entitled to hold as a normal caller) and the ability to fire two requests to the gateway at nearly the same time — no elevated privilege, no signature forgery, and no timing beyond ordinary network racing is needed. The race window is small (limited to JWT verification + map lookups) but is a classic, reliably reproducible TOCTOU race under concurrent load or an attacker deliberately sending parallel requests.

### Recommendation
Combine the check and the record into a single atomic operation under one lock, mirroring `RequestReplayGuard.CheckAndRecord`:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool {
    cache.mu.Lock()
    defer cache.mu.Unlock()
    if _, exists := cache.cache[jti]; exists {
        return true // replay
    }
    cache.cache[jti] = time.Now()
    return false
}
```
Call this once, early in `Authorize`, immediately treating a "true" result as a replay rejection, before performing the more expensive workflow/key lookups. Also verify the JWT signature (`VerifyRequestJWT`) is already done before this call as it is now, so only a verified `jti` is atomically claimed.

### Proof of Concept
Go concurrency test in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go`:
1. Set up a `WorkflowMetadataHandler` with one registered workflow and one authorized signer, as in existing `TestWorkflowMetadataHandler_Authorize` setup.
2. Create a single valid JWT (`tokenString`) for a fixed `req`, as done in the "JWT replay protection" subtest [9](#0-8) .
3. Launch two goroutines simultaneously (using a `sync.WaitGroup` and a start barrier/channel to maximize overlap) each calling `handler.Authorize(workflowID, tokenString, req)` with the same token.
4. Collect both `(key, err)` results.
5. Assert: exactly one call returns `err == nil` with non-nil `key`, and the other returns an error containing `"JWT token has already been used"`.
6. Under the current implementation this assertion is expected to intermittently fail (both succeed), demonstrating the race; after applying the atomic `checkAndRecord` fix, the test should pass deterministically across repeated runs (similar to `TestRequestReplayGuard_ConcurrentAccess`).

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func TestRequestReplayGuard_ConcurrentAccess(t *testing.T) {
	guard := NewRequestReplayGuard()
	futureExpiry := time.Now().UTC().Unix() + 100

	const goroutines = 100
	results := make([]error, goroutines)
	var wg sync.WaitGroup
	wg.Add(goroutines)

	for i := range goroutines {
		go func(idx int) {
			defer wg.Done()
			results[idx] = guard.CheckAndRecord("same-digest", futureExpiry)
		}(i)
	}
	wg.Wait()

	successCount := 0
	duplicateCount := 0
	for _, err := range results {
		if err == nil {
			successCount++
		} else {
			require.ErrorIs(t, err, ErrRequestAlreadySeen)
			duplicateCount++
		}
	}

	assert.Equal(t, 1, successCount, "exactly one goroutine should succeed")
	assert.Equal(t, goroutines-1, duplicateCount, "all others should be rejected as duplicates")
}
