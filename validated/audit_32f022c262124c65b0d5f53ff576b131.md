### Title
Unprivileged front-running of `LockupFactory::create` allows attacker to deploy and permanently bind a victim's deterministic lockup address with attacker-chosen parameters - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` (lockup-factory/src/lib.rs) has no access control beyond a minimum attached deposit check; any account can call it with an arbitrary `owner_account_id` before the legitimate grantor does. Because the lockup contract's address is fully deterministic (`sha256(owner_account_id)[..20].<factory>`), the attacker can pre-create and initialize the victim's lockup account with attacker-chosen `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, and `release_duration`, permanently blocking the legitimate `create` call for that same `owner_account_id`.

### Finding Description
The claimed binding is: `deployed LockupArgs for owner_account_id == LockupArgs the real creator (foundation/grantor) intended for owner_account_id`. This binding is broken because `create` is `#[payable]` and public with no caller restriction: [1](#0-0) 

The only guard is `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)`, which any unprivileged account can satisfy by attaching 3.5 NEAR. There is no `assert_called_by_foundation`, owner check, or any binding of `predecessor_account_id` to `owner_account_id`. The account address is derived purely from `owner_account_id`: [2](#0-1) 

The `Promise` chain then unconditionally does `create_account().deploy_contract(CODE).transfer(deposit).function_call("new", LockupArgs{...})` with the caller-supplied `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`: [3](#0-2) 

`LockupContract::new` (lockup/src/lib.rs, `#[init]`) accepts and stores whatever `LockupArgs` are passed since it only runs once at account creation and has no way to distinguish attacker vs. legitimate creator — the `#[init]` guard only prevents re-initialization, not initialization by the wrong party.

If the attacker calls `create(victim_owner_account_id, evil_duration, evil_timestamp, evil_vesting, evil_release, None)` first, `create_account()` succeeds and the account at the deterministic address is deployed and initialized with the attacker's parameters. When the real grantor later calls `create` for the same `owner_account_id`, `Promise::new(lockup_account_id).create_account()` fails because the account already exists, and `on_lockup_create`'s `is_promise_success()` check refunds the deposit and returns `false` — permanently blocking legitimate creation for that owner: [4](#0-3) 

No existing guard (`assert_self`, `is_promise_success`, min deposit check) prevents an arbitrary account from being the `predecessor_account_id` of the initial `create` call, so the divergence between intended and deployed `LockupArgs` is real.

### Impact Explanation
This matches the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The attacker can grief any `owner_account_id` that has not yet had its lockup created, permanently freezing/blocking that grantee's intended lockup terms (denial of legitimate creation) and forcing the victim/grantor to use a different, non-deterministic address (breaking any off-chain assumptions tied to the deterministic naming scheme). The attacker's own attached deposit (≥3.5 NEAR) is consumed into the account (not stolen from the victim), so no NEAR is extracted from a victim's existing funds, but the deployed contract state (`lockup_duration`, `vesting_schedule`, `release_duration`) is attacker-controlled and bound to the victim's identity, and the legitimate creation path is permanently blocked, which is a lasting, repeatable-across-accounts front-running/griefing primitive.

### Likelihood Explanation
Precondition: no account yet exists at the deterministic address for the target `owner_account_id` — this is normal for any grant not yet created. Attacker cost is exactly `MIN_ATTACHED_BALANCE` (3.5 NEAR) plus gas, and the call is fully public and requires no special permissions, keys, or foundation/owner status. The main constraint is that the attacker must know/guess the target `owner_account_id` before the real grantor calls `create` for it, which is feasible since grantee account IDs (e.g. employees, early investors) are often known or predictable ahead of the on-chain grant.

### Recommendation
Restrict `LockupFactory::create` so only the foundation/authorized grantor account (`assert_called_by_foundation` or similar) can invoke it, or require that `predecessor_account_id() == owner_account_id` for self-service grant creation, preventing arbitrary third parties from pre-empting deployment for accounts they do not control.

### Proof of Concept
```rust
// near-sdk-sim / testing_env! style test, extending lockup-factory/tests
#[test]
fn test_frontrun_create_blocks_legitimate_owner() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker (not foundation, not victim) calls create() for victim's owner_account_id
    let victim_owner = account_tokens_owner();
    let evil_duration: WrappedTimestamp = 1u64.into(); // attacker-chosen, differs from intended
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(victim_owner.clone(), evil_duration, None, None, None, None);

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let created = contract.on_lockup_create(
        lockup_account(), ntoy(30).into(), String::from("attacker.near"),
    );
    assert!(created); // account deployed at deterministic address with attacker's evil_duration

    // Real grantor later calls create() for the same owner_account_id with intended terms
    let intended_duration: WrappedTimestamp = 63036000000000000u64.into();
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(victim_owner.clone(), intended_duration, None, None, None, None);

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    // create_account() on already-existing account fails -> Promise::Failed
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(), ntoy(35).into(), String::from(account_tokens_owner()),
    );
    assert_eq!(res, false); // legitimate creation permanently blocked; deposit refunded
    // asserting deployed LockupContract state (via separate LockupContract::new invocation in the
    // simulated account) reflects evil_duration, not intended_duration, proves the binding is broken.
}
```

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
