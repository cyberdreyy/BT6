## Analog Found

### Title
Stale rejection weight is never reconciled when a signer flips to acceptance, letting a resolved rejection be recounted as a live one and wedge block delivery - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The report's bug class is a broken bookkeeping equality: one code path (`repayCreditAccount`) increments a value that a parallel/successor path (`mintProfit`) is supposed to reconcile, but the reconciliation never happens, leaving a permanent, unjustified offset that later causes a legitimate operation to fail. The same class of bug exists in the node-side `StackerDBListener`'s block-status tally: when a signer rejects a block and later legitimately reconsiders and accepts it, its rejection weight is folded into `total_weight_approved` on acceptance but is **never removed** from `total_weight_rejected`. The signer's weight then lives in both tallies simultaneously, and the two tallies are checked independently, with the rejection check evaluated first.

### Finding Description
`BlockStatus` tracks `total_weight_approved` and `total_weight_rejected` for a given block hash [1](#0-0) .

When an `Accepted` response arrives, the coordinator adds the signer's weight to `total_weight_approved` only if that slot_id is not already in `gathered_signatures` — this correctly guards against double counting an *acceptance* — but it does nothing to check or clear any *prior rejection* weight the same slot_id may have already contributed: [2](#0-1) 

When a `Rejected` response arrives, the weight is added to `total_weight_rejected` guarded only by `responded_signers.insert(slot_id)` (i.e., "first response wins" for the reject-weight bump), with no corresponding removal path when that signer's *later* response changes to acceptance: [3](#0-2) 

The only place `total_weight_rejected` is ever cleared is `reset_rejections`, which is explicitly a full wipe used on a proposal timeout/retry — and the comment there confirms the asymmetric design intent ("approvals cannot be cleared... an old approval could always be used to make a block reach the threshold") without addressing that a *rejection*, once flipped by the same signer to an approval, is likewise stale and should stop counting against the block: [4](#0-3) 

This is a direct analog to the report: `pool.repayCreditAccount()` increments a value (`profit` minted) without updating `expectedLiquidity`, leaving a permanent accounting gap that only surfaces later when someone (a withdrawer / here, an honest majority of signers) needs the ledger to be internally consistent. Here, a signer's rejection weight is "minted" into `total_weight_rejected` and never "unminted" when that same signer's stance is superseded by a later, valid acceptance — `signer.rs`'s own documented behavior explicitly allows a signer to change its answer once "the reason I rejected has since gone away" (see `docs/signer-flows.md` lines 27, 349-355), so this is a reachable, protocol-sanctioned state transition, not a contrived edge case.

The consumer of these two tallies, `SignerCoordinator`'s polling loop, checks the rejection condition strictly before the approval condition: [5](#0-4) 

Because `total_weight_rejected` can be permanently inflated by stale weight from a signer who has since accepted, the rejection branch (`SignersRejected`) can fire based on data that no longer reflects any live signer's opinion, even while the true, current opposition is below the 30%-blocking-minority and the true, current support (correctly reflected in `gathered_signatures`, since that map is keyed by slot and only ever holds real signatures) is on track to reach 70%.

### Impact Explanation
This causes the coordinator to declare a block globally rejected (`NakamotoNodeError::SignersRejected`) using an inflated `total_weight_rejected` that includes weight from a signer who no longer opposes the block. Concretely this:
- wedges delivery of an otherwise validly-signable block (a liveness failure matching the "wedged into never signing valid blocks" class, here manifesting on the node/coordinator side that gates when a signed block is ever assembled and pushed), and
- can trigger `temporarily_excluded_txids`/`permanently_excluded_txids` bans on transactions based on stale per-txid rejection weight that a signer no longer holds [6](#0-5) , permanently punishing transactions for a rejection reason that has already been resolved.

This is a genuine "rejection recounted" state inconsistency: the same signer's weight is simultaneously present in both the approve and reject sums, and the stale half of that duplication outlives the signer's actual, current opinion.

### Likelihood Explanation
Requires only one signer naturally reconsidering a rejection (an explicitly anticipated, protocol-sanctioned behavior per the signer's own capitulation/re-evaluation logic) and its two responses reaching the miner via ordinary StackerDB gossip — no majority collusion, no other signer's key, and no malicious miner action are needed.

### Recommendation
When processing an `Accepted` response for a slot_id that is present in `responded_signers` but *not* in `gathered_signatures` (i.e., the signer previously rejected and is now accepting), subtract that signer's weight from `total_weight_rejected` (and from any `failed_txids` entries it contributed to) before adding it to `total_weight_approved`, so the two tallies stay mutually exclusive per signer, mirroring how `mintProfit()` in the referenced report correctly updates the invariant (`expectedLiquidity`) that the alternate path silently skipped.

### Proof of Concept
1. Total signer weight = 100, threshold = 70 (blocking minority = 30).
2. Signer A (weight 10) validates the proposed block against a stale mempool view and sends `Rejected` → `total_weight_rejected = 10`, `responded_signers = {A}`.
3. The mempool issue resolves; signer A re-validates and sends `Accepted` for the same `signer_signature_hash` (explicitly permitted per the signer's documented capitulation logic). The listener adds A's weight to `total_weight_approved` (10) because `gathered_signatures` didn't contain A yet, but `total_weight_rejected` stays at 10 — untouched.
4. 21 weight worth of other, distinct signers independently and genuinely reject the block for a real, current reason: `total_weight_rejected = 10 (stale) + 21 (real) = 31`.
5. `signer_coordinator.rs`'s loop evaluates `31 + 70 = 101 > 100` → true, and returns `Err(SignersRejected)`, even though the actual, current opposing weight is only 21 (below the 30 blocking minority) and the block could otherwise still reach 70% approval.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
