### Title
`/debug/vars` endpoint is reachable by any authenticated session regardless of role, exposing Go runtime internals to view-role users - ([File: core/web/router.go])

### Summary
`debugRoutes` mounts `GET /debug/vars` behind only `auth.AuthenticateBySession`, with no `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` wrapper unlike virtually every other sensitive route in `v2Routes`. Any authenticated user — including the lowest-privilege `UserRoleView` — can hit this endpoint and retrieve the full `expvar` dump (command-line args, memstats, and any custom-registered vars).

### Finding Description
`debugRoutes` is defined as: [1](#0-0) 
This creates a `/debug` group protected only by `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)`, and mounts `expvar.Handler()` at `/vars` with no subsequent role-check wrapper. Compare this to every other authenticated route group in `v2Routes`, which wraps individual handlers with `auth.RequiresRunRole`, `auth.RequiresEditRole`, or `auth.RequiresAdminRole` on top of session/token authentication, e.g. `authv2.GET("/build_info", buildInfo.Show)` is unguarded but most sensitive routes (key management, transfers, jobs) are gated: [2](#0-1) 
The role hierarchy is `View < Run < Edit == Admin` as implemented in `auth.go`: [3](#0-2) 
Since `debugRoutes` only calls `AuthenticateBySession` (which merely validates the session cookie and sets the user in context, without any role check — see `AuthenticateBySession` at lines 55-71), any authenticated user of any role, including `UserRoleView`, passes through and reaches `expvar.Handler()`, dumping Go runtime `expvar` data (build info, GC/memstats, and any package-registered vars) to the caller.

### Impact Explanation
This matches Chainlink's low-severity "information disclosure of non-critical operational/runtime metadata to an authenticated user with insufficient privilege" class. `expvar.Handler()` by default exposes `cmdline` and `memstats`, and any other vars registered via `expvar.Publish` in the running process (which could include internal build/version details or metrics depending on what packages register). This is a low/informational impact: it does not expose secrets, private keys, or enable privilege escalation on its own, but it does violate the intended role-based authorization boundary — a `view`-role account is architecturally meant to be read-only/UI-observer, yet gains access to internal runtime diagnostics not exposed through any other view-role-accessible route.

### Likelihood Explanation
Trivial and fully repeatable: any valid authenticated session of any role (including the weakest, `view`) can issue `GET /debug/vars` and receive a 200 response with the expvar JSON. No additional preconditions, timing, or race conditions are required.

### Recommendation
Wrap the `/debug/vars` route with an explicit role check consistent with the rest of the router, e.g. `group.GET("/vars", auth.RequiresAdminRole(expvar.Handler()))` (adapting `expvar.Handler()`'s `http.Handler` into a `gin.HandlerFunc` as done via `ginHandlerFromHTTP`), so only admin (or at minimum edit) role sessions can access it.

### Proof of Concept
Go handler-level integration test plan (in `core/web/router_test.go` style, using existing test harness `setupWebAPITestCase`/`app.NewApplication` fixtures):
1. Table-driven test iterating over `clsessions.UserRoleView`, `clsessions.UserRoleRun`, `clsessions.UserRoleEdit`, `clsessions.UserRoleAdmin`.
2. For each role, create a user with that role, authenticate a session via the sessions endpoint (or set session cookie directly).
3. Issue `GET /debug/vars` with the authenticated session cookie.
4. Assert: current behavior — all four roles receive `http.StatusOK` and a JSON body containing `"cmdline"` and `"memstats"` keys.
5. Expected/desired behavior after fix — `UserRoleView` (and optionally `UserRoleRun`/`UserRoleEdit`) should receive `http.StatusUnauthorized`/`http.StatusForbidden`, and only `UserRoleAdmin` should receive `http.StatusOK`.
6. This test currently fails the "authorization-exact" invariant since all roles get identical (200 OK) access.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
