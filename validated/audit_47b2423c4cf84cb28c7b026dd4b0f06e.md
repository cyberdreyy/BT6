### Title
Inflated withdraw receipts via cross-tranche deposit shifting `_managedContractValue()` at request time - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external report describes a shared mutable quantity (`totalSupply()`) being read to size a fixed target/quantity, where an unprivileged user changes that quantity between setup and execution to bypass caps or cause DoS. The direct analog is `_calcInterestWithdrawRequest` in `IdleCDOEpochVariant`, which sizes a withdraw receipt's interest from the *current* managed TVL (`_managedContractValue()`), which any KYC'd lender can inflate at will by depositing into the opposite tranche during the buffer period — while the requester's own tranche NAV used as denominator stays unchanged.

### Finding Description
`requestWithdraw`/`writeOffDeposit`/`maxWithdrawable` size the receipt via `_calcInterestWithdrawRequest`:

- `totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer)` — linear in total managed TVL.
- `totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche)` — AA gets `totInterest * trancheAPRSplitRatio / FULL_ALLOC`.
- `_interest = _amount * totTrancheInterest / _trancheBal`, where `_trancheBal = _lastSavedNAV(_tranche)` is the *requester's* tranche NAV only. [1](#0-0) 

`_managedContractValue()` is the live strategy-token balance net of `unclaimedFees`, so it grows immediately whenever anyone deposits into *either* tranche. [2](#0-1) 

Deposits are accepted while the epoch is stopped/buffer and immediately mint strategy tokens 1:1 (`_deposit` → `_depositToVault`), raising managed value while only `lastNAV` of the deposited tranche grows. [3](#0-2) 

Attack trace (buffer phase, unprivileged KYC'd lender):

1. Attacker holds AA tranche tokens worth `X`.
2. During the buffer period the attacker deposits a large amount into **BB** (own capital, repaid to themselves later). `_managedContractValue()` and `lastNAVBB` jump; `lastNAVAA` is untouched.
3. Attacker calls `requestWithdraw(X, AATranche)`. `totInterest` is now inflated by the BB deposit, `totTrancheInterest(AA) = ratio * totInterest` is inflated, but `_trancheBal = lastNAVAA` is unchanged → per-unit `_interest` exceeds what the fixed borrower APR actually owes. The inflated `_amount` is minted to the attacker as a strategy-token receipt and added to `pendingWithdraws`. [4](#0-3) 

4. At `stopEpoch`, the CDO pulls `expectedInterest + pendingWithdraws` from the borrower via `getFundsFromBorrower`. The inflated component is cash pulled from the honest borrower beyond the true `expectedEpochInterest`, and paid out to the attacker on `claimWithdrawRequest`. [5](#0-4) 

The `_diff` adjustment to `expectedEpochInterest` only reallocates the borrower obligation between tranche buckets; it does not bound the per-requester interest to the interest genuinely attributable to that tranche's NAV. The inflation is symmetric to the report's "increase `totalSupply` to bypass `targetUnit`": here a deposit inflates the shared numerator while the fixed APR obligation is unchanged.

### Impact Explanation
Direct theft: every extra wei of inflated `_interest` in `pendingWithdraws` is pulled from the borrower's own balance at `stopEpoch` (`getFundsFromBorrower` transfers `_amountToPullFromBorrower + _pendingWithdraws`), so the attacker is paid interest the borrower never owed. If the borrower lacks the balance, the try/catch routes to `_handleBorrowerDefault`, forcing a spurious default and freezing the pool — permanent locking/insolvency path, not just a DoS. Loss is quantified: `attackerPrincipal * apr * duration * (injectedTVL / realTVL) * splitRatio / durationSec`, up to the full fabricated interest on an arbitrarily large deposit (bounded only by attacker capital and deposit limits).

### Likelihood Explanation
Requires only a KYC-passing lender — explicitly an allowed attacker class. No privileged action needed; deposits during the buffer period are a normal, intended flow (the queue/epoch design explicitly prices deposits made during buffer). Profit requires depositing into the opposite tranche then unwinding it via a normal withdraw request in a later epoch, so capital cost is real but the exploit needs no timing privileges. The guard set (skim, `pendingClaims`, epoch gating, `epochNumber <= lastWithdrawRequest` claim delay) does not bound interest to per-tranche accrued interest — the claim delay actually locks in the inflated receipt rather than fixing it.

### Recommendation
In `_calcInterestWithdrawRequest`, compute `totInterest` from a supply/NAV snapshot that cannot be moved by same-epoch deposits — e.g. use `lastNAVAA + lastNAVBB` captured at `stopEpoch`/`startEpoch` (or `expectedEpochInterest` scaled by the tranche's share) instead of live `_managedContractValue()`, or cap `_interest` at `expectedEpochInterest * trancheNav / totalNav` for the epoch in which the request is made. Analogous to the report's recommendation to pin the target against a fixed quantity rather than a mutable total.

```text
  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
```

```text
  function getContractValue() public override view returns (uint256) {

  /// @notice Calculates the current managed net TVL.
  /// @dev Raw underlyings held by the CDO are excluded because unsolicited transfers are skimmed on interactions.
  /// @return Strategy-token-backed TVL net of accrued fees.
  function _managedContractValue() internal virtual view returns (uint256) {
    uint256 strategyTokenBalance = _contractTokenBalance(strategyToken);
    uint256 fees = unclaimedFees;
    return strategyTokenBalance > fees ? strategyTokenBalance - fees : 0;
  }
```

```text
  function requestWithdraw(uint256 _amount, address _user, uint256 _principal) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    if (_amount == 0) return;
    if (defaultRecoveryFinalized) {
      // user should first claim old already-funded withdraw requests before requesting new ones after default
      if (_hasWithdrawRequest(_user) || instantWithdrawsRequests[_user] != 0 || postDefaultRequests[_user] != 0) {
        revert NotAllowed();
      }
      // Preserve request/claim UX after default without increasing borrower-facing pendingWithdraws.
      // The CDO passes an already-haircut amount because finalization lowered virtualPrice first.
      _burn(msg.sender, _amount);
      _mint(_user, _amount);
      postDefaultRequests[_user] = _amount;
      return;
    }
    bool isClosed = IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0;
    uint256 currentEpoch = epochNumber;
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (
      lossRecoveryPrice != 0 &&
      (withdrawsRequestsByEpoch[_user][lossEpoch] != 0 ||
      (apr0Users[_user].principal != 0 && apr0Users[_user].principalEpoch == lossEpoch))
    ) {
      // A loss-adjusted receipt must be claimed before opening a later request, otherwise
      // `lastWithdrawRequest` would stop pointing to the epoch that stores its haircut.
      revert NotAllowed();
    }
    // burn strategy tokens from cdo (we don't burn future interest here, only the principal)
    _burn(msg.sender, _principal);
    // mint equal amount of strategy tokens to the user as receipt (interest included), useful in case of default
    _mint(_user, _amount);
    // A successfully closed pool already recalled all funds and has no later stopEpoch.
    if (!isClosed) {
      // Global amount that stopEpoch must source from borrower/strategy for all pending receipts.
      pendingWithdraws += _amount;
    }
    // save the epoch of the last withdraw request (buffer + epochDuration is 1 epoch)
    lastWithdrawRequest[_user] = currentEpoch;
    // APR=0 requests keep separate accounting and settle interest at stopEpoch.
    // `_amount` here is the post-management-fee principal bucket for that flow.
    if (unscaledApr == 0 && !isClosed) {
      _requestWithdrawApr0(_amount, _user);
    } else {
      // increase the withdraw requests for the user
      // we record both per-user (old, kept for compatibility) and per-epoch so
      // on finalization we can distinguish "default-epoch pending receipts"
      // from old funded receipts.
      withdrawsRequests[_user] += _amount;
      withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    }
  }
```
