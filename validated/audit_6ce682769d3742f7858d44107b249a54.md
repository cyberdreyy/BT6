### Title
Unbounded, unpartitioned `savedCallbacks` map allows cross-user eviction and silent drop of pending pipeline-run callbacks - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores every incoming trigger request in a single global `h.savedCallbacks` map keyed only by the attacker-controlled `msg.Body.MessageId`, with no per-sender partitioning. `pruneCallbacks` evicts the oldest entries once the map exceeds `MaxSavedCallbacks` (20000) purely by `createdAt`, deleting them from the map without ever invoking `SendResponse` on the evicted `savedCallback`, so any victim's still-pending request can be silently dropped.

### Finding Description
`HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go:341-421) accepts a `TriggerRequestPayload`, validates message freshness/signature, and then does: [1](#0-0) 
storing the callback keyed solely by `msg.Body.MessageId` — a value entirely chosen by the caller (it comes directly from the JSON-RPC request `ID` field, validated only for length/format, not uniqueness or per-sender scoping): [2](#0-1) [3](#0-2) 

`pruneCallbacks` (handler.go:299-339) periodically removes expired entries by age, and if the map is still over `MaxSavedCallbacks`, sorts remaining entries by `createdAt` and deletes the oldest half — with no distinction of which sender created them and no error response sent to the evicted caller: [4](#0-3) 

Because the map is global (not partitioned per sender/DON member) and `MessageId` is attacker-chosen, an attacker who is any authenticated gateway/run-role client can submit a large volume of `HandleLegacyUserMessage` requests with distinct `MessageId`s. The code has an explicit unimplemented TODO for rate limiting/allowlisting at this exact call site: [5](#0-4) 
so nothing currently throttles a single sender's rate of new callback creation. Once total saved callbacks exceed 20000, the next prune sweep deletes the oldest half of *all* entries regardless of owner, which can include a legitimate victim's still-outstanding request. The deleted entry's `Callback.SendResponse` is never called, so the victim's original HTTP/gateway request handler is left blocked until its own timeout (or forever, depending on caller semantics) with no distinguishing error — a silent drop rather than a clean failure.

### Impact Explanation
This is a denial-of-service against a specific victim's in-flight pipeline-run/trigger request: the response callback is discarded without invoking the completion path, so the caller who is awaiting completion (e.g., through the gateway HTTP handler) never receives a response for their original request. This does not by itself allow response hijacking, since the MessageId is deleted but a new legitimate response from the DON for the victim's original message would arrive at `handleWebAPITriggerMessage` and simply be dropped as well (map lookup would miss). This maps to a bounded availability impact (temporary denial of pipeline-run completion for a specific user), not a fund-loss or authentication-bypass class impact.

### Likelihood Explanation
The attacker only needs run-role/client-level ability to submit `HandleLegacyUserMessage` requests to the gateway (i.e., a signed message accepted by the gateway's normal message validation), and needs to submit roughly 20000+ distinct messages to trigger a prune-eviction event that could reach a victim's entry. There is no rate limiting implemented at this handler (explicit TODO), so the attack is feasible for any client capable of high request throughput, though it requires meaningful throughput/volume and the eviction only removes the *oldest* half of entries, meaning the attacker must sustain the flood long enough that the victim's message becomes among the oldest — this is somewhat probabilistic/timing-dependent, not deterministic against an arbitrarily-timed victim request.

### Recommendation
- Partition `savedCallbacks` per sender (e.g., key by `sender+MessageId` or maintain per-sender sub-maps/limits) to enforce isolation between users.
- Apply per-sender rate limiting/quota on `HandleLegacyUserMessage` (the TODO at handler.go:384) before inserting into `savedCallbacks`.
- On eviction in `pruneCallbacks`, call `SendResponse` with an explicit timeout/eviction error so the calling client fails fast instead of silently hanging.
- Consider bounding per-sender outstanding callback count instead of (or in addition to) a single global cap.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with a small `MaxSavedCallbacks` (e.g., 10) for test speed.
2. Register one "victim" callback via `HandleLegacyUserMessage` with a mock `handlers.Callback` that records if `SendResponse` was ever invoked, and capture its `createdAt` ordering by inserting it first.
3. Flood the handler with `MaxSavedCallbacks + N` additional `HandleLegacyUserMessage` calls using distinct attacker-chosen `MessageId`s, each with its own mock callback.
4. Call `h.pruneCallbacks()` directly.
5. Assert: victim's `MessageId` is no longer present in `h.savedCallbacks`, and the victim's mock `SendResponse` was never called — demonstrating the silent drop.
6. As a secondary assertion, verify that `savedCallbacks` map keys are not partitioned by sender (i.e., two different senders using the same `MessageId` string collide/overwrite), showing lack of per-sender isolation.

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
