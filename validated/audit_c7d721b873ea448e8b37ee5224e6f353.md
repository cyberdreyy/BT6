### Title
Locally-Timed Reorg Permit Lets a Single-Slot Miner Get Signers to Sign a Conflicting Block Over an Already-Canonical Tenure - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` decides, per signer and using only that signer's own local receipt/approval timestamps, whether a miner is allowed to build off something other than the prior sortition (i.e., reorg a tenure). If the reorged tenure has exactly one globally accepted block and the signer's *local* clock says that block's proposal arrived "too close" to the next sortition, the signer unilaterally grants a "reorg permit" (`mark_tenure_superseded`) that erases its own earlier signature from the double-sign conflict guard. Because this permit is derived purely from local, network-observable timing rather than any canonically agreed fact, a miner who controls broadcast/gossip timing of the first tenure's block can induce this local verdict in enough signers to get them to sign a competing, conflicting block over a tenure the network has already treated as canonical.

### Finding Description
`check_parent_tenure_choice` only outright refuses a reorg when the reorged tenure has **more than one** globally accepted block: [1](#0-0) 

If the tenure has exactly one globally accepted block, the function does not reject; instead it computes a purely local timing signal — the gap between when *this signer* received the new sortition's burn block and when *this signer* pre-committed to the old tenure's first block — and if that gap is smaller than `first_proposal_burn_block_timing`, it treats the earlier block as "poorly timed" and queues its tenure to be superseded: [2](#0-1) 

Once superseded, the record is used later to exclude that already-signed block from the anti-double-sign conflict guard entirely: [3](#0-2) [4](#0-3) 

The permit is checked via `reorg_permit_stands`, which only asks whether the *permitting* sortition is still canonical on the burn chain — it never re-validates the timing verdict against any network-agreed fact: [5](#0-4) 

The documentation itself acknowledges this is a signer-local decision, not one the node can answer: "One decision does have to be recorded, because it is ours rather than the node's" and that the permit is only as strong as the sortition it was granted to, never as strong as the timing evidence used to grant it: [6](#0-5) 

The critical gap: `sortition_state_received_time` and `approved_time` are both **this signer's own wall-clock observations** of network messages — a miner (or anyone controlling propagation of the tenure-1 proposal to a given signer) can delay that signer's receipt of the proposal, or otherwise skew the observed gap, making a genuinely well-timed, already-globally-accepted block look "poorly timed" from that signer's local vantage point. The signer then permits a reorg of a tenure it should refuse, silences its own existing signature as a "conflict," and signs a new, competing tenure-start block at the same height — an invalid/conflicting-block signature over what the rest of the network may already consider canonical.

This directly maps to the external report's bug class: a privileged/consequential action (excluding your own signature from the double-sign guard, i.e., "spending" trust that should be tightly gated) is granted based on a check that is not properly scoped to a trustworthy, canonical authority (the report's "timelock"/"owner" analog) — here, a purely local and externally-influenceable timing heuristic stands in for what should be a canonically verifiable fact.

### Impact Explanation
This breaks the "approved-parent vs canonical" equality that `check_parent_tenure_choice` is meant to enforce: it is supposed to gate which parent tenures are legitimate to reorg, but its timing evidence is signer-local and gossip-timing-manipulable rather than canonical. When enough signers are affected (via genuine or induced propagation delay to their proposal reception), they independently silence their own already-placed signatures over a globally accepted block and sign a new conflicting block, letting a single miner steer a chain reorg past an already-canonical tenure. This is a Critical-class outcome under the given rubric: a signer signing a conflicting/non-canonical block.

### Likelihood Explanation
No signer-key compromise or signer majority collusion is required — only control over the block proposer (a single winning miner/slot) plus the ability to influence gossip/propagation timing of the reorged tenure's first-block proposal to signers (e.g., broadcasting it late, or exploiting natural network latency near a sortition boundary). Since `first_proposal_burn_block_timing` is signer-configurable and the timing gap is computed from unauthenticated local receipt times, the trigger conditions are plausible during normal tenure-boundary races, and the existing test suite (`mark_miner_as_invalid_if_reorg_is_rejected_v1`) already demonstrates that different signers can independently reach different verdicts on the same reorg based on local, not canonical, timing/config — confirming the check is not derived from a globally agreed fact.

### Recommendation
Do not base the reorg-permit decision solely on a signer's own local receipt/approval timestamps. Instead, tie the "poorly timed" determination to a canonically verifiable, node-derived fact (e.g., the sortition DB's burn-block timestamp compared against the block's provable commitment/mining time, or a value agreed via `StateMachineUpdate` threshold rather than each signer computing it independently). At minimum, require that a reorg permit for a tenure with a **globally accepted** block additionally be corroborated by the stacks node's own view (analogous to how `conflict_still_blocks` consults the node) rather than trusting a single signer's local clock difference.

### Proof of Concept
Conceptual PoC (requires a live signer network to fully validate the race window; the exact timing window is environment-dependent and could not be executed in ask-only mode):
1. Miner M wins tenure 1 and proposes tenure-start block A. Ensure A is broadcast/gossiped such that a target signer S (or a large fraction of signers) receives/pre-commits to A a moment before receiving the *next* sortition's burn block, so that `sortition_state_received_time - approved_time` on S is small.
2. A is validated, pre-committed, signed by the full signer set, and pushed/adopted by the node (`globally_accepted_blocks == 1` for tenure 1) — i.e., A is canonical.
3. Miner M immediately wins tenure 2 and proposes a competing tenure-start block B whose parent is *not* tenure 1 (reorging past A).
4. On S, `check_parent_tenure_choice` sees `globally_accepted_blocks == 1` (not `> 1`, so not auto-rejected) and computes `proposal_to_sortition` using S's own timestamps from step 1, finds it below `first_proposal_burn_block_timing`, and calls `mark_tenure_superseded` for tenure 1, permitting the reorg — see [2](#0-1) .
5. S's earlier signature over A no longer blocks it (via `reorg_permit_stands` / `get_signed_conflicts`), so S signs B — a block conflicting with the already globally accepted A — see [4](#0-3) .
6. If enough signers experience a similarly skewed local timing view (plausible given they all react to the same externally-controlled gossip timing), B can cross the 70% signing threshold, producing a signer-endorsed conflicting/non-canonical block over what was already treated as the canonical chain.

    /// signature we already placed on one of its blocks must stop counting as a conflict while

    ///
    /// A failure to record only costs a delayed replacement -- the conflict keeps blocking until

            tenure.burn_block_height,

                "superseded_tenure_id" => %tenure.consensus_hash,
                "superseded_by" => %self.consensus_hash,
            );
        }

    /// Whether a reorg permit recorded for this conflict's tenure still stands.
    ///
    /// `check_parent_tenure_choice` records a permit when the reorg-timing rules sanction a
    /// later tenure replacing what the conflict's tenure built (see
    /// [`SignerDb::mark_tenure_superseded`]). A standing permit excludes the conflict entirely:
    /// our signature must not stand in the way of a replacement we sanctioned. But the permit
    /// is only as alive as the sortition it was granted to: if a burnchain fork orphaned the
    /// permitting sortition, the reorg we sanctioned can no longer happen, and the record must
    /// not keep suppressing the conflict.
    ///
    /// A false 404 here (e.g. from a node still catching up) only restores a conflict the
    /// permit could have excluded, which at worst delays the replacement, so unlike
    /// `conflict_still_blocks` no tip-height guard is needed. A node error voids the permit for
    /// the same reason: blocking is the direction that can be taken back.
    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }

One decision does have to be recorded, because it is ours rather than the
node's. When a miner builds off something other than the prior sortition,
`check_parent_tenure_choice` decides whether the reorg is allowed: it is, if
every tenure being reorged has at most one globally accepted block and produced
its first block too close to the next sortition to count
(`first_proposal_burn_block_timing`). Having sanctioned that replacement, the
signer records those tenures as **superseded** (`mark_tenure_superseded`), so its
own signature over what they built does not then block the replacement it just
permitted — the node cannot answer this one at signing time, since it still
serves the reorged tenure as fully live until the replacement lands. What _is_
still derived from the node is the permit's own validity: the record carries the
permitting tenure's sortition, and it only excludes conflicts while that
sortition remains canonical (section 5, `reorg_permit_stands`), so a burnchain
fork that orphans the permitting tenure automatically voids the permit. A record
more than `MAX_FORK_DEPTH` (100) burn blocks below the tip is dropped; a fork
that deep would cause far bigger problems than a stale conflict.
