### Title
Client-Controlled MessageId Allows Cross-User Response Confusion in Gateway `WebAPIHandler` savedCallbacks Map - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The gateway's legacy `web_api_trigger` flow stores a per-request callback in a map keyed solely by the client-supplied `MessageId`, with no binding to sender identity. Since `MessageId` is taken verbatim from the incoming JSON-RPC request `ID` field (fully attacker-controlled), a malicious/unprivileged client can choose a `MessageId` that collides with another in-flight request. This is directly analogous to the reported bug class: two logically distinct "flows" (here, two different user requests) end up tied to the same identifier/state slot, causing divergence — in this case, the node's response for one user's request gets routed to a different user's callback.

### Finding Description
`HandleLegacyUserMessage` stores the callback keyed only by `msg.Body.MessageId`: [2](#0-1) 

This `MessageId` originates from the untrusted, caller-controlled JSON-RPC `ID` field with no server-side uniqueness enforcement or randomization: [1](#0-0) 

`Message.Validate()` only checks length/format constraints (non-empty, ≤128 bytes, no trailing null byte) — it never verifies uniqueness or ties the ID to the sender: [3](#0-2) 

When a node later responds, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageId` and forwards the first matching response to whatever callback is currently stored there: [4](#0-3) 

If a second unprivileged caller submits a request using the same `MessageId` as an in-flight legitimate request (map insertion at line 412 simply overwrites the prior entry), the original caller's saved callback is silently replaced. The node response that was meant for the first requester is instead delivered to the second (attacker's) callback — or vice versa, an attacker's crafted `MessageId` value can capture/observe the response destined for another user's request, or hijack routing of a genuine response to their own connection. This mirrors the `onERC721Received`/`registeredMarketplaces` root cause: an externally-influenced identifier being used, without an in-flow guard, to disambiguate which state (lien / callback) an inbound event should be applied to.

### Impact Explanation
This is cross-user response confusion: sensitive DON/node responses (e.g., compute action results, workflow trigger responses) can be misdirected to an unauthorized client, or a legitimate client's callback can be silently discarded/overwritten by an unrelated request. This breaks the confidentiality/integrity guarantees of the request/response pairing across the gateway's internet-facing surface, without requiring any special privilege — any client able to submit a JSON-RPC request with a chosen `ID` can attempt the collision.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to predict or race a `MessageId` used by another concurrent legitimate request within the callback's `defaultCallbackMaxAgeSec` (120s) window. If `MessageId` values are predictable (e.g., sequential or externally observable, since the same value is echoed back to the requester in the JSON-RPC `ID` and to DON nodes), or if an attacker can flood many guesses/collide with self-chosen deterministic IDs used by other integrations, exploitation becomes practical. Since the map is keyed with no per-sender namespacing, even accidental collisions from misbehaving/naive clients would cause the same divergence.

### Recommendation
Namespace the `savedCallbacks` map key by both the caller/session identity and `MessageId` (e.g., `sender+":"+MessageId`), or generate the callback-tracking key server-side (e.g., a gateway-generated UUID) rather than trusting the client-supplied `MessageId` directly, and reject/collision-check writes rather than silently overwriting an existing map entry at [2](#0-1) .

### Proof of Concept
1. Unprivileged Client A sends a JSON-RPC request to the gateway HTTP endpoint with `id: "X"` and method `web_api_trigger`; the gateway calls `HandleLegacyUserMessage`, which stores `savedCallbacks["X"] = CallbackA` and forwards the request to DON nodes.
2. Before a node responds, unprivileged Client B sends another JSON-RPC request also with `id: "X"`; this overwrites `savedCallbacks["X"] = CallbackB` per [2](#0-1) .
3. A DON node responds for Client A's original request, referencing `MessageId: "X"`; `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `CallbackB`, and delivers Client A's response to Client B instead: [4](#0-3) .
4. Client A's connection times out/never receives a response, while Client B receives data belonging to Client A's request — a concrete cross-user response confusion, unverifiable end-to-end because I could not confirm from the index whether an additional signer-based authorization/allowlist gate exists further upstream of `ProcessRequest` that would restrict who may submit such requests; this should be verified in a live/full-repo session.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	return nil
}
