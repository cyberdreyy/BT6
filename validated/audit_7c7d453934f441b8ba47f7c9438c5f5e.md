### Title
Loss-adjusted withdraw receipts escape their haircut because `collectWithdrawFunds` stores the recovery price under the post-increment `epochNumber`, letting defaulted/loss receipts be claimed at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records pending withdraw receipts under the `epochNumber` active at request time, but stores `lossRecoveryPriceByEpoch` under the `epochNumber` active when `collectWithdrawFunds` is called during `stopEpoch`. Because `deposit()` increments `epochNumber` while the epoch is still running (`isEpochRunning()` is true during the `stopEpoch` deposit, per the in-code comment), a loss-adjusted funding call can store the recovery price under `epochNumber N+1` while every pending receipt is keyed to `epochNumber N`. The `lastWithdrawRequest` guard then reads `lossRecoveryPriceByEpoch[N] == 0`, treats the receipts as fully funded, and pays them at par even though only the haircutted amount was collected.

### Finding Description
- `requestWithdraw` tags each receipt with `currentEpoch = epochNumber` and stores basis in `withdrawsRequestsByEpoch[_user][currentEpoch]` and `lastWithdrawRequest[_user] = currentEpoch` (lines 260-294).
- `deposit()` does `epochNumber += 1` whenever `IIdleCDOEpochVariant(idleCDO).isEpochRunning()` is true, which is exactly the case for the deposit made inside `stopEpoch` ("deposit done on stopEpoch (before setting the var to false) so we reset the counter", lines 607-611).
- `collectWithdrawFunds` writes the haircut with `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` using the *current* `epochNumber` (line 421). If the CDO calls `strategy.deposit(...)` before `collectWithdrawFunds(...)` inside `stopEpochWithDuration(_lossAmount)`, the price lands on `N+1`, while all receipts whose basis made up `pendingBasis` are keyed to `N`.
- After that stop, a victim receipt holder calls `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest]` = `lossRecoveryPriceByEpoch[N]` = 0 and returns 0 (lines 789-800). `_claimFundedWithdrawRequest` then only requires `epochNumber > lastWithdrawRequest` (N+1 > N, satisfied, lines 326-328) and pays `withdrawsRequests[_user]` in full via `_transferFundedClaim`.
- The same desynchronization also defeats the re-request guard at lines 263-271: an attacker can open a new request in a later epoch without ever seeing `lossRecoveryPrice != 0`, and worse, a new request sets `lastWithdrawRequest` to an epoch that *does* have a loss price, so `_claimLossAdjustedWithdrawRequest` applies the haircut to the attacker's small new receipt while the large old receipt is paid at par in the same call.

### Impact Explanation
Direct theft / insolvency. Pending receipts that should be paid `claimBasis * lossRecoveryPrice / 1e18` are paid `claimBasis` in full. The strategy only collected `pendingToFund < pendingBasis` underlying in `collectWithdrawFunds` (lines 411-430), so paying receipts at par spends underlyings that belong to other funded receipt holders, the APR0 settled-interest bucket, or the `defaultRecoveryReserve` guard boundary — i.e., the last claimants are left unpaid and the loss waterfall (BB-first socialization intended by `previewLossAdjustedWithdrawFunds`, lines 440-460) is bypassed. Attacker loss-up-to: full haircut amount `pendingBasis - pendingToFund`, which for a 50% loss-adjusted stop on a 10M USDC pending queue is ~5M USDC overpaid.

### Likelihood Explanation
Requires only an unprivileged tranche-token holder calling `requestWithdraw` before an honest `stopEpochWithDuration` loss event — a normal, expected vault operation (the function and `previewLossAdjustedWithdrawFunds` exist precisely for realized-loss epochs). The attacker does not need to cause the loss; any holder whose receipt survives a loss-adjusted stop benefits automatically on their next `claimWithdrawRequest`. The trigger depends on the CDO calling `deposit` (epoch increment) before `collectWithdrawFunds` in the stop flow, which is the natural order in which recalled funds are deposited and then accounted.

### Recommendation
Key the recovery price to the epoch that owns the pending receipts, not the mutable counter: in `collectWithdrawFunds`, store `lossRecoveryPriceByEpoch[epochNumber - 1]` (or pass the request epoch from the CDO), matching `withdrawsRequestsByEpoch[_user][lastWithdrawRequest[_user]]`. Alternatively, increment `epochNumber` only after the pending-receipt funding is resolved, or record `pendingWithdrawsEpoch` when receipts accumulate and use it for both the price write and the lookup.
