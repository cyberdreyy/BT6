## Finding: MEV liquidators can front-run users during panic-pause unwind window (M-24 analog)

### Title
Liquidators can front-run recovering users when the panic-pause auto-expires or is lifted, causing unfair liquidations - (File: programs/marginfi/src/state/panic_state.rs, programs/marginfi/src/instructions/marginfi_group/panic_unpause.rs, programs/marginfi/src/instructions/marginfi_account/liquidate.rs)

### Summary
Marginfi implements a protocol-wide "panic pause" (`panic_pause`/`panic_unpause`/`panic_unpause_permissionless`) that blocks deposit, withdraw, borrow, repay, and classic liquidation while active [1](#0-0) . This mirrors the Symmetrical bug class exactly: user self-help actions (deposit/repay to heal a position) are blocked at the same time liquidation is blocked, and there is no grace period built into the unpause path once the block is lifted.

### Finding Description
When `panic_pause` is invoked, `PanicState::pause` sets `FLAG_PAUSED` and the pause auto-expires after `PAUSE_DURATION_SECONDS` (6 hours) [2](#0-1) . While paused, `validate_bank_state(..., InstructionKind::FailsInPausedState)` blocks deposit, withdraw, borrow, repay AND `lending_account_liquidate` on both the asset and liability bank [1](#0-0) , confirmed by the test suite explicitly showing withdraw/repay/liquidation are all blocked during pause [3](#0-2) [4](#0-3) .

Oracle prices continue to move during the (up to 6-hour) pause window. A position that was healthy when the pause began can become unhealthy purely from price movement, and the affected user has no way to deposit collateral or repay debt to protect themselves, because these instructions are blocked identically to liquidation.

When the pause ends — either manually via `panic_unpause` (immediate, admin-only) or automatically/permissionlessly via `panic_unpause_permissionless` once `is_expired` becomes true — the flag is cleared instantly with no cooldown or grace window: `unpause()` simply clears `FLAG_PAUSED` and resets counters [5](#0-4) , and `panic_unpause` performs this state transition atomically within a single instruction with no additional delay before all instructions (including `lending_account_liquidate`) become valid again [6](#0-5) .

At that exact moment, both "healing" transactions (deposit/repay) and "attacking" transactions (`lending_account_liquidate`) become simultaneously valid. Because `lending_account_liquidate` is fully permissionless — anyone can call it with no special authority check, only bank/account/pause-state checks [7](#0-6)  — MEV searchers/liquidator bots can win the race to land the liquidation transaction ahead of the affected user's deposit/repay transaction, exactly as described in the Symmetrical report. Note that `panic_unpause_permissionless` (any caller may trigger unpause once expired) further widens the attack surface, since a liquidator can atomically bundle the permissionless unpause instruction together with their own liquidation instruction in the same block/transaction to guarantee ordering ahead of any human user reacting after observing the state.

### Impact Explanation
A user whose position became under-collateralized purely due to oracle price movement during a pause they had no ability to react to can be liquidated the instant the pause lifts, losing the liquidator fee + insurance fee (5% total) on the seized collateral, with no opportunity to self-heal first. This is a direct, deterministic loss of user funds tied to a protocol-owner/permissionless-unpause action, matching the accepted Sherlock Medium classification for the analogous Symmetrical issue.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: panic-pause is an emergency mechanism expected to be used during periods of market stress/volatility (exactly when prices are most likely to move adversely against open positions), and MEV/liquidation bots monitoring account health are well-positioned to submit the liquidation instruction in the same block as (or bundled with) the unpause/permissionless-unpause transaction, before an affected human user can react.

### Recommendation
Introduce a grace period after `panic_unpause`/`panic_unpause_permissionless` during which `lending_account_liquidate` (and the receivership `StartLiquidation`/`EndLiquidation` flow, if not already covered) remains blocked while deposit/repay/withdraw are re-enabled, giving users a window to restore health before liquidation resumes. Alternatively, disallow bundling `panic_unpause_permissionless` with a liquidation instruction in the same transaction/block, or require a minimum number of slots to elapse between unpause and the first permitted liquidation.

### Proof of Concept
1. `global_fee_admin`/`pause_delegate_admin` calls `panic_pause` [8](#0-7) , blocking deposit/withdraw/borrow/repay/`lending_account_liquidate` group-wide.
2. During the pause window (up to 6 hours), oracle prices move such that a user's account health, computed via live pricing, drops below the maintenance threshold — the user cannot deposit or repay to fix it because those instructions fail with `MarginfiError::ProtocolPaused` [9](#0-8) .
3. The pause is lifted (`panic_unpause` or `panic_unpause_permissionless` after expiry) [6](#0-5) ; `is_paused_flag()` becomes false immediately, with zero grace period.
4. A liquidator (or bundled transaction containing the permissionless unpause call itself) submits `lending_account_liquidate` against the now-unblocked, still-unhealthy account before the user's own deposit/repay transaction lands, seizing collateral at the discounted liquidation rate.

```rust
pub fn panic_unpause(ctx: Context<PanicUnpause>) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_mut()?;
    let current_timestamp = Clock::get()?.unix_timestamp;

    require!(
        fee_state.panic_state.is_paused_flag(),
        crate::errors::MarginfiError::ProtocolNotPaused
    );

    fee_state.panic_state.unpause_if_expired(current_timestamp);

    if fee_state.panic_state.is_paused_flag() {
        fee_state.panic_state.unpause();
        msg!(
            "Protocol manually unpaused by admin at timestamp: {}",
            current_timestamp
        );
    } else {
        msg!(
            "Protocol was already auto-unpaused due to expiration at timestamp: {}",
            current_timestamp
        );
    }

    msg!(
        "Consecutive pause count reset to: {}",
        fee_state.panic_state.consecutive_pause_count
    );

    Ok(())
}
```

```rust
pub fn panic_pause(ctx: Context<PanicPause>) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_mut()?;
    let current_timestamp = Clock::get()?.unix_timestamp;

    // Update panic state if the current pause has expired
    fee_state.panic_state.unpause_if_expired(current_timestamp);

    fee_state.panic_state.pause(current_timestamp)?;

    msg!("Protocol paused at timestamp: {}", current_timestamp);
    msg!(
        "Pause will auto-expire at: {}",
        current_timestamp + PanicState::PAUSE_DURATION_SECONDS
    );
    msg!(
        "Daily pause count: {}",
        fee_state.panic_state.daily_pause_count
    );
    msg!(
        "Consecutive pause count: {}",
        fee_state.panic_state.consecutive_pause_count
    );

    Ok(())
}
```
