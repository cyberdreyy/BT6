### Title
Builder withdrawal amount silently capped at balance while the committed `Withdrawal.amount` (which the EL must pay) is not - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas (`EIP7732`) beacon-chain spec, builder-originated withdrawals are computed with an uncapped `amount` and placed into `state.payload_expected_withdrawals` — the commitment the execution layer is required to honor by paying `fee_recipient`/`execution_address` that exact amount. However, when the consensus layer actually debits the builder's internal balance in `apply_withdrawals`, the deduction is silently capped at whatever balance remains: [1](#0-0) 

This is the same bug class as Ajna's M-8: a payment obligation that is fixed/committed at one point (the accumulated-rewards figure in Ajna; the `Withdrawal.amount` here) is later "settled" against a balance that may be smaller, with the shortfall discarded and untracked instead of causing a revert or being queued for later settlement.

### Finding Description
`get_builder_withdrawals` (builder pending withdrawals) and `get_builders_sweep_withdrawals` (builder sweep) both build `Withdrawal` entries whose `amount` field comes directly from the builder's committed obligation (`withdrawal.amount` from `state.builder_pending_withdrawals`, or `builder.balance` for sweep): [2](#0-1) 

These withdrawals are placed unmodified into `state.payload_expected_withdrawals` via `update_payload_expected_withdrawals`, which is the value the execution layer is bound to and will mint/pay to `fee_recipient` in full: [3](#0-2) 

But the actual state mutation that is supposed to "back" that payment only decreases the builder's tracked balance by `min(withdrawal.amount, builder_balance)`: [1](#0-0) 

If `withdrawal.amount > builder_balance` at processing time, the CL removes only `builder_balance` (down to 0) from `state.builders[builder_index].balance`, but the EL is still committed to pay the full, uncapped `withdrawal.amount` to the fee recipient (since that is what's recorded in `payload_expected_withdrawals`). No deficit/IOU is recorded anywhere in state — the shortfall simply vanishes from the accounting, exactly like the Ajna `RewardsManager._claimRewards` bug capping the ERC-20 transfer at `ajnaBalance` without tracking the unmet portion.

This is explicitly exercised by the repo's own test suite, which sets up a builder with insufficient balance relative to a pending withdrawal and asserts the committed withdrawal amount is the full (larger) requested amount while the balance deduction is capped: [4](#0-3) 

The project's own AI-generated report on this function documents the same asymmetry as accepted behavior rather than a guarded invariant: [5](#0-4) 

Note also that the spec text itself explicitly calls out that this exact "commit now, settle later, saturate at zero" pattern causes "net supply inflation" when it happens for *validator* withdrawals, and states that validator withdrawals are applied immediately in the same slot specifically to avoid it: [6](#0-5) 

Yet for **builder** withdrawals, the `min()`-capped deduction in `apply_withdrawals` reproduces the very same saturation-causes-inflation pattern the spec authors warned about for validators, without an equivalent same-slot mitigation. The obligation accounting (`get_pending_balance_to_withdraw_for_builder`, `can_builder_cover_bid`) attempts to prevent a builder from over-committing at bid-acceptance time: [7](#0-6) 

but this is a point-in-time check performed when a *new* bid is accepted; nothing in `apply_withdrawals` re-verifies that the sum of amounts actually being withdrawn in a given block still matches the builder's real balance before minting the full uncapped amount to the fee recipient. I was not able to fully rule out, within the scope of this review, whether some sequence of builder deposit/exit/bid processing could cause the sum of a builder's outstanding `builder_pending_withdrawals`/`builder_pending_payments` obligations to exceed `state.builders[i].balance` by the time `apply_withdrawals` runs — this is the residual uncertainty in this analog, and would require deeper tracing of every code path that reads/writes `state.builders[*].balance` (builder deposits, exits, bid settlement `settle_builder_payment`, etc.) to fully confirm reachability outside of directly-crafted test states.

### Impact Explanation
If reachable through legitimate state transitions (not just directly-crafted test states), this breaks the "Gwei created" invariant: the execution layer would mint/pay the full `Withdrawal.amount` to `fee_recipient` while the beacon state only ever removes `min(amount, balance)` from the builder's tracked balance — the difference is ETH created without a corresponding decrease anywhere in consensus-layer accounting, which is a Critical-class issue per the given impact taxonomy (Gwei created not backed by any decrease).

### Likelihood Explanation
Low-to-Medium confidence on reachability. The spec's `can_builder_cover_bid` check is designed to prevent commitments from ever exceeding a builder's balance, so under normal single-obligation flows this shortfall path may never trigger. However, the capping logic in `apply_withdrawals` exists and is explicitly tested as "expected" behavior, and the same failure pattern is explicitly documented by the spec authors as causing "net supply inflation" in the analogous validator-withdrawal case — suggesting the authors may not have fully closed this gap for builders. Confirming actual reachability would require exhaustively tracing all builder-balance-affecting operations across a block/epoch boundary, which was not completed here.

### Recommendation
Either (a) prove and formally document/assert an invariant that `sum(pending obligations for a builder) <= builders[i].balance` holds at all times up to and including `apply_withdrawals`, making the `min()` cap unreachable by construction, or (b) if the cap can be reached, do not silently discard the shortfall — either revert block processing when a builder's committed withdrawal cannot be fully backed by its balance, or explicitly track and re-queue the unmet portion so it isn't lost from consensus-layer accounting while the EL still pays the full committed amount.

### Proof of Concept
Analogous to Ajna's `_claimRewards`, the repository's own test demonstrates the mismatch directly at the spec level: [8](#0-7) 
- Builder balance = 1 ETH; a pending withdrawal for 5 ETH is queued.
- `get_builder_withdrawals` emits `Withdrawal(amount=5 ETH)` into `payload_expected_withdrawals` (what the EL must pay to `fee_recipient`).
- `apply_withdrawals` decreases `builders[0].balance` by only `min(5 ETH, 1 ETH) = 1 ETH`, leaving balance at 0.
- Net effect: EL pays out 5 ETH to `fee_recipient`; CL state only accounts for 1 ETH leaving the system — 4 ETH is unaccounted for (created), assuming this state is reachable through legitimate protocol operation and not merely direct test manipulation of `state.builders[...].balance`.

#### New `get_pending_balance_to_withdraw_for_builder`

```python
def get_pending_balance_to_withdraw_for_builder(
    state: BeaconState, builder_index: BuilderIndex
) -> Gwei:
    balance = Gwei(0)
    for withdrawal in state.builder_pending_withdrawals:
        if withdrawal.builder_index == builder_index:
            balance += withdrawal.amount
    for payment in state.builder_pending_payments:
        if payment.withdrawal.builder_index == builder_index:
            balance += payment.withdrawal.amount
    return balance
```

```python
def can_builder_cover_bid(
    state: BeaconState, builder_index: BuilderIndex, bid_amount: Gwei
) -> bool:
    builder_balance = state.builders[builder_index].balance
    pending_withdrawals_amount = get_pending_balance_to_withdraw_for_builder(state, builder_index)
    min_balance = MIN_DEPOSIT_AMOUNT + pending_withdrawals_amount
    if builder_balance < min_balance:
        return False
    return builder_balance - min_balance >= bid_amount

##### New `get_builder_withdrawals`

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

```markdown
*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
