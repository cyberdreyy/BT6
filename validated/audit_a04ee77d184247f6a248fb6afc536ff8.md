This is a promising lead — let me examine the `block_rejection_signer_addrs` table schema and its usage functions closely, since the primary key appears scoped only by `signer_addr`, not by block hash.### Title
Signer's block-rejection tracking table is keyed only by signer address, letting a later rejection silently erase/corrupt the weighted-rejection tally for an earlier block - ([File: stacks-signer/src/signerdb.rs])

### Summary
`stacks-signer` tracks which signer addresses have rejected a given block in the `block_rejection_signer_addrs` table so it can tally rejection weight and decide `mark_globally_rejected`. The table's `PRIMARY KEY` is declared on `signer_addr` alone, not on `(signer_signature_hash, signer_addr)`, even though the accompanying comment explicitly states the sighash is meant to uniquely identify the block being tracked. This mirrors the SYMM finding's root cause: an accounting record meant to be scoped per-context (per block, analogous to per-user balance) is instead stored in a structure keyed only by the actor (`signer_addr`, analogous to the shared `balances[feeCollector]` slot), so an action taken in one context (rejecting block B) silently clobbers the accounting state kept for another context (block A) that a different code path still depends on for a threshold decision.

### Finding Description
The schema is:
```rust
static CREATE_BLOCK_REJECTION_SIGNER_ADDRS_TABLE: &str = r#"
CREATE TABLE IF NOT EXISTS block_rejection_signer_addrs (
    -- The block sighash commits to all of the stacks and burnchain state as of its parent,
    -- ... Just the sighash is sufficient to uniquely identify the block ...
    signer_signature_hash TEXT NOT NULL,
    -- the signer address that rejected the block
    signer_addr TEXT NOT NULL,
    PRIMARY KEY (signer_addr)
) STRICT;"#;
``` [1](#0-0) 

Despite the comment's stated intent that the sighash is the identifying key for a rejection record, the actual `PRIMARY KEY` constraint is `(signer_addr)` only — a single signer address can have at most one row in this table for its *entire lifetime*, not one row per block it has rejected.

This table is written and read from `store_and_process_block_rejection_signature`, which is invoked every time this signer processes a peer's (or its own) block rejection:
```rust
match self.signer_db.add_block_rejection_signer_addr(
    block_hash,
    signer_address,
    reject_reason,
) { ... }
...
let rejection_addrs = match self.signer_db.get_block_rejection_signer_addrs(block_hash) { ... };
let total_reject_weight =
    self.compute_signature_signing_weight(rejection_addrs.iter().map(|(addr, _)| addr));
...
if total_reject_weight.saturating_add(min_weight) <= total_weight {
    // Not enough rejection signatures to make a decision
    return;
}
...
block_info.mark_globally_rejected()
``` [2](#0-1) 

Because the table's uniqueness is keyed only by `signer_addr`, once signer `S` rejects block `A` (inserting/updating the single row for `S` to point at sighash `A`), any subsequent rejection by `S` of a *different* block `B` (a sibling proposal at the same height, a reproposed/re-hashed block, or a block from a different tenure the signer is still concurrently evaluating) will overwrite that same row to point at sighash `B` instead. The row that recorded `S`'s rejection of `A` no longer exists under sighash `A`. Any later call to `get_block_rejection_signer_addrs(A)` (whether triggered by a fresh rejection from another signer, a re-evaluation of `A`, or a delayed/late-arriving rejection from a third signer) will now under-count `S`'s weight against `A`, even though `S` genuinely rejected `A` and never retracted that vote.

This breaks the "aggregated-weight vs verified-accepts" equality the tallying logic assumes holds: `total_reject_weight` computed from `get_block_rejection_signer_addrs(block_hash)` is supposed to reflect the sum of weights of every signer address that has genuinely rejected that specific block, but the storage layer can silently drop entries for a block once the same signer rejects any other block.

### Impact Explanation
The direct, concretely reachable consequence is a **miscounted rejection weight**, which is exactly the "rejection recounted" class the rules call out as Critical when it flips a decision, or High as a liveness wedge:
- If enough of block `A`'s recorded rejectors later reject other blocks (or even a single signer re-proposing/re-evaluating multiple blocks in the same window), `get_block_rejection_signer_addrs(A)` under-counts, so `total_reject_weight` for `A` can fail to cross the `> total_weight - min_weight` threshold in `store_and_process_block_rejection_signature`, meaning `A` is never `mark_globally_rejected` even though a real rejecting majority exists. This stalls the state machine's decision on `A` (a liveness wedge on a specific block's terminal state), and — since `check_state` treats `GloballyRejected`/`GloballyAccepted` as mutually terminal — leaves `A` stuck in a non-terminal local state indefinitely if no other rejections/acceptances arrive to re-trigger the tally.
- Because rows are keyed by `signer_addr` only, the corruption is triggered purely by the *number of distinct blocks a signer has rejected over its lifetime*, which is routine signer behavior (miners resubmit reproposals with different transaction sets/sighashes regularly, per the `signers_reprocess_late_block_proposals_signatures` and `signer_reevaluates_proposal_with_missing_burn_view` test flows) [3](#0-2) , not an attacker-controlled edge case — but it is a genuine one-slot-miner-triggerable condition: a miner that proposes multiple distinct blocks (legitimately or via crafted reproposals with different sighashes) at/near the same height causes signers to reject more than one distinct block hash, which is exactly the trigger.

### Likelihood Explanation
No majority collusion or privileged access is required. A single miner proposing more than one distinct block (e.g. a legitimate reproposal after a rejected transaction, or two competing miners at the same height) causes signers in the normal course of operation to reject more than one `signer_signature_hash`, which is sufficient to trigger the overwrite in this single-column-keyed table. The relevant code path (`store_and_process_block_rejection_signature` / `add_block_rejection_signer_addr` / `get_block_rejection_signer_addrs`) is on the hot path for every rejected block, so likelihood of manifesting under a network's regular reproposal/replay dynamics is high.

### Recommendation
Change the `block_rejection_signer_addrs` table's primary key to the compound key `(signer_signature_hash, signer_addr)` so that a signer's rejection is recorded per block, matching the stated intent in the table's own comment and matching how `get_block_rejection_signer_addrs(block_hash)` is actually queried. Add a migration to widen the existing primary key and re-verify `add_block_rejection_signer_addr`'s INSERT semantics (`INSERT OR REPLACE`/`INSERT OR IGNORE`) against the corrected key so that rejections for distinct blocks by the same signer no longer collide.

### Proof of Concept
1. Signer `S` receives block proposal `A` (sighash `H_A`), validates it, and rejects it (e.g. `ReorgNotAllowed`). `store_and_process_block_rejection_signature` calls `add_block_rejection_signer_addr(H_A, S, reason)`, inserting the row `(H_A, S)` with primary key `S`. [4](#0-3) 
2. Before enough other signers reject `A` to cross threshold, the same miner (or a competing miner at the same height) sends a second, distinct block proposal `B` (sighash `H_B`) which `S` also rejects. `add_block_rejection_signer_addr(H_B, S, reason)` is called, and because the table's primary key is `signer_addr` alone, this either overwrites the existing row for `S` to now reference `H_B`, or fails/no-ops depending on INSERT semantics — either way the entry associating `S` with `H_A` is lost. [1](#0-0) 
3. A third signer now rejects `A` and calls `get_block_rejection_signer_addrs(H_A)` to recompute `total_reject_weight`; `S`'s weight is no longer included in the result set for `H_A`, even though `S` genuinely rejected `A` and never changed that vote — under-counting the rejection weight used in the threshold check at `if total_reject_weight.saturating_add(min_weight) <= total_weight { return; }`. [5](#0-4) 

I could not retrieve the exact SQL body of `add_block_rejection_signer_addr` (only the schema and call sites) within the available tool budget, so the precise overwrite-vs-error behavior of the INSERT statement is unconfirmed; however, the schema-level primary-key mismatch is definitive on its own — either failure mode (silent overwrite or insert failure) produces the same miscounted-rejection-weight consequence described above.
