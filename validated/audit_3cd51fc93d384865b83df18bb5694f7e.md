### Title
Command Injection via Unquoted Heredoc in `BashWriter.DotEnvVariables` combined with insufficient `DotEnvEscape` value sanitization - ([File: shells/bash.go], [File: helpers/shell_escape.go])

### Summary
`BashWriter.DotEnvVariables` writes variable data into a temp file using an **unquoted** heredoc (`cat << EOF`), which causes bash to perform command/parameter substitution on the heredoc body at script-execution time. Because `helpers.DotEnvEscape` (used to build that heredoc body) only escapes backslashes, double quotes, newlines and carriage returns — not `$` or backticks — any variable value containing `$(...)`, `` ` ` `` or `${...}` is executed/expanded by the shell while the runner-generated script is running, before the resulting file is ever read back by `SourceEnv`.

### Finding Description
`DotEnvVariables` builds the script fragment as: [1](#0-0) 

The delimiter `EOF` is unquoted (`<< EOF`, not `<< 'EOF'`), so per POSIX/bash heredoc semantics the body undergoes parameter expansion, command substitution, and arithmetic expansion before being redirected into `dotEnvFile`.

The body is produced by `helpers.DotEnvEscape`, whose escaper only neutralizes `\`, `"`, `\n`, `\r`: [2](#0-1) 

It does **not** escape `$` or backticks. So a variable value such as `$(id > /tmp/pwned)` is emitted verbatim as:
```
KEY="$(id > /tmp/pwned)"
```
inside the heredoc, and because the heredoc terminator is unquoted, bash executes `id > /tmp/pwned` and substitutes its output the moment the generated script reaches this `cat << EOF` block — this happens independently of, and prior to, the separate `SourceEnv` consumer: [3](#0-2) 

(As a secondary, non-injection correctness issue: `SourceEnv`'s `export "$line"` also does not correctly re-parse the `KEY="value"` quoting produced by `DotEnvEscape` — the literal `"` characters end up embedded in the exported value rather than being consumed as quoting — but this by itself does not enable code execution since `"$line"` expansion is not re-scanned for further substitution.)

The exploitable path is entirely in `DotEnvVariables`/`DotEnvEscape`: whatever populates the `variables map[string]string` argument is the attacker-controlled input. If any value in that map originates from data an unprivileged pipeline author can influence but that is expected to be inert (e.g., values inherited from a `dotenv` artifact report of an upstream job, cache-key-derived variables, or other pipeline/job variables assembled by the Runner rather than the user's own job script), that value gets shell-evaluated during script generation/execution — i.e., code runs with the same privileges as the job shell but from a value the caller assumed was just data being persisted to a file, not code to be evaluated.

### Impact Explanation
An attacker who controls the *value* of any variable later routed through `DotEnvVariables` can achieve arbitrary shell command execution in the job's runner-generated script, at the point that variable set is materialized — even though the intended operation is "write these key/value pairs to a file for later export," not "execute this value as shell code." This breaks the invariant that value data (especially data crossing job/artifact boundaries, e.g. dotenv-report-inherited variables) is not re-interpreted as shell syntax.

### Likelihood Explanation
Trivial to trigger: any value assembled into the `variables` map that contains `$(`, `` ` ``, or `${` will be executed. No key format bypass is required (keys are already regex-restricted, but values are not restricted for `$`/backtick). This is 100% reproducible whenever `DotEnvVariables` is invoked with such a value.

### Recommendation
- Quote the heredoc delimiter (`cat << 'EOF' > file`) so the body is treated literally by bash and not subject to expansion, matching how `cat << EOF` is typically expected to just dump static content.
- Extend `escapeDotEnvValue` (or add a dedicated escaper) to also escape `$` and backtick characters if the heredoc must remain unquoted for any reason.
- Fix `SourceEnv`'s `while read -r line; do export "$line"; done` to correctly parse `KEY="value"` formatted lines (e.g., use `set -a; . "$file"; set +a` or explicitly strip surrounding quotes) rather than relying on literal quote characters being ignored.

### Proof of Concept
```go
func TestBashWriter_DotEnvVariables_HeredocInjection(t *testing.T) {
    w := &BashWriter{TemporaryPath: "/tmp/build"}
    // Attacker-controlled value containing command substitution
    vars := map[string]string{
        "SAFE": "$(touch /tmp/PWNED)",
    }
    dotEnvFile := w.DotEnvVariables("env_file", vars)

    script := w.String()
    // Assert the heredoc is unquoted (delimiter not quoted), proving the
    // shell will expand $() inside the body when the script executes.
    require.Contains(t, script, "cat << EOF > "+dotEnvFile)
    require.NotContains(t, script, "cat << 'EOF'")

    // Execute the generated fragment with bash and confirm command execution occurs.
    cmd := exec.Command("bash", "-c", script)
    require.NoError(t, cmd.Run())
    _, err := os.Stat("/tmp/PWNED")
    require.NoError(t, err, "expected command substitution in variable value to have executed")
}
```
Expected result before fix: `/tmp/PWNED` is created, proving that a value meant to be inert data is executed as shell code during `DotEnvVariables` script generation. After applying the quoted-heredoc fix, the file must NOT be created and the raw literal string `$(touch /tmp/PWNED)` should appear unexpanded in `dotEnvFile`.

func DotEnvEscape(variables map[string]string) string {
	var sb strings.Builder

	// Sort variables to get deterministic output
	keys := make([]string, 0, len(variables))
	for key := range variables {
		keys = append(keys, key)
	}
	sort.Strings(keys)

	for _, key := range keys {
		if !isValidDotEnvKey(key) {
			// Skip invalid keys
			continue
		}

		value := variables[key]
		fmt.Fprintf(&sb, "%s=\"%s\"\n", key, escapeDotEnvValue(value))
	}

	return sb.String()
}
