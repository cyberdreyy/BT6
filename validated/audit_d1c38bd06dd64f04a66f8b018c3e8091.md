## Confirmed: Beneficiary redirect breaks for pending commission requested during `switch_operator`

The mechanism is real, though it should be described precisely: it isn't that unpaid commission is "keyed to `operator_1`'s address" incorrectly (that's the normal design of the `distribution_pool`), it's that `distribute_internal`'s beneficiary-redirect check compares the pool's shareholder address against the *current* `operator` parameter of the call, which changes after a switch — causing commission requested for `operator_1` right before the switch to bypass `beneficiary_for_operator` and pay `operator_1`'s raw address instead.

### Title
Stale commission distribution shares bypass `beneficiary_for_operator` redirection after `switch_operator` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`switch_operator` first flushes already-inactive funds via `distribute_internal(staker, old_operator, ...)` (which correctly resolves `old_operator`'s beneficiary for that flush), then calls `request_commission_internal(old_operator, ...)` which adds a *new* distribution-pool share keyed to `old_operator`'s raw address for any newly accrued commission, and unlocks it via `stake::unlock_with_cap` (moving it to `pending_inactive`, not yet withdrawable). The `StakingContract` (with this pending share still in its `distribution_pool`) is then moved into the map under `new_operator`. `add_distribution` adds the recipient using the raw `operator` address, not the beneficiary: [1](#0-0) . On any later call to `distribute(staker, new_operator)`, `distribute_internal` runs with `operator = new_operator`, and its beneficiary-substitution logic only redirects when the redeemed share's address equals the `operator` parameter of that specific call: [2](#0-1) . Since the stale share's address is `old_operator` but the call's `operator` is now `new_operator`, the condition `recipient == operator` is false, so `beneficiary_for_operator(old_operator)` is never looked up, and the funds are paid directly to `old_operator`'s own account address instead of the beneficiary they configured via `set_beneficiary_for_operator`.

### Impact Explanation
This directly corrupts the operator-commission-to-beneficiary payout routing that `set_beneficiary_for_operator` is designed to guarantee: [3](#0-2) . Operators frequently use a beneficiary to route commission to cold storage/custody separate from the hot operator key; this bug silently reverts that routing to the operator's own address for any commission requested in the same transaction/epoch window as a `switch_operator` call, without any error or warning. It falls under "Operator commission, beneficiary payout... corruption that credits the wrong account."

### Likelihood Explanation
This triggers under normal, unprivileged usage — no attacker role is required. It happens whenever a staker calls `switch_operator`/`switch_operator_with_same_commission` (an ordinary staker action) while there is unpaid commission for the old operator that has just been unlocked (i.e., not yet inactive/withdrawable at switch time), which is a routine sequence (commission accrues continuously; switching operators is a normal owner operation). `distribute()` itself is `public entry` and callable by anyone: [4](#0-3) .

### Recommendation
`distribute_internal`'s beneficiary substitution should not depend on matching the call-time `operator` parameter. Either: (a) resolve the beneficiary at share-creation time in `add_distribution`/`request_commission_internal` (store the beneficiary address, not the operator address, as the share recipient), or (b) have `distribute_internal` check `beneficiary_for_operator` for the shareholder address itself whenever that address is a known/former operator, rather than only when it equals the currently passed-in `operator`.

### Proof of Concept
1. `staker` creates a staking contract with `operator_1`, stake accrues rewards.
2. `operator_1` calls `set_beneficiary_for_operator(operator_1, beneficiary)`.
3. `staker` calls `switch_operator(staker, operator_1, operator_2, commission)`; internally `request_commission_internal(operator_1, ...)` adds a distribution share for `operator_1`'s raw address and unlocks it (`pending_inactive`), then the contract moves under `operator_2`.
4. Advance epoch until lockup expires so the pending amount becomes `inactive`.
5. Anyone calls `distribute(staker, operator_2)`. Assert `operator_1`'s raw account balance increases by the commission amount, while `beneficiary`'s balance is unchanged — demonstrating beneficiary routing is bypassed for this share, contradicting the guarantee set up in step 2.

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
