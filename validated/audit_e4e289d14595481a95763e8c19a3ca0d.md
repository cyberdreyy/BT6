Confirmed root cause. This is a real analog: the miner-side vote tally in `stackerdb_listener.rs` guards duplicate acceptances against `gathered_signatures` (a map keyed by slot_id) but guards duplicate rejections against a **separate** field, `responded_signers` (a `HashSet<u32>`). A single signer that first rejects and later accepts (or races two messages) gets counted on **both** sides of the tally, because the accept branch never checks `responded_signers`, and the reject branch never checks `gathered_signatures`.

### Title
Signer weight double-counted across accept/reject on vote flip, breaking the aggregated-weight-vs-verified-accepts equality - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`BlockStatus` tracks approvals and rejections with two independently-gated counters that are supposed to represent the same underlying fact — "has this signer already been counted for this block". They are not kept in sync, so one signer's weight can land in both `total_weight_approved` and `total_weight_rejected` for the same block.

### Finding Description
`BlockStatus` holds `responded_signers: HashSet<u32>` and `gathered_signatures: BTreeMap<u32, MessageSignature>` [1](#0-0) .

- On `BlockResponse::Accepted`, the dedupe check is `if !block.gathered_signatures.contains_key(&slot_id)` before adding `signer_entry.weight` to `total_weight_approved`; `responded_signers.insert(slot_id)` is called unconditionally afterward [2](#0-1) .
- On `BlockResponse::Rejected`, the dedupe check is `if block.responded_signers.insert(slot_id)` before adding weight to `total_weight_rejected` [3](#0-2) .

Because the two paths gate on different sets, a signer who rejects first (populating `responded_signers`) and then sends an `Accepted` message for the same `signer_signature_hash` passes the accept-path check (`gathered_signatures` is still empty for that slot) and gets `total_weight_approved` incremented — while its weight is *still counted* in `total_weight_rejected`, since nothing ever removes it. The signer's weight now sits in both tallies simultaneously. The `reset_rejections` helper only special-cases the reverse direction (re-adding approvers into `responded_signers` after a rejection-timeout reset, at `start=706 end=723`), confirming the two sets are only loosely reconciled and not on the accept path [4](#0-3) .

The coordinator (`SignerCoordinator::get_block_status`) treats `total_weight_approved >= self.weight_threshold` and `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` as mutually exclusive outcomes and returns/erroring on whichever crosses first [5](#0-4) . This is the equality the bug breaks: "sum of verified accept-weight" is supposed to be disjoint from "sum of verified reject-weight" for the same signer set, since `total_weight_rejected + total_weight_approved` should never exceed `self.total_weight`. With the double count, a single flipping signer inflates *both* sides, letting `total_weight_approved` reach threshold sooner than genuinely warranted (fewer real distinct signers than the threshold requires) — this is the "aggregated-weight vs verified-accepts" equality break called out as in-scope.

### Impact Explanation
This lets a single signer artificially inflate the approve tally used by the miner to decide when a block has 70% signer weight and can be relayed as signed (`Ok(block_status.gathered_signatures.values().cloned().collect())` at `signer_coordinator.rs:545`). Because the leaked/duplicated weight is counted without a second independent signer actually approving, a block could be treated by the miner as having reached the signature threshold with less real approving weight than required — undermining the "aggregated weight == verified accepts" invariant the whole pre-commit/threshold design (see `docs/signer-flows.md` §5–6) depends on. This does not by itself forge a signature the node will accept (the node's own `NakamotoBlockHeader::compute_voting_weight_threshold` check on the actual signature set still applies), but it corrupts the miner-local bookkeeping used to decide when to stop waiting and push the block, which can cause the miner to prematurely believe it has enough approvals from what it thinks are distinct honest signers.

### Likelihood Explanation
Reachable by a single signer (one-slot) sending an `Accepted` message for a block it previously `Rejected` — a legitimate scenario is a signer that rejects, then later observes enough pre-commits/re-validates and legitimately signs the same block (this is explicitly the documented flow in `docs/signer-flows.md` — pre-commit driven re-signing after an earlier hold). No majority or other signer's key is needed; only ordinary message flow through StackerDB from one signer's own key.

### Recommendation
Gate both branches on the same set/field. E.g., before crediting `total_weight_approved`, also check (and remove from) `responded_signers`'s reject bookkeeping, or unify into a single `HashMap<u32, Vote>` recording the signer's current vote and only adjust the respective totals via a diff against the previous vote (decrement old bucket, increment new bucket) rather than two independently-gated counters.

### Proof of Concept
1. Signer slot `S` (weight `w`) sends `BlockResponse::Rejected` for block `B` → `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`.
2. Same signer `S` later sends `BlockResponse::Accepted` for `B` (e.g., after re-validating following a pre-commit threshold per `docs/signer-flows.md` §5) → `gathered_signatures.contains_key(&S)` is `false` → `total_weight_approved += w`.
3. Now `total_weight_approved + total_weight_rejected` counts `w` twice from the same signer, so both `total_weight_rejected` can stay near-threshold for rejection *and* `total_weight_approved` reaches threshold sooner than it should relative to the number of genuinely distinct approving signers, corrupting the miner's threshold decision in `signer_coordinator.rs` lines 509–545.

    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
