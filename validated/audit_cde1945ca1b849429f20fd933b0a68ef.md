### Title
Block-revenue commission (SIMD-0291/SIMD-0123) can be changed with no epoch delay, letting a validator retroactively apply a new commission rate to already-accrued block rewards before distribution - (File: programs/vote/src/vote_state/mod.rs)

### Summary
The external report's bug class is: a mutable global "rate" parameter is applied to value that already accrued under the old rate, letting the party in control front-run/back-run the rate change to their benefit. In Agave's vote program, the legacy per-vote-account commission (`update_commission`) and the inflation-rewards commission are protected against this by an epoch-delay mechanism, but the new basis-points **block-revenue commission** (`update_commission_bps` with `CommissionKind::BlockRevenue`, added for SIMD-0291/SIMD-0123) explicitly has no such delay and can be changed at any time, then applied to already-accumulated `pending_delegator_rewards` at distribution time.

### Finding Description
`update_commission_bps` in `programs/vote/src/vote_state/mod.rs` is documented as having "No commission update rule, per SIMD-0249 and SIMD-0291" and enforces no epoch-position or magnitude restriction: [1](#0-0) 

This contrasts with the legacy `update_commission`, which enforces `is_commission_update_allowed` (only increases in the first half of an epoch): [2](#0-1) 

For inflation rewards, the protocol additionally protects against last-minute rate changes at the *reward-calculation* layer: `redeem_delegation_rewards` reads the commission from a **snapshotted** vote-account state (`snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts`) when `delay_commission_updates` is active, rather than the live vote state, specifically "to prevent last minute commission rugs": [3](#0-2) [4](#0-3) 

However, block revenue (SIMD-0123) rewards accrue continuously into `pending_delegator_rewards` on the vote account (via `DepositDelegatorRewards`, `add_pending_delegator_rewards`) and are split at *distribution time* using `calculate_block_reward`, which reads directly from `distribution_epoch_vote_accounts` — i.e. the **live, current-epoch** vote state, not a delayed snapshot: [5](#0-4) [6](#0-5) 

`block_revenue_commission()` (via `VoteStateView`) is likewise read live off the current vote account bytes with no epoch-delay wrapper: [7](#0-6) 

The instruction handler wires `UpdateCommissionBps` straight to `update_commission_bps` with `disable_commission_update_rule` effectively bypassed for the bps path (no timing check at all is invoked for this instruction): [8](#0-7) 

Because `pending_delegator_rewards` (the analog of the loan's "accumulated interest") is a running balance that keeps growing over an epoch/slot range under whatever commission was believed to apply, but the actual commission split used to divide the accrued balance between the voter/collector and the delegators is read from the *current* vote-account state at redemption time (`calculate_block_reward`, using `vote_state.pending_delegator_rewards()` and, downstream, `block_revenue_commission_bps` for the eventual split), a withdraw authority can raise the block-revenue commission immediately before rewards for the epoch are redeemed/distributed and capture a larger share of value that delegators believed was already accruing under the old rate — exactly mirroring the "Alice/Bob" loan-interest scenario in the source report, except here the actor is the validator's authorized withdrawer rather than a lending-protocol admin.

### Impact Explanation
If exploited, a validator operator can unilaterally and instantly reprice the split of already-accrued, undistributed block-revenue rewards in their own favor at the moment of redemption/distribution, redirecting delegator stake rewards to the validator's commission collector. This is an economic/fund-misappropriation issue affecting delegators' expected rewards — a real "unauthorized state/fund mutation" in the sense that value delegators believed was locked in under the prior commission is retroactively reassigned. It does not cause a memory-safety or consensus-halting bug, but it is a concrete loss of delegator funds relative to the rate delegators believed was in effect, matching the primary/M-severity class in the source report.

### Likelihood Explanation
Likelihood is moderate-to-low in practice: it requires (a) `block_revenue_sharing` / SIMD-0123 and SIMD-0291 to be active, (b) the validator to hold the authorized-withdrawer key and choose to grief its own delegators, and (c) timing the commission change to just before block-reward redemption for a given epoch. Because there is no timelock or epoch-delay for the bps-based block-revenue commission (unlike the delayed inflation-rewards commission path), any validator operator can perform this at will with a single signed transaction, with no cluster-level cooldown to prevent it. This is a self-serving, non-consensus-breaking action fully reachable by an ordinary vote-account authority via a normal transaction (`UpdateCommissionBps`), which fits the "ordinary user's transaction" reachability bar.

### Recommendation
Apply the same epoch-delay ("delay commission updates") protection used for `inflation_rewards_commission_bps` to `block_revenue_commission_bps`: read the commission used in `calculate_block_reward` from the snapshotted `CachedVoteAccounts` (as `redeem_delegation_rewards` already does for inflation commission) rather than from `distribution_epoch_vote_accounts` directly, or require the block-revenue commission to be captured at deposit time (each `DepositDelegatorRewards` call) rather than at withdrawal/redemption time. Alternatively, apply `is_commission_update_allowed`-style timing restrictions (or a timelock) to `update_commission_bps` for `CommissionKind::BlockRevenue`.

### Proof of Concept
1. Enable `block_revenue_sharing`, `commission_rate_in_basis_points`, and `custom_commission_collector` features; create a VoteStateV4 vote account with `block_revenue_commission_bps = 0` (all block revenue goes to delegators).
2. Over the epoch, block rewards accumulate into `pending_delegator_rewards` via `DepositDelegatorRewards` (`programs/vote/src/vote_processor.rs:409-426`, `handler.rs::add_pending_delegator_rewards`).
3. Immediately before epoch-reward distribution (`calculate_stake_rewards_and_commissions` → `calculate_block_reward`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-232, 775-874`), the authorized withdrawer submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10_000, kind: CommissionKind::BlockRevenue }`, which succeeds unconditionally (`update_commission_bps`, `vote_state/mod.rs:827-859`; dispatcher `vote_processor.rs:202-220`).
4. When block rewards for the already-elapsed period are redeemed, `calculate_block_reward` reads the *live* (just-updated) vote state from `distribution_epoch_vote_accounts`, so the entire previously-accrued `pending_delegator_rewards` balance is now split (or entirely captured) under the new 100% commission rather than the 0% rate that was in effect while the rewards accrued — reproducing the "Alice pays 50% instead of the agreed 5%" scenario from the source report.

pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

    /// Get cached vote account state from the past few epochs so that some vote
    /// state configuration changes are delayed before being used in reward
    /// calculation.
    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        // Vote account state from the beginning of the rewarded epoch.
        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }
    }

    ) -> Result<(), InstructionError> {

            TargetVoteState::V4(v4) => {
                v4.pending_delegator_rewards = v4
                    .pending_delegator_rewards
                    .checked_add(amount)
                    .ok_or(InstructionError::ArithmeticOverflow)?;
                Ok(())
            }
        }
    }
