### Title
Funded instant-withdraw claims leave stale per-epoch basis, inflating default recovery and draining the reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests[_user]` receipt but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. The per-epoch ledger therefore keeps counting instant receipts that were already fully paid. If the borrower defaults in that same epoch while other instant requests remain unfunded, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` reuse this stale aggregate — the analog of reusing a cached result for a different input — producing a phantom reserve and an inflated `defaultRecoveryPrice`. This is the hash-collision analog: distinct lifecycle states (claimed vs outstanding receipts) collapse into the same epoch key and the stale value is silently reused.

### Finding Description
The normal claim path at lines 380–393 burns the user's receipt and pays at par but touches only `instantWithdrawsRequests[_user]`:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Neither `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` nor `instantWithdrawClaimsByEpoch[currentEpoch]` (populated at lines 371–372) is cleared. The only place that decrements them is the defaulted-claim path `_claimDefaultedInstantWithdrawRequest` (lines 847–853). So after a funded instant claim, `instantWithdrawClaimsByEpoch[E]` permanently overstates the outstanding claim basis for epoch E.

At default finalization (`finalizeDefaultRecovery` → `defaultPendingClaimBasis`, line 644–649), when `pendingInstantWithdraws != 0` the strategy adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis, and `_defaultPrefundedInstantReserve` (lines 716–723) computes `prefundedReserve = instantBasis - pendingInstant`, i.e. it assumes that difference is underlying still held by the strategy backing already-collected instant claims. But an already-claimed instant withdrawal's underlying was transferred out by `_transferFundedClaim` — the strategy no longer holds it. The claimed amount is thus counted twice: once as "reserve already held" and once as still-outstanding basis.

Attack sequence (attacker = unprivileged instant-withdraw user, epoch E running, honest borrower/manager):
1. Attacker requests instant withdrawal of `X`; a second user requests `Y`. `instantWithdrawClaimsByEpoch[E] = X + Y`, `pendingInstantWithdraws = X + Y`.
2. IdleCDO has liquidity only for `X`: `collectInstantWithdrawFunds(X)` leaves `pendingInstantWithdraws = Y`.
3. Attacker calls `claimInstantWithdrawRequest` and receives `X` underlying at par. `instantWithdrawsByEpoch`/`instantWithdrawClaimsByEpoch[E]` remain `X`/`X+Y`.
4. Borrower defaults during epoch E; manager finalizes. `defaultPendingClaimBasis` includes `X + Y` and `_defaultPrefundedInstantReserve` adds phantom `X` to `reserveAmount`, so `recoveryPrice = reserveAmount / totalBasis` is computed against a reserve that does not actually contain `X`.
5. The attacker is blocked from double-claiming by the `instantWithdrawsRequests[_user] -= claimBasis` underflow (line 848), but every legitimate defaulted claimant (normal withdraw receipt holders via `_claimDefaultedWithdrawRequest`, tranche holders via the AA/BB recovery path, and user Y's instant claim) draws from a reserve smaller than the one priced in. `defaultRecoveryReserve` is decremented per claim (line 915), so claims early in the sequence over-consume it and the last claimants' `_transferDefaultRecovery` reverts or they receive a permanently reduced payout.

Existing guards do not stop this: the underflow check prevents the attacker's own double claim but does nothing about the inflated `defaultRecoveryPrice`/`defaultRecoveryReserve` pair that penalizes all other claimants; `defaultRecoveryInitialized`, `_onlyIdleCDO`, and epoch gating are all satisfied along this path.

### Impact Explanation
Direct, quantifiable loss: the recovery reserve is short by the full amount `X` of already-paid instant claims in the default epoch, while `defaultRecoveryPrice` was set as if `X` were present. Legitimate claimants bearing the tail of the distribution lose up to `X`'s share of the reserve — a permanent loss/theft of recovery funds rather than mere freezing. Example: pool with 1M USDC basis, one funded-and-claimed instant request of 100k USDC in the default epoch inflates the computed reserve by 100k; roughly 100k USDC worth of claimant recovery is unbacked and the latest claimants absorb it entirely.

### Likelihood Explanation
Requires a specific but plausible ordering: (a) instant withdrawals enabled on a running epoch, (b) partial funding such that at least one instant receipt is claimed while another remains pending (`pendingInstantWithdraws != 0` at finalization), (c) borrower default finalized in that same epoch. All attacker actions are unprivileged (request instant withdraw, claim it). The default itself is an honest event the attacker merely sequences around — the same threat model as other pending-receipt recovery paths in this file. Likelihood is moderate: partial instant funding plus same-epoch default is not routine, but requires no privileged misbehavior and no exotic market conditions.

### Recommendation
Decrement the per-epoch instant ledger in the funded claim path: in `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` entries and subtract them from `instantWithdrawClaimsByEpoch[epochNumber]` (mirroring lines 847–853). If claims can span epochs, iterate or store the request epoch alongside the receipt; alternatively, keep a single `instantWithdrawOutstandingByEpoch` that both paths decrement so `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` always see only genuinely outstanding claims.

```solidity
// epoch E running; enable instant withdraws
cdoEpoch.setInstantWithdrawParams(0, 0, false);
// attacker requests instant withdraw X, victim requests Y
requestInstantWithdrawViaCdo(attacker, X);
requestInstantWithdrawViaCdo(victim, Y);
// CDO funds only X

// attacker claims at par

assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epochE), X); // stale!
assertEq(strategy.instantWithdrawClaimsByEpoch(epochE), X + Y);          // stale!
// borrower defaults in same epoch; manager finalizes recovery
handleBorrowerDefault();

// recoveryPrice was computed with phantom X reserve:
```

Uncertainty note: I verified the stale-mapping behavior and the phantom-reserve path from the code shown (lines 371–393, 644–649, 685–688, 716–723, 842–856). I did not fully confirm the exact CDO call sequence that leaves `pendingInstantWithdraws` partially funded within a single epoch (i.e., whether `collectInstantWithdrawFunds` is invoked per-batch or in full); if the CDO always fully funds instant requests before any claim, the preconditions narrow. The PoC above should be run against the real `IdleCDOEpochVariant` instant-withdraw flow to confirm reachability of partial funding in the default epoch.
