## Title
Unvalidated operator beneficiary in `staking_contract::set_beneficiary_for_operator` permanently DoS's `distribute()`/`switch_operator()`, locking staker funds - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
The external report's bug class is: a single unvalidated recipient parameter causes one entry in a sequentially-processed batch to revert, and because there is no per-item error isolation, the revert blocks the entire batch — permanently DoS-ing all other (legitimate) entries. The Aptos-native analog is in `staking_contract.move`: `distribute_internal()` pays out every shareholder (staker + operator/beneficiary) of a `distribution_pool` in one atomic `while` loop via `aptos_account::deposit_coins`. If the operator's beneficiary address is unregistered for `AptosCoin` **and** has opted out of direct coin transfers, that single deposit aborts, reverting the whole `distribute()` call and permanently blocking the staker's unrelated, legitimate withdrawal — because `set_beneficiary_for_operator()` never validates the new beneficiary can actually receive funds, unlike the analogous `vesting::set_beneficiary()`, which explicitly performs this check for exactly this reason.

### Finding Description
`distribute_internal()` withdraws all inactive/pending_inactive stake and pays every shareholder in the `distribution_pool` in a single loop: [1](#0-0) 

Each payout uses `aptos_account::deposit_coins`, which, for an unregistered recipient, requires `can_receive_direct_coin_transfers(to)`; if the account has opted out (`DirectTransferConfig.allow_arbitrary_coin_transfers = false`) and is not registered for `AptosCoin`, the call aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`: [2](#0-1) 

The operator controls which address receives their commission via `set_beneficiary_for_operator()`, but this function performs **no validation** that the new beneficiary can actually receive coins: [3](#0-2) 

Compare this to `vesting::set_beneficiary()`, which explicitly guards against this exact scenario with a code comment describing the DoS risk: [4](#0-3) 

`staking_contract.move` has no equivalent check for the operator's beneficiary. Because the `distribution_pool`'s two shareholders (staker and operator/beneficiary) are always paid out together in the same atomic loop, poisoning the operator's beneficiary blocks the staker's payout too. Worse, `switch_operator()` — the staker's only path to move away from a malicious/misconfigured operator without a lengthy unstake — unconditionally calls `distribute_internal()` first: [5](#0-4) 

so the staker cannot even switch operators to escape the situation; every call to `distribute()` or `switch_operator()` reverts identically.

### Impact Explanation
This causes a **permanent, non-recoverable lock of the staker's inactive/pending_inactive stake and rewards** — funds that belong to the staker (not the operator) — because the batched payout mechanism ties their release to the operator's beneficiary succeeding first in the same transaction. This matches the "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows" impact category. There is no admin override or alternate withdrawal path in `staking_contract.move` once the `distribution_pool` contains a poisoned recipient; both `distribute()` and `switch_operator()` fail identically.

### Likelihood Explanation
The operator is a role any account can hold (staker chooses/creates the staking contract with an operator address, and the operator unilaterally controls its own beneficiary via `set_beneficiary_for_operator`). Setting `allow_arbitrary_coin_transfers = false` (via `aptos_account::set_allow_direct_coin_transfers`, a standard user-facing config) on an unregistered beneficiary address requires no special privilege and no attacker-controlled precision math — it is simpler than the dust-based exploit in the external report. A rogue or compromised operator can trigger this at will against any staker who has an active `staking_contract` with them.

### Recommendation
In `set_beneficiary_for_operator()`, require that `new_beneficiary` is registered for `AptosCoin` or otherwise capable of receiving direct transfers (mirroring `vesting::set_beneficiary()`'s use of `assert_account_is_registered_for_apt`), before allowing the beneficiary to be set. Additionally, consider making `distribute_internal()` resilient to a single failing payout (e.g., skip/queue a failed recipient's coins rather than aborting the whole distribution), so a malformed beneficiary cannot block payouts to other shareholders.

### Proof of Concept
1. Staker creates a `staking_contract` with `operator` O and stakes 100 APT via `staking_contract::create_staking_contract`.
2. O sets `new_beneficiary = B` via `set_beneficiary_for_operator`, where B is a fresh, never-registered address.
3. O calls `aptos_account::set_allow_direct_coin_transfers(false)` from B's own signer beforehand (or B is any account whose owner opts out) — no permission from staker required, and this can be arranged before O is ever selected as operator.
4. Staker calls `unlock_stake` and waits for lockup to expire, creating inactive stake in the shared `distribution_pool`.
5. Staker (or anyone) calls `staking_contract::distribute(staker, O)`. `distribute_internal` reaches the loop iteration for recipient B, calls `aptos_account::deposit_coins(B, ...)`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. The whole `distribute()` transaction reverts; the staker's inactive stake remains permanently locked in the stake pool with no successful `distribute()` or `switch_operator()` call possible while B remains unregistered/opted-out.

    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;

            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
