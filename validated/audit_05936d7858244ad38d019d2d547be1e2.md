### Title
Unrestricted `replace`/`clean` on `state-manipulation` allow any caller to hijack a foundation migration on the whitelist account - ([File: state-manipulation/src/lib.rs])

### Summary
`state-manipulation/src/lib.rs` exports raw `replace` and `clean` functions with no predecessor/owner/key check whatsoever [1](#0-0) . This contract is meant to be deployed temporarily onto an account (e.g. the `whitelist` account, see `scripts/deploy/deploy_whitelist.sh`) to fix up raw storage during a migration [2](#0-1) ; while it is deployed, any unprivileged account can call `replace` with attacker-chosen base64 keys/values that map onto the real `WhitelistContract` layout (`foundation_account_id`, `LookupSet` prefixes `"w"`/`"f"`) [3](#0-2) , overwriting whatever the operator's own migration call wrote.

### Finding Description
The broken binding: **state_after_migration_tx == operator_intended_state**. `replace`/`clean` should only ever be driven by the account owner performing the migration, but the code contains no `assert_eq!(env::predecessor_account_id(), env::current_account_id())` or any equivalent guard [4](#0-3) . Any caller with a NEAR account can send a transaction invoking `replace` (or `clean`) against the account that currently has this contract deployed, because near-sdk/near-sys expose these as public, unauthenticated `#[no_mangle]` entrypoints — nothing checks who the caller is.

Root cause: the contract's `input()` helper reads raw JSON args and writes/removes storage keys directly via `near_sys::storage_write` / `near_sys::storage_remove`, with zero access control [5](#0-4) . Since transactions to the same account are processed in the order they are included by the network (not truly "raced" in any protocol-guaranteed way, but non-deterministic from the attacker's/operator's perspective within the same block), whichever call is applied last determines the final state. If an attacker submits a `replace` call with keys matching the `whitelist` contract's Borsh layout (`foundation_account_id` field, or the `LookupSet` entries under prefix `"w"` for `whitelist`/`"f"` for `factory_whitelist`) after the operator's own `replace`, the attacker's storage entries win and persist once the contract is redeployed to the proper `whitelist.wasm`.

None of the existing guards in the broader system (`assert_owner`, `assert_called_by_foundation`, multisig confirmation counts, etc.) apply here because `state-manipulation` is a standalone tool contract that bypasses all of that logic — it operates on raw storage below any of the application-level checks in `whitelist/src/lib.rs`.

### Impact Explanation
If the operator (NEAR Foundation) deploys `state-manipulation` onto the `lockup-whitelist.<MASTER_ACCOUNT_ID>` account to perform a live migration and an attacker races a `replace` call in the same window, the attacker can inject a crafted `factory_account_id`/staking-pool entry into the whitelist's `LookupSet`s, or overwrite `foundation_account_id` before the real whitelist contract is redeployed. This would let an attacker whitelist an arbitrary staking pool or factory account, matching the Critical category "an account whitelisted... with parameters its rightful creator never chose," and downstream this can enable lockup contracts to stake with an unauthorized pool, ultimately diverting NEAR that lockups/pools would otherwise pay out only to legitimate parties.

### Likelihood Explanation
This requires: (1) the foundation-owned account currently has `state-manipulation` deployed and reachable by public calls (an operational precondition that only exists during a migration window), and (2) the attacker knows the exact target storage keys of the destination contract (Borsh field layout / `LookupSet` prefixes), which is public since these contracts are open source. The attacker's cost is a single low-gas function call; no deposit or special privilege is needed. This is repeatable every time such a migration window is opened, but it is entirely contingent on the operator's own deployment behavior/timing rather than a flaw reachable purely by an attacker at will against a permanently-deployed contract.

### Recommendation
Add an explicit `assert_eq!(near_sys::predecessor_account_id or equivalent, current_account_id)` check (self-call only) or hard-code an allowed signer/owner check in `replace` and `clean` before performing any storage write/remove, so that only the account itself (i.e., a transaction signed with a full-access key of that account) can invoke these exports. Alternatively, since this is a one-shot migration utility, ensure operational procedure bundles `DeployContract(state-manipulation)`, the `replace` call, and `DeployContract(target-contract)` in a single atomic batched transaction so there is no window where an unauthenticated `replace`/`clean` call is even reachable by a third party.

### Proof of Concept
```rust
// state-manipulation/src/lib.rs (existing tests module, near-workspaces)
#[tokio::test]
async fn race_replace_hijacks_migration() -> anyhow::Result<()> {
    let worker = workspaces::sandbox().await?;
    let contract = worker.dev_deploy(&fs::read("res/state_manipulation.wasm").await?).await?;

    // Operator's legitimate migration write
    let operator = worker.dev_create_account().await?;
    let operator_entries = vec![(base64::encode(b"foundation_account_id"), base64::encode(b"foundation.near"))];

    // Attacker's malicious write targeting same key, submitted after operator's tx
    let attacker = worker.dev_create_account().await?;
    let attacker_entries = vec![(base64::encode(b"foundation_account_id"), base64::encode(b"attacker.near"))];

    operator.call(&worker, contract.id(), "replace")
        .args_json(json!({ "entries": &operator_entries }))?
        .transact().await?;

    attacker.call(&worker, contract.id(), "replace") // succeeds - no owner check
        .args_json(json!({ "entries": &attacker_entries }))?
        .transact().await?;

    let state = contract.view_state(&worker, None).await?;
    // Binding under test: state[foundation_account_id] == operator's value
    // Actual: overwritten by unprivileged attacker
    assert_eq!(state.get(b"foundation_account_id".as_ref()).unwrap(), b"attacker.near");
    Ok(())
}
```
This demonstrates that `replace` accepts calls from any signer (`operator` and `attacker` are both plain dev accounts with no special permission), and whichever call lands last controls final contract state — confirming the missing access-control invariant.

#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    #[derive(serde::Deserialize)]
    struct ReplaceInput<'a> {
        #[serde(borrow)]
        entries: Vec<(&'a str, &'a str)>,
    }

    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(
            &base64::decode(key).unwrap(),
            &base64::decode(value).unwrap(),
        );
    }
}

#[cfg(feature = "clean")]
#[no_mangle]
pub fn clean() {
    #[derive(serde::Deserialize)]
    struct CleanInput<'a> {
        #[serde(borrow)]
        keys: Vec<&'a str>,
    }

    let input = input().unwrap();
    let args: CleanInput = serde_json::from_slice(&input).unwrap();
    for key in args.keys {
        storage_remove(&base64::decode(key).unwrap());
    }
}
