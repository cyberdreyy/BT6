### Title
Node-side double counting of a signer's weight in both `total_weight_approved` and `total_weight_rejected` for the same block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tracks per-block signer support in `BlockStatus` using two independently-gated weight accumulators, `total_weight_approved` and `total_weight_rejected`, plus a single `responded_signers` set that is supposed to prevent a signer's weight from being counted more than once. The gating for the two accumulators is inconsistent: the reject path is gated on `responded_signers`, while the accept path is gated on a *different* set, `gathered_signatures`. If a signer first rejects and later accepts the same block (the same `signer_signature_hash`), its weight is added to `total_weight_rejected` once and then also added to `total_weight_approved`, because the accept-path guard only checks `gathered_signatures`, which is still empty for that signer.

### Finding Description
In `handle` (the message loop), the `Accepted` branch increments `total_weight_approved` when the slot id is not yet in `gathered_signatures`: [1](#0-0) 

and unconditionally records `responded_signers.insert(slot_id)` afterward, regardless of the earlier state of that set.

The `Rejected` branch increments `total_weight_rejected` only when `responded_signers.insert(slot_id)` returns `true` (i.e., first response ever): [2](#0-1) 

Because the accept path is gated on `gathered_signatures` and not on `responded_signers`, a signer that rejects first (adding its weight to `total_weight_rejected` and marking itself in `responded_signers`) and later sends an `Accepted` for the *same* `signer_signature_hash` will still pass the `!gathered_signatures.contains_key(&slot_id)` check and get its weight added to `total_weight_approved` too. The two accumulators are no longer partitioned by signer weight — the same weight unit is now present in both buckets, exactly the "two ratios that should sum to a fixed total but drift apart" pattern from the report, except here the drift goes the other way: the buckets can *both* count the same weight, so `total_weight_approved + total_weight_rejected` can exceed `total_weight`.

The `reset_rejections` helper only clears rejections at proposal retry/timeout, and explicitly documents that approvals are never cleared "because an old approval could always be used to make a block reach the approval threshold": [3](#0-2) 
There is no corresponding logic that removes a signer's earlier-counted rejection weight when that signer subsequently accepts, so the stale, double-counted rejection weight persists in `total_weight_rejected` for the lifetime of the `BlockStatus` entry.

This inflated `total_weight_rejected` is used directly to decide whether the miner should give up waiting on the block: [4](#0-3) 
and `weight_threshold`/`total_weight_approved` values feed `wait_for_block_status` callers used by the node's block-broadcast/coordinator decision logic.

### Impact Explanation
The double-counted weight corrupts the invariant `total_weight_approved + total_weight_rejected <= total_weight` that the "reached enough rejections" liveness check relies on. A single signer flip-flopping (reject then accept the identical block hash — a legitimate signer flow, since signers can re-evaluate and change their vote on an already-seen block when new information arrives, and this reconsideration path exists in `stacks-signer/src/v0/signer.rs`) can artificially inflate `total_weight_rejected`, causing the node to conclude "too many rejections" (`total_weight_rejected + weight_threshold > total_weight`) for a block that in fact still has, or even already reached, sufficient real approving weight. This wedges the miner/coordinator's decision loop into abandoning a block it should keep waiting on/broadcasting, a liveness degradation on the node side of the signing protocol. It does not, on the evidence gathered, produce a Critical-tier outcome (no invalid/non-canonical block gets signed, and the double count inflates rejection tracking rather than fabricating an approval threshold crossing that wasn't backed by real signatures), so this is best classified as a High-severity liveness issue rather than a safety break.

### Likelihood Explanation
Reaching this requires only (a) one signer legitimately switching its vote for the same block hash (a scenario the codebase itself anticipates — note the "we do not change our votes on rejected blocks unless ... the reject reason allows us to reconsider" comment in the pre-commit handler) and (b) the node/coordinator observing both messages via normal StackerDB gossip. No majority of signers, no separate keys, and no code outside the in-scope files are needed. However, I was not able to fully confirm, within the tool budget available, the exact conditions under which `stacks-signer/src/v0/signer.rs` will re-emit an `Accepted` response for a `signer_signature_hash` it previously rejected (as opposed to only ever emitting a fresh rejection/acceptance for genuinely new proposals with new hashes). This is the main open uncertainty in this finding.

### Recommendation
Gate both the accept and reject weight accumulators on the same single-response invariant (e.g., use one `responded_signers` map from slot id to the signer's *current* vote, and when a signer's vote changes, subtract its weight from the old bucket before adding it to the new one), so that `total_weight_approved + total_weight_rejected` can never exceed `total_weight` for a fixed reward set, mirroring the "always recompute from the current, consistent values" fix used in the referenced report.

### Proof of Concept
1. Miner proposes block `B` with hash `H`; `StackerDBListenerComms::insert_block` initializes `BlockStatus` with empty `responded_signers`/`gathered_signatures` and both weights at 0.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for `H`. `responded_signers.insert(slot_S)` succeeds → `total_weight_rejected += w`.
3. `S` later reconsiders and sends `BlockResponse::Accepted` for the same `H` (same `signer_signature_hash`, e.g. after a proposal re-evaluation that changes its verdict without changing the block hash). In the accept branch, `gathered_signatures.contains_key(slot_S)` is `false` (nothing was ever inserted into `gathered_signatures` for `S`), so the code executes `total_weight_approved += w` and then inserts into both `gathered_signatures` and `responded_signers`.
4. Result: `total_weight_approved == w` and `total_weight_rejected == w` simultaneously for the same signer's single weight unit `w`, violating `approved + rejected <= total_weight`, which can trip the "enough rejections" liveness check at [4](#0-3)  using stale/duplicated weight.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
