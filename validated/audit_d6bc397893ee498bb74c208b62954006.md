### Title
`lastWithdrawRequest` tracks only the latest request epoch, letting older receipts escape the loss haircut and be paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The ouroboros bug is a lifetime bug: a self-referencing value is consumed while a reference to it is still in use — the "pointer" outlives/escapes the data it indexes. The credit-vault analog is `lastWithdrawRequest[_user]`, a single pointer to the user's *latest* request epoch that doubles as the index into `lossRecoveryPriceByEpoch`. When `collectWithdrawFunds` records a haircut, it stores one price under the *funding* epoch and clears the whole `pendingWithdraws` aggregate, which can span receipts requested in *earlier* epochs. At claim time, `_claimLossAdjustedWithdrawRequest` clears only the `lastWithdrawRequest` epoch and resets the pointer to `0`, after which `_claimFundedWithdrawRequest` pays the older-epoch remainder at par even though the borrower only funded `pendingBasis * lossRecoveryPrice`. The excess is paid out of strategy underlyings backing other users.

### Finding Description
- `requestWithdraw` accumulates `withdrawsRequestsByEpoch[_user][currentEpoch]` across epochs and always overwrites `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:282-293`). The guard at lines 263-271 only blocks a new request when the *last* epoch already has a `lossRecoveryPriceByEpoch` entry — an earlier-epoch receipt with no loss entry does not block.
- On a lossy `stopEpochWithDuration`, `IdleCDOEpochVariant.stopEpoch` calls `previewLossAdjustedWithdrawFunds` and then `collectWithdrawFunds(_pendingWithdraws)` (`IdleCDOEpochVariant.sol:393-410`). When `_amount < pendingBasis`, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` and sets `pendingWithdraws = 0` (`IdleCreditVault.sol:413-421`) — the haircut applies to the aggregate but is indexed by a single epoch.
- In `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` plus that epoch's APR0 data (`IdleCreditVault.sol:789-794`, `811-837`). Because the cleared epoch equals `lastWithdrawRequest`, line 832-835 resets `lastWithdrawRequest[_user] = 0`.
- `_claimFundedWithdrawRequest` then runs: the epoch gate `epochNumber <= lastWithdrawRequest[_user]` passes trivially (pointer is 0 and `epochNumber` has advanced past the loss epoch), so it pays `withdrawsRequests[_user]` — which still contains the earlier-epoch receipt — **at par** (`IdleCreditVault.sol:326-349`). That receipt's share of the loss was already socialized into the funded amount.

Broken invariant: one receipt one payout / loss waterfall. Total funded = `(A + B) * p`, total paid = `B * p + A`. Excess taken = `A * (1 - p)`.

### Impact Explanation
An unprivileged lender (any KYC-passing tranche holder) who simply makes two withdraw requests in consecutive epochs and lets a manager-run `stopEpochWithDuration(_lossAmount)` haircut land on the later epoch drains `A * (1 - lossRecoveryPrice)` more than was funded. With a 50% haircut and a large earlier request, the attacker receives up to ~50% of that earlier principal on top of the haircut pool. The deficit is borne by the strategy's remaining underlyings: either later claimants' funded receipts revert (temporary freezing / insolvency of the claim reserve) or the strategy NAV is directly diluted — direct theft with fund impact, not a DoS.

### Likelihood Explanation
Requires: (a) attacker holds receipts in ≥2 distinct epochs at the moment of a loss stop (fully user-controlled — just don't claim between epochs, which is explicitly supported: "he will have to wait for another epoch to claim both requests"), and (b) an honest `stopEpochWithDuration` with `_lossAmount > 0` small enough that `previewLossAdjustedWithdrawFunds` doesn't revert (`_lossAmount < activeBasis + pendingBasis`, and `lossRecoveryPrice` must not round to 0). No privileged misbehavior is needed; borrower/manager act honestly and the loss may be organic or induced by ordinary borrower underperformance. Existing guards do not stop it: the `requestWithdraw` re-request guard only checks `lastWithdrawRequest`'s epoch, `_transferFundedClaim`'s reserve guard only protects `defaultRecoveryReserve`, and `pendingWithdraws` was already zeroed so nothing re-checks the funded amount.

### Recommendation
Attribute the loss haircut to every epoch contributing to `pendingBasis`, not only `epochNumber`. Concretely: when `collectWithdrawFunds` records a loss, iterate or otherwise mark all request epochs present in `pendingWithdraws` (e.g., store a global `pendingLossPrice` consumed FIFO, or a per-user mapping of haircut epochs), and make `_claimFundedWithdrawRequest` revert while any unclaimed loss-adjusted receipt remains rather than relying on `lastWithdrawRequest`. Alternatively, keep per-epoch pending basis (`pendingWithdrawsByEpoch`) so `collectWithdrawFunds` can price each contributing epoch and `_clearWithdrawClaimForEpoch` can clear them all.

### Proof of Concept
Foundry fork PoC sketch (harvest/fork environment per `test/foundry/IdleCreditVault.t.sol` patterns):

```solidity
// Attacker deposits into AA, epoch 1 runs and stops normally.
// During buffer of epoch 2: request withdraw #1  -> lastWithdrawRequest = 2, basis A
cdoEpoch.requestWithdraw(0, address(AAtranche)); // amount A

// epoch 2 starts and stops normally (no loss), epochNumber -> 3.
// During buffer of epoch 3: request withdraw #2 -> lastWithdrawRequest = 3, basis B
cdoEpoch.requestWithdraw(0, address(AAtranche)); // amount B

// epoch 3 runs; at stopEpoch borrower shortfall -> stopEpochWithDuration with _lossAmount.
// collectWithdrawFunds receives (A+B)*p and stores lossRecoveryPriceByEpoch[3] = p (<1e18).
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(newApr, newDuration, lossAmount);

// Attacker claims once:
uint256 balBefore = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(attacker) - balBefore;

// paid == B*p + A  (funded at par) instead of (A+B)*p
assertGt(paid, (A + B) * p / 1e18);          // overpay = A * (1 - p)
// Strategy now holds less than the sum of remaining funded claims.
```

Uncertainty I could not fully resolve within the iteration budget: the exact lines where `epochNumber` is incremented relative to `collectWithdrawFunds` inside `stopEpoch`/`deposit` (`IdleCreditVault.sol:607-610` bumps on deposits made while `isEpochRunning`, and `IdleCDOEpochVariant.sol:410` collects before the `deposit` at line 466 — consistent with the loss landing under the request epoch as assumed). The core flaw — `lastWithdrawRequest` being a single-epoch pointer while `pendingWithdraws`/the haircut span multiple epochs — holds regardless of the precise epoch index used, because the par-payment of the leftover `withdrawsRequests` remainder is unconditional once the pointer is cleared.
