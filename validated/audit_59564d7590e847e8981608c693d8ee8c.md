### Title
Loss-epoch withdraw receipts escape the haircut when a second request overwrites `lastWithdrawRequest`, letting an attacker claim at par and drain funded reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` applies a realized `stopEpoch` loss to pending withdraw receipts through `lossRecoveryPriceByEpoch`, but the loss-adjusted claim path is keyed only to `lastWithdrawRequest[_user]` — the user's most recent request epoch. An unprivileged lender who holds a receipt from the loss epoch can submit a second `requestWithdraw` in a later epoch, overwriting `lastWithdrawRequest`. The loss-adjusted path then returns 0, and `_claimFundedWithdrawRequest` pays the entire aggregate `withdrawsRequests[_user]` — including the haircutted epoch's receipt — at par. This is a stale-reference/use-after-free analog: the per-epoch ledger entry (`withdrawsRequestsByEpoch[user][lossEpoch]`) still exists, but the only pointer to the loss-epoch attribution (`lastWithdrawRequest`) has been overwritten, so the haircut is never applied.

### Finding Description
- `requestWithdraw` records receipts per-epoch via `withdrawsRequestsByEpoch[_user][currentEpoch]` and unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` (lines 282, 292–293).
- When the borrower underfunds pending receipts, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` and zeros `pendingWithdraws` — the strategy only receives the reduced `_amount` (lines 411–430).
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 789–801). It only looks at the *latest* request epoch. There is no scan or flag tying `withdrawsRequestsByEpoch` entries with nonzero `lossRecoveryPriceByEpoch` to the claim.
- `_clearWithdrawClaimForEpoch` clears only the epoch passed in, and `_claimFundedWithdrawRequest` then burns `withdrawsRequests[_user]` (which still includes the loss-epoch amount) and pays it 1:1 via `_transferFundedClaim` (lines 319–349, 811–837).
- The code's own NOTE (lines 323–324) confirms a user may request again without claiming: "if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests." So the overwrite is a normal, permitted action — no privileged role needed.

Broken invariant: the loss waterfall / fair burn. Receipts from a loss epoch must be paid at `claimBasis * lossRecoveryPrice / RECOVERY_FULL`, but they are paid at `RECOVERY_FULL`. Since `collectWithdrawFunds` only pulled the reduced amount from the CDO, paying one claimant at par leaves the strategy short for the remaining loss-epoch claimants — direct theft of their haircut share, up to insolvency of the funded-claim reserve.

### Impact Explanation
An attacker holding a loss-epoch receipt claims the un-haircutted principal. If the loss was L% and attacker basis is A, they extract `A * L%` more than entitled, paid from funds reserved for other claimants. Other loss-epoch claimants are permanently underpaid or their claims revert on insufficient balance (`_transferFundedClaim` guard at lines 897–906) — permanent loss/freezing of unclaimed yield proportional to the attacker's share of `pendingBasis`.

### Likelihood Explanation
Requires only: (1) attacker is a KYC-passed lender/tranche holder with a pending withdraw request in the epoch where `stopEpochWithDuration(_lossAmount)`/`collectWithdrawFunds` records a nonzero `lossRecoveryPriceByEpoch`; (2) attacker calls `requestWithdraw` again in a subsequent epoch (small dust amount suffices to overwrite `lastWithdrawRequest`); (3) after one more epoch boundary, calls `claimWithdrawRequest`. All steps are ordinary user actions; no honest-party misbehavior needed. The prefunded/apr0 variants do not change the keyed lookup.

### Recommendation
Attribute the loss haircut per epoch rather than via `lastWithdrawRequest`. In `_claimFundedWithdrawRequest` (or a pre-pass over claimable epochs), iterate or track the set of epochs in `withdrawsRequestsByEpoch[_user]` with nonzero `lossRecoveryPriceByEpoch` and pay those at the haircut, only paying the remainder at par. Alternatively, revert in `requestWithdraw` when the user has an uncleared receipt in an epoch with `lossRecoveryPriceByEpoch != 0`, or store a per-user list of loss epochs so overwritten `lastWithdrawRequest` cannot orphan a haircutted receipt.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossEpochReceiptEscapesHaircut() external {
    // epoch N: attacker deposits, requests withdraw of trancheAmount
    uint256 trancheAmount = ONE_TRANCHE;
    _requestWithdrawWithUser(attacker, trancheAmount); // records withdrawsRequestsByEpoch[attacker][N]

    // honest borrower partially funds: stopEpochWithDuration(_lossAmount) path
    // collectWithdrawFunds(_amount < pendingBasis) -> lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL
    _stopCurrentEpochWithLoss(lossAmount);

    // epoch N+1: attacker requests a dust withdraw, overwriting lastWithdrawRequest
    _requestWithdrawWithUser(attacker, dust);

    // stop epoch N+1 fully funded; epochNumber advances past lastWithdrawRequest
    _stopCurrentEpoch();

    // attacker claims: _claimLossAdjustedWithdrawRequest keys on lastWithdrawRequest = N+1,
    // lossRecoveryPriceByEpoch[N+1] == 0 -> returns 0; funded path pays
    // withdrawsRequests[attacker] (includes the N-epoch amount) at par.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    uint256 paid = underlying.balanceOf(attacker) - balPre;
    uint256 entitled = trancheAmount * strategy.lossRecoveryPriceByEpoch(lossEpoch) / RECOVERY_FULL + dust;
    assertGt(paid, entitled); // haircut escaped; reserve drained at others' expense
}
```

Uncertainty note: I was unable to fully verify (within iteration limits) whether `stopEpoch`/`collectWithdrawFunds` increments `epochNumber` before storing `lossRecoveryPriceByEpoch`, and whether an additional guard elsewhere blocks re-requesting with a pending loss-epoch receipt. If `lossRecoveryPriceByEpoch` is keyed to the post-increment epoch while `lastWithdrawRequest` stores the request epoch, the mismatch may even make the loss-adjusted path unreachable in some configurations — which would strengthen rather than weaken this finding, but the exact epoch key alignment should be confirmed against `IdleCDOEpochVariant.stopEpoch`.
