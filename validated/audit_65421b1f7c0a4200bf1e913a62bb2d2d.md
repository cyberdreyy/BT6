### Title
Loss haircut from `stopEpochWithDuration` is only applied to the user's latest request epoch — older pending receipts still claim at par, breaking the funded-recovery invariant - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.collectWithdrawFunds` applies a `stopEpochWithDuration` loss to the *aggregate* `pendingWithdraws` bucket, which can contain a user's receipts from multiple request epochs. However, `_claimLossAdjustedWithdrawRequest` resolves the haircut only through the single-epoch index `lastWithdrawRequest[_user]`. Receipts recorded under earlier epochs in `withdrawsRequestsByEpoch` fall through to `_claimFundedWithdrawRequest`, which pays the remaining aggregate `withdrawsRequests[_user]` at par. An early claimer therefore withdraws more than the haircut-funded amount, leaving the strategy undercollateralized for every other pending receipt holder.

### Finding Description
- `requestWithdraw` adds every request to the global `pendingWithdraws` and to `withdrawsRequestsByEpoch[_user][currentEpoch]`, and updates `lastWithdrawRequest[_user] = currentEpoch`. Multiple unclaimed requests across epochs are explicitly supported (see the NOTE in `_claimFundedWithdrawRequest`).
- When a loss is realized, `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` over the whole pending bucket and stores it under `lossRecoveryPriceByEpoch[epochNumber]` (the current epoch only).
- On claim, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and `_clearWithdrawClaimForEpoch` clears *only* that epoch's slice. Any older-epoch slices remain in `withdrawsRequests[_user]` and are paid 1:1 by `_claimFundedWithdrawRequest` via `_transferFundedClaim`.
- The guard in `requestWithdraw` (lines 263–271) only blocks a *new* request when the user's *last* epoch already has a nonzero `lossRecoveryPrice`; it does nothing for receipts pending in *earlier* epochs when the loss epoch is a later one.

This mirrors CVE-2017-11334's class: a single cached index (`lastWithdrawRequest`) is used to look up a per-epoch haircut (`lossRecoveryPriceByEpoch`) while the underlying debt spans multiple epochs — i.e., the lookup dereferences the wrong "range" of the receipt set, exactly like `qemu_map_ram_ptr` returning a pointer outside the intended RAM block.

### Impact Explanation
Direct theft / insolvency. Example: user deposits, requests withdraw of 100 in epoch N buffer and another 100 in epoch N+1 buffer (no claim in between). `stopEpochWithDuration` realizes a 50% loss on the 200 pending basis → only 100 is funded. The user claims: 50 via the loss-adjusted path (epoch N+1 slice) plus 100 at par via the funded path (epoch N slice) = 150 against a funded pool of 100. The extra 50 is paid out of funds reserved for other users' pending receipts (or the claim of the last receipt holder reverts), i.e., theft of unclaimed yield / permanent freezing of the residual claims.

### Likelihood Explanation
Requires (1) a user with pending receipts in ≥2 distinct request epochs — normal usage, no claim obligation between requests; (2) the honest manager calling `stopEpochWithDuration` with `_lossAmount > 0` (partial borrower repayment), a designed code path. First claimer after the loss deterministically overdraws; ordering favors whoever claims first.

### Recommendation
Track per-epoch loss adjustment independently of `lastWithdrawRequest`: either iterate all epochs with nonzero `withdrawsRequestsByEpoch[_user][e]` having `lossRecoveryPriceByEpoch[e] != 0`, or store a per-user bitmap/list of loss epochs. Alternatively, when a loss is applied, pro-rate and rewrite each user's pending entries so the aggregate `withdrawsRequests` itself is haircut, making `_claimFundedWithdrawRequest` safe. At minimum, `requestWithdraw` should reject a new request if the user has *any* pending receipt older than the current epoch, not only when the last epoch's recovery price is set.

### Proof of Concept
```solidity
// Foundry fork PoC sketch against test/foundry/IdleCreditVault.t.sol harness
function testLossHaircutOnlyAppliesToLastEpoch() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    idleCDO.depositBB(amount);

    // Epoch 0 runs and stops cleanly
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Buffer of epoch 1: request half of AA
    uint256 req1 = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 4, address(AAtranche));

    // Epoch 1 runs and stops cleanly
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Buffer of epoch 2: request again WITHOUT claiming -> lastWithdrawRequest = 2
    uint256 req2 = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 3, address(AAtranche));

    // Epoch 2 runs; manager stops with a realized loss haircutting the aggregate pending bucket
    _startEpochAndCheckPrices(2);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws(); // req1 + req2
    uint256 loss = pending / 2;
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() + pending - loss);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, 3 days, loss);

    // Claim: epoch-2 slice pays req2 * 50%, epoch-1 slice pays req1 at PAR
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 claimed = underlying.balanceOf(address(this)) - balPre;

    // Funded amount was (req1 + req2) * 50%; user extracts req1 + req2/2
    assertEq(claimed, req1 + req2 / 2);
    assertGt(claimed, pending - loss); // overdrawn vs what was actually funded
}
```
Expected: `claimed` exceeds the haircut-funded amount held by the strategy; subsequent claimers' `_transferFundedClaim` reverts on insufficient underlying or draws down funds meant for them.
