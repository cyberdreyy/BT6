### Title
Windows job object allows `CREATE_BREAKAWAY_FROM_JOB` escape, letting cancelled job processes survive `ForceKill` - (File: helpers/process/job_windows.go)

### Summary
`CreateJobObject` in `helpers/process/job_windows.go` explicitly sets `JOB_OBJECT_LIMIT_BREAKAWAY_OK` alongside `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, and the source comment states this is intended "to allow subprocesses to explicitly avoid termination using `CREATE_BREAKAWAY_FROM_JOB`." Because breakaway is permitted, any child process spawned from the job script with the `CREATE_BREAKAWAY_FROM_JOB` creation flag is never assigned to the job object, so it survives `windowsKiller.ForceKill`'s call to `pk.cmd.closeJobObject()`, which relies solely on `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` to terminate the tree.

### Finding Description
`CreateJobObject` (helpers/process/job_windows.go:86-108) configures the job object's `LimitFlags` as: [1](#0-0) 
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` is the mechanism that is supposed to guarantee the whole process tree dies when the job handle is closed, but `JOB_OBJECT_LIMIT_BREAKAWAY_OK` is a documented Windows API opt-in that permits a process running inside the job to call `CreateProcess`/`CreateProcessAsUser` with the `CREATE_BREAKAWAY_FROM_JOB` flag, which creates the new process completely outside of the job (it is never a member and is unaffected by the job's kill-on-close semantics).

The job script executed by the shell/custom executor runs as a normal child under this job object (assigned via `AssignPidToJobObject`, helpers/process/job_windows.go:120-128, called from `osCmd.Start`, lines 25-48). Because the job explicitly opts into breakaway, any code the job script executes — a compiled helper binary, a PowerShell script using P/Invoke to call `CreateProcess`, etc. — can request `CREATE_BREAKAWAY_FROM_JOB` and spawn a detached child.

On cancellation, `windowsKiller.ForceKill` (helpers/process/killer_windows.go:44-55) calls `taskKill` on the direct child PID and then `pk.cmd.closeJobObject()`: [2](#0-1) 
`closeJobObject` (helpers/process/job_windows.go:67-74) only closes the job handle, relying on `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` to kill members — but the breakaway child was never a member, so it is unaffected and keeps running. There is no other mechanism (e.g., recursive process-tree enumeration/kill, or omitting `JOB_OBJECT_LIMIT_BREAKAWAY_OK`) that would catch it.

This path is only reachable when the `FF_USE_WINDOWS_JOB_OBJECT` feature flag is enabled (default `false`, per `helpers/featureflags/flags.go:350-357` and the flags documentation), since `options.UseWindowsJobObject` gates whether the job object is created/used at all in `osCmd.Start`.

### Impact Explanation
When the operator has enabled `FF_USE_WINDOWS_JOB_OBJECT` (a flag documented as improving termination robustness), an unprivileged job script can defeat that very improvement: a process it spawns with `CREATE_BREAKAWAY_FROM_JOB` survives job cancellation/`ForceKill` and continues running on the shared Windows runner host as an orphan after the job is reported terminated, violating the invariant that job cancellation kills the full process tree. This matches the scoped impact exactly (orphaned process persisting past cancellation on a shared host).

### Likelihood Explanation
Preconditions: (1) the runner is configured with the `shell` or `custom` executor on Windows, and (2) `FF_USE_WINDOWS_JOB_OBJECT` is enabled. Given these, the attack requires only ordinary job-script capability to run a small compiled program or a PowerShell script that P/Invokes `CreateProcessW` with `CREATE_BREAKAWAY_FROM_JOB` — no elevated privileges are needed, since `JOB_OBJECT_LIMIT_BREAKAWAY_OK` is a per-job-object policy set by the runner itself, not an OS-level restriction the job would need to bypass. This is deterministic and repeatable.

### Recommendation
Do not set `JOB_OBJECT_LIMIT_BREAKAWAY_OK` when creating the job object in `CreateJobObject` (helpers/process/job_windows.go), so that `CREATE_BREAKAWAY_FROM_JOB` requests fail for job-script children, ensuring `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` remains an enforceable guarantee. If breakaway is required for some internal use case, scope it narrowly (e.g., only for trusted helper invocations) rather than applying it to the job object that wraps arbitrary user job scripts.

### Proof of Concept
Windows integration test in `helpers/process`:
1. Build a tiny helper binary (or use `rundll32`/a Go test helper) that, when invoked, calls `CreateProcessW` with `CREATE_BREAKAWAY_FROM_JOB` to launch a long-sleeping child (e.g., `ping -t localhost` or a sleep loop), then exits itself.
2. Start an `osCmd` with `CommandOptions.UseWindowsJobObject = true` whose script invokes that helper.
3. After the helper reports the breakaway child's PID (e.g., via a temp file), call `windowsKiller{...}.ForceKill()`.
4. Assert: `cmd.Wait()` returns, the direct child process is gone, but `os.FindProcess(breakawayChildPid)` / `OpenProcess` on that PID still succeeds and the process is running — proving it escaped termination. Clean up by killing it manually at test teardown.

func (pk *windowsKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := taskKill(pk.cmd.Process().Pid)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}

	pk.cmd.closeJobObject()
}
