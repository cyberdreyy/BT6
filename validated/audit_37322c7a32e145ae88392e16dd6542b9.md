### Title
Unbounded live-read of `order_execution_max_fee` lets keepers extract more equity from pending limit orders after an admin fee change - ([File: programs/marginfi/src/instructions/marginfi_account/order.rs])

### Summary
`MarginfiAccountPlaceOrder` lets a user create a stop-loss/take-profit `Order` that stores only `stop_loss`, `take_profit`, and `max_slippage` at placement time [1](#0-0) . The fee that bounds how much of the user's equity a keeper may take on execution, `fee_state.order_execution_max_fee`, is **not captured on the order** — it is read live from the global `FeeState` singleton at `end_execute_order` time [2](#0-1) . This is directly analogous to the reported `AaveStrategy.redeem` issue: a mutable, admin-controlled parameter is applied at execution time rather than being locked in (or bounded by a user-supplied minimum) at request time, so a legitimate, permissionless-timed parameter change between "order placed" and "order executed" changes the economic outcome the user actually receives, with no way for the user to protect themselves against it.

### Finding Description
When a user places a take-profit or "Both" order, they set `max_slippage` (a percentage of the tp/sl threshold) but have no control over, and no visibility baked into the order account for, `order_execution_max_fee` [3](#0-2) . That fee is a `FeeState` global stored in a singleton account and can be updated at any time by the `global_fee_admin` via `edit_fee_state` [4](#0-3) .

At order execution, `end_execute_order` computes the maximum amount of the user's health/equity a keeper is allowed to extract using this live value:
```
let max_fee_frac = {
    let max_fee: I80F48 = fee_state.order_execution_max_fee.into();
    I80F48::ONE.checked_sub(max_fee).ok_or_else(math_error!())?
};
...
let allowed_diff = (start_health)().checked_mul(max_fee_frac)...;
check!(net >= allowed_diff && net >= allowed_tp, MarginfiError::OrderExecutionOverWithdrawal);
``` [5](#0-4) 

If `order_execution_max_fee` is increased by the global fee admin after a user has placed an order but before a keeper executes it, `max_fee_frac` decreases, `allowed_diff` decreases, and the check that limits how much of `start_health` the keeper can consume becomes strictly more permissive. Since the keeper chooses the withdraw/repay amounts during `start_execute_order`/`end_execute_order` (a permissionless keeper flow) [6](#0-5) , a keeper racing (or simply executing after) an `edit_fee_state` transaction can legally take a larger cut of the user's equity than what was possible — and implicitly assumed by the user — when the order was placed, with only `max_slippage` (a separate, unrelated bound) protecting the user's floor payout.

This mirrors the AaveStrategy report precisely: the redeem-analog action (`end_execute_order`) has a user-set slippage/minimum-output-like guard (`max_slippage`), but a second, independent fee parameter (`order_execution_max_fee`, analogous to `redeemFeeBps`) is read live and can change between order placement and settlement, and there is no user-supplied minimum guard against that specific parameter.

### Impact Explanation
An unprivileged order-placing user can receive materially less residual equity than expected on take-profit/"Both" order execution if `order_execution_max_fee` is raised between order placement and keeper execution, because the fee-based floor (`allowed_diff`) shrinks and permits a larger, permissionless keeper-driven extraction from the user's account. This is a genuine value-redirection from an unprivileged user to an unprivileged (or at best semi-trusted) keeper, mediated by a parameter the user cannot see or bound at order-placement time.

### Likelihood Explanation
Requires: (1) a take-profit/Both order in flight, and (2) an `edit_fee_state` call raising `order_execution_max_fee` before execution. `edit_fee_state` is expected/normal governance-style maintenance and not rate-limited or timelocked in the code reviewed, and keepers are economically incentivized to maximize their extracted fee, so they would naturally execute right after (or race) such a change. Likelihood is comparable to the original report's "Low" classification — it depends on a coincident admin fee change, but the mechanism is real, reachable, and requires no privileged access.

### Recommendation
Snapshot `order_execution_max_fee` (or an equivalent user-visible maximum-fee bound) into the `Order` account at placement time (similar to how `max_slippage` is already stored), and use that stored value in `end_execute_order` rather than re-reading the live `FeeState`. Alternatively, allow the user to specify their own acceptable max-fee cap at `PlaceOrder` time and enforce `min(order.max_fee, fee_state.order_execution_max_fee)` at execution.

### Proof of Concept
1. User places a `TakeProfit` order via `MarginfiAccountPlaceOrder` with `max_slippage` set, while `fee_state.order_execution_max_fee` is at its initial value (e.g. low, per `init_global_fee_state`).
2. Global fee admin calls `edit_fee_state` raising `order_execution_max_fee` to a higher value [4](#0-3) .
3. Trigger condition for the order becomes true (oracle price reaches take-profit threshold).
4. A keeper calls `start_execute_order` → performs withdraw/repay instructions sized to maximize their extraction → `end_execute_order`. Because `allowed_diff = start_health * (1 - new_higher_max_fee)` is now lower, the `check!(net >= allowed_diff && net >= allowed_tp, ...)` passes even though the keeper took a larger cut of `start_health` than would have been allowed under the fee in effect when the order was placed [7](#0-6) .
5. User's residual equity after order execution is lower than what they would have received had the fee at placement time been enforced — with no recourse, since the order account never recorded the fee assumption.

// Note: repay_all will be applied to the `liab_bank`
async fn execute_order_with_withdraw(
    test_f: &TestFixture,
    borrower: &MarginfiAccountFixture,
    order_pda: Pubkey,
    keeper: &Keypair,
    liab_bank: &BankFixture,
    liab_account: Pubkey,
    asset_bank: &BankFixture,
    asset_account: Pubkey,
    withdraw_amount: f64,
    withdraw_all: Option<bool>,
    exclude_banks: Vec<Pubkey>,
) -> Result<(), solana_program_test::BanksClientError> {
    let (start_ix, execute_record) = borrower
        .make_start_execute_ix(order_pda, keeper.pubkey())
        .await;

    let withdraw_ix = borrower
        .make_withdraw_ix_with_authority(
            asset_account,
            asset_bank,
            withdraw_amount,
            withdraw_all,
            keeper.pubkey(),
        )
        .await;

    let repay_ix = borrower
        .make_repay_ix_with_authority(liab_account, liab_bank, 0.0, Some(true), keeper.pubkey())
        .await;

    let end_ix = borrower
        .make_end_execute_ix(
            order_pda,
            execute_record,
            keeper.pubkey(),
            keeper.pubkey(),
            exclude_banks,
        )
        .await;

    test_f.refresh_blockhash().await;
    let ctx = test_f.context.borrow_mut();
    let tx = Transaction::new_signed_with_payer(
        &[start_ix, withdraw_ix, repay_ix, end_ix],
        Some(&keeper.pubkey()),
        &[keeper],
        ctx.banks_client.get_latest_blockhash().await.unwrap(),
    );

    ctx.banks_client.process_transaction(tx).await
}
