### Title
Stale per-epoch instant-withdraw basis is never cleared on funded claims, inflating default recovery and draining the reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Like the vc4 binner slot that is recycled without clearing its tile state array, `IdleCreditVault` recycles per-epoch instant-withdraw bookkeeping across the claim lifecycle without zeroing it. The funded claim path in `claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and the global `instantWithdrawClaimsByEpoch[epoch]` untouched. If a default is later finalized in that same epoch, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` read the stale, already-paid basis, inflating `defaultRecoveryPrice` and the phantom "already-held" reserve, so recovery claimants are overpaid until the real reserve is exhausted.

### Finding Description
- `requestInstantWithdraw` records basis per request epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (lines 367–374).
- The normal funded claim path `claimInstantWithdrawRequest` only does `instantWithdrawsRequests[_user] = 0` (lines 387–392). Neither per-epoch mapping is decremented.
- The only place `instantWithdrawClaimsByEpoch` is reduced is `_claimDefaultedInstantWithdrawRequest` (line 853), and only for `defaultRecoveryEpoch`.
- On finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (lines 644–649), and `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` as reserve already held by the strategy (lines 716–723). A stale claimed amount in `instantWithdrawClaimsByEpoch[epochNumber]` is therefore counted twice: once as claim basis and once as prefunded reserve.

Attack sequence (attacker = ordinary KYC'd lender; all privileged roles honest):
1. Epoch N running. Attacker calls `requestInstantWithdraw(A)` via the CDO. `instantWithdrawClaimsByEpoch[N] = A`.
2. After `instantWithdrawDelay`, manager calls `getInstantWithdrawFunds`; `collectInstantWithdrawFunds` funds A and decrements `pendingInstantWithdraws`. Attacker calls `claimInstantWithdrawRequest` and is paid A at par. `instantWithdrawsRequestsByEpoch[attacker][N]` and `instantWithdrawClaimsByEpoch[N]` still hold A — stale state, exactly like the unzeroed TSDA.
3. Still epoch N (epochNumber only bumps at `stopEpoch`), any user makes a new instant request B that stays unfunded, or normal `pendingWithdraws` exist.
4. Epoch N ends with borrower default; owner calls `finalizeDefault`. `defaultPendingClaimBasis` = `pendingWithdraws + instantWithdrawClaimsByEpoch[N]` includes stale A. `_defaultPrefundedInstantReserve` = `(A + B) - pendingInstant` treats already-paid-out A as held reserve, so `reserveAmount` and `defaultRecoveryPrice` are computed against basis that has no backing.
5. Recovery claimants (including the attacker via a fresh request) draw from `defaultRecoveryReserve` at an inflated price; the reserve is exhausted before later claimants are paid.

### Impact Explanation
Direct theft/insolvency of the isolated default recovery reserve: `defaultRecoveryPrice` is scaled up by the ratio of stale claimed basis, so early claimants receive more underlying than their pro-rata share and `defaultRecoveryReserve` is drained (`_transferDefaultRecovery` line 915), leaving later defaulted-epoch and post-default claimants with reverts or zero payout. Broken invariant: one receipt one payout — the same instant receipt is paid once at par and then counted again as recovery basis. Quantified loss: up to the full stale claimed amount A per affected epoch.

### Likelihood Explanation
Requires: (a) a funded instant withdrawal claimed while `epochNumber == N`, (b) any unfunded instant or normal pending receipt in epoch N, and (c) an honest borrower default finalized in epoch N. Instant claims during a live epoch are a supported flow (`instantWithdrawDelay`, `getInstantWithdrawFunds`). No attacker privileges needed. The existing guards do not stop it: the `epochNumber <= lastWithdrawRequest` gate only covers normal requests, `_hasWithdrawRequest` reads only aggregate fields, and nothing validates that `instantWithdrawClaimsByEpoch` reflects unclaimed receipts.

### Recommendation
In the funded path of `claimInstantWithdrawRequest`, iterate or track the user's open request epochs (e.g. `lastInstantRequestEpoch`) and decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amounts, mirroring `_clearWithdrawClaimForEpoch`. Alternatively store each instant request under its epoch and clear it on claim so stale per-epoch basis can never survive into default accounting.

```solidity
// stale: instantWithdrawClaimsByEpoch[N] still == A

// 2. second unfunded instant request in same epoch N

//    defaultPendingClaimBasis() includes stale A;

//         claiming drains reserve early; last claimant reverts on safeTransfer
```

Uncertainty: I could not fully verify the CDO-side `getInstantWithdrawFunds`/`stopEpoch` sequencing in this iteration budget, but the missing per-epoch clearing in `claimInstantWithdrawRequest` (lines 387–392) versus the basis consumers (lines 647, 716–723) is confirmed in the strategy code.
