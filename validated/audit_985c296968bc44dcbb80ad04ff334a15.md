### Title
Already-claimed instant-withdraw receipts are replayed into default-recovery accounting, inflating the recovery price and draining the reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out a funded instant-withdraw receipt but never clears the per-epoch bookkeeping (`instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`). If the borrower defaults in the same epoch while any *other* instant request is still unfunded, `finalizeDefaultRecovery` counts the already-paid receipt again — both as claim basis and as "prefunded reserve" — which inflates `defaultRecoveryPrice` above what actual held funds support. Early claimants are overpaid and the reserve is exhausted, leaving later claimants (including the still-pending instant withdrawer and defaulted normal-withdraw users) permanently unpaid.

### Finding Description
The external report describes replay of stale, already-consumed requests because no nonce/consume marker invalidates them. The analog here is that a consumed instant-withdraw receipt is never invalidated in per-epoch state, so it is silently replayed into a later recovery computation.

In `requestInstantWithdraw`, the receipt is recorded both per-user and per-epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` [1](#0-0) .

When the borrower transfers instant-withdraw liquidity, `collectInstantWithdrawFunds` decreases only `pendingInstantWithdraws`; the per-epoch claim totals are untouched [2](#0-1) .

`claimInstantWithdrawRequest` then burns `instantWithdrawsRequests[_user]`, zeroes the aggregate, and transfers underlying — but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` nonzero forever [3](#0-2) . Compare with the normal-withdraw path, where `_clearWithdrawClaimForEpoch` zeroes `withdrawsRequestsByEpoch` before paying [4](#0-3) , and with the defaulted-instant path, which does clear `instantWithdrawsRequestsByEpoch` [5](#0-4) . The funded-claim path is the only one that skips per-epoch cleanup.

On default, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` (including the replayed, already-paid receipt) to the claim basis whenever `pendingInstantWithdraws != 0` [6](#0-5) . Then `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant`, treating the already-paid-out amount as underlying still held by the strategy, and adds it to `reserveAmount` [7](#0-6) . Both numerator and denominator shift, but the numerator grows by phantom funds: `recoveryPrice = reserveAmount * 1e18 / totalBasis` is computed as if the paid-out tokens were still in the contract [8](#0-7) . The CDO then pays claims at this inflated price via `_transferDefaultRecovery`, draining real reserve until it is empty.

### Impact Explanation
Direct theft / insolvency with quantified loss. The phantom reserve equals the amount of any instant-withdraw receipts funded and claimed earlier in the default epoch. The inflated `defaultRecoveryPrice` overpays whoever claims first (post-default requesters and defaulted-epoch receipt holders, callable by anyone through `claimWithdrawRequest`), while the actual `underlyingToken` balance is smaller by exactly the paid-out amount. Late claimants' transfers revert on insufficient balance or the price exceeds 1:1 backing — their recovery is permanently lost up to the full replayed amount.

### Likelihood Explanation
Requires a specific sequence within one epoch: (1) an instant-withdraw request is funded via `collectInstantWithdrawFunds` and claimed; (2) another instant or normal withdraw request remains unfunded (`pendingInstantWithdraws != 0`); (3) the borrower defaults and recovery is finalized in the same epoch. All steps use only unprivileged user actions plus honest borrower/manager calls; no attacker privilege is needed, and an attacker can deliberately open the unfunded request to set the precondition before a distressed borrower defaults. No existing guard stops it: `_onlyIdleCDO`, `defaultRecoveryFinalized` checks, and reserve checks in `_transferFundedClaim`/`_transferDefaultRecovery` all operate on the corrupted accounting.

### Recommendation
In `claimInstantWithdrawRequest` (or a shared cleanup helper), clear the per-epoch records the same way `_clearWithdrawClaimForEpoch` does for normal receipts: zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` for the epoch in which the receipt was created. Because a user can hold receipts across epochs, track the instant request epoch (e.g., a `lastInstantWithdrawRequest` marker analogous to `lastWithdrawRequest`) so the funded-claim path knows which epoch bucket to decrement, rather than only clearing in the default path.

### Proof of Concept
A Foundry PoC can be built against a forked/mainnet-like deployment of `IdleCDOEpochVariant` + `IdleCreditVault`:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;
import "forge-std/Test.sol";

// Sequence sketch (uses existing IdleCreditVault/IdleCDOEpochVariant harness):
function test_InstantClaimReplayInflatesRecovery() public {
    // Epoch N running, unscaledApr > 0, allowInstantWithdraw = true.
    // 1. Alice (KYC'd LP) deposits, then requestInstantWithdraw(100e6).
    //    -> instantWithdrawsRequestsByEpoch[alice][N] = 100, instantWithdrawClaimsByEpoch[N] = 100
    // 2. Borrower funds instant withdrawals; CDO calls collectInstantWithdrawFunds(100)
    //    -> pendingInstantWithdraws = 0, but per-epoch maps still hold 100.
    // 3. Eve (another KYC'd LP) calls requestInstantWithdraw(50e6)
    //    -> pendingInstantWithdraws = 50 (unfunded), instantWithdrawClaimsByEpoch[N] = 150
    // 4. Alice calls claimInstantWithdrawRequest -> receives 100 underlying.
    //    BUG: instantWithdrawsRequestsByEpoch / ClaimsByEpoch unchanged.
    // 5. Borrower defaults; manager calls finalizeDefault* path.
    //    defaultPendingClaimBasis = pendingWithdraws + 150 (replays Alice's paid 100)
    //    _defaultPrefundedInstantReserve = 150 - 50 = 100 (phantom, already paid out)
    //    -> defaultRecoveryPrice computed with 100 non-existent underlying.
    // 6. Eve (and any post-default requester) claims at inflated price first and is
    //    overpaid relative to real reserve; the last claimant's _transferDefaultRecovery
    //    reverts / is short by exactly the 100 replayed units.
    assertLt(strategy.underlyingBalance(), strategy.defaultRecoveryReserve());
}
```

Key assertions: `instantWithdrawClaimsByEpoch[epochNumber]` still includes Alice's claimed amount after step 4, and `defaultRecoveryPrice * totalBasis / 1e18` exceeds the strategy's real `underlyingToken` balance by the replayed amount.
