### Title
Loss-adjusted withdraw receipt escapes its haircut when the user opens a later withdraw request — the stale-epoch guard only checks `lastWithdrawRequest` (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When a `stopEpochWithDuration` loss is applied to pending withdraw receipts, `IdleCreditVault.collectWithdrawFunds` stores a per-epoch haircut in `lossRecoveryPriceByEpoch[epochNumber]` and collects only the reduced amount. The guard in `requestWithdraw` that is supposed to force users to claim that haircutted receipt before opening a new request only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]`. Once the user makes any later request, `lastWithdrawRequest` moves to the new epoch, the guard is permanently bypassed, and `_claimLossAdjustedWithdrawRequest` also keys off the same (now wrong) epoch — so the old haircutted receipt is paid at par through `_claimFundedWithdrawRequest`, overpaying the user out of the funded claims pool.

### Finding Description
`collectWithdrawFunds` sets `lossRecoveryPriceByEpoch[epochNumber]` when the borrower under-funds pending receipts (`contracts/strategies/idle/IdleCreditVault.sol:411-430`). The receipt is meant to be claimed through `_claimLossAdjustedWithdrawRequest`, which applies the haircut (`IdleCreditVault.sol:789-801`).

The protection in `requestWithdraw` reads:

- `lossEpoch = lastWithdrawRequest[_user]` and `lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch]` (`IdleCreditVault.sol:261-262`), reverting only if the *latest* request epoch carries a haircut and still has `withdrawsRequestsByEpoch` / `apr0Users` entries (`IdleCreditVault.sol:263-271`).

Because `lastWithdrawRequest[_user]` is overwritten with `currentEpoch` on every new request (`IdleCreditVault.sol:282`), a user with an unclaimed loss-adjusted receipt from epoch E1 can wait for the next buffer, call `requestWithdraw` again in epoch E2, and the guard now evaluates `lossRecoveryPriceByEpoch[E2] == 0` and lets the request through. The E1 receipt stays in `withdrawsRequests[_user]` (aggregate) and `withdrawsRequestsByEpoch[_user][E1]`.

On `claimWithdrawRequest` (`IdleCreditVault.sol:301-314`), `_claimLossAdjustedWithdrawRequest` again uses `lastWithdrawRequest[_user]` (now E2), finds `lossRecoveryPrice == 0`, and returns 0 — the E1 haircut is never applied. Then `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` at par, which still includes the full, unhaircutted E1 amount (`IdleCreditVault.sol:319-349`). The user burns `normalAmount` receipt tokens and receives `E1_full + E2` underlyings instead of `E1_full * lossRecoveryPrice / RECOVERY_FULL + E2`.

### Impact Explanation
The haircut that `stopEpochWithDuration` socialized onto pending receipts is silently reversed for any affected user who makes one more withdraw request. The excess is paid from the strategy's underlying balance — i.e., from funds reserved for other funded withdraw claims and instant-withdraw claimants — causing direct theft and potential insolvency of the claims pool. The overpayment per receipt equals `receiptAmount * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL`; with e.g. a 50% loss on a 100k USDC receipt, the attacker steals ~50k USDC. The skim, `pendingWithdraws` bookkeeping, and reserve guards do not stop it: `pendingWithdraws` was already zeroed by `collectWithdrawFunds`, and `_transferFundedClaim` only checks the default-recovery reserve, which is unset here.

### Likelihood Explanation
Requires only an unprivileged tranche holder who had a pending withdraw request in an epoch stopped with `stopEpochWithDuration(_lossAmount > 0)` — a normal, expected flow for realized losses. The second `requestWithdraw` is a plain user action during the next buffer period (no privileged or race condition needed; `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are re-enabled after a loss stop). One extra transaction converts a haircutted receipt into a par payout.

### Recommendation
Track per-epoch haircut state independently of `lastWithdrawRequest`. Concretely:

- In `requestWithdraw`, iterate or record the user's earliest outstanding request epoch (e.g., store `firstPendingRequestEpoch[_user]`) and revert if `lossRecoveryPriceByEpoch` is non-zero for *any* outstanding receipt epoch, not just the latest.
- Alternatively, eagerly settle the loss-adjusted receipt inside `requestWithdraw` (burn and pay the haircutted amount) before accepting the new request.
- In `_claimLossAdjustedWithdrawRequest`, look up the epoch that actually has a non-zero `lossRecoveryPriceByEpoch` for the user's receipts rather than assuming it equals `lastWithdrawRequest`.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossAdjustedReceiptBypassedByLaterRequest() external {
    uint256 amount = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                       // attacker deposits

    // Epoch 0: request withdraw during buffer, then start + stop with loss
    uint256 receipt = cdoEpoch.requestWithdraw(amount / 2, address(AAtranche));
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    // 50% loss: borrower funds only half of pendingWithdraws
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), lossAmount);

    // Guard check: lastWithdrawRequest == epoch of receipt -> a second request reverts NOW
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.requestWithdraw(amount / 4, address(AAtranche));

    // Next buffer: deposit again so requestWithdraw in a new epoch is allowed
    idleCDO.depositAA(amount / 4);
    // lastWithdrawRequest moves to epoch 1; lossRecoveryPriceByEpoch[1] == 0 -> guard bypassed
    cdoEpoch.requestWithdraw(amount / 4, address(AAtranche));

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    // BUG: paid == receipt + secondRequest (E1 receipt paid at par)
    // Expected: receipt * lossRecoveryPriceByEpoch[0] / 1e18 + secondRequest
    assertGt(paid, expectedHaircutted, "loss haircut escaped");
}
```

The invariant violated is loss socialization / "one receipt, haircutted payout": `withdrawsRequestsByEpoch[user][E1]` is cleared only inside `_clearWithdrawClaimForEpoch`, which is never reached for E1 once `lastWithdrawRequest` advances past it.
