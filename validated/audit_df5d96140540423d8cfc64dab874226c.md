### Title
Defaulted instant-withdraw claims decrement `pendingInstantWithdraws` for already-funded receipts, under-funding later instant withdrawals - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
In `IdleCreditVault._claimDefaultedInstantWithdrawRequest`, when a user claims a defaulted-epoch instant-withdraw receipt, the global `pendingInstantWithdraws` counter is reduced by the full `claimBasis` whenever `claimBasis < pendingInstantWithdraws`, even if that user's receipt was already funded (counted into `defaultRecoveryReserve` during default finalization). The code can only detect the "over-funded" case when `claimBasis >= pending`; for the partially-funded case it blindly decrements the global unfunded remainder. This is the direct analog of the reported `numTokensReservedForVesting` bug: a global "amount still owed/reserved" counter is mutated on a per-user claim without knowing whether that claim was actually drawn from the unfunded bucket.

### Finding Description
The buggy block is in `_claimDefaultedInstantWithdrawRequest` (`contracts/strategies/idle/IdleCreditVault.sol:842-856`):

```solidity
instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
instantWithdrawsRequests[_user] -= claimBasis;
uint256 pending = pendingInstantWithdraws;
// `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
// the extra amount was already counted as prefunded reserve during default finalization.
pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
_burn(_user, claimBasis);
_transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```

The comment itself admits the accounting ambiguity: `pendingInstantWithdraws` is meant to track only the *unfunded* remainder, but the function has no per-user record of how much of `claimBasis` was prefunded at finalization. If a user's receipt was (partially) prefunded into `defaultRecoveryReserve` during `finalizeDefaultRecovery`, and `claimBasis < pending`, the code subtracts the entire `claimBasis` from `pendingInstantWithdraws` anyway. Every such claim shrinks the amount `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`) will later pull from the CDO for genuinely unfunded instant withdrawers, while the claimant was already paid out of the recovery reserve via `_transferDefaultRecovery`.

### Impact Explanation
`pendingInstantWithdraws` is the solvency invariant for instant withdrawals: it is the amount the vault still expects to collect from `idleCDO` to honor unfunded instant receipts. Each defaulted-epoch instant claim by a user whose receipt was prefunded corrupts this counter downward by up to their full `claimBasis`. When the CDO later calls `collectInstantWithdrawFunds`, it collects less than the true unfunded liability, so remaining instant-withdraw requesters (or the same flow in `claimInstantWithdrawRequest` at `IdleCreditVault.sol:380-393`, which pays `instantWithdrawsRequests[_user]` at par from the vault balance) are permanently under-collateralized. Loss is bounded by the sum of prefunded defaulted-epoch instant claims processed while `claimBasis < pendingInstantWithdraws`, i.e., up to the entire prefunded instant bucket — a direct insolvency/theft-of-unclaimed-funds impact on honest users.

### Likelihood Explanation
Requires: (a) a borrower default reaches `finalizeDefaultRecovery` with a mix of prefunded and unfunded instant receipts in the default epoch — the code explicitly contemplates this split ("the extra amount was already counted as prefunded reserve"); (b) a user whose defaulted-epoch instant claim is smaller than the then-current `pendingInstantWithdraws` calls `claimInstantWithdrawRequest` via the CDO before the unfunded remainder is collected. Both are reachable by unprivileged lenders; the only privileged action is the honest manager's default finalization, which is sequenced around, not performed by the attacker. No existing guard stops it: `_transferFundedClaim`/`_transferDefaultRecovery` pay from reserves without reconciling which bucket funded the receipt.

### Recommendation
Track the funded vs unfunded portion of each defaulted-epoch instant receipt (e.g., store `instantWithdrawFundedByEpoch[user][epoch]` at finalization, or record a per-epoch funded price), and decrement `pendingInstantWithdraws` only by the unfunded component: `pendingInstantWithdraws -= unfundedPart`. Alternatively, keep `instantWithdrawClaimsByEpoch[defaultEpoch]` split into funded/unfunded sub-totals so claims consume the correct bucket.

### Proof of Concept
Foundry fork scenario (mirroring `test/foundry/IdleCreditVault.t.sol` default tests):

```solidity
// 1. Deposit AA/BB, start epoch, enable instant withdrawals via
//    cdoEpoch.setInstantWithdrawParams(delay, minAprDiff, false).
// 2. userA and userB each requestInstantWithdraw in epoch N.
// 3. Manager stops epoch with borrower default so that finalizeDefaultRecovery
//    prefunds userA's instant receipt into defaultRecoveryReserve but leaves
//    userB's unfunded (partial funding of instantWithdrawClaimsByEpoch[N]).
// 4. Record pendingBefore = strategy.pendingInstantWithdraws()
//    (== userB's unfunded basis).
// 5. userA calls cdoEpoch.claimInstantWithdrawRequest().
//    In _claimDefaultedInstantWithdrawRequest, claimBasis_A < pendingBefore, so:
//        pendingInstantWithdraws = pendingBefore - claimBasis_A;   // BUG
//    userA is paid from defaultRecoveryReserve (already prefunded).
// 6. CDO calls collectInstantWithdrawFunds(pendingInstantWithdraws):
//    collects pendingBefore - claimBasis_A instead of userB's full basis.
// 7. userB calls claimInstantWithdrawRequest(): vault underlying balance is
//    short by claimBasis_A (net of recovery haircut); the transfer either
//    reverts on insufficient balance or pays less than the haircut price.
assertLt(
    strategy.pendingInstantWithdraws(),   // after step 5
    pendingBefore - expectedUnfundedPartOfA // 0 if A fully prefunded
);
```

Note: I was unable to fully read `finalizeDefaultRecovery`/`_handleBorrowerDefault` within the available iterations to confirm exactly how prefunded instant receipts are split into `defaultRecoveryReserve` vs `pendingInstantWithdraws`; the finding relies on the code's own comment at `IdleCreditVault.sol:850-852` acknowledging that a claim can exceed the unfunded remainder because part was prefunded — which proves the mixed funded/unfunded case exists and that the decrement logic only handles the `claimBasis >= pending` boundary correctly.
