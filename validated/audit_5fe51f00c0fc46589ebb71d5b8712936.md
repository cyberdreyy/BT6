It only checks membership in `factory_whitelist`, then blindly inserts whatever `staking_pool_account_id` argument was supplied.### Title
Whitelisted Staking Pool Factory Can Whitelist an Arbitrary, Non-Conforming Account as a "Staking Pool" - (File: `whitelist/src/lib.rs`)

### Summary
The `whitelist` contract grants any account in `factory_whitelist` unrestricted authority to call `add_staking_pool` with **any** `staking_pool_account_id` of its choosing. The trust granted to a "staking pool factory" is meant to cover only pools that the factory itself deploys and initializes to the staking-pool spec (as `staking-pool-factory` does via `create_staking_pool`), but the whitelist contract enforces no binding between the calling factory's identity and the account being whitelisted, nor any check that the target actually runs conforming staking-pool code.

### Finding Description
`add_staking_pool` in [1](#0-0)  only checks that `env::predecessor_account_id()` is present in `factory_whitelist` (or is the foundation); it performs no validation that `staking_pool_account_id` is a subaccount of the calling factory, nor that it was actually created through that factory's `create_staking_pool` flow.

Compare this to how the legitimate `staking-pool-factory` contract behaves: it derives the pool's account deterministically as `"{staking_pool_id}.{current_account_id()}"`, deploys the spec-compliant `staking_pool.wasm` bytecode to it, and only then calls `add_staking_pool` for that specific, freshly created account, as shown in [2](#0-1)  and the callback at [3](#0-2) .

The whitelist contract, however, does not enforce this pattern — it trusts the factory's account ID as a proxy for "this argument is a pool I just deployed," but the code and argument accepted make no such guarantee. Any account added to `factory_whitelist` by the foundation (via `add_factory`, [4](#0-3) ) can call `add_staking_pool` directly with an arbitrary `staking_pool_account_id` — e.g., an attacker-controlled EOA-like account or a contract that does not implement the staking-pool spec's guarantee of returning delegated funds.

This is the same class of bug as the External Report: an entity holding a narrow scope of trust (here, "may whitelist pools it deploys") is able to exercise that trust far beyond its intended scope (whitelisting *any* account) because the code enforces no binding between the granted authority and the arguments accepted.

### Impact Explanation
Downstream, `lockup` contracts rely exclusively on `is_whitelisted` before delegating NEAR to a staking pool: `select_staking_pool` in [5](#0-4)  calls `ext_whitelist::is_whitelisted` and, on success, records the pool in `staking_information` via `on_whitelist_is_whitelisted` in [6](#0-5) , after which the owner can call `deposit_to_staking_pool` to actually transfer NEAR to that account.

If a whitelisted-but-compromised (or intentionally malicious) factory calls `add_staking_pool` with an account that does not implement the staking-pool spec's unstake/withdraw guarantees, any lockup contract that "selects" and deposits into that account will have its NEAR permanently frozen or stolen outright — matching the Critical impact bar of "a wrongly whitelisted...deployment" and "funds permanently frozen."

### Likelihood Explanation
Requires an account already holding "factory" trust (added once by the foundation) to misuse that trust — directly analogous to the original bug class ("a single malicious trusted account"). No owner, multisig member, or foundation action beyond the initial (documented) `add_factory` grant is required for the attacker's own malicious call; the exploit path (`add_staking_pool` with an arbitrary argument) is reachable with a single unprivileged-relative-to-the-lockup transaction from the compromised/malicious factory account.

### Recommendation
Bind the whitelist trust to the identity of the calling factory, e.g., require `staking_pool_account_id` to be a direct subaccount of `env::predecessor_account_id()` (matching the `"{id}.{factory_account_id}"` convention used by `create_staking_pool`), or have the whitelist contract track and only accept pool account IDs that were reported by an authenticated cross-contract callback from the factory's own `on_staking_pool_create`, rather than accepting an unconstrained argument from `add_staking_pool`.

### Proof of Concept
1. NEAR Foundation whitelists `factory.near` via `add_factory` ( [7](#0-6) ), trusting it to whitelist only pools it deploys.
2. The `factory.near` account (compromised, or malicious from inception) calls `whitelist.add_staking_pool({"staking_pool_account_id": "evil.near"})` directly — no `create_staking_pool` deployment ever occurs.
3. `add_staking_pool` ( [1](#0-0) ) only checks `factory_whitelist.contains(predecessor)`, which passes, and inserts `evil.near` into `whitelist`.
4. Any lockup contract calls `select_staking_pool("evil.near")`; `is_whitelisted` returns `true` ( [8](#0-7) ), so `on_whitelist_is_whitelisted` accepts it as the selected pool.
5. The lockup owner deposits NEAR to `evil.near` via `deposit_to_staking_pool`; `evil.near` is a contract/account controlled by the attacker with no unstake/withdraw guarantee, so the deposited NEAR is unrecoverable.

    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }

    /// Called after a given `staking_pool_account_id` was checked in the whitelist.
    pub fn on_whitelist_is_whitelisted(
        &mut self,
        #[callback] is_whitelisted: bool,
        staking_pool_account_id: AccountId,
    ) -> bool {
        assert_self();
        assert!(
            is_whitelisted,
            "The given staking pool account ID is not whitelisted"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();
        self.staking_information = Some(StakingInformation {
            staking_pool_account_id,
            status: TransactionStatus::Idle,
            deposit_amount: 0.into(),
        });
        true
    }
