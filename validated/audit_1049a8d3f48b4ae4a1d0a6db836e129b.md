### Title
Stale rejection weight is never retracted when a signer switches from reject to accept, causing the mining coordinator to miscount `total_weight_rejected` — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The `StackerDBListener` aggregates per-block signer weight into `BlockStatus.total_weight_approved` and `BlockStatus.total_weight_rejected` as `BlockResponse` messages arrive. When a signer legitimately re-evaluates a proposal and flips its vote from `Rejected` to `Accepted` (an explicitly supported transition in the signer's own state machine, `LocallyRejected -> LocallyAccepted`), the previously-tallied rejection weight for that signer's slot is never subtracted from `total_weight_rejected`. The result is a permanent, stale accounting entry, directly analogous to the reported bug where a withdrawn amount was never subtracted from `numTokensReservedForVesting`.

### Finding Description
`BlockStatus` tracks weight independently for acceptance and rejection: [1](#0-0) 

On `Accepted`, the gate for adding weight is whether the slot already appears in `gathered_signatures` — it does not check `responded_signers` or whether the slot previously rejected: [2](#0-1) 

On `Rejected`, the gate is `block.responded_signers.insert(slot_id)`, a single boolean membership set shared with the accept path, which increments `total_weight_rejected` the first time any response (of either kind) is seen from that slot: [3](#0-2) 

Because these two increments are gated on different, independent conditions (`gathered_signatures` vs. `responded_signers`), a slot that first rejects and later accepts gets its weight added to `total_weight_rejected` once (permanently, since nothing ever decrements it) and then also added to `total_weight_approved` — with no mechanism anywhere in this file to retract the earlier rejection tally. This is the same bug class as the report: a per-entity aggregate (`numTokensReservedForVesting` / `total_weight_rejected`) is updated on one leg of a state change (deposit/reject) but never adjusted on the other leg (withdraw/reconsider-and-accept), so the aggregate drifts from the true current state.

The coordinator then treats `total_weight_rejected` as ground truth for a "blocking minority" decision, checked eagerly and before the approval check: [4](#0-3) 

Since `total_weight_rejected` only ever accumulates stale votes from signers who later reconsidered, its value can be strictly larger than the weight of signers who currently still object to the block — allowing the >30% blocking-minority condition to trip on weight that no longer represents anyone's actual, current opinion.

### Impact Explanation
This is a liveness wedge for block production: the node coordinator can declare a block `SignersRejected` (and even `permanently_excluded_txids`, poisoning future proposals) purely because of accounting drift, not because a real blocking minority of signers currently oppose the block. For example, with `total_weight=100`, `weight_threshold=70` (blocking minority = 30): signer A (weight 20) rejects then reconsiders and accepts; signer B (weight 15) later rejects for an unrelated, legitimate reason. `total_weight_rejected` becomes `20+15=35 > 30`, tripping the eager-reject branch, even though the *current* opposition is only B's 15 (well under the blocking minority) and A's stance is now acceptance. The miner needlessly discards the block, potentially permanently excludes transactions the >30%-agreed-problematic check would not otherwise have flagged, and forces re-proposal — a liveness/availability degradation directly caused by an unretracted accounting entry, matching the "wedge" impact category in scope.

### Likelihood Explanation
This requires no majority, no key compromise, and no protocol violation — it is triggered by the ordinary, explicitly documented re-evaluation flow (`LocallyRejected -> LocallyAccepted`) of a single signer, combined with any other signer independently rejecting for a legitimate reason. It is a normal-operation accounting bug in the coordinator's bookkeeping, not an attack that needs coordination, so it is readily reachable in practice whenever transient rejections (e.g. timing/ordering-related "not-yet-fits-the-chain" rejections that later clear) precede acceptance from the same signer.

### Recommendation
Track weight per-slot with a single current "opinion" (e.g. `HashMap<slot_id, Vote>` storing the last known vote and its weight) rather than two independently-gated running sums. When a slot's vote changes from `Rejected` to `Accepted` (or vice versa), subtract the previous contribution from the corresponding total before adding the new one, so `total_weight_approved` and `total_weight_rejected` always reflect only the *current* stance of each responding signer, mirroring the intended "signature is sticky, rejection is revocable" design already documented for `has_signed_block_in_tenure`.

### Proof of Concept
1. Node proposes block B to signers with weights `A=20`, `B=15`, others summing to `65`; `total_weight=100`, `weight_threshold=70`.
2. Signer A initially rejects B (e.g. transient `ReorgNotAllowed`); `stackerdb_listener` records `total_weight_rejected=20` via [3](#0-2) .
3. Signer A re-evaluates per its local state machine (`LocallyRejected -> LocallyAccepted`) and sends `Accepted`; `stackerdb_listener` adds A's weight into `total_weight_approved` via [2](#0-1)  without ever decrementing the `total_weight_rejected=20` set in step 2.
4. Signer B independently and legitimately rejects B for its own reason; `total_weight_rejected` becomes `20+15=35`.
5. `signer_coordinator::get_block_status`'s eager-reject check (`total_weight_rejected + weight_threshold > total_weight` → `35+70=105>100`) fires via [4](#0-3) , and the miner treats B as globally rejected even though the currently-standing rejection weight (15, from signer B alone) is under the 30-weight blocking minority.
