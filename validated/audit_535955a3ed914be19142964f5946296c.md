Confirmed: `delete_member` (multisig2/src/lib.rs:356-379) only purges requests originally *submitted* by the removed member, and drops that member from `members` and `num_requests_pk`. It never scans the `confirmations: LookupMap<RequestId, HashSet<String>>` map to strip out prior confirmations that the removed member cast on *other* still-pending requests submitted by someone else. ### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts every string stored in the `confirmations` `HashSet` for a request against `num_confirmations`, but `delete_member` never removes a departing member's confirmations from requests they did not themselves submit. A member removed from the multisig (e.g., because their key was compromised or their authority revoked) can therefore have already-cast confirmations "posthumously" count toward executing a pending request, letting that request execute with fewer than `num_confirmations` currently-live approvals. [1](#0-0) [2](#0-1) 

### Finding Description
The binding this contract is supposed to maintain is: `confirmations counted == confirmations from members who are currently live members`. Concretely, at the moment `execute_request` runs, every entry in `confirmations.get(&request_id)` should correspond to an `AccountId`/`PublicKey` still present in `self.members`.

The flow that breaks this:
1. Member A submits a request via `add_request` (multisig2/src/lib.rs:170-200). Confirmations start empty.
2. Member B confirms via `confirm` (multisig2/src/lib.rs:294-315); since `confirmations.len()+1 < num_confirmations`, B's identifier (`member.to_string()`) is inserted into the `HashSet<String>` for that request.
3. Before the request accumulates enough confirmations to execute, the multisig itself removes B as a member through a separate, already-executed `DeleteMember` request, handled by `delete_member` (multisig2/src/lib.rs:356-379). That function only:
   - deletes requests where `r.member == member` (i.e., requests B *submitted*), removing their confirmations too, and
   - removes B from `self.members` and `self.num_requests_pk`.
   It does **not** iterate `self.confirmations` to strip B's stale confirmation off request A's confirmation set, because request A was submitted by A, not B.
4. Later, another live member C confirms request A. `confirm` computes `confirmations.len() as u32 + 1 >= self.num_confirmations` using the stale set that still contains B's now-invalid confirmation, so the request executes as if there were 2 live approvals (A implicitly via submission is not even counted unless A also called `confirm`, but crucially B's confirmation is stale) when in fact only B (removed) + C (live) contributed, i.e., only 1 currently-valid member's confirmation plus the stale one.
5. `current_member()` (multisig2/src/lib.rs:322-339) is only used to validate the *caller* of `confirm`/`add_request`/`delete_request` at call time — it is never used to filter the stored `confirmations` set before comparing against `num_confirmations`.

This lets `execute_request` (multisig2/src/lib.rs:224-290) run privileged actions — `Transfer`, `FunctionCall`, `AddKey` (including granting a full access key), `AddMember`/`DeleteMember` — while short of the intended threshold of currently-authorized approvers.

### Impact Explanation
This is a threshold-crossing (authorisation) bug matching the "multisig request executed below threshold" Critical-impact class: NEAR held by the multisig account can be transferred (`Transfer` action) or a full access key can be added to the multisig account (`AddKey` with `permission: None`, multisig2/src/lib.rs:258-261), effectively taking over the account, using a confirmation count that includes a since-revoked member. The practical trigger requires a member to be removed while they have a live unconsumed confirmation on some other pending request — a realistic scenario in a multisig responding to a compromised-key incident, which is exactly the situation `DeleteMember` exists to handle.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a pending request with fewer than `num_confirmations` confirmations, one of which comes from a member later removed via `DeleteMember`, and (b) enough additional live confirmations after removal to cross the threshold using the stale entry. This is a natural operational sequence (revoke a compromised key while other multisig business is in flight) rather than a contrived attack path, and no special privilege beyond being one of the remaining members (or the attacker controlling the removed member's still-cached key before removal propagates) is required to trigger execution.

### Recommendation
In `confirm`, before comparing to `num_confirmations`, filter `confirmations` to only entries where `self.members.contains(...)` still holds (reconstructing each `MultisigMember` from the stored string, or storing `MultisigMember` directly instead of `String` to make re-validation exact), and persist the pruned set. Alternatively, in `delete_member`, scan all entries in `self.confirmations` and remove the departing member's entry from every request's confirmation set, not just requests that member submitted.

### Proof of Concept
1. Deploy `MultiSigContract::new(members: [A, B, C, D], num_confirmations: 3)`.
2. A calls `add_request` to create request R (e.g., `Transfer` to attacker-controlled account), 0 confirmations.
3. B calls `confirm(R)` → confirmations = `{B}` (1 < 3, not executed).
4. Members submit and confirm a separate `DeleteMember { member: B }` request that reaches threshold and executes via `execute_request` → `delete_member` (multisig2/src/lib.rs:356-379). B is removed from `self.members`; R (submitted by A, not B) is untouched, confirmations for R remain `{B}`.
5. C calls `confirm(R)` → confirmations becomes `{B, C}`, `len()+1 = 3 >= num_confirmations(3)` → `execute_request` runs the `Transfer`, even though B is no longer a member and only C is a currently-valid confirmer beyond the implicit path.
6. NEAR is transferred out of the multisig account having received only confirmations from B (removed) and C, i.e., fewer than 3 *currently live* member confirmations, violating the K-of-N guarantee documented in `multisig2/README.md`.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));

        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
