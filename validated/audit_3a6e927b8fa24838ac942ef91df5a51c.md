### Title
Failed `stopEpoch` leaves borrower repayment and mutated receipt accounting in place while declaring default — plaintext-on-verification-failure analog in `_stopEpoch` try/catch — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external bug (CVE-2023-42811) is: `decrypt_in_place_detached` writes the plaintext into the caller's buffer **before** tag verification, so on failure the sensitive output is already exposed. The on-chain analog is `IdleCDOEpochVariant._stopEpoch`/`startEpoch`: the sensitive side-effect (pulling the borrower's repayment, reserving withdraw funds, mutating `pendingWithdraws`, minting interest) happens **inside** the `try` block *before* the "verification" steps (`_updateAccounting`, fee transfers, `settleBorrowerInterest`). If any later statement in the `try` reverts, the `catch` runs `_handleBorrowerDefault` and declares `defaulted = true` — but the already-executed effects are not rolled back. The "plaintext" (repaid funds, reduced `pendingWithdraws`, strategy-token mints) stays exposed while the epoch is treated as failed.

### Finding Description
In `_stopEpoch` (`contracts/IdleCDOEpochVariant.sol:408-505`), the external self-call `getFundsFromBorrower(_amountToPullFromBorrower + _pendingWithdraws)` succeeds first, then in the same `try` block the code executes `_strategy.collectWithdrawFunds(_pendingWithdraws)`, `IProgrammableBorrower(_borrower()).settleBorrowerInterest()`, `_transferFeeUnderlyings`, `mintStrategyTokens`, `_updateAccounting` and fee share mints. A revert at any point after `getFundsFromBorrower` drops into `catch { _handleBorrowerDefault(...) }`, which sets `defaulted = true`, pauses deposits, stops the epoch and disables withdraw requests (`contracts/IdleCDOEpochVariant.sol:577-599`). The borrower's repayment is already sitting in the CDO/strategy and `pendingWithdraws` is already decremented — exactly the "decrypted buffer left in place after tag failure" pattern: the protocol observes a failure and proceeds as if nothing was delivered, while the delivery already happened and stays mutated. Any underlying still held by the CDO at that point is subsequently treated as a donation and swept to `feeReceiver` by `_skimDonatedAssets` (`contracts/IdleCDOEpochVariant.sol:794-796`), which is invoked at the top of `finalizeDefault` and `updateAccounting`.

Concretely, in programmable/minted-interest mode (`isProgrammableBorrower && isInterestMinted`), `settleBorrowerInterest()` is an external call to the borrower contract inside the `try` (`contracts/IdleCDOEpochVariant.sol:413-415`). A user of the programmable borrower's ERC4626 vault can withdraw vault liquidity so that `settleBorrowerInterest` (or any ERC4626 `redeem`/`withdraw` it performs) reverts. The manager's honest `stopEpoch` call then: pulls pending-withdraw cash into the CDO (`getFundsFromBorrower` succeeded), forwards it to the strategy and decrements `pendingWithdraws` (`collectWithdrawFunds` succeeded), then reverts at `settleBorrowerInterest` → `defaulted = true` even though the borrower repaid and never defaulted. The same structure exists in `startEpoch` (`contracts/IdleCDOEpochVariant.sol:295-303`) and `getInstantWithdrawFunds` (`contracts/IdleCDOEpochVariant.sol:566-573`), where the sensitive transfer is attempted first and any residual failure is conflated with "borrower did not pay".

The broken invariant is the loss-waterfall/solvency one: `defaulted` is a terminal flag that gates `finalizeDefault`, `restoreOperations` (`_checkNotAllowed(defaulted || priceAA == 0)` at line 622), `_beforeUnpause` (line 636) and all request/claim flows, so a spurious default freezes the pool and forces every claim through the aggregate recovery haircut even though repayment funds were actually delivered. None of the existing guards (`_skimDonatedAssets`, `_onlyIdleCDO`, epoch gating, `_checkProgrammableBorrowerMode`) stop this, because the failure happens *after* the funds moved, not before.

### Impact Explanation
Once `defaulted = true` with delivered-but-unaccounted funds: (a) raw underlying left in the CDO is swept to `feeReceiver` as "donations" on the next `finalizeDefault`/`updateAccounting` — a direct leak of repaid assets away from lenders; (b) `epochNumber`/`lastWithdrawRequest` bookkeeping in `IdleCreditVault` has already been advanced/reduced (`collectWithdrawFunds` ran, `pendingWithdraws` decreased) while the epoch transition never completed, so receipt claims are settled only through the defaulted-receipt path at `defaultRecoveryPrice`, i.e., lenders take a haircut on receipts that were fully funded; (c) the pool is permanently frozen unless the owner/manager finalizes a "recovery", which crystallizes a loss that never occurred. Quantified loss in the worst path equals the full repaid interest plus the donated-asset skim of `_amountToPullFromBorrower + _pendingWithdraws`, and a forced haircut on all active NAV proportional to `1 - defaultRecoveryPrice/RECOVERY_FULL` chosen at finalization.

### Likelihood Explanation
The trigger requires a revert after `getFundsFromBorrower` inside the `try`. In programmable/minted mode the manager calls `stopEpoch` on a fixed cadence, and `settleBorrowerInterest()` hits the programmable borrower's ERC4626 vault; an unprivileged vault depositor can withdraw liquidity at the right block so the settlement reverts — no privileged role needed. The borrower, manager and owner remain honest; the attack only sequences around the manager's routine call. Likelihood is medium: it needs the programmable-borrower deployment mode and precise timing against the epoch-end call, but no capital is burned by the attacker (withdrawing one's own vault shares is free) and the manager's `stopEpoch` cannot be retried once `defaulted` is set because the flag is irreversible. Caveat: the exact revert surface of `settleBorrowerInterest`/`onStopEpoch` lives in `ProgrammableBorrower.sol` and depends on ERC4626 liquidity at call time; I could not fully verify every revert condition in that hook from the indexed context.

### Recommendation
Apply the AES-GCM-SIV fix pattern: undo or isolate the exposed state before signalling failure. Concretely: (1) perform `settleBorrowerInterest` **before** `getFundsFromBorrower`, or move it out of the `try` so a settlement failure cannot be conflated with non-payment; (2) in the `catch`, distinguish "transfer failed" from "post-transfer accounting failed" — e.g., check `IERC20(token).balanceOf(address(this))` delta and only call `_handleBorrowerDefault` when no funds arrived, otherwise complete accounting in a degraded path; (3) for `startEpoch`'s catch, note it already routes funds to `_strategy.reserveDefaultRecovery` — apply the same explicit reservation in `_stopEpoch` so pulled repayment can never be skimmed by `_skimDonatedAssets` as a "donation"; (4) add regression tests where a post-`getFundsFromBorrower` hook reverts and assert `defaulted` is not set (mirroring the wycheproof "bad tag ⇒ no plaintext" test idea).

### Proof of Concept
Foundry fork sketch (mode: programmable borrower + minted interest):

```solidity
// test/foundry/SpuriousDefaultOnSettleRevert.t.sol
function testSpuriousDefaultAfterRepayment() external {
    // Setup: programmable borrower + isInterestMinted, epoch running,
    // borrower has approved CDO for interest + pendingWithdraws and is solvent.
    _depositWithUser(victim, 100_000e6, true);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));   // creates pendingWithdraws
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Attacker = unprivileged user of borrower's ERC4626 vault:
    // drains vault liquidity so settleBorrowerInterest() reverts.
    vm.prank(attacker);
    borrowerVault.withdraw(borrowerVault.maxWithdraw(attacker), attacker, attacker);

    uint256 cdoBalPre = IERC20(underlying).balanceOf(address(cdoEpoch));
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);   // does NOT revert: catch swallows it

    // Bug: repayment was pulled + collectWithdrawFunds ran, but pool is "defaulted".
    assertGt(IERC20(underlying).balanceOf(address(cdoEpoch))
             + IERC20(underlying).balanceOf(address(strategy)), cdoBalPre);
    assertTrue(cdoEpoch.defaulted());                      // plaintext exposed on failure
    assertFalse(strategy.defaultRecoveryFinalized());

    // Repaid funds now sit unaccounted; finalizeDefault skims CDO balance to feeReceiver
    // and all receipts are haircut at defaultRecoveryPrice despite full repayment.
    vm.prank(manager);
    cdoEpoch.finalizeDefault(recovered, manager);          // _skimDonatedAssets leaks repaid cash
}
```

Key assertion: `defaulted == true` while the borrower demonstrably paid — the "decrypted buffer" (repaid funds, mutated `pendingWithdraws`) persists even though the epoch transition "failed".
