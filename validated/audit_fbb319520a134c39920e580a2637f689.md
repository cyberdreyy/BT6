### Title
Front-runnable lockup creation lets an attacker permanently bind a victim's lockup to an attacker-controlled whitelist, defeating the staking-pool trust anchor - ([File: lockup-factory/src/lib.rs, lockup/src/owner_callbacks.rs])

### Summary
`LockupFactory::create` derives the lockup's account ID deterministically from `sha256(owner_account_id)` and lets *any* caller supply `whitelist_account_id`, with no check that the intended owner authorized the call. An attacker can pre-create `victim.near`'s lockup with `staking_pool_whitelist_account_id` set to a whitelist contract they deploy and control, permanently binding that immutable field before the legitimate creator (owner/Foundation) ever transacts. `LockupContract::on_whitelist_is_whitelisted` then blindly trusts whatever boolean this attacker-controlled whitelist returns, so it can approve a pool whose `withdraw` no-ops, breaking `deposit_amount recorded on the lockup == NEAR recoverable from the selected pool`.

### Finding Description
Binding claimed broken: `self.staking_information.deposit_amount == NEAR actually recoverable from staking_pool_account_id`.

Path:
1. `LockupFactory::create` (`lockup-factory/src/lib.rs:107-166`) computes `lockup_account_id = sha256(owner_account_id)[..20] + "." + factory`, requires only `MIN_ATTACHED_BALANCE` (3.5 NEAR) attached by *any* predecessor, and lets the caller pass an arbitrary `whitelist_account_id: Option<ValidAccountId>` that becomes `staking_pool_whitelist_account_id` in `LockupArgs` [1](#0-0) . There is no check binding `owner_account_id` to `predecessor_account_id`, and no check that the deterministic account doesn't already logically "belong" to someone else — anyone can front-run the creation for a known future employee's `victim.near`.
2. `LockupContract::new` (`lockup/src/lib.rs:181-198`) only validates the whitelist account ID is *syntactically* valid, not that it is a legitimate/trusted whitelist, and stores it permanently in `self.staking_pool_whitelist_account_id` [2](#0-1) . No setter for this field exists anywhere in the contract (confirmed by searching `lockup/src/*`), so it can never be corrected after creation.
3. Later, the real owner (`victim.near`, as recorded in `owner_account_id`) calls `select_staking_pool` (`lockup/src/owner.rs:12-41`), which queries `ext_whitelist::is_whitelisted` on `self.staking_pool_whitelist_account_id` — now the attacker's contract — and unconditionally trusts the callback result in `on_whitelist_is_whitelisted` (`lockup/src/owner_callbacks.rs:7-25`), which sets `self.staking_information` with no independent validation of the pool's code/behavior [3](#0-2) .
4. Once selected, `deposit_to_staking_pool` → `on_staking_pool_deposit` and `withdraw_from_staking_pool` → `on_staking_pool_withdraw` only check `is_promise_success()` — i.e., that the cross-contract call didn't fail/panic — not that NEAR was actually transferred back [4](#0-3) . A pool whose `withdraw` method simply returns success without a `Promise::transfer` will make `is_promise_success()` return `true`, so `deposit_amount` is decremented on the lockup's ledger while no NEAR actually returns to the lockup account.

Root cause: the whitelist trust anchor (`staking_pool_whitelist_account_id`) is chosen by whoever calls the public, unauthenticated `create` function first, not necessarily by the intended owner or the Foundation, and it can never be changed afterward. `assert_owner`/`assert_self` on the lockup side guard *who* can call staking methods, but they do nothing to verify the whitelist itself is trustworthy — that trust was already misplaced at contract-creation time by a party outside the owner's control.

### Impact Explanation
This matches the explicit Critical category "a lockup deployed with parameters its rightful creator never chose": the attacker permanently fixes an untrusted whitelist for `victim.near`'s future lockup [5](#0-4) . Combined with the subsequent staking flow, once the real owner is coerced/misled into selecting the attacker's only-whitelisted pool, NEAR the owner deposits into that pool is not recoverable through `withdraw_from_staking_pool`, since the lockup's internal ledger (`deposit_amount`) can be silently zeroed by a no-op `withdraw` while the pool retains the NEAR — funds move out of the owner's effective control into a pool an unentitled party (the attacker) deployed and named. This is repeatable against any `owner_account_id` an attacker can predict (e.g., known future employees) at the cost of one `MIN_ATTACHED_BALANCE` (3.5 NEAR) transaction each.

### Likelihood Explanation
Cost is low (single `create` call with 3.5 NEAR attached, callable by any unprivileged account) and the only precondition is knowing/guessing the intended `owner_account_id` before the legitimate lockup is created for it — plausible for known future or targeted employees/accounts, since `create` is a fully public factory method with no allowlist on callers [6](#0-5) . The subsequent fund-loss step additionally requires the real owner to actively call `select_staking_pool` and `deposit_to_staking_pool` against the attacker's pool, which the squatted whitelist can force by whitelisting only that one pool.

### Recommendation
In `LockupFactory::create`, restrict who may create a lockup for a given `owner_account_id` (e.g., require `predecessor_account_id == owner_account_id` or an authenticated caller such as the Foundation/`whitelist_account_id` owner), and/or disallow a caller-supplied `whitelist_account_id` entirely, always defaulting to the factory's own audited `whitelist_account_id`. Additionally, consider adding an owner/Foundation-gated setter to allow migrating `staking_pool_whitelist_account_id` if it is ever found to be untrustworthy.

### Proof of Concept
`cargo test` plan (near-sdk-sim / near-workspaces, no mainnet):
1. Deploy `LockupFactory` normally with a legitimate `whitelist_account_id`.
2. As an unprivileged `attacker` account, call `factory.create(owner_account_id: "victim.near", ..., whitelist_account_id: Some("attacker-whitelist.near"))` with `MIN_ATTACHED_BALANCE` attached, after first deploying `attacker-whitelist.near` (a minimal contract whose `is_whitelisted` always returns `true`) and `attacker-pool.near` (a minimal pool whose `withdraw`/`unstake` are no-ops returning success, `deposit_and_stake` accepts NEAR).
3. Assert the resulting lockup account (deterministic hash of `"victim.near"`) exists with `get_staking_pool_whitelist_account_id() == "attacker-whitelist.near"` — i.e., `victim.near`'s registered owner never authorized this whitelist.
4. As `victim.near` (owner), call `select_staking_pool("attacker-pool.near")` → `on_whitelist_is_whitelisted(true, ...)` succeeds; assert `get_staking_pool_account_id() == Some("attacker-pool.near")`.
5. Call `deposit_and_stake(amount)`; assert `get_known_deposited_balance().0 == amount` (lockup ledger side of the equality).
6. Call `unstake(amount)` then, after simulating epoch advance, `withdraw_from_staking_pool(amount)` → `on_staking_pool_withdraw`; assert `is_promise_success()` path decrements `deposit_amount` to `0`.
7. Assert the lockup account's actual NEAR balance (`env::account_balance()` / on-chain balance) did **not** increase by `amount`, while `get_known_deposited_balance().0 == 0` — proving the ledger (`deposit_amount == 0`) diverges from reality (`NEAR recoverable == 0` but `NEAR actually sent to pool == amount`, never returned), demonstrating the broken binding and loss of the owner's funds to the attacker's pool.

    pub fn on_staking_pool_withdraw(&mut self, amount: WrappedBalance) -> bool {
        assert_self();

        let withdraw_succeeded = is_promise_success();
        self.set_staking_pool_status(TransactionStatus::Idle);

        if withdraw_succeeded {
            {
                let staking_information = self.staking_information.as_mut().unwrap();
                // Due to staking rewards the deposit amount can become negative.
                staking_information.deposit_amount.0 = staking_information
                    .deposit_amount
                    .0
                    .saturating_sub(amount.0);
            }
            env::log(
                format!(
                    "The withdrawal of {} from @{} succeeded",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        } else {
            env::log(
                format!(
                    "The withdrawal of {} from @{} failed",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        }
        withdraw_succeeded
    }
