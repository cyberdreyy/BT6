### Title
`DeployGlobalContractAction` (deploy_mode=AccountId) binds attacker-chosen wasm to an arbitrary victim account without consent and drains victim balance - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
`action_deploy_global_contract` and `action_use_global_contract` in `runtime/runtime/src/global_contracts.rs` operate purely on the receipt's `receiver_id` account and take no `actor_id` parameter, so nothing inside these functions verifies that the account executing the action is the account that authorized it (i.e., that `predecessor_id`/signer equals `receiver_id`). This differs from `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`, which `docs/RuntimeSpec/Actions.md` explicitly documents as requiring `predecessor_id == receiver_id`.

### Finding Description
`action_deploy_global_contract` at `runtime/runtime/src/global_contracts.rs:24-62` receives `account: &mut Account` and `account_id: &AccountId` which correspond to `receipt.receiver_id()` (set in `apply_action_receipt`, `runtime/runtime/src/lib.rs:791`), and it never receives or checks `actor_id`/`predecessor_id`: [1](#0-0) 

The storage cost is deducted directly from that account's balance, and `initiate_distribution` is called with `account_id.clone()`; when `deploy_mode == GlobalContractDeployMode::AccountId`, the resulting `GlobalContractIdentifier::AccountId(account_id)` is exactly the receiver account, not necessarily the signer: [2](#0-1) 

`action_use_global_contract`/`use_global_contract` (`global_contracts.rs:64-108`) similarly takes only `account_id` (the receiver) with no actor check: [3](#0-2) 

Static validation in `runtime/runtime/src/action_validation.rs` only checks contract size and the syntactic validity of the `AccountId` inside `GlobalContractIdentifier` — it never compares the identifier or receiver to the transaction's signer/predecessor: [4](#0-3) [5](#0-4) 

By contrast, `docs/RuntimeSpec/Actions.md` documents that for `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`, `predecessor_id` and `receiver_id` are required to be equal — `DeployGlobalContract` and `UseGlobalContract` are conspicuously absent from that list: [6](#0-5) 

Since an ordinary FullAccess access key permits a signer to target *any* `receiver_id` with non-`FunctionCall` actions (unlike `FunctionCallPermission` keys, which are receiver-restricted), an attacker who owns a FullAccess key on their own account can build a transaction with `signer_id = attacker`, `receiver_id = victim`, `actions = [DeployGlobalContractAction { deploy_mode: AccountId, code: attacker_wasm }]`. This transaction passes standard nonce/signature/access-key checks (FullAccess keys are not receiver-scoped) and is converted into an action receipt with `predecessor_id = attacker`, `receiver_id = victim`. When applied, `account_id` inside `action_deploy_global_contract` is the victim's account, so the victim's balance is charged the storage fee and `GlobalContractIdentifier::AccountId(victim)` is written to global-contract storage bound to attacker-supplied code — without the victim ever signing anything.

### Impact Explanation
Two concrete, in-scope impacts:
1. Loss of funds: the victim's account balance is unilaterally debited for `global_contract_storage_amount_per_byte * len(code)` as `storage_cost`, burned as `tokens_burnt`, with no consent or benefit to the victim.
2. Authorization escalation / identity impersonation: `GlobalContractIdentifier::AccountId(victim)` — a protocol-level identity binding meant to represent "code published by this account" — becomes permanently associated with attacker-chosen wasm. Any account can subsequently reference this identifier via `UseGlobalContractAction{contract_identifier: AccountId(victim)}` and run the attacker's code while it is nominally "published under `victim`'s identity," a cross-account authorization violation.

This matches the "authorization escalation across accounts" and "loss of funds" NEAR bounty categories.

### Likelihood Explanation
The only precondition is that the attacker controls one funded NEAR account with a FullAccess key (a standard, unprivileged capability of any user) and knows the victim's `account_id`. No validator/node/RPC-operator access, no leaked keys, and no social engineering are required. The transaction is a single ordinary action-list transaction that the public RPC endpoint would accept under the existing access-key permission model, and it is fully repeatable against any target account.

### Recommendation
In `runtime/runtime/src/global_contracts.rs`, thread `actor_id` (or equivalently `receipt.predecessor_id()`) into `action_deploy_global_contract` and `action_use_global_contract`/`use_global_contract`, and reject the action (e.g., a new `ActionErrorKind::ActorNoPermission`-style error) unless `actor_id == account_id`, mirroring the existing behavior for `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, and `DeleteAccount`. Alternatively (or additionally), enforce in `validate_deploy_global_contract_action` that for `GlobalContractDeployMode::AccountId`, the eventual `GlobalContractIdentifier::AccountId` must equal the receiver only when receiver equals the transaction's originating signer/predecessor chain.

### Proof of Concept
Runtime/test-loop integration test:
1. Create two accounts, `attacker.near` (funded, holds its own FullAccess key) and `victim.near` (funded, victim never authorizes anything).
2. Build a `SignedTransaction` with `signer_id = attacker.near`, `receiver_id = victim.near`, `actions = [Action::DeployGlobalContract(DeployGlobalContractAction { code: attacker_wasm.into(), deploy_mode: GlobalContractDeployMode::AccountId })]`, signed with `attacker.near`'s own FullAccess key.
3. Submit through the normal apply path (or `TestEnv`/test-loop apply flow) and let the resulting `GlobalContractDistributionReceipt` be processed.
4. Assertions:
   - Expect `ActionErrorKind` rejection (e.g., an actor-permission error) if the fix is applied — currently no such error occurs.
   - Currently observed (bug): `victim.near`'s balance decreases by the storage cost, and after distribution, `TrieKey::GlobalContractCode { identifier: GlobalContractCodeIdentifier::AccountId(victim.near) }` exists in state containing `attacker_wasm`, i.e., `GlobalContractIdentifier::AccountId` equals `victim.near`, not `attacker.near`.

```rust
pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
```

```rust
pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}
```

```markdown
Each transaction consists a list of actions to be performed on the `receiver_id` side. Since transactions are first
converted to receipts when they are processed, we will mostly concern ourselves with actions in the context of receipt
processing.
 
For the following actions, `predecessor_id` and `receiver_id` are required to be equal:

- `DeployContract`
- `Stake`
- `AddKey`
- `DeleteKey`
- `DeleteAccount`

NOTE: if the first action in the action list is `CreateAccount`, `predecessor_id` becomes `receiver_id`
for the rest of the actions until `DeleteAccount`. This gives permission by another account to act on the newly created account.
```
