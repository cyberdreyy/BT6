### Title
Canceled/expired async deposit and redeem requests refund escrowed funds to `request.receiver` instead of the paying `request.user` - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2` lets a caller create an async deposit/redeem request specifying an independent `receiver` who is only supposed to receive proceeds "when the order is solved" [1](#0-0) . When the request is instead canceled or expires and is refunded, the escrowed tokens/units are sent primarily to `request.receiver`, only falling back to the actual payer `request.user` if the transfer to `receiver` fails, mirroring the exact root cause described in the Dinari report where cancellation refunds go to the wrong party. This can cause the paying user to permanently lose the funds they escrowed if they designated a different receiver.

### Finding Description
`requestDeposit`/`requestRedeem` pull tokens/units from `msg.sender` and record `user = msg.sender` while `receiver` is an independently supplied address [2](#0-1) [3](#0-2) . The `RequestV2.receiver` field is documented purely as "Address that gets units/tokens when the order is solved" [1](#0-0) .

However, all cancellation and refund paths route the escrowed asset through `_transferWithFallback`, which sends first to `receiver` and only falls back to the payer (`requester`) if that transfer reverts: [4](#0-3) 

This helper is invoked with `requester = request.user` (or `msg.sender`, who must equal `request.user`) and `receiver = request.receiver` in every refund/cancel code path:
- `cancelRequest` (user self-cancel, guarded only by `msg.sender == request.user`) [5](#0-4) 
- `refundRequest` (expired-request refund) [6](#0-5) 
- `_clearHashAndTransferRefund`, the shared helper used by both of the above [7](#0-6) 
- deadline-expired branches inside the solver-facing solve functions (`_solveDepositVaultAutoPrice`, `_solveDepositVaultFixedPrice`, `_solveRedeemVaultAutoPrice`, `_solveRedeemVaultFixedPrice`, `_solveRequestDirect`) [8](#0-7) [9](#0-8) [10](#0-9) 

No guard anywhere requires `request.receiver == request.user`; the wrapper `requestDeposit(...)`/`requestRedeem(...)` overloads without a `receiver` param simply pass `msg.sender` as receiver [11](#0-10) , but the public overload that accepts an explicit `receiver` argument permits any address [12](#0-11) . Thus an ordinary user who funds a request for a different receiver (a normal, expected use case — analogous to gifting a deposit/redeem to someone else) will have their own funds sent to that receiver instead of returned to themselves upon cancellation or expiry.

### Impact Explanation
Any user who creates an async deposit or redeem request with `receiver != msg.sender` and later cancels the request (or lets it expire and someone/anyone calls `refundRequest`/`solveRequestsVault`/`solveRequestsDirect` on it) has their escrowed payment tokens (for deposits) or vault units (for redeems) sent to the `receiver` address instead of back to themselves. This is a direct, permanent loss of user funds with no way for the payer to recover them (barring the receiver transfer reverting), matching the High severity of the original Dinari finding.

### Likelihood Explanation
This requires no privileged role, oracle manipulation, or third-party token behavior — only an ordinary user calling the standard `requestDeposit`/`requestRedeem` overload with a distinct `receiver`, followed by a normal `cancelRequest` call (self-triggered) or simply letting the deadline pass so any refund/solve path executes the deadline-expired branch. Deposit/redeem cancellations must be enabled via `setCancellationDetails` for `cancelRequest`, but the deadline-expiry refund path (`refundRequest`, or solvers processing an expired request) requires no such toggle and is always reachable. The precondition (receiver ≠ user) is a normal, foreseeable usage pattern (e.g., depositing/redeeming on behalf of another account), making this highly likely to be triggered in production.

### Recommendation
On cancellation and refund of unfilled/expired requests, return the escrowed asset to `request.user` (the actual payer) rather than `request.receiver`. Concretely, in `_clearHashAndTransferRefund` and the deadline-expired branches of `_solveDepositVaultAutoPrice`, `_solveDepositVaultFixedPrice`, `_solveRedeemVaultAutoPrice`, `_solveRedeemVaultFixedPrice`, and `_solveRequestDirect`, call `_transferWithFallback` (or a direct `safeTransfer`) with `request.user` as the primary recipient, only falling back to `request.receiver` if desired for edge cases — or simply remove the receiver-first behavior for refund paths entirely so refunds always go to `request.user`.

### Proof of Concept
Foundry outline (against a local fork with `ProvisionerV2`, `MultiDepositorVault`, and `PriceAndFeeCalculator` deployed/configured as in production):
1. As admin, enable async deposits for a test token via `setTokenDetails` and enable self-cancellation via `setCancellationDetails(true, ..., depositCancellationFeeNumeraire=0, ...)`.
2. `bob` approves `token` to `ProvisionerV2` and calls `requestDeposit(token, tokensIn, minUnitsOut, 0, deadline, maxPriceAge, true, alice)` — a normal deposit-for-someone-else request; `bob`'s tokens are pulled into the provisioner and `RequestV2{user: bob, receiver: alice, ...}` hash is recorded.
3. Before the deadline, `bob` calls `cancelRequest(token, request)` with the exact `RequestV2` struct.
4. Assert: `token.balanceOf(alice)` increased by the (fee-adjusted) `tokensIn` amount, and `token.balanceOf(bob)` did **not** increase — i.e., `bob`, who paid and canceled his own order, received nothing back while `alice` received his funds. This confirms the loss-of-funds condition.

    function cancelRequest(IERC20 token, RequestV2 calldata request) external nonReentrant {
        // Requirements: self-cancel caller must be request user
        require(msg.sender == request.user, Aera__CallerIsNotRequestUser());

        if (_isRequestTypeDeposit(request.requestType)) {
            // Requirements: deposit cancellation toggle must be enabled
            require(_depositCancellationsEnabled, Aera__DepositRequestCancellationDisabled());

            uint256 refundAmount = request.tokens;
            // Requirements: pre-deadline self-cancel applies cancellation fee
            if (block.timestamp < request.deadline) {
                uint256 cancellationFee = _computeDepositCancellationFeeTokens(token);
                // Requirements: cancellation fee cannot exceed escrowed amount
                require(cancellationFee <= refundAmount, Aera__CancellationFeeExceedsRequestAmount());
                if (cancellationFee != 0) {
                    unchecked {
                        // unchecked: safe because cancellationFee <= refundAmount is enforced above
                        refundAmount -= cancellationFee;
                    }
                    // Interactions: transfer cancellation fee to vault
                    token.safeTransfer(MULTI_DEPOSITOR_VAULT, cancellationFee);
                }
            }

            // Effects + interactions: clear hash, emit refund event, and transfer net token amount with fallback
            _clearHashAndTransferRefund(token, request, msg.sender, refundAmount, token);
        } else {
            // Requirements: redeem cancellation toggle must be enabled
            require(_redeemCancellationsEnabled, Aera__RedeemRequestCancellationDisabled());

            // Interactions: compute redeem request size in numeraire with protocol-favoring rounding
            uint256 requestNumeraire = PRICE_FEE_CALCULATOR.convertUnitsToNumeraire(
                MULTI_DEPOSITOR_VAULT, request.units, Math.Rounding.Ceil
            );
            // Requirements: redeem self-cancel must not exceed configured cap
            require(requestNumeraire <= _redeemCancellationCapNumeraire, Aera__RequestAmountExceedsRefundCap());

            uint256 refundAmount = request.units;
            // Requirements: pre-deadline self-cancel applies cancellation fee
            if (block.timestamp < request.deadline) {
                uint256 cancellationFee = _computeRedeemCancellationFeeUnits(requestNumeraire);
                // Requirements: cancellation fee cannot exceed escrowed amount
                require(cancellationFee <= refundAmount, Aera__CancellationFeeExceedsRequestAmount());
                if (cancellationFee != 0) {
                    unchecked {
                        // unchecked: safe because cancellationFee <= refundAmount is enforced above
                        refundAmount -= cancellationFee;
                    }
                    // Interactions: burn cancellation fee units from provisioner escrow
                    IMultiDepositorVault(MULTI_DEPOSITOR_VAULT)
                        .exit(address(this), token, 0, cancellationFee, address(this));
                }
            }

            // Effects + interactions: clear hash, emit refund event, and transfer net unit amount with fallback
            _clearHashAndTransferRefund(token, request, msg.sender, refundAmount, IERC20(MULTI_DEPOSITOR_VAULT));
        }
    }

    function _clearHashAndTransferRefund(
        IERC20 token,
        RequestV2 calldata request,
        address requester,
        uint256 amount,
        IERC20 transferToken
    ) internal {
        bytes32 requestHash = _getRequestHash(token, request);
        // Requirements: hash has been set
        require(asyncRequestHashes[requestHash], Aera__HashNotFound());
        // Effects: unset hash as used
        asyncRequestHashes[requestHash] = false;
        // Interactions: transfer amount to receiver, fallback to requester on transfer failure
        _transferWithFallback(transferToken, requester, request.receiver, amount);

        // Log refund event
        if (_isRequestTypeDeposit(request.requestType)) {
            emit DepositRefunded(requestHash);
        } else {
            emit RedeemRefunded(requestHash);
        }
    }

    /// @notice Transfers amount to receiver and falls back to requester if receiver transfer fails
    /// @param token The ERC20 token being transferred
    /// @param requester The original requester address used as fallback receiver
    /// @param receiver The intended receiver from the request
    /// @param amount The amount of tokens to transfer
    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
