### Title
Front-Runnable Instant Multiplier Update Lets Holders Steal Rebase Yield From Other B20 Token Holders - (File: crates/common/precompiles/src/b20_asset/logic/v2.rs)

### Summary
The `AssetV2` B20 token precompile implements an ERC-8056 "Scaled UI Amount" rebasing mechanism where a global `multiplier` scales every holder's raw balance. Alongside the safe, pre-scheduled `updateUIMultiplier` path, the precompile retains an "instantaneous failsafe," `update_multiplier`, that applies a new multiplier immediately and atomically to the entire token supply [1](#0-0) . Because this multiplier is meant to reflect off-chain-accrued value (analogous to `wstTAO`'s manually-updated `exchangeRate`), and it is applied uniformly to whatever balance a holder has at call time, any unprivileged holder who observes the pending `updateMultiplier` transaction in the mempool can front-run it: acquire/transfer-in a balance immediately before the update lands, receive the full rebase boost the instant it is applied, then transfer/dispose of the balance immediately after — capturing yield that should have accrued only to holders who held the asset through the entire accrual period. This is the same "delayed/manual rate update front-running" bug class described in the external `wstTAO.sol` report, mapped onto Base's B20 rebasing-token precompile.

### Finding Description
`AssetV2::update_multiplier` is documented as an "Instantaneous failsafe" that "writes the current multiplier immediately, clearing any pending update" [2](#0-1) . It requires only the token's `OPERATOR_ROLE` and takes effect the moment the transaction is included on-chain [3](#0-2) , unlike the scheduled sibling `update_ui_multiplier`, which requires `effective_at` to be strictly in the future and therefore gives every holder equal, public advance notice of the new rate [4](#0-3) .

All UI-facing balance reads (`to_scaled_balance`, `scaled_balance_of`, `balance_of_ui`, `total_supply_ui`) multiply the raw balance by whatever the *current effective* multiplier is at call time, with no per-holder accrual bookkeeping: `balance * multiplier / WAD` [5](#0-4) . This means the multiplier increase is retroactively applied to every unit of raw balance a wallet holds at the moment the operator's `updateMultiplier` transaction executes, regardless of how long that wallet has held the balance.

Root-cause mapping to the report:
- `wstTAO.exchangeRate` (manually pushed, off-chain-computed value) ≈ `AssetV2`'s `multiplier` pushed via the instant `update_multiplier` path.
- Front-running `updateExchangeRate()` with `wrap()` ≈ front-running `updateMultiplier()` with an ordinary token acquisition (`transfer`/`transferFrom`) into the attacker's address.
- Unstaking immediately after the rate updates to lock in gains ≈ transferring the now-scaled balance back out (to an exchange, another wallet, or simply holding it) immediately after the multiplier flips.
- The report's noted lack of a sufficient deterrent fee applies even more strongly here: ordinary ERC-20 `transfer`/`transferFrom` calls in this precompile carry no fee analogous to `wstTAO`'s 0.2% staking fee, so the attack's only cost is gas.

### Impact Explanation
Any address holding, or able to quickly acquire, a balance of a token instantiated on `AssetV2` that uses the instant `update_multiplier` failsafe as its periodic reward-distribution mechanism (rather than the scheduled `updateUIMultiplier`) can extract a disproportionate share of the rebase yield that should belong only to holders who held the token throughout the accrual window. This is a value-theft/dilution attack against the other token holders: the front-runner's UI-scaled balance jumps by the full multiplier delta with zero holding time, while the accrued value ultimately comes from the token's economics representing real off-chain rewards, so legitimate long-term holders receive a diluted share. This matches the report's core impact category (unfair reward extraction / fund loss for legitimate participants), reachable purely by an unprivileged transaction sender monitoring the mempool for the operator's `updateMultiplier` call.

### Likelihood Explanation
- The `OPERATOR_ROLE`-gated `update_multiplier` call is a normal, non-privileged-to-observe mempool transaction; any token whose issuer periodically calls it to publish off-chain-accrued yield is trivially front-runnable.
- No minimum holding period, transfer fee, or per-holder accrual timestamp exists in the shared precompile logic to prevent a "buy right before / sell right after" strategy.
- The scheduled `updateUIMultiplier` path already exists and mitigates this exact issue by requiring `effective_at` to be in the future [6](#0-5) , which strongly implies the precompile authors are aware of the front-running risk of instantaneous updates — but the unsafe instant path remains available and is explicitly named a "failsafe," inviting operators to use it for routine updates, especially since it is the only path in `AssetV1`/pre-Cobalt tokens.
- Likelihood scales with how attractive the deployed token's yield rate is and how actively its `updateMultiplier` calls are monitored — directly mirroring the report's caveat about staking-fee/APY thresholds affecting exploit profitability.

### Recommendation
- Deprecate or explicitly discourage using the instant `update_multiplier` for periodic yield/reward distribution; document that only `update_ui_multiplier` (scheduled, future-dated) should be used for economically meaningful multiplier changes.
- Consider adding a mandatory minimum delay (non-zero `effective_at - now`) even to the "failsafe" path, or restricting the instant path to emergency/corrective use only (e.g., bounded to reverting an erroneous scheduled update) rather than allowing it to apply brand-new economic increases atomically.
- Alternatively, snapshot/checkpoint balances (or accrue per-holder reward using a Compound/Aave-style index) so that newly-acquired balances only start earning from their acquisition block rather than uniformly from the last multiplier snapshot.

### Proof of Concept
1. A B20 token creator deploys an `AssetV2` token representing a yield-bearing asset and periodically calls `updateMultiplier(newMultiplier)` (the instant path) to publish accrued off-chain yield, exactly as `wstTAO.updateExchangeRate()` does.
2. Attacker watches the mempool for the operator's `updateMultiplier` transaction.
3. Attacker submits (with higher gas / same block ordering) a normal `transfer`/`transferFrom` moving a large balance into their own address just before the operator's transaction is included.
4. `update_multiplier` executes, calling `token.accounting_mut().set_multiplier(new_multiplier)` immediately [7](#0-6) ; the attacker's raw balance is now scaled by the new multiplier the instant `scaled_balance_of`/`balance_of_ui` is read [8](#0-7) , exactly as if they had held the balance for the entire accrual period.
5. Attacker transfers the balance back out (e.g., to redeem, sell, or return to the lender) immediately after, having captured the full period's rebase gain for a few seconds of exposure — precisely the `wstTAO` `wrap()`/`requestUnstake()` sandwich reproduced against the multiplier-update instant path.

    /// Instantaneous failsafe. Writes the current multiplier immediately, clearing any pending
    /// update and (for a still-live schedule) emitting `UIMultiplierUpdateCancelled`. Emits BOTH
    /// the deprecated V1 `MultiplierUpdated` event (kept for backward compatibility with existing
    /// indexers) and the ERC-8056 `UIMultiplierUpdated` event.
    fn update_multiplier(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        new_multiplier: U256,
        privileged: bool,
    ) -> Result<()> {
        let now = token.accounting().timestamp()?;
        self.ensure_operator_role(token, caller, privileged)?;
        if new_multiplier.is_zero() || new_multiplier > Self::MAX_UI_MULTIPLIER {
            return Err(BasePrecompileError::revert(IB20Asset::InvalidMultiplier {}));
        }
        let pending_multiplier = U256::from(token.accounting().pending_multiplier()?);
        let pending_effective_at = U256::from(token.accounting().pending_effective_at()?);
        let live_pending = pending_effective_at > now;

        let old = self.effective_multiplier(token)?;
        token.accounting_mut().set_multiplier(new_multiplier)?;
        if pending_effective_at != U256::ZERO {
            token.accounting_mut().clear_pending_multiplier_and_effective_at()?;
        }
        if live_pending {
            token.accounting_mut().emit_event(
                IB20Asset::UIMultiplierUpdateCancelled {
                    cancelledMultiplier: pending_multiplier,
                    cancelledEffectiveAt: pending_effective_at,
                }
                .encode_log_data(),
            )?;
        }
        // Emit the deprecated V1 event alongside the ERC-8056 event so indexers watching the legacy
        // `MultiplierUpdated` topic keep working through the transition.
        token.accounting_mut().emit_event(
            IB20Asset::MultiplierUpdated { multiplier: new_multiplier }.encode_log_data(),
        )?;
        token.accounting_mut().emit_event(
            IB20Asset::UIMultiplierUpdated {
                oldMultiplier: old,
                newMultiplier: new_multiplier,
                effectiveAtTimestamp: now,
            }
            .encode_log_data(),
        )
    }

    fn to_scaled_balance(&self, token: &B20AssetToken<S, A>, balance: U256) -> Result<U256> {
        let multiplier = self.effective_multiplier(token)?;
        let product =
            balance.checked_mul(multiplier).ok_or_else(BasePrecompileError::under_overflow)?;
        Ok(product / B20AssetStorage::WAD)
    }

    fn to_raw_balance(&self, token: &B20AssetToken<S, A>, balance: U256) -> Result<U256> {
        let multiplier = self.effective_multiplier(token)?;
        let product = balance
            .checked_mul(B20AssetStorage::WAD)
            .ok_or_else(BasePrecompileError::under_overflow)?;
        Ok(product / multiplier)
    }

    fn scaled_balance_of(&self, token: &B20AssetToken<S, A>, account: Address) -> Result<U256> {
        let balance = token.accounting().balance_of(account)?;
        self.to_scaled_balance(token, balance)
    }

        Self::OPERATOR_ROLE

    // --- ERC-8056 scheduled multiplier (introduced at AssetV2, Cobalt) ---

    /// Lazy current multiplier: flips to a matured pending target once `now >= effectiveAt`.
    fn multiplier(&self, token: &B20AssetToken<S, A>) -> Result<U256> {
        self.effective_multiplier(token)
    }

    fn effective_multiplier(&self, token: &B20AssetToken<S, A>) -> Result<U256> {
        let now = token.accounting().timestamp()?;
        let effective_at = token.accounting().pending_effective_at()?;
        if effective_at != 0 && now >= U256::from(effective_at) {
            let pending = token.accounting().pending_multiplier()?;
            // Both setters reject zero, so a stored pending is never zero. Do not fall back to WAD:
            // the Solidity reference also returns the raw pending value.
            debug_assert!(pending != 0, "matured pending multiplier must be non-zero");
            return Ok(U256::from(pending));
        }
        token.accounting().multiplier()
    }

    fn ui_multiplier(&self, token: &B20AssetToken<S, A>) -> Result<U256> {
        self.multiplier(token)
    }

    fn new_ui_multiplier(&self, token: &B20AssetToken<S, A>) -> Result<U256> {
        let now = token.accounting().timestamp()?;
        let effective_at = token.accounting().pending_effective_at()?;
        if U256::from(effective_at) > now {
            return Ok(U256::from(token.accounting().pending_multiplier()?));
        }
        self.multiplier(token)
    }

    fn effective_at(&self, token: &B20AssetToken<S, A>) -> Result<U256> {
        Ok(U256::from(token.accounting().pending_effective_at()?))
    }

    fn balance_of_ui(&self, token: &B20AssetToken<S, A>, account: Address) -> Result<U256> {
        self.scaled_balance_of(token, account)

    fn update_ui_multiplier(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        new_multiplier: U256,
        effective_at: U256,
        privileged: bool,
    ) -> Result<()> {
        let now = token.accounting().timestamp()?;
        self.ensure_operator_role(token, caller, privileged)?;
        if new_multiplier.is_zero() || new_multiplier > Self::MAX_UI_MULTIPLIER {
            return Err(BasePrecompileError::revert(IB20Asset::InvalidMultiplier {}));
        }
        if effective_at <= now {
            return Err(BasePrecompileError::revert(IB20Asset::EffectiveAtInPast {
                effectiveAt: effective_at,
            }));
        }
        if effective_at > U256::from(u64::MAX) {
            return Err(BasePrecompileError::revert(IB20Asset::EffectiveAtTooFar {
                effectiveAt: effective_at,
            }));
        }

        let pending_effective_at = token.accounting().pending_effective_at()?;
        // A live pending blocks a new schedule.
        if U256::from(pending_effective_at) > now {
            return Err(BasePrecompileError::revert(IB20Asset::UIMultiplierUpdateExists {
                effectiveAt: U256::from(pending_effective_at),
            }));
        }
        // Fold a matured pending into the current multiplier before overwriting it.
        if pending_effective_at != 0 {
            let matured = U256::from(token.accounting().pending_multiplier()?);
            token.accounting_mut().set_multiplier(matured)?;
        }

        let old = token.accounting().multiplier()?;
        // Narrowing is safe because the guards above enforce the storage field bounds.
        token
            .accounting_mut()
            .set_pending_and_effective_at(new_multiplier.to::<u128>(), effective_at.to::<u64>())?;
