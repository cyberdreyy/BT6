### Title
Namespace/ServiceAccount/label overwrite regex validation uses unanchored substring matching instead of full-string matching - (File: executors/kubernetes/overwrites.go)

### Summary
`overwriteRegexCheck` (called from `evaluateOverwrite` for `KUBERNETES_NAMESPACE_OVERWRITE`, `KUBERNETES_SERVICE_ACCOUNT_OVERWRITE`, and from `evaluateMapOverwrite` for pod labels/annotations/node selectors) validates job-supplied overwrite values with `regexp.MatchString`, which succeeds on any substring match rather than requiring the whole value to match. Runner performs no code-level enforcement of full-string matching, so the security boundary depends entirely on the operator writing a fully anchored (`^...$`) regex in `NamespaceOverwriteAllowed`/`ServiceAccountOverwriteAllowed`.

### Finding Description
The reachable path is:
`createOverwrites` (executors/kubernetes/overwrites.go:147) reads `variables.Get(NamespaceOverwriteVariableName)` (attacker-controlled CI/CD job variable `KUBERNETES_NAMESPACE_OVERWRITE`) and passes it to `o.evaluateOverwrite("Namespace", config.Namespace, config.NamespaceOverwriteAllowed, namespaceOverwrite, logger)` [1](#0-0) .

`evaluateOverwrite` calls `overwriteRegexCheck(regex, overwriteValue)` [2](#0-1) , and if it returns nil, `overwriteValue` (the entire, unmodified attacker-supplied string) is used verbatim as the namespace [3](#0-2) .

`overwriteRegexCheck` performs the check with `r.MatchString(value)`: [4](#0-3) 
`regexp.MatchString` in Go reports whether the pattern matches *anywhere* in the string, not whether it matches the whole string, unless the pattern itself is anchored with `^` and `$`. Because Runner never anchors the pattern internally (e.g., it does not wrap it as `^(?:regex)$` or compare `FindString(value) == value`), the effective security boundary is only as strong as the operator's own regex authoring. The same helper is reused for `ServiceAccountOverwriteAllowed`, `PodLabelsOverwriteAllowed`, `PodAnnotationsOverwriteAllowed`, and `NodeSelectorOverwriteAllowed` (via `evaluateMapOverwrite`, line 683), so the same class of gap applies to all of these overwrite controls.

Exploitability caveat: the value that passes validation is used as-is for the Kubernetes namespace field, and Kubernetes itself enforces RFC 1123 DNS-label syntax on namespace names at the API level, so payloads containing characters like `;` or embedded newlines (as suggested in the fuzz idea) would be rejected by the Kubernetes API when the namespace/pod is created — this specific bypass vector (`kube-system;allowed-x`, embedded newlines) does not produce a usable cross-namespace scheduling result. The genuinely exploitable variant is narrower: if the operator's regex is under-anchored (e.g., missing `$`, such as `^ci-`), an attacker can supply any syntactically-valid Kubernetes namespace name that merely *starts with* (or contains, if `^` is also missing) the allowed prefix/substring, e.g., `ci-anything-outside-intended-scope`, which is accepted as a full, valid namespace name distinct from what the operator intended to allow.

### Impact Explanation
If the operator misconfigures `NamespaceOverwriteAllowed`/`ServiceAccountOverwriteAllowed` with an unanchored or partially-anchored regex, an unprivileged job can widen the effective set of permitted namespaces/service accounts beyond the intended pattern (e.g., beyond a strict `^ci-<project-id>$` scheme to any `ci-*` namespace), potentially landing the job's pod in a namespace or under a service account with stronger RBAC permissions than the operator intended for that project. This does not defeat a correctly anchored regex, and does not bypass Kubernetes' own namespace-name validation.

### Likelihood Explanation
Requires a precondition entirely outside Runner's control: the cluster operator must configure `NamespaceOverwriteAllowed` (or the other `*OverwriteAllowed` regex settings) without full anchoring. If the operator follows the common/recommended pattern of `^prefix-.*$`, the substring-matching semantics are neutralized. This is a latent hardening gap in Runner rather than a directly, universally exploitable bug — it manifests only in combination with a specific class of admin regex mistake, and the most severe fuzzed inputs (semicolons, newlines) are independently blocked by Kubernetes' namespace-name validation.

### Recommendation
Enforce full-string matching in `overwriteRegexCheck` regardless of how the operator writes the regex, e.g., compare `r.FindString(value) == value` or compile the pattern as `^(?:` + regex + `)$` before calling `MatchString`. Apply this to all callers (`evaluateOverwrite`, `evaluateBoolControlledOverwrite`, `evaluateMapOverwrite`) so operator intent is enforced by Runner itself and doesn't rely on correct regex anchoring by every operator.

func (o *overwrites) evaluateOverwrite(
	fieldName, value, regex, overwriteValue string,
	logger buildlogger.Logger,
) (string, error) {
	if regex == "" {
		logger.Debugln("Regex allowing overrides for", fieldName, "is empty, disabling override.")
		return value, nil
	}

	if overwriteValue == "" {
		return value, nil
	}

	if err := overwriteRegexCheck(regex, overwriteValue); err != nil {
		return value, err
	}

	if fieldName == "BearerToken" {

	}

	return overwriteValue, nil
}

func overwriteRegexCheck(regex, value string) error {
	var err error
	var r *regexp.Regexp
	if r, err = regexp.Compile(regex); err != nil {
		return err
	}
	if match := r.MatchString(value); !match {
		return &malformedOverwriteError{value: value, pattern: regex}
	}
	return nil
}
