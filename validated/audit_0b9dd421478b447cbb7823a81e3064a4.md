## Finding

### Title
Inconsistent rounding between `GlobalStateEvaluator::reached_agreement` and the protocol's canonical 70% supermajority computation lets a below-threshold weight coalition be treated as "global agreement" - (File: `libsigner/src/v0/signer_state.rs`)

### Summary
`GlobalStateEvaluator::reached_agreement`, which decides consensus on the signer's global state machine (active miner, burn view, active protocol version, tx replay set), uses **floor** division of the 70% threshold, while every other place in the codebase that enforces the same 70% Nakamoto signer-approval threshold (`NakamotoBlockHeader::compute_voting_weight_threshold`, used for block signature/pre-commit aggregation and consensus-critical on-chain signature verification, and the Clarity `get-threshold-weight` in `signers-voting.clar`) uses **ceiling** division. For any `total_weight` where `total_weight * 7` is not a multiple of 10, this creates a one-unit gap in which `reached_agreement` fires on a weight that is strictly below the protocol's real 70% supermajority requirement.

### Finding Description
`reached_agreement` in `libsigner/src/v0/signer_state.rs` is: [1](#0-0) 

```rust
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
```
This is `vote_weight >= floor(total_weight * 7 / 10)`.

Compare this against the canonical threshold used for actual block-signature aggregation and on-chain signature verification, `NakamotoBlockHeader::compute_voting_weight_threshold`: [2](#0-1) 

```rust
pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
    let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
    let total_weight = u64::from(total_weight);
    let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
    u32::try_from((total_weight * threshold) / 10 + ceil)...
}
```
This is `ceil(total_weight * 7 / 10)` - the same rounding style used by the Clarity voting contract's `get-threshold-weight` (`(/ (+ (* total-weight threshold-consensus) u99) u100)`), confirming that ceiling rounding is the intended, protocol-wide definition of "70% supermajority."

Whenever `total_weight * 7` is not evenly divisible by 10 (e.g. `total_weight = 511` from the existing unit test, `ceil = 358` vs `floor = 357`), a vote weight of exactly `floor(total_weight*7/10)` satisfies `reached_agreement` while being strictly below the real, protocol-defined 70% threshold used everywhere else. `reached_agreement` gates `determine_global_state`, `determine_latest_supported_signer_protocol_version`, and `find_majority_prefix_replay_set`: [3](#0-2) [4](#0-3) 

and these outputs feed directly into `check_block_against_state` / `determine_active_signer_protocol_version` in `stacks-signer/src/v0/signer.rs`, as well as `capitulate_miner_view` in `stacks-signer/src/v0/signer_state.rs`: [5](#0-4) [6](#0-5) 

This is directly analogous to the Ajna `moveQuoteToken` bug: a check is evaluated against an internally-inconsistent, weaker snapshot of the required invariant (the LUP/HTP comparison there; the 70% weight threshold here) instead of the value that the rest of the system treats as canonical, so a state transition is accepted (here: "global agreement reached") that would not be accepted under the correctly (ceiling-)computed threshold used for the on-chain-enforced signature aggregation.

### Impact Explanation
This lets the signer's global-state consensus (which determines the active miner view used to gate block proposal acceptance, the active signer protocol version, and the transaction replay set) flip on a coalition weight that is below the actual protocol-mandated 70% supermajority used for real signature aggregation (`compute_voting_weight_threshold`) and on-chain verification (`verify_signer_signatures`). This is an "acting on a stale/incorrect reward-set threshold" condition (High impact category): a signer can capitulate its local miner/protocol-version view to a value that lacks genuine supermajority support, potentially causing it to reject valid blocks under the correct view, or to activate a protocol version/replay-set prematurely, wedging its participation out of step with the rest of the honest set until the rounding gap resolves itself.

### Likelihood Explanation
No majority or attacker action is required. Any reward-set weight distribution where `total_weight * 7` is not a multiple of 10 (i.e., most non-trivially chosen weight totals) is sufficient; the mismatch is triggered by ordinary state-machine-update gossip whenever the aggregated update weight lands on `floor(total_weight*7/10)` but below `ceil(total_weight*7/10)`. This is a systemic quorum-computation flaw reachable purely through normal `StateMachineUpdate` message flow (`handle_state_machine_update` in `stacks-signer/src/v0/signer.rs`), not through majority collusion.

### Recommendation
Change `GlobalStateEvaluator::reached_agreement` (and any other threshold check that is meant to mirror the protocol's 70% supermajority) to use the same ceiling-rounding formula as `NakamotoBlockHeader::compute_voting_weight_threshold`, so that "global agreement" can never be reached with less weight than what the chain's actual signature-verification threshold requires.

### Proof of Concept
1. Configure a reward set with `total_weight = 511` (matches the existing `test_compute_voting_weight_threshold` fixture).
2. `NakamotoBlockHeader::compute_voting_weight_threshold(511) == 358` (ceiling) - this is the real 70% supermajority required for a valid signed block.
3. Have `StateMachineUpdate` messages accumulate so that `GlobalStateEvaluator`'s summed weight for one candidate `SignerStateMachine` (e.g., a particular `current_miner` view) reaches exactly `357`.
4. `GlobalStateEvaluator::reached_agreement(357)` returns `true` (`357 >= floor(511*7/10) == 357`), so `determine_global_state()` returns `Some(state_machine)` even though `357 < 358`, i.e., below the protocol's real 70% threshold.
5. This weaker "global state" propagates into `determine_active_signer_protocol_version`/`capitulate_miner_view`, causing the signer to adopt/act on a miner view, protocol version, or replay set that does not have the genuine 70% supermajority the rest of the protocol (block signature aggregation, on-chain verification) requires.

    pub fn determine_latest_supported_signer_protocol_version(&self) -> Option<u64> {
        let mut protocol_versions = HashMap::new();
        for (address, update) in &self.address_updates {
            let Some(weight) = self.address_weights.get(address) else {
                continue;
            };
            let entry = protocol_versions
                .entry(update.local_supported_signer_protocol_version)
                .or_insert_with(|| 0);
            *entry += weight;
        }
        // find the highest version number supported by a threshold number of signers
        let mut protocol_versions: Vec<_> = protocol_versions.into_iter().collect();
        protocol_versions.sort_by_key(|(version, _)| *version);
        let mut total_weight_support: u32 = 0;
        for (version, weight_support) in protocol_versions.into_iter().rev() {
            total_weight_support += weight_support;
            if self.reached_agreement(total_weight_support) {
                return Some(version);
            }
        }
        None
    }
