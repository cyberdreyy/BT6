### Title
`claimInstantWithdrawRequest` pays funded instant withdrawals at par but never clears `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`, permanently freezing re-requested claims after a same-epoch default - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the RealityCards `payout` bug (funds paid without updating the user's "foreclosed" standing), `claimInstantWithdrawRequest` pays a user their funded instant withdrawal but only resets the aggregate `instantWithdrawsRequests[_user]`. It leaves the per-epoch markers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` untouched. If the same epoch later becomes the default epoch, `_claimDefaultedInstantWithdrawRequest` re-reads the stale per-epoch basis and reverts, permanently freezing the user's genuinely pending claim.

### Finding Description
In `IdleCreditVault.sol`:

- `requestInstantWithdraw` (L356-375) records `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`.
- `claimInstantWithdrawRequest` (L380-393) burns the user's receipts and zeroes only `instantWithdrawsRequests[_user]`, then pays via `_transferFundedClaim`. The per-epoch entries are never decremented.
- `_claimDefaultedInstantWithdrawRequest` (L842-856), invoked once `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and executes `instantWithdrawsRequests[_user] -= claimBasis` (L848).

All of these events can occur within the same `epochNumber` (instant requests are made, funded via `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`, claimed, and a borrower default is handled, all before `stopEpoch` bumps `epochNumber`). If a user claims a funded request at par and then places a new instant request in the same epoch, `instantWithdrawsRequestsByEpoch[_user][N]` holds `oldClaim + newRequest` while the aggregate `instantWithdrawsRequests[_user]` holds only `newRequest`. After `finalizeDefault` with `defaultRecoveryEpoch == N`, any call to `claimInstantWithdrawRequest` reverts on the underflow at L848 (and additionally `_burn(_user, claimBasis)` at L854 would exceed the user's receipt balance). The revert is atomic and unavoidable, since the user cannot reduce `instantWithdrawsRequestsByEpoch` and receipt-token transfers are disabled (`_transfer` reverts unless caller is the CDO, L939-942).

### Impact Explanation
Permanent freezing of user funds. Any user who (a) claims an instant withdrawal funded in epoch N and (b) submits another instant withdraw request in the same epoch N before a borrower default is finalized loses all ability to claim: the claim path always underflows because the stale per-epoch basis strictly exceeds the aggregate. The locked amount is the user's entire pending instant request. Additionally, the stale `instantWithdrawClaimsByEpoch[N]` inflates `defaultPendingClaimBasis`/reserve sizing at `finalizeDefault`, over-allocating `defaultRecoveryReserve` for a receipt that was already paid, which can leave residual reserve stranded after all real claims settle.

### Likelihood Explanation
Requires a specific but plausible sequence: a funded instant claim, a subsequent instant request in the same epoch, and a borrower default finalized while `defaultRecoveryEpoch` equals that epoch. Instant withdrawals are designed exactly for same-epoch liquidity, and defaults during an active epoch are a supported flow (the whole `defaultInstantWithdrawsFinalized` machinery exists for it). No privileged actor misbehavior is needed — only the honest manager's ordinary calls, sequenced by the attacker around their own requests. The bug is deterministic once the sequence occurs.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch state alongside the aggregate:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
// also clear per-epoch markers so a later default cannot re-read them
uint256 e = epochNumber;
uint256 epochAmount = instantWithdrawsRequestsByEpoch[_user][e];
if (epochAmount != 0) {
    instantWithdrawsRequestsByEpoch[_user][e] = 0;
    instantWithdrawClaimsByEpoch[e] -= epochAmount;
}
_transferFundedClaim(_user, amount);
```

(If requests can span multiple epochs per user, iterate or track which epoch the funded portion belongs to so the decrement matches what was actually paid.)

### Proof of Concept
Foundry-style scenario against `IdleCreditVault` / `IdleCDOEpochVariant` (epochNumber N throughout):

```solidity
// 1. User deposits and requests instant withdraw of X during epoch N
vm.prank(user);
cdoEpoch.requestWithdraw(X, address(tranche)); // instant path

// 2. Manager funds instant claims; collectInstantWithdrawFunds(X) reduces pendingInstantWithdraws
vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds();

// 3. User claims at par: instantWithdrawsRequests[user] = 0,
//    but instantWithdrawsRequestsByEpoch[user][N] == X and
//    instantWithdrawClaimsByEpoch[N] == X remain stale
vm.prank(user);
cdoEpoch.claimInstantWithdrawRequest();

// 4. User requests a new instant withdraw Y in the SAME epoch N
vm.prank(user);
cdoEpoch.requestWithdraw(Y, address(tranche));
// state: instantWithdrawsRequests[user] = Y
//        instantWithdrawsRequestsByEpoch[user][N] = X + Y  (stale X included)

// 5. Borrower defaults in epoch N; manager finalizes recovery
//    -> defaultRecoveryEpoch = N, defaultInstantWithdrawsFinalized = true
_checkDefault();
cdoEpoch.finalizeDefault(recovered, manager);

// 6. User tries to claim Y -> always reverts
//    _claimDefaultedInstantWithdrawRequest: claimBasis = X + Y
//    instantWithdrawsRequests[user] -= claimBasis  => Y - (X + Y) underflows
vm.expectRevert();
vm.prank(user);
cdoEpoch.claimInstantWithdrawRequest();
// Y is permanently frozen; reserve is also over-sized by X
```

The exact revert may surface at L848 (arithmetic underflow) or at `_burn` (L854) depending on ordering; both make the claim unreachable. A fork-level PoC can be built on the existing `test/foundry/IdleCreditVault.t.sol` harness (`_depositWithUser`, `getInstantWithdrawFunds`, `finalizeDefault`) mirroring `testFinalizeDefaultHaircutsPendingInstantRedeems` but with a same-epoch claim-then-re-request sequence.
