The `httpTriggerHandler.callbacks` map in the gateway's HTTP trigger handler is keyed globally by the raw, user-supplied JSON-RPC `id` (`requestID`), not scoped by workflow, owner, or sender. Since auth/rate-limiting happen *before* the global uniqueness check in `setupCallback`, any authenticated-but-unrelated caller who can reach the gateway for *any* workflow they control can pre-claim a `requestID` value and cause `setupCallback` to reject a legitimate, unrelated request for the same ID with `"requestID: %s has already been used"`, exactly mirroring the `SafeGuardFactory`/`Registry` front-running DoS pattern (pre-claim a deterministic identifier in a shared, unauthenticated-write registry to block the legitimate actor's later registration of that same identifier).

### Title
Global, unscoped requestID map in the gateway HTTP trigger handler allows any caller to front-run and DoS another workflow's request by pre-claiming its `id` - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
`httpTriggerHandler.callbacks` is a single map keyed only by the client-supplied JSON-RPC `id` field, shared across *all* workflows and senders on the gateway node. Any caller that can submit an HTTP trigger request (even for their own, unrelated workflow) can insert an entry under an arbitrary `requestID` before another user's request with that same ID arrives, causing the victim's request to be rejected with a "conflict" error. This is the same root cause as the reported `SafeGuardFactory`/`Registry` bug: an unprivileged actor pre-registers a deterministic/attacker-chosen identifier into a shared registry/cache that lacks per-caller scoping, blocking the legitimate party's subsequent registration of that same identifier.

### Finding Description
`setupCallback` performs the uniqueness check purely on `requestID` (the raw request `id`) against the single, node-wide `h.callbacks` map: [1](#0-0) 

This check happens after `authorizeRequest`/`checkRateLimit`, but authorization there is scoped only to *whether the caller may execute the workflow they specified* — it does not scope or namespace `requestID` in any way to the (workflow, owner) pair: [2](#0-1) 

Because the map key is only `requestID` (a plain string map, `map[string]savedCallback`) and is not namespaced by workflowID/owner/sender, a caller who is authorized for *any* workflow can submit a request using an `id` value they expect another user to use for a *different* workflow. If that ID is inserted first, the legitimate request for that ID fails: [3](#0-2) 

This directly parallels the `Registry.register` bug: a shared identifier space with no ownership/ACL binding lets one caller block another caller's use of a shared resource ID.

By contrast, other gateway handlers in the same codebase (`vault` and `confidentialrelay` handlers) mitigate this exact class of bug by prefixing/binding the request ID to the authorized owner before using it as a map key (`owner + vaulttypes.RequestIDSeparator + requestID`), which prevents cross-owner ID collisions: [4](#0-3) 

The HTTP trigger handler lacks this owner/workflow-scoping for its `callbacks` map key, unlike its sibling handlers.

### Impact Explanation
An attacker with legitimate access to trigger *any* HTTP-triggered workflow on a gateway/DON (even their own low-value workflow) can grief other users' workflow executions by guessing or observing `requestID` values (e.g., sequential IDs, UUIDs reused by client libraries, or IDs learned via side channels/logs) and pre-claiming them. This causes denial of service for the affected caller's job execution request ("requestID has already been used" / `jsonrpc.ErrConflict`), preventing a legitimate workflow trigger from being processed until the attacker's stale entry is reaped by `reapExpiredCallbacks` (bounded by `CleanUpPeriodMs`, potentially several minutes). This is an unauthorized denial-of-service against unrelated users' job triggering via the internet-facing gateway, matching the "unauthorized job run" / "cross-user response confusion" impact categories.

### Likelihood Explanation
Exploitation requires the attacker to be an authorized caller for at least one workflow on the shared gateway node (a low bar in a multi-tenant DON/gateway deployment) and to know or guess the victim's intended `requestID`. If client applications use predictable ID schemes (timestamps, counters, or externally-visible correlation IDs), collision is straightforward to engineer; even with random UUIDs, an attacker who can observe outgoing requests (e.g., via logs, shared infra, or timing) could race to claim the ID first. Likelihood is moderate: it depends on ID predictability/observability, but the underlying map-scoping flaw is unconditionally present.

### Recommendation
Scope the `callbacks` map key by workflow/owner (or full authorized identity), not by the raw client-supplied `requestID` alone — mirroring the pattern already used in `core/capabilities/vault` and `core/services/gateway/handlers/confidentialrelay`, where the key incorporates the authorized owner. For example, key `h.callbacks` by `(workflowID, requestID)` or `(authorizedOwner, requestID)` so that no caller can occupy or collide with another caller's request-ID namespace.

### Proof of Concept
1. Attacker registers/owns Workflow A and is authorized to call `workflows.execute` on it.
2. Attacker predicts or observes that Victim's client is about to send a `workflows.execute` request for Workflow B with `id = "victim-req-42"`.
3. Attacker sends `HandleUserTriggerRequest` with `id = "victim-req-42"` for Workflow A first; `setupCallback` inserts `h.callbacks["victim-req-42"]`. [5](#0-4) 
4. Victim's legitimate request for Workflow B with the same `id` arrives; `setupCallback` finds the key already present and returns `jsonrpc.ErrConflict` ("requestID: victim-req-42 has already been used..."), denying the victim's execution — demonstrated by the existing test `TestHttpTriggerHandler_HandleUserTriggerRequest/duplicate request ID`, which shows the second caller receiving `jsonrpc.ErrConflict` for a reused ID regardless of which workflow the caller belongs to. [6](#0-5)

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
