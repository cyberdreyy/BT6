## Finding

### Title
Shared per-bank liquidation price cache can be overwritten by an unrelated concurrent receivership liquidation, corrupting health/profit checks - (File: `programs/marginfi/src/state/marginfi_account.rs`)

### Summary
Receivership liquidation (`start_liquidation` / `end_liquidation`) snapshots oracle prices into a **shared, per-Bank** cache (`BankCache.liquidation_price_rt`/`liquidation_price_twap`) rather than into the liquidator-specific `LiquidationRecord`. This is architecturally the same class of bug as the reported Prover issue: a hierarchical/dependent computation relies on "the latest" value stored in a single shared slot, and that slot can be silently overwritten by an unrelated, newer write before the dependent computation (the matching `end_liquidation`) consumes it.

### Finding Description
`start_receivership` calls `write_liquidation_price_cache_from`, which for every bank touched by the liquidated account unconditionally overwrites `bank.cache.liquidation_price_rt`/`liquidation_price_rt_confidence`/`liquidation_price_twap`/`liquidation_price_twap_confidence` and sets the lock flag, with **no check that the bank's cache is already locked by a different, in-flight liquidation**: [1](#0-0) 

`end_liquidation` (via `HealthPriceMode::Cached`) later reads back from this same shared `bank.cache.liquidation_price_rt`/`twap` fields to compute post-liquidation health and profit caps, asserting only that the lock flag is set: [2](#0-1) 

Because the cache is keyed by `Bank`, not by the specific `LiquidationRecord`/liquidator, any bank shared between two different accounts that are both undergoing receivership liquidation at (nearly) the same time will have its cached price fields overwritten by whichever `start_liquidation` lands most recently. The comment in `BankCache` explicitly acknowledges the lock is meant to guard against "edits between start and end," but the guard is a simple boolean flag rather than a scoped/ownership check, and `start_receivership` never checks the pre-existing state of the flag before writing: [3](#0-2) 

Sequence:
1. Liquidator A submits `start_liquidation` on unhealthy Account A, which shares Bank X with many other users. Bank X's cache is populated with A's price snapshot and locked.
2. Before A's `end_liquidation` lands, an attacker (or a colluding/incidental second liquidator) submits `start_liquidation` on a different unhealthy Account B that also touches Bank X. This unconditionally overwrites Bank X's `liquidation_price_rt`/`twap` fields with B's snapshot (re-setting the already-set lock flag).
3. A's `end_liquidation` now executes using `HealthPriceMode::Cached`, reading Bank X's price as B's snapshot instead of A's original snapshot. The `check!(bank.cache.is_liquidation_price_cache_locked(), ...)` guard still passes because the flag remains set — it does not verify the cache belongs to A's operation.
4. `clear_liquidation_price_cache_locks` then clears Bank X's lock as part of A's `end_receivership`, even though the values currently stored there are actually B's, leaving B's subsequent `end_liquidation` to fail the `is_liquidation_price_cache_locked` check with `MarginfiError::InternalLogicError`, or to itself read/clear a cache state it does not own.

### Impact Explanation
- **Denial of service to legitimate liquidators**: Analogous to the original report, an unrelated liquidation on a shared bank invalidates the price data a legitimate, in-flight liquidation depends on. The victim liquidator's `end_liquidation` can revert (`InternalLogicError`) or compute incorrect pre/post health using another liquidation's prices, causing `WorseHealthPostLiquidation` failures for what would otherwise be a legitimate liquidation, wasting gas and letting a genuinely unhealthy account remain unliquidated for longer.
- **Exploitable misvaluation with financial effect**: Because the profit cap (`Seized <= Repaid * (1 + max_fee)`) and the "no worse health" check in `end_receivership` are computed from the corrupted cached prices, an attacker who can arrange for their own trivial liquidation (Account B) to land between a victim's `start_liquidation`/`end_liquidation` pair can inject an arbitrary price snapshot (subject to B's own oracle-derived values at that time) into the check used to validate A's liquidation, potentially allowing a colluding liquidator to extract more value than the configured `liquidation_max_fee` should permit, or to pass a liquidation that should have failed the health-improvement requirement.

### Likelihood Explanation
Likelihood is comparable to the original report: it requires a bank that is shared across multiple accounts undergoing receivership liquidation in a tight window, and the ability to time a second `start_liquidation` between a victim's `start`/`end` pair. Popular collateral/borrow banks (e.g. USDC, SOL) are exactly the banks most likely to have multiple simultaneously-unhealthy accounts, especially during volatile markets when many liquidations occur in a short period — the same condition ("multiple unproven/pending states available") that the original report identifies as increasing likelihood.

### Recommendation
Scope the liquidation price cache to the specific liquidation instance rather than to the shared `Bank` account — e.g., store the snapshot directly in the `LiquidationRecord` (already used for `asset_value_maint`/`liability_value_maint`/equity values) instead of `BankCache`, or add an explicit check in `write_liquidation_price_cache_from`/`start_receivership` that fails if `bank.cache.is_liquidation_price_cache_locked()` is already true, so that a bank involved in one in-flight receivership liquidation cannot be used to start a second, overlapping one.

### Proof of Concept
1. Configure Bank X (e.g. USDC) as collateral/borrow for two independent accounts, A and B, both currently unhealthy enough to be liquidatable.
2. Tx1: `start_liquidation(A)` (touches Bank X) → Bank X cache locked with A's price snapshot.
3. Before Tx1's matching `end_liquidation(A)` lands, submit Tx2: `start_liquidation(B)` (also touches Bank X) → Bank X cache overwritten with B's snapshot, lock flag re-set.
4. Submit `end_liquidation(A)` using `HealthPriceMode::Cached`: it reads B's price values from Bank X's cache instead of A's, producing an incorrect post-liquidation health/profit computation for A's liquidation.
5. Submit `end_liquidation(B)`: depending on ordering, either fails `MarginfiError::InternalLogicError` (cache already cleared by A's end) or uses a lock it never actually owned.

    fn write_liquidation_price_cache_from(
        &self,
        liq_cache: &LiquidationPriceCache,
        index: usize,
    ) -> MarginfiResult<()> {
        let mut bank = self.bank.load_mut()?;
        let zero_price = OraclePriceWithConfidence {
            price: I80F48::ZERO,
            confidence: I80F48::ZERO,
        };
        let price_rt = liq_cache
            .get_price(OraclePriceType::RealTime, index)
            .unwrap_or(zero_price);
        let price_twap = liq_cache
            .get_price(OraclePriceType::TimeWeighted, index)
            .unwrap_or(zero_price);

        bank.cache.liquidation_price_rt = price_rt.price.into();
        bank.cache.liquidation_price_rt_confidence = price_rt.confidence.into();
        bank.cache.liquidation_price_twap = price_twap.price.into();
        bank.cache.liquidation_price_twap_confidence = price_twap.confidence.into();
        bank.cache.set_liquidation_price_cache_locked();

        Ok(())
    }
