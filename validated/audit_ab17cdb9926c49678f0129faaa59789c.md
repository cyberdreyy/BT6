### Title
Stale Rejection Weight Never Retracted in Node-Side Signer Tally — Liveness Wedge in Block Signing Coordinator - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The node-side `StackerDBListener` maintains an independent tally of per-signer weight (`BlockStatus.total_weight_approved` / `total_weight_rejected`) that `signer_coordinator.rs` uses to decide whether a block has been globally accepted or rejected. Unlike the signer's own `SignerDb`, which correctly retracts a signer's prior rejection when that same signer later signs the block, the node's tally never retracts rejection weight when the same signer subsequently sends an acceptance for the same block hash. A signer's weight can therefore remain permanently counted toward `total_weight_rejected` even after that signer has switched to accepting/signing the block, corrupting the miner's aggregated-weight vs. verified-accepts accounting and enabling a liveness wedge that can cause the miner to abandon a block that ultimately gathers full signer consensus.

### Finding Description
`BlockStatus` tracks two independently-accumulated totals: [1](#0-0) 

On `Accepted`, weight is added gated only on whether the slot already exists in `gathered_signatures`: [2](#0-1) 

On `Rejected`, weight is added gated only on whether the slot has been inserted into `responded_signers` (a one-time-ever flag): [3](#0-2) 

Nowhere in this file is `total_weight_rejected` decremented when a signer that previously rejected later sends a valid `Accepted` for the same `block_sighash` — the accept branch only checks/updates `gathered_signatures`, never touches or clears the rejection tally. This is the direct analog of the reported bug class: an operation that must keep two related accounting buckets consistent (here, "which outcome does this signer's weight count toward") updates one bucket (`gathered_signatures`/`total_weight_approved`) but silently leaves the other (`total_weight_rejected`) stale, instead of correcting it, exactly as `_withdraw` updated `caller`/`receiver` state but left `owner`'s rewards state stale/lost.

Crucially, the project has already identified and fixed this exact bug class once, but only in the *signer's own* local `SignerDb`: [4](#0-3) 

That fix is verified by a dedicated regression test showing that when a signature is added for a signer who previously rejected, the rejection record is cleared: [5](#0-4) 

The miner's independent tally in `stackerdb_listener.rs`, however, was never given the equivalent fix — it is a separate code path/data structure (`BlockStatus` in-memory maps, not `SignerDb`) consumed by `signer_coordinator.rs` to decide `SignersRejected` vs. accepted: [6](#0-5) 

Reject-then-accept for the same block hash by the same signer is not a contrived edge case — it is documented, tested, and expected protocol behavior (e.g. asynchronous validation races and reconsideration of certain reject reasons): [7](#0-6) [8](#0-7) 

### Impact Explanation
Because `signer_coordinator.rs` evaluates the reject condition (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`, i.e. >30% blocking minority) eagerly on every incoming message, stale/superseded rejection weight from signers who later legitimately signed can combine with other signers' rejections (transient or genuine) to cross the blocking-minority threshold even though a real supermajority ultimately accepts the block. This causes the miner to prematurely return `NakamotoNodeError::SignersRejected` and abandon a block that would otherwise have reached full consensus — a liveness wedge on block production/tenure advancement. This requires no majority collusion: it only needs the natural or attacker-driven sequence of a single signer's own two messages (reject, then accept) for the same block hash, something fully within that signer's unilateral control ("one-slot ... plus gossip").

### Likelihood Explanation
High. Reject-then-accept sequences for the same block hash are a normal, documented, and tested part of the v0 signer protocol (validation races, reconsiderable rejection reasons, pre-commit re-evaluation), so the corrupting condition arises organically without any adversarial behavior — a malicious single low-weight signer can also trivially and deliberately trigger it to bias the tally.

### Recommendation
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, mirror the fix already applied to `stacks-signer/src/signerdb.rs`: when processing `BlockResponse::Accepted` for a slot that is present in `responded_signers` due to a prior rejection, subtract that signer's weight from `total_weight_rejected` (and/or remove the slot from whatever set was used to count it) before/along with adding it to `total_weight_approved`, so a signer's weight counts toward exactly one outcome at a time, restoring the `total_weight_approved + total_weight_rejected <= total_weight` invariant.

### Proof of Concept
1. Configure a `signer_coordinator`/`stackerdb_listener` test harness with several signers of known weight, e.g. weights `[20, 20, 20, 20, 20]`, `weight_threshold = 70`.
2. Have signer A (weight 20) send a `BlockResponse::Rejected` for block hash H → `total_weight_rejected = 20`.
3. Have signer B (weight 20) send a `BlockResponse::Rejected` for H → `total_weight_rejected = 40` (already exceeds the 30 blocking-minority margin: `40 + 70 > 100`), triggering `SignersRejected` in `signer_coordinator.rs` at line 512-513 before signers A, B, C, D, E all subsequently send `Accepted` for H.
4. Observe that even though signers A–E all eventually send valid `Accepted` responses for H (100% approving weight), the coordinator already exited with `NakamotoNodeError::SignersRejected` and never reconsiders, because `total_weight_rejected` for A and B is never retracted by their later acceptances — reproducing the stale-tally wedge described above (assert on `wait_for_signer_signatures`'s return value / `total_weight_rejected` field of `BlockStatus` after the full accept sequence, showing it still reflects A and B's stale rejections).

Order matters here: the chainstate re-check runs first and produces an explicit
(sticky) rejection when the block now conflicts with a signed one. The conflict
guard behind it is the silent backstop for what that re-check cannot see, and
silence keeps the door open to sign later once the conflict goes stale. Two
blind spots make the guard necessary:

- the re-check only ever looks at _one_ tenure (a tenure-change block's parent,
  or any other block's own), so a signed sibling at the same height in a third
  tenure is invisible to it;
- the `DuplicateBlockFound` check that would catch a second block in the same
  tenure lives in `check_proposal` and runs only at proposal arrival, never
  again. A block that crosses the pre-commit threshold minutes later has no
  other guard, which is what the own-tenure branch above covers.
