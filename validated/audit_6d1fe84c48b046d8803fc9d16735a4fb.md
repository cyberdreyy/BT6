### Title
`depositAA`/`depositBB` mint tranche tokens at a donation-inflatable price with no slippage protection - (contracts/IdleCDO.sol)

### Summary
`IdleCDO._deposit` mints tranche tokens as `_amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` with no `minSharesOut` parameter. The tranche price is derived from `getContractValue()`, which counts the raw `token` balance held by the contract. An unprivileged attacker who is the dominant (or sole) holder of a tranche can inflate its price by directly transferring `token` to the CDO, causing a victim's deposit to mint far fewer tranche tokens than the fair amount; the attacker then redeems and captures the difference.

### Finding Description
The deposit path `depositAA`/`depositBB` → `_deposit` (contracts/IdleCDO.sol:234) calls `_updateAccounting()` (line 247), which computes `totalGain = getContractValue() - lastNAV` and splits gains between AA and BB via `_virtualPriceAux`, updating `priceAA`/`priceBB`. `getContractValue()` includes `_contractTokenBalance(token)` (unlent balance), so any direct `token` transfer to the contract raises NAV and therefore raises the saved tranche price on the next interaction. `_mintSharesAtCurrPrice` (line 437) then mints `_amount / _tranchePrice` shares — no lower bound is enforced anywhere in the call chain.

Attack sequence (running phase, normal mode):
1. Attacker becomes the dominant holder of, e.g., the AA tranche (any KYC'd lender can deposit).
2. Attacker sends `D` underlying tokens directly to the CDO contract (a plain ERC20 `transfer`, bypassing `_deposit`, `_guarded`, and `_checkSameBlock`).
3. Victim calls `depositAA(A)`. `_updateAccounting` sees `totalGain ≈ D`, pushes it into `priceAA` (attacker receives most of it as the dominant holder, minus `fee` and the BB split), then the victim mints `A / inflatedPrice` tranche tokens — arbitrarily few if `D` is large.
4. Attacker calls `withdrawAA` in a later block (`_checkSameBlock` only blocks same-block deposit+withdraw by the same caller; the donation was not a deposit) and redeems almost the entire NAV, including most of the victim's `A`.

The same path exists in `IdleCDOCreditVault._deposit` (contracts/IdleCDOCreditVault.sol:191-212), where `_managedContractValue()` feeds `_virtualPriceAux` and `_mintSharesAtCurrPrice` (line 344) again mints without a minimum.

### Impact Explanation
Direct theft of depositor funds: for a victim deposit of `A` with attacker-donated `D`, the victim's claim is worth roughly `A * NAV_before / (NAV_before + D)`, so the loss approaches 100% of `A` as `D` grows. The attacker recovers `D` plus the stolen fraction of `A` on redemption, netting approximately `A * D / (NAV + D)` minus performance `fee` and the share of the donation attributed to the other tranche (bounded by `trancheAPRSplitRatio`/`FULL_ALLOC`). Profit is positive whenever the attacker controls a large enough fraction of the minted tranche and `A` is comparable to or smaller than `D`.

### Likelihood Explanation
Requires an unprivileged attacker to be the dominant holder of a tranche class (achievable during guarded-launch/early liquidity or in a thin BB tranche) and capital `D` on the order of the victim deposit. No privileged role, oracle manipulation, or default is needed. Existing guards do not stop it: `_guarded` only caps deposit size, `_checkDefault` only reverts on *price decreases* (a donation is a gain), `skipDefaultCheck`/`Default` revert is loss-only, `_checkSameBlock` doesn't apply to raw transfers, and there is no skim/donation-isolation mechanism on the IdleCDO deposit path.

### Recommendation
Add a `minSharesOut` (minimum tranche tokens) parameter to `depositAA`/`depositBB`/`deposit` and revert inside `_deposit` if `_minted < minSharesOut`. Optionally also exclude unexpected `token` balance from `getContractValue()` or add a skim/sweep for donated underlying so donations cannot move tranche price before accounting.

### Proof of Concept
Foundry fork test (schematic, mainnet fork against a live IdleCDO such as an idleUSDC senior/junior CDO):

```solidity
// test/foundry/DonationInflation.t.sol
function testDepositDonationInflation() public {
    // 1. attacker deposits to become dominant AA holder
    deal(token, attacker, 1_000_000e6);
    vm.startPrank(attacker);
    IERC20(token).approve(cdo, type(uint256).max);
    cdo.depositAA(500_000e6);
    vm.stopPrank();

    uint256 priceBefore = cdo.virtualPrice(cdo.AATranche());

    // 2. attacker donates D directly (raw transfer, no guards)
    uint256 donation = 300_000e6;
    vm.prank(attacker);
    IERC20(token).transfer(cdo, donation);

    // 3. victim deposits A; shares minted at inflated price
    uint256 A = 100_000e6;
    deal(token, victim, A);
    vm.startPrank(victim);
    IERC20(token).approve(cdo, A);
    uint256 expected = A * 1e18 / cdo.virtualPrice(cdo.AATranche()); // preview
    uint256 minted = cdo.depositAA(A);
    vm.stopPrank();

    uint256 priceAfter = cdo.virtualPrice(cdo.AATranche());
    assertGt(priceAfter, priceBefore);
    // victim's shares are worth << A
    assertLt(minted * priceAfter / 1e18, A * 90 / 100);

    // 4. attacker withdraws (next block) and profits
    vm.roll(block.number + 1);
    vm.prank(attacker);
    uint256 out = cdo.withdrawAA(IERC20(cdo.AATranche()).balanceOf(attacker));
    assertGt(out, 500_000e6 + donation); // recovered donation + victim's loss
}
```

Note: I verified the mint path, `_updateAccounting` gain split, `_virtualPriceAux`, and the absence of a `minOut` parameter, but I could not fully confirm in this pass whether `IdleCDOCreditVault`'s `_managedContractValue`/epoch gating or any periphery skim function already neutralizes direct `token` donations on the credit-vault variant; the base `IdleCDO` path (`getContractValue` counting unlent `token` balance) is exploitable as described.
