### Title
Loss-adjusted stopEpoch only haircuts the latest request epoch; older pending receipts still pay out at par, draining the funded reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary

`IdleCreditVault` tracks a user's loss-adjusted receipt via the single pointer `lastWithdrawRequest[_user]` and applies `lossRecoveryPriceByEpoch` only to receipts recorded under that epoch. Receipts recorded under earlier epochs are silently exempted from the haircut and are later paid at par through `_claimFundedWithdrawRequest`, even though `collectWithdrawFunds` funded the *aggregate* `pendingWithdraws` at the reduced recovery price. This is the analog of CVE-2024-6774's use-after-free class: a stale pointer (`lastWithdrawRequest`) continues to reference only the newest epoch while an older receipt survives past the state transition that should have consumed/haircut it, breaking the "one receipt, one haircut-adjusted payout" invariant.

### Finding Description

In `requestWithdraw`, a user may hold withdraw receipts spanning multiple epochs: the code comments explicitly allow a second request before claiming the first ("he will have to wait for another epoch to claim both requests"), and each request appends to `withdrawsRequestsByEpoch[user][currentEpoch]` and overwrites `lastWithdrawRequest[user] = currentEpoch` (lines 243–295).

When a subsequent `stopEpoch` underfunds the pending bucket (`stopEpochWithDuration` / loss path), `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` over the **whole** `pendingWithdraws` aggregate — which includes the older epoch's receipts — and stores it under the current `epochNumber` (lines 411–430).

On claim, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and clears only that epoch's basis via `_clearWithdrawClaimForEpoch` (lines 789–801, 811–837). The older epoch's entry in `withdrawsRequests[user]` remains and is then paid **at par** by `_claimFundedWithdrawRequest` (lines 319–350), because the epoch-wait check only compares `epochNumber <= lastWithdrawRequest[_user]` — now reset to 0.

The funding math assumes every pending receipt accepts `recoveryPrice`; paying any subset at 100% makes the strategy's funded underlying insufficient for the remaining loss-adjusted claimants.

### Impact Explanation

Direct insolvency / theft: an attacker holding multi-epoch pending receipts withdraws more underlying than their pro-rata haircut share. The strategy holds only `pendingBasis * recoveryPrice`, so the excess paid at par is taken from funds reserved for other users' loss-adjusted claims, leaving later claimants' transactions to revert on insufficient balance (permanent freezing/theft of their funded yield). Loss scales with `pendingBasis * (1 - recoveryPrice)` attributed to the par-paid portion — e.g., a 50% recovery with half the pending basis belonging to the attacker's older epoch lets the attacker extract `0.5 * pendingBasis` extra.

### Likelihood Explanation

Requires only unprivileged actions: two `requestWithdraw` calls in different epochs (allowed by design), then one loss-adjusted `stopEpoch` (honest manager/borrower sequence — e.g., `stopEpochWithDuration` with realized loss, which is a normal operating path). No guard prevents it: `requestWithdraw`'s check at lines 263–271 only blocks a new request when the *previous* `lastWithdrawRequest` epoch already has a nonzero `lossRecoveryPriceByEpoch` — at the time of the second request no loss has occurred yet. The attacker simply needs pending receipts outstanding when a partial loss materializes, which any KYC-passed lender can arrange by splitting requests across an epoch boundary.

### Recommendation

Apply the loss haircut per receipt, not per `lastWithdrawRequest` pointer: when `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]`, record the funding epoch range (or mark all outstanding `withdrawsRequestsByEpoch` entries as subject to that price), and have `_claimFundedWithdrawRequest` revert/redirect to the loss-adjusted path for any user receipt whose epoch predates the funding epoch while a loss price exists. Alternatively, store the haircut basis globally (e.g., a per-user `lossAdjustedBasis`) covering all receipts pending at the loss-adjusted stop.

### Proof of Concept

Foundry fork test sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testLossAdjustedOlderReceiptPaysAtPar() external {
    uint256 amount = 10000 * ONE_SCALE;
    // attacker + victim deposits
    idleCDO.depositAA(amount);                       // attacker
    address victim = makeAddr('victim');
    _depositWithUser(victim, amount, true);

    // epoch 0: attacker requests withdraw #1 (epochNumber = 0)
    _startEpochAndCheckPrices(0);
    cdoEpoch.requestWithdraw(attackerTrancheBal / 2, address(AAtranche));
    _stopEpochAndCheckPrices(0, apr, expectedFunds); // epochNumber -> 1, receipt 1 still pending (don't claim)

    // epoch 1: attacker requests withdraw #2 -> lastWithdrawRequest = 1
    cdoEpoch.requestWithdraw(attackerTrancheBal / 2, address(AAtranche));
    // victim also requests -> pendingWithdraws includes all three receipts
    vm.prank(victim);
    cdoEpoch.requestWithdraw(victimTrancheBal, address(AAtranche));

    _startEpochAndCheckPrices(1);
    // stopEpochWithDuration realizes a loss: borrower funds only recoveryPrice * pendingBasis
    // (drive collectWithdrawFunds with _amount < pendingWithdraws)
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 funded = pending / 2; // 50% recovery
    deal(defaultUnderlying, borrower, funded + interestPart);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, lossAmount);   // stores lossRecoveryPriceByEpoch[epochNumber]

    // attacker claims: epoch-1 receipt haircut (correct),
    // epoch-0 receipt then paid AT PAR by _claimFundedWithdrawRequest
    uint256 pre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(address(this)) - pre;

    // attacker received epoch0Receipt + epoch1Receipt*0.5 > fair 0.5*(epoch0+epoch1)
    assertGt(got, (receipt0 + receipt1) / 2);
    // victim's loss-adjusted claim now reverts/underfunded
    vm.expectRevert();
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest();
}
```

Note: I could not fully confirm the exact `epochNumber` value at the moment `collectWithdrawFunds` runs inside `stopEpoch` (the increment happens in `deposit()` while the epoch is running). If the loss price is stored under an `epochNumber` that does not match `lastWithdrawRequest`, the flaw is worse — *no* receipt is haircut and everything pays at par — but the two-epoch scenario above is the minimal version that holds regardless of that ordering, since the older receipt is never reachable by `_claimLossAdjustedWithdrawRequest` either way.
