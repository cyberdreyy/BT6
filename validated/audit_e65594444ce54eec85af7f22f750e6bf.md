### Title
Gateway `WebAPIHandler.HandleLegacyUserMessage` forwards unauthenticated trigger requests to the entire DON with no allowlist enforcement - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The `VaultBooster.deposit` bug class is: an unprivileged caller can submit input (a token) that the contract never validates against its set of "supported" entries, yet the contract still performs the sensitive action (accepting the transfer) and forwards/records it as if it were legitimate. The chainlink analog is in the gateway's `capabilities` (WebAPI trigger) handler: an unprivileged client request is accepted and forwarded to every node of the DON without the allowlist check that the code explicitly marks as missing.

### Finding Description
`handler.HandleLegacyUserMessage` processes inbound gateway messages from unauthenticated HTTP clients (`api.Message`). After basic parsing/timestamp validation, it contains the following: [1](#0-0) 

The comment `// TODO: apply allowlist and rate-limiting here` sits directly before the only remaining check, which merely validates that `msg.Body.Method == MethodWebAPITrigger` — it does **not** verify that the caller (workflow owner / sender identity encoded in the message) is authorized to trigger the target workflow, nor does it apply any rate limit at this layer. Immediately after, the handler builds a request and forwards it to **every member node of the DON**: [2](#0-1) 

This mirrors the `VaultBooster.deposit` flaw: the function performs the state-changing/forwarding action (`don.SendToNode` to all DON members, and registering a `savedCallback` keyed by attacker-supplied `msg.Body.MessageId`) before/without checking whether the request is actually "supported" (i.e., whitelisted for this sender/workflow), just as `deposit` transferred tokens in before checking if the token was a supported/registered boost token.

### Impact Explanation
Because the allowlist gate is a documented TODO and not implemented at this layer, the gateway will relay any well-formed `web_api_trigger` message to all nodes in the configured DON, regardless of who sent it or whether the sender is authorized for the referenced workflow. Depending on what enforcement (if any) exists further downstream on the node side, this creates the potential for unauthorized workflow triggering by any unprivileged client that can reach the gateway's HTTP endpoint — directly matching the "unauthorized job run" acceptance criterion. Additionally, `savedCallbacks` is keyed purely by the client-supplied `msg.Body.MessageId`; combined with the missing allowlist, this could enable cross-user response confusion if two callers happen to reuse or predict a `MessageId` (the map only checks presence, not sender identity) — though this specific class of confusion would need corroboration on the ID generation scheme.

### Likelihood Explanation
The vulnerable code path is reached directly from `ProcessRequest` for any unauthenticated legacy user request routed to this handler's DON (`core/services/gateway/gateway.go` `ProcessRequest`), i.e., from an unprivileged external HTTP client — no special network position, node compromise, or operator privilege is required. The gap is explicitly flagged by the maintainers themselves via the TODO comment, indicating the control is known-incomplete rather than a subtle logic bug, which raises confidence that it is currently unenforced at this layer.

### Recommendation
Implement the allowlist/authorization check called out in the TODO before forwarding a `web_api_trigger` message to the DON: validate that the message's sender/signature is authorized for the target workflow (analogous to rejecting unsupported tokens in `VaultBooster.deposit`), and apply per-sender rate limiting at this handler in addition to the existing `nodeRateLimiter` (which only limits inbound node messages, not user messages). Reject the request with `UnsupportedMethodError`/`HandlerError` style responses (consistent with the rest of the function) if the sender is not allowlisted, rather than proceeding to populate `savedCallbacks` and fan the request out to all DON members.

### Proof of Concept
1. Send a JSON body to the gateway's `/node`-style HTTP endpoint as a legacy message with `Body.Method = "web_api_trigger"`, a valid `webapicap.TriggerRequestPayload` (with a non-zero `Timestamp` within `MaxAllowedMessageAgeSec`), and an arbitrary `Body.DonId` matching a configured DON — no prior authentication, API key, or workflow-ownership proof is required by this handler.
2. `HandleLegacyUserMessage` parses the payload, passes the timestamp check, passes the `Method == MethodWebAPITrigger` check (the only check present where the allowlist TODO is), and proceeds to call `don.SendToNode` for every member of `h.donConfig.Members`.
3. Because no allowlist verification ties the message to an authorized workflow owner, the request is relayed to the entire DON as if it were a legitimate, authorized trigger — demonstrating the missing "supported/authorized" check analogous to the missing token-support check in `VaultBooster.deposit`.

(Note: full confirmation of downstream node-side authorization — which could mitigate real-world impact — was not verified within the available index; a Devin session with full repo/build access would be needed to trace whether node-side capability code re-validates the sender before executing the trigger.)
