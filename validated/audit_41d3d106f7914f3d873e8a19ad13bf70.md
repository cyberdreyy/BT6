### Title
Stale confirmations from a removed multisig member still count toward execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in `multisig2/src/lib.rs` only purges requests that were *created* by the removed member; it does not scan and strip that member's confirmations from other members' pending requests. A confirmation recorded by a member before their removal therefore remains valid and continues to count toward `num_confirmations` when `confirm` is later called by other current members, letting a request execute with fewer than `num_confirmations` distinct *currently authorized* signers.

### Finding Description
`confirm()` computes whether a request has reached quorum purely from the size of the `HashSet<String>` stored in `self.confirmations`, without checking that every entry in that set is still a current member: [1](#0-0) 

`delete_member()` is the only place that scrubs confirmations, but it filters requests by `r.member == member` (i.e., only requests *added by* the removed member) and clears confirmations solely for those requests. Confirmations that the removed member cast on *other* members' requests are left untouched in `self.confirmations`: [2](#0-1) 

Concretely, with `num_confirmations = K` and `N` members:
1. Member A creates request R (not yet confirmed by A necessarily via `add_request_and_confirm`, or confirmed separately).
2. Member B (soon to be removed) calls `confirm(R)`, adding B's identity to `confirmations[R]`.
3. A separate governance request removes B via `DeleteMember`. Since R was added by A (not B), `delete_member`'s cleanup loop skips R entirely — B's confirmation on R survives.
4. Members continue confirming R. When the *live* member count of distinct confirmers reaches `K` — but one of those "confirmers" (B) is no longer a member — `execute_request` fires via `confirm`'s `confirmations.len() as u32 + 1 >= self.num_confirmations` check.

The binding that should hold is: `confirmations counted == confirmations from members currently in self.members`. After a `DeleteMember` action, the actual binding becomes `confirmations counted == confirmations from members currently in self.members` **plus stale confirmations from since-removed members**, i.e. the equality is broken: `|live confirmations| < num_confirmations` while `|counted confirmations| >= num_confirmations`.

### Impact Explanation
This crosses the authorization/threshold boundary explicitly called out as in-scope ("confirmations counted versus live members"). A multisig configured for K-of-N security can be made to execute an arbitrary request (`Transfer`, `FunctionCall`, `AddKey` granting full access, `DeployContract`, etc.) with fewer than K currently-trusted approvers, because a stale confirmation from an already-removed member is silently counted as live. This is a Critical-class issue per the rubric: it allows a multisig request to be executed below the configured threshold, directly enabling unauthorized movement of the account's NEAR/assets or unauthorized key/contract changes.

### Likelihood Explanation
Any multisig that legitimately rotates membership (a routine, expected operational action — replacing a lost/compromised key, offboarding a signer) while there exist other outstanding, not-yet-executed requests that the departing member had already confirmed, is exposed. No malicious deployment or foundation-only precondition is required beyond normal multisig operation (`add_request`, `confirm`, `DeleteMember`) — a departing/compromised member simply needs to have confirmed a pending request before being removed. Because `delete_member` never cross-references `self.confirmations` map keys against the removed member's identity, this triggers deterministically, not merely theoretically.

### Recommendation
When a member is deleted, iterate all requests' confirmation sets (not just those the member authored) and remove the departing member's identity string from each `HashSet<String>` in `self.confirmations`, persisting the updated sets. Alternatively, validate at `confirm`-time (when checking `>= self.num_confirmations`) that every identity present in the stored confirmation set is still contained in `self.members`, discarding/ignoring stale ones before comparing against the threshold.

### Proof of Concept
Given `MultiSigContract::new(members: [A, B, C, D], num_confirmations: 3)`:
1. `A.add_request(R)` — creates request `R` with `receiver_id = self`, e.g. a `Transfer` of the full balance to an attacker-controlled account.
2. `B.confirm(R)` → `confirmations[R] = {B}` (per `confirm()` logic at `multisig2/src/lib.rs:294-315`).
3. Separately, `A.add_request_and_confirm({DeleteMember{member: B}})`, then `C.confirm(...)` and `D.confirm(...)` to execute the removal (3-of-4 reached) — `B` is now removed from `self.members`, but per `delete_member` (`multisig2/src/lib.rs:356-379`) only requests where `r.member == B` are cleaned up; `R` (added by `A`) is untouched, so `confirmations[R]` still contains `B`.
4. `C.confirm(R)` → `confirmations[R] = {B, C}`, size 2, `2+1 < 3`, not yet executed.
5. `D.confirm(R)` → `confirmations.len() as u32 + 1 == 3 >= num_confirmations` → `execute_request(R)` fires, transferring funds — even though the confirming/authorizing set now only contains 3 *counted* entries but only `A(implicit as adder, not confirmer)`... more precisely only `C` and `D` are current members among the 3 confirming identities (`B`, `C`, plus the triggering `D`), i.e. only 2 of 3 "confirmations" are from live members, one below the intended 3-live-member threshold.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
